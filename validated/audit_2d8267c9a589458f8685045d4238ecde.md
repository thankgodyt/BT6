### Title
Missing Minimum Transfer Amount Validation Causes Permanent Token Lock — (`File: near/omni-bridge/src/lib.rs`)

### Summary

`init_transfer` accepts any non-zero token amount as long as `fee < amount`, but never validates that the amount-minus-fee will survive decimal normalization on the destination chain. When a user initiates a NEAR-outbound transfer with an amount smaller than the decimal-scaling factor, their tokens are permanently locked or burned on NEAR while `sign_transfer` will always revert, with no recovery path.

---

### Finding Description

The `init_transfer` function enforces only one amount-related invariant: [1](#0-0) 

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It then locks or burns the full token amount on NEAR: [2](#0-1) 

Later, when a relayer calls `sign_transfer`, the bridge normalizes the amount to the destination chain's decimal representation using floor division: [3](#0-2) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` then enforces: [4](#0-3) 

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

If `amount - fee < 10^(origin_decimals - decimals)`, `normalize_amount` returns 0 and `sign_transfer` panics. The transfer message is **never removed** from storage (removal only happens inside `sign_transfer_callback` on a successful MPC signature), and the locked/burned tokens have no refund path. [5](#0-4) 

---

### Impact Explanation

Tokens are permanently frozen. For a token whose NEAR representation uses 24 decimals and whose EVM representation uses 18 decimals (`diff_decimals = 6`), any transfer of fewer than `1_000_000` base units (after fee deduction) will normalize to zero. The user's tokens are burned or locked on NEAR, the transfer message persists in contract storage indefinitely, and no on-chain mechanism exists to cancel or refund the transfer. This satisfies the allowed impact: **permanent freezing of bridged funds**.

---

### Likelihood Explanation

The entry point is the public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path, callable by any token holder. The condition is triggered whenever:

- A token has a decimal difference between NEAR and the destination chain (common for tokens like USDC with 6 EVM decimals vs. a 24-decimal NEAR wrapper), **and**
- The user sends an amount smaller than `10^(origin_decimals - decimals)` after fee deduction.

This can happen accidentally (user sends "dust") or deliberately (attacker griefs a victim by front-running a deposit and splitting it into sub-threshold amounts, if the token contract allows it). The `InitTransferMsg` struct accepts any `fee: U128` and `amount` is whatever the token contract forwards, so no off-chain filter prevents this. [6](#0-5) 

---

### Recommendation

Add a pre-lock validation in `init_transfer` (or in `init_transfer_internal`) that computes `normalize_amount(amount - fee, decimals)` and requires it to be greater than zero before locking or burning any tokens. The `token_decimals` map is already available at that point. Alternatively, enforce a protocol-wide minimum transfer amount per token that accounts for the decimal scaling factor.

---

### Proof of Concept

1. A NEAR token is registered with `origin_decimals = 24`, `decimals = 18` (6-decimal difference, scaling factor = `10^6`).
2. A user calls `ft_transfer_call` transferring `500_000` base units with `fee = 0` and `recipient = eth:0x...`.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000`). Tokens are burned via `burn_tokens_if_needed`.
4. A relayer calls `sign_transfer`. `normalize_amount(500_000, {origin: 24, decimals: 18}) = 500_000 / 1_000_000 = 0`.
5. `require!(amount_to_transfer > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. `sign_transfer_callback` is never reached; the transfer message remains in storage.
7. The 500,000 base-unit tokens are permanently lost — no cancel, no refund, no retry path exists. [7](#0-6) [8](#0-7)
