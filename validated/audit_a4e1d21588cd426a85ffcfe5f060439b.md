### Title
ChainSync Client `checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot` Instead of Accumulated Peras Certificate Weights, Causing Incorrect Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client evaluates whether a candidate chain beyond the forecast horizon is preferred over the local selection. It hardcodes `emptyPerasWeightSnapshot` instead of reading the accumulated `PerasWeightSnapshot` from the `PerasCertDB`. This mirrors the external report's root cause: a global balance read (`address(this).balance`) that includes funds from a different context — here, the accumulated Peras certificate weights are simply omitted from the comparison, producing a structurally identical accounting mismatch.

---

### Finding Description

When a peer sends a header whose slot is beyond the current forecast horizon, the ChainSync client cannot yet validate it. It falls into the `readLedgerStateHelper` retry loop and calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect: [1](#0-0) 

Inside that guard, `preferAnchoredCandidate` is invoked with a hardcoded `emptyPerasWeightSnapshot`: [2](#0-1) 

The `emptyPerasWeightSnapshot` constant is defined as a map with no entries: [3](#0-2) 

By contrast, every other chain selection call site reads the live accumulated weights from the `PerasCertDB` via `Query.getPerasWeightSnapshot`: [4](#0-3) 

The `PerasCertDB` accumulates Peras certificates, each of which boosts the weight of a specific block point: [5](#0-4) 

`preferAnchoredCandidate` takes two distinct code paths depending on whether the snapshot is empty. With a non-empty snapshot it computes `weightedSelectView` over the suffix after the intersection, accounting for Peras boosts. With an empty snapshot it falls back to pure block-count comparison: [6](#0-5) 

The `WeightedSelectView` total weight is `blockNo + weightBoost`, so a chain with fewer blocks but significant Peras boosts can be strictly preferred: [7](#0-6) 

The `PerasCertDB` API comment for `getWeightSnapshot` explicitly states the snapshot is intended for comparing the current selection against candidate chains: [8](#0-7) 

The developers acknowledge the problem with an inline TODO referencing issue #64: [9](#0-8) 

---

### Impact Explanation

When Peras is active, a candidate chain may be heavier than the local selection by Peras weight while being shorter by block count. In `checkPreferTheirsOverOurs`, the comparison ignores all accumulated certificate boosts. The result:

- `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` returns `ShouldNotSwitch` (candidate appears shorter).
- The node throws `CandidateTooSparse` and disconnects from the peer.
- The node never fetches the blocks needed to adopt the Peras-boosted chain.
- The node remains on a less-preferred (lighter) chain, violating the Peras chain-selection invariant.

This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical, less-secure chain beyond the intended security assumptions of the Peras protocol, triggered by a crafted (or simply valid) sequence of headers from an unprivileged peer.

---

### Likelihood Explanation

Peras is not enabled by default today, but the code is present and the `PerasCertDB` is wired into the production `ChainDB`. Once Peras is activated on any network (testnet or mainnet), any peer that sends headers beyond the forecast horizon for a Peras-boosted fork will trigger this path. No special privileges are required — any ChainSync peer can send headers beyond the forecast horizon as a normal part of syncing. The scenario is reachable whenever the local node's forecast horizon lags behind the tip of a Peras-boosted candidate chain.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the `PerasCertDB`, consistent with how every other chain-selection call site obtains weights. The `checkPreferTheirsOverOurs` function runs inside an `STM` block that already has access to the `ChainDbView`, so `getPerasWeightSnapshot` can be called atomically in the same transaction. Alternatively, if the TODO to remove the check entirely (issue #64) is resolved first, the problem disappears with the check.

---

### Proof of Concept

1. Peras is enabled; the local node has selection `C` of length `n` blocks with no Peras boosts.
2. A peer holds a fork `C'` of length `n-1` blocks where the tip block carries a Peras certificate boost of weight `B > 1`. By `wsvTotalWeight`, `C'` is heavier: `(n-1) + B > n`.
3. The peer sends the tip header of `C'`. Its slot is beyond the local forecast horizon (e.g., the node is slightly behind).
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block counts only: `n-1 < n` → `ShouldNotSwitch`.
6. The node throws `CandidateTooSparse` and disconnects.
7. The node never adopts `C'`, remaining on the lighter chain `C`.

With the correct fix (using the live `PerasWeightSnapshot`), step 5 would compute `(n-1)+B > n` → `ShouldSwitch`, the node would wait for the forecast to advance, and eventually adopt `C'`. [2](#0-1) [10](#0-9) [5](#0-4)

          (Empty ourAnchor, _ :> theirTip) ->

            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
