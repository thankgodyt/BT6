Audit Report

## Title
Missing Pre-Lock Normalized-Amount Validation Causes Permanent Token Freeze — (`File: near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` burns or locks the full token amount on NEAR before any decimal-normalization check is performed. When the amount minus fee is smaller than the decimal scaling factor (`10^(origin_decimals - dest_decimals)`), `normalize_amount` returns zero, causing every subsequent `sign_transfer` call to panic. The transfer message is never removed and no cancel or refund path exists, permanently freezing the user's tokens.

## Finding Description
`init_transfer` constructs the `TransferMessage` and enforces only one amount invariant:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

It then calls `init_transfer_internal`, which immediately burns or locks the full `transfer_message.amount` on NEAR:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(..., transfer_message.amount.0);
``` [2](#0-1) 

The function returns `U128(0)` on the success path, signalling to the NEP-141 `ft_transfer_call` mechanism that zero tokens should be refunded — i.e., all tokens are consumed. [3](#0-2) 

Later, when a relayer calls `sign_transfer`, the bridge normalizes the net amount using floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [4](#0-3) 

`sign_transfer` then enforces:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [5](#0-4) 

This panic occurs before the MPC signing call is dispatched, so `sign_transfer_callback` is never reached. Transfer message removal only occurs inside `sign_transfer_callback` on a successful MPC response:

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
    ...
}
``` [6](#0-5) 

Because `sign_transfer` always panics for a sub-threshold transfer, the callback is never invoked, the transfer message persists in storage indefinitely, and no public cancel or refund function exists to recover the locked/burned tokens.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**. For any token whose NEAR representation has more decimals than its destination-chain representation (e.g., a 24-decimal NEAR wrapper of USDC with 6 EVM decimals, giving `diff_decimals = 18`), any transfer where `amount - fee < 10^18` base units normalizes to zero. The tokens are irreversibly burned (for bridge-deployed tokens) or locked in the bridge escrow (for native tokens) with no on-chain recovery path. This directly satisfies the allowed critical impact: *permanent freezing of bridged funds across NEAR and EVM chains*.

## Likelihood Explanation
The trigger path — `ft_transfer_call` → `ft_on_transfer` → `init_transfer` — is callable by any token holder without special privileges. The condition is met whenever a user sends a "dust" amount below the scaling threshold, which can happen accidentally (small test transfers, rounding from a UI) or deliberately (an attacker who controls a token contract or front-runs a deposit). The `InitTransferMsg` struct imposes no minimum-amount constraint, and no off-chain filter is enforced at the contract level. [7](#0-6) 

## Recommendation
In `init_transfer` (or at the top of `init_transfer_internal`), before burning or locking any tokens, compute `normalize_amount(amount - fee, decimals)` using the already-available `token_decimals` map and require the result to be greater than zero. This mirrors the check already present in `sign_transfer` at lines 475–485 and prevents tokens from being consumed when the transfer can never be completed. Alternatively, enforce a per-token protocol minimum that accounts for the decimal scaling factor.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (`diff_decimals = 18`, scaling factor = `10^18`).
2. A user calls `ft_transfer_call` transferring `500_000_000_000_000_000` (5 × 10^17) base units with `fee = 0` and an EVM recipient.
3. `init_transfer` passes the `fee < amount` check. `init_transfer_internal` burns or locks the full amount and returns `U128(0)` — no refund.
4. A trusted relayer calls `sign_transfer`. `normalize_amount(5e17, {origin:24, dest:6}) = 5e17 / 1e18 = 0`.
5. `require!(amount_to_transfer > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. The MPC call is never made.
6. `sign_transfer_callback` is never reached; the transfer message remains in storage.
7. The tokens are permanently lost — no cancel, no retry, no refund path exists on-chain.
