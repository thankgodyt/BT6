### Title
Re-entrant `execute_refund` Creates Multiple Non-Idempotent `BTCPendingInfo` Entries for the Same UTXO — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` is intentionally designed to be callable multiple times once a refund request is marked `executed = true`. However, `finalize_refund_with_psbt`, which is called on every execution, is **non-idempotent**: each invocation unconditionally creates a new `BTCPendingInfo` entry and consumes a caller's pending-sign slot. Because the re-execution guard only checks the caller's own capacity (default limit: 1), any number of distinct unprivileged callers can each trigger a separate MPC signing request for the same deposit UTXO, accumulating stale pending-sign state that requires privileged operator cleanup.

---

### Finding Description

`load_refund_request_for_execute` (the pre-execution guard) explicitly permits re-execution when `refund_request.executed == true`:

```rust
// refund.rs L254-L258
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

The design intent is to allow re-creating the refund transaction after a consensus branch change. However, `finalize_refund_with_psbt` — called on every successful `execute_refund` — performs non-idempotent state mutations:

1. **Creates a new `BTCPendingInfo`** keyed by the new PSBT's hash and inserts it into `btc_pending_infos` (line 366–372).
2. **Inserts the new pending-sign ID** into the caller's `btc_pending_sign_ids` (line 373–375), consuming one pending-sign slot.
3. **Emits a new MPC signing request** for the same deposit UTXO.

The capacity guard at line 342 checks only the *current caller's* account:

```rust
// refund.rs L342
self.require_pending_sign_capacity(&caller);
```

Because `caller` is `env::predecessor_account_id()`, each distinct NEAR account that calls `execute_refund` after the first execution passes this check (their own slot is still free) and successfully creates an independent `BTCPendingInfo` for the same UTXO. The `verified_deposit_utxo` insert at line 378–380 is idempotent (it is a `LookupSet`), so it does not prevent repeated execution.

---

### Impact Explanation

Each repeated `execute_refund` call by a different caller:

- Triggers a new MPC chain-signature request for the same deposit UTXO, wasting protocol gas.
- Adds a stale `BTCPendingInfo` entry to the caller's account, locking their pending-sign capacity until an operator manually calls `remove_refund_pending_tx_id`.
- Accumulates stale entries in `btc_pending_infos` that can never be finalized (only one Bitcoin transaction can spend the UTXO; the rest are invalid double-spends).

After `verify_refund_finalize` removes the refund request, the stale pending infos cannot self-clean: `remove_refund_pending_tx_id` requires the refund request to be absent, so cleanup depends on operator intervention per stale entry. If many callers race, the bridge accumulates unbounded stale MPC-signed transactions and locked accounts, constituting a stuck bridge state requiring operator intervention.

**Impact class: Medium** — stuck bridge state requiring operator intervention; attacker-triggered temporary locking of callers' pending-sign capacity; wasted MPC signing resources.

---

### Likelihood Explanation

- `execute_refund` is a public, permissionless function (no role check beyond timelock).
- After the timelock elapses, any NEAR account can call it with the required attached deposit.
- The `executed = true` flag is set on the first call and never cleared, so the window for repeated calls is open until `verify_refund_finalize` removes the request.
- The only cost to an attacker is the `required_balance_for_execute_refund()` deposit per call, which is a storage deposit (not burned), making repeated calls economically feasible.

**Likelihood: Medium** — requires timelock to elapse and multiple willing callers, but no privileged access is needed.

---

### Recommendation

Make `finalize_refund_with_psbt` idempotent with respect to re-execution. Before creating a new `BTCPendingInfo`, check whether a pending-sign entry for this UTXO already exists under any account. One concrete approach: when `refund_request.executed == true`, require that all previously created refund pending infos for this UTXO have been cleaned up (i.e., are no longer in `btc_pending_infos`) before allowing a new one to be created. Alternatively, restrict re-execution of `execute_refund` to privileged roles (DAO/RefundOperator) so that only a trusted party can re-create the refund transaction after a branch change.

---

### Proof of Concept

1. Alice deposits BTC; the deposit is never finalized via `verify_deposit`.
2. Alice (or anyone) calls `request_refund`, which is verified and stored with `executed = false`.
3. The timelock elapses.
4. Attacker account B calls `execute_refund(utxo_storage_key, ...)` with the required deposit:
   - `load_refund_request_for_execute`: `executed == false`, UTXO not in `verified_deposit_utxo` → passes.
   - `finalize_refund_with_psbt`: creates `BTCPendingInfo #1` under B, inserts UTXO into `verified_deposit_utxo`, sets `executed = true`.
5. Attacker account C calls `execute_refund(utxo_storage_key, ...)`:
   - `load_refund_request_for_execute`: `executed == true` → the `|| refund_request.executed` branch passes even though UTXO is in `verified_deposit_utxo`.
   - `require_pending_sign_capacity(&C)`: C's slot is free → passes.
   - `finalize_refund_with_psbt`: creates `BTCPendingInfo #2` under C, emits a second MPC signing request for the same UTXO.
6. Attacker accounts D, E, … repeat step 5.
7. MPC signs all requests. Only one Bitcoin transaction can confirm; the rest are invalid double-spends.
8. After `verify_refund_finalize` finalizes the confirmed tx and removes the refund request, stale `BTCPendingInfo` entries for B, C, D, E remain in `btc_pending_infos` and in each account's `btc_pending_sign_ids`, locking their pending-sign capacity.     pub(crate) fn load_refund_request_for_execute(
        &self,
        utxo_storage_key: &str,
        timelock_sec: u64,
    ) -> RefundRequest {
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();

        let now = nano_to_sec(env::block_timestamp());
        require!(
            u64::from(now) >= u64::from(refund_request.created_at_sec) + timelock_sec,
            "Refund timelock has not passed yet"
        );

        // Block only if the UTXO was claimed by a deposit. If it was claimed by
        // our own refund (executed == true, which also set verified_deposit_utxo),
        // re-running execute_refund is allowed — re-creating the refund tx, e.g.
        // after a consensus branch change.
        require!(
            !self.data().verified_deposit_utxo.contains(utxo_storage_key)
                || refund_request.executed,
            "UTXO already verified via deposit, cannot refund"
        );

        refund_request
    }
