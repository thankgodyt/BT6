### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Any Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which is the only active implementation in the codebase, defines `validatePerasCert` to unconditionally return `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. This implementation is wired directly into the production inbound-certificate processing path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can therefore inject arbitrary crafted `PerasCert` values — with any round number and any boosted-block pointer — and have them accepted, stored in the `PerasCertDB`, and used to influence chain selection via Peras boosting weights.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op:**

The degenerate instance at `SupportsPeras.hs:320` is the only concrete `BlockSupportsPeras` instance in the codebase. Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of content, is unconditionally wrapped in `Right` and returned as `ValidatedPerasCert`. No signature is checked, no committee membership is verified, no quorum is confirmed, and no round-number bounds are enforced. [1](#0-0) 

**Production wiring — the no-op validator is used for all inbound peer certificates:**

Both production pool writers pass `validatePerasCert mkPerasParams` as the validation function to `processCerts`:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

**`processCerts` — the inbound processing pipeline:**

`processCerts` receives a batch of `PerasCert` values from a peer, calls `validateCert` on each one, and — if all pass — adds them to the database and triggers chain selection side-effects:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
```

Because `validateCert` is `validatePerasCert mkPerasParams` and that always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted. [4](#0-3) 

**Chain selection impact — accepted certificates boost arbitrary blocks:**

Accepted certificates are added to the `PerasCertDB` and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection. The Peras weight assigned to each accepted certificate is `perasWeight mkPerasParams = PerasWeight 15`. Chain selection uses these weights to prefer boosted blocks over unboosted ones. An attacker who injects a certificate pointing to an adversarial block causes the node to assign that block a +15 weight advantage in chain selection. [5](#0-4) [6](#0-5) 

The `implAddCert` function in `PerasCertDB/Impl.hs` also carries an explicit acknowledgement of this gap:

-- see https://github.com/tweag/cardano-peras/issues/120

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block hash it wishes to boost. Because `validatePerasCert` never rejects anything, the certificate is stored and applied to chain selection with a weight of +15. By injecting certificates for an adversarial fork, the attacker can cause an honest node to prefer a non-canonical, adversarially-controlled chain over the honest chain, violating the chain-selection security guarantees of the Peras protocol extension. This constitutes a **High** impact: a chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only network connectivity to a target node running the Peras object-diffusion mini-protocol. No keys, stake, or privileged access are needed. The attacker simply sends a well-formed `PerasCert` CBOR message with a crafted `pcCertBoostedBlock`. The code path is reachable from any peer connection. Likelihood is **High** given the complete absence of any gate on certificate acceptance.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs the full Peras certificate validation required by the protocol specification:

1. **Committee membership**: verify that the signers are legitimate committee members for the claimed round, using the stake distribution snapshot for that round.
2. **Quorum**: verify that the aggregate stake of the signers meets `perasQuorumStakeThreshold`.
3. **Aggregate signature**: verify the aggregate BLS/VRF signature over `(electionId, candidate)`.
4. **Round bounds**: verify that `pcCertRound` is within the valid window relative to the current chain tip.
5. **Boosted block existence**: verify that `pcCertBoostedBlock` refers to a block that actually exists and is within the valid age window (`perasBlockMinSlots`).

Until the full `BlockSupportsPeras` instance for `CardanoBlock` is implemented, the Peras certificate diffusion mini-protocol should not be enabled in production builds, or inbound certificates should be dropped unconditionally rather than accepted unconditionally.

---

### Proof of Concept

1. Connect to a target node that has the Peras object-diffusion mini-protocol enabled.
2. Craft a `PerasCert` value:
   ```
   PerasCert { pcCertRound = <current_round>, pcCertBoostedBlock = <adversarial_block_point> }
   ```
   encoded as CBOR `[round_no, block_point]` per the `Serialise` instance.
3. Send it as a batch via the `ObjectDiffusion` protocol for Peras certificates.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`.
5. The certificate is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is called.
6. Chain selection now assigns the adversarial block a +15 weight advantage.
7. If the adversarial fork is otherwise equal in length to the honest chain, the node switches to the adversarial fork.
