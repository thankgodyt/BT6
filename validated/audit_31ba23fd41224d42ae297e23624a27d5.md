### Title
`get_user_deposit_address` Returns Valid Deposit Address When Bridge Is Paused, Misleading Users Into Sending Unclaimable BTC - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

The `satoshi-bridge` contract can be paused via `near_plugins::Pausable`. When paused, all deposit verification functions (`verify_deposit_v2`, `safe_verify_deposit`, etc.) and refund functions (`request_refund`, `execute_refund`) revert. However, `get_user_deposit_address` is not paused and continues to return a valid deposit address — and even emits a `LogDepositAddress` event — giving no indication that the bridge is non-operational. A user who calls this function while the bridge is paused, sends BTC to the returned address, and then attempts to claim nBTC will find that both the deposit and refund paths are unavailable, leaving their BTC temporarily locked until the bridge is unpaused.

### Finding Description

The `satoshi-bridge` contract derives from `Pausable` and applies `#[pause(except(roles(Role::DAO)))]` to all state-mutating bridge operations:

- `verify_deposit_v2`, `verify_deposit`, `safe_verify_deposit` — paused
- `request_refund`, `execute_refund`, `verify_refund_finalize` — paused
- `ft_on_transfer` (withdrawal entry) — paused [1](#0-0) [2](#0-1) [3](#0-2) 

However, `get_user_deposit_address` carries no `#[pause]` guard:

```rust
pub fn get_user_deposit_address(&self, deposit_msg: DepositMsg) -> String {
    let path = get_deposit_path(&deposit_msg);
    let deposit_address = self.generate_utxo_chain_address(&path).to_string();
    Event::LogDepositAddress {
        deposit_msg,
        path,
        deposit_address: deposit_address.clone(),
    }
    .emit();
    deposit_address
}
``` [4](#0-3) 

It returns a fully-formed deposit address and emits a `LogDepositAddress` event regardless of the bridge's paused state. There is no signal to the caller — or to any off-chain system monitoring events — that the bridge cannot currently process deposits.

This is the direct analog of the external report: just as `maxDeposit`/`maxMint` returned `type(uint256).max` while `deposit`/`mint` reverted, `get_user_deposit_address` returns a usable address while every path to claim nBTC for that address (`verify_deposit_v2`, `request_refund`, `execute_refund`) is paused.

### Impact Explanation

A user who sends BTC to the address returned by `get_user_deposit_address` while the bridge is paused cannot:

1. Call `verify_deposit_v2` to mint nBTC — paused.
2. Call `request_refund` to initiate a BTC return — paused.
3. Call `execute_refund` to recover funds — paused.

Their BTC is locked in the bridge's MPC-controlled deposit address until the bridge is unpaused. This constitutes a stuck-state in a production bridge path without direct theft, matching the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."* [5](#0-4) 

### Likelihood Explanation

The bridge is paused by a `PauseManager`-role holder, which is a privileged but realistic operational event (e.g., incident response). The function `get_user_deposit_address` is a standard user-facing entry point called by wallets, relayers, and automated deposit pipelines. Any such caller that does not separately query `pa_all_paused()` before generating an address will be unaware of the paused state. The `LogDepositAddress` event emitted by the function further reinforces the false impression that the bridge is ready to accept deposits.

### Recommendation

Add a pause guard to `get_user_deposit_address`, or add an explicit check that panics (or returns an error) when the bridge is paused:

```rust
pub fn get_user_deposit_address(&self, deposit_msg: DepositMsg) -> String {
    require!(!self.pa_is_paused(), "Bridge is paused");
    // ... existing logic
}
```

Alternatively, apply `#[pause(except(roles(Role::DAO)))]` consistently with the other deposit-path functions so that callers receive a clear revert rather than a silently unusable address.

### Proof of Concept

1. `PauseManager` calls `pa_pause_feature("*")` to pause the bridge.
2. User (or automated relayer) calls `get_user_deposit_address(deposit_msg)` — succeeds, returns a valid BTC address, emits `LogDepositAddress`.
3. User sends BTC to the returned address on-chain.
4. User calls `verify_deposit_v2(...)` — reverts: `"Pausable: method is paused"`.
5. User calls `request_refund(...)` — reverts: `"Pausable: method is paused"`.
6. User calls `execute_refund(...)` — reverts: `"Pausable: method is paused"`.
7. BTC remains locked in the MPC-controlled deposit address until the bridge is unpaused. [6](#0-5) [7](#0-6) [8](#0-7)
