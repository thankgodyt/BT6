### Title
Peras Vote and Certificate Validation Bypass Enables Unauthorized Chain Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance in production source code contains stub implementations of `validatePerasCert` and `validatePerasVote` that bypass all cryptographic validation. `validatePerasCert` unconditionally returns `Right` for any certificate regardless of content, and `validatePerasVote` only checks stake-distribution membership without verifying any cryptographic signature. An unprivileged peer can exploit this to submit forged votes and certificates that are accepted as valid, causing honest nodes to apply Peras weight boosts to adversarial blocks and potentially prefer a non-canonical chain during chain selection.

---

### Finding Description

**Analog mapping to the external report's vulnerability class:**

The external report describes three cooperating flaws: (1) phantom state (virtual shares) that is treated as real, (2) a sequential multi-step process with an intermediate external interaction that creates a manipulation window, and (3) incorrect accounting compensation for the manipulated state. The analog here is structurally identical:

1. **Phantom votes/certificates** — votes and certificates without valid cryptographic proofs are treated as real, validated objects.
2. **Sequential multi-step processing** — votes are validated in STM, then a certificate is generated, then chain selection is triggered asynchronously; each step trusts the output of the previous one.
3. **Incorrect weight compensation** — the chain selection logic applies a full Peras weight boost to the boosted block based on the accepted phantom certificate, exactly as the DeFi protocol incorrectly compensated for missing phantom shares by minting real supply.

**Root cause — `validatePerasCert` always returns `Right`:**

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` in production source contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every certificate, regardless of its cryptographic content, is unconditionally accepted and assigned the full `perasWeight` boost. [1](#0-0) 

**Root cause — `validatePerasVote` skips signature verification:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

The only check is whether the claimed voter ID appears in the stake distribution. No cryptographic signature over the vote content is verified. Any peer that knows a legitimate pool operator's ID can forge votes on their behalf. [2](#0-1) 

**The network entry path — `processVotes`:**

Inbound votes received from peers are processed by `processVotes`, which calls the `validateVote` callback. In the production wiring, that callback is `validatePerasVote mkPerasParams sd vote` — the stub above. [3](#0-2) 

The pool writer used from the `ChainDB` path passes this same stub validator: [4](#0-3) 

**The sequential multi-step processing window:**

`addPerasVoteWithAsyncCertHandling` performs the two-step process: (1) add the vote atomically to the `PerasVoteDB`, and (2) if quorum is reached, asynchronously add the generated certificate to the `ChainDB` and trigger chain selection. The certificate produced from forged votes is indistinguishable from a legitimate one at this point because `validatePerasCert` already accepted it unconditionally. [5](#0-4) 

**Chain selection uses the boost:**

`chainSelectionForBlock` is called for the boosted block, and `preferAnchoredCandidate` uses the Peras weight snapshot to compare candidates. A forged certificate thus directly influences which chain the node selects. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can forge Peras votes for any pool operator whose ID appears in the public stake distribution, accumulate enough forged votes to reach quorum, generate a certificate for an adversarial block, and cause honest nodes to apply a full Peras weight boost to that block during chain selection. This can make an adversarial chain preferred over the canonical chain, constituting a **Critical** bypass of Peras voting and certificate checks enabling unauthorized certificate acceptance and a chain-selection safety failure.

---

### Likelihood Explanation

The stake distribution is public. Any peer connected to the Peras vote mini-protocol can send crafted votes. The only barrier is knowing the pool operator IDs, which are on-chain. No privileged keys, operator access, or stake majority is required. The attack is fully reachable from an unprivileged network position as long as the Peras vote diffusion mini-protocol is active.

---

### Recommendation

1. **Implement real cryptographic validation in `validatePerasCert`**: verify the aggregate signature over the certificate content against the committee's public keys before returning `Right`.
2. **Implement real cryptographic validation in `validatePerasVote`**: verify the vote's signature against the claimed voter's public key (obtained from the stake distribution or committee selection context) before accepting the vote.
3. **Block the network entry point until validation is complete**: gate `processVotes` and `addPerasCertAsync` behind a feature flag or era check so that the Peras diffusion mini-protocols are not active until the validation stubs are replaced with real implementations.
4. **Add a compile-time or runtime assertion** that the degenerate `instance StandardHash blk => BlockSupportsPeras blk` is never used in a context where Peras is active.

---

### Proof of Concept

1. Obtain the current stake distribution (public on-chain data) to enumerate valid pool operator IDs.
2. Construct `PerasVote` messages claiming to be from those operators, targeting an adversarial block at a chosen round number. No valid signature is required — the `pvVoteVoterId` field is the only thing checked.
3. Send the forged votes to a target node via the Peras vote mini-protocol. `processVotes` calls `validatePerasVote`, which passes each vote as long as the voter ID is in the stake distribution.
4. Once enough forged votes accumulate to exceed `perasQuorumStakeThreshold`, `updatePerasRoundVoteStates` generates a `ValidatedPerasCert` for the adversarial block.
5. `addPerasVoteWithAsyncCertHandling` calls `addPerasCertAsync`, which enqueues a `ChainSelMessage` for the boosted block.
6. `chainSelSync` processes the message, calls `chainSelectionForBlock` for the adversarial block, and `preferAnchoredCandidate` now sees the adversarial chain as heavier due to the Peras weight boost.
7. The honest node switches to the adversarial chain.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

addPerasVoteWithAsyncCertHandling ::
  forall m blk.
  IOLike m =>
  ChainDbEnv m blk ->
  WithArrivalTime (ValidatedPerasVote blk) ->
  m (AddPerasVoteResult blk, Maybe (AddPerasCertPromise m))
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      let certTime = getArrivalTime vote
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)
      pure (addVoteRes, Just promise)
    _ -> pure (addVoteRes, Nothing)
