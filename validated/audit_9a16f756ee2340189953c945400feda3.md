### Title
DAO Cannot Re-Sync `chain_signatures_root_public_key` After Initial Set, Permanently Locking Withdrawal Capability - (File: `contracts/satoshi-bridge/src/api/management.rs`)

### Summary

`sync_chain_signatures_root_public_key` enforces a one-time-only guard (`is_none()`) that permanently prevents the DAO from ever re-syncing the MPC root public key. Because `ConfigUpdate` also omits `chain_signatures_root_public_key`, there is no alternative update path. If the underlying chain signatures contract rotates its root public key, the bridge's stored key becomes permanently stale, breaking all withdrawal signing and locking all bridge-controlled UTXOs.

### Finding Description

In `contracts/satoshi-bridge/src/api/management.rs`, the only function that sets `chain_signatures_root_public_key` is:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    require!(
        self.internal_config()
            .chain_signatures_root_public_key
            .is_none(),
        "Already sync"
    );
    self.sync_chain_signatures_root_public_key_promise()
}
``` [1](#0-0) 

Once the callback `sync_root_public_key_callback` writes a non-`None` value into `chain_signatures_root_public_key`, the `require!(...is_none(), "Already sync")` guard permanently blocks any future call to this function, even by the DAO. [2](#0-1) 

The `ConfigUpdate` struct, which is the only other mechanism for the DAO to update config fields, does not include `chain_signatures_root_public_key` or `change_address` as updatable fields: [3](#0-2) 

The `change_address` is also derived from the root public key and set in the same one-time callback, and is equally non-updatable via `ConfigUpdate`. [4](#0-3) 

### Impact Explanation

`chain_signatures_root_public_key` is the cryptographic root used to derive every BTC public key for every UTXO held by the bridge, via `generate_public_key` → `generate_btc_public_key`: [5](#0-4) 

If the chain signatures contract rotates its root public key (a normal operational event during upgrades or key rotation), the bridge's stored key becomes stale. All subsequent calls to `internal_sign_btc_transaction` would derive wrong public keys, producing invalid signatures. Every pending and future withdrawal would fail permanently. All bridge-controlled UTXOs — representing the entire BTC/ZEC backing supply — would be permanently locked with no recovery path short of a contract upgrade.

**Impact: Medium to Critical** — stuck bridge state requiring operator intervention, with potential for permanent locking of all bridge-controlled funds.

### Likelihood Explanation

The chain signatures (MPC) network is an external protocol that can and does rotate keys during upgrades. The NEAR chain signatures contract exposes a `public_key()` view function specifically because the key can change. The bridge's design of calling `public_key()` at init time acknowledges this, but the one-time guard means the bridge can never adapt to a key rotation. This is a realistic operational scenario, not a theoretical one.

### Recommendation

Remove the `is_none()` guard from `sync_chain_signatures_root_public_key` so the DAO can re-sync at any time:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    // Remove: require!(self.internal_config().chain_signatures_root_public_key.is_none(), "Already sync");
    self.sync_chain_signatures_root_public_key_promise()
}
```

Additionally, add `chain_signatures_root_public_key: Option<PublicKey>` and `change_address: Option<String>` to `ConfigUpdate` so the DAO can also update these fields directly if needed.

### Proof of Concept

1. DAO calls `sync_chain_signatures_root_public_key` at bridge initialization. The callback sets `chain_signatures_root_public_key = Some(key_v1)` and `change_address = Some(addr_v1)`.
2. The chain signatures contract rotates its root public key to `key_v2` (e.g., during a protocol upgrade).
3. DAO attempts to call `sync_chain_signatures_root_public_key` again to update the stored key.
4. The call panics with `"Already sync"` because `chain_signatures_root_public_key.is_none()` is `false`.
5. `ConfigUpdate` provides no field for `chain_signatures_root_public_key`, so `update_config` cannot help.
6. All subsequent withdrawal signing calls invoke `generate_btc_public_key` using the stale `key_v1`, producing keys that do not match the MPC signer's current derivation under `key_v2`.
7. All withdrawal signatures are invalid. All bridge UTXOs are permanently locked. [1](#0-0) [6](#0-5) [3](#0-2)
