### Title
No Minimum Attached-Deposit Validation in `sign_btc_transaction` Causes Withdrawal and Refund Funds to Become Temporarily Stuck - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` is `#[payable]` and blindly forwards `env::attached_deposit()` to the MPC Chain Signatures contract. There is no minimum-deposit guard and no fee-estimation helper. When a user attaches zero or insufficient NEAR, the MPC `sign` call fails silently, the callback returns `false` without reverting state, and the `BTCPendingInfo` is left permanently in `PendingSign` stage — locking the user's nBTC tokens (already transferred to the bridge for withdrawals) or their BTC (locked in the deposit address for refunds) until they discover and retry with the correct amount.

### Finding Description
`sign_btc_transaction` in `api/chain_signatures.rs` is the mandatory step that drives both the withdrawal and refund flows through the MPC signing stage. The function is declared `#[payable]`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
```

`internal_sign_btc_transaction` calls `sign_promise`, which passes whatever NEAR is attached — including zero — directly to the MPC contract:

```rust
pub fn sign_promise(&self, request: SignRequest) -> Promise {
    let config = self.internal_config();
    ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
        .with_static_gas(GAS_FOR_SIGN_CALL)
        .with_attached_deposit(env::attached_deposit())   // ← no floor check
        .sign(request)
}
```

The NEAR Chain Signatures contract requires a non-trivial attached deposit to pay for the MPC signing operation. When the deposit is insufficient the cross-contract call fails. The callback handles this gracefully (returns `false`) but **does not panic and does not roll back any state**:

```rust
pub fn sign_btc_transaction_callback(...) -> bool {
    if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
        // success path — saves signature, advances stage
        ...
        true
    } else {
        false   // ← silent failure; BTCPendingInfo stays in PendingSign
    }
}
```

Contrast this with every other payable entry-point in the bridge that requires NEAR for storage, all of which enforce a floor before proceeding (e.g., `internal_request_refund` at `refund.rs:147` and `resolve_execute_refund_timelock` at `refund.rs:203`). `sign_btc_transaction` has no equivalent guard, and no `get_sign_fee` / `required_balance_for_sign` view function exists to help callers estimate the correct amount.

### Impact Explanation
**Withdrawal path:** The user calls `nbtc.ft_transfer_call(bridge, amount, msg)`. The nBTC tokens are immediately transferred to the bridge balance. The bridge creates a `BTCPendingInfo` in `PendingSign` stage. The user must then call `sign_btc_transaction` with sufficient NEAR. If they attach zero NEAR, the MPC call fails, the callback returns `false`, and the `BTCPendingInfo` stays in `PendingSign`. The user's nBTC tokens remain locked inside the bridge contract with no automatic recovery path.

**Refund path:** After `execute_refund` builds the refund PSBT and marks the deposit UTXO in `verified_deposit_utxo`, the user must call `sign_btc_transaction`. If they attach insufficient NEAR, the same silent failure occurs. The BTC remains locked in the deposit address and the refund PSBT cannot be completed.

In both cases the funds are not permanently lost — the user can retry with the correct amount — but there is no on-chain mechanism to discover what that amount is, and the stuck state requires user intervention to resolve. This matches the allowed Medium impact: **attacker-triggered (or user-triggered) temporary locking of bridged funds**.

### Likelihood Explanation
The NEAR Chain Signatures MPC contract is documented to require an attached deposit for signing. Any user who calls `sign_btc_transaction` without reading external MPC documentation (which is not referenced anywhere in the bridge contract or its public API) will naturally attach zero NEAR, since the bridge itself provides no guidance. This is a routine UX mistake that will affect real users attempting withdrawals or refunds.

### Recommendation
1. **Add a minimum deposit check** at the top of `sign_btc_transaction` (or inside `sign_promise`) analogous to the checks already present in `internal_request_refund` and `resolve_execute_refund_timelock`:
   ```rust
   require!(
       env::attached_deposit() >= MIN_BALANCE_FOR_SIGN,
       "Insufficient deposit for MPC signing fee"
   );
   ```
2. **Expose a view function** (e.g., `required_balance_for_sign`) so callers can query the minimum before submitting the transaction.
3. **Document the required deposit** in the `sign_btc_transaction` doc-comment.

### Proof of Concept
1. User calls `nbtc.ft_transfer_call(bridge, 100_000, withdraw_msg)` — nBTC tokens are transferred to the bridge; a `BTCPendingInfo` in `PendingSign` is created.
2. User calls `bridge.sign_btc_transaction(pending_id, 0, 0)` with **zero attached NEAR**.
3. `sign_promise` forwards `0 yoctoNEAR` to the MPC `sign` contract call.
4. MPC rejects the call due to insufficient fee; the cross-contract promise fails.
5. `sign_btc_transaction_callback` receives a failed promise result, enters the `else` branch, and returns `false` — no state is rolled back.
6. `BTCPendingInfo` remains in `PendingSign`; the user's nBTC tokens remain locked in the bridge.
7. The user has no on-chain way to determine the correct NEAR amount to attach for a retry.
