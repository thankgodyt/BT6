### Title
Missing Ownership Check in `withdraw_rbf` Allows Any Caller to Trigger RBF on Another User's Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`withdraw_rbf` uses `env::predecessor_account_id()` as the acting account without verifying that the caller owns the targeted `BTCPendingInfo`. Any unprivileged NEAR account can call `withdraw_rbf` against another user's pending withdrawal, supplying attacker-controlled `output` (Bitcoin transaction outputs including target address and amounts), and the resulting RBF pending info is attributed to the attacker rather than the original owner.

---

### Finding Description

When a user initiates a withdrawal via `ft_on_transfer`, a `BTCPendingInfo` is created with `account_id` set to the original sender: [1](#0-0) 

The public `withdraw_rbf` entry point then does: [2](#0-1) 

`account_id` is taken from `env::predecessor_account_id()` — the **caller** — with no check that this matches `btc_pending_info.account_id`. The only guard is `require_pending_sign_capacity(&account_id)`, which checks the **caller's** own capacity, not the original owner's.

Contrast this with `cancel_withdraw`, which correctly retrieves the owner from the stored pending info before acting: [3](#0-2) 

`withdraw_rbf` is not role-restricted — only `#[pause]` applies — so any unprivileged account can call it while the contract is unpaused.

The `BTCPendingInfo` struct stores `account_id` as the authoritative owner of the pending operation: [4](#0-3) 

---

### Impact Explanation

An attacker calls `withdraw_rbf` targeting a victim's `original_btc_pending_verify_id` and supplies an attacker-controlled `output` vector (Bitcoin transaction outputs). The RBF pipeline replaces the victim's pending withdrawal transaction with a new one constructed from the attacker's `output`, which can include a different target BTC address. The resulting RBF `BTCPendingInfo` is attributed to the attacker's account. If `withdraw_rbf_chain_specific` does not re-validate the output against the original pending info's `target_btc_address`, the victim's BTC is redirected to the attacker — constituting unauthorized theft of bridged funds.

At minimum (if output redirection is blocked downstream), the attacker can still:
- Disrupt the victim's withdrawal by injecting a competing RBF that the victim cannot cancel (since the new pending info is owned by the attacker)
- Permanently lock the victim's withdrawal in a stuck state requiring operator intervention

**Impact class:** Critical (unauthorized redirection/theft of user BTC) or Medium (permanent locking of bridged funds).

---

### Likelihood Explanation

The function is publicly callable by any NEAR account with no role restriction. The only prerequisite is that a victim has an active pending withdrawal (`BTCPendingInfo` in `PendingSign` stage). This is a normal operational state for any bridge user. No special privileges, leaked keys, or external dependencies are required.

---

### Recommendation

Retrieve the owner from the stored `BTCPendingInfo` and assert it matches the caller, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>, ...) {
    let account_id = env::predecessor_account_id();
    // Verify caller owns the pending withdrawal
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(account_id == owner, "Only the owner can RBF their withdrawal");
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, ...);
}
```

---

### Proof of Concept

1. **Victim** calls `ft_transfer_call` on the nBTC token contract with a `Withdraw` message → `ft_on_transfer` → `create_btc_pending_info` stores `BTCPendingInfo { account_id: victim, ... }` with `btc_pending_id = X`.
2. **Attacker** observes `X` on-chain (all state is public).
3. **Attacker** calls `withdraw_rbf(original_btc_pending_verify_id: X, output: [TxOut { value: victim_amount, script_pubkey: attacker_btc_address }], ...)`.
4. Inside `withdraw_rbf`: `account_id = attacker` (no ownership check). `require_pending_sign_capacity(attacker)` passes if attacker has capacity.
5. `withdraw_rbf_chain_specific(attacker, X, attacker_output, ...)` is called — the RBF transaction is built with attacker-controlled outputs and attributed to the attacker's account.
6. The MPC signs the RBF transaction; victim's BTC is sent to the attacker's Bitcoin address. [5](#0-4) [6](#0-5)
