### Title
Shelley `ledgerViewForecastAt` Anchors Forecast at Current Tip, Reducing Effective Rollback to k−1 and Breaking the Chain-Selection Invariant — (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/SupportsProtocol.hs`)

---

### Summary

The `LedgerSupportsProtocol` class mandates that `ledgerViewForecastAt` must provide a forecast range wide enough to validate at least k+1 headers from an intersection k blocks back, so that chain selection can always prefer a longer alternative chain. The Shelley implementation violates this invariant: it anchors the stability window at the slot immediately after the current ledger tip (`succWithOrigin at`) rather than at the first unknown header. The formal specification acknowledges the resulting misalignment: the effective maximum rollback in Shelley is k−1, not k+1. An unprivileged peer serving a legitimate chain with k+1 blocks after the intersection can trigger the ChainSync client to exhaust the forecast horizon and disconnect from that peer, causing the honest node to stay on a shorter, less-secure chain.

---

### Finding Description

**Root cause — `ledgerViewForecastAt` for `ShelleyBlock (TPraos crypto) era`:**

```haskell
-- Exclusive upper bound
maxFor :: SlotNo
maxFor = addSlots swindow $ succWithOrigin at
``` [1](#0-0) 

Here `at = ledgerTipSlot ledgerState` and `swindow = SL.stabilityWindow globals` (= 3k/f slots). The forecast window is therefore `[at+1, at+1+swindow)`, anchored at the slot immediately after the current tip.

**The required invariant** is stated in `LedgerSupportsProtocol`:

> The range of the forecast should allow to validate a sufficient number of headers to validate an alternative chain longer than ours, so that chain selection can decide whether or not we prefer the alternative chain. [2](#0-1) 

The formal specification confirms the violation:

> Due to a misalignment between the consensus requirements and the Shelley specification, this is not the case for Shelley, where the effective maximum rollback is in fact k−1; see §shelley:forecasting. [3](#0-2) 

The appendix entry for Shelley forecasting explicitly records this as an open issue:

> Discuss the fact that the effective maximum rollback in Shelley is k−1, not k. [4](#0-3) 

**Why the anchor is wrong.** The stability window guarantees that no block within `swindow` slots of the current tip can alter the leader schedule. But the correct anchor for chain-selection purposes is the *first unknown header* (the header immediately after the intersection), not the current tip. The tech report notes this explicitly:

> We should change this. By anchoring the stability window at the last known block, we only have a guarantee that we can validate k headers, but we should really be able to validate k+1 headers … If we anchored the stability window after the first unknown header, where it *should* be anchored, we can validate k headers *after* the first unknown header, and hence k+1 in total. [5](#0-4) 

**How the ChainSync client reacts when the forecast horizon is exhausted.** When `projectLedgerView` returns `Nothing` (slot outside forecast range), the client calls `checkPreferTheirsOverOurs`: [6](#0-5) 

If the peer's fragment is not yet preferable (because the honest node has not validated enough headers to determine this), the client throws `CandidateTooSparse` and disconnects: [7](#0-6) 

This means the honest node **disconnects from a legitimate peer** whose chain it cannot yet evaluate, rather than waiting for its own chain to advance.

---

### Impact Explanation

**Classification: High — chain-selection bug.**

When the intersection with a peer is k blocks back (the maximum allowed before disconnection), the honest node needs to validate k+1 of the peer's headers to determine that the peer's chain is longer. Because the Shelley forecast range only guarantees k−1 blocks in the worst case, the honest node may exhaust the forecast horizon before validating the k+1th header. The ChainSync client then disconnects from the peer via `CandidateTooSparse`. The honest node remains on its current (shorter) chain while the rest of the network advances on the longer chain — a chain-selection failure that reduces the effective security parameter from k to k−1.

This directly parallels the external report: the protocol promises a property (sufficient forecast range for k+1-block chain selection) that the implementation does not deliver, causing the node to be stuck in a state that violates the invariant.

---

### Likelihood Explanation

In normal Cardano mainnet operation the stability window (3k/f ≈ 2160 slots for k=2160, f=0.05) vastly exceeds k, so the forecast range covers far more than k+1 blocks and the gap is never reached. However, the scenario is reachable on a private testnet or under adversarial conditions (e.g., after a network partition where one side forges exactly k blocks). The `TwoEras` test infrastructure explicitly limits partition duration to `2k−2` slots to avoid triggering this exact failure: [8](#0-7) 

The fact that tests must work around this limitation confirms the issue is reachable in a controlled reproduction.

---
