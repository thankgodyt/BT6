Audit Report

## Title
Missing Pre-Transfer Normalization Guard Causes Permanent Fund Loss for Sub-Unit Amounts — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` burns or locks user tokens before validating that the transfer amount survives decimal normalization. When a user initiates a NEAR→EVM transfer with an amount that normalizes to zero, the tokens are irreversibly consumed on NEAR, `sign_transfer` subsequently panics on the post-normalization guard, and no user-accessible recovery path exists.

## Finding Description

**Root cause:** The normalization check exists only inside `sign_transfer` (called later by a trusted relayer), not inside `init_transfer` or `init_transfer_internal` where funds are consumed.

`normalize_amount` uses floor division: [1](#0-0) 

The code comment at line 2781 explicitly acknowledges the behavior ("dust stays locked/burned"), but the referenced SECURITY.md contains only a generic Immunefi template with no NEAR-specific exclusion for this case.

`sign_transfer` enforces the post-normalization guard: [2](#0-1) 

By the time `sign_transfer` is called, `init_transfer_internal` has already burned or locked the tokens: [3](#0-2) 

The only pre-acceptance check in `init_transfer` is: [4](#0-3) 

There is no check that `normalize_amount(amount − fee, decimals) > 0` before funds are consumed. A grep for `cancel_transfer` and `set_locked_tokens` in `lib.rs` returns no matches, confirming there is no user-accessible recovery path.

**Exploit path:**
1. Token registered with `origin_decimals = 24`, `decimals = 6` (normalization factor = 10¹⁸).
2. User calls `ft_transfer_call` with `amount = 1`, `fee = 0`.
3. `init_transfer` passes the only check: `0 < 1`.
4. `init_transfer_internal` burns 1 yoctoNEAR and stores the transfer message.
5. Trusted relayer calls `sign_transfer`.
6. `normalize_amount(1, Decimals{decimals:6, origin_decimals:24})` = `1 / 10¹⁸` = **0**.
7. `require!(amount_to_transfer > 0, …)` panics; transaction reverts.
8. The user's 1 yoctoNEAR is permanently burned. No cancel or refund mechanism exists.

## Impact Explanation

This is **permanent freezing/loss of bridged funds** triggered by an unprivileged user through a standard public smart-contract call (`ft_transfer_call`). Deployed (foreign-origin) tokens are burned on NEAR with no recovery path. Native NEAR tokens are locked in the bridge with no user-accessible unlock. This matches the allowed Critical impact class: "permanent freezing of bridged funds" and "decimal/normalization abuse that changes user or protocol balances."

## Likelihood Explanation

The condition is reachable for any registered token pair where `origin_decimals > decimals`. The threshold for NEAR→EVM (24→6 decimals) is any amount below 10¹⁸ yoctoNEAR (< 0.000001 NEAR). This can be triggered accidentally (UI rounding, dust from prior operations) or deliberately by a malicious frontend. No special privileges are required — any token holder can trigger it via `ft_transfer_call`.

## Recommendation

Add a normalization guard inside `init_transfer` (or at the top of `init_transfer_internal`) **before** burning or locking tokens, mirroring the existing guard in `sign_transfer`:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This check should be placed before the `burn_tokens_if_needed` / `lock_tokens_if_needed` calls at [5](#0-4) 

so that the `ft_transfer_call` callback returns the full amount to the sender instead of consuming it.

## Proof of Concept

**Minimal contract call sequence (local testnet):**

1. Deploy the bridge contract and register a token with `origin_decimals = 24`, `decimals = 6`.
2. Call `ft_transfer_call` on the token contract with `amount = "1"` and a valid `InitTransferMsg` targeting an EVM chain.
3. Observe: `init_transfer_internal` emits `InitTransferEvent`; the token is burned/locked; `U128(0)` is returned (funds consumed).
4. Have a relayer call `sign_transfer` for the resulting transfer ID.
5. Observe: transaction panics with `InvalidAmountToTransfer`; no funds are returned; no cancel path exists.

**Invariant test:** Assert that for all registered token pairs, if `normalize_amount(amount - fee, decimals) == 0`, then `init_transfer` must return the full `amount` to the caller rather than emitting `InitTransferEvent`.
