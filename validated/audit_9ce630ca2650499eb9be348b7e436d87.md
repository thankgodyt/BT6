### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate, Bypassing Signature and Quorum Checks — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default implementation of `validatePerasCert` in the `BlockSupportsPeras` typeclass unconditionally returns `Right ValidatedPerasCert` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer that can submit a crafted Peras certificate to a node will have it accepted as fully valid, granting an arbitrary block a chain-selection weight boost without any quorum, signature, or eligibility check. The analog to the external report is exact: just as `BridgePool` inherited unnecessary mint/burn authority from `ExpandedERC20`, `validatePerasCert` grants every inbound certificate unconditional "validated" authority it has not earned.

---

### Finding Description

**Root cause — `validatePerasCert` is a stub that always succeeds:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` lines 350–358, the default typeclass method reads:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

The function signature is `validatePerasCert :: PerasParams -> PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)`. It is supposed to verify:
- that the certificate carries a valid aggregate BLS signature over the claimed election ID and boosted block,
- that the signers collectively hold sufficient stake to meet the quorum threshold,
- that each signer's VRF eligibility proof is valid (for non-persistent committee members).

None of these checks are performed. The function ignores the certificate's content entirely and wraps it in `Right`.

**Secondary stub — `validatePerasVote` skips signature verification:**

Lines 362–371 of the same file show `validatePerasVote` only checks that the voter's pool ID appears in the stake distribution; it never verifies the BLS vote signature (`pvSignature` field of `PerasVote`). A peer can submit a vote with a legitimate voter identity but a forged signature and it will be accepted.

**Code path from network to stub:**

Peras votes and certificates arrive over the peer-to-peer layer and are fed into `addPerasVoteWithAsyncCertHandling` / `addPerasCertAsync` in `ChainSel.hs` (lines 21–22 of the module export list). These call `validatePerasVote` / `validatePerasCert` before inserting into the vote/certificate stores and triggering chain selection. Because the stubs always return `Right`, the crafted objects pass directly into chain selection with a full `vpcCertBoost` weight.

**Analogy to the external report:**

`BridgePool` inherited `ExpandedERC20` (more privileged than `ERC20`), giving the deployer unnecessary mint/burn authority. Here, `validatePerasCert` grants every inbound certificate the authority of a fully-validated, quorum-backed certificate — authority it has not earned — because the function inherits the "always succeed" default instead of a properly restrictive implementation.

### Impact Explanation

**Severity: Critical** — falls squarely under the allowed scope item:

> *Critical. Bypass of leader eligibility, VRF/KES/certificate/signature validation, PBFT/Praos/TPraos/**Peras** voting or certificate checks, or hot-key rules that enables unauthorized block, vote, or certificate acceptance.*

An attacker with no stake and no keys can:

1. Craft a `PerasCert` naming any block hash as `pcCertBoostedBlock`.
2. Submit it to a target node.
3. The node calls `validatePerasCert`, receives `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`, and stores the certificate.
4. Chain selection now treats the attacker's chosen block as having a full Peras weight boost.
5. The node may switch to or prefer a chain the attacker controls, diverging from the honest chain — a consensus safety failure.

Because `vpcCertBoost` is derived from `perasWeight params` (a protocol parameter, not from actual stake), the boost is the same as a legitimately quorum-backed certificate.

---

### Likelihood Explanation

**Medium-High.** The stub is in production source (`ouroboros-consensus/src/ouroboros-consensus/`, not a test or mock directory). No concrete `BlockSupportsPeras` instance in the searched scope overrides the default with real validation. The TODO comment and linked issue (`tweag/cardano-peras#120`) confirm the stub is the live implementation. Any peer connected to a node with Peras enabled can trigger this path with a single crafted message; no keys, stake, or privileged access are required.

---

### Recommendation

Replace the stub with a complete implementation that:

1. Verifies the aggregate BLS signature in `pcCertBoostedBlock` against the aggregate public key derived from the declared voters' keys (using `verifyAggregateVoteSignature` already present in `Ouroboros.Consensus.Committee.Crypto`).
2. Checks that the declared voters collectively hold stake ≥ the quorum threshold from `PerasParams`.
3. For non-persistent voters, verifies each VRF eligibility proof against the epoch nonce and the voter's registered VRF key.
4. Rejects the certificate with a typed `PerasValidationErr` variant on any failure.

Until the full implementation is ready, the node should refuse to process inbound Peras certificates entirely (return a permanent `Left` error) rather than accept them unconditionally.

### Proof of Concept

**Private-testnet reproduction:**

1. Start a private Cardano testnet with Peras enabled (the `BlockSupportsPeras` instance active).
2. From an attacker node with zero stake, construct a `PerasCert` value:
   ```
   PerasCert { pcCertRound = <current round>, pcCertBoostedBlock = <attacker block hash> }
   ```
   with an arbitrary (invalid) aggregate signature field.
3. Inject the certificate via `addPerasCertAsync` (reachable through the Peras vote/cert miniprotocol).
4. Observe that `validatePerasCert` returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
5. Observe that chain selection now applies the full Peras weight boost to the attacker's chosen block, causing the honest node to prefer a chain it would otherwise reject.
