### Title
Unprivileged Users Can Bypass Deposit Fees via `safe_deposit` Path in `verify_deposit_v2` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`verify_deposit_v2` unconditionally routes to a zero-fee minting path whenever `deposit_msg.safe_deposit` is `Some(..)`. Because there is no access-control guard on this branch, any unprivileged NEAR account can obtain a deposit address derived from a `DepositMsg` with `safe_deposit = Some(..)`, deposit BTC to that address, and then call `verify_deposit_v2` to receive nBTC with **zero deposit fee**, bypassing the protocol's configured `deposit_bridge_fee`.

---

### Finding Description

`verify_deposit_v2` selects the execution path purely on whether `deposit_msg.safe_deposit` is `Some` or `None`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 81-101
if deposit_msg.safe_deposit.is_some() {
    self.internal_safe_verify_deposit_entry(...)   // ← charges NO fee
} else {
    self.internal_verify_deposit_entry(...)        // ← charges deposit_bridge_fee
}
```

The function's own doc-comment confirms the fee difference:

> `Some(..)` — safe deposit (e.g. Omni Bridge): **charges no fee** …  
> `None` — standard deposit: **charges the deposit fee** … [1](#0-0) 

The only decorator on `verify_deposit_v2` is `#[trusted_relayer]` and `#[pause]`. The `#[trusted_relayer]` attribute does **not** restrict who may call the function; it only increases the required confirmation count for callers not on the whitelist (controlled by `confirmations_delta`). [2](#0-1) 

The deposit address is derived from the full `DepositMsg` (including `safe_deposit`), so a user who wants to bypass fees simply:

1. Calls `get_user_deposit_address` with `deposit_msg.safe_deposit = Some(..)` to obtain a fee-free deposit address.
2. Sends BTC to that address on-chain.
3. Calls `verify_deposit_v2` with the same `DepositMsg` (`safe_deposit = Some(..)`) to mint nBTC with **zero deposit fee**.

The `BridgeFee` struct shows the fee that is bypassed:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
``` [3](#0-2) 

And the protocol/relayer split that is entirely skipped:

```rust
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
``` [4](#0-3) 

---

### Impact Explanation

Every deposit processed through the `safe_deposit` branch accrues **zero** to `cur_available_protocol_fee` and **zero** to the relayer. For a deposit of `N` satoshis with `fee_min = 10 000` sat and `protocol_fee_rate = 9 000` (90 %), the protocol loses up to 9 000 sat per deposit and the relayer loses 1 000 sat. At scale or for large deposits, this constitutes a meaningful and sustained bypass of the bridge's fee policy.

This matches the allowed Medium impact: **Bypass of bridge limits or policies**.

---

### Likelihood Explanation

The exploit requires no privileged role, no leaked key, and no external dependency. Any user who reads the public API (or the open-source contract) can construct the correct `DepositMsg`, obtain the fee-free deposit address, and execute the bypass. The only marginal cost is the NEAR storage deposit required by the `safe_deposit` path, which is negligible compared to the deposit fee saved on any non-trivial BTC amount.

---

### Recommendation

Add an explicit access-control check before routing to the fee-free path. Only accounts holding a designated role (e.g., `Role::OmniBridgeRelayer` or `Role::DAO`) should be permitted to supply `safe_deposit = Some(..)`:

```rust
if deposit_msg.safe_deposit.is_some() {
    let caller = env::predecessor_account_id();
    require!(
        self.acl_has_role(Role::SafeDepositRelayer.into(), caller),
        "Only authorized callers may use the safe_deposit path"
    );
    self.internal_safe_verify_deposit_entry(...)
} else {
    self.internal_verify_deposit_entry(...)
}
```

Alternatively, if the fee-free path is intentionally open to all users, document this explicitly and set `deposit_bridge_fee` to zero for the safe-deposit flow at the config level rather than silently skipping fee collection.

---

### Proof of Concept

1. Alice (unprivileged) calls `get_user_deposit_address` with:
   ```json
   { "deposit_msg": { "recipient_id": "alice.near", "safe_deposit": {}, "post_actions": null, "extra_msg": null, "refund_address": null } }
   ```
2. Alice sends 500 000 sat to the returned address on Bitcoin.
3. After sufficient confirmations, Alice (or any relayer) calls `verify_deposit_v2` with the same `DepositMsg` and a valid `TxInclusionProof`, attaching the required NEAR storage deposit.
4. `internal_safe_verify_deposit_entry` is invoked; **no** `deposit_bridge_fee` is deducted. Alice receives the full 500 000 sat as nBTC.
5. With `deposit_bridge_fee = { fee_min: 10000, fee_rate: 0, protocol_fee_rate: 9000 }`, the protocol loses 9 000 sat and the relayer loses 1 000 sat per such deposit. [5](#0-4) [6](#0-5)
