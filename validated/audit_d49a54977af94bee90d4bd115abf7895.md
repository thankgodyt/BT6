### Title
Peras Vote Validation Accepts Unauthenticated Votes, Enabling Forged Quorum and Chain Selection Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` performs no cryptographic signature verification because the `PerasVote` data type carries no signature field. Any unprivileged peer can forge votes for any voter ID present in the public stake distribution, for any round and any block target. These forged votes accumulate in the `PerasVoteDB`, trigger quorum, cause a `ValidatedPerasCert` to be forged, and are then submitted to chain selection via `addPerasCertAsync`, applying a `PerasWeight` boost to an adversarially chosen block. This is the direct analog of the Cosmos SDK `ValidateVoteExtensions` issue: total voting power is computed only from the votes present (which an attacker controls), not from the full validator set, and no round-number constraint is enforced.

---

### Finding Description

**Root cause — missing signature field and stub validation in `validatePerasVote`:**

The `PerasVote` data type has no signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

The `validatePerasVote` implementation only checks whether the voter ID appears in the stake distribution map; it performs no cryptographic check:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

The quorum check in `votesReachQuorum` / `stakeAboveThreshold` sums only the stakes of votes that are present, with no reference to the total stake of the full validator set:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [3](#0-2) 

The `stakeAboveThreshold` function itself carries an explicit TODO acknowledging that the `PerasVoteStake` values may not be normalized relative to the total stake, making the threshold comparison potentially meaningless: [4](#0-3) 

**Attacker-controlled entry path — `processVotes` in the diffusion layer:**

Inbound votes from peers flow through `processVotes`, which calls `validatePerasVote` as the sole gate:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

`processVotes` then adds all validated votes to the `PerasVoteDB` via `addPerasVoteWithAsyncCertHandling`: [6](#0-5) 

**Certificate forging and chain selection impact:**

When accumulated vote stake crosses the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert`, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params`. This certificate is then submitted to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message: [7](#0-6) 

`chainSelSync` processes the certificate and may switch the node to the boosted fork: [8](#0-7) 

**Secondary issue — `validatePerasCert` is also a stub:**

Certificates received directly from peers (via `makePerasCertPoolWriterFromChainDB`) are validated by `validatePerasCert`, which unconditionally returns `Right` for any certificate with any round number:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [9](#0-8) 

This is called in production via `makePerasCertPoolWriterFromChainDB`: [10](#0-9)

### Impact Explanation

An unprivileged peer with knowledge of any voter ID in the public stake distribution (which is public ledger state) can:

1. Craft `PerasVote` messages claiming to be multiple legitimate voters, all voting for an adversarially chosen block in any round number.
2. These votes pass `validatePerasVote` because the voter IDs exist in the stake distribution.
3. The accumulated fake stake crosses the quorum threshold, causing the node to forge a `ValidatedPerasCert` boosting the adversarial block.
4. The certificate is submitted to chain selection, applying a `PerasWeight` boost (default: 15) to the adversarial block.
5. The node may switch to a non-canonical chain that it would otherwise reject.

This matches: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

The voter IDs (`PerasVoterId`, which are `KeyHash StakePool`) are public ledger state, trivially enumerable. The attack requires only the ability to send network messages to the target node, which any peer in the diffusion layer can do. No key material, stake majority, or privileged access is required. The attack is deterministic and requires no brute force.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote`** and implement signature verification in `validatePerasVote`, binding each vote to the specific voter's key, round, and block target — analogous to how `WFALS.implVerifyVote` and `EveryoneVotes.implVerifyVote` verify vote signatures against the committee's public keys.
2. **Normalize `PerasVoteStake` before quorum comparison** in `stakeAboveThreshold`: the total stake of votes present must be divided by the total stake of the full validator set before comparing against the relative quorum threshold, so that a subset of voters cannot manufacture a false quorum.
3. **Validate the round number in `validatePerasCert`**: reject certificates whose `pcCertRound` is not the current or immediately preceding round, preventing injection of certificates from arbitrary past rounds.
4. **Implement `validatePerasCert` with actual quorum proof verification** rather than unconditionally returning `Right`.

---

### Proof of Concept

On a private testnet with a known stake distribution containing voter IDs `[v1, v2, v3]` each holding 30% relative stake (quorum threshold = 77%):

```
# Attacker sends forged votes to the target node for an adversarial block B_adv in round R:
send PerasVote { pvVoteRound = R, pvVoteBlock = B_adv, pvVoteVoterId = v1 }
send PerasVote { pvVoteRound = R, pvVoteBlock = B_adv, pvVoteVoterId = v2 }
send PerasVote { pvVoteRound = R, pvVoteBlock = B_adv, pvVoteVoterId = v3 }
```

Each vote passes `validatePerasVote` (voter IDs are in the stake distribution). After the third vote, `votesReachQuorum` returns `Just` (0.30 + 0.30 + 0.30 = 0.90 ≥ 0.77). `forgePerasCert` produces a `ValidatedPerasCert` boosting `B_adv` with `vpcCertBoost = 15`. `addPerasCertAsync` enqueues the certificate. `chainSelSync` applies the boost, and the node switches to the adversarial fork containing `B_adv`.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
