### Title
Deposit Mints During Migration Window Permanently Strand User nBTC Balances - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

### Summary
`internal_migrate_to_new_token` snapshots the old token's supply and per-account balances via async cross-contract calls, but does not lock the bridge against new deposits during the async window. Any `verify_deposit` call that completes between the snapshot queries and the `migrate_to_new_token_resolve` callback mints nBTC on the old token that is never replicated to the new token. After migration, `nbtc_account_id` is updated to the new token, permanently stranding those users' balances on the old token with no withdrawal path.

### Finding Description

`internal_migrate_to_new_token` dispatches parallel cross-contract reads (`ft_total_supply` + `ft_balance_of` for every account) against the old token, then chains a callback `migrate_to_new_token_mint`: [1](#0-0) 

In the callback, the integrity check compares the queried `sum` against the queried `total_supply` — both from the same snapshot — so the check always passes regardless of what happened to the old token after the queries were dispatched: [2](#0-1) 

The bridge has no migration-in-progress flag. `verify_deposit` and `verify_deposit_v2` are gated only by `#[trusted_relayer]` and `#[pause]`, not by any migration lock: [3](#0-2) 

A grep for `migration_in_progress`, `is_migrating`, or any equivalent guard returns no matches anywhere in the codebase.

When `migrate_to_new_token_resolve` fires, it unconditionally updates `nbtc_account_id` to the new token: [4](#0-3) 

Any nBTC minted on the old token after the snapshot but before this line is never replicated to the new token.

### Impact Explanation

After migration completes, the bridge uses the new token for all operations (withdrawals burn from the new token). Users whose nBTC was minted on the old token during the async window hold tokens that:
- Cannot be transferred to the bridge for withdrawal (bridge's `ft_on_transfer` now expects the new token)
- Cannot be burned (burn is called on the new token)
- Are permanently locked with no recovery path short of operator intervention

This constitutes permanent locking of user funds, matching the **Critical** impact category: *Significant loss, theft, destruction, or permanent locking of user or protocol funds.*

### Likelihood Explanation

The async window spans the time for the parallel `ft_total_supply` + `ft_balance_of` cross-contract calls to resolve — typically 1–3 NEAR blocks (~1–3 seconds). On an active bridge with pending BTC confirmations, a relayer processing a deposit during this window is a realistic, non-adversarial scenario. No malicious actor is required; normal bridge operation is sufficient.

### Recommendation

Before dispatching the snapshot queries, set a `migration_in_progress: bool` flag in contract state and check it at the start of `verify_deposit_callback` (and all other mint-triggering callbacks), reverting if migration is in progress. Clear the flag in `migrate_to_new_token_resolve` after updating `nbtc_account_id`. Alternatively, require the operator to pause the bridge before calling `migrate_to_new_token`, and enforce this with an explicit `require!(!self.is_paused(), "bridge must be paused during migration")` guard.

### Proof of Concept

1. Bridge has old token with holders A (500 sat) and B (500 sat); `total_supply = 1000`.
2. MigrationOperator calls `migrate_to_new_token(new_token, [A, B])`.
3. Bridge dispatches `ft_total_supply` and `ft_balance_of(A)`, `ft_balance_of(B)` — these are async; the bridge contract is now free to accept new calls.
4. While those queries are in-flight, a relayer calls `verify_deposit` for user C's confirmed BTC transaction. The deposit callback fires and calls `nbtc.mint(C, 100)` on the **old** token. Old token now has `total_supply = 1100`.
5. The snapshot queries resolve: `total_supply = 1000`, `A = 500`, `B = 500`, `sum = 1000`. The check `sum == total_supply` passes (both values are from the pre-mint snapshot).
6. `migrate_to_new_token_mint` mints A=500 and B=500 on the new token.
7. `migrate_to_new_token_resolve` sets `nbtc_account_id = new_token`.
8. Result: new token supply = 1000; old token supply = 1100. C holds 100 nBTC on the old token. The bridge now routes all withdrawals through the new token. C's 100 nBTC are permanently stranded — they cannot be used to withdraw BTC. [5](#0-4) [6](#0-5)

    pub(crate) fn internal_migrate_to_new_token(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> Promise {
        let old_token = self.internal_config().nbtc_account_id.clone();
        require!(
            new_token != old_token,
            "New token must differ from the current token"
        );

        let mut queries = ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_total_supply();
        for account in &accounts {
            queries = queries.and(
                ext_nbtc::ext(old_token.clone())
                    .with_static_gas(GAS_FOR_FT_QUERY)
                    .ft_balance_of(account.clone()),
            );
        }

        let callback_gas = Gas::from_gas(
            GAS_FOR_MIGRATION_MINT_CALL_BACK.as_gas()
                + GAS_FOR_MIGRATION_RESOLVE_CALL_BACK.as_gas()
                + GAS_FOR_MINT_ACTION.as_gas() * accounts.len() as u64,
        );
        queries.then(
            Self::ext(env::current_account_id())
                .with_static_gas(callback_gas)
                .migrate_to_new_token_mint(new_token, accounts),
        )
    }

    #[private]
    pub fn migrate_to_new_token_resolve(
        &mut self,
        new_token: AccountId,
        accounts: usize,
        total_amount: U128,
    ) {
        require!(is_promise_success(), "Migration mint failed");
        self.internal_mut_config().nbtc_account_id = new_token.clone();
        Event::TokenMigrated {
            new_token: &new_token,
            accounts,
            total_amount,
        }
        .emit();
    }
