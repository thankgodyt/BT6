Batch-Rejection in Peras Vote/Certificate Inbound Processing Allows Unprivileged Peer to Suppress Valid Votes and Prevent Certificate Formation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

Both `processVotes` and `processCerts` implement an all-or-nothing batch-rejection policy: if **any single** vote or certificate in a received batch fails validation, the **entire batch** is discarded and the sending peer is disconnected. An unprivileged peer can exploit this by mixing one crafted invalid vote/certificate with several valid ones from legitimate voters, causing the receiving node to permanently discard those valid votes. If done consistently across the voting window, this prevents quorum from being reached, suppresses Peras certificate formation, and removes the chain-weight boost that Peras provides to the honest chain — enabling an adversary to influence chain selection in favor of a less-secure or adversarially-boosted chain.

---

### Finding Description

In `processVotes`:

  ([], validatedVotes) ->
    mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _) ->
    throw (PerasVoteValidationError errs)   -- entire batch discarded
``` [1](#0-0) 

The same pattern appears in `processCerts`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)   -- entire batch discarded
``` [2](#0-1) 

The `processVotes` function first filters out votes already in the DB, then validates the remainder atomically in a single STM transaction, and then either accepts all or rejects all: [3](#0-2) 

The `opwAddObjects` field of `ObjectPoolWriter` is set to `processVotes` in `makePerasVotePoolWriterFromChainDB`, which is the production path used by the ObjectDiffusion inbound miniprotocol handler: [4](#0-3) 

The inbound handler calls `opwAddObjects` when it receives a `CollectObjects` message from a peer: [5](#0-4) 

The attack exploits the fact that an adversary can observe valid votes being diffused on the network, collect them, append one crafted invalid vote, and re-send the combined batch to a target node. The target node's `processVotes` will reject the entire batch — including the valid votes from legitimate voters — because `partitionEithers` finds at least one error. The valid votes in the rejected batch are silently dropped; they are not re-requested from other peers.

The `alreadyInDb` filter only skips votes whose IDs are already present. If the adversary sends the poisoned batch before the valid votes arrive from other peers, those votes are lost for this node. [6](#0-5) 

---

### Impact Explanation

Peras certificates provide a chain-weight boost (`perasWeight`) to blocks they endorse. This boost is the core mechanism by which Peras accelerates finality and strengthens chain selection against adversarial forks: [7](#0-6) 

Certificates are forged only when accumulated vote stake crosses the quorum threshold (`perasQuorumStakeThreshold`). If an adversary can prevent a node from accumulating enough valid votes, no certificate is forged, and the honest chain loses its weight boost. The adversary's chain — which may carry a certificate from a different round or target — can then be preferred by chain selection.

This maps to the **High** impact class: a chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

The `addPerasCertAsync` path confirms that certificates directly trigger chain selection re-evaluation: [8](#0-7) 

---

### Likelihood Explanation

The attack requires only a single connected peer. The adversary:
1. Observes valid votes being diffused on the network (they are public).
2. Constructs a batch containing those valid votes plus one crafted invalid vote (e.g., a vote with a `PerasVoterId` not present in the stake distribution, which causes `validatePerasVote` to return `Left PerasValidationErr`).
3. Sends the poisoned batch to the target node via the ObjectDiffusion miniprotocol.

The current `validatePerasVote` implementation returns `Left PerasValidationErr` whenever the voter ID is absent from the stake distribution: [9](#0-8) 

This is trivially triggerable. The adversary does not need stake, keys, or any privileged access. The attack is repeatable every voting round.

---

### Recommendation

Replace the all-or-nothing batch policy with per-item processing: accept valid votes/certificates individually and discard only the invalid ones. The peer should be disconnected only if it sends a vote/certificate that is structurally malformed (protocol violation), not merely invalid by consensus rules. This mirrors the fix applied in the referenced external report (processing valid items rather than reverting the entire operation).

Concretely, change `processVotes` and `processCerts` to:
1. Partition results with `partitionEithers` as today.
2. Add all valid items from `validatedVotes`/`validatedCerts` to the pool regardless of whether some items failed.
3. Only disconnect the peer if the invalid items represent a protocol-level violation (e.g., structurally malformed data), not a consensus-level invalidity.

---

### Proof of Concept

1. Node A is running with the Peras ObjectDiffusion inbound handler active.
2. Adversary peer B observes votes `v1, v2, v3` (all valid, from legitimate voters) being diffused on the network.
3. Adversary B constructs `v_bad`: a `PerasVote` with a `pvVoteVoterId` not present in the current `PerasVoteStakeDistr`. `validatePerasVote` will return `Left PerasValidationErr` for this vote.
4. Adversary B sends the batch `[v1, v2, v3, v_bad]` to Node A via `MsgReplyObjects` in the ObjectDiffusion protocol.
5. Node A's `processVotes` runs `partitionEithers` over the validation results. `v_bad` produces an error.
6. The `(errs, _)` branch fires: `throw (PerasVoteValidationError errs)` — the entire batch including `v1, v2, v3` is discarded.
7. Node A never adds `v1, v2, v3` to its vote pool. If B repeats this attack each time new valid votes appear, Node A never accumulates enough stake to reach quorum, no certificate is forged, and the honest chain loses its Peras weight boost. [1](#0-0) [10](#0-9)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes

    -- encountered.
