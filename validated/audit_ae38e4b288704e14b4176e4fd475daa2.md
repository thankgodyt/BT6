Audit Report

## Title
Excess ETH Permanently Lost Due to Missing Fee Validation in Wormhole Extension Hooks - (File: `evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

## Summary
`OmniBridgeWormhole` overrides `deployTokenExtension`, `logMetadataExtension`, and `finTransferExtension` to forward the caller's full `msg.value` verbatim to `_wormhole.publishMessage`. No check enforces `msg.value == _wormhole.messageFee()` and no excess is refunded. Any ETH above the required Wormhole fee is permanently transferred to the Wormhole core bridge contract and irrecoverable by the caller.

## Finding Description
Three extension hooks in `OmniBridgeWormhole` forward `msg.value` directly:

- `deployTokenExtension` (L63): `_wormhole.publishMessage{value: msg.value}(...)`
- `logMetadataExtension` (L87): `_wormhole.publishMessage{value: msg.value}(...)`
- `finTransferExtension` (L109): `_wormhole.publishMessage{value: msg.value}(...)`

The base entry points `deployToken` (L138), `logMetadata` (L224), and `logMetadata1155` (L234) are all `external payable` with no ETH accounting guard before calling the extension. The `IWormhole` interface exposes `messageFee()` (L15) but it is never queried in any of these paths.

For `initTransfer` (ERC20 path), `extensionValue = msg.value - nativeFee` (L393) is passed to `initTransferExtension` and forwarded to Wormhole (L143). If `msg.value - nativeFee > messageFee()`, the excess is equally lost.

When `messageFee() == 0` (current Wormhole mainnet value), any non-zero `msg.value` sent to `logMetadata`, `logMetadata1155`, or `deployToken` is entirely and permanently lost to the Wormhole contract.

## Impact Explanation
This is a fee mis-accounting flaw that causes direct, irreversible loss of user ETH. The functions are `external payable`, creating a reasonable expectation that ETH is either consumed exactly or refunded. Instead, any overpayment is silently transferred to the Wormhole core bridge with no recovery path. This matches the Critical allowed impact: **fee mis-accounting that changes user or protocol balances**.

## Likelihood Explanation
These are permissionless, publicly callable functions. Any token deployer or metadata logger interacting with the Wormhole-variant bridge is exposed. Users who send a small overpayment to guarantee transaction success — a common Ethereum pattern — silently lose the excess. With `messageFee() == 0` on mainnet, any user who sends ETH at all to `logMetadata` or `deployToken` loses the entire amount. The Wormhole fee can also change over time, making exact-fee knowledge non-trivial for integrators.

## Recommendation
Add an explicit check in each Wormhole extension hook that `msg.value == _wormhole.messageFee()` (or for `initTransfer`, that `extensionValue == _wormhole.messageFee()`), and revert with a descriptive error if not. Alternatively, compute the exact required fee and refund any excess to `msg.sender` after the `publishMessage` call:

```solidity
function logMetadataExtension(...) internal override {
    uint256 fee = _wormhole.messageFee();
    require(msg.value == fee, "InvalidWormholeFee");
    _wormhole.publishMessage{value: fee}(...);
}
```

For `initTransfer`, enforce `extensionValue == _wormhole.messageFee()` before forwarding.

## Proof of Concept
1. Deploy `OmniBridgeWormhole` pointing to a Wormhole core bridge where `messageFee() == X` (or `X == 0` on mainnet).
2. Call `logMetadata(tokenAddress)` with `msg.value = X + 1 ether`.
3. `logMetadataExtension` executes `_wormhole.publishMessage{value: X + 1 ether}(...)`.
4. Wormhole accepts the call (fee satisfied), retaining `X + 1 ether`.
5. The caller's `1 ether` excess is permanently locked in the Wormhole contract with no refund path.
6. Repeat with `deployToken` and `finTransfer` for the same result; for `initTransfer` (ERC20), send `msg.value = nativeFee + messageFee() + 1 ether` to lose `1 ether`.

A fuzz test can confirm: for any `msg.value > messageFee()`, the caller's post-call ETH balance decreases by `msg.value` rather than `messageFee()`.
