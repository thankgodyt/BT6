### Title
Attacker Can Block User Refund Requests by Front-Running `request_refund` with Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account. The `request_refund_callback` enforces a uniqueness check on `utxo_storage_key` and panics if a refund request already exists for that UTXO. An attacker who observes a confirmed BTC deposit (whose `deposit_msg` is publicly emitted via `LogDepositAddress` events) can race the legitimate user by submitting a refund request for the same UTXO with an attacker-controlled `refund_address`. This permanently blocks the user's own `request_refund` call until a DAO/Operator manually rejects the attacker's entry, requiring privileged operator intervention to unblock the user's funds.

---

### Finding Description

**Root cause — no access control on `request_refund`**

The `request_refund` public method carries only `#[payable]` and `#[pause]` attributes: [1](#0-0) 

The `#[trusted_relayer]` attribute on the surrounding `impl` block does **not** gate individual methods; only methods that carry `#[trusted_relayer]` on the method itself are restricted to whitelisted relayers. Comparing `verify_refund_finalize` (which has `#[trusted_relayer]` on the method and is relayer-gated) with `request_refund` (which does not) confirms this: [2](#0-1) 

**Root cause — hard panic on duplicate UTXO key**

Inside `request_refund_callback`, after the Light Client proof is verified, the callback checks for a pre-existing request and panics if one is found: [3](#0-2) 

There is no fallback, no idempotency path, and no way for the legitimate user to recover without operator intervention.

**Root cause — `deposit_msg` is publicly broadcast**

`get_user_deposit_address` emits a `LogDepositAddress` event that includes the full `deposit_msg`: [4](#0-3) 

An attacker passively monitoring NEAR events learns every `deposit_msg` and its corresponding BTC deposit address. Once the BTC transaction confirms on-chain, the attacker has all inputs needed to construct a valid `request_refund` call.

**Attack path**

1. Attacker monitors NEAR for `LogDepositAddress` events, collecting `(deposit_msg, btc_address)` pairs.
2. Attacker watches the BTC chain for a confirmed deposit to any known address.
3. Attacker calls `request_refund` with the victim's `deposit_msg`, the same `tx_bytes`/`vout`/`proof`, but with the attacker's own BTC `refund_address` (permitted because `deposit_msg.refund_address` is `None` in the standard flow).
4. The Light Client proof passes; `request_refund_callback` stores the attacker's entry under `utxo_storage_key`.
5. The victim calls `request_refund` — the callback panics: `"Refund request already exists for this UTXO"`.
6. The victim's BTC is stuck. The attacker's entry sits with `unsafe_refund_timelock_sec` ticking down. [5](#0-4) 

---

### Impact Explanation

The victim cannot obtain a refund through the normal flow. Their BTC deposit is locked in the bridge's UTXO set with no self-service recovery path. The only resolution is for a DAO/Operator to call `reject_refund` on the attacker's entry, after which the victim may retry. This constitutes **attacker-triggered temporary locking of bridged funds requiring operator intervention** — a Medium bridge impact.

Additionally, if the DAO/Operator fails to reject the attacker's request before `unsafe_refund_timelock_sec` elapses, `execute_refund` becomes callable by anyone and would route the victim's BTC to the attacker's `refund_address` via the MPC signing pipeline: [6](#0-5) 

---

### Likelihood Explanation

- `request_refund` requires only an attached NEAR deposit (storage fee) and a valid BTC Merkle proof — both are trivially obtainable by any NEAR account once the BTC transaction is confirmed.
- The `deposit_msg` is publicly emitted on every `get_user_deposit_address` call, so the attacker needs no privileged information.
- The attack window opens the moment the BTC transaction reaches the required confirmation depth, which is the same moment the victim would attempt to request a refund.
- No special role, leaked key, or majority attack is required.

---

### Recommendation

1. **Bind refund requests to the caller**: Store `predecessor_account_id()` in the refund request at submission time and require that only the original submitter (or DAO/Operator) can have their request stored, or alternatively allow only one request per UTXO per account.
2. **Alternatively, allow idempotent re-submission**: If a refund request already exists for the UTXO and was submitted by the same caller with the same `refund_address`, treat it as a no-op rather than panicking.
3. **Restrict `request_refund` to trusted relayers or the deposit recipient**: Add `#[trusted_relayer]` to the method, or verify that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`.

---

### Proof of Concept

```
# 1. Attacker reads LogDepositAddress event from NEAR:
#    deposit_msg = { recipient_id: "victim.near", ... }
#    btc_address = "bc1q..."

# 2. BTC tx confirmed: txid = "abc123", vout = 0

# 3. Attacker calls (any NEAR account, with storage deposit attached):
request_refund(
  deposit_msg   = { recipient_id: "victim.near", ... },  # from event
  refund_address = "attacker_btc_address",               # attacker-controlled
  tx_bytes      = <confirmed BTC tx bytes>,
  vout          = 0,
  proof         = <valid Merkle proof>,
  gas_fee       = None
)
# → stored: refund_requests["abc123@0"] = { refund_address: "attacker_btc_address", ... }

# 4. Victim calls request_refund with their own refund_address:
# → request_refund_callback panics: "Refund request already exists for this UTXO"
# → victim's BTC is locked; operator intervention required
```

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }
