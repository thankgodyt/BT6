Audit Report

## Title
`fin_transfer_send_tokens_callback` Ignores `ft_transfer` Failure for Native Tokens, Permanently Freezing Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When finalizing an inbound transfer to a NEAR recipient with an empty `msg`, `process_fin_transfer_to_near` records the transfer as finalized via `add_fin_transfer` and then dispatches a plain `ft_transfer`. If that `ft_transfer` fails (e.g., the recipient is blacklisted by a USDC-style NEP-141 token), the callback `fin_transfer_send_tokens_callback` receives `is_ft_transfer_call = false` and calls `is_refund_required(false)`, which unconditionally returns `false` without inspecting the promise result. No recovery path is taken: the transfer ID remains consumed in `finalised_transfers`, the tokens remain locked in the bridge, and there is no admin escape hatch to release them.

## Finding Description

`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, committing the transfer ID to `finalised_transfers` in the current receipt before any cross-contract call is made. [1](#0-0) 

`send_tokens` is then dispatched. For a non-deployed (native) token with an empty `msg`, it issues a plain `ft_transfer`: [2](#0-1) 

The callback is chained with `is_ft_transfer_call = !msg.is_empty()`, so when `msg` is empty, `is_ft_transfer_call = false`: [3](#0-2) 

Inside `fin_transfer_send_tokens_callback`, the recovery branch is gated entirely on `is_refund_required`: [4](#0-3) 

`is_refund_required(false)` unconditionally returns `false` — it never calls `env::promise_result_checked`: [5](#0-4) 

Because `is_refund_required` returns `false`, the callback falls into the `else` branch, sends fees, and logs `FinTransferEvent` as if the transfer succeeded — regardless of whether `ft_transfer` panicked: [6](#0-5) 

Under NEAR's execution model, `add_fin_transfer`'s state change is committed in the scheduling receipt; only the token contract's receipt is reverted on failure. The bridge ends up with the transfer marked finalized but the tokens never delivered. `remove_fin_transfer` and `revert_lock_actions` are never called, so the transfer ID is consumed and the locked tokens have no release path.

## Impact Explanation

This directly satisfies the Critical impact category: **permanent freezing of bridged funds**. Native tokens (e.g., USDC held in escrow by the bridge) that cannot be delivered to a blacklisted recipient become permanently irrecoverable. The transfer ID is consumed from `finalised_transfers`, so the proof cannot be replayed. The tokens sit in the bridge contract indefinitely with no admin function to forcibly remove a finalized transfer or redirect tokens.

## Likelihood Explanation

Circle's native USDC on NEAR implements a blacklist. A user whose NEAR address is added to that blacklist after initiating a cross-chain transfer — or who is already blacklisted when a relayer finalizes — triggers this path. The relayer cannot substitute a different recipient because the recipient is embedded in the verified proof. No privileged access is required; any unprivileged bridge user whose address is blacklisted by a supported NEP-141 token with transfer restrictions can trigger this condition. The relayer calling `fin_transfer` is the proximate trigger, but the root cause is the missing promise-result check in the callback.

## Recommendation

1. **Check the promise result for `ft_transfer` as well.** Extend `is_refund_required` (or add a parallel check) to call `env::promise_result_checked(0, …)` even when `is_ft_transfer_call = false`. If the promise failed, execute the same recovery path: `remove_fin_transfer`, `revert_lock_actions`, and emit `FailedFinTransferEvent`.
2. **Add an alternative recipient field** to `TransferMessage` so a relayer or the user can supply a fallback delivery address without invalidating the proof.
3. **Add an admin escape hatch** to forcibly remove a stuck finalized transfer and return the locked tokens to a designated address as a last-resort recovery mechanism.

## Proof of Concept

1. Alice initiates a transfer of native USDC (NEP-141, blacklist-enabled) from Ethereum to `alice.near`.
2. Before the relayer finalizes, Circle blacklists `alice.near`.
3. Relayer calls `fin_transfer` on NEAR. `process_fin_transfer_to_near` runs:
   - `add_fin_transfer` records the transfer ID in `finalised_transfers` (line 1875).
   - `send_tokens` dispatches `ft_transfer(alice.near, amount, None)` (lines 2102–2106).
4. USDC's `ft_transfer` panics because `alice.near` is blacklisted. Promise result is `Failed`.
5. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
6. `is_refund_required(false)` returns `false` unconditionally (lines 1800–1803).
7. The callback logs `FinTransferEvent` as if the transfer succeeded. No `remove_fin_transfer` or `revert_lock_actions` is called (lines 1719–1746).
8. Alice's USDC is permanently locked in the bridge. The transfer ID is consumed. No retry is possible.

A local integration test can demonstrate this by deploying a mock NEP-141 token whose `ft_transfer` always panics, calling `fin_transfer` for a transfer to that token's recipient, and asserting that (a) the promise result is `Failed`, (b) the transfer ID remains in `finalised_transfers`, and (c) the bridge's token balance is unchanged while no `FailedFinTransferEvent` was emitted.
