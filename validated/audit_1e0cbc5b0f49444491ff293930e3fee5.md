### Title
Missing Peras Vote Signature Verification Enables Unauthorized Vote Acceptance and Quorum Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production catch-all `BlockSupportsPeras` instance's `validatePerasVote` implementation performs **no cryptographic signature verification** on inbound Peras votes. Combined with the `PerasVoteId`-based deduplication check in `processVotes`, which keys on only `(roundNo, voterId)` and not the voted block, an unprivileged peer can forge a vote for any registered voter, have it accepted and stored, and cause the legitimate voter's real vote to be silently dropped as a duplicate. This allows an attacker to redirect any voter's stake toward an attacker-chosen block and manipulate Peras quorum and chain-selection boosting.

---

### Finding Description

**Root cause — no signature check in `validatePerasVote`:**

The only `BlockSupportsPeras` instance in production source is the catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

The function accepts any `PerasVote` whose `pvVoteVoterId` appears in the stake distribution. No BLS signature over `(roundNo, boostedBlock)` is verified. The concrete V1 vote type in `Peras/Vote/V1.hs` carries a `pvSignature :: VoteSignature PerasBLSCrypto` field and the `CryptoSupportsVoteSigning` interface (`Committee/Crypto.hs`) provides `verifyVoteSignature`, but neither is invoked here.

**Deduplication keyed only on `(roundNo, voterId)` — not on the voted block:**

`processVotes` in `ObjectPool/PerasVote.hs` filters inbound votes before validation:

```haskell
let votesNotAlreadyInDb =
      filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
```

`getPerasVoteId` returns:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo  :: !PerasRoundNo
  , pviVoterId  :: !PerasVoterId
  }
```

The voted block (`pvVoteBlock`) is **not** part of the ID. The model explicitly acknowledges this assumption:

```
-- NOTE: this is under the assumption that a voter doesn't cast two different
-- votes for the same round (that is, with the same ID but different body).
```

This assumption is never enforced by signature verification.

**Attack path:**

1. Attacker observes the stake distribution (public) and picks target voter `X`.
2. Attacker sends a forged `PerasVote { pvVoteRound = R, pvVoteBlock = A, pvVoteVoterId = X }` to the victim node via the node-to-node object-diffusion mini-protocol.
3. `processVotes` calls `validatePerasVote`: voter `X` is in the stake distribution → vote is accepted as `ValidatedPerasVote` with `X`'s stake weight.
4. The vote is stored in `PerasVoteDbState` under ID `(R, X)`.
5. Voter `X`'s legitimate vote for block `B` arrives later → `getPerasVoteId` returns the same `(R, X)` → filtered out as "already in DB" → silently dropped.
6. The attacker has permanently redirected `X`'s stake-weighted vote to block `A` for round `R`.

Repeating this for enough voters allows the attacker to manufacture a fraudulent Peras quorum for any block, or to suppress a legitimate quorum from forming.

---

### Impact Explanation

Peras certificates are produced when a quorum of votes for the same `(round, block)` target is reached. A certificate boosts the weight of the targeted block in chain selection (`ValidatedPerasCert.vpcCertBoost`). By forging votes for an attacker-chosen block and suppressing legitimate votes, an attacker can:

- Force a fraudulent Peras certificate to be generated for a non-canonical or adversarially chosen block.
- Prevent a legitimate certificate from forming, denying the Peras safety boost to the honest chain.
- Cause honest nodes to prefer a different chain than they otherwise would, constituting a chain-selection safety failure.

This is a **Critical** impact: bypass of Peras voting checks enabling unauthorized certificate and vote acceptance.

---

### Likelihood Explanation

- **Entry path is fully unprivileged**: any peer connected via the node-to-node object-diffusion protocol can send `PerasVote` objects.
- **No key material required**: the attacker only needs to know a voter's `PerasVoterId` (a `KeyHash StakePool`, which is public on-chain).
- **No brute force**: a single well-formed forged vote per target voter per round is sufficient.
- **Race condition is mild**: the attacker only needs to deliver the forged vote before the legitimate voter's vote reaches the victim node, which is straightforward given network-level timing control.

Likelihood: **High** once Peras is active on a live network.

---

### Recommendation

1. **Enforce signature verification inside `validatePerasVote`**: call `verifyVoteSignature` (from `CryptoSupportsVoteSigning`) against the voter's public key before accepting any vote. The BLS infrastructure (`Committee/Crypto/BLS.hs`, `Peras/Crypto/BLS.hs`) already provides this.
2. **Include the voted block in `PerasVoteId`**: the deduplication key should be `(roundNo, voterId, votedBlock)` so that equivocating votes (same voter, same round, different block) are not silently collapsed.
3. **Validate before deduplication-filter**: the current `processVotes` flow filters by ID first, then validates. Signature verification must happen before the vote is stored, not after.

---

1. A sends PerasVote {
     pvVoteRound   = R,
     pvVoteBlock   = attacker_block,   -- attacker's preferred block
     pvVoteVoterId = voter_X,          -- legitimate voter's public key hash
     -- no valid signature required
   }

2. V: processVotes calls validatePerasVote
   → lookupPerasVoteStake finds voter_X → stake_s
   → returns Right (ValidatedPerasVote { vpvVote, vpvVoteStake = stake_s })

     pvVoteRound   = R,
     pvVoteBlock   = honest_block,
     pvVoteVoterId = voter_X,
   }

   → getPerasVoteId → PerasVoteId { R, voter_X }
   → Set.member → True (already in DB)
   → vote silently dropped

Result: attacker_block accumulates voter_X's stake weight toward quorum;

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
