### Title
Stale (Empty) Peras Weight Snapshot in ChainSync Client Forecast-Horizon Disconnection Check Causes Incorrect Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client uses a hardcoded `emptyPerasWeightSnapshot` instead of the live Peras weight snapshot when deciding whether to disconnect from a peer whose header is beyond the forecast horizon. This mirrors the external report's root cause exactly: a state value that should be current is stale (here, permanently zero) at the point where it is used for a critical decision. The result is that the node may disconnect from an honest peer offering a legitimately heavier Peras-boosted chain, causing the node to prefer a lighter, non-canonical chain.

---

### Finding Description

When the ChainSync client receives a header whose slot is beyond the current forecast horizon, it blocks waiting for the local selection to advance. During this wait it calls `checkPreferTheirsOverOurs` to decide whether to keep the connection open or disconnect (throwing `CandidateTooSparse`):

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero; never the live snapshot
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` has two branches: when the weight snapshot is empty it falls back to a pure block-count comparison; when it is non-empty it computes `weightedSelectView` using the actual Peras certificate boosts:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- pure block-count comparison
      ...
  | otherwise =
      -- weighted comparison using certificate boosts
      ...
``` [2](#0-1) 

Because `emptyPerasWeightSnapshot` is always passed, the weighted branch is never reached inside `checkPreferTheirsOverOurs`. The live snapshot — populated by `PerasCertDB` as certificates arrive — is available via `getPerasWeightSnapshot` and is correctly used everywhere else in chain selection:

```haskell
-- In chainSelSync (ChainSel.hs):
<*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [3](#0-2) 

The `PerasWeightSnapshot` is built from all certificates in `PerasCertDB` and maps each boosted block point to its accumulated `PerasWeight`:

```haskell
newtype PerasWeightSnapshot blk = PerasWeightSnapshot
  { getPerasWeightSnapshot :: Map (Point blk) PerasWeight }
``` [4](#0-3) 

The `wsvTotalWeight` used for chain ordering is `BlockNo + PerasWeight`, so a chain with fewer blocks but a large certificate boost can legitimately outweigh a longer chain:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4)

### Impact Explanation

**High — Chain selection error that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

Concrete scenario once Peras certificates are live:

1. Honest node holds chain C (length 10, Peras weight 10).
2. Honest peer B offers candidate chain D (length 9, Peras weight 20 due to a certificate boost) — D is the canonical chain under Peras.
3. Adversary peer A offers chain E (length 11, Peras weight 11) — E is lighter but longer.
4. Header in D is beyond the forecast horizon; `checkPreferTheirsOverOurs` fires.
5. With `emptyPerasWeightSnapshot`, D (9 blocks) appears shorter than C (10 blocks) → `CandidateTooSparse` → node disconnects from peer B.
6. Node stays connected to adversary A and eventually adopts chain E (11 > 10 by block count).
7. Chain D (weight 20) — the correct canonical chain — is never adopted.

The adversary needs only to offer a longer-by-block-count but lighter-by-weight chain; no keys, stake, or privileged access are required.

---

### Likelihood Explanation

**Medium.** The preconditions are:

- Peras certificate issuance is active (the protocol is in active development and the infrastructure — `PerasCertDB`, `PerasVoteDB`, `shelleyLedgerLatestPerasCertRound` — is already wired into production code).
- A certificate boost exists that makes a shorter chain heavier than the node's current selection.
- The boosted chain's next header happens to be beyond the current forecast horizon (a normal transient condition during sync or after a gap).

All three conditions are realistic during normal operation once Peras is enabled. The TODO comment (`// TODO: remove this entire check`) confirms the developers recognise the check is incorrect but have not yet removed or fixed it. [6](#0-5) 

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot. The snapshot is already available in the `ChainDbView` used by the ChainSync client (via `getPerasWeightSnapshot`). The fix mirrors what `chainSelSync` already does:

```diff
- emptyPerasWeightSnapshot
+ liveWeightSnapshot   -- obtained from ChainDB.getPerasWeightSnapshot
```

Alternatively, if the intent is to remove the check entirely (as the TODO suggests), the check should be deleted rather than left with incorrect semantics that will silently misbehave once Peras is active.

---

### Proof of Concept

No code changes are needed to demonstrate the root cause; it is directly visible in the production source:

1. `checkPreferTheirsOverOurs` at line 1839 passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate`. [6](#0-5) 

2. `preferAnchoredCandidate` at line 1187 takes the `isEmptyPerasWeightSnapshot` branch and performs a pure block-count comparison, ignoring all certificate boosts. [7](#0-6) 

3. The live snapshot is populated by `implGetWeightSnapshot` in `PerasCertDB/Impl.hs` from all stored certificates, and is correctly used in `chainSelSync` — but not here. [8](#0-7) 

4. A node running with active Peras certificates and a peer whose boosted-but-shorter chain header is beyond the forecast horizon will hit `CandidateTooSparse` and disconnect, permanently missing the canonical chain until it reconnects and the forecast horizon advances past that header — by which point the adversary's longer-but-lighter chain may already be adopted.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
