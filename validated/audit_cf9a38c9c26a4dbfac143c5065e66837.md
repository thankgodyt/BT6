### Title
Stale `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Causes Incorrect Peer Disconnection from Canonical Peras-Boosted Chain — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs` inside the ChainSync client, the chain-preference comparison uses a hardcoded `emptyPerasWeightSnapshot` (zero Peras weight boosts) instead of the actual live `PerasWeightSnapshot`. This is the direct analog of the Morpho bug: a threshold comparison uses a stale/zero value on one side while the real decision-making path uses the fully-updated value, causing the wrong branch to be taken. When Peras is active and a peer's candidate chain has fewer blocks but higher Peras-boosted total weight than the local chain, the stale empty snapshot causes the node to incorrectly conclude the candidate is not preferred and disconnect from the peer with `CandidateTooSparse` — even though the real chain selection logic (which uses actual weights) would have preferred and adopted that chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is called inside `readLedgerStateHelper` when `forecastFor` returns `OutsideForecastRange` (the peer's header is beyond the forecast horizon). Its purpose is: *if their chain is not preferred over ours, disconnect now rather than waiting forever for a chain we would never select anyway*.

The comparison is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← stale: always zero Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`. When the snapshot is empty it falls into the **block-count-only** path; when non-empty it falls into the **Peras-weighted** path:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- compares only by BlockNo / SelectView (block count)
      ...
  | otherwise =
      -- compares by wsvTotalWeight = BlockNo + PerasWeightBoost
      ...
```

Meanwhile, the actual chain selection in `ChainSel.hs` always passes the real `weights` snapshot:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
```

and

```haskell
. NE.filter (not . Diff.rollbackExceedsSuffix weights curChain)
```

The mismatch is exact: `checkPreferTheirsOverOurs` evaluates the "should we keep this peer?" question with zero Peras boosts, while the actual "should we adopt this chain?" question is evaluated with real Peras boosts. These two evaluations can disagree whenever any block on either fragment carries a non-zero Peras weight boost.

**Vulnerable scenario** (analogous to Morpho's wrong-branch case):

- Our chain has N blocks, no Peras boosts → real weight = N.
- Peer's chain has M < N blocks, but each block carries a Peras boost B → real weight = M + M·B >> N.
- `checkPreferTheirsOverOurs` with empty snapshot: `BlockNo M < BlockNo N` → `ShouldNotSwitch` → **disconnect** (`CandidateTooSparse`).
- Real chain selection with actual snapshot: total weight M(1+B) > N → `ShouldSwitch` → **should adopt**.

The node disconnects from the peer serving the heavier canonical chain and never adopts it.

---

### Impact Explanation

This is a **High** chain-selection bug. When Peras is active and a peer's chain is beyond the forecast horizon, an honest node can be made to permanently disconnect from peers serving the canonical Peras-boosted chain. The node remains on a lighter, potentially non-canonical chain. Because the disconnect is recorded as `CandidateTooSparse` and the peer is not reconnected to for this candidate, the node's chain selection is durably wrong for the duration of the session. This matches the allowed impact: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Peras is an active protocol extension already integrated into the codebase (the `PerasWeightSnapshot` infrastructure, `addToPerasWeightSnapshot`, `prunePerasWeightSnapshot`, and `weightedSelectView` are all production code). The trigger requires:

1. Peras is active (non-empty weight snapshot in ChainSel).
2. A peer sends a header beyond the forecast horizon (a slot gap larger than the forecast window — explicitly documented as the trigger for this code path).
3. The peer's chain has fewer blocks but higher Peras-boosted total weight than the local chain.

Condition 2 is reachable by any unprivileged peer simply by serving a chain with a large slot gap. Condition 3 is the normal Peras scenario where certificates boost a shorter chain above a longer one. The developers themselves flagged this with a `TODO` comment referencing issue #64, confirming awareness of the incomplete Peras integration at this call site.

---

### Recommendation

Pass the live `PerasWeightSnapshot` from the ChainDB (or from the `ChainSyncClientHandleCollection`) into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`, so that the "should we keep this peer?" decision uses the same weight accounting as the actual chain selection. This mirrors the Morpho fix: replace the stale raw-storage value with the interest-accrued value (`_morpho.expectedSupplyAssets`) so both sides of the comparison are computed consistently.

Alternatively, as the TODO comment suggests, remove `checkPreferTheirsOverOurs` entirely (issue #64) if the Genesis/LoE machinery already provides a sufficient guard against waiting forever on non-preferred candidates.
