### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance contains a stub `validatePerasCert` implementation that unconditionally returns `Right` for every certificate, performing no cryptographic or semantic validation whatsoever. This stub is wired directly into the production certificate ingest path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can send a crafted `PerasCert` message over the ObjectDiffusion mini-protocol; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection that applies a weight boost of 15 to an arbitrary block, potentially causing the node to switch to a shorter adversarial fork.

---

### Finding Description

**Root cause — stub always returns `Right`:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for accepting inbound certificates. The only concrete instance in the codebase is the universal one:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee membership check, no round-number bounds check, no boosted-block existence check — every certificate is unconditionally accepted and assigned the full `perasWeight` boost (currently `PerasWeight 15`). [2](#0-1) 

**Production ingest path wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [3](#0-2) 

`processCerts` calls `validateCert` on each inbound certificate from a peer. Since the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addPerasCertAsync`: [4](#0-3) 

**Chain selection consequence:**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event. `chainSelSync` processes it: if the boosted block is in the `VolatileDB`, it immediately calls `chainSelectionForBlock` for that block: [5](#0-4) 

Chain selection uses `WeightedSelectView`, where `wsvTotalWeight = blockNo + weightBoost`. A boost of 15 means a fork that is up to 15 blocks shorter than the honest chain can be preferred: [6](#0-5) 

**Secondary: `validatePerasVote` also skips cryptographic verification:**

The vote stub only checks stake-distribution membership but performs no signature verification, allowing any peer to impersonate any registered voter and contribute stake toward a quorum: [7](#0-6) 

---

### Impact Explanation

**High — Chain selection bug enabling non-canonical chain preference.**

An unprivileged peer can craft a `PerasCert` that names any block in the local `VolatileDB` as the boosted block. Because `validatePerasCert` never rejects, the certificate is stored and the boosted block's chain gains `PerasWeight 15` in the `WeightedSelectView` comparison. With the default `perasWeight = 15`, a fork that is 15 blocks shorter than the honest chain becomes preferred, causing the node to roll back up to 15 blocks and switch to the adversarial fork. This directly violates the Peras chain-selection invariant that only legitimately certified blocks should receive a weight boost.

---

### Likelihood Explanation

Any peer connected via the ObjectDiffusion mini-protocol can send arbitrary `PerasCert` objects. No stake, no key material, and no prior relationship is required. The only constraint is that the boosted block's hash must already be present in the local `VolatileDB` (i.e., the attacker must have previously served a valid block to the victim node, which is a normal part of block diffusion). The attack is therefore reachable by any network peer in a private testnet or, once Peras is activated, on mainnet.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's aggregate signature against the committee's public keys and checks that the round number, boosted block, and quorum threshold all satisfy the Peras protocol rules before returning `Right`.
2. Similarly, replace the stub `validatePerasVote` with a real implementation that verifies the voter's individual signature.
3. Until real validation is implemented, gate the entire Peras certificate/vote ingest path behind a feature flag that is disabled by default, so the stub cannot be reached from the network.
4. Add property tests that confirm `validatePerasCert` rejects certificates with invalid signatures, out-of-range round numbers, and non-existent boosted blocks.

---

### Proof of Concept

On a private two-node testnet with Peras enabled:

1. Connect an adversarial peer to the victim node via the ObjectDiffusion mini-protocol.
2. Serve the victim a valid block `B_adv` on a fork that is 15 blocks shorter than the honest chain (so `B_adv` is in the victim's `VolatileDB`).
3. Send a crafted `PerasCert` message with `pcCertBoostedBlock = blockPoint B_adv` and any `pcCertRound`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally. [8](#0-7) 
5. The cert is forwarded to `addPerasCertAsync`, which enqueues `ChainSelAddPerasCert`.
6. `chainSelSync` finds `B_adv` in the `VolatileDB` and calls `chainSelectionForBlock` for it. [5](#0-4) 
7. `WeightedSelectView` now gives the adversarial fork `wsvTotalWeight = blockNo(B_adv) + 15`, which exceeds the honest chain's `wsvTotalWeight = blockNo(honest_tip)` when the honest chain is at most 15 blocks ahead. [9](#0-8) 
8. The victim node rolls back to `B_adv`'s fork, accepting the adversarial chain as canonical.
