### Title
Peras Vote Signature and Eligibility Verification Bypass Allows Unprivileged Peer to Forge Quorum Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` default instance's `validatePerasVote` implementation performs no cryptographic signature verification and no committee eligibility check. Any unprivileged peer can craft `PerasVote` messages claiming to be from any pool ID present in the stake distribution. These votes pass validation, are counted toward quorum, and can cause the node to forge a Peras certificate for an adversarially-chosen block, boosting its chain weight and influencing chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasVote` as the gate that must be passed before a received vote is stored in the `PerasVoteDB` and counted toward quorum. The universal default instance (applied to all `StandardHash blk`) implements this gate as a pure stake-distribution lookup with no cryptographic checks:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The check is: "does `pvVoteVoterId` appear in the stake distribution?" — nothing more. The following are entirely absent:

1. **Cryptographic signature verification** — the `pvVoteBlock` / `pvVoteRound` payload is never verified against the claimed voter's key.
2. **Committee eligibility** — no VRF proof is checked for non-persistent members; no persistent-member seat-index range check is performed.
3. **One-vote-per-voter-per-round enforcement at validation time** — the deduplication in `implAddVote` is keyed on `PerasVoteId = (roundNo, voterId)`, so a single voter ID can only contribute once per round, but the *signature* binding that voter ID to the actual key-holder is never verified. [2](#0-1) 

The same stub pattern applies to `validatePerasCert`, which unconditionally returns `Right` for any certificate:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [3](#0-2) 

This stub is the live implementation used by both production vote-pool writers:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) [5](#0-4) 

`processVotes` — the inbound handler for votes arriving over the network — calls this validator for every vote in a batch before storing them: [6](#0-5) 

Once a vote passes `validatePerasVote`, it is inserted into `PerasVoteDB` via `implAddVote`, which immediately feeds it into `updatePerasRoundVoteStates` and triggers certificate forging when quorum is reached: [7](#0-6) 

The quorum check in `votesReachQuorum` simply sums `vpvVoteStake` values — the stake that was assigned during the unchecked `validatePerasVote` call: [8](#0-7) 

The `PerasVoteId` deduplication set (`pvdsVoteIds`) prevents the *same* `(roundNo, voterId)` pair from being counted twice, but it does not prevent an attacker from sending one forged vote per pool ID in the stake distribution — each with a different `pvVoteVoterId` — all of which pass the stub validator. [9](#0-8) 

The well-specified committee implementations (`WFALS`, `EveryoneVotes`) do perform full signature and VRF verification in `implVerifyVote` / `implVerifyCert`, but these are **not wired into the production vote-processing pipeline** — the pipeline uses the `BlockSupportsPeras` stub directly. [10](#0-9) 

---

### Impact Explanation

An attacker who knows the current stake distribution (publicly available on-chain) can:

1. Enumerate all pool IDs present in `PerasVoteStakeDistr`.
2. For each pool ID, craft a `PerasVote` with an arbitrary `pvVoteBlock` (the block they wish to boost) and that pool's `pvVoteVoterId`. No valid key material is required.
3. Send these votes to a target node via the ObjectDiffusion miniprotocol.
4. Each vote passes `validatePerasVote` (stake lookup succeeds), is stored, and its stake is added to the tally.
5. Once the accumulated stake exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for the attacker's chosen block.
6. This certificate carries `perasWeight` boost, directly influencing chain selection in favour of the adversarially-chosen block.

This constitutes a **bypass of Peras vote signature and eligibility verification** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical" tier: *bypass of certificate/vote verification checks that enables unauthorized vote or certificate acceptance*.

---

### Likelihood Explanation

The attack requires only:
- Knowledge of the current stake distribution (public).
- The ability to connect to a target node and send ObjectDiffusion messages (any network peer).
- No cryptographic keys, no stake, no privileged access.

The vulnerable code path is active in the current codebase for all block types via the universal `instance StandardHash blk => BlockSupportsPeras blk`. The TODO comment and linked issue (`tweag/cardano-peras#120`) confirm the stub is intentionally incomplete but is nonetheless the live implementation.

---

### Recommendation

1. **Wire the committee-level vote verification** (`implVerifyVote` from `WFALS` or `EveryoneVotes`) into `validatePerasVote` before any vote is accepted into `PerasVoteDB`. The committee implementations already perform full signature and VRF verification.
2. **Wire `implVerifyCert`** into `validatePerasCert` so that certificates received over the network or extracted from blocks are fully verified before being stored or used for chain selection.
3. Until the full committee selection context is available, reject all inbound votes rather than accepting them with a stub validator — a safe default is `Left PerasValidationErr` for all votes, not `Right`.
4. Track issue `tweag/cardano-peras#120` as a security-critical blocker, not merely a correctness TODO.

---

### Proof of Concept

```
1. Attacker queries the current PerasVoteStakeDistr (public ledger state).
2. For target round R and adversarially-chosen block B, attacker constructs:
     votes = [ PerasVote { pvVoteRound = R
                         , pvVoteBlock = B
                         , pvVoteVoterId = poolId }
             | poolId <- Map.keys stakeDistr ]
3. Attacker sends `votes` to the victim node via the ObjectDiffusion
   miniprotocol (no authentication required to connect).
4. processVotes calls validatePerasVote for each vote:
     validatePerasVote _params stakeDistr vote
       | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
   Each vote passes because poolId ∈ stakeDistr.
5. implAddVote stores each vote; updatePerasRoundVoteStates accumulates stake.
6. Once totalStake >= quorumThreshold + safetyMargin, forgePerasCert fires,
   producing ValidatedPerasCert { vpcCert = PerasCert R B, vpcCertBoost = W }.
7. Block B now carries weight W in chain selection, regardless of whether
   any legitimate committee member ever voted for it.
```

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
