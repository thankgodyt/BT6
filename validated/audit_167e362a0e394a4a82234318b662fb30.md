### Title
Any Caller Can Redirect Victim's Refund BTC to an Arbitrary Address via `request_refund` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is a public, permissionless function. When a deposit's `deposit_msg.refund_address` is `None`, any caller may submit a refund request for **any** deposit UTXO and supply an arbitrary BTC `refund_address`. There is no check that the caller is the original depositor or has any relationship to the deposit. After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless, so the attacker can complete the redirect without further authorization. The only protection is that DAO/Operator can reject the request during the timelock window; if they are absent or slow, the victim's BTC is permanently redirected to the attacker.

---

### Finding Description

`request_refund` accepts a caller-supplied `refund_address` and stores it verbatim in the `RefundRequest`: [1](#0-0) 

The only guard on `refund_address` is inside `request_refund_callback`: if `deposit_msg.refund_address` is `Some`, the supplied value must match it. When it is `None`, **any** BTC address is accepted without restriction: [2](#0-1) 

The stored `refund_address` is then used verbatim when building the refund output: [3](#0-2) 

`execute_refund` is equally permissionless — any account may call it after the timelock: [4](#0-3) 

The timelock applied when `deposit_msg.refund_address` is `None` is the *longer* `unsafe_refund_timelock_sec`, explicitly designed to give DAO/Operator time to reject: [5](#0-4) 

If the DAO/Operator does not reject within that window, `execute_refund` proceeds and the BTC is sent to the attacker-controlled address.

---

### Impact Explanation

A victim deposits BTC with `deposit_msg.refund_address = None`. If the deposit is never finalized (wrong `recipient_id`, relayer failure, etc.), an attacker who observes the on-chain BTC transaction can:

1. Call `request_refund` with the victim's `tx_bytes`/`vout`/`proof` and their own BTC address as `refund_address`.
2. Wait for `unsafe_refund_timelock_sec`.
3. Call `execute_refund` — the MPC pipeline signs a transaction paying the attacker's address.

The victim's BTC is permanently lost. This maps to **Critical — significant loss or theft of user funds**.

---

### Likelihood Explanation

The attack is fully permissionless and requires only:
- Knowledge of the victim's unfinalized deposit transaction (publicly visible on-chain).
- Payment of `required_balance_for_request_refund()` (a small NEAR storage deposit).
- DAO/Operator failing to reject within `unsafe_refund_timelock_sec`.

The last condition is the only barrier. Any period of DAO/Operator inactivity (maintenance, key rotation, monitoring gap) opens the window. The attack is repeatable for every unfinalized deposit with `refund_address: None`. Likelihood is **Medium**.

---

### Recommendation

1. **Bind `refund_address` to the depositor**: when `deposit_msg.refund_address` is `None`, require `env::predecessor_account_id() == deposit_msg.recipient_id` (or an account explicitly authorized by the recipient) before accepting a caller-supplied `refund_address`.
2. **Alternatively**, require `deposit_msg.refund_address` to always be pre-set in the deposit message, removing the ability for any third party to supply it at refund time.
3. Document clearly that any deposit with `refund_address: None` relies on DAO/Operator liveness for fund safety.

---

### Proof of Concept

```
# 1. Alice deposits BTC; deposit_msg.refund_address = None; deposit never finalized.
# 2. Attacker observes Alice's tx on-chain (tx_bytes, vout, block proof).

# 3. Attacker calls (with attached NEAR storage deposit):
request_refund(
    deposit_msg  = Alice's original deposit_msg,   # refund_address: None
    refund_address = "attacker_btc_address",        # arbitrary — no check
    tx_bytes     = Alice's raw BTC tx,
    vout         = Alice's output index,
    proof        = valid SPV proof,
    gas_fee      = None,
)
# → request_refund_callback stores RefundRequest { refund_address: "attacker_btc_address", ... }
# → unsafe_refund_timelock_sec starts

# 4. DAO/Operator does not reject within the timelock.

# 5. Attacker calls:
execute_refund(utxo_storage_key = Alice's UTXO key, chain_specific_data = None)
# → finalize_refund_with_psbt builds PSBT paying "attacker_btc_address"
# → MPC signs; attacker broadcasts; Alice's BTC is gone.
```

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
