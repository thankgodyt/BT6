### Title
Stub `validatePerasCert` Accepts Any Peer-Supplied Certificate, Enabling Monotonic `pcdsLatestCertSeen` Advancement to Grief Peras Voting — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate. Any unprivileged peer can inject a certificate for an arbitrarily far-future round via the ObjectDiffusion miniprotocol. Because `pcdsLatestCertSeen` in `PerasCertDB` advances monotonically (only updated when the new cert's round exceeds the current maximum), this permanently advances the "latest cert seen" to the adversary-chosen round. The Peras voting rules VR-1A and VR-2A both depend on `latestCertSeen`; both fail for all current rounds once the state is poisoned, silencing the node's Peras voting participation for an extended period.

---

### Finding Description

**Root cause — stub certificate validation in production code**

In `BlockSupportsPeras.hs`, the catch-all `BlockSupportsPeras` instance (used for all block types, including production Cardano blocks) implements `validatePerasCert` as a no-op stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called from `processCerts` in the inbound certificate handler for the ObjectDiffusion miniprotocol:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` filters out already-known round numbers, then calls `validateCert` on each remaining certificate. Because the stub always returns `Right`, every peer-supplied certificate passes and is timestamped and added to the DB:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Monotonically-advancing `pcdsLatestCertSeen`**

In `implAddCert` (`PerasCertDB/Impl.hs`), every accepted certificate updates `pcdsLatestCertSeen` if its round number exceeds the current maximum:

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [4](#0-3) 

This is a strictly monotone ratchet: once advanced to round N, it never decreases. The API documentation explicitly acknowledges the security sensitivity of this field:

> "This field impacts voting directly because having seen a certificate is a precondition for voting in any round except for the very first one (at origin)." [5](#0-4) 

**Voting rules broken by poisoned state**

The Peras voting rules consume `latestCertSeen` (sourced from `pcdsLatestCertSeen`):

- **VR-1A** (happy path): requires `currRoundNo == getPerasCertRound(latestCertSeen) + 1`
- **VR-2A** (cooldown exit): requires `getPerasCertRound(latestCertSeen) + R ≤ currRoundNo` [6](#0-5) [7](#0-6) 

If an adversary injects a certificate for round N = 1,000,000 while the node is in round R = 5:
- VR-1A: `5 == 1,000,001` → **False**
- VR-2A: `1,000,000 + R ≤ 5` → **False**

Both voting paths fail. The node cannot vote for approximately N − R rounds.

**Analog to the external report**

| External report | Ouroboros Consensus |
|---|---|
| `rewardEpochs[token][len-1] < _epoch` — strict monotone epoch check | `pcdsLatestCertSeen` — strict monotone round ratchet |
| Attacker calls `addRewardToEpoch()` with a future epoch | Attacker sends a `PerasCert` with a far-future `pcCertRound` |
| Legitimate pending tx reverts (`Cannot backdate to this epoch`) | Node's VR-1A/VR-2A checks fail for all current rounds |
| Griefs reward distribution | Griefs Peras voting participation |

---

### Impact Explanation

This is a **bypass of Peras certificate validation** (unauthorized certificate acceptance) that permanently corrupts the `pcdsLatestCertSeen` monotone state. The corrupted state prevents the node from satisfying either Peras voting precondition (VR-1A or VR-2A), effectively silencing the node's vote for an attacker-controlled number of rounds. If applied to a sufficient fraction of the committee, this weakens or eliminates Peras finality guarantees for those rounds.

---

### Likelihood Explanation

Any peer reachable via the ObjectDiffusion miniprotocol can trigger this with a single message. No stake, keys, or special privileges are required. The attack is cheap (one certificate message) and the effect is long-lasting (proportional to the chosen future round number).

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the ObjectDiffusion path is enabled in production. At minimum, reject certificates whose round number exceeds `currRound + maxLookahead` for some protocol-defined bound.
2. **Add a round-number bound check** in `implAddCert` or `processCerts` to reject certificates with round numbers implausibly far in the future, independent of the cryptographic validation.
3. **Track and close** the referenced issues: `https://github.com/tweag/cardano-peras/issues/120` (validation) and `https://github.com/tweag/cardano-peras/issues/73` (degenerate instance).

---

### Proof of Concept

```
1. Connect to a Peras-enabled node via the ObjectDiffusion miniprotocol
   for Peras certificates.

2. Send a PerasCert message:
     pcCertRound       = PerasRoundNo 1_000_000   (far future)
     pcCertBoostedBlock = any valid-looking Point

3. processCerts calls validatePerasCert mkPerasParams cert
   → returns Right (stub, no checks performed)

4. implAddCert updates pcdsLatestCertSeen to round 1,000,000
   (since 1,000,000 > current latest round)

5. Node is in round R = 5 and tries to vote:
   VR-1A check 1: currRoundNo == latestCertSeenRound + 1
                  5 == 1,000,001  →  False
   VR-2A:         latestCertSeenRound + R <= currRoundNo
                  1,000,000 + 5 <= 5  →  False

6. Node cannot vote for ~999,995 rounds.
   Repeat with a fresh round number to extend the effect indefinitely.
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

    VR1A := vr1a1 :/\: vr1a2

    -- The latest certificate seen is from the previous round

    -- of its round
    vr1a2 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its arrival time
        NotOrigin cert ->

        -- We have never seen a certificate ==> vacuously true
