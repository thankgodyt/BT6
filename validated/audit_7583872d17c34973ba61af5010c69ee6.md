Audit Report

## Title
Non-Atomic `burn.and(mint)` with No Failure Callback in `swap_migrated_token` Causes Permanent Loss of User Funds or Unauthorized Minting — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` schedules `burn` and `mint` as parallel, independent NEAR receipts via `Promise::and()`. Because `ft_on_transfer` immediately returns `U128(0)` (consuming the user's old tokens with no NEP-141 refund path) and `.detach()`es the combined promise (no failure callback), a `mint` failure after a successful `burn` permanently destroys the user's old tokens with no new tokens issued. Symmetrically, a `burn` failure after a successful `mint` produces unauthorized token inflation.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `swap_migrated_token` (lines 2738–2753) constructs two cross-contract calls and combines them with `burn.and(mint)`. In NEAR Protocol, `Promise::and()` dispatches both as independent action receipts that execute in parallel; neither is rolled back if the other fails. The function is invoked from `ft_on_transfer` (lines 275–279) with `.detach()` — discarding the promise result — and the handler returns `U128(0)`, which under NEP-141 signals that all transferred tokens are consumed (no refund). Once `ft_on_transfer` returns, the old tokens are irrecoverably held by the bridge contract. If the `mint` receipt subsequently panics (e.g., due to missing storage deposit on the new token contract, gas exhaustion, or a bug in the new token's `mint` implementation), the `burn` receipt has already been dispatched and will succeed independently, permanently destroying the user's old tokens with no recovery path. No `#[private]` callback exists to detect the failure or issue a refund.

## Impact Explanation
- **Primary (Critical — permanent loss of bridged funds):** `mint` fails after `burn` succeeds → user's old tokens are permanently destroyed, zero new tokens received. Direct, irreversible loss of bridged funds.
- **Secondary (Critical — unauthorized minting):** `burn` fails while `mint` succeeds → user receives new tokens without surrendering old ones, inflating the new token supply and breaking the 1:1 migration invariant.

Both outcomes match the Critical allowed impact scope: permanent loss of bridged funds and unauthorized minting.

## Likelihood Explanation
The entry point (`old_token.ft_transfer_call → ft_on_transfer` with `SwapMigratedToken`) requires no privilege — any token holder can trigger it. Realistic, non-adversarial failure conditions for `mint` include: (1) missing storage deposit — NEP-141 tokens require prior `storage_deposit` registration; if the bridge has not pre-registered on the new token contract, `mint` panics with a storage error, a common operational oversight during migrations; (2) gas exhaustion — no explicit gas is attached via `.with_static_gas()`, so if the user's `ft_transfer_call` provides insufficient prepaid gas, the `mint` receipt may fail while the `burn` receipt succeeds; (3) any panic in the new token's `mint` implementation. These are realistic conditions, not adversarial constructions.

## Recommendation
Replace the parallel `burn.and(mint)` pattern with a sequential, callback-guarded chain:
1. Call `burn` first with explicit gas (`.with_static_gas(BURN_TOKEN_GAS)`).
2. In a `#[private]` callback, verify `burn` succeeded (check `PromiseResult`), then call `mint` with explicit gas.
3. In a second `#[private]` callback, verify `mint` succeeded; if it failed, re-mint the old tokens back to the user or store a claimable refund entry.

Do **not** `.detach()` the promise chain. Return the promise from `ft_on_transfer` instead of `U128(0)` so the NEP-141 mechanism can participate in error handling, or manage refunds explicitly in the callback.

## Proof of Concept
1. Admin registers migration: `migrated_tokens[old_token] = new_token`.
2. Bridge contract has **not** called `storage_deposit` on `new_token` for itself.
3. User calls `old_token.ft_transfer_call(bridge, amount, "\"SwapMigratedToken\"")`.
4. `ft_on_transfer` returns `U128(0)` — old tokens are consumed by the bridge; NEP-141 will not refund.
5. `swap_migrated_token` dispatches `burn.and(mint).detach()`.
6. `burn` receipt executes: bridge's `old_token` balance is destroyed. ✓
7. `mint` receipt executes: `new_token` panics with "account not registered" (no storage deposit). ✗
8. No callback exists to detect the failure or issue a refund.
9. User has permanently lost `amount` of `old_token` and received 0 `new_token`.

To reproduce in a local integration test: deploy `old_token` and `new_token` NEP-141 contracts, register the migration on the bridge, skip `storage_deposit` on `new_token` for the bridge account, then execute the `ft_transfer_call` sequence and assert that the user's `old_token` balance decreased and `new_token` balance remained zero.
