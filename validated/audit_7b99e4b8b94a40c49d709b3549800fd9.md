### Title
Permissionless `request_refund` Allows Any Caller to Register an Attacker-Controlled BTC Refund Address, Locking or Redirecting User Funds - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is callable by any NEAR account. When the original `DepositMsg` was created with `refund_address: None`, the function accepts any caller-supplied `refund_address` with no ownership check. Because only one refund request can exist per UTXO, the first caller wins the slot. An attacker who races the legitimate user can register their own BTC address as the refund destination, permanently blocking the user from submitting their own request and — if the DAO/Operator fails to reject within `unsafe_refund_timelock_sec` — redirecting the user's BTC to the attacker.

---

### Finding Description

`request_refund` is declared in a `#[trusted_relayer]` impl block but carries no `#[trusted_relayer]` attribute on the function itself, unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` in the same block. Integration tests confirm that ordinary accounts (e.g. `"alice"`) call it successfully. [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` the branch is skipped entirely, so the caller's arbitrary `refund_address` is accepted without restriction.

In `request_refund_callback` a duplicate-request guard prevents a second submission for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

The stored `refund_address` is later used verbatim when building the refund output: [4](#0-3) 

The `DepositMsg` is fully public — it is emitted as a `LogDepositAddress` event by `get_user_deposit_address`, so any observer can reconstruct it: [5](#0-4) 

---

### Impact Explanation

**Medium (with a conditional Critical path).**

An attacker who races the legitimate user registers a malicious `refund_address`. The legitimate user's subsequent `request_refund` call is rejected with "Refund request already exists for this UTXO", permanently blocking them from the refund path without DAO/Operator intervention. This is an attacker-triggered stuck state requiring operator intervention — a Medium bridge impact.

If the DAO/Operator fails to call `reject_refund` before `unsafe_refund_timelock_sec` elapses, `execute_refund` builds and MPC-signs a Bitcoin transaction paying the attacker's address. The user's deposited BTC is permanently lost — a Critical bridge impact (significant loss of user funds). [6](#0-5) 

---

### Likelihood Explanation

- The `DepositMsg` is emitted on-chain, so the attacker has all inputs needed to construct a valid `request_refund` call.
- The BTC transaction is public on the Bitcoin network; the attacker can monitor for unfinalized deposits.
- No privileged role is required; any NEAR account can call `request_refund`.
- The attacker only needs to submit before the legitimate user, not race a specific transaction.
- The anti-spam NEAR deposit is a minor cost barrier, not a meaningful deterrent for a targeted attack on a large BTC deposit.
- The `unsafe_refund_timelock_sec` window is the only mitigation, and it depends entirely on DAO/Operator vigilance.

---

### Recommendation

Bind the refund address to the caller's identity when `deposit_msg.refund_address` is `None`. Two options:

1. **Require `deposit_msg.refund_address` to always be set.** Reject `request_refund` calls where `deposit_msg.refund_address` is `None`. Users who want a refund must have pre-authorized their BTC address in the original `DepositMsg`.

2. **Record the NEAR caller and enforce it at execute time.** Store `env::predecessor_account_id()` in `RefundRequest` when `deposit_msg.refund_address` is `None`, and require the same account to call `execute_refund` (or at minimum require DAO/Operator to approve the address before execution).

Option 1 is simpler and eliminates the attack surface entirely.

---

### Proof of Concept

1. Alice deposits BTC using a `DepositMsg` with `refund_address: None`. The `LogDepositAddress` event reveals the full `DepositMsg`.
2. The relayer never calls `verify_deposit` (relayer is down or Alice changed her mind).
3. Attacker Bob observes the on-chain event, reconstructs Alice's `DepositMsg`, and calls:
   ```
   request_refund(
       deposit_msg = Alice's DepositMsg (refund_address: None),
       refund_address = "bc1q<BOB_ADDRESS>",
       tx_bytes = <Alice's BTC tx>,
       vout = 0,
       proof = <valid Merkle proof>,
       gas_fee = None
   )
   ```
4. `internal_request_refund` skips the `refund_address` check because `deposit_msg.refund_address` is `None`. The request is stored with Bob's address.
5. Alice calls `request_refund` — it fails: "Refund request already exists for this UTXO".
6. If DAO/Operator does not call `reject_refund` before `unsafe_refund_timelock_sec` elapses, anyone calls `execute_refund`, the bridge MPC-signs a transaction paying Bob's address, and Alice's BTC is gone. [7](#0-6) [8](#0-7)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
