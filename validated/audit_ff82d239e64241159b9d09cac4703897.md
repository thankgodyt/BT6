### Title
Unpermissioned `log_metadata` on Solana Allows Any Attacker to Register Arbitrary SPL Tokens on NEAR — (`solana/programs/bridge_token_factory/src/instructions/user/log_metadata.rs`)

---

### Summary

The Solana `log_metadata` instruction has no caller-authorization check. Any account can invoke it with any SPL mint they control. Because the Wormhole VAA is always emitted with the bridge's own config PDA as the emitter — the same address registered as the Solana factory on NEAR — NEAR's `deploy_token_callback` unconditionally accepts the resulting VAA and deploys a wrapped token for the attacker-chosen mint. Since the attacker retains the mint authority, they can subsequently mint unlimited SPL tokens and bridge them to NEAR, receiving legitimately-deployed wrapped tokens backed by worthless self-minted supply.

---

### Finding Description

**Step 1 — No authorization on Solana `log_metadata`**

The `LogMetadata` account struct imposes exactly one constraint on the submitted mint:

```rust
#[account(
    constraint = !mint.mint_authority.contains(authority.key),
    mint::token_program = token_program,
)]
pub mint: Box<InterfaceAccount<'info, Mint>>,
``` [1](#0-0) 

This only rejects mints whose mint authority is the bridge's authority PDA (i.e., already-bridged tokens). Any other mint — including one freshly created by an attacker with themselves as mint authority — passes. There is no signer role check, no pause gate, and no registration requirement on the caller.

**Step 2 — Wormhole VAA emitter is always the bridge config PDA**

`post_message` is called with the bridge's config PDA as the emitter, signed via PDA seeds:

```rust
emitter: self.config.to_account_info(),
...
&[&[CONFIG_SEED, &[self.config.bumps.config]]], // emitter
``` [2](#0-1) 

This means every `log_metadata` call — regardless of who calls it or which mint is submitted — produces a VAA whose `emitter_address` is the bridge's config PDA.

**Step 3 — Payload encodes the attacker's mint as the token address**

```rust
let payload = LogMetadataPayload {
    token: self.mint.key(),   // attacker's arbitrary mint
    name: ...,
    symbol: ...,
    decimals: self.mint.decimals,
}.serialize_for_near(())?;
self.common.post_message(payload)?;
``` [3](#0-2) 

**Step 4 — NEAR prover parses the VAA and sets `emitter_address` from the VAA header**

```rust
emitter_address: OmniAddress::new_from_slice(chain_kind, &self.emitter_address)?,
``` [4](#0-3) 

`self.emitter_address` is the VAA's header field — the bridge config PDA — not anything from the payload.

**Step 5 — NEAR `deploy_token_callback` validates emitter against registered factories**

```rust
let chain = metadata.emitter_address.get_chain();
require!(
    self.factories.get(&chain) == Some(metadata.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
``` [5](#0-4) 

Because the emitter is the bridge config PDA — which is the registered Solana factory — this check passes unconditionally for any VAA produced by the Solana bridge program, regardless of which mint triggered it.

**Step 6 — NEAR deploys a wrapped token for the attacker's mint**

`deploy_token_internal` is called with the attacker's mint address as `token_address`, deploying a new NEP-141 wrapped token on NEAR. [6](#0-5)

### Impact Explanation

Once the wrapped token is deployed on NEAR, the attacker — who retains mint authority over the underlying SPL mint — can:

1. Mint an arbitrary quantity of SPL tokens on Solana (zero cost beyond rent).
2. Call `init_transfer` on Solana to lock those tokens in the bridge vault.
3. NEAR finalizes the transfer and mints an equivalent quantity of the newly-deployed wrapped token.

The wrapped token is indistinguishable from a legitimately-registered bridged token. Any user or protocol on NEAR that accepts it as valuable is exposed to unbounded inflation by the attacker. This constitutes unauthorized minting of bridged tokens and an authorization bypass of the token-registration flow that is supposed to be controlled by the bridge protocol.

---

### Likelihood Explanation

The attack requires no special privileges, no admin compromise, and no Wormhole guardian compromise. It is executable by any Solana account that can pay transaction fees and rent for a new mint. The only precondition is that the Solana factory (bridge config PDA) is registered on NEAR, which is a normal deployment requirement. The path is fully reproducible on a local testnet with unmodified code.

---

### Recommendation

Add an explicit authorization check to the `log_metadata` instruction. Options include:

1. **Allowlist check**: Maintain an on-chain set of approved mints (or mint authorities) and require the submitted mint to be in it.
2. **Admin-only gate**: Require the caller to be the bridge admin or a designated metadata-admin role (the `metadata_admin` field already exists in `Config`).
3. **Pause gate**: At minimum, gate `log_metadata` behind the existing pause mechanism so the protocol can halt abuse.

The `metadata_admin` field in `Config` suggests the intent was to restrict this operation; the enforcement is simply missing from the instruction.
