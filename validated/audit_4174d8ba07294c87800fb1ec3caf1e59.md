### Title
Unchecked `burn().detach()` in `safe_mint_callback` Enables nBTC Supply Inflation on Burn Failure — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary
When `safe_mint` returns `U128(0)` (indicating the recipient account does not exist or the receiver rejected the transfer), `safe_mint_callback` removes the UTXO from `verified_deposit_utxo` and then fires a `burn()` cross-contract call with `.detach()` — no callback, no success check. If that burn fails, the UTXO is permanently removed from the verified set while the minted tokens remain in `bridge_id`, allowing the same UTXO to be re-submitted via the public `safe_verify_deposit` entry point, minting a second batch of nBTC against the same BTC deposit.

---

### Finding Description

In `safe_mint_callback`, when `is_success` is `false`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 439–455
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);   // (1) UTXO removed

ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(
        env::current_account_id(),
        mint_amount,
        relayer_account_id,
        U128(0),
    )
    .detach();                                        // (2) fire-and-forget, no callback

Promise::new(env::signer_account_id())
    .transfer(self.required_balance_for_safe_deposit())
    .detach();                                        // (3) also unchecked
```

Step (1) is committed to state before step (2) executes. If the `burn` receipt fails (e.g., `bridge_id` balance is insufficient due to a concurrent operation, gas exhaustion in the nbtc contract, or any panic inside `internal_withdraw`), the UTXO key is gone from `verified_deposit_utxo` but the minted tokens remain in `bridge_id`.

Because `verified_deposit_utxo` no longer contains the key, the public `safe_verify_deposit` path will pass the duplicate-check at:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 399–403
require!(
    self.data_mut()
        .verified_deposit_utxo
        .insert(pending_utxo_info.utxo_storage_key.clone()),
    "Already deposit utxo"
);
```

A second `safe_verify_deposit` call for the same BTC transaction will succeed, triggering a second `safe_mint` and adding the UTXO to `utxos`. The result is two batches of nBTC minted against one BTC deposit: one batch stuck in `bridge_id` (from the failed burn) and one batch delivered to the recipient.

The `mint` function in the nbtc contract also uses `.detach()` for post-actions:

```rust
// contracts/nbtc/src/lib.rs  lines 143–147
Self::ext(env::current_account_id())
    .handle_post_actions(mint_account_id, post_actions)
    .detach();
```

And `handle_post_action` itself detaches the `ft_on_transfer` + `ft_resolve_transfer` chain:

```rust
// contracts/nbtc/src/lib.rs  lines 408–416
ext_ft_receiver::ext(receiver_id.clone())
    ...
    .ft_on_transfer(...)
    .then(ext_ft_resolver::ext(...).ft_resolve_transfer(...))
    .detach();
```

These secondary detached calls can silently fail, leaving tokens in an unresolved state.

---

### Impact Explanation

If the `burn().detach()` call fails, the nBTC total supply exceeds the BTC held by the bridge: `bridge_id` holds un-burned tokens and the re-submitted UTXO mints a fresh batch. This is unauthorized minting / supply inflation above the backed amount — a direct violation of the bridge's 1:1 backing invariant. The extra tokens in `bridge_id` are not immediately accessible to the attacker, but the protocol's collateralization ratio is permanently broken for that deposit amount.

---

### Likelihood Explanation

The `burn` call fails only if `bridge_id`'s nBTC balance drops below `mint_amount` between the `ft_resolve_transfer` receipt (which returns tokens to `bridge_id`) and the `burn` receipt. In NEAR's asynchronous receipt model, other receipts can execute in between. A concurrent `safe_mint_callback` for a different UTXO that also calls `burn` from `bridge_id` could race and drain the balance. While this requires concurrent activity, the public `safe_verify_deposit` entry point means any user can submit deposits, making concurrent execution realistic on a live bridge. Likelihood is **low-to-medium**.

---

### Recommendation

Replace the fire-and-forget `burn().detach()` with a chained callback that checks `is_promise_success()`. If the burn fails, re-insert the UTXO key into `verified_deposit_utxo` to prevent re-submission, and record the un-burned amount in `lost_found` or a dedicated recovery map for operator intervention. This mirrors the pattern already used correctly in `transfer_nbtc_callback`:

```rust
// contracts/satoshi-bridge/src/token_transfer.rs  lines 54–74
pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
    let promise_success = is_promise_success();
    if !promise_success {
        self.data_mut().lost_found.entry(...).or_insert(amount.0);
    }
    promise_success
}
```

Apply the same pattern to the burn path in `safe_mint_callback`: chain a `burn_callback` that, on failure, re-inserts the UTXO into `verified_deposit_utxo` and logs the stuck tokens.

---

### Proof of Concept

1. Attacker controls a NEAR contract `evil.near` that implements `ft_on_transfer` and always returns the full `amount` (rejecting the transfer).
2. Attacker sends BTC to a deposit address derived from `recipient_id = evil.near`.
3. Attacker calls `safe_verify_deposit` with `msg` pointing to `evil.near`.
4. Bridge calls `safe_mint(evil.near, amount, Some(msg))` on nbtc. `evil.near::ft_on_transfer` returns `amount`, so `ft_resolve_transfer` returns tokens to `bridge_id`. `safe_mint` resolves to `U128(0)`.
5. `safe_mint_callback` fires: `verified_deposit_utxo.remove(utxo_key)` commits; `burn(...).detach()` is scheduled.
6. Attacker (or a concurrent transaction) causes `bridge_id`'s nbtc balance to be below `amount` before the burn receipt executes (e.g., via a racing concurrent `safe_mint_callback` for another UTXO). The burn receipt panics; tokens remain in `bridge_id`.
7. Attacker calls `safe_verify_deposit` again with the same BTC transaction. `verified_deposit_utxo.insert(utxo_key)` succeeds (key was removed in step 5). A second `safe_mint` executes, minting `amount` nBTC to the attacker's account and adding the UTXO to `utxos`.
8. Result: `bridge_id` holds `amount` un-burned nBTC; attacker holds `amount` nBTC; only one BTC deposit exists on-chain. Total nBTC supply = 2× BTC deposit. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
