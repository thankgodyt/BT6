### Title
Peras Certificate Validation Bypass — `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. This function is the sole validation gate in the production certificate ingestion path (`processCerts`) for Peras certificates received from network peers. An unprivileged peer can inject arbitrary, structurally crafted `PerasCert` values that will be accepted, stored in the `ChainDB`/`PerasCertDB`, and applied as a chain-selection boost to any block the attacker names.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository (the "degenerate instance for all blks to get things to compile"). No era-specific override exists.

**Production ingestion path — `processCerts` calls this stub directly:**

`makePerasCertPoolWriterFromChainDB` wires `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this callback on every inbound certificate and only rejects a batch when `validateCert` returns `Left`. Because `validatePerasCert` always returns `Right`, the rejection branch is unreachable:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Accepted certificates are forwarded to `ChainDB.addPerasCertAsync`, which stores them and triggers chain-selection side-effects.

**Attacker-controlled entry path:**

```
Unprivileged peer
  → Peras cert diffusion mini-protocol
  → makePerasCertPoolWriterFromChainDB / makePerasCertPoolWriterFromCertDB
  → processCerts
  → validatePerasCert mkPerasParams cert   ← always Right
  → ChainDB.addPerasCertAsync              ← stored, boost applied
```

The `PerasCert` data type carries only a round number and a block `Point`:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [4](#0-3) 

Both fields are fully attacker-controlled. No signature, quorum proof, or committee membership check is performed before the certificate is accepted.

**Analog to the tbtc report:**

| tbtc | Ouroboros Consensus |
|---|---|
| `provideRedemptionSignature` accepts high-s ECDSA signatures that pass `ecrecover` but are rejected by Bitcoin | `validatePerasCert` accepts any certificate that passes the stub check (always `Right`) but carries no cryptographic proof |
| Missing s-value range check → signature appears valid to Ethereum, invalid to Bitcoin → redemption loop | Missing certificate validation → certificate appears valid to the consensus layer, carries no proof → unauthorized chain boost |
| Attacker-controlled `_s` parameter | Attacker-controlled `pcCertRound` + `pcCertBoostedBlock` |

### Impact Explanation

A peer with no stake or privileges can:

1. Craft a `PerasCert` naming any block `Point` and any `PerasRoundNo`.
2. Deliver it via the Peras certificate diffusion protocol.
3. The certificate is accepted, stored, and assigned `vpcCertBoost = perasWeight params`.
4. Chain selection applies this boost to the named block, potentially causing honest nodes to prefer a non-canonical or adversarially chosen chain over the honest chain.

This is a **bypass of certificate verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical" impact category: *Bypass of certificate checks that enables unauthorized certificate acceptance.*

### Likelihood Explanation

Exploitation requires only a network connection to a target node. No stake, no keys, no privileged access. The Peras certificate diffusion mini-protocol is an externally reachable endpoint. Any peer can send a `PerasCert` message. The stub validation guarantees acceptance.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS vote signature over `(electionId, candidate)` using the declared voter verification keys.
2. Confirms the declared voters form a quorum (total stake ≥ threshold) according to the current committee selection.
3. Verifies VRF eligibility proofs for non-persistent voters.
4. Rejects any certificate that fails any of these checks.

Until a full implementation is available, the stub should at minimum reject all certificates (`Left PerasValidationErr`) rather than accept all of them, so that the network cannot be used to inject unauthenticated boosts.

### Proof of Concept

```
1. Connect to a target node as a peer via the Peras cert diffusion protocol.
2. Construct a PerasCert with:
     pcCertRound      = <any round number, e.g. 1>
     pcCertBoostedBlock = <Point of any block on the network, e.g. the attacker's fork tip>
3. Send the certificate.
4. processCerts calls validatePerasCert mkPerasParams cert
   → always returns Right ValidatedPerasCert { vpcCertBoost = perasWeight params }
5. ChainDB.addPerasCertAsync stores the cert and applies the boost.
6. Chain selection now treats the attacker-named block as having a Peras boost,
   potentially causing the honest node to switch to the attacker's fork.
```
