Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Is Token-Blacklisted — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.finTransfer` unconditionally pushes native ERC20 tokens (e.g., USDC) to `payload.recipient` via `safeTransfer`. If the recipient is on the USDC (or any token with a transfer restriction) blocklist, every finalization attempt reverts. Because the MPC signature commits to the exact recipient and no public cancel or redirect mechanism exists on the NEAR side, tokens burned or locked on NEAR during `init_transfer_internal` are permanently unrecoverable.

## Finding Description

**EVM side — push-only delivery:**

In `finTransfer`, the nonce is marked used at line 287, then token delivery is attempted. For native ERC20 tokens (those not registered as bridge tokens, custom minters, or ERC1155), the `else` branch executes:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
// ...
IERC20(payload.tokenAddress).safeTransfer(             // lines 351-354
    payload.recipient,
    payload.amount
);
``` [1](#0-0) [2](#0-1) 

If `payload.recipient` is on the USDC blocklist, `safeTransfer` reverts, rolling back the entire transaction including the nonce mark. The nonce is never permanently consumed, so the relayer can retry indefinitely — but every attempt reverts identically. No alternative delivery path exists.

**NEAR side — no cancel mechanism:**

When a user initiates a NEAR → EVM transfer, `init_transfer_internal` burns (for deployed tokens) or locks (for native tokens) the user's funds and stores a `TransferMessage` in `pending_transfers`: [3](#0-2) 

The only public path that removes a `pending_transfers` entry is `claim_fee_callback`, which requires a `ProverResult::FinTransfer` proof — i.e., proof that the EVM side already emitted a `FinTransfer` event: [4](#0-3) 

If `finTransfer` always reverts, no `FinTransfer` event is ever emitted on EVM, so no valid proof can ever be produced. The `pending_transfers` entry is permanently stuck. `remove_transfer_message` is private and only reachable through this callback: [5](#0-4) 

There is no public cancel, redirect, or emergency-release function anywhere in the NEAR contract.

## Impact Explanation

This matches the allowed critical impact: **permanent freezing of bridged funds across NEAR and EVM flows**.

- **Burned tokens** (deployed/bridged tokens on NEAR): burned on NEAR, never minted on EVM — permanently destroyed.
- **Locked tokens** (native tokens on NEAR, e.g., USDC locked in the bridge): locked in the NEAR bridge contract forever, with no release path.

The `evm/SECURITY.md` documents no known issue or accepted risk for this scenario. [6](#0-5) 

## Likelihood Explanation

Low but realistic. USDC blacklisting is a documented, exercised real-world mechanism (OFAC sanctions, exchange enforcement). A user whose EVM address is sanctioned after initiating a bridge transfer, or who unknowingly bridges to a sanctioned address, triggers this condition without any attacker action. No privileged access is required; the condition arises from the normal bridge flow combined with an external token restriction.

## Recommendation

Adopt a pull-over-push pattern for EVM token delivery. Instead of pushing tokens to `payload.recipient` inside `finTransfer`, record the claimable balance in a mapping and let the recipient (or a designated address) call a separate `claimTransfer(nonce)` function. This decouples finalization (nonce consumption, `FinTransfer` event emission) from delivery, so a blacklisted recipient does not block the protocol and the NEAR side can receive the finalization proof regardless of delivery outcome.

## Proof of Concept

1. Alice holds USDC on NEAR and calls `ft_transfer_call` to bridge 1000 USDC to her EVM address `0xAlice`. NEAR burns the wrapped USDC and stores the `TransferMessage` in `pending_transfers` via `init_transfer_internal`.
2. Alice (or a relayer) calls `sign_transfer`; the MPC signs a `TransferMessagePayload` with `recipient = 0xAlice`.
3. Before the relayer submits the signature, `0xAlice` is added to the USDC blocklist on Ethereum.
4. The relayer calls `OmniBridge.finTransfer(sig, payload)`. Execution reaches line 351: `IERC20(USDC).safeTransfer(0xAlice, 1000e6)`. USDC reverts because `0xAlice` is blacklisted. The entire transaction reverts, including the nonce mark.
5. Every subsequent `finTransfer` attempt reverts identically. No `FinTransfer` event is ever emitted.
6. On NEAR, `claim_fee_callback` requires a `ProverResult::FinTransfer` proof (line 1075). Since no EVM finalization event exists, no proof can be produced. The `pending_transfers` entry for Alice's transfer is never removed. Alice's 1000 USDC are permanently lost. [7](#0-6) [8](#0-7)

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
