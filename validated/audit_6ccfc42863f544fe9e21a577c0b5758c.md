### Title
Peras Quorum Check Indifferent to `PerasVoteStake` Denomination — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares the accumulated `PerasVoteStake` of a voting round directly against the `perasQuorumStakeThreshold` (a relative fraction, e.g. `3/4`) without enforcing that both values share the same unit. The code itself documents this assumption as unverified. If `PerasVoteStake` values are populated from the ledger in absolute lovelace rather than as a normalized fraction, the quorum check is trivially bypassed by any registered stake pool, allowing unauthorized Peras certificate forging and chain-weight manipulation.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the core Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake          -- Rational, unit unknown
  quorumThreshold = unPerasQuorumStakeThreshold ...   -- Rational, always relative (e.g. 3/4)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ...  -- Rational, relative
``` [1](#0-0) 

The code comment on `PerasVoteStake` explicitly acknowledges the unresolved unit problem:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [2](#0-1) 

The `perasQuorumStakeThreshold` is always a relative fraction. In `mkPerasParams` it is set to `3/4`: [3](#0-2) 

`PerasVoteStake` is a bare `Rational` newtype with no enforced unit: [4](#0-3) 

The `stakeAboveThreshold` function is called in two production paths:

1. `votesReachQuorum` — the smart constructor that gates certificate forging: [5](#0-4) 

2. `updateLoserVoteState` — which checks whether a losing target has gone above quorum (triggering a `RoundVoteStateLoserAboveQuorum` error): [6](#0-5) 

The `PerasVoteStakeDistr` that feeds `vpvVoteStake` into validated votes is constructed from the ledger's stake distribution. The ledger stores stake in absolute lovelace (`Coin`). If the conversion from ledger stake to `PerasVoteStake` omits normalization (i.e., passes absolute lovelace directly), then for any voter with stake > 0.75 lovelace (effectively every real stake pool), the comparison `stake >= 0.75 + 0.02` evaluates to `True` immediately, regardless of how many distinct voters participated.

The `implEligiblePartyVoteWeight` function in `WFALS.hs` shows that persistent members receive `VoteWeight stake` (absolute lovelace), while non-persistent members receive a normalized value. This confirms the mixed-unit risk is real and not hypothetical: [7](#0-6) 

---

### Impact Explanation

Peras certificates boost the chain weight of the block they certify by `perasWeight` (default: 15 block-equivalents). `stakeAboveThreshold` is the sole gate that determines whether a certificate may be forged. If the quorum check is bypassed due to the unit mismatch:

- A single registered stake pool (even with negligible stake) can cause `votesReachQuorum` to return `Just`, triggering `forgePerasCert`.
- The resulting `ValidatedPerasCert` carries a `vpcCertBoost` of 15, which is added to the chain's `PerasWeight` in `wsvTotalWeight` during chain selection.
- Honest nodes receiving this certificate-boosted chain will prefer it over an unboosted canonical chain of equal or shorter length, constituting an unauthorized chain-selection manipulation.

This maps to: **Critical — Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance**, and **High — Chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The Peras voting pipeline is active production code. `stakeAboveThreshold` is already wired into `votesReachQuorum` and `updateLoserVoteState`. The `PerasVoteStakeDistr` is populated from the ledger's stake snapshot, which stores values in absolute lovelace. The code comment explicitly flags the missing normalization step as unresolved. Any stake pool operator running a node with Peras enabled and sending a single vote for any block would trigger the bypass if the `PerasVoteStakeDistr` is built without normalization.

---

### Recommendation

1. Enforce unit consistency at the type level: introduce distinct newtypes `AbsolutePerasVoteStake` (lovelace) and `RelativePerasVoteStake` (fraction in [0,1]), and require `stakeAboveThreshold` to accept only the relative form.
2. Normalize `PerasVoteStake` at the point of construction from the ledger stake distribution by dividing each voter's absolute stake by the total active stake before inserting into `PerasVoteStakeDistr`.
3. Alternatively, change `stakeAboveThreshold` to accept the total stake distribution and perform normalization internally, eliminating the caller-side assumption.
4. Resolve the acknowledged TODO on `PerasVoteStake` before the Peras voting path is enabled on any live network.

---

### Proof of Concept

Assume `perasQuorumStakeThreshold = 3/4`, `perasQuorumStakeThresholdSafetyMargin = 2/100`, and a `PerasVoteStakeDistr` built directly from ledger lovelace values (no normalization). A single stake pool with 1 ADA (= 1,000,000 lovelace) sends one vote:

```
totalVoteStake = PerasVoteStake (1_000_000 % 1)   -- absolute lovelace
quorumThreshold + safetyMargin = 3/4 + 2/100 = 77/100

stakeAboveThreshold:
  1_000_000 >= 77/100  →  True
```

`votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a certificate boosting the block by 15 weight units is produced — with only a single voter holding a fraction of a percent of total stake, far below the intended 75% quorum.
