### Title
Peras Quorum Check Unit Mismatch Allows Unauthorized Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` directly compares `PerasVoteStake` (a `Rational` that may carry an absolute ledger-stake value) against `perasQuorumStakeThreshold` (a relative normalized value, e.g. `3/4`). The code itself acknowledges this unit mismatch with an explicit TODO. If the `PerasVoteStakeDistr` fed into vote validation contains absolute lovelace-denominated values, the comparison is dimensionally wrong: any pool whose absolute stake exceeds `3/4` (trivially true for any pool holding more than `0.75` lovelace) would cause quorum to be declared after a single vote, enabling unauthorized Peras certificate forging and chain-selection manipulation.

### Finding Description

**Root cause — `stakeAboveThreshold`:**

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake          = unPerasVoteStake voteStake          -- unit unknown
  quorumThreshold = unPerasQuorumStakeThreshold ...    -- relative: 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ...  -- 2/100
``` [1](#0-0) 

The code's own comment at lines 155–161 states:

> "this function assumes that the `PerasVoteStake` and the quorum threshold … are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type comment (lines 136–143) further admits there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [3](#0-2) 

**Call chain from network input to the flawed check:**

1. A peer submits a `PerasVote` via the miniprotocol. `processVotes` calls `validatePerasVote`, which looks up the voter's stake from `PerasVoteStakeDistr` and attaches it as `vpvVoteStake`. [4](#0-3) 

2. The validated vote is stored and then processed by `updateCandidateVoteState`, which calls `votesReachQuorum`. [5](#0-4) 

3. `votesReachQuorum` sums `vpvVoteStake` values and calls `stakeAboveThreshold`. [6](#0-5) 

4. `stakeAboveThreshold` compares the raw `Rational` against `3/4 + 2/100` with no normalization. [7](#0-6) 

5. The `PerasQuorumStakeThreshold` is set to the relative value `3/4`. [8](#0-7) 

**The mismatch:** If `PerasVoteStakeDistr` is populated with absolute lovelace values (the natural ledger representation), then a pool holding, say, `1_000_000_000` lovelace has `PerasVoteStake = 1_000_000_000 / 1 = 1_000_000_000`. Comparing `1_000_000_000 >= 3/4 + 2/100` is trivially `True`. A single vote from any pool with positive stake would immediately satisfy the quorum check, causing a certificate to be forged.

The `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` both accept `STM m PerasVoteStakeDistr` as an external parameter with no normalization contract enforced at the type level. [9](#0-8) 

### Impact Explanation

If the unit mismatch is triggered (absolute stake values fed into a relative-threshold comparison), any unprivileged peer can submit a single valid `PerasVote` and cause the node to forge a Peras certificate for an arbitrary block. A forged certificate grants that block a `perasWeight = 15` chain-selection boost, causing honest nodes to prefer the attacker's chosen chain over the canonical chain. This is a **bypass of the Peras quorum/certificate check** and a **chain-selection manipulation**, matching the "Critical — bypass of Peras voting or certificate checks" and "High — chain selection bug" impact categories.

### Likelihood Explanation

The likelihood depends on whether the upstream code that populates `PerasVoteStakeDistr` normalizes values before insertion. The type system provides no enforcement, the TODO comment confirms the normalization is not yet implemented, and the `PerasVoteStake` type comment explicitly states the unit is unresolved. Any integration that passes raw ledger lovelace values (the most natural representation) triggers the bug. Given the Peras protocol is under active development and the normalization step is documented as missing, the probability of an incorrect integration is high.

### Recommendation

1. **Enforce units at the type level**: split `PerasVoteStake` into `AbsolutePerasVoteStake` and `RelativePerasVoteStake`; require `stakeAboveThreshold` to accept only the relative variant.
2. **Normalize before comparison**: `stakeAboveThreshold` (or its callers) must divide the accumulated vote stake by the total committee stake before comparing against `perasQuorumStakeThreshold`.
3. **Remove the TODO and assert the invariant**: add a runtime assertion or type-level proof that the `PerasVoteStakeDistr` values are normalized (sum ≤ 1) before any quorum check.

### Proof of Concept

```
Given:
  perasQuorumStakeThreshold = 3/4
  perasQuorumStakeThresholdSafetyMargin = 2/100
  threshold = 3/4 + 2/100 = 77/100

Scenario (absolute stake, total supply = 45e15 lovelace):
  Pool A holds 1% of stake = 4.5e13 lovelace
  PerasVoteStake for Pool A = 4.5e13 (absolute, not normalized)

stakeAboveThreshold check:
  4.5e13 >= 77/100  →  True  (trivially, since 4.5e13 >> 0.77)

Result:
  votesReachQuorum returns Just (single vote from Pool A)
  → forgePerasCert is called
  → certificate with boost=15 is forged for attacker's chosen block
  → honest nodes apply +15 weight to attacker's block in chain selection
  → canonical chain may be displaced
```
