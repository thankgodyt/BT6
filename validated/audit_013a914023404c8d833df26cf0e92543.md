### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. Any unprivileged peer can send a crafted `PerasCert` naming any block point as the boosted target; the certificate is accepted, stored in the `PerasCertDB`, and immediately used to inflate the Peras weight of that block in chain selection, potentially causing the node to switch to a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must be passed before a peer-supplied certificate is accepted. The only deployed instance is the catch-all degenerate instance:

    Right

This function is called directly in the production inbound certificate pool writer `makePerasCertPoolWriterFromChainDB`, which is the path used when certificates arrive from network peers:

`processCerts` calls `validateCert` on each inbound certificate and, because `validatePerasCert` always returns `Right`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` processes it, stores the certificate in `PerasCertDB`, and triggers `chainSelectionForBlock` for the boosted block: [4](#0-3) 

The `PerasWeightSnapshot` is then updated with the certificate's `vpcCertBoost` (= `perasWeight params`) for the attacker-chosen block point. Chain selection uses `weightedSelectView` and `preferCandidate`, which compares `wsvTotalWeight` — block length plus accumulated Peras weight boost — to decide whether to switch forks: [5](#0-4) 

The `PerasCertDB` implementation also carries a matching TODO acknowledging that non-trivial validation logic is absent: [6](#0-5)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on any fork. Because `validatePerasCert` never rejects, the certificate is accepted, stored, and its weight boost is applied to that block in the `PerasWeightSnapshot`. If the boosted fork's `wsvTotalWeight` then exceeds the current chain's, `preferCandidate` returns `ShouldSwitch` and the node rolls back to the attacker-chosen fork. This is a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended Peras security assumptions, and simultaneously a bypass of Peras certificate checks enabling unauthorized certificate acceptance.

**Impact: High**

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production node. The attack requires only sending a well-formed CBOR-serialised `PerasCert` message over the object-diffusion mini-protocol — no keys, no stake, no prior relationship with the target node. The degenerate instance is the only `BlockSupportsPeras` instance in the codebase; no more-specific instance for `CardanoBlock` overrides it.

**Likelihood: High**

---

### Recommendation

1. Implement real cryptographic and semantic validation inside `validatePerasCert` before the Peras certificate diffusion mini-protocol is enabled on any network. At minimum, verify the aggregate BLS/KES signature over the certificate, check that the claimed round number is within the current epoch's valid range, and confirm that the boosted block point exists and is within the rollback window.
2. Until real validation is in place, gate the inbound certificate path behind a feature flag so that the degenerate instance is never reachable from untrusted peers.
3. Track and close [cardano-peras issue #120](https://github.com/tweag/cardano-peras/issues/120) before any mainnet or public-testnet deployment.

### Proof of Concept

**Attacker-controlled entry path:**

1. Connect to a target node via the Peras object-diffusion mini-protocol.
2. Send a `PerasCert` message with:
   - `pcCertRound` = any round number not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of a block on a fork the attacker wants the node to adopt
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}`.
4. The certificate is enqueued via `addPerasCertAsync` → `ChainSelAddPerasCert`.
5. `chainSelSync` stores the cert and calls `chainSelectionForBlock` for the boosted block.
6. `constructPreferableCandidates` computes `weightedSelectView` for the fork; the injected boost raises its `wsvTotalWeight` above the current chain's.
7. `preferCandidate` returns `ShouldSwitch`; the node rolls back and adopts the attacker-chosen fork. [7](#0-6) [3](#0-2) [8](#0-7) [5](#0-4)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
