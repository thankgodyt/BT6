### Title
Per-Account `pending_tx_limits` Check Can Be Bypassed via Multiple NEAR Accounts, Enabling UTXO Exhaustion - (File: `contracts/satoshi-bridge/src/account.rs`, `contracts/satoshi-bridge/src/api/token_receiver.rs`)

---

### Summary
The bridge enforces a per-account limit on simultaneous pending withdrawal (sign) transactions via `get_max_pending_sign_txs`, defaulting to 1. Because this limit is keyed on the NEAR `sender_id` (account), an attacker who distributes nBTC across many NEAR accounts can trivially bypass it, initiating an unbounded number of concurrent withdrawals. This exhausts the bridge's available UTXO pool and temporarily prevents legitimate users from withdrawing.

---

### Finding Description

The withdrawal flow begins when a user calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message. The bridge's `ft_on_transfer` handler dispatches to `create_btc_pending_info`, which enforces the pending-sign limit:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs
let max_pending = self.get_max_pending_sign_txs(&sender_id);
let account = self.internal_unwrap_or_create_mut_account(&sender_id);
require!(
    account.pending_sign_count() < max_pending,
    "Too many pending sign transactions"
);
``` [1](#0-0) 

`get_max_pending_sign_txs` looks up the limit from `pending_tx_limits` keyed by `account_id`, defaulting to `1` if no entry exists:

```rust
// contracts/satoshi-bridge/src/account.rs
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)
}
``` [2](#0-1) 

The limit is **per-account, not global**. There is no cap on the total number of concurrent pending withdrawals across all accounts. An attacker who controls N NEAR accounts — each holding some nBTC — can initiate N simultaneous withdrawals, one per account, each consuming one or more UTXOs from the bridge's available pool.

The same per-account check is also used in `require_pending_sign_capacity`, called from `withdraw_rbf` and `cancel_withdraw`: [3](#0-2) 

The `pending_tx_limits` map is only writable by DAO: [4](#0-3) 

There is no mechanism to set a global ceiling on total pending withdrawals, so the per-account limit provides no protection against a multi-account attacker.

---

### Impact Explanation

**Medium.** An attacker with nBTC distributed across many NEAR accounts can exhaust the bridge's UTXO pool by initiating one withdrawal per account simultaneously. Once all UTXOs are locked in pending withdrawals, legitimate users cannot initiate new withdrawals until the attacker's transactions are either signed and confirmed on-chain or cancelled via `cancel_withdraw` (which requires DAO/Operator intervention). This constitutes an attacker-triggered temporary locking of bridged funds and a bypass of the bridge's stated per-account withdrawal-rate policy.

---

### Likelihood Explanation

**Medium.** Creating multiple NEAR accounts is free and trivial. The only cost to the attacker is holding nBTC across those accounts (capital they already own). The attack requires no privileged access, no leaked keys, and no external dependency. The pattern (multi-wallet bypass of a per-account limit) is well-known and has been executed in analogous NFT/DeFi contexts.

---

### Recommendation

1. **Document the limitation**: Make explicit that `pending_tx_limits` is a per-account courtesy limit and does not protect against multi-account UTXO exhaustion.
2. **Add a global pending-withdrawal cap**: Introduce a contract-level counter for total active pending sign transactions and enforce a configurable ceiling (e.g., `max_global_pending_sign_txs` in `Config`). Reject new withdrawals when the global cap is reached.
3. **Consider a minimum withdrawal size or UTXO reservation policy**: Require a minimum nBTC amount per withdrawal to raise the capital cost of exhaustion attacks.

---

### Proof of Concept

1. Attacker acquires nBTC and splits it across N NEAR accounts (`attacker_0.near` … `attacker_N.near`).
2. Each account calls `nbtc.ft_transfer_call(bridge, amount, Withdraw { input: [utxo_i], ... })`.
3. For each call, `create_btc_pending_info` checks `account.pending_sign_count() < get_max_pending_sign_txs(&sender_id)`. Since each account has 0 pending sign txs and the default limit is 1, all N calls succeed.
4. Each call removes `utxo_i` from the available UTXO pool (`generate_vutxos` marks them unavailable).
5. After N calls, all UTXOs are locked in pending withdrawals.
6. A legitimate user calls `ft_transfer_call` with a `Withdraw` message — the PSBT construction fails because no UTXOs are available, and the withdrawal is rejected.
7. The bridge remains in this state until DAO/Operator calls `cancel_withdraw` for each of the attacker's pending transactions, requiring significant operator intervention. [5](#0-4) [6](#0-5)

    pub fn set_pending_tx_limit(&mut self, account_id: AccountId, max_pending: Option<u32>) {
        assert_one_yocto();
        if let Some(max_pending) = max_pending {
            require!(max_pending >= 1, "Invalid max_pending value");
            self.data_mut()
                .pending_tx_limits
                .insert(account_id, max_pending);
        } else {
            let prev = self.data_mut().pending_tx_limits.remove(&account_id);

                prev.is_some(),
                format!("Invalid account_id: {}", account_id)
            );
        }
