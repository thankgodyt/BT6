### Title
`safe_mint` Unconditionally Mints to Bridge Before Account-Registration Check, Inflating Token Supply — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nbtc token contract mints tokens to `bridge_id` **before** verifying that the recipient account is registered. When the recipient is unregistered the function returns `U128(0)` without burning the already-minted tokens, leaving unbacked nBTC permanently credited to `bridge_id`. Because NEAR cross-contract state changes are not rolled back by a caller-side revert, a failed `safe_mint` call permanently inflates the token supply, and — if the bridge does not mark the UTXO as verified on failure — the same BTC deposit can be used to mint nBTC a second time.

---

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` (lines 101–124) follows this sequence:

```
1. self.token.internal_deposit(&self.bridge_id, amount.into());   // tokens minted to bridge_id
2. if self.token.accounts.get(&account_id).is_none() {
       return PromiseOrValue::Value(U128(0));                      // early return, NO burn
   }
3. // transfer from bridge_id to account_id (only reached when registered)
``` [1](#0-0) 

When `account_id` is not registered the function returns `U128(0)` after step 1 has already executed. The `amount` tokens now reside in `bridge_id`'s balance with no corresponding BTC backing and no mechanism to burn them.

In NEAR's asynchronous execution model each cross-contract call is a separate receipt. If the bridge's callback panics or reverts upon seeing the `0` return value, only the bridge contract's state in that callback is rolled back; the nbtc contract's `internal_deposit` — which already committed — is **not** undone.

The bridge's deposit-verification path (`verify_deposit_v2` → `internal_safe_verify_deposit_entry`) guards against double-processing via `verified_deposit_utxo`: [2](#0-1) 

If the bridge treats the `0` return as a failure and therefore does **not** insert the UTXO into `verified_deposit_utxo`, the same UTXO remains eligible for a second `verify_deposit_v2` call. After the user registers their NEAR account a relayer can resubmit the proof, causing `safe_mint` to mint a second `amount` to `bridge_id` and transfer it to the user — two rounds of nBTC minted against one BTC deposit.

---

### Impact Explanation

**Minimum (Medium):** Every failed `safe_mint` call permanently inflates `bridge_id`'s nBTC balance by `amount` without any BTC backing. The 1:1 BTC:nBTC invariant is broken; the protocol's total supply exceeds locked BTC. This constitutes a stuck bridge state requiring operator intervention to reconcile.

**Maximum (Critical):** If the bridge does not mark the UTXO as verified on a `0` return, the same BTC UTXO can be used to mint nBTC twice — unauthorized minting of bridge-backed tokens. The attacker receives `amount` nBTC while the bridge's supply is inflated by `2 × amount` against `1 × amount` of locked BTC.

---

### Likelihood Explanation

The trigger condition — a user's NEAR account not being registered in the nbtc contract at the moment the deposit is processed — is realistic. Users in the Omni Bridge / safe-deposit flow may deposit BTC before completing NEAR-side account registration. A relayer that retries failed deposits (standard operational behavior) would automatically trigger the double-mint path once the user registers.

---

### Recommendation

Move the account-registration check **before** `internal_deposit`. Only mint to `bridge_id` after confirming the recipient account exists:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check FIRST, mint SECOND
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer / ft_transfer_call
}
```

Alternatively, if the early-return path must remain, add an explicit burn before returning:

```rust
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_withdraw(&self.bridge_id, amount.into()); // undo mint
    return PromiseOrValue::Value(U128(0));
}
```

### Proof of Concept

1. User deposits BTC to their bridge deposit address.
2. User's NEAR account is **not** registered in the nbtc contract.
3. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
4. Bridge calls `safe_mint(user_account, amount, msg)` on nbtc.
5. nbtc executes `internal_deposit(&bridge_id, amount)` → `bridge_id` balance increases by `amount`. [3](#0-2) 
6. nbtc checks `accounts.get(&user_account)` → `None` → returns `U128(0)`. [4](#0-3) 
7. Bridge callback receives `0` → treats as failure → does **not** insert UTXO into `verified_deposit_utxo`.
8. `bridge_id` now holds `amount` unbacked nBTC; total supply > locked BTC. *(Medium impact confirmed.)*
9. User registers their NEAR account in nbtc.
10. Relayer retries `verify_deposit_v2` for the same UTXO (not blocked, since step 7 skipped the `verified_deposit_utxo` insert).
11. nbtc executes `internal_deposit(&bridge_id, amount)` **again** → `bridge_id` balance increases by another `amount`.
12. nbtc transfers `amount` to `user_account`.
13. **Result:** `2 × amount` nBTC minted; `1 × amount` BTC locked. *(Critical double-mint.)*
