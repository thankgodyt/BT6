### Title
Unvalidated `refund_address` in `request_refund` Enables Attacker-Triggered Temporary Locking of User BTC Refund Path — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund` accepts any arbitrary string as `refund_address` without validating it against the configured chain's address format. The invalid string is stored verbatim in `RefundRequest`. Because a duplicate-request guard then blocks any second `request_refund` for the same UTXO, the user's BTC refund path is stuck until a DAO/Operator manually calls `reject_refund`. This is a direct analog of the external report's missing-input-validation class, applied to the bridge's refund surface.

### Finding Description

`internal_request_refund` performs only one check on the caller-supplied `refund_address`: when `deposit_msg.refund_address` is `Some`, it asserts the two strings are equal. When `deposit_msg.refund_address` is `None` (the "unsafe" path), no format check is performed at all. [1](#0-0) 

The unvalidated string is then forwarded through the async Light-Client verification and stored verbatim in `RefundRequest.refund_address` inside `request_refund_callback`: [2](#0-1) 

The first and only format check occurs much later, inside `build_refund_output`, which is called during `execute_refund`: [3](#0-2) 

`Address::parse(...).expect("Invalid refund address")` panics if the stored string is not a valid address for the configured chain. Because `execute_refund` panics before `finalize_refund_with_psbt` is reached, the UTXO is **not** added to `verified_deposit_utxo`, and the `RefundRequest` remains in storage.

The duplicate-request guard in `request_refund_callback` then prevents any new `request_refund` for the same UTXO: [4](#0-3) 

### Impact Explanation

A user who deposited BTC with `deposit_msg.refund_address = None` and whose deposit was never finalized (relayer down, etc.) needs to call `request_refund` to recover their BTC. An attacker who observes the on-chain deposit can front-run or race the user's `request_refund` call with an identical `deposit_msg` but a garbage `refund_address` (e.g., `"INVALID"`). Once that request is stored, the user cannot submit a second one. Every subsequent `execute_refund` call panics. The user's BTC refund path is blocked until a DAO/Operator calls `reject_refund` to clear the malicious entry, after which the user can re-submit. This constitutes attacker-triggered temporary locking of bridged funds requiring operator intervention. [5](#0-4) 

### Likelihood Explanation

The `request_refund` function is permissionless — any NEAR account can call it for any deposit whose `deposit_msg` is publicly observable (it is emitted in `LogDepositAddress` events). The attacker only needs to supply a valid BTC transaction proof (already on-chain) and a garbage `refund_address` string. The `unsafe_refund_timelock_sec` gives the DAO a window to reject suspicious requests, but this is a mitigation that requires active monitoring, not a prevention. The attack is cheap (only the storage deposit is required) and repeatable. [6](#0-5) 

### Recommendation

Validate `refund_address` against the configured chain's address format at the entry point of `internal_request_refund`, before the async Light-Client call, so an invalid address is rejected immediately:

```rust
// In internal_request_refund, after the deposit_msg.refund_address match block:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the validation already applied in `build_refund_output` and `string_to_script_pubkey`, and is consistent with the fix described in the external report (reject inputs that do not adhere to the expected format). [7](#0-6) 

### Proof of Concept

1. Alice deposits BTC to the address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The deposit is confirmed on-chain but `verify_deposit` is never called (relayer is down).

2. Attacker observes the `LogDepositAddress` event, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
     refund_address = "INVALID_NOT_A_BTC_ADDRESS",
     tx_bytes = <valid deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
   )
   ```
   `internal_request_refund` passes the string through without format validation. [1](#0-0) 

3. `request_refund_callback` stores `RefundRequest { refund_address: "INVALID_NOT_A_BTC_ADDRESS", ... }`. [8](#0-7) 

4. Alice tries to call `request_refund` for the same UTXO — rejected: `"Refund request already exists for this UTXO"`.

5. After `unsafe_refund_timelock_sec` passes, anyone calls `execute_refund`. `build_refund_output` panics: `"Invalid refund address"`. The UTXO is not marked verified; the bad `RefundRequest` remains. [3](#0-2) 

6. Alice's BTC refund path is blocked. A DAO/Operator must call `reject_refund` before Alice can re-submit a valid request. [9](#0-8)

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
