### Title
Orchard Bundle Action Count Mismatch Renders Zcash Orchard Withdrawal Path Unusable — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary
`EXPECTED_ACTIONS_NUMBER = 1` enforces exactly one Orchard action, but the standard Orchard SDK builder pads every bundle to at least 2 actions (`MIN_ACTIONS = 2`). Any user submitting a standard Orchard bundle triggers a panic in `ft_on_transfer_callback`. Tokens are refunded via NEP-141 callback semantics; no funds are permanently lost.

### Finding Description
`extract_orchard_bundle` in `orchard_policy.rs` line 49 checks `bundle.actions().len() != EXPECTED_ACTIONS_NUMBER` where `EXPECTED_ACTIONS_NUMBER = 1`. The comment on lines 13–15 references the Orchard builder's `MIN_ACTIONS` constant (which is `2`) as justification, but then sets the expected count to `1` — a direct contradiction. The standard Orchard SDK builder always pads bundles to at least 2 actions for privacy. When a user submits a withdrawal with a standard Orchard bundle (2 actions), `extract_orchard_bundle` returns `Err(...)`, and `PsbtWrapper::new` (line 81–83 of `psbt_wrapper.rs`) calls `env::panic_str(...)`. This panic propagates through `ft_on_transfer_callback`, causing the Promise to fail. The FT contract's `ft_resolve_transfer` then refunds the full amount to the sender.

### Impact Explanation
**Low.** The Orchard shielded withdrawal path is completely non-functional for any user using the standard Orchard SDK. The panic is publicly reachable via `ft_transfer_call`. However, NEP-141 callback semantics ensure the transferred nZEC is refunded — there is no permanent fund loss, no theft, and no stuck bridge state.

### Likelihood Explanation
Certain for any user attempting an Orchard withdrawal with standard tooling. The standard Orchard builder always produces ≥ 2 actions; the bridge requires exactly 1.

### Recommendation
Change `EXPECTED_ACTIONS_NUMBER` to `2` (matching the actual Orchard protocol `MIN_ACTIONS`), or relax the check to `bundle.actions().len() < EXPECTED_ACTIONS_NUMBER` (minimum, not exact), and update `recover_output_with_ovk` logic to iterate all actions rather than hardcoding index `0`.

### Proof of Concept
1. User calls `ft_transfer_call` on the nZEC FT contract with a `Withdraw` message containing a standard Orchard bundle (2 actions, as produced by the Orchard SDK builder).
2. `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` returns a Promise to `ft_on_transfer_callback`.
3. `ft_on_transfer_callback` calls `PsbtWrapper::new(input, output, orchard_bundle, ...)`.
4. `PsbtWrapper::new` calls `extract_orchard_bundle(orchard_bundle_bytes, ...)`.
5. `bundle.actions().len()` is `2`; `2 != 1` → `Err("Orchard bundle must have 1 actions, got 2")`.
6. `unwrap_or_else(|_| env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: ..."))` fires.
7. Promise fails; FT contract refunds nZEC to user. Orchard withdrawal is rejected.
