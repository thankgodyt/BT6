### Title
Peras Vote Validation Bypass — Incomplete `validatePerasVote` Allows Forged Votes to Accumulate Quorum Stake — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default implementation of `validatePerasVote` in the `BlockSupportsPeras` typeclass only checks whether the voter ID exists in the stake distribution. It performs no cryptographic verification of the vote signature or VRF eligibility proof. An unprivileged peer can craft `PerasVote` messages using any valid stake pool key hash from the publicly observable stake distribution, have them accepted as legitimate, and accumulate enough forged stake to trigger quorum — causing an illegitimate Peras certificate to be forged and a chosen block's chain weight to be boosted.

---

### Finding Description

**Root cause — `validatePerasVote` stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote
        { vpvVote = vote
        , vpvVoteStake = stake
        }
  | otherwise =
      Left PerasValidationErr
```

`lookupPerasVoteStake` only performs a `Map.lookup` on the voter ID: [2](#0-1) 

The check that is **absent**:
- No vote signature verification (which would prove the voter actually signed this vote)
- No VRF eligibility proof verification (which would prove the voter was selected for the committee via local sortition)

The `WFALS.hs` module contains a complete `implVerifyVote` that performs both checks — signature verification and VRF output verification — but it is **not wired into** `validatePerasVote`: [3](#0-2) 

**Production call site — vote inbound processing:**

`validatePerasVote` is called directly in the production vote diffusion path: [4](#0-3) 

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
```

Any vote that passes this stub is timestamped and forwarded to `ChainDB.addPerasVoteWithAsyncCertHandling`, which feeds the `PerasVoteDB` aggregation engine: [5](#0-4) 

**Stake accumulation in the aggregation engine:**

Once a vote passes `validatePerasVote`, it is inserted into `PerasTargetVoteTally.ptvtTotalStake`. The deduplication guard (`pvdsVoteIds`) only prevents the same `PerasVoteId` (round + voter) from being inserted twice — it does not prevent an attacker from submitting votes for *different* voter IDs drawn from the stake distribution: [6](#0-5) 

`PerasVoteId` is defined as `{pviRoundNo, pviVoterId}` — it does not include the block being voted for, so each distinct voter ID in the distribution can contribute its full stake to any target: [7](#0-6) 

When accumulated stake crosses the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` and returns it via `AddedPerasVoteAndGeneratedNewCert`: [8](#0-7) 

---

### Impact Explanation

The forged certificate is accepted by `addPerasCertAsync` and applied to chain selection via `getPerasWeightSnapshot`. The boosted block gains `PerasWeight` that honest nodes use when comparing candidate chains: [9](#0-8) 

An attacker who controls no stake can cause honest nodes to prefer a non-canonical chain by:
1. Selecting a target block on a minority fork
2. Sending crafted `PerasVote` messages using valid stake pool key hashes from the public stake distribution
3. Accumulating enough forged stake to exceed the quorum threshold
4. Triggering certificate forging for the minority-fork block
5. Causing honest nodes to switch to the boosted (but illegitimately certified) chain

This matches the **Critical** allowed impact: *"Bypass of… Peras voting or certificate checks… that enables unauthorized… vote, or certificate acceptance."*

---

### Likelihood Explanation

The attack requires only:
- Knowledge of valid `PerasVoterId` values (stake pool key hashes), which are publicly observable from the stake distribution
- The ability to send `PerasVote` protocol messages to a target node (standard unprivileged peer capability)
- No cryptographic keys, no stake, no operator access

The `processVotes` function in `ObjectPool/PerasVote.hs` is the live inbound path for votes received from peers: [10](#0-9) 

---

### Recommendation

Wire `implVerifyVote` (or an equivalent) from `Committee/WFALS.hs` into `validatePerasVote` so that every inbound vote is checked for:
1. A valid vote signature over `(roundNo, boostedBlock)` using the voter's public key
2. A valid VRF output proving committee eligibility via local sortition

The existing TODO at lines 360–362 of `SupportsPeras.hs` acknowledges this gap and references issue `https://github.com/tweag/cardano-peras/issues/120`. Until this is resolved, the Peras vote diffusion path must not be enabled on any network where chain-weight manipulation is a security concern.

---

### Proof of Concept

```
-- Attacker controls no stake but knows the stake distribution
-- Step 1: enumerate valid voter IDs from the public PerasVoteStakeDistr
let voterIds = Map.keys (unPerasVoteStakeDistr stakeDistr)

-- Step 2: craft votes for a minority-fork block in round R
let forgedVotes =
      [ PerasVote
          { pvVoteRound   = R
          , pvVoteBlock   = minorityForkBlockPoint
          , pvVoteVoterId = vid
          }
      | vid <- voterIds
      ]

-- Step 3: send via Peras vote diffusion miniprotocol
-- validatePerasVote accepts each vote because vid ∈ stakeDistr
-- Each vote's stake is added to ptvtTotalStake for (R, minorityForkBlockPoint)

-- Step 4: once accumulated stake > quorum threshold,
-- updatePerasRoundVoteStates returns VoteGeneratedNewCert
-- → ValidatedPerasCert is forged for minorityForkBlockPoint
-- → addPerasCertAsync boosts that block's chain weight
-- → honest nodes switch to the minority fork
```

**Analog to the FLUX bug:** In FLUX, merging a "spent" token into an "unspent" token inflates the unspent token's balance, allowing rewards to be claimed against a balance that was already consumed. Here, submitting forged votes using already-"owned" stake pool identities inflates the vote tally for a chosen block, allowing a certificate (and its chain-weight boost) to be obtained without any legitimate voting stake being committed — the same pattern of unauthorized value accumulation through a state-tracking/validation gap.

  let voteId = getPerasVoteId vote
  addPerasVoteRes <- do

    (res, pvds') <- addOrIgnoreVote pvds voteId
    writeTVar pvdeState (WithFingerprint pvds' (succ fp))
    pure res
  pure $ do
    traceWith pvdeTracer (AddVote voteId vote addPerasVoteRes)
    return addPerasVoteRes

  addOrIgnoreVote pvds voteId
    -- Vote is already in the DB => ignore it
    | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds

updateTargetVoteTally ::
  StandardHash blk =>
  WithArrivalTime (ValidatedPerasVote blk) ->
  PerasTargetVoteTally blk ->
  PerasTargetVoteTally blk
updateTargetVoteTally
  vote
  ptvt@PerasTargetVoteTally
    { ptvtVotes
    , ptvtTarget
    , ptvtTotalStake
    } =
    assert (getPerasVoteTarget vote == ptvtTarget) $ do
      ptvt
        { ptvtVotes = pvaVotes'
        , ptvtTotalStake = pvaTotalStake'
        }
   where
    swapVote =
      Map.insertLookupWithKey
        (\_k old _new -> old)
        (getPerasVoteId vote)

    (pvaVotes', pvaTotalStake')
      -- key WAS NOT present → vote inserted and stake updated
      | (Nothing, votes') <- swapVote vote ptvtVotes =
          (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
      -- key WAS already present → votes and stake unchanged
      | otherwise =
          (ptvtVotes, ptvtTotalStake)
