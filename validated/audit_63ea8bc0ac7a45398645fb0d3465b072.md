### Title
Unprivileged Caller Can Submit Refund Request for Any Deposit with Attacker-Controlled BTC Destination — (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` performs no check that the caller is the intended deposit recipient. When `deposit_msg.refund_address` is `None`, any NEAR account can submit a refund request for any confirmed BTC deposit and supply an arbitrary attacker-controlled BTC address as the refund destination. The only protection is the `unsafe_refund_timelock_sec` window during which DAO/Operator can reject the request — a trust assumption that is absent from the code itself.

### Finding Description
`request_refund` is a publicly callable function (no role restriction on the function itself). It accepts a `deposit_msg` containing `recipient_id` (the intended NEAR recipient) and a separate `refund_address` (the BTC address to receive the refund). The function verifies the BTC transaction via the Light Client and checks that the output script matches the deposit address derived from `deposit_msg`, but it never checks that `env::predecessor_account_id() == deposit_msg.recipient_id`. [1](#0-0) 

When `deposit_msg.refund_address` is `Some(addr)`, the callback enforces that the provided `refund_address` matches the pre-authorized value, so the refund destination is locked. [2](#0-1) 

However, when `deposit_msg.refund_address` is `None` — the common case for users who did not pre-authorize a refund address — the caller freely supplies any BTC address as `refund_address`, and the callback stores it verbatim: [3](#0-2) 

The only guard for this case is a longer `unsafe_refund_timelock_sec` to give DAO/Operator time to reject: [4](#0-3) 

`execute_refund` is also callable by anyone after the timelock: [5](#0-4) 

The refund PSBT is built to pay `refund_amount` to the stored `refund_address`, which is the attacker's address: [6](#0-5) 

### Impact Explanation
An attacker who observes a victim's BTC deposit on-chain (before the relayer calls `verify_deposit`) can call `request_refund` with the victim's `deposit_msg` (publicly observable via `Event::LogDepositAddress`) and set their own BTC address as `refund_address`. If the DAO/Operator does not reject the request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the victim's BTC is sent to the attacker's address. The victim receives neither nBTC (deposit was blocked by the refund) nor their BTC back. This is a direct, complete theft of bridged user funds — matching the **Critical** impact class: unauthorized release of bridge-controlled BTC.

### Likelihood Explanation
The `deposit_msg` is emitted as a public event when `get_user_deposit_address` is called, making it trivially observable. The BTC transaction is also public on-chain. The attacker only needs to race the relayer's `verify_deposit` call, which is realistic since relayers are not always instant. The sole mitigation — DAO/Operator rejection during `unsafe_refund_timelock_sec` — is a trust assumption not enforced by the contract itself. If `unsafe_refund_timelock_sec` is configured to zero, or the DAO/Operator is offline or slow, the attack succeeds unconditionally. Likelihood is **Medium-High**.

### Recommendation
Add a caller-ownership check in `internal_request_refund` (or in the `request_refund` public entry) when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund without a pre-authorized refund address"
    );
}
```

This ensures that only the intended NEAR recipient can submit a refund request when no BTC refund address was pre-committed in the deposit message, eliminating the attacker-controlled destination vector entirely.

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, ... })` — the deposit_msg is emitted in a public event.
2. Alice sends BTC to the derived deposit address.
3. Bob (attacker) observes the BTC transaction on-chain before the relayer calls `verify_deposit`.
4. Bob calls `request_refund(deposit_msg={recipient_id: alice, refund_address: None}, refund_address="<Bob's BTC address>", tx_bytes=<Alice's tx>, ...)` with the required NEAR storage deposit.
5. `request_refund_callback` verifies the Light Client proof and stores `RefundRequest { refund_address: Bob's BTC address, ... }`. No check on `predecessor_account_id`.
6. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key)`.
7. The bridge builds a PSBT paying Alice's BTC to Bob's address and initiates MPC signing.
8. Alice's BTC is sent to Bob. Alice receives no nBTC and no BTC refund. [7](#0-6)

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );
