### Title
Dogecoin P2PKH Refund Permanently Locks User Funds via `p2wpkh_signature_hash` on Legacy Script — (`contracts/satoshi-bridge/src/bitcoin_utils/psbt_wrapper.rs`)

---

### Summary

On the Dogecoin deployment (using the `bitcoin` feature), deposit addresses are P2PKH. When a refund is executed, `finalize_refund_with_psbt` permanently marks the UTXO in `verified_deposit_utxo` and stores a `BTCPendingInfo`. Later, every call to `sign_btc_transaction` panics because `get_hash_to_sign` calls `p2wpkh_signature_hash` on a P2PKH `script_pubkey`. The signing can never succeed, re-execution is blocked by "pending info already exist", and `verified_deposit_utxo` has no admin-clearable path, permanently destroying the user's deposited funds.

---

### Finding Description

**Step 1 — Dogecoin deposit addresses are P2PKH.**

`generate_utxo_chain_address` calls `Address::from_pubkey(chain, pubkey)`. [1](#0-0) 

`get_segwit_hrp` returns `None` for `DogecoinMainnet`/`DogecoinTestnet`, so `from_pubkey` falls through to the `else` branch and returns `Address::P2pkh`. The deposit output's `script_pubkey` is therefore `OP_DUP OP_HASH160 <hash> OP_EQUALVERIFY OP_CHECKSIG`. [2](#0-1) 

**Step 2 — `internal_execute_refund` sets the P2PKH output as `witness_utxo`.** [3](#0-2) 

`deposit_output` is the raw P2PKH `TxOut` from the original deposit transaction. `psbt.set_input_utxo(vec![deposit_output])` stores it verbatim as `psbt.inputs[0].witness_utxo`. [4](#0-3) 

**Step 3 — `finalize_refund_with_psbt` permanently marks `verified_deposit_utxo` before any signing.** [5](#0-4) 

This runs synchronously inside `execute_refund` (which is publicly callable after the timelock with no ACL guard at the method level). [6](#0-5) 

**Step 4 — `get_hash_to_sign` always panics for P2PKH inputs.** [7](#0-6) 

`p2wpkh_signature_hash` in the `bitcoin` crate (0.32.x) internally calls `script_pubkey.p2wpkh_script_code()`, which returns `None` for any non-P2WPKH script, causing the function to return `Err(P2wpkhError::NotP2wpkhScript)`. The `.expect(...)` on line 151 panics. Every call to `sign_btc_transaction` for this `BTCPendingInfo` will panic.

**Step 5 — Re-execution is blocked.**

`load_refund_request_for_execute` allows re-execution when `refund_request.executed == true`: [8](#0-7) 

But `finalize_refund_with_psbt` requires the `btc_pending_id` to be absent: [9](#0-8) 

Since the same PSBT (same inputs/outputs) produces the same `btc_pending_id`, re-execution panics at "pending info already exist".

**Step 6 — No recovery path exists.**

- `verify_deposit` is blocked because `verified_deposit_utxo` contains the key.
- `internal_remove_refund_pending_tx_id` requires the refund request to be absent, but it is still present (`executed = true`).
- DAO can call `reject_refund` to remove the refund request, then `remove_refund_pending_tx_id` to clean up `BTCPendingInfo`. But `verified_deposit_utxo` is never cleared by any admin function, so `verify_deposit` remains permanently blocked. [10](#0-9) 

The deposited DOGE is permanently locked in the bridge's P2PKH address with no on-chain or contract-level recovery.

---

### Impact Explanation

Permanent, irrecoverable loss of user-deposited funds on the Dogecoin chain. The UTXO is locked in the bridge's MPC-controlled P2PKH address: it cannot be minted as nDOGE (blocked by `verified_deposit_utxo`) and cannot be refunded (signing always panics). This matches the Critical impact category: "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

---

### Likelihood Explanation

Any user who deposits DOGE and then requests a refund will trigger this automatically when `execute_refund` is called (by themselves or anyone else after the timelock). No special attacker capability is needed — the public `execute_refund` entrypoint is sufficient. The preconditions (Dogecoin chain, P2PKH deposit, refund request) are the normal operating conditions for the Dogecoin bridge.

---

### Recommendation

In `bitcoin_utils/psbt_wrapper.rs`, `get_hash_to_sign` and `save_signature` must branch on the input script type:

- For P2WPKH inputs (`script_pubkey.is_p2wpkh()`): use `p2wpkh_signature_hash` and `Witness::p2wpkh` (current behavior, correct for Bitcoin/Litecoin).
- For P2PKH inputs (`script_pubkey.is_p2pkh()`): use the legacy `legacy_signature_hash` (BIP143 does not apply) and set `final_script_sig` with a DER-encoded signature + pubkey push, leaving `final_script_witness` empty.

Additionally, `finalize_refund_with_psbt` should not insert into `verified_deposit_utxo` until the refund transaction is confirmed on-chain (i.e., move the marking to `verify_refund_finalize_callback`), to prevent permanent UTXO lockout if any later step fails.

---

### Proof of Concept

```
Chain: DogecoinMainnet (bitcoin feature, no zcash feature)

1. User deposits 1 DOGE to the bridge's P2PKH address
   (generated by generate_utxo_chain_address → Address::P2pkh).

2. User calls request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, None).
   → request_refund_callback stores RefundRequest { executed: false }.

3. After timelock, anyone calls execute_refund(utxo_storage_key, None).
   → internal_execute_refund:
       deposit_output = P2PKH TxOut { script_pubkey: OP_DUP OP_HASH160 ... }
       psbt.set_input_utxo([deposit_output])  // witness_utxo = P2PKH TxOut
   → finalize_refund_with_psbt:
       verified_deposit_utxo.insert(key)      // PERMANENT
       btc_pending_infos.insert(id, info)     // PendingSign
       refund_request.executed = true

4. sign_btc_transaction(btc_pending_sign_id, 0, 0) is called.
   → get_hash_to_sign(0, pubkeys):
       witness_utxo.script_pubkey = P2PKH script
       p2wpkh_signature_hash(..., &P2PKH_script, ...) → Err(NotP2wpkhScript)
       .expect("ERR_SIGHASH: ...") → PANIC

5. State after panic:
   - verified_deposit_utxo contains key → verify_deposit blocked forever
   - BTCPendingInfo in PendingSign → signing always panics
   - execute_refund again → "pending info already exist" panic
   - User's 1 DOGE is permanently locked.

Assert: p2wpkh_signature_hash on a P2PKH script_pubkey returns Err in bitcoin 0.32.x.
```

    pub fn get_hash_to_sign(&self, vin: usize, public_keys: &[bitcoin::PublicKey]) -> [u8; 32] {
        let tx = self.psbt.unsigned_tx.clone();
        let mut cache = SighashCache::new(tx);
        let witness_utxo = self.psbt.inputs[vin]
            .witness_utxo
            .as_ref()
            .expect("ERR_MISSING_WITNESS_UTXO: input missing witness UTXO data");
        cache
            .p2wpkh_signature_hash(

                &witness_utxo.script_pubkey,
                witness_utxo.value,
                bitcoin::EcdsaSighashType::All,
            )
            .expect("ERR_SIGHASH: failed to compute signature hash")
            .to_raw_hash()
            .to_byte_array()
    }

    pub(crate) fn internal_remove_refund_pending_tx_id(&mut self, tx_id: String) {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_related();

        // A refund spends exactly one deposit UTXO, whose key is the refund request key.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        require!(
            !self
                .data()
                .refund_requests
                .contains_key(&utxo_storage_keys[0]),
            "refund request still active"
        );

        let account_id = btc_pending_info.account_id.clone();
        self.internal_remove_btc_pending_info(&tx_id);
        let account = self.internal_unwrap_mut_account(&account_id);
        account.btc_pending_sign_ids.remove(&tx_id);
        account.btc_pending_verify_list.remove(&tx_id);
    }
