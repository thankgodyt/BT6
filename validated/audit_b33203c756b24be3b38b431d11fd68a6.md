### Title
Stub `validatePerasCert` Always Accepts Any Peras Certificate Without Validation, Enabling Unauthorized Certificate Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a degenerate stub `validatePerasCert` that unconditionally returns `Right` (success) for every certificate it receives, performing no cryptographic or structural checks. This stub is wired directly into the production Peras certificate inbound processing pipeline. An unprivileged peer can send arbitrarily crafted Peras certificates that will be accepted, stored in the `PerasCertDB`, and used to influence chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines the certificate validation interface:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

A single universal instance covers **all** block types:

```haskell

  ...

  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120

    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params

This stub is not a dead-code path. It is the function passed directly into the production inbound certificate processing pipeline in two places:

**`makePerasCertPoolWriterFromCertDB`:**
```haskell

**`makePerasCertPoolWriterFromChainDB`:**
```haskell

(validatePerasCert mkPerasParams)
``` [3](#0-2) 

The `processCerts` function that consumes this validator has no other validation gate — it partitions results into `(errors, validCerts)` and accepts the batch if the error list is empty:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the error list is always empty, and every certificate from every peer is unconditionally accepted.

The accepted certificates are then added to the `ChainDB` via `ChainDB.addPerasCertAsync`, which triggers chain selection. The `PerasCert` structure contains a `pcCertBoostedBlock :: Point blk` field that the attacker controls, pointing to any block they choose. The boost weight `vpcCertBoost` is set to `perasWeight mkPerasParams` (a fixed default of 15), which is the weight used in chain selection comparisons. [5](#0-4) 

The same pattern applies to `validatePerasVote`, which also skips all cryptographic signature checks on votes. [6](#0-5) 

---

### Impact Explanation

This is a **Critical** bypass of Peras certificate validation. An unprivileged peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block on a weaker or adversarial chain.
2. Send it via the ObjectDiffusion mini-protocol.
3. The certificate passes `validatePerasCert` unconditionally (always `Right`).
4. The certificate is stored in the `PerasCertDB` and submitted to `ChainDB.addPerasCertAsync`.
5. Chain selection is triggered with the injected boost, potentially causing the honest node to prefer a non-canonical chain.

This directly matches the allowed impact: **"Bypass of... Peras voting or certificate checks... that enables unauthorized... certificate acceptance"** and **"Chain selection... bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."**

---

### Likelihood Explanation

**Medium.** Peras is currently disabled by default (`eraPerasRoundLength = HardFork.NoPerasEnabled` in all current era configurations). [7](#0-6) 

However, the production code paths (`makePerasCertPoolWriterFromChainDB`, `makePerasCertPoolWriterFromCertDB`) are compiled and wired into the node. On any private testnet or staging environment where Peras is enabled, this is immediately exploitable by any peer that can connect to the node. The TODO comments explicitly acknowledge the stub is temporary and reference open issues (#73, #120), confirming this is known incomplete production code, not a test artifact.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's cryptographic signature against the expected committee key(s).
2. That the boosted block (`pcCertBoostedBlock`) refers to a known, valid block.
3. That the certificate round number is consistent with the current era's Peras parameters.

Until real validation is implemented, the inbound certificate processing pipeline (`processCerts`) should reject all certificates when Peras validation is not yet implemented, rather than accepting them all. A guard such as `Left PerasValidationErr` as the default should be used instead of `Right`.

---

### Proof of Concept

On a private testnet with Peras enabled, an attacker node connects to an honest node and sends a crafted certificate via the ObjectDiffusion protocol:

```haskell
-- Attacker constructs a certificate boosting a block on a weaker chain
let craftedCert = PerasCert
      { pcCertRound       = PerasRoundNo 1   -- fresh round, not yet in DB
      , pcCertBoostedBlock = blockPoint adversarialBlock  -- attacker's chosen block
      }

-- Sends craftedCert to the honest node via the PerasCert ObjectDiffusion channel.
-- processCerts calls: validatePerasCert mkPerasParams craftedCert
-- => always returns Right ValidatedPerasCert { vpcCertBoost = 15 }
-- => certificate is stored and triggers chain selection with boost=15
-- => honest node may switch to adversarialBlock's chain
```

The `processCerts` function at `PerasCert.hs:164` will accept the batch because `validatePerasCert` returns `Right` for every input, the error list is empty, and `addCert` is called unconditionally. [8](#0-7)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
