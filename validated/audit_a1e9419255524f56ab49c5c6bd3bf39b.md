### Title
Peras Certificate Validation Bypass via Unconditional `validatePerasCert` Inflates Chain Weight in Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the codebase is a degenerate universal instance that unconditionally accepts every Peras certificate without performing any cryptographic or structural validation. This is the direct analog of the external report's bug: just as `total_shares` is decremented before backing assets are removed (inflating the share price denominator), here the Peras chain-weight numerator is inflated by accepting certificates whose backing quorum of stake has never been verified. An unprivileged peer can inject arbitrary crafted certificates, inflating the `PerasWeightSnapshot` used in chain selection and causing honest nodes to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` as the mandatory validation gate for Peras certificates before they may influence chain selection. The only instance of this typeclass is the universal degenerate instance at line 320:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every certificate, regardless of its content, round number, boosted block, aggregate signature, or whether any quorum of stake ever voted for it, is unconditionally wrapped in `ValidatedPerasCert` and assigned the full `perasWeight params` boost. No signature is checked, no quorum is verified, no round-number consistency is enforced.

This `ValidatedPerasCert` is then added to the `PerasCertDB` and the `PerasWeightSnapshot` via `chainSelSync`:

```haskell
certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
``` [2](#0-1) 

The `PerasWeightSnapshot` is then consumed by `totalWeightOfFragment` during chain selection:

```haskell
totalWeightOfFragment weightSnap frag =
  weightLength <> weightBoost
 where
  weightLength = PerasWeight $ fromIntegral $ AF.length frag
  weightBoost  = weightBoostOfFragment weightSnap frag
``` [3](#0-2) 

Because `weightBoost` is inflated by unvalidated certificates, the total weight of any attacker-chosen chain fragment can be made arbitrarily large, causing chain selection to prefer it over the honest canonical chain.

**Structural analogy to the external report:**

| External report | This codebase |
|---|---|
| `total_shares` decremented before assets removed | Certificate boost added before quorum verified |
| Denominator too small → inflated price | Numerator too large → inflated chain weight |
| `price = assets / total_shares` incorrect | `totalWeight = length + weightBoost` incorrect |
| User extracts more value than entitled | Attacker's chain preferred over canonical chain |

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block as the boosted block. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored in the `PerasCertDB`, and its boost is recorded in the `PerasWeightSnapshot`. Chain selection then calls `totalWeightOfFragment` with the inflated snapshot, causing the attacker's chosen chain to appear heavier than the honest canonical chain. The honest node switches to the attacker's non-canonical chain.

This satisfies the **High** impact criterion: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

It also satisfies the **Critical** criterion: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

**High.** The degenerate instance is the only `BlockSupportsPeras` instance in the entire repository. Any peer participating in the Peras protocol can send a `PerasCert` message. No keys, stake, or special privileges are required. The attacker only needs to craft a `PerasCert` with a `pcCertBoostedBlock` pointing to their preferred block and transmit it over the standard Peras miniprotocol.

---

### Recommendation

Replace the degenerate `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS signature over the election identifier and boosted block hash.
2. Confirms that the set of voters in the certificate collectively hold stake above the quorum threshold.
3. Checks that the certificate's round number is consistent with the current protocol state.
4. Rejects certificates whose `pcCertBoostedBlock` does not correspond to a known, valid block.

Until a proper implementation is in place, the `PerasWeightSnapshot` should not be updated from network-received certificates, or the Peras chain-weight path in `totalWeightOfFragment` should be gated behind a feature flag that is disabled by default.

---

### Proof of Concept

1. Attacker connects to an honest node running the Peras miniprotocol.
2. Attacker constructs a `PerasCert` with `pcCertRound = r` and `pcCertBoostedBlock = P` where `P` is a block on the attacker's preferred (non-canonical) fork.
3. Attacker sends the certificate to the honest node.
4. The node calls `validatePerasCert params cert` — the degenerate instance returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. `chainSelSync` adds the certificate to `PerasCertDB` and updates `PerasWeightSnapshot` with the full `perasWeight` boost for block `P`.
6. Chain selection calls `totalWeightOfFragment snap frag` for the attacker's fork; `weightBoostOfFragment` returns the injected boost, making the fork appear heavier than the honest chain.
7. The honest node switches to the attacker's non-canonical fork. [4](#0-3) [5](#0-4) [3](#0-2)
