Audit Report

## Title
Missing Normalized-Amount Validation in `init_transfer` Permanently Locks Sub-Threshold Deposits — (`near/omni-bridge/src/lib.rs`)

## Summary

`normalize_amount` applies floor division to scale a token amount from its origin precision to its destination precision. `sign_transfer` requires the normalized result to be strictly positive, but `init_transfer` only checks that `fee < amount` — it never verifies that `normalize_amount(amount - fee) > 0`. Any deposit whose post-fee amount is smaller than `10^(origin_decimals - decimals)` normalizes to zero, causing every subsequent `sign_transfer` call to panic and leaving the deposited tokens permanently locked with no recovery path.

## Finding Description

`normalize_amount` performs integer floor division: [1](#0-0) 

The inline comment above it explicitly acknowledges that when `fee = 0`, dust "stays locked/burned" — but this refers to the sub-unit remainder after normalization, not to the case where the *entire* amount normalizes to zero.

`sign_transfer` computes the normalized amount and panics if it is zero: [2](#0-1) 

`init_transfer` stores the transfer message after only checking `fee < amount`: [3](#0-2) 

No normalization check is performed at deposit time. Once the transfer message is stored, the only way `remove_transfer_message` is called is inside `sign_transfer_callback` (when signing succeeds and fee is zero): [4](#0-3) 

Because `sign_transfer` panics before the MPC call is ever made, `sign_transfer_callback` is never reached. No `cancel_transfer` function exists. The transfer message — and the locked tokens — are irrecoverable.

## Impact Explanation

This concretely satisfies the critical impact class: **permanent freezing of bridged funds**. Tokens deposited via `ft_transfer_call → ft_on_transfer → init_transfer` are immediately escrowed in the bridge contract. If the deposited amount (minus fee) is below `10^(origin_decimals - decimals)`, the MPC signing step can never succeed, and no on-chain path exists to recover the funds.

## Likelihood Explanation

The condition is triggered by two standard, realistic facts: (1) a token is registered with `origin_decimals > decimals` — a normal configuration for bridging high-precision tokens — and (2) a user submits an amount below the normalization threshold. This can happen accidentally (dust amounts, UI rounding errors) or deliberately by any unprivileged external user calling `ft_transfer_call` with a crafted amount. No special privileges, key leaks, or social engineering are required.

## Recommendation

Add a normalization guard inside `init_transfer_internal` (or at the end of `init_transfer`) before the transfer message is stored:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, enforce a minimum deposit equal to `10^(origin_decimals - decimals)` at the `ft_on_transfer` entry point so the transfer is rejected before any tokens are locked.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`, threshold = 1,000,000).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`. `init_transfer` accepts it: `0 < 500_000` passes. Transfer message is stored; tokens are locked.
3. Call `sign_transfer` for the stored `transfer_id`.
4. `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0` (floor division).
5. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — transaction reverts.
6. The transfer message remains in storage. Repeat step 3 indefinitely — always panics.
7. No `cancel_transfer` exists; `sign_transfer_callback` is never reached; `remove_transfer_message` is never called. Funds are permanently frozen.
