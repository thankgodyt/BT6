### Title
Excess NEAR Attached to `verify_deposit_v2` Standard-Path Call Is Silently Retained by the Contract - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`verify_deposit_v2` is marked `#[payable]` to support the safe-deposit path, which requires an attached NEAR deposit for token storage. When called with `deposit_msg.safe_deposit = None` (the standard deposit path), no NEAR is required. The function does not guard against a non-zero `env::attached_deposit()` in the standard path, so any NEAR accidentally attached by the caller is silently absorbed into the contract balance with no recovery mechanism.

---

### Finding Description

`verify_deposit_v2` dispatches to one of two internal paths based on `deposit_msg.safe_deposit`: [1](#0-0) 

- `Some(..)` → `internal_safe_verify_deposit_entry`, which enforces `env::attached_deposit() >= required_balance_for_safe_deposit()`
- `None` → `internal_verify_deposit_entry`, which requires **no NEAR** and performs **no deposit check at all** [2](#0-1) 

Because the outer function carries `#[payable]`, the NEAR runtime accepts any attached deposit regardless of which branch is taken. When the standard path (`safe_deposit = None`) is selected, `internal_verify_deposit_entry` neither inspects nor returns `env::attached_deposit()`. Any NEAR sent by the caller is permanently absorbed into the contract balance.

The safe-deposit path correctly enforces a minimum deposit: [3](#0-2) 

But the standard path has no analogous guard — not even a `require!(env::attached_deposit() == 0, ...)`.

The deprecated `verify_deposit` function is **not** `#[payable]` and is therefore not affected. Only `verify_deposit_v2` (and the deprecated `safe_verify_deposit` / `safe_verify_deposit_compact` variants, which always take the safe path) expose this surface.

---

### Impact Explanation

Any caller — relayer or otherwise — who attaches NEAR when invoking `verify_deposit_v2` with `safe_deposit = None` permanently loses that NEAR. The contract has no refund or recovery path for this case. This is harmful smart-contract behavior resulting in permanent, irrecoverable loss of caller funds without any direct theft by a third party.

---

### Likelihood Explanation

Low. Relayers are typically automated systems configured to send the correct deposit amount (zero for the standard path). However, `verify_deposit_v2` is publicly callable by any NEAR account with no role restriction beyond the `#[trusted_relayer]` confirmation-count adjustment. A misconfigured relayer, a developer testing the function, or any caller who mistakenly attaches NEAR (e.g., copy-pasting a safe-deposit call) will silently lose those funds. The loss is permanent and unrecoverable.

---

### Recommendation

In `verify_deposit_v2`, when `deposit_msg.safe_deposit.is_none()`, add an explicit guard before dispatching:

```rust
} else {
    require!(
        env::attached_deposit() == NearToken::from_yoctonear(0),
        "Standard deposit path does not accept an attached deposit"
    );
    self.internal_verify_deposit_entry(...)
}
```

Alternatively, split the function into two separate entry points: one `#[payable]` for the safe path and one non-payable for the standard path, eliminating the ambiguity entirely.

---

### Proof of Concept

1. Deploy the `satoshi-bridge` contract.
2. Construct a valid `DepositMsg` with `safe_deposit: None`.
3. Call `verify_deposit_v2` with a valid `tx_bytes` / `proof` **and** attach 1 NEAR.
4. The call succeeds (proof verifies, nBTC is minted normally).
5. The 1 NEAR is permanently retained by the contract — no event is emitted, no refund is issued, and no view function exposes the lost amount to the caller. [1](#0-0) [4](#0-3)

        tx_index: u64,

            .expect("Deserialization tx_bytes failed");

        require!(deposit_amount > 0, "Invalid deposit_amount");

            "Invalid deposit tx_bytes"
        );

        self.internal_verify_deposit(
