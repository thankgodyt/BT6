## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Token Causes Nonce Collision and Unauthorized Minting — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` before making an external `safeTransferFrom` call but never caches the incremented value into a local variable, reading `currentOriginNonce` again at both `initTransferExtension` and `emit` time. There is no reentrancy guard on the function. A malicious ERC1155 token can re-enter `initTransfer1155` during `safeTransferFrom`, causing `currentOriginNonce` to be incremented a second time so that both the inner and outer calls emit `InitTransfer` with the same nonce, enabling unauthorized minting of bridged tokens on NEAR with zero collateral locked on EVM.

## Finding Description

In `initTransfer1155` (lines 439–490 of `OmniBridge.sol`):

```
currentOriginNonce += 1;                    // L448 — incremented to N+1
...
IERC1155(tokenAddress).safeTransferFrom(    // L458 — external call, re-entry window
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...);  // L471 — reads live storage
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...);  // L483 — reads live storage
``` [1](#0-0) 

`currentOriginNonce` is never saved to a local variable after the increment. The function carries no `nonReentrant` modifier — the only reentrancy-related comments in the file are `slither-disable-next-line` annotations on unrelated paths. [2](#0-1) 

The `onERC1155Received` hook is declared `view` and only checks `operator != address(this)`. [3](#0-2) 

A malicious token's `safeTransferFrom` is not required to call `onERC1155Received` at all; it can call back directly into `initTransfer1155`, bypassing this check entirely.

**Reentrancy trace (starting nonce = N):**

| Step | `currentOriginNonce` | Action |
|---|---|---|
| Outer call enters | N+1 | incremented at L448 |
| Outer calls `safeTransferFrom` | N+1 | external call at L458 |
| Malicious token re-enters `initTransfer1155` | N+2 | inner call increments at L448 |
| Inner calls `safeTransferFrom` (no-op, depth guard) | N+2 | returns immediately |
| Inner emits `InitTransfer(nonce=N+2)` | N+2 | L483 reads storage |
| Inner call returns | N+2 | |
| Outer `safeTransferFrom` returns | N+2 | |
| Outer emits `InitTransfer(nonce=N+2)` | N+2 | L483 reads storage — **same nonce** |

Nonce N+1 is never emitted. Nonce N+2 is emitted twice. In `OmniBridgeWormhole`, `initTransferExtension` also passes `currentOriginNonce` (not a cached value) to `_wormhole.publishMessage`, so both the Wormhole message and the EVM event carry the colliding nonce. [4](#0-3) 

## Impact Explanation

The NEAR bridge's `add_fin_transfer` uses `origin_nonce` as part of `TransferId` and inserts it into `finalised_transfers`, panicking on duplicate insertion:

```rust
require!(
    self.finalised_transfers.insert(transfer_id),
    BridgeError::TransferAlreadyFinalised.as_ref()
);
``` [5](#0-4) 

The NEAR relayer submits proof of the first N+2 event (inner call — no ERC1155 tokens were actually locked on EVM). NEAR mints bridged tokens to the attacker. The second N+2 event proof is rejected as `TransferAlreadyFinalised`. The attacker receives minted tokens on NEAR with zero collateral locked on EVM — direct unauthorized minting and theft of bridged token supply. This matches the Critical impact class: **unauthorized minting and balance manipulation via nonce/replay misuse**.

## Likelihood Explanation

All three preconditions are permissionless:

1. Deploying a malicious ERC1155 token — no restrictions.
2. Calling `logMetadata1155` — no access control, open to any caller. [6](#0-5) 

3. Calling `initTransfer1155` — gated only by `whenNotPaused(PAUSED_INIT_TRANSFER)`, which is the normal operating state. [7](#0-6) 

No admin keys, oracle access, MPC collusion, or validator compromise is required. Any unprivileged EVM address can execute this end-to-end. The attack is repeatable as long as the bridge is unpaused.

## Recommendation

Cache `currentOriginNonce` into a local variable immediately after incrementing, before any external call, and use only the local variable for all subsequent reads within the same transaction:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // cache before external call

IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");

initTransferExtension(msg.sender, deterministicToken, nonce, ...);
emit BridgeTypes.InitTransfer(msg.sender, deterministicToken, nonce, ...);
```

Apply the identical fix to `initTransfer`, which has the same pattern — `currentOriginNonce` is read at `initTransferExtension` (L418) and `emit` (L430) after ERC20 external calls, with no local cache. [8](#0-7) 

Additionally, consider adding OpenZeppelin's `ReentrancyGuard` (`nonReentrant`) to both `initTransfer` and `initTransfer1155` as defense-in-depth.

## Proof of Concept

1. Deploy `MaliciousERC1155` with a `safeTransferFrom` that, on first invocation, re-enters `OmniBridge.initTransfer1155` once (depth flag prevents infinite recursion), then returns without transferring any tokens.
2. Call `OmniBridge.logMetadata1155(maliciousToken, tokenId)` → emits `LogMetadata`.
3. Submit light-client proof of the `LogMetadata` event to NEAR's `bind_token` → token registered.
4. Call `OmniBridge.initTransfer1155(maliciousToken, tokenId, amount, 0, 0, "near:attacker.near", "")`:
   - `currentOriginNonce` → N+1.
   - `safeTransferFrom` triggers re-entry into `initTransfer1155`:
     - Inner: `currentOriginNonce` → N+2; inner `safeTransferFrom` is no-op; emits `InitTransfer(nonce=N+2)`.
   - Outer resumes: emits `InitTransfer(nonce=N+2)`.
5. NEAR relayer submits proof of the first N+2 event → `add_fin_transfer` succeeds, mints `amount` tokens to `attacker.near`. Zero ERC1155 tokens were locked on EVM.
6. Second N+2 proof submission panics with `TransferAlreadyFinalised`. Nonce N+1 is permanently skipped.

A local Hardhat/Foundry test can confirm the double-emit by asserting that two `InitTransfer` events with identical `nonce` fields are emitted in a single transaction, and that the ERC1155 balance of `OmniBridge` does not increase.
