### Title
Missing Account Pending-List Cleanup in `clear_invalid_pending_verify_rbf` Allows Permanent Capacity Reduction - (File: contracts/satoshi-bridge/src/btc_pending_info.rs)

### Summary
`clear_invalid_pending_verify_rbf` is callable by any unprivileged account and removes a `BTCPendingInfo` entry from `btc_pending_infos` without removing the corresponding entry from the owning account's `btc_pending_sign_ids` and `btc_pending_verify_list` sets. This leaves permanently stale entries in the account's pending-capacity tracking state, analogous to the eigenPod report's pattern of removing a queue entry without verifying/clearing its associated balance state.

### Finding Description
`clear_invalid_pending_verify_rbf` (and its batch variant) carry only a `#[pause]` decorator — no `#[access_control_any]` and no `#[trusted_relayer]`. Any NEAR account can call it when the contract is unpaused. [1](#0-0) 

The internal implementation removes the `BTCPendingInfo` record from `btc_pending_infos` via `internal_remove_btc_pending_info`, then validates state — but never touches the owning account's `btc_pending_sign_ids` or `btc_pending_verify_list`: [2](#0-1) 

Every other removal path in the codebase performs this cleanup. `internal_remove_refund_pending_tx_id` explicitly removes from both account sets after calling `internal_remove_btc_pending_info`: [3](#0-2) 

`verify_refund_finalize_callback` similarly removes from `btc_pending_verify_list`: [4](#0-3) 

`internal_remove_btc_pending_info` itself only removes from `btc_pending_infos` and does nothing to account-level sets: [5](#0-4) 

After `clear_invalid_pending_verify_rbf` succeeds, the removed `btc_pending_id` remains in `account.btc_pending_sign_ids` and `account.btc_pending_verify_list` with no code path to remove it. `require_pending_sign_capacity` is called before every new pending-info creation and enforces a per-account limit against these sets: [6](#0-5) 

### Impact Explanation
Each stale entry permanently occupies one slot of the victim account's pending-transaction capacity. If an account has multiple RBF transactions cleaned up this way, its effective capacity shrinks by that count. Once the capacity reaches the configured maximum, the account can no longer initiate withdrawals, active UTXO management, or refunds — a stuck-state condition requiring operator intervention to resolve (there is no self-service path to remove the stale entries). This matches the **Low** allowed impact: publicly reachable invariant-violation causing a stuck bridge state.

### Likelihood Explanation
The preconditions are met in normal bridge operation: an original withdrawal is verified on-chain (removing its `rbf_txs` entry), while one or more RBF candidates remain in `PendingVerify` state. At that point any unprivileged caller can invoke `clear_invalid_pending_verify_rbf` on the victim's RBF `btc_pending_id`. No special knowledge beyond observing on-chain state is required.

### Recommendation
Mirror the cleanup performed by `internal_remove_refund_pending_tx_id`: after removing the `BTCPendingInfo`, retrieve the owning `account_id` from the removed record and call `account.btc_pending_sign_ids.remove(&btc_pending_id)` and `account.btc_pending_verify_list.remove(&btc_pending_id)` before returning.

### Proof of Concept
1. Alice initiates a withdrawal; the bridge creates `BTCPendingInfo` with id `orig_tx`.
2. Alice (or operator) creates a user-RBF; bridge creates `BTCPendingInfo` with id `rbf_tx`, and `rbf_txs["orig_tx"] = {"rbf_tx"}`. Alice's `btc_pending_sign_ids` now contains both `orig_tx` and `rbf_tx`.
3. `rbf_tx` is signed → moves to `PendingVerify` stage. `btc_pending_verify_list` now contains `rbf_tx`.
4. `orig_tx` is confirmed on-chain; `verify_withdraw_v2` is called → `rbf_txs` entry for `orig_tx` is removed. `orig_tx` is cleaned from Alice's account sets normally.
5. Attacker (any account) calls `clear_invalid_pending_verify_rbf("rbf_tx")`.
   - `internal_remove_btc_pending_info("rbf_tx")` succeeds — record deleted from `btc_pending_infos`.
   - `assert_pending_verify()` passes.
   - `!rbf_txs.contains_key("orig_tx")` passes (removed in step 4).
   - Function returns — **no cleanup of Alice's `btc_pending_sign_ids` or `btc_pending_verify_list`**.
6. Alice's `btc_pending_sign_ids` still contains `"rbf_tx"` and `btc_pending_verify_list` still contains `"rbf_tx"`, permanently consuming one capacity slot. If Alice's limit is 1, she can no longer create any new pending transactions.

    pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
        let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
        btc_pending_info.assert_pending_verify();
        let original_tx_id = btc_pending_info
            .get_original_tx_id()
            .expect("Not rbf transaction");
        require!(
            !self.data().rbf_txs.contains_key(original_tx_id),
            "Not invalid pending verify rbf"
        );
    }
