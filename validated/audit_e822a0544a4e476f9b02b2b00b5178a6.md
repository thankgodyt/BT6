### Title
Unrestricted Access to `clear_invalid_pending_verify_rbf` / `batch_clear_invalid_pending_verify_rbf` Causes Permanent Account Stuck-State - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` carry no role restriction — only a `#[pause]` guard — so any unprivileged NEAR account can invoke them. The internal helper `internal_clear_invalid_pending_verify_rbf` removes the `BTCPendingInfo` record from `btc_pending_infos` but never removes the corresponding entry from the owning account's `btc_pending_verify_list`. An attacker who calls either function on a legitimately stale RBF entry leaves the victim account with a dangling pointer in `btc_pending_verify_list`, permanently inflating the account's apparent pending-tx count and blocking future withdrawals.

### Finding Description
`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` are decorated only with `#[pause(except(roles(Role::DAO)))]` and carry no `#[access_control_any]` or `#[trusted_relayer]` guard: [1](#0-0) 

The internal implementation removes the `BTCPendingInfo` from `btc_pending_infos` but performs no cleanup of the account-level `btc_pending_verify_list`: [2](#0-1) 

Compare this with `internal_remove_refund_pending_tx_id`, which correctly removes from both `btc_pending_infos` and the account's `btc_pending_sign_ids` / `btc_pending_verify_list`: [3](#0-2) 

The guard inside `internal_clear_invalid_pending_verify_rbf` only checks that the original tx is absent from `rbf_txs` (i.e., the original was already verified on-chain). Once that condition is true, any caller — including an attacker — can remove the `BTCPendingInfo` record while leaving the stale ID in the victim's `btc_pending_verify_list`.

The account's `btc_pending_verify_list` is a `HashSet<String>` stored inside `VAccount`: [4](#0-3) 

Any code path that iterates or counts `btc_pending_verify_list` entries and then looks them up in `btc_pending_infos` will either panic (entry not found) or count the stale entry against the account's pending-tx capacity, permanently blocking new withdrawals for that account.

### Impact Explanation
After an attacker calls `clear_invalid_pending_verify_rbf` on a victim's stale RBF entry, the victim's `btc_pending_verify_list` contains an ID that no longer exists in `btc_pending_infos`. Any subsequent call that checks pending capacity or iterates the list will encounter the dangling reference, causing a stuck state that requires operator intervention to repair. No direct theft occurs, but the victim's bridge account is rendered non-functional for withdrawals.

This maps to: **Low — Publicly reachable invariant-violation / stuck-state in production bridge paths without direct theft.**

### Likelihood Explanation
Stale RBF pending-verify entries arise naturally whenever a user performs a `withdraw_rbf` and the original transaction is subsequently confirmed on-chain. At that point the RBF candidate remains in `btc_pending_infos` and `btc_pending_verify_list` until cleaned up. Any observer can detect this state (e.g., by watching `btc_pending_infos` via view calls) and immediately call `clear_invalid_pending_verify_rbf` before the legitimate off-chain relayer does, triggering the inconsistency for any victim account.

### Recommendation
1. Add a role restriction (`#[access_control_any(roles(Role::DAO, Role::Operator))]` or `#[trusted_relayer]`) to both `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`, consistent with every other state-mutating cleanup function in the contract.
2. Fix `internal_clear_invalid_pending_verify_rbf` to also remove the entry from the owning account's `btc_pending_verify_list`, mirroring the pattern used in `internal_remove_refund_pending_tx_id`.

### Proof of Concept
1. Alice initiates a withdrawal; the bridge creates `BTCPendingInfo` with id `W`.
2. Alice calls `withdraw_rbf`; the bridge creates RBF entry `R` with `original_tx_id = W`.
3. The original tx `W` is confirmed on-chain via `verify_withdraw_v2`; `rbf_txs` entry for `W` is removed. `R` is now stale.
4. Attacker calls `clear_invalid_pending_verify_rbf("R")`. The check `!rbf_txs.contains_key("W")` passes. `btc_pending_infos["R"]` is deleted, but Alice's `btc_pending_verify_list` still contains `"R"`.
5. Alice attempts a new withdrawal. Any capacity check that reads `btc_pending_verify_list` counts the dangling `"R"`, blocking Alice from initiating further withdrawals — a stuck state requiring operator intervention. [1](#0-0) [2](#0-1)

    pub(crate) fn internal_remove_refund_pending_tx_id(&mut self, tx_id: String) {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_related();

        // A refund spends exactly one deposit UTXO, whose key is the refund request key.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        require!(
            !self
                .data()
                .refund_requests
                .contains_key(&utxo_storage_keys[0]),
            "refund request still active"
        );

        let account_id = btc_pending_info.account_id.clone();
        self.internal_remove_btc_pending_info(&tx_id);
        let account = self.internal_unwrap_mut_account(&account_id);
        account.btc_pending_sign_ids.remove(&tx_id);
        account.btc_pending_verify_list.remove(&tx_id);
    }
