Audit Report

## Title
ERC1155 `finTransfer` Permanently Freezes Bridged Tokens When Recipient Contract Lacks `IERC1155Receiver` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.finTransfer` delivers ERC1155 tokens via `IERC1155.safeTransferFrom`, which mandates that contract recipients implement `onERC1155Received`. If `payload.recipient` is a contract without this interface, every finalization attempt reverts. Because the recipient is cryptographically bound in the MPC-signed payload and no cancel or refund path exists in the contract, the ERC1155 tokens locked on the source chain by `initTransfer1155` are permanently frozen.

## Finding Description

In `finTransfer`, the ERC1155 delivery branch executes:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per EIP-1155, `safeTransferFrom` calls `onERC1155Received` on any contract recipient and reverts if the correct selector is not returned. There is no `try/catch` around this call and no pre-flight `supportsInterface` check. The call at line 287 sets `completedTransfers[payload.destinationNonce] = true` before the transfer, but because the entire transaction reverts on failure, this state change is also rolled back — meaning the nonce is never consumed and the transfer can never be finalized.

The source-chain lock is performed in `initTransfer1155` (lines 458–464), which transfers custody of the ERC1155 tokens to the bridge before any destination-side action. The MPC signature covers `payload.recipient` (line 298), making it immutable. No `cancel`, `rescue`, `refund`, or `withdraw` function exists anywhere in `OmniBridge.sol` to recover locked ERC1155 tokens.

## Impact Explanation

This concretely matches the allowed critical impact: **permanent freezing of bridged funds**. The source-chain ERC1155 tokens are locked in the bridge with no on-chain recovery path. Every `finTransfer` attempt reverts, the nonce is never consumed, no alternative recipient can be substituted (payload is MPC-signed), and no relayer can ever successfully finalize the transfer. The tokens are irrecoverably frozen in the current contract code.

## Likelihood Explanation

Contract addresses are routine bridge recipients: Gnosis Safe multisigs, DAO treasuries, protocol vaults, and smart-contract wallets. Many of these do not implement `IERC1155Receiver`. Any token holder calling `initTransfer1155` with such a contract as recipient triggers the freeze. No special privilege, attacker cooperation, or unusual condition is required — it is a normal user action through a public function.

## Recommendation

Replace the bare `safeTransferFrom` with a pattern that handles non-receiver contracts gracefully:

1. **Try/catch with escrow**: Wrap the `safeTransferFrom` in a `try/catch`; on failure, store the tokens in a per-recipient claimable balance that the recipient can pull later.
2. **Pre-flight interface check**: Before calling `safeTransferFrom`, call `IERC165(payload.recipient).supportsInterface(type(IERC1155Receiver).interfaceId)` and fall back to a pull-payment escrow if it returns `false`.
3. **Add a cancel/refund path**: Implement a mechanism (e.g., MPC-signed cancellation) that allows the source-chain bridge to release locked ERC1155 tokens when finalization is provably impossible.

## Proof of Concept

1. User holds ERC1155 `(tokenAddress, tokenId=1)` on the source EVM chain.
2. User calls `initTransfer1155(tokenAddress, 1, 100, 0, 0, "RecipientContract", "")` where `RecipientContract` on the destination chain is a Gnosis Safe or similar contract without `onERC1155Received`. 100 units of token ID 1 are now held by `OmniBridge`.
3. NEAR MPC signs the transfer payload with `recipient = RecipientContract`.
4. Relayer calls `finTransfer(sig, payload)` on the destination chain.
5. `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), RecipientContract, 1, 100, "")` is executed.
6. The ERC1155 contract calls `RecipientContract.onERC1155Received(...)` — reverts because `RecipientContract` has no such function.
7. The entire `finTransfer` transaction reverts; `completedTransfers[nonce]` remains `false`.
8. No alternative recipient can be substituted (payload is MPC-signed). No refund path exists.
9. The 100 ERC1155 tokens are permanently locked in the source-chain `OmniBridge`.

A local integration test can reproduce this by deploying a mock ERC1155 token, a mock recipient contract without `IERC1155Receiver`, calling `initTransfer1155`, constructing a valid MPC-signed payload, and asserting that `finTransfer` always reverts while the bridge's token balance remains non-zero with no recovery function callable.
