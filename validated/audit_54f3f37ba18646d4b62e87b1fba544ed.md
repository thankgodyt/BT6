Audit Report

## Title
Native ETH `finTransfer` reverts on recipient failure, permanently freezing bridged funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

In `OmniBridge.finTransfer`, when `payload.tokenAddress == address(0)`, native ETH is pushed to `payload.recipient` via an uncapped `.call{value: payload.amount}("")`. If the recipient's fallback reverts, `FailedToSendEther` is thrown, rolling back the entire transaction including the `completedTransfers[payload.destinationNonce] = true` write that was set earlier in the same function. Because the nonce is never durably marked, every subsequent relay attempt fails identically, and the tokens already burned or locked on NEAR during `init_transfer` are permanently unrecoverable.

## Finding Description

`finTransfer` marks the nonce at line 287 before performing the ETH transfer:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
```

Later, for native ETH (`tokenAddress == address(0)`):

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();              // lines 319-322
```

A revert at line 322 rolls back the entire EVM transaction, including the nonce write at line 287. The nonce is therefore never durably stored. Every subsequent relay attempt reaches the same reverting recipient and fails identically. There is no pull-payment fallback, no `rescueETH` function, and no cancel/refund path in the NEAR hub (`cancel_transfer`, `refund_transfer`, `unlock_on_failure` — none exist in the codebase) that would release the tokens when EVM finalization is permanently blocked.

On the NEAR side, `init_transfer_internal` calls `burn_tokens_if_needed` and `lock_tokens_if_needed` before emitting the `InitTransferEvent`. Once those state changes are committed on NEAR, the only recovery path is a successful `finTransfer` on EVM. If that can never succeed, the burned/locked tokens are gone.

## Impact Explanation

Tokens burned or locked on NEAR during `init_transfer` are permanently unrecoverable when EVM `finTransfer` is blocked by a reverting recipient. This is a concrete, irreversible loss of bridged funds matching the Critical impact: **permanent freezing of bridged funds across NEAR → EVM flows**.

## Likelihood Explanation

Any user who specifies a smart-contract wallet, multisig, DAO treasury, or protocol contract that lacks a `payable` fallback as the EVM recipient will trigger this path. An adversary can also deliberately deploy a contract whose fallback always reverts and specify it as the recipient when initiating a transfer on NEAR. No special privilege is required — the `recipient` field is freely chosen by the initiator of the NEAR-side transfer.

## Recommendation

1. **Pull-over-push**: On send failure, store the unclaimed ETH in a `mapping(address => uint256)` and allow the recipient to withdraw it later. This ensures the nonce is durably marked as used and the transfer is considered finalized even if the immediate ETH push fails.
2. **Do not revert on send failure**: Replace `revert FailedToSendEther()` with a storage write to a pending-withdrawals mapping, so the nonce write at line 287 is preserved.
3. **Cap forwarded gas**: Use `call{gas: 2300, value: payload.amount}` to prevent gas-griefing by a malicious recipient fallback.

## Proof of Concept

1. Deploy `MaliciousRecipient` on EVM with `fallback() external payable { revert(); }`.
2. On NEAR, call `ft_transfer_call` (or equivalent) to initiate a NEAR → EVM native ETH transfer specifying `MaliciousRecipient` as the EVM recipient. NEAR burns/locks the corresponding wrapped-ETH tokens.
3. MPC signs the `TransferMessagePayload` (standard protocol behavior for a valid transfer).
4. Relayer calls `OmniBridge.finTransfer` with the signed payload.
5. Line 287 writes `completedTransfers[payload.destinationNonce] = true`.
6. Line 319 executes `payload.recipient.call{value: payload.amount}("")` → `MaliciousRecipient.fallback()` reverts.
7. Line 322: `success == false` → `revert FailedToSendEther()` rolls back the entire transaction, including the nonce write at line 287.
8. Relayer retries → identical outcome. Transfer is permanently unfinalizeable. Tokens on NEAR are frozen.

A Foundry test can reproduce this with a mock `MaliciousRecipient` contract and a forked or local `OmniBridge` instance, asserting that `completedTransfers[nonce]` remains `false` after every relay attempt.
