### Title
Peras Certificate Validation Stub Always Accepts Any Certificate, Enabling Unauthorized Chain Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types contains a `validatePerasCert` implementation that unconditionally returns `Right` — accepting every certificate without performing any cryptographic or semantic checks. An unprivileged peer can send a crafted Peras certificate over the ObjectDiffusion mini-protocol; it will be accepted, stored in the `PerasCertDB`, and its weight boost will be applied during chain selection, potentially causing an honest node to prefer a non-canonical chain.

### Finding Description

The structural analog to the external report is exact: just as a disabled oracle silently returns a zero value that propagates unchecked into weight calculations, `validatePerasCert` silently returns a "valid" result for any certificate, and that result propagates unchecked into Peras chain-selection weight calculations.

**Root cause — the stub validator:**

**Inbound path — `processCerts` trusts the validator:**

The ObjectDiffusion inbound handler calls `validatePerasCert` and, if it returns `Right`, adds the certificate to the database. Since the stub always returns `Right`, every certificate from every peer is accepted.

```haskell

  processCerts
    systemTime
    (ChainDB.getPerasCertIds chainDB)
    (validatePerasCert mkPerasParams)   -- always Right
    (void . ChainDB.addPerasCertAsync chainDB)
    certs
``` [2](#0-1) 

`processCerts` partitions results and only rejects a batch when `Left` values appear. Because `validatePerasCert` never produces `Left`, the entire batch is always accepted: [3](#0-2) 

**Weight propagation — accepted cert boosts chain selection:**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` from every certificate in `pcdsCertsByTicket`, including the attacker-injected one: [4](#0-3) 

`chainSelectionForBlock` reads this snapshot atomically and passes it directly to `constructPreferableCandidates` and `preferAnchoredCandidate`: [5](#0-4) 

`preferCandidate` for `WeightedSelectView` compares `wsvTotalWeight`, which sums block count and the Peras weight boost. A fraudulent boost can make a shorter or otherwise non-preferred fork appear heavier: [6](#0-5) 

### Impact Explanation

An attacker controlling any peer connection can inject a certificate that boosts an arbitrary block point. If the boosted point lies on a fork the attacker is serving, the honest node's chain selection will compute a higher `wsvTotalWeight` for that fork and switch to it, accepting a non-canonical chain. This is a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**, matching the "High" impact tier. If the attacker can also influence which block is boosted to be one that has not been fully validated, this escalates toward invalid-block acceptance.

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is reachable from any peer. No key material, stake, or operator privilege is required. The only precondition is that the Peras feature is active. The stub is in the default `instance StandardHash blk => BlockSupportsPeras blk`, so it applies to all block types including `CardanoBlock`. Likelihood is **medium-high** once Peras is deployed, and the attack requires only sending a single crafted certificate message.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature over `(roundNo, boostedBlock)`.
2. That the signers form a quorum of the committee for the claimed round.
3. That the boosted block point exists and is within the valid boost window.

Until real validation is implemented, `processCerts` should treat an unimplemented validator as a hard error rather than silently accepting all certificates. The TODO at `https://github.com/tweag/cardano-peras/issues/120` tracks this work and must be resolved before Peras certificates are accepted from untrusted peers.

### Proof of Concept

1. Connect to a target node as a peer via the ObjectDiffusion mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = P` where `P` is the tip of a fork you are serving.
3. Send the certificate. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored; `getWeightSnapshot` now returns a snapshot with a boost of `perasWeight params` at point `P`.
5. When the node next runs chain selection (e.g., upon receiving the next block on your fork), `preferAnchoredCandidate` computes `wsvTotalWeight` including the boost and switches to your fork.
6. The node has adopted a non-canonical chain driven entirely by an unauthenticated certificate.
