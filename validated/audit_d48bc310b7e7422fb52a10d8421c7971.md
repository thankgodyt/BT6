### Title
Unprivileged User Can Front-Run `request_refund` to Block Legitimate Refund Requests - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

An unprivileged NEAR account can front-run any legitimate `request_refund` call by submitting their own request for the same UTXO with an attacker-controlled `refund_address`. A uniqueness precondition in `request_refund_callback` then causes the legitimate user's callback to revert, permanently blocking their refund until a privileged operator manually rejects the attacker's entry. If the operator fails to act before `unsafe_refund_timelock_sec` elapses, the attacker can execute the refund and redirect the victim's BTC to their own address.

---

### Finding Description

`request_refund_callback` enforces a uniqueness invariant before storing a new refund request:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 544-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [1](#0-0) 

The public `request_refund` entry-point (which calls `internal_request_refund`) has **no caller-binding access control** — the only gate is an attached NEAR storage deposit:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 146-149
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the caller may supply **any** `refund_address`; the contract only enforces a match when the field is pre-set:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

The `deposit_msg` is passed as a plain call parameter, making it visible in the NEAR mempool before the transaction is finalized. An attacker who observes a pending `request_refund` call can:

1. Extract `deposit_msg`, `tx_bytes`, `vout`, and `proof` from the mempool.
2. Re-submit `request_refund` with the **same UTXO** but `refund_address = attacker_btc_address`, attaching a higher gas price so their transaction is processed first.
3. The attacker's `request_refund_callback` succeeds and inserts a `RefundRequest` keyed by `utxo_storage_key` with the attacker's address.
4. The victim's `request_refund_callback` then hits the uniqueness check and reverts: `"Refund request already exists for this UTXO"`.

The victim's BTC is now locked. The only recovery path is for a privileged `RefundOperator` or `DAO` account to call `internal_reject_refund`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 187-196
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [4](#0-3) 

If the operator does not reject the attacker's request before `unsafe_refund_timelock_sec` elapses (the longer timelock applied when `deposit_msg.refund_address` is `None`), the attacker may call `execute_refund`. The bridge will then build and MPC-sign a Bitcoin transaction paying the attacker's address, and the victim's BTC is stolen.

The timelock path is confirmed in `resolve_execute_refund_timelock`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 223-228
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [5](#0-4) 

---

### Impact Explanation

**Medium (DoS / temporary fund lock):** The victim's refund is blocked until a privileged operator manually rejects the attacker's entry. This requires operator intervention and introduces indefinite delay.

**Critical escalation (fund theft):** If the operator is slow, offline, or the attacker repeats the front-run after each rejection, the attacker can eventually let `unsafe_refund_timelock_sec` expire, call `execute_refund`, and receive the victim's BTC at their own address. This constitutes a direct theft of user funds bridged through the protocol.

---

### Likelihood Explanation

**Medium.** NEAR transaction parameters are visible in the mempool before finalization. The attacker only needs to pay a small NEAR storage deposit (non-refundable on rejection, but negligible relative to BTC value). The attack is economically rational for any UTXO whose BTC value exceeds the storage deposit cost. No privileged access, leaked keys, or third-party compromise is required.

---

### Recommendation

**Short term:** Bind the refund request to `env::predecessor_account_id()` at submission time and store it as part of the request. In `request_refund_callback`, reject any submission where the stored caller does not match the current predecessor, or enforce that only one account may hold a pending refund request per UTXO.

**Long term:** Require `deposit_msg.refund_address` to be set at deposit time (e.g., embedded in the Bitcoin transaction's OP_RETURN output). This eliminates the attacker's ability to supply an arbitrary `refund_address`, since the check at lines 154–159 would then enforce the pre-authorized address.

---

### Proof of Concept

1. **Alice** sends BTC to a bridge deposit address derived from `deposit_msg` where `refund_address = None`.
2. The deposit fails (e.g., Alice's nBTC account is not registered). Alice calls:
   ```
   request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)
   ```
3. **Eve** monitors the NEAR mempool, extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof` from Alice's pending call.
4. Eve submits:
   ```
   request_refund(deposit_msg, eve_btc_addr, tx_bytes, vout, proof, None)
   ```
   with a higher gas price, causing her transaction to be processed first.
5. Eve's `request_refund_callback` passes all checks and inserts `RefundRequest { refund_address: eve_btc_addr, ... }` keyed by `utxo_storage_key`.
6. Alice's `request_refund_callback` hits line 544–547 and reverts: `"Refund request already exists for this UTXO"`. Alice's BTC is now locked.
7. If the DAO does not call `reject_refund` before `unsafe_refund_timelock_sec` elapses, Eve calls `execute_refund`. The bridge builds and signs a Bitcoin transaction paying `eve_btc_addr`, and Eve receives Alice's BTC.
