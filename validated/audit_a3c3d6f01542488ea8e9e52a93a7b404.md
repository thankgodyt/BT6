### Title
Batch Peras Vote/Certificate Rejection Suppresses Valid Votes, Preventing Certificate Formation and Weakening Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

`processVotes` and `processCerts` implement an all-or-nothing batch policy: if any single vote or certificate in an inbound batch fails validation, the **entire batch is thrown away** and a `PerasVoteInboundException` / `PerasCertInboundException` is raised. An unprivileged peer can exploit this by bundling one crafted-invalid vote alongside legitimate votes it has collected from the network. The receiving node discards all votes in the batch — including the valid ones — permanently suppressing them from the `PerasVoteDB`. Repeated across multiple peers or rounds, this prevents Peras quorum from being reached, blocking certificate formation and stripping the Peras weight boost from the canonical chain, which weakens chain selection security.

---

### Finding Description

`processVotes` in `PerasVote.hs` validates all votes in a batch atomically inside a single STM transaction, then uses `partitionEithers` to split results: [1](#0-0) 

The comment at line 165 explicitly documents the policy:

> "if /any/ vote in the batch fails validation, the entire batch is rejected by throwing a `PerasVoteInboundException`" [2](#0-1) 

The same pattern exists verbatim in `processCerts`: [3](#0-2) 

The `opwAddObjects` field of `ObjectPoolWriter` is the interface called by `objectDiffusionInbound` when a batch of downloaded objects is ready: [4](#0-3) 

This is wired into the live node-to-node handler for the Peras vote diffusion mini-protocol: [5](#0-4) 

`PerasVoteInboundException` and `PerasCertInboundException` are **not listed** in `consensusRethrowPolicy`, so the default policy applies: disconnect the peer but allow reconnect after ~10–20 s. [6](#0-5) 

The valid votes that were in the rejected batch are **never retried** — they are simply lost. The `PerasVoteDB` deduplication filter (`alreadyInDbSTM`) means that even if the same votes arrive later in a clean batch from another peer, they will only be accepted if that peer happens to send them before the round window closes.

---

### Impact Explanation

Peras certificates provide a weight boost (`perasWeight`) to the chain they certify. This boost is the core chain-selection security mechanism of Peras: it makes the certified chain heavier and harder to displace. [7](#0-6) 

Certificate formation requires a quorum of validated votes for the same target: [8](#0-7) 

If an attacker suppresses enough votes to prevent quorum, no certificate is forged for that round. The chain loses the Peras weight boost, making it easier for an adversary's competing chain (which has not had its votes suppressed) to appear heavier in chain selection. This is a chain-selection security degradation that goes beyond the intended Peras security assumptions.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node operate without the Peras weight boost, weakening chain selection security beyond intended assumptions.

---

### Likelihood Explanation

- The attacker needs only a standard node-to-node connection — no stake, no keys, no admin access.
- The object diffusion protocol allows the peer to control the contents of each batch it sends.
- The attacker can collect legitimate votes from other peers (they are broadcast) and bundle them with one crafted-invalid vote.
- After disconnection, the attacker can reconnect within ~10–20 s and repeat for the next batch.
- A single attacker connected to a victim node can suppress votes from every batch it delivers, across every Peras round, indefinitely.
- The code comment at line 197–199 itself acknowledges the assumption that "vote validation is cheap, which may not be true in practice" and flags a potential revisit — indicating the design is known to be provisional. [9](#0-8) 

---

### Recommendation

**Short term:** Replace the all-or-nothing batch rejection with a per-vote NoThrow variant: validate each vote individually, silently drop invalid ones (or log them), and add all valid votes to the pool. Only disconnect the peer if the batch contains a vote that is structurally malformed (e.g., fails deserialization), not merely one that fails stake-distribution lookup.

**Long term:** Add `PerasVoteInboundException` and `PerasCertInboundException` to `consensusRethrowPolicy` with an explicit `theyBuggyOrEvil` policy so that the peer-management layer handles them consistently. Audit all other batch-processing paths in the object diffusion layer for the same pattern.

---

### Proof of Concept

1. Attacker node connects to victim via the Peras vote diffusion mini-protocol (`hPerasVoteDiffusionClient`).
2. Attacker collects N legitimate votes for round R from other peers on the network (votes are broadcast).
3. Attacker constructs a batch containing those N legitimate votes plus one vote with a `pvVoteVoterId` not present in the victim's `PerasVoteStakeDistr` (guaranteed to fail `validatePerasVote` since `lookupPerasVoteStake` returns `Nothing`). [10](#0-9) 

4. Victim calls `processVotes` on the batch. `partitionEithers` finds one `Left` error. `throw (PerasVoteValidationError errs)` is called. All N legitimate votes are discarded.
5. Victim disconnects attacker. Attacker reconnects after ~10–20 s and repeats for round R+1.
6. No Peras certificate is ever formed for any round the attacker targets. The canonical chain loses all Peras weight boosts. Chain selection operates as if Peras were disabled.

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```

```haskell
consensusRethrowPolicy ::
  forall blk.
  (Typeable blk, StandardHash blk) =>
  Proxy blk ->
  RethrowPolicy
consensusRethrowPolicy pb =
  mkRethrowPolicy (\_ctx (_ :: DbMarkerError) -> shutdownNode)
    -- Any exceptions in the storage layer should terminate the node
    --
    -- NOTE: We do not catch IOExceptions here; they /ought/ to be caught
    -- by the FS layer (and turn into FsError). If we do want to catch
    -- them, we'd somehow have to distinguish between IO exceptions
    -- arising from disk I/O (shutdownNode) and those arising from
    -- network failures (SuspendConsumer).
    <> mkRethrowPolicy (\_ctx (_ :: DbMarkerError) -> shutdownNode)
    <> mkRethrowPolicy (\_ctx (_ :: DbLocked) -> shutdownNode)
    <> mkRethrowPolicy (\_ctx (_ :: ChainDbFailure blk) -> shutdownNode)
    <> mkRethrowPolicy
      ( \_ctx (e :: VolatileDBError blk) ->
          case e of
            VolatileDB.ApiMisuse{} -> ourBug
            VolatileDB.UnexpectedFailure{} -> shutdownNode
      )
    <> mkRethrowPolicy
      ( \_ctx (e :: ImmutableDBError blk) ->
          case e of
            ImmutableDB.ApiMisuse{} -> ourBug
            ImmutableDB.UnexpectedFailure{} -> shutdownNode
      )
    <> mkRethrowPolicy (\_ctx (_ :: FsError) -> shutdownNode)
    -- When the system clock moved back, we have to restart the node.
    <> mkRethrowPolicy (\_ctx (_ :: SystemClockMovedBackException) -> shutdownNode)
    -- Some chain DB errors are indicative of a bug in our code, others
    -- indicate an invalid request from the peer. If the DB is closed
    -- entirely, it will only be reopened after a node restart.
    <> mkRethrowPolicy
      ( \_ctx (e :: ChainDbError blk) ->
          case e of
            ClosedDBError{} -> shutdownNode
            ClosedFollowerError{} -> ourBug
            InvalidIteratorRange{} -> theyBuggyOrEvil
      )
    -- We have some resource registries that are used per-connection,
    -- and so if we have ResourceRegistry related exception, we close
    -- the connection but leave the rest of the node running.
    <> mkRethrowPolicy (\_ctx (_ :: RegistryClosedException) -> ourBug)
    <> mkRethrowPolicy (\_ctx (_ :: ResourceRegistryThreadException) -> ourBug)
    <> mkRethrowPolicy (\_ctx (_ :: TempRegistryException) -> ourBug)
    -- An exception in the block fetch server meant the client asked
    -- for some blocks we used to have but got GCed. This means the
    -- peer is on a chain that forks off more than @k@ blocks away.
    <> mkRethrowPolicy (\_ctx (_ :: BlockFetchServerException) -> distantPeer)
    -- Peras components as part of the ChainDB can create exceptions, see
    -- https://github.com/tweag/cardano-peras/issues/216
    <> mkRethrowPolicy
      ( \_ctx (e :: PerasVoteDbError blk) ->
          case e of
            MultipleWinnersInRound{} -> ourBug -- TODO: should we instead shutdown the node?
            ForgingCertError{} -> ourBug
      )
    -- Some chain sync client exceptions indicate malicious behaviour,
    -- others merely mean that we should disconnect from this client
    -- because we have diverged too much.
    <> mkRethrowPolicy (\_ctx (_ :: ChainSyncClientException) -> theyBuggyOrEvil)
    -- Dispatch on nested exception
    <> mkRethrowPolicy
      ( \ctx (ExceptionInLinkedThread _ e) ->
          runRethrowPolicy (consensusRethrowPolicy pb) ctx e
      )
```

```haskell
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```
