### Title
Unprivileged Attacker Can Redirect Victim's BTC Refund to Attacker-Controlled Address via `request_refund` with `refund_address: None` DepositMsg — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
When a victim's `DepositMsg` has `refund_address: None`, any unprivileged caller can submit a `request_refund` for that victim's deposit UTXO while supplying an attacker-controlled BTC address as `refund_address`. The address-binding check is skipped entirely when `deposit_msg.refund_address` is `None`, and the script_pubkey verification only confirms the UTXO belongs to the path derived from the supplied `deposit_msg` — it does not verify the caller is the original depositor.

### Finding Description
`internal_request_refund` enforces address binding only when `deposit_msg.refund_address` is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `refund_address` is `None`, the block is skipped entirely. The subsequent `request_refund_callback` verifies only that the on-chain output's `script_pubkey` matches the address derived from the supplied `deposit_msg`. Since the attacker supplies the same `deposit_msg` as the victim (with `refund_address: None`), `get_deposit_path` produces the same hash, `generate_utxo_chain_address` produces the same address, and the check passes. The `RefundRequest` is then stored with the attacker's `refund_address`. There is no check that `env::predecessor_account_id()` matches any depositor identity.

### Impact Explanation
After `unsafe_refund_timelock_sec` elapses (and if DAO/Operator does not reject the request), anyone can call `execute_refund`, which builds a PSBT paying `refund_amount` to the stored `refund_address` — the attacker's BTC address. The victim's BTC is permanently redirected to the attacker. This is theft of user funds.

### Likelihood Explanation
- The victim's `deposit_msg` is publicly observable via the `LogDepositAddress` event emitted by `get_user_deposit_address`, or from any prior `verify_deposit` call on-chain.
- The victim's deposit transaction is publicly visible on the Bitcoin blockchain.
- The attacker needs only to attach the required NEAR storage deposit and supply a valid BTC inclusion proof (all public data).
- The only defense is DAO/Operator actively monitoring and rejecting the request within `unsafe_refund_timelock_sec`. If they miss it, the attack succeeds.
- Deposits with `refund_address: None` are the common case (the field is optional and defaults to absent).

### Recommendation
In `internal_request_refund`, when `deposit_msg.refund_address` is `None`, require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` (the NEAR account that made the deposit), or alternatively require that `deposit_msg.refund_address` always be set (non-`None`) so the address is cryptographically bound to the deposit path at deposit time. The `unsafe_refund_timelock_sec` is a useful defense-in-depth measure but must not be the sole protection against address substitution.

### Proof of Concept
1. Victim calls `get_user_deposit_address(DepositMsg{recipient_id: "victim.near", refund_address: None, ...})` — emits event with full `deposit_msg` and derived BTC address.
2. Victim sends BTC to that address; the deposit transaction is confirmed on Bitcoin.
3. Victim never calls `verify_deposit` (e.g., the relayer fails, or the victim abandons the deposit).
4. Attacker observes the event and the Bitcoin transaction.
5. Attacker calls `request_refund(deposit_msg=DepositMsg{recipient_id:"victim.near", refund_address:None,...}, refund_address="attacker_btc_addr", tx_bytes=<victim_tx>, vout=0, proof=<valid_proof>)` with sufficient NEAR attached.
6. `internal_request_refund`: `deposit_msg.refund_address` is `None` → address check skipped.
7. `request_refund_callback`: `get_deposit_path(deposit_msg)` → same path as victim's deposit → `script_pubkey` matches → `RefundRequest` stored with `refund_address = "attacker_btc_addr"`.
8. After `unsafe_refund_timelock_sec` (if DAO does not reject), attacker or anyone calls `execute_refund`.
9. BTC is sent to `"attacker_btc_addr"`. Victim's funds are stolen.
