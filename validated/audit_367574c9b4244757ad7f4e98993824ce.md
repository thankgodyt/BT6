Audit Report

## Title
Sub-Unit Transfer Amount Permanently Freezes Bridged Funds — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates only that `fee.fee < amount`, allowing a transfer where `amount - fee` normalizes to zero on the destination chain. Once stored in `pending_transfers` and tokens burned/locked by `init_transfer_internal`, the transfer can never be signed (because `sign_transfer` hard-panics on a zero normalized amount) and no cancellation or refund path exists, permanently freezing the user's funds.

## Finding Description

**Root cause:** The normalization check is present in `sign_transfer` but absent from `init_transfer`/`init_transfer_internal`.

`init_transfer` enforces only: [1](#0-0) 

`init_transfer_internal` then burns or locks the full `amount` before any normalization is applied: [2](#0-1) 

Later, `sign_transfer` calls `normalize_amount` using floor division: [3](#0-2) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the result is `0`, and `sign_transfer` hard-panics: [4](#0-3) 

This panic is deterministic — the same inputs always produce the same result. The only removal paths for a pending outbound transfer are:

- `sign_transfer_callback` — only reached on MPC signing success, which requires `sign_transfer` to not panic first: [5](#0-4) 
- `claim_fee_callback` — requires proof of a `FinTransfer` event on the destination chain, which can never exist because the transfer was never signed: [6](#0-5) 

No `cancel_transfer` or `refund_transfer` function exists anywhere in `lib.rs`. `update_transfer_fee` can only increase the fee (`fee.fee >= current_fee.fee`), making `amount_without_fee` smaller and worsening the condition: [7](#0-6) 

## Impact Explanation

This is **permanent freezing of bridged funds**. Once `init_transfer_internal` burns or locks the user's tokens and stores the transfer, there is no on-chain path to recover them. The transfer is stuck in `pending_transfers` indefinitely. This matches the allowed Critical impact: *permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet*.

## Likelihood Explanation

Any token whose NEAR-side `origin_decimals` exceeds its destination `decimals` (e.g., `origin_decimals = 24`, `decimals = 18`, `diff = 6`) is affected. A user sending fewer than `10^6` base units — a realistic small transfer for a high-precision token — triggers the freeze. The user needs no special privileges; the attack path is a standard `ft_transfer_call` from any token holder. The condition is repeatable and deterministic.

## Recommendation

Add a normalization check inside `init_transfer` (or at the top of `init_transfer_internal`) before storing the transfer and burning/locking tokens:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing check in `sign_transfer` but must be enforced at creation time, before tokens are burned/locked and the transfer is stored in `pending_transfers`.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (diff = 6).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`, destination = any EVM address.
3. `init_transfer` passes: `0 < 500_000`. ✓
4. `init_transfer_internal` burns 500,000 tokens and stores the transfer in `pending_transfers`.
5. Relayer calls `sign_transfer`. `normalize_amount(500_000, diff=6)` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0)` panics → `InvalidAmountToTransfer`.
7. Transfer remains in `pending_transfers` forever. Tokens are permanently burned. No recovery path exists.

A unit test can be written against the NEAR contract in the existing test suite: initialize a token with the above decimals, call `ft_transfer_call` with a sub-unit amount, then assert that `sign_transfer` panics and that the transfer ID remains in `pending_transfers` with no callable removal function.
