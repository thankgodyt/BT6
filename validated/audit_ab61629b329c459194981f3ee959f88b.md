### Title
LoP Bucket Level Unconditionally Reset to Full Capacity on GSM State Transition Allows Adversarial Peer to Evade Patience Enforcement - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs)

---

### Summary

The `updateLopBucketConfig` function in the ChainSync client unconditionally resets the Limit on Patience (LoP) leaky bucket to **full capacity** whenever the Genesis State Machine (GSM) transitions back to `Syncing`, permanently discarding all accumulated patience debt for every connected peer. An adversarial peer can exploit this by repeatedly cycling the GSM between `PreSyncing` and `Syncing` (e.g., by being the only peer and disconnecting/reconnecting), resetting its LoP bucket each time and evading the patience enforcement mechanism indefinitely.

---

### Finding Description

The Limit on Patience (LoP) mechanism uses a leaky token bucket to disconnect peers that withhold headers during Genesis sync. The bucket drains at a constant rate (`csbcRate`); when a peer sends a valid header, the bucket is refilled by one token. If the bucket empties, the peer is disconnected via `throwIO EmptyBucket`.

The `updateLopBucketConfig` function is called on every GSM state change:

```haskell
-- NOTE: The new level is currently the maximal capacity of the bucket;
-- maybe we want to change that later.
updateLopBucketConfig :: LeakyBucket.Handlers m -> GsmState -> Time -> STM m ()
updateLopBucketConfig lopBucket gsmState =
  LeakyBucket.updateConfig lopBucket $ \_ ->
    let config = lopBucketConfig gsmState
     in (LeakyBucket.capacity config, config)
```

The lambda `\_ ->` **ignores the current bucket level** (`oldLevel`) entirely and always sets the new level to `LeakyBucket.capacity config`. When `gsmState = Syncing`, this is the full capacity `csbcCapacity` (default 100,000 tokens). When `gsmState = PreSyncing` or `CaughtUp`, `lopBucketConfig` returns `dummyConfig` with `capacity = 0`.

Inside `updateConfig` in `LeakyBucket.hs`, the level is then clamped:

```haskell
let (newLevel, newConfig) = f (oldLevel, oldConfig)
    Config{capacity = newCapacity} = newConfig
    newLevel' = clamp (0, newCapacity) newLevel
```

The sequence on a `Syncing → PreSyncing → Syncing` cycle is therefore:

| Step | GSM State | Bucket Level | Effect |
|---|---|---|---|
| 1 | `Syncing` | `L` (partially drained) | Peer has been withholding headers |
| 2 | `PreSyncing` | `0` (dummyConfig, `onEmpty = pure ()`) | No disconnection fires |
| 3 | `Syncing` | `csbcCapacity` (full) | **Patience debt permanently erased** |

The peer's entire accumulated patience debt is reset to zero on every cycle. The code comment itself acknowledges this is a known design gap: *"NOTE: The new level is currently the maximal capacity of the bucket; maybe we want to change that later."*

This is structurally identical to the external report: just as `userPendingRewards[msg.sender][_platform] = 0` permanently zeroes accumulated rewards when a cap is applied, `(LeakyBucket.capacity config, config)` permanently zeroes accumulated patience debt when the GSM transitions.

---

### Impact Explanation

An adversarial peer can evade the LoP mechanism by triggering GSM state transitions. By cycling the GSM between `PreSyncing` and `Syncing` (achievable when the adversary is the only peer, by disconnecting and reconnecting), the adversary resets its LoP bucket to full capacity on each `Syncing` re-entry.

Without the LoP enforcing disconnection, the GDD cannot make a density decision about the adversary's chain. The LoE anchor cannot advance past the adversary's fork point. The syncing node is permanently stuck and cannot select the honest chain. This is a chain selection failure in the Genesis protocol: an unprivileged peer can prevent an honest node from ever advancing its chain selection beyond the LoE anchor, keeping it on a less-secure chain indefinitely.

---

### Likelihood Explanation

The attack requires the adversary to trigger GSM state transitions. This is achievable when the adversary is the only peer (or one of few peers) of the syncing node — a realistic scenario during initial sync when the node is connecting to bootstrap peers. The adversary connects, withholds headers to drain the LoP bucket, then disconnects (HAA unsatisfied → `PreSyncing`) and reconnects (HAA satisfied → `Syncing`), resetting the bucket. This cycle can be repeated indefinitely with no stake requirement and no cryptographic material needed.

---

### Recommendation

Preserve the accumulated patience debt across GSM state transitions. When the GSM transitions back to `Syncing`, restore the previous bucket level (clamped to the new capacity) rather than unconditionally resetting to full capacity:

```haskell
updateLopBucketConfig lopBucket gsmState =
  LeakyBucket.updateConfig lopBucket $ \(oldLevel, _) ->
    let config = lopBucketConfig gsmState
     in (min oldLevel (LeakyBucket.capacity config), config)
```

This ensures that patience debt accumulated before a `PreSyncing` detour is not erased when the peer re-enters `Syncing`.

---

### Proof of Concept

1. Syncing node connects to adversarial peer A (only peer; HAA satisfied; GSM = `Syncing`; bucket = 100,000).
2. A sends a few headers, then withholds further headers. Bucket drains to level `L` (e.g., 50,000).
3. A disconnects. HAA unsatisfied → GSM transitions to `PreSyncing`. `updateLopBucketConfig` called with `PreSyncing` → bucket level set to 0 via `dummyConfig` (no `EmptyBucket` fires because `onEmpty = pure ()`).
4. A reconnects. HAA satisfied → GSM transitions to `Syncing`. `updateLopBucketConfig` called with `Syncing` → **bucket level reset to 100,000**.
5. A withholds headers again. Bucket drains from 100,000.
6. Repeat from step 3.

The adversary stalls indefinitely without ever being disconnected, preventing the LoE anchor from advancing and the GDD from making a chain density decision.
