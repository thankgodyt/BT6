### Title
Unchecked `burn()` Call in `safe_mint_callback` Leaves Unbacked nBTC in Bridge Balance — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary

In the `safe_mint_callback` function, when `safe_mint` fails (recipient account not registered), the bridge calls `ext_nbtc::ext(...).burn(...)` with `.detach()` and no callback. If this burn call fails silently, the bridge retains unbacked nBTC in its own balance while simultaneously rolling back the UTXO from `verified_deposit_utxo`, allowing the same BTC deposit to be re-processed and double-minted.

### Finding Description

The `safe_verify_deposit` flow calls `safe_mint` on the nBTC contract. The `safe_mint` function **always** mints tokens to the bridge's own balance first via `internal_deposit`, then checks if the recipient account is registered: [1](#0-0) 

If the recipient is not registered, `safe_mint` returns `U128(0)` without transferring the tokens — they remain in the bridge's balance. The `safe_mint_callback` detects this failure via `is_refund_required()` and enters the failure branch: [2](#0-1) 

Two critical actions happen in this failure branch:

1. The UTXO is removed from `verified_deposit_utxo` (rollback, allowing re-deposit).
2. `burn()` is called with `.detach()` — **no callback** is attached to verify success.

If the `burn()` call fails (e.g., due to gas exhaustion with only `GAS_FOR_BURN_CALL = 5 TGas` allocated, or any panic inside the nBTC contract), the failure is silently discarded: [3](#0-2) 

Contrast this with the `verify_withdraw_burn_promise` and `verify_active_utxo_management_burn_promise` paths, which both attach a proper callback (`verify_withdraw_burn_callback` / `verify_active_utxo_management_burn_callback`) to handle burn failures: [4](#0-3) 

The `safe_mint_callback` burn is the only burn call in the bridge that has no failure-handling callback.

### Impact Explanation

If the detached `burn()` call fails:

- The bridge holds nBTC in its balance that is **not backed by any BTC deposit** (the tokens were minted by `safe_mint`'s `internal_deposit` but never burned).
- The UTXO key was removed from `verified_deposit_utxo`, so the same BTC transaction can be re-submitted via `safe_verify_deposit` (or `verify_deposit`) and processed again, minting a second batch of nBTC for the same BTC.
- This results in nBTC total supply exceeding the BTC locked in the bridge — a permanent supply inflation / backing invariant violation.

The bridge's own nBTC balance is also used as the source for burns in `verify_withdraw_burn_promise`. Extra unbacked nBTC in the bridge's balance could allow a withdrawal to be processed without a corresponding BTC deposit having been locked, constituting unauthorized release of bridge-controlled funds.

This matches the allowed impact: **broken callback rollback** and **permanent burning below backed supply**.

### Likelihood Explanation

The `safe_verify_deposit` path is publicly callable by any relayer for any NEAR account. A deposit to an unregistered NEAR account is a realistic scenario (e.g., Omni Bridge integration where the recipient has not yet called `storage_deposit`). The `burn()` call is allocated only `5 TGas`: [3](#0-2) 

While 5 TGas is normally sufficient for a simple burn, gas exhaustion is possible if the nBTC contract state is large or if NEAR gas pricing changes. Any panic inside `burn()` (e.g., arithmetic overflow in relayer fee transfer) would also cause silent failure. Because there is no callback, **any failure mode goes undetected and unrecoverable**.

### Recommendation

Attach a callback to the `burn()` call in `safe_mint_callback`, analogous to how all other burn calls in the bridge are handled. The callback should check `is_promise_success()` and, on failure, record the unbacked amount in a recoverable state (e.g., a dedicated field) so an operator can retry or the bridge can be paused:

```rust
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(
        env::current_account_id(),
        mint_amount,
        relayer_account_id,
        U128(0),
    )
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_SAFE_MINT_BURN_CALLBACK)
            .safe_mint_burn_callback(mint_amount, pending_utxo_info.utxo_storage_key),
    );
```

Also consider increasing `GAS_FOR_BURN_CALL` from 5 TGas to a safer margin.

### Proof of Concept

1. User sends BTC to their deposit address. Their NEAR account (`alice.near`) is **not** registered in the nBTC contract.
2. Relayer calls `safe_verify_deposit(proof, DepositMsg { recipient: "alice.near", safe_deposit: Some(...) })`.
3. Bridge verifies the Merkle proof, inserts the UTXO into `verified_deposit_utxo`, and calls `safe_mint("alice.near", amount, msg)`.
4. `safe_mint` executes `internal_deposit(&bridge_id, amount)` — bridge now holds `amount` nBTC — then returns `U128(0)` because `alice.near` is not registered.
5. `safe_mint_callback` fires: `is_refund_required()` returns `true`, so `is_success = false`.
6. Bridge removes the UTXO from `verified_deposit_utxo` (rollback).
7. Bridge calls `burn(bridge_id, amount, relayer, 0)` with `.detach()` and only 5 TGas.
8. The `burn()` call runs out of gas and fails — **silently discarded**.
9. Bridge balance: `+amount` nBTC (unbacked). `verified_deposit_utxo`: UTXO removed.
10. Relayer (or attacker) re-submits the same proof via `verify_deposit`. The UTXO is not in `verified_deposit_utxo`, so the duplicate check passes. A second `amount` nBTC is minted to `alice.near`.
11. Total nBTC minted for one BTC deposit: `2 × amount`. Supply is permanently inflated. [2](#0-1) [5](#0-4)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
