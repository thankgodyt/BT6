### Title
Sibling RBF Candidates Orphaned in `btc_pending_sign_ids` When One RBF Is Confirmed, Permanently Inflating Pending-Sign Count - (File: contracts/satoshi-bridge/src/nbtc/burn.rs)

### Summary

When multiple RBF replacement transactions exist for the same original withdrawal, confirming one RBF removes the entire `rbf_txs[original_tx_id]` tracking entry but leaves sibling RBF candidates stranded in `account.btc_pending_sign_ids`. This inflates the user's pending-sign count, blocking them from initiating new withdrawals until a relayer manually signs the orphaned transaction.

### Finding Description

`set_rbf_pending_info` in `contracts/satoshi-bridge/src/rbf/mod.rs` registers every new RBF candidate in two places: the global `rbf_txs[original_tx_id]` set and the account's `btc_pending_sign_ids` HashSet. [1](#0-0) 

When a signed RBF transaction is later confirmed on-chain, `verify_withdraw_burn_callback` in `contracts/satoshi-bridge/src/nbtc/burn.rs` cleans up the original tx and the confirmed RBF, but removes the **entire** `rbf_txs` entry for the original tx in one call: [2](#0-1) 

Any **sibling** RBF candidates that were still in `PendingSign` stage at the time of confirmation are not touched. Their `btc_pending_infos` entries survive, and — critically — they remain in `account.btc_pending_sign_ids`: [3](#0-2) 

The only existing cleanup path, `internal_clear_invalid_pending_verify_rbf`, explicitly asserts `pending_verify` stage and therefore cannot remove a sibling that is still in `PendingSign`: [4](#0-3) 

The `sign_btc_transaction_callback` removes a tx from `btc_pending_sign_ids` only when all inputs are signed and the tx transitions to `PendingVerify`: [5](#0-4) 

Until that happens, `pending_sign_count()` remains elevated. [6](#0-5) 

### Impact Explanation

`require_pending_sign_capacity` enforces `pending_sign_count() < max_pending` (default 1) before any new withdrawal or RBF is accepted: [7](#0-6) 

With a stale sibling stuck in `btc_pending_sign_ids`, the user's count reads 1 even though no real pending-sign work remains. The user cannot initiate a new `ft_transfer_call` withdrawal or `withdraw_rbf` until a trusted relayer signs the orphaned transaction (which moves it out of `btc_pending_sign_ids`). This constitutes **attacker-triggered temporary locking of bridged funds** — the user's nBTC is locked in the bridge with no self-rescue path available to an unprivileged account.

### Likelihood Explanation

The preconditions are:
1. `rbf_num_limit >= 2` (operator-configurable; the field exists precisely to allow multiple RBF rounds).
2. The user creates two RBF candidates for the same original withdrawal (both `withdraw_rbf` calls succeed because each is submitted after the previous one moves out of `btc_pending_sign_ids`).
3. The first RBF is confirmed on-chain before the second is signed.

Steps 1–3 are all reachable by an ordinary bridge user without any privileged access. The timing window (step 3) is realistic given Bitcoin block times and the asynchronous nature of MPC signing.

### Recommendation

In `verify_withdraw_burn_callback`, after removing `rbf_txs[original_tx_id]`, iterate over the sibling set and remove each sibling from both `btc_pending_infos` and `account.btc_pending_sign_ids` (and `btc_pending_verify_list` if applicable) before discarding the set. Analogously to the Knox recommendation: only remove the tracking entry when **all** associated candidates have been resolved.

### Proof of Concept

1. User calls `ft_transfer_call` → original tx **O** enters `btc_pending_sign_ids` (count = 1).
2. Relayer signs O → O leaves `btc_pending_sign_ids` (count = 0), enters `btc_pending_verify_list`.
3. User calls `withdraw_rbf` → RBF **R1** enters `btc_pending_sign_ids` (count = 1); `rbf_txs[O] = {R1}`.
4. Relayer signs R1 → R1 leaves `btc_pending_sign_ids` (count = 0), enters PendingVerify; `rbf_txs[O] = {R1}`.
5. User calls `withdraw_rbf` again (count = 0 < 1 = max_pending, allowed) → RBF **R2** enters `btc_pending_sign_ids` (count = 1); `rbf_txs[O] = {R1, R2}`.
6. Relayer calls `verify_withdraw` for R1 (confirmed on-chain):
   - `rbf_txs.remove(O)` — entire set `{R1, R2}` discarded.
   - `btc_pending_infos.remove(O)`, `btc_pending_infos.remove(R1)`.
   - **R2 is NOT removed from `btc_pending_sign_ids`** (count stays at 1).
7. User attempts a new `ft_transfer_call` withdrawal → `require_pending_sign_capacity` panics: "Too many pending sign transactions".
8. User is locked out of new withdrawals. No public self-rescue function exists for a `PendingSign`-stage orphan; only a relayer signing R2 (a now-useless transaction) can decrement the count.
