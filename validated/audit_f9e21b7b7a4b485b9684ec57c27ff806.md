### Title
Detached `burn()` Call in `safe_mint_callback` Silently Ignores Failure, Leaving Unbacked nBTC in Circulation - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
In `safe_mint_callback`, when a safe-deposit mint fails and a rollback burn is required, the bridge fires the `burn()` cross-contract call with `.detach()`. This is the NEAR analog of Solidity's deprecated `transfer()`: the result is never observed. If the burn fails for any reason, the failure is silently swallowed, nBTC tokens remain minted without a corresponding tracked UTXO, and the deposit UTXO key is simultaneously removed from `verified_deposit_utxo`, allowing the same BTC deposit to be re-submitted and minted a second time.

### Finding Description

In `safe_mint_callback`, the failure branch (when `is_refund_required()` returns `true`) executes two fire-and-forget promises:

```rust
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(
        env::current_account_id(),
        mint_amount,
        relayer_account_id,
        U128(0),
    )
    .detach();                          // ← result never checked

Promise::new(env::signer_account_id())
    .transfer(self.required_balance_for_safe_deposit())
    .detach();                          // ← result never checked
``` [1](#0-0) 

Critically, before these detached calls are issued, the UTXO key is already removed from `verified_deposit_utxo`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);
``` [2](#0-1) 

The removal is unconditional and happens synchronously, before the async burn result is known. If the `burn()` cross-contract call fails (e.g., the nbtc contract panics, the bridge account does not hold the tokens at that moment, or `GAS_FOR_BURN_CALL` of 20 Tgas is insufficient for the nbtc contract's burn logic), the failure is never observed because the promise is detached. [3](#0-2) 

The downstream consequence is that `verify_safe_deposit_callback` guards re-submission only with:

```rust
require!(
    self.data_mut()
        .verified_deposit_utxo
        .insert(pending_utxo_info.utxo_storage_key.clone()),
    "Already deposit utxo"
);
``` [4](#0-3) 

Because the key was removed, this guard passes on re-submission, allowing the same BTC UTXO to mint nBTC a second time.

### Impact Explanation

**Critical.** If the detached `burn()` fails:

1. nBTC tokens minted by `safe_mint` remain in circulation with no corresponding UTXO tracked by the bridge.
2. The UTXO key is absent from `verified_deposit_utxo`, so a relayer (or the original depositor) can call `verify_deposit_v2` again for the same BTC transaction, passing the replay guard and minting a second batch of nBTC for the same on-chain BTC.
3. The result is unauthorized nBTC supply inflation — tokens backed by no BTC — matching the "Unauthorized minting" critical impact category.

### Likelihood Explanation

The `safe_deposit` path is the Omni Bridge integration path, actively used in production. The `GAS_FOR_BURN_CALL` constant is only 20 Tgas: [3](#0-2) 

Any nbtc contract burn logic that exceeds this budget, or any transient panic in the nbtc contract, silently drops the burn. Additionally, if `safe_mint` leaves the tokens with `recipient_id` rather than the bridge contract itself, the burn call targeting `env::current_account_id()` will fail unconditionally because the bridge holds no balance to burn. Either scenario is reachable by an ordinary depositor triggering the failure path (e.g., by deploying a receiver contract whose `ft_on_transfer` returns 0).

### Recommendation

Replace the detached burn with a chained callback that checks the burn result and, on failure, either re-inserts the UTXO key into `verified_deposit_utxo` (to prevent re-submission) or records the unbacked amount in a recoverable state. The pattern already used elsewhere in the codebase — `internal_transfer_nbtc` with `transfer_nbtc_callback` — demonstrates the correct approach:

```rust
// Correct pattern (already used in token_transfer.rs)
ext_ft_core::ext(...)
    .with_static_gas(GAS_FOR_TOKEN_TRANSFER)
    .ft_transfer(...)
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_AFTER_TOKEN_TRANSFER)
            .transfer_nbtc_callback(...),
    )
``` [5](#0-4) 

Apply the same pattern to the burn: chain a `burn_callback` that, on failure, re-inserts the UTXO key into `verified_deposit_utxo` to block re-submission, and emits an alert event so operators can intervene.

### Proof of Concept

1. Attacker deploys a NEAR contract `evil.near` whose `ft_on_transfer` always returns `"0"` (used 0 tokens).
2. Attacker deposits BTC to a safe-deposit address with `recipient_id = evil.near` and `msg` pointing to `evil.near`.
3. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)`.
4. `verify_safe_deposit_callback` inserts the UTXO key into `verified_deposit_utxo` and calls `safe_mint`.
5. `safe_mint` mints nBTC and calls `ft_transfer_call` to `evil.near`; `evil.near.ft_on_transfer` returns `"0"`.
6. `safe_mint_callback` is invoked: `is_refund_required()` returns `true`.
7. The UTXO key is removed from `verified_deposit_utxo`.
8. `burn(env::current_account_id(), ...)` is fired and detached. If the bridge does not hold the tokens (they are with `evil.near` or `recipient_id`), the burn fails silently.
9. nBTC tokens remain with `evil.near` (or `recipient_id`).
10. Relayer (or attacker) calls `verify_deposit_v2` again with the same BTC transaction. The UTXO key is absent from `verified_deposit_utxo`, so the guard passes, and a second batch of nBTC is minted for the same BTC deposit.
