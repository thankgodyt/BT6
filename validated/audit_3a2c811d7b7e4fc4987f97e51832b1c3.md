### Title
Unconditional Acceptance of Peras Certificates in Stub `validatePerasCert` Allows Any Peer to Inject Forged Certificates — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Because the Peras certificate diffusion protocol is fully wired into the node-to-node layer, any unprivileged peer can send a crafted `PerasCert` that will be accepted and stored without any check on committee membership, aggregate BLS signature, or VRF eligibility proofs. The accepted certificate then applies an unearned chain-selection boost to an arbitrary block, enabling an attacker to manipulate chain selection on the receiving node.

---

### Finding Description

**Root cause — the absent authorization check**

In `BlockSupportsPeras.hs`, the only deployed instance of `BlockSupportsPeras` provides the following implementation of `validatePerasCert`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the exact structural analog of the Solidity bug: instead of checking that the caller is the registered creator, the Solidity function checked a caller-supplied parameter against state. Here, instead of checking that the certificate was signed by a quorum of authorized committee members, the function skips all checks entirely and wraps every input in `Right`. The "validation" is vacuous — the function's return type promises a `ValidatedPerasCert`, but the value is constructed from the raw, unverified input.

**Attacker-controlled entry path**

The path from an unprivileged peer to this function is fully wired:

1. A peer connects via the node-to-node Peras cert diffusion mini-protocol (`hPerasCertDiffusionClient` in `NodeToNode.hs`, lines 375–383).
2. The inbound handler calls `makePerasCertPoolWriterFromChainDB`, which passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts` (`PerasCert.hs`, lines 118–137).
3. `processCerts` calls `validatePerasCert` on each certificate not already in the database (`PerasCert.hs`, lines 164–173).
4. Because `validatePerasCert` always returns `Right`, every certificate passes, is timestamped, and is added to the ChainDB via `ChainDB.addPerasCertAsync`.
5. The stored `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is applied to the referenced block during chain selection.

**Why existing checks fail**

The only guard in `processCerts` is a deduplication check (`Set.member roundNo certIds`). There is no fallback signature check, no committee membership check, and no VRF eligibility check anywhere in the path. The `PerasValidationErr` data type is a single opaque constructor with no variants, confirming that no error conditions are modelled.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` referencing any block at any round number and send it to a target node. The node will:

1. Accept the certificate unconditionally.
2. Apply the Peras boost (`perasWeight`) to the referenced block.
3. Prefer that block over competing tips in chain selection.

This constitutes a **bypass of Peras certificate verification** that enables an unauthorized peer to make an honest node prefer a non-canonical or adversarially chosen chain. The impact category is: *Critical — bypass of Peras certificate checks that enables unauthorized certificate acceptance and chain-selection manipulation*.

---

### Likelihood Explanation

The Peras cert diffusion protocol is unconditionally enabled in the node-to-node handler setup (`NodeToNode.hs`, lines 375–390). Any peer that can establish a connection can send crafted certificates. No stake, no keys, and no prior knowledge beyond the target node's address are required. The attack is deterministic and requires a single crafted message per target round.

---

### Recommendation

Replace the stub with a real implementation that:
1. Deserializes the certificate into the abstract `WFALSCert` (or `EveryoneVotesCert`) type via `fromPerasCert`.
2. Calls `Committee.verifyCert committee cert` to verify the aggregate BLS signature and, for non-persistent voters, the batch VRF outputs.
3. Checks that the number of verified voters meets the quorum threshold before returning `Right`.

Until the real implementation is in place, the Peras cert diffusion inbound handler should be disabled or should reject all inbound certificates.

### Proof of Concept

**Attacker constructs a forged certificate:**

```haskell
-- Attacker-controlled values (all public information)
let forgeryRound  = PerasRoundNo 42
    targetBlock   = someKnownBlockPoint   -- any block hash the attacker wants boosted
    fakeVoters    = NEMap.singleton (SeatIndex 0) Nothing  -- claim seat 0 is a persistent voter
    fakeAggSig    = someArbitraryBytes    -- any bytes; signature is never checked

    forgery = WFALSCert forgeryRound targetBlock fakeVoters fakeAggSig
```

**Attacker sends it via the Peras cert diffusion protocol to the target node.**

**On the target node, `processCerts` calls:**

```haskell
validatePerasCert mkPerasParams forgery
-- Returns: Right (ValidatedPerasCert { vpcCert = forgery, vpcCertBoost = perasWeight mkPerasParams })
-- No signature check. No committee membership check. No VRF check.
```
