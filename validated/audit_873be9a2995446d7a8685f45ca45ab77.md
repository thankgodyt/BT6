### Title
Stub `validatePerasCert` Unconditionally Accepts Any Fabricated Peras Certificate, Enabling Unauthorized Chain Selection Weight Boost — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally returns `Right` for every certificate, performing no BLS signature verification, no committee quorum check, no round validity check, and no boosted-block existence check. This stub is wired directly into the production NodeToNode `hPerasCertDiffusionClient` handler. Any peer connecting via `NodeToNodeV_16` can send a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`, have it accepted without any cryptographic validation, and trigger chain selection with a weight boost of `perasWeight = 15` for an attacker-chosen block.

---

### Finding Description

**Root cause — stub validator:**

In `SupportsPeras.hs`, the `instance StandardHash blk => BlockSupportsPeras blk` provides a degenerate implementation of `validatePerasCert` that ignores all certificate fields and returns `Right` unconditionally:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

**Production wiring — `makePerasCertPoolWriterFromChainDB`:**

`PerasCert.hs` wires this stub directly as the validation function in the production pool writer:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

**`processCerts` passes every cert through:**

`processCerts` calls `validateCert` (the stub) on each inbound cert. Since the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `addCert` (i.e., `ChainDB.addPerasCertAsync`): [3](#0-2) 

**NodeToNode handler — reachable via `NodeToNodeV_16`:**

The production `NodeToNode.hs` handler wires `makePerasCertPoolWriterFromChainDB` into `hPerasCertDiffusionClient`, which is invoked for every peer that negotiates `NodeToNodeV_16`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      (contramap (TraceLabelPeer peer) (Node.perasCertDiffusionInboundTracer tracers))
      ( perasCertDiffusionMaxObjectsUnacknowledged miniProtocolParameters
      , 10 , 10
      )
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

`NodeToNodeV_16` is present in `supportedNodeToNodeVersions` for both `CardanoBlock` and `ShelleyBlock`: [5](#0-4) 

**`chainSelSync` triggers chain selection for the boosted block:**

Once the fabricated cert reaches `ChainDB.addPerasCertAsync`, `chainSelSync` processes it. The only guards are: slot older than immutable tip (exits early), block on current chain (exits early), Genesis point (exits early), or block not yet in VolatileDB (exits early). None of these validate the certificate's cryptographic integrity. If the attacker's target block is in the VolatileDB, `chainSelectionForBlock` is called with the full `perasWeight = 15` boost: [6](#0-5) 

---

### Impact Explanation

An attacker peer connecting via `NodeToNodeV_16` can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block hash in the target node's VolatileDB (including blocks on an adversarial fork). The cert bypasses all cryptographic validation and is accepted as a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params = 15`. If the boosted block is present in the VolatileDB, `chainSelectionForBlock` is triggered for it with this artificial weight boost, potentially causing the honest node to prefer an adversarial fork over the canonical chain. This is a **Critical** bypass of Peras certificate validation enabling unauthorized chain selection weight manipulation.

---

### Likelihood Explanation

- `NodeToNodeV_16` is in `supportedNodeToNodeVersions` and will be negotiated with any peer that also advertises it. `latestReleasedNodeVersion` returns `Just NodeToNodeV_15`, indicating V_16 is not yet the default released version, but any node running this codebase will negotiate V_16 with a peer that requests it.
- The attacker only needs to: (1) connect to a target node, (2) negotiate `NodeToNodeV_16`, (3) send a `PerasCert` with a `pcCertBoostedBlock` pointing to a block hash the attacker has previously diffused to the target's VolatileDB via normal block diffusion.
- No key material, stake majority, or privileged access is required. The attack is fully executable by any network peer.

---

### Recommendation

Replace the stub `validatePerasCert` with real validation before `NodeToNodeV_16` is enabled in any released build. Real validation must include at minimum:
1. Aggregate BLS signature verification over the claimed committee votes.
2. Committee quorum check (≥ `perasQuorumStakeThreshold` of eligible stake).
3. Round validity check (cert round within acceptable window).
4. Boosted block eligibility check (block age ≥ `perasBlockMinSlots`).

Until real validation is wired in, `NodeToNodeV_16` should be removed from `supportedNodeToNodeVersions` or the `hPerasCertDiffusionClient` handler should unconditionally reject all inbound certs.

---

### Proof of Concept

Using `io-sim` or a private two-node testnet with both nodes running this codebase:

1. Start node A (victim) and node B (attacker), both supporting `NodeToNodeV_16`.
2. From node B, diffuse a block `X` on an adversarial fork to node A via normal block diffusion (so `X` lands in node A's VolatileDB).
3. From node B's object diffusion client, send a `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = pointOf X }` to node A.
4. Observe that node A's `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{vpcCertBoost = 15}`, then calls `ChainDB.addPerasCertAsync`.
5. Observe that `chainSelSync` finds block `X` in the VolatileDB and calls `chainSelectionForBlock` for it with the 15-unit boost.
6. Assert that node A's selected chain now includes block `X` on the adversarial fork, despite no valid aggregate BLS signature ever being verified.

The assertion at step 6 will succeed on unmodified code because `validatePerasCert` at `SupportsPeras.hs:353–358` never inspects the certificate's cryptographic content. [7](#0-6)

    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
