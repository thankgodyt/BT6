Audit Report

## Title
Detached Relayer Repayment with Unconditional Fast-Transfer Finalization Causes Permanent Fund Loss - (File: near/omni-bridge/src/lib.rs)

## Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the `send_tokens` call that repays the fast-transfer relayer is fired with `.detach()` — no callback checks whether the underlying `ft_transfer` succeeded. The fast transfer record is permanently finalised in the same transaction regardless of transfer outcome. If `ft_transfer` panics (e.g., the relayer's account is no longer registered for the token), the relayer permanently loses the tokens they fronted on the destination chain with no recovery path.

## Finding Description

**Location 1 — `process_fin_transfer_to_other_chain`** (lines 1985, 2028–2040):

`add_fin_transfer` at line 1985 inserts the transfer ID into `finalised_transfers` at the top of the function. Then:

```rust
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, amount, "").detach(); // no callback
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // committed regardless
}
```

`send_tokens` with an empty `msg` resolves to `ext_token::ext(token).ft_transfer(recipient, amount, None)` (lines 2102–2106). If `ft_transfer` panics, the detached promise fails silently. Both `finalised_transfers` (via `add_fin_transfer`) and the fast transfer entry (via `mark_fast_transfer_as_finalised`) are already committed. The transfer cannot be re-submitted and the fast transfer cannot be replayed.

**Location 2 — `utxo_fin_transfer_fast`** (lines 2529–2548):

```rust
let amount = if fast_transfer.get_destination_chain() == ChainKind::Near {
    self.remove_fast_transfer(&fast_transfer.id());   // entry deleted
    fast_transfer.amount
} else {
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // entry finalised
    ...
};
self.send_tokens(...).detach(); // no callback
```

Same pattern: state is mutated before the token transfer result is known.

**Contrast with the safe path** (`fast_fin_transfer_to_near_callback`, lines 877–892): `send_tokens` is chained with `.then(resolve_fast_transfer(...))`, which on failure removes the fast transfer entry and returns the amount as a refund. The two detached call sites lack this protection entirely.

The project's own security checklist (CLAUDE.md, line 228) explicitly states: *"Detached promises should only be used for non-critical operations."* Repaying a relayer for fronted bridge funds is not a non-critical operation.

## Impact Explanation

A relayer who fronted real tokens on the destination chain (ETH, Solana, etc.) and whose NEAR-side repayment `ft_transfer` fails will permanently lose those tokens. The `finalised_transfers` set already contains the transfer ID (added by `add_fin_transfer` at line 1985), so the transfer cannot be re-submitted. The fast transfer entry is also finalised or removed, closing every recovery path. This constitutes a direct, permanent loss of bridged funds — matching the critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

## Likelihood Explanation

`ft_transfer` on a NEP-141 token panics when the recipient account is not registered for that token. A relayer who performed a fast transfer via `ft_transfer_call` (reducing their token balance to 0) may subsequently call `storage_unregister` on the token contract to reclaim their storage deposit — a standard and reasonable NEAR operation when balance is zero. The finalization window (hours to days) makes this a realistic race condition. No privileged access is required; the relayer's own account state is sufficient to trigger the failure. The condition can also arise if the relayer's registration is removed by the token contract through other means.

## Recommendation

Replace the detached calls with a chained callback that reverts the fast-transfer state on failure, mirroring the pattern already used in `fast_fin_transfer_to_near_callback`:

```rust
self.send_tokens(token, relayer, amount, "")
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(RESOLVE_FAST_TRANSFER_GAS)
            .resolve_fast_transfer_repayment(&fast_transfer.id(), relayer, amount),
    );
// Move mark_fast_transfer_as_finalised into the callback's success branch only
```

The callback should mark the fast transfer as finalised only on success, and on failure should leave the fast transfer entry intact so the repayment can be retried after the relayer re-registers storage.

## Proof of Concept

1. Relayer R calls `ft_transfer_call` on the NEAR-side USDC contract, sending tokens to the bridge with a `FastFinTransfer` message. Bridge records `FastTransferStatus { relayer: R, finalised: false }`. R's USDC balance is now 0.
2. R calls `storage_unregister` on the NEAR-side USDC contract (balance is 0, so this succeeds), reclaiming the storage deposit. R's USDC account is removed.
3. The original ETH proof arrives at NEAR. A relayer calls `fin_transfer_callback`. Since the recipient is on ETH (not NEAR), `process_fin_transfer_to_other_chain` is invoked.
4. `add_fin_transfer` inserts the transfer ID into `finalised_transfers`.
5. The bridge detects the fast transfer entry for R, calls `send_tokens(usdc, R, amount, "").detach()`. Internally this resolves to `ext_token::ext(usdc).ft_transfer(R, amount, None)`.
6. `ft_transfer` panics: R is not registered for USDC. The detached promise fails silently.
7. In the same transaction, `mark_fast_transfer_as_finalised` commits.
8. R has no mechanism to recover: the fast transfer is finalised, the transfer ID is in `finalised_transfers`, and R's fronted ETH-side tokens are permanently lost.
