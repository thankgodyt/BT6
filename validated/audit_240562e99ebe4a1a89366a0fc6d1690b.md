### Title
Unconditional `validatePerasCert` Stub Allows Forged Peras Certificates to Inject Unauthorized Chain-Weight Boosts — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound `PerasCert`, granting the full `perasWeight` boost (currently `PerasWeight 15`) without performing any cryptographic, quorum, or committee validation. Because the Peras object-diffusion writer calls this function on every cert received from a peer, an attacker who can send a crafted `PerasCert` over the NodeToNode diffusion layer can cause the victim node to assign a weight boost of +15 to an arbitrary block, potentially making the attacker's chain appear heavier than the honest chain in Peras-weighted chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The universal `BlockSupportsPeras` instance (lines 320–389) is explicitly labelled a "degenerate instance for all blks to get things to compile" and contains a TODO referencing issue #120:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always PerasWeight 15
      }
``` [1](#0-0) 

No signature verification, no committee membership check, no quorum check, no round-number bounds check, and no boosted-block existence check are performed.

**Inbound path — `processCerts` in the object-diffusion writer:**

`makePerasCertPoolWriterFromChainDB` (the production writer) passes `validatePerasCert mkPerasParams` directly as the validation function for every batch of certs received from a peer:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this function on every cert not already in the DB, and adds all certs that return `Right` to the `ChainDB` via `addPerasCertAsync`: [3](#0-2) 

**Weight boost — `mkPerasParams`:**

The default params set `perasWeight = PerasWeight 15`, meaning each accepted cert adds +15 to the total weight of the boosted block's chain: [4](#0-3) 

**Chain selection — `weightedSelectView` / `preferCandidate`:**

`weightedSelectView` computes `wsvTotalWeight = BlockNo + weightBoostOfFragment`, and `preferCandidate` switches to the candidate chain whenever its total weight exceeds the current selection's:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
``` [6](#0-5) 

A forged cert pointing to a block on the attacker's chain adds +15 weight to that chain, which can cause the victim to prefer it over an honest chain that is up to 15 blocks longer.

---

### Impact Explanation

This is a **Critical** bypass of Peras certificate checks enabling unauthorized chain preference via forged weight boost. An unprivileged peer can:

1. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = attackerBlockPoint }` for any round and any block point.
2. Send it via the NodeToNode object-diffusion miniprotocol.
3. The victim node accepts it unconditionally, stores it, and adds `PerasWeight 15` to the attacker's block in the weight snapshot.
4. Chain selection then prefers the attacker's chain over the honest chain if the honest chain's total weight is within 15 of the attacker's.

This directly satisfies the "bypass of Peras certificate checks enabling unauthorized chain preference via forged weight boost" impact scope.

---

### Likelihood Explanation

**Conditional on Peras being active.** The Peras object-diffusion layer is wired into the production `ChainDB` path (`makePerasCertPoolWriterFromChainDB`), but Peras is still in active development (many TODOs, `getPerasCertInBlock _ = Nothing`). The vulnerability is exploitable as soon as the Peras diffusion miniprotocol is enabled in a deployment. No key compromise, stake majority, or operator access is required — any peer that can connect to the node can send `PerasCert` objects.

---

### Recommendation

Replace the stub with a real implementation before enabling the Peras diffusion layer in any deployment:

1. **Cryptographic signature verification**: verify that the cert carries valid signatures from a quorum of committee members for the claimed round.
2. **Committee membership check**: verify each signer was elected to the committee for the given round via the VRF-based sortition.
3. **Quorum check**: verify the aggregate stake of signers exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
4. **Round-number bounds check**: verify `pcCertRound` is within the valid window relative to the current tip.
5. **Boosted-block existence check**: verify `pcCertBoostedBlock` refers to a block that actually exists in the node's chain.

Until issue #120 is resolved and these checks are implemented, the Peras cert diffusion writer must not be enabled in production. [7](#0-6)

### Proof of Concept

```haskell
-- Locally testable unit test (no mainnet required)
import Ouroboros.Consensus.Block.SupportsPeras
import Ouroboros.Consensus.Peras.Params (mkPerasParams)

-- Forge a cert with an arbitrary round and a non-existent block point
let forgedCert = PerasCert
      { pcCertRound        = PerasRoundNo 9999
      , pcCertBoostedBlock = BlockPoint (SlotNo 1) (coerce "deadbeef" :: HeaderHash TestBlock)
      }

-- This should return Left, but currently returns Right with full boost
case validatePerasCert mkPerasParams forgedCert of
  Right vc -> error $ "VULNERABLE: boost = " ++ show (vpcCertBoost vc)
  Left  _  -> putStrLn "OK: cert rejected"
```

The test will print `VULNERABLE: boost = PerasWeight 15`, confirming that a forged cert with an arbitrary round number and non-existent block point receives the full weight boost. [8](#0-7)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
