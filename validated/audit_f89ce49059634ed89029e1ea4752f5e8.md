### Title
Peras Certificate and Vote Validation Bypass Allows Adversary to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance — which is the live production instance wired into both the `PerasCertDB` and `ChainDB` diffusion paths — performs no cryptographic validation whatsoever on inbound Peras certificates and votes. `validatePerasCert` unconditionally returns `Right` for every certificate it receives, and `validatePerasVote` only checks that a voter ID appears in the stake distribution without verifying the vote signature. An unprivileged peer can therefore inject arbitrary certificates or forged votes that are accepted as valid, stored, and used to trigger chain selection for an adversary-chosen block.

### Finding Description

**Root cause — `validatePerasCert` is a no-op:**

The `instance StandardHash blk => BlockSupportsPeras blk` block, explicitly labelled a "degenerate instance for all blks to get things to compile", implements `validatePerasCert` as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is checked, no committee membership is verified, no round validity is enforced. Every field of the certificate (`pcCertRound`, `pcCertBoostedBlock`) is accepted as-is.

**Root cause — `validatePerasVote` ignores the vote signature:**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

The only check is a stake-distribution lookup by `pvVoteVoterId`. No cryptographic proof of identity is required. The degenerate `PerasVote` type carries no signature field at all, so any message claiming to be from a known voter ID passes.

**These stubs are wired into production diffusion paths:**

`makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` both call `validatePerasCert mkPerasParams` directly:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

Similarly, `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` call `validatePerasVote mkPerasParams sd vote`: [4](#0-3) 

**Chain selection consequence:**

Once a `ValidatedPerasCert` is stored in the `PerasCertDB`, `chainSelSync` triggers `chainSelectionForBlock` for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The boost weight (`vpcCertBoost = perasWeight params`) is assigned from the local config, not from the certificate, so the adversary-injected certificate carries the full configured Peras boost weight and can tip chain selection toward the adversary's chosen block.

**Analog to the external report:**

The external report describes `isValidSignature()` ignoring the `appData` field, allowing an adversary to substitute an arbitrary value that keeps the signature valid while redirecting surplus. Here, `validatePerasCert` ignores *all* cryptographic fields — the entire certificate body is accepted without any check — allowing an adversary to substitute arbitrary `pcCertRound` and `pcCertBoostedBlock` values that redirect chain selection weight to a block of their choosing.

### Impact Explanation

**High.** An unprivileged peer can send a crafted `PerasCert` naming any block hash as `pcCertBoostedBlock`. The certificate is accepted without verification, stored in the `PerasCertDB`, and immediately used to trigger chain selection for the named block. If the adversary's chosen block is on a competing fork, the injected boost weight can cause the honest node to prefer that fork over the canonical chain, constituting a chain-selection integrity failure. Via the vote path, an adversary can also forge enough votes for any voter IDs present in the stake distribution to manufacture a quorum, causing the node to locally forge and store a certificate for an adversary-chosen block without any real committee participation.

### Likelihood Explanation

**High.** The entry point is the standard Peras object-diffusion mini-protocol, reachable by any peer that connects to the node. No keys, stake, or privileged access are required. The adversary only needs to construct a well-formed CBOR-encoded `PerasCert` with the desired `pcCertRound` and `pcCertBoostedBlock` fields. The stub validation is unconditional and contains no randomness or secret-dependent check that would make exploitation probabilistic.

### Recommendation

1. Replace the degenerate `validatePerasCert` stub with a real implementation that verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the declared voter set, checks committee membership and quorum, and validates the round number against the current epoch.
2. Replace the degenerate `validatePerasVote` stub with a real implementation that verifies the BLS vote signature (`pvSignature`) over `(pvRoundNo, pvBoostedBlock)` using the voter's registered verification key, as already implemented in `implVerifyVote` in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Committee.EveryoneVotes`.
3. Until real validation is in place, gate the Peras diffusion paths behind a feature flag so that nodes not running an active Peras committee do not accept inbound certificates or votes at all.
4. Track this under the existing issue https://github.com/tweag/cardano-peras/issues/120 and treat it as a security blocker before any Peras-enabled release.

### Proof of Concept

**Attacker preconditions:** Any peer connection to a node running this codebase with Peras diffusion enabled.

**Steps:**

1. Attacker connects to the target node as a standard peer.
2. Attacker constructs a `PerasCert` CBOR payload:
   - `pcCertRound`: any `PerasRoundNo` not already in the node's `PerasCertDB`
   - `pcCertBoostedBlock`: the `Point` (slot + hash) of a block on a competing fork the attacker wants the node to prefer
3. Attacker sends the crafted certificate via the Peras certificate object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`.
5. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
6. The certificate is stored in `PerasCertDB` and enqueued in `cdbChainSelQueue` as `ChainSelAddPerasCert`.
7. `chainSelSync` processes the message: it looks up the boosted block header from `VolatileDB` and calls `chainSelectionForBlock` with the full Peras boost weight.
8. If the boosted block is on a competing fork and the boost tips the chain-order comparison, the node switches to the adversary's chosen fork.

**Expected outcome:** The node adopts a non-canonical chain boosted by a certificate that was never signed by any legitimate Peras committee member.
