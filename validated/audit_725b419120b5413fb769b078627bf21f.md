Audit Report

## Title
Callback panic in `send_fee_internal` after committed `remove_transfer_message` permanently destroys transfer record and freezes fee tokens — (`near/omni-bridge/src/btc.rs`, `near/omni-bridge/src/lib.rs`)

## Summary
`submit_transfer_to_utxo_chain_connector` calls `self.remove_transfer_message(transfer_id)` before dispatching the async `ft_transfer_call`. In NEAR's execution model this state change is committed and cannot be rolled back by a later callback panic. When the connector accepts tokens and the callback invokes `send_fee_internal` with `native_fee > 0` on a UTXO-chain transfer, `env::panic_str` is called, reverting only the callback's own state. The transfer record is permanently deleted and the withheld `token_fee` amount is permanently frozen in the bridge contract with no recovery path.

## Finding Description
**Step 1 — State committed before async call.** [1](#0-0) 
`remove_transfer_message(transfer_id)` executes and its storage write is finalized before `ft_transfer_call` is dispatched. NEAR's async model does not roll back the calling function's committed state when a callback panics.

**Step 2 — Amount withheld from connector.** [2](#0-1) 
Only `amount = total - token_fee` is sent to the connector; `token_fee` remains in the bridge contract.

**Step 3 — Callback invokes `send_fee_internal` on connector acceptance.** [3](#0-2) 
`result.0 > 0` means `ft_resolve_transfer` returned a positive net-transferred amount (connector accepted tokens). The else branch (re-add transfer) only runs when the connector rejects all tokens.

**Step 4 — `send_fee_internal` panics for UTXO + native_fee > 0.** [4](#0-3) 
`env::panic_str` is a hard panic. It reverts only state changes made within this callback invocation. The `remove_transfer_message` committed in Step 1 is unaffected.

**Step 5 — No guard at creation time.** [5](#0-4) 
The e2e test passes `"native_token_fee":"162"` in a BTC transfer message. Neither `ft_on_transfer` nor `submit_transfer_to_utxo_chain_connector` validates `native_fee == 0` for UTXO-chain transfers before `remove_transfer_message` is called. The only rejection point is inside `send_fee_internal`, which executes inside the callback after state has already been committed.

**Resulting state after panic:**

| Item | Outcome |
|---|---|
| Transfer record in `pending_transfers` | Permanently deleted |
| BTC tokens sent to connector | With connector (settled) |
| `token_fee` tokens withheld at line 39 | Permanently frozen in bridge contract |
| Relayer fee | Never distributed |
| Callback re-add of transfer | Never runs (panic, not else branch) |

## Impact Explanation
`token_fee` (denominated in nBTC) is permanently frozen in the bridge contract with no administrative or user-facing recovery path, because the transfer record that would identify the owner no longer exists. This is a concrete instance of **permanent freezing of bridged funds** and **fee mis-accounting** within the Critical impact scope.

## Likelihood Explanation
Any user can set `native_token_fee > 0` in their BTC transfer message via a standard `ft_transfer_call`. No special attacker capability is required. A trusted relayer processing the transfer normally (calling `submit_transfer_to_utxo_chain_connector` with a cooperating connector that accepts tokens) is sufficient to trigger the bug. The e2e test confirms this is a supported user-facing input path.

## Recommendation
Validate `native_fee == 0` for UTXO-chain transfers at `ft_on_transfer` time (when the transfer is first stored), or at the entry of `submit_transfer_to_utxo_chain_connector` before `remove_transfer_message` is called. Do not rely on `send_fee_internal` as the sole rejection point, since it executes inside a callback after state has already been committed and cannot be rolled back.

## Proof of Concept
1. User calls `ft_transfer_call` on the nBTC token contract with `msg` containing `native_token_fee: 162` and a BTC recipient address.
2. Bridge stores the transfer with `native_fee = 162` (no validation rejects it).
3. Trusted relayer calls `submit_transfer_to_utxo_chain_connector`.
4. `remove_transfer_message` commits at line 84 — transfer record is gone.
5. `ft_transfer_call` sends `amount - token_fee` to the connector.
6. Connector's `ft_on_transfer` returns 0 (all tokens accepted); `ft_resolve_transfer` returns `amount - token_fee > 0`.
7. Callback: `result.0 > 0` → `send_fee_internal` called with `native_fee = 162`.
8. `origin_chain.is_utxo_chain()` is true → `env::panic_str(NativeFeeForUtxoChain)`.
9. Assert: transfer no longer exists in `pending_transfers`; `token_fee` nBTC is in bridge contract; relayer received no fee; no refund to user; no recovery path exists.
