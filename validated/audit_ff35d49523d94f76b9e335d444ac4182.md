Audit Report

## Title
Stale `MetadataPayload` Signatures Enable Foreign-Chain Token Deployment With Incorrect Decimals — (`near/omni-types/src/lib.rs`, `near/omni-bridge/src/lib.rs`, `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`MetadataPayload` contains no nonce, timestamp, or version field, so any MPC-signed metadata signature is valid indefinitely. If a token's `decimals` is legitimately updated via `set_metadata` after a signature has been emitted, an attacker can replay the old signed payload to deploy the token on any chain where it has not yet been deployed, permanently storing the wrong decimal value. All subsequent transfers to that chain are mis-normalized, causing users to receive zero or astronomically incorrect token amounts.

## Finding Description

**Root cause — `MetadataPayload` has no replay-prevention field.**
The struct at `near/omni-types/src/lib.rs` L694–702 contains only `prefix`, `token`, `name`, `symbol`, and `decimals`. There is no nonce, block height, timestamp, or version. A signature over this struct is valid indefinitely and on every chain.

**Signature is emitted publicly.**
`log_metadata_callback` in `near/omni-bridge/src/lib.rs` L329–384 requests an MPC signature over the `MetadataPayload` and then emits the full signed payload as a NEAR event log in `sign_log_metadata_callback`. Any observer can capture it.

**`set_metadata` freely updates decimals with no guard.**
`near/omni-token/src/lib.rs` L156–188 only calls `assert_controller()`. There is no check that a `MetadataPayload` has already been signed, no invalidation of prior signatures, and no version bump.

**EVM `deployToken` replay guard is insufficient.**
`evm/src/omni-bridge/contracts/OmniBridge.sol` L151–158 verifies the MPC signature and then checks `!isBridgeToken[nearToEthToken[metadata.token]]`. This only prevents deploying the same token on the same chain twice. It does not prevent deploying on a different chain that has not yet received the token using a stale signed payload with old decimals.

**SECURITY.md confirms signatures are intentionally chain-agnostic.**
`evm/SECURITY.md` L10 states: "Metadata signatures are intentionally chain-agnostic — one NEAR-side signature deploys the same token on all EVM chains." This design means a stale signature is equally valid on every EVM chain.

**Starknet `deploy_token` has the same gap.**
`starknet/src/omni_bridge.cairo` L202–209 verifies the signature and checks `existing_token.is_zero()`. No nonce on the metadata signature.

**Normalization uses the stale stored decimals.**
`near/omni-bridge/src/lib.rs` L471–480 reads `token_decimals` from the mapping populated at deployment time and passes it to `normalize_amount`. If the stored value is wrong, every transfer to that chain is mis-normalized.

**Exploit flow:**
1. Token deployed with `decimals=18`. `log_metadata` called → MPC signs `MetadataPayload{decimals=18}` → emitted as NEAR event. Attacker captures it.
2. DAO legitimately calls `set_metadata(decimals=Some(6))`. Token now has `decimals=6` on NEAR.
3. Token deployed on Chain A correctly (fresh `log_metadata` call) with `decimals=6`.
4. Token not yet deployed on Chain B.
5. Attacker submits old signed payload (`decimals=18`) to Chain B's `deployToken`. Signature verifies. `!isBridgeToken[nearToEthToken[token]]` is true. Token deployed on Chain B with `decimals=18`. `token_decimals[chainB_token_address] = 18` stored permanently.
6. User transfers 1.0 token (1,000,000 units at `decimals=6`) from NEAR to Chain B. `normalize_amount(1_000_000, stored_decimals=18)` → `1_000_000 / 10^12 = 0`. User receives 0 tokens. Funds permanently lost.

## Impact Explanation
This is a concrete instance of **decimal/normalization abuse and token metadata binding confusion that changes user balances**. The decimal mismatch is permanent and unrecoverable for every transfer routed through the affected chain's token address. A 10^12 factor error in `normalize_amount` causes users to receive either zero tokens or astronomically inflated amounts, constituting permanent loss of bridged funds. This matches the Critical allowed impact: "decimal/normalization abuse… that changes user or protocol balances."

## Likelihood Explanation
- `log_metadata` is permissionless; signed payloads are public NEAR events capturable by any observer.
- `set_metadata` is a legitimate, documented controller operation (decimal corrections during token migration are a normal DAO action).
- The vulnerability window is any chain where the token has not yet been deployed at the time of the metadata update.
- No admin compromise is required. The attacker only needs the publicly emitted signed event and the ability to call `deployToken` on the target chain.
- The SECURITY.md explicitly acknowledges that `deployToken` is permissionless and that signatures are chain-agnostic, confirming the attacker's ability to submit the payload to any chain.

## Recommendation
1. **Add a monotonic `metadata_version` counter** to `OmniToken` state. Include it in `MetadataPayload`. Increment it on every `set_metadata` call. EVM/Starknet `deployToken` should reject payloads whose version does not match the current one (verified via a NEAR view call or an on-chain registry).
2. **Alternatively, add a nonce or block-height field** to `MetadataPayload` and have `deployToken` reject payloads older than a configurable window.
3. **At minimum**, add an on-chain guard (e.g., a `metadata_signed` flag) that blocks `set_metadata` once a signature has been emitted, or that requires a new `log_metadata` cycle before any deployment can proceed on a new chain.
