Audit Report

## Title
Non-Atomic `burn.and(mint)` with Detached Promise in `swap_migrated_token` Causes Permanent Token Loss on Mint Failure — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` schedules a burn of the old token and a mint of the new token as two parallel, independent NEAR promises via `burn.and(mint)`. The resulting joint promise is `.detach()`ed in `ft_on_transfer`, so any mint failure is silently ignored. If the recipient is not registered (no storage deposit) in the new token contract, `internal_deposit` panics, the mint promise fails, but the burn has already executed and is irreversible — the user permanently loses their tokens and receives nothing.

## Finding Description
**`ft_on_transfer` (lib.rs:275-279):** The `SwapMigratedToken` branch calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)`, meaning the bridge retains the old tokens and no refund is issued regardless of what happens to the joint promise.

**`swap_migrated_token` (lib.rs:2738-2752):** The function constructs two independent promises and combines them with `burn.and(mint)`. In NEAR SDK, `Promise::and()` schedules both sub-promises in parallel with no dependency between them — neither waits for the other, and there is no rollback if one fails.

**`mint` in `omni-token` (lib.rs:140-142):** When `msg` is `None`, `mint` calls `self.token.internal_deposit(&account_id, amount.into())` directly. `FungibleToken::internal_deposit` panics if `account_id` has no storage registration, causing the mint promise to fail.

**`migrate_deployed_token` (lib.rs:1651-1655):** Only the bridge contract itself (`env::current_account_id()`) is registered via `storage_deposit` in the new token. No user registration is performed, and no guard in `swap_migrated_token` or `ft_on_transfer` checks whether `sender_id` is registered before issuing the promises.

**`burn` in `omni-token` (lib.rs:146-151):** `burn` calls `internal_withdraw` from the bridge's balance in the old token. Because `ft_on_transfer` returned `U128(0)`, the bridge holds the full amount, so this withdrawal always succeeds unconditionally.

Execution sequence:
1. User calls `old_token.ft_transfer_call(bridge, amount, "SwapMigratedToken")`.
2. NEP-141 transfers `amount` from user to bridge; `ft_on_transfer` is invoked.
3. Bridge returns `U128(0)` → bridge permanently holds old tokens; no refund path exists.
4. `burn(old_token, amount)` executes → bridge's old-token balance is destroyed. Irreversible.
5. `mint(new_token, sender_id, amount, None)` executes → `internal_deposit` panics because `sender_id` is not registered → promise fails.
6. `.detach()` means the failure is never observed or handled by the bridge.
7. User has lost `amount` of old tokens and received 0 new tokens. Permanent loss.

## Impact Explanation
This is a **Critical** impact matching the allowed scope: permanent, unrecoverable destruction of user funds during a legitimate migration flow. Any user who calls `swap_migrated_token` without first registering storage in the new token contract loses their entire transferred amount with no recovery mechanism. The bridge contract has no callback to detect the failure, no refund path, and no way to reconstruct the lost balance.

## Likelihood Explanation
The migration flow is a production feature (DAO-callable `migrate_deployed_token` + user-callable `ft_transfer_call` with `SwapMigratedToken`). NEP-141 storage registration is a separate, non-obvious prerequisite that many users will not know to perform before swapping. There is no on-chain guard, pre-check, or documentation enforcing registration before the swap. The loss is triggered accidentally (not only by a malicious actor), making it a high-likelihood event during any real migration. Any unprivileged token holder can trigger this by simply calling `ft_transfer_call` on the old token without having previously called `storage_deposit` on the new token.

## Recommendation
Replace the parallel `burn.and(mint)` with a sequential, callback-guarded pattern:
1. Call `mint(new_token, sender_id, amount, None)` first.
2. In the callback, check success: if mint succeeded, call `burn(old_token, amount)`; if mint failed, refund the old tokens to `sender_id` via `ft_transfer`.

Alternatively, before issuing any promises, verify that `sender_id` is registered in the new token via `storage_balance_of`, and panic (causing `ft_resolve_transfer` to refund the full amount) if not registered.

The `.detach()` on the joint promise must be replaced with a proper callback that handles partial failure.

## Proof of Concept
```
# Localnet test (no mainnet interaction)
1. Deploy old_token (omni-token), new_token (omni-token), bridge.
2. DAO calls bridge.migrate_deployed_token(chain, old_token, new_token).
3. Register sender in old_token; mint 1000 old tokens to sender.
4. Do NOT call new_token.storage_deposit for sender.
5. sender calls old_token.ft_transfer_call(bridge, 1000, "SwapMigratedToken").
6. Assert: sender's old_token balance = 0 (burned).
7. Assert: sender's new_token balance = 0 (mint failed, not registered).
8. Assert: bridge's old_token balance = 0 (burned).
9. Net result: 1000 tokens permanently destroyed.
```
