### Title
Unguarded Fallthrough in `ft_transfer` Panics When Withdraw Relayer Is Unset — (`contracts/nbtc/src/lib.rs`)

### Summary

When `WITHDRAW_RELAYER_ADDRESS` is absent from storage, any registered nBTC holder can trigger a panic in `ft_transfer` by sending to `receiver_id = env::current_account_id()` with a `WITHDRAW_TO:`-prefixed memo. The outer intercept block falls through to the standard `FungibleToken::ft_transfer` with the nBTC contract itself as receiver, which panics because the contract is never registered as a token holder.

### Finding Description

`ft_transfer` contains a legacy Near Intents withdrawal intercept: [1](#0-0) 

When both conditions are true (`receiver_id == current_account_id()` AND memo starts with `"WITHDRAW_TO:"`), the code enters the outer `if` block. If `read_withdraw_relayer_address()` returns `None` (storage key absent), the inner `if let Some(...)` is skipped and execution falls through to line 195:

```rust
self.token.ft_transfer(receiver_id, amount, memo);
//                     ^^^^^^^^^^^ = env::current_account_id()
```

The standard `FungibleToken::ft_transfer` calls `internal_transfer` → `internal_deposit`, which panics with "The account is not registered" because the nBTC contract's own account is never registered as a token holder. The constructor only registers `bridge_id`: [2](#0-1) 

`set_withdraw_relayer_address` is controller-gated and optional — there is no guarantee it is called before users attempt the legacy withdrawal path: [3](#0-2) 

### Impact Explanation

- The caller's transaction panics and reverts; their tokens are not transferred (no funds lost).
- The legacy Near Intents withdrawal path (`ft_transfer` → `WITHDRAW_TO:` memo) is completely broken for every user who attempts it while the relayer is unset or has been cleared.
- This violates the NEP-141 invariant that `ft_transfer` with a valid sender balance and a valid (registered) sender must not panic due to internal contract state.

### Likelihood Explanation

The precondition (relayer not set) is realistic during initial deployment, after a relayer rotation that clears the key, or on any fork/test deployment. Any registered nBTC holder can trigger it with a single public call — no privilege required.

### Recommendation

Add an explicit guard when the relayer is absent so the call fails with a clear error instead of falling through:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
self.token.ft_transfer(receiver_id, amount, memo);
```

### Proof of Concept

1. Deploy nBTC contract without calling `set_withdraw_relayer_address`.
2. Register a user account and mint nBTC to it.
3. Call `ft_transfer(nbtc_contract_id, 1, Some("WITHDRAW_TO:bc1qxxx"))` with 1 yoctoNEAR attached from the user.
4. Observe: transaction panics with "The account is not registered" (or equivalent from `internal_deposit`), confirming the fallthrough path at line 195 reaches the unregistered receiver. [4](#0-3)

    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // Legacy bridging flow used by Near Intents
        if receiver_id == env::current_account_id()
            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
        {
            if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
                return self.token.ft_transfer(withdraw_relayer, amount, memo);
            }
        }

        self.token.ft_transfer(receiver_id, amount, memo);
    }
