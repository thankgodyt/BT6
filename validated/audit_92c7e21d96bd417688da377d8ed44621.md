### Title
Missing Vote Signature Verification in `validatePerasVote` Enables Unauthorized Peras Certificate Forging — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasVote` implementation is a stub that accepts any vote from a known voter ID without performing cryptographic signature verification. An unprivileged peer can forge `PerasVote` messages claiming to be any voter in the stake distribution. Because the production vote-ingestion path calls this stub directly, forged votes accumulate in the `PerasVoteDB` with the impersonated voter's full stake weight. Once the accumulated stake crosses the quorum threshold, a `ValidatedPerasCert` is forged for the attacker's chosen block, boosting it in chain selection.

---

### Finding Description

**Root cause — stub validation in the catch-all `BlockSupportsPeras` instance:** [1](#0-0) 

The instance comment reads *"TODO: degenerate instance for all blks to get things to compile"*. The `validatePerasVote` body only performs a map lookup on the voter ID; it ignores `_params` entirely and never calls any signature-verification primitive:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

**Production call site — peer-facing vote ingestion:**

`makePerasVotePoolWriterFromChainDB` (the production writer used by the Peras vote mini-protocol) passes this stub directly as the `validateVote` callback inside `processVotes`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` rejects only votes whose ID is already in the DB; every other vote that passes `validateVote` is timestamped and forwarded to `ChainDB.addPerasVoteWithAsyncCertHandling`: [4](#0-3) 

**Downstream quorum trigger:**

Once a forged vote is stored, `updateCandidateVoteState` calls `votesReachQuorum`, which sums `vpvVoteStake` values and compares against the quorum threshold via `stakeAboveThreshold`. If the impersonated voter holds sufficient stake, a single forged vote suffices to cross the threshold: [5](#0-4) [6](#0-5) 

When quorum is reached, `forgePerasCert` is called and a `ValidatedPerasCert` is produced for the attacker's target block. The default `forgePerasCert` stub also performs no verification: [7](#0-6) 

**Compounding issue — `stakeAboveThreshold` unit mismatch:**

An explicit TODO in the same file warns that `stakeAboveThreshold` assumes `PerasVoteStake` and the quorum threshold are expressed in the same units (both relative), but there is no enforcement of this invariant. If the `PerasVoteStakeDistr` is populated with absolute ledger-stake values while the threshold is relative (e.g. 0.75), a single vote carrying absolute stake ≥ 1 trivially satisfies the check regardless of the voter's true share: [8](#0-7) 

---

### Impact Explanation

An unprivileged peer can:

1. Enumerate `PerasVoterId` values present in the public stake distribution.
2. Craft a `PerasVote` naming a high-stake voter and any desired target block.
3. Send it over the Peras vote mini-protocol; `validatePerasVote` accepts it (no signature check).
4. The vote is stored in `PerasVoteDB` with the impersonated voter's full `PerasVoteStake`.
5. `votesReachQuorum` detects quorum; `forgePerasCert` produces a `ValidatedPerasCert` for the attacker's block.
6. The certificate is stored in `PerasCertDB` and applied to chain selection, boosting the attacker's block by `perasWeight`.

This constitutes a **bypass of Peras vote/certificate verification** that lets an unprivileged peer make an honest node accept an unauthorized certificate and prefer a non-canonical chain — matching the "High" impact tier (unauthorized certificate acceptance enabling chain-selection manipulation).

---

### Likelihood Explanation

The Peras vote mini-protocol is reachable by any connected peer. No private keys, operator access, or stake majority is required. The attacker only needs to know a valid `PerasVoterId` (public information derivable from the ledger stake snapshot). The attack is deterministic and reproducible on a private testnet with the current codebase.

---

### Recommendation

1. **Implement real signature verification in `validatePerasVote`**: verify the vote's BLS signature against the voter's public key retrieved from the committee selection context (the `verifyVoteSignature` primitive already exists in `Ouroboros.Consensus.Committee.Crypto`).
2. **Implement real certificate verification in `validatePerasCert`**: call `verifyCert` from the appropriate `CryptoSupportsVotingCommittee` instance before accepting any certificate.
3. **Enforce unit consistency in `stakeAboveThreshold`**: either normalize `PerasVoteStake` to a relative value before the comparison, or change the function signature to accept the total committee stake and perform normalization internally, eliminating the implicit assumption documented in the TODO.

--
-- Precondition: node is running with Peras enabled; stake distribution
-- contains voter V with PerasVoteStake s where s >= quorumThreshold + safetyMargin.

let forgedVote = PerasVote
      { pvVoteRound   = currentRound
      , pvVoteBlock   = attackerChosenBlock   -- any block the attacker wants to boost
      , pvVoteVoterId = V                     -- impersonated high-stake voter
      }

-- Send forgedVote to the target node via the Peras vote mini-protocol.
-- processVotes calls:
--   validatePerasVote mkPerasParams stakeDistr forgedVote
--   => lookupPerasVoteStake forgedVote stakeDistr = Just s   (no sig check)
--   => Right (ValidatedPerasVote { vpvVoteStake = s })
--
-- updateCandidateVoteState then calls votesReachQuorum:
--   totalVoteStake = s >= quorumThreshold + safetyMargin  => True
--   forgePerasCert produces ValidatedPerasCert for attackerChosenBlock
--
-- Chain selection now boosts attackerChosenBlock by perasWeight,
-- causing honest nodes to prefer the attacker's chain.
```

The structural parallel to M-08 is exact: just as the ERC721Votes `_delegate` function lacked a guard against `address(0)` — allowing vote accounting to underflow — `validatePerasVote` lacks a guard against unsigned votes, allowing any peer to inject arbitrary stake weight into the quorum tally.

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
