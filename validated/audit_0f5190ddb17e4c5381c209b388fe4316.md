### Title
Unvalidated `refund_address` Causes `build_refund_output` Panic on Network Mismatch — (`contracts/satoshi-bridge/src/network.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` accepts and stores a `refund_address` string with no validation against the bridge's configured chain. When `execute_refund` later calls `build_refund_output`, it calls `Address::parse(refund_address, config.chain)` and unwraps the result with `.expect("Invalid refund address")`. If the stored address belongs to the wrong Zcash network (e.g., a testnet P2SH address on a ZcashMainnet bridge), `convert_if_network` returns `Err`, the `.expect()` panics, and the refund transaction can never be built.

---

### Finding Description

**Step 1 — Public entrypoint: `request_refund`**

`request_refund` is publicly callable (no per-method `#[trusted_relayer]` guard; the comment at line 487 explicitly states "anyone can call `execute_refund`", and the same pattern applies to `request_refund`). It accepts a free-form `refund_address: String` and passes it to `internal_request_refund`. [1](#0-0) 

**Step 2 — Address stored without chain validation**

`request_refund_callback` verifies the deposit transaction via the light client and checks the output script, but it never validates that `refund_address` is a valid address for the bridge's configured chain. The raw string is stored directly in `RefundRequest`. [2](#0-1) 

**Step 3 — `execute_refund` → `execute_refund_callback` → `build_refund_output`**

For a transparent (non-Orchard) refund, `execute_refund_callback` calls `build_refund_output` with the stored `refund_address`. [3](#0-2) 

**Step 4 — `.expect()` on `Address::parse` result**

`build_refund_output` calls `Address::parse(refund_address, config.chain)` and immediately unwraps with `.expect("Invalid refund address")`. There is no graceful error path. [4](#0-3) 

**Step 5 — `Address::parse` returns `Err` on network mismatch**

For Zcash chains, `Address::parse` calls `ZcashAddress::try_from_encoded` (which succeeds for any valid Zcash address regardless of network) and then `convert_if_network::<Self>(NetworkType::Main)`. If the address is a testnet address, `convert_if_network` returns `Err` (network mismatch), which propagates out of `Address::parse` as `Err(...)`. [5](#0-4) 

**Clarification on the "prefix overlap" claim:** The question states there is a P2SH prefix overlap between mainnet (`[0x1C, 0xBD]`) and testnet (`[0x1C, 0xBA]`). These prefixes are distinct — the second byte differs. There is no overlap. However, this does not affect the vulnerability: `ZcashAddress::try_from_encoded` parses both mainnet and testnet addresses successfully, and the network rejection happens inside `convert_if_network`, not during prefix decoding. [6](#0-5) 

---

### Impact Explanation

Every call to `execute_refund` for a refund request with a cross-network address will panic. The refund PSBT is never built, the UTXO is never signed, and the user's deposit remains locked in the bridge. The DAO/Operator can reject the malicious refund request via `reject_refund`, but an attacker can front-run the victim's `request_refund` call with a testnet address, forcing the DAO to intervene before the victim can submit a valid request. This constitutes attacker-triggered temporary locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

- `request_refund` is publicly callable by any NEAR account with the required storage deposit.
- Deposit transactions are visible on-chain, so an attacker can observe any unrefunded deposit and front-run the victim's `request_refund`.
- The attack requires no privileged role, no key compromise, and no external dependency.
- The only mitigation is DAO/Operator rejection of the malicious request, which is reactive and requires manual intervention.

---

### Recommendation

Validate `refund_address` against the bridge's configured chain at `request_refund_callback` time, before storing it. Replace the `.expect()` in `build_refund_output` with proper error propagation so a bad address causes a clean `require!` failure rather than a panic.

---

### Proof of Concept

1. Bridge is deployed with `config.chain = ZcashMainnet`.
2. Victim deposits ZEC to the bridge's deposit address.
3. Attacker observes the deposit transaction on-chain and calls `request_refund` with:
   - `refund_address = "t26YqBabLj2kpZUPd3xCBhVHucMSV83GWSw"` (a valid ZcashTestnet P2SH address)
   - Valid `deposit_msg`, `tx_bytes`, `vout`, and `proof` for the victim's deposit
4. `request_refund_callback` stores the testnet address without validation.
5. After the timelock, anyone calls `execute_refund`.
6. `execute_refund_callback` calls `build_refund_output("t26YqBabLj2kpZUPd3xCBhVHucMSV83GWSw", refund_amount)`.
7. `Address::parse("t26YqBabLj2kpZUPd3xCBhVHucMSV83GWSw", ZcashMainnet)`:
   - `ZcashAddress::try_from_encoded(...)` → `Ok(testnet_addr)`
   - `convert_if_network::<Address>(NetworkType::Main)` → `Err("network mismatch")`
   - Returns `Err(...)`
8. `.expect("Invalid refund address")` panics. Transaction reverts.
9. The victim's deposit UTXO is locked until the DAO rejects the malicious request.
