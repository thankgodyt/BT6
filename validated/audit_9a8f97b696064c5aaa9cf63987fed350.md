### Title
Peras Quorum Bypass via Unit Mismatch Between Absolute Vote Stake and Relative Quorum Threshold — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` (accumulated from individual votes) directly against `perasQuorumStakeThreshold` (a relative `Rational` like `3/4`) without any normalization. The code itself documents this as an unresolved unit mismatch. When the `PerasVoteStakeDistr` is populated with absolute lovelace amounts from the ledger — as the comments explicitly anticipate — a single vote from any pool with positive stake will satisfy the quorum check, allowing an adversarial peer to forge a Peras certificate for an arbitrary block.

---

### Finding Description

`PerasVoteStake` is a bare `Rational` wrapper with no enforced unit: [1](#0-0) 

The code comment at lines 136–143 explicitly states that the ledger provides **absolute** stake values and that there is currently no agreed-upon method to convert them to the **relative** values that the quorum threshold requires.

`stakeAboveThreshold` then performs a direct numeric comparison between the accumulated `PerasVoteStake` and the relative threshold `perasQuorumStakeThreshold` (set to `3/4` in `mkPerasParams`): [2](#0-1) 

The TODO comment at lines 155–161 explicitly acknowledges the assumption that both operands must be in the same unit, and that normalization is missing.

`votesReachQuorum` calls `stakeAboveThreshold` after summing all `vpvVoteStake` values via `mconcat`: [3](#0-2) 

`updateLoserVoteState` in `Aggregation.hs` also calls `stakeAboveThreshold` on the raw accumulated tally: [4](#0-3) 

The production vote inbound path in `NodeToNode.hs` currently passes `pure (PerasVoteStakeDistr mempty)` as a placeholder, with a TODO noting that the actual ledger committee selection data must be wired in: [5](#0-4) 

When that wiring is completed — as the code explicitly anticipates — the `PerasVoteStakeDistr` will contain absolute lovelace amounts (e.g., `1_000_000_000 % 1` for a pool with 1 billion lovelace). Comparing this against `3/4` evaluates to `True` immediately, meaning **any single vote from any pool with positive stake satisfies the quorum**.

The `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` functions both accept an externally-supplied `STM m PerasVoteStakeDistr`, confirming the stake distribution is an external input: [6](#0-5) 

---

### Impact Explanation

When the ledger stake distribution is wired in (the intended production state), an adversarial peer can send a single `PerasVote` message via the Peras vote diffusion mini-protocol. Because the voter's absolute lovelace stake (e.g., `1_000_000_000`) is numerically far greater than the relative quorum threshold (`3/4`), `stakeAboveThreshold` returns `True` immediately. `votesReachQuorum` then returns a `ValidatedPerasVotesWithQuorum`, `forgePerasCert` produces a `ValidatedPerasCert`, and the certificate is accepted into the ChainDB. The certificate boosts the adversary's chosen block by `perasWeight` (default: 15 blocks) in chain selection, causing honest nodes to prefer the adversary's chain over the canonical chain. This is a **Critical** bypass of the Peras certificate quorum requirement.

---

### Likelihood Explanation

The bug is triggered the moment the `PerasVoteStakeDistr` is populated with absolute ledger values, which is the explicitly planned next step per the TODO in `NodeToNode.hs`. Any peer that can send a `PerasVote` message (i.e., any node-to-node peer) can exploit this. No special privileges, key compromise, or stake majority is required — only a valid voter identity present in the stake distribution with any positive stake.

---

### Recommendation

Before calling `stakeAboveThreshold`, normalize each voter's `PerasVoteStake` to a relative value by dividing by the total stake in the `PerasVoteStakeDistr`. Concretely, `stakeAboveThreshold` should accept the full `PerasVoteStakeDistr` and compute the normalized fraction internally, or `validatePerasVote` should store the pre-normalized relative stake. The type `PerasVoteStake` should be given a phantom unit tag (e.g., `Absolute` vs `Relative`) to make future unit confusion a compile-time error.

---

### Proof of Concept

With the stake distribution wired in as absolute lovelace values, the following sequence triggers the bug:

1. Populate `PerasVoteStakeDistr` with one entry: `voterId → PerasVoteStake (1_000_000_000 % 1)` (1 billion lovelace, a realistic pool size).
2. Send a single `PerasVote` from `voterId` for an adversary-chosen block via the vote diffusion mini-protocol.
3. `validatePerasVote` looks up the stake: `vpvVoteStake = PerasVoteStake (1_000_000_000 % 1)`.
4. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake (1_000_000_000 % 1))`.
5. The check evaluates: `1_000_000_000 >= 3/4 + 2/100` → `True`.
6. `forgePerasCert` produces a certificate for the adversary's block.
7. The certificate is stored in the ChainDB and boosts the adversary's block by 15 in chain selection.

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
