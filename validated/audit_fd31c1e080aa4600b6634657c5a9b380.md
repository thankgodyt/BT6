### Title
`validatePerasCert` Unconditionally Accepts Any Peras Certificate, Bypassing All Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that always returns `Right` without performing any cryptographic or committee-membership checks. Any unprivileged peer can send a crafted `PerasCert` over the object-diffusion mini-protocol; the certificate passes "validation" unconditionally, is stored in the `PerasCertDB`, and immediately influences chain selection by boosting an arbitrary block. This is a direct analog to the original report's pattern: a second code path (the stub validator) lacks the access-control checks that the intended path should enforce.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase — declared as a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — so it covers every block type, including production Cardano blocks. [2](#0-1) 

**Attacker-controlled entry path:**

The object-diffusion layer calls `makePerasCertPoolWriterFromChainDB`, which wires `validatePerasCert mkPerasParams` as the sole validation gate before forwarding the certificate to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`processCerts` calls `validateCert` on each inbound certificate; if all pass (they always do), each is timestamped and forwarded to `addCert`: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which processes it and may switch the node to a different chain based on the certificate's `vpcCertBoost` weight: [5](#0-4) [6](#0-5) 

**Exploit path:**
1. Attacker peer connects via the Peras object-diffusion mini-protocol (no credentials required).
2. Peer sends a crafted `PerasCert` naming any block point and any round number.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
4. The certificate is stored in `PerasCertDB` and enqueued via `addPerasCertAsync`.
5. `chainSelSync` processes the certificate; the boosted block gains `vpcCertBoost` weight in chain selection, potentially causing the honest node to switch to the attacker's preferred (non-canonical) chain.

**Analog to original report:**
- Original: `createAgentWithNFT` lacked the whitelist check present in `createAgentWithWhitelistUsers`.
- Here: `validatePerasCert` (the only validation gate) lacks the committee-membership and cryptographic checks that the `BlockSupportsPeras` contract requires, while `processCerts` assumes the returned `Right` value is genuinely validated.

### Impact Explanation

An unprivileged peer can inject arbitrary Peras certificates with no cryptographic proof of committee membership or quorum. Each accepted certificate boosts an attacker-chosen block in chain selection. By injecting certificates for a minority fork, the attacker can cause honest nodes to prefer a non-canonical chain, constituting a **chain-selection safety failure**. This maps to:

> **Critical** — Bypass of Peras certificate checks that enables unauthorized certificate acceptance.
> **High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

### Likelihood Explanation

The object-diffusion mini-protocol is reachable by any peer without authentication. The stub is the universal instance for all block types. No special stake, keys, or operator access is required. Likelihood is **High** once Peras is active on a network that uses this code.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the certificate's aggregate BLS/committee signature against the declared voter set.
2. Confirms each declared voter was eligible (VRF-sortition or persistent-committee membership) for the claimed round.
3. Confirms the total weight of eligible voters meets the quorum threshold.

Until a real implementation is available, `processCerts` should reject all inbound certificates (return `Left PerasValidationErr`) rather than accept them unconditionally, so the stub cannot be exploited.

### Proof of Concept

```
1. Connect to a Cardano node running this code via the Peras object-diffusion
   mini-protocol (standard NtN connection, no credentials).

2. Send a PerasCert message:
     PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <attacker fork tip> }

3. processCerts calls validatePerasCert mkPerasParams cert
   => always returns Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }

4. addPerasCertAsync enqueues the cert; chainSelSync runs.

5. The attacker's fork tip now carries vpcCertBoost weight in chain selection.
   If the fork is otherwise plausible, the honest node switches to it.
```

No stake, no keys, no operator access required. The only precondition is a standard peer connection.
