Audit Report

## Title
Native Fee (ETH) Permanently Frozen in EVM Bridge on NEAR-Side `ft_transfer_call` Rejection - (File: near/omni-bridge/src/lib.rs)

## Summary
When a cross-chain EVM→NEAR transfer includes a non-zero `native_fee` and a non-empty `msg` field, the EVM bridge retains the user's ETH. If the NEAR-side recipient contract rejects the tokens via `ft_on_transfer`, `fin_transfer_send_tokens_callback` enters the refund branch, which correctly reverts the NEP-141 token state but never mints or returns the `native_fee`. The ETH remains permanently locked in the EVM bridge contract with no on-chain recovery path.

## Finding Description
The function `fin_transfer_send_tokens_callback` at `near/omni-bridge/src/lib.rs:1692` handles two outcomes of a `ft_transfer_call`. When `is_ft_transfer_call = true` and the recipient returns 0 (full rejection), `is_refund_required` evaluates to `true` and the refund branch executes:

```rust
// L1702–1718
if Self::is_refund_required(is_ft_transfer_call) {
    self.burn_tokens_if_needed(token.clone(), ...);   // NEP-141 handled
    self.revert_lock_actions(&lock_actions);           // NEAR-side accounting only
    self.remove_fin_transfer(...);
    env::log_str(&OmniBridgeEvent::FailedFinTransferEvent { ... });
    // native_fee: never touched
}
``` [1](#0-0) 

`revert_lock_actions` only adjusts NEAR-side `locked_tokens` accounting; it has no cross-chain effect on the EVM contract. [2](#0-1) 

The success branch, by contrast, explicitly mints the wrapped native token to the fee recipient:

```rust
// L1736–1743
if transfer_message.fee.native_fee.0 > 0 {
    let native_token_id = self.get_native_token_id(...);
    ext_token::ext(native_token_id)
        .with_static_gas(MINT_TOKEN_GAS)
        .mint(fee_recipient.clone(), transfer_message.fee.native_fee, None)
        .detach();
}
``` [3](#0-2) 

The `FailedFinTransferEvent` emitted is a plain log, not a cross-chain message; it does not trigger any EVM-side refund. The ETH is therefore irrecoverably locked.

## Impact Explanation
This is a **permanent freezing of bridged user funds**. The `native_fee` is ETH deposited by the user into the EVM bridge contract at transfer initiation. When the NEAR-side refund path executes without minting or returning this ETH, it is frozen in the EVM contract indefinitely. This matches the allowed critical impact: *"permanent freezing of bridged funds across NEAR, EVM … flows."*

## Likelihood Explanation
Any user who sends a transfer with a non-zero `nativeFee` and a non-empty `msg` to a recipient contract that rejects tokens (returns 0 from `ft_on_transfer`) triggers this path. This is reachable by an unprivileged external user through the standard cross-chain transfer flow. A malicious recipient contract can deliberately reject tokens to guarantee the sender's ETH fee is frozen. The condition is fully controllable by the attacker (who can deploy the recipient contract) or occurs naturally when a legitimate recipient rejects an incompatible transfer.

## Recommendation
In the refund branch of `fin_transfer_send_tokens_callback`, add handling for `native_fee` symmetric to the success path. Options:
1. **Mint wrapped native token back to the original sender** (requires passing sender address into the callback).
2. **Emit a cross-chain message** to the EVM bridge instructing it to refund the ETH to the original sender.
3. At minimum, **mint to the fee recipient** (relayer) so the ETH is not frozen, consistent with the relayer having performed work.

The fix must be applied inside the `if Self::is_refund_required(is_ft_transfer_call)` block, mirroring the `native_fee` mint logic already present in the `else` branch.

## Proof of Concept
1. Deploy a malicious NEAR contract implementing `ft_on_transfer` that always returns the full amount (rejecting all tokens).
2. On EVM, call `initTransfer` with a non-zero `nativeFee` (send ETH) and a `message` field pointing to the malicious contract.
3. Wait for the relayer to call `fin_transfer` on NEAR, which calls `ft_transfer_call` to the malicious contract.
4. The malicious contract returns the full amount; `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = true`.
5. Observe: NEP-141 tokens are burned/reverted correctly; `native_fee` is never minted or returned.
6. Verify: the ETH remains in the EVM bridge contract with no callable function to release it.

A unit test in `near/omni-bridge/src/tests/lib_test.rs` can mock `ft_transfer_call` returning full rejection and assert that `native_fee` is handled in the callback — currently this assertion will fail, confirming the bug.

    pub fn revert_lock_actions(&mut self, lock_actions: &[LockAction]) {
        for lock_action in lock_actions {
            match lock_action {
                LockAction::Locked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.unlock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unlocked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.lock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unchanged => {}
            }
        }
    }
