Audit Report

## Title
Tokens Permanently Frozen When Initiating Transfer to Chain Where Token Is Not Registered - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` burns (for bridge-minted tokens) or locks (for native NEAR tokens) user funds before any check that the token has a registered address on the destination chain. When `sign_transfer` is later called, it panics with `FailedToGetTokenAddress` if no mapping exists, reverting only that transaction while the prior burn/lock and `pending_transfers` entry remain committed. No public cancel or refund path exists, leaving funds permanently frozen.

## Finding Description

**Step 1 — `init_transfer` validates only that the recipient chain is not NEAR:** [1](#0-0) 

No check is made that the token has a registered address on the destination chain.

**Step 2 — `init_transfer_internal` unconditionally burns/locks and returns `U128(0)`:** [2](#0-1) 

- `burn_tokens_if_needed` fires a detached cross-contract burn call for bridge-minted tokens; the `.detach()` means the burn is committed regardless of what happens next. [3](#0-2) 

- `lock_tokens_if_needed` increments the `locked_tokens` counter for native NEAR tokens (only if an entry already exists for that `(chain, token)` pair; otherwise the tokens simply sit in the bridge's account with no tracking). [4](#0-3) 

Returning `U128(0)` signals the NEP-141 token contract that all tokens were consumed — no refund is issued.

**Step 3 — `sign_transfer` panics if the token is unregistered:** [5](#0-4) 

This panic reverts only the `sign_transfer` transaction. The `pending_transfers` entry and the burn/lock from Step 2 are already finalized on-chain and are unaffected.

**Step 4 — `sign_transfer_callback` only removes the transfer on MPC success:** [6](#0-5) 

Because `sign_transfer` panics before the MPC call is ever made, `sign_transfer_callback` is never reached. The `pending_transfers` entry is never cleaned up.

**No recovery path exists.** A search across the contract confirms there is no public `cancel_transfer`, `refund_transfer`, or equivalent function. `remove_transfer_message_without_refund` is only called internally when storage balance checks fail (before burning/locking), and `remove_transfer_message` is only called inside `sign_transfer_callback` on MPC success.

## Impact Explanation

This concretely matches the allowed Critical impact: **permanent freezing of bridged funds**.

- **Bridge-minted (deployed) tokens**: `burn_tokens_if_needed` destroys the tokens on NEAR via a detached call. No corresponding release occurs on the destination chain. The loss is irreversible.
- **Native NEAR tokens**: tokens are transferred into the bridge contract and either tracked in `locked_tokens` or simply held in the bridge's account with no user-accessible recovery. An admin could theoretically register the token post-hoc, but this is not guaranteed and leaves funds at risk indefinitely.

In both cases the user has no self-service path to recover funds.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` on a NEP-141 token with a recipient on a chain where that token has no registered address. The bridge supports 13 destination chains; tokens are commonly registered for only a subset. A realistic accidental scenario: a user holds a NEAR-side bridge token that originated from Ethereum and attempts to send it to Arbitrum instead of back to Ethereum. No attacker capability is required — this is a normal user mistake with permanent consequences.

## Recommendation

Add a pre-flight check in `init_transfer` (before `init_transfer_internal` is called) that verifies the token has a registered address for the destination chain. If not, return the full `amount` to trigger a refund:

```rust
// In init_transfer, before calling init_transfer_internal:
let destination_chain = init_transfer_msg.recipient.get_chain();
if self.get_token_address(destination_chain, token_id.clone()).is_none() {
    return PromiseOrPromiseIndexOrValue::Value(amount); // refund to sender
}
```

Additionally, add an emergency `cancel_transfer` function (callable by the original sender or DAO) that removes a stuck `pending_transfers` entry and re-mints/unlocks the corresponding tokens.

## Proof of Concept

1. Token `foo.near` is a bridge-minted token registered for `ChainKind::Eth` but not `ChainKind::Arb`.
2. User calls `ft_transfer_call` on `foo.near` with `receiver_id = omni-bridge.near` and `msg = {"recipient": "arb:0xRecipient", "fee": "0", ...}`.
3. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `burn_tokens_if_needed("foo.near", amount)` fires a detached burn — tokens destroyed.
   - `init_transfer_internal` returns `U128(0)` — token contract issues no refund.
   - `pending_transfers` entry is committed.
4. Relayer calls `sign_transfer` for the stuck transfer ID.
5. `get_token_address(ChainKind::Arb, "foo.near")` returns `None`.
6. `env::panic_str(BridgeError::FailedToGetTokenAddress...)` — `sign_transfer` transaction reverts.
7. `pending_transfers` entry remains; tokens remain burned.
8. Steps 4–7 repeat indefinitely. No recovery path exists.

A local integration test can confirm this by: (a) deploying the bridge with `foo.near` registered only for Eth, (b) calling `ft_transfer_call` with an Arb recipient, (c) asserting `U128(0)` is returned and the `pending_transfers` entry exists, (d) calling `sign_transfer` and asserting it panics, (e) asserting the `pending_transfers` entry is unchanged and the token supply has decreased.
