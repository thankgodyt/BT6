### Title
Unvalidated `key_version` Parameter in `sign_btc_transaction` Passed to MPC Signing Service - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary

The public `sign_btc_transaction` function accepts a caller-supplied `key_version: u32` parameter and passes it directly to the NEAR chain signatures (MPC) service without any validation. There is no ownership check on the function — any NEAR account can invoke it for any pending withdrawal transaction. If the MPC service signs with a wrong key version, the resulting signature is cryptographically invalid for the UTXO's script pubkey, causing the assembled Bitcoin transaction to be rejected by the network and the user's nBTC tokens to be temporarily locked in the bridge.

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is a public, payable function with no role restriction beyond the global pause:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,          // ← fully caller-controlled, never validated
) -> PromiseOrValue<bool> {
```

It delegates to `internal_sign_btc_transaction` in `contracts/satoshi-bridge/src/chain_signature.rs`, which constructs a `SignRequest` and forwards `key_version` verbatim to the MPC service:

```rust
self.sign_promise(SignRequest {
    payload,
    path,
    key_version,   // ← no check that this equals the expected version (0)
})
```

The contract stores no expected `key_version` in its config and performs no comparison before the cross-contract call. The `sign_btc_transaction_callback` stores whatever signature the MPC service returns:

```rust
btc_pending_info.signatures[sign_index] = Some(signature.clone());
```

Once all signature slots are filled, `psbt.extract_tx_bytes_with_sign()` assembles the final transaction and the state transitions to `PendingVerify`. If any slot was filled with a signature produced under the wrong key version, the assembled transaction carries an invalid witness and will be rejected by Bitcoin nodes.

**Attack path:**

1. User calls `nbtc.ft_transfer_call` → tokens transferred to bridge, `BTCPendingInfo` created in `PendingSign` state.
2. Attacker (any NEAR account) calls `sign_btc_transaction(pending_id, sign_index, 1)` with a non-zero `key_version`, attaching the required NEAR deposit.
3. MPC service signs the payload under key version 1 (a different key than the one controlling the UTXO) and returns a valid-looking `SignatureResponse`.
4. Callback stores the wrong signature; once all slots are filled, the bridge emits `SignedBtcTransaction` and moves to `PendingVerify`.
5. Relayer broadcasts the transaction; Bitcoin nodes reject it (signature does not satisfy the P2WPKH/P2TR script derived from key version 0).
6. `verify_withdraw_v2` is never called; the user's nBTC tokens remain locked in the bridge.

Recovery requires the user to invoke `withdraw_rbf` to create a new PSBT with fresh signature slots. The attacker can repeat the attack on each RBF attempt, sustaining the lock as long as they are willing to pay MPC signing fees.

### Impact Explanation

The user's nBTC tokens are transferred to the bridge at withdrawal initiation and are not returned until `verify_withdraw_v2` burns them. An invalid Bitcoin transaction never confirms, so the burn never occurs. The user's funds are locked in the bridge for an indefinite period, recoverable only through repeated RBF cycles that the attacker can keep invalidating. This constitutes attacker-triggered temporary locking of bridged funds.

### Likelihood Explanation

`sign_btc_transaction` is a public, permissionless function. Any NEAR account can call it for any pending withdrawal. The attacker must attach NEAR to cover the MPC signing fee, but this cost is bounded and predictable. The attack requires no privileged access, no leaked keys, and no governance control — only the ability to submit a NEAR transaction before the legitimate relayer.

### Recommendation

Validate `key_version` against the expected value before forwarding to the MPC service. The simplest fix is to hardcode the expected version or store it in the contract config and enforce it:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    require!(
        key_version == self.internal_config().expected_key_version,
        "Invalid key_version"
    );
    // ... rest of function
}
```

Additionally, consider restricting `sign_btc_transaction` to trusted relayers (via `#[trusted_relayer]` or an explicit role check) to prevent arbitrary accounts from triggering MPC signing requests.

### Proof of Concept

1. Alice initiates a withdrawal: `nbtc.ft_transfer_call(bridge, 100_000, WithdrawMsg{...})` → `BTCPendingInfo` created with id `"pending_abc"`, state `PendingSign`, one signature slot.
2. Attacker calls: `bridge.sign_btc_transaction("pending_abc", 0, 1)` with 1 NEAR attached.
3. MPC service signs payload under key version 1 → returns `SignatureResponse`.
4. `sign_btc_transaction_callback` stores the signature; `is_all_signed()` returns `true`; `extract_tx_bytes_with_sign()` assembles the transaction; state → `PendingVerify`.
5. Relayer broadcasts the transaction; Bitcoin rejects it (wrong key).
6. Alice's 100,000 satoshis worth of nBTC remain locked in the bridge.
7. Alice calls `withdraw_rbf` → new PSBT created → attacker repeats step 2 → cycle continues.
