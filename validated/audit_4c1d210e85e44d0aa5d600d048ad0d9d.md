Audit Report

## Title
Permanent Fund Loss via Decimal Normalization Truncation to Zero in `sign_transfer` - (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a token's NEAR-side decimal count (`decimals`) is less than its origin-chain decimal count (`origin_decimals`), the floor division in `normalize_amount` can reduce a small-but-nonzero NEAR amount to zero. Because `init_transfer_internal` irreversibly burns or locks tokens before any relayer ever calls `sign_transfer`, and no `cancel_transfer` or admin-recovery path exists, the user's funds are permanently lost with the transfer record stuck in `pending_transfers` indefinitely.

## Finding Description

`normalize_amount` converts a NEAR-native amount to the destination-chain precision via floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

In `sign_transfer`, the normalized value is checked to be nonzero before the MPC signing request is dispatched:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the division truncates to zero and `sign_transfer` panics. This panic occurs **after** the user's tokens have already been irreversibly consumed in `init_transfer_internal`:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
``` [3](#0-2) 

`burn_tokens_if_needed` issues a fire-and-forget `.detach()` burn call, and `lock_tokens_if_needed` increments the locked-token counter — both committed before any relayer calls `sign_transfer`: [4](#0-3) 

The `init_transfer` entry point only validates `fee.fee < amount`; it performs no pre-flight check that `normalize_amount(amount - fee, decimals) > 0`: [5](#0-4) 

`remove_transfer_message` is only reachable via `sign_transfer_callback` (after a successful MPC signature) or `claim_fee_callback` — neither of which is reachable when `sign_transfer` itself panics: [6](#0-5) 

No `cancel_transfer`, `refund_transfer`, or `recover_transfer` function exists anywhere in the contract.

The `#[trusted_relayer]` restriction on `sign_transfer` is irrelevant to the loss: the tokens are burned/locked at `init_transfer_internal` time, before any relayer is involved. Even if no relayer ever calls `sign_transfer`, the funds are already gone and the transfer record is permanently stuck in `pending_transfers`.

The code comment at line 2781–2783 acknowledges floor-division dust behavior ("When fee = 0, dust stays locked/burned"), but this refers to sub-unit remainders, not the case where the **entire** `amount_without_fee` normalizes to zero. [7](#0-6) 

## Impact Explanation

This is a **permanent freezing of bridged funds**. For bridge-deployed tokens, `burn_tokens_if_needed` destroys the tokens on NEAR with no mint on the destination chain. For native tokens, `lock_tokens_if_needed` locks them in the bridge with no corresponding release. The transfer record remains in `pending_transfers` forever, and every subsequent `sign_transfer` call for that transfer ID will always revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`. This matches the allowed critical impact: *permanent freezing of bridged funds* and *decimal/normalization abuse that changes user or protocol balances*.

## Likelihood Explanation

The condition is reachable by any unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` → `init_transfer_internal` path. No special role or privilege is required to initiate a transfer. The threshold below which the entire amount normalizes to zero is `10^(origin_decimals - decimals)` NEAR base units. For tokens with a large decimal gap (e.g., `origin_decimals=24`, `decimals=6`, divisor=`10^18`), any transfer below `10^18` base units (i.e., below 1 microtoken in NEAR representation) triggers the loss — a realistic amount. For the NEAR native token bridged to EVM (`origin_decimals=24`, `decimals=18`, divisor=`10^6`), the threshold is `10^6` yoctoNEAR, which is negligible in value but still reachable. The user can self-inflict this loss without any relayer cooperation.

## Recommendation

1. **Add a pre-flight check in `init_transfer` (before burning/locking)** that verifies `normalize_amount(amount - fee.fee, decimals) > 0`. Reject the transfer immediately and return the tokens to the user if this check fails.
2. Alternatively, enforce a protocol-level minimum transfer amount of `10^(origin_decimals - decimals)` at the `ft_on_transfer` / `init_transfer` entry point.
3. Add a `cancel_transfer` escape hatch callable by the original sender for transfers stuck in `pending_transfers` with no valid signing path, which reverses the burn/lock and removes the transfer record.

## Proof of Concept

**Setup**: Token registered with `Decimals { decimals: 18, origin_decimals: 24 }` (diff = 6, divisor = 1,000,000).

**Step 1** — User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`:
- `init_transfer_internal` is entered.
- `burn_tokens_if_needed` burns 500,000 tokens (detached, irreversible).
- `lock_tokens_if_needed` increments locked counter by 500,000.
- Transfer message stored in `pending_transfers`. Returns `U128(0)` — success from the user's perspective.

**Step 2** — Any trusted relayer calls `sign_transfer(transfer_id, ...)`:
- `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 })` = `500_000 / 1_000_000` = **0** (floor division).
- `require!(0 > 0, ...)` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.

**Result**: 500,000 tokens are burned/locked on NEAR. The transfer can never be signed. No refund mechanism exists. Funds are permanently lost.

**Reproducible test**: Write a unit test in `near/omni-bridge/src/tests/lib_test.rs` that registers a token with `Decimals { decimals: 18, origin_decimals: 24 }`, calls `ft_on_transfer` with `amount = 500_000` and `fee = 0`, then calls `sign_transfer` and asserts it panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Confirm that the transfer remains in `pending_transfers` and no recovery path exists.
