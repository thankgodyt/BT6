### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Arbitrary Peras Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. Any unprivileged peer can send a crafted `PerasCert` via the ObjectDiffusion miniprotocol; `processCerts` will call `validatePerasCert`, receive `Right`, and persist the certificate into the `PerasCertDB` / `ChainDB`, triggering Peras chain-selection side-effects for an attacker-chosen block.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must be passed before any externally received certificate is stored. The default instance, which covers all `StandardHash blk` block types, is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is not a dead code path. The production inbound-certificate pipeline in `makePerasCertPoolWriterFromChainDB` passes exactly this function as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

Inside `processCerts`, the result of `validateCert` is the sole gate between a peer-supplied `PerasCert` and a call to `addCert` (which persists the certificate and triggers chain selection):

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is never taken. Every certificate sent by any peer is treated as `ValidatedPerasCert` and forwarded to `ChainDB.addPerasCertAsync`, which then feeds into Peras chain selection.

The parallel to the external report is exact: just as `onTokenBridged()` processed arbitrary data without verifying the L1 sender, `processCerts` processes arbitrary certificates without verifying the issuer's identity, committee membership, or aggregate signature.

A secondary, related gap exists for votes: `validatePerasVote` checks only stake-distribution membership but performs no signature verification, also carrying a `TODO` for the same issue tracker entry. [4](#0-3) 

---

### Impact Explanation

Peras certificates carry a configurable `vpcCertBoost` weight that is added to the chain-selection score of the boosted block. An attacker who can inject a certificate for an arbitrary block point causes honest nodes to assign extra weight to that block, potentially making a weaker (or even invalid) chain appear heavier than the canonical chain. This is a direct bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: Bypass of certificate/vote verification checks that enables unauthorized certificate acceptance" impact category.

---

### Likelihood Explanation

The ObjectDiffusion miniprotocol is a standard peer-to-peer channel; any node that connects to a victim node can send `PerasCert` objects. No special privileges, keys, or stake are required. The attacker only needs to craft a `PerasCert` with a desired `pcCertRound` and `pcCertBoostedBlock`, connect to the target, and transmit it. The `processCerts` deduplication check (`Set.member roundNo alreadyInDb`) is the only remaining barrier, and it is trivially bypassed by choosing a round number not yet present in the database. [5](#0-4) 

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert`: verify the aggregate BLS signature over the claimed voter set, confirm each voter's committee membership and stake via the current ledger's stake distribution, and check that the certificate's round number is within the expected window. The existing `implVerifyCert` logic in `WFALS.hs` and `EveryoneVotes.hs` provides the correct template.

2. **Implement real vote validation** in `validatePerasVote`: verify the per-voter cryptographic signature (and VRF proof for non-persistent members) before accepting a vote into the `PerasVoteDB`.

3. **Remove or gate the degenerate default instance**: the `instance StandardHash blk => BlockSupportsPeras blk` stub should either be removed from production code or replaced with a version that rejects all certificates/votes until a proper implementation is wired in, rather than silently accepting everything. [6](#0-5)

### Proof of Concept

1. Attacker connects to a victim node via the ObjectDiffusion miniprotocol.
2. Attacker crafts a `PerasCert` with `pcCertRound = R` (any round not yet in the victim's `PerasCertDB`) and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. Attacker sends the certificate batch to the victim.
4. Victim's `makePerasCertPoolWriterFromChainDB` calls `processCerts`, which calls `validatePerasCert mkPerasParams cert`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
6. `processCerts` calls `ChainDB.addPerasCertAsync chainDB (WithArrivalTime now validatedCert)`.
7. The ChainDB stores the certificate and triggers a Peras chain-selection re-evaluation that assigns `vpcCertBoost` extra weight to the attacker-chosen block, potentially causing the victim to prefer a non-canonical chain. [2](#0-1) [1](#0-0)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
