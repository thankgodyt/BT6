### Title
Token Migration Permanently Blockable by Any nBTC Holder via Supply Mismatch — (File: `contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

The `migrate_to_new_token_mint` callback enforces a strict `sum == total_supply` invariant. Because any nBTC holder can transfer tokens to an address that was not included in the operator-supplied `accounts` list, an unprivileged user can permanently prevent the bridge from completing a token migration.

---

### Finding Description

`internal_migrate_to_new_token` accepts a caller-supplied list of `accounts` and queries `ft_balance_of` for each one, then queries `ft_total_supply` for the old token. In the callback `migrate_to_new_token_mint`, the contract enforces:

```rust
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [1](#0-0) 

If any nBTC balance exists in an account that was **not** included in the `accounts` list — even a single satoshi — `sum` will be strictly less than `total_supply` and the entire migration promise chain panics and reverts.

The operator must snapshot all holders off-chain and submit the list atomically. However, between the moment the snapshot is taken and the moment the cross-contract calls resolve, any of the following can happen without any privilege:

1. An existing holder calls `ft_transfer` to send tokens to a fresh address not in the list.
2. A new deposit is verified (`verify_deposit`) and mints tokens to a new recipient.
3. The bridge's own protocol-fee balance (`bridge_id`) accumulates additional tokens via a concurrent deposit.

Any of these events causes `sum < total_supply`, reverting the migration. The attacker can repeat this indefinitely, making migration permanently impossible. [2](#0-1) 

---

### Impact Explanation

A successful griefing attack permanently blocks the `migrate_to_new_token` flow. The bridge's `nbtc_account_id` is never updated:

```rust
// Only reached if migration mint succeeded:
self.internal_mut_config().nbtc_account_id = new_token.clone();
``` [3](#0-2) 

This is a **Medium** impact: stuck bridge state requiring operator intervention. The bridge cannot switch to the new token contract, which may be required for a security upgrade or bug fix. Repeated griefing makes the migration permanently unachievable without pausing the entire token contract first.

---

### Likelihood Explanation

**High.** Any nBTC holder — including ordinary bridge users — can execute this with a single `ft_transfer` call to a fresh address costing only gas. No special role, leaked key, or privileged access is required. The window of vulnerability is every block between snapshot and callback resolution, and the attacker can repeat the attack on every retry.

---

### Recommendation

Remove the strict `sum == total_supply` equality check. Instead, mint only the balances of the provided accounts and accept that unlisted accounts retain their old-token balance (they can be migrated in a subsequent batch call). Alternatively, require the token contract to be paused before initiating migration so no transfers can occur during the window.

---

### Proof of Concept

1. Operator calls `migrate_to_new_token(new_token, [alice, bob, bridge])` with a complete snapshot.
2. Before the cross-contract `ft_balance_of` queries resolve, attacker (charlie) calls `nbtc.ft_transfer(charlie2, 1, None)` where `charlie2` is a fresh address.
3. `migrate_to_new_token_mint` callback fires: `sum = balance(alice) + balance(bob) + balance(bridge)` but `total_supply` now includes `charlie2`'s 1-satoshi balance.
4. `require!(sum == total_supply, ...)` panics; migration reverts.
5. Attacker repeats on every operator retry, permanently blocking the migration. [4](#0-3)

impl Contract {
    #[private]
    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }
