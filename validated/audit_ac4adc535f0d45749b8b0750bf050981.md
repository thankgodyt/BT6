### Title
Uncapped Caller-Supplied `gas_fee` in Refund Request Enables Griefing of Depositors — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Any caller can submit a refund request for any deposit UTXO and supply an arbitrarily large `gas_fee`. The only guard is `resolved_gas_fee < amount`; there is no cap against the protocol's configured `max_btc_gas_fee`. Because refund requests are first-come-first-served (duplicate submissions are rejected), a malicious actor can front-run the legitimate depositor's refund request with a near-total gas fee, leaving the user with 1 satoshi.

---

### Finding Description

In `request_refund_callback`, the gas fee is resolved from the caller-supplied optional value or the protocol default: [1](#0-0) 

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

The sole validation is `resolved_gas_fee < amount`. No check against `max_btc_gas_fee` is performed. By contrast, withdrawal transactions enforce a strict range: [2](#0-1) 

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
```

This cap is entirely absent from the refund path.

The stored `gas_fee` directly determines the user's refund amount in `refund_execution_inputs`: [3](#0-2) 

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

Refund requests are keyed by UTXO storage key and duplicates are rejected: [4](#0-3) 

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

`internal_request_refund` contains no access-control check restricting who may submit a refund for a given UTXO: [5](#0-4) 

The combination means: whoever calls first with an inflated `gas_fee` locks in that value permanently for the UTXO.

---

### Impact Explanation

A malicious actor who front-runs the depositor's `request_refund` call with `gas_fee = Some(deposit_amount - 1)` causes the stored refund amount to be 1 satoshi. After the timelock elapses, `execute_refund` builds a refund transaction paying the user 1 satoshi while the remainder is consumed as a Bitcoin miner fee. The user suffers near-total loss of their deposited BTC. This matches **Medium** (attacker-triggered harmful bridge behavior causing significant user fund loss without direct theft by the attacker) and potentially **Critical** (significant loss of user funds) depending on deposit size.

---

### Likelihood Explanation

The attack requires:
1. Monitoring for BTC deposits to bridge-controlled addresses (publicly observable on-chain).
2. Calling `request_refund` before the depositor with `gas_fee = Some(large_value)` and the user's own refund address (so the DAO does not flag the address as suspicious).
3. Paying only the NEAR storage deposit (`required_balance_for_request_refund`), which is refundable.

The DAO can reject requests during the timelock, but if the attacker supplies the correct user refund address and only inflates the fee, the request appears legitimate and may not be caught. Likelihood is **Medium**.

---

### Recommendation

Cap the caller-supplied `gas_fee` against the protocol's configured `max_btc_gas_fee` in `request_refund_callback`:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
require!(
    resolved_gas_fee <= config.max_btc_gas_fee,
    "Gas fee exceeds max_btc_gas_fee"
);
```

Additionally, consider restricting `request_refund` so that only the NEAR account named in `deposit_msg` (or a whitelisted relayer) may submit the request, eliminating the front-running surface entirely.

---

### Proof of Concept

1. User deposits 1 BTC (100 000 000 satoshis) to a bridge address. The deposit fails (e.g., below `min_deposit_amount`).
2. Attacker observes the deposit on-chain and extracts `deposit_msg`, `tx_bytes`, and `vout`.
3. Attacker calls `request_refund(deposit_msg, user_btc_address, tx_bytes, vout, proof, gas_fee = Some(99_999_999))`.
4. `request_refund_callback` stores `RefundRequest { amount: 100_000_000, gas_fee: 99_999_999, refund_address: user_btc_address, ... }`.
5. User's subsequent `request_refund` call panics: `"Refund request already exists for this UTXO"`.
6. After `refund_timelock_sec` (2 days), anyone calls `execute_refund`.
7. `refund_execution_inputs` computes `refund_amount = 100_000_000 - 99_999_999 = 1`.
8. The refund transaction pays the user 1 satoshi; 99 999 999 satoshis are paid to Bitcoin miners.
9. The DAO does not reject because the `refund_address` is the user's own address. [6](#0-5)
