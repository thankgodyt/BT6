### Title
Front-Running `request_refund` Allows Attacker to Redirect BTC Refunds to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is publicly callable with no caller-identity check. When a user's `DepositMsg` has `refund_address: None`, any observer can front-run the legitimate call with the same proof data but substitute their own BTC address, seizing ownership of the refund slot and ultimately receiving the user's BTC.

### Finding Description

`request_refund` accepts a `refund_address` parameter from any caller. The only guard on that address is: [1](#0-0) 

This guard only fires when `deposit_msg.refund_address` is already set. When it is `None` — the common case for users who did not pre-authorize a refund address — the provided `refund_address` is stored verbatim with no check that the caller is the intended recipient: [2](#0-1) 

The function is publicly callable (`#[payable]` + `#[pause]`, no `#[trusted_relayer]` on the function): [3](#0-2) 

The callback enforces uniqueness per UTXO, so the first request wins and all subsequent ones revert: [4](#0-3) 

`execute_refund` is also publicly callable (no `#[trusted_relayer]`), so after the timelock the attacker can trigger execution themselves: [5](#0-4) 

The refund output is built directly from the stored `refund_address`: [6](#0-5) [7](#0-6) 

### Impact Explanation

An attacker who wins the race owns the refund slot. After `unsafe_refund_timelock_sec` elapses (default **14 days**), they call `execute_refund` and the MPC pipeline builds and signs a Bitcoin transaction paying the attacker's address. The legitimate user's BTC is permanently redirected. This is a direct, complete theft of user funds — Critical impact. [8](#0-7) [9](#0-8) 

### Likelihood Explanation

All inputs needed to front-run are visible in the pending NEAR transaction: `deposit_msg`, `tx_bytes`, `vout`, and the Merkle `proof`. NEAR's transaction pool is observable via public RPC. The attacker only needs to submit the same call with their own `refund_address` before the victim's transaction is finalized. The 14-day `unsafe_refund_timelock_sec` window is intended to let DAO/Operator reject suspicious requests, but this relies on active monitoring and timely intervention — if the DAO misses the window, the attacker executes the refund unimpeded. Likelihood is **Medium**: requires mempool monitoring and DAO inaction, but the attack is mechanically straightforward and the payoff is the full deposit amount. [10](#0-9) 

### Recommendation

Bind the refund request to the caller's identity. In `request_refund_callback`, record `env::predecessor_account_id()` (the original caller, passed through the async chain) and require that only that account can later call `execute_refund` for this request. Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the destination is committed at deposit time and cannot be overridden by any caller. [11](#0-10) 

### Proof of Concept

1. User A sends BTC to the deposit address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`.
2. `verify_deposit` is never called (e.g. relayer failure). User A calls `request_refund` with `refund_address = "bc1q...alice"`, attaching the required storage deposit.
3. Attacker observes the pending NEAR transaction via public RPC, extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof`.
4. Attacker submits `request_refund` with identical parameters but `refund_address = "bc1q...attacker"` and sufficient attached deposit, landing in the same or an earlier block.
5. Attacker's `request_refund_callback` succeeds; `refund_requests[utxo_key].refund_address = "bc1q...attacker"` is stored.
6. User A's callback reverts: `"Refund request already exists for this UTXO"`.
7. After 14 days (assuming DAO does not reject), attacker calls `execute_refund(utxo_key, None)`.
8. `finalize_refund_with_psbt` builds a PSBT paying `"bc1q...attacker"`, MPC signs it, and the BTC is broadcast to the attacker's address. [12](#0-11)

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
