### Title
Executed Refund Permanently Locks User BTC When Refund Transaction Is Dropped From Bitcoin Mempool — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When `execute_refund` is called, the deposit UTXO is permanently marked in `verified_deposit_utxo` and a `BTCPendingInfo` is created with a deterministic ID. If the refund transaction is subsequently dropped from the Bitcoin mempool (e.g., due to low fees or congestion), the user cannot re-execute the refund (same PSBT → same deterministic ID → panic), cannot request a new refund (UTXO permanently marked), and cannot deposit (UTXO permanently marked). Even with operator intervention, the UTXO remains permanently marked, locking the user's BTC forever with no recovery path.

---

### Finding Description

The `execute_refund` entrypoint calls `finalize_refund_with_psbt`, which performs three irreversible state mutations:

**1. Permanently marks the UTXO as verified:** [1](#0-0) 

**2. Inserts a `BTCPendingInfo` keyed by a deterministic PSBT-derived ID:** [2](#0-1) 

**3. Sets `executed = true` on the `RefundRequest`:** [3](#0-2) 

The `executed` flag was explicitly added to allow re-execution of `execute_refund` after a "consensus branch change": [4](#0-3) 

`load_refund_request_for_execute` correctly passes when `executed == true`: [5](#0-4) 

**However, the re-execution path is broken.** The `btc_pending_id` is derived deterministically from the PSBT signing payload preimages: [6](#0-5) 

A refund PSBT is fully determined by the deposit UTXO (fixed), refund address (fixed), and gas fee (fixed at request time in `RefundRequest.gas_fee`). Re-executing `execute_refund` for the same `RefundRequest` always produces the **identical** `btc_pending_id`. The insert in `finalize_refund_with_psbt` then panics:

```
"pending info already exist"
```

**The stale `BTCPendingInfo` cannot be removed while the `RefundRequest` is active.** `internal_remove_refund_pending_tx_id` enforces: [7](#0-6) 

The `RefundRequest` is only removed in `verify_refund_finalize_callback` (on confirmed finalization) or by a privileged `reject_refund` call. If the refund tx is dropped from the mempool, neither happens automatically.

**Even after operator intervention, the UTXO is permanently blocked.** `verified_deposit_utxo` is a grow-only set — there is no code path that removes entries from it. After `execute_refund` marks the UTXO, `request_refund_callback` permanently blocks any new refund request: [8](#0-7) 

And `verify_deposit` / `safe_verify_deposit` are permanently blocked by the same registry (per wiki section 5.2, `"Already deposit utxo"` panic). Even if an operator calls `reject_refund` and `internal_remove_refund_pending_tx_id` to clean up the NEAR-side state, the UTXO entry in `verified_deposit_utxo` persists, making the BTC permanently unrecoverable through the bridge.

---

### Impact Explanation

**Critical — Permanent locking of user funds.**

The user's BTC is locked in the deposit UTXO on Bitcoin with no recovery path:
- **Cannot re-execute refund**: same PSBT → same `btc_pending_id` → `"pending info already exist"` panic.
- **Cannot request a new refund**: `verified_deposit_utxo` check blocks `request_refund_callback`.
- **Cannot deposit**: same `verified_deposit_utxo` check blocks `verify_deposit`.
- **Operator intervention is insufficient**: `reject_refund` + `internal_remove_refund_pending_tx_id` cleans NEAR state but cannot remove the UTXO from `verified_deposit_utxo`, leaving the user permanently locked out.

The BTC remains unspent on Bitcoin but is permanently inaccessible through the bridge.

---

### Likelihood Explanation

**Moderate.** Bitcoin mempool congestion is a routine occurrence. Transactions with insufficient fees are routinely evicted from mempools after hours or days. No attacker is required — this is triggered by ordinary network conditions. Any user who calls `execute_refund` with a gas fee that proves insufficient for timely confirmation is at risk. The bridge provides no RBF mechanism for refund transactions (unlike withdrawals, which have `internal_withdraw_rbf`), leaving users with no recourse once the refund tx is broadcast.

---

### Recommendation

1. **Fix re-execution in `finalize_refund_with_psbt`**: Before inserting the new `BTCPendingInfo`, check if one with the same `btc_pending_id` already exists and remove it, enabling the intended re-execution semantics.
2. **Add a `verified_deposit_utxo` removal path**: When a refund is rejected or cancelled after `execute_refund` has already marked the UTXO, remove the entry from `verified_deposit_utxo` so the user can re-request a refund or deposit.
3. **Add RBF support for refund transactions**: Analogous to `internal_withdraw_rbf`, allow users to bump the fee on a stuck refund transaction.

---

### Proof of Concept

```
1. User calls request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee=500_sat)
   → RefundRequest stored: { executed: false, gas_fee: 500, utxo_storage_key: "txid:0" }

2. Timelock elapses. User calls execute_refund("txid:0")
   → load_refund_request_for_execute: passes (executed == false, UTXO not yet marked)
   → finalize_refund_with_psbt:
       - btc_pending_id = sha256(psbt_payload) = "aabbcc..."
       - btc_pending_infos.insert("aabbcc...", ...) → OK
       - verified_deposit_utxo.insert("txid:0")
       - refund_request.executed = true

3. User calls sign_btc_transaction("aabbcc...", ...)
   → MPC signs; BTCPendingInfo moves to PendingVerify stage

4. Refund tx broadcast to Bitcoin. Fee too low → evicted from mempool after 2 days.

5. User calls execute_refund("txid:0") again (intending to re-create tx):
   → load_refund_request_for_execute: passes (executed == true, UTXO marked but executed==true)
   → finalize_refund_with_psbt:
       - Same PSBT built (same UTXO, same refund_address, same gas_fee=500)
       - btc_pending_id = sha256(same_payload) = "aabbcc..." (identical)
       - btc_pending_infos.insert("aabbcc...", ...) → PANIC: "pending info already exist"

6. User calls request_refund(...) for same UTXO:
   → request_refund_callback: verified_deposit_utxo.contains("txid:0") == true
   → PANIC: "UTXO already verified via deposit"

7. Operator calls reject_refund("txid:0"):
   → refund_requests.remove("txid:0") → OK
   → verified_deposit_utxo: "txid:0" still present (no removal mechanism)

8. Operator calls internal_remove_refund_pending_tx_id("aabbcc..."):
   → refund_requests.contains_key("txid:0") == false → passes
   → btc_pending_infos.remove("aabbcc...") → OK

9. State: no RefundRequest, no BTCPendingInfo, but verified_deposit_utxo still contains "txid:0"

10. User calls request_refund(...) again:
    → PANIC: "UTXO already verified via deposit"

11. User calls verify_deposit(...):
    → PANIC: "Already deposit utxo"

→ BTC permanently locked. No recovery path exists.
```

            .flatten()
            .copied()
