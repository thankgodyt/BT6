### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Peras Certificate, Enabling Arbitrary Chain-Weight Inflation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `validatePerasCert` in `BlockSupportsPeras` is an acknowledged stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic checks. Because this function is the only gatekeeper between a peer-supplied `PerasCert` and the `PerasCertDB`, any unprivileged peer can inject an arbitrary certificate that boosts any block's chain-selection weight. This causes an honest node to prefer a non-canonical fork over the honest chain.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the mandatory validation step before a certificate is stored and used in chain selection. The only instance in the codebase is a degenerate stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production inbound-certificate path in `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator on every inbound certificate from a peer. If it returns `Right` (which it always does), the certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

Once stored, `implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every certificate in `pcdsCertsByTicket`, including the crafted one:

```haskell
mkPerasWeightSnapshot
  [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
  | cert <- Map.elems (pcdsCertsByTicket pcds)
  ]
``` [4](#0-3) 

Chain selection then uses this snapshot in `weightedSelectView` to compute `wsvWeightBoost` for each candidate fragment: [5](#0-4) 

`preferCandidate` compares `wsvTotalWeight` (block number + weight boost) between the current chain and the candidate: [6](#0-5) 

A crafted certificate that boosts a block on a shorter fork can make `wsvTotalWeight` of that fork exceed the honest chain's total weight, causing `preferCandidate` to return `ShouldSwitch`.

Additionally, `forksAtMostKWeight` uses the same weight snapshot to enforce the k-rollback limit: [7](#0-6) 

Crafted boosts on the current chain's suffix inflate its measured weight, potentially blocking legitimate rollbacks to a better chain.

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` naming any block point as the boosted block. Because `validatePerasCert` always returns `Right`, the certificate is stored and its boost is unconditionally added to the weight snapshot. Chain selection then uses this inflated weight to prefer the attacker's fork over the honest canonical chain. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a batch of `PerasCert` objects. The attack requires no keys, no stake, no admin access, and no prior knowledge beyond the block hash of the target block (which is public). The only constraint is that one certificate per round number is stored (deduplication by `PerasRoundNo`), but an attacker can use any unused round number to inject a fresh boost.

---

### Recommendation

1. Implement real cryptographic and semantic validation inside `validatePerasCert` before the Peras feature is enabled on any network. At minimum, verify the aggregate BLS signature over the round number and boosted block hash against the claimed committee members, verify each voter's eligibility proof, and confirm the total stake of the signers meets the quorum threshold.
2. Until real validation is implemented, gate the entire Peras certificate inbound path behind a feature flag that is disabled by default, so the stub cannot be reached on production nodes.
3. Add an integration test that sends a crafted certificate from an unprivileged peer and asserts that chain selection is not affected.

---

### Proof of Concept

**Setup:** Node A is on the honest chain at block height 100. An adversarial peer B is on a fork that diverges at block 95 and has tip at block 99 (shorter by 1 block, so normally not preferred).

**Attack:**
1. Peer B connects to Node A via the ObjectDiffusion mini-protocol.
2. Peer B sends a `PerasCert` with `pcCertRound = <any unused round>` and `pcCertBoostedBlock = <hash of block 99 on the fork>`.
3. Node A calls `processCerts` → `validatePerasCert mkPerasParams` → always `Right` → certificate stored in `PerasCertDB`.
4. `chainSelSync` triggers chain selection for the boosted block.
5. `implGetWeightSnapshot` returns a snapshot containing the crafted boost (value = `perasWeight params`, e.g. 15).
6. `weightedSelectView` computes for the fork: `wsvBlockNo = 99`, `wsvWeightBoost = 15`, `wsvTotalWeight = 114`.
7. For the honest chain: `wsvBlockNo = 100`, `wsvWeightBoost = 0`, `wsvTotalWeight = 100`.
8. `preferCandidate` returns `ShouldSwitch (Heavier ...)` — Node A rolls back to block 95 and adopts the adversarial fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
