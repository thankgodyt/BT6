### Title
Peras Vote Signature Does Not Commit to `seatIndex`, Enabling Cross-Seat Signature Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `signVote` / `hashVoteSignature` implementation for `PerasBLSCrypto` signs only `(roundNo, boostedBlock)`. The `seatIndex` — the field that identifies *which committee seat* is casting the vote — is carried in the `Vote` struct but is never included in the signed payload. This is the direct analog of the Gateway bug: just as the Gateway signed message omitted the `account` address (allowing the same signature to be submitted for multiple accounts owned by the same signer), the Peras vote signature omits the voter's seat identity, allowing the same signature to be submitted for multiple seats that share the same BLS signing key.

---

### Finding Description

`hashVoteSignature` in `Peras/Crypto/BLS.hs` hashes only the round number and the boosted block:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
``` [1](#0-0) 

`signVote` then signs this hash:

```haskell
signVote sk roundNo boostedBlock =
  PerasBLSCryptoVoteSignature . BLS.signWithRole @SIGN sk
    $ hashVoteSignature roundNo boostedBlock
``` [2](#0-1) 

The `seatIndex` is present in the `Vote` data constructor but is never fed into the hash:

```haskell
-- WFALS
WFALSPersistentVote seatIndex electionId candidate sig
-- EveryoneVotes
EveryoneVotesVote seatIndex electionId candidate sig
``` [3](#0-2) [4](#0-3) 

During vote verification, the verifier looks up the voter's public key by `seatIndex` and checks the signature — but the signature itself does not commit to that `seatIndex`:

```haskell
implVerifyVote committee = \case
  WFALSPersistentVote seatIndex electionId candidate sig
    | Just (_, voterPublicKey, ...) <-
        getCandidateIfSeatWithinBounds seatIndex ... -> do
        let voterVerificationKey = getVoteVerificationKey ... voterPublicKey
        checkVoteSignature voterVerificationKey electionId candidate sig
``` [5](#0-4) 

The same pattern exists in `EveryoneVotes.implVerifyVote`: [6](#0-5) 

The `CryptoSupportsVoteSigning` interface itself defines `signVote` with no `seatIndex` parameter, making this a structural omission across all implementations: [7](#0-6) 

---

### Impact Explanation

**Two concrete attack paths arise:**

**Path 1 — Same BLS key at multiple seats (cross-pool replay):** Two pools controlled by the same operator share the same BLS signing key. Pool A (seat 5) produces a valid vote `σ = sign(sk, hash(R, B))`. The operator submits the identical `σ` as a vote from Pool B (seat 7). `implVerifyVote` looks up Pool B's public key by seat index 7, finds the same underlying BLS key, and the signature verifies. The operator has cast two votes with one signing operation, doubling their effective voting weight.

**Path 2 — WFALS non-persistent multi-seat amplification:** In WFALS, a non-persistent member is granted `numSeats > 1` via local sortition. The `WFALSCert` carries `NE (Map SeatIndex (Maybe (VRFOutput crypto)))` — a non-empty list of per-round seat maps — allowing the same pool to appear across multiple rounds. Because BLS aggregation is linear (`e(N·sig, G2) = e(H(msg), N·pk)`), submitting the same individual signature `N` times produces an aggregate that verifies against the `N`-fold aggregate key. A pool with `numSeats = N` can forge `N` valid-looking votes from a single signing operation. [8](#0-7) 

A fraudulent Peras certificate accepted by honest nodes causes them to boost a block the attacker chose, directly influencing chain selection. This is a **bypass of vote/certificate verification enabling unauthorized certificate acceptance**.

---

### Likelihood Explanation

Path 1 requires an operator to register the same BLS key for two pools — a realistic operational scenario (key reuse). Path 2 requires a pool with sufficient stake to win multiple non-persistent seats, which is a normal outcome for large stake pools. Both paths require only a network-connected pool operator; no privileged access, key compromise, or stake majority is needed. The crafted vote is indistinguishable from a legitimate one at the wire level.

---

### Recommendation

Include `seatIndex` in the signed payload. Concretely, extend `hashVoteSignature` to incorporate the seat index bytes before hashing:

```haskell
hashVoteSignature seatIndex roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (8 + 8 + 8 + 32)
    $ seatIndexBytes <> roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
  where
    seatIndexBytes = BS.word64BE (unSeatIndex seatIndex)
    ...
```

Correspondingly update the `CryptoSupportsVoteSigning` class to pass `seatIndex` through `signVote` and `verifyVoteSignature`, and update all call sites in `implForgeVote` and `implVerifyVote` for both `WFALS` and `EveryoneVotes`. [1](#0-0)

### Proof of Concept

```
Setup:
  - Committee for round R, candidate block B
  - Pool A: seatIndex=5, BLS key (sk, pk_A)
  - Pool B: seatIndex=7, BLS key (sk, pk_B)  -- same sk as Pool A

Attack:
  1. Pool A legitimately forges vote:
       sig = sign(sk, hash(R, B))
       voteA = WFALSPersistentVote 5 R B sig

  2. Attacker constructs replayed vote for Pool B:
       voteB = WFALSPersistentVote 7 R B sig   -- same sig, different seatIndex

  3. implVerifyVote on voteB:
       - getCandidateIfSeatWithinBounds 7 → returns (_, pk_B, ...)
       - voterVerificationKey = getVoteVerificationKey pk_B  -- same underlying BLS key
       - checkVoteSignature voterVerificationKey R B sig
       - verifyVoteSignature: BLS.verifyWithRole pk_B (hashVoteSignature R B) sig
       - hashVoteSignature R B is identical to what was signed → PASSES

  4. Both voteA and voteB are accepted; attacker has doubled their voting weight
     with a single signing operation, potentially pushing a fraudulent certificate
     over the quorum threshold.
``` [9](#0-8) [10](#0-9)
