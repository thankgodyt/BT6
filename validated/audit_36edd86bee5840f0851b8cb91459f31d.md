### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing no cryptographic, committee-membership, or round-validity checks. Any unprivileged peer can therefore inject a crafted `PerasCert` for an arbitrary block via the object-diffusion mini-protocol. The certificate is stored in `PerasCertDB`, its boost weight is added to the targeted block's chain weight, and chain selection may then prefer the attacker's non-canonical chain.

---

### Finding Description

`validatePerasCert` in the degenerate `BlockSupportsPeras` instance is a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is the live implementation used in both certificate pool writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` calls this validator on every inbound certificate before storing it:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate passes, regardless of whether its claimed voters are eligible committee members, whether the aggregate BLS signature is valid, or whether the round number is legitimate.

The same pattern applies to `validatePerasVote`, which only checks stake-distribution membership and never verifies the vote's cryptographic signature:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [5](#0-4) 

This means a peer can claim to be any voter present in the current `PerasVoteStakeDistr` and have its vote accepted and counted toward quorum — directly analogous to the external report's "votes from removed guardians being counted."

### Impact Explanation

An unprivileged peer can:

1. Craft a `PerasCert` for any block of its choice (any round, any boosted block point).
2. Send it via the object-diffusion mini-protocol.
3. The receiving node accepts it unconditionally, stores it in `PerasCertDB`, and applies the `perasWeight` boost to that block's chain weight.
4. Chain selection may then prefer the attacker's targeted (non-canonical) block over the honest chain.

This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is the standard peer-to-peer path for certificate propagation. Any connected peer can send a `PerasCert` message. No special privileges, keys, or stake are required. The vulnerable code path is exercised on every inbound certificate batch.

---

### Recommendation

1. **Implement `validatePerasCert`** to perform full cryptographic verification: verify the aggregate BLS signature over the claimed voters, check that each voter's seat index is within bounds and corresponds to an eligible committee member in the current epoch's stake distribution, and verify the round number is within the valid acceptance window.

2. **Implement `validatePerasVote`** to verify the vote's cryptographic signature in addition to the stake-distribution membership check.

3. Until the full committee-selection plumbing (tracked in issue #120) is in place, consider rejecting all inbound certificates and votes at the network boundary rather than accepting them unconditionally.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer → ObjectDiffusion inbound mini-protocol
     → processCerts (PerasCert.hs:164)
     → validatePerasCert mkPerasParams crafted_cert   -- always Right
     → PerasCertDB.addCert crafted_cert
     → getWeightSnapshot returns boosted weight for attacker's block
     → ChainSelection prefers attacker's block
```

Concretely, an attacker constructs:

```haskell
craftedCert = PerasCert
  { pcCertRound       = someRoundNo   -- any round
  , pcCertBoostedBlock = attackerBlock -- attacker's preferred block point
  }
```

Sends it to a peer. `validatePerasCert mkPerasParams craftedCert` returns:

```haskell
Right ValidatedPerasCert
  { vpcCert      = craftedCert
  , vpcCertBoost = perasWeight mkPerasParams  -- full boost applied
  }
``` [7](#0-6) 

The certificate is stored and the attacker's block receives the full Peras chain-weight boost, with no signature or committee-membership check performed at any point.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
