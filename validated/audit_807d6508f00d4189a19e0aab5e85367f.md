Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Yield-Resume Path in `init_transfer_resume` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function guards the direct execution path with a `NativeFeeRestricted` role check that prevents flagged accounts from registering outbound transfers with a non-zero `native_fee`. This guard is entirely absent in `init_transfer_resume`, the yield-resume callback. A `NativeFeeRestricted` account can deliberately enter the yield path and then call `storage_deposit` on the deterministically-derivable message-storage account, causing `init_transfer_resume` to proceed through `init_transfer_internal` with the non-zero native fee intact — fully bypassing the role restriction.

## Finding Description
In `init_transfer`, the branch condition at lines 566–584 is:

```rust
if self.try_to_transfer_balance_from_message_account(...).is_ok()
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

For a `NativeFeeRestricted` account submitting `native_token_fee > 0` when the message-storage account does not yet exist, both sub-conditions evaluate to `false`: `try_to_transfer_balance_from_message_account` returns `Err(StorageError::MessageAccountNotRegistered)`, and the second arm is blocked by the role check. Execution falls into the `else` branch at line 586, which calls `env::promise_yield_create("init_transfer_resume", ...)` and registers a pending yield keyed on `message_storage_account_id`.

The resume callback at lines 621–646 contains no role check whatsoever:

```rust
pub fn init_transfer_resume(...) -> U128 {
    self.remove_promise(&message_storage_account_id);
    if let Err(err) = self.try_to_transfer_balance_from_message_account(
        &message_storage_account_id,
        NearToken::from_yoctonear(transfer_message.fee.native_fee.0),
        &storage_owner,
        self.required_balance_for_init_transfer_message(transfer_message.clone()),
    ) { ... return transfer_message.amount; }
    self.init_transfer_internal(transfer_message, storage_owner)
}
```

The `storage_deposit` function at line 141 of `near/omni-bridge/src/storage.rs` is public and permissionless; it calls `self.resume_promise(&account_id)` after crediting the balance, which fires `env::promise_yield_resume`. Once the attacker deposits sufficient NEAR to the message-storage account, `try_to_transfer_balance_from_message_account` succeeds and `init_transfer_internal` is called with the original `TransferMessage` — which carries the non-zero `native_fee` set by the restricted account.

The `message_storage_account_id` is deterministically derivable before the call is made, as it is computed from `TransferMessageStorageAccount` fields (token, amount, recipient, fee, sender, msg) that are all known to the attacker at submission time.

## Impact Explanation
This is a concrete authorization bypass matching the allowed impact class: "role bypass… that lets an attacker execute bridge… actions." The `NativeFeeRestricted` role is the sole mechanism preventing flagged accounts from registering transfers with non-zero native fees. Via the yield path, a restricted account can register such a transfer, causing the stored `TransferMessage.fee.native_fee` to be non-zero. A relayer can then call `sign_transfer` and `claim_fee`, receiving the native fee payment. The restriction is rendered entirely ineffective for any account that has been administratively flagged.

## Likelihood Explanation
The attacker must already hold the `NativeFeeRestricted` role (i.e., have been explicitly flagged by the DAO). Once flagged, the bypass requires exactly two standard, permissionless bridge calls: `ft_transfer_call` (to enter the yield path) and `storage_deposit` on the predicted message-storage account (to trigger the resume). No special privileges, leaked keys, or off-chain coordination are needed. The message-storage account ID is fully predictable from public transfer parameters. The attack is repeatable for every transfer the restricted account wishes to submit.

## Recommendation
Add the `NativeFeeRestricted` role check inside `init_transfer_resume`, mirroring the guard in `init_transfer`. Before calling `init_transfer_internal`, verify:

```rust
if transfer_message.fee.native_fee.0 != 0
    && self.acl_has_role(Role::NativeFeeRestricted.into(), storage_owner.clone())
{
    env::log_str("NativeFeeRestricted account attempted native fee via yield path");
    return transfer_message.amount;
}
```

This should be placed after `remove_promise` and before `try_to_transfer_balance_from_message_account`, consistent with how other invalid-state resumes return the full token amount as a refund.

## Proof of Concept
1. DAO calls `acl_grant_role` granting `NativeFeeRestricted` to the attacker account.
2. Attacker calls `ft_transfer_call` on the token contract with `msg` containing `native_token_fee > 0`. Inside `ft_on_transfer` → `init_transfer`, the direct path is blocked; the yield path is entered and a pending promise is registered for the computed `message_storage_account_id`.
3. Attacker pre-computes `message_storage_account_id` from the known `TransferMessageStorageAccount` fields (all known before the call).
4. Attacker calls `storage_deposit` on the bridge contract for `message_storage_account_id` with NEAR ≥ `required_balance_for_init_transfer_message + native_fee`.
5. `storage_deposit` calls `resume_promise`, which fires `env::promise_yield_resume`, triggering `init_transfer_resume`.
6. `init_transfer_resume` calls `try_to_transfer_balance_from_message_account` — succeeds — then calls `init_transfer_internal` with the non-zero `native_fee`. No role check is performed.
7. The transfer is stored with `fee.native_fee > 0`. A relayer calls `sign_transfer` and `claim_fee`, receiving the native fee. The `NativeFeeRestricted` restriction is fully bypassed.
