### Title
`safe_mint()` Mints Tokens to Bridge Before Checking Recipient Registration, Breaking Atomic "Safe" Semantics - (File: `contracts/nbtc/src/lib.rs`)

### Summary

The `safe_mint()` function in the nbtc token contract is documented and designed to provide atomic "safe" minting — either completing fully or reverting entirely. However, it calls `internal_deposit` to mint tokens to the bridge's own account **before** checking whether the recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` without reverting the already-committed mint. This is a direct analog to the reported pattern: a function named "safe" does not implement the safe behavior it implies.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint()` function (lines 101–124) is called by the bridge during the safe deposit flow (when `deposit_msg.safe_deposit = Some(..)`). The bridge documentation explicitly states this path "reverts the whole transaction if minting fails (no lost & found)."

The implementation is:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted HERE

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← silent return, mint NOT reverted
    }
    ...
}
```

The `internal_deposit` call on line 112 is a committed state mutation in the nbtc contract. When the recipient is unregistered, the function returns `PromiseOrValue::Value(U128(0))` on line 115 — a successful cross-contract return, not a panic. In NEAR Protocol, the callee's state changes are committed once the cross-contract call succeeds. The bridge's callback receives `U128(0)` and may panic to revert the bridge's own state, but it **cannot** roll back the nbtc contract's `internal_deposit`. The minted tokens remain permanently in the bridge's account.

This is the exact structural analog to the reported bug: `safeTransferMany()` calling `_transfer()` instead of `_safeTransfer()` — a function named "safe" that does not implement the safe invariant.

### Impact Explanation

**Medium → Critical.** Two concrete impacts:

1. **nBTC supply inflation / broken callback rollback**: Every failed `safe_mint` call (unregistered recipient) permanently mints `amount` nBTC to the bridge's account without a corresponding BTC backing. The bridge's callback cannot roll back the nbtc state. The bridge accumulates unbacked nBTC.

2. **Potential double-minting**: If the bridge's callback panics (as documented — "reverts the whole transaction if minting fails"), the bridge's deposit state is reverted, meaning the UTXO is **not** added to `verified_deposit_utxo`. The user's BTC remains in the deposit address. The user (or relayer) can then call the standard `verify_deposit` flow to claim nBTC again. Result: 2× nBTC minted for 1× BTC deposited — a critical supply/accounting failure.

### Likelihood Explanation

The `safe_mint` path is triggered whenever `deposit_msg.safe_deposit = Some(..)`, which is the Omni Bridge integration path. An unregistered recipient is a realistic scenario: new users, contract accounts, or any account that has not called `storage_deposit` on the nbtc contract. The relayer is expected to call `verify_deposit_v2` for all valid deposits regardless of recipient registration status.

### Recommendation

Move the recipient registration check **before** the `internal_deposit` call, or use `require!` to panic if the account is not registered (which reverts the entire nbtc transaction atomically):

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

This ensures that if the recipient is unregistered, the entire call panics and no state is committed — matching the documented "safe" semantics.

### Proof of Concept

1. User deposits BTC to a safe-deposit address (`deposit_msg.safe_deposit = Some(..)`).
2. User's NEAR account is not registered in the nbtc contract (no `storage_deposit` called).
3. Relayer calls `verify_deposit_v2` with the inclusion proof.
4. Bridge verifies the proof and calls `nbtc.safe_mint(user, amount, msg)`.
5. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount)` — **committed**.
6. `safe_mint` checks `self.token.accounts.get(&account_id).is_none()` → `true`.
7. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no panic, nbtc state committed.
8. Bridge's callback receives `U128(0)`, panics to "revert" the deposit — but only the bridge's own state is reverted; nbtc's `internal_deposit` is permanent.
9. `verified_deposit_utxo` is **not** updated (bridge state reverted).
10. User or relayer calls standard `verify_deposit` for the same UTXO — succeeds, minting another `amount` nBTC to the user.
11. **Result**: 2× nBTC in circulation backed by 1× BTC; bridge holds unbacked nBTC from step 5. [1](#0-0) [2](#0-1) [3](#0-2)
