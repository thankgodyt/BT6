### Title
Unauthorized Redirection of Refund Destination: Any Caller Can Submit `request_refund` With Arbitrary `refund_address` for Another User's Deposit - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`request_refund` in `contracts/satoshi-bridge/src/refund.rs` does not verify that the caller is the original depositor (`deposit_msg.recipient_id`). When `deposit_msg.refund_address` is `None`, the caller freely supplies any BTC `refund_address`. Because the `deposit_msg` is public on-chain (emitted or passed as a parameter to `verify_deposit`), any attacker who observes a pending unverified deposit can front-run the legitimate user and redirect the BTC refund to their own address.

---

### Finding Description

The `request_refund` public entry point in `api/bridge.rs` (lines 507–535) accepts a caller-supplied `deposit_msg` and `refund_address`. The only access check is whether `gas_fee` is `Some` (restricted to DAO/Operator); when `gas_fee` is `None`, the function is callable by any NEAR account with no identity verification.

Inside `internal_request_refund` (refund.rs lines 154–158), the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` — which is the common case for standard deposits — the caller's `refund_address` is accepted verbatim with no check that the caller is `deposit_msg.recipient_id`. The `deposit_msg` is public: it is passed as a parameter to `verify_deposit` / `verify_deposit_v2` by relayers, making it visible in NEAR transaction history.

The `request_refund_callback` (refund.rs lines 497–581) only verifies that the BTC transaction output script matches the deposit address derived from `deposit_msg` — it does not check who is calling. The attacker supplies the same `deposit_msg` as the victim, so this check passes.

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` (api/bridge.rs lines 582–589) is also publicly callable with no role restriction, completing the theft.

---

### Impact Explanation

**Critical.** An attacker can redirect BTC that a legitimate user deposited to the bridge — but whose deposit was never finalized via `verify_deposit` — to the attacker's own BTC address. The victim loses their deposited BTC entirely. This is a direct, permanent theft of user funds with no recovery path once the refund transaction is signed by MPC and broadcast to Bitcoin.

---

### Likelihood Explanation

**Medium-High.** The `deposit_msg` is public on-chain (visible in relayer `verify_deposit` call parameters). Deposits that fail verification (light client issues, relayer downtime, etc.) are the target. The attacker only needs to:
1. Monitor NEAR for failed or pending `verify_deposit` calls to extract the `deposit_msg`.
2. Call `request_refund` with the victim's `deposit_msg` and the attacker's BTC address before the victim does.
3. Wait for `unsafe_refund_timelock_sec` and call `execute_refund`.

The DAO/Operator can reject suspicious requests, but this is a manual process with no guarantee of catching every case, especially under volume or if the attacker times the request near the end of the timelock.

---

### Recommendation

Enforce that the caller of `request_refund` is the original depositor. Add a check in `internal_request_refund`:

```rust
let caller = env::predecessor_account_id();
require!(
    caller == deposit_msg.recipient_id
        || self.acl_has_role(Role::DAO.into(), caller.clone())
        || self.acl_has_role(Role::Operator.into(), caller),
    "Only the original recipient or privileged roles can request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always `Some` (pre-authorized at deposit time) for any permissionless refund request, and restrict the `refund_address: None` path to DAO/Operator only.

---

### Proof of Concept

1. Alice deposits BTC to the bridge with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`.
2. The relayer calls `verify_deposit(deposit_msg, tx_bytes, ...)` — this transaction is now public on NEAR.
3. The deposit fails (e.g., light client rejects the proof). Alice's BTC sits unverified.
4. Bob reads Alice's `deposit_msg` from the failed `verify_deposit` transaction.
5. Bob calls:
   ```
   request_refund(
     deposit_msg = alice's deposit_msg,   // same msg → same deposit address → passes script check
     refund_address = "bob_btc_address",  // attacker's BTC address
     tx_bytes = alice's tx_bytes,
     vout = alice's vout,
     proof = alice's proof,
     gas_fee = None
   )
   ```
6. `request_refund_callback` verifies the BTC tx output script matches the deposit address derived from `deposit_msg` — it does, because Bob used Alice's exact `deposit_msg`. The refund request is stored with `refund_address = "bob_btc_address"`.
7. After `unsafe_refund_timelock_sec`, Bob calls `execute_refund(utxo_storage_key)`.
8. The bridge builds a refund PSBT paying `"bob_btc_address"`, requests MPC signature, and broadcasts it.
9. Alice's BTC is permanently transferred to Bob.

**Root cause** (refund.rs lines 154–158): the `refund_address` is accepted without verifying `env::predecessor_account_id() == deposit_msg.recipient_id`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,

        )
    }
