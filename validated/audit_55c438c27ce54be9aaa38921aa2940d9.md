### Title
Missing `validatePerasCert` Implementation Allows Peer-Injected Certificates to Manipulate Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production stub instance of `BlockSupportsPeras` unconditionally accepts every inbound Peras certificate without any cryptographic or structural validation. Because the ObjectDiffusion mini-protocol is fully wired into the production node-to-node handler stack, an unprivileged peer can inject an arbitrary `PerasCert` that is stored in the `PerasCertDB` and immediately triggers chain selection for the boosted block, potentially causing the node to prefer a weaker fork.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub**

The universal instance `instance StandardHash blk => BlockSupportsPeras blk` (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of content, is accepted and assigned the full `perasWeight` boost (15 weight units per `mkPerasParams`). [2](#0-1) 

**Production wiring — the path is fully active**

`mkHandlers` in `NodeToNode.hs` wires `hPerasCertDiffusionClient` directly to `makePerasCertPoolWriterFromChainDB`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator and `ChainDB.addPerasCertAsync` as the sink: [4](#0-3) 

`processCerts` calls `validateCert` on each inbound cert; since `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `addPerasCertAsync`: [5](#0-4) 

**Chain selection impact**

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` processes it by calling `chainSelectionForBlock` for the boosted block if that block is present in the VolatileDB and is not already on the current chain: [6](#0-5) 

The CHANGELOG explicitly confirms: *"the candidate fragment is now selected based on its Peras weight, instead of its length."* [7](#0-6) 

The `perasCertDiffusionProtocol` is included unconditionally in both `initiator` and `initiatorAndResponder` without any consensus-layer feature-flag check: [8](#0-7) [9](#0-8) 

---

### Impact Explanation

An unprivileged peer that has negotiated `NodeToNodeV_16` (which includes the ObjectDiffusion mini-protocol) can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block hash present in the target node's VolatileDB (learnable via ChainSync).
2. Send it over the `perasCertDiffusionProtocol` channel.
3. `validatePerasCert` returns `Right` unconditionally; the cert is stored and `addPerasCertAsync` is called.
4. `chainSelSync` triggers `chainSelectionForBlock` for the boosted block, which now carries 15 extra weight units.
5. If the boosted block is on a fork that was previously lighter than the current selection, the node switches to that fork.

This matches the **High** impact scope: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- The protocol is negotiated automatically on `NodeToNodeV_16`; no special privileges are required.
- The attacker only needs to know a block hash in the target's VolatileDB, which is observable via ChainSync headers.
- The stub is the only `BlockSupportsPeras` instance in the codebase; there is no more-specific instance for `CardanoBlock` that would override it.
- The `ferasWeight` is non-zero (15) in `mkPerasParams`, so the boost is material.

The only mitigating uncertainty is whether the network layer's `nodeToNodeProtocols` gates the `perasCertDiffusionProtocol` behind a feature flag that is off by default. The consensus layer passes the handler unconditionally; whether the network layer suppresses it is not visible in this repository.

---

### Recommendation

1. **Immediate**: Implement real cryptographic and structural validation in `validatePerasCert` before the ObjectDiffusion mini-protocol is enabled in any deployment. At minimum, verify the certificate's aggregate signature against the claimed committee votes and check that the quorum threshold is met.
2. **Short-term**: Add a consensus-layer feature flag check in `mkHandlers` / `hPerasCertDiffusionClient` so that the handler is a no-op (or the protocol is not offered) when Peras is not yet activated for the current era.
3. **Tracking**: Resolve [cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120) before any release that includes `NodeToNodeV_16`.

---

### Proof of Concept

An io-sim scenario demonstrating the issue:

1. Start a node with a VolatileDB containing blocks `A → B → C` (current selection) and `A → B → D` (weaker fork, `D` has lower chain weight than `C`).
2. Connect a second peer that speaks `NodeToNodeV_16`.
3. The peer sends a `PerasCert { pcCertRound = 1, pcCertBoostedBlock = blockPoint D }` over the `perasCertDiffusionProtocol` channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })`.
5. `addPerasCertAsync` enqueues the cert; `chainSelSync` calls `chainSelectionForBlock` for `D`.
6. Chain selection now sees `A → B → D` with weight `length(D) + 15` vs `A → B → C` with weight `length(C)`. If `15 > length(C) - length(D)`, the node switches to the `D` fork.
7. Assert: `getCurrentChain` returns the `D` fork; the `PerasCertDB` contains the forged cert.

  (StandardHash blk, IOLike m) =>
  SystemTime m ->

makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.
          -- The async action is still launched and executed behind the scenes
          -- even though we drop the promise.
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    , opwHasObject = do
        certIds <- ChainDB.getPerasCertIds chainDB
        pure $ \roundNo -> Set.member roundNo certIds
    }

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
