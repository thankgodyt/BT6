Audit Report

## Title
Push-Based Token Delivery in `finTransfer` Permanently Freezes Funds When Recipient Is Blacklisted - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` unconditionally pushes tokens to `payload.recipient` via `safeTransfer`. If the recipient is blacklisted by the token contract (e.g., USDC) between the time `init_transfer` is called on NEAR and the time a relayer calls `finTransfer` on EVM, every finalization attempt reverts. Because the NEAR side has already burned or locked the user's tokens and no cancel, redirect, or pull-based fallback exists anywhere in the protocol, the bridged funds are permanently frozen.

## Finding Description

**EVM side — push-based delivery with no fallback:**

In `finTransfer`, the nonce is marked consumed at line 287 before the token transfer:

```solidity
completedTransfers[payload.destinationNonce] = true;
```

For a native ERC20 token such as USDC (not a bridge-deployed token, not a custom minter, not ERC1155), execution reaches the final `else` branch:

```solidity
} else {
    IERC20(payload.tokenAddress).safeTransfer(
        payload.recipient,
        payload.amount
    );
}
```

If `payload.recipient` is USDC-blacklisted, `safeTransfer` reverts. Because Solidity reverts unwind all state changes, the nonce is not permanently consumed. However, every subsequent call to `finTransfer` for the same transfer will reach the same `safeTransfer` and revert identically. There is no alternative branch, no pull-based claim mapping, and no redirect parameter.

**NEAR side — tokens burned/locked with no cancel path:**

`init_transfer_internal` (lines 1850–1857) burns deployed bridge tokens or locks native tokens before emitting the `InitTransferEvent`:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
```

The pending transfer record is stored in `pending_transfers`. Searching the entire NEAR contract, `remove_transfer_message` is called only in:
- `sign_transfer_callback` — only when `fee.is_zero()` and MPC signing succeeds (removes the record but does not restore burned tokens)
- `claim_fee_callback` — requires a proof of successful EVM `finTransfer`, which will never be produced if finalization is permanently blocked

There is no `cancel_transfer`, `rescue`, or admin redirect function anywhere in the NEAR contract. Even if the pending record were removed, `burn_tokens_if_needed` uses `.detach()` on the burn promise, meaning the burn is fire-and-forget and cannot be reversed by removing the record.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, which is explicitly within the Critical impact scope. A user's tokens are burned or locked on NEAR, the EVM finalization is permanently blocked by the blacklisted recipient, and no protocol-level recovery path exists. The funds are irrecoverable without an out-of-band contract upgrade and manual admin intervention, neither of which is guaranteed or encoded in the protocol.

## Likelihood Explanation

USDC is one of the most commonly bridged assets. Circle regularly exercises its blacklist capability in response to sanctions and law enforcement requests. The window between `init_transfer` on NEAR and `finTransfer` on EVM can range from minutes to hours, providing a realistic opportunity for blacklisting to occur in between. No attacker action is required — the blacklisting is performed by the token issuer. Any user bridging a blacklist-capable token to an address that is subsequently blacklisted is affected.

## Recommendation

Replace the push-based delivery in `finTransfer` with a pull-based pattern:

1. Instead of calling `safeTransfer` directly to `payload.recipient` inside `finTransfer`, record the claimable balance in a mapping: `claimable[recipient][token] += amount`.
2. Mark the nonce consumed and emit the event as today.
3. Expose a separate `claimTokens(address token)` function that the recipient (or any address they authorize) calls to withdraw their balance.

This isolates a single recipient's blacklist status from the finalization of the transfer, ensuring the nonce is consumed and the protocol flow completes regardless of the recipient's token-level status.

## Proof of Concept

1. Alice holds 10,000 USDC (bridged) on NEAR and calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer_internal`. The NEAR bridge burns her bridged USDC tokens via `burn_tokens_if_needed` and stores the pending transfer in `pending_transfers`.
2. A relayer calls `sign_transfer` on NEAR; the MPC produces a signature over the `TransferMessagePayload`.
3. Before any relayer calls `finTransfer` on EVM, Circle blacklists Alice's EVM address.
4. A relayer calls `OmniBridge.finTransfer(signatureData, payload)` where `payload.recipient = Alice_EVM`. Signature verification passes. Execution reaches `IERC20(USDC).safeTransfer(Alice_EVM, amount)` at line 351. USDC's `transfer` reverts because Alice is blacklisted. The entire transaction reverts; the nonce is not consumed.
5. Every future relayer attempt to finalize this transfer reaches the same `safeTransfer` and reverts identically.
6. `claim_fee_callback` on NEAR requires a proof of a successful EVM `FinTransfer` event, which is never emitted. The pending transfer record in `pending_transfers` is never removed.
7. Alice's 10,000 USDC on NEAR is permanently burned with no recovery path in the protocol.

**Minimal local test plan:** Deploy a mock ERC20 with a blacklist. Call `initTransfer` on the EVM bridge (or simulate the NEAR→EVM flow). Blacklist the recipient on the mock token. Attempt `finTransfer` — confirm it reverts. Confirm no alternative call sequence in the contract allows the funds to be recovered.
