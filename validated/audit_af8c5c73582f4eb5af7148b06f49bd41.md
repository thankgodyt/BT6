### Title
Any Caller Can Trigger MPC Signing for Another User's Pending BTC Transaction - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
The `sign_btc_transaction` public function contains no ownership check: it never verifies that `env::predecessor_account_id()` matches the `account_id` stored inside the `BTCPendingInfo`. Any unprivileged NEAR account can therefore call it with any valid `btc_pending_sign_id` and force the MPC network to sign another user's pending withdrawal or refund transaction, advancing it to `PendingVerify` state and emitting the signed transaction bytes before the legitimate owner intends.

### Finding Description
`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` (lines 21–43) accepts a `btc_pending_sign_id` and a caller-supplied `key_version`, looks up the `BTCPendingInfo`, asserts it is in `PendingSign` state, and immediately delegates to `internal_sign_btc_transaction`. At no point is `env::predecessor_account_id()` compared to `btc_pending_info.account_id`.

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ← no check: env::predecessor_account_id() == btc_pending_info.account_id
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
```

`internal_sign_btc_transaction` (`contracts/satoshi-bridge/src/chain_signature.rs`, lines 76–113) then calls the MPC `sign` endpoint with the UTXO path and the attacker-supplied `key_version`, forwarding `env::attached_deposit()` (paid by the attacker). The callback (`sign_btc_transaction_callback`, lines 135–213) stores the resulting signature, and when all inputs are signed, moves the pending info to `PendingVerify` stage and emits `SignedBtcTransaction` with the full signed transaction bytes.

By contrast, every other function that mutates a user's pending transaction enforces ownership. `internal_withdraw_rbf` (`contracts/satoshi-bridge/src/rbf/withdraw.rs`, line 43–45) requires `&original_tx_btc_pending_info.account_id == account_id`. `internal_active_utxo_management_rbf` (`contracts/satoshi-bridge/src/rbf/active_utxo_management.rs`, lines 36–38) does the same. `sign_btc_transaction` is the sole public mutation path that omits this guard.

**Attacker-controlled entry path:**
1. Victim calls `ft_transfer_call` → bridge creates `BTCPendingInfo` in `PendingSign` state.
2. Attacker observes the emitted `GenerateBtcPendingInfo` event to learn `btc_pending_id`.
3. Attacker calls `sign_btc_transaction(btc_pending_id, 0, key_version)` attaching enough NEAR for the MPC fee.
4. MPC signs the PSBT using the bridge's key for the victim's UTXO path.
5. Callback stores the signature; if all inputs are signed, the pending info advances to `PendingVerify` and the signed transaction bytes are broadcast in an event.

### Impact Explanation
The signed Bitcoin transaction pays BTC to the victim's intended address (the PSBT output is fixed at creation time), so funds are not redirected. However:

- **Forced premature broadcast**: The victim loses control over when their transaction is submitted to the Bitcoin network. If Bitcoin mempool fees spike after the attacker forces signing, the victim's transaction may be stuck with a low fee. The victim must then call `withdraw_rbf` (which requires `PendingVerify` state, so it is still available) to bump the fee, incurring additional cost and delay.
- **Invalid-signature griefing via wrong `key_version`**: If the attacker supplies a `key_version` that the MPC accepts but that does not correspond to the key committed in the PSBT, the stored signature is cryptographically invalid for the Bitcoin transaction. The slot is marked filled (`signatures[sign_index] = Some(...)`), so the victim cannot re-sign that input. The victim must issue a `withdraw_rbf` to create a fresh PSBT and sign it correctly.
- **Invariant violation**: The protocol invariant that only the owner of a pending transaction may advance it through the signing pipeline is broken for every pending transaction type (withdrawal, refund, active UTXO management).

This matches the allowed Low impact: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
`btc_pending_sign_id` values are emitted in `GenerateBtcPendingInfo` events, which are publicly observable on-chain. The function requires no privileged role and no special precondition beyond attaching enough NEAR for the MPC fee. Any NEAR account can execute this attack against any pending transaction at any time.

### Recommendation
Add an ownership check at the top of `sign_btc_transaction`:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    require!(
        env::predecessor_account_id() == btc_pending_info.account_id,
        "Only the transaction owner may sign"
    );
    ...
}
```

If the protocol intentionally allows third-party signing (e.g., a relayer service), restrict it to whitelisted relayer accounts via `#[trusted_relayer]` or `#[access_control_any(roles(Role::Operator, ...))]`, consistent with how other sensitive functions are guarded.

### Proof of Concept

1. Alice initiates a withdrawal: `nbtc.ft_transfer_call(bridge, 100_000, withdraw_msg)`.
2. Bridge emits `GenerateBtcPendingInfo { account_id: "alice", btc_pending_id: "abc123..." }`.
3. Attacker (Bob) reads the event and calls:
   ```
   bridge.sign_btc_transaction(
       btc_pending_sign_id = "abc123...",
       sign_index = 0,
       key_version = 0,
   )
   ```
   attaching 1 yoctoNEAR for the MPC fee.
4. MPC signs Alice's PSBT. `sign_btc_transaction_callback` stores the signature and emits `SignedBtcTransaction` with the full signed transaction bytes.
5. Alice's withdrawal is now in `PendingVerify` state and the signed transaction is publicly visible — broadcast before Alice chose to sign it, and potentially with a fee she would have bumped via RBF. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }

    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }
