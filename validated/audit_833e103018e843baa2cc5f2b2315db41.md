### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates Without Any Signature or Content Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. Because this function is the sole gate used by the ObjectDiffusion inbound pipeline before a certificate is stored and used to influence chain selection, any unprivileged peer can inject an arbitrary Peras certificate — for any round number and any block point — and have it accepted as fully valid, directly manipulating the Peras boost applied during chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory validation step for inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only production instance — the degenerate catch-all for all `blk` — is a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into both ObjectDiffusion pool writers that handle inbound peer certificates. `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` both pass `validatePerasCert mkPerasParams` as the validator argument to `processCerts`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (PerasCertDB.getCertIds perasCertDB)
      (validatePerasCert mkPerasParams)   -- stub: always Right
      (void . join . atomically . PerasCertDB.addCert perasCertDB)
      certs
``` [2](#0-1) 

`processCerts` is the inbound processing function for peer-supplied certificates. It filters out already-known round numbers, then calls `validateCert` on each remaining certificate. If all pass, they are timestamped and stored:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertInboundException ...)
``` [3](#0-2) 

Because `validateCert` is the stub, the `(errs, _)` branch is unreachable. Every certificate from every peer passes.

The same pattern applies to `validatePerasVote`, which also carries an explicit TODO and performs no signature verification — it only checks whether the voter ID appears in the stake distribution, meaning any peer who knows a valid pool ID (public information) can forge votes attributed to that pool:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

Forged votes are aggregated by `updatePerasRoundVoteStates` inside `implAddVote`. Once the accumulated `ptvtTotalStake` crosses the quorum threshold, `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` is produced and stored — all without any real cryptographic proof:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [5](#0-4) 

`votesReachQuorum` checks only that all votes share the same target and that their combined `vpvVoteStake` exceeds the threshold — it does not re-verify signatures:

```haskell
votesReachQuorum cfg votes =
  case votes of
    [] -> Nothing
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) -> Nothing
      | not votesHaveEnoughStake       -> Nothing
      | otherwise -> Just ValidatedPerasVotesWithQuorum { ... }
``` [6](#0-5)

### Impact Explanation

**Certificate injection path**: An unprivileged peer sends a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. `processCerts` calls the stub validator, which returns `Right`. The certificate is stored with a `vpcCertBoost = perasWeight params` weight. Chain selection subsequently applies this boost to the attacker-chosen block, potentially causing honest nodes to prefer a non-canonical or attacker-controlled chain tip over the honest chain.

**Vote-forging path**: An attacker who knows any pool ID present in the current stake distribution (all pool IDs are public) can send `PerasVote` messages attributed to high-stake pools. `validatePerasVote` accepts them because the pool ID resolves to a stake entry. By sending forged votes from pools whose combined stake exceeds the quorum threshold, the attacker causes `votesReachQuorum` to succeed, `forgePerasCert` to produce a `ValidatedPerasCert`, and that certificate to be stored and applied as a chain-selection boost — all without possessing any private key material.

Both paths constitute a **Peras certificate/vote verification bypass** that enables unauthorized certificate acceptance and chain-selection manipulation, matching the Critical impact category.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras votes and certificates is a standard peer-to-peer channel; any connected peer can submit objects. No stake, no private keys, and no special network position are required. The pool IDs needed for the vote-forging path are published on-chain. The attack requires only knowledge of the protocol message format and the current stake distribution, both of which are publicly available.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation — verify the aggregate BLS signature over `(electionId, candidate)` using the aggregated verification keys of the claimed voter set, confirm the voter set's combined stake exceeds the quorum threshold, and confirm the certified block point exists on a known chain. The `implVerifyCert` implementations in `EveryoneVotes.hs` and `WFALS.hs` already contain the correct logic and should be wired in via the proper `BlockSupportsPeras` instance for Cardano blocks. [7](#0-6) 

2. **`validatePerasVote`**: Implement full vote validation — verify the vote signature using the voter's public key retrieved from the stake distribution, verify any VRF eligibility proof for non-persistent voters, and confirm the round number and block point are within acceptable bounds. The `implVerifyVote` implementations in `EveryoneVotes.hs` and `WFALS.hs` provide the correct reference.

3. Remove the degenerate catch-all `BlockSupportsPeras` instance or gate it behind a compile-time flag that is never enabled in production builds, to prevent the stubs from silently becoming the active implementation.

### Proof of Concept

On a private testnet running the current codebase:

1. Connect a malicious peer via the ObjectDiffusion mini-protocol.
2. Send a `PerasCert` message with `pcCertRound = <current round>` and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. Observe via tracing that `processCerts` calls `validatePerasCert`, receives `Right`, and stores the certificate.
4. Observe that subsequent chain selection applies `perasWeight` as a boost to the attacker-chosen block, causing the node to prefer it over the honest tip.

For the vote-forging variant:

1. Query the current stake distribution to obtain pool IDs and their stakes.
2. Send `PerasVote` messages attributed to pools whose combined stake exceeds the quorum threshold, all targeting the same `(pvVoteRound, pvVoteBlock)`.
3. Observe that `validatePerasVote` accepts each vote (pool ID resolves in the stake distribution), `votesReachQuorum` triggers, `forgePerasCert` produces a `ValidatedPerasCert`, and the certificate is stored and applied as a chain-selection boost — without any private key material.

  forall crypto.
  CryptoSupportsAggregateVoteSigning crypto =>
  VotingCommittee crypto EveryoneVotes ->

implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)
        aggVerificationKey
        electionId
        candidate
        aggSig

    pure members
