### Title
Peras Weight Snapshot Hardcoded as Empty in Forecast-Horizon Chain Comparison Causes Incorrect Peer Disconnection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs`, the Peras weight snapshot is hardcoded to `emptyPerasWeightSnapshot` when comparing a peer's candidate chain against the local selection. This is the direct analog of the reported bug: just as the liquidation premium accumulated in `sharingProfitTokenAmts` is silently skipped when `netPnLE36 <= 0`, the Peras certificate weight boost (the "premium" that makes a chain heavier) is silently dropped from the chain-preference comparison when a header is beyond the forecast horizon. The result is that the node may incorrectly disconnect from a peer serving the canonical, Peras-boosted chain, and remain on a less-preferred selection.

---

### Finding Description

When the ChainSync client receives a header whose slot is beyond the current forecast horizon, `readLedgerStateHelper` cannot project a ledger view for it. It falls into the `Nothing` branch and calls `checkPreferTheirsOverOurs` before retrying:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
``` [1](#0-0) 

`checkPreferTheirsOverOurs` then decides whether to keep the connection or throw `CandidateTooSparse` (disconnect):

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← Peras boosts are IGNORED
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [2](#0-1) 

`preferAnchoredCandidate` has two code paths: when `isEmptyPerasWeightSnapshot weights` is true it compares chains purely by block count/`SelectView`; when false it uses `weightedSelectView` which incorporates Peras certificate boosts:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- compares only by block number / SelectView tiebreaker
      ...
  | otherwise =
      -- compares by wsvTotalWeight = BlockNo + PerasWeight boost
      ...
``` [3](#0-2) 

Because `emptyPerasWeightSnapshot` is always passed, the `otherwise` branch (which accounts for Peras boosts) is **never reached** inside `checkPreferTheirsOverOurs`. The Peras weight boost — the "premium" — is silently dropped from the comparison, exactly as the liquidation premium was dropped when `netPnLE36 <= 0`.

**Concrete scenario:**

1. The local node holds chain `C_local` of block-length 10, with no Peras certificate boosts.
2. An honest peer serves chain `C_peer` of block-length 9, but `C_peer` carries a Peras certificate boost of weight `W` such that `9 + W > 10` (i.e., `C_peer` is the heavier, canonical chain).
3. The tip of `C_peer` is beyond the local forecast horizon, so `prj lst` returns `Nothing`.
4. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`.
5. Without the boost, `C_peer` (length 9) loses to `C_local` (length 10): `preferAnchoredCandidate` returns `ShouldNotSwitch`.
6. The node throws `CandidateTooSparse` and **disconnects from the honest peer**.
7. The node remains on `C_local`, the less-preferred chain.

The TODO comment in the source code explicitly acknowledges the problem: `-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`. [4](#0-3) 

---

### Impact Explanation

This is a **High** chain-selection bug. When Peras is active, the canonical chain is determined by `wsvTotalWeight = BlockNo + PerasWeight`. A node that evaluates `checkPreferTheirsOverOurs` with zero Peras weights will disconnect from any peer whose chain is heavier only because of certificate boosts, causing the node to permanently prefer a non-canonical, lighter chain. An adversary who controls the node's current selection (e.g., via an eclipse or by being the first peer to serve a fork) can exploit this to keep the node on a minority chain: the adversary's chain need only be longer in block count than the honest chain, and the node will reject every honest peer that tries to serve the Peras-boosted canonical chain as "too sparse."

---

### Likelihood Explanation

Likelihood is **Medium**. The bug is only reachable when Peras is active (currently gated behind a feature flag, but the code is production-path). Once Peras is live, the scenario requires a chain where the canonical fork is shorter in block count but heavier due to certificate boosts — a normal outcome of Peras operation after a cooldown period or a short fork. No special privileges are needed; any peer can trigger the path by sending a header beyond the forecast horizon, which is a routine occurrence during syncing or after a slot gap.

---

### Recommendation

The TODO comment already identifies the correct fix: **remove the `checkPreferTheirsOverOurs` call entirely** (per issue `cardano-peras#64`). The check was designed for a pre-Peras world where chain length alone determined preference; with Peras weights it cannot be evaluated correctly without the live `PerasWeightSnapshot`. Removing it means the node will simply `retry` (block) until the forecast horizon advances, which is the safe behavior. Alternatively, if the check must be retained, the actual `PerasWeightSnapshot` must be read from the ChainDB (it is available as `getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))`) and passed to `preferAnchoredCandidate` instead of `emptyPerasWeightSnapshot`. [5](#0-4)

### Proof of Concept

**Entry path (unprivileged peer, no special keys required):**

1. Peras is enabled; the honest network has produced a certificate boosting block `B` on chain `C_honest` (block-length 9, total weight 9 + W > 10).
2. Adversary connects to the victim node first and serves chain `C_adv` of block-length 10, no Peras boosts (total weight 10).
3. Victim selects `C_adv` (it appears heavier without Peras weights).
4. Honest peer connects and begins serving `C_honest`. The tip of `C_honest` is beyond the victim's forecast horizon.
5. Inside `readLedgerStateHelper`, `prj lst` returns `Nothing` → `checkPreferTheirsOverOurs` is called.
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot C_adv C_honest` compares block-lengths: 10 vs 9 → `ShouldNotSwitch`.
7. `throwSTM (CandidateTooSparse ...)` — victim disconnects from the honest peer.
8. Victim remains on `C_adv` indefinitely; the Peras-boosted canonical chain `C_honest` is never adopted. [6](#0-5) [7](#0-6) [8](#0-7)
