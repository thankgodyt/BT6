### Title
Unpermissioned `sign_btc_transaction` Allows Any Account to Trigger MPC Signing of Any Pending BTC Transaction — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary
`sign_btc_transaction` carries no caller-ownership check. Any unprivileged NEAR account can invoke it against any `btc_pending_sign_id`, triggering the MPC/Chain-Signatures pipeline for a transaction it does not own.

### Finding Description

Every other state-mutating bridge entry point that operates on a specific user's pending transaction either (a) restricts the caller via `#[trusted_relayer]`, `#[access_control_any]`, or an explicit `acl_has_role` guard, or (b) derives the acting account from `env::predecessor_account_id()` and validates ownership. `sign_btc_transaction` does neither. [1](#0-0) 

The function is decorated only with `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. There is no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`, and no role requirement. The outer `impl` block in `bridge.rs` carries `#[trusted_relayer]`, but the `chain_signatures.rs` impl block does not. [2](#0-1) 

Compare with `withdraw_rbf`, which explicitly binds the caller: [3](#0-2) 

Or `cancel_withdraw`, which requires `Role::DAO` or `Role::Operator`: [4](#0-3) 

### Impact Explanation

An attacker who observes a `btc_pending_sign_id` (emitted via `Event::GenerateBtcPendingInfo` and therefore publicly visible on-chain) can call `sign_btc_transaction` against it at any time. Concretely:

- **Forced premature signing**: A user who submitted a withdrawal and then wants to replace it via `withdraw_rbf` (e.g., to adjust the fee or cancel) may find the transaction already signed and queued for broadcast before they can act. Once all inputs are signed and `tx_bytes_with_sign` is populated, the signed raw transaction is ready to be relayed to Bitcoin.
- **Griefing via wrong `sign_index`**: Calling with an out-of-range or already-signed `sign_index` causes a panic or overwrites a valid partial signature, potentially corrupting the signing state of a multi-input PSBT and requiring operator intervention to recover.

The PSBT outputs are fixed at construction time, so the attacker cannot redirect funds. However, the attacker can force execution of a withdrawal the user intended to cancel, or corrupt the signing state of a pending transaction.

### Likelihood Explanation

`Event::GenerateBtcPendingInfo` is emitted for every withdrawal and refund, making `btc_pending_sign_id` values publicly observable. The function requires only an attached NEAR deposit (paid by the attacker). No privileged access is needed. Likelihood is **Medium**. [5](#0-4) 

### Recommendation

Add an ownership check at the top of `sign_btc_transaction`:

```rust
let caller = env::predecessor_account_id();
let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
require!(
    caller == btc_pending_info.account_id
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::Operator.into()], caller),
    "Caller is not the owner of this pending transaction"
);
```

This mirrors the pattern used in `withdraw_rbf` and `cancel_withdraw`.

### Proof of Concept

1. Alice calls `ft_on_transfer` (Withdraw variant), burning nBTC. The bridge emits `GenerateBtcPendingInfo { account_id: alice, btc_pending_id: "abc123" }`.
2. Alice observes BTC network congestion and decides to cancel via `withdraw_rbf`.
3. Bob (attacker) reads `btc_pending_id = "abc123"` from chain events and calls:
   ```
   sign_btc_transaction(btc_pending_sign_id: "abc123", sign_index: 0, key_version: 0)
   ```
   attaching the required NEAR deposit. No role or ownership check blocks this call.
4. The MPC signs input 0. Bob repeats for each remaining input index.
5. `tx_bytes_with_sign` is now populated; the signed transaction is ready to broadcast.
6. Alice's `withdraw_rbf` call either races against the broadcast or finds the pending info already in a signed state, preventing a clean RBF replacement. [6](#0-5)

```rust
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
```
