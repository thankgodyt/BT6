### Title
Unconditional `validatePerasCert` Stub Accepts All Peer-Supplied Peras Certificates Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or eligibility checks. This function sits on the live inbound path of the Peras certificate diffusion mini-protocol (`hPerasCertDiffusionClient` in `NodeToNode.hs`). Any unprivileged peer can therefore send a crafted `PerasCert` for an arbitrary block and have it accepted, assigning that block the full Peras weight boost and potentially causing chain selection to prefer a non-canonical fork.

---

### Finding Description

**Root cause — unconditional stub in production code**

`validatePerasCert` in the universal `BlockSupportsPeras` instance is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every certificate, regardless of origin or content, is accepted and assigned the full `perasWeight` boost. [1](#0-0) 

**Reachable inbound path — production node-to-node handler**

The production node-to-node handler wires the Peras cert diffusion inbound path directly to `makePerasCertPoolWriterFromChainDB`, which processes peer-supplied certificates through `validatePerasCert`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [2](#0-1) 

Contrast this with the vote diffusion path, which is intentionally broken by passing `(pure (PerasVoteStakeDistr mempty))` — the code comment there explicitly notes "the empty stake distribution will cause all votes to be considered invalid." No equivalent protective measure exists for certificates; the cert path accepts everything. [3](#0-2) 

**Downstream effect — chain selection weight manipulation**

Accepted certificates are added to the ChainDB via `addPerasCertAsync`, which triggers chain selection with the boosted weight. The `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is the full Peras weight assigned to the boosted block during chain selection. [4](#0-3) 

The `PerasWeightSnapshot` is read during chain selection to assign extra weight to blocks covered by certificates: [5](#0-4) 

**Structural parallel to the external report**

The external report describes `registerTokenOnL2` being callable by anyone because no `onlyOwner` guard exists — the function mutates critical state (the L2 token address) without authorization. Here, `validatePerasCert` is the missing guard: it is the authorization boundary that should reject certificates from unauthorized parties, but instead it unconditionally admits every certificate, mutating critical consensus state (block weight) without any authorization check.

---

### Impact Explanation

**Impact: High — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain selection manipulation.**

Peras certificates boost the weight of specific blocks during chain selection. An attacker who injects a forged `PerasCert` pointing to a block on a minority fork causes the honest node to assign that block the full `perasWeight` boost. If the attacker's fork is otherwise competitive (e.g., same length), the weight boost can tip chain selection in favor of the non-canonical chain, causing the node to diverge from the honest network. This directly matches the allowed impact: *"Bypass of… Peras voting or certificate checks… that enables unauthorized… certificate acceptance"* and *"High. Chain selection… bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

**Likelihood: High.**

- No stake, keys, or special privileges are required. Any peer connected via the node-to-node protocol can send Peras cert diffusion messages.
- The attacker only needs to craft a valid CBOR-encoded `PerasCert` (two fields: `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk`) and send it over the established mini-protocol session.
- The `PerasCert` serialization is fully public. [6](#0-5) 
- The Peras cert diffusion mini-protocol is active in the production handler set.

---

### Recommendation

1. **Immediate mitigation**: Replace the stub `validatePerasCert` with a version that returns `Left PerasValidationErr` for all inputs until the real implementation is ready. This mirrors the intentional behavior already applied to the vote path (empty stake distribution → all votes rejected). A cert path that rejects everything is safer than one that accepts everything.

2. **Correct fix**: Implement `validatePerasCert` to verify the aggregate BLS/committee signature over the certificate's voter set, confirm that the voters are eligible committee members with sufficient combined stake exceeding the quorum threshold, and validate the election ID and round number against the current ledger state.

3. **Structural guard**: Add a compile-time or runtime assertion that `validatePerasCert` is never the identity function in any production build, analogous to how the vote path is guarded by the stake distribution lookup.

---

### Proof of Concept

1. Connect to a target node as a peer via the node-to-node protocol and negotiate the Peras cert diffusion mini-protocol (`hPerasCertDiffusionClient`).
2. Craft a `PerasCert` with:
   - `pcCertRound` = current Peras round number (observable from the chain tip)
   - `pcCertBoostedBlock` = the `Point` of a block on the attacker's preferred (minority) fork
3. CBOR-encode the cert per the `Serialise (PerasCert blk)` instance and send it as an `ObjectDiffusion` message.
4. The node's inbound handler calls `makePerasCertPoolWriterFromChainDB`, which calls `validatePerasCert params cert`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally. [7](#0-6) 
6. The cert is added to the ChainDB via `addPerasCertAsync`, triggering chain selection with the full Peras weight boost applied to the attacker's block. [8](#0-7) 
7. If the attacker's fork is otherwise competitive, the node switches to it, diverging from the honest network.
