### Title
Front-Running `request_refund` Causes User Callback Revert and Storage Deposit Loss, with Path to BTC Theft — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Any unprivileged NEAR account can front-run a legitimate user's `request_refund` call by submitting their own `request_refund` for the same UTXO. Because `request_refund` is publicly callable and the resulting `RefundRequest` is not bound to the caller's identity, an attacker whose callback executes first inserts a refund entry that causes the victim's callback to revert with `"Refund request already exists for this UTXO"`. The victim loses their non-refundable storage deposit and their BTC remains stuck. When `deposit_msg.refund_address` is `None`, the attacker can embed their own Bitcoin address in the winning request, creating a path to BTC theft if the DAO/Operator does not reject the request within `unsafe_refund_timelock_sec`.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no caller restriction — it is `#[payable]` and `#[pause(except(roles(Role::DAO)))]` only: [1](#0-0) 

It calls `internal_request_refund`, which fires an async cross-contract call to the Light Client and chains `request_refund_callback`. The callback enforces uniqueness: [2](#0-1) 

Because NEAR cross-contract calls span multiple blocks, there is a window between the user's original call and the execution of their callback. An attacker who submits their own `request_refund` for the same UTXO during this window — using the same `deposit_msg` (which is public) but their own `refund_address` — can have their callback execute first. Once the attacker's `RefundRequest` is stored, the victim's callback panics and all state changes from that callback are rolled back, but the storage deposit already transferred to the contract is **not** refunded.

The `RefundRequest` struct stores no caller identity: [3](#0-2) 

`execute_refund` is also unrestricted — any account may call it after the timelock: [4](#0-3) 

When `deposit_msg.refund_address` is `None`, the longer `unsafe_refund_timelock_sec` applies: [5](#0-4) 

This timelock is the only mitigation: the DAO/Operator must actively call `reject_refund` before it expires. If they do not, the attacker calls `execute_refund` and the bridge MPC pipeline signs a Bitcoin transaction to the attacker's address.

---

### Impact Explanation

**Primary (Medium):** The victim's `request_refund_callback` panics, their storage deposit is permanently lost, and their BTC remains stuck in the bridge address — a stuck bridge state requiring operator intervention to resolve.

**Secondary (Critical path):** When `deposit_msg.refund_address` is `None`, the attacker's winning `RefundRequest` carries the attacker's Bitcoin address. If the DAO/Operator fails to call `reject_refund` before `unsafe_refund_timelock_sec` elapses, the attacker executes the refund and receives the victim's BTC — an unauthorized release of user funds.

---

### Likelihood Explanation

- `request_refund` is publicly callable; no whitelist or role is required.
- The `deposit_msg` and proof are observable on-chain the moment the user's transaction is submitted.
- NEAR cross-contract calls span multiple blocks, giving the attacker a reliable multi-block window to submit a competing call.
- The only cost to the attacker is the storage deposit (`required_balance_for_request_refund`), a small NEAR amount.
- The DAO/Operator must actively monitor and reject within `unsafe_refund_timelock_sec`; any lapse enables the theft path.

---

### Recommendation

In `request_refund_callback`, before the uniqueness check, test whether an existing request already covers the same UTXO with an equivalent or compatible `refund_address`. If so, treat the call as idempotent and return `true` rather than panicking. This mirrors the fix recommended in the reference report:

```rust
// Analogous to the allowance-check fix in the reference report:
if self.data().refund_requests.contains_key(&utxo_storage_key) {
    // Refund already registered for this UTXO — nothing to do.
    return true;
}
```

Additionally, bind `RefundRequest` to the caller's `AccountId` so that only the original requester can create a request for a given UTXO, and enforce this in `execute_refund`.

---

### Proof of Concept

1. User deposits BTC to a bridge address derived from `deposit_msg` (with `refund_address = None`).
2. The deposit is never finalized via `verify_deposit`.
3. User calls `request_refund(deposit_msg, user_btc_addr, tx_bytes, vout, proof, None)` with the required storage deposit attached.
4. Attacker observes the transaction and immediately calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with their own storage deposit.
5. Both calls trigger `verify_transaction_inclusion_promise` to the Light Client.
6. Attacker's `request_refund_callback` executes first (same or next block); it passes all checks and inserts `RefundRequest { refund_address: attacker_btc_addr, … }`.
7. User's `request_refund_callback` executes and hits:
   ```
   require!(!self.data().refund_requests.contains_key(&utxo_storage_key), "Refund request already exists for this UTXO");
   ```
   The callback panics; the user's storage deposit is not returned.
8. DAO/Operator does not reject within `unsafe_refund_timelock_sec`.
9. Attacker calls `execute_refund(utxo_storage_key, None)`.
10. The bridge builds a PSBT spending the deposit UTXO to `attacker_btc_addr` and requests an MPC signature.
11. After signing, the attacker broadcasts the transaction and receives the user's BTC. [2](#0-1) [1](#0-0) [6](#0-5)

        utxo_storage_key: String,

            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],

            tx_bytes_with_sign: None,

            }),
        };

        require!(

                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),

        // Mark UTXO as verified to prevent verify_deposit later

            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

            amount: refund_request.amount.into(),
