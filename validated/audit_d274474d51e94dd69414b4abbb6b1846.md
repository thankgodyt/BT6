### Title
Tokens Minted to Bridge Account but Never Delivered to User in `safe_mint` When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints tokens to `bridge_id` before checking whether the recipient `account_id` is registered. If the account is not registered, the function silently returns `U128(0)` without transferring the minted tokens, leaving them permanently stranded in the bridge's own token balance with no delivery path to the user.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes `internal_deposit` to the bridge's own account first, then checks registration:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into()); // tokens minted to bridge

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // silently returns 0, tokens never forwarded
}
``` [1](#0-0) 

When `account_id` is not registered for nBTC storage, the function:
1. Mints `amount` nBTC tokens into `bridge_id`'s balance (line 112).
2. Returns `PromiseOrValue::Value(U128(0))` — signaling to the bridge caller that zero tokens were used/delivered (lines 114–116).
3. Never transfers the minted tokens to the intended recipient.

The tokens now reside in `bridge_id`'s nBTC balance. There is no code path in `safe_mint` or its callers (confirmed present in `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` and `contracts/satoshi-bridge/src/nbtc/mod.rs`) that recovers or re-routes these stranded tokens to the user. [2](#0-1) 

### Impact Explanation
A user who deposits BTC to a bridge-derived address but has not registered their NEAR account for nBTC storage will have their deposit processed by the bridge (proof verified, UTXO consumed, deposit marked used), yet receive zero nBTC. The minted tokens accumulate in `bridge_id`'s balance, inflating the circulating nBTC supply above the amount of BTC actually backing it. The user has no mechanism to claim the stranded tokens; the bridge operator would need to manually intervene. This matches the **Medium** impact class: broken callback/delivery rollback and stuck bridge state requiring operator intervention, with potential for supply-backing invariant violation.

### Likelihood Explanation
Any user who sends BTC to a deposit address without first calling `storage_deposit` on the nBTC contract to register their NEAR account will trigger this path. This is a realistic user error — the deposit address is derived off-chain and BTC is sent before any NEAR-side registration step. The relayer then submits the proof, the bridge calls `safe_mint`, and the silent failure occurs. No privileged access or adversarial intent is required.

### Recommendation
Move the registration check **before** minting, or revert (panic) when the recipient is unregistered so the deposit proof is not consumed and the user can retry after registering:

```rust
// Option A: check registration before minting
if self.token.accounts.get(&account_id).is_none() {
    env::panic_str("Recipient account not registered for nBTC storage");
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

Alternatively, auto-register the account before minting (consistent with `mint_inner`'s behavior at line 342–343), so no tokens are ever stranded. [3](#0-2) 

### Proof of Concept
1. User derives a BTC deposit address for their NEAR account `alice.near`.
2. User sends 0.01 BTC to that address **without** calling `storage_deposit` on the nBTC contract for `alice.near`.
3. Relayer submits the Merkle inclusion proof; bridge verifies it and calls `safe_mint("alice.near", 1_000_000, None)`.
4. `internal_deposit(&bridge_id, 1_000_000)` executes — 1,000,000 satoshi-units of nBTC are credited to `bridge_id`.
5. `self.token.accounts.get(&"alice.near")` returns `None`; function returns `U128(0)`.
6. `alice.near` receives 0 nBTC. The deposit UTXO is marked used. The 1,000,000 nBTC sit in `bridge_id`'s balance indefinitely, unbacked by any future BTC deposit. [1](#0-0)
