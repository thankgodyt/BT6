### Title
TOCTOU Race Condition in `sign_btc_transaction` Allows Attacker to Inject Wrong Signature and Permanently Lock Withdrawal Funds - (File: contracts/satoshi-bridge/src/chain_signature.rs)

---

### Summary

`sign_btc_transaction` is publicly callable with no access control beyond the global pause. It performs a pre-call check (`signatures[sign_index].is_none()`) before dispatching an async MPC sign promise, but that check is not atomic with the state write that happens in the callback. Two concurrent callers — an attacker and a legitimate relayer — can both pass the pre-check in the same block, both dispatch sign promises to the MPC, and whichever callback lands first wins. If the attacker's callback lands first carrying a signature derived from a wrong `key_version`, that invalid signature is permanently written into the PSBT, the pending info transitions to `PendingVerify` stage, and the legitimate relayer's callback panics and reverts. The withdrawal is then stuck: the signed Bitcoin transaction is invalid and will be rejected by the network, and the user cannot self-recover without operator (`cancel_withdraw`) intervention.

---

### Finding Description

**Entry point — publicly callable, no role restriction:** [1](#0-0) 

`sign_btc_transaction` carries only `#[payable]` and `#[pause]`. There is no `#[trusted_relayer]` or `#[access_control_any]`, so any NEAR account can call it for any `btc_pending_sign_id`, any `sign_index`, and any `key_version`.

**Pre-call check (not atomic with state write):** [2](#0-1) 

The check `signatures[sign_index].is_none()` is evaluated against the current on-chain state before the async MPC call is dispatched. Because NEAR processes multiple transactions per block and the state is only mutated in the callback (a later receipt), two transactions submitted in the same block both read `None` and both pass.

**Async MPC call dispatched with caller-supplied `key_version`:** [3](#0-2) 

The `key_version` is passed verbatim to the MPC signer. An attacker supplies an arbitrary value.

**Callback — actual state write, but too late to prevent the race:** [4](#0-3) 

The callback re-checks `signatures[sign_index].is_none()`. The first callback to execute wins and writes its signature. The second callback hits the `require!` and panics, reverting only its own receipt — the first callback's write is already committed.

**Transition to verify stage on first callback:** [5](#0-4) 

If the attacker's callback arrives first and `is_all_signed()` becomes true, the pending info is moved to `PendingVerify` stage and removed from `btc_pending_sign_ids`. The PSBT now contains a signature produced under the wrong key.

---

### Impact Explanation

Once the pending info is in `PendingVerify` stage with an invalid signature:

- The signed Bitcoin transaction will be rejected by the Bitcoin network (invalid witness).
- `withdraw_rbf` operates on `PendingSign`-stage entries; it cannot be used here.
- `cancel_withdraw` is restricted to `Role::DAO` or `Role::Operator`.

The user's nBTC tokens are held by the bridge (transferred in `ft_on_transfer`) and cannot be reclaimed without privileged operator intervention. This is **attacker-triggered temporary locking of bridged funds requiring operator intervention** — Medium severity per the allowed impact scope.

---

### Likelihood Explanation

- `sign_btc_transaction` is publicly callable by any NEAR account with no role check.
- The `btc_pending_sign_id` and `sign_index` are emitted as on-chain events (`GenerateBtcPendingInfo`, `BtcInputSignature`), so an attacker can observe them trivially.
- The attacker only needs to submit their transaction in the same block as the legitimate relayer's call — standard front-running on NEAR.
- The only uncertainty is whether the MPC signer accepts an arbitrary `key_version` and returns a signature (rather than an error). If it does, the wrong signature is stored and the withdrawal is stuck. If it returns an error, the attacker's callback takes the `else` branch and returns `false` without writing, allowing the legitimate relayer's callback to succeed — reducing impact to wasted gas only.

---

### Recommendation

1. **Restrict `sign_btc_transaction` to trusted relayers or operators** using `#[trusted_relayer]` or `#[access_control_any(roles(Role::DAO, Role::Operator))]`, eliminating the public attack surface.
2. **Mark the slot as "in-flight" before dispatching the sign promise** (e.g., a sentinel value in `signatures[sign_index]`) so that a second concurrent call fails the pre-check atomically, preventing duplicate MPC calls entirely.
3. **Validate the returned signature against the expected public key** inside `sign_btc_transaction_callback` before writing it to the PSBT, so that a signature from a wrong key is rejected rather than stored.

---

### Proof of Concept

1. User Alice initiates a withdrawal; `btc_pending_sign_id = "abc"`, `sign_index = 0`, correct `key_version = 0`. Event is emitted on-chain.
2. Attacker Bob observes the event and submits `sign_btc_transaction("abc", 0, 999)` in the same block as the legitimate relayer's `sign_btc_transaction("abc", 0, 0)`.
3. Both transactions read `signatures[0] == None` and pass the pre-check. Both dispatch sign promises to the MPC signer.
4. MPC processes both requests. Bob's callback arrives first, storing a signature derived from key version 999. `is_all_signed()` returns true; pending info transitions to `PendingVerify`.
5. The legitimate relayer's callback arrives, hits `require!(signatures[0].is_none(), "Already signed")`, and panics — reverting only its own receipt.
6. The bridge broadcasts the Bitcoin transaction with the invalid signature; it is rejected by the Bitcoin network.
7. Alice's nBTC remains locked in the bridge. She cannot do RBF (wrong stage) and must wait for a DAO/Operator to call `cancel_withdraw` on her behalf.
