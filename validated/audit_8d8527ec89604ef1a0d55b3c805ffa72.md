### Title
Safe-Deposit UTXO Replay via Attacker-Controlled `ft_on_transfer` Return Value Removing Claim Marker — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

The `safe_mint_callback` failure branch unconditionally removes the UTXO key from `verified_deposit_utxo` whenever `safe_mint` returns `U128(0)`. Because the attacker controls `recipient_id` (and therefore the `ft_on_transfer` implementation that determines what `safe_mint` returns), the attacker can reliably trigger this removal, then re-submit the identical BTC deposit a second time and receive a second mint. This is a concrete, unprivileged, cross-chain double-spend.

---

### Finding Description

**Step 1 — Entry point**

`internal_safe_verify_deposit_entry` is the public entry for the safe-deposit path. It accepts an attacker-chosen `DepositMsg` (including `recipient_id` and `safe_deposit.msg`) and a valid BTC transaction proof. [1](#0-0) 

**Step 2 — Replay guard is set**

`verify_safe_deposit_callback` inserts the UTXO storage key into `verified_deposit_utxo` before calling `safe_mint`. This is the *only* replay guard for the safe-deposit path. [2](#0-1) 

**Step 3 — `safe_mint` mints to `bridge_id` then calls `ft_transfer_call` to `recipient_id`**

In the nbtc contract, `safe_mint` first deposits tokens into `bridge_id`, then — when `msg` is `Some` — calls `ft_transfer_call(account_id=recipient_id, amount, msg)`. The return value of `safe_mint` is the `used_amount` returned by `ft_resolve_transfer`, which equals whatever `ft_on_transfer` on the receiver returns. [3](#0-2) 

**Step 4 — Attacker-controlled `ft_on_transfer` returns full amount → `safe_mint` returns `U128(0)`**

If the attacker's `recipient_id` contract returns the full `amount` from `ft_on_transfer` (signalling "I used nothing"), `ft_resolve_transfer` returns `used_amount = 0`, so `safe_mint` returns `U128(0)`.

**Step 5 — `safe_mint_callback` removes the replay guard on this path**

`is_refund_required()` returns `true` when `safe_mint` returned `U128(0)`. The failure branch then **removes** the UTXO key from `verified_deposit_utxo` and fires a detached `burn` call. [4](#0-3) [5](#0-4) 

**Step 6 — Replay**

With the UTXO key removed, the attacker (or any relayer) re-submits the identical BTC transaction proof. `verify_safe_deposit_callback` inserts the key again (the `require!` passes), `safe_mint` mints a fresh `mint_amount` of nBTC, and this time the attacker uses a normal `recipient_id` (or no `msg`) so the success path executes and the UTXO is stored. The attacker has now received two mints for one on-chain BTC deposit.

**Why the `burn` does not save the invariant**

The `burn` is `.detach()` — fire-and-forget with no error handling. Even if it succeeds, the UTXO key is already gone from `verified_deposit_utxo` before the burn receipt executes, so the replay window is open regardless. [6](#0-5) 

---

### Impact Explanation

An unprivileged attacker can mint nBTC/nZEC tokens twice for a single on-chain BTC/ZEC deposit. This is unauthorized minting and constitutes direct theft from the protocol's backing reserve. The wrapped-token supply grows beyond the actual BTC locked, breaking the 1:1 peg.

---

### Likelihood Explanation

The attacker only needs to:
1. Deploy a NEAR contract whose `ft_on_transfer` returns the full amount.
2. Submit a valid BTC deposit (they are the depositor, so they control `recipient_id` and `safe_deposit.msg`).
3. Wait for `safe_mint_callback` to complete, then re-submit the same proof.

No privileged role, leaked key, or external dependency is required. The entire path is reachable from public contract calls.

---

### Recommendation

The UTXO key must **never** be removed from `verified_deposit_utxo` once it has been inserted, regardless of the outcome of `safe_mint`. The safe-deposit path should be all-or-nothing at the claim-marker level:

- On `safe_mint` failure: keep the UTXO key in `verified_deposit_utxo` (mark it as permanently consumed), burn the minted tokens, and refund storage — but do **not** remove the key.
- Alternatively, do not insert the key until the `safe_mint` call is confirmed successful (move the insert into the success branch of `safe_mint_callback`), and ensure the failure branch never allows re-entry for the same UTXO.

---

### Proof of Concept

```
1. Attacker deploys `attacker.near`:
   fn ft_on_transfer(&mut self, sender_id, amount, msg) -> U128 {
       amount  // return full amount = "I used nothing"
   }

2. Attacker sends 1 BTC to the bridge deposit address derived from:
   DepositMsg { recipient_id: "attacker.near", safe_deposit: Some(SafeDepositMsg { msg: "{...}" }), ... }

3. Relayer calls verify_deposit_v2 with the valid merkle proof.
   → verify_safe_deposit_callback inserts utxo_storage_key into verified_deposit_utxo
   → safe_mint mints 1 nBTC to bridge_id, calls ft_transfer_call("attacker.near", 1 nBTC, msg)
   → attacker.near.ft_on_transfer returns 1 nBTC (full amount)
   → ft_resolve_transfer returns used_amount = 0
   → safe_mint returns U128(0)
   → safe_mint_callback: is_refund_required() = true
       → verified_deposit_utxo.remove(utxo_storage_key)   ← guard gone
       → burn(bridge_id, 1 nBTC).detach()
       → transfer(storage_refund).detach()

4. Attacker (or any relayer) re-submits the identical proof with:
   DepositMsg { recipient_id: "attacker.near", safe_deposit: None, ... }
   (or any recipient that will accept the transfer)
   → verified_deposit_utxo.insert(utxo_storage_key) succeeds (key was removed)
   → safe_mint mints another 1 nBTC → transferred to attacker

Result: 2 nBTC minted for 1 BTC deposited.
```

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
