### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Peras Certificate Without Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance for `StandardHash blk` implements `validatePerasCert` as an unconditional stub that always returns `Right` (success), performing zero cryptographic or structural checks on inbound Peras certificates. Both production pool-writer paths (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) invoke this stub via `validatePerasCert mkPerasParams`, meaning any peer can inject arbitrary certificates that are accepted, stored, and used to boost block weights in chain selection.

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No check is performed on `cert`. The function unconditionally wraps any input as a `ValidatedPerasCert` with the full `perasWeight params` boost.

**Production call sites — both pool writers use this stub:** [2](#0-1) [3](#0-2) 

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `(validatePerasCert mkPerasParams)` as the validation function to `processCerts`.

**`processCerts` accepts all certs that pass validation (which is all of them):** [4](#0-3) 

`processCerts` calls `validateCert` on each inbound certificate; since `validatePerasCert` always returns `Right`, every certificate passes and is stored.

**Chain selection uses the stored boost weights:**

`ValidatedPerasCert` carries `vpcCertBoost = perasWeight params` (currently `PerasWeight 15`). The `PerasCertDB` exposes `getWeightSnapshot` which feeds directly into chain selection weight comparisons. A certificate for an adversarial block therefore grants it a weight boost of 15, potentially making it preferred over the honest chain. [5](#0-4) 

**Analog to the original bug:**

The original `LibOwnable._setAdmin` bug: a critical state-setter accepts a null/invalid value (`address(0)`) without checking, corrupting privileged state. Here, `validatePerasCert` accepts any certificate without checking, corrupting chain-selection state. Both are missing-validation bugs on a function that sets security-critical state.

### Impact Explanation

An unprivileged peer connected via the ObjectDiffusion mini-protocol can craft and send `PerasCert` objects with arbitrary `pcCertRound` and `pcCertBoostedBlock` fields. Because `validatePerasCert` performs no checks — no aggregate signature verification, no quorum check, no round-number bounds check, no boosted-block existence check — every such certificate is accepted and stored. The stored certificates inflate the chain-selection weight of the attacker-chosen block by `perasWeight = 15` per certificate per round. This directly enables an unprivileged peer to make an honest node prefer a non-canonical or adversarially-controlled chain, violating the Peras chain-selection security guarantee.

**Severity: Critical** — matches "Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" and "Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain."

### Likelihood Explanation

The ObjectDiffusion mini-protocol is a standard peer-to-peer channel; any connected peer can send `PerasCert` messages. No keys, stake, or privileged access are required. The attacker only needs to be a connected peer and send a well-formed CBOR-encoded `PerasCert` with a crafted `pcCertBoostedBlock`. The code path is unconditional and exercised on every inbound certificate batch.

### Recommendation

Replace the stub with real validation before any certificate is stored or used in chain selection. At minimum, `validatePerasCert` must verify:

1. The aggregate vote signature over the claimed quorum of voters.
2. That the total stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold`).
3. That `pcCertRound` is within a valid range relative to the current chain tip.
4. That `pcCertBoostedBlock` refers to a block that actually exists and is old enough (`perasBlockMinSlots`).

Until real validation is implemented, inbound certificates from peers should be rejected entirely rather than accepted unconditionally. The `PerasCfg` passed to `validatePerasCert` must be the live, chain-derived configuration rather than the hardcoded `mkPerasParams` placeholder.

### Proof of Concept

1. Connect to a node as a peer via the ObjectDiffusion mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <adversarial block point>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert cert 15)`.
4. The certificate is stored in `PerasCertDB` / `ChainDB`.
5. `getWeightSnapshot` now returns a weight of 15 for the adversarial block.
6. Chain selection compares the honest chain (weight = block count) against the adversarial chain (weight = block count + 15); the adversarial chain is preferred if its block count is within 15 of the honest tip.
7. Repeat for multiple rounds to accumulate weight and force a permanent switch to the adversarial chain. [6](#0-5) [7](#0-6) [8](#0-7)
