Audit Report

## Title
`ft_transfer` Failure Silently Ignored in `fin_transfer_send_tokens_callback`, Permanently Freezing Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

In `process_fin_transfer_to_near`, the transfer ID is committed to `finalised_transfers` before the token push-payment executes. When the subsequent `ft_transfer` call fails (e.g., recipient blacklisted in a USDC-like NEP-141 token), `fin_transfer_send_tokens_callback` does not inspect the promise result for the non-`ft_transfer_call` path and unconditionally takes the success branch. The transfer ID remains permanently in `finalised_transfers`, the recipient receives zero tokens, and no recovery path exists — bridged funds are permanently frozen.

## Finding Description

**State committed before push-payment.** `process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875 as its first action, inserting the transfer ID into `finalised_transfers`. This state is committed when the parent receipt completes. All subsequent steps (`send_tokens`, `fin_transfer_send_tokens_callback`) execute as separate receipts; a failure in them does not roll back this insertion.

**`ft_transfer` path selected for non-deployed tokens with empty `msg`.** In `send_tokens` (lines 2102–2106), when `msg.is_empty()` and the token is not a deployed bridge token, `ft_transfer` is dispatched. `ft_transfer` panics as a NEAR receipt if the recipient is blacklisted, the token is paused, or any other token-level restriction applies.

**Callback never checks the `ft_transfer` promise result.** `is_refund_required` (lines 1784–1803) only inspects `env::promise_result_checked` when `is_ft_transfer_call == true`. For the plain `ft_transfer` path, `is_ft_transfer_call` is `false` (set at line 1973 as `!msg.is_empty()`), so `is_refund_required` unconditionally returns `false`. The callback then takes the else-branch: emits `FinTransferEvent`, sends fees to the fee recipient, and returns — regardless of whether `ft_transfer` succeeded or failed.

**Lock accounting already decremented.** `unlock_tokens_if_needed` is called at lines 1881–1885 before `send_tokens`. The locked-token counter is decremented, but the tokens remain physically in the bridge contract. The `revert_lock_actions` path inside the callback is never reached, leaving accounting permanently inconsistent.

**No retry possible.** Because the transfer ID is in `finalised_transfers`, any subsequent call to `fin_transfer` with the same transfer ID panics with `TransferAlreadyFinalised`.

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**: the recipient receives zero tokens, the bridge holds the funds with no withdrawal mechanism, the locked-token accounting is corrupted, and `FinTransferEvent` falsely signals success to off-chain observers and the origin chain. Retrying `fin_transfer` is blocked by `TransferAlreadyFinalised`. This matches the Critical allowed impact class: *permanent freezing of bridged funds across NEAR flows*.

## Likelihood Explanation

Any NEP-141 token implementing a transfer blacklist (USDC, USDT, and similar regulated stablecoins) can trigger this path. The recipient address is fully attacker-controlled from the origin chain — a user specifies any NEAR account as recipient. If that account is blacklisted in the token contract (whether by the token issuer for regulatory reasons, or by a user who controls the recipient account and deliberately triggers blacklisting after initiating the transfer), the next relayer call to `fin_transfer` permanently freezes the funds. No bridge admin action is required; the trigger is a standard, widely-deployed token-contract feature. The condition is realistic and repeatable for any blacklist-capable token registered with the bridge.

## Recommendation

`fin_transfer_send_tokens_callback` must check the promise result for the plain `ft_transfer` path. Specifically, `is_refund_required` should be extended to call `env::promise_result_checked` when `is_ft_transfer_call == false` and treat a failed promise as requiring a refund. On failure, the callback should:

1. Call `remove_fin_transfer` to un-finalize the transfer ID, restoring retryability.
2. Call `revert_lock_actions` to restore the locked-token accounting.
3. Call `burn_tokens_if_needed` if the token is a deployed bridge token (to reverse any mint).
4. Emit `FailedFinTransferEvent` so relayers and the origin chain observe the failure.

This mirrors the existing `ft_transfer_call` failure-handling logic and closes the asymmetry between the two paths.

## Proof of Concept

1. Deploy a NEP-141 token on NEAR with a blacklist feature (USDC-equivalent). Register it with the bridge on both EVM and NEAR sides.
2. User on EVM calls `initTransfer` sending 1000 USDC to NEAR recipient `alice.near`.
3. Token issuer blacklists `alice.near` in the NEAR token contract (before or after step 2).
4. Relayer calls `fin_transfer` with the proof. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (committed).
   - `unlock_tokens_if_needed` decrements the locked-token counter.
   - `send_tokens` dispatches `ft_transfer(alice.near, 1000, None)`.
   - `ft_transfer` panics because `alice.near` is blacklisted — receipt fails.
5. `fin_transfer_send_tokens_callback` is invoked with a failed promise result.
   - `is_ft_transfer_call = false` → `is_refund_required` returns `false` without reading the promise result.
   - Callback takes the success branch, emits `FinTransferEvent`.
6. **Result**: `alice.near` holds 0 tokens. Transfer ID is permanently in `finalised_transfers`. Retrying `fin_transfer` panics with `TransferAlreadyFinalised`. 1000 USDC are permanently frozen in the bridge contract with corrupted lock accounting.

A local integration test can reproduce this by deploying a mock NEP-141 contract that panics on `ft_transfer` for a specific account, then executing the full `fin_transfer` flow and asserting that `finalised_transfers` contains the transfer ID while the recipient balance remains zero.
