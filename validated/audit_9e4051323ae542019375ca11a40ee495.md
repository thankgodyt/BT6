### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `validatePerasCert` implementation in the catch-all `BlockSupportsPeras` instance unconditionally returns `Right` (success) for every inbound certificate, performing no cryptographic or semantic checks whatsoever. This stub is wired directly into the production inbound-certificate processing path (`makePerasCertPoolWriterFromChainDB`). When Peras is enabled, any unprivileged peer can send a crafted `PerasCert` naming any block as the boosted target; the certificate is accepted, stored, and used to add `PerasWeight 15` to that block's chain during chain selection, potentially causing the node to prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

In the catch-all instance `instance StandardHash blk => BlockSupportsPeras blk`, the `validatePerasCert` method is a stub that unconditionally succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always PerasWeight 15
      }
```

No signature is verified, no quorum is checked, no committee membership is validated. [1](#0-0) 

**Production inbound path — `makePerasCertPoolWriterFromChainDB`:**

The production pool writer for certificates received from peers passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**`processCerts` accepts every certificate that passes the stub:**

`processCerts` calls `validateCert` on each new certificate and adds all `Right` results to the DB. Because the stub always returns `Right`, every peer-supplied certificate is stored. [3](#0-2) 

**Chain selection is triggered for the boosted block:**

`chainSelSync` in `ChainSel.hs` processes each accepted certificate: it stores it in `PerasCertDB` and then calls `chainSelectionForBlock` for the block named in `pcCertBoostedBlock`. The `weightedSelectView` function subsequently adds the stored `vpcCertBoost` (= `PerasWeight 15`) to the total weight of any chain fragment containing that block. [4](#0-3) [5](#0-4) 

**`PerasWeight 15` is the configured default boost:**

`mkPerasParams` sets `perasWeight = PerasWeight 15`. A single forged certificate therefore adds 15 to the total weight of the targeted chain, equivalent to 15 extra blocks, which is enough to flip chain selection in favour of a shorter adversary chain. [6](#0-5) 

### Impact Explanation

When Peras is enabled, an unprivileged peer can send one crafted `PerasCert` per round (one per `PerasRoundNo`) naming any block in the volatile DB as the boosted target. Each accepted certificate adds `PerasWeight 15` to that block's chain. An adversary who controls a minority chain can boost its tip repeatedly, causing an honest node to switch away from the canonical chain and onto the adversary's chain. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical, less-secure chain beyond the intended security assumptions of Ouroboros Peras.

### Likelihood Explanation

Peras is currently disabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However, the code is in production files and the vulnerability is fully active the moment Peras is enabled on any network (private testnet, future mainnet activation). No privileged access, no key compromise, and no stake majority are required — any connected peer can send a `PerasCert` message. The attack is trivially reproducible on a private testnet with Peras enabled.

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before Peras is enabled on any network. At minimum, the implementation must:

1. Verify the aggregate BLS signature in `pcSignature` against the claimed voters' public keys (as defined in `Ouroboros.Consensus.Peras.Cert.V1`).
2. Verify each voter's eligibility proof (`PerasCertVoters`) against the current epoch's committee selection.
3. Verify that the total stake of the certified voters exceeds the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
4. Verify that `pcCertRound` and `pcBoostedBlock` are within the valid window (not too old, not in the future).

Until real validation is in place, the Peras feature flag must remain disabled and the stub must not be reachable from any peer-facing code path.

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect a malicious peer to an honest node via the Object Diffusion miniprotocol.
2. Send a `PerasCert` message with:
   - `pcCertRound = <any fresh round number not yet in the node's DB>`
   - `pcCertBoostedBlock = <point of a block on the adversary's minority fork>`
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })` unconditionally.
4. The certificate is stored in `PerasCertDB`.
5. `chainSelSync` calls `chainSelectionForBlock` for the boosted block.
6. `weightedSelectView` adds `PerasWeight 15` to the adversary's chain fragment.
7. If the adversary's chain is within 15 blocks of the honest tip, the node switches to the adversary's chain.
8. Repeat once per round to maintain the boost advantage indefinitely.

  alreadyInDb <- atomically alreadyInDbSTM

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
