### Title
Concurrent `sign_btc_transaction` calls for the same index cause second callback to panic and lose the attached NEAR deposit — (`contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` is a public, payable function with no caller-identity guard. The pre-call `is_none()` check in `internal_sign_btc_transaction` is a plain read that is not atomic with the write performed in `sign_btc_transaction_callback`. Two calls for the same `(btc_pending_sign_id, sign_index)` pair can both pass the pre-call check before either callback lands, both forward their attached NEAR deposit to the MPC contract, and then the second callback panics at the identical `is_none()` guard inside the callback. Because the MPC `sign` call already succeeded and consumed the deposit, the panic does not trigger a refund, and the deposit is permanently lost.

---

### Finding Description

**Step 1 — Public entry, no caller check.**

`sign_btc_transaction` is `#[payable]` and carries no `require!(env::predecessor_account_id() == btc_pending_info.account_id)` guard. [1](#0-0) 

**Step 2 — Pre-call check is a plain read, not a write.**

`internal_sign_btc_transaction` reads `signatures[sign_index]` and requires it to be `None`, but does **not** write anything to the slot. The slot stays `None` until the callback fires in a future receipt. [2](#0-1) 

**Step 3 — Deposit is forwarded unconditionally.**

`sign_promise` attaches `env::attached_deposit()` to the outgoing MPC call. Once the MPC `sign` function succeeds, the deposit belongs to the MPC contract regardless of what the callback does. [3](#0-2) 

**Step 4 — Callback repeats the same guard.**

The callback re-checks `signatures[sign_index].is_none()` and panics with `"Already signed"` if the first callback already wrote the slot. [4](#0-3) 

**Race window:** In NEAR's async execution model, Call A and Call B are two separate transactions. Both can be included in the same block (or in consecutive blocks before the MPC receipt returns). Both read `signatures[sign_index] == None` at step 2, both dispatch the MPC promise, and both schedule a callback. When Callback A fires it writes the slot and returns `true`. When Callback B fires it hits the `require!` and panics. NEAR reverts Callback B's state changes, but the deposit that was already transferred to the MPC contract in Call B's receipt is not returned.

---

### Impact Explanation

- The NEAR deposit attached to the second `sign_btc_transaction` call is permanently lost.
- Because `sign_btc_transaction` has no caller-identity check, an adversary can deliberately race a legitimate user's call: the adversary submits their own call first, their callback succeeds, and the legitimate user's callback panics, burning the legitimate user's deposit.
- The `BTCPendingInfo` state itself is not permanently corrupted (the first callback's writes survive; the second callback's panic reverts nothing meaningful), but the deposit loss is irreversible.

---

### Likelihood Explanation

- The function is public and payable with no access control beyond the global pause flag.
- The MPC signing round-trip takes multiple blocks, giving a wide window for a second call to pass the pre-call check.
- An attacker only needs to observe the mempool (or the on-chain pending-sign state) and submit a competing call before the first callback lands.

---

### Recommendation

1. **Mark the slot as "in-flight" atomically at call time.** Before dispatching the MPC promise, write a sentinel value (e.g., a dedicated `InFlight` variant) to `signatures[sign_index]`. The callback then checks for `InFlight` rather than `None`, and any concurrent call that reads a non-`None` slot is rejected immediately.

2. **Add a caller-identity check.** Require `env::predecessor_account_id() == btc_pending_info.account_id` (or a trusted relayer role) so that only the owning account can trigger signing for its own pending transaction.

3. **Refund the deposit on callback failure.** In the `else` branch of `sign_btc_transaction_callback`, explicitly refund `env::attached_deposit()` to the original caller so that a failed callback does not silently burn funds.
