Looking at the vulnerability class from M-07 — an accounting balance being decremented without a corresponding credit, leaving a counter below what subsequent operations expect — I need to find an analog in this bridge's production token/bridge files.

Let me examine the nBTC contract's `safe_mint` function and the `burn` function closely. [1](#0-0) [2](#0-1) 

The `safe_mint` function mints tokens to `self.bridge_id` **before** checking whether the recipient has a registered storage account. If the recipient has no storage, the function returns `U128(0)` and exits — but the tokens are already credited to the bridge's own nBTC balance with no recovery path inside the nBTC contract.

The `burn` function then withdraws from `self.bridge_id`'s balance unconditionally. Any "orphaned" tokens left in the bridge's balance from failed `safe_mint` calls are indistinguishable from tokens legitimately transferred there by withdrawing users, and can be consumed by future `burn` calls.

### Title
`safe_mint` Credits Bridge Balance Before Storage Check, Causing Permanent Loss of User Deposits — (File: `contracts/nbtc/src/lib.rs`)

### Summary
`safe_mint` in the nBTC contract mints tokens to the bridge's own account before verifying that the intended recipient has registered storage. When the recipient has no storage account, the function silently returns `U128(0)`, leaving the minted tokens stranded in the bridge's nBTC balance. Because the satoshi-bridge marks the deposit UTXO as verified regardless of whether the user actually received tokens, the depositor's BTC is permanently consumed with no nBTC issued to them.

### Finding Description
In `safe_mint` (`contracts/nbtc/src/lib.rs` lines 101–124):

```rust
self.token.internal_deposit(&self.bridge_id, amount.into()); // (1) tokens minted to bridge

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));                   // (2) early return, tokens stay in bridge
}
// (3) only reaches here if user has storage
self.ft_transfer(account_id, amount, None);
```

Step (1) unconditionally increases the bridge's nBTC balance by `amount`. Step (2) exits without transferring anything to the user and without reversing the mint. The nBTC contract has no internal recovery mechanism for this case — there is no `lost_found` entry, no refund, and no revert.

The `burn` function (`contracts/nbtc/src/lib.rs` lines 150–177) later withdraws from `self.bridge_id`:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
```

Orphaned tokens from failed `safe_mint` calls inflate the bridge's nBTC balance. They are structurally identical to tokens legitimately deposited by withdrawing users and can be consumed by any subsequent `burn` call, permanently destroying the depositor's claim. [3](#0-2) [4](#0-3) 

### Impact Explanation
A user whose BTC deposit triggers `safe_mint` while they have no nBTC storage account loses their entire deposit:
- Their BTC UTXO is marked verified in the satoshi-bridge (consumed).
- They receive zero nBTC.
- The minted tokens sit in the bridge's nBTC balance and can be silently burned during any future withdrawal, permanently destroying the user's funds.

This matches the **Medium** allowed impact: *permanent burning below backed supply* and *stuck bridge state requiring operator intervention*, and potentially **Critical** if the orphaned balance is consumed by another user's burn (unauthorized release of bridge-controlled funds).

### Likelihood Explanation
The trigger condition — a user depositing BTC before registering storage on the nBTC contract — is realistic and reachable by any unprivileged actor:
- A new user unfamiliar with NEP-141 storage registration deposits BTC first.
- A relayer (public, permissionless) submits the inclusion proof before the user registers storage.
- An adversary deliberately submits a proof for a victim who has not yet registered, front-running the victim's storage registration.

No privileged access is required. The relayer path is fully public.

### Recommendation
Move the storage check **before** the mint. Only call `internal_deposit` after confirming the recipient has a registered account (or register them automatically):

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // no mint, no orphaned tokens
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, if the bridge's callback receives `U128(0)`, it must explicitly reverse the deposit UTXO verification and refund the user, rather than treating the deposit as finalized.

### Proof of Concept
1. User Alice deposits BTC to her bridge-derived address without calling `storage_deposit` on the nBTC contract.
2. A relayer (or Alice herself) submits the Merkle inclusion proof to the satoshi-bridge.
3. The satoshi-bridge verifies the proof, marks Alice's UTXO as verified, and calls `nbtc.safe_mint(alice, amount, None)`.
4. `safe_mint` executes `internal_deposit(&bridge_id, amount)` — bridge's nBTC balance increases by `amount`.
5. `safe_mint` checks `accounts.get(&alice)` → `None` → returns `U128(0)`.
6. Alice's UTXO remains in `verified_deposit_utxo`; her BTC is permanently locked.
7. Alice holds zero nBTC. The `amount` tokens sit in the bridge's balance.
8. Later, when Bob withdraws nBTC, the bridge calls `burn(bob, burn_amount, ...)` which calls `internal_withdraw(&bridge_id, burn_amount)`. If `burn_amount` draws on Alice's orphaned tokens, Alice's deposit is silently destroyed to satisfy Bob's withdrawal. [1](#0-0) [2](#0-1)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
