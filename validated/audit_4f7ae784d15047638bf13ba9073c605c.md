### Title
Peras `PerasCertDB` weight snapshot includes expired certificates without round-based expiry filtering, enabling chain-selection weight manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The `PerasCertDB` implementation accepts Peras certificates from unprivileged peers without performing any actual cryptographic or protocol-level validation (`validatePerasCert` is a stub that always returns `Right`), and the weight snapshot used for chain selection (`implGetWeightSnapshot`) includes **all** stored certificates without filtering those that have expired per the Peras round-based expiry window (`currRoundNo > _A + certRoundNo`). This is directly analogous to the external report's finding: stale/expired data is included in a security-critical calculation without an expiry check, allowing an attacker to permanently inflate chain selection weights for a chosen block.

---

### Finding Description

**Root cause 1 — `validatePerasCert` is a no-op stub:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the default `validatePerasCert` implementation unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called by `processCerts` in the inbound certificate handler: [2](#0-1) 

Any certificate received from a peer passes validation and is forwarded to `implAddCert`.

**Root cause 2 — `implAddCert` performs no expiry or round-validity check:**

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  ...
  if Set.member roundNo (pcdsCertIds pcds)
    then pure PerasCertAlreadyInDB
    else do ...
``` [3](#0-2) 

The only guard is a duplicate-round check. There is no check that the certificate's round number is within the valid window relative to the current chain state.

**Root cause 3 — `implGetWeightSnapshot` includes all stored certificates without expiry filtering:**

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds)
          ]
  pure (WithFingerprint weights fp)
``` [4](#0-3) 

Every certificate in `pcdsCertsByTicket` contributes to the weight snapshot, regardless of whether its round number has expired per the Peras protocol parameter `_A` (`PerasCertMaxRounds`). The expiry check `currRoundNo <= _A + latestCertSeenRoundNo` exists only in the **cert inclusion** logic for block forging: [5](#0-4) 

It is **not** applied to the weight snapshot used for chain selection.

**Root cause 4 — Garbage collection uses slot age, not round expiry:**

`implGarbageCollect` removes certificates only when the boosted block's slot falls below the immutable tip: [6](#0-5) 

A certificate from a round that is `> _A` rounds old but whose boosted block is still in the volatile DB is never garbage-collected and permanently contributes to the weight snapshot.

**The weight snapshot feeds directly into chain selection:**

`preferAnchoredCandidate` uses the snapshot to compute `weightedSelectView` for both the current chain and every candidate: [7](#0-6) 

`totalWeightOfFragment` adds the weight boost from the snapshot to the block count, so inflated boosts directly cause the node to prefer a heavier-looking but non-canonical candidate: [8](#0-7) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Send a crafted `PerasCert` for an arbitrary round number and boosted block point.
2. The certificate passes `validatePerasCert` (always `Right`) and `implAddCert` (no expiry check).
3. The certificate is stored permanently in `PerasCertDB` and contributes to every subsequent `implGetWeightSnapshot` call.
4. Chain selection via `preferAnchoredCandidate` now sees an inflated total weight for the attacker's chosen chain fragment.
5. The honest node switches to a non-canonical chain that it would not have selected under correct Peras semantics.

This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended Peras security assumptions, by exploiting the absence of expiry filtering in the weight snapshot — directly analogous to the external report's expired-order price manipulation.

---

### Likelihood Explanation

- **Entry path is fully reachable**: certificates arrive via the `ObjectDiffusion` mini-protocol from any connected peer; no special privileges are required.
- **Peras is currently disabled by default** (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"), which limits immediate production exposure. However, the code is present in production source files and the feature is actively being enabled.
- The TODO comments referencing issue #120 confirm the developers are aware validation is incomplete, but the code is already wired into the live chain-selection path.
- Likelihood is **Medium**: the attack is trivially executable once Peras is enabled, requiring only the ability to send a network message.

---

### Recommendation

1. **`implGetWeightSnapshot`** should filter out certificates whose round number has expired: `certRoundNo + _A < currentRoundNo`. The current round number must be threaded into the snapshot query, or the snapshot must be recomputed at chain-selection time with the current round as context.

2. **`implGarbageCollect`** should additionally remove certificates whose round number is more than `_A` rounds behind the current round, not only those whose boosted block has become immutable.

3. **`validatePerasCert`** must be implemented with real cryptographic and protocol-level checks before Peras is enabled in production. The stub should at minimum reject certificates with round numbers outside the valid window.

4. **`implAddCert`** should reject certificates whose round number is already expired at insertion time, consistent with the expiry check in `latestCertSeenIsNotExpired`.

---

### Proof of Concept

```
Precondition: Peras is enabled; current round is R; _A = 3.

1. Attacker connects as a peer and sends PerasCert { round = R-10, boostedBlock = B_adv }
   where B_adv is the tip of an adversarial fork.

2. processCerts calls validatePerasCert → always Right.
   implAddCert stores the cert (round R-10 not yet in pcdsCertIds).

3. implGetWeightSnapshot returns a PerasWeightSnapshot containing
   (B_adv, perasWeight) even though round R-10 is expired (R-10 + 3 < R).

4. preferAnchoredCandidate computes totalWeightOfFragment for the adversarial
   fragment: blockCount + perasWeight > honest chain's blockCount.

5. The node switches to the adversarial fork, violating chain-selection safety.

Note: step 1 can be repeated for multiple rounds to accumulate weight boosts
across many expired certificates, amplifying the effect.
```
