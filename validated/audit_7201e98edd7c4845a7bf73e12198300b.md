Audit Report

## Title
Arbitrary `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Relayer Fees - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`sign_transfer` accepts a caller-supplied `fee_recipient: Option<AccountId>` with no validation that the caller has any claim to that field. Any trusted relayer can call `sign_transfer` on any pending transfer and embed their own account as `fee_recipient` in the MPC-signed payload. Because the fee claim on NEAR (`claim_fee_callback`) enforces that only the account named as `fee_recipient` in the on-chain proof can receive the fee, a malicious trusted relayer who submits their signed payload to the destination chain first irrecoverably redirects the fee to themselves.

## Finding Description
`sign_transfer` places the caller-supplied `fee_recipient` directly into `TransferMessagePayload` without any check against `env::predecessor_account_id()`:

```rust
// near/omni-bridge/src/lib.rs L447-500
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,   // fully caller-controlled
    fee: &Option<Fee>,
) -> Promise {
    ...
    let transfer_payload = TransferMessagePayload {
        ...
        fee_recipient,   // embedded verbatim, no validation
        ...
    };
```

The MPC network signs this payload. On the EVM destination chain, `OmniBridge.finTransfer` verifies the MPC signature and emits a `FinTransfer` event that includes `feeRecipient` verbatim from the signed payload:

```solidity
// evm/src/omni-bridge/contracts/OmniBridge.sol L359-366
emit BridgeTypes.FinTransfer(
    payload.originChain, payload.originNonce,
    payload.tokenAddress, payload.amount,
    payload.recipient,
    payload.feeRecipient   // taken directly from the MPC-signed payload
);
```

Back on NEAR, `claim_fee_callback` reads `fee_recipient` from the prover result (the EVM `FinTransfer` event) and enforces:

```rust
// near/omni-bridge/src/lib.rs L1083-1086
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

This means whoever is named as `fee_recipient` in the EVM event is the only account that can claim the fee on NEAR. Because the EVM `finTransfer` marks the destination nonce as consumed (`completedTransfers[payload.destinationNonce] = true`) on first use, the first valid signature submitted wins permanently.

For non-zero fee transfers, `sign_transfer_callback` does **not** remove the pending transfer record:

```rust
// near/omni-bridge/src/lib.rs L655-658
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
```

This means the transfer remains open for any trusted relayer to call `sign_transfer` on it at any time, obtaining a competing MPC signature with a different `fee_recipient`.

## Impact Explanation
This is a concrete instance of **fee mis-accounting / unauthorized fund redirection** — an explicitly listed Critical impact. A malicious trusted relayer can steal 100% of the relayer fee from every pending non-zero-fee transfer. The fee is paid on NEAR (via `claim_fee` → `send_fee_internal`) to whichever account is named in the MPC-signed EVM event. Once the attacker's signature is submitted to the EVM and the nonce is consumed, the legitimate relayer's signature is permanently invalidated and the fee is irrecoverably redirected.

## Likelihood Explanation
Becoming a trusted relayer is permissionless: stake 1,000 NEAR and wait ~7 days. The attack is economically rational for any attacker who can steal fees from all other relayers indefinitely. NEAR has no public mempool, so there is no race condition in the traditional sense — the attacker simply calls `sign_transfer` on any pending transfer at any time while it remains in `pending_transfers`, then races to submit the signed payload to the EVM destination chain. The attack is deterministic and repeatable for every non-zero-fee transfer.

## Recommendation
Bind `fee_recipient` to the caller inside `sign_transfer`. Replace the caller-supplied parameter with `env::predecessor_account_id()`, or add an explicit guard:

```rust
if let Some(ref recipient) = fee_recipient {
    require!(
        recipient == &env::predecessor_account_id(),
        "fee_recipient must be the caller"
    );
}
```

This ensures only the relayer who calls `sign_transfer` can be named as `fee_recipient` in the MPC-signed payload, preventing fee redirection.

## Proof of Concept
1. Alice (trusted relayer) monitors pending transfers and intends to call `sign_transfer(transfer_id: {Near, 42}, fee_recipient: Some("alice.near"), fee: Some(...))`.
2. Eve (malicious trusted relayer) calls first: `sign_transfer(transfer_id: {Near, 42}, fee_recipient: Some("eve.near"), fee: Some(...))`. This succeeds because there is no check that `fee_recipient == env::predecessor_account_id()`.
3. The MPC network signs a `TransferMessagePayload` with `fee_recipient = "eve.near"`.
4. Eve submits this signature to the EVM `finTransfer`. The EVM marks `completedTransfers[destination_nonce] = true` and emits `FinTransfer(..., feeRecipient: "eve.near")`.
5. Alice's subsequent `sign_transfer` call also succeeds (transfer is not removed for non-zero fee), but when Alice submits her signature to the EVM, it reverts with `NonceAlreadyUsed`.
6. Eve calls `claim_fee` on NEAR with proof of the EVM `FinTransfer` event. `claim_fee_callback` reads `fee_recipient = "eve.near"` from the proof, checks `fee_recipient == predecessor_account_id` (both are `eve.near`) → passes, and pays the fee to Eve.
7. Alice cannot call `claim_fee` because the on-chain proof has `feeRecipient = "eve.near"`, causing the `OnlyFeeRecipientCanClaim` check to fail.

A local integration test can reproduce this by: (a) registering two trusted relayers, (b) initiating a transfer with non-zero fee, (c) having the second relayer call `sign_transfer` with their own account as `fee_recipient`, (d) submitting that signature to a mock EVM prover, and (e) verifying that `claim_fee` succeeds for the attacker and fails for the legitimate relayer.
