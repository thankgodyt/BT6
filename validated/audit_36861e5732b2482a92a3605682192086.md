### Title
No Minimum Refund-Amount Dust Check Enables Permanently Stuck Deposit UTXOs - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The refund system accepts a caller-supplied `gas_fee` with no lower bound and validates the resulting refund amount only against zero. When the computed `refund_amount = deposit_amount − gas_fee` falls below Bitcoin's per-output dust threshold, the signed refund transaction is unrelayable by any Bitcoin node. Because `execute_refund` simultaneously marks the deposit UTXO as `verified_deposit_utxo` and removes it from the available UTXO set, the deposit is permanently locked with no on-chain or contract-level recovery path.

### Finding Description

`internal_request_refund` accepts an `Option<u128>` `gas_fee` from the caller. In `request_refund_callback`, the resolved fee is validated with a single guard:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 549-553
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

No minimum gas-fee floor and no dust-threshold floor on the resulting refund amount are enforced here.

Later, `refund_execution_inputs` computes the refund amount and checks only:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 280-284
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

`> 0` is the only guard. There is no check that `refund_amount >= dust_threshold` (≈ 294 sat for P2WPKH, ≈ 546 sat for P2PKH).

`build_refund_output` then constructs a `TxOut` with the raw `refund_amount` value and no dust validation:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 301-307
TxOut {
    value: Amount::from_sat(
        u64::try_from(refund_amount)
            .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
    ),
    script_pubkey: refund_script_pubkey,
}
```

`finalize_refund_with_psbt` then:
1. Removes the UTXO from the available set (via `generate_vutxos` → `remove_vutxo_by_psbt`).
2. Inserts the UTXO key into `verified_deposit_utxo`, permanently blocking any future `verify_deposit` call for that UTXO.
3. Creates a `BTCPendingInfo` in `PendingInfoStage::PendingSign`.

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 377-380
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
```

If the resulting Bitcoin transaction carries a sub-dust output, every Bitcoin node rejects it as non-standard. The transaction can never confirm, `verify_refund_finalize` can never succeed, and the UTXO is permanently irrecoverable.

### Impact Explanation

A deposit UTXO whose refund transaction carries a dust output is permanently locked:
- It cannot be minted (already below `min_deposit_amount` or the refund path was taken).
- It cannot be re-deposited (`verified_deposit_utxo` blocks `verify_deposit`).
- It cannot be broadcast on Bitcoin (dust relay policy).
- The `BTCPendingInfo` entry persists in `PendingInfoStage::PendingSign` indefinitely.

The operator can call `internal_reject_refund` to remove the `RefundRequest` and then `internal_remove_refund_pending_tx_id` to clean up the pending info, but the UTXO key remains in `verified_deposit_utxo` with no removal path, so the on-chain BTC is permanently unspendable by the bridge. This matches the **Low** allowed impact: publicly reachable stuck-state fault in a production bridge path without direct theft of other users' funds.

### Likelihood Explanation

Any user who sends a small BTC deposit (e.g., 300 sat, below `min_deposit_amount`) to the bridge address can trigger this path. The refund API is publicly callable. The attacker passes `gas_fee = Some(1)`, making `refund_amount = deposit_amount − 1`. For a 295-sat deposit this yields a 294-sat P2WPKH output, which is exactly at the dust boundary and will be rejected by Bitcoin nodes. No privileged role is required; the only prerequisite is a confirmed on-chain deposit.

### Recommendation

Add a dust-threshold check in `request_refund_callback` (or `refund_execution_inputs`) before storing or executing the refund request:

```rust
// After computing resolved_gas_fee and refund_amount:
let min_refund_amount: u128 = config.min_change_amount; // or a dedicated dust_threshold config field
require!(
    refund_amount >= min_refund_amount,
    "Refund amount after gas fee is below dust threshold"
);
```

Alternatively, enforce a minimum gas-fee floor equal to `config.min_btc_gas_fee` even for caller-supplied fees, and reject any refund request where `amount − min_btc_gas_fee < dust_threshold`.

### Proof of Concept

1. Attacker sends 300 satoshis to the bridge-derived deposit address on Bitcoin mainnet.
2. The deposit is confirmed; `min_deposit_amount` is, say, 1 000 sat, so no nBTC is minted.
3. Attacker calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee = Some(1))`.
4. `request_refund_callback` resolves `resolved_gas_fee = 1`, passes `1 < 300` ✓, stores `RefundRequest { amount: 300, gas_fee: 1 }`.
5. Attacker (or anyone) calls `execute_refund` after the timelock.
6. `refund_execution_inputs` computes `refund_amount = 300 − 1 = 299`, passes `299 > 0` ✓.
7. `build_refund_output` creates a `TxOut { value: 299 sat, script_pubkey: P2WPKH }`.
8. `finalize_refund_with_psbt` marks the UTXO as `verified_deposit_utxo` and creates a `BTCPendingInfo`.
9. MPC signs the PSBT successfully (no on-chain validation of dust).
10. Relayer attempts to broadcast: every Bitcoin node rejects the transaction (`dust` policy, P2WPKH minimum ≈ 294 sat; 299 sat is marginal and chain-dependent, or use 200 sat for a cleaner example).
11. The 300-sat UTXO is permanently locked: not in the available UTXO set, blocked from `verify_deposit`, and the refund transaction will never confirm. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
