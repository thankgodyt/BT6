### Title
Unconditional `validatePerasCert` Acceptance Bypasses All Peras Certificate Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance — the only instance in the codebase — implements `validatePerasCert` as an unconditional `Right`, accepting every inbound Peras certificate without performing any cryptographic or structural validation. An unprivileged peer can send a crafted `PerasCert` pointing to any block, and the node will accept it as valid, allowing the attacker to inject forged certificates that boost adversarial blocks in Peras-weighted chain selection.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the sole `BlockSupportsPeras` instance is declared as a universal catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its `validatePerasCert` method unconditionally returns `Right`:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This is not a dead code path. `validatePerasCert` is called from the production network-facing object diffusion handler in `Ouroboros.Consensus.MiniProtocol.ObjectDiffusion.ObjectPool.PerasCert`, which processes certificates received from remote peers over the Peras certificate mini-protocol. [2](#0-1) 

The analogous `validatePerasVote` has a secondary weakness: the `PerasVote` data type carries no cryptographic signature field, so the only check performed is a stake-distribution lookup by `PerasVoterId`. Any peer that knows a valid voter ID (which is a public `KeyHash StakePool`, derivable from on-chain data) can forge votes for that voter without possessing the corresponding private key. [3](#0-2) 

The production vote-processing path in `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote` for every inbound vote, meaning forged votes pass validation and enter the `PerasVoteDB`. [4](#0-3) 

---

### Impact Explanation

Peras certificates carry a `PerasWeight` boost (default `15`) applied to the boosted block during chain selection. A `ValidatedPerasCert` accepted by `validatePerasCert` is stored and used to weight chain selection in favour of `pcCertBoostedBlock`. [5](#0-4) [6](#0-5) 

Because `validatePerasCert` never rejects any certificate, an attacker can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to an adversarial (minority or invalid) block.
2. Deliver it to a target node via the Peras certificate object-diffusion mini-protocol.
3. The node accepts it unconditionally and applies the weight boost to the adversarial block.
4. Chain selection may then prefer the adversarial chain over the honest chain.

This is a **Critical** bypass of Peras certificate validation that enables unauthorized certificate acceptance and can cause a node to select a non-canonical chain, violating consensus safety.

---

### Likelihood Explanation

The Peras certificate mini-protocol is a public, unauthenticated peer-to-peer channel. Any node that connects as a peer can submit arbitrary `PerasCert` objects. No stake, key material, or privileged access is required. The attacker only needs to know the wire format of `PerasCert` (which is CBOR-serialised and fully specified in the codebase). [7](#0-6) 

The Peras protocol is under active development and the object-diffusion infrastructure is wired into the production `ChainDB` path (`makePerasVotePoolWriterFromChainDB`), making this reachable in any deployment that enables Peras.

---

### Recommendation

1. **`validatePerasCert`**: Implement real certificate validation before the Peras mini-protocol is enabled in any production or testnet deployment. At minimum, verify that the certificate's aggregate BLS signature (or equivalent) over the set of votes is valid against the claimed voter public keys and the boosted block point. Until a concrete cryptographic scheme is finalised, the stub must not be reachable from the network layer.

2. **`validatePerasVote`**: Add a cryptographic signature field to `PerasVote` and verify it in `validatePerasVote`. The current structure allows any peer to impersonate any registered stake pool voter.

3. **Guard the network entry point**: Until validation is complete, the Peras certificate and vote object-diffusion handlers should be disabled or gated behind a feature flag so that the stub implementations are never reachable from untrusted peers. [8](#0-7) 

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to the target node as a peer over the Peras certificate object-diffusion mini-protocol.
2. Construct a `PerasCert` value:
   ```
   PerasCert
     { pcCertRound = <current round>
     , pcCertBoostedBlock = <point of an adversarial/minority block>
     }
   ```
   Serialise it as CBOR per the `Serialise (PerasCert blk)` instance.
3. Send it to the target node.
4. The node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = 15, ...}` unconditionally.
5. The certificate is stored. Chain selection now applies a weight of `15` to the adversarial block.
6. Observe via the node's chain selection trace that the adversarial block is preferred over the honest tip. [9](#0-8) [6](#0-5)
