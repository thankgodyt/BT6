### Title
Attached NEAR Deposit Permanently Frozen When `sign_btc_transaction` Takes Early-Exit Path - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary

`sign_btc_transaction` is `#[payable]` and forwards `env::attached_deposit()` to the MPC chain-signatures contract to cover signing fees. However, when the function detects that the original transaction for an RBF pending entry no longer exists, it returns early via `PromiseOrValue::Value(true)` without forwarding or refunding the attached deposit. The NEAR tokens are permanently frozen on the bridge contract.

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` (lines 19–43) is marked `#[payable]`. The normal execution path calls `self.internal_sign_btc_transaction(...)`, which in turn calls `self.sign_promise(...)` in `contracts/satoshi-bridge/src/chain_signature.rs` (line 66), forwarding the full `env::attached_deposit()` to the chain-signatures MPC contract:

```rust
// chain_signature.rs line 62-68
pub fn sign_promise(&self, request: SignRequest) -> Promise {
    let config = self.internal_config();
    ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
        .with_static_gas(GAS_FOR_SIGN_CALL)
        .with_attached_deposit(env::attached_deposit())  // deposit forwarded here
        .sign(request)
}
```

But there is an early-exit branch in `sign_btc_transaction` (lines 29–39):

```rust
if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
    if !self.check_btc_pending_info_exists(original_tx_id) {
        require!(
            self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                .btc_pending_sign_ids
                .remove(&btc_pending_sign_id),
            "Internal error"
        );
        self.internal_remove_btc_pending_info(&btc_pending_sign_id);
        return PromiseOrValue::Value(true);  // ← attached deposit NOT forwarded, NOT refunded
    }
}
```

This branch fires when the pending info is an RBF replacement transaction (has an `original_tx_id`) but the original transaction no longer exists in storage (already finalized or cleaned up). In this case the function returns immediately, the attached deposit is neither forwarded to the MPC contract nor returned to the caller, and it accumulates permanently on the bridge contract balance.

### Impact Explanation

Any NEAR tokens attached by the caller to cover MPC signing fees are permanently locked on the `satoshi-bridge` contract whenever the early-exit path is taken. There is no mechanism in the contract to recover or redistribute these frozen funds. Over time, repeated calls in this state cause cumulative loss of caller NEAR.

This matches: **Medium — harmful smart-contract behavior without direct funds theft; stuck bridge state / permanent locking of user funds.**

### Likelihood Explanation

The condition is reachable by any unprivileged NEAR account. It triggers when:
1. An RBF replacement pending-sign entry exists (created by `withdraw_rbf` or `active_utxo_management_rbf`).
2. The original transaction is finalized (verified on-chain) and its `BTCPendingInfo` is removed, while the RBF entry is still in the pending-sign set.
3. The caller invokes `sign_btc_transaction` on the RBF entry with an attached deposit.

This is a realistic race condition during normal bridge operation: a user or relayer may attempt to sign an RBF transaction after the original has already been confirmed, attaching NEAR for the MPC fee. The bridge gives no indication that the deposit will not be used.

### Recommendation

In the early-exit branch, refund the attached deposit to the caller before returning:

```rust
if !self.check_btc_pending_info_exists(original_tx_id) {
    // ... cleanup ...
    let deposit = env::attached_deposit();
    if deposit.as_yoctonear() > 0 {
        Promise::new(env::predecessor_account_id()).transfer(deposit).detach();
    }
    return PromiseOrValue::Value(true);
}
```

### Proof of Concept

1. User initiates a withdrawal; bridge creates `BTCPendingInfo` with id `"orig_tx"`.
2. User calls `withdraw_rbf`, creating a replacement `BTCPendingInfo` with `original_tx_id = "orig_tx"`.
3. Relayer calls `verify_withdraw_v2` for `"orig_tx"` — it is confirmed on-chain, `BTCPendingInfo` for `"orig_tx"` is removed.
4. User (or anyone) calls `sign_btc_transaction("rbf_tx", 0, 0)` with `1 NEAR` attached to cover MPC fees.
5. `get_original_tx_id()` returns `Some("orig_tx")`, `check_btc_pending_info_exists("orig_tx")` returns `false`.
6. The early-exit branch fires: `BTCPendingInfo` for `"rbf_tx"` is removed, `PromiseOrValue::Value(true)` is returned.
7. The `1 NEAR` attached deposit is neither forwarded to chain-signatures nor returned — it is permanently frozen on the `satoshi-bridge` contract. [1](#0-0) [2](#0-1) [3](#0-2)
