### Title
LSM UTxO Table Loaded Without Consensus-Layer Integrity Check, and Checksum Verified After Table Handle Is Created — (File: `ouroboros-consensus/src/ouroboros-consensus-lsm/Ouroboros/Consensus/Storage/LedgerDB/V2/LSM.hs`)

---

### Summary

In the LSM backend's `loadSnapshot`, the `snapshotChecksum` stored in the snapshot `meta` file covers only the `state` file (the CBOR-encoded `ExtLedgerState`). The LSM UTxO table data is opened via `LSM.openTableFromSnapshot` and a live handle is created **before** the checksum comparison is even executed. An on-disk snapshot whose `state` file is intact but whose LSM table data has been silently corrupted or deliberately replaced will pass the only integrity gate and be used as the node's authoritative UTxO set.

---

### Finding Description

**Root cause — checksum covers only `state`, not the LSM table**

In `InMemory.hs` `implTakeSnapshot`, the metadata checksum is the concatenated CRC of both the `state` file and the `tables` file:

```haskell
crc1 <- writeExtLedgerState shfs ... (snapshotToStatePath ds) $ state st
crc2 <- takeHandleSnapshot (StateRef.tables st) (state st) $ snapshotToDirName ds
writeSnapshotMetadata shfs ds $
  SnapshotMetadata { snapshotChecksum = maybe crc1 (crcOfConcat crc1) crc2, ... }
``` [1](#0-0) 

In the LSM backend's `loadSnapshot`, the only CRC that is ever compared is `checksumAsRead`, which is the CRC produced by `readExtLedgerState` — i.e., the CRC of the `state` file alone:

```haskell
(extLedgerSt, checksumAsRead) <-
    withExceptT (InitFailureRead . ReadSnapshotFailed) $
      readExtLedgerState fs (decodeDiskExtLedgerState ccfg) decode (snapshotToStatePath ds)
``` [2](#0-1) 

No CRC of the LSM table data is ever computed or compared. The final check is:

```haskell
Monad.when
    (checksumAsRead /= snapshotChecksum snapshotMeta)
    $ throwE $ InitFailureRead ReadSnapshotDataCorruption
``` [3](#0-2) 

This compares the `state`-file CRC against the stored checksum. Because the stored checksum was also computed from only the `state` file at write time, the LSM table data is entirely outside the integrity envelope.

**Root cause — table handle created before the checksum check**

`LSM.openTableFromSnapshot` and `newLSMLedgerTablesHandle` are called before the checksum comparison:

```haskell
values <-
    lift $ ... LSM.openTableFromSnapshot session (fromString $ snapshotToDirName ds) ...
h <- lift $ newLSMLedgerTablesHandle tracer exportSnapshot msz values
Monad.when (checksumAsRead /= snapshotChecksum snapshotMeta) $ throwE ...
pure (StateRef extLedgerSt h, pt)
``` [4](#0-3) 

Even if the `state`-file CRC check were to fail, the LSM session has already been opened. More critically, if the `state` file is intact (matching CRC) but the LSM table files have been tampered with, the function returns `Right (StateRef extLedgerSt h, pt)` with the corrupted table handle.

**Contrast with ImmutableDB**

The ImmutableDB explicitly documents and implements CRC32 verification of every block before use, including a fallback to cryptographic hash verification when the CRC is unavailable: [5](#0-4) 

The LedgerDB snapshot design follows the same principle for the InMemory backend. The LSM backend deviates from this established pattern.

**`SnapshotMetadata` structure**

The `snapshotChecksum` field is a single `CRC` value: [6](#0-5) 

For the InMemory backend this is `crcOfConcat crc_state crc_tables`; for the LSM backend it is only `crc_state`, so the field name is misleading — it does not represent the checksum of the full snapshot.

---

### Impact Explanation

When a node restarts and loads an LSM snapshot, it replays only the blocks that follow the snapshot tip. The UTxO set in the LSM table is taken as ground truth without any consensus-layer integrity verification. A snapshot whose `state` file is authentic but whose LSM table has been silently corrupted (hardware bit-flip, partial write, or deliberate replacement) will be accepted and used as the starting ledger state. All subsequent block validation, transaction acceptance, and chain-selection decisions are made against this wrong UTxO set. This can cause the node to accept double-spends, reject valid transactions, or diverge permanently from the canonical chain — a durable use of the wrong ledger state matching the "High" impact category: *LedgerDB/snapshot/LSM corruption bug that causes durable use of the wrong ledger state without operator fault*.

---

### Likelihood Explanation

The entry path is a crafted or silently corrupted LSM snapshot placed in the node's `ledger/` directory. This does not require network-level access; it requires the ability to write to the snapshot directory (the same privilege level as the node process itself, reachable by a co-located malicious process, a compromised dependency, or hardware-level silent corruption). The `initialize` function in `LedgerDB/API.hs` iterates snapshots newest-first and uses the first one that passes `initFromSnapshot`; a crafted snapshot with a valid `state` file and a tampered LSM table will succeed at line 632 and be used immediately. [7](#0-6) 

---

### Recommendation

1. **Cover the LSM table in the snapshot checksum.** At snapshot-write time, compute a CRC (or cryptographic hash) over the LSM table data and include it in `snapshotChecksum` via `crcOfConcat`, mirroring the InMemory backend's approach.

2. **Verify integrity before opening the table.** Move `LSM.openTableFromSnapshot` to execute only after the `state`-file checksum has been verified, so that a corrupted `state` file aborts the load before any LSM I/O is performed. This mirrors the recommendation in the original report: perform the integrity check before the expensive/stateful operation.

3. **Align the LSM `takeSnapshot` with the InMemory pattern** so that `snapshotChecksum` always represents the integrity of the complete snapshot, not just one component.

---

### Proof of Concept

1. Start a node with the LSM backend and let it write a snapshot to `ledger/<slot>/`.
2. Stop the node.
3. Overwrite one or more LSM run files inside the LSM session directory (e.g., flip bytes in a `.data` file corresponding to a UTxO entry) while leaving `ledger/<slot>/state` and `ledger/<slot>/meta` untouched.
4. Restart the node. `loadSnapshot` will:
   - Read `meta` → `snapshotChecksum` = CRC of the original `state` file. ✓
   - Read `state` → `checksumAsRead` = CRC of the (unmodified) `state` file. ✓
   - Open the tampered LSM table via `LSM.openTableFromSnapshot`. ✓ (no consensus-layer check)
   - Compare `checksumAsRead == snapshotChecksum` → equal. ✓
   - Return `Right (StateRef extLedgerSt h, pt)` with the corrupted UTxO handle.
5. The node replays blocks from the snapshot tip using the corrupted UTxO set as its starting state, silently diverging from the canonical chain.
