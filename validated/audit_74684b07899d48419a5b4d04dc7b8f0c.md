### Title
Peras Quorum Check Compares Unnormalized `PerasVoteStake` Against Relative Threshold in `stakeAboveThreshold` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares a `PerasVoteStake` value (which may carry absolute ledger stake in lovelace) against a relative quorum threshold (e.g., `3/4`). The code itself contains an explicit TODO acknowledging that the two operands must be in the same units, and that normalization is not currently performed. If `PerasVoteStake` values are absolute, any single vote from a voter with positive stake will always exceed the relative threshold, allowing a single network peer to forge a Peras certificate for any block without a real quorum.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The default `perasQuorumStakeThreshold` is `3/4` and `perasQuorumStakeThresholdSafetyMargin` is `2/100`, giving a combined threshold of `0.77` — a relative fraction of total committee stake. [2](#0-1) 

The code's own comment explicitly acknowledges the unit mismatch:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The `PerasVoteStake` assigned to a vote comes from `PerasVoteStakeDistr`, which is populated externally (via `getStakeDistrSTM`) without any normalization step in the production code path: [4](#0-3) 

The `validatePerasVote` implementation simply looks up the stake from the distribution and attaches it to the vote without normalizing it: [5](#0-4) 

The `EveryoneVotes` committee's `implEligiblePartyVoteWeight` returns the raw `LedgerStake` (absolute ledger value) as the vote weight: [6](#0-5) 

Similarly, the `WFALS` persistent member path returns the raw ledger stake directly: [7](#0-6) 

If these absolute values (e.g., lovelace amounts >> 1) are stored in `PerasVoteStakeDistr` and then compared against the relative threshold `0.77`, the comparison is always `True` for any voter with positive stake. The quorum check becomes a no-op.

---

### Impact Explanation

**Critical.** Bypass of Peras voting/certificate quorum checks. If `PerasVoteStake` carries absolute ledger stake (any positive lovelace amount >> 0.77), then `stakeAboveThreshold` returns `True` for every single vote. This means:

- A single network-received vote from any voter with positive stake immediately triggers `votesReachQuorum`, causing `updateCandidateVoteState` to forge a Peras certificate.
- The certificate is then accepted by the ChainDB and used to boost the target block's chain weight by `perasWeight` (default: 15 blocks).
- An unprivileged peer can forge a Peras certificate for any block of their choice, causing honest nodes to prefer an adversarially chosen chain over the canonical one. [8](#0-7) 

---

### Likelihood Explanation

**High.** The unit mismatch is self-documented in the production source as an unresolved TODO. The `PerasVoteStakeDistr` is populated from ledger stake distributions, which naturally carry absolute lovelace values. No normalization step exists in the current code between the ledger stake and the quorum comparison. Any peer that can send a valid `PerasVote` (i.e., one whose voter ID appears in the stake distribution) triggers the condition.

---

### Recommendation

Normalize `PerasVoteStake` to a relative fraction of total committee stake before calling `stakeAboveThreshold`. Concretely, either:

1. Divide each voter's absolute stake by the total committee stake when populating `PerasVoteStakeDistr`, or
2. Change `stakeAboveThreshold` to accept the total stake distribution and perform normalization internally before comparing against the relative threshold.

The `WFALS` non-persistent member path already demonstrates the correct pattern — dividing individual stake by `nonPersistentStake` before producing a `VoteWeight`: [9](#0-8) 

The same normalization must be applied uniformly before any quorum comparison.

---

### Proof of Concept

With `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100` (defaults from `mkPerasParams`), the effective threshold is `0.77`.

If a voter's absolute ledger stake is stored as, say, `1_000_000` lovelace (1 ADA), then:

```
stake = 1000000
quorumThreshold + safetyMargin = 0.75 + 0.02 = 0.77
1000000 >= 0.77  →  True
```

A single vote from this voter causes `votesReachQuorum` to return `Just votesWithQuorum`, `updateCandidateVoteState` to call `forgePerasCert`, and the resulting certificate to be stored and applied as a chain-weight boost — all without any real quorum of honest stake. [10](#0-9) [11](#0-10)

updateCandidateVoteState cfg vote oldState =
  let
    newVoteTally = updateTargetVoteTally vote (ptvsVoteTally oldState)
    voteList = forgetArrivalTime <$> Map.elems (ptvtVotes newVoteTally)
   in
    case votesReachQuorum cfg voteList of
      Just votesWithQuorum -> do
        cert <- forgePerasCert cfg votesWithQuorum
        pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
      Nothing -> do
        pure $ RemainedCandidate (PerasTargetVoteCandidate newVoteTally)
