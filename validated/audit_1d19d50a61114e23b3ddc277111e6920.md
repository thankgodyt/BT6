Audit Report

## Title
`#[trusted_relayer]` Gate on `claim_fee` Permanently Freezes Earned Fee Tokens When Relayer Resigns or Is Revoked — (`near/omni-bridge/src/lib.rs`)

## Summary

`claim_fee` is gated by `#[trusted_relayer]`, requiring the caller to be a currently-active trusted relayer. Simultaneously, `claim_fee_callback` enforces that only the specific `fee_recipient` embedded in the on-chain proof can collect the fee. If a relayer resigns or is revoked after executing a fast transfer to a non-NEAR chain but before the destination-chain proof is submitted, neither the original relayer nor any substitute can ever call `claim_fee` for that transfer. The fee tokens and the `pending_transfers` entry are permanently frozen in the bridge contract with no permissionless recovery path.

## Finding Description

Two independent restrictions in `claim_fee` and its callback create an irrecoverable dead-end:

**Restriction 1** — `claim_fee` at `near/omni-bridge/src/lib.rs:1054-1064` carries `#[trusted_relayer]`, which rejects any caller not presently in the active-relayer set:

```rust
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise {
```

**Restriction 2** — `claim_fee_callback` at `near/omni-bridge/src/lib.rs:1083-1086` enforces that the caller must equal the `fee_recipient` cryptographically bound in the destination-chain event proof:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

These two restrictions are mutually exclusive once a relayer loses trusted status: the original relayer (who is the `fee_recipient`) fails Restriction 1; any currently-trusted relayer fails Restriction 2.

The fee is created and locked when `fast_fin_transfer_to_other_chain` (`lib.rs:914-973`) stores a second-leg `TransferMessage` in `pending_transfers` with `origin_transfer_id = Some(fast_transfer.transfer_id.clone())` and `amount` including the fee portion. The fee is only released when `claim_fee_callback` calls `send_fee_internal` (`lib.rs:1133`). There is no alternative permissionless path to release it.

An additional guard at `lib.rs:1107` (`fast_transfer_status.finalised`) means the fast transfer's first leg must be confirmed before `claim_fee` can succeed, but this does not close the vulnerability — it only narrows the window to: first leg finalized → relayer resigns → destination-chain proof becomes available.

The integration test at `near/omni-tests/src/relayer_staking.rs:336-368` confirms that `resign_trusted_relayer` immediately removes trusted status and returns stake, with `is_trusted_relayer` returning `false` immediately after.

## Impact Explanation

Fee tokens earned by a relayer for executing a fast transfer to a non-NEAR destination chain are permanently frozen in the bridge contract. The `pending_transfers` entry for the second leg is never removed. The only escape is DAO intervention via `transfer_token_as_dao`, which is an out-of-band privileged action and does not restore the fee to the rightful relayer. This constitutes **fee mis-accounting and permanent freezing of bridged funds**, matching the allowed Critical impact scope.

## Likelihood Explanation

Low. The window requires a relayer to resign or be revoked after the fast transfer's first leg is finalized but before the destination-chain proof is submitted and `claim_fee` is called. Fast transfers are time-sensitive, but the window is realistic for chains with longer finality (e.g., Ethereum mainnet ~12 minutes) or if the DAO revokes a relayer for misconduct while that relayer has pending fee claims. The scenario is not dependent on any attacker — it can be triggered by the relayer's own voluntary resignation.

## Recommendation

Remove the `#[trusted_relayer]` gate from `claim_fee`. The `fee_recipient == predecessor_account_id` check in `claim_fee_callback` already ensures only the correct party can collect the fee; the additional trusted-relayer check adds no security benefit and creates the described dead-end. The fee was earned at the time the fast transfer was executed, and the right to claim it should not depend on the relayer's current status.

## Proof of Concept

1. Relayer A applies and becomes a trusted relayer (stake deposited, waiting period elapsed).
2. Relayer A calls `ft_transfer_call` on the token contract with a `FastFinTransferMsg` targeting a Base-chain recipient. `fast_fin_transfer_to_other_chain` burns the principal, stores a second-leg `TransferMessage` in `pending_transfers` with `origin_transfer_id = Some(fast_transfer_id)`, and records `FastTransferStatus { relayer: RelayerA, finalised: false }`.
3. The first leg (origin chain → NEAR) is finalized via `fin_transfer`, setting `fast_transfer_status.finalised = true`.
4. A regular relayer calls `sign_transfer` on the second-leg transfer. Because `fee > 0`, the `TransferMessage` remains in `pending_transfers` after signing.
5. Relayer A calls `resign_trusted_relayer`. Stake is returned; Relayer A is removed from the trusted set (`is_trusted_relayer` returns `false`).
6. The signed payload is submitted to Base. Base emits `FinTransfer` with `fee_recipient = RelayerA`.
7. Relayer A attempts `claim_fee` with the Base proof → **panics at `#[trusted_relayer]`** because Relayer A is no longer active (`lib.rs:1055`).
8. Any other trusted relayer attempts `claim_fee` with the same proof → **panics at `OnlyFeeRecipientCanClaim`** because `fee_recipient (RelayerA) != predecessor_account_id` (`lib.rs:1083-1086`).
9. The fee tokens and the `pending_transfers` entry are permanently stuck. No permissionless path exists to recover them.
