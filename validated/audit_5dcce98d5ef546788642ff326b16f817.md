### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Inject Arbitrary Weight Boosts and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function unconditionally accepts every inbound Peras certificate without performing any cryptographic proof, committee-membership, or round-number check. An unprivileged peer reachable via the object-diffusion mini-protocol can send crafted certificates that boost arbitrary blocks, causing honest nodes to apply unearned weight boosts during chain selection and potentially switch to adversarial forks.

---

### Finding Description

**Root cause — stub validation always returns `Right`**

`validatePerasCert` in `BlockSupportsPeras.hs` is a placeholder that accepts every certificate unconditionally:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function is wired directly into the production inbound-certificate path in `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**Processing path — `processCerts` adds every cert that passes the stub**

`processCerts` partitions the batch into valid/invalid using the stub validator. Because the stub always returns `Right`, the invalid branch is never taken and every cert in the batch is forwarded to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Secondary issue — `alreadyInDb` snapshot taken outside the STM transaction**

The deduplication snapshot is fetched atomically at the start of `processCerts`, but the actual insertion happens later, outside that transaction:

```haskell
alreadyInDb <- atomically alreadyInDbSTM
let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
``` [4](#0-3) 

A peer can therefore send a single batch containing two equivocating certificates for the same round (boosting different blocks). Both pass the stale filter, both pass the stub validator, and `mapM_` attempts to insert both. `implAddCert` rejects the second at the STM level, so the **first cert in the batch wins**. Because the attacker controls the ordering of objects in the batch they send, they choose which equivocating certificate is accepted. [5](#0-4) 

**Chain-selection consequence**

Once a certificate is stored, `chainSelSync` triggers `chainSelectionForBlock` for the boosted block. The weight snapshot used during candidate comparison is derived directly from the `PerasCertDB`, so the injected boost is immediately visible to chain selection: [6](#0-5) 

The weight boost is summed over all boosted points on a candidate fragment: [7](#0-6)

### Impact Explanation

An unprivileged peer can:

1. Craft a `PerasCert` for any round, naming any block as the boosted block (e.g., a block on an adversarial fork).
2. Send it via the object-diffusion mini-protocol; `validatePerasCert` returns `Right` unconditionally.
3. The certificate is stored in `PerasCertDB` and its boost is added to the weight snapshot.
4. Chain selection re-evaluates the boosted block's candidate fragment with the injected weight.
5. If the adversarial fragment's total weight now exceeds the honest chain's weight, the node switches forks.

This is a **bypass of Peras certificate verification** enabling unauthorized certificate acceptance and a **chain-selection error** that lets an unprivileged peer make an honest node prefer a non-canonical chain — matching the Critical/High impact tiers in the allowed scope.

---

### Likelihood Explanation

**High.** Any peer that can establish an object-diffusion connection (i.e., any network peer) can exploit this. No stake, no keys, and no special privileges are required. The attack is deterministic and requires only a single crafted message.

---

### Recommendation

1. **Implement real validation in `validatePerasCert`**: verify the certificate's cryptographic aggregate signature, confirm the signers are eligible committee members for the claimed round, check the boosted block point is within the valid range, and enforce one certificate per round per boosted block.
2. **Move the `alreadyInDb` snapshot inside the STM transaction** in `processCerts` (or rely solely on `implAddCert`'s STM-level dedup) to close the TOCTOU window that allows equivocating certificates in the same batch to race for acceptance.

---

### Proof of Concept

```
1. Attacker connects to an honest node via the object-diffusion mini-protocol.
2. Attacker constructs PerasCert { pcCertRound = R, pcCertBoostedBlock = B_adv }
   where B_adv is a block on an adversarial fork that the attacker controls.
3. Attacker sends the cert in a batch to the node.
4. processCerts calls validatePerasCert — returns Right (no checks performed).
5. addCert stores the cert; PerasCertDB now contains a boost for B_adv.
6. chainSelSync triggers chainSelectionForBlock for B_adv.
7. weightBoostOfFragment adds the injected boost to the adversarial fragment's weight.
8. preferAnchoredCandidate now prefers the adversarial fragment → node switches chain.
```

**Analog mapping to the external report:**
- TON Observer: iterates tx hashes, stores the last successfully processed result, allowing a malicious observer to append a crafted hash that overrides the canonical result.
- Ouroboros Consensus: iterates inbound certificates, accepts every cert because `validatePerasCert` is a stub, allowing a malicious peer to inject a crafted certificate that overrides the honest chain's weight advantage — the same "validation bypass leading to state manipulation" root cause, applied to Peras certificate/chain-selection logic instead of outbound transaction tracking.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
