### Title
Front-Running `request_refund` Redirects Deposited BTC to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account and accepts a caller-supplied `refund_address` with no ownership check. Because the first successful call for a given UTXO wins and all subsequent calls are blocked, an attacker who observes a pending BTC deposit can front-run the legitimate user's refund request and permanently redirect the BTC to an attacker-controlled address.

---

### Finding Description

**Vulnerability class:** First-registration wins / deposit-address pre-emption (direct analog of the Swell report).

**Entry point — `request_refund` is fully public:**

`request_refund` in `api/bridge.rs` carries no `#[trusted_relayer]` attribute on the function itself and no role guard:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← caller-supplied, no ownership check
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

**`refund_address` is only validated when `deposit_msg.refund_address` is pre-set:**

In `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` — the common case for users who did not pre-commit a refund address — any caller may supply any BTC address.

**First-registration wins — duplicate requests are blocked:**

Inside `request_refund_callback`, after the Light Client proof is verified, the contract stores the request and then hard-blocks any second request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

The stored `refund_address` is whatever the first caller supplied:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker's address, locked in permanently
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [4](#0-3) 

**`execute_refund` is also public — attacker completes the theft unilaterally:**

```rust

    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,

``` [5](#0-4) 

No role check; any account can call it once the timelock elapses.

**The legitimate user cannot self-help:**

`reject_refund` is restricted to DAO/Operator, or to the case where the UTXO was already finalized via `verify_deposit`. The depositor has no independent path to cancel the fraudulent request:

```rust
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
``` [6](#0-5) 

---

### Impact Explanation

After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`. The bridge's MPC pipeline builds and signs a Bitcoin transaction paying the attacker's address. The depositor's BTC is permanently transferred to the attacker. This is a **critical, direct theft of user funds** with no on-chain recovery path for the victim.

---

### Likelihood Explanation

The `deposit_msg` is publicly observable: it is emitted as a NEAR event by `get_user_deposit_address` and is also visible as a call parameter in any relayer `verify_deposit_v2` transaction. An attacker monitoring NEAR events or the BTC mempool can identify unfinalized deposits and race to call `request_refund` before the legitimate user. The only cost is the NEAR storage deposit required by `required_balance_for_request_refund`, which is negligible relative to the BTC value at stake. The `unsafe_refund_timelock_sec` gives DAO/Operator a window to reject, but this is an off-chain, manual, non-guaranteed mitigation. [7](#0-6) 

---

### Recommendation

1. **Bind `refund_address` to the depositor.** Require that `request_refund` is called by the `deposit_msg.recipient_id` (the NEAR account that was to receive nBTC), or require `deposit_msg.refund_address` to be non-null and pre-committed at deposit-address derivation time.
2. **Alternatively, restrict `request_refund` to trusted relayers** (add `#[trusted_relayer]`) so only whitelisted accounts can submit refund requests, eliminating the front-running surface entirely.
3. **Allow the depositor to self-reject** a fraudulent refund request by proving ownership of `deposit_msg.recipient_id`.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The `LogDepositAddress` event is emitted publicly with the full `deposit_msg`.
2. Alice sends BTC to the derived address. The relayer has not yet called `verify_deposit_v2` (e.g., waiting for confirmations).
3. Attacker Bob observes the event, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
       deposit_msg = <Alice's deposit_msg>,
       refund_address = <Bob's BTC address>,
       tx_bytes = <Alice's BTC tx>,
       vout = 0,
       proof = <valid Light Client proof>,
       gas_fee = None
   )
   ```
4. `request_refund_callback` verifies the proof, finds no existing refund request, and stores Bob's address as `refund_address`.
5. Alice attempts `request_refund` — it panics: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec`, Bob calls `execute_refund(utxo_storage_key)`. The MPC signs a transaction paying Bob's address.
7. Bob receives Alice's BTC. Alice's funds are permanently lost.
