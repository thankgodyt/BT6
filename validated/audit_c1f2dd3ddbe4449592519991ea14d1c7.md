### Title
Peras Certificate Verification Bypass via Unconditional `validatePerasCert` Stub — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally accepts every inbound `PerasCert` without verifying quorum, cryptographic signatures, round validity, or any other security property. An unprivileged peer can craft and submit a certificate for any block, causing the receiving node to apply a Peras chain-weight boost to that block and potentially switch to a non-canonical chain.

---

### Finding Description

In `SupportsPeras.hs`, the universal `BlockSupportsPeras` instance (lines 320–389) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into both production inbound-certificate processing paths:

- `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`: [2](#0-1) 

- `makePerasCertPoolWriterFromCertDB` does the same: [3](#0-2) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, timestamps and adds them to the database via `addCert` (which ultimately calls `addPerasCertAsync chainDB`): [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the "validation" gate is entirely absent. No quorum check, no aggregate-signature verification, no round-number bounds check, and no check that the boosted block actually exists on any chain is performed.

The analog to the external report is direct: in HatsSignerGateBase, two checks exist but are jointly insufficient because `reconcileSignerCount()` can reduce the safe's threshold below `minThreshold`, letting both checks pass with fewer signers than required. Here, the analogous check (`validatePerasCert`) is not merely insufficient — it is completely absent, so the quorum requirement is bypassed unconditionally for every inbound certificate.

---

### Impact Explanation

**Critical — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

A `ValidatedPerasCert` produced by the stub carries `vpcCertBoost = perasWeight params`, which is `PerasWeight 15` under `mkPerasParams`: [5](#0-4) 

Once accepted into the ChainDB, this boost is applied during chain selection via `getPerasWeightSnapshot`. A crafted certificate for a block on a minority fork inflates that fork's weight by 15 units, potentially causing an honest node to switch away from the canonical chain. Because the boost is durable (stored in the ChainDB), the effect persists across restarts.

---

### Likelihood Explanation

**High.** Any peer connected via the Peras certificate miniprotocol can send a crafted `PerasCert`. No stake, no keys, and no special privileges are required. The `processCerts` function is the sole gate between the network and the ChainDB for inbound certificates, and it delegates all security decisions to `validatePerasCert`, which is a no-op.

---

### Recommendation

Implement real certificate validation inside `validatePerasCert` (tracked in issue #120). At minimum, the implementation must verify:

1. **Quorum**: the aggregate vote stake embedded in the certificate meets `stakeAboveThreshold` against the current epoch's stake distribution.
2. **Aggregate signature**: the BLS aggregate signature over the election identifier and boosted-block hash is cryptographically valid against the claimed voter keys.
3. **Round validity**: the certificate's round number falls within the acceptable window relative to the current tip.
4. **Block existence**: the `pcCertBoostedBlock` point refers to a block that is actually present in the node's chain fragment.

Until this is implemented, the certificate miniprotocol should not be enabled in any deployment where chain-selection integrity is required.

---

### Proof of Concept

1. Establish a peer connection to a target node that has the Peras certificate object-diffusion miniprotocol active.
2. Craft a `PerasCert` with `pcCertRound = <any fresh round>` and `pcCertBoostedBlock = <point of a block on a minority fork>`.
3. Send the certificate via the miniprotocol. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
4. The certificate is timestamped and forwarded to `addPerasCertAsync chainDB`.
5. Chain selection now treats the minority-fork block as carrying 15 additional weight units.
6. If the minority fork's total weight (natural + boost) exceeds the canonical chain's weight, the node switches forks — accepting a non-canonical chain without any honest quorum having voted for it.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of

    ([], validatedCerts) ->
