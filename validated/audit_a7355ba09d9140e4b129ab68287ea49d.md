### Title
Missing Stake Normalization in Peras Quorum Check Enables Unauthorized Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (which is sourced from the absolute ledger stake distribution) directly against a relative quorum threshold (`3/4`) without performing normalization. The code itself acknowledges this with a TODO comment. This is the exact structural analog of the RToken bug: a raw (unscaled) value is compared against a threshold that expects a normalized (scaled) value, bypassing the quorum check.

---

### Finding Description

In `stakeAboveThreshold`, the quorum check compares `unPerasVoteStake voteStake` against `perasQuorumStakeThreshold` (set to `3/4` in `mkPerasParams`) plus a safety margin:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The code carries an explicit TODO acknowledging the unit mismatch:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` is populated by `validatePerasVote`, which calls `lookupPerasVoteStake` — a raw `Map.lookup` that returns whatever absolute ledger stake value is stored in `PerasVoteStakeDistr`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [3](#0-2) 

The companion note on `PerasVoteStake` confirms there is no consensus on how to normalize from absolute ledger stake to relative vote stake:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [4](#0-3) 

The quorum threshold is set to `3/4` (a relative value in `[0,1]`):

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2 / 100)
``` [5](#0-4) 

If `PerasVoteStakeDistr` contains absolute ledger stake (e.g., lovelace values in the millions), then `stake >= 0.77` is trivially true for any voter with positive stake. The `votesReachQuorum` function, which gates certificate forging, calls `stakeAboveThreshold` on the sum of these unnormalized values:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5) 

The same flawed check is used in `updateLoserVoteState` and `updateCandidateVoteState` in the vote aggregation path: [7](#0-6) [8](#0-7) 

---

### Impact Explanation

**Bypass of Peras voting/certificate quorum checks enabling unauthorized certificate acceptance.**

If absolute ledger stake values flow into `PerasVoteStakeDistr` (the expected case given the unresolved normalization TODO), then `stakeAboveThreshold` returns `True` for any voter with positive stake, because any absolute lovelace value (e.g., `1_000_000`) is ≥ `0.77`. A single vote from any committee member immediately satisfies quorum. This allows an attacker to:

1. Send a single crafted `PerasVote` for any target block.
2. `validatePerasVote` assigns the voter's absolute ledger stake as `vpvVoteStake`.
3. `votesReachQuorum` calls `stakeAboveThreshold`, which returns `True` trivially.
4. `forgePerasCert` is called, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` (15 by default).
5. The certificate is accepted into the `PerasVoteDB` and propagated to `ChainDB`.
6. The boosted block gains a weight advantage of 15 in chain selection via `wsvTotalWeight`, causing honest nodes to prefer the adversary's chain. [9](#0-8) 

---

### Likelihood Explanation

**High.** The entry path is a standard node-to-node mini-protocol: any unprivileged peer can submit a `PerasVote` message. The vote is processed by `makePerasVotePoolWriterFromChainDB` (or `makePerasVotePoolWriterFromVoteDB`), which calls `validatePerasVote` with the current `PerasVoteStakeDistr`. The normalization gap is explicitly acknowledged in the production source with a TODO, confirming the missing step is known and unresolved. No key compromise, admin access, or stake majority is required. [10](#0-9) 

---

### Recommendation

`stakeAboveThreshold` must not be called with unnormalized (absolute) stake values. The fix should follow one of two approaches, consistent with the existing TODO:

1. **Normalize before comparison**: Before calling `stakeAboveThreshold`, divide each voter's absolute stake by the total stake of the committee to produce a relative value in `[0,1]`.
2. **Internalize normalization**: Change `stakeAboveThreshold` to accept the total committee stake and perform the division internally, making the unit contract explicit in the type signature.

The `PerasVoteStake` type should be given a distinct newtype for relative vs. absolute stake to make unit mismatches a compile-time error.

---

### Proof of Concept

Assume `mkPerasParams` is used (quorum threshold = `3/4 + 2/100 = 0.77`) and a voter has absolute ledger stake of `1_000_000` lovelace stored in `PerasVoteStakeDistr`.

1. Attacker sends one `PerasVote` for target block `B` in round `R`.
2. `validatePerasVote` returns `Right ValidatedPerasVote { vpvVoteStake = PerasVoteStake (1000000 % 1) }`.
3. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1000000 % 1)`.
4. `stakeAboveThreshold params totalVoteStake` evaluates `1000000 >= 0.77` → `True`.
5. `forgePerasCert` produces a certificate boosting block `B` by weight 15.
6. Any honest node receiving this certificate will add 15 to `B`'s chain weight in `wsvTotalWeight`, preferring `B`'s chain over an equally long unboosted honest chain. [11](#0-10) [12](#0-11)
