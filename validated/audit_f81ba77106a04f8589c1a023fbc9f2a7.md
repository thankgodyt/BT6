### Title
`triggerHardForkDijkstra` Silently Dropped in `protocolInfoCardano`, Permanently Disabling the Conway→Dijkstra Era Transition - (File: `ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

In `protocolInfoCardano`, the `triggerHardForkDijkstra` field is accepted as part of `CardanoHardForkTriggers'` but is silently omitted from the record pattern match. As a result, `partialLedgerConfigConway` is hardcoded with `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`. This permanently prevents the Conway→Dijkstra era transition from ever being signalled by the HFC, regardless of what the caller passes for `triggerHardForkDijkstra`.

---

### Finding Description

In `protocolInfoCardano`, the `CardanoHardForkTriggers'` record is destructured at lines 604–612:

```haskell
cardanoHardForkTriggers =
  CardanoHardForkTriggers'
    { triggerHardForkShelley
    , triggerHardForkAllegra
    , triggerHardForkMary
    , triggerHardForkAlonzo
    , triggerHardForkBabbage
    , triggerHardForkConway
    -- triggerHardForkDijkstra is NOT bound here
    }
``` [1](#0-0) 

The `CardanoHardForkTriggers'` pattern has **seven** fields (Shelley through Dijkstra), but only six are bound. `triggerHardForkDijkstra` is silently discarded. Haskell's record pattern syntax does not warn about omitted fields by default. [2](#0-1) 

Consequently, `partialLedgerConfigConway` is constructed with a hardcoded `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`:

```haskell
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    TriggerHardForkNotDuringThisExecution   -- should be: toTriggerHardFork triggerHardForkDijkstra
``` [3](#0-2) 

Every other era correctly threads its next-era trigger through:

| Era | Trigger used |
|---|---|
| Byron | `toTriggerHardFork triggerHardForkShelley` |
| Shelley | `toTriggerHardFork triggerHardForkAllegra` |
| Allegra | `toTriggerHardFork triggerHardForkMary` |
| Mary | `toTriggerHardFork triggerHardForkAlonzo` |
| Alonzo | `toTriggerHardFork triggerHardForkBabbage` |
| Babbage | `toTriggerHardFork triggerHardForkConway` |
| **Conway** | **`TriggerHardForkNotDuringThisExecution` ← hardcoded wrong value** | [4](#0-3) 

The `TriggerHardForkNotDuringThisExecution` constructor is documented as meaning "the era cannot end within this node process before it restarts with different software and/or configuration." It causes `singleEraTransition` for Conway to always return `Nothing`, so the HFC never advances past Conway. [5](#0-4) 

The callers — including `Cardano.Node.Protocol.Cardano` — do supply a meaningful `triggerHardForkDijkstra` (either `CardanoTriggerHardForkAtDefaultVersion` for protocol version 12, or a test epoch override), but it is entirely ignored. [6](#0-5) 

---

### Impact Explanation

**Classification:** Hard-fork era transition bug that breaks cross-era consensus.

When on-chain Conway governance reaches protocol version 12 (the Dijkstra trigger), the ledger layer will signal the transition. However, because `partialLedgerConfigConway` carries `TriggerHardForkNotDuringThisExecution`, the HFC's `singleEraTransition @Conway` always returns `Nothing`. The node never advances to the Dijkstra era.

Nodes running patched software (with the correct `toTriggerHardFork triggerHardForkDijkstra`) will transition to Dijkstra and begin accepting Dijkstra-era blocks. Nodes running the buggy `protocolInfoCardano` will remain in Conway and reject those blocks as coming from the wrong era. This produces a **permanent chain split** between patched and unpatched nodes — a consensus safety failure.

Additionally, any node-to-client query issued against a buggy node after the transition epoch will return stale Conway-era state, silently misrepresenting the ledger to wallets and explorers.

---

### Likelihood Explanation

The Dijkstra era is fully implemented in this codebase (all block configs, ledger configs, and transition configs for Dijkstra are present). The `triggerHardForkDijkstra` field is wired through `CardanoHardForkTriggers'` and populated by callers. The bug is latent until the Conway→Dijkstra on-chain governance action completes, at which point it becomes immediately exploitable by any peer that sends a valid Dijkstra-era block. No special privileges are required; the trigger is purely on-chain.

---

### Recommendation

Bind `triggerHardForkDijkstra` in the pattern match and use it in `partialLedgerConfigConway`, mirroring every other era:

```haskell
-- In the pattern match, add:
cardanoHardForkTriggers =
  CardanoHardForkTriggers'
    { triggerHardForkShelley
    , triggerHardForkAllegra
    , triggerHardForkMary
    , triggerHardForkAlonzo
    , triggerHardForkBabbage
    , triggerHardForkConway
    , triggerHardForkDijkstra   -- ADD THIS
    }

-- In partialLedgerConfigConway, replace:
    TriggerHardForkNotDuringThisExecution
-- with:
    (toTriggerHardFork triggerHardForkDijkstra)
```

Enable `-Wincomplete-record-updates` or `-Wall` in the Cabal component to catch future omissions of this kind at compile time.

---

### Proof of Concept

1. Configure a private testnet with `npcTestEnableDevelopmentHardForkEras = True` and `npcTestDijkstraHardForkAtEpoch = Just 5`.
2. Start two nodes: one using the current `protocolInfoCardano` (buggy), one with the fix applied.
3. Advance the chain to epoch 5.
4. The fixed node transitions to Dijkstra and begins producing/accepting Dijkstra-era blocks.
5. The buggy node's `singleEraTransition @Conway` returns `Nothing` (because `TriggerHardForkNotDuringThisExecution` is hardcoded), so it remains in Conway and rejects all Dijkstra-era blocks from the fixed node as `HardForkApplyTxErrWrongEra` / wrong-era header errors.
6. The two nodes diverge permanently — the buggy node is on a shorter Conway chain while the fixed node is on the canonical Dijkstra chain. [3](#0-2) [1](#0-0)
