### Title
Attacker-Controlled `refund_address` Redirects BTC Refunds When `DepositMsg.refund_address` Is `None` - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user deposits BTC/ZEC using a `DepositMsg` with `refund_address: None`, any unprivileged NEAR account can call the publicly accessible `request_refund` function and supply an attacker-controlled Bitcoin address as the refund destination. After `unsafe_refund_timelock_sec` elapses without DAO/Operator rejection, the attacker calls `execute_refund` and the bridge MPC-signs a transaction sending the victim's BTC to the attacker's address. This is a direct analog to the ZetaChain M-12 finding: the wrong address (attacker-supplied instead of the legitimate depositor's address) is recorded as the refund recipient.

---

### Finding Description

`DepositMsg` declares `refund_address` as an optional field: [1](#0-0) 

When this field is `None`, `internal_request_refund` accepts the caller-supplied `refund_address` parameter without any ownership check: [2](#0-1) 

The caller-supplied address is then stored verbatim in the `RefundRequest`: [3](#0-2) 

`request_refund` in the public API carries no access control beyond `#[pause]`. The only internal check is that a custom `gas_fee` requires DAO/Operator — confirming the function itself is open to any NEAR account: [4](#0-3) 

The sole protection for the `refund_address: None` case is a longer `unsafe_refund_timelock_sec` and the expectation that DAO/Operator will reject suspicious requests before it expires: [5](#0-4) 

When `execute_refund` is called after the timelock, `finalize_refund_with_psbt` uses `refund_request.refund_address` — the attacker-supplied value — to build the Bitcoin output: [6](#0-5) [7](#0-6) 

The MPC then signs and broadcasts a transaction paying the attacker's BTC address.

Additionally, a duplicate-request guard prevents the legitimate depositor from overwriting the attacker's entry once it is stored: [8](#0-7) 

---

### Impact Explanation

**Critical.** An attacker who observes an unfinalized BTC/ZEC deposit whose `DepositMsg` has `refund_address: None` can permanently redirect the entire deposit amount to their own Bitcoin address. The bridge MPC signs the refund transaction, making the theft irreversible once the signed transaction is broadcast. This constitutes significant, permanent loss of user funds.

---

### Likelihood Explanation

**Medium.** The `DepositMsg` and the raw Bitcoin transaction are both fully public on-chain. Any depositor who omits `refund_address` (the default for most integrations) is vulnerable. The attack requires only that:

1. A deposit is not finalized (relayer downtime, network congestion, or deliberate griefing are all realistic triggers).
2. The DAO/Operator fails to reject the malicious `request_refund` within `unsafe_refund_timelock_sec`.

The attacker can also front-run the legitimate depositor's own `request_refund` call, since only one request per UTXO is accepted.

---

### Recommendation

Require that `deposit_msg.refund_address` is always set at deposit time and enforce that the `refund_address` argument to `request_refund` matches it. If supporting caller-supplied addresses is necessary, bind the request to `env::predecessor_account_id()` and require the same account to call `execute_refund`, eliminating the ability for a third party to register a refund on behalf of another depositor.

---

### Proof of Concept

1. **Victim** constructs `DepositMsg { recipient_id: "victim.near", refund_address: None, ... }` and sends 1 BTC to the derived deposit address.
2. The relayer fails to call `verify_deposit`; the UTXO remains unfinalized.
3. **Attacker** reads the `DepositMsg` and `tx_bytes` from the Bitcoin blockchain (both public).
4. Attacker calls:
   ```
   request_refund(
       deposit_msg,           // victim's DepositMsg with refund_address: None
       "attacker_btc_addr",   // attacker-controlled BTC address
       tx_bytes,
       vout,
       proof,
       None                   // no custom gas_fee needed
   )
   ```
   The check at `refund.rs:154–158` is skipped because `deposit_msg.refund_address` is `None`. The `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`.
5. The legitimate depositor attempts `request_refund` with their own address — it panics at `refund.rs:544–547` ("Refund request already exists for this UTXO").
6. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), attacker calls `execute_refund(utxo_storage_key, None)`.
7. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `"attacker_btc_addr"` and submits it to the MPC for signing.
8. The signed transaction is broadcast; 1 BTC (minus gas fee) is permanently transferred to the attacker.

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())

                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
