### Title
`cancel_withdraw` Panics for `WithdrawOriginal/PendingSign` Withdrawals After Timeout, Permanently Locking User nBTC — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

### Summary

`internal_cancel_withdraw` unconditionally calls `assert_withdraw_original_pending_verify_tx`, which internally asserts `stage == PendingVerify`. A withdrawal that has not yet been signed by the relayer remains in `PendingSign`. Once `max_btc_tx_pending_sec` elapses, the DAO/Operator's only cancel path panics, leaving the user's nBTC permanently locked in the bridge contract with no on-chain recovery mechanism.

### Finding Description

**Withdrawal creation** — `ft_on_transfer` → `create_btc_pending_info` stores the pending info with:

```rust
state: PendingInfoState::WithdrawOriginal(OriginalState {
    stage: PendingInfoStage::PendingSign,
    ...
})
``` [1](#0-0) 

At this point the user's nBTC is held by the bridge contract. The actual burn only happens later in `verify_withdraw_burn_promise`, which is only reachable after the withdrawal reaches `PendingVerify` and then `PendingBurn`. [2](#0-1) 

**Cancel path** — `cancel_withdraw` (DAO/Operator gated) calls `internal_cancel_withdraw`: [3](#0-2) 

Inside `internal_cancel_withdraw`, after the timeout guard passes, line 37 calls:

```rust
original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();
``` [4](#0-3) 

**The panicking assertion** — `assert_withdraw_original_pending_verify_tx` matches `WithdrawOriginal` and immediately calls `state.assert_pending_verify()`:

```rust
pub fn assert_withdraw_original_pending_verify_tx(&self) {
    match self.state.borrow() {
        PendingInfoState::WithdrawOriginal(state) => state.assert_pending_verify(),
        _ => env::panic_str("Not withdraw original tx"),
    }
}
``` [5](#0-4) 

`assert_pending_verify` on `OriginalState` panics with `"Not pending verify stage"` whenever `stage != PendingVerify`:

```rust
pub fn assert_pending_verify(&self) {
    require!(
        self.stage == PendingInfoStage::PendingVerify,
        "Not pending verify stage"
    );
}
``` [6](#0-5) 

A withdrawal in `PendingSign` (relayer has not yet signed) will always hit this panic. There is no alternative cancel or force-refund function for `WithdrawOriginal/PendingSign` state anywhere in the production contract surface.

### Impact Explanation

The user's nBTC is transferred to the bridge at withdrawal initiation and is not burned until `PendingBurn`. If the relayer fails to sign within `max_btc_tx_pending_sec`, the withdrawal is stuck in `PendingSign`. The DAO/Operator's only recovery tool (`cancel_withdraw`) panics. No other on-chain path exists to return the nBTC to the user. The funds are permanently locked in the bridge contract under the current code.

### Likelihood Explanation

Any scenario where the relayer is slow, offline, or the MPC signing round fails causes a withdrawal to remain in `PendingSign` past the timeout. This is an operational reality for any MPC-based bridge. The user's public `ft_on_transfer` call is the entry point; the DAO/Operator's inability to cancel is the stuck-state consequence.

### Recommendation

In `assert_withdraw_original_pending_verify_tx` (or in `internal_cancel_withdraw` directly), accept both `PendingSign` and `PendingVerify` stages for the cancel path:

```rust
pub fn assert_withdraw_original_pending_verify_tx(&self) {
    match self.state.borrow() {
        PendingInfoState::WithdrawOriginal(state) => {
            require!(
                state.stage == PendingInfoStage::PendingSign
                    || state.stage == PendingInfoStage::PendingVerify,
                "Not pending sign or verify stage"
            );
        }
        _ => env::panic_str("Not withdraw original tx"),
    }
}
```

Ensure the downstream logic in `internal_cancel_withdraw` (e.g., `check_cancel_withdraw_rbf_psbt_valid`, `get_transaction`) gracefully handles the case where `tx_bytes_with_sign` is `None` (which it will be in `PendingSign`).

### Proof of Concept

1. User calls `ft_on_transfer` with a `Withdraw` message → `BTCPendingInfo` created with `stage = PendingSign`.
2. Relayer does not sign within `max_btc_tx_pending_sec` seconds.
3. DAO/Operator calls `cancel_withdraw(original_btc_pending_verify_id, output)`.
4. `internal_cancel_withdraw` passes the timeout check (line 31–35).
5. `assert_not_canceled()` passes (`cancel_rbf_reserved` is `None`).
6. `assert_withdraw_original_pending_verify_tx()` → `state.assert_pending_verify()` → **panics: "Not pending verify stage"**.
7. User's nBTC remains locked in the bridge with no recovery path. [7](#0-6) [5](#0-4)
