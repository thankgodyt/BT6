### Title
`isIncorrectClaimedFlag` for `DijkstraEra` Always Returns `False` Due to Incorrect Pattern Match — (`File: ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Eras.hs`)

---

### Summary

The `isIncorrectClaimedFlag` instance for `DijkstraEra` contains an incorrect pattern match that wraps `SL.DijkstraUtxowFailure` inside a spurious `Dijkstra.LedgerFailure` constructor. Because `DijkstraUtxowFailure` is a direct constructor of `DijkstraLedgerPredFailure` (not nested inside `LedgerFailure`), the pattern never matches, causing `isIncorrectClaimedFlag` to always return `False` for Dijkstra-era transactions. This is structurally identical to the `isToken0Weth` bug: a flag that is always the wrong default value, causing the wrong branch to be taken in a critical path.

---

### Finding Description

`applyAlonzoBasedTx` implements the two-phase validation intervention mechanism for Alonzo-and-later eras. When a remote peer submits a transaction (`DoNotIntervene`), the function forcibly sets `isValid = True` on the transaction before applying it:

```haskell
intervenedTx = case wti of
    DoNotIntervene -> tx & Core.isValidTxL .~ Alonzo.IsValid True
    Intervene -> tx
```

If the ledger then rejects the transaction with a `ValidationTagMismatch` error (meaning the script is actually invalid), the `handler` is supposed to catch it, call `isIncorrectClaimedFlag` to confirm the error type, and retry with `IsValid False` so the ledger can penalize the peer by taking their collateral:

```haskell
handler e = case (wti, e) of
    (DoNotIntervene, err)
      | isIncorrectClaimedFlag (Proxy @era) err ->
          defaultApplyShelleyBasedTx ... (tx & Core.isValidTxL .~ Alonzo.IsValid False)
    _ -> throwError e
```

The `isIncorrectClaimedFlag` instance for `DijkstraEra` is:

```haskell
instance SupportsTwoPhaseValidation DijkstraEra where
  isIncorrectClaimedFlag _ (DijkstraApplyTxError (err :| [])) = case err of
    Dijkstra.LedgerFailure
      ( SL.DijkstraUtxowFailure
          ( Dijkstra.UtxoFailure
              ( Dijkstra.UtxosFailure
                  ( Conway.ValidationTagMismatch ... )
                )
            )
        ) -> True
    _ -> False
  isIncorrectClaimedFlag _ _ = False
```

The imports reveal the problem:

```haskell
import qualified Cardano.Ledger.Dijkstra.Rules as Dijkstra
import qualified Cardano.Ledger.Dijkstra.Rules as SL
  ( DijkstraLedgerPredFailure (..)
  )
```

Both `Dijkstra.LedgerFailure` and `SL.DijkstraUtxowFailure` are constructors of `DijkstraLedgerPredFailure` from the same module. The pattern `Dijkstra.LedgerFailure (SL.DijkstraUtxowFailure ...)` attempts to match a `LedgerFailure` constructor wrapping something that itself contains a `DijkstraUtxowFailure`. Since `DijkstraUtxowFailure` is a direct constructor of `DijkstraLedgerPredFailure` (not a constructor of whatever `LedgerFailure` wraps), this nested pattern can never match.

The correct pattern — consistent with the `ConwayEra` instance — should be `SL.DijkstraUtxowFailure (Dijkstra.UtxoFailure ...)` directly, without the `Dijkstra.LedgerFailure` wrapper:

```haskell
-- Conway (correct):
SL.ConwayUtxowFailure (Conway.UtxoFailure (Conway.UtxosFailure (Conway.ValidationTagMismatch ...)))

-- Dijkstra (incorrect — spurious LedgerFailure wrapper):
Dijkstra.LedgerFailure (SL.DijkstraUtxowFailure (Dijkstra.UtxoFailure (Dijkstra.UtxosFailure (Conway.ValidationTagMismatch ...))))
```

This is directly analogous to the `isToken0Weth` bug: a boolean flag that is always `False` (the default), causing the wrong branch to execute in a critical conditional.

The changelog confirms this class of bug has occurred before in this exact function: *"Bugfix: Add an extra case to `isIncorrectClaimedFlag` for `Babbage` and `Conway`"* (v0.15.0.0). [1](#0-0) [2](#0-1) [3](#0-2)

### Impact Explanation

In Dijkstra era, `isIncorrectClaimedFlag` always returns `False`. When a remote peer submits a transaction with `isValid = True` but an actually-invalid Plutus script, the `handler` in `applyAlonzoBasedTx` fails to recognize the `ValidationTagMismatch` error and re-throws it instead of retrying with `IsValid False`. The transaction is rejected from the mempool rather than being included in a block with the corrected flag. As a result:

1. The remote peer's transaction is not included in a block, so the ledger never executes the collateral-seizure path.
2. The peer avoids the economic penalty (collateral forfeiture) that the two-phase validation mechanism is designed to impose.
3. The node wastes script-execution resources validating the invalid script with no compensating penalty to the submitter.

This materially weakens transaction authorization for Dijkstra-era transactions submitted by untrusted remote peers over the Node-to-Node protocol.

**Impact class:** Medium — public miniprotocol flaw that materially weakens transaction authorization without relying on DoS. [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

Any remote peer can trigger this by submitting a Dijkstra-era transaction with `isValid = True` and an invalid Plutus script over the Node-to-Node `TxSubmission` miniprotocol. No special privileges, keys, or stake are required. The `DoNotIntervene` path is taken for all remote-peer submissions. The Dijkstra era is the current production era, so this is immediately reachable on any node that has upgraded to support it. [6](#0-5) 

---

### Recommendation

Remove the spurious `Dijkstra.LedgerFailure` wrapper in the `DijkstraEra` instance of `isIncorrectClaimedFlag`, aligning it with the `ConwayEra` instance:

```haskell
-- Before (incorrect):
instance SupportsTwoPhaseValidation DijkstraEra where
  isIncorrectClaimedFlag _ (DijkstraApplyTxError (err :| [])) = case err of
    Dijkstra.LedgerFailure
      ( SL.DijkstraUtxowFailure
          ( Dijkstra.UtxoFailure
              ( Dijkstra.UtxosFailure
                  ( Conway.ValidationTagMismatch
                      (Alonzo.IsValid _claimedFlag)
                      _validationErrs
                    )
                )
            )
        ) -> True
    _ -> False
  isIncorrectClaimedFlag _ _ = False

-- After (correct):
instance SupportsTwoPhaseValidation DijkstraEra where
  isIncorrectClaimedFlag _ (DijkstraApplyTxError (err :| [])) = case err of
    SL.DijkstraUtxowFailure
      ( Dijkstra.UtxoFailure
          ( Dijkstra.UtxosFailure
              ( Conway.ValidationTagMismatch
                  (Alonzo.IsValid _claimedFlag)
                  _validationErrs
                )
            )
        ) -> True
    _ -> False
  isIncorrectClaimedFlag _ _ = False
```

Additionally, verify whether Dijkstra's error hierarchy (like Babbage's) has a second `ValidationTagMismatch` path that also needs to be covered, following the precedent of the v0.15.0.0 bugfix. [7](#0-6) [8](#0-7)

### Proof of Concept

**Entry path:**

1. A remote peer connects over the Node-to-Node `TxSubmission` miniprotocol and submits a Dijkstra-era transaction with `isValid = True` and an invalid Plutus script.
2. The mempool calls `addTx` with `AddTxForRemotePeer`, which sets `wti = DoNotIntervene`.
3. `applyAlonzoBasedTx` is called. `intervenedTx` sets `isValid = True` (already the case).
4. `defaultApplyShelleyBasedTx` calls the ledger's `applyTx`, which rejects the transaction with `DijkstraApplyTxError (DijkstraUtxowFailure (UtxoFailure (UtxosFailure (ValidationTagMismatch (IsValid True) ...))) :| [])`.
5. The `handler` calls `isIncorrectClaimedFlag (Proxy @DijkstraEra) err`.
6. The pattern `Dijkstra.LedgerFailure (SL.DijkstraUtxowFailure ...)` does not match the actual error `SL.DijkstraUtxowFailure (...)`, so `isIncorrectClaimedFlag` returns `False`.
7. The handler falls through to `_ -> throwError e`, re-throwing the error.
8. The transaction is rejected from the mempool. The peer's collateral is never seized. The penalty mechanism is silently bypassed. [9](#0-8) [1](#0-0)

applyAlonzoBasedTx globals ledgerEnv mempoolState wti tx = do
  (mempoolState', vtx) <-

        ledgerEnv
        mempoolState

      | isIncorrectClaimedFlag (Proxy @era) err ->
