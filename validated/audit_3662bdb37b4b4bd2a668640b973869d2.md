### Title
Missing Access Control on `clear_invalid_pending_verify_rbf` / `batch_clear_invalid_pending_verify_rbf` Allows Anyone to Remove Pending RBF State - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` are state-mutating functions documented as intended for the off-chain relayer program, but carry no role restriction. Any unprivileged NEAR account can invoke them, removing `BTCPendingInfo` entries from `btc_pending_infos` while leaving stale references in the owning account's `btc_pending_verify_list`, creating a persistent state inconsistency.

### Finding Description
Both public functions are decorated only with `#[pause(except(roles(Role::DAO)))]` — no `#[access_control_any]`, no `#[trusted_relayer]`:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) {
    self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
}

#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
``` [1](#0-0) 

The internal implementation removes the entry from `btc_pending_infos` but never removes the corresponding key from the account's `btc_pending_verify_list`:

```rust
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
}
``` [2](#0-1) 

The safety gate (`!rbf_txs.contains_key`) limits the call to entries whose original transaction has already been removed from `rbf_txs` (i.e., already verified on-chain). However, the function still removes the `BTCPendingInfo` record from `btc_pending_infos` without touching the account's `btc_pending_verify_list`, leaving a dangling key.

Contrast with the properly guarded sibling functions that require `Role::DAO` or `Role::Operator`: [3](#0-2) 

### Impact Explanation
An unprivileged attacker can call `batch_clear_invalid_pending_verify_rbf` with any set of qualifying RBF pending-verify IDs. After the call:

- `btc_pending_infos` no longer contains the entry.
- The victim account's `btc_pending_verify_list` still holds the now-dangling key.

Any subsequent code path that iterates or dereferences `btc_pending_verify_list` entries and calls `internal_unwrap_btc_pending_info` on the stale key will panic with `"BTC pending info not exist"`, potentially leaving the account in a stuck state that requires operator intervention to resolve. No direct fund theft occurs, but the bridge state for the affected account becomes inconsistent.

This maps to the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
The precondition (original tx already verified, RBF entry in `PendingVerify` state) is a normal operational state that occurs routinely after every RBF-accelerated withdrawal cycle. An attacker monitoring on-chain events can trivially identify qualifying IDs and race the legitimate off-chain cleanup call.

### Recommendation
Add `#[access_control_any(roles(Role::DAO, Role::Operator))]` (or at minimum `#[trusted_relayer]`) to both `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`, consistent with the pattern used on all other operator-level cleanup functions in the same file.

Additionally, `internal_clear_invalid_pending_verify_rbf` should also remove the key from the account's `btc_pending_verify_list` to avoid the state inconsistency regardless of who calls it.

### Proof of Concept
1. Alice initiates a withdrawal; the bridge creates a `BTCPendingInfo` in `PendingSign` state.
2. Alice calls `withdraw_rbf`, creating an RBF entry in `PendingVerify` state; the original tx ID is tracked in `rbf_txs`.
3. The relayer calls `verify_withdraw_v2` on the original tx; the original tx is verified and its `rbf_txs` entry is removed.
4. Attacker (any NEAR account) calls `clear_invalid_pending_verify_rbf(alice_rbf_pending_id)`.
   - `assert_pending_verify()` passes (state is `PendingVerify`).
   - `get_original_tx_id()` returns the original tx ID.
   - `!rbf_txs.contains_key(original_tx_id)` passes (already removed in step 3).
   - `internal_remove_btc_pending_info` deletes the entry from `btc_pending_infos`.
   - Alice's `btc_pending_verify_list` still contains the now-deleted key.
5. Any subsequent operation on Alice's account that dereferences `btc_pending_verify_list` and calls `internal_unwrap_btc_pending_info` on the stale key panics, leaving Alice's account in a stuck state. [1](#0-0) [2](#0-1)
