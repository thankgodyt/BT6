Audit Report

## Title
Relayer Permanently Loses Fronted BTC Tokens When `send_tokens` Fails in `utxo_fin_transfer_fast` — (File: near/omni-bridge/src/lib.rs)

## Summary
In `utxo_fin_transfer_fast`, the fast-transfer record is irrevocably removed or marked finalised before the relayer repayment is dispatched, and that repayment is fired with `.detach()` — no callback, no rollback. If the underlying `ft_transfer` to the relayer fails for any reason (e.g., relayer account not registered for the BTC NEP-141 token), the failure is silently swallowed and the relayer's fronted BTC tokens are permanently unrecoverable. The developers explicitly flagged this gap with a `// TODO: check how to deal with failed send_tokens` comment at the exact call site.

## Finding Description
`utxo_fin_transfer` is the entry point called when the BTC connector submits a UTXO proof via `ft_transfer_call`. When a matching fast-transfer record exists, it delegates to `utxo_fin_transfer_fast` (line 2485). Inside that function:

1. **State is mutated first (lines 2529–2540):** For NEAR-destination transfers, `remove_fast_transfer` permanently deletes the record. For other-chain transfers, `mark_fast_transfer_as_finalised` permanently seals it. Both paths are irreversible.
2. **Repayment is fire-and-forget (lines 2542–2548):** `send_tokens(...).detach()` dispatches the `ft_transfer` to the relayer with no callback. Any failure — panic in `send_tokens`, NEP-141 rejection, insufficient storage deposit — is silently swallowed.
3. **No recovery path exists:** The fast-transfer record is already gone. There is no retry mechanism, no event that signals failure, and no on-chain state that would allow the relayer to reclaim their fronted tokens.

The connector authenticity check (lines 2471–2474) ensures only the legitimate BTC connector can reach this path, but it provides no protection against the relayer repayment failing after state has already been mutated.

## Impact Explanation
A relayer who fronted real BTC-backed NEP-141 tokens is entitled to repayment when the UTXO proof is finalised. If the `ft_transfer` to the relayer fails after the fast-transfer record has been removed/finalised, those tokens are permanently lost — they are neither returned to the bridge escrow nor credited to the relayer. This is a concrete, permanent loss of bridged BTC funds, matching the Critical impact class: *loss or permanent freezing of bridged funds across Bitcoin/NEAR flows*.

## Likelihood Explanation
The most direct trigger is a relayer account that lacks a storage deposit for the BTC NEP-141 token at the time the UTXO proof is finalised. This can occur naturally (storage registration lapses between fast-transfer initiation and UTXO proof submission) or can be deliberately arranged. No privileged access is required; any entity acting as a relayer and submitting fast transfers is exposed. The BTC connector itself is trusted and behaves correctly; the failure mode is entirely within the NEAR contract's own promise-handling logic.

## Recommendation
1. Do **not** call `remove_fast_transfer` / `mark_fast_transfer_as_finalised` before the token transfer is confirmed to have succeeded.
2. Replace `.detach()` with a `#[private]` callback registered on the `send_tokens` promise.
3. In the callback: on success, remove/finalise the fast-transfer record; on failure, leave the record intact so the transfer can be retried or the relayer can be repaid via an alternative path.

## Proof of Concept
1. Register a fast transfer for a UTXO ID where the relayer account (`relayer.near`) has **no** storage deposit for the BTC NEP-141 token.
2. Have the BTC connector call `ft_transfer_call` with the matching UTXO proof, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Observe that `remove_fast_transfer` (line 2530) executes and the record is deleted.
4. Observe that `send_tokens(...).detach()` (lines 2542–2548) fires but the underlying `ft_transfer` to `relayer.near` fails silently because the account is not registered for the token.
5. Assert: the fast-transfer record no longer exists; the relayer's BTC token balance is unchanged. The relayer has permanently lost their fronted tokens with no on-chain recovery path.
