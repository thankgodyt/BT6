### Title
Stub `validatePerasCert` Accepts Arbitrary Peer-Supplied Certificates, Permanently Corrupting `latestCertSeen` and Disabling Node Voting - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate without any cryptographic or semantic validation. A single malicious peer can send a crafted certificate carrying an arbitrarily large future round number. Because `PerasCertDB` updates `pcdsLatestCertSeen` to the highest-round cert ever seen, this permanently sets the node's "latest certificate seen" to a round that can never be matched by the real chain, causing both Peras voting rules (VR-1A and VR-2A) to fail forever and silently disabling the node's participation in Peras voting.

---

### Finding Description

**Root cause — stub validator always returns `Right`**

The universal `BlockSupportsPeras` instance, which is the only production instance, contains a placeholder `validatePerasCert` that unconditionally wraps every inbound certificate in `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No round-number range check, no boosted-block existence check, no committee-membership check, and no cryptographic signature check is performed.

**Inbound path — peer-supplied certs reach the stub without any prior gate**

Both production pool writers call `validatePerasCert mkPerasParams` directly on the raw peer-supplied `PerasCert`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- stub: always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` filters out already-known round numbers, then calls the validator on the remainder. Because the stub always returns `Right`, every new-round cert is accepted and forwarded to `addCert`. [3](#0-2) 

**State mutation — `pcdsLatestCertSeen` is updated to the highest round ever seen**

`implAddCert` unconditionally promotes the incoming cert to `pcdsLatestCertSeen` whenever its round number exceeds the current maximum:

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [4](#0-3) 

**Downstream effect — voting rules permanently fail**

The `PerasCertDB` API documents that `getLatestCertSeen` "impacts voting directly because having seen a certificate is a precondition for voting in any round except for the very first one": [5](#0-4) 

The two voting rules that consume this value are:

- **VR-1A**: requires `currRoundNo == getPerasCertRound latestCertSeen + 1`. If `latestCertSeen` carries round `maxBound`, this equality can never hold. [6](#0-5) 

- **VR-2A**: requires `getPerasCertRound latestCertSeen + R <= currRoundNo`. If `latestCertSeen` carries a far-future round, this inequality can never hold. [7](#0-6) 

Both VR-1 and VR-2 fail simultaneously, so `isPerasVotingAllowed` returns `NoVote` for every future round, permanently. [8](#0-7) 

---

### Impact Explanation

A single unprivileged peer can permanently disable a target node's Peras voting capability by injecting one crafted certificate. The node continues to follow the chain normally but never casts another Peras vote, removing it from quorum calculations. This materially weakens Peras vote authorization for the affected node without any operator fault and without relying on sustained DoS. The impact matches: **Medium — public miniprotocol flaw that materially weakens vote authorization**.

---

### Likelihood Explanation

The ObjectDiffusion miniprotocol for Peras certificates is reachable by any peer the node connects to. No stake, no key material, and no privileged access is required. The attacker needs only to send one well-formed CBOR-encoded `PerasCert` with `pcCertRound` set to a large value (e.g., `maxBound :: Word64`). The stub validator provides zero resistance. Likelihood is **High** given the trivial preconditions.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that at minimum validates: (a) the round number is within a plausible window of the current chain tip, (b) the boosted block point exists in the local VolatileDB or ImmutableDB, and (c) the certificate carries a valid committee signature.
2. Until the full cryptographic validation is in place, add a round-number range guard in `processCerts` or `implAddCert` that rejects any certificate whose round number exceeds `currentRound + maxFutureRoundTolerance`.
3. Consider making `pcdsLatestCertSeen` update-resistant to future-round certs by bounding accepted round numbers against the node's current slot/round view before persisting.

---

### Proof of Concept

1. Connect to a target node via the Peras certificate ObjectDiffusion miniprotocol.
2. Send a single `PerasCert` message with:
   - `pcCertRound = PerasRoundNo maxBound` (e.g., `18446744073709551615`)
   - `pcCertBoostedBlock` = any recent valid block point (or `GenesisPoint`)
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right` unconditionally.
4. `implAddCert` stores the cert; `pcdsLatestCertSeen` is updated to round `maxBound`.
5. From this point forward, `isPerasVotingAllowed` evaluates:
   - VR-1A: `currRoundNo == maxBound + 1` → overflow/false → fails
   - VR-2A: `maxBound + R <= currRoundNo` → overflow/false → fails
6. The node returns `NoVote` for every subsequent round and never participates in Peras quorum again.
