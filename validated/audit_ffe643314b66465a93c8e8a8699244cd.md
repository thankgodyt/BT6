### Title
Hardcoded Mainnet `HistoricityCutoff` in `mkGenesisConfig` Weakens Genesis Sync Safety on Non-Mainnet Networks — (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` in `Genesis.hs` hardcodes the `HistoricityCutoff` to `3 * 2160 * 20 + 3600 = 133,200 s` (37 hours), which is the correct value only for Cardano mainnet (`k=2160`, `f=1/20`, 1 s/slot). The value is never derived from the actual network's `SecurityParam`, active-slot coefficient, or slot length. Critically, `GenesisConfigFlags` — the record that maps to the node's config file — has no field for this parameter, so it cannot be overridden by operators. On any network whose stability window differs from mainnet's (private testnets, preview, preprod, or any future network with changed parameters), the historicity check is miscalibrated: if the actual stability window is shorter than the hardcoded cutoff, an unprivileged adversarial peer can serve historical headers without being disconnected, weakening the Genesis Sync Safety guarantee.

---

### Finding Description

`mkGenesisConfig` in `Genesis.hs` unconditionally sets:

```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
``` [1](#0-0) 

The inline comment confirms the intent: this is the Shelley stability window for **Cardano mainnet** (`3k/f` slots × 1 s/slot + 1 h safety margin). The actual network's `k`, `f`, and slot length are never consulted.

`GenesisConfigFlags` — the record parsed from the node's config file — exposes overrides for every other Genesis tuning knob (`gcfBucketCapacity`, `gcfBucketRate`, `gcfCSJJumpSize`, `gcfGDDRateLimit`, `gcfBlockFetchGracePeriod`) but has **no field** for the historicity cutoff:

```haskell
data GenesisConfigFlags = GenesisConfigFlags
  { gcfEnableCSJ :: Bool
  , gcfEnableLoEAndGDD :: Bool
  , gcfEnableLoP :: Bool
  , gcfBlockFetchGracePeriod :: Maybe DiffTime
  , gcfBucketCapacity :: Maybe Integer
  , gcfBucketRate :: Maybe Integer
  , gcfCSJJumpSize :: Maybe SlotNo
  , gcfGDDRateLimit :: Maybe DiffTime
  }
``` [2](#0-1) 

The `HistoricityCutoff` type and its required semantics are documented in `HistoricityCheck.hs`:

> "This should be set to at least the maximum duration (across all eras) of a stability window (the number of slots in which at least `k` blocks are guaranteed to arise)." [3](#0-2) 

The check is enforced in `mkCheck`, which disconnects any peer whose `MsgRollBackward` or `MsgAwaitReply` references a header older than the cutoff at arrival time:

```haskell
pure $
  when (historicityCutoff < actualRollbackAge) $
    throwError HistoricityException { ... }
``` [4](#0-3) 

The check is wired into the node in `Node.hs` directly from `gcHistoricityCutoff`:

```haskell
historicityCheck getGsmState =
  case gcHistoricityCutoff llrnGenesisConfig of
    Nothing -> HistoricityCheck.noCheck
    Just historicityCutoff ->
      HistoricityCheck.mkCheck systemTime getGsmState historicityCutoff
``` [5](#0-4) 

The design document explicitly acknowledges that `HistoricityCutoff` is a constant in the implementation and that it must track `Scg` (the stability window) of the chain's current era:

> "MaxCaughtUpAge and HistoricityCutoff are indeed constants in the implementation… Other parameters such as MaxCaughtUpAge and HistoricityCutoff have this same caveat as Sgen." [6](#0-5) 

---

### Impact Explanation

The `HistoricityCutoff` is a Genesis security boundary. When it is **larger than the actual stability window** of the running network (which happens on any network with `k < 2160`, `f > 0.05`, or slot length > 1 s), an adversarial peer can:

1. Connect to a syncing node running Genesis mode.
2. Send `MsgRollBackward` or `MsgAwaitReply` messages referencing a header whose slot time is older than the actual stability window (`3k/f` seconds for that network) but younger than the hardcoded 37-hour cutoff.
3. The `mkCheck` predicate evaluates `historicityCutoff < actualRollbackAge` — because `historicityCutoff` is the mainnet constant (133,200 s) and `actualRollbackAge` is less than that, the condition is **false** and the peer is **not disconnected**.
4. The adversarial peer remains connected and can continue serving a historical (potentially adversarial) chain fragment, bypassing the historicity filter that is the first line of defense against long-range attacks during Genesis sync.

This directly weakens the **Sync Safety** property of Ouroboros Genesis: the guarantee that a syncing node will never select more than `k` blocks of a chain not extended by a recent honest selection. The historicity check is specifically designed to eliminate peers serving historical chains before the GDD/LoE/LoP layers are engaged; miscalibrating it enlarges the attack surface for long-range attacks on non-mainnet deployments.

---

### Likelihood Explanation

Private testnets routinely use `k` values orders of magnitude smaller than mainnet (e.g., `k=10`, `k=100`). The Cardano preview and preprod networks use the same `k=2160` but have historically used different slot lengths and active-slot coefficients during testing phases. Any such network running Genesis mode with `enableGenesisConfigDefault` or `mkGenesisConfig (Just defaultGenesisConfigFlags)` silently inherits the wrong cutoff with no warning. Because `GenesisConfigFlags` provides no override field, operators have no supported path to correct it short of patching the library. The misconfiguration is silent — no log message, no startup assertion — so it will go undetected until an adversarial peer exploits it.

---

### Recommendation

1. Add a `gcfHistoricityCutoff :: Maybe NominalDiffTime` field to `GenesisConfigFlags` so operators can override the value from the node's config file.
2. Derive the default value from the actual network's `SecurityParam` (`k`), active-slot coefficient (`f`), and slot length rather than hardcoding mainnet constants. The formula is `max_over_eras(3 * k / f * slotLength) + safetyMargin`.
3. Add a startup assertion (or at minimum a warning log) when Genesis is enabled and the configured `HistoricityCutoff` is less than the computed stability window for the running network.

---

### Proof of Concept

**Setup**: private testnet, `k = 100`, `f = 0.05`, slot length = 1 s. Actual Shelley stability window: `3 × 100 / 0.05 × 1 s = 6,000 s ≈ 100 minutes`. Hardcoded cutoff: `133,200 s ≈ 37 hours`.

**Attack sequence**:

1. Adversary pre-builds a chain fork that diverges from the honest chain at a point whose slot time is, say, 3 hours ago (10,800 s). This is well beyond the actual stability window (6,000 s) but well within the hardcoded cutoff (133,200 s).
2. Adversary connects to a syncing node with Genesis enabled (`LoE`, `GDD`, `LoP`, `CSJ` all active).
3. Adversary sends `MsgRollBackward` to the slot 3 hours ago.
4. `mkCheck` evaluates: `133,200 < 10,800` → **false** → no `HistoricityException` → peer is **not disconnected**.
5. The adversary's historical chain is now eligible to be evaluated by the GDD/LoE layers. Because the adversary controls the chain and can craft it to appear dense in the Genesis window, the GDD may not immediately disconnect them.
6. The syncing node is exposed to a long-range attack vector that the historicity check was specifically designed to close.
