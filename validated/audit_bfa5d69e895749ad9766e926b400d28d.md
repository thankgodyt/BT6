### Title
Fee-on-Transfer Token Escrow Over-Minting via Caller-Supplied `amount` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
`OmniBridge.initTransfer` records the caller-supplied `amount` in the `InitTransfer` event without measuring the actual tokens received by the contract. For deflationary / fee-on-transfer ERC20 tokens, the bridge holds fewer tokens than the event claims, causing NEAR to mint more wrapped tokens than were deposited and leaving the escrow permanently undercollateralized.

### Finding Description
In `OmniBridge.sol`, the `initTransfer` function accepts a caller-controlled `amount` parameter. For standard (non-bridge, non-custom-minter) ERC20 tokens, it executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
```

and immediately emits:

```solidity
emit BridgeTypes.InitTransfer(msg.sender, tokenAddress, currentOriginNonce, amount, ...);
``` [1](#0-0) 

The contract never snapshots `balanceOf(address(this))` before and after the transfer to determine the **actual** received amount. It blindly trusts the caller-supplied `amount` as the canonical value in the event.

The NEAR prover reads this event and passes `amount` to `fin_transfer`, which mints or unlocks exactly that many tokens to the recipient on NEAR. [2](#0-1) 

The same pattern exists in the Starknet bridge: `init_transfer` calls `transfer_from(caller, get_contract_address(), amount.into())` and emits `amount` verbatim without measuring actual receipt. [3](#0-2) 

### Impact Explanation
Any ERC20 token that deducts a fee during `transferFrom` (deflationary tokens, tokens with transfer taxes, rebasing tokens with negative rebase) can be used to mint more wrapped tokens on NEAR than the bridge actually holds in escrow. Over repeated deposits, the escrow becomes progressively undercollateralized. When legitimate users bridge back, the EVM bridge cannot fulfill withdrawals — constituting permanent loss of funds for those users. An attacker can also directly profit by depositing deflationary tokens and withdrawing the full `amount` on NEAR as a non-deflationary wrapped token, then bridging back a different supported token.

### Likelihood Explanation
Fee-on-transfer ERC20 tokens are common on Ethereum mainnet (e.g., tokens with 1–5% transfer taxes). The bridge has no allowlist restricting which ERC20 tokens can be deposited via `initTransfer` — any address is accepted. An unprivileged user can call `initTransfer` directly with no preconditions beyond token approval. The exploit requires no privileged access, no admin compromise, and no coordination. [4](#0-3) 

### Recommendation
Measure the actual received balance using a before/after `balanceOf` snapshot and use the delta as the canonical amount in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 received = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(received > 0, "ZeroReceived");
// use `received` (cast to uint128) in the event and downstream logic
```

Apply the same fix to `starknet/src/omni_bridge.cairo`'s `init_transfer`. Additionally, consider maintaining an explicit allowlist of supported tokens so that tokens with non-standard transfer semantics can be reviewed before being accepted by the bridge.

### Proof of Concept

1. Deploy or identify a fee-on-transfer ERC20 token `T` that burns 10% on every `transferFrom`. `T` is not in `isBridgeToken` and has no `customMinters` entry.
2. Attacker holds 1000 `T` and approves `OmniBridge`.
3. Attacker calls `OmniBridge.initTransfer(T, 1000, 0, 0, "attacker.near", "")`.
4. Inside `initTransfer`, `safeTransferFrom` moves tokens: bridge receives **900** `T` (100 burned as fee). [5](#0-4) 
5. The event `InitTransfer(..., amount=1000, ...)` is emitted with the caller-supplied value. [6](#0-5) 
6. A relayer picks up the event and submits a proof to the NEAR bridge's `fin_transfer`.
7. NEAR's `init_transfer_internal` mints **1000** wrapped-`T` tokens to `attacker.near`. [7](#0-6) 
8. Attacker now holds 1000 wrapped-`T` on NEAR but the EVM bridge only holds 900 `T`.
9. Attacker bridges back 1000 wrapped-`T` to Ethereum; the bridge attempts to release 1000 `T` but only holds 900, causing the last 100 `T` worth of withdrawals by other users to fail permanently.

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
