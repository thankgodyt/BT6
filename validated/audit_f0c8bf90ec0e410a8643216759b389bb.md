### Title
Unauthenticated Peras Certificate Injection Inflates Chain Weight, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance unconditionally accepts every inbound `PerasCert` as valid. Because Peras certificates are diffused over a live node-to-node miniprotocol and their boost weight is directly added to the `PerasWeightSnapshot` used in chain selection, an unprivileged peer can inject arbitrarily many fake certificates that inflate the apparent weight of any chain fragment, causing an honest node to prefer a non-canonical adversarial chain.

---

### Finding Description

`validatePerasCert` in the universal `BlockSupportsPeras` instance always returns `Right`:

```haskell

  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

This is the only `BlockSupportsPeras` instance in the repository (the comment explicitly calls it a "degenerate instance for all blks to get things to compile"). It is therefore the instance used for all block types, including production Cardano blocks. [2](#0-1) 

The production certificate ingest path in `makePerasCertPoolWriterFromChainDB` passes this stub directly as the validator:

```haskell

``` [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate; if all pass (which they always do), each is timestamped and stored: [4](#0-3)

The snapshot feeds directly into `constructPreferableCandidates` → `preferAnchoredCandidate` and `rollbackExceedsSuffix`, which use `totalWeightOfFragment` (block count + boost) to decide whether a candidate chain is preferred: [7](#0-6) 

The `perasCertDiffusionProtocol` miniprotocol is wired into the live node-to-node application, so any connected peer can send `PerasCert` objects: [8](#0-7)

### Impact Explanation

An adversary controlling one or more peers can send crafted `PerasCert` messages, each for a distinct `PerasRoundNo` (the `PerasCertDB` deduplicates by round, so one cert per round is accepted), all pointing to a block on the adversary's fork. Each accepted certificate adds `perasWeight` to that block's entry in the `PerasWeightSnapshot`. The glossary explicitly notes "the same point can be boosted multiple times." [9](#0-8) 

`totalWeightOfFragment` = chain length + accumulated boost. Once the injected boost exceeds the honest chain's length advantage, `preferAnchoredCandidate` returns `ShouldSwitch` for the adversarial fork, and the honest node switches to the adversary's chain — a direct chain-selection safety failure caused by an unprivileged peer sending crafted network messages. [10](#0-9) 

This matches the **High** impact class: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The `perasCertDiffusionProtocol` is a live, enabled miniprotocol in the node-to-node application bundle. Any peer that successfully connects can immediately send `PerasCert` messages. No stake, key material, or privileged access is required. The only rate-limiting factor is the one-cert-per-round deduplication, but an adversary can trivially enumerate distinct round numbers. The attack requires only crafting valid CBOR-encoded `PerasCert` structs (round number + block point), which are fully serialisable without any cryptographic material. [11](#0-10) 

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate BLS signature against the claimed committee members.
2. That the committee members were legitimately elected for the stated round (using the epoch's stake snapshot and the WFA/LS committee selection algorithm).
3. That the boosted block point exists on a valid chain and falls within the allowed round window.

Until real validation is in place, the `perasCertDiffusionProtocol` should be disabled or gated behind a feature flag so that no inbound certificates can reach `processCerts`.

---

### Proof of Concept

1. Connect to a target node as a peer via the node-to-node protocol.
2. Negotiate `perasCertDiffusionProtocol`.
3. Send a batch of `PerasCert` objects, each with a distinct `pcCertRound` (e.g., rounds 1–1000) and `pcCertBoostedBlock` pointing to a block on the adversary's fork.
4. `processCerts` calls `validatePerasCert mkPerasParams` on each — all return `Right`.
5. Each cert is stored in `PerasCertDB`; `implGetWeightSnapshot` accumulates `perasWeight * 1000` boost for the adversary's block.
6. When the adversary's fork is next considered in `constructPreferableCandidates`, `totalWeightOfFragment` for that fork exceeds the honest chain's weight, `preferAnchoredCandidate` returns `ShouldSwitch`, and the node adopts the adversary's chain.

**File:** docs/website/contents/references/glossary.md (L516-527)
```markdown
## ;Peras ;weight ;boost

Peras is an extension of Praos enabling faster settlement under optimistic conditions.
To this end, Peras can result in a block `B` receiving a *boost*, which means that any chain containing `B` gets additional weight when being compared to other chains.

Consider a chain fragment `F`:

- Its ;*weight boost* is the sum of all boosts received by points on this fragment (excluding the anchor). Note that the same point can be boosted multiple times.

- Its ;*total weight* is its tip block number plus its weight boost.

Note that these notions are always relative to a particular anchor, so different chain fragments must have the same anchor when their total weight is to be compared.
```
