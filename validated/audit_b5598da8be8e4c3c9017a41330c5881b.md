Audit Report

## Title
Finalized Transfer Record Removed on `ft_transfer_call` Rejection Enables Cross-Chain Replay Double-Spend — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When an inbound transfer to a NEAR recipient includes a non-empty `msg`, `process_fin_transfer_to_near` inserts the transfer ID into `finalised_transfers` via `add_fin_transfer`, then issues an `ft_transfer_call`. If the recipient contract rejects the tokens (returning the full amount from `ft_on_transfer`), `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, permanently erasing the replay guard. The same source-chain proof can then be re-submitted and finalized a second time, resulting in double-spending of bridged funds.

## Finding Description

`process_fin_transfer_to_near` first inserts the transfer ID into `finalised_transfers`: [1](#0-0) 

It then calls `send_tokens` with the attacker-controlled `msg` field and chains `fin_transfer_send_tokens_callback`, passing `is_ft_transfer_call = !msg.is_empty()`: [2](#0-1) 

The `msg` field originates verbatim from `init_transfer.msg` (the EVM `initTransfer` `message` parameter, fully attacker-controlled): [3](#0-2) 

In `fin_transfer_send_tokens_callback`, when `is_refund_required` returns `true` (i.e., `ft_transfer_call` resolved to `U128(0)` — meaning the recipient rejected all tokens), the code burns/reverts and then **removes the transfer ID from `finalised_transfers`**: [4](#0-3) 

`is_refund_required` returns `true` when `is_ft_transfer_call` is `true` and the promise result is `U128(0)`: [5](#0-4) 

`remove_fin_transfer` unconditionally removes the entry from `finalised_transfers` and refunds storage: [6](#0-5) 

After removal, `add_fin_transfer` will succeed again for the same `TransferId` because the `require!` only panics if the ID is already present: [7](#0-6) 

The `trusted_relayer` guard on `fin_transfer` does not prevent the exploit. The relayer staking mechanism is permissionless — any account can call `apply_for_trusted_relayer` with sufficient NEAR stake and, after the waiting period, becomes a trusted relayer: [8](#0-7) 

Furthermore, even without the attacker being a relayer themselves, a legitimate relayer observing the `FailedFinTransferEvent` would naturally re-submit the same proof (the intended retry behavior for failed transfers), completing the exploit without any attacker-controlled relayer.

## Impact Explanation

**For deployed (bridge-minted) tokens**: First finalization mints tokens and sends via `ft_transfer_call`; the attacker's contract rejects them; `burn_tokens_if_needed` burns the returned tokens; `remove_fin_transfer` erases the replay guard. Re-submission mints a fresh batch of tokens delivered to the attacker. Net effect: unauthorized minting backed by no corresponding lock on the source chain.

**For native (escrow-locked) tokens**: First finalization decrements the escrow counter via `unlock_tokens_if_needed`; the attacker's contract rejects; `revert_lock_actions` re-increments the counter; `remove_fin_transfer` erases the replay guard. Re-submission decrements the escrow again and delivers tokens to the attacker. Net effect: double-unlock draining the escrow.

This matches the allowed Critical impact: *cross-chain replay / nonce misuse enabling double-spending of bridged funds* and *balance manipulation / escrow mis-accounting that changes user or protocol balances*.

## Likelihood Explanation

The attacker needs only:
1. Tokens on the source chain (EVM/Starknet/Solana) — normal user capability.
2. A non-empty `message` in `initTransfer` — fully attacker-controlled parameter.
3. A NEAR recipient contract they deploy that returns the full amount from `ft_on_transfer` on the first call and `0` on the second.
4. Either: become a trusted relayer by staking (open, permissionless application process), or rely on a legitimate relayer to re-submit after observing `FailedFinTransferEvent`.

No admin compromise, key leakage, or MPC collusion is required. The exploit is repeatable for each new source-chain nonce.

## Recommendation

Do not call `remove_fin_transfer` on the refund path. The finalization record in `finalised_transfers` must be permanent regardless of whether the downstream `ft_transfer_call` succeeded or failed. The token burn and lock reversion can proceed without erasing the replay guard. To track failed finalizations for UX/retry purposes, introduce a separate `failed_transfers` set or a status enum (e.g., `Finalized::Success` / `Finalized::Failed`) that does not allow re-finalization of the same transfer ID.

## Proof of Concept

1. Attacker deploys `MaliciousRecipient` on NEAR. Its `ft_on_transfer` returns the full `amount` on the first call and `0` on the second.
2. Attacker calls `initTransfer` on EVM with `message = "trigger"` (non-empty) and `recipient = "malicious_recipient.near"`.
3. A trusted relayer (or the attacker acting as one after staking) submits the proof to `fin_transfer`.
4. `fin_transfer_callback` → `process_fin_transfer_to_near`: `add_fin_transfer` inserts `TransferId{Eth, N}` into `finalised_transfers`; `unlock_tokens_if_needed` decrements escrow by `amount`.
5. `send_tokens` issues `ft_transfer_call`; `MaliciousRecipient.ft_on_transfer` returns `amount` → `ft_transfer_call` resolves to `U128(0)`.
6. `fin_transfer_send_tokens_callback`: `is_refund_required` returns `true`; `burn_tokens_if_needed` burns (deployed) or `revert_lock_actions` re-locks (native); `remove_fin_transfer` erases `TransferId{Eth, N}` from `finalised_transfers`.
7. Attacker (or relayer observing `FailedFinTransferEvent`) re-submits the identical proof to `fin_transfer`.
8. `add_fin_transfer` succeeds (ID no longer in set); `unlock_tokens_if_needed` decrements escrow again; `send_tokens` issues `ft_transfer_call`; `MaliciousRecipient.ft_on_transfer` returns `0` → tokens delivered.
9. Attacker has received tokens for a single source-chain lock event — double-spend complete.

        let storage_usage = env::storage_usage();
        require!(

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }
