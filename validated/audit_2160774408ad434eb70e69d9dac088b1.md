### Title
Peras Vote Signature Lacks Network Domain Separation in `hashVoteSignature` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function that produces the message digest signed by Peras committee members commits only to `(roundNo, boostedBlockSlot, boostedBlockHash)`. It omits any network-specific identifier (network magic, genesis hash). The sole domain-separation mechanism is the `KeyScope` embedded in the BLS key, but `KeyScope` is an unenforced `ByteString`, is not serialized inside the signature, and is never checked against an expected network value during vote or certificate verification. An unprivileged peer who captures a valid Peras vote on one network can replay it verbatim on a second network where the same pool is registered with the same BLS key bytes and the same scope, causing the receiving node to accept an unauthorized vote.

---

### Finding Description

`hashVoteSignature` in `Peras/Crypto/BLS.hs` builds the message that every committee member signs:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
``` [1](#0-0) 

The preimage is `(roundNo ‖ boostedBlockSlot ‖ boostedBlockHash)`. No network magic, genesis hash, or any other network-specific field is included.

The intended domain separator is the `KeyScope` field embedded in every `BLS.PrivateKey` / `BLS.PublicKey`:

```haskell
-- | Key scope, later instantiated with usage and network id (e.g. PERAS/MAINNET)
type KeyScope = ByteString
``` [2](#0-1) 

The scope is injected into the BLS augmentation context at sign/verify time:

```haskell
instance HasBLSContext SIGN where
  blsCtx _ keyScope =
    minSigSignatureDST { blsSignContextAug = Just ("VOTE:" <> keyScope <> ":V0") }
``` [3](#0-2) 

`verifyWithRole` uses `publicKeyScope pk` — the scope stored in the **local** copy of the verification key — to reconstruct the context:

```haskell
verifyWithRole pk msg (Signature sig) =
  verifyDSIGN (blsCtx (Proxy @r) (publicKeyScope pk)) (unPublicKey pk) msg sig
``` [4](#0-3) 

Three structural gaps make this insufficient:

1. **`KeyScope` is unenforced.** It is a plain `ByteString` with no type-level or runtime constraint that it must contain a network identifier. The comment "e.g. PERAS/MAINNET" is aspirational. Test code uses `"ROUNDTRIP"` and `"TEST"`. [5](#0-4) 

2. **`Signature` carries no scope.** The serialized `PerasBLSCryptoVoteSignature` is a bare `SigDSIGN BLS12381MinSigDSIGN` with no scope field. A received signature cannot be independently checked for scope. [6](#0-5) 

3. **Verification never checks scope against an expected network value.** `verifyVoteSignature` and `verifyAggregateVoteSignature` both call `BLS.verifyWithRole` using whatever scope happens to be in the local key; there is no assertion that this scope equals the expected network scope. [7](#0-6) [8](#0-7) 

The same gaps apply to the aggregate certificate path in `implVerifyCert` for both `WFALS` and `EveryoneVotes` committee schemes. [9](#0-8) [10](#0-9)

### Impact Explanation

**Cross-network vote replay.** A pool operator registered on both mainnet and a testnet (or a private fork) with the same BLS key bytes and the same `KeyScope` value produces votes whose signatures are valid on both networks. An unprivileged peer who observes a valid vote on network A can forward it to network B. The receiving node on B will:

1. Look up the voter's public key from the committee (same raw key bytes, same scope).
2. Reconstruct `hashVoteSignature(roundNo, boostedBlock)` — identical bytes if the same block hash appears on both networks (pre-fork blocks share hashes).
3. Call `verifyWithRole` with the same BLS context — verification succeeds.
4. Accept the vote as legitimate.

If enough replayed votes accumulate to form a quorum, a certificate can be forged for a block that was only intended to be boosted on the other network, directly affecting Peras chain selection and block-boosting decisions on the target network.

This matches the allowed impact: **bypass of Peras voting checks enabling unauthorized vote/certificate acceptance**.

---

### Likelihood Explanation

- Pool operators routinely run the same pool on both mainnet and a preview/preprod testnet, reusing key material.
- The `KeyScope` mechanism is documented as "e.g. PERAS/MAINNET" but there is no enforcement; if operators or tooling omit the network suffix (or use an empty scope), both networks share the same BLS context.
- Pre-fork blocks (before a testnet diverges from mainnet) have identical hashes on both networks, satisfying the block-hash condition without any cryptographic attack.
- The attack requires only passive observation of votes on one network and forwarding them to another — no privileged access, no key compromise.

---

### Recommendation

Include an explicit, network-bound domain tag in the `hashVoteSignature` preimage rather than relying solely on the key scope:

```haskell
hashVoteSignature networkMagic roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (4 + 8 + 8 + 32) $
    BS.word32BE networkMagic
    <> BS.word64BE (unPerasRoundNo roundNo)
    <> BS.word64BE (unSlotNo (bytes32RealPointSlot (unPerasBoostedBlock boostedBlock)))
    <> BS.byteStringCopy (BS.fromShort (bytes32RealPointHash (unPerasBoostedBlock boostedBlock)))
```

Additionally:
- Enforce at key-loading time that `KeyScope` contains the network magic (e.g., `"PERAS/" <> show networkMagic`).
- Add a runtime assertion in `verifyVoteSignature` / `verifyAggregateVoteSignature` that `publicKeyScope pk` equals the expected scope for the current network.
- Consider embedding the scope in the serialized `Signature` type so that received signatures can be independently validated.

### Proof of Concept

**Setup**: Pool P is registered on both mainnet (network magic `764824073`) and preprod testnet (network magic `1`) with identical BLS key bytes. Both networks load the key with scope `"PERAS"` (no network suffix).

**Step 1** — Testnet vote production (legitimate):
```
roundNo = 42
boostedBlock = (slot=1000, hash=H)   -- H is a pre-fork block hash shared with mainnet
Pool P signs: hashVoteSignature 42 (slot=1000, H)
             = SHA256(42‖1000‖H)     -- no network magic in preimage
BLS context: "VOTE:PERAS:V0"         -- same on both networks
```

**Step 2** — Mainnet replay (attack):
```
Attacker forwards the testnet vote to a mainnet node.
Mainnet node looks up Pool P's public key (same bytes, scope "PERAS").
Reconstructs: hashVoteSignature 42 (slot=1000, H) -- identical bytes
BLS context: "VOTE:PERAS:V0"                       -- identical context
verifyWithRole succeeds → vote accepted on mainnet.
```

**Step 3** — Certificate forgery: If the attacker replays enough votes from testnet round 42 to meet the mainnet quorum threshold, `forgeCert` / `implVerifyCert` will produce and accept a certificate boosting block H on mainnet, influencing Peras chain selection without any legitimate mainnet committee participation.
