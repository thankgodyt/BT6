Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Is Blacklisted on Destination Token — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
When bridging tokens from NEAR to EVM, if the destination token (e.g., USDC, USDT) implements an address blacklist and the recipient is blacklisted, every `finTransfer` call reverts at the `safeTransfer` step. Because the MPC signature is cryptographically committed to the exact `recipient` field, no valid alternative payload can be constructed. Tokens already burned or locked on NEAR are permanently unrecoverable with no protocol-level user remedy.

## Finding Description
In `OmniBridge.finTransfer`, the nonce guard is set at line 287 before the transfer executes:

```solidity
completedTransfers[payload.destinationNonce] = true;   // L287
```

If the subsequent `safeTransfer` at line 351 reverts (e.g., USDC blacklist check), the entire transaction reverts, including the nonce write — so the nonce is never consumed. However, the MPC signature is produced over a Borsh-encoded payload that includes `Borsh.encodeAddress(payload.recipient)` at line 298. The signed hash commits to the exact recipient address. There is no mechanism to produce a valid signature for a different recipient without re-initiating the transfer on NEAR. Every retry with the same signed payload reverts identically. There is no `try/catch`, no fallback address, and no redirect path in any of the four transfer branches (`safeTransfer`, `IERC1155.safeTransferFrom`, `IBridgeToken.mint`, `ICustomMinter.mint`).

On the NEAR side, `init_transfer_internal` calls `burn_tokens_if_needed` (for deployed tokens) and `lock_tokens_if_needed` (for native tokens) before the transfer is stored in `pending_transfers`. There is no user-callable cancellation function. The transfer message remains in `pending_transfers` indefinitely with no on-chain recovery path available to the user.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds** — an explicitly listed Critical impact. Tokens are burned or locked on NEAR and can never be released on EVM. The MPC signature is bound to the blacklisted recipient, so no valid `finTransfer` call can ever succeed. The user loses the full bridged amount with no on-chain recourse. The impact is not hypothetical: USDC and USDT both implement operational blacklists, and Circle has exercised blacklisting in response to regulatory and sanctions actions.

## Likelihood Explanation
USDC and USDT are among the most commonly bridged assets and both implement address blacklists. A recipient address can be blacklisted by Circle or Tether after a NEAR-side transfer is initiated (e.g., due to regulatory action, OFAC sanctions, or exchange compliance). The NEAR bridge performs no blacklist pre-check, so the transfer is accepted and tokens are burned before the incompatibility is discovered. The scenario requires no attacker — it is triggered by normal user behavior combined with a post-initiation blacklisting event. Likelihood is Medium.

## Recommendation
Wrap each token transfer branch in a `try/catch` and redirect funds to a designated admin-controlled fallback address on failure, emitting a recoverable event:

```solidity
try IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount) {
    // success
} catch {
    IERC20(payload.tokenAddress).safeTransfer(fallbackAddress, payload.amount);
    emit RedistributeFunds(payload.recipient, payload.tokenAddress, payload.amount);
}
```

Apply the same pattern to the `IERC1155.safeTransferFrom`, `IBridgeToken.mint`, and `ICustomMinter.mint` branches. Additionally, consider adding a NEAR-side cancellation function that allows the DAO or the original sender to reclaim burned/locked tokens when a transfer has been pending beyond a configurable timeout.

## Proof of Concept
1. User holds USDC (NEP-141) on NEAR and calls `ft_transfer_call` to the bridge with recipient `0xBlacklisted` on Ethereum.
2. `init_transfer_internal` calls `burn_tokens_if_needed`, burning the USDC, and stores the transfer in `pending_transfers`.
3. A relayer calls `sign_transfer`; the MPC service signs a Borsh-encoded payload committing to `0xBlacklisted` as recipient.
4. The relayer submits `finTransfer` on EVM with the signed payload.
5. `OmniBridge.finTransfer` reaches `IERC20(USDC).safeTransfer(0xBlacklisted, amount)` at line 351.
6. USDC's internal blacklist check causes `transfer` to revert.
7. The entire transaction reverts; `completedTransfers[nonce]` is never set.
8. Every subsequent retry with the same MPC-signed payload reverts identically — the signature cannot be reused with a different recipient.
9. The NEAR-side USDC is permanently burned; the EVM-side USDC held by the bridge is permanently inaccessible to the user with no protocol-level recovery path.

To reproduce locally: deploy a mock ERC-20 with a blacklist, register it as a non-bridge token in `OmniBridge`, blacklist a test address, produce a valid MPC signature over a payload targeting that address, and call `finTransfer` — observe the revert and confirm the nonce remains unconsumed across repeated calls.
