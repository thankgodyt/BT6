Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Callback Allows Emitting `InitTransfer` Events Without Locking Tokens — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` and then makes an external call to an untrusted ERC1155 token contract via `IERC1155.safeTransferFrom`. A malicious ERC1155 token can re-enter `initTransfer1155` during that call, incrementing the nonce again and emitting a second `InitTransfer` event with a fresh nonce — while zero tokens are ever locked. The NEAR side's `add_fin_transfer` deduplicates by `(origin_chain, origin_nonce)`, so two events with distinct nonces are both accepted, releasing bridged assets twice for a single (or zero) deposit.

## Finding Description

`initTransfer1155` follows this sequence: [1](#0-0) 

1. `currentOriginNonce += 1` — nonce incremented.
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — untrusted external call.
3. `emit BridgeTypes.InitTransfer(...)` — event emitted using the already-incremented nonce.

There is no `ReentrancyGuard` / `nonReentrant` modifier on `initTransfer1155`. [2](#0-1) 

The `onERC1155Received` hook checks `operator != address(this)`: [3](#0-2) 

This check only blocks direct ERC1155 sends to the bridge (where `operator` would be an external address). It does **not** block a malicious token's `safeTransferFrom` from calling `bridge.initTransfer1155(...)` directly during the callback. The malicious token can then satisfy `onERC1155Received` by passing `msg.sender` (the bridge) as the `operator` argument, which passes the check.

**Corrected re-entrant call sequence:**

1. Attacker calls `bridge.initTransfer1155(maliciousToken, ...)` — nonce → 1.
2. Bridge calls `maliciousToken.safeTransferFrom(attacker, bridge, ...)`.
3. Malicious token re-enters: calls `bridge.initTransfer1155(maliciousToken, ...)` — nonce → 2.
4. Bridge calls `maliciousToken.safeTransferFrom(maliciousToken, bridge, ...)` (inner).
5. Malicious token calls `bridge.onERC1155Received(msg.sender /*=bridge*/, ...)` — operator check passes.
6. Inner `initTransfer1155` emits `InitTransfer` with nonce 2. Zero tokens transferred.
7. Outer malicious `safeTransferFrom` calls `bridge.onERC1155Received(msg.sender /*=bridge*/, ...)` — passes.
8. Outer `initTransfer1155` emits `InitTransfer` with nonce 1. Zero tokens transferred.

Note: the submitted PoC passes `address(this)` (the malicious token) as `operator` to `onERC1155Received`, which would revert. The corrected version passes `msg.sender` (the bridge) as `operator`, which passes the check and makes the exploit functional.

On the NEAR side, `fin_transfer_callback` calls `process_fin_transfer_to_near`, which calls `add_fin_transfer`: [4](#0-3) 

The `TransferId` is keyed by `(origin_chain, origin_nonce)`. Since the two re-entrant events carry distinct nonces (1 and 2), `finalised_transfers.insert(transfer_id)` succeeds for both, and both are finalized independently. [5](#0-4) 

## Impact Explanation

**Critical.** An attacker emits N `InitTransfer` events (one per re-entrant depth) while locking zero ERC1155 tokens on the EVM side. The NEAR bridge treats each event as proof of a locked deposit and releases the corresponding bridged assets for each distinct nonce. This is direct theft of funds from the NEAR-side liquidity pool, bounded only by the NEAR-side token supply and EVM gas limits. This matches the allowed critical impact: *stealing or unauthorized minting of bridged funds* and *balance manipulation / escrow mis-accounting*.

## Likelihood Explanation

**High.** `initTransfer1155` is a public, permissionless function with no token whitelist. `logMetadata1155` is also permissionless, allowing any ERC1155 token to emit a `LogMetadata` event for NEAR-side registration. An attacker needs only to deploy a malicious ERC1155 contract, register it (permissionlessly), and call `initTransfer1155`. No admin access, privileged role, leaked key, or external dependency compromise is required. The attack is fully self-contained in a single EVM transaction.

## Recommendation

Add OpenZeppelin's `ReentrancyGuardUpgradeable` to `OmniBridge` and apply `nonReentrant` to `initTransfer1155` (and `initTransfer` as defense-in-depth):

```diff
 import {ReentrancyGuardUpgradeable} from
     "@openzeppelin/contracts-upgradeable/utils/ReentrancyGuardUpgradeable.sol";

 contract OmniBridge is
     UUPSUpgradeable,
     AccessControlUpgradeable,
     SelectivePausableUpgradable,
+    ReentrancyGuardUpgradeable,
     IERC1155Receiver
 {
     function initTransfer1155(...) external payable
+        nonReentrant
         whenNotPaused(PAUSED_INIT_TRANSFER) { ... }

     function initTransfer(...) external payable
+        nonReentrant
         whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
```

## Proof of Concept

Deploy a malicious ERC1155 whose `safeTransferFrom` re-enters `initTransfer1155`. The critical fix to the submitted PoC is passing `msg.sender` (the bridge) as `operator` to `onERC1155Received` so the operator check passes:

```solidity
function safeTransferFrom(
    address, address, uint256, uint256, bytes calldata
) external {
    if (reentrant) {
        reentrant = false;
        bridge.initTransfer1155(address(this), 1, 100, 0, 0, "attacker.near", "");
    }
    // Pass msg.sender (the bridge) as operator — satisfies operator == address(this) check
    IERC1155Receiver(msg.sender).onERC1155Received(
        msg.sender,      // operator = bridge ✓
        address(this),
        1, 100, ""
    );
}
```

**Steps:**
1. Deploy `MaliciousERC1155(bridgeAddress)`.
2. Call `bridge.logMetadata1155(malicious, 1)` to register the token (permissionless).
3. Wait for NEAR-side token registration via the `LogMetadata` event.
4. Call `bridge.initTransfer1155(malicious, 1, 100, 0, 0, "attacker.near", "")`.
5. Observe two `InitTransfer` events emitted (nonces 1 and 2) with zero tokens locked.
6. Submit both proofs to the NEAR bridge via `fin_transfer`; both are accepted and assets released twice.
