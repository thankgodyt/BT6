Audit Report

## Title
Unvalidated Destination Chain in `init_transfer` Causes Permanent Locking or Burning of User Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function validates only that the recipient chain is not `ChainKind::Near`, but performs no check that the destination chain has a registered factory in `self.factories` or a token mapping in `self.token_id_to_address`. Any user who initiates a transfer to a `ChainKind` variant with no registered factory will have their tokens immediately and irreversibly locked or burned, with no on-chain recovery path available.

## Finding Description
`ft_on_transfer` is the public entry point for NEAR-side bridge operations and is callable by any token holder via `ft_transfer_call`. It is not gated by `#[trusted_relayer]` — only by `#[pause]`. Execution reaches `init_transfer`, where the sole chain-level guard is:

```rust
// near/omni-bridge/src/lib.rs L531-534
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

No check is made against `self.factories` (the map of `ChainKind → registered factory address`). After this check, `init_transfer_internal` is called unconditionally, which:
1. Inserts the transfer into `self.pending_transfers` via `add_transfer_message`.
2. Calls `burn_tokens_if_needed` for deployed bridge tokens (irreversible destruction).
3. Calls `lock_tokens_if_needed` for native tokens (locked in contract).
4. Returns `U128(0)`, signaling to the NEP-141 token contract that zero tokens are refunded.

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

When a trusted relayer subsequently calls `sign_transfer` for this transfer, execution reaches:

```rust
// near/omni-bridge/src/lib.rs L462-469
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

Because no token address is registered for the unsupported destination chain, this panics. The MPC signing call is never made, `sign_transfer_callback` is never reached, and the transfer remains in `pending_transfers` indefinitely.

The only paths that remove a transfer from `pending_transfers` are:
- `sign_transfer_callback` — only on successful MPC signing with zero fee; unreachable here due to the panic.
- `claim_fee_callback` (line 1094) — requires a valid on-chain proof from the destination chain, which cannot exist for an unsupported chain.
- `submit_transfer_to_utxo_chain_connector` (btc.rs line 84) — only applicable to UTXO chains.

There is no `cancel_transfer` function in the contract.

## Impact Explanation
This directly causes permanent freezing of bridged funds: bridge tokens are burned (destroyed), and native tokens are locked in the contract with no recovery path accessible to the user or any unprivileged party. This matches the allowed critical impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."* The `ChainKind` enum includes variants such as `Fogo`, `Abs`, `HyperEvm`, and `Strk` that may have no factory registered at any given time, making this a realistic and repeatable loss scenario.

## Likelihood Explanation
The entry path is fully unprivileged. Any token holder can call `ft_transfer_call` on any NEP-141 token, specifying the bridge as receiver and an `InitTransferMsg` with a `recipient` on any `ChainKind` variant. The `ChainKind` enum is a small, fixed, publicly visible set of named variants. A user relying on a buggy front-end, or one who manually constructs a transaction to a chain that is enumerated but not yet deployed, will trigger this with no special role or key required. The condition is repeatable for every such transfer.

## Recommendation
Add a factory-existence check inside `init_transfer` before any tokens are locked or burned:

```rust
require!(
    self.factories.contains_key(&init_transfer_msg.get_destination_chain()),
    BridgeError::InvalidRecipientChain.as_ref()
);
```

Additionally, implement a `cancel_transfer` function that allows the original sender to reclaim locked tokens for transfers that have been pending beyond a configurable timeout, as defense-in-depth against any future cases where a transfer becomes permanently uncompletable.

## Proof of Concept
1. Assume `ChainKind::Fogo` has no factory registered in `self.factories` and no token address in `self.token_id_to_address`.
2. User calls `ft_transfer_call` on a NEAR NEP-141 token with `receiver_id` = omni-bridge contract and `msg` = `BridgeOnTransferMsg::InitTransfer(InitTransferMsg { recipient: OmniAddress::Fogo(<address>), fee: U128(0), native_token_fee: U128(0), ... })`.
3. `ft_on_transfer` → `init_transfer` executes. The only check (`recipient.get_chain() != ChainKind::Near`) passes.
4. `init_transfer_internal` is called: the transfer is inserted into `pending_transfers`, and the user's tokens are burned (if bridge token) or locked (if native token). The function returns `U128(0)`, so the NEP-141 contract retains all tokens.
5. A trusted relayer calls `sign_transfer` for this transfer ID.
6. `get_token_address(ChainKind::Fogo, token_id)` returns `None`; the contract panics with `FailedToGetTokenAddress`. The transfer remains in `pending_transfers` forever.
7. No `cancel_transfer` exists. `claim_fee_callback` requires a proof from `ChainKind::Fogo`, which cannot be produced. User's tokens are permanently lost.

A local unit test can reproduce steps 2–4 by calling `run_ft_on_transfer` with a `ChainKind` that has no entry in `contract.factories`, then asserting that `contract.pending_transfers` contains the transfer and the token balance is zero, and that a subsequent `sign_transfer` call panics.     fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
