### Title
Permissionless Refund Request Hijacking Allows Attacker to Redirect BTC Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
Any unprivileged NEAR account can call `request_refund` for any unfinalized deposit UTXO and supply an attacker-controlled `refund_address`. Because the refund request is keyed only by `{tx_id}@{vout}` (the UTXO identity, not the caller), the first caller wins and the BTC refund is permanently routed to their address. The legitimate depositor is then blocked from submitting their own request and has no permissionless way to cancel the attacker's entry.

### Finding Description

`request_refund` is a public, payable function callable by any NEAR account: [1](#0-0) 

Inside the Light-Client callback `request_refund_callback`, the refund request is stored keyed by `utxo_storage_key = "{tx_id}@{vout}"`: [2](#0-1) 

The only guard against a caller-supplied `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(msg_refund_address == &refund_address, ...);
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), **any caller may supply any BTC address as `refund_address`**. The callback then stores it without further validation: [4](#0-3) 

A duplicate-request guard prevents a second submission for the same UTXO: [5](#0-4) 

So whichever caller arrives first owns the `refund_address` slot permanently.

The `deposit_msg` needed to pass the deposit-address check is publicly observable: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`: [6](#0-5) 

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` (also permissionless) builds and signs a PSBT that pays `refund_request.refund_address` — the attacker's address: [7](#0-6) 

The legitimate depositor cannot call `reject_refund` because that path requires DAO/Operator role or proof that the UTXO was already verified via `verify_deposit`: [8](#0-7) 

### Impact Explanation

An attacker who races (or simply acts first) on an unfinalized deposit UTXO can permanently redirect the BTC refund to their own Bitcoin address. The victim's BTC is lost unless the DAO/Operator actively monitors and rejects the malicious request within `unsafe_refund_timelock_sec`. The victim has no self-service remedy.

This matches: **Medium — attacker-triggered temporary locking of bridged funds** (escalating to Critical theft if the DAO/Operator does not intervene in time).

### Likelihood Explanation

- `deposit_msg` is publicly emitted on every `get_user_deposit_address` call.
- Bitcoin deposits are publicly visible on-chain; an attacker can monitor for unfinalized deposits to known bridge addresses.
- `request_refund` requires only a small NEAR storage deposit (anti-spam fee), not any privileged role.
- The victim may not even know they need to call `request_refund`, giving the attacker ample time to act first.
- The only mitigation is DAO/Operator vigilance during `unsafe_refund_timelock_sec`, which is not guaranteed.

### Recommendation

Bind the `refund_address` to the caller at request time when `deposit_msg.refund_address` is `None`. Store `requester: AccountId` in `RefundRequest` and, in `execute_refund`, require `env::predecessor_account_id() == refund_request.requester` (or a privileged role). Alternatively, require that `deposit_msg.refund_address` always be set (non-optional) so the BTC destination is committed before the deposit is made, eliminating the caller-supplied address path entirely.

### Proof of Concept

1. Victim calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The `LogDepositAddress` event reveals `deposit_msg` publicly.
2. Victim sends BTC to the derived deposit address. The deposit is never finalized (e.g., bridge paused, wrong amount).
3. Attacker observes the Bitcoin deposit and calls:
   ```
   request_refund(
       deposit_msg,           // copied from the public event
       attacker_btc_address,  // attacker's own BTC address
       tx_bytes, vout, proof, None
   )
   ```
   attaching the required NEAR storage deposit.
4. `request_refund_callback` runs: deposit-address check passes (same `deposit_msg`), `refund_address` check is skipped (`deposit_msg.refund_address` is `None`), and `RefundRequest { refund_address: attacker_btc_address }` is stored under `utxo_storage_key`.
5. Victim's subsequent `request_refund` call fails: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec`, attacker (or anyone) calls `execute_refund(utxo_storage_key, None)`.
7. The bridge constructs and MPC-signs a PSBT paying `attacker_btc_address`. Victim's BTC is gone.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
