### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold Without Enforcing Unit Consistency - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares a `PerasVoteStake` (`Rational`) against the `perasQuorumStakeThreshold` (also `Rational`) without enforcing that both values are expressed in the same units. The code itself documents this as an unresolved assumption. If `PerasVoteStakeDistr` is populated with absolute lovelace-denominated stake values (the natural output of the ledger), while `perasQuorumStakeThreshold` is a relative fraction (e.g., `3/4`), the comparison is semantically invalid: any voter whose absolute stake exceeds `3/4` (i.e., virtually every voter) would single-handedly satisfy the quorum check, enabling unauthorized certificate forging and chain-selection manipulation.

---

### Finding Description

`stakeAboveThreshold` is the sole gate for Peras quorum decisions:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
--
-- So, for now you can consider this 'Rational' as the best approximation we
-- have at the moment of the concrete type for a relative vote stake that can be
-- compared to the quorum threshold value (also currently a 'Rational').
newtype PerasVoteStake = PerasVoteStake
  { unPerasVoteStake :: Rational }
``` [1](#0-0)

The `validatePerasVote` implementation assigns the stake value directly from `PerasVoteStakeDistr` into `vpvVoteStake` with no normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =

``` [6](#0-5) 

The `PerasVoteStakeDistr` type is a plain `Map PerasVoterId PerasVoteStake` with no unit annotation: [7](#0-6) 

The analog to the original report is exact: the original bug enforced `requireAssetAmountValidForTokenBridge` for ERC-20 tokens but not for native assets. Here, normalization is required for `PerasVoteStake` before calling `stakeAboveThreshold`, but no normalization is enforced at any call site — the constraint is documented as a TODO assumption, not a runtime invariant.

### Impact Explanation

If `PerasVoteStakeDistr` is populated from the ledger with absolute lovelace values (e.g., a voter holding `500_000_000_000` lovelace), and `perasQuorumStakeThreshold` is `3/4`, then `stakeAboveThreshold` evaluates `500_000_000_000 >= 3/4 + 2/100`, which is trivially `True`. A single vote from any non-trivial stake holder would satisfy quorum, allowing:

- **Unauthorized Peras certificate forging**: a certificate is produced for an attacker-chosen block with only one vote.
- **Chain-selection manipulation**: the forged certificate boosts the attacker's block by `perasWeight` (default 15), causing honest nodes to prefer the attacker's chain over the canonical chain.

This maps to the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized block, vote, or certificate acceptance."*

---

### Likelihood Explanation

The vulnerability is triggered the moment `PerasVoteStakeDistr` is populated from the ledger using absolute stake values — the natural and expected source. No key compromise, stake majority, or privileged access is required. Any node that receives a crafted `PerasVote` from an unprivileged peer and evaluates it against an absolute-valued distribution will incorrectly grant quorum. The code comment explicitly acknowledges the unresolved unit question, confirming this is a known open design gap rather than an intentional choice.

---

### Recommendation

Enforce normalization at the boundary where `PerasVoteStakeDistr` is constructed from the ledger. Either:

1. **Normalize at construction**: divide each voter's absolute stake by the total active stake when building `PerasVoteStakeDistr`, so all `PerasVoteStake` values are relative fractions in `[0, 1]`.
2. **Normalize inside `stakeAboveThreshold`**: change the signature to accept the total stake distribution and perform normalization internally before comparing against the threshold, removing the implicit unit assumption.
3. **Use a newtype with phantom units**: introduce distinct newtypes for absolute and relative stake to make unit mismatches a compile-time error.

The TODO comment at lines 155–161 of `SupportsPeras.hs` should be resolved before Peras certificate validation is connected to live ledger data.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Obtain a voter identity with any non-trivial absolute stake (e.g., 1 ADA = `1_000_000` lovelace).
2. Populate `PerasVoteStakeDistr` from the ledger using raw lovelace values (absolute units).
3. Submit a `PerasVote` for an attacker-controlled block in round `R`.
4. `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake (1_000_000 % 1)`.
5. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake (1_000_000 % 1))`.
6. The check evaluates `1_000_000 >= 3/4 + 2/100` → `True`.
7. `forgePerasCert` produces a certificate boosting the attacker's block.
8. Honest nodes receiving this certificate apply the `perasWeight` boost (15 blocks) to the attacker's chain, causing them to prefer it over the canonical chain.
