### Title
Degenerate `validatePerasCert` Bypasses Peras Certificate Validation, Enabling Unprivileged Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass ships a degenerate global instance in which `validatePerasCert` unconditionally returns `Right` — accepting every inbound certificate without any cryptographic or structural check. This stub is wired directly into the production `hPerasCertDiffusionClient` handler. Because accepted certificates are stored in the `PerasCertDB` and immediately feed the `PerasWeightSnapshot` used by chain selection, any unprivileged peer that can speak the `PerasCertDiffusion` mini-protocol can inject arbitrary certificates that boost attacker-chosen blocks, potentially causing an honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — degenerate `validatePerasCert`**

`BlockSupportsPeras` is a typeclass whose intended contract is to validate Peras certificates before they are stored. The file contains a single catch-all instance for every `StandardHash blk`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every certificate, regardless of its content, is wrapped in `Right` and assigned the full `perasWeight` boost. No signature, committee membership, round-number range, or boosted-block validity check is performed.

**Production wiring — `makePerasCertPoolWriterFromChainDB`**

The pool writer used in the live node calls `validatePerasCert mkPerasParams` directly:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions the results of `validateCert` into errors and successes. Because `validatePerasCert` never produces an error, the `(errs, _)` branch is never taken and every certificate is forwarded to `addCert`: [3](#0-2) 

**Handler registration — `mkHandlers`**

This writer is registered unconditionally in the node-to-node handler record:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain-selection impact — `chainSelSync` and `PerasWeightSnapshot`**

Once a certificate is stored in the `PerasCertDB`, `chainSelSync` is triggered for the boosted block. If that block is on a fork, chain selection is re-run with the updated `PerasWeightSnapshot`: [5](#0-4) 

`WeightedSelectView` compares chains by `wsvTotalWeight = BlockNo + wsvWeightBoost`. An injected certificate with a large `vpcCertBoost` (set to `perasWeight params` by the degenerate instance) can make a fork appear heavier than the honest chain: [6](#0-5) 

The `PerasCertDB` is initialised and its weight snapshot is consumed at startup and on every cert addition: [7](#0-6) 

---

### Impact Explanation

**High — Chain selection manipulation by an unprivileged peer.**

An attacker who can speak the `PerasCertDiffusion` mini-protocol sends a crafted `PerasCert` whose `pcCertBoostedBlock` points to a block on an adversarial fork. Because `validatePerasCert` always returns `Right`, the certificate is stored without any check. The `PerasWeightSnapshot` is updated, and `chainSelSync` re-runs chain selection for the boosted block. If the fork's boosted weight exceeds the honest chain's weight, the node switches to the fork — an honest node is made to prefer a non-canonical chain beyond the intended security assumptions of Ouroboros.

This matches the allowed scope: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

**High.** The `hPerasCertDiffusionClient` handler is registered unconditionally in `mkHandlers` for every node instance. The degenerate `validatePerasCert` is the only instance in scope (it is a catch-all `instance StandardHash blk =>`). No feature flag or version gate prevents a peer from sending certificates once the `PerasCertDiffusion` protocol is negotiated. The attack requires only the ability to connect as a node-to-node peer and send a well-formed CBOR-encoded `PerasCert` message — no keys, stake, or privileged access are needed.

---

### Recommendation

Replace the degenerate stub with a real implementation of `validatePerasCert` that checks:

1. The certificate's round number is within the current Peras window.
2. The boosted block exists and is within the valid age range (`PerasBlockMinSlots`, `PerasCertMaxRounds`).
3. The certificate carries a valid aggregate signature from a quorum of eligible committee members, verified against the current stake distribution.

Until the real implementation is ready, the `hPerasCertDiffusionClient` handler should be gated behind an explicit feature flag so that nodes not running Peras do not accept inbound certificates at all. The analogous issue for `PerasVoteStakeDistr mempty` (which causes all votes to be silently rejected) should be resolved at the same time. [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
