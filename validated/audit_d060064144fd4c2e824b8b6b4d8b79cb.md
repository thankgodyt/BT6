Audit Report

## Title
Non-Trusted-Relayer Fee Recipients Are Permanently Blocked from Claiming Earned Fees - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `claim_fee` function is gated by `#[trusted_relayer]`, requiring the caller to be an active trusted relayer, DAO, or UnrestrictedRelayer. Simultaneously, `claim_fee_callback` enforces `fee_recipient == predecessor_account_id`. Because `sign_transfer` accepts any `AccountId` as `fee_recipient` with no validation that it is a trusted relayer, these two conditions become mutually exclusive whenever `fee_recipient` is not an active trusted relayer, permanently locking the fee in the bridge with no recovery path.

## Finding Description
In `sign_transfer` (line 447–500), a trusted relayer freely sets `fee_recipient: Option<AccountId>` which is embedded in `TransferMessagePayload`, MPC-signed, and recorded in the foreign chain's `FinTransfer` event. To claim the fee, a caller must simultaneously satisfy:

- **Condition 1** (`claim_fee`, line 1055): `#[trusted_relayer]` — caller must be an active trusted relayer, DAO, or UnrestrictedRelayer.
- **Condition 2** (`claim_fee_callback`, lines 1083–1086): `require!(fee_recipient == *predecessor_account_id)` — caller must be the exact `fee_recipient` embedded in the proof.

When `fee_recipient` is not an active trusted relayer:
- The `fee_recipient` account fails Condition 1 and cannot enter `claim_fee`.
- Any active trusted relayer fails Condition 2 because they are not the `fee_recipient`.

No account can satisfy both conditions. `remove_transfer_message` at line 1094 is never reached, so the `pending_transfers` entry persists indefinitely and the fee is permanently locked. No timeout, cancellation, or DAO recovery path exists for `pending_transfers`.

## Impact Explanation
This constitutes permanent freezing of bridged funds (fee escrow) and fee mis-accounting in the bridge, matching the allowed Critical impact: *"Balance manipulation, escrow mis-accounting, fee mis-accounting … that changes user or protocol balances."* The locked tokens are not yet minted or transferred on NEAR — they are gated behind the `claim_fee_callback` execution path that is never reached — so `transfer_token_as_dao` cannot recover them.

## Likelihood Explanation
Two realistic, externally-reachable paths exist through the relayer flow:

**Path A:** A trusted relayer calls `sign_transfer` with `fee_recipient = Some(treasury.near)` (a non-relayer account such as a treasury, partner, or custom account). The `fee_recipient` parameter has no validation requiring it to be a trusted relayer. This is a natural and expected use case.

**Path B:** A trusted relayer calls `sign_transfer` with `fee_recipient = Some(self)`. After the transfer is finalized on the foreign chain, the DAO calls `reject_relayer_application`, revoking the relayer's status. The relayer's `is_trusted_relayer` check now returns false, permanently blocking `claim_fee`. DAO revocation is a legitimate, documented protocol action.

Both paths are reachable through normal relayer flows without any malicious intent.

## Recommendation
Remove the `#[trusted_relayer]` guard from `claim_fee`. The function's security is already fully enforced by:
1. `verify_proof` — cryptographically validates the foreign-chain proof.
2. `require!(fee_recipient == *predecessor_account_id)` — ensures only the legitimate fee recipient can claim.
3. `require!(self.factories.get(...) == Some(fin_transfer.emitter_address))` — validates the emitting factory.

The `#[trusted_relayer]` guard is redundant for security and is the sole cause of the permanent lockup.

## Proof of Concept
**Scenario A (non-relayer fee_recipient):**
1. Trusted relayer A calls `sign_transfer(transfer_id, fee_recipient=Some("treasury.near"), fee=Some(fee))`.
2. MPC signs the payload with `fee_recipient = treasury.near`.
3. Transfer is finalized on the EVM chain; `FinTransfer` event records `fee_recipient = treasury.near`.
4. `treasury.near` calls `claim_fee` → reverts: not a trusted relayer (Condition 1 fails).
5. Trusted relayer A calls `claim_fee` → reverts: `fee_recipient (treasury.near) != predecessor (A)` (Condition 2 fails).
6. Fee is permanently locked; `pending_transfers` entry persists indefinitely.

**Scenario B (revoked relayer):**
1. Trusted relayer A calls `sign_transfer(transfer_id, fee_recipient=Some(A), fee=Some(fee))`.
2. Transfer finalized on foreign chain with `fee_recipient = A`.
3. DAO calls `reject_relayer_application(A)` — A's stake is slashed, `is_trusted_relayer(A)` returns false.
4. A calls `claim_fee` → reverts at `#[trusted_relayer]` guard (Condition 1 fails).
5. Fee is permanently locked.

**Test plan:** Deploy the bridge contract on a local NEAR sandbox. Register a trusted relayer, initiate a NEAR→EVM transfer, call `sign_transfer` with a non-relayer `fee_recipient`, mock the prover to return a valid `FinTransfer` proof, and assert that both `claim_fee` calls (from `fee_recipient` and from the trusted relayer) revert, and that the `pending_transfers` entry remains after both attempts.
