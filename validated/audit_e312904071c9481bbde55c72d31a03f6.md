### Title
Peras Quorum Check Unit Mismatch in `stakeAboveThreshold` Allows Single-Voter Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value — which is sourced from the ledger's absolute stake distribution — against a relative/normalized quorum threshold (`3/4`). Because the two operands are in incompatible units (absolute lovelace vs. a fraction in `[0,1]`), the check is almost always trivially satisfied by a single vote, bypassing the Peras quorum requirement entirely.

### Finding Description

`stakeAboveThreshold` performs the comparison:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake          -- sourced from ledger stake distr
  quorumThreshold = unPerasQuorumStakeThreshold
                      (perasQuorumStakeThreshold params)   -- = 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin
                      (perasQuorumStakeThresholdSafetyMargin params)  -- = 2/100
``` [1](#0-0) 

The code itself documents the mismatch in a TODO comment immediately above the function:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` assigned to a validated vote is taken directly from `PerasVoteStakeDistr` without normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

`PerasVoteStakeDistr` is populated from the ledger's absolute stake distribution (in lovelace). The companion note on `PerasVoteStake` confirms no normalization path exists yet:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [4](#0-3) 

The default `PerasParams` sets the quorum threshold to `3/4` (a normalized fraction):

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
``` [5](#0-4) 

Any real stake pool's absolute lovelace stake (e.g., `10^15` for 1 billion ADA) is astronomically larger than `3/4 + 2/100 = 0.77`. The comparison `stake >= 0.77` is therefore trivially `True` for any single vote from any non-trivial stake pool.

`stakeAboveThreshold` is the sole quorum gate in `votesReachQuorum`, which is the only check before `forgePerasCert` is called:

```haskell
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5) 

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
``` [7](#0-6) 

The production inbound vote path in `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` calls `validatePerasVote mkPerasParams sd vote` with the raw ledger stake distribution `sd`, then immediately adds the validated vote to the database where it triggers the quorum check: [8](#0-7) 

### Impact Explanation

A single Peras vote from any stake pool with non-trivial absolute stake causes `stakeAboveThreshold` to return `True`, immediately satisfying the quorum check. This allows a single unprivileged peer to unilaterally forge a `ValidatedPerasCert` for any block of their choosing. Peras certificates boost a block's chain-selection weight by `perasWeight` (default: 15 block-equivalents). An adversary can therefore make honest nodes prefer an adversarially-chosen chain, constituting a **bypass of Peras certificate/quorum validation** and a **chain-selection bug** that lets an unprivileged peer cause honest nodes to adopt a non-canonical chain.

### Likelihood Explanation

The entry path is a standard Peras vote mini-protocol message from any peer. No special privileges are required beyond operating a stake pool (which is permissionless). The `PerasVoteStakeDistr` is read directly from the ledger's absolute stake distribution with no normalization step anywhere in the production code path. Any stake pool with lovelace stake > 0.77 (i.e., every real stake pool) triggers the bypass on their first vote.

### Recommendation

Normalize `PerasVoteStake` to a relative fraction of total committee stake before calling `stakeAboveThreshold`, or change `stakeAboveThreshold` to accept the total stake distribution and perform normalization internally. The quorum threshold in `PerasParams` must be expressed in the same unit as the vote stake being compared. Until normalization is implemented, the quorum check provides no security guarantee.

### Proof of Concept

1. A peer holds a stake pool with 1 billion ADA (absolute stake = `10^15` lovelace).
2. The node's `PerasVoteStakeDistr` maps this pool's `PerasVoterId` to `PerasVoteStake (10^15 % 1)`.
3. The peer sends a single `PerasVote` for any block `B` in round `r`.
4. `validatePerasVote mkPerasParams stakeDistr vote` returns `Right (ValidatedPerasVote { vpvVoteStake = PerasVoteStake (10^15 % 1) })`.
5. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake (10^15 % 1))`.
6. The check evaluates `10^15 >= 3/4 + 2/100` → `True`.
7. `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting block `B` by weight 15.
8. Chain selection now prefers any chain containing `B` over chains of equal length without the boost, regardless of whether `B` is on the honest chain.
