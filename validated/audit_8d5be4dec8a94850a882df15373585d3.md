Audit Report

## Title
`init_transfer` Lacks Normalization Guard, Enabling Permanent Token Freezing - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks tokens after only checking `fee < amount`, without verifying that `normalize_amount(amount - fee) > 0`. `sign_transfer` applies floor-division normalization and rejects zero-valued transfers. For any token where `origin_decimals > decimals`, a user can lock tokens whose post-normalization value is zero, with no recovery path available.

## Finding Description
`sign_transfer` computes the destination amount via floor division and enforces a non-zero check:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` performs `amount / 10^(origin_decimals - decimals)` (floor division):

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The docstring at L2781-2783 explicitly acknowledges: *"When fee = 0, dust stays locked/burned."* However, the guard in `init_transfer` only checks:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

Tokens are locked (or burned for bridge tokens) before any normalization check. Once stored, the `TransferMessage` has no user-accessible removal path: `remove_transfer_message` is only reachable via `claim_fee_callback` (requires a valid on-chain `FinTransfer` proof) and `submit_transfer_to_utxo_chain_connector` (BTC/Zcash path only). `update_transfer_fee` only permits fee increases, which worsens the situation by reducing `amount - fee` further.

## Impact Explanation
Any user who initiates a NEAR → EVM (or other destination) transfer where `(amount - fee) < 10^(origin_decimals - decimals)` will have their tokens permanently frozen in the bridge contract. This directly matches the allowed critical impact: **permanent freezing of bridged funds**. No attacker is needed — a user acting in good faith with a small transfer amount triggers the freeze themselves.

## Likelihood Explanation
The condition is reachable by any unprivileged user via the standard `ft_transfer_call` entry point. For a 6-decimal gap (e.g., a 24-decimal NEAR token bridged to an 18-decimal EVM chain), any transfer of fewer than 1,000,000 base units after fee deduction triggers the freeze. No special access, coordination, or external dependency is required.

## Recommendation
Add the normalization guard inside `init_transfer` (or `init_transfer_internal`) before tokens are locked:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, implement a user-facing cancel/refund function that removes the `TransferMessage` and returns locked tokens when no MPC signature has been produced for the transfer.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = 10⁶).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes: `0 < 500_000` ✓; tokens are locked in the contract.
4. Relayer calls `sign_transfer`.
5. `normalize_amount(500_000 - 0) = 500_000 / 1_000_000 = 0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics.
7. `TransferMessage` remains in storage permanently; 500,000 tokens are frozen with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
