### Title
Zcash Orchard Amount Causes Unchecked Subtraction Panic in `check_withdraw_psbt` — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

An unprivileged bridge user can craft a Zcash withdrawal PSBT containing an Orchard bundle whose recovered note value exceeds the sum of the transparent UTXO inputs. This causes an arithmetic underflow panic at line 238 of `psbt.rs`. With `overflow-checks = true` in the release profile, the result is a panic/abort on the Zcash withdrawal path. NEAR transaction atomicity rolls back all state changes (including UTXO removal), and the NEP-141 refund mechanism returns the user's nBTC. There is no permanent fund loss, but the panic is publicly reachable and constitutes a DoS fault on the production Zcash withdrawal path.

---

### Finding Description

**Vulnerable line** — `contracts/satoshi-bridge/src/psbt.rs:238`:

```rust
let gas_fee = total_input_amount - total_output_amount;
```

`total_input_amount` is the sum of the vutxo balances (transparent inputs only). [1](#0-0) 

`total_output_amount` is built from two sources:
1. Transparent outputs (accumulated in the loop at lines 192–215).
2. The return value of `psbt.add_extra_outputs()` added at line 218. [2](#0-1) 

In the Zcash `PsbtWrapper`, `add_extra_outputs` returns `orchard.amount()` — the note value recovered from the Orchard bundle using the bridge's all-zeros OVK: [3](#0-2) 

The Orchard amount is sourced from `ParsedOrchardBundle::amount()`, which is the `u64` value recovered from the bundle's single action: [4](#0-3) 

**No bound check exists between lines 218 and 238.** The only Orchard-specific validation (`validate_orchard_bundle`, called via `check_psbt_chain_specific`) is invoked at line 260 — *after* the underflow: [5](#0-4) 

The bridge OVK is hardcoded to all-zeros and is publicly known: [6](#0-5) 

An attacker can therefore generate a valid Orchard bundle (with a valid Halo2 proof) encoding any note value they choose, including one that exceeds `total_input_amount`.

**Call path (Zcash feature enabled):**

```
ft_on_transfer
  → ft_on_transfer_withdraw_chain_specific
    → cross-contract call (get_last_block_height)
      → ft_on_transfer_callback          [zcash_utils/contract_methods.rs:110]
        → create_btc_pending_info        [token_receiver.rs:71]
          → generate_vutxos              [psbt.rs:266]  ← UTXOs removed here
          → check_withdraw_psbt_valid    [psbt.rs:10]
            → check_withdraw_psbt        [psbt.rs:164]
              → line 218: total_output_amount += orchard.amount()
              → line 238: gas_fee = total_input_amount - total_output_amount  ← PANIC
``` [7](#0-6)

### Impact Explanation

**`overflow-checks = true` is set in the release profile:** [8](#0-7) 

This means the subtraction panics rather than wrapping silently. The "critical" scenario (silent wrap producing a near-zero `gas_fee` that passes the range check) does **not** apply in the current build configuration.

The actual impact is:
- **Panic/abort** on the Zcash withdrawal path for any withdrawal where the attacker supplies an Orchard bundle with `amount > total_input_amount - transparent_output_sum`.
- **NEAR atomicity** rolls back the UTXO removal performed by `generate_vutxos` at line 79 of `token_receiver.rs`, so UTXOs are **not** permanently locked.
- **NEP-141 `ft_resolve_transfer`** handles the failed promise and refunds the attacker's nBTC.
- Net result: a publicly reachable panic-driven DoS fault on the production Zcash withdrawal path, with no permanent fund loss.

This matches the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

---

### Likelihood Explanation

- The bridge OVK is all-zeros and public, so any user can generate a valid Orchard bundle with an arbitrary note value.
- The Zcash feature must be enabled (it is a compile-time feature flag, not a runtime guard).
- No privileged role is required; the entry point is the public `ft_on_transfer` NEP-141 callback.
- The attacker only needs to supply a UTXO they own and an Orchard bundle with `amount > utxo_value`.

---

### Recommendation

Insert a bounds check immediately after line 218, before the subtraction at line 238:

```rust
total_output_amount += psbt.add_extra_outputs(&mut actual_received_amounts);

require!(
    total_output_amount <= total_input_amount,
    format!(
        "Total output amount ({}) exceeds total input amount ({})",
        total_output_amount, total_input_amount
    )
);

let gas_fee = total_input_amount - total_output_amount;
```

This converts the panic into a clean, user-visible `require!` rejection before any arithmetic is attempted. [9](#0-8) 

---

### Proof of Concept

1. Alice deposits a UTXO worth 500,000 zatoshis into the bridge.
2. Alice generates a valid Orchard bundle (using the public all-zeros OVK) with `amount = 500,001`.
3. Alice calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message specifying:
   - `input`: her UTXO
   - `output`: empty (shielded-only address)
   - `chain_specific_data.orchard_bundle_bytes`: the crafted bundle
4. Inside `ft_on_transfer_callback` → `create_btc_pending_info` → `check_withdraw_psbt`:
   - `total_input_amount = 500_000`
   - `total_output_amount = 0 + 500_001 = 500_001`
   - Line 238: `500_000u128 - 500_001u128` → **panic** (overflow-checks = true)
5. NEAR rolls back the UTXO removal; `ft_resolve_transfer` refunds Alice's nBTC.
6. Assert: the NEAR transaction receipt shows a panic; UTXOs are unchanged; Alice's nBTC balance is unchanged.
