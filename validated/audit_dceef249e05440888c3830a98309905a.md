### Title
Unprivileged caller triggers panic in `generate_public_key` when `chain_signatures_root_public_key` is `None`, wasting attached deposit — (`contracts/satoshi-bridge/src/chain_signature.rs` / `kdf.rs`)

---

### Summary

`sign_btc_transaction` is a public, payable entry point with no guard ensuring `chain_signatures_root_public_key` is populated. The call chain reaches `generate_public_key`, which calls `.expect("Missing chain_signatures_root_public_key")` on an `Option`. If the root key has not been synced (or the sync callback failed), any caller with a valid `btc_pending_sign_id` triggers a contract panic, losing their attached NEAR deposit.

---

### Finding Description

`sign_btc_transaction` is declared `#[payable]` with only a `#[pause]` guard — no role restriction prevents an unprivileged caller from invoking it: [1](#0-0) 

It unconditionally delegates to `internal_sign_btc_transaction`, which iterates over all vUTXOs and calls `generate_btc_public_key` for each: [2](#0-1) 

`generate_btc_public_key` calls `generate_public_key`, which performs an unconditional `.expect()` on the `Option<PublicKey>` field: [3](#0-2) 

`chain_signatures_root_public_key` is declared as `Option<PublicKey>` and starts as `None`: [4](#0-3) 

It is only populated inside `sync_root_public_key_callback`, which is a `#[private]` async callback that can silently return `false` on failure, leaving the field `None`: [5](#0-4) 

There is no pre-flight check anywhere in `sign_btc_transaction` or `internal_sign_btc_transaction` that asserts the root key is `Some` before proceeding.

---

### Impact Explanation

Any caller who holds (or can observe) a valid `btc_pending_sign_id` — which is created as part of the normal user-facing withdrawal flow — can call `sign_btc_transaction` while the root key is absent. The NEAR runtime aborts the transaction with a panic, and the caller's attached yoctoNEAR deposit is not refunded. The signing attempt is permanently stuck until an operator re-syncs the root key. This matches the **Low** allowed impact: *publicly reachable panic-driven fault in production bridge/token paths without direct theft*.

---

### Likelihood Explanation

Two realistic triggers exist:

1. **Race at deployment**: the contract is deployed and a withdrawal is initiated before `sync_chain_signatures_root_public_key` completes successfully.
2. **Callback failure**: `sync_root_public_key_callback` returns `false` (e.g., the MPC contract is temporarily unavailable), leaving `chain_signatures_root_public_key = None`; subsequent signing calls panic until the operator re-syncs.

Neither scenario requires any privileged access — the attacker only needs a valid pending-sign ID, which is observable on-chain.

---

### Recommendation

Add an explicit guard at the top of `internal_sign_btc_transaction` (or inside `sign_btc_transaction`) before the `generate_btc_public_key` loop:

```rust
require!(
    self.internal_config().chain_signatures_root_public_key.is_some(),
    "chain_signatures_root_public_key not initialized"
);
```

This converts the panic into a clean, refundable `require!` failure and makes the missing-key state explicit to callers.

---

### Proof of Concept

1. Deploy the contract with `chain_signatures_root_public_key: None` (do not call `sync_chain_signatures_root_public_key`).
2. Initiate a withdrawal to create a `BTCPendingInfo` entry with a known `btc_pending_sign_id`.
3. Call `sign_btc_transaction(btc_pending_sign_id, 0, 0)` with any attached deposit.
4. Observe the transaction aborts with `"Missing chain_signatures_root_public_key"` and the deposit is not returned.
