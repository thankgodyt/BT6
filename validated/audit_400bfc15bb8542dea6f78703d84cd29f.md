### Title
Updating `nbtc_account_id` via `update_config` Permanently Breaks In-Flight Withdrawals and `claim_lost_found` - (File: `contracts/satoshi-bridge/src/api/management.rs`)

---

### Summary

The DAO can update `nbtc_account_id` at any time via `update_config`. Every burn and nBTC transfer call reads `nbtc_account_id` from the live config at execution time, not at withdrawal-initiation time. If the config is changed while withdrawals are in-flight — after the user's nBTC has already been transferred to the bridge on the **old** contract — all subsequent burn calls are directed to the **new** contract where the bridge holds zero balance. The burns fail permanently, leaving the bridge under-collateralized (BTC already sent, nBTC never burned) and the pending withdrawal stuck. The same config-read-at-call-time pattern also breaks `claim_lost_found`.

---

### Finding Description

**Root cause — `nbtc_account_id` is mutable and read at call time:**

`update_config` accepts a `ConfigUpdate` that includes `nbtc_account_id` and applies it immediately with no guard against in-flight operations:

```rust
// contracts/satoshi-bridge/src/api/management.rs
#[payable]
#[access_control_any(roles(Role::DAO))]
pub fn update_config(&mut self, update: ConfigUpdate) {
    assert_one_yocto();
    update.apply(self.internal_mut_config());   // ← overwrites nbtc_account_id instantly
}
```

```rust
// contracts/satoshi-bridge/src/config.rs
pub struct ConfigUpdate {
    pub nbtc_account_id: Option<AccountId>,   // ← freely settable
    ...
}
impl ConfigUpdate {
    pub fn apply(self, config: &mut Config) {
        set_if_some!(nbtc_account_id);         // ← no in-flight check
        ...
    }
}
```

**Burn path reads config at call time:**

```rust
// contracts/satoshi-bridge/src/nbtc/burn.rs
pub fn verify_withdraw_burn_promise(&self, tx_id: String) -> Promise {
    let config = self.internal_config();
    ext_nbtc::ext(config.nbtc_account_id.clone())   // ← current config, not initiation-time
        .burn(...)
        .then(Self::ext(...).verify_withdraw_burn_callback(...))
}
```

**Transfer path reads config at call time:**

```rust
// contracts/satoshi-bridge/src/token_transfer.rs
pub fn internal_transfer_nbtc(&self, account_id: &AccountId, amount: u128) -> Promise {
    ext_ft_core::ext(self.internal_config().nbtc_account_id.clone())  // ← current config
        .ft_transfer(account_id.clone(), amount.into(), None)
        .then(Self::ext(...).transfer_nbtc_callback(...))
}
```

**`claim_lost_found` also uses the live config:**

```rust
// contracts/satoshi-bridge/src/api/bridge.rs
pub fn claim_lost_found(&mut self) -> Promise {
    let amount = self.data_mut().lost_found.remove(&account_id)...;
    self.internal_transfer_nbtc(&account_id, amount)   // ← reads nbtc_account_id at call time
}
```

**The nBTC `burn` function burns from the bridge's own balance on whichever contract it is called on:**

```rust
// contracts/nbtc/src/lib.rs
pub fn burn(&mut self, burn_account_id: AccountId, burn_amount: U128, ...) {
    self.assert_bridge();
    self.token.internal_withdraw(&self.bridge_id, burn_amount.into());  // ← bridge balance on THIS contract
    ...
}
```

The bridge's nBTC balance exists only on the **old** contract (where the user's `ft_transfer_call` deposited it). Calling `burn` on the **new** contract panics or fails because the bridge has zero balance there.

---

### Impact Explanation

**Scenario A — In-flight withdrawal broken:**

1. User calls `nbtc.ft_transfer_call(bridge, amount, withdraw_msg)` → nBTC lands in bridge balance on **old** nBTC contract; `BTCPendingInfo` is created.
2. Bridge signs and broadcasts the BTC transaction (BTC is now en route to the user).
3. DAO calls `update_config({ nbtc_account_id: new_nbtc })` — config is overwritten.
4. Relayer calls `verify_withdraw` → `verify_withdraw_burn_promise` → `burn` is called on **new** nBTC contract → fails (bridge has 0 balance there).
5. `verify_withdraw_burn_callback` receives `is_success = false` → pending info is moved back to `PendingVerify` stage.
6. The BTC has already been sent. The nBTC is permanently stuck in the bridge's balance on the old contract and can never be burned.
7. The bridge is under-collateralized: total nBTC supply exceeds BTC backing.

**Scenario B — `claim_lost_found` broken:**

If a `cancel_withdraw` or failed transfer puts nBTC into `lost_found`, the user calls `claim_lost_found`. This calls `internal_transfer_nbtc` with the current (new) `nbtc_account_id`. The bridge has no balance on the new contract → transfer fails → `transfer_nbtc_callback` re-inserts the amount into `lost_found`. The user is permanently unable to recover their nBTC.

Both scenarios result in stuck bridge state and permanent under-collateralization — matching the allowed impact: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

The DAO is expected to update `nbtc_account_id` during token migrations (the repo includes a `migrate/` directory and `upgrade_and_migrate` flow). Any such migration performed while withdrawals are pending — a realistic operational scenario — triggers this bug. No attacker action is required; the DAO acting in good faith is sufficient.

---

### Recommendation

1. **Guard `nbtc_account_id` updates against in-flight operations.** Before applying a new `nbtc_account_id`, require that `btc_pending_infos` is empty (no in-flight withdrawals or refunds) and `lost_found` is empty.
2. **Alternatively, store `nbtc_account_id` inside `BTCPendingInfo` at creation time** so each pending operation always burns against the contract it was initiated with, regardless of subsequent config changes.
3. **Emit a dedicated event** when `nbtc_account_id` is changed so off-chain monitors can pause relaying until in-flight operations drain.

---

### Proof of Concept

```
1. Alice calls nbtc_old.ft_transfer_call(bridge, 100_000, withdraw_msg)
   → bridge balance on nbtc_old += 100_000
   → BTCPendingInfo { burn_amount: 100_000, ... } created

2. Bridge signs BTC PSBT; BTC tx broadcast to Bitcoin network.

3. DAO calls bridge.update_config({ nbtc_account_id: "nbtc_new.near" })
   → config.nbtc_account_id = "nbtc_new.near"

4. Relayer calls bridge.verify_withdraw(tx_id, proof)
   → verify_withdraw_burn_promise reads config.nbtc_account_id = "nbtc_new.near"
   → ext_nbtc::ext("nbtc_new.near").burn(alice, 100_000, ...)
   → nbtc_new.burn: self.token.internal_withdraw(&bridge_id, 100_000)
      FAILS: bridge has 0 balance on nbtc_new

5. verify_withdraw_burn_callback(is_success=false)
   → pending info moved back to PendingVerify; withdrawal permanently stuck.

Result:
  - Alice received BTC (tx already broadcast).
  - 100_000 nBTC stuck in bridge balance on nbtc_old, never burned.
  - Bridge is under-collateralized by 100_000 satoshis worth of nBTC.
  - No recovery path without DAO reverting nbtc_account_id (if old contract still live).

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id);

        let (protocol_fee, relayer_fee) = config

    pub fn burn(
        &mut self,
        burn_account_id: AccountId,
        burn_amount: U128,
        relayer_account_id: AccountId,
        relayer_fee: U128,
    ) {
        self.assert_bridge();
        self.token
            .internal_withdraw(&self.bridge_id, burn_amount.into());
        if relayer_fee.0 > 0 {
            if self.token.accounts.get(&relayer_account_id).is_none() {
                self.token.internal_register_account(&relayer_account_id);
            }
            self.token.internal_transfer(
                &self.bridge_id,
                &relayer_account_id,
                relayer_fee.into(),
                None,
            );
        }
        near_contract_standards::fungible_token::events::FtBurn {
            owner_id: &burn_account_id,
            amount: burn_amount,
            memo: None,
        }
        .emit();
    }
