### Title
Unrestricted Caller Access to `sign_btc_transaction` Enables Signature Slot Corruption and Withdrawal Lockup - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` imposes no origin check on its caller. Any unprivileged NEAR account can invoke it for any pending withdrawal or refund transaction, supplying an arbitrary `key_version`. If the MPC network accepts a non-canonical `key_version` and returns a signature, the resulting invalid signature is stored in the pending-info slot and the `is_none()` guard permanently blocks legitimate re-signing, locking the user's funds until operator intervention.

### Finding Description
Every other externally-callable signing or verification function in the bridge is decorated with `#[trusted_relayer]`, which restricts callers to a DAO-managed whitelist. `sign_btc_transaction` carries only `#[payable]` and `#[pause]` — no relayer whitelist check, no ownership check, no role check. [1](#0-0) 

Compare with the deposit/withdraw verification functions, which all sit inside a `#[trusted_relayer]`-annotated `impl` block: [2](#0-1) [3](#0-2) 

Inside `internal_sign_btc_transaction`, the caller-supplied `key_version` is forwarded verbatim to the MPC `sign` call: [4](#0-3) 

In `sign_btc_transaction_callback`, if the MPC returns a result (even one produced with a wrong key), the signature is unconditionally stored and the slot is marked occupied: [5](#0-4) 

The guard that prevents re-signing checks only for `None`: [6](#0-5) 

Once a slot is filled with a signature produced under the wrong key, the PSBT is assembled with an invalid witness and can never be confirmed on Bitcoin. The withdrawal is stuck.

### Impact Explanation
A stuck withdrawal means the user's nBTC has already been transferred to the bridge (via `ft_transfer_call`) and the corresponding Bitcoin UTXO cannot be released. Funds remain locked until a DAO/Operator calls `cancel_withdraw` to issue an RBF cancellation transaction. This matches the allowed Medium impact: **attacker-triggered temporary locking of bridged funds requiring operator intervention**. [7](#0-6) 

For refund pending infos the recovery path is more complex: `execute_refund` inserts a new `BTCPendingInfo` only if the key is absent (`is_none()` guard), so a corrupted refund pending info blocks re-execution until `remove_refund_pending_tx_id` is called by a trusted relayer. [8](#0-7) 

### Likelihood Explanation
The entry point is fully public — no deposit, no role, no whitelist membership required. The attacker only needs to know a valid `btc_pending_sign_id` (emitted as a public on-chain event `GenerateBtcPendingInfo`) and a `sign_index`. The `key_version` parameter is an unsigned integer with no on-chain validation before the MPC call. Likelihood is **medium**: the attack requires the MPC to accept a non-zero `key_version` and return a signature; if the MPC rejects unknown key versions the callback receives an `Err` and no state change occurs, but this behavior is an external dependency assumption not enforced by the bridge contract itself. [9](#0-8) 

### Recommendation
Add `#[trusted_relayer]` to the `sign_btc_transaction` impl block (or to the function itself), consistent with every other externally-callable signing function. Alternatively, add an explicit caller check:

```rust
self.assert_trusted_relayer(); // or equivalent whitelist check
```

This mirrors the pattern already applied to `verify_deposit`, `verify_withdraw`, `verify_refund_finalize`, and all other relayer-facing endpoints.

### Proof of Concept
1. Attacker observes a `GenerateBtcPendingInfo` event and extracts `btc_pending_id` for a victim's pending withdrawal.
2. Attacker calls `sign_btc_transaction(btc_pending_id, sign_index=0, key_version=1)` with 1 yoctoNEAR attached.
3. The bridge forwards the call to the MPC with `key_version=1`; if the MPC returns a signature (signed under a different derived key), `sign_btc_transaction_callback` stores it at `signatures[0]`.
4. The legitimate relayer attempts `sign_btc_transaction(btc_pending_id, sign_index=0, key_version=0)` — the call panics at `require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed")`.
5. All signature slots eventually fill with invalid signatures; `is_all_signed()` returns `true`, the state transitions to `PendingVerify`, but the assembled Bitcoin transaction carries an invalid witness and is rejected by the Bitcoin network.
6. The victim's nBTC remains locked in the bridge; only a DAO/Operator `cancel_withdraw` RBF can recover the funds. [10](#0-9) [11](#0-10)

    ///
    /// # Arguments
    ///
    /// * `btc_pending_sign_id` - Pending signature BTC transaction ID.
    /// * `sign_index` -  Specify the input index for this signature.

    /// # Returns
    ///

    #[pause(except(roles(Role::DAO)))]

        sign_index: usize,
        key_version: u32,

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();

            if !self.check_btc_pending_info_exists(original_tx_id) {

                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
