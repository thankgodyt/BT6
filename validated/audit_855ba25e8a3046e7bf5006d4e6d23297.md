### Title
Peras Vote and Certificate Signature Verification Bypass via Stub `validatePerasVote`/`validatePerasCert` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance for all `StandardHash blk` types ships stub implementations of `validatePerasVote` and `validatePerasCert` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks stake-distribution membership without verifying any signature — because the `PerasVote` data type carries no signature field at all. An unprivileged peer can craft votes claiming to be from any stake pool and certificates claiming to boost any block; both will be accepted by every node running this code.

---

### Finding Description

**Root cause — `validatePerasVote` stub (no signature field, no crypto check):**

The universal `BlockSupportsPeras` instance defines `PerasVote` without a signature:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

The corresponding validator only looks up the voter in the stake distribution and returns the stake; it performs zero cryptographic verification:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

**Root cause — `validatePerasCert` stub (always `Right`):**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert
    { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [3](#0-2) 

**Attacker-controlled entry path — `processVotes`:**

Inbound votes from any peer flow through `processVotes`, which calls the stub `validatePerasVote` before storing them:

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

`processVotes` rejects a batch only when `validatePerasVote` returns `Left`; since the stub returns `Right` for any voter present in the stake distribution, crafted votes pass unconditionally: [5](#0-4) 

**Duplicate-ID silencing amplifies the issue:**

`PerasVoteId` is `(roundNo, voterId)` — it does not include the voted block:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo  :: !PerasRoundNo
  , pviVoterId  :: !PerasVoterId
  }
``` [6](#0-5) 

The model explicitly acknowledges this assumption is unsafe:

> "NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body)." [7](#0-6) 

An equivocating vote (same voter, same round, different block) is silently dropped as a duplicate rather than flagged as an attack.

### Impact Explanation

An unprivileged peer that knows the current stake distribution (public on-chain data) can:

1. Enumerate any set of `PerasVoterId` values present in the distribution.
2. Craft `PerasVote` messages for those voters targeting an attacker-chosen block, with no signature required.
3. Send the batch; `processVotes` → `validatePerasVote` accepts every vote because the voter exists in the distribution.
4. Once accumulated stake exceeds the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` boosting the attacker's block.
5. Alternatively, the attacker sends a crafted `PerasCert` directly; `validatePerasCert` returns `Right` unconditionally, so the certificate is stored and applied.

The forged certificate boosts the attacker-chosen block's chain-selection weight, enabling the attacker to make honest nodes prefer a non-canonical chain — a direct bypass of Peras voting/certificate checks.

**Impact category:** Critical — bypass of Peras voting and certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

- **No privileged access required.** The attacker only needs to be a connected peer and know the public stake distribution.
- **No cryptographic break required.** The `PerasVote` type carries no signature; the validator never calls any signature-verification primitive.
- **Reachable in the current production code path.** The stub instance is the universal `StandardHash blk` instance, not a test mock. `processVotes` and `makePerasVotePoolWriterFromChainDB` are the live diffusion entry points.
- **Likelihood: High** given that the Peras object-diffusion mini-protocol is active and any peer can submit votes.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote`** (e.g., a KES or BLS signature over `(roundNo, votedBlock, voterId)`).
2. **Implement `validatePerasVote`** to verify that signature against the voter's registered verification key before accepting the vote.
3. **Implement `validatePerasCert`** to verify the aggregate signature and quorum proof rather than unconditionally returning `Right`.
4. **Include the voted block in `PerasVoteId`** so that equivocating votes (same voter, same round, different block) are detected and rejected rather than silently dropped.
5. **Track the TODO at `https://github.com/tweag/cardano-peras/issues/120`** as a security-critical blocker before the Peras diffusion layer is enabled on any network that processes real stake.

---

### Proof of Concept

```
Precondition: attacker is a connected peer; stake distribution is public.

1. Read the current PerasVoteStakeDistr (public ledger state).
2. Select N voter IDs whose combined stake exceeds the quorum threshold.
3. For each voter ID v_i, construct:
     PerasVote { pvVoteRound = targetRound
               , pvVoteBlock = attackerChosenBlock
               , pvVoteVoterId = v_i }
   No signature field exists; no signing key needed.
4. Send the batch to the victim node via the Peras vote object-diffusion
   mini-protocol.
5. processVotes calls validatePerasVote for each vote.
   validatePerasVote finds v_i in the stake distribution => returns Right.
6. All votes are stored in PerasVoteDB.
7. updatePerasRoundVoteStates accumulates stake; once quorum is exceeded,
   a ValidatedPerasCert boosting attackerChosenBlock is forged and stored.
8. Chain selection now applies the Peras boost to attackerChosenBlock,
   causing the node to prefer the attacker's chain.

Expected outcome: fraudulent Peras certificate accepted; chain selection
manipulated without any cryptographic key material.
```

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
