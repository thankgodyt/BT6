### Title
Passive UTXO Management Policy Bypassed at Boundary via Strict-Inequality Gap — (`File: contracts/satoshi-bridge/src/psbt.rs`)

### Summary
The `check_withdraw_psbt_valid` function enforces passive UTXO management constraints using strict inequalities (`<` and `>`), leaving the equality case (`==`) unhandled. When the UTXO count is exactly at `passive_management_lower_limit` or `passive_management_upper_limit`, no constraint on the `input_num`/`change_num` ratio is applied. Any bridge user initiating a withdrawal at that exact boundary can submit a PSBT that violates the intended UTXO management policy, pushing the pool's UTXO count outside the configured health range.

### Finding Description
In `check_withdraw_psbt_valid`, the passive management enforcement reads:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
// equality case: no branch fires, no constraint applied
``` [1](#0-0) 

When `utxo_num == passive_management_lower_limit`, the protocol is at its minimum healthy UTXO count. The intent is to force withdrawals to produce more change outputs than inputs (net UTXO increase). Because the equality case is silently skipped, a withdrawal with `input_num > change_num` (net UTXO decrease) is accepted, driving the pool below the lower limit.

When `utxo_num == passive_management_upper_limit`, the symmetric bypass allows a withdrawal with `input_num < change_num` (net UTXO increase) to be accepted, driving the pool above the upper limit.

By contrast, the active UTXO management path in `check_active_management_psbt_valid` correctly handles the equality case by panicking:

```rust
} else {
    env::panic_str("Active management conditions are not met");
}
``` [2](#0-1) 

The passive management path has no such guard.

`utxo_num` is computed as the remaining available UTXOs plus the inputs being spent, representing the pre-withdrawal pool size: [3](#0-2) 

The limits themselves are operator-configured integers with no overlap guarantee beyond `lower < upper`: [4](#0-3) 

### Impact Explanation
**Medium — Bypass of bridge UTXO management policy.**

The passive management policy exists to keep the bridge's UTXO pool within a healthy range so that future withdrawals can always be served. Bypassing it at the lower boundary allows a user to consolidate UTXOs when the pool is already at its minimum, pushing the count below the lower limit. Subsequent withdrawals are then forced into the split-UTXO path, but the damage is already done: the pool is in an unhealthy state that requires operator-initiated active UTXO management to correct. This is a stuck/degraded bridge state requiring operator intervention, matching the Medium allowed impact.

### Likelihood Explanation
The UTXO count reaching exactly a configured boundary is a natural event in a live bridge (the count is an integer and must pass through every value). An attacker monitoring on-chain state can observe when `utxo_num` equals a limit and submit a boundary-violating withdrawal at that moment. No special privilege, flash loan, or off-chain coordination is required — only a standard `ft_transfer_call` withdrawal by any nBTC holder.

### Recommendation
Replace the strict inequalities with `<=` / `>=` so that the boundary values are included in the enforced range, mirroring the active management path's exhaustive handling:

```rust
if utxo_num <= config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num >= config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
```

This ensures that when the pool is exactly at a limit, the corrective constraint is still applied.

### Proof of Concept
1. Operator configures `passive_management_lower_limit = 10`, `passive_management_upper_limit = 50`.
2. Bridge UTXO pool reaches exactly 10 UTXOs (observable on-chain via view calls).
3. Attacker (any nBTC holder) initiates a withdrawal spending 3 UTXOs and producing 1 change output (`input_num=3 > change_num=1`).
4. `utxo_num = 10` — neither `< 10` nor `> 50` is true, so no passive management constraint fires.
5. The PSBT passes `check_withdraw_psbt_valid`; the withdrawal is accepted.
6. After the transaction confirms, the pool has `10 - 3 + 1 = 8` UTXOs — below the lower limit.
7. The bridge is now in a degraded UTXO state; operator must invoke `active_utxo_management` to recover. [1](#0-0) [5](#0-4)
