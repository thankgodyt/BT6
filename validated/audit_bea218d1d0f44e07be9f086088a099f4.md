Audit Report

## Title
Silent `ft_transfer` Failure Permanently Freezes Bridged Funds on NEAR — (File: near/omni-bridge/src/lib.rs)

## Summary
When `fin_transfer` finalizes an inbound transfer to a native NEP-141 token recipient with an empty `msg`, the transfer nonce is permanently inserted into `finalised_transfers` before the async `ft_transfer` call. If `ft_transfer` fails (e.g., token is paused), the callback `fin_transfer_send_tokens_callback` unconditionally treats the outcome as success because `is_refund_required(false)` returns `false` without inspecting the promise result. The nonce is never removed, the source-chain funds are already locked/burned, and the recipient never receives tokens — resulting in permanent, irrecoverable fund loss.

## Finding Description
The exploit path is confirmed by the actual code:

**Step 1 — Nonce permanently consumed before async call:**
`process_fin_transfer_to_near` calls `add_fin_transfer` at L1875, which inserts the `TransferId` into `finalised_transfers` and panics if already present (L2226–2234). This happens synchronously, before any cross-contract call.

**Step 2 — `ft_transfer` dispatched for native tokens with empty `msg`:**
In `send_tokens`, when the token is not wNEAR and not a deployed bridge token and `msg` is empty, the code dispatches `ft_transfer` (L2102–2106). This is the standard NEP-141 transfer, not `ft_transfer_call`.

**Step 3 — Callback registered with `is_ft_transfer_call = false`:**
`process_fin_transfer_to_near` passes `!msg.is_empty()` as the `is_ft_transfer_call` argument (L1973). For the empty-`msg` case, this evaluates to `false`.

**Step 4 — `is_refund_required(false)` unconditionally returns `false`:**
The `else` branch at L1800–1803 returns `false` without calling `env::promise_result(0)` at all. The promise outcome of the `ft_transfer` is never inspected.

**Step 5 — Success path taken despite failure:**
Because `is_refund_required` returned `false`, the callback at L1719–1746 sends the fee (detached), logs `FinTransferEvent`, and returns. `remove_fin_transfer` and `revert_lock_actions` are never called. The nonce remains permanently in `finalised_transfers`, blocking any retry.

The recovery path (L1702–1718) — which calls `burn_tokens_if_needed`, `revert_lock_actions`, `remove_fin_transfer`, and emits `FailedFinTransferEvent` — is only reachable when `is_ft_transfer_call = true` AND the `ft_transfer_call` promise returns `U128(0)`. It is structurally unreachable for the `ft_transfer` (non-call) path.

## Impact Explanation
This directly matches the Critical allowed impact: **permanent freezing of bridged funds**. The source-chain tokens (EVM/Solana/Starknet) are already locked or burned and cannot be recovered from the source side. The destination nonce is permanently consumed — any retry of `fin_transfer` panics with `ERR_TRANSFER_ALREADY_FINALISED`. The `FinTransferEvent` is emitted as if the transfer succeeded, providing no on-chain signal of failure. The recipient never receives tokens and has no recourse.

## Likelihood Explanation
Many widely-used NEP-141 tokens implement pause/blacklist mechanisms (e.g., USDC.e, USDT wrappers). The bridge explicitly supports arbitrary native tokens via the `else` branch in `send_tokens`. Any relayer — an unprivileged external actor — can submit a valid cross-chain proof to trigger `fin_transfer`. No admin compromise or special privilege is required. If the token is paused at the moment of finalization (even transiently), the silent-failure path is hit. The condition is realistic and does not require attacker-controlled token state — a routine issuer pause is sufficient.

## Recommendation
In `is_refund_required`, inspect the promise result even when `is_ft_transfer_call = false`. When the `ft_transfer` promise failed, return `true` to trigger the recovery path:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    amount.0 == 0
                } else {
                    false
                }
            }
            Err(_) => false,
        }
    } else {
        // NEW: check if the ft_transfer itself failed
        matches!(env::promise_result(0), PromiseResult::Failed)
    }
}
```

This ensures that a failed `ft_transfer` triggers `remove_fin_transfer` and `revert_lock_actions`, allowing the transfer to be retried once the token is unpaused.

## Proof of Concept
1. Register a pausable NEP-141 token (e.g., a USDC wrapper) with the NEAR omni-bridge.
2. A user initiates a transfer from EVM → NEAR; EVM-side tokens are locked.
3. The token issuer pauses the token (or it is already paused).
4. A relayer submits a valid proof to `fin_transfer` on NEAR.
5. `fin_transfer_callback` → `process_fin_transfer_to_near` → `add_fin_transfer` (L1875, L2226–2234) marks the nonce used in `finalised_transfers`.
6. `send_tokens` dispatches `ft_transfer` (L2102–2106); the token contract panics with "paused".
7. NEAR runtime calls `fin_transfer_send_tokens_callback` with `is_ft_transfer_call = false` (L1973).
8. `is_refund_required(false)` returns `false` (L1800–1803); callback logs `FinTransferEvent` (L1745) and exits.
9. `finalised_transfers` still contains the nonce — any retry of `fin_transfer` panics with `ERR_TRANSFER_ALREADY_FINALISED`.
10. User's funds are permanently frozen; no recovery path exists on either chain.

A local integration test can demonstrate this by deploying a mock pausable NEP-141 token, registering it with the bridge, pausing it, and calling `fin_transfer` with a mocked valid proof — then asserting that `finalised_transfers` contains the nonce, no tokens were received, and a second `fin_transfer` call panics.
