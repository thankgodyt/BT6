### Title
Peras Vote Membership-Only Check Bypasses Signature Verification, Allowing Forged Votes to Reach Quorum - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The blanket `BlockSupportsPeras` instance's `validatePerasVote` implementation validates incoming Peras votes by checking only whether the voter's ID appears in the stake distribution, without performing any cryptographic signature verification. This is structurally identical to the reported `onlyTraderOrSettler` bypass: group membership alone (`isTraders[msg.sender]`) is sufficient to pass the guard, just as stake-distribution membership alone is sufficient to pass `validatePerasVote`. Any unprivileged peer who knows the public pool IDs (which are on-chain public data) can forge votes for arbitrary pools, accumulate enough forged stake to reach quorum, and cause the node to forge a certificate boosting an adversarially chosen block.

### Finding Description

The default `BlockSupportsPeras` instance is a blanket instance covering all block types:

```haskell
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right
          ValidatedPerasVote
            { vpvVote = vote
            , vpvVoteStake = stake
            }
    | otherwise =
        Left PerasValidationErr
``` [1](#0-0) 

The `_params` argument is discarded (underscore prefix), and the only guard is `lookupPerasVoteStake vote stakeDistr` — a pure map lookup that checks whether the `pvVoteVoterId` field of the incoming vote exists in the stake distribution. The `PerasVote` data type in this instance carries no signature field at all:

```haskell
data PerasVote blk = PerasVote
    { pvVoteRound   :: PerasRoundNo
    , pvVoteBlock   :: Point blk
    , pvVoteVoterId :: PerasVoterId
    }
``` [2](#0-1) 

There is no KES, VRF, or BLS signature field and no call to any verification primitive. The TODO comment at line 360 acknowledges the missing validation but the stub is the only deployed implementation:

Once a `ValidatedPerasVote` is produced, it is fed into `updatePerasRoundVoteStates`, which accumulates stake and calls `forgePerasCert` when the quorum threshold is crossed: [4](#0-3) 

The `forgePerasCert` default stub also unconditionally succeeds: [5](#0-4) 

The resulting `ValidatedPerasCert` carries a `vpcCertBoost` equal to `perasWeight params`, which is added to the chain weight of the boosted block during chain selection.

The `CryptoSupportsVotingCommittee` class (used by the real WFALS and EveryoneVotes committee implementations) does enforce cryptographic verification — `verifyVoteSignature` is called in both `implVerifyVote` implementations: [6](#0-5) [7](#0-6) 

But the `BlockSupportsPeras` vote path is entirely separate from the committee path and has no such check.

### Impact Explanation

**High — Bypass of certificate/signature validation enabling unauthorized certificate acceptance.**

An attacker who sends crafted `PerasVote` network messages with a known pool ID (all pool IDs are public on-chain) will have those votes accepted as `ValidatedPerasVote` with the full stake weight of that pool. By sending forged votes for enough pools to exceed `perasQuorumStakeThreshold`, the attacker causes the local node to forge a `ValidatedPerasCert` for any block point of the attacker's choosing. That certificate is then applied as a chain-weight boost (`perasWeight`) during chain selection, making the adversarially chosen block appear heavier than the honest tip. This directly enables a chain-selection manipulation: an honest node can be made to prefer a non-canonical, adversarially boosted chain without the attacker holding any stake or private keys.

### Likelihood Explanation

**High.** Pool IDs are public. The attacker needs only to send well-formed `PerasVote` network messages with valid pool IDs. No key material, stake, or privileged access is required. The vote diffusion protocol (`perasVoteDiffusionInboundTracer` is wired in `NodeKernel`) accepts votes from any connected peer. [8](#0-7) 

### Recommendation

Replace the stub `validatePerasVote` with a real implementation that:
1. Verifies the cryptographic signature on the vote using the pool's registered verification key from the stake distribution.
2. Verifies any VRF eligibility proof if the committee scheme requires it (as `implVerifyVote` in `WFALS.hs` does).
3. Rejects votes whose `pvVoteVoterId` does not match the key that produced the signature.

Until a real implementation exists, the vote diffusion inbound handler should refuse to process any incoming votes rather than silently accepting them.

### Proof of Concept

1. Attacker connects to an honest node as a peer via the Peras vote diffusion mini-protocol.
2. Attacker reads the on-chain stake distribution to enumerate pool IDs with large stake.
3. Attacker sends `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = poolId_1 }` for each high-stake pool, with no signature (the data type has no signature field).
4. The node calls `validatePerasVote _params stakeDistr vote`; `lookupPerasVoteStake` succeeds for each known pool ID; each vote is accepted as `ValidatedPerasVote` with full pool stake.
5. `updatePerasRoundVoteStates` accumulates stake; once `perasQuorumStakeThreshold` is exceeded, `forgePerasCert` is called and returns a `ValidatedPerasCert` boosting `adversarialBlock`.
6. Chain selection adds `perasWeight` to `adversarialBlock`'s chain weight; the node may switch to the adversarially boosted fork. [9](#0-8)
