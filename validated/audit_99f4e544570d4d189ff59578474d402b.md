### Title
Peras Certificate Silently Dropped via Unprocessed `AddPerasVoteResult` in `makePerasVotePoolWriterFromVoteDB` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

`makePerasVotePoolWriterFromVoteDB` uses `void` to discard the `AddPerasVoteResult blk` returned by `PerasVoteDB.addVote`. When quorum is reached and the result is `AddedPerasVoteAndGeneratedNewCert cert`, the freshly-forged Peras certificate is silently dropped and never forwarded to the ChainDB for chain-selection processing. The sibling function `makePerasVotePoolWriterFromChainDB` avoids this by routing through `ChainDB.addPerasVoteWithAsyncCertHandling`, which internally handles certificate submission. The `makePerasVotePoolWriterFromVoteDB` path has no equivalent handling.

---

### Finding Description

In `PerasVote.hs`, the `addVote` callback supplied to `processVotes` is:

```haskell
(void . join . atomically . PerasVoteDB.addVote perasVoteDB)
``` [1](#0-0) 

`PerasVoteDB.addVote` has type:

```haskell
addVote :: WithArrivalTime (ValidatedPerasVote blk) -> STM m (m (AddPerasVoteResult blk))
``` [2](#0-1) 

`AddPerasVoteResult` has three constructors:

```haskell
data AddPerasVoteResult blk
  = PerasVoteAlreadyInDB
  | AddedPerasVoteButDidntGenerateNewCert
  | AddedPerasVoteAndGeneratedNewCert (ValidatedPerasCert blk)
``` [3](#0-2) 

When enough votes accumulate to reach quorum, `implAddVote` returns `AddedPerasVoteAndGeneratedNewCert cert`: [4](#0-3) 

The `void` in `makePerasVotePoolWriterFromVoteDB` discards this entire result. The `ValidatedPerasCert blk` embedded in `AddedPerasVoteAndGeneratedNewCert` is never extracted and never submitted to the ChainDB via `addPerasCertAsync` or any equivalent path.

By contrast, `makePerasVotePoolWriterFromChainDB` uses `ChainDB.addPerasVoteWithAsyncCertHandling`, which internally inspects the `AddPerasVoteResult` and calls `addPerasCertAsync` when a certificate is generated: [5](#0-4) [6](#0-5) 

The comment on `makePerasVotePoolWriterFromChainDB` explicitly states it "properly handles the produced certs", implying `makePerasVotePoolWriterFromVoteDB` does not.

---

### Impact Explanation

Peras certificates provide a chain-selection boost (`vpcCertBoost :: PerasWeight`) to the block they target. When a certificate is silently dropped, `getPerasWeightSnapshot` in the ChainDB never learns of the new boost, so `preferAnchoredCandidate` computes chain preference without it. [7](#0-6) 

A node running with `makePerasVotePoolWriterFromVoteDB` as its inbound vote writer will never apply Peras boosts derived from peer-supplied votes, even after quorum is reached. An adversary who controls a competing fork can exploit this: by ensuring the honest node's Peras certificates are never registered, the adversary's unboosted fork may be preferred over the legitimately-boosted canonical chain, constituting a chain-selection safety failure beyond the intended Peras security assumptions.

**Impact class**: High — chain-selection bug that lets an unprivileged peer (by supplying votes that trigger quorum) cause an honest node to prefer a non-boosted chain over the Peras-certified canonical chain.

---

### Likelihood Explanation

The function `makePerasVotePoolWriterFromVoteDB` is exported from a production source module and is a named, documented API entry point. Any deployment that wires the inbound Peras vote miniprotocol to this writer (rather than `makePerasVotePoolWriterFromChainDB`) is affected. The trigger condition — enough peer-supplied votes to reach quorum — is a normal, expected network event, not an exotic edge case. No special privileges are required; any peer participating in Peras voting can supply votes.

---

### Recommendation

Replace the `addVote` callback in `makePerasVotePoolWriterFromVoteDB` with one that inspects the `AddPerasVoteResult` and, on `AddedPerasVoteAndGeneratedNewCert cert`, submits the certificate to the ChainDB (e.g., via `addPerasCertAsync`). Alternatively, deprecate `makePerasVotePoolWriterFromVoteDB` entirely and require all callers to use `makePerasVotePoolWriterFromChainDB`, which already handles this correctly.

---

### Proof of Concept

1. A node is configured with `makePerasVotePoolWriterFromVoteDB` as its inbound Peras vote pool writer.
2. Peers (honest or adversarial) send enough `PerasVote` messages to reach quorum for a given round targeting block `B`.
3. `processVotes` calls `(void . join . atomically . PerasVoteDB.addVote perasVoteDB)` for each vote.
4. On the vote that tips the tally over quorum, `implAddVote` returns `AddedPerasVoteAndGeneratedNewCert cert` (a `ValidatedPerasCert` for block `B`).
5. `void` discards this value; `cert` is never passed to `addPerasCertAsync` or `addPerasCertSync`.
6. The `PerasCertDB` and the in-memory weight snapshot remain unaware of the certificate.
7. Chain selection proceeds without the Peras boost for block `B`.
8. An adversary's fork that would have been outweighed by the boosted canonical chain is now selected instead. [1](#0-0) [8](#0-7) [9](#0-8)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
