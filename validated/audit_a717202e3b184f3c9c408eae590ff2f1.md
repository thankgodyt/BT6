### Title
Peras Quorum Check Compares Incommensurable Stake Units, Enabling False Certificate Acceptance or Permanent Quorum Failure - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares a `PerasVoteStake` (sourced from the ledger stake distribution, potentially absolute) against a `PerasQuorumStakeThreshold` (a relative/normalized `Rational` in `PerasParams`), with no type-level or runtime enforcement that both values are in the same units. The code itself documents this as an unresolved correctness assumption. If the stake distribution supplied to `validatePerasVote` carries absolute ledger stake rather than normalized values, the quorum gate is either trivially bypassed (false certificate) or permanently unsatisfiable (quorum never reached), both of which break Peras chain selection.

---

### Finding Description

In `SupportsPeras.hs`, `stakeAboveThreshold` performs the core Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The code's own TODO comment (lines 155–161) explicitly states:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`PerasVoteStake` is a bare `Rational` newtype with no phantom type distinguishing absolute from relative stake: [3](#0-2) 

The `validatePerasVote` implementation simply looks up whatever `Rational` is stored in the caller-supplied `PerasVoteStakeDistr` and assigns it directly to `vpvVoteStake` — no normalization is performed: [4](#0-3) 

The `PerasVoteStakeDistr` is populated externally from `getStakeDistrSTM` (an STM action reading the ledger stake distribution), and is passed directly into `validatePerasVote` without any normalization step: [5](#0-4) 

`votesReachQuorum` then sums the raw `vpvVoteStake` values and calls `stakeAboveThreshold` directly: [6](#0-5) 

The `PerasQuorumStakeThreshold` in `PerasParams` is documented and used as a relative value (e.g., `0.75` meaning 75% of committee stake): [7](#0-6)

### Impact Explanation

Two failure modes arise depending on what unit the `PerasVoteStakeDistr` carries:

1. **False quorum (certificate bypass):** If the distribution stores absolute lovelace fractions of total ADA supply (e.g., a pool with 5% of total stake stores `0.05`), but the quorum threshold is `0.75` (relative to committee), a single large pool's vote (`0.05`) never reaches `0.75`. However, if the distribution stores raw lovelace counts (e.g., `2_250_000_000_000_000` for a 5% pool), the comparison `2_250_000_000_000_000 >= 0.75` is trivially true for every single vote, meaning **any single vote immediately forges a certificate** for any block, regardless of actual committee support.

2. **Permanent quorum failure:** If absolute stake fractions (e.g., `0.001` per pool) are compared against a relative threshold of `0.75`, quorum is mathematically unreachable even with 100% honest participation, permanently disabling Peras certificate generation and its chain-selection boost.

In the false-quorum case, an unprivileged peer can send a single crafted vote to cause the node to forge and accept a `ValidatedPerasCert` for an adversarially chosen block, granting it a `PerasWeight` boost in chain selection. This constitutes a **bypass of Peras certificate/vote verification** and a **chain selection bug** — the boosted block may be preferred over the honest canonical chain.

---

### Likelihood Explanation

The `PerasVoteStakeDistr` is populated from the ledger stake distribution via `getStakeDistrSTM`. The ledger natively stores absolute stake (lovelace). The comment at lines 136–143 explicitly acknowledges there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake." This means the conversion (or lack thereof) is an active open question, not a resolved implementation detail. Any deployment that wires the ledger's absolute stake distribution directly into `PerasVoteStakeDistr` — the most natural implementation — triggers this bug. The likelihood is **high** for any production deployment of Peras. [8](#0-7) 

---

### Recommendation

1. Introduce a phantom-typed wrapper distinguishing absolute from relative `PerasVoteStake` at the type level, preventing incommensurable values from being compared.
2. Normalize `PerasVoteStake` to relative (committee-fraction) units inside `validatePerasVote` or `stakeAboveThreshold`, using the total committee stake as the denominator.
3. Alternatively, express `PerasQuorumStakeThreshold` in absolute units and normalize the threshold instead.
4. Remove the TODO and enforce the invariant with a runtime assertion or type constraint until the type-safe fix is in place.

### Proof of Concept

Assume `PerasVoteStakeDistr` is populated with absolute lovelace fractions of total supply (e.g., a pool holding 5% of 45B ADA stores `PerasVoteStake (45_000_000_000_000_000 % 20)` = `2_250_000_000_000_000`). `perasQuorumStakeThreshold` is `PerasQuorumStakeThreshold (3 % 4)` (75%).

A peer sends one vote from this pool. `validatePerasVote` looks up `2_250_000_000_000_000` from the distribution and stores it in `vpvVoteStake`. `votesReachQuorum` calls `stakeAboveThreshold`:

```
stake = 2_250_000_000_000_000
quorumThreshold + safetyMargin ≈ 0.75 + ε
2_250_000_000_000_000 >= 0.75  →  True
```

`votesReachQuorum` returns `Just ValidatedPerasVotesWithQuorum`, `forgePerasCert` is called, and a `ValidatedPerasCert` is produced for the adversary's chosen block. The ChainDB applies the `PerasWeight` boost, causing the node to prefer the adversarially boosted chain over the honest canonical chain. [9](#0-8) [10](#0-9)

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```
