### Title
Refund Recovery Can Be Stolen or Permanently Griefed When `deposit_msg.refund_address` Is None - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user deposits BTC to an address derived from a `DepositMsg` with `refund_address: None`, any unprivileged NEAR account can front-run the legitimate refund request by supplying their own BTC address. Because only one refund request can exist per UTXO, the first submitter wins. The attacker can either steal the BTC (if the DAO fails to reject within the timelock) or permanently grief recovery by re-submitting immediately after every DAO rejection.

### Finding Description

The `internal_request_refund` function in `refund.rs` validates the `refund_address` against `deposit_msg.refund_address` only when the latter is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None`, no check is performed and any caller-supplied `refund_address` is accepted verbatim and stored in the `RefundRequest`.

The `request_refund` public entrypoint in `api/bridge.rs` does not carry an individual `#[trusted_relayer]` attribute (unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` which do), making it callable by any NEAR account: [2](#0-1) 

The `deposit_msg` is publicly logged on-chain whenever a user calls `get_user_deposit_address`, which emits a `LogDepositAddress` event containing the full `deposit_msg` and the corresponding BTC address: [3](#0-2) 

An attacker monitoring NEAR events can therefore learn every `deposit_msg` and its BTC address. When a BTC deposit to one of those addresses is never finalized (i.e., `verify_deposit` is never called), the attacker calls `request_refund` with the correct `deposit_msg` but with their own BTC address.

The `request_refund_callback` enforces a strict uniqueness constraint — only one refund request may exist per UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

This means the first caller wins. The legitimate user cannot submit their own refund request once the attacker's is stored.

The `resolve_execute_refund_timelock` function applies a longer `unsafe_refund_timelock_sec` for caller-supplied addresses (the `refund_address: None` case), giving the DAO time to reject: [5](#0-4) 

However, `reject_refund` removes the request entirely, after which the attacker can immediately re-submit a new request with their address. There is no mechanism to prevent this cycle: [6](#0-5) 

This creates two distinct attack paths:

**Path 1 — Theft:** Attacker submits refund request with their BTC address. If the DAO does not reject within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the MPC network signs a transaction sending the BTC to the attacker's address.

**Path 2 — Permanent Grief:** Attacker submits → DAO rejects → attacker immediately re-submits. Repeated indefinitely. The legitimate user can never reclaim their BTC because the UTXO slot is always occupied by the attacker's request.

### Impact Explanation

**Critical (theft):** If the DAO fails to reject within the timelock window, the attacker receives the user's BTC via the MPC-signed refund transaction. This is a direct, permanent loss of user funds with no recovery path.

**Medium (grief):** Even if the DAO is vigilant, the attacker can permanently prevent the legitimate user from recovering their BTC by re-submitting after every rejection. The funds are locked in the bridge's deposit address indefinitely, constituting permanent loss of user funds.

### Likelihood Explanation

The `deposit_msg` is publicly broadcast on NEAR via the `LogDepositAddress` event every time a user generates a deposit address. An attacker can run an automated script that:
1. Monitors NEAR events for `LogDepositAddress` emissions.
2. Monitors the Bitcoin blockchain for deposits to those addresses.
3. Monitors the NEAR bridge contract for the absence of a corresponding `verify_deposit` call.
4. Immediately calls `request_refund` with the attacker's BTC address when a deposit goes unfinalized.

This requires no special privileges, no leaked keys, and no trusted role. The only prerequisite is a user sending BTC to a deposit address derived from a `DepositMsg` with `refund_address: None`, which is the common case for standard deposits.

### Recommendation

1. **Require caller authentication for `refund_address` when `deposit_msg.refund_address` is None.** For example, require the caller to be the `deposit_msg.recipient_id` (the NEAR account that was to receive nBTC), or require a signed proof from the BTC sender.
2. **Alternatively, restrict `request_refund` to trusted relayers** (add `#[trusted_relayer]` individually to the function) and require relayers to validate the refund address against the original depositor before submitting.
3. **Implement a cooldown after rejection** to prevent immediate re-submission of a refund request for the same UTXO, giving the legitimate user a window to submit their own request.
4. **Document clearly** that deposits using `deposit_msg.refund_address: None` do not have a guaranteed self-service recovery path and are subject to DAO discretion.

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The contract emits `LogDepositAddress` with the full `deposit_msg` and the BTC address `bc1q...alice`.
2. Alice sends 1 BTC to `bc1q...alice`. The deposit is never finalized (e.g., Alice used the wrong network or the relayer missed it).
3. Attacker Bob monitors NEAR events, sees the `LogDepositAddress` event, and monitors Bitcoin for the deposit.
4. Bob calls `request_refund(deposit_msg=<alice's msg>, refund_address="bc1q...bob", tx_bytes=<alice's tx>, vout=0, proof=<valid proof>)` with a small NEAR storage deposit attached.
5. `request_refund_callback` verifies the BTC transaction is included, verifies the output script matches the deposit address derived from Alice's `deposit_msg`, and stores the `RefundRequest` with `refund_address = "bc1q...bob"`.
6. Alice attempts to call `request_refund` with her own address — it reverts with `"Refund request already exists for this UTXO"`.
7. **Theft path:** After `unsafe_refund_timelock_sec` elapses without DAO intervention, Bob calls `execute_refund`. The MPC network signs a transaction sending 1 BTC to `bc1q...bob`.
8. **Grief path:** DAO calls `reject_refund`. Bob immediately calls `request_refund` again with his address. Alice still cannot submit. Repeat indefinitely.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
    }
