Audit Report

## Title
Missing Pre-Burn Normalization Check Causes Permanent Loss of Bridged Tokens When Amount Normalizes to Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a user initiates a NEAR→foreign transfer with an amount smaller than the decimal normalization factor (`10^(origin_decimals - decimals)`), `normalize_amount` silently returns 0 via floor division. The `init_transfer` path only validates `fee < amount` before proceeding to `init_transfer_internal`, which irreversibly burns or locks the tokens and returns `U128(0)` to the NEP-141 caller (no refund). The subsequent `sign_transfer` call always reverts with `InvalidAmountToTransfer`, and no public cancel or refund path exists for the stuck pending transfer, resulting in permanent loss of the user's tokens.

## Finding Description

`normalize_amount` performs floor division with no guard against a zero result:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The `init_transfer` path (reached via `ft_on_transfer` → `ft_on_transfer_internal`) validates only that `fee < amount`:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

There is no check that `normalize_amount(amount_without_fee, decimals) > 0` at this stage. Execution proceeds to `init_transfer_internal`, which irreversibly burns deployed tokens or locks native tokens and returns `U128(0)` — signaling to the NEP-141 token contract that all tokens were consumed with no refund:

```rust
// near/omni-bridge/src/lib.rs L1850-1864
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
// ...
U128(0)
```

The transfer message is stored in `pending_transfers`. Later, when a relayer calls `sign_transfer`, the zero-amount guard fires and always reverts:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

The only early-exit paths in `init_transfer_internal` that return a refund are: storage balance failure and a non-Near token address — neither applies to the normal deployed-token flow. The `remove_transfer_message_without_refund` function used in those paths is not publicly callable. No public cancel function exists for pending transfers.

The inline comment on `normalize_amount` (L2781-2783) acknowledges that "dust stays locked/burned" when fee = 0, but this refers to the sub-unit remainder after normalization, not to the case where the entire amount normalizes to zero and `sign_transfer` is permanently blocked.

## Impact Explanation

For deployed (bridged) tokens: they are burned and cannot be recovered. For native tokens: they are locked in the bridge contract with no recovery path. The transfer message remains in `pending_transfers` indefinitely. This constitutes permanent freezing/loss of bridged funds, matching the Critical impact scope item: *"permanent freezing of bridged funds"* and *"decimal/normalization abuse... that changes user or protocol balances."*

## Likelihood Explanation

Low-to-medium. The condition requires a user to send an amount below the normalization threshold. For a token with `origin_decimals=24` normalized to `decimals=18`, the threshold is `10^6` base units — a very small but non-zero amount. Users unfamiliar with decimal normalization, or those sending small test amounts, can trigger this. The condition is reachable through the standard `ft_transfer_call` → `ft_on_transfer` public flow with no privileged access required. The CLAUDE.md false-positive list (L192-195) explicitly covers only the `origin_decimals < decimals` underflow/panic case, not the floor-division-to-zero case.

## Recommendation

Add a normalization sanity check in `init_transfer` (before `init_transfer_internal` is called, i.e., after the `fee < amount` check at L554-557) that validates the net amount survives normalization:

```rust
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing guard in `sign_transfer` (L482-485) but places it before the irreversible burn/lock step, allowing the NEP-141 callback to return the full amount as a refund.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = `10^6`).
2. User calls `ft_transfer_call` on the deployed token contract with `amount = 5`, `fee = 0`, targeting the bridge.
3. Bridge's `ft_on_transfer` → `init_transfer` runs: `fee (0) < amount (5)` passes.
4. `init_transfer_internal` is called: 5 base units are burned (deployed token) or locked (native). `ft_on_transfer` returns `U128(0)` — no refund issued.
5. Transfer message stored in `pending_transfers`.
6. Relayer calls `sign_transfer` for this transfer.
7. `normalize_amount(5, Decimals{decimals:18, origin_decimals:24})` = `5 / 1_000_000` = `0`.
8. `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`. Transaction reverts.
9. No public cancel or refund function exists. The 5 base units are permanently lost and the pending transfer is stuck forever. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
