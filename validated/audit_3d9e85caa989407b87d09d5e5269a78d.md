Audit Report

## Title
Unchecked `u128` Multiplication Overflow in `denormalize_amount` Permanently Freezes Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary

`denormalize_amount` performs a bare `u128` multiplication with no overflow guard. The workspace compiles with `overflow-checks = true`, so any overflow panics at runtime. When triggered inside `fin_transfer_callback`, `fast_fin_transfer`, or `claim_fee_callback`, the callback aborts after the EVM side has already locked or burned the user's tokens, permanently freezing them with no recovery path.

## Finding Description

`denormalize_amount` is defined as:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← bare multiplication, no checked_mul
}
``` [1](#0-0) 

The workspace release profile explicitly enables `overflow-checks = true`: [2](#0-1) 

This means any multiplication that exceeds `u128::MAX` causes an immediate panic/abort rather than silent wrapping.

The `Decimals` struct stores both `decimals` (EVM-side) and `origin_decimals` (NEAR-side) as `u8` values: [3](#0-2) 

`denormalize_amount` is called unconditionally at three critical sites:

1. Inside `fin_transfer_callback` to reconstruct the NEAR-side amount from the EVM proof: [4](#0-3) 

2. Inside `fast_fin_transfer`: [5](#0-4) 

3. Inside `claim_fee_callback`: [6](#0-5) 

At all three sites, the EVM-side amount is passed directly from the submitted proof without any upper-bound validation before the multiplication. No existing guard checks whether `amount * 10^diff_decimals` would overflow before the operation is performed.

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**, which is an explicitly listed Critical impact. For a token with `origin_decimals = 24` and `decimals = 18` (`diff_decimals = 6`), the overflow threshold is `u128::MAX / 10^6 ≈ 3.4 × 10^32`. Any EVM `uint128` amount above this value causes `denormalize_amount` to panic. With `overflow-checks = true`, the NEAR runtime aborts the callback. Because the EVM side has already locked or burned the tokens before the proof is submitted, and because the NEAR nonce is never marked used (the callback never completes), the transfer is permanently unfinalisable. Every subsequent relay attempt produces the same panic. The user's funds are frozen with no recovery path.

## Likelihood Explanation

Any unprivileged bridge user can trigger this by calling `initTransfer` on the EVM contract with a `uint128` amount above the overflow threshold for the specific token's decimal configuration. No special role, key, or collusion is required. The EVM contract imposes no upper-bound on `amount` beyond the `fee < amount` check. Tokens bridging between chains with large decimal differences (e.g., NEAR native token: 24 origin decimals, 18 EVM decimals) are directly affected. For tokens with larger decimal gaps (e.g., `diff_decimals = 18`), the overflow threshold drops to `u128::MAX / 10^18 ≈ 3.4 × 10^20`, making the attack trivially reachable with moderate token amounts.

## Recommendation

Replace the bare multiplication in `denormalize_amount` with a checked variant that returns an error on overflow, and propagate that error to the caller:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> Option<u128> {
    let diff_decimals: u32 = decimals.origin_decimals.checked_sub(decimals.decimals)?.into();
    amount.checked_mul(10_u128.checked_pow(diff_decimals)?)
}
```

All call sites (`fin_transfer_callback`, `fast_fin_transfer`, `claim_fee_callback`) should handle `None` by panicking with a descriptive `BridgeError` rather than letting an arithmetic abort propagate. Additionally, consider enforcing an upper-bound check on the EVM `initTransfer` amount relative to the token's decimal configuration so that overflowing amounts are rejected at the source before tokens are locked or burned.

## Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`).
2. Attacker calls `initTransfer` on EVM with `amount = u128::MAX / 10^6 + 1` (a valid `uint128`). EVM locks/burns the tokens.
3. Relayer submits the EVM proof to NEAR `fin_transfer` → `fin_transfer_callback`.
4. Inside the callback: `denormalize_amount(amount, decimals)` computes `(u128::MAX / 10^6 + 1) * 10^6`, which exceeds `u128::MAX`. With `overflow-checks = true`, the NEAR runtime panics.
5. The callback aborts; no state is written; the destination nonce is never marked used.
6. Every subsequent retry by any relayer produces the same panic.
7. The attacker's (or victim's) tokens are permanently frozen on EVM with no NEAR-side release possible.

A fuzz test targeting `denormalize_amount` with arbitrary `u128` amounts and `Decimals` values where `origin_decimals > decimals` would reproduce the panic deterministically.
