### Title
Missing Ownership Check in `withdraw_rbf()` Allows Any Caller to Replace a Victim's Pending Withdrawal with Attacker-Controlled Outputs — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`withdraw_rbf()` is a public, unprivileged function that accepts an arbitrary `original_btc_pending_verify_id` (which identifies any user's pending withdrawal) together with a fully attacker-controlled `output` vector. The function never verifies that the pending transaction belongs to the caller. An attacker can supply a victim's pending-ID and their own BTC output address, causing the bridge to build and sign a replacement (RBF) Bitcoin transaction that sends the victim's funds to the attacker.

---

### Finding Description

`withdraw_rbf` in `contracts/satoshi-bridge/src/api/bridge.rs` (lines 259–274):

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,   // ← any user's pending ID
    output: Vec<TxOut>,                        // ← fully attacker-controlled
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // caller, not owner
    self.require_pending_sign_capacity(&account_id);  // checked on caller, not owner

    self.withdraw_rbf_chain_specific(
        account_id,                            // attacker's account
        original_btc_pending_verify_id,        // victim's pending ID
        output,                                // attacker's BTC outputs
        chain_specific_data,
    );
}
```

The function:
1. Derives `account_id` from `env::predecessor_account_id()` (the attacker).
2. Checks `require_pending_sign_capacity` against the **attacker's** account, not the owner of the pending transaction.
3. Passes the attacker's `account_id` and the victim's `original_btc_pending_verify_id` — along with the attacker-supplied `output` — into `withdraw_rbf_chain_specific`.

The privileged counterpart `cancel_withdraw` (lines 285–299) demonstrates the correct pattern: it first looks up the owner from the pending info and uses **that** account for all subsequent checks:

```rust
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
```

`withdraw_rbf` never performs this ownership lookup, so the caller can target any pending ID regardless of who created it.

`BTCPendingInfo` stores the true owner in its `account_id` field (line 108 of `btc_pending_info.rs`), but `withdraw_rbf` never compares that field against `env::predecessor_account_id()`.

---

### Impact Explanation

The `output: Vec<TxOut>` parameter is fully attacker-controlled and is forwarded directly into `withdraw_rbf_chain_specific`, which constructs a new Bitcoin RBF transaction. By supplying their own BTC address as the output, the attacker redirects the victim's bridged BTC to themselves. The victim's nBTC tokens are already held by the bridge (transferred during `ft_on_transfer`), so a successful RBF results in complete loss of the victim's funds with no recourse.

**Impact class:** Critical — theft/permanent loss of user funds via unauthorized redirection of bridge-controlled BTC.

---

### Likelihood Explanation

`withdraw_rbf` carries no role restriction (`#[access_control_any]`) and no `assert_one_yocto()` guard. Any NEAR account can call it at any time. A victim's `original_btc_pending_verify_id` is publicly observable on-chain (emitted in `Event::GenerateBtcPendingInfo`). The attacker only needs to observe a pending withdrawal and call `withdraw_rbf` before the original transaction is signed and broadcast.

---

### Recommendation

Add an ownership check at the start of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();
    // Verify the caller owns the pending transaction
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(account_id == owner, "Not authorized to RBF this transaction");
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

---

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract, initiating a withdrawal. The bridge emits `Event::GenerateBtcPendingInfo` with `btc_pending_id = ALICE_PENDING_ID`. Alice's nBTC is now held by the bridge.
2. Attacker Bob observes `ALICE_PENDING_ID` on-chain.
3. Bob calls:
   ```
   withdraw_rbf(
       original_btc_pending_verify_id = ALICE_PENDING_ID,
       output = [TxOut { value: alice_amount - fee, script_pubkey: BOB_BTC_ADDRESS }],
       chain_specific_data = None,
   )
   ```
4. Because there is no ownership check, the call succeeds. `withdraw_rbf_chain_specific` is invoked with Bob's `account_id` and Alice's pending ID, constructing a replacement Bitcoin transaction that pays Bob's BTC address.
5. The MPC signers sign the replacement transaction (via `sign_btc_transaction`, also callable by anyone).
6. The replacement transaction is broadcast and confirmed on Bitcoin. Alice's BTC arrives at Bob's address. Alice's nBTC is burned. Alice loses all funds.
