### Title
Peras Certificate Validation Always Returns Success — Certificate Verification Bypass - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance, which applies to all `StandardHash blk` blocks, implements `validatePerasCert` and `validatePerasVote` as unconditional stubs that always return `Right` (success) without performing any cryptographic verification. This is the direct analog of the `ecrecover` returning 0 not being checked: the verification function never rejects any input, so any crafted certificate or vote submitted by an unprivileged peer is accepted as valid. When Peras is enabled, this allows an attacker to inject arbitrary certificates that boost any block, directly manipulating chain selection.

### Finding Description

In `BlockSupportsPeras.hs`, the default instance for all `StandardHash blk` blocks implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The same unconditional stub applies to `validatePerasVote`: [2](#0-1) 

This default instance is declared for all `StandardHash blk`: [3](#0-2) 

The attacker-controlled entry path is:
1. A peer sends a crafted `PerasCert` over the network miniprotocol.
2. The node calls `validatePerasCert`, which unconditionally returns `Right ValidatedPerasCert` with the full `perasWeight` boost assigned.
3. The `ValidatedPerasCert` is passed to `addPerasCertAsync`, which enqueues it for chain selection.
4. `chainSelSync` processes the certificate via `ChainSelAddPerasCert`, adds it to `PerasCertDB`, and calls `chainSelectionForBlock` for the boosted block. [4](#0-3) 

Because `validatePerasCert` never checks the certificate's cryptographic content (no BLS aggregate signature verification, no voter eligibility check, no quorum threshold), any `PerasCert` with an arbitrary `pcCertBoostedBlock` is accepted and applied to chain selection with full weight.

The real certificate verification logic exists in `implVerifyCert` in `WFALS.hs` and `EveryoneVotes.hs`, which properly aggregates and verifies BLS signatures and VRF outputs: [5](#0-4) 

But this logic is never invoked by the production `validatePerasCert` path.

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

When Peras is enabled, an attacker with no privileged keys can:
- Craft a `PerasCert` pointing to any block on a minority fork.
- Submit it to an honest node via the Peras certificate miniprotocol.
- The node accepts it unconditionally and applies the full `perasWeight` boost to that fork.
- Chain selection now prefers the attacker's fork over the canonical chain.

This directly violates the Peras security invariant: only a certificate backed by a quorum of legitimately eligible, cryptographically verified committee votes should be able to boost a block's chain weight.

### Likelihood Explanation

**Medium.** Peras is disabled by default on mainnet ("Note that if Peras is disabled (which is the default), there is no observable difference" — CHANGELOG), but the vulnerability is fully reachable in any private testnet or staging environment where Peras is enabled. The exploit requires no privileged access, no key material, and no stake — only the ability to send a well-formed `PerasCert` message to a peer. [6](#0-5) 

### Recommendation

Replace the stub `validatePerasCert` and `validatePerasVote` implementations with real cryptographic verification before enabling Peras in any environment. Specifically:

1. `validatePerasCert` must call `verifyCert` (e.g., `implVerifyCert` from `WFALS` or `EveryoneVotes`) against the current epoch's `VotingCommittee`, verifying the aggregate BLS vote signature and all VRF eligibility proofs.
2. `validatePerasVote` must call `verifyVote` against the same committee.
3. Until the real implementation is in place, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that enabling Peras does not silently open the bypass.

### Proof of Concept

On a private testnet with Peras enabled:

```
-- Attacker constructs a PerasCert pointing to a block on a minority fork:
let craftedCert = PerasCert
      { pcCertRound    = <any round>
      , pcCertBoostedBlock = <point on attacker's fork>
      }

-- Submit via the Peras certificate diffusion miniprotocol.
-- validatePerasCert is called; it returns Right unconditionally.
-- The certificate is added to PerasCertDB with full perasWeight boost.
-- chainSelectionForBlock is triggered for the boosted block.
-- The honest node switches to the attacker's fork.
```

No cryptographic material is required. The bypass is identical in structure to the `ecrecover`-returns-zero case: the verification function returns a success value for all inputs, including malformed ones, because the check body is a stub. [1](#0-0) [7](#0-6)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
