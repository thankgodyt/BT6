### Title
Broken `execute_refund` Re-Execution Permanently Locks User Refund Funds — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `execute_refund` function is explicitly designed to be re-callable to re-create a refund transaction (e.g., after a consensus branch change or a stuck MPC signing). However, `finalize_refund_with_psbt` unconditionally requires the `btc_pending_id` to not already exist in `btc_pending_infos`. Because `btc_pending_id` is deterministically derived from the fixed PSBT inputs (same deposit UTXO, same refund address, same amount), any second call to `execute_refund` always panics with `"pending info already exist"`. If the first execution's `BTCPendingInfo` gets stuck, the user's BTC refund is permanently locked in a state that requires operator intervention to resolve.

---

### Finding Description

In `finalize_refund_with_psbt`, the code inserts a new `BTCPendingInfo` and asserts it did not previously exist: [1](#0-0) 

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

The `btc_pending_id` is computed by `generate_btc_pending_sign_id` as a SHA-256 hash of the PSBT signing payload preimages: [2](#0-1) 

For a refund, the PSBT is always built from the same fixed inputs: the deposit UTXO outpoint, the deposit output script, and the refund output (fixed address and amount from the stored `RefundRequest`). Therefore `btc_pending_id` is identical on every call to `execute_refund` for the same refund request.

The code comment at lines 395–401 explicitly states the intent that re-execution must be possible: [3](#0-2) 

```rust
// Keep the request (so `execute_refund` can be called again to re-create
// the transaction) but mark it executed; it is removed only when the
// refund is finalized in `verify_refund_finalize`.
refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

The `load_refund_request_for_execute` guard correctly allows re-entry when `executed == true`: [4](#0-3) 

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

So the guard passes on the second call, but execution panics later inside `finalize_refund_with_psbt` at the `"pending info already exist"` check. The implementation directly contradicts the documented intent.

Furthermore, the only cleanup path — `internal_remove_refund_pending_tx_id` — is blocked while the refund request is still active: [5](#0-4) 

```rust
require!(
    !self
        .data()
        .refund_requests
        .contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
```

Since the refund request is kept with `executed = true` until `verify_refund_finalize` succeeds, neither the user nor anyone else can remove the stuck `BTCPendingInfo` without operator intervention (`reject_refund` first, then `remove_refund_pending_tx_id`).

---

### Impact Explanation

If the first `execute_refund` call creates a `BTCPendingInfo` that becomes stuck — because MPC signing fails, or because the signed transaction is never confirmed on-chain (e.g., insufficient fee) — the user's BTC refund is permanently locked in a stuck state. The user cannot:

- Call `execute_refund` again (panics with `"pending info already exist"`).
- Call `remove_refund_pending_tx_id` (blocked by `"refund request still active"`).

Resolution requires an operator to call `reject_refund` (removing the refund request) followed by `remove_refund_pending_tx_id`, after which the user must restart the entire refund process from `request_refund`. This is a stuck bridge state requiring operator intervention, matching the Medium allowed impact.

---

### Likelihood Explanation

The stuck state is triggered by realistic production conditions:

1. **MPC signing failure**: The MPC service (`chain_signatures`) can be temporarily or permanently unavailable (downtime, key rotation). `sign_btc_transaction_callback` returns `false` on failure without removing the `BTCPendingInfo`, leaving it in `PendingSign` state indefinitely.
2. **Transaction non-confirmation**: The refund gas fee is fixed at request time in the `RefundRequest` and cannot be increased. If network fees rise after the request is created, the broadcast refund transaction may never confirm, leaving the `BTCPendingInfo` in `PendingVerify` state indefinitely. There is no RBF mechanism for refund transactions.

Any user who has submitted a refund request can trigger this stuck state simply by calling `execute_refund` once and then attempting to call it again after the first execution stalls.

---

### Recommendation

Before inserting a new `BTCPendingInfo` in `finalize_refund_with_psbt`, check whether one already exists for the same `btc_pending_id` and remove it first (since the intent is to replace the stale pending info with a fresh one). Alternatively, relax the guard in `internal_remove_refund_pending_tx_id` to allow removal of a stuck refund `BTCPendingInfo` when the associated refund request has `executed == true`, so users can self-service the cleanup without operator intervention.

---

### Proof of Concept

1. User calls `request_refund` for deposit UTXO `X` → `RefundRequest` stored with `executed = false`.
2. Timelock passes; user calls `execute_refund("X@0", None)` → `finalize_refund_with_psbt` runs, inserts `BTCPendingInfo` with `btc_pending_id = H(psbt_inputs)`, sets `executed = true`.
3. MPC signing fails (or signed tx is broadcast but never confirmed due to low fee).
4. User calls `execute_refund("X@0", None)` again → same PSBT is built → same `btc_pending_id = H(psbt_inputs)` → `require!(...is_none(), "pending info already exist")` **panics**.
5. User calls `remove_refund_pending_tx_id(btc_pending_id)` → **panics** with `"refund request still active"`.
6. User's BTC refund is permanently stuck. Only an operator calling `reject_refund` followed by `remove_refund_pending_tx_id` can unblock it, after which the user must restart the entire refund flow.

pub fn generate_btc_pending_sign_id(payload_preimages: &[Vec<u8>]) -> String {
    let hash_bytes = env::sha256_array(
        payload_preimages
            .iter()
            .flatten()
            .copied()
            .collect::<Vec<u8>>(),
    );
    hex::encode(hash_bytes)
}
