### Title
`is_structure_equal` vacuously accepts `{}` against any object template, bypassing `post_action_msg_templates` whitelist — (`contracts/satoshi-bridge/src/json_utils.rs`)

### Summary
The structural equality check in `is_structure_equal` treats all template keys as optional (Rule 1 in the docstring). When the input is an empty JSON object `{}`, both the template-key loop and the extra-key loop are vacuously satisfied, causing the function to return `true` for any object-typed template. This allows a depositor to supply `post_action.msg="{}"` and pass the `post_action_msg_templates` guard in `check_deposit_msg`, forwarding an unconstrained empty-object message to any whitelisted DeFi contract.

### Finding Description
`is_structure_equal` in `json_utils.rs` implements two loops over an `(Object, Object)` pair:

1. For each key in the **template**, check the input value if present (optional-field semantics).
2. For each key in the **input**, reject if not in the template (no-extra-fields semantics).

When `input = {}`, loop 1 finds no matching keys (all template keys are absent, treated as optional) and loop 2 iterates zero keys. Both loops exit without returning `false`, so the function returns `true`. [1](#0-0) 

In `check_deposit_msg`, when `post_action_msg_templates` contains at least one JSON-object template for the receiver, the guard calls `is_structure_equal` and accepts the message if any template matches. Because `{}` matches every object template, the guard is trivially bypassed. [4](#0-3) 

### Impact Explanation
A depositor can forward `msg="{}"` to any whitelisted DeFi contract (e.g. Burrowland) via `ft_transfer_call` after a successful nBTC mint. The `post_action_msg_templates` whitelist is intended to restrict which message structures are permitted; this bypass defeats that restriction entirely for any object-typed template. The whitelisted contract receives an `ft_on_transfer` call with `msg="{}"` — behavior depends on the contract's parser, but the bridge policy is violated regardless. This matches **Medium: bypass of bridge limits or policies**.

### Likelihood Explanation
The attack requires only that:
- The receiver is on `post_action_receiver_id_white_list` (a normal deployment condition).
- `post_action_msg_templates` has at least one JSON-object template for that receiver (the feature's intended use case).

The depositor controls the full `DepositMsg` content because the deposit address is derived from its hash. No privileged access is needed beyond a normal BTC deposit routed through any trusted relayer.

### Recommendation
Require that the input object is **non-empty** before accepting an object match, or change the semantics so that all template keys are **required** (not optional) in the input. Concretely, in the `(Value::Object(t_obj), Value::Object(i_obj))` branch, add a check that every key present in `t_obj` is also present in `i_obj` (unless the template value is `Value::Null`, which is the documented "unconstrained" sentinel):

```rust
for (key, t_val) in t_obj {
    match i_obj.get(key) {
        Some(i_val) => {
            if !is_structure_equal(t_val, i_val) {
                return false;
            }
        }
        None => {
            // Only allow omission when the template value is Null (unconstrained).
            if !matches!(t_val, Value::Null) {
                return false;
            }
        }
    }
}
```
