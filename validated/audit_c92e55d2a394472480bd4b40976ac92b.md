### Title
Missing Ownership Validation in `withdraw_rbf` Allows Any User to Modify Another User's Withdrawal Transaction - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
The `withdraw_rbf` function does not validate that the caller is the owner of the `BTCPendingInfo` identified by `original_btc_pending_verify_id`. Any unprivileged NEAR account can invoke `withdraw_rbf` against a victim's pending withdrawal, supplying attacker-controlled `output` (BTC destination addresses and amounts), which is then forwarded to the MPC signing pipeline.

### Finding Description
`withdraw_rbf` is the public, permissionless entry point that allows a user to bump the gas fee on their own pending withdrawal via Replace-By-Fee. Its implementation reads the caller's identity from `env::predecessor_account_id()` and immediately passes it — without any cross-check against the `account_id` stored inside the targeted `BTCPendingInfo` — to `withdraw_rbf_chain_specific`: [1](#0-0) 

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← attacker's ID
    self.require_pending_sign_capacity(&account_id);  // ← checks attacker's quota, not victim's

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← attacker passed as "owner"
        original_btc_pending_verify_id,      // ← victim's pending tx
        output,                              // ← fully attacker-controlled outputs
        chain_specific_data,
    );
}
```

The correct pattern is demonstrated by `cancel_withdraw`, which reads the owner **from the pending info itself** before proceeding: [2](#0-1) 

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id          // ← reads owner from stored state
        .clone();
    self.require_pending_sign_capacity(&user_account_id);
    ...
}
```

`BTCPendingInfo` stores the authoritative owner in its `account_id` field: [3](#0-2) 

`withdraw_rbf` never reads that field, so the binding between the caller and the resource being modified is never established — the exact structural flaw described in the external report.

### Impact Explanation
An attacker who supplies a victim's `original_btc_pending_verify_id` and an attacker-controlled `output` vector (containing the attacker's BTC address) causes the bridge to build and submit a new RBF transaction that redirects the victim's BTC to the attacker. Once the MPC network signs and broadcasts this transaction, the victim's funds are irreversibly redirected. This constitutes unauthorized redirection of bridge-controlled funds — matching the **Critical** impact class: *Chain-signature / PSBT / transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds*.

### Likelihood Explanation
`withdraw_rbf` is a public, payable-free, permissionless function. Any NEAR account can call it at any time against any pending withdrawal that is in the `PendingSign` stage. No privileged access, leaked key, or social engineering is required. The attacker only needs to know (or observe on-chain) a victim's `btc_pending_id`, which is emitted as a public event (`GenerateBtcPendingInfo`) at withdrawal creation time. [4](#0-3) 

### Recommendation
Mirror the pattern used in `cancel_withdraw`: read the owner from the stored `BTCPendingInfo` and assert it equals `env::predecessor_account_id()` before proceeding.

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let caller = env::predecessor_account_id();
    // Read the authoritative owner from the stored pending info
    let account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(
        caller == account_id,
        "Only the withdrawal owner can call withdraw_rbf"
    );
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

### Proof of Concept

1. Alice calls `ft_on_transfer` (Withdraw variant) and a `BTCPendingInfo` is created with `account_id = alice`, `btc_pending_id = "abc123"`, targeting Alice's BTC address. The `GenerateBtcPendingInfo` event is emitted publicly.
2. Attacker observes `btc_pending_id = "abc123"` on-chain.
3. Attacker calls:
   ```
   withdraw_rbf(
       original_btc_pending_verify_id = "abc123",
       output = [TxOut { value: ..., script_pubkey: attacker_btc_address }],
       chain_specific_data = None,
   )
   ```
4. `account_id = env::predecessor_account_id()` = attacker. No ownership check is performed.
5. `withdraw_rbf_chain_specific(attacker, "abc123", attacker_output, ...)` is called, building a new RBF PSBT with attacker-controlled outputs.
6. The MPC network signs the RBF transaction; it is broadcast and confirms on Bitcoin, sending Alice's BTC to the attacker's address.
7. Alice's original pending info is superseded; her funds are permanently lost.
