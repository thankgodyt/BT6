### Title
DAO Refund Rejection Bypassed via Orphaned `BTCPendingInfo` After `execute_refund` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

After `execute_refund` creates a `BTCPendingInfo` entry in `PendingSign` state, a subsequent DAO call to `reject_refund` only removes the `RefundRequest` from `refund_requests` but leaves the `BTCPendingInfo` intact. Because `sign_btc_transaction` performs no check that the originating refund request still exists, the user can sign the MPC-backed refund transaction after rejection, obtain the signed bytes from the emitted event, and broadcast them to Bitcoin — bypassing the DAO's cancellation entirely.

### Finding Description

`execute_refund` calls `finalize_refund_with_psbt`, which:
1. Inserts a `BTCPendingInfo` (state `PendingInfoState::Refund`, stage `PendingSign`) into `btc_pending_infos`.
2. Inserts the UTXO key into `verified_deposit_utxo`.
3. Keeps the `RefundRequest` in `refund_requests` with `executed = true`. [1](#0-0) 

When DAO subsequently calls `reject_refund`, `internal_reject_refund` only removes the entry from `refund_requests`: [2](#0-1) 

It does **not** remove the `BTCPendingInfo`, does not remove the account's `btc_pending_sign_ids` entry, and does not clear `verified_deposit_utxo`. The `BTCPendingInfo` remains fully intact in `PendingSign` state.

`sign_btc_transaction` then checks only that the `BTCPendingInfo` exists and is in `PendingSign` state. For a refund transaction `get_original_tx_id()` returns `None`, so the RBF-parent check is skipped entirely. There is no check that the originating `RefundRequest` still exists in `refund_requests`: [3](#0-2) 

After signing completes, `sign_btc_transaction_callback` emits a `SignedBtcTransaction` event containing the fully-signed transaction bytes: [4](#0-3) 

The user reads those bytes from the event log and broadcasts the transaction to Bitcoin independently of any NEAR state.

The only intended cleanup path is `remove_refund_pending_tx_id`, callable only by a `#[trusted_relayer]`, which races against the user's `sign_btc_transaction` call: [5](#0-4) 

### Impact Explanation

The DAO's rejection of an in-flight refund is rendered ineffective. A user who has already called `execute_refund` can sign and broadcast the refund transaction to Bitcoin after the DAO rejects it, recovering the locked BTC to the refund address regardless of the DAO's decision. This is a direct bypass of the bridge's operator-controlled refund cancellation policy. Matches: **Medium — Bypass of bridge limits or policies**.

### Likelihood Explanation

The window exists whenever the DAO rejects a refund after `execute_refund` has already been called. The test `test_reject_refund_blocked_after_execute` explicitly exercises this path, confirming the DAO can and does reject post-execution. The user needs only to submit one `sign_btc_transaction` call before the trusted relayer submits `remove_refund_pending_tx_id`. Since NEAR block times are ~1 second and the relayer must observe the rejection event before acting, the race window is practically exploitable.

### Recommendation

`internal_reject_refund` should be extended to also remove any `BTCPendingInfo` entries whose UTXO storage key matches the rejected request. Alternatively, `sign_btc_transaction` (or `internal_sign_btc_transaction`) should verify that for a `Refund`-state pending info, the corresponding `RefundRequest` still exists in `refund_requests` before proceeding with the MPC signing call.

### Proof of Concept

1. User sends BTC to their deposit address on Bitcoin.
2. User calls `request_refund` on NEAR — `RefundRequest` is stored.
3. Timelock elapses; user calls `execute_refund` — `BTCPendingInfo` (PendingSign) is created, UTXO added to `verified_deposit_utxo`, `RefundRequest` kept with `executed = true`.
4. DAO calls `reject_refund` — `RefundRequest` is removed from `refund_requests`; `BTCPendingInfo` remains untouched.
5. User calls `sign_btc_transaction(btc_pending_sign_id, 0, 0)` — no check for refund request existence; MPC signs the transaction; `SignedBtcTransaction` event emitted with full signed tx bytes.
6. User reads signed bytes from the NEAR event log and broadcasts the transaction to Bitcoin.
7. BTC arrives at the refund address — DAO rejection has no effect. [2](#0-1) [6](#0-5) [7](#0-6)

        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {

                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
