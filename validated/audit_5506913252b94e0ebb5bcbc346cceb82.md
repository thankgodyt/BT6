### Title
Missing Proof-of-Possession Verification Before BLS Key Aggregation Enables Rogue Key Attack on Peras Certificate Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

---

### Summary

`aggregatePublicKeys` in `BLS.hs` carries an explicit documented precondition that all BLS public keys must have their Proof-of-Possession (PoP) verified before aggregation. The production certificate-verification path (`implVerifyCert` → `aggregateVoteVerificationKeys` → `aggregatePublicKeys`) never calls `verifyProofOfPossession`. This violates the precondition and leaves the aggregate-signature verification open to a classic BLS rogue-key attack, allowing an adversary committee member to forge a Peras quorum certificate that appears to include voters who never actually voted.

---

### Finding Description

**Root cause — undischarged precondition in `aggregatePublicKeys`**

`aggregatePublicKeys` in `BLS.hs` is explicitly documented:

```haskell
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  ...
  aggKey <-
    uncheckedAggregateVerKeysDSIGN   -- "unchecked" — no PoP enforcement
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
``` [1](#0-0) 

The precondition is never discharged. The `aggregateVoteVerificationKeys` implementation for `PerasBLSCrypto` calls `aggregatePublicKeys` directly, with no PoP check:

```haskell
aggregateVoteVerificationKeys _ pks = do
  aggPk <- BLS.aggregatePublicKeys @SIGN pks
  pure (PerasBLSCryptoAggregateVoteVerificationKey aggPk)
``` [2](#0-1) 

This is called from `implVerifyCert` in both the `WFALS` and `EveryoneVotes` committee implementations:

```haskell
aggVerificationKey <-
  bimap CryptoError id $
    aggregateVoteVerificationKeys
      (Proxy @crypto)
      voteVerificationKeys
bimap InvalidCertSignature id $
  verifyAggregateVoteSignature ...
``` [3](#0-2) [4](#0-3) 

`verifyProofOfPossession` is defined in `BLS.hs` but has no call sites in any production code path:

```haskell
verifyProofOfPossession ::
  PublicKey POP ->
  KeyHash StakePool ->
  ProofOfPossession ->
  Either String ()
``` [5](#0-4) 

**How the rogue-key attack works**

In BLS aggregate-signature schemes, if a public key `pk_A` is aggregated with a victim's key `pk_V` without first verifying that the holder of `pk_A` actually knows the corresponding secret key (i.e., without PoP), an adversary can register a rogue key `pk_A = pk_A_real − pk_V`. Then:

- Aggregate key: `pk_A + pk_V = pk_A_real − pk_V + pk_V = pk_A_real`
- The adversary signs with `sk_A_real`; the aggregate signature verifies against `pk_A_real`
- The certificate appears to carry votes from both seat `i` (adversary) and seat `j` (victim), but only the adversary signed

The committee members' public keys are stored in the `ExtWFAStakeDistr` and are public (they come from the ledger stake distribution), so the adversary can compute the rogue key in advance:

```haskell
data VotingCommittee crypto WFALS
  = WFALSVotingCommittee
  { extWFAStakeDistr :: !(ExtWFAStakeDistr (PublicKey crypto))
  ...
  }
``` [6](#0-5) 

The `PerasPublicKey` type bundles both a vote-signing key and a VRF key, both of which are BLS keys subject to the same attack:

```haskell
data PerasPublicKey
  = PerasPublicKey
  { perasVoteVerKey :: BLS.PublicKey SIGN
  , perasVRFVerKey  :: BLS.PublicKey VRF
  }
``` [7](#0-6) 

The codebase itself acknowledges the VRF swap-attack variant and defends against it via linearization in `linearizeAndVerifyVRFs`, but the analogous defense for vote-signing keys (PoP verification before `aggregatePublicKeys`) is absent: [8](#0-7) 

---

### Impact Explanation

An adversary who is a registered stake pool and is selected as a Peras committee member can register a rogue BLS vote-signing key crafted to cancel out one or more other committee members' keys. By doing so, they can forge a `PerasCert` / `WFALSCert` that passes `implVerifyCert` while claiming a quorum of voters that never actually voted. A forged quorum certificate causes honest nodes to accept an unauthorized block boost, directly corrupting Peras chain-selection by making a non-canonical or adversary-preferred chain appear to carry a valid certificate. This is a bypass of certificate-signature validation enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The adversary must be a registered stake pool (requires stake, but not admin/operator compromise or key theft) and must be selected as a committee member in the relevant epoch. Both conditions are achievable by a well-resourced but otherwise unprivileged network participant. The victim pool's public key is publicly visible in the stake distribution, so the rogue key can be computed offline. No interaction with the victim is required.

---

### Recommendation

1. **Enforce PoP verification before key aggregation.** Either verify PoPs inside `aggregateVoteVerificationKeys` (or `aggregatePublicKeys` itself), or verify them when the `VotingCommitteeInput` / `ExtWFAStakeDistr` is constructed from the ledger stake distribution.
2. **Call `verifyProofOfPossession` for every BLS public key** before it enters the committee state, binding each key to its pool's `KeyHash StakePool`.
3. **Consider making the precondition a type-level guarantee** (e.g., a `VerifiedPoP (PublicKey r)` newtype) so that `aggregatePublicKeys` cannot be called with unverified keys.

---

### Proof of Concept

```
-- Adversary setup (offline):
-- 1. Observe victim committee member V at seat j with public key pk_V.
-- 2. Compute rogue key: sk_A_rogue such that derivePublicKey sk_A_rogue = pk_A_real - pk_V
--    (i.e., pk_A_rogue + pk_V = pk_A_real, where sk_A_real is the adversary's true key)
-- 3. Register a stake pool with BLS key pk_A_rogue on the ledger.
--    (No PoP check prevents this registration.)

-- At certificate-forging time:
-- 4. Adversary A (seat i) signs the vote with sk_A_real.
-- 5. Adversary forges a WFALSCert / PerasCert claiming voters {i, j}.

-- At verification time (implVerifyCert):
-- 6. System looks up pk_A_rogue (seat i) and pk_V (seat j) from committee state.
-- 7. aggregateVoteVerificationKeys computes:
--      aggKey = aggregatePublicKeys [pk_A_rogue, pk_V]
--             = pk_A_rogue + pk_V
--             = pk_A_real
-- 8. verifyAggregateVoteSignature checks adversary's signature against pk_A_real => PASSES
-- 9. Certificate is accepted as having a quorum including V, who never voted.
```

-- | Aggregate multiple public keys into a single one.
--
-- PRECONDITION: all keys must have the same scope.
--
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  -- Ensure all keys have the same scope before aggregation
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $
    PublicKey
      { unPublicKey = aggKey
      , publicKeyScope = publicKeyScope firstKey
      }

-- | Verify a list of VRF outputs against on the same input using linearization.
--
-- The idea is to first aggregate all public keys and VRF outputs into a single
-- aggregate ones. These can then be verified in one go, saving the (higher)
-- cost of multiple signature verifications.
--
-- However, since we later derive a numeric value from each individual VRF
-- output, verifying the aggregate signature alone is not sufficient. This is
-- because an attacker could swap their (bad) VRF output with someone else's
-- (better) one, and a naive signature aggregation and verification approach
-- would still succeed.
--
-- Instead, each VRF output is first linearized using a scalar derived from the
-- signature itself, and then aggregated together. This way, if an attacker
-- tries to swap their VRF output with someone else's, the linearization will
-- produce a different aggregate signature that will fail verification.
--
-- PRECONDITION: all keys must have the same scope.
--
-- PRECONDITION: the number of signatures must match the number of keys.
linearizeAndVerifyVRFs ::
  SignableRepresentation msg =>
  NE [PublicKey VRF] ->
  msg ->
  NE [Signature VRF] ->
  Either String ()
linearizeAndVerifyVRFs keys@(firstKey :| restKeys) msg sigs = do
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"

  when (length sigs /= length keys) $
    Left "Number of signatures must match number of public keys"
