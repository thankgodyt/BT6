Audit Report

## Title
Missing `multiTokens` Registration Check in `initTransfer1155` Allows ERC1155 Token Freezing — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` accepts and locks ERC1155 tokens into the bridge without verifying that `multiTokens[deterministicToken]` was previously populated by `logMetadata1155`. When a user initiates an ERC1155 transfer without prior metadata registration, the tokens are locked in the bridge and `finTransfer` will revert on every relay attempt, as the ERC1155 dispatch branch is never entered. Recovery depends entirely on whether the NEAR-side relayer retries after a retroactive `logMetadata1155` call — a behavior not guaranteed by the EVM contract.

## Finding Description

`initTransfer1155` computes `deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId)` and immediately pulls tokens from the caller via `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` with no guard on `multiTokens[deterministicToken].tokenAddress`. [1](#0-0) 

The `onERC1155Received` operator check does not block this path: the bridge contract itself is the `operator` when it calls `safeTransferFrom`, so `operator == address(this)` passes. [2](#0-1) 

`multiTokens[deterministicToken]` is only populated by `logMetadata1155`. [3](#0-2) 

On the release side, `finTransfer` reads `multiToken = multiTokens[payload.tokenAddress]`. When `multiToken.tokenAddress == address(0)`, the ERC1155 branch is skipped and execution falls through to `IERC20(payload.tokenAddress).safeTransfer(...)`. Since `deterministicToken` is a `keccak256`-derived address with no deployed code, `safeTransfer` reverts. [4](#0-3) 

Because `completedTransfers[payload.destinationNonce] = true` is set before the transfer attempt, a revert rolls back that assignment, leaving the nonce unconsumed. The relayer can retry indefinitely but will always revert until `logMetadata1155` is called retroactively — and whether the NEAR-side relayer retries after that is not enforced by the EVM contract. [5](#0-4) 

There is no admin rescue or withdrawal function for locked ERC1155 tokens. [6](#0-5) 

## Impact Explanation

ERC1155 tokens are locked in the bridge with no on-chain recovery path enforced by the EVM contract. The NEAR-side relayer may never successfully finalize the transfer, constituting permanent or indefinite freezing of bridged funds — a Critical impact under the allowed scope (permanent freezing of bridged funds).

## Likelihood Explanation

`initTransfer1155` is permissionless and payable, callable by any token holder. The bridge is explicitly described as fully permissionless. No documentation or on-chain warning informs users of the mandatory two-step flow (`logMetadata1155` → `initTransfer1155`). Ordinary user error — not adversarial intent — is sufficient to trigger the loss. The function emits `InitTransfer` and increments `currentOriginNonce` normally, giving no indication of failure. [7](#0-6) 

## Recommendation

Add a registration guard at the top of `initTransfer1155`, before any token transfer:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
if (multiTokens[deterministicToken].tokenAddress == address(0)) {
    revert ERC1155NotRegistered();
}
```

This ensures tokens are only accepted after `logMetadata1155` has been successfully called for the `(tokenAddress, tokenId)` pair, mirroring the pattern already used in `logMetadata1155` itself. [8](#0-7) 

## Proof of Concept

1. Deploy `OmniBridge`. Do **not** call `logMetadata1155` for token `T`, id `42`.
2. Call `initTransfer1155(T, 42, 10, 0, 0, "victim.near", "")`. The call succeeds: 10 units of token `T` id `42` are transferred to the bridge, `currentOriginNonce` increments, and `InitTransfer` is emitted with `deterministicToken = deriveDeterministicAddress(T, 42)`.
3. The NEAR-side relayer observes `InitTransfer` and eventually triggers `finTransfer` on EVM with `payload.tokenAddress = deterministicToken`.
4. Inside `finTransfer`: `multiTokens[deterministicToken]` returns `{tokenAddress: address(0), tokenId: 0}`. The ERC1155 branch (`multiToken.tokenAddress != address(0)`) is skipped. Execution reaches `IERC20(deterministicToken).safeTransfer(recipient, 10)` — reverts because no code exists at `deterministicToken`.
5. The transaction reverts; `completedTransfers` is not updated. The relayer retries but always reverts. The 10 ERC1155 tokens remain locked in the bridge with no on-chain recovery mechanism.

        address tokenAddress,
        uint256 tokenId
    ) external payable {
        address deterministicToken = deriveDeterministicAddress(
            tokenAddress,

        MultiTokenInfo storage multiToken = multiTokens[deterministicToken];

        if (multiToken.tokenAddress == address(0)) {
            multiToken.tokenAddress = tokenAddress;
            multiToken.tokenId = tokenId;
        } else {
            if (
                multiToken.tokenAddress != tokenAddress ||
                multiToken.tokenId != tokenId
