### Title
Unchecked Withdrawal Ownership in `withdraw_rbf` Allows Attacker to Redirect Victim's BTC - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`withdraw_rbf` is a publicly callable function that allows any NEAR account to submit a Replace-By-Fee (RBF) transaction for any pending withdrawal, regardless of whether the caller owns that withdrawal. Because the function uses `env::predecessor_account_id()` (the caller) as the authorizing account rather than deriving the owner from the stored pending info, an attacker can supply a victim's `original_btc_pending_verify_id` together with attacker-controlled `output` entries that redirect the BTC to the attacker's address. The MPC signing pipeline then signs and broadcasts this attacker-crafted transaction.

---

### Finding Description

`withdraw_rbf` is documented as the mechanism by which **the withdrawal owner** accelerates their own pending withdrawal by increasing the gas fee. However, the function performs no check that the caller is the owner of the referenced pending withdrawal:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not owner
    self.require_pending_sign_capacity(&account_id);  // ← checks caller's quota

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller passed as "owner"
        original_btc_pending_verify_id,      // ← can be any user's pending ID
        output,                              // ← attacker-controlled outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

The contrast with `cancel_withdraw` (a privileged-only function) is instructive. There, the owner is **derived from the stored pending info** before any further action is taken:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();                            // ← owner taken from stored state
    self.require_pending_sign_capacity(&user_account_id);
    ...
}
``` [2](#0-1) 

`withdraw_rbf` never performs the equivalent lookup. It passes the caller's `AccountId` directly into `withdraw_rbf_chain_specific` as the authorizing identity, while simultaneously accepting an arbitrary `original_btc_pending_verify_id` that may belong to a completely different user. The `require_pending_sign_capacity` call is made against the **caller's** account, not the pending info's stored owner, so it provides no ownership gate. [3](#0-2) 

The `BTCPendingInfo` struct records the true owner in its `account_id` field, which is set at withdrawal creation time from `sender_id` (the `ft_on_transfer` caller): [4](#0-3) 

No code path in `withdraw_rbf` compares `env::predecessor_account_id()` against `btc_pending_info.account_id`.

---

### Impact Explanation

An attacker who observes a victim's `original_btc_pending_verify_id` (emitted as a public event via `GenerateBtcPendingInfo`) can call `withdraw_rbf` with:

- `original_btc_pending_verify_id` = victim's pending withdrawal ID
- `output` = a crafted output vector that pays the full BTC amount to the attacker's Bitcoin address

`withdraw_rbf_chain_specific` will construct a new RBF transaction using the attacker-supplied outputs and submit it to the MPC Chain Signatures service for signing. Once signed and broadcast, the victim's BTC is irreversibly sent to the attacker's address. The victim's original pending withdrawal is superseded by the RBF transaction.

This constitutes **unauthorized redirection of bridge-controlled BTC funds** — a Critical impact under the allowed scope.

---

### Likelihood Explanation

- `withdraw_rbf` carries no role restriction, no `#[trusted_relayer]` guard, and no `assert_one_yocto()` requirement. It is callable by any NEAR account.
- Pending withdrawal IDs are emitted as on-chain events (`GenerateBtcPendingInfo`) and are publicly observable.
- The attacker needs only a valid NEAR account and knowledge of a victim's pending withdrawal ID.
- No privileged access, key compromise, or external dependency failure is required.

Likelihood: **High**.

---

### Recommendation

Before delegating to `withdraw_rbf_chain_specific`, verify that the caller is the owner of the referenced pending withdrawal:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();

    // Verify caller owns the pending withdrawal
    let pending_owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(
        account_id == pending_owner,
        "Only the withdrawal owner can submit an RBF"
    );

    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

This mirrors the pattern already used correctly in `cancel_withdraw`.

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message. The bridge emits `GenerateBtcPendingInfo { account_id: "alice.near", btc_pending_id: "abc123" }`.
2. Attacker Eve observes `btc_pending_id = "abc123"` from chain events.
3. Eve calls `withdraw_rbf("abc123", [TxOut { value: <full_amount>, script_pubkey: <eve_btc_address> }], None)`.
4. `withdraw_rbf` sets `account_id = "eve.near"`, passes Eve's capacity check (she has 0 pending txs), and calls `withdraw_rbf_chain_specific("eve.near", "abc123", [eve_output], None)`.
5. The RBF transaction is constructed with Eve's output, submitted to Chain Signatures, signed by MPC, and broadcast to Bitcoin.
6. Alice's BTC is sent to Eve's Bitcoin address. Alice's original pending withdrawal is invalidated. [5](#0-4)
