### Title
Sub-Minimum nBTC Remainder After Partial Withdrawal Leaves Balance Unwithdrawable - (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary
`ft_on_transfer` enforces `amount >= min_withdraw_amount` on the withdrawal amount itself, but never checks that the sender's remaining nBTC balance after the withdrawal is either zero or also `>= min_withdraw_amount`. A user can therefore withdraw a partial amount that leaves a sub-minimum remainder that cannot be directly redeemed for BTC.

### Finding Description
The bridge's withdrawal entry point is `ft_on_transfer`, called by the nBTC contract when a user invokes `ft_transfer_call(bridge, amount, WithdrawMsg)`. The only balance-related guard is:

```rust
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
``` [1](#0-0) 

There is no check that `user_balance - amount >= min_withdraw_amount || user_balance - amount == 0`. The bridge never queries the nBTC token contract for the sender's remaining balance before accepting the withdrawal.

`min_withdraw_amount` is a configurable parameter (e.g., 70,000 satoshis in test setup): [2](#0-1) 

A user holding 150,000 nBTC satoshis can call `ft_transfer_call(bridge, 90_000, WithdrawMsg)`. The check passes (90,000 >= 70,000), the withdrawal proceeds, and 60,000 nBTC remains in the user's account — below `min_withdraw_amount`. Any subsequent attempt to withdraw that remainder will fail the same `require!` guard.

### Impact Explanation
The user's remaining nBTC balance below `min_withdraw_amount` cannot be directly redeemed for BTC through the bridge. The user must either receive additional nBTC to bring their balance back above the minimum, or transfer the remainder to a third party who can aggregate it. This is a publicly reachable invariant violation: the bridge's minimum-withdrawal policy is intended to ensure every withdrawal is economically viable, but it does not prevent a user from ending up in a state where their remaining balance violates that policy. Funds are not permanently destroyed — they remain as nBTC — but the bridge's core redemption path is blocked for that remainder without external action.

**Severity: Low** — no direct theft; funds are not permanently locked (nBTC is a standard NEP-141 token and can be transferred), but the bridge's own withdrawal path is unavailable for the sub-minimum remainder.

### Likelihood Explanation
Any user who withdraws a partial amount of their nBTC balance where the remainder is non-zero and below `min_withdraw_amount` triggers this condition. No special privileges or attacker cooperation are required — the user only needs to choose a withdrawal amount that is itself valid (`>= min_withdraw_amount`) but leaves a sub-minimum residue. This is a routine scenario for any user who does not hold a balance that is an exact multiple of `min_withdraw_amount`.

### Recommendation
After confirming `amount >= min_withdraw_amount`, also verify that the sender's post-withdrawal balance is either zero or `>= min_withdraw_amount`. Because the bridge cannot read the nBTC balance synchronously without a cross-contract call, the simplest mitigation is to require the user to pass their total nBTC balance as the withdrawal amount (i.e., withdraw-all semantics) or to add a cross-contract view of `ft_balance_of` before accepting the withdrawal and enforce the post-withdrawal invariant in the callback.

### Proof of Concept
1. `min_withdraw_amount` = 70,000 satoshis (representative production value).
2. Alice holds 150,000 nBTC satoshis.
3. Alice calls `nbtc.ft_transfer_call(bridge, "90000", WithdrawMsg{...})`.
4. Bridge `ft_on_transfer` receives `amount = 90,000`. Check `90,000 >= 70,000` passes. [1](#0-0) 

5. Withdrawal proceeds; Alice's nBTC balance becomes 60,000.
6. Alice attempts `nbtc.ft_transfer_call(bridge, "60000", WithdrawMsg{...})`.
7. Bridge `ft_on_transfer` receives `amount = 60,000`. Check `60,000 >= 70,000` **fails** → `"Invalid amount"` revert.
8. Alice's 60,000 nBTC cannot be redeemed for BTC through the bridge without first acquiring at least 10,000 more nBTC.
