### Title
Floor Division in `normalize_amount` Permanently Locks User Tokens When Transfer Amount Rounds to Zero - (`File: near/omni-bridge/src/lib.rs`)

### Summary

The `normalize_amount` function in the NEAR omni-bridge contract uses integer floor division to scale token amounts across decimal boundaries. When a user initiates a transfer whose `amount_without_fee` is smaller than `10^diff_decimals`, the normalized amount rounds to zero. The `sign_transfer` function then unconditionally panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, but the user's tokens were already locked or burned during `init_transfer_internal`. There is no automatic cancellation or refund path triggered by this failure, leaving the tokens permanently frozen in the bridge.

### Finding Description

`normalize_amount` performs a plain integer division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

The code comment above this function acknowledges floor division produces "dust" but only addresses the case where `normalize_amount > 0`. It does not address the case where the entire amount rounds to zero: [2](#0-1) 

The transfer lifecycle is:

**Step 1 — Tokens locked/burned during `init_transfer_internal`:**

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(..., transfer_message.amount.0);
``` [3](#0-2) 

**Step 2 — `sign_transfer` computes the normalized amount and panics if it is zero:**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [4](#0-3) 

When `sign_transfer` panics, the NEAR runtime reverts only that call. The transfer message remains in `pending_transfers` and the tokens remain locked or burned. No automatic refund or cancellation is triggered.

**Concrete example:**
- Token with `origin_decimals = 24`, `decimals = 8` (diff = 16).
- User sends `amount = 10^15` base units (= 0.000000001 tokens).
- `normalize_amount(10^15, diff=16) = 10^15 / 10^16 = 0`.
- `sign_transfer` panics; tokens are permanently frozen.

For tokens with `origin_decimals = 24` and `decimals = 18` (diff = 6, common for NEAR → EVM), any transfer below `10^6` base units triggers this path.

### Impact Explanation

User tokens are permanently locked in the bridge escrow (for native tokens) or permanently burned (for deployed bridge tokens) with no automatic recovery path. This constitutes permanent freezing of bridged funds. The transfer message persists in storage but can never be finalized, and no cancel/refund entrypoint is triggered by the `sign_transfer` panic.

### Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` → `ft_on_transfer` with a sufficiently small amount. The `init_transfer` validation only checks `fee < amount`; it does not validate that `normalize_amount(amount - fee) > 0`. [5](#0-4) 

For tokens with large decimal differences (e.g., 24 vs 8), the threshold below which funds are permanently lost is `10^16` base units — a non-negligible quantity for high-value tokens. The scenario is realistic for any user who sends a "dust" amount or makes a UI rounding error.

### Recommendation

Add a pre-flight check in `init_transfer` (before locking/burning tokens) that validates the normalized amount is greater than zero:

```rust
let normalized = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0).ok_or(...)?,
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the fix applied to the GroupBuy M-09 issue: validate the rounding constraint at the point of commitment, not after funds are already escrowed.

### Proof of Concept

1. Deploy a NEAR token with `origin_decimals = 24`; register it on the bridge with EVM `decimals = 8` (diff = 16).
2. Call `ft_transfer_call` with `amount = 5 * 10^15` (5 quadrillion base units, well below `10^16`), `fee = 0`, valid EVM recipient.
3. `init_transfer_internal` locks/burns `5 * 10^15` tokens. Transfer message stored.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(5 * 10^15, diff=16) = 0` → panic `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Transfer message remains in storage; tokens are permanently frozen. No refund is issued. [4](#0-3) [3](#0-2)
