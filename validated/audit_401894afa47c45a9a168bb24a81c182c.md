### Title
Unvalidated `refund_address` at Request Time Enables Griefing Attack That Temporarily Locks User Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund` entry point accepts a caller-supplied `refund_address` string and stores it in a `RefundRequest` without validating that it is a parseable, network-correct Bitcoin/Zcash address. Address parsing only occurs later, inside `execute_refund` → `build_refund_output`, where an invalid address causes an irrecoverable `expect`-panic. Because only one refund request per UTXO is allowed at a time, an attacker can front-run a legitimate user's refund with an invalid address, permanently blocking `execute_refund` for that request and forcing DAO/Operator intervention before the victim can resubmit.

### Finding Description
In `internal_request_refund`, the only check on `refund_address` is an equality comparison against `deposit_msg.refund_address` when that optional field is set: [1](#0-0) 

No format, length, or network-correctness validation is performed. The address is stored verbatim in `RefundRequest.refund_address`: [2](#0-1) 

Address parsing is deferred to `build_refund_output`, called from `execute_refund`: [3](#0-2) 

The `expect("Invalid refund address")` call panics and aborts the entire `execute_refund` transaction if the stored address is malformed or for the wrong network. There is no recovery path inside `execute_refund` itself.

Meanwhile, `request_refund_callback` enforces a one-request-per-UTXO invariant: [4](#0-3) 

This means a second, legitimate `request_refund` for the same UTXO is rejected with "Refund request already exists for this UTXO" until the poisoned request is explicitly removed by a DAO/Operator `reject_refund` call.

The public entry point `request_refund` in `api/bridge.rs` is callable by any NEAR account with sufficient attached deposit: [5](#0-4) 

### Impact Explanation
An attacker who observes an unfinalized deposit UTXO on the Bitcoin chain (all data — `tx_bytes`, `vout`, Merkle proof, and `deposit_msg` — are publicly visible on-chain) can submit `request_refund` with a syntactically invalid or wrong-network `refund_address` before the legitimate depositor does. The stored request causes every subsequent `execute_refund` call to panic. The victim's BTC remains locked at the bridge-controlled deposit address with no way to recover it until a DAO/Operator calls `reject_refund`. This matches **Medium: attacker-triggered temporary locking of bridged funds requiring operator intervention**.

### Likelihood Explanation
The attack requires:
1. Monitoring the Bitcoin blockchain for deposits whose corresponding `verify_deposit` was never submitted (e.g., relayer failure, dust amounts, wrong network).
2. Reconstructing the `deposit_msg` (available from OP_RETURN data or the deposit address derivation path).
3. Paying the non-refundable storage deposit for `request_refund`.

All inputs are public; no privileged access is needed. The cost to the attacker is only the storage deposit. Likelihood is **Low-Medium**.

### Recommendation
Validate `refund_address` against the configured chain/network at `request_refund` time, before storing the `RefundRequest`. Specifically, call `crate::network::Address::parse(&refund_address, config.chain.clone())` inside `internal_request_refund` and return an error (or `require!` failure) immediately if parsing fails. This mirrors the validation already performed in `build_refund_output` but moves it to the entry point where it can be rejected cheaply and without storing state.

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: None }`. The relayer fails to submit `verify_deposit`.

2. Bob (attacker) observes the unconfirmed/confirmed deposit on-chain. He calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None },
     refund_address = "INVALID_ADDRESS_XYZ",   // malformed, no network check
     tx_bytes = <Alice's tx bytes>,
     vout = 0,
     proof = <valid Merkle proof>,
     gas_fee = None,
   )
   ```
   with the required attached deposit. The light-client verification passes; `request_refund_callback` stores `RefundRequest { refund_address: "INVALID_ADDRESS_XYZ", ... }`.

3. Alice tries to call `request_refund` with her real address. It reverts: `"Refund request already exists for this UTXO"`.

4. Anyone calls `execute_refund(utxo_storage_key, None)`. Inside `build_refund_output`, `Address::parse("INVALID_ADDRESS_XYZ", chain)` returns `Err`, and `.expect("Invalid refund address")` panics. The call aborts; the `RefundRequest` remains.

5. Alice's BTC is locked until a DAO/Operator calls `reject_refund(utxo_storage_key)`, after which Alice can resubmit with her correct address and wait out the full timelock again.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
