### Title
Peras Certificate Validation Unconditionally Returns Success, Enabling Unprivileged Peer to Manipulate Chain Selection Weight - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. Any unprivileged peer can send a crafted `PerasCert` pointing to any block in the VolatileDB; the certificate is accepted, stored in `PerasCertDB`, and used to boost that block's chain weight in chain selection. When Peras is enabled, this allows an attacker to make an honest node prefer a non-canonical fork over the legitimate chain.

### Finding Description

The degenerate `BlockSupportsPeras` instance (the only production instance, covering all `StandardHash blk` blocks) implements `validatePerasCert` as an unconditional success:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is structurally identical to the reported Chainlink bug: a validation function that is supposed to check a proof/certificate but instead always returns success because the required state (here: actual cryptographic/quorum checks) is never consulted.

The attacker-controlled entry path is:

1. A peer sends a batch of `PerasCert` objects via the object-diffusion mini-protocol.
2. `makePerasVotePoolWriterFromChainDB` → `processCerts` calls `validatePerasCert mkPerasParams` on each certificate not already in the DB. [2](#0-1) 

3. `processCerts` accepts the batch if all validations pass (they always do) and calls `addCert` for each. [3](#0-2) 

4. `addPerasCertAsync` enqueues the certificate for chain selection processing. [4](#0-3) 

5. `chainSelSync` processes the certificate: it stores it in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block, using the `vpcCertBoost` weight from the fake certificate. [5](#0-4) 

6. Chain selection now compares candidate fragments using Peras weight. The boosted fork gains `perasWeight params` additional weight, potentially making it preferred over the canonical chain.

The `PerasCert` type contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — both fully attacker-controlled over the wire. No quorum proof, no aggregate signature, no committee membership check is performed. [6](#0-5) 

### Impact Explanation

When Peras is enabled via feature flags, an unprivileged peer can send a single crafted `PerasCert` that boosts any block already present in the node's VolatileDB. Chain selection then re-evaluates candidates using the inflated weight, and the node may switch to a non-canonical fork. This is a **High** severity chain-selection bug: it lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of Ouroboros Peras.

### Likelihood Explanation

Peras is currently disabled by default but is an experimental feature that can be enabled via `rnFeatureFlags`. Any node operator enabling Peras is immediately exposed. The attack requires only a network connection to the target node and the ability to send a single well-formed (but cryptographically invalid) `PerasCert` message — no keys, no stake, no privileged access.

### Recommendation

Replace the stub implementation with actual certificate validation before Peras is enabled in production. At minimum, `validatePerasCert` must verify:
- The certificate's aggregate vote signature covers the claimed `pcCertBoostedBlock` and `pcCertRound`.
- The signers constitute a valid quorum of the committee for that round (using the epoch nonce and stake distribution).
- The round number is within the valid window.

The existing `implVerifyCert` logic in `WFALS.hs` and `EveryoneVotes.hs` demonstrates the correct pattern (membership check + aggregate signature verification). The `validatePerasCert` stub should be wired to the appropriate committee-aware verification before the feature flag is enabled on any production node. [7](#0-6) 

### Proof of Concept

With Peras enabled and a node that has block `B_fork` (a fork block) in its VolatileDB:

1. Attacker connects as a peer.
2. Attacker sends via the cert diffusion protocol:
   ```
   PerasCert { pcCertRound = <any valid round>, pcCertBoostedBlock = point(B_fork) }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
4. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` is called.
5. `chainSelSync` triggers `chainSelectionForBlock` for `B_fork`.
6. The chain containing `B_fork` now has weight boosted by `perasWeight`, making it preferred over the canonical chain of equal or slightly greater length.
7. The node switches to the fork. [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
