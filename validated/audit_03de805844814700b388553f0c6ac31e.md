### Title
Any Caller Can Redirect Unfinalized BTC Deposits to an Arbitrary Address via `request_refund` When `deposit_msg.refund_address` Is `None` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user deposits BTC using a `DepositMsg` with `refund_address: None` and the deposit is never finalized, any NEAR account can call `request_refund` with an arbitrary attacker-controlled BTC address. After the `unsafe_refund_timelock_sec` window elapses (if the DAO does not reject), the attacker can call the permissionless `execute_refund` and `sign_btc_transaction` functions to have the MPC network sign a PSBT that sends the BTC to the attacker's address instead of the depositor's address.

### Finding Description
In `internal_request_refund`, the `refund_address` is only validated against `deposit_msg.refund_address` when the latter is `Some`:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` is accepted unconditionally and stored verbatim in the `RefundRequest`:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 564-574
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-controlled
    ...
};
```

The full `deposit_msg` (including the fact that `refund_address` is `None`) is publicly broadcast on-chain via the `LogDepositAddress` event emitted by `get_user_deposit_address`. An attacker who observes this event can reconstruct the exact `deposit_msg` and submit a `request_refund` call with their own BTC address before the legitimate depositor does.

Once the `RefundRequest` is stored, a second `request_refund` for the same UTXO is rejected (`"Refund request already exists for this UTXO"`), so the depositor is locked out.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone (no caller restriction beyond the pause guard). It builds a PSBT paying `refund_amount` to the stored `refund_address` (the attacker's address) and creates a `BTCPendingInfo` owned by the caller:

```rust
// contracts/satoshi-bridge/src/refund.rs lines 344-345
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
};
```

`sign_btc_transaction` likewise has no caller restriction — any account can trigger MPC signing for any pending transaction:

```rust
// contracts/satoshi-bridge/src/api/chain_signatures.rs lines 21-43
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> { ... }
```

Once signed, the attacker broadcasts the transaction and the BTC is irreversibly sent to their address. The depositor receives nothing.

The DAO can call `reject_refund` during the `unsafe_refund_timelock_sec` window (and even after `execute_refund` but before signing completes), but this is an off-chain operational dependency, not an on-chain guarantee. If the DAO is slow, offline, or simply does not notice the suspicious request, the theft completes.

### Impact Explanation
A depositor who sent real BTC to a bridge deposit address derived from a `DepositMsg` with `refund_address: None` — and whose deposit was never finalized — permanently loses their BTC to the attacker. This is a direct, irreversible theft of user funds with no on-chain recourse once the Bitcoin transaction confirms.

### Likelihood Explanation
- `deposit_msg.refund_address: None` is a valid and documented usage (the field is `Option<String>` and `skip_serializing_if = "Option::is_none"`).
- The full `deposit_msg` is emitted publicly via `LogDepositAddress`, making it trivially observable by any on-chain monitor.
- Deposits can fail to finalize for legitimate reasons (relayer downtime, user changed mind), creating a realistic window.
- The `unsafe_refund_timelock_sec` is finite; if the DAO monitoring is delayed or the DAO key is unavailable, the window closes and the theft proceeds.
- `sign_btc_transaction` requires no special role, so the attacker completes the full chain unilaterally.

### Recommendation
1. **Require `deposit_msg.refund_address` to be set** before a `request_refund` is accepted, eliminating the unconstrained-address path entirely.
2. **Or**, restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (the intended nBTC recipient) can submit the request, binding the refund destination to the depositor's identity.
3. **Or**, store the `recipient_id` in the `RefundRequest` and enforce that `execute_refund` can only be called by that account (or a privileged role), preventing a third party from completing the theft even if they submitted the request.

### Proof of Concept
1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The full `deposit_msg` is emitted in a `LogDepositAddress` event.
2. Alice sends BTC to the returned deposit address. The relayer never calls `verify_deposit`.
3. Attacker observes the `LogDepositAddress` event, reconstructs `deposit_msg`, and calls:
   `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)`
   — accepted because `deposit_msg.refund_address` is `None`.
4. The `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`. Alice's subsequent `request_refund` fails: `"Refund request already exists for this UTXO"`.
5. After `unsafe_refund_timelock_sec` elapses (DAO did not reject), attacker calls `execute_refund(utxo_storage_key, None)`. A PSBT paying Alice's BTC to `"attacker_btc_addr"` is built and stored.
6. Attacker calls `sign_btc_transaction(btc_pending_sign_id, 0, 0)`. The MPC network signs the PSBT.
7. Attacker broadcasts the signed transaction. Alice's BTC is permanently transferred to the attacker's address. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) [7](#0-6)

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
