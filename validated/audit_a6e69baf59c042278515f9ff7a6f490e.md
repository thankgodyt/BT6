### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Forge Peras Certificates and Manipulate Chain Selection — (`Ouroboros/Consensus/Block/SupportsPeras.hs`, `MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally returns `Right` for every input. An unprivileged ObjectDiffusion peer can therefore send a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any valid block already in the VolatileDB. The cert passes `processCerts`, is enqueued via `addPerasCertAsync`, and the ChainDB background thread calls `chainSelectionForBlock` on the attacker-chosen block with the fake boost applied to the `PerasWeightSnapshot`. If the boosted fork's total weight (`blockNo + 15`) exceeds the current chain's weight, the node switches to the adversarially-chosen fork.

---

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

The degenerate instance (line 320: "TODO: degenerate instance for all blks to get things to compile") unconditionally returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` with no committee membership check, no quorum check, and no cryptographic signature verification.

**Production writer uses this stub:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator: [2](#0-1) 

**`processCerts` accepts every cert:** [3](#0-2) 

Because `validateCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and `addCert` (= `void . ChainDB.addPerasCertAsync chainDB`) is called for every cert.

**ChainDB processes the cert and triggers chain selection:**

`chainSelSync (ChainSelAddPerasCert ...)` has only two early-exit guards before calling `chainSelectionForBlock`:

1. Boosted block's slot is older than the immutable tip (line 490).
2. Boosted block is not yet in the VolatileDB (line 520–526).

If neither guard fires — i.e., the attacker's chosen block is in the VolatileDB and recent enough — `chainSelectionForBlock` is called unconditionally: [4](#0-3) 

**The fake boost is already in the `PerasWeightSnapshot` at this point.** The cert was added to `PerasCertDB` at line 495, which updates the weight snapshot. `chainSelectionForBlock` reads the snapshot at line 634 and passes it to `constructPreferableCandidates` and `chainSelection`. The comparison in `preferCandidate` uses `wsvTotalWeight = blockNo + weightBoost`: [5](#0-4) 

**The boost magnitude is `perasWeight = PerasWeight 15`:** [6](#0-5) 

A fork that is up to 15 blocks shorter than the current chain can be made to appear heavier by a single fake cert.

**`chainSelection` does perform full ledger validation** via `validateCandidate` → `LedgerDB.validateFork`: [7](#0-6) 

This means the attacker **cannot** cause a switch to a ledger-invalid block. However, the attacker **can** cause a switch to any valid block on a competing fork that is already in the VolatileDB, as long as the fake boost makes it heavier.

---

### Impact Explanation

An unprivileged ObjectDiffusion peer can:

1. Deliver a valid block on a competing fork via BlockFetch/ChainSync (normal protocol operation).
2. Send a `PerasCert` with `pcCertBoostedBlock` pointing to that block.
3. The cert passes `validatePerasCert` (stub), is stored in the PerasCertDB, and adds `PerasWeight 15` to the boosted block's weight.
4. `chainSelectionForBlock` runs for the boosted block. If the boosted fork's total weight exceeds the current chain's weight, the node switches to the adversarially-chosen fork.

This bypasses the core Peras security invariant: **only blocks certified by a legitimate quorum of committee members may receive a weight boost**. The attacker can steer the node to any valid fork of their choosing, violating the chain selection guarantee that Peras is designed to provide.

The switch is not permanently irreversible (it can be undone within k blocks if the honest chain grows), but an attacker who continuously sends fake certs can keep the node on the adversarial fork indefinitely.

---

### Likelihood Explanation

- The ObjectDiffusion protocol and `makePerasCertPoolWriterFromChainDB` are production code paths, not gated behind a feature flag in the files examined.
- The stub is explicitly marked TODO but is wired into the production writer.
- The attack requires only: (a) a valid block already in the VolatileDB (achievable via normal block diffusion), and (b) sending a single `PerasCert` message over the ObjectDiffusion miniprotocol.
- No stake, keys, or privileged access are required.

---

### Recommendation

Replace the `validatePerasCert` stub with real committee membership, quorum, and cryptographic signature verification before the ObjectDiffusion cert writer is connected to a live network. Until that validation is in place, the cert writer should either be disabled or the `addPerasCertAsync` path should be gated behind a feature flag that is off by default. [8](#0-7) 

---

### Proof of Concept

Construct a unit test using `io-sim` or `IOSim`:

1. Instantiate a `ChainDB` with a two-block fork in the VolatileDB: current chain `[A, B]` (blockNo 2), competing fork `[A, C]` (blockNo 2, same length — normally not preferred).
2. Call `makePerasCertPoolWriterFromChainDB` to get the production writer.
3. Call `opwAddObjects` with a `PerasCert { pcCertRound = 1, pcCertBoostedBlock = blockPoint C }`.
4. Assert: `validatePerasCert mkPerasParams cert` returns `Right` (stub confirmed).
5. Assert: `processCerts` calls `addPerasCertAsync` with the cert.
6. Wait for the ChainDB background thread to process `ChainSelAddPerasCert`.
7. Assert: the node's preferred chain tip is now `C`, not `B` — the fake boost of 15 made the `[A, C]` fork heavier despite equal block count.

The test requires no mock of `validatePerasCert` — the real stub is the vulnerability. [9](#0-8)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
