### Title
Anyone Can Submit a Refund Request for Any User's Deposit with an Attacker-Controlled Refund Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is a public, permissionless function. When a deposit's `deposit_msg.refund_address` is `None`, any caller can supply an arbitrary `refund_address`. An attacker who observes an unfinalized BTC deposit on-chain can front-run the legitimate user by submitting a refund request that names the attacker's BTC address as the destination. Because only one refund request is allowed per UTXO, the attacker's request also blocks the user from filing their own. If the DAO does not reject the request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and receives the user's BTC.

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the check is skipped entirely and the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`: [3](#0-2) 

A duplicate-request guard prevents a second request for the same UTXO: [4](#0-3) 

So the attacker's request, once accepted, monopolises the UTXO slot and blocks the legitimate user from filing their own.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless: [5](#0-4) 

`load_refund_request_for_execute` only blocks execution if the UTXO was already finalised via `verify_deposit` (and `executed == false`): [6](#0-5) 

If the relayer has not called `verify_deposit` before the timelock expires, `execute_refund` proceeds and `finalize_refund_with_psbt` builds a PSBT paying the attacker's address: [7](#0-6)

### Impact Explanation

If the DAO does not reject the attacker's request and the relayer does not finalise the deposit before `unsafe_refund_timelock_sec` expires, the attacker receives the user's BTC. The user permanently loses their funds and cannot recover them through the refund path (the UTXO slot is occupied). This maps to **Medium — attacker-triggered redirection of bridged funds** (and potentially Critical if the DAO/relayer are both unavailable).

---

### Likelihood Explanation

All inputs required by the attacker (`deposit_msg`, raw `tx_bytes`, Merkle proof) are public Bitcoin on-chain data. The attacker only needs to pay the storage anti-spam deposit. The attack window is any deposit whose `verify_deposit` has not yet been submitted — a normal state for deposits that are pending relayer processing or that are genuinely unfinalized. The `unsafe_refund_timelock_sec` is the sole on-chain mitigation, and it relies entirely on off-chain DAO vigilance.

---

### Recommendation

Restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (or a privileged role such as `DAO`, `Operator`, or `RefundOperator`) may supply an arbitrary `refund_address`. For example:

```rust
if deposit_msg.refund_address.is_none() {
    let caller = env::predecessor_account_id();
    require!(
        caller == deposit_msg.recipient_id
            || self.acl_has_any_role(
                vec![Role::DAO.into(), Role::Operator.into(), Role::RefundOperator.into()],
                caller
            ),
        "Only recipient or privileged role can set refund_address when deposit_msg.refund_address is None"
    );
}
```

This mirrors the fix suggested in H-04: keep the function publicly callable for legitimate use, but add a guard that prevents arbitrary callers from manipulating state on behalf of other users.

---

### Proof of Concept

1. User deposits BTC with `deposit_msg = { recipient_id: "user.near", refund_address: None, … }`. The relayer has not yet called `verify_deposit`.
2. Attacker observes the confirmed BTC transaction on-chain, extracts `deposit_msg`, `tx_bytes`, `vout`, and constructs a valid Merkle proof.
3. Attacker calls:
   ```
   request_refund(
       deposit_msg  = { recipient_id: "user.near", refund_address: None, … },
       refund_address = "attacker_btc_address",
       tx_bytes     = <raw tx>,
       vout         = 0,
       proof        = <valid merkle proof>,
       gas_fee      = None,
   )
   ```
   with the required storage deposit attached.
4. `request_refund_callback` succeeds: a `RefundRequest` with `refund_address = "attacker_btc_address"` is stored. The user's own `request_refund` call now reverts with `"Refund request already exists for this UTXO"`.
5. DAO does not reject the request within `unsafe_refund_timelock_sec`.
6. Attacker calls `execute_refund(utxo_storage_key, None)`. The timelock check passes, `verified_deposit_utxo` does not contain the key, and a PSBT paying `"attacker_btc_address"` is built and submitted to MPC for signing.
7. After MPC signing and broadcast, the user's BTC is permanently transferred to the attacker.
