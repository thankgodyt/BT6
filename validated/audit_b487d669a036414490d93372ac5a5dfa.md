Audit Report

## Title
Permanent Freezing of Bridged Funds When EVM Recipient Cannot Receive Native ETH or ERC-1155 Tokens in `finTransfer` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`OmniBridge.sol::finTransfer` hard-reverts when the EVM recipient cannot receive native ETH or ERC-1155 tokens. Because the entire transaction reverts, `completedTransfers[destinationNonce]` is never durably set, so every retry fails identically. The user's tokens were already burned/locked on NEAR during `init_transfer_internal`, and no `cancel_transfer` or redirect mechanism exists on NEAR to recover them, resulting in permanent freezing of bridged funds.

## Finding Description

**Root cause:** `completedTransfers[payload.destinationNonce] = true` is written at line 287 before any external call. If the subsequent ETH send at lines 319–322 fails, `revert FailedToSendEther()` rolls back the entire transaction including the nonce assignment. The nonce is never consumed, so the relayer can retry indefinitely — but will always revert identically if the recipient is a contract without a `receive()`/`fallback()` function.

The same applies to ERC-1155: `IERC1155.safeTransferFrom` at lines 324–330 calls `onERC1155Received` on the recipient; if the recipient does not implement `IERC1155Receiver`, the call reverts and the entire `finTransfer` transaction reverts.

**NEAR side:** During `init_transfer_internal`, tokens are burned or locked at lines 1850–1857 of `near/omni-bridge/src/lib.rs`. The transfer is recorded in `pending_transfers`. There is no `cancel_transfer` function (confirmed by exhaustive search). `update_transfer_fee` only modifies the fee. `claim_fee` requires proof of successful EVM finalization, which can never be produced. The MPC signature is cryptographically bound to the original `recipient` field in the Borsh-encoded payload; no new signature for a different recipient can be obtained without a new `sign_transfer` call, but the NEAR-side transfer nonce is already consumed.

**Existing guards are insufficient:** The nonce-already-used check at line 283–285 only prevents replay of a *successfully finalized* transfer. It does not help here because the nonce is never durably set when the tx reverts.

## Impact Explanation

Permanent freezing of bridged funds. Tokens burned/locked on NEAR are irrecoverable if the EVM recipient is a contract that cannot receive native ETH or ERC-1155 tokens. This directly matches the Critical allowed impact: *permanent freezing of bridged funds across NEAR and EVM flows*.

## Likelihood Explanation

Realistic. Multisig wallets (Gnosis Safe without ETH receive), DAO treasuries, protocol contracts, and smart contract wallets are common bridge recipients. Many do not implement `receive()`/`fallback()` or `IERC1155Receiver`. A single mistaken or incompatible recipient address causes permanent, irrecoverable loss with no on-chain remedy. No attacker is required — a normal user initiating a transfer to their own multisig is sufficient to trigger this.

## Recommendation

1. **On EVM (ETH case):** Replace the hard revert with a pull-payment pattern. On failed ETH send, record the amount in a `pendingWithdrawals[recipient]` mapping and emit an event. Add a `withdraw(address to)` function allowing the original recipient to redirect funds.
2. **On EVM (ERC-1155 case):** Wrap `safeTransferFrom` in a try/catch or use a low-level call; on failure, record the pending claim similarly.
3. **On NEAR:** Add a `cancel_transfer` function (sender-gated after a timeout, or DAO-gated) that removes the entry from `pending_transfers`, re-mints/unlocks tokens to the original sender, and invalidates the destination nonce to prevent MPC signature replay.

## Proof of Concept

1. User holds a NEAR-side token and calls `ft_on_transfer` targeting a NEAR→ETH transfer with `recipient = 0xNoReceive` (a deployed contract with no `receive()` or `fallback()`).
2. `init_transfer_internal` burns the token and records the transfer in `pending_transfers` (NEAR lib.rs lines 1850–1857).
3. Relayer calls `sign_transfer`; MPC signs the payload binding `recipient = 0xNoReceive`.
4. Relayer calls `finTransfer` on EVM. `completedTransfers[nonce] = true` is set (line 287), then `payload.recipient.call{value: payload.amount}("")` returns `success = false` (line 319–321), triggering `revert FailedToSendEther()` (line 322). The entire transaction reverts; nonce is not consumed.
5. Every subsequent `finTransfer` attempt reverts identically. The transfer remains in `pending_transfers` on NEAR indefinitely. The burned token is unrecoverable. No cancel or redirect function exists.

**Minimal test:** Deploy a contract with no `receive()` on a local EVM fork. Call `finTransfer` with `tokenAddress = address(0)` and `recipient = <that contract>`. Observe the revert. Confirm `completedTransfers[nonce]` remains `false`. Confirm no NEAR-side recovery path exists.
