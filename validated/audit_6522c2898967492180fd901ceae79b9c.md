Audit Report

## Title
Wrong `internal_deposit` Target in `OmniToken::mint` When `msg` Is Provided Causes Partial Refunds to Be Permanently Stuck in Bridge Contract — (File: `near/omni-token/src/lib.rs`)

## Summary

In `OmniToken::mint()`, when `msg` is `Some(...)`, newly minted tokens are credited to `env::predecessor_account_id()` (the bridge contract) via `internal_deposit` instead of `account_id` (the intended recipient). A subsequent `ft_transfer_call` forwards the tokens to `account_id`, but if `ft_on_transfer` returns a partial refund, those tokens are returned to the bridge contract and never burned. The bridge's `fin_transfer_send_tokens_callback` only triggers a burn when `used_amount == 0`; partial refunds are silently ignored, permanently stranding tokens in the bridge contract and inflating the on-NEAR omni-token supply beyond the amount locked on the source chain.

## Finding Description

**Root cause — `near/omni-token/src/lib.rs` lines 135–139:**

```rust
if let Some(msg) = msg {
    self.token
        .internal_deposit(&env::predecessor_account_id(), amount.into()); // bridge contract, not account_id

    self.ft_transfer_call(account_id, amount, None, msg)
``` [1](#0-0) 

`ft_transfer_call` (delegating to `self.token.ft_transfer_call`) transfers from `predecessor_account_id()` — the bridge contract — to `account_id`, then invokes `account_id.ft_on_transfer(sender=bridge_contract, amount, msg)`. If `ft_on_transfer` returns a partial refund `r` (where `0 < r < amount`), `ft_resolve_transfer` credits `r` tokens back to the bridge contract and returns `used_amount = amount - r` to the bridge's callback.

**Guard that fails — `near/omni-bridge/src/lib.rs` lines 1788–1791:**

```rust
if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
    // refund if the used token amount is zero
    amount.0 == 0
``` [2](#0-1) 

`is_refund_required` returns `true` only when `used_amount == 0` (full rejection). For any partial refund (`used_amount > 0`), it returns `false`.

**Callback — `near/omni-bridge/src/lib.rs` lines 1702–1718:**

```rust
if Self::is_refund_required(is_ft_transfer_call) {
    self.burn_tokens_if_needed(...)
    ...
} else {
    // Send fee to fee recipient, log event — no burn of partial refund
}
``` [3](#0-2) 

When `is_refund_required` returns `false`, `burn_tokens_if_needed` is never called. The `r` refunded tokens remain in the bridge contract's balance in the token contract with no recovery path.

**Call site — `near/omni-bridge/src/lib.rs` lines 2094–2101:**

```rust
ext_token::ext(token)
    .with_attached_deposit(deposit)
    .with_static_gas(MINT_TOKEN_GAS.saturating_add(ft_transfer_call_gas))
    .mint(
        recipient,
        amount,
        (!msg.is_empty()).then(|| msg.to_string()),
    )
``` [4](#0-3) 

`msg` originates from `transfer_message.msg`, an unrestricted user-controlled string field set on the source chain.

## Impact Explanation

Every bridge transfer to NEAR carrying a non-empty `msg` whose recipient contract returns a partial refund from `ft_on_transfer` results in:

1. **Permanent loss of bridged funds** — the refunded token amount is stranded in the bridge contract with no mechanism to recover or burn it.
2. **Token supply inflation / escrow mis-accounting** — the on-NEAR omni-token total supply exceeds the amount locked on the source chain by the stranded amount, breaking the 1:1 peg invariant.

This matches the "escrow mis-accounting" and "balance manipulation" critical impact categories.

## Likelihood Explanation

The `msg` field is a first-class, documented feature of the bridge protocol used for DeFi composability (e.g., depositing bridged tokens directly into a lending protocol or DEX). Any recipient contract that partially accepts a transfer — a standard pattern in NEP-141 DeFi integrations — triggers the bug. No admin access or special privilege is required; any unprivileged user initiating a cross-chain transfer with a non-empty `msg` to a contract recipient can trigger it, either accidentally or deliberately.

## Recommendation

The primary fix must be in `fin_transfer_send_tokens_callback` / `is_refund_required`: extend the burn logic to handle **partial** refunds, not only full rejection. When `0 < used_amount < amount`, the bridge should burn `amount - used_amount` tokens from its own balance:

```rust
// is_refund_required should return the refund amount, not a bool
// OR fin_transfer_send_tokens_callback should compute and burn the partial refund:
let refund = amount - used_amount;
if refund > 0 {
    self.burn_tokens_if_needed(token, U128(refund));
}
```

Additionally, consider whether `internal_deposit` should credit `account_id` directly and the `ft_transfer_call` flow restructured accordingly, so that any partial refund goes back to `account_id` rather than the bridge contract — eliminating the stranding risk entirely.

## Proof of Concept

**Setup:** A deployed omni-token exists for an EVM asset. An attacker deploys `attacker.near` implementing `ft_on_transfer` to return `amount - 1` as refund (keeping only 1 token).

**Steps:**

1. Attacker locks 1,000 tokens on EVM, specifying `recipient = attacker.near`, `msg = "trigger"`.
2. Relayer calls `fin_transfer` on the NEAR bridge → `send_tokens` → `mint(attacker.near, 1000, Some("trigger"))`.
3. Inside `mint`: `internal_deposit(&bridge_contract, 1000)` — 1,000 tokens credited to bridge contract. [5](#0-4) 
4. `ft_transfer_call(attacker.near, 1000, None, "trigger")` executes; `attacker.near.ft_on_transfer` returns `999` (refund 999, keep 1).
5. `ft_resolve_transfer` returns 999 tokens to bridge contract; `attacker.near` keeps 1 token.
6. `fin_transfer_send_tokens_callback` runs: `is_refund_required` sees `used_amount = 1 > 0` → returns `false` → no burn. [2](#0-1) 
7. **Result:** Bridge contract holds 999 permanently unburnable tokens. On-NEAR total supply is 1,000; source-chain locked amount is 1,000; only 1 token is in user hands — 999 are irrecoverably stranded, supply invariant broken.
