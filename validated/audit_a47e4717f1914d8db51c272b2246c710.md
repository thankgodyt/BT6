Audit Report

## Title
Malicious ERC1155 Recipient Permanently Freezes Bridged Funds via `onERC1155Received` Revert — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`finTransfer` in `OmniBridge.sol` marks the destination nonce as consumed at line 287 before executing the token delivery. For ERC1155 tokens, delivery uses `safeTransferFrom`, which mandatorily calls `onERC1155Received` on the recipient; a revert there rolls back the nonce flag atomically. Because the MPC-signed payload fixes the recipient address and no NEAR-side recovery path exists for EVM-destined transfers, the NEAR-locked tokens are permanently frozen with no admin or user escape hatch.

## Finding Description
In `finTransfer` (line 279–367), the execution order is:

1. **Line 287**: `completedTransfers[payload.destinationNonce] = true` — nonce marked used.
2. **Lines 323–330**: `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), payload.recipient, ...)` — ERC1155 standard requires the recipient contract to implement `onERC1155Received`; any revert in that hook propagates up and causes the entire transaction to revert, including the state write at step 1.
3. **Lines 317–322**: The native-ETH path has the same structure — `if (!success) revert FailedToSendEther()` rolls back the nonce flag.

Because Solidity reverts are atomic, the nonce is never durably consumed. Every subsequent relay attempt hits the same revert. On the NEAR side, `process_fin_transfer_to_other_chain` (line 1980) handles EVM-destined transfers and has no callback or failure-recovery mechanism — unlike `fin_transfer_send_tokens_callback` (line 1692), which handles NEAR-recipient failures by burning/reverting lock actions and emitting `FailedFinTransferEvent`. The MPC-signed payload embeds the recipient address and cannot be altered post-signing, so no alternative finalization path exists.

## Impact Explanation
Once a user initiates a NEAR→EVM transfer, tokens are locked or burned on NEAR. The only release mechanism is a successful `finTransfer` on EVM. If the EVM recipient is a contract that unconditionally reverts in `onERC1155Received` (or whose ETH `receive()` reverts), `finTransfer` can never succeed, the nonce is never consumed, and the NEAR-side tokens are permanently frozen. This is concrete, irreversible loss of bridged funds — matching the critical impact class of "permanent freezing of bridged funds."

## Likelihood Explanation
Any user bridging ERC1155 tokens (or native ETH) to a contract address on EVM is exposed. The attacker only needs to be the designated EVM recipient — no privileged access, no key compromise, no validator collusion required. In cross-chain DeFi flows (escrows, DEX integrations, cross-chain swaps), the recipient is often a protocol-controlled contract the sender cannot change. A single malicious or buggy contract deployment is sufficient to trigger the freeze for any sender who routes tokens to it.

## Recommendation
1. **Wrap ERC1155 and ETH delivery in a `try/catch`**: on delivery failure, emit a `FinTransferFailed` event and leave `completedTransfers[payload.destinationNonce] = true` set, so the nonce is consumed and the failed state is durable.
2. **Add a NEAR-side recovery path for EVM-destined transfers**: analogous to `fin_transfer_send_tokens_callback`'s `FailedFinTransferEvent` handling, allow the NEAR contract to process a proof of a `FinTransferFailed` event and refund the sender's locked/burned tokens.
3. **For ERC1155 specifically**: consider a pull-based delivery pattern — transfer tokens to an intermediate escrow and let the recipient claim them — eliminating the mandatory callback entirely.

## Proof of Concept
1. Deploy `MaliciousReceiver` on the target EVM chain implementing `onERC1155Received` that unconditionally reverts.
2. On NEAR, call `init_transfer` (or equivalent) specifying `MaliciousReceiver`'s address as the EVM recipient; tokens are locked/burned on NEAR.
3. MPC signs the payload; relayer submits `finTransfer` on EVM.
4. `safeTransferFrom` calls `MaliciousReceiver.onERC1155Received` → revert → entire transaction reverts → `completedTransfers[nonce]` remains `false`.
5. Every subsequent relay attempt produces the same revert. NEAR-side tokens remain permanently locked; no admin function on either chain can recover them.
