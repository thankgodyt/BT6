### Title
Retroactive Timelock Application on Pending Refund Requests After `update_config` - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `refund_timelock_sec` and `unsafe_refund_timelock_sec` configuration parameters are read from the **current** live config at `execute_refund` time rather than being snapshotted at `request_refund` time. A DAO call to `update_config` therefore retroactively changes the effective timelock for every already-pending `RefundRequest`, mirroring the LendingLedger pattern where reward/block-time parameters were applied retroactively to markets that had not yet been updated.

### Finding Description

`RefundRequest` records `created_at_sec` at the moment the request is stored: [1](#0-0) 

The timelock that must elapse before `execute_refund` is allowed is resolved in `resolve_execute_refund_timelock`, which reads the **live** config values at call time: [2](#0-1) 

The elapsed-time check then combines the stored creation timestamp with the freshly-read timelock: [3](#0-2) 

`update_config` (DAO-only) can change both `refund_timelock_sec` and `unsafe_refund_timelock_sec` at any time with no awareness of pending requests: [4](#0-3) [5](#0-4) 

Because no snapshot of the timelock is stored inside `RefundRequest`, every pending request is silently re-evaluated against the new value the next time `execute_refund` is called.

### Impact Explanation

Two directions of harm exist:

**Timelock increase — temporary locking of user funds (Medium).** A user who submitted a refund request under a 2-day `refund_timelock_sec` (the `DEFAULT_REFUND_TIMELOCK_SEC`) will find their refund blocked for the new, longer duration if the DAO raises the value before they call `execute_refund`. Their BTC remains locked in the bridge longer than the protocol promised at request time.

**Timelock decrease — bypass of the DAO review window (Medium).** `unsafe_refund_timelock_sec` (default 14 days) exists specifically to give the DAO/Operator time to call `reject_refund` on suspicious requests where the caller supplied their own `refund_address`. If the DAO legitimately decreases this value (e.g., to improve UX for future requests), every existing pending "unsafe" request immediately becomes executable with the shorter window. A user who submitted a borderline refund request can race to call `execute_refund` before the DAO has had a chance to review and reject it, bypassing the intended security policy. [6](#0-5) 

### Likelihood Explanation

The DAO is expected to tune configuration parameters over the bridge's lifetime. Any adjustment to either timelock field — even a well-intentioned one — silently retroacts onto all pending requests. There is no warning in the code or documentation that `update_config` must be preceded by settling all open refund requests, analogous to the missing warning for `setRewards` in the external report.

### Recommendation

Snapshot the applicable timelock inside `RefundRequest` at creation time (in `request_refund_callback`) and use that stored value in `resolve_execute_refund_timelock` instead of reading from the live config. This ensures that a user's refund is always evaluated against the rules that were in effect when they submitted the request.

Alternatively, restrict timelock changes in `update_config` so that the new value only applies to requests created **after** the config change (e.g., by storing a `config_version` or `effective_from` timestamp alongside each request).

### Proof of Concept

1. User calls `request_refund` with `deposit_msg.refund_address = None`; `unsafe_refund_timelock_sec` is 14 days. `RefundRequest.created_at_sec` is set to `T`.
2. On day 3, DAO calls `update_config` with `unsafe_refund_timelock_sec = 259200` (3 days) to improve UX for future requests.
3. User immediately calls `execute_refund`. `resolve_execute_refund_timelock` reads `config.unsafe_refund_timelock_sec = 259200`. The check `now >= T + 259200` passes (3 days have elapsed).
4. The refund is executed — 11 days before the DAO's intended review window would have closed — bypassing the security policy that motivated the original 14-day default. [7](#0-6)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
