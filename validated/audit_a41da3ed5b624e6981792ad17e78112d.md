### Title
ChainSync Client Evaluates Candidate Weight Without Peras Boosts, Causing Asymmetric Chain Selection Rejection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`, while the actual chain selection in `ChainSel.hs` uses the real `PerasWeightSnapshot`. This creates an asymmetric evaluation of the same candidate chain: the ChainSync client ignores Peras weight boosts when deciding whether to keep or disconnect a peer, but the chain database uses those boosts when deciding which chain to adopt. A candidate chain that is shorter but heavier (due to Peras certificates) is incorrectly rejected as `CandidateTooSparse` and the peer is disconnected, even though the chain would be preferred by the actual chain selection algorithm.

---

### Finding Description

The root cause is in `checkPreferTheirsOverOurs`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- <-- always ignores Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The actual chain selection in `constructPreferableCandidates` and `chainSelection` uses the live `weights :: PerasWeightSnapshot blk` passed through `ChainSelEnv`:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [2](#0-1) 

`preferAnchoredCandidate` with a non-empty `PerasWeightSnapshot` computes `weightedSelectView` on the intersection suffixes, where `wsvTotalWeight = BlockNo + weightBoostOfFragment`. With an empty snapshot it falls back to comparing only `SelectView` (block number and tiebreaker): [3](#0-2) 

`weightBoostOfFragment` sums the Peras certificate boosts for every block in the fragment: [4](#0-3) 

The two evaluation paths therefore produce different orderings for the same pair of fragments whenever any block in the candidate suffix carries a non-zero `PerasWeight`. The ChainSync client uses path 1 (no boosts); the chain database uses path 2 (with boosts). This is the direct analog of the external report's asymmetric fee paths: the same economic position (chain preference) is evaluated differently depending on which code path is taken.

---

### Impact Explanation

When Peras is active and a fork exists where one branch is shorter in block count but heavier in Peras weight:

1. A peer offers the shorter-but-heavier chain.
2. `checkPreferTheirsOverOurs` evaluates it with `emptyPerasWeightSnapshot` and concludes the candidate is not preferred (it has fewer blocks).
3. The node throws `CandidateTooSparse` and disconnects from the peer.
4. The node never downloads the full blocks for the heavier chain.
5. The node remains on the lighter (less-secure) chain.

This is a **chain selection failure**: an honest node is made to prefer a non-canonical, less-secure chain because the ChainSync client's pre-filter uses a different weight metric than the chain database's actual selection. Different nodes with different peer sets could end up on different chains, breaking consensus safety.

---

### Likelihood Explanation

Peras is an active development track in this repository (the `PerasWeightSnapshot` infrastructure is fully wired into `ChainSel`). The scenario requires:
- Peras to be enabled (non-empty `PerasWeightSnapshot`).
- A fork where one branch has fewer blocks but more Peras certificate boosts — a realistic outcome when one branch receives a quorum certificate and the other does not.

The TODO comment in the code (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware this check is incompatible with Peras weight semantics. No attacker capability is required; the bug is triggered by normal network conditions once Peras is live.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` from the node's current state, so the ChainSync client's pre-filter uses the same weight metric as the chain database. Alternatively, remove the check entirely as the TODO suggests, since its original purpose (Genesis density disconnection) can be handled by the LoE mechanism without this asymmetric pre-filter.

---

### Proof of Concept

Consider a two-block fork anchored at block B:

- **Our chain**: B → C → D (block numbers 10, 11, 12; no Peras boosts; `totalWeight = 2`)
- **Peer's chain**: B → C' (block numbers 10, 11; C' has a Peras boost of 5; `totalWeight = 1 + 5 = 6`)

**ChainSync client evaluation** (`emptyPerasWeightSnapshot`):
- `preferAnchoredCandidate` compares `SelectView(D)` vs `SelectView(C')` → block 12 > block 11 → `ShouldNotSwitch` → `CandidateTooSparse` thrown → peer disconnected.

**Chain database evaluation** (real `PerasWeightSnapshot`):
- `preferAnchoredCandidate` compares `wsvTotalWeight(oursSuffix={C,D}) = 2` vs `wsvTotalWeight(candSuffix={C'}) = 6` → `ShouldSwitch` → peer's chain would be adopted.

The node disconnects from the peer offering the canonical (heavier) chain and stays on the lighter fork, violating chain selection correctness. [5](#0-4) [6](#0-5) [7](#0-6)

  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
