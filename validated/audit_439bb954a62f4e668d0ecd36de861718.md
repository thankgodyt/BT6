Audit Report

## Title
Permanent Fund Freezing Due to Missing Normalized-Amount Validation in `init_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts a token deposit and stores a `TransferMessage` in `pending_transfers` after only validating that `fee < amount`. It does not verify that the amount, after decimal normalization to the destination chain's precision, is still greater than zero. When a relayer later calls `sign_transfer`, the normalization check always panics for such a transfer, the MPC call is never dispatched, `sign_transfer_callback` is never reached, and the transfer record is never cleaned up. No user-accessible cancel or refund path exists, permanently locking the deposited tokens inside the bridge contract.

## Finding Description

**Root cause — missing pre-flight normalization check in `init_transfer`:**

`init_transfer` constructs a `TransferMessage` and validates only that the fee is less than the amount: [1](#0-0) 

No check is performed to verify that `amount - fee`, after decimal normalization to the destination chain's precision, is still greater than zero. The tokens are immediately held by the bridge (transferred in via `ft_on_transfer`) and the `TransferMessage` is written to `pending_transfers` via `init_transfer_internal`.

**Blocking check in `sign_transfer`:**

When a relayer calls `sign_transfer`, the amount is normalized using the `Decimals` struct (carrying both `decimals` and `origin_decimals`): [2](#0-1) 

If the destination chain has fewer decimals than NEAR (e.g., a token with 18 NEAR-side decimals and 6 Ethereum-side decimals, giving a divisor of `10^12`), and `amount_without_fee` is less than `10^12`, integer division in `normalize_amount` yields 0. The `require!(amount_to_transfer > 0, ...)` guard then always panics, making `sign_transfer` permanently revert for this specific transfer ID.

**No recovery path:**

`sign_transfer_callback` only removes the transfer from `pending_transfers` when the MPC signing call succeeds: [3](#0-2) 

Because `sign_transfer` panics before the MPC call is ever dispatched, the callback is never reached and the transfer record is never cleaned up. The only other call to `remove_transfer_message` is inside `claim_fee_callback`, which requires a valid cross-chain finalization proof — impossible for a transfer that was never signed. No `cancel_transfer`, `withdraw_transfer`, or equivalent user-accessible refund function exists in the contract. The DAO-only `transfer_token_as_dao` function is not a user recovery path.

**`Decimals` struct driving the normalization:** [4](#0-3) 

## Impact Explanation

**Critical — permanent freezing of bridged funds.** The user's NEP-141 tokens are transferred to the bridge contract during `ft_on_transfer` → `init_transfer`. They are recorded in `pending_transfers` and can never be recovered: every call to `sign_transfer` for that transfer ID reverts unconditionally due to the normalized-amount guard, and no alternative exit path exists for the user. This matches the allowed Critical impact: *permanent freezing of bridged funds*.

## Likelihood Explanation

**Medium.** Two realistic conditions must hold simultaneously:

1. A token whose NEAR-side representation has significantly more decimals than its destination-chain representation (e.g., USDC/USDT with 18 decimals on NEAR, 6 on Ethereum — a `10^12` divisor). Such tokens are already deployed and in active use on the bridge.
2. A user sending an amount smaller than the minimum representable unit on the destination chain (e.g., fewer than `10^12` NEAR-side units, which is less than 1 micro-USDC equivalent on Ethereum).

Both conditions require no admin action or privileged access. Any user can trigger this unilaterally by calling `ft_transfer_call` with a small amount. The scenario is repeatable and self-inflicted, but the loss is permanent and irrecoverable without DAO intervention.

## Recommendation

Add a normalized-amount check inside `init_transfer` (or `init_transfer_internal`) before accepting the deposit. At the point where `token_decimals` is available, compute:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively (or additionally), introduce a `cancel_transfer` function that allows the original sender to reclaim tokens from a stuck `pending_transfers` entry, providing a recovery path even if the normalization check is missed.

## Proof of Concept

1. Token X is registered with 18 NEAR-side decimals and 6 Ethereum-side decimals (`decimals = 18`, `origin_decimals = 6` in the `Decimals` struct), giving a normalization divisor of `10^(18-6) = 10^12`.
2. User calls `ft_transfer_call` on Token X with `amount = 999_999_999_999` (just under `10^12`) and `fee = 0`.
3. `init_transfer` stores the transfer: fee check `0 < 999_999_999_999` passes. Tokens are now held by the bridge contract.
4. Relayer calls `sign_transfer` for this `transfer_id`.
5. `normalize_amount(999_999_999_999, decimals)` performs integer division: `999_999_999_999 / 10^12 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — `sign_transfer` reverts entirely.
7. No MPC call is dispatched; `sign_transfer_callback` is never invoked; the transfer record remains in `pending_transfers` indefinitely.
8. The user's `999_999_999_999` Token X units are permanently locked in the bridge with no user-accessible recovery path.

A local integration test can reproduce this by: (a) registering a token with mismatched decimals, (b) calling `ft_on_transfer` with a sub-minimum amount, (c) asserting the transfer is stored in `pending_transfers`, and (d) asserting that `sign_transfer` panics with `InvalidAmountToTransfer` on every subsequent call.
