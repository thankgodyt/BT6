Audit Report

## Title
`MetadataPayload` Hash Lacks Chain ID Binding, Enabling Cross-Chain Replay of `deployToken` Signatures — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/omni_bridge.cairo`)

## Summary

The Borsh-encoded hash used to authorize token deployments in `deployToken` (EVM) and `deploy_token` (Starknet) does not include a destination chain identifier. Because both chains share the same NEAR MPC-derived signing key and produce byte-for-byte identical hash inputs for the same `(token, name, symbol, decimals)` tuple, a valid signature extracted from a public `deployToken` transaction on EVM can be replayed verbatim on Starknet (and vice versa). This allows an unprivileged attacker to permanently occupy the `near_to_starknet_token` mapping slot for any NEAR token ID, blocking all future legitimate deployments of that token on Starknet.

## Finding Description

**EVM root cause (`OmniBridge.sol`, L142–153):**

The `deployToken` function constructs its hash as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),  // 0x01
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
``` [1](#0-0) 

No `omniBridgeChainId` is included. The signer key `nearBridgeDerivedAddress` is the NEAR MPC-derived Ethereum address shared across all supported chains. [2](#0-1) 

**Starknet root cause (`omni_bridge.cairo`, L202–205 and `bridge_types.cairo`, L36–44):**

`deploy_token` calls `_verify_borsh_signature(ref self, @payload.to_borsh(), signature)`. [3](#0-2) 

`MetadataPayload::to_borsh()` produces:

```cairo
borsh_bytes.append_byte(PayloadType::Metadata.into()); // 0x01
borsh_bytes.append(@borsh::encode_byte_array(self.token));
borsh_bytes.append(@borsh::encode_byte_array(self.name));
borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
borsh_bytes.append_byte(*self.decimals);
``` [4](#0-3) 

No chain ID is included. The verifying key `omni_bridge_derived_address` is the same NEAR MPC-derived Ethereum address. [5](#0-4) 

**Contrast with `finTransfer`:** The EVM `finTransfer` hash correctly includes `bytes1(omniBridgeChainId)` twice, binding it to the specific chain. [6](#0-5) 

The Starknet `fin_transfer` similarly passes `self.omni_bridge_chain_id.read()` into `payload.to_borsh(chain_id)`, and `TransferMessagePayloadImpl::to_borsh` appends `chain_id` at two positions. [7](#0-6) [8](#0-7) 

The `deployToken` path has no equivalent binding on either chain.

**Encoding equivalence:** Both `Borsh.encodeString` (EVM) and `borsh::encode_byte_array` (Starknet) produce the standard Borsh wire format: 4-byte little-endian length prefix followed by raw UTF-8 bytes. The `PayloadType::Metadata` discriminant is `1` on both chains. The hash inputs are therefore byte-for-byte identical for the same `(token, name, symbol, decimals)` tuple.

**Exploit path:**

1. Attacker observes a successful `deployToken(signatureData, metadata)` call on EVM — all inputs are public calldata.
2. Attacker extracts `signatureData` and `metadata`.
3. Attacker calls `deploy_token(signature, payload)` on Starknet with the identical values.
4. `_verify_borsh_signature` passes because the keccak hash is identical and the signing key is the same.
5. The token is deployed on Starknet and `near_to_starknet_token[token_id_hash]` is permanently written. [9](#0-8) 
6. Any subsequent legitimate `deploy_token` call for the same NEAR token ID reverts with `ERR_TOKEN_ALREADY_DEPLOYED`. [10](#0-9) 

**Existing guards are insufficient:** The `ERR_TOKEN_EXIST` check on EVM and `ERR_TOKEN_ALREADY_DEPLOYED` on Starknet only prevent re-deployment on the same chain; neither prevents cross-chain replay. [11](#0-10) 

## Impact Explanation

This is a **chain/domain separation flaw** enabling an attacker to execute token-deployer-equivalent actions on Starknet using a signature the NEAR MPC authorized only for EVM (or vice versa). Concretely:

- **Authorization bypass**: The MPC signed a payload authorizing deployment on chain A. The attacker uses that authorization to deploy on chain B without any additional MPC approval.
- **Permanent blocking**: Once the replay succeeds, `near_to_starknet_token` is permanently populated for that NEAR token ID. The legitimate deployer can never deploy the canonical version of that token on Starknet; every attempt reverts with `ERR_TOKEN_ALREADY_DEPLOYED`.
- **Unauthorized bridge token creation**: The attacker-deployed contract on Starknet is recognized as a bridge token (`starknet_to_near_token` is written), so the bridge will mint tokens into it during `fin_transfer` calls.

This matches the allowed Critical impact: *"Cross-chain replay... or chain/domain separation flaw enabling invalid finalization or double-spending"* and *"Unauthorized transaction, authorization bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

## Likelihood Explanation

**High.** The attack requires zero privileged access. All inputs (`signatureData`, `metadata`) are visible in the calldata of any public `deployToken` transaction on EVM. The replay is a single contract call on Starknet. Any NEAR token that has been deployed on EVM but not yet on Starknet is permanently at risk from the moment its EVM deployment transaction is confirmed. The reverse direction (Starknet → EVM replay) is equally feasible.

## Recommendation

Include the destination chain ID in the `MetadataPayload` hash, mirroring the pattern already used in `finTransfer`/`fin_transfer`.

**EVM (`OmniBridge.sol`):**
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),   // ADD THIS
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

**Starknet (`bridge_types.cairo`):** Change `to_borsh(self: @MetadataPayload)` to `to_borsh(self: @MetadataPayload, chain_id: u8)` and prepend `borsh_bytes.append_byte(chain_id)` after the payload type byte. Update the call site in `deploy_token` to pass `self.omni_bridge_chain_id.read()`.

The NEAR MPC signing side must also be updated to include the target chain ID when constructing the payload to sign, so that signatures are chain-specific.

## Proof of Concept

**Minimal test sequence (local testnet):**

1. Deploy `OmniBridge` on a local EVM chain with `omniBridgeChainId = 1` and deploy the Starknet `OmniBridge` with `omni_bridge_chain_id = 2`, both configured with the same `nearBridgeDerivedAddress`/`omni_bridge_derived_address`.
2. Obtain a valid MPC-signed `MetadataPayload` for token `"token.near"`, name `"Token"`, symbol `"TKN"`, decimals `18`.
3. Call `deployToken(signatureData, metadata)` on EVM — succeeds.
4. Using the identical `signatureData` and `metadata`, call `deploy_token(signature, payload)` on Starknet — **succeeds** despite the signature being authorized for chain ID 1, not chain ID 2.
5. Verify `near_to_starknet_token[keccak("token.near")]` is now set to the attacker-deployed contract address.
6. Attempt a legitimate `deploy_token` call for `"token.near"` on Starknet — reverts with `ERR_TOKEN_ALREADY_DEPLOYED`.

This can be demonstrated with the existing Starknet test harness by constructing `build_deploy_token_message` (as shown in `starknet/tests/test_contract.cairo`, L83–93) with the same payload used in an EVM deployment and verifying the signature passes on Starknet.
