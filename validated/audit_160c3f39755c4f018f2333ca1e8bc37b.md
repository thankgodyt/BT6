Audit Report

## Title
Detached Token Transfers With No Failure Callback Cause Permanent Relayer Fund Loss — (`near/omni-bridge/src/lib.rs`)

## Summary

In `send_fee_internal`, `process_fin_transfer_to_other_chain`, and `utxo_fin_transfer_fast`, token transfers are dispatched via `.detach()` (fire-and-forget) or returned as bare `PromiseOrValue` with no chained failure callback. State mutations (`remove_transfer_message`, `mark_fast_transfer_as_finalised`, `remove_fast_transfer`) and event emissions (`ClaimFeeEvent`, `FinTransferEvent`, `UtxoTransferEvent`) occur synchronously before the cross-contract calls resolve. If any transfer fails, the state is permanently gone, the event is already on-chain, and the relayer has no recovery path.

## Finding Description

**`claim_fee` path:**

`claim_fee_callback` permanently removes the transfer message at line 1094 before calling `send_fee_internal`: [1](#0-0) 

Inside `send_fee_internal`, the native fee is detached: [2](#0-1) 

`ClaimFeeEvent` is then logged synchronously, before the token-fee cross-contract call is even dispatched: [3](#0-2) 

The returned `PromiseOrValue<()>` from `ft_transfer`/`mint` has no `.then(callback)` chained to it. If the NEP-141 `ft_transfer` panics (e.g., recipient not storage-registered), the failure receipt is silently dropped.

**`process_fin_transfer_to_other_chain` path:**

When a fast transfer exists, `send_tokens` is detached, then the fast transfer is permanently marked finalised, then the event is emitted — all with no failure handler: [4](#0-3) 

**`utxo_fin_transfer_fast` path:**

State is mutated (fast transfer removed or marked finalised at lines 2530–2533), then `send_tokens` is detached, then the event is emitted: [5](#0-4) 

In all three paths, `unlock_tokens_if_needed` also updates locked-token accounting before the transfer succeeds, creating escrow mis-accounting. [6](#0-5) 

## Impact Explanation

In the fast-transfer paths (`process_fin_transfer_to_other_chain`, `utxo_fin_transfer_fast`), the relayer fronts the bridged amount to the user. The reimbursement `send_tokens` call is detached. If it fails, the relayer permanently loses the fronted bridged funds — the fast-transfer entry is already finalised/removed, so no retry is possible. This is a direct, permanent loss of bridged funds. In the `claim_fee` path, the relayer loses their earned fee (native and/or token). The locked-token counter (`unlock_tokens_if_needed`) is decremented before the transfer succeeds, constituting escrow mis-accounting. These match the allowed critical impacts: **loss of bridged funds** and **escrow/fee mis-accounting**.

## Likelihood Explanation

The failure condition is straightforward and reachable by any relayer: NEP-141 requires `storage_deposit` before `ft_transfer` can succeed. A fee recipient or relayer account that has not pre-registered storage for the specific bridged token will cause the `ft_transfer` receipt to panic and fail. This is a standard operational condition, not an exotic edge case. No privileged access is required — any relayer executing a fast transfer or claiming a fee can encounter this. The condition is also triggerable by a token contract that is paused or blacklists the recipient.

## Recommendation

1. Remove `.detach()` from all native-fee and token-transfer promises in `send_fee_internal`, `process_fin_transfer_to_other_chain`, and `utxo_fin_transfer_fast`. Chain them with a `#[private]` callback.
2. Move all event emissions (`ClaimFeeEvent`, `FinTransferEvent`, `UtxoTransferEvent`) into those callbacks, emitting only on success.
3. In the failure branch of each callback, re-insert the transfer message (or re-mark the fast transfer as not finalised) so the relayer can retry.
4. Move `unlock_tokens_if_needed` into the success callback so locked-token accounting only changes after confirmed transfer.

## Proof of Concept

1. Relayer executes a fast transfer, fronting the bridged token amount to the user.
2. The origin-chain finalization proof arrives; `process_fin_transfer_to_other_chain` is called.
3. `send_tokens(token, relayer, amount, "").detach()` is called — result ignored.
4. `mark_fast_transfer_as_finalised` permanently marks the fast transfer as done.
5. `FinTransferEvent` is emitted on-chain.
6. The `ft_transfer` receipt fails because the relayer's account has not called `storage_deposit` on the bridged token contract (standard NEP-141 requirement).
7. No callback catches the failure. The failed receipt is silently dropped.
8. **Result**: fast transfer is permanently finalised, `FinTransferEvent` is on-chain, relayer receives nothing and has no retry path — permanent loss of fronted bridged funds.
