### Title
Wrong `internal_deposit` Target in `OmniToken::mint` When `msg` Is Provided Causes Partial Refunds to Be Permanently Stuck in Bridge Contract — (File: `near/omni-token/src/lib.rs`)

---

### Summary

In `OmniToken::mint()`, when the optional `msg` argument is `Some(...)`, newly minted tokens are credited to `env::predecessor_account_id()` (the bridge contract) instead of `account_id` (the intended recipient). A subsequent `ft_transfer_call` forwards the tokens to `account_id`, but if the recipient's `ft_on_transfer` returns a **partial** refund, the refunded portion is returned to the bridge contract and never burned. The bridge's `fin_transfer_send_tokens_callback` only triggers a burn when `used_amount == 0` (full rejection); partial refunds are silently ignored, leaving tokens permanently stranded in the bridge contract and inflating the on-NEAR token supply beyond the amount locked on the source chain.

---

### Finding Description

`OmniToken::mint` has two branches:

```rust
// near/omni-token/src/lib.rs  lines 127-144
fn mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_controller();

    if let Some(msg) = msg {
        self.token
            .internal_deposit(&env::predecessor_account_id(), amount.into()); // ← BUG: bridge contract, not account_id

        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.token.internal_deposit(&account_id, amount.into());              // ← correct
        PromiseOrValue::Value(amount)
    }
}
``` [1](#0-0) 

When `msg` is `Some`, `internal_deposit` credits the bridge contract (`predecessor_account_id()`) instead of `account_id`. `ft_transfer_call` then transfers from the bridge contract to `account_id` and invokes `account_id.ft_on_transfer(sender=bridge_contract, amount, msg)`.

The NEP-141 `ft_resolve_transfer` callback returns `used_amount` (how many tokens the receiver kept). The bridge contract's `fin_transfer_send_tokens_callback` calls `is_refund_required`, which only returns `true` — and therefore only triggers `burn_tokens_if_needed` — when `used_amount == 0`:

```rust
// near/omni-bridge/src/lib.rs  lines 1788-1791
if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
    // refund if the used token amount is zero
    amount.0 == 0
``` [2](#0-1) 

For a **partial** refund (`0 < used_amount < amount`):

- `ft_resolve_transfer` returns `amount - used_amount` tokens to the bridge contract.
- `is_refund_required` returns `false` (used_amount > 0).
- `burn_tokens_if_needed` is **never called**.
- The refunded tokens remain in the bridge contract's balance with no recovery path. [3](#0-2) 

The `send_tokens` function is the call site that passes `msg` to `mint` for all deployed (omni) tokens:

```rust
// near/omni-bridge/src/lib.rs  lines 2094-2101
ext_token::ext(token)
    .with_attached_deposit(deposit)
    .with_static_gas(MINT_TOKEN_GAS.saturating_add(ft_transfer_call_gas))
    .mint(
        recipient,
        amount,
        (!msg.is_empty()).then(|| msg.to_string()),
    )
``` [4](#0-3) 

`msg` originates from `transfer_message.msg`, which is set by the user on the source chain and is an unrestricted string field.

---

### Impact Explanation

Every bridge transfer to NEAR that carries a non-empty `msg` and whose recipient contract returns a partial refund from `ft_on_transfer` results in:

1. **Permanent loss of bridged funds** — the refunded token amount is stranded in the bridge contract with no mechanism to recover or burn it.
2. **Token supply inflation / escrow mis-accounting** — the on-NEAR omni-token total supply exceeds the amount locked on the source chain by the stranded amount, breaking the 1:1 peg invariant that the bridge relies on.

This matches the "escrow mis-accounting" and "balance manipulation" impact categories in the allowed scope.

---

### Likelihood Explanation

The `msg` field is a first-class, documented feature of the bridge protocol, used for DeFi composability (e.g., depositing bridged tokens directly into a lending protocol or DEX). Any recipient contract that partially accepts a transfer — a standard pattern in NEP-141 DeFi integrations — triggers the bug. No admin access or special privilege is required; any unprivileged user initiating a cross-chain transfer with a non-empty `msg` to a contract recipient can trigger it, either accidentally or deliberately.

---

### Recommendation

Change the `internal_deposit` target in the `msg` branch from `env::predecessor_account_id()` to `account_id`, so that the minted tokens are credited to the intended recipient before `ft_transfer_call` is invoked:

```rust
if let Some(msg) = msg {
    self.token
        .internal_deposit(&account_id, amount.into()); // ← fix: credit recipient, not bridge

    self.ft_transfer_call(account_id, amount, None, msg)
}
```

Additionally, update `fin_transfer_send_tokens_callback` / `is_refund_required` to also burn the **partial** refund amount (not only the full-rejection case), so that any tokens returned to the bridge contract are immediately destroyed and the supply invariant is maintained.

---

### Proof of Concept

**Setup:** A deployed omni-token exists for an EVM asset. An attacker deploys a NEAR contract `attacker.near` that implements `ft_on_transfer` to return `amount - 1` as refund (keeping only 1 token).

**Steps:**

1. Attacker locks 1 000 tokens on EVM and specifies `recipient = attacker.near`, `msg = "trigger"`.
2. Relayer calls `fin_transfer` on the NEAR bridge, which calls `send_tokens` → `mint(attacker.near, 1000, Some("trigger"))`.
3. Inside `mint`: `internal_deposit(&bridge_contract, 1000)` — 1 000 tokens credited to bridge contract.
4. `ft_transfer_call(attacker.near, 1000, None, "trigger")` executes; `attacker.near.ft_on_transfer` returns `999` (refund).
5. `ft_resolve_transfer` returns 999 tokens to bridge contract; `attacker.near` keeps 1 token.
6. `fin_transfer_send_tokens_callback` runs: `is_refund_required` sees `used_amount = 1 > 0` → returns `false` → no burn.
7. **Result:** Bridge contract holds 999 permanently unburnable tokens. On-NEAR total supply is 1 000; source-chain locked amount is 1 000; but only 1 token is in user hands — 999 are irrecoverably stranded. [5](#0-4) [6](#0-5)
