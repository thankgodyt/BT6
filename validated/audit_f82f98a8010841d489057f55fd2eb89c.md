### Title
User Can Block Operator `cancel_withdraw` by Maintaining a Pending RBF Sign Slot — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`cancel_withdraw` calls `require_pending_sign_capacity(&user_account_id)` against the **withdrawal owner's** account before creating its own cancel-RBF pending entry. A user can deliberately keep their `btc_pending_sign_ids` at capacity by calling `withdraw_rbf` after each signing cycle, causing every operator `cancel_withdraw` attempt to panic with `"Too many pending sign transactions"` until the user exhausts their RBF limit.

---

### Finding Description

`cancel_withdraw` in `api/bridge.rs` is gated by `#[access_control_any(roles(Role::DAO, Role::Operator))]` — only privileged roles can call it. However, before creating the cancel-RBF pending entry it unconditionally checks the **victim user's** pending-sign capacity: [1](#0-0) 

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    self.require_pending_sign_capacity(&user_account_id);   // ← checked against victim
    self.cancel_withdraw_chain_specific(...)
}
```

`require_pending_sign_capacity` panics if `pending_sign_count >= max`: [2](#0-1) 

The default limit is **1**: [3](#0-2) 

`btc_pending_sign_ids` is populated by the `define_rbf_method!` macro, which is used for **both** `withdraw_rbf_chain_specific` and `cancel_withdraw_chain_specific`: [4](#0-3) [5](#0-4) 

Entries are only removed from `btc_pending_sign_ids` when `sign_btc_transaction_callback` completes all signatures: [6](#0-5) 

**Concrete attack sequence (default limit = 1):**

1. User initiates withdrawal → `btc_pending_sign_ids = {tx1}` (count = 1)
2. Relayer signs original tx → `btc_pending_sign_ids = {}` (count = 0), state → `PendingVerify`
3. User calls `withdraw_rbf` (public, no role gate) → `require_pending_sign_capacity` passes (0 < 1) → `btc_pending_sign_ids = {rbf_tx1}` (count = 1)
4. Operator calls `cancel_withdraw` → `require_pending_sign_capacity` checks `1 < 1` → **PANIC: "Too many pending sign transactions"**

The user repeats step 3 after each relayer signing cycle. The `rbf_num_limit` config bounds the total number of RBF calls: [7](#0-6) 

Until that limit is exhausted, the user can maintain exactly 1 pending sign entry at all times, permanently blocking `cancel_withdraw` for the duration.

---

### Impact Explanation

The operator/DAO invariant that a stuck withdrawal can always be cancelled via `cancel_withdraw` is violated. The withdrawal remains locked in `PendingVerify` state for as long as the user can sustain RBF slots. This is temporary (bounded by `rbf_num_limit`) but requires no operator intervention to initiate — the user simply calls the public `withdraw_rbf` after each signing. The funds are not stolen, but the operator's ability to manage stuck withdrawals is disabled for the attack window.

---

### Likelihood Explanation

Any withdrawal owner can execute this with a single public call (`withdraw_rbf`) timed after each relayer signing. No leaked keys, no privileged access, no external dependencies. The default limit of 1 makes the condition trivially reachable.

---

### Recommendation

Remove `require_pending_sign_capacity` from `cancel_withdraw` (and `cancel_active_utxo_management`). The capacity check exists to prevent users from flooding the signing queue; operator-initiated cancel paths should be exempt from this user-facing limit. Alternatively, maintain a separate counter for operator-created cancel entries that does not count against the user's `pending_tx_limits` quota.

---

### Proof of Concept

State-based test (pseudo-code):

```
// Setup: user has limit = 1
1. ft_on_transfer → create withdrawal for victim (btc_pending_sign_ids = {tx1})
2. sign_btc_transaction_callback (all inputs) → btc_pending_sign_ids = {} (PendingVerify)
3. victim calls withdraw_rbf(tx1, ...) → btc_pending_sign_ids = {rbf_tx1}
4. operator calls cancel_withdraw(tx1, ...) 
   → require_pending_sign_capacity(victim) 
   → pending_sign_count() = 1, max = 1
