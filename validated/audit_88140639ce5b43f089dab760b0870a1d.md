Peras Certificate Validation Unconditionally Accepts All Inbound Certificates, Enabling Unauthorized Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. This stub is wired directly into the production node-to-node Peras certificate diffusion inbound path. Any unprivileged peer can send a crafted `PerasCert` boosting an arbitrary block; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection that applies a weight boost of `perasWeight = 15` to the attacker-chosen block, potentially causing the honest node to abandon the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must authenticate a certificate before it influences the node's state. The universal instance (the only one that exists) implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, round-number, or boosted-block validity check is performed. Every certificate is unconditionally wrapped in `ValidatedPerasCert` and returned as `Right`.

This stub is called directly in the production inbound certificate pool writer:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

That writer is wired into the live node-to-node handler:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

The `processCerts` function calls `validateCert` on each inbound certificate; if all pass (they always do), each is timestamped and forwarded to `addPerasCertAsync`: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for the background chain-selection thread, which calls `chainSelSync` → `chainSelectionForBlock` for the boosted block, applying the full `perasWeight = 15` boost to chain selection: [5](#0-4) 

The weight boost is applied via `WeightedSelectView`, where `wsvTotalWeight = blockNo + weightBoost`. A fork that is 15 blocks shorter than the honest chain but carries an attacker-forged certificate will be preferred: [6](#0-5) 

The `PerasCertDB` enforces at most one certificate per round (`PerasCertAlreadyInDB` for duplicates), so the **first** certificate received for a given round wins — directly mirroring the oracle's first-in-first-out selection flaw. An attacker who sends a certificate for a round before the honest certificate arrives permanently installs their chosen boosted block for that round. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` naming any block as the boosted block for any round. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and used to add 15 weight units to the attacker-chosen block during chain selection. If the attacker's fork has accumulated enough blocks to be within 15 of the honest tip, the honest node will switch to the adversarial fork. This constitutes:

- **Bypass of Peras certificate verification** — the cryptographic quorum proof that a certificate represents ≥ 3/4 of stake is never checked.
- **Unauthorized chain-selection manipulation** — an adversary with no stake can cause an honest node to prefer a non-canonical chain, breaking the Peras security guarantee that weight boosts are tied to honest quorum.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's Peras certificate diffusion port and the ability to construct a syntactically valid `PerasCert` CBOR message (round number + block point). No stake, keys, or prior chain knowledge beyond the target block's hash is needed. The stub is present in the only `BlockSupportsPeras` instance in the codebase and is unconditionally used in production diffusion setup.

---

### Recommendation

- **Short term:** Gate `processCerts` on a real `validatePerasCert` implementation that verifies the aggregate BLS signature and quorum threshold before accepting any certificate. Until real validation is available, reject all inbound certificates from peers (return `Left` unconditionally) rather than accepting them all.
- **Long term:** Implement `validatePerasCert` using the `WFALS` committee verification path (which already has proper aggregate-signature and VRF verification) as defined in `Ouroboros.Consensus.Committee.WFALS`. Ensure the first-certificate-per-round acceptance policy is only applied after cryptographic validation passes. [8](#0-7) 

---

### Proof of Concept

1. Connect to a node's Peras certificate diffusion mini-protocol endpoint.
2. Identify a block hash `H` on a fork that is up to 15 blocks behind the honest tip.
3. Send a `PerasCert { pcCertRound = R, pcCertBoostedBlock = Point { slot = S, hash = H } }` for any round `R` not yet seen by the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`.
5. The certificate is added to `PerasCertDB` via `addPerasCertAsync`.
6. `chainSelSync` runs `chainSelectionForBlock` for block `H`, now carrying +15 weight.
7. `preferAnchoredCandidate` computes `wsvTotalWeight(fork) = blockNo(H) + 15 > wsvTotalWeight(honest tip)` and returns `ShouldSwitch`.
8. The node rolls back to the fork, accepting the adversarially boosted chain as canonical. [9](#0-8) [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch

    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

      STM m (m AddPerasCertResult)

  -- certificate to the in-memory index, and the resulting 'm' action performs
  -- tracing and might perform side-effects in implementations with on-disk
  -- storage.
  -- The 'AddPerasCertResult' indicates whether the certificate was actually
  -- added, or if it was already present.
  --
  -- NOTE: Use the @join . atomically@ pattern to run both the transaction
  -- and the side-effects in sequence.
  , getCertIds ::
      STM m (Set PerasRoundNo)
  -- ^ Get the set of all cert IDs currently in the database.
  , getCertsAfter ::
      PerasCertTicketNo ->
      STM m (Map PerasCertTicketNo (m (WithArrivalTime (ValidatedPerasCert blk))))
  -- ^ Get all certs with a ticket number strictly greater than the given one,
  -- in ascending order.
  -- Unlike 'getVotesAfter' in 'PerasVoteDB', the resulting map contains 'm' actions to
  -- retrieve the certificates, instead of the certificates directly. This is to
  -- allow implementation with on-disk storage to retrieve certificates from disk.

  -- The 'Fingerprint' is updated every time a new certificate is added, but it
