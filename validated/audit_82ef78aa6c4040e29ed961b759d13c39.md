### Title
Attacker-Controlled Pending-Sign Slot Blocks Operator `cancel_withdraw` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` checks `require_pending_sign_capacity` against the **withdrawal owner's** account before creating the cancel-RBF pending info. Because a user can freely fill their own pending-sign slot by initiating a second withdrawal, they can permanently front-run every operator `cancel_withdraw` call, preventing the bridge from ever cleaning up their stuck withdrawal.

### Finding Description
`cancel_withdraw` is the operator-only mechanism for cancelling a user withdrawal that has not been confirmed on Bitcoin within `max_btc_tx_pending_sec`. Its implementation in `api/bridge.rs` reads the original pending info's `account_id` and immediately calls `require_pending_sign_capacity` on that account before doing any state mutation: [1](#0-0) 

`require_pending_sign_capacity` panics if the account's `btc_pending_sign_ids` count is not strictly less than the per-account limit (default: 1): [2](#0-1) 

The default limit is 1: [3](#0-2) 

The normal withdrawal lifecycle moves the original tx from `btc_pending_sign_ids` to `btc_pending_verify_list` once the MPC signs it, freeing the pending-sign slot. At that point the user can immediately initiate a **second** withdrawal via `ft_on_transfer → create_btc_pending_info`, which re-occupies the slot: [4](#0-3) 

With the slot full, every subsequent `cancel_withdraw` call on the original stuck tx reverts with "Too many pending sign transactions". The cancel-RBF path (`internal_cancel_withdraw`) never adds to `btc_pending_sign_ids`, so the check is purely a gate that the user controls: [5](#0-4) 

The same pattern applies to `cancel_active_utxo_management`, which performs the identical `require_pending_sign_capacity` check on the initiating account before creating the cancel RBF: [6](#0-5) 

### Impact Explanation
A user whose withdrawal is stuck on Bitcoin can indefinitely block the operator from cancelling it. The original withdrawal's nBTC (already transferred to the bridge) remains locked. The bridge accumulates uncancellable stuck withdrawals, degrading its operational state and requiring a contract upgrade or governance intervention to resolve. This matches **Medium — attacker-triggered temporary locking of bridged funds / bypass of bridge cancel policy**.

### Likelihood Explanation
The attack requires only that the user hold a small amount of nBTC above `min_withdraw_amount` to repeatedly re-fill their pending-sign slot. The nBTC spent on the blocking withdrawal is not lost — if the operator cancels the blocking withdrawal, the tokens are returned via `lost_found` and the user can repeat the attack. The window to front-run is the entire `max_btc_tx_pending_sec` period, which is a configurable but substantial timeout. Any user with a stuck withdrawal and residual nBTC balance can execute this.

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` and `cancel_active_utxo_management`. These are privileged operator actions that create cancel-RBF entries; the cancel-RBF path does not add to `btc_pending_sign_ids`, so the capacity check is both unnecessary and exploitable. Alternatively, scope the check only to user-initiated actions (`ft_on_transfer`, `withdraw_rbf`) and skip it for operator-initiated cancellations.

### Proof of Concept

1. Alice initiates a withdrawal: `nbtc.ft_transfer_call(bridge, 100_000, WithdrawMsg{...})`. Her `btc_pending_sign_ids` = `{tx_A}`.
2. MPC signs `tx_A`; it moves to `btc_pending_verify_list`. Her `btc_pending_sign_ids` = `{}`.
3. `tx_A` is broadcast to Bitcoin but stalls (low fee, mempool congestion). After `max_btc_tx_pending_sec`, the operator prepares to call `cancel_withdraw(tx_A, ...)`.
4. Alice observes the pending operator call and immediately calls `nbtc.ft_transfer_call(bridge, min_withdraw_amount, WithdrawMsg{...})`, creating `tx_B`. Her `btc_pending_sign_ids` = `{tx_B}`.
5. Operator's `cancel_withdraw(tx_A, ...)` executes: `require_pending_sign_capacity` sees `pending_sign_count() = 1 >= max = 1` → **panics**, cancel reverts.
6. Alice repeats step 4 each time the operator retries. Alice's nBTC for `tx_B` is returned via `lost_found` if the operator cancels `tx_B` first, allowing indefinite repetition.
7. `tx_A` remains permanently stuck in `btc_pending_verify_list`; the bridge cannot reclaim the locked nBTC without a contract upgrade.

    pub fn internal_cancel_withdraw(
        &mut self,
        _account_id: &AccountId,
        original_btc_pending_verify_id: String,
        cancel_withdraw_rbf_psbt: PsbtWrapper,
        predecessor_account_id: AccountId,
    ) -> String {
        let original_tx_btc_pending_info =
            self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
        require!(
            nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
                > self.internal_config().max_btc_tx_pending_sec,
            "Please wait user rbf"
        );
        original_tx_btc_pending_info.assert_not_canceled();
        original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();

        let mut btc_pending_info = init_rbf_btc_pending_info(
            original_tx_btc_pending_info,
            PendingInfoState::WithdrawCancelRbf(RbfState {
                stage: PendingInfoStage::PendingSign,
                original_tx_id: original_btc_pending_verify_id.clone(),
            }),
        );
        let (actual_received_amount, gas_fee) = self.check_cancel_withdraw_rbf_psbt_valid(
            original_tx_btc_pending_info,
            &cancel_withdraw_rbf_psbt,
        );

        btc_pending_info.gas_fee = gas_fee;
        btc_pending_info.burn_amount = gas_fee;
        btc_pending_info.actual_received_amount = actual_received_amount;
        Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);
        let excess_gas_fee = gas_fee
            .saturating_sub(btc_pending_info.transfer_amount - btc_pending_info.withdraw_fee);
        if excess_gas_fee > 0 {
            require!(
                self.acl_has_role(Role::DAO.into(), predecessor_account_id),
                "gas fee exceeds the user's balance, only the owner is allowed to cancel"
            );
            require!(
                self.data().cur_available_protocol_fee >= excess_gas_fee,
                "Insufficient protocol fee"
            );
            self.data_mut().cur_available_protocol_fee -= excess_gas_fee;
            self.data_mut().cur_reserved_protocol_fee += excess_gas_fee;
        }
        self.internal_unwrap_mut_btc_pending_info(&original_btc_pending_verify_id)
            .do_cancel(gas_fee, excess_gas_fee);
        self.set_rbf_pending_info(
            &original_btc_pending_verify_id,
            btc_pending_info,
            cancel_withdraw_rbf_psbt,
            true,
        )
    }
