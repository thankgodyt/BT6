### Title
Envelope Validation Result Silently Discarded in `revalidateHeader` via No-Op `assertWithMsg` in Production Builds — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`)

---

### Summary

`revalidateHeader` in `HeaderValidation.hs` guards its envelope check with `assertWithMsg`, which is compiled as a **complete no-op** in production builds (without `ENABLE_ASSERTIONS`). The result of `validateEnvelope` — which checks block-number consecutiveness, slot monotonicity, and hash-chain integrity — is silently discarded. If `revalidateHeader` is ever called on a header whose envelope is invalid (e.g., due to ImmutableDB corruption or a caller bug), the node accepts the resulting `HeaderState` without error, exactly mirroring the CToken pattern of ignoring a returned error code.

---

### Finding Description

**Root cause — `Assert.hs` lines 9–13:**

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

Without the `ENABLE_ASSERTIONS` CPP flag the `Left`-branch is not compiled. Every call `assertWithMsg (Left "…") x` silently returns `x`. [1](#0-0) 

**Call site — `HeaderValidation.hs` lines 539–561:**

`revalidateHeader` computes `envelopeCheck` (a full run of `validateEnvelope`) and passes it to `assertWithMsg`. In production the check is computed but its `Left` branch is never acted upon; the function unconditionally returns the new `HeaderState` with `reupdateChainDepState` (which also skips KES/VRF checks by design). [2](#0-1) 

`validateEnvelope` enforces:
- consecutive block numbers
- strictly increasing slot numbers
- hash-chain linkage
- checkpoint matching [3](#0-2) 

**Production caller — `Extended.hs` lines 213–227:**

`reapplyBlockLedgerResult` on `ExtLedgerState` calls `revalidateHeader` directly. This is the path exercised during ImmutableDB replay at node initialisation and during chain-selection fork switching. [4](#0-3) 

---

### Impact Explanation

If `revalidateHeader` is invoked on a header whose envelope is invalid — wrong block number, non-monotone slot, or broken hash chain — the node silently accepts the resulting `HeaderState`. Downstream, this corrupted `HeaderState` is used as the authoritative consensus state for subsequent header validation (`validateHeader` reads `untickedHeaderStateTip` from it) and for chain selection. A node that has accepted a wrong `HeaderState` will diverge from honest peers: it will accept headers that honest nodes reject and reject headers that honest nodes accept, constituting a **consensus safety failure and durable use of the wrong ledger state**.

---

### Likelihood Explanation

The precondition for `revalidateHeader` — that the header was previously validated — is maintained under normal operation. The silent discard becomes exploitable in two realistic scenarios:

1. **ImmutableDB corruption without operator fault** (hardware bit-flip, filesystem error, or a crafted snapshot imported from an untrusted source). During initialisation the node replays every block in the ImmutableDB via `reapplyBlockLedgerResult`; a corrupted header envelope would pass silently.
2. **Latent caller bug**: any future or existing code path that calls `reapplyBlockLedgerResult` with a `TickedExtLedgerState` built from the wrong prior state (e.g., wrong fork anchor) would produce an envelope mismatch that is silently swallowed.

Because `ENABLE_ASSERTIONS` is a development-only flag absent from production Cardano node builds, the safety net is permanently absent in all deployed nodes.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with a hard error that fires unconditionally in all build configurations, or promote `revalidateHeader` to return `Except (HeaderError blk) (HeaderState blk)` (matching `validateHeader`) so callers are forced to handle the error. At minimum, `assertWithMsg` should be enabled in production release builds, or the envelope check should be performed with `runExcept` and an explicit `error`/exception on `Left` regardless of the CPP flag. [1](#0-0) 

---

### Proof of Concept

1. Build `ouroboros-consensus` **without** `-DENABLE_ASSERTIONS` (the default production configuration).
2. Construct a `TickedExtLedgerState` whose `tickedHeaderState` has tip `T` (block number `N`, slot `S`, hash `H`).
3. Call `reapplyBlockLedgerResult cfg blk tickedExtLedgerState` where `blk`'s header has block number `N+2` (skipping one), slot `S-1` (non-monotone), or `prevHash ≠ H`.
4. Observe that `revalidateHeader` returns a `HeaderState` with the new (invalid) tip without raising any exception — `envelopeCheck` evaluates to `Left "UnexpectedBlockNo …"` but `assertWithMsg` discards it and returns the `HeaderState` unchanged.
5. The returned `ExtLedgerState` now carries a `HeaderState` whose `headerStateTip` reflects the invalid header, and all subsequent `validateHeader` calls use this corrupted tip as `oldTip`, accepting headers that chain off the invalid block. [5](#0-4) [4](#0-3)

validateEnvelope ::
  forall blk.
  ValidateEnvelope blk =>
  TopLevelConfig blk ->
  LedgerView (BlockProtocol blk) ->
  -- | Old tip
  WithOrigin (AnnTip blk) ->
  Header blk ->
  Except (HeaderEnvelopeError blk) ()
validateEnvelope cfg ledgerView oldTip hdr = do
  unless (actualBlockNo == expectedBlockNo) $
    throwError $
      UnexpectedBlockNo expectedBlockNo actualBlockNo
  unless (actualSlotNo >= expectedSlotNo) $
    throwError $
      UnexpectedSlotNo expectedSlotNo actualSlotNo
  unless (checkPrevHash' (annTipHash <$> oldTip) actualPrevHash) $
    throwError $
      UnexpectedPrevHash (annTipHash <$> oldTip) actualPrevHash
  validateIfCheckpoint (topLevelConfigCheckpoints cfg) hdr
  withExcept OtherHeaderEnvelopeError $
    additionalEnvelopeChecks cfg ledgerView hdr
 where

    WithOrigin (HeaderHash blk) ->
    ChainHash blk ->
    Bool
  checkPrevHash' Origin GenesisHash = True
  checkPrevHash' (NotOrigin h) (BlockHash h') = h == h'
  checkPrevHash' _ _ = False
