### Title
Peras Certificate Validation Stub Always Accepts Any Inbound Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production implementation of `validatePerasCert` in the `BlockSupportsPeras` type-class instance unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural checks. The production inbound-certificate pipeline (`makePerasCertPoolWriterFromChainDB`) calls this stub directly. An unprivileged peer can therefore inject arbitrary, structurally-crafted Peras certificates that bypass all committee-membership, quorum, BLS-signature, and round-number checks, have them stored in the `PerasCertDB`, and trigger chain-selection for any block the attacker names.

---

### Finding Description

`BlockSupportsPeras` is the type-class that every block type must satisfy to participate in the Peras protocol. It declares `validatePerasCert` as the gate that must accept or reject inbound certificates before they are stored or acted upon.

The repository contains exactly **one** instance of this class:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is a catch-all `StandardHash blk` instance — no era-specific or Cardano-specific override exists anywhere in the repository (confirmed by `grep` returning only two matches in the same file). Every block type, including the live Cardano block type, therefore resolves to this stub.

The production inbound path for peer-supplied certificates is `makePerasCertPoolWriterFromChainDB`, which wires this stub directly into `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
```

`processCerts` calls `validateCert` on every certificate not already in the DB. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is unconditionally forwarded to `ChainDB.addPerasCertAsync`.

`addPerasCertAsync` feeds into `chainSelSync`, which calls `chainSelectionForBlock` for the block named in the certificate's `boostedBlock` field. This means the attacker-controlled `boostedBlock` point directly influences chain selection.

The analog to the ERC1155 bug is exact: `rageQuit()` was designed to handle all treasury assets (ETH, ERC20, ERC1155) but silently skipped ERC1155. Here, `validatePerasCert` is designed to check all certificate properties (committee membership, quorum threshold, BLS aggregate signature, round-number bounds) but silently skips all of them — the "validation" function is present and called, but the required checks for the certificate type it handles are entirely absent.

Additionally, `getPerasCertInBlock _ = Nothing` means certificates embedded in on-chain blocks are never extracted, so the only source of certificates entering the `PerasCertDB` is the unauthenticated peer diffusion path.

---

### Impact Explanation

An unprivileged peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block in the `VolatileDB`.
2. Send it over the Peras object-diffusion mini-protocol.
3. The node accepts it unconditionally, stores it in `PerasCertDB`, and immediately triggers `chainSelectionForBlock` for the attacker-named block.
4. Because Peras weight is additive in chain selection, the attacker can make the node prefer a fork that would otherwise lose under the longest-chain rule, causing the node to diverge from the canonical chain.

This is a **Critical** bypass of Peras certificate/vote checks: an unauthorized certificate is accepted and directly influences chain selection without any committee, quorum, or signature verification.

---

### Likelihood Explanation

The attack requires only network access to a node running the Peras object-diffusion mini-protocol. No keys, stake, or privileged access are needed. The stub is the only implementation in the codebase and is wired into the production `ChainDB`-backed writer. Any peer that can open a connection and speak the object-diffusion protocol can exploit this.

---

### Recommendation

1. Implement a real `validatePerasCert` for the Cardano block type (resolving issue #73 and #120) that verifies: committee-seat eligibility proofs, BLS aggregate signature over the `(roundNo, boostedBlock)` payload, quorum threshold against the current stake distribution, and round-number bounds.
2. Until a real implementation exists, the degenerate instance should **not** be wired into the production `makePerasCertPoolWriterFromChainDB`. The `TODO` comment acknowledges this but the placeholder is already reachable from live code.
3. Add a Cardano-specific `BlockSupportsPeras` instance that overrides the catch-all, so the compiler enforces that production code never falls back to the stub.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
