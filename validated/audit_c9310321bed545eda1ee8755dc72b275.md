### Title
All-or-Nothing Batch Rejection in Peras Vote/Certificate Ingest Allows Adversary to Suppress Valid Votes and Certificates — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `PerasCert.hs`)

---

### Summary

`processVotes` and `processCerts` implement an all-or-nothing batch rejection policy: if **any single** vote or certificate in a received batch fails validation, the **entire batch** is thrown away and the peer is disconnected. An unprivileged adversary peer can exploit this by including one crafted invalid vote/certificate alongside valid ones it has observed on the network. All valid votes/certificates in the poisoned batch are silently discarded. Repeated or timed application of this attack can prevent a node from accumulating the votes needed to reach Peras quorum for a round, suppressing certificate generation and depriving the node of the Peras weight boost on the canonical chain — a chain-selection weakening reachable by any peer.

---

### Finding Description

`processVotes` in `PerasVote.hs` and `processCerts` in `PerasCert.hs` share the same structural pattern:

```
partitionEithers (validate <$> batch)
  ([], valid)  -> add all valid objects
  (errs, _)    -> throw exception   -- entire batch dropped, peer disconnected
``` [1](#0-0) [2](#0-1) 

The code comment at line 174–183 of `PerasCert.hs` explicitly acknowledges the all-or-nothing design:

> "Some certs are invalid => reject the whole batch" [3](#0-2) 

The `throw` call (synchronous, from `GHC.Exception`) propagates out of the ObjectDiffusion writer thread, which the `withPeer` bracket in `ouroboros-network` is expected to catch and translate into a peer disconnection. The valid objects in the `_` (discarded) arm of `partitionEithers` are never added to the pool. [4](#0-3) 

The vote validation function `validatePerasVote` already performs a real check — it returns `Left PerasValidationErr` for any vote whose voter ID is absent from the current stake distribution: [5](#0-4) 

This means the attack is exercisable today, not only after future cryptographic validation is wired in.

---

### Impact Explanation

Peras votes accumulate per-round to reach a quorum threshold. Once quorum is reached, a certificate is forged and stored; that certificate then provides a weight boost to the boosted block during chain selection (`preferAnchoredCandidate` / `compareCandidateChains`). [6](#0-5) 

If an adversary can prevent a node from accumulating the votes needed for quorum in a given round, the node will not generate (or accept) the certificate for that round. Without the certificate, the weight boost is absent from the node's chain-selection view. The node may then prefer a competing chain that lacks the boost over the canonical chain that carries it — a chain-selection deviation beyond the intended Peras security assumptions.

This maps to the **High** allowed impact: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The attack requires only an unprivileged peer connection via the ObjectDiffusion mini-protocol. The adversary:

1. Observes valid votes `v1 … vN` already circulating on the network (public gossip).
2. Crafts one invalid vote `v_bad` — e.g., using a voter ID not present in the current stake distribution (public information).
3. Sends the batch `[v1, …, vN, v_bad]` to the target node.

No key material, stake majority, or privileged access is required. The attack can be repeated from multiple sybil peers to exhaust the node's ability to receive valid votes from any single connection before the round window closes.

---

### Recommendation

Replace the all-or-nothing rejection with per-object independent processing:

- Validate each vote/certificate individually.
- Add valid objects to the pool immediately.
- Collect invalid objects separately; log them and count them.
- Disconnect the peer only if the fraction of invalid objects exceeds a configurable threshold (or if any object is invalid and the peer is known to be adversarial by other signals).

This mirrors the `try/catch`-per-derivative recommendation in the original M-06 report: skip the failed item rather than aborting the entire batch.

---

### Proof of Concept

```
1. Adversary peer A connects to honest node N via ObjectDiffusion.
2. A observes valid votes v1, v2, v3 from eligible voters on the network.
3. A crafts v_bad: a PerasVote with pvVoteVoterId set to a voter ID
   not present in N's current PerasVoteStakeDistr.
4. A calls opwAddObjects [v1, v2, v3, v_bad] on N.
5. processVotes runs:
     validationResults = [Right vv1, Right vv2, Right vv3, Left PerasValidationErr]
     partitionEithers → ([PerasValidationErr], [vv1, vv2, vv3])
     → throw (PerasVoteValidationError [PerasValidationErr])
6. vv1, vv2, vv3 are in the discarded arm and are never passed to addVote.
7. N disconnects from A.
8. If v1, v2, v3 were the last votes needed for quorum in this round,
   N fails to forge the certificate.
9. N's chain selection proceeds without the Peras weight boost for this round,
   making N susceptible to preferring a non-boosted competing chain.
``` [1](#0-0) [2](#0-1)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
