### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is an unconditional stub that returns `Right` for every certificate it receives, performing no cryptographic, quorum, or committee-membership checks. Because the `PerasCert` data type itself carries no signature or proof field, no real validation is even possible. Any unprivileged peer that connects via the live `PerasCertDiffusion` mini-protocol can submit a crafted certificate naming any block in the VolatileDB as the boosted block; the certificate is accepted, stored, and used to inflate that block's chain-selection weight, potentially causing the node to switch to a non-canonical fork.

---

### Finding Description

**Root cause — stub validation that always succeeds**

The universal `BlockSupportsPeras` instance (the only instance in the codebase) defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The `PerasCert` data type carries only a round number and a boosted block point — no aggregate signature, no voter set, no VRF proof:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

There is no other `BlockSupportsPeras` instance in the repository; `grep` for `BlockSupportsPeras.*instance` returns no results.

**Attacker-controlled entry path**

The `PerasCertDiffusion` mini-protocol is wired into the live node-to-node handler in `NodeToNode.hs`:

`processCerts` accepts the entire batch if all calls to `validatePerasCert` return `Right`, then timestamps and stores each certificate: [5](#0-4) 

**How the accepted certificate reaches chain selection**

Once stored, `chainSelSync` processes the certificate via `ChainSelAddPerasCert`. It looks up the boosted block in the VolatileDB and calls `chainSelectionForBlock` for it:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [6](#0-5) 

`constructPreferableCandidates` then calls `preferAnchoredCandidate` with the current `PerasWeightSnapshot`, which now includes the attacker-supplied boost. When Peras weights are non-empty, chain comparison uses `weightedSelectView`, which computes `wsvTotalWeight = blockNo + weightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [7](#0-6) 

A fork that was previously lighter than the current chain can become heavier after the artificial boost, causing `preferAnchoredCandidate` to return `ShouldSwitch` and the node to adopt the non-canonical fork. [8](#0-7)

### Impact Explanation

**Severity: High** — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

A single connecting peer with no stake, no keys, and no special privileges can:

1. Craft a `PerasCert` naming any block in the target node's VolatileDB as `pcCertBoostedBlock`.
2. Send it over the `PerasCertDiffusion` mini-protocol.
3. The certificate passes `validatePerasCert` unconditionally and is stored.
4. Chain selection re-runs for the boosted block; the artificial `perasWeight` boost is added to its fragment's total weight.
5. If the boosted block is on a competing fork, that fork may now be preferred, causing the node to roll back its current selection and adopt the attacker-chosen chain.

Because `perasWeight` is added on top of block number, even a shorter fork can be made to appear heavier than the honest chain, violating the chain-growth and common-prefix security properties that Peras is designed to strengthen.

---

### Likelihood Explanation

**High.** The `PerasCertDiffusion` mini-protocol is active in the production node-to-node handler. Any peer that can establish a connection — no stake, no keys required — can send crafted certificates. The validation function unconditionally returns `Right`, so exploitation requires only constructing a valid CBOR-encoded `PerasCert` (two fields: a `Word64` round number and a `Point`), which is trivially achievable.

---

### Recommendation

1. **Implement real certificate validation.** `validatePerasCert` must verify an aggregate BLS/KES signature over the `(electionId, candidate)` pair from a quorum of registered committee members, as specified by the Peras design. Until this is done, the function must not return `Right` unconditionally.
2. **Add a signature field to `PerasCert`.** The data type must carry the aggregate signature and the voter set so that validation is structurally possible.
3. **Gate the mini-protocol.** Until validation is complete, the `PerasCertDiffusion` inbound handler should reject all incoming certificates (return a hard error or be disabled), rather than silently accepting them.
4. **Track the open issue.** The existing `https://github.com/tweag/cardano-peras/issues/120` covers this; it should be treated as a security-critical blocker before Peras is enabled on any network that connects to untrusted peers.

---

### Proof of Concept

**Private-testnet sequence (no privileged access required):**

1. Start a node with Peras enabled and at least one block in its VolatileDB (hash `H`, slot `S`).
2. Connect a malicious peer to the node's `PerasCertDiffusion` inbound port.
3. Send a CBOR-encoded `PerasCert` with `pcCertRound = 1` and `pcCertBoostedBlock = BlockPoint S H` (pointing to a block on a competing fork, or any block whose chain should not be preferred).
4. Observe: `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
5. The cert is stored; `chainSelSync` triggers `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` now computes `wsvTotalWeight` for the boosted fork as `blockNo + perasWeight`, which may exceed the current chain's total weight.
7. The node switches to the attacker-chosen fork.

The attack requires only a TCP connection and the ability to send a two-field CBOR structure; no cryptographic material is needed.
