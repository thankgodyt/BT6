Audit Report

## Title
Tokens Permanently Burned/Locked When Transfer Amount Normalizes to Zero — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` increments the nonce, stores the transfer message, and burns or locks the full raw token amount before any check that the normalized destination-chain amount is non-zero. For tokens with a large decimal gap (e.g., `origin_decimals=24`, `decimals=6`), any amount below `10^18` base units normalizes to 0. Every subsequent `sign_transfer` call then reverts with `InvalidAmountToTransfer`, while the already-committed burn/lock has no recovery path.

## Finding Description
`normalize_amount` performs floor division with no zero-guard:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

In `init_transfer`, the nonce is incremented and the transfer message is built with only a `fee < amount` check — which passes for `amount=1, fee=0`: [2](#0-1) 

`init_transfer_internal` is then called, which stores the message and unconditionally burns (deployed tokens) or locks (native tokens) the full raw amount, returning `U128(0)` to signal the token contract to keep the funds: [3](#0-2) 

Only later, in `sign_transfer`, is normalization applied and the zero-check enforced: [4](#0-3) 

This `require!` panic reverts only the `sign_transfer` transaction. The `init_transfer` state — burned/locked tokens and the stored `pending_transfers` entry — is already committed and cannot be rolled back. No `cancel_transfer` or equivalent public recovery function exists anywhere in the contract. [5](#0-4) 

## Impact Explanation
Any user who sends an amount below `10^(origin_decimals - decimals)` base units permanently loses their tokens. The tokens are burned (for deployed bridge tokens via a detached cross-contract call) or locked (for native tokens via internal accounting) in `init_transfer_internal`, but the cross-chain transfer can never be completed because every `sign_transfer` call will revert. This constitutes permanent freezing/loss of bridged funds, matching the critical impact scope.

## Likelihood Explanation
The entry path is the public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow, callable by any token holder. For tokens with a large decimal gap (e.g., 24 → 6 decimals, divisor = `10^18`), the threshold is `10^18` base units. A user sending a sub-threshold amount by mistake (e.g., due to UI rounding, copy-paste error, or testing with a small amount) triggers the permanent loss. No minimum-amount guard exists in `init_transfer`. The protocol's own comment at line 2781-2783 acknowledges that dust stays locked/burned when fee=0, but does not guard against the case where the *entire* amount truncates to zero before tokens are committed. [6](#0-5) 

## Recommendation
Add a normalization check in `init_transfer` (or `init_transfer_internal`) before burning/locking tokens. If the destination-chain decimals are already registered, verify `normalize_amount(amount.0, decimals) > 0` and revert early — returning the full amount to the caller via the NEP-141 refund mechanism (returning `transfer_message.amount` instead of `U128(0)`). Additionally, introduce a public `cancel_transfer` function so users can recover tokens from stuck pending transfers regardless of the cause.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 6` on the destination chain (divisor = `10^18`).
2. Call `ft_transfer_call` on the token contract with `amount = 1` and a valid `InitTransferMsg` (fee = 0).
3. `ft_on_transfer` → `init_transfer` → `init_transfer_internal` succeeds: 1 base unit is burned/locked, transfer message stored in `pending_transfers`, nonce incremented, `U128(0)` returned (tokens kept by bridge).
4. Relayer calls `sign_transfer` for the stored transfer ID.
5. `normalize_amount(1, {origin_decimals: 24, decimals: 6})` = `1 / 10^18` = `0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics; `sign_transfer` transaction reverts.
7. The 1 base unit is permanently burned/locked; the transfer message remains in `pending_transfers` with no recovery path.

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
