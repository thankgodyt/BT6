### Title
u128 Underflow in `check_withdraw_psbt` Blocks RBF for Small-Amount Withdrawals with High Gas Fees - (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `check_withdraw_psbt`, the subtraction `min_received_amount = max_received_amount - config.min_change_amount` at line 243 is an unchecked u128 subtraction. When `amount - withdraw_fee - gas_fee < config.min_change_amount`, `max_received_amount` is smaller than `config.min_change_amount`, causing a wrapping underflow in WASM release mode. The gas-fee bounds check that would independently reject the transaction is ordered **after** this subtraction, so a valid gas_fee can still trigger the underflow. The result is a revert with a misleading error message, permanently blocking RBF for any withdrawal where the configuration satisfies `amount - withdraw_fee < min_change_amount + max_btc_gas_fee`.

---

### Finding Description

`check_withdraw_psbt` computes the valid received-amount window as:

```rust
// psbt.rs line 242-243
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
``` [1](#0-0) 

Both subtractions are plain `u128 -` with no overflow guard. In WASM (release mode) Rust, integer underflow wraps silently.

The gas-fee bounds check that would catch an out-of-range `gas_fee` is placed **after** these two lines:

```rust
// psbt.rs line 252-258
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [2](#0-1) 

So if a user submits an RBF PSBT with a `gas_fee` that is within `[min_btc_gas_fee, max_btc_gas_fee]` but satisfies `amount - withdraw_fee - gas_fee < config.min_change_amount`, the underflow at line 243 fires first. `min_received_amount` wraps to a value near `u128::MAX`, the range check at lines 244-251 always fails, and the call reverts with a confusing "out of valid range" message rather than a meaningful one. [3](#0-2) 

The public entry point is `withdraw_rbf` (no role gate for the transaction owner):

```rust
// api/bridge.rs line 259-274
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    ...
)
``` [4](#0-3) 

It flows through `withdraw_rbf_chain_specific` → `internal_withdraw_rbf` → `check_withdraw_rbf_psbt_valid`, which calls `check_withdraw_psbt` with `amount` and `withdraw_fee` fixed from the stored original pending info:

```rust
// rbf/withdraw.rs line 23-30
let (_, _, actual_received_amount, gas_fee) = self.check_withdraw_psbt(
    withdraw_rbf_psbt,
    target_address,
    &withdraw_change_address_script_pubkey,
    &original_tx_btc_pending_info.vutxos,
    original_tx_btc_pending_info.transfer_amount,
    original_tx_btc_pending_info.withdraw_fee,
);
``` [5](#0-4) 

The user controls only the `output` field of the RBF PSBT, which determines `gas_fee = total_input_amount - total_output_amount`. By reducing total output, the user can set `gas_fee` to any value in `[min_btc_gas_fee, max_btc_gas_fee]`.

The `Config::assert_valid()` function enforces several invariants but **does not** enforce `min_withdraw_amount - max_withdraw_fee >= min_change_amount + max_btc_gas_fee`: [6](#0-5) 

This means a deployment where, for example, `min_withdraw_amount = 70_000`, `withdraw_fee = 50_000`, `max_btc_gas_fee = 50_000`, and `min_change_amount = 5_000` satisfies `70_000 - 50_000 - 50_000 < 5_000` (wraps), and every RBF attempt at or near max gas fee will underflow and revert.

---

### Impact Explanation

In WASM release mode, `max_received_amount - config.min_change_amount` wraps to approximately `u128::MAX - (config.min_change_amount - max_received_amount)`. The range check `actual_received_amount >= min_received_amount` is always false for any realistic `actual_received_amount`, so every RBF call reverts. The user's original withdrawal remains pending and cannot be fee-bumped. If the original gas fee is insufficient for confirmation, the withdrawal is stuck until an operator/DAO calls `cancel_withdraw` after `max_btc_tx_pending_sec` elapses — a stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

The condition is configuration-dependent. No invariant in `assert_valid()` prevents deploying a config where `min_withdraw_amount - max_withdraw_fee < min_change_amount + max_btc_gas_fee`. Any user whose original withdrawal was accepted near `min_withdraw_amount` with a bridge fee that leaves little headroom can trigger this by submitting an RBF PSBT with gas near `max_btc_gas_fee`. The call path is fully public and requires no privileged role.

---

### Recommendation

1. Guard the subtraction with a checked or saturating operation, and explicitly reject the PSBT when `max_received_amount < config.min_change_amount`:

```rust
let min_received_amount = max_received_amount.saturating_sub(config.min_change_amount);
```

2. Add an invariant to `Config::assert_valid()` ensuring:

```
min_withdraw_amount - max_withdraw_fee >= min_change_amount + max_btc_gas_fee
```

3. Reorder the gas-fee bounds check to execute **before** the received-amount window computation, so an out-of-range gas fee is caught with a clear error before any arithmetic on derived values.

---

### Proof of Concept

**Config values that trigger the bug:**
- `min_withdraw_amount = 70_000` sats
- `withdraw_bridge_fee.fee_min = 50_000` (so `withdraw_fee = 50_000`)
- `max_btc_gas_fee = 50_000`
- `min_change_amount = 5_000`

**Trigger:**
1. User initiates a withdrawal of exactly `70_000` sats → accepted (original gas fee = `10_000`, `max_received_amount = 10_000 >= 5_000`).
2. Transaction stalls on-chain. User calls `withdraw_rbf` with outputs totalling `total_input - 50_000` (gas_fee = `50_000 = max_btc_gas_fee`).
3. Inside `check_withdraw_psbt`:
   - `max_received_amount = 70_000 - 50_000 - 50_000` → wraps to `u128::MAX - 29_999`
   - `min_received_amount = (u128::MAX - 29_999) - 5_000` → wraps again to `u128::MAX - 34_999`
   - `require!(actual_received_amount >= u128::MAX - 34_999 ...)` → always false → **revert**
4. Gas-fee check at line 252 (`50_000 <= max_btc_gas_fee`) would have passed, but is never reached.
5. Every subsequent RBF attempt at any gas_fee ≥ `15_001` triggers the same underflow. The withdrawal is stuck.
