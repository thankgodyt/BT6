Audit Report

## Title
Missing Bridge Contract Address in `finTransfer` Signed Payload Enables Cross-Instance Replay Attacks — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
The `finTransfer` function in `OmniBridge.sol` constructs a Borsh-encoded payload for MPC signature verification that includes `omniBridgeChainId` and `destinationNonce` but never includes `address(this)`. Because the signed payload is not bound to a specific bridge contract instance, any valid MPC signature accepted by one bridge instance on a given chain is cryptographically indistinguishable from a valid signature for any other bridge instance on the same chain that shares the same `nearBridgeDerivedAddress` and `omniBridgeChainId`. An attacker can replay historical `finTransfer` calldata against a second bridge instance whose `completedTransfers` mapping has not yet recorded those nonces, causing double-spending of bridged tokens.

## Finding Description
In `OmniBridge.sol`, `finTransfer` builds `borshEncoded` as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.TransferMessage)),
    Borsh.encodeUint64(payload.destinationNonce),
    bytes1(payload.originChain),
    Borsh.encodeUint64(payload.originNonce),
    bytes1(omniBridgeChainId),
    Borsh.encodeAddress(payload.tokenAddress),
    Borsh.encodeUint128(payload.amount),
    bytes1(omniBridgeChainId),
    Borsh.encodeAddress(payload.recipient),
    ...
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

`address(this)` is never included. The only domain-separation fields are `omniBridgeChainId` (chain-level) and `destinationNonce` (replay prevention within one instance). The `completedTransfers` mapping that enforces nonce uniqueness is per-contract storage — a fresh deployment starts with all entries `false`.

The NEAR side's `TransferMessagePayload.encode_hashable()` serializes `destination_nonce`, `transfer_id`, `token_address`, `amount`, `recipient`, `fee_recipient`, and `message`, but no destination bridge contract address. The Starknet `to_borsh` encodes `chain_id` twice but also omits the contract address. The signed payload is therefore identical for any two bridge instances on the same chain sharing the same `nearBridgeDerivedAddress` and `omniBridgeChainId`.

The NEAR bridge assigns `destination_nonce` via `get_next_destination_nonce`, which is keyed by `ChainKind` (e.g., `ChainKind::Eth` for all EVM chains). This means all EVM bridge instances on the same chain share the same nonce counter from NEAR's perspective, but each maintains its own independent `completedTransfers` mapping.

Two realistic configurations produce the required second instance:
1. **Non-proxy redeployment**: The bridge is deployed as a UUPS proxy (`upgrades.deployProxy`). If the protocol deploys a new proxy (e.g., after a critical bug fix or architecture change), the new proxy's `completedTransfers` is empty while the old proxy's nonces 1–N are all marked used. The MPC key derivation path is hardcoded as `"bridge-1"` for the same NEAR account ID, so `nearBridgeDerivedAddress` is identical.
2. **Co-existence of `OmniBridge` and `OmniBridgeWormhole`**: `OmniBridgeWormhole` extends `OmniBridge` and both can be deployed on the same chain. The deployment script derives `nearBridgeDerivedAddress` from the same NEAR account ID and path `"bridge-1"` for both variants. If both are deployed with the same `omniChainId`, a signature produced for one is valid for the other.

## Impact Explanation
**Critical — double-spending / unauthorized minting of bridged tokens.**

An attacker who observes a historical `finTransfer` transaction on Bridge V1 (nonce = K, signature = σ) can submit the identical calldata to Bridge V2. V2 checks `completedTransfers[K] == false` (true, since V2 is fresh), recomputes the identical `keccak256(borshEncoded)` (no contract address in the payload), recovers the same `nearBridgeDerivedAddress`, and mints or unlocks tokens to the specified recipient. Tokens disbursed on V1 are disbursed again on V2, constituting a direct double-spend. This matches the allowed impact: "Cross-chain replay, message forgery, event/proof parsing flaw, light-client verification bypass, Wormhole VAA verification bypass, or chain/domain separation flaw enabling invalid finalization or double-spending."

## Likelihood Explanation
The attacker requires only:
- Public on-chain calldata from any historical `finTransfer` transaction (fully observable)
- A second bridge instance on the same chain sharing the same `nearBridgeDerivedAddress` and `omniBridgeChainId`

No private keys, admin access, or privileged roles are needed by the attacker. The second instance arises from a protocol-level operational event (redeployment or co-deployment), not from attacker action. Bridge redeployments are a realistic operational event, particularly given the presence of migration infrastructure (`migrate.rs`) and the UUPS upgrade pattern. The co-existence of `OmniBridge` and `OmniBridgeWormhole` on the same chain is architecturally possible given the shared derivation path. Every previously finalized transfer with nonce ≤ N is independently replayable on the fresh instance.

## Recommendation
Include the destination bridge contract address in the Borsh-encoded payload before hashing. On the EVM side, add `Borsh.encodeAddress(address(this))` to `borshEncoded` in `finTransfer`. The NEAR `sign_transfer` → `encode_hashable()` payload construction and all destination-chain verifiers (Starknet `to_borsh`, Solana `serialize_for_near`) must be updated consistently to include the destination bridge contract address, so that a signature produced for one contract instance is cryptographically bound to that instance and cannot be accepted by any other.

## Proof of Concept
```
// Setup
Bridge V1 deployed at 0xAAAA on Ethereum
  nearBridgeDerivedAddress = X (derived from nearBridgeAccountId + "bridge-1")
  omniBridgeChainId = 1
  completedTransfers[7] = true  (nonce 7 already finalized)

Bridge V2 deployed at 0xBBBB on Ethereum (fresh deployment, same MPC key)
  nearBridgeDerivedAddress = X  (same derivation)
  omniBridgeChainId = 1         (same chain)
  completedTransfers[7] = false (empty mapping)

// Step 1: Attacker observes historical finTransfer on V1
//   calldata: (signatureData=σ, payload={destinationNonce=7, originChain=Near,
//              originNonce=42, tokenAddress=USDC, amount=1000, recipient=Alice, ...})
//   V1 accepted: completedTransfers[7] = true, Alice received 1000 USDC

// Step 2: Attacker replays identical calldata on V2
//   V2.completedTransfers[7] == false  → passes nonce check
//   borshEncoded is byte-for-byte identical (no address(this) in payload)
//   keccak256(borshEncoded) is identical
//   ECDSA.recover(hash, σ) == X == V2.nearBridgeDerivedAddress  → passes
//   V2 mints/unlocks 1000 USDC to Alice (or attacker-controlled address)

// Result: 1000 USDC double-spent; bridge protocol is insolvent by that amount
// Attack is repeatable for every nonce 1..N finalized on V1
```

A local integration test can demonstrate this by deploying two `OmniBridge` proxy instances with the same `nearBridgeDerivedAddress` and `omniBridgeChainId`, calling `finTransfer` on the first with a valid test-key signature, then replaying the identical call on the second and asserting that tokens are minted a second time.
