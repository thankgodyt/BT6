### Title
Peras Quorum Check Bypassed by Unit Mismatch in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` (which may carry absolute lovelace values from the ledger stake distribution) directly against `perasQuorumStakeThreshold` (a relative fraction, e.g. `3/4`). The code itself documents that this comparison is only meaningful when both operands are in the same units, but no normalization is enforced. If the stake distribution is populated with absolute lovelace values — the natural result of reading from the ledger — any single vote from any legitimate pool trivially satisfies the quorum check, allowing an unprivileged peer to forge a Peras certificate for an arbitrary block with a single crafted vote.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

where `quorumThreshold` is `3/4` (a relative fraction) and `stake` is `unPerasVoteStake voteStake` — a `Rational` whose unit is unspecified. [1](#0-0) 

The code carries an explicit TODO warning:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`PerasVoteStake` values are populated by looking up the voter's entry in `PerasVoteStakeDistr` during `validatePerasVote`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [3](#0-2) 

The `PerasVoteStakeDistr` is provided externally via `getStakeDistrSTM` in the production vote pool writers:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

The comment on that same call site acknowledges: "In the future, we won't read it from the stake distr directly, but rather use the committee selection data." This confirms the current path reads raw ledger stake, which is in absolute lovelace — not normalized fractions. [5](#0-4) 

The accumulated `PerasVoteStake` is then passed to `votesReachQuorum` → `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5)

### Impact Explanation

**Scenario A — absolute stake in distribution (lovelace >> 0.77):**
A pool with even 1 lovelace of stake has `PerasVoteStake = 1 % 1`. The check `1 >= 3/4 + 2/100` evaluates to `True`. A single vote from any legitimate pool immediately satisfies quorum. The attacker forges a `ValidatedPerasCert` for an arbitrary block, which is then added to the ChainDB and boosts that block's chain weight by `perasWeight` (default: 15). Honest nodes running `preferCandidate` via `wsvTotalWeight` will switch to the boosted chain, accepting a non-canonical or adversarially chosen block. [7](#0-6) 

**Scenario B — relative stake in distribution but quorum threshold is absolute:**
The inverse: quorum is never reachable, permanently disabling the Peras certificate mechanism and its chain-quality guarantees.

The primary danger is Scenario A: **unauthorized Peras certificate acceptance**, enabling chain selection manipulation by an unprivileged peer.

---

### Likelihood Explanation

The code comment explicitly states the normalization is unresolved ("no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake"). The production vote pool writers read the stake distribution directly from the ledger without any normalization step visible in the codebase. Any peer operating a legitimate stake pool (or any peer whose `PerasVoterId` appears in the distribution) can trigger this path by sending a single `PerasVote` message via the object diffusion mini-protocol. No key compromise, admin access, or stake majority is required.

---

### Recommendation

1. **Enforce unit consistency at the boundary**: normalize `PerasVoteStake` to a relative fraction (divide by total stake in the distribution) before storing it in `ValidatedPerasVote`, or pass the total stake into `stakeAboveThreshold` and normalize there.
2. **Add a type-level distinction** between absolute and relative stake (e.g., `AbsoluteStake` vs `RelativeStake` newtypes) so the compiler rejects mismatched comparisons.
3. **Resolve the TODO** at `SupportsPeras.hs:155–161` before any production deployment of Peras voting.
