### Title
`request_refund` Does Not Verify Caller Is the Deposit Owner, Enabling Refund Address Hijacking — (`File: contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The public `request_refund` function accepts a `deposit_msg` and a caller-supplied `refund_address` without verifying that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`. Any unprivileged NEAR account can submit a refund request for any unfinalized deposit UTXO and inject an arbitrary BTC destination address. Because only one refund request can exist per UTXO, this permanently blocks the legitimate depositor from filing their own request and, after the `unsafe_refund_timelock_sec` elapses, allows the attacker to redirect the deposited BTC to their own address.

---

### Finding Description

`request_refund` is a public, payable function: [1](#0-0) 

It delegates to `internal_request_refund`, which contains the only `refund_address` validation: [2](#0-1) 

This check only enforces consistency when `deposit_msg.refund_address` is already set. When it is `None` — the common case for users who did not pre-authorize a BTC refund address — the caller may supply **any** BTC address and the contract accepts it without question.

The `DepositMsg` struct shows that `refund_address` is an optional field: [3](#0-2) 

After the Light Client verifies the transaction, `request_refund_callback` stores the attacker-supplied `refund_address` verbatim in the `RefundRequest`: [4](#0-3) 

A duplicate-request guard then permanently blocks the legitimate depositor: [5](#0-4) 

Once the `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone and sends BTC to the stored `refund_address`: [6](#0-5) 

The timelock logic confirms that the longer `unsafe_refund_timelock_sec` applies precisely when `deposit_msg.refund_address` is `None` (i.e., the attacker-controlled path): [7](#0-6) 

---

### Impact Explanation

**Medium** (escalates to Critical if DAO/Operator does not reject in time).

- An attacker who front-runs the legitimate depositor permanently occupies the UTXO's refund slot, preventing the real owner from ever filing their own request.
- After `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the bridge's MPC pipeline signs a transaction paying the attacker's BTC address — a direct theft of the deposited BTC.
- Even if DAO/Operator rejects the malicious request, the depositor's funds are temporarily locked and the depositor must re-submit, paying another storage deposit.

---

### Likelihood Explanation

**Medium.**

- The attack requires no special privilege — any NEAR account can call `request_refund`.
- The attacker must monitor the Bitcoin mempool/chain for deposits whose `deposit_msg.refund_address` is `None` and whose `verify_deposit` has not yet been called — a straightforward off-chain task.
- The attacker must attach the storage deposit (anti-spam fee), which is a minor economic barrier.
- The `unsafe_refund_timelock_sec` window gives DAO/Operator a chance to reject, but this is an operational assumption, not a code-level guarantee, and the DAO may not monitor every request.

---

### Recommendation

Add an ownership check at the start of `request_refund` (or inside `internal_request_refund`) that requires the caller to be the `deposit_msg.recipient_id`:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<u128>,
) -> Promise {
+   let caller = env::predecessor_account_id();
+   require!(
+       caller == deposit_msg.recipient_id
+           || self.acl_has_role(Role::DAO.into(), caller.clone())
+           || self.acl_has_role(Role::Operator.into(), caller.clone()),
+       "Only the deposit recipient or a privileged role may request a refund"
+   );
    // ... existing gas_fee privilege check ...
```

This mirrors the fix recommended in the external report: derive the authoritative owner from the resource itself (`deposit_msg.recipient_id`) and enforce it at the entry point.

---

### Proof of Concept

1. Alice deposits BTC using a `DepositMsg` with `recipient_id = "alice.near"` and `refund_address = None`. The relayer never calls `verify_deposit`.
2. Bob (attacker) observes the confirmed BTC transaction on-chain and reconstructs Alice's `deposit_msg`.
3. Bob calls `request_refund(deposit_msg, "bob_btc_address", tx_bytes, vout, proof, None)` with the required storage deposit attached.
4. `internal_request_refund` verifies the transaction via the Light Client; `request_refund_callback` stores `refund_address = "bob_btc_address"` in the `RefundRequest`.
5. Alice attempts `request_refund` for the same UTXO — it panics with `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (and assuming DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key, None)`.
7. The bridge builds a PSBT paying `"bob_btc_address"` and requests an MPC signature — Alice's BTC is sent to Bob.
