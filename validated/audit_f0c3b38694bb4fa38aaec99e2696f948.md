`validatePerasCert` Stub Unconditionally Accepts Any Certificate, Enabling Unauthorized Peras Weight Boost and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` (success) for **any** certificate, without performing any cryptographic or structural validation. This is the direct analog of the SpigotLib bug: just as `claimRevenue` silently used `ownerSplit = 0` for an unregistered contract (sending all funds to treasury), `validatePerasCert` silently accepts any certificate with an arbitrary `pcCertBoostedBlock`, allowing an attacker to inject a weight boost for any block of their choosing into the `PerasWeightSnapshot` and thereby manipulate Peras-weighted chain selection.

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker who can submit a `PerasCert` (e.g., via the Peras certificate submission mini-protocol or any path that calls `validatePerasCert` and feeds the result into the `PerasCertDB`) can:

1. Craft a certificate with `pcCertBoostedBlock` pointing to a block on a minority or adversarial fork.
2. The stub returns `Right` unconditionally; the certificate is accepted as valid.
3. The `PerasWeightSnapshot` is updated: the adversarial fork's tip block now carries `perasWeight params` additional weight.
4. `preferAnchoredCandidate` computes `wsvTotalWeight` for both chains; the adversarial fork now appears heavier.
5. The node switches to the adversarial fork, violating chain selection safety.

This matches the **High** impact category: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The `validatePerasCert` stub is the **only** `BlockSupportsPeras` instance in the repository (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`). There is no overriding Cardano-specific instance. Any code path that calls `validatePerasCert` — including certificate ingestion from the `PerasCertDB` API — will unconditionally succeed.

Note: `getPerasCertInBlock _ = Nothing` (also a stub) means certificates are not currently extracted from received blocks, which limits one ingestion path. However, the `PerasCertDB` `addPerasCert` API is a separate, direct ingestion path. If any network-facing handler (e.g., a Peras certificate submission mini-protocol) calls `validatePerasCert` before inserting into the DB, the bypass is fully reachable by an unprivileged peer on a private testnet or production network once Peras is enabled.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:

1. Verifies the certificate's aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the known committee keys for that round.
2. Checks that `pcCertBoostedBlock` is a known block point (present in VolatileDB or ImmutableDB).
3. Checks that `pcCertRound` falls within the valid Peras round window relative to the current slot.
4. Returns `Left (PerasValidationErr ...)` with a descriptive error for any failure, rather than silently succeeding.

Until a real implementation exists, any network-facing handler that calls `validatePerasCert` should be gated behind a feature flag that is disabled by default, preventing untrusted certificates from reaching the `PerasWeightSnapshot`.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
