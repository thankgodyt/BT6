### Title
Batch-Reject-All in `processCerts`/`processVotes` Lets Any Peer Suppress Valid Peras Certificates and Votes, Corrupting Chain Weight - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` and `processVotes` implement a batch-reject-all policy: if **any** item in a received batch fails validation, the **entire batch** is thrown away via an exception, including all valid items. An unprivileged peer can exploit this by sending a batch that mixes one crafted-invalid certificate or vote with otherwise-valid ones. The valid items are permanently dropped for that connection, corrupting the node's `PerasWeightSnapshot`. Because Peras chain selection compares `wsvTotalWeight = BlockNo + WeightBoost`, a node missing valid certificates may prefer a non-canonical, less-boosted chain over the correct one.

---

### Finding Description

`processCerts` in `PerasCert.hs` receives a list of inbound Peras certificates from a peer, filters out already-known ones, then validates the remainder:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [1](#0-0) 

`partitionEithers` correctly separates valid from invalid items into `(errs, validatedCerts)`, but the second branch discards `validatedCerts` entirely and throws. The valid certificates are never passed to `addCert`.

The identical pattern exists in `processVotes`:

```haskell
case partitionEithers validationResults of
  ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, _)            -> throw (PerasVoteValidationError errs)
``` [2](#0-1) 

The production wiring is in `NodeToNode.hs`, where `makePerasCertPoolWriterFromChainDB` and `makePerasVotePoolWriterFromChainDB` are passed as the `ObjectPoolWriter` to `objectDiffusionInbound` for every peer connection: [3](#0-2) 

`objectDiffusionInbound` calls `opwAddObjects objectsToAck` directly on the collected batch: [4](#0-3) 

The thrown `PerasCertInboundException` / `PerasVoteInboundException` propagates out of `opwAddObjects`, disconnecting the peer. The valid items in the batch are never stored.

The code comment acknowledges the design choice but does not address the security consequence: [5](#0-4) 

---

### Impact Explanation

Peras certificates boost chain weight. `addPerasCertAsync` feeds valid certificates into `chainSelSync`, which updates the `PerasWeightSnapshot` and may trigger a fork switch: [6](#0-5) 

Chain selection compares `wsvTotalWeight = BlockNo + WeightBoost`: [7](#0-6) 

If valid certificates are suppressed, the node's `PerasWeightSnapshot` is incomplete. A candidate chain that should be preferred (because it contains a boosted block) may be rejected in favour of a shorter or less-boosted chain. This is a concrete chain-selection divergence from the correct Peras outcome, matching the **High** impact class: *a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*.

For votes: suppressing valid votes prevents quorum from being reached, blocking certificate formation entirely for that round, with the same downstream chain-weight effect.

---

### Likelihood Explanation

The attack requires only a standard node-to-node connection. The adversary sends a batch via the Peras cert/vote diffusion miniprotocol containing at least one crafted-invalid item alongside valid ones. No stake, keys, or operator access is needed. The batch size is bounded by `perasCertDiffusionMaxObjectsUnacknowledged` / `perasVoteDiffusionMaxObjectsUnacknowledged`, so the adversary can always fit one invalid item alongside legitimate ones. The node disconnects after the throw, but the valid items are already lost for that connection; if the adversary is the only peer advertising those cert/vote IDs (or can consistently poison every batch), the node never processes them.

---

### Recommendation

Replace the all-or-nothing throw with a split policy: add the valid items to the database and only disconnect (or log) for the invalid ones. The `partitionEithers` call already produces the correct split; the fix is to use `validatedCerts`/`validatedVotes` unconditionally and treat `errs` as a reason to disconnect without discarding the valid subset:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, validatedCerts) -> do
    -- Still add the valid certs
    mapM_ (addCert . WithArrivalTime now) validatedCerts
    -- Then signal the protocol layer to disconnect from this peer
    throw (PerasCertValidationError errs)
```

The same change applies symmetrically to `processVotes`.

---

### Proof of Concept

1. Adversary peer connects to an honest node via the node-to-node Peras cert diffusion miniprotocol.
2. Adversary announces two certificate IDs: `round_valid` (a legitimately-formed cert for a boosted block on the canonical chain) and `round_invalid` (a cert with a forged/malformed signature or out-of-range round number).
3. The honest node requests both; the adversary delivers both in the same `CollectObjects` batch.
4. `objectDiffusionInbound` calls `opwAddObjects [cert_valid, cert_invalid]`.
5. `processCerts` runs `partitionEithers [Right cert_valid, Left err]`, enters the `(errs, _)` branch, and throws `PerasCertValidationError [err]`.
6. `cert_valid` is never passed to `addCert` / `addPerasCertAsync`.
7. The node's `PerasWeightSnapshot` does not include the boost for the block certified by `cert_valid`.
8. In subsequent chain selection, `wsvTotalWeight` for the canonical chain is underestimated; the node may prefer a competing, unboosted chain, diverging from the correct Peras chain-selection outcome.
