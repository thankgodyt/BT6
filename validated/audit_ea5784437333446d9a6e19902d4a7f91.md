### Title
Missing Proof-of-Possession Enforcement Enables Rogue-Key Attack on BLS Aggregate Certificate Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/EveryoneVotes.hs`)

---

### Summary

`implVerifyCert` aggregates voter BLS public keys via `aggregateVoteVerificationKeys` → `BLS.aggregatePublicKeys` without ever verifying proof-of-possession (PoP) for any key. The function `BLS.aggregatePublicKeys` explicitly documents this as a caller precondition, but `verifyProofOfPossession` is never called anywhere in the codebase outside its own definition file. An attacker who can register a pool with a crafted rogue BLS key can cancel out a target voter's key in the aggregate, then produce a valid aggregate signature alone — making a certificate appear to carry multiple voters' signatures when only the attacker signed.

---

### Finding Description

`BLS.aggregatePublicKeys` carries an explicit documented precondition:

> "PRECONDITION: this assumes that proofs of possession have already been verified for all keys in advance." [1](#0-0) 

The function `verifyProofOfPossession` is defined in `BLS.hs` but a codebase-wide grep confirms it is **never called anywhere outside that file**. Neither `implVerifyCert` in `EveryoneVotes.hs`, nor the equivalent in `WFALS.hs`, nor the `PerasBLSCrypto` instance performs any PoP check before aggregating keys.

The call chain in `implVerifyCert`:

```
implVerifyCert
  → aggregateVoteVerificationKeys (Proxy @crypto) voteVerificationKeys
      → BLS.aggregatePublicKeys @SIGN pks          -- no PoP check
  → verifyAggregateVoteSignature ... aggVerificationKey ...
``` [2](#0-1) 

The `PerasBLSCrypto` instance delegates directly:

```haskell
aggregateVoteVerificationKeys _ pks = do
  aggPk <- BLS.aggregatePublicKeys @SIGN pks
  pure (PerasBLSCryptoAggregateVoteVerificationKey aggPk)
``` [3](#0-2) 

The same gap exists in `WFALS.implVerifyCert`: [4](#0-3)

### Impact Explanation

**Classic BLS rogue-key attack** (no knowledge of victim's private key required):

1. Honest voter H has registered public key `PK_H = sk_H * G2`.
2. Attacker A generates a real key pair `(sk_A, PK_A_real)` where `PK_A_real = sk_A * G2`.
3. Attacker registers their pool with the crafted key `PK_A = PK_A_real − PK_H` (a valid G2 point, computable from the public `PK_H`).
4. Both pools are in the committee (both have positive stake).
5. Attacker crafts a certificate claiming both H and A voted.
6. `implVerifyCert` aggregates: `PK_H + PK_A = PK_H + (sk_A * G2 − PK_H) = sk_A * G2 = PK_A_real`.
7. Attacker signs with `sk_A`: `sig_A = sk_A * H(msg)`.
8. Verification: `e(sig_A, G2) = e(H(msg), sk_A * G2) = e(H(msg), PK_H + PK_A)` — **passes**.

The certificate is accepted as if both H and A signed, but only A signed. This violates the invariant that every declared voter in the certificate must have contributed a valid individual signature, enabling **unauthorized certificate acceptance with a forged aggregate signature**.

---

### Likelihood Explanation

The preconditions are:
- The attacker must register a pool with positive stake and a crafted BLS public key. Pool registration is a standard, supported on-chain operation.
- The attacker must know the target voter's BLS public key, which is public by design (it is stored in the ledger state and used to populate `ExtWFAStakeDistr`).
- No knowledge of any private key other than the attacker's own is required.

The mathematical construction is straightforward and well-documented in the BLS literature (Boneh et al., "Compact Multi-Signatures for Smaller Blockchains"). The only barrier is that Peras BLS key registration must be live on the target network.

---

### Recommendation

1. **Enforce PoP at key registration time** in the ledger: when a pool registers a BLS voting key, require and verify a `ProofOfPossession` over the pool's key hash using `BLS.verifyProofOfPossession`. The infrastructure for this already exists. [5](#0-4) 

2. **Alternatively, enforce PoP at committee construction time** in `mkExtWFAStakeDistr` or `mkEveryoneVotesVotingCommittee`/`mkWFALSVotingCommittee` by requiring that each `(PoolId, PublicKey)` pair is accompanied by a verified `ProofOfPossession`.

3. **Add a subgroup/infinity check** in `aggregatePublicKeys` to reject the identity point as an aggregate result (defense-in-depth), mirroring the check already present in `linearizeAndVerifyVRFs`. [6](#0-5) 

---

### Proof of Concept

Using the `PerasBLSCrypto` or `TestCrypto` instance on a local testnet or in a unit test:

```haskell
-- Setup: honest voter H with (sk_H, pk_H), attacker A with (sk_A, pk_A_real)
-- Attacker computes rogue key: pk_A_rogue = pk_A_real - pk_H
--   (i.e., uncheckedAggregateVerKeysDSIGN [pk_A_real, negateG2 pk_H])

-- Register two pools: pool_H with pk_H, pool_A with pk_A_rogue
-- Both pools have positive stake => both are in the committee

-- Attacker forges a certificate claiming both pool_H and pool_A voted:
--   voters = {seat_H, seat_A}
--   aggSig = signVote sk_A electionId candidate   -- only attacker signs

-- implVerifyCert aggregates: pk_H + pk_A_rogue = pk_A_real
-- verifyAggregateVoteSignature pk_A_real electionId candidate aggSig
--   => Right ()   -- PASSES, despite pool_H never signing

assert (isRight (verifyCert committee craftedCert))
-- This assertion holds, demonstrating unauthorized certificate acceptance.
```

The test should be run on unmodified code against a local private testnet or io-sim environment with two registered pools, one of which holds the rogue key.
