Audit Report

## Title
`fin_transfer_send_tokens_callback` Ignores Token Delivery Failure, Permanently Freezing Inbound Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When an inbound transfer (foreign chain → NEAR) is finalized via `fin_transfer`, the transfer ID is irrevocably committed to `finalised_transfers` in `process_fin_transfer_to_near` before the actual token delivery (`ft_transfer`, `mint`, or wNEAR unwrap) executes. The callback `fin_transfer_send_tokens_callback` delegates failure detection entirely to `is_refund_required`, which only inspects the promise result when `is_ft_transfer_call = true`. For all plain token deliveries (empty `msg`), `is_refund_required` returns `false` unconditionally — it never reads the promise result. If token delivery fails, the transfer is permanently stuck in `finalised_transfers` with no recovery path, freezing the user's funds.

## Finding Description

**Root cause — `add_fin_transfer` commits before token delivery:**

In `process_fin_transfer_to_near`, `add_fin_transfer` is called at line 1875, committing the transfer ID to `finalised_transfers` in the same receipt as `fin_transfer_callback`. The `send_tokens` call at line 1957 is a chained cross-contract call that executes in a subsequent receipt. Because NEAR's receipt model commits state changes atomically per receipt, `add_fin_transfer` is irrevocably committed regardless of what happens in `send_tokens`.

**`is_ft_transfer_call` is `false` for all plain deliveries:**

At line 1973, `!msg.is_empty()` is passed as `is_ft_transfer_call`. For the common case of a plain transfer (empty `msg`), this is `false`. This covers:
- Deployed tokens: `mint(recipient, amount, None)` (lines 2094–2101)
- Native tokens: `ft_transfer(recipient, amount, None)` (lines 2102–2106)
- wNEAR: `near_withdraw` → `near_withdraw_callback` (lines 2071–2081)

**`is_refund_required` never checks the promise result for `is_ft_transfer_call = false`:**

```rust
// lines 1800–1803
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

The function returns `false` without calling `env::promise_result_checked`. It cannot distinguish a successful `ft_transfer` from a failed one.

**On failure, the success path executes:**

Because `is_refund_required` returns `false`, the `else` branch at lines 1719–1746 runs unconditionally: fees are minted/transferred to the relayer, and `FinTransferEvent` is emitted. `remove_fin_transfer` is never called. The transfer ID remains in `finalised_transfers` permanently, and any retry of `fin_transfer` with the same proof panics with `TransferAlreadyFinalised`.

**wNEAR sub-path:** `near_withdraw_callback` panics on failure (line 1050), but `add_fin_transfer` was already committed in a prior receipt. The panic propagates as a `Failed` promise result to `fin_transfer_send_tokens_callback`, which still takes the success path because `is_refund_required(false)` returns `false`.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing of bridged funds**.

- **Native tokens (locked in bridge on outbound):** `unlock_tokens_if_needed` decreases `locked_tokens` accounting at line 1881–1885, but the tokens remain in the bridge contract because `ft_transfer` failed. The transfer is in `finalised_transfers` and cannot be re-submitted. Tokens are permanently frozen in the bridge contract with no recovery mechanism.
- **Deployed/bridged tokens:** `mint` fails, no tokens are created for the user, yet the transfer is marked finalized. The user's cross-chain value is destroyed with no recourse.

## Likelihood Explanation

Any inbound transfer to a NEAR recipient is affected. No special privilege is required. Realistic failure triggers include:

1. **Token contract paused:** Many NEP-141 tokens implement a pause mechanism. If the token contract is paused between the storage-check receipt and the `ft_transfer` receipt, delivery fails silently.
2. **Recipient unregisters storage:** The storage check (`check_storage_balance_result` at lines 1905–1913) and the `ft_transfer` execute in separate receipts. A recipient (or a griefing third party controlling the recipient account) can call `storage_unregister` in the window between the two receipts, causing `ft_transfer` to panic.
3. **Token contract bug or upgrade:** Any panic in the token contract during `ft_transfer` or `mint` triggers the same silent-success path.

## Recommendation

1. In `is_refund_required`, add a check for the promise result when `is_ft_transfer_call = false`: use `env::promise_result_checked(0, ...)` and treat `Err(_)` as a failure requiring refund/revert.
2. On detected failure, call `remove_fin_transfer`, revert lock actions via `revert_lock_actions`, and emit `FailedFinTransferEvent` — mirroring the existing refund path at lines 1702–1718.
3. Alternatively, move `add_fin_transfer` into `fin_transfer_send_tokens_callback` so it is only committed after confirmed delivery.

## Proof of Concept

1. A user bridges a native NEAR token from Ethereum back to NEAR (inbound transfer).
2. The token contract owner pauses the token contract.
3. A relayer calls `fin_transfer` with a valid proof.
4. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` at line 1875 commits the transfer ID to `finalised_transfers`.
   - `unlock_tokens_if_needed` at line 1881 decreases `locked_tokens` accounting.
   - `send_tokens` at line 1957 dispatches `ft_transfer` on the paused token contract.
5. `ft_transfer` panics (contract is paused). The promise result is `Failed`.
6. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false` (line 1973: `!msg.is_empty()` where `msg` is empty).
7. `is_refund_required(false)` returns `false` at lines 1800–1803 without inspecting the promise result.
8. The `else` branch at lines 1719–1746 executes: fee is minted to the relayer, `FinTransferEvent` is emitted.
9. The transfer ID is permanently in `finalised_transfers`. Any retry of `fin_transfer` with the same proof panics with `TransferAlreadyFinalised`.
10. The user's tokens are frozen in the bridge contract with no recovery mechanism.
