### Title
Dual Ledger-View Computation Paths (`ledgerViewForecastAt` vs `protocolLedgerView . applyChainTick`) with Unenforced Agreement Invariant — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Ledger/SupportsProtocol.hs`)

---

### Summary

`LedgerSupportsProtocol` exposes two separate code paths that both compute the protocol ledger view for a future slot: `ledgerViewForecastAt` (used by the ChainSync client for header validation) and `protocolLedgerView . applyChainTick` (used by ChainDB/ChainSel during block application). The codebase documents a required agreement invariant between them but enforces it only through a dead-code lemma function (`_lemma_ledgerViewForecastAt_applyChainTick`) that is never called in production. The two paths use structurally different implementations — TICKF vs TICK for Shelley/TPraos, and an additional coerce-then-translate indirection for Praos — creating a latent dual-implementation discrepancy directly analogous to the `virtualPrice()` / `_updatePrices()` split in the IdleCDO report.

---

### Finding Description

The `LedgerSupportsProtocol` typeclass defines two methods that must agree within the forecast range:

- `ledgerViewForecastAt`: used by the ChainSync client to obtain a `LedgerView` for validating incoming peer headers before any block is downloaded.
- `protocolLedgerView`: called on the result of `applyChainTick` during block application inside `ExtLedgerState.applyChainTickLedgerResult`.

The required invariant is stated in the source:

> "We expect the two functions to produce the same view whenever the SlotNo is in range." [1](#0-0) 

The only enforcement mechanism is `_lemma_ledgerViewForecastAt_applyChainTick`, a function prefixed with `_` that is never invoked anywhere in production code: [2](#0-1) 

The grep confirms it appears only in `SupportsProtocol.hs` itself — zero call sites.

**Shelley/TPraos divergence**: `ledgerViewForecastAt` for `ShelleyBlock (TPraos crypto) era` uses `SL.futureLedgerView` (the ledger's TICKF rule) for future slots, while `protocolLedgerView` calls `SL.currentLedgerView . tickedShelleyLedgerState` (the result of the full TICK rule): [3](#0-2) 

**Praos divergence**: `ledgerViewForecastAt` for `ShelleyBlock (Praos crypto) era` coerces the ledger state to a TPraos state, delegates to the TPraos forecast, and then applies `translateLedgerView`. `protocolLedgerView` for the same instance directly extracts `nesPd`, `ppMaxBBSizeL`, `ppMaxBHSizeL`, and `ppProtocolVersionL` from the ticked `NewEpochState`: [4](#0-3) 

These are genuinely separate implementations. The `hard_won_wisdom.md` document explicitly acknowledges the fragility of the TICKF/TICK relationship and the fact that Consensus must perform its own range-checking before invoking ledger code, because the ledger's TICKF rule cannot itself signal failure cleanly. [5](#0-4) 

The block-application path that uses `protocolLedgerView` is in `ExtLedgerState.applyChainTickLedgerResult`: [6](#0-5) 

And `validateHeader` (called during block application) uses this ticked ledger view, while the ChainSync client uses the forecast: [7](#0-6)

### Impact Explanation

The `LedgerView` for Praos/TPraos contains the pool stake distribution (`lvPoolDistr`/`nesPd`) and protocol parameters including `lvMaxHeaderSize` and `lvMaxBodySize`. These are used in `updateChainDepState` to verify VRF proofs and check that the block producer was an eligible slot leader.

If `ledgerViewForecastAt` and `protocolLedgerView . applyChainTick` diverge:

1. **More-permissive forecast**: A header from a node that is not a valid slot leader (according to the ticked view) passes ChainSync validation. The corresponding block is downloaded. During block application, `validateHeader` is called again with the ticked ledger view and rejects it — the block is marked invalid. The node cannot adopt the chain. If the adversary can reliably trigger this, it can prevent the node from ever adopting a valid longer chain, causing it to remain on a shorter or less-secure fork.

2. **More-restrictive forecast**: A header from a legitimate slot leader is rejected during ChainSync. The node disconnects from the honest peer. The node cannot build a candidate fragment for the honest chain and may prefer an adversarial chain that does not trigger the discrepancy. This is a chain-selection error that lets an unprivileged peer cause an honest node to prefer a non-canonical chain.

The `reapplyBlockLedgerResult` path uses `revalidateHeader` → `reupdateChainDepState`, which skips all cryptographic checks: [8](#0-7) [9](#0-8) 

If a block was previously accepted via the more-permissive forecast path and stored, a subsequent reapplication via `revalidateHeader` would not re-check leader eligibility, meaning the wrong `ChainDepState` (nonces, OC counters) would be durably committed.

**Impact class**: High — ledger-view/forecast bug that lets an unprivileged peer (by serving crafted headers that exploit the discrepancy) make an honest node prefer a non-canonical or less-secure chain, or permanently corrupt the `ChainDepState` via the reapplication path.

---

### Likelihood Explanation

The discrepancy requires the TICKF rule and the TICK rule to produce different ledger views for the same slot. The `hard_won_wisdom.md` document explicitly discusses the complexity of this relationship and the fact that the Consensus layer must perform its own range-checking because the ledger's TICKF rule cannot signal failure cleanly. The Praos instance adds an additional coerce-and-translate indirection not present in `protocolLedgerView`. The invariant is documented but unenforced. Any future change to the Shelley ledger's TICKF rule, the stake-distribution snapshot schedule, or the protocol-parameter extraction logic could silently break the agreement without any compile-time or runtime check catching it. An adversary who discovers a slot where the two paths diverge (e.g., at an epoch boundary where the stake snapshot transitions) can craft headers targeting that slot.

---

### Recommendation

1. **Unify the implementation**: Implement a single function that computes the ledger view for a given slot, and use it in both `ledgerViewForecastAt` and `protocolLedgerView`. This is the direct analog of the IdleCDO recommendation to implement a single method and use it everywhere.

2. **Enforce the invariant at runtime**: Call `_lemma_ledgerViewForecastAt_applyChainTick` (or an equivalent assertion) in the ChainSync client and in ChainSel whenever a ledger view is obtained, at least in debug/test builds.

3. **Add property-based tests**: Add a QuickCheck property that, for all valid ledger states and all slots within the forecast range, `forecastFor (ledgerViewForecastAt cfg st) slot == Right (protocolLedgerView cfg (applyChainTick cfg slot st))`. This should cover all era instances including Praos.

4. **Remove the coerce-and-translate indirection in the Praos instance**: The Praos `ledgerViewForecastAt` coerces to a TPraos state and then translates, while `protocolLedgerView` extracts directly. These should use the same extraction logic.

---

### Proof of Concept

**Scenario**: Epoch boundary slot where the stake snapshot transitions.

1. Node has a Shelley/Praos ledger state `st` at tip slot `at`, near an epoch boundary.
2. Adversary peer sends a header for slot `for` where `at < for < maxFor` (within forecast range) but `for` crosses an epoch boundary.
3. ChainSync client calls `forecastFor (ledgerViewForecastAt cfg st) for` → uses `SL.futureLedgerView` (TICKF rule) → returns stake distribution snapshot `S_TICKF`.
4. `updateChainDepState` validates the header's VRF proof against `S_TICKF`. Suppose the adversary's node is eligible under `S_TICKF` but not under the TICK result.
5. Header passes ChainSync validation; block is downloaded.
6. ChainSel calls `applyChainTick cfg for st` → uses full TICK rule → `protocolLedgerView` returns stake distribution `S_TICK ≠ S_TICKF`.
7. `validateHeader` in `applyHelper` calls `updateChainDepState` with `S_TICK` → VRF proof fails → block marked invalid.
8. Node cannot adopt the adversary's chain. If the adversary can repeat this for all honest-chain headers (by exploiting the discrepancy in the other direction), the node is stuck on a shorter chain.

The dead-code lemma that would catch this at step 3: [10](#0-9) 

is never called, so the discrepancy propagates silently.

_lemma_ledgerViewForecastAt_applyChainTick ::
  ( LedgerSupportsProtocol blk
  , Eq (LedgerView (BlockProtocol blk))
  ) =>
  LedgerConfig blk ->
  LedgerState blk mk ->
  Forecast (LedgerView (BlockProtocol blk)) ->
  SlotNo ->
  Either String ()
_lemma_ledgerViewForecastAt_applyChainTick cfg st forecast for
  | NotOrigin for >= ledgerTipSlot st
  , let lhs = forecastFor forecast for
        rhs =
          protocolLedgerView cfg
            . applyChainTick OmitLedgerEvents cfg for
            . forgetLedgerTables
            $ st

      Left $
        unlines

          , show lhs'
          , " /= "
          , show rhs
          ]

**File:** docs/website/contents/references/miscellaneous/hard_won_wisdom.md (L71-87)
```markdown
When we returned to this code for the first time in a while, we thought it was odd that the code both handles an `Either` in the return type of `SL.futureLedgerView` and also does its own `for < maxFor` check; can't the Ledger code instead return `Left` whenever `for >= maxFor`?

We looked at the upstream code to investigate; how easily could we arrange that?
The answer is: it could be done, but the core architecture of the State Transition System code in the core Ledger library does not currently naturally allow for that (at least in our subjective opinion of _naturally_ and specifically for the `TICKF` example).
At the moment, any rule that can _fail_ must also provide a "default" value for the rest of the rule to use (see the `Predicate` constructor of the `Clause` GADT, specifically its argument of type `a`).
For the Ledger's code implementing the `TICKF` rule to observe the `Either` layer of the `EpochInfo` would require that the rule has some way to continue when the `EpochInfo` query (used to determine if the requested forecast crosses an epoch transition) fails.

It is not obvious how to do that when `EpochInfo` returns `Left`.
While it may be possible to work something out, such as perhaps the `TICKF` rule emits a new `PredicateFailure` and simply leaves the `NewEpochState` unchanged, no idea seems natural to us.
They all involve creating an incorrect `LedgerView` and then only throwing it away at the last moment.
And notably, the rest of the rule could emit additional errors, all of which would be presumably spurious given that we already know the very first check (ie querying the `EpochInfo`) failed.

So instead, for now at least, the Consensus code must do its own checking before invoking Ledger code that relies on the `EpochInfo` never failing.

- By design, any invocation of Ledger code that causes the `EpochInfo` to return `Left` would be a _bug_, with no obvious way to recover.
  Thus this isn't a particularly burdensome requirement; not much extra code (such as `for < maxFor` above).
  And also thus: throwing these exceptions from pure code is reasonable choice.
```

    validateEnvelope
      cfg
      ledgerView

      hdr

      updateChainDepState
        (configConsensus cfg)
