### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Always Returning `Right` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types unconditionally accepts every inbound Peras certificate without performing any validation. This is the direct analog of the "no expiration deadline" class: just as `deadline: block.timestamp` imposes no real temporal constraint on a swap, `validatePerasCert` imposes no real constraint on a certificate, allowing any peer-supplied certificate to be stored and to influence chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve a certificate before it is stored and acted upon. The production-wide degenerate instance (used for all block types until HFC plumbing is complete) implements this gate as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production inbound-certificate processing path in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

The `processCerts` function calls `validateCert` on each inbound certificate and, because the stub always returns `Right`, every certificate passes and is stored via `addCert`: [4](#0-3) 

After storage, `makePerasCertPoolWriterFromChainDB` calls `ChainDB.addPerasCertAsync`, which triggers `chainSelSync`. Inside `chainSelSync`, the only staleness guard is a slot-based check against the immutable tip:

```haskell
when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
  idExitEarly PerasCertIgnoredTooOld
``` [5](#0-4) 

There is no check on:
- The certificate's round number (could be from any round, past or future)
- The certificate's cryptographic validity (no quorum/signature verification)
- The certificate's expiry relative to the current Peras round (`currRoundNo <= _A + certRound`)

The expiry predicate `latestCertSeenIsNotExpired` exists only in the block-forging inclusion rules (`Cert/Inclusion.hs`), not in the inbound validation path: [6](#0-5) 

---

### Impact Explanation

A certificate accepted by `chainSelSync` that boosts a block on a candidate chain adds `perasWeight` (currently 15) to that chain's weight during chain selection. An adversary who sends a crafted certificate boosting a block on a weaker candidate chain can cause an honest node to prefer that non-canonical chain over the canonical one, constituting a chain-selection safety failure.

This maps to the **High** impact category: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Any peer connected via the object-diffusion mini-protocol can send arbitrary `PerasCert` objects. No stake, key material, or privileged access is required. The attacker only needs to craft a `PerasCert` with a `pcCertBoostedBlock` pointing to a block in the volatile DB of the target node. The degenerate instance is the only `BlockSupportsPeras` instance in scope for all current block types. [7](#0-6) 

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks at minimum:

1. **Round expiry**: reject certificates whose round number satisfies `currRoundNo > _A + certRound` (mirroring `latestCertSeenIsNotExpired`).
2. **Quorum/signature**: verify the certificate carries a valid quorum of committee signatures over the correct boosted block and round.
3. **Round number bounds**: reject certificates from rounds that are in the future relative to the current slot.

Until the HFC plumbing is complete, the inbound path should refuse all certificates rather than accept all of them, i.e., the stub should return `Left PerasValidationErr` rather than `Right`.

---

### Proof of Concept

1. Connect to a target node as a peer via the object-diffusion mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of a block in the node's volatile DB on a weaker candidate chain>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is called.
5. `chainSelSync` runs; the slot-age guard passes (the boosted block is recent enough).
6. Chain selection is triggered for the boosted block; the candidate chain gains `perasWeight = 15` extra weight.
7. If the candidate chain's weight now exceeds the current chain's weight, the node switches to the non-canonical chain.
