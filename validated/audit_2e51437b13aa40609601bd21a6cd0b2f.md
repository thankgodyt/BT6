### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates, Enabling Unauthorized Chain Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance used for all block types in production implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, regardless of content. Because the production node-to-node handler for inbound Peras certificates calls this stub directly, any unprivileged peer can inject a crafted `PerasCert` that boosts an arbitrary block on a candidate fork, causing the honest node to switch away from the canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate's BLS aggregate signature, committee membership, quorum threshold, and round number before the certificate is allowed to influence chain selection. The only concrete instance in the codebase is a degenerate placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This instance applies universally to every block type (`instance StandardHash blk => BlockSupportsPeras blk`). No cryptographic check is performed; every certificate is unconditionally promoted to `ValidatedPerasCert` with the full configured boost weight. [1](#0-0) 

**Production inbound path — `makePerasCertPoolWriterFromChainDB`:**

The production node-to-node handler for the `PerasCertDiffusion` mini-protocol wires this stub directly into the inbound certificate writer:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator on every certificate received from a peer; because it always returns `Right`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

**Chain selection side-effect — `chainSelSync`:**

When a certificate is added, `chainSelSync` checks whether the boosted block is present in the VolatileDB on a candidate fork. If it is, chain selection is immediately re-run for that block with the certificate's weight boost applied:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Diffusion handler wiring:**

The `hPerasCertDiffusionClient` handler in the production node-to-node stack passes `makePerasCertPoolWriterFromChainDB` directly, completing the end-to-end path from peer message to chain selection: [5](#0-4)

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Serve the honest node a block on an adversarial fork (which lands in the VolatileDB after passing ordinary header validation).
2. Send a crafted `PerasCert` via the `PerasCertDiffusion` mini-protocol that claims to boost that adversarial block.
3. Because `validatePerasCert` always returns `Right`, the certificate is accepted without any BLS signature, committee membership, or quorum check.
4. `chainSelSync` re-runs chain selection for the boosted block; the fraudulent weight boost can make the adversarial fork heavier than the honest chain.
5. The node switches to the adversarial fork, diverging from the canonical chain.

This is a **bypass of Peras certificate validation** that enables unauthorized chain selection manipulation — an honest node can be made to prefer a non-canonical chain by a single unprivileged peer, violating the core consensus safety property.

---

### Likelihood Explanation

- Peras is currently disabled by default, but the code is present in production files and the vulnerability activates the moment Peras is enabled via configuration.
- The attack requires only a standard peer connection and the ability to send a well-formed (but cryptographically fraudulent) `PerasCert` message — no stake, no keys, no privileged access.
- The adversary must have a block already in the target node's VolatileDB (easily achieved by serving any valid-header block on a fork), which is a routine condition during normal operation.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that checks:
- The aggregate BLS signature over `(roundNo, boostedBlockHash)` against the claimed committee members' public keys.
- That the signers are legitimate committee members for the claimed round (via the VRF-based committee selection).
- That the aggregate stake of the signers meets the quorum threshold.
- That the round number is within the valid window relative to the current chain tip.

Until this is implemented, the `PerasCertDiffusion` mini-protocol should not be enabled in any deployment where Peras is active.

---

### Proof of Concept

**Setup:** Node A (honest) is connected to Node B (adversary). Peras is enabled.

1. Node B serves Node A a block `X` on a fork `F` that diverges from the canonical chain `C`. Block `X` passes header validation (valid KES/VRF) and is stored in Node A's VolatileDB. Fork `F` is currently lighter than `C` by weight `W`.

2. Node B sends Node A a `PerasCert` via the `PerasCertDiffusion` protocol:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = point(X) }
   ```
   No valid BLS signature is included.

3. Node A's `processCerts` calls `validatePerasCert mkPerasParams cert`. The stub returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.

4. The certificate is forwarded to `ChainDB.addPerasCertAsync`. `chainSelSync` finds block `X` in the VolatileDB and re-runs chain selection. If `perasWeight params > W`, fork `F` is now heavier than `C`.

5. Node A switches to fork `F`, diverging from the canonical chain. Node A is now on a non-canonical chain controlled by the adversary. [6](#0-5) [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
