### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic checks. This function is wired directly into the production inbound ObjectDiffusion mini-protocol handler for Peras certificates. An unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and boosted block point; the certificate will pass "validation," be stored in the `PerasCertDB`, and trigger chain selection with an attacker-controlled weight boost applied to an arbitrary block.

### Finding Description

**Root cause — stub validator that always succeeds:**

The default `BlockSupportsPeras` instance, which is the only implementation in the codebase, defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This unconditionally wraps any incoming `PerasCert` in `ValidatedPerasCert` and assigns it the full Peras weight boost, regardless of the certificate's content, signature, committee membership, or round validity.

**Inbound path — production wiring:**

`makePerasCertPoolWriterFromChainDB` (the production writer used by the node) passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and only rejects on `Left`. Since the stub never returns `Left`, every certificate passes: [3](#0-2) 

**End-to-end exploit path:**

1. Attacker connects as a peer via the node-to-node ObjectDiffusion mini-protocol (`objectDiffusionInbound`).
2. Attacker sends a crafted `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` (any block point the attacker wants to boost).
3. `objectDiffusionInbound` collects the cert and calls `opwAddObjects` → `processCerts`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
5. The cert is timestamped and stored in `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. Chain selection reads the cert's weight boost (`vpcCertBoost = perasWeight params`) and applies it to the attacker-specified block, potentially causing the node to prefer a non-canonical or adversarially chosen chain. [4](#0-3) 

### Impact Explanation

**Impact: High — Bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

The Peras protocol assigns weight boosts to blocks via certificates to strengthen chain selection. By bypassing certificate validation entirely, an unprivileged peer can inject certificates for arbitrary blocks and rounds. The node will apply the weight boost from these forged certificates during chain selection, potentially causing it to prefer a non-canonical chain over the honest chain. This directly matches the allowed impact scope: "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."

### Likelihood Explanation

**Likelihood: 2 (Low-Medium)**

The Peras protocol and its ObjectDiffusion mini-protocol are under active development and not yet activated on Cardano mainnet. However, the code is in production files, the inbound handler is fully wired up, and the vulnerability is reachable on any private testnet or staging environment where Peras is enabled. No privileged access is required — any peer that can establish a node-to-node connection can exploit this.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that checks:
- The certificate's aggregate BLS signature against the claimed committee members' public keys.
- That the claimed voters are legitimate committee members for the given round (committee eligibility via VRF proofs).
- That the boosted block point is a known, valid block on a plausible chain.
- That the round number is within the acceptable window (not stale or far-future).

Until real validation is implemented, inbound Peras certificates from untrusted peers should be rejected at the protocol level, or the ObjectDiffusion handler for certificates should not be activated in production builds.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
