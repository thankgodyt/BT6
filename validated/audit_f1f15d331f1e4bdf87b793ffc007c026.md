### Title
Unchecked `burn` Promise Return in `safe_mint_callback` Leaves nBTC Supply Unbacked on Failure — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when `safe_mint` fails (recipient rejects the minted tokens), the bridge fires a `burn` cross-contract call using `.detach()` to destroy the already-minted nBTC. The result of this burn is never observed. If the burn fails for any reason, the UTXO is removed from `verified_deposit_utxo` while the minted nBTC tokens remain in the bridge's balance — creating an unbacked token supply and re-opening the UTXO for re-deposit.

---

### Finding Description

`safe_mint_callback` is the callback for the `safe_verify_deposit` flow (used by Omni Bridge integration). It calls `is_refund_required()` to determine whether `safe_mint` returned `U128(0)` — meaning the recipient either was not registered in the nBTC contract, or its `ft_on_transfer` returned the full amount (rejected the tokens). [1](#0-0) 

In the failure branch (`is_success == false`):

1. **The UTXO is removed from `verified_deposit_utxo`** (lines 439–441) — this is a committed state mutation.
2. **A `burn` call is fired with `.detach()`** (lines 443–451) — the result is never checked.
3. **A NEAR storage-deposit refund is fired with `.detach()`** (lines 453–455) — also unchecked.

The `burn` function in the nBTC contract calls `internal_withdraw` from the bridge's balance: [2](#0-1) 

If `internal_withdraw` panics (e.g., bridge nBTC balance is less than `mint_amount` due to a concurrent receipt reducing it, or if `GAS_FOR_BURN_CALL = 5 TGas` is insufficient for the nBTC contract's storage operations), the burn receipt fails silently. The bridge has no callback to detect this failure and no rollback path. [3](#0-2) 

The `safe_mint` flow mints tokens to the bridge's own balance first, then transfers them to the recipient via `ft_transfer_call`: [4](#0-3) 

When the recipient rejects the tokens, `ft_resolve_transfer` returns them to the bridge's balance. By the time `safe_mint_callback` runs, the bridge holds `mint_amount` nBTC. The burn is intended to destroy these tokens, but since it is detached, a failure leaves the bridge holding unbacked nBTC with no record of the inconsistency.

The UTXO guard that prevents double-deposit is `verified_deposit_utxo`: [5](#0-4) 

Because the failure branch removes the UTXO from this set before the burn executes, a subsequent `safe_verify_deposit` or `verify_deposit` call for the same UTXO passes the guard and mints a second batch of tokens against the same BTC UTXO.

---

### Impact Explanation

If the detached `burn` call fails:

- The bridge holds `mint_amount` nBTC tokens that are not backed by any BTC UTXO.
- The UTXO is no longer in `verified_deposit_utxo`, so it can be re-submitted for deposit.
- A second successful deposit mints another `mint_amount` nBTC, resulting in `2 × mint_amount` nBTC backed by only `1 × mint_amount` BTC — unauthorized minting above backed supply.
- Even without re-submission, the bridge's nBTC supply is permanently inflated above its BTC backing, violating the 1:1 peg invariant.
- There is no recovery mechanism: no callback, no `lost_found` entry, no operator alert.

This matches: **Medium — broken callback rollback, stuck bridge state requiring operator intervention**, with escalation to **Critical — unauthorized minting** if the UTXO is re-submitted.

---

### Likelihood Explanation

The failure branch is reachable by any user who sets `recipient_id` in `DepositMsg` to a contract whose `ft_on_transfer` returns the full amount (token rejection). This is a normal, unprivileged action — the user controls the recipient address in the deposit message. [6](#0-5) 

The burn failing is the lower-likelihood step. Realistic triggers include:

- **Gas exhaustion**: `safe_mint_callback` is allocated only `GAS_FOR_MINT_CALL_BACK = 10 TGas`. After the callback body executes, the two detached promises share the remainder. The burn is allocated `GAS_FOR_BURN_CALL = 5 TGas`. If the callback body consumes more than 5 TGas, the burn promise creation panics — but since the UTXO removal already occurred as a committed state change before the `.detach()` call, the inconsistency is locked in.
- **Concurrent receipt reducing bridge nBTC balance**: Between `safe_mint_callback` committing the UTXO removal and the burn receipt executing, another receipt (e.g., a withdrawal burn) could reduce the bridge's nBTC balance below `mint_amount`, causing `internal_withdraw` to panic. [7](#0-6) 

---

### Recommendation

Replace the detached `burn` call with a chained callback that checks the result and rolls back the UTXO removal on failure:

```rust
// Instead of:
ext_nbtc::ext(...).burn(...).detach();

// Use:
ext_nbtc::ext(...).burn(...)
    .then(
        Self::ext(env::current_account_id())

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn burn(
        &mut self,
        burn_account_id: AccountId,
        burn_amount: U128,
        relayer_account_id: AccountId,
        relayer_fee: U128,
    ) {
        self.assert_bridge();
        self.token
            .internal_withdraw(&self.bridge_id, burn_amount.into());
        if relayer_fee.0 > 0 {
            if self.token.accounts.get(&relayer_account_id).is_none() {
                self.token.internal_register_account(&relayer_account_id);

                &self.bridge_id,
                &relayer_account_id,
                relayer_fee.into(),
                None,
            );
        }
        near_contract_standards::fungible_token::events::FtBurn {
            owner_id: &burn_account_id,
            amount: burn_amount,
            memo: None,
        }
        .emit();
    }
