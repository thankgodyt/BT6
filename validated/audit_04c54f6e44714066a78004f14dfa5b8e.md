### Title
Blacklisted ERC-20 Recipient Permanently Freezes Bridged Funds in `finTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.finTransfer` uses a push-payment pattern to deliver native ERC-20 tokens directly to `payload.recipient`. If that address is blacklisted by the token contract (e.g., USDC/USDT), every call to `finTransfer` reverts. Because the recipient is cryptographically bound inside the MPC-signed payload, no alternative delivery path exists, and the source-chain tokens — already burned or locked on NEAR — can never be recovered.

---

### Finding Description

When a user bridges a native ERC-20 token (e.g., USDC) from NEAR to an EVM chain, the protocol executes the following irreversible sequence:

**Step 1 — NEAR side: tokens burned/locked.**
`init_transfer_internal` burns or locks the user's tokens and emits `InitTransferEvent`. There is no on-chain cancellation path after this point. [1](#0-0) 

**Step 2 — NEAR side: pending transfer removed, MPC signature emitted.**
`sign_transfer_callback` removes the pending transfer entry from `pending_transfers` and emits the MPC signature over a `TransferMessagePayload` that cryptographically binds `recipient`, `tokenAddress`, `amount`, and `destinationNonce` together. [2](#0-1) 

**Step 3 — EVM side: push-payment to recipient.**
A relayer calls `finTransfer`. The contract marks the nonce used, verifies the MPC signature, then calls `safeTransfer` directly to `payload.recipient`:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
// ... signature verification ...
} else {
    IERC20(payload.tokenAddress).safeTransfer(         // line 351
        payload.recipient,
        payload.amount
    );
}
``` [3](#0-2) 

If `payload.recipient` is blacklisted by USDC, `safeTransfer` reverts, rolling back the entire transaction (including the nonce flag at line 287). The relayer can retry, but every retry reverts for the same reason. Because the recipient address is part of the MPC-signed payload, no valid signature can be produced for a different recipient — the MPC key signs the exact Borsh-encoded struct containing `recipient`. [4](#0-3) 

There is no refund path on NEAR: `sign_transfer_callback` already removed the pending transfer, and the tokens were already burned/locked. The NEAR contract has no mechanism to detect that EVM finalization permanently failed.

---

### Impact Explanation

Bridged funds are permanently frozen. The user's USDC (or any blacklist-capable ERC-20 held natively by the bridge) is burned/locked on NEAR with no possibility of recovery on either chain. This is a direct instance of **permanent freezing of bridged funds** — a critical impact under the allowed scope.

---

### Likelihood Explanation

USDC and USDT both enforce address blacklists at the token contract level. Circle has blacklisted hundreds of addresses (OFAC-sanctioned wallets, Tornado Cash-related addresses, exchange hack recipients). Two realistic triggers exist:

1. The recipient address is already blacklisted at the time the user initiates the bridge transfer.
2. The recipient address is blacklisted after `init_transfer` (tokens burned on NEAR) but before `finTransfer` is called on EVM — a window that can span minutes to hours depending on relayer latency.

Both scenarios require no privileged access and no attacker profit motive; the loss is suffered by the ordinary bridge user.

---

### Recommendation

Replace the push-payment pattern with a pull-payment (escrow) pattern for native ERC-20 tokens:

1. In `finTransfer`, credit the amount to an internal mapping instead of calling `safeTransfer` directly:
   ```solidity
   claimable[payload.recipient][payload.tokenAddress] += payload.amount;
   ```
2. Add a separate `claimTokens(address token)` function that lets the recipient pull their funds at any time.

This decouples delivery failure from finalization: the nonce is consumed, the `FinTransfer` event is emitted, and the transfer is permanently recorded even if the recipient cannot currently receive the token. The user retains the ability to claim once the blacklist is lifted, or the protocol can add an admin-assisted redirect path.

---

### Proof of Concept

1. Alice holds USDC on NEAR and calls `ft_transfer_call` to bridge 1 000 USDC to her EVM address `0xAlice`.
2. `init_transfer_internal` burns Alice's USDC on NEAR and emits `InitTransferEvent`. [5](#0-4) 
3. MPC signs `TransferMessagePayload{recipient: 0xAlice, tokenAddress: USDC, amount: 1000, destinationNonce: N}`.
4. Circle blacklists `0xAlice` (e.g., OFAC sanction).
5. Relayer calls `OmniBridge.finTransfer(sig, payload)`.
6. `USDC.safeTransfer(0xAlice, 1000)` reverts → entire transaction reverts. [6](#0-5) 
7. Relayer retries → same revert indefinitely.
8. Alice's 1 000 USDC is permanently lost: burned on NEAR, undeliverable on EVM. No admin function, no refund path, no alternative recipient exists in the protocol.
