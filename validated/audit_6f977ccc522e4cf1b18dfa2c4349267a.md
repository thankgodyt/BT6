### Title
Missing Certificate Validation in `implAddCert` Allows Equivocating Certificates to Boost Arbitrary Blocks in Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The `implAddCert` function in the Peras certificate database accepts any `ValidatedPerasCert` without performing the non-trivial validation logic that is explicitly acknowledged as missing via a `TODO` comment. The only deduplication check is by `PerasRoundNo` — one certificate per round. However, the `ValidatedPerasCert` wrapper is accepted as-is from the caller, and the `vpcCertBoost` field (the weight boost applied to a block during chain selection) is taken directly from the certificate without any independent verification against the protocol parameters. An unprivileged peer that can inject a certificate with an inflated `vpcCertBoost` value — or a certificate boosting a block on an adversarial fork — will cause `preferAnchoredCandidate` and `compareAnchoredFragments` to use that inflated weight, potentially making the node prefer and adopt a non-canonical or adversarial chain.

---

### Finding Description

In `implAddCert` (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`, lines 167–201), the code contains an explicit `TODO`:


The only check performed is whether the `PerasRoundNo` is already in `pcdsCertIds`:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
```

The `vpcCertBoost` field of the stored certificate is taken verbatim from the incoming `ValidatedPerasCert`. This boost value is later used directly in `implGetWeightSnapshot`:

```haskell
mkPerasWeightSnapshot
  [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
  | cert <- Map.elems (pcdsCertsByTicket pcds)
  ]
```

That snapshot is then consumed by `preferAnchoredCandidate` and `compareAnchoredFragments` in `Ouroboros.Consensus.Util.AnchoredFragment` (lines 186–213) to decide whether to switch chains:

```haskell
preferAnchoredCandidate cfg weights ours cand
  ...
  | otherwise =
      case AF.intersect ours cand of
        ...
          case preferCandidate ...
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
```

And at node startup, `initialChainSelection` (`ChainSel.hs`, lines 116–182) reads the weight snapshot from the `PerasCertDB` and passes it directly into chain selection:

```haskell
initialWeights <- atomically $ PerasCertDB.getWeightSnapshot perasCertDB
chain <-
  ChainSel.initialChainSelection
    ...
    (forgetFingerprint initialWeights)
```

The analog to the original report is exact: just as `stethPrice = 0` until `submitState` is called (uninitialized/unvalidated state used in a critical computation), here `vpcCertBoost` is whatever the caller supplies — the "initialized" value is never independently verified against `perasWeight` from the protocol parameters. The `ValidatedPerasCert` name implies validation has occurred, but the `TODO` confirms it has not.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

If a peer can deliver a `ValidatedPerasCert` with an arbitrarily large `vpcCertBoost` (e.g., `maxBound :: Word64`) for a block on an adversarial fork, the `totalWeightOfFragment` for that fork will exceed the honest chain's weight. `preferAnchoredCandidate` will return `ShouldSwitch`, causing the node to adopt the adversarial chain. The same snapshot is used in `readChainComparison` by the BlockFetch client interface (`ClientInterface.hs`, line 235), meaning the node will also preferentially download blocks from the adversarial fork.

Additionally, `takeVolatileSuffix` uses the same snapshot to determine the immutability boundary (which blocks are beyond rollback depth `k`). An inflated boost can cause the node to treat fewer blocks as immutable, expanding the rollback window beyond the security parameter.

---

### Likelihood Explanation

The `ValidatedPerasCert` type is constructed and delivered via the Peras miniprotocol. The `vpcCertBoost` field is set by the caller at construction time (e.g., in the state machine test at line 98: `vpcCertBoost = perasWeight perasTestCfg`). In a production deployment, the network-facing certificate handler must construct this value. If the construction path does not independently enforce `vpcCertBoost == perasWeight (configPeras cfg)`, any peer that can send a certificate message can supply an arbitrary boost. The `TODO` at line 167 explicitly acknowledges that the validation is not yet implemented.

---

### Recommendation

1. In `implAddCert`, add a check that `getPerasCertBoost cert == perasWeight params` where `params` is the protocol's `PerasParams`, rejecting certificates with any other boost value.
2. Remove the `TODO` only after the full validation logic from CIP-0140 (referenced in issue #120) is implemented.
3. Consider making `ValidatedPerasCert` a newtype that can only be constructed through a smart constructor that enforces the boost invariant, so the type system prevents unvalidated certificates from reaching the DB.

---

### Proof of Concept

**Setup:** A private testnet running Peras-enabled Cardano consensus. Two chains exist: the honest chain `H` (length `n`) and an adversarial fork `A` (length `n-1`, branching `k+1` blocks back).

**Attack sequence:**

1. Adversary constructs a `ValidatedPerasCert` for a block on fork `A` with `vpcCertBoost = PerasWeight maxBound`.
2. Adversary delivers this certificate via the Peras certificate miniprotocol to the target node.
3. `implAddCert` stores it without checking the boost value. [1](#0-0) 
4. `implGetWeightSnapshot` returns a snapshot where the adversarial block has weight `maxBound`. [2](#0-1) 
5. When the next block arrives on fork `A`, `chainSelectionForBlock` calls `constructPreferableCandidates` with this snapshot. `preferAnchoredCandidate` computes `weightedSelectView` for both chains; fork `A`'s `wsvWeightBoost = maxBound` dominates, returning `ShouldSwitch`. [3](#0-2) 
6. The node switches to fork `A`, accepting a non-canonical chain. The honest chain `H` is abandoned.
7. On restart, `initialChainSelection` reads the same snapshot and again selects fork `A`. [4](#0-3)

```haskell
implAddCert ::

  PerasCertDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)
    pure addPerasCertRes
```
