### Title
Missing Peras Vote and Certificate Signature/Committee Membership Validation Allows Unauthorized Vote Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasVote` and `validatePerasCert` implementations are production-path stubs that omit all cryptographic and committee-membership checks. Any unprivileged peer can send crafted `PerasVote` messages that pass validation solely by referencing a voter ID present in the stake distribution, with no BLS signature check, no committee seat-index check, and no VRF eligibility-proof check. `validatePerasCert` unconditionally returns `Right` for every certificate it receives. Both stubs are wired into the live vote-diffusion pipeline.

---

### Finding Description

`BlockSupportsPeras` is the class that governs Peras vote and certificate validation. Its default instance (the one actually used in the current codebase) provides the following stub for `validatePerasVote`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check performed is whether the `pvVoterId` appears in the stake distribution. The following mandatory checks are entirely absent:

1. **BLS signature verification** — the `pvSignature` field is never verified against the voter's public key.
2. **Committee seat-index membership** — the `pvSeatIndex` is never checked against the epoch's committee selection (WFALS or EveryoneVotes).
3. **VRF eligibility proof** — for non-persistent committee members, the `pvEligibilityProof` VRF output is never verified.
4. **Round/epoch binding** — the vote's `pvRoundNo` is never cross-checked against the committee that was selected for that round.

The full committee-aware verification logic exists in `WFALS.implVerifyVote` and `EveryoneVotes.implVerifyVote`, but it is never invoked from the inbound vote processing path. [2](#0-1) 

Similarly, `validatePerasCert` unconditionally accepts every certificate:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [3](#0-2) 

Both stubs are wired directly into the live vote-diffusion pipeline. `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` both call `validatePerasVote` as the sole gate before adding a vote to the pool:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) [5](#0-4) 

`processVotes` then adds every vote that passes this stub check to the vote database, where it is counted toward quorum: [6](#0-5) 

Additionally, `getVotingCommitteeForElection` — the function that would retrieve the correct epoch committee for cross-epoch vote validation — is an unimplemented stub that throws a runtime `error`:

```haskell
getVotingCommitteeForElection _electionId _interEpochVotingCommittee = do
  error "TODO: implement getVotingCommitteeForElection"
``` [7](#0-6)

### Impact Explanation

An unprivileged peer can craft `PerasVote` messages that reference any pool ID present in the stake distribution, with an arbitrary (or zeroed) BLS signature and any seat index. These votes pass `validatePerasVote` and are added to the vote pool. Because `votesReachQuorum` aggregates stake from `ValidatedPerasVote` records, an attacker who controls enough pool IDs in the stake distribution (or who can enumerate them) can accumulate sufficient fake stake-weighted votes to trigger `forgePerasCert`. The resulting forged certificate boosts a non-canonical chain in Peras chain selection (`PerasSelectView`), causing honest nodes to prefer an attacker-controlled fork over the canonical chain.

This is a bypass of Peras voting and certificate checks that enables unauthorized vote and certificate acceptance, matching the **High** impact tier: *"Bypass of… Peras voting or certificate checks… that enables unauthorized… vote, or certificate acceptance."*

---

### Likelihood Explanation

The attack requires only network access to a node running the Peras vote-diffusion mini-protocol. No keys, stake, or privileged access are needed — only knowledge of pool IDs present in the current stake distribution, which is public information. The attacker must send enough fake votes to exceed the quorum threshold, which depends on the configured `perasWeight` and the total stake. This is a realistic attack for any adversary with network access to a Peras-enabled node.

---

### Recommendation

1. Replace the stub `validatePerasVote` with a call to the appropriate committee's `verifyVote` (e.g., `WFALS.implVerifyVote` or `EveryoneVotes.implVerifyVote`), passing the correct `VotingCommittee` for the vote's round/epoch.
2. Replace the stub `validatePerasCert` with a call to the appropriate committee's `verifyCert`.
3. Implement `getVotingCommitteeForElection` in `AcrossEpochs.hs` so that votes and certificates from the previous epoch can be validated against the correct committee.
4. Ensure the `PerasCfg` passed to `validatePerasVote` in the pool writers carries the full committee selection context, not just `mkPerasParams`.

---

### Proof of Concept

1. Enumerate pool IDs from the public stake distribution.
2. Craft `PerasVote` messages with valid `pvVoteRound`, `pvVoteBlock` pointing to a target block on an attacker-controlled fork, arbitrary `pvSeatIndex`, `PersistentPerasVoteEligibilityProof`, and a zeroed/random `pvSignature`.
3. Send these votes via the Peras vote-diffusion mini-protocol to a target node.
4. `processVotes` → `validatePerasVote` accepts each vote (signature is never checked; only stake-distribution lookup is performed).
5. `updatePerasRoundVoteState` accumulates stake from the fake votes.
6. Once the quorum threshold is exceeded, `forgePerasCert` produces a certificate for the attacker's target block.
7. The certificate is stored and applied to chain selection, boosting the attacker's fork by `perasWeight` in `PerasSelectView`, causing the node to prefer the non-canonical chain.

implVerifyVote ::
  forall crypto.
  ( CryptoSupportsVoteSigning crypto
  , CryptoSupportsVRF crypto
  ) =>
  VotingCommittee crypto WFALS ->
  Vote crypto WFALS ->
  Either
    (VotingCommitteeError crypto WFALS)
    (EligibilityWitness crypto WFALS)
implVerifyVote committee = \case
  WFALSPersistentVote seatIndex electionId candidate sig
    | Just (_, voterPublicKey, voterStake, _) <-
        getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
    , isPersistentMember seatIndex committee -> do
        let voterVerificationKey =
              getVoteVerificationKey (Proxy @crypto) voterPublicKey
        checkVoteSignature voterVerificationKey electionId candidate sig
        pure $
          WFALSPersistentMember
            seatIndex
            voterStake
    | otherwise -> do
        Left (NotAPersistentMember seatIndex)
  WFALSNonPersistentVote seatIndex electionId message vrfOutput sig
    | Just (_, voterPublicKey, voterStake, _) <-
        getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
    , not (isPersistentMember seatIndex committee) -> do
        let voterVoteVerificationKey =
              getVoteVerificationKey (Proxy @crypto) voterPublicKey
        bimap InvalidVoteSignature id $ do
          verifyVoteSignature
            voterVoteVerificationKey
            electionId
            message
            sig
        let voterVRFVerificationKey =
              getVRFVerificationKey (Proxy @crypto) voterPublicKey
        let vrfContext =
              VRFVerifyContext voterVRFVerificationKey vrfOutput
        void $ bimap InvalidVoterEligibilityProof id $ do
          evalVRF
            vrfContext
            ( mkVRFElectionInput
                @crypto
                (epochNonce committee)
                electionId
            )
        let numSeats =
              localSortitionNumSeats
                (nonPersistentCommitteeSize committee)
                (totalNonPersistentStake committee)
                voterStake
                (normalizeVRFOutput vrfOutput)
        case nonZero numSeats of
          Nothing ->
            Left (ZeroNonPersistentSeats seatIndex)
          Just nonZeroNumSeats ->
            pure $
              WFALSNonPersistentMember
                seatIndex
                voterStake
                vrfOutput
                nonZeroNumSeats
    | otherwise ->
        Left (NotANonPersistentMember seatIndex)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
