### Title
Missing Ownership Check in `withdraw_rbf` Allows Any Caller to Redirect Another User's Pending BTC Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` is a public, unprivileged function that accepts an `original_btc_pending_verify_id` identifying any user's pending withdrawal and a caller-supplied `output` vector. It never verifies that `env::predecessor_account_id()` is the owner of that pending transaction. An attacker who knows a victim's pending-tx ID can call `withdraw_rbf` with a modified output that redirects the BTC to the attacker's own address, causing unauthorized loss of the victim's bridged funds.

### Finding Description

`withdraw_rbf` is exposed without any role guard and without an ownership check:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← attacker's account
    self.require_pending_sign_capacity(&account_id);  // ← checks attacker's capacity, not ownership

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← attacker passed as the acting account
        original_btc_pending_verify_id,     // ← victim's pending tx
        output,                             // ← attacker-controlled outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

The privileged sibling function `cancel_withdraw` (DAO/Operator only) demonstrates the correct pattern: it **looks up the owner from the stored pending info** and uses that as the acting account, never trusting the caller:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();                                    // ← owner from storage
    self.require_pending_sign_capacity(&user_account_id);
    self.cancel_withdraw_chain_specific(user_account_id, ...);
}
``` [2](#0-1) 

`withdraw_rbf` omits this lookup entirely. It passes the **caller's** `account_id` — not the stored owner — into `withdraw_rbf_chain_specific`, together with the caller-supplied `output` vector. Because the RBF path rebuilds the Bitcoin transaction with the new outputs, an attacker who supplies outputs pointing to their own BTC address will cause the MPC-signed replacement transaction to pay them instead of the victim.

### Impact Explanation

The `output` parameter directly controls the Bitcoin transaction outputs of the replacement (RBF) transaction. The bridge's MPC signing pipeline signs whatever PSBT is constructed from those outputs. If an attacker substitutes their own BTC address in `output`, the signed and broadcast RBF transaction sends the victim's BTC to the attacker. This constitutes **unauthorized redirection and theft of bridge-controlled BTC funds** — a critical impact matching "Significant loss, theft, or permanent locking of user or protocol funds."

### Likelihood Explanation

`withdraw_rbf` is a public, payable-free function with no role restriction. All `btc_pending_verify_id` values are observable on-chain (emitted as events and stored in public contract state). Any NEAR account can call the function at any time while a victim's withdrawal is in the `PendingSign` stage. No privileged access, leaked keys, or social engineering is required.

### Recommendation

Add an ownership check at the start of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let caller = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the owner can RBF their own withdrawal");
    self.require_pending_sign_capacity(&owner);
    self.withdraw_rbf_chain_specific(owner, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Alice calls `ft_transfer_call` → bridge initiates a BTC withdrawal for Alice. A `BTCPendingInfo` entry is created with `account_id = alice` and a known `btc_pending_id` (emitted via `GenerateBtcPendingInfo` event).
2. Attacker observes the event and learns Alice's `btc_pending_id`.
3. Attacker calls `withdraw_rbf(alice_btc_pending_id, [TxOut { value: alice_amount, script_pubkey: attacker_btc_address }], None)`.
4. `env::predecessor_account_id()` returns attacker's NEAR account. `require_pending_sign_capacity` passes (attacker has capacity). No ownership check is performed.
5. `withdraw_rbf_chain_specific(attacker_account, alice_btc_pending_id, attacker_outputs, ...)` is called, constructing a replacement PSBT with attacker-controlled outputs.
6. The MPC network signs the replacement transaction. When broadcast, Alice's BTC is sent to the attacker's address. [1](#0-0) [2](#0-1)
