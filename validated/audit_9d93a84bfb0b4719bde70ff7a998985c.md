### Title
Chain Sync Client Uses Empty Peras Weight Snapshot in Beyond-Forecast-Horizon Candidate Preference Check, Causing Incorrect Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the Chain Sync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a candidate chain is preferred over the node's current chain. This mirrors the external report's root cause: a critical comparison uses an incomplete/zeroed-out value instead of the actual tracked state, producing incorrect decisions. When Peras is active, a candidate chain that is shorter in block count but heavier in total Peras weight is incorrectly classified as non-preferred, causing the node to disconnect from the peer and permanently forgo adopting the heavier (more secure) chain.

---

### Finding Description

When a header received from a peer is beyond the forecast horizon (the ledger state cannot produce a `LedgerView` for that slot), `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
``` [1](#0-0) 

The guard function is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero weights
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [2](#0-1) 

`preferAnchoredCandidate` dispatches on whether the weight snapshot is empty. With `emptyPerasWeightSnapshot`, it falls into the block-count-only path:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- purely block-count comparison
      ...
  | otherwise =
      -- weighted comparison using actual Peras boosts
      ...
``` [3](#0-2) 

The total weight of a fragment is `blockNo + weightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

A single Peras certificate can boost a block by a weight far exceeding the block-count difference between two chains. When the candidate chain has fewer blocks than ours but carries a Peras certificate boost that makes its total weight larger, `checkPreferTheirsOverOurs` with `emptyPerasWeightSnapshot` evaluates `shouldSwitch` as `False` (candidate has fewer blocks) and fires `throwSTM CandidateTooSparse`, disconnecting from the peer. The node then never validates those headers and never performs the real weighted chain selection that would have adopted the heavier chain.

The actual `PerasWeightSnapshot` is available from the ChainDB via `getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))`: [5](#0-4) 

It is already used correctly everywhere else in the chain selection pipeline (initial chain selection, `chainSelectionForBlock`, block fetch plausibility check), but is omitted here.

---

### Impact Explanation

**Impact: High — Chain selection bug that causes an honest node to prefer a non-canonical, lighter chain.**

When Peras is active:

1. A peer presents a candidate chain `C` that is shorter in block count than the node's current chain `O`, but carries a Peras certificate boost making `totalWeight(C) > totalWeight(O)`.
2. A header in `C` falls beyond the forecast horizon (e.g., during initial sync or after a long slot gap).
3. `checkPreferTheirsOverOurs` compares purely by block count (because `emptyPerasWeightSnapshot` is used), concludes `C` is not preferred, and disconnects with `CandidateTooSparse`.
4. The node never validates `C`'s headers and never performs the weighted chain selection that would have switched to `C`.
5. The node remains on the lighter chain `O`, violating the Peras chain selection invariant that the heaviest chain should be preferred.

This is a direct analog to the external report: the external report's `quoteBuyPortalEnergy` used `balanceOf(VIRTUAL_LP)` (gross balance including reserved `fundingRewardPool`) instead of the net balance, producing an incorrect price. Here, `checkPreferTheirsOverOurs` uses `emptyPerasWeightSnapshot` (zero weights) instead of the actual Peras weight snapshot, producing an incorrect chain preference decision.

---

### Likelihood Explanation

**Likelihood: Low (currently), rising to Medium once Peras is deployed.**

- Peras is not yet active on Cardano mainnet; the weight snapshot is empty in all current production deployments, making `emptyPerasWeightSnapshot` accidentally correct today.
- Once Peras is activated, any syncing node that encounters a Peras-boosted candidate chain whose tip header is beyond the forecast horizon will trigger this path.
- The beyond-forecast-horizon condition arises naturally during initial sync and after long slot gaps, both of which are common.
- No special adversarial capability is required: an honest peer serving a legitimately Peras-certified chain is sufficient to trigger the bug.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` read from the ChainDB (via `getPerasWeightSnapshot`, which is already an `STM` action and therefore usable inside the surrounding `atomically` block). This ensures the beyond-forecast-horizon candidate preference check is consistent with the weighted chain selection used everywhere else in the pipeline.

---

### Proof of Concept

**Setup (private testnet with Peras active):**

1. Node N has current chain O: 100 blocks, no Peras boosts → `totalWeight(O) = 100`.
2. Peer P serves candidate chain C: 80 blocks, one Peras certificate boosting block 50 by weight 50 → `totalWeight(C) = 80 + 50 = 130`.
3. Block 81 of C falls beyond N's forecast horizon (e.g., N's ledger tip is at slot S and block 81 is at slot S + stabilityWindow + 1).

**Trigger:**

4. N's chain sync client calls `readLedgerStateHelper` for block 81 of C.
5. `prj lst` returns `Nothing` (beyond forecast horizon).
6. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`.
7. `preferAnchoredCandidate` compares block counts: `blockNo(O_tip) = 100 > blockNo(C_tip) = 80` → `ShouldNotSwitch`.
8. `shouldSwitch` is `False` → `throwSTM CandidateTooSparse`.

**Result:**

9. N disconnects from P. N never validates C's headers. N never performs weighted chain selection.
10. N remains on O with `totalWeight = 100`, ignoring C with `totalWeight = 130`.
11. With the correct fix (actual weight snapshot), step 7 would compute `totalWeight(C) = 130 > totalWeight(O) = 100` → `ShouldSwitch` → `pure ()` → N keeps waiting and eventually adopts C.

          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
