### Title
Peras Vote Validation Accepts Claimed Voter Identity Without Cryptographic Proof, Enabling Forged Quorum Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` implementation in the production `BlockSupportsPeras` instance accepts a `PerasVote` whose `pvVoteVoterId` field is a bare, self-declared `KeyHash StakePool`. Validation only checks that this claimed voter ID exists in the stake distribution; it never verifies any cryptographic proof that the submitting peer actually controls the corresponding key. Because the `PerasVote blk` data type carries no signature field at all, an unprivileged peer can submit votes claiming to be any pool operator in the stake distribution. Accumulating enough such forged votes triggers quorum, causing the node to forge and store a `ValidatedPerasCert` that boosts an attacker-chosen block's chain weight, directly corrupting chain selection.

---

### Finding Description

The `PerasVote blk` data type in the production `BlockSupportsPeras` instance is defined as:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- bare KeyHash, no signature
  }
``` [1](#0-0) 

There is no signature field. The corresponding `validatePerasVote` implementation only performs a stake-distribution membership lookup:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This is the instance used for all blocks (`instance StandardHash blk => BlockSupportsPeras blk`), and it is the validation function called in the production inbound diffusion path:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

The `processVotes` function, which is the inbound handler for votes received from peers over the `ObjectDiffusion` mini-protocol, calls this validation and then adds passing votes to the `PerasVoteDB`: [4](#0-3) 

The `PerasVoteDB.Impl` also carries an explicit TODO acknowledging that non-trivial validation logic is missing: [5](#0-4) 

Once enough forged votes accumulate to reach quorum, `updatePerasRoundVoteStates` triggers certificate forging inside `implAddVote`, and the resulting `ValidatedPerasCert` is stored and propagated: [6](#0-5) 

The `VotingCommittee` abstraction (`verifyVote`, `verifyCert`) does perform full BLS signature and VRF verification, but this path is entirely bypassed by the degenerate `BlockSupportsPeras` instance used in production: [7](#0-6)

### Impact Explanation

An unprivileged peer can submit `PerasVote` messages over the `ObjectDiffusion` mini-protocol claiming to be any pool operator whose `KeyHash StakePool` appears in the public stake distribution. Because pool IDs are public ledger data, the attacker can enumerate them freely. By submitting votes from pools whose combined `PerasVoteStake` exceeds the quorum threshold, the attacker causes the receiving node to forge a `ValidatedPerasCert` for an arbitrary block of the attacker's choosing. This certificate is stored in `PerasCertDB` and used by chain selection to assign a Peras weight boost to that block, causing the honest node to prefer the attacker's chosen chain over the canonical chain. This is a **High** chain-selection integrity violation: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The attack requires only a network connection to a node running the `ObjectDiffusion` mini-protocol for Peras votes. Pool IDs are fully public. The attacker needs no keys, no stake, and no privileged access. The only constraint is knowing the stake distribution, which is public on-chain data. Likelihood is **High**.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote blk`** (analogous to how `WFALSPersistentVote` and `WFALSNonPersistentVote` carry a `VoteSignature`). The `PerasVote` type must carry a proof of origin.

2. **Implement `validatePerasVote` to verify that proof** using the voter's public key from the stake distribution, mirroring `implVerifyVote` in `WFALS.hs` or `EveryoneVotes.hs`.

3. **Do not accept `ValidatedPerasVote` from the network as already-validated.** The `ValidatedPerasVote` wrapper must only be constructed after local signature verification, not by trusting the peer's claimed voter ID.

The existing `VotingCommittee` class already provides the correct interface (`verifyVote`) — the fix is to wire it into the `BlockSupportsPeras` instance's `validatePerasVote` rather than leaving a stub that only checks stake membership.

---

### Proof of Concept

1. Attacker connects to a target node via the `ObjectDiffusion` mini-protocol for Peras votes.
2. Attacker reads the current stake distribution from the public ledger, identifying pool IDs whose combined stake exceeds the quorum threshold.
3. Attacker constructs `PerasVote` objects for each such pool, all targeting the same `(pvVoteRound, pvVoteBlock)` pointing to an attacker-chosen block:
   ```
   PerasVote { pvVoteRound = r, pvVoteBlock = attackerBlock, pvVoteVoterId = poolId_i }
   ```
4. Attacker sends these votes to the target node. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; since each `poolId_i` is in the stake distribution, all pass.
5. Each vote is added to `PerasVoteDB`. When cumulative stake exceeds the quorum threshold, `updatePerasRoundVoteStates` triggers `forgePerasCert`, producing a `ValidatedPerasCert` for `attackerBlock`.
6. The certificate is stored in `PerasCertDB` and used by chain selection to boost `attackerBlock`'s weight, causing the node to prefer the attacker's chain. [8](#0-7) [9](#0-8) [10](#0-9)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
