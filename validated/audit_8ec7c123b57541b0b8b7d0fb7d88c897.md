### Title
Permissionless `request_refund` Allows Any Caller to Front-Run and Permanently Block a User's Refund Request — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`request_refund` is a fully permissionless public entrypoint. Because only one refund request per UTXO is allowed at a time, any attacker can front-run a legitimate user's `request_refund` call with their own call (supplying an attacker-controlled `refund_address`), causing the user's call to revert with "Refund request already exists for this UTXO". The DAO can reject the malicious request, but the attacker can immediately re-submit, creating a persistent blocking loop that keeps the user's BTC locked in the bridge-controlled deposit address indefinitely.

### Finding Description

`request_refund` carries no caller-identity check. Any NEAR account can invoke it for any UTXO, supplying any `refund_address`, as long as `deposit_msg.refund_address` is `None`: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is that it must equal `deposit_msg.refund_address` **when that field is `Some`**. When it is `None`, any address is accepted without restriction: [2](#0-1) 

The callback then enforces a hard uniqueness constraint — a second `request_refund` for the same UTXO always reverts: [3](#0-2) 

The `created_at_sec` timestamp is set at the moment the attacker's request lands, and the timelock is measured from that moment: [4](#0-3) 

The default `unsafe_refund_timelock_sec` is 14 days: [5](#0-4) 

**Attack flow:**

1. A user deposits BTC to a bridge address derived from a `DepositMsg` where `refund_address` is `None`. The `LogDepositAddress` event makes the `DepositMsg` publicly observable.
2. The deposit is never finalized via `verify_deposit` (relayer down, user changed mind, etc.).
3. The user submits `request_refund` with their own BTC address.
4. An attacker observes this (or simply monitors unfinalized deposits) and submits `request_refund` first, supplying an attacker-controlled BTC address. The attacker pays the 2 NEAR non-refundable storage fee.
5. The attacker's request is stored. The user's call reverts: "Refund request already exists for this UTXO".
6. The DAO can call `reject_refund` to remove the malicious request.
7. The attacker immediately re-submits another `request_refund` (paying another 2 NEAR).
8. Steps 6–7 repeat indefinitely. The user's BTC remains locked in the bridge-controlled deposit address for as long as the attacker continues.

### Impact Explanation

The user's BTC is held at a bridge-controlled MPC address. The only on-chain path to recover it is through the refund pipeline. By persistently occupying the single refund-request slot for that UTXO, the attacker prevents the user from ever initiating a refund, causing indefinite locking of the user's bridged funds. This matches the allowed Medium impact: **attacker-triggered temporary (potentially indefinite) locking of bridged funds**.

Additionally, if the DAO fails to reject within the 14-day `unsafe_refund_timelock_sec` window even once, the attacker can call `execute_refund` and redirect the BTC to their own address via the MPC signing pipeline: [6](#0-5) [7](#0-6) 

### Likelihood Explanation

- All deposit transactions and `DepositMsg` values are publicly observable on-chain (Bitcoin blockchain + NEAR `LogDepositAddress` events).
- `request_refund` requires no special role — any NEAR account can call it.
- The 2 NEAR cost per attempt is a deterrent but not a prohibitive barrier for a motivated attacker targeting a high-value deposit.
- The attack is especially effective against users who do not set `deposit_msg.refund_address` (the `None` case), which is the common path for standard deposits.

### Recommendation

Restrict `request_refund` so that only the intended recipient (`deposit_msg.recipient_id`) or a privileged role (DAO/Operator/RefundOperator) can submit a refund request for a given UTXO. Alternatively, when `deposit_msg.refund_address` is `None`, bind the stored `refund_address` to the caller's identity and verify on `execute_refund` that the caller matches, preventing third-party hijacking of the refund slot.

    pub fn request_refund(

        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();

            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
