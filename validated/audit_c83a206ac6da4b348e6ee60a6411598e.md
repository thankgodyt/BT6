Audit Report

## Title
Cross-Chain Replay of MPC `deploy_token` Signature Due to Missing `chain_id` in `MetadataPayload` Borsh Encoding — (`starknet/src/bridge_types.cairo`, `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`MetadataPayload::to_borsh` on Starknet omits a `chain_id` field, and the equivalent Borsh encoding in EVM's `deployToken` likewise omits `chain_id`. Because NEAR signs with a single `SIGN_PATH = "bridge-1"` for all destination chains, and both EVM (`nearBridgeDerivedAddress`) and Starknet (`omni_bridge_derived_address`) verify against the same MPC-derived Ethereum address, a valid MPC signature produced for an EVM `deployToken` call produces byte-for-byte identical Borsh bytes to what Starknet's `deploy_token` verifies. An attacker can replay the EVM signature on Starknet to deploy a bridge token on Starknet without any Starknet-specific MPC authorization.

## Finding Description

**Starknet `MetadataPayload::to_borsh`** encodes only `PayloadType::Metadata`, `token`, `name`, `symbol`, and `decimals` — no `chain_id`: [1](#0-0) 

**EVM `deployToken`** constructs an identical Borsh encoding with no `chain_id`: [2](#0-1) 

**NEAR `MetadataPayload`** struct has no `chain_id` field and is serialized directly by Borsh: [3](#0-2) 

NEAR uses a single signing path for all destination chains: [4](#0-3) 

Starknet's `deploy_token` calls `_verify_borsh_signature` with no chain binding: [5](#0-4) 

`_verify_borsh_signature` verifies against `omni_bridge_derived_address` — the same MPC-derived address used by EVM's `nearBridgeDerivedAddress`: [6](#0-5) 

**Contrast with `TransferMessagePayload`**, which correctly passes `chain_id` in both Starknet's `fin_transfer` and EVM's `finTransfer`: [7](#0-6) [8](#0-7) [9](#0-8) 

The exploit path: NEAR's MPC signs a `MetadataPayload` for a given token targeting EVM. A relayer submits `(signature, payload)` to EVM's `deployToken` — the signature is now public in EVM calldata. An attacker copies the exact `(signature, payload)` and calls Starknet's `deploy_token`. `_verify_borsh_signature` computes `keccak256(payload.to_borsh())` — identical bytes to what NEAR signed — and verifies against `omni_bridge_derived_address`. The check passes. The token is registered in `near_to_starknet_token` and `starknet_to_near_token` as a mintable/burnable bridge token on Starknet.

## Impact Explanation

This is a **signer/prover verification bypass** and **cross-chain replay / chain-domain separation flaw**: the MPC signature is accepted as authorizing Starknet token deployment when it only authorized EVM deployment. The attacker executes a deployer-equivalent action (registering a bridge token with mint/burn privileges on Starknet) without any Starknet-specific MPC authorization. The resulting state — `near_to_starknet_token` mapping a token that NEAR's bridge never registered for Starknet — constitutes a persistent token registry inconsistency and unauthorized bridge token deployment, matching the allowed critical impact classes for signer/prover verification bypass and cross-chain replay/chain-domain separation flaw.

## Likelihood Explanation

All inputs required for the replay are public: `MetadataPayload` fields and the MPC signature are submitted as calldata to EVM's `deployToken` and are readable from any EVM block explorer. No privileged access, key compromise, or MPC collusion is required. The attacker only needs to copy the calldata and submit it to Starknet's `deploy_token`. The attack is repeatable for every token that is deployed on EVM via the MPC-signed flow.

## Recommendation

Include `chain_id` in `MetadataPayload::to_borsh` on all chains, mirroring the pattern already used in `TransferMessagePayload::to_borsh`. On Starknet, change the signature to `fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray` and prepend `chain_id` after the payload type byte. Apply the same change to EVM's `deployToken` Borsh encoding (using `omniBridgeChainId`) and to NEAR's `MetadataPayload` Borsh serialization. NEAR's `log_metadata_callback` must pass the target chain's ID when constructing the payload to sign, so each chain receives a chain-specific, non-replayable signature.

## Proof of Concept

1. Call `log_metadata` on NEAR for `token.near`. NEAR's MPC signs `keccak256(borsh(MetadataPayload{prefix:1, token:"token.near", name:"Token", symbol:"TKN", decimals:18}))` with path `"bridge-1"`.
2. A relayer submits `(signature, payload)` to EVM's `deployToken`. The token is deployed on EVM. The signature is now public in EVM calldata.
3. An attacker copies the exact `(signature, payload)` and calls Starknet's `deploy_token(signature, payload)`.
4. `_verify_borsh_signature` computes `keccak256(payload.to_borsh())` — identical bytes to step 1 — and verifies against `omni_bridge_derived_address`. The check passes.
5. `token.near` is registered as a bridge token on Starknet. `near_to_starknet_token[keccak("token.near")]` is set to a newly deployed contract address.
6. Assert: `dispatcher.get_token_address("token.near")` returns a non-zero address on Starknet, confirming deployment without any Starknet-specific MPC authorization.

        ref self: ContractState, borsh_bytes: @ByteArray, signature: Signature,
    ) {
        let message_hash_le = compute_keccak_byte_array(borsh_bytes);
        let message_hash = reverse_u256_bytes(message_hash_le);
