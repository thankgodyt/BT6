### Title
`checkPreferTheirsOverOurs` Ignores Peras Weights, Causing Incorrect Peer Disconnection and Non-Canonical Chain Preference When Peras Is Active - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client evaluates whether a candidate chain is preferred over the current selection using a hardcoded `emptyPerasWeightSnapshot`, completely ignoring any Peras certificate weight boosts. The actual chain selection in `ChainSel.hs` reads the real `PerasWeightSnapshot` from the ChainDB. When Peras is active, a candidate chain that is heavier by total weight (block count + Peras boost) but not strictly longer by block count will be incorrectly judged as non-preferred, causing the node to throw `CandidateTooSparse` and disconnect from the peer. The node then stays on a non-canonical chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is called inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` — i.e., the incoming header is beyond the forecast horizon and the client must block waiting for the local chain to advance. During that wait, the guard checks whether the candidate is still worth waiting for:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded; ignores real Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

The call site that triggers this guard:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
``` [2](#0-1) 

By contrast, the actual chain selection in `chainSelectionForBlock` reads the live snapshot:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [3](#0-2) 

`preferAnchoredCandidate` branches on whether the snapshot is empty. With real weights it computes `weightedSelectView` (block count + Peras boost); with `emptyPerasWeightSnapshot` it falls back to block-count-only comparison:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count-only path
      ...
  | otherwise =
      -- weighted path using wsvTotalWeight = blockNo + perasBoost
      ...
``` [4](#0-3) 

The `WeightedSelectView` total weight is `wsvBlockNo + wsvWeightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

**The discrepancy**: `checkPreferTheirsOverOurs` always uses the block-count-only path, while `chainSelection` uses the weighted path when Peras is active. A candidate fork that is heavier by total weight (e.g., same block count as ours but boosted by a Peras certificate) will pass the real chain selection criterion but fail the guard, causing a spurious `CandidateTooSparse` disconnect.

---

### Impact Explanation

When Peras is active and a Peras certificate boosts a block on a candidate fork:

1. The candidate fork may have equal or fewer blocks than the current selection but greater total weight.
2. A peer offering that fork sends a header beyond the forecast horizon.
3. `checkPreferTheirsOverOurs` fires, compares by block count only, concludes the candidate is not preferred, and throws `CandidateTooSparse`.
4. The ChainSync client disconnects from the peer.
5. The node remains on the non-canonical, lighter chain.

If all peers offering the canonical Peras-boosted chain trigger this code path simultaneously (e.g., during a period of low slot density creating a large forecast gap), the node permanently prefers the non-canonical chain. This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical, less-secure chain by a crafted (but fully valid) peer interaction, violating the Peras security assumption that weight-boosted chains are preferred.

---

### Likelihood Explanation

Peras is not yet active by default (CHANGELOG: "Note that if Peras is disabled (which is the default), there is no observable difference"), but the code is present and will be activated. Once active, the scenario is realistic:

- A Peras certificate is issued for a block on a minority fork, making it heavier.
- The fork has the same block count as the majority chain (common during a tie-breaking round).
- Peers on that fork have headers beyond the local forecast horizon (common during sync or after a slot gap).

No special privileges are required; any peer offering a valid Peras-boosted chain triggers the path. The TODO comment in the code (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers recognise the check is broken under Peras but have not yet removed it.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the ChainDB (e.g., pass it in from `readLedgerStateHelper` which already has access to the ChainDB view), so the guard uses the same criterion as the actual chain selection. Alternatively, remove the check entirely as the TODO suggests, since the LoP/GDD mechanisms provide equivalent protection without this race-prone guard.

---

### Proof of Concept

**Setup** (private testnet with Peras enabled):

1. Node A is on chain `C_ours` (block count = 100, Peras weight = 100).
2. A Peras certificate is issued boosting block at height 95 on fork `C_cand` (block count = 100, Peras weight = 115 — heavier by boost).
3. Peer B offers `C_cand` via ChainSync. The tip header of `C_cand` is at a slot beyond A's forecast horizon (e.g., a slot gap > forecast window exists on `C_cand`).

**Trigger**:

```
-- Inside readLedgerStateHelper on Node A:
prj lst == Nothing   -- header beyond forecast horizon
-- checkPreferTheirsOverOurs called with emptyPerasWeightSnapshot
-- preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag
--   => compares blockNo(ourTip)=100 vs blockNo(theirTip)=100 => EQ => ShouldNotSwitch
-- throws CandidateTooSparse, Node A disconnects from Peer B
```

**Actual chain selection** (if the block were downloaded):

```
-- chainSelectionForBlock reads real weights
-- preferAnchoredCandidate ... realWeights ourFrag theirFrag
--   => wsvTotalWeight(ours)=100, wsvTotalWeight(cand)=115 => ShouldSwitch
-- Node A would switch to C_cand
```

**Result**: Node A stays on `C_ours` (non-canonical) instead of switching to `C_cand` (canonical by Peras weight), violating the Peras chain-selection invariant. [6](#0-5) [7](#0-6)

          (Empty ourAnchor, _ :> theirTip) ->

            (projectChainOrderConfig cfg)
