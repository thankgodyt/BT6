Audit Report

## Title
Floor Division in `normalize_amount` Permanently Freezes User Funds When Transfer Amount Is Below Decimal Threshold - (File: near/omni-bridge/src/lib.rs)

## Summary
`normalize_amount` applies integer floor division to scale a token amount from its origin precision to the bridge's normalized precision. When a user initiates a transfer whose `amount_without_fee` is smaller than `10^(origin_decimals - decimals)`, the division truncates to zero. The subsequent `require!(amount_to_transfer > 0)` guard in `sign_transfer` permanently reverts every signing attempt, while the user's tokens are already locked or burned on NEAR with no cancellation or refund path available.

## Finding Description
`normalize_amount` is confirmed at lines 2784–2787 to use integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The inline comment at line 2781 acknowledges dust truncation and states "When fee = 0, dust stays locked/burned. See SECURITY.md for details." However, SECURITY.md contains only a generic exclusion list with no mention of this behavior, and the comment addresses only remainder dust — not the case where the entire `amount_without_fee` normalizes to zero.

`sign_transfer` (lines 475–485) calls `normalize_amount` on `amount_without_fee` and panics if the result is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`init_transfer` (lines 554–557) only validates `fee < amount` — it does not check that `normalize_amount(amount_without_fee) > 0` before proceeding:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

`init_transfer_internal` (lines 1850–1857) then burns or locks the tokens unconditionally:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
```

All six call sites of `remove_transfer_message` in `lib.rs` are gated behind either a successful MPC signing (`sign_transfer_callback`, line 657) or a valid destination-chain proof (`claim_fee_callback`, line 1094). No public `cancel_transfer` or user-callable refund function exists — confirmed by exhaustive search returning zero matches.

## Impact Explanation
This directly matches the Critical allowed impact: **permanent freezing of bridged funds**. Tokens are burned or locked on NEAR, the `TransferMessage` is stored in contract state, and every subsequent `sign_transfer` call reverts with `InvalidAmountToTransfer`. There is no code path by which the user can recover their funds. The loss is irreversible.

## Likelihood Explanation
The condition is reachable by any unprivileged user via a standard `ft_transfer_call`. No special role or privileged access is required. Tokens with a decimal gap between origin and bridge representation (e.g., `origin_decimals = 24`, `decimals = 18`, giving a divisor of 1,000,000) are explicitly supported. A user who sends fewer than 1,000,000 base units (minus fee) triggers the freeze. The `init_transfer` validation accepts the call without error, giving the user no indication that their funds will be permanently frozen. The condition is repeatable for any user unaware of the implicit minimum transfer size.

## Recommendation
Add a minimum-amount check inside `init_transfer` (before tokens are locked or burned) that verifies `normalize_amount(amount_without_fee, decimals) > 0`. This ensures the contract rejects sub-threshold transfers before taking any irreversible action. As a defense-in-depth measure, implement a user-callable `cancel_transfer` function that refunds locked/burned tokens when a transfer has not yet been signed, providing a recovery path for any stuck transfers.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`, divisor = 1,000,000).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000`). Tokens are burned/locked. `TransferMessage` is stored.
4. Relayer calls `sign_transfer`.
5. `normalize_amount(500_000, {origin_decimals:24, decimals:18})` = `500_000 / 1_000_000` = **0**.
6. `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`.
7. MPC signing is never requested; `sign_transfer_callback` is never reached; `TransferMessage` is never removed.
8. The user's 500,000 base-unit tokens are permanently frozen with no recovery path.

A local unit test can reproduce this by constructing a `TransferMessage` with the above parameters, calling `init_transfer_internal` to confirm tokens are locked, then calling `sign_transfer` to confirm it panics with `InvalidAmountToTransfer`, and finally asserting the `TransferMessage` remains in storage.
