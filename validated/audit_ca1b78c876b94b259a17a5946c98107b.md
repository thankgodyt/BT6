### Title
Relayer Fees Misdirected to Transaction Signer Instead of Actual Relayer Contract — (`contracts/satoshi-bridge/src/nbtc/mint.rs`, `contracts/satoshi-bridge/src/nbtc/burn.rs`)

### Summary

Both the deposit and withdrawal fee-payment paths use `env::signer_account_id()` to identify the relayer fee recipient. In NEAR Protocol, `signer_account_id` is the **original transaction signer**, not the immediate caller. When a trusted relayer is implemented as a NEAR contract (a common production pattern), `signer_account_id` resolves to the user who triggered the relayer contract, not the relayer contract itself. The relayer contract earns no fee; the user receives it instead.

### Finding Description

**Withdrawal path** — `verify_withdraw_burn_promise` in `contracts/satoshi-bridge/src/nbtc/burn.rs`:

```rust
ext_nbtc::ext(config.nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(
        btc_pending_info.account_id.clone(),
        btc_pending_info.burn_amount.into(),
        env::signer_account_id(),   // ← relayer_account_id
        relayer_fee.into(),
    )
``` [2](#0-1) 

Both functions are called from `#[private]` self-callbacks (`verify_deposit_callback` and `internal_verify_withdraw_callback`). In that callback context:

- `env::predecessor_account_id()` = the bridge contract itself (the self-callback scheduler)
- `env::signer_account_id()` = the original transaction signer

The `#[trusted_relayer]` access-control macro, applied to `verify_deposit` and `verify_withdraw`, checks `predecessor_account_id` at the time of the outer call to enforce the relayer role. [3](#0-2) [4](#0-3) 

When the relayer is a **contract** (e.g., an automated relayer service, a meta-transaction relayer, or any NEAR contract holding the `UnrestrictedRelayer` role):

| Context variable | Value |
|---|---|
| `predecessor_account_id` at `verify_deposit` call | relayer contract (passes `#[trusted_relayer]` check) |
| `signer_account_id` throughout the call chain | user who triggered the relayer contract |
| Fee recipient passed to `nbtc.mint` / `nbtc.burn` | **user** (wrong account) |

The relayer contract's address is never captured and threaded through the callback chain. The `nbtc` contract's `mint` and `burn` functions unconditionally credit `relayer_account_id` with `relayer_fee` tokens: [5](#0-4) [6](#0-5) 

The same pattern appears in `safe_mint_callback`, which also uses `env::signer_account_id()` for the NEAR storage-deposit refund: [7](#0-6) 

### Impact Explanation

Relayer contracts that hold the `UnrestrictedRelayer` role or are in the active relayer whitelist do not receive the fees they earn. Instead, the fees are credited to the original transaction signer (the user who triggered the relayer contract). This is a fee-accounting invariant violation: the party that performs the relayer work receives no compensation, while the user receives an unearned bonus. Over time this makes contract-based relaying economically unviable and breaks the incentive model for the relayer network.

### Likelihood Explanation

NEAR contract-based relayers are a standard production pattern (automated relaying, meta-transaction infrastructure, Omni Bridge integration). The bridge already anticipates contract-based callers — the `#[trusted_relayer]` macro is designed to check `predecessor_account_id`, which is the contract's address, not the signer's. Any user who can invoke a publicly callable trusted-relayer contract to process their deposit or withdrawal will receive the relayer fee instead of the relayer contract, with no special privileges required beyond triggering the relayer contract.

### Recommendation

Capture `env::predecessor_account_id()` at the entry point of `verify_deposit` / `verify_withdraw` (before any cross-contract calls) and thread it explicitly through the callback arguments, analogous to how the OVM fix introduced a designated fee wallet. For example:

```rust
// In verify_deposit_callback, add relayer_account_id as a parameter
// populated from predecessor_account_id at the time verify_deposit was called.
pub fn verify_deposit_callback(
    &mut self,
    recipient_id: AccountId,
    mint_amount: U128,
    protocol_fee: U128,
    relayer_fee: U128,
    relayer_account_id: AccountId,   // ← captured predecessor, not signer
    pending_utxo_info: PendingUTXOInfo,
    post_actions: Option<Vec<PostAction>>,
) -> PromiseOrValue<bool> { ... }
```

Pass this value through to `internal_mint_promise` and `verify_withdraw_burn_promise` instead of calling `env::signer_account_id()`.

### Proof of Concept

1. Bridge operators grant `UnrestrictedRelayer` to a publicly callable relayer contract `relayer-contract.near`.
2. User `alice.near` signs a transaction calling `relayer-contract.near::process_deposit(deposit_msg, tx_bytes, ...)`.
3. `relayer-contract.near` calls `satoshi-bridge.near::verify_deposit(...)`.
   - `predecessor_account_id` = `relayer-contract.near` → passes `#[trusted_relayer]` check.
   - `signer_account_id` = `alice.near`.
4. After the light-client callback resolves, `internal_mint_promise` fires with `relayer_account_id = env::signer_account_id() = alice.near`.
5. `nbtc.mint(alice.near, mint_amount, protocol_fee, alice.near, relayer_fee, ...)` is called.
6. `alice.near` receives both her minted nBTC **and** the relayer fee. `relayer-contract.near` receives nothing. [8](#0-7) [9](#0-8)
