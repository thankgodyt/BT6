### Title
`safe_mint` Mints nBTC to Bridge Before Recipient Registration Check, Permanently Locking User BTC Deposits - (File: contracts/nbtc/src/lib.rs)

---

### Summary

In `safe_mint`, `self.token.internal_deposit(&self.bridge_id, amount.into())` is called **before** checking whether the recipient account is registered. If the recipient is unregistered, the function returns `PromiseOrValue::Value(U128(0))` without transferring the already-minted tokens. The nBTC is permanently stuck in the bridge's own token balance, the total nBTC supply is inflated without a corresponding user receiving the tokens, and the underlying BTC UTXO is consumed — permanently locking the depositor's BTC.

---

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` follows this sequence:

```
Line 112: self.token.internal_deposit(&self.bridge_id, amount.into());
Line 114: if self.token.accounts.get(&account_id).is_none() {
Line 115:     return PromiseOrValue::Value(U128(0));
           }
``` [1](#0-0) 

`internal_deposit` is the NEAR FT standard's unconditional balance-and-supply increment. It increases both the bridge's nBTC balance and the global total supply by `amount` atomically and irreversibly within the call. The registration check on line 114 comes **after** this mutation. When the recipient is unregistered, the early return on line 115 exits without any `ft_transfer` or `ft_transfer_call`, so the minted tokens remain in `bridge_id`'s balance with no path back to the user. [2](#0-1) 

On the bridge side, the deposit flow marks the UTXO as consumed in `verified_deposit_utxo` when the deposit is processed: [3](#0-2) 

Once the UTXO is in `verified_deposit_utxo`, `request_refund_callback` blocks any refund for it: [4](#0-3) 

There is no `lost_found` entry created for the stuck nBTC (the `lost_found` map is only populated in `transfer_nbtc_callback` for failed `ft_transfer` cross-contract calls, not for the `safe_mint` early-return path): [5](#0-4) 

The result is a three-way inconsistency:
- The BTC UTXO is consumed (bridge custody, MPC-controlled).
- The nBTC total supply is inflated by `amount`.
- The user receives 0 nBTC and has no recovery path.

---

### Impact Explanation

**Critical — Significant permanent locking of user funds.**

Every `safe_mint` call where the recipient is unregistered results in:
1. The depositor's BTC being permanently locked in the bridge's MPC-controlled custody address (no refund possible once UTXO is verified).
2. The bridge's nBTC balance growing by `amount` — nBTC that is unbacked by any user claim. Over time, the bridge accumulates "orphaned" nBTC that represents real BTC locked in custody but owed to no one. A privileged operator could drain this surplus via `internal_withdraw_protocol_fee` or similar privileged paths, effectively stealing the depositor's BTC. [6](#0-5) 

---

### Likelihood Explanation

**Medium.** The trigger condition — recipient account not registered in the nBTC token contract — is reachable by any depositor:

- A user who sends BTC specifying a `recipient_id` that has never called `storage_deposit` on the nBTC contract.
- A user who unregisters (`storage_unregister`) their nBTC account between sending BTC on-chain and the relayer submitting the deposit proof.
- A griefing attacker who crafts a `DepositMsg` with a `recipient_id` they know is unregistered, then submits the proof themselves (relayer role is permissioned but the proof submission path exists). [7](#0-6) 

---

### Recommendation

Move the registration check **before** `internal_deposit`. If the recipient is unregistered, either:
- Revert the call (forcing the depositor to register first and retry via a separate mechanism), or
- Mint directly to the recipient using `mint_inner` only after confirming registration, or
- Record the amount in `lost_found` keyed to `account_id` so the user can recover after registering.

```rust
// Proposed fix: check registration before minting
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // no mint, no loss
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

### Proof of Concept

1. Alice sends 1 BTC on-chain to the bridge deposit address, with `DepositMsg { recipient_id: "alice.near", ... }`.
2. `alice.near` has never called `storage_deposit` on the nBTC contract (or has called `storage_unregister`).
3. Relayer submits the Merkle proof; bridge verifies it and calls `nbtc.safe_mint(alice.near, 100_000_000, None)`.
4. **Line 112 executes**: `internal_deposit(&bridge_id, 100_000_000)` — bridge's nBTC balance: `+100_000_000`, total supply: `+100_000_000`.
5. **Line 114 evaluates**: `accounts.get(&alice.near).is_none()` → `true`.
6. **Line 115 executes**: returns `U128(0)` — no transfer, no `lost_found` entry.
7. Bridge marks the UTXO in `verified_deposit_utxo` — refund path is now blocked.
8. Alice's 1 BTC is permanently locked in MPC custody. Alice holds 0 nBTC. The bridge holds 100,000,000 sat worth of nBTC with no legitimate owner. [1](#0-0) [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
