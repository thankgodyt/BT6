### Title
Incorrect Taylor-expansion error bound in `localSortitionNumSeats` causes wrong Peras non-persistent committee seat counts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract states `boundX` **must** equal `e^{|x|}` for correct error bounds. The argument `x = -lambda`, so `boundX` must be `e^{lambda}`. When `lambda > ln(3) ≈ 1.099`, the hardcoded `3` is an underestimate of the true bound, causing the error term to be too small and the Taylor comparison to terminate with an incorrect result. This produces a wrong non-persistent seat count for any voter whose `lambda` exceeds that threshold.

---

### Finding Description

In `localSortitionNumSeats`, the Poisson-based seat count is computed by comparing the normalized VRF output against a series of thresholds (`orders`) using a Taylor expansion of `e^x`:

```haskell
-- LS.hs lines 93-99
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- boundX (hardcoded)
      orders
      (-lambda)  -- x
``` [1](#0-0) 

The helper's own documentation is explicit:

```haskell
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

Inside `decideOne`, the error term is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX < e^{lambda}`, `errorTerm` is smaller than the true remainder of the Taylor series. The algorithm then makes premature decisions:

- `cmp >= acc' + errorTerm` fires too easily → `Stop` (returns current index, potentially too few seats)
- `cmp < acc' - errorTerm` fires too easily → `Below` (advances past a threshold, potentially too many seats)

`lambda` is defined as:

```haskell
lambda = fromRational $
  fromIntegral numNonPersistentVoters * voterStake / totalNonPersistentStake
``` [4](#0-3) 

`numNonPersistentVoters` is a `Word64` committee size. For a committee of 100 non-persistent voters and a voter holding 2% of non-persistent stake, `lambda = 100 × 0.02 = 2.0 > ln(3) ≈ 1.099`. The required `e^{lambda} = e^2 ≈ 7.39`, but `boundX = 3` — an underestimate by more than 2×. For larger committees or larger stake fractions the divergence grows exponentially.

The code itself acknowledges the uncertainty with an open TODO:

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
--
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
``` [5](#0-4) 

The reason `3` is safe in `checkLeaderNatValue` (Ledger) does **not** transfer here. In Praos, `x = -sigma × ln(1-f)` where `sigma` is a pool's stake fraction and `f ≈ 0.05`, giving `|x| ≤ 0.051` even for a 100%-stake pool, so `e^{|x|} ≈ 1.052` and `3` is a generous overestimate. In `localSortitionNumSeats`, `|x| = lambda` which scales with committee size and is unbounded above `ln(3)`.

---

### Impact Explanation

`localSortitionNumSeats` is called during vote eligibility verification in `WFALS.hs`:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing -> Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats -> pure $ WFALSNonPersistentMember ...
``` [6](#0-5) 

An incorrect seat count has two concrete consequences:

1. **Unauthorized vote acceptance / vote denial**: A voter whose true seat count is 0 may receive a non-zero count (or vice versa), bypassing or incorrectly applying the `ZeroNonPersistentSeats` rejection guard. This directly enables unauthorized Peras committee participation.

2. **Cross-node consensus divergence**: Because `lambda` is a deterministic function of on-chain stake, every honest node recomputes the same (wrong) seat count for the same voter. However, if any node runs a corrected version of the bound, it will compute a different seat count, causing nodes to disagree on vote validity — a Peras voting consensus failure.

The impact maps to: **Critical — bypass of Peras voting committee eligibility checks enabling unauthorized vote acceptance**, and **High — cross-node consensus divergence on vote validity**.

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is triggered whenever:

```
numNonPersistentVoters × (voterStake / totalNonPersistentStake) > 1.099
```

For any realistic Peras committee (e.g., 100 non-persistent seats), any voter holding more than ~1.1% of non-persistent stake triggers the bug. This covers the vast majority of non-persistent committee participants in a real deployment. No special privileges, key compromise, or adversarial input are required — the voter's own legitimate VRF output and stake fraction are sufficient.

---

### Recommendation

Replace the hardcoded `3` with the correct value `e^{lambda}`, computed from the actual `lambda`:

```haskell
import Cardano.Ledger.BaseTypes (fpExp)  -- or equivalent

expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (fpExp lambda)   -- correct: e^{|x|} = e^{lambda}
      orders
      (-lambda)
```

Alternatively, if `FixedPoint` does not expose `exp`, compute `e^{lambda}` via the same Taylor series used elsewhere in the codebase, or use a sufficiently large conservative upper bound derived from the maximum possible `lambda` (i.e., `numNonPersistentVoters`, when a single voter holds all non-persistent stake).

---

### Proof of Concept

For a committee with `numNonPersistentVoters = 100`, a voter with `voterStake / totalNonPersistentStake = 0.05` (5% of non-persistent stake):

- `lambda = 100 × 0.05 = 5.0`
- Required `boundX = e^5 ≈ 148.41`
- Actual `boundX = 3`
- Ratio: `3 / 148.41 ≈ 0.020` — the error term is underestimated by ~50×

At iteration `n`, `err' ≈ lambda^n / n!` and `errorTerm = err' × 3` instead of `err' × 148.41`. The algorithm will declare certainty (Stop or Below) roughly when `err' × 3 < epsilon` rather than when `err' × 148.41 < epsilon`, i.e., it terminates ~50× too early. For `lambda = 5`, the Taylor series for `e^{-5} ≈ 0.0067` converges slowly; premature termination at, say, 3 terms gives `1 - 5 + 12.5 = 8.5` (wildly wrong), and the comparison against `orders` thresholds will produce an incorrect seat count.
