### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Fraudulent Chain-Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally accepts every inbound `PerasCert` without performing any structural, cryptographic, or quorum-membership check. An unprivileged peer can craft a `PerasCert` for any block point and any round number, have it accepted as a `ValidatedPerasCert` carrying the full `perasWeight` boost, and thereby cause an honest node's chain-selection logic to prefer a non-canonical chain. This is the direct analog of the "zero-amount withdrawal" class: a parameter that should be validated (the certificate's authenticity and quorum proof) is accepted at face value with no guard.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for all inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
``` [1](#0-0) 

The sole production instance — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — implements this as:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [2](#0-1) 

No era-specific override exists; this catch-all is the only instance. The function never inspects `cert` beyond copying it into the result. It assigns the full `perasWeight` (default `PerasWeight 15`) to every certificate regardless of content.

The cert diffusion infrastructure (mirroring the vote diffusion path in `makePerasVotePoolWriterFromChainDB`) receives `PerasCert` objects from peers and calls `validatePerasCert` before storing them. Once stored, the `PerasWeightSnapshot` is updated via `addToPerasWeightSnapshot`: [3](#0-2) 

Chain selection then uses `weightedSelectView` → `weightBoostOfFragment` → `wsvTotalWeight`, comparing chains by `BlockNo + PerasWeight`: [4](#0-3) 

A fraudulently boosted block gains `PerasWeight 15` extra weight, which can tip chain selection toward a non-canonical fork.

The analog to the original bug is exact: `requestWithdrawal` accepted `_tokensToWithdraw = 0` because there was no `> 0` guard; `validatePerasCert` accepts every certificate because there is no validity guard at all.

### Impact Explanation

**High — Peras certificate check bypass enabling unauthorized certificate acceptance and chain-selection manipulation.**

A malicious peer sends a crafted `PerasCert{pcCertRound = r, pcCertBoostedBlock = p}` for any block point `p` it wishes to boost. `validatePerasCert` returns `Right` unconditionally. The honest node stores the cert, adds `PerasWeight 15` to point `p` in its `PerasWeightSnapshot`, and chain selection now prefers any chain containing `p` over a longer honest chain that lacks the boost. This satisfies the allowed impact: "Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" and "chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain."

### Likelihood Explanation

The cert diffusion mini-protocol is reachable by any peer that can establish a connection. No keys, stake, or privileged access are required to craft a `PerasCert` CBOR payload (the serialisation is two fields: a `Word64` round number and a block `Point`). The attack requires only a network connection and knowledge of a target block's hash and slot.

### Recommendation

`validatePerasCert` must reject any certificate that does not carry a verifiable quorum proof. At minimum, the implementation should:

1. Verify that `pcCertBoostedBlock` is a known, non-genesis block point.
2. Verify that `pcCertRound` corresponds to a valid Peras round for that block's slot.
3. Verify the cryptographic quorum proof (BLS aggregate signature or equivalent) over the `(round, block)` pair against the committee's public keys.

Until a real implementation exists, the catch-all instance should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), matching the conservative posture of `validatePerasVote` which rejects voters absent from the stake distribution. [5](#0-4)
