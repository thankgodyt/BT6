### Title
Attacker Can Front-Run `request_refund` to Register a Malicious Refund Address, Blocking or Redirecting Victim's BTC Refund - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `request_refund` function is publicly callable by any NEAR account. When a victim's `deposit_msg` carries no pre-authorized `refund_address` (`deposit_msg.refund_address == None`), the contract accepts any caller-supplied BTC address without verifying that the caller owns the deposit. Because the deduplication key (`utxo_storage_key = {txid}@{vout}`) is fully deterministic and publicly derivable, an attacker who observes the victim's pending `request_refund` transaction can race it with an identical call that substitutes the attacker's own BTC address. Whichever call lands first wins; the second is rejected with "Refund request already exists for this UTXO". If the attacker wins the race, the stored refund request points to the attacker's address, and after the `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention, `execute_refund` builds and MPC-signs a Bitcoin transaction paying the deposit UTXO to the attacker.

---

### Finding Description

**Root cause — no caller-ownership check on `refund_address` when `deposit_msg.refund_address` is `None`:**

`request_refund` is a public, payable function with no `#[trusted_relayer]` guard on the function itself: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-authorize a BTC address), this block is skipped entirely and any caller-supplied `refund_address` is accepted.

**Deterministic, publicly derivable deduplication key:**

The storage key that prevents duplicate refund requests is:

```rust
let utxo_storage_key = generate_utxo_storage_key(
    tx_id,
    u32::try_from(vout)...
);
``` [3](#0-2) 

`generate_utxo_storage_key` simply concatenates `{txid}@{vout}`: [4](#0-3) 

Both `txid` and `vout` are visible on the Bitcoin blockchain and in the victim's pending NEAR transaction. The attacker can compute the key before the victim's call is finalized.

**Collision check that enforces first-writer-wins:**

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [5](#0-4) 

**Stored `refund_address` is used verbatim in the refund PSBT:**

```rust
let refund_address = refund_request.refund_address.clone();
``` [6](#0-5) 

`build_refund_output` then constructs a Bitcoin output paying that address: [7](#0-6) 

The MPC network signs this PSBT without any further address validation.

---

### Impact Explanation

If the attacker's `request_refund` is processed before the victim's:

1. The refund request is stored with the attacker's BTC address.
2. The victim's call reverts ("Refund request already exists for this UTXO"), blocking the legitimate refund.
3. After `unsafe_refund_timelock_sec` elapses, anyone (including the attacker) calls `execute_refund`.
4. The bridge builds a PSBT paying the deposit UTXO to the attacker's address and submits it to the MPC for signing.
5. The attacker receives the victim's BTC.

The `unsafe_refund_timelock_sec` is a partial mitigation: it gives DAO/Operator a window to call `reject_refund`. However, if the operator is not monitoring continuously, or the attack is timed during off-hours, the attacker receives the funds. Even in the best case (operator rejects), the victim's funds are temporarily locked and require privileged operator intervention to unblock — a medium-severity stuck-state impact.

**Minimum guaranteed impact:** Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.
**Maximum impact:** Critical — theft of the victim's BTC deposit via unauthorized redirection of bridge-controlled funds.

---

### Likelihood Explanation

- `request_refund` is publicly callable with no role restriction.
- The `deposit_msg` is transmitted in plaintext in the victim's NEAR transaction, observable from any NEAR RPC node before the transaction is finalized.
- The `utxo_storage_key` is trivially computable from the public Bitcoin transaction.
- The attacker only needs to pay the storage deposit (`required_balance_for_request_refund`) — a small, fixed NEAR cost.
- NEAR does not have a gas-price auction, but within a single shard, transaction ordering is validator-controlled; an attacker submitting in the same block has a realistic chance of being ordered first.
- The attack is repeatable for every refund where `deposit_msg.refund_address` is `None`.

Likelihood: **Medium** (requires observing a pending NEAR transaction and winning a same-block race, which is feasible but not guaranteed).

---

### Recommendation

1. **Short term:** Require the caller of `request_refund` to prove ownership of the deposit. The simplest approach is to require that `deposit_msg.recipient_id == env::predecessor_account_id()` when `deposit_msg.refund_address` is `None`, so only the intended nBTC recipient can register a refund address for their own deposit.

2. **Long term:** Encourage users to always set `deposit_msg.refund_address` to a pre-authorized BTC address at deposit time. This eliminates the open `refund_address` parameter entirely and removes the attack surface. The bridge UI should make this the default flow.

---

### Proof of Concept

1. **Victim** calls `request_refund` with:
   - `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`
   - `refund_address = "bc1q...victim_btc_address..."`
   - `tx_bytes`, `vout`, `proof` for a real BTC deposit

2. **Attacker** observes the pending NEAR transaction, extracts `deposit_msg`, `tx_bytes`, `vout`, `proof`, and submits their own `request_refund` in the same block with:
   - `deposit_msg` = identical to victim's (passes the script_pubkey check in the callback)
   - `refund_address = "bc1q...attacker_btc_address..."`
   - Same `tx_bytes`, `vout`, `proof`

3. Attacker's transaction is processed first. `request_refund_callback` stores:
   ```
   refund_requests["{txid}@{vout}"] = RefundRequest {
       refund_address: "bc1q...attacker_btc_address...",
       ...
   }
   ``` [8](#0-7) 

4. Victim's transaction reaches the callback and panics: `"Refund request already exists for this UTXO"`. [5](#0-4) 

5. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund("{txid}@{vout}", None)`. The bridge builds a PSBT with `build_refund_output` paying the attacker's address and submits it to MPC for signing. [7](#0-6) 

6. MPC signs; attacker broadcasts the transaction and receives the victim's BTC.

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
