### Title
Uninitialized `chain_signatures_root_public_key` / `change_address` Read via `.expect()` Before `sync_chain_signatures_root_public_key_promise` Completes — (File: `contracts/satoshi-bridge/src/kdf.rs`, `contracts/satoshi-bridge/src/config.rs`)

### Summary

The bridge contract is deployed with `chain_signatures_root_public_key = None` and `change_address = None` by design. These fields are only populated after the operator calls `sync_chain_signatures_root_public_key_promise()` and its callback succeeds. However, every public bridge path that constructs or validates a deposit/withdrawal address calls `generate_public_key()` or `get_change_script_pubkey()`, both of which unconditionally `.expect()` on these `Option` fields. Any user who submits a deposit proof or initiates a withdrawal before that initialization step completes will trigger a contract panic, reverting the transaction and leaving their BTC temporarily unprocessable.

### Finding Description

`Contract::new()` explicitly enforces that both fields start as `None`: [1](#0-0) 

They are only set inside `sync_root_public_key_callback()`: [2](#0-1) 

Every path that needs to derive or verify a deposit address calls `generate_public_key()`, which unconditionally unwraps the `None` field: [3](#0-2) 

Similarly, every withdrawal PSBT validation path calls `get_change_script_pubkey()`, which unconditionally unwraps `change_address`: [4](#0-3) 

There is no guard (no `require!`, no `is_some()` check, no pause enforcement visible in the initialization path) that prevents a public caller from invoking `verify_deposit` or `ft_transfer_call` in the window between contract deployment and the successful completion of `sync_chain_signatures_root_public_key_promise`. This is the direct structural analog to the snap bug: a specific initialization method must run first, but all other methods read the resulting state without checking whether it was ever set.

### Impact Explanation

When a user submits a deposit proof (`verify_deposit`) before the root public key is synced, the light-client verification cross-contract call succeeds, but the subsequent callback panics at `generate_public_key` → `.expect("Missing chain_signatures_root_public_key")`. The panic reverts all state changes in that callback, so the UTXO is never marked in `verified_deposit_utxo`. The user's BTC is on-chain but nBTC is not minted; the user is stuck until the operator completes initialization and the user retries. For the withdrawal path, `ft_on_transfer` panics and NEP-141 refunds the tokens, so no token loss occurs there. The net impact is a publicly reachable panic-driven stuck state in the deposit path without direct theft.

**Impact level: Low** — publicly reachable invariant-violation / stuck-state / panic-driven fault in production bridge paths without direct theft.

### Likelihood Explanation

The window exists from contract deployment until `sync_chain_signatures_root_public_key_promise` is called and its callback succeeds. Any unprivileged NEAR account can call `verify_deposit` or `ft_transfer_call` immediately after deployment. A relayer submitting a proof in this window, or a user who sent BTC and is eagerly polling, will hit the panic. The likelihood is low in practice (the window is short under normal operations) but the entry path is fully permissionless.

### Recommendation

Mirror the fix described in the external report: introduce a wrapper that returns safe defaults (or an explicit error) when the optional state is not yet set, and guard every public entry point that depends on `chain_signatures_root_public_key` / `change_address` with an explicit `is_some()` check or a `require!` that produces a clear, non-panicking error message. Alternatively, enforce a pause on all deposit/withdrawal entry points until `sync_root_public_key_callback` has successfully populated both fields, then unpause as part of the initialization sequence.

### Proof of Concept

1. Deploy the bridge contract via `Contract::new(config)` — both `chain_signatures_root_public_key` and `change_address` are `None` by the enforced invariant.
2. Do **not** call `sync_chain_signatures_root_public_key_promise`.
3. As any unprivileged NEAR account, submit a valid BTC deposit proof to `verify_deposit` (or call `ft_transfer_call` with nBTC).
4. The light-client cross-contract call resolves successfully.
5. The callback invokes `generate_utxo_chain_address` → `generate_btc_public_key` → `generate_public_key`: [5](#0-4) 

6. `.expect("Missing chain_signatures_root_public_key")` panics on `None`.
7. All state changes in the callback are reverted; the UTXO is not marked verified; nBTC is never minted; the user's BTC is stuck until the operator completes initialization.

```rust
    pub fn sync_root_public_key_callback(&mut self) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_PUBLIC_KEY_RESULT) {
            let root_public_key =
                serde_json::from_slice::<PublicKey>(&result_bytes).expect("Invalid PublicKey");
            self.internal_mut_config().chain_signatures_root_public_key = Some(root_public_key);
            let change_address = self
                .generate_utxo_chain_address(env::current_account_id().as_str())
                .to_string();
            self.internal_mut_config().change_address = Some(change_address);
            true
        } else {
            false
        }
    }
```
