The key question is whether `request_refund` is truly open to any caller, and whether the `None`-refund-address path has a real exploit. Let me trace every guard precisely.

**`#[trusted_relayer]` scope analysis:**

The `request_refund` function sits in a `#[trusted_relayer]` impl block (bridge.rs:480), but it does **not** carry an individual `#[trusted_relayer]` attribute on the method itself. Comparing with other methods in the same file: `verify_refund_finalize` (line 602) and `remove_refund_pending_tx_id` (line 622) both carry individual `#[trusted_relayer]` attributes. Methods without individual attributes — `request_refund`, `reject_refund`, `execute_refund`, `withdraw_rbf`, `claim_lost_found`, `get_user_deposit_address` — are all publicly callable. The unauthorized-access test in `test_satoshi_bridge.rs` only tests methods with individual `#[trusted_relayer]` attributes, confirming the impl-level attribute does not gate all methods.

**The `None`-refund-address guard:** [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the `require!` block is skipped entirely. Any caller-supplied `refund_address` is accepted without restriction.

**`request_refund_callback` verification:** [2](#0-1) 

The callback verifies the transaction output's script matches the deposit address derived from `deposit_msg`. This is a cryptographic binding to the `deposit_msg` hash — but the `deposit_msg` is public (emitted via `LogDepositAddress` event when `get_user_deposit_address` is called). An attacker can observe the victim's `deposit_msg` on-chain and pass it verbatim.

**Timelock applied to the `None` path:** [3](#0-2) 

When `deposit_msg.refund_address` is `None`, `unsafe_refund_timelock_sec` (default: 14 days) applies. The code comment explicitly acknowledges this is the "unsafe" path and relies on DAO/Operator to reject suspicious requests. [4](#0-3) 

**`reject_refund` — victim has no self-help:** [5](#0-4) 

Only DAO/Operator can reject a refund request (unless the UTXO was already deposited). The victim themselves cannot cancel an attacker-submitted refund request. Additionally, the duplicate check in `request_refund_callback` (line 544-547) prevents the victim from submitting their own competing refund request after the attacker's is stored.

### Title
Unauthenticated `request_refund` allows attacker to redirect victim's BTC to attacker-controlled address — (`contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund` has no caller authentication. When a victim's `deposit_msg.refund_address` is `None`, any unprivileged attacker can submit a refund request for the victim's UTXO supplying the attacker's own BTC address. After `unsafe_refund_timelock_sec` (14 days default), the attacker calls `execute_refund` and the victim's BTC is permanently sent to the attacker's address. The victim has no on-chain mechanism to prevent or cancel this.

### Finding Description

**Step 1 — Attacker observes victim's `deposit_msg`:**
The victim calls `get_user_deposit_address(deposit_msg)` which emits a `LogDepositAddress` event containing the full `deposit_msg` (including `recipient_id`, `refund_address: None`, etc.). This is public on-chain data.

**Step 2 — Attacker calls `request_refund`:**
`request_refund` is publicly callable (no `#[trusted_relayer]` on the method). The attacker passes:
- The victim's `deposit_msg` (with `refund_address: None`)
- The attacker's own BTC address as `refund_address`
- The victim's BTC transaction bytes and a valid light-client proof [6](#0-5) 

**Step 3 — `None`-address guard is skipped:**
In `internal_request_refund`, the guard at lines 154-158 only fires when `deposit_msg.refund_address` is `Some`. With `None`, the attacker's address passes through unchecked.

**Step 4 — Callback stores attacker's address:**
`request_refund_callback` verifies the transaction output matches the deposit address derived from `deposit_msg` (which the attacker supplied correctly). It then stores a `RefundRequest` with `refund_address` = attacker's BTC address. [7](#0-6) 

**Step 5 — Victim is locked out:**
The duplicate check prevents the victim from submitting their own refund request for the same UTXO. [8](#0-7) 

**Step 6 — After 14 days, attacker calls `execute_refund`:**
`execute_refund` is also publicly callable. After `unsafe_refund_timelock_sec`, the attacker calls it and the bridge builds a PSBT paying the victim's BTC to the attacker's address. [9](#0-8) 

### Impact Explanation
The victim's BTC is permanently redirected to the attacker's Bitcoin address. Once `execute_refund` is called and the MPC signs the transaction, there is no recovery path. This is a direct, permanent theft of user funds — Critical impact.

### Likelihood Explanation
The attack requires:
1. Knowing the victim's `deposit_msg` — trivially available from on-chain events
2. Providing a valid light-client proof for the victim's BTC transaction — the transaction is on the Bitcoin blockchain and the proof is constructible by anyone
3. Attaching ~2 NEAR for storage — a small cost
4. Waiting 14 days without DAO/Operator intervention

The 14-day window is the only protection, and it relies entirely on off-chain monitoring. The victim has no on-chain recourse. Any lapse in DAO/Operator monitoring enables the theft.

### Recommendation
- Require the caller of `request_refund` to prove ownership of the `deposit_msg.recipient_id` NEAR account (e.g., require `env::predecessor_account_id() == deposit_msg.recipient_id`), OR
- When `deposit_msg.refund_address` is `None`, require the caller to be the `recipient_id` or a trusted relayer, OR
- Store the `predecessor_account_id` at `request_refund` time and only allow that account (or DAO/Operator) to call `execute_refund` for that request.

### Proof of Concept
```
1. Victim calls get_user_deposit_address({recipient_id: "victim.near", refund_address: None})
   → emits LogDepositAddress event with full deposit_msg
2. Victim sends BTC to the deposit address; transaction confirmed on Bitcoin
3. Attacker calls request_refund(
       deposit_msg = {recipient_id: "victim.near", refund_address: None},
       refund_address = "attacker_btc_address",
       tx_bytes = <victim's BTC tx>,
       proof = <valid merkle proof>
   ) with 2 NEAR attached
   → request_refund_callback stores RefundRequest{refund_address: "attacker_btc_address"}
4. Wait 14 days (unsafe_refund_timelock_sec)
5. Attacker calls execute_refund(utxo_storage_key = "<victim_txid>@0")
   → PSBT built paying victim's BTC to attacker_btc_address
   → MPC signs; attacker broadcasts; victim's BTC permanently stolen
```

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
