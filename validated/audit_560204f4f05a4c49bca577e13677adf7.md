### Title
Stale `btc_pending_verify_list` Entry After RBF Withdrawal Finalization — (`File: contracts/satoshi-bridge/src/nbtc/burn.rs`)

### Summary
In both `verify_withdraw_burn_callback` and `verify_active_utxo_management_burn_callback`, when finalizing an RBF (Replace-By-Fee) transaction, the code removes the **original** tx ID from `btc_pending_verify_list` but omits removing the **RBF** tx ID (`tx_id`) from the same list, even though the RBF tx's `BTCPendingInfo` is fully removed from `btc_pending_infos`. This is a direct analog to the BloomPool M-02 pattern: in the "partial" (RBF) branch, only one of two paired state fields is cleaned up, leaving the other stale.

### Finding Description

In `verify_withdraw_burn_callback` (`burn.rs` lines 102–134), the RBF branch is:

```rust
if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
    self.data_mut().rbf_txs.remove(original_tx_id);
    self.internal_unwrap_mut_account(&btc_pending_info.account_id)
        .btc_pending_verify_list
        .remove(original_tx_id);          // ← removes ORIGINAL tx
    let original_tx_btc_pending_info =
        self.internal_remove_btc_pending_info(original_tx_id);
    // ... fee accounting ...
} else {
    self.internal_unwrap_mut_account(&btc_pending_info.account_id)
        .btc_pending_verify_list
        .remove(&tx_id);                  // ← removes CURRENT tx (non-RBF path only)
    self.data_mut().rbf_txs.remove(&tx_id);
    // ...
}
// ...
self.internal_remove_btc_pending_info(&tx_id);  // ← removes RBF pending info
``` [1](#0-0) 

The `else` branch correctly removes `tx_id` from `btc_pending_verify_list`. The RBF branch removes only `original_tx_id` from `btc_pending_verify_list`, but `tx_id` (the RBF tx) is also in `btc_pending_verify_list` at this point — it was moved there when the last signature was collected — and is never removed. The pending info for `tx_id` is removed at line 143, leaving a dangling reference.

The identical omission exists in `verify_active_utxo_management_burn_callback`: [2](#0-1) 

The RBF tx enters `btc_pending_verify_list` during the signing phase (moved from `btc_pending_sign_ids` when the last signature is collected), so it is guaranteed to be present when the callback fires.

### Impact Explanation

After an RBF withdrawal is finalized, the account's `btc_pending_verify_list` retains a stale entry for the RBF tx ID whose `BTCPendingInfo` no longer exists. This violates the invariant that every entry in `btc_pending_verify_list` has a corresponding live `BTCPendingInfo`. Consequences:

1. **Inflated pending count**: If `pending_sign_count()` or `require_pending_sign_capacity` counts `btc_pending_verify_list` entries, the count is permanently inflated by one per completed RBF. Over multiple RBFs, a user's account could be permanently blocked from initiating new withdrawals or refunds.
2. **Panic-driven stuck state**: Any code path that iterates `btc_pending_verify_list` and calls `internal_unwrap_btc_pending_info` on each entry will panic on the stale ID, potentially freezing the account in an unrecoverable state without operator intervention.

**Impact**: Low–Medium — publicly reachable invariant violation and stuck-state fault in production bridge paths, without direct theft.

### Likelihood Explanation

Any user who initiates a standard RBF withdrawal (a normal, documented user action) and has it finalized by a relayer will trigger this bug. No privileged access is required. The trigger path is: `ft_on_transfer` → `internal_withdraw_rbf` → `sign_btc_transaction` → `verify_withdraw` → `verify_withdraw_burn_callback`. The bug fires on every successful RBF withdrawal finalization.

### Recommendation

In the RBF branch of both `verify_withdraw_burn_callback` and `verify_active_utxo_management_burn_callback`, add the removal of `tx_id` from `btc_pending_verify_list` alongside the removal of `original_tx_id`:

```rust
if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
    self.data_mut().rbf_txs.remove(original_tx_id);
    let account = self.internal_unwrap_mut_account(&btc_pending_info.account_id);
    account.btc_pending_verify_list.remove(original_tx_id);
    account.btc_pending_verify_list.remove(&tx_id);  // ← add this
    // ...
}
```

### Proof of Concept

1. Alice initiates a withdrawal via `ft_on_transfer` → `create_btc_pending_info`. Original tx ID = `T1`. `T1` enters `btc_pending_sign_ids`.
2. Relayer calls `sign_btc_transaction` for `T1`. `T1` moves to `btc_pending_verify_list`.
3. Alice calls `withdraw_rbf` → `internal_withdraw_rbf`. RBF tx ID = `T2`. `T2` enters `btc_pending_sign_ids`.
4. Relayer calls `sign_btc_transaction` for `T2`. `T2` moves to `btc_pending_verify_list`. Both `T1` and `T2` are now in `btc_pending_verify_list`.
5. Relayer calls `verify_withdraw` for `T2` → `verify_withdraw_burn_callback(tx_id = T2)`.
6. Inside the callback: `original_tx_id = T1` is removed from `btc_pending_verify_list`; `T2`'s `BTCPendingInfo` is removed from `btc_pending_infos`. But `T2` is **never** removed from `btc_pending_verify_list`.
7. Post-callback: `btc_pending_verify_list` contains stale `T2`; `btc_pending_infos` has no entry for `T2`. The invariant is broken. Any subsequent operation that reads `btc_pending_verify_list` and dereferences `T2` will panic, permanently corrupting Alice's account state.
