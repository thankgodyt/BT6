The critical code is in `contracts/satoshi-bridge/src/psbt.rs` at lines 242–243, and the workspace `Cargo.toml` confirms `overflow-checks = true` for the release profile. Here is the full analysis:

### Title
Panic-driven DoS in `check_withdraw_psbt` via u128 underflow at `min_received_amount` computation — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

An unprivileged user can trigger a contract panic by submitting a withdrawal PSBT where `gas_fee` is within the allowed bounds but large enough that `amount - withdraw_fee - gas_fee < config.min_change_amount`. The subtraction at line 243 underflows, and because `overflow-checks = true` is set in the release profile, the WASM runtime panics. This blocks all small withdrawals that satisfy this arithmetic condition.

### Finding Description

In `check_withdraw_psbt`, the contract computes:

```rust
let max_received_amount = amount - withdraw_fee - gas_fee;       // line 242
let min_received_amount = max_received_amount - config.min_change_amount; // line 243
``` [1](#0-0) 

The gas-fee bounds check that would reject an out-of-range `gas_fee` appears **after** these two subtractions:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [2](#0-1) 

So if a user submits a PSBT where `gas_fee = max_btc_gas_fee` (exactly at the allowed ceiling) and `amount = min_withdraw_amount`, and the config satisfies `min_withdraw_amount - withdraw_fee - max_btc_gas_fee < min_change_amount`, the subtraction at line 243 underflows before the gas-fee guard is ever evaluated.

The workspace `Cargo.toml` explicitly sets `overflow-checks = true` for the release profile:

```toml
[profile.release]
overflow-checks = true
``` [3](#0-2) 

This means the underflow is a **panic** in both debug and release WASM builds — not a silent wrap.

The public entry point is `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`. No privileged role is required. [4](#0-3) [5](#0-4) 

The user controls `gas_fee` indirectly by choosing the PSBT output amounts; `gas_fee = total_input_amount - total_output_amount` is computed from contract-validated UTXOs (inputs) minus user-supplied outputs. [6](#0-5) 

### Impact Explanation

With `overflow-checks = true`, the panic causes the entire `ft_on_transfer` call to abort. NEAR rolls back the FT transfer, so the user's nBTC is returned — **no funds are permanently lost**. However, any withdrawal attempt that hits this arithmetic condition will always panic, making those small-amount withdrawals permanently unreachable through the normal path. This is a publicly reachable panic-driven fault in a production bridge path.

Impact category: **Low** — publicly reachable invariant-violation / panic-driven fault without direct theft.

### Likelihood Explanation

Reachable only when the deployed config satisfies `min_withdraw_amount - withdraw_fee(min_withdraw_amount) - max_btc_gas_fee < min_change_amount`. Whether this holds depends on operator-set parameters. If the gap between `min_withdraw_amount` and `max_btc_gas_fee + min_change_amount` is small (common for BTC dust-limit configurations), the condition is easily triggered by any user who submits a PSBT with `gas_fee` near the ceiling.

### Recommendation

Reorder the gas-fee bounds check to execute **before** the `max_received_amount` / `min_received_amount` computations, or use saturating/checked arithmetic:

```rust
// Check gas_fee bounds FIRST
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ...")
);
// Then compute, using checked_sub to surface a clear error
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .expect("amount insufficient to cover fees");
let min_received_amount = max_received_amount
    .checked_sub(config.min_change_amount)
    .unwrap_or(0); // or require! with a clear message
```

Additionally, add a config-level invariant check at initialization/update time that enforces `min_withdraw_amount > withdraw_fee_max + max_btc_gas_fee + min_change_amount`.

### Proof of Concept

Fuzz parameters satisfying:
- `amount = min_withdraw_amount` (e.g., 2000 sat)
- `withdraw_fee = fee_on(amount)` (e.g., 100 sat)
- `gas_fee = max_btc_gas_fee` (e.g., 2000 sat)
- `min_change_amount = 546` (dust limit)

Then: `max_received_amount = 2000 - 100 - 2000` → underflow → panic before the gas-fee `require!` at line 252 is reached.

The user submits this via `ft_on_transfer` with a PSBT whose outputs sum to `total_input_amount - max_btc_gas_fee`. The contract panics at line 243. The FT transfer is rolled back; the withdrawal is permanently blocked for this amount/fee combination. [7](#0-6)
