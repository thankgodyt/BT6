### Title
`post_action_msg_templates` Whitelist Not Enforced When No Templates Are Configured for a Whitelisted Receiver — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

The `post_action_msg_templates` map is a control structure designed to restrict which `msg` values can be sent to whitelisted `post_action` receivers during a deposit. However, the enforcement is wrapped in an `if let Some(...)` guard: if a receiver is on the `post_action_receiver_id_white_list` but has **no entry** in `post_action_msg_templates`, the template check is skipped entirely and any arbitrary `msg` is accepted. This is a direct structural analog to the reported `selectedApplications` bug — a whitelist/allowlist exists and is consulted, but is silently bypassed when the controlling data structure is absent for a given entity.

---

### Finding Description

In `check_deposit_msg`, the receiver-id whitelist is enforced unconditionally:

```rust
if !self
    .data()
    .post_action_receiver_id_white_list
    .contains(&post_action.receiver_id)
{
    // reject
    return None;
}
``` [1](#0-0) 

Immediately after, the message-template check is gated on `if let Some(...)`:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validate msg against templates
    if !is_match {
        return None;
    }
}
// ← if no templates exist for this receiver, execution falls through here
//   with an unchecked, attacker-supplied msg
``` [2](#0-1) 

When the DAO or operator adds a receiver to `post_action_receiver_id_white_list` without simultaneously populating `post_action_msg_templates` for that receiver, the `msg` field of the `PostAction` is completely unchecked. The bridge will then call `ft_transfer_call(receiver_id, amount, <arbitrary_attacker_msg>)` on the nBTC contract after minting.

The two whitelists live in `ContractData`:

```rust
pub post_action_receiver_id_white_list: IterableSet<AccountId>,
pub post_action_msg_templates: IterableMap<AccountId, HashSet<String>>,
``` [3](#0-2) 

The `post_action_msg_templates` map is the analog to `selectedApplications` in the reference report: it is the authoritative list of permitted message shapes, but it is never enforced when absent for a given receiver.

---

### Impact Explanation

A whitelisted receiver contract (e.g., a DeFi lending protocol, AMM, or staking contract) that accepts `ft_transfer_call` may interpret the `msg` field to determine the operation to perform — for example, which pool to deposit into, which address to credit, or which action to execute. With an unchecked `msg`, an attacker can:

1. Trigger unintended operations in the receiver contract using the attacker's own freshly minted nBTC (e.g., manipulate shared pool state, set an arbitrary beneficiary address inside the receiver's logic, or invoke a privileged code path that the template restriction was meant to block).
2. Bypass the bridge's stated policy that `post_action_msg_templates` restricts the set of permissible cross-contract call shapes — a direct bypass of bridge limits/policies.

This matches the **Medium** impact class: *Bypass of bridge limits or policies*.

---

### Likelihood Explanation

The likelihood is **Medium**. The precondition is that at least one receiver is on `post_action_receiver_id_white_list` with no corresponding entry in `post_action_msg_templates`. This is a realistic operational state: the DAO/operator may add a receiver to the whitelist as a first step, intending to configure templates later, or may simply not be aware that the absence of templates disables enforcement. Any unprivileged depositor can then exploit the gap immediately by crafting a `DepositMsg` with an arbitrary `msg` targeting that receiver.

---

### Recommendation

Change the `if let Some(...)` guard to a hard enforcement: if a receiver is on the whitelist but has no templates configured, reject the `post_action` rather than silently accepting any `msg`. Concretely:

```rust
// Require templates to be configured; absence of templates = no msg is permitted.
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .ok_or(/* emit InvalidPostAction: no templates configured */)?;

let is_match = /* validate msg against msg_templates */;
if !is_match {
    // emit InvalidPostAction: unsupported msg
    return None;
}
```

This mirrors the fix applied in the reference report: enforce the controlling list unconditionally, not only when it happens to be populated.

---

### Proof of Concept

1. DAO calls `add_post_action_receiver_id_to_white_list(receiver_id: "defi.near")` but does **not** call `add_post_action_msg_template("defi.near", ...)`.
2. Attacker sends BTC to the bridge deposit address derived from:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi.near",
       "amount": "100000",
       "msg": "{\"action\":\"withdraw\",\"to\":\"attacker.near\"}"
     }]
   }
   ```
3. Relayer calls `verify_deposit(proof, deposit_msg)`. The bridge mints nBTC to `attacker.near`, then calls `check_deposit_msg`. The receiver-id check passes (it is whitelisted). The template check at line 117 evaluates `post_action_msg_templates.get("defi.near")` → `None`, so the `if let Some` body is skipped entirely. `check_deposit_msg` returns `Some(post_actions)`.
4. The bridge executes `ft_transfer_call("defi.near", 100000, "{\"action\":\"withdraw\",\"to\":\"attacker.near\"}")` on the nBTC contract.
5. `defi.near` receives the call with the attacker-crafted `msg` and executes the unintended operation. [2](#0-1)
