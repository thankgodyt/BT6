Audit Report

## Title
Unvalidated Zero EVM Recipient Address Causes Permanent Freezing of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` in the NEAR bridge contract accepts `address(0)` as a valid EVM recipient because the only validation checks the chain kind, not the address value. Once tokens are locked on NEAR and an MPC signature is produced over a payload encoding `recipient = address(0)`, there is no on-chain path to cancel or recover the transfer. For ERC20/bridge tokens the EVM `finTransfer` reverts (mint to zero address), leaving tokens permanently frozen on NEAR. For native ETH transfers, the low-level call to `address(0)` succeeds and ETH is permanently burned.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

`OmniAddress::is_zero()` exists in `near/omni-types/src/lib.rs` and correctly handles all chain variants including EVM addresses, but is never invoked here: [2](#0-1) 

A user passes `recipient = "eth:0x0000000000000000000000000000000000000000"`. The chain check passes (`Eth != Near`), tokens are locked, and a `TransferMessage` with `recipient = OmniAddress::Eth(H160::ZERO)` is stored in `pending_transfers`: [3](#0-2) 

The relayer calls `sign_transfer`, which builds a `TransferMessagePayload` with `recipient = address(0)` and requests an MPC signature. On EVM, `finTransfer` sets `completedTransfers[nonce] = true` before the transfer: [4](#0-3) 

For bridge tokens, `IBridgeToken(tokenAddress).mint(address(0), amount)` is called, which reverts via OpenZeppelin's `_mint` zero-address guard. The revert rolls back `completedTransfers`, so the nonce is not consumed. However, the NEAR `pending_transfers` entry remains with `recipient = address(0)` and no cancel or admin-recovery function exists (confirmed: no `pending_transfers.remove` or `fn cancel` anywhere in the NEAR contract). Re-signing via `sign_transfer` on the same `transfer_id` produces the identical payload — tokens are permanently frozen.

For native ETH (`tokenAddress == address(0)`), the path is:
```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
``` [5](#0-4) 

A low-level call to `address(0)` with ETH succeeds (address(0) has no code; EVM treats it as an EOA). The nonce is consumed and ETH is permanently burned.

## Impact Explanation
Permanent freezing (ERC20/bridge tokens) or permanent burning (native ETH) of user funds. Tokens are locked on NEAR with no on-chain recovery path. This directly matches the allowed critical impact: *"permanent freezing of bridged funds across NEAR, EVM."*

## Likelihood Explanation
The entry path is fully unprivileged — any user can call `ft_transfer_call` on NEAR with an arbitrary recipient string. A user may accidentally supply a zero address (copy-paste error, uninitialized field) or do so intentionally. No validation exists at any layer: NEAR `init_transfer`, MPC signing, or EVM `finTransfer`. The relayer has no on-chain incentive or mechanism to filter zero-address transfers before signing.

## Recommendation
Add a zero-address guard in `init_transfer` immediately after the chain-kind check:

```rust
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipient.as_ref()
);
```

Optionally add a corresponding guard in EVM `finTransfer`:

```solidity
if (payload.recipient == address(0)) revert InvalidRecipient();
```

## Proof of Concept

1. User calls `ft_transfer_call` on NEAR with:
   ```json
   {"InitTransfer": {"recipient": "eth:0x0000000000000000000000000000000000000000", "fee": "0", ...}}
   ```
2. `init_transfer` checks `Eth != Near` → passes. Tokens locked. `TransferMessage { recipient: OmniAddress::Eth(H160::ZERO) }` stored in `pending_transfers`.
3. Relayer calls `sign_transfer(transfer_id, fee_recipient, fee)` → MPC signs payload with `recipient = 0x000…000`.
4. Relayer submits signed payload to EVM `finTransfer`.
5. **ERC20 path**: `IBridgeToken(tokenAddress).mint(address(0), amount)` → reverts. Nonce rolled back. NEAR transfer permanently frozen.
6. **Native ETH path**: `address(0).call{value: amount}("")` → succeeds. Nonce consumed. ETH permanently burned.
7. No cancel function exists on NEAR; re-signing produces the same zero-address payload.
