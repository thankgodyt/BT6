### Title
Peras Quorum Check Bypassed by Absolute-vs-Relative `PerasVoteStake` Unit Mismatch — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` `Rational` directly against the relative quorum threshold (`3/4 + 2/100 = 0.77`). The code itself documents that **there is no consensus on whether `PerasVoteStake` carries absolute or relative (normalised) stake**. If the `PerasVoteStakeDistr` supplied at runtime is populated with absolute lovelace values, any pool whose absolute stake exceeds `0.77` — effectively every registered pool — can forge a Peras certificate with a single vote, bypassing the quorum requirement entirely and corrupting chain selection.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee …
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }

-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. …
-- Under the current implementation of 'PerasParams', this function only
-- makes sense when both values are relative (normalized) values, so we
-- should either normalize the 'PerasVoteStake' before calling this function,
-- or change this function to accept a stake distribution and perform the
-- normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The default `PerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`, so the combined threshold is `0.77`. [2](#0-1) 

**Production call path:**

`makePerasVotePoolWriterFromChainDB` (the live writer used by the node) calls `validatePerasVote mkPerasParams sd vote` where `sd :: PerasVoteStakeDistr` is read from an STM cell:

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

The degenerate `validatePerasVote` instance simply looks up the stake from the distribution and stores it verbatim in `ValidatedPerasVote.vpvVoteStake` — no normalisation is performed:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

That `vpvVoteStake` is then summed and fed directly into `stakeAboveThreshold` inside `updateCandidateVoteState → votesReachQuorum`:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner …
``` [5](#0-4) 

**The mismatch:** `mkPerasParams` sets the quorum threshold as a relative fraction (`0.77`). If the `PerasVoteStakeDistr` is populated with absolute lovelace values — which the code explicitly admits is an open question — then a pool holding, say, `1_000_000` lovelace would have `PerasVoteStake = 1000000`, and `1000000 >= 0.77` is trivially `True`. A single vote from that pool would immediately forge a certificate.

---

### Impact Explanation

A Peras certificate forged from negligible real stake is accepted by `validatePerasCert` (the current degenerate instance always returns `Right`) and stored in the `PerasVoteDB`. When the ChainDB processes it, the boosted block receives `perasWeight = 15` extra chain weight. Honest nodes running the standard chain-selection rule will prefer the artificially boosted block over an equally long but unboosted honest chain, allowing an adversary to steer chain selection toward a non-canonical tip without holding a stake majority. This is a **High** impact chain-selection bug: an unprivileged peer with any registered stake can make honest nodes prefer a non-canonical chain beyond the intended security assumptions of Peras.

---

### Likelihood Explanation

The code comment states explicitly that **"there is no consensus from researchers/engineers"** on the absolute-vs-relative question. The `stakeAboveThreshold` TODO acknowledges the assumption is unverified. Any implementation of `getStakeDistrSTM` that populates `PerasVoteStakeDistr` with raw ledger lovelace values (a natural first implementation) triggers the bug immediately. The entry path requires only a registered stake pool and the ability to send votes over the Peras vote-diffusion mini-protocol — both available to any unprivileged network peer.

---

### Recommendation

1. **Enforce normalisation at the boundary.** `stakeAboveThreshold` should accept the total stake of the distribution and normalise internally: `stake / totalStake >= quorumThreshold + safetyMargin`.
2. **Alternatively**, change `PerasVoteStake` to a newtype that can only be constructed via a normalising smart constructor that takes the full distribution, making it impossible to pass absolute values.
3. **Resolve the open question** documented in the `NOTE` comment before any production deployment of Peras voting.

---

### Proof of Concept

```
Setup (private testnet):
  - Pool P registered with absolute stake S = 1_000_000 lovelace
  - PerasVoteStakeDistr populated with absolute values:
      { P -> PerasVoteStake (1000000 % 1) }

Attack:
  1. Adversary sends one PerasVote for an adversarial block B_adv
     from pool P via the Peras vote-diffusion mini-protocol.
  2. Node calls validatePerasVote mkPerasParams sd vote
       → returns Right (ValidatedPerasVote { vpvVoteStake = 1000000 })
  3. updateCandidateVoteState calls votesReachQuorum cfg [vote]
       → stakeAboveThreshold cfg (PerasVoteStake 1000000)
       → 1000000 >= 0.77  ✓  (True)
  4. forgePerasCert is called → ValidatedPerasCert { vpcCertBoost = 15 }
  5. Certificate stored; B_adv gains +15 chain weight.
  6. Honest nodes select B_adv over the canonical tip.

-- | Create a pool writer from the 'ChainDB'.
-- This properly handles the produced certs by letting the ChainDB take care
-- of them (see 'ChainDB.addPerasVoteWithAsyncCertHandling').
makePerasVotePoolWriterFromChainDB ::
  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  -- | This is needed for validating votes (since its during the validation of
  -- votes that we give them a verified weight. In the future, we won't read it
  -- from the stake distr directly, but rather use the committee selection data)
  STM m PerasVoteStakeDistr ->
  ChainDB m blk ->
  ObjectPoolWriter (PerasVoteId blk) (PerasVote blk) m
makePerasVotePoolWriterFromChainDB systemTime getStakeDistrSTM chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasVoteId
    , opwAddObjects = \votes ->
        processVotes
          systemTime
          (ChainDB.getPerasVoteIds chainDB)
          -- TODO: in the future we won't need just the stake distribution for
          -- validating votes, but also the whole committee selection context
          -- (containing vote weights of committee members = voters)
          (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- votes to the ChainDB and ignore the returned promise.
          -- The async action (if any) is still launched and executed behind the
          -- scenes even though we drop the promise.
          (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
          votes
    , opwHasObject = do
        voteIds <- ChainDB.getPerasVoteIds chainDB
        pure $ \voteId -> Set.member voteId voteIds
    }

updateCandidateVoteState cfg vote oldState =
  let
    newVoteTally = updateTargetVoteTally vote (ptvsVoteTally oldState)
    voteList = forgetArrivalTime <$> Map.elems (ptvtVotes newVoteTally)
   in
    case votesReachQuorum cfg voteList of
