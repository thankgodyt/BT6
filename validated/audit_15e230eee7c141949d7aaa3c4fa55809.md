### Title
Peras Vote and Certificate Validation Stubs Unconditionally Accept Any Peer-Supplied Vote or Certificate - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a function that unconditionally returns `Right` for every certificate, and `validatePerasVote` as a function that performs only a stake-distribution membership lookup with no cryptographic signature check. Both functions are called on the hot inbound path from the ObjectDiffusion miniprotocol. An unprivileged peer can therefore inject an arbitrary crafted certificate or a forged vote for any known voter, bypassing all validity checks, causing the node to store and act on fraudulent Peras consensus objects.

---

### Finding Description

The catch-all `BlockSupportsPeras` instance in `SupportsPeras.hs` provides two stub validation functions that are explicitly marked as incomplete:

**`validatePerasCert` — always accepts:**
```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function returns `Right` for every input, regardless of whether the certificate carries a valid aggregate BLS signature, a valid quorum of votes, or any other structural requirement.

**`validatePerasVote` — no signature check:**
```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This only checks that the claimed `PerasVoterId` appears in the stake distribution. It does not verify the BLS vote signature (`pvSignature` in the concrete `V1.PerasVote` type). Any peer who knows a legitimate voter's ID can forge a vote on their behalf.

Both stubs are used directly on the inbound network path. `processVotes` in `ObjectPool/PerasVote.hs` calls `validatePerasVote` inside an STM transaction for every incoming vote batch:
```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processCerts` in `ObjectPool/PerasCert.hs` calls `validatePerasCert` for every incoming certificate batch:
```haskell
(validatePerasCert mkPerasParams)
``` [4](#0-3) 

The `processCerts` function's only other guard is a round-number deduplication check (`Set.member` on `PerasRoundNo`), which only prevents a second certificate for the same round — it does not prevent the first fraudulent certificate from being accepted:
```haskell
let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
``` [5](#0-4) 

The `PerasVoteId` used for vote deduplication is `(PerasRoundNo, PerasVoterId)` — it does not include the block being voted for:
```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [6](#0-5) 

This means an attacker who sends N forged votes (one per known voter ID) for a target block in a given round will have all N votes pass `validatePerasVote`, pass the deduplication filter (since none are yet in the DB), and be counted toward quorum in `updatePerasRoundVoteStates`. Once quorum is reached, a `ValidatedPerasCert` is forged and stored in `PerasCertDB`, boosting the attacker's chosen chain in chain selection.

---

### Impact Explanation

**Chain selection corruption via fraudulent Peras certificate (High).**

A fraudulent certificate stored in `PerasCertDB` is returned by `getWeightSnapshot` and used to assign Peras boost weight to the attacker's chosen block. This directly influences chain selection, potentially causing an honest node to prefer a non-canonical or adversarially-chosen chain over the honest chain. The `validatePerasCert` stub makes this even more direct: a single crafted certificate message is sufficient without needing to forge individual votes.

---

### Likelihood Explanation

**High.** The attack requires only:
1. Knowledge of legitimate voter IDs (publicly derivable from the stake distribution, which is public).
2. The ability to send ObjectDiffusion protocol messages to the target node (any peer connection).
3. No cryptographic material (no private keys, no VRF keys).

The stub is the catch-all instance for all block types (`instance StandardHash blk => BlockSupportsPeras blk`), explicitly noted as a placeholder for all blocks to compile. There is no more specific production instance that overrides it.

---

### Recommendation

1. Implement `validatePerasCert` to verify the aggregate BLS signature over the claimed election ID and candidate block, and to confirm that the signers' combined stake exceeds the quorum threshold.
2. Implement `validatePerasVote` to verify the individual BLS vote signature (`pvSignature`) against the voter's public key (derivable from the committee selection data), in addition to the existing stake lookup.
3. Until these are implemented, the ObjectDiffusion inbound handlers for Peras votes and certificates should not be enabled on any node that participates in chain selection.

---

### Proof of Concept

**Fraudulent certificate injection (single message):**

1. Attacker connects to a target node via the ObjectDiffusion miniprotocol for Peras certificates.
2. Attacker sends a `PerasCert` with `pcCertRound = R` (any round not yet in the node's `PerasCertDB`) and `pcCertBoostedBlock = <attacker's chosen block point>`.
3. `processCerts` reads `alreadyInDb`; round `R` is absent, so the cert passes the deduplication filter.
4. `validatePerasCert mkPerasParams cert` is called and unconditionally returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })`.
5. The fraudulent `ValidatedPerasCert` is stored in `PerasCertDB` via `addCert`.
6. `getWeightSnapshot` now returns a boost for the attacker's block, influencing chain selection.

**Fraudulent quorum via forged votes (no private keys needed):**

1. Attacker reads the public stake distribution to enumerate voter IDs with positive stake.
2. Attacker sends a batch of `PerasVote` messages, one per voter ID, all for round `R` and the attacker's chosen block, with arbitrary (invalid) `pvSignature` fields.
3. `processVotes` reads `alreadyInDb`; none of the vote IDs `(R, voterId_i)` are present.
4. Each vote passes `validatePerasVote` (only stake lookup, no signature check).
5. `implAddVote` calls `updatePerasRoundVoteStates` for each vote; once cumulative stake exceeds the quorum threshold, a `ValidatedPerasCert` is forged and stored.
6. The fraudulent certificate boosts the attacker's block in chain selection.
