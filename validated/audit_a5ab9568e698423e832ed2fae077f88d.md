Audit Report

## Title
Partial `ft_on_transfer` Refund Permanently Freezes Bridged Tokens in Bridge Contract - (`near/omni-bridge/src/lib.rs`)

## Summary
`is_refund_required` uses a binary check (`amount.0 == 0`) that only distinguishes full rejection from any non-zero result. When a recipient's `ft_on_transfer` returns a partial refund (used some but not all tokens), the NEP-141 token contract silently returns the unused portion to the bridge's balance, the bridge emits `FinTransferEvent` as if the transfer fully succeeded, and the residual tokens are permanently frozen with no recovery path. The integration test suite explicitly documents this behavior with `expected_locker_balance: 1`.

## Finding Description
`is_refund_required` at `near/omni-bridge/src/lib.rs:1784–1804` reads the promise result of `ft_transfer_call` and returns `true` only when `amount.0 == 0`:

```rust
amount.0 == 0
```

In NEP-141, `ft_resolve_transfer` returns the amount of tokens actually used by the receiver. A value of `0` means the receiver used nothing (full rejection). Any non-zero value means the receiver used that many tokens — but it does not mean the receiver used *all* of them. If the receiver used 998 out of 999 sent tokens, `ft_resolve_transfer` returns `998`, `is_refund_required` sees `998 != 0`, returns `false`, and the bridge proceeds to the success path in `fin_transfer_send_tokens_callback` (L1719–1746), emitting `FinTransferEvent`. Meanwhile, the token contract has already refunded the 1 unused token back to the bridge's balance. The bridge has no code in the success path to forward this residual.

The same binary check is present in:
- `resolve_fast_transfer` (L906): `if Self::is_refund_required(is_ft_transfer_call)`
- `resolve_utxo_fin_transfer` (L1025): `if Self::is_refund_required(is_ft_transfer_call)`

The integration test at `near/omni-tests/src/fin_transfer.rs:533–545` explicitly proves the behavior: with `amount=1000`, `fee=1`, and `ft_on_transfer` returning `U128(1)` (1 token refunded), the test asserts `expected_locker_balance: 1` — the bridge retains 1 token permanently.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**. The foreign-chain sender has already irrevocably burned or locked their tokens before `fin_transfer` is called. After `FinTransferEvent` is emitted, the transfer ID is consumed and cannot be replayed. The residual tokens accumulate in the bridge contract's token balance with no withdrawal, sweep, or recovery function. For non-deployed tokens (e.g., USDC, WETH), the tokens are frozen. For bridge-minted tokens, the returned tokens sit in the bridge's balance as orphaned supply. In both cases the user suffers a direct, unrecoverable loss of bridged funds, matching the Critical impact class of permanent freezing of bridged funds.

## Likelihood Explanation
The trigger is any `fin_transfer` or `fast_fin_transfer` call with a non-empty `msg` field directed at a recipient contract that implements standard NEP-141 partial-fill behavior: slippage protection, minimum output enforcement, or insufficient liquidity. This is a documented and supported use case (DeFi integrations). The `msg` field is user-controlled and relayer-submitted, making this reachable by any unprivileged bridge user without any special role or privilege. It is not an edge case — it is the normal behavior of any production DEX or AMM integrated via `ft_transfer_call`.

## Recommendation
Replace the binary `is_refund_required` with a function that returns the actual used amount. In `fin_transfer_send_tokens_callback`, `resolve_fast_transfer`, and `resolve_utxo_fin_transfer`, after confirming the transfer is not fully rejected, compare the used amount against the sent amount. If a shortfall exists, forward the residual to the original recipient (or the transfer sender as a fallback) via an additional `ft_transfer` before emitting the finalization event:

```rust
let used = get_used_amount(); // read promise result as U128
let sent = transfer_message.amount_without_fee();
if used == 0 {
    // full rejection: revert
} else {
    let residual = sent - used.0;
    if residual > 0 {
        // ft_transfer residual back to recipient or original sender
    }
    // emit FinTransferEvent
}
```

## Proof of Concept
The existing integration test at `near/omni-tests/src/fin_transfer.rs:533–545` is a direct, reproducible proof:

1. Call `fin_transfer` with `amount=1000`, `fee=1`, `msg=<non-empty>` targeting a mock receiver that returns `U128(1)` from `ft_on_transfer`.
2. Bridge calls `ft_transfer_call(recipient, 999, msg)`.
3. Receiver uses 998 tokens, returns `U128(1)` to refund.
4. Token contract's `ft_resolve_transfer` refunds 1 token to bridge; returns `998` as used amount.
5. `is_refund_required` sees `998 != 0`, returns `false`.
6. `fin_transfer_send_tokens_callback` emits `FinTransferEvent` — transfer finalized.
7. Test asserts `expected_locker_balance: 1` — 1 token is permanently frozen in the bridge.
8. No recovery function exists; the foreign-chain transfer is already consumed.
