### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.sol`'s `initTransfer` function locks native ERC-20 tokens via `safeTransferFrom` and immediately emits an `InitTransfer` event using the caller-supplied `amount` parameter verbatim, with no pre/post balance check. For fee-on-transfer tokens, the contract receives `amount − transfer_fee` but broadcasts `amount` as the locked quantity. The NEAR bridge reads this event value and mints or releases the full `amount` to the recipient, permanently under-collateralizing the EVM escrow.

---

### Finding Description

In the native ERC-20 lock path of `initTransfer` (reached when `customMinters[tokenAddress] == address(0)` and `isBridgeToken[tokenAddress] == false`):

```solidity
// evm/src/omni-bridge/contracts/OmniBridge.sol  lines 407-411
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-controlled
);
```

Immediately after, the event is emitted with the same caller-supplied value:

```solidity
// lines 427-436
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,          // no actual-received check
    fee,
    nativeFee,
    recipient,
    message
);
```

No snapshot of `balanceOf(address(this))` is taken before the transfer, and no comparison against the post-transfer balance is performed. The `amount` written into the event is therefore the requested amount, not the actually received amount.

The identical pattern exists in `starknet/src/omni_bridge.cairo` `init_transfer` (lines 304–306 and 316–330): `transfer_from(caller, get_contract_address(), amount.into())` followed by emitting `amount` with no balance delta check.

---

### Impact Explanation

The `InitTransfer` event is the authoritative cross-chain message consumed by the NEAR prover. The NEAR bridge's `fin_transfer` path mints or releases exactly the `amount` field from the proven event to the recipient. If the EVM contract received `amount − fee_delta` but emitted `amount`, the NEAR side releases `amount`, creating a permanent shortfall of `fee_delta` tokens in the EVM escrow per transaction. Repeated transfers with a fee-on-transfer token drain the escrow below its liabilities, eventually preventing legitimate withdrawals — a direct loss of bridged funds.

**Impact: Critical** — escrow mis-accounting leading to insolvency and loss of bridged funds.

---

### Likelihood Explanation

The `initTransfer` function imposes no check that the token is whitelisted or registered; any ERC-20 address is accepted on the EVM side. A fee-on-transfer token becomes exploitable the moment it is mapped on the NEAR side (e.g., via admin `addCustomToken` or any future permissionless registration path). Several real-world tokens (deflationary tokens, tokens with configurable transfer taxes) exhibit this behavior. A single registered fee-on-transfer token is sufficient to trigger continuous escrow drain with every user transfer.

**Likelihood: Low-Medium** — requires a fee-on-transfer token to be registered with the bridge, which is currently admin-gated, but the code contains no defense against it.

---

### Recommendation

Capture the contract's token balance before and after the `safeTransferFrom` call and use the delta as the canonical locked amount in both internal accounting and the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
require(actualReceived == amount, "FEE_ON_TRANSFER_NOT_SUPPORTED");
// or: use actualReceived as the amount in the event
```

Apply the same fix to `starknet/src/omni_bridge.cairo` `init_transfer`.

---

### Proof of Concept

1. Admin registers a fee-on-transfer ERC-20 token `FOT` (2% fee per transfer) on both EVM and NEAR sides.
2. Attacker (or any user) calls `initTransfer(FOT, 1_000_000, 0, 0, "recipient.near", "")`.
3. `safeTransferFrom` moves `1_000_000` tokens; the token contract retains 2% (`20_000`) as a fee; the bridge receives `980_000`.
4. `InitTransfer` event is emitted with `amount = 1_000_000`.
5. Relayer submits the EVM proof to NEAR `fin_transfer`; NEAR mints/releases `1_000_000` FOT-equivalent tokens to `recipient.near`.
6. EVM escrow holds `980_000` but NEAR has issued claims for `1_000_000` — a `20_000`-token shortfall per transaction.
7. After `N` such transfers the escrow is insolvent; the last `N × 20_000` tokens worth of NEAR-side claims cannot be redeemed. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
