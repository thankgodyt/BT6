### Title
Cross-Network Orchard Bundle Accepted Without Binding-Signature Network Check, Causing Temporary UTXO Lock — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`, `psbt_wrapper.rs`)

---

### Summary

An unprivileged user can supply a `ChainSpecificData.orchard_bundle_bytes` that is a structurally valid Orchard bundle created for a **different network** (e.g., ZcashMainnet bundle submitted to a ZcashTestnet bridge). The bridge's `extract_orchard_bundle` and `validate_orchard_bundle` functions accept it, the PSBT is committed, and the bridge's ZEC UTXOs are marked unavailable. The resulting transaction is **rejected by Zcash nodes** because the Orchard `binding_sig` was computed over the wrong network's `consensus_branch_id`. Recovery requires operator intervention via the cancel mechanism.

---

### Finding Description

**Entry point** — `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `ft_on_transfer_callback`: [1](#0-0) 

The callback extracts `orchard_bundle_bytes` from the user-supplied `ChainSpecificData` and passes them directly to `PsbtWrapper::new`: [2](#0-1) 

**`PsbtWrapper::new`** calls `orchard_policy::extract_orchard_bundle`: [3](#0-2) 

**`extract_orchard_bundle`** uses `read_v5_bundle`, which is a **network-agnostic** binary deserializer — it reads the Orchard bundle format without any network identifier check: [4](#0-3) 

The only checks performed are: action count == 1, output recoverable with the hardcoded all-zeroes bridge OVK, and non-zero value. No network binding is verified.

**`validate_orchard_bundle`** (called from `check_psbt_chain_specific`) only checks recipient address bytes and value balance: [5](#0-4) 

It does **not** verify the Orchard `binding_sig` against the configured chain's `consensus_branch_id`. The `binding_sig` is the cryptographic binding between the Orchard bundle and the specific transaction it was built for (including network). This verification only happens at the Zcash node level.

**Why the cross-network attack works at the address level**: Orchard raw address bytes (43 bytes) carry no network tag. The same key pair can be encoded as both a mainnet and testnet Unified Address. The bridge's `Address::parse` validates the HRP of the submitted address against the configured chain, but the raw Orchard receiver bytes extracted by `extract_orchard_receiver` are identical for both encodings: [6](#0-5) 

So the attacker creates a mainnet bundle sending to key K (using the known all-zeroes bridge OVK), encodes K as a testnet Unified Address, and submits both. `validate_orchard_bundle` passes because the raw bytes match.

**The `binding_sig` mismatch**: The Orchard `binding_sig` is a signature over `sighash_orchard`, which commits to the transaction's `consensus_branch_id`. A mainnet bundle carries a mainnet branch_id in its sighash. When `get_zcash_tx` assembles the final transaction using the testnet `branch_id` (derived from `config.chain.get_branch_id(current_height)`), the `binding_sig` is cryptographically invalid for that transaction: [7](#0-6) 

Testnet Zcash nodes reject the transaction. The UTXOs remain locked in the bridge state.

---

### Impact Explanation

**Medium** — attacker-triggered temporary locking of bridged ZEC UTXOs requiring operator intervention.

The UTXOs consumed by the PSBT are marked unavailable in the bridge state. The signed transaction is unbroadcastable on the target network. A recovery path **does exist** via the cancel mechanism (`cancel_withdraw_chain_specific` → `cancel_withdraw_callback` → `internal_cancel_withdraw`), which creates a new valid transparent transaction spending the same UTXOs back to the bridge change address: [8](#0-7) 

However, this requires the relayer/operator to detect the failure and manually invoke the cancel path. Until then, the UTXOs are stuck. A well-resourced attacker burning nZEC tokens repeatedly could keep a significant portion of bridge UTXOs in a stuck state, degrading bridge liveness.

The claim of "no recovery path" in the question is **incorrect** — the cancel mechanism provides recovery. This downgrades the finding from Critical to **Medium**.

---

### Likelihood Explanation

- The attacker only needs to transfer nZEC tokens (public `ft_on_transfer` path) — no privileged role required.
- The bridge OVK is hardcoded to all-zeroes (`BRIDGE_OVK = [0u8; 32]`), a publicly known value, making it straightforward to construct a bundle recoverable by the bridge.
- Creating a valid Orchard bundle requires the Zcash SDK but is computationally feasible offline.
- The attack is repeatable at the cost of nZEC tokens burned per attempt. [9](#0-8) 

---

### Recommendation

In `extract_orchard_bundle` (or `validate_orchard_bundle`), verify the Orchard bundle's `binding_sig` against the expected `consensus_branch_id` for the configured chain **before** committing the PSBT. Concretely:

1. Pass the configured chain's `BranchId` into `extract_orchard_bundle`.
2. Reconstruct the `sighash_orchard` for a dummy transaction with that `branch_id` and verify the `binding_sig` using the bundle's `binding_verification_key`. This is the same check Zcash nodes perform and would reject any cross-network bundle at PSBT-construction time rather than at broadcast time.

Alternatively, reject any Orchard bundle whose `binding_sig` cannot be verified against the bridge's configured network before the PSBT is stored.

---

### Proof of Concept

1. Using the Zcash SDK on **mainnet** parameters, generate Orchard key pair K. Construct a bundle sending `amount` zatoshis to K, using OVK = `[0u8; 32]`. Serialize the bundle bytes.
2. Encode K's raw address bytes as a **testnet** Unified Address `T` (same 43-byte Orchard receiver, different HRP).
3. Call `ft_transfer_call` on the nZEC token contract, transferring `amount` nZEC to the testnet bridge, with `msg` containing `target_btc_address = T`, valid `input` UTXOs, and `chain_specific_data.orchard_bundle_bytes = <mainnet bundle bytes>`.
4. Observe: `ft_on_transfer_callback` succeeds; PSBT is committed; UTXOs are marked unavailable.
5. Attempt to broadcast the signed transaction to a testnet Zcash node — it is rejected with an Orchard `binding_sig` verification failure.
6. Confirm UTXOs remain locked until the relayer manually invokes `cancel_withdraw_chain_specific`.

pub fn extract_orchard_bundle(
    orchard_bundle_bytes: Option<Vec<u8>>,
    proof_size_enforcement: ProofSizeEnforcement,
) -> Result<Option<ParsedOrchardBundle>, String> {
    if let Some(orchard_bundle_bytes) = orchard_bundle_bytes {
        let mut reader = Cursor::new(orchard_bundle_bytes);
        let bundle = read_v5_bundle(&mut reader, proof_size_enforcement)
            .map_err(|_| "Failed to read orchard bundle".to_string())?
            .ok_or_else(|| "Orchard bundle is empty".to_string())?;

        // Check action count first per Orchard protocol requirements
        if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
            return Err(format!(
                "Orchard bundle must have {} actions, got {}",
                EXPECTED_ACTIONS_NUMBER,
                bundle.actions().len()
            ));
        }

        // Since we require exactly 1 action, directly recover the single output
        let ovk = orchard::keys::OutgoingViewingKey::from(BRIDGE_OVK);
        let (note, addr, _memo) = bundle
            .recover_output_with_ovk(0, &ovk)
            .ok_or_else(|| "Failed to recover Orchard output with bridge OVK".to_string())?;

        let value = note.value().inner();
        if value == 0 {
            return Err("Orchard output value must be non-zero".to_string());
        }

        Ok(Some(ParsedOrchardBundle {
            bundle,
            output: OrchardOutput {
                amount: value,
                recipient_addr: addr.to_raw_address_bytes(),
            },
        }))
    } else {
        Ok(None)
    }
}

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())

    pub fn extract_orchard_receiver(&self) -> Result<OrchardRawAddress, String> {
        match self {
            Address::Unified { address, .. } => {
                let receiver_list = address.items_as_parsed();
                for receiver in receiver_list {
                    match receiver {
                        Receiver::Orchard(bytes) => return Ok(*bytes),
                        _ => continue,
                    }
                }

                Err("Unified address missing Orchard receiver".to_string())
            }
            _ => Err("No Orchard address found".to_string()),
        }
    }
