### Title
Degenerate `BlockSupportsPeras` Instance Bypasses All Peras Certificate Cryptographic Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production Peras certificate ingest path calls `validatePerasCert` using a degenerate placeholder instance of `BlockSupportsPeras` that unconditionally returns `Right` for every certificate. Any unprivileged peer can send a crafted `PerasCert` over the Peras object-diffusion mini-protocol and have it accepted into the `ChainDB` without any cryptographic or structural verification, allowing the attacker to boost arbitrary blocks and corrupt chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gating check before a received certificate is admitted to the node's `PerasCertDB` / `ChainDB`. The codebase contains a single catch-all instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This instance performs **zero** cryptographic or structural checks. It wraps the raw, unverified `cert` directly into a `ValidatedPerasCert` and returns `Right`. The `ValidatedPerasCert` newtype is the type-level proof that a certificate has been verified; by constructing it unconditionally, the instance forges that proof for every input.

Both production pool-writer constructors pass this degenerate validator to `processCerts`:

```haskell
-- makePerasCertPoolWriterFromChainDB (production path)
(validatePerasCert mkPerasParams)   -- line 126

-- makePerasCertPoolWriterFromCertDB
(validatePerasCert mkPerasParams)   -- line 103
```

`processCerts` then admits every certificate that passes the (trivially satisfied) validator:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
```

Because `validateCert` never returns `Left`, the `(errs, _)` branch is unreachable and every inbound certificate is unconditionally added to the `ChainDB`.

The structural parallel to the BGT report is exact: the BGT module called `BGTStaker::stake` directly (the wrong interface, which always fails due to `onlyBGT`), making the intended staking functionality non-functional. Here, the consensus layer calls `validatePerasCert` through the wrong implementation (the degenerate placeholder, which always succeeds), making the intended certificate-rejection functionality non-functional.

---

### Impact Explanation

A Peras certificate stored in the `ChainDB` carries a `vpcCertBoost` weight that is applied during chain selection (`preferAnchoredCandidate`). An adversary who can inject an accepted certificate for an arbitrary `(round, block)` pair can:

1. Boost a block that was not legitimately certified by the Peras committee, causing honest nodes to prefer a non-canonical chain.
2. Suppress the boost of a legitimately certified block by pre-filling the round slot with a forged certificate for a different block (since the DB silently deduplicates by round number).

Both outcomes constitute a **chain-selection safety failure** triggered by an unprivileged peer sending a crafted network message.

Impact category: **Critical — Bypass of Peras certificate verification checks that enables unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

The Peras object-diffusion mini-protocol is an externally reachable network endpoint. Any peer that can establish a connection to the node can submit `PerasCert` objects. No stake, key material, or operator privilege is required. The degenerate instance is the only `BlockSupportsPeras` instance in the production codebase and is unconditionally selected for all block types. The exploit requires only constructing a well-formed CBOR-encoded `PerasCert` with an attacker-chosen `pcCertRound` and `pcCertBoostedBlock`.

---

### Recommendation

Replace the degenerate `validatePerasCert` body with a real implementation that:
1. Verifies the aggregate BLS/committee signature over `(electionId, candidate)` using the `VotingCommittee` derived from the current ledger state.
2. Checks that the certified block exists in the local `VolatileDB` or `ImmutableDB`.
3. Checks that the round number is within the valid window relative to the current chain tip.

Until the real implementation is ready, the production pool-writer constructors (`makePerasCertPoolWriterFromChainDB`, `makePerasCertPoolWriterFromCertDB`) should refuse all inbound certificates (return `Left` unconditionally) rather than accept them all, so that the security boundary is closed even before the full committee-selection plumbing is in place.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to the node's Peras object-diffusion mini-protocol endpoint.
2. Peer sends a `PerasCert` message with `pcCertRound = R` and `pcCertBoostedBlock = P` where `P` is any block point the attacker wishes to boost (or a point that conflicts with the legitimate certificate for round `R`).
3. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert` is called.
4. The degenerate instance returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams }` without inspecting the certificate's cryptographic fields.
5. `ChainDB.addPerasCertAsync chainDB` stores the forged `ValidatedPerasCert`.
6. On the next chain-selection trigger, `preferAnchoredCandidate` applies the `vpcCertBoost` weight for round `R` to block `P`, causing the node to prefer the attacker-chosen chain over the honest canonical chain.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
