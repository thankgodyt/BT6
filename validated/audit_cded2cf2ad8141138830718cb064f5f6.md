### Title
Stub `validatePerasCert` Accepts Any Certificate Without Committee Validation, Enabling Unprivileged Fork Switch via Peras Weight Boost — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is an unconditional stub that always returns `Right`, accepting every inbound certificate without any committee, quorum, or cryptographic check. An unprivileged peer can send a crafted `PerasCert` boosting a block on a non-canonical fork; the certificate is stored in `PerasCertDB`, its boost is reflected in the `PerasWeightSnapshot`, and `preferAnchoredCandidate` then selects the heavier fork, causing the honest node to switch away from the canonical chain.

---

### Finding Description

**Step 1 — Inbound certificate path (object diffusion, NodeToNode)**

`makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` is the production writer used for NodeToNode cert diffusion. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```
(validatePerasCert mkPerasParams)
(void . ChainDB.addPerasCertAsync chainDB)
``` [1](#0-0) 

**Step 2 — `validatePerasCert` is a no-op stub**

The production `BlockSupportsPeras` instance (the only instance, covering all blocks) implements `validatePerasCert` as:

```haskell

-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

Every certificate, regardless of content, is accepted and wrapped as `ValidatedPerasCert`. [2](#0-1) 

**Step 3 — `getVotingCommitteeForElection` is dead code, never called**

`getVotingCommitteeForElection` in `AcrossEpochs.hs` is defined as `error "TODO: implement getVotingCommitteeForElection"` and is exported but never imported or called anywhere in production code (grep confirms only 4 occurrences, all within the defining file). The production cert validation path (`validatePerasCert`) does not call it at all — the "alternative code path" the question describes is simply the only production path. [3](#0-2) 

**Step 4 — `PerasCertDB.addCert` / `implAddCert` performs no committee check**

`implAddCert` stores the certificate directly into the in-memory index with no further validation. The TODO comment explicitly acknowledges this:

```
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
``` [4](#0-3) 

**Step 5 — `implGetWeightSnapshot` builds the weight map from all stored certs**

`implGetWeightSnapshot` unconditionally maps every stored certificate's boosted block to its weight boost. No validity gate exists here. [5](#0-4) 

**Step 6 — `chainSelSync` for `ChainSelAddPerasCert` triggers chain selection with the boosted weight**

After storing the cert, `chainSelSync` calls `chainSelectionForBlock` for the boosted block. The only guard is an age check (slot vs. immutable tip); there is no committee or quorum check. [6](#0-5) 

**Step 7 — `preferAnchoredCandidate` uses the weight snapshot to prefer the fork**

`preferAnchoredCandidate` computes `weightedSelectView` for both the current chain and the candidate, summing `weightBoostOfFragment` from the snapshot. A fork block boosted by the injected certificate gains `perasWeight` extra weight, potentially making it heavier than the canonical chain. [7](#0-6)

### Impact Explanation

An unprivileged peer connected via the NodeToNode object-diffusion protocol can craft a `PerasCert` naming any block hash on a non-canonical fork as the boosted block. Because `validatePerasCert` unconditionally returns `Right`, the certificate is stored, its boost is added to the weight snapshot, and chain selection switches the honest node to the fork. This violates the invariant that only certificates with a valid quorum from the correct epoch committee may boost a block's weight in chain selection.

**Scope match:** High — "Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

The attack requires only a NodeToNode connection and the ability to send a well-formed (but cryptographically fabricated) `PerasCert` CBOR message. No stake, keys, or operator access are needed. The boosted block must be in the node's VolatileDB (i.e., the attacker must also have diffused the fork block), which is achievable via normal block diffusion. The path is fully exercisable in io-sim or a private testnet on unmodified code.

---

### Recommendation

1. **Implement `validatePerasCert`** to call the appropriate committee's `verifyCert` method, using `getVotingCommitteeForElection` (once implemented) to resolve the correct epoch committee for the certificate's `ElectionId`.
2. **Implement `getVotingCommitteeForElection`** in `AcrossEpochs.hs` to look up the committee by matching the election's epoch against `currEpochVotingCommittee` / `prevEpochVotingCommittee`.
3. **Gate `implAddCert`** on a pre-validated type (`ValidatedPerasCert` should only be constructible after a successful `verifyCert` call), or add a secondary check inside `implAddCert` as defense-in-depth.
4. Track this under the existing issue https://github.com/tweag/cardano-peras/issues/120 and ensure it is resolved before any deployment that enables Peras weight-based chain selection.

---

### Proof of Concept

An io-sim scenario:

1. Set up a ChainDB with a two-block fork: canonical chain `A → B`, fork `A → C`.
2. Diffuse block `C` to the node (so it is in the VolatileDB).
3. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = blockPoint C }` with arbitrary (fabricated) content.
4. Call `ChainDB.addPerasCertSync chainDB (WithArrivalTime now validatedCert)` where `validatedCert` is obtained by calling `validatePerasCert mkPerasParams cert` — which returns `Right` unconditionally.
5. Assert that the node's current chain tip is now `C` (the non-canonical fork), demonstrating the switch.

The assertion will hold on unmodified code because `validatePerasCert` never rejects any certificate.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
