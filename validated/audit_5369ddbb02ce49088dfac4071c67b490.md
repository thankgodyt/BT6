### Title
Silent Return in `safe_mint` Permanently Locks nBTC in Bridge Account When Recipient Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

`safe_mint` in the nbtc contract mints tokens to `bridge_id` **before** checking whether the recipient account is registered. If the recipient is unregistered, the function silently returns `PromiseOrValue::Value(U128(0))` without reverting. Because NEAR's async receipt model does not roll back state changes from a prior receipt when a callback panics, the minted tokens are permanently stranded in the bridge's own nbtc balance with no recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

```rust
// Step 1 — tokens are minted to bridge_id unconditionally
self.token.internal_deposit(&self.bridge_id, amount.into());

// Step 2 — silent return if recipient has no storage registration
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));   // ← no revert, tokens already minted
}
``` [1](#0-0) 

The function is called by the satoshi-bridge during the safe-deposit flow (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)` / `safe_verify_deposit`). The satoshi-bridge's callback receives `U128(0)` and may panic to signal failure. However, in NEAR's execution model, the `internal_deposit` to `bridge_id` already executed in a separate receipt and **cannot be rolled back** by a later callback panic. The minted nBTC is now credited to the satoshi-bridge's own account inside the nbtc token. [2](#0-1) 

The satoshi-bridge has no mechanism to recover these tokens:

- `withdraw_protocol_fee` is bounded by `cur_available_protocol_fee`, which is only incremented via the `DepositProtocolFee` path in `ft_on_transfer` — not by `safe_mint`. [3](#0-2) [4](#0-3) 

- `internal_transfer_nbtc` is only used for lost-found and cancel-withdraw refunds; it is never invoked for amounts stranded by `safe_mint`. [5](#0-4) 

- There is no general rescue or sweep function in the satoshi-bridge.

The stuck nBTC is therefore unrecoverable through any existing contract path.

---

### Impact Explanation

Every satoshi of BTC deposited through the safe-deposit flow for an unregistered NEAR account results in:

1. The deposit UTXO being recorded as verified and locked in the bridge's UTXO set.
2. An equal amount of nBTC minted to the bridge's own nbtc balance — permanently stranded.
3. No lost-found entry created (the safe-deposit path explicitly skips lost-found).
4. No way for the user or the DAO to recover either the BTC or the nBTC.

This constitutes **permanent locking of user funds** and a **backed-supply inflation** of the bridge's internal nbtc balance that is never burned, breaking the 1:1 BTC↔nBTC invariant over time.

**Severity: Critical** — permanent, irrecoverable loss of user BTC deposits and protocol nBTC supply integrity.

---

### Likelihood Explanation

The safe-deposit flow (`verify_deposit_v2` with `safe_deposit = Some(..)`) is the path used by integrations such as Omni Bridge. The documentation states the caller must attach NEAR for the recipient's token storage, but:

- If the storage registration step is omitted or fails before the deposit proof is submitted, the recipient account will be unregistered when `safe_mint` executes.
- A relayer submitting a proof for a user who has never interacted with the nbtc token (no storage deposit) will trigger this path.
- No on-chain guard in the satoshi-bridge verifies that the recipient is registered in nbtc before calling `safe_mint`.

The condition is reachable in normal operation without any malicious actor.

---

### Recommendation

Swap the order of operations in `safe_mint`: check registration **before** minting, and revert (panic) rather than silently returning `U128(0)` when the recipient is unregistered:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting — panic if unregistered so the caller's callback
    // can observe a failed promise and the deposit is not silently lost.
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

This ensures that if the recipient is unregistered, no tokens are minted and the satoshi-bridge's callback receives a failed promise result, allowing it to revert the deposit state atomically.

---

### Proof of Concept

1. User sends BTC to their deposit address derived from a `DepositMsg` with `safe_deposit = Some(..)`.
2. The user's NEAR account (`account_id`) has never called `storage_deposit` on the nbtc contract and is therefore unregistered.
3. A relayer calls `verify_deposit_v2` (or `safe_verify_deposit`) with the BTC proof.
4. After light-client verification succeeds, the satoshi-bridge calls `safe_mint(account_id, amount, msg)` on the nbtc contract.
5. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — nBTC is minted to the bridge's own account. [6](#0-5) 
6. `self.token.accounts.get(&account_id).is_none()` is `true` — the function returns `PromiseOrValue::Value(U128(0))`. [7](#0-6) 
7. The satoshi-bridge's callback receives `U128(0)`. Even if it panics, the `internal_deposit` from step 5 is already committed in a prior NEAR receipt and is not rolled back.
8. The nBTC tokens remain in the bridge's nbtc balance. `cur_available_protocol_fee` is unchanged, so `withdraw_protocol_fee` cannot reach them. [8](#0-7) 
9. The user's BTC is locked in the bridge UTXO. The nBTC is permanently stranded. Neither can be recovered.

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
