Audit Report

## Title
Native ETH `finTransfer` Permanently Freezes Bridged Funds When Recipient Contract Lacks `receive`/`fallback` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`OmniBridge.finTransfer()` unconditionally performs a low-level ETH call to `payload.recipient` when `payload.tokenAddress == address(0)`. If the recipient is a contract that does not implement `receive()` or `fallback()`, the call returns `success = false`, the function reverts with `FailedToSendEther`, and the NEAR-side tokens locked during `init_transfer_internal` have no recovery path — resulting in permanent freezing of bridged funds.

## Finding Description
In `finTransfer`, the native-ETH branch executes:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
```

`completedTransfers[payload.destinationNonce] = true` is written before this call. Because the revert rolls back all state changes, the nonce is not consumed and relayers can retry — but every retry hits the same structural failure: the recipient contract cannot accept ETH via a low-level call. No guard checks whether the recipient is ETH-capable before attempting delivery.

On the NEAR side, `init_transfer_internal` burns or locks the user's tokens and emits `InitTransferEvent`. The `sign_transfer_callback` only removes the `pending_transfers` entry when `fee.is_zero()`; for non-zero-fee transfers the entry persists indefinitely. There is no user-callable cancel, redirect, or admin-rescue function for a pending transfer whose EVM finalization permanently reverts. The NEAR-side funds are frozen with no on-chain recovery path.

`OmniBridgeWormhole` inherits `OmniBridge` without overriding `finTransfer`, carrying the identical vulnerability.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**, which is explicitly within the Critical allowed impact scope. The user's NEAR-side tokens are irreversibly locked: the EVM delivery can never succeed for a structurally ETH-rejecting recipient, and the NEAR contract provides no mechanism to cancel or redirect a pending transfer once it has been signed and submitted to the EVM relayer pipeline.

## Likelihood Explanation
Smart-contract recipients are routine bridge destinations: Gnosis Safe multisigs, DAO treasuries, DeFi vaults, and protocol fee collectors are all common targets. Many such contracts accept ETH only through named payable functions, not via anonymous low-level calls. A user or protocol integrator who specifies any such address as the recipient of a native-ETH bridge transfer — a fully supported flow — triggers this condition without any on-chain warning. No special permissions, adversarial setup, or privileged access are required.

## Recommendation
Replace the hard revert with a pull-based withdrawal pattern. If the low-level call fails, store the claimable ETH in a `pendingWithdrawals` mapping, consume the nonce, and emit a `DeliveryFailed` event so the NEAR-side transfer is finalized and the recipient (or an admin) can claim later:

```solidity
if (payload.tokenAddress == address(0)) {
    if (payload.amount > 0) {
        (bool success, ) = payload.recipient.call{value: payload.amount}("");
        if (!success) {
            pendingWithdrawals[payload.recipient] += payload.amount;
            emit DeliveryFailed(payload.recipient, payload.amount);
        }
    }
}
```

This ensures the destination nonce is permanently consumed, the NEAR-side transfer is finalized, and funds remain claimable rather than frozen.

## Proof of Concept
1. Deploy on EVM:
   ```solidity
   contract NoReceive {
       function doSomething() external {}
       // no receive(), no fallback()
   }
   ```
2. On NEAR, call `ft_on_transfer` with `recipient = Eth::<address(NoReceive)>` and a non-zero amount of native ETH equivalent.
3. `init_transfer_internal` locks/burns tokens, emits `InitTransferEvent`, stores entry in `pending_transfers`.
4. Relayer calls `sign_transfer`; MPC signs; `sign_transfer_callback` emits `SignTransferEvent` (transfer message remains in `pending_transfers` because fee > 0).
5. Relayer calls `OmniBridge.finTransfer(signature, payload)` with `payload.tokenAddress == address(0)` and `payload.recipient == address(NoReceive)`.
6. `completedTransfers[nonce] = true` is written, then `NoReceive.call{value: amount}("")` returns `success = false`.
7. `revert FailedToSendEther()` rolls back all state; nonce is not consumed.
8. Every subsequent relay attempt reverts identically.
9. NEAR-side `pending_transfers` entry is never removed; tokens are permanently frozen.
