### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or structural validation. This function is called on every `PerasCert` received from an untrusted peer via the live `PerasCertDiffusion` mini-protocol. A single unprivileged peer can inject crafted certificates that boost arbitrary blocks in the `PerasWeightSnapshot`, causing chain selection to prefer a non-canonical chain over the honest chain.

---

### Finding Description

**Root cause — stub validator always succeeds:**

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate for accepting peer-supplied certificates. The sole production instance (a blanket `instance StandardHash blk => BlockSupportsPeras blk`) implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of content, is wrapped in `Right` and assigned the full `perasWeight` boost. No signature, no committee membership, no round-number range, no boosted-block existence check is performed. [1](#0-0) 

**Production inbound path — peer certificates reach the stub without any prior filter:**

`makePerasCertPoolWriterFromChainDB` wires `validatePerasCert mkPerasParams` directly as the validation callback for every batch of certificates received from a peer:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each certificate not already in the DB; if all pass (they always do), each is timestamped and forwarded to `addCert`: [3](#0-2) 

**Live mini-protocol wiring — reachable by any unprivileged peer:**

`hPerasCertDiffusionClient` in the node-to-node handler passes `makePerasCertPoolWriterFromChainDB` directly to `objectDiffusionInbound`, which is run for every connecting peer:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain-selection consequence — fake boost alters fork choice:**

`chainSelSync` processes each accepted certificate: it adds it to the `PerasCertDB`, updates the `PerasWeightSnapshot`, and calls `chainSelectionForBlock` for the boosted block:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  -- Trigger chain selection for the boosted block.
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

Chain selection compares candidates using `weightedSelectView`, which sums `wsvBlockNo` and `wsvWeightBoost` from the `PerasWeightSnapshot`. A fake certificate injects an attacker-controlled `PerasWeight` boost onto any block point, directly inflating the total weight of any chain containing that block: [6](#0-5) 

The `PerasWeightSnapshot` accumulates boosts additively with no cap: [7](#0-6) 

**Analog to the return-bomb vulnerability class:**

The external report describes a caller that makes a call to an untrusted party and processes the returned data without bounding or validating it, causing incorrect downstream behavior. Here, the node calls `validatePerasCert` on peer-supplied data and processes the result without any actual validation — the "return" is always `Right`, unconditionally, regardless of what the peer sent. The downstream effect is not out-of-gas but chain-selection manipulation: the node is forced to re-evaluate fork choice with an attacker-controlled weight, potentially switching to a non-canonical chain.

---

### Impact Explanation

**Classification:** Critical — bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain weight manipulation.

An unprivileged peer can:
1. Send a `PerasCert` with `pcCertBoostedBlock` pointing to any block on an adversarial fork.
2. The certificate passes `validatePerasCert` unconditionally.
3. The `PerasWeightSnapshot` is updated with the full `perasWeight` boost for that block.
4. `chainSelectionForBlock` is triggered; if the adversarial chain's total weight now exceeds the honest chain's weight, the node switches forks.
5. Repeated injections across multiple rounds can accumulate unbounded weight on an adversarial chain, permanently biasing the node's fork choice away from the canonical chain.

This satisfies the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."* It also satisfies: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- The `PerasCertDiffusion` mini-protocol is wired into the live node-to-node application and runs for every peer connection.
- No stake, key material, or privileged access is required; any connecting peer can send crafted `PerasCert` messages.
- The stub is explicitly marked `TODO` and linked to an open issue (`cardano-peras/issues/120`), confirming it is intentionally incomplete but already deployed in the production code path.
- The `PerasWeightSnapshot` has no per-peer rate limit or deduplication beyond one certificate per round number, so a single peer can boost one block per round.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that checks at minimum:
1. **Signature validity**: the certificate must carry a valid aggregate/threshold signature from a quorum of eligible committee members for the claimed round.
2. **Committee eligibility**: the signers must be drawn from the committee elected for `pcCertRound` according to the stake distribution at the relevant epoch.
3. **Round-number bounds**: `pcCertRound` must be within the current or recent Peras window; stale or far-future rounds must be rejected.
4. **Boosted-block existence and ancestry**: `pcCertBoostedBlock` must correspond to a block that was actually a candidate in the claimed round.

Until real validation is implemented, consider disabling the `PerasCertDiffusion` inbound handler entirely (or making it a no-op) so that peer-supplied certificates cannot reach `addPerasCertAsync` and influence chain selection.

### Proof of Concept

```
Attacker (unprivileged peer) connects via PerasCertDiffusion mini-protocol.

1. Attacker constructs:
     PerasCert
       { pcCertRound      = <any PerasRoundNo, e.g. 42>
       , pcCertBoostedBlock = <Point of a block on adversarial fork F>
       }

2. Attacker sends the certificate batch to the victim node.

3. processCerts calls (validatePerasCert mkPerasParams cert)
   → always returns Right (ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams })
   → certificate is accepted unconditionally.

4. ChainDB.addPerasCertAsync enqueues the certificate.

5. chainSelSync processes it:
   - PerasCertDB.addCert stores it.
   - PerasWeightSnapshot gains boost for the block on fork F.
   - chainSelectionForBlock is triggered for that block.

6. weightedSelectView now computes:
     wsvTotalWeight(F) = blockNo(F_tip) + perasWeight(mkPerasParams)
   If this exceeds wsvTotalWeight(honest chain), the node switches to F.

7. Attacker repeats for additional rounds to accumulate weight on F,
   permanently biasing the victim node's chain selection.
```

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
