### Title
Peras Certificate Validation Stub Always Accepts Any Inbound Certificate, Enabling Adversarial Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production inbound-certificate pipeline (`processCerts`) documents that every received Peras certificate is cryptographically validated before being stored, and that any invalid certificate causes the entire batch to be rejected and the peer to be disconnected. In reality, the `validatePerasCert` implementation that is wired into that pipeline is a stub that unconditionally returns `Right` for every input, performing no cryptographic or semantic checks whatsoever. An unprivileged peer can therefore inject an arbitrary crafted certificate for any round, boosting any block, and the node will store it and trigger chain selection on its behalf.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into the production path**

The `BlockSupportsPeras` type-class declares `validatePerasCert` as the function responsible for verifying inbound Peras certificates. The only concrete instance in the codebase is the degenerate catch-all instance for `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function **always** returns `Right`, regardless of the certificate's content. No signature is checked, no quorum is verified, no round-number bounds are enforced, and no boosted-block validity is confirmed.

**The production pipeline claims validation occurs but calls this stub**

`processCerts` — the function that handles every batch of inbound Peras certificates received from a remote peer — is documented as follows:

> "The remaining certificates are validated; if /any/ certificate in the batch fails validation, the entire batch is rejected by throwing a `PerasCertInboundException` (which should make us disconnect from the distant peer)." [2](#0-1) 

The implementation reads:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validateCert` is bound to `validatePerasCert mkPerasParams` — the stub above — `partitionEithers` will always produce `([], validatedCerts)`. The `(errs, _)` branch is permanently unreachable. Every certificate, no matter how malformed or fraudulent, is accepted and forwarded to `addCert`.

**The production writer uses this path**

`makePerasCertPoolWriterFromChainDB` is the production `ObjectPoolWriter` for inbound Peras certificates. It passes `validatePerasCert mkPerasParams` directly as the validator:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [4](#0-3) 

After passing "validation", the certificate is added to the `PerasCertDB` and `ChainDB.addPerasCertAsync` is called, which enqueues a `ChainSelAddPerasCert` event. The chain-selection loop then uses the certificate's boost weight to potentially prefer a different chain:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

**The inconsistency mirrors the Sake analog exactly**

The Sake report describes documentation claiming an automatic operation occurs (staking), while the code only conditionally handles the reverse (unstaking). Here, the documentation of `processCerts` claims automatic rejection of invalid certificates occurs, while the code only conditionally handles the rejection branch — a branch that is structurally unreachable because the validator it calls never returns `Left`.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and an arbitrary `pcCertBoostedBlock` pointing to any block hash. Because `validatePerasCert` always returns `Right`, the certificate:

1. Passes the "validation" filter in `processCerts`.
2. Is stored in the `PerasCertDB` with a boost weight of `perasWeight params`.
3. Triggers `chainSelectionForBlock` for the boosted block.

The Peras boost weight is added to the chain-selection score of the boosted block's chain. A crafted certificate boosting a block on an adversary-controlled fork can cause an honest node to prefer that fork over the canonical chain, constituting a **chain-selection manipulation** by an unprivileged network peer.

**Severity: High** — matches "Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. No authentication, stake ownership, or operator privilege is required to send a `PerasCert` message. The only gate is the round-number deduplication check (`certsNotAlreadyInDb`), which an attacker trivially bypasses by using a fresh round number. The attack requires sending a single well-formed CBOR-encoded `PerasCert` message over the wire.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs the full cryptographic and semantic checks required by the Peras specification (aggregate BLS signature verification, quorum threshold check, round-number bounds, boosted-block validity). Until that implementation is complete, the production `makePerasCertPoolWriterFromChainDB` should not be wired to the stub, or inbound certificates should be quarantined rather than immediately forwarded to chain selection. The documentation of `processCerts` should be updated to reflect the current (non-)validation behavior if the stub is intentionally retained during development.

---

### Proof of Concept

1. Connect to a node running this code as an unprivileged peer via the object-diffusion mini-protocol for Peras certificates.
2. Craft a `PerasCert` with:
   - `pcCertRound` = any round number not yet present in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of a block on an adversary-controlled fork
3. Send the certificate in a batch via `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` unconditionally.
5. `partitionEithers` yields `([], [validatedCert])` — the rejection branch is never taken.
6. `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
7. `chainSelSync` adds the certificate to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block, applying the Peras boost weight to the adversary's fork.
8. If the boosted fork's score now exceeds the honest chain's score, the node switches to the adversary's chain. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
