Audit Report

## Title
Permanent Freezing of User Funds via `normalize_amount` Returning Zero in `sign_transfer` — (`near/omni-bridge/src/lib.rs`)

## Summary

When a user bridges a token amount smaller than `10^(origin_decimals − decimals)`, `normalize_amount` (floor division) reduces the net amount to zero. `sign_transfer` then hard-panics with `InvalidAmountToTransfer` before reaching the MPC signer, so `sign_transfer_callback` is never invoked, `remove_transfer_message` is never called, and the tokens remain permanently locked in the bridge with no user-accessible cancel or refund path.

## Finding Description

**Root cause — `normalize_amount` (L2784–2787):**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

Floor division silently truncates any amount smaller than `10^(origin_decimals − decimals)` to `0`.

**Step 1 — `init_transfer` (L554–557):** The only guard is `fee < amount`; there is no check that the normalized amount is non-zero. Tokens are locked/burned and a `TransferMessage` is stored in `pending_transfers`. [2](#0-1) 

**Step 2 — `sign_transfer` (L475–485):** The relayer calls `sign_transfer`, which normalizes the stored amount and immediately panics:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

Because the panic occurs before the `ext_signer::ext(...).sign(...)` call, the `.then(sign_transfer_callback(...))` chain is never scheduled. [4](#0-3) 

**Step 3 — `sign_transfer_callback` never reached (L655–658):** `remove_transfer_message` is only called inside the callback on a successful MPC signature. Since the callback is never reached, the `TransferMessage` stays in `pending_transfers` forever. [5](#0-4) 

The stored amount is fixed; every future relayer call to `sign_transfer` for the same `transfer_id` will produce the same zero result and panic again. No public cancel or user-refund function exists in the contract.

## Impact Explanation

This is a **permanent freezing of bridged funds** — a Critical impact under the allowed scope. The user's NEP-141 tokens are locked or burned in `init_transfer` and can never be recovered or forwarded to the destination chain without DAO-level intervention. The frozen state is deterministic and irreversible through any permissionless call path.

## Likelihood Explanation

Any token registered with `origin_decimals > decimals` (e.g., a NEAR-native 24-decimal token bridged to an EVM chain where it is registered with 18 decimals — a 6-decimal gap) is affected. A user sending fewer than `10^6` raw units triggers the freeze. The `ft_transfer_call` entry point is fully permissionless; no attacker capability is required — an ordinary user making a small transfer is sufficient. The condition is repeatable and deterministic.

## Recommendation

Add a normalized-amount guard inside `init_transfer` **before** tokens are locked, so the transfer is rejected early and the tokens are returned to the sender:

```rust
let normalized = Self::normalize_amount(amount.0, decimals);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Alternatively, in `sign_transfer`, instead of panicking, refund the stored amount to the original sender and call `remove_transfer_message` to clean up state. The preferred fix is the early guard in `init_transfer` to prevent funds from ever entering an unrecoverable state.

## Proof of Concept

1. Admin registers a token with `origin_decimals = 24`, `decimals = 18` (6-decimal gap).
2. User calls `ft_transfer_call` transferring `500_000` raw units with a valid `InitTransferMsg` targeting an EVM chain.
3. `init_transfer` succeeds — `fee < amount` passes, tokens are locked, `TransferMessage` stored.
4. Relayer calls `sign_transfer` for that `transfer_id`.
5. `normalize_amount(500_000, Decimals { origin_decimals: 24, decimals: 18 }) = 500_000 / 1_000_000 = 0`.
6. `require!(0 > 0, ...)` panics — transaction reverts, no state change.
7. Steps 4–6 repeat forever; `500_000` raw units are permanently locked in the bridge with no user-accessible recovery path.
