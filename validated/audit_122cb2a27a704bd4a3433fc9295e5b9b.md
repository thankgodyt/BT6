### Title
`safe_mint` Mints Tokens to Bridge Before Checking Recipient Registration, Causing Permanent Token Lock - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nbtc token contract unconditionally mints tokens to the bridge account before verifying whether the intended recipient is registered. When the recipient is unregistered, the function returns early with `U128(0)` and the minted tokens remain permanently stranded in the bridge with no built-in recovery path. This is a supply/accounting state corruption analogous to the SynthToken report's root cause: a storage write that produces an irrecoverable incorrect on-chain state.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally on line 112, increasing both the bridge's token balance and the global total supply by `amount`. Only after that mutation does it check whether `account_id` is registered:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into()); // supply inflated here

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));  // early return, tokens already minted
}
``` [1](#0-0) 

When the account is absent the function returns `U128(0)` without transferring or reversing the deposit. The result is:

- `ft_total_supply()` is permanently inflated by `amount`.
- The bridge account holds `amount` extra tokens that are not backed by any user claim.
- No burn, refund, or sweep path exists in the nbtc contract to recover these orphaned tokens.
- The caller (bridge) receives `U128(0)`, which it may interpret as "mint skipped", while the token ledger has already been mutated.

The contrast with the correct path (registered account) is that `ft_transfer` or `ft_transfer_call` is then called from the bridge's balance to the recipient, so the deposit is consumed. The unregistered path leaves the deposit unconsumed. [2](#0-1) 

### Impact Explanation
**Medium — stuck bridge state requiring operator intervention.**

The total supply diverges from the sum of all user balances. Tokens minted to the bridge in this path are not burnable via the normal `burn` path (which requires the bridge to hold exactly the amount a user transferred for withdrawal). Over time, repeated occurrences inflate the bridge's balance with phantom tokens, corrupting the backed-supply invariant. Recovery requires a privileged operator to manually burn the orphaned balance, which is not a documented or automated procedure.

### Likelihood Explanation
**Medium.**

NEAR accounts must explicitly call `storage_deposit` before they can hold NEP-141 tokens. A first-time BTC depositor who has never interacted with the nbtc contract will not have a registered account. The bridge's `safe_mint` call is triggered by a relayer submitting a valid deposit proof — a fully public, permissionless action. Any deposit whose recipient has not pre-registered their nbtc storage slot will hit this code path.

### Recommendation
Move the registration check **before** the `internal_deposit` call, or return early without minting if the account is absent:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

Alternatively, auto-register the account (paying storage from attached deposit) before minting, consistent with how `mint_inner` handles unregistered accounts. [3](#0-2) 

### Proof of Concept

1. Alice sends BTC to her bridge deposit address but has never called `storage_deposit` on the nbtc contract — her account is unregistered.
2. A relayer submits a valid `verify_deposit` proof to the satoshi-bridge.
3. The bridge calls `nbtc.safe_mint(alice.near, 100_000, None)`.
4. Inside `safe_mint`, `internal_deposit(&bridge_id, 100_000)` executes: bridge balance +100 000, total supply +100 000.
5. `self.token.accounts.get(&alice.near)` returns `None`.
6. Function returns `U128(0)` — no transfer occurs.
7. Alice receives 0 nBTC. Her BTC is locked in the bridge UTXO set. The bridge holds 100 000 phantom nBTC with no corresponding user claim. `ft_total_supply()` is now overstated by 100 000 satoshis permanently. [4](#0-3)

    #[payable]
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
