Audit Report

## Title
Inverted NEP-141 Callback Condition in `submit_transfer_to_btc_connector_callback` Causes Stale Re-insertion on Success — (`near/omni-bridge/src/btc.rs`)

## Summary

`submit_transfer_to_btc_connector_callback` treats `ft_transfer_call` returning `Ok(U128(0))` as failure and re-inserts the transfer into `pending_transfers`. Under NEP-141, `U128(0)` is the canonical success value — it means the receiver accepted all tokens (refunded zero). Because the BTC connector must return `U128(0)` to retain the nBTC tokens it receives, every successful withdrawal triggers the re-insertion path, leaving a stale `pending_transfers` entry that a trusted relayer will naturally retry, causing a second `ft_transfer_call` for the same transfer and a double-spend.

## Finding Description

In `submit_transfer_to_utxo_chain_connector`, the bridge removes transfer `T` from `pending_transfers` at line 84, then calls `ft_transfer_call` forwarding `amount` nBTC to the BTC connector. [1](#0-0) 

The callback at line 111 evaluates:
```rust
if matches!(call_result, Ok(result) if result.0 > 0) {
    // send fee  ← treated as success
} else {
    // re-insert transfer ← treated as failure
}
``` [2](#0-1) 

Under NEP-141, `ft_on_transfer` returns the amount to **refund** (unused tokens). A correct BTC connector that accepts all nBTC tokens to initiate a withdrawal **must** return `U128(0)` — returning any non-zero value would cause the token contract to refund those tokens back to the bridge, leaving the connector with zero nBTC and no ability to execute the withdrawal. Therefore `ft_transfer_call` resolves to `Ok(U128(0))` on every successful connector call.

With `result.0 == 0`, the `if` guard is false, execution falls into the `else` branch, and `add_transfer_message` re-inserts `T` into `pending_transfers`. [3](#0-2) 

`add_transfer_message` panics only if the key already exists; since `T` was removed before the `ft_transfer_call`, the re-insertion succeeds silently. [4](#0-3) 

The existing test `test_btc_callback_failure_preserves_storage_balance` only exercises the `Err(PromiseError)` branch (the mock connector has no `ft_on_transfer`), so the inverted `Ok(U128(0))` path is untested. [5](#0-4) 

## Impact Explanation

After the callback re-inserts `T`, a trusted relayer observing `T` in `pending_transfers` will call `submit_transfer_to_utxo_chain_connector` again — this is standard relayer retry behavior with no malicious intent required. On the second call the bridge removes `T` again and issues a second `ft_transfer_call` for the same `amount`. If the bridge holds sufficient nBTC from other users' pending transfers, the second call succeeds and the BTC connector receives `amount` nBTC a second time, initiating a second MPC signing request for the same withdrawal. The result is a double-spend: the user's BTC address receives two on-chain outputs for a single bridged transfer, funded by draining other users' escrowed nBTC. This matches the Critical impact class: double-spending of bridged funds across the NEAR–Bitcoin flow.

## Likelihood Explanation

The inverted condition fires on **every** successful BTC withdrawal — the normal case. Any trusted relayer running standard retry logic against `pending_transfers` will trigger the second submission without any malicious intent. Becoming a trusted relayer is an open, permissioned process (`apply_for_trusted_relayer` with a stake and waiting period), so the trigger is reachable through normal relayer flows. The only practical brake is whether the bridge holds enough nBTC from concurrent users to fund the second transfer, which is likely in any live deployment. [6](#0-5) 

## Recommendation

Invert the condition to match NEP-141 semantics:

```rust
// Correct: result.0 == 0 means all tokens were accepted (success)
if matches!(call_result, Ok(result) if result.0 == 0) {
    let token_fee = transfer_msg.fee.fee.0;
    self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
} else {
    // Connector returned tokens or call failed — re-insert transfer
    let required_storage_balance =
        self.add_transfer_message(transfer_msg, transfer_owner.clone());
    self.update_storage_balance(
        transfer_owner,
        required_storage_balance,
        NearToken::from_yoctonear(0),
    );
    PromiseOrValue::Value(())
}
```

Additionally, add a `finalised_utxo_transfers`-style idempotence guard keyed on `transfer_id` before the `ft_transfer_call` to prevent any re-submission regardless of callback outcome, and add an integration test that uses a mock connector whose `ft_on_transfer` returns `U128(0)` and asserts the transfer is **not** re-inserted.

## Proof of Concept

1. Deploy the bridge with a mock BTC connector whose `ft_on_transfer` returns `U128(0)` (standard NEP-141 acceptance).
2. User initiates a BTC withdrawal; transfer `T` enters `pending_transfers`.
3. Trusted relayer calls `submit_transfer_to_utxo_chain_connector(T, ...)`.
4. Bridge removes `T`, sends `amount` nBTC to connector; connector's `ft_on_transfer` returns `U128(0)`; `ft_transfer_call` resolves to `Ok(U128(0))`.
5. Callback: `result.0 == 0` → `else` branch → `add_transfer_message` re-inserts `T` into `pending_transfers`.
6. Relayer queries `get_transfer_message(T)` — it exists — and calls `submit_transfer_to_utxo_chain_connector(T, ...)` again.
7. Bridge removes `T` again, sends `amount` nBTC again from other users' escrowed balance.
8. Assert: connector received `2 × amount` nBTC; MPC signing was requested twice for the same transfer ID.
