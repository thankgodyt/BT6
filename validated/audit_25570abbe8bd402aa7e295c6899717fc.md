Audit Report

## Title
`normalize_amount` Floor-Division to Zero Causes Permanent Fund Lock in `sign_transfer` - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts any transfer where `fee < amount` without verifying that the post-normalization transfer amount is non-zero. For tokens where `origin_decimals > decimals` (e.g., 24 vs 18, divisor = 10^6), any `amount_without_fee()` below the divisor undergoes floor division to zero in `normalize_amount`. The subsequent `require!(amount_to_transfer > 0, ...)` guard in `sign_transfer` then permanently rejects every signing attempt for that transfer ID. Because no public cancel or refund path exists, the user's tokens are permanently burned or locked in the bridge with no recovery.

## Finding Description

**Step 1 — Permissive validation in `init_transfer`**

`init_transfer` constructs the `TransferMessage` and performs only a single fee check before proceeding: [1](#0-0) 

This allows `amount = 500_000, fee = 0` to pass for a token whose normalization divisor is `10^6`.

**Step 2 — Full amount is burned/locked immediately in `init_transfer_internal`** [2](#0-1) 

The entire `amount` is burned or locked before any normalization check occurs. The transfer record is then stored in `pending_transfers`.

**Step 3 — `normalize_amount` uses floor division** [3](#0-2) 

The code comment at L2781–2782 explicitly acknowledges this: *"When fee = 0, dust stays locked/burned."* However, the comment treats this as a "dust" edge case, not the scenario where the **entire** `amount_without_fee()` normalizes to zero.

**Step 4 — `sign_transfer` permanently rejects the transfer** [4](#0-3) 

Every call to `sign_transfer` for this transfer ID panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. The transfer record remains in `pending_transfers` indefinitely.

**Step 5 — No public cancel/refund path**

`remove_transfer_message` is a private internal function called only from `claim_fee_callback` and similar internal flows. [5](#0-4) 

No public `cancel_transfer` or equivalent function exists. The user has no mechanism to recover their locked/burned tokens.

## Impact Explanation

This is a **permanent freezing of bridged funds** triggered by a normal, unprivileged user action. For any token pair where `origin_decimals > decimals` (e.g., a NEAR-native 24-decimal token bridging to an 18-decimal EVM chain, divisor = 10^6), any user who initiates a transfer with `amount_without_fee() < 10^6` base units will have their tokens permanently burned or locked with no recovery path. This matches the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, ... flows"* and *"decimal/normalization abuse ... that changes user or protocol balances."*

## Likelihood Explanation

The condition is reachable by any unprivileged user calling `ft_transfer_call` into the bridge. No special permissions, front-running, or external dependencies are required. For a 24-vs-18 decimal token pair, the threshold is 1,000,000 base units — a realistic "dust" or small transfer amount. The `fee < amount` check at L554–557 is the only guard, and it passes trivially for any positive amount with zero fee.

## Recommendation

Add a normalization check inside `init_transfer` (or at the start of `init_transfer_internal`) **before** burning or locking tokens. Retrieve the token's `Decimals` for the destination chain and call `Self::normalize_amount` on `amount_without_fee()`; reject with `BridgeError::InvalidAmountToTransfer` if the result is zero. This mirrors the existing guard in `sign_transfer` but applies it before funds are committed.

Additionally, consider adding a public `cancel_transfer` function that allows the transfer owner to reclaim locked/burned tokens for transfers that are stuck in `pending_transfers` and cannot be signed.

## Proof of Concept

1. Register a NEAR-native token with `origin_decimals = 24`, `decimals = 18` (divisor = `10^6`).
2. Call `ft_transfer_call` on the token contract with `amount = 500_000` and `msg` encoding an `InitTransferMsg` with `fee = 0` and any non-NEAR recipient.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000`). `init_transfer_internal` burns/locks `500_000` tokens. The transfer is stored in `pending_transfers`.
4. Call `sign_transfer` with the resulting `transfer_id`.
5. `normalize_amount(500_000, {decimals:18, origin_decimals:24})` = `500_000 / 1_000_000` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Repeat step 4 indefinitely — it always panics. The `500_000` tokens are permanently lost with no cancel path available.

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
