### Title
`validatePerasCert` Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain-Selection Manipulation via Fake Peras Boosts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives. Because `processCerts` calls this function to gate admission into the `PerasCertDB`, and because the `PerasCertDB` directly feeds the `PerasWeightSnapshot` used by chain selection, any unprivileged peer can inject arbitrarily-crafted Peras certificates that boost a non-canonical chain, causing an honest node to prefer it over the canonical chain.

---

### Finding Description

The default `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` provides the only in-scope implementation of `validatePerasCert`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function performs **zero cryptographic or structural checks**. It wraps the raw, peer-supplied `PerasCert` directly into a `ValidatedPerasCert` and returns `Right`. The `ValidatedPerasCert` wrapper is the type-level signal that a certificate has been verified; here it is issued unconditionally.

The inbound processing pipeline in `processCerts` calls this function as its sole admission gate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is admitted.

Admitted certificates are stored in `PerasCertDB`. `implGetWeightSnapshot` then derives the `PerasWeightSnapshot` directly from every certificate in the database:

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds)
          ]
  pure (WithFingerprint weights fp)
``` [3](#0-2) 

This snapshot is consumed directly by chain selection. `initialChainSelection` accepts a `PerasWeightSnapshot` parameter and passes it through to `preferAnchoredCandidate` / `compareAnchoredFragments`: [4](#0-3) 

`preferAnchoredCandidate` uses the snapshot to compute a weighted chain comparison. When the snapshot is non-empty (i.e., after an attacker injects a certificate), the Peras-weighted path is taken:

```haskell
| otherwise =
    case AF.intersect ours cand of
      Nothing -> error "precondition violated: fragments must intersect"
      Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
        case preferCandidate

          (weightedSelectView cfg weights oursSuffix)

``` [5](#0-4) 

The `PerasCertDB` is also consulted at `ChainDB` open time to seed the initial weight snapshot:

```haskell
initialWeights <- atomically $ PerasCertDB.getWeightSnapshot perasCertDB
chain <-
  ChainSel.initialChainSelection
    ...
    (forgetFingerprint initialWeights)
``` [6](#0-5) 

The analog to the original report is exact: `processCerts` contains the call to the validation function (`validateCert`, analogous to `checkConditions`), but the implementation of that function (`validatePerasCert`, analogous to the missing `conditionCheck` modifier) performs no actual check and always succeeds.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that names any block point as the "boosted block" and assigns it the full `perasWeight`. Because `validatePerasCert` never rejects any certificate, this fake certificate is stored in `PerasCertDB` and immediately reflected in the `PerasWeightSnapshot`. Chain selection then treats the attacker-chosen block as having a large Peras boost. If the attacker targets a block on a shorter or otherwise non-preferred fork, the node will switch to that fork, diverging from the canonical chain. This is a chain-selection safety failure triggered entirely by a crafted network message from an unprivileged peer.

---

### Likelihood Explanation

The Peras certificate mini-protocol is wired into the production `ChainDB` and `ChainSel` code paths. The `processCerts` function is reachable from any connected peer that speaks the Peras object-diffusion protocol. No key material, stake, or operator access is required. The stub is the only `BlockSupportsPeras` instance in the repository. Likelihood is **High** given the direct, unauthenticated network entry point.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the certificate's aggregate BLS signature against the claimed committee members' public keys.
2. Checks that the claimed voters collectively hold sufficient stake to meet the quorum threshold.
3. Verifies that the boosted block point is plausible (e.g., within the current volatile window).

Until a real implementation is available, the `processCerts` admission gate should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them, so that the `PerasWeightSnapshot` remains empty and chain selection is not affected by peer-supplied data.

---

### Proof of Concept

1. Connect to a node that has the Peras object-diffusion protocol enabled.
2. Send a `PerasCert` message naming the tip of a shorter competing fork as `pcCertBoostedBlock`, with `pcCertRound` set to any round not already in the `PerasCertDB`.
3. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
4. `implAddCert` stores the certificate; `implGetWeightSnapshot` now returns a snapshot with a large boost on the attacker-chosen block.
5. The next chain-selection run calls `preferAnchoredCandidate` with this snapshot; `weightedSelectView` assigns the boosted block a `WeightedSelectView` that dominates the canonical tip.
6. The node switches to the attacker-chosen fork. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
