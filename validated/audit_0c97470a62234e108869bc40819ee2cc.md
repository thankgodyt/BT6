Audit Report

## Title
Unhandled `send_tokens` Failure in Fast-Transfer Relayer Repayment Causes Permanent Relayer Fund Loss - (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `near/omni-bridge/src/lib.rs`, two code paths that repay a fast-transfer relayer call `send_tokens(…).detach()` — a fire-and-forget promise — and then immediately update the fast-transfer state to mark it finalised or remove it. If the detached promise fails, the relayer's pre-paid funds are permanently lost: the fast-transfer record is already gone or locked, so no retry path exists. A developer TODO comment at line 2484 explicitly acknowledges this unresolved problem.

## Finding Description

**Path 1 — `process_fin_transfer_to_other_chain` (lines 2028–2040):**

The code at lines 2028–2040 calls `send_tokens(…).detach()` and then unconditionally calls `mark_fast_transfer_as_finalised`. [1](#0-0) 

If the detached `send_tokens` promise fails (e.g., `ft_transfer` panics because the relayer has no storage registration, or gas is exhausted), the fast transfer is permanently finalised with no repayment to the relayer.

**Path 2 — `utxo_fin_transfer_fast` (lines 2518–2548):**

The fast-transfer record is removed or finalised **before** `send_tokens` is even called. [2](#0-1) 

The `require!(!fast_transfer_status.finalised, …)` guard at line 2524 blocks any re-entry once the record is finalised, confirming there is no retry path. [3](#0-2) 

**Developer acknowledgment:**

The TODO comment at line 2484 explicitly flags this unresolved problem: [4](#0-3) 

**Root cause:** `send_tokens` for non-deployed tokens uses a static `FT_TRANSFER_GAS` budget for `ft_transfer` with no callback to detect failure. [5](#0-4)  The state mutation (remove/finalise) happens before or immediately after the detached promise, with no rollback mechanism.

## Impact Explanation

A relayer who executed a fast transfer pre-paid the user on the destination chain with their own tokens. When the canonical proof is finalized on NEAR, the bridge attempts to repay the relayer via `send_tokens(…).detach()`. If that promise fails:

- For non-deployed tokens: the tokens remain locked inside the bridge contract with no on-chain mechanism for the relayer to claim them — **permanent freezing of bridged funds**.
- The fast-transfer record is already finalised or removed, so neither `utxo_fin_transfer_fast` nor `process_fin_transfer_to_other_chain` can be re-entered for the same transfer.
- The relayer has no on-chain recourse.

This matches the allowed Critical impact: **permanent freezing/loss of bridged funds**.

## Likelihood Explanation

`send_tokens` can fail under realistic conditions reachable by any registered relayer:

1. **Storage not registered**: For non-deployed tokens, `ft_transfer` panics if the recipient (relayer) has no storage registration in the token contract. A relayer who has never held that specific token on NEAR triggers this deterministically.
2. **Insufficient gas**: The static `FT_TRANSFER_GAS` allocation for `ft_transfer` may be insufficient for token contracts with non-trivial transfer logic.
3. **Token contract panic**: Any panic in the token contract (paused state, balance underflow, etc.) causes the detached promise to fail silently.

The fast-transfer flow is open to any registered relayer via `ft_transfer_call` → `ft_on_transfer` → `fast_fin_transfer`, and the repayment path is triggered by a separate connector call to `fin_transfer`. The failure condition (unregistered storage) is deterministic and not hypothetical.

## Recommendation

Replace the `.detach()` pattern with a proper callback that checks the promise result and, on failure, either re-stores the fast-transfer record or emits a recoverable event:

1. Do **not** call `mark_fast_transfer_as_finalised` / `remove_fast_transfer` before `send_tokens` succeeds.
2. Chain a callback (analogous to `fin_transfer_send_tokens_callback`) that inspects the promise result and reverts the state update on failure, allowing a retry.
3. Remove the `// TODO: check how to deal with failed send_tokens` comment once the fix is in place.

## Proof of Concept

1. Relayer R calls `ft_transfer_call` on a NEAR token contract, sending 1000 tokens to the bridge with a `FastFinTransferMsg` targeting a UTXO-chain recipient. The bridge records the fast transfer and sends tokens to the user on the destination chain.
2. The UTXO connector later calls `ft_on_transfer` with the canonical proof, triggering `utxo_fin_transfer_fast`.
3. Inside `utxo_fin_transfer_fast`, `remove_fast_transfer` is called (line 2530), then `send_tokens(token, R, 1000, "").detach()` (line 2542–2548).
4. R has never held this specific token on NEAR and has no storage registration. The `ft_transfer` call panics inside the detached promise. The NEAR runtime silently discards the failure.
5. The fast-transfer record is gone. R cannot call `utxo_fin_transfer_fast` again (record no longer exists). The 1000 tokens remain locked in the bridge contract. R has permanently lost their pre-paid funds.
