Unconditional Acceptance of Peras Certificates and Votes Without Cryptographic Validation Enables Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The sole `BlockSupportsPeras` instance in the codebase provides stub implementations of `validatePerasCert` and `validatePerasVote` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate it receives. `validatePerasVote` only checks that the claimed voter ID appears in the stake distribution, but never verifies the vote signature. Because these are the only instances in the repository, every production code path that validates Peras certificates or votes uses these stubs. An unprivileged peer can therefore send a crafted certificate boosting any block and have it accepted, stored in `PerasCertDB`, and used to trigger chain selection — potentially causing an honest node to prefer a non-canonical chain.

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate/vote verification enabling unauthorized certificate acceptance and chain selection manipulation.**

A Peras certificate carries a cryptographic boost weight (`vpcCertBoost`) that is added to a block's chain-selection score. Because `validatePerasCert` unconditionally wraps any received `PerasCert` as `ValidatedPerasCert` with the full `perasWeight`, an attacker can:

1. Send a crafted `PerasCert` naming any block hash and any round number.
2. The certificate passes validation (stub returns `Right`), is stored in `PerasCertDB`, and triggers `chainSelectionForBlock` for the named block.
3. If the named block is already in the node's `VolatileDB`, the node re-evaluates chain selection with the forged boost weight applied, potentially switching to the attacker's fork.

For votes: an attacker who knows the stake distribution (public information) can forge votes for any staked voter, accumulate enough forged votes to reach quorum, and cause the node to internally forge a certificate boosting an attacker-chosen block — all without possessing any private key.

This directly satisfies: *"Critical. Bypass of … certificate/vote verification … that enables unauthorized … certificate acceptance."* and *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

**Likelihood: High.**

- The entry path is a standard miniprotocol handler reachable by any peer that connects to the node.
- No special privileges, stake majority, or key material are required.
- The attacker only needs to know the hash of a block already present in the target node's `VolatileDB` (obtainable via `ChainSync`).
- The stub is the only instance in the repository; there is no override for Cardano-specific block types.
- The TODO comments and linked issue (`cardano-peras/issues/120`) confirm the missing validation is a known, unresolved gap, not an intentional design choice.

---

### Recommendation

1. **Implement `validatePerasCert`** to perform full cryptographic verification: verify the aggregate BLS signature over the certificate body, check that the signing committee members are eligible for the claimed round, verify each member's VRF output (for non-persistent members), and validate round-number bounds against the current epoch.

2. **Implement `validatePerasVote`** to verify the vote signature using the voter's public key from the committee, in addition to the existing stake-distribution lookup.

3. Until real validation is implemented, **disable the Peras certificate and vote inbound miniprotocol handlers** in production builds, or gate them behind a feature flag, to prevent the stub from being reachable by untrusted peers.

4. Add a compile-time or runtime assertion that the degenerate `instance StandardHash blk => BlockSupportsPeras blk` is never used in a production node configuration.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer (attacker)
  → sends PerasCert { pcCertRound = R, pcCertBoostedBlock = <attacker_block_point> }
    via Peras certificate miniprotocol

Node receives cert
  → processCerts (PerasCert.hs:164)
      → filter already-in-db (round R not yet seen → passes)
      → validatePerasCert mkPerasParams cert
           -- stub: returns Right (ValidatedPerasCert cert perasWeight)
           -- NO signature check, NO committee check, NO round bounds check
      → addCert (ChainDB.addPerasCertAsync)

ChainDB background thread
  → chainSelSync (ChainSel.hs:483)
      → PerasCertDB.addCert  (stored, round R now in pcdsCertIds)
      → VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash
           -- if attacker's block is in VolatileDB (e.g. sent earlier via BlockFetch):
      → chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
           -- chain selection re-runs with forged boost weight on attacker's block
           -- node may switch to attacker's fork
```

The forged certificate is indistinguishable from a legitimate one because `validatePerasCert` performs no checks. The node stores it, applies its boost weight, and may irreversibly switch its preferred chain to the attacker's fork.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
```
