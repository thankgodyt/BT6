### Title
`lost_found` nBTC Escrow Has No Recipient-Flexible Recovery Path — Tokens Permanently Locked When Recipient Cannot Receive - (File: contracts/satoshi-bridge/src/token_transfer.rs)

### Summary

The bridge uses a `lost_found` map as a fallback escrow when `internal_transfer_nbtc` fails. Analogous to the `pendingWithdrawals` pattern in the external report, the `lost_found` entry is keyed by the original recipient `account_id`. If that account cannot receive nBTC tokens (e.g., not registered for storage on the nBTC contract, or the account is deleted), there is no mechanism to redirect the escrowed tokens to an alternative address. The tokens are permanently locked in the bridge contract.

### Finding Description

`internal_transfer_nbtc` in `token_transfer.rs` issues an `ft_transfer` cross-contract call to the nBTC contract. If the call fails, `transfer_nbtc_callback` records the amount in `lost_found[account_id]`: [1](#0-0) 

The `lost_found` map is keyed by the original `account_id`. Any future recovery attempt must send tokens back to that same address. If the address is not registered for storage on the nBTC contract (a hard requirement for NEP-141 `ft_transfer`), every recovery attempt will also fail, leaving the tokens permanently stuck.

This fallback is triggered in `verify_withdraw_burn_callback` when a cancel-withdraw RBF is finalized and a refund is owed to the user: [2](#0-1) 

The `.detach()` call means the promise result is not propagated to the parent callback — the burn has already been committed, the UTXOs released, and the pending info removed. If the `ft_transfer` then fails, the only record of the owed tokens is the `lost_found` entry, with no alternative recipient path.

The `lost_found` storage key is declared in contract state: [3](#0-2) 

No `withdraw_lost_found_to(to: AccountId)` or equivalent function was found in the scanned production source. The only recovery path (if any) would re-attempt `ft_transfer` to the same locked address.

### Impact Explanation

nBTC tokens owed to a user as a cancel-withdraw refund are permanently locked inside the bridge contract with no operator or user recovery path. The tokens are correctly attributed to the user in `lost_found` but cannot be extracted. This constitutes a stuck bridge state requiring operator intervention and matches the Medium impact class: *broken callback rollback or stuck bridge state requiring operator intervention*.

### Likelihood Explanation

Any NEAR account that initiates a withdrawal, then triggers a cancel-withdraw RBF, and whose account is not registered for storage on the nBTC contract at the time of finalization will trigger this path. A user who unregisters from the nBTC contract between initiating the withdrawal and the cancel-RBF finalization, or a smart-contract account that never registered, will permanently lose their refund. This is a realistic scenario for contract-controlled accounts.

### Recommendation

Add a `withdraw_lost_found_to(to: AccountId)` function (analogous to the `withdrawTo` fix suggested in the external report) that allows `msg.sender` (the account recorded in `lost_found`) to redirect their escrowed tokens to a different, storage-registered recipient address:

```rust
pub fn withdraw_lost_found_to(&mut self, to: AccountId) -> Promise {
    assert_one_yocto();
    let caller = env::predecessor_account_id();
    let amount = self.data_mut().lost_found.remove(&caller)
        .expect("No lost_found balance for caller");
    self.internal_transfer_nbtc(&to, amount)
}
```

This mirrors the `withdrawTo` mitigation recommended in the external report and ensures that even if the original address cannot receive tokens, the user retains control over where their funds are sent.

### Proof of Concept

1. User (a smart-contract account `victim.near`) calls `ft_transfer_call` on nBTC, initiating a withdrawal.
2. User triggers a cancel-withdraw RBF. The bridge finalizes the cancel RBF, burning `burn_amount` and computing `refund > 0`.
3. `verify_withdraw_burn_callback` calls `self.internal_transfer_nbtc(&victim.near, refund).detach()`.
4. `victim.near` is not registered for storage on the nBTC contract. The `ft_transfer` cross-contract call fails.
5. `transfer_nbtc_callback` records `lost_found[victim.near] += refund`.
6. `victim.near` attempts recovery. Any recovery function re-calls `ft_transfer` to `victim.near`, which fails again for the same reason.
7. The `refund` amount of nBTC is permanently locked in the bridge, with no path to redirect it to a registered address. [4](#0-3) [5](#0-4) [6](#0-5) [2](#0-1)
