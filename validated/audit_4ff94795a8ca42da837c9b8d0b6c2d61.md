### Title
Single-Step `set_controller` Transfer Allows Outgoing Controller to Poison `withdraw_relayer_address`, Permanently Redirecting User nBTC Funds — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `nbtc` token contract's `set_controller` function performs a direct, single-step controller handoff with no acceptance mechanism from the incoming party. The outgoing controller can atomically front-run the handoff by first calling `set_withdraw_relayer_address` with an attacker-controlled account. After the transfer completes, the new controller holds the role but the withdraw-relayer slot is permanently poisoned. Every subsequent user `ft_transfer` that uses the legacy `WITHDRAW_TO:` memo pattern silently sends the user's nBTC to the attacker's account instead of the intended destination.

---

### Finding Description

**Root cause — single-step controller transfer with no accept step:**

`set_controller` overwrites `self.controller` in one atomic call with no pending-transfer state and no confirmation from the incoming controller. [1](#0-0) 

**Privileged pre-transfer action — poisoning the withdraw relayer:**

`set_withdraw_relayer_address` is gated solely by `assert_controller()`. The outgoing controller can call it immediately before (or in the same block as) `set_controller`, writing an arbitrary `AccountId` into the raw storage slot `WITHDRAW_RELAYER_ADDRESS`. [2](#0-1) 

**Victim path — silent fund redirection in `ft_transfer`:**

Any user who calls `ft_transfer` with `receiver_id == nbtc_contract_id` and a memo beginning with `"WITHDRAW_TO:"` (the Near Intents legacy bridging flow) has their tokens silently redirected to whatever address is stored in `WITHDRAW_RELAYER_ADDRESS`. There is no validation that the stored address is legitimate, and there is no public view function exposing the current value, so the new controller may not even detect the poisoning. [3](#0-2) 

**No public read path for the poisoned slot:**

`read_withdraw_relayer_address` is a private helper; the new controller cannot query the current value through the contract's public API to detect the attack. [4](#0-3) 

---

### Impact Explanation

Every user who relies on the `WITHDRAW_TO:` legacy flow (Near Intents integration) after the poisoned handoff loses their entire nBTC transfer amount to the attacker. Because the redirection is silent — `ft_transfer` returns normally — users receive no error and may not notice until they check their balance. The attacker retains the stolen nBTC indefinitely. This constitutes **significant theft of user funds** matching the Critical impact tier.

---

### Likelihood Explanation

The scenario requires the outgoing controller to act maliciously at the moment of a handoff. Controller handoffs are rare but real operational events (governance migrations, DAO transitions). The two-call sequence (`set_withdraw_relayer_address` then `set_controller`) is trivially executable in a single NEAR block with no special tooling. The new controller has no on-chain mechanism to verify the pre-handoff state of the relayer slot, making detection before harm difficult.

---

### Recommendation

1. **Two-step controller transfer**: Introduce a `propose_controller` / `accept_controller` pattern (analogous to OpenZeppelin `Ownable2Step`). The incoming controller must explicitly accept before `self.controller` is updated, giving them the opportunity to inspect contract state first.
2. **Public view for withdraw relayer**: Expose `get_withdraw_relayer_address() -> Option<AccountId>` so any party can audit the current value before and after a handoff.
3. **Emit an event** in `set_withdraw_relayer_address` so on-chain monitors can detect unexpected changes.

---

### Proof of Concept

```
// Step 1 — outgoing controller poisons the relayer slot
nbtc.set_withdraw_relayer_address(attacker_account)   // controller-only, no yocto required

// Step 2 — outgoing controller completes the handoff
nbtc.set_controller(new_controller, deposit=1_yocto)

// Step 3 — new controller now holds the role; relayer slot is silently poisoned.
// Any user executing the Near Intents legacy withdrawal:
nbtc.ft_transfer(
    receiver_id = nbtc_contract_id,
    amount      = 1_000_000,          // user's nBTC
    memo        = "WITHDRAW_TO:bc1q..."
)
// → ft_transfer reads WITHDRAW_RELAYER_ADDRESS → attacker_account
// → self.token.ft_transfer(attacker_account, 1_000_000, memo)
// → user's 1_000_000 nBTC transferred to attacker; user receives nothing
```

The attack requires zero unprivileged capability — it is entirely within the outgoing controller's existing authority window, executed before relinquishing that authority, with no recourse for the new controller or affected users.

        // Legacy bridging flow used by Near Intents

            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))

                return self.token.ft_transfer(withdraw_relayer, amount, memo);
            }
        }

        self.token.ft_transfer(receiver_id, amount, memo);
    }
