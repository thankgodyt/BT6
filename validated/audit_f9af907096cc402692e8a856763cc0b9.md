### Title
Inverted Vacuous Predicate in `noCertsFromTwoRoundsAgo` Permanently Blocks Peras Certificate Inclusion in Rounds 0 and 1 - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Cert/Inclusion.hs`)

---

### Summary

The `noCertsFromTwoRoundsAgo` function in `Inclusion.hs` returns `Bool False` when `currRoundNo < 2`, asserting that the predicate "we haven't seen a certificate from two rounds ago" is **False** during rounds 0 and 1. This is logically inverted: since rounds −2 and −1 do not exist, the predicate is vacuously **True**, not False. Because `needCertRules` is a strict conjunction (`:/\:`), this single False short-circuits the entire rule, causing `needCert` to unconditionally return `DoNotIncludeCert` for every block built in rounds 0 and 1, regardless of whether a valid certificate is available. The test model in `Test/Consensus/Peras/Cert/Inclusion.hs` replicates the same wrong value, so the conformance property test passes and masks the defect.

---

### Finding Description

**Root cause — wrong boolean literal in the vacuous branch:** [1](#0-0) 

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously false.   ← comment is wrong
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool False    -- ← should be Bool True
```

The predicate is named `NoCertsFromTwoRoundsAgo` and is documented as "we haven't seen a certificate from two rounds ago." [2](#0-1) 

- `Bool True` → predicate holds → "there are no certs from two rounds ago" → inclusion may proceed.
- `Bool False` → predicate fails → "there ARE certs from two rounds ago" → inclusion is blocked.

When `currRoundNo` is 0 or 1, rounds −2 and −1 do not exist, so the predicate is vacuously **True**. The code returns `Bool False`, the opposite value.

**The `explain Deep` text confirms the correct intent:** [3](#0-2) 

```haskell
NoCertsFromTwoRoundsAgo currRoundNo
  | currRoundNo < 2 ->
      "we are in round "
        <> condense currRoundNo
        <> ", so we cannot have seen a certificate from two rounds ago"
```

The explanation correctly states the condition is satisfied (no certs from two rounds ago), yet the predicate value contradicts it.

**Propagation through `needCertRules`:** [4](#0-3) 

```haskell
needCertRules pciv =
  noCertsFromTwoRoundsAgo pciv          -- ← always False when currRoundNo < 2
    :/\: latestCertSeenIsNotExpired pciv
    :/\: latestCertSeenIsNewerThanLatestCertOnChain pciv
```

`evalPred` short-circuits on the first `False` in a conjunction: [5](#0-4) 

```haskell
a :/\: b ->
  case go a of
    Left a' -> Left a'   -- short-circuit: entire conjunction is False
```

So `needCert` always returns `DoNotIncludeCert` in rounds 0 and 1, regardless of the other two rules. [6](#0-5) 

**The test model carries the same bug, masking it:** [7](#0-6) 

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then False   -- ← same wrong value as the production code
    else not ((currRoundNo - 2) `Set.member` certIds)
```

Because both the implementation and the model return `False` for `currRoundNo < 2`, `prop_needCert` passes, giving false confidence.

---

### Impact Explanation

The Peras protocol (CIP-0140) uses certificates to boost chains. A block producer who has seen a valid certificate in round 0 must include it in a block built during round 1 (if the other two inclusion conditions hold). The bug unconditionally suppresses this inclusion for every honest block producer in rounds 0 and 1. Certificates earned in round 0 are never embedded on-chain during round 1, so the chain-boosting weight those certificates carry is permanently lost for those rounds. An adversary who knows honest nodes will not include round-0 certificates can present a competing fork that would otherwise be outweighed by the boosted canonical chain, materially weakening the Peras chain-selection security guarantee during the protocol's initial rounds.

This matches the allowed impact: **"Medium — public node API or miniprotocol flaw that materially weakens certificate … authorization"** and borders on **High** ("chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical … chain beyond the intended security assumptions").

---

### Likelihood Explanation

No attacker action is required to trigger the bug. Every honest Peras-enabled block producer is affected automatically during rounds 0 and 1 of any Peras epoch. The defect is deterministic and reproducible on any private testnet running the Peras extension. The masking test model means the bug survives the existing test suite undetected.

---

### Recommendation

Change `Bool False` to `Bool True` in the `currRoundNo < 2` branch of `noCertsFromTwoRoundsAgo`:

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously TRUE.
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool True
```

Fix the same error in the test model: [7](#0-6) 

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then True   -- vacuously true: no rounds -2 or -1 exist
    else not ((currRoundNo - 2) `Set.member` certIds)
```

After the fix, `prop_needCert` will correctly exercise the case where `currRoundNo < 2` and a valid certificate is available, and `needCert` will return `IncludeCert` when the other two rules are also satisfied.

---

### Proof of Concept

1. Construct a `PerasCertInclusionView` with `currRoundNo = 1`, a non-`Origin` `latestCertSeen` (cert from round 0), `latestCertOnChain = Origin`, and any `certIds`.
2. Call `needCert` on this view.
3. **Expected** (per CIP-0140): `IncludeCert` — round 0 cert should be included in a round-1 block.
4. **Actual**: `DoNotIncludeCert` — `noCertsFromTwoRoundsAgo` returns `Bool False`, short-circuiting the conjunction.

The same result holds for `currRoundNo = 0` with a cert from round 0 (e.g., a cert produced mid-round before the block is built). In both cases the `explain Deep` output will paradoxically read *"we are in round 0/1, so we cannot have seen a certificate from two rounds ago"* as the stated reason for **not** including the certificate — a self-contradictory diagnostic that confirms the inversion.
