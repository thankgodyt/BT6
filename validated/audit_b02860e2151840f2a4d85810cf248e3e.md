### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`) passes a degenerate stub — `validatePerasCert mkPerasParams` — as the certificate validation function to `processCerts`. This stub unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic checks. Any unprivileged peer can therefore inject an arbitrary `PerasCert` (with a fabricated round number and boosted-block pointer) that will be accepted, stored, and used to influence chain selection.

---

### Finding Description

**Vulnerable call site — production pool writer:**

In `makePerasCertPoolWriterFromChainDB`, the `opwAddObjects` field calls `processCerts` with `validatePerasCert mkPerasParams` as the validation callback:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [1](#0-0) 

The comment explicitly acknowledges this is a placeholder, but the code is live and reachable in the production path. The same pattern appears in `makePerasCertPoolWriterFromCertDB`: [2](#0-1) 

**The stub implementation — unconditional `Right`:**

The `BlockSupportsPeras` instance (the only instance in scope, explicitly labelled "degenerate instance for all blks") implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [3](#0-2) 

This stub skips every check that a real implementation must perform:
- BLS aggregate signature verification over the claimed voters
- Committee membership and seat-index bounds checks
- VRF eligibility proofs for non-persistent voters
- Round-number and boosted-block semantic validity

**`processCerts` trusts the result:**

`processCerts` partitions the results of `validateCert` and, if all pass, timestamps and stores each certificate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because the stub never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is stored.

**Chain selection is then affected:**

The production writer passes `ChainDB.addPerasCertAsync chainDB` as the `addCert` action, meaning accepted certificates are forwarded directly into chain selection: [5](#0-4) 

A `ValidatedPerasCert` carries a `vpcCertBoost` weight (`perasWeight params = PerasWeight 15` from `mkPerasParams`) that is applied to the boosted block during chain selection: [6](#0-5) 

---

### Impact Explanation

An unprivileged peer connected via the object-diffusion mini-protocol can craft a `PerasCert` with:
- An arbitrary `pcCertRound` (any round number not yet in the DB)
- An arbitrary `pcCertBoostedBlock` (any block point, including one on a minority or adversarial fork)

The node will accept it, store it, and apply a weight boost of 15 to the targeted block during chain selection. By injecting certificates that boost blocks on a weaker fork, an adversary can cause an honest node to prefer a non-canonical chain, violating Peras's chain-selection invariants. This matches the **High** impact category: a chain-selection bug triggered by an unprivileged peer that makes an honest node prefer a less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The entry path is the standard Peras certificate diffusion mini-protocol, reachable by any connected peer. No special privileges, keys, or stake are required — only the ability to send a well-formed CBOR-encoded `PerasCert` message. The `PerasCert` type is simple (round number + boosted block point) and trivially constructable: [7](#0-6) 

The only natural rate-limiter is the per-round deduplication check (`Set.member roundNo certIds`), which means one fabricated certificate per round number can be injected. Given that Peras rounds are 90 slots long (`perasRoundLength = PerasRoundLength 90`), an attacker can inject one boosting certificate roughly every 90 slots indefinitely. [8](#0-7) 

---

### Recommendation

Replace the stub `validatePerasCert mkPerasParams` call in both `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` with a real validation function that:
1. Verifies the BLS aggregate signature against the claimed voter set.
2. Checks each voter's committee membership and seat-index bounds.
3. Verifies VRF eligibility proofs for non-persistent voters.
4. Validates the round number and boosted-block point against the current ledger state.

Until a real implementation is available, the production writer (`makePerasCertPoolWriterFromChainDB`) should reject all inbound certificates (return `Left` unconditionally) rather than accept them all, mirroring the recommendation in the external report: *"reject the transaction … since the feature is not enabled yet."*

### Proof of Concept

1. Connect to a node running this codebase as a peer via the object-diffusion mini-protocol for Peras certificates.
2. Construct a `PerasCert` value:
   ```haskell
   PerasCert
     { pcCertRound = PerasRoundNo 42          -- any round not yet in DB
     , pcCertBoostedBlock = <point on fork>   -- any block point
     }
   ```
3. Send it as a batch of one certificate via `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = PerasWeight 15}` without any checks.
5. The certificate is timestamped and passed to `ChainDB.addPerasCertAsync`, applying a weight of 15 to the targeted block in chain selection.
6. The node's preferred chain now includes the adversarially boosted block, deviating from the canonical chain. [9](#0-8) [10](#0-9)

  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  ChainDB m blk ->
  ObjectPoolWriter PerasRoundNo (PerasCert blk) m
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.
          -- The async action is still launched and executed behind the scenes
          -- even though we drop the promise.
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    , opwHasObject = do
        certIds <- ChainDB.getPerasCertIds chainDB
        pure $ \roundNo -> Set.member roundNo certIds
    }
