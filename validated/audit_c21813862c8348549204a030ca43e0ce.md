### Title
Peras Certificate and Vote Validation Stubs Unconditionally Accept All Inbound Objects, Enabling Unauthorized Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types contains stub implementations of `validatePerasCert` and `validatePerasVote` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate it receives. `validatePerasVote` only checks that the voter ID exists in the stake distribution but never verifies the BLS signature or VRF eligibility proof. Because the Peras vote and certificate object-diffusion protocol is live, an unprivileged peer can send crafted votes (using any publicly known voter ID) or crafted certificates to immediately inject a `PerasWeightSnapshot` boost onto an adversarial fork, causing the victim node to prefer and switch to that fork via chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` is an unconditional stub:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every `PerasCert` received from any peer is immediately wrapped in `ValidatedPerasCert` and assigned the full `perasWeight` boost without any check on round number, boosted-block validity, quorum proof, or aggregate BLS signature.

**Root cause — `validatePerasVote` skips all cryptographic checks:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

The only check is `lookupPerasVoteStake`, which looks up the `PerasVoterId` in the stake distribution map. Voter IDs are stake-pool key hashes — public information. The BLS vote signature (`pvSignature`) and the VRF eligibility proof (`pvEligibilityProof`) carried in the concrete `V1.PerasVote` type are never verified. [3](#0-2) 

**This degenerate instance applies to all block types**, including `CardanoBlock`, because no specific override exists:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [4](#0-3) 

**Exploit path — votes:**

1. Attacker connects as an unprivileged peer and sends crafted `PerasVote` objects via the object-diffusion mini-protocol.
2. `makePerasVotePoolWriterFromChainDB` calls `processVotes`, which calls `validatePerasVote mkPerasParams sd vote` for each vote. [5](#0-4) 

3. Because only the voter ID is checked, the attacker forges votes for any known pool ID targeting an adversarial block. Once enough forged votes accumulate to exceed the quorum threshold, `updatePerasRoundVoteStates` fires `VoteGeneratedNewCert`. [6](#0-5) 

4. `addPerasVoteWithAsyncCertHandling` enqueues the forged certificate via `addPerasCertAsync`. [7](#0-6) 

**Exploit path — direct certificate injection:**

Alternatively, the attacker sends a crafted `PerasCert` directly. `validatePerasCert` returns `Right` unconditionally, so the cert is immediately added to `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block. [8](#0-7) 

**Chain-selection impact:**

When `PerasWeightSnapshot` is non-empty, `preferAnchoredCandidate` switches from simple block-number comparison to `weightedSelectView`, which adds `weightBoostOfFragment` to the total weight. A single forged certificate with `perasWeight = 15` (the default) outweighs 15 honest blocks, causing the node to immediately switch to the adversarial fork. [9](#0-8) [10](#0-9) 

---

### Impact Explanation

**Critical — Bypass of Peras certificate/vote verification enabling unauthorized certificate acceptance and chain-selection divergence.**

An unprivileged peer with knowledge of any registered stake-pool key hash (public on-chain data) can:

- Forge votes for an adversarial block without possessing any signing key.
- Inject a certificate that immediately boosts an adversarial fork by `perasWeight` (default 15) blocks of equivalent weight.
- Cause the victim node to switch its selected chain to the adversarial fork, diverging from the honest network.

This is a direct analog to the external report: just as the immediately-upgradeable Exchange.sol proxy allows a malicious actor to abuse the trust users placed in the original contract without any delay, the stub `validatePerasCert`/`validatePerasVote` allows a malicious peer to abuse the trust the chain-selection logic places in "validated" certificates without any cryptographic barrier.

---

### Likelihood Explanation

The Peras vote and certificate object-diffusion infrastructure is fully wired into the production `ChainDB` and mini-protocol stack. Any peer that can establish a connection and speak the Peras object-diffusion sub-protocol can send crafted votes or certificates. Voter IDs are public. No privileged access, leaked keys, or stake majority is required. The only prerequisite is that Peras weight-based chain selection is active (i.e., `isEmptyPerasWeightSnapshot` returns `False` after the first certificate is accepted).

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` and `validatePerasVote` before enabling Peras on any network where the object-diffusion protocol is reachable. At minimum, verify the aggregate BLS signature over `(roundNo, boostedBlock)` against the claimed committee members' public keys, and verify the VRF eligibility proof for non-persistent voters.
2. **Gate the degenerate instance** so it is only compiled into test builds, not production. Add a compile-time or runtime guard that prevents the stub from being used when Peras is enabled.
3. **Add a round-number validity check** in `validatePerasCert` to reject certificates for rounds that are too old or too far in the future relative to the current slot.
4. **Track the GitHub issues** (`#73`, `#120`) as security-blocking items before any Peras mainnet activation.

---

### Proof of Concept

```
Attacker (unprivileged peer, knows pool ID P):

1. Observe on-chain stake distribution → obtain PerasVoterId for pool P.
2. Craft N PerasVote objects:
     { pvVoteRound = currentRound
     , pvVoteBlock = adversarialBlockPoint
     , pvVoteVoterId = P   -- no signature needed
     }
   where N * stake(P) > quorumThreshold * totalStake.
3. Send votes via Peras object-diffusion protocol.
4. processVotes calls validatePerasVote mkPerasParams sd vote:
     lookupPerasVoteStake vote sd = Just stake(P)  -- passes
     BLS signature: NOT CHECKED
     VRF proof:     NOT CHECKED
5. Votes accumulate → updatePerasRoundVoteStates fires VoteGeneratedNewCert.
6. forgePerasCert returns Right (also a stub, no validation).
7. Certificate added to PerasCertDB; addToPerasWeightSnapshot boosts adversarialBlockPoint.
8. Next chainSelectionForBlock call: preferAnchoredCandidate uses weightedSelectView,
   adversarial fork has total weight = blockNo + 15 (perasWeight) > honest fork.
9. Node switches to adversarial fork.
``` [11](#0-10) [12](#0-11)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
