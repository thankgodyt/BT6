### Title
Peras Certificate Validation Unconditionally Accepts Any Attacker-Crafted Certificate, Enabling Chain-Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method of the `BlockSupportsPeras` typeclass is implemented as a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. This is the only instance in the production codebase. Any unprivileged peer can therefore inject a crafted `PerasCert` with an arbitrary `pcBoostedBlock` and have it accepted as a `ValidatedPerasCert`, causing the receiving node to apply a Peras boost weight to an attacker-chosen block and potentially prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a certificate is wrapped in `ValidatedPerasCert` and stored in the `PerasCertDB`. The sole production instance is a catch-all for `StandardHash blk`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The `ValidatedPerasCert` wrapper is the type-level proof that a certificate has been validated. Because `validatePerasCert` always returns `Right`, the wrapper is granted to every certificate regardless of its content. No more specific instance for Cardano/Shelley blocks exists in the codebase to override this behaviour.

The `PerasCertDB` stores `ValidatedPerasCert` values and exposes them to chain selection via `getWeightSnapshot`:

```haskell
, getWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
-- ^ Return the Peras weights in order compare the current selection against
-- potential candidate chains
``` [2](#0-1) 

The boost weight applied to the boosted block is `perasWeight params`, a protocol-level constant. An attacker who injects a certificate pointing to a block on a minority fork causes that block to receive the full Peras boost, making the minority chain appear heavier to chain selection.

The `addCert` path in `PerasCertDB` accepts a `WithArrivalTime (ValidatedPerasCert blk)` directly:

```haskell
addCert ::
    WithArrivalTime (ValidatedPerasCert blk) ->
    STM m (m AddPerasCertResult)
``` [3](#0-2) 

Because `validatePerasCert` is the only gate before `ValidatedPerasCert` is constructed, and it is a no-op, the `ValidatedPerasCert` type guarantee is hollow.

**Analog to the external report**: In the Solidity report, `sender == address(this)` is checked but `sender` is a caller-supplied parameter, so the attacker passes `sender = address(this)` to bypass the check. Here, `validatePerasCert` is the "check" and the certificate is the "caller-supplied parameter" — but the check unconditionally returns success, so any crafted certificate bypasses it.

---

### Impact Explanation

**High — Chain selection bug.** An unprivileged peer can send a crafted `PerasCert` whose `pcBoostedBlock` points to any block (including one on a minority or attacker-controlled fork). The certificate passes `validatePerasCert`, is stored in `PerasCertDB`, and its boost weight is applied to chain selection. If the boost is large enough relative to the honest chain's length advantage, the receiving node will switch to the attacker's fork. This violates the Peras security assumption that only legitimately quorum-certified blocks receive a boost.

---

### Likelihood Explanation

**High.** The entry path is the Peras mini-protocol, which is reachable by any peer without any privileged credentials. The stub is the only instance in the production codebase. No secondary check downstream re-validates the certificate before its weight is applied to chain selection. The TODO comment and linked GitHub issue confirm the validation is intentionally absent in the current code.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature in `pcSignature` against the claimed voters' public keys and the `(pcRoundNo, pcBoostedBlock)` message.
2. Verifies each voter's eligibility (seat index within bounds, non-zero stake, VRF proof for non-persistent members) against the epoch's voting committee.
3. Checks that the total vote weight of the claimed voters meets the quorum threshold.

Until a real implementation exists, the `ValidatedPerasCert` wrapper should not be constructible from an unvalidated certificate, and the Peras mini-protocol handler should refuse to accept certificates if validation is not yet implemented.

---

### Proof of Concept

1. Attacker connects to an honest node as a peer via the Peras mini-protocol.
2. Attacker constructs a `PerasCert` with:
   - `pcRoundNo` = any round number
   - `pcBoostedBlock` = the hash of a block on the attacker's minority fork
   - `pcVoters` = any non-empty voter bitmap (e.g., a single seat index)
   - `pcSignature` = any bytes (e.g., all zeros)
3. Attacker sends the certificate to the honest node.
4. The node calls `validatePerasCert params cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate is stored in `PerasCertDB` via `addCert`.
6. `getWeightSnapshot` now includes a boost for the attacker's block.
7. Chain selection compares the honest chain against the attacker's fork using Peras-weighted chain length; if the boost exceeds the honest chain's length advantage, the node switches to the attacker's fork. [4](#0-3) [3](#0-2) [2](#0-1)
