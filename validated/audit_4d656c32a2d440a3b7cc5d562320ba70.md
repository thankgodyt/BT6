### Title
Race Condition in Token Migration Allows In-Flight Withdrawal Burn to Target New Token While Bridge Holds Only Old Tokens — (`contracts/satoshi-bridge/src/nbtc/migration.rs`, `contracts/satoshi-bridge/src/nbtc/burn.rs`)

---

### Summary

A race condition in NEAR's async cross-contract call model allows a user's `ft_transfer_call` to execute between the balance-query phase and the resolve phase of `migrate_to_new_token`. When this happens, the migration mints new tokens to the user based on their pre-transfer balance, then updates `nbtc_account_id` to the new token. Subsequent `verify_withdraw` calls attempt to burn from the bridge's balance on the **new** token contract, but the bridge holds only **old** tokens. The burn fails on every retry, leaving the withdrawal permanently oscillating between `PendingVerify` and `PendingBurn` with no on-chain recovery path.

---

### Finding Description

**Step 1 — Migration balance queries (time T1)**

`internal_migrate_to_new_token` fires parallel `ft_balance_of` queries against the old token for each account in `accounts`, plus `ft_total_supply`. [1](#0-0) 

At T1 the bridge's old-token balance is 0 (no in-flight withdrawal yet), and the user's balance is X. `sum == total_supply` passes.

**Step 2 — User's `ft_transfer_call` executes (time T2, T1 < T2 < T3)**

The user calls `ft_transfer_call` on the old token. The old token contract transfers X tokens from the user to the bridge, then calls `ft_on_transfer` on the bridge. The bridge validates `token_id == nbtc_account_id` (still the old token at this point) and creates a `BTCPendingInfo`. [2](#0-1) [3](#0-2) 

After T2: bridge holds X old tokens; user holds 0 old tokens.

**Step 3 — `migrate_to_new_token_mint` callback (time T3)**

The callback uses the T1 snapshot: user balance = X, bridge balance = 0. It mints X new tokens to the user and 0 to the bridge. [4](#0-3) 

**Step 4 — `migrate_to_new_token_resolve` updates `nbtc_account_id`** [5](#0-4) 

From this point every bridge function that reads `config.nbtc_account_id` targets the new token.

**Step 5 — `verify_withdraw_burn_promise` targets new token**

`verify_withdraw_burn_promise` reads `config.nbtc_account_id` at call time and issues `burn` against the **new** token contract. [6](#0-5) 

**Step 6 — New token's `burn` withdraws from bridge's balance on the new token**

The new token's `burn` implementation calls `internal_withdraw(&self.bridge_id, burn_amount)` — it burns from the bridge's balance on the **new** token contract. [7](#0-6) 

The bridge has **zero** new-token balance (it was not included in the migration mint). `internal_withdraw` panics → promise fails.

**Step 7 — Callback reverts to `PendingVerify`, loop begins** [8](#0-7) 

Every subsequent `verify_withdraw_v2` call repeats steps 5–7. There is no on-chain escape hatch: `internal_transfer_nbtc` also reads `nbtc_account_id` (new token), so even a refund path would fail because the bridge holds no new tokens. [9](#0-8) 

---

### Impact Explanation

- The user's withdrawal is permanently stuck in a `PendingVerify ↔ PendingBurn` loop with no on-chain resolution.
- The bridge holds X old tokens that cannot be burned (wrong token contract) and cannot be refunded (bridge has no new tokens to transfer).
- The user simultaneously holds X new tokens (minted during migration) and has X old tokens locked in the bridge — the old-token supply is inflated relative to the new-token supply by X until an operator manually intervenes.
- Resolution requires a privileged contract upgrade or manual state surgery; no existing public call can clear the stuck `BTCPendingInfo`.

---

### Likelihood Explanation

NEAR's async receipt model guarantees a multi-block window between the balance-query receipt and the resolve receipt. A user watching the chain can submit `ft_transfer_call` in the very next block after observing the migration transaction. No special privilege is required beyond holding old nBTC. The migration is a rare but documented operational event, making the window predictable.

---

### Recommendation

1. **Snapshot in-flight bridge balance at migration time.** Before updating `nbtc_account_id`, verify that the bridge's old-token balance is zero, or explicitly include the bridge contract in the `accounts` list so it receives an equivalent new-token mint.
2. **Guard `ft_on_transfer` during migration.** Pause the bridge (or reject `ft_on_transfer` for withdrawals) from the moment `migrate_to_new_token` is called until `migrate_to_new_token_resolve` completes.
3. **Add a token-aware burn path.** Store the token contract address inside each `BTCPendingInfo` at creation time so the burn always targets the token the bridge actually holds, regardless of later `nbtc_account_id` changes.

---

### Proof of Concept

```
1. Bridge is live with old_token; nbtc_account_id = old_token.
2. MigrationOperator calls migrate_to_new_token(new_token, [user, ...]).
   → Receipt A: ft_total_supply() and ft_balance_of(user) queried.
     At this moment: user.balance = X, bridge.balance = 0.
3. [Next block] User calls old_token.ft_transfer_call(bridge, X, withdraw_msg).
   → Bridge receives X old tokens; BTCPendingInfo created (PendingSign).
4. Receipt B (migrate_to_new_token_mint): sum = X = total_supply ✓.
   new_token.mint(user, X) executed; bridge receives 0 new tokens.
5. Receipt C (migrate_to_new_token_resolve): nbtc_account_id = new_token.
6. MPC signing completes; BTCPendingInfo → PendingVerify.
7. Relayer calls verify_withdraw_v2(tx_id, proof).
   → internal_verify_withdraw_callback: BTCPendingInfo → PendingBurn.
   → verify_withdraw_burn_promise: ext_nbtc::ext(new_token).burn(user, X, ...).
   → new_token.burn: internal_withdraw(bridge_id, X) → bridge has 0 new tokens → PANIC.
8. verify_withdraw_burn_callback: is_promise_success() = false.
   → BTCPendingInfo.to_pending_verify_stage() → back to PendingVerify.
9. Steps 7–8 repeat indefinitely. Withdrawal is permanently stuck.
   Bridge holds X old tokens; user holds X new tokens; no on-chain recovery.
```

    pub fn verify_withdraw_burn_promise(&self, tx_id: String) -> Promise {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id);
        let config = self.internal_config();
        let (protocol_fee, relayer_fee) = config
            .withdraw_bridge_fee
            .get_protocol_and_relayer_fee(btc_pending_info.withdraw_fee);
        ext_nbtc::ext(config.nbtc_account_id.clone())
            .with_static_gas(GAS_FOR_BURN_CALL)
            .burn(
                btc_pending_info.account_id.clone(),
                btc_pending_info.burn_amount.into(),
                env::signer_account_id(),
                relayer_fee.into(),

                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_WITHDRAW_BURN_CALL_BACK)
                    .verify_withdraw_burn_callback(tx_id, protocol_fee.into(), relayer_fee.into()),

    }
