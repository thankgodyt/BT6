### Title
User-Controlled `gas_fee` in Refund Requests Bypasses Minimum Fee Enforcement, Causing Stuck Bridge State - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
The `request_refund` flow accepts a caller-supplied `gas_fee: Option<u128>` that is stored verbatim in the `RefundRequest`. The only validation is that the fee is strictly less than the deposit amount. There is no check against `min_btc_gas_fee`. An unprivileged user can pass `gas_fee = Some(0)` (or any sub-minimum value), causing the bridge to construct and MPC-sign a Bitcoin refund transaction whose miner fee is zero (or below relay threshold). That transaction cannot propagate on the Bitcoin network, permanently locking the deposit UTXO in a state where neither a deposit nor a fresh refund is possible.

---

### Finding Description

In `request_refund_callback` the resolved fee is validated only against the deposit amount: [1](#0-0) 

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

There is no lower-bound check against `config.min_btc_gas_fee`. A caller who passes `gas_fee = Some(0)` satisfies `0 < amount` and the request is stored with `gas_fee = 0`. [2](#0-1) 

Later, `refund_execution_inputs` computes the amount returned to the user as: [3](#0-2) 

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)   // gas_fee == 0
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

With `gas_fee = 0`, `refund_amount = deposit_amount`. The resulting PSBT has a single input (the deposit UTXO) and a single output paying the full deposit value to the user, leaving zero satoshis as the implicit miner fee. The MPC network signs this PSBT normally (it has no visibility into fee adequacy), and the signed transaction is broadcast but rejected by every Bitcoin relay node because it violates the minimum relay fee rule.

`finalize_refund_with_psbt` marks the UTXO as verified before the broadcast attempt: [4](#0-3) 

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
```

And sets `refund_request.executed = true`: [5](#0-4) 

`load_refund_request_for_execute` permits re-execution only when `executed == true`, but re-execution re-reads the same stored `gas_fee = 0` from the `RefundRequest`, so every subsequent call produces the same unbroadcastable transaction. The deposit UTXO is permanently locked: `verify_deposit` is blocked by `verified_deposit_utxo`, and `verify_refund_finalize` can never succeed because the transaction never confirms.

The `min_btc_gas_fee` field exists in `Config` and is enforced elsewhere, but is never consulted during refund request creation: [6](#0-5) 

---

### Impact Explanation

**Medium — attacker-triggered permanent locking of the deposit UTXO.**

The deposit UTXO is irrecoverably stuck: it cannot be claimed as a deposit (blocked by `verified_deposit_utxo`) and the refund transaction can never confirm (zero fee). The bridge operator's only recourse is to call `reject_refund` before `execute_refund` is called, but once `execute_refund` runs and sets `executed = true`, the request cannot be rejected (the `internal_reject_refund` path removes the request, but the `verified_deposit_utxo` entry and the stale `BTCPendingInfo` remain). The user's deposited BTC is permanently lost.

---

### Likelihood Explanation

**Medium.** Any user who deposits BTC and then calls `request_refund` with `gas_fee = Some(0)` triggers this path. No privileged access is required. The only prerequisite is a valid on-chain deposit and a passing light-client proof, both of which are normal user actions. The timelock (`refund_timelock_sec` / `unsafe_refund_timelock_sec`) delays but does not prevent exploitation.

---

### Recommendation

Add a minimum-fee guard in `request_refund_callback` immediately after resolving the fee:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee >= self.internal_config().min_btc_gas_fee,
    "Gas fee must be at least min_btc_gas_fee"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

This mirrors the existing `min_btc_gas_fee` enforcement used in the withdrawal path and closes the bypass.

---

### Proof of Concept

1. Alice deposits X satoshis to her bridge deposit address and obtains a valid Merkle inclusion proof.
2. Alice calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee = Some(0))`.
3. `request_refund_callback` resolves `resolved_gas_fee = 0`; the check `0 < X` passes; the `RefundRequest` is stored with `gas_fee = 0`.
4. After `unsafe_refund_timelock_sec` elapses, Alice calls `execute_refund(utxo_storage_key, ...)`.
5. `refund_execution_inputs` computes `refund_amount = X - 0 = X`.
6. `build_refund_output` creates a single output paying X satoshis to Alice's address.
7. `finalize_refund_with_psbt` inserts the UTXO key into `verified_deposit_utxo` and sets `executed = true`.
8. The MPC signs the PSBT (input = X sat, output = X sat, implicit fee = 0 sat).
9. The signed transaction is broadcast; every relay node rejects it (fee below `minRelayTxFee`).
10. Alice's X satoshis are permanently locked: `verify_deposit` is blocked, `verify_refund_finalize` can never succeed, and re-running `execute_refund` reproduces the same zero-fee transaction.
