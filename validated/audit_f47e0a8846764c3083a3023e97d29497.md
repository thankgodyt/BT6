### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Submitted Certificates, Enabling Unprivileged Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` always returns `Right` without performing any cryptographic or semantic checks. When Peras is enabled, an unprivileged peer can inject arbitrary Peras certificates via the object-diffusion mini-protocol. Each accepted certificate is stored in the `PerasCertDB` and immediately triggers `chainSelectionForBlock`, causing the node to re-evaluate chain selection with the attacker-controlled weight boost applied to any block in the VolatileDB.

---

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the gate that decides whether a received certificate is cryptographically and semantically valid before it enters the node's state.

The catch-all default instance, explicitly marked as a temporary stub, bypasses every check:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is the validator wired into both inbound certificate paths. In `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`, `processCerts` is called with `(validatePerasCert mkPerasParams)`: [2](#0-1) 

`processCerts` only skips a certificate if its round number is already in the DB; otherwise it calls the validator and, on `Right`, timestamps and stores it: [3](#0-2) 

Once stored, `chainSelSync` is invoked for the boosted block, unconditionally triggering `chainSelectionForBlock`: [4](#0-3) 

Chain selection then reads the `PerasWeightSnapshot` — which now reflects the attacker-injected boost — and computes `wsvTotalWeight` as `BlockNo + weightBoost`: [5](#0-4) 

**Structural analog to the external report.** In the reported DeFi bug, `issuedShares` was a single map used for both router-deposited liquidity and user-deposited funds; because both kinds of deposit landed in the same structure, users could call the router-only `removeLiquidity`. Here, `PerasCertDB` is the single store used for both legitimately block-embedded certificates (privileged path) and peer-diffused certificates (unprivileged path). Because `validatePerasCert` never rejects anything, the unprivileged path is indistinguishable from the privileged one, and the attacker's certificate triggers the same chain-selection side-effect as a genuine committee certificate would.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash present in the target node's VolatileDB as the boosted block. After injection:

1. The `PerasWeightSnapshot` is updated to reflect the artificial boost.
2. `chainSelectionForBlock` re-evaluates all candidate chains against the current selection using `WeightedSelectView`, which sums `BlockNo` and `weightBoost`.
3. If the boosted block is on a fork, the node may switch to that fork even though it would not have been preferred under honest Peras rules.

This satisfies the **High** impact tier: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Peras is disabled by default in the current codebase (CHANGELOG: *"Note that if Peras is disabled (which is the default), there is no observable difference"*). However:

- The object-diffusion mini-protocol and `PerasCertDB` plumbing are already wired in and compile-ready.
- The vulnerability is fully reachable on any private testnet or staging deployment where Peras is enabled via `rnFeatureFlags`.
- No keys, stake, or operator access are required — any TCP-connected peer can send a `PerasCert` object.

Likelihood is **Medium** (conditional on Peras activation, but trivially exploitable once active).

---

### Recommendation

Replace the stub with a real implementation before enabling Peras in any environment. At minimum, `validatePerasCert` must:

1. Verify the aggregate BLS signature against the claimed voter set.
2. Confirm each voter's seat index is within the committee bounds for the given epoch nonce and round.
3. Confirm the aggregate weight meets the quorum threshold.
4. Confirm the boosted block hash is well-formed.

Until the real implementation is in place, the object-diffusion inbound handler should refuse all certificates (return a hard error rather than delegating to the stub), so that enabling Peras does not silently open this path.

---

### Proof of Concept

**Setup**: private testnet with Peras enabled via `rnFeatureFlags`.

1. Attacker connects to the victim node as a normal peer via the node-to-node mini-protocol stack.
2. Attacker observes a block `B_fork` on a minority fork present in the victim's VolatileDB (learnable via ChainSync).
3. Attacker constructs a `PerasCert` with `pcCertRound = <any unseen round>` and `pcCertBoostedBlock = point(B_fork)`. No valid signature is required — the stub ignores all fields.
4. Attacker sends the certificate via the Peras object-diffusion sub-protocol.
5. `processCerts` calls `validatePerasCert`, receives `Right`, timestamps the cert, and calls `ChainDB.addPerasCertAsync`.
6. `chainSelSync` fires `chainSelectionForBlock` for `B_fork`.
7. `constructPreferableCandidates` now sees `B_fork`'s chain with `wsvTotalWeight = blockNo(B_fork) + perasWeight(params)`, which may exceed the honest chain's weight.
8. The victim node switches to the attacker-boosted fork. [6](#0-5) [7](#0-6) [8](#0-7)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
