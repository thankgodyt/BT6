### Title
Unpermissioned `request_refund` Allows Any Caller to Hijack Refund Destination for Deposits Without a Pre-Authorized Refund Address — (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`request_refund` in the satoshi-bridge contract carries no per-function `#[trusted_relayer]` guard. Any NEAR account can call it. When a user's `deposit_msg.refund_address` is `None`, the caller freely supplies the BTC destination address. An attacker who observes the on-chain deposit can race the user, register a refund request pointing to the attacker's own BTC address, and — if the DAO does not reject it within `unsafe_refund_timelock_sec` — execute the refund and steal the deposited BTC.

---

### Finding Description

**Access-control gap**

The second `impl Contract` block in `api/bridge.rs` carries a block-level `#[trusted_relayer]` attribute:

```
#[trusted_relayer]   // line 480 — block-level, configuration only
#[near]
impl Contract {
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(...)   // line 510 — NO per-function #[trusted_relayer]
``` [1](#0-0) 

Comparing with the first impl block, every function that is actually restricted carries **both** the block-level and a per-function `#[trusted_relayer]`:

```
#[trusted_relayer]   // line 5 — block-level
#[near]
impl Contract {
    #[trusted_relayer]   // line 26 — per-function enforcement
    #[pause(...)]
    pub fn verify_deposit(...)
``` [2](#0-1) 

The doc-comment for `execute_refund` (same block, line 582) explicitly states *"anyone can call `execute_refund`"*, confirming that the block-level attribute is configuration, not enforcement. `request_refund` therefore inherits the same open access. [3](#0-2) 

**Caller-supplied refund address**

The function signature accepts a free `refund_address` parameter. The doc-comment states: *"If `deposit_msg.refund_address` is `None`, this value is used directly."* [4](#0-3) 

There is no check that the caller is the `deposit_msg.recipient_id` or any other party with a legitimate claim to the UTXO.

**`deposit_msg` is fully observable**

`get_user_deposit_address` emits a `LogDepositAddress` event that includes the complete `deposit_msg`. The BTC transaction itself is public on-chain. An attacker has all inputs needed to construct a valid `request_refund` call. [5](#0-4) 

**Exploit path**

1. User deposits BTC using a `deposit_msg` with `refund_address: None` (no pre-authorized BTC return address).
2. The relayer does not call `verify_deposit` (relayer down, user changed mind, etc.).
3. Attacker reads the `LogDepositAddress` event, obtains `deposit_msg`, fetches the BTC transaction bytes and Merkle proof from Bitcoin.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` before the user.
5. Bridge verifies the Merkle proof via the Light Client and stores a `RefundRequest` keyed by `utxo_storage_key = {tx_id}@{vout}` with `refund_address = attacker_btc_addr`.
6. User's subsequent `request_refund` call for the same UTXO fails — the key is already occupied.
7. Because `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` (the longer timelock intended to give the DAO time to reject suspicious requests).
8. If the DAO does not reject within that window, the attacker calls `execute_refund`, triggering MPC signing and broadcasting a BTC transaction to the attacker's address. [6](#0-5) 

---

### Impact Explanation

**If the DAO rejects in time:** The attacker's refund request is removed. The user must re-submit their own `request_refund` and wait through the full timelock again. This is attacker-triggered temporary locking of bridged funds — **Medium**.

**If the DAO fails to act (monitoring gap, key unavailability, or deliberate griefing at scale):** The attacker executes the refund and receives the user's BTC. The user's nBTC was never minted (deposit was never finalized), so the user loses their BTC with no compensation — **Critical: significant theft of user funds**.

---

### Likelihood Explanation

- `deposit_msg` is emitted in a public on-chain event; no off-chain secret is required.
- BTC transactions and Merkle proofs are publicly available.
- The attacker only needs to pay the NEAR storage anti-spam deposit (`required_balance_for_request_refund()`), a small amount.
- Deposits with `refund_address: None` are the common case (the standard deposit flow does not require a pre-authorized refund address).
- The attack is viable any time the relayer is slow or the user has not yet called `request_refund` themselves.

---

### Recommendation

Add `#[trusted_relayer]` to the `request_refund` function itself (matching the pattern used by `verify_deposit`, `verify_withdraw_v2`, etc.), or add an explicit caller check inside the function body that requires `env::predecessor_account_id() == deposit_msg.recipient_id` (or a trusted relayer role). This binds the refund request to the legitimate depositor, eliminating the open-caller attack surface.

---

### Proof of Concept

```
// Attacker (any NEAR account) observes LogDepositAddress event:
//   deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }
//   deposit_address = "bc1q..."

// Attacker fetches BTC tx bytes + Merkle proof from Bitcoin RPC.

// Attacker calls (no role required):
bridge.request_refund(
    deposit_msg   = { recipient_id: "alice.near", refund_address: None, ... },
    refund_address = "bc1q_ATTACKER_ADDRESS",
    tx_bytes      = <alice's BTC tx>,
    vout          = 0,
    proof         = <valid Merkle proof>,
    gas_fee       = None,
    attached_deposit = required_balance_for_request_refund()
)

// Bridge stores RefundRequest { refund_address: "bc1q_ATTACKER_ADDRESS", ... }

// Alice's request_refund now fails: "Refund request already exists for this UTXO"

// After unsafe_refund_timelock_sec (if DAO does not reject):
attacker.execute_refund(utxo_storage_key = "{tx_id}@0")
// → MPC signs BTC tx sending funds to bc1q_ATTACKER_ADDRESS
// → Alice's BTC is stolen
```

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
