Peras Certificate Validation Always Succeeds, Enabling Unauthorized Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) without performing any cryptographic or structural validation. This is the active production instance used by the Peras certificate inbound processing pipeline. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and boosted block point; the certificate will pass validation, be stored in the `PerasCertDB`, and trigger chain selection that may cause the node to prefer a non-canonical chain.

---

Once stored, the certificate is processed by `chainSelSync`, which triggers chain selection for the boosted block if it is present in the VolatileDB:

Chain selection uses `preferAnchoredCandidate`, which incorporates the `PerasWeightSnapshot` (built from accepted certificates) to compare chains. A forged certificate boosting a block on a non-canonical fork adds weight to that fork, potentially causing the node to switch to it:

```haskell
preferAnchoredCandidate cfg weights ours cand

      case AF.intersect ours cand of
        ...
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain selection manipulation.**

An attacker who can send messages over the Peras object-diffusion mini-protocol can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. Because `validatePerasCert` always returns `Right`, the certificate is accepted without any cryptographic, committee-membership, quorum, or round-number check. The accepted certificate is stored in the `PerasCertDB` and its weight boost is applied during chain selection. If the attacker has previously delivered a valid block on a non-canonical fork, the forged certificate can give that fork enough weight to be preferred over the honest canonical chain, causing the victim node to switch to the adversarial fork. This directly undermines the Peras finality guarantee and constitutes unauthorized certificate acceptance.

---

### Likelihood Explanation

**Medium.** The Peras object-diffusion mini-protocol is implemented and wired into the production `ChainDB` interface. The attack requires only that the attacker be a connected peer and have previously delivered a block on a competing fork — both are normal network conditions. No key compromise, stake majority, or privileged access is required. The only mitigating factor is that Peras certificate diffusion may not yet be active on mainnet, but the code path is present and reachable in any deployment that enables the Peras object-diffusion protocol.

---

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that verifies:
1. The certificate's BLS aggregate signature over the election identifier and boosted block hash.
2. That the signing committee members are eligible for the claimed round (VRF/persistent-seat check).
3. That the number of signers meets the quorum threshold.
4. That the boosted block's slot falls within the valid range for the claimed round.

Until a real implementation is available, the inbound certificate processing pipeline should reject all certificates rather than accept them unconditionally, to avoid the security regression. The same audit should be applied to `validatePerasVote`, which also omits cryptographic checks.

---

### Proof of Concept

1. Connect to a victim node as a peer via the Peras certificate object-diffusion mini-protocol.
2. Deliver a valid block `B` on a non-canonical fork (e.g., a fork that diverges one block before the current tip).
3. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B) }` with any round number `r` and any content — no valid signature or committee proof is required.
4. Send the crafted certificate to the victim node.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. The certificate is stored in `PerasCertDB` and `chainSelSync` triggers `chainSelectionForBlock` for `B`.
7. `preferAnchoredCandidate` now computes `weightedSelectView` for the fork containing `B`, which includes the forged weight boost. If the boost is large enough (controlled by `perasWeight params`), the victim node switches to the adversarial fork.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
