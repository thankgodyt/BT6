### Title
Peras Certificate Validation Guard Missing: `validatePerasCert` Unconditionally Returns `Right`, Enabling Peer-Injected Weight Boost to Corrupt Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as a function that **always returns `Right`** — it accepts every inbound certificate unconditionally, performing zero cryptographic or structural checks. When Peras is enabled, any unprivileged peer can inject arbitrary certificates through the object-diffusion mini-protocol. Each accepted certificate applies a configurable weight boost (`perasWeight = 15`) to an attacker-chosen block, directly influencing chain selection and potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory guard that must approve a certificate before it is stored and used for chain selection. The sole production instance — a catch-all for every `StandardHash blk` — stubs this guard out entirely:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** instance; the comment at line 318 confirms it is a placeholder for all blocks: [2](#0-1) 

The production inbound path for peer-supplied certificates is `makePerasCertPoolWriterFromChainDB`, which wires `validatePerasCert mkPerasParams` directly as the validation callback:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [3](#0-2) 

`processCerts` partitions results into valid/invalid; because `validatePerasCert` never returns `Left`, every certificate is classified as valid and forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`chainSelSync` then calls `chainSelectionForBlock` for the boosted block, applying the weight boost to chain selection: [5](#0-4) 

Chain selection uses `WeightedSelectView`, which adds `wsvWeightBoost` to `wsvBlockNo` to compute total weight. A single injected certificate contributes `perasWeight = PerasWeight 15` (from `mkPerasParams`): [6](#0-5) [7](#0-6) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can craft a `PerasCert` naming any block hash and any round number. Because `validatePerasCert` never rejects it, the certificate is stored in `PerasCertDB` and its weight boost is applied to chain selection. By injecting multiple certificates targeting the same block, an attacker can accumulate arbitrary weight on a non-canonical fork, causing the victim node to switch away from the honest chain. This is a **chain selection bug** that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The CHANGELOG notes that Peras is disabled by default: *"Note that if Peras is disabled (which is the default), there is no observable difference."* However, the feature is enabled via `rnFeatureFlags` in `RunNodeArgs`, and the production code path (`makePerasCertPoolWriterFromChainDB`) is unconditionally wired with the stub validator. Any operator who enables Peras exposes their node to this attack from any connected peer with no additional preconditions. The attack requires only the ability to send a well-formed `PerasCert` message over the object-diffusion mini-protocol.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that checks:
1. The certificate's aggregate signature against the claimed committee members' keys.
2. That the claimed voters hold sufficient stake to meet `perasQuorumStakeThreshold`.
3. That the boosted block point is structurally valid (non-genesis, within the volatile window).
4. Round-number consistency with the current epoch/slot.

Until real validation is implemented, the Peras feature flag must not be enabled in any production deployment, and the stub should be guarded with an explicit runtime assertion or compile-time note that makes the missing check impossible to overlook during integration.

---

### Proof of Concept

1. Connect to a Peras-enabled node as an unprivileged peer via the object-diffusion mini-protocol.
2. Send a batch containing a single `PerasCert` with:
   - `pcCertRound` = any valid `PerasRoundNo`
   - `pcCertBoostedBlock` = the `Point` of a block on a competing fork present in the node's VolatileDB
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally.
4. The certificate is stored via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` retrieves the boosted block's header from VolatileDB and calls `chainSelectionForBlock`.
6. `constructPreferableCandidates` now computes a `WeightedSelectView` for the fork with `wsvWeightBoost = 15`, potentially making it heavier than the honest chain.
7. The node switches to the attacker-chosen fork. [8](#0-7) [9](#0-8) [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs

      mapM_

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
