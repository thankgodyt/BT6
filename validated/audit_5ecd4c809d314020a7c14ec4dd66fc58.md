### Title
User Can Block Operator `cancel_withdraw` by Filling Pending-Sign Slot via Second Withdraw — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
An unprivileged user can permanently prevent the operator from canceling their stuck withdraw by submitting a second withdraw (via `ft_on_transfer`) to fill their `btc_pending_sign_ids` slot before the operator calls `cancel_withdraw`. The capacity guard in `cancel_withdraw` then panics, leaving the original withdraw permanently stuck in `PendingVerify`.

### Finding Description
The public `cancel_withdraw` function (operator-only, but blocked by user-controlled state) calls `require_pending_sign_capacity(&user_account_id)` at line 291 of `api/bridge.rs` before creating the cancel-RBF entry. This guard checks:

```rust
pending_sign_count() < get_max_pending_sign_txs(account_id)
// default limit = 1
```

The attack sequence:
1. User submits withdraw #1 via `ft_on_transfer` → `btc_pending_sign_ids = {tx1}`.
2. Relayer signs tx1 → `btc_pending_sign_ids = {}`, tx1 moves to `PendingVerify`.
3. tx1 becomes stuck (low fee) for `> max_btc_tx_pending_sec`.
4. User submits withdraw #2 via `ft_on_transfer` → `btc_pending_sign_ids = {tx2}` (allowed, since count `0 < 1`).
5. Operator calls `cancel_withdraw(tx1)` → `require_pending_sign_capacity` evaluates `1 < 1` → **panics with "Too many pending sign transactions"**.

The cancel-RBF is never created. The original withdraw is permanently stuck.

### Impact Explanation
The stuck withdraw cannot be resolved via the normal `cancel_withdraw` path. The user's nBTC is locked in the bridge indefinitely. Operator intervention beyond the standard flow (e.g., manually raising the user's `pending_tx_limits` via a DAO call, then retrying) is required. This matches the **Medium** impact category: stuck bridge state requiring operator intervention, and attacker-triggered temporary locking of bridged funds.

### Likelihood Explanation
The attack requires only that the user hold enough nBTC for a second withdraw and time the second `ft_on_transfer` call after their first withdraw moves to `PendingVerify` but before the operator calls `cancel_withdraw`. Both conditions are easily met by a motivated user. The default limit of `1` makes every standard user account vulnerable.

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` (and `cancel_active_utxo_management`). The cancel-RBF path is operator-initiated and must be unconditionally available after the timeout. Alternatively, skip the capacity check specifically when the caller is DAO/Operator and the operation is a cancel, or exempt cancel-RBF entries from counting against the user's pending-sign limit.
