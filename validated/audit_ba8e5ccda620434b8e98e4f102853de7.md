### Title
Missing Caller Authorization in `sign_btc_transaction` Enables Signature-Slot Poisoning via Attacker-Controlled `key_version` — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`, `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` is a public, payable function that accepts any `btc_pending_sign_id` from any caller. It performs no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. Combined with the fully attacker-controlled `key_version` parameter, an adversary can submit a signing request for a victim's pending transaction using a wrong key version. If the chain-signatures MPC service accepts that version, the resulting (invalid) signature is stored unconditionally, and the `is_none()` guard then permanently blocks the legitimate signer from that slot, freezing the victim's funds.

---

### Finding Description

**Entry point — no ownership guard:**

`sign_btc_transaction` fetches the pending info and immediately proceeds to signing without ever comparing the caller to the stored `account_id`:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();   // stage check only
    // ← no require!(env::predecessor_account_id() == btc_pending_info.account_id)
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version).into()
}
``` [1](#0-0) 

`internal_sign_btc_transaction` likewise performs no ownership check and forwards the attacker-supplied `key_version` verbatim to the MPC service: [2](#0-1) 

**Callback stores the result without signature verification:**

`sign_btc_transaction_callback` re-checks `is_none()` and then unconditionally stores whatever the MPC service returned. There is no cryptographic verification that the returned signature was produced by the key that corresponds to the UTXO's locking script:

```rust
require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed");
btc_pending_info.signatures[sign_index] = Some(signature.clone());
``` [3](#0-2) 

**The `is_none()` guard becomes the weapon:**

Once a signature (even an invalid one from the wrong key version) is stored, the slot is permanently locked. The legitimate relayer's subsequent call for the same `sign_index` panics with "Already signed": [4](#0-3) 

**Pending info is global, not per-account:**

`internal_unwrap_btc_pending_info` looks up by ID in a contract-wide map with no ownership enforcement: [5](#0-4) 

The `account_id` field inside `BTCPendingInfo` is only used for bookkeeping (event emission, account list cleanup) — never as an access gate in the signing path: [6](#0-5)

### Impact Explanation

If the chain-signatures MPC service accepts the attacker-supplied `key_version` (the service is designed for key rotation and can accept versions beyond 0), the callback stores a signature produced by the wrong key. The PSBT is then serialized with that invalid signature. When `is_all_signed()` returns true, the transaction is finalized and moved to `PendingVerify` stage with `tx_bytes_with_sign` set to an unbroadcastable transaction. The victim's UTXOs were already removed from the active set at pending-info creation time. The nBTC burn is tied to the verify/finalize flow. The result is **permanent freezing of the victim's bridged BTC** — the UTXO can never be spent and the nBTC accounting is corrupted.

Even if the MPC service rejects the wrong key version (promise fails → callback returns `false`, slot stays `None`), the missing ownership check is still a structural flaw: any account can race the legitimate relayer and, with a valid `key_version = 0`, sign on behalf of any user — a confused-deputy path that violates the invariant that only the account owner (or an authorized relayer acting on their behalf) should drive their own signing pipeline.

---

### Likelihood Explanation

- `btc_pending_sign_id` values are public contract state (emitted in `GenerateBtcPendingInfo` events and queryable via view methods).
- The function is `#[payable]` but the attacker pays the deposit themselves; no victim funds are required to mount the attack.
- NEAR's chain-signatures MPC service is explicitly designed to support `key_version` for key rotation. Any deployment that has rotated keys (or where the attacker guesses a future valid version) makes the poisoning attack immediately executable.
- The race window is the entire `PendingSign` lifetime of the transaction, which can span many blocks.

---

### Recommendation

1. **Add a caller ownership check** at the top of `sign_btc_transaction`:
   ```rust
   require!(
       env::predecessor_account_id() == btc_pending_info.account_id,
       "Not authorized"
   );
   ```
   Or, if relayers are intended to call this function, maintain an explicit allowlist of authorized relayers and check against it.

2. **Validate `key_version`** against a contract-configured expected value (e.g., stored in `Config`) before forwarding to the MPC service, so an attacker cannot supply an arbitrary version.

3. **Verify the returned signature** in `sign_btc_transaction_callback` against the expected public key before storing it, so a signature from the wrong key is rejected rather than persisted.

### Proof of Concept

```
// Victim alice has pending tx "alice_tx_abc" with 2 inputs, both unsigned.
// Attacker bob observes the pending ID from on-chain events.

// Step 1: Bob calls sign_btc_transaction with wrong key_version for input 0
bob.call(bridge, "sign_btc_transaction", {
    btc_pending_sign_id: "alice_tx_abc",
    sign_index: 0,
    key_version: 1          // wrong version; MPC signs with key_v1
}).attach_deposit(mpc_fee);

// Step 2: MPC returns sig_v1 (signed by key version 1, not the UTXO's key)
// sign_btc_transaction_callback stores sig_v1 at signatures[0]

// Step 3: Legitimate relayer tries to sign input 0
relayer.call(bridge, "sign_btc_transaction", {
    btc_pending_sign_id: "alice_tx_abc",
    sign_index: 0,
    key_version: 0
});
// → panics: "Already signed"

// Step 4: Bob repeats for input 1 → both slots poisoned
// → is_all_signed() = true, tx finalized with two invalid signatures
// → tx_bytes_with_sign is set but the Bitcoin transaction is invalid
// → Alice's UTXO is permanently unspendable; funds frozen
```

        btc_pending_sign_id: String,

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
