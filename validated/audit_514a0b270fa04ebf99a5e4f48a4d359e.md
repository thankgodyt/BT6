### Title
Peras Quorum Check Compares Unnormalized Absolute `PerasVoteStake` Against a Relative Threshold, Enabling Spurious Certificate Acceptance - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares the accumulated `PerasVoteStake` value against the `perasQuorumStakeThreshold` (a relative `Rational`, defaulting to `3/4`). The code itself documents that `PerasVoteStake` may carry **absolute** ledger stake (in lovelace) rather than a normalized fraction, and that normalization is not performed before the comparison. If absolute stake values are supplied — which the code acknowledges is the unresolved current state — any single voter with even 1 lovelace of stake produces a `PerasVoteStake` of `1`, which trivially satisfies `1 ≥ 0.75 + 0.02`. This mirrors the external report's root cause: a global/aggregate value (gauge weight) used where an individual proportional value (user stake) is required, causing the threshold to be meaningless.

---

### Finding Description

**Root cause — `stakeAboveThreshold`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The `PerasVoteStake` type comment explicitly states the conversion from absolute ledger stake to relative vote stake is **unresolved**:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
``` [2](#0-1) 

The quorum threshold is a relative `Rational` hardcoded to `3/4`:

```haskell
perasQuorumStakeThreshold =
    PerasQuorumStakeThreshold (3 / 4)
, perasQuorumStakeThresholdSafetyMargin =
    PerasQuorumStakeThresholdSafetyMargin (2 / 100)
``` [3](#0-2) 

**Call chain — `votesReachQuorum`:**

```haskell
totalVoteStake =
  mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake =
  stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

`vpvVoteStake` is populated by `validatePerasVote` via a direct lookup from `PerasVoteStakeDistr` — no normalization step exists anywhere in this path:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [5](#0-4) 

**The miscalculation:** If `PerasVoteStakeDistr` is populated with absolute ledger stake (e.g., lovelace counts), a voter with even 1 lovelace contributes `PerasVoteStake = 1 % 1`. The check `1 ≥ 0.75 + 0.02` is immediately satisfied. The total accumulated stake across multiple votes would be an even larger integer, making the quorum check permanently trivially true. This is structurally identical to the external report's bug: a global gauge weight (here, absolute lovelace) is used where a proportional individual value (relative stake fraction) is required, causing the threshold to be meaningless and the "distribution" (here, quorum gate) to be bypassed entirely.

---

### Impact Explanation

**High — Chain selection bug enabling unauthorized certificate acceptance.**

A Peras certificate boosts a block's chain-selection weight by `perasWeight` (default: 15 slots worth of weight). If quorum is trivially reachable by any single voter regardless of their actual stake fraction, an unprivileged peer with any positive stake can:

1. Cast a single vote for any block of their choosing.
2. Have `votesReachQuorum` return `Just` immediately.
3. Cause `forgePerasCert` to produce a `ValidatedPerasCert` boosting that block.
4. Force honest nodes to prefer the adversarially boosted chain over the canonical chain.

This breaks the Peras protocol's core security guarantee: that only a block backed by ≥ 3/4 of total stake can receive a boost. The result is a chain-selection divergence exploitable by any peer with any stake.

---

### Likelihood Explanation

**Medium.** The vulnerability is latent: it activates the moment `PerasVoteStakeDistr` is populated from ledger absolute stake without normalization, which the code explicitly acknowledges has not been resolved. The Peras protocol is not yet deployed on mainnet, but the production source path (`ouroboros-consensus/src/ouroboros-consensus/`) is live and the degenerate `BlockSupportsPeras` instance (which performs no real certificate validation) is the only instance currently compiled for all block types. Any integration that wires ledger absolute stake directly into `PerasVoteStakeDistr` — the natural and undocumented-against approach — triggers the bug.

---

### Recommendation

1. **Enforce normalization at the boundary.** `stakeAboveThreshold` should accept a total-stake parameter and normalize internally, or `validatePerasVote` should normalize `PerasVoteStake` before storing it:

   ```haskell
   stakeAboveThreshold :: PerasParams -> TotalStake -> PerasVoteStake -> Bool
   stakeAboveThreshold params (TotalStake total) voteStake =
     (unPerasVoteStake voteStake / total) >= quorumThreshold + safetyMargin
   ```

2. **Resolve the open design question** documented in the `PerasVoteStake` comment. Until the conversion from absolute ledger stake to relative vote stake is formally specified and implemented, the quorum check is undefined behavior.

3. **Add a type-level or runtime invariant** asserting that all `PerasVoteStake` values stored in `PerasVoteStakeDistr` are in `[0, 1]` before any quorum comparison.

### Proof of Concept

Given `mkPerasParams` defaults (`quorumThreshold = 3/4`, `safetyMargin = 2/100`):

```haskell
-- Attacker has 1 lovelace of absolute stake
attackerStake :: PerasVoteStake
attackerStake = PerasVoteStake 1  -- absolute lovelace, not normalized

-- Single-vote quorum check
stakeAboveThreshold mkPerasParams attackerStake
-- = (1 :: Rational) >= (3/4 + 2/100)
-- = 1 >= 0.77
-- = True  ← quorum reached with 1 lovelace
``` [6](#0-5) 

`votesReachQuorum` would return `Just ValidatedPerasVotesWithQuorum`, triggering `forgePerasCert` and boosting the attacker's chosen block, regardless of actual network stake distribution. [7](#0-6)

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
