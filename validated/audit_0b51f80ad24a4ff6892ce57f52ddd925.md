Looking at the exact computation path in `check_withdraw_psbt`:

### Title
`check_withdraw_psbt` `min_received_amount` Underflow Causes Panic-Driven Withdrawal DoS — (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `check_withdraw_psbt`, line 243 performs an unchecked subtraction `max_received_amount - config.min_change_amount`. When a user submits a withdrawal with `amount` near `min_withdraw_amount` and a PSBT whose gas fee is near `max_btc_gas_fee`, `max_received_amount` can be smaller than `config.min_change_amount`, causing a `u128` underflow. The gas-fee range guard that would bound `gas_fee` is placed **after** the underflowing computation, so it cannot prevent the fault.

---

Inside `check_withdraw_psbt`, the two consecutive subtractions are:

```rust
// psbt.rs line 242-243
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
``` [1](#0-0) 

The gas-fee range check that bounds `gas_fee` to `[min_btc_gas_fee, max_btc_gas_fee]` appears **after** these lines: [2](#0-1) 

So the ordering is: compute → (potential underflow) → validate. The guard arrives too late.

The only pre-entry check on `amount` is:

```rust

require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
``` [3](#0-2) 

`config.assert_valid()` enforces several invariants but has **no** check that prevents:

```
min_withdraw_amount - withdraw_fee_min - max_btc_gas_fee < min_change_amount
``` [4](#0-3) 

The `gas_fee` in the PSBT is user-controlled (it is derived from `total_input_amount - total_output_amount` where the user supplies both inputs and outputs), bounded only by the range check that comes after the underflow. [5](#0-4) 

---

### Impact Explanation

**With overflow checks enabled** (typical for NEAR WASM release builds): the subtraction at line 243 panics. The panic propagates through `ft_on_transfer`, causing the NEP-141 `ft_resolve_transfer` callback to refund the user's nBTC. No fund loss, but the withdrawal is permanently blocked for any `(amount, gas_fee)` pair that satisfies the underflow condition.

**With overflow checks disabled** (wrapping semantics): `min_received_amount` wraps to `u128::MAX - (config.min_change_amount - max_received_amount - 1)`, an astronomically large value. The subsequent `require!` check `actual_received_amount >= min_received_amount` then always fails for any realistic `actual_received_amount`, producing a misleading error message and reverting the transaction. Tokens are still refunded.

In neither case does the attacker steal funds. The impact is a **publicly reachable panic-driven DoS** on the withdrawal path for configurations where the arithmetic invariant is not maintained.

---

### Likelihood Explanation

The condition is reachable whenever the deployed configuration satisfies:

```
min_withdraw_amount - withdraw_bridge_fee.fee_min - max_btc_gas_fee < min_change_amount
```

Any unprivileged user can trigger it by calling `ft_transfer_call` with `amount = min_withdraw_amount` and constructing a PSBT whose `total_input_amount - total_output_amount = max_btc_gas_fee`. No special role or leaked key is required. The likelihood depends entirely on whether the deployed configuration satisfies the above inequality, which `assert_valid()` does not prevent.

---

### Recommendation

Add an invariant check to `Config::assert_valid()` that enforces the arithmetic relationship:

```rust
require!(
    min_withdraw_amount
        > withdraw_bridge_fee.fee_min
            .saturating_add(max_btc_gas_fee)
            .saturating_add(min_change_amount),
    "min_withdraw_amount too small relative to max fees and min_change_amount"
);
```

Additionally, replace the bare subtractions at lines 242–243 with checked or saturating arithmetic and an explicit `require!` before proceeding:

```rust
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .unwrap_or_else(|| env::panic_str("amount insufficient to cover fees"));
let min_received_amount = max_received_amount
    .checked_sub(config.min_change_amount)
    .unwrap_or(0); // dust tolerance floor is 0 when change is not needed
```

### Proof of Concept

Assume a configuration with:
- `min_withdraw_amount = 10_000` sats
- `withdraw_bridge_fee.fee_min = 1_000` sats (so `withdraw_fee = 1_000`)
- `max_btc_gas_fee = 8_000` sats
- `min_change_amount = 2_000` sats

User calls `ft_transfer_call` with `amount = 10_000` and a PSBT where `total_input_amount - total_output_amount = 8_000`.

Execution reaches line 242–243:

```
max_received_amount = 10_000 - 1_000 - 8_000 = 1_000
min_received_amount = 1_000 - 2_000  ← underflow (u128 wraps or panics)
```

The gas-fee range check at line 252 (`gas_fee = 8_000 <= max_btc_gas_fee = 8_000`) would have passed, but it is never reached. The transaction reverts and the user's nBTC is refunded via `ft_resolve_transfer`. The withdrawal is impossible for this `(amount, gas_fee)` pair.
