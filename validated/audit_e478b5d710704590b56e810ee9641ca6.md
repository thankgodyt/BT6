### Title
Off-by-One Boundary in `get_confirmations` Causes Deposits at Tier Boundaries to Require Excess Confirmations — (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary

`Config::get_confirmations` uses a strict `>` comparison when matching a deposit amount to a confirmation tier. When the deposit amount exactly equals a tier boundary key, the condition evaluates to `false`, the tier is skipped, and the function returns the next (higher) tier's confirmation count instead of the intended one. This is the same class of off-by-one boundary error as the reported finding: a strict inequality causes the wrong branch to execute at the exact boundary value.

---

### Finding Description

In `Config::get_confirmations`, the sorted tier keys are iterated and the first key for which `*key > satoshi_amount` is true is selected:

```rust
for key in &keys {
    if *key > satoshi_amount {          // strict greater-than
        return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
    }
}
// fallthrough: use the last (highest) key's value
let max_key = keys.last().unwrap();
u64::from(*self.confirmations_strategy.get(&max_key.to_string()).unwrap())
``` [1](#0-0) 

The `confirmations_strategy` field is documented as "Satoshi upper limit for amount checks → confirmations", meaning each key is an inclusive upper bound for its tier. [2](#0-1) 

With a strict `>`, a deposit whose amount is **exactly equal** to a tier boundary key does not match that tier. It falls through to the next tier, which has a higher confirmation requirement. For example:

| Strategy | Amount | Expected confirmations | Actual confirmations |
|---|---|---|---|
| `{1_000_000: 3, 10_000_000: 6}` | 999_999 | 3 | 3 ✓ |
| `{1_000_000: 3, 10_000_000: 6}` | **1_000_000** | **3** | **6 ✗** |
| `{1_000_000: 3, 10_000_000: 6}` | 1_000_001 | 6 | 6 ✓ |

`get_confirmations` is called in both the deposit refund request path and the refund finalization path: [3](#0-2) [4](#0-3) 

It is also called in the main deposit verification path (via `Contract::get_confirmations`, which delegates to `Config::get_confirmations`): [5](#0-4) 

---

### Impact Explanation

When a user deposits or requests a refund for an amount that exactly equals a tier boundary, the bridge demands more confirmations than the configured tier specifies. The user's Merkle-proof submission — prepared with the correct (lower) confirmation count — will be rejected by the light client call. The user's funds remain unprocessed until they obtain additional Bitcoin block confirmations and resubmit. This is a publicly reachable stuck-state fault in the production deposit/refund path without direct theft.

**Impact class:** Low — publicly reachable invariant-violation / stuck-state in production bridge paths without direct theft.

---

### Likelihood Explanation

Tier boundaries are typically set at economically meaningful round numbers (e.g., 0.01 BTC = 1,000,000 satoshis, 0.1 BTC = 10,000,000 satoshis). Users frequently deposit round amounts. The condition is reachable by any unprivileged depositor without any special knowledge or coordination.

---

### Recommendation

Change the strict `>` to `>=` so that a deposit amount equal to a tier boundary is matched by that tier, not the next one:

```rust
// Before
if *key > satoshi_amount {

// After
if *key >= satoshi_amount {
``` [6](#0-5) 

---

### Proof of Concept

1. Deploy bridge with `confirmations_strategy = {"1000000": 3, "10000000": 6}`.
2. User sends a BTC deposit of exactly **1,000,000 satoshis** (0.01 BTC).
3. After 3 confirmations the user calls `request_refund` (or `verify_deposit`). The bridge internally calls `get_confirmations(1_000_000)`.
4. Loop: `1_000_000 > 1_000_000` → `false` → skip. `10_000_000 > 1_000_000` → `true` → return **6**.
5. The light-client call is issued requiring **6** confirmations; the submitted proof (3 confirmations) is rejected.
6. The user's deposit is stuck until 6 confirmations are reached and the proof is resubmitted.
