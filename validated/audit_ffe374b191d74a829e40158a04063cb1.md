### Title
Missing `change_address` Setter in `ConfigUpdate` Permanently Breaks Withdrawal PSBT Construction - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
The `Config` struct's `change_address` field is mandated to be `None` at contract initialization, yet the `ConfigUpdate` struct — the sole mechanism for post-deployment config mutation — omits `change_address` entirely. No alternative setter exists. As a result, `change_address` is permanently `None` after deployment, and any withdrawal that requires a change output will panic inside `get_change_script_pubkey()`, rendering the withdrawal path of the bridge permanently inoperable.

### Finding Description
The `Config` struct holds a `change_address: Option<String>` field used to route Bitcoin change outputs during PSBT construction for withdrawals. [1](#0-0) 

The `new()` initializer explicitly **requires** this field to be `None`: [2](#0-1) 

So the bridge is always deployed with `change_address = None`. The only post-deployment config mutation path is `update_config`, which applies a `ConfigUpdate` struct: [3](#0-2) 

However, `ConfigUpdate` lists 25 updatable fields and **does not include `change_address`**: [4](#0-3) 

The `apply()` method only sets fields present in `ConfigUpdate`; `change_address` is never touched: [5](#0-4) 

No other function in `management.rs` sets `change_address`. The full management API was reviewed and confirmed to contain no `set_change_address` or equivalent:



The analog pattern is exact: `chain_signatures_root_public_key` is also initialized as `None` but has a dedicated post-deployment setter (`sync_chain_signatures_root_public_key`). `change_address` has no equivalent. [6](#0-5) 

When any withdrawal PSBT is constructed and a change output is needed, the code calls: [7](#0-6) 

This unconditionally panics with `"ERR_CONFIG: change_address not configured"` because `change_address` is permanently `None`.

### Impact Explanation
Every withdrawal that produces a change output — which is the overwhelming majority of Bitcoin withdrawals, since UTXOs rarely match withdrawal amounts exactly — will panic inside `ft_on_transfer`. The NEP-141 `ft_resolve_transfer` callback will refund the nBTC to the user, so funds are not permanently destroyed, but the bridge's withdrawal path is permanently broken and stuck, requiring a contract upgrade (operator intervention) to recover. This matches: **Medium — stuck bridge state requiring operator intervention**.

### Likelihood Explanation
The bridge is deployed with `change_address = None` by design (enforced by `require!`). Since `ConfigUpdate` has no `change_address` field and serde silently ignores unknown JSON keys, even a DAO attempt to pass `{"change_address": "bc1q..."}` to `update_config` would be silently dropped. The broken state is permanent from block 0 of deployment. Likelihood is **High**.

### Recommendation
Add `change_address: Option<String>` to `ConfigUpdate` and handle it in `apply()`:

```rust
// In ConfigUpdate struct
pub change_address: Option<Option<String>>,

// In apply()
if let Some(v) = self.change_address {
    config.change_address = v;
}
```

Alternatively, add a dedicated `set_change_address(address: Option<String>)` management function gated on `Role::DAO`, mirroring the pattern used by `sync_chain_signatures_root_public_key`.

### Proof of Concept

1. Deploy `satoshi-bridge` with any valid `Config` where `change_address` is `None` (the only accepted value at init).
2. Attempt to set `change_address` post-deployment:
   ```json
   // Call update_config with:
   {"update": {"change_address": "bc1qexampleaddress..."}}
   ```
   This call succeeds but silently ignores `change_address` because the field is absent from `ConfigUpdate`. `config.change_address` remains `None`.
3. Any user calls `ft_transfer_call` on the `nbtc` contract to initiate a withdrawal.
4. The `nbtc` contract calls `ft_on_transfer` on the bridge.
5. The bridge begins PSBT construction; when a change output is required, it calls `get_change_script_pubkey()`.
6. `get_change_script_pubkey()` executes `.expect("ERR_CONFIG: change_address not configured")` on `None` → **panic**.
7. `ft_on_transfer` fails; `ft_resolve_transfer` refunds nBTC to the user.
8. The withdrawal is permanently impossible. No withdrawal can ever succeed until the contract is upgraded. [7](#0-6) [8](#0-7) [2](#0-1)
