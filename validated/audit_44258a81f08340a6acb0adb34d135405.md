### Title
Permissionless `request_refund` Allows Race-Condition Hijacking of Refund Address to Redirect User BTC — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
The `request_refund` flow is fully permissionless and accepts a caller-supplied `refund_address` whenever `deposit_msg.refund_address` is `None`. Because the first callback to succeed wins and blocks all subsequent requests for the same UTXO, an attacker who observes a pending `request_refund` NEAR transaction can race it with an identical call carrying their own BTC address, causing the victim's BTC to be sent to the attacker.

### Finding Description

`internal_request_refund` in `contracts/satoshi-bridge/src/refund.rs` (lines 137–184) is a public, permissionless function. When `deposit_msg.refund_address` is `None`, the only validation on the caller-supplied `refund_address` is that it is a syntactically valid BTC address — there is no binding to the original depositor's identity:

```rust
// refund.rs L154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
// If deposit_msg.refund_address is None → any refund_address is accepted
```

The callback (`request_refund_callback`, lines 497–581) stores the first request that passes and rejects all later ones for the same UTXO:

```rust
// refund.rs L544-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

Because `deposit_msg`, `tx_bytes`, `vout`, and the Merkle proof are all observable on-chain (Bitcoin) or in the NEAR transaction payload, an attacker can replay the exact same call with a substituted `refund_address`. Whichever callback resolves first owns the stored `RefundRequest`. The victim's subsequent callback is rejected with "Refund request already exists for this UTXO", and the victim cannot resubmit until the DAO explicitly rejects the attacker's request.

The `unsafe_refund_timelock_sec` delay is the only mitigation — it gives the DAO a window to call `internal_reject_refund`. If the DAO does not act within that window, `execute_refund` can be called by anyone and the BTC is sent to the attacker's address.

### Impact Explanation
If the DAO fails to reject the attacker's request within `unsafe_refund_timelock_sec`, the victim's BTC is permanently redirected to the attacker's Bitcoin address. This constitutes a **Critical** loss of user funds. Even if the DAO does act, the victim's funds are temporarily locked and the user must resubmit, constituting at minimum a **Medium** stuck-bridge-state requiring operator intervention.

### Likelihood Explanation
- `deposit_msg.refund_address: None` is the common case for users who did not pre-specify a refund address at deposit time.
- All inputs needed to race the call (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are publicly visible on Bitcoin and in the NEAR transaction.
- NEAR transaction ordering within a chunk is deterministic but observable before finality; a well-positioned attacker can submit a competing transaction in the same or next chunk.
- The DAO must actively monitor every refund request and reject suspicious ones within `unsafe_refund_timelock_sec` — a purely operational control with no code-level enforcement.

### Recommendation
1. **Bind refund address to depositor identity**: Require the caller of `request_refund` to be the `deposit_msg.recipient_id`, or require `deposit_msg.refund_address` to be non-`None` (set at deposit time, before the BTC transaction is broadcast).
2. **Commit-reveal**: Accept a hash commitment of the `refund_address` in the first call and reveal it in a second permissioned call, preventing substitution.
3. **Idempotent caller binding**: Store the `predecessor_account_id` alongside the refund request and only allow that account to execute it, so a frontrunner's request is useless to them.

### Proof of Concept

1. User deposits BTC with `deposit_msg = { recipient_id: "user.near", refund_address: None }`. The deposit fails (e.g., `user.near` is not registered).
2. User constructs and submits:
   ```
   request_refund(deposit_msg, "user_btc_addr", tx_bytes, vout, proof, None)
   ```
3. Attacker observes this NEAR transaction (before or immediately after it lands) and submits:
   ```
   request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)
   ```
   with the same `deposit_msg`, `tx_bytes`, `vout`, and `proof` but `refund_address = "attacker_btc_addr"`.
4. Both calls invoke the Light Client cross-contract call. Whichever callback resolves first stores its `RefundRequest`. If the attacker's lands first, `refund_requests[utxo_storage_key].refund_address = "attacker_btc_addr"` is persisted.
5. The user's callback hits line 544–547 and panics: `"Refund request already exists for this UTXO"`. The user's attached storage deposit is returned but the request slot is taken.
6. If the DAO does not call `internal_reject_refund` within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund`, which calls `finalize_refund_with_psbt` → `build_refund_output("attacker_btc_addr", ...)` → signs and broadcasts a BTC transaction paying the victim's deposit to the attacker.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
