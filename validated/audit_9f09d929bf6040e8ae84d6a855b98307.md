Audit Report

## Title
Cross-Chain Replay of `deployToken`/`deploy_token` Signatures Due to Missing Chain ID in Message Hash — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary
The `deployToken`/`deploy_token` Borsh-encoded payload omits any chain identifier on EVM, Starknet, and Solana, while the analogous `finTransfer`/`fin_transfer` payload explicitly encodes the destination chain ID. Because all bridge deployments verify against the same `nearBridgeDerivedAddress` (derived from the single NEAR MPC key), a valid `deployToken` signature produced by the NEAR MPC for one chain is cryptographically valid on every other supported chain. An unprivileged attacker who observes any `deployToken` transaction can replay the signature on every other chain to execute unauthorized token deployer actions without a new MPC authorization.

## Finding Description

**Root cause — missing chain binding in `deployToken`:**

On EVM, `deployToken` constructs the Borsh payload as: [1](#0-0) 

No `omniBridgeChainId` is included. By contrast, `finTransfer` encodes `omniBridgeChainId` twice: [2](#0-1) 

On Starknet, `MetadataPayloadImpl::to_borsh` encodes only the payload type, token, name, symbol, and decimals — no `chain_id`: [3](#0-2) 

While `TransferMessagePayloadImpl::to_borsh` takes and encodes `chain_id` twice: [4](#0-3) 

On Solana, `DeployTokenPayload::serialize_for_near` writes only the `IncomingMessageType::Metadata` discriminant followed by the raw fields — no `SOLANA_OMNI_BRIDGE_CHAIN_ID`: [5](#0-4) 

While `FinalizeTransferPayload::serialize_for_near` writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` twice: [6](#0-5) 

**Why existing checks fail:**

The `nearBridgeDerivedAddress` is a single Ethereum address derived from the NEAR MPC key, configured identically across all EVM deployments: [7](#0-6) [8](#0-7) 

Because the Borsh encoding of `deployToken` is chain-agnostic, `keccak256(borshEncoded)` produces the identical hash on every EVM chain for the same token metadata. `ECDSA.recover` therefore returns the same `nearBridgeDerivedAddress` on every chain, and the signature check passes unconditionally.

The `ERR_TOKEN_EXIST` guard only prevents a second deployment of the same token on the same chain — it does not prevent the first (attacker-initiated) deployment on a chain where the token has not yet been deployed: [9](#0-8) 

On Starknet, `deploy_token` calls `_verify_borsh_signature` on the chain-ID-free payload, then checks `existing_token.is_zero()` — which is zero on any chain where the token has not yet been deployed: [10](#0-9) 

## Impact Explanation

This is a **Critical authorization bypass and chain/domain separation flaw**. An attacker executes token deployer actions across all supported chains using a single MPC signature obtained by observing any one chain's public `deployToken` transaction — without any MPC authorization for the target chains. On EVM chains, the attacker front-runs the official relayer, deploying the bridge token at the bridge contract's current nonce; the `ERR_TOKEN_EXIST` guard then permanently blocks any subsequent official deployment attempt for that token on that chain. On Starknet and Solana, the attacker sets the token mapping state before the official relayer, executing an unauthorized deployer action. This matches the allowed Critical impact: **unauthorized transaction / authorization bypass / chain-domain separation flaw enabling invalid finalization**.

## Likelihood Explanation

All `deployToken` transactions are fully public on-chain. The attacker requires no privileged access, no leaked keys, and no off-chain coordination. The steps are: (1) monitor any supported chain for a `deployToken` call, (2) extract `signatureData` and `metadata` from calldata, (3) submit the identical call to every other supported chain before the official relayer. The attack is executable by any external observer immediately after a `deployToken` transaction is broadcast, and is repeatable for every new token deployment across all chains.

## Recommendation

Include the destination chain identifier in the `deployToken`/`deploy_token` Borsh-encoded payload, exactly as `finTransfer`/`fin_transfer` already does.

On EVM (`OmniBridge.sol`):
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the equivalent fix to `MetadataPayloadImpl::to_borsh` in `starknet/src/bridge_types.cairo` (pass and encode `chain_id` as `TransferMessagePayloadImpl::to_borsh` does) and to `DeployTokenPayload::serialize_for_near` in `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs` (write `SOLANA_OMNI_BRIDGE_CHAIN_ID` before the payload fields). The NEAR MPC signing logic must also be updated to include the target chain ID when constructing the payload to sign, so that signatures are chain-specific.

## Proof of Concept

1. Observe a `deployToken(signatureData, metadata)` call on Ethereum mainnet for token `"usdc.near"` (name `"USD Coin"`, symbol `"USDC"`, decimals `6`).
2. The Borsh-encoded message is: `[0x01] ++ borsh("usdc.near") ++ borsh("USD Coin") ++ borsh("USDC") ++ [0x06]` — identical on every EVM chain, Starknet, and Solana.
3. Submit the same `signatureData` and `metadata` to the Base bridge contract before the official relayer does.
4. `ECDSA.recover(keccak256(borshEncoded), signatureData)` returns `nearBridgeDerivedAddress` (same key, same hash) → signature accepted.
5. The token is deployed on Base; `nearToEthToken["usdc.near"]` and `isBridgeToken` are set.
6. When the official relayer later attempts to deploy `"usdc.near"` on Base, `require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")` reverts — the official deployment is permanently blocked.
7. Repeat for Arbitrum, Polygon, Starknet, and Solana using the same `signatureData`.

A local integration test can demonstrate this by: (a) deploying two instances of `OmniBridge` with different `omniBridgeChainId` values but the same `nearBridgeDerivedAddress`, (b) calling `deployToken` on instance A with a valid MPC signature, (c) replaying the identical calldata on instance B and asserting it succeeds — confirming the signature is accepted without chain-specific authorization.
