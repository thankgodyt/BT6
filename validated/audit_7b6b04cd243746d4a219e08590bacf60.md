Audit Report

## Title
ERC1155 `safeTransferFrom` Callback Permanently Freezes Bridged Funds for Non-Compliant Contract Recipients - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
In `OmniBridge.finTransfer`, ERC1155 tokens are delivered via `IERC1155.safeTransferFrom` (line 324), which mandatorily invokes `onERC1155Received` on any contract recipient per EIP-1155. If the recipient contract does not implement `IERC1155Receiver`, the call reverts. Because the MPC-signed payload cryptographically binds `payload.recipient` (line 298), no relayer can ever successfully finalize that transfer, and the corresponding NEAR-side tokens — already burned or locked — are permanently frozen with no on-chain rescue path.

## Finding Description
In `finTransfer` (line 287), `completedTransfers[payload.destinationNonce] = true` is set before the transfer. If the ERC1155 transfer reverts, the entire transaction reverts and the nonce is unwound — so the nonce is not permanently consumed. However, the Borsh-encoded message signed by the MPC system includes `Borsh.encodeAddress(payload.recipient)` at line 298, making the signature cryptographically inseparable from the specific recipient address. The ERC1155 branch (lines 323–330) calls:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per EIP-1155, `safeTransferFrom` to a contract address must call `onERC1155Received` and revert if the correct selector is not returned. If `payload.recipient` is any contract without `IERC1155Receiver` (e.g., Gnosis Safe, any DeFi protocol), every `finTransfer` attempt for that signed payload reverts. There is no EVM-side mechanism to substitute an alternative recipient, and no on-chain rescue path exists. The NEAR-side tokens were consumed at initiation, leaving them permanently frozen.

## Impact Explanation
This concretely matches the allowed critical impact of **permanent freezing of bridged funds**. The NEAR-side tokens are burned/locked at `initTransfer1155` time. The EVM finalization is provably impossible for the signed payload — every retry reverts identically. The bridge holds the ERC1155 tokens indefinitely with no recovery mechanism. This is not a theoretical loss; the funds are irrecoverably stuck.

## Likelihood Explanation
ERC1155 bridging is a production feature (`initTransfer1155` / `finTransfer` with `multiTokens` mapping). No attacker capability is required — any unprivileged user who bridges ERC1155 tokens from NEAR back to a contract address that does not implement `IERC1155Receiver` triggers this. Gnosis Safe (the most widely used multisig), account-abstraction wallets, and the vast majority of DeFi contracts do not implement `IERC1155Receiver`. This is a common, realistic scenario, not an edge case.

## Recommendation
Wrap the `safeTransferFrom` call in a `try/catch` block. On failure, leave the nonce unconsumed and emit a `FinTransferFailed` event so that an admin-specified rescue path (alternative recipient or NEAR-side refund) can be triggered. Additionally, consider adding a protocol-level mechanism allowing the MPC/NEAR system to re-sign a `finTransfer` payload with a corrected recipient when the original finalization is provably impossible.

## Proof of Concept
1. User holds ERC1155 token `T` (tokenId `42`) on NEAR (bridged from EVM).
2. User calls NEAR bridge to transfer back to EVM, specifying `recipient = address(GnosisSafe)` (a contract without `IERC1155Receiver`).
3. NEAR burns the user's tokens and emits a cross-chain event.
4. Relayer calls `OmniBridge.finTransfer(sig, payload)` where `payload.tokenAddress` maps to the ERC1155 via `multiTokens`.
5. `completedTransfers[nonce] = true` is set (line 287).
6. `IERC1155(multiToken.tokenAddress).safeTransferFrom(bridge, GnosisSafe, 42, amount, "")` is called (line 324).
7. ERC1155 calls `GnosisSafe.onERC1155Received(...)` — GnosisSafe does not implement it → reverts.
8. Entire `finTransfer` reverts; nonce is cleared.
9. Relayer retries — same result every time, since the signature is bound to `GnosisSafe` as recipient.
10. User's NEAR-side tokens are gone; ERC1155 tokens remain locked in the bridge contract forever.

A local Foundry test can reproduce this by deploying a mock ERC1155, a mock recipient contract without `IERC1155Receiver`, constructing a valid signed payload targeting that recipient, and asserting that `finTransfer` always reverts.
