### Title
Arithmetic Underflow Panic in `check_withdraw_psbt` at Line 243 — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

An unprivileged user can craft a withdrawal PSBT where `amount - withdraw_fee - gas_fee < config.min_change_amount`, triggering an arithmetic underflow panic at `psbt.rs:243` rather than a graceful `require!` rejection. The state-inconsistency concern raised in the question is **not valid** due to NEAR's atomic transaction model, but the panic itself is a real, publicly reachable invariant violation.

---

### Finding Description

The public entry point is `ft_on_transfer` in `contracts/satoshi-bridge/src/api/token_receiver.rs`, callable by any user via the NEP-141 `ft_transfer_call` flow. [1](#0-0) 

The call chain is:

```
ft_on_transfer → ft_on_transfer_withdraw_chain_specific
              → create_btc_pending_info
              → check_withdraw_psbt_valid
              → check_withdraw_psbt
```

Inside `check_withdraw_psbt`, `gas_fee` is computed as: [2](#0-1) 

The attacker controls the `output` vector, so they control `total_output_amount` and therefore `gas_fee`. Then: [3](#0-2) 

There is **no guard** between line 242 and line 243 that checks `max_received_amount >= config.min_change_amount` before the subtraction. The gas-fee range check that would reject an out-of-range `gas_fee` appears only **after** line 243: [4](#0-3) 

If `overflow-checks = true` is set in the release profile (standard NEAR SDK practice), the subtraction at line 243 panics instead of wrapping. If overflow checks are disabled, the subtraction wraps to a near-`u128::MAX` value and the subsequent `require!` at lines 244–251 rejects it gracefully — meaning the vulnerability is **conditional on overflow checks being enabled**. [5](#0-4) 

---

### Impact Explanation

The panic causes `ft_on_transfer` to abort. Due to NEAR's atomic execution model, **all state mutations within that call — including UTXO removal performed in `generate_vutxos`** — are rolled back: [6](#0-5) 

The nBTC token contract's `ft_resolve_transfer` callback then refunds the transferred tokens to the sender. Therefore:
- **No permanent UTXO removal** occurs.
- **No fund loss** occurs.
- **No stuck bridge state** results.

The state-inconsistency scenario described in the question is **not reachable** because NEAR panics roll back the entire call frame. The actual impact is limited to: a panic-driven fault in a production bridge path instead of a graceful `require!` rejection, violating the invariant that PSBT validation must reject invalid inputs cleanly.

---

### Likelihood Explanation

Any unprivileged user can trigger this by sending nBTC via `ft_transfer_call` with a `Withdraw` message containing outputs crafted so that `gas_fee` satisfies:

```
amount - withdraw_fee - min_change_amount < gas_fee ≤ amount - withdraw_fee
```

This is straightforward to achieve by adjusting the `output` amounts. The only prerequisite is that the bridge has UTXOs available matching the specified `input` outpoints, which is normal operating state.

---

### Recommendation

Insert a checked subtraction or an explicit guard before line 243:

```rust
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .unwrap_or_else(|| env::panic_str("amount insufficient to cover fees"));

require!(
    max_received_amount >= config.min_change_amount,
    format!(
        "Remaining amount ({}) is less than min_change_amount ({})",
        max_received_amount, config.min_change_amount
    )
);
let min_received_amount = max_received_amount - config.min_change_amount;
```

Apply the same pattern to line 242 (`amount - withdraw_fee - gas_fee`) to prevent a prior underflow there as well.

---

### Proof of Concept

Given config values:
- `min_withdraw_amount` = 5000
- `withdraw_bridge_fee` → computes `withdraw_fee` = 100
- `min_btc_gas_fee` = 200, `max_btc_gas_fee` = 50000
- `min_change_amount` = 1000

Craft a PSBT where:
- `amount` = 5000 (transferred nBTC)
- UTXO inputs total = 10000 sat
- Outputs: one recipient output of 500 sat + one change output of 5300 sat → `total_output_amount` = 5800, `gas_fee` = 4200

Then:
- `max_received_amount = 5000 - 100 - 4200 = 700`
- `min_received_amount = 700 - 1000` → **underflow panic** at line 243

The gas-fee check (`4200 ≤ 50000`) would have passed, but it is never reached. [7](#0-6)
