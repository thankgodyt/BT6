### Title
Unguarded `Word64` Arithmetic in Hard-Fork Era Boundary Computation Silently Corrupts `Summary`, Bypassing Invariant Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Summary.hs`, `Ouroboros/Consensus/HardFork/History/Util.hs`)

---

### Summary

The Hard-Fork History subsystem computes era-transition `Bound` values (slot, epoch, time) using unguarded `Word64` arithmetic. Two distinct but compounding weaknesses exist: (1) the multiplication `inEraSlots = inEraEpochs * unEpochSize eraEpochSize` in `mkUpperBound` has no overflow protection whatsoever; (2) the subtraction guards in `subSlots`, `countSlots`, `countEpochs`, and `countPerasRounds` rely on `Control.Exception.assert`, which is a **no-op in production** because the `asserts` Cabal flag defaults to `False`. When overflow occurs, `invariantSummary` cannot detect it because it recomputes the same overflowed product, making the self-check blind. A corrupted `Summary` is used for every slot↔epoch↔time translation and every era-boundary decision across the entire node.

---

### Finding Description

**Root cause 1 — unguarded multiplication, no protection at all:** [1](#0-0) 

```haskell
inEraEpochs, inEraSlots :: Word64
inEraEpochs = countEpochs hiEpoch (boundEpoch lo)
inEraSlots  = inEraEpochs * unEpochSize eraEpochSize   -- no overflow guard
```

Both operands are `Word64`. Haskell's `Word64` arithmetic is modular; there is no checked-arithmetic wrapper, no `assert`, and no saturation. A product that exceeds `2^64 − 1` silently wraps to a small value.

**Root cause 2 — subtraction guards disabled by default in production:** [2](#0-1) 

```haskell
addSlots  n (SlotNo x)  = SlotNo (x + n)          -- no overflow guard
subSlots  n (SlotNo x)  = assert (x >= n) $ SlotNo (x - n)
countSlots  (SlotNo to) (SlotNo fr) = assert (to >= fr) $ to - fr
countEpochs (EpochNo to)(EpochNo fr)= assert (to >= fr) $ to - fr
```

`assert` from `Control.Exception` is silenced by GHC unless `-fno-ignore-asserts` is passed. The project's Cabal flag: [3](#0-2) 

```
flag asserts
  description: Enable assertions
  manual: False
  default: False          -- OFF in production
``` [4](#0-3) 

```
if flag(asserts)
  ghc-options: -fno-ignore-asserts
```

The Nix build even has an explicit `noAsserts` variant that strips `cabal/asserts.cabal` entirely: [5](#0-4) 

So in every standard production build, all four `assert`-guarded arithmetic operations execute without any runtime check.

**Root cause 3 — `invariantSummary` is blind to the overflow:** [6](#0-5) 

```haskell
let epochsInEra, slotsInEra :: Word64
    epochsInEra = countEpochs (boundEpoch curEnd) (boundEpoch curStart)
    slotsInEra  = epochsInEra * unEpochSize (eraEpochSize curParams)  -- same multiplication
...
unless (boundSlot curEnd == addSlots slotsInEra (boundSlot curStart)) $
  throwError "Invalid final boundSlot ... (INV-1b)"
```

`invariantSummary` recomputes `slotsInEra` with the **identical** overflowing expression. If `mkUpperBound` overflowed, `invariantSummary` overflows by the same amount and the equality check passes. The corruption is undetectable by the built-in invariant.

**Downstream use — the corrupted `Summary` drives all consensus time/era logic:** [7](#0-6) 

`reconstructSummary` calls `mkUpperBound` for every `TransitionKnown` era and returns the `Summary` that is subsequently used for every `slotToEpoch`, `epochToSlot`, `wallclockToSlot`, and safe-zone calculation across the node.

---

### Impact Explanation

A corrupted `boundSlot` in an era's upper `Bound` causes the node to place the era boundary at the wrong absolute slot. Consequences:

- **Cross-era consensus break**: the node disagrees with peers about which era a given slot belongs to, causing it to apply the wrong era's validation rules to incoming blocks — accepting blocks that should be rejected or rejecting valid blocks.
- **Hard-fork transition failure**: `applySafeZone` and `reconstructSummary` use the corrupted `Bound` to decide when the safe zone ends; a node may prematurely or never transition to the next era.
- **Ledger-view / forecast corruption**: `EpochInfo` derived from the corrupted `Summary` feeds into leader-schedule and VRF/KES period calculations, potentially causing a node to compute wrong KES periods and reject valid operational certificates.

This matches the allowed impact: *"Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes."*

---

### Likelihood Explanation

**Overflow of the multiplication** requires `inEraEpochs * eraEpochSize > 2^64`. With Cardano mainnet's epoch size of 432,000 slots, overflow needs `inEraEpochs > ~4.3 × 10^13` — not reachable on mainnet. However:

- On a **private testnet** with a large `eraEpochSize` (e.g., `2^32`) and a transition epoch set far in the future (`hiEpoch` large), the product overflows with modest parameter values.
- A **crafted snapshot** (DB/snapshot input) containing a ledger state with extreme protocol parameters would trigger the path on node restart.
- The test suite itself acknowledges the overflow risk and explicitly avoids large values: [8](#0-7) 

```haskell
-- The functions 'slotAtTime' and 'timeUntilNextSlot' suffer from arithmetic
-- overflow for very large values, so generate values that avoid overflow when
-- used in these two functions.
genLimitedSlotNo :: Gen SlotNo
genLimitedSlotNo =
  SlotNo <$> arbitrary `suchThat` (< 0x8000000000000000)
```

The production code has no equivalent limit. **Likelihood: Low on mainnet; Medium on private testnets or with crafted snapshots.**

---

### Recommendation

1. **Replace the bare `Word64` multiplication** in `mkUpperBound` and `invariantSummary` with a checked variant that throws a hard error on overflow:
   ```haskell
   checkedMul :: Word64 -> Word64 -> Word64
   checkedMul a b
     | b /= 0, a > maxBound `div` b = error "Word64 overflow in era slot count"
     | otherwise = a * b
   ```
   Apply the same pattern to `addSlots` and `addEpochs`.

2. **Enable the `asserts` flag unconditionally** for production node builds, or replace `Control.Exception.assert` with always-on checked arithmetic (e.g., using `Data.Bits` overflow detection or `Natural` for intermediate products).

3. **Fix `invariantSummary`** to detect overflow independently — e.g., by computing `slotsInEra` via `Natural` and then checking it fits in `Word64` before comparing.

---

### Proof of Concept

On a private testnet, configure an era with:
```
eraEpochSize = 2^32   -- 4,294,967,296 slots/epoch
```
and schedule a hard-fork transition at epoch `hiEpoch = boundEpoch lo + 2^32`.

Then:
```
inEraEpochs = 2^32
inEraSlots  = 2^32 * 2^32 = 2^64  ≡  0  (mod 2^64)
```

`mkUpperBound` sets `boundSlot = addSlots 0 (boundSlot lo) = boundSlot lo`. The era end slot equals the era start slot. `invariantSummary` recomputes the same zero and passes the check. Every subsequent `slotToEpoch` query for any slot in that era returns the wrong epoch, and the node diverges from peers that computed the correct boundary.
