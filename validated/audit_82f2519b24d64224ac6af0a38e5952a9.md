### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold, Enabling Certificate Forging With Minority Stake - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` accumulates raw `PerasVoteStake` values and compares them directly against a fixed relative quorum threshold (`3/4 + 2/100`) without normalizing by the total committee stake. The code itself documents this flaw with an explicit TODO. If the `PerasVoteStakeDistr` is populated with absolute ledger-stake values (the natural output of the Cardano ledger), any single pool whose absolute stake exceeds `0.77` — which is every pool with any meaningful stake — can forge a Peras certificate with a single vote, bypassing the quorum requirement entirely.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate that decides whether accumulated votes constitute a valid Peras quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake        = unPerasVoteStake voteStake          -- raw accumulated Rational
  quorumThreshold = unPerasQuorumStakeThreshold ...  -- 3/4
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin ... -- 2/100
```

The code's own comment at lines 155–161 states:

> **TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units. … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally.**

`PerasVoteStake` is a bare `Rational` with no enforced unit. The `PerasVoteStakeDistr` that feeds it is populated from the ledger stake distribution, which naturally carries absolute lovelace values. No normalization step exists anywhere in the call chain:

1. `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote` where `sd` is the raw `PerasVoteStakeDistr` from `getStakeDistrSTM`.
2. `validatePerasVote` (degenerate instance, lines 363–371) does a plain `lookupPerasVoteStake` and stores the raw value as `vpvVoteStake`.
3. `updateCandidateVoteState` (lines 577–587) calls `votesReachQuorum`, which sums `vpvVoteStake` values and passes the raw sum to `stakeAboveThreshold`.
4. `updateLoserVoteState` (lines 600–606) calls `stakeAboveThreshold` on the raw tally directly.

There is no division by total committee stake, no normalization pass, and no type-level distinction between absolute and relative stake.

**Concrete mismatch:** The Cardano ledger expresses pool stake in lovelace (e.g., a 1 % pool ≈ 450 × 10¹² lovelace). The quorum threshold is `0.77` (a fraction). The comparison `450_000_000_000_000 ≥ 0.77` is trivially `True`. A single pool operator submitting one vote would immediately satisfy `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just`, and `updateCandidateVoteState` to call `forgePerasCert` — producing a valid `ValidatedPerasCert` backed by a single vote.

---

### Impact Explanation

**Peras certificate verification bypass.** An unprivileged pool operator can forge a Peras certificate for any block with a single vote, bypassing the `3/4`-stake quorum. A forged certificate carries `perasWeight = 15` boost in chain selection. An adversary who can forge certificates at will can boost an adversarial fork's chain weight by 15 per round, causing honest nodes to prefer the adversarial chain over the canonical chain. This is a chain-selection safety failure reachable from the public Peras vote miniprotocol.

---

### Likelihood Explanation

**Medium.** The attack requires only that the node's `PerasVoteStakeDistr` is populated with absolute lovelace values — the natural output of the Cardano ledger's pool distribution. Any registered pool operator can submit a vote via the Peras vote diffusion miniprotocol. No key compromise, stake majority, or privileged access is needed. The TODO comment confirms the normalization gap is known and unresolved.

---

### Recommendation

`stakeAboveThreshold` must normalize the accumulated vote stake by the total committee stake before comparing against the relative threshold. Concretely:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStakeDistr -> PerasVoteStake -> Bool
stakeAboveThreshold params distr voteStake =
  normalizedStake >= quorumThreshold + safetyMargin
 where
  totalStake      = sum (Map.elems (unPerasVoteStakeDistr distr))
  normalizedStake = unPerasVoteStake voteStake / unPerasVoteStake totalStake
  ...
```

Alternatively, enforce at the type level that `PerasVoteStake` values stored in `PerasVoteStakeDistr` are always pre-normalized (summing to 1) before being handed to the aggregation layer, and add an assertion or `newtype` wrapper to make this invariant machine-checked.

### Proof of Concept

**Entry point:** Peras vote miniprotocol → `processVotes` → `validatePerasVote` → `PerasVoteDB.addVote` → `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold`.

**Trigger sequence (private testnet):**

1. Register a stake pool with any positive lovelace stake (e.g., 1 ADA = 1,000,000 lovelace).
2. Submit a single `PerasVote` for any block in the current round via the Peras vote diffusion channel.
3. The node calls `validatePerasVote`, which looks up the pool's stake in `PerasVoteStakeDistr` and stores `vpvVoteStake = PerasVoteStake (1_000_000 % 1)`.
4. `votesReachQuorum` sums to `1_000_000 % 1` and calls `stakeAboveThreshold params (PerasVoteStake (1_000_000 % 1))`.
5. The check `1_000_000 >= 0.75 + 0.02` evaluates to `True`.
6. `forgePerasCert` is called and a `ValidatedPerasCert` is produced and stored in the `PerasVoteDB`.
7. The certificate is included in the next block, boosting the adversarial fork's chain weight by `perasWeight = 15`.
