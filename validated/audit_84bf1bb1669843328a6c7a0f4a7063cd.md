Audit Report

## Title
Push-Based ETH Delivery in `finTransfer` Permanently Freezes Bridged Native Funds When Recipient Reverts - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.finTransfer()` delivers native ETH to the recipient using a push-based `.call{value}` pattern. If the recipient contract's `receive`/`fallback` reverts, the entire transaction reverts — including the nonce-consumption write — but the `payload.recipient` field is cryptographically bound inside the MPC-signed payload and cannot be altered by any relayer. Every subsequent finalization attempt with the same signed payload produces an identical revert, permanently preventing delivery. Because the originating NEAR tokens are already burned or locked at initiation time, the user suffers permanent loss of bridged funds with no on-chain recovery path.

## Finding Description

In `finTransfer`, the nonce is marked consumed at line 287, then the MPC signature is verified at line 311 over a Borsh-encoded payload that includes `payload.recipient` at line 298. After signature verification, the ETH delivery branch executes:

```solidity
// OmniBridge.sol L317-322
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
```

If `payload.recipient` is a contract whose `receive`/`fallback` reverts, `revert FailedToSendEther()` unwinds the entire transaction, including the `completedTransfers[payload.destinationNonce] = true` write at line 287. The nonce is therefore never consumed. However, because `payload.recipient` is part of the signed Borsh blob (line 298) and the signature check at line 311 enforces that no field — including `recipient` — can be altered, every future call with the same signed payload produces the identical revert. There is no admin rescue function, no pull-withdrawal mapping, and no alternative finalization path. The ETH held by the bridge for this transfer is permanently frozen.

The identical structural flaw exists in the ERC-1155 branch (lines 323–330): `IERC1155.safeTransferFrom` calls `onERC1155Received` on the recipient; if the recipient does not implement `IERC1155Receiver`, the call reverts and the same permanent freeze results.

Existing guards are insufficient: the `NonceAlreadyUsed` check (line 283) only prevents replay of *successfully completed* transfers; it provides no relief here because the nonce is never durably consumed. The `whenNotPaused` modifier (line 282) is an emergency brake, not a recovery mechanism.

## Impact Explanation

This directly matches the allowed Critical impact: **permanent freezing of bridged funds across NEAR and EVM**. The user's NEAR-side tokens are burned or locked at `initTransfer` time. The EVM-side finalization can never succeed. The ETH allocated for the transfer remains locked in the bridge contract indefinitely with no mechanism for the user, relayer, or admin to recover it.

## Likelihood Explanation

No privileged access or attacker cooperation is required. The condition is triggered by the user's own legitimate action: specifying as `recipient` any smart contract that lacks a payable `receive`/`fallback`. This class of contract is extremely common — Gnosis Safe multisigs deployed without a payable fallback, ERC-20 token contracts, protocol vaults, and DAO treasuries all fall into this category. A user bridging ETH into a DeFi contract they intend to interact with post-bridge is a routine operation. The scenario is repeatable, requires no special timing, and is fully self-contained within public bridge calls.

## Recommendation

Replace the push pattern with a pull pattern for native ETH delivery:

1. Instead of `payload.recipient.call{value: payload.amount}("")`, credit `ethBalance[payload.recipient] += payload.amount` in a `mapping(address => uint256)` and allow `finTransfer` to complete successfully.
2. Add a public `withdrawETH()` function: `uint256 amt = ethBalance[msg.sender]; ethBalance[msg.sender] = 0; (bool ok,) = msg.sender.call{value: amt}(""); require(ok);`
3. Apply the same pattern to the ERC-1155 `safeTransferFrom` branch: catch the revert (via a try/catch) and store the pending transfer for the recipient to claim via a separate `claimERC1155` function.

This ensures a reverting recipient never blocks finalization and that funds remain claimable rather than frozen.

## Proof of Concept

1. Deploy `RevertingReceiver` on a local fork:
   ```solidity
   contract RevertingReceiver {
       receive() external payable { revert(); }
   }
   ```
2. On NEAR (or simulated), initiate a NEAR → EVM transfer of native ETH with `recipient = address(RevertingReceiver)`. NEAR tokens are burned/locked.
3. MPC produces a valid signature over the Borsh-encoded `TransferMessagePayload` with `tokenAddress = address(0)`, `amount = X`, `recipient = address(RevertingReceiver)`.
4. Call `OmniBridge.finTransfer(signatureData, payload)`.
5. Execution reaches line 319: `payload.recipient.call{value: X}("")` → callee reverts.
6. Line 322: `revert FailedToSendEther()` unwinds the transaction; `completedTransfers[nonce]` remains `false`.
7. Repeat step 4 with the same `signatureData` and `payload` — identical revert every time.
8. Observe: NEAR tokens permanently burned; ETH in bridge permanently frozen; no recovery path exists.
