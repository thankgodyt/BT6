### Title
`assertWithMsg` Envelope Check Silently Discarded in Production Builds in `revalidateHeader` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full header-envelope check (block number, slot number, previous hash, checkpoint) and passes it to `assertWithMsg`. However, `assertWithMsg` is a CPP-gated no-op in every production build where the `asserts` Cabal flag is absent — which is the **default**. The computed check result is silently discarded, and the function unconditionally returns the updated `HeaderState`. This is the direct structural analog of the ERC-20 `transferFrom` unchecked-return-value pattern: the operation is invoked, a success/failure value is produced, and that value is thrown away.

---

### Finding Description

**`assertWithMsg` is a compile-time no-op by default.** [1](#0-0) 

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

`ENABLE_ASSERTIONS` is only defined when the `asserts` Cabal flag is set: [2](#0-1) [3](#0-2) 

```
flag asserts
  description: Enable assertions
  manual: False
  default: False          -- OFF by default
...
  if flag(asserts)
    ghc-options: -fno-ignore-asserts
    cpp-options: -DENABLE_ASSERTIONS
```

The project documentation explicitly calls this out as something that must be *temporarily* enabled for extra checks, confirming it is **not** on in normal production deployments.

**`revalidateHeader` relies solely on `assertWithMsg` for its envelope check.** [4](#0-3) 

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← silently discarded in production
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' =
    reupdateChainDepState               -- skips expensive crypto checks by design
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck :: Either String ()
  envelopeCheck =
    runExcept $
      withExcept show $
        validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` checks consecutive block numbers, monotonically increasing slot numbers, the previous-hash linkage, and checkpoint hashes: [5](#0-4) 

In production (no `asserts` flag), `assertWithMsg envelopeCheck` reduces to `id`. The `envelopeCheck` value is computed and immediately discarded; the function returns the new `HeaderState` regardless of whether the envelope is valid.

Contrast with `validateHeader` (the primary path for new headers), which uses a proper `Except` monad and propagates every error: [6](#0-5) 

`revalidateHeader` is called from `reapplyBlockLedgerResult` on `ExtLedgerState`, which is the path taken when a block is re-applied from the `prevApplied` set or from an on-disk snapshot during chain replay: [7](#0-6) 

---

### Impact Explanation

In production builds the envelope check inside `revalidateHeader` is a dead computation. Any block reaching this path with a mismatched block number, wrong slot, broken hash chain, or checkpoint violation will silently produce an updated `HeaderState` as if the check had passed. This corrupts the node's local `HeaderState`, which is the authoritative record of the chain-dep state (KES/VRF evolution counter, PBFT window, etc.) and the tip used for all subsequent header validation. A corrupted `HeaderState` can cause the node to accept headers it should reject, or reject headers it should accept, diverging from the honest chain — a chain-selection / ledger-view integrity failure.

---

### Likelihood Explanation

`revalidateHeader` is invoked only for blocks already in `prevApplied` (previously validated in the same session) or during startup replay from an on-disk snapshot. Under normal operation the blocks reaching this path are genuinely valid, so the silent discard has no observable effect. However:

1. **On-disk replay**: blocks replayed from the ImmutableDB at startup pass through `reapplyThenPushNOW` → `tickThenReapply` → `revalidateHeader`. A crafted or corrupted ImmutableDB entry (e.g., injected via a snapshot-converter tool or a storage-layer bug) would bypass the envelope check entirely.
2. **Future code paths**: any new caller that passes a not-yet-validated block to `reapplyBlockLedgerResult` (e.g., an optimistic fast-path) would silently skip the envelope check in production, exactly as the ERC-20 report warns about future development increasing impact.

Likelihood is **low** today but non-zero and structurally unguarded.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with a proper `Except`-based check that is always enforced, mirroring `validateHeader`. The `reupdateChainDepState` call (which intentionally skips expensive crypto) can be retained; only the envelope check needs to be unconditional:

```haskell
revalidateHeader cfg ledgerView hdr st = do
  withExcept HeaderEnvelopeError $
    validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
  return $ HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' = reupdateChainDepState ...
```

Alternatively, if the assertion-only pattern is intentional for performance, the `asserts` flag should be documented as **required** for production deployments and enforced in the release build pipeline (analogous to recommending `safeTransferFrom` to ensure all ERC-20 implementations are handled correctly).

---

### Proof of Concept

1. Build `cardano-node` / `ouroboros-consensus` without the `asserts` flag (the default).
2. Construct an ImmutableDB chunk file in which one block's header has its `blockNo` field incremented by 1 (breaking the consecutive-block-number invariant).
3. Start the node from that database. During startup replay, `reapplyThenPushNOW` calls `tickThenReapply` → `reapplyBlockLedgerResult` (ExtLedgerState) → `revalidateHeader`.
4. `revalidateHeader` computes `envelopeCheck = Left "UnexpectedBlockNo ..."` but `assertWithMsg` discards it; the node proceeds with a `HeaderState` whose `headerStateTip` records the wrong block number.
5. All subsequent `validateHeader` calls use this corrupted tip as the "old tip", causing legitimate successor headers to fail the `expectedNextBlockNo` check and be rejected — a persistent, silent chain-selection failure triggered by a crafted on-disk input. [1](#0-0) [8](#0-7) [2](#0-1)
