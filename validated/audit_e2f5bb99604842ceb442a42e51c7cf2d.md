Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Message-Account Pre-Deposit in `init_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `NativeFeeRestricted` role check in `init_transfer` is placed exclusively inside Branch 2 of a short-circuit OR condition. Branch 1 (`try_to_transfer_balance_from_message_account`) performs no role check and succeeds whenever the deterministic message-storage virtual account is pre-funded. An attacker holding the `NativeFeeRestricted` role can pre-deposit to the predictable virtual account and trigger Branch 1, causing the OR to short-circuit and the role guard in Branch 2 to be skipped entirely, allowing a non-zero `native_token_fee` to be attached to any outbound transfer.

## Finding Description
In `near/omni-bridge/src/lib.rs` lines 566–584, `init_transfer` evaluates:

```rust
if self.try_to_transfer_balance_from_message_account(   // Branch 1 – no role check
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    ).is_ok()
    || (self.has_storage_balance(...)                    // Branch 2 – role check here
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

The `NativeFeeRestricted` guard (`!self.acl_has_role(...)`) lives only in Branch 2. `try_to_transfer_balance_from_message_account` (lines 260–290 of `near/omni-bridge/src/storage.rs`) performs only balance checks — no role check — and returns `Ok(())` whenever the message-storage virtual account holds sufficient balance.

The message-storage account ID is computed deterministically from `TransferMessageStorageAccount { token, amount, recipient, fee, sender, msg }` (lines 623–634 of `near/omni-types/src/lib.rs`). Critically, `origin_nonce` is excluded from this struct, so the attacker can compute the virtual account address before submitting the transfer. The attacker pre-funds this account via a public `storage_deposit` call, causing Branch 1 to succeed, the OR to short-circuit, and Branch 2's role guard to be skipped. `init_transfer_internal` is then called with the non-zero `native_fee` intact.

## Impact Explanation
This is a concrete **role bypass**: the protocol's access-control invariant — that `NativeFeeRestricted` accounts cannot attach a non-zero `native_token_fee` to outbound transfers — is violated. The bypass is fully self-funded (the attacker deposits their own NEAR to the virtual account), so there is no direct theft of protocol funds, but the role restriction is rendered entirely ineffective. This matches the allowed Critical impact class: "Unauthorized transaction, authorization bypass, role bypass … that lets an attacker execute bridge … actions."

## Likelihood Explanation
The attacker must already hold the `NativeFeeRestricted` role (i.e., the protocol has flagged them). Given that precondition, the bypass requires exactly two permissionless public calls: `storage_deposit` to the pre-computed virtual account, then `ft_transfer_call` with a non-zero `native_token_fee`. Both calls are available to any account. The virtual account ID is fully predictable from attacker-controlled inputs with no randomness or admin involvement required. The attack is repeatable for every transfer the attacker initiates.

## Recommendation
Move the `NativeFeeRestricted` check to an unconditional position before the OR branch, so it cannot be bypassed regardless of which storage path is taken:

```rust
if init_transfer_msg.native_token_fee.0 != 0 {
    require!(
        !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
        BridgeError::NativeFeeRestricted.as_ref()
    );
}

if self.try_to_transfer_balance_from_message_account(...).is_ok()
    || self.has_storage_balance(...)
{
    self.init_transfer_internal(transfer_message, signer_id)
}
```

## Proof of Concept
1. Admin grants `NativeFeeRestricted` to `attacker.near`.
2. Attacker constructs the planned `InitTransferMsg` (token, amount, recipient, fee, msg).
3. Attacker computes `message_storage_account_id` by hashing `TransferMessageStorageAccount { token, amount, recipient, fee, sender: OmniAddress::Near("attacker.near"), msg }` — no `origin_nonce` needed.
4. Attacker calls `storage_deposit(account_id = message_storage_account_id)` depositing `native_token_fee + required_storage_balance`.
5. Attacker calls `ft_transfer_call` on the token contract with `receiver_id = locker`, `amount`, and `msg = InitTransferMsg { native_token_fee: <non-zero>, ... }`.
6. Inside `ft_on_transfer` → `init_transfer`, Branch 1 (`try_to_transfer_balance_from_message_account`) returns `Ok(())` because the virtual account is funded. The OR short-circuits; Branch 2 and its `NativeFeeRestricted` check are never evaluated.
7. `init_transfer_internal` is called with a non-zero `native_fee` in the stored `TransferMessage`.
8. The relayer later receives the native fee — despite the attacker being `NativeFeeRestricted`.

The existing integration test in `near/omni-tests/src/native_fee_role.rs` (`test_native_fee_restriction`) only tests the direct Branch 2 path (sender deposits to their own account) and does not cover the message-account pre-deposit path, confirming the bypass is untested.
