### Title
Peras Certificate Validation Bypass Allows Any Peer to Forge Weight-Boosting Certificates and Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally accepts every inbound Peras certificate without performing any cryptographic or structural verification. An unprivileged peer can craft a `PerasCert` for any block, have it accepted by the node's certificate diffusion miniprotocol, and cause chain selection to apply an unearned weight boost to a non-canonical block, making the node prefer a fork it should not.

---

### Finding Description

The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` defines the interface for Peras certificate and vote validation. The only active instance is the catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

Within this instance, `validatePerasCert` is implemented as:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [2](#0-1) 

Every certificate is unconditionally accepted and assigned the full `perasWeight` boost. The `PerasCert blk` data type in this instance carries only a round number and a block point — no aggregate BLS signature, no voter bitmap, no eligibility proof:

```haskell
  data PerasCert blk = PerasCert
    { pcCertRound :: PerasRoundNo
    , pcCertBoostedBlock :: Point blk
    }
``` [3](#0-2) 

The concrete BLS-signed certificate type (`Peras.Cert.V1.PerasCert`) that does carry a `pcSignature :: AggregateVoteSignature` and a `pcVoters :: PerasCertVoters` bitmap is defined in a separate module but is **not** wired into the `BlockSupportsPeras` instance. [4](#0-3) 

The same pattern applies to `validatePerasVote`: it only performs a stake-distribution lookup to confirm the claimed `pvVoteVoterId` is a committee member, but never verifies the BLS vote signature. The `PerasVote blk` type in the production instance has no signature field at all. [5](#0-4) 

**Attacker-controlled entry path — certificate diffusion miniprotocol:**

In `NodeToNode.hs`, the `hPerasCertDiffusionClient` handler wires inbound peer certificates directly to `makePerasCertPoolWriterFromChainDB`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [6](#0-5) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator, then passes accepted certificates to `ChainDB.addPerasCertAsync`:

```haskell
(validatePerasCert mkPerasParams)
...
(void . ChainDB.addPerasCertAsync chainDB)
``` [7](#0-6) 

`processCerts` calls `validateCert` on each new certificate and, if all pass, adds them to the database. Since `validatePerasCert` always returns `Right`, every certificate from every peer is stored. [8](#0-7) 

Once stored, the certificate's boost is applied to chain selection via `getPerasWeightSnapshot` / `addPerasCertAsync`, causing the node to prefer the boosted block. [9](#0-8) 

**Analogy to the external report:**

In the Solidity bug, `receiveTokenOrETH` accepts ETH from `msg.sender` without verifying `msg.sender == lender` — the actual payer is not checked against the claimed payer. Here, `validatePerasCert` accepts a certificate claiming to certify block B without verifying any cryptographic proof that a quorum of committee members actually signed it — the actual signers are never checked against the claimed certifiers.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A peer that connects via the standard Peras certificate diffusion miniprotocol can send a crafted `PerasCert` naming any block point. The certificate passes `validatePerasCert` unconditionally, is stored in the ChainDB, and its `perasWeight` boost is applied to chain selection. If the boosted block is on a fork, the node may switch away from the canonical chain. Because the boost is persistent (stored in the cert DB), the effect survives reconnections. Multiple forged certificates for different rounds can compound the effect.

---

### Likelihood Explanation

Any peer that speaks the Peras certificate diffusion miniprotocol can trigger this. No stake, no keys, no prior relationship is required. The miniprotocol is enabled in the production `NodeToNode` handlers. The only prerequisite is that the Peras era is active on the network. The attack requires sending a single well-formed CBOR-encoded `PerasCert` message with an arbitrary `pcCertRound` and `pcCertBoostedBlock`.

---

### Recommendation

1. **Immediate**: Gate `validatePerasCert` on the aggregate BLS signature check using the concrete `Peras.Cert.V1` type and the `verifyCert` method from `CryptoSupportsVotingCommittee`. The `PerasCert blk` data type in the production instance must include the aggregate signature and voter bitmap fields before any certificate is accepted from the network.

2. **Structural**: Replace the catch-all `instance StandardHash blk => BlockSupportsPeras blk` placeholder with a proper Cardano-specific instance that uses the BLS-signed `Peras.Cert.V1.PerasCert` type and calls `verifyCert` from `Committee.Class`.

3. **For `validatePerasVote`**: Similarly, the production vote type must include the BLS `pvSignature` field (as in `Peras.Vote.V1.PerasVote`) and `validatePerasVote` must verify it against the committee member's public key before accepting the vote.

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate diffusion miniprotocol.
2. Construct a `PerasCert blk` value with:
   - `pcCertRound = <any round not yet in the node's cert DB>`
   - `pcCertBoostedBlock = <point of a fork block you want the node to prefer>`
3. Send it as a batch via the object diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
5. The cert is passed to `ChainDB.addPerasCertAsync`.
6. Chain selection applies the weight boost to the fork block, potentially causing the node to switch chains.

No cryptographic material, stake, or operator access is required. The attack is repeatable for each new round number.

makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- certs to the ChainDB and ignore the returned promise.
          -- The async action is still launched and executed behind the scenes
          -- even though we drop the promise.
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    , opwHasObject = do
        certIds <- ChainDB.getPerasCertIds chainDB
        pure $ \roundNo -> Set.member roundNo certIds
    }

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
