### Title
Attacker Can Front-Run `request_refund` to Block Victim's Refund and Cause Loss of NEAR Storage Deposit - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

An unprivileged attacker who observes a victim's `request_refund` transaction in the NEAR mempool can front-run it by submitting their own `request_refund` for the same UTXO with an attacker-controlled `refund_address`. Because the bridge stores at most one refund request per UTXO key, the victim's subsequent callback panics with "Refund request already exists for this UTXO," causing the victim to permanently lose their non-refundable NEAR storage deposit and leaving their BTC refund blocked until DAO/Operator intervention.

---

### Finding Description

`request_refund` is a two-step async flow: the outer call verifies the BTC transaction via the Light Client, then `request_refund_callback` stores the refund request. The outer call immediately consumes the caller's attached NEAR deposit (checked at entry, transferred to the contract on success) before the async verification completes. [1](#0-0) 

Inside the callback, a duplicate-key guard panics if a refund request already exists for the derived `utxo_storage_key`: [2](#0-1) 

The comment on that guard explicitly acknowledges the race: *"another request_refund could have landed between our check and callback."* However, the code does not handle this gracefully — it panics, which in NEAR's async model means the victim's attached deposit is **not returned**.

An attacker who sees the victim's `request_refund` in the NEAR mempool can:

1. Copy the victim's `deposit_msg`, `tx_bytes`, `vout`, and `proof` verbatim.
2. Submit their own `request_refund` with `refund_address = attacker_btc_address` and higher gas priority.
3. The attacker's callback succeeds first, inserting a refund request keyed to the same `utxo_storage_key` with the attacker's BTC address.
4. The victim's callback then hits the duplicate guard and panics.

Because `deposit_msg.refund_address` is `None` in the common case (no pre-authorized address), the check at line 154–158 does not prevent the attacker from supplying a different `refund_address`: [3](#0-2) 

The victim's NEAR storage deposit (sized to cover ~200 KB ≈ 2 NEAR per the inline comment) is permanently lost: [4](#0-3) 

The attacker's refund request now occupies the slot with the attacker's BTC address. The victim cannot submit a new `request_refund` until a DAO/Operator calls `reject_refund` to clear it: [5](#0-4) 

The attacker can repeat this front-run each time the victim retries, causing sustained denial of the refund path.

---

### Impact Explanation

**Medium.** The attack causes:

1. **Permanent loss of the victim's NEAR storage deposit** (~2 NEAR per attempt) — a real financial loss on each front-run.
2. **Attacker-triggered temporary locking of the victim's BTC refund** — the victim's deposit UTXO is stuck in the refund system under the attacker's address until DAO/Operator intervenes.

The BTC itself is not immediately stolen (theft requires the operator to fail to reject the attacker's request within `unsafe_refund_timelock_sec`), so this is classified as Medium rather than Critical. It matches the allowed impact: *"Medium. Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds."*

---

### Likelihood Explanation

**Moderate.** NEAR transactions are visible in the mempool before finalization. The attacker needs only to:
- Monitor the mempool for `request_refund` calls.
- Copy the proof and deposit data (all public).
- Pay their own NEAR storage deposit (non-refundable, ~2 NEAR).

The economic cost to the attacker is real but not prohibitive, especially if the victim's BTC deposit is large. The attack can be repeated on every retry, making it a sustained griefing vector.

---

### Recommendation

When `request_refund_callback` detects that a refund request already exists for the UTXO, it should **return `false`** (or emit an event and return gracefully) rather than panicking, and **refund the caller's attached deposit** via a Promise transfer back to `env::predecessor_account_id()`. This mirrors the correct pattern for handling benign races without penalizing the victim.

Additionally, consider binding the refund request to the `predecessor_account_id` of the original caller so that only the depositor (or a pre-authorized address) can create a refund request for a given UTXO, eliminating the front-run vector entirely.

---

### Proof of Concept

1. Victim calls `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, None)` attaching 2 NEAR.
2. Attacker observes the NEAR mempool, extracts `deposit_msg`, `tx_bytes`, `vout`, `proof`.
3. Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with higher gas, attaching 2 NEAR.
4. Attacker's `request_refund_callback` runs first → inserts `RefundRequest { refund_address: attacker_btc_addr, ... }` at `utxo_storage_key`.
5. Victim's `request_refund_callback` runs → hits `require!(!self.data().refund_requests.contains_key(&utxo_storage_key), "Refund request already exists for this UTXO")` → panics.
6. Victim's 2 NEAR deposit is not returned; victim's refund is blocked.
7. Victim retries → attacker repeats step 3 → victim loses another 2 NEAR.
8. Victim's BTC refund remains inaccessible until DAO/Operator calls `reject_refund`. [6](#0-5)

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
