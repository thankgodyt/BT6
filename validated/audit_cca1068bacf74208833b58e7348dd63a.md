### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Produces Incorrect Peras Non-Persistent Seat Counts for Realistic `lambda` Values — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds, where `x = -lambda`. For any voter whose `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, causing the Taylor-series comparison to terminate prematurely with an incorrect seat count. This is the direct analog of the Basin report's LUT gap: a pre-computed or hardcoded bound that is too coarse for extreme parameter values causes an iterative numerical algorithm to produce wrong results. The incorrect seat count propagates into `implVerifyVote` and `implVerifyCert` in `WFALS.hs`, materially weakening the Peras voting committee eligibility check.

---

### Finding Description

**Root cause — `LS.hs` lines 86–99:**

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
--
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded boundX
      orders
      (-lambda)  -- ← x = -lambda
``` [1](#0-0) 

The function's own contract, stated at line 121, is unambiguous:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

Since `x = -lambda`, the correct `boundX` is `e^lambda`. The hardcoded value `3` is only valid when `lambda ≤ ln(3) ≈ 1.099`.

**How `lambda` is computed:**

```haskell
lambda = fromRational $
  fromIntegral numNonPersistentVoters
    * voterStake
    / totalNonPersistentStake
``` [3](#0-2) 

`lambda` is the expected number of seats for this voter under the Poisson model. With a committee of 100 non-persistent seats and a voter holding 2% of non-persistent stake, `lambda = 2.0 > ln(3)`. This is a completely ordinary configuration.

**Why `3` is safe for slot leadership but not here:**

The TODO comment notes that `checkLeaderNatValue` in the Cardano ledger also uses `3`. That is safe because for slot leadership, `x = ln(1-f) * sigma` where `f ≈ 0.05` and `sigma ≤ 1`, giving `|x| ≤ 0.051` and `e^{0.051} ≈ 1.052 < 3`. For local sortition, `lambda` is unbounded above `ln(3)` and grows linearly with committee size and voter stake fraction.

**Mechanism of incorrect result:**

Inside `decideOne`, the error term is:

```haskell
errorTerm = abs (err' * boundX)
``` [4](#0-3) 

When `boundX = 3 < e^lambda`, `errorTerm` is underestimated. The "uncertain" band `[acc' - errorTerm, acc' + errorTerm]` is too narrow. The algorithm prematurely classifies a comparison as `Stop` (ABOVE) or `Below` before the Taylor series has converged, returning the wrong index — i.e., the wrong number of seats. This is structurally identical to the Basin report's step-size overshoot: a pre-computed bound that is too coarse for extreme parameter values causes the iterative algorithm to skip past the correct answer.

**Propagation into vote and certificate verification:**

`localSortitionNumSeats` is called in three production paths in `WFALS.hs`:

1. `implCheckShouldVote` (line 286) — determines how many seats to claim when forging a vote.
2. `implVerifyVote` (line 376) — verifies an incoming vote's non-persistent eligibility.
3. `implVerifyCert` (line 529) — verifies each non-persistent voter in an incoming certificate. [5](#0-4) [6](#0-5) 

The returned `numSeats` is stored in the `WFALSNonPersistentMember` eligibility witness and used directly to compute voting weight:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [7](#0-6) 

An inflated `numSeats` directly inflates the voter's `VoteWeight` proportionally.

---

### Impact Explanation

Because both the voter (`implCheckShouldVote`) and the verifier (`implVerifyVote`, `implVerifyCert`) call the same buggy `localSortitionNumSeats`, the incorrect seat count is computed identically on both sides. A voter whose `lambda > ln(3)` will have their seat count computed incorrectly. When the bug inflates the count, the voter's `VoteWeight` is proportionally inflated, and the inflated vote passes verification — because the verifier computes the same wrong count. This is a bypass of the Peras voting committee eligibility check: a non-persistent voter can accumulate more voting weight than their stake entitles them to, weakening the stake-proportionality guarantee of the wFA^LS scheme and potentially allowing a minority-stake voter to influence certificate formation beyond their intended bound.

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is triggered whenever:

```
numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.099
```

With a 100-seat non-persistent committee, any voter holding more than ~1.1% of the non-persistent stake is affected. This covers the vast majority of realistic stake pool configurations. The bug is triggered by any non-persistent voter submitting a vote or certificate — no special crafting is required. The TODO comment at line 86 and the linked issue (https://github.com/tweag/cardano-peras/issues/234) confirm the team is already aware this bound may be wrong. [8](#0-7) 

---

### Recommendation

Replace the hardcoded `3` with the correct `boundX = e^lambda`. Since `lambda` is already computed as a `FixedPoint`, use the `exp` function from `Cardano.Ledger.BaseTypes` (or the `NonIntegral` module) to compute `e^lambda` before passing it to `taylorExpCmpFirstNonLower`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda since x = -lambda
      orders
      (-lambda)
```

This mirrors the fix in the Basin report: replace the coarse pre-computed bound with the exact value required by the algorithm's convergence contract. Additionally, add a property test asserting that `localSortitionNumSeats` agrees with a reference Poisson CDF implementation for `lambda` values in the range `[0, 20]`.

---

### Proof of Concept

Consider a committee with `numNonPersistentVoters = 100`, a voter with `voterStake / totalNonPersistentStake = 0.05` (5% of non-persistent stake), and a `normalizedVRFOutput` near the median. Then:

- `lambda = 100 * 0.05 = 5.0`
- Correct `boundX = e^5 ≈ 148.4`
- Actual `boundX = 3`
- `errorTerm` is underestimated by a factor of ~49×

In `decideOne`, the Taylor partial sum for `e^{-5}` oscillates with large intermediate terms (the series `1 - 5 + 12.5 - 20.83 + ...` before converging to `≈ 0.0067`). With `errorTerm` underestimated by 49×, the algorithm will prematurely declare `Stop` at a partial sum that is far from `e^{-5}`, returning the wrong threshold index. The voter is assigned a seat count that does not correspond to the correct Poisson CDF comparison, and this incorrect count is accepted by `implVerifyVote` because it recomputes the same wrong value.
