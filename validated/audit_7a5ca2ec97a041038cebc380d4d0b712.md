### Title
Wrong Variable Used in Withdrawal Confirmation Threshold Calculation - (File: `contracts/satoshi-bridge/src/btc_light_client/withdraw.rs`)

### Summary
In `internal_verify_withdraw`, the confirmation count required to verify a withdrawal BTC transaction is determined using `btc_pending_info.actual_received_amount` instead of `btc_pending_info.transfer_amount`. Because `actual_received_amount` is always strictly less than `transfer_amount` (by `withdraw_fee + gas_fee`), the confirmation threshold lookup can resolve to a lower tier than the security policy intends, allowing a relayer to finalize a withdrawal with fewer on-chain confirmations than required for the full economic value being processed.

### Finding Description

In `internal_verify_withdraw` (`contracts/satoshi-bridge/src/btc_light_client/withdraw.rs`, line 20):

```rust
let confirmations = self.get_confirmations(config, btc_pending_info.actual_received_amount);
```

`actual_received_amount` is the BTC amount the user receives after deducting both the bridge fee (`withdraw_fee`) and the BTC network fee (`gas_fee`):

```
actual_received_amount = transfer_amount - withdraw_fee - gas_fee
```

The `get_confirmations` function (`contracts/satoshi-bridge/src/config.rs`, lines 196–220) maps satoshi thresholds to confirmation counts — higher amounts require more confirmations. By passing `actual_received_amount` instead of `transfer_amount`, the lookup is performed on a value that is always smaller than the true economic value being withdrawn.

By contrast, the deposit path correctly uses the full `deposit_amount`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs, line 31
let confirmations = self.get_confirmations(config, deposit_amount);
```

The `BTCPendingInfo` struct stores both values:
- `transfer_amount`: the nBTC amount the user transferred to the bridge (the full value)
- `actual_received_amount`: the BTC amount the user receives (reduced by fees)

The correct variable to use is `transfer_amount`, which represents the full value at risk and is the symmetric counterpart to `deposit_amount` used in the deposit path.

### Impact Explanation

The `confirmations_strategy` config maps satoshi thresholds to required confirmation counts. If a user withdraws an amount that crosses a threshold (e.g., requiring 6 confirmations), but `actual_received_amount` (after fees) falls below that threshold (requiring only 3 confirmations), the bridge will request verification with only 3 confirmations from the light client. This is a bypass of the bridge's confirmation policy for the actual economic value being processed.

With fewer confirmations than required, the verified BTC transaction is more susceptible to a Bitcoin chain reorganization. If a reorg occurs after `verify_withdraw_burn_callback` burns the nBTC from the bridge's balance, the user loses their nBTC without receiving BTC — a permanent loss of user funds. The bridge's nBTC supply becomes unbacked.

This matches the **Medium** impact category: bypass of bridge limits or policies.

### Likelihood Explanation

Any unprivileged relayer can call `verify_withdraw` (the public entry point that calls `internal_verify_withdraw_entry` → `internal_verify_withdraw`). The wrong variable is used unconditionally on every withdrawal. The fee amounts (`withdraw_fee + gas_fee`) are non-trivial (the bridge enforces `min_btc_gas_fee` and a percentage-based `withdraw_fee`), so for withdrawals near a confirmation threshold, the reduced amount will frequently resolve to a lower confirmation tier. Bitcoin chain reorganizations are rare but not impossible, especially at low confirmation depths.

### Recommendation

Replace `actual_received_amount` with `transfer_amount` in the confirmation lookup for withdrawals, consistent with how `deposit_amount` is used in the deposit path:

```rust
// contracts/satoshi-bridge/src/btc_light_client/withdraw.rs, line 20
let confirmations = self.get_confirmations(config, btc_pending_info.transfer_amount);
```

### Proof of Concept

1. Assume `confirmations_strategy = {"5000000": 3, "10000000": 6}` (amounts in satoshis).
2. User calls `nbtc.ft_transfer_call(bridge, 10_000_001, WithdrawMsg{...})` — `transfer_amount = 10_000_001` satoshis, which would require **6 confirmations**.
3. Bridge deducts `withdraw_fee` (e.g., 500_000) and `gas_fee` (e.g., 25_000): `actual_received_amount = 9_475_001`.
4. In `internal_verify_withdraw`, `get_confirmations(config, 9_475_001)` resolves to **3 confirmations** (below the 10_000_000 threshold).
5. The light client is asked to verify with only 3 confirmations instead of 6.

    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
