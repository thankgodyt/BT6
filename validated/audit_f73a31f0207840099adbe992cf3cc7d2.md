### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Bypasses Peras Weight in Chain Comparison, Enabling Incorrect Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when calling `preferAnchoredCandidate`, stripping all Peras certificate weight boosts from the chain comparison. This is the direct structural analog of the Pendle `minLpOut = 0` / `minTokenOut = 0` pattern: a bound that should reflect real accumulated value is instead fixed at the zero/empty sentinel, making the comparison blind to the dimension that matters most when Peras is active. An unprivileged peer can exploit this to either (a) keep a node connected to a non-canonical, lighter-by-Peras-weight chain, or (b) cause a node to disconnect from the canonical chain it should be following.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever the ledger cannot yet forecast a view for the peer's next header (i.e., the header is beyond the forecast horizon). Its job is to decide whether to keep waiting for the local chain to advance (stay connected) or to disconnect with `CandidateTooSparse`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero-weight snapshot
        ourFrag
        theirFrag =
      pure ()          -- stay connected
  | otherwise =
      throwSTM $ CandidateTooSparse ...   -- disconnect
```

`preferAnchoredCandidate` branches on whether the weight snapshot is empty:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- falls back to pure BlockNo comparison
      ...
  | otherwise =
      -- uses wsvTotalWeight = BlockNo + PerasWeightBoost
      ...
```

Because `emptyPerasWeightSnapshot` is always passed, `isEmptyPerasWeightSnapshot weights` is always `True`, and the comparison always reduces to a raw block-count (`BlockNo`) comparison, completely ignoring any Peras certificate weight boosts accumulated on either fragment.

The `PerasWeightSnapshot` is a live, non-trivial data structure maintained by the ChainDB (`getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))` is already wired into `ChainDbView`). When Peras certificates are being issued, blocks on the canonical chain accumulate weight boosts that make the canonical chain heavier than a same-length adversarial chain. The hardcoded empty snapshot discards this information entirely.

---

### Impact Explanation

**Impact class: High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

Two exploitable directions arise:

**Direction A — Adversary keeps node connected to a lighter chain:**
1. The adversary serves a chain with more blocks (higher `BlockNo`) but zero Peras weight boosts.
2. The canonical chain has fewer blocks but significant Peras weight boosts, making it heavier overall.
3. A header from the adversary's chain is beyond the forecast horizon; `checkPreferTheirsOverOurs` is called.
4. With `emptyPerasWeightSnapshot`, the comparison sees only block count: adversary's chain wins (`ShouldSwitch`).
5. The node stays connected, keeps downloading, and eventually selects the adversary's lighter chain.

**Direction B — Adversary causes node to disconnect from the canonical chain:**
1. The adversary is not involved; an honest peer serves the canonical chain, which has fewer blocks but more Peras weight.
2. A header from the canonical chain is beyond the forecast horizon.
3. With `emptyPerasWeightSnapshot`, the comparison sees only block count: canonical chain loses (`ShouldNotSwitch`).
4. The node throws `CandidateTooSparse` and disconnects from the honest peer serving the canonical chain.

Both directions result in the node diverging from the canonical chain, violating the chain selection invariant that Peras weight boosts are designed to enforce.

---

### Likelihood Explanation

**Likelihood: Medium.**

- Requires Peras to be active and certificates to be issued (weight boosts must be non-zero on the canonical chain). Peras infrastructure is already present in the codebase and being actively developed.
- The trigger condition — a header beyond the forecast horizon — is a normal operational event, not an exotic edge case. It occurs whenever a peer's chain advances faster than the local node's forecast window.
- No special privileges are required. Any peer connected via the ChainSync miniprotocol can present a chain with a higher block count, triggering the vulnerable comparison.
- The TODO comment (`TODO: remove this entire check`) confirms the developers are aware the function is incorrect under Peras but have not yet removed or fixed it.

---

### Recommendation

The immediate fix is to pass the actual live `PerasWeightSnapshot` from the ChainDB into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`, consistent with how the real chain selection in `ChainSel.hs` uses the live `weights` from `ChainSelEnv`. The referenced issue (`https://github.com/tweag/cardano-peras/issues/64`) proposes removing the entire check; until that is done, the snapshot must not be hardcoded to empty when Peras is active.
