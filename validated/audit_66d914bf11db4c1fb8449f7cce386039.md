### Title
Missing Ownership Validation of `original_btc_pending_verify_id` in `withdraw_rbf` Allows Any User to Trigger RBF with Attacker-Controlled Outputs on Another User's Pending Withdrawal - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `withdraw_rbf` function validates the **caller's** pending-sign capacity but never checks that the supplied `original_btc_pending_verify_id` belongs to the caller. Any bridge user can pass another user's pending withdrawal ID together with attacker-controlled `output` values, potentially replacing the victim's in-flight BTC transaction with one that redirects funds to the attacker.

### Finding Description
`withdraw_rbf` is a public, unpermissioned function. Its only guard is `require_pending_sign_capacity(&account_id)`, which checks the **caller's** own slot count — not the ownership of the referenced pending transaction:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,   // ← any pending ID accepted
    output: Vec<TxOut>,                        // ← fully attacker-controlled outputs
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();
    self.require_pending_sign_capacity(&account_id); // checks caller's own capacity only

    self.withdraw_rbf_chain_specific(
        account_id,                            // caller, not the victim
        original_btc_pending_verify_id,        // victim's tx ID — never validated
        output,
        chain_specific_data,
    );
}
``` [1](#0-0) 

The capacity check is performed against the **caller's** account, not the account that owns the referenced pending transaction. This is structurally identical to the H-03 pattern: one identifier (the caller's account) is validated, while the second identifier embedded in the call (`original_btc_pending_verify_id`) is forwarded without any ownership assertion.

`BTCPendingInfo` stores the true owner in its `account_id` field:

```rust
pub struct BTCPendingInfo {
    pub account_id: AccountId,   // the real owner
    ...
}
``` [2](#0-1) 

No code path between `withdraw_rbf` and `withdraw_rbf_chain_specific` compares `env::predecessor_account_id()` against `btc_pending_info.account_id` for the referenced transaction.

### Impact Explanation
An attacker who supplies a victim's `original_btc_pending_verify_id` and crafts a malicious `output` vector can cause the bridge's MPC pipeline to sign and broadcast a replacement BTC transaction whose outputs redirect the victim's BTC to the attacker's address. Because RBF replaces the original transaction in the mempool, the victim's original withdrawal is superseded. This constitutes direct theft of user funds via an unauthorized RBF substitution — matching the **Critical** impact tier: *Significant loss, theft, or destruction of user funds*.

### Likelihood Explanation
The function is public, requires no role, no special token, and no privileged access. Any NEAR account that has ever interacted with the bridge (or simply has a NEAR account) can call it. The only prerequisite is knowing a victim's `btc_pending_verify_id`, which is emitted as a public on-chain event (`GenerateBtcPendingInfo`) and is therefore trivially observable by any chain watcher. [3](#0-2) 

### Recommendation
Add an ownership check at the top of `withdraw_rbf` (or at the start of `withdraw_rbf_chain_specific`) that asserts the referenced pending transaction belongs to the caller:

```rust
let pending_info = self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
require!(
    pending_info.account_id == env::predecessor_account_id(),
    "Caller does not own this pending withdrawal"
);
```

This mirrors the mitigation applied in the H-03 fix: ensure the identifier supplied in the call matches the caller's identity before any state mutation proceeds.

### Proof of Concept
1. Alice calls `ft_transfer_call` → bridge creates `BTCPendingInfo` with `account_id = alice`, emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Bob observes the event and learns `btc_pending_id = "abc123"`.
3. Bob calls:
   ```
   withdraw_rbf(
       original_btc_pending_verify_id: "abc123",   // Alice's tx
       output: [TxOut { value: alice_amount, script_pubkey: bob_address }],
       chain_specific_data: None,
   )
   ```
4. `require_pending_sign_capacity(&bob)` passes (Bob has capacity).
5. `withdraw_rbf_chain_specific(bob, "abc123", [bob_output], …)` is called — no ownership check blocks it.
6. A new RBF transaction is constructed spending Alice's UTXOs with Bob's output address, associated with Bob's account.
7. The MPC signs and broadcasts the RBF transaction; Alice's original transaction is replaced.
8. Alice's BTC arrives at Bob's address.
