Audit Report

## Title
`nativeFee` ETH Permanently Locked With No Distribution or Withdrawal Path — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

Every call to `initTransfer` or `initTransfer1155` that includes a non-zero `nativeFee` causes the corresponding ETH to accumulate inside `OmniBridge.sol` with no mechanism to distribute it to relayers or return it to users. The `nativeFee` is subtracted from `msg.value` before the remainder (`extensionValue`) is forwarded to Wormhole, but the retained ETH has no exit path: no `receive()`, no `fallback()`, and no ETH-withdrawal or relayer-payout function exists anywhere in the contract.

## Finding Description

In `initTransfer`, `msg.value` is split as follows:

- For ERC-20 tokens: `extensionValue = msg.value - nativeFee` — only `extensionValue` is passed to `initTransferExtension`.
- For native ETH token: `extensionValue = msg.value - amount - nativeFee`. [1](#0-0) 

The `nativeFee` portion is never forwarded anywhere. `initTransferExtension` in `OmniBridgeWormhole` only spends `value` (the Wormhole fee) via `_wormhole.publishMessage{value: value}(...)`. [2](#0-1) 

The `nativeFee` amount is encoded into the Wormhole payload and relayed to NEAR, but no corresponding EVM-side mechanism exists to pay it out. The base `initTransferExtension` in `OmniBridge` reverts if `value != 0`, confirming that only `extensionValue` is consumed. [3](#0-2) 

`initTransfer1155` has the identical pattern. [4](#0-3) 

`finTransfer` on EVM handles token delivery to recipients but contains no logic to pay accumulated `nativeFee` ETH to the relayer who submitted the proof. [5](#0-4) 

No `receive()`, `fallback()`, or ETH-sweep function is declared anywhere in `OmniBridge.sol` or `OmniBridgeWormhole.sol`.

## Impact Explanation

This is a concrete instance of **fee mis-accounting**: ETH paid by users as `nativeFee` is collected by the contract but never distributed to relayers or returned to users. Every EVM→NEAR transfer where `nativeFee > 0` results in permanent loss of that ETH. The relayer receives no on-chain ETH compensation despite the user paying for it. The funds are irrecoverable without an admin contract upgrade (the contract is UUPS-upgradeable, but recovery requires privileged action). This matches the allowed critical impact: *"fee mis-accounting … that changes user or protocol balances"* and *"permanent freezing of bridged funds."*

## Likelihood Explanation

High. `nativeFee` is a first-class, documented parameter of the public `initTransfer` API. Any unprivileged user following the documented bridge flow and supplying `nativeFee > 0` with sufficient `msg.value` triggers the loss unconditionally. It affects every EVM deployment (`OmniBridgeWormhole` on Ethereum, Arbitrum, Base, BNB, Polygon). No special attacker capability is required — the user is the victim of their own legitimate usage.

## Recommendation

Forward `nativeFee` ETH to a designated fee recipient (e.g., a relayer treasury address stored in the contract) at `initTransfer` time, or accumulate it keyed by nonce and allow the relayer to claim it after submitting the Wormhole VAA. At minimum, add an admin ETH-sweep function so that already-locked funds can be recovered. The fix should mirror the NEAR-side `send_fee_internal` pattern: resolve the fee on the same chain where it is collected.

## Proof of Concept

1. Deploy `OmniBridgeWormhole` on a local fork (or testnet). Set Wormhole `messageFee()` to 0 for simplicity.
2. Call `initTransfer(tokenAddress, amount, fee=0, nativeFee=1 ether, recipient, "")` with `msg.value = 1 ether` (ERC-20 path) or `msg.value = amount + 1 ether` (native ETH path).
3. Observe: `extensionValue = 0`; `_wormhole.publishMessage{value: 0}` succeeds.
4. Check `address(omniBridge).balance`: it has increased by exactly `1 ether`.
5. Attempt any function call to withdraw or claim that ETH: none exists. The ETH is permanently locked.
6. Repeat for `initTransfer1155` — identical outcome.
