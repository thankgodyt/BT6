### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Weight Injection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a TODO stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. An unprivileged peer connected via the ObjectDiffusion mini-protocol can send a crafted `PerasCert` pointing to any block hash; the cert passes "validation," is inserted into the `PerasCertDB`, and triggers chain selection with an attacker-controlled Peras weight boost. This directly parallels the external report's `globalModification: true` bypass: a special-case code path skips all real validation and lets peer-supplied data overwrite critical consensus state — here, the chain-selection weight of arbitrary blocks.

---

### Finding Description

**Root cause — `validatePerasCert` stub, lines 350–358:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is the **catch-all instance** for every `StandardHash blk` type, including `CardanoBlock`: [2](#0-1) 

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory certificate-validation gate: [3](#0-2) 

**Inbound certificate processing — `processCerts`, lines 156–185:**

When the ObjectDiffusion layer receives certificates from a peer, it calls `processCerts` with `validatePerasCert mkPerasParams` as the sole validation function: [4](#0-3) 

`processCerts` partitions results into valid/invalid; because the stub always returns `Right`, every cert is "valid": [5](#0-4) 

**Chain-selection trigger — `chainSelSync`, lines 483–532:**

After insertion into `PerasCertDB`, `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event. `chainSelSync` then calls `chainSelectionForBlock` for the attacker-nominated boosted block: [6](#0-5) 

**Weight applied to chain comparison:**

The injected `ValidatedPerasCert` contributes `vpcCertBoost` (set to `perasWeight params` — the full configured boost) to `weightBoostOfFragment`, which is added to the chain length in `totalWeightOfFragment` during chain selection: [7](#0-6) 

**End-to-end exploit path:**

1. Attacker peer connects to the network (no restrictions on who can connect).
2. Peer sends a crafted `PerasCert{pcCertRound = r, pcCertBoostedBlock = adversarialBlockPoint}` via the ObjectDiffusion mini-protocol.
3. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. The cert is timestamped and inserted into `PerasCertDB` via `addPerasCertAsync`.
5. `chainSelSync` triggers `chainSelectionForBlock` for `adversarialBlockPoint`.
6. The adversarial block's fragment now carries the full Peras weight boost, making it preferred over the honest chain in `totalWeightOfFragment` comparisons.
7. The node switches to the adversarial chain.

---

### Impact Explanation

**Severity: Critical.** This is a direct bypass of Peras certificate/vote checks — exactly the impact class "Bypass of … certificate/signature validation … that enables unauthorized … certificate acceptance." An unprivileged peer can cause an honest node to prefer a non-canonical, adversary-controlled chain by injecting a crafted certificate that grants an arbitrary Peras weight boost to any block in the VolatileDB. Because Peras weight is additive to chain length, a sufficiently large boost can override the honest chain's length advantage, causing a chain-selection flip. The `PerasCertDB` comment confirms the cert is accepted as authoritative: "certificate equivocation is impossible" — but that invariant is only sound if `validatePerasCert` actually verifies the certificate. [8](#0-7) 

---

### Likelihood Explanation

Any peer reachable via the ObjectDiffusion mini-protocol can trigger this. No stake, no keys, no prior knowledge of the network state is required — only the ability to send a well-formed CBOR-encoded `PerasCert` message. The attack is deterministic and requires a single message. The only precondition is that Peras is enabled on the target node; the CHANGELOG notes it is disabled by default, but the stub is present and wired into the live inbound path for any deployment that enables Peras. [9](#0-8) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS/committee signature over `(pcCertRound, pcCertBoostedBlock)` against the current epoch's committee public keys.
2. Checks that `pcCertRound` falls within the valid range (not too old, not in the future).
3. Confirms `pcCertBoostedBlock` refers to a block that actually exists and is within the volatile window.
4. Rejects any cert whose `vpcCertBoost` would exceed the protocol-configured maximum.

Until a real implementation is available, the inbound `processCerts` path should refuse all externally received certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all.

craftedCert :: PerasCert CardanoBlock
craftedCert = PerasCert
  { pcCertRound        = PerasRoundNo 42          -- any active round

-- processCerts calls (validatePerasCert mkPerasParams craftedCert)

-- => addPerasCertAsync inserts it into PerasCertDB

-- => totalWeightOfFragment(adversarialFrag) = length + fullBoost > length(honestFrag)

The `validatePerasCert` stub at lines 353–358 is the necessary and sufficient vulnerable step; no other code in the inbound path performs certificate signature verification. [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
