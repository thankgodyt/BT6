### Title
Peras Certificate Validation Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The only concrete `BlockSupportsPeras` instance in the production codebase implements `validatePerasCert` as an unconditional `Right`, meaning every certificate received from any peer passes validation without any cryptographic or structural check. Because validated certificates are enqueued into the ChainDB and their `vpcCertBoost` field directly influences chain selection weight, an unprivileged peer can inject crafted certificates that boost an attacker-chosen block, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validation that always succeeds**

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate for accepting inbound Peras certificates. The only instance present in the production source tree is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature is verified, no committee membership is checked, no round-number or target-block plausibility is tested. Every certificate, regardless of content or origin, is wrapped in `Right ValidatedPerasCert` and returned as valid.

**Inbound path — peer-supplied certificates reach `validatePerasCert` directly**

`processCerts` is the inbound handler for batches of certificates received from a remote peer. It filters out already-known rounds, then calls the supplied `validateCert` callback on every remaining certificate:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` is bound to `validatePerasCert mkPerasParams` (the degenerate instance), the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addCert`.

**State mutation — accepted certificate is enqueued for chain selection**

`addCert` resolves to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message carrying the `ValidatedPerasCert` (including its `vpcCertBoost`) into the `cdbChainSelQueue`:

```haskell
addPerasCertAsync CDB{cdbTracer, cdbChainSelQueue} =
  addPerasCertToQueue (TraceAddPerasCertEvent >$< cdbTracer) cdbChainSelQueue
``` [3](#0-2) 

The background chain-selection thread dequeues this message and uses `vpcCertBoost` to increase the Peras weight of the certified block's chain, directly influencing which chain is selected as canonical.

**Network entry point — any peer can send certificates**

The `hPerasCertDiffusionClient` handler is registered as a standard node-to-node mini-protocol handler, reachable by any connecting peer without authentication:

```haskell
hPerasCertDiffusionClient ::
  NodeToNodeVersion ->
  ControlMessageSTM m ->
  ConnectionId addr ->
  PerasCertDiffusionInboundPipelined blk m ()
``` [4](#0-3)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block as `pcCertBoostedBlock`. Because `validatePerasCert` unconditionally accepts it, the certificate is stored and its boost weight is applied during chain selection. The attacker can therefore cause an honest node to prefer a non-canonical or adversarially-chosen chain over the honest chain, constituting a **chain selection integrity failure**. This maps directly to the allowed High impact category: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The attack requires only a standard peer connection — no keys, no stake, no privileged access. The degenerate instance is the only `BlockSupportsPeras` instance in the production source tree (the Cardano-specific override is explicitly deferred via the linked GitHub issue). Any peer that can establish a node-to-node connection and speak the Peras certificate diffusion mini-protocol can exploit this immediately.

---

### Recommendation

1. **Do not deploy the Peras certificate diffusion mini-protocol** until `validatePerasCert` is replaced with a real implementation that verifies committee membership, aggregate BLS signature, round number, and target-block plausibility — analogous to the `implVerifyCert` logic already present in `WFALS.hs` and `EveryoneVotes.hs`.
2. Until a concrete Cardano-block instance overrides the degenerate catch-all, gate the `hPerasCertDiffusionClient` handler behind a feature flag that is disabled by default.
3. Apply the same scrutiny to `validatePerasVote`, which checks stake-distribution membership but does not verify the vote signature, allowing any peer to forge votes for any registered voter ID.

---

### Proof of Concept

1. Attacker connects to a target node as a standard peer.
2. Attacker constructs a `PerasCert` with `pcCertBoostedBlock` pointing to an attacker-chosen block (e.g., a minority fork tip) and `pcCertRound` set to any round not yet present in the node's `PerasCertDB`.
3. Attacker sends the certificate via the `PerasCertDiffusion` mini-protocol.
4. `processCerts` filters out already-known rounds (none match), then calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is enqueued via `addPerasCertAsync` into `cdbChainSelQueue` as `ChainSelAddPerasCert`.
6. The chain-selection background thread processes the message, applies `vpcCertBoost` to the attacker-chosen block's chain weight, and may switch the node's canonical chain to the attacker-chosen fork.
7. The node now tracks a non-canonical chain; honest peers on the canonical chain are effectively ignored for the boosted fork.
