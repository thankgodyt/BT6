### Title
`checkPreferTheirsOverOurs` Ignores Peras Weight Snapshot, Causing Incorrect Chain Selection Disconnection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a peer's candidate chain is preferable to the local selection. Because actual chain selection uses the real `PerasWeightSnapshot` (populated from validated Peras certificates), the two comparisons operate on different weight bases. An honest node can be made to disconnect from a peer offering the canonical, certificate-boosted chain while remaining connected to a peer offering a lighter, non-canonical chain.

---

### Finding Description

When a header arrives beyond the forecast horizon, `checkPreferTheirsOverOurs` is invoked to decide whether to stay connected to the upstream peer or throw `CandidateTooSparse` and disconnect:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot          -- ← always empty; ignores real Peras weights
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

The real chain selection path — `chainSelectionForBlock`, `constructPreferableCandidates`, and `chainSelection` — all receive the live `PerasWeightSnapshot` read from `cdbPerasCertDB` via `getPerasWeightSnapshot`:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [2](#0-1) 

`preferAnchoredCandidate` branches on whether the snapshot is empty. With a non-empty snapshot it computes `weightedSelectView` over the suffix after the intersection, summing `wsvBlockNo` and `wsvWeightBoost` (certificate boosts) into `wsvTotalWeight`:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count-only comparison
  | otherwise =
      case AF.intersect ours cand of
        ...
          case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                                   (weightedSelectView cfg weights candSuffix) of ...
``` [3](#0-2) 

`wsvTotalWeight` is the decisive quantity:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

Because `checkPreferTheirsOverOurs` always passes `emptyPerasWeightSnapshot`, it falls into the block-count-only branch regardless of how many certificate boosts the local chain has accumulated. The disconnection decision and the actual chain-selection decision therefore use incompatible comparison functions.

---

### Impact Explanation

**Scenario A — node incorrectly disconnects from the canonical chain (High impact):**

1. The local node's current chain has accumulated Peras certificate boosts (e.g., `wsvWeightBoost = B`), making it heavier than a longer but unboosted fork.
2. An honest upstream peer offers a chain that is heavier still (more boosts), but has fewer raw blocks than the local chain.
3. `checkPreferTheirsOverOurs` compares by block count only (empty snapshot): the peer's chain has fewer blocks → `ShouldNotSwitch` → the node throws `CandidateTooSparse` and **disconnects from the honest peer**.
4. Actual chain selection, had it been reached, would have found the peer's chain heavier and switched.
5. The node remains on a lighter, non-canonical chain and loses its only path to the canonical tip.

This matches: **High — chain selection bug that lets an unprivileged peer (or the absence of proper weight consideration) make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

**Scenario B — node stays connected to a peer offering a chain it will never adopt:**

1. The local chain has Peras boosts; a peer offers a longer but unboosted chain.
2. `checkPreferTheirsOverOurs` (empty snapshot) sees the peer's chain as longer → `ShouldSwitch` → stays connected.
3. Actual chain selection (real snapshot) finds the local chain heavier → never switches.
4. The node blocks indefinitely in `readLedgerState` retrying for a ledger view it will never use, while the peer can keep extending the unboosted fork. [5](#0-4) 

---

### Likelihood Explanation

The condition is reachable by any unprivileged peer once Peras is active on the network and at least one certificate has been issued (boosting the local chain). No key compromise, stake majority, or operator action is required. The peer only needs to offer a valid chain with a different block count than the local selection. The code path (`checkTime` → `readLedgerState` → `checkPreferTheirsOverOurs`) is exercised whenever a header arrives beyond the current forecast horizon, which is a normal occurrence during syncing or after a slot gap. The developers have already flagged this with a `TODO` comment referencing issue #64, confirming awareness of the inconsistency. [6](#0-5) 

---

### Recommendation

Pass the live `PerasWeightSnapshot` into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`. The snapshot is already available in the `ChainDbView` (via `getPerasWeightSnapshot`) and is read atomically alongside `getCurrentChain` in every other chain-selection call site. The fix should be applied atomically with the intersection check so that the weight snapshot and the chain fragment are consistent:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot  -- read real snapshot
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This aligns the disconnection predicate with the actual chain-selection predicate, eliminating the weight-basis mismatch.

---

### Proof of Concept

**Setup:** Peras is active; the local node has adopted chain `C_local` with 10 blocks and 2 certificate boosts (`wsvTotalWeight = 12`). An honest peer `P` offers chain `C_peer` with 8 blocks and 5 certificate boosts (`wsvTotalWeight = 13`). `C_peer` is heavier and is the canonical chain.

**Trigger:** `P` sends a header for slot `s` that is beyond the current forecast horizon. `checkTime` calls `readLedgerState`, which calls `checkPreferTheirsOverOurs`.

**Comparison with `emptyPerasWeightSnapshot`:**
- `ourFrag` tip: `BlockNo 10`; `theirFrag` tip: `BlockNo 8`
- `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` → block-count comparison → `10 > 8` → `ShouldNotSwitch`
- `checkPreferTheirsOverOurs` throws `CandidateTooSparse` → **node disconnects from `P`**

**What should happen with the real snapshot:**
- `weightedSelectView ... oursSuffix` → `wsvTotalWeight = 12`
- `weightedSelectView ... candSuffix` → `wsvTotalWeight = 13`
- `preferCandidate` → `12 < 13` → `ShouldSwitch` → node stays connected and eventually adopts `C_peer`

The mismatch causes the node to discard the canonical chain's only upstream source. [7](#0-6) [8](#0-7)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
