### Title
Inconsistent Peras Weight Snapshot in `checkPreferTheirsOverOurs` Causes Incorrect Peer Disconnection and Chain-Selection Failure - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a candidate chain is preferred over the local selection. Every other chain-selection code path — ChainDB's `constructPreferableCandidates`, `chainSelection`, `plausibleCandidateChain` in BlockFetch, and the GSM — reads the real `PerasWeightSnapshot` from the ChainDB. When Peras is active and a candidate chain is shorter in block count but heavier in total Peras weight (due to a boosted block), this inconsistency causes the node to incorrectly disconnect from the peer offering the heavier, canonical chain, preventing adoption of the correct chain.

This is the direct analog of the `getBidValue()` inconsistency: one code path uses the proper weighted comparison function while another uses the raw/empty value directly.

---

### Finding Description

The vulnerability class from the external report is **inconsistent use of a value-extraction function**: `getBidValue()` is used in `Sorter` for sorting but `solverOp.bidAmount` is used directly in `Atlas` and `Escrow`, causing divergent behavior when the two differ.

In Ouroboros Consensus, the analog is the inconsistent use of `PerasWeightSnapshot` across chain-comparison call sites.

**The correct path — ChainDB chain selection** reads the real snapshot and passes it to `preferAnchoredCandidate`:

**The broken path — `checkPreferTheirsOverOurs`** hardcodes `emptyPerasWeightSnapshot`:

```haskell

  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always ignores Peras weight boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [3](#0-2) 

`checkPreferTheirsOverOurs` is called from `readLedgerStateHelper` when a header arrives beyond the forecast horizon and the ledger view is not yet available: [4](#0-3) 

The `preferAnchoredCandidate` function, when given `emptyPerasWeightSnapshot`, takes the non-Peras branch and compares only by block number (`selectView`), completely ignoring `wsvWeightBoost`: [5](#0-4) 

Under Peras, `wsvTotalWeight = blockNo + weightBoost`, so a chain with fewer blocks but a large boost can be heavier than the current chain: [6](#0-5) 

---

### Impact Explanation

When Peras is active and a Peras certificate boosts a block on a fork that is shorter in block count than the local chain:

1. ChainDB correctly considers the fork heavier (preferred) and would adopt it.
2. But if a header on that fork arrives beyond the forecast horizon, `checkPreferTheirsOverOurs` evaluates the fork using `emptyPerasWeightSnapshot`, sees it is shorter in block count, concludes `ShouldNotSwitch`, and throws `CandidateTooSparse` — disconnecting the peer.
3. The node never downloads the blocks for the heavier chain and permanently stays on the lighter, non-canonical chain.

This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical (less-weight) chain over the correct Peras-weighted chain, violating the Peras chain-selection invariant.

---

### Likelihood Explanation

Likelihood is **Medium**. The condition requires:
- Peras to be active (currently in development, not yet on mainnet, but the code is production-ready).
- A Peras certificate to boost a block on a fork that is shorter in block count than the local chain.
- A header on that fork to arrive beyond the forecast horizon (a normal occurrence during syncing or when a peer is slightly ahead).

All three conditions are realistic in a live Peras-enabled network. No attacker privileges are required — any peer serving a valid Peras-boosted chain can trigger this.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the real `PerasWeightSnapshot` read from the ChainDB, consistent with all other chain-comparison call sites. The existing TODO comment (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) acknowledges the problem; the fix should either remove the check entirely (as the TODO suggests) or supply the real weights. [7](#0-6)

### Proof of Concept

Consider Peras active with security parameter `k = 10` and a weight boost of `B = 15` per certificate.

**Setup:**
- Our chain: `Genesis → A₁ → A₂ → … → A₁₁` (block number 11, total weight 11)
- Candidate fork: `Genesis → A₁ → … → A₅ → F₆` (block number 6, but F₆ has Peras boost 15, total weight = 6 + 15 = 21)

**ChainDB evaluation** (correct): `preferAnchoredCandidate cfg realWeights ours cand` → `ShouldSwitch` (21 > 11). The fork is heavier and would be adopted.

**`checkPreferTheirsOverOurs` evaluation** (broken): `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ours cand` → compares block numbers only: 6 < 11 → `ShouldNotSwitch GT` → throws `CandidateTooSparse`, disconnects the peer.

The node stays on the lighter chain (weight 11) and never adopts the canonical heavier chain (weight 21), violating Peras chain-selection safety. [3](#0-2) [8](#0-7)
