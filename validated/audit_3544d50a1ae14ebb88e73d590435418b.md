### Title
`safe_mint` Inflates nBTC Total Supply Before Checking Account Registration, Returning `U128(0)` on Unregistered Recipient — (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function unconditionally mints nBTC tokens to the bridge account before verifying that the recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` — signaling to the bridge that zero tokens were minted — while the tokens remain minted in the bridge account and the total supply is permanently inflated without BTC backing.

### Finding Description
In `safe_mint` (nbtc/src/lib.rs), the execution order is:

1. **Line 112**: `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC to `bridge_id`, increasing total supply.
2. **Lines 114–116**: Only *after* minting does the function check whether the recipient account is registered. If not, it returns `PromiseOrValue::Value(U128(0))`. [1](#0-0) 

The return value `U128(0)` is semantically ambiguous: it signals to the bridge callback that zero tokens were minted (i.e., minting failed), but the nBTC total supply has already been increased by `amount` and those tokens sit in `bridge_id`. This is the direct analog to the ERC20 `approve` issue: a function performs a state-changing operation and then returns an unexpected/misleading value, causing the caller to enter an inconsistent state.

The bridge's documented safe-deposit semantics state: *"reverts the whole transaction if minting fails (no lost & found)"*. [2](#0-1) 

When the bridge callback receives `U128(0)`, it interprets this as a mint failure and may attempt to revert the deposit (e.g., refund the user's BTC). However, the nBTC total supply has already been inflated by `amount` with no corresponding BTC backing — the tokens are stranded in `bridge_id` with no automatic recovery path.

### Impact Explanation
**Medium.** This is a broken callback rollback / stuck bridge state scenario. The nBTC total supply is inflated without BTC backing whenever a safe deposit targets an unregistered account. The stranded tokens in `bridge_id` require privileged operator intervention to burn back. If the bridge callback simultaneously attempts a BTC refund (treating `U128(0)` as failure), the protocol ends up with unbacked nBTC supply — a supply/accounting failure. [3](#0-2) 

### Likelihood Explanation
**Medium.** The `safe_mint` path is exercised by any safe deposit (e.g., Omni Bridge integration) via `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`. [4](#0-3) 

The existence of the `is_none()` guard inside `safe_mint` itself demonstrates that the developers anticipated this case occurring in production. Any user whose nBTC account is not registered at the moment `safe_mint` executes — due to a race condition, a storage-registration failure, or incorrect bridge-side pre-registration — triggers the bug. No privileged access is required; the attacker-controlled entry point is the public `verify_deposit_v2` call.

### Recommendation
Move the account-registration check **before** `internal_deposit`, so no tokens are minted if the recipient is unregistered:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

Alternatively, if minting-first is required, add an explicit `internal_withdraw` burn-back on the `U128(0)` return path to restore the total supply.

### Proof of Concept

1. User calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)` and a valid BTC Merkle proof.
2. User's nBTC account is **not** registered on the nBTC contract (no `storage_deposit` was made).
3. Bridge's deposit callback calls `safe_mint(user_account, amount, None)` on the nBTC contract.
4. `safe_mint` executes `internal_deposit(&bridge_id, amount)` → nBTC total supply increases by `amount`; tokens sit in `bridge_id`.
5. `safe_mint` checks `self.token.accounts.get(&account_id).is_none()` → `true` → returns `PromiseOrValue::Value(U128(0))`.
6. Bridge callback receives `U128(0)`, interprets it as mint failure, and may initiate a BTC refund to the user.
7. **Result**: User recovers their BTC; `amount` nBTC remain minted in `bridge_id` with no BTC backing — total supply is permanently inflated until an operator manually burns the stranded tokens. [1](#0-0)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"

        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
