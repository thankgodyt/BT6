Looking at the `validatePerasCert` and `validatePerasVote` implementations in `BlockSupportsPeras.hs`, and tracing the inbound network path through `ObjectDiffusion/PerasCert.hs` and `PerasVote.hs` into the ChainDB.

### Title
Peras Certificate Verification Unconditionally Bypassed — Any Peer Can Inject a Fake Certificate to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance for all block types implements `validatePerasCert` as an unconditional `Right` — it performs zero cryptographic or structural validation. Any unprivileged peer can send a crafted `PerasCert` over the ObjectDiffusion mini-protocol; the node will accept it as a `ValidatedPerasCert`, add it to the ChainDB, and trigger chain selection with the attacker-chosen weight boost, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a received certificate before it is stored and used in chain selection. The universal production instance (the only instance in the codebase) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function never inspects the certificate body. It does not verify:
- The aggregate BLS signature over the election result
- Committee membership of the signers
- VRF eligibility proofs for non-persistent voters
- Round number plausibility or slot range

The same pattern applies to `validatePerasVote`, which only checks stake-distribution membership but skips all cryptographic signature verification:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

**Inbound network path (certs):**

1. A remote peer sends a `PerasCert` message via the ObjectDiffusion mini-protocol (`ObjectDiffusion/PerasCert.hs`).
2. The inbound handler calls `validatePerasCert`, which unconditionally returns `Right (ValidatedPerasCert cert boost)`.
3. The `ValidatedPerasCert` is passed to `addPerasCertAsync` on the `ChainDB`. [3](#0-2) 

4. `addPerasCertAsync` enqueues the cert into `cdbChainSelQueue`, which is processed by `chainSelSync`. [4](#0-3) 

5. Chain selection reads the `PerasWeightSnapshot` and applies the boost from the fake certificate, potentially switching to the attacker-chosen fork. [5](#0-4) 

**Inbound network path (votes):**

The `processVotes` function in `ObjectPool/PerasVote.hs` calls `validatePerasVote` before adding votes. Because `validatePerasVote` skips signature verification, any peer can forge votes attributed to any registered stake pool (whose pool ID appears in the stake distribution) without possessing that pool's private key. [6](#0-5) 

Once enough forged votes accumulate to reach quorum, `implAddVote` automatically forges a certificate and enqueues it for chain selection — again with no cryptographic check. [7](#0-6)

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

A crafted `PerasCert` with an attacker-chosen `pcCertBoostedBlock` and `pcCertRound` will be accepted as valid and stored in the ChainDB. The Peras weight boost (`vpcCertBoost = perasWeight params`) is then applied to the attacker-chosen block during chain selection. If the boosted block is on a minority or adversarial fork, the honest node may switch away from the canonical chain. Because the certificate is persisted and propagated, the effect can spread to other nodes that receive the same fake certificate.

---

### Likelihood Explanation

**High.** The attack requires only:
- Network connectivity to a Cardano node running the Peras ObjectDiffusion mini-protocol.
- Knowledge of any block hash present in the node's VolatileDB (obtainable via ChainSync).
- No private keys, no stake, no privileged access.

The `validatePerasCert` bypass is unconditional — there is no code path that performs real verification. The TODO comment and linked issue confirm this is a known incomplete state, not a deliberate design choice.

---

### Recommendation

Implement real cryptographic validation inside `validatePerasCert` and `validatePerasVote` before the Peras ObjectDiffusion mini-protocol is enabled on any network:

1. **`validatePerasCert`**: Verify the aggregate BLS signature against the claimed committee members, check committee membership and VRF eligibility proofs, and validate the round number against the current epoch state.
2. **`validatePerasVote`**: In addition to the stake-distribution lookup, verify the vote's cryptographic signature using the pool's registered vote verification key.
3. **Defense-in-depth**: `implAddVote` should re-verify the `ValidatedPerasVote` invariant rather than trusting the caller, consistent with the existing TODO at line 172.

---

### Proof of Concept

1. Connect to a target node's ObjectDiffusion endpoint.
2. Obtain a block hash `H` from the node's volatile chain via ChainSync.
3. Construct a `PerasCert { pcCertRound = R, pcCertBoostedBlock = H }` for any round `R` and any block hash `H` on a minority fork.
4. Send the cert via the ObjectDiffusion cert diffusion protocol.
5. The node calls `validatePerasCert`, which returns `Right (ValidatedPerasCert cert boost)` unconditionally.
6. The cert is enqueued via `addPerasCertAsync` and processed by `chainSelSync`.
7. Chain selection applies the Peras weight boost to block `H`; if the boosted weight exceeds the current preferred chain's weight, the node switches forks.
