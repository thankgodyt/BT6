### Title
Missing Cryptographic Vote Signature Verification in Peras Vote Ingestion Pipeline — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

---

### Summary

The Peras vote ingestion pipeline (`processVotes` → `validatePerasVote` → `implAddVote`) accepts inbound votes from any peer but only validates stake-based eligibility using the stake distribution. It does **not** verify the cryptographic signature of the vote. An unprivileged peer can therefore submit crafted votes attributed to any legitimate voter ID, accumulate enough forged stake weight to reach quorum, and cause the local node to forge a fraudulent Peras certificate that boosts an attacker-chosen block — corrupting local chain selection.

---

### Finding Description

In `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB`, the validation callback passed to `processVotes` is:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [1](#0-0) 

The only inputs to `validatePerasVote` are the Peras parameters and the `PerasVoteStakeDistr` (a stake distribution). There are no cryptographic verification keys, no committee selection context, and no VRF/BLS material. The function therefore cannot verify the vote's cryptographic signature.

Both call sites carry an explicit TODO acknowledging this incompleteness:

> "TODO: in the future we won't need just the stake distribution for validating votes, but also the whole committee selection context (containing vote weights of committee members = voters)" [2](#0-1) 

Inside the database itself, `implAddVote` carries a second TODO:

> "TODO: we will need to update this method with non-trivial validation logic — see https://github.com/tweag/cardano-peras/issues/120" [3](#0-2) 

`implAddVote` accepts a `ValidatedPerasVote` and immediately stores it, then calls `updatePerasRoundVoteStates` to accumulate stake weight. When accumulated weight crosses the quorum threshold, a `ValidatedPerasCert` is forged locally and stored: [4](#0-3) 

The `ValidatedPerasVote` wrapper therefore provides no cryptographic guarantee — it only records that the vote passed the incomplete stake-distribution check. The `CryptoSupportsVotingCommittee` class defines `verifyVote` (which checks the vote signature against the voter's public key) and `verifyCert` (which checks the aggregate BLS/KES signature), but neither is invoked anywhere in this pipeline. [5](#0-4) 

---

### Impact Explanation

An attacker who can observe the public stake distribution (which is public on-chain data) knows every eligible voter ID and their seat index. Because no signature is verified, the attacker can craft `PerasVote` messages with any legitimate `voterId` field and an arbitrary (invalid) signature body. `validatePerasVote` will accept these votes as long as the voter ID appears in the stake distribution. Once the attacker submits enough forged votes to exceed the quorum threshold, `implAddVote` triggers `updatePerasRoundVoteStates`, which calls `forgeCert` and stores a `ValidatedPerasCert` boosting an attacker-chosen block. This fraudulent certificate is then used by the local node's chain selection logic to prefer the boosted block over the canonical chain — a direct chain-selection safety failure.

This maps to the **High** impact category: *Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

It also partially maps to **Critical**: *Bypass of … certificate/vote verification … that enables unauthorized … vote, or certificate acceptance.*

---

### Likelihood Explanation

The attacker entry path is the ObjectDiffusion mini-protocol, which is a public peer-to-peer channel. Any node that connects to the victim and sends `PerasVote` objects exercises this code path directly via `opwAddObjects` → `processVotes`. No privileged access, no key material, and no stake ownership is required. The stake distribution is public. The attack requires only knowledge of voter IDs (seat indices) and the ability to send crafted network messages — both trivially achievable by any network peer.

---

### Recommendation

1. Pass the full `VotingCommittee crypto committee` context (not just the stake distribution) to `validatePerasVote`, so that `verifyVote` from `CryptoSupportsVotingCommittee` can be called to check the cryptographic signature of each inbound vote before it is stored.
2. Remove the TODO in `implAddVote` by implementing the "non-trivial validation logic" referenced in issue #120, ensuring that `implAddVote` rejects any `ValidatedPerasVote` whose signature has not been cryptographically verified.
3. Treat `ValidatedPerasVote` as a type that guarantees full cryptographic validation, not merely stake-eligibility.

---

### Proof of Concept

1. Observe the public stake distribution to enumerate all eligible voter IDs and their stake weights.
2. Craft `PerasVote` messages for a target round, each with a legitimate `voterId` (from the distribution) but an arbitrary/zeroed signature field.
3. Connect to the victim node via the ObjectDiffusion mini-protocol and submit the crafted votes via `opwAddObjects`.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote` — this passes because only the stake distribution is checked; no signature verification occurs. [6](#0-5) 
5. Each forged vote is wrapped in `ValidatedPerasVote` and passed to `implAddVote`, which stores it and accumulates stake weight. [7](#0-6) 
6. Once accumulated weight exceeds the quorum threshold, `updatePerasRoundVoteStates` returns `VoteGeneratedNewCert cert`, and `implAddVote` stores a `ValidatedPerasCert` boosting the attacker's chosen block. [8](#0-7) 
7. The local node's chain selection now treats the attacker's block as boosted, deviating from the canonical chain.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
