### Title
Unauthenticated Peras Vote Injection Enables Unauthorized Chain Boost via Missing Signature Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` function performs no cryptographic signature verification on inbound Peras votes. The `PerasVote blk` data type carries no signature field, and the validation only checks that the claimed voter ID (`pvVoteVoterId`) exists in the stake distribution. Any unprivileged peer can craft votes claiming to be from any registered stake pool, accumulate a forged quorum, and cause the receiving node to generate and accept a `ValidatedPerasCert` that boosts an attacker-chosen block — directly influencing chain selection.

---

### Finding Description

**Root cause — no signature field and no signature check in the production vote type:**

The production `PerasVote blk` data type is defined as:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- just a KeyHash, no signature
  }
``` [1](#0-0) 

There is no `pvSignature` field. The concrete BLS-signed vote type (`Ouroboros.Consensus.Peras.Vote.V1.PerasVote`) does carry a `pvSignature :: VoteSignature PerasBLSCrypto` field, but it is **not** the type used by the production `BlockSupportsPeras` instance. [2](#0-1) 

The production `validatePerasVote` implementation (the degenerate instance, explicitly marked with a TODO) only performs a stake-distribution lookup:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

`lookupPerasVoteStake` only checks `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)` — it verifies that the claimed voter ID is a registered pool, but never verifies that the sender controls that pool's key. [4](#0-3) 

**Attacker-controlled entry path — the ObjectDiffusion miniprotocol:**

Inbound votes arrive via `makePerasVotePoolWriterFromChainDB` (production path) or `makePerasVotePoolWriterFromVoteDB`. Both call `processVotes`, which calls `validatePerasVote` as the sole gate before adding votes to the database:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

`processVotes` adds all votes that pass `validatePerasVote` to the database: [6](#0-5) 

**Quorum → certificate → chain selection:**

Once enough fake votes accumulate in the `PerasVoteDB`, `updatePerasRoundVoteStates` detects a quorum and `implAddVote` forges a `ValidatedPerasCert`: [7](#0-6) 

The certificate is then passed to `addPerasCertAsync`, which enqueues it for chain selection processing: [8](#0-7) 

The certificate carries a `vpcCertBoost :: PerasWeight` that inflates the chain weight of the boosted block, potentially causing the node to switch to the attacker-chosen fork.

**Secondary: `validatePerasCert` is also a no-op:**

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [9](#0-8) 

Any directly submitted certificate is accepted unconditionally, compounding the attack surface.

---

### Impact Explanation

An unprivileged peer can:

1. Enumerate registered stake pool key hashes from the public ledger (they are public).
2. Craft `PerasVote blk` messages claiming to be from those pools, targeting any block point of the attacker's choice.
3. Submit enough fake votes to exceed the quorum threshold (`stakeAboveThreshold`).
4. Cause the victim node to generate a `ValidatedPerasCert` boosting the attacker-chosen block.
5. The boosted block gains a `PerasWeight` advantage in chain selection, potentially causing the node to switch to a non-canonical fork.

This is a **High** severity chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain by injecting forged Peras votes, bypassing the certificate/vote verification that is the core authorization mechanism of the Peras protocol.

---

### Likelihood Explanation

- **Preconditions**: The attacker only needs a network connection to the target node and knowledge of registered stake pool key hashes (both are publicly available on-chain).
- **No privileged access required**: No keys, no stake, no operator access needed.
- **Directly reachable**: The ObjectDiffusion miniprotocol is an externally reachable peer-to-peer protocol. Any peer can send `PerasVote` messages.
- **Deterministic**: The attack is fully deterministic — the attacker controls exactly which pool IDs and which block point to use.

---

### Recommendation

1. **Add a cryptographic signature to `PerasVote blk`**: The concrete `Peras.Vote.V1.PerasVote` type already has the correct structure with `pvSignature :: VoteSignature PerasBLSCrypto`. The production `BlockSupportsPeras` instance must be wired to use this type (or an equivalent) rather than the signatureless degenerate type.

2. **Implement `validatePerasVote` with actual signature verification**: The TODO at line 360 must be resolved. Validation must verify the BLS signature over `(pvVoteRound, pvVoteBlock)` using the public key associated with `pvVoteVoterId` in the stake distribution, and verify the VRF eligibility proof for non-persistent committee members.

3. **Implement `validatePerasCert` with actual aggregate signature verification**: The TODO at line 353 must also be resolved. Certificate validation must verify the aggregate BLS signature against the claimed voter set.

4. **Treat the degenerate instance as a compile-time error in production builds**: The degenerate `instance StandardHash blk => BlockSupportsPeras blk` should be gated behind a flag or replaced entirely before any production deployment.

---

### Proof of Concept

An attacker peer connects via the ObjectDiffusion miniprotocol and sends the following batch of votes (pseudocode):

```haskell
-- Attacker knows pool IDs from the public ledger
let victimPools = [pool1, pool2, pool3, ...]  -- enough to exceed quorum

-- Craft votes for an attacker-chosen block
let attackerBlock = someBlockPoint  -- any block the attacker wants to boost

let fakeVotes =
      [ PerasVote
          { pvVoteRound   = currentRound
          , pvVoteBlock   = attackerBlock
          , pvVoteVoterId = poolId
          }
      | poolId <- victimPools
      ]

-- Send fakeVotes via ObjectDiffusion to the target node
sendVotes targetNode fakeVotes
```

**Expected (correct) behavior**: `validatePerasVote` rejects each vote because the sender cannot produce a valid BLS signature over `(currentRound, attackerBlock)` using the private key of `poolId`.

**Actual behavior**: `validatePerasVote` calls `lookupPerasVoteStake` which succeeds for every registered pool ID. All votes pass. Once total stake exceeds the quorum threshold, `implAddVote` forges a `ValidatedPerasCert` for `attackerBlock`. `addPerasCertAsync` enqueues the certificate. Chain selection applies the `PerasWeight` boost to `attackerBlock`, potentially switching the node's preferred chain to the attacker-chosen fork. [10](#0-9) [11](#0-10) [12](#0-11)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
