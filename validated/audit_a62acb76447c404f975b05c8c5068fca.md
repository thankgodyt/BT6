### Title
Peras Quorum Check Compares Potentially Absolute Vote Stake Against Relative Threshold Without Normalization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares `PerasVoteStake` (which may carry absolute ledger stake values) against `perasQuorumStakeThreshold` (a relative value, e.g. `3/4`) without any normalization step. The production code itself documents this as an unresolved assumption. If `PerasVoteStake` is populated with absolute stake (e.g. Lovelace), the comparison is meaningless and the quorum check is either trivially satisfied or permanently unsatisfiable, enabling unauthorized Peras certificate forging or permanently blocking certificate creation.

---

### Finding Description

The function `stakeAboveThreshold` is the sole gate that determines whether a collection of Peras votes has accumulated enough stake to forge a certificate:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake        = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
``` [1](#0-0) 

The default `perasQuorumStakeThreshold` is `3/4` and `perasQuorumStakeThresholdSafetyMargin` is `2/100` — both are relative fractions in `[0,1]`: [2](#0-1) 

The type `PerasVoteStake` is a bare `Rational` with no enforced unit. The comment on the type definition explicitly acknowledges the unresolved unit question:

> "NOTE: At the moment there is no consensus from researchers/engineers on how we go from the **absolute** stake of a voter in the ledger to the **relative** stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [3](#0-2) 

`stakeAboveThreshold` is called in three production paths:

1. `votesReachQuorum` — the smart constructor that gates certificate forging: [4](#0-3) 

2. `updateCandidateVoteState` — transitions a candidate target to a winner and forges a cert: [5](#0-4) 

3. `updateLoserVoteState` — detects the multi-winner error condition: [6](#0-5) 

The `PerasVoteStake` attached to each validated vote is sourced from `PerasVoteStakeDistr` via `lookupPerasVoteStake` during `validatePerasVote`: [7](#0-6) 

The `PerasVoteStakeDistr` is injected at runtime via `getStakeDistrSTM :: STM m PerasVoteStakeDistr` in both the vote-DB and ChainDB pool writers: [8](#0-7) 

In the `EveryoneVotes` committee scheme, `implEligiblePartyVoteWeight` returns the raw `LedgerStake` rational directly as `VoteWeight` without normalization: [9](#0-8) 

In the `WFALS` scheme, persistent members also receive their raw `LedgerStake` as vote weight: [10](#0-9) 

If `LedgerStake` carries absolute Lovelace values (as the `PerasVoteStake` comment implies), then any pool with more than 0.75 Lovelace — effectively every pool — would satisfy `stake >= 3/4 + 2/100`, making `stakeAboveThreshold` return `True` for a single vote. Conversely, if the values are normalized to the total supply (e.g. `1/45_000_000_000`), the check would never be satisfied, permanently blocking certificate creation.

---

### Impact Explanation

**Critical.** This is a bypass of the Peras quorum certificate check. If `PerasVoteStake` carries absolute stake values:

- A single vote from any pool (with > 0.75 Lovelace of absolute stake) satisfies `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to be called immediately.
- An unprivileged peer can send a single crafted `PerasVote` message that causes the local node to forge and accept a Peras certificate for an arbitrary block, boosting that block's chain weight by `perasWeight` (default: 15 blocks).
- This directly enables unauthorized chain-selection manipulation: a minority-stake adversary can boost a non-canonical fork to be preferred over the honest chain, breaking Peras safety.

If the values are normalized to near-zero fractions, the opposite holds: quorum is permanently unreachable, disabling the Peras finality mechanism entirely.

---

### Likelihood Explanation

**Medium.** The Peras vote diffusion infrastructure is wired into the production `ChainDB` and miniprotocol stack. The `getStakeDistrSTM` parameter is populated from the ledger stake distribution at runtime. The code comment explicitly states the ledger provides "absolute stake," and neither `validatePerasVote` nor `stakeAboveThreshold` performs normalization. The TODO has been present since the feature was introduced and has not been resolved. Any node running with Peras enabled and receiving votes from peers is on the vulnerable path.

---

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` before comparison. Either:

1. Normalize at the call site: divide each voter's stake by the total committee stake before storing it in `PerasVoteStakeDistr`, so all stored values are in `[0,1]`.
2. Change `stakeAboveThreshold` to accept the total stake as an additional parameter and perform the division internally:

```haskell
stakeAboveThreshold :: PerasParams -> TotalCommitteeStake -> PerasVoteStake -> Bool
stakeAboveThreshold params (TotalCommitteeStake total) voteStake =
  (unPerasVoteStake voteStake / total) >= quorumThreshold + safetyMargin
```

The type system should enforce the distinction between absolute and relative stake to prevent future regressions (e.g. introduce `AbsoluteStake` and `RelativeStake` newtypes).

---

### Proof of Concept

Given the default parameters (`perasQuorumStakeThreshold = 3/4`, `perasQuorumStakeThresholdSafetyMargin = 2/100`):

```haskell
-- Suppose a pool has 1,000,000 ADA = 1e12 Lovelace, stored as absolute Rational:
let voteStake = PerasVoteStake (1_000_000_000_000 % 1)  -- 1e12 Lovelace

-- stakeAboveThreshold compares:
--   1_000_000_000_000 >= (3/4) + (2/100)
--   1_000_000_000_000 >= 0.77
-- => True  (trivially, for any pool with > 0 ADA)

-- Result: votesReachQuorum returns Just with a single vote,
-- forgePerasCert is called, and the certificate is accepted,
-- boosting the adversary's block by perasWeight=15 in chain selection.
```

A peer sends one `PerasVote` for a non-canonical block. The receiving node's `processVotes` → `validatePerasVote` (looks up absolute stake from `PerasVoteStakeDistr`) → `addVote` → `updateCandidateVoteState` → `votesReachQuorum` → `forgePerasCert` path completes, producing a `ValidatedPerasCert` that is then submitted to `addPerasCertAsync`, triggering a chain-selection re-evaluation that may prefer the adversary's boosted fork.
