### Title
Missing `msg` Content Verification for Whitelisted `post_action` Receivers Allows Arbitrary Cross-Contract Calls - (File: contracts/satoshi-bridge/src/deposit_msg.rs)

### Summary
`check_deposit_msg` enforces a whitelist on `post_action.receiver_id` but only validates `post_action.msg` against configured templates when a template set exists for that receiver. When a receiver is whitelisted but has no entry in `post_action_msg_templates`, the `msg` field is accepted without any content check. Any depositing user can therefore craft an arbitrary `msg` payload directed at such a receiver, bypassing the bridge's intended policy restriction on what cross-contract calls are permitted after minting.

### Finding Description

`check_deposit_msg` in `deposit_msg.rs` performs two checks on each `PostAction`:

1. `receiver_id` must be in `post_action_receiver_id_white_list`
2. If `post_action_msg_templates` contains an entry for `receiver_id`, `msg` must match a template

The second check is wrapped in an `if let Some(msg_templates)` guard:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // msg is validated here
}
// if no entry exists, msg is accepted unconditionally
``` [1](#0-0) 

When a receiver is added to `post_action_receiver_id_white_list` without a corresponding entry in `post_action_msg_templates`, the `msg` field is never validated. Any string is accepted.

The `receiver_id` cannot be the bridge contract itself (line 90), but any other whitelisted contract is reachable with an unconstrained `msg`. [2](#0-1) 

The `deposit_msg` is user-controlled: the deposit address is derived by hashing the full `deposit_msg` JSON, so the relayer must submit the exact `deposit_msg` the user encoded when generating their deposit address via `get_user_deposit_address`. [3](#0-2) 

### Impact Explanation

A user can craft a `DepositMsg` with a `post_action` targeting a whitelisted receiver that has no configured templates, supplying an arbitrary `msg`. After the BTC deposit is verified and nBTC is minted, the bridge calls `ft_transfer_call` on the nBTC contract forwarding the user's nBTC to the whitelisted receiver with the attacker-controlled `msg`. If the whitelisted receiver is a DeFi contract (DEX, lending protocol, vault), the arbitrary `msg` can trigger unintended operations — for example, routing the nBTC into an attacker-controlled position, manipulating shared pool state, or invoking a function the bridge operator never intended to authorize. This bypasses the bridge's explicit policy of restricting which cross-contract operations are permitted post-mint.

### Likelihood Explanation

The condition is reachable by any unprivileged depositor. It requires only that at least one whitelisted receiver has no template set configured — a plausible operational state, since the whitelist and template map are managed independently by the DAO. The user constructs the `deposit_msg` off-chain before sending BTC, so no privileged access is needed to inject the malicious `msg`.

### Recommendation

Change the template check from optional to mandatory: if a receiver is in `post_action_receiver_id_white_list` but has no entry in `post_action_msg_templates`, reject the `post_action` rather than silently accepting any `msg`. Alternatively, require that every whitelisted receiver must have at least one template configured before it can be used in `post_actions`.

```rust
// Proposed: treat absence of templates as "no msg is allowed"
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id);

let Some(msg_templates) = msg_templates else {
    // No templates configured → reject
    Event::InvalidPostAction { ... }.emit();
    return None;
};
// proceed with existing template matching
```

### Proof of Concept

1. DAO calls `add_post_action_receiver_id_to_white_list(defi_contract.near)` but does **not** call `add_post_action_msg_template` for that receiver.
2. Attacker generates a deposit address using:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi_contract.near",
       "amount": "100000",
       "msg": "<arbitrary payload triggering unintended defi_contract behavior>"
     }]
   }
   ```
   via `get_user_deposit_address`.
3. Attacker sends BTC to the derived address.
4. Relayer calls `verify_deposit_v2` with the attacker's `deposit_msg`.
5. `check_deposit_msg` passes: `receiver_id` is whitelisted, and because `post_action_msg_templates.get("defi_contract.near")` returns `None`, the `msg` check is skipped entirely.
6. nBTC is minted and `ft_transfer_call(defi_contract.near, amount, "<arbitrary msg>")` is executed, triggering the attacker's chosen operation in `defi_contract`. [4](#0-3)
