### Title
Permissionless `execute_refund` Allows Any Caller to Seize Ownership of a Refund Pending Transaction, Permanently Blocking the Legitimate User's Refund - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

The `execute_refund` entrypoint is fully permissionless: any NEAR account can call it for any pending refund request once the timelock has elapsed. The caller becomes the owner of the resulting `BTCPendingInfo`. For Bitcoin, the refund transaction ID is deterministic (same UTXO → same PSBT → same txid). A griefing attacker who front-runs `execute_refund` before the legitimate user creates a `BTCPendingInfo` under their own account. The legitimate user's subsequent call is rejected with `"pending info already exist"`. If the attacker never signs, the user's BTC refund is stuck indefinitely with no on-chain recovery path that does not require DAO intervention — and DAO intervention itself permanently blocks the deposit path.

---

### Finding Description

`execute_refund` is declared with no caller restriction:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

Inside `finalize_refund_with_psbt`, the `BTCPendingInfo` is created under `caller` — whoever called `execute_refund` — not under the original requester:

```rust
if !self.check_account_exists(&caller) {
    self.internal_set_account(&caller, crate::Account::new(&caller));
}
self.require_pending_sign_capacity(&caller);
// ...
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
};
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [2](#0-1) 

The `btc_pending_id` is derived from the PSBT (which encodes the UTXO being spent). For Bitcoin, the same UTXO always produces the same txid, so the same `btc_pending_id`. A second call for the same refund request therefore always panics with `"pending info already exist"`.

The refund request is kept alive (`executed = true`) after the first `execute_refund`, but the duplicate-txid guard prevents any second `execute_refund` from succeeding: [3](#0-2) 

The only removal path for a refund `BTCPendingInfo` is `internal_remove_refund_pending_tx_id`, which requires the refund request to already be gone:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
``` [4](#0-3) 

The refund request is only removed by `verify_refund_finalize_callback` (requires the attacker to sign and broadcast) or `reject_refund` (DAO/Operator action). If the DAO calls `reject_refund` to unblock the state, `internal_reject_refund` removes the request but does **not** remove the UTXO from `verified_deposit_utxo`: [5](#0-4) 

The UTXO was inserted into `verified_deposit_utxo` by `execute_refund` to block a later deposit. After DAO rejection, the UTXO remains there permanently, blocking both the deposit path and any future refund path. The user's BTC is irrecoverably locked.

---

### Impact Explanation

An attacker who front-runs `execute_refund` causes the user's BTC to be stuck in the bridge with no self-service recovery. If the DAO intervenes by rejecting the refund request (the only on-chain cleanup path), the UTXO is permanently marked as verified, blocking both `verify_deposit` and any future `execute_refund`. The user's BTC is permanently locked in the bridge — matching **Critical: significant loss or permanent locking of user funds** — or at minimum **Medium: attacker-triggered temporary locking of bridged funds** if the DAO declines to intervene and the attacker eventually cooperates.

---

### Likelihood Explanation

NEAR transactions are publicly visible before finalization. Any NEAR account can call `execute_refund` for 1 NEAR (non-refundable). The attacker needs no special role, no BTC, and no knowledge beyond watching the `refund_requests` map. The default pending-sign limit is 1 per account, but the attacker can use multiple accounts to target multiple victims simultaneously. The timelock window (e.g., `refund_timelock_sec` seconds) gives the attacker ample time to prepare and submit the front-running call. [6](#0-5) 

---

### Recommendation

- **Short term**: Restrict `execute_refund` so that only the account that submitted `request_refund` (stored in the `RefundRequest`) or a privileged role (DAO / RefundOperator) may call it. This eliminates the front-running surface entirely.
- **Long term**: Add a timeout-based cancellation path for refund `BTCPendingInfo` entries (analogous to `max_btc_tx_pending_sec` for withdrawals) that restores the UTXO's refundable state without permanently marking it in `verified_deposit_utxo`, so a stuck refund can be retried without DAO intervention.

---

### Proof of Concept

1. Alice sends BTC to her deposit address and calls `request_refund` (pays 2 NEAR non-refundable). The `RefundRequest` is stored keyed by `utxo_storage_key`.
2. The `refund_timelock_sec` elapses.
3. Attacker monitors `get_refund_requests_paged`, sees Alice's request, and immediately calls `execute_refund(utxo_storage_key)` (pays 1 NEAR). The attacker's account becomes the owner of the `BTCPendingInfo`.
4. Alice calls `execute_refund(utxo_storage_key)` — the call panics with `"pending info already exist"` because the Bitcoin txid is deterministic and the attacker's entry already occupies that slot.
5. Attacker never calls `sign_btc_transaction`. Alice's BTC refund is stuck.
6. If the DAO calls `reject_refund` to clean up, the refund request is removed but the UTXO remains in `verified_deposit_utxo`. Alice can no longer deposit or refund — her BTC is permanently locked in the bridge.
