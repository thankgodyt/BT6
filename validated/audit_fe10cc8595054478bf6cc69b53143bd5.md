Audit Report

## Title
Permissionless `logMetadata` + No Balance-Check in `initTransfer` Enables Unauthorized NEAR-Side Minting With Zero EVM Collateral — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.sol`'s `logMetadata` function is fully permissionless, allowing any caller to register an arbitrary ERC-20 address as a known token. `initTransfer` then accepts that same arbitrary address and calls `safeTransferFrom` without verifying the bridge's actual token balance changed, meaning a malicious ERC-20 that returns `true` from `transferFrom` without moving tokens satisfies the check. Because the `InitTransfer` event is emitted unconditionally by the OmniBridge contract (the registered factory), the resulting EVM proof passes all NEAR-side validation, causing the NEAR hub to mint the full claimed amount to the attacker with zero real collateral deposited.

## Finding Description

**Step 1 — Permissionless token registration via `logMetadata`:**

`logMetadata` at lines 224–232 of `OmniBridge.sol` carries no access control modifier and no token allowlist check:

```solidity
function logMetadata(address tokenAddress) external payable {
    string memory name  = IERC20Metadata(tokenAddress).name();
    string memory symbol = IERC20Metadata(tokenAddress).symbol();
    uint8  decimals = IERC20Metadata(tokenAddress).decimals();
    logMetadataExtension(tokenAddress, name, symbol, decimals);
    emit BridgeTypes.LogMetadata(tokenAddress, name, symbol, decimals);
}
```

Any EOA can pass a malicious contract address. The emitted `LogMetadata` event originates from OmniBridge itself — the address registered as the factory on the NEAR hub.

**Step 2 — No balance check in `initTransfer`:**

For tokens that are neither bridge tokens nor custom-minter tokens, `initTransfer` (lines 406–412) falls through to:

```solidity
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
```

OpenZeppelin's `SafeERC20.safeTransferFrom` only asserts the call did not revert and that any returned boolean is `true`. It does not verify that `address(this)`'s balance increased by `amount`. A malicious ERC-20 that returns `true` from `transferFrom` without moving any tokens satisfies this check entirely.

After the fake transfer, the function unconditionally emits `InitTransfer` (lines 427–436), which is the event the NEAR prover will verify.

**Step 3 — NEAR-side validation is insufficient:**

`fin_transfer_callback` (lines 700–718 of `near/omni-bridge/src/lib.rs`) performs only two checks:

```rust
require!(
    self.factories.get(&init_transfer.emitter_address.get_chain())
        == Some(init_transfer.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
let decimals = self.token_decimals.get(&init_transfer.token)
    .near_expect(BridgeError::TokenDecimalsNotFound);
```

Both checks pass: the emitter is OmniBridge (the registered factory), and the token's decimals were stored when `deploy_token_callback` processed the `LogMetadata` proof. There is no check that actual EVM-side custody exists. The NEAR hub then mints the full `amount` to the attacker.

**Replay protection does not prevent the attack:**

`finalised_transfers` prevents reuse of the same `TransferId`. However, each call to `initTransfer` increments `currentOriginNonce`, producing a fresh unique nonce and a new unique `InitTransfer` event. The attacker can repeat steps 4–5 indefinitely with increasing amounts.

## Impact Explanation

An unprivileged attacker can mint an unbounded quantity of a NEAR-side bridged token without depositing any EVM-side collateral. This is unauthorized minting of bridged funds — a Critical impact under the allowed scope. If the minted token is listed on a DEX or used as collateral in a lending protocol, the attacker extracts real value while the bridge's escrow accounting is permanently inflated relative to actual custody.

## Likelihood Explanation

Both prerequisite steps (`logMetadata` and `initTransfer`) are permissionless public functions callable by any EOA with no admin key, no privileged role, no front-running dependency, and no special on-chain state beyond deploying a ~20-line malicious ERC-20. The attack is fully self-contained and repeatable across any EVM chain where OmniBridge is deployed.

## Recommendation

In `initTransfer`, record the bridge's token balance before calling `safeTransferFrom` and assert it increased by at least `amount` after:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 balanceAfter  = IERC20(tokenAddress).balanceOf(address(this));
require(balanceAfter - balanceBefore >= amount, "Transfer amount mismatch");
```

Additionally, add an explicit token allowlist so only pre-approved ERC-20 addresses can be passed to `initTransfer`, eliminating the malicious-token registration vector through `logMetadata` entirely.

## Proof of Concept

1. **Deploy malicious ERC-20** — `transferFrom` always returns `true` without moving tokens; `name()`, `symbol()`, `decimals()` return valid non-empty strings.

2. **Register the token** — Call `OmniBridge.logMetadata(maliciousToken)`. The `LogMetadata` event is emitted from the registered factory address (OmniBridge). No access control prevents this.

3. **Deploy on NEAR** — Submit the EVM proof of the `LogMetadata` event to `deploy_token` on the NEAR hub. `deploy_token_callback` verifies the emitter matches the registered factory and calls `deploy_token_internal`, creating a NEAR token mapped to `maliciousToken` with stored decimals.

4. **Fake deposit** — Call `OmniBridge.initTransfer(maliciousToken, 1_000_000_000_000, 0, 0, "near:attacker.near", "")`. `safeTransferFrom` returns `true` without transferring. `InitTransfer` is emitted with `amount = 1_000_000_000_000`.

5. **Claim on NEAR** — Submit the EVM proof of the `InitTransfer` event to `fin_transfer`. `fin_transfer_callback` passes both the factory check and the decimals lookup, then mints `1_000_000_000_000` of the NEAR token to `attacker.near`.

Steps 4–5 can be repeated indefinitely with fresh nonces and increasing amounts.
