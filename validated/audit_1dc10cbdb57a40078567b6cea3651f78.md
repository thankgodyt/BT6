### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or structural checks. Any unprivileged peer can send crafted Peras certificates over the object-diffusion mini-protocol; `processCerts` will call this stub, accept every certificate, store it in `PerasCertDB`, and allow it to influence chain selection via the Peras weight mechanism. This is the direct analog of the external report's pattern: a critical prerequisite step (validation / approval) is silently absent, so the downstream operation (certificate acceptance / reward distribution) proceeds on invalid inputs without error.

---

### Finding Description

The `BlockSupportsPeras` typeclass requires implementors to supply `validatePerasCert`. The sole production instance (a catch-all `instance StandardHash blk => BlockSupportsPeras blk`) provides:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the function called by `processCerts`, the inbound certificate handler used by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate received from every peer is unconditionally accepted and stored.

The accepted certificates are then surfaced through `getWeightSnapshot` in `PerasCertDB`, which is consumed during chain selection to assign Peras boost weights to blocks: [3](#0-2) 

A second related gap compounds this: `getPerasCertInBlock _ = Nothing` means the ledger never extracts certificates from applied blocks, so `shelleyLedgerLatestPerasCertRound` is permanently `SNothing`. [4](#0-3) 

This means `latestCertOnChain` is always `Origin` in `mkPerasCertInclusionView`, making the `LatestCertSeenIsNewerThanLatestCertOnChain` inclusion rule vacuously true for any certificate, further weakening the gate. [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can craft Peras certificates for arbitrary `(round, block)` pairs and send them via the object-diffusion mini-protocol. Because `validatePerasCert` never rejects anything, these certificates are stored in `PerasCertDB` and contribute Peras boost weight to the attacker-chosen blocks during chain selection. This allows a remote peer to make an honest node assign elevated weight to a non-canonical chain, potentially causing it to prefer and adopt that chain over the honest chain — a direct chain-selection safety failure.

This matches the **Critical** allowed impact: bypass of Peras certificate validation checks that enables unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The entry path requires only a standard peer connection over the Peras object-diffusion mini-protocol — no keys, no stake, no operator access. Any peer that can connect to the node can exploit this. The stub is the only production instance of `BlockSupportsPeras`, so there is no fallback validation path.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's BLS/committee signature against the known committee for the claimed round.
2. That the boosted block point exists and is within the valid range for the round.
3. That the certificate round number is within the current cooldown/active window.

Similarly, implement `getPerasCertInBlock` to actually extract certificates from blocks so that `shelleyLedgerLatestPerasCertRound` is correctly maintained and the `LatestCertSeenIsNewerThanLatestCertOnChain` inclusion rule is not vacuously bypassed.

---

### Proof of Concept

1. Connect a peer to a node running this codebase.
2. Send a batch of `PerasCert` objects via the object-diffusion protocol, each claiming to certify an attacker-controlled block at an arbitrary round number.
3. Observe that `processCerts` calls `validatePerasCert` for each, receives `Right` for all, and stores them via `addCert`.
4. The `getWeightSnapshot` now returns non-zero Peras boost weights for the attacker's blocks.
5. During the next chain selection comparison, the node assigns elevated weight to the attacker's chain and may switch to it.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
