### Title
Peras Vote and Certificate Signature Verification Bypass Enables Unauthorized Chain Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types unconditionally accepts any inbound Peras certificate (`validatePerasCert` always returns `Right`) and accepts any vote whose voter ID appears in the stake distribution without verifying a cryptographic signature (`validatePerasVote`). The `PerasVote` and `PerasCert` data types defined in this instance carry no signature field at all. An unprivileged peer can therefore inject crafted votes and certificates via the object-diffusion mini-protocol, accumulate a forged quorum, and cause honest nodes to apply a weight boost to an attacker-controlled block during chain selection.

---

### Finding Description

**Root cause — missing interface verification before use (analog of the Lido callback bug)**

The Lido Oracle bug registers a callback without verifying it implements the required method; when the method is later called, execution reverts. The analog here is that the `BlockSupportsPeras` typeclass declares `validatePerasCert` and `validatePerasVote` as the required verification interface, but the only concrete instance in the codebase — a catch-all degenerate instance covering every block type — provides stub implementations that perform no cryptographic check whatsoever.

**Degenerate instance — unconditional acceptance** [1](#0-0) 

This `instance StandardHash blk => BlockSupportsPeras blk` is the only `BlockSupportsPeras` instance in the repository. No more-specific instance exists for `CardanoBlock` or any Shelley-family block.

`validatePerasCert` unconditionally stamps every inbound certificate as valid: [2](#0-1) 

`validatePerasVote` only checks that the voter ID appears in the stake distribution; it does not verify any cryptographic signature because the `PerasVote` data type carries no signature field: [3](#0-2) 

**Production inbound path**

`makePerasVotePoolWriterFromChainDB` is the production writer that processes votes arriving from peers. It calls `validatePerasVote` using the degenerate instance above: [4](#0-3) 

`processVotes` accepts the entire batch if all votes pass `validatePerasVote`, then adds them to the database: [5](#0-4) 

`implAddVote` in the `PerasVoteDB` implementation also carries an explicit TODO acknowledging that non-trivial validation logic is absent: [6](#0-5) 

Once votes accumulate to quorum, `forgePerasCert` (also stub-implemented) produces a `ValidatedPerasCert` that is then submitted to `addPerasCertAsync` in the `ChainDB`, which applies the Peras weight boost to the targeted block during chain selection: [7](#0-6) 

**Exploit flow**

1. Attacker connects as an unprivileged peer via the object-diffusion mini-protocol.
2. Attacker reads the public stake distribution to enumerate valid `PerasVoterId` values.
3. Attacker crafts `PerasVote` messages (no signature required — the data type has no signature field) targeting an attacker-controlled block, using voter IDs from the stake distribution.
4. `processVotes` → `validatePerasVote` accepts all votes (stake-distribution membership check passes).
5. Votes accumulate to quorum; `forgePerasCert` produces a `ValidatedPerasCert` for the attacker's block.
6. Alternatively, the attacker sends a crafted `PerasCert` directly; `validatePerasCert` returns `Right` unconditionally.
7. The certificate is stored and its `vpcCertBoost` weight is applied to the attacker's block.
8. Chain selection on the honest node now prefers the attacker's chain over the canonical chain.

---

### Impact Explanation

**Critical — bypass of Peras certificate/vote checks enabling unauthorized chain weight manipulation.**

An unprivileged peer can make an honest node apply a Peras weight boost to any block of the attacker's choosing. Because Peras weight is used in chain selection to prefer one fork over another, this allows the attacker to cause honest nodes to diverge from the canonical chain and adopt a non-canonical fork, constituting a consensus safety failure reachable without any key compromise or stake majority.

---

### Likelihood Explanation

**High.** The degenerate instance is the only `BlockSupportsPeras` instance in the codebase and is explicitly marked as a placeholder. The object-diffusion mini-protocol for Peras votes is wired into the production node diffusion layer. Any peer that can connect to the node can send crafted votes. Voter IDs are public (stake distribution). No private key material is required to construct a passing vote.

---

### Recommendation

1. **Add a cryptographic signature field** to `PerasVote` and `PerasCert` in the concrete data types before the object-diffusion protocol is enabled in production.
2. **Implement real signature verification** in `validatePerasVote` and `validatePerasCert` — analogous to EIP-165 interface verification in the Lido report — before any vote or certificate is admitted to the `PerasVoteDB` or `ChainDB`.
3. **Gate the object-diffusion inbound path** behind a feature flag that is disabled until the real validation logic (tracked in `https://github.com/tweag/cardano-peras/issues/120`) is complete and audited.
4. **Remove or replace the catch-all `instance StandardHash blk => BlockSupportsPeras blk`** with a compile-time error or a safe default that rejects all votes/certificates, so that any block type without a real implementation fails closed rather than open.

---

### Proof of Concept

```
Attacker node A connects to honest node H via the Peras vote object-diffusion protocol.

1. A reads the current PerasVoteStakeDistr from H (public, available via state query).
2. A constructs N crafted PerasVote values:
     PerasVote { pvVoteRound = r
               , pvVoteBlock = attacker_block_point   -- any block A controls
               , pvVoteVoterId = vid_i                -- any vid_i in the stake distr
               }
   No signature is needed; the PerasVote data type has no signature field.
3. A sends the batch to H via opwAddObjects.
4. processVotes calls validatePerasVote for each vote.
   validatePerasVote succeeds for every vote whose pvVoteVoterId is in the
   stake distribution (no crypto check).
5. Votes are stored in H's PerasVoteDB.
6. When total stake of accepted votes exceeds the quorum threshold,
   forgePerasCert produces a ValidatedPerasCert for attacker_block_point.
7. addPerasCertAsync stores the cert; chain selection applies vpcCertBoost
   to attacker_block_point.
8. H's chain selection now prefers the attacker's fork.

Alternatively (for direct certificate injection):
1. A sends a PerasCert { pcCertRound = r, pcCertBoostedBlock = attacker_block_point }.
2. validatePerasCert returns Right unconditionally.
3. Steps 7–8 above follow.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
