### Title
Tokens Minted to Bridge Account When Recipient Is Unregistered in `safe_mint`, Silently Losing User Funds - (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the `nbtc` token contract mints the full token amount to `bridge_id` unconditionally, then checks whether the intended recipient (`account_id`) has a registered storage account. If the recipient is not registered, the function returns `U128(0)` and exits — leaving the minted tokens permanently credited to the bridge's own balance with no delivery to the user and no rollback of the mint. This is a direct analog to the FiinuCoin bug where tokens were allocated to placeholder addresses nobody owns: here, tokens are allocated to `bridge_id` (an address that is not the intended recipient) whenever the deposit target account has not pre-registered on the nBTC contract.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Unconditionally mints** `amount` tokens into `bridge_id`'s balance via `internal_deposit` (line 112).
2. **Checks** whether `account_id` has a registered storage slot (line 114).
3. If `account_id` is **not registered**, returns `PromiseOrValue::Value(U128(0))` immediately (line 115) — no transfer occurs, no rollback of the mint occurs. [1](#0-0) 

The tokens are now credited to `bridge_id`. The bridge contract receives `U128(0)` as the return value. Because the deposit UTXO is marked as verified in the bridge's state before or during the deposit callback (preventing a retry via `verify_deposit`), the user's BTC is consumed but they receive zero nBTC.

Contrast this with `mint_inner`, which is used by the `mint` function and **auto-registers** any unregistered account before depositing: [2](#0-1) 

`safe_mint` deliberately omits this auto-registration, creating the gap.

---

### Impact Explanation

A user who deposits BTC to the bridge but has not pre-registered a storage account on the nBTC contract will have their deposit UTXO consumed and marked verified, yet receive zero nBTC. The minted tokens accumulate in `bridge_id`'s balance — indistinguishable from protocol fee accumulation — with no on-chain record linking them to the user. The user has no self-service recovery path; the tokens are not placed in the `lost_found` map. Recovery requires privileged operator intervention to identify the discrepancy and manually credit the user, constituting a stuck bridge state. The user's BTC is effectively lost until an operator acts.

This matches the allowed impact: **Medium — broken callback rollback / stuck bridge state requiring operator intervention**, and potentially **Critical — significant loss of user funds** if the operator does not intervene.

---

### Likelihood Explanation

NEAR storage registration is a separate, non-obvious prerequisite step. A first-time bridge user who sends BTC to their derived deposit address without first calling `storage_deposit` on the nBTC contract will trigger this path. The bridge's deposit flow calls `safe_mint` (not `mint`) for this code path, and the nBTC contract provides no guard or auto-registration. Any unprivileged user who skips the storage registration step — a realistic and common mistake — will silently lose their nBTC.

---

### Recommendation

Reorder the operations in `safe_mint` so that the registration check (and auto-registration or explicit revert) happens **before** `internal_deposit` is called on `bridge_id`. Either:

- Auto-register `account_id` (matching `mint_inner` behavior), or
- Revert with a clear error if `account_id` is not registered, so the bridge can handle the failure and place funds in `lost_found` or trigger a refund path.

The current design — mint first, check second, silently return 0 — is the root cause and must be inverted.

---

### Proof of Concept

1. User Alice deposits BTC to her bridge-derived address without calling `storage_deposit` on the nBTC contract.
2. A relayer calls `verify_deposit` on the satoshi-bridge; the UTXO is verified and marked in `verified_deposit_utxo`.
3. The bridge calls `safe_mint(alice.near, amount, None)` on the nBTC contract.
4. `internal_deposit(&self.bridge_id, amount)` executes — `amount` nBTC is credited to `bridge_id`. [3](#0-2) 
5. `self.token.accounts.get(&alice.near)` returns `None` (Alice never registered). [4](#0-3) 
6. `safe_mint` returns `U128(0)`. Alice receives zero nBTC.
7. Alice's UTXO is already in `verified_deposit_utxo`; she cannot re-submit the deposit. [5](#0-4) 
8. The `amount` nBTC sits in `bridge_id`'s balance with no `lost_found` entry for Alice. Alice's BTC is lost without operator intervention.
