Audit Report

## Title
`ft_transfer` Failure Silently Ignored in `fin_transfer_send_tokens_callback`, Permanently Freezing Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

In `process_fin_transfer_to_near`, the transfer ID is committed to `finalised_transfers` before the token push-payment is dispatched. When `send_tokens` uses `ft_transfer` (the non-`ft_transfer_call` path), a failure of that call is never detected by `fin_transfer_send_tokens_callback` because `is_refund_required` unconditionally returns `false` for that path. The callback proceeds as if delivery succeeded, emitting `FinTransferEvent` and sending fees, while the recipient receives nothing and the transfer ID is permanently finalized with no recovery path.

## Finding Description

**Root cause — `is_refund_required` ignores promise result for `ft_transfer`:**

`is_refund_required` only inspects the promise result when `is_ft_transfer_call == true`. For the plain `ft_transfer` path it returns `false` unconditionally:

```rust
// near/omni-bridge/src/lib.rs L1800-1803
} else {
    // Not ft_transfer_call: don't refund
    false
}
``` [1](#0-0) 

**State committed before push-payment:**

`add_fin_transfer` inserts the transfer ID into `finalised_transfers` at the very start of `process_fin_transfer_to_near`, before `send_tokens` is called: [2](#0-1) 

`unlock_tokens_if_needed` is also called before `send_tokens`, decrementing the locked-token accounting: [3](#0-2) 

**`ft_transfer` is selected when `msg.is_empty()` for non-deployed tokens:** [4](#0-3) 

**Callback is chained but never checks the `ft_transfer` result:**

`fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = !msg.is_empty()`, so when `msg` is empty, `is_ft_transfer_call = false`, and `is_refund_required` returns `false` regardless of whether `ft_transfer` panicked: [5](#0-4) 

The callback then takes the `else` branch: it sends fees and emits `FinTransferEvent`: [6](#0-5) 

The recovery branch (`revert_lock_actions`, `remove_fin_transfer`, `FailedFinTransferEvent`) is never reached: [7](#0-6) 

## Impact Explanation

This matches the critical allowed impact class: **permanent freezing of bridged funds**. Specifically:

- The transfer ID remains in `finalised_transfers`; any retry of `fin_transfer` panics with `TransferAlreadyFinalised`.
- For locked (non-deployed) tokens, the funds remain physically in the bridge contract with no withdrawal mechanism.
- The locked-token counter is decremented while the tokens are not delivered, creating permanent accounting inconsistency.
- `FinTransferEvent` is emitted, falsely signaling success to off-chain observers and the origin chain.

## Likelihood Explanation

USDC (Centre/Circle) and USDT both implement NEP-141-compatible blacklists on NEAR. The recipient address is fully attacker-controlled from the origin chain — any user can specify any NEAR account as recipient. If that account is blacklisted in the token contract (whether by the issuer for regulatory reasons, or by any party who can influence the token contract), the next relayer call to `fin_transfer` will trigger this path. No bridge admin action is required; the trigger is a standard, widely-deployed token-contract feature. The condition is realistic and repeatable for any blacklist-capable token.

## Recommendation

`fin_transfer_send_tokens_callback` must check the promise result for the plain `ft_transfer` path. Specifically, `is_refund_required` should be extended to also inspect `env::promise_result_checked(0, ...)` when `is_ft_transfer_call == false`, treating a failed promise as requiring a refund. On failure, the callback must:

1. Call `revert_lock_actions(&lock_actions)` to restore the locked-token accounting.
2. Call `remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner)` to un-finalize the transfer, allowing a future retry.
3. Emit `FailedFinTransferEvent` so relayers and the origin chain observe the failure.

This mirrors the existing `ft_transfer_call` failure-handling logic and closes the gap for the `ft_transfer` path.

## Proof of Concept

1. Deploy a NEP-141 token on NEAR with a blacklist (USDC-equivalent).
2. Register the token with the bridge on both EVM and NEAR sides.
3. User on EVM calls `initTransfer` sending 1000 USDC to NEAR recipient `alice.near`.
4. Token issuer blacklists `alice.near` in the NEAR token contract.
5. Relayer calls `fin_transfer` with the proof.
6. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (committed).
   - `unlock_tokens_if_needed` decrements the locked-token counter.
   - `send_tokens` dispatches `ft_transfer(alice.near, 1000, None)`.
   - `ft_transfer` panics because `alice.near` is blacklisted.
7. `fin_transfer_send_tokens_callback` is called with a failed promise result.
   - `is_ft_transfer_call = false` → `is_refund_required` returns `false`.
   - Callback takes the success branch, emits `FinTransferEvent`, sends fees.
8. `alice.near` has 0 tokens. Transfer ID is permanently finalized. Retrying `fin_transfer` panics with `TransferAlreadyFinalised`. 1000 USDC are permanently frozen in the bridge contract.
