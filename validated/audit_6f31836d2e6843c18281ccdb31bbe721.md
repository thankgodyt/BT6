### Title
Fee Calculation Rounds Down, Systematically Under-Collecting Protocol Revenue - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`BridgeFee::get_fee()` and `BridgeFee::get_protocol_and_relayer_fee()` both use Rust's integer division, which truncates toward zero (rounds down). This means every deposit and withdrawal charges the user slightly less fee than the exact mathematical value, causing the protocol to permanently under-collect revenue on every bridge operation.

### Finding Description
In `config.rs`, `BridgeFee::get_fee` computes the bridge fee as:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
``` [1](#0-0) 

`MAX_RATIO` is `10000`. Rust's `/` operator on `u128` truncates toward zero. Whenever `amount * fee_rate` is not exactly divisible by `MAX_RATIO`, the computed fee is floored, and the user is charged 1 satoshi less than the true fee. The protocol absorbs this loss silently on every transaction.

The same pattern appears in `get_protocol_and_relayer_fee`:

```rust
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
``` [2](#0-1) 

Here `protocol_fee` rounds down, so the relayer silently receives 1 extra satoshi at the protocol treasury's expense on every fee split.

Both functions are called on every deposit and withdrawal:

- Deposit path: `config.deposit_bridge_fee.get_fee(deposit_amount)` [3](#0-2) 
- Withdrawal path: `self.internal_config().withdraw_bridge_fee.get_fee(amount)` [4](#0-3) 

### Impact Explanation
On every deposit or withdrawal where `amount * fee_rate` is not a multiple of `MAX_RATIO` (which is the common case), the protocol collects 1 satoshi less than it should. This is a permanent, irrecoverable loss of fee revenue on each transaction. The loss is bounded at 1 satoshi per call but is strictly accumulative across the entire lifetime of the bridge. This matches the M-3 vulnerability class: rounding direction in a financial division that systematically favors the user over the protocol.

**Impact: Low** — publicly reachable accounting discrepancy in production bridge fee paths without direct theft of user funds.

### Likelihood Explanation
Likelihood is **High**. Every deposit and every withdrawal triggers `get_fee`. The rounding error occurs whenever `amount * fee_rate mod MAX_RATIO != 0`, which is the overwhelming majority of real-world deposit amounts. No special attacker action is required; ordinary bridge usage is sufficient.

### Recommendation
Use ceiling division for fee computation so the protocol always collects at least the correct fee:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    let ratio = u128::from(MAX_RATIO);
    let rate  = u128::from(self.fee_rate);
    std::cmp::max(
        (amount * rate + ratio - 1) / ratio,   // ceiling division
        self.fee_min,
    )
}

pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let ratio = u128::from(MAX_RATIO);
    let rate  = u128::from(self.protocol_fee_rate);
    // Round protocol_fee UP so the protocol never loses to relayer rounding
    let protocol_fee = (fee_amount * rate + ratio - 1) / ratio;
    let relayer_fee  = fee_amount.saturating_sub(protocol_fee);
    (protocol_fee, relayer_fee)
}
```

### Proof of Concept
Concrete example with `fee_rate = 30` (0.3%), `MAX_RATIO = 10000`, `amount = 10_001` satoshis:

```
Exact fee  = 10_001 × 30 / 10_000 = 300_030 / 10_000 = 30.003 satoshis
Truncated  = 30   ← what the contract charges
Correct    = 31   ← what ceiling division would charge
Loss       =  1 satoshi per transaction
```

Over 1 000 000 deposits the protocol silently loses up to 1 000 000 satoshis (0.01 BTC) in fee revenue with no operator visibility and no way to recover the shortfall.
