### Title
Stub `validatePerasCert` Allows Unprivileged Peer to Inject Arbitrary Peras Certificates, Manipulating Chain-Selection Weight — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras certificate validation function `validatePerasCert` is a stub that unconditionally accepts every certificate. An unprivileged peer can therefore send crafted `PerasCert` messages with arbitrary `pcCertBoostedBlock` values. Those certificates are stored in `PerasCertDB`, and `implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from all stored certificates. That snapshot is the sole input to the Peras chain-selection weight calculation (`wsvTotalWeight`, `forksAtMostKWeight`, `takeVolatileSuffix`). The attacker can inflate the apparent weight of any fork, causing an honest node to switch to an adversarial chain, or can inflate the weight of the current chain's suffix to prevent valid rollbacks.

### Impact Explanation

An unprivileged peer can:

1. **Force a chain switch to an adversarial fork.** By sending a certificate whose `pcCertBoostedBlock` points to a block on an adversarial fork, the attacker increases that fork's `wsvWeightBoost`. Once `wsvTotalWeight(fork) > wsvTotalWeight(honest)`, `preferCandidate` returns `ShouldSwitch`, and the node adopts the adversarial chain.

2. **Prevent valid rollbacks.** By sending certificates that boost blocks on the current chain's volatile suffix, the attacker inflates `totalWeightOfFragment weights ourSuffix`. Once this exceeds `maxRollbackWeight` (= `k`), `forksAtMostKWeight` returns `False` for any candidate that forks from those blocks, permanently blocking the node from switching to a longer honest chain.

3. **Shrink the volatile suffix.** `takeVolatileSuffix` uses `totalWeightOfFragment` to determine which blocks are "immutable." Inflated weights cause more blocks to be treated as immutable, reducing the set of blocks eligible for rollback and locking in the attacker's preferred chain state.

All three effects constitute a **High** chain-selection / rollback bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The Peras certificate object-diffusion mini-protocol is reachable from any connected peer. The only deduplication guard is a round-number set membership check; there is no cryptographic check, no committee membership check, no boosted-block existence check, and no quorum check. A single malicious peer can inject one certificate per Peras round (or more, targeting different round numbers) to continuously manipulate the weight snapshot. The attack requires no special privileges, no stake, and no key material.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the Peras feature is enabled on any network. At minimum, verify: (a) the certificate's cryptographic signature, (b) that the signer held a valid committee seat for the claimed round, (c) that the boosted block exists and is on a known chain, and (d) that the boost weight matches the protocol parameters for that round.

2. **Do not build `PerasWeightSnapshot` from unvalidated content.** The snapshot should only include certificates whose boosted block has been verified to exist in the VolatileDB or ImmutableDB, analogous to the recommendation in the external report to use an internal tracked mapping rather than a live `balanceOf` call.

3. **Add a guard in `implAddCert`** (the existing `TODO` at line 167 of `PerasCertDB/Impl.hs`) that rejects certificates whose `pcCertBoostedBlock` is not a known block point, preventing the injection of phantom boosts.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
