### Title
Missing Update Function for `chain_signatures_account_id` Config Field - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
The `Config` struct contains a `chain_signatures_account_id` field that cannot be updated after initialization. Unlike the analogous `btc_light_client_account_id` and `nbtc_account_id` fields — which are both present in `ConfigUpdate` and updatable via `update_config` — `chain_signatures_account_id` is absent from `ConfigUpdate` and has no dedicated setter. If the chain-signatures contract must be migrated to a new account, the bridge is permanently stuck: all MPC signing calls will target the stale address, blocking every withdrawal indefinitely.

### Finding Description
`Config` declares three peer account-ID fields:

```
pub btc_light_client_account_id: AccountId,   // updatable via ConfigUpdate
pub nbtc_account_id: AccountId,               // updatable via ConfigUpdate
pub chain_signatures_account_id: AccountId,   // ← NOT in ConfigUpdate, no setter
```

`ConfigUpdate` includes `btc_light_client_account_id` and `nbtc_account_id` as `Option<AccountId>` fields applied by `ConfigUpdate::apply`, but `chain_signatures_account_id` is entirely absent. No separate management function exists for it either — the only related function, `sync_chain_signatures_root_public_key`, updates the *public key* (not the account ID) and is itself a one-shot operation blocked by `require!(is_none(), "Already sync")`. ### Impact Explanation
`chain_signatures_account_id` is the cross-contract call target for every MPC signing request that drives the withdrawal flow. If the chain-signatures contract is ever redeployed to a new account (security incident, protocol upgrade, key-set rotation), the bridge has no on-chain path to update this field. Every subsequent `sign_btc_transaction` call will target the stale account, causing all signing promises to fail. Pending withdrawals cannot complete, escrowed nBTC cannot be burned, and the bridge enters a stuck state that requires a full contract upgrade to resolve — matching the **Medium** allowed impact: *broken callback rollback or stuck bridge state requiring operator intervention*.

### Likelihood Explanation
Chain-signatures contracts on NEAR are upgradeable infrastructure. A redeployment to a new account ID is a realistic operational event (e.g., MPC network migration, security patch). The bridge already anticipates that `btc_light_client_account_id` and `nbtc_account_id` may need to change (hence their presence in `ConfigUpdate`); the omission of `chain_signatures_account_id` is an oversight rather than a design choice, making this a credible operational risk.

### Recommendation

Add `chain_signatures_account_id` to `ConfigUpdate` and its `apply` method, mirroring the pattern used for the other account-ID fields:

```diff
// config.rs – ConfigUpdate struct
+    pub chain_signatures_account_id: Option<AccountId>,

// ConfigUpdate::apply
+    set_if_some!(chain_signatures_account_id);
```

### Proof of Concept

1. Bridge is deployed with `chain_signatures_account_id = "v1.chain-sigs.near"`.
2. The MPC network migrates; the contract is redeployed at `"v2.chain-sigs.near"`.
3. DAO calls `update_config` with every available field — `chain_signatures_account_id` is not a recognised field in `ConfigUpdate`, so the stored value remains `"v1.chain-sigs.near"`.
4. A user initiates a withdrawal via `ft_transfer_call`; the bridge constructs a PSBT and calls `sign_btc_transaction`.
5. `internal_sign_btc_transaction` dispatches a cross-contract call to `"v1.chain-sigs.near"` (the stale address), which no longer exists or no longer holds the correct key set.
6. The signing promise fails; the withdrawal is permanently stuck; escrowed nBTC cannot be burned; the bridge requires a full contract upgrade to recover. [5](#0-4) [6](#0-5) [7](#0-6)
