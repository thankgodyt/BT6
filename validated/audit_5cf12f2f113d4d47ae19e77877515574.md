### Title
Refund Request Front-Running Allows Attacker to Redirect Victim's BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

`request_refund` allows any caller to supply an arbitrary `refund_address` when `deposit_msg.refund_address` is `None`. Because the first `request_refund_callback` to land for a given UTXO wins and blocks all subsequent ones, an attacker who observes a victim's pending `request_refund` call can race to submit an identical call with the attacker's own BTC address. The attacker's refund request is stored, the victim's is rejected as a duplicate, and after the timelock the attacker executes the refund and receives the victim's BTC.

### Finding Description

The `request_refund` public entry point accepts a caller-supplied `refund_address` whenever `deposit_msg.refund_address` is `None`:

```rust

        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"

}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the `refund_address` argument is accepted verbatim with no ownership check — any NEAR account can supply any BTC address.

The callback that actually writes the `RefundRequest` enforces a first-writer-wins uniqueness check:

```rust

``` [2](#0-1) 

The stored `refund_address` is later used verbatim when building the refund output:

```rust

`execute_refund` is fully public — any account can call it after the timelock:

### Impact Explanation

The attacker's `RefundRequest` is stored with `refund_address = attacker_btc_address`. After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, the MPC signs the PSBT, and the victim's BTC is sent to the attacker's address. The victim's BTC is permanently stolen. This matches the **Critical** impact class: unauthorized claiming/release of underlying BTC.

### Likelihood Explanation

All inputs needed to mount the attack are public: `deposit_msg` is submitted on-chain, `tx_bytes` are visible on the Bitcoin blockchain, and `proof` is derivable from the light client. The attacker only needs to monitor the NEAR network for `request_refund` calls and submit a competing call in the same or next block. NEAR receipt ordering within a block is deterministic and attacker-influenceable. The storage deposit required is small relative to any real BTC deposit value. No privileged role is required.

### Recommendation

Bind the `refund_address` to the depositor at request time. The simplest fix is to require that `deposit_msg.refund_address` is always set (non-`None`) before a refund request is accepted, so the refund destination is committed at deposit time and cannot be overridden by a racing third party. Alternatively, record `env::predecessor_account_id()` as the owner of the refund request and require that only the owner can execute it, or add an existence check before the async light-client call so that a duplicate submission is rejected immediately rather than in the callback.

### Proof of Concept

1. Victim sends BTC to the deposit address derived from `deposit_msg = { recipient_id: victim.near, refund_address: None, ... }`.
2. The deposit is never finalized (relayer never calls `verify_deposit`).
3. Victim submits `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, None)`.
4. Attacker observes this call on the NEAR network and immediately submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` — same `deposit_msg`, same `tx_bytes`/`vout`/`proof`, but `refund_address = attacker_btc_addr`.
5. Attacker's `request_refund_callback` executes first; it passes all checks (UTXO not yet in `verified_deposit_utxo`, no existing refund request) and writes `RefundRequest { refund_address: attacker_btc_addr, ... }`.
6. Victim's `request_refund_callback` executes and panics: `"Refund request already exists for this UTXO"`. Victim's attached NEAR deposit is consumed with no recourse.
7. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_storage_key, None)`. The bridge builds a PSBT paying `attacker_btc_addr`, MPC signs it, and the victim's BTC is broadcast to the attacker's address.
8. `verify_refund_finalize` confirms the on-chain transaction and cleans up state. Victim's BTC is permanently lost.
