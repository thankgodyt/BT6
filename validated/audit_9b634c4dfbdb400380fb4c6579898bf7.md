Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Pre-Funded Message Storage Account - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function uses a two-branch OR condition to select a storage-payment path. The `NativeFeeRestricted` role check exists only in Branch 2, but Branch 1 (`try_to_transfer_balance_from_message_account`) contains no such check. Because the message storage account ID is deterministically computable off-chain, a restricted account can pre-fund that account via `storage_deposit`, causing Branch 1 to succeed and the OR to short-circuit, silently skipping the role restriction entirely.

## Finding Description
In `near/omni-bridge/src/lib.rs` lines 566–581, `init_transfer` evaluates:

```rust
if self
    .try_to_transfer_balance_from_message_account(   // Branch 1 – no role check
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()
    || (self.has_storage_balance(...)                // Branch 2 – role check here
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

`try_to_transfer_balance_from_message_account` (storage.rs L260–290) only verifies that the message account has sufficient balance and the signer is registered — it performs no role check. The `message_storage_account_id` is derived deterministically at lib.rs L562–563 via `transfer_message.calculate_storage_account_id(...)`, making it fully predictable before submission.

Exploit flow:
1. Attacker (holding `NativeFeeRestricted`) computes `message_storage_account_id` off-chain.
2. Calls `storage_deposit` with `account_id = message_storage_account_id`, depositing at least `native_token_fee` yoctoNEAR.
3. Calls `ft_transfer_call` with a non-zero `native_token_fee`.
4. Inside `init_transfer`, Branch 1 succeeds (message account is funded, signer is registered), OR short-circuits, Branch 2 is never evaluated.
5. `init_transfer_internal` is called with the non-zero native fee accepted.

## Impact Explanation
This is a concrete role bypass: an account explicitly assigned `NativeFeeRestricted` can set an arbitrary non-zero `native_token_fee` on outbound transfers, an action the protocol explicitly prohibits for that role. This falls directly under the allowed critical impact class of "authorization bypass, role bypass… that lets an attacker execute bridge… actions." The native fee is transferred to the relayer from the attacker's own storage balance, enabling selective relayer incentivization in violation of the protocol's role-based policy controls.

## Likelihood Explanation
Exploitation requires only two standard public contract calls (`storage_deposit` then `ft_transfer_call`) and no privileged access, leaked keys, or external dependencies. The message storage account ID is fully deterministic and computable off-chain. Any account assigned `NativeFeeRestricted` that is motivated to bypass it can do so trivially and repeatably.

## Recommendation
Move the `NativeFeeRestricted` check unconditionally before the two-branch OR condition:

```rust
if init_transfer_msg.native_token_fee.0 > 0 {
    require!(
        !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
        BridgeError::NativeFeeRestricted.as_ref()
    );
}

if self.try_to_transfer_balance_from_message_account(...).is_ok()
    || self.has_storage_balance(...)
{
    ...
}
```

This ensures the restriction is enforced regardless of which storage-payment path is taken.

## Proof of Concept
```
// Precondition: attacker has NativeFeeRestricted role.

// Step 1: compute message_storage_account_id off-chain using transfer parameters.

// Step 2: pre-fund the message account
attacker.call(bridge, "storage_deposit")
    .args_json({"account_id": message_storage_account_id})
    .deposit(native_fee_amount + required_storage_balance)

// Step 3: register attacker's own account
attacker.call(bridge, "storage_deposit")
    .args_json({"account_id": attacker.id()})
    .deposit(required_balance_for_account)

// Step 4: initiate transfer with non-zero native fee
attacker.call(token, "ft_transfer_call")
    .args_json({
        "receiver_id": bridge,
        "amount": transfer_amount,
        "msg": {"InitTransfer": {"native_token_fee": native_fee_amount, "fee": 0, "recipient": eth_address}}
    })
    .deposit(1)

// Result: try_to_transfer_balance_from_message_account succeeds,
// OR short-circuits, NativeFeeRestricted check is never reached,
// transfer stored with non-zero native_fee, relayer receives NEAR fee.
```
