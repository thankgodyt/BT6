Audit Report

## Title
Precision Loss in `normalize_amount` Permanently Locks User Tokens When Transfer Amount Falls Below Decimal Threshold — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a user initiates a NEAR-to-foreign-chain transfer for a token whose `origin_decimals` exceeds the registered destination `decimals`, and the net transfer amount (after fee) is smaller than `10^(origin_decimals − decimals)`, the `normalize_amount` helper returns `0` via floor division. The subsequent relayer call to `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because the user's tokens were already accepted and locked in `pending_transfers` during `ft_on_transfer`, and no public cancel or refund path exists, those tokens are permanently frozen in the bridge.

## Finding Description

**Root cause — `normalize_amount` floor division:**

`normalize_amount` performs integer floor division with no lower-bound guard:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

When `amount < 10^diff_decimals`, the result is `0`.

**Tokens are locked before the zero-amount check:**

`ft_on_transfer` → `init_transfer` → `init_transfer_internal` stores the `TransferMessage` in `pending_transfers`, burns or locks the tokens, and returns `U128(0)` (no refund to the caller), all before any decimal normalization is attempted:

```rust
fn init_transfer_internal(...) -> U128 {
    let required_storage_balance = self
        .add_transfer_message(transfer_message.clone(), storage_owner.clone())...;
    ...
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(..., transfer_message.amount.0);
    ...
    U128(0)   // tokens accepted, no refund
}
``` [2](#0-1) 

**`sign_transfer` panics after the fact:**

The zero-amount check only occurs inside `sign_transfer`, which is called later by a relayer — after the tokens are already locked:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

This `require!` fires before the MPC signing call at line 508, so `sign_transfer_callback` is never reached and `remove_transfer_message` is never invoked for this transfer. [4](#0-3) 

**No public recovery path:**

`remove_transfer_message` is only called from:
- `sign_transfer_callback` (line 657) — only when MPC signing succeeds and fee is zero; unreachable here because `sign_transfer` panics before the MPC call.
- `remove_transfer_message_without_refund` in `init_transfer_internal` (lines 1846, 1859) — only on storage-balance failure or non-NEAR token, not applicable after successful initiation. [5](#0-4) [6](#0-5) 

There is no public `cancel_transfer`, `refund_transfer`, or equivalent function in the contract.

## Impact Explanation

Any user who sends a token amount (net of fee) smaller than `10^(origin_decimals − decimals)` from NEAR to a foreign chain will have their tokens permanently frozen in the bridge with no on-chain recovery path. This constitutes **permanent freezing of bridged funds**, which directly matches the allowed critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation

The condition is reachable by any unprivileged bridge user via `ft_transfer_call`. Tokens bridged between chains with large decimal differences — e.g., a NEAR-native token with 24 decimals registered on an EVM chain with 6 decimals (`diff_decimals = 18`) — have a minimum transferable unit of `10^18`. Any amount below that threshold triggers the freeze. The bridge provides no feedback at initiation time to warn the user, and NEAR token balances are commonly expressed in yocto units, making sub-threshold amounts a plausible user error. No special role or privileged access is required.

## Recommendation

1. **Enforce a minimum amount at initiation time**: In `init_transfer_internal` (or `init_transfer`), look up the token's `Decimals` and reject (refund) any transfer whose `amount_without_fee()` is less than `10^(origin_decimals − decimals)`, returning the full amount to the caller per the NEP-141 refund convention.
2. **Add a public `cancel_transfer` function**: Allow the original sender to cancel a pending transfer that has not yet been signed, unlocking/returning the locked tokens. This also serves as a general safety valve for other stuck-transfer scenarios.

## Proof of Concept

**Setup**: Token registered with `origin_decimals = 24`, `decimals = 6` (`diff_decimals = 18`). Minimum transferable unit = `10^18`.

**Steps**:
1. User calls `ft_transfer_call` on the token contract with `amount = 5 × 10^17` and `fee = 0`.
2. Bridge's `ft_on_transfer` → `init_transfer_internal` accepts the tokens, stores the `TransferMessage` in `pending_transfers`, locks `5 × 10^17` tokens, and returns `U128(0)` (no refund).
3. Relayer calls `sign_transfer(transfer_id, ...)`.
4. Inside `sign_transfer`:
   - `amount_without_fee()` = `5 × 10^17`
   - `normalize_amount(5×10^17, {origin_decimals:24, decimals:6})` = `5×10^17 / 10^18` = **0**
   - `require!(0 > 0, ...)` → **panic: ERR_INVALID_AMOUNT_TO_TRANSFER**
5. Every subsequent relayer call for this `transfer_id` panics identically.
6. `sign_transfer_callback` is never reached; `remove_transfer_message` is never called.
7. The user's `5 × 10^17` tokens remain permanently locked in the bridge with no recovery path.

A unit test can reproduce this by registering a token with `decimals = 6` / `origin_decimals = 24`, calling `ft_on_transfer` with `amount = 5×10^17`, inserting the resulting `pending_transfer` entry, and asserting that `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` while `pending_transfers` still contains the entry afterward.
