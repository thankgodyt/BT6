Audit Report

## Title
ERC1155 `finTransfer` Permanently Locks Bridged Funds When Recipient Contract Lacks `onERC1155Received` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` uses `IERC1155.safeTransferFrom` to deliver ERC1155 tokens to the recipient. If the recipient is a contract that does not implement `IERC1155Receiver`, the call reverts. Because the recipient is embedded in the MPC-signed payload and cannot be altered, and because no admin rescue or claim path exists, the ERC1155 tokens are permanently locked inside the bridge contract while the corresponding NEAR-side tokens are already burned.

## Finding Description
In `finTransfer` (lines 323–330), when `multiToken.tokenAddress != address(0)`, the bridge executes:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per the ERC1155 standard, `safeTransferFrom` calls `onERC1155Received` on the recipient if it is a contract. If the recipient does not implement `IERC1155Receiver`, the call reverts with `"ERC1155: transfer to non ERC1155Receiver implementer"`.

The nonce is set at line 287 (`completedTransfers[payload.destinationNonce] = true`) before the transfer, but because the entire transaction reverts atomically, the nonce write is also rolled back. The nonce is therefore never permanently consumed. However, every subsequent retry with the same signed payload produces the same revert, because the recipient address is Borsh-encoded into the MPC-signed message (lines 289–308) and is immutable — no alternative payload can be signed for a different recipient.

`OmniBridge` itself implements `onERC1155Received` (lines 522–535) but only accepts transfers where `operator == address(this)`. This is irrelevant to the failure path: the revert occurs at the recipient contract, not at the bridge.

There is no admin rescue function, no claimable-escrow fallback, and no mechanism to override the recipient in a signed payload.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**: ERC1155 tokens remain locked inside `OmniBridge` on EVM, while the corresponding tokens on NEAR are already burned at the time `finTransfer` is attempted. The funds are irrecoverable. This matches the critical allowed impact: *permanent freezing of bridged funds across NEAR, EVM, or other supported chains*.

## Likelihood Explanation
ERC1155 bridging is a production feature exposed via `initTransfer1155`. Many widely-used contract types — Gnosis Safe multisigs, DAO treasuries, yield aggregators, NFT marketplaces — do not implement `IERC1155Receiver`. A user who specifies any such contract as the EVM recipient when initiating a bridge-back on NEAR triggers the permanent lock. No attacker capability is required; the user only needs to choose a contract recipient. The scenario is realistic and repeatable.

## Recommendation
Replace `safeTransferFrom` with the non-safe `transferFrom` for ERC1155 delivery in `finTransfer`, eliminating the `onERC1155Received` callback requirement. Alternatively, wrap the `safeTransferFrom` call in a `try/catch` and store undeliverable tokens in a claimable mapping keyed by recipient, allowing the recipient to pull the tokens later. A third option is to validate at `initTransfer1155` time (or at the NEAR signing stage) that the EVM recipient either is an EOA or implements `IERC1155Receiver` before burning NEAR-side tokens.

## Proof of Concept
1. User holds ERC1155 token (`tokenId = 7`) on EVM and calls `initTransfer1155`. Tokens are escrowed in `OmniBridge`.
2. On NEAR, the bridge mints the bridged representation to the user.
3. User initiates a bridge-back from NEAR, specifying a Gnosis Safe multisig (which does not implement `IERC1155Receiver`) as the EVM recipient. NEAR burns the tokens.
4. Relayer obtains MPC signature and calls `finTransfer` on EVM with the signed payload.
5. `finTransfer` reaches line 324 and calls `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), gnosisSafe, 7, amount, "")`.
6. The ERC1155 token contract calls `onERC1155Received` on the Gnosis Safe; the Safe does not implement it; the call reverts.
7. The entire `finTransfer` transaction reverts. `completedTransfers[nonce]` is rolled back.
8. Every subsequent retry with the same signed payload reverts identically — the payload is immutable.
9. The ERC1155 tokens are permanently locked in `OmniBridge`; the NEAR tokens are already burned.

**Minimal test plan**: Deploy a mock ERC1155 token and a mock recipient contract that does not implement `IERC1155Receiver`. Register the token via `logMetadata1155`, escrow tokens via `initTransfer1155`, then call `finTransfer` with the mock recipient as `payload.recipient`. Assert the transaction reverts and the token balance of `OmniBridge` is unchanged. Confirm no subsequent call with the same payload can succeed.
