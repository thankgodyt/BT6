Audit Report

## Title
Missing Zero-Address Recipient Validation in `init_transfer` Allows Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function validates that the recipient chain is not `ChainKind::Near` but never calls the existing `OmniAddress::is_zero()` predicate on the recipient. A user who supplies a zero EVM address (e.g., `eth:0x0000000000000000000000000000000000000000`) will have their tokens burned or locked on NEAR with no recovery path, because no `cancel_transfer` or refund mechanism exists in the contract.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

A zero EVM address passes this check because `ChainKind::Eth != ChainKind::Near`. The `OmniAddress::is_zero()` helper in `near/omni-types/src/lib.rs` covers all chain variants including EVM, Solana, and Starknet:

```rust
pub fn is_zero(&self) -> bool {
    match self {
        Self::Eth(address) | ... => address.is_zero(),
        ...
    }
}
``` [2](#0-1) 

but it is never invoked in `init_transfer`. After the check passes, the transfer message is stored and the user's tokens are locked or burned on NEAR. The relayer then calls `sign_transfer`, which constructs a `TransferMessagePayload` with the zero recipient verbatim: [3](#0-2) 

On the EVM side, `finTransfer` in `OmniBridge.sol` dispatches based on token type. For native ETH (`tokenAddress == address(0)`), it executes a low-level call to `address(0)` which succeeds and permanently burns the ETH:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
``` [4](#0-3) 

For bridge tokens, `IBridgeToken.mint(address(0), amount)` reverts (OpenZeppelin rejects minting to the zero address), leaving the NEAR-side tokens permanently locked: [5](#0-4) 

A grep across the entire NEAR contract confirms no `cancel_transfer`, `refund`, or `revert_transfer` function exists, so there is no recovery path once the transfer is stored.

## Impact Explanation
This directly matches the critical impact class "permanent freezing or loss of bridged funds." For native ETH transfers, funds are irrecoverably sent to `address(0)`. For ERC20/bridge-token transfers, `finTransfer` reverts on EVM while the NEAR-side tokens remain permanently locked with no cancellation mechanism available.

## Likelihood Explanation
The entry point is fully unprivileged: any token holder can call `ft_transfer_call` on any NEP-141 token with an `InitTransferMsg` payload containing a zero recipient. No admin compromise, key leak, or colluding validator is required. A zero EVM address is a realistic input from a buggy frontend, a copy-paste error, or a developer testing. The exploit is repeatable for any token and any user.

## Recommendation
Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipient.as_ref()
);
```

As defence-in-depth, add a symmetric guard in `OmniBridge.sol`'s `finTransfer`:

```solidity
require(payload.recipient != address(0), "InvalidRecipient");
```

## Proof of Concept
1. User holds 1 WETH bridged token on NEAR.
2. User calls `ft_transfer_call` on the WETH NEP-141 contract:
   ```json
   {
     "receiver_id": "omni-bridge.near",
     "amount": "1000000000000000000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"eth:0x0000000000000000000000000000000000000000\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
3. `ft_on_transfer` → `init_transfer`: chain-kind check passes (`Eth != Near`); no `is_zero()` check fires. Tokens are burned on NEAR; transfer stored.
4. Relayer calls `sign_transfer`; MPC signs a payload with `recipient = 0x000…000`.
5. Relayer submits `finTransfer` on Ethereum:
   - For a bridge token: `mint(address(0), amount)` reverts; NEAR tokens remain permanently locked.
   - For native ETH: `address(0).call{value: amount}("")` succeeds; ETH is permanently burned.
6. No cancellation path exists on NEAR; funds are permanently lost.
