### Title
Missing Stake Normalization in Peras Quorum Check Enables Unauthorized Certificate Forging - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares accumulated `PerasVoteStake` values directly against the quorum threshold without normalizing them to the same unit. The code itself documents this as an unresolved design gap: `PerasVoteStake` may carry absolute ledger stake (lovelace), while `PerasQuorumStakeThreshold` is a relative fraction. When the production stake-distribution wiring is completed (replacing the current empty-distribution placeholder), any registered pool with absolute stake exceeding the relative threshold value can forge a Peras certificate with a single vote, bypassing the quorum requirement and manipulating chain selection.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs a bare numeric comparison:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The function's own documentation acknowledges the unit mismatch:

> TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally. [2](#0-1) 

The `PerasVoteStake` type itself carries a companion NOTE:

> At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake). [3](#0-2) 

The degenerate `validatePerasVote` instance (the only instance in the codebase) copies the stake value from `PerasVoteStakeDistr` into `ValidatedPerasVote` without any normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

`stakeAboveThreshold` is called in two places inside the vote aggregation engine: `votesReachQuorum` (which triggers certificate forging) and `updateLoserVoteState` (which detects multiple winners): [5](#0-4) [6](#0-5) 

The production diffusion handler in `NodeToNode.hs` currently passes `pure (PerasVoteStakeDistr mempty)` — an empty distribution — as a temporary placeholder, with an explicit TODO to replace it with real committee selection data:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [7](#0-6) 

When the real ledger stake distribution is wired in, `PerasVoteStakeDistr` will contain absolute lovelace values (e.g., `1_000_000_000_000 % 1`). The quorum threshold `PerasQuorumStakeThreshold` is a relative `Rational` (e.g., `3 % 4` for 75%). The comparison `1_000_000_000_000 >= 0.75` is trivially true, so **any single vote from any pool with more than ~0.75 lovelace of stake passes the quorum check immediately**.

This is the direct analog of the LP token bug: just as `token_a_amount + token_b_amount` ignores the relative price of the two tokens, `stake >= quorumThreshold` ignores the unit difference between absolute lovelace and a normalized fraction.

### Impact Explanation

A Peras certificate forged from a single vote is accepted by `votesReachQuorum`, stored in the CertDB, and applied as a `PerasWeight` boost to the targeted block during chain selection via `wsvTotalWeight`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [8](#0-7) 

An adversary who controls a single registered stake pool can boost an adversarial block's chain weight by `perasWeight` (a configurable `Word64`), causing honest nodes to prefer the adversarial chain over the canonical chain. This constitutes a **Critical bypass of Peras certificate/vote checks** enabling unauthorized certificate acceptance and a **High chain-selection bug** that lets an unprivileged peer make an honest node prefer a non-canonical chain.

### Likelihood Explanation

The vulnerability is latent in the production source tree today. The empty-distribution placeholder is an acknowledged temporary measure with a concrete TODO to replace it. Once the committee selection plumbing is completed — a planned milestone — the bug becomes immediately exploitable by any peer that can submit a vote via the Peras vote diffusion mini-protocol. No key compromise, stake majority, or admin access is required; only a valid registered pool key (needed to appear in the ledger stake distribution) is sufficient.

### Recommendation

`stakeAboveThreshold` must not compare heterogeneous units. Two concrete fixes:

1. **Normalize at validation time**: in `validatePerasVote`, divide the voter's absolute ledger stake by the total stake in `PerasVoteStakeDistr` before storing it in `ValidatedPerasVote.vpvVoteStake`. This mirrors the non-persistent member normalization already done in `implEligiblePartyVoteWeight`.

2. **Normalize at comparison time**: change `stakeAboveThreshold` to accept the total stake as an additional parameter and compute `stake / totalStake >= quorumThreshold` internally, eliminating the implicit unit assumption.

Either approach must be applied consistently to both `votesReachQuorum` and `updateLoserVoteState`. The `PerasVoteStake` type should be given a phantom unit tag (e.g., `Absolute` vs `Relative`) to make future unit mismatches a compile-time error rather than a runtime bug.

### Proof of Concept

With the real stake distribution wired in, the following scenario demonstrates the bypass:

```
-- Assume:
--   Pool P has 1,000,000,000,000 lovelace absolute stake
--   PerasVoteStakeDistr maps P -> PerasVoteStake (1_000_000_000_000 % 1)
--   perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 % 4)  -- 75%
--   perasQuorumStakeThresholdSafetyMargin = 0

-- stakeAboveThreshold check:
stake           = 1_000_000_000_000 % 1
quorumThreshold = 3 % 4
safetyMargin    = 0

-- Result: 1_000_000_000_000 >= 0.75  =>  True
-- => votesReachQuorum returns Just, certificate is forged from 1 vote
-- => adversarial block receives full perasWeight boost
-- => chain selection prefers adversarial chain
```

The attacker's entry path is: craft a `PerasVote` for an adversarial block → submit it via the Peras vote diffusion mini-protocol → `processVotes` calls `validatePerasVote` (stake lookup succeeds) → vote is added to `PerasVoteDB` → `updateCandidateVoteState` calls `votesReachQuorum` → `stakeAboveThreshold` returns `True` with a single vote → `forgePerasCert` produces a `ValidatedPerasCert` → ChainDB applies the boost → chain selection switches to the adversarial chain.
