### Title
Unconditional Peras Certificate Acceptance in `validatePerasCert` Bypasses All Certificate Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic, structural, or stake-based validation. Because this is the only instance in the codebase, any Peras certificate received from an unprivileged peer is accepted and stored with a full chain-weight boost, allowing an adversary to manipulate chain selection in their favour.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must verify a received `PerasCert` before it is stored and used in chain selection. The sole concrete instance — a blanket instance over all `StandardHash blk` — is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- hardcoded full boost
      }
``` [1](#0-0) 

The function ignores every field of `cert` and returns `Right` unconditionally. No signature is checked, no round number is validated, no boosted-block existence is confirmed, and no stake-quorum requirement is enforced. The returned `ValidatedPerasCert` carries the full protocol-configured `perasWeight` boost (default **15**). [2](#0-1) 

This is the direct structural analog to the external report's `token_min_a = token_min_b = 0`: both replace a meaningful threshold check with a hardcoded permissive value that makes the guard always pass.

The same degenerate instance also skips all cryptographic signature verification in `validatePerasVote`, accepting any vote whose voter ID appears in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

---

### Impact Explanation

Peras certificates directly affect chain selection. `preferAnchoredCandidate` and `compareAnchoredFragments` both accept a `PerasWeightSnapshot` and, when it is non-empty, compare chains by `wsvTotalWeight = BlockNo + wsvWeightBoost` rather than by block number alone:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

```haskell
instance ChainOrder (WeightedSelectView proto) where
  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch ...
``` [5](#0-4) 

A fake certificate accepted by `validatePerasCert` is stored in the `PerasCertDB` and included in the `PerasWeightSnapshot` passed to chain selection. It inflates the apparent weight of the adversarially-boosted block by `perasWeight` (15 by default). Because `wsvTotalWeight` is the primary comparison key, a chain that is up to 15 blocks shorter than the honest chain can be made to appear heavier, causing the node to switch to the adversarial fork.

---

### Likelihood Explanation

The Peras certificate mini-protocol (`ObjectDiffusion`) is a public, network-facing protocol. Any connected peer — without any special privilege, key material, or stake — can craft and send a `PerasCert` with an arbitrary `pcCertBoostedBlock` and `pcCertRound`. The `processVotes`/cert-pool writer path calls `validatePerasCert` on every inbound certificate: [6](#0-5) 

Because `validatePerasCert` always returns `Right`, every such crafted certificate is accepted. No brute-force, no key compromise, and no stake majority is required.

---

### Recommendation

Replace the stub implementation with real validation before the Peras certificate path is enabled in production. At minimum, `validatePerasCert` must:

1. Verify the aggregate cryptographic signature over the certificate body against the claimed committee members.
2. Confirm the `pcCertRound` is within the valid window (`perasCertMaxRounds`).
3. Confirm the `pcCertBoostedBlock` refers to a block that is at least `perasBlockMinSlots` old.
4. Confirm the total stake of the signatories meets the `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` requirement (mirroring the check already present in `stakeAboveThreshold` / `votesReachQuorum`). [7](#0-6) 

Until these checks are implemented, the Peras certificate diffusion path must not be enabled on any node that participates in chain selection with a non-empty `PerasWeightSnapshot`.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Adversary connects to an honest node via the Peras `ObjectDiffusion` mini-protocol.
2. Adversary sends a `PerasCert` with `pcCertBoostedBlock = <point of adversarial block B>` and any `pcCertRound`.
3. The node's cert-pool writer calls `validatePerasCert mkPerasParams cert`.
4. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` unconditionally. [8](#0-7) 

5. The certificate is stored in `PerasCertDB`; the `PerasWeightSnapshot` for block `B` now carries a boost of 15.
6. On the next chain-selection trigger, `preferAnchoredCandidate` computes:
   - Honest chain tip at block number N: `wsvTotalWeight = N + 0 = N`
   - Adversarial chain tip at block number N−14 with fake cert: `wsvTotalWeight = (N−14) + 15 = N+1`
7. `compare (wsvTotalWeight ours) (wsvTotalWeight cand)` returns `LT`; the node switches to the adversarial fork. [9](#0-8)
