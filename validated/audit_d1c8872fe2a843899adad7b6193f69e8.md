Audit Report

## Title
`ft_transfer` Failure Silently Ignored in `fin_transfer_send_tokens_callback`, Permanently Freezing Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

In `process_fin_transfer_to_near`, the transfer ID is committed to `finalised_transfers` and locked-token accounting is decremented before the `ft_transfer` push-payment is dispatched. When `ft_transfer` fails (e.g., recipient is blacklisted in a USDC-like token), `fin_transfer_send_tokens_callback` does not inspect the promise result for the non-`ft_transfer_call` path and unconditionally takes the success branch. The transfer ID is permanently finalized, the recipient receives zero tokens, and no recovery path exists — bridged funds are permanently frozen in the contract.

## Finding Description

**Step 1 — Finalization committed before push-payment.**

`process_fin_transfer_to_near` calls `add_fin_transfer` as its very first action: [1](#0-0) 

`add_fin_transfer` inserts the transfer ID into `finalised_transfers` and panics if already present: [2](#0-1) 

This state change is committed when the parent receipt completes. Subsequent receipts (`send_tokens`, `fin_transfer_send_tokens_callback`) cannot roll it back on failure.

**Step 2 — Locked-token accounting decremented before push-payment.**

`unlock_tokens_if_needed` is called immediately after `add_fin_transfer`, before `send_tokens`: [3](#0-2) 

**Step 3 — `ft_transfer` used for non-deployed tokens with empty `msg`.**

`send_tokens` dispatches `ft_transfer` (not `ft_transfer_call`) when `msg.is_empty()` and the token is not a deployed bridge token: [4](#0-3) 

`ft_transfer` panics as a NEAR receipt if the recipient is blacklisted, the contract is paused, or any token-level restriction applies.

**Step 4 — Callback never checks the `ft_transfer` promise result.**

`fin_transfer_send_tokens_callback` is chained after `send_tokens`: [5](#0-4) 

The callback's sole branch condition is `Self::is_refund_required(is_ft_transfer_call)`. When `msg.is_empty()`, `is_ft_transfer_call = false`, and `is_refund_required` unconditionally returns `false` without reading the promise result: [6](#0-5) 

So when `ft_transfer` fails, the callback still takes the `else` branch: it emits `FinTransferEvent`, sends fees to the fee recipient, and returns — leaving the transfer permanently finalized with no tokens delivered: [7](#0-6) 

The revert path (`revert_lock_actions`, `remove_fin_transfer`, `FailedFinTransferEvent`) is never reached.

## Impact Explanation

This is a **permanent freezing of bridged funds**, matching the Critical allowed impact scope. Specifically:

- The transfer ID is permanently in `finalised_transfers`; retrying `fin_transfer` panics with `TransferAlreadyFinalised`.
- The recipient receives zero tokens.
- For non-deployed (locked) tokens, the funds remain physically in the bridge contract with no withdrawal mechanism.
- The locked-token counter is decremented while the tokens remain in the contract — permanent accounting inconsistency.
- `FinTransferEvent` is emitted, falsely signaling success to off-chain observers and the origin chain.

## Likelihood Explanation

Any NEP-141 token implementing a transfer blacklist (USDC, USDT, and similar regulated stablecoins) can trigger this path. The recipient address is fully attacker-controlled from the origin chain. If the recipient is blacklisted in the NEAR token contract — whether by the token issuer for regulatory reasons, or by a malicious actor who controls the recipient account and deliberately triggers blacklisting — the next relayer call to `fin_transfer` will permanently freeze the funds. No admin action on the bridge side is required; the trigger is a standard token-contract feature exercised by the token issuer.

## Recommendation

`fin_transfer_send_tokens_callback` must check the promise result for the plain `ft_transfer` path, mirroring the existing `ft_transfer_call` check in `is_refund_required`. Specifically:

1. Extend `is_refund_required` (or add a separate check) to call `env::promise_result_checked(0, ...)` when `is_ft_transfer_call = false` and treat a failed promise as requiring a refund.
2. On detected failure: call `revert_lock_actions(&lock_actions)`, call `remove_fin_transfer(...)`, and emit `FailedFinTransferEvent` — mirroring the existing refund branch at lines 1703–1718.
3. Do **not** emit `FinTransferEvent` or send fees until the push-payment promise is confirmed successful.

## Proof of Concept

1. Deploy a NEP-141 token on NEAR with a blacklist feature (USDC-equivalent).
2. Register the token with the bridge on both EVM and NEAR sides.
3. User on EVM calls `initTransfer` sending 1000 USDC to NEAR recipient `alice.near`.
4. Token issuer blacklists `alice.near` in the NEAR token contract.
5. Relayer calls `fin_transfer` with the proof.
6. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (committed to storage).
   - `unlock_tokens_if_needed` decrements the locked-token counter.
   - `send_tokens` dispatches `ft_transfer(alice.near, 1000, None)`.
   - `ft_transfer` panics because `alice.near` is blacklisted — receipt fails.
7. `fin_transfer_send_tokens_callback` is called with a failed promise result.
   - `is_ft_transfer_call = false` → `is_refund_required` returns `false` without reading the promise result.
   - Callback takes the success branch, emits `FinTransferEvent`, sends fees.
8. `alice.near` has 0 tokens. Transfer ID is permanently in `finalised_transfers`. Retrying `fin_transfer` panics with `TransferAlreadyFinalised`. 1000 USDC are permanently frozen in the bridge contract with no recovery path.
