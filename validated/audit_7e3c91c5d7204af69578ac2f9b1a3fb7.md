### Title
Quorum Threshold Bypass via Absolute/Relative Stake Unit Mismatch in `stakeAboveThreshold` — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function compares a `PerasVoteStake` value directly against a relative quorum threshold (`3/4 + 2/100 = 0.77`) without normalizing the vote stake. The production code itself documents that no consensus exists on how to convert absolute ledger stake to relative vote stake, and that normalization is not currently performed. If the `PerasVoteStakeDistr` supplied at runtime contains absolute ledger stake values (e.g., lovelace amounts), any single vote from any pool with stake > 0.77 lovelace — effectively every pool — immediately satisfies the quorum check. This allows an unprivileged peer to forge a Peras certificate for any block, granting it a chain-weight boost and causing honest nodes to prefer an adversarially constructed chain.

---

### Finding Description

**Root cause — unit mismatch in threshold comparison:**

`stakeAboveThreshold` in `SupportsPeras.hs` performs a direct numeric comparison:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake          = unPerasVoteStake voteStake          -- raw Rational
  quorumThreshold = ...  -- 3/4 = 0.75
  safetyMargin    = ...  -- 2/100 = 0.02
```

The function's own documentation acknowledges the invariant it relies on is not enforced:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

The `PerasVoteStake` assigned to a validated vote comes from `lookupPerasVoteStake` in `validatePerasVote`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
```

No normalization is applied. The `PerasVoteStakeDistr` is a plain `Map PerasVoterId PerasVoteStake` with no type-level guarantee that values are relative. The companion note at line 136–143 explicitly states:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)."

**Exploit path:**

1. An adversary sends a `PerasVote` message via the object-diffusion miniprotocol to an honest node.
2. `processVotes` in `ObjectPool/PerasVote.hs` calls `validatePerasVote mkPerasParams sd vote`, where `sd` is the `PerasVoteStakeDistr` from `getStakeDistrSTM`.
3. If `sd` contains absolute ledger stake (e.g., `1_000_000_000` lovelace for a pool), `vpvVoteStake` is set to `1_000_000_000 % 1`.
4. `updateCandidateVoteState` calls `votesReachQuorum cfg voteList`, which calls `stakeAboveThreshold cfg totalVoteStake`.
5. `1_000_000_000 >= 0.77` is `True` — quorum is declared reached with a single vote.
6. `forgePerasCert` produces a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params = 15`.
7. The certificate is stored and the boosted block's weight is increased by 15 in `PerasWeightSnapshot`.
8. `preferAnchoredCandidate` and `compareAnchoredFragments` use `weightedSelectView` / `wsvTotalWeight`, which adds `wsvWeightBoost` to `wsvBlockNo`. The adversary's chain now has weight `blockNo + 15` vs the honest chain's `blockNo`, causing honest nodes to switch.

**Structural analog to M-19:**

In M-19, a `gaugeWeightTolerance` multiplier of 1.2× inflates the effective debt ceiling so that `debtCeilingBefore == issuance` even when the gauge is at full capacity, bypassing the unstake guard. Here, the absence of normalization means the accumulated `PerasVoteStake` (absolute lovelace) is compared against a relative threshold (0.77), making the quorum check trivially satisfiable with a single vote — bypassing the certificate-forging guard.

---

### Impact Explanation

**Severity: Critical** — Bypass of Peras certificate/quorum validation that enables unauthorized certificate acceptance and chain-weight manipulation.

A single unprivileged peer can cause an honest node to:
- Accept a forged Peras certificate for any block the adversary chooses.
- Apply a weight boost of `perasWeight = 15` to that block.
- Prefer the adversary's chain over the honest chain in `preferAnchoredCandidate`, triggering a chain switch.

This is a consensus safety failure: honest nodes diverge from the canonical chain by switching to an adversarially boosted fork. The `SecurityParam` rollback bound (`k`) is expressed in total weight units, so a boost of 15 can also cause blocks to be prematurely moved to the ImmutableDB, making the switch irreversible.

---

### Likelihood Explanation

The attack is reachable by any unprivileged peer connected via the object-diffusion miniprotocol. No special keys, stake majority, or operator access is required. The adversary only needs:
1. A valid `PerasVoterId` present in the `PerasVoteStakeDistr` (i.e., any registered stake pool).
2. The ability to send a `PerasVote` message to the target node.

The condition that makes this exploitable — absolute vs. relative stake in `PerasVoteStakeDistr` — is explicitly flagged as unresolved in the production source, making it likely to manifest in any deployment that uses real ledger stake distributions.

---

### Recommendation

1. **Normalize `PerasVoteStake` before comparison**: Before calling `stakeAboveThreshold`, divide each voter's absolute stake by the total stake of the committee to produce a relative value in `[0, 1]`.
2. **Enforce units at the type level**: Introduce distinct newtypes for absolute and relative stake (e.g., `AbsolutePerasVoteStake` vs. `RelativePerasVoteStake`) so that `stakeAboveThreshold` can only accept the normalized form.
3. **Resolve the TODO**: The comment at lines 155–161 of `SupportsPeras.hs` must be resolved before Peras is activated on any network. The fix should either normalize inside `stakeAboveThreshold` (accepting the total stake distribution as an additional parameter) or enforce normalization at the point where `PerasVoteStakeDistr` is constructed.

### Proof of Concept

```
Preconditions:
  - Honest node running with Peras enabled.
  - PerasVoteStakeDistr populated with absolute lovelace values
    (e.g., pool P has stake 1_000_000_000 lovelace → PerasVoteStake (1000000000 % 1)).
  - mkPerasParams: quorumThreshold = 3/4, safetyMargin = 2/100.

Attack:
  1. Adversary sends PerasVote { pvVoteRound = r, pvVoteBlock = adversaryBlock, pvVoteVoterId = P }
     via the object-diffusion miniprotocol.

  2. processVotes calls validatePerasVote mkPerasParams sd vote.
     lookupPerasVoteStake returns PerasVoteStake (1000000000 % 1).
     ValidatedPerasVote { vpvVoteStake = 1000000000 % 1 } is produced.

  3. updateCandidateVoteState calls votesReachQuorum:
     totalVoteStake = 1000000000 % 1
     stakeAboveThreshold: (1000000000 % 1) >= (3/4 + 2/100) = 0.77  →  True

  4. forgePerasCert produces ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }.

  5. addToPerasWeightSnapshot adds weight 15 to adversaryBlock's point.

  6. preferAnchoredCandidate computes:
     wsvTotalWeight(adversaryChain) = blockNo + 15
     wsvTotalWeight(honestChain)    = blockNo
     → ShouldSwitch (Heavier ...)

  7. Honest node switches to adversary's chain.
```
