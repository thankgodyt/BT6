### Title
Peras Certificate Validation Bypass via Degenerate `validatePerasCert` Stub — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` method in the catch-all `BlockSupportsPeras` instance unconditionally returns `Right` — accepting every inbound Peras certificate without any cryptographic or committee-membership check. This is structurally analogous to the reported vulnerability: the guard that is supposed to reject unauthorized actors is permanently bypassed because the prerequisite state it depends on (the voting-committee lookup via `getVotingCommitteeForElection`) is not yet implemented. Any unprivileged peer can therefore inject arbitrary forged certificates through the Peras object-diffusion mini-protocol, have them stored in the `PerasCertDB`, and thereby corrupt the `PerasWeightSnapshot` that drives chain selection.

### Finding Description

**Root cause — degenerate `validatePerasCert` always returns `Right`**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must be passed before a certificate is stored. The only instance that currently exists is the degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of content, is wrapped in `Right` and treated as valid.

**Why the prerequisite state cannot be established — `getVotingCommitteeForElection` is unimplemented**

The function that is supposed to supply the voting committee needed to perform real validation is:

```haskell
getVotingCommitteeForElection _electionId _interEpochVotingCommittee = do
  error "TODO: implement getVotingCommitteeForElection"
``` [2](#0-1) 

Because the committee-lookup state can never be established, the validation layer was replaced with the always-`Right` stub — exactly the same structural pattern as the reported bug: the only mechanism that could set the blocking state requires prior state that does not yet exist, so the guard is permanently ineffective.

**Production inbound path — `processCerts` / `makePerasCertPoolWriterFromChainDB`**

The stub is wired directly into the production certificate-ingest path. Both pool-writer constructors pass `validatePerasCert mkPerasParams` as the validation callback:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [3](#0-2) 

`processCerts` calls `validateCert` on every certificate not already in the DB and, if all pass, stores them: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is stored.

**Chain-selection impact — `PerasWeightSnapshot` feeds `readChainComparison`**

Stored certificates are used to compute the `PerasWeightSnapshot`, which is read by the BlockFetch client interface to compare candidate chains:

```haskell
readChainComparison :: STM m (WithFingerprint (ChainComparison (HeaderWithTime blk)))
readChainComparison =
  fmap mkChainComparison <$> getPerasWeightSnapshot chainDB
``` [5](#0-4) 

An attacker who injects certificates boosting a non-canonical block can therefore shift the weight comparison in `compareCandidateChains`, causing the honest node to prefer the adversarial chain.

### Impact Explanation

An unprivileged peer can send a batch of forged `PerasCert` objects over the Peras object-diffusion mini-protocol. Because `validatePerasCert` unconditionally returns `Right`, every certificate passes the only validation gate and is persisted to the `PerasCertDB`. The stored certificates directly feed `PerasWeightSnapshot`, which is consumed by `readChainComparison` in the BlockFetch decision logic. By crafting certificates that boost a non-canonical block, an adversary can make an honest node's chain-selection logic prefer a chain that does not represent the honest network's tip — a consensus safety failure.

This matches the **Critical** allowed impact: *bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance*.

### Likelihood Explanation

The attack requires only a network connection. No stake, keys, or prior registration is needed. The object-diffusion mini-protocol is open to any peer, and the `processCerts` ingest path is active in production. The degenerate instance applies to all block types via the catch-all `instance StandardHash blk => BlockSupportsPeras blk`, so no era-specific condition limits exposure.

### Recommendation

1. Implement `getVotingCommitteeForElection` in `AcrossEpochs.hs` so that the correct `VotingCommittee` can be retrieved for any `ElectionId`.
2. Replace the always-`Right` stub in `validatePerasCert` with a real check that calls `verifyVote`/`verifyCert` against the committee returned by `getVotingCommitteeForElection`.
3. Until (1) and (2) are complete, the `processCerts` ingest path should reject all inbound certificates rather than silently accepting them, to prevent the `PerasWeightSnapshot` from being poisoned.

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the Peras object-diffusion mini-protocol.
2. Construct a `PerasCert blk` with an arbitrary `pcCertRound` and a `pcCertBoostedBlock` pointing to a non-canonical block.
3. Send the certificate batch to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
5. The certificate is stored in the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. `getPerasWeightSnapshot` now reflects the injected boost; `readChainComparison` returns a `ChainComparison` that favours the adversarial block.
7. The BlockFetch decision logic selects the adversarial chain over the honest chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
