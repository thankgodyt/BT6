### Title
Missing Storage Registration for New Withdraw Relayer Address Breaks Legacy Near Intents Bridging Flow - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

`set_withdraw_relayer_address()` in the `nbtc` contract stores a new relayer `AccountId` without registering it in the NEP-141 token ledger. Any subsequent `ft_transfer` call using the legacy Near Intents memo path redirects tokens to that unregistered account, causing the transfer to panic and permanently blocking the legacy bridging flow for all users until an operator manually registers the relayer.

---

### Finding Description

The `nbtc` contract implements a legacy Near Intents bridging path inside its `ft_transfer` override. When a user calls `ft_transfer` with `receiver_id == nbtc_contract` and a memo starting with `"WITHDRAW_TO:"`, the contract silently redirects the transfer to the stored `withdraw_relayer` address:

```rust
// contracts/nbtc/src/lib.rs:183-196
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

The relayer address is set by the controller via:

```rust
// contracts/nbtc/src/lib.rs:324-328
pub fn set_withdraw_relayer_address(&mut self, relayer: &AccountId) {
    self.assert_controller();
    env::storage_write(WITHDRAW_RELAYER_ADDRESS, &borsh::to_vec(relayer).unwrap());
}
```

This setter **only writes the raw `AccountId` bytes to contract storage**. It does not call `self.token.internal_register_account(&relayer)` or any equivalent. The NEP-141 standard `FungibleToken::ft_transfer` (and its underlying `internal_transfer`) requires both sender and receiver to have a registered storage slot. If the receiver is not registered, the call panics with an account-not-found error.

Contrast this with `new()`, which explicitly registers `bridge_id` at initialization:

```rust
// contracts/nbtc/src/lib.rs:86-88
contract.token.internal_register_account(&contract.bridge_id);
```

And `burn()`, which defensively registers the relayer before transferring a fee:

```rust
// contracts/nbtc/src/lib.rs:161-163
if self.token.accounts.get(&relayer_account_id).is_none() {
    self.token.internal_register_account(&relayer_account_id);
}
```

No such guard exists in `set_withdraw_relayer_address` or in the `ft_transfer` redirect path.

---

### Impact Explanation

After a controller calls `set_withdraw_relayer_address` with a new (unregistered) relayer account, every user who attempts the legacy Near Intents withdrawal flow (`ft_transfer` with `WITHDRAW_TO:` memo) will have their transaction panic. Because NEAR transactions are atomic, the panic reverts the transfer and the user's tokens are returned — no direct theft occurs. However, the entire legacy bridging path is completely non-functional until an operator separately calls `storage_deposit` for the new relayer. This constitutes a **stuck bridge state requiring operator intervention**, matching the Medium impact class.

---

### Likelihood Explanation

The trigger is a routine administrative action: updating the withdraw relayer address. There is no on-chain enforcement requiring the operator to also register the new address. The Near Intents integration is a documented, production-facing flow (`WITHDRAW_MEMO_PREFIX` is a named constant, the path is commented "Legacy bridging flow used by Near Intents"). Any user of that integration after a relayer rotation will immediately hit the panic. Likelihood is **medium-high** given that relayer rotation is an expected operational event.

---

### Recommendation

Inside `set_withdraw_relayer_address`, register the new relayer account if it is not already registered:

```rust
pub fn set_withdraw_relayer_address(&mut self, relayer: &AccountId) {
    self.assert_controller();
    if self.token.accounts.get(relayer).is_none() {
        self.token.internal_register_account(relayer);
    }
    env::storage_write(WITHDRAW_RELAYER_ADDRESS, &borsh::to_vec(relayer).unwrap());
}
```

Alternatively, add a registration guard inside the `ft_transfer` redirect path before calling `self.token.ft_transfer(withdraw_relayer, ...)`, mirroring the pattern already used in `burn()`.

---

### Proof of Concept

1. Controller calls `set_withdraw_relayer_address({ relayer: "new-relayer.near" })`. The account `new-relayer.near` has never called `storage_deposit` on the `nbtc` contract.
2. User Alice holds 100,000 nBTC and calls:
   ```
   nbtc.ft_transfer(
     receiver_id: "nbtc.near",
     amount: "100000",
     memo: "WITHDRAW_TO:bc1q..."
   )
   ```
3. Inside `ft_transfer`, the condition at line 185–188 matches. `read_withdraw_relayer_address()` returns `Some("new-relayer.near")`.
4. `self.token.ft_transfer("new-relayer.near", 100000, memo)` is called. The NEP-141 `FungibleToken` implementation calls `internal_transfer`, which panics because `new-relayer.near` has no registered storage slot.
5. The entire transaction reverts. Alice's tokens are returned, but the legacy Near Intents withdrawal path is completely broken for all users until the operator manually registers the new relayer.

**Root cause:** [1](#0-0)  does not register the new relayer, while [2](#0-1)  unconditionally forwards to it. The registration pattern that should be applied is already demonstrated at [3](#0-2)  in `burn()` and at [4](#0-3)  in `new()`.
