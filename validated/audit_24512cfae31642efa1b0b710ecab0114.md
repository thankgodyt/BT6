### Title
ChainSync Client Uses `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs`, Causing Incorrect Peer Disconnection and Non-Canonical Chain Preference When Peras Is Enabled - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` (zero weights) instead of reading the live `PerasWeightSnapshot` from the `PerasCertDB`. This is the direct analog of the external report's zero-initialization bug: just as `self.value = 0` causes `calculateAverage()` to always return 0 and propagate through every period transition, using `emptyPerasWeightSnapshot` causes `preferAnchoredCandidate` to always ignore all Peras weight boosts, making every beyond-forecast-horizon chain comparison behave as if Peras is disabled.

---

### Finding Description

When a ChainSync peer sends a header that is beyond the local forecast horizon, the client calls `checkPreferTheirsOverOurs` to decide whether to stay connected or throw `CandidateTooSparse` and disconnect. The decision is made by calling `preferAnchoredCandidate`, which branches on whether the supplied `PerasWeightSnapshot` is empty:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero, never reads live certs
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

Because `isEmptyPerasWeightSnapshot emptyPerasWeightSnapshot` is always `True`, `preferAnchoredCandidate` falls into its pure block-count branch:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- pure block-count comparison, Peras boosts ignored
      ...
  | otherwise =
      -- weighted comparison using actual PerasWeightSnapshot
      ...
``` [2](#0-1) 

The live weight snapshot is correctly maintained by `PerasCertDB.implGetWeightSnapshot`, which builds it from all stored certificates:

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds) ]
  pure (WithFingerprint weights fp)
``` [3](#0-2) 

This live snapshot is correctly used everywhere else in chain selection — `chainSelSync`, `chainSelectionForBlock`, `constructPreferableCandidates`, `initialChainSelection` — but is silently bypassed in `checkPreferTheirsOverOurs`. [4](#0-3) 

---

### Impact Explanation

Under Peras, the canonical chain is the **heaviest** chain (block-count + sum of Peras boosts), not the longest chain. A canonical chain can therefore have **fewer blocks** than a competing fork if it carries sufficient Peras certificate boosts.

When a peer presents such a chain and its tip is beyond the local forecast horizon, `checkPreferTheirsOverOurs` compares purely by block count (because weights are empty). The canonical chain appears shorter, so `preferAnchoredCandidate` returns `ShouldNotSwitch`, the node throws `CandidateTooSparse`, and **disconnects from the peer offering the canonical chain**. The node then remains on the lighter, non-canonical fork.

This is a chain-selection bug that lets an honest node prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions. It matches the **High** impact tier: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- Peras is the explicit new feature being integrated; the codebase already wires up `PerasCertDB`, weight snapshots, and weighted chain selection everywhere except this one call site.
- Any peer can send headers beyond the forecast horizon during normal ChainSync operation — no special privileges required.
- The scenario (canonical chain is heavier but shorter in blocks) is the normal operating condition Peras is designed for.
- The developers themselves flagged this with a `TODO` comment referencing issue #64, confirming awareness that the empty snapshot is incorrect here.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the `PerasCertDB`, consistent with how every other chain-selection call site obtains weights:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot  -- read live snapshot
  if shouldSwitch $ preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This ensures that when Peras is enabled, the beyond-forecast-horizon disconnection decision respects the same weighted chain ordering used everywhere else in the consensus layer.

---

### Proof of Concept

**Setup**: Peras enabled; security parameter `k = 2160`; boost weight `B = 15` per certificate.

1. Honest node `N` is on chain `C_ours` of length 100 blocks (total weight 100).
2. Peer `P` offers chain `C_cand` of length 98 blocks but with 2 Peras-boosted blocks (total weight `98 + 2×15 = 128 > 100`). `C_cand` is the canonical chain.
3. `C_cand`'s tip is beyond `N`'s forecast horizon.
4. `checkPreferTheirsOverOurs` is invoked with `emptyPerasWeightSnapshot`.
5. `preferAnchoredCandidate` compares block counts: `98 < 100` → `ShouldNotSwitch`.
6. `N` throws `CandidateTooSparse` and disconnects from `P`.
7. `N` remains on `C_ours` (weight 100), which is lighter than the canonical `C_cand` (weight 128).

The root cause — `emptyPerasWeightSnapshot` at line 1842 — is the exact analog of `self.value = 0` in the external report: a zero initial value substituted for the actual accumulated state, causing every downstream decision to be computed as if no weight accumulation ever occurred. preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
