Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Message-Account Pre-funding in `init_transfer` — (File: near/omni-bridge/src/lib.rs)

## Summary
The `NativeFeeRestricted` role check in `init_transfer` is placed exclusively inside Branch B of a short-circuit OR condition. Branch A (`try_to_transfer_balance_from_message_account`) carries no role check. Because the message storage account ID is deterministically computable from publicly known transfer parameters (including the desired `native_fee`), a `NativeFeeRestricted` user can pre-fund that virtual account via `storage_deposit`, causing Branch A to succeed and `init_transfer_internal` to be called with a non-zero native fee — the role is never consulted. The same gap exists in `init_transfer_resume`.

## Finding Description
In `init_transfer` (lines 566–584 of `near/omni-bridge/src/lib.rs`), the condition is:

```rust
if self.try_to_transfer_balance_from_message_account(...)  // Branch A — no role check
    .is_ok()
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
    // Branch B — role check lives here only
```

Due to short-circuit evaluation, if Branch A returns `Ok`, Branch B (and its `acl_has_role` guard) is never evaluated. `init_transfer_internal` is then called with whatever `native_token_fee` the user specified.

`try_to_transfer_balance_from_message_account` (lines 260–290 of `near/omni-bridge/src/storage.rs`) returns `Err(StorageError::MessageAccountNotRegistered)` only when the virtual account has no entry in `accounts_balances`. If the account is registered and holds sufficient balance (`balance.total >= native_fee`), it returns `Ok(())`.

`storage_deposit` (lines 141–169 of `near/omni-bridge/src/storage.rs`) accepts an arbitrary `account_id` parameter with no restrictions — any caller can register and fund any account ID.

The virtual account ID is computed by `TransferMessageStorageAccount::id()` (lines 610–620 of `near/omni-types/src/lib.rs`) as `sha256(borsh(token, amount, recipient, fee, sender, msg))`. The `fee` field includes `native_fee`. Nonces and other runtime values are excluded, so the ID is fully deterministic from the attacker's chosen transfer parameters before the transfer is submitted.

The same bypass exists in `init_transfer_resume` (lines 635–645 of `near/omni-bridge/src/lib.rs`): it calls `try_to_transfer_balance_from_message_account` and on success calls `init_transfer_internal` with no role check at all.

## Impact Explanation
This is a role/authorization bypass matching the allowed critical impact class: "Unauthorized transaction, authorization bypass, role bypass... that lets an attacker execute bridge... actions." The `NativeFeeRestricted` role is a compliance control preventing designated accounts from attaching a native NEAR fee to outbound transfers. By bypassing it, a restricted user can attach an arbitrary native NEAR fee, incentivizing relayers to process their transfer despite the compliance restriction. The restriction is defeated entirely.

## Likelihood Explanation
Exploitation requires only two on-chain calls from any account that has been assigned the `NativeFeeRestricted` role. No privileged access beyond that role assignment is needed. The virtual account ID is computable off-chain before the transfer is submitted. The attacker funds the virtual account with their own NEAR (which becomes the native fee), so no victim cooperation or external dependency is required. The attack is repeatable for every transfer the restricted user wishes to submit.

## Recommendation
Move the `NativeFeeRestricted` role check to an unconditional position before the branching logic, evaluated whenever `native_token_fee > 0`:

```rust
if init_transfer_msg.native_token_fee.0 > 0 {
    require!(
        !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
        BridgeError::OperationNotAllowed.as_ref()
    );
}
```

Apply the same guard at the start of `init_transfer_resume` before calling `try_to_transfer_balance_from_message_account`, checking `transfer_message.fee.native_fee.0 > 0` against the `storage_owner`.

## Proof of Concept
```
1. Admin grants NativeFeeRestricted role to attacker.near.

2. Attacker computes the virtual message storage account ID off-chain:
   TransferMessageStorageAccount {
       token:     Near("token.near"),
       amount:    U128(1_000),
       recipient: Eth(0xDEAD...),
       fee:       Fee { fee: U128(10), native_fee: U128(1_000_000_000_000_000_000_000_000) },
       sender:    Near("attacker.near"),
       msg:       "",
   }.id(None)
   → deterministic 64-char hex account ID (e.g., "a3f7...c2d1")

3. Attacker calls:
   bridge.storage_deposit({ account_id: "a3f7...c2d1" })
   with deposit = native_fee + required_storage_balance
   (storage_deposit accepts any account_id with no restriction)

4. Attacker calls:
   token.ft_transfer_call({
       receiver_id: "bridge.near",
       amount: "1000",
       msg: InitTransferMsg { native_token_fee: "1000000000000000000000000", ... }
   })

5. Inside init_transfer:
   - try_to_transfer_balance_from_message_account("a3f7...c2d1", ...) → Ok(())
     (account is registered, balance.total >= native_fee)
   - Short-circuit: Branch B and acl_has_role check are never evaluated
   - init_transfer_internal is called with native_fee = 1 NEAR

6. Transfer is registered with a non-zero native fee.
   NativeFeeRestricted role is bypassed entirely.
   Relayers are incentivized to process the restricted user's transfer.
```
