Audit Report

## Title
Dust-Amount NEAR-Originated Transfer Permanently Burns Tokens with No Refund Path - (`near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR-originated cross-chain transfer via `ft_transfer_call` with an amount smaller than the decimal normalization factor (e.g., less than `10^(origin_decimals − dest_decimals)` base units), `init_transfer_internal` immediately burns or locks the full token amount on NEAR. Subsequently, every relayer call to `sign_transfer` will permanently panic with `InvalidAmountToTransfer` because `normalize_amount` returns 0 via floor division. No cancel or refund path exists, resulting in permanent, irreversible loss of the user's bridged tokens.

## Finding Description

**Step 1 — Tokens burned/locked before normalization check.**
`init_transfer` (called via `ft_on_transfer`) validates only `fee < amount` at line 554–557, with no floor on `amount` itself. It then calls `init_transfer_internal`, which at lines 1850–1857 unconditionally burns (for deployed tokens) or locks the full `transfer_message.amount` on NEAR before any normalization is attempted:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(..., transfer_message.amount.0);
}
```

**Step 2 — `sign_transfer` always panics for sub-threshold amounts.**
When a relayer later calls `sign_transfer`, lines 475–485 compute:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(...),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` at lines 2784–2786 performs integer floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For an 18-decimal NEAR token bridged to an 8-decimal destination, `diff_decimals = 10`, so any `amount < 10^10` produces `amount_to_transfer = 0`, causing the `require!` to panic. The code's own comment at line 2781–2783 acknowledges: *"When fee = 0, dust stays locked/burned"* — but this only addresses remainder dust, not the case where the entire amount is below the threshold.

**Step 3 — No recovery path.**
The transfer message remains in `pending_transfers` indefinitely. There is no public `cancel_transfer` or user-callable refund function. `remove_transfer_message_without_refund` is only invoked internally on storage failures or for non-NEAR tokens. The `sign_transfer` function is decorated `#[trusted_relayer]`, so the user cannot even retry it themselves — and no relayer can ever succeed for this transfer ID.

The PoC in the submission incorrectly describes an EVM-originated flow; the actual vulnerable path is NEAR-originated (`ft_transfer_call` → `init_transfer` → `init_transfer_internal`). The core mechanism and impact are nonetheless correct.

## Impact Explanation
Any user who calls `ft_transfer_call` on a NEAR-native token with `amount < 10^(origin_decimals − dest_decimals)` and `fee = 0` (both pass all on-chain validation) will have their tokens permanently burned or locked. `sign_transfer` will revert for that transfer ID on every invocation, forever. This constitutes **permanent freezing/loss of bridged funds** — a Critical impact under the allowed scope ("permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet…" and "decimal/normalization abuse… that changes user or protocol balances").

## Likelihood Explanation
The condition is reachable by any unprivileged NEP-141 token holder through the standard `ft_transfer_call` entry point. Tokens bridged between chains with differing decimal precision (e.g., 18-decimal NEAR token to 8-decimal Solana/Bitcoin representation) are the common case in OmniBridge. A user sending a "dust" amount — or any amount below `10^diff_decimals` — triggers permanent loss. No special role, leaked key, or admin action is required. The `Fee` struct defaults both fields to zero, so `fee=0, amount=1` is a valid and natural call.

## Recommendation
1. **Eager normalization check in `init_transfer`**: Before burning/locking, compute `normalize_amount(amount - fee, decimals)` and revert with a clear error if the result is zero. This prevents the transfer from ever entering `pending_transfers` with an un-signable amount.
2. **Minimum amount enforcement**: Enforce a protocol-level minimum transfer amount per registered token pair, sized to guarantee `normalize_amount(amount - fee, decimals) > 0`.
3. **User-callable cancel with timeout**: Add a `cancel_transfer` function that refunds locked/burned tokens for transfers that have been pending beyond a configurable timeout, as a safety net for any future stuck transfers.

## Proof of Concept
1. Register a NEAR-native token with `origin_decimals = 18`, `decimals = 8` on the destination chain (normalization factor = `10^10`).
2. As an unprivileged user, call `ft_transfer_call(bridge_contract, amount="1", msg=<InitTransferMsg with fee=0, recipient=<dest_chain_address>>)` on the token contract. The call succeeds; `fee (0) < amount (1)` passes; `init_transfer_internal` burns 1 unit and stores the `TransferMessage`.
3. A trusted relayer calls `sign_transfer(transfer_id, None, None)`. Inside, `normalize_amount(1 - 0, {origin_decimals:18, decimals:8})` = `1 / 10^10` = `0`. The `require!(amount_to_transfer > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
4. Repeat step 3 indefinitely — it always panics. The 1-unit token is permanently burned. No refund is possible.
5. Verify with a NEAR workspaces integration test: assert that after `ft_transfer_call` with `amount=1` on an 18→8 decimal token pair, `get_transfer_message` returns the stuck entry, and `sign_transfer` always returns a failure result, while the user's token balance is permanently reduced.
