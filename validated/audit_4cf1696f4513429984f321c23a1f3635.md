### Title
Orchard Binding Signature Never Verified — Bridge Accepts Invalid Bundle and Locks UTXOs in PendingVerify — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

---

### Summary

The bridge never verifies the Orchard binding signature at any point in the withdrawal pipeline. An unprivileged user can submit an Orchard bundle whose Halo2 proof and note encryption are valid (so all bridge-side policy checks pass) but whose 64-byte Redpallas binding signature is zeroed. The bridge accepts the bundle, completes MPC signing of the transparent inputs, assembles the final transaction, and advances to `PendingVerify`. The Zcash network rejects the transaction because the binding signature is invalid, leaving the bridge's UTXOs stuck in `PendingVerify` until privileged operator intervention.

---

### Finding Description

**Entry point — `ft_on_transfer` → `ft_on_transfer_callback`**

The attacker calls `ft_on_transfer` with a `ChainSpecificData` payload containing `orchard_bundle_bytes` whose binding signature bytes are zeroed. [1](#0-0) 

**Step 1 — `extract_orchard_bundle` (orchard_policy.rs)**

`read_v5_bundle` deserializes the bundle, reading the binding signature bytes into the `Bundle<Authorized, ZatBalance>` struct. It does **not** verify the signature — verification requires the full transaction sighash, which is not available at parse time. [2](#0-1) 

The subsequent checks — action count, `recover_output_with_ovk`, value non-zero — are all independent of the binding signature: [3](#0-2) 

**Step 2 — `validate_orchard_bundle` (orchard_policy.rs)**

Called from `check_psbt_chain_specific`. Validates recipient address and value balance. No binding signature check: [4](#0-3) 

**Step 3 — `get_zcash_tx` / `extract_tx_bytes_with_sign` (psbt_wrapper.rs)**

After MPC signing of transparent inputs, `get_zcash_tx` assembles the final transaction by passing the stored bundle (with its zeroed binding signature) directly into `TransactionData::from_parts`. No verification occurs: [5](#0-4) 

`extract_tx_bytes_with_sign` then encodes the transaction — pure serialization, no crypto verification: [6](#0-5) 

**Step 4 — `sign_btc_transaction_callback` advances to `PendingVerify`**

The callback stores the invalid `tx_bytes_with_sign` and transitions the state machine: [7](#0-6) 

**Step 5 — Zcash network rejects the transaction**

The Zcash network performs full transaction validation including the Redpallas binding signature check. The transaction is rejected. The bridge's UTXOs remain unspent on-chain but the bridge state machine is stuck in `PendingVerify`.

---

### Impact Explanation

The bridge's UTXOs are locked in `PendingVerify` until a privileged operator calls `cancel_withdraw` (requires `Role::DAO` or `Role::Operator`, plus waiting for `max_btc_tx_pending_sec` to elapse): [8](#0-7) [9](#0-8) 

The UTXOs are not permanently lost (the operator can recover them), but the attack causes a forced stuck state requiring privileged intervention. An attacker who burns a small amount of nZEC can lock a much larger UTXO. Repeated attacks can exhaust the bridge's UTXO pool and halt all withdrawals until each is manually cancelled.

**Impact**: Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

- The attacker only needs to hold nZEC tokens (publicly accessible via the bridge).
- Crafting the malicious bundle requires: generate a valid Orchard bundle (valid Halo2 proof + valid OVK-encrypted note), then zero out the last 64 bytes (the Redpallas binding signature) of the serialized bundle. This is trivial with any Zcash library.
- No privileged access, no key leakage, no external dependency compromise required.
- The attack is repeatable for each bridge UTXO.

---

### Recommendation

Verify the Orchard binding signature before accepting the bundle. The binding signature must be verified against the full transaction sighash (ZIP-244). Since the sighash depends on the final transparent inputs/outputs, verification must occur **after** the complete transaction is assembled in `get_zcash_tx` / `extract_tx_bytes_with_sign`, before advancing to `PendingVerify`. Use `orchard::bundle::Bundle::verify_binding_sig` (or the equivalent from `zcash_primitives`) with the transaction's `sighash` computed via `zcash_primitives::transaction::sighash::signature_hash`.

---

### Proof of Concept

1. Generate a valid Orchard bundle for the correct amount and recipient, encrypted with `BRIDGE_OVK = [0u8; 32]`.
2. Serialize the bundle with `write_v5_bundle`. Zero out the last 64 bytes (the Redpallas binding signature).
3. Call `ft_on_transfer` on the bridge contract with the modified `orchard_bundle_bytes` and a valid UTXO input.
4. Observe that `ft_on_transfer_callback` succeeds and a `BTCPendingInfo` is created.
5. Call `sign_btc_transaction` (any caller). Observe that `sign_btc_transaction_callback` succeeds and the state advances to `PendingVerify` with `tx_bytes_with_sign` set.
6. Attempt to broadcast `tx_bytes_with_sign` to the Zcash network. Observe rejection with a binding signature error.
7. Observe the bridge UTXO is locked in `PendingVerify` and cannot be released without operator `cancel_withdraw`.

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())

    pub fn get_zcash_tx(self) -> Transaction {
        let transparent_bundle = zcash_transparent::bundle::Bundle {
            vin: self.vin.clone(),
            vout: self.vout.clone(),
            authorization: zcash_transparent::bundle::Authorized,
        };

        // Here we encode the Zcash transaction with orchard bundle so it can be submited to the network
        let inner_tx = TransactionData::from_parts(
            TxVersion::V5,
            self.branch_id,
            0,
            BlockHeight::from(self.expiry_height),
            Some(transparent_bundle),
            None,
            None,
            self.orchard.map(|b| b.bundle),
        )
        .freeze()
        .unwrap_or_else(|_| {
            env::panic_str("ERR_TX_FREEZE: failed to freeze Zcash transaction data")
        });

        Transaction { inner_tx }
    }
