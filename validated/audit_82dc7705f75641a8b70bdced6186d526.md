### Title
Missing `FtMint` Event in `safe_mint` Bypasses NEP-141 Supply Tracking — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract increases the token total supply via `internal_deposit` but never emits the `FtMint` event. Any minting done through this path is invisible to indexers, wallets, and monitoring tools that rely on NEP-141 standard events to track token supply. A parallel issue exists in `ft_resolve_transfer`, which can destroy tokens without emitting `FtBurn`.

---

### Finding Description

The `mint` function correctly calls `mint_inner`, which calls `internal_deposit` **and** emits `FtMint`: [1](#0-0) 

However, `safe_mint` calls `internal_deposit` directly on `bridge_id` to increase total supply, then transfers to the user — emitting only `FtTransfer`, never `FtMint`: [2](#0-1) 

The `internal_deposit` call at line 112 increases `total_supply` in the underlying `FungibleToken` state, but no `FtMint` event is emitted. From an event-log perspective, the bridge appears to have already held those tokens and merely transferred them, rather than minting new ones. The actual on-chain supply and the event-derived supply diverge with every `safe_mint` call.

A second, narrower instance of the same class exists in `ft_resolve_transfer`: when a cross-contract transfer is rejected and tokens are destroyed, the code only logs the burn rather than emitting `FtBurn`: [3](#0-2) 

---

### Impact Explanation

Every `safe_mint` call silently inflates the on-chain `total_supply` without a corresponding `FtMint` log entry. Indexers, block explorers, and DeFi integrations that reconstruct supply from NEP-141 events will permanently undercount circulating nBTC. Over time the gap between event-derived supply and actual on-chain supply grows monotonically, breaking any off-chain invariant check or audit that relies on event data. This matches the **Medium** impact class: harmful smart-contract behavior (broken supply-tracking invariant) without direct fund theft.

---

### Likelihood Explanation

`safe_mint` is an active, non-deprecated code path used for the legacy Near Intents bridging flow (referenced by the `WITHDRAW_MEMO_PREFIX` / `WITHDRAW_RELAYER_ADDRESS` constants in the same file). It is callable by the bridge contract whenever a deposit is processed through that flow. The discrepancy accumulates silently with no on-chain signal. [4](#0-3) 

---

### Recommendation

Replace the `internal_deposit` + raw transfer pattern in `safe_mint` with a call to `mint_inner` (or an equivalent that emits `FtMint`) before performing the transfer. For example:

```rust
pub fn safe_mint(...) {
    self.assert_bridge();
    // Mint to bridge_id AND emit FtMint
    self.mint_inner(&self.bridge_id.clone(), amount);
    // then transfer to user as before
    ...
}
```

For `ft_resolve_transfer`, replace the `log!` call with a proper `FtBurn` event emission when `burned_amount > 0`, consistent with the NEP-141 standard.

---

### Proof of Concept

1. Bridge calls `safe_mint(user.near, 1_000_000, None)`.
2. `internal_deposit(&bridge_id, 1_000_000)` executes — `total_supply` increases by 1,000,000. No `FtMint` event is emitted.
3. `ft_transfer(user.near, 1_000_000, None)` executes — `FtTransfer { old_owner: bridge, new_owner: user, amount: 1_000_000 }` is emitted.
4. An indexer summing `FtMint` events records 0 new tokens minted. An indexer reading `ft_total_supply()` on-chain records 1,000,000 new tokens. The discrepancy is permanent and grows with each `safe_mint` invocation. [5](#0-4)

            return PromiseOrValue::Value(U128(0));

            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
        if self.token.accounts.get(account_id).is_none() {
            self.token.internal_register_account(account_id);
        }
        self.token.internal_deposit(account_id, amount.into());
        near_contract_standards::fungible_token::events::FtMint {
            owner_id: account_id,
            amount,
            memo: None,
        }
        .emit();
