Audit Report

## Title
`finTransferExtension` Forwards Full `msg.value` to Wormhole After Native ETH Already Sent to Recipient, Causing Permanent Revert - (File: `evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

## Summary
`OmniBridgeWormhole.finTransferExtension` unconditionally passes `msg.value` to `_wormhole.publishMessage`. When `payload.tokenAddress == address(0)`, the base `finTransfer` function first transfers `payload.amount` ETH to the recipient, leaving only `msg.value - payload.amount` in the contract. The subsequent `publishMessage{value: msg.value}` call exceeds the available balance and reverts the entire transaction. Every NEAR → EVM native ETH bridge finalization via Wormhole is permanently blocked.

## Finding Description
In `OmniBridge.finTransfer` (L317–357), when `payload.tokenAddress == address(0)`, `payload.amount` ETH is sent to `payload.recipient` via a low-level call before `finTransferExtension(payload)` is invoked. In `OmniBridgeWormhole.finTransferExtension` (L109), the call is `_wormhole.publishMessage{value: msg.value}(...)`. At this point the contract holds only `msg.value - payload.amount` ETH (the Wormhole fee portion), so forwarding the full `msg.value` exceeds the available balance and the EVM reverts the entire transaction — including the ETH transfer to the recipient and the nonce mark.

The `initTransfer` path avoids this by computing `extensionValue = msg.value - amount - nativeFee` before calling `initTransferExtension`, which then uses the `value` parameter rather than `msg.value`. No equivalent residual-value computation exists in the `finTransfer` path.

## Impact Explanation
Permanent freezing of bridged funds. Any user who initiates a NEAR → EVM native ETH transfer routed through Wormhole will have their NEAR-side locked funds permanently unreleasable: the EVM finalization step (`finTransfer` with `tokenAddress == address(0)`) always reverts, and no alternative finalization path exists. This matches the critical allowed impact of permanent freezing of bridged funds across NEAR/EVM/Wormhole-routed flows.

## Likelihood Explanation
High. Native ETH (`address(0)`) is an explicitly supported bridgeable asset with a dedicated branch in `finTransfer`. Any relayer attempting to finalize a NEAR → EVM native ETH transfer will trigger the revert unconditionally — no special attacker capability is required. The condition is deterministic and affects every such transfer.

## Recommendation
Mirror the `initTransfer` pattern: compute the residual ETH value before calling `finTransferExtension`, and thread it through as a parameter instead of using `msg.value` in the extension.

```solidity
// In OmniBridge.finTransfer, before calling finTransferExtension:
uint256 extensionValue = (payload.tokenAddress == address(0))
    ? msg.value - payload.amount
    : msg.value;
finTransferExtension(payload, extensionValue);
```

Update `finTransferExtension` signatures in both `OmniBridge` (L369–371) and `OmniBridgeWormhole` (L96–116) to accept `uint256 value` and use it in place of `msg.value` when calling `_wormhole.publishMessage`.

## Proof of Concept
1. Deploy `OmniBridgeWormhole` on a local EVM testnet with a mock Wormhole that charges `wormholeFee`.
2. Call `finTransfer` with `payload.tokenAddress = address(0)`, `payload.amount = 1 ether`, sending `msg.value = 1 ether + wormholeFee`.
3. Observe: the base contract attempts `payload.recipient.call{value: 1 ether}("")` — succeeds, contract now holds `wormholeFee`.
4. `finTransferExtension` then calls `_wormhole.publishMessage{value: 1 ether + wormholeFee}(...)` — contract only has `wormholeFee`, EVM reverts.
5. Entire transaction is rolled back; the recipient receives nothing and the nonce is not consumed, but the NEAR-side transfer remains locked with no viable retry path since the same revert occurs on every attempt.
