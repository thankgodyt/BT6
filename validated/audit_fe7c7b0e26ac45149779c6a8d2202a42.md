### Title
Missing Cryptographic/Committee Validation Guard in `validatePerasCert` While `validatePerasVote` Has a Guard — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras protocol extension processes inbound votes and certificates from peers via the ObjectDiffusion mini-protocol. `validatePerasVote` enforces a guard — it checks that the voter is present in the stake distribution before accepting a vote. The analogous function `validatePerasCert` is **missing this guard entirely**: it unconditionally returns `Right` for every certificate, accepting any peer-supplied certificate without any cryptographic, committee-membership, or quorum check. Accepted certificates are stored and applied as chain-selection weight boosts, meaning an unprivileged peer can inject arbitrary Peras certificates to influence which chain the node prefers.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines two validation functions:

**`validatePerasVote`** — has a guard: it checks that the voter's ID is present in the `PerasVoteStakeDistr` before accepting the vote.

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [1](#0-0) 

**`validatePerasCert`** — is **missing the equivalent guard**: it unconditionally returns `Right` for every certificate, performing zero validation.

```haskell
validatePerasCert params cert =
    Right ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [2](#0-1) 

Both functions are called from the production inbound-processing pipeline. `processCerts` (called from `makePerasCertPoolWriterFromChainDB`) passes `validatePerasCert mkPerasParams` as the validation callback: [3](#0-2) 

Inside `processCerts`, every certificate that is not already in the DB is passed through `validateCert`. Because `validatePerasCert` always returns `Right`, every peer-supplied certificate passes validation and is stored: [4](#0-3) 

The stored `ValidatedPerasCert` carries a `vpcCertBoost` field (set to `perasWeight params`) that is used by the ChainDB to compute the `PerasWeightSnapshot`, which directly influences chain selection: [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can send a batch of `PerasCert` objects via the ObjectDiffusion mini-protocol targeting any block point and any round number. Because `validatePerasCert` performs no check, every such certificate is accepted, stored, and contributes a `perasWeight`-sized boost to the targeted block in the `PerasWeightSnapshot`. This lets the attacker make the local node assign artificially elevated chain-selection weight to an adversarially chosen block, potentially causing the node to prefer a non-canonical or adversary-controlled chain over the honest chain — a chain-selection safety violation.

**Impact: High** — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol is a public, peer-facing interface. Any connected peer can send `PerasCert` messages. No special privileges, keys, or stake are required. The attack requires only sending a well-formed (but cryptographically unverified) `PerasCert` CBOR message. The Peras code is present in production files and the `makePerasCertPoolWriterFromChainDB` path is wired into the node's ChainDB. Likelihood is **Medium-High** once Peras weight is actively used in chain selection.

---

### Recommendation

Add the missing validation guard to `validatePerasCert` analogous to the guard already present in `validatePerasVote`. Specifically, `validatePerasCert` must verify:

1. The certificate's claimed quorum is backed by a valid aggregate signature from a sufficient number of eligible committee members (cryptographic check).
2. The committee members are drawn from the correct stake-weighted committee for the given round (committee membership check).
3. The total weight of the signers meets the quorum threshold (quorum check).

Until the full cryptographic plumbing is in place, the function should return `Left PerasValidationErr` by default (fail-closed) rather than `Right` (fail-open), mirroring the conservative posture of `validatePerasVote`. [6](#0-5) 

---

### Proof of Concept

1. Connect to a node running this code as a peer via the ObjectDiffusion mini-protocol.
2. Send a `PerasCert` message with `pcCertRound = <target round>` and `pcCertBoostedBlock = <adversary block point>`.
3. `makePerasCertPoolWriterFromChainDB` calls `processCerts` → `validatePerasCert mkPerasParams cert` → unconditionally returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }`.
4. The certificate is stored via `ChainDB.addPerasCertAsync`.
5. The node's `getPerasWeightSnapshot` now includes a boost for the adversary-chosen block.
6. Chain selection uses this snapshot to prefer the boosted (adversary-chosen) block over the honest canonical tip. [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
