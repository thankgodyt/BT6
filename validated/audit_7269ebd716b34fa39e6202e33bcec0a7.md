### Title
Missing Administrative Setter for `change_address` Permanently Breaks All Withdrawal Paths - (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary

The bridge contract enforces that `change_address` is `None` at initialization, but provides no administrative function to set it afterward. `ConfigUpdate` omits `change_address`, and no dedicated setter exists in the management API. Because every withdrawal, UTXO-management, and cancel-withdraw path calls `get_change_script_pubkey()`, which panics when `change_address` is `None`, the bridge is structurally unable to process any withdrawal from the moment of deployment.

---

### Finding Description

**Root cause — init enforces `None`:**

`Contract::new()` hard-requires `change_address` to be absent at deployment: [1](#0-0) 

**Root cause — `ConfigUpdate` omits `change_address`:**

`ConfigUpdate`, the only struct accepted by the DAO-gated `update_config`, lists every mutable config field except `change_address` (and `chain_signatures_account_id`): [2](#0-1) 

`ConfigUpdate::apply()` therefore never touches `config.change_address`: [3](#0-2) 

**Root cause — no dedicated setter exists:**

The entire management API (`management.rs`) contains no `set_change_address` function. The only analogous post-init setter is `sync_chain_signatures_root_public_key` for the MPC root key — no equivalent exists for `change_address`. [4](#0-3) 

**Panic site — `get_change_script_pubkey`:**

Every withdrawal and UTXO-management code path calls this helper, which panics unconditionally when `change_address` is `None`: [5](#0-4) 

**Affected callers:**

- `create_btc_pending_info` (withdrawal initiation via `ft_on_transfer`): [6](#0-5) 

- `verify_withdraw_burn_callback` (post-sign burn): [7](#0-6) 

- `verify_active_utxo_management_burn_callback` (UTXO consolidation): [8](#0-7) 

---

### Impact Explanation

The bridge is deployed with `change_address = None` (enforced by `new()`). Because no DAO-callable function can set it afterward, every withdrawal attempt panics inside `ft_on_transfer`. The nBTC tokens are returned to the caller (the panic reverts the transfer), so no immediate token loss occurs. However, the bridge is permanently unable to process any BTC withdrawal, UTXO management, or cancel-withdraw operation without a contract upgrade. BTC deposited into the bridge's MPC-controlled addresses cannot be redeemed by users holding nBTC, constituting a stuck bridge state requiring operator intervention.

**Impact: Medium** — stuck bridge state requiring operator intervention; no direct theft but withdrawals are permanently broken at deployment.

---

### Likelihood Explanation

This is a structural deployment-time defect. Every deployment of the bridge starts with `change_address = None` and has no on-chain path to set it. Any user who attempts a withdrawal after deployment will trigger the panic. Likelihood is **High** — it affects every deployment unconditionally.

---

### Recommendation

Add `change_address: Option<String>` to `ConfigUpdate` and handle it in `ConfigUpdate::apply()`:

```rust
// In ConfigUpdate struct
pub change_address: Option<String>,

// In ConfigUpdate::apply()
if let Some(addr) = self.change_address {
    config.change_address = Some(addr);
}
```

Alternatively, add a dedicated DAO-gated `set_change_address(address: String)` function in `management.rs`, mirroring the existing `sync_chain_signatures_root_public_key` pattern.

---

### Proof of Concept

1. Deploy the bridge via `Contract::new(config)` — `config.change_address` must be `None` (enforced by `require!`).
2. DAO attempts `update_config(ConfigUpdate { ... })` — `change_address` field does not exist in `ConfigUpdate`; no setter is available.
3. A user deposits BTC and receives nBTC via `verify_deposit_v2`.
4. User calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message, triggering `ft_on_transfer` on the bridge.
5. `ft_on_transfer` → `create_btc_pending_info` → `self.internal_config().get_change_script_pubkey()` → `panic!("ERR_CONFIG: change_address not configured")`.
6. The entire `ft_on_transfer` call reverts; nBTC is returned to the user.
7. No withdrawal can ever succeed. The bridge is permanently stuck in a withdrawal-disabled state with no on-chain remedy.
