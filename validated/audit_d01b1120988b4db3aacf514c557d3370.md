### Title
Intra-Batch Equivocating Peras Certificate Accepted Without Uniqueness Check, Enabling Unprivileged Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` deduplicates inbound Peras certificates only against the current DB state, never against other certificates in the same batch. A malicious peer can therefore send a single batch containing two certificates for the same round number but boosting different blocks (equivocating certificates). Both pass the DB-membership filter, both pass the stub `validatePerasCert` that unconditionally returns `Right`, and both are submitted to `addCert`. The first certificate is stored and triggers chain selection; the second is silently discarded. Because the equivocation is never detected, the peer is not disconnected, and it can deterministically choose which block receives the Peras boost by controlling the order of entries in the batch.

---

### Finding Description

`processCerts` in `PerasCert.hs` performs its deduplication check by reading the set of round numbers already in the database once, then filtering the incoming list against that snapshot:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  ...
  mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [1](#0-0) 

The filter at line 166 checks each certificate against `alreadyInDb` (the DB state at call time), but it does **not** check whether two certificates in the same batch share the same round number. If the batch contains `[cert(round=5, blockA), cert(round=5, blockB)]`, both pass the filter because neither round 5 entry is in the DB yet.

Both certificates then reach `validatePerasCert`, which is currently a stub that unconditionally returns `Right`:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

Both validated certificates are then submitted sequentially via `mapM_ (addCert . WithArrivalTime now) validatedCerts`. The underlying `implAddCert` is atomic and idempotent — the second certificate for round 5 returns `PerasCertAlreadyInDB` — but the result is discarded with `void`, so the equivocation is never surfaced as an error and the peer is never disconnected. [3](#0-2) 

The production writer used by the `ChainDB` path passes `void . ChainDB.addPerasCertAsync chainDB` as the `addCert` action: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which calls `PerasCertDB.addCert` and, if the certificate is new, triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

The first certificate in the batch wins the race and triggers chain selection for its boosted block. The attacker controls the order.

The state-machine test model explicitly acknowledges that equivocating certificates (same round, different block) must be rejected, but enforces this only as a test precondition, not in production code: [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can craft a single ObjectDiffusion batch containing two Peras certificates for the same round number that boost different blocks. Because `processCerts` does not check for intra-batch round-number collisions, and because `validatePerasCert` is a stub that accepts every certificate unconditionally, both certificates pass all checks. The first certificate is stored and triggers `chainSelectionForBlock` for its boosted block; the second is silently dropped. The peer can therefore deterministically steer the local node's Peras chain-selection boost toward any block it chooses, potentially causing the node to prefer a non-canonical chain over the honest chain. The equivocation is never reported and the peer is never disconnected, so the attack can be repeated.

This maps to the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Low.** The Peras protocol and its ObjectDiffusion mini-protocol are still under active development (multiple `TODO` markers reference issue #120 for real validation). The attack requires a peer that deliberately sends equivocating certificates, which is detectable at the network layer once real cryptographic validation is in place. However, the missing intra-batch uniqueness check is an independent structural gap that will persist even after `validatePerasCert` is completed unless explicitly addressed.

---

### Recommendation

1. **Add an intra-batch uniqueness check in `processCerts`**: Before validating, deduplicate `certsNotAlreadyInDb` by round number. If two certificates in the same batch share a round number, treat the batch as equivocating and throw a `PerasCertInboundException` (causing peer disconnection), just as invalid certificates do.

2. **Implement real `validatePerasCert` logic**: The stub at `SupportsPeras.hs:353–358` must be replaced with actual cryptographic and protocol-rule checks (tracked as issue #120) so that forged certificates are rejected before reaching the DB or chain selection.

---

### Proof of Concept

**Setup**: A private Cardano testnet with Peras enabled. An attacker controls one peer node.

**Steps**:

1. Attacker constructs a batch of two `PerasCert` objects:
   - `cert_A = PerasCert { pcCertRound = 42, pcCertBoostedBlock = blockA }` (canonical chain tip)
   - `cert_B = PerasCert { pcCertRound = 42, pcCertBoostedBlock = blockB }` (attacker's fork tip)

2. Attacker sends the batch `[cert_B, cert_A]` (fork cert first) via the ObjectDiffusion inbound protocol to an honest node.

3. In `processCerts`:
   - `alreadyInDb` does not contain round 42 → both certs pass the filter.
   - `validatePerasCert` returns `Right` for both (stub).
   - `mapM_` calls `addCert cert_B` first → stored, `chainSelectionForBlock blockB` triggered.
   - `addCert cert_A` → `PerasCertAlreadyInDB`, silently discarded.

4. The honest node now has a Peras boost on `blockB` (the attacker's fork). If `blockB`'s chain weight plus the boost exceeds the canonical chain's weight, the node switches to the attacker's fork.

5. No error is logged, no peer disconnection occurs. [7](#0-6) [2](#0-1) [5](#0-4)
