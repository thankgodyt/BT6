### Title
Orchard Amount Not Bound to `transfer_amount` in `withdraw_rbf` — Attacker Can Inflate Shielded Output, Stealing ZEC from Bridge UTXO Pool - (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

### Summary
A user who initiated a shielded Zcash withdrawal can call `withdraw_rbf` supplying a new Orchard bundle whose `value_balance` encodes a higher amount than the original. The `check_withdraw_psbt` constraint on `actual_received_amount` is circular (the Orchard amount cancels out of the inequality), so no check enforces `orchard_amount == transfer_amount - withdraw_fee - gas_fee`. The attacker can extract up to `original_gas_fee - min_btc_gas_fee` extra ZEC per RBF call, redirecting ZEC that should return to the bridge's UTXO pool into their own shielded address.

### Finding Description

**Entry point:** `withdraw_rbf` in `contracts/satoshi-bridge/src/api/bridge.rs:259` is a public method callable by any user who owns the original pending withdrawal. [5](#0-4) 

**Bundle replacement:** `withdraw_rbf_callback` extracts `orchard_bundle_bytes` from the attacker-supplied `chain_specific_data` and passes it to `generate_psbt_from_original_psbt_and_new_output`, which calls `PsbtWrapper::from_original_psbt`. This replaces the Orchard bundle wholesale while preserving the original transparent inputs. [6](#0-5) [7](#0-6) 

**Circular constraint:** In `check_withdraw_psbt`, `gas_fee` is computed as `total_input_amount - total_output_amount`, and `total_output_amount` includes `orchard_amount`. The check `actual_received_amount <= amount - withdraw_fee - gas_fee` therefore reduces to `0 <= amount - withdraw_fee - total_input_amount + transparent_change`, which is independent of `orchard_amount`. The Orchard amount is unconstrained. [3](#0-2) 

**`validate_orchard_bundle` does not check amount vs. `transfer_amount`:** It only verifies the recipient matches the original Unified Address and that `value_balance == -orchard_amount` (internal bundle self-consistency). A bundle with the same recipient but a higher amount passes all checks. [8](#0-7) 

**`check_withdraw_chain_specific` is a no-op for Zcash:** No gas-increase enforcement exists on the RBF path for Zcash (unlike Bitcoin). [1](#0-0) 

**The fix exists only in the refund path:** `execute_refund_callback` explicitly asserts `psbt.get_orchard_output_amount() == refund_amount`. This guard is absent from `check_withdraw_psbt` and `check_withdraw_rbf_psbt_valid`. [4](#0-3) 

### Impact Explanation
The attacker burns `X` nZEC, but the signed Zcash transaction sends `X - withdraw_fee - min_btc_gas_fee` ZEC to the shielded pool instead of `X - withdraw_fee - original_gas_fee`. The difference (`original_gas_fee - min_btc_gas_fee`) is ZEC that should have returned to the bridge's UTXO pool as change but instead flows to the attacker's shielded address. Over repeated RBF calls the bridge's UTXO pool is drained by this delta per withdrawal, breaking custody/supply alignment: more ZEC leaves the bridge than nZEC was burned.

### Likelihood Explanation
The attack requires only that the user own a pending shielded withdrawal (a normal user action) and be able to construct a valid Orchard bundle for their own address with a higher amount — straightforward with any Zcash wallet SDK. No privileged role is needed. The only limit is `original_gas_fee - min_btc_gas_fee` per call, but this can be repeated across many withdrawals.

### Recommendation
Add an explicit amount check in `check_withdraw_psbt` (or in `check_psbt_chain_specific` for the Zcash path) mirroring the refund path:

```rust
if psbt.has_orchard_bundle() {
    let expected = amount - withdraw_fee - gas_fee;
    require!(
        psbt.get_orchard_output_amount() == expected,
        format!("Orchard amount ({}) != expected ({})",
                psbt.get_orchard_output_amount(), expected)
    );
}
```

This is exactly the pattern already used in `execute_refund_callback`. [4](#0-3) 

### Proof of Concept
1. Alice deposits 500 000 zatoshis into the bridge.
2. Alice initiates a shielded withdrawal of 200 000 nZEC with `original_gas_fee = 14 000`, `withdraw_fee = 2 000`, so `original_orchard_amount = 184 000`. The original PSBT is stored.
3. Alice constructs a new valid Orchard bundle for the same recipient UA but with `orchard_amount = 184 000 + (14 000 - min_btc_gas_fee)` (e.g., `min_btc_gas_fee = 5 000` → new amount = `193 000`).
4. Alice calls `withdraw_rbf(original_id, same_change_output, new_chain_specific_data)`.
5. `withdraw_rbf_callback` builds a new PSBT via `from_original_psbt` with the inflated bundle.
6. `check_withdraw_psbt` computes `gas_fee = 500 000 - 307 000 - 193 000 = 0`... wait, let me redo with change output.

Concrete numbers (UTXO = 500 000, change = 307 000, original orchard = 184 000, original gas = 9 000, min_gas = 5 000):
- Attacker sets `new_orchard_amount = 188 000` (increase by 4 000), keeps `change = 307 000`
- `new_gas_fee = 500 000 - 307 000 - 188 000 = 5 000` (= `min_btc_gas_fee`, passes)
- `max_received_amount = 200 000 - 2 000 - 5 000 = 193 000 >= 188 000` ✓ (circular, always passes)
- `validate_orchard_bundle`: recipient matches ✓, `value_balance = -188 000` ✓
- Transaction is accepted; bridge signs and broadcasts a Zcash tx sending 188 000 zatoshis to Alice's shielded address instead of 184 000
- Bridge UTXO pool receives 307 000 change instead of 307 000 — but Alice received 4 000 extra ZEC that was not backed by burned nZEC
- `assert psbt.get_orchard_output_amount() > transfer_amount - gas_fee` → `188 000 > 184 000` ✓

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())

            expiry_height,
            vin: original_psbt.vin,
            vout,
            inputs_utxo: original_psbt.inputs_utxo,
            orchard,
            recipient_address: original_psbt.recipient_address,
