### Title
`safe_mint` Unconditionally Mints to Bridge Before Checking Recipient Registration, Permanently Locking User Funds - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC contract mints tokens to `bridge_id` **before** checking whether the recipient account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the already-minted tokens, leaving them permanently stuck in the bridge's nBTC balance while the user's BTC remains locked in the bridge's UTXO pool.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` performs two logically paired operations — mint to bridge, then transfer to user — but the second step is silently skipped when the recipient is unregistered, while the first step always executes:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← always executes

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← early return, tokens stuck
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

This is the direct analog of the vMaia `forfeitBoost` bug: one half of a paired operation (`internal_deposit` to bridge) always runs, while the corresponding half (transfer to user) is silently skipped when the account is absent. The non-safe sibling `mint` correctly handles this via `mint_inner`, which auto-registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id); // ← auto-registers
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
}
```

`safe_mint` lacks this guard, so the "claim" step (deposit to bridge) runs without the "deliver" step (transfer to user), creating an irrecoverable accounting mismatch.

---

### Impact Explanation

- The user's BTC is permanently locked in the bridge's UTXO pool — the deposit proof is consumed and cannot be resubmitted.
- The minted nBTC accumulates in `bridge_id`'s balance with no corresponding user entitlement, inflating the bridge's nBTC holdings above what is owed to users.
- The user has no on-chain recovery path; only privileged operator intervention could attempt remediation.
- This constitutes permanent loss of user funds and a broken 1:1 backing invariant.

**Severity: Medium** — stuck bridge state requiring operator intervention; permanent locking of bridged user funds.

---

### Likelihood Explanation

NEAR's NEP-141 storage model requires recipients to call `storage_deposit` before receiving tokens. A user who sends BTC to the bridge's deposit address without first registering on the nBTC contract — a realistic scenario for new users unfamiliar with NEAR's storage model — will silently lose their entire deposit. No attacker action is required; the victim triggers the loss themselves through normal bridge usage.

---

### Recommendation

Move the registration check **before** `internal_deposit`, so no tokens are minted if the recipient is unregistered:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");

    // Guard BEFORE minting — no tokens are created if recipient is absent
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

Alternatively, auto-register the account (matching `mint_inner` behavior) so no deposit is ever silently discarded.

---

### Proof of Concept

1. Alice sends 0.01 BTC to the bridge's deposit address.
2. Alice has **not** called `storage_deposit` on the nBTC contract — her account is unregistered.
3. A relayer submits the inclusion proof; the bridge verifies it and calls `safe_mint(alice.near, 1_000_000, None)`.
4. `internal_deposit(&bridge_id, 1_000_000)` executes — 1,000,000 nBTC is minted to the bridge. [1](#0-0) 
5. `self.token.accounts.get(&alice.near)` returns `None`. [2](#0-1) 
6. The function returns `U128(0)` — no transfer occurs.
7. Alice's 0.01 BTC is permanently locked in the bridge's UTXO pool; 1,000,000 nBTC is stuck in the bridge's balance with no owner.
8. The `mint` path, by contrast, would have auto-registered Alice and delivered the tokens. [3](#0-2)
