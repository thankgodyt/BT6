### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every inbound certificate, performing zero cryptographic, committee-membership, or quorum checks. Any unprivileged peer can inject an arbitrary `PerasCert` (pointing to any block) over the node-to-node `PerasCertDiffusion` mini-protocol, have it accepted as "validated," stored in the `PerasCertDB`, and used to influence chain selection — causing the honest node to prefer a non-canonical, attacker-chosen chain.

---

### Finding Description

The `BlockSupportsPeras` instance in `SupportsPeras.hs` is the universal production instance (via `instance StandardHash blk => BlockSupportsPeras blk`). Its `validatePerasCert` method is a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production inbound certificate handler. `makePerasCertPoolWriterFromChainDB` — the writer used by the live node-to-node `hPerasCertDiffusionClient` handler — passes `validatePerasCert mkPerasParams` as the validation function to `processCerts`:

```haskell

  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)

          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, adds them to the DB: [3](#0-2) 

This writer is registered as the live handler in `NodeToNode.hs`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

Once a certificate passes `validatePerasCert` (which it always does), it is added to the `PerasCertDB` via `addPerasCertAsync`, which enqueues a chain-selection event: [5](#0-4) 

The `PerasCert` type carries only a round number and a boosted block point — no signature field in the stub instance: [6](#0-5) 

There is no cryptographic signature, no committee membership proof, and no quorum check anywhere in this path.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

A Peras certificate boosts the weight of the block it references in chain selection. By injecting a fake certificate pointing to any block (including one on a minority fork), an attacker can cause the victim node to assign extra weight to that block and switch away from the canonical chain. This directly undermines the Peras protocol's safety guarantee, which is to accelerate finality by boosting the honest chain — not an attacker-chosen one.

---

### Likelihood Explanation

**High.** The attack requires only a standard node-to-node connection. The `PerasCertDiffusion` mini-protocol is open to any peer. No keys, stake, or privileged access are needed. The attacker constructs a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`, serializes it, and sends it. The stub `validatePerasCert` will accept it unconditionally.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs full cryptographic and protocol validation before the Peras certificate diffusion mini-protocol is enabled in production. At minimum, the validation must:

1. Verify the aggregate BLS signature over `(roundNo, boostedBlock)` against the claimed voter set.
2. Verify each voter's committee membership and eligibility proof (VRF output for non-persistent members).
3. Verify that the aggregate stake of the voter set exceeds the quorum threshold.
4. Verify that the boosted block is a known, valid block on a plausible chain.

Until this is implemented, the `PerasCertDiffusion` mini-protocol must not be enabled on production nodes. The existing `TODO` comment references issue `cardano-peras/issues/120` but the stub is already wired into the live network handler path. [7](#0-6) 

---

### Proof of Concept

**Private-testnet sequence:**

1. Start a node with the Peras certificate diffusion mini-protocol enabled (as wired in `NodeToNode.hs`).
2. Connect a malicious peer to the node.
3. The malicious peer sends a `PerasCert` message with:
   - `pcCertRound = <any round number not yet in the DB>`
   - `pcCertBoostedBlock = <point of a minority-fork block>`
4. The node's `hPerasCertDiffusionClient` handler calls `makePerasCertPoolWriterFromChainDB`, which calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{...}`.
5. The certificate is added to the `PerasCertDB` and `addPerasCertAsync` is called.
6. Chain selection runs and assigns the Peras weight boost to the minority-fork block.
7. If the boosted block's chain now has greater weight than the current selection, the node switches to the attacker's fork.

No cryptographic material, stake, or operator access is required at any step. [8](#0-7) [1](#0-0)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
