### Title
`revalidateHeader` Envelope Validation Result Silently Discarded in Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full envelope check (`validateEnvelope`) but wraps it in `assertWithMsg`, which is a **CPP-guarded no-op in production builds**. When the `ENABLE_ASSERTIONS` flag is absent (the default for production), the check result is unconditionally discarded and the function always returns a `HeaderState` regardless of whether the envelope validation passed or failed. This is the structural analog of the ERC20 missing-return-value pattern: a critical check is performed, its result is computed, but the result is never enforced in the production code path.

---

### Finding Description

`revalidateHeader` in `HeaderValidation.hs` is defined as:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck :: Either String ()
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [1](#0-0) 

`assertWithMsg` is defined with a CPP guard:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [2](#0-1) 

When `ENABLE_ASSERTIONS` is **not** defined — which is the default for production node builds, as the flag must be explicitly opted into via `cabal.project` — the `#if` branch is dead code. The fallthrough `assertWithMsg _ a = a` matches unconditionally, meaning the `Either String ()` result of `envelopeCheck` is evaluated but its value is **always discarded**. The `HeaderState` is returned regardless of whether `validateEnvelope` returned `Left` (failure) or `Right ()` (success).

The documentation itself confirms this is an opt-in debug facility, not a production control:

> "Even if the Consensus code is being benchmarked, it might be a good idea to *temporarily* enable assertions to perform additional checks on consistency." [3](#0-2) 

The envelope checks that are silently bypassed include: consecutive block numbers, monotonically increasing slot numbers, and the `prevHash` linkage check — all of which are the structural integrity checks that prevent a header from being grafted onto the wrong chain position. [4](#0-3) 

Additionally, `reupdateChainDepState` (called inside `revalidateHeader`) intentionally skips all cryptographic checks (KES, VRF) by design:

> "It is worth noting that since we already know that the header is valid w.r.t. the provided ChainDepState, no validation checks should be performed." [5](#0-4) 

This means `revalidateHeader` in production performs **zero enforcement** of any header validity property — neither envelope nor cryptographic.

---

### Impact Explanation

`revalidateHeader` is called during chain selection when re-applying previously-seen headers (e.g., when switching forks). The design invariant is that these headers were already validated by `validateHeader`. However, because the production build silently discards the envelope check, any scenario in which `revalidateHeader` is called with a header that does not match the expected `HeaderState` (wrong block number, wrong slot, wrong `prevHash`) will produce a silently corrupted `HeaderState` with the invalid header's tip recorded as `NotOrigin (getAnnTip hdr)`.

A corrupted `HeaderState` tip propagates forward: subsequent calls to `validateEnvelope` use `untickedHeaderStateTip st` as the `oldTip`, so a wrong tip causes all subsequent envelope checks to use an incorrect reference point. This can cause a node to accept a chain fragment that does not correctly extend its immutable tip, constituting a **chain-selection / header-state bug** that allows acceptance of an invalid chain without operator fault.

The impact class matches: **High — ChainDB or header-state bug that causes durable use of the wrong ledger state or permanent acceptance of a chain without operator fault.**

---

### Likelihood Explanation

The invariant that `revalidateHeader` is only called on previously-validated headers is maintained by the callers in `Extended.hs` under normal operation. The likelihood of the invariant being violated is low in a correctly-operating node. However:

1. The production build provides **zero enforcement** of the invariant at the call site — any future refactor or caller bug that passes an unvalidated header to `revalidateHeader` will be silently accepted in production while being caught in debug mode.
2. The `assertWithMsg` pattern is used in multiple security-critical paths in the same codebase (ChainSync client invariant checks, `withTime` fragment/history length check), all of which are similarly inert in production. [6](#0-5) 

The structural pattern — a check is computed, its result is wrapped in `Either`, and then passed to a function that silently ignores it in production — is the direct Haskell analog of the ERC20 `approve()` missing-return-value pattern.

---

### Recommendation

Replace the `assertWithMsg envelopeCheck` guard in `revalidateHeader` with an unconditional enforcement that is active in production. Since `revalidateHeader` is a pure function returning `HeaderState blk` (not in `Except`), the appropriate fix is to use `error` (or a dedicated `HasCallStack`-annotated panic) unconditionally when the envelope check fails, rather than gating it behind a CPP flag:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left msg -> error ("revalidateHeader: envelope invariant violated: " ++ msg)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

This preserves the performance intent (no `Except` monad overhead on the happy path) while ensuring the invariant is enforced in production, not just in assertion-enabled builds.

---

### Proof of Concept

In a production build (no `+asserts` flag), compile and call:

```haskell
-- Construct a HeaderState whose tip is at block N, slot S
-- Then call revalidateHeader with a header claiming block N+2 (skipping N+1)
-- validateEnvelope will return Left "UnexpectedBlockNo ..."
-- assertWithMsg discards the Left, returns HeaderState with block N+2 as tip
-- No exception is raised; the corrupted HeaderState is silently returned
let badState = revalidateHeader cfg ledgerView headerWithWrongBlockNo tickedState
-- badState now records the wrong block number as the chain tip
-- All subsequent validateEnvelope calls use this wrong tip as oldTip
```

The `validateEnvelope` call inside `envelopeCheck` would return `Left (show (UnexpectedBlockNo expected actual))`, but `assertWithMsg (Left _) result = result` (the production fallthrough) returns `HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'` unconditionally. [2](#0-1) [7](#0-6)
