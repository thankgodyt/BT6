Audit Report

## Title
ERC-1155 `safeTransferFrom` Callback Causes Permanent Fund Freeze in `finTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` marks the destination nonce as used at line 287 before executing the ERC-1155 delivery via `safeTransferFrom` at line 324. Because `safeTransferFrom` mandatorily invokes `onERC1155Received` on any contract recipient and reverts if the hook does not return the correct selector, a contract recipient that cannot receive ERC-1155 tokens causes the entire transaction to revert atomically—unwinding the nonce write. Since the recipient is immutably encoded in the MPC-signed payload and no rescue or re-routing mechanism exists, the bridged ERC-1155 tokens (whose NEAR-side counterparts are already burned) are permanently frozen in the bridge contract.

## Finding Description
In `finTransfer` (lines 283–330 of `OmniBridge.sol`):

```solidity
// line 287 — nonce marked BEFORE delivery
completedTransfers[payload.destinationNonce] = true;

// ... signature verification ...

// lines 323–330 — ERC-1155 delivery with mandatory callback
} else if (multiToken.tokenAddress != address(0)) {
    IERC1155(multiToken.tokenAddress).safeTransferFrom(
        address(this),
        payload.recipient,
        multiToken.tokenId,
        payload.amount,
        ""
    );
}
```

Per EIP-1155, `safeTransferFrom` MUST call `onERC1155Received` on any contract recipient and MUST revert if the hook does not return `bytes4(keccak256("onERC1155Received(address,address,uint256,uint256,bytes)"))`. If `payload.recipient` is a contract that:
- does not implement `IERC1155Receiver` (e.g., a Gnosis Safe prior to module support, a DAO governor, a DeFi vault), or
- deliberately reverts in `onERC1155Received`,

the `safeTransferFrom` call reverts. Solidity's atomicity unwinds the `completedTransfers` write, leaving the nonce unconsumed. However, `payload.recipient` is part of the Borsh-encoded message signed by `nearBridgeDerivedAddress` (line 311–313). No alternative recipient can be substituted without a fresh MPC signature. There is no admin rescue function, no pull-payment fallback, and no `claimTokens` path. The same structural flaw applies to the native-ETH branch (lines 317–322): `FailedToSendEther` reverts the transaction if the recipient rejects ETH.

The `evm/SECURITY.md` lists known low-severity issues but does not acknowledge this delivery-failure scenario. No existing guard prevents or recovers from a permanently failing delivery.

## Impact Explanation
The NEAR-side tokens are burned or locked at the time the user initiates the cross-chain transfer. If `finTransfer` can never succeed for a given MPC-signed payload, those assets are irrecoverably lost. This directly satisfies the allowed critical impact: **permanent freezing of bridged funds across NEAR-to-EVM flows**. The bridge contract holds the ERC-1155 tokens indefinitely with no on-chain path to recover them.

## Likelihood Explanation
ERC-1155 transfers to contract addresses are a standard use case: users routinely bridge to multisig wallets, DAO treasuries, and DeFi vaults. A large fraction of such contracts do not implement `IERC1155Receiver`. No malicious intent is required—an ordinary user bridging to their team's Gnosis Safe (if it lacks the ERC-1155 module) triggers permanent loss. A deliberate attacker can additionally deploy a contract whose `onERC1155Received` conditionally reverts to permanently block specific transfers or extort the protocol. The condition is reachable by any unprivileged user through the normal `finTransfer` relayer flow.

## Recommendation
Replace `safeTransferFrom` with a pull-payment (escrow) pattern for contract recipients:

1. Wrap the `safeTransferFrom` call in a `try/catch`. On failure, credit `(multiToken.tokenAddress, multiToken.tokenId, payload.amount)` to a per-recipient claimable mapping instead of reverting.
2. Expose a `claimERC1155(address token, uint256 tokenId)` function that lets the intended recipient pull their tokens at any time.
3. Apply the same pattern to the native-ETH branch: on failed `.call`, credit the amount to a claimable-ETH mapping and expose a `claimETH()` function.
4. Ensure the nonce is consumed regardless of delivery success (which the current code already does structurally—the problem is that the revert undoes it), so the escrow credit is the definitive record.

## Proof of Concept
1. Deploy `MaliciousRecipient` on a local EVM fork—a contract whose `onERC1155Received` always reverts (or omits the function entirely).
2. On the NEAR side (or via a test harness), initiate a transfer of ERC-1155 token `(tokenAddress, tokenId=7)` specifying `recipient = MaliciousRecipient`. The MPC signs the `TransferMessagePayload`.
3. Call `OmniBridge.finTransfer(signature, payload)`.
4. Observe: execution reaches line 324 (`safeTransferFrom`), `MaliciousRecipient` reverts (or EIP-1155 reverts on missing selector), the entire transaction reverts, `completedTransfers[nonce]` remains `false`.
5. Attempt to call `finTransfer` again with the same MPC-signed payload—same result.
6. Attempt to call `finTransfer` with a different recipient—`InvalidSignature` is thrown because the payload hash changes.
7. Confirm: ERC-1155 tokens remain in `OmniBridge`, NEAR-side tokens are burned, no recovery path exists.

A Foundry invariant test can assert: *for any `finTransfer` call that reverts after line 287, the bridge's ERC-1155 balance must not increase and no claimable balance is recorded*—demonstrating the permanent lock.
