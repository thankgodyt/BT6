### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the codebase provides a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. This stub is wired directly into the production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`). Because no cryptographic or protocol checks are performed, any unprivileged peer can send crafted `PerasCert` messages that are accepted without question. Each accepted certificate adds a weight boost to an arbitrary block in the `PerasWeightSnapshot`. By sending certificates for multiple distinct round numbers all targeting the same fork block, an attacker can accumulate an unbounded weight boost on that block and cause the node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` class declares `validatePerasCert` as the cryptographic gate for inbound certificates. The only instance in the production codebase is a degenerate placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee-membership check, no round-eligibility check, and no quorum check is performed. Every certificate is accepted and assigned the full protocol-parameter weight boost.

**Production ingest path uses the stub**

`makePerasCertPoolWriterFromChainDB` — the function that processes inbound Peras certificates received from peers over the network — passes this stub directly as the validator:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate; if all pass (they always do), each is timestamped and forwarded to `addPerasCertAsync`. [3](#0-2) 

**`implAddCert` deduplicates only by round number**

Inside `PerasCertDB`, `implAddCert` rejects a certificate only if its `PerasRoundNo` is already present:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
``` [4](#0-3) 

There is no check that the boosted block is the same across rounds. An attacker can send N certificates for N distinct round numbers, all with `pcCertBoostedBlock` pointing to the same fork block. All N are accepted and stored.

**Weight snapshot feeds directly into chain selection**

`implGetWeightSnapshot` aggregates all stored certificates into a `PerasWeightSnapshot`:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [5](#0-4) 

This snapshot is read atomically at the start of every `chainSelectionForBlock` call:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [6](#0-5) 

`weightedSelectView` then computes the total weight of a candidate fragment as `BlockNo + weightBoostOfFragment`, and `preferCandidate` switches to the candidate if its total weight exceeds the current chain's:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ Comparing ...)
``` [7](#0-6) 

**`chainSelSync` triggers chain selection for the boosted block**

When a certificate is added via `addPerasCertAsync`, `chainSelSync` checks whether the boosted block is in the VolatileDB and, if so, calls `chainSelectionForBlock` for it:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [8](#0-7)

### Impact Explanation

An unprivileged peer can cause an honest node to abandon its canonical chain and adopt a fork by:

1. Identifying a fork block `B` that is present in the target node's VolatileDB but not on its current chain (observable via the ChainSync miniprotocol).
2. Sending N crafted `PerasCert` messages, each with a distinct `pcCertRound` and `pcCertBoostedBlock = blockPoint B`.
3. Each certificate passes `validatePerasCert` (always `Right`) and is stored in `PerasCertDB`.
4. The `PerasWeightSnapshot` now records block `B` with a cumulative weight boost of `N × perasWeight`.
5. `chainSelectionForBlock` is triggered for `B`; `weightedSelectView` computes the fork chain's total weight as `blockNo(B) + N × perasWeight`.
6. Once this exceeds the current chain's total weight, `preferCandidate` returns `ShouldSwitch` and the node switches to the fork.

This is a **Critical** bypass of Peras certificate verification: an unprivileged peer can make an honest node accept an invalid chain selection outcome, directly violating consensus safety.

---

### Likelihood Explanation

**High.** The attack requires only network access to the Peras certificate miniprotocol. No stake, no cryptographic keys, and no privileged access are needed. The attacker needs only to observe a fork block in the target's VolatileDB (trivially available via ChainSync) and send a small number of crafted certificate messages. The stub is the only instance in the codebase and is unconditionally used in the production path.

---

### Recommendation

1. **Implement real `validatePerasCert`**: verify the BLS aggregate signature, confirm each claimed voter was eligible for the round via VRF-based sortition, and confirm the total stake of the committee exceeds the quorum threshold.
2. **Until real validation is in place**: treat all inbound peer certificates as having zero weight boost (i.e., do not add them to the `PerasWeightSnapshot`), or gate the entire Peras certificate ingest path behind a feature flag that is disabled until validation is complete.
3. **Add a cross-round uniqueness check in `implAddCert`**: reject a certificate if a different certificate for the same boosted block already exists for a prior round, to prevent weight accumulation across rounds targeting the same block.

### Proof of Concept

```
Attacker                          Target Node
   |                                   |
   |-- PerasCert(round=1, block=B) --> |  validatePerasCert → Right ✓
   |-- PerasCert(round=2, block=B) --> |  validatePerasCert → Right ✓
   |-- PerasCert(round=3, block=B) --> |  validatePerasCert → Right ✓
   |         ...N times...             |
   |                                   |
   |                          PerasWeightSnapshot:
   |                            block B → N × perasWeight
   |                                   |
   |                          chainSelectionForBlock(B):
   |                            weight(fork) = blockNo(B) + N×perasWeight
   |                            weight(canon) = blockNo(tip)
   |                            if N×perasWeight > gap → ShouldSwitch
   |                                   |
   |                          Node switches to fork chain ← SAFETY VIOLATION
```

This is the consensus analog of the M-18 sandwich attack: instead of sandwiching a liquidity deposit to double-dip on pool rewards by controlling instantaneous pool state, the attacker floods the node with crafted certificates across multiple rounds to accumulate weight boosts on a fork block, exploiting the same absence of time-weighted or authenticity checks to manipulate the state used for a critical decision (chain selection instead of reward calculation).
