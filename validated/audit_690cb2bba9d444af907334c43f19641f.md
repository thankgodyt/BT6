### Title
Outbound Transfer with Sub-Unit Amount Becomes Permanently Wedged — (`near/omni-bridge/src/lib.rs`)

### Summary

A user can initiate an outbound transfer (NEAR → EVM/Solana/Starknet) with an amount that passes `init_transfer` validation but normalizes to zero on the destination chain. Once stored in `pending_transfers` and tokens burned/locked, the transfer can never be signed or cancelled, permanently freezing the user's funds.

### Finding Description

`init_transfer` enforces only `fee.fee < amount`, which allows a transfer where `amount - fee` is a positive but sub-unit value relative to the destination chain's decimal precision. [1](#0-0) 

`sign_transfer` later calls `normalize_amount` using floor division: [2](#0-1) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the result is `0`. `sign_transfer` then hard-panics: [3](#0-2) 

This panic is permanent — the same inputs will always produce the same result. There is no cancel or refund path for a pending outbound transfer. The only removal paths are:

- `sign_transfer_callback` — only reached on MPC signing success, which requires `sign_transfer` to not panic first.
- `claim_fee_callback` — requires a proof of a `FinTransfer` event on the destination chain, which can never exist because the transfer was never signed.
- `submit_transfer_to_utxo_chain_connector` — only for BTC/Zcash destinations. [4](#0-3) [5](#0-4) 

Meanwhile, `init_transfer_internal` has already burned (for deployed tokens) or locked the user's tokens: [6](#0-5) 

### Impact Explanation

The user's tokens are permanently burned or locked in the bridge with no recovery path. This is permanent freezing of bridged funds. The `update_transfer_fee` function can only increase the fee (enforced by `fee.fee >= current_fee.fee`), which makes `amount_without_fee` smaller — worsening the condition, not fixing it. [7](#0-6) 

### Likelihood Explanation

Any token whose NEAR-side decimals differ from its origin-chain decimals by a large factor (e.g., a token with 24 origin decimals bridged to an 18-decimal EVM representation, giving `diff = 6`) is affected. A user sending fewer than `10^6` base units (e.g., less than 1 token if the token has 6 significant digits) will trigger this. This is a realistic user error, especially for tokens with high decimal precision. The `normalize_amount` comment in `SECURITY.md` acknowledges dust truncation but only for the remainder case, not the total-amount-to-zero case. [8](#0-7) 

### Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before storing the transfer and burning/locking tokens:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the check already present in `sign_transfer` but must be enforced at creation time, before tokens are burned/locked and the transfer is stored.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 18` (diff = 6).
2. User calls `ft_transfer_call` with `amount = 500_000` (500,000 base units, less than `10^6`), `fee = 0`, destination = EVM address.
3. `init_transfer` passes: `fee (0) < amount (500_000)`. ✓
4. `init_transfer_internal` burns 500,000 tokens and stores the transfer in `pending_transfers`.
5. Relayer calls `sign_transfer`. `normalize_amount(500_000, diff=6)` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0)` panics → `InvalidAmountToTransfer`.
7. Transfer remains in `pending_transfers` forever. Tokens are gone. No cancel function exists. [9](#0-8) [10](#0-9)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
