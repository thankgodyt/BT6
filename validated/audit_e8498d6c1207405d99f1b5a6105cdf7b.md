Audit Report

## Title
Promise Result Unchecked in `is_refund_required` Causes Permanent Token Loss on Failed `ft_transfer`/`mint` — (`near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` returns `false` (no refund) without ever inspecting the promise result when `is_ft_transfer_call = false`, and also returns `false` when `env::promise_result_checked` returns `Err` in the `is_ft_transfer_call = true` branch. Because `add_fin_transfer` and `unlock_tokens_if_needed` are called before `send_tokens`, any failure of the token-delivery promise leaves the transfer permanently finalized with no tokens delivered and no state rollback.

## Finding Description

`process_fin_transfer_to_near` (lines 1867–1978) executes in this order:

1. `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (line 1875).
2. `unlock_tokens_if_needed` decrements `locked_tokens` (lines 1881–1885).
3. `send_tokens` dispatches `ft_transfer` (empty msg, non-deployed token), `mint` (deployed token, empty msg), `ft_transfer_call` (non-deployed, non-empty msg), or `mint(..., Some(msg))` (deployed, non-empty msg) (lines 1957–1977).
4. `fin_transfer_send_tokens_callback` is chained as the callback (lines 1967–1977).

`is_refund_required` (lines 1784–1804) has two silent "success" branches:

- **`is_ft_transfer_call = false`** (covers `ft_transfer` and `mint` with empty msg): returns `false` unconditionally — the promise result is never read.
- **`is_ft_transfer_call = true`, `Err(_)` arm** (covers `ft_transfer_call`/`mint` with non-empty msg when the promise itself panics): returns `false`.

When `is_refund_required` returns `false`, `fin_transfer_send_tokens_callback`'s `else` branch (lines 1719–1746) only sends fees and emits `FinTransferEvent`. It does **not** call `revert_lock_actions` (which would re-increment `locked_tokens`) and does **not** call `remove_fin_transfer` (which would allow the proof to be re-submitted). The transfer ID remains in `finalised_transfers` permanently.

The same shared `is_refund_required` flaw propagates to `resolve_fast_transfer` (lines 895–912) and `resolve_utxo_fin_transfer` (lines 1016–1044).

## Impact Explanation

**Deployed (bridged) tokens:** Source-chain tokens are burned/locked when the user initiates the transfer. If `mint` on NEAR fails (promise-level failure), tokens are burned on the source chain and never minted on NEAR. The transfer ID is in `finalised_transfers`, so no relayer can re-submit the proof. Full transfer amount is permanently and irrecoverably lost — matching the critical impact class of permanent freezing/loss of bridged funds.

**Non-deployed (locked) tokens:** `locked_tokens` is decremented by `unlock_tokens_if_needed` before `ft_transfer` is called. If `ft_transfer` fails, `locked_tokens` is not restored, permanently corrupting the bridge's escrow accounting (under-counting locked tokens), which can enable subsequent over-minting on the source chain — matching the critical impact class of balance/escrow mis-accounting.

## Likelihood Explanation

Any promise-level failure of `ft_transfer`, `ft_transfer_call`, or `mint` triggers the bug. Realistic causes include: the token contract being paused by its owner between the storage-check promise and the transfer promise (a window that exists in every finalisation); a recipient account calling `storage_unregister` in that same window (NEP-141 permits this when balance is zero, which is the state before the inbound transfer arrives); or gas exhaustion inside the token contract's transfer logic. The window is narrow but the consequence is irreversible, and no admin rescue function exists in the contract.

## Recommendation

1. **Check the promise result unconditionally.** `is_refund_required` must call `env::promise_result_checked` even when `is_ft_transfer_call = false`, and treat `Err` as a delivery failure requiring refund/revert.
2. **Treat unexpected `Ok` deserialization failures as delivery failures.** The inner `else { false }` branch (line 1794) should also trigger a refund.
3. **On any delivery failure, fully revert state.** The `else` branch in `fin_transfer_send_tokens_callback` (and the analogous branches in `resolve_fast_transfer` / `resolve_utxo_fin_transfer`) must call `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent` — exactly as the existing refund path does — whenever the delivery promise fails for any reason.
4. **Consider moving `add_fin_transfer` after confirmed delivery**, or use a two-phase commit that only marks finalisation once the callback confirms success.

## Proof of Concept

```
1. User initiates transfer of 1000 USDC from Ethereum → NEAR (msg = "").
   Tokens are locked/burned on Ethereum.

2. Relayer calls fin_transfer() on NEAR.
   fin_transfer_callback() → process_fin_transfer_to_near():
     - add_fin_transfer(transfer_id)            // transfer_id now in finalised_transfers
     - unlock_tokens_if_needed(Eth, USDC, 1000) // locked_tokens[Eth][USDC] -= 1000
     - send_tokens(USDC, recipient, 1000, "")
         → ft_transfer(recipient, 1000, None)   // promise dispatched
         is_ft_transfer_call = false             // passed to callback

3. Between the storage-check promise and ft_transfer, the USDC token contract
   is paused by its owner (or recipient calls storage_unregister).

4. ft_transfer promise result = Err (panic in token contract).

5. fin_transfer_send_tokens_callback is called:
     is_ft_transfer_call = false
     is_refund_required(false) → false   // promise result never checked (line 1800-1802)
     else branch (lines 1719-1746):
       - fee sent to relayer (if fee > 0)
       - FinTransferEvent logged
       // revert_lock_actions NOT called → locked_tokens stays at -1000
       // remove_fin_transfer NOT called → transfer_id stays finalised

6. Result:
   - Recipient received 0 USDC.
   - transfer_id is in finalised_transfers → proof cannot be re-submitted.
   - locked_tokens[Eth][USDC] is 1000 less than actual bridge balance.
   - 1000 USDC are permanently inaccessible.
```

To reproduce locally: deploy the bridge and a pausable NEP-141 token contract on a NEAR sandbox; fund the bridge with the token; submit a `fin_transfer` proof; pause the token contract immediately after the storage-deposit promise resolves but before `ft_transfer` executes; observe that `fin_transfer_send_tokens_callback` logs `FinTransferEvent` (not `FailedFinTransferEvent`), `finalised_transfers` still contains the transfer ID, `locked_tokens` is decremented, and the recipient balance is unchanged.
