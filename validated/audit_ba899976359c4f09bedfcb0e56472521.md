### Title
`msg.value` Forwarded in Full After ETH Already Sent to Recipient in `finTransferExtension`, Permanently Blocking Native ETH Finalization - (`File: evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

---

### Summary

`OmniBridgeWormhole.finTransferExtension` forwards the full `msg.value` to Wormhole's `publishMessage`, but when `tokenAddress == address(0)` (native ETH), `finTransfer` has already spent `payload.amount` of that `msg.value` sending ETH to the recipient. The contract no longer holds enough ETH to cover `msg.value` when `finTransferExtension` executes, causing every native ETH finalization call to revert and permanently freezing bridged ETH funds.

---

### Finding Description

`OmniBridge.finTransfer` is `payable`. When `payload.tokenAddress == address(0)`, it first sends `payload.amount` ETH to `payload.recipient`:

```solidity
// OmniBridge.sol lines 317-322
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
```

After this transfer, the contract's remaining ETH balance is `msg.value - payload.amount`. Then `finTransferExtension(payload)` is called (line 357). In `OmniBridgeWormhole`, that override does:

```solidity
// OmniBridgeWormhole.sol lines 109-113
_wormhole.publishMessage{value: msg.value}(
    wormholeNonce,
    messagePayload,
    _consistencyLevel
);
```

`msg.value` here is the **original** full call value, not the remaining balance. The contract only holds `msg.value - payload.amount` at this point, so the `{value: msg.value}` sub-call reverts with an insufficient-balance error every time.

The developers correctly handled this pattern in `initTransferExtension`, which receives a pre-computed `value` parameter (`msg.value - amount - nativeFee` for ETH, or `msg.value - nativeFee` for ERC-20) and passes it to `publishMessage{value: value}`. That same discipline was not applied to `finTransferExtension`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

---

### Impact Explanation

Any cross-chain transfer of native ETH (or the native gas token of the destination chain) whose finalization goes through `OmniBridgeWormhole` (deployed on BNB, Arbitrum, Base, Polygon) will **always revert**. The user's tokens are already locked/burned on the source chain (NEAR or another EVM chain), but `finTransfer` can never succeed, so the funds are permanently frozen with no recovery path. This matches the "permanent freezing of bridged funds" critical impact class. [3](#0-2) 

---

### Likelihood Explanation

Any unprivileged relayer (or the user themselves) who attempts to finalize a native ETH transfer on `OmniBridgeWormhole` triggers this path. The entry point is the public `finTransfer` function. No special role or precondition is required beyond a valid MPC signature for a legitimate native ETH transfer. The condition `tokenAddress == address(0)` is a standard, documented bridge feature for native token transfers. [5](#0-4) 

---

### Recommendation

Mirror the `initTransferExtension` pattern: add a `value` parameter to `finTransferExtension` representing the ETH remaining after the recipient payment, and use it instead of `msg.value`.

In `OmniBridge.sol`, compute the remaining value before calling the extension:

```solidity
uint256 extensionValue = (payload.tokenAddress == address(0))
    ? msg.value - payload.amount
    : msg.value;
finTransferExtension(payload, extensionValue);
```

In `OmniBridgeWormhole.sol`, update the override signature and use the passed value:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload,
    uint256 value
) internal override {
    ...
    _wormhole.publishMessage{value: value}(...);
}
``` [6](#0-5) [7](#0-6) 

---

### Proof of Concept

1. Deploy `OmniBridgeWormhole` with a mock Wormhole that requires `messageFee() = 10_000 wei`.
2. A user bridges 1 ETH from NEAR to Arbitrum (native ETH, `tokenAddress = address(0)`).
3. A relayer calls `finTransfer` with `msg.value = 1 ETH + 10_000 wei` and a valid MPC signature.
4. `finTransfer` sends 1 ETH to `payload.recipient` — succeeds.
5. `finTransferExtension` attempts `_wormhole.publishMessage{value: 1 ETH + 10_000 wei}(...)` but the contract only holds `10_000 wei` — **reverts**.
6. The entire transaction reverts; `completedTransfers[nonce]` was set to `true` before the revert unwinds it, so the nonce is not consumed, but the user's ETH on NEAR is already locked with no finalization possible. [8](#0-7) [9](#0-8)
