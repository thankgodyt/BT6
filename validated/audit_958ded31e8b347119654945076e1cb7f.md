### Title
Publicly Callable `request_refund` Allows Frontrunning to Block Victim Refunds and Redirect Funds — (`File: contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`request_refund` enforces a strict one-per-UTXO constraint and is callable by any NEAR account. An attacker who observes a victim's pending `request_refund` call in the mempool can frontrun it with the same `deposit_msg` and proof but a different `refund_address`, permanently occupying the UTXO slot and blocking the victim's refund until a DAO/Operator manually rejects the malicious request.

### Finding Description

`request_refund` is a `#[payable]` public function with no per-caller access restriction on the individual function itself: [1](#0-0) 

The callback enforces a hard one-per-UTXO invariant: [2](#0-1) 

The UTXO key is deterministic (`{tx_id}@{vout}`), derived entirely from the public Bitcoin transaction: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, the caller supplies an arbitrary `refund_address` that is stored verbatim in the `RefundRequest`: [4](#0-3) [5](#0-4) 

An attacker who sees the victim's `request_refund` transaction in the NEAR mempool can copy the `deposit_msg`, `tx_bytes`, `vout`, and `proof` (all public), substitute their own `refund_address`, and submit first. The victim's subsequent call fails with `"Refund request already exists for this UTXO"`. The stored request now carries the attacker's address.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone: [6](#0-5) [7](#0-6) 

The refund PSBT is built to pay the stored `refund_address` — the attacker's address — and the resulting pending transaction enters the MPC signing pipeline: [8](#0-7) 

The only recovery path is a DAO/Operator `reject_refund` call before `execute_refund` is triggered: [9](#0-8) 

### Impact Explanation

**Medium.** The immediate, guaranteed impact is that the victim's deposit UTXO is locked in a malicious refund request, requiring DAO/Operator intervention (`reject_refund`) before the victim can re-submit. This is a "stuck bridge state requiring operator intervention." If the operator window is missed (e.g., during off-hours or under a coordinated spam campaign across many UTXOs), `execute_refund` can be called to route the BTC to the attacker's address — escalating to a Critical theft of user funds.

### Likelihood Explanation

**Medium.** The attack requires only:
1. Watching the public NEAR mempool for `request_refund` calls.
2. Copying the `deposit_msg`, `tx_bytes`, `vout`, and `proof` fields verbatim.
3. Substituting a different `refund_address`.
4. Paying the `required_balance_for_request_refund` storage deposit.

No privileged key or special role is needed. The attacker can target any deposit whose `deposit_msg.refund_address` is `None`. The cost is the storage deposit; the benefit is either blocking a competitor's refund or, if the operator window is missed, stealing the BTC.

### Recommendation

1. **Bind `refund_address` to the caller or the deposit recipient**: Only allow `request_refund` to be submitted by the original `deposit_msg.recipient_id` or require `deposit_msg.refund_address` to be pre-set (non-`None`), so the attacker cannot substitute their own address.
2. **Alternatively, restrict submission to trusted relayers**: Gate `request_refund` with `#[trusted_relayer]` on the individual function (as is done for `verify_deposit_v2`) so arbitrary accounts cannot submit.
3. **Emit an on-chain alert** when a refund request is submitted for a UTXO that already has a pending request, to aid operator monitoring.

### Proof of Concept

1. Alice deposits BTC to the bridge with `deposit_msg.refund_address = None` and her BTC address as `refund_address`.
2. Alice calls `request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)`.
3. Attacker observes Alice's pending NEAR transaction in the mempool.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with higher gas priority.
5. Attacker's transaction lands first; `refund_requests[utxo_key].refund_address = attacker_btc_addr`.
6. Alice's transaction fails: `"Refund request already exists for this UTXO"`.
7. Alice's BTC is now locked. DAO/Operator must call `reject_refund(utxo_key)` to unblock her.
8. If the operator does not act before `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund(utxo_key, None)`, the PSBT is built paying `attacker_btc_addr`, MPC signs it, and Alice's BTC is sent to the attacker.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
