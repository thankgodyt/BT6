### Title
Token Supply Inflation via Race Condition in `migrate_to_new_token` — (File: `contracts/satoshi-bridge/src/nbtc/migration.rs`)

### Summary

The `migrate_to_new_token` flow snapshots old-token balances via asynchronous cross-contract queries, then mints equivalent amounts on the new token in a separate callback transaction. Because NEAR cross-contract calls are not atomic, a `verify_withdraw` burn can execute on the old token between the balance snapshot and the mint, causing the new token to be over-minted by the burned amount. The resulting surplus tokens are permanently stuck in the bridge's balance with no on-chain mechanism to resolve them — an exact analog of the M-04 "unresolvable system debt" pattern.

---

### Finding Description

`internal_migrate_to_new_token` issues parallel `ft_total_supply` and `ft_balance_of` queries against the old token, then chains a callback `migrate_to_new_token_mint` that mints the snapshot amounts on the new token: [1](#0-0) 

The queries and the mint callback execute in **separate NEAR transactions**. Between those two transactions, any whitelisted relayer can call `verify_withdraw`, which triggers `verify_withdraw_burn_promise` → `burn()` on the **old** token, reducing the bridge's old-token balance by `burn_amount`: [2](#0-1) 

The `burn()` function in the nbtc contract withdraws `burn_amount` from the bridge's balance on the **old** token: [3](#0-2) 

When `migrate_to_new_token_mint` fires, it uses the **pre-burn snapshot** values. The check `sum == total_supply` passes because both `sum` and `total_supply` were captured before the burn: [4](#0-3) 

The mint batch then mints the bridge's **pre-burn** balance on the new token: [5](#0-4) 

After `migrate_to_new_token_resolve` succeeds, `nbtc_account_id` is updated to the new token: [6](#0-5) 

**Net result:** The new token's bridge balance is inflated by `burn_amount` (the amount burned on the old token during the race window). The BTC corresponding to that burn has already been released on-chain. The new token now has `burn_amount` tokens in the bridge's balance that are not backed by any BTC UTXO.

There is no on-chain function to burn tokens from the bridge's balance without a corresponding verified BTC transaction. The bridge's `burn()` call path requires a confirmed BTC tx proof via `verify_withdraw`: [2](#0-1) 

The `ContractData` has no admin burn or "repay surplus" function: [7](#0-6) 

The surplus tokens are permanently stuck in the bridge's balance, inflating the new token's total supply above the BTC backing — an unresolvable accounting discrepancy with no on-chain remedy, directly analogous to M-04's "system debt with no repayment mechanism."

---

### Impact Explanation

**Medium.** The new token's `ft_total_supply()` permanently exceeds the BTC locked in bridge UTXOs by `burn_amount`. The surplus tokens reside in the bridge's balance and cannot be burned, transferred to users, or otherwise resolved without a contract upgrade. This constitutes a "permanent burning below backed supply" and a "stuck bridge state requiring operator intervention." No user funds are directly stolen, but the nBTC/nZEC peg invariant is broken for the new token.

---

### Likelihood Explanation

**Low-Medium.** Migration is a rare, privileged operation (`MigrationOperator` or `DAO` role). However, the race window spans multiple NEAR blocks (the time for parallel `ft_balance_of` queries to resolve), and whitelisted relayers routinely call `verify_withdraw` as part of normal bridge operation. No malicious intent is required — a relayer processing a legitimate pending withdrawal during migration is sufficient to trigger the discrepancy. The more pending withdrawals exist at migration time, the wider the exposure.

---

### Recommendation

1. **Pause the bridge before migration.** The `migrate_to_new_token` entry point should assert the bridge is paused (or pause it atomically) so that `verify_withdraw` and other burn-triggering paths cannot execute during the snapshot-to-mint window.
2. **Exclude the bridge's own balance from the migration snapshot.** Pending-withdrawal tokens held by the bridge are already accounted for by the `btc_pending_infos` state; they should be minted separately after all pending withdrawals are resolved, not included in the user-balance snapshot.
3. **Add an admin burn function.** Implement a DAO-gated function to burn surplus tokens from the bridge's balance, providing a recovery path if a discrepancy occurs.

---

### Proof of Concept

**Setup:** 10 BTC deposited; 1 BTC withdrawal pending (tokens transferred to bridge, BTC tx signed but not yet confirmed on NEAR).

1. DAO calls `migrate_to_new_token(new_token, [user_a, ..., bridge])`.
2. Bridge sends parallel queries: `ft_total_supply()` → 10 BTC, `ft_balance_of(bridge)` → 1 BTC (pending withdrawal tokens).
3. **Race:** Relayer calls `verify_withdraw(tx_id, proof)` → `burn(bridge, 1 BTC)` executes on old token. Bridge's old-token balance → 0.
4. `migrate_to_new_token_mint` callback fires with snapshot: bridge balance = 1 BTC, sum = 10 BTC = total_supply ✓.
5. Mints 1 BTC to bridge on new token. `nbtc_account_id` → new token.
6. **Result:** New token total supply = 10 BTC. BTC backing = 9 BTC (1 BTC already released). Bridge holds 1 BTC on new token with no corresponding UTXO and no on-chain burn path. [8](#0-7) [2](#0-1) [9](#0-8)

    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }

    pub fn verify_withdraw_burn_promise(&self, tx_id: String) -> Promise {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id);
        let config = self.internal_config();
        let (protocol_fee, relayer_fee) = config

        ext_nbtc::ext(config.nbtc_account_id.clone())
            .with_static_gas(GAS_FOR_BURN_CALL)
