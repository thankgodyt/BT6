Audit Report

## Title
Permanent Fund Freeze via u128→u64 Overflow in `FinalizeTransfer::process` with No NEAR-Side Upper-Bound Guard — (`solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

## Summary

`FinalizeTransferPayload.amount` is typed as `u128`, but Solana SPL token operations require `u64`. NEAR's `sign_transfer` path normalizes the transfer amount to `u128` and places it into the MPC-signed payload with no check that the result fits in `u64`. When the normalized amount exceeds `u64::MAX`, every call to `finalize_transfer` on Solana returns `AmountOverflow` (error 6010). Solana's transaction atomicity rolls back `use_nonce`, so the nonce is never permanently consumed, but the transfer can never succeed, permanently locking the user's funds on NEAR with no visible refund path.

## Finding Description

`FinalizeTransferPayload` carries `amount: u128` at `solana/programs/bridge_token_factory/src/state/message/finalize_transfer.rs` lines 10–16.

In `FinalizeTransfer::process` (`finalize_transfer.rs` lines 91–99), `UsedNonces::use_nonce` is called first. The narrowing cast `data.amount.try_into().map_err(|_| error!(ErrorCode::AmountOverflow))?` is attempted afterward at lines 114 and 134. The same ordering exists in `FinalizeTransferSol::process` (`finalize_transfer_sol.rs` lines 69–77 for `use_nonce`, line 88 for the cast). Because Solana rolls back the entire transaction on error, the nonce bit is never permanently set — but the payload is MPC-signed and immutable, so every retry fails identically.

On the NEAR side, `sign_transfer` (`near/omni-bridge/src/lib.rs` lines 475–496) calls `normalize_amount` (lines 2784–2787), which performs pure floor-division returning `u128`, and places the result directly into `TransferMessagePayload` as `U128(amount_to_transfer)`. The only guard present is `require!(amount_to_transfer > 0, ...)` — there is no `require!(amount_to_transfer <= u64::MAX as u128, ...)` anywhere in the signing path.

For tokens where `origin_decimals == decimals` (no normalization), the overflow threshold is `u64::MAX` raw base units. For a token with 18 decimals on both sides, this is only ~18.45 tokens — trivially reachable by any ordinary holder. For tokens with 18 origin decimals and 9 Solana decimals, the threshold is ~18.45 billion tokens, reachable for high-supply tokens.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing of bridged funds**. Once NEAR locks the funds and MPC signs the payload, the transfer is unfinalizeable on Solana. No NEAR-side timeout or refund mechanism is visible in the contract. The user's funds are permanently locked on NEAR with no recovery path.

## Likelihood Explanation

Any unprivileged token holder can trigger this by initiating a transfer whose normalized amount exceeds `u64::MAX`. No attacker action is required — a legitimate large transfer suffices. For tokens where `origin_decimals == decimals` and decimals is large (e.g., 18), the threshold is as low as ~18.45 tokens, making this trivially reachable. For tokens with higher origin decimals than Solana decimals, the threshold scales up but remains reachable for high-supply tokens. The condition is deterministic and repeatable: every retry fails identically.

## Recommendation

Add a guard in `sign_transfer` on the NEAR side (`near/omni-bridge/src/lib.rs`) before MPC signing:

```rust
require!(
    amount_to_transfer <= u64::MAX as u128,
    BridgeError::AmountExceedsSolanaMax
);
```

This prevents the MPC from signing an unexecutable payload and allows NEAR to refund the user before funds are locked. Alternatively, add the check in `FinalizeTransfer::process` *before* `use_nonce` and ensure NEAR emits a refund event upon receiving the rejection, but the NEAR-side guard is strongly preferred as it prevents the lock entirely.

## Proof of Concept

The existing test at `solana/programs/bridge_token_factory/tests/mollusk/test_finalize_transfer_sol.rs` lines 212–223 already confirms the failure path: calling `finalize_transfer_sol` with `amount = u64::MAX + 1` produces `ProgramResult::Failure(ProgramError::Custom(6010))`.

To confirm permanent lock:
1. Call `finalize_transfer` (or `finalize_transfer_sol`) with `amount = u64::MAX + 1` in the signed payload.
2. Observe `ProgramResult::Failure(ProgramError::Custom(6010))`.
3. Verify the nonce account bit remains unset (rolled back by Solana atomicity).
4. Repeat — fails identically every time.
5. Confirm no NEAR-side refund event is emitted and the transfer remains in locked state indefinitely.
