### Title
Missing Zero-Stake Guard in `validatePerasVote` Enables Unauthorized Zero-Weight Peras Vote Acceptance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` function accepts Peras votes from any voter present in the `PerasVoteStakeDistr` map, regardless of whether their recorded stake is zero. An unprivileged peer can craft and submit a vote on behalf of a zero-stake voter ID that exists in the distribution; the node accepts and stores it as a `ValidatedPerasVote` without error. The sibling `EveryoneVotes` committee implementation explicitly guards against this with a `nonZero` check and returns `PoolHasNoStake`, but the degenerate instance — which is the only live production instance — omits this guard entirely.

---

### Finding Description

`validatePerasVote` in the catch-all `BlockSupportsPeras` instance resolves the voter's stake via `lookupPerasVoteStake`, which is a plain `Map.lookup`:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
```

`PerasVoteStake` is a `Rational` newtype with no non-zero invariant. If the map contains an entry `(voterId, PerasVoteStake 0)`, the lookup returns `Just (PerasVoteStake 0)`, and `validatePerasVote` immediately wraps it into a `Right ValidatedPerasVote` without any further check:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The `EveryoneVotes` implementation, by contrast, explicitly rejects zero-stake voters after verifying the signature:

```haskell
case nonZero voterStake of
  Nothing -> Left (PoolHasNoStake seatIndex)
  Just nonZeroVoterStake -> pure $ EveryoneVotesMember seatIndex nonZeroVoterStake
``` [2](#0-1) 

The degenerate instance is the only `BlockSupportsPeras` instance in the codebase (it is a catch-all `instance StandardHash blk => BlockSupportsPeras blk`). It is wired directly into the production vote-ingestion path via `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` disconnects a peer only when validation returns `Left`; a zero-stake vote returns `Right`, so the peer is not penalised and the vote is forwarded to `ChainDB.addPerasVoteWithAsyncCertHandling`. [4](#0-3) 

---

### Impact Explanation

A zero-stake `ValidatedPerasVote` is stored in the `PerasVoteDB` and propagated to other peers as a legitimately validated vote. The `votesReachQuorum` / `stakeAboveThreshold` path sums `vpvVoteStake` values; with the production default of `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`, a single zero-stake vote cannot alone forge a certificate. [5](#0-4) 

However, the bypass is a direct violation of the Peras voting check invariant: a voter with no stake is not a legitimate committee member and must not produce an accepted `ValidatedPerasVote`. The `ValidatedPerasVote` wrapper is the trust boundary used by downstream aggregation (`updatePerasRoundVoteStates`, `votesReachQuorum`) and by the `PerasVoteDB` model to track per-round quorum state. Accepting zero-stake votes corrupts the per-round tally, occupies vote-DB slots under a voter identity that should be ineligible, and — if the `PerasVoteStakeDistr` is ever populated with zero-stake entries due to a ledger edge case or a future code path — could be chained with other votes to reach quorum for an adversarially chosen block target. [6](#0-5) 

---

### Likelihood Explanation

The attack requires a voter ID to appear in the `PerasVoteStakeDistr` with a zero `PerasVoteStake` value. The `PerasVoteStakeDistr` type (`Map PerasVoterId PerasVoteStake`) carries no non-zero invariant, and `PerasVoteStake` is a plain `Rational`. Any code path that populates the distribution from a ledger snapshot without filtering out zero-stake entries would expose the vulnerability. An unprivileged peer that knows such a voter ID can submit a syntactically valid `PerasVote` message; the receiving node's `processVotes` handler will accept it without disconnecting the peer. [7](#0-6) 

---

### Recommendation

Mirror the `EveryoneVotes` guard in `validatePerasVote`: after a successful `lookupPerasVoteStake`, check `nonZero stake` and return a dedicated error (e.g., `PerasValidationErrZeroStake`) when the result is `Nothing`. Additionally, enforce the non-zero invariant at the `PerasVoteStakeDistr` construction site so that zero-stake entries are never inserted into the map.

---

### Proof of Concept

1. Populate `PerasVoteStakeDistr` with an entry `(targetVoterId, PerasVoteStake 0)`.
2. Construct a `PerasVote` with `pvVoteVoterId = targetVoterId` for any round and block point.
3. Call `validatePerasVote mkPerasParams distr vote`.
4. Observe `Right (ValidatedPerasVote { vpvVoteStake = PerasVoteStake 0 })` — the vote is accepted.
5. Feed this vote through `processVotes` (as a remote peer would via the object-diffusion mini-protocol); observe it is stored in the `PerasVoteDB` without triggering peer disconnection.

Contrast with `implVerifyVote` in `EveryoneVotes.hs`, which returns `Left (PoolHasNoStake seatIndex)` for the identical zero-stake scenario. [8](#0-7)
