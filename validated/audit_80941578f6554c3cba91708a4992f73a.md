### Title
Placeholder `validatePerasCert` Parameters Allow Peer-Injected Peras Certificates with Arbitrary Boost to Manipulate Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The Peras certificate ingest path in `processCerts` calls `validatePerasCert mkPerasParams` using a hardcoded placeholder parameter set instead of the actual ledger-derived committee parameters. This is explicitly marked as a TODO. Additionally, `implAddCert` in `PerasCertDB/Impl.hs` carries a second TODO acknowledging that "non-trivial validation logic" has not yet been implemented. Because `ValidatedPerasCert` carries a `vpcCertBoost` field that is set during validation, an insufficiently validated certificate can carry an arbitrary weight boost. Any unprivileged peer can send such a certificate over the object-diffusion mini-protocol; if it passes the stub validator, it is stored in `PerasCertDB`, its boost is included in the `PerasWeightSnapshot`, and chain selection immediately re-runs using the inflated weight — potentially causing the node to switch to a non-canonical fork.

---

### Finding Description

**Root cause — placeholder validation parameters**

In `PerasCert.hs`, both pool-writer factories pass a hardcoded `mkPerasParams` to `validatePerasCert` instead of the actual epoch-specific committee parameters derived from the ledger:

```haskell
-- makePerasCertPoolWriterFromCertDB (line 103)
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place

-- makePerasCertPoolWriterFromChainDB (line 126)
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [1](#0-0) 

Because `validatePerasCert` receives a static, epoch-agnostic parameter set, it cannot verify that the certificate's aggregate BLS signature was produced by the actual voting committee for the current epoch. A certificate forged by a single peer (or carrying a fabricated `vpcCertBoost`) cannot be distinguished from a legitimate one.

**Root cause — missing DB-level validation**

`implAddCert` in `PerasCertDB/Impl.hs` carries an explicit TODO:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert :: ...
``` [2](#0-1) 

The current implementation performs only a round-number deduplication check; it does not verify the certificate's cryptographic content, committee membership, or that `vpcCertBoost` is consistent with the committee's aggregate stake.

**How the boost reaches chain selection**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every stored `ValidatedPerasCert`, summing `getPerasCertBoost cert` for each entry: [3](#0-2) 

`chainSelSync` then calls `PerasCertDB.addCert` and immediately triggers `chainSelectionForBlock` using the updated snapshot: [4](#0-3) 

`weightedSelectView` uses `weightBoostOfFragment` to compute the total weight of each candidate fragment, and `preferCandidate` switches to the heavier chain: [5](#0-4) 

**Attacker-controlled entry path**

Certificates arrive from any peer via the object-diffusion mini-protocol. `processCerts` is the sole gate before `addCert`: [6](#0-5) 

No privileged access is required; any connected peer can send a `PerasCert` message.

---

### Impact Explanation

**Severity: High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

Because `vpcCertBoost` is set during validation and the validator uses placeholder parameters, a malicious peer can craft a `PerasCert` whose boost value is not constrained by the actual committee stake. Once stored, the inflated boost is added to the `PerasWeightSnapshot`. Chain selection compares `wsvTotalWeight = blockNo + weightBoost`; a sufficiently large injected boost can make a shorter, non-canonical fork appear heavier than the honest chain, causing the node to roll back and adopt the adversarial fork. Under Peras, the security parameter `k` is interpreted as a maximum rollback *weight*, not just block count, so an inflated boost can exceed `k` and force a rollback that would otherwise be impossible. [7](#0-6) 

---

### Likelihood Explanation

- The TODO comments in both `PerasCert.hs` and `PerasCertDB/Impl.hs` confirm the validation is intentionally incomplete and not yet production-ready.
- The entry point (object-diffusion mini-protocol) is reachable by any peer without authentication.
- The exploit requires only sending a well-formed `PerasCert` struct with an inflated `vpcCertBoost`; no cryptographic key material is needed if the stub validator does not check the aggregate signature against the actual committee.
- Peras is currently disabled by default, which limits immediate exposure, but the vulnerable code path is present in the production binary and can be activated via configuration.

---

### Recommendation

1. **Replace `mkPerasParams` with ledger-derived parameters**: Pass the actual epoch-specific `PerasParams` (committee composition, voting thresholds, aggregate key material) to `validatePerasCert` so that the aggregate BLS signature is verified against the real committee.
2. **Implement `implAddCert` validation**: Complete the non-trivial validation logic referenced in the TODO at `PerasCertDB/Impl.hs:167`, including verifying that `vpcCertBoost` is consistent with the committee's aggregate stake and that no equivocation is present.
3. **Gate Peras cert acceptance on full cryptographic verification**: Until both TODOs are resolved, consider rejecting all inbound certificates at the network boundary rather than accepting them with a stub validator.

---

### Proof of Concept

1. Node A (honest) has current chain tip at block `B` (block number 100, weight 100).
2. Attacker peer sends a `PerasCert` for round `R` boosting block `B'` on a fork (block number 95, weight 95) with `vpcCertBoost = 10` (a value that exceeds the gap of 5).
3. `processCerts` calls `validatePerasCert mkPerasParams` — because `mkPerasParams` is a placeholder, the certificate passes without verifying the aggregate signature against the actual epoch committee.
4. `implAddCert` stores the certificate; `implGetWeightSnapshot` now returns a snapshot where `B'` has boost 10, giving it total weight `95 + 10 = 105 > 100`.
5. `chainSelSync` triggers `chainSelectionForBlock`; `preferCandidate` finds the fork heavier and switches Node A to the adversarial chain, rolling back 5 blocks.
6. The attacker can repeat with increasing boost values to force deeper rollbacks, up to the weight limit `k`.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert ::
  IOLike m =>
  PerasCertDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)
    pure addPerasCertRes

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14. In the latter case, the chain fragment has
-- total weight @2 + 2 * 14 = 30@.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
  deriving (Eq, Generic, NoThunks, ToCBOR, FromCBOR)
  deriving Show via Quiet SecurityParam

-- | The maximum amount of weight we can roll back.
maxRollbackWeight :: SecurityParam -> PerasWeight
maxRollbackWeight = PerasWeight . unNonZero . maxRollbacks
