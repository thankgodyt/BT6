### Title
Peras Certificate and Vote Validation Stubs Unconditionally Accept Any Input Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, and `validatePerasVote` without any cryptographic signature check. Because this default instance is the only one in the repository (via `instance StandardHash blk => BlockSupportsPeras blk`), any Peras-enabled node accepts every inbound certificate and every vote whose voter-ID appears in the stake distribution, regardless of whether the underlying cryptographic proof is valid. An unprivileged peer can therefore inject crafted certificates that add arbitrary weight boosts to attacker-chosen blocks, directly manipulating chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` never validates:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of its content, is returned as `ValidatedPerasCert` with the full configured boost weight. No round-number check, no quorum check, no signature check, no target-block existence check is performed. [1](#0-0) 

**Root cause — `validatePerasVote` skips signature verification:**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

Only the voter-ID's presence in the stake distribution is checked. The cryptographic witness (VRF proof, KES signature, or equivalent) is never verified. Any peer that knows a legitimate voter-ID can forge votes for that voter. [2](#0-1) 

**This is the only instance in the repository.** The declaration `instance StandardHash blk => BlockSupportsPeras blk` makes it the universal fallback for all block types, including the Cardano `HardForkBlock`. [3](#0-2) 

**Inbound certificate processing path:**

`processVotes` in `PerasVote.hs` calls the `validateVote` callback (which resolves to `validatePerasVote`) for every inbound vote batch. Any vote whose voter-ID is in the stake distribution is accepted and stored. [4](#0-3) 

**Inbound certificate → chain selection path:**

`chainSelSync` handles `ChainSelAddPerasCert` events. After a certificate passes `validatePerasCert` (which always succeeds), it is added to `PerasCertDB` and chain selection is immediately re-triggered for the boosted block. The weight boost is then applied in `weightedSelectView` / `weightBoostOfFragment`, which feeds directly into `preferAnchoredCandidate`. [5](#0-4) [6](#0-5) 

**Analog to the external report:**

The external report describes checks that are only performed when `needsPreSolver() == true` or `needsSolverPostCall() == true`, leaving other code paths unguarded. Here the analog is symmetric but more severe: the validation check is never performed at all — the conditional is permanently `True` (always accept). The incomplete-check pattern from the report maps directly onto the unconditional-accept pattern here.

---

### Impact Explanation

**Severity: High — chain selection manipulation via forged Peras certificates.**

A Peras certificate boosts the `PerasWeight` of a block, which is added to its `BlockNo` to form the `wsvTotalWeight` used in `preferAnchoredCandidate`. Because `validatePerasCert` always returns `Right`, an attacker can:

1. Craft a `PerasCert` whose `pcCertBoostedBlock` points to any block on a competing fork.
2. Send it to the victim node via the Peras certificate miniprotocol.
3. The certificate is accepted, stored, and the boosted block's weight is inflated by `perasWeight params`.
4. Chain selection re-runs; if the inflated weight makes the competing fork heavier than the current selection, the node switches to it.

This allows an unprivileged peer to make an honest node prefer a non-canonical or adversarially-chosen chain, violating the chain-selection security invariant of Ouroboros Praos/Peras. [7](#0-6) 

---

### Likelihood Explanation

**Medium.** The Peras miniprotocol and the `chainSelSync` certificate handler are present and wired into the node kernel. The vulnerability is reachable on any private testnet or staging environment where Peras is enabled. The attack requires only a network connection to the victim node — no keys, no stake, no privileged access. The only mitigating factor is that Peras is not yet deployed on Cardano mainnet; however, the code is production-grade and the issue is present in the repository as shipped.

---

### Recommendation

Replace the stub implementations with real cryptographic validation before enabling Peras on any network:

1. **`validatePerasCert`**: Verify that the certificate encodes a valid quorum of signatures over the claimed `(round, boostedBlock)` pair, that the round number is within the expected window, and that the aggregate stake of the signers meets the quorum threshold.

2. **`validatePerasVote`**: Verify the cryptographic witness (VRF proof or equivalent) that proves the voter was legitimately elected for the claimed round and that the signature over `(round, block, voterId)` is valid under the voter's registered key.

3. Track the open issue (`https://github.com/tweag/cardano-peras/issues/120`) and gate Peras activation on completion of both validations.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe the victim node's current chain tip at block `B_honest` (block number `N`).
2. Identify any block `B_adv` on a competing fork with block number `N - delta` (shorter chain).
3. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B_adv) }` for any round `r`.
4. Send this certificate to the victim node via the Peras certificate miniprotocol.
5. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. `chainSelSync` adds the certificate to `PerasCertDB` and calls `chainSelectionForBlock` for `B_adv`.
7. `weightBoostOfFragment` adds `perasWeight params` to every fragment containing `B_adv`.
8. If `perasWeight params > delta`, `preferAnchoredCandidate` returns `ShouldSwitch` for the adversarial fork, and the node switches chains. [1](#0-0) [8](#0-7) [9](#0-8)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
