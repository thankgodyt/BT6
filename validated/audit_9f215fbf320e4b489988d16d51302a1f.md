### Title
Peras Quorum Check Uses Absolute Stake Against Relative Threshold — Unit Mismatch Allows Single-Vote Certificate Forgery - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a hardcoded relative quorum threshold (`3/4 + 2/100 = 0.77`), but the function's own documentation acknowledges that the `PerasVoteStake` values stored in `PerasVoteStakeDistr` are absolute ledger stakes — not normalized. When the actual stake distribution is wired into the vote diffusion path (replacing the current placeholder `mempty`), any voter with absolute stake greater than `0.77` (i.e., essentially every stakepool) will trigger quorum with a single vote, allowing a single unprivileged peer to forge a Peras certificate for any block and boost it in chain selection.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the core Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The function's own TODO comment explicitly states the unit mismatch:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

The quorum threshold is hardcoded as a relative value `3/4` in `mkPerasParams`:

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2 / 100)
``` [2](#0-1) 

The `PerasVoteStake` type itself carries a comment acknowledging there is no agreed-upon normalization from absolute ledger stake to relative vote stake:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [3](#0-2) 

The default `validatePerasVote` instance assigns the raw value from `PerasVoteStakeDistr` directly to `vpvVoteStake` with no normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [4](#0-3) 

This raw stake flows directly into `votesReachQuorum` → `stakeAboveThreshold` and into `updateCandidateVoteState` → `votesReachQuorum`: [5](#0-4) 

The production vote diffusion path in `NodeToNode.hs` currently passes `pure (PerasVoteStakeDistr mempty)` as a placeholder, with a TODO noting it must be replaced with actual committee selection data:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [6](#0-5) 

When the actual ledger stake distribution is wired in (as the TODO requires), absolute stake values (e.g., lovelace amounts in the billions) will be compared directly against the relative threshold `0.77`. Every stakepool with any positive stake will satisfy `stake >= 0.77`, so `stakeAboveThreshold` will return `True` for the very first vote received, forging a certificate immediately.

### Impact Explanation

This is a **High** impact chain-selection bug. When the stake distribution placeholder is replaced with real data:

1. A single `PerasVote` message from any voter with positive ledger stake causes `stakeAboveThreshold` to return `True`.
2. `updateCandidateVoteState` calls `votesReachQuorum`, which calls `forgePerasCert`, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight = 15`.
3. The certificate is added to the `ChainDB`, boosting the voted block by 15 block-equivalents in `WeightedSelectView` chain selection.
4. An honest node will prefer the adversarially boosted chain over the canonical chain, constituting a chain-selection failure triggered by a single unprivileged peer message. [7](#0-6) 

### Likelihood Explanation

The vulnerability is latent but structurally certain: the TODO in `NodeToNode.hs` explicitly states the empty distribution must be replaced. The unit mismatch is acknowledged in the source code itself. No special attacker capability is needed beyond sending a valid `PerasVote` message via the vote diffusion mini-protocol with a voter ID present in the stake distribution.

### Recommendation

`stakeAboveThreshold` must normalize the accumulated `PerasVoteStake` before comparing it to the relative threshold. The function should either:

1. Accept the total stake distribution and compute `totalVoteStake / totalDistributionStake` before comparing to the threshold, or
2. Require that callers (e.g., `validatePerasVote`) normalize the stake at the point of validation, storing only relative values in `ValidatedPerasVote`.

The `PerasVoteStake` type should be split into distinct `AbsolutePerasVoteStake` and `RelativePerasVoteStake` newtypes to make the unit contract enforced by the type system rather than a comment.

### Proof of Concept

With a non-empty `PerasVoteStakeDistr` mapping voter `V` to absolute stake `s` (e.g., `s = 1_000_000_000` lovelace):

1. Peer sends `PerasVote { pvVoteRound = r, pvVoteBlock = b, pvVoteVoterId = V }`.
2. `validatePerasVote mkPerasParams stakeDistr vote` returns `Right ValidatedPerasVote { vpvVoteStake = PerasVoteStake (1_000_000_000 % 1) }`.
3. `votesReachQuorum cfg [validatedVote]` calls `stakeAboveThreshold cfg (PerasVoteStake (1_000_000_000 % 1))`.
4. `1_000_000_000 >= 3/4 + 2/100` evaluates to `True`.
5. `forgePerasCert` is called, producing a certificate boosting block `b` by `perasWeight = 15`.
6. `preferAnchoredCandidate` now prefers any chain containing `b` over chains of equal block count that lack the boost. [8](#0-7) [9](#0-8) [10](#0-9)
