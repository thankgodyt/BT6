### Title
Peras Vote Signature Verification Bypass via Stub `validatePerasVote` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasVote` implementation in the universal `BlockSupportsPeras` instance performs **no cryptographic signature verification**. The `PerasVote blk` data type carries no signature field, and validation only checks stake-distribution membership. When the stake distribution is non-empty — as explicitly planned for production Peras — any unprivileged peer can forge votes for any committee member, potentially accumulating fabricated quorum and causing a false `ValidatedPerasCert` to be generated and accepted by the node.

---

### Finding Description

The external report's vulnerability class is: **signature verification that binds only to a class of identity (the router contract) rather than to the specific originating party**, allowing any peer to replay or forge messages that pass validation.

The direct analog in Ouroboros Consensus is in the Peras vote diffusion path.

**1. The `PerasVote blk` stub type has no signature field.** [1](#0-0) 

The universal instance (`instance StandardHash blk => BlockSupportsPeras blk`) defines `PerasVote blk` as a plain record of `(pvVoteRound, pvVoteBlock, pvVoteVoterId)` with no cryptographic proof of authorship. Compare this to the separate `Peras.Vote.V1.PerasVote` type, which does carry a `pvSignature :: VoteSignature PerasBLSCrypto` field but is **not** wired into the `BlockSupportsPeras` instance.

**2. `validatePerasVote` performs no signature check — it only looks up the voter ID in the stake distribution.** [2](#0-1) 

The function accepts any `PerasVote` whose `pvVoteVoterId` appears in `PerasVoteStakeDistr`, returning a `ValidatedPerasVote` with the associated stake. There is no check that the vote was actually signed by the holder of the corresponding key. The `_params` argument is discarded entirely.

**3. The inbound vote processing path calls this stub directly.** [3](#0-2) 

`makePerasVotePoolWriterFromChainDB` — the production writer used in `NodeToNode.hs` — passes each inbound `PerasVote` to `validatePerasVote mkPerasParams sd vote`. If `sd` is non-empty, any vote whose `pvVoteVoterId` is present in `sd` is accepted and stored.

**4. The current mitigation is explicitly temporary.** [4](#0-3) 

The production wiring currently passes `(pure (PerasVoteStakeDistr mempty))`, which causes all votes to be rejected. The inline TODO comment explicitly states this will be replaced with real committee selection data once Peras plumbing is complete. At that point, the missing signature check becomes fully exploitable.

**5. `validatePerasCert` is equally unguarded — it unconditionally returns `Right`.** [5](#0-4) 

Any certificate received from a peer is accepted without any verification, compounding the vote-forgery risk.

---

### Impact Explanation

Once the stake distribution is populated (the stated production intent), an unprivileged peer can:

1. Enumerate committee members from the public stake distribution.
2. Construct `PerasVote blk` records for those members — no key material required, since the type carries no signature.
3. Send the batch via the `PerasVoteDiffusion` miniprotocol.
4. `processVotes` passes each vote through `validatePerasVote`, which accepts them based solely on stake-distribution membership.
5. The `PerasVoteDB` accumulates the forged votes; once their combined stake exceeds the quorum threshold, `updatePerasRoundVoteStates` triggers `forgeCert`, producing a `ValidatedPerasCert` for an attacker-chosen block. [6](#0-5) 

The resulting certificate boosts the attacker's chosen block, directly influencing chain selection. This is a **bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance** — matching the "Critical" tier of the allowed impact scope.

---

### Likelihood Explanation

**Medium** at present (the empty stake distribution blocks exploitation), escalating to **Critical** once Peras is fully wired. The TODO comment in the production `NodeToNode.hs` handler and the tracked issue (`https://github.com/tweag/cardano-peras/issues/120`) confirm this transition is planned. The attack requires only a network connection and knowledge of the public stake distribution — no privileged keys or operator access.

---

### Recommendation

1. **Add a signature field to `PerasVote blk`** in the universal `BlockSupportsPeras` instance, or gate the instance behind a feature flag that is only enabled when the full BLS-signed `Peras.Vote.V1.PerasVote` type is wired in.
2. **`validatePerasVote` must verify the BLS signature** against the voter's public key from the committee before returning `Right`. The `Peras.Vote.V1` module already has the correct `verifyVoteSignature` path via `CryptoSupportsVoteSigning`; it must be called here.
3. **`validatePerasCert` must not unconditionally return `Right`**; it must verify the aggregate BLS signature against the declared voter set.
4. Until the full validation is in place, the empty stake distribution guard should be enforced by a compile-time or runtime assertion, not left as an implicit side-effect of an uninitialized field.

---

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
