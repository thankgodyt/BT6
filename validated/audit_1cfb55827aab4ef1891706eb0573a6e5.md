### Title
Double-Execution of Zcash Shielded Refund via Different Caller Creates Competing BTCPendingInfo Entries for the Same UTXO — (`contracts/satoshi-bridge/src/zcash_utils/refund.rs` + `refund.rs`)

---

### Summary

`execute_refund` is a public, unpermissioned function. After the first execution sets `refund_request.executed = true` and inserts the UTXO key into `verified_deposit_utxo`, `load_refund_request_for_execute` explicitly allows re-execution. Because `get_pending_id()` for Zcash includes the Orchard bundle in the txid (ZIP-244), a second caller supplying a different Orchard bundle produces a different `btc_pending_id`, bypasses the `"pending info already exist"` guard, and creates a second `BTCPendingInfo` for the same UTXO.

---

### Finding Description

**Step 1 — First execution (Account A)**

`execute_refund` is public and payable with no ACL guard on the caller: [1](#0-0) 

`load_refund_request_for_execute` passes because `verified_deposit_utxo` does not yet contain the key: [2](#0-1) 

`finalize_refund_with_psbt` inserts a `BTCPendingInfo` keyed by `btc_pending_id = psbt.get_pending_id()`, adds the UTXO key to `verified_deposit_utxo`, and sets `refund_request.executed = true`: [3](#0-2) 

**Step 2 — Second execution (Account B, different Orchard bundle)**

After the first execution, the guard condition evaluates to `!true || true` = `true` — re-execution is explicitly permitted: [4](#0-3) 

The comment confirms this is intentional for consensus-branch-change recovery, but it does not restrict who the second caller may be.

**Step 3 — Different txid from different Orchard bundle**

`get_pending_id()` in the Zcash wrapper calls `get_zcash_tx().compute_txid()`, which builds a full v5 `TransactionData` including the Orchard bundle: [5](#0-4) [6](#0-5) 

Under ZIP-244, the Zcash v5 txid commits to the Orchard bundle. A different Orchard bundle (even one paying the same `refund_address`) produces a different txid, hence a different `btc_pending_id`.

**Step 4 — `require_pending_sign_capacity` does not block Account B**

The capacity check is per-caller account. Account B has zero pending entries, so `0 < 1` passes: [7](#0-6) 

**Step 5 — Second `BTCPendingInfo` inserted**

Because `btc_pending_id` differs, `btc_pending_infos.insert(...)` returns `None` and the `require!` passes, creating a second entry for the same UTXO: [8](#0-7) 

The Orchard bundle is validated to pay to `refund_request.refund_address`, so the recipient cannot be changed — but the second PSBT is a structurally distinct transaction that also spends the same UTXO.

---

### Impact Explanation

Two `BTCPendingInfo` entries now exist for the same deposit UTXO. Only one can ever confirm on-chain (the other is a double-spend). The stale entry persists until `internal_remove_refund_pending_tx_id` is called after the refund request is removed by `verify_refund_finalize_callback`. No fund theft is possible because the Orchard bundle recipient is validated against the fixed `refund_address`. The impact is a publicly reachable invariant violation and stuck bridge state requiring operator intervention.

**Impact: Low** — publicly reachable invariant-violation / stuck-state in production bridge paths without direct theft.

---

### Likelihood Explanation

`execute_refund` is fully public. Any NEAR account can call it after the timelock. Creating a second NEAR account costs fractions of a cent. The attacker only needs a valid Orchard bundle paying to the same `refund_address` (which is public on-chain from the `RefundRequested` event). Likelihood is **Medium** — trivially reachable by any observer of the chain.

---

### Recommendation

Before inserting a new `BTCPendingInfo` in `finalize_refund_with_psbt`, check whether a pending entry already exists for this UTXO (not just for this txid). One approach: when `refund_request.executed == true`, require the old `btc_pending_id` to be explicitly removed (or superseded) before a new one is created. Alternatively, restrict re-execution of an already-executed refund to the original caller stored in the `RefundRequest`, or to privileged roles only.

---

### Proof of Concept

```
1. Alice calls request_refund(utxo_storage_key=K) → RefundRequest stored, executed=false.
2. Timelock passes.
3. Alice calls execute_refund(K, orchard_bundle=B1):
   - load_refund_request_for_execute: verified_deposit_utxo∌K → passes.
   - finalize_refund_with_psbt: btc_pending_id=txid(B1) inserted, verified_deposit_utxo∋K, executed=true.
4. Attacker (Bob, fresh account) calls execute_refund(K, orchard_bundle=B2):
   - load_refund_request_for_execute: verified_deposit_utxo∋K BUT executed==true → passes.
   - execute_refund_callback builds PSBT with B2.
   - check_psbt_chain_specific validates B2 pays to refund_address → passes.
   - finalize_refund_with_psbt:
       require_pending_sign_capacity(Bob): 0 < 1 → passes.
       btc_pending_id = txid(B2) ≠ txid(B1).
       btc_pending_infos.insert(txid(B2), ...) → None → passes.
   → Second BTCPendingInfo created for UTXO K.
5. Bridge now has two competing refund PSBTs (txid(B1) and txid(B2)) for the same UTXO.
   Only one can confirm on-chain; the other is permanently stale until operator cleanup.
```

    pub fn get_zcash_tx(self) -> Transaction {
        let transparent_bundle = zcash_transparent::bundle::Bundle {
            vin: self.vin.clone(),
            vout: self.vout.clone(),
            authorization: zcash_transparent::bundle::Authorized,
        };

        // Here we encode the Zcash transaction with orchard bundle so it can be submited to the network
        let inner_tx = TransactionData::from_parts(
            TxVersion::V5,
            self.branch_id,
            0,
            BlockHeight::from(self.expiry_height),
            Some(transparent_bundle),
            None,
            None,
            self.orchard.map(|b| b.bundle),
        )
        .freeze()
        .unwrap_or_else(|_| {
            env::panic_str("ERR_TX_FREEZE: failed to freeze Zcash transaction data")
        });

        Transaction { inner_tx }
