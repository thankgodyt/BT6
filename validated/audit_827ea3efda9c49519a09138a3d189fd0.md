### Title
Hardcoded `EXPECTED_ACTIONS_NUMBER = 1` Rejects All Valid Orchard Bundles — (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary
`EXPECTED_ACTIONS_NUMBER` is hardcoded to `1` in `orchard_policy.rs`. The Orchard protocol enforces a minimum of **2 actions** per bundle (`MIN_ACTIONS = 2` in the `orchard` crate, referenced by the code's own comment). The `extract_orchard_bundle` function enforces an exact equality check against this constant, so every real Orchard bundle — which the builder pads to at least 2 actions — is unconditionally rejected. This permanently blocks all Zcash Orchard-address withdrawals.

---

### Finding Description
In `orchard_policy.rs`, the constant and its guard are:

```rust
pub const EXPECTED_ACTIONS_NUMBER: usize = 1;
...
if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
    return Err(format!(
        "Orchard bundle must have {} actions, got {}",
        EXPECTED_ACTIONS_NUMBER,
        bundle.actions().len()
    ));
}
```

The inline comment directly contradicts the value:

> "Minimum number of actions required in an Orchard bundle per the Orchard protocol. The Orchard builder automatically pads bundles to meet this minimum for privacy. See: https://github.com/zcash/orchard/blob/main/src/builder.rs#L36"

The referenced upstream constant (`MIN_ACTIONS`) is `2`. The Orchard builder always pads a bundle to at least 2 actions for privacy. Therefore any bundle produced by a standard Orchard client will have `actions().len() >= 2`, and the strict `!= 1` check will always return `Err(...)`.

This is the direct analog of the `TELLOR_DIGITS` bug: a hardcoded precision/count constant that was calibrated for one specific case (a single-action bundle) but is wrong for every real-world instance of the protocol it is supposed to handle.

---

### Impact Explanation
Every user who attempts a Zcash withdrawal to an Orchard (shielded) address triggers `extract_orchard_bundle`. The function returns an error for any bundle with ≥ 2 actions, which is every valid bundle. The PSBT construction or validation step that calls this function will panic or propagate the error, causing the `ft_on_transfer_callback` to fail. Under NEAR's `ft_transfer_call` resolver semantics, a failed callback causes the transferred nZEC to be returned to the user, so direct fund loss is avoided. However, **Orchard-address withdrawals are permanently and silently broken** for all users — a stuck bridge state that requires operator intervention to fix.

Impact: **Low–Medium** (publicly reachable stuck-state / broken callback in production Zcash bridge path; no direct theft, but Orchard withdrawals are entirely non-functional).

---

### Likelihood Explanation
Any unprivileged NEAR account holding nZEC who attempts to withdraw to a Zcash Unified Address with an Orchard receiver will hit this path. No special privileges or unusual conditions are required. The failure is deterministic and 100% reproducible.

---

### Recommendation
Change the constant to match the actual Orchard protocol minimum, or make it configurable:

```rust
// Correct: Orchard protocol MIN_ACTIONS = 2
pub const EXPECTED_ACTIONS_NUMBER: usize = 2;
```

Alternatively, relax the check to `bundle.actions().len() < EXPECTED_ACTIONS_NUMBER` (at-least semantics) if the bridge only needs to recover a single output from a multi-action bundle.

---

### Proof of Concept
1. User holds nZEC and calls `ft_transfer_call` on the nbtc contract, passing a `WithdrawMsg` targeting a Zcash Unified Address with an Orchard receiver and supplying a valid Orchard bundle (constructed by any standard Orchard client, which pads to 2 actions).
2. The bridge's `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `ft_on_transfer_callback` path is invoked.
3. Inside `ft_on_transfer_callback`, `PsbtWrapper::new` (or the subsequent `check_psbt_chain_specific` → `validate_orchard_bundle`) calls `extract_orchard_bundle`.
4. `bundle.actions().len()` returns `2` (the padded minimum); the check `2 != 1` is `true`; the function returns `Err("Orchard bundle must have 1 actions, got 2")`.
5. The callback panics/fails; the NEAR resolver returns nZEC to the user; the withdrawal is permanently blocked for all Orchard recipients. [1](#0-0) [2](#0-1) [3](#0-2)
