### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate from Any Peer — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that always returns `Right` without performing any cryptographic or authorization check. The `PerasCert` wire type itself carries no committee signature or eligibility proof. Because the active `hPerasCertDiffusionClient` handler in the node-to-node diffusion layer feeds inbound certificates directly through this stub validator, any unprivileged peer can inject arbitrary Peras certificates into a node's ChainDB, causing the node to apply weight boosts to attacker-chosen blocks during chain selection.

### Finding Description

**Root cause — stub validator that always succeeds**

The catch-all `BlockSupportsPeras` instance (the only instance in the codebase) provides a default `validatePerasCert` that unconditionally wraps every inbound certificate in `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature field exists on the wire type either:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

There is nothing to verify even if the stub were replaced — the certificate carries no committee proof at all.

**Attacker-controlled entry path — production node-to-node handler**

The `hPerasCertDiffusionClient` handler in the production node-to-node wiring passes inbound certificates directly to `makePerasCertPoolWriterFromChainDB`, which internally calls `validatePerasCert mkPerasParams` as its validator:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

`processCerts` in the cert pool module calls the supplied `validateCert` on every inbound certificate; if it returns `Right`, the certificate is timestamped and forwarded to `addCert` (i.e., `addPerasCertAsync` on the ChainDB): [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for chain selection processing: [5](#0-4) 

**Contrast with votes**

For votes, the production wiring deliberately passes `(pure (PerasVoteStakeDistr mempty))` — an empty distribution — so all inbound votes are rejected. No equivalent mitigation exists for certificates; `validatePerasCert` always succeeds regardless of the distribution or any other state. [6](#0-5) 

**End-to-end exploit path**

1. Attacker connects to a target node as an ordinary peer (no credentials required).
2. Attacker sends a crafted `PerasCert` message via the `PerasCertDiffusion` miniprotocol, naming any `pcCertRound` and any `pcCertBoostedBlock` (e.g., a block on a minority fork).
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert cert boost)` unconditionally.
4. The certificate is added to the ChainDB via `addPerasCertAsync`.
5. Chain selection applies the Peras weight boost (`perasWeight params`) to the attacker-chosen block, potentially making a minority fork heavier than the honest chain.
6. The node switches to the attacker's fork.

### Impact Explanation

This is a **Critical bypass of Peras certificate/vote verification** that enables unauthorized certificate acceptance. An unprivileged peer can make an honest node accept a fabricated Peras certificate for any block, injecting an illegitimate weight boost into chain selection. If the boosted block is on a minority or adversarial fork, the node will prefer that fork over the honest chain — a consensus safety failure reachable with zero privileges.

### Likelihood Explanation

The `hPerasCertDiffusionClient` handler is active in every node that runs the node-to-node stack. Any peer that can establish a connection (the normal Cardano peer-to-peer network) can send `PerasCert` messages. The exploit requires no key material, no stake, and no prior knowledge beyond the target node's address and the block hash to boost.

### Recommendation

1. **Immediate**: The `PerasCert` wire type must include a cryptographic aggregate committee signature (analogous to `AggregateVoteSignature` already present in `WFALSCert`/`EveryoneVotesCert`). Without a signature field there is nothing to verify.
2. **Short-term**: Replace the stub `validatePerasCert` with a real implementation that verifies committee membership, quorum, and the aggregate signature against the epoch's stake distribution — mirroring the pattern already implemented in `implVerifyCert` for `WFALS` and `EveryoneVotes`.
3. **Defensive**: Until real validation is in place, apply the same mitigation used for votes — reject all inbound certificates at the diffusion layer — to prevent the current unconditional acceptance.

### Proof of Concept

```
1. Start a local Cardano node (or private testnet node) with Peras diffusion enabled.
2. Connect a custom peer that speaks the PerasCertDiffusion miniprotocol.
3. Send a PerasCert message:
     PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <hash of minority fork tip> }
4. Observe: the node's ChainDB accepts the certificate (no error, no disconnect).
5. Observe: getLatestPerasCertSeen returns the injected certificate.
6. Observe: chain selection applies the Peras weight boost to the minority fork block,
   causing the node to prefer it over the honest chain tip.
```

The stub at `SupportsPeras.hs:353` (`validatePerasCert params cert = Right ...`) is the single necessary and sufficient condition for the bypass; no other check intervenes between the peer message and the ChainDB insertion. [7](#0-6)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
