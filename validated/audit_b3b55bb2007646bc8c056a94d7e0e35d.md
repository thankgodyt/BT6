### Title
VR-1A Voting Rule Uses Wrong Round Start Slot, Permanently Disabling Normal Peras Voting — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Voting/View.hs`)

---

### Summary

In `mkLatestCertSeenView` (inside `mkPerasVotingView`), the field `lcsRoundStartSlot` is computed as the start of the **certificate's own round** (round r−1) rather than the start of the **current round** (round r). The VR-1A check then compares the certificate's arrival slot against a deadline that is one full round length in the past, making VR-1A permanently false for every certificate. This completely disables the normal Peras voting path (VR-1), breaking the certificate-based chain-selection boosting mechanism.

---

### Finding Description

`LatestCertSeenView.lcsRoundStartSlot` is documented as:

> "Starting slot number of the round **where this certificate was received**"

meaning the start of the current round r (the round in which the voter receives the certificate for round r−1).

However, the field is populated in `mkLatestCertSeenView` as:

```haskell
lcsRoundStartSlot <- perasRoundStart (getPerasCertRound lcsCert)
```

`getPerasCertRound lcsCert` returns the round number **of the certificate** (round r−1), so `lcsRoundStartSlot` is actually `startSlot(r−1)` — one full round length earlier than the documented value.

The VR-1A sub-rule `vr1a2` then evaluates:

```haskell
lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X
-- i.e.  arrivalSlot  <=  startSlot(r−1)  +  X
```

A certificate for round r−1 can only be produced after quorum is reached in round r−1, so its earliest possible arrival slot is `startSlot(r−1) + roundLength`. With the default parameters `roundLength = 90` and `X = 30`:

```
arrivalSlot  >=  startSlot(r−1) + 90
threshold    =   startSlot(r−1) + 30
```

The check `arrivalSlot ≤ startSlot(r−1) + 30` is **always false**. VR-1A is permanently false for every non-`Origin` certificate.

The correct computation, consistent with both the field's own documentation and CIP-0140 VR-1A ("received in the first X slots after the start of the round"), is:

```haskell
lcsRoundStartSlot <- perasRoundStart currRoundNo   -- start of round r, not r−1
```

`currRoundNo` is already in scope inside `mkPerasVotingView`.

---

### Impact Explanation

VR-1A always false → VR-1 (= VR-1A ∧ VR-1B) always false → nodes can never vote via the normal "happy path". The only remaining path is VR-2 (cooldown exit), which requires waiting at least R = 487 rounds (≈ 43 830 slots ≈ 12 hours) before any vote can be cast, and then only at specific round offsets satisfying VR-2B. In practice this means:

- No Peras certificates are ever produced via the normal path.
- The chain-selection weight boost that Peras certificates provide is never applied.
- An adversary presenting a competing fork without Peras boosts faces no additional chain-selection penalty from the honest majority, weakening the security guarantees Peras is designed to provide.

This matches the **High** impact class: a chain-selection bug that lets an unprivileged peer (or simply the passage of time) cause honest nodes to operate without the intended Peras security margin.

---

### Likelihood Explanation

The bug is triggered unconditionally by normal protocol operation. Every node that evaluates `isPerasVotingAllowed` with a non-`Origin` `latestCertSeen` will hit the always-false VR-1A branch. No crafted message, special block, or adversarial stake is required. Any deployment of the Peras extension is affected from the first round onward.

---

### Recommendation

In `mkLatestCertSeenView` (inside `mkPerasVotingView`), replace:

```haskell
lcsRoundStartSlot <- perasRoundStart (getPerasCertRound lcsCert)
```

with:

```haskell
lcsRoundStartSlot <- perasRoundStart currRoundNo
```

`currRoundNo` is already a parameter of the enclosing `mkPerasVotingView` and is in scope. This aligns the field value with its documentation
