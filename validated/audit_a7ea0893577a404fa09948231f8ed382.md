Audit Report

## Title
Missing Pre-Transfer Normalization Guard Causes Permanent Fund Loss on NEAR → Foreign Chain Transfers - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` locks or burns user tokens without verifying that `(amount - fee)`, after decimal normalization, is non-zero on the destination chain. The guard that rejects a zero normalized amount exists only in `sign_transfer`, which is called later by a relayer. Any transfer whose net amount falls below the decimal-scaling threshold is permanently undeliverable, and the user's tokens are permanently lost with no on-chain recovery path.

## Finding Description

The outbound transfer lifecycle is split into two steps. In `init_transfer_internal` (lines 1829–1865), tokens are burned or locked unconditionally for any NEAR-native token, and `U128(0)` is returned (all tokens consumed): [1](#0-0) 

The only validation in `init_transfer` before this point is `fee < amount`: [2](#0-1) 

The normalization guard lives exclusively in `sign_transfer` (lines 475–485), called later by a trusted relayer: [3](#0-2) 

`normalize_amount` uses floor division: [4](#0-3) 

For a 24-decimal NEAR token bridging to an 18-decimal EVM chain, the divisor is `10^6`. Any `(amount - fee) < 1_000_000` normalizes to `0`, causing every subsequent `sign_transfer` call to revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`.

The only call to `remove_transfer_message` with refund semantics is inside `claim_fee_callback` (line 1094), which requires a proof of finalization on the destination chain — a proof that can never exist for a transfer that was never signed: [5](#0-4) 

No `cancel_transfer` function exists anywhere in the NEAR contract source. The pending transfer record remains in `pending_transfers` indefinitely, and the locked/burned tokens are unrecoverable.

The `normalize_amount` doc comment acknowledges that "dust stays locked/burned" when `fee = 0`, but references a SECURITY.md that contains no such documentation: [6](#0-5) [7](#0-6) 

The comment addresses remainder dust (a small fraction of a larger transfer), not the case where the entire normalized amount is zero — which makes the transfer wholly undeliverable.

## Impact Explanation

This is a permanent, irreversible loss of bridged funds. Tokens are locked or burned at `init_transfer` time; the pending transfer is stored but can never be signed (every `sign_transfer` call reverts); and no on-chain path exists to recover the funds. This matches the allowed Critical impact: **permanent freezing of bridged funds** and **decimal/normalization abuse that changes user balances**.

## Likelihood Explanation

The condition is reachable by any unprivileged user calling `ft_transfer_call` on any registered NEAR token whose `origin_decimals > dest_decimals`. For the common NEAR (24 decimals) → EVM (18 decimals) pair, the threshold is 1,000,000 base units (~$0.0001 at current prices). A user sending a small test transfer, or a UI that rounds down to a sub-threshold amount, triggers the bug. No special role or privilege is required. The exploit is repeatable and deterministic.

## Recommendation

Add the normalization check inside `init_transfer` (or `init_transfer_internal`) before tokens are locked or burned, mirroring the guard already present in `sign_transfer`:

```rust
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This ensures any transfer that would be undeliverable is rejected before funds are consumed.

## Proof of Concept

1. Register a NEAR token with `origin_decimals = 24`, `decimals = 18` for an EVM destination chain.
2. Call `ft_transfer_call` with `amount = 500_000` and `fee = 0`, targeting the EVM chain.
3. Observe: `ft_on_transfer` → `init_transfer` → `init_transfer_internal` succeeds; `burn_tokens_if_needed` fires; `U128(0)` is returned (all tokens consumed).
4. Trusted relayer calls `sign_transfer` for the resulting `TransferId`.
5. Observe: `normalize_amount(500_000, {origin_decimals:24, decimals:18}) = 500_000 / 1_000_000 = 0`; the `require!(amount_to_transfer > 0)` guard at line 482 panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. The transfer remains in `pending_transfers` indefinitely. No `cancel_transfer` exists. `remove_transfer_message` is only reachable via `claim_fee_callback`, which requires a destination-chain finalization proof that can never be produced. The user's 500,000 base-unit tokens are permanently lost.
