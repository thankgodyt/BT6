### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Permanently Disables Peras-Aware Chain Selection at Forecast-Horizon Disconnect Decision — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the production ChainSync client hardcodes `emptyPerasWeightSnapshot` when calling `preferAnchoredCandidate`, unconditionally ignoring all Peras certificate boosts. Every other chain-selection call site in the codebase reads the live `PerasWeightSnapshot` from the ChainDB. This single omission means the disconnect decision made at the forecast horizon is always computed as if Peras does not exist, which can cause an honest node to incorrectly disconnect from a peer serving the canonical Peras-weighted chain, or to fail to disconnect from a peer serving an inferior one.

---

### Finding Description

`checkPreferTheirsOverOurs` is called from `readLedgerStateHelper` whenever a peer's header is beyond the current forecast horizon and the node must block waiting for its own chain to advance. Its purpose is to guard against waiting indefinitely for a chain that will never be adopted: if the peer's candidate fragment is not preferable to the local selection, the client throws `CandidateTooSparse` and disconnects. [1](#0-0) 

The comparison is performed by `preferAnchoredCandidate`, which accepts a `PerasWeightSnapshot` parameter and uses it to compute the total Peras-boosted weight of each fragment. When the snapshot is non-empty, the function takes the `otherwise` branch and computes `weightedSelectView` for both fragments; when it is empty, it falls back to pure block-count comparison. [2](#0-1) 

In `checkPreferTheirsOverOurs`, the snapshot is hardcoded to `emptyPerasWeightSnapshot` with an explicit TODO acknowledging the problem: [3](#0-2) 

Every other production call site reads the live snapshot. In `NodeKernel.initNodeKernel`, the GSM's `getCandidateOverSelection` reads `ChainDB.getPerasWeightSnapshot chainDB` and passes `forgetFingerprint weights` to `preferAnchoredCandidate`: [4](#0-3) 

In `BlockFetch/ClientInterface.hs`, `readChainComparison` similarly reads the live snapshot: [5](#0-4) 

In `ChainSel.hs`, the `addBlockAsync` path also uses the live snapshot: [6](#0-5) 

`checkPreferTheirsOverOurs` is the sole production call site that hardcodes the empty snapshot, making it structurally identical to the external report's `isPaused` field: the mechanism exists and is wired correctly everywhere else, but is permanently disabled at this one critical decision point. [7](#0-6) 

---

### Impact Explanation

When Peras is active, a peer may serve a chain whose Peras-boosted total weight exceeds the local selection's weight, yet whose raw block count is lower. `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls back to block-count comparison and returns `ShouldNotSwitch`, causing `checkPreferTheirsOverOurs` to throw `CandidateTooSparse` and disconnect from that peer. The node then never adopts the canonical Peras-weighted chain from that peer, constituting a chain-selection error: an honest node is made to prefer a non-canonical, less-secure chain.

The symmetric failure also exists: if the local chain has Peras boosts that make it heavier by total weight but lighter by raw block count, the empty snapshot causes the check to return `ShouldSwitch` (their chain appears better), so the node does not disconnect when it should, wasting time waiting for an inferior chain and potentially adopting it.

This maps to: **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

Peras is not the default today (`disableGenesisConfig` is the default), but the `PerasCertDB`, `PerasVoteDB`, and `getPerasWeightSnapshot` are fully wired into the production `ChainDB` and `NodeKernel`. The CHANGELOG entry for `1.0.0.0` explicitly states: "Make the ChainDB aware of the PerasCertDB, and modify the chain selection function accordingly … Note that if Peras is disabled (which is the default), there is no observable difference." Once Peras is enabled on any network, this code path is reachable by any peer that serves a valid Peras-boosted chain whose header falls beyond the local forecast horizon — a normal occurrence during syncing. [8](#0-7) 

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot, consistent with every other call site. The snapshot is already available in the `ChainDbView` passed to `checkTime`; `getPerasWeightSnapshot` should be read inside the `atomically` block in `readLedgerStateHelper` and forwarded to `checkPreferTheirsOverOurs`. Alternatively, if the TODO's intent (remove the check entirely per issue #64) is acted upon, the function should be deleted rather than left with incorrect weights.

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Produce a chain `C_peer` with Peras-boosted blocks such that `totalWeight(C_peer) > totalWeight(C_local)` but `blockNo(tip(C_peer)) < blockNo(tip(C_local))`.
3. Connect a peer serving `C_peer` to the honest node.
4. Arrange for the peer's next header to be beyond the local forecast horizon (e.g., by creating a slot gap larger than the forecast window).
5. `checkTime` → `readLedgerState` → `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` returns `ShouldNotSwitch` because `theirFrag` has fewer blocks, ignoring the Peras boost.
7. `CandidateTooSparse` is thrown; the node disconnects from the peer serving the canonical chain.
8. The node retains its lighter (by Peras weight) local chain, diverging from the canonical Peras-weighted chain. [9](#0-8)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
