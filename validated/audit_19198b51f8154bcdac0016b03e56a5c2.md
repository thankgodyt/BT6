Audit Report

## Title
Silent Failure of `ft_transfer`/`mint` Causes Permanent Fund Loss and Locked-Token Mis-Accounting — (`File: near/omni-bridge/src/lib.rs`)

## Summary

When finalizing an inbound transfer to a NEAR recipient, `process_fin_transfer_to_near` consumes the transfer nonce and decrements `locked_tokens` before token delivery occurs. If the subsequent `ft_transfer` or `mint` call fails (e.g., recipient blacklisted in USDC NEP-141), `fin_transfer_send_tokens_callback` unconditionally treats the outcome as success because `is_refund_required` always returns `false` for non-`ft_transfer_call` paths. The user's tokens are permanently lost, the nonce is consumed, and the bridge's locked-token accounting is irreversibly corrupted.

## Finding Description

**Step 1 — State mutated before delivery.**
`process_fin_transfer_to_near` calls `add_fin_transfer` (consuming the nonce) and `unlock_tokens_if_needed` (decrementing `locked_tokens`) synchronously, before any cross-contract token delivery: [1](#0-0) 

**Step 2 — Plain `ft_transfer` or `mint` used when `msg` is empty.**
`send_tokens` issues `ft_transfer` (non-deployed token, empty msg) or `mint` (deployed token, empty msg). The callback is chained with `is_ft_transfer_call = !msg.is_empty()`, which is `false` when no msg is present: [2](#0-1) [3](#0-2) 

**Step 3 — `is_refund_required` ignores promise failure for non-`ft_transfer_call`.**
When `is_ft_transfer_call` is `false`, the function unconditionally returns `false` without inspecting the promise result at all: [4](#0-3) 

**Step 4 — Callback takes the success branch regardless of delivery outcome.**
Because `is_refund_required` returned `false`, `revert_lock_actions` and `remove_fin_transfer` are never called. The fee is minted/transferred to the relayer and `FinTransferEvent` is emitted: [5](#0-4) 

**Root cause:** `is_refund_required` only inspects the promise result for `ft_transfer_call`. For plain `ft_transfer` and `mint`, it assumes success unconditionally, making it impossible to detect and handle a failed delivery. [6](#0-5) 

## Impact Explanation

Two simultaneous Critical impacts:

1. **Permanent loss of bridged funds.** The transfer nonce is consumed by `add_fin_transfer` before delivery. A failed `ft_transfer`/`mint` is never retried and cannot be re-submitted (nonce already finalized). The user's tokens are irretrievably lost.

2. **Locked-token accounting corruption.** `unlock_tokens_if_needed` decrements `locked_tokens` before delivery. On failure, `revert_lock_actions` (which would call `lock_tokens` to restore the counter) is never invoked. The bridge permanently under-counts locked tokens for the origin chain, enabling future transfers to over-mint or over-release tokens beyond what is actually escrowed on the source chain. [7](#0-6) 

Both impacts match the allowed Critical scope: permanent loss of bridged funds and escrow mis-accounting that changes protocol balances.

## Likelihood Explanation

USDC is a first-class bridged asset on NEAR. Its NEP-141 contract enforces a blacklist; `ft_transfer` to a blacklisted account panics, causing the cross-contract promise to fail. A user whose NEAR address is blacklisted after initiating a cross-chain transfer (or already blacklisted) triggers this path. The relayer has no way to detect the blacklist status before calling `fin_transfer`, and no off-chain fallback exists. The same applies to any other NEP-141 token with transfer restrictions. No special privileges are required — any relayer submitting a valid proof for a blacklisted recipient triggers the bug.

## Recommendation

In `fin_transfer_send_tokens_callback`, inspect the promise result for all transfer types, not only `ft_transfer_call`. Concretely, replace the `is_refund_required` logic so that a failed promise (i.e., `env::promise_result_checked` returns `Err(_)`) is treated as a refund case for both `ft_transfer` and `mint` paths:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Err(_) => true, // promise panicked/failed — always refund
        Ok(value) if is_ft_transfer_call => {
            near_sdk::serde_json::from_slice::<U128>(&value)
                .map_or(false, |u| u.0 == 0)
        }
        Ok(_) => false,
    }
}
```

This ensures a failed `ft_transfer` or `mint` triggers `revert_lock_actions`, `remove_fin_transfer`, and `FailedFinTransferEvent`, restoring locked-token accounting and preventing permanent fund loss. [6](#0-5) 

## Proof of Concept

1. User bridges USDC from Ethereum to NEAR; recipient is `alice.near`.
2. After the source-chain event is emitted, `alice.near` is added to the USDC blacklist on NEAR.
3. Relayer calls `fin_transfer` with a valid proof and storage deposit for `alice.near`.
4. `process_fin_transfer_to_near` runs: `add_fin_transfer` consumes the nonce; `unlock_tokens_if_needed` decrements `locked_tokens[Eth][usdc]`.
5. `send_tokens` issues `ft_transfer(alice.near, amount)` → USDC contract panics (blacklisted) → promise result = `Failed`.
6. `fin_transfer_send_tokens_callback` runs with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` without reading the promise result.
8. Callback enters the `else` branch: fee minted to relayer (detached), `FinTransferEvent` emitted.
9. `alice.near` receives zero tokens. Transfer cannot be retried (nonce consumed). `locked_tokens` is permanently under-counted.

A local integration test can reproduce this by deploying a mock NEP-141 token whose `ft_transfer` always panics, then calling `fin_transfer` and asserting that `FinTransferEvent` is emitted while the recipient balance remains zero and `locked_tokens` is not restored. [8](#0-7)

        if is_ft_transfer_call {

                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {

                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.

                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }

    pub fn revert_lock_actions(&mut self, lock_actions: &[LockAction]) {
        for lock_action in lock_actions {
            match lock_action {
                LockAction::Locked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.unlock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unlocked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.lock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unchanged => {}
            }
        }
    }
