### Title
Peras Quorum Check Unit Mismatch in `stakeAboveThreshold` Enables Trivial Certificate Forging or Permanent Quorum Failure - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
`stakeAboveThreshold` directly compares accumulated `PerasVoteStake` values against `PerasQuorumStakeThreshold` without enforcing that both quantities are expressed in the same units (absolute ledger stake vs. normalized/relative stake). This is explicitly acknowledged in a developer TODO comment in the production source. When the actual stake-distribution plumbing is connected, if `PerasVoteStakeDistr` is populated with absolute ledger-stake values while the quorum threshold is a relative fraction, a single vote from any peer immediately satisfies the quorum check, allowing unauthorized Peras certificate creation and chain-selection manipulation. The inverse configuration makes quorum permanently unachievable.

### Finding Description

**Root cause — `stakeAboveThreshold`:**

```haskell
-- NOTE: ... this function only makes sense when both values are relative
-- (normalized) values, so we should either normalize the 'PerasVoteStake'
-- before calling this function, or change this function to accept a stake
-- distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

`PerasVoteStake` is a bare `Rational` with no unit tag: [2](#0-1) 

`PerasQuorumStakeThreshold` is likewise a bare `Rational`: [3](#0-2) 

The `PerasVoteStakeDistr` that supplies each voter's `PerasVoteStake` is an externally-provided map with no normalization contract: [4](#0-3) 

Vote validation simply copies whatever `Rational` is stored in that map into the validated vote: [5](#0-4) 

The production wiring in `NodeToNode.hs` currently passes an **empty** `PerasVoteStakeDistr` as a placeholder, with an explicit comment that this causes all votes to be rejected: [6](#0-5) 

The TODO comments in both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` confirm that the real stake-distribution plumbing is a planned next step: [7](#0-6) 

**Two failure modes when real plumbing is connected:**

1. **Trivial quorum (absolute vs. relative mismatch):** If `PerasVoteStakeDistr` is populated with absolute ledger-stake values (e.g., lovelace amounts such as `1_000_000`), while `perasQuorumStakeThreshold` is a relative fraction (e.g., `3/4`), then `1_000_000 >= 0.75 + safetyMargin` is trivially `True`. A single vote from any peer immediately satisfies `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to produce a `ValidatedPerasCert`. [8](#0-7) 

2. **Permanent quorum failure (relative values that don't sum to 1):** If individual `PerasVoteStake` values are relative fractions derived from ledger stake but are not normalized to sum to exactly 1.0 (e.g., due to rounding or truncation in the conversion from absolute to relative), the maximum achievable accumulated stake is strictly less than 1.0, and the quorum threshold (e.g., `3/4`) may never be reached even when every eligible voter votes. This is the direct analog of the external report's rounding-error scenario.

The `WFALS` committee's `implEligiblePartyVoteWeight` for non-persistent members compounds this: the vote weight is `numSeats * stake / nonPersistentStake`, a `Rational` division that is not guaranteed to sum to exactly `1.0` across all non-persistent voters due to the stochastic nature of local sortition: [9](#0-8) 

### Impact Explanation

**Scenario 1 (trivial quorum):** An unprivileged peer sends a single `PerasVote` message via the `PerasVoteDiffusion` mini-protocol. The vote passes `validatePerasVote` (stake lookup succeeds), `stakeAboveThreshold` returns `True`, and a `ValidatedPerasCert` is forged for the peer's chosen block. The certificate boosts that block's weight in chain selection by `perasWeight`, causing the honest node to prefer a non-canonical chain. This is a bypass of Peras certificate/vote verification checks.

**Scenario 2 (permanent quorum failure):** Even with 100% of eligible voters casting votes, the accumulated `PerasVoteStake` never reaches the quorum threshold. No Peras certificates are ever forged, the Peras boosting mechanism is permanently disabled, and the protocol degrades silently to plain Praos — breaking the Peras security assumptions without any observable error.

Both scenarios match the allowed impact scope: "Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance" (Scenario 1) and "Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants" (Scenario 2).

### Likelihood Explanation

The TODO comment in the production source explicitly acknowledges the unresolved unit ambiguity. The current empty-distribution workaround is a known placeholder, not a permanent fix. When the actual stake-distribution plumbing is connected — which is the stated next development step — the unit mismatch will manifest. The natural representation of ledger stake from the Cardano ledger is absolute (lovelace), making Scenario 1 the most likely outcome unless explicit normalization is added at the connection point.

### Recommendation

1. **Enforce unit consistency at the type level:** Introduce distinct newtypes for absolute and normalized stake (e.g., `AbsolutePerasVoteStake` vs. `NormalizedPerasVoteStake`) so that the compiler rejects comparisons between incompatible units.
2. **Normalize inside `stakeAboveThreshold`:** Change the function signature to accept the total stake distribution and perform normalization internally before comparing against the relative quorum threshold, as suggested by the existing TODO comment.
3. **Resolve the TODO before connecting real plumbing:** The empty-distribution workaround must not be replaced with real stake data until the normalization issue is resolved.
4. **Verify that non-persistent vote weights sum to 1.0:** Add an invariant check (or property test) that the sum of `implEligiblePartyVoteWeight` across all selected non-persistent voters equals the total non-persistent stake fraction, preventing the rounding-error variant of the bug.
