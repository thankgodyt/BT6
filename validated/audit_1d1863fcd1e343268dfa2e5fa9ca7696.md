### Title
Missing Cryptographic Signature Verification in Peras Vote Acceptance Allows Unauthorized Certificate Forging and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function — the sole production implementation of the `BlockSupportsPeras` class — accepts any vote whose voter ID appears in the stake distribution without verifying the vote's cryptographic signature. The `implAddVote` function in `PerasVoteDB/Impl.hs` carries an explicit TODO acknowledging that "non-trivial validation logic" is missing. An unprivileged peer can craft votes for any registered voter ID (all of which are publicly visible on-chain) and inject them into the local node's `PerasVoteDB`. If enough such crafted votes accumulate, a fraudulent Peras certificate is forged and submitted to the ChainDB, where it influences chain selection via Peras weight boosts.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasVote` as the authorization gate before a vote is accepted as `ValidatedPerasVote`. The only production instance (the degenerate instance at line 320 of `SupportsPeras.hs`, which applies to all `StandardHash blk`) implements this check as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

This only checks that the `PerasVoterId` (a public key hash) is present in the stake distribution. It does **not** verify:
- The cryptographic signature of the vote body
- That the vote is for a valid round or a valid block
- Any other protocol-level authorization

The `implAddVote` function in `PerasVoteDB/Impl.hs` carries a matching TODO at line 172–173:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
```

The inbound path in `makePerasVotePoolWriterFromChainDB` (`ObjectPool/PerasVote.hs`, line 141) calls `validatePerasVote` as the sole authorization check before forwarding to `addPerasVoteWithAsyncCertHandling`. Because `validatePerasVote` only checks stake distribution membership, any peer who knows a registered voter's public key hash (publicly derivable from on-chain data) can forge votes for that voter without the corresponding private key.

Similarly, `validatePerasCert` unconditionally returns `Right` for any certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

### Impact Explanation

Once a crafted vote passes `validatePerasVote`, it is stored in `PerasVoteDB` and fed into `updatePerasRoundVoteStates`. When the accumulated stake of crafted votes for a single target block exceeds the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert` and produces a `ValidatedPerasCert`. This certificate is then submitted to the ChainDB via `addPerasCertAsync`, which enqueues a chain-selection event. The ChainDB's chain selection logic uses the Peras weight boost from this certificate to prefer the attacker's chosen block over the honest chain. This constitutes:

- **Bypass of Peras vote/certificate verification** enabling unauthorized certificate acceptance.
- **Chain selection manipulation**: the node may switch to a fork containing the attacker's chosen block, diverging from the honest chain.

---

### Likelihood Explanation

All registered voter IDs (`PerasVoterId`, which are `KeyHash StakePool` values) are publicly visible on-chain. An attacker needs only to enumerate the current stake distribution (available via any node's local state query) to obtain valid voter IDs. No private keys, admin access, or stake majority is required. The object diffusion mini-protocol for Peras votes is reachable from any connected peer. The attacker must send enough crafted votes to exceed the quorum threshold, which depends on the configured `perasQuorumStakeThreshold`. With a sufficiently large number of registered voters in the distribution, an attacker can impersonate multiple voters to accumulate the required stake.

---

### Recommendation

The `validatePerasVote` implementation must verify the cryptographic signature of the vote body against the voter's registered public key before accepting the vote. The `validatePerasCert` implementation must similarly verify the certificate's aggregate signature. Both functions should be updated to perform full protocol-level validation as described in the referenced issue (`cardano-peras/issues/120`). Until this is done, the `ValidatedPerasVote` and `ValidatedPerasCert` wrappers provide a false guarantee of validity.

---

### Proof of Concept

1. Attacker queries the local state query protocol to obtain the current `PerasVoteStakeDistr` (the registered voter set and their stakes).
2. Attacker selects a target block `B` on a fork they wish to boost.
3. For each registered voter ID `v_i` in the distribution, attacker crafts a `PerasVote { pvVoteRound = r, pvVoteBlock = B, pvVoteVoterId = v_i }` — no private key needed, as the voter ID is a public key hash.
4. Attacker sends these votes to the victim node via the Peras vote object diffusion mini-protocol.
5. `processVotes` calls `validatePerasVote` for each vote; each passes because `v_i` is in the stake distribution.
6. Each `ValidatedPerasVote` is forwarded to `addPerasVoteWithAsyncCertHandling` → `implAddVote`.
7. Once the accumulated `vpvVoteStake` for block `B` in round `r` exceeds `perasQuorumStakeThreshold`, `updateCandidateVoteState` calls `forgePerasCert`, producing a `ValidatedPerasCert` for `B`.
8. The certificate is enqueued via `addPerasCertAsync` and processed by chain selection.
9. The node's chain selection now applies a Peras weight boost to block `B`, potentially switching to the attacker's chosen fork.

addPerasVoteWithAsyncCertHandling ::
  forall m blk.
  IOLike m =>
  ChainDbEnv m blk ->
  WithArrivalTime (ValidatedPerasVote blk) ->
  m (AddPerasVoteResult blk, Maybe (AddPerasCertPromise m))
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      let certTime = getArrivalTime vote
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)
      pure (addVoteRes, Just promise)
    _ -> pure (addVoteRes, Nothing)
