### Title
Missing BLS Vote Signature Verification in `validatePerasVote` Default Instance Enables Forged Vote Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasVote` implementation validates incoming Peras votes by checking only whether the voter ID exists in the stake distribution. It performs **no BLS signature verification**. Any unprivileged peer can craft votes with arbitrary block targets using any valid voter ID and have them accepted as cryptographically valid, potentially forging a quorum certificate for an attacker-chosen block.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasVote` as the entry point for vote validation. The default instance (used for all block types via the catch-all `instance StandardHash blk => BlockSupportsPeras blk`) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check performed is `lookupPerasVoteStake`, which looks up the voter's ID in a public stake distribution map:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [2](#0-1) 

The `pvSignature` field of the vote — a BLS signature over `hashVoteSignature(roundNo, boostedBlock)` — is never verified. The `PerasVote` data type carries this signature:

```haskell
, pvSignature :: !(VoteSignature PerasBLSCrypto)
-- ^ BLS signature on the hash of the election identifier and vote message
``` [3](#0-2) 

This stub is the implementation invoked by the live network diffusion layer. Both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` call `validatePerasVote mkPerasParams sd vote` directly:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

The correct BLS verification logic exists in `PerasBLSCrypto` and is used in the committee-layer `implVerifyVote` functions, but is never called from the network-facing validation path:

```haskell
verifyVoteSignature pk roundNo boostedBlock (PerasBLSCryptoVoteSignature sig) =
  BLS.verifyWithRole @SIGN pk (hashVoteSignature roundNo boostedBlock) sig
``` [5](#0-4) 

A compounding structural issue: `PerasVoteId` is defined as `(roundNo, voterId)` with no block hash:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [6](#0-5) 

The deduplication check in `processVotes` uses this ID. An attacker who sends a forged vote for block B with voter V's ID before the legitimate vote for block A arrives will have the forged vote accepted and the legitimate vote silently dropped as a duplicate.

---

### Impact Explanation

An unprivileged peer can:

1. Enumerate the public stake distribution to identify high-stake committee members.
2. Craft `PerasVote` messages with those voter IDs but pointing to an attacker-chosen block.
3. Submit these votes via the object diffusion miniprotocol. `processVotes` calls `validatePerasVote`, which accepts them because the voter IDs are present in the stake distribution.
4. If the combined stake of the spoofed voters exceeds the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for the attacker's block.
5. This certificate is injected into the `ChainDB` via `addPerasVoteWithAsyncCertHandling`, boosting the attacker's block with the full Peras weight.

The result is unauthorized certificate acceptance and chain selection manipulation: an honest node is made to prefer a non-canonical chain boosted by a fraudulent certificate, directly violating Peras safety.

---

### Likelihood Explanation

The attack requires only a network connection to a target node and knowledge of the current stake distribution (which is public on-chain data). No key compromise, stake majority, or social engineering is needed. The object diffusion miniprotocol is designed to accept votes from any connected peer. The stub is the only implementation wired into the live diffusion layer.

---

### Recommendation

1. **Immediately wire BLS signature verification into the network-facing `validatePerasVote` path.** The correct implementation already exists in `PerasBLSCrypto.verifyVoteSignature` and the committee-layer `implVerifyVote` functions. The default instance must call `verifyVoteSignature` (or the equivalent committee-layer check) before accepting a vote.

2. **Include the block hash in `PerasVoteId`.** The vote ID should be `(roundNo, voterId, boostedBlock)` so that deduplication correctly distinguishes votes for different blocks in the same round by the same voter, preventing front-running substitution attacks.

3. **Remove or gate the stub.** The TODO default instance should either be replaced with a proper implementation or restricted to non-production contexts (e.g., behind a compile-time flag or a separate test-only typeclass instance).

---

### Proof of Concept

```
Attacker (unprivileged peer) → connects to honest node N

1. Query on-chain stake distribution: voter V has stake S > quorum_threshold.
2. Craft PerasVote {
     pvRoundNo    = current_round,
     pvBoostedBlock = attacker_block,   -- arbitrary block hash
     pvSeatIndex  = V's seat index,
     pvEligibilityProof = PersistentPerasVoteEligibilityProof,
     pvSignature  = <garbage bytes>     -- never checked
   }
3. Send via object diffusion miniprotocol to node N.
4. processVotes calls validatePerasVote mkPerasParams stakeDistr vote.
5. lookupPerasVoteStake finds V in stakeDistr → returns Right ValidatedPerasVote.
6. updatePerasRoundVoteStates accumulates stake S for attacker_block.
7. stakeAboveThreshold → quorum reached → forgePerasCert produces ValidatedPerasCert
   boosting attacker_block.
8. ChainDB receives the certificate; chain selection now prefers attacker_block.
``` [7](#0-6) [8](#0-7)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
