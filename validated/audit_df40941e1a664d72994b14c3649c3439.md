### Title
`BlockSupportsPeras#validatePerasCert` Always Returns `Right` — Peras Certificate Verification Bypass - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which is the catch-all instance used for all block types, implements `validatePerasCert` as an unconditional `Right` — it always reports every certificate as valid without performing any cryptographic or structural checks. This is the exact structural analog of the reported `isClosed()` bug: a guard function that is supposed to reject invalid inputs instead always returns the "pass" value.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all `instance StandardHash blk => BlockSupportsPeras blk` implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function is supposed to validate a Peras certificate before it is accepted into the node's `PerasCertDB` and used to influence chain selection. Instead, it unconditionally wraps any input certificate in `Right ValidatedPerasCert`, granting it a chain-selection boost weight of `perasWeight params` with zero verification.

This instance is the **production fallback** for all block types, explicitly marked as a "degenerate instance for all blks to get things to compile": [2](#0-1) 

The function is wired directly into the inbound certificate processing pipeline. In `PerasCert.hs`, both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `validatePerasCert mkPerasParams` as the `validateCert` callback to `processCerts`: [3](#0-2) [4](#0-3) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, stores them in the database: [5](#0-4) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken — no certificate is ever rejected.

The `BlockSupportsPeras` class contract requires `validatePerasCert` to check the certificate against `PerasCfg blk` and return `Left (PerasValidationErr blk)` on failure: [6](#0-5) 

The implementation violates this contract entirely.

---

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate verification enabling unauthorized certificate acceptance.**

A stored `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` that is used by the chain selection logic to prefer boosted chains. An attacker who can inject arbitrary certificates — with any `pcCertRound` and any `pcCertBoostedBlock` — will have those certificates unconditionally accepted and stored. This allows an unprivileged peer to:

1. Inject a certificate boosting an attacker-controlled (non-canonical) block.
2. Have honest nodes store that certificate as valid.
3. Cause chain selection to prefer the boosted non-canonical chain over the honest canonical chain, since the Peras boost weight is applied without any cryptographic proof of quorum.

This is a bypass of Peras voting/certificate checks that enables unauthorized certificate acceptance, matching the Critical impact tier: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The Peras certificate ObjectDiffusion mini-protocol is present and wired up in the production node. Any peer connected via this protocol can send a crafted `PerasCert` message. No special privileges, keys, or stake are required — the attacker only needs a network connection to a target node. The bypass requires zero cryptographic knowledge because the validation function performs no checks whatsoever.

---

### Recommendation

Replace the stub implementation with actual certificate validation. At minimum, the `validatePerasCert` function must verify:

1. **Cryptographic signature / aggregate signature** of the certificate against the claimed committee members' keys.
2. **Quorum threshold**: the certificate must represent sufficient stake.
3. **Round number bounds**: the certificate round must be within the valid range relative to the current chain tip.
4. **Boosted block existence**: `pcCertBoostedBlock` must refer to a known block on a valid chain.

Until real validation is implemented, the function should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), to fail safely:

```haskell
validatePerasCert _params _cert = Left PerasValidationErr
```

This mirrors the correct fix for the reported `isClosed()` bug: use the actual state variable rather than a hardcoded pass value.

---

### Proof of Concept

1. Connect to a node that has the Peras certificate ObjectDiffusion mini-protocol active.
2. Send a `PerasCert` with an arbitrary `pcCertRound` and a `pcCertBoostedBlock` pointing to an attacker-controlled block.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}` unconditionally.
4. The certificate is stored in `PerasCertDB` via `addCert`.
5. Chain selection now applies the Peras boost weight to the attacker-specified block, potentially causing the node to prefer a non-canonical chain.

The root cause is the single line:

```haskell
validatePerasCert params cert = Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
