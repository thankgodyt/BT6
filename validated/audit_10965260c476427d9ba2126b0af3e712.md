### Title
Front-Running `request_refund` With Attacker-Controlled `refund_address` Enables BTC Theft When `deposit_msg.refund_address` Is `None` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user deposits BTC using a `DepositMsg` with `refund_address: None`, the `request_refund` function accepts a caller-supplied `refund_address` parameter with no binding to the depositor's identity. An unprivileged attacker can observe the victim's pending `request_refund` NEAR transaction, front-run it with the same `deposit_msg` and `tx_bytes`/`proof` but substitute their own BTC address as `refund_address`. Because the refund request is keyed by `utxo_storage_key` (`{tx_id}@{vout}`), the first callback to land wins; the victim's callback is rejected with "Refund request already exists for this UTXO", the victim loses their attached NEAR anti-spam deposit, and the stored refund record points to the attacker's BTC address. After `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund` to send the victim's BTC to the attacker.

### Finding Description

`request_refund` accepts two separate address fields:

1. `deposit_msg.refund_address` — embedded in the deposit message that determines the deposit address path.
2. `refund_address` — the BTC address that will actually receive the refund.

The only guard linking them is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` this block is skipped entirely, so any caller may supply any BTC address as `refund_address`.

Inside `request_refund_callback`, the only check performed is that the transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg`:

```rust
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
``` [2](#0-1) 

This check passes for any caller who supplies the same `deposit_msg` (with `refund_address: None`), because the deposit address is derived solely from `deposit_msg` fields, not from who is calling.

The callback then stores the refund request keyed by `utxo_storage_key`:

```rust
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

A duplicate-check prevents a second request for the same key:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

So whichever callback lands first wins. The stored `refund_address` is later used verbatim in `finalize_refund_with_psbt` to build the Bitcoin output:

```rust
let refund_address = refund_request.refund_address.clone();
``` [5](#0-4) 

`execute_refund` is publicly callable by anyone after the timelock:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
``` [6](#0-5) 

### Impact Explanation

An attacker who front-runs the victim's `request_refund` with an attacker-controlled `refund_address` causes:

1. **Victim's NEAR anti-spam deposit is permanently lost** — the callback panics and the attached NEAR is not returned.
2. **Victim's BTC is redirected to the attacker** — after `unsafe_refund_timelock_sec`, the attacker (or anyone) calls `execute_refund`, and the bridge MPC signs a Bitcoin transaction paying the attacker's address.

This is a direct, complete theft of the victim's bridged BTC. Impact: **Critical**.

### Likelihood Explanation

- NEAR transactions are observable in the mempool before finalization.
- All inputs needed to replicate the call (`deposit_msg`, `tx_bytes`, `proof`) are public Bitcoin blockchain data.
- The attacker only needs to pay `required_balance_for_request_refund()` (a small NEAR storage fee) to execute the attack.
- The `unsafe_refund_timelock_sec` gives DAO/Operator time to reject, but this is an off-chain, manual, trusted-operator dependency — not a cryptographic guarantee. If the DAO is not actively monitoring or the timelock is short, the attack succeeds.
- Any user who deposits BTC without pre-setting `deposit_msg.refund_address` is vulnerable.

Likelihood: **Medium** (requires mempool monitoring and DAO inaction, but the economic incentive is high).

### Recommendation

Bind the `refund_address` to the caller's identity or to the deposit message at the time of deposit. Specifically:

- When `deposit_msg.refund_address` is `None`, require that `refund_address` is provided at deposit time and stored in the deposit message, OR restrict `request_refund` so that only `env::predecessor_account_id() == deposit_msg.recipient_id` may supply an arbitrary `refund_address`.
- Alternatively, generate the `utxo_storage_key` to include the caller's account ID and the supplied `refund_address`, so different callers produce different keys and cannot collide.

### Proof of Concept

1. Alice deposits BTC to the address derived from `DepositMsg { recipient_id: alice.near, refund_address: None, ... }`.
2. Alice calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: alice.near, refund_address: None },
     refund_address = "alice_btc_addr",
     tx_bytes = <alice's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
   )
   ```
   with attached NEAR ≥ `required_balance_for_request_refund()`.
3. Attacker observes Alice's pending NEAR transaction and immediately submits:
   ```
   request_refund(
     deposit_msg = { recipient_id: alice.near, refund_address: None },
     refund_address = "attacker_btc_addr",   // ← attacker's address
     tx_bytes = <same tx_bytes>,
     vout = 0,
     proof = <same proof>,
   )
   ```
   with a higher gas price so it is processed first.
4. Attacker's `request_refund_callback` succeeds: `deposit_script_pubkey == output.script_pubkey` (same `deposit_msg`), and the refund request is stored with `refund_address = "attacker_btc_addr"`.
5. Alice's `request_refund_callback` panics: "Refund request already exists for this UTXO". Alice's NEAR deposit is lost.
6. After `unsafe_refund_timelock_sec`, the attacker calls `execute_refund(utxo_storage_key)`.
7. The bridge builds and MPC-signs a Bitcoin transaction paying `"attacker_btc_addr"`. Alice's BTC is stolen.
