### Title
`validatePerasCert` Unconditionally Returns `Right` Without Performing Any Certificate Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation always returns `Right` without performing any cryptographic or committee-membership validation. This is the only `BlockSupportsPeras` instance in the codebase. An unprivileged peer can inject an arbitrary Peras certificate via the ObjectDiffusion mini-protocol, causing the node to accept it as valid, store it in the ChainDB, and trigger chain selection for any block the attacker chooses to boost — potentially making the node prefer a non-canonical chain.

---

### Finding Description

**Vulnerability class**: Bypass of certificate/signature validation that enables unauthorized certificate acceptance, leading to a chain-selection bug.

**Root cause — `validatePerasCert` stub always returns `Right`:**

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` is the only instance in the codebase:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No committee membership check, no VRF proof verification, no aggregate signature verification, and no quorum check is performed. Any `PerasCert` — regardless of its `pcCertRound` or `pcCertBoostedBlock` — is unconditionally wrapped in `Right ValidatedPerasCert`.

**Attacker-controlled entry path:**

`makePerasCertPoolWriterFromChainDB` is the production entry point for inbound peer certificates. It passes `validatePerasCert mkPerasParams` as the validator to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate. Since `validatePerasCert` always returns `Right`, the `partitionEithers` branch always takes the "all certs valid" path and calls `addCert` on every certificate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

The accepted certificate is then forwarded to `ChainDB.addPerasCertAsync`, which enqueues it for `chainSelSync`. `chainSelSync` processes it by adding it to the `PerasCertDB` and triggering chain selection for the boosted block:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  -- Trigger chain selection for the boosted block.
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Analog to the LiFi bug:**

In LiFi, `LibSwap.swap()` was called and returned success, but no tokens were actually received — no post-condition check verified the output. Here, `validatePerasCert` is called and returns `Right` (success), but no actual validation is performed — the "output" (a `ValidatedPerasCert`) is produced without any check on the certificate's cryptographic content. The `ValidatedPerasCert` type is supposed to be a proof-of-validation token, but the stub makes it meaningless.

**Secondary issue — `validatePerasVote` also skips signature verification:**

The same stub instance's `validatePerasVote` checks only that the voter is in the stake distribution, but does not verify the vote signature:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [5](#0-4) 

An attacker can forge votes from any pool in the stake distribution without knowing their private keys. If enough forged votes accumulate to reach quorum, a certificate is generated and added to the ChainDB via the same unvalidated path.

---

### Impact Explanation

A Peras certificate adds weight `vpcCertBoost = perasWeight params` to the boosted block in chain selection. Since `validatePerasCert` always accepts any certificate, an unprivileged peer can:

1. Send a `PerasCert` with `pcCertBoostedBlock` pointing to any block on a competing (non-canonical) fork.
2. The certificate is accepted, stored, and triggers chain selection.
3. The boosted fork now appears heavier than the honest chain.
4. The node switches to the non-canonical chain.

This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The attack path is direct and requires no special privileges:
- Any peer connected via the ObjectDiffusion mini-protocol can send `PerasCert` messages.
- The `makePerasCertPoolWriterFromChainDB` path is the production code path for handling inbound certificates.
- There is no Cardano-specific `BlockSupportsPeras` override — the stub is the only instance.
- The attack requires only crafting a `PerasCert` with a desired `pcCertRound` and `pcCertBoostedBlock`, both of which are plain data fields with no cryptographic protection under the current stub.

---

### Recommendation

Implement actual certificate validation in `validatePerasCert` that verifies:
1. All voters in the certificate are legitimate committee members (persistent or non-persistent via local sortition).
2. VRF proofs for non-persistent voters are valid and yield a non-zero seat count.
3. The aggregate vote signature is valid against the aggregated verification keys of all voters.
4. The total voting weight of the certificate's voters meets the quorum threshold.

The existing `implVerifyCert` implementations in `WFALS.hs` and `EveryoneVotes.hs` provide the correct validation logic and should be wired into `validatePerasCert` once the HFC plumbing is in place (tracked at https://github.com/tweag/cardano-peras/issues/120 and https://github.com/tweag/cardano-peras/issues/73).

Until then, the stub should at minimum reject all inbound certificates rather than accept them unconditionally, to prevent the chain-selection bypass.

---

### Proof of Concept

1. Connect to a target node via the ObjectDiffusion mini-protocol (peer connection).
2. Craft a `PerasCert` with:
   - `pcCertRound = <any round not already in the DB>`
   - `pcCertBoostedBlock = <point of a block on a competing fork>`
3. Send the certificate to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always returns `Right ValidatedPerasCert`.
5. The certificate is forwarded to `ChainDB.addPerasCertAsync`.
6. `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
7. The boosted fork gains `perasWeight params` additional weight in chain selection.
8. If the boosted fork's total weight now exceeds the current selection, the node switches chains. [6](#0-5) [2](#0-1) [7](#0-6)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
