### Title
`validatePerasCert` and `getPerasCertInBlock` are production stubs that unconditionally accept/suppress all Peras certificates, bypassing certificate validation and breaking chain selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The global `BlockSupportsPeras` instance for all block types ships two stub implementations in production code: `validatePerasCert` unconditionally returns `Right` (accepts any certificate without any check), and `getPerasCertInBlock` unconditionally returns `Nothing` (never extracts a certificate from a block). Test infrastructure explicitly bypasses both stubs. This is the direct Ouroboros Consensus analog of LID-17: the real implementation has a degenerate stub where only mock/test code provides the correct behaviour, hiding the defect.

---

### Finding Description

**Root cause — `validatePerasCert` stub (always accepts):** [1](#0-0) 

The comment at line 318 is explicit: *"TODO: degenerate instance for all blks to get things to compile."* The implementation of `validatePerasCert` is: [2](#0-1) 

Every `PerasCert`, regardless of its content, round number, boosted-block pointer, or cryptographic material, is wrapped in `Right ValidatedPerasCert` and returned as valid. The TODO at line 350 acknowledges: *"TODO: perform actual validation against all possible `PerasValidationErr` variants."*

**Root cause — `getPerasCertInBlock` stub (always suppresses):** [3](#0-2) 

Every block, regardless of whether it carries a Peras certificate, returns `Nothing`. The TODO at line 387 acknowledges: *"TODO: extract actual Peras certificates from blocks when the HFC plumbing is in place."*

**Test infrastructure explicitly bypasses both stubs — the LID-17 pattern:**

The `TestBlock` `ApplyBlock` instance contains this comment and workaround: [4](#0-3) 

The test block reads `tbPerasCertRound` directly from the block body, bypassing `getPerasCertInBlock` entirely. This is structurally identical to the Lido `WithdrawalQueueStub` that had `getWithdrawalRequestStatus` while the real contract did not: the test path works correctly, the production path is broken, and the discrepancy is invisible to the test suite.

**`LedgerSupportsPeras` default also returns `Nothing`:** [5](#0-4) 

The default implementation of `getLatestPerasCertRound` also returns `Nothing`, meaning the ledger state never records the latest on-chain certificate round unless a concrete era overrides it.

---

### Impact Explanation

When Peras is enabled:

1. **Certificate validation bypass (Critical):** An unprivileged peer sends a crafted `PerasCert` with an arbitrary round number and boosted-block pointer via the ObjectDiffusion mini-protocol. `validatePerasCert` accepts it unconditionally. The certificate is stored in the `PerasCertDB` and assigned `perasWeight` boost. Chain selection then uses this fake certificate to prefer a non-canonical chain fragment. This is a direct bypass of Peras certificate/vote checks enabling unauthorized certificate acceptance, matching the Critical impact tier.

2. **Chain selection broken by `getPerasCertInBlock _ = Nothing` (High):** On-chain certificates are never extracted from blocks, so `getLatestPerasCertRound` in the ledger state is never updated from the chain. The cooldown-period coordination logic in the Peras voting rules (`perasVR2A`, `perasVR2B`) depends on this value. With it always `Nothing`, the voting rules operate on stale state, potentially allowing votes in rounds that should be suppressed, or suppressing votes in rounds that should proceed. [6](#0-5) 

---

### Likelihood Explanation

**Medium.** Peras is disabled by default (`eraPerasRoundLength = NoPerasEnabled`): [7](#0-6) 

However, the code is in the production library, `LedgerSupportsPeras` is a required constraint on `SingleEraBlock`: [8](#0-7) 

Any private-testnet or staging deployment that enables Peras (`eraPerasRoundLength = PerasEnabled ...`) immediately exposes both stubs to any connected peer. No key compromise, stake majority, or operator privilege is required — sending a crafted certificate over the ObjectDiffusion mini-protocol is sufficient.

---

### Recommendation

1. **Implement real `validatePerasCert`:** Verify the certificate's cryptographic material (aggregate BLS/KES signature over the quorum of votes), check the round number is within the valid window, and verify the boosted block is on the candidate chain.

2. **Implement real `getPerasCertInBlock`:** Wire through the HFC plumbing to extract the `PerasCert` embedded in a Shelley-family block body and return it.

3. **Add integration tests** that use the real `getPerasCertInBlock` path (not the `tbPerasCertRound` bypass) so that the stub cannot silently regress again.

---

### Proof of Concept

```
1. Configure a node with Peras enabled (eraPerasRoundLength = PerasEnabled N).
2. Connect an unprivileged peer.
3. Peer constructs a PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <any point> }
   with no valid signatures.
4. Peer sends the certificate via the ObjectDiffusion mini-protocol.
5. Node calls validatePerasCert params cert
   → returns Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
   (lines 353–358 of SupportsPeras.hs)
6. Certificate is stored in PerasCertDB with full boost weight.
7. Chain selection (WeightedSelectView) now prefers any chain fragment that includes
   the boosted block, regardless of whether that chain is canonical.
8. Honest node diverges from the canonical chain.
``` [9](#0-8)
