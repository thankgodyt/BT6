Audit Report

## Title
Fee Validity Check Before Decimal Normalization Causes Permanent Token Lock - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates `fee < amount` using raw NEAR-native token amounts before any decimal normalization, then immediately burns or locks the full `amount`. When `sign_transfer` is later called, it normalizes `amount - fee` via floor division to the destination chain's decimal precision. If the net amount is smaller than the normalization divisor, the result is zero and `sign_transfer` permanently reverts — but the user's tokens are already irreversibly burned or locked with no recovery path.

## Finding Description

**Step 1 — `init_transfer_internal`:**

The fee validity check at [1](#0-0)  operates on raw NEAR-native amounts with no awareness of destination-chain decimal precision. Immediately after, tokens are burned or locked at [2](#0-1) .

**Step 2 — `sign_transfer`:**

`normalize_amount` applies floor division: [3](#0-2) 

The zero-amount guard fires only after tokens are already gone: [4](#0-3) 

`amount_without_fee` is a simple subtraction: [5](#0-4) 

**No recovery path exists:**

- There is no `cancel_transfer` function in `lib.rs`.
- `update_transfer_fee` enforces `fee.fee >= current_fee.fee`, meaning the fee can only be increased, not decreased: [6](#0-5) 

The code comment at L2781–2783 acknowledges dust truncation but only for the remainder case ("dust absorbed into fee via `claim_fee`"), not for the case where the entire net amount normalizes to zero: [7](#0-6) 

## Impact Explanation

This constitutes **permanent freezing of bridged funds** — a Critical impact under the allowed scope. A user's tokens are irreversibly burned or locked by `init_transfer_internal`, and `sign_transfer` will revert on every subsequent call with `InvalidAmountToTransfer`. No privileged or unprivileged function can recover the funds. The impact is concrete and caused entirely by this repository's logic.

## Likelihood Explanation

Any NEAR-native token with `origin_decimals > destination_decimals` is affected. For a token with 24 NEAR decimals bridging to a 6-decimal EVM token, the normalization divisor is `10^18`. Any transfer where `amount - fee < 10^18` (i.e., the net amount is less than 1 full unit on the destination chain) produces a zero normalized result. This is reachable by any unprivileged user through the standard `ft_transfer_call` → `sign_transfer` flow with no special preconditions. The user need not act maliciously — a user attempting to bridge a fractional token amount (e.g., 0.5 tokens with a 0.1 token fee, net = 0.4 tokens < 1 destination unit) triggers this permanently.

## Recommendation

Compute `normalize_amount(amount - fee, decimals)` inside `init_transfer_internal` — after resolving the destination token's decimals — and revert immediately if the result is zero, **before** calling `burn_tokens_if_needed` or `lock_tokens_if_needed`. This ensures the zero-amount guard fires before any irreversible state change. Alternatively, add a `cancel_transfer` function that allows the original sender to reclaim locked/burned tokens when a transfer is permanently stuck.

## Proof of Concept

1. Register token `T` with `origin_decimals = 24`, `destination_decimals = 6` (divisor = `10^18`).
2. User calls `ft_transfer_call` with `amount = 5 × 10^17` base units and `fee = 10^17` base units (`fee < amount` passes).
3. `init_transfer_internal` burns `5 × 10^17` units of `T` from the user. Transfer is stored in `pending_transfers`.
4. Relayer calls `sign_transfer`. `normalize_amount(5×10^17 - 10^17, {24, 6}) = 4×10^17 / 10^18 = 0`.
5. `require!(amount_to_transfer > 0, ...)` reverts. Every future `sign_transfer` call reverts identically.
6. `update_transfer_fee` cannot help — it only allows increasing the fee, which makes the net amount smaller and the situation worse.
7. The user's `5 × 10^17` units of `T` are permanently burned with no recovery path.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
