### Title
Inconsistent Token Delivery in `safe_mint`: Tokens Minted to Bridge but Not Tracked When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary

The `safe_mint` function in the nBTC contract unconditionally mints tokens to the bridge account in all code paths, but only delivers them to the recipient in branches where the recipient account is already registered. When the recipient is unregistered, the function returns `U128(0)` and exits — with no secondary step to track the owed amount or schedule a later delivery. This is a direct analog to the reported vulnerability class: a secondary accounting step is applied inconsistently across branches, producing divergent outcomes depending on which branch executes.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes as follows:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // always mints

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // exits with no tracking
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
``` [1](#0-0) 

There are three execution branches:

| Branch | Condition | `internal_deposit` to bridge | Delivery to user | Owed-amount tracking |
|---|---|---|---|---|
| A | account not registered | YES | NO | **NONE** |
| B | account registered, no msg | YES | YES (ft_transfer) | N/A |
| C | account registered, with msg | YES | YES (ft_transfer_call) | N/A |

In Branch A, `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the total nBTC supply and credits the bridge account, but the function immediately returns `U128(0)`. No entry is written to any "owed" or "lost-found" ledger inside the nBTC contract. The bridge's own `lost_found` map is only populated inside `transfer_nbtc_callback` when an `ft_transfer` call fails — a completely separate code path that is never reached here. [2](#0-1) 

The nBTC contract exposes no `claim`, `recover`, or equivalent function that would let the bridge later push the stuck tokens to the user after they register. [3](#0-2) 

### Impact Explanation

When a user deposits BTC and the bridge calls `safe_mint` for an account that has not yet registered in the nBTC token contract:

1. The BTC is locked in the bridge's UTXO pool (the deposit is verified and consumed).
2. `amount` nBTC tokens are minted and credited to the bridge account (total supply increases).
3. The user receives 0 nBTC.
4. No on-chain record links those bridge-held tokens to the user.
5. Without manual operator intervention (a privileged `ft_transfer` from the bridge account), the tokens are permanently stuck.

This matches the allowed Medium impact: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."* The backed supply is not reduced (BTC remains in the pool), but the user's nBTC is irrecoverably stranded in the bridge account, requiring privileged action to remedy.

### Likelihood Explanation

The `safe_mint` path is reachable by any unprivileged depositor. A user who sends BTC to a deposit address derived from their NEAR account ID but has not yet called `storage_deposit` on the nBTC contract will trigger Branch A. This is a realistic scenario: the deposit address is derived off-chain and the user may send BTC before completing the NEAR-side registration step. The bridge calls `safe_mint` precisely because it cannot guarantee the account is registered.

### Recommendation

Apply the secondary accounting step consistently across all branches of `safe_mint`. Two options:

1. **Register-on-mint**: Call `self.token.internal_register_account(&account_id)` before `internal_deposit` when the account is absent, so the transfer always succeeds.
2. **Track owed amount**: When the account is absent, record the owed amount in a persistent map (analogous to `lost_found` in the bridge) and expose a permissionless `claim` function that delivers the tokens once the account registers.

Either approach ensures that every code path that mints tokens also guarantees eventual delivery to the intended recipient.

### Proof of Concept

1. User derives a deposit address for NEAR account `alice.near` but does not call `storage_deposit` on the nBTC contract.
2. User sends 0.01 BTC to the deposit address.
3. Relayer submits the Merkle inclusion proof; the bridge verifies it and calls `safe_mint("alice.near", 1_000_000, None)`.
4. `internal_deposit(&bridge_id, 1_000_000)` executes — bridge nBTC balance increases by 1,000,000 satoshis-worth.
5. `self.token.accounts.get(&"alice.near")` returns `None` → function returns `U128(0)`.
6. `alice.near` has 0 nBTC. The 1,000,000 nBTC units sit in the bridge account with no on-chain claim record.
7. `alice.near` later calls `storage_deposit` and registers — but there is no function to retrieve the stranded tokens without operator action. [3](#0-2) [1](#0-0)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
