### Title
Unprivileged Caller Can Redirect Another User's BTC Refund to an Attacker-Controlled Address via `request_refund` — (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`request_refund` is a public, permissionless function that accepts a caller-supplied `refund_address` without verifying the caller owns the deposit. When `deposit_msg.refund_address` is `None` (the common case), any attacker who observes a victim's unfinalized BTC deposit on-chain can submit a refund request that redirects the victim's BTC to the attacker's own address.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no role restriction — it is decorated only with `#[payable]` and `#[pause]`, making it callable by any NEAR account. [1](#0-0) 

The function accepts three attacker-controllable inputs: `deposit_msg` (public, derived from the deposit address), `tx_bytes` (public on-chain data), and `refund_address` (arbitrary string). Inside the callback `request_refund_callback`, the only guard on `refund_address` is: [2](#0-1) 

This check fires **only** when `deposit_msg.refund_address` is `Some`. The `DepositMsg` struct shows `refund_address` is an optional field: [3](#0-2) 

When a user deposits without pre-specifying a refund address (`refund_address: None`), the callback skips the guard entirely and stores the caller's arbitrary `refund_address` verbatim: [4](#0-3) 

The `deposit_msg` is public knowledge — users call `get_user_deposit_address` to derive their deposit address, and the `deposit_msg` is the exact input to that derivation. The BTC transaction is public on-chain. An attacker can reconstruct both without any privileged access.

The only on-chain protection is `unsafe_refund_timelock_sec`, a longer timelock applied when `deposit_msg.refund_address` is `None`, intended to give DAO/Operator time to reject suspicious requests: [5](#0-4) 

This is not a prevention mechanism — it is a detection window that relies entirely on off-chain monitoring. If the DAO does not reject within the timelock, `execute_refund` becomes callable by anyone and the victim's BTC is sent to the attacker's address.

---

### Impact Explanation

**Critical.** A successful attack results in direct, permanent theft of a victim's BTC. The victim deposited BTC expecting to receive nBTC (or a refund to their own address), but instead their BTC is redirected to the attacker's Bitcoin address via the MPC signing pipeline. There is no on-chain recovery path once `execute_refund` is finalized and `verify_refund_finalize` confirms the transaction.

---

### Likelihood Explanation

**Medium.** Three conditions are required:

1. **A victim's deposit is unfinalized** — relayer failures, network congestion, or light-client delays are realistic operational scenarios.
2. **The attacker observes the BTC transaction** — trivial; Bitcoin is a public ledger.
3. **The DAO fails to reject within `unsafe_refund_timelock_sec`** — the DAO is not required to monitor continuously, and the timelock is a finite configuration value. If the DAO is slow, offline, or the timelock is short, the attack succeeds.

The combination of a realistic trigger (unfinalized deposit) and a trivial observation step makes this a credible attack path.

---

### Recommendation

Add an ownership check to `request_refund`. The simplest fix is to require the caller to be `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient can request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always `Some` for refund requests, so the refund address is pre-committed in the deposit message at deposit time and cannot be overridden by a third party. This mirrors the fix applied in the referenced report: replacing `addStakeTo` (which allowed a caller to set parameters for another account) with `addStake` (which only allows the caller to act on their own record).

---

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }` and sends BTC to the returned address.
2. The deposit is never finalized (e.g., relayer outage).
3. Attacker observes the BTC transaction on-chain and reconstructs the identical `deposit_msg` (it is the public input to the deposit address derivation).
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's tx>,
     vout = <victim's vout>,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
5. In `request_refund_callback`, the guard at line 154 is skipped because `deposit_msg.refund_address` is `None`. The `RefundRequest` is stored with `refund_address = "attacker_btc_address"`.
6. After `unsafe_refund_timelock_sec` elapses (assuming DAO does not reject), attacker calls `execute_refund(utxo_storage_key, None)`.
7. `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to `"attacker_btc_address"`, requests an MPC signature, and marks the UTXO as verified — permanently blocking any future `verify_deposit` for the victim.
8. Once the BTC transaction confirms, `verify_refund_finalize` cleans up state. The victim's BTC is irreversibly in the attacker's wallet. [6](#0-5)

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
