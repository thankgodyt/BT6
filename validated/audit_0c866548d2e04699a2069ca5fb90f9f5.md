### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a placeholder that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or stake-based checks. The production node-to-node diffusion handler wires this directly into the live cert-inbound path. Any unprivileged peer can therefore inject arbitrary Peras certificates, which are accepted, stored in the `PerasCertDB`, and used to compute `PerasWeightSnapshot` values that drive chain selection.

This is the direct analog of the reported bug class: a placeholder/wrong value (unconditional acceptance) is used in place of the correct current value (actual cryptographic + committee-stake validation), causing downstream calculations (chain-weight decisions) to be based on fabricated data.

---

### Finding Description

**Root cause — `validatePerasCert` placeholder:** [1](#0-0) 

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every `PerasCert` received from any peer is wrapped in `Right ValidatedPerasCert` with the full configured `perasWeight`. No signature, no committee membership check, no round-number sanity check, no boosted-block ancestry check.

**Production wiring — cert diffusion inbound handler:** [2](#0-1) 

The `hPerasCertDiffusionClient` handler calls `makePerasCertPoolWriterFromChainDB`, which passes `validatePerasCert mkPerasParams` directly as the validation function: [3](#0-2) 

`processCerts` then calls this validator on every inbound cert and, on `Right`, immediately calls `addPerasCertAsync` on the `ChainDB`: [4](#0-3) 

**Downstream effect — weight snapshot used in chain selection:**

Accepted certificates are stored in `PerasCertDB` and immediately reflected in `getPerasWeightSnapshot`, which is exposed on the `ChainDB` API and consumed by chain selection: [5](#0-4) 

The weight snapshot assigns `vpcCertBoost` (= `perasWeight params`) to every block boosted by an accepted certificate. Because `validatePerasCert` accepts any cert for any block point, an attacker can boost an arbitrary block on a non-canonical fork.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point and any round number. The receiving node accepts it unconditionally, stores it, and applies the full Peras weight boost to the named block during chain selection. If the attacker targets a block on a minority or adversarial fork, the honest node may compute that fork as heavier than the canonical chain and switch to it — a chain-selection safety failure driven entirely by fabricated certificate data.

This matches the allowed impact: **Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance**, and **High — chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The cert-diffusion miniprotocol is active in the production node-to-node handler. Any connected peer (no special privileges required) can send a `PerasCert` message. The attack requires only constructing a valid CBOR-encoded `PerasCert` struct (round number + block point), which is trivially derivable from the serialisation instances: [6](#0-5) 

No key material, no stake, no operator access is needed.

---

### Recommendation

Replace the placeholder `validatePerasCert` with a real implementation that verifies:
1. The certificate's cryptographic signature against the committee's aggregate key for the claimed round.
2. That the voter set meets the quorum threshold using the correct epoch's stake distribution (analogous to using `slot0`'s `sqrtPriceX96` rather than a stale oracle value).
3. That the boosted block point exists on a chain the node has seen.

Until real validation is in place, the cert-diffusion inbound handler should either be disabled or gated behind a feature flag that is off by default on production nodes.

### Proof of Concept

1. Connect to a production node running this code as a peer via the node-to-node miniprotocol.
2. Send a `PerasCertDiffusion` message containing a `PerasCert` with:
   - `pcCertRound = PerasRoundNo <any_round>`
   - `pcCertBoostedBlock = <point of a block on a minority fork>`
3. The node calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
4. `addPerasCertAsync` stores the cert; `getPerasWeightSnapshot` now returns a snapshot boosting the minority-fork block by `perasWeight params`.
5. Chain selection computes the minority fork as heavier and switches to it. [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
