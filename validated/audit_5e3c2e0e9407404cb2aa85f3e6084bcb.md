### Title
Peras Certificate Validation Completely Bypassed — Any Peer Can Inject Arbitrary Certificates to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or eligibility verification. This instance is wired directly into the live `processCerts` inbound pipeline used by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`. An unprivileged peer can therefore inject an arbitrary `PerasCert` — for any round, boosting any block — and every honest node will accept and store it, causing those nodes to apply a chain-selection boost to an attacker-chosen block.

### Finding Description

**Root cause.** The `BlockSupportsPeras` instance for all `StandardHash blk` types implements `validatePerasCert` as an unconditional success:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee membership, no round-number plausibility, and no quorum check is performed. The `Either` return type that is supposed to carry a `PerasValidationErr` on failure is structurally bypassed: the `Left` branch is never reachable.

**Wiring into the live inbound pipeline.** `processCerts` is the function that handles every batch of `PerasCert` objects received from a remote peer. It calls the supplied `validateCert` callback on each certificate not already in the database, and only rejects the batch if at least one call returns `Left`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Both production pool-writer constructors pass `validatePerasCert mkPerasParams` as that callback:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [3](#0-2) [4](#0-3) 

Because `validatePerasCert` never returns `Left`, `partitionEithers` always produces an empty error list, and every inbound certificate — regardless of content — is timestamped and stored.

**Analogy to the reference report.** The reference vulnerability is that `receiveToken()` returns the actual amount transferred, but the caller ignores that return value and continues using the original `amountIn`. Here, `validatePerasCert` returns an `Either` that is supposed to signal rejection, but the implementation hard-codes `Right`, so the rejection path is structurally unreachable. In both cases a validation step whose result should gate further processing is silently bypassed.

### Impact Explanation

Every accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`:

```haskell
ValidatedPerasCert
  { vpcCert = cert
  , vpcCertBoost = perasWeight params
  }
``` [5](#0-4) 

This boost is applied during chain selection. An attacker who can connect to a node as a peer can craft a `PerasCert` naming any `(round, block-point)` pair and have it stored with full boost weight. Honest nodes will then prefer the attacker-chosen block over the canonical chain, constituting a **chain-selection safety failure** driven entirely by unauthenticated peer input. This matches the "High / Critical" impact tier: bypass of Peras certificate checks enabling unauthorized certificate acceptance and non-canonical chain preference.

### Likelihood Explanation

The entry path requires only a standard peer connection — no keys, no stake, no privileged access. The object-diffusion mini-protocol for Peras certificates is reachable by any peer the node accepts. The attacker needs only to construct a well-formed `PerasCert` CBOR value (the serialisation format is public) and send it. Likelihood is high.

### Recommendation

Replace the stub with a real implementation that verifies:
1. The certificate's aggregate BLS signature against the claimed voter set.
2. That each claimed voter is a legitimate committee member with positive stake for the relevant epoch.
3. That the aggregate voter weight meets the quorum threshold.
4. That the round number is within the acceptable window.

Until the real implementation is ready, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the security boundary is closed rather than open by default.

### Proof of Concept

1. Establish a peer connection to an honest node running this code.
2. Craft a `PerasCert` with `pcCertRound = <target round>` and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. Send the certificate via the Peras certificate object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
5. The certificate is stored in the `PerasCertDB` / `ChainDB` with `vpcCertBoost = perasWeight params`.
6. Chain selection on the honest node now applies the Peras boost to the attacker-chosen block, causing it to prefer that block over the canonical tip.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
