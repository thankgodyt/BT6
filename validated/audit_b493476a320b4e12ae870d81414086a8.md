### Title
Light Client Callback Panics on Failure Instead of Returning `false`, Causing Permanent Loss of User NEAR Storage Deposit - (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`, `contracts/satoshi-bridge/src/btc_light_client/withdraw.rs`)

---

### Summary

Every light-client verification callback in the bridge uses `.expect()` on `env::promise_result_checked()`. When the light-client cross-contract call fails for any reason, the callback panics instead of returning `false`. The most harmful instance is `request_refund_callback`: the user's NEAR storage deposit (attached to the original `request_refund` call) is already transferred to the contract before the callback executes, so it is permanently stranded in the contract when the callback panics and rolls back all state changes. The deposit/withdraw callbacks produce a stuck-state that requires a retry, but the refund path causes an unrecoverable loss of user funds.

---

### Finding Description

The external report identifies the vulnerability class as: **a function that should handle errors gracefully (return 0 / `false`) instead panics/reverts, breaking the caller's assumption about error semantics.**

The exact same pattern exists throughout the bridge's light-client verification callbacks. Every callback that wraps a `verify_transaction_inclusion` cross-contract call uses the following pattern:

```rust
// contracts/satoshi-bridge/src/refund.rs  (request_refund_callback, line 505-506)
let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
    .expect("Call verify_transaction_inclusion failed");
``` [1](#0-0) 

The same `.expect()` pattern appears in:

- `verify_refund_finalize_callback` [2](#0-1) 
- `unavailable_utxo_callback` [3](#0-2) 
- `verify_migrate_deposit_callback` [4](#0-3) 
- `verify_deposit_callback` [5](#0-4) 
- `verify_safe_deposit_callback` [6](#0-5) 
- `internal_verify_withdraw_callback` [7](#0-6) 

By contrast, the chain-signature callbacks in the same contract correctly use `if let Ok(...)` to handle failures gracefully and return `false`:

```rust
// contracts/satoshi-bridge/src/chain_signature.rs (sign_btc_transaction_callback, line 141)
if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
    ...
    true
} else {
    false
}
``` [8](#0-7) 

The inconsistency is clear: the MPC signing path handles failures gracefully; the light-client verification path does not.

**Root cause of the most harmful instance — `request_refund_callback`:**

`internal_request_refund` requires the caller to attach a NEAR storage deposit before the cross-contract call chain is initiated:

```rust
// contracts/satoshi-bridge/src/refund.rs, line 146-149
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
``` [9](#0-8) 

This NEAR is transferred to the contract in Receipt 1 (the `request_refund` call). The light-client call is dispatched in Receipt 2. The callback executes in Receipt 3. If the light-client call fails (Receipt 2 panics), `env::promise_result_checked()` returns `Err(...)`, and `.expect()` panics Receipt 3. NEAR's execution model rolls back all state changes made in Receipt 3, but the NEAR transfer from Receipt 1 is a separate, already-finalized receipt — it is **not** rolled back. The user's storage deposit is permanently stranded in the contract with no automated recovery path.

---

### Impact Explanation

**Medium.** The `request_refund_callback` panic causes broken callback rollback: the refund request is never stored (state rolled back), but the user's NEAR storage deposit — sized to cover up to ~2 NEAR for the maximum 200 KB `tx_bytes` — is permanently lost in the contract. There is no automated mechanism to return it; recovery requires DAO intervention. For the deposit and withdraw callbacks, the impact is a stuck bridge state: the UTXO is not marked verified and the pending info stays in `PendingVerify`, requiring the user to retry once the light client recovers.

---

### Likelihood Explanation

The light-client cross-contract call (`verify_transaction_inclusion` / `verify_transaction_inclusion_v2`) can fail due to:
- Transient gas exhaustion in the light-client contract
- A bug in the light-client triggered by a specific block hash or merkle proof
- A light-client upgrade or migration that temporarily breaks the interface

Any user who calls `request_refund` during such a window loses their NEAR storage deposit. The `request_refund` entrypoint is publicly reachable (any bridge user with a failed deposit can call it). [10](#0-9) 

---

### Recommendation

Replace `.expect()` with graceful error handling in all light-client verification callbacks, mirroring the pattern already used in `sign_btc_transaction_callback`:

```rust
// Before (panics on light-client failure):
let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
    .expect("Call verify_transaction_inclusion failed");

// After (returns false on light-client failure):
let result_bytes = match env::promise_result_checked(0, MAX_BOOL_RESULT) {
    Ok(bytes) => bytes,
    Err(_) => return false, // or PromiseOrValue::Value(false)
};
```

For `request_refund_callback` specifically, also refund the user's NEAR storage deposit when the light-client call fails, to prevent permanent loss of user funds.

---

### Proof of Concept

1. User calls `request_refund` attaching the required NEAR storage deposit (e.g., 2 NEAR).
2. `internal_request_refund` validates inputs and dispatches `verify_transaction_inclusion_promise` to the light-client contract.
3. The light-client call fails (e.g., transient gas exhaustion or a bug triggered by the submitted proof).
4. `request_refund_callback` is invoked with a failed promise result.
5. `env::promise_result_checked(0, MAX_BOOL_RESULT)` returns `Err(...)`.
6. `.expect("Call verify_transaction_inclusion failed")` panics the callback.
7. All state changes in the callback are rolled back — the refund request is never stored.
8. The user's 2 NEAR storage deposit, transferred in the original `request_refund` receipt, is permanently stranded in the contract with no automated recovery path. [11](#0-10)

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
