Looking at the external report's vulnerability class — **a security check that should apply universally is only applied in a specific branch, allowing bypass through an alternative code path** — I need to find an analog in Ouroboros Consensus where a validation check is conditionally absent.

The most direct analog is in the `BlockSupportsPeras` default instance.

---

### Title
Peras Certificate Validation Universally Bypassed via Stub `validatePerasCert` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `BlockSupportsPeras` type class defines `validatePerasCert` as the mandatory gate for accepting a Peras certificate before it can influence chain selection. The universal default instance for all block types unconditionally returns `Right` (success) without performing any cryptographic or structural checks. Any certificate, regardless of content, is accepted and assigned the full `perasWeight` boost. This is structurally identical to the GuardCM bug: a restriction that must apply universally is absent in the only reachable code path.

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the entry point for certificate validation: [1](#0-0) 

The universal instance that covers all block types (including production Cardano blocks, since no more-specific instance overrides it) implements this as a stub that always succeeds: [2](#0-1) 

The comment explicitly acknowledges the missing validation:

```
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

The same instance also omits vote-signature verification in `validatePerasVote`, checking only stake-distribution membership while ignoring the cryptographic signature: [3](#0-2) 

The ChainDB chain-selection code consumes the result of `validatePerasCert` (via `addPerasCert`) and uses the returned `ValidatedPerasCert` to trigger `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Because `validatePerasCert` always returns `Right` with the full weight, any certificate that reaches `addPerasCert` — regardless of whether it carries a valid aggregate signature, a valid election ID, or legitimate voter membership — will be accepted and will trigger chain selection for the block it claims to boost.

The parallel to GuardCM is exact:

| GuardCM | Ouroboros Consensus |
|---|---|
| `delegatecall` restriction only enforced when `to == owner` | Certificate validation only enforced when… never |
| All other `delegatecall` targets bypass the guard | All certificates bypass validation |
| CM gains unrestricted protocol control | Attacker gains unrestricted chain-selection weight |

### Impact Explanation

An unprivileged peer that can deliver a `PerasCert` message to a node's `addPerasCert` handler can craft a certificate that:

1. Claims to boost any block already in the node's VolatileDB.
2. Passes `validatePerasCert` unconditionally.
3. Causes `chainSelectionForBlock` to run for that block with the full Peras weight boost.

This allows the attacker to make an honest node prefer a non-canonical or adversarially-chosen chain over the honest chain, violating chain-selection safety. The weight boost assigned by Peras is the mechanism by which Peras accelerates finality; if it can be forged freely, the entire chain-selection ordering is attacker-controlled for any block in the volatile window.

### Likelihood Explanation

The `BlockSupportsPeras` instance is the only instance in the codebase (no more-specific instance for `CardanoBlock` or `HardForkBlock` overrides it). The chain-selection code that consumes `ValidatedPerasCert` is present in the production `ChainDB` module. The primary uncertainty is whether a network miniprotocol for delivering Peras certificates to peers is currently active on mainnet. The `getPerasCertInBlock _ = Nothing` stub suggests the full Peras pipeline is not yet live, which reduces immediate exploitability. However, the stub is in production code with no feature flag, and any partial activation of the Peras receive path would immediately expose the bypass.

### Recommendation

Replace the stub with a real implementation that:
1. Verifies the aggregate vote signature over `(electionId, candidate)` against the aggregated public keys of the claimed voters.
2. Verifies each claimed voter's membership in the committee for the given election.
3. Verifies that the quorum threshold is met by the combined stake of verified voters.
4. Rejects any certificate that fails any of these checks with an appropriate `PerasValidationErr`.

Until a real implementation exists, the `addPerasCert` entry point should refuse all externally-sourced certificates (e.g., by returning an error or by gating on a feature flag), so that the absent validation cannot be reached from network input.

### Proof of Concept

A peer sends a `WFALSCert` (or the equivalent `PerasCert` for the production block type) with:
- An arbitrary `electionId`
- A `candidate` pointing to any block hash in the target node's VolatileDB
- A `voters` map with any seat indices
- A zeroed or random `aggSig`

`validatePerasCert` is called and returns:
```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

`addPerasCert` proceeds to call `chainSelectionForBlock` for the boosted block. The node now treats that block as having the full Peras weight, potentially switching to the attacker's chain. [5](#0-4) [6](#0-5)
