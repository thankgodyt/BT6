### Title
Stub `validatePerasCert` Enables Unbounded Peras Weight Accumulation via Forged Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally accepts every inbound certificate. Combined with the additive `PerasWeightSnapshot` accumulation logic, an unprivileged peer can send an unbounded number of forged certificates—each for a distinct round number but all boosting the same block—causing a victim node to assign arbitrarily large chain weight to an attacker-chosen block and switch to a non-canonical chain.

---

### Finding Description

**Root cause 1 — stub certificate validation always returns `Right`**

The `BlockSupportsPeras` instance used in production (via `mkPerasParams`) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No BLS aggregate signature check, no quorum membership check, no round-number range check, and no check that the boosted block is on any known chain is performed. [1](#0-0) 

The same stub is wired into both production object-diffusion writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

**Root cause 2 — `PerasCertDB` deduplicates only by `roundNo`**

`implAddCert` rejects a certificate only if its `roundNo` is already present in `pcdsCertIds`. Certificates for distinct round numbers are always stored, even if they boost the same block:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do ...
``` [4](#0-3) 

**Root cause 3 — `PerasWeightSnapshot` accumulates boosts additively**

`addToPerasWeightSnapshot` uses `Map.insertWith (<>)`, where `(<>)` for `PerasWeight` is integer addition (`deriving via Sum Word64`). Every certificate stored in `pcdsCertsByTicket` contributes its boost to the same block point:

```haskell
addToPerasWeightSnapshot pt weight =
  PerasWeightSnapshot . Map.insertWith (<>) pt weight . getPerasWeightSnapshot
``` [5](#0-4) 

`implGetWeightSnapshot` iterates over all stored certificates and feeds them into `mkPerasWeightSnapshot`, so N certificates boosting the same block produce a total boost of `N × perasWeight`: [6](#0-5) 

**Root cause 4 — `processCerts` performs no additional round-number or chain-membership checks**

The inbound certificate pipeline reads the current `certIds` set once, filters out known rounds, calls the stub validator, and inserts the rest. There is no check that the round number is plausible for the current epoch, that the boosted block exists in the local chain, or that the boost weight is within any bound: [7](#0-6) 

**Exploit sequence (analog to the Alchemix reset+merge loop)**

| Alchemix step | Ouroboros analog |
|---|---|
| `reset(tokenId)` accrues flux proportional to balance | Peer sends cert for round R boosting block B; `perasWeight` is added to B's snapshot entry |
| `merge(tokenId1, tokenId2)` transfers accumulated flux | Peer sends cert for round R+1 boosting the same block B; another `perasWeight` is added |
| Repeat N times → N× flux | Repeat for rounds R, R+1, …, R+N-1 → total boost = N × `perasWeight` |

The attacker constructs N `PerasCert` values with distinct `pcCertRound` fields and the same `pcCertBoostedBlock`. Each passes `validatePerasCert` (stub), each passes the `roundNo` deduplication check, and each adds `perasWeight` to the snapshot. Chain selection then computes:

```
wsvTotalWeight = blockNo + N × perasWeight
``` [8](#0-7) 

making any chain containing block B appear heavier than any honest chain, regardless of actual chain length.

---

### Impact Explanation

An unprivileged peer can make an honest node permanently prefer a non-canonical chain by inflating the Peras weight of an attacker-chosen block without bound. This directly subverts the Peras chain-selection invariant that weight boosts are bounded by the number of legitimately certified rounds. The node will switch to the attacker's chain and refuse to switch back as long as the inflated weight persists in the snapshot (until garbage collection, which the attacker can outpace by sending fresh certificates for recent rounds).

This matches the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, and also the **Critical** category: *bypass of Peras certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

The attack requires only network access to a running node. The attacker needs to:
1. Connect as a peer via the object-diffusion mini-protocol.
2. Send a batch of `PerasCert` objects with distinct round numbers and the same boosted block.

No stake, no keys, no prior chain knowledge beyond a single block hash is required. The stub validation is wired into both the `PerasCertDB`-direct and `ChainDB`-backed writers, so both code paths are affected. The attack is trivially automatable.

---

### Recommendation

1. **Replace the stub `validatePerasCert`** with a real implementation that verifies the aggregate BLS signature, checks that the voter set constitutes a valid quorum from the stake distribution for the relevant epoch, and confirms the boosted block is within the rollback window.
2. **Add a round-number range check** in `processCerts` (or `implAddCert`) to reject certificates whose round number is implausibly far in the past or future relative to the current slot.
3. **Add a per-block boost cap** in `addToPerasWeightSnapshot` or in `implGetWeightSnapshot` to enforce that the total boost for any single block cannot exceed `perasWeight × maxCertsPerBlock` for some protocol-defined constant.
4. Track the referenced GitHub issue [tweag/cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120) as a security-critical blocker before any production deployment.

### Proof of Concept

```haskell
-- Attacker sends N certificates, all boosting the same block B,
-- each with a distinct round number.
attackInflateWeight :: ChainDB IO TestBlock -> Point TestBlock -> Int -> IO ()
attackInflateWeight chainDB blockB n = do
  now <- getCurrentTime
  forM_ [0 .. n - 1] $ \i -> do
    let cert = WithArrivalTime now $
          ValidatedPerasCert
            { vpcCert  = PerasCert
                { pcCertRound        = PerasRoundNo (fromIntegral i)
                , pcCertBoostedBlock = blockB
                }
            , vpcCertBoost = perasWeight mkPerasParams
            }
    -- validatePerasCert is a stub: always Right, no signature check
    void $ addPerasCertSync chainDB cert

-- After the loop, getPerasWeightSnapshot returns a snapshot where
-- weightBoostOfPoint snap blockB == n * perasWeight mkPerasParams
-- Chain selection will unconditionally prefer any chain containing blockB.
```

The `validatePerasCert` stub at `SupportsPeras.hs:353–358` ensures every certificate is accepted. The `implAddCert` deduplication at `PerasCertDB/Impl.hs:178` passes because each `pcCertRound` is unique. The `implGetWeightSnapshot` loop at `PerasCertDB/Impl.hs:209–213` sums all N boosts for `blockB` via `mkPerasWeightSnapshot`, and `weightedSelectView` at `SelectView.hs:104–112` uses this inflated snapshot for chain comparison. processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
