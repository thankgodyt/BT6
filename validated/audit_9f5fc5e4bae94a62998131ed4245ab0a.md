Audit Report

## Title
Finalized Transfer Record Removed on `ft_transfer_call` Rejection Enables Cross-Chain Replay Double-Spend — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When an inbound transfer to NEAR uses `ft_transfer_call` and the recipient contract rejects the tokens (returning the full amount from `ft_on_transfer`), `fin_transfer_send_tokens_callback` removes the transfer ID from `finalised_transfers` via `remove_fin_transfer`. This permanently erases the only replay guard for that transfer, allowing the identical source-chain proof to be re-submitted and finalized a second time, resulting in unauthorized minting (for bridge-deployed tokens) or double-unlock (for escrow-locked tokens).

## Finding Description

`process_fin_transfer_to_near` (line 1875) calls `add_fin_transfer`, which inserts the `TransferId` into `finalised_transfers` and panics if it is already present: [1](#0-0) [2](#0-1) 

When the transfer includes a non-empty `msg`, `send_tokens` issues an `ft_transfer_call`. If the recipient's `ft_on_transfer` returns the full amount (rejection), `ft_transfer_call` resolves to `0`. `is_refund_required` detects this: [3](#0-2) 

In the refund branch of `fin_transfer_send_tokens_callback`, after burning tokens and reverting lock actions, the code calls `remove_fin_transfer` at line 1714, which unconditionally removes the `TransferId` from `finalised_transfers`: [4](#0-3) [5](#0-4) 

Once removed, `add_fin_transfer`'s `require!(self.finalised_transfers.insert(transfer_id), ...)` will succeed again for the same `TransferId`, because the set no longer contains it. The `msg` field that triggers `ft_transfer_call` originates from the attacker-controlled `message` parameter of `initTransfer` on the EVM side and is propagated verbatim into the NEAR `TransferMessage`: [6](#0-5) 

## Impact Explanation

**Deployed (bridge-minted) tokens**: First finalization mints tokens and sends via `ft_transfer_call`; attacker's contract rejects them; `burn_tokens_if_needed` burns the returned tokens; `remove_fin_transfer` erases the replay guard. Re-submission mints a fresh batch delivered to the attacker — unauthorized minting backed by no new source-chain lock.

**Native (escrow-locked) tokens**: First finalization decrements the escrow counter via `unlock_tokens_if_needed`; attacker rejects; `revert_lock_actions` re-increments the counter; `remove_fin_transfer` erases the guard. Re-submission decrements the counter again and delivers tokens — double-unlock draining the escrow.

Both outcomes match the critical impact class: cross-chain replay enabling double-spending / unauthorized minting of bridged funds.

## Likelihood Explanation

No privileged access is required. The attacker needs only: (1) tokens on the source chain (normal user capability); (2) a non-empty `message` in `initTransfer` (fully attacker-controlled parameter); (3) a NEAR recipient contract they deploy whose `ft_on_transfer` returns the full amount on the first call and `0` on the second — trivial to implement. The same Wormhole VAA or light-client proof is reusable after the finalization record is erased. The attack is repeatable and requires no timing luck or race condition.

## Recommendation

Do not remove the `TransferId` from `finalised_transfers` on the refund path. The finalization record must be permanent regardless of whether the downstream `ft_transfer_call` succeeded or failed. The token refund (burn + revert lock actions) can proceed without erasing the replay guard. If tracking failed finalizations for UX or retry purposes is needed, introduce a separate `failed_transfers` set or a status enum, leaving the entry in `finalised_transfers` intact.

Concretely, remove the call to `self.remove_fin_transfer(...)` at line 1714 from the refund branch of `fin_transfer_send_tokens_callback`: [7](#0-6) 

## Proof of Concept

1. Attacker deploys `MaliciousRecipient` on NEAR whose `ft_on_transfer` returns the full `amount` on the first call and `0` on the second.
2. Attacker calls `initTransfer` on EVM with `message = "trigger"` and `recipient = "malicious_recipient.near"`.
3. Relayer submits the proof to `fin_transfer_callback` on NEAR.
4. `add_fin_transfer` inserts `TransferId { origin_chain: Eth, origin_nonce: N }` into `finalised_transfers`.
5. `unlock_tokens_if_needed` decrements the escrow counter by `amount` (or tokens are minted for deployed tokens).
6. `send_tokens` issues `ft_transfer_call`; `MaliciousRecipient.ft_on_transfer` returns `amount` → `ft_transfer_call` resolves to `0`.
7. `fin_transfer_send_tokens_callback` fires: `is_refund_required` returns `true`; tokens are burned/re-locked; `remove_fin_transfer` erases the `TransferId` from `finalised_transfers`.
8. Attacker re-submits the identical proof to `fin_transfer_callback`.
9. `add_fin_transfer` succeeds (ID no longer in set); escrow decremented again; `ft_transfer_call` issued; `MaliciousRecipient.ft_on_transfer` returns `0` → tokens delivered.
10. Attacker receives tokens for a single source-chain lock event — double-spend confirmed.

A local integration test can reproduce this by: deploying the bridge contract and a mock NEP-141 token, registering a `MaliciousRecipient` contract, calling `fin_transfer_callback` twice with the same serialized `ProverResult::InitTransfer`, and asserting that the second call succeeds and the recipient's balance increases.

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }
