### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Sent Peras Certificate, Enabling Unauthorized Chain-Selection Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic validation. Because this function is wired directly into the live ObjectDiffusion inbound pipeline, any unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and an arbitrary boosted-block pointer. The certificate is accepted, stored in the `PerasCertDB`, and immediately fed into chain selection, where it applies a full `perasWeight` boost (default: 15) to the targeted block. This lets a peer artificially tip chain selection toward a non-canonical fork without possessing any quorum of stake.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate that must verify a certificate before it is trusted:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The sole production instance (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`) implements this as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No checks are performed on:
- The aggregate BLS signature over the election identifier and boosted block
- Voter eligibility proofs
- Whether the claimed quorum of stake actually signed the certificate
- Whether the round number is plausible relative to the current chain state

This stub is directly wired into the live inbound certificate pipeline in `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator on every inbound certificate from a peer. If validation returns `Right`, the certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`chainSelSync` then processes the certificate. If the boosted block is present in the VolatileDB, it immediately triggers a full chain-selection run for that block with the artificial weight boost applied: [4](#0-3) 

The weight boost is drawn from `perasWeight params`, which is `PerasWeight 15` in `mkPerasParams`: [5](#0-4) 

The security parameter `k = 2160` means the VolatileDB holds up to 2160 blocks. Any of those blocks can be targeted by a crafted certificate.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A peer with no stake can send a `PerasCert` pointing to any block in the node's VolatileDB. The node applies a weight boost of 15 to that block's chain fragment. Under Peras chain selection, total weight = block number + weight boost. A fork that is 15 blocks shorter than the current selection becomes equally preferred once boosted; a fork that is 14 blocks shorter becomes strictly preferred. Because the VolatileDB spans up to `k` blocks, an attacker can target forks deep in the volatile window. This constitutes an unauthorized chain-selection manipulation: the node may roll back up to 15 blocks and adopt a non-canonical chain that it would never have selected under honest conditions, violating the Peras security assumption that only a quorum of stake can produce a valid certificate.

---

### Likelihood Explanation

**Medium.** The ObjectDiffusion mini-protocol is reachable by any peer the node connects to. No stake, no key material, and no prior knowledge beyond the node's VolatileDB contents (obtainable via ChainSync) is required. The attacker only needs to craft a `PerasCert` CBOR structure with a valid `PerasRoundNo` and a `Point blk` matching a block hash in the VolatileDB. The stub validation means the certificate is accepted regardless of its cryptographic content.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation before the ObjectDiffusion certificate pipeline is enabled in production. At minimum, the implementation must:

1. Verify the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the claimed voter set.
2. Verify each voter's eligibility proof against the committee selection data for the given round.
3. Confirm that the total stake of the verified voters exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
4. Reject certificates whose `pcCertRound` is outside the valid window relative to the current chain tip.

Until this is implemented, the ObjectDiffusion certificate inbound path should be disabled or gated behind a feature flag that is off by default in production builds.

---

### Proof of Concept

An attacker node connects to a victim node and observes (via ChainSync) that the victim's VolatileDB contains a fork block `B_fork` at block number `N`, while the victim's current selection tip is at block number `N + 14` (i.e., the fork is 14 blocks behind).

The attacker serialises the following CBOR structure and sends it via the ObjectDiffusion certificate mini-protocol:

```
PerasCert {
  pcCertRound      = <any PerasRoundNo>,
  pcCertBoostedBlock = <Point of B_fork>,
  pcVoters         = <empty or arbitrary voter bitmap>,
  pcSignature      = <arbitrary bytes>
}
```

On the victim node, `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }
``` [6](#0-5) 

The certificate is added to the `PerasCertDB`. `chainSelSync` finds `B_fork` in the VolatileDB and triggers chain selection. The fork's total weight becomes `N + 15`, which exceeds the current selection's weight of `N + 14`. The victim node rolls back 14 blocks and adopts the attacker's fork — without the attacker possessing any stake or valid cryptographic material.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
