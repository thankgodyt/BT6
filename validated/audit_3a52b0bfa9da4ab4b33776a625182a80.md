### Title
Peras Certificate Verification Bypass via Unconditional `Right` in `validatePerasCert` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default production instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound Peras certificate without performing any cryptographic or structural validation. This instance is wired directly into the production miniprotocol inbound path (`makePerasCertPoolWriterFromChainDB`) and the `PerasCertDB` path. An unprivileged peer can send a crafted `PerasCert` message with an arbitrary boosted-block pointer; the node will accept it, store it, apply a chain-weight boost of 15 to the targeted block, and potentially switch to a non-canonical fork — all without any signature, quorum, or voter-set check.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params   -- always PerasWeight 15
        }
```

No aggregate BLS signature is verified, no voter set is checked, no quorum threshold is enforced, and no round-number or boosted-block constraints are applied. The function is structurally identical to the `ecrecover()` analog: it never returns `Left`, so the caller's error-handling branch is unreachable.

**Production wiring — both ChainDB and PerasCertDB paths use this stub:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the `validateCert` argument to `processCerts`. The comment "TODO replace when actual plumbing is in place" confirms this is the live production path, not a test shim. [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate from a peer. Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch at line 184 is never reached; every certificate is unconditionally accepted and forwarded to `addCert`.

**Chain-selection consequence:**

Once a `ValidatedPerasCert` is stored in the `PerasCertDB`, `chainSelSync` in `ChainSel.hs` triggers `chainSelectionForBlock` for the boosted block: [4](#0-3) 

The boosted block receives a weight of `PerasWeight 15` (from `mkPerasParams`). Chain selection then compares candidates by total weight (block count + boost sum). A fork that is up to 15 blocks shorter than the honest chain can be preferred if it contains the attacker-boosted block.

---

### Impact Explanation

**High — Chain selection manipulation via unauthorized certificate acceptance.**

An unprivileged peer can cause an honest node to switch to a non-canonical fork by sending a single crafted `PerasCert` message. The boost of 15 weight units means a fork up to 15 blocks shorter than the current selection can be preferred. This violates the Peras security assumption that only certificates backed by a quorum of honest stake can influence chain selection. The node's `PerasCertDB` is permanently polluted with the forged certificate, and the chain-selection side-effect (`chainSelectionForBlock`) is triggered immediately upon receipt.

---

### Likelihood Explanation

**High.** Any peer connected via the Peras certificate miniprotocol can send a `PerasCert` message. No stake, key material, or privileged access is required. The attacker only needs to know (or guess) the hash of a block on a competing fork — information that is publicly observable on the network. The vulnerability is present in the current production code with no mitigating guard.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the aggregated public keys of the claimed voters.
2. Checks that the claimed voter set meets the quorum stake threshold.
3. Validates each voter's eligibility (seat index within bounds, non-zero stake).

Until the real implementation is ready, the stub should at minimum reject all inbound certificates from peers (return `Left PerasValidationErr` unconditionally) so that the network-facing path is closed. The `TODO` at `https://github.com/tweag/cardano-peras/issues/120` tracks this work.

---

### Proof of Concept

1. Connect to a target node as a Peras-certificate miniprotocol peer.
2. Identify a block `B` on a fork that is up to 15 blocks shorter than the node's current selection (observable from the chain-sync miniprotocol).
3. Construct a `PerasCert` with `pcCertRound = <any fresh round>` and `pcCertBoostedBlock = blockPoint B`. No valid signature or voter set is needed.
4. Send the certificate via the object-diffusion miniprotocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`.
6. The certificate is stored in `PerasCertDB`; `chainSelSync` calls `chainSelectionForBlock` for `B`.
7. If the fork containing `B` now has total weight ≥ the current selection's total weight, the node switches to the fork — accepting a non-canonical chain without any honest quorum backing the certificate.

  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
