### Title
Front-Running `request_refund` Allows Attacker to Redirect BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Any unprivileged NEAR account can call `request_refund` for any Bitcoin UTXO. The refund request is keyed solely by `txid@vout` — the caller's identity is never included. An attacker who observes a pending `request_refund` call in the NEAR transaction pool can front-run it with the same UTXO proof but substitute their own Bitcoin `refund_address`. The legitimate user's subsequent callback is then permanently rejected with "Refund request already exists for this UTXO," and after the `unsafe_refund_timelock_sec` elapses, the attacker can execute the refund and redirect the deposited BTC to their own address.

---

### Finding Description

`internal_request_refund` is an open, unpermissioned entry point. It accepts `deposit_msg`, `refund_address`, `tx_bytes`, `vout`, and a Merkle proof from any caller. [1](#0-0) 

After the light-client inclusion proof resolves, `request_refund_callback` derives the storage key exclusively from the Bitcoin transaction ID and output index: [2](#0-1) 

`generate_utxo_storage_key` produces `"<txid>@<vout>"` — the caller's NEAR account ID is absent: [3](#0-2) 

The duplicate-request guard then rejects any second submission for the same UTXO, regardless of who submitted the first: [4](#0-3) 

The `refund_address` stored in the winning `RefundRequest` is what `finalize_refund_with_psbt` uses to build the Bitcoin output: [5](#0-4) 

The only guard against a caller-supplied `refund_address` is that it must match `deposit_msg.refund_address` **when that field is set**: [6](#0-5) 

When `deposit_msg.refund_address` is `None` — the common case for users who did not pre-commit a refund address on-chain — the caller may supply any Bitcoin address, and no ownership check is performed.

**Attack path:**

1. Victim broadcasts `request_refund(deposit_msg={recipient_id: victim, refund_address: None, …}, refund_address: "victim_btc_addr", tx_bytes, vout, proof, …)`.
2. Attacker observes the pending NEAR transaction and immediately submits `request_refund` with identical `deposit_msg`, `tx_bytes`, `vout`, `proof` but `refund_address: "attacker_btc_addr"`.
3. Because NEAR transaction ordering is not guaranteed, the attacker's call lands first. The light-client proof passes; the `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`.
4. Victim's callback executes and panics: `"Refund request already exists for this UTXO"`. The victim cannot submit a new request for the same UTXO.
5. After `unsafe_refund_timelock_sec` elapses, the attacker (or anyone) calls `execute_refund`. `resolve_execute_refund_timelock` applies the longer timelock but does not restrict the caller: [7](#0-6) 

6. The refund PSBT is built paying `"attacker_btc_addr"`, signed by MPC, and broadcast. The victim's BTC is transferred to the attacker.

---

### Impact Explanation

The attacker redirects the victim's entire BTC deposit to an attacker-controlled Bitcoin address. The victim's NEAR-side `recipient_id` is unchanged (the `deposit_msg` must be identical to pass the script-pubkey check), so the victim receives no nBTC either — the deposit UTXO is consumed by the attacker's refund transaction. This constitutes direct, significant theft of user funds.

**Impact: Critical** — unauthorized redirection and theft of bridge-held BTC.

---

### Likelihood Explanation

- `request_refund` is fully open to any NEAR account; no role or whitelist is required.
- NEAR transaction ordering within a block is not guaranteed, making front-running straightforward for an attacker monitoring the RPC mempool.
- The `deposit_msg` is public (embedded in the Bitcoin transaction or observable from the victim's NEAR call arguments).
- The only partial mitigation is the `unsafe_refund_timelock_sec` window during which the DAO/Operator can call `internal_reject_refund`. This requires active, continuous monitoring and is not a protocol-level guarantee.

**Likelihood: Medium** — requires mempool observation and a race, but no privileged access and no cryptographic barrier.

---

### Recommendation

Include the caller's NEAR account ID in the refund request storage key (analogous to adding `proposer` to `proposalHash()` in the original report). For example:

```rust
// In request_refund_callback, key by (txid, vout, predecessor):
let utxo_storage_key = format!(
    "{}{}{}{}{}",
    tx_id,
    UTXO_STORAGE_KEY_TAG,
    vout,
    UTXO_STORAGE_KEY_TAG,
    env::predecessor_account_id()
);
```

Alternatively, enforce that only the `deposit_msg.recipient_id` (or a pre-authorized account) may submit a refund request for a given UTXO, and reject any submission from a different caller.

### Proof of Concept

```
// Victim submits (observed in NEAR mempool):
request_refund(
  deposit_msg = { recipient_id: "victim.near", refund_address: None },
  refund_address = "victim_btc_addr",
  tx_bytes = <victim_deposit_tx>,
  vout = 0,
  proof = <valid_merkle_proof>,
  gas_fee = None
)

// Attacker front-runs with identical proof, different refund_address:
request_refund(
  deposit_msg = { recipient_id: "victim.near", refund_address: None },
  refund_address = "attacker_btc_addr",   // <-- attacker's address
  tx_bytes = <victim_deposit_tx>,          // same tx
  vout = 0,
  proof = <valid_merkle_proof>,            // same proof
  gas_fee = None
)

// Attacker's request_refund_callback stores:
//   refund_requests["<txid>@0"] = RefundRequest { refund_address: "attacker_btc_addr", ... }

// Victim's request_refund_callback panics:
//   "Refund request already exists for this UTXO"

// After unsafe_refund_timelock_sec:
execute_refund(utxo_storage_key = "<txid>@0", ...)
// → MPC signs PSBT paying "attacker_btc_addr"
// → Victim's BTC stolen
```

The root cause is in `request_refund_callback` at the key derivation step: [2](#0-1) 
and the missing caller-identity binding in `generate_utxo_storage_key`: [3](#0-2)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
