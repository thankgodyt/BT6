### Title
Peras Vote Validation Skips Cryptographic Signature Check, Enabling Unauthorized Vote Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The blanket `BlockSupportsPeras` instance's `validatePerasVote` checks only whether the voter ID exists in the stake distribution (eligibility), but entirely omits verification of the vote's cryptographic signature (authentication). Separately, `validatePerasCert` unconditionally returns `Right`, bypassing all certificate validation. Both functions are called on every batch of inbound Peras objects received from an unprivileged peer via the ObjectDiffusion mini-protocol. An adversary can therefore inject forged votes attributed to any eligible voter, accumulate them to quorum, and cause the node to forge and accept a fraudulent Peras certificate that boosts an attacker-chosen chain.

### Finding Description

The `BlockSupportsPeras` type class defines two validation methods:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote ::
  PerasCfg blk ->
  PerasVoteStakeDistr ->
  PerasVote blk ->
  Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The only concrete instance in the codebase is the blanket instance for all `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

`validatePerasCert` always returns `Right` — no field of the certificate is checked. `validatePerasVote` only looks up the voter ID in the stake distribution; it never verifies the vote's cryptographic signature. A vote's `PerasVoterId` is a public key hash, so any peer that knows an eligible pool's ID can forge a vote for that pool without possessing the corresponding private key.

These functions are called directly in the production inbound-object pipeline:

```haskell
-- makePerasCertPoolWriterFromChainDB
processCerts systemTime (ChainDB.getPerasCertIds chainDB)
    (validatePerasCert mkPerasParams)          -- always Right
    (void . ChainDB.addPerasCertAsync chainDB)
    certs

-- makePerasVotePoolWriterFromChainDB
processVotes systemTime (ChainDB.getPerasVoteIds chainDB)
    (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
    (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
    votes
```

`processCerts` and `processVotes` apply the validation function to every object in the batch and add all objects that pass to the ChainDB. Because `validatePerasCert` always passes and `validatePerasVote` passes for any vote whose voter ID appears in the stake distribution, the signature check — the only check that binds a vote to its claimed author — is absent.

### Impact Explanation

**Impact: Critical.** An unprivileged peer can:

1. Send forged `PerasVote` objects claiming to be from any pool in the current stake distribution. Because `validatePerasVote` never verifies the signature, these votes are accepted and stored in the `PerasVoteDB`.
2. Once enough forged votes accumulate to reach quorum (`votesReachQuorum`), the node internally forges a `PerasCert` and adds it to the `PerasCertDB` via `addPerasVoteWithAsyncCertHandling`.
3. The resulting certificate carries a `vpcCertBoost` weight that is applied during Peras chain selection, causing the node to prefer the attacker-chosen chain over the honest chain.
4. Separately, the peer can send arbitrary `PerasCert` objects directly; `validatePerasCert` accepts all of them unconditionally, immediately injecting a weight boost for any block the attacker names.

This constitutes a bypass of Peras voting and certificate checks that enables unauthorized certificate acceptance and materially distorts chain selection.

### Likelihood Explanation

**Likelihood: High.** The entry path requires only a TCP connection to the node's ObjectDiffusion endpoint. No stake, no keys, and no privileged access are needed. The attacker only needs to know the `PerasVoterId` values (pool key hashes) of eligible voters, which are public on-chain data. The `processVotes` and `processCerts` handlers are invoked for every batch received from every connected peer.

### Recommendation

1. **`validatePerasVote`**: Add cryptographic signature verification before accepting a vote. The vote must be signed by the private key corresponding to the `PerasVoterId` (pool VRF/KES key or a dedicated vote key). Reject the vote if the signature does not verify.

2. **`validatePerasCert`**: Implement full certificate verification: check that the certificate's aggregate signature is valid over the claimed election ID and candidate, that the claimed voters are committee members, and that their combined stake meets the quorum threshold. The `implVerifyCert` logic in `Ouroboros.Consensus.Committee.EveryoneVotes` and `Ouroboros.Consensus.Committee.WFALS` shows the correct pattern.

3. Until real validation is in place, the blanket stub instance should not be reachable from the live ObjectDiffusion pipeline. Gate the `processVotes`/`processCerts` handlers behind a feature flag or replace the stub with a function that always returns `Left` (reject all) rather than `Right` (accept all).

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer TCP connection
  → ObjectDiffusion mini-protocol (PerasVote / PerasCert object diffusion)
  → makePerasVotePoolWriterFromChainDB / makePerasCertPoolWriterFromChainDB
  → processVotes / processCerts
  → validatePerasVote / validatePerasCert   ← stub, no signature check
  → ChainDB.addPerasVoteWithAsyncCertHandling / ChainDB.addPerasCertAsync
  → PerasVoteDB / PerasCertDB
  → chain selection weight boost applied
```

**Concrete steps:**

1. Observe the current stake distribution to enumerate eligible `PerasVoterId` values (public pool key hashes).
2. Construct `PerasVote` objects with `pvVoteRound = <target round>`, `pvVoteBlock = <attacker-chosen block point>`, `pvVoteVoterId = <any eligible pool ID>` — no signature field exists in the stub data type, so no key material is required.
3. Send enough such votes (one per eligible pool ID) to exceed the quorum threshold.
4. The receiving node's `processVotes` accepts all votes (each passes `lookupPerasVoteStake`), stores them, and when quorum is reached, internally forges a `PerasCert` boosting the attacker-chosen block.
5. Alternatively, send a single `PerasCert` directly; `validatePerasCert` returns `Right` unconditionally, and the cert is added to the `PerasCertDB` with full weight boost.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
