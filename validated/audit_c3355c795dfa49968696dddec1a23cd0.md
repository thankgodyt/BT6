Audit Report

## Title
Transfer Permanently Frozen When `normalize_amount(amount - fee) == 0` Due to Missing Pre-validation — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts outbound transfers without verifying that the net amount survives decimal normalization to the destination chain. When `sign_transfer` is later called, it computes `normalize_amount(amount_without_fee())` and panics if the result is zero. Because the fee can only be increased (never decreased) and no cancel/refund path exists for the user, the transfer is permanently deadlocked with tokens locked in the bridge.

## Finding Description

**Root cause — missing pre-validation in `init_transfer`**

`init_transfer` enforces only one amount constraint: [1](#0-0) 

It does not verify that `normalize_amount(amount - fee, decimals) > 0`. Tokens are immediately locked when `ft_on_transfer` returns `U128(0)`.

**Normalization uses floor division:** [2](#0-1) 

For a token with `origin_decimals = 18` and `decimals = 6`, `diff_decimals = 12`. Any `amount - fee < 10^12` normalizes to 0.

**`sign_transfer` panics and cannot proceed:** [3](#0-2) 

Every call to `sign_transfer` for this transfer reverts. The transfer message stays in `pending_transfers` indefinitely.

**Fee update cannot rescue the transfer.** The fee update path at line 400 rejects any decrease (`fee.fee >= current_fee.fee`): [4](#0-3) 

Increasing the fee makes `amount_without_fee()` even smaller, worsening the situation.

**No cancel or refund path exists.** A search of `lib.rs` confirms there is no `cancel_transfer`, `refund_transfer`, or equivalent user-callable function. The only removal of a transfer message occurs inside `sign_transfer_callback` on a successful MPC signature: [5](#0-4) 

Since `sign_transfer` always panics before reaching the MPC call, this removal path is never reached.

## Impact Explanation

This constitutes **permanent freezing of bridged funds** — a concrete critical impact under the allowed scope. A user's tokens are locked in the bridge contract with no mechanism to recover them. The `pending_transfers` entry persists forever, and the locked token balance is never returned.

## Likelihood Explanation

Any unprivileged bridge user can trigger this by calling `ft_transfer_call` with an `InitTransferMsg` whose net amount (`amount - fee`) is below the normalization threshold. For tokens with large decimal differences (e.g., 18 → 6), the threshold is `10^12` base units — a realistic transfer size (e.g., 0.000001 of an 18-decimal token). No special privileges or coordination are required. The condition is reachable through the standard public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow.

## Recommendation

Add a normalization check inside `init_transfer_internal` (or at the end of `init_transfer`) before accepting the transfer, mirroring the check already present in `sign_transfer`:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This ensures the transfer is rejected at initiation time (with a full token refund via `ft_on_transfer` returning the full amount) rather than silently accepted and permanently frozen.

## Proof of Concept

1. Register a token with `origin_decimals = 18`, `decimals = 6` (diff = 12).
2. Call `ft_transfer_call` with `amount = 999_999_999_999` (i.e., `10^12 - 1`) and `fee = 0`.
3. `init_transfer` accepts the message (`fee < amount` ✓). Tokens are locked (`ft_on_transfer` returns `U128(0)`).
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(999_999_999_999, {origin: 18, dest: 6}) = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics → transaction reverts.
7. Transfer remains in `pending_transfers`. Tokens remain locked.
8. Attempting to update the fee to a lower value is rejected with `ERR_INVALID_FEE` (line 400–402).
9. Increasing the fee reduces `amount_without_fee()` further, making normalization still 0.
10. No cancel path exists. Funds are permanently frozen.
