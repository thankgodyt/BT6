### Title
Missing Ownership Check in `withdraw_rbf` Allows Any Caller to RBF Another User's Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
The public `withdraw_rbf` function checks pending-sign capacity against the **caller's** account but passes the caller-supplied `original_btc_pending_verify_id` — which may belong to a **different** user — directly into `withdraw_rbf_chain_specific`. There is no assertion that the pending info identified by `original_btc_pending_verify_id` is owned by the caller. An unprivileged attacker can therefore trigger an RBF replacement of any victim's in-flight withdrawal, supplying attacker-controlled `output` values, which are then submitted to the MPC signing pipeline.

### Finding Description

`withdraw_rbf` is a public, unprivileged function (only gated by the pause flag):

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 259-274
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();
    self.require_pending_sign_capacity(&account_id);   // ← checked for CALLER

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller's account
        original_btc_pending_verify_id,      // ← arbitrary, caller-supplied ID
        output,                              // ← attacker-controlled outputs
        chain_specific_data,
    );
}
```

The capacity guard is evaluated against `env::predecessor_account_id()` (the attacker), while `original_btc_pending_verify_id` is passed unchecked. `withdraw_rbf_chain_specific` receives the **caller's** `account_id` alongside a pending-info ID that may belong to a **victim**.

Contrast this with the privileged `cancel_withdraw`, which correctly resolves the true owner from the stored pending info before proceeding:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 285-299
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id          // ← resolved from stored state, not from caller
        .clone();
    self.require_pending_sign_capacity(&user_account_id);
    self.cancel_withdraw_chain_specific(user_account_id, original_btc_pending_verify_id, ...);
}
```

The missing check in `withdraw_rbf` is exactly the analog of H-04: a caller-supplied identifier (`original_btc_pending_verify_id`) is used to drive a sensitive operation without verifying it matches the stored authoritative value (`btc_pending_info.account_id == env::predecessor_account_id()`).

### Impact Explanation

`withdraw_rbf_chain_specific` receives the attacker's `account_id` and the victim's pending-info ID together with attacker-controlled `output` (destination `TxOut` values). The function will build a replacement PSBT using the victim's locked UTXOs but with the attacker's outputs, then submit it to the MPC signing pipeline. Once MPC signs and the RBF transaction confirms on-chain, the victim's BTC is sent to the attacker-specified address. This constitutes **unauthorized redirection / theft of user funds** — Critical impact.

Even in a best-case scenario where `withdraw_rbf_chain_specific` enforces the original target address on outputs, the attacker can still create a competing RBF entry that interferes with the victim's withdrawal, causing it to be stuck or cancelled — Medium impact (attacker-triggered temporary locking of bridged funds).

### Likelihood Explanation

`withdraw_rbf` is callable by any NEAR account with no role restriction and no attached deposit requirement. The `original_btc_pending_verify_id` of any pending withdrawal is emitted as a public on-chain event (`GenerateBtcPendingInfo`), so it is trivially discoverable. The attacker only needs to be a normal NEAR account holder.

### Recommendation

Add an ownership assertion at the top of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();
    // Verify the pending info belongs to the caller
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(owner == account_id, "Not the owner of this pending withdrawal");
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Victim calls `ft_on_transfer` with a `Withdraw` message, creating a pending withdrawal with ID `victim_pending_id` (emitted via `GenerateBtcPendingInfo` event).
2. Attacker observes `victim_pending_id` from on-chain events.
3. Attacker calls `withdraw_rbf(victim_pending_id, [TxOut { value: X, script_pubkey: attacker_address }], None)`.
4. `require_pending_sign_capacity(&attacker_account_id)` passes (attacker has capacity).
5. `withdraw_rbf_chain_specific(attacker_account_id, victim_pending_id, attacker_outputs, None)` is invoked with no ownership check.
6. A replacement PSBT is built spending the victim's locked UTXOs with attacker-controlled outputs and submitted to MPC for signing.
7. MPC signs the RBF transaction; once confirmed on Bitcoin, the victim's BTC is delivered to the attacker's address.
