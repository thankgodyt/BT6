Audit Report

## Title
Partial `ft_on_transfer` Rejection Not Handled in `fin_transfer_send_tokens_callback`, Causing Supply Inflation for Deployed Tokens — (`near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` only triggers a refund when `ft_resolve_transfer` returns `used = 0` (full rejection). When a recipient contract partially accepts tokens (`0 < used < amount`), the bridge treats the transfer as fully successful, emitting `FinTransferEvent` for the full amount while the undelivered remainder sits permanently in the bridge's own token balance. For bridge-minted (deployed) tokens, the source chain already burned the full amount, so the stranded tokens directly inflate circulating supply on NEAR.

## Finding Description

The call chain for an inbound cross-chain transfer with a non-empty `msg` is:

`process_fin_transfer_to_near` → `send_tokens` → `mint(recipient, amount, Some(msg))`

Inside `OmniToken::mint`, when `msg` is `Some`, the full `amount` is first deposited to the bridge's own account (`env::predecessor_account_id()`), then forwarded via `ft_transfer_call`: [1](#0-0) 

`ft_transfer_call` invokes `ft_on_transfer` on the recipient, then `ft_resolve_transfer` as its callback. Per NEP-141, `ft_resolve_transfer` returns the **used** amount (`amount - unused`) and transfers `unused` tokens back to the sender (the bridge). The promise result of the entire `mint` call is therefore the `used_amount` returned by `OmniToken::ft_resolve_transfer`: [2](#0-1) 

Back in `fin_transfer_send_tokens_callback`, `is_refund_required` reads this promise result and checks: [3](#0-2) 

The check `amount.0 == 0` only catches full rejection (`used = 0`). For a partial rejection where `ft_on_transfer` returns `unused = 500` out of `amount = 1000`, `ft_resolve_transfer` returns `used = 500`. `is_refund_required` sees `500 != 0` and returns `false`. The `else` branch executes unconditionally: [4](#0-3) 

Fees are paid and `FinTransferEvent` is emitted for the full `amount`, while the 500 unused tokens returned to the bridge's balance are never burned and no recovery path exists.

## Impact Explanation

For bridge-minted (deployed) tokens: the source chain burned `amount` tokens, but only `used < amount` tokens reach the recipient. The `unused` portion remains in the bridge's balance without being burned, directly inflating the circulating supply on NEAR relative to the locked/burned supply on the source chain. This constitutes unauthorized minting and balance mis-accounting — a Critical impact matching "unauthorized minting" and "escrow mis-accounting that changes user or protocol balances."

For native (escrowed) tokens: the bridge's escrow balance drifts from its internal accounting, as the returned tokens are not credited back to `locked_tokens`, making them permanently unrecoverable.

## Likelihood Explanation

Both required conditions are fully user-controlled:
1. A non-empty `msg` field in the cross-chain transfer — standard DeFi integration path, set by the initiating user on the source chain.
2. A NEAR recipient contract whose `ft_on_transfer` returns a non-zero unused amount — the attacker deploys such a contract themselves.

No admin involvement, no privileged access, and no victim mistakes are required. The attacker initiates the transfer on the source chain naming their malicious NEAR contract as recipient; the relayer finalizes it normally. The attack is repeatable and scales linearly with transfer amount.

## Recommendation

In `fin_transfer_send_tokens_callback`, pass the expected amount into `is_refund_required` and compare `used < expected` instead of `used == 0`. For partial delivery of deployed tokens, burn only the undelivered portion (`expected - used`) and do not emit `FinTransferEvent` for the full amount (or emit a partial-failure event). Concretely:

```rust
fn is_refund_required(is_ft_transfer_call: bool, expected: u128) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(used) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    used.0 < expected  // refund/burn if ANY tokens were not delivered
                } else { false }
            }
            Err(_) => false,
        }
    } else { false }
}
```

For partial delivery, burn only `expected - used` (for deployed tokens) and emit a partial-failure event so the source chain can be informed.

## Proof of Concept

1. Attacker deploys `MaliciousReceiver` on NEAR implementing `ft_on_transfer` that always returns `amount / 2` as unused.
2. On EVM, attacker calls `initTransfer(token, 1000, 0, 0, "near:malicious.near", "trigger")` — the non-empty `message` propagates as `msg`.
3. Relayer submits proof; `fin_transfer` → `process_fin_transfer_to_near` → `send_tokens(token, malicious.near, 1000, "trigger")`.
4. `mint(malicious.near, 1000, Some("trigger"))` deposits 1000 tokens to bridge, calls `ft_transfer_call(malicious.near, 1000, ...)`.
5. `MaliciousReceiver::ft_on_transfer` returns `500` (unused). `ft_resolve_transfer` transfers 500 back to bridge, returns `U128(500)` (used).
6. `is_refund_required`: `500 != 0` → `false`. `fin_transfer_send_tokens_callback` emits `FinTransferEvent` for 1000 tokens.
7. Result: EVM burned 1000 tokens. NEAR: 500 tokens at `malicious.near`, 500 tokens stuck in bridge (not burned). Supply inflated by 500.

A local integration test can confirm this by mocking `ft_on_transfer` to return a non-zero unused amount and asserting that `FinTransferEvent` is emitted for the full amount while the bridge's token balance retains the unused portion without a corresponding burn.
