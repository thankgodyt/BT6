### Title
`safe_mint_callback` treats any non-zero used-amount as full success, silently locking user BTC while only partial nBTC is credited - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

When `safe_verify_deposit` (Omni Bridge integration path) is used, the bridge calls `nbtc::safe_mint` with a routing `msg`. `safe_mint` internally calls `ft_transfer_call`, which invokes the downstream receiver's `ft_on_transfer`. If that receiver only consumes a **partial** amount of the minted nBTC (returning a non-zero refund), the bridge's `safe_mint_callback` misclassifies this as a complete success, permanently locks the user's BTC UTXO, and leaves the unconsumed nBTC silently stranded in the bridge's own token balance — never returned to the user.

---

### Finding Description

The safe-deposit flow proceeds as follows:

1. `verify_safe_deposit_callback` calls `nbtc.safe_mint(recipient_id, mint_amount, Some(msg))`.
2. `safe_mint` mints `mint_amount` into the bridge's own balance, then calls `ft_transfer_call(recipient_id, mint_amount, None, msg)`.
3. `ft_transfer_call` transfers `mint_amount` to `recipient_id` and calls `recipient_id.ft_on_transfer(bridge, mint_amount, msg)`.
4. Per NEP-141, if `ft_on_transfer` returns `refund_amount > 0`, `ft_resolve_transfer` moves `refund_amount` back to the bridge. `ft_transfer_call` resolves to `mint_amount - refund_amount` (the "used" amount).
5. `safe_mint` propagates this resolved value back to `safe_mint_callback`.

`safe_mint_callback` then calls `is_refund_required()`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0   // ← only flags TOTAL rejection
            } else {
                false
            }
        }
        Err(_) => false,
    }
}
``` [1](#0-0) 

The check `amount.0 == 0` only catches the case where the receiver used **zero** tokens. Any non-zero used amount — including a partial amount — causes `is_refund_required()` to return `false`, so `is_success = true`.

} else {

``` [2](#0-1) 

When the receiver partially consumes the tokens:
- `refund_amount` nBTC is silently returned to the bridge's own balance by `ft_resolve_transfer`.
- The bridge records the UTXO as finalized (user's BTC is permanently locked).
- The user receives only `mint_amount - refund_amount` nBTC.
- The `refund_amount` nBTC is absorbed into the bridge's balance with no accounting or recovery path for the user.

The `safe_mint` function in the nbtc contract confirms this path:

```rust
if let Some(msg) = msg {
    self.ft_transfer_call(account_id, amount, None, msg)  // returns used amount
} else {
    self.ft_transfer(account_id, amount, None);
    PromiseOrValue::Value(amount)
}
``` [3](#0-2) 

The bridge's own documentation confirms the safe-deposit path is specifically designed for Omni Bridge integration, where the receiver's `ft_on_transfer` may impose its own caps or limits: [4](#0-3) 

---

### Impact Explanation

A user deposits real BTC on-chain. The bridge verifies the deposit and mints the correct `mint_amount` of nBTC. However, if the downstream receiver (e.g., Omni Bridge) only accepts a portion of the minted nBTC — for example because it has reached an internal cap analogous to the `reserveCap` in the external report — the following occurs:

- The user's BTC UTXO is permanently finalized in the bridge (`verified_deposit_utxo` set, UTXO added to available pool).
- The user receives fewer nBTC than their BTC deposit entitles them to.
- The unconsumed nBTC is silently absorbed into the bridge's own balance, with no mechanism to recover it for the user.
- The user cannot request a refund because the UTXO is already marked as verified.

This constitutes a **significant, permanent loss of user funds** with no recovery path.

---

### Likelihood Explanation

The `safe_verify_deposit` / `verify_deposit_v2` (with `safe_deposit: Some(..)`) path is the documented Omni Bridge integration entry point and is publicly callable by any trusted relayer. Any downstream receiver contract that enforces a deposit cap, rate limit, or partial-fill semantics in its `ft_on_transfer` will trigger this condition. The NEP-141 standard explicitly permits receivers to return a partial refund amount, so this is a well-defined, reachable code path — not a theoretical edge case.

---

### Recommendation

In `safe_mint_callback`, compare the resolved used-amount against the full `mint_amount`. Only treat the result as success if the full amount was consumed:

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(used_amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Require full consumption; partial use is also a failure
                used_amount.0 < mint_amount.0
            } else {
                false
            }
        }
        Err(_) => false,
    }
}
```

Alternatively, pass `mint_amount` into `is_refund_required` and assert `used_amount == mint_amount`. On partial use, execute the same rollback path as on total failure: unmark the UTXO from `verified_deposit_utxo` and burn the full `mint_amount` from the bridge's balance.

---

### Proof of Concept

Assume `mint_amount = 1_000_000` satoshis and the downstream receiver has an internal cap leaving only `400_000` satoshis of capacity.

1. User sends `1_000_000` sat of BTC to their bridge deposit address.
2. Relayer calls `safe_verify_deposit` (or `verify_deposit_v2` with `safe_deposit: Some(..)`).
3. Bridge verifies inclusion proof → `verify_safe_deposit_callback` fires.
4. Bridge calls `nbtc.safe_mint(recipient_id, 1_000_000, Some(msg))`.
5. `safe_mint` mints `1_000_000` into bridge balance, calls `ft_transfer_call(recipient_id, 1_000_000, None, msg)`.
6. Receiver's `ft_on_transfer` accepts only `400_000`, returns `600_000` as refund.
7. `ft_resolve_transfer` moves `600_000` back to bridge balance; `ft_transfer_call` resolves to `400_000`.
8. `safe_mint` returns `U128(400_000)` to `safe_mint_callback`.
9. `is_refund_required()` sees `400_000 != 0` → returns `false` → `is_success = true`.
10. Bridge permanently adds UTXO; user's `1_000_000` sat BTC is locked.
11. User's nBTC balance: `400_000`. Missing `600_000` sat worth of nBTC is silently in bridge balance.
12. User attempts `request_refund` → panics: `"UTXO already verified via deposit"`. Funds are unrecoverable. [5](#0-4) [6](#0-5)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }
