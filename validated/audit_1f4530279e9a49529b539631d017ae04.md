### Title
Rejected Refund Requests Can Be Immediately Re-Submitted, Bypassing DAO/Operator Rejection — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `reject_refund` function allows DAO/Operator to block a suspicious refund request, but because rejected UTXOs are not tracked anywhere, any user can immediately re-submit the identical refund request. This is a direct analog to the Arbitrum M-04 pattern: one privileged role's "remove" action can be silently undone by the original submitter, because the system has no memory of the removal.

---

### Finding Description

`internal_reject_refund` removes the entry from `refund_requests` and emits an event, but writes nothing to any persistent "blocked" or "rejected" set:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [1](#0-0) 

The only two guards that `request_refund_callback` enforces before inserting a new refund request are:

1. The UTXO must not already be in `verified_deposit_utxo` (i.e., a successful `verify_deposit` was called).
2. No existing entry in `refund_requests` for the same key.

```rust
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

After `reject_refund` removes the entry, both guards pass again. There is no third guard checking a "rejected" set, so the user can call `request_refund` again immediately with the same (or a different) `refund_address`, restarting the 14-day `unsafe_refund_timelock_sec` clock from scratch.

The `reject_refund` public entry point confirms that DAO/Operator rejection is the intended policy control:

```rust
pub fn reject_refund(&mut self, utxo_storage_key: String) {
    ...
    require!(
        is_privileged || is_already_deposited,
        "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
    );
    self.internal_reject_refund(utxo_storage_key);
}
``` [3](#0-2) 

---

### Impact Explanation

The DAO/Operator's rejection is not durable. A user whose refund request is rejected can re-submit the same proof immediately, forcing the DAO/Operator to monitor and reject continuously. If the DAO/Operator misses a single 14-day window (`unsafe_refund_timelock_sec`), `execute_refund` becomes callable by anyone and the refund executes — potentially to a refund address the DAO/Operator had already flagged as suspicious (e.g., a sanctioned address, or one associated with a known exploit). This constitutes a bypass of bridge policy controls and can result in attacker-triggered execution of a refund the protocol explicitly attempted to block.

**Allowed impact matched**: *Bypass of bridge limits or policies* (Medium).

---

### Likelihood Explanation

Likelihood is medium-high. Any user whose refund request is rejected can re-submit with zero additional on-chain cost beyond the storage deposit (which is non-refundable but small relative to a meaningful BTC deposit). The re-submission requires only a valid BTC inclusion proof, which the user already possesses from the first submission. No special knowledge or privileged access is needed.

---

### Recommendation

Introduce a persistent `rejected_refund_utxos: LookupSet<String>` in `ContractData`. In `internal_reject_refund`, insert the `utxo_storage_key` into this set. In `request_refund_callback`, add a third guard:

```rust
require!(
    !self.data().rejected_refund_utxos.contains(&utxo_storage_key),
    "Refund request was permanently rejected for this UTXO"
);
```

Optionally, allow DAO/Operator to remove entries from `rejected_refund_utxos` if a rejection needs to be reversed. This mirrors the mitigation recommended in the Arbitrum report: track removals for the lifecycle of the relevant period so the same item cannot be silently re-added.

---

### Proof of Concept

1. User sends BTC to a bridge deposit address. The deposit is not yet finalized via `verify_deposit`, so `verified_deposit_utxo` does not contain the UTXO key.
2. User calls `request_refund` with a suspicious `refund_address` (e.g., a sanctioned address). The Light Client proof is valid; `request_refund_callback` inserts the entry into `refund_requests`.
3. DAO/Operator detects the suspicious address and calls `reject_refund(utxo_storage_key)`. `internal_reject_refund` removes the entry from `refund_requests`. No other state is written.
4. User immediately calls `request_refund` again with identical parameters. `request_refund_callback` checks: `verified_deposit_utxo` — not present; `refund_requests` — not present (just removed). Both pass. The entry is re-inserted.
5. DAO/Operator must reject again. Steps 3–4 repeat indefinitely at the user's discretion.
6. If the DAO/Operator misses the 14-day `unsafe_refund_timelock_sec` window on any iteration, any caller can invoke `execute_refund`, which builds a BTC transaction paying the suspicious address and enters the MPC signing pipeline.
7. Once `finalize_refund_with_psbt` runs, the UTXO is added to `verified_deposit_utxo` and the refund is irreversible. [1](#0-0) [4](#0-3) [3](#0-2)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
