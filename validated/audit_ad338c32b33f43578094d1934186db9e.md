Audit Report

## Title
`fast_fin_transfer` Bypasses `fin_transfer` Pause via Independent `ft_on_transfer` Pause Key — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The NEAR bridge uses `near-plugins` `#[pause]` macros that create independent pause keys per decorated function. Pausing `fin_transfer` only blocks the proof-based inbound finalization path; the `fast_fin_transfer` path, dispatched through `ft_on_transfer` under a separate pause key, remains fully operational. A trusted relayer can continue minting bridged tokens to recipients on NEAR even while `fin_transfer` is paused.

## Finding Description
`fin_transfer` is decorated with `#[pause(except(roles(Role::DAO)))]` at line 672, creating a pause key scoped to `"fin_transfer"`. `ft_on_transfer` is decorated with `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]` at line 252, creating a completely independent `"ft_on_transfer"` pause key. When `ft_on_transfer` receives a `BridgeOnTransferMsg::FastFinTransfer` payload (lines 265–266), it dispatches directly to the private `fast_fin_transfer` function (line 749), which has no `#[pause]` decorator and performs no check against the `"fin_transfer"` pause bit. `fast_fin_transfer` validates the trusted-relayer role (line 756), constructs a `FastTransfer`, and calls `send_tokens` to deliver tokens to the recipient (lines 877–882). The same gap exists for `utxo_fin_transfer` (lines 268–274). Because the two pause keys are independent, an admin who calls `pause("fin_transfer")` to halt inbound minting leaves the `fast_fin_transfer` path entirely unaffected. Closing it requires pausing `ft_on_transfer`, which simultaneously blocks all outbound `init_transfer` flows — making selective inbound-only pausing structurally impossible.

## Impact Explanation
This is a concrete pause bypass enabling unauthorized minting of bridged tokens. When `fin_transfer` is paused in response to a security incident (e.g., compromised prover, suspicious minting), a trusted relayer can still invoke `ft_on_transfer` with a `FastFinTransfer` payload to mint tokens to arbitrary NEAR recipients. This directly matches the allowed critical impact: "Unauthorized transaction, authorization bypass, role bypass, pause bypass… that lets an attacker execute bridge… actions" and "unauthorized minting… of bridged funds."

## Likelihood Explanation
Exploitation requires trusted-relayer status, which is an externally reachable role granted by `RelayerManager` — not an admin-only capability. A malicious or compromised trusted relayer can exploit this at any time `fin_transfer` is paused but `ft_on_transfer` is not. The two pause states are independently managed, and an operator responding to an incident is likely to pause only `fin_transfer`. The exploit is repeatable for any unfinalized transfer ID.

## Recommendation
Add an explicit check for the `fin_transfer` pause bit inside `fast_fin_transfer` (and `utxo_fin_transfer`), mirroring the guard on `fin_transfer` itself. Alternatively, introduce a shared `PAUSED_FIN_TRANSFER` flag checked by all inbound-finalization code paths regardless of entry point. This ensures that pausing inbound finalization is atomic across all paths.

## Proof of Concept
1. Admin calls `pause("fin_transfer")` to halt proof-based inbound transfers.
2. `fin_transfer` is blocked for all non-DAO callers (line 672 guard active).
3. A trusted relayer constructs a `FastFinTransferMsg` for an unfinalized transfer ID.
4. The relayer calls `ft_transfer_call` on a NEAR token contract, sending tokens to the bridge with `msg = {"FastFinTransfer": {...}}`.
5. The token contract invokes `ft_on_transfer` on the bridge. The `"ft_on_transfer"` pause key is not set, so execution proceeds past line 252.
6. `fast_fin_transfer` (line 749) runs: trusted-relayer check passes (line 756), `send_tokens` is called (lines 877–882), tokens are minted/transferred to the recipient.
7. The `fin_transfer` pause has no effect on this path; inbound minting continues unimpeded.
