### Title
Peras Certificate Validation Unconditionally Accepts Any Inbound Certificate Without Cryptographic Proof - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The sole `BlockSupportsPeras` instance in the codebase is a degenerate stub where `validatePerasCert` unconditionally returns `Right` for every inbound certificate, and `PerasCert`/`PerasVote` carry no cryptographic signature field at all. Because the Peras object-diffusion layer (`processCerts`, `processVotes`) calls these validation functions before storing objects and using them in chain selection, any unprivileged peer can inject arbitrary Peras certificates that boost any block's chain-selection weight, potentially causing honest nodes to prefer an adversarial chain.

### Finding Description

**Root cause — stub validation that always succeeds**

The only `BlockSupportsPeras` instance is the catch-all stub:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

The `PerasCert` associated data type carries only a round number and a block point — no signature, no committee proof, no VRF output:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

`validatePerasCert` unconditionally returns `Right`, accepting every certificate regardless of content:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [3](#0-2) 

Similarly, `PerasVote` carries no signature field, and `validatePerasVote` only checks stake-distribution membership — it never verifies that the sender controls the private key for the claimed `pvVoteVoterId`:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound :: PerasRoundNo
  , pvVoteBlock :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [4](#0-3) 

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr

**Attacker-controlled entry path — `processCerts` in the object-diffusion layer**

`processCerts` is the inbound handler for Peras certificates received from remote peers. It calls `validateCert` (bound to `validatePerasCert`) and, because that always returns `Right`, adds every inbound certificate to the local database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [6](#0-5) 

The analogous path for votes is `processVotes`, which calls `validateVote` (bound to `validatePerasVote`) and adds every vote whose `pvVoteVoterId` appears in the public stake distribution: [7](#0-6) 

Both handlers are wired into the node-to-node diffusion layer (`NodeToNode.hs`), making them reachable by any unprivileged peer.

**Chain-selection impact**

Accepted `ValidatedPerasCert` objects carry a `vpcCertBoost` weight drawn from `perasWeight params`. This boost is consumed by `preferAnchoredCandidate` via `PerasWeightSnapshot` during chain selection: [8](#0-7) 

An attacker who injects a `PerasCert` pointing to an adversarial block causes that block to receive a Peras boost, making the adversarial chain appear heavier than the honest chain to the victim node's chain-selection logic.

For votes, because `votesReachQuorum` only checks accumulated stake (not signatures), an attacker who knows the public stake distribution can forge votes for enough distinct `PerasVoterId` values to exceed the quorum threshold, triggering automatic certificate forging for any target block: [9](#0-8) 

### Impact Explanation

**Severity: Critical — Bypass of Peras certificate/vote verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

An unprivileged peer can:
1. Send a crafted `PerasCert{pcCertRound=r, pcCertBoostedBlock=adversarialPoint}` to any node. Because `validatePerasCert` always returns `Right`, the certificate is stored and its boost is applied to the adversarial block.
2. Alternatively, send forged `PerasVote` messages using any public `PerasVoterId` values from the stake distribution (no signature required). Once enough stake is accumulated, `votesReachQuorum` triggers automatic certificate forging for the adversarial block.

In both cases the victim node's chain-selection logic assigns extra weight to the adversarial chain, potentially causing it to prefer that chain over the honest chain — a consensus safety failure.

### Likelihood Explanation

The Peras object-diffusion mini-protocol is wired into the production node-to-node layer. The stake distribution is public on-chain data. No privileged keys, no stake majority, and no brute force are required. Any peer that can open a node-to-node connection can exploit this immediately. The only mitigating factor is that Peras is still being integrated (the `getPerasCertInBlock _ = Nothing` stub means certificates are not yet extracted from blocks), but the inbound diffusion path is live and the boost is applied to any certificate already in the database.

### Recommendation

1. **Add a cryptographic signature field** to both `PerasCert blk` and `PerasVote blk` in the stub instance (or, preferably, replace the stub with a concrete Cardano-specific instance before enabling the diffusion layer).
2. **Implement real validation** in `validatePerasCert`: verify the committee quorum proof and all member signatures against the current epoch's committee.
3. **Implement real validation** in `validatePerasVote`: verify the VRF/KES/BLS signature proving the sender controls the private key for the claimed `pvVoteVoterId`.
4. **Gate the object-diffusion handlers** behind the same feature flag that controls Peras activation, so the inbound path is unreachable until validation is complete.

### Proof of Concept

1. Connect to a target node running the current code as an unprivileged peer via the node-to-node mini-protocol.
2. Send an `ObjectDiffusion` message containing a `PerasCert` with `pcCertBoostedBlock` set to the hash of any adversarial block already in the node's VolatileDB.
3. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB` with `vpcCertBoost = perasWeight params`.
5. On the next chain-selection run, `preferAnchoredCandidate` reads the `PerasWeightSnapshot` and applies the boost to the adversarial block, making the adversarial chain heavier than the honest chain.
6. The node selects the adversarial chain.

The same result is achievable via the vote path: send forged `PerasVote` messages for enough distinct `PerasVoterId` values (all public) to exceed `votesReachQuorum`, causing the node itself to forge and store the boosting certificate.

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
