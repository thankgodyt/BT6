### Title
Underflow Panic in `check_withdraw_psbt` Causes DoS on Small Withdrawals — (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `check_withdraw_psbt`, two sequential u128 subtractions at lines 242–243 are performed before the gas fee bounds check. When a user submits a PSBT with a gas fee large enough that `amount - withdraw_fee - gas_fee < config.min_change_amount`, the subtraction at line 243 underflows. Because the workspace `Cargo.toml` sets `overflow-checks = true` for the release profile, this causes a **panic/abort** rather than wrapping, reverting the entire `ft_on_transfer` call.

---

### Finding Description

In `contracts/satoshi-bridge/src/psbt.rs`, `check_withdraw_psbt` computes:

```rust
let max_received_amount = amount - withdraw_fee - gas_fee;   // line 242
let min_received_amount = max_received_amount - config.min_change_amount; // line 243
``` [1](#0-0) 

The gas fee bounds check that would catch an out-of-range `gas_fee` appears **after** these lines:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [2](#0-1) 

`gas_fee` is derived from the user-controlled PSBT as `total_input_amount - total_output_amount`. [3](#0-2) 

The only pre-entry guard is `amount >= min_withdraw_amount` in `ft_on_transfer`. [4](#0-3) 

`config.assert_valid()` enforces no relationship between `min_withdraw_amount`, `max_btc_gas_fee`, and `min_change_amount`, so the combination `amount - withdraw_fee - gas_fee < min_change_amount` is not structurally prevented. [5](#0-4) 

The workspace release profile has `overflow-checks = true`: [6](#0-5) 

This means the subtraction at line 243 **panics** (aborts) rather than wrapping.

---

### Impact Explanation

The panic reverts the entire `ft_on_transfer` cross-contract call. Under NEP-141 `ft_transfer_call` semantics, a failed `ft_on_transfer` causes the nBTC contract to refund the tokens to the sender — **no funds are lost**. The impact is limited to a DoS on the specific withdrawal transaction: the call fails and the user must retry with a different gas fee or a larger amount. Other users and other transactions are unaffected.

This matches: **Low — Publicly reachable panic-driven fault in a production bridge path without direct theft.**

---

### Likelihood Explanation

Triggerable by any unprivileged user via the public `ft_transfer_call` → `ft_on_transfer` path. The attacker only needs to submit a PSBT where `gas_fee` (within the valid `[min_btc_gas_fee, max_btc_gas_fee]` range) is large enough relative to a small `amount` to satisfy `amount - withdraw_fee - gas_fee < min_change_amount`. Whether this is reachable in practice depends on the deployed config values, but no code-level invariant prevents it.

---

### Recommendation

Add a guard before line 243 to ensure `max_received_amount >= config.min_change_amount` before performing the subtraction, and emit a clean `require!` error rather than panicking:

```rust
let max_received_amount = amount - withdraw_fee - gas_fee;
require!(
    max_received_amount >= config.min_change_amount,
    "Withdrawal amount too small to cover gas fee and minimum change"
);
let min_received_amount = max_received_amount - config.min_change_amount;
```

Additionally, consider adding a config-level invariant in `assert_valid` that enforces `min_withdraw_amount > max_btc_gas_fee + min_change_amount + max_withdraw_fee` to make this structurally impossible. [5](#0-4) 

---

### Proof of Concept

Given config:
- `min_withdraw_amount = 10_000` sat
- `max_btc_gas_fee = 8_000` sat
- `min_change_amount = 1_000` sat
- `withdraw_fee = 500` sat (flat)

User submits `amount = 10_000`, PSBT with `gas_fee = 8_000`:
- `max_received_amount = 10_000 - 500 - 8_000 = 1_500`
- `min_received_amount = 1_500 - 1_000 = 500` ← OK here

Now with `min_change_amount = 2_000`:
- `max_received_amount = 1_500`
- `min_received_amount = 1_500 - 2_000` → **underflow → panic**

The call aborts; nBTC is refunded. No state is written. [7](#0-6)
