Looking at the `claim_lost_found` function in `bridge.rs` and the analog vulnerability pattern (state mutated before a cross-contract call that can fail, with no rollback).

### Title
State Permanently Deleted Before Cross-Contract Transfer Completes in `claim_lost_found` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`claim_lost_found` removes the caller's entry from `lost_found` storage **before** the nBTC transfer cross-contract call (XCC) completes. In NEAR, state changes in the calling function are committed immediately and are not rolled back if a subsequent XCC fails. If `internal_transfer_nbtc` fails, the user's `lost_found` balance is permanently deleted with no recovery path.

### Finding Description
In `contracts/satoshi-bridge/src/api/bridge.rs`, the `claim_lost_found` function follows this sequence:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found                          // ← state mutated here
        .remove(&account_id)
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)  // ← XCC issued here
}
``` [1](#0-0) 

The `lost_found.remove(&account_id)` call commits the deletion to contract storage immediately. The function then returns the `Promise` from `internal_transfer_nbtc` directly — there is no `.then(callback)` chained on `claim_lost_found` itself to restore the entry if the XCC fails. If `internal_transfer_nbtc` (an XCC to the nBTC contract) fails for any reason — nBTC contract paused, insufficient storage deposit attached, nBTC contract upgraded/broken — the user's balance is gone from `lost_found` and no tokens are received.

This is the direct analog of the PoolKeeper bug: `executionPrice[_pool] = latestPrice` was committed before `pool.poolUpkeep()` could revert, losing the previous price. Here, `lost_found.remove(account_id)` is committed before the nBTC transfer XCC can fail, losing the user's funds.

### Impact Explanation
Users whose nBTC ended up in `lost_found` (e.g., after a `cancel_withdraw` where the refund transfer failed) call `claim_lost_found` to recover their funds. If the nBTC transfer XCC fails, their `lost_found` entry is permanently deleted and the funds are irrecoverable — neither in `lost_found` nor transferred to the user. This constitutes permanent destruction of user funds. [2](#0-1) 

### Likelihood Explanation
The nBTC transfer can fail if: (a) the nBTC contract is paused at the time of the callback, (b) the user's account has insufficient storage and no NEAR is attached to cover it, or (c) the nBTC contract is mid-upgrade. These are realistic operational conditions. Any unprivileged user with a `lost_found` balance can trigger this path.

### Recommendation
Move the `lost_found.remove` into a callback that only executes after confirming the XCC succeeded, mirroring the fix applied in PR 327 for PoolKeeper:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data()
        .lost_found
        .get(&account_id)
        .copied()
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)
        .then(Self::ext(env::current_account_id())
            .claim_lost_found_callback(account_id, amount))
}

#[private]
pub fn claim_lost_found_callback(&mut self, account_id: AccountId, amount: u128) {
    if is_promise_success() {
        self.data_mut().lost_found.remove(&account_id);
    }
    // else: entry remains, user can retry
}
```

### Proof of Concept
1. User's withdrawal is cancelled via `cancel_withdraw`; their remaining nBTC is stored in `lost_found[user]`.
2. User calls `claim_lost_found` with 1 yoctoNEAR attached.
3. `lost_found.remove(&account_id)` executes and commits — the entry is gone from storage.
4. `internal_transfer_nbtc` issues an XCC to the nBTC contract. The nBTC contract is paused (or the user has no storage registered), causing the XCC to fail.
5. No callback restores `lost_found[user]`.
6. User's funds are permanently lost: not in `lost_found`, not transferred. [1](#0-0)
