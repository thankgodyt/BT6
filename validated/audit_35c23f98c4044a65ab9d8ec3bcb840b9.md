Audit Report

## Title
TOCTOU in `fast_fin_transfer_to_near_callback`: Finalization Not Re-Verified After Cross-Contract Call Enables Double-Spend - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`fast_fin_transfer` checks `is_unified_transfer_finalised` before issuing a `check_or_pay_ft_storage` cross-contract call. Because NEAR cross-contract calls span multiple blocks, a concurrent `fin_transfer` can execute during this window, marking the transfer finalized in `finalised_transfers` and sending tokens to the recipient. When `fast_fin_transfer_to_near_callback` subsequently runs, it does not re-check finalization status; `add_fast_transfer` only guards against duplicate entries in the `fast_transfers` map (not `finalised_transfers`), so it succeeds and `send_tokens` fires a second time, delivering tokens to the recipient twice.

## Finding Description

**Time of Check** — `fast_fin_transfer` verifies the transfer is not yet finalized: [1](#0-0) 

**External Call Delay** — Immediately after, a cross-contract call to `check_or_pay_ft_storage` is issued, suspending execution for at least one block: [2](#0-1) 

**Race Window** — During this window, `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near` can execute. `process_fin_transfer_to_near` calls `add_fin_transfer` first (inserting into `finalised_transfers`), then calls `get_fast_transfer_status`, which returns `None` because `add_fast_transfer` has not yet been called: [3](#0-2) 

With `fast_transfer_status == None`, `process_fin_transfer_to_near` sends tokens to the original recipient: [4](#0-3) 

**Time of Use** — `fast_fin_transfer_to_near_callback` then executes. It calls `add_fast_transfer`, which only checks the `fast_transfers` map for a duplicate entry — it does **not** consult `finalised_transfers`: [5](#0-4) 

Because `fast_transfers` has no entry for this ID (it was never inserted before `fin_transfer` ran), `add_fast_transfer` succeeds. `send_tokens` then fires again: [6](#0-5) 

There is no re-check of `is_unified_transfer_finalised` anywhere in `fast_fin_transfer_to_near_callback`. [7](#0-6) 

## Impact Explanation

For **deployed (bridged) tokens**, `send_tokens` calls `mint` on the token contract. The second mint in the callback creates tokens beyond what was locked on the source chain — **unauthorized minting**. For **native (locked) tokens**, the bridge transfers from its own reserves twice — **direct loss of bridge funds**. In both cases the recipient receives `2 × (amount − fee)` tokens while only `amount` was locked on the source chain. This matches the Critical impact class: double-spending and unauthorized minting of bridged funds.

## Likelihood Explanation

`fin_transfer` is gated by `#[trusted_relayer]`, so the race requires a trusted relayer to submit the proof during the multi-block external call window. A trusted relayer who is also the NEAR recipient (or colluding with the recipient) can deliberately sequence the two calls: front `amount` tokens via `fast_fin_transfer`, then immediately submit `fin_transfer` with the valid proof. They receive `2 × (amount − fee)` tokens on NEAR while only `amount` was locked on the source chain, netting `amount − 2 × fee`. Even without malicious intent, two independent trusted relayers concurrently processing the same transfer (one via fast path, one via normal finalization) will accidentally trigger the double-spend. Relayer flows are an explicitly valid attack surface per the program rules.

## Recommendation

At the start of `fast_fin_transfer_to_near_callback`, re-check `is_unified_transfer_finalised` before calling `add_fast_transfer` or `send_tokens`. If the transfer was finalized during the external call window, abort the token send and return the relayer's fronted tokens:

```rust
pub fn fast_fin_transfer_to_near_callback(...) -> Promise {
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // Refund the relayer's fronted tokens
        return self.send_tokens(fast_transfer.token_id.clone(), storage_payer, amount, "");
    }
    // ... existing logic
}
```

## Proof of Concept

1. A transfer originates on Ethereum (origin_chain: Eth, origin_nonce: N). A valid proof exists.
2. Trusted Relayer R (who is also the NEAR recipient) calls `ft_transfer_call` on the token contract with a `FastFinTransfer` message, sending `amount` tokens to the bridge. This triggers `fast_fin_transfer`.
3. `fast_fin_transfer` passes the `is_unified_transfer_finalised` check (returns false) and issues the `check_or_pay_ft_storage` cross-contract call. Execution suspends.
4. In the next NEAR block, before `fast_fin_transfer_to_near_callback` executes, Relayer R submits `fin_transfer` with the valid proof.
5. `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near`: `add_fin_transfer` inserts into `finalised_transfers`; `get_fast_transfer_status` returns `None` (fast_transfers is empty); `send_tokens` mints/transfers `amount − fee` tokens to Relayer R as recipient.
6. `fast_fin_transfer_to_near_callback` executes: `add_fast_transfer` succeeds (only checks `fast_transfers`, which has no entry for this ID); `send_tokens` mints/transfers another `amount − fee` tokens to Relayer R.
7. Relayer R has received `2 × (amount − fee)` tokens. Only `amount` was locked on the source chain. Net gain: `amount − 2 × fee`.

A private-testnet integration test can reproduce this by: (a) calling `ft_transfer_call` with `FastFinTransfer` message, (b) intercepting execution after the `check_or_pay_ft_storage` promise is scheduled but before the callback fires, (c) calling `fin_transfer` with the valid proof in the same block, and (d) observing the recipient's token balance equals `2 × (amount − fee)`.
