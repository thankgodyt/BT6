### Title
Incorrect `utxo_num` Calculation Ignores UTXOs Locked in Other Pending Transactions, Bypassing Passive UTXO Management Policy - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary
The `utxo_num` calculation in `check_withdraw_psbt_valid` and `check_active_management_psbt_valid` does not account for UTXOs that are already locked in other in-flight pending transactions. This causes the passive (and active) UTXO management policy checks to operate on a stale, understated UTXO count, allowing any nBTC holder to bypass the bridge's UTXO management limits when concurrent pending transactions exist.

### Finding Description
When a withdrawal is initiated via `ft_on_transfer` → `create_btc_pending_info`, the flow first calls `generate_vutxos`, which calls `remove_vutxo_by_psbt`. This physically removes the selected UTXOs from `self.data().utxos` and stores them as `vutxos` inside the new `BTCPendingInfo` entry. Those UTXOs remain locked there until the pending transaction is either verified on-chain or cancelled.

Immediately after, `check_withdraw_psbt_valid` is called to enforce the passive management policy:

```rust
// psbt.rs line 24
let utxo_num = self.data().utxos.len() + vutxos_len;
```

`self.data().utxos.len()` counts only the UTXOs that are currently free (not locked in any pending transaction). `vutxos_len` adds back only the UTXOs consumed by the **current** transaction. UTXOs locked in **other** concurrent pending transactions are not counted at all.

The same pattern appears in `check_active_management_psbt_valid` at line 81:

```rust
let utxo_num = self.data().utxos.len() + vutxos_len;
```

The passive management policy then uses this understated `utxo_num`:

```rust
// psbt.rs lines 56-60
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
```

If N UTXOs are locked in other pending transactions, the effective `utxo_num` seen by the policy check is understated by N. This can push the apparent count below `passive_management_upper_limit` even when the true total (including locked UTXOs) is above it, or above `passive_management_lower_limit` when the true total is below it.

### Impact Explanation
The passive management policy is the bridge's mechanism for maintaining a healthy UTXO set. When the true UTXO count exceeds `passive_management_upper_limit`, every withdrawal must consolidate (consume more UTXOs than it creates). When the true count is below `passive_management_lower_limit`, every withdrawal must split (create more UTXOs than it consumes).

By exploiting the stale count, an attacker can:
- Submit a withdrawal that **fragments** UTXOs (input_num < change_num) when the bridge is already over the upper limit, worsening UTXO bloat.
- Submit a withdrawal that **consolidates** UTXOs (input_num > change_num) when the bridge is already below the lower limit, worsening UTXO scarcity.

Sustained UTXO scarcity can prevent the bridge from constructing valid withdrawal transactions (no available UTXOs to spend), temporarily locking bridged funds. This matches the allowed Medium impact: **Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds**.

### Likelihood Explanation
Any nBTC holder can trigger this. The attacker only needs to have one or more of their own withdrawals in the `PendingSign` or `PendingVerify` state simultaneously with a new withdrawal submission. Since pending transactions can remain open for up to `max_btc_tx_pending_sec` (configurable, default 24 hours), the window is wide. No privileged access is required.

### Recommendation
The `utxo_num` calculation should include UTXOs locked in all currently active pending transactions. One approach is to maintain a running counter of locked UTXOs in `ContractData`, incremented when UTXOs are moved into a `BTCPendingInfo` and decremented when they are returned (on verification or cancellation). The corrected calculation would be:

```rust
let utxo_num = self.data().utxos.len() + self.data().locked_utxo_count + vutxos_len;
```

Alternatively, iterate over `btc_pending_infos` to sum `vutxos.len()` across all active entries, though this is more expensive.

### Proof of Concept
1. Bridge has 13 UTXOs available; `passive_management_upper_limit = 12`.
2. Relayer submits an active UTXO management transaction consuming 3 UTXOs → those 3 are removed from `self.data().utxos` and stored in a `BTCPendingInfo`. Now `self.data().utxos.len() = 10`.
3. Alice calls `ft_transfer_call` to withdraw, specifying 1 input UTXO and 2 change outputs (input_num=1, change_num=2, i.e. splitting).
4. In `check_withdraw_psbt_valid`: `utxo_num = 10 (available) + 1 (this tx's vutxos) = 11`. Since `11 < 12 = passive_management_upper_limit`, the consolidation requirement (`input_num > change_num`) is **not** enforced.
5. True UTXO count = 10 (available) + 3 (locked in step 2) + 1 (this tx) = 14 > 12, so consolidation **should** have been required.
6. Alice's splitting withdrawal is accepted, worsening UTXO fragmentation beyond the configured limit. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```rust
    pub fn remove_vutxo_by_psbt(&mut self, psbt: &PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let mut utxo_storage_keys = vec![];
        let vutxos = psbt
            .get_utxo_storage_keys()
            .into_iter()
            .map(|utxo_storage_key| {
                utxo_storage_keys.push(utxo_storage_key.clone());
                self.data_mut()
                    .utxos
                    .remove(&utxo_storage_key)
                    .unwrap_or_else(|| {
                        env::panic_str(&format!("UTXO {} not exist", utxo_storage_key))
                    })
            })
            .collect::<Vec<_>>();
        (utxo_storage_keys, vutxos)
    }
```
