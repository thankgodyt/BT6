Audit Report

## Title
`HyperliquedBridgeToken.mint(address,uint256,bytes)` Unconditionally Redirects All Minted Tokens to `_systemAddress`, Causing Permanent Loss of Bridged Funds — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

The 3-arg `mint` override in `HyperliquedBridgeToken` is designed for HyperCore spot-balance parking: it mints tokens to `account` and immediately transfers the full amount to `_systemAddress`. However, `OmniBridge.finTransfer` invokes this same 3-arg path for **any** inbound bridge transfer where `payload.message.length > 0`, regardless of whether the destination is HyperCore or HyperEVM. The `bytes memory` message parameter is silently ignored. Any recipient of a `HyperliquedBridgeToken` transfer that includes a non-empty message field receives zero tokens; the full bridged amount is permanently parked at the Hyperliquid system precompile address.

## Finding Description

`OmniBridge.finTransfer` dispatches to the 3-arg `IBridgeToken.mint` whenever `isBridgeToken[payload.tokenAddress]` is true **and** `payload.message.length > 0`: [1](#0-0) 

The `HyperliquedBridgeToken` implementation of that 3-arg signature is: [2](#0-1) 

`_mint(account, value)` (OZ ERC-20 internals) calls `_update(address(0), account, value)`, crediting `account` with `value`. The immediately following `_update(account, _systemAddress, value)` transfers that same `value` out of `account` to `_systemAddress`. Net effect on `account`: **+value − value = 0**. The `bytes memory` parameter carrying `payload.message` is unnamed and never read; the redirect to `_systemAddress` is unconditional regardless of message content.

The contract's own NatSpec documents the two-path design: [3](#0-2) 

The 3-arg path was designed exclusively for HyperCore spot-balance parking (tokens parked at `_systemAddress` are later released via `coreReceiveWithData`). `OmniBridge.finTransfer` uses `message.length > 0` as its sole routing criterion, which is a completely different semantic — it covers any cross-chain DeFi callback, memo, or bridge-level metadata, not just HyperCore-bound transfers.

The `onlyOwner` guard on `mint` is satisfied because `OmniBridge` is set as the token owner during `initialize` via `__Ownable_init(_msgSender())`: [4](#0-3) 

## Impact Explanation

Any inbound cross-chain transfer to a `HyperliquedBridgeToken` that includes a non-empty `message` field will:
1. Mint `payload.amount` tokens — increasing `totalSupply` correctly.
2. Immediately move all of those tokens to `_systemAddress`.
3. Leave `payload.recipient` with **zero tokens**.

`_systemAddress` is the Hyperliquid system precompile, not a user-controlled account. Tokens parked there can only be released via `coreReceiveWithData`, which requires the system address itself to call the contract — a path that is not triggered by the normal bridge finalization flow. This constitutes **permanent, irreversible loss of bridged funds** for every affected recipient, matching the Critical impact class: *loss or permanent freezing of bridged funds*.

## Likelihood Explanation

The trigger condition — `payload.message.length > 0` — is a standard, user-initiated feature of the bridge (cross-chain DeFi callbacks, memos, bridge-level metadata). Any user on NEAR who initiates a transfer to a `HyperliquedBridgeToken` address with a non-empty message will have their funds lost upon finalization. No special attacker capability is required; a legitimate relayer submitting a legitimately signed payload is sufficient. The NEAR bridge MPC key signs the full payload including the `message` field, so a valid signature over a payload with `message.length > 0` is obtainable through the normal bridge flow. [5](#0-4) 

## Recommendation

The 3-arg `mint` in `HyperliquedBridgeToken` must not unconditionally redirect tokens to `_systemAddress`. Two options:

1. **Revert on direct bridge calls**: Override the 3-arg `mint` to revert, forcing all `finTransfer` paths through the 2-arg mint (tokens always delivered directly to the recipient on HyperEVM), and handle HyperCore parking exclusively through `coreReceiveWithData`.

2. **Decode the message to determine routing**: If `bytes memory message` encodes a HyperCore-specific instruction, apply the `_systemAddress` redirect only when that instruction is present; otherwise fall through to a plain `_mint(account, value)`.

Additionally, `OmniBridge.finTransfer` should not use `message.length > 0` as a proxy for "HyperCore-bound transfer." The routing criterion should be explicit (e.g., a dedicated flag or a separate function entry point for HyperCore transfers).

## Proof of Concept

```solidity
// 1. Deploy HyperliquedBridgeToken with a non-zero _systemAddress (e.g. address(0xSYS))
// 2. Register it in OmniBridge: isBridgeToken[token] = true, OmniBridge is token owner
// 3. Obtain a valid nearBridgeDerivedAddress signature over a TransferMessagePayload
//    where payload.message = bytes("\x00")  (length == 1 > 0)
// 4. Call OmniBridge.finTransfer(sig, payload)
//    → isBridgeToken branch, message.length > 0
//    → IBridgeToken(token).mint(recipient, amount, "\x00")
//    → _mint(recipient, amount)                        // recipient balance = amount
//    → _update(recipient, _systemAddress, amount)      // recipient balance = 0
// 5. Assert:
assert(token.balanceOf(recipient)      == 0);
assert(token.balanceOf(_systemAddress) == amount);
```

The exploit requires only a standard bridge transfer with a one-byte non-empty message. No privileged access, no key compromise, and no victim mistake is needed beyond initiating a normal cross-chain transfer with any message field set.
