Audit Report

## Title
Fire-and-Forget Relayer Reimbursement With Unconditional State Finalisation Causes Permanent Fund Freezing — (`near/omni-bridge/src/lib.rs`)

## Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge permanently marks a fast transfer as finalised (or removes it) before confirming that the reimbursement token transfer to the relayer succeeded. Because `send_tokens` is called with `.detach()`, any failure is silently discarded. Once the state is written, no code path allows re-sending the reimbursement, permanently freezing the relayer's bridged funds inside the contract.

## Finding Description

**`process_fin_transfer_to_other_chain` (L2027–2041):**

```rust
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, U128(...), "")
        .detach();                                        // ← failure invisible
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // ← permanent
}
```

`send_tokens` dispatches either `ft_transfer` (non-deployed token, requires NEP-141 storage registration on the token contract) or `mint` (deployed token). With `.detach()` the returned `Promise` is abandoned; NEAR will execute the receipt but the bridge contract never inspects the outcome. `mark_fast_transfer_as_finalised` then sets `status.finalised = true` and writes it back to storage unconditionally.

**`utxo_fin_transfer_fast` (L2529–2548):**

```rust
let amount = if ... == ChainKind::Near {
    self.remove_fast_transfer(&fast_transfer.id());   // ← state cleared
    ...
} else {
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // ← state cleared
    ...
};
self.send_tokens(..., fast_transfer_status.relayer, amount, "").detach(); // ← fire-and-forget
```

Here the state mutation precedes even the dispatch of the promise.

**Why existing checks are insufficient:** The guard `require!(!fast_transfer_status.finalised, ...)` at L2524–2527 prevents re-entry, but it also prevents any retry after a failed reimbursement. `mark_fast_transfer_as_finalised` (L2270–2277) writes `finalised = true` with no rollback hook. There is no admin function, no callback, and no alternative code path that re-sends the reimbursement once the record is finalised.

**Contrast with the correct pattern:** `process_fin_transfer_to_near` (L1967–1977) chains `send_tokens` with `.then(fin_transfer_send_tokens_callback(...))`, which inspects the result and can revert state. The relayer reimbursement paths do not use this pattern.

## Impact Explanation

The relayer pre-paid tokens from their own account to the transfer recipient. The bridge contract holds the equivalent amount (locked or minted) that must be returned to the relayer as reimbursement. If `send_tokens` fails silently, those tokens remain inside the bridge contract with no mechanism to recover them. This is **permanent freezing of bridged funds** belonging to the relayer, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR … flows."*

## Likelihood Explanation

For non-deployed tokens, `send_tokens` calls `ft_transfer`, which panics if the recipient (relayer) has no storage deposit registered on the token contract. A relayer who has never registered storage for a particular token, or whose registration has been unregistered, will silently lose their reimbursement. This requires no privileged access and no attacker: it is triggered by the normal canonical `fin_transfer` call made by any party holding a valid proof. For deployed tokens, any panic in the token contract's `mint` function has the same effect. The scenario is reachable through ordinary bridge operation.

## Recommendation

Replace `.detach()` with a `.then(callback)` pattern mirroring `fin_transfer_send_tokens_callback`. The callback should:
1. Inspect the promise result.
2. If the token transfer succeeded, call `mark_fast_transfer_as_finalised` / `remove_fast_transfer`.
3. If it failed, leave the fast-transfer record untouched so the reimbursement can be retried.

This is the pattern already used in `process_fin_transfer_to_near` and should be applied consistently to both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`.

## Proof of Concept

1. Relayer R performs a fast transfer for transfer ID `T`, pre-paying tokens to the NEAR recipient. R has never registered storage for token `X` on its token contract.
2. Any party calls `fin_transfer` with a valid proof for `T` targeting a non-NEAR destination, routing into `process_fin_transfer_to_other_chain`.
3. The bridge finds the fast-transfer record for `T`, calls `send_tokens(X, R, amount, "").detach()`, then immediately calls `mark_fast_transfer_as_finalised(&T)`.
4. The `ft_transfer` receipt to R fails (storage not registered); the failure is invisible to the bridge.
5. `fast_transfers[T].finalised == true` is now permanently stored. The `require!(!status.finalised)` guard blocks any future attempt to re-send.
6. R has lost `amount` tokens. The tokens remain in the bridge contract. No recovery path exists.

To reproduce locally: write a sandbox integration test that (a) deploys a NEP-141 token without registering storage for the relayer account, (b) executes the fast-transfer + fin-transfer sequence, and (c) asserts that the relayer's balance is unchanged while the fast-transfer record shows `finalised = true`.
