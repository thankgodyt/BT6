Audit Report

## Title
Floor Division in `normalize_amount` Permanently Locks/Burns User Tokens When Transfer Amount Rounds to Zero - (File: near/omni-bridge/src/lib.rs)

## Summary

The `normalize_amount` function uses integer floor division to scale token amounts across decimal boundaries. When a user initiates a transfer whose `amount_without_fee` is smaller than `10^diff_decimals`, the normalized result is zero. The `sign_transfer` function then panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, but the user's tokens were already locked or burned in the prior `init_transfer_internal` transaction. No cancel or refund path exists, leaving the tokens permanently frozen.

## Finding Description

`normalize_amount` at L2784–2787 performs plain integer division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

The transfer lifecycle spans two separate NEAR transactions:

**Transaction 1 — `init_transfer_internal` locks or burns tokens:**

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [2](#0-1) 

The only pre-flight validation at this stage is `fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

There is no check that `normalize_amount(amount - fee) > 0` before committing tokens.

**Transaction 2 — `sign_transfer` computes the normalized amount and panics if zero:**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [4](#0-3) 

When `sign_transfer` panics, the NEAR runtime reverts only that transaction. The transfer message remains in `pending_transfers` and the tokens remain locked or burned from Transaction 1. The `sign_transfer_callback` is never reached, so no cleanup occurs. [5](#0-4) 

A search of the contract confirms there is no `cancel_transfer` or equivalent public function that would unlock tokens or restore burned supply for a stuck pending transfer. The `remove_transfer_message_without_refund` helper is only invoked in storage-payment error paths inside `init_transfer_internal` itself, before tokens are locked. [6](#0-5) 

## Impact Explanation

For native (non-deployed) tokens: the locked balance counter is incremented and never decremented, permanently freezing the escrowed funds. For deployed bridge tokens: `burn_tokens_if_needed` issues a detached burn call, permanently destroying the tokens with no mint-back path. Both outcomes constitute permanent freezing/loss of bridged funds, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR."*

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a sufficiently small amount. The threshold depends on the decimal difference: for `origin_decimals = 24`, `decimals = 8` (diff = 16), any amount below `10^16` base units triggers the zero-normalization path. For the common NEAR→EVM case (`origin_decimals = 24`, `decimals = 18`, diff = 6), any amount below `10^6` base units is affected. These are realistic amounts reachable through UI rounding errors or deliberate dust transfers. The condition is repeatable and requires no special privileges.

## Recommendation

Add a pre-flight normalization check inside `init_transfer` (or at the start of `init_transfer_internal`) before tokens are locked or burned:

```rust
let normalized = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0)
        .ok_or(BridgeError::InvalidFee)?,
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This ensures the invariant `normalize_amount(amount - fee) > 0` is enforced at the point of commitment, not after funds are already escrowed.

## Proof of Concept

1. Deploy a NEAR token with `origin_decimals = 24`; register it on the bridge with EVM `decimals = 8` (diff = 16).
2. Call `ft_transfer_call` with `amount = 5 * 10^15`, `fee = 0`, and a valid EVM recipient.
3. `init_transfer_internal` burns or locks `5 * 10^15` tokens; transfer message is stored in `pending_transfers`.
4. Relayer calls `sign_transfer` for the resulting transfer ID.
5. `normalize_amount(5 * 10^15, diff=16) = 0` → `require!` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Transaction 2 is fully reverted; transfer message remains in storage; tokens remain locked/burned. No refund is issued. Tokens are permanently frozen.
