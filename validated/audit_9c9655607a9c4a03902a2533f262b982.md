### Title
Peras Vote and Certificate Validation Bypass via Missing Cryptographic Voter-Identity Binding — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all Peras vote and certificate processing omits any cryptographic signature from the `PerasVote` wire type and performs no signature verification in `validatePerasVote`. The `pvVoteVoterId` field is a self-reported `KeyHash StakePool` with no cryptographic binding to the vote content. An unprivileged peer can craft a `PerasVote` claiming to be any high-stake pool and submit it via the ObjectDiffusion mini-protocol; the node will accept it as valid, potentially driving a fake quorum and an unauthorized `PerasCert` that boosts the wrong chain.

---

### Finding Description

The degenerate `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` defines the `PerasVote` wire type as:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- self-reported KeyHash, no signature
  }
```

There is no signature field. The `pvVoteVoterId` is a plain `KeyHash StakePool` that any sender can set to any value. [1](#0-0) 

The `validatePerasVote` implementation for this instance only checks that the claimed voter ID exists in the stake distribution; it performs no cryptographic verification:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` simply does a `Map.lookup` on the self-reported `pvVoteVoterId`: [3](#0-2) 

`validatePerasCert` is even weaker — it unconditionally returns `Right` for every certificate received:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

Both functions are wired directly into the production network-facing `processVotes` and `processCerts` handlers, which are called from the ObjectDiffusion mini-protocol inbound path: [5](#0-4) [6](#0-5) 

The TODO comments in the code acknowledge this is incomplete but the stub is the only active instance: [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can:

1. Observe the `PerasVoteStakeDistr` (public, derived from the ledger) to identify high-stake pool IDs.
2. Craft a `PerasVote` with `pvVoteVoterId` set to a high-stake pool's `KeyHash` and `pvVoteBlock` pointing to any block of the attacker's choice.
3. Submit the crafted vote via the ObjectDiffusion mini-protocol.
4. `validatePerasVote` accepts it because the voter ID is in the stake distribution.
5. The vote is stored in `PerasVoteDB` and contributes to quorum accounting.
6. If enough such fake votes are submitted (impersonating multiple high-stake pools), `votesReachQuorum` returns `Just`, a `PerasCert` is forged for the attacker's chosen block, and `validatePerasCert` accepts it unconditionally.
7. The forged certificate boosts the chain weight of the attacker's chosen block via `vpcCertBoost`, causing the node's chain selection to prefer a non-canonical chain.

This is a bypass of Peras voting and certificate checks enabling unauthorized vote and certificate acceptance, directly affecting chain selection.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol is a standard node-to-node protocol reachable by any unprivileged peer. The attack requires only knowledge of the public stake distribution (available from the ledger state) and the ability to send crafted `PerasVote` messages. No key material, admin access, or stake is required. The degenerate `BlockSupportsPeras` instance is the only one wired into the production diffusion path; the cryptographically sound `WFALS` and `EveryoneVotes` committee implementations are not yet connected to it. [8](#0-7) 

---

### Recommendation

1. Add a `pvSignature` field to the `PerasVote` wire type (as already done in `Ouroboros.Consensus.Peras.Vote.V1`) and include the voter's pool ID in the signed message so the signature cryptographically binds the voter identity to the vote content. [9](#0-8) 

2. Implement `validatePerasVote` to verify the BLS signature against the voter's public key (looked up from the stake distribution), as already specified in `CryptoSupportsVoteSigning.verifyVoteSignature`. [10](#0-9) 

3. Implement `validatePerasCert` to perform actual aggregate signature verification rather than unconditionally returning `Right`, following the pattern already implemented in `implVerifyCert` for `WFALS` and `EveryoneVotes`. [11](#0-10) 

4. Resolve issue `cardano-peras#120` before enabling the Peras ObjectDiffusion protocol on any network where the degenerate instance is active.

---

### Proof of Concept

```
1. Attacker queries the ledger state to obtain PerasVoteStakeDistr, identifying
   pool P with high stake (e.g., 30% of total).

2. Attacker constructs a crafted PerasVote:
     PerasVote
       { pvVoteRound   = currentRound
       , pvVoteBlock   = attackerChosenBlock  -- any block point
       , pvVoteVoterId = PerasVoterId (keyHashOf P)  -- self-reported, no sig
       }

3. Attacker sends this vote to a target node via the ObjectDiffusion
   mini-protocol (standard NtN connection, no authentication required).

4. processVotes calls:
     validatePerasVote mkPerasParams stakeDistr craftedVote
   which calls:
     lookupPerasVoteStake craftedVote stakeDistr
   => Map.lookup (keyHashOf P) stakeDistr => Just (30% stake)
   => Right (ValidatedPerasVote { vpvVoteStake = 30% })

5. Attacker repeats for pools Q (25%) and R (20%), totalling 75% stake.

6. votesReachQuorum returns Just, forgePerasCert is called, producing a
   ValidatedPerasCert for attackerChosenBlock.

7. validatePerasCert unconditionally returns Right for this certificate.

8. The certificate is stored and applied to chain selection, boosting
   attackerChosenBlock's chain weight by perasWeight, causing the node
   to prefer the attacker's chosen chain over the canonical one.
```
