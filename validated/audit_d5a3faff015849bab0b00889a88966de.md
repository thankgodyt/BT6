### Title
nBTC Tokens Sent to Bridge via Plain `ft_transfer` Are Permanently Stuck — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

### Summary
The `satoshi-bridge` contract has no mechanism to recover nBTC tokens sent to it via the standard NEP-141 `ft_transfer` function instead of the required `ft_transfer_call`. Such tokens accumulate in the bridge's nBTC balance permanently, with no user-facing or admin recovery path.

### Finding Description
The intended withdrawal flow requires users to call `nbtc.ft_transfer_call(bridge_id, amount, msg)`, which triggers `bridge.ft_on_transfer(sender, amount, msg)` and creates a tracked `BTCPendingInfo` entry. [1](#0-0) 

However, if a user calls `nbtc.ft_transfer(bridge_id, amount, None)` instead — a valid NEP-141 call — the nBTC contract transfers the tokens directly into the bridge's registered balance without invoking any callback on the bridge. No `BTCPendingInfo` is created, no withdrawal state is initialized, and the tokens are not recorded in the `lost_found` map. [2](#0-1) 

The bridge's only token-recovery mechanisms are:

- `claim_lost_found` — only covers entries explicitly inserted into the `lost_found` map by `transfer_nbtc_callback` after a failed cancel-withdraw transfer. [3](#0-2) 

- `withdraw_protocol_fee` — only covers the `cur_available_protocol_fee` accounting field.
- `cancel_withdraw` — only operates on existing `BTCPendingInfo` entries. [4](#0-3) 

None of these paths can recover nBTC that arrived via a plain `ft_transfer` with no associated pending state. The `burn` function in the nBTC contract burns exactly `burn_amount` from the bridge's balance for each legitimate withdrawal, leaving any surplus tokens permanently stranded. [5](#0-4) 

### Impact Explanation
Any nBTC sent to the bridge via `ft_transfer` is permanently lost to the sender. The tokens sit in the bridge's nBTC balance indefinitely, unrecoverable by the user or any admin function. This constitutes a permanent, irreversible loss of user funds with no operator intervention path. Matches: **Low — publicly reachable stuck-state in production bridge/token paths without direct theft.**

### Likelihood Explanation
Any NEAR account holding nBTC can trigger this by calling `nbtc.ft_transfer(bridge_id, amount, None)`. This is a realistic user mistake: both `ft_transfer` and `ft_transfer_call` are standard NEP-141 functions on the same contract, and a user or integrating dApp could easily use the wrong one. No privileged access is required.

### Recommendation
Add an admin-gated function (e.g., restricted to `Role::DAO`) that computes the bridge's unaccounted nBTC balance (total bridge nBTC balance minus the sum of all pending `transfer_amount` values and `cur_available_protocol_fee`) and transfers or burns the surplus. Alternatively, document clearly that `ft_transfer` to the bridge is irreversible and add an on-chain guard that panics or returns the amount if the bridge receives nBTC without a valid withdrawal message.

### Proof of Concept
1. Alice holds 100,000 nBTC and intends to withdraw to Bitcoin.
2. Alice mistakenly calls `nbtc.ft_transfer(bridge_id, 100_000, None)` with 1 yoctoNEAR attached (valid NEP-141 call).
3. The nBTC contract executes `internal_transfer`, moving 100,000 nBTC into the bridge's registered balance. No callback is fired on the bridge.
4. No `BTCPendingInfo` is created; no `lost_found` entry is written.
5. Alice calls `bridge.claim_lost_found()` — panics: "The account does not have lostfound".
6. No other public function on the bridge can return Alice's tokens.
7. Alice's 100,000 nBTC remain permanently locked in the bridge's nBTC balance, indistinguishable from legitimate withdrawal collateral, with no recovery path. [6](#0-5) [7](#0-6)

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }
    }

            owner_id: &burn_account_id,
            amount: burn_amount,
            memo: None,

    }

    #[private]
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
