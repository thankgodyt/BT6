### Title
Hardcoded Mainnet-Specific `HistoricityCutoff` in `mkGenesisConfig` Bypasses Genesis Historicity Check on Non-Mainnet Networks - (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes the Genesis `HistoricityCutoff` to `3 * 2160 * 20 + 3600` seconds — a value derived from Cardano mainnet's security parameter `k = 2160` and active-slot coefficient `f = 0.05` (`1/f = 20`). This constant is not exposed in `GenesisConfigFlags` and is therefore not configurable. On any network whose `k` or `f` differs from mainnet values, the cutoff is wrong. When it is too large, an unprivileged adversarial peer can send `MsgRollBackward` messages rolling back to headers far older than the network's actual stability window without triggering a disconnect, bypassing the Genesis historicity defense and enabling chain-selection manipulation during syncing.

---

### Finding Description

In `mkGenesisConfig (Just cfg)`, the `gcHistoricityCutoff` field is unconditionally set to a literal:

```haskell
-- ouroboros-consensus-diffusion/.../Node/Genesis.hs, line 151
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
```

The inline comment reads: *"Duration in seconds of one Cardano mainnet Shelley stability window (3k/f slots times one second per slot) plus one extra hour as a safety margin."* The magic numbers `2160` (mainnet `k`) and `20` (mainnet `1/f`) are not derived from any runtime configuration; they are compile-time literals. [1](#0-0) 

The `GenesisConfigFlags` record — the only user-facing knob for Genesis tuning — has no field for the historicity cutoff:

```haskell
data GenesisConfigFlags = GenesisConfigFlags
  { gcfEnableCSJ            :: Bool
  , gcfEnableLoEAndGDD      :: Bool
  , gcfEnableLoP            :: Bool
  , gcfBlockFetchGracePeriod :: Maybe DiffTime
  , gcfBucketCapacity       :: Maybe Integer
  , gcfBucketRate           :: Maybe Integer
  , gcfCSJJumpSize          :: Maybe SlotNo
  , gcfGDDRateLimit         :: Maybe DiffTime
  }
``` [2](#0-1) 

Every other Genesis tunable (`gcfCSJJumpSize`, `gcfBucketCapacity`, etc.) has a `Maybe`-override path; `gcHistoricityCutoff` has none.

The cutoff is wired into the live ChainSync client in `Node.hs`:

```haskell
historicityCheck getGsmState =
  case gcHistoricityCutoff llrnGenesisConfig of
    Nothing           -> HistoricityCheck.noCheck
    Just historicityCutoff ->
      HistoricityCheck.mkCheck systemTime getGsmState historicityCutoff
``` [3](#0-2) 

`mkCheck` disconnects a peer only when `historicityCutoff < actualRollbackAge`:

```haskell
when (historicityCutoff < actualRollbackAge) $
  throwError HistoricityException{...}
``` [4](#0-3) 

The specification for `HistoricityCutoff` states it *"should be set to at least the maximum duration (across all eras) of a stability window"* and is network-parameter-dependent: [5](#0-4) 

On a network with, say, `k = 100` and `f = 0.5`, the correct stability window is `3 × 100 × 2 × 1 = 600 s`. The hardcoded cutoff of `133,200 s` is **222× too large**, meaning an adversarial peer can roll back to headers up to 133,200 s old without being disconnected, when the correct threshold is 600 s.

---

### Impact Explanation

The `HistoricityCutoff` is the primary defense against historical `MsgRollBackward` and `MsgAwaitReply` messages when ChainSync Jumping (CSJ) is enabled. The `noCheck` documentation explicitly states that without CSJ the Limit on Patience (LoP) provides equivalent protection, but *with* CSJ the historicity check is the designated guard: [6](#0-5) 

When the cutoff is too large, an adversarial peer can:
1. Send `MsgRollBackward` to a point far older than the network's actual stability window without being disconnected.
2. Follow with `MsgRollForward` presenting a dense adversarial chain rooted at that old point.
3. Remain connected and influence the Limit on Eagerness (LoE) fragment and Genesis Density Disconnector (GDD) decisions.
4. Cause the syncing node to prefer a non-canonical, adversarially-constructed chain over the honest chain.

**Impact class: High** — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended Genesis security assumptions.

---

### Likelihood Explanation

This affects any deployment where Genesis is enabled (`mkGenesisConfig (Just ...)`) and the network's `k` or `f` differs from Cardano mainnet values (`k = 2160`, `f = 0.05`). Cardano mainnet, preview, and preprod all share these parameters, so they are unaffected. Private testnets and custom Cardano deployments with different consensus parameters are directly affected. The attack requires only an unprivileged peer connection — no key material, no stake, no admin access. **Likelihood: Low** for production mainnet; **Medium** for private-testnet or custom-network deployments running Genesis with non-mainnet parameters.

---

### Recommendation

1. Add `gcfHistoricityCutoff :: Maybe NominalDiffTime` to `GenesisConfigFlags`, mirroring the pattern used for every other Genesis tunable.
2. In `mkGenesisConfig`, replace the literal with `fromMaybe defaultHistoricityCutoff gcfHistoricityCutoff`, where `defaultHistoricityCutoff` retains the current mainnet value as a safe default for mainnet operators.
3. Document that operators on non-mainnet networks **must** override this value to `3 * k * (1/f) * slotLengthSeconds + safetyMarginSeconds` for their specific network parameters.
4. Ideally, derive the cutoff automatically from the `ProtocolInfo` / genesis configuration rather than requiring manual operator input, eliminating the class of misconfiguration entirely.

---

### Proof of Concept

**Setup**: Private testnet with `k = 100`, `f = 0.5` (slot length 1 s). Genesis enabled with CSJ enabled. Correct stability window = `3 × 100 × 2 = 600 s`.

**Attack sequence**:
1. Adversarial peer connects to a syncing honest node.
2. Adversarial peer sends `MsgRollBackward` to a header whose slot time is 700 s before the current wall-clock time (older than the correct 600 s cutoff, but younger than the hardcoded 133,200 s cutoff).
3. `mkCheck` evaluates `133200 < 700` → `False` → no disconnect. The peer remains connected.
4. Adversarial peer sends `MsgRollForward` with a chain of blocks denser than the honest chain in the relevant window.
5. The LoE fragment is influenced by the adversarial peer's candidate; GDD does not disconnect because the adversarial chain appears dense.
6. The honest node's chain selection is steered toward the adversarial chain, violating the Genesis security guarantee.

**Root cause line**: `gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600` [7](#0-6)

-- syncing node should not be connected to that peer.
