### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value directly against `PerasQuorumStakeThreshold` without enforcing that both quantities are expressed in the same units. The code itself acknowledges this in a `TODO` comment: the quorum threshold is a relative (normalized) `Rational`, but `PerasVoteStake` values stored in `PerasVoteStakeDistr` are looked up directly from the ledger stake distribution and may be absolute lovelace-denominated values. No normalization step exists anywhere in the vote-validation pipeline before the comparison is made. This is a direct analog to the M-4 bug: the wrong quantity (absolute vs. relative) is used in a security-critical threshold check.

---

### Finding Description

The `stakeAboveThreshold` function performs the Peras quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake    = unPerasVoteStake voteStake          -- Rational
  quorumThreshold = unPerasQuorumStakeThreshold  -- Rational (relative, e.g. 0.75)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin
```

The function's own `TODO` comment (lines 153–161) explicitly states:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

The `PerasVoteStake` values that reach this function originate from `PerasVoteStakeDistr`, which is populated from the ledger stake distribution. The note at lines 136–143 confirms:

> "At the moment there is no consensus from researchers/engineers on how we go from the **absolute** stake of a voter in the ledger to the **relative** stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)."

The vote-validation pipeline is:

1. A peer sends a `PerasVote` message, received by `makePerasVotePoolWriterFromChainDB` / `makePerasVotePoolWriterFromVoteDB`.
2. `processVotes` calls `validatePerasVote mkPerasParams sd vote`, which calls `lookupPerasVoteStake vote stakeDistr` and stores the raw value directly into `ValidatedPerasVote { vpvVoteStake = stake }` — **no normalization**.
3. `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` sums `vpvVoteStake` values and calls `stakeAboveThreshold cfg totalVoteStake`.
4. If the unit mismatch is present, the comparison is meaningless. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

### Impact Explanation

**Scenario A — Absolute stake >> relative threshold (quorum trivially bypassed):**
If `PerasVoteStakeDistr` is populated with absolute lovelace values (e.g., a voter with 1,000,000 lovelace), and `perasQuorumStakeThreshold` is a relative value such as `0.75`, then `stake (1000000) >= quorumThreshold (0.75)` is always `True`. A single vote from any voter with more than `0.75` lovelace of absolute stake causes `votesReachQuorum` to return `Just`, forging a Peras certificate for a block that has no genuine quorum. The certificate is then accepted by `implAddVote` and propagated, causing all honest nodes to boost that block's chain weight via `vpcCertBoost`.

**Scenario B — Normalized stake << absolute threshold (quorum permanently blocked):**
If the threshold is expressed as an absolute value but votes carry normalized stakes in `[0,1]`, quorum can never be reached, permanently disabling the Peras boosting mechanism and degrading chain security to base Praos.

In Scenario A, an unprivileged peer sending a single crafted `PerasVote` can cause an honest node to forge and accept a certificate for an adversarially chosen block, directly influencing chain selection. [6](#0-5) 

---

### Likelihood Explanation

The entry point is the Peras vote mini-protocol, reachable by any unprivileged peer. The `processVotes` function is called for every batch of inbound votes. The unit mismatch is not a hypothetical: the code explicitly documents that no decision has been made on how to convert absolute ledger stake to relative vote stake, and no normalization is performed anywhere in the pipeline. Any deployment that populates `PerasVoteStakeDistr` with raw ledger lovelace values (the natural choice) will exhibit Scenario A. [7](#0-6) 

---

### Recommendation

1. **Enforce unit consistency at the boundary.** `validatePerasVote` must normalize the absolute ledger stake to a relative value before storing it in `ValidatedPerasVote.vpvVoteStake`. The normalization requires the total stake of the voting committee, which should be passed into `validatePerasVote` alongside `stakeDistr`.

2. **Alternatively**, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, as the `TODO` comment suggests.

3. **Remove the degenerate `BlockSupportsPeras` instance** (lines 318–389) that skips all validation with `TODO` comments, or gate it behind a compile-time flag so it cannot be used in production. [8](#0-7) 

---

### Proof of Concept

**Setup:** Populate `PerasVoteStakeDistr` with a single voter `V` having absolute stake `1_000_000` (lovelace). Set `perasQuorumStakeThreshold = 0.75` (relative). Set `perasQuorumStakeThresholdSafetyMargin = 0.0`.

**Step 1:** Peer sends one `PerasVote` from voter `V` targeting block `B`.

**Step 2:** `processVotes` calls `validatePerasVote mkPerasParams sd vote`. `lookupPerasVoteStake` returns `PerasVoteStake 1_000_000`. This is stored in `ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1_000_000 }`.

**Step 3:** `updateCandidateVoteState` calls `votesReachQuorum cfg [vote]`. `totalVoteStake = PerasVoteStake 1_000_000`. `stakeAboveThreshold` evaluates `1_000_000 >= 0.75 + 0.0` → `True`.

**Step 4:** `forgePerasCert` is called, producing a `ValidatedPerasCert` for block `B` with `vpcCertBoost = perasWeight params`.

**Step 5:** The certificate is stored and propagated. All honest nodes now treat block `B` as having a Peras boost, preferring it in chain selection — with no genuine quorum having been reached. [9](#0-8) [10](#0-9)
