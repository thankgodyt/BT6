### Title
Peras Certificate Validation Bypass Allows Any Peer to Inject Arbitrary Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` (success) for every inbound certificate, performing no cryptographic or structural validation whatsoever. This stub is wired directly into the production node-to-node `PerasCertDiffusion` inbound handler. Any unprivileged peer can therefore inject a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` target, causing the receiving node to apply a Peras weight boost to an attacker-chosen block and potentially switch to a non-canonical chain.

---

### Finding Description

**Root cause — unconditional `Right` in `validatePerasCert`:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** instance of `BlockSupportsPeras` in the codebase (confirmed by `grep_search`). There is no Cardano-specific override. Every `PerasCert` received from any peer is unconditionally promoted to a `ValidatedPerasCert` carrying the full `perasWeight` boost (`PerasWeight 15` from `mkPerasParams`). [2](#0-1) 

**Production inbound handler wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` calls this validator on every inbound certificate not already in the DB, and on `([], validatedCerts)` (all valid) immediately adds each one to the ChainDB: [4](#0-3) 

This pool writer is registered as the production `hPerasCertDiffusionClient` handler in `mkHandlers`: [5](#0-4) 

**End-to-end exploit path:**

1. Attacker connects to a victim node via the `PerasCertDiffusion` mini-protocol (standard node-to-node, no privilege required).
2. Attacker sends a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = <point of a minority-fork block B>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}`.
4. The certificate is added to `PerasCertDB` via `ChainDB.addPerasCertAsync`, triggering chain selection.
5. Chain selection now applies a weight boost of 15 to block B, potentially making the minority fork heavier than the honest chain.
6. The node switches to the attacker-chosen fork. [6](#0-5) 

---

### Impact Explanation

**High — Chain selection manipulation via unauthorized certificate injection.**

An unprivileged peer can make an honest node apply a `PerasWeight 15` boost to any block of the attacker's choosing. Because Peras weight boosts are the mechanism by which the protocol enforces finality preferences, injecting a forged certificate for a minority-fork block can cause the victim node to diverge from the honest majority chain. This directly violates the chain-selection security assumption: the node prefers a non-canonical, less-secure chain without any stake majority or cryptographic capability on the attacker's part.

---

### Likelihood Explanation

**High.** The `PerasCertDiffusion` mini-protocol is a standard node-to-node protocol reachable by any peer. No keys, stake, or privileged access are required. The attacker only needs to know a valid block point (obtainable from the public chain) to target. The stub is the sole implementation and is unconditionally used in production.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The certificate's BLS aggregate signature (or equivalent committee signature scheme) against the registered committee public keys.
- That the signing committee members collectively hold sufficient stake to meet the quorum threshold (`perasQuorumStakeThreshold`).
- That the boosted block point corresponds to a known, valid block.

Until real validation is implemented, the `PerasCertDiffusion` inbound handler should be disabled or gated behind a feature flag so that no peer-supplied certificates are accepted. [7](#0-6) 

---

### Proof of Concept

**Setup:** A local private testnet with two nodes, A (victim) and B (attacker). Both nodes are on the honest chain at tip `T`.

**Steps:**

1. On node B, identify a minority-fork block `B_fork` at point `(slot=S, hash=H)` that is in node A's VolatileDB but not on its current chain.
2. Node B connects to node A via the `PerasCertDiffusion` mini-protocol.
3. Node B sends a single `PerasCert { pcCertRound = currentRound, pcCertBoostedBlock = BlockPoint S H }`.
4. Node A's `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}`.
5. The certificate is added to node A's `PerasCertDB`; chain selection is triggered.
6. **Expected (correct) outcome:** Certificate rejected; node A stays on honest chain.
7. **Actual outcome:** Certificate accepted; node A's chain selection now weights the fork containing `B_fork` 15 units heavier; if the fork is otherwise competitive, node A switches to it, diverging from the honest majority.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
