### Title
Unchecked Caller in `request_refund` Allows Attacker to Redirect Pending BTC Refunds and Block Legitimate Refund Requests - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` imposes no restriction on who can call it. When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the caller freely supplies any `refund_address`. Combined with a duplicate-request guard that prevents a second request for the same UTXO, an attacker can front-run a legitimate refund, lock the victim's UTXO under an attacker-controlled BTC address, and block the victim from submitting their own refund request for the full `unsafe_refund_timelock_sec` (14 days by default). If the DAO does not reject within that window, the attacker executes the refund and steals the deposited BTC.

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries only `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. There is no check that the caller is the original depositor or has any relationship to the deposit: [1](#0-0) 

The only guard on `refund_address` inside `internal_request_refund` is: [2](#0-1) 

When `deposit_msg.refund_address` is `None`, this block is skipped entirely and any caller-supplied BTC address is accepted without validation.

In `request_refund_callback`, a duplicate-request guard prevents a second request for the same UTXO: [3](#0-2) 

This means the **first** caller to submit a refund request for a given UTXO wins. An attacker who front-runs the legitimate user locks the UTXO under the attacker's BTC address and prevents the user from ever submitting their own refund request.

After `unsafe_refund_timelock_sec`, `execute_refund` is also callable by any NEAR account with no caller restriction: [4](#0-3) 

If the DAO does not reject the attacker's request within 14 days, the attacker calls `execute_refund`, which triggers MPC signing of a transaction paying the attacker's BTC address.

The `deposit_msg` used to derive the deposit path is publicly observable: it is emitted via `Event::LogDepositAddress` when `get_user_deposit_address` is called, and the BTC transaction itself is public on-chain. [5](#0-4) 

The output-script verification in `request_refund_callback` only confirms that the transaction output matches the deposit address derived from `deposit_msg`; it does not verify the identity of the caller: [6](#0-5) 

### Impact Explanation

- **Guaranteed (Medium)**: The attacker blocks the legitimate depositor from submitting their own refund request. The user's BTC is inaccessible through the refund path for the entire `unsafe_refund_timelock_sec` window (14 days by default), constituting attacker-triggered temporary locking of bridged funds.
- **Conditional (Critical)**: If the DAO does not reject the attacker's request within 14 days, the attacker calls `execute_refund`, the bridge constructs a PSBT paying the attacker's BTC address, MPC signs it, and the attacker receives the user's BTC — a direct theft of user funds. [7](#0-6) 

### Likelihood Explanation

- The `deposit_msg` is publicly derivable from on-chain data (NEAR events, BTC transaction OP_RETURN, or the deposit address itself).
- The BTC transaction proof is publicly available from the Bitcoin blockchain.
- The attacker only needs to attach the required NEAR storage deposit and submit a valid Light Client proof — both are permissionless.
- The attack requires no privileged access, no leaked keys, and no operator collusion.
- The sole mitigation is DAO vigilance over a 14-day window; any monitoring gap or operational delay is sufficient for the attacker to execute.

### Recommendation

Restrict `request_refund` so that only the original depositor (`deposit_msg.recipient_id`) can submit a refund request when `deposit_msg.refund_address` is `None`. Alternatively, require that `deposit_msg.refund_address` always be pre-committed at deposit time (enforced during `verify_deposit`) so that the refund destination cannot be overridden by an arbitrary caller.

### Proof of Concept

1. Alice deposits 1 BTC to the bridge. Her `deposit_msg` has `refund_address: None` and `recipient_id: alice.near`. The relayer has not yet called `verify_deposit`.
2. Bob (attacker) observes the BTC transaction on-chain and reconstructs Alice's `deposit_msg` from the public deposit address derivation event.
3. Bob calls `request_refund(deposit_msg=Alice's, refund_address="bob_btc_address", tx_bytes=..., vout=0, proof=..., gas_fee=None)` with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the Light Client proof, confirms the output script matches Alice's deposit address (it does), and stores the refund request with `refund_address = "bob_btc_address"`.
5. Alice attempts `request_refund` with her own BTC address — the call panics: `"Refund request already exists for this UTXO"`.
6. The DAO does not notice or act within 14 days.
7. Bob calls `execute_refund(utxo_storage_key=...)`. The bridge builds a PSBT sending 1 BTC to Bob's address and requests MPC signing.
8. The signed transaction is broadcast; Bob receives Alice's 1 BTC.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
