### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Produces Incorrect Non-Persistent Seat Counts for Large Lambda, Enabling Peras Vote-Weight Inflation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds. Because `x = -lambda`, the correct value is `e^lambda`. For any non-persistent voter whose `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, the Taylor-series convergence test terminates with a wrong answer, and the voter is assigned an incorrect number of non-persistent seats. An over-count inflates the voter's `VoteWeight` in `implEligiblePartyVoteWeight`, allowing them to contribute more stake toward quorum than the protocol intends.

---

### Finding Description

`localSortitionNumSeats` computes the Poisson parameter:

```
lambda = fromRational (numNonPersistentVoters * voterStake / totalNonPersistentStake)
```

and then calls:

```haskell
taylorExpCmpFirstNonLower
  3          -- boundX  ← HARDCODED
  orders
  (-lambda)
``` [1](#0-0) 

The function's own documentation states:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

Inside `decideOne`, the error term is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX < e^lambda`, `errorTerm` is smaller than the true Taylor-remainder bound. The algorithm then:

1. Declares a threshold **ABOVE** (`cmp >= acc' + errorTerm`) when the partial sum has not yet converged — returning `Just i` (granting `i+1` seats) prematurely.
2. Declares a threshold **BELOW** (`cmp < acc' - errorTerm`) when it is actually indeterminate — skipping to the next threshold and potentially granting even more seats.
3. Hits the `maxN = 1000` iteration cap and returns `Stop` (grants seats) when the series has not converged.

The threshold at which `boundX = 3` becomes incorrect is `lambda = ln(3) ≈ 1.099`. For a committee with `numNonPersistentVoters = 100`, any voter holding more than `ln(3)/100 ≈ 1.1 %` of non-persistent stake has `lambda > 1.099` and is affected. For `lambda = 5` (e.g., 5 % stake in a 100-seat committee), `e^5 ≈ 148`, so the error bound is underestimated by a factor of ~49×.

The code itself contains a TODO acknowledging the constant is unvalidated:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3)

### Impact Explanation

`localSortitionNumSeats` is called in three production verification paths:

1. **`implVerifyVote`** — verifies an individual non-persistent vote. [5](#0-4) 

2. **`implVerifyCert`** — verifies a Peras certificate containing non-persistent voters. [6](#0-5) 

3. **`implCheckShouldVote`** — self-check by the voter before forging a vote. [7](#0-6) 

The returned `NonZero LocalSortitionNumSeats` is stored in the `WFALSNonPersistentMember` eligibility witness and fed directly into `implEligiblePartyVoteWeight`:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [8](#0-7) 

An inflated seat count directly inflates `VoteWeight`. Because quorum is checked against the sum of `VoteWeight` values, a voter with an over-counted seat count can push a certificate over the quorum threshold with fewer legitimate co-voters than the protocol requires. This constitutes an unauthorized Peras certificate acceptance — a bypass of Peras voting committee checks.

---

### Likelihood Explanation

- The bug is triggered for any non-persistent voter with `lambda > ln(3)`. For realistic committee sizes (e.g., 100 non-persistent seats), this threshold is ~1.1 % of non-persistent stake — easily met by any mid-sized stake pool.
- The attacker is a legitimate pool operator (non-persistent committee candidate) submitting a crafted vote or certificate over the standard Peras miniprotocol. No privileged keys, no stake majority, no external dependency is required beyond holding a modest stake fraction.
- The code's own TODO comment confirms the constant has never been validated against the mathematical requirement.
- The bug is deterministic: for a given `lambda` and VRF output, the incorrect seat count is reproducible across all verifying nodes, so the inflated certificate passes verification on every honest node.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound `e^lambda`, computed using the existing `FixedPoint` arithmetic:

```haskell
-- Correct: boundX = e^{lambda} as required by taylorExpCmpFirstNonLower
let boundX = exp (fromRational (toRational lambda))  -- or use the ledger's expFixedPoint
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      boundX
      orders
      (-lambda)
```

Alternatively, adopt the same approach used by `checkLeaderNatValue` in `cardano-ledger`, which computes the bound dynamically rather than hardcoding it. The linked issue (https://github.com/tweag/cardano-peras/issues/234) should be resolved before the Peras protocol is activated on any network where non-persistent committee members are present.

### Proof of Concept

**Setup**: A private testnet with Peras enabled. Configure a non-persistent committee with `numNonPersistentVoters = 100`. Register a stake pool holding 5 % of the non-persistent stake distribution, giving `lambda = 5`.

**Trigger**:
1. The pool operator calls `implCheckShouldVote`. `localSortitionNumSeats` is invoked with `lambda = 5` and `boundX = 3`.
2. `taylorExpCmpFirstNonLower 3 orders (-5)` runs. Because `e^5 ≈ 148 ≫ 3`, the error bound `errorTerm = abs(err' * 3)` is ~49× too small. The algorithm declares a threshold ABOVE (or hits `maxN = 1000`) before the partial sum has converged, returning `Just i` for an `i` larger than the correct value.
3. The voter forges a `WFALSNonPersistentVote` embedding the inflated `nonZeroNumSeats`.
4. `implVerifyVote` on every honest node recomputes `localSortitionNumSeats` with the same incorrect `boundX = 3` and the same `lambda = 5`, arriving at the same inflated count — so the vote passes verification.
5. `implEligiblePartyVoteWeight` multiplies the inflated seat count by `stake / nonPersistentStake`, producing a `VoteWeight` larger than the protocol intends.
6. A certificate forged from a quorum computed with this inflated weight is accepted by `implVerifyCert` on all honest nodes, boosting a block that would not have reached quorum under correct arithmetic. [9](#0-8)
