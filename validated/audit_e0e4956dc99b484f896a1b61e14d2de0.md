### Title
`cancel_withdraw` unconditionally panics for `WithdrawOriginal/PendingSign` withdrawals that have exceeded the timeout — (`contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

---

### Summary

`internal_cancel_withdraw` calls `assert_withdraw_original_pending_verify_tx`, which hard-requires the inner `OriginalState.stage` to be `PendingVerify`. If the original withdrawal is still in `PendingSign` (the relayer has not yet signed) when `max_btc_tx_pending_sec` elapses, every call to `cancel_withdraw` panics with "Not pending verify stage". No other on-chain path exists to recover the user's locked nBTC without a contract upgrade.

---

### Finding Description

A withdraw creates a `BTCPendingInfo` with state `WithdrawOriginal(OriginalState { stage: PendingSign, … })`. [1](#0-0) 

The stage advances to `PendingVerify` only after the relayer calls `sign_btc_transaction` and the signing callback completes. If the relayer is slow or offline, the record stays in `PendingSign` indefinitely.

`cancel_withdraw` (DAO/Operator-gated) is the intended recovery path once the timeout elapses: [2](#0-1) 

Inside `internal_cancel_withdraw`, after the timeout check passes, the code calls: [3](#0-2) 

`assert_withdraw_original_pending_verify_tx` matches the `WithdrawOriginal` variant (so the outer arm is taken) but then unconditionally delegates to `state.assert_pending_verify()`: [4](#0-3) 

`assert_pending_verify` panics whenever `stage != PendingVerify`: [5](#0-4) 

Result: the cancel call always reverts with "Not pending verify stage" for any `PendingSign` original, regardless of how long the timeout has been exceeded.

---

### Impact Explanation

The user's nBTC is transferred to the bridge contract at the start of the withdraw flow and is not returned until either the cancel RBF is verified or the original withdraw is verified. With the cancel path blocked, the nBTC remains locked inside the bridge contract with no on-chain recovery mechanism. Resolution requires a contract upgrade or governance intervention.

This matches: **Low — publicly reachable stuck-state / panic-driven fault in production bridge/token paths without direct theft.**

---

### Likelihood Explanation

The precondition is that the chain-signature relayer fails to sign within `max_btc_tx_pending_sec`. This is an operational scenario (relayer downtime, key-rotation lag, network partition) rather than a direct attacker action. It is realistic in production and the timeout mechanism was explicitly designed to handle exactly this case, making the missing coverage a latent operational risk.

---

### Recommendation

In `assert_withdraw_original_pending_verify_tx`, accept both `PendingSign` and `PendingVerify` stages when called from the cancel path, or introduce a separate `assert_withdraw_original_tx` (stage-agnostic) guard for `internal_cancel_withdraw`. The RBF cancel PSBT construction does not require the original to have been broadcast; it only needs the UTXO set from the original record, which is available in both stages.

---

### Proof of Concept

```
1. Alice calls ft_transfer_call → bridge creates WithdrawOriginal { stage: PendingSign }.
2. Relayer goes offline; max_btc_tx_pending_sec elapses.
3. DAO/Operator calls cancel_withdraw(original_id, output).
4. internal_cancel_withdraw:
     require!(elapsed > max_btc_tx_pending_sec)  ← passes
     assert_not_canceled()                        ← passes (cancel_rbf_reserved is None)
     assert_withdraw_original_pending_verify_tx() ← PANICS: "Not pending verify stage"
5. Alice's nBTC remains locked in the bridge with no on-chain recovery path.
```
