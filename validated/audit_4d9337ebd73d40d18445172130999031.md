### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Certificate, Enabling Crafted-Certificate Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. An unprivileged peer can therefore send a crafted `PerasCert` naming any block as the boosted target. That certificate is stored in `PerasCertDB`, its boost is folded into the `PerasWeightSnapshot`, and chain selection then uses the inflated weight to prefer the attacker's fork over the canonical chain — directly analogous to the external report's "buy seats to inflate the price, then extract value" pattern.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must authenticate a certificate before it may influence chain selection. The only deployed instance is the catch-all:

```haskell

`processCerts` rejects a batch only when `validateCert` returns `Left`; because the stub always returns `Right`, every certificate from every peer is accepted and timestamped: [3](#0-2) 

Once stored, `implGetWeightSnapshot` materialises the `PerasWeightSnapshot` by iterating over every certificate in `pcdsCertsByTicket` and summing their boosts per target block:

```haskell

`wsvTotalWeight` = `BlockNo + WeightBoost`, so a single certificate with boost `B` applied to a fork block at height `H` gives that fork a total weight of `H + B`, which can exceed the canonical chain's weight of `H_canonical`: [6](#0-5)

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a `PerasCert` naming any block in the node's VolatileDB as the boosted target. The node will accept it unconditionally, add the configured `perasWeight` boost to that block's weight, and — if the resulting total weight exceeds the current chain's weight — switch to the fork containing that block. This is a **chain-selection manipulation**: an honest node is made to prefer a non-canonical or adversarially-chosen chain, violating the longest-chain / heaviest-chain security invariant of Peras.

The analogy to the external report is exact: the `PerasWeightSnapshot` plays the role of `perp_clients_count`; the attacker "buys seats" by injecting certificates that inflate the fork's weight, causing the victim node to "pay" by rolling back to the attacker's chain.

---

### Likelihood Explanation

Peras is not enabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"), so the attack surface is limited to nodes that have explicitly opted into Peras. However, for any such node, exploitation requires only a TCP connection and the ability to send a single well-formed `PerasCert` message — no stake, no keys, no prior relationship. The object-diffusion mini-protocol is a public-facing endpoint. The TODO comments and linked issue (`tweag/cardano-peras#120`) confirm the stub is known but not yet replaced.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's committee membership proof and aggregate signature over `(round, boostedBlock)`.
2. That `pcCertRound` falls within the current valid window (not expired, not from the future).
3. That `pcCertBoostedBlock` refers to a block that could plausibly be on a valid chain (slot within range).

Until the real implementation is in place, the node should refuse to accept any inbound `PerasCert` from peers (return `Left PerasValidationErr` unconditionally) rather than accept all of them. The `makePerasCertPoolWriterFromChainDB` entry point should not be wired into the live network stack while the validation is a stub.

---

### Proof of Concept

**Setup**: A Cardano node with Peras enabled. The canonical chain has tip at block `C` with `BlockNo = 100`. A competing fork has tip at block `F` with `BlockNo = 99` (one block shorter, so normally rejected).

**Attack**:
1. Attacker connects to the node via the object-diffusion mini-protocol.
2. Attacker sends:
   ```
   PerasCert { pcCertRound = 42, pcCertBoostedBlock = BlockPoint slotF hashF }
   ```
   where `(slotF, hashF)` is the point of fork block `F` already in the node's VolatileDB.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`. [7](#0-6) 
4. Certificate is stored; `implGetWeightSnapshot` now returns `{ F → perasWeight }`.
5. `chainSelectionForBlock` is triggered for `F`; `constructPreferableCandidates` calls `preferAnchoredCandidate` with the non-empty snapshot. [8](#0-7) 
6. Fork weight = `99 + perasWeight`; canonical weight = `100`. If `perasWeight ≥ 2` (the default is non-trivial), fork weight > canonical weight → `ShouldSwitch`.
7. Node rolls back to fork `F`, abandoning the canonical chain.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
