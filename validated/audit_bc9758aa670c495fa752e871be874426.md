### Title
Failed `fin_transfer` Removes Replay Protection, Enabling Proof Reuse - (File: near/omni-bridge/src/lib.rs)

### Summary

When an inbound `fin_transfer` to NEAR fails because the recipient contract rejects the token transfer, `remove_fin_transfer` deletes the `TransferId` from `finalised_transfers`. This is the sole replay guard for inbound proofs. After deletion, the identical foreign-chain proof can be re-submitted, causing tokens to be minted or released a second time for a single foreign-chain deposit.

### Finding Description

The inbound transfer flow (Foreign → NEAR) works as follows:

1. `fin_transfer` verifies the foreign-chain proof via the prover.
2. `fin_transfer_callback` calls `process_fin_transfer_to_near`.
3. `process_fin_transfer_to_near` calls `add_fin_transfer`, which inserts the `TransferId` into `finalised_transfers` — the only on-chain replay guard.
4. Tokens are sent to the recipient via `send_tokens`, which uses `ft_transfer_call` when the transfer carries a non-empty `msg`.
5. `fin_transfer_send_tokens_callback` is invoked. If `is_refund_required` returns `true` (the recipient's `ft_on_transfer` returned `0`, i.e., rejected the tokens), the callback:
   - Burns the tokens if the token is a bridge-deployed token (`burn_tokens_if_needed`).
   - Reverts lock-accounting (`revert_lock_actions`).
   - **Calls `remove_fin_transfer`, which removes the `TransferId` from `finalised_transfers`.**

After step 5, the replay guard is gone. The prover holds no per-transfer state; it only validates the cryptographic proof against the foreign chain. Re-submitting the identical proof passes the prover again, `add_fin_transfer` succeeds (the set no longer contains the entry), and a second token release is executed.

### Impact Explanation

**For bridge-deployed (wrapped) tokens**: `burn_tokens_if_needed` destroys the tokens after the rejection. Re-submitting the proof mints a fresh batch. The attacker receives tokens on NEAR that correspond to a single foreign-chain burn, effectively creating tokens out of thin air and inflating the wrapped-token supply.

**For native (locked) tokens**: `burn_tokens_if_needed` is a no-op (only deployed tokens are burned). The bridge still holds the locked tokens. Re-submitting the proof transfers them to the attacker a second time, draining the bridge's reserve beyond what was deposited on the foreign chain.

Both cases constitute unauthorized minting or permanent loss of bridged funds — critical impact under the allowed scope. [5](#0-4) 

### Likelihood Explanation

The attacker must:
1. Initiate a legitimate transfer on a supported foreign chain (EVM, Solana, Starknet) with a non-empty `msg` field so that `ft_transfer_call` is used on the NEAR side.
2. Control the NEAR recipient address (deploy a contract whose `ft_on_transfer` returns the full amount on the first call and `0` on the second).
3. Submit the proof twice — both calls are permissionless (`fin_transfer` is public).

No privileged access, leaked keys, or external dependency failure is required. The attacker funds only the initial foreign-chain deposit; all subsequent steps are free. This is a realistic, low-barrier attack path.

### Recommendation

Do **not** remove the `TransferId` from `finalised_transfers` on a failed token delivery. The entry must remain to prevent proof replay. Instead, handle the failed delivery by:

- Keeping the `TransferId` in `finalised_transfers` permanently.
- Storing the undelivered amount in a claimable escrow keyed by the recipient, allowing the recipient to retry or withdraw without re-verifying the proof.

This mirrors the standard CEI (Checks-Effects-Interactions) pattern: the replay guard (effect) must never be undone after the proof has been accepted.

### Proof of Concept

```
1. Attacker deploys RecipientContract on NEAR.
   - First call to ft_on_transfer: returns `amount` (rejects tokens).
   - Second call to ft_on_transfer: returns `0` (accepts tokens).

2. Attacker calls initTransfer on EVM/Solana/Starknet:
   - token: any bridged token
   - recipient: RecipientContract
   - msg: "<non-empty>"   ← forces ft_transfer_call on NEAR side
   - amount: X

3. Relayer (or attacker) submits proof to NEAR fin_transfer.
   - process_fin_transfer_to_near → add_fin_transfer inserts TransferId.
   - ft_transfer_call → RecipientContract.ft_on_transfer returns X (reject).
   - fin_transfer_send_tokens_callback: is_refund_required = true.
     → burn_tokens_if_needed (burns X if deployed token).
     → remove_fin_transfer removes TransferId from finalised_transfers.

4. Attacker re-submits the identical proof to NEAR fin_transfer.
   - add_fin_transfer succeeds (TransferId absent from set).
   - ft_transfer_call → RecipientContract.ft_on_transfer returns 0 (accept).
   - Attacker receives X tokens.

Result: Attacker received X tokens on NEAR for a single deposit of X on the
foreign chain. For deployed tokens, X tokens were burned and X new tokens
minted — net +X supply inflation. For native tokens, the bridge vault is
drained by X beyond the single deposit.
```

    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {
            match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                        // Normal case: refund if the used token amount is zero
                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                        amount.0 == 0
                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }

        require!(

            BridgeError::TransferAlreadyFinalised.as_ref()

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }
