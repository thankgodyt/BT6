Audit Report

## Title
ERC1155 `safeTransferFrom` in `finTransfer` Permanently Locks Bridged Funds When Recipient Contract Lacks `IERC1155Receiver` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.finTransfer` delivers ERC1155-backed tokens via `IERC1155.safeTransferFrom`, which mandates that any contract recipient implement `IERC1155Receiver.onERC1155Received`. `initTransfer1155` accepts any cross-chain recipient string with no such validation. When a user bridges ERC1155 tokens to a contract recipient that does not implement `IERC1155Receiver` (e.g., a Gnosis Safe, DAO treasury, or DeFi vault), source-chain tokens are permanently locked: initiation succeeds and funds are committed, but every finalization attempt reverts, and no on-chain refund or cancellation path exists.

## Finding Description
`finTransfer` marks the destination nonce as used before executing the transfer: [1](#0-0) 

Then dispatches ERC1155 delivery via: [2](#0-1) 

`safeTransferFrom` is mandated by EIP-1155 to call `onERC1155Received` on any contract recipient and revert if the call fails or returns the wrong selector. Because the nonce write at line 287 is part of the same transaction, a revert in `safeTransferFrom` rolls back the nonce write — so the relayer can retry indefinitely, but the recipient address is immutably encoded in the MPC-signed Borsh payload (line 298), meaning no retry can ever succeed with a different recipient.

The ERC1155 initiation path, `initTransfer1155`, locks tokens in the bridge with no validation of whether the cross-chain recipient can receive ERC1155 tokens: [3](#0-2) 

The other `finTransfer` delivery branches — `IBridgeToken.mint` (ERC20 `_mint`, no receiver callback) and `IERC20.safeTransfer` — impose no receiver-interface requirement: [4](#0-3) [5](#0-4) 

There is no `cancelTransfer`, `refund`, or equivalent function anywhere in `OmniBridge.sol` to recover source-chain locked tokens.

## Impact Explanation
**Critical — permanent freezing of bridged funds.** When a user bridges ERC1155 tokens to a contract recipient that does not implement `IERC1155Receiver`: (1) source-chain tokens are locked in the bridge via `initTransfer1155`; (2) every `finTransfer` call on the destination chain reverts at `safeTransferFrom`; (3) the MPC-signed payload fixes the recipient, so no retry can substitute a valid address; (4) no on-chain refund path exists. The bridged assets are permanently frozen. This matches the allowed critical impact: *permanent freezing of bridged funds across EVM flows*.

## Likelihood Explanation
Any unprivileged bridge user can trigger this by specifying a contract address as the cross-chain recipient in `initTransfer1155`. No special privileges, leaked keys, or colluding parties are required. Many widely-deployed contracts — Gnosis Safe multisigs, governance contracts, yield aggregators, lending protocols — do not implement `IERC1155Receiver`. The protocol provides no warning or pre-flight validation. The condition is reachable through normal bridge usage.

## Recommendation
Apply one or more of the following mitigations:

1. **Validate at initiation**: In `initTransfer1155`, when the parsed recipient is a contract address on the destination chain, call `supportsInterface(type(IERC1155Receiver).interfaceId)` on the recipient and revert if it returns false.

2. **Use non-safe transfer in `finTransfer`**: Replace `safeTransferFrom` with a low-level `transferFrom` (without the receiver callback) for ERC1155 delivery, consistent with how ERC20 tokens are delivered. This removes the inconsistency at the cost of not enforcing the receiver interface — acceptable if the user is responsible for specifying a valid recipient.

3. **Add a cancellation/refund path**: Implement an on-chain mechanism allowing users to cancel a committed source-chain transfer and recover locked tokens if finalization is provably impossible (e.g., after a timeout or explicit failure proof).

## Proof of Concept
1. Admin registers an ERC1155 token via `logMetadata1155`, populating `multiTokens[deterministicToken]`.
2. User calls `initTransfer1155(tokenAddress, tokenId, amount, fee, nativeFee, "eth:0xGnosisSafe...", "")` where `0xGnosisSafe` is a deployed Gnosis Safe that does not implement `IERC1155Receiver`. `safeTransferFrom` at line 458 succeeds (bridge is the recipient, which implements `onERC1155Received`). Tokens are locked.
3. NEAR `fin_transfer` processes the proof; MPC signs a `TransferMessagePayload` with `recipient = 0xGnosisSafe`.
4. Relayer calls `finTransfer` on the destination EVM chain. Execution reaches line 324: `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), 0xGnosisSafe, tokenId, amount, "")`. The ERC1155 contract calls `0xGnosisSafe.onERC1155Received(...)`. The Gnosis Safe does not implement this selector; the call reverts. The entire `finTransfer` transaction reverts, rolling back the nonce write at line 287.
5. The relayer retries — same result every time, because the recipient is fixed in the MPC-signed payload.
6. The user's ERC1155 tokens remain permanently locked in the source-chain bridge with no recovery path. [6](#0-5) [7](#0-6)
