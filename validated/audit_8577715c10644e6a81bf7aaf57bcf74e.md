### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates Without Any Cryptographic or Semantic Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. Any unprivileged peer can send a completely fabricated `PerasCert` over the object-diffusion mini-protocol, which will be accepted, stored in the `PerasCertDB`, and used to boost the chain-selection weight of an arbitrary block. This allows an adversary to manipulate chain selection on an honest node without holding any stake or keys.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The production instance for all block types is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the direct analog of the reported Solidity bug: just as `protectedTokens()` was supposed to include `yveCrv` in its protected set but omitted it entirely, `validatePerasCert` is supposed to validate the full set of certificate properties (aggregate BLS signature, round number, boosted block hash, quorum membership) but validates **none** of them — the entire validation set is empty.

The inbound path that reaches this stub is `processCerts` in the object-diffusion pool writer:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

This is used in both the `PerasCertDB`-backed writer and the `ChainDB`-backed writer: [3](#0-2) 

`processCerts` calls `validateCert` on each received certificate and, if all pass, stores them via `addCert`. Because `validatePerasCert` always returns `Right`, every certificate from every peer passes: [4](#0-3) 

Once stored, the certificate contributes `vpcCertBoost = perasWeight params` to chain-selection weight via `getWeightSnapshot` / `PerasWeightSnapshot`, causing the node to prefer the boosted block over competing chains.

The `PerasCert` data type accepted over the wire contains only `pcCertRound` and `pcCertBoostedBlock`: [5](#0-4) 

An attacker can freely craft any `(pcCertRound, pcCertBoostedBlock)` pair and have it accepted as a valid certificate.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

Peras certificates exist specifically to boost the chain-selection weight of a block. A node that receives a fabricated certificate for an adversary-controlled block will assign it extra weight in chain selection, potentially causing it to prefer that block over the honest canonical chain. Because the boost is applied without any quorum or signature check, a single peer with no stake can inject an arbitrary number of fake certificates for arbitrary blocks, systematically biasing chain selection on any node it connects to.

---

### Likelihood Explanation

**High.** The object-diffusion mini-protocol is a standard peer-to-peer channel reachable by any unprivileged network peer. The `PerasCert` wire format is simple (round number + block point), requires no keys or stake to construct, and the stub validation gate offers no resistance. The only prerequisite is a TCP connection to the target node.

---

### Recommendation

Replace the stub `validatePerasCert` with a complete implementation that verifies:
1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. That the voter set constitutes a valid quorum under the current committee for the given round.
3. That `pcCertRound` is within the acceptable window (not stale, not from the future).
4. That `pcCertBoostedBlock` refers to a block that exists and is plausible given the current chain state.

Until this is implemented, inbound certificates from untrusted peers should not be used to influence chain-selection weight.

---

### Proof of Concept

1. Connect to a target node's object-diffusion endpoint as an unprivileged peer.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of adversary block>`.
3. Send the certificate via the object-diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB` / `ChainDB`.
6. `getWeightSnapshot` now returns a `PerasWeightSnapshot` that assigns `perasWeight params` extra weight to the adversary's block.
7. Chain selection on the honest node now prefers the adversary's block over the canonical chain tip, constituting a chain-selection manipulation without any stake or cryptographic material.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
