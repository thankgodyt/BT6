### Title
Unprivileged Caller Can Corrupt Withdrawal Signing by Injecting Wrong `key_version` — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary

`sign_btc_transaction` is a fully public function with no caller authorization. Any NEAR account can invoke it for any pending withdrawal, supplying an arbitrary `key_version`. Because the contract stores the first signature that arrives and permanently blocks re-signing of the same input, an attacker who races the legitimate relayer with a mismatched `key_version` permanently corrupts the PSBT, producing a Bitcoin transaction whose signature does not match the on-chain script pubkey. The withdrawal can never confirm on Bitcoin, and the user's nBTC remains locked in the bridge until a DAO/Operator manually cancels the withdrawal.

### Finding Description

`sign_btc_transaction` is declared as a plain `#[payable] #[pause] pub fn` with no `#[access_control_any]` or `#[trusted_relayer]` guard: [1](#0-0) 

It accepts a caller-supplied `key_version: u32` and passes it verbatim to the MPC signing service: [2](#0-1) 

The callback that processes the MPC response stores the returned signature unconditionally and then enforces a one-write-only invariant: [3](#0-2) 

The public key embedded in the PSBT is derived from the UTXO path **without** the caller-supplied `key_version`: [4](#0-3) 

When `key_version` differs from the version used to derive the deposit address, the MPC service produces a valid ECDSA signature but for a **different** child key. That signature is saved alongside the path-derived public key. Once all inputs are signed the PSBT is finalized and `tx_bytes_with_sign` is written: [5](#0-4) 

The resulting Bitcoin transaction carries a signature that does not satisfy the P2WPKH/P2PKH script locking the bridge UTXO. Bitcoin nodes reject it. `verify_withdraw` can never succeed, and the pending info is stuck in `PendingVerify`.

### Impact Explanation

The user's nBTC is held by the bridge during the withdrawal lifecycle and is only burned upon successful `verify_withdraw`. With the signing permanently corrupted the burn never executes, the nBTC is frozen, and the bridge UTXO is also effectively frozen (the signed-but-invalid transaction has been broadcast, spending the UTXO in the mempool). Recovery requires a DAO/Operator `cancel_withdraw` call, which is a privileged action: [6](#0-5) 

This matches the allowed impact: **attacker-triggered temporary locking of bridged funds requiring operator intervention**.

### Likelihood Explanation

- `btc_pending_sign_id` is emitted as a public on-chain event (`GenerateBtcPendingInfo`) the moment a withdrawal is initiated, so any observer can learn it immediately.
- The attacker only needs to attach a small NEAR deposit (forwarded to the MPC service) and submit one transaction before the legitimate relayer.
- No special role, leaked key, or off-chain infrastructure is required.
- The attack is cheap and repeatable across every withdrawal in the system.

### Recommendation

Restrict `sign_btc_transaction` to authorized callers (e.g., add `#[trusted_relayer]` or `#[access_control_any(roles(Role::DAO, Role::Operator, Role::UnrestrictedRelayer))]`), mirroring the pattern already applied to `verify_withdraw_v2` and `verify_deposit_v2`.

Additionally, validate `key_version` against a contract-configured allowlist or a single canonical value stored in `Config`, and reject calls that supply a version that does not match the key used to derive the deposit address.

### Proof of Concept

1. Alice calls `ft_transfer_call` to withdraw 1 BTC. The bridge creates `BTCPendingInfo` with `state = PendingSign` and emits `GenerateBtcPendingInfo { btc_pending_id: "abcd…" }`.
2. Attacker observes the event and immediately calls:
   ```
   sign_btc_transaction(btc_pending_sign_id="abcd…", sign_index=0, key_version=1)
   ```
   attaching enough NEAR for the MPC fee.
3. The MPC service signs the payload with the child key for `(path, key_version=1)` — a different key than the one locking the UTXO (which was derived with `key_version=0`).
4. `sign_btc_transaction_callback` stores the mismatched signature. The `"Already signed"` guard now blocks any further signing attempt for `sign_index=0`.
5. Once all inputs are "signed" (with at least one bad signature), the PSBT is finalized and the invalid transaction is stored in `tx_bytes_with_sign`; the state advances to `PendingVerify`.
6. The relayer broadcasts the transaction; Bitcoin nodes reject it (invalid witness).
7. `verify_withdraw` can never return `true`. Alice's nBTC is frozen until a DAO/Operator calls `cancel_withdraw`. [7](#0-6) [8](#0-7)

    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
