Audit Report

## Title
`normalize_amount` Floor-Division to Zero Causes Permanent Fund Lock in `sign_transfer` - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts any transfer where `fee < amount` without verifying that the net amount survives decimal normalization. When `amount_without_fee()` is smaller than the normalization divisor (`10^(origin_decimals - decimals)`), `normalize_amount` returns `0` via floor division. Every subsequent `sign_transfer` call then panics on `require!(amount_to_transfer > 0, ...)`, and because no public cancel or refund path exists, the user's tokens are permanently locked or burned in the bridge.

## Finding Description

**Step 1 — Permissive validation in `init_transfer`**

The only pre-lock check is:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

No normalization check is performed before tokens are committed.

**Step 2 — Tokens are burned/locked immediately**

`init_transfer_internal` at L1850-1857 calls `burn_tokens_if_needed` and `lock_tokens_if_needed` on the full `amount` before any normalization is evaluated.

**Step 3 — `normalize_amount` uses floor division**

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The code comment at L2781-2782 explicitly acknowledges: *"When fee = 0, dust stays locked/burned."* However, this only contemplates sub-unit remainders; it does not address the case where the **entire** amount normalizes to zero.

**Step 4 — `sign_transfer` permanently rejects the transfer**

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

Every call to `sign_transfer` for this `transfer_id` panics. The transfer record remains in `pending_transfers` indefinitely.

**Step 5 — No public cancel/refund path**

`remove_transfer_message` (L2194-2211) is a private helper called only from `claim_fee_callback`. No `pub fn cancel_transfer` or equivalent exists. The user has no on-chain mechanism to recover their locked/burned tokens.

## Impact Explanation

This is a **permanent freezing of bridged funds** triggered by a normal user action. For any token pair where `origin_decimals > decimals` (e.g., a NEAR-native 24-decimal token bridging to an 18-decimal EVM chain, divisor = `10^6`), any transfer with `amount_without_fee() < 10^6` base units results in tokens that are irreversibly burned or locked with no recovery path. This matches the allowed critical impact: *"permanent freezing of bridged funds"* and *"decimal/normalization abuse that changes user or protocol balances."*

## Likelihood Explanation

Any unprivileged user calling `ft_transfer_call` into the bridge can trigger this. No special permissions, front-running, or external dependencies are required. For a 24-vs-18 decimal pair, the threshold is 1,000,000 base units — a realistic "dust" or small transfer amount. The condition is reachable on every deployment that supports such a token pair.

## Recommendation

Add a normalization check inside `init_transfer` (or at the start of `init_transfer_internal`) **before** `burn_tokens_if_needed` / `lock_tokens_if_needed` is called:

```rust
// After building transfer_message, before locking tokens:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This ensures the transfer is rejected before any tokens are committed, mirroring the guard already present in `sign_transfer`.

## Proof of Concept

1. Register a NEAR-native token with `origin_decimals = 24`, `decimals = 18` (divisor = `10^6`).
2. Call `ft_transfer_call` with `amount = 500_000` and `msg` encoding an `InitTransferMsg` with `fee = 0` and any non-NEAR recipient.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000`). `init_transfer_internal` burns/locks `500_000` tokens. The transfer is stored in `pending_transfers`.
4. Call `sign_transfer` with the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin_decimals:24, decimals:18})` = `500_000 / 1_000_000` = `0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Repeat step 4 indefinitely — it always panics. The `500_000` tokens are permanently lost.

A local integration test can confirm this by: (a) deploying the bridge and a mock NEP-141 token with the above decimal configuration, (b) calling `ft_transfer_call` with `amount = 500_000`, (c) asserting the transfer is stored in `pending_transfers`, and (d) asserting every `sign_transfer` call returns `ERR_INVALID_AMOUNT_TO_TRANSFER` while the token balance of the bridge remains unchanged (tokens locked forever).
