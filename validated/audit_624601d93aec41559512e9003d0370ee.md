### Title
Reachable u128 Underflow Panic in `check_withdraw_psbt` Does Not Lock Funds — (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

The underflow panic at lines 242–243 of `check_withdraw_psbt` is **real and reachable** because the workspace enables `overflow-checks = true`. However, the claimed critical impact — **permanent locking of the user's nBTC** — does **not** materialize. NEP-141's `ft_resolve_transfer` callback refunds the full token amount to the sender whenever `ft_on_transfer` panics. The actual impact is a publicly reachable panic-driven fault (Low severity), not a fund-locking or fund-destruction event.

---

### Finding Description

**Overflow-checks are enabled.** The workspace `Cargo.toml` sets:

```toml
[profile.release]
overflow-checks = true
``` [1](#0-0) 

This means any u128 underflow in release WASM builds panics rather than wrapping.

**The two vulnerable arithmetic lines** in `check_withdraw_psbt`:

```rust
let max_received_amount = amount - withdraw_fee - gas_fee;        // line 242
let min_received_amount = max_received_amount - config.min_change_amount; // line 243
``` [2](#0-1) 

The `gas_fee` validation that would catch an oversized fee appears **after** these lines:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, ...
);
``` [3](#0-2) 

Because the guard is ordered after the arithmetic, it can never prevent the underflow.

**`gas_fee` is attacker-influenced.** It is computed as:

```rust
let gas_fee = total_input_amount - total_output_amount;
``` [4](#0-3) 

`total_input_amount` comes from the bridge UTXOs the attacker selects (via the `input: Vec<OutPoint>` field in the `Withdraw` message), and `total_output_amount` comes from the PSBT outputs the attacker crafts. By selecting large UTXOs and providing a minimal user output, the attacker can make `gas_fee` arbitrarily large within the bridge's UTXO set.

**The public entry path** is fully unprivileged:

`ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt` [5](#0-4) [6](#0-5) 

The only pre-check before `check_withdraw_psbt` is called is `amount >= min_withdraw_amount`: [7](#0-6) 

No guard validates that `amount - withdraw_fee >= gas_fee` before the arithmetic executes.

---

### Impact Explanation

**The panic is real but the fund-locking claim is wrong.**

When `ft_on_transfer` panics in NEAR, the execution receipt fails and all state mutations within that call (including the UTXO removal performed by `generate_vutxos`) are atomically rolled back. The nBTC contract's `ft_resolve_transfer` callback — which is scheduled by `ft_transfer_call` — detects the failed promise and refunds the full token amount to the sender. This is standard NEP-141 behavior enforced by `near-contract-standards`.

Consequently:
- The user's nBTC is **refunded**, not permanently locked or destroyed.
- The bridge's UTXO set is **restored** (state rollback).
- The attacker recovers their nBTC (minus NEAR gas), making this a zero-cost self-funded DoS.

The actual impact is: **publicly reachable panic-driven fault in a production bridge path, without direct fund loss** — Low severity under the allowed scope.

---

### Likelihood Explanation

The panic is triggerable by any user who holds `min_withdraw_amount` nBTC and can observe the bridge's UTXO set (which is public on-chain state). The attacker selects a large UTXO and crafts a PSBT with a minimal user output to push `gas_fee` into the underflow range. No privileged access is required.

---

### Recommendation

Reorder the validation so that `gas_fee` is range-checked **before** the subtraction, or use checked/saturating arithmetic:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].", gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee)
);
require!(
    amount >= withdraw_fee + gas_fee + config.min_change_amount,
    "Withdrawal amount too small to cover fees and minimum change"
);
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
```

### Proof of Concept

```
config.min_withdraw_amount = 10_000 sat
config.min_change_amount   = 5_000 sat
config.max_btc_gas_fee     = 50_000 sat
withdraw_fee               = 100 sat (computed from fee schedule)

Bridge UTXO selected by attacker: 1_000_000 sat
PSBT user output:                      1 sat
gas_fee = 1_000_000 - 1 = 999_999 sat

Line 242: 10_000 - 100 - 999_999  →  u128 underflow → PANIC (overflow-checks=true)
```

The panic aborts `ft_on_transfer`; `ft_resolve_transfer` refunds 10_000 sat nBTC to the attacker. No funds are lost; the bridge panics instead of returning a graceful error.

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }
    }
