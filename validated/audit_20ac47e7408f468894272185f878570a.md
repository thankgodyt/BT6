Audit Report

## Title
`sign_transfer()` Normalisation-to-Zero Check Deferred After Irreversible Token Burn/Lock — Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

The NEAR omni-bridge uses a two-transaction transfer flow. In the first transaction (`init_transfer`/`init_transfer_internal`), tokens are irreversibly burned or locked. In the second transaction (`sign_transfer`), the normalised amount is computed and validated against zero. Because NEAR's atomicity does not span separate transactions, any transfer whose `amount_without_fee` falls below the decimal-precision threshold causes `sign_transfer` to always panic, with no cancel or refund path, permanently destroying the user's funds.

## Finding Description

**Step 1 — `init_transfer_internal` (L1829–1865):** Tokens are burned or locked unconditionally before any normalisation check:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

The only fee guard at this stage (`L554–557`) is `fee < amount`, which explicitly permits `amount_without_fee = 1`.

**Step 2 — `sign_transfer` (L447–521):** The normalised amount is computed and checked:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

**`normalize_amount` (L2784–2787)** uses floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token where `origin_decimals > decimals` (e.g., 24 on NEAR, 18 on EVM — a 6-decimal gap, threshold = 10^6), any `amount_without_fee < 10^(origin_decimals − decimals)` truncates to zero. The `require!` then panics. The code comment at L2781–2783 explicitly acknowledges "When fee = 0, dust stays locked/burned," but this refers to remainders, not the case where the entire amount normalises to zero.

**`sign_transfer_callback` (L648–668)** provides no refund path — it only handles a successful MPC signature result and emits a log event. There is no `cancel_transfer` or user-initiated unlock function reachable after `init_transfer` succeeds.

## Impact Explanation

This matches the Critical allowed impact: **permanent freezing or loss of bridged funds**.

- **Bridge-deployed tokens:** burned at `init_transfer` time and permanently destroyed — the user loses the full transferred amount with no mint-back path.
- **Native tokens:** locked at `init_transfer` time and permanently frozen — no code path exists to release the locked balance because `sign_transfer` always panics and no other function unlocks them.

Both outcomes are irreversible and caused entirely by on-chain contract logic in this repository.

## Likelihood Explanation

Any token registered with `origin_decimals > decimals` is affected. This is the standard configuration for NEAR-native tokens (24 decimals) bridged to EVM chains (18 decimals), giving a threshold of 1,000,000 base units. A user who sends an amount below this threshold — or who sets a fee high enough that `amount_without_fee` falls below it — will trigger the condition. The `init_transfer` fee check (`fee < amount`) explicitly allows `amount_without_fee = 1`. This is a realistic user mistake (sending a "small" amount) with no on-chain guard. No special privileges are required to call `ft_transfer_call` → `init_transfer`.

## Recommendation

Move the `normalize_amount > 0` check into `init_transfer` (or `init_transfer_internal`) **before** burning or locking tokens:

```rust
// Before burn_tokens_if_needed / lock_tokens_if_needed:
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::FailedToGetTokenAddress);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This causes `ft_transfer_call` to return the tokens to the sender (NEAR's `ft_transfer_call` refund mechanism) rather than burning/locking them.

## Proof of Concept

Given a token with `origin_decimals = 24`, `decimals = 18` (threshold = 1,000,000):

1. Alice calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
2. `init_transfer` passes the `fee < amount` check (0 < 500,000). `init_transfer_internal` burns 500,000 units. `TransferMessage` is stored on-chain. Transaction succeeds.
3. Trusted relayer calls `sign_transfer`:
   - `amount_without_fee = 500_000`
   - `normalize_amount(500_000, {origin: 24, dest: 18}) = 500_000 / 10^6 = 0`
   - `require!(0 > 0, ...)` → **panic**
4. `sign_transfer` always panics for this transfer. Alice's 500,000 units are permanently burned. No cancel, no refund, no unlock path exists.
