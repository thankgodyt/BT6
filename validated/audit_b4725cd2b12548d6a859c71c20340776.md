### Title
`emptyPerasWeightSnapshot` Substituted for Actual Peras Weights in `checkPreferTheirsOverOurs` Causes Incorrect Chain-Preference Decision Beyond Forecast Horizon — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs`, the chain-preference comparison passes `emptyPerasWeightSnapshot` (a zero-weight map) instead of the actual live `PerasWeightSnapshot` to `preferAnchoredCandidate`. This is structurally identical to the Burve `removedBalance`-before-assignment bug: a zero/default value is substituted for the actual computed value in a security-critical comparison. The consequence is that Peras certificate boosts are completely ignored when the ChainSync client decides whether to stay connected to a peer whose candidate chain extends beyond the forecast horizon. A node will incorrectly disconnect from peers offering a Peras-boosted canonical chain that is genuinely heavier than the node's current selection, causing the node to remain on a less-secure fork.

---

### Finding Description

`checkPreferTheirsOverOurs` is called from `readLedgerStateHelper` whenever the ledger cannot yet forecast a view for the candidate tip (the candidate is beyond the forecast horizon). Its purpose is to disconnect from peers whose candidate chain is not preferred over the node's current selection, preventing the node from wasting resources on a chain it will never adopt.

The comparison is performed via `preferAnchoredCandidate`, which, when Peras is active, computes the total weight of each fragment as `blockNo + weightBoostOfFragment`. The weight boost is looked up from the supplied `PerasWeightSnapshot`.

At line 1841–1842, the snapshot argument is hard-coded to `emptyPerasWeightSnapshot` — an empty `Map` that returns `mempty` (i.e. `PerasWeight 0`) for every point:

```haskell
-- Client.hs lines 1834–1851
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← zero weights; should be actual snapshot
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`emptyPerasWeightSnapshot` is defined as `PerasWeightSnapshot Map.empty`, which causes `weightBoostOfFragment` to return `mempty` for every fragment: [2](#0-1) 

`preferAnchoredCandidate` with a non-empty snapshot computes the intersection of the two fragments and compares their `WeightedSelectView`s, where `wsvTotalWeight = blockNo + weightBoost`. With `emptyPerasWeightSnapshot`, `weightBoost` is always zero for both fragments, so the comparison degenerates to a pure block-count comparison — exactly as if Peras were disabled: [3](#0-2) [4](#0-3) 

The actual live snapshot is available in the ChainDB via `getPerasWeightSnapshot` and is used correctly everywhere else in chain selection (e.g. `chainSelectionForBlock`, `initialChainSelection`, `compareAnchoredFragments`). Only this one call site substitutes the zero snapshot. [5](#0-4) 

---

### Impact Explanation

When Peras is active, a candidate chain can be heavier than the node's current selection even if it has fewer blocks, because Peras certificate boosts add weight on top of block count. The canonical chain is precisely the chain with the highest total weight.

Consider the following scenario:

- Node's current chain: 100 blocks, no Peras boosts → total weight = 100.
- Peer's candidate chain: 98 blocks, one Peras certificate boost of weight B > 2 → total weight = 98 + B > 100.

With the actual snapshot, `preferAnchoredCandidate` returns `ShouldSwitch` (candidate is heavier) → `checkPreferTheirsOverOurs` passes → node stays connected and eventually adopts the canonical chain.

With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` returns `ShouldNotSwitch` (candidate has fewer blocks) → `checkPreferTheirsOverOurs` throws `CandidateTooSparse` → node disconnects from the peer.

If all honest peers are offering the Peras-boosted canonical chain, the node will persistently disconnect from all of them and remain on its current, less-secure fork. This is a chain-selection error: the node fails to adopt the canonical chain and is permanently stuck on a non-canonical fork without any operator fault.

This matches the **High** allowed impact: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- **Peras must be enabled.** The CHANGELOG notes Peras is disabled by default; the bug is dormant until Peras is activated in production. However, Peras is actively being developed for production Cardano nodes, making this a forward-looking production risk.
- **No special attacker capability required.** Any honest peer offering the canonical Peras-boosted chain triggers the bug. No key compromise, stake majority, or social engineering is needed.
- **Triggered by normal protocol operation.** The forecast horizon is routinely exceeded during initial sync and after network partitions. The bug fires on every such occurrence when the candidate is Peras-boosted but shorter in block count.
- **Persistent effect.** The node will repeatedly disconnect from peers offering the canonical chain, not just once.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` with the actual live `PerasWeightSnapshot` obtained from the ChainDB (via `getPerasWeightSnapshot`), consistent with how every other call site in `ChainSel.hs` uses the snapshot. The developers' own TODO acknowledges the check is problematic and references issue #64 for removal; until removal, the snapshot argument must be correct to avoid incorrect disconnections.

```haskell
-- Correct fix (until the check is removed per issue #64):
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        weights          -- actual PerasWeightSnapshot, not emptyPerasWeightSnapshot
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

where `weights` is read from `getPerasWeightSnapshot` (already available in the enclosing `STM` context).

### Proof of Concept

1. Enable Peras with a non-zero `perasWeight` parameter.
2. Build a two-node private testnet. Node A has a chain of length 100 with no Peras certificates. Node B has a chain of length 98 with one Peras certificate boosting its tip by weight 3 (total weight 101 > 100).
3. Node B's candidate tip is beyond Node A's forecast horizon (e.g. due to a slot gap).
4. `readLedgerStateHelper` on Node A calls `checkPreferTheirsOverOurs`.
5. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares block counts only: 100 vs 98 → `ShouldNotSwitch` → Node A throws `CandidateTooSparse` and disconnects from Node B.
6. With the actual snapshot, `preferAnchoredCandidate` compares total weights: 100 vs 101 → `ShouldSwitch` → Node A stays connected and eventually adopts Node B's chain.
7. Node A is permanently stuck on the less-secure fork.
