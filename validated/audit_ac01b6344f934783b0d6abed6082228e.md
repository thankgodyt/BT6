### Title
Unconditional Peras Certificate Acceptance in Default `BlockSupportsPeras` Instance Bypasses All Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` provides a `validatePerasCert` implementation that unconditionally returns `Right` for every certificate received from a peer, performing zero cryptographic or structural checks. Any unprivileged peer can inject arbitrary Peras certificates that are accepted as fully valid, bypassing the quorum, signature, and round-number requirements that the Peras protocol depends on for chain-selection boosting.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` (lines 350–358), the default instance that applies to every block type reads:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no round number is checked, no boosted-block reference is validated, and no quorum threshold is enforced. The function wraps any attacker-supplied `PerasCert` in a `ValidatedPerasCert` carrying the full `perasWeight`.

**Attacker-controlled entry path**

1. An unprivileged peer connects and sends a batch of `PerasCert` objects via the object-diffusion mini-protocol.
2. `processCerts` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` (lines 156–185) calls the injected `validateCert` callback on each certificate.
3. That callback resolves to `validatePerasCert` from the default instance above.
4. `validatePerasCert` returns `Right ValidatedPerasCert` unconditionally.
5. The certificate is timestamped and stored via `addCert`; it is now treated as a legitimately validated certificate for chain-selection boosting.

**Structural parallel to the external report**

The external report's `compound` function accepts attacker-controlled `callConfigs` and executes them via `delegatecall` without constraining the `callee` or `payload`. The authorization check (`msg.sender == masterSynthChef`) validates the caller identity but not the content of the inputs. Here, the peer-connection check validates the transport layer but not the content of the certificate: `validatePerasCert` is the exact analogue of the unconstrained `delegatecall` — it accepts any input and executes it in a privileged context (chain-selection boosting) without restriction.

---

### Impact Explanation

A peer that injects a crafted `PerasCert` pointing to an adversarial block causes that block to receive the full `perasWeight` boost in chain selection. Because no quorum of stake is required, a single peer can manufacture a certificate for any block at any round. This enables:

- **Unauthorized certificate acceptance**: the Peras quorum requirement — the core security property of the Peras extension — is entirely bypassed.
- **Chain-selection manipulation**: the boosted adversarial block may be preferred over the honest chain tip, causing an honest node to switch to a non-canonical fork.
- **Consensus safety failure**: if the boosted block is on a chain that diverges from the honest chain, the node accepts an invalid or adversarially-chosen chain state.

This falls squarely within the allowed impact scope: *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The entry path requires only that an attacker establish a peer connection — no keys, no stake, no privileged access. The object-diffusion protocol for Peras certificates is implemented in production source files (not test or mock libraries). The `processCerts` pipeline is wired to call `validatePerasCert` directly. The only mitigating factor is that the Peras protocol extension carries multiple `TODO` comments indicating it is still under active development; if the object-diffusion endpoint for certificates is not yet enabled in deployed `cardano-node` binaries, the attack surface is not yet exposed on mainnet. However, the code is present in production modules and will become exploitable as soon as the feature is activated.

---

### Recommendation

Replace the stub with a real implementation that:

1. Verifies the aggregate cryptographic signature over the certificate's `(roundNo, boostedBlock)` payload against the committee's aggregate verification key.
2. Checks that `pcCertRound` is within the expected window relative to the current chain tip.
3. Verifies that `pcCertBoostedBlock` refers to a block that exists on a chain the node has seen.
4. Confirms that the certificate represents a quorum of eligible stake as defined by the Peras parameters.

As an immediate defensive measure, change the default stub to reject all certificates:

```haskell
validatePerasCert _params _cert = Left PerasValidationErr
```

This is safe because the stub is explicitly labelled a placeholder; rejecting certificates by default is strictly safer than accepting them unconditionally until the real validation logic is in place.

### Proof of Concept

```
Precondition: node is running with Peras object-diffusion enabled.

1. Attacker connects to the node as a normal peer.
2. Attacker constructs PerasCert { pcCertRound = R, pcCertBoostedBlock = P }
   where P is the tip of an adversarial fork.
3. Attacker sends the certificate batch via the object-diffusion protocol.
4. processCerts calls validatePerasCert, which returns
   Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }).
5. The certificate is stored in the PerasCertDB.
6. Chain selection reads the certificate and applies perasWeight to block P.
7. If perasWeight is sufficient to make P's chain preferred, the node switches
   to the adversarial fork — accepting an invalid or non-canonical chain state
   without any quorum of honest stake having voted for it.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
