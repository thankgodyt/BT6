### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, performing no cryptographic or structural verification. The Peras certificate diffusion miniprotocol is wired up and active in the node-to-node handler, meaning any unprivileged peer can inject arbitrarily crafted `PerasCert` objects that pass "validation" and are committed to the ChainDB. Once accepted, these certificates influence chain selection by boosting the weight of the block they reference, potentially causing an honest node to prefer a non-canonical fork.

### Finding Description

**Root cause.** The only production instance of `BlockSupportsPeras` is the universal catch-all `instance StandardHash blk => BlockSupportsPeras blk`. Its `validatePerasCert` implementation is a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

Every certificate, regardless of content or cryptographic correctness, is wrapped in `Right` and returned as `ValidatedPerasCert`. [1](#0-0) 

**Reachable entry path.** The node-to-node handler wires the Peras cert diffusion inbound miniprotocol directly to `makePerasCertPoolWriterFromChainDB`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound ... (makePerasCertPoolWriterFromChainDB systemTime getChainDB) ...
``` [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` calls `validateCert` on each received certificate and, if all pass, adds them to the ChainDB via `addPerasCertAsync`: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, every certificate from every peer passes this gate unconditionally and is committed to the ChainDB.

**Contrast with the vote path.** The analogous vote diffusion handler deliberately passes `pure (PerasVoteStakeDistr mempty)` as the stake distribution, causing all peer-supplied votes to be rejected. The cert path has no equivalent defensive measure:

```haskell
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [5](#0-4) 

This asymmetry is the direct analog of the external report's pattern: the vote path enforces a check (stake distribution lookup rejects unknown voters), while the cert path skips the equivalent check entirely.

**Chain selection effect.** Once a `ValidatedPerasCert` is in the ChainDB, `chainSelectionForBlock` reads the Peras weight snapshot and uses it to compare candidate chains: [6](#0-5) 

A fraudulent certificate boosting a block on a weaker fork can make that fork preferred over the honest chain.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` referencing any block point and any round number, send it over the Peras cert diffusion miniprotocol, and have it accepted without any cryptographic or eligibility check. The accepted certificate is stored as a `ValidatedPerasCert` and contributes a weight boost to the referenced block during chain selection. This enables an adversary to manipulate chain selection on an honest node, causing it to prefer a non-canonical or adversarially controlled fork — a chain selection safety failure reachable from the network without any privileged access.

**Impact: High** — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

### Likelihood Explanation

The Peras cert diffusion miniprotocol is fully wired up and active in the node-to-node handler. Any connected peer can send crafted certificates. No keys, stake, or special privileges are required. The attacker only needs a TCP connection to the target node.

**Likelihood: High** — zero-privilege network-reachable exploit with no preconditions beyond peer connectivity.

### Recommendation

Until a real `validatePerasCert` implementation is in place, apply the same defensive measure used for votes: reject all externally received certificates at the diffusion layer (e.g., by returning `Left PerasValidationErr` unconditionally in the stub, or by gating the cert diffusion handler behind a feature flag that is disabled until the full validation logic is implemented). The stub should never silently accept all inputs in a live network-facing code path.

### Proof of Concept

1. Connect to a running node as a peer via the node-to-node protocol.
2. Send a `PerasCert` message over the Peras cert diffusion miniprotocol referencing any `Point blk` (e.g., a block on a weaker fork) and any `PerasRoundNo`.
3. Observe that `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
4. The certificate is passed to `addPerasCertAsync` and committed to the ChainDB.
5. The next chain selection run reads the Peras weight snapshot, finds the fraudulent boost, and may switch the node's selection to the boosted fork.

The stub at [1](#0-0)  is the necessary vulnerable step; without it, the certificate would be rejected before reaching the ChainDB.
