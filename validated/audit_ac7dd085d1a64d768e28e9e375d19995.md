### Title
`request_refund` Accepts Unvalidated `refund_address` at Submission Time, Enabling Attacker-Triggered Stuck Refund State - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`request_refund` is publicly callable and stores an arbitrary `refund_address` string without validating it is a legitimate BTC/ZEC address for the configured chain. Validation only occurs later inside `execute_refund` → `build_refund_output`, where a panic terminates execution. Because only one refund request is permitted per UTXO, an attacker who races to submit a request with an invalid address permanently blocks the legitimate user's refund path until a DAO/Operator manually rejects the malicious request.

---

### Finding Description

`request_refund` is publicly callable (no `#[trusted_relayer]` attribute on the function itself, only on the impl block for configuration purposes): [1](#0-0) 

Inside `internal_request_refund`, the `refund_address` is forwarded to the callback without any address-format check: [2](#0-1) 

In `request_refund_callback`, the callback verifies the BTC transaction and deposit script, but stores `refund_address` verbatim with no validation: [3](#0-2) 

The only validation of `refund_address` occurs much later, inside `build_refund_output`, called from `execute_refund`: [4](#0-3) 

If `Address::parse` fails, the call panics and `finalize_refund_with_psbt` is never reached, so the UTXO is **not** marked verified and the `RefundRequest` remains in storage with `executed = false`.

The duplicate-request guard in `request_refund_callback` enforces that only one refund request can exist per UTXO: [5](#0-4) 

There is also no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`, so any NEAR account can submit a refund request for any deposit.

---

### Impact Explanation

An attacker who observes an unfinalized BTC deposit on-chain can:

1. Call `request_refund` with the real `deposit_msg` and `tx_bytes` but supply a syntactically invalid `refund_address` (e.g., an empty string or a garbage value).
2. The light-client proof passes; the request is stored.
3. Every subsequent call to `execute_refund` panics at `build_refund_output`, leaving the refund permanently stuck.
4. The legitimate depositor cannot submit their own refund request because the duplicate guard rejects it.
5. The depositor is forced to either finalize the deposit via `verify_deposit` (which they may not want, e.g., the deposit was accidental or the recipient account is wrong) or wait for a DAO/Operator to call `reject_refund`.

This is a **stuck bridge state requiring operator intervention** and **attacker-triggered temporary locking of bridged funds** — both Medium-severity impacts in the allowed scope.

---

### Likelihood Explanation

- `request_refund` is publicly callable by any NEAR account.
- Unfinalized BTC deposits are visible on-chain; an attacker can monitor for them.
- The attacker must pay the storage deposit (`required_balance_for_request_refund`), which is a small NEAR amount — a low economic barrier.
- The attack is race-condition-based (attacker must submit before the legitimate user), but the window is large (deposits can remain unfinalized indefinitely).
- Likelihood: **Low-Medium**.

---

### Recommendation

Validate `refund_address` against the configured chain inside `request_refund_callback` (or `internal_request_refund`) before storing the `RefundRequest`, mirroring the validation already present in `build_refund_output`:

```rust
// In request_refund_callback, before inserting the RefundRequest:
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

Additionally, consider requiring that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` for the permissionless (non-DAO/Operator) path, or at minimum enforcing the `unsafe_refund_timelock_sec` path for all third-party submissions.

---

### Proof of Concept

1. Alice sends 0.01 BTC to the bridge deposit address derived from `DepositMsg { recipient_id: "alice.near", ... }`.
2. The deposit is confirmed on-chain but `verify_deposit` has not been called yet.
3. Attacker Bob calls:
   ```
   request_refund(
     deposit_msg = <Alice's real DepositMsg>,
     refund_address = "INVALID_ADDRESS_XYZ",
     tx_bytes = <real tx bytes>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None,
   )
   ```
   with the required storage deposit attached.
4. Light-client verification passes; `request_refund_callback` stores the `RefundRequest` with `refund_address = "INVALID_ADDRESS_XYZ"`.
5. Alice tries to call `request_refund` with her own valid address → panics: `"Refund request already exists for this UTXO"`.
6. Anyone calls `execute_refund(utxo_storage_key, None)` → panics at `build_refund_output`: `"Invalid refund address"`.
7. Alice's refund is stuck until DAO calls `reject_refund`, requiring operator intervention. [6](#0-5) [7](#0-6)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
