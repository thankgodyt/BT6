### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate Without Cryptographic Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, and a stub `validatePerasVote` that checks only stake-distribution membership while skipping all cryptographic (signature) verification. Both stubs are wired directly into the live peer-facing object-diffusion mini-protocol handlers (`processCerts` / `processVotes`). An unprivileged peer can therefore inject arbitrarily crafted Peras certificates and votes that will be accepted, stored, and used to influence chain selection without any cryptographic check ever being performed.

---

### Finding Description

`BlockSupportsPeras` defines two validation entry points:

```haskell
validatePerasCert :: PerasCfg blk -> PerasCert blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote :: PerasCfg blk -> PerasVoteStakeDistr -> PerasVote blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The universal instance (covering all block types) implements them as stubs:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
  | otherwise = Left PerasValidationErr
```

`validatePerasCert` **always** returns `Right` — no round-number range check, no quorum check, no aggregate-signature verification, no check that the boosted block point is plausible. `validatePerasVote` performs only a stake-distribution membership lookup; it never verifies the vote's cryptographic signature.

These stubs are the concrete validators passed to the live inbound-processing pipeline:

- `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` to `processCerts`.
- `makePerasVotePoolWriterFromChainDB` passes `validatePerasVote mkPerasParams sd` to `processVotes`.

`processCerts` / `processVotes` call the validator on every new object received from a peer and, if it returns `Right`, immediately persist it to the `PerasCertDB` / `PerasVoteDB` and (for the ChainDB variant) trigger asynchronous chain-selection side-effects. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

**Certificate path (critical):** `validatePerasCert` returns `Right` unconditionally. A peer can send a `PerasCert` naming any `Point blk` as `pcCertBoostedBlock`. The certificate is stored and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection. Because Peras certificates carry a configurable `perasWeight` boost, a fake certificate can make the node prefer a non-canonical or adversary-controlled chain over the honest chain, constituting a chain-selection safety failure.

**Vote path (high):** `validatePerasVote` skips signature verification entirely. Any peer knowing a valid voter ID (which is public, derived from the stake distribution) can forge votes for that voter targeting any block. Forged votes accumulate toward quorum; once quorum is reached, `forgePerasCert` is called and the resulting certificate is injected into chain selection — again without any cryptographic proof that the named voters actually cast those votes.

Both paths match the allowed impact scope: *"Bypass of … certificate/vote … checks … that enables unauthorized … vote, or certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical … chain."* [4](#0-3) [5](#0-4) 

---

### Likelihood Explanation

The object-diffusion mini-protocol handlers are reachable by any peer that connects to the node. No special privilege, key material, or stake is required to send a `PerasCert` or `PerasVote` message. The only gating is that the `pvVoteVoterId` in a forged vote must appear in the current stake distribution — a fully public data structure. The stub implementations are wired into the production `ChainDB`-backed pool writers (not only test paths), and the TODO comments confirm the stubs are intentionally left in place pending future work, meaning the code is live and callable today whenever Peras diffusion is active. [6](#0-5) 

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation before the Peras diffusion layer is enabled in any network. At minimum this must include: verifying the aggregate BLS signature over the claimed voter set against the committee's public keys, checking that `pcCertRound` falls within the current valid window, and confirming that `pcCertBoostedBlock` refers to a block that is plausibly on the chain.

2. **`validatePerasVote`**: Add cryptographic signature verification (e.g., via `verifyVoteSignature` already present in `CryptoSupportsVoteSigning`) before accepting a vote. Stake-distribution membership is a necessary but not sufficient condition.

3. **Guard the diffusion layer**: Until real validation is in place, the Peras object-diffusion mini-protocol should not be enabled on any network where the stub instance is the active implementation. [7](#0-6)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
