### Title
Peras Certificate Validation Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or committee-eligibility checks. Because this function is the sole validation gate in the inbound certificate pipeline (`processCerts` → `ChainDB.addPerasCertAsync` → `chainSelectionForBlock`), any unprivileged peer can inject an arbitrary `PerasCert` that will be accepted as `ValidatedPerasCert` and applied as a weight boost of `PerasWeight 15` to any block in the VolatileDB, directly manipulating chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory cryptographic gate before a certificate may influence consensus. The only live instance of this class is the universal degenerate instance declared at line 320:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its `validatePerasCert` body is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, committee membership, round eligibility, or boosted-block validity check is performed. Every `PerasCert` — regardless of content — is wrapped in `ValidatedPerasCert` and returned as `Right`.

The inbound network path that feeds this function is `makePerasCertPoolWriterFromChainDB`, which is the production writer used by the object-diffusion mini-protocol:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, forwards them to `addCert`: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every peer-supplied certificate is forwarded to `ChainDB.addPerasCertAsync`.

`chainSelSync` then processes the certificate: it adds it to `PerasCertDB` and, if the boosted block is present in the VolatileDB, immediately triggers `chainSelectionForBlock` for that block: [4](#0-3) 

Chain selection uses the `PerasWeightSnapshot` to compare candidate fragments. A certificate accepted via this path contributes `PerasWeight 15` (the value of `perasWeight mkPerasParams`) to the boosted block's weight: [5](#0-4) 

The analog to the Open Dollar bug is exact: just as `SAFEEngine.modifySAFECollateralization()` could be called directly to bypass the `ODSafeManager` tax-collector gate, here the "validation gate" (`validatePerasCert`) is structurally present but functionally absent — it never rejects anything, so the downstream chain-selection machinery operates on unverified, attacker-controlled input.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block hash it knows is in the target node's VolatileDB (learnable via ChainSync). The certificate will pass "validation" and be stored in `PerasCertDB`. Chain selection will then re-evaluate the boosted block with an additional weight of 15, which is equivalent to 15 extra blocks of chain length in the Peras comparison. This can cause the honest node to switch to or retain a non-canonical fork that it would otherwise have rejected, constituting a **chain-selection safety failure driven by unauthorized certificate acceptance**. The weight boost is permanent for the lifetime of the certificate in the DB and affects all subsequent chain-selection runs involving that block.

---

### Likelihood Explanation

The entry path is the standard object-diffusion mini-protocol, reachable by any peer that connects to the node. No special keys, stake, or privileges are required. The attacker only needs to know a block hash present in the target's VolatileDB (trivially obtained from ChainSync headers). The degenerate instance is the only live instance for all block types, so there is no era or configuration in which real validation is performed.

---

### Recommendation

Replace the stub `validatePerasCert` body with a real implementation that verifies:
1. The certificate's aggregate BLS signature against the claimed committee members' public keys.
2. That the signers were eligible committee members for the claimed round (VRF-based sortition check).
3. That the aggregate stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold`).
4. That `pcCertBoostedBlock` refers to a block that satisfies `perasBlockMinSlots` age.

Until the full cryptographic plumbing is in place, the inbound certificate handler should refuse all externally received certificates rather than accepting them unconditionally. The `makePerasCertPoolWriterFromChainDB` function should not be wired to the live network until `validatePerasCert` performs real validation. [6](#0-5)

### Proof of Concept

```
Attacker (peer) connects to honest node N via the object-diffusion mini-protocol.

1. Attacker learns block hash H of a block on a minority fork F
   (e.g., by observing ChainSync headers from N or another peer).

2. Attacker constructs:
     cert = PerasCert
       { pcCertRound    = <any round number not yet in N's PerasCertDB>
       , pcCertBoostedBlock = BlockPoint <slot> H
       }
   No valid BLS signature, no committee proof — the struct is fabricated.

3. Attacker sends [cert] to N via the Peras certificate object-diffusion
   mini-protocol.

4. N's makePerasCertPoolWriterFromChainDB calls:
     processCerts ... (validatePerasCert mkPerasParams) ... [cert]
   validatePerasCert returns Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}
   unconditionally.

5. processCerts forwards the "validated" cert to ChainDB.addPerasCertAsync.

6. chainSelSync adds the cert to PerasCertDB and calls
   chainSelectionForBlock for block H.

7. Chain selection now sees block H with PerasWeight 15 extra weight.
   If fork F was previously disfavoured by ≤15 blocks of chain length,
   N now switches to F, diverging from the canonical chain.
```

The `validatePerasCert` stub is the necessary vulnerable step: without it always returning `Right`, the fabricated certificate would be rejected at step 4 and never reach chain selection. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
