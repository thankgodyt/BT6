### Title
Reentrancy in `initTransfer` Causes Duplicate `originNonce` Emission, Permanently Locking Bridged Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

### Summary
`OmniBridge.initTransfer` increments `currentOriginNonce` at the top of the function but reads it again from storage when calling `initTransferExtension` and emitting `InitTransfer`. Because no reentrancy guard is present, a malicious ERC20 token (or ERC777 token) can reenter `initTransfer` during the `safeTransferFrom` / `burn` external call, increment `currentOriginNonce` a second time, and cause both the reentrant call and the original call to emit `InitTransfer` with the **same** nonce. The NEAR side treats the first event it finalizes as authoritative and marks that nonce used; the second event is silently discarded, permanently locking the corresponding EVM-side tokens with no NEAR-side release.

### Finding Description

`initTransfer` follows this sequence:

```
currentOriginNonce += 1;          // (1) nonce written to storage as N
...
safeTransferFrom / burn / ...     // (2) external call — reentrancy window
...
initTransferExtension(..., currentOriginNonce, ...);  // (3) reads storage → may be N+1
emit InitTransfer(..., currentOriginNonce, ...);       // (4) reads storage → may be N+1
``` [1](#0-0) 

`currentOriginNonce` is a `uint64` storage variable read at steps (3) and (4), not a local snapshot taken at step (1). If a reentrant call executes between steps (1) and (3), it increments `currentOriginNonce` to N+1, completes its own `emit InitTransfer(..., N+1, ...)`, and returns. The original call then also reads N+1 from storage and emits `InitTransfer(..., N+1, ...)` — a duplicate nonce — while nonce N is never emitted. [2](#0-1) 

No `nonReentrant` modifier is present on `initTransfer` or `initTransfer1155`. [3](#0-2) 

The `OmniBridgeWormhole` variant compounds this: `initTransferExtension` calls `_wormhole.publishMessage` (another external call) before incrementing `wormholeNonce`, creating a second reentrancy window inside the same transaction. [4](#0-3) 

The project's own security invariant states: *"Every `originNonce` is incremented atomically. A nonce must never be reusable"* and *"`InitTransfer` must only be emitted in a code path where tokens have already been burned/locked."* [5](#0-4) 

Both invariants are violated by this reentrancy path.

### Impact Explanation

**Concrete loss-of-funds scenario:**

1. Attacker deploys malicious token `M` whose `transferFrom` implementation re-enters `initTransfer(M, amount, ...)` once before returning.
2. Attacker calls `initTransfer(M, amount, recipient_near, ...)`.
   - `currentOriginNonce` → N.
   - `safeTransferFrom` triggers the hook → reentrant `initTransfer(M, amount, recipient_near, ...)` executes:
     - `currentOriginNonce` → N+1.
     - Reentrant call emits `InitTransfer(attacker, M, N+1, amount, ...)`.
   - Original call resumes; reads `currentOriginNonce` = N+1.
   - Original call emits `InitTransfer(attacker, M, N+1, amount, ...)` — **same nonce**.
3. NEAR side observes two `InitTransfer` events both carrying nonce N+1. It finalizes the first and marks N+1 used. The second is rejected as a replay.
4. Nonce N is never emitted. Any tokens locked/burned under nonce N have no corresponding NEAR-side release — **permanently lost**.

If `M` is a registered bridge token on NEAR (bridge-deployed, mint/burn model), the NEAR side mints tokens for the attacker based on the first event while the EVM-side burn for the second event is unmatched, breaking the token supply invariant across chains.

The same window exists for any ERC-777 token or token with a `transferFrom` callback registered with the bridge, without the attacker needing to deploy a custom token.

### Likelihood Explanation

- `initTransfer` is a fully public, permissionless entry point callable by any EVM address.
- The bridge explicitly supports custom tokens via `ICustomMinter` and arbitrary ERC-20 `tokenAddress` values; no whitelist prevents a malicious token from being passed.
- ERC-777 tokens (which have mandatory send/receive hooks) are deployed on all supported EVM chains (Ethereum, Arbitrum, Base, Polygon, BNB).
- The attacker controls the token contract and can craft the exact reentrancy depth and parameters needed.
- No reentrancy guard, no local nonce snapshot, and no CEI-compliant event emission exist to prevent this.

### Recommendation

Cache `currentOriginNonce` in a local variable immediately after the increment and use only the local variable in all subsequent reads within the same call:

```solidity
function initTransfer(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    uint64 nonce = ++currentOriginNonce;   // local snapshot
    ...
    // external calls (burn / transferFrom / customMinter)
    ...
    initTransferExtension(msg.sender, tokenAddress, nonce, ...);
    emit BridgeTypes.InitTransfer(msg.sender, tokenAddress, nonce, ...);
}
```

Apply the same fix to `initTransfer1155`. Additionally, add OpenZeppelin's `ReentrancyGuard` (`nonReentrant`) to both `initTransfer` and `initTransfer1155` as defense-in-depth, consistent with the project's stated invariant that nonces must be atomically assigned.

    IOmniBridge bridge;
    bool entered;

        if (!entered) {
            entered = true;

        return true;

**File:** evm/CLAUDE.md (L32-36)
```markdown
- **No replay attacks**: Every `destinationNonce` must be checked against `completedTransfers` and marked used before any token transfer. Every `originNonce` is incremented atomically. A nonce must never be reusable
- **Event completeness**: `InitTransfer` and `FinTransfer` events must contain every field needed to reconstruct the transfer. The NEAR side relies solely on these events — any missing or ambiguous field means lost funds or spoofable transfers. Fields must not be collapsible (e.g. two different transfers must never produce the same event data)
- **State before external calls**: Always mutate state (e.g. mark nonce used) before any external call (token transfer, ETH send, custom minter). This is the primary reentrancy defense
- **No token release without signature**: Never mint, transfer, or unlock tokens to a recipient without first verifying a valid MPC signature. No admin function, emergency path, or refactor may bypass this — it is the only authorization gate for finTransfer
- **Event–transfer atomicity**: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held
```
