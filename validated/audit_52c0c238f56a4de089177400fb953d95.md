### Title
Stub `validatePerasCert` Allows Any Peer to Trigger Chain Switch to a Shorter Fork via Crafted PerasCert — (`Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance unconditionally accepts every inbound `PerasCert` (stub `validatePerasCert`). Because the cert diffusion path is fully wired into production chain selection, an unprivileged peer can send a cert whose `pcBoostedBlock` points to any block already in the VolatileDB, causing `chainSelSync` → `chainSelectionForBlock` → `constructPreferableCandidates` → `preferAnchoredCandidate` to prefer a shorter fork whose `blockNo + perasWeight` exceeds the honest chain's `blockNo`, switching the node away from the honest chain.

---

### Finding Description

**1. Stub always accepts every cert** [1](#0-0) 

The `validatePerasCert` implementation for the universal instance (the only instance in the codebase) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature check, no committee membership check, no round-number check, no boosted-block plausibility check. Every cert from every peer passes.

**2. Cert diffusion path is wired to production chain selection**

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with the stub validator, then calls `ChainDB.addPerasCertAsync` for every cert that passes: [2](#0-1) 

**3. `chainSelSync` processes the cert and triggers chain selection for the boosted block** [3](#0-2) 

The only guards are:
- `pointSlot boostedBlock < AF.anchorToSlotNo immTip` → ignored if too old (slot-based, not block-number-based)
- `AF.withinFragmentBounds (castPoint boostedBlock) curChain` → exits early only if the boosted block is already on the current chain
- `VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash` → exits early only if the block is not yet in the VolatileDB

If the boosted block IS in the VolatileDB on a fork, `chainSelectionForBlock` is called unconditionally.

**4. Chain selection uses `blockNo + perasWeight` as the comparison metric** [4](#0-3) 

`wsvTotalWeight wsv = PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv`

`preferCandidate` switches when `wsvTotalWeight cand > wsvTotalWeight ours`. The cert boost is added to the VolatileDB weight snapshot immediately before `chainSelectionForBlock` is called (line 495 adds the cert to `cdbPerasCertDB`, which is read at line 634 inside `chainSelectionForBlock`). [5](#0-4) 

**5. The `rollbackExceedsSuffix` filter does not enforce the security parameter k** [6](#0-5) 

`rollbackExceedsSuffix` only filters out candidates where the weight of what is rolled back exceeds the weight of the new suffix — it is a weight-balance filter, not a k-rollback-depth filter. The k-depth limit is enforced implicitly by the VolatileDB/ImmutableDB split (the current chain is at most k blocks), but within that window a cert-boosted 1-block fork can beat a 10-block honest chain if `1 + perasWeight > 10`.

---

### Impact Explanation

An unprivileged peer sends a `PerasCert` with `pcBoostedBlock` pointing to a 1-block fork tip already in the VolatileDB. The stub validator accepts it. The cert boost (`perasWeight params`) is added to the weight snapshot. `preferAnchoredCandidate` computes `1 + perasWeight` for the fork vs `N + 0` for the honest chain. If `perasWeight > N - 1`, the node switches to the shorter fork, rolling back up to `N` honest blocks. This breaks the common-prefix property: the node's selection diverges from the honest chain without any cryptographic justification.

Impact scope: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.**

---

### Likelihood Explanation

- The cert diffusion miniprotocol is fully wired in production code.
- The stub is the only `BlockSupportsPeras` instance; it applies to all block types.
- No cryptographic material is required from the attacker — only a valid CBOR-encoded `PerasCert` with a `pcBoostedBlock` hash matching a block already in the VolatileDB.
- The attacker can learn which blocks are in the VolatileDB via ChainSync headers.
- The attack is repeatable: after the node switches, the attacker can send another cert to switch it again.

---

### Recommendation

1. **Do not deploy the cert diffusion path to production nodes until `validatePerasCert` performs real cryptographic validation** (committee membership, quorum signatures, round-number bounds, boosted-block plausibility).
2. Gate the `makePerasCertPoolWriterFromChainDB` path behind a feature flag that is disabled until issue [#120](https://github.com/tweag/cardano-peras/issues/120) and [#73](https://github.com/tweag/cardano-peras/issues/73) are resolved.
3. Add a property-based test asserting that a node receiving a cert boosting a fork block does NOT switch when the cert fails cryptographic validation.

---

### Proof of Concept

```
io-sim cluster test (unmodified code):
1. Start a node with honest chain of length N (N > 1).
2. Inject a 1-block fork block into the node's VolatileDB via BlockFetch.
3. Have a peer send a PerasCert { pcCertRound = 1, pcCertBoostedBlock = forkBlockPoint }.
4. Wait for addPerasCertAsync → chainSelSync to complete.
5. Assert: if perasWeight > N - 1, the node's current chain tip is the fork block.
   (This assertion PASSES, demonstrating the switch.)
6. Assert: the node's current chain tip is NOT the fork block.
   (This assertion FAILS, confirming the vulnerability.)
```

The stub at [7](#0-6)  is the root cause. The chain selection logic at [8](#0-7)  correctly implements Peras semantics but relies on the validator to have already rejected illegitimate certs — which the stub never does.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

-- | Return 'True' iff applying the 'ChainDiff' to the given chain @C@ will
-- result in a chain with less weight than @C@, i.e., the suffix of @C@ to roll
-- back has more weight than suffix is adding.
rollbackExceedsSuffix ::
  forall b0 b1 b2.
  ( HasHeader b0
  , HasHeader b1
  , HasHeader b2
  , HeaderHash b0 ~ HeaderHash b1
  , HeaderHash b0 ~ HeaderHash b2
  ) =>
  PerasWeightSnapshot b0 ->
  -- | The chain @C@ the diff is applied to.
  AnchoredFragment b1 ->
  ChainDiff b2 ->
  Bool
rollbackExceedsSuffix weights curChain (ChainDiff nbRollback suffix) =
  weightOf suffixToRollBack > weightOf suffix
 where
  suffixToRollBack = AF.anchorNewest nbRollback curChain

  weightOf ::
    (HasHeader b, HeaderHash b ~ HeaderHash b0) =>
    AnchoredFragment b -> PerasWeight
  weightOf = totalWeightOfFragment weights
