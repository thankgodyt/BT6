### Title
Hardcoded All-Zeroes `BRIDGE_OVK` Cannot Be Rotated Without Contract Redeployment — (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary
The Zcash Orchard deposit path hardcodes the bridge's Outgoing Viewing Key (OVK) to 32 zero bytes at compile time. Because this constant is baked into the WASM binary, it cannot be updated without a full contract redeployment. The all-zeroes value is also publicly known to every observer of the source code, meaning any party can construct an Orchard bundle that the bridge will successfully decrypt with this key.

### Finding Description
`BRIDGE_OVK` is declared as a Rust `const` in the production Zcash utility module:

```rust
// contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs, line 11
pub const BRIDGE_OVK: [u8; 32] = [0u8; 32];
```

The comment on line 10 explicitly acknowledges the limitation: *"Hardcoded to all zeroes for now; can be made configurable later."*

This constant is consumed directly in `extract_orchard_bundle` to decrypt every incoming Orchard deposit bundle:

```rust
// orchard_policy.rs lines 58-61
let ovk = orchard::keys::OutgoingViewingKey::from(BRIDGE_OVK);
let (note, addr, _memo) = bundle
    .recover_output_with_ovk(0, &ovk)
    .ok_or_else(|| "Failed to recover Orchard output with bridge OVK".to_string())?;
```

`recover_output_with_ovk` uses the OVK to derive the outgoing cipher key (`ock`) and decrypt the encrypted note inside the Orchard action. Because the OVK is all zeroes and is a public constant, any external party can:

1. Derive the same `ock` for any Orchard action.
2. Construct a well-formed Orchard bundle whose encrypted note decrypts successfully under this key, with attacker-chosen `(note.value, recipient_addr)` fields.

The bridge has no on-chain mechanism to rotate the OVK; the only remediation path is redeployment.

### Impact Explanation
**Low — publicly reachable invariant-violation in the production Zcash bridge path without direct theft.**

- The OVK is the sole cryptographic gate the bridge uses to authenticate that an Orchard output was legitimately addressed to it. With a publicly known all-zeroes OVK, the bridge cannot distinguish a genuine depositor-constructed bundle from one crafted by a third party.
- `validate_orchard_bundle` does cross-check the recovered recipient address and value balance against the withdrawal target and transparent outputs, which limits immediate fund theft. However, the integrity of those checks depends entirely on the Orchard bundle bytes being bound to the on-chain transaction — a binding that is not enforced within the code examined.
- If the OVK ever needs to change (e.g., due to a cryptographic weakness discovered in the all-zeroes derivation path, or an operational key-rotation policy), the bridge is permanently stuck on the current value until a full redeployment is executed, which constitutes a stuck bridge state requiring operator intervention.

### Likelihood Explanation
**Low.** The all-zeroes OVK is a known, documented design choice. Exploitation of the weak-key property requires constructing a valid Zcash v5 transaction with a crafted Orchard bundle and getting it confirmed on-chain, which has a non-trivial cost. However, the inability to rotate the key without redeployment is a permanent, unconditional constraint that applies from the moment the contract is deployed.

### Recommendation
Move `BRIDGE_OVK` from a compile-time `const` to a configurable field stored in the on-chain `Config` struct (analogous to `chain_signatures_root_public_key` or `change_address`), protected by the `Role::DAO` access-control gate. This allows the key to be rotated via a governance transaction without redeployment. Additionally, derive the OVK from a secret held by the MPC/chain-signatures service rather than using the all-zeroes value, so that the key is not publicly reconstructible.

### Proof of Concept

1. Observe that `BRIDGE_OVK = [0u8; 32]` is a public constant in the deployed WASM binary.
2. Using the Orchard SDK, construct a v5 Zcash transaction whose single Orchard action encrypts a note under `OutgoingViewingKey::from([0u8; 32])` with an arbitrary `(value, recipient)` pair.
3. Broadcast the transaction to the Zcash network and obtain a Merkle inclusion proof.
4. Call `verify_deposit` on the bridge, supplying the proof and the crafted `orchard_bundle_bytes`.
5. `extract_orchard_bundle` calls `recover_output_with_ovk(0, &ovk)` with the all-zeroes OVK; because the bundle was encrypted with that same key, recovery succeeds and returns the attacker-chosen `(value, addr)`.
6. `validate_orchard_bundle` then checks the recovered recipient and value balance against the transparent outputs — the only remaining guard. If those checks pass (or if the bundle bytes are not bound to the on-chain transaction body), the bridge proceeds to mint nZEC based on the attacker-supplied amount. [1](#0-0) [2](#0-1) [3](#0-2)
