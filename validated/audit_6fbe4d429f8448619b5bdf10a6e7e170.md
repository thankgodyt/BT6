### Title
Incorrect `boundX` Constant in Peras Local Sortition Taylor-Series Comparison Causes Wrong Non-Persistent Seat Counts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` passes the hardcoded constant `3` as the `boundX` (error-bound multiplier) to `taylorExpCmpFirstNonLower`. The function's own contract states `boundX` **must** equal `e^{|x|}` for correct error bounds. Here `x = -lambda`, so the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the constant `3` underestimates the true error bound, causing the Taylor-series comparison to terminate prematurely with an incorrect result. This produces wrong non-persistent seat counts, which are used directly in vote and certificate verification.

---

### Finding Description

`localSortitionNumSeats` computes how many Peras voting-committee seats a non-persistent voter is granted via local sortition. The Poisson-CDF comparison is performed by `taylorExpCmpFirstNonLower`:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; must be e^{|x|} = e^lambda
      orders
      (-lambda)
``` [1](#0-0) 

The function's own documentation is explicit:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

The error term is computed as:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX = 3 < e^lambda`, `errorTerm` is underestimated. The early-exit conditions:

```haskell
| cmp >= acc' + errorTerm = Stop   -- declares cmp ABOVE e^x
| cmp < acc' - errorTerm = Below   -- declares cmp BELOW e^x
``` [4](#0-3) 

…can fire incorrectly when the VRF output is near a Poisson-CDF threshold, returning a seat count that is one too high or one too low.

`lambda` is:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [5](#0-4) 

With a committee of 10 non-persistent voters and a voter holding 15 % of non-persistent stake, `lambda = 1.5` and `e^lambda ≈ 4.48`, already 49 % larger than `3`. With 20 % stake, `lambda = 2.0` and `e^lambda ≈ 7.39`, underestimating the error bound by a factor of ~2.46.

The codebase itself acknowledges the uncertainty via a TODO:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
``` [6](#0-5) 

In `checkLeaderNatValue` (ledger), `x = -sigma * ln(1-f)` with `sigma ≤ 1` and `f ≈ 0.05`, giving `|x| ≤ 0.051` and `e^|x| ≤ 1.052`; `3` is a safe **over**estimate there. In `localSortitionNumSeats`, `lambda` can far exceed `ln(3)`, making `3` a dangerous **under**estimate.

---

### Impact Explanation

The wrong seat count propagates into three security-critical paths:

**1. `implVerifyVote`** — verifies a vote received over the network:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure $ WFALSNonPersistentMember ...
``` [7](#0-6) 

If the correct seat count is 0 but the buggy computation returns 1, an ineligible voter's vote is accepted.

**2. `implVerifyCert`** — verifies a Peras certificate received over the network:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure ( WFALSNonPersistentMember ... )
``` [8](#0-7) 

**3. `implEligiblePartyVoteWeight`** — inflated seat count directly inflates vote weight:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [9](#0-8) 

Peras certificates boost blocks in chain selection. Accepting a certificate with ineligible voters or inflated vote weights can cause an honest node to boost a block it should not, weakening the security guarantees of the Peras protocol and potentially causing divergent chain selection.

**Impact class:** High — Bypass of Peras certificate/vote verification that enables unauthorized vote or certificate acceptance, weakening chain-selection security beyond intended assumptions.

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is met whenever:

```
numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.099
```

With a committee of 10 non-persistent voters (a plausible production parameter), any voter holding more than ~11 % of non-persistent stake triggers the bug. This is a routine scenario in a moderately concentrated stake distribution. The bug is deterministic: for a given `lambda` and VRF output, the wrong result is always produced when the VRF output falls within the inflated error band near a Poisson-CDF threshold.

---

### Recommendation

Replace the hardcoded `3` with the correct `e^lambda`:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp (realToFrac lambda))   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

This matches the contract stated in the function's own documentation and mirrors how `checkLeaderNatValue` in the ledger correctly uses `e^|x|` as its bound.

---

### Proof of Concept

**Setup:** 10 non-persistent voters; target voter holds 20 % of non-persistent stake.

```
lambda = 10 * 0.20 = 2.0
e^lambda = e^2.0 ≈ 7.389
boundX used = 3
```

**Effect on error term** (after, say, 5 Taylor terms where `err' ≈ x^5/5! = (-2)^5/120 ≈ -0.267`):

```
errorTerm (correct) = |err'| * 7.389 ≈ 1.97
errorTerm (buggy)   = |err'| * 3     ≈ 0.80
```

The buggy error band is 2.46× too narrow. A VRF output `cmp` satisfying:

```
acc' + 0.80 <= cmp < acc' + 1.97
```

will be declared ABOVE (Stop → seat granted) by the buggy code but would correctly require more Taylor terms to resolve. If the true `e^(-lambda)` is actually above `cmp`, the voter is incorrectly denied a seat; if below, the voter is incorrectly granted one. An attacker whose VRF output lands in this band (width ≈ 1.17 in fixed-point units) for the 0-seat threshold receives 1 seat and has their vote accepted by `implVerifyVote` and `implVerifyCert` on every honest node in the network.
