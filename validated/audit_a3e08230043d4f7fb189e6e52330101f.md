Let me look at the exact `execute_refund` public entrypoint and the `resolve_execute_refund_timelock` to confirm the full call chain, and also check whether `btc_pending_sign_ids` is decremented when a withdrawal moves to pending-verify state.

The code path is fully confirmed. Here is the complete analysis:

---

### Title
Withdrawal `BTCPendingInfo` Blocks Independent Refund Execution via Shared `pending_sign_count` — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

`finalize_refund_with_psbt` calls `require_pending_sign_capacity` against the **caller's** account. Because `pending_sign_count()` counts all entries in `btc_pending_sign_ids` regardless of type (withdrawal, refund, active UTXO management), a user who already has one withdrawal in the pending-sign stage will hit the default limit of 1 and have their `execute_refund` call panic with `"Too many pending sign transactions"`. The refund is then stuck until the relayer signs the withdrawal or an operator manually raises the per-account limit.

---

### Finding Description

**Entrypoint** — `execute_refund` is a public, unpermissioned call: [1](#0-0) 

It calls `internal_execute_refund`, which on Bitcoin captures `caller = env::predecessor_account_id()` and immediately calls `finalize_refund_with_psbt`: [2](#0-1) 

Inside `finalize_refund_with_psbt`, after optionally creating the account, the capacity guard fires: [3](#0-2) 

`require_pending_sign_capacity` checks `pending_sign_count() < get_max_pending_sign_txs()`: [4](#0-3) 

`pending_sign_count()` is simply the length of `btc_pending_sign_ids`, a single `HashSet` that holds **all** pending-sign IDs regardless of whether they are withdrawals, refunds, or active UTXO management operations: [5](#0-4) 

The default limit is **1**: [6](#0-5) 

When a withdrawal is created, its ID is inserted into `btc_pending_sign_ids`: [7](#0-6) 

It stays there until **all inputs are signed** (i.e., `sign_btc_transaction_callback` completes all signatures), at which point it is removed and moved to `btc_pending_verify_list`: [8](#0-7) 

So during the entire pending-sign phase of a withdrawal, `pending_sign_count() == 1 == limit`, and any call to `execute_refund` by the same account panics.

**The operator escape hatch (`cancel_withdraw`) is also blocked.** `cancel_withdraw` creates a new RBF transaction and also calls `require_pending_sign_capacity` for the user's account: [9](#0-8) 

With `pending_sign_count == 1 == limit`, this call also panics. The operator cannot cancel the withdrawal to free capacity without first calling `set_pending_tx_limit` to raise the per-account limit.

The test suite itself acknowledges this interaction: `test_refund_execute_twice_same_tx` explicitly raises the limit to 2 with the comment *"Allow two pending refund txs so the second call is not blocked by capacity"*: [10](#0-9) 

---

### Impact Explanation

A user who has an active withdrawal (pending-sign stage) and a separate deposit that needs to be refunded cannot execute the refund. The refund UTXO is locked until either:
1. The relayer signs all inputs of the withdrawal (moves it out of `btc_pending_sign_ids`), or
2. An operator calls `set_pending_tx_limit` to raise the account's limit, then optionally cancels the withdrawal.

This is a temporary but operator-dependent lock on the user's refund path — matching the Medium impact: *"attacker-triggered temporary locking of bridged funds requiring operator intervention."*

---

### Likelihood Explanation

The scenario is realistic: a user initiates a withdrawal, then separately discovers a deposit that was never processed and needs a refund. The default limit of 1 makes this trivially reproducible with no special conditions. No privileged access is required to reach the failing state.

---

### Recommendation

Decouple the capacity guard for refunds from the shared `btc_pending_sign_ids` counter. Options:

1. **Skip the capacity check for refunds entirely** in `finalize_refund_with_psbt` — refunds are user-initiated recovery operations and should not be gated by the same limit as withdrawals.
2. **Use a separate counter** for refund pending-sign entries, distinct from the withdrawal/active-UTXO counter.
3. **Raise the default limit** to at least 2 so a single withdrawal does not block a refund.

---

```rust
//    pending_sign_count() == 1, limit == 1
// 2. Alice calls execute_refund(utxo_storage_key, None)
//    → internal_execute_refund → finalize_refund_with_psbt
//    → require_pending_sign_capacity(&alice)
//    → require!(1 < 1, "Too many pending sign transactions")  ← PANIC
// 3. Refund is stuck; operator must call set_pending_tx_limit(alice, 2)
//    before execute_refund can succeed.
```

The existing test `test_refund_execute_twice_same_tx` already demonstrates the workaround (raising the limit to 2) and confirms the capacity check fires in this exact scenario.
