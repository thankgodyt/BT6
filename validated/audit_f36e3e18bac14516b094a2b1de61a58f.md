### Title
`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Peras Chain-Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right`, accepting every inbound certificate without any cryptographic or semantic check. An unprivileged peer can send a crafted `PerasCert` via the ObjectDiffusion mini-protocol; the certificate passes "validation", is inserted into the ChainDB, and immediately triggers chain selection with a full Peras weight boost applied to an attacker-chosen block. This is the direct analog of the withdrawal-precompile bug: both functions blindly accept an object without verifying its source/authenticity, causing the system to act on a fraudulent state transition.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate before any certificate influences chain selection. The only instance in the codebase is a catch-all stub:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No Cardano-specific override exists anywhere in the repository; this stub is the live implementation for all block types.

The inbound certificate pipeline in `processCerts` calls this function directly:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` partitions results into valid/invalid; because `validatePerasCert` always returns `Right`, every certificate is classified as valid and forwarded to `addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate into the `cdbChainSelQueue`, which the background chain-selection thread processes synchronously: [4](#0-3) 

Chain selection then applies the `vpcCertBoost` weight (set to `perasWeight params` by the stub) to the attacker-chosen block, potentially making a minority fork appear heavier than the honest chain: [5](#0-4) 

The `PerasValidationErr` data type is also a single-constructor stub with no fields, confirming that no real error taxonomy exists yet: [6](#0-5) 

A secondary, compounding gap exists in `validatePerasVote`: it only checks stake-distribution membership and never verifies the BLS vote signature, so crafted votes can also accumulate toward quorum and trigger fraudulent certificate forging internally: [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can make an honest node apply a full Peras weight boost to any block the attacker names in a crafted certificate. If the boosted block is on a minority fork, the node's chain-selection function will prefer that fork over the honest chain, causing the node to diverge from the canonical chain. Because the Peras boost is designed to be decisive (it is the mechanism that enforces finality), a single forged certificate is sufficient to flip chain selection. This constitutes a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**, matching the High-severity category in the allowed impact scope.

---

### Likelihood Explanation

The attack requires only the ability to connect to a node and speak the ObjectDiffusion mini-protocol, which is open to any peer. The crafted certificate needs only a valid CBOR structure (no cryptographic material is checked). The `processCerts` path is exercised every time a certificate is received from any peer, so the vulnerable code is on the hot path of normal operation. Likelihood is **High**.

---

### Recommendation

1. Implement real cryptographic and semantic validation inside `validatePerasCert` before Peras is enabled on any network. At minimum this must verify: (a) the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the committee's aggregate verification key, (b) that `pcRoundNo` is within the valid window relative to the current tip, and (c) that `pcBoostedBlock` refers to a known block.
2. Until (1) is complete, gate the ObjectDiffusion certificate inbound handler so that it rejects all certificates (analogous to option 2 in the original report: disable the call variant entirely until the check is implemented).
3. Apply the same fix to `validatePerasVote`: add BLS signature verification before accepting a vote as `ValidatedPerasVote`.

### Proof of Concept

```
Private testnet with Peras ObjectDiffusion enabled:

1. Attacker connects to an honest node via the ObjectDiffusion mini-protocol
   (standard peer connection, no credentials required).

2. Attacker serialises a PerasCert CBOR value:
     pcRoundNo      = <any round number, e.g. current round>
     pcBoostedBlock = <RealPoint of a block on a minority fork>
     pcVoters       = <empty or minimal voter map>
     pcSignature    = <zeroed/random bytes — never checked>

3. Attacker sends the certificate as a batch of one via ObjectDiffusion.

4. processCerts calls validatePerasCert mkPerasParams cert
   → returns Right ValidatedPerasCert{vpcCertBoost = perasWeight params}
   unconditionally.

5. addPerasCertAsync enqueues the ValidatedPerasCert into cdbChainSelQueue.

6. chainSelSync applies the Peras weight boost to the minority-fork block.

7. If boost > (honest chain weight − minority fork weight), the honest node
   switches to the minority fork, diverging from the canonical chain.
```
