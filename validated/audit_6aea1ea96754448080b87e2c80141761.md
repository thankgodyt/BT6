### Title
Missing Cryptographic Signature Verification in Peras Vote Validation Allows Unprivileged Peer to Forge Votes and Bypass Quorum — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation does not verify any cryptographic signature on incoming votes. An unprivileged peer connected via the ObjectDiffusion mini-protocol can craft `PerasVote` messages claiming to be any voter present in the stake distribution. These forged votes pass validation, are counted toward quorum, and can cause honest nodes to forge and accept a `ValidatedPerasCert` for an attacker-chosen block, directly affecting Peras chain selection.

---

### Finding Description

The `BlockSupportsPeras` instance used for all block types is defined in `SupportsPeras.hs` as a catch-all placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its `validatePerasVote` implementation ignores the `_params` argument entirely and performs only a stake-distribution lookup:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

No signature is verified. The `PerasVote blk` type in this instance carries only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId` — there is no signature field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

`PerasVoterId` is a key hash. Because `validatePerasVote` only calls `lookupPerasVoteStake` (a `Map.lookup` on the voter ID), any peer who knows the key hash of a high-stake validator — which is public information derivable from the stake distribution — can craft a vote that passes validation. [3](#0-2) 

The inbound vote handler `processVotes` calls this validation inside an `atomically` block, then adds all validated votes:

```haskell
validationResults <- atomically $ do
  alreadyInDb <- alreadyInDbSTM
  let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
  mapM validateVote votesNotAlreadyInDb
``` [4](#0-3) 

The deduplication guard uses `PerasVoteId = (PerasRoundNo, PerasVoterId)` — it prevents the same voter from voting twice in the same round, but it cannot prevent an attacker from forging a first vote for a victim voter ID, since no key ownership is ever proven. [5](#0-4) 

Once enough forged votes accumulate in `PerasVoteDB`, `updateCandidateVoteState` calls `votesReachQuorum` and then `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's chosen block: [6](#0-5)

### Impact Explanation

Peras certificates boost specific blocks in chain selection. A forged certificate for an attacker-chosen block causes honest nodes to prefer a non-canonical chain. This is a **Critical** bypass of Peras voting checks: an unprivileged peer can reach quorum for any block without holding any stake or private key, causing honest nodes to accept an invalid certificate and diverge from the canonical chain.

---

### Likelihood Explanation

The attack requires only a network connection to a node running the ObjectDiffusion vote-gossip mini-protocol and knowledge of validator key hashes (public information from the stake distribution). No stake, no private keys, and no privileged access are needed. The `validatePerasVote` stub is the active production code path for all block types, since no more specific `BlockSupportsPeras` instance exists for Cardano blocks in this repository.

---

### Recommendation

1. Implement cryptographic signature verification in `validatePerasVote`. The concrete V1 vote type (`Ouroboros.Consensus.Peras.Vote.V1.PerasVote`) already carries a `pvSignature :: VoteSignature PerasBLSCrypto` field and the `EveryoneVotes`/`WFALS` committee implementations provide `implVerifyVote` with proper BLS signature checks. The production `BlockSupportsPeras` instance must delegate to these.
2. Resolve the tracked issues (`cardano-peras/issues/73` and `cardano-peras/issues/120`) before the Peras vote gossip path is enabled on any network where the stake distribution is real.
3. Until signature verification is in place, the ObjectDiffusion vote-gossip handler should not be reachable from untrusted peers.

---

### Proof of Concept

On a private testnet with the ObjectDiffusion vote mini-protocol enabled:

1. Observe the current stake distribution to obtain the `PerasVoterId` (key hash) of validators holding enough combined stake to exceed the quorum threshold.
2. Craft `PerasVote` messages with `pvVoteVoterId` set to those key hashes, `pvVoteRound` set to the current round, and `pvVoteBlock` set to an attacker-chosen block point.
3. Send these votes to a target node via the ObjectDiffusion mini-protocol.
4. `processVotes` calls `validatePerasVote`, which calls `lookupPerasVoteStake` — this succeeds because the voter IDs exist in the stake distribution. No signature is checked.
5. `implAddVote` inserts the votes; `updateCandidateVoteState` detects quorum and calls `forgePerasCert`.
6. The resulting `ValidatedPerasCert` boosts the attacker's block in chain selection on the target node, causing it to prefer a non-canonical chain.
