Audit Report

## Title
Race Condition in `fast_fin_transfer_to_near_callback` Allows Double-Spending of Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary
`fast_fin_transfer` checks `is_unified_transfer_finalised` (reading `finalised_transfers`) before scheduling an async callback, but does not yet write to `fast_transfers`. A proof-based `fin_transfer` submitted in the inter-transaction window finds `fast_transfers` empty and pays the recipient. The subsequent `fast_fin_transfer_to_near_callback` contains no re-check of `finalised_transfers`, calls `add_fast_transfer` (which only guards against `fast_transfers` duplicates), and pays the recipient a second time.

## Finding Description

**Transaction 1 — `fast_fin_transfer`:** [1](#0-0) 
The guard reads `finalised_transfers`. At this point nothing has been written to `fast_transfers`. The function then schedules `check_or_pay_ft_storage` chained to `fast_fin_transfer_to_near_callback` — both execute in a later block. [2](#0-1) 

**Race window — `fin_transfer` / `process_fin_transfer_to_near`:**
`add_fin_transfer` inserts into `finalised_transfers` (panics on duplicate, so replay is blocked). [3](#0-2) 
Then `get_fast_transfer_status` queries `fast_transfers`, which is still empty because the callback has not run yet. [4](#0-3) 
`fast_transfer_status` is `None`, so the original recipient is paid (first payment).

**Transaction 2 — `fast_fin_transfer_to_near_callback`:**
No check of `is_unified_transfer_finalised` or `finalised_transfers` is performed. [5](#0-4) 
`add_fast_transfer` only asserts the key is absent from `fast_transfers` — which it is, because `process_fin_transfer_to_near` never inserted it (it only reads and removes). [6](#0-5) 
`send_tokens` then dispatches a second payment to the same recipient. [7](#0-6) 

The two maps are checked in opposite order by the two paths, creating a TOCTOU gap:
- Fast path: reads `finalised_transfers` → (async gap) → writes `fast_transfers`
- Fin path: writes `finalised_transfers` → reads `fast_transfers`

Neither path sees the other's write during the gap.

## Impact Explanation
The recipient receives bridged tokens twice for a single origin-chain transfer — a concrete double-spend of bridged funds. For bridge-minted tokens the bridge mints twice; for native tokens it unlocks from escrow and also transfers the relayer's deposited tokens. This matches the critical allowed impact: **double-spending / unauthorized minting of bridged funds**. The relayer's deposited tokens are consumed without reimbursement.

## Likelihood Explanation
The Ethereum (or other chain) finality proof is available before the relayer submits the fast transfer. The recipient monitors the NEAR chain for the `ft_on_transfer` / `fast_fin_transfer` transaction, then immediately submits `fin_transfer` with the pre-obtained proof. The exploitable window is 2–3 NEAR blocks (~2–6 seconds), which is sufficient for a prepared, automated attacker. No privileged access is required; `fin_transfer` is a public entry point callable by any account holding a valid proof.

## Recommendation
At the start of `fast_fin_transfer_to_near_callback`, before calling `add_fast_transfer` or `send_tokens`, re-check `is_unified_transfer_finalised`. If the proof-based finalization already ran, refund the relayer's tokens and abort:

```rust
pub fn fast_fin_transfer_to_near_callback(
    &mut self,
    fast_transfer: &FastTransfer,
    storage_payer: AccountId,
    relayer_id: AccountId,
) -> Promise {
    require!(Self::check_storage_balance_result(0), ...);

    // Re-check: abort if proof-based fin_transfer already ran
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        return self.send_tokens(
            fast_transfer.token_id.clone(),
            storage_payer,
            fast_transfer.amount,
            "",
        );
    }

    let required_balance = self
        .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
        ...
}
```

Alternatively, write a sentinel entry into `fast_transfers` synchronously inside `fast_fin_transfer` (before the async chain) so that `process_fin_transfer_to_near` sees it and redirects payment to the relayer instead of the recipient.

## Proof of Concept

1. 100 USDC transfer from Ethereum to NEAR is finalized on Ethereum; proof is available.
2. Relayer calls `ft_transfer_call` with `FastFinTransferMsg`. `fast_fin_transfer` runs: `is_unified_transfer_finalised` → `false`; `check_or_pay_ft_storage` + callback scheduled. `fast_transfers` is still empty. (Block N)
3. Recipient (or any party with the proof) calls `fin_transfer`. `process_fin_transfer_to_near` → `add_fin_transfer` (inserts into `finalised_transfers`) → `get_fast_transfer_status` → `None` → `send_tokens` → recipient receives 100 USDC. (Block N or N+1)
4. `fast_fin_transfer_to_near_callback` executes. No `is_unified_transfer_finalised` check. `add_fast_transfer` succeeds (key absent from `fast_transfers`). `send_tokens` → recipient receives another 100 USDC. (Block N+1 or N+2)

Recipient holds 200 USDC. Relayer's 100 USDC is consumed without reimbursement. A local integration test can reproduce this by executing steps 2–4 in sequence within a NEAR sandbox, asserting the recipient's final balance equals 2× the transfer amount.
