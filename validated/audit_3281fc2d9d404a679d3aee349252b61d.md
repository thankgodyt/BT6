### Title
Any Caller Can Submit a Refund Request With an Arbitrary `refund_address` for Deposits Lacking a Pre-Authorized Refund Address, Enabling BTC Theft - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user's Bitcoin deposit encodes a `DepositMsg` with `refund_address = None`, any unprivileged NEAR account can call `request_refund` for that deposit and supply an attacker-controlled BTC address as the `refund_address`. After the `unsafe_refund_timelock_sec` elapses (unless the DAO/Operator rejects the request in time), `execute_refund` sends the victim's BTC to the attacker's address. The root cause is the same class as H-7: a missing ownership/origin check — the bridge never validates that the caller of `request_refund` has any relationship to the deposit being refunded.

---

### Finding Description

`internal_request_refund` accepts a caller-supplied `refund_address` and only validates it against `deposit_msg.refund_address` when that field is `Some`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` the branch is skipped entirely, and the caller's arbitrary `refund_address` is stored verbatim in the `RefundRequest`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 564-574
let refund_request = RefundRequest {
    deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
    ...
    refund_address,          // ← attacker-supplied value, no ownership check
    gas_fee: resolved_gas_fee,
    ...
};
```

`finalize_refund_with_psbt` later builds the Bitcoin refund output directly from `refund_request.refund_address`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 323-324
let refund_address = refund_request.refund_address.clone();
```

and passes it to `build_refund_output`, which constructs the on-chain output paying that address. There is no check anywhere that the caller of `request_refund` (or `execute_refund`) is the intended recipient of the deposit.

The `RefundRequest` struct stores no `requester` field, so there is no way to enforce caller identity at execution time either.

The protocol designers added `unsafe_refund_timelock_sec` as a partial mitigation — the comment in `resolve_execute_refund_timelock` reads *"Refund address supplied by caller of `request_refund`: longer timelock to give DAO/Operator time to reject suspicious requests"* — but this is a trusted-operator backstop, not a trustless fix. If the DAO/Operator misses the window, the BTC is irrecoverably sent to the attacker.

---

### Impact Explanation

**Critical.** A successful attack results in permanent, irreversible theft of the victim's deposited BTC. The victim's deposit UTXO is spent by the refund transaction, the `verified_deposit_utxo` set is updated to block any future `verify_deposit` for that UTXO, and the nBTC mint never occurs. The victim loses their BTC with no recourse on-chain.

---

### Likelihood Explanation

**Medium.** The preconditions are:

1. The victim's `DepositMsg` has `refund_address = None` (the field is optional; many users will omit it).
2. The attacker can read the victim's `DepositMsg` from the Bitcoin blockchain (it is embedded in the transaction, e.g. via OP\_RETURN, and is passed as a public parameter to `request_refund`).
3. The attacker submits `request_refund` before the victim does (or before the victim's deposit is processed as a normal mint).
4. The DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`.

Conditions 1–3 are easily satisfied by any attacker monitoring the mempool or confirmed Bitcoin blocks. Condition 4 is the only gate, and it relies entirely on off-chain human vigilance.

---

### Recommendation

1. **Store the requester identity in `RefundRequest`** and require that only the original requester (or a privileged role) can call `execute_refund`:

```rust
pub struct RefundRequest {
    pub requester: AccountId,   // ← add this field
    ...
}
```

In `execute_refund`, enforce:
```rust
let caller = env::predecessor_account_id();
require!(
    caller == refund_request.requester
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller.clone()),
    "Only the original requester or a privileged role can execute this refund"
);
```

2. **Alternatively**, require that `deposit_msg.refund_address` is always `Some` (i.e., users must pre-authorize a BTC refund address at deposit time). This eliminates the open-address path entirely.

---

### Proof of Concept

1. **Victim** sends 1 BTC to the bridge deposit address derived from:
   ```json
   { "recipient_id": "victim.near", "refund_address": null, ... }
   ```
2. **Attacker** observes the confirmed Bitcoin transaction and reads the `DepositMsg` from the OP\_RETURN output.
3. **Attacker** calls `request_refund` on the NEAR bridge contract with:
   - `deposit_msg` = victim's `DepositMsg` (copied from chain)
   - `refund_address` = attacker's own BTC address
   - `tx_bytes` + `proof` = victim's Bitcoin transaction and its Merkle inclusion proof
4. `request_refund_callback` verifies the proof and the script\_pubkey match, then stores:
   ```rust
   RefundRequest { refund_address: "attacker_btc_addr", ... }
   ```
   No ownership check is performed. [1](#0-0) 
5. After `unsafe_refund_timelock_sec` elapses (and assuming the DAO does not reject), **attacker** (or anyone) calls `execute_refund`.
6. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `refund_request.refund_address` — the attacker's address — and requests an MPC signature. [2](#0-1) 
7. The signed transaction is broadcast; 1 BTC arrives at the attacker's address. The victim's UTXO is permanently spent; no nBTC is ever minted for the victim. [3](#0-2)
