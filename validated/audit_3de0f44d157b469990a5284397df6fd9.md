Audit Report

## Title
Permanent Freezing of Bridged Funds via Reverting ERC1155/ETH Recipient in `finTransfer` — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`finTransfer` sets `completedTransfers[payload.destinationNonce] = true` at line 287 before executing token delivery. For ERC1155 tokens, delivery uses `IERC1155.safeTransferFrom`, which mandatorily invokes `onERC1155Received` on the recipient contract. If that hook reverts, Solidity rolls back all state changes including the nonce flag, leaving the nonce unconsumed. Because the NEAR-side `process_fin_transfer_to_other_chain` path has no failure-recovery callback analogous to `fin_transfer_send_tokens_callback`, the sender's tokens locked on NEAR are permanently frozen with no refund path.

## Finding Description

In `finTransfer` (`OmniBridge.sol` lines 283–330), the nonce is consumed before delivery:

```solidity
// L283-287
if (completedTransfers[payload.destinationNonce]) {
    revert NonceAlreadyUsed(payload.destinationNonce);
}
completedTransfers[payload.destinationNonce] = true;
```

Then for ERC1155 tokens (lines 323–330):

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,   // attacker-controlled contract
    multiToken.tokenId,
    payload.amount,
    ""
);
```

`safeTransferFrom` per EIP-1155 requires the recipient to implement `IERC1155Receiver.onERC1155Received` and return the correct selector; any revert propagates up and rolls back the entire transaction, including the `completedTransfers` write. The nonce is therefore never consumed, yet every retry hits the same revert. The same structural flaw exists for the native-ETH path (lines 319–322): `revert FailedToSendEther()` is triggered when `success == false`, rolling back the nonce flag identically.

On the NEAR side, `process_fin_transfer_to_other_chain` (lib.rs line 1980) records the transfer and locks/unlocks tokens but registers no cross-chain failure callback. The `fin_transfer_send_tokens_callback` refund path (lib.rs lines 1702–1718) — which burns tokens and emits `FailedFinTransferEvent` — is only reachable for NEAR-recipient transfers, not for EVM-destination transfers. There is no admin-accessible cancellation or refund mechanism for the EVM-recipient path.

## Impact Explanation

This concretely matches the allowed critical impact: **permanent freezing of bridged funds**. Once a user initiates a transfer from NEAR (tokens locked or burned on-chain), the only release mechanism is a successful `finTransfer` on the destination EVM chain. A recipient contract that unconditionally reverts in `onERC1155Received` (or its ETH `receive()`) makes `finTransfer` permanently unexecutable for that nonce, with no on-chain recovery path on either chain.

## Likelihood Explanation

Any user bridging ERC1155 tokens or native ETH to a contract address on EVM is exposed. The attacker only needs to be the designated EVM recipient — no privileged access is required. Realistic vectors include cross-chain swaps, escrow contracts, or DeFi protocol integrations where the counterparty controls the recipient address. The recipient address is fixed in the MPC-signed payload and cannot be changed post-signing. The attack is repeatable and requires no special on-chain permissions.

## Recommendation

1. **Wrap token delivery in a `try/catch`** (Solidity ≥ 0.8): on delivery failure, mark the nonce as consumed anyway and emit a `FinTransferFailed` event, preventing indefinite retry loops.
2. **Add a NEAR-side refund path for EVM-destination failures**: implement a mechanism (e.g., a signed failure proof or a timeout-based reclaim) analogous to `fin_transfer_send_tokens_callback` so the sender can recover locked tokens when EVM finalization provably cannot succeed.
3. **For ERC1155 specifically**: consider a pull-based delivery pattern — transfer tokens to an intermediate escrow that the recipient must explicitly claim — removing the mandatory `onERC1155Received` callback from the critical finalization path.

## Proof of Concept

**Setup:**
1. Deploy `MaliciousReceiver` on EVM:
```solidity
function onERC1155Received(
    address, address, uint256, uint256, bytes calldata
) external pure returns (bytes4) {
    revert("blocked");
}
```
2. On NEAR, call `init_transfer` (or `initTransfer1155` on EVM origin) specifying `MaliciousReceiver` as the EVM recipient. Tokens are locked/burned on NEAR.
3. MPC signs the payload; relayer calls `finTransfer` on EVM.

**Execution trace:**
- `finTransfer` sets `completedTransfers[nonce] = true` (line 287).
- Reaches `safeTransferFrom` (line 324), which calls `MaliciousReceiver.onERC1155Received`.
- Hook reverts → entire transaction reverts → `completedTransfers[nonce]` is rolled back.
- Every subsequent relay attempt produces the same revert.
- NEAR-side tokens remain permanently locked; `process_fin_transfer_to_other_chain` has no failure callback to trigger a refund.
