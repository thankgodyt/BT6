### Title
Strict `normalize_amount > 0` Check in `sign_transfer` Can Permanently Freeze User Funds When Fee Consumes Most of Transfer Amount - (File: `near/omni-bridge/src/lib.rs`)

### Summary
`init_transfer` validates only that `fee < amount`, but `sign_transfer` applies a stricter check: the net amount after fee must survive decimal normalization (floor division) and remain `> 0`. For tokens where `origin_decimals > decimals`, if a user sets a fee such that `amount - fee < 10^(origin_decimals - decimals)`, the normalized amount becomes 0, `sign_transfer` panics permanently, and the user's locked tokens have no recovery path because `update_transfer_fee` cannot decrease fees.

### Finding Description

**Step 1 — `init_transfer` accepts the transfer with a permissive fee check:** [1](#0-0) 

The only constraint is `fee.fee < amount`. A user can set `fee = amount - 1`, which passes.

**Step 2 — Tokens are immediately locked/burned and the transfer message is stored in `pending_transfers`.**

**Step 3 — `sign_transfer` applies a stricter normalization check:** [2](#0-1) 

`normalize_amount` uses floor division: [3](#0-2) 

For a token registered with `origin_decimals = 24` (NEAR-side) and `decimals = 18` (EVM-side), the divisor is `10^6 = 1,000,000`. If `amount - fee < 1,000,000`, the result is `0`, and `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.

**Step 4 — The fee cannot be reduced to fix the state:** [4](#0-3) 

`update_transfer_fee` enforces `fee.fee >= current_fee.fee`, so the fee can only be increased, never decreased. Once the user is in this state, no on-chain action can unblock `sign_transfer`.

**Step 5 — No cancel/refund mechanism exists for pending transfers.** The `pending_transfers` map is only cleared via `claim_fee` (requires a proof from the destination chain, which can never be produced because `sign_transfer` never succeeds) or normal transfer completion.

### Impact Explanation

A user who initiates a transfer from NEAR to a foreign chain (e.g., Ethereum) with a fee set such that `amount - fee < 10^(origin_decimals - decimals)` will have their tokens permanently locked in the bridge contract. The transfer message is stored, the tokens are burned/locked, but `sign_transfer` will always revert. There is no cancel path, and the fee cannot be lowered. This constitutes **permanent freezing of bridged funds**.

### Likelihood Explanation

Low-to-medium. The scenario requires `amount - fee` to fall below the normalization threshold. For a 24→18 decimal token pair, the threshold is 1,000,000 yoctoNEAR (0.000001 NEAR). A user who sets a high fee to attract relayers, or who makes a calculation error, can trigger this. The protocol provides no guard at `init_transfer` time to prevent it, and no warning that the transfer will be unresolvable.

### Recommendation

Add a normalization check at `init_transfer` time (or in `init_transfer_internal`) to verify that `normalize_amount(amount - fee, decimals) > 0` before locking tokens. This mirrors the check already present in `sign_transfer` and prevents the irrecoverable state from being created. Alternatively, add a cancel/refund function that allows the original sender to reclaim locked tokens for a pending transfer that has not yet been signed.

### Proof of Concept

1. A token is registered with `origin_decimals = 24`, `decimals = 18` (6-decimal difference, divisor = `1_000_000`).
2. User calls `ft_transfer_call` → `init_transfer` with `amount = 1_000_001`, `fee = 1_000_000`.
3. Check `fee < amount` → `1_000_000 < 1_000_001` ✓ — transfer stored, tokens locked.
4. Relayer calls `sign_transfer`:
   - `amount_without_fee() = 1_000_001 - 1_000_000 = 1`
   - `normalize_amount(1, Decimals { decimals: 18, origin_decimals: 24 }) = 1 / 1_000_000 = 0`
   - `require!(0 > 0, ...)` → **panic: ERR_INVALID_AMOUNT_TO_TRANSFER**
5. User tries `update_transfer_fee` to reduce fee → rejected: `fee.fee >= current_fee.fee` enforced.
6. No cancel function exists. Tokens are permanently frozen. [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
