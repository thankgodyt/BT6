Audit Report

## Title
Missing Post-Normalization Amount Validation in `update_transfer_fee` Enables Permanent Token Lock — (File: near/omni-bridge/src/lib.rs)

## Summary

`update_transfer_fee` enforces only a raw-amount guard (`fee.fee < transfer.message.amount`) without verifying that the post-fee amount survives decimal normalization. Because `sign_transfer` applies `normalize_amount` (floor division) before producing the on-chain payload and panics unconditionally when the result is zero, a sender who raises their fee to `amount − k` where `k < 10^(origin_decimals − decimals)` permanently bricks their transfer. The fee ratchet prevents any reduction, and no public cancel or refund entry point exists, leaving locked or burned tokens irrecoverable.

## Finding Description

`update_transfer_fee` accepts any fee satisfying:

```
fee.fee >= current_fee.fee && fee.fee < transfer.message.amount
``` [1](#0-0) 

No normalization check follows. When `sign_transfer` is later called by a trusted relayer, it computes:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

`normalize_amount` performs floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

For a standard NEAR-24-decimal → Ethereum-18-decimal token, the divisor is `10^6`. Setting `fee = amount − 1` leaves `amount_without_fee = 1`; `1 / 10^6 = 0`; `sign_transfer` panics every time.

The fee ratchet makes this irreversible: [1](#0-0) 

Tokens are burned or locked in `init_transfer_internal` before `sign_transfer` is ever reached: [4](#0-3) 

The same missing guard exists in `init_transfer` itself: [5](#0-4) 

## Impact Explanation

Bridged assets (burned or locked on NEAR) become permanently irrecoverable. The only recovery paths — `claim_fee_callback` (requires successful destination-chain finalization) and `sign_transfer_callback` (requires successful MPC signing) — both depend on `sign_transfer` completing without panic, which is impossible once the normalized amount is zero. This is a concrete, permanent freezing of bridged funds, matching the Critical impact class.

## Likelihood Explanation

The condition is reachable by any unprivileged bridge user. No special role is required to call `update_transfer_fee`. The vulnerable configuration (NEAR 24-decimal token bridged to an 18-decimal EVM token) is the standard, documented deployment. The attacker need only be the original sender of the transfer (enforced by `SenderCanUpdateTokenFeeOnly`) and supply a fee of `amount − k` where `k < 10^6`. The `#[trusted_relayer]` restriction on `sign_transfer` does not mitigate this — it only means the panic is triggered when any trusted relayer attempts to process the transfer, not that the attacker must be a relayer.

## Recommendation

In both `update_transfer_fee` and `init_transfer`, after computing `amount_without_fee`, look up the destination token's `Decimals` and assert `normalize_amount(amount_without_fee, decimals) > 0` before persisting the state. In `update_transfer_fee`, after line 422:

```rust
let token_address = self.get_token_address(
    transfer.message.get_destination_chain(),
    self.get_token_id(&transfer.message.token),
).near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer.message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

Apply the equivalent guard in `init_transfer` when the token's decimals are already registered.

## Proof of Concept

1. Register token `tok.near` with `origin_decimals = 24`, `decimals = 18` (Ethereum). Divisor = `10^6`.
2. Call `ft_transfer_call` with `amount = 2_000_000`, `fee = 0`. Transfer stored; `amount_without_fee = 2_000_000`; `normalize_amount(2_000_000) = 2` — valid. Tokens are burned/locked.
3. Call `update_transfer_fee` with `fee.fee = 1_999_999`. Guard: `1_999_999 >= 0 && 1_999_999 < 2_000_000` — passes. Fee persisted.
4. `amount_without_fee = 1`. `normalize_amount(1, {origin:24, dest:18}) = 0`.
5. Any trusted relayer calls `sign_transfer` → panics: `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Fee cannot be lowered (`fee.fee >= current_fee.fee`). No public cancel entry point exists.
7. The 2,000,000 raw units of `tok.near` are permanently locked in the bridge contract.
