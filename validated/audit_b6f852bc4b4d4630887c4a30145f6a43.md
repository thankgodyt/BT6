Audit Report

## Title
ERC-1155 `safeTransferFrom` Callback Revert in `finTransfer` Permanently Freezes Bridged Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.finTransfer` marks the destination nonce as used at line 287 before executing the ERC-1155 transfer at lines 323–330 via `IERC1155.safeTransferFrom`. If the recipient contract does not implement `IERC1155Receiver` or deliberately reverts in `onERC1155Received`, the entire transaction reverts atomically, unwinding the nonce write. Because the MPC-signed payload immutably encodes the recipient address, no alternative delivery is possible, and the source-chain tokens (already burned on NEAR) are permanently unrecoverable.

## Finding Description

In `finTransfer` (line 287), the nonce is marked consumed before any token transfer occurs:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
```

The ERC-1155 delivery branch (lines 323–330) then calls:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per EIP-1155, `safeTransferFrom` MUST invoke `onERC1155Received` on any contract recipient and MUST revert if the hook does not return the correct magic selector. If the recipient contract:
- does not implement `IERC1155Receiver` (e.g., a Gnosis Safe multisig, a DeFi vault, a DAO treasury), or
- deliberately reverts in `onERC1155Received`,

the entire `finTransfer` call reverts atomically. The `completedTransfers` write is rolled back, leaving the nonce unconsumed. However, `payload.recipient` is part of the Borsh-encoded message signed by `nearBridgeDerivedAddress` (verified at line 311–313). No alternative recipient can be substituted without a fresh MPC signature. There is no admin rescue function, no pull-payment fallback, and no `claimTokens` escape hatch in the contract. The ERC-1155 tokens remain locked in the bridge contract indefinitely.

The same structural flaw exists in the native-ETH branch (lines 319–322): if `payload.recipient` is a contract that rejects ETH (no `receive()` function or explicit revert), `FailedToSendEther` is thrown, the transaction reverts, and the ETH is permanently frozen under the same conditions.

## Impact Explanation

The source-chain ERC-1155 tokens are locked or burned on NEAR at the time `finTransfer` is called. If the EVM-side delivery can never succeed—because the recipient is a contract that does not implement `IERC1155Receiver`—those assets are irrecoverably lost. This constitutes **permanent freezing of bridged funds across the NEAR-to-EVM flow**, which is an explicitly listed Critical impact. There is no administrative recovery path in the contract.

## Likelihood Explanation

ERC-1155 transfers to contract addresses are a normal use-case. Many widely-deployed contracts (Gnosis Safe, Compound, Uniswap pools, DAO treasuries) do not implement `IERC1155Receiver`. A user who specifies any such contract as the NEAR-to-EVM recipient triggers permanent loss with no malicious intent required—this is a realistic, non-exotic scenario. A deliberate attacker can also deploy a contract that always reverts in `onERC1155Received`, burn their own NEAR-side tokens, and create a permanently stuck transfer to grief the protocol or demonstrate the vulnerability.

## Recommendation

Replace `safeTransferFrom` with a pull-payment (escrow) pattern for contract recipients:

1. Wrap the `safeTransferFrom` call in a `try/catch`. On failure, credit the `(tokenAddress, tokenId, amount)` to a per-recipient claimable mapping instead of reverting.
2. Expose a `claimERC1155(address token, uint256 tokenId)` function that lets the intended recipient pull their tokens at any time.
3. Apply the same pattern to the native-ETH branch: on failed `.call`, credit the amount to a claimable-ETH mapping and expose a `claimETH()` function.
4. Ensure the nonce is consumed regardless of delivery success (as it already is structurally, but delivery failure currently reverts it).

## Proof of Concept

1. Alice holds ERC-1155 token `(tokenAddress, tokenId=7)` on NEAR (previously bridged from EVM).
2. Alice initiates a NEAR-to-EVM transfer specifying `recipient = VaultContract`, a DeFi vault that does not implement `IERC1155Receiver`. NEAR-side tokens are burned.
3. The MPC signs a `TransferMessagePayload` with `recipient = VaultContract`.
4. A relayer calls `finTransfer(signature, payload)`.
5. Execution reaches line 324: `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), VaultContract, 7, amount, "")`.
6. The ERC-1155 contract calls `VaultContract.onERC1155Received(...)`. `VaultContract` does not implement this function; the call reverts.
7. The entire `finTransfer` transaction reverts; `completedTransfers[nonce]` is reset to `false`.
8. No alternative recipient can be used (payload is MPC-signed and immutable). No admin rescue exists.
9. The ERC-1155 tokens are permanently locked in the bridge. Alice's NEAR-side tokens are already burned.

**Minimal test plan:** Deploy a mock ERC-1155 token and a mock recipient contract that does not implement `IERC1155Receiver`. Call `finTransfer` with that recipient. Assert the transaction reverts and the tokens remain in the bridge with no recovery path available.
