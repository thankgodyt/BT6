### Title
`safe_mint` Mints nBTC to Bridge Before Verifying Recipient Registration, Silently Trapping Funds on Unregistered Accounts - (File: contracts/nbtc/src/lib.rs)

---

### Summary

`safe_mint` in the nBTC token contract unconditionally mints tokens into the bridge's own internal balance before checking whether the intended recipient has a registered storage account. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens and without reverting. The minted nBTC remains trapped in the bridge's nBTC balance with no automatic recovery path for the depositing user.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` follows this sequence:

1. **Mint to bridge first** — `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally credits the full deposit amount to the bridge's own nBTC account.
2. **Check recipient registration** — only *after* minting does it check `self.token.accounts.get(&account_id).is_none()`.
3. **Silent early return** — if the recipient is unregistered, it returns `PromiseOrValue::Value(U128(0))` with no transfer, no revert, and no error.

```rust
// contracts/nbtc/src/lib.rs  lines 112-116
self.token.internal_deposit(&self.bridge_id, amount.into());

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
``` [1](#0-0) 

The result is that nBTC is minted (total supply increases) but the tokens are stranded in the bridge's own nBTC balance. The user's BTC deposit has been consumed by the bridge's UTXO set, yet they receive zero nBTC. The `U128(0)` return value signals failure to the bridge's callback, but no automatic refund or `lost_found` crediting is performed at the nBTC contract level.

---

### Impact Explanation

**Medium.** The user's BTC is locked in the bridge's UTXO set and their nBTC is minted but unreachable — a stuck bridge state that requires operator intervention to diagnose and manually recover. The bridge's `lost_found` map exists for failed `ft_transfer` callbacks, but `safe_mint`'s silent `U128(0)` return on an unregistered account is a distinct, earlier failure point that bypasses that recovery path entirely. The backed supply invariant is also broken: total nBTC supply increases without a corresponding user balance increase.

---

### Likelihood Explanation

Any user who sends a BTC deposit targeting a NEAR account that has not yet called `storage_deposit` on the nBTC contract will trigger this path. This is a realistic and common mistake — users frequently deposit before registering storage, especially when interacting via scripts, relayers, or third-party integrations. No special privileges or adversarial setup are required; the condition is reachable by any ordinary bridge user.

---

### Recommendation

Reverse the order of operations in `safe_mint`: check recipient registration *before* minting. If the recipient is unregistered, either revert with a clear error or credit the amount to `lost_found` so the bridge can recover it. Do not mint tokens to the bridge's balance until it is confirmed the full transfer to the recipient will succeed.

```rust
// Suggested fix sketch
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // or panic / lost_found
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

---

### Proof of Concept

1. User deposits BTC to the bridge-derived address for their NEAR account `alice.near`.
2. `alice.near` has never called `storage_deposit` on the nBTC contract.
3. The bridge's deposit verification succeeds; it calls `safe_mint(alice.near, amount, None)`.
4. `safe_mint` executes `internal_deposit(&self.bridge_id, amount)` — nBTC total supply increases by `amount`, all credited to the bridge's own account.
5. `self.token.accounts.get(&alice.near)` returns `None`.
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
7. `alice.near` receives zero nBTC. The BTC UTXO is consumed. The minted nBTC sits in the bridge's balance with no user-facing recovery mechanism. [2](#0-1)
