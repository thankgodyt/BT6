### Title
Bridge Pause Blocks `claim_lost_found`, Temporarily Locking User nBTC — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

The `claim_lost_found` function, which is the sole recovery path for users whose nBTC ended up in the bridge's `lost_found` mapping, is gated by `#[pause(except(roles(Role::DAO)))]`. During any bridge pause — including a routine emergency pause for bug fixes — ordinary users are completely blocked from retrieving their own nBTC. The funds remain locked in the bridge's `lost_found` state for the entire duration of the pause with no user-accessible escape hatch.

### Finding Description

When a withdrawal is cancelled via `cancel_withdraw`, the bridge attempts to return the user's nBTC via `internal_transfer_nbtc`. If that cross-contract call fails (e.g., the user's nBTC storage account is not registered), the amount is silently redirected into the `lost_found` mapping inside `transfer_nbtc_callback`: [1](#0-0) 

The only way for a user to recover these funds is `claim_lost_found`: [2](#0-1) 

This function carries `#[pause(except(roles(Role::DAO)))]`, meaning it is completely disabled for all non-DAO callers whenever the bridge is paused. The `PauseManager` role can trigger a pause at any time: [3](#0-2) 

Unlike the `cancel_withdraw` and `sign_btc_transaction` functions — which are also paused but have DAO bypass — `claim_lost_found` is a pure user-recovery function. There is no alternative path for the user to retrieve their nBTC during a pause. The DAO can bypass the pause to call `claim_lost_found` on behalf of users, but this requires active operator intervention for every affected account.

### Impact Explanation

During a bridge pause, any user with nBTC in `lost_found` has their funds completely inaccessible. The nBTC is held in the bridge contract's `lost_found` map: [4](#0-3) 

The user cannot transfer, spend, or recover these tokens until the bridge is unpaused. This constitutes a **temporary but complete locking of user funds** with no user-side remedy. The impact matches: *Medium — attacker-triggered temporary locking of bridged funds* and *Medium — stuck bridge state requiring operator intervention*.

### Likelihood Explanation

Bridge pauses are an expected operational event (the `PauseManager` role exists precisely for this). The `lost_found` mapping is populated whenever an nBTC `ft_transfer` fails inside `transfer_nbtc_callback`, which is a realistic scenario (e.g., user's nBTC storage account not registered at the time of `cancel_withdraw`). The `LostFoundNbtc` event is emitted on every such failure: [5](#0-4) 

Any overlap between an active pause and a non-empty `lost_found` entry triggers the issue. Given that pauses can last hours to days and `lost_found` entries can accumulate from routine operations, the likelihood is realistic.

### Recommendation

Remove the `#[pause]` decorator from `claim_lost_found` entirely. This function is a pure user-recovery path — it only transfers tokens that already belong to the user and are already accounted for in the bridge's `lost_found` map. Pausing it provides no security benefit (the funds are already committed) while directly harming users. Alternatively, add the user's own account to the bypass roles, though the simplest and most correct fix is to leave this function unpaused.

### Proof of Concept

1. User initiates a withdrawal: `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)` — nBTC moves to bridge balance.
2. DAO/Operator calls `cancel_withdraw` for the pending withdrawal (legitimate operational action).
3. Bridge calls `internal_transfer_nbtc(user, amount)` to return nBTC to user.
4. The `ft_transfer` cross-contract call fails (e.g., user's nBTC storage not registered).
5. `transfer_nbtc_callback` fires: `lost_found[user] += amount` — user's nBTC is now in `lost_found`.
6. A `PauseManager` pauses the bridge (e.g., for a bug fix): `pa_pause_feature("ALL")`.
7. User calls `claim_lost_found()` → **panics: "Method is paused"**.
8. User's nBTC remains locked in `lost_found` for the entire duration of the pause with no recourse. [6](#0-5) [2](#0-1)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }

            .data_mut()
