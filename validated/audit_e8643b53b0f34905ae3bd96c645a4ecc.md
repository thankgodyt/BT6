### Title
Unvalidated `refund_address` Chain Compatibility Causes Permanent Fund Lock in `execute_refund` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `refund_address` stored in a `RefundRequest` is never validated against the bridge's configured chain at `request_refund` time. When `execute_refund` later calls `build_refund_output()`, it attempts to parse the stored address against the configured chain and panics via `.expect()` if the address belongs to a different chain. Because the stored address cannot be updated after the request is created, the refund is permanently unexecutable and the user's BTC is locked.

### Finding Description
`DepositMsg.refund_address` is an optional raw `String` with no chain-format validation at any point before `execute_refund`.

In `internal_request_refund()`, the only check on `refund_address` is a string-equality guard against `deposit_msg.refund_address` when that field is pre-set:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

No chain-format validation is performed. The raw string is then stored verbatim in `RefundRequest.refund_address`: [2](#0-1) 

Later, `execute_refund` calls `build_refund_output()`, which parses the stored address against the contract's configured chain and panics if it is incompatible:

```rust
let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
    .expect("Invalid refund address");
``` [3](#0-2) 

The bridge supports multiple chains with distinct address formats (`BitcoinMainnet`, `LitecoinMainnet`, `DogecoinMainnet`, `ZcashMainnet`, etc.): [4](#0-3) 

Each chain has a distinct P2PKH/P2SH prefix byte: [5](#0-4) 

A Litecoin mainnet address (prefix `0x30`) passed to a `BitcoinMainnet`-configured bridge (prefix `0x00`) will fail `Address::parse()` and trigger the `expect()` panic. Since `RefundRequest` has no mechanism to update the stored `refund_address`, every subsequent call to `execute_refund` for that request will also panic.

Additionally, on testnet there is a silent cross-chain address collision: `BitcoinTestnet` and `LitecoinTestnet` share the same P2PKH prefix byte `0x6F`, and `BitcoinTestnet` and `DogecoinTestnet` share the same P2SH prefix byte `0xC4`. A Litecoin testnet P2PKH address will parse successfully as a Bitcoin testnet P2PKH address, causing the refund to be sent to a Bitcoin address the user may not control. [6](#0-5) 

### Impact Explanation
**Medium.** A user who provides a wrong-chain `refund_address` (either in `DepositMsg.refund_address` or as the `refund_address` argument to `request_refund`) will have their BTC permanently locked:

- `execute_refund` panics on every invocation for that request.
- The DAO can call `reject_refund` to remove the request, but this does not return funds; it only unblocks the `verify_deposit` path.
- If the deposit amount is below `min_deposit_amount`, `verify_deposit` will not mint nBTC, leaving the BTC irrecoverable.
- On testnet, the silent prefix collision means the refund is sent to a Bitcoin address the user does not control, constituting direct fund loss.

### Likelihood Explanation
Low-to-medium. The bridge supports multiple chains and the `refund_address` field is a free-form string. A user interacting directly with the contract (not through a validated UI) can easily supply a Litecoin, Dogecoin, or other chain address. The bridge provides no on-chain guard to prevent this at `request_refund` or `get_user_deposit_address` time. [7](#0-6) [8](#0-7) 

### Recommendation
Validate `refund_address` against `config.chain` inside `request_refund_callback` (and optionally inside `get_user_deposit_address`) before storing it. Replace the deferred `expect()` in `build_refund_output` with an early `require!` at storage time:

```rust
// In request_refund_callback, before storing:
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("refund_address invalid for chain: {e}")));
```

This mirrors the same-chain validation that `Address::parse` already enforces for Zcash via `convert_if_network` and for segwit via HRP comparison, and prevents the deferred panic from permanently locking funds.

### Proof of Concept
1. Bridge is deployed and configured for `Chain::BitcoinMainnet`.
2. User calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: Some("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd"), ... })` — a valid Litecoin mainnet address.
3. Bridge returns a deposit address derived from the hash of that `DepositMsg`.
4. User sends BTC below `min_deposit_amount` to the derived deposit address.
5. Relayer calls `verify_deposit`; nBTC is not minted (below minimum).
6. User calls `request_refund(deposit_msg, "LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", tx_bytes, vout, proof, None)`.
7. `request_refund_callback` stores `RefundRequest { refund_address: "LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", ... }` — no chain validation.
8. After timelock, user calls `execute_refund(utxo_storage_key)`.
9. `build_refund_output("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", ...)` calls `Address::parse("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", Chain::BitcoinMainnet)`.
10. Parsing fails (Litecoin prefix `0x30` ≠ Bitcoin prefix `0x00`); `.expect("Invalid refund address")` panics.
11. The `RefundRequest` remains in storage with the unparseable address; every future `execute_refund` call panics identically.
12. DAO can only `reject_refund` (removes the request); with amount below minimum, `verify_deposit` also fails to mint. User's BTC is permanently locked.

        &mut self,

        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())

                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
