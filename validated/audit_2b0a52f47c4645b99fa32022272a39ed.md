### Title
Accidentally Attached NEAR Tokens Permanently Stuck in Bridge Contract via `#[payable]` `sign_btc_transaction` Without Deposit Guard - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is marked `#[payable]` but contains no guard on `env::attached_deposit()`. Any NEAR tokens attached to a successful call are silently absorbed by the contract with no recovery mechanism.

---

### Finding Description

In NEAR, `#[payable]` allows callers to attach NEAR tokens to a function call. When a function succeeds, any attached NEAR stays in the contract. When it panics, the NEAR is returned. The correct pattern for functions that do not need attached NEAR is either to omit `#[payable]` entirely (which causes NEAR SDK to auto-reject any attached deposit) or to assert `env::attached_deposit() == 0` / `assert_one_yocto()`.

`sign_btc_transaction` in `chain_signatures.rs` is `#[payable]` but performs no check on the attached deposit: [1](#0-0) 

The function has no `#[access_control_any]` or `#[trusted_relayer]` restriction — only a `#[pause]` guard — making it callable by any NEAR account. A user who has a valid `btc_pending_sign_id` (i.e., any bridge user who initiated a withdrawal) can call this function with an arbitrary attached NEAR balance. If the call succeeds, the attached NEAR is permanently absorbed into the contract's balance.

The contract exposes `withdraw_protocol_fee` for recovering tracked protocol fees, but there is no mechanism to recover untracked NEAR that accumulates from `sign_btc_transaction` calls. [2](#0-1) 

By contrast, every other `#[payable]` function in the bridge that does not need a real deposit uses `assert_one_yocto()`: [3](#0-2) 

`sign_btc_transaction` is the only publicly reachable `#[payable]` function with no deposit guard of any kind.

---

### Impact Explanation

Any NEAR attached to a successful `sign_btc_transaction` call is permanently locked in the contract with no recovery path. This is a stuck-funds scenario without direct theft of bridge assets. Matches: **Low — publicly reachable stuck-state fault in production bridge path without direct theft.**

---

### Likelihood Explanation

`sign_btc_transaction` is called by bridge users during the normal withdrawal flow. A user who mistakenly attaches NEAR (e.g., copy-pasting a call pattern from another `#[payable]` function, or using a wallet/script that defaults to attaching a deposit) will lose those tokens permanently. The function is publicly reachable by any account that has initiated a withdrawal.

---

### Recommendation

Remove `#[payable]` from `sign_btc_transaction`. The NEAR SDK will then automatically reject any call that attaches a non-zero deposit, preventing accidental loss:

```rust
// Before
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(...) -> PromiseOrValue<bool> { ... }

// After
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(...) -> PromiseOrValue<bool> { ... }
```

Alternatively, add `require!(env::attached_deposit() == NearToken::from_yoctonear(0), "No deposit expected");` at the top of the function body.

---

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call`, creating a `btc_pending_sign_id` for her account.
2. Alice (or any script) calls `sign_btc_transaction` with `btc_pending_sign_id = <her_id>`, `sign_index = 0`, `key_version = 0`, and attaches `1 NEAR` to the call.
3. The function succeeds (no deposit check), the MPC signing proceeds normally.
4. The 1 NEAR is now in the bridge contract's balance, untracked by any accounting variable.
5. `withdraw_protocol_fee` cannot recover it (it only withdraws `cur_available_protocol_fee`).
6. The NEAR is permanently stuck. [4](#0-3)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

        assert_one_yocto();
        let total_protocol_fee = self.data().cur_available_protocol_fee;
        let amount = amount.map_or(total_protocol_fee, |v| v.0);
        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
        self.internal_withdraw_protocol_fee(amount)
    }
