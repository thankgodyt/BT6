### Title
ChainSync Client Ignores Peras Weight When Disconnecting Peers Beyond Forecast Horizon - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a candidate chain is preferable to the current selection. This is structurally identical to the reported bug: a zero/empty guard causes a critical state-update path to be skipped. Here, the "zero" is the empty weight snapshot, and the skipped logic is Peras-boost-aware chain comparison. When Peras is enabled, a node can be made to disconnect from a peer offering a legitimately heavier (Peras-boosted) chain that is shorter in raw block count, causing the node to stay on a lighter, non-canonical chain.

### Finding Description

In `checkPreferTheirsOverOurs`, called when a candidate header is beyond the forecast horizon, the node decides whether to keep the connection or disconnect with `CandidateTooSparse`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` branches on whether the weight snapshot is empty:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- simple block-number comparison, no Peras boosts
      ...
  | otherwise =
      -- weighted comparison using Peras certificate boosts
      ...
``` [2](#0-1) 

By passing `emptyPerasWeightSnapshot`, the function always takes the first branch — a pure block-number comparison — regardless of whether Peras certificates have boosted blocks on the candidate chain. The actual live weight snapshot is available at this point (it is read atomically in `chainSelectionForBlock` and stored in `ChainSelEnv`), but is not threaded into this check. [3](#0-2)

### Impact Explanation

When Peras is enabled and a Peras certificate has boosted a block on a candidate chain, that chain may have a higher total weight (`blockNo + weightBoost`) than the node's current selection, even if it has a lower raw block number. `checkPreferTheirsOverOurs` evaluates this scenario using only block numbers (via `emptyPerasWeightSnapshot`), so it concludes `ShouldNotSwitch` and throws `CandidateTooSparse`, disconnecting from the peer. The node then stays on the lighter chain. This is a **chain selection error**: an honest node is made to prefer a non-canonical, less-secure chain over the Peras-boosted canonical chain, violating the Peras weight-based chain selection invariant.

**Impact class**: High — chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain beyond the intended Peras security assumptions.

### Likelihood Explanation

- Requires Peras to be enabled (currently in active development; the TODO comment at line 1841 explicitly flags this as a known incomplete integration).
- Requires a scenario where a candidate chain is beyond the forecast horizon AND carries Peras certificate boosts that make it heavier despite fewer blocks — a realistic scenario during normal Peras operation when a certificate round has just completed.
- The attacker-controlled entry path is a crafted block/header sequence: an adversary presents a chain that is longer in raw block count but lighter in Peras weight, while the honest chain is shorter in block count but heavier due to a certificate boost. The node disconnects from the honest peer and stays on the adversarial chain.
- The developers have already acknowledged the issue via the `TODO` comment referencing issue #64.

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual live `PerasWeightSnapshot` (already available in the enclosing `ChainSyncClientEnv` or readable atomically from the ChainDB), so that Peras-boosted chains are correctly evaluated as preferable even when they have fewer raw blocks. Alternatively, resolve the referenced issue #64 and remove the check entirely if it is superseded by the Genesis density comparison.

### Proof of Concept

1. Peras is enabled; a certificate for round `R` boosts block `B` on the honest chain with weight `W`.
2. The honest chain has tip at block number `N` with total weight `N + W`.
3. An adversarial peer presents a chain of length `N + 1` (one more block) with no Peras boosts, total weight `N + 1`.
4. If `N + W > N + 1` (i.e., `W > 1`, which is the normal Peras boost), the honest chain is heavier.
5. The adversarial chain is adopted as the current selection (block number `N + 1`).
6. The honest peer's next header is beyond the forecast horizon; `checkPreferTheirsOverOurs` is called.
7. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares block numbers: honest tip `N` vs. our tip `N + 1` → `ShouldNotSwitch`.
8. The node throws `CandidateTooSparse` and disconnects from the honest peer.
9. The node remains on the adversarial lighter chain, violating Peras chain selection. [6](#0-5) [7](#0-6)
