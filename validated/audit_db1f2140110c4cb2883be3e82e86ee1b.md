### Title
Privileged Caller's `is_privileged` Flag Is Silently Ignored for Unsafe Refunds, Blocking Operator Fast-Track - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
In `resolve_execute_refund_timelock`, the `is_privileged` flag is computed for the calling account but is only consulted in the pre-authorized-address branch. In the unsafe-address branch (where `deposit_msg.refund_address` is `None`), the flag is silently discarded and the full `unsafe_refund_timelock_sec` (14 days by default) is unconditionally applied — even to DAO and RefundOperator callers. This mirrors the Goldigovernor pattern exactly: a legitimate actor's identity is checked, the result is stored, and then a second condition ignores it and blocks the actor anyway.

### Finding Description
`resolve_execute_refund_timelock` in `contracts/satoshi-bridge/src/refund.rs` computes `is_privileged` at lines 206–208:

```rust
let caller = env::predecessor_account_id();
let is_privileged =
    self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
```

It then branches on whether the refund address was pre-authorized:

```rust
if refund_request.deposit_msg().refund_address.is_some() {
    // Pre-authorized refund address: privileged users can fast-track.
    if is_privileged {
        0
    } else {
        config.refund_timelock_sec
    }
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec   // ← is_privileged never consulted
}
```

In the `else` branch `is_privileged` is never read. A DAO or RefundOperator calling `execute_refund` on an unsafe refund receives the same 14-day timelock as any unprivileged account. The comment itself reveals the design intent — the long timelock exists "to give DAO/Operator time to reject suspicious requests" — yet when the DAO/Operator *is* the caller they have already decided the request is legitimate and should be able to fast-track it, exactly as they can for pre-authorized addresses.

The Goldigovernor analog is direct:
- **Goldigovernor**: proposer identity is checked (`msg.sender != proposal.proposer`), then a second independent check (`getPriorVotes > proposalThreshold`) blocks the proposer anyway.
- **Bridge**: caller privilege is checked (`is_privileged`), then the unsafe-address branch ignores it and applies the full timelock anyway.

### Impact Explanation
A DAO or RefundOperator who has verified that an unsafe refund request is legitimate cannot execute it for 14 days. During that window the user's deposited BTC remains locked in the bridge with no recourse: the operator cannot fast-track the refund, and the user must wait the full unsafe timelock. This constitutes a stuck bridge state requiring operator intervention that the operator is structurally prevented from providing — matching the "stuck bridge state requiring operator intervention" Medium impact category.

### Likelihood Explanation
Any time a user submits `request_refund` without a pre-authorized `deposit_msg.refund_address` (the common case for ad-hoc refunds), the DAO or RefundOperator is blocked from fast-tracking even after manual off-chain verification. This is a normal operational path, not an edge case, so the likelihood of hitting this limitation is high.

### Recommendation
Apply the same privilege fast-track logic in the unsafe-address branch:

```rust
} else {
    if is_privileged {
        0   // or config.refund_timelock_sec if a minimal delay is still desired
    } else {
        config.unsafe_refund_timelock_sec
    }
}
```

This mirrors the pre-authorized branch and ensures the computed `is_privileged` value is actually used in both code paths.

### Proof of Concept
1. User calls `request_refund` with `deposit_msg.refund_address = None` and a valid BTC proof. The request is stored with `created_at_sec = T`.
2. DAO account calls `execute_refund` at time `T + 1 second`. `resolve_execute_refund_timelock` computes `is_privileged = true` for the DAO caller.
3. Because `deposit_msg.refund_address` is `None`, the `else` branch executes and returns `config.unsafe_refund_timelock_sec` (14 days) regardless of `is_privileged`.
4. `load_refund_request_for_execute` then panics: `"Refund timelock has not passed yet"`.
5. The DAO cannot execute the refund for 14 days despite being a privileged operator, leaving the user's BTC locked in the bridge for the full unsafe timelock period. [1](#0-0) [2](#0-1) [3](#0-2)
