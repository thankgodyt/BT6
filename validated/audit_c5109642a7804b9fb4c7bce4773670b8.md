Audit Report

## Title
Cross-Chain Replay of MPC-Signed MetadataPayload: Missing Chain Domain Separator in `deploy_token` — (`starknet/src/bridge_types.cairo`)

## Summary

`MetadataPayload::to_borsh()` produces byte-for-byte identical Borsh output to the EVM `deployToken` Borsh encoding, with no chain-domain separator. Because both the EVM and Starknet OmniBridge instances verify against the same `omni_bridge_derived_address` (the shared NEAR MPC secp256k1 key), a valid MPC signature obtained for an EVM `deployToken` call can be submitted unchanged to Starknet `deploy_token` and will pass `_verify_borsh_signature`, deploying a bridge token on Starknet without any Starknet-scoped MPC authorization.

## Finding Description

**Root cause — `MetadataPayload::to_borsh()` encodes no chain ID:** [1](#0-0) 

The encoded bytes are exactly: `[1] | borsh(token) | borsh(name) | borsh(symbol) | [decimals]`.

**EVM `deployToken` produces the identical byte sequence:** [2](#0-1) 

`bytes1(PayloadType.Metadata) | Borsh.encodeString(token) | Borsh.encodeString(name) | Borsh.encodeString(symbol) | bytes1(decimals)` — structurally and byte-for-byte identical.

**Both chains verify against the same shared MPC key:** [3](#0-2) 

**`deploy_token` calls `to_borsh()` with no chain_id:** [4](#0-3) 

**Contrast: `TransferMessagePayload::to_borsh()` correctly binds `chain_id` twice:** [5](#0-4) 

And `fin_transfer` passes `self.omni_bridge_chain_id.read()` into it: [6](#0-5) 

**No replay protection on `deploy_token`:** The only guard is `ERR_TOKEN_ALREADY_DEPLOYED`, which checks whether the token already exists on Starknet: [7](#0-6) 

A cross-chain replay targets a token not yet deployed on Starknet, so this guard does not fire.

**Exploit path:**
1. Attacker observes a legitimate EVM `deployToken` transaction on-chain, extracting `(r, s, v)` and `MetadataPayload` fields.
2. Attacker calls Starknet `deploy_token(Signature{r,s,v}, MetadataPayload{token, name, symbol, decimals})`.
3. Starknet computes `keccak256(borsh(1 | token | name | symbol | decimals))` — identical to the EVM hash.
4. `verify_eth_signature` passes because the same `omni_bridge_derived_address` is configured on both chains.
5. A bridge token is deployed on Starknet with no fresh MPC signing event for Starknet.

## Impact Explanation

This is a **chain/domain separation flaw** and an **MPC authorization bypass for the token deployer role**. An unprivileged external attacker can deploy any bridge token on Starknet using only a signature produced for an EVM deployment, violating the invariant that every Starknet token deployment must be independently authorized by the MPC for the Starknet chain. This matches the allowed Critical impact class: "Unauthorized transaction, authorization bypass, role bypass, pause bypass, or signer/prover verification bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions" and "Cross-chain replay... chain/domain separation flaw enabling invalid finalization or double-spending."

## Likelihood Explanation

The precondition — both chains sharing the same `omni_bridge_derived_address` — is not a misconfiguration; it is the intended design of the NEAR MPC architecture. All EVM `deployToken` transactions are public on-chain, so the signature and payload are trivially observable. No privileged access, victim interaction, or special tooling is required. The attack is repeatable for every new EVM token deployment.

## Recommendation

Add the Starknet chain ID to `MetadataPayload::to_borsh()`, mirroring the pattern already used in `TransferMessagePayload::to_borsh()`:

```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);   // domain separator
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
```

Update `deploy_token` to pass `self.omni_bridge_chain_id.read()`, matching the `fin_transfer` pattern. The EVM `deployToken` Borsh encoding and the NEAR MPC signing infrastructure must also be updated to include the destination chain ID when producing `MetadataPayload` signatures, so that signatures are chain-scoped end-to-end.

## Proof of Concept

1. On EVM testnet, call `deployToken(sig, {token:"test.near", name:"Test", symbol:"TST", decimals:18})` with a test secp256k1 key as `nearBridgeDerivedAddress`. Record `(r, s, v)`.
2. Deploy a Starknet OmniBridge instance configured with the **same** `omni_bridge_derived_address`.
3. Submit `deploy_token(Signature{r,s,v}, MetadataPayload{token:"test.near", name:"Test", symbol:"TST", decimals:18})` to the Starknet instance.
4. The call succeeds: `_verify_borsh_signature` passes because `keccak256(borsh(1|"test.near"|"Test"|"TST"|18))` is identical on both chains and the signer matches.
5. A bridge token is deployed on Starknet with no fresh MPC signing event for Starknet.

The existing Starknet test infrastructure already demonstrates the exact signing and verification path; the PoC requires only substituting a signature generated by the EVM test helper `metadataSignature()` into the Starknet test suite.

        ref self: ContractState, borsh_bytes: @ByteArray, signature: Signature,
    ) {
        let message_hash_le = compute_keccak_byte_array(borsh_bytes);
        let message_hash = reverse_u256_bytes(message_hash_le);

        let sig = signature_from_vrs(signature.v, signature.r, signature.s);
