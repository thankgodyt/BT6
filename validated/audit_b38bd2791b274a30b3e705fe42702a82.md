### Title
Whole-Batch Rejection in `processVotes`/`processCerts` Permanently Discards Valid Peras Votes and Certificates - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` and `PerasCert.hs`)

---

### Summary

`processVotes` and `processCerts` implement an all-or-nothing batch validation policy: if **any** vote or certificate in a peer-supplied batch fails validation, the **entire batch** is thrown away and the peer is disconnected. The valid items in the same batch — including legitimate votes from honest stake-pool operators — are silently discarded and never added to the `PerasVoteDB` / `PerasCertDB`. An unprivileged adversarial peer can exploit this by bundling one crafted invalid vote/cert with a set of valid ones it has collected from the network, causing the receiving node to permanently lose those valid votes. If this is done systematically across enough peers, the node never accumulates enough stake-weighted votes to reach quorum, so no Peras certificate is forged for that round, weakening chain-selection security.

---

### Finding Description

`processVotes` in `PerasVote.hs` validates all new votes atomically and then branches on the result of `partitionEithers`:

```haskell
case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    -- Some votes are invalid => reject the whole batch
    (errs, _) ->
      throw (PerasVoteValidationError errs)
``` [1](#0-0) 

The `(errs, _)` arm discards the second component of `partitionEithers` — the valid votes — whenever any error is present. The same pattern is reproduced verbatim in `processCerts`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

The thrown exception (`PerasVoteInboundException` / `PerasCertInboundException`) is intended to trigger peer disconnection via the `withPeer` bracket in `ouroboros-network`. [3](#0-2) 

After disconnection the peer is gone; the valid votes it carried are never re-requested. The `PerasVoteDB` deduplication check (`alreadyInDbSTM`) means those vote IDs will be silently skipped if the same peer reconnects and re-sends them, but only if the votes are still in the peer's outbound FIFO — which is not guaranteed after a reconnect. [4](#0-3) 

The validation logic itself (`validatePerasVote`) rejects a vote whose `pvVoteVoterId` is absent from the current `PerasVoteStakeDistr`. An adversary can trivially craft such a vote by using a random voter ID. [5](#0-4) 

---

### Impact Explanation

Peras certificates are forged only when accumulated stake-weighted votes for a block exceed the quorum threshold (`stakeAboveThreshold`). [6](#0-5) 

A forged certificate boosts the boosted block's weight in chain selection (`vpcCertBoost`). [7](#0-6) 

If an adversary can prevent enough valid votes from reaching the `PerasVoteDB`, quorum is never reached, no certificate is forged, and the Peras chain-selection boost is lost for that round. This degrades the node's chain-selection security to the base Ouroboros Praos level, which is weaker than the intended Peras security guarantees (fast settlement / resistance to short-range reorgs). An adversary who can suppress certificates across multiple consecutive rounds can therefore make an honest node prefer a less-secure chain than it should.

---

### Likelihood Explanation

The attack requires only an unprivileged peer connection. The adversary:

1. Monitors the `perasVoteDiffusionProtocol` gossip to collect valid votes from legitimate stake-pool operators.
2. Constructs a batch containing those valid votes plus one vote with a fabricated `pvVoteVoterId` not present in the stake distribution.
3. Sends the batch to the target node.
4. The target node rejects the entire batch, discards the valid votes, and disconnects.

No key material, stake majority, or operator access is required. The attack is repeatable from multiple sybil peers. Votes are round-scoped and time-limited, so if the attack is sustained for the duration of a Peras round, the certificate for that round is permanently unachievable on the targeted node.

---

### Recommendation

Replace the all-or-nothing policy with a partial-success policy: add valid votes/certs to the DB and only penalise (disconnect) the peer for the invalid items. Concretely, change the `(errs, _)` branch to:

```haskell
(errs, validatedVotes) -> do
  mapM_ (addVote . WithArrivalTime now) validatedVotes
  throw (PerasVoteValidationError errs)
```

This mirrors the second mitigation suggested in the FactoryDAO report: process what can be processed, then signal the error. The same fix applies symmetrically to `processCerts`. If the design intent is to keep strict peer-disconnection semantics for any invalid item, the valid items should still be committed to the DB before throwing.

---

### Proof of Concept

1. Node A is running with a known `PerasVoteStakeDistr` containing pools `P1 … Pk`.
2. Adversary B connects to node A via the `perasVoteDiffusionProtocol`.
3. B has observed valid votes `v1 … v(k-1)` from pools `P1 … P(k-1)` on the gossip network (these votes alone are insufficient for quorum).
4. B constructs a batch `[v1, …, v(k-1), v_bad]` where `v_bad` has `pvVoteVoterId = X` and `X ∉ unPerasVoteStakeDistr`.
5. B sends the batch to A via `opwAddObjects`.
6. `processVotes` calls `validatePerasVote` on each vote; `v_bad` returns `Left PerasValidationErr` because `lookupPerasVoteStake v_bad stakeDistr = Nothing`. [8](#0-7) 

7. `partitionEithers` produces `([PerasValidationErr], [validatedV1, …, validatedV(k-1)])`.
8. The `(errs, _)` branch fires: `throw (PerasVoteValidationError [PerasValidationErr])`.
9. `v1 … v(k-1)` are never passed to `addVote`; they are permanently absent from A's `PerasVoteDB`.
10. A disconnects from B. The round closes without quorum; no Peras certificate is forged for that round on node A. [1](#0-0)
