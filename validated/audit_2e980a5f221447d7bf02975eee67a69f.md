### Title
Hardcoded Tentative Peras Protocol Parameters Used in Production Vote/Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Params.hs`)

### Summary
`mkPerasParams` in `Ouroboros/Consensus/Peras/Params.hs` defines hardcoded "tentative" values for Peras protocol parameters that are explicitly acknowledged in the source as not final. These values are wired directly into production code paths that validate incoming Peras votes and certificates from peers. If the tentative values differ from the correct protocol specification values, nodes will incorrectly enforce the Peras voting rules (VR-2A and VR-2B), potentially accepting votes or certificates that should be rejected, or vice versa.

### Finding Description

`mkPerasParams` is the sole source of Peras protocol parameters in the codebase and is used in production (non-test) code: [1](#0-0) 

The function's own comment explicitly states the values are not final:

```
-- Many of these parameters are provided with sensible default values for now,
-- waiting for a final decision (in a future stage of the project) on the
-- exact values to use.
```

The hardcoded values include:
- `perasIgnoranceRounds = 487` (R — controls VR-2A, the chain-healing period)
- `perasCooldownRounds = 1928` (K — controls VR-2B, the cooldown exit condition)
- `perasRoundLength = 90` (used in all round-to-slot conversions)

These are wired into production code in three places:

**1. ChainDB initialization (`completeChainDbArgs`):** [2](#0-1) 

**2. Production vote validation (`makePerasVotePoolWriterFromChainDB`):** [3](#0-2) 

**3. Production certificate validation (`makePerasCertPoolWriterFromCertDB`):** [4](#0-3) 

The voting rules that consume these parameters are:

- **VR-2A** uses `perasIgnoranceRounds` as `_R`: a node may only exit cooldown if the last seen certificate is at least `_R` rounds old. If `_R` is too small, nodes exit the chain-healing period prematurely. [5](#0-4) 

- **VR-2B** uses `perasCooldownRounds` as `_K`: a node may only exit cooldown if the on-chain certificate round satisfies `currRound mod K == certRound mod K`. If `_K` is too small, this congruence is satisfied more frequently, allowing premature cooldown exit. [6](#0-5) 

The comment in `mkPerasParams` derives `perasIgnoranceRounds` as `ceil((T_heal + T_cq) / perasRoundLength)` with `T_heal = 600`, `T_cq = 43200`, `perasRoundLength = 90`. The stated formula for `T_heal` is `2B/asc = 600`. With Cardano mainnet `f = 0.05` and `perasRoundLength = 90`, the expected blocks per round `B = 90 × 0.05 = 4.5`, giving `T_heal = 2 × 4.5 / 0.05 = 180`, not 600. The value 600 is only consistent with `B = 15`, implying an active slot coefficient of `15/90 ≈ 0.167` — inconsistent with the mainnet value of `0.05`. This means `perasIgnoranceRounds` and `perasCooldownRounds` are derived from an internally inconsistent assumption about the active slot coefficient, making them too large by a factor of roughly 3.3× relative to mainnet parameters.

### Impact Explanation

If `perasIgnoranceRounds` (R) is too large relative to the correct value, VR-2A is harder to satisfy than it should be, causing nodes to remain in cooldown longer than the protocol requires — a liveness concern. Conversely, if R is too small (e.g., if the final specification uses a larger value), nodes exit the chain-healing period prematurely, allowing adversarially boosted blocks to persist on the chain without sufficient honest blocks to overcome them. The same logic applies to `perasCooldownRounds` (K) and VR-2B: an incorrect K changes the frequency at which the cooldown exit condition is satisfied, directly affecting whether adversarial certificate boosting can be exploited. Because `mkPerasParams` is used in `validatePerasVote` and `validatePerasCert` on the inbound network path, a crafted vote or certificate from an unprivileged peer that is valid under the wrong parameters but invalid under the correct ones would be accepted, constituting a bypass of Peras voting/certificate checks.

### Likelihood Explanation

The code itself explicitly states the values are "tentative" and "waiting for a final decision." The inconsistency in the `T_heal` derivation (using `B = 15` blocks/round, implying `asc ≈ 0.167`, versus the Cardano mainnet `f = 0.05`) is a concrete arithmetic discrepancy visible in the source. The values are already wired into the production `completeChainDbArgs` path, meaning any node built from this codebase uses these parameters for live vote/cert validation.

### Recommendation

1. Remove `mkPerasParams` from all production code paths and replace it with parameters derived from the node's `BlockConfig` or genesis configuration, as the `NOTE` in the function already anticipates: `"in the future this will depend on a concrete 'BlockConfig'."` [7](#0-6) 
2. Audit the `T_heal = 2B/asc = 600` derivation against the actual Cardano mainnet active slot coefficient (`f = 0.05`) and the Peras design document to confirm whether `B = 15` is the intended value or whether the formula should yield `T_heal = 180`.
3. Add a compile-time or startup assertion that `perasIgnoranceRounds`, `perasCooldownRounds`, and `perasRoundLength` are consistent with the genesis-configured active slot coefficient.

### Proof of Concept

**Arithmetic inconsistency in `T_heal`:**

```
Given:
  perasRoundLength = 90 slots
  Cardano mainnet f = 0.05 (active slot coefficient)
  Expected blocks per round B = 90 * 0.05 = 4.5

Formula from comment: T_heal = 2B/asc = 2 * 4.5 / 0.05 = 180 slots

But mkPerasParams uses T_heal = 600, which requires B = 15:
  2 * 15 / 0.05 = 600  →  B/perasRoundLength = 15/90 = 0.167 ≠ 0.05

Derived perasIgnoranceRounds with T_heal = 600:
  ceil((600 + 43200) / 90) = ceil(486.67) = 487  (current value)

Correct perasIgnoranceRounds with T_heal = 180:
  ceil((180 + 43200) / 90) = ceil(482) = 482

Derived perasCooldownRounds with T_heal = 600:
  ceil((600 + 43200 + 129600) / 90) + 1 = 1928  (current value)

Correct perasCooldownRounds with T_heal = 180:
  ceil((180 + 43200 + 129600) / 90) + 1 = ceil(1932) + 1 = 1933
```

The discrepancy means VR-2A's chain-healing window and VR-2B's cooldown period are computed from an inconsistent active slot coefficient assumption, making the production vote/certificate validation diverge from the protocol specification for mainnet parameters.

        PerasIgnoranceRounds 487
