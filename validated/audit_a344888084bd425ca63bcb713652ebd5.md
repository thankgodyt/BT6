Audit Report

## Title
Missing Zero-Address Recipient Validation in `init_transfer` Allows Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function in `near/omni-bridge/src/lib.rs` validates only that the recipient chain is not NEAR, but does not check whether the recipient `OmniAddress` is a zero address. A user who supplies `eth:0x0000000000000000000000000000000000000000` as the recipient will have their tokens burned/locked on NEAR, and the resulting EVM `finTransfer` call will either permanently destroy ETH (native path) or permanently freeze the locked tokens (ERC20 path). The `OmniAddress::is_zero()` method already exists in the shared type library but is not called here.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

No subsequent check calls `OmniAddress::is_zero()`, which is fully implemented in `near/omni-types/src/lib.rs`: [2](#0-1) 

The transfer message with the zero recipient is stored and the user's tokens are burned/locked. When the relayer calls `sign_transfer`, the MPC network signs a payload containing `recipient = address(0)`. On the EVM side, `finTransfer` marks the nonce used and dispatches:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
``` [3](#0-2) 

A low-level `.call` to `address(0)` in the EVM always returns `success = true`, so ETH is permanently burned. For ERC20/bridge-token paths, OpenZeppelin's `safeTransfer` and `mint` to `address(0)` revert, causing the entire `finTransfer` transaction to revert. Because the transfer message on NEAR already has the zero address baked in and there is no mechanism to alter or cancel a stored transfer message, the locked tokens on NEAR are permanently frozen with no recovery path.

`finish_withdraw_v2` has the same gap: it parses the recipient string via `H160::from_str` (which accepts the all-zeros hex string without error) and stores it without a zero-address check: [4](#0-3) 

## Impact Explanation
- **Native ETH path**: Tokens are burned on NEAR; `finTransfer` sends ETH to `address(0)` via a low-level call that succeeds — ETH is permanently destroyed. This is direct, irreversible loss of bridged funds.
- **ERC20/bridge-token path**: `finTransfer` reverts (zero-address guard in OpenZeppelin), but the NEAR-side tokens remain locked with no way to complete or cancel the transfer — permanent freezing of bridged funds.

Both outcomes match the Critical allowed impact: *permanent loss or freezing of bridged funds*.

## Likelihood Explanation
The entry point (`ft_transfer_call` → `ft_on_transfer` → `init_transfer`) is callable by any unprivileged token holder. No special role or access is required. The `OmniAddress` type parses and accepts a zero EVM address without error. A user can trigger this accidentally (copy-paste error) or intentionally. The exploit is repeatable for any token and any amount.

## Recommendation
Add a zero-address guard in `init_transfer` immediately after the chain-kind check, using the already-available `OmniAddress::is_zero()`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipientAddress.as_ref()
);
```

Apply the same guard in `finish_withdraw_v2` after parsing the `H160` recipient, before constructing the `TransferMessage`. [5](#0-4) 

## Proof of Concept
1. User holds 1 wETH (NEP-141) on NEAR.
2. User calls `ft_transfer_call` on the wETH token contract with `receiver_id` = omni-bridge and `msg` = `InitTransfer { recipient: "eth:0x0000000000000000000000000000000000000000", fee: 0 }`.
3. `init_transfer` passes the chain-kind check (`Eth != Near`), stores the transfer, burns 1 wETH on NEAR.
4. Relayer calls `sign_transfer`; MPC signs the payload containing `recipient = address(0)`.
5. Relayer calls `finTransfer` on the EVM bridge with the valid MPC signature, `payload.recipient = address(0)`, `payload.tokenAddress = address(0)` (native ETH).
6. EVM executes `address(0).call{value: 1 ether}("")` → returns `success = true`.
7. 1 ETH is permanently burned. The user's wETH on NEAR is already gone. Funds are irrecoverably lost.

For the ERC20 freeze variant, substitute any ERC20 token: step 6 reverts (OpenZeppelin zero-address guard), the NEAR-side tokens remain locked permanently with no recovery path. [6](#0-5)
