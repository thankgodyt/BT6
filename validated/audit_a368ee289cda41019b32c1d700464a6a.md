### Title
`checkPreferTheirsOverOurs` Uses Hardcoded Empty Peras Weight Snapshot, Causing Incorrect Chain Selection Beyond Forecast Horizon — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the live Peras certificate weight snapshot. This is structurally identical to the reported bug: a function that requires prior state setup (the actual weight snapshot) is called without that setup, so the operation silently degrades to a weight-unaware comparison. When a candidate chain is beyond the forecast horizon and is preferred only due to Peras certificate boosts (i.e., it is shorter by block count but carries certificate weight), the node incorrectly disconnects from the peer serving that chain, causing it to prefer a non-canonical chain.

---

### Finding Description

`preferAnchoredCandidate` accepts a `PerasWeightSnapshot blk` parameter and branches on whether it is empty:

- If `isEmptyPerasWeightSnapshot weights` → compare chains purely by `selectView` (block count / slot tiebreaker, the pre-Peras rule).
- Otherwise → compare chains by `weightedSelectView`, which accounts for Peras certificate boosts. [1](#0-0) 

The live snapshot is maintained in the ChainDB and is read correctly in `chainSelSync` and in the BlockFetch client interface: [2](#0-1) 

However, `checkPreferTheirsOverOurs` — called inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` (forecast outside range) — passes the hardcoded `emptyPerasWeightSnapshot` directly:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty; actual snapshot never fetched
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [3](#0-2) 

The call site that triggers `checkPreferTheirsOverOurs`: [4](#0-3) 

`projectLedgerView` returns `Nothing` when `forecastFor` raises `OutsideForecastRange`: [5](#0-4) 

The analog to the reported bug is exact:

| Reported bug | This finding |
|---|---|
| `queueDropBoost` (setup) never called before `dropBoost` | `getPerasWeightSnapshot` (setup) never called before `preferAnchoredCandidate` |
| `dropBoost` checks `dropBoostQueue`, finds it empty, returns `false` | `preferAnchoredCandidate` checks `isEmptyPerasWeightSnapshot`, finds it empty, falls back to weight-unaware comparison |
| Reward adjustments silently never happen | Peras certificate boosts silently never influence the disconnect decision |

---

### Impact Explanation

**High. Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

Under Peras, a chain can be the canonical (preferred) chain even if it is shorter by block count, provided it carries sufficient certificate weight. When such a chain's tip is beyond the forecast horizon of the syncing node's intersection:

1. `projectLedgerView` returns `Nothing`.
2. `checkPreferTheirsOverOurs` is invoked with `emptyPerasWeightSnapshot`.
3. `preferAnchoredCandidate` sees the candidate as shorter and returns `ShouldNotSwitch`.
4. The node throws `CandidateTooSparse` and disconnects from the peer.

The node then never adopts the Peras-preferred chain. If all peers serving the canonical chain are in this situation (e.g., during a large slot gap that pushes the chain tip beyond the forecast window), the node permanently selects the non-canonical, longer-by-block-count chain. This violates the chain-selection invariant that Peras is designed to enforce.

---

### Likelihood Explanation

**Medium.** Three conditions must hold simultaneously:

1. Peras is active and certificates have been issued for a chain that is shorter by block count.
2. The candidate chain's tip is beyond the forecast horizon of the syncing node's intersection (a slot gap larger than the stability window, `3k/f` slots).
3. The weight-boosted chain is not also longer by block count (i.e., the boost is the sole reason for preference).

Condition 2 is not rare during initial sync or after a node restart with a stale chain. Conditions 1 and 3 become increasingly likely as Peras certificate issuance becomes routine. The TODO comment at the call site (`https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is incorrect but have not yet removed or corrected it.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the ChainDB (via `getPerasWeightSnapshot`), consistent with how `chainSelSync` and the BlockFetch client interface already obtain it: [2](#0-1) 

Alternatively, if the intent is to remove `checkPreferTheirsOverOurs` entirely (as the TODO suggests), that removal should be prioritised before Peras certificate issuance is enabled on production networks, since the current code actively makes incorrect disconnect decisions once Peras weights are non-trivial.

---

### Proof of Concept

**Attacker-controlled entry path**: An honest (or adversarial) peer serves a valid chain `C_peras` that:
- Is shorter than the local selection `C_local` by block count.
- Carries Peras certificate boosts sufficient to make `weightedSelectView cfg weights C_peras > weightedSelectView cfg weights C_local`.
- Has its tip in a slot beyond the forecast horizon of the syncing node's intersection with `C_peras`.

**Execution path**:

1. ChainSync client receives a header from the peer at slot `s` where `s >= maxFor` (outside forecast range).
2. `checkTime` calls `readLedgerState` with `prj = projectLedgerView s`.
3. `projectLedgerView s` returns `Nothing` (outside forecast range).
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs kis'`.
5. `checkPreferTheirsOverOurs` calls `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag`.
6. Because `isEmptyPerasWeightSnapshot emptyPerasWeightSnapshot = True`, the comparison uses `selectView` only.
7. `theirFrag` is shorter by block count → `ShouldNotSwitch` → `throwSTM CandidateTooSparse`.
8. The node disconnects from the peer serving `C_peras`.
9. The node retains `C_local` as its selection, which is non-canonical under Peras. [6](#0-5) [7](#0-6) [8](#0-7)
