### Title
Unprivileged caller can hijack any user's deposit refund by supplying victim's `DepositMsg` with attacker-controlled `refund_address` — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable by any unprivileged account. `request_refund_callback` verifies only that the output at the caller-supplied `vout` matches the deposit address derived from the caller-supplied `deposit_msg`, but **never verifies that the caller owns or is authorized to act on that `deposit_msg`**. An attacker who knows a victim's `DepositMsg` (emitted publicly via `Event::LogDepositAddress`) can submit a refund request for the victim's UTXO with an attacker-controlled `refund_address`. After the 24-hour unsafe timelock elapses (if the DAO/Operator does not reject it), anyone can call `execute_refund` and the victim's BTC is sent to the attacker.

---

### Finding Description

**Step 1 — `request_refund` is open to all callers.**

`request_refund` in `bridge.rs` carries only `#[payable]` and `#[pause]`; it does **not** carry an individual `#[trusted_relayer]` attribute. The `#[trusted_relayer]` on the impl block generates the whitelist infrastructure but does not enforce the check on methods that lack the per-method attribute (compare: `verify_refund_finalize` at line 602 and `remove_refund_pending_tx_id` at line 622 both carry individual `#[trusted_relayer]`, while `request_refund` at line 510 does not). [1](#0-0) 

**Step 2 — The only `refund_address` guard is opt-in and easily bypassed.**

`internal_request_refund` checks `deposit_msg.refund_address` only when it is `Some`. If the victim's `DepositMsg` was created without a pre-authorized refund address (the common case for standard deposits), the check is skipped entirely and the caller's arbitrary `refund_address` is accepted. [2](#0-1) 

**Step 3 — `request_refund_callback` verifies script_pubkey but not caller identity.**

The callback derives the deposit address from the caller-supplied `deposit_msg`, checks that `output[vout].script_pubkey` matches, and stores the `RefundRequest`. There is no check that the caller is the NEAR account embedded in `deposit_msg`, nor any check that the caller is the depositor. [3](#0-2) 

**Step 4 — The stored `RefundRequest` carries the attacker's `refund_address`.**

The `RefundRequest` is stored verbatim with the attacker-supplied `refund_address`. `execute_refund` later builds a PSBT that pays to this address. [4](#0-3) 

**Step 5 — After the unsafe timelock, anyone can execute the refund.**

Because `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` (24 hours). After that window, any caller can invoke `execute_refund`, which builds and signs a PSBT paying the victim's UTXO to the attacker's address. [5](#0-4) 

---

### Impact Explanation

The attacker can permanently redirect a victim's BTC deposit to an address they control. No nBTC is ever minted for the victim, and the underlying BTC is spent to the attacker. This is a direct, irreversible theft of user funds from bridge custody.

---

### Likelihood Explanation

- `DepositMsg` values are public: they are emitted by `get_user_deposit_address` via `Event::LogDepositAddress` and are required inputs to `verify_deposit_v2`, so any on-chain observer can reconstruct them.
- The attacker only needs to attach the required NEAR storage deposit and supply a valid SPV proof (the same proof the legitimate relayer would use).
- The 24-hour unsafe timelock is the sole mitigation; it relies entirely on DAO/Operator vigilance. If monitoring is delayed or the operator is offline, the attack succeeds.
- The multi-output scenario in the question is one concrete instantiation: a transaction with outputs at two distinct deposit addresses lets the attacker pick either victim's UTXO by choosing the matching `deposit_msg` and `vout`.

---

### Recommendation

Add a caller-identity check inside `internal_request_refund` or `request_refund_callback`. The simplest fix is to require that `env::predecessor_account_id()` matches the `account_id` field embedded in `deposit_msg` (or a field explicitly designating who may request the refund). Alternatively, require that `deposit_msg.refund_address` is always pre-set (i.e., reject requests where it is `None` and the caller is not a trusted relayer), so the `refund_address` is always bound at deposit-address-derivation time and cannot be overridden by a third party.

---

### Proof of Concept

```
Precondition:
  - Victim sends BTC to deposit address derived from DepositMsg_victim
    { account_id: "victim.near", ..., refund_address: None }
  - The BTC transaction is confirmed; its tx_id and SPV proof are observable on-chain.
  - Attacker observes DepositMsg_victim from the NEAR LogDepositAddress event.

Attack:
  1. Attacker calls request_refund(
       deposit_msg  = DepositMsg_victim,   // victim's public DepositMsg
       refund_address = "attacker_btc_addr",
       tx_bytes     = <victim's confirmed tx>,
       vout         = 0,                   // victim's output index
       proof        = <valid SPV proof>,
       gas_fee      = None
     ) with required NEAR storage deposit attached.

  2. request_refund_callback fires:
     - output[0].script_pubkey == derive(DepositMsg_victim).script_pubkey  ✓
     - deposit_msg.refund_address is None → no address guard fires          ✓
     - RefundRequest stored: { utxo_storage_key: "{tx_id}@0",
                               refund_address: "attacker_btc_addr", ... }

  3. After 24 hours (unsafe_refund_timelock_sec), attacker calls execute_refund(
       utxo_storage_key = "{tx_id}@0"
     ).

  4. Bridge builds and MPC-signs a PSBT spending victim's UTXO to "attacker_btc_addr".
     Victim's BTC is permanently redirected to the attacker.
```
