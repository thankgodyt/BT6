### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Unauthorized Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The external report describes a publicly callable operation (`sweep`) that executes without checking against a trusted reference price (`belief_price`), allowing an attacker to sandwich the operation by manipulating state before and after it. The consensus analog is the Peras certificate ingest pipeline: any peer can submit a `PerasCert` object, the validation function `validatePerasCert` in the production degenerate `BlockSupportsPeras` instance unconditionally returns `Right` (no cryptographic or committee-membership check), and the accepted certificate immediately influences chain selection by boosting a peer-chosen block's weight. An unprivileged peer can therefore inject a fake certificate that tips chain selection toward a non-canonical fork — the exact "no trusted reference, publicly triggerable, state-manipulating" pattern from the report.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` — the only instance in the production codebase. No specific override exists for `CardanoBlock` or any Shelley-era block. Every certificate from every peer passes "validation" unconditionally. [2](#0-1) 

**Ingest path — peer certificates reach `validatePerasCert` via the object-diffusion pool writer:** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is the production writer used when Peras is enabled. It calls `processCerts … (validatePerasCert mkPerasParams) … (void . ChainDB.addPerasCertAsync chainDB)`. The `-- TODO replace when actual plumbing is in place` comment confirms the stub is live in the production path. [4](#0-3) 

`processCerts` calls `validateCert` on each certificate; if all pass (they always do), it calls `addCert` — which is `ChainDB.addPerasCertAsync`.

**Chain-selection effect — accepted certificate triggers a fork switch:** [5](#0-4) 

`chainSelSync … (ChainSelAddPerasCert cert …)` adds the certificate to `PerasCertDB`, reads the boosted block from `VolatileDB`, and calls `chainSelectionForBlock` for it. Chain selection then uses `getPerasWeightSnapshot`, which now includes the attacker-injected boost, and may switch to the fork containing the boosted block.

**Weight snapshot used in candidate comparison:** [6](#0-5) 

`preferCandidate` compares `wsvTotalWeight` (block number + weight boost). A fake certificate with `perasWeight params` boost can make a shorter fork appear heavier than the canonical chain.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. **Front-run**: send a `PerasCert` boosting a block on an adversarial fork. The certificate passes `validatePerasCert` unconditionally and is stored in `PerasCertDB`.
2. **Trigger**: the node's `chainSelectionForBlock` runs with the inflated `PerasWeightSnapshot`, preferring the boosted fork over the canonical chain.
3. **Back-run**: the node is now on the adversarial fork; the attacker can sustain this by continuing to inject certificates for each new adversarial block.

This is a **bypass of Peras certificate verification** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical" scope item: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."* It also matches "High": *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

- **Peras is disabled by default**, so the attack surface is gated behind operator opt-in. Once enabled, however, the path is fully reachable from any connected peer with no stake, keys, or privileges required.
- The object-diffusion protocol is a standard node-to-node mini-protocol; any peer can submit `PerasCert` objects.
- The stub is explicitly marked TODO and linked to an open issue (`cardano-peras/issues/120`), confirming it is not a deliberate design choice but an unfinished implementation shipped in the production binary.

---

### Recommendation

1. **Block Peras certificate ingestion entirely until `validatePerasCert` performs real cryptographic and committee-membership checks.** The current stub must not be reachable from the network path.
2. Implement `validatePerasCert` to verify: (a) the certificate's aggregate signature against the committee's public keys for the round, (b) that the round number is within the valid window, and (c) that the boosted block point is on a plausible chain.
3. Add a feature-flag guard in `makePerasCertPoolWriterFromChainDB` that refuses to process any certificate if the validation function is still the degenerate stub.
4. Mirror the fix for `validatePerasVote`, which similarly omits cryptographic signature verification. [7](#0-6)

### Proof of Concept

**Private-testnet sequence (Peras enabled):**

```
1. Node A (honest) and Node B (attacker) are peers.
   Peras is enabled; perasWeight = W (e.g., 1000).

2. Canonical chain tip: block C at height H, total weight H.
   Adversarial fork tip: block F at height H-1, total weight H-1.

3. Attacker constructs PerasCert { pcCertRound = R, pcCertBoostedBlock = F }.
   No signature, no committee proof — the struct is accepted by the degenerate instance.

4. Attacker sends the certificate via the object-diffusion protocol.

5. processCerts calls validatePerasCert → Right (unconditional).
   ChainDB.addPerasCertAsync stores the cert.

6. chainSelSync (ChainSelAddPerasCert) runs:
   - PerasWeightSnapshot now maps F → W.
   - chainSelectionForBlock is called for F.
   - preferAnchoredCandidate compares:
       canonical: wsvTotalWeight = H + 0
       adversarial: wsvTotalWeight = (H-1) + W  (= H + W - 1 > H for W ≥ 2)
   - ShouldSwitch: node adopts the adversarial fork.

7. Attacker repeats for each new adversarial block, keeping the node off the canonical chain.
``` [8](#0-7) [9](#0-8) [10](#0-9)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
