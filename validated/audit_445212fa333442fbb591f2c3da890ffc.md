### Title
Invalid `refund_address` Accepted Without Format Validation, Permanently Blocking `execute_refund` — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` / `request_refund_callback` flow stores the user-supplied `refund_address` string with no BTC/ZEC address format validation. The only check performed is an optional equality comparison against `deposit_msg.refund_address`. The actual address parsing occurs much later, inside `build_refund_output`, where a malformed or wrong-network address causes an irrecoverable panic. Because the refund request is already persisted and duplicate requests are rejected, every subsequent `execute_refund` call panics, leaving the user's deposit permanently stuck until a privileged operator intervenes.

---

### Finding Description

In `internal_request_refund`, the `refund_address` parameter undergoes no format validation: [1](#0-0) 

The only check is whether `refund_address` matches `deposit_msg.refund_address` when the latter is `Some`. When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a refund address), the string is forwarded verbatim to `request_refund_callback`: [2](#0-1) 

`request_refund_callback` stores the address in `RefundRequest` without any `Address::parse` call. The duplicate-request guard then prevents a second `request_refund` for the same UTXO: [3](#0-2) 

The format check only occurs in `build_refund_output`, called from `execute_refund`: [4](#0-3) 

`Address::parse(...).expect("Invalid refund address")` panics on any malformed or wrong-network string. In NEAR, a panic inside a call rolls back all state changes for that call, so the refund request remains with `executed = false` and the UTXO is never added to `verified_deposit_utxo` (that insertion happens inside `finalize_refund_with_psbt`, which is never reached): [5](#0-4) 

The user is now in a dead-end state:
- `execute_refund` panics on every call.
- `request_refund` is rejected because the request already exists.
- No user-callable function can update or remove the stuck request.

The only exit is a privileged `reject_refund` call by DAO or Operator: [6](#0-5) 

---

### Impact Explanation

This maps to **Medium — stuck bridge state requiring operator intervention**. The user's BTC deposit is locked: the refund path is broken (panics on every attempt), and the user cannot re-submit a corrected address without operator action. The non-refundable NEAR storage deposit paid at `request_refund` time is also lost. The bridge supports multiple chains (Bitcoin, Zcash, Litecoin, Dogecoin), so a wrong-network address (e.g., a mainnet address submitted against a testnet-configured bridge) is a realistic trigger. No funds are directly stolen, but the user's BTC is inaccessible through the intended refund path until a privileged role intervenes.

---

### Likelihood Explanation

**Medium.** Any unprivileged user who calls `request_refund` can trigger this by supplying a `refund_address` that is syntactically invalid, belongs to the wrong network, or uses an unsupported address type. The bridge's multi-chain support (Bitcoin mainnet/testnet, Zcash mainnet/testnet, Litecoin, Dogecoin) increases the probability of a network mismatch. The `unsafe_refund_timelock_sec` path (used when `deposit_msg.refund_address` is `None`) imposes a longer waiting period before `execute_refund` can even be called, meaning the user discovers the failure only after a significant delay.

---

### Recommendation

Validate `refund_address` early — in `request_refund_callback` (or in `internal_request_refund` before the async promise chain) — by calling `Address::parse(&refund_address, config.chain.clone())` and rejecting the request immediately if parsing fails. This mirrors the pattern already used in `build_refund_output` and `target_script_pubkey`, and prevents invalid addresses from ever being persisted.

---

### Proof of Concept

1. User has a BTC deposit that was never finalized (e.g., the `deposit_msg` contained an unreachable `recipient_id`).
2. User calls `request_refund` with `refund_address = "tb1qinvalidaddress"` (testnet bech32 string submitted to a mainnet-configured bridge, or any syntactically invalid string). `deposit_msg.refund_address` is `None`, so no equality check fires.
3. `request_refund_callback` verifies the BTC transaction inclusion proof, then stores the invalid address in `RefundRequest` without calling `Address::parse`.
4. After `unsafe_refund_timelock_sec` elapses, user calls `execute_refund`.
5. `build_refund_output` calls `Address::parse("tb1qinvalidaddress", Chain::BitcoinMainnet).expect("Invalid refund address")` → panics.
6. NEAR rolls back the call; `RefundRequest.executed` remains `false`; UTXO is not added to `verified_deposit_utxo`.
7. User calls `request_refund` again → rejected: `"Refund request already exists for this UTXO"`.
8. User calls `execute_refund` again → panics again for the same reason.
9. User's BTC deposit is permanently stuck until DAO or Operator calls `reject_refund` to clear the request, after which the user can re-submit with a valid address.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
