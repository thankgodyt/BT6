### Title
Strict Equality in `migrate_to_new_token_mint` Enables Attacker-Triggered DoS on Token Migration — (File: `contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

The `migrate_to_new_token_mint` callback in the satoshi-bridge enforces a strict equality check (`sum == total_supply`) between the sum of queried account balances and the old token's total supply. Any unprivileged nBTC holder can front-run the migration by transferring tokens to an account not included in the migration list, causing the equality to fail and permanently blocking the migration until the operator retries with an updated list — which can be disrupted again indefinitely.

---

### Finding Description

In `contracts/satoshi-bridge/src/nbtc/migration.rs`, the `migrate_to_new_token_mint` callback collects the `ft_total_supply` and `ft_balance_of` results for each account in the provided list, sums them, and then enforces:

```rust
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [1](#0-0) 

The `internal_migrate_to_new_token` function issues all queries as parallel cross-contract calls and chains the callback: [2](#0-1) 

On NEAR, cross-contract calls are asynchronous — each receipt executes in a separate block. Between the query receipts and the callback receipt, other transactions can execute. The nBTC token exposes a standard, permissionless `ft_transfer` that any holder can call: [3](#0-2) 

An attacker holding any amount of nBTC can call `ft_transfer` to send tokens to a fresh account that was not included in the `accounts` list passed to `migrate_to_new_token`. After this transfer:

- `sum` (sum of balances of listed accounts) decreases by the transferred amount
- `total_supply` is unchanged (transfers do not affect supply)
- `sum != total_supply` → `require!` panics → entire migration callback reverts

The operator must retry with an updated account list, but the attacker can repeat the attack on every retry by transferring to yet another unlisted account. The cost on NEAR is minimal (one storage deposit + 1 yoctoNEAR per disruption).

---

### Impact Explanation

The token migration (`migrate_to_new_token`) is a critical bridge upgrade path that switches the bridge's active nBTC token contract. A persistent DoS on this function means the bridge cannot complete a token migration, leaving the bridge stuck on the old token contract indefinitely. This constitutes a **stuck bridge state requiring operator intervention** and a **bypass of bridge upgrade controls**.

---

### Likelihood Explanation

Any nBTC holder — including a user with a dust balance — can execute this attack. The attacker only needs to observe the pending `migrate_to_new_token` transaction in the NEAR mempool and submit an `ft_transfer` to a new account before the callback executes. NEAR transaction costs are negligible. The attack can be repeated on every retry, making the migration permanently uncompletable as long as the attacker is willing to spend dust amounts.

---

### Recommendation

Replace the strict equality with a `>=` check (the sum of listed accounts can never exceed total supply since balances are non-negative), and separately verify that no supply is left unaccounted for by minting any remainder to a designated bridge/treasury account, or by reverting only if `sum > total_supply`:

```rust
require!(
    sum <= total_supply,
    "Sum of account balances exceeds total supply"
);
// Optionally: mint (total_supply - sum) to a designated overflow account
```

This ensures the migration succeeds even if tokens were transferred to unlisted accounts between the query and the callback, while still preventing over-minting.

---

### Proof of Concept

1. Operator (MigrationOperator role) calls `migrate_to_new_token(new_token, [alice, bob])` where Alice and Bob hold all nBTC supply (e.g., 1000 sat total).
2. Bridge issues parallel cross-contract calls: `ft_total_supply()` → 1000, `ft_balance_of(alice)` → 600, `ft_balance_of(bob)` → 400.
3. Before the `migrate_to_new_token_mint` callback executes, attacker (Alice) calls `nbtc.ft_transfer(charlie, 1, None)` where `charlie` is a new account not in the list.
4. Callback executes: `total_supply = 1000`, `sum = ft_balance_of(alice) + ft_balance_of(bob)`. But the queried values were snapshotted at query time (600 + 400 = 1000). Wait — actually the promise results are the values at the time the queries executed, not at callback time. Let me clarify:

The queries and the callback are in the same promise chain. The `ft_balance_of` results returned to the callback reflect the state **at the time those query receipts executed**. However, `ft_total_supply` and each `ft_balance_of` are separate receipts that may execute in different blocks. If the attacker's transfer executes **after** the `ft_balance_of(alice)` receipt but **before** `ft_total_supply` receipt (or vice versa), the snapshot is inconsistent.

More directly: if the attacker transfers **before any of the query receipts execute**, then `ft_balance_of(alice)` returns 599, `ft_balance_of(bob)` returns 400, `ft_total_supply` returns 1000, and `sum = 999 != 1000` → migration reverts. [4](#0-3)
