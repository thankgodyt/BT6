### Title
Inverted Success/Failure Condition in `submit_transfer_to_btc_connector_callback` Causes Permanent Fund Freezing and Fee Mis-accounting — (File: `near/omni-bridge/src/btc.rs`)

### Summary

`submit_transfer_to_btc_connector_callback` in `near/omni-bridge/src/btc.rs` contains an inverted condition that confuses the success and failure outcomes of a NEAR `ft_transfer_call`. Under NEAR's NEP-141 standard, `ft_on_transfer` returns the number of tokens to **refund** (i.e., `result.0 > 0` means the BTC connector **rejected** the tokens — failure). The code treats this as the success branch and pays the relayer fee. Conversely, when the BTC connector **accepts** all tokens (`result.0 == 0` — success), the code treats it as failure and re-inserts the transfer message without paying the fee. This is a direct analog of the external report's two vulnerability classes: fee mis-accounting (wrong amount/condition used for fee payment) and refund/callback inconsistency (user funds permanently frozen in an edge case).

### Finding Description

In `submit_transfer_to_utxo_chain_connector`, the transfer message is removed from `pending_transfers` before the `ft_transfer_call` is dispatched: [1](#0-0) 

The callback then decides whether to pay the fee or re-insert the transfer: [2](#0-1) 

The guard on line 111 is:
```rust
if matches!(call_result, Ok(result) if result.0 > 0) {
    let token_fee = transfer_msg.fee.fee.0;
    self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
} else {
    // re-insert transfer message
}
```

Under NEAR's `ft_transfer_call` protocol, `ft_on_transfer` returns the number of tokens to **refund back to the sender**:
- `result.0 == 0` → BTC connector consumed all tokens → **withdrawal succeeded**
- `result.0 > 0` → BTC connector returned tokens → **withdrawal failed**

The code has these two branches swapped:

| Actual outcome | `result.0` | Code branch executed | Effect |
|---|---|---|---|
| BTC withdrawal **succeeded** | `== 0` | `else` | Transfer re-inserted, fee **not** paid |
| BTC withdrawal **failed** | `> 0` | `if` | Fee **paid** to relayer, transfer **not** re-inserted |

### Impact Explanation

**When BTC withdrawal fails (the critical path):**
1. The transfer message was already removed from `pending_transfers` at line 84.
2. The callback's `if` branch fires, paying the fee to the relayer via `send_fee_internal`.
3. The transfer message is **never re-inserted** — there is no retry path and no refund mechanism for the user.
4. The user's bridged tokens (locked in the NEAR omni-bridge escrow) are **permanently frozen** with no recovery path.

**When BTC withdrawal succeeds:**
1. The transfer message is re-inserted into `pending_transfers`.
2. The fee is **not** paid to the relayer despite the work being completed.
3. The relayer can call `submit_transfer_to_utxo_chain_connector` again, but the bridge no longer holds the tokens (they were consumed by the BTC connector), so the second `ft_transfer_call` will fail — creating a stuck state.

The fee mis-accounting is a direct analog of the external report's royalty permyriad bug: the wrong value/condition is used to determine what is paid and to whom.

### Likelihood Explanation

Any BTC withdrawal failure — whether caused by a legitimate BTC connector error (invalid UTXO set, connector-side validation, network conditions) or by a malicious trusted relayer deliberately supplying invalid `input`/`output` UTXO fields (which are not validated by the bridge, only by the connector) — triggers this path. The `msg` parameter's `input` and `output` fields pass through the bridge unchecked: [3](#0-2) 

A malicious trusted relayer can craft a `msg` with invalid UTXO inputs that the BTC connector rejects, causing `result.0 > 0`, collecting the fee, and permanently freezing the user's funds. Even without malice, any legitimate connector failure has the same effect.

### Recommendation

Invert the condition in `submit_transfer_to_btc_connector_callback`:

```rust
// CORRECT: result.0 == 0 means all tokens consumed (success)
if matches!(call_result, Ok(result) if result.0 == 0) {
    let token_fee = transfer_msg.fee.fee.0;
    self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
} else {
    // failure: re-insert transfer message so the relayer can retry
    let required_storage_balance =
        self.add_transfer_message(transfer_msg, transfer_owner.clone());
    self.update_storage_balance(
        transfer_owner,
        required_storage_balance,
        NearToken::from_yoctonear(0),
    );
    PromiseOrValue::Value(())
}
```

This mirrors the correct pattern used in `fin_transfer_send_tokens_callback`, which checks `is_refund_required` (i.e., whether the downstream call failed) before deciding whether to revert state or pay the fee: [4](#0-3) 

### Proof of Concept

1. User initiates a NEAR → Bitcoin transfer via `init_transfer`, locking tokens in the omni-bridge.
2. Relayer calls `submit_transfer_to_utxo_chain_connector` with a `msg` containing invalid UTXO `input` fields.
3. The bridge removes the transfer message and calls `ft_transfer_call` to the BTC connector.
4. The BTC connector's `ft_on_transfer` rejects the invalid inputs and returns `amount` (full refund) → `result.0 > 0`.
5. `submit_transfer_to_btc_connector_callback` fires the `if` branch: pays `transfer_msg.fee.fee.0` to the relayer via `send_fee_internal`.
6. The transfer message is **not** re-inserted. The user's tokens remain locked in the bridge with no pending transfer record and no recovery path.
7. The relayer has collected the fee without completing the withdrawal. [2](#0-1)
