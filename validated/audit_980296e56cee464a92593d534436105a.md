### Title
`safe_mint` Silently Mints nBTC to Bridge Balance Without Crediting Unregistered User Accounts — (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge's own balance before checking whether the recipient account is registered. When the recipient is unregistered, the function returns `U128(0)` early — a silent non-panic return — leaving the freshly minted nBTC permanently credited to the bridge's internal balance with no corresponding user credit. Because the bridge's deposit callback observes `is_promise_success() == true` (no panic occurred), it marks the deposit UTXO as consumed. The depositing user's BTC is locked in the bridge's Bitcoin address while they receive zero nBTC.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Unconditionally mints** `amount` nBTC into the bridge's own token balance:
   `self.token.internal_deposit(&self.bridge_id, amount.into());` [1](#0-0) 

2. **Checks registration** of the intended recipient:
   `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` [2](#0-1) 

3. Only if the account is registered does it proceed to `ft_transfer` / `ft_transfer_call` to move tokens to the user. [3](#0-2) 

The early return on line 115 is **not a panic**. From the bridge's perspective the cross-contract call to `safe_mint` succeeded (`is_promise_success() == true`). The bridge's deposit callback pattern — as seen in `transfer_nbtc_callback` — only branches on `is_promise_success()`: [4](#0-3) 

It does not inspect the `U128` return value of `safe_mint`. Consequently:
- The bridge marks the deposit UTXO as verified/consumed (`verified_deposit_utxo` set).
- The nBTC total supply increases by `amount` (tokens sit in `bridge_id`'s balance).
- The user's nBTC balance remains zero.
- The user cannot burn nBTC to initiate a withdrawal because they hold none.

This is the direct analog of M-05: an operation assumed to always succeed (token credit to user) silently fails for a specific class of inputs (unregistered accounts), and the surrounding flow does not detect or compensate for the failure.

### Impact Explanation
- **nBTC supply inflation without backing**: Total supply grows by `amount` but no user holds those tokens, violating the 1:1 BTC-backing invariant.
- **User funds stuck**: The depositor's BTC is locked in the bridge's Bitcoin UTXO set. They cannot withdraw it (no nBTC to burn) and cannot re-deposit it (UTXO already marked verified). Recovery requires operator intervention via the refund system, which itself requires a separate proof submission and timelock.
- Matches allowed impact: *Medium — permanent burning below backed supply / stuck bridge state requiring operator intervention.*

### Likelihood Explanation
Any NEAR account that sends BTC to the bridge address before calling `storage_deposit` on the nBTC contract triggers this path. This is a realistic scenario for first-time users unfamiliar with NEP-141 storage registration requirements. No special privilege or key is needed; the attacker-controlled input is simply the absence of prior storage registration.

### Recommendation
Reorder the logic in `safe_mint` so that tokens are only minted **after** confirming the recipient account exists, or auto-register the account (as `mint_inner` already does via `internal_register_account`) before depositing:

```rust
// Option A: register on demand (mirrors mint_inner)
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

Alternatively, if the intent is to return early for unregistered accounts, do so **before** calling `internal_deposit` so no tokens are minted when the transfer cannot proceed.

### Proof of Concept
1. Alice sends 0.01 BTC to the bridge's deposit address derived from her NEAR account `alice.near`.
2. Alice has **not** called `storage_deposit` on the nBTC contract, so `self.token.accounts.get(&alice.near)` returns `None`.
3. A relayer submits `verify_deposit_v2` with a valid Merkle proof; the bridge verifies it and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
4. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — nBTC total supply increases by 1,000,000 satoshis, all credited to `bridge_id`.
5. `safe_mint` finds `alice.near` unregistered and returns `PromiseOrValue::Value(U128(0))` — **no panic**.
6. The bridge's deposit callback sees `is_promise_success() == true`, marks the UTXO as consumed in `verified_deposit_utxo`.
7. Alice holds 0 nBTC. Her BTC UTXO is spent/locked. She cannot withdraw and cannot re-deposit the same UTXO.
8. The bridge's nBTC balance is inflated by 1,000,000 units with no corresponding user entitlement. [5](#0-4) [6](#0-5)

```rust
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```

```rust
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
```
