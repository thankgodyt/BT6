### Title
`stakeAboveThreshold` Compares Absolute Per-Voter Stake Against Relative Quorum Threshold Without Normalization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras quorum check function `stakeAboveThreshold` directly compares the sum of individual voters' `PerasVoteStake` values against `perasQuorumStakeThreshold`, which is a relative (normalized) value. The `PerasVoteStake` type is explicitly documented as potentially holding absolute (non-normalized) ledger stake, and the committee weight computation (`implEligiblePartyVoteWeight`) for persistent members returns raw absolute `LedgerStake` with no normalization by total stake. This unit mismatch — individual absolute stake used where a system-wide normalized fraction is required — is the direct analog of the external report's `_boostState.votingPower` misassignment.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The function performs a bare `>=` comparison between `unPerasVoteStake voteStake` (a `Rational`) and `unPerasQuorumStakeThreshold` (also a `Rational`), with no normalization step. The `PerasVoteStake` type's own documentation acknowledges the unit ambiguity: [2](#0-1) 

**Source of absolute stake — `implEligiblePartyVoteWeight` in `EveryoneVotes.hs`:**

For the `EveryoneVotes` committee scheme, the vote weight returned is the raw absolute `LedgerStake`:

```haskell
implEligiblePartyVoteWeight _committee member =
  VoteWeight (unLedgerStake (unNonZero voterStake))
``` [3](#0-2) 

For the `WFALS` committee scheme, persistent members also receive their raw absolute ledger stake as vote weight:

```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight stake
``` [4](#0-3) 

Only non-persistent members normalize by `totalNonPersistentStake` — not by total stake — so even they are not properly normalized relative to the full committee. [5](#0-4) 

**How the absolute stake flows into the quorum check:**

`validatePerasVote` looks up the voter's stake from `PerasVoteStakeDistr` and attaches it as `vpvVoteStake`: [6](#0-5) 

`votesReachQuorum` then sums all `vpvVoteStake` values and calls `stakeAboveThreshold`: [7](#0-6) 

The `PerasQuorumStakeThreshold` is a relative fraction (e.g., 0.75 of total committee stake): [8](#0-7) 

When `LedgerStake` values are absolute (e.g., a pool holds 5,000,000 lovelace out of 100,000,000 total), the sum of absolute stakes will be compared against a threshold like 0.75, producing a wildly incorrect result in either direction.

The `localSortitionNumSeats` function confirms `LedgerStake` is absolute — it explicitly divides `voterStake` by `totalNonPersistentStake` to normalize: [9](#0-8) 

---

### Impact Explanation

**Two failure modes depending on the magnitude of absolute stakes:**

1. **Quorum trivially reached with a single vote (unauthorized certificate acceptance):** If absolute stakes are large numbers (e.g., 5,000,000 lovelace), a single voter's stake far exceeds the relative threshold of 0.75. A single malicious or colluding voter can forge a Peras certificate without true quorum, causing the node to accept an invalid certificate and apply an unearned chain-weight boost. This directly enables chain-selection manipulation — an adversary can make an honest node prefer a non-canonical chain by boosting a minority fork.

2. **Quorum never reached (Peras permanently disabled):** If absolute stakes are small fractions (e.g., 0.001 per voter), the sum of all honest votes never reaches 0.75, so no certificate is ever forged. Peras boost is silently disabled, degrading settlement guarantees to pure Praos.

Both outcomes constitute a bypass of Peras voting/certificate checks. The first is Critical: it enables unauthorized certificate acceptance and chain-selection divergence reachable by an unprivileged peer sending crafted votes over the node-to-node diffusion protocol.

---

### Likelihood Explanation

The production node-to-node handler in `NodeToNode.hs` currently passes `pure (PerasVoteStakeDistr mempty)` as a placeholder: [10](#0-9) 

The TODO comment there explicitly states this will be replaced with real committee selection data. When that wiring is completed — which is the intended production path — the absolute `LedgerStake` values from `implEligiblePartyVoteWeight` will flow into `stakeAboveThreshold` without normalization, triggering the bug. The vulnerability is latent in the current codebase and will activate upon Peras deployment. The entry path is fully reachable by any unprivileged peer sending Peras votes via the object-diffusion mini-protocol.

---

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` by the total committee stake before comparing against the relative quorum threshold. Concretely:

1. Pass the total committee stake (sum of all `LedgerStake` values in `PerasVoteStakeDistr`) into `stakeAboveThreshold`, or
2. Pre-normalize all values stored in `PerasVoteStakeDistr` at construction time (divide each voter's absolute stake by the total stake), or
3. Introduce a distinct `NormalizedPerasVoteStake` newtype enforced at the type level to prevent mixing absolute and relative values.

The `implEligiblePartyVoteWeight` implementations for persistent members in both `EveryoneVotes.hs` and `WFALS.hs` should also normalize by total stake, consistent with how non-persistent members normalize by `totalNonPersistentStake`.

---

### Proof of Concept

Consider a committee with two pools:
- Pool A: absolute `LedgerStake = 5_000_000` (5% of 100M total)
- Pool B: absolute `LedgerStake = 3_000_000` (3% of 100M total)
- `perasQuorumStakeThreshold = 0.75` (relative, 75% of total)

Pool A sends a single vote. `validatePerasVote` looks up its stake: `PerasVoteStake (5_000_000 % 1)`. `votesReachQuorum` calls `stakeAboveThreshold` with `totalVoteStake = 5_000_000`. The check `5_000_000 >= 0.75` is `True`. A certificate is forged with only 5% of actual stake — far below the intended 75% quorum. The node accepts this certificate and applies a chain-weight boost to the voted block, making an adversarially chosen minority fork appear heavier than the honest majority chain.
