Audit Report

## Title
Unregistered Token Transfer Permanently Locks User Funds in NEAR Bridge - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` (invoked via `ft_on_transfer`) accepts any NEAR NEP-141 token without verifying that it has been registered in the bridge (i.e., has a `token_decimals` entry and a mapped destination-chain address). The bridge retains the user's tokens (returning `U128(0)` to the NEP-141 callback), stores the transfer in `pending_transfers`, and provides no user-accessible cancellation path. Every subsequent `sign_transfer` call for that transfer ID will unconditionally panic because the required token metadata is absent, leaving the funds permanently locked until DAO intervention.

## Finding Description

**Step 1 – `init_transfer` accepts the token without registration checks.**

`ft_on_transfer` dispatches to `init_transfer` for any `InitTransfer` message:

```
near/omni-bridge/src/lib.rs L253-263
```

`init_transfer` performs only two semantic checks before proceeding:
- `recipient.get_chain() != ChainKind::Near` (L531-534)
- `fee < amount` (L554-557)

There is no check that the token has a `token_decimals` entry or a mapped destination-chain address. Execution then reaches `init_transfer_internal`.

**Step 2 – `init_transfer_internal` locks the tokens and returns `U128(0)`.**

`init_transfer_internal` (L1829-1865) inserts the transfer into `pending_transfers` via `add_transfer_message`, calls `lock_tokens_if_needed`, and returns `U128(0)`. Returning `U128(0)` to the NEP-141 callback means zero tokens are refunded; the bridge retains the full amount.

**Step 3 – `sign_transfer` unconditionally panics for unregistered tokens.**

When a relayer later calls `sign_transfer`, it unconditionally requires both a registered destination-chain address and a `token_decimals` entry (L462-474):

```rust
let token_address = self
    .get_token_address(...)
    .unwrap_or_else(|| env::panic_str(BridgeError::FailedToGetTokenAddress...));

let decimals = self
    .token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
```

For an unregistered token, `get_token_address` returns `None` and the function panics. This is not recoverable by any relayer action.

**Step 4 – No user-accessible cancellation path exists.**

A grep for `cancel_transfer` in `near/omni-bridge/src/lib.rs` returns zero matches. The only function that can move tokens out of the bridge on behalf of a stuck transfer is `transfer_token_as_dao` (L1511-1529), which is gated by `#[access_control_any(roles(Role::DAO))]`. The user has no self-service escape hatch.

## Impact Explanation

This matches the allowed critical impact: **permanent freezing of bridged funds**. A user who calls `ft_transfer_call` on any NEAR token not registered with the bridge will have their tokens locked in the contract indefinitely. `sign_transfer` will always revert for that transfer ID, and the user cannot recover their funds without DAO intervention. The DAO recovery path (`transfer_token_as_dao`) is privileged and not guaranteed to be exercised promptly or at all.

## Likelihood Explanation

Realistic. A token may exist on NEAR and on a foreign chain but not yet be registered in the bridge (e.g., `bind_token`/`deploy_token` not yet called, or called only for one destination chain while the user targets another). A user who observes the token on both chains and attempts a bridge transfer will trigger this silently. No special attacker capability is required — only a standard `ft_transfer_call` from any NEAR account. The scenario is repeatable for every unregistered token.

## Recommendation

Add a registration guard at the start of `init_transfer` (or inside `init_transfer_internal`) before storing the transfer and retaining tokens:

```rust
// Verify the token is registered for the destination chain
let token_omni = OmniAddress::Near(token_id.clone());
let token_address = self.get_token_address(
    init_transfer_msg.get_destination_chain(),
    self.get_token_id(&token_omni),
);
require!(token_address.is_some(), BridgeError::FailedToGetTokenAddress.as_ref());
let token_address = token_address.unwrap();
require!(
    self.token_decimals.contains_key(&token_address),
    BridgeError::TokenDecimalsNotFound.as_ref()
);
```

If the check fails, `init_transfer` should return `transfer_message.amount` (full refund) instead of `U128(0)`, so the NEP-141 callback refunds the user's tokens. This mirrors the existing refund pattern already used in `init_transfer_internal` (L1846-1848) and `init_transfer_resume` (L641-643).

## Proof of Concept

1. Deploy a standard NEP-141 token (`unregistered.token`) on NEAR that has **not** been passed to `bind_token` or `deploy_token` on the bridge.
2. Call `ft_transfer_call` on `unregistered.token` targeting the bridge contract, with a valid `InitTransferMsg` specifying an EVM recipient.
3. Observe: `ft_on_transfer` → `init_transfer` → `init_transfer_internal` completes, emits `InitTransferEvent`, returns `U128(0)` — tokens are retained.
4. Call `sign_transfer` with the resulting `TransferId` (as a trusted relayer or via a test harness that bypasses the relayer check).
5. Observe: the call panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`.
6. Confirm no public function exists to cancel the transfer or recover the tokens without DAO role.
7. Confirm `get_transfer_message` still returns the stuck entry in `pending_transfers`.

A NEAR sandbox integration test (analogous to the existing `zcash_stale_transfer_poc.rs` pattern) can demonstrate steps 1-6 deterministically without mainnet access.
