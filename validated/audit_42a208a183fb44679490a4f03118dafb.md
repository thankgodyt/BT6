### Title
Missing Proof-of-Possession Verification Before BLS Public Key Aggregation Enables Rogue-Key Forgery of Peras Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

---

### Summary

`aggregatePublicKeys` in `BLS.hs` explicitly documents that all BLS public keys must have their proofs of possession (PoP) verified before aggregation. However, `verifyProofOfPossession` is defined and exported but **never called anywhere in the production code**. Both `implVerifyCert` implementations (`EveryoneVotes.hs` and `WFALS.hs`) aggregate voter public keys directly from the ledger stake distribution without any PoP check. This leaves the BLS aggregate signature scheme open to the classical **rogue key attack**, where an adversary registers a crafted public key that cancels out a legitimate voter's key, allowing the attacker to forge a Peras certificate that appears to have quorum support it does not have.

### Impact Explanation

In BLS aggregate signature schemes, the **rogue key attack** works as follows. Suppose legitimate voter `V` has public key `pk_V`. An attacker `A` registers a crafted key `pk_A = pk_A_real * pk_V^{-1}` on the ledger. When the verifier aggregates `pk_V` and `pk_A`, the result is `pk_V * pk_A = pk_A_real`. The attacker, who knows the private key for `pk_A_real`, can now produce a valid aggregate signature over any message using only their own private key. The verifier accepts this as a multi-party aggregate signature, even though `V` never signed anything.

Applied here: an attacker who registers a rogue BLS `SIGN` key as a stake pool can forge a `EveryoneVotesCert` or `WFALSCert` Peras certificate that appears to carry quorum support from legitimate committee members. This bypasses the Peras voting and certificate checks entirely, allowing unauthorized block boosting — a critical bypass of Peras certificate verification.

**Impact class:** Critical — bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

Any stake pool operator can register a BLS public key on the ledger. Crafting a rogue BLS key requires only standard elliptic-curve arithmetic (computing a group inverse and a scalar multiplication on BLS12-381 G2). No privileged access, key compromise, or stake majority is required. The attack is deterministic and requires no brute force. The only prerequisite is being a registered stake pool, which is an unprivileged on-chain action.

---

### Recommendation

1. **Enforce PoP verification before aggregation.** In `implVerifyCert` (both `EveryoneVotes.hs` and `WFALS.hs`), call `BLS.verifyProofOfPossession` for each voter's public key before passing the keys to `aggregateVoteVerificationKeys`. The PoP for each pool's `SIGN` key should be stored alongside the public key in the ledger stake distribution and checked at certificate verification time.

2. **Alternatively, use a rogue-key-resistant aggregation scheme.** The IETF BLS draft (section 3.3, `BLS_POP`) specifies a scheme where PoP is verified once at key registration and the aggregate signature scheme is then safe. Ensure the ledger enforces PoP at pool BLS key registration and that the consensus layer can rely on this invariant — and document it explicitly as a verified precondition rather than an unverified assumption.

3. **Remove the `unchecked` aggregation path from the certificate verification hot path** or rename it to make the security-critical precondition impossible to accidentally skip.

### Proof of Concept

**Setup:**
- Legitimate pool `V` has BLS SIGN key pair `(sk_V, pk_V)` registered on the ledger.
- Attacker `A` computes `pk_A = g^{sk_A} * pk_V^{-1}` for a chosen `sk_A`, and registers `pk_A` as their pool's BLS SIGN key.

**Forgery:**
1. A Peras certificate `EveryoneVotesCert electionId candidate {seatV, seatA} aggSig` is to be forged.
2. The verifier in `implVerifyCert` collects `pk_V` and `pk_A` from the ledger and calls `aggregateVoteVerificationKeys [pk_V, pk_A]`.
3. The aggregate key is `pk_V * pk_A = pk_V * g^{sk_A} * pk_V^{-1} = g^{sk_A}`.
4. Attacker `A` computes `aggSig = sign(sk_A, hashVoteSignature electionId candidate)`.
5. `verifyAggregateVoteSignature aggKey electionId candidate aggSig` succeeds — the certificate is accepted as if both `V` and `A` voted, even though `V` never participated.

The entry point is a crafted Peras certificate received over the network miniprotocol, processed by `implVerifyCert` in `EveryoneVotes.hs` or `WFALS.hs`. [6](#0-5) [7](#0-6) [5](#0-4)

-- | Aggregate multiple public keys into a single one.
--
-- PRECONDITION: all keys must have the same scope.
--
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  -- Ensure all keys have the same scope before aggregation
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $
    PublicKey
      { unPublicKey = aggKey
      , publicKeyScope = publicKeyScope firstKey
      }
