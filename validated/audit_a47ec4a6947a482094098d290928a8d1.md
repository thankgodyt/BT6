Audit Report

## Title
Re-entrancy via Malicious ERC-1155 Token Causes `originNonce` Collision and Permanent Freezing of Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer` and `initTransfer1155` both increment `currentOriginNonce` at the top of the function but then read the storage variable again — not a local snapshot — after an external token-transfer call when passing it to `initTransferExtension` and `emit InitTransfer`. A malicious ERC-1155 token can re-enter `initTransfer1155` inside its own `safeTransferFrom` body, advance `currentOriginNonce` a second time, and cause the outer call to emit `InitTransfer` with the same `originNonce` as the inner call. The NEAR side processes the first proof and permanently ignores the second, locking the outer call's tokens in the EVM bridge with no recovery path.

## Finding Description

**Root cause — storage variable read after external call:**

In `initTransfer1155` (L448–490), `currentOriginNonce` is incremented at L448, but the value used in `initTransferExtension` (L471) and `emit InitTransfer` (L483) is read from the storage variable *after* the external call at L458–464:

```solidity
currentOriginNonce += 1;                          // L448 — nonce becomes N
// ...
IERC1155(tokenAddress).safeTransferFrom(          // L458 — external call
    msg.sender, address(this), tokenId, amount, ""
);
// ...
initTransferExtension(..., currentOriginNonce, ...); // L471 — reads storage, may be N+1
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...); // L483 — same
```

The identical pattern exists in `initTransfer` (L381, L418, L430).

**Attack path via malicious ERC-1155:**

A malicious ERC-1155 token's `safeTransferFrom` can re-enter `initTransfer1155` directly — before returning to the bridge — because Solidity has no built-in re-entrancy guard here. The `onERC1155Received` guard at L530 (`operator != address(this)`) is irrelevant: the re-entry happens inside the malicious token's `safeTransferFrom` body, not through `onERC1155Received`. Furthermore, when the bridge calls `safeTransferFrom`, it is the operator, so `operator == address(this)` would pass the guard anyway.

**State trace (starting at `currentOriginNonce = 5`):**

```
Outer call: initTransfer1155(MaliciousERC1155, ...)
  L448: currentOriginNonce = 6
  L458: MaliciousERC1155.safeTransferFrom → re-enters initTransfer1155
        Inner call:
          L448: currentOriginNonce = 7
          L458: MaliciousERC1155.safeTransferFrom → transfers normally, returns
          L471: initTransferExtension(..., nonce=7, ...)
          L483: emit InitTransfer(originNonce=7)   ← INNER event
        returns to outer safeTransferFrom
  L471: initTransferExtension(..., currentOriginNonce=7, ...)  ← reads 7, not 6
  L483: emit InitTransfer(originNonce=7)   ← OUTER event, SAME nonce

Result:
  originNonce 6 — never emitted (gap)
  originNonce 7 — emitted twice (collision)
```

This directly violates the documented invariant in `evm/CLAUDE.md` (L34): *"State before external calls: Always mutate state … before any external call … This is the primary reentrancy defense."*

**Why existing guards are insufficient:**

The `onERC1155Received` guard (L530) only blocks direct ERC-1155 sends from external parties. It does not prevent re-entrancy through the malicious token's `safeTransferFrom` implementation itself. There is no `ReentrancyGuard` or `nonReentrant` modifier on either function.

## Impact Explanation

The NEAR `fin_transfer_callback` reconstructs the transfer using `origin_nonce` from the parsed EVM event (near/omni-bridge/src/lib.rs L723). Two `InitTransfer` events with identical `originNonce` are indistinguishable to the NEAR prover. NEAR processes the first proof and permanently ignores the second. The outer call's tokens — already transferred into the bridge at L458–464 — are locked inside the EVM bridge contract with no admin-recovery function and no mechanism to re-submit the proof. This constitutes **permanent freezing of bridged funds**, which is in the critical impact scope.

## Likelihood Explanation

The attack requires only three permissionless steps:
1. Deploy a malicious ERC-1155 contract whose `safeTransferFrom` re-enters `initTransfer1155` on the first invocation and transfers normally on the second.
2. Call `logMetadata1155` (L234, fully permissionless) to register the malicious token with the bridge.
3. Call `initTransfer1155` with the malicious token.

No admin keys, no MPC compromise, no front-running, and no external dependency failure are required. Any unprivileged user can execute this on-chain.

## Recommendation

Capture the nonce into a local variable immediately after incrementing, before any external call, and use only that local variable in `initTransferExtension` and `emit`:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // snapshot before external calls

IERC1155(tokenAddress).safeTransferFrom(...);

initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Apply this fix to both `initTransfer` and `initTransfer1155` in `OmniBridge.sol`. Alternatively, add OpenZeppelin's `ReentrancyGuard` (`nonReentrant` modifier) to both functions. Both fixes should be applied together for defense in depth.

## Proof of Concept

**Minimal Foundry test plan:**

```solidity
contract MaliciousERC1155 is ERC1155 {
    OmniBridge bridge;
    bool reentered;

    function safeTransferFrom(address from, address to, uint256 id,
                               uint256 amount, bytes memory) public override {
        if (!reentered) {
            reentered = true;
            // Re-enter initTransfer1155 before returning
            bridge.initTransfer1155{value: ...}(address(this), id, amount, fee,
                                                nativeFee, recipient, message);
        }
        // Second call: transfer normally
        _safeTransferFrom(from, to, id, amount, "");
    }
}

// Test:
// 1. Deploy MaliciousERC1155, mint tokens to attacker
// 2. Call bridge.logMetadata1155(address(malicious), tokenId)
// 3. Call bridge.initTransfer1155(address(malicious), tokenId, ...)
// 4. Assert: two InitTransfer events emitted with identical originNonce
// 5. Assert: originNonce-1 never appears in any event
// 6. Assert: attacker's tokens are locked in bridge with no recovery path
```

**File:** evm/CLAUDE.md (L32-34)
```markdown
- **No replay attacks**: Every `destinationNonce` must be checked against `completedTransfers` and marked used before any token transfer. Every `originNonce` is incremented atomically. A nonce must never be reusable
- **Event completeness**: `InitTransfer` and `FinTransfer` events must contain every field needed to reconstruct the transfer. The NEAR side relies solely on these events — any missing or ambiguous field means lost funds or spoofable transfers. Fields must not be collapsible (e.g. two different transfers must never produce the same event data)
- **State before external calls**: Always mutate state (e.g. mark nonce used) before any external call (token transfer, ETH send, custom minter). This is the primary reentrancy defense
```
