### Title
Stale (Empty) Peras Weight Snapshot Used in `checkPreferTheirsOverOurs` Causes Incorrect Chain-Selection Disconnection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hard-codes `emptyPerasWeightSnapshot` when comparing the candidate chain against the local selection at the moment a header exceeds the forecast horizon. Because the comparison ignores all Peras certificate weight boosts, the node can disconnect from honest peers that offer a *heavier* (more secure under Peras) chain while remaining connected to an adversary that offers a *longer-by-block-count but lighter* chain. This is the direct analog of the Ditto oracle-price caching bug: a critical selection decision is made with a zeroed-out "price" (weight) instead of the real one.

---

### Finding Description

When the ChainSync client cannot yet forecast a `LedgerView` for an incoming header (the slot is beyond the forecast horizon), `projectLedgerView` returns `Nothing` and the client falls into `readLedgerStateHelper`, which calls `checkPreferTheirsOverOurs` before retrying:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'   -- ← called when beyond forecast horizon
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

`checkPreferTheirsOverOurs` decides whether to keep the connection or throw `CandidateTooSparse`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        emptyPerasWeightSnapshot   -- ⚠ always zero — ignores all Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

The `emptyPerasWeightSnapshot` constant contains no boosted blocks at all. The comparison therefore degrades to a pure block-count comparison, identical to pre-Peras behaviour. The actual chain-selection path (`chainSelectionForBlock`) correctly reads the live snapshot from the ChainDB:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/ChainDB/Impl/ChainSel.hs
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)  -- ✓ real weights
```

The discrepancy between the two call sites is the root cause. The in-code TODO acknowledges the problem but does not fix it:

```haskell
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
emptyPerasWeightSnapshot
```

---

### Impact Explanation

Under Peras, a chain with fewer blocks can be *heavier* than a longer chain because Peras certificates add weight boosts to specific blocks. `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls back to block-count comparison only. This produces two wrong outcomes:

1. **False disconnection (security-critical):** A peer offers a chain that is shorter by block count but heavier by Peras weight (the canonical chain under Peras). `preferAnchoredCandidate` with empty weights returns `ShouldNotSwitch` → the node throws `CandidateTooSparse` and disconnects. The node loses its only path to the heavier chain.

2. **False continuation:** A peer offers a chain that is longer by block count but lighter by Peras weight. `preferAnchoredCandidate` with empty weights returns `ShouldSwitch` → the node keeps the connection. The node remains connected to a sub-canonical chain.

Combining both: an adversary that has produced more blocks than the honest chain (not requiring stake majority, only a temporary lead) can cause the victim node to disconnect from all honest peers offering the heavier Peras chain while staying connected to the adversary's lighter chain. Once the honest peers are gone, the node's only available chain is the adversary's, which it will eventually adopt via normal chain selection. The node ends up on a less-secure, non-canonical chain — violating Peras's core security guarantee.

---

### Likelihood Explanation

- Peras is an active extension in this codebase with production-grade certificate and vote infrastructure.
- The forecast-horizon condition is a normal network event: any peer can send headers for slots slightly ahead of the local tip, triggering this code path without any special privilege.
- The adversary needs only a temporary block-count lead over the honest chain, not a stake majority.
- The TODO comment and linked issue confirm the developers are aware the empty snapshot is incorrect here, raising the probability that the condition can be reached in practice.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` read from the ChainDB (the same snapshot already used in `chainSelectionForBlock`). The snapshot should be passed into the ChainSync client's `InternalEnv` or read atomically from the ChainDB reference, consistent with how `chainSelectionForBlock` obtains it via `Query.getPerasWeightSnapshot`.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Adversary peer connects to an honest node running Peras.
2. Adversary sends a sequence of headers for a chain that is longer by block count but lighter by Peras weight, with the tip slot beyond the current forecast horizon.
3. `projectLedgerView` returns `Nothing` → `checkPreferTheirsOverOurs` is invoked.
4. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares by block count only → `ShouldSwitch` (adversary's chain is longer) → connection kept.
5. Simultaneously, honest peers offer a chain that is shorter by block count but heavier by Peras weight, also with headers beyond the forecast horizon.
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag honestFrag` → `ShouldNotSwitch` (honest chain is shorter by block count) → `throwSTM CandidateTooSparse` → honest peers disconnected.
7. Node is now connected only to the adversary. Normal chain selection eventually adopts the adversary's lighter chain.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
