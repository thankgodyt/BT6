Audit Report

## Title
Missing Zero-Address Recipient Validation in `init_transfer` Causes Permanent Fund Loss - (File: near/omni-bridge/src/lib.rs)

## Summary
The `init_transfer` function in `near/omni-bridge/src/lib.rs` validates only that the recipient chain is not NEAR, but never checks whether the recipient address itself is zero. A user who specifies a zero address (e.g., `eth:0x0000000000000000000000000000000000000000`) causes tokens to be immediately locked or burned on NEAR, after which the MPC signs a payload committing to that zero-address recipient. On the EVM side, native ETH sent to `address(0)` is permanently burned, while ERC-20/bridge-token `finTransfer` calls revert on every relay attempt, permanently freezing the NEAR-side funds with no recovery path.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

No zero-address check follows. The zero-address recipient is stored verbatim in `TransferMessage`: [2](#0-1) 

It is then embedded into `TransferMessagePayload` and submitted to the NEAR MPC for signing: [3](#0-2) 

The utility method `is_zero()` already exists on `OmniAddress` in `near/omni-types/src/lib.rs` and covers all supported chain types, but is never called in `init_transfer`: [4](#0-3) 

On the EVM side, `finTransfer` in `OmniBridge.sol` has no zero-address guard on `payload.recipient`. For native ETH (`tokenAddress == address(0)`), the low-level call to `address(0)` succeeds silently, permanently burning the ETH: [5](#0-4) 

For ERC-20 and bridge tokens, OpenZeppelin's `_transfer`/`_mint` revert on a zero-address recipient. Because `completedTransfers[payload.destinationNonce] = true` is written before the token transfer and the entire transaction reverts on failure, the nonce is never consumed: [6](#0-5) 

Every subsequent relay attempt also reverts, leaving the NEAR-side funds permanently frozen with no cancellation or refund mechanism reachable by the user.

## Impact Explanation
This matches the Critical allowed impact: **permanent freezing or loss of bridged funds**. For native ETH the loss is a direct, irreversible burn. For ERC-20/bridge tokens the funds are permanently frozen on NEAR because `finTransfer` will revert on every relay attempt and no user-accessible recovery path exists in the NEAR bridge contract.

## Likelihood Explanation
Any unprivileged user can trigger this through a standard `ft_transfer_call` with a zero-address recipient in the `InitTransferMsg`. No special role, admin access, or external dependency failure is required. A single malformed (or malicious) call is sufficient, and the condition is repeatable for any token and any amount.

## Recommendation
Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipient.as_ref()  // add this error variant
);
```

The `is_zero()` method already exists on `OmniAddress` and covers all supported chain types including EVM, Solana, Starknet, Bitcoin, and Zcash variants. [4](#0-3) 

## Proof of Concept
1. Attacker holds 1 wETH (NEP-141) on NEAR.
2. Attacker calls `ft_transfer_call` on the wETH token contract targeting the NEAR bridge with `msg`:
   ```json
   {"InitTransfer": {"recipient": "eth:0x0000000000000000000000000000000000000000", "fee": "0", "native_token_fee": "0"}}
   ```
3. `ft_on_transfer` → `init_transfer` passes the chain-kind check (Eth ≠ Near) and stores the transfer with `recipient = OmniAddress::Eth(H160::ZERO)`. The 1 wETH is locked/burned on NEAR.
4. A relayer calls `sign_transfer`; the NEAR MPC signs a `TransferMessagePayload` with `recipient = 0x0000000000000000000000000000000000000000`.
5. The relayer calls `finTransfer` on the EVM `OmniBridge` with the signed payload:
   - **ERC-20 path**: `safeTransfer(address(0), amount)` or `mint(address(0), amount)` reverts. The transaction reverts before `completedTransfers` is durably set, so the nonce is never consumed. Every subsequent relay attempt also reverts. The 1 wETH equivalent is permanently frozen on NEAR.
   - **Native ETH path**: `address(0).call{value: amount}("")` succeeds silently. ETH is permanently burned.
6. No user-accessible cancellation or refund function exists in the NEAR bridge contract to recover the locked/burned tokens.
