### Title
Permissionless `request_refund` Allows Attacker to Register Attacker-Controlled BTC Address for Deposits with `refund_address: None`, Locking User Funds and Enabling Potential Theft — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a permissionless entrypoint. When a user's `DepositMsg` has `refund_address: None`, any unprivileged NEAR account can call `request_refund` on behalf of that deposit and supply an **attacker-controlled BTC address** as the refund destination. This locks the victim's BTC in a pending refund state for up to 14 days (`unsafe_refund_timelock_sec`), blocks the victim from registering their own refund request (duplicate-key guard), and — if the DAO fails to reject within the timelock — causes the BTC to be sent to the attacker's address.

---

### Finding Description

`DepositMsg.refund_address` is an optional field. [1](#0-0) 

When a user generates a deposit address with `refund_address: None`, the deposit path (and therefore the on-chain BTC address) is derived from the full `DepositMsg` hash. [2](#0-1) 

`request_refund` has no caller-identity check. The only guard on the `refund_address` parameter is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None`, this block is skipped entirely, and **any caller-supplied `refund_address` is accepted without restriction**. The callback then stores it verbatim:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker-supplied address
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [4](#0-3) 

Once a `RefundRequest` exists for a UTXO, a second `request_refund` for the same UTXO is rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [5](#0-4) 

This means the victim cannot overwrite the attacker's entry with their own BTC address.

When `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` always applies `unsafe_refund_timelock_sec` (default: 14 days), even for privileged callers:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [6](#0-5) 

After 14 days, `execute_refund` is permissionless and builds a PSBT paying `refund_amount` to the attacker's address: [7](#0-6) 

The `finalize_refund_with_psbt` function then marks the UTXO as verified (blocking any future `verify_deposit`) and creates the pending BTC transaction to the attacker's address. [8](#0-7) 

---

### Impact Explanation

**Primary (Medium):** An attacker can lock any user's BTC deposit (where `deposit_msg.refund_address` is `None` and `verify_deposit` was never called) for up to 14 days, blocking the victim from registering their own refund request and forcing mandatory DAO intervention. This matches the allowed impact: *"Attacker-triggered temporary locking of bridged funds."*

**Secondary (Critical):** If the DAO fails to call `reject_refund` within `unsafe_refund_timelock_sec`, `execute_refund` sends the victim's BTC to the attacker's address. This matches: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

- `DepositMsg` contents (including `refund_address: None`) are emitted as on-chain NEAR events via `Event::LogDepositAddress` when the user calls `get_user_deposit_address`. [9](#0-8)  The attacker can trivially reconstruct the exact `deposit_msg`.
- The BTC deposit transaction is public on the Bitcoin blockchain.
- The attacker's only cost is 2 NEAR (non-refundable anti-spam fee). [10](#0-9)  For any non-trivial BTC deposit, this cost is negligible.
- The scenario where `verify_deposit` is never called (relayer downtime, user changed mind) is explicitly the intended use-case for `request_refund`, making it a realistic target.
- The DAO's ability to reject is a mitigation, not a fix — it requires continuous monitoring and timely action across a 14-day window.

---

### Recommendation

Restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (the intended NEAR recipient of the nBTC) can supply the `refund_address` parameter. Add a caller-identity check:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can supply a refund address when none is pre-authorized"
    );
}
```

Alternatively, require that `refund_address` must always be pre-committed in `deposit_msg.refund_address` at deposit time, and reject `request_refund` calls where `deposit_msg.refund_address` is `None`.

---

### Proof of Concept

1. Alice generates a deposit address with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The `DepositMsg` is emitted as a NEAR event.
2. Alice sends 1 BTC to the derived deposit address. The BTC transaction is confirmed on-chain.
3. The relayer goes offline; `verify_deposit` is never called.
4. Attacker observes the NEAR event, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None },
     refund_address = "attacker_btc_address",
     tx_bytes = <Alice's BTC tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   with 2 NEAR attached.
5. `request_refund_callback` verifies the tx output matches the deposit address (it does, since the correct `deposit_msg` was used) and stores `RefundRequest { refund_address: "attacker_btc_address", ... }`.
6. Alice tries to call `request_refund` with her own BTC address — it fails: `"Refund request already exists for this UTXO"`.
7. After 14 days, attacker (or anyone) calls `execute_refund`. The bridge builds and signs a BTC transaction paying Alice's 1 BTC to `attacker_btc_address`.
8. Alice's BTC is stolen. The DAO's only recourse was to call `reject_refund` within the 14-day window. [11](#0-10) [12](#0-11) [13](#0-12)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"

            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )

            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
