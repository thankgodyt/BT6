### Title
Unauthenticated `request_refund` Allows Attacker to Redirect Any User's BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` does not verify that the caller is the `recipient_id` named in the supplied `deposit_msg`. When `deposit_msg.refund_address` is `None`, the caller freely supplies any `refund_address`. Because the `deposit_msg` (including `recipient_id`) is publicly emitted in a NEAR event by `get_user_deposit_address`, and the underlying BTC transaction is public on-chain, an unprivileged attacker can reconstruct a victim's `deposit_msg`, call `request_refund` with their own BTC address, wait out the `unsafe_refund_timelock_sec`, and call `execute_refund` to steal the victim's BTC.

### Finding Description
`get_user_deposit_address` emits a `LogDepositAddress` event that includes the full `deposit_msg` (with `recipient_id`): [1](#0-0) 

`request_refund` accepts a caller-supplied `refund_address` with no check that `env::predecessor_account_id()` equals `deposit_msg.recipient_id`: [2](#0-1) 

Inside `request_refund_callback`, the only address-binding check is: if `deposit_msg.refund_address` is already set, the caller's `refund_address` argument must match it. When it is `None`, the caller's value is stored verbatim: [3](#0-2) [4](#0-3) 

`execute_refund` is also publicly callable (no `#[trusted_relayer]` on the function itself, unlike `verify_refund_finalize` and `remove_refund_pending_tx_id` which carry the attribute explicitly): [5](#0-4) 

The only mitigation is a longer `unsafe_refund_timelock_sec` that gives DAO/Operator time to reject, but this is a weak operational control, not a cryptographic or authorization guarantee: [6](#0-5) 

### Impact Explanation
An attacker who successfully executes this attack receives the victim's BTC at their own address. The victim's deposit is permanently lost: the UTXO is marked in `verified_deposit_utxo` by `finalize_refund_with_psbt`, blocking any future `verify_deposit` for the same UTXO: [7](#0-6) 

This constitutes **Critical** impact: significant theft of user funds (BTC) with no recovery path once the refund transaction is signed and broadcast.

### Likelihood Explanation
All inputs needed for the attack are public:
- The victim's `deposit_msg` (including `recipient_id`) is emitted on-chain by `get_user_deposit_address`.
- The BTC transaction bytes and Merkle proof are observable on the Bitcoin blockchain.
- The attacker only needs to attach a small NEAR storage deposit and wait for `unsafe_refund_timelock_sec`.

The attack is blocked only if the DAO/Operator actively monitors and calls `reject_refund` within the timelock window. If monitoring lapses or the timelock expires unnoticed, the attack succeeds unconditionally. Likelihood is **Medium** (requires an unfinalized deposit and operator inaction, but both conditions arise naturally during relayer downtime or below-minimum deposits).

### Recommendation
Bind the refund request to the caller's identity. Require `env::predecessor_account_id() == deposit_msg.recipient_id` inside `request_refund` (or inside `request_refund_callback` where the `deposit_msg` is already validated against the on-chain UTXO). Alternatively, require that `deposit_msg.refund_address` is always pre-committed (non-`None`) so the refund destination is fixed at deposit time and cannot be overridden by an arbitrary caller.

### Proof of Concept
1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The event `LogDepositAddress` is emitted, revealing her exact `deposit_msg`.
2. Alice sends BTC to the returned deposit address. The relayer fails to call `verify_deposit` (e.g., deposit is below `min_deposit_amount`, triggering `unavailable_utxo_callback` instead of minting, or the relayer is simply offline).
3. Attacker reads Alice's `deposit_msg` from the NEAR event log and the BTC transaction from the Bitcoin blockchain.
4. Attacker calls `request_refund(deposit_msg=alice_msg, refund_address="attacker_btc_addr", tx_bytes=..., vout=..., proof=...)` with sufficient NEAR attached. The Light Client validates the proof; `request_refund_callback` stores the request with `refund_address = "attacker_btc_addr"`.
5. After `unsafe_refund_timelock_sec` elapses (and assuming DAO/Operator did not call `reject_refund`), attacker calls `execute_refund(utxo_storage_key=...)`.
6. `finalize_refund_with_psbt` builds a BTC PSBT paying `refund_amount` to `"attacker_btc_addr"`, initiates MPC signing, and marks the UTXO as verified — permanently blocking Alice from ever recovering her BTC via `verify_deposit`.
7. Once the MPC-signed transaction is broadcast and confirmed, Alice's BTC is irreversibly transferred to the attacker.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())

                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
