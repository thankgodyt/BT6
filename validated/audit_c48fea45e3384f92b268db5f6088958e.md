### Title
Unconditional Peras Certificate Acceptance Allows Unprivileged Peer to Manipulate Chain Selection Weight - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic validation. An unprivileged peer can send crafted `PerasCert` objects with arbitrary round numbers and boosted block points over the Peras cert diffusion mini-protocol. These certificates are stored in the `PerasCertDB` and contribute weight boosts to chain selection, allowing an attacker to make an honest node prefer a non-canonical adversarial chain.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate for accepting inbound Peras certificates. The sole production instance — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — implements this method as an unconditional stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is invoked directly in both inbound certificate processing paths. `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` both pass `validatePerasCert mkPerasParams` as the validation function to `processCerts`: [2](#0-1) 

`processCerts` calls `validateCert <$> certsNotAlreadyInDb` and, if all results are `Right`, adds every certificate to the database: [3](#0-2) 

Once stored, the certificate's boost is incorporated into the `PerasWeightSnapshot` used by chain selection. `chainSelSync` processes inbound certs and triggers `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection compares candidates using `WeightedSelectView`, where `wsvTotalWeight = blockNo + weightBoost`. A fraudulent certificate inflates the weight of an adversarial fork's block, potentially causing the honest node to switch to it: [5](#0-4) 

The Peras cert diffusion mini-protocol is wired into the node-to-node stack and is reachable by any connecting peer: [6](#0-5) 

No quorum proof, no aggregate signature, no round-number bounds, and no boosted-block existence check are performed. The `PerasCert` data type carries only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk`, both of which are attacker-controlled: [7](#0-6) 

---

### Impact Explanation

**High / Critical — Chain selection manipulation via unauthorized certificate acceptance.**

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` naming any block on a minority or adversarial fork as the boosted block.
2. Send it over the Peras cert diffusion channel.
3. The receiving node accepts it unconditionally, stores it, and adds its boost to the `PerasWeightSnapshot`.
4. Chain selection now sees the adversarial fork as having higher total weight (`blockNo + fraudulent boost`) than the honest chain.
5. The honest node switches to the adversarial fork, accepting an invalid or attacker-controlled chain.

This directly violates the Peras security model, which requires that only certificates backed by a quorum of stake-weighted committee votes can boost a block. The bypass maps to: **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**, and **bypass of Peras certificate checks that enables unauthorized certificate acceptance**.

---

### Likelihood Explanation

**Medium-High.** The Peras cert diffusion mini-protocol is active whenever Peras is enabled. Any peer that can establish a node-to-node connection can send crafted certificates. No stake, keys, or privileged access are required. The only precondition is that Peras is enabled in the node's configuration, which is the intended production state once Peras is deployed.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:

1. The certificate's aggregate BLS signature over `(roundNo, boostedBlock)` using the committee's aggregate verification key.
2. That the round number falls within the valid acceptance window (not expired per `perasCertMaxRounds`).
3. That the boosted block point is structurally valid (non-genesis, within the volatile window).
4. That the quorum threshold is met by the signers' combined stake.

Until a full implementation is available, inbound certificates from peers should be rejected at the diffusion layer when Peras is enabled, rather than accepted unconditionally. The existing `PerasValidationErr` type and `processCerts` rejection path are already in place to support this. [8](#0-7) 

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to an honest node with Peras enabled.
2. Peer sends via the Peras cert diffusion channel a `PerasCert` with:
   - `pcCertRound = <current round>`
   - `pcCertBoostedBlock = <tip of adversarial fork>`
3. `makePerasCertPoolWriterFromChainDB` → `processVotes` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
4. `ChainDB.addPerasCertAsync` enqueues the cert; `chainSelSync` processes it.
5. `PerasCertDB.addCert` stores it; `getWeightSnapshot` now returns a snapshot boosting the adversarial block.
6. `chainSelectionForBlock` is triggered for the boosted block; `constructPreferableCandidates` computes `WeightedSelectView` with inflated `wsvWeightBoost`.
7. `preferAnchoredCandidate` returns `ShouldSwitch`; the honest node adopts the adversarial chain. [9](#0-8)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight
-- could be cached, but then we need to be careful to maintain the invariant
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker
      ]

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of
        ShouldSwitch r -> ShouldSwitch (WeightedSelectViewTiebreak r)
        ShouldNotSwitch o -> ShouldNotSwitch o
