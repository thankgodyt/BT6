### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural checks. This function is called directly in the live object-diffusion inbound path (`makePerasCertPoolWriterFromChainDB`) when processing Peras certificates received from unprivileged peers. As a result, any peer can inject arbitrary, structurally invalid, or forged Peras certificates into the node's `ChainDB`, causing those certificates to apply their chain-selection boost weight to attacker-chosen blocks.

---

### Finding Description

`BlockSupportsPeras` defines the interface for Peras certificate and vote validation. A degenerate catch-all instance is provided for all `StandardHash blk` types:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This implementation **always returns `Right`** regardless of the certificate's content. No signature is verified, no round number is checked against the current epoch, no boosted-block point is validated against the chain, and no committee membership is confirmed. [1](#0-0) 

This stub is wired directly into the production inbound certificate processing path. `makePerasCertPoolWriterFromChainDB` constructs the `ObjectPoolWriter` used by the object-diffusion mini-protocol to handle certificates arriving from peers, and it passes `validatePerasCert mkPerasParams` as the validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each certificate not already in the database. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

The same stub is used in `makePerasCertPoolWriterFromCertDB`: [4](#0-3) 

The `ValidatedPerasCert` produced by the stub carries `vpcCertBoost = perasWeight params`, which is the weight applied to the boosted block during chain selection. A certificate accepted into the `ChainDB` therefore directly influences which chain the node considers canonical. [5](#0-4) 

The analog to the external report is direct: just as the PixelSwap settlement contract never validates the `exec_id` fields of nested `PlaceOrder` messages—allowing orders to be routed to and processed by the wrong pool—the Ouroboros consensus layer never validates the cryptographic or structural fields of inbound Peras certificates, allowing any peer to have arbitrary certificates accepted and applied to chain selection.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block on any fork. Because `validatePerasCert` accepts it unconditionally, the certificate is stored in the `ChainDB` and its `perasWeight` boost is applied to the attacker-chosen block during chain selection. This allows a peer with no stake and no committee membership to make an honest node prefer a non-canonical or adversarially-chosen chain, violating the Peras protocol's security assumption that only legitimately elected committee members can issue valid certificates.

This falls under: **Critical — Bypass of Peras certificate/vote verification checks that enables unauthorized certificate acceptance**, and **High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is a live network-facing component. Any connected peer can send a batch of `PerasCert` objects. The only gate before `validatePerasCert` is a deduplication check (`Set.member roundNo certIds`), which is trivially bypassed by using a fresh `pcCertRound` value. No authentication, stake proof, or signature is required to reach this code path.

---

### Recommendation

- **Short term:** Replace the stub `validatePerasCert` implementation with one that performs at minimum: (1) signature verification against the committee's aggregate verification key, (2) round-number range checks against the current epoch, and (3) verification that `pcCertBoostedBlock` refers to a known block on a plausible chain. Until real validation is in place, the inbound certificate path should reject all certificates rather than accept all of them.
- **Long term:** Complete the HFC plumbing referenced in the TODO comments (cardano-peras issue #73 and #120) so that `validatePerasCert` is dispatched to the era-specific implementation that performs full committee-based cryptographic verification, mirroring the complete `implVerifyCert` logic already present in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Committee.EveryoneVotes`.

---

### Proof of Concept

1. Connect to a target node that has the Peras object-diffusion mini-protocol enabled.
2. Construct a `PerasCert blk` with `pcCertRound = <any fresh round number>` and `pcCertBoostedBlock = <point of an adversarially chosen block on a minority fork>`.
3. Send the certificate via the object-diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` without inspecting any field of `cert`.
5. The certificate passes the `([], validatedCerts)` branch and is forwarded to `ChainDB.addPerasCertAsync`.
6. The ChainDB stores the certificate and applies `perasWeight` as a chain-selection boost to the attacker-specified block, causing the node to prefer the adversarial fork over the honest canonical chain. [6](#0-5) [7](#0-6)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
