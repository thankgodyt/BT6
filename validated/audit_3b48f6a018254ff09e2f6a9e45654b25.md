### Title
Peras Certificate Verification Bypass via Unconditional `Right` Stub Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance ships a `validatePerasCert` implementation that unconditionally returns `Right` for every inbound certificate, performing no cryptographic, quorum, or committee membership checks. This stub is wired directly into the production inbound certificate handler (`processCerts`) used by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`. Any unprivileged peer connected via the Peras certificate diffusion miniprotocol can send a crafted `PerasCert` naming an arbitrary block, have it accepted as "validated," and trigger chain selection with a Peras weight boost of 15 blocks, causing the victim node to prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

The universal instance at `SupportsPeras.hs:320` covers every `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature over the certificate body is verified, no quorum threshold is checked, no committee membership is confirmed. Every `PerasCert` value, regardless of content, is wrapped in `Right ValidatedPerasCert`.

**Production wiring — stub used in both inbound pool writers:**

`makePerasCertPoolWriterFromChainDB` (the production path) passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`makePerasCertPoolWriterFromCertDB` (used in tests but also wired in) has the same stub: [3](#0-2) 

**`processCerts` — the inbound handler:**

`processCerts` filters out certs already in the DB by round number, then calls `validateCert` on the remainder. Because `validateCert` is the stub, every new-round cert passes:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

**Chain selection consequence:**

`addPerasCertAsync` enqueues the accepted cert into the `ChainSelQueue`. `chainSelSync` then looks up the cert's `pcCertBoostedBlock` in the VolatileDB and, if found, calls `chainSelectionForBlock` for it: [5](#0-4) 

The Peras weight boost applied is `perasWeight mkPerasParams = PerasWeight 15`, meaning the boosted block is treated as if it has 15 additional blocks of chain weight: [6](#0-5) 

**Network entry point:**

The pool writer is wired into the node-to-node miniprotocol handler as `hPerasCertDiffusionClient`, which calls `objectDiffusionInbound` → `opwAddObjects` → `processCerts`: [7](#0-6) 

Any peer that the node connects to (or that connects to the node) can send crafted `PerasCert` messages through this miniprotocol.

### Impact Explanation

**Severity: High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

A peer sends a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's VolatileDB (e.g., a block on a minority fork). The cert is accepted without any verification, stored in `PerasCertDB`, and triggers chain selection. The boosted block gains 15 blocks of extra weight. If the minority fork plus 15 weight units exceeds the honest chain's weight, the node switches to the minority fork. An attacker controlling multiple peers can send certs for successive rounds, each boosting a different block on the adversarial fork, compounding the weight advantage. This directly violates the Peras security assumption that only a quorum of legitimate committee members can produce a valid certificate.

### Likelihood Explanation

**High.** The entry point is the standard Peras certificate diffusion miniprotocol, reachable by any peer the node connects to. No keys, stake, or operator access are required. The only constraint is that the boosted block must already be in the node's VolatileDB, which is trivially satisfied by sending the block first via the normal block diffusion protocol. The `TODO` comments and the linked issue (`cardano-peras/issues/120`) confirm this is a known incomplete stub shipped in production code, not a test-only path.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate carries a valid aggregate signature from a quorum of eligible committee members.
2. Each signing member's eligibility is confirmed against the stake distribution / committee selection data for the relevant Peras round.
3. The boosted block point is consistent with the round number.

Until real validation is implemented, the inbound certificate handler should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them, to prevent exploitation of the stub in a deployed network.

### Proof of Concept

1. Attacker node connects to victim via the Peras cert diffusion miniprotocol (`hPerasCertDiffusionClient`).
2. Attacker first diffuses a valid block `B_adv` on a minority fork via block fetch; `B_adv` lands in the victim's VolatileDB.
3. Attacker sends a `PerasCert { pcCertRound = r, pcCertBoostedBlock = pointOf(B_adv) }` for any round `r` not yet in the victim's `PerasCertDB`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`.
5. The cert is stored in `PerasCertDB`; `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
6. `chainSelSync` finds `B_adv` in the VolatileDB, calls `chainSelectionForBlock` with the 15-block weight boost applied to `B_adv`'s chain.
7. If `B_adv`'s chain length + 15 > honest chain length, the victim switches to the adversarial fork.
8. Repeat with new round numbers to maintain the boost across epochs.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
