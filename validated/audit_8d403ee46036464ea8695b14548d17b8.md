Audit Report

## Title
`HyperliquedBridgeToken.mint(address,uint256,bytes)` Unconditionally Redirects All Minted Tokens to `_systemAddress`, Causing Permanent Loss of Bridged Funds — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

The 3-arg `mint` override in `HyperliquedBridgeToken` unconditionally mints tokens to `account` and then immediately transfers the full amount to `_systemAddress`, leaving the recipient with zero tokens. `OmniBridge.finTransfer` dispatches to this 3-arg path whenever `payload.message.length > 0`, regardless of whether the message encodes a HyperCore instruction or any other bridge-level data. Any inbound cross-chain transfer to a `HyperliquedBridgeToken` that carries a non-empty `message` field results in permanent, irreversible loss of the bridged amount for the recipient.

## Finding Description

`OmniBridge.finTransfer` branches on `isBridgeToken[payload.tokenAddress]` and then on `payload.message.length`: [1](#0-0) 

When `message.length > 0`, the 3-arg `IBridgeToken.mint` is called with `payload.message` as the third argument. The `HyperliquedBridgeToken` override of that signature is: [2](#0-1) 

The `bytes memory` parameter is unnamed and never read. `_mint(account, value)` (OpenZeppelin ERC-20) calls `_update(address(0), account, value)`, crediting `account` with `value`. The immediately following `_update(account, _systemAddress, value)` transfers that same `value` out of `account` to `_systemAddress`. Net effect on `account`: **+value − value = 0**. `_systemAddress` silently absorbs the full bridged amount.

The contract's own NatSpec documents the two-path design intent: [3](#0-2) 

The 3-arg path is designed exclusively for HyperCore spot-balance parking, but `OmniBridge` invokes it for **any** non-empty `message` — a completely different semantic. The `bytes memory message` argument, which carries `payload.message`, is never decoded or inspected; the redirect to `_systemAddress` is unconditional.

Tokens parked at `_systemAddress` can only be released via `coreReceiveWithData`, which is gated to `msg.sender == _systemAddress`: [4](#0-3) 

The Hyperliquid system precompile only invokes `coreReceiveWithData` in response to a legitimate HyperCore `sendToEvmWithData` event. Tokens incorrectly parked there due to a NEAR→HyperEVM transfer with a non-empty message have no recovery path; they are permanently inaccessible to the intended recipient.

The `onlyOwner` guard on `mint` is satisfied because `OmniBridge` is set as owner during `initialize` via `__Ownable_init(_msgSender())`: [5](#0-4) 

## Impact Explanation

This is a **Critical** impact matching "loss or permanent freezing of bridged funds across NEAR, EVM flows." Every inbound transfer to a `HyperliquedBridgeToken` with `payload.message.length > 0` results in:

1. `totalSupply` increasing correctly (tokens are minted).
2. The full minted amount being transferred to `_systemAddress` instead of the recipient.
3. The recipient receiving zero tokens with no recourse.

Funds are not burned but are permanently inaccessible to the recipient, constituting irreversible loss of bridged assets.

## Likelihood Explanation

The trigger condition — `payload.message.length > 0` — is a standard, user-initiated feature of the bridge (cross-chain DeFi callbacks, memos, any bridge-level metadata). No attacker capability is required beyond initiating a normal bridge transfer from NEAR with a non-empty `message` field. The NEAR bridge MPC key signs the full payload including `message`, so a valid signature over such a payload is obtainable through the normal bridge flow. A legitimate relayer submitting a legitimately signed payload is sufficient to trigger the loss. The condition is repeatable for every such transfer.

## Recommendation

The 3-arg `mint` in `HyperliquedBridgeToken` must not unconditionally redirect tokens to `_systemAddress`. Two concrete options:

1. **Revert on direct bridge calls**: Override the 3-arg `mint` to `revert`, forcing all `finTransfer` paths through the 2-arg mint (tokens delivered directly to the recipient on HyperEVM). Handle HyperCore parking exclusively through `coreReceiveWithData`.

2. **Decode the message to determine routing**: Inspect the `bytes memory message` argument. Apply the `_systemAddress` redirect only when the message encodes a recognized HyperCore-specific instruction (e.g., a leading action byte matching `ACTION_TRANSFER` or `ACTION_INIT_TRANSFER`); otherwise fall through to a plain `_mint(account, value)`.

## Proof of Concept

```solidity
// 1. Deploy HyperliquedBridgeToken with a non-zero _systemAddress (e.g. address(0xSYS))
// 2. Register it in OmniBridge: isBridgeToken[token] = true, customMinters[token] = address(0)
//    (via addCustomToken with customMinter = address(0), or deployToken with HlBridgeToken impl)
// 3. Obtain a valid nearBridgeDerivedAddress ECDSA signature over a TransferMessagePayload
//    where payload.message = bytes("\x00")  (length == 1 > 0)
// 4. Call OmniBridge.finTransfer(sig, payload)
//    → isBridgeToken branch, message.length > 0
//    → IBridgeToken(token).mint(recipient, amount, "\x00")
//    → _mint(recipient, amount)                        // recipient balance = amount
//    → _update(recipient, _systemAddress, amount)      // recipient balance = 0
// 5. Assert:
assert(token.balanceOf(recipient)      == 0);
assert(token.balanceOf(_systemAddress) == amount);
// 6. Confirm no recovery path: coreReceiveWithData requires msg.sender == _systemAddress,
//    which is the Hyperliquid system precompile — it will not spontaneously release
//    tokens that were incorrectly parked by a NEAR→HyperEVM transfer.
```
