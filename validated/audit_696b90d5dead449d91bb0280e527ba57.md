### Title
Fee Calculation Truncates in Protocol's Disfavor Due to Integer Division Rounding - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`BridgeFee::get_fee` and `BridgeFee::get_protocol_and_relayer_fee` both use Rust integer division, which truncates toward zero (rounds down). Both divisions round in the user's/relayer's favor rather than the protocol's favor. Every deposit and withdrawal triggers this path, causing the protocol to systematically under-collect fees.

### Finding Description
In `contracts/satoshi-bridge/src/config.rs`, the two fee helpers are:

```rust
// line 30-35
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),  // truncates
        self.fee_min,
    )
}

// line 37-41
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO); // truncates
    let relayer_fee = fee_amount - protocol_fee;   // relayer absorbs the remainder
    (protocol_fee, relayer_fee)
}
``` [1](#0-0) 

`MAX_RATIO = 10000`. Integer division of `amount * fee_rate` by `10000` discards the remainder, so the computed fee is always `≤` the mathematically exact fee. The maximum per-call shortfall is `9999 / 10000 < 1 satoshi`, i.e. up to **1 satoshi per call** is silently dropped.

Both helpers are called on every standard deposit:

```rust
// btc_light_client/deposit.rs lines 52-56
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
``` [2](#0-1) 

And `get_fee` is called again on every withdrawal (confirmed by `api/token_receiver.rs` and `nbtc/burn.rs` grep hits). Each call can silently drop up to 1 satoshi of fee revenue.

### Impact Explanation
Two compounding shortfalls occur per deposit:

1. **`get_fee` truncation** — `deposit_fee` is up to 1 satoshi too low → `mint_amount` is up to 1 satoshi too high → user receives slightly more nBTC than the deposited BTC strictly warrants.
2. **`get_protocol_and_relayer_fee` truncation** — `protocol_fee` is up to 1 satoshi too low → `relayer_fee` absorbs the remainder → the protocol treasury is shorted again.

Over `n` deposits the protocol can be short by up to `2n` satoshis in fee revenue. For withdrawals, the same `get_fee` truncation means the user burns slightly less nBTC in fees than intended, and the bridge sends slightly more BTC than the fee schedule requires. This is a publicly reachable, systematic invariant violation: the nBTC minted per deposit can exceed the fee-adjusted BTC backing by up to 1 satoshi per transaction, and the protocol fee ledger is understated by up to 1 satoshi per transaction.

**Impact level: Low** — no direct theft, but a reachable accounting invariant is violated on every bridge operation.

### Likelihood Explanation
Every standard deposit and every withdrawal exercises both functions. The shortfall is deterministic and accumulates monotonically with transaction volume. No special conditions or attacker setup are required; any ordinary bridge user triggers it.

### Recommendation
Replace floor division with ceiling division for all fee computations so rounding favors the protocol:

```rust
// ceiling division: (a * b + denominator - 1) / denominator
pub fn get_fee(&self, amount: u128) -> u128 {
    let numerator = amount * u128::from(self.fee_rate);
    let denom = u128::from(MAX_RATIO);
    std::cmp::max(
        (numerator + denom - 1) / denom,
        self.fee_min,
    )
}

pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let denom = u128::from(MAX_RATIO);
    let protocol_fee = (fee_amount * u128::from(self.protocol_fee_rate) + denom - 1) / denom;
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
```

This ensures the protocol never collects less than the exact fee, mirroring the fix applied in HomoraBank PR#95.

### Proof of Concept

**Deposit scenario** — `fee_rate = 9999`, `protocol_fee_rate = 5000`, `deposit_amount = 10_001` satoshis:

| Step | Exact value | Truncated (current) | Shortfall |
|---|---|---|---|
| `get_fee(10_001)` | 9999.9999 | **9999** | 1 sat |
| `mint_amount` | 1.0001 | **2** | user gets +1 sat nBTC |
| `get_protocol_and_relayer_fee(9999)` protocol share | 4999.5 | **4999** | 1 sat to relayer |

After `n` such deposits the protocol treasury is short up to `n` satoshis from the `get_fee` truncation and up to `n` additional satoshis from the `get_protocol_and_relayer_fee` truncation, while the outstanding nBTC supply exceeds the fee-adjusted BTC backing by up to `n` satoshis — a publicly reachable, monotonically growing invariant violation requiring no privileged access.
