### Title
Silent nBTC Loss in `safe_mint` When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens into the bridge's own account **before** checking whether the recipient user account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring anything to the user. The minted tokens remain stranded in the bridge's nBTC balance, the user receives zero nBTC, and their underlying BTC deposit is permanently locked because the UTXO is already marked as verified — blocking any refund path.

---

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` executes in this order:

1. **Unconditionally** calls `self.token.internal_deposit(&self.bridge_id, amount.into())`, which increases the bridge's nBTC balance and the token's total supply by `amount`.
2. **Then** checks whether the intended recipient account exists: `if self.token.accounts.get(&account_id).is_none()`.
3. If the account is absent, returns `PromiseOrValue::Value(U128(0))` — no transfer, no revert, no event for the user.

```
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← minted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));           // ← silent zero return
    }
    ...
}
``` [1](#0-0) 

Contrast this with `mint_inner`, which **auto-registers** the account before depositing:

```
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id); // ← registers first
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
}
``` [2](#0-1) 

`safe_mint` deliberately skips auto-registration but still mints into the bridge's account first, creating the stranded-token window.

On the bridge side, once a deposit is verified the UTXO is inserted into `verified_deposit_utxo`. The refund path explicitly blocks any UTXO that has already been verified:

```
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [3](#0-2) 

So once the deposit is verified and `safe_mint` silently returns 0, the user has no self-service recovery path.

---

### Impact Explanation

- The nBTC total supply is inflated by `amount` (tokens sit in the bridge's own balance), but the user receives zero nBTC.
- The corresponding BTC UTXO is permanently marked as verified, blocking any refund request.
- The user's BTC is effectively locked until an operator manually intervenes (e.g., via the `lost_found` map or a direct transfer from the bridge's nBTC balance).
- This matches the allowed **Medium** impact: *"broken callback rollback, or stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

NEP-141 storage registration is a prerequisite that many users overlook. A user who sends BTC to the bridge address without first calling `storage_deposit` on the nBTC contract will trigger this path on every deposit. The condition is reachable by any ordinary depositor with no special privileges required.

---

### Recommendation

Apply the same auto-registration pattern used in `mint_inner`: check and register the recipient account **before** calling `internal_deposit`, or revert with a clear error if the account is absent. Alternatively, deposit directly to the recipient (not the bridge) and let the standard NEP-141 transfer handle the unregistered-account case with a proper revert so the bridge callback can detect failure and place the amount in `lost_found`.

---

### Proof of Concept

1. User sends BTC to the bridge deposit address.
2. Relayer calls `verify_deposit` / `safe_verify_deposit` on the satoshi-bridge; the bridge validates the Merkle proof and marks the UTXO in `verified_deposit_utxo`.
3. Bridge calls `nbtc.safe_mint(user_account_id, amount, msg)`.
4. `safe_mint` executes `internal_deposit(&self.bridge_id, amount)` — bridge's nBTC balance increases by `amount`, total supply increases.
5. `safe_mint` checks `self.token.accounts.get(&user_account_id)` — account absent (user never called `storage_deposit`).
6. `safe_mint` returns `U128(0)`. No transfer. No revert. No user-facing event.
7. User holds 0 nBTC. Their BTC UTXO is already in `verified_deposit_utxo`.
8. User attempts `request_refund` → rejected: *"UTXO already verified via deposit, cannot refund"*.
9. Funds are stuck; only operator action (manual transfer from bridge's nBTC balance or `lost_found` credit) can recover them.
