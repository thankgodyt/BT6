Audit Report

## Title
Uncapped User-Controlled Fee in `coreReceiveWithData` ACTION_INIT_TRANSFER Enables Near-Total Value Redirection — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`HyperliquedBridgeToken.coreReceiveWithData` decodes `fee` directly from attacker-controlled calldata and forwards it verbatim to `OmniBridge.initTransfer` with no intermediate bounds check. The only guard in `initTransfer` is `fee >= amount`, which means `fee = amount - 1` is accepted. A HyperCore user who is also a trusted NEAR relayer can set this value to redirect nearly the entire bridged amount to themselves as the fee recipient, leaving the declared recipient with 1 unit.

## Finding Description

In `coreReceiveWithData`, the `ACTION_INIT_TRANSFER` branch decodes `fee` from the `data` bytes supplied by the HyperCore user and passes it directly to `initTransfer` with no intermediate bounds check: [1](#0-0) 

The only fee guard lives in `OmniBridge.initTransfer`: [2](#0-1) 

`fee >= amount` rejects equality but `fee = amount - 1` satisfies `fee < amount` and passes. The resulting `InitTransfer` event carries `fee = amount - 1`: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` denormalizes the fee from the event and constructs a `TransferMessage` where `fee.fee = amount - 1`: [4](#0-3) 

In `process_fin_transfer_to_near`, when no fast transfer is in progress, the `fee_recipient` is set to `predecessor_account_id` (the relayer): [5](#0-4) 

The recipient receives `amount_without_fee() = amount - fee = 1`: [6](#0-5) 

The fee (`amount - 1`) is then minted or transferred to the relayer: [7](#0-6) 

`amount_without_fee()` is a simple checked subtraction with no floor: [8](#0-7) 

## Impact Explanation

This is a concrete fee mis-accounting exploit matching the allowed impact class "fee mis-accounting that changes user or protocol balances." An attacker who is both the HyperCore sender and a trusted NEAR relayer:

1. Sends `amount` tokens from HyperCore with `fee = amount - 1` and `recipient = "near:victim"`.
2. The `InitTransfer` event is accepted by `OmniBridge` (`fee < amount` passes).
3. The attacker relays the proof on NEAR via `fin_transfer`, receiving `amount - 1` tokens as the fee recipient.
4. The victim receives 1 unit.

Net: attacker recovers `amount - 1` tokens on NEAR while the victim is deprived of `amount - 1` tokens they were owed. This is direct, profitable fee mis-accounting — not mere griefing.

## Likelihood Explanation

The entry point (`sendToEvmWithData` → `coreReceiveWithData`) is a supported production path for HyperCore users. The attacker fully controls the `data` bytes including the `fee` field. The `fin_transfer` function is gated by `#[trusted_relayer]`, which requires staking NEAR and a waiting period before activation: [9](#0-8) [10](#0-9) 

The staking requirement and waiting period are configurable by the DAO and can be set to minimal values. A motivated attacker with sufficient capital can satisfy both conditions. No key compromise or privileged role beyond trusted relayer status is required. The exploit is repeatable for every transfer initiated through this path.

## Recommendation

Add an explicit fee cap in `coreReceiveWithData` before delegating to `initTransfer`. The `fee` decoded from user-supplied calldata must be validated against a protocol-defined maximum (e.g., a percentage of `amount128`) before the call reaches `OmniBridge`. At minimum, enforce `fee < amount128` at the `HlBridgeToken` layer, and ideally enforce a much stricter cap (e.g., `fee <= maxFeeBps * amount128 / 10000`). The root fix is that `coreReceiveWithData` must not blindly trust the user-supplied `fee` field.

## Proof of Concept

```solidity
// Foundry test (local fork)
function test_feeManipulation() public {
    uint256 amount = 1000e18;
    uint128 fee = uint128(amount) - 1; // amount - 1

    bytes memory data = abi.encodePacked(
        uint8(1), // ACTION_INIT_TRANSFER
        abi.encode(fee, "near:victim", "")
    );

    vm.prank(systemAddress); // msg.sender == _systemAddress passes NotSystemAddress guard
    token.coreReceiveWithData(
        attacker,
        bytes32(0),
        0,
        amount,
        0,
        data
    );
    // InitTransfer event emitted with fee = amount - 1
    // On NEAR finalization by attacker-relayer:
    //   victim receives amount_without_fee() = 1
    //   attacker-relayer receives fee = amount - 1
}
```

The call succeeds because `msg.sender == _systemAddress` passes the `NotSystemAddress` guard, `fee = amount - 1` satisfies `fee < amount` in `initTransfer`, and no other guard in `coreReceiveWithData` validates the fee magnitude. [11](#0-10) [2](#0-1)
