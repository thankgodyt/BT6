### Title
Peras Certificate Validation Unconditionally Returns `Right`, Allowing Any Peer to Inject Arbitrary Certificates into ChainDB - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The sole production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right`, meaning every Peras certificate received from any peer passes validation without any cryptographic or committee-membership check. Because `makePerasCertPoolWriterFromChainDB` wires this stub directly into the live `hPerasCertDiffusionClient` handler, an unprivileged peer can inject a certificate for any block point into the node's ChainDB, causing that block to receive the full `perasWeight` chain-selection boost.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The only `BlockSupportsPeras` instance in the codebase is the "degenerate instance for all blks to get things to compile":

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature, no committee-membership check, no quorum check — every certificate is unconditionally accepted and assigned the full `perasWeight` boost.

**This stub is called on every inbound certificate from every peer:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this callback on every new certificate; if all return `Right` (which they always do), each is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**The writer is wired into the live node-to-node handler:**

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

This handler is registered for every active node-to-node connection in both `initiator` and `initiatorAndResponder` bundles: [5](#0-4) 

**Exploit path:**

1. Adversary establishes a standard node-to-node connection.
2. Adversary sends a `PerasCert` message naming any `(PerasRoundNo, Point blk)` — including a point on an adversarial fork.
3. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert{..., vpcCertBoost = perasWeight params}` unconditionally.
4. The certificate is stored in the ChainDB via `addPerasCertAsync`.
5. Chain selection applies the `perasWeight` boost to the adversarially chosen block, potentially causing the honest node to prefer a non-canonical chain.

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.**

The `validatePerasCert` stub skips all cryptographic and committee-membership checks. Any connected peer can forge a certificate for any block and have it accepted with full `perasWeight` boost. Because Peras certificates directly influence chain selection (they are the mechanism by which Peras accelerates finality and boosts a winning block), an adversary can steer an honest node's chain selection toward an adversarial fork without holding any stake or keys.

This matches the allowed scope: *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

### Likelihood Explanation

**Medium.** The `PerasCertDiffusion` miniprotocol is unconditionally registered for every node-to-node connection. Any peer that can open a connection — no stake, no keys required — can send a crafted `PerasCert`. The only natural barrier is that Peras is not yet fully activated on mainnet; however, the handler and the stub validation are live in the production binary today.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over the certificate against the committee's public keys.
2. Checks that the claimed voters are legitimate committee members for the given round (using the actual stake distribution / committee selection data from the ChainDB).
3. Verifies that the aggregate vote stake meets the quorum threshold before accepting the certificate.

Until real validation is in place, the `hPerasCertDiffusionClient` handler should either be disabled or should reject all inbound certificates rather than silently accepting them.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
