### Title
Peras Quorum Certificate Forged via Unit Mismatch in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (populated from the raw ledger stake distribution, i.e. absolute lovelace-scale `Rational`) against `perasQuorumStakeThreshold` (a relative value, hardcoded to `3/4`). The code itself documents this unit mismatch as a `TODO`. Because any absolute ledger stake in lovelace is orders of magnitude larger than `3/4`, the threshold check always passes for any voter with any positive stake, allowing a single vote from an unprivileged peer to forge a Peras certificate and boost a block's chain weight.

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

where `stake = unPerasVoteStake voteStake` is a raw `Rational` and `quorumThreshold = 3/4`.

The code carries an explicit `TODO` warning:

> "this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

The `PerasVoteStake` assigned to a validated vote is taken directly from `PerasVoteStakeDistr` via `lookupPerasVoteStake`, which maps voter IDs to their raw ledger stake. The pool writer code confirms this:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [2](#0-1) 

The `validatePerasVote` default instance assigns the raw stake directly without normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [3](#0-2) 

This `vpvVoteStake` (absolute lovelace-scale) is then accumulated in `ptvtTotalStake` and passed to `stakeAboveThreshold` inside `votesReachQuorum` and `updateLoserVoteState`: [4](#0-3) [5](#0-4) 

Since any absolute ledger stake (e.g. `1_000_000 % 1` lovelace for 1 ADA) is vastly greater than `3/4`, `stakeAboveThreshold` returns `True` for any single vote from any voter with any positive stake. The result is that `updateCandidateVoteState` immediately transitions to `BecameWinner` and calls `forgePerasCert`, producing a `ValidatedPerasCert` with `vpcCertBoost = perasWeight = 15`. [6](#0-5) 

### Impact Explanation

A `ValidatedPerasCert` with boost weight 15 is accepted by the `ChainDB` and applied to chain selection. The boosted block gains 15 extra weight units, causing honest nodes to prefer it over competing chains. An unprivileged peer who controls any registered stake pool (even with negligible stake) can:

1. Submit a single vote for any block of their choice.
2. Trigger certificate forging on the receiving node due to the always-true quorum check.
3. Cause the node to boost that block's chain weight by 15, influencing chain selection in their favor.

This is a bypass of Peras certificate/voting checks enabling unauthorized certificate acceptance and chain selection manipulation — matching the **Critical** impact class: "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."

### Likelihood Explanation

Any peer that is a registered stake pool (a `PerasVoterId` present in the `PerasVoteStakeDistr`) can trigger this with a single well-formed vote message. No key compromise, admin access, or majority stake is required. The attack is deterministic and reproducible on any private testnet running the Peras vote diffusion miniprotocol.

### Recommendation

Normalize `PerasVoteStake` to a relative value (fraction of total committee stake) before calling `stakeAboveThreshold`, or change `stakeAboveThreshold` to accept the total stake distribution and perform normalization internally. The `TODO` comment at line 155–161 of `SupportsPeras.hs` already identifies the exact fix needed. Until normalization is implemented, the quorum check is semantically broken and must not be used in production certificate forging. [7](#0-6) 

### Proof of Concept

1. Start a private testnet with Peras vote diffusion enabled.
2. Register a stake pool with 1 lovelace of stake; obtain its `PerasVoterId`.
3. Ensure the pool's entry appears in `PerasVoteStakeDistr` with value `PerasVoteStake (1 % 1)`.
4. Send a single `PerasVote` for any target block from this pool.
5. `processVotes` → `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake (1 % 1)`.
6. `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold`: `1 % 1 >= 3/4 + 2/100` → `True`.
7. `forgePerasCert` is called; a `ValidatedPerasCert` with `vpcCertBoost = 15` is produced.
8. The ChainDB accepts the certificate and boosts the target block's chain weight by 15, causing chain selection to prefer it over honest competing chains.
