### Title
`DepositProtocolFee` permanently blocked by withdrawal-specific `min_withdraw_amount` guard in `ft_on_transfer` — (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

---

### Summary

`ft_on_transfer` applies a `min_withdraw_amount` validation to **every** incoming `ft_transfer_call` before the message type is even parsed. The `DepositProtocolFee` variant is a distinct operation that has no semantic relationship to the withdrawal minimum, yet it is silently blocked whenever the transferred amount falls below that threshold.

---

### Finding Description

In `contracts/satoshi-bridge/src/api/token_receiver.rs`, the `ft_on_transfer` entry-point unconditionally enforces the withdrawal floor before branching on the message payload:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs  (lines 29-66)
fn ft_on_transfer(
    &mut self,
    sender_id: AccountId,
    amount: U128,
    msg: String,
) -> PromiseOrValue<U128> {
    let amount = amount.into();
    require!(                                          // ← applied to ALL callers
        amount >= self.internal_config().min_withdraw_amount,
        "Invalid amount"
    );
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    ...
    match message {
        TokenReceiverMessage::DepositProtocolFee => {  // ← never reached if amount is small
            self.data_mut().acc_collected_protocol_fee += amount;
            self.data_mut().cur_available_protocol_fee += amount;
            ...
            PromiseOrValue::Value(U128(0))
        }
        TokenReceiverMessage::Withdraw { ... } => ...
    }
}
```

The `DepositProtocolFee` branch is designed to accept **any** positive amount and credit it to the protocol fee pool. The `min_withdraw_amount` guard is a withdrawal-specific policy (preventing dust withdrawals) and carries no meaning for fee deposits. Because the guard fires before the message is parsed, a `DepositProtocolFee` call with `amount < min_withdraw_amount` always panics and is rejected — the intended operation can never succeed for small amounts.

This is the direct analog of the Miniwasm `setBeforeSendHook` bug: a shared validation gate rejects a value that is perfectly valid for one of the downstream branches, making that branch permanently unreachable for that input class.

---

### Impact Explanation

**Low.** The `DepositProtocolFee` path is permanently inaccessible for amounts below `min_withdraw_amount`. Because NEAR's NEP-141 `ft_transfer_call` refunds the full amount on a panic in `ft_on_transfer`, no tokens are lost. However:

- The protocol fee pool cannot be topped up with amounts below the withdrawal floor, which may be set to tens of thousands of satoshis in production.
- Any caller (DAO, operator, or third-party integrator) relying on small fee top-ups will receive a silent rejection with no clear error distinguishing "amount too small for a withdrawal" from "amount too small for a fee deposit."
- This is a publicly reachable invariant-violation in a production bridge path without direct fund theft, matching the **Low** allowed impact tier.

---

### Likelihood Explanation

The `min_withdraw_amount` is a configurable parameter that is expected to be set to a non-trivial value (e.g., 10 000–100 000 satoshis) to prevent dust withdrawals. Any actor who calls `ft_transfer_call` with `msg = "DepositProtocolFee"` and an amount below that threshold will always hit the guard. This is a straightforward, publicly reachable call path requiring no special privileges.

---

### Recommendation

Parse the message type **before** applying amount-specific guards, and skip the `min_withdraw_amount` check for the `DepositProtocolFee` branch:

```rust
fn ft_on_transfer(...) -> PromiseOrValue<U128> {
    let amount: u128 = amount.into();
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    ...
    match message {
        TokenReceiverMessage::DepositProtocolFee => {
            // No withdrawal-floor check needed here
            ...
        }
        TokenReceiverMessage::Withdraw { ... } => {
            require!(
                amount >= self.internal_config().min_withdraw_amount,
                "Invalid amount"
            );
            ...
        }
    }
}
```

---

### Proof of Concept

1. DAO configures `min_withdraw_amount = 100_000` (satoshis).
2. Any account calls `nbtc.ft_transfer_call(bridge, 50_000, "DepositProtocolFee")`.
3. `ft_on_transfer` fires; `require!(50_000 >= 100_000)` panics immediately.
4. NEP-141 refunds the 50 000 nBTC to the caller.
5. `acc_collected_protocol_fee` and `cur_available_protocol_fee` are never incremented.
6. The `DepositProtocolFee` operation is permanently blocked for any amount below the withdrawal floor, regardless of intent. [1](#0-0) [2](#0-1)
