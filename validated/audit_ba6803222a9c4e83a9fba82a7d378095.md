Audit Report

## Title
`update_transfer_fee` Allows Fee Increase That Permanently Blocks `sign_transfer` for Tokens With Decimal Mismatch, Causing Irreversible Fund Freezing — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`update_transfer_fee` permits the sender to raise the token fee to any value strictly less than `transfer.message.amount`, with no lower bound on the remaining transferable amount. For tokens where `origin_decimals > destination_decimals` (e.g., 24-decimal NEAR tokens bridging to 18-decimal EVM tokens), setting `fee = amount - 1` leaves `amount_without_fee = 1`, which `normalize_amount` floors to `0`. Every subsequent `sign_transfer` call then panics with `InvalidAmountToTransfer`. Because the fee is monotonically increasing and no cancel or refund path exists, the sender's already-locked tokens are permanently frozen.

## Finding Description
**Root cause — `update_transfer_fee` (L399–402):**
The only constraint on the new token fee is:
```rust
require!(
    fee.fee >= current_fee.fee && fee.fee < transfer.message.amount,
    BridgeError::InvalidFee.as_ref()
);
```
This allows `fee.fee = amount - 1`, leaving `amount_without_fee = 1`. The `>=` lower bound means the fee can never be decreased; each call can only raise it.

**Normalization guard — `sign_transfer` (L475–485):**
```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```
This panics whenever `normalize_amount` returns `0`.

**Floor division — `normalize_amount` (L2784–2787):**
```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```
For `origin_decimals = 24`, `destination_decimals = 18`: `diff_decimals = 6`, so any `amount_without_fee < 1_000_000` normalizes to `0`.

**No recovery path:**
`sign_transfer_callback` (L655–658) only removes the transfer from `pending_transfers` when `fee.is_zero()`. A grep of `lib.rs` confirms no `cancel_transfer`, `admin_remove_transfer`, or refund function exists. Once the fee is set to `amount - 1`, the transfer record is permanently stuck in `pending_transfers` and the locked/burned tokens are unrecoverable.

## Impact Explanation
Permanent freezing of bridged funds. The sender's tokens are already burned or locked at `ft_transfer_call` time. After `update_transfer_fee` sets `fee = amount - 1`, every `sign_transfer` call panics, the transfer can never be finalized, and no refund path exists. This matches the critical impact class: *permanent freezing of bridged funds across NEAR/EVM flows*.

## Likelihood Explanation
NEAR native tokens use 24 decimals; EVM tokens commonly use 18 — the 6-decimal normalization gap is the standard NEAR→EVM case. Any `amount_without_fee < 10^6` (i.e., `< 1_000_000` raw units) triggers the zero-normalization. A sender who sets the fee near the maximum to maximize relayer incentive — without understanding the decimal normalization — will permanently lose their funds with no on-chain warning. The fee is monotonically increasing with no undo. Likelihood: **Medium-Low** (requires the common decimal mismatch case and a sender setting the fee near the maximum).

## Recommendation
Add a normalization check inside `update_transfer_fee` before accepting the new fee:
```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let remaining = transfer.message.amount.0
    .checked_sub(fee.fee.0)
    .near_expect(BridgeError::InvalidFee);
require!(
    Self::normalize_amount(remaining, decimals) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```
Alternatively (or additionally), add a `cancel_transfer` function that allows the sender to reclaim locked tokens when no MPC signature has yet been produced, providing a safe exit path for stuck transfers.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `destination_decimals = 18` (standard NEAR→EVM).
2. Sender calls `ft_transfer_call` with `amount = 2_000_000`, `fee = 0`. Tokens are locked; transfer enters `pending_transfers`.
3. Sender calls `update_transfer_fee(transfer_id, UpdateFee::Fee({ fee: 1_999_999, native_fee: 0 }))`. Accepted because `1_999_999 >= 0 && 1_999_999 < 2_000_000`.
4. `amount_without_fee() = 2_000_000 − 1_999_999 = 1`.
5. Relayer calls `sign_transfer`. `normalize_amount(1, Decimals { origin_decimals: 24, decimals: 18 }) = 1 / 10^6 = 0`.
6. `require!(amount_to_transfer > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Fee cannot be decreased. No cancel path exists. The 2_000_000 tokens are permanently frozen.
