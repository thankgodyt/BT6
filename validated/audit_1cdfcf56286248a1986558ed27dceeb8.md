Audit Report

## Title
Missing `token::authority` Constraint Allows Delegate to Drain Victim Token Accounts via `InitTransfer` - (File: `solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary
The `InitTransfer` Anchor account struct constrains `from` only by mint and token program, but not by owner. Because the SPL token program permits approved delegates to act as transfer authority, any attacker holding a delegate approval on a victim's token account can call `init_transfer` with the victim's account as `from` and their own signing key as `user`, locking the victim's tokens in the bridge vault and routing them to an attacker-controlled cross-chain recipient.

## Finding Description
In `InitTransfer` (lines 34–39), the `from` account is declared with only:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

There is no `token::authority = user` constraint. The `user` field (lines 60–64) is only required to be a `Signer` and a system-owned account — it is never checked to be the owner of `from`.

The downstream CPI at lines 90–102 passes `self.user` as the `authority` to `transfer_checked`:

```rust
TransferChecked {
    from: self.from.to_account_info(),
    to: vault.to_account_info(),
    authority: self.user.to_account_info(),  // attacker's key
    mint: self.mint.to_account_info(),
}
```

The SPL token program accepts `transfer_checked` when `authority` is either the token account's owner **or** an approved delegate with sufficient allowance. Because Anchor never verifies `from.owner == user.key()`, an attacker who holds a delegate approval on a victim's token account satisfies the SPL check while supplying an arbitrary `payload.recipient` cross-chain destination.

The same flaw exists in the burn path (lines 110–120) for bridged tokens, where `self.user` is passed as `authority` to `burn` with no ownership check on `from`.

The cross-chain message (lines 123–127) records `self.user.key()` as the sender and the attacker-supplied `payload.recipient` as the destination, so the attacker controls both the source of funds and the destination address.

## Impact Explanation
This is a **Critical** impact matching "Stealing, loss, double-spending, or permanent freezing of bridged funds across NEAR, EVM, Solana." An attacker can irreversibly drain a victim's token account into the bridge vault and cause the equivalent tokens to be minted or released to an attacker-controlled address on the destination chain. The victim has no recourse once the Wormhole message is emitted and finalized on the destination chain.

## Likelihood Explanation
The only precondition is that the victim has previously granted a delegate approval (`spl_token::approve`) to any keypair or program that the attacker controls or can impersonate. This is routine in Solana DeFi: DEX routers, lending protocols, and yield aggregators routinely request token approvals. The attacker needs no privileged role, no admin access, and no leaked keys — only a valid delegate approval that may have been granted for an entirely unrelated purpose. The attack is repeatable for any token account with an outstanding approval and is executable by any unprivileged external user via a standard public program call.

## Recommendation
Add `token::authority = user` to the `from` account constraint in `InitTransfer`:

```rust
#[account(
    mut,
    token::mint = mint,
    token::authority = user,          // enforce from.owner == user
    token::token_program = token_program,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

Anchor's `token::authority` constraint checks `from.owner == user.key()` at the account-validation layer, before any CPI is executed, ensuring only the actual owner of the token account can initiate a bridge transfer. This eliminates the delegate-drain vector for both the `transfer_checked` and `burn` paths.

## Proof of Concept
1. Alice holds 10,000 USDC in `alice_ata` and has previously called `spl_token::approve(alice_ata, delegate=bob, amount=10_000)` for any DeFi interaction.
2. Bob constructs an `InitTransfer` transaction:
   - `from = alice_ata`
   - `user = bob` (Bob signs)
   - `payload.amount = 10_000`
   - `payload.recipient = "eth:0xBob..."` (Bob's EVM address)
3. Anchor constraint validation passes: `from` only checks `token::mint` and `token::token_program`, both satisfied.
4. The `transfer_checked` CPI succeeds: SPL token program accepts Bob as a valid delegate of `alice_ata`.
5. 10,000 USDC are locked in the bridge vault; the Wormhole message triggers release/minting of 10,000 USDC to Bob's EVM address.
6. Alice's funds are permanently lost with no on-chain recourse.

**Minimal test plan:** Write a local Anchor integration test that (a) creates `alice_ata`, (b) calls `spl_token::approve` to grant Bob delegate authority, (c) invokes `init_transfer` signed by Bob with `from=alice_ata`, and (d) asserts the vault balance increases and the Wormhole message payload contains Bob's recipient address — confirming the exploit without any mainnet interaction.
