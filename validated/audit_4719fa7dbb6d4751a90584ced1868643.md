### Title
Cross-Chain Replay of `deploy_token` / `deployToken` Signatures Due to Missing Chain ID in Signed Payload - (File: `starknet/src/omni_bridge.cairo`, `evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-bridge/src/lib.rs`)

---

### Summary

The NEAR MPC signs a `MetadataPayload` that contains no destination chain identifier. The identical Borsh-encoded bytes are accepted verbatim by both the EVM `deployToken` and the Starknet `deploy_token` functions, which both verify against the same NEAR-derived ECDSA address. A single valid signature obtained from one chain can be replayed on every other supported chain, causing unauthorized token deployment without the bridge operator's intent.

---

### Finding Description

**NEAR signing side** (`near/omni-bridge/src/lib.rs`, `log_metadata_callback`):

The `MetadataPayload` that is hashed and sent to the MPC signer contains only `{ prefix, token, name, symbol, decimals }` — no chain ID, no nonce, no destination identifier. [1](#0-0) 

**EVM verification** (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `deployToken`):

The EVM contract reconstructs and verifies the exact same five-field Borsh blob. No chain ID is mixed in. [2](#0-1) 

**Starknet verification** (`starknet/src/bridge_types.cairo`, `MetadataPayloadImpl::to_borsh`):

The Starknet `to_borsh()` implementation produces the identical byte sequence: `PayloadType::Metadata | token | name | symbol | decimals`. [3](#0-2) 

**Contrast with `fin_transfer`**: The `TransferMessagePayload` for `fin_transfer` correctly binds the signature to a specific chain by embedding `chain_id` twice in the signed bytes (destination chain and recipient chain). [4](#0-3) [5](#0-4) 

The `deploy_token` path has no equivalent chain binding. Because both EVM and Starknet verify against the same `nearBridgeDerivedAddress` / `omni_bridge_derived_address` (the single NEAR MPC-derived key), a signature that passes on one chain passes on every other chain that uses the same payload format. [6](#0-5) [7](#0-6) 

---

### Impact Explanation

1. An attacker observes a successful `deployToken` call on EVM (or `deploy_token` on Starknet) and extracts the `(signatureData, metadata)` arguments from the transaction.
2. They submit the identical call to the other chain. The signature verifies correctly because the signed bytes are chain-agnostic.
3. The token is deployed on the target chain and a `DeployToken` event is emitted.
4. A relayer (or the attacker) submits this event to NEAR via `bind_token`. NEAR's factory check (`self.factories.get(&deploy_token.emitter_address.get_chain()) == Some(deploy_token.emitter_address)`) passes because the event originates from the legitimate registered factory contract on that chain. [8](#0-7) 

5. The token is now registered on NEAR for the target chain without the operator's authorization.
6. Users who subsequently call `initTransfer` on the target chain lock real assets. If the bridge is not operationally ready for that chain (e.g., the NEAR side has not set up the correct decimal mapping, or the operator intended to deploy with different parameters), those assets are permanently locked with no corresponding release path — constituting permanent freezing of bridged funds.

Additionally, the attacker can race ahead of the legitimate deployment: if the operator has not yet deployed the token on a given chain, the attacker can deploy it first, potentially with a manipulated `name`/`symbol`/`decimals` field (since the attacker controls the `metadata` calldata argument — only the signature is fixed). The signature only commits to the values in the signed payload, but the attacker can pass any `metadata` struct to the function as long as its Borsh encoding matches the signed hash. If the attacker crafts a `metadata` struct with different `name`/`symbol` values that Borsh-encode to the same bytes (e.g., by exploiting length-prefix ambiguity), they could deploy a misleading token. Even without that, deploying on an unintended chain with the correct metadata still constitutes an unauthorized deployer action.

---

### Likelihood Explanation

The attack requires only:
- Reading a publicly visible on-chain transaction (zero privilege).
- Submitting the same calldata to a different chain's bridge contract.

No keys, no admin access, no MEV infrastructure. Any unprivileged observer of the source chain can execute this immediately after the legitimate `deployToken` transaction is confirmed.

---

### Recommendation

Include the destination chain ID in the `MetadataPayload` that is signed by the NEAR MPC, mirroring the pattern already used in `TransferMessagePayload`:

**NEAR side** (`log_metadata_callback`): Add a `destination_chain: ChainKind` field to `MetadataPayload` and include it in the Borsh-serialized bytes before signing.

**EVM side** (`deployToken`): Append `bytes1(omniBridgeChainId)` to `borshEncoded` before hashing.

**Starknet side** (`MetadataPayloadImpl::to_borsh`): Append `omni_bridge_chain_id` to the Borsh bytes, matching the `fin_transfer` pattern.

This ensures a signature issued for chain A is cryptographically invalid on chain B.

---

### Proof of Concept

**Step 1**: Observe a `deployToken(signatureData, metadata)` call on the EVM bridge for token `"token.near"` with `name="Token"`, `symbol="TKN"`, `decimals=18`.

**Step 2**: The signed bytes are:
```
keccak256(Borsh(0x01 | "token.near" | "Token" | "TKN" | 0x12))
```
No chain ID. The same hash is produced on Starknet for the same `MetadataPayload`.

**Step 3**: Submit `deploy_token(signature, MetadataPayload { token: "token.near", name: "Token", symbol: "TKN", decimals: 18 })` to the Starknet bridge.

**Step 4**: `_verify_borsh_signature` passes (same key, same hash). `existing_token.is_zero()` passes (not yet deployed on Starknet). Token is deployed and `DeployToken` event emitted. [9](#0-8) 

**Step 5**: Submit the Starknet `DeployToken` event to NEAR via `bind_token`. NEAR registers `"token.near"` for `ChainKind::Strk` without the operator ever authorizing Starknet deployment. [10](#0-9)

        fn deploy_token(ref self: ContractState, signature: Signature, payload: MetadataPayload) {
            assert(!_is_paused(@self, PAUSE_DEPLOY_TOKEN), 'ERR_DEPLOY_TOKEN_PAUSED');

            _verify_borsh_signature(ref self, @payload.to_borsh(), signature);

            let token_id_hash = compute_keccak_byte_array(@payload.token);
            let existing_token = self.near_to_starknet_token.read(token_id_hash);
            assert(existing_token.is_zero(), 'ERR_TOKEN_ALREADY_DEPLOYED');

            let decimals = _normalizeDecimals(payload.decimals);

            let mut constructor_calldata: Array<felt252> = array![];
            (payload.name.clone(), payload.symbol.clone(), decimals)
                .serialize(ref constructor_calldata);

            // Use the low part of the u256 hash to ensure it fits in felt252
            let salt: felt252 = token_id_hash.low.into();
            let (contract_address, _) = deploy_syscall(
                self.bridge_token_class_hash.read(), salt, constructor_calldata.span(), false,
            )
                .unwrap_syscall();

            self.starknet_to_near_token.write(contract_address, payload.token.clone());
            self.near_to_starknet_token.write(token_id_hash, contract_address);
