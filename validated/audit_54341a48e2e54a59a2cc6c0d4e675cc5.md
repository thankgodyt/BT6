Audit Report

## Title
Permanent Fund Loss via Zero-Normalized Transfer Amount — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal` unconditionally burns or locks user tokens before any normalization check is performed. When the transferred amount is smaller than the normalization divisor (`10^(origin_decimals - decimals)`), `sign_transfer` will always panic with `InvalidAmountToTransfer` on every subsequent call. Because the burn/lock is already committed on-chain and no cancel or refund path exists, the user's funds are permanently destroyed or frozen.

## Finding Description

**Step 1 — Tokens are burned/locked with no normalization guard.**

`init_transfer_internal` (lines 1829–1865) first stores the transfer message, then unconditionally calls `burn_tokens_if_needed` and `lock_tokens_if_needed` at lines 1850–1857:

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
}
``` [1](#0-0) 

There is no normalization check anywhere in `init_transfer_internal`.

**Step 2 — `sign_transfer` normalizes the amount and panics if it rounds to zero.**

`sign_transfer` (lines 475–485) performs the normalization check only after the burn/lock is already committed:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

`normalize_amount` uses floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

For a token with `origin_decimals=24` and `decimals=18`, the divisor is `10^6`. Any amount below `10^6` normalizes to `0`, causing `sign_transfer` to panic on every call. The panic reverts `sign_transfer` but does **not** undo the already-committed burn/lock from Step 1.

**Step 3 — `sign_transfer_callback` has no recovery path.**

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
    // ...
}
``` [4](#0-3) 

The `Err` branch is silently ignored. No refund, no cleanup, no unlock.

**Step 4 — No cancel or refund function exists.**

A search for `pub fn cancel`, `pub fn refund`, `pub fn withdraw`, and `pub fn unlock` returns no matches in `lib.rs`. `remove_transfer_message` is only reachable on a successful MPC signing result — which is impossible when `sign_transfer` always panics before reaching the MPC call. [5](#0-4) 

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**, which is an explicitly listed Critical impact. For deployed (bridged) tokens, `burn_tokens_if_needed` destroys the tokens with no mint-back path. For native tokens, `lock_tokens_if_needed` locks them in the bridge contract with no unlock path available to the user. The transfer message remains in `pending_transfers` indefinitely, and every `sign_transfer` call for that transfer ID panics identically.

## Likelihood Explanation

Any unprivileged user who calls `ft_transfer_call` with an amount below `10^(origin_decimals - decimals)` triggers this. The only guard in `init_transfer` is `fee < amount`, which passes trivially for `fee=0`. The user receives no error at `init_transfer` time — the failure only surfaces later when a relayer calls `sign_transfer`. For tokens with a 6-decimal gap (common for NEAR-native tokens bridged to EVM chains), the threshold is `10^6 - 1` base units. A user entering a small amount or whose amount is reduced by fees below the threshold will silently lose funds.

## Recommendation

Add a normalization check inside `init_transfer_internal` **before** `burn_tokens_if_needed` and `lock_tokens_if_needed`. Retrieve the token address and decimals for the destination chain, compute `normalize_amount`, and `require!(normalized > 0, BridgeError::InvalidAmountToTransfer)`. If the check fails, return the amount to the caller (as is already done in other early-exit paths in `init_transfer_internal`). This mirrors the guard already present in `sign_transfer` but places it before any irreversible state change. [6](#0-5) 

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization divisor = `10^6`).
2. User calls `ft_transfer_call` transferring `500_000` base units with `fee = 0`.
3. `init_transfer` passes its only guard: `fee < amount` → `0 < 500_000` ✓.
4. `init_transfer_internal` calls `burn_tokens_if_needed`, destroying the `500_000` tokens on-chain, and stores the transfer message in `pending_transfers`.
5. Trusted relayer calls `sign_transfer`. `normalize_amount(500_000, {24, 18})` = `500_000 / 10^6` = `0`. The `require!(amount_to_transfer > 0)` panics.
6. The panic reverts `sign_transfer` but the burn from Step 4 is already committed.
7. Every subsequent `sign_transfer` call for this transfer ID panics identically.
8. No cancel or refund function exists. The `500_000` tokens are permanently destroyed.

A local integration test can reproduce this by: (a) deploying a mock bridged token contract, (b) calling `ft_transfer_call` with a sub-threshold amount, (c) asserting the burn occurred, (d) calling `sign_transfer` and asserting it panics, (e) asserting the transfer message remains in `pending_transfers` with no recovery path.

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
