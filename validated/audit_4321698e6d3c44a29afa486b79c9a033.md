The key code to analyze is the interaction between `load_refund_request_for_execute`, `finalize_refund_with_psbt`, and `get_pending_id`. Let me trace the exact path.

**Step 1 — Guard in `load_refund_request_for_execute`:** [1](#0-0) 

After the first successful `execute_refund`, `executed=true` and the UTXO is in `verified_deposit_utxo`. The condition `!contains || executed` evaluates to `!true || true = true`, so the guard **passes** on the second call. The code comment explicitly documents this as intentional: [2](#0-1) 

**Step 2 — `btc_pending_id` is deterministic:**

`get_pending_id()` computes the Bitcoin txid of the unsigned transaction built from the same `outpoint` and `refund_output`: [3](#0-2) 

Since the deposit UTXO (`outpoint`), refund address, and amount are all fixed by the stored `RefundRequest`, the second call produces the **identical** `btc_pending_id`.

**Step 3 — Panic in `finalize_refund_with_psbt`:** [4](#0-3) 

The old `btc_pending_info` from the first execution is still in `btc_pending_infos` (it is only removed in `verify_refund_finalize_callback`). The `insert(...).is_none()` check fails, and the contract panics with `"pending info already exist"`.

**Step 4 — The deadlock:**

`internal_remove_refund_pending_tx_id` cannot remove the old entry while the refund request is still active: [5](#0-4) 

And the refund request is only removed in `verify_refund_finalize_callback`: [6](#0-5) 

So if the original PSBT becomes unbroadcastable (e.g., after a consensus branch change — the exact scenario the design comment describes), the state is stuck: re-execution panics, the old pending info cannot be cleaned up, and the refund cannot progress without operator intervention (`reject_refund` by DAO/Operator, then `remove_refund_pending_tx_id`).

**Verdict:**

The re-execution path is **concretely broken**. The design intent (re-create the refund tx after a consensus branch change) is documented in two places in the source but the implementation never removes the stale `btc_pending_info` before inserting the new one. Any unprivileged caller can trigger the panic by calling `execute_refund` twice; the more impactful scenario is a legitimate user whose refund PSBT is invalidated and who cannot recover without operator intervention.

### Title
Re-execution of `execute_refund` always panics due to stale `btc_pending_info` — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
`execute_refund` is explicitly designed to be callable multiple times for the same refund request (e.g., to re-create the PSBT after a consensus branch change), but `finalize_refund_with_psbt` unconditionally panics with `"pending info already exist"` on any second call because the old `BTCPendingInfo` entry is never removed first.

### Finding Description
After the first successful `execute_refund`:
- `refund_request.executed` is set to `true`
- The UTXO is inserted into `verified_deposit_utxo`
- A `BTCPendingInfo` entry is stored under the deterministic `btc_pending_id` (the Bitcoin txid of the unsigned refund transaction)

On a second call, `load_refund_request_for_execute` passes because `executed == true` satisfies the `!contains || executed` guard. [7](#0-6)  `internal_execute_refund` then rebuilds an identical PSBT from the same stored inputs, producing the same `btc_pending_id`. [8](#0-7)  `finalize_refund_with_psbt` attempts to insert into `btc_pending_infos` and panics because the key already exists. [4](#0-3) 

There is no code path that removes the old `BTCPendingInfo` before re-execution. `internal_remove_refund_pending_tx_id` explicitly blocks removal while the refund request is still active. [5](#0-4) 

### Impact Explanation
If the original refund PSBT is invalidated (e.g., after a consensus branch change — the exact scenario the design comments describe), the refund enters a permanently stuck state: re-execution panics, the stale pending info cannot be cleaned up by the user, and recovery requires DAO/Operator intervention via `reject_refund` followed by `remove_refund_pending_tx_id`. User BTC remains locked in the bridge until operator action. This matches **Low** (publicly reachable stuck-state/panic-driven fault in production bridge path without direct theft).

### Likelihood Explanation
Any caller can reproduce the panic by calling `execute_refund` twice for the same request. The more impactful scenario (stuck refund after consensus branch change) is less frequent but is the exact use-case the design explicitly targets.

### Recommendation
In `finalize_refund_with_psbt`, before inserting the new `BTCPendingInfo`, check whether an entry already exists for `btc_pending_id` and remove it (along with the corresponding `btc_pending_sign_ids` entry) if so. This makes re-execution idempotent and fulfills the documented design intent.

### Proof of Concept
```
1. Call execute_refund(utxo_storage_key) → succeeds; btc_pending_infos[txid] created, executed=true.
2. Call execute_refund(utxo_storage_key) again (same caller, same key).
3. load_refund_request_for_execute passes (executed==true).
4. finalize_refund_with_psbt builds identical PSBT → same btc_pending_id.
5. btc_pending_infos.insert(...).is_none() == false → panic "pending info already exist".
6. Transaction reverts; refund is permanently stuck until operator intervention.
```
