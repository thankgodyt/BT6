### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Weight Boost — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. An unprivileged peer can therefore send a crafted `PerasCert` over the ObjectDiffusion miniprotocol, have it accepted as "validated," stored in the `PerasCertDB`, and used to trigger a Peras weight-boost chain-selection pass for an arbitrary block in the VolatileDB. This is the direct consensus analog of the XSS report's root cause: attacker-controlled data accepted without sanitization, stored, and later consumed in a security-critical path.

### Finding Description

**Root cause — stub validation that always succeeds**

In the degenerate `BlockSupportsPeras` instance that covers all block types, `validatePerasCert` is implemented as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance is declared as the universal fallback for every `StandardHash blk`: [2](#0-1) 

No signature, committee membership, round-number range, or boosted-block existence check is performed. The function simply wraps the raw peer-supplied `PerasCert` in a `ValidatedPerasCert` and assigns it the full configured `perasWeight`.

**Attacker-controlled entry path — ObjectDiffusion miniprotocol**

The production inbound path for certificates is `makePerasCertPoolWriterFromChainDB`, which wires `validatePerasCert mkPerasParams` directly as the validation callback: [3](#0-2) 

`processCerts` calls this callback on every certificate in the peer's batch. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

**Security-critical consumption — chain selection weight boost**

`chainSelSync` in `ChainSel.hs` processes the stored certificate. After a slot-age check against the immutable tip, it calls `chainSelectionForBlock` for the block named in `pcCertBoostedBlock`, giving that block the full Peras weight boost in the chain-selection comparison: [5](#0-4) 

The `ValidatedPerasCert` carries `vpcCertBoost :: PerasWeight`, which is the weight assigned to the boosted block during chain selection: [6](#0-5) 

**Secondary issue — `validatePerasVote` skips cryptographic verification**

`validatePerasVote` only checks that the claimed voter ID exists in the stake distribution; it performs no signature verification: [7](#0-6) 

A peer can therefore forge votes for any registered stake pool, accumulate enough stake to satisfy `votesReachQuorum`, and cause the node to internally forge a certificate — compounding the certificate-injection path.

### Impact Explanation

An unprivileged peer can inject a `PerasCert` that names any block currently in the VolatileDB as the boosted block. The node will apply the full `perasWeight` boost to that block during chain selection, potentially causing it to prefer a shorter or non-canonical fork over the honest chain. Because Peras weight is designed to make certified blocks effectively irreversible within the security parameter, a fraudulent boost can lock the node onto an adversary-chosen chain segment, constituting a **High** chain-selection integrity failure: an unprivileged peer makes an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

Any peer that can establish an ObjectDiffusion connection (no stake, no keys required) can trigger this. The crafted certificate requires only a valid CBOR encoding of a `PerasCert` with an arbitrary `pcCertRound` and a `pcCertBoostedBlock` pointing to a block the attacker knows is in the target node's VolatileDB (learnable via ChainSync). The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is a known incomplete stub shipped in production code, not a test artifact.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's cryptographic proof of committee quorum (signature/VRF evidence).
2. That `pcCertRound` falls within the valid range relative to the current chain tip.
3. That `pcCertBoostedBlock` refers to a block that is a plausible candidate (e.g., within the last *k* blocks).

Until the real implementation is available, the degenerate instance should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that no peer-supplied certificate can influence chain selection. The same applies to `validatePerasVote`: reject votes whose voter signatures are not verified rather than accepting any vote whose voter ID appears in the stake distribution.

### Proof of Concept

1. Connect to a target node's ObjectDiffusion endpoint as an unprivileged peer.
2. Observe via ChainSync that the node's VolatileDB contains block `B` at point `(slot=S, hash=H)` on a minority fork.
3. Craft a CBOR-encoded `PerasCert`:
   ```
   [roundNo, [S, H]]   -- pcCertRound=roundNo, pcCertBoostedBlock=(S,H)
   ```
4. Send the certificate in a single-element batch over the ObjectDiffusion protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
6. `ChainDB.addPerasCertAsync` stores the certificate; `chainSelSync` fires `chainSelectionForBlock` for block `B` with the full Peras weight boost.
7. Observe the node switch its selection to the fork containing `B`, even though that fork is shorter or has less honest work than the canonical chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
