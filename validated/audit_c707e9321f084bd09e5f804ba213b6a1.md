### Title
Peras Certificate Validation Unconditionally Accepts Any Certificate, Enabling Chain Selection Manipulation via ObjectDiffusion — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, ignoring all parameters. Because chain selection has been modified to use Peras certificate weight instead of chain length, an unprivileged peer can inject a crafted `PerasCert` via the `ObjectDiffusion` mini-protocol, have it accepted without any validation, and cause an honest node to prefer a non-canonical chain. The analog to the UMA migration bug is precise: just as the UMA `onlyRegisteredContract` modifier allows price requests to be forwarded to the old contract while `onlyIfNotMigrated` prevents them from ever being voted on, the Ouroboros Peras activation creates an inconsistent transition state where the certificate-acceptance path is fully open (no validation gate) while the chain-selection path unconditionally trusts the accepted certificate's weight.

---

### Finding Description

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` explicitly labelled "degenerate instance for all blks to get things to compile": [2](#0-1) 

Every `PerasCert` received from any peer is therefore stamped `ValidatedPerasCert` with the full `perasWeight` boost, regardless of its content.

**Chain selection now uses Peras weight:**

The `ChainDB` chain-selection function was modified to select candidate fragments based on Peras weight rather than length: [3](#0-2) 

> Make the `ChainDB` aware of the `PerasCertDB`, and modify the chain selection function accordingly. In practice, it means that the candidate fragment is now selected based on its Peras weight, instead of its length.

**Inbound diffusion path — `ObjectDiffusion` → `opwWriteObjects`:**

Certificates received from peers flow through `objectDiffusionInbound`, which calls `opwWriteObjects` on the `ObjectPoolWriter`: [4](#0-3) 

The cert pool writer (mirroring the vote pool writer pattern) calls `validatePerasCert` before storing the certificate in `PerasCertDB`. Because `validatePerasCert` always returns `Right`, every crafted certificate is stored and its weight is applied to chain selection.

**Parallel vote-validation bypass (same instance):**

The same instance's `validatePerasVote` ignores `_params` entirely and only checks stake-distribution membership, performing no cryptographic signature verification: [5](#0-4) 

Furthermore, the vote pool writer hardcodes `mkPerasParams` rather than reading the actual on-chain Peras parameters: [6](#0-5) 

**`getPerasCertInBlock` always returns `Nothing`:**

Certificates embedded in blocks are never extracted, so the ledger's `latestCertOnChain` is permanently `Origin`, silently breaking the VR-2B voting rule for all nodes: [7](#0-6)

### Impact Explanation

**Chain selection manipulation (High → Critical):** An unprivileged peer sends a crafted `PerasCert` with `pcCertBoostedBlock` pointing to any block on a minority or adversarial fork. `validatePerasCert` accepts it unconditionally. The `PerasCertDB` stores it. Chain selection applies the `perasWeight` boost (default `PerasWeight 15`) to that block. The honest node's `WeightedSelectView` now prefers the adversarially boosted chain over the canonical chain, causing a divergence from the honest majority without any stake requirement on the attacker's part.

This satisfies: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions"* and *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The `ObjectDiffusion` mini-protocol is a standard peer-to-peer protocol reachable by any connected peer. No keys, stake, or operator access are required. The only prerequisite is that Peras is enabled (currently disabled by default, but the production code path is fully wired). Once Peras is activated on any network (testnet or mainnet), the attack is immediately executable by any peer that can establish a connection.

---

### Recommendation

1. **Implement real `validatePerasCert`:** Verify the certificate's aggregate BLS signature against the claimed committee members, confirm the round number falls within the current era's Peras-enabled range, and check that the boosted block exists on the node's chain.
2. **Implement real `validatePerasVote`:** Verify the individual BLS/VRF eligibility proof; do not ignore `_params`.
3. **Remove the catch-all `BlockSupportsPeras` instance** or make it a compile-time error, forcing each concrete block type to provide a real implementation before Peras can be enabled.
4. **Implement `getPerasCertInBlock`** so that on-chain certificates update `latestCertOnChain` in the ledger state, restoring the VR-2B voting rule invariant.
5. **Gate chain-selection weight on validated certificates only**, ensuring that the weight applied to a block is derived exclusively from certificates that have passed full cryptographic validation.

### Proof of Concept

```
Private testnet with Peras enabled:

1. Attacker node A connects to honest node H via the standard
   node-to-node mini-protocol stack (ObjectDiffusion enabled).

2. A crafts a PerasCert:
     pcCertRound       = <any round number>
     pcCertBoostedBlock = <Point of an adversarial minority-fork block B'>

3. A advertises the cert ID via MsgAdvertiseIds in the
   ObjectDiffusion protocol.

4. H sends MsgRequestObjects; A replies with MsgReplyObjects
   containing the crafted PerasCert.

5. objectDiffusionInbound on H calls opwWriteObjects([crafted_cert]).

6. validatePerasCert is called → returns Right ValidatedPerasCert
   { vpcCertBoost = PerasWeight 15 } unconditionally.

7. The cert is stored in H's PerasCertDB.

8. H's chain selection now computes WeightedSelectView for B'
   with an extra weight of 15, exceeding the canonical chain's
   weight if the canonical chain has fewer than 15 weight units
   of advantage.

9. H switches to the adversarial fork containing B', diverging
   from the honest majority.
