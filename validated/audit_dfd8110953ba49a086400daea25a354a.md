Audit Report

## Title
Double-Spend via Finalization Record Removal on `ft_transfer_call` Rejection — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When `fin_transfer` finalizes an inbound transfer to a NEAR recipient with a non-empty `msg`, the bridge uses `ft_transfer_call` to deliver tokens. If the recipient's `ft_on_transfer` rejects all tokens, `fin_transfer_send_tokens_callback` burns the refunded tokens and then calls `remove_fin_transfer`, permanently erasing the `TransferId` from `finalised_transfers`. This allows the same foreign-chain proof to be submitted a second time, minting tokens again with no additional foreign-chain collateral.

## Finding Description
**Root cause:** `remove_fin_transfer` is called unconditionally whenever `is_refund_required` returns `true`, which destroys the sole replay-protection record for the transfer.

**Code path:**

1. `process_fin_transfer_to_near` calls `add_fin_transfer`, inserting the `TransferId` into `finalised_transfers` (L1875). The `add_fin_transfer` guard panics if the ID is already present (L2228–2230).

2. `send_tokens` calls `mint` on the token contract with a non-empty `msg`. The token contract's `mint` function (omni-token `lib.rs` L135–139) mints tokens to the bridge itself and then calls `ft_transfer_call` to the recipient. The `ft_transfer_call` result — via `ft_resolve_transfer` (omni-token `lib.rs` L238–242) — is the **used amount** (tokens accepted by the receiver).

3. `is_refund_required` (L1784–1803) checks `amount.0 == 0`. When `ft_on_transfer` returns the full amount (full rejection), `ft_resolve_transfer` returns `used_amount = 0`, so `is_refund_required` returns `true`. The inline comment confirms this: *"The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics."*

4. Inside `fin_transfer_send_tokens_callback` (L1702–1714), when `is_refund_required` is `true`, the bridge burns the tokens and then calls `remove_fin_transfer`, deleting the `TransferId` from `finalised_transfers`.

5. After deletion, `add_fin_transfer` will succeed again for the same `TransferId` because `finalised_transfers.insert` no longer finds the ID present. The prover verifies against immutable foreign-chain state, so the same proof passes a second time.

**Why existing checks fail:** The only replay guard is `finalised_transfers`. There is no secondary record, nonce, or flag that survives the `remove_fin_transfer` call. The `msg` field is user-controlled (set in `initTransfer` on the EVM side, stored verbatim in `TransferMessage.msg`), so any user can trigger the `ft_transfer_call` path.

## Impact Explanation
**Critical — unauthorized minting / double-spend of bridged tokens.**

For deployed (bridged) tokens, the attacker causes the bridge to mint tokens twice against a single foreign-chain lock/burn event. On the first submission the minted tokens are burned (net zero), but the replay guard is erased. On the second submission the minted tokens are accepted and kept by the attacker. The bridged token supply is inflated by N tokens backed by zero foreign-chain collateral, directly stealing value from the bridge's reserves. This matches the Critical impact class: *"Cross-chain replay … enabling invalid finalization or double-spending."*

## Likelihood Explanation
**Medium.** The attacker must: (1) deploy a NEAR contract whose `ft_on_transfer` rejects on the first call and accepts on the second — trivial for any NEAR user; (2) set a non-empty `msg` in `initTransfer` on the EVM side — freely chosen by the sender; (3) cause `fin_transfer` to be called a second time — realistic, since after `remove_fin_transfer` any relayer querying `is_transfer_finalised` sees `false` and may resubmit in good faith, or the attacker can call `fin_transfer` directly. No privileged role is required.

## Recommendation
**Do not remove the `TransferId` from `finalised_transfers` when `ft_transfer_call` delivery fails.** The finalization record is the sole replay-protection gate; erasing it on delivery failure reopens the proof for reuse.

Concrete fix options:
- Remove the `self.remove_fin_transfer(...)` call at L1714 from the refund branch. Keep the `TransferId` in `finalised_transfers` permanently.
- Store the undelivered token amount in a per-recipient claimable balance so the recipient can retrieve tokens without re-proving.
- Emit `FailedFinTransferEvent` (already present at L1716–1718) so off-chain systems can alert without resubmitting the proof.

## Proof of Concept
```
1. Attacker deploys `attacker.near` with `ft_on_transfer` that:
   - Call 1: returns `amount` (full rejection)
   - Call 2: returns `0` (full acceptance)

2. Attacker calls `initTransfer` on EVM OmniBridge:
     recipient = "attacker.near"
     msg       = "trigger"   // non-empty → ft_transfer_call path
     amount    = 1_000_000

3. Relayer submits `fin_transfer` on NEAR with valid proof.
   Bridge: add_fin_transfer(id) → mint(bridge, 1_000_000) → ft_transfer_call(attacker.near)

4. `attacker.near::ft_on_transfer` returns 1_000_000 (rejection).
   ft_resolve_transfer returns used_amount = 0.
   is_refund_required → true.
   fin_transfer_send_tokens_callback: burn(1_000_000), remove_fin_transfer(id).

5. is_transfer_finalised(id) → false.
   Relayer (or attacker directly) resubmits fin_transfer with same proof.
   Bridge: add_fin_transfer(id) succeeds → mint(bridge, 1_000_000) → ft_transfer_call(attacker.near)

6. `attacker.near::ft_on_transfer` returns 0 (acceptance).
   Attacker keeps 1_000_000 tokens.

Result: 1_000_000 tokens minted with no additional EVM collateral.
```
