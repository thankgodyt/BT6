### Title
Unprivileged caller can create a competing `BTCPendingInfo` for an already-executed refund request by switching transparent/shielded branch — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/zcash_utils/refund.rs`)

### Summary

`execute_refund` is callable by any unprivileged account. After a first execution marks a refund request `executed = true`, the re-execution guard in `load_refund_request_for_execute` intentionally allows a second call. Because the `btc_pending_id` is derived from the PSBT bytes, a transparent PSBT and a shielded PSBT for the same deposit produce **different IDs**, so the duplicate-pending-info guard in `finalize_refund_with_psbt` does not fire. A second caller can therefore insert a second live `BTCPendingInfo` — owned by themselves — for the same deposit UTXO.

### Finding Description

**Step 1 — `execute_refund` is fully public.** [1](#0-0) 

The function carries `#[payable]` and `#[pause(except(roles(Role::DAO)))]` but no `#[trusted_relayer]` or ACL guard. The doc comment at line 487 explicitly states "anyone can call `execute_refund`". `resolve_execute_refund_timelock` only adjusts the wait period for unprivileged callers; it does not block them. [2](#0-1) 

**Step 2 — Re-execution is allowed once `executed == true`.**

After the first call, `finalize_refund_with_psbt` sets `refund_request.executed = true` and inserts the UTXO into `verified_deposit_utxo`. The guard in `load_refund_request_for_execute` is:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
``` [3](#0-2) 

When `executed == true` the condition is `!true || true = true`, so any caller passes.

**Step 3 — Transparent vs. shielded PSBTs produce different `btc_pending_id`s.**

In `execute_refund_callback`, the branch is chosen by whether `chain_specific_data` carries an Orchard bundle: [4](#0-3) 

A transparent PSBT has one P2PKH output and no Orchard bundle; a shielded PSBT has no transparent output and an Orchard bundle. Their serialized bytes differ, so `psbt.get_pending_id()` returns different values.

**Step 4 — The only duplicate guard checks `btc_pending_id`, not the underlying UTXO.** [5](#0-4) 

Because the two IDs differ, the `insert(...).is_none()` check passes for both, and two `BTCPendingInfo` entries — owned by different accounts — are inserted for the same deposit UTXO.

**Step 5 — Both entries are economically live.**

Each `BTCPendingInfo` is in `PendingInfoState::Refund(PendingInfoStage::PendingSign)` and is linked to the owner's `btc_pending_sign_ids`. Both can be progressed through the MPC signing pipeline independently. [6](#0-5) 

### Impact Explanation

Two signed refund transactions spending the same UTXO will be broadcast. Only one can confirm on-chain. The other's `BTCPendingInfo` becomes permanently stuck — it can only be cleaned up via `remove_refund_pending_tx_id`, which is `#[trusted_relayer]`-gated, requiring operator intervention. This is a **stuck bridge state requiring operator intervention** and a concrete invariant violation: one refundable deposit has two economically live candidates simultaneously.

Funds are not redirected (the `refund_address` is fixed in the stored `RefundRequest` and cannot be changed by the attacker), so direct theft is not possible.

### Likelihood Explanation

The attack requires only:
1. A public refund request to exist (anyone can create one).
2. Waiting for the `unsafe_refund_timelock_sec` to elapse.
3. Calling `execute_refund` with a valid Orchard bundle paying to the already-stored `refund_address`.

No privileged role, leaked key, or external dependency is needed. The attacker must supply a well-formed Orchard bundle, which is technically demanding but not infeasible.

### Recommendation

In `load_refund_request_for_execute` (or at the start of `finalize_refund_with_psbt`), record the `AccountId` of the first executor inside the `RefundRequest` and require that any subsequent re-execution comes from the same account. Alternatively, before inserting a new `BTCPendingInfo`, scan the existing entries for any that already reference the same UTXO storage key and reject the second call if one is found.

### Proof of Concept

```
1. Alice calls request_refund(deposit_msg, refund_addr, tx_bytes, vout, proof, None)
   → RefundRequest stored with executed=false

2. After timelock, Alice calls execute_refund(key, None)   // transparent
   → execute_refund_callback: caller=Alice, orchard_bundle=None
   → finalize_refund_with_psbt: inserts BTCPendingInfo P1 (id=H_transparent), account=Alice
   → verified_deposit_utxo.insert(key), refund_request.executed=true

3. Bob calls execute_refund(key, Some(valid_orchard_bundle_for_refund_addr))  // shielded
   → load_refund_request_for_execute: !true || true → passes
   → execute_refund_callback: caller=Bob, orchard_bundle=Some(...)
   → finalize_refund_with_psbt: btc_pending_id=H_shielded ≠ H_transparent
     → insert(H_shielded, ...).is_none() → true → succeeds
   → BTCPendingInfo P2 (id=H_shielded), account=Bob inserted

4. Both P1 and P2 are live PendingSign entries for the same UTXO.
   Assert: btc_pending_infos.contains(H_transparent) && btc_pending_infos.contains(H_shielded)
   → invariant broken.
```

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
