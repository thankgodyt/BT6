Audit Report

## Title
Cross-Chain Replay of `deployToken` Signature Due to Missing Chain ID in Borsh-Encoded `MetadataPayload` — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.deployToken` constructs its Borsh-encoded payload from only `PayloadType.Metadata`, `token`, `name`, `symbol`, and `decimals` — no chain identifier is included. A NEAR-signed `MetadataPayload` authorizing token deployment on one chain is cryptographically identical on every other OmniBridge deployment. Any unprivileged observer can extract `signatureData` from a `deployToken` transaction on chain A and replay it verbatim on chain B, deploying an unauthorized `BridgeToken` proxy and permanently blocking legitimate deployment on that chain.

## Finding Description

`MetadataPayload` contains no chain field: [1](#0-0) 

`deployToken` hashes exactly those four fields with no `omniBridgeChainId`: [2](#0-1) 

The resulting `keccak256` digest is therefore identical on every EVM chain for the same NEAR token. The only replay guard is the per-chain `isBridgeToken` / `nearToEthToken` mapping, which only prevents a second deployment on the *same* chain: [3](#0-2) 

By contrast, `finTransfer` explicitly binds its signed payload to the destination chain by embedding `omniBridgeChainId` twice: [4](#0-3) 

`omniBridgeChainId` is a `uint8` set once at initialization and never referenced in the `deployToken` path: [5](#0-4) [6](#0-5) 

## Impact Explanation

**Primary (unconditional):** Any observer of a `deployToken` transaction on chain A can extract `signatureData` and call `deployToken` on chain B with identical arguments. The ECDSA check passes because the hash is chain-agnostic. A `BridgeToken` proxy is deployed on chain B and permanently bound to the NEAR token ID via `nearToEthToken` / `ethToNearToken` / `isBridgeToken`. This constitutes an authorization bypass — NEAR never authorized deployment on chain B — and permanently blocks legitimate deployment on chain B (the `ERR_TOKEN_EXIST` guard fires for all future calls). This matches the Critical scope: *"Unauthorized transaction, authorization bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions"* and *"Cross-chain replay... or chain/domain separation flaw enabling invalid finalization or double-spending."*

**Secondary (requires same `omniBridgeChainId`):** If two OmniBridge deployments share the same `omniBridgeChainId`, `finTransfer` signatures are also chain-agnostic. Combined with the `deployToken` replay, a single NEAR-side lock event can be used to mint on both chains. The `completedTransfers` nonce map is per-contract: [7](#0-6) 

so the same `destinationNonce` is unused on chain B, enabling double-minting without additional NEAR-side locking.

## Likelihood Explanation

The `deployToken` replay requires zero privileges: any on-chain observer can extract calldata from chain A and resubmit it on chain B. No victim mistake, no misconfiguration, and no special role is required. The `uint8` space for `omniBridgeChainId` (256 values) makes same-ID collisions plausible across many deployments, but the primary impact is unconditional.

## Recommendation

Include `omniBridgeChainId` in the Borsh-encoded `MetadataPayload` hash inside `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // bind to destination chain
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

This requires NEAR to produce a separate signature per destination chain, matching the existing `finTransfer` design.

## Proof of Concept

```solidity
// Foundry test — two OmniBridge instances, different omniBridgeChainId
OmniBridge bridgeA = new OmniBridge(); bridgeA.initialize(impl, nearAddr, 1);
OmniBridge bridgeB = new OmniBridge(); bridgeB.initialize(impl, nearAddr, 2);

// NEAR signs MetadataPayload hash — no chain ID in preimage
bytes32 hash = keccak256(abi.encodePacked(
    bytes1(uint8(1)),          // PayloadType.Metadata
    borshString("token.near"),
    borshString("Token"),
    borshString("TKN"),
    bytes1(uint8(18))
));
(uint8 v, bytes32 r, bytes32 s) = vm.sign(nearPrivKey, hash);
bytes memory sig = abi.encodePacked(r, s, v);

BridgeTypes.MetadataPayload memory meta =
    BridgeTypes.MetadataPayload("token.near", "Token", "TKN", 18);

address addrA = bridgeA.deployToken(sig, meta); // succeeds on chain A
address addrB = bridgeB.deployToken(sig, meta); // succeeds on chain B — same sig, no chain binding

assert(addrA != addrB);
assert(keccak256(bytes(bridgeA.ethToNearToken(addrA))) ==
       keccak256(bytes(bridgeB.ethToNearToken(addrB)))); // same NEAR token ID bound on both chains
```

Both calls succeed on unmodified code. The root cause is confirmed at `OmniBridge.sol` L142–149: `omniBridgeChainId` is never included in the `deployToken` Borsh preimage, while it is included in `finTransfer` at L294 and L297.
