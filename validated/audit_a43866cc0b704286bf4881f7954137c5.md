Audit Report

## Title
Native ETH Delivery Revert in `finTransfer` Permanently Freezes Source-Chain Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`finTransfer` marks the destination nonce as consumed at line 287, then attempts a low-level ETH `call` to the recipient at lines 319–321. If the recipient is a smart contract that reverts on ETH receipt, `revert FailedToSendEther()` at line 322 rolls back the entire transaction — including the nonce write — leaving the nonce permanently unconsumed. Because the recipient address is immutably embedded in the MPC-signed payload, no future call can succeed, and the user's source-chain tokens are irrecoverable.

## Finding Description
In `OmniBridge.finTransfer`:

```
completedTransfers[payload.destinationNonce] = true;   // line 287
``` [1](#0-0) 

is written before the signature is even verified and before any token delivery. For native ETH (`tokenAddress == address(0)`):

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
``` [2](#0-1) 

A Solidity `revert` rolls back all state changes in the call frame, so the `completedTransfers` write at line 287 is also undone. The nonce is never consumed. The recipient address is part of the Borsh-encoded, MPC-signed payload:

```solidity
Borsh.encodeAddress(payload.recipient),
``` [3](#0-2) 

Altering `payload.recipient` invalidates the MPC signature, so no alternative delivery is possible. The contract exposes no admin escape hatch, no pull-payment mapping, and no function that can consume the nonce without delivering ETH. [4](#0-3) 

The `evm/SECURITY.md` known-issues list does not acknowledge this scenario. [5](#0-4) 

## Impact Explanation
Permanent freezing of bridged funds — an explicitly listed Critical impact. A user who initiates a NEAR → EVM native-ETH transfer specifying a non-payable smart contract as recipient will have their source-chain tokens locked forever: `finTransfer` reverts on every attempt, the nonce is never consumed, and no on-chain path exists to redirect or reclaim the ETH. [6](#0-5) 

## Likelihood Explanation
Smart-contract recipients (multisigs, protocol treasuries, DeFi vaults, proxy contracts without payable fallbacks) are a routine bridge use case; the `message` field in the payload already anticipates programmatic recipients. The trigger requires only one ordinary cross-chain transfer to a non-payable contract address — no special privileges, no collusion, no oracle manipulation. The condition is self-inflicted by normal user behaviour and is not recoverable after the fact. [2](#0-1) 

## Recommendation
Apply the pull-over-push pattern: on a failed ETH `call`, do **not** revert. Instead, record the unclaimed amount in a mapping keyed by `destinationNonce` (or `(destinationNonce, recipient)`), keep `completedTransfers[destinationNonce] = true` so the nonce is consumed, and expose a separate `claimEth(uint64 destinationNonce)` function that lets the original recipient (or an admin-designated fallback) withdraw. Alternatively, enforce `require(payload.recipient.code.length == 0, "ETH recipient must be EOA")` before the transfer so the failure is surfaced at initiation time on the source chain rather than after the cross-chain proof is submitted. [7](#0-6) 

## Proof of Concept
1. Deploy a contract `NoReceive` with no `receive()` or `fallback()` function on the target EVM chain.
2. On NEAR, call `initTransfer` with `tokenAddress = address(0)` (native ETH) and `recipient = address(NoReceive)`.
3. Wait for the MPC network to sign the `TransferMessage` payload embedding `NoReceive` as recipient.
4. Submit `OmniBridge.finTransfer(signatureData, payload)` with `msg.value = payload.amount`.
5. Observe: `NoReceive` has no `receive()`, so the low-level `call` returns `success = false`; the function reverts with `FailedToSendEther()`; `completedTransfers[destinationNonce]` remains `false`.
6. Repeat step 4 any number of times — every call reverts identically. The source-chain tokens are permanently locked.

A Foundry unit test can reproduce this in isolation: deploy `OmniBridge`, fund it with ETH, construct a valid signed payload targeting a non-payable contract, call `finTransfer`, and assert both that the call reverts and that `completedTransfers[nonce]` is still `false`. [7](#0-6)
