Audit Report

## Title
Missing Refund in `deploy_token_by_deployer_callback` Failure Branch Permanently Traps Caller's NEAR Deposit — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`deploy_token` is `#[payable]` and accepts a NEAR deposit to cover bridge storage and token deployment costs. When the downstream `TokenDeployer` cross-contract call fails, `deploy_token_by_deployer_callback` removes the state entries it created but never returns the caller's NEAR. The deposit is permanently absorbed into the bridge contract's balance with no user-accessible recovery path.

## Finding Description
`deploy_token` captures `env::attached_deposit()` and passes it into `deploy_token_callback`, which forwards it to `deploy_token_internal`. [1](#0-0) 

Inside `deploy_token_internal`, the deposit is split: `required_deposit` covers bridge-side storage (maps, sets), and the remainder is forwarded to the `TokenDeployer` contract. [2](#0-1) 

When the deployer call fails (e.g., `LackBalance` because the forwarded amount is insufficient for WASM code storage), the NEAR runtime refunds `attached_deposit - required_deposit` back to the bridge contract. `deploy_token_by_deployer_callback` is then invoked and removes the state entries — freeing the `required_deposit` storage — but issues no `Self::refund(...)` to the original caller. [3](#0-2) 

The `refund` helper exists and is used in `bind_token` via a trailing `bind_token_refund` callback that always runs and returns unused deposit to the predecessor. [4](#0-3) [5](#0-4) 

`deploy_token` has no equivalent trailing refund step, and a grep for `deploy_token_refund` returns no matches anywhere in the repository.

## Impact Explanation
The caller permanently loses their entire attached NEAR deposit. The freed storage NEAR and the runtime-refunded deployer amount both accumulate in the bridge contract's balance with no user-accessible recovery mechanism. This constitutes a direct, irreversible loss of user funds — matching the Critical allowed impact of "loss… of bridged funds across NEAR" and "fee mis-accounting… that changes user or protocol balances."

## Likelihood Explanation
The contract exposes `required_balance_for_deploy_token()` as the canonical minimum deposit, but this value does not include WASM code storage for the new token account. [6](#0-5) 

The integration test suite explicitly confirms that sending exactly this minimum causes the deployer call to fail with `LackBalance`. [7](#0-6) 

Any unprivileged user who queries `required_balance_for_deploy_token()` and uses that value as their deposit — the natural, documented usage pattern — will trigger the failure path and permanently lose their NEAR. The function is callable by any user when the contract is not paused.

## Recommendation
In the failure branch of `deploy_token_by_deployer_callback`, add a `Self::refund(predecessor, attached_deposit)` call. The original caller's account ID and the full deposit amount must be threaded through as callback arguments (mirroring how `bind_token` passes `predecessor_account_id` and `attached_deposit` to `bind_token_refund`). Alternatively, add a trailing `deploy_token_refund` callback chained after `deploy_token_by_deployer_callback` that always runs and returns any remaining balance to the predecessor, exactly as `bind_token` does.

## Proof of Concept
1. Call `required_balance_for_deploy_token()` → receive value `V`.
2. Call `deploy_token(args)` with exactly `V` NEAR attached.
3. `deploy_token_internal` consumes `required_deposit ≤ V` for bridge storage; forwards `V - required_deposit` to `TokenDeployer::deploy_token`.
4. `TokenDeployer::deploy_token` fails with `LackBalance` (WASM code storage requires additional NEAR beyond `V - required_deposit`).
5. NEAR runtime refunds `V - required_deposit` to the bridge contract's balance.
6. `deploy_token_by_deployer_callback` is called with `Err`; removes state entries (freeing `required_deposit` storage) but issues no `Self::refund(...)`.
7. Caller's wallet is reduced by `V` NEAR permanently; bridge contract balance increases by `V` with no user-accessible recovery path. The existing integration test at `near/omni-tests/src/omni_token.rs:582-597` already demonstrates step 4 reproducibly on a local sandbox.

    pub fn deploy_token_by_deployer_callback(
        &mut self,
        token_address: &OmniAddress,
        token_id: AccountId,
    ) -> PromiseOrValue<()> {
        if env::promise_result_checked(0, usize::MAX).is_ok() {
            ext_token::ext(token_id)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                .with_attached_deposit(NEP141_DEPOSIT)
                .storage_deposit(&env::current_account_id(), Some(true))
                .into()
        } else {
            self.deployed_tokens.remove(&token_id);
            self.deployed_tokens_v2.remove(&token_id);
            self.token_id_to_address
                .remove(&(token_address.get_chain(), token_id));
            self.token_address_to_id.remove(token_address);
            self.token_decimals.remove(token_address);
            PromiseOrValue::Value(())
        }
    }
