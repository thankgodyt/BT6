### Title
Hardcoded Zcash Network-Upgrade Activation Block Heights Are Not Admin-Configurable, Causing Permanent DoS of All Zcash Bridge Operations on Future Network Upgrades - (File: contracts/satoshi-bridge/src/network.rs)

### Summary
The `BranchIdUpdateBlockHeight` struct in `network.rs` hardcodes the Zcash NU6.1 and NU6.2 activation block heights as compile-time constants with no on-chain mechanism for the contract admin to update them. The `BranchId` derived from these heights is embedded in every Zcash V5 transaction the bridge constructs (withdrawals, refunds, UTXO management). When Zcash activates a future network upgrade (NU7, etc.), the bridge will permanently use the stale `BranchId::Nu6_2`, causing every constructed transaction to be rejected by Zcash nodes and locking all bridged ZEC.

### Finding Description

`BranchIdUpdateBlockHeight::new()` in `network.rs` hardcodes the activation heights for NU6.1 and NU6.2:

```rust
Chain::ZcashMainnet => Self {
    nu6_1_update: 3146400,
    nu6_2_update: 3364600,
},
Chain::ZcashTestnet => Self {
    nu6_1_update: 3536500,
    nu6_2_update: 4052000,
},
``` [1](#0-0) 

`Chain::get_branch_id()` calls this function and returns `BranchId::Nu6_2` for any block height at or above 3,364,600 (mainnet), with no upper bound and no fallback for future upgrades: [2](#0-1) 

`get_branch_id()` in `psbt_wrapper.rs` delegates directly to this hardcoded function: [3](#0-2) 

The resulting `BranchId` is stored in every `PsbtWrapper` and serialized into the PSBT hex stored on-chain: [4](#0-3) 

It is then embedded in the final Zcash V5 transaction header via `get_zcash_tx()`: [5](#0-4) 

The `to_bytes()` serializer also contains a hard `unreachable!()` arm that would panic if any future `BranchId` variant were ever returned: [6](#0-5) 

Neither `Config` nor `ConfigUpdate` expose any field for updating the activation block heights: [7](#0-6) [8](#0-7) 

The hardcoded heights are consumed in every Zcash-specific bridge operation: withdrawal initiation (`ft_on_transfer_callback`), UTXO management (`active_utxo_management_callback`), RBF (`withdraw_rbf_callback`, `active_utxo_management_rbf_callback`), and cancellation callbacks: [9](#0-8) [10](#0-9) 

### Impact Explanation

The Zcash consensus branch ID is part of the V5 transaction header and is validated by every Zcash full node. A transaction whose `nConsensusBranchId` field does not match the current network upgrade is unconditionally rejected. When Zcash activates a new upgrade (NU7 or later), the bridge will continue constructing transactions with `BranchId::Nu6_2`. Every such transaction will be rejected by the Zcash network. Because all withdrawal, refund, and UTXO-management paths go through `PsbtWrapper::new()` → `get_branch_id()` → hardcoded `Nu6_2`, none of these operations can succeed. ZEC held in bridge UTXOs becomes permanently unspendable from the bridge's perspective, and nZEC holders cannot redeem their tokens. This matches **Medium: stuck bridge state requiring operator intervention** (contract redeployment) and potentially **Critical: Zcash-specific validation failure that enables permanent loss** of bridged ZEC.

### Likelihood Explanation

Zcash has a well-established cadence of network upgrades: NU6, NU6.1, and NU6.2 all activated within the past two years. A future NU7 upgrade is a near-certainty. The bridge has no upgrade path for the activation heights short of a full contract redeployment, which itself requires migration of all on-chain UTXO and pending-info state. The window between a new upgrade activating and a redeployment completing is a period of total bridge DoS.

### Recommendation

1. Add `nu_upgrade_block_heights: HashMap<String, u32>` (or equivalent) to `Config` so the contract admin can register future activation heights via `update_config` without redeployment.
2. Make `Chain::get_branch_id()` consult the configurable map rather than the hardcoded `BranchIdUpdateBlockHeight` struct.
3. Remove the `_ => unreachable!()` arm in `PsbtWrapper::to_bytes()` and replace it with a proper error path so that an unsupported future `BranchId` produces a recoverable error rather than a panic.

### Proof of Concept

1. Zcash activates NU7 at mainnet block height N (N > 3,364,600).
2. A user calls `ft_transfer_call` on the nZEC contract to initiate a ZEC withdrawal.
3. The bridge calls `get_last_block_height_promise()`, receives block height N+k (k ≥ 0).
4. `ft_on_transfer_callback` calls `get_branch_id(N+k, config)` → `Chain::ZcashMainnet.get_branch_id(N+k)` → `BranchIdUpdateBlockHeight::new(ZcashMainnet)` returns `nu6_2_update = 3364600`; since `N+k >= 3364600`, the function returns `BranchId::Nu6_2`.
5. `PsbtWrapper::new()` stores `branch_id = BranchId::Nu6_2`.
6. After MPC signing, `get_zcash_tx()` constructs a V5 transaction with `consensus_branch_id = Nu6_2`.
7. The relayer broadcasts this transaction to the Zcash network; every node rejects it because the current consensus branch ID is `Nu7`, not `Nu6_2`.
8. The withdrawal is permanently stuck; the user's nZEC is locked in the bridge contract with no valid path to recover the underlying ZEC. [11](#0-10) [12](#0-11)

impl BranchIdUpdateBlockHeight {
    pub fn new(chain: &Chain) -> Self {
        match chain {
            Chain::ZcashMainnet => Self {
                nu6_1_update: 3146400,
                nu6_2_update: 3364600,
            },
            Chain::ZcashTestnet => Self {
                nu6_1_update: 3536500,
                nu6_2_update: 4052000,
            },
            _ => unreachable!(),
        }
    }
}
impl Chain {
    #[cfg(feature = "zcash")]
    pub fn get_branch_id(&self, block_height: u32) -> BranchId {
        let block_height_update = BranchIdUpdateBlockHeight::new(self);
        if block_height_update.nu6_2_update != 0 && block_height >= block_height_update.nu6_2_update
        {
            return BranchId::Nu6_2;
        }
        if block_height_update.nu6_1_update != 0 && block_height >= block_height_update.nu6_1_update
        {
            return BranchId::Nu6_1;
        }

        BranchId::Nu6
    }
