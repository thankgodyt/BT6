### Title
Unconditional Peras Certificate Acceptance via Stub `validatePerasCert` Bypasses All Cryptographic Checks - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic validation. Any unprivileged peer can send crafted `PerasCert` objects over the `PerasCertDiffusion` mini-protocol; these certificates pass the validation gate, are stored in the `PerasCertDB`/`ChainDB`, and their boost weight is applied during chain selection. This is a direct bypass of Peras certificate authorization, the analog of a privileged withdrawal function with no access-control guard.

### Finding Description

**Root cause — stub validation always succeeds:**

The universal `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of its content, is wrapped in `Right ValidatedPerasCert` and returned as valid. No BLS aggregate-signature verification, no committee-membership check, no round-number bounds check, and no boosted-block existence check is performed.

**Inbound network path:**

`makePerasCertPoolWriterFromChainDB` wires this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

`processCerts` calls `validateCert` on every certificate received from a peer. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
```

`addPerasCertAsync` enqueues the certificate on `cdbChainSelQueue`, which is consumed by `chainSelSync`. Chain selection then applies the `vpcCertBoost` weight from the fraudulent certificate when comparing candidate chains via `getPerasWeightSnapshot`.

**Complete attacker-controlled entry path:**

```
peer (node-to-node) 
  → aPerasCertDiffusionClient / objectDiffusionInbound
  → opwAddObjects (makePerasCertPoolWriterFromChainDB)
  → processCerts
  → validatePerasCert  ← always Right, no check
  → ChainDB.addPerasCertAsync
  → chainSelSync / chainSelection
  → switchTo  ← chain selection influenced by fraudulent boost
```

### Impact Explanation

An unprivileged peer can inject a `PerasCert` claiming any `pcCertRound` and any `pcCertBoostedBlock`. The certificate is accepted without signature verification and stored with a boost weight equal to `perasWeight params`. During chain selection, `preferAnchoredCandidate` uses the Peras weight snapshot; a fraudulent certificate boosting a non-canonical block can cause an honest node to switch to an adversary-controlled fork. This is a **Critical bypass of Peras certificate verification** that enables unauthorized certificate acceptance and a **High chain-selection bug** that lets an unprivileged peer make an honest node prefer a non-canonical chain.

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is wired into the node-to-node application in `NodeToNode.hs`. Any peer that successfully negotiates a node-to-node connection can send `PerasCert` objects. No stake, no keys, and no prior relationship are required. The stub is present in the production codebase with an explicit `TODO` comment acknowledging the missing validation. Exploitation requires only the ability to open a standard node-to-node connection and send a well-formed CBOR-encoded `PerasCert`.

### Recommendation

Replace the stub `validatePerasCert` implementation with full cryptographic validation before the Peras certificate diffusion path is reachable on any network. At minimum, the implementation must:

1. Verify the aggregate BLS signature (`pcSignature`) over `(pcRoundNo, pcBoostedBlock)` against the aggregate public key derived from the declared voters.
2. Verify each voter's committee-membership proof (VRF output for non-persistent members, stake-distribution lookup for persistent members).
3. Confirm the boosted block exists and is within the valid round window.
4. Reject certificates whose `pcCertRound` is outside the current protocol window.

Until the real implementation is in place, the `PerasCertDiffusion` mini-protocol should be disabled at the protocol-negotiation level so that no inbound certificates can reach `processCerts`.

### Proof of Concept

1. Connect to a target node via the node-to-node protocol and negotiate a version that includes `PerasCertDiffusion`.
2. Craft a `PerasCert` (CBOR list of 4 fields: `pcRoundNo`, `pcBoostedBlock`, `pcVoters`, `pcSignature`) targeting any block hash on a minority fork.
3. Send the certificate via the `ObjectDiffusion` outbound protocol.
4. The node calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{..}`.
5. The certificate is enqueued via `addPerasCertAsync` and processed by `chainSelSync`.
6. Chain selection applies the boost weight to the targeted block; if the boosted fork now scores higher than the current chain, `switchTo` is called and the node adopts the adversary-chosen fork.
