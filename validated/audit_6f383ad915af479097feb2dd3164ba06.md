### Title
Insufficient Gas Stipend for `burn` Cross-Contract Call Causes Permanent Withdrawal Stuck State and Supply Inflation - (File: `contracts/satoshi-bridge/src/nbtc/burn.rs`)

---

### Summary

`GAS_FOR_BURN_CALL` is set to only **5 TGas** for the cross-contract call to `nbtc.burn()`. The `burn` function performs multiple NEAR storage operations (LookupMap reads and writes, conditional account registration, token transfer, and event emission) that require significantly more than 5 TGas. This causes the burn call to consistently fail with an out-of-gas error. The primary consequence is that withdrawal finalization is permanently broken: BTC has already been sent to the user on Bitcoin, but nBTC tokens are never burned, creating a stuck bridge state and permanent supply inflation below backed supply.

---

### Finding Description

`GAS_FOR_BURN_CALL` is defined as 5 TGas in `contracts/satoshi-bridge/src/nbtc/burn.rs`:

```rust
pub const GAS_FOR_BURN_CALL: Gas = Gas::from_tgas(5);
```

This constant is used in three call sites:

**1. `verify_withdraw_burn_promise` (withdrawal finalization):**
```rust
ext_nbtc::ext(config.nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)   // only 5 TGas
    .burn(...)
    .then(Self::ext(...).verify_withdraw_burn_callback(...))
```

**2. `verify_active_utxo_management_burn_promise` (UTXO management):**
```rust
ext_nbtc::ext(...)
    .with_static_gas(GAS_FOR_BURN_CALL)   // only 5 TGas
    .burn(...)
```

**3. `safe_mint_callback` (safe deposit failure cleanup — detached):**
```rust
ext_nbtc::ext(...)
    .with_static_gas(GAS_FOR_BURN_CALL)   // only 5 TGas
    .burn(...)
    .detach();
```

The `burn` function in `contracts/nbtc/src/lib.rs` performs the following operations, each consuming gas:

```rust
pub fn burn(&mut self, burn_account_id, burn_amount, relayer_account_id, relayer_fee) {
    self.assert_bridge();                                    // predecessor check
    self.token.internal_withdraw(&self.bridge_id, ...);     // LookupMap read + write
    if relayer_fee.0 > 0 {
        if self.token.accounts.get(&relayer_account_id).is_none() {
            self.token.internal_register_account(...);       // storage write (new account)
        }
        self.token.internal_transfer(...);                   // LookupMap read + write
    }
    FtBurn { ... }.emit();                                   // logging
}
```

NEAR's base gas costs for storage operations are approximately:
- `storage_read` (LookupMap get): ~5.5 TGas
- `storage_write` (LookupMap insert): ~10 TGas

Even the minimal path through `burn` (no relayer fee) requires `internal_withdraw`, which performs one storage read and one storage write: ~15.5 TGas minimum. This already exceeds the 5 TGas budget. When a relayer fee is nonzero and the relayer account is unregistered, the cost is even higher (~30+ TGas).

For comparison, `GAS_FOR_MINT_CALL` — used for the analogous `mint` cross-contract call — is set to **90 TGas**, an 18× difference that confirms `GAS_FOR_BURN_CALL` is severely misconfigured.

---

### Impact Explanation

**Primary path — `verify_withdraw_burn_promise`:**

When `verify_withdraw_burn_callback` receives a failed burn promise, it executes:
```rust
} else {
    self.internal_unwrap_mut_btc_pending_info(&tx_id)
        .to_pending_verify_stage();
}
```

The state reverts to `pending_verify_stage`, allowing the relayer to retry `verify_withdraw`. However, since 5 TGas is always insufficient for `burn`, every retry fails identically. The result is:

- The BTC transaction is confirmed on-chain and the user has received their BTC.
- The nBTC tokens (transferred to the bridge during `ft_on_transfer`) are permanently stuck in the bridge balance and can never be burned.
- The nBTC total supply permanently exceeds the BTC backing — supply inflation below backed supply.
- The bridge state is stuck and requires operator intervention to resolve.

**Secondary path — `safe_mint_callback` (detached burn):**

When `safe_mint` fails for an unregistered recipient, `safe_mint_callback` removes the UTXO from `verified_deposit_utxo` and fires a detached burn with 5 TGas:
```rust
self.data_mut().verified_deposit_utxo.remove(&pending_utxo_info.utxo_storage_key);
ext_nbtc::ext(...).with_static_gas(GAS_FOR_BURN_CALL).burn(...).detach();
```

The detached burn fails silently. The bridge retains unbacked nBTC tokens (minted to the bridge in `safe_mint`'s `internal_deposit` call), and the UTXO is no longer in `verified_deposit_utxo`, potentially allowing re-deposit via the standard `verify_deposit` path, which could lead to double-minting.

---

### Likelihood Explanation

The failure is deterministic and affects every withdrawal finalization. Any user who initiates a withdrawal via `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)` will find their withdrawal permanently stuck once the BTC transaction is confirmed on-chain. No special attacker capability is required — this is triggered by the normal public bridge flow. The `safe_mint_callback` path is triggered whenever `safe_verify_deposit` is called for an unregistered recipient, which is a documented and expected scenario (Omni Bridge integration).

---

### Recommendation

Increase `GAS_FOR_BURN_CALL` to a value sufficient for the `burn` function's storage operations. Given that `GAS_FOR_MINT_CALL` is 90 TGas for the analogous `mint` call, and `burn` performs a comparable number of storage operations, `GAS_FOR_BURN_CALL` should be set to at least **10–15 TGas** for the no-relayer-fee path and **20–30 TGas** when relayer fee and account registration are included. A conservative safe value aligned with `GAS_FOR_MINT_CALL` would be appropriate. Additionally, the detached burn in `safe_mint_callback` should be monitored or replaced with a pattern that handles failure explicitly rather than silently discarding the result.

---

### Proof of Concept

1. User calls `nbtc.ft_transfer_call(bridge_id, 100_000, WithdrawMsg { target_btc_address, input, output })`.
2. Bridge's `ft_on_transfer` returns `0`, keeping the tokens; a `BTCPendingInfo` is created.
3. Bridge constructs a BTC transaction, Chain Signatures signs it; user broadcasts it to Bitcoin.
4. BTC transaction is confirmed on-chain.
5. Relayer calls `bridge.verify_withdraw(tx_id, proof)`.
6. `internal_verify_withdraw_callback` succeeds (light client confirms inclusion), transitions state to `pending_burn_stage`, calls `verify_withdraw_burn_promise`.
7. `ext_nbtc::ext(...).with_static_gas(Gas::from_tgas(5)).burn(...)` is dispatched. The `burn` function in nbtc attempts `internal_withdraw` (LookupMap read ~5.5 TGas + write ~10 TGas = ~15.5 TGas), immediately exhausting the 5 TGas budget → out-of-gas failure.
8. `verify_withdraw_burn_callback` receives `is_promise_success() == false`, calls `to_pending_verify_stage()`.
9. Relayer retries step 5 — identical failure every time.
10. **Result**: BTC is in the user's wallet. The nBTC tokens remain in the bridge balance forever. `nbtc.ft_total_supply()` permanently exceeds the BTC backing. The bridge is stuck and requires operator intervention. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
