Audit Report

## Title
Fee Validity Check Before Decimal Normalization Causes Permanent Token Lock - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates `fee < amount` using raw NEAR-native token amounts and immediately burns or locks the full `amount`. When `sign_transfer` is later called, it normalizes `amount - fee` via floor division to the destination chain's decimal precision. If `amount - fee` is smaller than the normalization divisor, the result is zero, causing `sign_transfer` to permanently revert with `InvalidAmountToTransfer` — while the user's tokens are already irreversibly burned or locked with no recovery path.

## Finding Description

**Step 1 — `init_transfer` / `init_transfer_internal`:**

The fee validity check at [1](#0-0)  operates on raw NEAR-native amounts with no awareness of destination-chain decimal precision. Immediately after this check passes, `init_transfer_internal` burns or locks the full `amount`: [2](#0-1) 

**Step 2 — `sign_transfer` (separate transaction, called later by a relayer):**

`sign_transfer` resolves the destination token's decimals and normalizes the net amount via floor division: [3](#0-2) 

`normalize_amount` uses floor division: [4](#0-3) 

`amount_without_fee` is simply `amount - fee`: [5](#0-4) 

**Why existing guards fail:**

`update_transfer_fee` enforces `fee.fee >= current_fee.fee`, meaning the fee can only be increased, never decreased: [6](#0-5) 

No `cancel_transfer` or refund function exists in the contract. When `sign_transfer` reverts, it is a separate transaction from `init_transfer`, so the token burn/lock from Step 1 is not rolled back. The transfer is permanently stuck.

## Impact Explanation

This constitutes **permanent, irrecoverable freezing of bridged funds** — a concrete Critical impact under the allowed scope ("permanent freezing of bridged funds across NEAR, EVM, Solana..."). The user's tokens are burned or locked in Step 1 and can never be recovered because Step 2 will always revert and no cancel/refund path exists.

## Likelihood Explanation

Triggerable by any unprivileged user via `ft_transfer_call` (a public token callback). The condition is realistic for any token with a large decimal difference between origin and destination chains. For a token with `origin_decimals = 24` and `destination_decimals = 6`, the normalization divisor is `10^18`. Any transfer where `amount - fee < 10^18` (i.e., less than 1 full destination-chain token unit) produces a zero normalized amount. A user sending `amount = 2, fee = 1` in raw units satisfies `fee < amount` but yields `normalize_amount(1, {24, 6}) = 0`. This is a realistic user mistake given that the fee check gives no indication of the decimal mismatch.

## Recommendation

Compute `normalize_amount(amount - fee, decimals)` inside `init_transfer_internal` — after resolving the destination token's decimals — and revert immediately if the result is zero, **before** any call to `burn_tokens_if_needed` or `lock_tokens_if_needed`. This mirrors the pattern already used in `sign_transfer` but must be enforced earlier, before irreversible state changes occur.

## Proof of Concept

1. Register token `T` with `origin_decimals = 24`, `destination_decimals = 6` (divisor = `10^18`).
2. User calls `ft_transfer_call` with `amount = 2` (raw units) and `InitTransferMsg { fee: 1, ... }`.
3. `init_transfer` checks `1 < 2` → passes. [1](#0-0) 
4. `init_transfer_internal` burns 2 units of `T` from the user. [7](#0-6) 
5. Transfer is stored in `pending_transfers`.
6. Relayer calls `sign_transfer`. `normalize_amount(2 - 1, {24, 6}) = 1 / 10^18 = 0`. [4](#0-3) 
7. `require!(amount_to_transfer > 0, ...)` reverts. [8](#0-7) 
8. The transfer is permanently stuck. `update_transfer_fee` cannot help (fee can only increase, not decrease). No cancel path exists. The 2 units of `T` are burned with no recovery. [6](#0-5)
