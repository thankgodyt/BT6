### Title
Hard-Fork Era Transition Accepted Despite Chain Growth Violation Due to Incorrect Block Counting Window in `shelleyAfterVoting` — (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `ShelleyTransitionInfo.shelleyAfterVoting` counter in `applyHelper` accumulates **all** blocks after the voting deadline, but the intended design (Iteration 4 of the HFC's Chain Growth violation handling) requires counting only blocks within the **stability window** (`3k/f` slots) immediately after the voting deadline. When a Chain Growth violation occurs in that window, the node may still reach the `k`-block threshold by counting blocks from the second half of the post-deadline period, causing it to signal an era transition that should have been suppressed. This is a self-acknowledged bug in the codebase.

---

### Finding Description

**Root cause — `applyHelper` in `Ledger.hs`:**

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [1](#0-0) 

The `votingDeadline` is computed as `startOfNextEpoch - 2 * swindow`, placing it `4k/f` slots before the epoch boundary. The stability window is `3k/f` slots. The code increments `shelleyAfterVoting` for every block whose slot is `>= votingDeadline`, covering the full `2 * swindow = 6k/f`-slot post-deadline period. [2](#0-1) 

**Intended behavior — `civic_time.md`:**

The design document explicitly states the intended rule for Iteration 4:

> "Silently ignore the on-chain governance … if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth)."
> "(TODO this is today's intended behavior, but **a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window**.)" [3](#0-2) 

**Decision point — `shelleyTransition` in `ShelleyHFC.hs`:**

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
return newPParamsEpochNo
``` [4](#0-3) 

When `shelleyAfterVoting` reaches `k`, `singleEraTransition` returns `Just epoch`, signalling the HFC to transition. Because the counter spans `6k/f` slots instead of `3k/f`, a node can reach `k` blocks even when the stability window itself contained fewer than `k+1` blocks — the exact condition under which the transition should be suppressed.

**Counter reset — `applyChainTickLedgerResult`:**

The counter is correctly reset to `0` at each epoch boundary, so the window is bounded to the current epoch. The bug is that within that epoch the window is `6k/f` slots wide rather than `3k/f`. [5](#0-4) 

**`ShelleyTransitionInfo` documentation confirms the intent:**

```haskell
-- 3. If we count how many blocks we have seen post deadline, and we have
--    reached k of them, we know that that last pre-deadline block won't
--    be rolled back anymore.
``` [6](#0-5) 

The comment describes the correct intent (k blocks in the stability window), but the implementation counts over a window twice as wide.

---

### Impact Explanation

When a Chain Growth violation occurs in the `3k/f`-slot stability window after the voting deadline (e.g., due to a network partition that suppresses block production in that window), the node should suppress the era transition. Instead, because blocks from the second `3k/f`-slot window are also counted, the node may accumulate `k` post-deadline blocks and signal `TransitionKnown` to the HFC. This causes `reconstructSummaryLedger` to embed the next era's start bound into the `Summary`, extending the forecast range across the era boundary. [7](#0-6) 

Nodes that have not yet accumulated `k` post-deadline blocks (e.g., nodes that are slightly behind) will compute `TransitionUnknown` and keep the forecast range within the current era. The two populations of nodes now hold divergent `Summary` values for the same ledger state, producing different slot/epoch/time translations and different era assignments for the same headers. This breaks the `ImmutableTranslations` and `MonotonicTranslations` invariants the HFC is designed to guarantee, and constitutes a hard-fork/era-transition mismatch that can cause cross-era consensus failure. [8](#0-7) 

---

### Likelihood Explanation

The bug requires a Chain Growth violation in the `3k/f`-slot window immediately after the voting deadline. On Cardano mainnet (`k=2160`, `f=0.05`), this window is 129,600 slots (~36 hours). A natural network partition of that duration, or an adversary suppressing honest block production in that window while allowing blocks to appear in the subsequent `3k/f`-slot window, would trigger the discrepancy. Such conditions are rare but not impossible, and the bug is already acknowledged as a known defect in the codebase. The impact is bounded to epochs in which a governance vote is pending and a Chain Growth violation coincides with the stability window.

---

### Recommendation

Track the slot of the first block after the voting deadline and only increment `shelleyAfterVoting` for blocks whose slot falls within `[votingDeadline, votingDeadline + swindow)`. Alternatively, record the block number of the first post-deadline block and count only blocks within the next `swindow` slots from that anchor, matching the precise condition described in the Iteration 4 design.

---

### Proof of Concept

Concrete parameters: `k = 2160`, `f = 0.05`, `swindow = 3k/f = 129600` slots, epoch = `10k/f = 432000` slots.

1. Voting deadline = `startOfNextEpoch − 259200` (slot `T`).
2. Stability window = slots `[T, T+129600)`.
3. Adversary (or partition) suppresses honest block production in `[T, T+129600)`: only `k−1 = 2159` blocks appear.
4. Normal production resumes in `[T+129600, T+259200)`: `2` more blocks appear, bringing the total post-deadline count to `2161 ≥ k`.
5. `shelleyAfterVoting` reaches `k = 2160`; `shelleyTransition` returns `Just epoch`.
6. The HFC signals `TransitionKnown` and embeds the next era's start in the `Summary`.
7. A peer node that has only processed blocks up to slot `T+129600` has `shelleyAfterVoting = 2159 < k`, computes `TransitionUnknown`, and keeps the forecast range in the current era.
8. The two nodes now disagree on the era of headers in the transition epoch, breaking cross-era consensus.

reconstructSummary ::
  History.Shape xs ->
  -- | At the tip
  TransitionInfo ->
  HardForkState f xs ->
  History.Summary xs
reconstructSummary (History.Shape shape) transition (HardForkState st) =
  History.Summary $ go shape st
 where
  go ::
    Exactly xs' EraParams ->
    Telescope (K Past) (Current f) xs' ->
    NonEmpty xs' EraSummary
  go ExactlyNil t = case t of {}
  go (ExactlyCons params ss) (TS (K Past{..}) t) =
    NonEmptyCons (EraSummary pastStart (EraEnd pastEnd) params) $ go ss t
  go (ExactlyCons params ss) (TZ Current{..}) =
    case transition of
      TransitionKnown epoch ->
        -- We haven't reached the next era yet, but the transition is
        -- already known. The safe zone applies from the start of the
        -- next era.
        let currentEnd = History.mkUpperBound params currentStart epoch
            nextStart = currentEnd
         in case ss of
              ExactlyCons nextParams _ ->
                NonEmptyCons
                  EraSummary
                    { eraStart = currentStart
                    , eraParams = params
                    , eraEnd = EraEnd currentEnd
                    }
                  $ NonEmptyOne
                    EraSummary
                      { eraStart = nextStart
                      , eraParams = nextParams
                      , eraEnd =
                          applySafeZone
                            nextParams
                            nextStart
                            (boundSlot nextStart)
                      }
