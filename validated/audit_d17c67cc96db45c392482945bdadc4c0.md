Audit Report

## Title
Detached `send_tokens` Promise After Irreversible State Mutation in UTXO Fast Transfer Finalization Causes Permanent Relayer Fund Loss — (`near/omni-bridge/src/lib.rs`)

## Summary
In `utxo_fin_transfer_fast()`, the fast-transfer accounting state is permanently mutated — either via `remove_fast_transfer()` or `mark_fast_transfer_as_finalised()` — before `send_tokens()` is dispatched as a detached promise whose result is silently discarded. If `send_tokens` fails (e.g., `ft_transfer` panics because the relayer has no storage deposit registered with the UTXO token contract), the relayer's fronted tokens remain permanently locked inside the bridge with no recovery path. The same pattern appears in `process_fin_transfer_to_other_chain()`. The code itself acknowledges this gap with an explicit `TODO` comment.

## Finding Description
In `utxo_fin_transfer_fast()` (lines 2518–2561), the function first permanently mutates state:

- NEAR destination: `self.remove_fast_transfer(&fast_transfer.id())` at line 2530 — record is **deleted**.
- Other-chain destination: `self.mark_fast_transfer_as_finalised(&fast_transfer.id())` at line 2533 — record is **permanently locked**.

Immediately after, `send_tokens(...).detach()` is called at lines 2542–2548, discarding the promise result entirely. The function then returns `PromiseOrPromiseIndexOrValue::Value(U128(0))` synchronously — there is no callback to observe whether the token transfer succeeded.

In `send_tokens()` (lines 2102–2106), when `msg` is empty and the token is neither wNEAR nor a deployed bridge token, the call resolves to `ext_token::ext(token).ft_transfer(recipient, amount, None)`. The NEP-141 `ft_transfer` method panics if the recipient account has no storage deposit registered with that token contract, causing the detached promise to fail silently.

The same detach-then-mutate pattern appears in `process_fin_transfer_to_other_chain()` (lines 2028–2040): `send_tokens(...).detach()` at line 2039 is followed by `mark_fast_transfer_as_finalised()` at line 2040 in the same synchronous frame.

The code explicitly acknowledges this is unresolved at line 2484:
```rust
// TODO: check how to deal with failed send_tokens
return self.utxo_fin_transfer_fast(fast_transfer, status, utxo_fin_transfer_msg);
```

By contrast, the non-UTXO fast-transfer-to-NEAR path (lines 1967–1977) correctly chains a `fin_transfer_send_tokens_callback` that can observe and react to promise failure. The UTXO fast-transfer path has no equivalent callback.

## Impact Explanation
When `send_tokens` fails silently: (1) the fast-transfer record is either deleted or permanently locked — neither state can be undone; (2) the relayer's fronted tokens (transferred to the bridge during `fast_fin_transfer`) remain in the bridge contract with no withdrawal or recovery function; (3) the UTXO connector's tokens consumed by the bridge are also unrecoverable. This constitutes **permanent freezing of bridged funds**, matching the critical allowed impact scope.

## Likelihood Explanation
`ft_transfer` panics — and thus the detached promise fails — if the recipient (the relayer) does not have a storage deposit registered with the UTXO-chain token contract (e.g., the wrapped BTC token). A relayer who has not explicitly registered storage with that specific token contract will trigger this failure path during normal protocol operation. No malicious action is required; the UTXO connector is a legitimate, DAO-configured protocol participant whose `ft_transfer_call` is the standard finalization entry point. The relayer is a legitimate protocol participant executing the documented fast-transfer flow.

## Recommendation
Replace the `.detach()` call in `utxo_fin_transfer_fast` with a chained callback (analogous to `fin_transfer_send_tokens_callback`) that: (1) checks whether `send_tokens` succeeded; (2) if it failed, reverts the fast-transfer state — re-inserts the fast-transfer record (or un-marks it as finalised) so the relayer's tokens can be recovered on a subsequent retry. The same fix should be applied to the fast-transfer branch in `process_fin_transfer_to_other_chain`. Additionally, consider pre-checking or pre-registering storage for the relayer before dispatching `send_tokens`.

## Proof of Concept
1. A trusted relayer calls `fast_fin_transfer` on the bridge, fronting `amount - fee` tokens to the recipient. The bridge stores the fast-transfer record.
2. The UTXO connector later calls `ft_transfer_call` to the bridge with a `UtxoFinTransferMsg` matching the same transfer, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Inside `utxo_fin_transfer_fast` (line 2530), `remove_fast_transfer()` is called, deleting the record.
4. `send_tokens(token_id, relayer, amount, "").detach()` (lines 2542–2548) is dispatched. Because the relayer has no storage deposit registered with the UTXO token contract, `ft_transfer` panics inside the detached promise.
5. The panic is silently discarded. The fast-transfer record is gone. The relayer's fronted tokens remain in the bridge. No recovery is possible.

A local integration test can reproduce this by: deploying a mock NEP-141 token that panics on `ft_transfer` when the recipient has no storage; executing the fast-transfer registration followed by the UTXO finalization call; and asserting that the fast-transfer record is absent while the relayer's balance on the token contract remains unchanged.
