### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Crafted Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. This stub is wired directly into the live node-to-node Peras certificate diffusion handler. Any unprivileged peer can send a crafted `PerasCert` targeting any block at any round, and the node will accept it, store it in the ChainDB, and apply its chain-selection weight boost — without any quorum, signature, voter eligibility, or round-number verification.

### Finding Description

**Root cause — stub validator always succeeds:**

The sole production implementation of `validatePerasCert` is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs`. Its body is:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No check is performed on `cert`. Every certificate, regardless of content, is returned as `Right (ValidatedPerasCert ...)` with a boost of `perasWeight params = PerasWeight 15`. [1](#0-0) 

**Call path — stub is used in the live node-to-node handler:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` applies `validateCert <$> certsNotAlreadyInDb`. Since the validator always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

This writer is registered in the production node-to-node `Handlers` record under `hPerasCertDiffusionClient`: [4](#0-3) 

**What is skipped:** The `BlockSupportsPeras` type class contract requires `validatePerasCert` to verify quorum stake threshold, voter eligibility, aggregate BLS signature, round-number bounds, and boosted-block validity. None of these are checked. [5](#0-4) 

The quorum threshold is defined as `3/4 + 2/100` of total stake in `mkPerasParams`, meaning a certificate should only be valid if it represents ≥77% of stake. The stub bypasses this entirely. [6](#0-5) 

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

A peer can craft a `PerasCert` with `pcCertRound = r` and `pcCertBoostedBlock = p` for any round `r` and any block point `p` it wishes to boost. The node will:

1. Accept the certificate unconditionally.
2. Store it in the ChainDB.
3. Apply `vpcCertBoost = PerasWeight 15` to block `p` during chain selection weight computation.

By boosting a non-canonical or adversarially-chosen block, the attacker can cause an honest node to prefer a less-secure or non-canonical chain over the honest chain, violating Peras chain-selection invariants. Multiple crafted certificates for the same block compound the effect.

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production node-to-node handler. Any peer that successfully completes the node-to-node handshake can send `PerasCert` objects. No stake, key, or privileged role is required. The attack requires only the ability to connect as a normal peer and send a well-formed (but semantically invalid) certificate CBOR message.

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs at minimum:
- Quorum stake threshold check (≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` of total stake).
- Voter eligibility verification against the current stake distribution.
- Aggregate BLS signature verification.
- Round-number and boosted-block validity checks.

Until a full implementation is ready, the Peras certificate diffusion inbound handler should be disabled or should reject all inbound certificates rather than accepting them unconditionally. The `TODO` comment at line 103 of `PerasCert.hs` acknowledges this is a placeholder, but the placeholder's behavior (accept everything) is the unsafe direction. [7](#0-6) 

### Proof of Concept

1. Connect to a running node as a normal peer (no privileged keys needed).
2. Complete the node-to-node handshake to negotiate a protocol version that includes `hPerasCertDiffusionClient`.
3. Send a `PerasCert` CBOR message with `pcCertRound = 999` and `pcCertBoostedBlock = <point of any block in the node's VolatileDB>`.
4. The node calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })`.
5. The certificate is stored via `ChainDB.addPerasCertAsync`.
6. Chain selection now applies a weight of 15 to the targeted block, potentially causing the node to switch to a fork containing that block.

Repeating step 3 with different `pcCertRound` values (each round is deduplicated by round number, so a new round number is needed per injection) allows an attacker to accumulate arbitrary chain-selection weight on a chosen block.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
