Looking at the exact code path across `api/bridge.rs`, `account.rs`, `btc_pending_info.rs`, `refund.rs`, and `chain_signature.rs`.

**Key facts established:**

**1. `cancel_withdraw` checks the user's pending sign capacity, not the caller's:** [1](#0-0) 

The function is DAO/Operator-gated but calls `require_pending_sign_capacity(&user_account_id)` — the *withdrawal owner's* account, not the privileged caller's.

**2. `require_pending_sign_capacity` panics unconditionally when at limit:** [2](#0-1) 

Default `max_pending_sign_txs` is 1. [3](#0-2) 

**3. `finalize_refund_with_psbt` inserts a `Refund(PendingSign)` entry into the user's `btc_pending_sign_ids`:** [4](#0-3) 

**4. Items are removed from `btc_pending_sign_ids` only when all signatures are collected (move to PendingVerify):** [5](#0-4) 

**5. `execute_refund` is publicly callable** — it has no individual `#[trusted_relayer]` or `#[access_control_any]` attribute, only `#[pause]`. The impl-level `#[trusted_relayer]` does not apply to all methods (confirmed by `cancel_withdraw`, `withdraw_rbf`, `active_utxo_management` in the same impl block having no such restriction): [6](#0-5) 

**Concrete attack path:**

1. User has withdrawal in `PendingVerify` state → removed from `btc_pending_sign_ids` (count = 0).
2. User has a deposit that was never finalized (e.g., sent BTC to a deposit address with a `post_actions` that fails, so the relayer never calls `verify_deposit`).
3. User calls `request_refund` (publicly callable, no role restriction beyond `gas_fee` param) with a valid BTC inclusion proof.
4. After timelock, user calls `execute_refund` → `finalize_refund_with_psbt` inserts `Refund(PendingSign)` into user's `btc_pending_sign_ids` (count = 1 = max).
5. DAO/Operator calls `cancel_withdraw(withdrawal_id, output)` → `require_pending_sign_capacity(&user_account_id)` panics: `"Too many pending sign transactions"`.

**Alternative simpler path** (requires user to hold extra nBTC): User initiates a second withdrawal while withdrawal 1 is in `PendingVerify`. The second withdrawal's `PendingSign` entry fills the slot, blocking `cancel_withdraw` on withdrawal 1.

**Why the blocking is real:** The cancel RBF (`WithdrawCancelRbf`) pending info that `cancel_withdraw` is about to create would be owned by the user's account and inserted into `btc_pending_sign_ids`. The capacity check guards this insertion. There is no bypass for privileged callers.

**Operator remediation path:** Operator must call `reject_refund` to remove the refund request, then `remove_refund_pending_tx_id` to remove the stale refund pending info, freeing the slot before retrying `cancel_withdraw`. [7](#0-6)

### Title
Unprivileged user can block DAO/Operator `cancel_withdraw` by filling their pending-sign slot with a refund — (`contracts/satoshi-bridge/src/api/bridge.rs`, `account.rs`)

### Summary
`cancel_withdraw` (DAO/Operator-only) calls `require_pending_sign_capacity` on the *withdrawal owner's* account before creating the cancel-RBF pending info. A user can fill their single pending-sign slot with a `Refund(PendingSign)` entry by calling the public `execute_refund`, causing `cancel_withdraw` to panic and preventing the operator from canceling the withdrawal until the blocking entry is manually cleared.

### Finding Description
`cancel_withdraw` in `api/bridge.rs` (line 291) calls `self.require_pending_sign_capacity(&user_account_id)` where `user_account_id` is the account that owns the pending withdrawal — not the DAO/Operator caller. `require_pending_sign_capacity` in `account.rs` (line 114) panics with `"Too many pending sign transactions"` if `pending_sign_count() >= max_pending_sign_txs` (default: 1).

A `Refund(PendingSign)` entry is inserted into `btc_pending_sign_ids` by `finalize_refund_with_psbt` (line 374 of `refund.rs`) when `execute_refund` is called. `execute_refund` is publicly callable (no role restriction). Once the user's slot is filled, every call to `cancel_withdraw` on their withdrawal panics, regardless of the caller's privilege level.

### Impact Explanation
DAO/Operator cannot cancel the user's stuck withdrawal. The bridge funds locked in the withdrawal remain unresolvable until an operator manually clears the blocking refund pending info via `reject_refund` + `remove_refund_pending_tx_id`. This is attacker-triggered temporary locking of bridged funds requiring operator intervention.

### Likelihood Explanation
The user needs a withdrawal in `PendingVerify` state and a refund request eligible for execution. Both are normal bridge states. The user can engineer this by making a deposit with a `post_actions` that fails (so the relayer never finalizes it), then requesting a refund. The attack requires no special privilege and only standard NEAR gas + storage deposit.

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` (and `cancel_active_utxo_management`). The capacity check exists to prevent users from creating unbounded pending-sign entries; it should not gate privileged operator actions. The cancel-RBF pending info can be created unconditionally by the DAO/Operator regardless of the user's current pending-sign count. Alternatively, associate the cancel-RBF pending info with the operator's account rather than the user's account.

### Proof of Concept
```
State setup:
  user.btc_pending_sign_ids = {}          // withdrawal moved to PendingVerify
  user.btc_pending_verify_list = { withdrawal_1_id }
  refund_requests = { utxo_key: RefundRequest { ... } }  // timelock elapsed

Step 1: user calls execute_refund(utxo_key)
  → finalize_refund_with_psbt(caller=user, ...)
  → require_pending_sign_capacity(user)  // passes: count=0 < max=1
  → btc_pending_sign_ids.insert(refund_pending_id)
  // user.btc_pending_sign_ids = { refund_pending_id }

Step 2: DAO calls cancel_withdraw(withdrawal_1_id, output)
  → user_account_id = withdrawal_1.account_id = user
  → require_pending_sign_capacity(user)
  // pending_sign_count() = 1 >= max_pending_sign_txs = 1
  → PANIC: "Too many pending sign transactions"

cancel_withdraw is blocked until operator calls:
  reject_refund(utxo_key) + remove_refund_pending_tx_id(refund_pending_id)
```

    pub(crate) fn internal_remove_refund_pending_tx_id(&mut self, tx_id: String) {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_related();

        // A refund spends exactly one deposit UTXO, whose key is the refund request key.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        require!(
            !self
                .data()
                .refund_requests
                .contains_key(&utxo_storage_keys[0]),
            "refund request still active"
        );

        let account_id = btc_pending_info.account_id.clone();
        self.internal_remove_btc_pending_info(&tx_id);
        let account = self.internal_unwrap_mut_account(&account_id);
        account.btc_pending_sign_ids.remove(&tx_id);
        account.btc_pending_verify_list.remove(&tx_id);
