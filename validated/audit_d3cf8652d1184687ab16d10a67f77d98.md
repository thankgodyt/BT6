### Title
Unsolicited Refund Request With Attacker-Controlled BTC Address Enables Theft of Unverified Deposits - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is a public, permissionless function that accepts a `deposit_msg` (identifying the victim's deposit) and a caller-supplied `refund_address`. When `deposit_msg.refund_address` is `None`, there is no validation that the caller is the owner of the deposit. An attacker who observes a pending, unverified BTC deposit can submit a refund request for it with their own BTC address as the destination, and after the timelock, execute the refund to steal the victim's BTC.

### Finding Description

`request_refund` performs no check that `env::predecessor_account_id()` matches the NEAR account embedded in `deposit_msg`. The only caller-identity check is for the optional `gas_fee` parameter: [1](#0-0) 

Inside `internal_request_refund`, the `refund_address` is only validated against `deposit_msg.refund_address` when the latter is `Some`. When it is `None`, any caller-supplied BTC address is accepted without restriction: [2](#0-1) 

The `deposit_msg` used to derive the deposit address is emitted publicly via `Event::LogDepositAddress` in `get_user_deposit_address`: [3](#0-2) 

The BTC transaction bytes are public on the Bitcoin blockchain. An attacker can therefore reconstruct all inputs needed to call `request_refund` for a victim's deposit.

In `request_refund_callback`, the stored `RefundRequest` records the attacker-supplied `refund_address` and the current `block_timestamp` as `created_at_sec`: [4](#0-3) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless — anyone can call it: [5](#0-4) 

The refund PSBT is built to pay `refund_amount` to the stored `refund_address` (the attacker's address), not to the original depositor: [6](#0-5) 

### Impact Explanation

If the DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the bridge's MPC pipeline constructs and signs a Bitcoin transaction paying the victim's deposit amount (minus gas fee) to the attacker's BTC address. This constitutes unauthorized release and theft of user BTC funds — a Critical impact matching "Unauthorized minting, reminting, unlocking, release, or claiming of nBTC/nZEC or underlying BTC/ZEC."

### Likelihood Explanation

- `deposit_msg` is emitted on-chain via `LogDepositAddress` events and is fully reconstructable by any observer.
- BTC transaction bytes are public on the Bitcoin network.
- The attack window is the period between the BTC deposit being confirmed and `verify_deposit` being called by the relayer. During high load or relayer downtime this window can be significant.
- The attacker must pay the storage deposit for `request_refund`, which is a minor cost.
- The only mitigation is DAO/Operator rejection during `unsafe_refund_timelock_sec`. If the DAO is slow, offline, or the request is not noticed, the attack succeeds.

### Recommendation

Validate that the caller of `request_refund` is the NEAR account identified in `deposit_msg`. Add a check analogous to the esFLUO fix:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
    // Ensure only the deposit owner can submit a refund for their deposit
    require!(
        deposit_msg.account_id == env::predecessor_account_id()
            || self.acl_has_role(Role::DAO.into(), env::predecessor_account_id())
            || self.acl_has_role(Role::Operator.into(), env::predecessor_account_id()),
        "Only the deposit owner, DAO, or Operator can request a refund"
    );
    ...
}
```

Alternatively, if permissionless refund submission is intentional, enforce that `deposit_msg.refund_address` must be `Some` (pre-authorized in the deposit message) so the caller cannot supply an arbitrary BTC destination.

### Proof of Concept

1. **Victim** calls `get_user_deposit_address(deposit_msg)` where `deposit_msg.refund_address = None`. The contract emits `LogDepositAddress` with the full `deposit_msg` on-chain.
2. **Victim** sends BTC to the derived deposit address. The transaction is confirmed on Bitcoin.
3. **Attacker** observes the `LogDepositAddress` event, reconstructs `deposit_msg`, and fetches `tx_bytes` from the Bitcoin network.
4. **Attacker** calls `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)` before the relayer calls `verify_deposit`. The Light Client validates the proof; `request_refund_callback` stores a `RefundRequest` with `refund_address = attacker_btc_address` and `created_at_sec = now`.
5. After `unsafe_refund_timelock_sec` elapses (and assuming DAO does not reject), **Attacker** calls `execute_refund(utxo_storage_key, None)`.
6. The bridge builds a PSBT paying `deposit_amount - gas_fee` satoshis to `attacker_btc_address`, requests an MPC signature, and broadcasts the transaction.
7. Victim's BTC is transferred to the attacker. Victim receives nothing.

        tx_bytes: Base64VecU8,
