### Title
`validatePerasCert` Stub Always Returns Success, Enabling Unauthorized Peras Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `BlockSupportsPeras` catch-all instance in `SupportsPeras.hs` implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or protocol validation. This function is wired directly into the production inbound-certificate processing path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can therefore send a crafted `PerasCert` for any round boosting any block, have it accepted without any check, stored in the `PerasCertDB`, and used to influence chain selection — the exact analog of the original report's "return value of the inner call is never checked, so invalid state is accepted and persisted."

### Finding Description

**Root cause — stub validation that always succeeds:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of its content, round number, boosted block, or any cryptographic field, is wrapped in `Right` and returned as `ValidatedPerasCert`. No signature, committee membership, round eligibility, or any other check is performed.

**Production wiring — this stub is the validator used for all inbound peer certificates:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`. The `processCerts` function does correctly branch on `Left`/`Right`: [3](#0-2) 

But because the validator always returns `Right`, the `Left` branch (rejection) is structurally unreachable. The check exists but is permanently bypassed by the stub — the same logical pattern as the original report where the try/catch in `anyExecute` made the failure branch unreachable from the caller.

**Accepted certificates are persisted and trigger chain selection:** [4](#0-3) 

The accepted `ValidatedPerasCert` is passed to `ChainDB.addPerasCertAsync`, which stores it in the `PerasCertDB` and triggers chain selection with the certificate's boost weight applied. [5](#0-4) 

**Exploit path:**
1. Attacker peer connects via the object-diffusion mini-protocol.
2. Peer sends a crafted `PerasCert` claiming to boost an arbitrary block in an arbitrary round.
3. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert` → always `Right`.
4. Certificate is stored in `PerasCertDB` as `ValidatedPerasCert`.
5. `addPerasCertAsync` triggers chain selection; the fraudulent certificate's boost weight is applied.
6. The honest node may switch to a non-canonical chain preferred only because of the fraudulent boost.

### Impact Explanation

This is a **bypass of Peras certificate verification** that enables unauthorized certificate acceptance. An unprivileged peer with a network connection can make an honest node accept a certificate for any round boosting any block, with no cryptographic proof of committee membership, quorum, or signature validity. The accepted certificate durably influences chain selection, potentially causing the node to prefer a non-canonical or adversarially chosen chain. This matches the **High** impact category: bypass of Peras certificate checks that enables unauthorized certificate acceptance and chain-selection manipulation.

### Likelihood Explanation

Any peer reachable via the object-diffusion mini-protocol can trigger this. No privileged keys, stake, or special role is required. The attacker only needs to craft a `PerasCert` value with a desired `pcCertRound` and `pcCertBoostedBlock` and send it. The path is fully reachable in any node running the Peras object-diffusion protocol.

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation before the production inbound-certificate path is active. At minimum, the validation must verify:
- The certificate's aggregate BLS signature against the claimed committee members' public keys.
- That the claimed voters are eligible committee members for the given round (VRF-based sortition proof).
- That the aggregate stake of the claimed voters meets the quorum threshold.
- That the boosted block exists and is within the valid range for the given round.

Until real validation is implemented, the inbound-certificate writer (`makePerasCertPoolWriterFromChainDB`) should not be wired into a live node, or should be gated behind a feature flag that is disabled by default.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
