### Title
Degenerate `validatePerasCert` Unconditionally Accepts Any Peer-Submitted Certificate, Enabling Unauthorized Chain-Selection Boost — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `BlockSupportsPeras` instance for `StandardHash blk` — the only instance currently wired into production — implements `validatePerasCert` as an unconditional `Right`, accepting every inbound `PerasCert` without any cryptographic or eligibility check. Because the `PerasCertDiffusion` miniprotocol is exposed to all untrusted NTN peers and feeds directly into `addPerasCertAsync` / chain selection, any peer can submit a crafted certificate that boosts an arbitrary block, causing the node to prefer a non-canonical chain.

### Finding Description

**Root cause — degenerate `validatePerasCert` always succeeds:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is checked, no committee membership is verified, no quorum is confirmed. Every `PerasCert` value — regardless of origin — is wrapped in `ValidatedPerasCert` and returned as `Right`.

**Production inbound path — NTN cert diffusion client:** [2](#0-1) 

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
```

`makePerasCertPoolWriterFromChainDB` calls `validatePerasCert` (the degenerate instance above) on every inbound cert, then passes the `ValidatedPerasCert` to `addPerasCertAsync`: [3](#0-2) 

```haskell
addPerasCertAsync :: WithArrivalTime (ValidatedPerasCert blk) -> m (AddPerasCertPromise m)
-- ^ Asynchronously insert a certificate to the DB. If this leads to a fork to
-- be weightier than our current selection, this will trigger a fork switch.
```

**Contrast with the real validation that is bypassed:**

The `WFALS` committee scheme (`implVerifyCert`) performs full aggregate BLS signature verification, VRF output batch verification, and seat-index membership checks: [4](#0-3) 

None of this is invoked for inbound certs; the degenerate instance short-circuits all of it.

**Contrast with `validatePerasVote` — which has a partial guard:** [5](#0-4) 

`validatePerasVote` at least checks that the voter ID appears in the stake distribution (and the production writer passes an empty distribution, so all votes are rejected). `validatePerasCert` has no analogous guard — it accepts unconditionally.

**End-to-end exploit path:**

1. Attacker connects to a victim node as a normal NTN peer (no keys required).
2. Attacker sends a crafted `PerasCert` message over the `PerasCertDiffusion` miniprotocol, claiming to boost an arbitrary block `B` on a minority fork.
3. `hPerasCertDiffusionClient` → `objectDiffusionInbound` → `makePerasCertPoolWriterFromChainDB` → `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = crafted, vpcCertBoost = perasWeight params })`.
4. `addPerasCertAsync` inserts the cert; ChainDB applies the boost weight to block `B`.
5. If the boosted fork's total weight now exceeds the honest chain's weight, the node switches chains.

### Impact Explanation

This is a **High** chain-selection bug. An unprivileged peer with a standard NTN connection can make an honest node prefer a non-canonical chain by injecting a certificate that grants an arbitrary block the full Peras boost weight (`perasWeight params`). This violates the core Peras security invariant that only a quorum of authorized committee members can boost a block. The impact matches: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

### Likelihood Explanation

The `PerasCertDiffusion` miniprotocol is wired into the standard NTN application bundle and is reachable by any peer that can open a connection to the node. No privileged keys, stake, or prior state are required. The degenerate instance is the only `BlockSupportsPeras` instance in the codebase and is used for all block types.

### Recommendation

Until the real `validatePerasCert` implementation (with BLS aggregate signature and committee membership verification, as in `implVerifyCert`) is wired in, the inbound cert diffusion handler must reject all certificates rather than accept them. Replace the degenerate body with:

```haskell
validatePerasCert _params _cert = Left PerasValidationErr
```

This mirrors the safe fallback already present in `validatePerasVote` when the stake distribution is empty, and ensures no cert can influence chain selection until proper cryptographic validation is in place.

  (StandardHash blk, IOLike m) =>
  SystemTime m ->
  -- | This is needed for validating votes (since its during the validation of
  -- votes that we give them a verified weight. In the future, we won't read it
  -- from the stake distr directly, but rather use the committee selection data)
  STM m PerasVoteStakeDistr ->
  ChainDB m blk ->
  ObjectPoolWriter (PerasVoteId blk) (PerasVote blk) m
makePerasVotePoolWriterFromChainDB systemTime getStakeDistrSTM chainDB =
  ObjectPoolWriter
    { opwObjectId = getPerasVoteId
    , opwAddObjects = \votes ->
        processVotes
          systemTime
          (ChainDB.getPerasVoteIds chainDB)
          -- TODO: in the future we won't need just the stake distribution for
          -- validating votes, but also the whole committee selection context
          -- (containing vote weights of committee members = voters)
          (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
          -- We do not want to block the writer thread on waiting for ChainSel
          -- side-effects to complete, so we use the async version of adding
          -- votes to the ChainDB and ignore the returned promise.
          -- The async action (if any) is still launched and executed behind the
          -- scenes even though we drop the promise.
          (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
          votes
    , opwHasObject = do
        voteIds <- ChainDB.getPerasVoteIds chainDB
        pure $ \voteId -> Set.member voteId voteIds
