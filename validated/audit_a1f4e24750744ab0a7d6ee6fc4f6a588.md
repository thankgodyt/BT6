### Title
Silent nBTC Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own balance **before** checking whether the intended recipient account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the newly minted tokens, leaving them permanently stranded in the bridge's balance with no on-chain recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124) executes in this order:

1. **Mints unconditionally to `bridge_id`** — `self.token.internal_deposit(&self.bridge_id, amount.into())` (line 112) increases the bridge's token balance and the global total supply by `amount`.
2. **Checks registration after the fact** — `if self.token.accounts.get(&account_id).is_none()` (line 114) is evaluated only after the mint has already occurred.
3. **Returns silently on failure** — `return PromiseOrValue::Value(U128(0))` (line 115) exits without transferring the tokens or reverting the mint. [1](#0-0) 

The correct order would be to verify registration **before** minting. As written, the total supply is inflated by `amount` but the user receives nothing. The minted tokens accumulate in `bridge_id`'s balance. The bridge's `lost_found` recovery mechanism (used in `transfer_nbtc_callback`) is not wired to `safe_mint`'s zero-return path, so there is no automatic recovery. [2](#0-1) 

The `mint` function (the non-safe variant) avoids this by calling `mint_inner`, which auto-registers the account before depositing. `safe_mint` deliberately skips auto-registration to avoid storage-cost attacks, but the current implementation does not revert the mint when registration is absent. [3](#0-2) 

---

### Impact Explanation

A user whose BTC deposit is processed via the `safe_deposit` path with an unregistered `recipient_id` loses their nBTC: the BTC is locked in the deposit address, nBTC is minted to the bridge's balance, and the user receives nothing. The tokens are not burned (total supply is inflated above backed supply) and are not recoverable without privileged operator action. This matches the **Medium** impact class: *permanent burning below backed supply / stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

Any user can craft a `DepositMsg` with a `safe_deposit` field pointing to any NEAR account ID. If that account has not called `storage_deposit` on the nBTC contract, the condition at line 114 triggers. This is reachable by any unprivileged bridge user — no special role or key is required. The scenario can occur accidentally (user specifies a fresh account) or deliberately (attacker griefs a specific recipient by front-running their deposit before they register storage). [4](#0-3) 

---

### Recommendation

Move the registration check **before** `internal_deposit`. If `account_id` is not registered, either:
- Revert with a clear error (forcing the caller to ensure registration first), or
- Register the account inline (accepting the storage cost, consistent with `mint_inner`'s behavior).

The corrected logic in `safe_mint` should be:

```rust
// Check registration BEFORE minting
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // or panic
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

---

### Proof of Concept

1. Attacker (or naive user) constructs a `DepositMsg` with `safe_deposit: Some(SafeDepositMsg { msg: "..." })` and `recipient_id` set to a NEAR account that has **not** registered storage on the nBTC contract.
2. User sends BTC to the derived deposit address; a relayer submits the inclusion proof via `verify_deposit`.
3. The bridge, after light-client verification, calls `nbtc.safe_mint(unregistered_account, amount, Some(msg))`.
4. `internal_deposit(&bridge_id, amount)` executes — nBTC total supply increases by `amount`, bridge balance increases by `amount`.
5. `accounts.get(&unregistered_account)` returns `None` → function returns `U128(0)`.
6. No transfer occurs. The user's BTC is locked; they hold zero nBTC. The bridge's nBTC balance is inflated by `amount` with no corresponding liability entry and no recovery hook. [5](#0-4)
