Audit Report

## Title
Missing Chain-ID Binding in `DeployTokenPayload::serialize_for_near()` Enables Cross-Chain Replay of NEAR MPC Signatures — (`solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary

`DeployTokenPayload::serialize_for_near()` omits the `SOLANA_OMNI_BRIDGE_CHAIN_ID` byte that every other payload serializer in the program writes into the signed body. Because the Solana build (chain_id=2) and the FOGO build (chain_id=12) produce byte-for-byte identical signed messages for the same `DeployTokenPayload`, a single NEAR-MPC-signed `SignedPayload<DeployTokenPayload>` is unconditionally accepted by both chains' `deploy_token` instructions. An unprivileged observer can extract a valid `(payload, signature)` pair from a public Solana transaction and replay it on FOGO (or vice versa), creating an unauthorized wrapped mint and emitting a false `DeployTokenResponse` Wormhole message back to NEAR.

## Finding Description

`build.rs` bakes `SOLANA_OMNI_BRIDGE_CHAIN_ID` into the binary at compile time: [1](#0-0) 

Solana gets `2`, FOGO gets `12`: [2](#0-1) 

Every other `serialize_for_near` implementation writes this byte into the signed body before the chain-specific address fields:

- `FinalizeTransferPayload` — writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` for both token and recipient: [3](#0-2) 

- `InitTransferPayload` — writes it for sender and token: [4](#0-3) 

- `LogMetadataPayload` — writes it for the token field: [5](#0-4) 

`DeployTokenPayload::serialize_for_near()` is the sole exception — it writes only the `IncomingMessageType::Metadata` discriminant followed by the raw Borsh fields, with no chain byte: [6](#0-5) 

`SignedPayload::verify_signature` calls `serialize_for_near`, hashes the result with keccak, and checks the recovered key against `derived_near_bridge_address`: [7](#0-6) 

Because the serialized bytes are identical on both chains, the keccak hash is identical, and the recovered signer is identical. The check passes on both chains for the same `(payload, signature)` pair.

The `deploy_token` instruction has no nonce or used-nonces account — the only replay guard is the `init` constraint on the mint PDA, which is chain-local: [8](#0-7) 

After the mint is created, `initialize_token_metadata` posts a `DeployTokenResponse` Wormhole message back to NEAR: [9](#0-8) 

## Impact Explanation

An attacker who observes a valid `SignedPayload<DeployTokenPayload>` submitted to the Solana bridge can immediately replay it on FOGO (or vice versa). The FOGO `deploy_token` instruction accepts the signature (identical signed bytes → identical keccak hash → same recovered signer). A wrapped mint is then created on FOGO under the program's authority PDA, and a `DeployTokenResponse` Wormhole message is emitted back to NEAR. NEAR receives a message asserting the token is live on FOGO without having authorized it for FOGO — a chain/domain separation flaw and unauthorized deployer-equivalent action. The `init` constraint on the mint PDA also permanently occupies the wrapped-mint PDA on FOGO, preventing any future legitimate deployment attempt from succeeding. This matches the allowed Critical impact class: **unauthorized transaction / signer verification bypass enabling deployer-equivalent action**, and **cross-chain replay / chain/domain separation flaw enabling invalid finalization**.

## Likelihood Explanation

All `SignedPayload<DeployTokenPayload>` transactions are public on-chain. Any observer can extract the payload and signature from a Solana transaction and submit them to FOGO with no special access or privileges. The precondition — both deployments sharing the same `derived_near_bridge_address` — is the intended production configuration (both bridge to the same NEAR MPC key). This is trivially exploitable by any party watching the chain.

## Recommendation

Add `SOLANA_OMNI_BRIDGE_CHAIN_ID` to the signed body of `DeployTokenPayload::serialize_for_near()`, consistent with every other payload serializer:

```rust
fn serialize_for_near(&self, _params: Self::AdditionalParams) -> Result<Vec<u8>> {
    let mut writer = BufWriter::new(Vec::with_capacity(DEFAULT_SERIALIZER_CAPACITY));
    IncomingMessageType::Metadata.serialize(&mut writer)?;
    // Bind to the target chain — prevents cross-chain replay
    writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?;
    self.serialize(&mut writer)?;
    writer.into_inner().map_err(|_| error!(ErrorCode::InvalidArgs))
}
```

The NEAR side's `log_metadata_callback` must be updated to include the target chain byte in the `MetadataPayload` it constructs and submits to the MPC signer, so that the signed bytes match the updated Solana serialization.

## Proof of Concept

A minimal differential unit test demonstrates the flaw without requiring a live network. Build the program twice — once with `OMNI_CHAIN_ID=2` (Solana) and once with `OMNI_CHAIN_ID=12` (FOGO) — and assert that `serialize_for_near` produces identical output:

```rust
#[test]
fn deploy_token_cross_chain_replay() {
    use bridge_token_factory::state::message::{
        deploy_token::DeployTokenPayload, Payload,
    };

    let payload = DeployTokenPayload {
        token: "usdc.token.near".to_string(),
        name: "USD Coin".to_string(),
        symbol: "USDC".to_string(),
        decimals: 6,
    };

    // SOLANA_OMNI_BRIDGE_CHAIN_ID is a compile-time constant never written
    // into the serialized body, so both builds produce identical bytes.
    let bytes_chain2  = payload.serialize_for_near(()).unwrap(); // Solana build
    let bytes_chain12 = payload.serialize_for_near(()).unwrap(); // FOGO build

    assert_eq!(bytes_chain2, bytes_chain12,
        "signed body must differ between chains but does not");
}
```

Because `SOLANA_OMNI_BRIDGE_CHAIN_ID` is never written by `serialize_for_near`, the assertion holds regardless of which binary is running. A single NEAR MPC signature over this payload is accepted by both the Solana and FOGO `deploy_token` instructions. On a private testnet, the exploit can be demonstrated end-to-end by submitting a Solana `deploy_token` transaction, extracting the `(payload, signature)` from the transaction data, and replaying it against a FOGO deployment sharing the same `derived_near_bridge_address`.

    pub fn verify_signature(
        &self,
        params: P::AdditionalParams,
        derived_near_bridge_address: &[u8; 64],
    ) -> Result<()> {
        let serialized = self.payload.serialize_for_near(params)?;
        let hash = keccak::hash(&serialized);

        let signature_bytes = &self.signature[0..64];

        let signature = libsecp256k1::Signature::parse_standard_slice(signature_bytes)
            .map_err(|_| ProgramError::InvalidArgument)?;
        require!(!signature.s.is_high(), ErrorCode::MalleableSignature);

        let signer = secp256k1_recover(&hash.to_bytes(), self.signature[64], signature_bytes)
            .map_err(|_| error!(ErrorCode::SignatureVerificationFailed))?;

        require!(
            signer.0 == *derived_near_bridge_address,
            ErrorCode::SignatureVerificationFailed
        );

        Ok(())
    }
