Audit Report

## Title
Permanent Fund Lock via `normalize_amount` Rounding to Zero in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates an outbound NEAR transfer with an amount smaller than the decimal scaling factor between origin and destination chains, `normalize_amount` returns `0` via floor division. The `sign_transfer` function then panics with `InvalidAmountToTransfer`. Because token locking occurs in the already-committed `init_transfer` transaction, the user's funds are permanently frozen in `pending_transfers` with no cancel or refund path available.

## Finding Description
The bridge's outbound flow is split across two separate NEAR transactions:

**Step 1 — `init_transfer` (via `ft_on_transfer`):** Tokens are locked/burned and the `TransferMessage` is stored in `pending_transfers`. The only validation on `amount` at this stage is: [1](#0-0) 

There is no check that the amount survives decimal normalization.

**Step 2 — `sign_transfer` (trusted-relayer only):** The function is gated by `#[trusted_relayer]`: [2](#0-1) 

It normalizes the net amount for the destination chain: [3](#0-2) 

`normalize_amount` performs integer floor division: [4](#0-3) 

If `amount - fee < 10^(origin_decimals - decimals)`, the result is `0` and the `require!` panics. This panic reverts only `sign_transfer`'s own state — the lock from `init_transfer` is already committed and remains in `pending_transfers`.

The `sign_transfer_callback` only removes the transfer message when MPC signing succeeds: [5](#0-4) 

Since the panic occurs before the MPC signing call is even dispatched, the callback is never reached and the transfer is never removed.

A grep search for `cancel_transfer` in `lib.rs` returns no matches — there is no user-callable cancellation or refund mechanism for stuck transfers.

The `normalize_amount` docstring acknowledges dust locking when `fee = 0`: [6](#0-5) 

However, this only addresses the case where the *remainder* (dust) is locked after a successful normalization. It does not address the case where the *entire* amount normalizes to `0`, causing `sign_transfer` to panic and leaving the full principal permanently frozen.

## Impact Explanation
User funds are permanently frozen in `pending_transfers`. The relayer has no incentive to retry (every attempt panics identically). The user cannot call `sign_transfer` themselves (it is `#[trusted_relayer]`-gated). No `cancel_transfer` or user-callable refund function exists in the contract. This constitutes **permanent freezing of bridged funds**, which matches the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation
Any token pair where `origin_decimals > decimals` is susceptible. A concrete realistic case: a token with 24 NEAR-side decimals bridging to an EVM chain registered with 6 decimals (diff = 18). Any transfer of fewer than `10^18` base units (less than 1 full token in NEAR representation) normalizes to `0`. Users routinely transfer fractional token amounts. No special attacker setup is required — a regular user sending a small amount triggers this inadvertently. The condition is reachable through the standard public `ft_on_transfer` callback.

## Recommendation
Add a pre-lock validation in `init_transfer` (or in `ft_on_transfer` before locking) that computes `normalize_amount(amount - fee, decimals)` and rejects the transfer if the result is `0`. This ensures the panic surface is moved to before any state is committed. Alternatively, implement a user-callable `cancel_transfer` that refunds locked tokens for transfers that have not yet been signed, providing a recovery path for already-stuck funds.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 6` (decimal diff = 18).
2. User calls `ft_on_transfer` transferring `amount = 5 × 10^17` (0.5 of the smallest NEAR-side whole unit), `fee = 0`.
3. `init_transfer` passes the `fee < amount` check, locks `5 × 10^17` tokens, stores the `TransferMessage` in `pending_transfers`. State is committed on-chain.
4. Trusted relayer calls `sign_transfer` with the resulting `transfer_id`.
5. `normalize_amount(5 × 10^17, {origin: 24, dest: 6})` = `5 × 10^17 / 10^18` = `0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — `sign_transfer` reverts entirely.
7. `pending_transfers` still holds the message; tokens remain locked with no recovery path.
8. Every subsequent relayer retry produces the same panic. The user has no callable function to reclaim their tokens.

A local integration test can reproduce this by: (a) registering a token with the described decimal configuration, (b) calling `ft_on_transfer` with the sub-threshold amount, (c) asserting the transfer is stored in `pending_transfers`, (d) calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`, and (e) asserting the transfer remains in `pending_transfers` after the panic.
