### Title
`safe_mint_callback` Treats `safe_mint` Panic as Successful Mint, Permanently Locking User BTC Without Minting nBTC — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In the `safe_verify_deposit` flow, when the cross-contract call to `safe_mint` panics (e.g., because `recipient_id == bridge_id`), the `safe_mint_callback` function incorrectly interprets the panic as a successful mint. It adds the UTXO to the bridge's available set, but no nBTC is ever minted to the user. The user's BTC is permanently absorbed into the bridge's UTXO pool without compensation.

---

### Finding Description

The `is_refund_required()` helper function in `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` is used by `safe_mint_callback` to determine whether the `safe_mint` call succeeded:

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0
            } else {
                false  // Unexpected case: don't refund
            }
        }
        Err(_) => false,  // Unexpected case: don't refund
    }
}
``` [1](#0-0) 

The function returns `false` (meaning "no refund needed, treat as success") for **both**:
1. A genuine success — `safe_mint` returned a non-zero `U128` (tokens transferred to user).
2. A `safe_mint` **panic** — `promise_result_checked` returns `Err(_)`.

This conflation makes it impossible to distinguish "tokens successfully delivered to user" from "safe_mint panicked and all its state was reverted."

When `safe_mint` panics, `safe_mint_callback` executes the success branch:

```rust
if is_success {
    Event::UtxoAdded { ... }.emit();
    self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
}
``` [2](#0-1) 

The UTXO is permanently added to the bridge's available set, but because `safe_mint` panicked, all its state changes (including `internal_deposit` to the bridge's balance) were reverted by the NEAR runtime. No nBTC exists anywhere.

The `safe_mint` function in `contracts/nbtc/src/lib.rs` panics when `account_id == bridge_id`:

```rust
require!(
    account_id != self.bridge_id,
    "safe_mint: account_id must not be the bridge"
);
self.token.internal_deposit(&self.bridge_id, amount.into());
``` [3](#0-2) 

The bridge's `verify_safe_deposit_callback` does **not** validate `recipient_id != bridge_id` before calling `safe_mint`:

```rust
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_MINT_CALL)
    .with_attached_deposit(NearToken::from_yoctonear(1))
    .safe_mint(recipient_id.clone(), mint_amount, msg)
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_MINT_CALL_BACK)
            .safe_mint_callback(recipient_id.clone(), mint_amount, pending_utxo_info),
    )
    .into()
``` [4](#0-3) 

The existing test `test_safe_verify_deposit_to_bridge_recipient_is_rejected` confirms `safe_mint` panics in this case and that no tokens are minted, but it does **not** assert whether the UTXO was incorrectly added to the bridge's available set — leaving the accounting bug undetected. [5](#0-4) 

---

### Impact Explanation

When the bug is triggered:
- The UTXO is permanently added to the bridge's available UTXO pool (usable for future withdrawals by other users).
- No nBTC is minted to the depositing user.
- The user's BTC is irrecoverably absorbed into the bridge's UTXO pool with no compensation.
- The 1:1 BTC-to-nBTC backing invariant is broken: the bridge holds a UTXO with no corresponding nBTC in circulation.

This constitutes **permanent loss of user funds** and a **broken bridge accounting invariant**.

---

### Likelihood Explanation

The attack path is fully user-controlled and requires no privileged access:

1. A user crafts a `DepositMsg` with `recipient_id = bridge_id` and `safe_deposit: Some(SafeDepositMsg { msg: "" })`.
2. The deposit address is deterministically derived from this msg hash.
3. The user sends BTC to that address.
4. A trusted relayer (acting honestly, with no reason to reject a valid BTC transaction) calls `safe_verify_deposit` with the proof.
5. The bug triggers automatically.

The relayer has no obligation to validate `recipient_id != bridge_id` — it only verifies the BTC transaction inclusion proof. The user fully controls the `DepositMsg` content.

---

### Recommendation

**Option 1 (Preferred):** In `is_refund_required()`, treat a failed promise (`Err(_)`) as "refund required" (`true`), not as success. A panic in `safe_mint` means no tokens were transferred; the UTXO must be released.

```rust
Err(_) => true,  // safe_mint panicked: no tokens transferred, release UTXO
```

**Option 2:** Add an explicit guard in `verify_safe_deposit_callback` (or earlier in the deposit entry path) that rejects `recipient_id == bridge_id` before calling `safe_mint`, causing the entire transaction to fail atomically.

---

### Proof of Concept

1. User crafts: `DepositMsg { recipient_id: bridge_account_id, safe_deposit: Some(SafeDepositMsg { msg: "" }), ... }`
2. User sends BTC to the deposit address derived from this msg.
3. Trusted relayer calls `safe_verify_deposit(deposit_msg, tx_bytes, vout, proof)`.
4. Bridge verifies inclusion → calls `verify_safe_deposit_callback`.
5. Bridge calls `nbtc.safe_mint(bridge_id, amount, None)` with 1 yoctoNEAR attached.
6. `safe_mint` hits `require!(account_id != self.bridge_id, ...)` → **panics**.
7. NEAR runtime reverts all `safe_mint` state changes; bridge's nBTC balance unchanged.
8. `safe_mint_callback` is invoked; `promise_result_checked(0, ...)` returns `Err(_)`.
9. `is_refund_required()` returns `false` → `is_success = !false = true`.
10. `self.internal_set_utxo(...)` executes → UTXO permanently added to bridge's available set.
11. User receives **zero nBTC**; their BTC is absorbed into the bridge's UTXO pool with no recourse.
