### Title
Missing Pause Guard on `reject_refund` Allows Permanent Deletion of Refund Requests During Emergency Pause - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

The `reject_refund` function in `contracts/satoshi-bridge/src/api/bridge.rs` is missing the `#[pause(except(roles(Role::DAO)))]` decorator that guards every other state-mutating function in the same file. This allows any unprivileged caller to permanently delete pending refund requests even when the bridge is in a paused (emergency) state.

### Finding Description

Every sensitive state-mutating function in the bridge is decorated with `#[pause(except(roles(Role::DAO)))]`, which causes the function to revert with `"Method is paused"` for non-DAO callers when the contract is paused. The following functions all carry this guard:

- `request_refund` [1](#0-0) 
- `execute_refund` [2](#0-1) 
- `verify_refund_finalize` [3](#0-2) 
- `remove_refund_pending_tx_id` [4](#0-3) 

However, `reject_refund` has no such guard:

```rust
pub fn reject_refund(&mut self, utxo_storage_key: String) {
    let caller = env::predecessor_account_id();
    let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
        || self.acl_has_role(Role::Operator.into(), caller);
    ...
    let is_already_deposited = !executed
        && self.data().verified_deposit_utxo.contains(&utxo_storage_key);
    require!(
        is_privileged || is_already_deposited,
        "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
    );
    self.internal_reject_refund(utxo_storage_key);
}
``` [5](#0-4) 

The permissionless branch (`is_already_deposited`) is reachable by any NEAR account when the target UTXO key exists in `verified_deposit_utxo` and the refund request has not yet been executed. This branch is entirely independent of any role check and is not blocked by the pause mechanism.

The pause system is configured at the contract level:

```rust
#[pausable(pause_roles(Role::PauseManager), unpause_roles(Role::UnpauseManager))]
``` [6](#0-5) 

When `pa_pause_feature("ALL")` is called, all `#[pause]`-decorated functions revert for non-DAO callers, but `reject_refund` continues to execute normally.

### Impact Explanation

When the bridge is paused due to an emergency (e.g., a bug in deposit verification that incorrectly populates `verified_deposit_utxo`, or an active exploit), an attacker can call `reject_refund` against any refund request whose UTXO key appears in `verified_deposit_utxo`. `internal_reject_refund` permanently removes the refund request from storage. Because `verified_deposit_utxo` also blocks re-submission of a refund for the same UTXO, the victim's refund path is permanently closed.

In the scenario where the pause was triggered precisely because `verify_deposit` was misbehaving (e.g., adding UTXOs to `verified_deposit_utxo` without correctly minting nBTC to the user), the attacker can exploit the unguarded `reject_refund` to destroy the user's only recovery path — their BTC is locked in the bridge and their refund request is gone. This constitutes a stuck bridge state requiring operator intervention, and in the worst case, permanent loss of user funds.

### Likelihood Explanation

The permissionless path of `reject_refund` is reachable by any NEAR account without any role or deposit requirement. The only precondition is that the target UTXO key is in `verified_deposit_utxo`, which is a normal post-deposit state. A pause event is an infrequent but realistic emergency condition. An attacker monitoring the chain can detect a pause event and immediately call `reject_refund` on any eligible refund requests before the pause is lifted.

### Recommendation

Add the `#[pause(except(roles(Role::DAO)))]` decorator to `reject_refund`, consistent with every other state-mutating function in the same `impl` block:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn reject_refund(&mut self, utxo_storage_key: String) {
```

### Proof of Concept

1. PauseManager calls `pa_pause_feature("ALL")` — bridge enters emergency pause.
2. Prior to the pause, a relayer had called `verify_deposit` for UTXO `abc@0`, adding it to `verified_deposit_utxo`. A user also has a pending `RefundRequest` for `abc@0` with `executed = false`.
3. Attacker (any NEAR account) calls `reject_refund("abc@0")`.
4. `is_already_deposited` evaluates to `true` (UTXO is in `verified_deposit_utxo`, request not executed).
5. `require!(is_privileged || is_already_deposited, ...)` passes.
6. `internal_reject_refund("abc@0")` executes, permanently deleting the refund request.
7. The pause check is never triggered because `reject_refund` has no `#[pause]` decorator.
8. When the bridge is unpaused, the user's refund request is gone and cannot be re-submitted for the same UTXO. [5](#0-4) [1](#0-0) [7](#0-6)
