### Title
Rejected Refund Request Can Be Re-Submitted by Anyone with Arbitrary Refund Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

`internal_reject_refund` only removes the refund entry from `refund_requests` without recording the UTXO in any permanent "rejected" set. Because `request_refund` is publicly callable and `request_refund_callback` only checks `verified_deposit_utxo` and `refund_requests`, any NEAR account can immediately re-submit a new refund request for the same UTXO — with an attacker-controlled `refund_address` — the moment the DAO/Operator rejects the original one.

### Finding Description

`reject_refund` is callable by anyone when `is_already_deposited` is true, and by DAO/Operator at any time. Its implementation is:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [1](#0-0) 

After rejection the UTXO is absent from both `refund_requests` and `verified_deposit_utxo`. `ContractData` has no "rejected UTXOs" set: [2](#0-1) 

`request_refund_callback` only guards against two conditions — UTXO already deposited, and duplicate in-flight request — with no check for prior rejection:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

`request_refund` itself is in the `#[trusted_relayer]` impl block but carries no method-level `#[trusted_relayer]` attribute (unlike `verify_deposit`, `verify_withdraw`, etc.), so it is publicly callable by any NEAR account that attaches the required storage deposit: [4](#0-3) 

The `reject_refund` function's own comment confirms the permissionless surface: "Anyone can reject a request if the UTXO has already been verified via `verify_deposit`." [5](#0-4) 

### Impact Explanation

When `deposit_msg.refund_address` is `None` (the caller-supplied path), the stored `refund_address` is whatever the submitter provides. After the DAO rejects the original request, an attacker re-submits with `refund_address = attacker_btc_address`. If the DAO does not notice and reject again before `unsafe_refund_timelock_sec` elapses, `execute_refund` builds a PSBT paying the attacker's address, the MPC network signs it, and the BTC is sent to the attacker — a direct theft of the user's deposited BTC.

The timelock for the caller-supplied path is `unsafe_refund_timelock_sec` (longer than `refund_timelock_sec`), which is specifically intended to give the DAO time to reject suspicious requests. However, the DAO's rejection is not permanent: the attacker can re-submit immediately after each rejection, creating an indefinite loop that the DAO must win every round of. A single missed rejection results in BTC theft. [6](#0-5) 

### Likelihood Explanation

- `request_refund` is publicly callable; the only cost is the storage deposit (`required_balance_for_request_refund()`).
- Rejected refund events (`RefundRejected`) are emitted on-chain, so an attacker can trivially monitor for them.
- The attacker only needs to win once (DAO misses one round) to execute the theft.
- The attack is repeatable at low cost and requires no privileged role.

### Recommendation

Track rejected UTXOs in a dedicated `LookupSet<String>` (e.g., `rejected_refund_utxos`). In `internal_reject_refund`, insert the `utxo_storage_key` into this set. In `request_refund_callback`, add a guard:

```rust
require!(
    !self.data().rejected_refund_utxos.contains(&utxo_storage_key),
    "Refund request was previously rejected for this UTXO"
);
```

This mirrors the fix recommended in the external report: once a refund is rejected, it cannot be re-submitted, analogous to not allowing a removed adapter to be re-added.

### Proof of Concept

1. Alice sends 0.01 BTC to her deposit address (derived from `deposit_msg` with `refund_address: None`).
2. Alice calls `request_refund(deposit_msg, refund_address="alice_btc_addr", tx_bytes, vout, proof)` paying the storage deposit.
3. DAO calls `reject_refund(utxo_storage_key)` — `refund_requests` entry is removed; UTXO is not in `verified_deposit_utxo`.
4. Attacker immediately calls `request_refund(deposit_msg, refund_address="attacker_btc_addr", tx_bytes, vout, proof)` — `request_refund_callback` passes both guards (UTXO not in `verified_deposit_utxo`, no existing request) and stores the attacker's request.
5. DAO does not notice the new request within `unsafe_refund_timelock_sec`.
6. Attacker calls `execute_refund(utxo_storage_key)` — PSBT is built paying `attacker_btc_addr`, MPC signs it.
7. Attacker broadcasts the signed transaction; Alice's 0.01 BTC (minus gas fee) is sent to the attacker. [7](#0-6)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }

    /// Reject a pending refund request.
    /// - DAO or Operator can reject any request.
    /// - Anyone can reject a request if the UTXO has already been verified via `verify_deposit`
    ///
    /// # Arguments
    ///
    /// * `utxo_storage_key` - The UTXO key identifying the refund request (`{tx_id}@{vout}`).
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
