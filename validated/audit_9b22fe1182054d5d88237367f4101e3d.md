### Title
Finalized Transfer Record Removed on `ft_transfer_call` Rejection Enables Cross-Chain Replay Double-Spend — (File: `near/omni-bridge/src/lib.rs`)

### Summary
When an inbound transfer to NEAR uses `ft_transfer_call` (non-empty `msg`) and the recipient contract rejects the tokens (returns the full amount from `ft_on_transfer`), `fin_transfer_send_tokens_callback` removes the transfer ID from `finalised_transfers`. This permanently erases the only replay guard, allowing the same source-chain proof to be re-submitted and finalized a second time, resulting in double-spending of bridged funds.

### Finding Description

The NEAR bridge contract tracks finalized inbound transfers in `finalised_transfers` to prevent replay. When a transfer to a NEAR recipient includes a non-empty `msg`, `send_tokens` issues an `ft_transfer_call`. If the recipient's `ft_on_transfer` returns the full amount (rejection), `ft_transfer_call` resolves to `0`, and `is_refund_required` returns `true`. [1](#0-0) 

In the refund branch of `fin_transfer_send_tokens_callback`, the code burns tokens (for deployed tokens), reverts lock actions, and then **removes the transfer ID from `finalised_transfers`**: [2](#0-1) 

The removal is performed by `remove_fin_transfer`: [3](#0-2) 

After removal, `add_fin_transfer` will succeed again for the same `TransferId` because the set no longer contains it: [4](#0-3) 

The `msg` field in the transfer message originates from the `message` parameter of `initTransfer` on the EVM side, which is fully attacker-controlled: [5](#0-4) 

The `msg` is propagated verbatim into the NEAR `TransferMessage` inside `fin_transfer_callback`: [6](#0-5) 

### Impact Explanation

**For deployed (bridge-minted) tokens**: On the first finalization, tokens are minted and sent via `ft_transfer_call`. The attacker's recipient contract rejects them; the tokens are returned to the bridge and then burned by `burn_tokens_if_needed`. The transfer ID is removed from `finalised_transfers`. On re-submission of the same proof, new tokens are minted and delivered to the attacker. Net effect: unauthorized minting — the attacker receives tokens backed by no corresponding lock on the source chain.

**For native (escrow-locked) tokens**: On the first finalization, `unlock_tokens_if_needed` decrements the escrow counter and tokens are sent via `ft_transfer_call`. The recipient rejects them; tokens return to the bridge and `revert_lock_actions` re-increments the escrow counter. The transfer ID is removed. On re-submission, the escrow is decremented again and tokens are delivered to the attacker. Net effect: double-unlock — the attacker drains tokens that were already returned to escrow. [7](#0-6) 

### Likelihood Explanation

The attacker only needs to be a regular bridge user. They must:
1. Hold tokens on the source chain (EVM/Starknet/Solana) — normal user capability.
2. Set a non-empty `message` in `initTransfer` — fully attacker-controlled parameter.
3. Set the NEAR recipient to a contract they deploy that returns the full amount from `ft_on_transfer` — trivial on NEAR.
4. Re-submit the same proof after the first finalization fails — the same Wormhole VAA or light-client proof is reusable since the finalization record was erased.

No admin compromise, key leakage, or MPC collusion is required.

### Recommendation

Do not remove the transfer ID from `finalised_transfers` on the refund path. The finalization record must be permanent regardless of whether the downstream `ft_transfer_call` succeeded or failed. The refund of tokens to the bridge (burn + revert lock) can proceed without erasing the replay guard. A separate mechanism (e.g., a `failed_transfers` set or a status enum) can track failed finalizations for UX purposes without compromising replay protection.

### Proof of Concept

1. Attacker deploys `MaliciousRecipient` on NEAR. Its `ft_on_transfer` returns the full `amount` on the first call and `0` on the second call.
2. Attacker calls `initTransfer` on EVM with `message = "trigger_ft_transfer_call"` and `recipient = "malicious_recipient.near"`.
3. Relayer submits the proof to `fin_transfer_callback` on NEAR.
4. `add_fin_transfer` inserts `TransferId { origin_chain: Eth, origin_nonce: N }` into `finalised_transfers`.
5. `unlock_tokens_if_needed` decrements the escrow counter by `amount`.
6. `send_tokens` issues `ft_transfer_call`; `MaliciousRecipient.ft_on_transfer` returns `amount` → `ft_transfer_call` resolves to `0`.
7. `fin_transfer_send_tokens_callback` fires: burns tokens (deployed) or re-locks (native), then calls `remove_fin_transfer` — the transfer ID is erased from `finalised_transfers`.
8. Attacker re-submits the identical proof to `fin_transfer_callback`.
9. `add_fin_transfer` succeeds (ID no longer in set).
10. `unlock_tokens_if_needed` decrements escrow again; `send_tokens` issues `ft_transfer_call`; `MaliciousRecipient.ft_on_transfer` returns `0` → tokens delivered.
11. Attacker has received tokens for a single source-chain lock event. [8](#0-7)

    #[allow(clippy::needless_pass_by_value)]
    #[private]
    pub fn fin_transfer_send_tokens_callback(
        &mut self,
        #[serializer(borsh)] transfer_message: TransferMessage,
        #[serializer(borsh)] fee_recipient: &AccountId,
        #[serializer(borsh)] is_ft_transfer_call: bool,
        #[serializer(borsh)] storage_owner: &AccountId,
        #[serializer(borsh)] lock_actions: Vec<LockAction>,
    ) {
        let token = self.get_token_id(&transfer_message.token);

        if Self::is_refund_required(is_ft_transfer_call) {
            self.burn_tokens_if_needed(
                token.clone(),
                U128(
                    transfer_message
                        .amount_without_fee()
                        .near_expect(BridgeError::InvalidFee),
                ),
            );

            self.revert_lock_actions(&lock_actions);

            self.remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner);

            env::log_str(
                &OmniBridgeEvent::FailedFinTransferEvent { transfer_message }.to_log_string(),
            );
        } else {
            // Send fee to the fee recipient
            if transfer_message.fee.fee.0 > 0 {
                if self.is_deployed_token(&token) {
                    ext_token::ext(token)
                        .with_static_gas(MINT_TOKEN_GAS)
                        .mint(fee_recipient.clone(), transfer_message.fee.fee, None)
                        .detach();
                } else {
                    ext_token::ext(token)
                        .with_attached_deposit(ONE_YOCTO)
                        .with_static_gas(FT_TRANSFER_GAS)
                        .ft_transfer(fee_recipient.clone(), transfer_message.fee.fee, None)
                        .detach();
                }
            }

            if transfer_message.fee.native_fee.0 > 0 {
                let native_token_id = self.get_native_token_id(transfer_message.get_origin_chain());

                ext_token::ext(native_token_id)
                    .with_static_gas(MINT_TOKEN_GAS)
                    .mint(fee_recipient.clone(), transfer_message.fee.native_fee, None)
                    .detach();
            }

            env::log_str(&OmniBridgeEvent::FinTransferEvent { transfer_message }.to_log_string());
        }
    }

    fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
        let storage_usage = env::storage_usage();
        self.finalised_transfers.remove(transfer_id);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(storage_owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(storage_owner, &storage);
        }
    }

    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }
