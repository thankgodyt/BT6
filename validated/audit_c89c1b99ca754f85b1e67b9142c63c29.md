### Title
Attacker Can Race `request_refund` With Caller-Controlled `gas_fee` Leaving Victim With Near-Zero Refund - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund` flow allows any unprivileged NEAR account to submit a refund request for any BTC deposit UTXO whose `deposit_msg.refund_address` is `None`, and to freely set the `gas_fee` field. The only guard is `gas_fee < amount`; there is no minimum-refund-amount floor. An attacker who races the victim to call `request_refund` can set `gas_fee = amount − 1`, locking the UTXO into a refund request that will return 1 satoshi to the victim while consuming the rest as a miner fee, or can set their own `refund_address` with a minimal `gas_fee` to redirect the bulk of the deposit to themselves.

### Finding Description
In `request_refund_callback` the resolved gas fee is validated only by:

```rust
// refund.rs lines 549-553
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The downstream computation in `refund_execution_inputs` only checks `refund_amount > 0`:

```rust
// refund.rs lines 280-284
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the caller supplies the `refund_address` freely:

```rust
// refund.rs lines 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

Once a refund request is stored, a duplicate is blocked:

```rust
// refund.rs lines 544-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

This means the first caller wins the slot. A legitimate victim who calls `request_refund` after the attacker will be rejected.

The `RefundRequest` struct stores the attacker-chosen `gas_fee` and `refund_address` verbatim:

```rust

    ...
    pub amount: u128,
    pub refund_address: String,
    pub gas_fee: u128,
    ...
}
``` [5](#0-4) 

### Impact Explanation
**Scenario A – Griefing (deposit_msg.refund_address = Some):** Attacker races the victim with `gas_fee = amount − 1` and `refund_address = victim_btc_address`. After the `refund_timelock_sec` (2 days), `execute_refund` is called and the victim receives 1 satoshi while `amount − 1` satoshis are consumed as a miner fee. The victim loses virtually their entire BTC deposit.

**Scenario B – Theft (deposit_msg.refund_address = None):** Attacker races the victim with `gas_fee = min_btc_gas_fee` and `refund_address = attacker_btc_address`. After the `unsafe_refund_timelock_sec` (14 days), the attacker calls `execute_refund` and receives `amount − min_btc_gas_fee` satoshis — the bulk of the victim's deposit. The victim's UTXO is simultaneously marked verified, permanently blocking a legitimate deposit claim. [6](#0-5) 

The DAO can reject the request during the timelock, but this is an off-chain, manual, and time-sensitive mitigation that is not guaranteed.

**Classified impact:** Medium (attacker-triggered locking of bridged funds with potential escalation to Critical theft if the DAO does not intervene within the timelock window).

### Likelihood Explanation
- The BTC deposit transaction and its embedded `deposit_msg` (OP_RETURN data) are fully public on the Bitcoin blockchain.
- Any NEAR account can call `request_refund` with a valid Merkle proof; no privileged role is required.
- The attacker only needs to submit their transaction before the victim's `request_refund_callback` is stored — a realistic race on NEAR where block ordering is deterministic and observable.
- Many users will omit `deposit_msg.refund_address` (it is optional), widening the attack surface to Scenario B.

### Recommendation
1. **Enforce a minimum net refund amount.** After computing `refund_amount`, require it to meet a protocol-configured floor (e.g., `min_deposit_amount` or a dedicated `min_refund_amount` config field):
   ```rust
   require!(
       refund_amount >= config.min_refund_amount,
       "Refund amount after gas fee is below minimum"
   );
   ```
2. **Restrict who may submit a refund request.** When `deposit_msg.refund_address` is `None`, require the caller to be the `deposit_msg.recipient_id` (the intended nBTC recipient) or a privileged `RefundOperator`/DAO role, preventing third-party races.
3. **Cap the caller-supplied `gas_fee`.** Bound it to `config.max_btc_gas_fee` rather than `amount`, consistent with the existing gas-fee ceiling used elsewhere.
