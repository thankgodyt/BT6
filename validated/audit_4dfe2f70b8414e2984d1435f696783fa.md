### Title
Peras Vote and Certificate Signature Verification Entirely Absent in Production `BlockSupportsPeras` Instance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types omits cryptographic signature fields from `PerasVote` and `PerasCert` data types and implements `validatePerasVote` / `validatePerasCert` as stub functions that perform no signature verification. Any unprivileged peer can craft and diffuse arbitrary Peras votes (claiming any voter identity in the stake distribution) and arbitrary Peras certificates (for any round and block), which will be unconditionally accepted by a receiving node. This is the direct analog of the external report's "signature used multiple times" class: rather than a signature being replayable, the authorization token is entirely absent, making every forged object indistinguishable from a legitimate one.

### Impact Explanation

**Vote forgery:** An attacker who knows any `PerasVoterId` present in the current stake distribution can craft a `PerasVote` for any round and any block, send it over the Peras vote diffusion mini-protocol, and have it accepted and counted toward quorum. By sending enough forged votes (one per eligible voter ID), the attacker can single-handedly trigger quorum for an arbitrary block, causing the node to forge a `PerasCert` boosting that block.

**Certificate forgery:** An attacker can craft a `PerasCert` for any round and any block point and have it unconditionally accepted (`validatePerasCert` always returns `Right`). Accepted certificates are stored in the `PerasCertDB` and fed into chain selection via the cert-boost weight, allowing the attacker to bias chain selection toward an attacker-chosen block.

Both paths are reachable by any unprivileged peer connected via the object-diffusion mini-protocol. No key material, stake, or operator access is required.

This maps to: **Bypass of certificate/signature validation that enables unauthorized certificate acceptance** (Critical), and **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain** (High).

---

### Likelihood Explanation

**High.** The attack requires only a TCP connection to a node running the Peras diffusion protocol. The attacker needs only to enumerate voter IDs from the public stake distribution (available on-chain) and send well-formed CBOR-encoded `PerasVote` or `PerasCert` objects. No cryptographic material is needed because no signature field exists in the types and no signature check is performed.

---

### Recommendation

1. Add a cryptographic signature field to `PerasVote blk` and `PerasCert blk` in the production instance (analogous to the `pvSignature :: VoteSignature PerasBLSCrypto` field already present in `Ouroboros.Consensus.Peras.Vote.V1.PerasVote`).
2. Implement `validatePerasVote` to verify the BLS vote signature against the voter's verification key from the committee/stake distribution.
3. Implement `validatePerasCert` to verify the aggregate BLS certificate signature against the aggregate verification key of the quorum voters.
4. Wire the concrete `V1.PerasVote` / `V1.PerasCert` types and their committee-based validators (already implemented in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Committee.EveryoneVotes`) into the production `BlockSupportsPeras` instance, replacing the stub.
5. Track issue #120 (`https://github.com/tweag/cardano-peras/issues/120`) as a security-critical blocker before enabling Peras on any network that processes real stake.

---

### Proof of Concept

1. Connect to a node with Peras object diffusion enabled.
2. Read the current stake distribution to obtain any `PerasVoterId` (pool key hash) with non-zero stake.
3. Craft a `PerasVote` CBOR payload: `[roundNo, blockPoint, voterId]` — no signature field required by the stub type.
4. Send the vote via the Peras vote mini-protocol. `processVotes` calls `validatePerasVote`, which succeeds because `lookupPerasVoteStake` finds the voter ID in the distribution.
5. Repeat for enough voter IDs to exceed the quorum threshold. The node's `PerasVoteDB` will call `updatePerasRoundVoteStates`, reach quorum, and forge a `ValidatedPerasCert` boosting the attacker-chosen block.
6. Alternatively, craft a `PerasCert` CBOR payload: `[roundNo, blockPoint]`. Send it via the Peras cert mini-protocol. `processCerts` calls `validatePerasCert`, which unconditionally returns `Right`, and the cert is stored and applied as a chain-selection boost. [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
