### Title
Missing Bounds Constraint on `PerasQuorumStakeThreshold` Enables Trivial Quorum Bypass in Peras Certificate Forging — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`PerasQuorumStakeThreshold` and `PerasQuorumStakeThresholdSafetyMargin` are bare `Rational` newtypes with no enforced bounds (no check that values are in `(0, 1]`). The quorum-check function `stakeAboveThreshold` compares a `PerasVoteStake` — which the code itself acknowledges may carry absolute ledger-stake (lovelace) values — directly against the relative threshold `3/4 + 2/100 = 0.77`. Because any absolute lovelace amount (e.g., 50,000 lovelace) is trivially `≥ 0.77`, a single vote from any legitimate voter passes the quorum gate, allowing unauthorized Peras certificate forging and chain-weight manipulation.

---

### Finding Description

`PerasQuorumStakeThreshold` is defined as:

```haskell
newtype PerasQuorumStakeThreshold
  = PerasQuorumStakeThreshold {unPerasQuorumStakeThreshold :: Rational}
```

with no smart constructor, no `[0,1]` range check, and no normalization requirement. [1](#0-0) 

The default value is `3/4` (relative fraction of total stake): [2](#0-1) 

The quorum check function is:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [3](#0-2) 

The code itself documents the unit-mismatch problem in the comment immediately above `stakeAboveThreshold`:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [4](#0-3) 

And the `PerasVoteStake` type note confirms the ambiguity:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [5](#0-4) 

`PerasVoteStake` is populated by `lookupPerasVoteStake`, which reads directly from `PerasVoteStakeDistr` — a plain `Map PerasVoterId PerasVoteStake` with no normalization enforced at insertion: [6](#0-5) 

In the production vote-processing path, the stake distribution is read from `getStakeDistrSTM` and fed directly into `validatePerasVote`, which assigns the raw looked-up stake to the validated vote without normalization: [7](#0-6) 

When the ledger stake distribution is used as-is (absolute lovelace values, e.g., `50_000_000_000` lovelace), the comparison `50_000_000_000 >= 0.77` is trivially `True`. The quorum gate is bypassed for every single vote from any voter with positive stake.

The forging path triggered by this bypass: [8](#0-7) 

The forged certificate is then added to the `PerasCertDB` and triggers chain selection for the boosted block: [9](#0-8) 

Chain selection uses `totalWeightOfFragment`, which adds the certificate's `PerasWeight` boost to the fragment's length, potentially making a shorter/weaker chain appear heavier: [10](#0-9) 

---

### Impact Explanation

**Impact: Critical / High.**

Any legitimate voter (any stake pool operator with positive ledger stake) can send a single `PerasVote` message via the object-diffusion mini-protocol. Because `stakeAboveThreshold` compares an absolute lovelace value against the relative threshold `0.77`, the quorum check trivially passes. The node immediately forges a `ValidatedPerasCert` for the voted block and triggers chain selection. The certificate adds `perasWeight = 15` to the chain's total weight, which can cause the node to prefer a non-canonical or adversarially chosen chain over the honest longest chain. This is a bypass of Peras certificate/quorum validation that enables unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

**Likelihood: Medium.**

Peras must be enabled via `rnFeatureFlags` (it is an experimental feature, not on by default). However, once enabled, any legitimate voter — an unprivileged network peer — can trigger this with a single well-formed vote message. No key compromise, no stake majority, and no special privilege is required beyond being a registered stake pool with positive stake.

---

### Recommendation

1. Add a bounds-enforcing smart constructor for `PerasQuorumStakeThreshold` and `PerasQuorumStakeThresholdSafetyMargin` that rejects values outside `(0, 1]`, analogous to how `ascFromDouble` enforces `0 < x < 1` for the active slot coefficient: [11](#0-10) 

2. Resolve the acknowledged unit mismatch in `stakeAboveThreshold`: either normalize `PerasVoteStake` to a relative fraction before comparison, or pass the total stake into the function and perform normalization internally. The normalization must happen before the `>=` comparison, not after.

3. Add a `SanityCheckIssue` variant (analogous to `SnapshotRateLimitDisabled`) that fires on node startup if `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin > 1` or `≤ 0`: [12](#0-11) 

---

### Proof of Concept

**Private-testnet sequence with Peras enabled:**

1. Enable Peras via `rnFeatureFlags` on a test node.
2. Populate `PerasVoteStakeDistr` with absolute lovelace values from the ledger (e.g., voter A has `50_000_000_000` lovelace).
3. Send a single `PerasVote` from voter A for any block `B` via the object-diffusion mini-protocol.
4. The node calls `validatePerasVote`, which assigns `vpvVoteStake = PerasVoteStake 50_000_000_000`.
5. `stakeAboveThreshold` evaluates `50_000_000_000 >= (3/4 + 2/100)` = `50_000_000_000 >= 0.77` = `True`.
6. `votesReachQuorum` returns `Just votesWithQuorum` with only one vote.
7. `forgePerasCert` is called, producing a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15`.
8. The certificate is added to `PerasCertDB` and chain selection is triggered for block `B`.
9. Any chain containing `B` now has `+15` total weight, potentially displacing the honest chain.

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
