### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Always Accepts Any Certificate, Enabling Unauthorized Chain Boost via ObjectDiffusion - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance in the codebase — implements `validatePerasCert` as an unconditional `Right`, accepting every inbound Peras certificate without any cryptographic or structural check. This stub is wired directly into the production node-to-node `PerasCertDiffusion` mini-protocol handler. Any unprivileged peer can send a crafted `PerasCert` for an arbitrary block; the certificate is accepted, stored in the shared `PerasCertDB`, and its boost weight is applied during chain selection, potentially causing the node to prefer an adversary-controlled chain.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository (declared as a catch-all `instance StandardHash blk => BlockSupportsPeras blk`). No cryptographic signature, no committee membership check, no round-number plausibility check — every `PerasCert` value is unconditionally wrapped in `ValidatedPerasCert` and returned as valid. [2](#0-1) 

**Production inbound path — `processCerts` in `PerasCert.hs`:**

`processCerts` calls the supplied `validateCert` function on every new certificate received from a peer. Because `validatePerasCert` always returns `Right`, the `partitionEithers` call always produces an empty error list, and every certificate is unconditionally forwarded to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

The production writer (`makePerasCertPoolWriterFromChainDB`) passes `validatePerasCert mkPerasParams` as the validator and routes accepted certificates into `ChainDB.addPerasCertAsync`:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
...
(void . ChainDB.addPerasCertAsync chainDB)
``` [4](#0-3) 

**Wired into the live node-to-node handler:**

`NodeToNode.hs` registers `makePerasCertPoolWriterFromChainDB` as the inbound handler for the `hPerasCertDiffusionClient` mini-protocol, meaning every connected peer can trigger this path:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [5](#0-4) 

**Shared-state analog to the reported vulnerability:**

The original DeFi bug used a single global `lastBorrowTimestamp` (not per-user), so a second account could update it to bypass the check for the first account. Here, the `PerasCertDB` is a single shared database (not per-peer). Because `validatePerasCert` never rejects, any peer can write an arbitrary certificate into it. The certificate's boost weight is then read by `getWeightSnapshot` during chain selection, affecting the node's chain preference globally — exactly the same pattern of one entity manipulating shared state to subvert a check that was meant to be per-entity (per-round, per-block). [6](#0-5)

### Impact Explanation

An unprivileged peer can inject a `PerasCert` claiming to certify any block at any round. The certificate is stored in the `PerasCertDB` and its `vpcCertBoost` weight (derived from `perasWeight params`) is applied to the targeted block during chain selection via `getWeightSnapshot`. This allows the adversary to artificially boost an adversarial fork, causing the honest node to prefer a non-canonical chain — a consensus safety failure.

This maps to: **Critical — Bypass of Peras certificate checks that enables unauthorized certificate acceptance and chain selection manipulation.**

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is active in the production node-to-node handler. Any peer that speaks the protocol can send a crafted certificate. No stake, no key material, and no special privilege is required — only the ability to connect to the node and send a well-formed CBOR-encoded `PerasCert` message. The attack is deterministic and requires a single message.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's cryptographic aggregate signature against the claimed committee.
2. That the signer set constitutes a valid quorum for the claimed round.
3. That the boosted block point is plausible (exists within the known chain, correct era, etc.).

Until real validation is implemented, the `hPerasCertDiffusionClient` handler should either be disabled or gated behind a feature flag that is off by default, so that the stub cannot be reached from the network.

The fix mirrors the recommendation in the original report: track validity per-entity (per-round, per-block) rather than relying on a single shared acceptance function that ignores all inputs.

### Proof of Concept

1. Adversary connects to a target node via the node-to-node `PerasCertDiffusion` mini-protocol.
2. Adversary constructs a `PerasCert` with `pcCertRound = R` (any round not yet in the DB) and `pcCertBoostedBlock = <adversarial block point>`.
3. The message is sent as the inbound side of `objectDiffusionInbound`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{..}`.
5. `ChainDB.addPerasCertAsync chainDB` stores the certificate; `getWeightSnapshot` now returns a non-zero boost for the adversarial block.
6. On the next chain selection trigger, the adversarial block's effective weight is inflated by `perasWeight params`, potentially making it preferred over the honest tip.
7. The node selects the adversarial chain. [1](#0-0) [7](#0-6) [5](#0-4)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
