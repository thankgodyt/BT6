### Title
Anyone Can Call `request_refund` With Attacker-Controlled `refund_address`, Redirecting Victim's BTC to Attacker — (`contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a permissionless function callable by any NEAR account for any unfinalized BTC deposit. When the original `deposit_msg.refund_address` field is `None`, the caller freely supplies the `refund_address` BTC destination. Because `request_refund_callback` enforces a duplicate-request guard, a single attacker-submitted request locks out the legitimate depositor from filing their own. After `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund`, sending the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` in `api/bridge.rs` (lines 510–535) has no check that the caller is the original depositor:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    ...
) -> Promise {
    ...
    if let Some(msg_refund_address) = &deposit_msg.refund_address {
        require!(
            msg_refund_address == &refund_address,
            "refund_address does not match deposit_msg.refund_address"
        );
    }
    // No else-branch: when deposit_msg.refund_address is None,
    // any caller-supplied refund_address is accepted without restriction.
    self.internal_request_refund(deposit_msg, refund_address, ...)
}
```

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the `refund_address` parameter is entirely attacker-controlled.

In `request_refund_callback` (refund.rs lines 544–547), a duplicate-request guard prevents a second request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

This means the first caller wins. If the attacker submits before the victim, the victim's own `request_refund` call will revert, and the stored `RefundRequest` will carry the attacker's BTC address as `refund_address`.

After `unsafe_refund_timelock_sec` passes, `execute_refund` is callable by anyone (no role restriction beyond `#[pause]`), and `finalize_refund_with_psbt` (refund.rs lines 315–401) builds and signs a PSBT paying `refund_amount` to the stored `refund_address` — the attacker's address.

The `deposit_msg` needed to mount the attack is public: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg` (bridge.rs lines 462–472), and `deposit_msg` is also visible as a call argument in any `verify_deposit` or `request_refund` transaction.

---

### Impact Explanation

**Critical.** The attacker redirects the victim's entire BTC deposit (minus gas fee) to an attacker-controlled Bitcoin address. This is a direct, permanent theft of user funds from the bridge. The victim has no on-chain recourse once the malicious `RefundRequest` is stored; they cannot file a competing request (duplicate guard), and the BTC is irreversibly sent to the attacker after the timelock.

---

### Likelihood Explanation

**Medium.** The attack requires:
1. The victim's `deposit_msg` to be known (trivially obtained from on-chain events or call arguments).
2. The deposit to be unfinalized (i.e., `verify_deposit` was never called for that UTXO).
3. The attacker to submit `request_refund` before the victim (front-running on NEAR, or simply racing).
4. The DAO/Operator to fail to reject the malicious request within `unsafe_refund_timelock_sec`.

Conditions 1–3 are realistic for any user whose deposit was not processed by the relayer. Condition 4 is the only mitigation, and it is a trust assumption, not a trustless protection. The `unsafe_refund_timelock_sec` window is finite and the DAO/Operator may not monitor every request.

---

### Recommendation

Bind the `refund_address` to the caller's identity or to the original depositor. Two options:

1. **Require caller to be the `deposit_msg.recipient_id`** when `deposit_msg.refund_address` is `None`:
   ```rust
   if deposit_msg.refund_address.is_none() {
       require!(
           env::predecessor_account_id() == deposit_msg.recipient_id,
           "Only the recipient may supply a refund_address when none is pre-authorized"
       );
   }
   ```

2. **Require `deposit_msg.refund_address` to always be set** (i.e., make it non-optional), so the BTC destination is committed at deposit time and cannot be overridden by any caller.

---

### Proof of Concept

**Setup:**
- Victim deposits BTC using `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`.
- Victim calls `get_user_deposit_address(deposit_msg)`, which emits `LogDepositAddress` with the full `deposit_msg` (bridge.rs lines 462–472). Attacker observes this event.
- The relayer fails to finalize the deposit (no `verify_deposit` call).

**Attack:**
1. Victim submits `request_refund(deposit_msg, "victim_btc_address", tx_bytes, vout, proof, None)`.
2. Attacker front-runs with `request_refund(deposit_msg, "attacker_btc_address", tx_bytes, vout, proof, None)`.
   - `deposit_msg.refund_address` is `None`, so the `refund_address` check is skipped (bridge.rs lines 519–526).
   - Attacker's request is stored with `refund_address = "attacker_btc_address"` (refund.rs lines 564–578).
3. Victim's `request_refund` call reverts: `"Refund request already exists for this UTXO"` (refund.rs lines 544–547).
4. After `unsafe_refund_timelock_sec` elapses, attacker (or anyone) calls `execute_refund(utxo_storage_key, None)`.
5. `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to `"attacker_btc_address"` (refund.rs lines 293–308, 315–401).
6. MPC signs and broadcasts the transaction. Victim's BTC is permanently sent to the attacker.
