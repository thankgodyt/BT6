### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection Weight — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole concrete `BlockSupportsPeras` instance unconditionally accepts every Peras certificate and every Peras vote without performing any cryptographic or structural verification. Because chain selection uses the resulting `PerasWeightSnapshot` to compare candidate chains, an unprivileged peer can inject a crafted certificate that boosts any block's weight, causing an honest node to prefer a non-canonical fork.

---

### Finding Description

`BlockSupportsPeras` is the class that gates Peras certificate and vote acceptance. The only instance in the codebase is a catch-all degenerate instance declared for all `StandardHash blk`:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

`validatePerasCert` returns `Right` for every input, unconditionally wrapping the attacker-supplied certificate in `ValidatedPerasCert` and assigning it the full configured `perasWeight`. No aggregate-signature check, no quorum check, no voter-eligibility check is performed.

Similarly, `validatePerasVote` only checks whether the voter ID appears in the stake distribution; it never verifies the vote signature:

```haskell
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
``` [2](#0-1) 

Once a certificate passes `validatePerasCert`, it is submitted to `addPerasCertAsync` in the ChainDB API, which adds it to `PerasCertDB` and immediately triggers chain selection for the boosted block: [3](#0-2) 

Chain selection reads the `PerasWeightSnapshot` (populated from accepted certificates) and passes it to `preferAnchoredCandidate`, which calls `weightedSelectView` to compare candidate fragments by total weight when the snapshot is non-empty: [4](#0-3) 

The `wsvTotalWeight` of a fragment is `BlockNo + PerasWeightBoost`, so a single accepted fake certificate can make a shorter fork appear heavier than the honest chain: [5](#0-4) 

The `chainSelSync` path that processes an incoming certificate and triggers chain selection is: [6](#0-5) 

The `PerasWeightSnapshot` is the mutable state that the attacker manipulates — directly analogous to the pending-transaction state in the reference report. The attacker submits a crafted certificate (analogous to submitting a transaction) to inflate the weight of a chosen block, causing the privileged chain-selection operation to prefer the wrong chain.

---

### Impact Explanation

An unprivileged peer can send a single crafted `PerasCert` that boosts any block in the VolatileDB. Because `validatePerasCert` accepts it unconditionally, the certificate enters the `PerasWeightSnapshot`. Chain selection then computes a higher total weight for the attacker's fork and switches to it, permanently diverging from the honest chain. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions of Ouroboros Praos/Peras.

---

### Likelihood Explanation

The Peras certificate reception and chain-selection infrastructure is fully wired in the production codebase. The `addPerasCertAsync` entry point exists in the ChainDB API and is reachable from the network layer. No special privileges, keys, or stake are required — any connected peer can send a `PerasCert` message. The degenerate instance is the **only** `BlockSupportsPeras` instance; no concrete Cardano block type overrides it with real validation. The attack requires sending one network message.

---

### Recommendation

**Short term:** Replace the unconditional `Right` in `validatePerasCert` with `Left PerasValidationErr` (reject all certificates) until a proper implementation is in place. This is strictly safer than accepting everything.

**Medium term:** Implement `validatePerasCert` to:
1. Retrieve the correct `VotingCommittee` for the certificate's `ElectionId` via `getVotingCommitteeForElection` (currently also unimplemented — it always calls `error "TODO"`).
2. Call `verifyCert` against that committee to verify the aggregate BLS signature and voter eligibility.
3. Verify the quorum threshold is met.

Implement `validatePerasVote` to call `verifyVote` and check the vote signature before accepting the vote.

**Long term:** Complete the implementation of `getVotingCommitteeForElection` in `AcrossEpochs.hs` (currently `error "TODO: implement getVotingCommitteeForElection"`) so that cross-epoch certificate validation is possible. [7](#0-6) 

---

### Proof of Concept

1. Attacker connects to a node running the Peras-enabled build.
2. Attacker constructs a `PerasCert` whose `pcCertBoostedBlock` points to a block on a minority fork `F` that is currently shorter than the honest chain.
3. Attacker sends the certificate via the Peras mini-protocol.
4. The node calls `validatePerasCert params cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` with no checks.
5. `addPerasCertAsync` stores the certificate and calls `chainSelSync … (ChainSelAddPerasCert cert …)`.
6. `chainSelectionForBlock` is invoked for the boosted block on fork `F`.
7. `preferAnchoredCandidate` computes `wsvTotalWeight(F) = blockNo(F) + perasWeight > wsvTotalWeight(honest)` and returns `ShouldSwitch`.
8. The node adopts fork `F`, diverging from the honest chain.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
