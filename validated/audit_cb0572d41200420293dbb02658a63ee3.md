### Title
Unprivileged Caller Can Trigger MPC Signing With Attacker-Controlled `key_version`, Permanently Locking Withdrawal Funds - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` carries no caller-restriction beyond the global pause check. Any unprivileged NEAR account can invoke it and supply an arbitrary `key_version`. If the MPC contract accepts the wrong key version and returns a signature, the callback stores it in the pending-info slot, permanently blocking the legitimate relayer from re-signing. The withdrawal transaction is then broadcast with an invalid signature, rejected by Bitcoin, and the user's funds are permanently locked.

### Finding Description
`sign_btc_transaction` is the public entry point that drives the MPC signing pipeline for every pending BTC transaction (withdrawals, refunds, UTXO management). All other state-mutating bridge functions that should be restricted to trusted relayers carry the `#[trusted_relayer]` macro (e.g., `verify_deposit_v2`, `verify_withdraw_v2`, `verify_refund_finalize`). `sign_btc_transaction` is the sole exception: it only carries `#[pause(except(roles(Role::DAO)))]`, leaving it open to any caller.

```
// contracts/satoshi-bridge/src/api/chain_signatures.rs  lines 19-43
#[payable]
#[pause(except(roles(Role::DAO)))]          // ← no #[trusted_relayer] / #[access_control_any]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,                       // ← fully attacker-controlled
) -> PromiseOrValue<bool> { … }
```

The attacker supplies a `key_version` that differs from the one used when the UTXO was locked. The MPC contract (which supports multiple key versions for key rotation) signs the payload with the wrong key and returns a `SignatureResponse`. The callback (`sign_btc_transaction_callback`) unconditionally stores it:

```
// contracts/satoshi-bridge/src/chain_signature.rs  lines 154-158
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
btc_pending_info.signatures[sign_index] = Some(signature.clone());
```

Once the slot is `Some(…)`, the guard at line 92 of `chain_signatures.rs` (`require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed")`) prevents any further signing attempt for that input. When all slots are filled, `is_all_signed()` returns `true`, the PSBT is finalised with the wrong signature, and the pending info advances to `PendingVerify`. The signed-but-invalid transaction bytes are broadcast; Bitcoin rejects them. The withdrawal is now permanently stuck.

### Impact Explanation
User funds (nBTC already deducted from the user's balance via `ft_on_transfer`) are locked in a `PendingVerify` state that can never be resolved: `verify_withdraw_v2` requires the Bitcoin transaction to be confirmed, which it never will be. The `cancel_withdraw` escape hatch requires `Role::DAO` or `Role::Operator`, so an ordinary user has no self-service recovery path. This constitutes permanent locking of user funds.

### Likelihood Explanation
The attack requires only a NEAR account and enough attached NEAR to cover the MPC signing fee (the function is `#[payable]`). The attacker needs to know a valid `btc_pending_sign_id` (these are emitted as on-chain events and are publicly observable) and a `key_version` value that the MPC contract accepts but that differs from the one used to derive the UTXO's public key. Key rotation is a documented MPC feature, making multiple valid key versions a realistic deployment scenario. No privileged access, leaked keys, or off-chain coordination is required.

### Recommendation
Add `#[trusted_relayer]` to `sign_btc_transaction`, consistent with every other relayer-facing function in the bridge API. Alternatively, add `#[access_control_any(roles(Role::DAO, Role::Operator))]` if operator-level signing is desired. Additionally, validate that `key_version` matches the version recorded at UTXO-lock time before forwarding the signing request to the MPC contract.

### Proof of Concept
1. Alice initiates a withdrawal; the bridge creates a `BTCPendingInfo` with `state = WithdrawOriginal(PendingSign)` and emits the `btc_pending_sign_id` in an event.
2. The UTXO was locked under MPC `key_version = 0`.
3. Attacker Eve calls:
   ```
   sign_btc_transaction(
       btc_pending_sign_id = "<alice_tx_id>",
       sign_index = 0,
       key_version = 1          // wrong version; MPC signs with a different key
   )
   ```
   attaching sufficient NEAR for the MPC fee.
4. The MPC contract (which supports key_version 1 for rotation) returns a valid `SignatureResponse` for key_version 1.
5. `sign_btc_transaction_callback` stores the signature: `signatures[0] = Some(wrong_sig)`.
6. `is_all_signed()` returns `true`; the PSBT is finalised and the pending info moves to `PendingVerify`.
7. The relayer broadcasts the transaction; Bitcoin rejects it (signature does not match the P2WPKH script derived from key_version 0).
8. Alice's nBTC is already locked/burned; her BTC UTXO is still controlled by the bridge; she has no self-service recovery. Funds are permanently locked. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
