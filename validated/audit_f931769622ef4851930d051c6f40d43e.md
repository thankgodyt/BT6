### Title
`PerasVote` Accepted Without Cryptographic Signature Verification, Enabling Vote Forgery and Quorum Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `validatePerasVote` implementation for the degenerate `BlockSupportsPeras` instance accepts any inbound Peras vote that names a registered stake pool voter, without verifying any cryptographic signature. The `PerasVote blk` data type carries no signature field at all. An unprivileged peer can forge votes on behalf of any registered stake pool, directing them to an attacker-chosen block, and those votes will be counted toward quorum. The legitimate vote from the impersonated pool is then silently suppressed as a duplicate.

### Finding Description

**Root cause — missing signature field and no signature check:**

The production `PerasVote blk` data type is defined as:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

There is no signature field. The `validatePerasVote` implementation for the active degenerate instance only checks whether the `PerasVoterId` appears in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

**Attacker-controlled entry path:**

Inbound votes from peers are processed by `processVotes` in the vote diffusion mini-protocol. It filters out votes whose `PerasVoteId` (`roundNo`, `voterId`) is already in the DB, then calls `validatePerasVote` on the remainder:

```haskell
validationResults <- atomically $ do
  alreadyInDb <- alreadyInDbSTM
  let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
  mapM validateVote votesNotAlreadyInDb
``` [3](#0-2) 

The `validateVote` callback used in production is:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

**Exploit flow:**

1. Attacker observes that stake pool `X` (a registered `PerasVoterId`) has not yet voted in round `R`.
2. Attacker crafts `PerasVote { pvVoteRound = R, pvVoteBlock = attackerBlock, pvVoteVoterId = X }` — no private key required.
3. The vote passes `validatePerasVote` because `X` is present in the stake distribution.
4. The vote is inserted into the `PerasVoteDB` with `voteId = (R, X)` marked as seen.
5. When pool `X` later sends its legitimate vote for `legitimateBlock`, `processVotes` finds `(R, X)` already in `alreadyInDb` and silently drops it. [5](#0-4) 

The model explicitly acknowledges the assumption being violated:

> `-- NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body).` [6](#0-5) 

**Analog to the external report:**

| reNFT | Ouroboros Consensus |
|---|---|
| `RentPayload` has no `orderHash` unique field | `PerasVote blk` has no `signature` field |
| Signature valid for any order with same metadata | Vote accepted for any registered voter ID |
| Same signature replayed across multiple orders | Forged vote suppresses legitimate vote |
| `validateOrder` checks expiry but not uniqueness | `validatePerasVote` checks stake membership but not authenticity |

### Impact Explanation

An unprivileged peer can forge Peras votes for any registered stake pool without possessing their private key. By pre-filling the vote DB with forged votes targeting an attacker-chosen block, the attacker can:

1. **Manipulate which block receives a Peras certificate** (quorum boost), causing honest nodes to prefer a non-canonical chain.
2. **Suppress legitimate votes** from impersonated pools, preventing quorum from being reached for the correct block.
3. **Bypass Peras voting checks entirely** — the `validatePerasVote` function is the sole cryptographic gate for vote acceptance, and it performs no cryptographic verification.

This matches the allowed impact: *Critical — Bypass of Peras voting checks that enables unauthorized vote acceptance*, and *High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain*.

### Likelihood Explanation

The attack requires only a network connection to an honest node running the Peras vote diffusion mini-protocol. No keys, stake, or privileged access are needed. The attacker only needs to know the `KeyHash` of a registered stake pool (publicly available on-chain) and the current round number. The attack is deterministic and requires no brute force.

### Recommendation

1. Add a `pvSignature` field to `PerasVote blk` (analogous to adding `orderHash` to `RentPayload`), binding the vote cryptographically to the voter's private key, the round, and the target block.
2. Implement `validatePerasVote` to verify this signature using the voter's registered verification key from the stake distribution, before accepting the vote.
3. Until the full committee-selection crypto is wired in (tracked in issue #120), at minimum reject votes whose `PerasVoterId` does not correspond to a verifiable signature over `(roundNo, blockPoint)`.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
