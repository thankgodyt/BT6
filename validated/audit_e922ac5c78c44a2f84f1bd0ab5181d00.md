### Title
Peras Vote and Certificate Validation Stubs Unconditionally Accept All Inbound Objects — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships stub implementations of `validatePerasCert` and `validatePerasVote` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate it receives. `validatePerasVote` only checks that the claimed voter ID appears in the stake distribution map, but never verifies the vote's cryptographic signature or VRF eligibility proof. Both stubs are wired directly into the live object-diffusion inbound pipelines (`processCerts`, `processVotes`), making them reachable by any unprivileged peer.

---

### Finding Description

The `BlockSupportsPeras` instance (the only instance in the codebase) provides the following stub for certificate validation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every `PerasCert` received from a peer is immediately wrapped in `ValidatedPerasCert` and returned as `Right`, regardless of its content. [1](#0-0) 

The vote validation stub is equally incomplete:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

It only checks that the claimed `pvVoteVoterId` appears in the `PerasVoteStakeDistr` map. No BLS signature, no VRF eligibility proof, and no round-number or block-point sanity check is performed. [2](#0-1) 

Both stubs are used verbatim in the production inbound pipelines. For certificates:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

For votes (both the `PerasVoteDB` and `ChainDB` writers):

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) [5](#0-4) 

`processVotes` runs validation inside a single `atomically` block and then calls `addVote` for each validated vote outside that transaction. Because validation always succeeds, every vote that names a known voter ID is stored and counted toward the quorum tally. [6](#0-5) 

Once enough forged votes accumulate for a target, `updateCandidateVoteState` calls `votesReachQuorum`, which checks only the summed `vpvVoteStake` values (baked in from the stake distribution at validation time) against the quorum threshold, and then calls `forgePerasCert` — also a stub that always returns `Right`. [7](#0-6) 

---

### Impact Explanation

**Certificate path:** A single crafted `PerasCert` naming any round number and any block point is accepted unconditionally. The stored `ValidatedPerasCert` carries a `vpcCertBoost` equal to `perasWeight params`. Chain selection uses this boost to prefer the attacker-chosen block over the honest canonical tip, constituting an unauthorized chain-weight manipulation.

**Vote path:** An attacker who knows any pool ID present in the current `PerasVoteStakeDistr` (publicly observable on-chain) can send fabricated votes for that pool ID. Because no signature is checked, the votes are accepted, their stake is credited to the tally, and once the tally crosses the quorum threshold a certificate is forged for an attacker-chosen block. This is a full bypass of the Peras quorum mechanism.

Both paths map to: **Critical — bypass of Peras certificate/vote verification checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

The object-diffusion mini-protocol is reachable by any peer the node connects to. The `PerasVote` wire type carries only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId` — all of which are public information. No private key material is required to construct a vote that passes the current stub. The attack requires only knowledge of the stake distribution (available from any chain-sync peer) and the ability to open a connection to the target node.

---

### Recommendation

1. Replace the `validatePerasCert` stub with a real implementation that verifies the aggregate BLS signature and the quorum of VRF eligibility proofs against the committee for the certificate's round, using the correct epoch-snapshot stake distribution.
2. Replace the `validatePerasVote` stub with a real implementation that verifies the BLS vote signature (`pvSignature`) and, for non-persistent voters, the VRF eligibility proof, before accepting the vote into the DB.
3. Until real validation is in place, gate the Peras object-diffusion inbound pipelines behind a feature flag so that no peer-supplied votes or certificates are processed on production nodes.

---

### Proof of Concept

**Certificate injection (private testnet):**

1. Connect a malicious peer to an honest node running the Peras object-diffusion server.
2. Send a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = <attacker-chosen block point>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The certificate is stored; the boosted block gains `perasWeight` extra chain weight.
5. Chain selection on the honest node switches to the attacker-chosen fork.

**Vote-based quorum forgery (private testnet):**

1. Observe the current `PerasVoteStakeDistr` (e.g., via a `LocalStateQuery`).
2. For each pool ID in the distribution, send a `PerasVote` with `pvVoteVoterId = <pool id>`, `pvVoteRound = R`, `pvVoteBlock = <attacker-chosen block>`, and an arbitrary/empty signature field.
3. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; all pass because only the map lookup is checked.
4. Votes accumulate in `PerasVoteDbState`; once total stake exceeds the quorum threshold, `updateCandidateVoteState` forges a certificate for the attacker-chosen block.
5. The forged certificate is propagated to chain selection, boosting the attacker's fork. [8](#0-7) [9](#0-8) [10](#0-9)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
