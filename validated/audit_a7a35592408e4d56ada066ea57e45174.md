### Title
Peras Certificate Validation Stub Always Accepts Any Peer-Injected Certificate, Enabling Unauthorized Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used across the codebase implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) without performing any cryptographic or semantic verification. Any unprivileged peer can therefore inject an arbitrary Peras certificate via the certificate diffusion protocol. Because accepted certificates are stored in the `PerasCertDB` and immediately trigger chain selection for the boosted block, an attacker can boost a fork block's weight beyond the honest chain's weight, causing the victim node to switch to a non-canonical chain. This is the direct analog of the external report's pattern: a function callable by any party modifies shared state (chain-selection weight) on behalf of the node, with no authorization check.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The catch-all instance of `BlockSupportsPeras` (introduced as a compilation shim) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the `validateCert` function passed into `processCerts` by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate from a peer. Because the stub always returns `Right`, every certificate passes validation and is timestamped and stored:

```haskell
([], validatedCerts) ->
  mapM_
    (addCert . WithArrivalTime now)
    validatedCerts
``` [4](#0-3) 

**State mutation — `PerasCertDB` and `pcdsLatestCertSeen`:**

`implAddCert` stores the certificate and updates `pcdsLatestCertSeen` to the certificate with the highest round number seen so far:

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [5](#0-4) 

**Chain selection trigger — `chainSelSync`:**

When a certificate is added to the `ChainDB` path, `chainSelSync` immediately triggers chain selection for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [6](#0-5) 

**Weight boost applied to chain selection:**

The `PerasWeightSnapshot` derived from all stored certificates is used in `weightedSelectView` to compute `wsvTotalWeight = blockNo + weightBoost`. A chain containing the attacker-boosted block gains additional weight:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [7](#0-6) 

`preferCandidate` then switches to the candidate if its total weight exceeds the current chain's:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch ...
``` [8](#0-7) 

**Secondary impact — voting rule manipulation via `pcdsLatestCertSeen`:**

`pcdsLatestCertSeen` is read by `getLatestCertSeen` and fed into `PerasVotingView.latestCertSeen`. Voting rule VR-2A requires the latest cert seen to be at least `R` rounds old:

```haskell
getPerasCertRound (lcsCert cert) + _R :<=: currRoundNo
``` [9](#0-8) 

An attacker injecting a certificate with a round number close to the current round causes VR-2A to fail, suppressing the victim node's votes for `R` rounds.

### Impact Explanation

**Primary (High — chain selection):** An unprivileged peer can inject a crafted `PerasCert` boosting a block on a fork. Because `validatePerasCert` performs no cryptographic check, the certificate is accepted, stored, and immediately triggers chain selection. The fork block's `wsvTotalWeight` is inflated by `perasWeight` (the configured Peras boost), potentially exceeding the honest chain's weight. The node then irreversibly switches to the non-canonical fork. This matches the "High" impact category: an unprivileged peer makes an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

**Secondary (Critical — certificate validation bypass):** The bypass of all Peras certificate cryptographic and semantic checks (`verifyCert`, quorum threshold, voter eligibility, aggregate BLS signature) means any peer can forge a certificate for any round and any block. This directly matches the "Critical" impact: bypass of Peras certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

Any peer connected to the node via the Peras certificate diffusion mini-protocol can send a `PerasCert` message. No stake, key material, or privileged access is required. The attacker only needs to know the hash of a block already in the victim node's `VolatileDB` (obtainable via the ChainSync protocol). The attack is deterministic and requires a single crafted message.

---

### Recommendation

1. **Implement real `validatePerasCert`** for the production Cardano block type: verify the aggregate BLS signature over `(roundNo, boostedBlock)`, check that the voter set meets the quorum threshold against the stake distribution from the relevant epoch, and verify each voter's eligibility proof. Remove the degenerate catch-all instance or gate it behind a compile-time flag that is disabled in production builds.

2. **Do not trigger chain selection** from a certificate until it has passed full cryptographic validation. The `chainSelSync` path should only be reached for `ValidatedPerasCert` values produced by a non-stub `validatePerasCert`.

3. **Bound `pcdsLatestCertSeen` updates** to certificates that have passed full validation, so that voting rules cannot be manipulated by injecting high-round-number certificates.

### Proof of Concept

```
1. Attacker node A connects to victim node V via the Peras cert diffusion protocol.

2. A observes (via ChainSync) that V's VolatileDB contains a fork block B'
   at BlockNo N with hash H, which is NOT on V's current chain.

3. A constructs a PerasCert:
     { pcCertRound    = <any round number>
     , pcCertBoostedBlock = BlockPoint slotOf(B') H
     }
   No signature or voter set is required because validatePerasCert ignores them.

4. A sends this PerasCert to V via the object diffusion protocol.

5. processCerts calls validatePerasCert mkPerasParams cert => Right (no check).
   The cert is stored in PerasCertDB with boost = perasWeight params.

6. chainSelSync fires for B'. The PerasWeightSnapshot now maps H -> perasWeight.
   weightedSelectView computes wsvTotalWeight(fork) = N + perasWeight.

7. If perasWeight > (honest_tip_blockNo - N), preferCandidate returns ShouldSwitch.
   V switches to the fork containing B', abandoning the honest chain.
```
