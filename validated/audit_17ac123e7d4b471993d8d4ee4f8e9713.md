### Title
ChainSync Client `checkPreferTheirsOverOurs` Ignores Peras Weight Boosts, Causing Incorrect Peer Disconnection and Chain Selection Failure — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client evaluates chain preference using `emptyPerasWeightSnapshot` — ignoring all Peras certificate weight boosts — while every other chain-preference call site in the codebase (ChainDB chain selection, GSM candidate comparison) uses the real, populated `PerasWeightSnapshot`. When Peras is active and a peer's chain carries fewer blocks but more Peras-boosted weight than the local chain, the guard incorrectly concludes the peer's chain is not preferred and throws `CandidateTooSparse`, severing the connection. The node then remains on its current, lighter chain and never adopts the legitimately heavier Peras-boosted candidate.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever a peer's header lies beyond the current forecast horizon and the ledger view cannot yet be projected. Its purpose is to disconnect from peers whose chains the node would never select anyway, avoiding wasted resources. The guard calls `preferAnchoredCandidate` with a hard-coded `emptyPerasWeightSnapshot`:

```haskell
-- ChainSync/Client.hs ~line 1838
shouldSwitch $
  preferAnchoredCandidate
    (configBlock cfg)
    emptyPerasWeightSnapshot   -- ← always empty; ignores Peras boosts
    ourFrag
    theirFrag
```

With an empty snapshot, `preferAnchoredCandidate` falls back to a pure block-number comparison (longest-chain rule). If the peer's fragment has fewer blocks than the local fragment, `ShouldNotSwitch` is returned and the client throws `CandidateTooSparse`, disconnecting.

Every other call site that performs the same logical comparison uses the real weight snapshot:

- **ChainDB `constructPreferableCandidates`** (ChainSel.hs ~line 777): `preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain`
- **ChainDB `initialChainSelection`** (ChainSel.hs ~line 177): `preferAnchoredCandidate bcfg weights curChain chain`
- **GSM `getCandidateOverSelection`** (NodeKernel.hs ~line 306–310): `preferAnchoredCandidate (configBlock cfg) (forgetFingerprint weights) headers (csCandidate state)`

The inconsistency is acknowledged by a TODO comment in the source:

```haskell
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
emptyPerasWeightSnapshot
```

---

### Impact Explanation

Under Peras, a chain with fewer blocks can carry strictly more total weight than a longer chain if it has accumulated sufficient certificate boosts. When such a chain is offered by a peer and the relevant header is beyond the forecast horizon:

1. `checkPreferTheirsOverOurs` compares by block number only.
2. The peer's chain (fewer blocks, more Peras weight) appears not preferred.
3. The client throws `CandidateTooSparse` and disconnects.
4. The node never downloads or validates the heavier chain.
5. The node remains on the lighter, less-preferred chain.

This is a **chain selection failure**: an honest node is made to prefer a non-canonical chain (its own, lighter one) over the correct Peras-boosted chain, violating the Peras chain-selection invariant. If the condition is widespread across nodes, the network may fail to converge on the heaviest chain, undermining the security guarantees Peras is designed to provide.

**Impact class**: High — chain selection bug that causes an honest node to reject a legitimately preferred chain beyond the intended security assumptions.

---

### Likelihood Explanation

The bug is triggered whenever all three conditions hold simultaneously:

1. Peras is active and certificates have been issued, creating non-trivial weight boosts.
2. A peer's chain has accumulated more Peras weight than the local chain but has fewer blocks (possible when the local chain grew faster in slots but the peer's chain received more certificates).
3. The peer's next header is beyond the local forecast horizon (a normal transient condition during syncing or after a long slot gap).

Condition 3 is a routine occurrence during initial sync and after network partitions. Conditions 1 and 2 become increasingly likely as Peras certificate issuance grows. No adversarial action is required; the scenario arises from normal honest-node operation.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live Peras weight snapshot, consistent with every other call site. The ChainSync client already has access to the node configuration and ChainDB handle; the snapshot can be fetched via `ChainDB.getPerasWeightSnapshot` (as done in `NodeKernel.hs`) and threaded into the client environment, or read atomically inside the STM block. The existing TODO (`https://github.com/tweag/cardano-peras/issues/64`) should be resolved before Peras is activated on mainnet.
