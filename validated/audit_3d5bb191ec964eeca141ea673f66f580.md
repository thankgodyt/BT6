### Title
Migration Window Allows Deposits to Mint Unredeemable Old nBTC, Permanently Locking BTC — (`contracts/satoshi-bridge/src/nbtc/migration.rs`, `contracts/satoshi-bridge/src/api/token_receiver.rs`)

### Summary
The `migrate_to_new_token` flow in `satoshi-bridge` does not pause `verify_deposit` during the multi-block async migration window. Any deposit verified after the balance snapshot is taken but before `migrate_to_new_token_resolve` completes mints old nBTC tokens that are excluded from the migration. After migration finalizes, `ft_on_transfer` rejects the old token, making those old nBTC tokens permanently unredeemable while the corresponding BTC remains locked in the bridge's UTXOs.

### Finding Description

`migrate_to_new_token` executes as a three-step async promise chain:

1. **Snapshot** — `internal_migrate_to_new_token` fires parallel cross-contract calls to `ft_total_supply` and `ft_balance_of` for every listed account on the old token.
2. **Mint** — `migrate_to_new_token_mint` validates `sum == total_supply` against the snapshot values, then issues a sequential batch of `mint` calls on the new token.
3. **Resolve** — `migrate_to_new_token_resolve` updates `nbtc_account_id` to the new token. [1](#0-0) [2](#0-1) 

This chain spans multiple NEAR blocks, especially when N accounts are large (N sequential `mint` calls in step 2). During this entire window, `verify_deposit` and `verify_deposit_v2` remain callable by any relayer and continue to mint on the **current** `nbtc_account_id`, which is still the old token until step 3 completes. [3](#0-2) 

The `sum == total_supply` integrity check in `migrate_to_new_token_mint` compares the snapshot sum to the snapshot total supply — both captured at the same moment — so it passes even if new old-nBTC was minted after the snapshot. The newly minted old tokens are simply invisible to the migration. [4](#0-3) 

After `migrate_to_new_token_resolve` runs, `ft_on_transfer` enforces:

```rust
require!(
    token_id == self.internal_config().nbtc_account_id,
    "Invalid token_id"
);
``` [5](#0-4) 

Any user holding old nBTC minted during the migration window is now permanently blocked from initiating a withdrawal. The bridge's UTXOs still hold the corresponding BTC, but there is no code path that allows old-token holders to redeem it. The old tokens are also not burned by the migration. [6](#0-5) 

### Impact Explanation

BTC deposited during the migration window is permanently locked in the bridge's UTXO set. The depositor receives old nBTC that the bridge refuses to accept for withdrawal, and the migration does not burn or account for those tokens. There is no recovery path in the production code: a second migration round cannot safely include the missed accounts without double-minting for accounts already migrated in round one. This constitutes **permanent locking of user funds**.

### Likelihood Explanation

The migration window spans the full duration of the async promise chain — snapshot queries (1 round-trip per account), N sequential mint calls on the new token, and the resolve callback. With a non-trivial account list this window covers tens to hundreds of NEAR blocks. Any relayer submitting a legitimate `verify_deposit` during this interval triggers the issue without any special knowledge or adversarial intent. The existence of the privileged `verify_migrate_deposit` function confirms the protocol is aware that deposits during migration are a concern, but there is no code-level enforcement preventing unprivileged relayers from calling the standard deposit path during this window. [7](#0-6) 

### Recommendation

Before initiating `migrate_to_new_token`, the bridge should be paused (using the existing `#[pause]` mechanism) to prevent any `verify_deposit` calls from executing during the migration window. The migration operator should:

1. Pause the bridge via the DAO.
2. Call `migrate_to_new_token` with the complete account list.
3. Unpause only after `migrate_to_new_token_resolve` has confirmed success and `nbtc_account_id` has been updated.

Alternatively, `migrate_to_new_token` itself should assert that the bridge is paused before proceeding, making the safe ordering a hard requirement rather than an operational convention.

### Proof of Concept

1. Bridge is live; old nBTC total supply is 1,000,000 sat across accounts A, B, C.
2. `MigrationOperator` calls `migrate_to_new_token(new_token, [A, B, C])`.
3. Snapshot promises are dispatched. The migration window begins.
4. Relayer calls `verify_deposit` for user D's 50,000-sat BTC deposit. The call succeeds and mints 50,000 old nBTC to D (bridge still points to old token).
5. `migrate_to_new_token_mint` fires: snapshot sum (1,000,000) == snapshot total_supply (1,000,000) ✓. New nBTC is minted for A, B, C only.
6. `migrate_to_new_token_resolve` sets `nbtc_account_id = new_token`.
7. D attempts `ft_transfer_call` on old nBTC → `ft_on_transfer` panics: `"Invalid token_id"`.
8. D's 50,000 sat of BTC is permanently locked in the bridge's UTXOs. D holds 50,000 old nBTC with no redemption path.

    pub fn migrate_to_new_token_resolve(
        &mut self,
        new_token: AccountId,
        accounts: usize,
        total_amount: U128,
    ) {
        require!(is_promise_success(), "Migration mint failed");
        self.internal_mut_config().nbtc_account_id = new_token.clone();
        Event::TokenMigrated {
            new_token: &new_token,
            accounts,
            total_amount,
        }
        .emit();
    }
