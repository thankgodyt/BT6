Audit Report

## Title
Silent `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

`process_fin_transfer_to_near` inserts the transfer ID into `finalised_transfers` and decrements `locked_tokens` before dispatching `ft_transfer` to the recipient. When `ft_transfer` panics (e.g., because a rebasable NEP-141 token's balance in the bridge has dropped below the recorded amount), `fin_transfer_send_tokens_callback` calls `is_refund_required(false)`, which unconditionally returns `false` without inspecting the promise result. The callback therefore emits `FinTransferEvent` and does not revert the finalization or the unlock action, permanently freezing the user's funds.

## Finding Description

**Step 1 — Transfer ID committed before token delivery.**
`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, which inserts the `TransferId` into `finalised_transfers` and panics if already present. This write is committed to contract state before `send_tokens` is dispatched at line 1957. [1](#0-0) 

**Step 2 — `send_tokens` uses plain `ft_transfer` for the common case.**
When `msg.is_empty()` (the default for most transfers), `send_tokens` issues `ft_transfer`, not `ft_transfer_call`, so `is_ft_transfer_call = !msg.is_empty()` evaluates to `false`. [2](#0-1) [3](#0-2) 

**Step 3 — Callback never checks the promise result for plain `ft_transfer`.**
`is_refund_required` returns `false` unconditionally when `is_ft_transfer_call` is `false`, without calling `env::promise_result_checked`. A panicking `ft_transfer` is therefore indistinguishable from a successful one. [4](#0-3) 

**Step 4 — Failure path is never taken; state is not reverted.**
Because `is_refund_required` returns `false`, the callback skips the revert block (lines 1703–1718) that would call `revert_lock_actions`, `remove_fin_transfer`, and emit `FailedFinTransferEvent`. Instead it falls into the `else` branch and emits `FinTransferEvent`, leaving `finalised_transfers` permanently containing the transfer ID and `locked_tokens` permanently decremented. [5](#0-4) 

**Trigger — rebasable NEP-141 token.**
`init_transfer_internal` records the exact transferred amount in `locked_tokens` using the caller-supplied value, not the bridge's actual balance. After a negative rebase the bridge holds fewer tokens than recorded. The subsequent `ft_transfer(recipient, original_amount)` panics because the bridge's balance is insufficient. [6](#0-5) [7](#0-6) 

## Impact Explanation

This matches the critical allowed impact: **permanent freezing of bridged funds**. The user's tokens on the source chain are already burned/locked at the time of finalization. After the failed `ft_transfer`, the transfer ID is permanently in `finalised_transfers` (preventing any retry), `locked_tokens` is decremented to zero, and the bridge holds stranded tokens it can never release through the normal flow. The user receives nothing on NEAR and cannot recover funds on the source chain.

## Likelihood Explanation

Rebasable NEP-141 tokens (e.g., liquid staking derivatives subject to slashing) exist in the NEAR ecosystem. The bridge imposes no programmatic restriction on registering rebasable tokens via `bind_token` or `add_deployed_tokens`. Once a rebasable token is registered, any user can bridge it via `ft_transfer_call` → `ft_on_transfer`. A negative rebase (slashing event or protocol adjustment) is an inherent property of the token class and requires no attacker action. The finalization is triggered by a trusted relayer performing its normal duty. No privileged or malicious action is required beyond the initial token registration.

## Recommendation

1. **Check the promise result unconditionally in `is_refund_required`**: for `is_ft_transfer_call = false`, call `env::promise_result_checked(0, ...)` and return `true` on `Err`, so a panicking `ft_transfer` triggers the same revert path as a failed `ft_transfer_call`.
2. **Alternatively, move `add_fin_transfer` after a successful `send_tokens` callback**, so a failed delivery leaves the transfer retryable.
3. **Document and enforce** that rebasable NEP-141 tokens must not be registered as bridged assets on the NEAR side.

## Proof of Concept

1. Register a rebasable NEP-141 token via `bind_token` (proof from registered factory).
2. User calls `ft_transfer_call(bridge, 1000, InitTransferMsg{recipient: eth_addr})` → `init_transfer_internal` records `locked_tokens[(Eth, token)] += 1000`; bridge holds 1000 tokens.
3. Token rebases down: bridge account balance drops to 900.
4. Trusted relayer calls `fin_transfer(FinTransferArgs{chain_kind: Eth, prover_args: proof_of_1000_token_return})`.
5. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer(&transfer_id)` → `finalised_transfers.insert(transfer_id)` = **true** (state committed).
   - `unlock_tokens_if_needed(Eth, token, 1000)` → `locked_tokens[(Eth, token)] = 0` (state committed).
   - `send_tokens(token, recipient, 1000, "")` → `ft_transfer(recipient, 1000)` → **panics** (bridge holds only 900).
6. `fin_transfer_send_tokens_callback(…, is_ft_transfer_call=false, lock_actions)`:
   - `is_refund_required(false)` → `false` (promise result never checked).
   - Enters `else` branch → emits `FinTransferEvent`.
   - Lock actions NOT reverted; `finalised_transfers` NOT cleaned up.
7. **Result**: transfer ID permanently in `finalised_transfers`; `locked_tokens = 0`; bridge holds 900 stranded tokens; user receives 0 tokens on NEAR; source-chain tokens are burned. Funds are permanently frozen.

    fn lock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(current_amount) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        let new_amount = current_amount
            .checked_add(amount)
            .near_expect(TokenLockError::LockedTokensOverflow);

        self.locked_tokens.insert(&key, &new_amount);

        LockAction::Locked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
