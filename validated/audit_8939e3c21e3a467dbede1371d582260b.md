### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Fake Peras Certificates and Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the universal `BlockSupportsPeras` instance unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or quorum validation. Any unprivileged peer can send a crafted `PerasCert` naming an arbitrary block as the boosted target. The certificate passes the inbound validation gate in `processCerts`, is stored in the `PerasCertDB`, and triggers `chainSelectionForBlock` with the attacker-chosen block receiving a `perasWeight` boost. This lets an adversary make an honest node prefer a non-canonical chain.

---

### Finding Description

**Vulnerability class:** Bypass of certificate/vote verification — the validation function that is supposed to authenticate a Peras certificate (verify aggregate BLS signature, check voter eligibility, confirm quorum) is a stub that always succeeds. This is the direct analog of the external report's pattern: a function that should bind a resource to an authorized identity instead accepts any caller-supplied identity without verification.

**Root cause — `validatePerasCert` stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** instance of `BlockSupportsPeras` in the production path (the universal `StandardHash blk` instance). It accepts every certificate unconditionally and assigns it the full `perasWeight` boost from the hardcoded `mkPerasParams`.

**Inbound processing path — `processCerts`:** [2](#0-1) 

`processCerts` calls the injected `validateCert` function on every inbound certificate. Because `validatePerasCert` always returns `Right`, every certificate from every peer passes this gate and is forwarded to `addCert`.

**Pool writer wires the stub directly to the ChainDB:** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validator and `ChainDB.addPerasCertAsync` as the sink. The hardcoded `mkPerasParams` is a secondary compounding issue (wrong parameters even if validation were fixed), but the primary flaw is the stub.

**Chain selection consequence — `chainSelSync` for a Peras cert:** [4](#0-3) 

Once the certificate is stored in `PerasCertDB`, `chainSelSync` retrieves the boosted block from `VolatileDB` and calls `chainSelectionForBlock` for it. The `PerasWeightSnapshot` now contains the attacker-chosen block with a `perasWeight` of 15 (default), causing `compareChainDiffs` to prefer any candidate chain that contains that block.

**Weight snapshot used in candidate comparison:** [5](#0-4) 

The `weights` snapshot is read atomically and passed into `constructPreferableCandidates` and `chainSelection`, directly influencing which fork the node adopts.

**Default weight value:** [6](#0-5) 

`perasWeight = PerasWeight 15` — a boost of 15 is applied to the attacker-chosen block, overriding the honest chain's preference.

---

### Impact Explanation

An unprivileged peer can inject a `PerasCert` naming any block hash as `pcCertBoostedBlock`. The certificate bypasses all validation, is stored durably in `PerasCertDB`, and triggers chain selection that may cause the node to switch to a fork containing the boosted block. Because the weight boost (15) is applied unconditionally and the `PerasCertDB` deduplicates only by round number, an attacker can boost one block per round. This constitutes a **chain selection manipulation** that lets an adversary make an honest node prefer a non-canonical or adversarially-controlled chain, violating the Peras security assumption that only legitimately certified blocks receive weight boosts.

---

### Likelihood Explanation

The Peras certificate mini-protocol (ObjectDiffusion) is reachable by any connected peer without authentication. The attack requires only sending a well-formed CBOR-encoded `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. No key material, stake, or privileged access is needed. The stub is the active production code path for all block types (the universal `StandardHash blk` instance), not a test-only path.

---

### Recommendation

1. **Implement `validatePerasCert` properly.** The concrete `V1.PerasCert` type already carries `pcVoters` and `pcSignature` (aggregate BLS). Validation must verify: (a) the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)`, (b) voter eligibility against the epoch's stake distribution and committee selection, and (c) that the aggregate stake of eligible voters meets the quorum threshold.

2. **Replace the hardcoded `mkPerasParams` stub** in `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` with the actual chain-derived `PerasParams` once the HFC plumbing (tracked in issue #73) is in place.

3. **Do not ship the universal stub instance as production code.** The `TODO` comment referencing issue #120 confirms this is known incomplete work; it must be gated behind a feature flag or replaced before the Peras protocol is activated on any network where the certificate mini-protocol is enabled.

---

### Proof of Concept

```
Attacker (unprivileged peer) connects to an honest node via the Peras
ObjectDiffusion mini-protocol.

1. Attacker observes that block B (on a minority fork) is in the node's
   VolatileDB (e.g., via ChainSync headers).

2. Attacker sends a single PerasCert message:
     PerasCert { pcCertRound = <any unused round R>
               , pcCertBoostedBlock = <Point of block B> }

3. processCerts calls (validatePerasCert mkPerasParams) on the cert.
   validatePerasCert returns Right unconditionally.

4. The cert is forwarded to ChainDB.addPerasCertAsync.

5. chainSelSync (ChainSelAddPerasCert branch) adds the cert to PerasCertDB
   and calls chainSelectionForBlock for block B.

6. compareChainDiffs now sees block B with PerasWeight 15 boost.
   If the minority fork containing B is otherwise equal in length to the
   honest chain, the node switches to the minority fork.

Result: honest node adopts an adversarially-chosen chain without any
legitimate quorum of Peras voters having certified it.
```

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
```
