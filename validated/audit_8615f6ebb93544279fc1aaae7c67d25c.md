### Title
Silent `tx_bytes` Corruption in `internal_safe_verify_deposit_entry` Permanently Locks Deposited BTC - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the caller-supplied `tx_bytes` exceed 10,000 bytes, the code silently replaces them with 300 zero bytes (`vec![0u8; 300]`). The bridge still mints nBTC using the correct `deposit_amount` (computed from the original transaction before the replacement), but stores a UTXO with corrupted, all-zero `tx_bytes`. When the bridge later attempts to spend that UTXO to service a withdrawal, `WrappedTransaction::decode` is called on the zeroed bytes and panics, permanently locking the deposited BTC.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, the `deposit_amount` and `tx_id` are derived from the original decoded `transaction` object: [1](#0-0) 

Then, **after** those values are captured, the `tx_bytes` variable is silently overwritten: [2](#0-1) 

The UTXO is then constructed using the now-corrupted `tx_bytes` but the correct `balance` and `tx_id`: [3](#0-2) 

This UTXO (with zeroed `tx_bytes`) is passed through `internal_safe_verify_deposit` → `verify_safe_deposit_callback` → `internal_set_utxo`, landing in the bridge's live UTXO set: [4](#0-3) 

The minting proceeds correctly — nBTC is issued for the real `deposit_amount` — but the stored UTXO is permanently broken. Any future attempt to build a withdrawal PSBT that selects this UTXO will call `WrappedTransaction::decode` on 300 zero bytes and panic, making the BTC unspendable.

This is the direct analog to the zkSync issue: the value used for the policy check (`deposit_amount`, derived from the real transaction) differs from the data stored for the actual downstream operation (`tx_bytes`, now zeroed). In zkSync the mismatch was between `_l2Value` (checked) and `msg.value` (minted); here it is between the verified transaction bytes (used for proof and amount) and the stored transaction bytes (used for PSBT construction).

The entry points that reach this path are all publicly callable (with extra confirmations for non-whitelisted relayers): [5](#0-4) [6](#0-5) 

---

### Impact Explanation

The deposited BTC is permanently locked inside the bridge's MPC-controlled deposit address. The bridge has minted nBTC against it, so the token supply is no longer fully backed. Every subsequent withdrawal that happens to select this UTXO will panic, and the UTXO can never be recovered without a contract upgrade. This constitutes **permanent locking of protocol funds** and a broken backing invariant.

---

### Likelihood Explanation

A Bitcoin transaction exceeds 10,000 bytes when it has roughly 67+ P2PKH inputs (≈148 bytes each) or fewer inputs of other script types. A user who has accumulated many small UTXOs — a realistic scenario for active bridge users — can produce such a transaction. The attacker does not need any privileged role; they only need to deposit BTC via a large consolidation transaction and wait for a relayer (or call the function themselves with extra confirmations) to submit it through the safe-deposit path.

---

### Recommendation

Replace the silent corruption with a hard rejection:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes too large for safe deposit"
);
```

If large transactions must be supported, store the full `tx_bytes` without modification. The current behavior of replacing bytes with zeros is never safe: it corrupts the UTXO irreversibly while allowing minting to proceed.

---

### Proof of Concept

1. User accumulates 70+ small Bitcoin UTXOs (e.g., from many small deposits or payments).
2. User constructs a consolidation transaction spending all 70+ UTXOs, with one output sending BTC to the bridge's deposit address derived from a chosen `DepositMsg`. Total `tx_bytes` length exceeds 10,000 bytes.
3. A relayer (or the user themselves, accepting extra confirmations) calls `safe_verify_deposit` / `verify_deposit_v2` (with `safe_deposit` set) supplying the large `tx_bytes`.
4. `internal_safe_verify_deposit_entry` decodes the transaction, computes the correct `deposit_amount`, then replaces `tx_bytes` with `vec![0u8; 300]`.
5. The light-client proof passes; `verify_safe_deposit_callback` fires, `safe_mint` succeeds, and nBTC is credited to the user.
6. `internal_set_utxo` stores the UTXO with `tx_bytes = [0u8; 300]` and the correct `balance`.
7. Later, when any withdrawal PSBT selects this UTXO, `WrappedTransaction::decode(&utxo.tx_bytes, &config.chain)` is called on 300 zero bytes and panics with "Deserialization tx_bytes failed".
8. The BTC is permanently unspendable; the bridge's backing is broken by the full deposit amount.
