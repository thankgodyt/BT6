### Title
Unprivileged Caller Can Trigger MPC Signing of Any User's Pending Transaction via `sign_btc_transaction` - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary
`sign_btc_transaction` is a public, payable function with no ownership check. Any NEAR account can call it with an arbitrary `btc_pending_sign_id` and an arbitrary `sign_index` / `key_version`, triggering an MPC chain-signature request against a pending transaction that belongs to a different user. This is the direct analog of the reported `EscrowVoteManagerV1.poke()` pattern: a state-mutating function that accepts an identifier the caller does not own and acts on it without verifying ownership.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is decorated only with `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. It performs no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. [1](#0-0) 

The function accepts a caller-supplied `btc_pending_sign_id`, looks up the corresponding `BTCPendingInfo`, and immediately forwards to `internal_sign_btc_transaction` (or, for RBF transactions whose original no longer exists, removes the pending info entirely from the owner's account). Neither branch verifies that the caller is the owner of the pending transaction.

The `BTCPendingInfo` struct carries an `account_id` field that records the legitimate owner: [2](#0-1) 

That field is never compared against `env::predecessor_account_id()` inside `sign_btc_transaction`.

The RBF early-exit path is particularly direct: if an attacker calls `sign_btc_transaction` with an RBF `btc_pending_sign_id` at a moment when the original transaction's pending info has been removed (e.g., immediately after `verify_withdraw` succeeds), the contract removes the RBF entry from the **owner's** `btc_pending_sign_ids` and deletes the `BTCPendingInfo` — all on behalf of an unrelated caller: [3](#0-2) 

For the non-RBF path, the attacker supplies an arbitrary `sign_index` and `key_version` to `internal_sign_btc_transaction`, which dispatches an MPC chain-signature request. Supplying a wrong `key_version` causes the MPC to produce a signature under a different key than the one that controls the bridge's Bitcoin UTXOs, rendering the resulting Bitcoin transaction invalid and permanently unbroadcastable.

---

### Impact Explanation

**Medium / Critical boundary.**

- **Stuck withdrawal (Medium):** An attacker who supplies a valid `sign_index` but an incorrect `key_version` causes the MPC to store a signature that cannot satisfy the Bitcoin script. The victim's `BTCPendingInfo` advances to a signed state with a bad signature; `verify_withdraw` will never succeed, and the nBTC that was already transferred to the bridge is locked until an operator manually intervenes to rebuild and re-sign the transaction.
- **Premature RBF cleanup (Medium):** For RBF pending transactions, the attacker can silently delete the victim's pending info and remove it from the victim's `btc_pending_sign_ids`, making the victim unable to track or complete their own RBF withdrawal. The underlying UTXO remains locked in the bridge's signing pipeline with no recoverable handle.

Both outcomes match the allowed impact: *"attacker-triggered temporary locking of bridged funds"* and *"stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

The function is publicly reachable by any NEAR account. The only cost to the attacker is the NEAR storage deposit required by `#[payable]`. All `btc_pending_sign_id` values are emitted as on-chain events (`GenerateBtcPendingInfo`), so an attacker can enumerate live pending IDs without any privileged access. No leaked keys, no governance control, and no third-party compromise are required. [4](#0-3) 

---

### Recommendation

Add an ownership guard at the top of `sign_btc_transaction`, before any state mutation or cross-contract call:

```rust
let caller = env::predecessor_account_id();
require!(
    btc_pending_info.account_id == caller
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::Operator.into()], caller),
    "sign_btc_transaction: caller is not the owner of this pending transaction"
);
```

This mirrors the pattern already used in `resolve_execute_refund_timelock` where privileged roles are allowed to bypass the normal restriction: [5](#0-4) 

---

### Proof of Concept

```
// Attacker observes on-chain event: GenerateBtcPendingInfo { account_id: victim, btc_pending_id: "abc123" }
// Attacker calls, attaching 1 yoctoNEAR:
sign_btc_transaction(
    btc_pending_sign_id = "abc123",   // victim's pending tx
    sign_index          = 0,          // valid input index
    key_version         = 9999,       // wrong key version → MPC signs with wrong key
)
// Result: MPC stores a signature under key_version 9999.
// The PSBT is now "fully signed" with an invalid signature.
// verify_withdraw will never succeed; victim's nBTC is permanently locked in the bridge.
// Operator must manually detect the bad signature, rebuild the PSBT, and re-sign.
```

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
