Audit Report

## Title
`init_transfer` Accepts Amounts That Normalize to Zero, Permanently Freezing Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` locks user tokens into the bridge without verifying that `normalize_amount(amount - fee) > 0`. `sign_transfer` enforces this check and panics before reaching the MPC call when the normalized amount is zero, meaning the MPC callback that would remove the transfer message is never invoked. With no cancellation or refund path, the locked tokens are permanently frozen.

## Finding Description
The NEAR bridge uses a two-step outbound flow: `init_transfer` locks tokens and stores a `TransferMessage`; `sign_transfer` requests an MPC signature for the destination chain. Decimal normalization is required because NEAR-side tokens may have higher precision than their destination-chain counterparts.

`init_transfer` only validates:
```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```
at `near/omni-bridge/src/lib.rs` lines 554–557. Tokens are locked immediately after this check passes.

`sign_transfer` then calls:
```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```
at lines 475–485. If `amount - fee < 10^(origin_decimals - decimals)`, this panics — before the MPC `sign` call is ever made.

`sign_transfer_callback` only removes the `TransferMessage` on a successful MPC response:
```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
}
```
at lines 655–658. Since `sign_transfer` panics before reaching the MPC call, the callback is never scheduled, and `remove_transfer_message` is never called. No other public function provides a cancellation or refund path. The `TransferMessage` remains in `pending_transfers` indefinitely and the locked balance is never released.

`update_transfer_fee` has the same gap: it only checks `fee.fee < transfer.message.amount` (lines 399–402), so a sender can raise the token fee post-initiation until `amount - fee` normalizes to zero, rendering a previously valid transfer permanently un-signable.

## Impact Explanation
This constitutes **permanent freezing of bridged funds** — a Critical impact under the allowed scope. Any token pair where `origin_decimals > decimals` creates a minimum transferable unit of `10^(origin_decimals - decimals)`. Amounts below this threshold pass `init_transfer`, are locked, and can never be moved to the destination chain or recovered on NEAR.

## Likelihood Explanation
Any unprivileged user interacting with a token pair where `origin_decimals > decimals` (e.g., a 24-decimal NEAR token bridged to a 6-decimal EVM token, diff = 18, minimum unit = 10^18) can trigger this by calling `ft_transfer_call` with an amount below the minimum unit. No special role or access is required. There is no on-chain rejection at `init_transfer` and no UI-enforced minimum, making accidental triggering realistic. The `update_transfer_fee` vector additionally allows a sender to self-inflict this on an already-initiated transfer.

## Recommendation
Add the normalization check inside `init_transfer` (after constructing `transfer_message` and before storing it) and inside `update_transfer_fee` (after updating the fee):

```rust
// In init_transfer, after the fee < amount check:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

Apply the same guard in `update_transfer_fee` after `transfer.message.fee = fee` to prevent a valid transfer from being made un-signable after the fact.

## Proof of Concept
1. Deploy a NEAR token with `origin_decimals = 24`; bind it to an EVM address with `decimals = 6` via `bind_token` (diff = 18, minimum unit = 10^18).
2. Call `ft_transfer_call` on the token contract with `amount = 999_999_999_999_999_999` (< 10^18) and `msg` encoding `InitTransferMsg { fee: U128(0), native_token_fee: U128(0), recipient: <EVM address> }`.
3. Observe `init_transfer` succeeds; tokens are deducted from the user and locked in the bridge contract.
4. Call `sign_transfer` with the resulting `transfer_id`.
5. Observe the call panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` because `normalize_amount(999_999_999_999_999_999, {24, 6}) = 999_999_999_999_999_999 / 10^18 = 0`.
6. Confirm no public function exists to recover the locked tokens — `remove_transfer_message` is only reachable via `sign_transfer_callback` (requires a successful MPC response, which is never requested) or `claim_fee_callback` (requires a `FinTransfer` proof from the destination chain, which never exists because no signature was ever produced).
