### Title
Zero-Amount `PostAction` Bypasses Per-Item Validation in `check_deposit_msg`, Causing Silent Panic in `handle_post_action` - (File: contracts/satoshi-bridge/src/deposit_msg.rs)

### Summary

The `check_deposit_msg` function validates `PostAction` entries in a loop, accumulating `total_amount` and comparing it against `actual_mintable_amount`. However, it never checks that individual `PostAction.amount` values are non-zero. A zero-amount entry passes every per-item check (whitelist, gas bounds, msg-template match) and contributes nothing to `total_amount`, so the aggregate guard also passes. The zero-amount post_action is then returned as valid and forwarded to `handle_post_action`, which calls `internal_transfer` with `amount = 0`. The NEP-141 standard mandates a panic on zero-amount transfers; because the call is `.detach()`-ed, the panic is silent and the post_action never executes.

### Finding Description

In `contracts/satoshi-bridge/src/deposit_msg.rs`, `check_deposit_msg` iterates over `post_actions` and accumulates `total_amount`:

```rust
let mut total_amount = 0;
for (index, post_action) in post_actions.iter().enumerate() {
    total_amount += post_action.amount.0;
    // whitelist check, gas check, msg-template check …
}
if total_amount > actual_mintable_amount {
    // emit event, return None
}
Some(post_actions)   // ← zero-amount entries included here
```

There is no guard of the form `require!(post_action.amount.0 > 0, …)`. A `PostAction { amount: U128(0), … }` passes every branch and is returned inside `Some(post_actions)`.

The returned list is forwarded to `nbtc::mint`, which calls `handle_post_actions`, which calls `handle_post_action` for each entry:

```rust
let amount = amount.into();   // 0u128
self.token.internal_transfer(&sender_id, &receiver_id, amount, memo);
// ↑ panics: NEP-141 requires amount > 0
```

Because every `handle_post_action` call is `.detach()`-ed, the panic is swallowed silently. The deposit itself succeeds and nBTC is minted to `recipient_id`, but the intended post-action (e.g., a DeFi deposit) never executes.

### Impact Explanation

**Low.** This is a publicly reachable invariant violation and panic-driven fault in a production bridge path. User funds are not lost — nBTC is already minted to `recipient_id` before `handle_post_actions` runs. However, the post_action silently fails, leaving the user's nBTC stranded in their account rather than forwarded to the intended DeFi receiver. No operator intervention is required to recover funds, but the bridge's post_action invariant (validated entries must be executable) is broken.

### Likelihood Explanation

Any unprivileged user can trigger this. A user controls the `DepositMsg` by choosing which BTC deposit address to send funds to (the address is derived from the `DepositMsg` hash). A user can craft a `DepositMsg` containing a `PostAction` with `amount: 0` targeting a whitelisted receiver, send real BTC to the corresponding address, and have a relayer call `verify_deposit`. The zero-amount entry passes `check_deposit_msg` and reaches `handle_post_action`.

### Recommendation

Add a per-item zero-amount guard inside the validation loop in `check_deposit_msg`:

```rust
for (index, post_action) in post_actions.iter().enumerate() {
    if post_action.amount.0 == 0 {
        Event::InvalidPostAction {
            index: Some(index),
            err_msg: "post_action amount must be greater than zero.".to_string(),
        }.emit();
        return None;
    }
    total_amount += post_action.amount.0;
    // … existing checks …
}
```

### Proof of Concept

1. Construct a `DepositMsg` with:
   ```json
   {
     "recipient_id": "alice.near",
     "post_actions": [
       { "receiver_id": "<whitelisted_dapp>", "amount": "0", "msg": "<valid_template>", "gas": "50000000000000" }
     ]
   }
   ```
2. Derive the BTC deposit address from this `DepositMsg` and send real BTC to it.
3. A relayer calls `verify_deposit` with the above `DepositMsg`.
4. `check_deposit_msg` is called: `total_amount = 0`, `0 > actual_mintable_amount` is `false`, so `Some(post_actions)` is returned with the zero-amount entry.
5. `nbtc::mint` mints nBTC to `alice.near` and calls `handle_post_actions` with the zero-amount entry.
6. `handle_post_action` calls `internal_transfer(sender, receiver, 0, …)`, which panics.
7. The panic is silently swallowed (detached call). Alice's nBTC is minted but the DeFi post_action never executes. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
