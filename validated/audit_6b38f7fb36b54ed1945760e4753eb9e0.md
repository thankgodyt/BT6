### Title
Missing Proof-of-Possession Enforcement Enables BLS Rogue Key Attack on Peras Certificate Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

---

### Summary

`aggregatePublicKeys` in `BLS.hs` explicitly documents that proofs of possession (PoP) must be verified for all keys before aggregation, but `verifyProofOfPossession` is never called anywhere outside of `BLS.hs` itself. The entire Peras certificate verification pipeline — both `WFALS.implVerifyCert` and `EveryoneVotes.implVerifyCert` — aggregates pool BLS public keys taken directly from the ledger stake distribution without any PoP check. A malicious pool operator can register a crafted BLS key that, when naively aggregated with the other committee members' keys, yields an aggregate key the attacker controls, allowing them to forge Peras certificates for arbitrary blocks.

---

### Finding Description

**Root cause — unenforced precondition on `aggregatePublicKeys`:**

`aggregatePublicKeys` carries an explicit precondition comment:

```
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  ...
  aggKey <- uncheckedAggregateVerKeysDSIGN ...
``` [1](#0-0) 

The function is named `uncheckedAggregateVerKeysDSIGN` — the "unchecked" prefix signals that no PoP validation is performed inside. The entire safety guarantee is delegated to callers.

**`verifyProofOfPossession` is never called outside `BLS.hs`:**

A grep for `verifyProofOfPossession` returns matches only within `BLS.hs` (the definition itself). `ProofOfPossession` similarly appears only in `BLS.hs`. No production code path ever calls `verifyProofOfPossession` before aggregating keys. [2](#0-1) 

**Certificate verification aggregates keys without PoP:**

`WFALS.implVerifyCert` collects voter public keys directly from `extWFAStakeDistr` (the ledger stake distribution) and passes them to `aggregateVoteVerificationKeys`, which calls `BLS.aggregatePublicKeys`, with no PoP check at any point: [3](#0-2) 

The same pattern holds in `EveryoneVotes.implVerifyCert`: [4](#0-3) 

The concrete `PerasBLSCrypto` instance wires `aggregateVoteVerificationKeys` directly to `BLS.aggregatePublicKeys`: [5](#0-4) 

**The rogue key attack:**

In BLS without PoP, an attacker who knows the public keys of all other committee members `pk_1, ..., pk_{n-1}` can register a crafted key:

```
pk_A = target_key - (pk_1 + pk_2 + ... + pk_{n-1})
```

where `target_key = sk_target * G` for a scalar `sk_target` the attacker knows. The naive aggregate then becomes:

```
pk_1 + ... + pk_{n-1} + pk_A = target_key
```

The attacker can now produce a valid BLS aggregate signature over any message using `sk_target`, which will verify against `target_key`.

---

### Impact Explanation

A malicious pool operator can forge a Peras certificate boosting an arbitrary block. Honest nodes call `verifyCert`, which calls `implVerifyCert`, which aggregates the committee's public keys (including the attacker's crafted key) and verifies the forged aggregate signature — and succeeds. This constitutes a **bypass of Peras certificate/vote verification** enabling unauthorized certificate acceptance. A forged certificate can cause honest nodes to boost a non-canonical block, breaking chain selection and potentially causing irreversible chain divergence.

Impact classification: **Critical** — bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The attacker must:
1. Be a registered pool operator with positive stake (no privileged access required — any pool operator qualifies).
2. Know the stake distribution at the epoch boundary to compute the committee composition. This is public on-chain data.
3. Register a crafted BLS key before the target epoch. Key registration is a normal on-chain operation.

The committee composition is deterministic from the public stake distribution, so the attacker can compute it in advance. The only constraint is timing: the crafted key must be registered before the epoch snapshot. This is a realistic, low-barrier attack for any pool operator.

---

### Recommendation

**Short term:** Enforce PoP verification at the point where pool BLS keys are accepted into the ledger state (during pool registration/update transactions). The `verifyProofOfPossession` function already exists and is correct; it must be called before any key is admitted to the stake distribution used for committee construction.

**Long term:** Consider making the PoP check structurally impossible to bypass by introducing a `VerifiedPublicKey` newtype that can only be constructed by `verifyProofOfPossession`, and changing `aggregatePublicKeys` to accept only `VerifiedPublicKey` values. This eliminates the reliance on an unenforced precondition comment. [6](#0-5) 

---

### Proof of Concept

1. Observe the on-chain stake distribution at epoch `E-2` (the snapshot epoch for epoch `E`'s committee).
2. Compute the set of committee members `{pk_1, ..., pk_{n-1}}` that will be in the Peras committee for epoch `E` (deterministic from public data).
3. Choose a target scalar `sk_target` and compute `target_key = sk_target * G`.
4. Compute the crafted key: `pk_A = target_key - (pk_1 + ... + pk_{n-1})`.
5. Submit an on-chain pool registration/update transaction registering `pk_A` as the pool's BLS key (no PoP required because `verifyProofOfPossession` is never called).
6. In epoch `E`, forge a Peras certificate for an arbitrary block `B`:
   - Compute `msg = hashVoteSignature(roundNo, B)`.
   - Produce aggregate signature `aggSig = sk_target * H(msg)` (standard BLS signing with `sk_target`).
   - Construct a `WFALSCert` or `EveryoneVotesCert` claiming all committee members voted for `B`, with `aggSig`.
7. Submit the forged certificate to an honest node.
8. The node calls `verifyCert` → `implVerifyCert` → `aggregateVoteVerificationKeys` → `BLS.aggregatePublicKeys`, producing `target_key`. It then calls `verifyAggregateVoteSignature` with `target_key` and `aggSig`, which succeeds.
9. The honest node accepts the forged certificate and boosts block `B`.

-- | Aggregate multiple public keys into a single one.
--
-- PRECONDITION: all keys must have the same scope.
--
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  -- Ensure all keys have the same scope before aggregation
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $
    PublicKey
      { unPublicKey = aggKey
      , publicKeyScope = publicKeyScope firstKey
      }
