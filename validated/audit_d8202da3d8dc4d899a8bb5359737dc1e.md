### Title
Stub `validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates, Enabling Unauthorized Chain-Selection Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` is a no-op stub that unconditionally returns `Right` for every certificate it receives. Because this function is the sole validation gate in the inbound certificate pipeline (`processCerts` → `makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject arbitrary `PerasCert` values — with any round number and any boosted-block point — that are accepted, stored in the `PerasCertDB`, and used to trigger Peras-weighted chain selection. This is the direct analog of the ERC-721 report: invalid objects are accepted without validity checks at intake time, and the downstream critical process (chain selection) is then corrupted by them.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory cryptographic/semantic gate before a certificate may be stored or acted upon. The only concrete instance in the codebase is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called directly in the production inbound-certificate path. `makePerasCertPoolWriterFromChainDB` constructs the pool writer that the ObjectDiffusion mini-protocol uses to process peer-supplied certificates:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each new certificate and, if it returns `Right`, timestamps it and passes it to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, every certificate from every peer passes. The certificate is then added to the `PerasCertDB` and forwarded to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` processes it: it adds the cert to the DB and, if the boosted block is in the VolatileDB, immediately triggers `chainSelectionForBlock` for that block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `PerasWeightSnapshot` used during chain selection will now include the injected boost (`perasWeight mkPerasParams = PerasWeight 15`) for the attacker-chosen block, making any chain containing that block heavier by 15 units in the weighted comparison.

---

### Impact Explanation

**Impact: High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

A peer can craft a `PerasCert` with:
- `pcCertRound` set to any round not yet in the local `PerasCertDB` (deduplication is per round number, so many distinct rounds are available)
- `pcCertBoostedBlock` pointing to any block hash the attacker knows is in the target node's VolatileDB (e.g., a block on a minority fork)

The injected certificate assigns a weight boost of `PerasWeight 15` to the attacker-chosen block. If the honest node's current chain and a fork differ by fewer than 15 blocks in length, the injected boost is sufficient to flip chain selection in favor of the fork. This constitutes unauthorized chain-selection manipulation: the node switches to a chain it would not have selected under correct Peras rules, violating the settlement guarantees Peras is designed to provide.

---

### Likelihood Explanation

**Likelihood: Medium** — The Peras ObjectDiffusion mini-protocol is a public peer-to-peer interface. Any node that connects to a Peras-enabled node can send `PerasCert` messages. No special privileges, keys, or stake are required. The attacker only needs to know a block hash present in the target's VolatileDB (easily obtained via ChainSync) and a round number not yet in the target's cert DB. The only constraint is that Peras must be enabled on the target node; the codebase notes Peras is disabled by default, but the vulnerability is present in the production code path for when it is enabled.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed committee members' public keys.
2. That the committee members are eligible for the given round (VRF-based committee selection).
3. That the total stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold`).
4. That the certificate's round number is within the valid window (not expired per `perasCertMaxRounds`).

Until the real implementation is in place, the `processCerts` inbound path should refuse all externally-supplied certificates (or gate them behind a feature flag that is off by default), rather than accepting them unconditionally.

The analogous fix to the ERC-721 report's recommendation is: validate at intake (`provideERC721` → `processCerts`) rather than deferring to the downstream critical process (liquidation → chain selection).

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a Peras-enabled honest node via the ObjectDiffusion mini-protocol for certificates.
2. Attacker observes (via ChainSync) that the honest node has block `B` (on a minority fork) in its VolatileDB, at slot `s`.
3. Attacker sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = B }` for any round `R` not yet in the node's `PerasCertDB`.
4. `makePerasCertPoolWriterFromChainDB` → `processCerts` calls `validatePerasCert mkPerasParams cert`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally. [5](#0-4) 
6. `addPerasCertAsync` enqueues the cert; `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for block `B`. [6](#0-5) 
7. Chain selection now computes the weight of any fragment containing `B` as `blockNo(tip) + 15`. If the honest node's current chain tip has block number within 15 of the fork tip, the node switches to the fork.
8. The attacker can repeat with additional round numbers to inject multiple boosts, each adding `PerasWeight 15`, amplifying the effect.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
