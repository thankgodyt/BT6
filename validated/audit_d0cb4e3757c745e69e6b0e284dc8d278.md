Audit Report

## Title
`deploy_token` Missing Pause Check Allows Token Deployment When Program Is Fully Paused - (`solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program's `deploy_token` instruction contains no pause guard, while every other user-facing instruction (`finalize_transfer`, `finalize_transfer_sol`, `init_transfer`, `init_transfer_sol`) checks the `paused` bitflag before proceeding. When an operator calls `pause()`, which sets `config.paused = ALL_PAUSED`, `deploy_token` remains fully callable by any party holding a valid MPC-signed `DeployTokenPayload`. This is a direct pause bypass allowing a bridge action to execute during an emergency halt, in contrast to the EVM `OmniBridge.sol` which explicitly guards `deployToken` with `whenNotPaused(PAUSED_DEPLOY_TOKEN)`.

## Finding Description
In `solana/programs/bridge_token_factory/src/lib.rs`, the `deploy_token` handler (lines 66–76) performs only signature verification and then calls `initialize_token_metadata` with no check against `config.paused`:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

By contrast, `finalize_transfer` (lines 82–85) and `init_transfer` (lines 125–128) both open with:

```rust
require!(
    ctx.accounts.common.config.paused & FINALIZE_TRANSFER_PAUSED == 0,
    error::ErrorCode::Paused
);
```

The constants file (`constants.rs`, lines 36–42) defines:

```rust
pub const INIT_TRANSFER_PAUSED: u8 = 1 << 0;
pub const FINALIZE_TRANSFER_PAUSED: u8 = 1 << 1;
pub const ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED;
```

No `DEPLOY_TOKEN_PAUSED` bit exists. The `pause()` instruction (`pause.rs`, line 27) sets `self.config.paused = ALL_PAUSED`, which only covers bits 0 and 1. Even with the bridge in a fully-paused emergency state, `deploy_token` is unconditionally reachable.

The EVM counterpart (`OmniBridge.sol`, line 138) explicitly guards the equivalent function with `whenNotPaused(PAUSED_DEPLOY_TOKEN)`, and `pauseAll()` (lines 552–557) includes `PAUSED_DEPLOY_TOKEN` in its flag set. The Solana implementation is inconsistent with this design.

**Exploit path:**
1. During normal operation, an attacker observes or collects a valid MPC-signed `DeployTokenPayload` for a token not yet deployed on Solana.
2. An operator calls `pause()` → `config.paused = 0b11`.
3. The attacker submits a `deploy_token` transaction with the collected `SignedPayload<DeployTokenPayload>`.
4. The instruction has no `require!(config.paused & DEPLOY_TOKEN_PAUSED == 0, ...)` guard; execution proceeds unconditionally.
5. `initialize_token_metadata` runs: a new SPL mint PDA is created (seeded by `[WRAPPED_MINT_SEED, token_hash]`), Metaplex metadata is written, and a Wormhole message is posted — all while the bridge is in an emergency-halted state.

Note: because the mint PDA uses `init` with a seed derived from the token ID, an already-deployed token cannot be redeployed (the `init` constraint would fail). The attack applies only to tokens not yet deployed.

## Impact Explanation
This is a **pause bypass** allowing an unprivileged external user to execute a bridge token-deployment action during an emergency halt. This matches the allowed critical impact: *"Unauthorized transaction, authorization bypass, role bypass, pause bypass, or signer/prover verification bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

Concrete consequences during a pause triggered by a suspected vulnerability in the token-deployment flow or a compromised MPC key:
- New SPL token mints and their NEAR-token-ID mappings are written into program state, expanding the token registry in a state the operators intended to be frozen.
- A Wormhole message is posted from the paused program, potentially triggering downstream cross-chain state changes on NEAR or EVM chains that operators cannot anticipate or block.
- If the pause was triggered because the MPC signing key is suspected compromised, an attacker with access to the compromised key can deploy attacker-influenced token mappings before operators can rotate the key, setting up unauthorized minting paths once the bridge is unpaused.

## Likelihood Explanation
The entry path is fully unprivileged. `deploy_token` requires only a valid MPC-signed `DeployTokenPayload`, which is routinely produced during normal bridge operation whenever a new NEAR token is bridged to Solana. An attacker can passively collect such a signature by monitoring on-chain or off-chain MPC output before any pause event. No admin compromise, key theft, or collusion is required for the basic pause-bypass scenario. The attack is repeatable for any token whose signature has been collected but whose mint PDA has not yet been initialized.

## Recommendation
1. Add a `DEPLOY_TOKEN_PAUSED` constant (e.g., `1 << 2`) to `constants.rs` and include it in `ALL_PAUSED`:
   ```rust
   pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;
   pub const ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED;
   ```
2. Add the corresponding pause guard at the top of `deploy_token` in `lib.rs`, mirroring the pattern used by `finalize_transfer` and `init_transfer`:
   ```rust
   pub fn deploy_token(
       ctx: Context<DeployToken>,
       data: SignedPayload<DeployTokenPayload>,
   ) -> Result<()> {
       require!(
           ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
           error::ErrorCode::Paused
       );
       msg!("Deploying token");
       data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
       ctx.accounts.initialize_token_metadata(data.payload)?;
       Ok(())
   }
   ```
3. Import `DEPLOY_TOKEN_PAUSED` in `lib.rs` alongside `FINALIZE_TRANSFER_PAUSED` and `INIT_TRANSFER_PAUSED`.
