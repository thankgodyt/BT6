### Title
Front-Running of `request_refund` Redirects BTC Refund to Attacker's Address When `deposit_msg.refund_address` is `None` - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None` and later calls `request_refund`, an attacker can observe the pending NEAR transaction and submit an identical call with their own BTC address as `refund_address`. Because only one refund request can exist per UTXO, the attacker's request lands first, and after the `unsafe_refund_timelock_sec` elapses, the bridge MPC-signs a transaction sending the user's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, permissionless function (no method-level `#[trusted_relayer]` guard) callable by any NEAR account. [1](#0-0) 

When `deposit_msg.refund_address` is `None`, `internal_request_refund` skips the address-match check entirely: [2](#0-1) 

The callback only verifies that the BTC transaction output matches the deposit address derived from `deposit_msg`. Since the attacker copies the same `deposit_msg` (with `refund_address: None`), the deposit address is identical and the check passes: [3](#0-2) 

A duplicate-request guard ensures only one `RefundRequest` can exist per UTXO: [4](#0-3) 

So whichever `request_refund` call is confirmed first wins. The stored `refund_address` is then used verbatim when `execute_refund` builds the Bitcoin refund transaction: [5](#0-4) 

The `deposit_msg` is fully public: `get_user_deposit_address` emits a `LogDepositAddress` event containing the entire struct. The BTC `tx_bytes` and Merkle proof are public on-chain data. The attacker needs no privileged information. [6](#0-5) 

---

### Impact Explanation

The attacker redirects the entire BTC deposit (minus gas fee) to their own Bitcoin address. The user's BTC is permanently lost. This is a direct theft of user funds via a publicly reachable, unprivileged entry point.

The `unsafe_refund_timelock_sec` is intended to give DAO/Operator time to reject suspicious requests, but it is ineffective here: the attacker's request contains a valid proof and a valid `deposit_msg`. Because `deposit_msg.refund_address` is `None`, there is no on-chain record of the user's intended BTC address. The DAO/Operator cannot distinguish the attacker's request from a legitimate one without off-chain communication from the victim. [7](#0-6) 

---

### Likelihood Explanation

- All inputs needed to construct the attack (`deposit_msg`, `tx_bytes`, Merkle proof) are publicly observable on NEAR and Bitcoin.
- `request_refund` is permissionless — any NEAR account can call it.
- NEAR transactions are visible to validators and monitoring nodes before finalization, enabling race-condition submission.
- The attack is economically rational for any deposit large enough to exceed the NEAR storage deposit cost (`required_balance_for_request_refund()`).
- The `deposit_msg.refund_address: None` path is an explicitly supported and tested use case. [8](#0-7) 

---

### Recommendation

Bind the `refund_address` to the caller's identity at request time. Specifically:

1. **Require caller authentication**: Record `env::predecessor_account_id()` in the `RefundRequest` and require that only the original requester (or DAO/Operator) can call `execute_refund` for that request.
2. **Or pre-authorize the refund address**: Require that `deposit_msg.refund_address` is always set (non-`None`) so the BTC destination is committed at deposit time and cannot be overridden by any caller.
3. **Or commit-reveal**: Require the caller to commit a hash of `refund_address` in one transaction and reveal it in a subsequent one, preventing observation-based front-running.

---

### Proof of Concept

1. Alice deposits BTC using `DepositMsg { recipient_id: alice.near, refund_address: None, ... }`. The `LogDepositAddress` event reveals the full `deposit_msg`.
2. `verify_deposit` is never called (relayer down, etc.).
3. Alice calls `request_refund(deposit_msg, "bc1q_alice...", tx_bytes, vout, proof, None)`.
4. Attacker observes Alice's pending NEAR transaction. Attacker calls `request_refund(deposit_msg, "bc1q_attacker...", tx_bytes, vout, proof, None)` with higher priority / in the same block.
5. Attacker's transaction is confirmed first. `RefundRequest` is stored with `refund_address = "bc1q_attacker..."`.
6. Alice's `request_refund` fails: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec`, anyone calls `execute_refund`. The bridge MPC-signs a Bitcoin transaction paying `"bc1q_attacker..."`.
8. Alice's BTC is sent to the attacker. [9](#0-8)
