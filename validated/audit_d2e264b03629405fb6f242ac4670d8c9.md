### Title
Cross-Era EBB Special-Case Bypass in `BasicEnvelopeValidation` for `HardForkBlock` - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/Combinator/Block.hs`)

---

### Summary

The `BasicEnvelopeValidation` instance for `HardForkBlock` falls back to `succ b` / `succ s` for cross-era block transitions, bypassing the EBB-specific special-case logic that is correctly implemented for single-era blocks. This is structurally identical to the reported Iron Bank bug: a special-case check for a specific type (WstETH / Byron EBB) is bypassed when that type is accessed through a wrapper (PToken / `HardForkBlock`).

---

### Finding Description

Byron EBBs have two well-known invariants that require special-case handling in envelope validation:

1. An EBB shares its **block number** with its predecessor (`IsNotEBB → IsEBB` transition: expected block number stays `b`, not `succ b`).
2. An EBB shares its **slot number** with its successor (`IsEBB → IsNotEBB` transition: minimum next slot is `s`, not `succ s`).

These special cases are correctly implemented in `BasicEnvelopeValidation ByronBlock`: [1](#0-0) 

However, the `BasicEnvelopeValidation (HardForkBlock xs)` instance in `Block.hs` only delegates to the per-era logic when the old tip and new block are **from the same era** (`Right matched`). When they are from **different eras** (`Left _mismatch`), it unconditionally falls back to `succ b` / `succ s`, bypassing the EBB special cases entirely: [2](#0-1) 

The code itself carries explicit `TODO` comments acknowledging this defect:

> "TODO: If the block is from a different era as the current tip, we just expect `succ b`. This may not be sufficient: if we ever transition /to/ an era with EBBs, this is not correct."

The `validateEnvelope` function in `HeaderValidation.hs` calls `expectedNextBlockNo` and `minimumNextSlotNo` directly to compute the expected values used in the `UnexpectedBlockNo` and `UnexpectedSlotNo` rejection checks: [3](#0-2) 

This is the same structural pattern as the Iron Bank bug: the special-case check (`if asset == wsteth` / `Right matched → per-era EBB logic`) is bypassed when the input is a wrapped type (`PToken` / `HardForkBlock` cross-era).

---

### Impact Explanation

If a cross-era transition involves an EBB at the boundary — specifically, if the last block of the departing era is an EBB, or if the first block of the arriving era is an EBB — `validateEnvelope` will compute wrong expected block/slot numbers. A valid header at the era boundary will be rejected with `UnexpectedBlockNo` or `UnexpectedSlotNo`, causing the node to be unable to advance its chain past the era transition. This breaks cross-era consensus and ledger invariants for any node running this code against such a chain.

---

### Likelihood Explanation

On Cardano mainnet, EBB production stopped before the Byron-to-Shelley transition, and the transition occurs at an epoch boundary, making it structurally impossible for the last Byron slot to be occupied solely by an EBB (as noted in `translateChainDepStateByronToShelley`): [4](#0-3) 

However, the defect is reachable on a private testnet or any chain where EBBs appear at era boundaries. The chain sync client validates headers received from unprivileged peers using this exact code path, so a peer presenting a valid cross-era EBB header would trigger the incorrect rejection.

---

### Recommendation

In `BasicEnvelopeValidation (HardForkBlock xs)`, the `Left _mismatch` branch of `expectedNextBlockNo` and `minimumNextSlotNo` should not unconditionally return `succ b` / `succ s`. Instead, it should inspect the `TipInfo` of the new block to determine whether it is an EBB and apply the correct EBB-aware logic, or at minimum delegate to the per-era `BasicEnvelopeValidation` instance for the new block's era. The existing `TODO` comments at lines 245 and 262 of `Block.hs` already identify this gap. [5](#0-4) 

---

### Proof of Concept

On a private testnet configured with Byron EBBs enabled, construct a chain where the last Byron block is an EBB (slot `s`, block number `b`). The first Shelley block legitimately has slot `s` (same as the EBB, per the EBB invariant). When a peer presents this Shelley header to a syncing node:

1. `validateEnvelope` calls `minimumNextSlotNo` on the `HardForkBlock` instance.
2. Old tip (`OneEraTipInfo`) is Byron EBB; new block (`OneEraTipInfo`) is Shelley — `Match.matchNS` returns `Left _mismatch`.
3. `minimumNextSlotNo` returns `succ s` instead of `s`.
4. `actualSlotNo = s < succ s = expectedSlotNo` → `throwError (UnexpectedSlotNo (succ s) s)`.
5. The valid Shelley header is rejected; the node cannot advance past the era boundary.
