### Title
HFC Era-Transition Stability Check Uses Unbounded Block Count Instead of Stability-Window-Bounded Count — (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/ShelleyHFC.hs`)

---

### Summary

The Hard Fork Combinator's era-transition stability logic — which decides whether to proceed with or suppress a signalled era transition — counts **all blocks after the voting deadline** to determine whether Chain Growth holds, rather than counting only those blocks that fall **within the subsequent stability window** (`3k/f` slots). This is the direct structural analog of the TWAV/OWAV bug: a criterion that is supposed to be time-bounded (slot-window-bounded) is instead observation-count-bounded (unbounded block count), making the check weaker than intended.

---

### Finding Description

The Ouroboros Genesis / HFC design (Iteration 4, the current implementation) is supposed to suppress an era transition if the stability window immediately after the voting deadline contains fewer than `k+1` blocks — i.e., if Praos Chain Growth is violated within that window. The rationale is that only `k+1` blocks within `3k/f` slots provides the rollback-safety guarantee that makes the transition irreversible.

The self-documented bug, recorded in the production codebase, is:

> *"TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window."* [1](#0-0) 

The intended check (Iteration 4):

> Silently ignore the on-chain governance if **the stability window** (`3k/f` slots) after the voting deadline contains fewer than `k+1` blocks. [2](#0-1) 

The actual check (buggy):

> Silently ignore the on-chain governance if there are fewer than `k+1` blocks **anywhere** after the voting deadline — with no upper slot bound.

This is implemented in `singleEraTransition` for Shelley-based eras: [3](#0-2) 

The correct design requires that the `k+1`-block threshold be evaluated only within the `3k/f`-slot window anchored at the voting deadline — exactly as the stability window is defined: [4](#0-3) 

The `singleEraTransition` contract requires the function to be monotonic and to report the transition only once it is stable (rollback-safe): [5](#0-4) 

The `reconstructSummaryLedger` function, which consumes `singleEraTransition` output to build the HFC summary used for all slot/time/era translations, is therefore also affected: [6](#0-5) 

---

### Impact Explanation

**Vulnerability class:** Hard-fork / era-transition mismatch breaking cross-era consensus.

The stability window (`3k/f` slots) is the time-bounded guarantee that `k+1` honest blocks exist after the voting deadline, making any rollback past that deadline impossible. By counting all blocks after the deadline with no slot-window bound, the implementation accepts a weaker condition: `k+1` blocks spread over an arbitrarily long period — even one that violates Chain Growth within the stability window.

Consequence: during a Chain Growth violation (e.g., a network partition that lasts longer than `3k/f` slots but still eventually produces `k+1` blocks), the HFC will **proceed with the era transition** when the correct behavior is to **suppress it**. Nodes that have accumulated `k+1` blocks after the deadline (spread over more than `3k/f` slots) will cross into the next era, while nodes on a shorter fork that have not yet accumulated `k+1` blocks will remain in the current era. This produces a **cross-era consensus split**: the two groups of nodes are now in different eras and cannot validate each other's blocks.

This directly satisfies the allowed impact category:

> *High. Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.*

---

### Likelihood Explanation

The bug manifests only when all three conditions hold simultaneously:

1. A Chain Growth violation occurs — the stability window (`3k/f` slots) after the voting deadline contains fewer than `k+1` blocks.
2. Despite the violation, `k+1` blocks are eventually produced after the deadline (spread over more than `3k/f` slots).
3. An era transition voting deadline falls within this low-density period.

On Cardano mainnet, Chain Growth violations are rare but not impossible (e.g., a prolonged network partition, a BGP routing incident, or a coordinated eclipse attack on a subset of block producers). The conditions do not require stake majority — a network-level partition affecting honest nodes suffices. The likelihood is therefore **low but non-negligible**, and the scenario is realistic on a private testnet or during a network incident.

---

### Recommendation

In `singleEraTransition` for Shelley-based eras (and in `reconstructSummaryLedger`), replace the unbounded block count after the voting deadline with a count restricted to blocks whose slots fall within `[votingDeadlineSlot, votingDeadlineSlot + stabilityWindow)`. Concretely:

- Compute `stabilityWindow = 3k/f` slots.
- Count only blocks `b` such that `slot(b) < votingDeadlineSlot + stabilityWindow`.
- Suppress the era transition if this bounded count is `< k+1`.

This mirrors the correct Iteration 4 design described in the documentation and aligns with how the stability window is used everywhere else in the codebase (e.g., `ledgerViewForecastAt` uses `addSlots swindow (succWithOrigin at)` as an exclusive upper bound): [7](#0-6)

### Proof of Concept

**Setup:** Cardano private testnet, `k = 2160`, `f = 0.05`, stability window `= 3k/f = 129600` slots. An era transition from Shelley to Allegra is voted on and confirmed at slot `S` (the voting deadline).

**Attack sequence:**

1. **Slot `S`** — voting deadline passes; on-chain governance signals transition to Allegra.
2. **Slots `S` to `S + 129600`** — a network partition isolates a subset of nodes. Only 500 blocks are produced in this window (< `k+1 = 2161`). Chain Growth is violated within the stability window.
3. **Slots `S + 129600` to `S + 600000`** — the partition resolves slowly. Over the next ~470,000 slots, the remaining `1661` blocks are produced, bringing the total to `k+1 = 2161` blocks after `S`.
4. **Buggy HFC check:** counts all `2161` blocks after `S` (no slot bound) → `2161 >= k+1` → **proceeds with Allegra transition**.
5. **Correct HFC check:** counts only blocks in `[S, S+129600)` → `500 < k+1` → **suppresses transition, stays in Shelley**.
6. **Result:** nodes that accumulated `2161` blocks after `S` enter Allegra; nodes on a shorter fork that have not yet accumulated `2161` blocks remain in Shelley. The two groups cannot validate each other's headers. Cross-era consensus split.
