### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold, Enabling Single-Vote Certificate Forging — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function, which is the sole gate for Peras certificate forging, compares an accumulated `PerasVoteStake` value directly against a relative (normalized) quorum threshold without performing any normalization. The code itself carries an explicit TODO acknowledging that the two operands may be in different units. If the `PerasVoteStakeDistr` supplied to `validatePerasVote` is populated with absolute ledger-stake values (the natural representation from the Cardano ledger), any single vote from any committee member with absolute stake exceeding the relative threshold value (e.g., > 0.75 lovelace) trivially passes the quorum check, allowing unauthorized certificate forging and adversarial chain boosting.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake      = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The code's own comment immediately above this function states:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`PerasVoteStake` is a bare `Rational` with no type-level unit tag: [3](#0-2) 

The quorum threshold in `PerasParams` is also a bare `Rational` intended to be a relative fraction (e.g., `0.75`): [4](#0-3) 

The `PerasVoteStake` attached to each validated vote is looked up from a `PerasVoteStakeDistr` that is supplied externally at validation time. In the production ObjectDiffusion pool writer, this distribution is obtained from an STM action `getStakeDistrSTM` and passed directly to `validatePerasVote mkPerasParams sd vote`: [5](#0-4) 

There is no normalization step between the stake lookup and the quorum comparison. The accumulated `PerasVoteStake` flows directly into `stakeAboveThreshold` via `votesReachQuorum`: [6](#0-5) 

and via `updateCandidateVoteState`: [7](#0-6) 

---

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute ledger-stake values (e.g., lovelace amounts or raw `Rational` fractions of total ADA supply, which is the natural output of the Cardano ledger), while `perasQuorumStakeThreshold` is set as a relative fraction (e.g., `3 % 4` = 75%), the comparison `stake >= 0.75` is satisfied by any voter whose absolute stake exceeds 0.75 — which is true for essentially every stake pool.

Concretely:
- A pool with 0.1% of total stake has absolute stake ≈ `450,000,000,000` lovelace.
- `450,000,000,000 >= 0.75` → `True`.
- A single vote from that pool triggers `votesReachQuorum → forgePerasCert`, producing a valid `ValidatedPerasCert` with a `PerasWeight` boost.
- The boosted block is preferred by chain selection on all honest nodes that accept the certificate.

This is a complete bypass of the Peras quorum requirement: the security property that a certificate requires a supermajority of committee stake is nullified. Any single committee member — including an adversary with minimal stake — can unilaterally boost any block they choose, causing honest nodes to prefer an adversarially-selected chain.

The same flaw is present in `updateLoserVoteState`, which uses `stakeAboveThreshold` to detect the `MultipleWinnersInRound` safety condition: [8](#0-7) 

With the mismatch, this guard also fires on every vote, causing the system to treat every round as having multiple winners and rejecting all votes — a secondary denial-of-certificate path.

---

### Likelihood Explanation

The entry path is fully reachable by an unprivileged peer. The ObjectDiffusion mini-protocol accepts inbound `PerasVote` messages from any connected peer, validates them via `processVotes`, and adds them to the `PerasVoteDB`. No special privilege, key compromise, or stake majority is required beyond being a registered committee member (or even just having a valid `PerasVoterId` in the stake distribution).

The mismatch is latent today because the test harness populates `PerasVoteStakeDistr` with small relative fractions (e.g., `1 % 2` to `1 % 10`). However, the production integration path — reading the stake distribution from the Cardano ledger — naturally produces absolute values. The TODO comment confirms the normalization step is missing and unresolved.

---

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes for absolute and relative stake (analogous to the `Stake Ledger` / `Stake Weight` phantom-typed approach already used in `Committee/WFA.hs` and the test model) so that `stakeAboveThreshold` can only accept a normalized `RelativePerasVoteStake`.

2. **Normalize before comparison.** Either normalize `PerasVoteStake` by the total committee stake before calling `stakeAboveThreshold`, or change `stakeAboveThreshold` to accept the total stake and perform normalization internally:

   ```haskell
   stakeAboveThreshold :: PerasParams -> TotalCommitteeStake -> PerasVoteStake -> Bool
   stakeAboveThreshold params (TotalCommitteeStake total) voteStake =
     (unPerasVoteStake voteStake / total) >= quorumThreshold + safetyMargin
   ```

3. **Add a property test** asserting that the sum of all committee members' vote weights equals 1 (or the total stake), and that quorum requires strictly more than one vote under any valid parameterization.

### Proof of Concept

Given the production call site in `makePerasVotePoolWriterFromChainDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

Populate `sd :: PerasVoteStakeDistr` with a single entry mapping `attackerVoterId` to `PerasVoteStake (1_000_000_000 % 1)` (1 billion lovelace = 1000 ADA, a plausible absolute stake). Set `mkPerasParams` with `perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 % 4)` (relative 75%).

Send a single `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = attackerVoterId }` from the attacker peer.

`stakeAboveThreshold` evaluates:
```
1_000_000_000 >= (3/4) + safetyMargin   -- True
```

`votesReachQuorum` returns `Just votesWithQuorum`, `forgePerasCert` is called, and a `ValidatedPerasCert` boosting `adversarialBlock` is produced and stored. All honest nodes that receive this certificate will apply the `PerasWeight` boost to `adversarialBlock` in chain selection, preferring it over the honest chain.
