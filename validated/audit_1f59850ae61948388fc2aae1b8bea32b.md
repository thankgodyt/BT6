Audit Report

## Title
Trusted-Relayer Guard on `claim_fee()` Permanently Locks Earned Fee Tokens After Relayer Removal - (`near/omni-bridge/src/lib.rs`)

## Summary
`claim_fee()` is gated by `#[trusted_relayer]`, which rejects any caller who is not currently a trusted relayer. If a relayer is removed from the trusted set (via `resign_trusted_relayer` or `reject_relayer_application`) after calling `sign_transfer()` but before calling `claim_fee()`, the fee tokens embedded in the pending transfer cannot be claimed by anyone: the removed relayer is blocked by the `#[trusted_relayer]` guard, and no substitute caller can pass the `fee_recipient == predecessor_account_id` check in `claim_fee_callback()` because the MPC-signed payload irrevocably names the removed relayer as fee recipient. The fee tokens remain locked in `pending_transfers` indefinitely with no permissionless recovery path.

## Finding Description

**Guard 1 — method-level `#[trusted_relayer]` on `claim_fee()`:**

```rust
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise {
    self.verify_proof(args.chain_kind, args.prover_args).then(
        Self::ext(env::current_account_id())
            .with_attached_deposit(env::attached_deposit())
            .with_static_gas(CLAIM_FEE_CALLBACK_GAS)
            .claim_fee_callback(&env::predecessor_account_id()),
    )
}
``` [1](#0-0) 

Any caller who is not currently a trusted relayer (or does not hold `Role::DAO` / `Role::UnrestrictedRelayer`) is rejected before the proof is even verified.

**Guard 2 — `fee_recipient == predecessor_account_id` in `claim_fee_callback()`:**

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
``` [2](#0-1) 

The `fee_recipient` is the value embedded in the MPC-signed `TransferMessagePayload` at `sign_transfer()` time and is cryptographically bound. The `predecessor_account_id` passed to the callback is the original caller of `claim_fee()`. [3](#0-2) 

**Why the bypass roles do not help:**

The impl-block-level macro exposes `bypass_roles(Role::DAO, Role::UnrestrictedRelayer)`, meaning the DAO or an `UnrestrictedRelayer` account can pass Guard 1. [4](#0-3) 

However, if the DAO calls `claim_fee()`, the `predecessor_account_id` forwarded to `claim_fee_callback()` is the DAO account, not the removed relayer. The `fee_recipient` in the proof is the removed relayer's account. Guard 2 therefore rejects the DAO's call as well. There is no way for any account other than the exact `fee_recipient` to satisfy both guards simultaneously.

**Why the transfer stays locked:**

`sign_transfer_callback()` only removes the transfer from `pending_transfers` when the fee is zero:

```rust
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
``` [5](#0-4) 

For any non-zero fee, the transfer message (and the fee tokens it accounts for) remains in `pending_transfers` until `claim_fee_callback()` calls `remove_transfer_message()`. If `claim_fee()` can never succeed, the transfer and its fee tokens are locked indefinitely.

**Relayer removal paths are confirmed in tests:**

`resign_trusted_relayer` (relayer-initiated) and `reject_relayer_application` (DAO-initiated) both immediately remove the relayer from the trusted set. [6](#0-5) [7](#0-6) 

## Impact Explanation

The fee portion of every pending transfer signed by the removed relayer becomes permanently frozen in the bridge contract. These are NEP-141 tokens originally deposited via `ft_transfer_call` and held in `pending_transfers`. No permissionless on-chain path exists to recover them; the only mitigation requires the DAO to grant `Role::UnrestrictedRelayer` back to the removed relayer, which is a privileged out-of-band action. This constitutes permanent freezing of bridged funds, matching the Critical impact scope.

## Likelihood Explanation

The scenario is operationally realistic on multiple paths:

1. **Voluntary resignation:** A relayer resigns (e.g., to exit the system) without first draining all pending fee claims. The window between `sign_transfer()` and `claim_fee()` spans at least one destination-chain finalization cycle, which can be hours or days.
2. **DAO revocation:** The DAO revokes a relayer for misconduct or operational reasons at any time, with no obligation to first allow pending fee claims to settle.

Relayers routinely sign many transfers in bulk before claiming fees, so multiple pending claims can be affected in a single removal event.

## Recommendation

Remove the `#[trusted_relayer]` attribute from `claim_fee()` specifically. The function is already protected by two independent security mechanisms that are sufficient on their own:

1. **Cryptographic proof verification** via `verify_proof()` — ensures the destination-chain finalization event is genuine.
2. **`fee_recipient == predecessor_account_id`** in `claim_fee_callback()` — ensures only the legitimate fee earner can collect.

The `#[trusted_relayer]` guard adds no security value to `claim_fee()` and exclusively creates the risk of locking legitimately earned fees.

## Proof of Concept

1. Relayer R becomes trusted (stake deposited, waiting period elapsed).
2. User initiates a transfer with a non-zero fee; the transfer is stored in `pending_transfers`.
3. R calls `sign_transfer(transfer_id, fee_recipient = R, fee)` — MPC signs a payload embedding R as `fee_recipient`. Because the fee is non-zero, the transfer remains in `pending_transfers` after `sign_transfer_callback()`.
4. The signed transaction is broadcast; the destination chain finalizes the transfer.
5. Before R calls `claim_fee()`, either:
   - R calls `resign_trusted_relayer()`, or
   - DAO calls `reject_relayer_application(R)`.
   R is now removed from the trusted set.
6. R calls `claim_fee(proof_args)` — the `#[trusted_relayer]` check fires and the call is rejected.
7. The DAO attempts `claim_fee(proof_args)` — passes Guard 1 (bypass role), but `claim_fee_callback()` receives `predecessor_account_id = DAO`, while `fee_recipient = R`. Guard 2 rejects the call.
8. The fee tokens remain locked in `pending_transfers` with no permissionless recovery path.

A sandbox integration test can reproduce this by: (a) setting up a trusted relayer, (b) initiating a transfer with a non-zero fee, (c) calling `sign_transfer`, (d) calling `resign_trusted_relayer`, and (e) asserting that a subsequent `claim_fee` call from the resigned relayer fails with the trusted-relayer error.
