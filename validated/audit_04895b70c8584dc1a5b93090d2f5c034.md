### Title
Stub `validatePerasCert` Combined with Round-Keyed First-Write-Wins Deduplication Allows Unprivileged Peer to Preempt Legitimate Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally accepts every inbound certificate without performing any cryptographic verification. The `PerasCertDB` deduplicates certificates solely by `PerasRoundNo` (first-write-wins). An unprivileged peer can therefore send a crafted certificate for any round, have it accepted and stored, and cause the legitimate certificate for that round to be permanently rejected as a duplicate. Because the stored certificate's boosted block drives Peras chain-selection weight, the attacker can make an honest node prefer a non-canonical chain.

---

### Finding Description

**Vulnerable component 1 — stub `validatePerasCert`**

The `BlockSupportsPeras` catch-all instance (used for all block types until a concrete instance is wired in) defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub performs zero checks: no aggregate BLS signature verification, no voter eligibility proof verification, no check that the boosted block exists or is on any known chain. Every certificate, regardless of content or origin, is returned as `Right` (validated).

**Vulnerable component 2 — first-write-wins deduplication in `implAddCert`**

`implAddCert` in `PerasCertDB/Impl.hs` deduplicates by `roundNo` only:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
    pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
``` [2](#0-1) 

The first certificate received for a given round is stored unconditionally; all subsequent certificates for the same round are silently dropped as `PerasCertAlreadyInDB`. There is no comparison of the boosted block, no signature check, and no equivocation detection at this layer.

**Vulnerable component 3 — production inbound path uses the stub**

Both production pool-writer constructors call `validatePerasCert mkPerasParams` directly:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [3](#0-2) 

`processCerts` filters out already-known round numbers, then calls `validateCert` on the remainder, and adds every `Right` result to the DB: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, every crafted certificate from any peer passes this gate.

**Analogy to the external report**

The external report's root cause: a game ID is computed without `msg.sender`, so an attacker can submit the same ID and overwrite the initiator field. Here, the certificate "ID" is `roundNo`, and the "sender identity" is the aggregate BLS signature over the committee members' keys — but that identity is never verified. The attacker can therefore submit any certificate for any round and have it stored as the canonical certificate for that round, exactly as the attacker in the external report overwrites the initiator.

---

### Impact Explanation

Once an attacker's crafted certificate for round R is stored in the `PerasCertDB`, the `getWeightSnapshot` function returns a `PerasWeightSnapshot` that assigns Peras boost weight to the attacker's chosen block: [5](#0-4) 

Chain selection in `chainSelSync` reads this snapshot and uses it to prefer chains containing the boosted block: [6](#0-5) 

The attacker can therefore cause an honest node to switch to a fork containing the attacker's chosen block, bypassing the Peras protocol's intended guarantee that only a block certified by a quorum of legitimate committee members receives a weight boost. The legitimate certificate for round R is permanently rejected as `PerasCertAlreadyInDB` and can never displace the attacker's certificate.

**Impact category**: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

- The attack requires only network access: any peer connected via the Peras certificate miniprotocol can send a crafted `PerasCert` message.
- No keys, stake, or privileged access are required.
- The attacker must send the crafted certificate before the legitimate one arrives, which is trivially achievable by sending it immediately upon connecting.
- The `PerasCertDB` comment in the state-machine test explicitly acknowledges the equivocation scenario but relies on the precondition that equivocating certificates are filtered out before reaching `addCert` — a precondition that is not enforced in the production path because `validatePerasCert` is a stub. [7](#0-6) 

---

### Recommendation

1. **Implement `validatePerasCert` for the concrete Cardano block type** before the Peras certificate miniprotocol is enabled on any network. The validation must verify the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregate public key of the claimed committee members, and verify each non-persistent voter's VRF eligibility proof. The existing `WFALS` committee verification logic in `Committee/WFALS.hs` provides the correct template.

2. **Add equivocation detection in `implAddCert`**: if a certificate for `roundNo` already exists and the new certificate's `boostedBlock` differs, the new certificate should be treated as an equivocation and rejected (or flagged), not silently dropped as a duplicate. The current `PerasCertAlreadyInDB` result conflates "duplicate" with "equivocation".

3. **Track the issue**: the existing GitHub issue `https://github.com/tweag/cardano-peras/issues/120` covers the missing validation; it should be treated as a security-critical blocker before any production deployment.

---

### Proof of Concept

```
1. Attacker connects to an honest node via the Peras certificate miniprotocol.

2. Attacker constructs a PerasCert for round R = 42 with boostedBlock = <attacker-chosen block hash>.
   No valid BLS signature is required because validatePerasCert is a stub.

3. Attacker sends the crafted certificate to the honest node.

4. processCerts (PerasCert.hs:164) checks: is round 42 already in the DB? No.
   validatePerasCert mkPerasParams cert → Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = ... })
   addCert is called → implAddCert stores the certificate, pcdsCertIds now contains 42.

5. The legitimate certificate for round 42 (signed by the actual committee) arrives later.
   processCerts checks: is round 42 already in the DB? Yes.
   The legitimate certificate is filtered out and never reaches implAddCert.

6. getWeightSnapshot returns a snapshot boosting the attacker's chosen block.

7. chainSelSync uses this snapshot to trigger chain selection for the attacker's block,
   potentially causing the honest node to switch to the attacker's fork.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
