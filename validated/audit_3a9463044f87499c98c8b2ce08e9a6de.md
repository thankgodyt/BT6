Audit Report

## Title
Race Condition in `fast_fin_transfer_to_near_callback` Enables Double-Spending of Bridged Tokens - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`fast_fin_transfer` checks `is_unified_transfer_finalised` synchronously before dispatching a cross-contract call, but the fast-transfer record is only written inside the asynchronous callback `fast_fin_transfer_to_near_callback`. If `fin_transfer` is processed during the cross-contract call window, it finds no fast-transfer record, sends tokens to the original recipient, and marks the transfer finalized. When the callback subsequently executes, it has no guard against this already-finalized state and sends tokens to the recipient a second time, constituting a double-spend.

## Finding Description

**Step 1 — `fast_fin_transfer` (lines 778–826):**
`is_unified_transfer_finalised` is checked at line 778 against `finalised_transfers`. If the transfer is not yet finalized, `check_or_pay_ft_storage` is dispatched as a cross-contract call spanning at least one block. Critically, no fast-transfer record is written to `fast_transfers` at this point.

**Step 2 — Race window:**
While the cross-contract call is in flight, `fin_transfer` can be submitted. `process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, inserting the transfer ID into `finalised_transfers`. It then calls `get_fast_transfer_status` at line 1879, which queries `fast_transfers` and returns `None` because `add_fast_transfer` has not yet executed. The `None` branch at lines 1897–1901 sends tokens to the original recipient and sets `fee_recipient` to the regular relayer.

**Step 3 — `fast_fin_transfer_to_near_callback` (lines 839–893):**
The callback contains no call to `is_unified_transfer_finalised` and no check against `finalised_transfers`. It unconditionally calls `add_fast_transfer` at line 855 (which inserts into `fast_transfers` — a separate map from `finalised_transfers` — and succeeds because `fin_transfer`'s `None` branch never called `remove_fast_transfer`), then calls `send_tokens` at line 877, delivering tokens to the recipient a second time.

**Why existing guards fail:**
- The `is_unified_transfer_finalised` guard in `fast_fin_transfer` (line 778) only prevents a *new* `fast_fin_transfer` invocation after finalization; it does not protect the already-scheduled callback.
- `add_fin_transfer` (line 2226) inserts into `finalised_transfers` and panics on duplicate, preventing a second `fin_transfer` call — but this does not stop the in-flight callback.
- `add_fast_transfer` (line 2253) panics only if a record already exists in `fast_transfers`. Since `fin_transfer` took the `None` branch and never touched `fast_transfers`, the insert succeeds and execution continues to `send_tokens`.

## Impact Explanation

This is a concrete double-spend of bridged tokens. The recipient receives `amount_without_fee` tokens from `process_fin_transfer_to_near` and again from `fast_fin_transfer_to_near_callback`. For minted (bridged) tokens this inflates total supply beyond what is locked on the origin chain; for locked native tokens the bridge loses reserves. The fast relayer's pre-paid funds are unrecoverable because `fin_transfer` directed reimbursement to the regular relayer. This matches the Critical impact category: stealing/double-spending/unauthorized minting of bridged funds.

## Likelihood Explanation

NEAR's async execution model guarantees that any cross-contract call spans at least one block, making the race window structurally unavoidable. A regular relayer submitting `fin_transfer` concurrently with an in-flight `fast_fin_transfer` is a normal operational scenario requiring no malicious intent. Both relayers act correctly per protocol. The window is predictable and repeatable for any NEAR-bound transfer that uses the fast-transfer path.

## Recommendation

Add a finalization guard at the start of `fast_fin_transfer_to_near_callback` that aborts and refunds the fast relayer if `fin_transfer` has already finalized the transfer:

```rust
pub fn fast_fin_transfer_to_near_callback(
    &mut self,
    fast_transfer: &FastTransfer,
    storage_payer: AccountId,
    relayer_id: AccountId,
) -> Promise {
    // Guard: abort if fin_transfer already finalized this transfer
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // refund storage_payer and return tokens to relayer
        env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
    }
    // ... existing logic
}
```

Alternatively, write the fast-transfer record synchronously inside `fast_fin_transfer` (before the cross-contract call) so that `process_fin_transfer_to_near` can detect it via `get_fast_transfer_status` and redirect tokens to the relayer rather than the recipient.

## Proof of Concept

1. Alice initiates a transfer of 1000 USDC from Ethereum to `alice.near`.
2. **Block N:** Trusted fast relayer calls `ft_on_transfer` → `fast_fin_transfer` → `is_unified_transfer_finalised` returns `false` → `check_or_pay_ft_storage` dispatched. No entry in `fast_transfers`.
3. **Block N+1:** Regular relayer calls `fin_transfer` with the Ethereum proof → `process_fin_transfer_to_near` → `add_fin_transfer` inserts into `finalised_transfers` → `get_fast_transfer_status` returns `None` → 1000 USDC sent to `alice.near`.
4. **Block N+2:** `fast_fin_transfer_to_near_callback` executes → `add_fast_transfer` inserts into `fast_transfers` (succeeds, no prior entry) → `send_tokens` sends 1000 USDC to `alice.near` **again**.

Result: `alice.near` holds 2000 USDC. The fast relayer's 1000 USDC pre-payment is unrecoverable. The bridge's token supply is inflated by 1000 USDC.

A local integration test can reproduce this by: (a) calling `fast_fin_transfer` on a mock token contract that delays the storage-check callback by one block, (b) calling `fin_transfer` in that block, and (c) asserting the recipient's balance after both callbacks resolve equals `2 × amount_without_fee`.
