### Title
Tokens Permanently Stuck in Bridge When Recipient Account Is Unregistered in `safe_mint` - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nbtc token contract mints tokens to `bridge_id` before checking whether the recipient account is registered. When the recipient is not registered, the function returns early with `U128(0)` without transferring the already-minted tokens, leaving them permanently stuck in the bridge's own token balance with no recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // (1) tokens minted to bridge_id

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // (2) early return — no transfer
    }
    // (3) transfer only reached when account IS registered
    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

Step (1) calls `internal_deposit`, which permanently credits `amount` nBTC to `bridge_id`'s balance. Step (2) then returns successfully (no panic, so no state rollback) when the recipient account has no storage registration. The tokens are now in `bridge_id`'s balance with no on-chain mechanism to route them to the intended recipient.

There is a secondary interaction that reinforces the stuck path: `safe_mint` is not marked `#[payable]`, so it is called with zero attached deposit. If the account IS registered, the subsequent call to `self.ft_transfer` internally invokes `assert_one_yocto()` (via the standard NEP-141 implementation), which panics because `env::attached_deposit() == 0`. That panic rolls back all state, so no tokens are lost in the registered-account path. The only execution path that commits state and returns successfully is the unregistered-account path — which is precisely the path that leaves tokens stuck.

### Impact Explanation
A user whose NEAR account is not registered in the nbtc contract sends BTC to the bridge. The bridge calls `safe_mint` on their behalf. The function mints `amount` nBTC to `bridge_id` and returns `U128(0)` without delivering anything to the user. The user's BTC remains locked on the Bitcoin side; the corresponding nBTC is credited to the bridge's own token balance and is inaccessible to the user. Recovery requires privileged operator intervention (e.g., a manual `burn` or `ft_transfer` from the bridge account). This matches the allowed Medium impact: *"Harmful smart-contract behavior without direct funds theft, including … stuck bridge state requiring operator intervention."*

### Likelihood Explanation
Any user who initiates a BTC deposit without first calling `storage_deposit` on the nbtc contract to register their NEAR account will trigger this path. New or infrequent users are the most likely victims. No special attacker capability is required — the user simply omits the storage registration step, which is a common mistake in NEP-141 ecosystems.

### Recommendation
Reorder the check and the mint: verify that `account_id` is registered **before** calling `internal_deposit`. If the account is not registered, either register it automatically (mirroring what `mint_inner` does) or panic/return without minting:

```rust
// Check registration BEFORE minting
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

Alternatively, align `safe_mint` with `mint_inner`, which already calls `internal_register_account` when the account is absent, eliminating the stuck-token scenario entirely.

### Proof of Concept
1. User `alice.near` sends BTC to the bridge deposit address.
2. `alice.near` has never called `storage_deposit` on the nbtc contract, so `token.accounts.get(&"alice.near")` returns `None`.
3. The bridge calls `nbtc.safe_mint(alice.near, 100_000, None)`.
4. `internal_deposit(&bridge_id, 100_000)` executes — 100,000 nBTC are credited to `bridge_id`. State is committed.
5. `token.accounts.get(&alice.near).is_none()` is `true` → function returns `U128(0)`.
6. Alice receives 0 nBTC. Her BTC is locked. The 100,000 nBTC sit in `bridge_id`'s balance with no automated recovery path. [1](#0-0) [2](#0-1) [3](#0-2)
