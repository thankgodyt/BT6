Audit Report

## Title
ERC-1155 `safeTransferFrom` in `finTransfer` Permanently Freezes Bridged Funds When Recipient Is a Non-Receiver Contract - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.sol::finTransfer` uses `IERC1155.safeTransferFrom` to deliver ERC-1155 tokens to the recipient. If the recipient is a contract that does not implement `IERC1155Receiver.onERC1155Received()`, the call reverts, rolling back the `completedTransfers[payload.destinationNonce] = true` state assignment that precedes it. Because the nonce is never permanently consumed, every subsequent relay attempt for that transfer also reverts, while the user's tokens remain locked in the NEAR bridge contract with no on-chain recovery path.

## Finding Description

In `finTransfer`, the destination nonce is marked used at line 287 **before** the token delivery branch executes:

```solidity
completedTransfers[payload.destinationNonce] = true;  // line 287
```

For ERC-1155 tokens, delivery is performed at lines 324–330:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per EIP-1155, `safeTransferFrom` must call `onERC1155Received` on any contract recipient and revert if the return value is not `bytes4(keccak256("onERC1155Received(address,address,uint256,uint256,bytes)"))`. Contracts that do not implement `IERC1155Receiver` — including Gnosis Safe multisigs, governance contracts, yield aggregators, and any contract predating ERC-1155 — will cause this revert.

Because Solidity reverts unwind all state changes in the transaction, the `completedTransfers[payload.destinationNonce] = true` assignment at line 287 is also rolled back. The nonce is therefore never permanently consumed. Every subsequent relay attempt for this transfer will reach the same `safeTransferFrom` call and revert identically.

On the NEAR side, tokens are locked or burned during `init_transfer` / `ft_on_transfer`. There is no NEAR-side callback or escape hatch triggered by a permanent EVM finalization failure — the NEAR contract's refund logic (`is_refund_required`, `fin_transfer_send_tokens_callback`) only fires in response to NEAR-internal promise failures, not EVM-side reverts. The locked tokens have no recovery path.

## Impact Explanation

**Critical — Permanent freezing of bridged funds.** The user's ERC-1155 tokens on NEAR are locked inside the bridge contract. The EVM finalization can never succeed for a non-receiver contract recipient. There is no NEAR-side escape hatch that fires when EVM finalization permanently fails. This matches the allowed Critical impact: *permanent freezing of bridged funds across NEAR/EVM flows*.

## Likelihood Explanation

**High.** Any bridge user can supply an arbitrary `recipient` address in the cross-chain message — no special privilege is required. Many common contract types (Gnosis Safe multisigs, DAO governance contracts, DeFi vaults, any contract deployed before ERC-1155 became widespread) do not implement `IERC1155Receiver`. A user who specifies such a contract as the recipient — intentionally (e.g., bridging to a team multisig) or by mistake — will trigger this condition. The condition is deterministic and repeatable for the same nonce.

## Recommendation

Replace `safeTransferFrom` with a pattern that does not revert on non-receiver contracts. Since ERC-1155 does not define a non-safe `transferFrom`, the correct approaches are:

1. **Wrap in try/catch and implement a pull-based withdrawal pattern**: on delivery failure, record the owed amount in a claimable mapping so the recipient can withdraw later, preserving the nonce consumption.
2. **Use a low-level call bypassing the receiver check**: call the ERC-1155 `transferFrom` logic directly if the token contract exposes it, or use assembly to skip the `onERC1155Received` callback.

The nonce must remain consumed (`completedTransfers[payload.destinationNonce] = true`) regardless of delivery outcome to prevent replay. Delivery failure should be handled gracefully without reverting the entire transaction.

## Proof of Concept

1. Register an ERC-1155 token via `logMetadata1155` on the deployed `OmniBridge`, populating `multiTokens[deterministicToken]`.
2. On NEAR, call `init_transfer` / `ft_on_transfer` with `recipient` set to a contract address that does **not** implement `IERC1155Receiver` (e.g., a plain Gnosis Safe or any EOA-less contract). Tokens are locked in the NEAR bridge.
3. A relayer submits the signed payload and calls `finTransfer` on EVM.
4. Execution sets `completedTransfers[nonce] = true` at line 287, then reaches line 324; `safeTransferFrom` calls `onERC1155Received` on the Safe, which returns nothing or reverts.
5. The entire `finTransfer` transaction reverts. `completedTransfers[nonce]` is rolled back to `false`.
6. Every subsequent relay attempt for this nonce also reverts at step 4.
7. The user's tokens remain locked in the NEAR bridge contract with no recovery path.
