### Title
Frontrunning `update_config` Fee Increase Allows Users to Bypass Withdrawal Fee Policy - (File: `contracts/satoshi-bridge/src/api/management.rs`)

### Summary
The `update_config` function applies fee changes immediately with no timelock. Because the withdrawal fee is computed and locked into `BTCPendingInfo` at the moment a user initiates a withdrawal via `ft_transfer_call`, any user who observes a pending DAO fee-increase transaction can frontrun it—initiating their withdrawal first and permanently locking in the old, lower fee rate.

### Finding Description
`update_config` is restricted to the `DAO` role and applies the new `withdraw_bridge_fee` atomically and immediately: [1](#0-0) 

The `ConfigUpdate::apply` macro unconditionally overwrites `config.withdraw_bridge_fee` with the new value the moment the transaction lands: [2](#0-1) 

There is no announcement period, no timelock, and no delay between the DAO submitting the update and it taking effect.

On the withdrawal side, when a user calls `ft_transfer_call` the bridge creates a `BTCPendingInfo` record that stores the computed `withdraw_fee` (and `burn_amount`) at that instant. Later, during burn finalization, `verify_withdraw_burn_promise` reads the **stored** `btc_pending_info.withdraw_fee`—not the current config—to determine the total fee: [3](#0-2) 

Because the fee is frozen in `BTCPendingInfo` at initiation time, any withdrawal initiated before `update_config` executes will be finalized at the old, lower fee rate regardless of what the config says at burn time.

The fee calculation itself uses `BridgeFee::get_fee`: [4](#0-3) 

A user who initiates a withdrawal one block before a `fee_rate` increase from, say, 10 bps to 100 bps on a 1 BTC withdrawal saves ~0.009 BTC in fees.

### Impact Explanation
This is a **bypass of bridge fee policy**. The DAO's intent to collect a higher fee is circumvented by any user who times their `ft_transfer_call` to land before the `update_config` transaction. The protocol collects less revenue than intended. No funds are stolen, but the bridge's fee enforcement is rendered ineffective for any withdrawal initiated in the window before the config update lands.

### Likelihood Explanation
**Low.** NEAR Protocol does not have a public mempool with gas-price ordering, so classical frontrunning is harder than on EVM chains. However, DAO governance actions on NEAR are often announced off-chain (Discord, governance forums) before being submitted on-chain, giving sophisticated users ample time to act. Additionally, NEAR's transaction ordering within a block is deterministic and observable, so a user who monitors the chain can still race a config update in the same block.

### Recommendation
Introduce a two-phase fee update: the DAO first announces the new fee (stored as `pending_fee`), and a mandatory delay (e.g., 24–48 hours) must elapse before `apply_pending_fee` makes it active. Alternatively, apply the new fee only to withdrawals initiated **after** the block in which `update_config` was called, by recording the effective block height alongside each `BTCPendingInfo` entry and resolving the applicable fee at burn time based on that height.

### Proof of Concept
1. DAO submits `update_config` with `withdraw_bridge_fee: { fee_rate: 500, ... }` (up from 50).
2. User observes the pending governance transaction (off-chain announcement or on-chain mempool monitoring).
3. User calls `ft_transfer_call` on the nBTC contract, transferring nBTC to the bridge, **before** the `update_config` transaction is included.
4. The bridge's `ft_on_transfer` handler computes `withdraw_fee` using the current `fee_rate = 50` and stores it in `BTCPendingInfo`.
5. `update_config` lands in the next block; `fee_rate` is now 500.
6. The withdrawal proceeds through MPC signing and BTC broadcast normally.
7. When a relayer calls `verify_withdraw`, `verify_withdraw_burn_promise` reads `btc_pending_info.withdraw_fee` (computed at step 4 with `fee_rate = 50`) and burns that amount—10× less than the protocol now intends. [1](#0-0) [5](#0-4) [4](#0-3)
