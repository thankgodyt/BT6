### Title
Wrong Amount Used for Confirmation-Count Calculation in Refund Finalization - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

`internal_verify_refund_finalize` calculates the required number of Bitcoin confirmations using `btc_pending_info.actual_received_amount` (the refund amount after gas-fee deduction) instead of the original deposit amount. This is a direct analog to the MOMP bug: a partial/reduced value is substituted for the correct global value in a security-critical threshold calculation, allowing the refund to be finalized with fewer confirmations than the bridge's policy requires for the original deposit size.

### Finding Description

The bridge's confirmation strategy (`confirmations_strategy` in `Config`) maps deposit-amount upper bounds to required confirmation counts. A larger deposit requires more confirmations to guard against chain reorganizations.

When a refund is executed, `finalize_refund_with_psbt` stores the refund economics in a `BTCPendingInfo` record:

```rust
// refund.rs lines 347-349
actual_received_amount: refund_amount,   // = deposit_amount - gas_fee
``` [1](#0-0) 

`refund_amount` is computed as:

```rust
// refund.rs lines 280-283
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
``` [2](#0-1) 

Later, `internal_verify_refund_finalize` passes `actual_received_amount` — the already-reduced refund amount — to `get_confirmations`:

```rust
// refund.rs line 441
let confirmations = self.get_confirmations(config, btc_pending_info.actual_received_amount);
``` [3](#0-2) 

The correct value to pass is the **original deposit amount** (`refund_request.amount`), which is what the confirmation policy was designed to protect. The `get_confirmations` function in `Config` selects a confirmation tier based on the amount:

```rust
// config.rs lines 208-210
for key in &keys {
    if *key > satoshi_amount {
        return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
    }
}
``` [4](#0-3) 

If the deposit sits just above a tier boundary and the gas fee is large enough to push `actual_received_amount` below that boundary, the refund is finalized with the lower tier's confirmation count.

### Impact Explanation

The bridge's confirmation policy exists to make chain-reorganization attacks economically infeasible for large deposits. By using the post-fee refund amount instead of the original deposit amount, the policy is silently bypassed: a deposit that required N confirmations can have its refund finalized with fewer than N confirmations. This constitutes a bypass of bridge confirmation limits/policies.

### Likelihood Explanation

The default gas fee is `config.max_btc_gas_fee` (applied when no custom fee is provided). If a deposit amount is within `max_btc_gas_fee` satoshis above a confirmation-tier boundary, the condition is met automatically without any attacker action beyond making a deposit of that size and requesting a refund. The `verify_refund_finalize` entry point is callable by any account (it is a `#[trusted_relayer]` function open to the public with a confirmations delta for non-whitelisted callers). [5](#0-4) 

### Recommendation

Replace `btc_pending_info.actual_received_amount` with the original deposit amount when computing confirmations in `internal_verify_refund_finalize`. The original deposit amount is stored in `RefundRequest.amount` and should either be preserved in `BTCPendingInfo` (e.g., as a dedicated field) or re-read from the refund request at verification time.

### Proof of Concept

1. Operator configures `confirmations_strategy = {"5000000": 3, "10000000": 6}` and `max_btc_gas_fee = 100000` satoshis.
2. User deposits `10_000_001` satoshis (just above the 10 M boundary → 6 confirmations required).
3. User calls `request_refund`; default gas fee = `100_000` satoshis is applied.
4. `execute_refund` runs; `actual_received_amount = 10_000_001 - 100_000 = 9_900_001` satoshis (below 10 M boundary).
5. `BTCPendingInfo.actual_received_amount` is stored as `9_900_001`.
6. Anyone calls `verify_refund_finalize` with a proof of only **3** confirmations.
7. `get_confirmations(config, 9_900_001)` returns **3** (below the 10 M tier), so the check passes.
8. The refund is finalized with 3 confirmations instead of the 6 that the bridge policy requires for a 10 M+ satoshi deposit — a bypass of the bridge's reorganization-resistance policy. [6](#0-5)
