### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Certificate - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or semantic validation. This stub is wired directly into the live inbound certificate processing pipeline, allowing any unprivileged peer to inject arbitrary Peras certificates that are accepted and used to influence chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gating check before a peer-supplied certificate is stored and applied to chain selection. The sole production instance — the overlapping `instance StandardHash blk => BlockSupportsPeras blk` — implements this check as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired into both production inbound certificate writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

The `processCerts` function — the production inbound handler for peer-received certificates — calls this validation function for every certificate in a batch. Because it always returns `Right`, every certificate passes, is timestamped, stored in `PerasCertDB`, and forwarded to chain selection via `addPerasCertAsync`: [4](#0-3) 

The accepted certificate then triggers chain selection: [5](#0-4) 

**Analog to the external report**: In the MagicSea bug, the authorization check (`ownerOf`) is placed inside `_modify()`, which is called by the voter contract — so `msg.sender` is the voter contract, not the NFT owner, causing the check to always fail for valid votes. Here, the validation check (`validatePerasCert`) is a stub that always succeeds for any certificate, including adversarially crafted ones. Both are "check placed in the wrong context" bugs: one blocks valid operations, the other accepts invalid ones.

The `validatePerasVote` function has a related but less severe issue — it only checks stake distribution membership and does not verify the cryptographic signature of the vote:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [6](#0-5) 

This allows a peer to forge votes from any eligible voter ID in the stake distribution without possessing the corresponding BLS signing key.

---

### Impact Explanation

A crafted `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` (pointing to any block, including one on a minority fork) will pass `validatePerasCert`, be stored, and trigger chain selection. Chain selection applies a boost of `perasWeight = PerasWeight 15` to the boosted block: [7](#0-6) 

This boost is added to the total weight of any chain containing the boosted block: [8](#0-7) 

An adversary can:
1. Boost any block (including one on a minority fork) to make it appear heavier than the canonical chain.
2. Cause honest nodes to switch to a non-canonical chain, breaking chain selection safety.
3. Cause divergence between nodes that receive the crafted certificate and those that do not.

This is a **Critical** bypass of Peras certificate/vote verification that enables unauthorized certificate acceptance and chain selection manipulation.

---

### Likelihood Explanation

The entry path is direct and requires no special privileges. Any peer connected via the object diffusion mini-protocol can send a `PerasCert` message. The `processCerts` function is the production inbound handler and is unconditionally reachable from the network layer. No stake, keys, or operator access are required.

---

### Recommendation

Implement actual cryptographic and semantic validation in `validatePerasCert` before the Peras certificate diffusion pipeline is active in production. Specifically:

1. Verify the certificate's aggregate BLS signature against the claimed voters' public keys from the stake distribution.
2. Verify that the boosted block exists and is within the valid round range (`perasCertMaxRounds`).
3. Verify that the certificate's round number is within the valid range relative to the current tip.
4. Verify that the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`) is met by the claimed voters' combined stake.

The existing `implVerifyCert` implementations in `EveryoneVotes.hs` and `WFALS.hs` demonstrate the correct pattern for performing these checks. [9](#0-8) 

---

### Proof of Concept

A peer sends a single-element batch containing:

```haskell
PerasCert
  { pcCertRound      = PerasRoundNo 999999   -- arbitrary round, no bounds check
  , pcCertBoostedBlock = blockPoint minorityForkBlock  -- any block point
  }
```

**Step 1**: The peer's object diffusion handler calls `makePerasCertPoolWriterFromChainDB`, which calls `processCerts` with `validatePerasCert mkPerasParams` as the validator.

**Step 2**: `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally. [10](#0-9) 

**Step 3**: `processCerts` stores the certificate and calls `addPerasCertAsync chainDB`. [4](#0-3) 

**Step 4**: Chain selection applies a boost of 15 to `minorityForkBlock`. If the minority fork's total weight (block count + 15) exceeds the canonical chain's weight, the node switches to the minority fork.
