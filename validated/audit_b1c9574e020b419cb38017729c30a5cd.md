### Title
Vacuous Array Match in `is_structure_equal` Allows Empty-Array Msg to Bypass Template Restriction — (`contracts/satoshi-bridge/src/json_utils.rs`)

### Summary
`is_structure_equal` returns `true` when the template array is non-empty but the input array is empty, because the element-validation loop is vacuously skipped. An unprivileged depositor can exploit this to pass a `post_action.msg` containing empty arrays where the DAO-registered template requires non-empty structured arrays, bypassing the msg-template whitelist policy.

### Finding Description
In the `Array` branch of `is_structure_equal`:

```rust
// json_utils.rs lines 32–48
(Value::Array(t_arr), Value::Array(i_arr)) => {
    if t_arr.is_empty() {
        return i_arr.is_empty();   // only guards empty-template case
    }
    for i_item in i_arr {          // if i_arr == [], loop body never runs
        ...
        if !matched { return false; }
    }
    true                           // reached even when i_arr is empty
}
``` [1](#0-0) 

The guard on line 33 only handles the case where the **template** array is empty. When the template array is non-empty and the **input** array is empty, the for-loop over `i_arr` executes zero iterations and the function returns `true`.

`check_deposit_msg` uses this function to validate `post_action.msg` against DAO-registered templates:

```rust
// deposit_msg.rs lines 122–135
let is_match = match serde_json::from_str::<Value>(&post_action.msg) {
    Ok(msg_value) => msg_templates.iter().any(|template| {
        match serde_json::from_str::<Value>(template) {
            Ok(template_value) => is_structure_equal(&template_value, &msg_value),
            Err(_) => false,
        }
    }),
    ...
};
``` [2](#0-1) 

If `is_match` is `true`, the `post_action` is forwarded to the whitelisted receiver via `ft_transfer_call` with the attacker-supplied msg. [3](#0-2) 

### Impact Explanation
The DAO-registered msg templates are the sole content-level restriction on what messages can be sent to whitelisted receivers. Bypassing this allows an attacker to send structurally invalid messages (e.g., `{"actions":[]}` instead of `{"actions":[{"type":"..."}]}`) to a whitelisted DeFi receiver. The receiver processes an empty actions list, which may cause it to accept the `ft_transfer_call` without performing the intended action (leaving the attacker's nBTC stranded in the receiver), or to behave in an unintended way that affects protocol state. This is a bypass of a DAO-enforced bridge policy.

### Likelihood Explanation
Any depositor can trigger this by embedding a `post_action` with a msg containing an empty array in place of any array field required by the template. No privileged access is needed beyond having a whitelisted receiver with a JSON-structured template registered. The path is fully reachable through the public `verify_deposit` entry point. [4](#0-3) 

### Recommendation
Add an explicit check in the `Array` branch to reject an empty input array when the template array is non-empty:

```rust
(Value::Array(t_arr), Value::Array(i_arr)) => {
    if t_arr.is_empty() {
        return i_arr.is_empty();
    }
    if i_arr.is_empty() {   // ADD: non-empty template must not match empty input
        return false;
    }
    for i_item in i_arr { ... }
    true
}
``` [1](#0-0)
