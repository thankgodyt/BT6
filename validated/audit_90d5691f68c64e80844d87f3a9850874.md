### Title
Unprivileged Caller Can Grief `None`-Address Refunds by Hijacking `BTCPendingInfo` Ownership — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

`execute_refund` is a public, unpermissioned function. When `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` to **all callers** with no privileged bypass. Once that timelock elapses, any account can call `execute_refund` and become the `account_id` owner of the resulting `BTCPendingInfo`. On Bitcoin, the refund txid is fully deterministic (same inputs/outputs → same txid), so the original depositor cannot re-execute to reclaim ownership. Because `sign_btc_transaction_callback` enforces that the pending tx must be in the signing account's `btc_pending_sign_ids`, the original user cannot sign the attacker-owned pending tx. The refund is stuck until an operator rejects the refund request and removes the stale pending tx — a process that forces Alice to restart from scratch and that the attacker can repeat indefinitely.

---

### Finding Description

**Step 1 — Timelock resolution is open to all callers for `None`-address refunds.** [1](#0-0) 

When `deposit_msg().refund_address.is_none()`, the function unconditionally returns `config.unsafe_refund_timelock_sec` regardless of the caller's role. There is no privileged fast-track, but more importantly there is also **no restriction** preventing an arbitrary account from calling `execute_refund` once that timelock has elapsed.

**Step 2 — The caller becomes the `account_id` owner of the `BTCPendingInfo`.** [2](#0-1) 

`caller = env::predecessor_account_id()` is captured and forwarded to `finalize_refund_with_psbt`. [3](#0-2) 

`BTCPendingInfo { account_id: caller.clone(), ... }` is stored, and the pending tx id is inserted into `caller.btc_pending_sign_ids`. The original depositor has no role in this.

**Step 3 — On Bitcoin the txid is deterministic; re-execution is blocked.** [4](#0-3) 

A second call with the same UTXO inputs/outputs produces the identical txid and panics with `"pending info already exist"`. Alice cannot create a new `BTCPendingInfo` with herself as owner.

**Step 4 — `sign_btc_transaction_callback` enforces account ownership.** [5](#0-4) 

The callback removes the pending tx from `account_id.btc_pending_sign_ids`. If Alice calls `sign_btc_transaction`, `account_id` resolves to Alice, but the pending tx lives in the **attacker's** `btc_pending_sign_ids`. The `require!` fires with `"Internal error"`, wasting Alice's gas and leaving the pending tx unsigned.

**Step 5 — Operator recovery path is destructive.** [6](#0-5) 

`remove_refund_pending_tx_id` (trusted-relayer only) requires the refund request to be **absent**. The operator must first reject the refund request (destroying it), then remove the stale pending tx. Alice must then submit a brand-new `request_refund` and wait for `unsafe_refund_timelock_sec` again — at which point the attacker can repeat the attack.

---

### Impact Explanation

Alice's BTC is locked in the bridge UTXO. The refund cannot proceed without operator intervention. Each intervention cycle destroys the refund request, forcing Alice to restart. The attacker can loop this indefinitely at the cost of a storage deposit per call, with no financial gain but permanent disruption of Alice's refund. This matches **Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention**.

---

### Likelihood Explanation

- The attack requires only a funded NEAR account and knowledge of the `utxo_storage_key` (derivable from public on-chain events).
- The attacker must race Alice after `unsafe_refund_timelock_sec` elapses, which is straightforward to monitor.
- The attacker needs no existing pending sign txs (default limit = 1), a trivially satisfiable precondition.
- The attack is repeatable at low cost.

**Note on Zcash:** The question's Zcash framing is incorrect. On Zcash the txid encodes `last_block_height`, so Alice **can** call `execute_refund` again at a later block to create a new `BTCPendingInfo` with herself as owner. The griefing is effective only on **Bitcoin**, where the txid is fully deterministic.

---

### Recommendation

1. **Restrict `execute_refund` to the original depositor** for `None`-address refunds, or record the depositor's `account_id` in `RefundRequest` and enforce it in `finalize_refund_with_psbt`.
2. Alternatively, **use the depositor's `account_id`** (from `refund_request`) rather than `env::predecessor_account_id()` when constructing `BTCPendingInfo`, so ownership always belongs to the depositor regardless of who triggers execution.
3. Allow `remove_refund_pending_tx_id` to operate while the refund request is still active (with appropriate guards), so operators can clear stale attacker-owned pending txs without destroying the refund request.

---

### Proof of Concept

```
1. Alice deposits BTC with deposit_msg { refund_address: None, recipient_id: alice, ... }.
2. Alice calls request_refund(deposit_msg, refund_btc_address, tx_bytes, vout, ...).
3. unsafe_refund_timelock_sec elapses.
4. Attacker (bob) calls execute_refund(utxo_storage_key, None).
   → BTCPendingInfo { account_id: bob, ... } created; bob.btc_pending_sign_ids contains the id.
5. Alice calls execute_refund(utxo_storage_key, None).
   → Panics: "pending info already exist" (same deterministic txid on Bitcoin).
6. Alice calls sign_btc_transaction(pending_id, 0, 0).
   → Callback: alice.btc_pending_sign_ids.remove(pending_id) == false → "Internal error".
7. Refund is stuck. Bob does not sign. Alice's BTC remains locked in the bridge.
8. Operator must: reject_refund(utxo_storage_key) → remove_refund_pending_tx_id(pending_id).
   Alice restarts from step 2; attacker repeats from step 4.
```

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
