### Title
`revalidateHeader` Silently Discards Envelope Validation Result in Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` wraps its only envelope check in `assertWithMsg`, a CPP-gated macro that compiles to a complete no-op in production builds (i.e., when the `asserts` Cabal flag is absent). Simultaneously, the inner call to `reupdateChainDepState` is explicitly documented to skip all cryptographic checks (KES/VRF/OCert). The net result is that in every production deployment that does not opt into the `asserts` flag, `revalidateHeader` performs **zero validation** — it unconditionally constructs and returns a new `HeaderState` regardless of whether the header is structurally or cryptographically valid. This is the direct analog of the external report's vulnerability: a critical return value (the `Either String ()` result of `validateEnvelope`) is silently discarded rather than enforced.

---

### Finding Description

`assertWithMsg` is defined as:

```haskell
-- Ouroboros/Consensus/Util/Assert.hs
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

When `ENABLE_ASSERTIONS` is not defined (the default for production), the CPP block is omitted and the only surviving equation is `assertWithMsg _ a = a` — the check argument is evaluated but its result is unconditionally thrown away.

`revalidateHeader` relies on this macro as its sole guard:

```haskell
-- HeaderValidation.hs lines 531-561
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← no-op in production
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' =
    reupdateChainDepState               -- ← skips KES/VRF/OCert
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView
        (untickedHeaderStateTip st) hdr  -- ← result discarded in production
```

`revalidateHeader` is called unconditionally from the production `ApplyBlock ExtLedgerState` instance:

```haskell
-- Extended.hs lines 213-227
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
  where
    ...
    hdr = revalidateHeader
            (getExtLedgerCfg cfg)
            ledgerView
            (getHeader blk)
            tickedHeaderState
```

`reapplyBlockLedgerResult` is invoked during two critical production paths:
1. **ImmutableDB replay on node startup** — replaying the entire immutable chain to reconstruct the in-memory ledger state.
2. **Chain selection fork switching** — reapplying blocks from the VolatileDB when the node switches to a competing fork.

In both paths, the `ledgerView` passed to `revalidateHeader` is derived from the *current* ticked ledger state, which may differ from the one used during original validation (e.g., after an era transition handled by the Hard Fork Combinator). If `additionalEnvelopeChecks` or the structural envelope checks would fail against the new `ledgerView`, the failure is silently swallowed in production.

The `asserts` flag is explicitly described as an opt-in, temporary diagnostic measure:

> "Even if the Consensus code is being benchmarked, it might be a good idea to *temporarily* enable assertions to perform additional checks on consistency."
> — `docs/website/contents/howtos/contributing/sanity_checks.md`

This confirms that production deployments run without `ENABLE_ASSERTIONS`, making `assertWithMsg` a permanent no-op on mainnet.

---

### Impact Explanation

In production, `revalidateHeader` constructs a `HeaderState` with no validation of any kind:
- **Envelope checks** (block number consecutiveness, slot monotonicity, prev-hash chain linkage) are computed but their `Either String ()` result is discarded.
- **Cryptographic checks** (KES signature, VRF proof, OCert counter) are skipped entirely by `reupdateChainDepState`.

If `revalidateHeader` is invoked with a header whose envelope is inconsistent with the provided `HeaderState` — for example, because the `ledgerView` has changed across an era boundary during fork switching — the resulting `HeaderState` will contain a `ChainDepState` computed from an invalid input. This corrupted `ChainDepState` (carrying wrong nonces, OCert counters, or last-slot values) is then stored as the authoritative protocol state for subsequent header validation via `updateChainDepState`, potentially causing honest headers to be rejected or invalid ones to be accepted in future rounds.

This maps to the allowed impact: **ChainDB/LedgerDB replay/rollback bug that causes durable use of the wrong ledger state without operator fault** (High), or at minimum **a flaw that materially weakens block authorization** (Medium).

---

### Likelihood Explanation

The invariant that `revalidateHeader` is only called for headers previously validated against the *same exact* `HeaderState` is maintained by convention, not by the type system or any runtime enforcement in production. The `ledgerView` argument is not the same object used during original validation — it is recomputed from the current ticked ledger state at replay time. For the Hard Fork Combinator, `additionalEnvelopeChecks` is era-specific and depends on the `ledgerView`; a mismatch between the era at original validation time and the era at replay time (which can occur during fork switches that cross an era boundary) would produce a failing `envelopeCheck` that is silently ignored. An unprivileged peer that serves a chain straddling an era boundary can trigger this path via the ChainSync miniprotocol, causing the node to call `reapplyBlockLedgerResult` for blocks near the hard-fork transition point.

---

### Recommendation

Replace the `assertWithMsg`-guarded envelope check in `revalidateHeader` with a proper enforced check that is active in all build configurations, matching the pattern used in `validateHeader`:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case runExcept (withExcept show (validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr)) of
    Left err -> error ("revalidateHeader: envelope invariant violated: " <> err)
    Right () ->
      HeaderState
        (NotOrigin (getAnnTip hdr))
        (reupdateChainDepState ...)
```

Alternatively, if the performance cost of `validateEnvelope` is a concern on the hot path, the result should at minimum be enforced unconditionally (not behind a CPP flag) so that invariant violations are never silently swallowed in production.
