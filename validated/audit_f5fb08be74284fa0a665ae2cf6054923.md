### Title
`safe_mint` Mints nBTC to Bridge Before Checking Recipient Registration, Causing Permanent Token Lock — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function unconditionally mints nBTC tokens into the bridge contract's own account (`bridge_id`) before verifying that the intended recipient's account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens, leaving them permanently locked in the bridge's nBTC balance with no on-chain recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mints first** — `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally credits `amount` nBTC to the bridge contract's own account.
2. **Checks registration after** — `if self.token.accounts.get(&account_id).is_none()` — if the recipient is not registered, the function returns `PromiseOrValue::Value(U128(0))` immediately.
3. **No rollback of step 1** — the minted tokens remain in `bridge_id`'s nBTC balance; NEAR's cross-contract call model does not roll back the nBTC contract's state when the bridge's callback later panics. [1](#0-0) 

The satoshi-bridge contract has no mechanism to recover these orphaned tokens. The `lost_found` map only covers failed `ft_transfer` calls; `withdraw_protocol_fee` only covers explicitly tracked protocol fees. Neither covers nBTC silently stranded in `bridge_id`'s balance by a failed `safe_mint`. [2](#0-1) 

The safe-deposit path is triggered when `deposit_msg.safe_deposit` is `Some(..)` in `verify_deposit_v2`: [3](#0-2) 

### Impact Explanation
When `safe_mint` returns `U128(0)` and the bridge's callback panics to "revert" the deposit:
- The bridge's own state changes (e.g., marking the UTXO verified) are rolled back.
- The nBTC contract's state change — minting `amount` to `bridge_id` — is **not** rolled back (it is in a separate NEAR receipt that already committed).
- Result: `amount` nBTC is permanently minted into the bridge's own balance with no corresponding user credit and no recovery function. The total nBTC supply is inflated without BTC backing, breaking the 1:1 peg invariant. This matches the **Medium** impact class: permanent burning below backed supply / broken callback rollback / stuck bridge state requiring operator intervention.

### Likelihood Explanation
The safe-deposit flow is the standard path for Omni Bridge integrations. Any user who sends BTC with `safe_deposit` set in their `DepositMsg` but whose NEAR account is not yet registered in the nBTC contract will trigger this path. Account registration is a separate prerequisite that users can easily miss, and there is no pre-flight check in the bridge before calling `safe_mint`. [4](#0-3) 

### Recommendation
Check whether `account_id` is registered **before** minting to `bridge_id`. If the account is unregistered, either:
- Revert immediately (panic) without minting, so no tokens are created.
- Auto-register the account (as `mint_inner` already does) and proceed.
- Store the orphaned amount in a recoverable mapping (analogous to `lost_found`) so the user can claim later. [5](#0-4) 

### Proof of Concept
1. User sends BTC to a deposit address derived from a `DepositMsg` with `safe_deposit = Some(...)`.
2. User's NEAR account is **not** registered in the nBTC contract.
3. Relayer calls `verify_deposit_v2` with the inclusion proof.
4. Bridge verifies the deposit and calls `safe_mint(account_id, amount, msg)` on the nBTC contract.
5. `safe_mint` executes `internal_deposit(&bridge_id, amount)` — `amount` nBTC is minted to the bridge's own account.
6. `safe_mint` checks `accounts.get(&account_id)` — returns `None`.
7. `safe_mint` returns `U128(0)` without any transfer.
8. The bridge's callback panics (safe-deposit "revert" semantics); the bridge's state is rolled back, but the nBTC mint in step 5 is already committed in the nBTC contract.
9. `amount` nBTC is permanently locked in `bridge_id`'s balance; the user receives nothing; the nBTC total supply exceeds the BTC held by the bridge.

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
