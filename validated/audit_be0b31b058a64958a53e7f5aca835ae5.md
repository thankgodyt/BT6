### Title
Incorrect `EXPECTED_ACTIONS_NUMBER` Constant Permanently Breaks All Orchard Shielded Withdrawals - (File: contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs)

---

### Summary

The constant `EXPECTED_ACTIONS_NUMBER` is set to `1` in `orchard_policy.rs`, but the Orchard protocol builder always pads bundles to a minimum of **2** actions for privacy. The validation check `bundle.actions().len() != EXPECTED_ACTIONS_NUMBER` therefore rejects every valid Orchard bundle submitted by any user, permanently breaking all shielded (Orchard) ZEC withdrawals.

---

### Finding Description

In `orchard_policy.rs`, the constant and its enforcement are:

```rust
pub const EXPECTED_ACTIONS_NUMBER: usize = 1;
...
if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
    return Err(format!(
        "Orchard bundle must have {} actions, got {}",
        EXPECTED_ACTIONS_NUMBER,
        bundle.actions().len()
    ));
}
```

The code comment directly contradicts the constant's value:

> "Minimum number of actions required in an Orchard bundle per the Orchard protocol. **The Orchard builder automatically pads bundles to meet this minimum for privacy.** See: https://github.com/zcash/orchard/blob/main/src/builder.rs#L36"

The referenced `MIN_ACTIONS` in the orchard crate is **2**. The builder always pads to at least 2 actions. Therefore, any bundle produced by a standard Zcash wallet will have `actions().len() >= 2`, causing the strict `!= 1` check to always fail.

This error propagates as follows:

1. `extract_orchard_bundle` returns `Err(...)` for any valid bundle.
2. `PsbtWrapper::new` calls `.unwrap_or_else(|_| env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: ..."))`.
3. The `ft_on_transfer_callback` panics.
4. NEAR's NEP-141 refund mechanism returns the nZEC to the user.
5. The Orchard withdrawal path is permanently non-functional.

The analog to the external report is direct: just as `_token1 == PEAS` should have been `_token0 == PEAS` (wrong direction in a conditional), `EXPECTED_ACTIONS_NUMBER = 1` should be `2` (wrong value in a validation formula). Both are incorrect constants/conditions embedded in a critical validation path that cause the feature to produce wrong outcomes for every caller.

---

### Impact Explanation

Every user who attempts a shielded (Orchard) nZEC withdrawal is rejected at the `PsbtWrapper::new` call inside `ft_on_transfer_callback`. While NEAR's refund mechanism returns the tokens, the Orchard withdrawal feature is entirely non-functional. This is a Zcash-specific validation failure causing a stuck bridge state that requires operator intervention (contract redeployment) to resolve. No transparent ZEC withdrawals are affected, but the shielded pool withdrawal path — a core Zcash privacy feature — is permanently broken.

**Impact: Medium** — Harmful smart-contract behavior without direct funds theft; stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

The bug is triggered by **every** user who submits a valid Orchard bundle for a shielded withdrawal. There are no preconditions beyond using the Orchard withdrawal path. Any standard Zcash wallet produces bundles with `actions().len() >= 2`, so the failure is 100% reproducible for all Orchard withdrawal attempts.

---

### Recommendation

Change the constant to match the actual Orchard protocol minimum enforced by the builder:

```rust
// Before (incorrect):
pub const EXPECTED_ACTIONS_NUMBER: usize = 1;

// After (correct):
pub const MIN_ACTIONS_NUMBER: usize = 2;
```

And update the check to allow bundles with at least the minimum number of actions (since the builder may pad beyond 2):

```rust
if bundle.actions().len() < MIN_ACTIONS_NUMBER {
    return Err(format!(
        "Orchard bundle must have at least {} actions, got {}",
        MIN_ACTIONS_NUMBER,
        bundle.actions().len()
    ));
}
```

The `recover_output_with_ovk(0, &ovk)` call already correctly targets only action index 0 (the real output); dummy padding actions at index 1+ carry zero value and do not affect the recovered amount or recipient.

---

### Proof of Concept

1. User holds nZEC on NEAR and calls `ft_transfer_call` targeting the bridge, providing a valid Orchard bundle (produced by any standard Zcash wallet, which always generates `actions().len() == 2`).
2. Bridge dispatches `ft_on_transfer_withdraw_chain_specific` → `get_last_block_height_promise().then(ft_on_transfer_callback(...))`.
3. Inside `ft_on_transfer_callback`, `PsbtWrapper::new(input, output, orchard_bundle, ...)` is called.
4. `extract_orchard_bundle` reads the bundle: `bundle.actions().len()` returns `2`.
5. Check: `2 != 1` → `true` → returns `Err("Orchard bundle must have 1 actions, got 2")`.
6. `PsbtWrapper::new` hits `.unwrap_or_else(|_| env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: failed to extract Orchard bundle"))` → contract panics.
7. Callback promise fails; NEP-141 refunds nZEC to user.
