Audit Report

## Title
Tokens Permanently Frozen When Transfer Amount Normalizes to Zero - (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` locks user tokens and stores a pending transfer without verifying that the transfer amount survives decimal normalization. When `sign_transfer` is later called by a trusted relayer, it computes the normalized amount and panics with `InvalidAmountToTransfer` if the result is zero. Because the two calls occur in separate transactions and no cancel or refund path exists, the locked tokens are permanently frozen.

## Finding Description

`normalize_amount` performs integer floor division, truncating any sub-unit remainder: [1](#0-0) 

`init_transfer` constructs the `TransferMessage` and stores it without checking whether `amount_without_fee()` survives normalization. The only pre-storage guard is `fee.fee < amount`: [2](#0-1) 

After storage, `init_transfer_internal` is called and the tokens are locked in the same transaction. In a subsequent, separate transaction, the trusted relayer calls `sign_transfer`, which is where the normalization check actually lives: [3](#0-2) 

Because this `require!` fires before the MPC cross-contract call at line 508, `sign_transfer_callback` is never reached. The callback is the only place where `remove_transfer_message` is called, and only when MPC signing succeeds and the fee is zero: [4](#0-3) 

A grep across the entire codebase finds no `cancel_transfer`, `refund_transfer`, or any other function that removes a pending transfer message outside of `sign_transfer_callback`. `update_transfer_fee` cannot help because it only allows the fee to be *increased* (enforced by `fee.fee >= current_fee.fee`), which shrinks `amount_without_fee()` further: [5](#0-4) 

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds**. For a NEAR-native token registered with `origin_decimals = 24` and `decimals = 6` (a standard EVM USDC pairing), `diff_decimals = 18`, so any transfer below `10^18` yoctoNEAR (i.e., below 1 NEAR) normalizes to zero and is permanently frozen. The loss is not dust — it is the entire transferred amount. This matches the critical impact category of permanent freezing of bridged funds.

## Likelihood Explanation

The exploit path is fully unprivileged: any user can call `ft_transfer_call` on a registered NEP-141 token, which triggers `ft_on_transfer` → `init_transfer`. No special role is required to initiate the transfer. The only precondition is that the token pair has `origin_decimals > decimals`, which is the normal configuration for NEAR tokens (24 decimals) bridging to EVM chains (6 or 18 decimals). A user unfamiliar with the normalization mechanics who sends a "small" amount (e.g., 0.5 NEAR) will trigger this silently — `init_transfer` returns `U128(0)` (tokens accepted), giving no indication of failure until the relayer's `sign_transfer` panics.

## Recommendation

Add the normalization check inside `init_transfer` (before `init_transfer_internal` is called and tokens are locked). If the check fails, `ft_on_transfer` should return the full amount so the NEP-141 token contract refunds the user atomically:

```rust
// Inside init_transfer, after constructing transfer_message and before init_transfer_internal:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        require!(
            Self::normalize_amount(
                transfer_message.amount_without_fee().unwrap_or(0),
                decimals,
            ) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

This mirrors the existing guard in `sign_transfer` but places it before token locking, allowing `ft_on_transfer` to return the amount and trigger an automatic refund.

## Proof of Concept

1. Register a NEAR-native token with `origin_decimals = 24`, `decimals = 6` (diff = 18).
2. User calls `ft_transfer_call` sending `5 × 10^17` yoctoNEAR (0.5 NEAR) with `fee = 0`.
3. `ft_on_transfer` → `init_transfer` stores the `TransferMessage` and calls `init_transfer_internal`, locking the tokens. Returns `U128(0)` — tokens are accepted.
4. Trusted relayer calls `sign_transfer` for the stored transfer ID.
5. `normalize_amount(5×10^17, {24, 6})` = `5×10^17 / 10^18` = `0` (floor division).
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics; the NEAR transaction is reverted.
7. The transfer message remains in storage; the 0.5 NEAR is permanently locked with no cancel or refund mechanism available.
8. Repeating step 4 always produces the same panic. `update_transfer_fee` cannot help (fee can only increase, worsening the situation).
