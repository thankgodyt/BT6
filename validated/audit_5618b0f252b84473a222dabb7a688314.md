### Title
Peras BLS Vote Signature Lacks Network Domain Separation, Enabling Cross-Network/Fork Replay — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function that produces the message signed by Peras committee members encodes only `(roundNo, boostedBlockSlot, boostedBlockHash)`. It includes no network magic, genesis hash, or any chain-specific domain separator. A valid BLS vote signature captured from one Cardano network (e.g., a testnet or a pre-fork chain) is cryptographically valid on any other network where the same `(roundNo, boostedBlock)` tuple appears, allowing an unprivileged peer to replay captured votes and forge a quorum certificate.

---

### Finding Description

`hashVoteSignature` in `Ouroboros.Consensus.Peras.Crypto.BLS` constructs the signed message as a raw concatenation of three fields:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
``` [1](#0-0) 

The three fields are: the 8-byte Peras round number, the 8-byte slot of the boosted block, and the 32-byte block hash. No network magic, genesis hash, protocol version, or any other chain-specific identifier is included.

This function is called directly in both `signVote` and `verifyVoteSignature`:

```haskell
signVote sk roundNo boostedBlock =
  PerasBLSCryptoVoteSignature
    . BLS.signWithRole @SIGN sk
    $ hashVoteSignature roundNo boostedBlock
``` [2](#0-1) 

It is also used in `verifyAggregateVoteSignature` for certificate verification:

```haskell
verifyAggregateVoteSignature _ aggPk roundNo boostedBlock aggSig = do
  BLS.verifyWithRole @SIGN
    (unPerasBLSCryptoAggregateVoteVerificationKey aggPk)
    (hashVoteSignature roundNo boostedBlock)
    (unPerasBLSCryptoAggregateVoteSignature aggSig)
``` [3](#0-2) 

The `BLS.signWithRole @SIGN` call provides role-based domain separation between the `SIGN` and `VRF` key roles, but this only prevents cross-role confusion within a single deployment — it does not separate signatures across different Cardano networks. [4](#0-3) 

By contrast, the VRF election input (`hashVRFInput`) does include the epoch nonce, which is chain-specific:

```haskell
hashVRFInput roundNo epochNonce =
  ...
  $ roundNoBytes <> epochNonceBytes
``` [5](#0-4) 

This asymmetry means VRF eligibility proofs are chain-bound, but vote signatures are not.

The `CryptoSupportsVoteSigning` interface that `PerasBLSCrypto` implements defines `signVote` and `verifyVoteSignature` with no provision for a network context parameter: [6](#0-5) 

The concrete Peras vote type `PerasVote` in `Peras/Vote/V1.hs` carries the `pvSignature` field which is this context-free BLS signature: [7](#0-6) 

The WFALS committee implementation calls `verifyAggregateVoteSignature` during certificate verification, which ultimately calls `hashVoteSignature` with no network context: [8](#0-7) 

---

### Impact Explanation

When Peras is activated, an unprivileged peer who has observed valid Peras vote messages on one Cardano network (e.g., a testnet, a pre-hard-fork chain, or a private fork) can replay those BLS vote signatures on a different network where:

1. The same committee member's public key is eligible (same or overlapping stake distribution).
2. The same `(roundNo, boostedBlock)` tuple is being voted on — realistic in fork scenarios where pre-fork blocks are shared.

By replaying enough captured votes to reach quorum, the attacker can cause an honest node to accept a forged Peras certificate. A forged certificate boosts a block that was not legitimately chosen by the Peras voting process, directly corrupting the Peras chain-selection boost and potentially causing honest nodes to prefer a non-canonical chain. This falls under the **Critical** allowed impact: bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance, and **High**: chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

The attack is most realistic in two scenarios:

- **Hard fork / network split**: Pre-fork blocks are identical on both chains. Votes cast for pre-fork blocks on the old chain are valid on the new chain. Committee members with stake on both sides of the fork are common.
- **Testnet/mainnet overlap**: SPOs who run on both testnet and mainnet with the same BLS keys (if key reuse occurs) expose their testnet votes to mainnet replay.

The attacker requires no private key material — only the ability to observe and forward vote messages, which is achievable by any peer connected to the gossip network. The `pvSignature` field is transmitted in plain `PerasVote` messages over the network.

---

### Recommendation

Include a chain-specific domain separator in `hashVoteSignature`. The separator should be derived from the genesis hash or a network magic value that is fixed per deployment. For example:

```haskell
hashVoteSignature networkMagic roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (4 + 8 + 8 + 32)
    $ networkMagicBytes
      <> roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
```

Alternatively, follow the pattern already used in Byron block signing, where `ProtocolMagicId` is part of the `ContextDSIGN`: [9](#0-8) 

The `CryptoSupportsVoteSigning` interface should be extended to accept a network context, or the `PerasCfg` passed to `validatePerasCert` / `validatePerasVote` should carry the genesis hash and be threaded into `hashVoteSignature`. [10](#0-9)

### Proof of Concept

**Setup**: Two Cardano networks A (testnet) and B (mainnet) share genesis up to slot S. A hard fork occurs at slot S+1. Both networks have the same Peras committee member M with BLS signing key `sk_M`.

**Step 1**: On network A, at Peras round R, committee member M legitimately votes for block `b` (which exists on both chains, having been produced before the fork). M broadcasts `PerasVote { pvRoundNo = R, pvBoostedBlock = b, pvSeatIndex = i, pvSignature = BLS.sign(sk_M, hash(R, slot(b), hash(b))) }`.

**Step 2**: Attacker intercepts this vote message from network A's gossip layer.

**Step 3**: On network B, Peras round R is also active and the same block `b` is a candidate for boosting. The attacker injects the captured vote into network B's gossip.

**Step 4**: Network B nodes call `verifyVoteSignature pk_M R b sig`, which computes `hashVoteSignature R b` — identical to what was computed on network A — and the BLS verification succeeds.

**Step 5**: If the attacker collects enough such replayed votes to reach quorum, `forgePerasCert` produces a valid certificate on network B for block `b`, boosting it in chain selection regardless of whether it is the legitimate Peras winner on network B.
