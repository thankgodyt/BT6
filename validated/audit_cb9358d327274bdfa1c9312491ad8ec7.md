### Title
Wrong Amount Variable Used for Confirmation Threshold in Refund Finalization — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`internal_verify_refund_finalize` passes `btc_pending_info.actual_received_amount` (the post-gas-fee refund amount) to `get_confirmations`, instead of the original deposit amount (`actual_received_amount + gas_fee`). This mirrors the report's root cause: a derived/adjusted value is computed and stored, but the wrong (smaller) variable is used in the critical call, causing the bridge's confirmation-threshold policy to be evaluated against a systematically lower number than intended.

### Finding Description
When a refund is finalized via `execute_refund`, `finalize_refund_with_psbt` stores the following fields in `BTCPendingInfo`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 344–351
let btc_pending_info = BTCPendingInfo {
    transfer_amount: 0,
    actual_received_amount: refund_amount,   // = deposit_amount - gas_fee
    withdraw_fee: 0,
    gas_fee,
    burn_amount: 0,
    ...
};
``` [1](#0-0) 

`refund_amount` is explicitly `deposit_amount - gas_fee`:

```rust
// refund.rs  lines 280–283
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
``` [2](#0-1) 

Later, when the relayer calls `verify_refund_finalize`, the contract determines how many on-chain confirmations to require:

```rust
// refund.rs  line 441
let confirmations = self.get_confirmations(config, btc_pending_info.actual_received_amount);
``` [3](#0-2) 

`actual_received_amount` is the **refund amount** (deposit minus gas fee), not the original deposit amount. The correct call should use `btc_pending_info.actual_received_amount + btc_pending_info.gas_fee` to reconstruct the original deposit value.

`get_confirmations` maps satoshi upper-bound thresholds to required confirmation counts:

```rust
// config.rs  lines 196–220
pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
    ...
    for key in &keys {
        if *key > satoshi_amount {
            return u64::from(...);
        }
    }
    ...
}
``` [4](#0-3) 

By contrast, the deposit path correctly uses the raw UTXO value:

```rust
// btc_light_client/deposit.rs  lines 134, 168
let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
let confirmations = self.get_confirmations(config, deposit_amount);
``` [5](#0-4) 

And the refund-request path also correctly uses the raw deposit amount:

```rust
// refund.rs  lines 167–168
let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
let confirmations = self.get_confirmations(config, deposit_amount);
``` [6](#0-5) 

Only `internal_verify_refund_finalize` uses the wrong (smaller) variable.

### Impact Explanation
When a deposit amount sits just above a confirmation threshold and the gas fee is large enough to push `actual_received_amount` below that threshold, `verify_refund_finalize` accepts the refund proof with fewer confirmations than the bridge policy requires for that deposit size. A relayer (or any public caller) can finalize a refund on a shorter chain tip than the bridge's security model intends, weakening the reorganization resistance guarantee for that refund. This is a bypass of the bridge's confirmation-count policy.

**Impact: Medium** — Bypass of bridge limits or policies (confirmation-count policy bypass reachable by any public caller of `verify_refund_finalize`).

### Likelihood Explanation
The bypass only activates when `deposit_amount` straddles a threshold in `confirmations_strategy` and `gas_fee` is large enough to push `actual_received_amount` below it. This is an edge-case condition but requires no privileged access and no external dependency compromise — any user who deposits BTC, requests a refund, and calls `execute_refund` + `verify_refund_finalize` can trigger it.

**Likelihood: Low**

### Recommendation
Replace the wrong variable with the reconstructed original deposit amount:

```rust
// internal_verify_refund_finalize
let deposit_amount = btc_pending_info.actual_received_amount + btc_pending_info.gas_fee;
let confirmations = self.get_confirmations(config, deposit_amount);
```

This mirrors how both `internal_request_refund` and `internal_verify_deposit_entry` already compute confirmations from the raw UTXO satoshi value.

### Proof of Concept
Assume `confirmations_strategy = { "10000000": 6, "100000000": 12 }` (i.e., deposits ≤ 10 M sat → 6 confs; > 10 M sat → 12 confs).

1. User deposits 10,000,001 sat. `internal_verify_deposit_entry` calls `get_confirmations(10_000_001)` → **12 confirmations** required.
2. User calls `request_refund` with `gas_fee = 2`. `internal_request_refund` calls `get_confirmations(10_000_001)` → **12 confirmations** required (correct).
3. After timelock, user calls `execute_refund`. `finalize_refund_with_psbt` stores `actual_received_amount = 9_999_999`, `gas_fee = 2`.
4. User calls `verify_refund_finalize`. `internal_verify_refund_finalize` calls `get_confirmations(9_999_999)` → **6 confirmations** required — half the intended security level for this deposit size.

The refund proof is accepted after only 6 confirmations instead of the 12 the bridge policy mandates for a 10,000,001-sat UTXO.

    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
```
