### Title
First-Caller-Wins `request_refund` Allows Front-Running to Redirect Refund Address and Block Legitimate Refund Requests — (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is a public, permissionless function. The contract enforces exactly one refund request per UTXO (first-caller-wins). When `deposit_msg.refund_address` is `None`, the caller freely supplies the BTC refund address. An unprivileged attacker who observes a pending `request_refund` call in the NEAR transaction pool can front-run it with an identical proof but a malicious BTC address, permanently occupying the UTXO's refund slot and blocking the legitimate user from ever submitting their own request.

---

### Finding Description

**Root cause — single-slot, first-caller-wins enforcement:**

In `request_refund_callback`, the contract rejects any second submission for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [1](#0-0) 

**No ownership check on the refund address:**

When `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` is stored verbatim with no verification that the caller owns or is related to the deposit:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

If `deposit_msg.refund_address` is `None`, the branch is skipped entirely and any BTC address is accepted.

**`request_refund` is fully public — no role restriction:**

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [3](#0-2) 

Unlike `verify_deposit_v2` and `verify_refund_finalize`, this function carries no `#[trusted_relayer]` attribute, so any NEAR account can call it.

**`execute_refund` is also fully public:**

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
``` [4](#0-3) 

After the `unsafe_refund_timelock_sec` elapses, anyone — including the attacker — can trigger execution.

**`execute_refund` marks the UTXO as verified, permanently blocking re-submission:**

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [5](#0-4) 

Once `execute_refund` is called (even with a malicious address), the UTXO enters `verified_deposit_utxo`. The `request_refund_callback` then permanently rejects any new refund request for that UTXO:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
``` [6](#0-5) 

---

### Impact Explanation

An attacker who successfully front-runs `request_refund` and subsequently calls `execute_refund` before the DAO rejects the request causes:

1. The MPC signing pipeline to be initiated for a PSBT paying the attacker's BTC address.
2. The deposit UTXO to be permanently marked in `verified_deposit_utxo`, blocking any future legitimate refund submission.
3. If MPC signs and the transaction confirms on-chain, the user's BTC is irreversibly sent to the attacker.

This matches: **Medium — attacker-triggered temporary locking of bridged funds** (if DAO responds in time) escalating to **Critical — significant loss of user funds** (if DAO does not reject before `execute_refund` is called and MPC signs).

---

### Likelihood Explanation

- `deposit_msg.refund_address` is `None` in the standard deposit flow (the field is optional and most deposits will not pre-authorize a refund address).
- All inputs needed to front-run (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the NEAR transaction pool before inclusion.
- NEAR validators can reorder transactions within a block; an attacker can submit with higher gas priority.
- The `unsafe_refund_timelock_sec` window is the only defense, and it relies entirely on the DAO being online and responsive — a liveness assumption not guaranteed by the protocol.

---

### Recommendation

1. **Bind the refund address to the depositor at deposit time.** Require `deposit_msg.refund_address` to be set (non-`None`) before a refund request is accepted, so the address is committed on-chain before any refund can be requested.
2. **Restrict `request_refund` to the depositor or a trusted relayer.** Add `#[trusted_relayer]` or require the caller to prove ownership of the deposit (e.g., sign with the NEAR account embedded in `deposit_msg`).
3. **Allow multiple refund requests per UTXO** (analogous to the report's option 1), so a malicious first request does not permanently block legitimate ones. Only the DAO-approved or depositor-owned request should be executable.

---

### Proof of Concept

1. Alice sends 1 BTC to the bridge deposit address derived from her `deposit_msg` (with `refund_address: None`).
2. Alice broadcasts `request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)` on NEAR.
3. Attacker observes Alice's pending transaction, copies `deposit_msg`, `tx_bytes`, `vout`, `proof`, and submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with higher gas.
4. Attacker's transaction is included first. `refund_requests[utxo_key] = { refund_address: attacker_btc_addr, ... }`.
5. Alice's transaction fails: `"Refund request already exists for this UTXO"`.
6. Attacker waits for `unsafe_refund_timelock_sec` to elapse.
7. Attacker calls `execute_refund(utxo_key, None)`. A PSBT paying `attacker_btc_addr` is created; `verified_deposit_utxo` now contains `utxo_key`; `executed = true`.
8. MPC signs the PSBT. The signed transaction is broadcast to Bitcoin.
9. Alice's 1 BTC (minus gas fee) is delivered to the attacker's address. Alice cannot submit a new refund request because `verified_deposit_utxo` permanently blocks it.
