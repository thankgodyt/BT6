### Title
Peras Quorum Threshold Bypass via Absolute/Relative Stake Unit Mismatch in `stakeAboveThreshold` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` (accumulated from ledger-sourced absolute stake values) directly against a relative quorum threshold (`3/4 + 2/100 = 0.77`). The function itself documents that this comparison is only meaningful when both operands are in the same units, but no normalization is enforced anywhere in the production path. Because absolute ledger stake values (in lovelace) are orders of magnitude larger than `0.77`, a single vote from any pool with positive stake trivially satisfies the threshold, allowing an unprivileged peer to forge a Peras certificate for any block of their choosing.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The function carries an explicit TODO warning:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [1](#0-0) 

The `PerasVoteStake` type itself carries a matching admission:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [2](#0-1) 

The quorum threshold is configured as `3/4` with a safety margin of `2/100`, giving a combined threshold of `0.77`: [3](#0-2) 

The `validatePerasVote` implementation (the degenerate instance used for all blocks) looks up the stake directly from the provided `PerasVoteStakeDistr` without any normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [4](#0-3) 

The accumulated `ptvtTotalStake` in `PerasTargetVoteTally` is the raw sum of these un-normalized `vpvVoteStake` values: [5](#0-4) 

`votesReachQuorum` then passes this raw sum directly to `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5) 

`updateCandidateVoteState` calls `votesReachQuorum` and immediately forges a certificate if it returns `Just`: [7](#0-6) 

---

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute ledger stake values (e.g., lovelace), any pool with stake greater than `0.77` lovelace — which is every pool on the network — will have its single vote satisfy `stakeAboveThreshold`. This means:

1. A single `PerasVote` from any pool with positive stake causes `votesReachQuorum` to return `Just`, triggering `forgePerasCert`.
2. The resulting `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params = 15` (the default weight boost).
3. This certificate is stored in `PerasVoteDB` and propagated to `ChainDB`.
4. During chain selection, the boosted block gains a weight advantage of 15 blocks over all competing chains, causing honest nodes to prefer the adversarially chosen block.

This is a **bypass of the Peras quorum/certificate check** that enables unauthorized certificate acceptance and chain selection manipulation by an unprivileged peer. [8](#0-7) 

---

### Likelihood Explanation

The entry path is fully reachable by any peer that can send a `PerasVote` via the `ObjectDiffusion` mini-protocol. The `objectDiffusionInbound` handler accepts votes from any connected peer and submits them to the `ObjectPoolWriter`, which calls `implAddVote` in `PerasVoteDB`: [9](#0-8) [10](#0-9) 

No special privileges, key compromise, or stake majority is required. Any pool operator (or any node that can impersonate a pool ID present in the `PerasVoteStakeDistr`) can trigger this with a single crafted vote message.

---

### Recommendation

1. **Enforce normalization at the boundary**: `validatePerasVote` must normalize the absolute ledger stake to a relative value (dividing by total committee stake) before constructing `ValidatedPerasVote`. The total committee stake must be passed in or derived from the `PerasVoteStakeDistr`.

2. **Alternatively, change the threshold representation**: Express `PerasQuorumStakeThreshold` as an absolute value (total lovelace required) rather than a fraction, and ensure the threshold is recomputed from the current epoch's total stake at validation time.

3. **Add a type-level or runtime invariant**: Introduce a `NormalizedPerasVoteStake` newtype that can only be constructed via a normalization function, preventing raw absolute values from reaching `stakeAboveThreshold`.

4. **Resolve the documented TODO**: The comment at line 155–161 of `SupportsPeras.hs` and the comment at line 136–143 must be resolved before Peras is activated on any production network. [1](#0-0) 

---

### Proof of Concept

**Setup**: A private testnet with Peras enabled. Pool A has 1,000,000 lovelace of stake. The `PerasVoteStakeDistr` is populated with absolute ledger stake values (as the code currently provides no normalization).

**Attack sequence**:

1. Pool A sends a single `PerasVote` for block `B` in round `R` via the `ObjectDiffusion` mini-protocol to an honest node.
2. The honest node calls `validatePerasVote params stakeDistr vote`. The lookup returns `PerasVoteStake (1000000 % 1)`.
3. `implAddVote` calls `updatePerasRoundVoteStates`, which calls `updateCandidateVoteState`.
4. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1000000 % 1)`.
5. `stakeAboveThreshold` evaluates `1000000 % 1 >= 77 % 100` → `True`.
6. `forgePerasCert` is called and returns a `ValidatedPerasCert` with `vpcCertBoost = 15`.
7. The certificate is stored and diffused. All honest nodes now apply a weight boost of 15 to block `B`.
8. Chain selection on all honest nodes prefers the chain containing `B` over any competing chain that lacks this boost, even if the competing chain is longer by up to 14 blocks.

**Expected (correct) behavior**: Certificate forging should require votes from pools representing at least 77% of the total committee stake. A single pool with 1,000,000 lovelace out of a total committee stake of, say, 10,000,000,000 lovelace represents only 0.01% of stake and should not reach quorum. [11](#0-10) [7](#0-6) [12](#0-11)
