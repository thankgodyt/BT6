### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Boost — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the universal `BlockSupportsPeras` instance is a no-op stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or quorum validation. Because this function is the sole validation gate called on certificates received from untrusted peers before they are stored and used to boost chain selection, any unprivileged peer can inject a crafted `PerasCert` that boosts an arbitrary block on a competing fork, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the required validation hook for Peras certificates. The only deployed instance — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — implements this as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub skips all of the following checks that a correct implementation must perform:
- Aggregate BLS signature verification over the election ID and boosted block hash
- Verification that the claimed voters are eligible committee members
- Verification that the aggregate voter stake meets the quorum threshold (`stakeAboveThreshold`)

The network ingest path in `processCerts` calls exactly this function as its validation gate before storing and forwarding the certificate:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

`processCerts` is the function that processes all inbound certificates from peers; if validation passes (which it always does), the certificate is timestamped and added to the `PerasCertDB`: [4](#0-3) 

The `PerasCertDB` implementation's `implAddCert` also carries an explicit TODO acknowledging that non-trivial validation is missing: [5](#0-4) 

Once stored, the certificate's boost is immediately reflected in the `PerasWeightSnapshot` returned by `getWeightSnapshot`, which is used by chain selection: [6](#0-5) 

`chainSelSync` then triggers `chainSelectionForBlock` for the boosted block, potentially switching the node's preferred chain: [7](#0-6) 

Chain selection compares `wsvTotalWeight`, which is the sum of block number and weight boost: [8](#0-7) 

The `perasWeight` parameter (the boost magnitude assigned to every accepted certificate) is a large fixed value intended to represent a genuine quorum of stake. Because `validatePerasCert` never checks whether the certificate actually represents such a quorum, an attacker can manufacture this boost for free.

---

### Impact Explanation

An unprivileged peer can send a single crafted `PerasCert` message pointing to any block on a competing fork. The receiving node will:
1. Accept it unconditionally through `validatePerasCert`
2. Store it in `PerasCertDB`, updating the weight snapshot
3. Trigger chain selection for the boosted block
4. Potentially switch its preferred chain to the adversary's fork, because the fake boost (`perasWeight`) can exceed the honest chain's length advantage

This is a **chain-selection bug**: an honest node is made to prefer a non-canonical or adversarially-controlled chain without any legitimate quorum of stake backing the certificate. This directly undermines the Peras security guarantee that a boosted block represents a genuine supermajority of stake.

---

### Likelihood Explanation

The attack requires only the ability to send a well-formed `PerasCert` message over the Peras certificate diffusion mini-protocol, which is an unauthenticated peer-to-peer channel. No stake, keys, or privileged access are required. The attacker only needs to know the hash of a block on a competing fork (publicly observable from the chain). The attack is repeatable every Peras round.

---

### Recommendation

Replace the stub `validatePerasCert` with a complete implementation that:
1. Verifies the aggregate BLS signature over `(electionId, boostedBlock)` using the aggregate public key of the claimed voters
2. Verifies each claimed voter is a legitimate committee member for the given round (via the committee selection scheme, e.g., WFALS or EveryoneVotes)
3. Verifies that the aggregate stake of the claimed voters satisfies `stakeAboveThreshold params totalVoterStake`

The `verifyCert` functions in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Committee.EveryoneVotes` already implement the correct per-committee-scheme verification logic and should be wired into `validatePerasCert`. [9](#0-8) [10](#0-9) 

---

### Proof of Concept

**Schematic attack sequence:**

1. Attacker observes that the honest network is on chain `C` with tip at block `B_honest` (block number `N`).
2. Attacker has a competing fork with tip `B_adv` at block number `N - delta` (shorter chain).
3. Attacker crafts a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B_adv) }` with arbitrary (invalid) voter fields and a garbage aggregate signature.
4. Attacker sends this cert to a victim node via the Peras cert diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight }` unconditionally.
6. The cert is stored; `getWeightSnapshot` now returns a boost of `perasWeight` for `B_adv`.
7. `chainSelSync` triggers `chainSelectionForBlock` for `B_adv`.
8. `preferCandidate` compares `wsvTotalWeight`: `(N - delta) + perasWeight` vs `N + 0`. If `perasWeight > delta`, the victim switches to the adversary's fork.

The `perasWeight` parameter is designed to be large (on the order of the security parameter `k`) to provide fast settlement, so `delta` can be substantial and the attack still succeeds. [11](#0-10) [12](#0-11)
