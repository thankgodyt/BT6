Audit Report

## Title
`deploy_token` Bypasses Pause Mechanism — (`solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program defines `ALL_PAUSED` as the bitwise OR of only `INIT_TRANSFER_PAUSED` and `FINALIZE_TRANSFER_PAUSED`, with no bit for token deployment. The `deploy_token` entry point contains no pause guard, so any relayer holding a valid MPC-signed `DeployTokenPayload` can call it after a full pause is active, creating new token mints on-chain while the program is supposed to be completely halted. The EVM counterpart explicitly guards the equivalent function with `whenNotPaused(PAUSED_DEPLOY_TOKEN)` and includes that bit in `pauseAll()`, confirming the Solana omission is unintentional.

## Finding Description
`constants.rs` defines exactly two pause flags and their union:

```rust
pub const INIT_TRANSFER_PAUSED: u8 = 1 << 0;
pub const FINALIZE_TRANSFER_PAUSED: u8 = 1 << 1;
pub const ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED;
``` [1](#0-0) 

`pause.rs` sets `config.paused = ALL_PAUSED` (bit value `0b11`): [2](#0-1) 

All four transfer entry points gate on the relevant bit before proceeding (`finalize_transfer`, `finalize_transfer_sol`, `init_transfer`, `init_transfer_sol`): [3](#0-2) [4](#0-3) 

`deploy_token`, however, performs only a signature verification and immediately proceeds to mint creation — no `require!` on `config.paused` anywhere:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
``` [5](#0-4) 

The EVM counterpart explicitly guards the equivalent operation: [6](#0-5) [7](#0-6) [8](#0-7) 

## Impact Explanation
This is a concrete **pause bypass** matching the allowed critical impact class: "pause bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions." Creating a new token mint and registering its metadata is a deployer-equivalent action. When an admin triggers `pause()` to halt the bridge in response to a security incident, `deploy_token` remains fully operational. Any relayer can submit a previously obtained valid signed payload to register new mints on-chain, circumventing the admin's explicit halt. Once the pause is lifted, those mints are immediately usable in `finalize_transfer`, and any metadata inconsistency (e.g., incorrect decimals in the signed payload) would cause mis-accounting of bridged amounts.

## Likelihood Explanation
No key compromise or threshold MPC collusion is required. A relayer only needs a valid `SignedPayload<DeployTokenPayload>` — a normal artifact of the bridge flow — obtained at any point before the pause. Submitting it after the pause is a single public program call. The window between a pause being triggered and all in-flight signed payloads being invalidated is realistic in any production incident response scenario. The call is permissionless beyond possessing the signed payload.

## Recommendation
1. Add `pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;` to `solana/programs/bridge_token_factory/src/constants.rs`.
2. Update `ALL_PAUSED` to `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED`.
3. Import `DEPLOY_TOKEN_PAUSED` in `lib.rs` alongside the existing pause constants.
4. Add the following guard at the top of `deploy_token` in `lib.rs`:
   ```rust
   require!(
       ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
       error::ErrorCode::Paused
   );
   ```

## Proof of Concept
1. Admin calls `pause()` → `config.paused = 0b11` (`ALL_PAUSED`).
2. Relayer holds a valid `SignedPayload<DeployTokenPayload>` obtained before the pause (normal bridge operation).
3. Relayer calls `deploy_token(ctx, signed_payload)` on the paused program.
4. The function executes `data.verify_signature(...)` (succeeds — signature is valid and unaffected by pause state), then calls `ctx.accounts.initialize_token_metadata(data.payload)`.
5. A new token mint is registered on Solana while `config.paused == ALL_PAUSED`.
6. After the pause is lifted, `finalize_transfer` accepts this mint and distributes tokens to recipients using the registered metadata.

A local integration test can confirm this by: (a) calling `pause()`, (b) asserting `finalize_transfer` reverts with `Paused`, and (c) asserting `deploy_token` with a pre-signed payload succeeds — demonstrating the asymmetric behavior.
