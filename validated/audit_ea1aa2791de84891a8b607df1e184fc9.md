### Title
Peras `PerasVoteId` consumed-key omits vote target and `validatePerasVote` skips signature verification, enabling any peer to forge votes and force quorum for an attacker-chosen block — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras vote-ingestion pipeline has two compounding flaws that together are the direct analog of the bridge-deposit replay bug. First, the `validatePerasVote` default implementation performs no cryptographic signature check — it only looks up the voter in the stake distribution. Second, the deduplication key `PerasVoteId` is `{pviRoundNo, pviVoterId}` and omits the block being voted for. An unprivileged peer can therefore forge a vote for any known voter, targeting any block, have it accepted and counted toward quorum, and simultaneously consume that voter's slot so the legitimate vote is silently dropped. Repeating this for enough voters forces a certificate for an attacker-chosen block.

---

### Finding Description

**Root cause 1 — stub validation with no signature check**

`validatePerasVote` in `Block/SupportsPeras.hs` is the implementation that `processVotes` calls for every inbound vote:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The function ignores `_params`, never inspects the BLS signature, never verifies the VRF eligibility proof, and never checks the round number or block target. Any peer who knows a voter's `PerasVoterId` (public information) can craft a structurally valid `PerasVote` for that voter and have it accepted.

**Root cause 2 — consumed key omits the vote target**

The deduplication key stored in `pvdsVoteIds` is:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [2](#0-1) 

The block being voted for (`pvtBlock`) is absent. `implAddVote` checks this key atomically:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [3](#0-2) 

Once a `(roundNo, voterId)` pair is consumed, any subsequent vote with the same pair — including the legitimate one — is silently dropped as `PerasVoteAlreadyInDB`, regardless of which block it targets.

**Root cause 3 — validation and insertion are split across two separate atomic blocks**

`processVotes` validates all votes in one `atomically` block, then calls `addVote` outside it:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
``` [4](#0-3) 

The `implAddVote` TODO comment confirms that the DB-level re-validation is not yet implemented:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
``` [5](#0-4) 

This means the only validation gate is the one in `processVotes`, which is the stub that skips signatures.

**How the two root causes combine**

The `PerasTargetVoteTally` correctly prevents the same `PerasVoteId` from being double-counted within a single target:

```haskell
swapVote = Map.insertLookupWithKey (\_k old _new -> old) (getPerasVoteId vote)
(pvaVotes', pvaTotalStake')
  | (Nothing, votes') <- swapVote vote ptvtVotes =
      (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
  | otherwise = (ptvtVotes, ptvtTotalStake)
```
