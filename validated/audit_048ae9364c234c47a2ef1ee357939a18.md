### Title
Peras Weight Ignored in Forecast-Horizon Disconnect Check, Causing Incorrect Chain Rejection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally uses `emptyPerasWeightSnapshot` when comparing a peer's candidate fragment against the local selection. When Peras is enabled, this causes the node to disconnect from peers whose chain is genuinely preferred by total Peras weight but is shorter by raw block count, permanently preventing adoption of the correct heavier chain.

### Finding Description

When a received header's slot is beyond the current forecast horizon, `readLedgerStateHelper` blocks waiting for the local selection to advance. On each retry it calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always ignores Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` has two code paths: when the weight snapshot is empty it compares only by `SelectView` (block number + VRF tiebreaker); when it is non-empty it computes `wsvTotalWeight = blockNo + weightBoost` and compares that instead:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count-only comparison
      ...
  | otherwise =
      -- full Peras-weighted comparison
      ...
``` [2](#0-1) 

By hard-coding `emptyPerasWeightSnapshot`, `checkPreferTheirsOverOurs` always takes the block-count-only path, even when the node has a live `PerasWeightSnapshot` with real boosts. The `WeightedSelectView` definition confirms that a shorter chain can legitimately outweigh a longer one:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [3](#0-2) 

The structural parallel to M-09 is exact: M-09's `validateUserIsNotUnderwater` required a fully-healthy CR after a single step, blocking all incremental improvement. Here, `checkPreferTheirsOverOurs` requires the candidate to win on raw block count alone, blocking adoption of any chain that is heavier only because of Peras certificates. In both cases a post-operation check uses an incomplete measure of "goodness," causing legitimate progress to be rejected.

The TODO comment in the code explicitly acknowledges the problem:

```
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
``` [4](#0-3) 

### Impact Explanation

When Peras is active, a peer serving the canonical chain may have a fragment that is heavier (due to Peras certificates) but shorter by block count than the local selection. When that peer's next header falls beyond the forecast horizon, `checkPreferTheirsOverOurs` fires, sees `ShouldNotSwitch` (because block count alone does not prefer the candidate), and throws `CandidateTooSparse`, permanently disconnecting the peer. The node then never downloads or validates the Peras-boosted blocks, stays on the lighter chain, and diverges from the honest network. This is a **High** chain-selection bug: an unprivileged peer interaction (sending a valid header beyond the forecast horizon) causes an honest node to prefer a non-canonical, less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

Peras is currently disabled by default (`emptyPerasWeightSnapshot` is used everywhere when Peras is off, so there is no observable difference today). However, the code path is fully wired and the Peras infrastructure is production-ready per the CHANGELOG. Once Peras is enabled on any network (testnet or mainnet), any syncing node that receives a Peras-boosted header beyond its forecast horizon will trigger this bug. The scenario — a chain that is heavier but shorter — is the normal operating condition Peras is designed to produce. Likelihood is **Medium** conditional on Peras activation.

### Recommendation

Replace the hard-coded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the ChainDB (the same snapshot already used in `chainSelection` and `constructPreferableCandidates`). The corrected call should be:

```haskell
weights <- getPerasWeightSnapshot   -- read from cdbPerasWeightSnapshot
shouldSwitch $
  preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
```

This mirrors the fix described for M-09: measure the true "goodness" (Peras total weight) rather than a proxy (block count), and only disconnect when the candidate is genuinely not preferred under the full metric.

### Proof of Concept

1. Enable Peras on a private testnet.
2. Produce a fork `F` that is one block shorter than the local selection `S` but carries a Peras certificate boosting its tip, making `totalWeight(F) > totalWeight(S)`.
3. Connect a peer serving `F`. The peer's next header after the fork tip falls beyond the forecast horizon (e.g., the fork tip is near the epoch boundary).
4. `readLedgerStateHelper` blocks on `projectLedgerView`, calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate … emptyPerasWeightSnapshot ourFrag theirFrag` returns `ShouldNotSwitch` because `theirFrag` is shorter by block count.
6. `CandidateTooSparse` is thrown; the peer is disconnected.
7. The node never adopts `F`, remaining on the lighter chain `S` despite `F` being the canonical Peras-preferred chain. [5](#0-4) [1](#0-0) [6](#0-5)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"

            (projectChainOrderConfig cfg)
