### Title
Peras Certificate Validation Bypass Allows Any Peer to Inject Fraudulent Chain-Selection Boosts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. The production inbound-certificate pipeline (`processCerts`) calls this stub directly. An unprivileged peer can therefore inject an arbitrary `PerasCert` (any round number, any boosted block) that will be accepted, stored in `PerasCertDB`, and used to inflate the Peras weight of an attacker-chosen chain fragment during chain selection.

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must accept or reject inbound certificates before they are stored. The only deployed instance is the catch-all `instance StandardHash blk => BlockSupportsPeras blk`, whose implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This stub always returns `Right`, wrapping the caller-supplied `cert` verbatim as a `ValidatedPerasCert`. No BLS aggregate-signature check, no committee-membership check, no round-number range check, and no boosted-block existence check is performed.

The production inbound pipeline in `processCerts` calls this function directly for every certificate received from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertInboundException errs)
```

Because `validateCert` is `validatePerasCert mkPerasParams`, the `(errs, _)` branch is unreachable. Every certificate that is not already in the DB is unconditionally added.

The accepted certificate is then stored in `PerasCertDB` and immediately reflected in `getWeightSnapshot`, which `preferAnchoredCandidate` consults during chain selection to compute `weightBoostOfFragment` for competing chains.

The analog to the external report is precise:

| External report (Quest Protocol) | This codebase (Peras) |
|---|---|
| `_setClaimed(tokens)` marks a token as used | `validatePerasCert` is supposed to mark a cert as legitimate |
| The NFT can still be transferred after being claimed | Any cert passes `validatePerasCert` regardless of content |
| Buyer receives a token that appears valid but is spent | Honest node receives a cert that appears validated but is fabricated |
| Buyer cannot claim the reward | Honest node's chain selection is skewed toward attacker's chain |

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with:
- `pcCertRound` set to any round number not yet in the DB
- `pcCertBoostedBlock` set to the point of any block the attacker wants to boost

After injection, `implGetWeightSnapshot` computes a `PerasWeightSnapshot` that includes the fraudulent boost. `preferAnchoredCandidate` then uses `weightBoostOfFragment` to compare the attacker's candidate chain against the honest chain. If the fraudulent boost is large enough (controlled by `perasWeight params`), the honest node will switch to the attacker's chain, constituting a chain-selection safety failure driven entirely by a fabricated certificate.

This maps to the **Critical** impact class: bypass of Peras certificate checks that enables unauthorized certificate acceptance and chain-selection manipulation by an unprivileged peer.

### Likelihood Explanation

The entry path requires only a network connection. The attacker sends a single well-formed CBOR-encoded `PerasCert` message over the Peras certificate mini-protocol. No stake, no keys, and no prior relationship with the target node are required. The stub is the only deployed instance; there is no fallback validation path.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the BLS aggregate signature over `(pcCertRound, pcCertBoostedBlock)` against the aggregate public key of the claimed committee.
2. Verifies committee membership and quorum threshold using the epoch's stake distribution and VRF outputs.
3. Checks that `pcCertBoostedBlock` refers to a block that exists within the volatile window.
4. Rejects certificates whose `pcCertRound` is outside the valid range for the current epoch.

Until the real implementation is in place, the node should refuse to process inbound certificates entirely rather than accepting all of them.

  let roundNo = getPerasCertRound cert

    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
