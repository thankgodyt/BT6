### Title
`stakeAboveThreshold` Compares Unnormalized Accumulated Vote Stake Against a Relative Quorum Threshold, Enabling Incorrect Peras Certificate Generation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` directly compares the accumulated `PerasVoteStake` (a sum of per-voter stake values whose unit — absolute lovelace vs. normalized fraction — is explicitly unresolved) against `perasQuorumStakeThreshold` (a relative `Rational` fraction of total committee stake). No normalization step divides the accumulated vote stake by the total committee stake before the comparison. The code itself documents this as an open defect. When the actual ledger stake distribution is wired into the production vote-validation path, a single vote from any voter whose absolute stake exceeds the relative threshold (e.g., any pool holding more than 75% of total stake in lovelace terms) would trivially satisfy the quorum check, causing the node to forge and accept an invalid Peras certificate that boosts an adversarial chain.

---

### Finding Description

`PerasVoteStake` is defined as a bare `Rational` with no type-level guarantee that it is normalized:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting committee (given that the quorum is expressed as
-- a relative value of the voting committee total stake).
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [1](#0-0) 

`stakeAboveThreshold` then performs a raw comparison of the accumulated vote stake against the relative quorum threshold, with an explicit TODO acknowledging the missing normalization:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. ...
-- this function only makes sense when both values are relative (normalized)
-- values, so we should either normalize the 'PerasVoteStake' before calling
-- this function, or change this function to accept a stake distribution and
-- perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

`stakeAboveThreshold` is called from `votesReachQuorum`, which is the gate that decides whether a `ValidatedPerasVotesWithQuorum` — and therefore a Peras certificate — is produced:

```haskell
votesHaveEnoughStake =
  stakeAboveThreshold cfg totalVoteStake
``` [3](#0-2) 

`votesReachQuorum` is called from `updateCandidateVoteState` in the vote aggregation engine:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [4](#0-3) 

This aggregation is driven by `implAddVote` in the production `PerasVoteDB` implementation, which is reached via the node-to-node Peras vote diffusion mini-protocol:

```haskell
case updatePerasRoundVoteStates vote perasCfg (pvdsRoundVoteStates pvds) of
  Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
    pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
``` [5](#0-4) 

The production wiring in `NodeToNode.hs` currently passes `PerasVoteStakeDistr mempty` as a placeholder, with a TODO noting that the real ledger stake distribution must be plumbed in:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [6](#0-5) 

When that placeholder is replaced with the real ledger distribution, the `PerasVoteStake` values assigned during `validatePerasVote` will come from the ledger. If those values are absolute (lovelace) rather than normalized fractions, the comparison in `stakeAboveThreshold` is between incommensurable quantities: an absolute lovelace amount (e.g., `1_000_000_000_000`) versus a relative threshold (e.g., `0.75`). The absolute value trivially exceeds the threshold, so quorum is declared after the very first vote from any pool with non-trivial stake.

---

### Impact Explanation

This is a **Critical** bypass of Peras voting/certificate checks. An unprivileged peer that controls a legitimate stake pool key can send a single crafted vote. Because the accumulated `PerasVoteStake` (absolute lovelace) is compared directly against the relative quorum threshold (e.g., `0.75`), the check `stake >= quorumThreshold + safetyMargin` evaluates to `True` immediately. The node then calls `forgePerasCert` and stores a `ValidatedPerasCert` with a `PerasWeight` boost. This certificate is subsequently used in chain selection to boost the adversarial block, causing honest nodes to prefer a non-canonical chain. The Peras safety guarantee — that a boosted block requires a genuine supermajority of committee stake — is entirely defeated.

---

### Likelihood Explanation

The vulnerability is latent: it is blocked today only by the `PerasVoteStakeDistr mempty` placeholder. The TODO comment in `NodeToNode.hs` explicitly marks this placeholder for replacement with real ledger data. Once that wiring is completed (a planned, necessary step for Peras activation), the bug becomes immediately exploitable by any peer that holds a registered stake pool key, with no further preconditions. The attacker does not need a stake majority, leaked keys, or social engineering — only a valid pool key and knowledge of the unit mismatch.

---

### Recommendation

`stakeAboveThreshold` must normalize the accumulated vote stake before comparing it to the relative quorum threshold. The fix should either:

1. Accept the total committee stake as an additional parameter and divide `totalVoteStake` by it before the comparison, or
2. Require that `PerasVoteStakeDistr` always stores pre-normalized (relative) values and enforce this at the construction site where the ledger's absolute stake distribution is converted into `PerasVoteStakeDistr`.

The `PerasVoteStake` newtype should carry a phantom tag (e.g., `Absolute` vs. `Normalized`) to make unit mismatches a compile-time error, analogous to how `LedgerStake` and `Cumulative LedgerStake` are distinguished in `WFA.hs`.

---

### Proof of Concept

1. Node starts with the real ledger stake distribution wired into `makePerasVotePoolWriterFromChainDB` (replacing `PerasVoteStakeDistr mempty`).
2. Attacker controls pool `P` with absolute stake `s_P` (e.g., `1_000_000_000` lovelace ≈ 1000 ADA, a tiny fraction of total stake).
3. Attacker sends a single `PerasVote` for an adversarial block `B` in round `r`.
4. `validatePerasVote` looks up `P` in `PerasVoteStakeDistr` and assigns `vpvVoteStake = PerasVoteStake (1_000_000_000 % 1)`.
5. `updateCandidateVoteState` calls `votesReachQuorum`, which computes `totalVoteStake = 1_000_000_000`.
6. `stakeAboveThreshold` evaluates `1_000_000_000 >= 0.75 + safetyMargin` → `True`.
7. `forgePerasCert` is called; a `ValidatedPerasCert` boosting `B` is stored in the `PerasVoteDB`.
8. Chain selection applies the `PerasWeight` boost to `B`, causing honest nodes to prefer the adversarial chain.
