### Title
Detached Burn in `safe_mint_callback` Failure Path Removes UTXO Guard Before Burn Confirmation, Enabling Unauthorized Re-Mint — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when `safe_mint` returns `U128(0)` (unregistered recipient), the contract removes the UTXO from `verified_deposit_utxo` and then fires a `burn()` call with `.detach()`. Because the burn is fire-and-forget, a failure silently leaves the bridge holding unbacked minted tokens while the UTXO guard is already gone. A relayer can then re-submit the same UTXO via `safe_verify_deposit`, triggering another `safe_mint` and minting another unbacked tranche. This is the NEAR async analog of the Sudoswap cached-balance re-entrancy: the guard is invalidated before the compensating external call is confirmed, allowing the same deposit to be processed more than once.

The sequence is:

1. `safe_verify_deposit` is called for a UTXO whose recipient is not yet registered on nBTC.
2. `verify_safe_deposit_callback` inserts the UTXO key into `verified_deposit_utxo` (the double-spend guard) and calls `safe_mint`. [2](#0-1) 

3. `safe_mint` mints `mint_amount` tokens to the bridge's own account (because the recipient is unregistered) and returns `U128(0)`.
4. `safe_mint_callback` detects `is_refund_required() == true` and enters the failure branch.
5. **The UTXO key is removed from `verified_deposit_utxo` first** (line 440–441).
6. A `burn()` call is issued with `.detach()` (lines 443–451). If this burn fails for any reason (nBTC contract paused, gas exhaustion, internal panic), the failure is silently discarded.
7. The bridge now holds `mint_amount` unbacked nBTC tokens, and the UTXO key is no longer in `verified_deposit_utxo`.
8. A relayer re-submits the same UTXO via `safe_verify_deposit`. `verify_safe_deposit_callback` finds the key absent from `verified_deposit_utxo`, inserts it again, and calls `safe_mint` again — minting another `mint_amount` to the bridge.
9. Steps 4–8 repeat for every re-submission, accumulating unbacked tokens.

The structural parallel to the Sudoswap finding is exact: in Sudoswap the cached balance was read before the external call and remained valid after re-entry; here the `verified_deposit_utxo` guard is **removed** before the compensating external call (burn) is confirmed, leaving the same UTXO re-processable.

The `is_refund_required` helper confirms the trigger condition: any `safe_mint` that returns `U128(0)` causes the failure branch. [3](#0-2) 

---

### Impact Explanation

**Critical — Unauthorized minting / permanent loss of backed supply.**

Each successful re-submission of the same UTXO mints an additional `mint_amount` of nBTC tokens to the bridge's balance without any new BTC being deposited. Over multiple iterations the total nBTC supply exceeds the BTC held by the bridge, permanently breaking the 1:1 backing invariant. The accumulated unbacked tokens can subsequently be transferred or used within the NEAR ecosystem.

---

### Likelihood Explanation

**Medium.**

The trigger requires the detached `burn()` to fail. Realistic failure modes include:

- The nBTC contract is paused by a `PauseManager` at the moment the burn executes (a separate, independently reachable condition).
- The allocated `GAS_FOR_BURN_CALL` is insufficient for the nBTC contract's internal accounting path in an edge case.
- A future nBTC contract upgrade introduces a revert path that the bridge does not anticipate.

Once the burn fails once, the UTXO is permanently unguarded and any whitelisted relayer (or the original submitter if the whitelist is open) can re-submit it repeatedly. The attacker does not need to control the nBTC contract — they only need to observe that a burn failed (visible on-chain) and then re-submit the proof.

---

### Recommendation

1. **Do not remove the UTXO guard before the burn is confirmed.** Replace the detached burn with an awaited promise chain, and only remove the UTXO key from `verified_deposit_utxo` inside the burn's success callback.
2. **Alternatively**, keep the UTXO key in `verified_deposit_utxo` on the failure path and introduce a separate "retry-eligible" set. The UTXO is moved to the retry set only after the burn is confirmed successful, allowing re-submission only from that set.
3. **Never use `.detach()` for state-compensating operations.** Any cross-contract call that is meant to roll back minted tokens must be awaited and its result must gate any subsequent state changes.

---

### Proof of Concept

1. Alice generates a deposit address with `safe_deposit` set, but has not yet called `storage_deposit` on nBTC.
2. Relayer calls `safe_verify_deposit` with Alice's UTXO proof. Light client confirms inclusion.
3. `verify_safe_deposit_callback` inserts UTXO key into `verified_deposit_utxo` and calls `safe_mint(alice, 100_000, msg)`.
4. nBTC's `safe_mint` mints 100 000 tokens to the bridge (Alice unregistered) and returns `U128(0)`.
5. `safe_mint_callback` enters the failure branch: removes UTXO key from `verified_deposit_utxo`, fires `burn(bridge, 100_000)` with `.detach()`.
6. The nBTC contract is paused at this moment (or burn fails for another reason). The detached failure is silently ignored. Bridge balance: +100 000 nBTC. `verified_deposit_utxo`: UTXO key absent.
7. Relayer (or attacker) calls `safe_verify_deposit` again with the identical proof. `verify_safe_deposit_callback` finds the key absent, inserts it, calls `safe_mint` again → bridge receives another 100 000 nBTC.
8. Repeat step 7 N times → bridge holds N × 100 000 unbacked nBTC.
9. These tokens can be transferred out via `ft_transfer`, permanently inflating supply beyond BTC backing. [4](#0-3)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }

fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
