### Title
Incomplete Peras Weight Calculation in ChainSync Client Disconnection Check - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client always uses `emptyPerasWeightSnapshot` when comparing chain weights beyond the forecast horizon, omitting all Peras weight boosts from the comparison. This is directly analogous to M-6: a security-critical decision (whether to disconnect from a peer) is made using an incomplete value calculation that omits a component — Peras weight boosts — that is part of the protocol's canonical chain-weight definition.

### Finding Description

When a header from a peer is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to keep waiting for the chain to advance or to disconnect from the peer with `CandidateTooSparse`. The comparison is performed via `preferAnchoredCandidate`, but the call is hardcoded to pass `emptyPerasWeightSnapshot` instead of the actual live `PerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero boosts; ignores all Peras certificates
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The canonical total weight of a chain fragment under Peras is defined as:

> **total weight = block count (tip BlockNo) + sum of all Peras weight boosts on the fragment** [2](#0-1) 

`preferAnchoredCandidate` correctly implements this when a non-empty `PerasWeightSnapshot` is supplied — it intersects the two fragments and compares their `WeightedSelectView`s, which include `wsvWeightBoost`: [3](#0-2) 

But because `emptyPerasWeightSnapshot` is passed, `isEmptyPerasWeightSnapshot` returns `True` and the function falls into the non-Peras branch, comparing only raw block counts: [4](#0-3) 

The ChainDB API already exposes the live snapshot via `getPerasWeightSnapshot`: [5](#0-4) 

### Impact Explanation

**Concrete scenario:**

- Our chain: `A → B → C → D` (4 blocks, no boosts, total weight = 4)
- Peer's chain: `A → B → C'` (3 blocks, `C'` carries a Peras boost of 2, total weight = 5)
- Peer's next header `D'` (extending `C'`) is beyond the forecast horizon

With `emptyPerasWeightSnapshot`, the comparison sees our weight as 4 and their weight as 3 (boost ignored) → `ShouldNotSwitch` → the node throws `CandidateTooSparse` and **disconnects from the peer**.

With the correct snapshot, the comparison sees our weight as 4 and their weight as 5 → `ShouldSwitch` → the node correctly keeps waiting.

The node disconnects from a peer serving the **canonically heavier Peras chain** and will not adopt it. If all or most peers are serving this heavier chain, the node permanently diverges onto a lighter, less-secure chain. This is a chain-selection safety failure under Peras.

**Impact class:** High — chain-selection bug that causes an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

### Likelihood Explanation

- Triggered whenever a peer sends a header beyond the forecast horizon (a normal occurrence during syncing or when a peer is slightly ahead).
- No special privileges required; any peer can trigger this code path.
- Becomes exploitable as soon as Peras is activated and certificates are being issued on mainnet, causing real weight boosts to exist.
- The TODO comment (`https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is problematic with Peras, but the current code is still live and incorrect.

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` obtained from the ChainDB (via `getPerasWeightSnapshot`), consistent with how `preferAnchoredCandidate` is called everywhere else in the chain-selection pipeline: [6](#0-5) 

Alternatively, if the intent of the linked issue is to remove the check entirely, that should be done before Peras activation to avoid the incorrect disconnection behaviour.

### Proof of Concept

1. Activate Peras on a private testnet so that certificates are issued and blocks receive weight boosts.
2. Set up node A (our node) with chain `A → B → C → D` (4 blocks, no boosts).
3. Set up node B (peer) with chain `A → B → C'` where `C'` has a Peras boost of 2 (total weight 5 > 4).
4. Have node B send header `D'` (extending `C'`) to node A such that `D'`'s slot is beyond node A's current forecast horizon.
5. Observe: node A calls `checkPreferTheirsOverOurs`, computes peer weight as 3 (ignoring boost), concludes peer chain is not preferable, and throws `CandidateTooSparse`, disconnecting from node B.
6. Node A never adopts the heavier Peras chain, diverging from the canonical chain.
