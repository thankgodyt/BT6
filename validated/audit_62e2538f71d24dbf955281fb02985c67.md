### Title
Missing Minimum Normalized-Amount Check in `init_transfer` Allows Permanent Fund Lock - (File: near/omni-bridge/src/lib.rs)

### Summary
`sign_transfer` guards against a zero normalized transfer amount, but the upstream `init_transfer` entry point does not. A user can lock tokens in the bridge with an amount that floor-divides to zero after decimal normalization, making the transfer permanently unfinalizeable and the funds permanently frozen.

### Finding Description
The NEAR bridge contract stores two decimal values per token: `origin_decimals` (the token's native precision on the source chain) and `decimals` (the reduced precision used across the bridge). When a NEAR-side outbound transfer is signed, `sign_transfer` normalizes the net amount via floor division and enforces a non-zero result: [1](#0-0) 

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee()...,
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` uses floor division: [2](#0-1) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

However, the `init_transfer` function — the entry point called from `ft_on_transfer` — only checks that `fee < amount`: [3](#0-2) 

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

There is no check that `normalize_amount(amount - fee, decimals) > 0` at the time the transfer is created and the tokens are locked. The transfer is stored in `pending_transfers` and the user's tokens are transferred into the bridge contract before any normalization is evaluated. [4](#0-3) 

### Impact Explanation
When a relayer later calls `sign_transfer` for such a transfer, the `require!(amount_to_transfer > 0, ...)` check panics, reverting the signing transaction. The transfer remains in `pending_transfers` indefinitely. There is no cancel or refund mechanism for this state. The user's tokens are permanently frozen in the bridge contract. This matches the "permanent freezing of bridged funds" critical impact class.

### Likelihood Explanation
Any token registered with `origin_decimals > decimals` (e.g., a token with 18 decimals on Ethereum mapped to 6 decimals on NEAR, giving `diff_decimals = 12`) is vulnerable. Any user who sends fewer than `10^12` base units of such a token triggers the bug. This is reachable by any unprivileged user via the public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path with no special permissions required. [5](#0-4) 

### Recommendation
Add the normalization check inside `init_transfer`, before storing the transfer message and locking tokens. Specifically, after computing the fee-adjusted amount, verify that `normalize_amount(amount - fee, decimals) > 0`. This mirrors the guard already present in `sign_transfer` and prevents dust transfers from being accepted at the entry point.

### Proof of Concept
1. A token is registered with `origin_decimals = 18`, `decimals = 6` (diff = 12). Any amount < `10^12` normalizes to 0.
2. User calls `ft_transfer_call` on the token contract with `amount = 1`, `msg = InitTransferMsg { fee: 0, ... }`.
3. `ft_on_transfer` dispatches to `init_transfer`. The check `0 < 1` passes. The transfer is stored in `pending_transfers` and 1 token unit is locked in the bridge.
4. A trusted relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(1, decimals)` = `1 / 10^12` = `0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics; the signing transaction reverts.
7. The transfer remains in `pending_transfers` with no path to finalization or cancellation. The user's 1 token unit is permanently frozen. [6](#0-5)
