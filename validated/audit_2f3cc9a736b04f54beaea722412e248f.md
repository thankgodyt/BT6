### Title
`chain_signatures_account_id` Cannot Be Updated After Initialization — (File: `contracts/satoshi-bridge/src/config.rs`, `contracts/satoshi-bridge/src/api/management.rs`)

### Summary
The `chain_signatures_account_id` field in `Config` is permanently locked after contract initialization. Unlike `btc_light_client_account_id` and `nbtc_account_id`, it is absent from `ConfigUpdate` and has no dedicated setter. Additionally, `sync_chain_signatures_root_public_key` enforces a one-time-only constraint, permanently locking the MPC root public key as well. If the chain signatures (MPC) contract is ever migrated to a new account or rotates its root key, the bridge's entire signing pipeline — withdrawals, refunds, and UTXO management — becomes permanently inoperable.

### Finding Description

`ConfigUpdate` in `config.rs` (lines 225–263) is the sole mechanism for updating `Config` fields at runtime. It includes `btc_light_client_account_id` and `nbtc_account_id` as updatable fields, but **omits `chain_signatures_account_id`**: [1](#0-0) 

The `apply` method iterates only the fields present in `ConfigUpdate`, so `chain_signatures_account_id` is never touched: [2](#0-1) 

The only other MPC-related management function, `sync_chain_signatures_root_public_key`, enforces a hard one-time constraint — it panics with `"Already sync"` if the root public key is already set, making the root key equally immutable: [3](#0-2) 

The `chain_signatures_account_id` is used in `chain_signature.rs` to dispatch every MPC signing cross-contract call. If this account ID becomes stale, every call to sign a PSBT fails: [4](#0-3) 

### Impact Explanation

If the NEAR chain signatures contract is migrated to a new account ID (e.g., due to a protocol upgrade, security incident, or planned deprecation), the bridge has no mechanism to update `chain_signatures_account_id`. Every withdrawal, refund execution, and UTXO management operation that requires an MPC signature will permanently fail. User funds locked in pending withdrawals or refund requests cannot be released. The bridge enters a stuck state that cannot be resolved without a full contract upgrade and state migration — a complex, time-consuming recovery path.

This matches the **Medium** impact category: *stuck bridge state requiring operator intervention*.

### Likelihood Explanation

NEAR's chain signatures service is an active, evolving system. Contract migrations or root key rotations are plausible operational events. The asymmetry is notable: `btc_light_client_account_id` and `nbtc_account_id` were deliberately made updatable, indicating the developers recognized the need for account ID mutability — but `chain_signatures_account_id` was overlooked. The one-time-only `sync_chain_signatures_root_public_key` compounds the risk.

### Recommendation

1. Add `chain_signatures_account_id: Option<AccountId>` to `ConfigUpdate` and handle it in `apply`, mirroring the pattern used for `btc_light_client_account_id` and `nbtc_account_id`.
2. Remove the `is_none()` guard from `sync_chain_signatures_root_public_key` (or add a separate `force_sync_chain_signatures_root_public_key` callable by DAO) so the root public key can be re-synced when the MPC network rotates it.

### Proof of Concept

1. Deploy the bridge with `chain_signatures_account_id = "v1.chain-signatures.near"`.
2. NEAR migrates the chain signatures service to `"v2.chain-signatures.near"`.
3. DAO calls `update_config` with any valid `ConfigUpdate` — `chain_signatures_account_id` is not a field, so it cannot be changed.
4. DAO calls `sync_chain_signatures_root_public_key` — panics with `"Already sync"` because the key was set at step 1.
5. Any user initiating a withdrawal triggers an MPC signing call to the now-defunct `"v1.chain-signatures.near"`, which fails. The withdrawal is stuck. The user's nBTC is held in the bridge's pending state with no recovery path short of a full contract upgrade. [5](#0-4) [6](#0-5) [3](#0-2)
