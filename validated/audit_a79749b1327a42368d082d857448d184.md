### Title
Peras Certificate Validation Bypass Allows Any Peer to Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` method unconditionally returns `Right` (success) for every inbound certificate, performing no cryptographic, committee-membership, or quorum checks. Because this is the validator wired into the live Peras certificate diffusion inbound handler, any unprivileged peer can inject an arbitrary `PerasCert` that passes "validation" and is forwarded to chain selection, where it applies a weight boost to an attacker-chosen block and can cause the node to switch to a non-canonical chain.

---

### Finding Description

**Vulnerable stub — always-`Right` certificate validator**

The universal `BlockSupportsPeras` instance (the only instance in the codebase, covering all block types via `instance StandardHash blk => BlockSupportsPeras blk`) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- 15 weight units
      }
``` [1](#0-0) 

No signature, no committee membership check, no quorum proof — every certificate is unconditionally accepted.

**Production inbound handler wires this stub directly**

`makePerasCertPoolWriterFromChainDB` — the writer used in the live NTN handler — passes `validatePerasCert mkPerasParams` as the validation function to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**NTN miniprotocol handler is open to any peer**

The `hPerasCertDiffusionClient` handler in `NodeToNode.hs` calls `objectDiffusionInbound` with the above writer, with no peer-identity or trust check:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [3](#0-2) 

**Accepted certificate triggers chain selection**

`processCerts` calls `addCert` (= `ChainDB.addPerasCertAsync`) for every cert that passes the stub validator. `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then looks up the boosted block in the VolatileDB and calls `chainSelectionForBlock` for it:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The boosted block's chain now carries an extra `perasWeight = 15` units (from `mkPerasParams`), which can tip chain selection in its favour. [5](#0-4) 

---

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

An attacker who can establish a standard NTN connection (any peer on the network) can:

1. Craft a `PerasCert` whose `pcCertBoostedBlock` points to any block currently in the target node's VolatileDB.
2. Send it via the Peras cert diffusion miniprotocol.
3. The stub validator accepts it unconditionally; `addPerasCertAsync` enqueues it; `chainSelectionForBlock` re-evaluates the boosted block's chain with +15 weight.
4. If the boosted block is on a fork that was previously lighter than the canonical chain by ≤ 15 weight units, the node switches to that fork.

This breaks the chain-selection invariant that only legitimately certified blocks (backed by a quorum of committee members) receive a Peras weight boost. An attacker can steer an honest node onto a non-canonical chain without holding any stake or keys.

---

### Likelihood Explanation

**High.** The Peras cert diffusion miniprotocol is open to all NTN peers. The stub is the only `BlockSupportsPeras` instance in the codebase and is used in the production code path (not just tests). The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is a known placeholder, but it is currently reachable from the network. Any peer that can connect to the node can exploit this immediately.

---

### Recommendation

1. **Replace the stub with real validation** in `validatePerasCert`: verify the certificate's cryptographic proof, confirm the signer is a registered committee member for the claimed round, and check that the certificate represents a genuine quorum. This is tracked in `cardano-peras/issues/120`.
2. Until real validation is in place, **gate the Peras cert diffusion miniprotocol** so it is not advertised or accepted on production/mainnet node-to-node connections.
3. Consider adding a compile-time or runtime guard that prevents the stub instance from being used in any non-test context.

---

### Proof of Concept

**Private-testnet sequence:**

1. Start two nodes A (victim) and B (attacker) on a private testnet with Peras enabled.
2. Let both nodes sync to a common chain tip T. Ensure node A has a fork block F in its VolatileDB (e.g., a block at the same height as T but on a different branch, with chain weight exactly 14 units less than T's chain).
3. From node B, open a NTN connection to node A and send a single `PerasCert` message via the Peras cert diffusion miniprotocol with:
   - `pcCertRound` = any round not yet in A's `PerasCertDB`
   - `pcCertBoostedBlock` = the point of fork block F
4. Observe: `validatePerasCert mkPerasParams` returns `Right` unconditionally; `addPerasCertAsync` is called; `chainSelSync` runs `chainSelectionForBlock` for F; F's chain now has weight +15, exceeding T's chain; node A switches to the fork.
5. Node A is now on a non-canonical chain chosen by the attacker, with no stake or key material required.
