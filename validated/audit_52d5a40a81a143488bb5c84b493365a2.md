### Title
Peras Certificate Validation Completely Bypassed — Any Peer Can Inject Arbitrary Weight-Boosting Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. This stub is directly wired into the production network inbound path (`makePerasCertPoolWriterFromChainDB` / `makePerasCertPoolWriterFromCertDB`). An unprivileged peer can send crafted `PerasCert` objects for any round and any block hash; they will pass "validation" and be stored, causing the node to apply a Peras weight boost to an attacker-chosen block during chain selection.

---

### Finding Description

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gate for all inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The universal default instance, which is the only instance in the codebase, implements this as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No fields of `cert` are inspected. There is no check of:
- the aggregate BLS signature over the election identifier and boosted block,
- committee membership or quorum (≥ 3/4 stake threshold),
- the VRF eligibility proofs for non-persistent voters,
- the round number being within a valid window,
- or any other semantic constraint.

This stub is directly passed as the `validateCert` argument in both production pool-writer constructors:

```haskell
-- makePerasCertPoolWriterFromCertDB
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place

-- makePerasCertPoolWriterFromChainDB
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
```

`processCerts` — the function that handles every batch of certificates received from a remote peer — calls `validateCert` on each certificate and adds all that return `Right` to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
```

Because `validateCert = validatePerasCert mkPerasParams` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted and stored.

---

### Impact Explanation

Accepted certificates are stored in the `PerasCertDB` and propagated to the `ChainDB` via `ChainDB.addPerasCertAsync`. The `ValidatedPerasCert` carries a `vpcCertBoost = perasWeight params` (default: 15 blocks' worth of weight). This boost is applied during chain selection: a chain whose tip is "boosted" by a certificate is preferred over an equally long or even slightly shorter chain without a boost.

An attacker who can connect as a peer can therefore:
1. Craft a `PerasCert` naming any `pcCertRound` and any `pcCertBoostedBlock` (any slot/hash pair).
2. Send it to the target node.
3. The node stores it as a `ValidatedPerasCert` with full boost weight.
4. Chain selection now prefers the attacker-chosen block, potentially causing the honest node to switch to a non-canonical fork or to stall on a fork that the rest of the network has not adopted.

This directly satisfies the **High** impact criterion: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

It also satisfies the **Critical** criterion: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The attack requires only a standard peer-to-peer connection. The Peras certificate diffusion mini-protocol (`ObjectDiffusion`) is designed to accept certificates from any connected peer. No special privileges, keys, or stake are required. The attacker needs only to serialize a valid-looking `PerasCert` CBOR structure (two fields: a round number and a block point) and send it. The validation gate is a no-op, so the attack succeeds deterministically on every attempt.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(electionId, boostedBlock)` against the aggregated public keys of the claimed voters.
2. Checks that each claimed voter is a member of the correct voting committee for the given round (using the epoch's stake distribution and committee selection algorithm).
3. Verifies VRF eligibility proofs for non-persistent voters.
4. Confirms that the total stake of the signers meets the quorum threshold (`≥ 3/4 + safety_margin`).
5. Validates that `pcCertRound` falls within the acceptable window relative to the current chain tip.

Until the full implementation is ready, the stub should at minimum reject all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the network path is safe even in the incomplete state.

### Proof of Concept

The root cause is directly readable in the source. The complete call chain is:

**Step 1 — Stub validator always returns `Right`:** [1](#0-0) 

**Step 2 — Production pool writer for ChainDB wires in the stub:** [2](#0-1) 

**Step 3 — `processCerts` accepts every certificate whose `validateCert` returns `Right`:** [3](#0-2) 

**Step 4 — The `BlockSupportsPeras` class contract that `validatePerasCert` is supposed to enforce:** [4](#0-3) 

A concrete exploit sequence on a private testnet:

```
1. Attacker connects to target node as a Peras peer.
2. Attacker serialises:
     PerasCert { pcCertRound = <current_round>
               , pcCertBoostedBlock = <attacker_chosen_block_point> }
   as CBOR (2-element list: Word64 + RealPoint).
3. Attacker sends this via the ObjectDiffusion mini-protocol.
4. processCerts calls (validatePerasCert mkPerasParams cert)
   => always Right ValidatedPerasCert { vpcCertBoost = 15 }
5. Certificate is stored in PerasCertDB / ChainDB.
6. Chain selection now applies +15 weight to the attacker-chosen block,
   causing the node to prefer that fork over the honest chain.
```
