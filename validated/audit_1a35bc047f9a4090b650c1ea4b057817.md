### Title
Unprivileged Caller Can Hijack a Victim's Refund Execution and Permanently Block Self-Service Recovery — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` carries no caller-identity guard. Any account that has pending-sign capacity and can satisfy the timelock can call it against any refund request. On Bitcoin the refund transaction is fully deterministic (same inputs, same output, same txid), so the first caller to succeed owns the `BTCPendingInfo`. Every subsequent call — including the legitimate victim — is rejected with "pending info already exist". The victim has no self-service escape: `remove_refund_pending_tx_id` is `#[trusted_relayer]`-gated, and `reject_refund` is blocked because `executed == true` disables the permissionless path. The victim's BTC is stuck in the bridge's MPC-controlled deposit address until the attacker voluntarily signs or an operator intervenes.

---

### Finding Description

**Entrypoint — no caller restriction on `execute_refund`**

`execute_refund` is decorated only with `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. There is no check that `env::predecessor_account_id()` matches the deposit recipient or the original refund requester. [1](#0-0) 

**Step 1 — attacker calls `execute_refund(victim_utxo_key)`**

`resolve_execute_refund_timelock` only checks the attached deposit and the elapsed timelock; it does not verify the caller's identity. [2](#0-1) 

`load_refund_request_for_execute` passes because the timelock has elapsed and `verified_deposit_utxo` does not yet contain the key. [3](#0-2) 

**Step 2 — `finalize_refund_with_psbt` assigns ownership to the attacker**

`BTCPendingInfo` is created with `account_id: caller` (the attacker). The UTXO key is inserted into `verified_deposit_utxo`, and the refund request is kept with `executed = true`. [4](#0-3) 

**Step 3 — victim's retry is blocked by "pending info already exist"**

On Bitcoin the refund PSBT is built deterministically from the fixed deposit outpoint and the fixed `refund_address`. The resulting txid (= `btc_pending_id`) is identical regardless of who calls `execute_refund`. When the victim retries, `finalize_refund_with_psbt` tries to insert the same key and panics. [5](#0-4) 

**Step 4 — `remove_refund_pending_tx_id` is inaccessible to the victim**

The function is `#[trusted_relayer]`-gated, so the victim cannot call it at all. [6](#0-5) 

Even if the victim could call it, `internal_remove_refund_pending_tx_id` rejects the call because the refund request is still present in `refund_requests`. [7](#0-6) 

**Step 5 — `reject_refund` is also blocked for the victim**

Because `executed == true`, `is_already_deposited` evaluates to `false`, so the permissionless reject path is closed. Only DAO/Operator can call `reject_refund`. [8](#0-7) 

**Step 6 — operator intervention does not fully restore the victim**

Even after an operator calls `reject_refund` (removing the refund request) and a trusted relayer calls `remove_refund_pending_tx_id` (removing the stale pending info), `verified_deposit_utxo` still contains the UTXO key. `request_refund_callback` unconditionally rejects any new refund request for that key. [9](#0-8) 

There is no admin function that removes entries from `verified_deposit_utxo`. The only full resolution is for the attacker to sign the pending transaction (which sends BTC to the victim's pre-set `refund_address` — no theft, but the attacker controls the timeline).

---

### Impact Explanation

The victim's BTC is locked in the bridge's MPC-controlled deposit address. The victim cannot refund, cannot deposit (same UTXO key is blocked), and has no self-service recovery path. The attacker does not steal funds — the `refund_address` is fixed in the refund request — but they can indefinitely delay the victim's recovery. Full resolution requires either the attacker signing or operator intervention followed by a manual state repair (no existing function clears `verified_deposit_utxo` for a non-finalized refund).

**Severity: Medium** — attacker-triggered temporary/indefinite locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

- The attacker only needs: (a) knowledge of the victim's `utxo_storage_key` (observable from on-chain events), (b) one free pending-sign slot (default limit is 1 per account, trivially satisfied with a fresh account), and (c) the storage deposit attached to `execute_refund`.
- The timelock must have elapsed, but that is the normal precondition for any legitimate caller.
- No privileged role, leaked key, or off-chain coordination is required.

---

### Recommendation

Add a caller-identity check at the start of `execute_refund` (or inside `resolve_execute_refund_timelock`): require that `env::predecessor_account_id()` is either the deposit recipient recorded in `refund_request.deposit_msg().recipient_id`, or holds a privileged role (DAO / RefundOperator). This mirrors the pattern already used for `reject_refund`.

Additionally, consider adding an admin function to remove a specific key from `verified_deposit_utxo` (guarded by DAO role) so that operator intervention can fully restore the victim's ability to create a new refund request.

---

### Proof of Concept

```
// Setup: alice has a refund request with elapsed timelock.
// attacker (bob) has one free pending-sign slot.

// 1. Bob calls execute_refund for alice's UTXO.
//    Precondition: timelock elapsed, bob has pending capacity.
bob.execute_refund(alice_utxo_key)
// → succeeds; BTCPendingInfo created with account_id = bob
// → verified_deposit_utxo now contains alice_utxo_key
// → refund_requests[alice_utxo_key].executed = true

// 2. Bob does NOT sign.

// 3. Alice retries execute_refund.
alice.execute_refund(alice_utxo_key)
// → finalize_refund_with_psbt tries to insert same btc_pending_id
// → PANIC: "pending info already exist"

// 4. Alice tries remove_refund_pending_tx_id.
alice.remove_refund_pending_tx_id(bob_pending_id)
// → PANIC: caller is not trusted_relayer

// 5. Alice tries reject_refund.
alice.reject_refund(alice_utxo_key)
// → executed == true → is_already_deposited = false
// → PANIC: "Only DAO/Operator can reject..."

// 6. Operator calls reject_refund + trusted relayer calls remove_refund_pending_tx_id.
//    verified_deposit_utxo still contains alice_utxo_key.
alice.request_refund(...)
// → request_refund_callback: "UTXO already verified via deposit"
// Alice's BTC remains locked.
```

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub(crate) fn load_refund_request_for_execute(
        &self,
        utxo_storage_key: &str,
        timelock_sec: u64,
    ) -> RefundRequest {
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();

        let now = nano_to_sec(env::block_timestamp());
        require!(
            u64::from(now) >= u64::from(refund_request.created_at_sec) + timelock_sec,
            "Refund timelock has not passed yet"
        );

        // Block only if the UTXO was claimed by a deposit. If it was claimed by
        // our own refund (executed == true, which also set verified_deposit_utxo),
        // re-running execute_refund is allowed — re-creating the refund tx, e.g.
        // after a consensus branch change.
        require!(
            !self.data().verified_deposit_utxo.contains(utxo_storage_key)
                || refund_request.executed,
            "UTXO already verified via deposit, cannot refund"
        );

        refund_request
    }
