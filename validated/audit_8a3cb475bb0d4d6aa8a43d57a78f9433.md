### Title
`execute_refund` Re-execution Deadlock When Old `BTCPendingInfo` Still Exists — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

The code explicitly documents that `execute_refund` must be re-callable when `executed == true` (e.g., after a consensus branch change). However, `finalize_refund_with_psbt` unconditionally panics if a `BTCPendingInfo` with the same deterministic `btc_pending_id` already exists. Because the `btc_pending_id` is the Bitcoin txid of the unsigned refund transaction — derived entirely from the deposit UTXO outpoint and the refund output, both of which are fixed by the refund request — re-execution always produces the same id. If the first refund transaction was never confirmed and its `BTCPendingInfo` was never cleaned up, every subsequent `execute_refund` call panics, and `remove_refund_pending_tx_id` also fails because the refund request is still present. The result is a permanent stuck state.

---

### Finding Description

**Step 1 — `execute_refund` is public and re-entry is explicitly intended.**

`execute_refund` carries no `#[trusted_relayer]` or `#[access_control_any]` guard; any account can call it. [1](#0-0) 

**Step 2 — `load_refund_request_for_execute` passes on re-execution.**

The guard that blocks re-execution is `!verified_deposit_utxo.contains(key) || refund_request.executed`. When `executed == true` the `|| refund_request.executed` branch short-circuits the check, so the call proceeds regardless of whether the UTXO is already in `verified_deposit_utxo`. [2](#0-1) 

**Step 3 — The `btc_pending_id` is deterministic.**

`get_pending_id()` computes the Bitcoin txid of the *unsigned* transaction, which is built from the fixed deposit outpoint and the fixed refund output. For the same refund request, every call to `internal_execute_refund` produces the identical `btc_pending_id`. [3](#0-2) [4](#0-3) 

**Step 4 — `finalize_refund_with_psbt` panics if the old entry exists.**

The `require!` on `insert(...).is_none()` panics with `"pending info already exist"` when the old `BTCPendingInfo` (from the first execution) is still present. [5](#0-4) 

**Step 5 — `remove_refund_pending_tx_id` is also blocked.**

`internal_remove_refund_pending_tx_id` requires the refund request to be absent before it will remove the pending info. Because the request is kept alive (with `executed = true`) until `verify_refund_finalize` succeeds, this call always fails with `"refund request still active"`. [6](#0-5) 

**Step 6 — `verify_refund_finalize` cannot help.**

`verify_refund_finalize` requires the pending info to be in `PendingVerify` stage and the transaction to be confirmed on-chain. If the first refund tx was never confirmed (low fee, reorg, etc.) the light-client proof will be rejected, so this path is also closed. [7](#0-6) 

**Step 7 — The UTXO is permanently locked in `verified_deposit_utxo`.**

`finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo` during the *first* successful execution. `request_refund_callback` blocks any new refund request for a UTXO already in that set, so even after operator intervention the user cannot re-submit a refund. [8](#0-7) [9](#0-8) 

---

### Impact Explanation

The deposit UTXO is locked in `verified_deposit_utxo` (blocking `verify_deposit`), the old `BTCPendingInfo` is stuck (blocking `remove_refund_pending_tx_id`), and `execute_refund` panics on every re-attempt. The only escape is DAO/Operator calling `reject_refund` followed by `remove_refund_pending_tx_id`. However, `reject_refund` does not remove the UTXO from `verified_deposit_utxo`, so after operator cleanup the user still cannot submit a new refund request — their BTC is permanently unrecoverable. This matches **Medium** (stuck bridge state requiring operator intervention) escalating to **Critical** (permanent locking of user funds) if the operator attempts the natural recovery path. [10](#0-9) 

---

### Likelihood Explanation

The precondition — a refund transaction that was signed and broadcast but never confirmed — is a normal operational scenario (mempool congestion, fee too low, chain reorg). The code comment on `RefundRequest.executed` explicitly anticipates re-execution after a branch change, confirming this is an expected operational path, not an edge case. [11](#0-10) 

---

### Recommendation

Before inserting the new `BTCPendingInfo` in `finalize_refund_with_psbt`, check whether an entry with the same `btc_pending_id` already exists and, if so, remove it (along with its account-level tracking) before inserting the replacement. Alternatively, remove the old pending info at the start of `internal_execute_refund` when `refund_request.executed == true`. Either approach restores the documented re-execution invariant without changing the external API. [12](#0-11)

### Proof of Concept

```
State setup
───────────
1. request_refund(utxo_key, ...) → refund_requests[utxo_key] = {executed: false, ...}

2. execute_refund(utxo_key)
   → load_refund_request_for_execute: passes (executed=false, timelock elapsed)
   → builds PSBT with outpoint=(deposit_txid, vout), output=(refund_addr, refund_amount)
   → btc_pending_id = txid(unsigned_tx)  ← deterministic, call it X
   → btc_pending_infos[X] = BTCPendingInfo{state: Refund(PendingSign)}
   → verified_deposit_utxo.insert(utxo_key)
   → refund_requests[utxo_key].executed = true

3. Refund tx X is signed and broadcast but never confirmed on-chain.
   btc_pending_infos[X] remains (PendingSign or PendingVerify).

Attack / stuck-state trigger
─────────────────────────────
4. execute_refund(utxo_key)  ← anyone can call; no role guard
   → load_refund_request_for_execute:
       !verified_deposit_utxo.contains(utxo_key) || executed
       = false || true  → PASSES
   → builds identical PSBT → same btc_pending_id X
   → finalize_refund_with_psbt:
       btc_pending_infos.insert(X, ...).is_none()
       = Some(old_entry).is_none() = false
       → require! PANICS: "pending info already exist"

5. remove_refund_pending_tx_id(X)  ← trusted relayer
   → refund_requests.contains_key(utxo_key) = true
   → require! PANICS: "refund request still active"

6. verify_refund_finalize(X, proof)
   → light-client rejects proof (tx not on-chain)
   → FAILS

Result: execute_refund, remove_refund_pending_tx_id, and verify_refund_finalize
all fail. The UTXO is permanently in verified_deposit_utxo. User BTC is locked.
```

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
