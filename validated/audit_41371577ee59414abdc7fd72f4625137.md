### Title
`max_change_amount` Upper-Bound Not Enforced When `input_num <= change_num` in Withdrawal PSBT Validation — (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

In `check_withdraw_psbt`, the `max_change_amount` cap on change outputs is guarded by `if input_num > change_num`. When `input_num <= change_num` — a condition reachable by any unprivileged withdrawer — the only upper bound on each change output is `min_input_amount - 1`. If the bridge holds large UTXOs, this can be orders of magnitude above `max_change_amount`, violating the UTXO-management policy.

---

### Finding Description

The withdrawal entrypoint is the public NEP-141 `ft_on_transfer` callback: [1](#0-0) 

Any holder of nBTC can call it by transferring tokens with a `Withdraw` message that includes attacker-controlled `input` (UTXOs to spend) and `output` (transaction outputs). The call chain is:

`ft_on_transfer` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`

Inside `check_withdraw_psbt`, each change output is validated per-output with only two checks: [2](#0-1) 

- `output_value >= config.min_change_amount`
- `output_value < min_input_amount` (or caller has `UnrestrictedRelayer`)

There is **no per-output `max_change_amount` check here**. The only place `max_change_amount` is enforced is: [3](#0-2) 

This block is **entirely skipped** when `input_num <= change_num`.

The passive-management guard in `check_withdraw_psbt_valid` does not close this gap: [4](#0-3) 

- When `utxo_num` is in the normal range (between `passive_management_lower_limit` and `passive_management_upper_limit`), there is **no constraint** on the relationship between `input_num` and `change_num`, so `input_num <= change_num` is freely reachable.
- When `utxo_num < passive_management_lower_limit`, the requirement is `input_num < change_num`, which is a strict subset of `input_num <= change_num` — the bypass still applies.

---

### Impact Explanation

The change outputs go to the bridge's own `withdraw_change_address_script_pubkey`. No funds are stolen from users. However, the bridge's UTXO set can be populated with UTXOs whose value exceeds `max_change_amount` by an arbitrary margin (up to `min_input_amount - 1`). This directly violates the UTXO-management policy whose purpose is to keep individual UTXOs within a manageable size range for future withdrawals and active/passive management operations. [5](#0-4) 

Oversized UTXOs can disrupt the active/passive management thresholds and make it harder or impossible to satisfy future PSBT construction constraints, potentially causing operational degradation or stuck-state conditions requiring operator intervention.

---

### Likelihood Explanation

The path is fully public (any nBTC holder), requires no privileged role, and is reachable whenever the bridge's UTXO count is in the normal operating range. The attacker only needs to construct a PSBT with `input_num <= change_num` and set a change output above `max_change_amount` but below `min_input_amount`. If the bridge holds UTXOs of, say, 1 BTC and `max_change_amount` is 0.01 BTC, the window is wide.

---

### Recommendation

Move the `max_change_amount` check out of the `if input_num > change_num` branch and apply it unconditionally to every change output inside the per-output loop (alongside the existing `min_change_amount` check). The conditional branch should only control the error message or additional policy, not whether the cap is enforced at all.

---

### Proof of Concept

1. Bridge has `utxo_num` in the normal range (between `passive_management_lower_limit` and `passive_management_upper_limit`).
2. Bridge holds one UTXO of value `V` where `V > max_change_amount` (e.g., `V = 1 BTC`, `max_change_amount = 1_000_000 sat`).
3. Attacker transfers nBTC to the bridge with a `Withdraw` message:
   - `input`: `[that_utxo]` → `input_num = 1`
   - `output`: `[user_output, change_output_1, change_output_2]` where each `change_output_i = max_change_amount + 1` (but `< V`) → `change_num = 2`
4. Since `input_num (1) <= change_num (2)`, the `if input_num > change_num` block at lines 227–237 is skipped.
5. Per-output checks pass: each change output `>= min_change_amount` and `< min_input_amount (V)`.
6. Gas fee and user output checks pass with appropriate values.
7. PSBT is accepted; bridge's UTXO set now contains two UTXOs each exceeding `max_change_amount`, violating the policy. [6](#0-5)

    fn ft_on_transfer(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        msg: String,
    ) -> PromiseOrValue<U128> {
        let amount = amount.into();
        require!(
            amount >= self.internal_config().min_withdraw_amount,
            "Invalid amount"
        );
        let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
        let token_id = env::predecessor_account_id();
        require!(
            token_id == self.internal_config().nbtc_account_id,
            "Invalid token_id"
        );
        match message {
            TokenReceiverMessage::DepositProtocolFee => {
                self.data_mut().acc_collected_protocol_fee += amount;
                self.data_mut().cur_available_protocol_fee += amount;
                Event::DepositProtocolFee {
                    account_id: &sender_id,
                    amount: U128(amount),
                }
                .emit();
                PromiseOrValue::Value(U128(0))
            }
            TokenReceiverMessage::Withdraw {
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            } => self.ft_on_transfer_withdraw_chain_specific(
                sender_id,
                amount,
                target_btc_address,
                input,
                output,
                max_gas_fee,
                chain_specific_data,
            ),
        }
    }
