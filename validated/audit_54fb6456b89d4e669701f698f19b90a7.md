### Title
`checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot`, Disabling Peras Weight-Based Chain Preference Check Beyond the Forecast Horizon — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client is supposed to decide whether to disconnect from a peer whose headers are beyond the forecast horizon by comparing the peer's candidate chain against the node's current selection. When Peras is active, this comparison must account for Peras weight boosts. Instead, the function hardcodes `emptyPerasWeightSnapshot` — an always-empty weight map — as the weight argument to `preferAnchoredCandidate`. This is structurally identical to the reported bug: a check is performed against the wrong entity (an empty placeholder instead of the real state), silently disabling the Peras weight mechanism for this code path.

---

### Finding Description

In `ChainSync/Client.hs`, the function `checkPreferTheirsOverOurs` is invoked when an incoming header is beyond the forecast horizon and the node cannot yet validate it. Its purpose is to avoid wasting resources on a candidate chain the node will never adopt: if the peer's chain is not preferred over the node's current selection, the client disconnects with `CandidateTooSparse`. [1](#0-0) 

The critical lines are:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always-empty, ignores real Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

`emptyPerasWeightSnapshot` is a constant `PerasWeightSnapshot` wrapping an empty `Map`: [2](#0-1) 

When `preferAnchoredCandidate` receives an empty weight snapshot, it takes the `isEmptyPerasWeightSnapshot` fast path and compares chains purely by block number (chain length), ignoring all Peras weight boosts: [3](#0-2) 

The real Peras weight snapshot is available from the ChainDB via `getPerasWeightSnapshot` and is correctly used in every other chain-selection call site (e.g., `initialChainSelection`, `chainSelEnv`, and the GSM's `getCandidateOverSelection`): [4](#0-3) [5](#0-4) 

`checkPreferTheirsOverOurs` is the sole call site that substitutes the real snapshot with the empty constant.

---

### Impact Explanation

When Peras is active, the canonical chain is selected by **total weight** = block count + Peras certificate weight boosts. A scenario where the canonical chain is heavier due to Peras boosts but shorter in raw block count is the normal operating condition Peras is designed for.

In that scenario:

1. A peer serves headers from the canonical (Peras-heavier, block-count-shorter) chain that extend beyond the forecast horizon.
2. `checkPreferTheirsOverOurs` compares the peer's fragment against the node's current selection using only block count (because `emptyPerasWeightSnapshot` zeroes out all boosts).
3. The canonical chain appears shorter, so `preferAnchoredCandidate` returns `ShouldNotSwitch`.
4. The node throws `CandidateTooSparse` and disconnects from the honest peer.
5. Simultaneously, a peer serving a non-canonical chain that is longer in block count but lighter in Peras weight passes the same check and is retained.
6. The node remains connected to the non-canonical peer and may adopt the non-canonical chain.

This is a **chain selection error**: an honest node is made to prefer a non-canonical, less-secure chain over the canonical Peras-weighted chain, directly violating the security guarantees Peras is intended to provide.

**Impact: High** — matches "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

- Peras is an active development target in this codebase; the `PerasCertDB`, `PerasWeightSnapshot`, and all associated chain-selection machinery are production code.
- The bug is triggered by the ordinary ChainSync protocol: any peer can send headers beyond the forecast horizon, which is a routine occurrence during bulk sync or when the node is slightly behind.
- No special privileges, keys, or stake are required. An adversary needs only to serve a chain that is longer in block count than the canonical chain — a standard eclipse/long-range attack vector that Peras weight boosts are specifically designed to defeat.
- The TODO comment (`// TODO: remove this entire check`) confirms the developers are aware the check is incorrect but have not yet removed or fixed it.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` with the actual Peras weight snapshot obtained from the ChainDB, consistent with every other chain-selection call site:

```haskell
-- Before (broken):
preferAnchoredCandidate (configBlock cfg) emptyPerasWeightSnapshot ourFrag theirFrag

-- After (correct):
weights <- getPerasWeightSnapshot chainDbView
preferAnchoredCandidate (configBlock cfg) (forgetFingerprint weights) ourFrag theirFrag
```

Alternatively, if the intent of the TODO is to remove the check entirely (as the linked issue suggests), the entire `checkPreferTheirsOverOurs` guard should be deleted so that the node never disconnects from a peer solely because its beyond-horizon fragment appears shorter by block count. [6](#0-5)

### Proof of Concept

**Setup**: Peras is active. The canonical chain `C` has 100 blocks and 50 units of Peras weight boost (total weight 150). The adversary's chain `A` has 110 blocks and 0 Peras weight (total weight 110). The node's current selection is `C` up to block 90 (within the forecast horizon). The adversary serves headers for `A` starting at block 91, which is beyond the forecast horizon.

**Trace**:

1. ChainSync client receives header 91 from the adversary's peer. It is beyond the forecast horizon.
2. `checkPreferTheirsOverOurs` is called with `ourFrag = C[0..90]`, `theirFrag = A[0..110]`.
3. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers: `A` tip block 110 > `C` tip block 90 → `ShouldSwitch`. The adversary's peer is retained.
4. ChainSync client receives header 91 from an honest peer serving `C`. It is also beyond the forecast horizon.
5. `checkPreferTheirsOverOurs` is called with `ourFrag = C[0..90]`, `theirFrag = C[0..100]`.
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers: `C` tip block 100 > `C` tip block 90 → `ShouldSwitch`. The honest peer is also retained — **so far so good**.

**The dangerous case** (Peras weight causes canonical chain to be shorter):

Suppose the canonical chain `C` has 95 blocks + 60 Peras weight (total 155) and the adversary's chain `A` has 105 blocks + 0 Peras weight (total 105). The node's selection is at block 90.

1. Honest peer serves `C[91..95]` beyond the forecast horizon.
2. `checkPreferTheirsOverOurs`: block 95 < block 90 is false, but block 95 > block 90 → `ShouldSwitch`. Honest peer retained. *(Still OK here.)*

Now suppose the node's current selection is already at `A[0..100]` (adopted before Peras boosts were computed). The honest peer now serves `C[91..95]`:

1. `checkPreferTheirsOverOurs`: `ourFrag` tip = block 100, `theirFrag` tip = block 95. Block 95 < block 100 → `ShouldNotSwitch` → `throwSTM CandidateTooSparse`.
2. The honest peer serving the canonical Peras-heavier chain is disconnected.
3. The node remains on the adversary's lighter chain `A`, which has more blocks but less total weight.
4. With the real weights, `C` (total weight 155) > `A` (total weight 105) → the node should have switched to `C`. The bug prevents this. [7](#0-6) [2](#0-1) [8](#0-7)

          (Empty ourAnchor, _ :> theirTip) ->
