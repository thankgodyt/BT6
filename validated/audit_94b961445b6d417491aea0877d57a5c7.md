### Title
Peras Certificate BLS Aggregate Signature Verification Absent Before Acceptance into Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

Peras certificates received from peers via the `PerasCertDiffusion` mini-protocol are accepted and stored in the `PerasCertDB` — and subsequently used to boost blocks in chain selection — without performing BLS aggregate signature verification. The `implAddCert` function carries an explicit TODO acknowledging that "non-trivial validation logic" is not yet implemented. The `Cert/V1.hs` module explicitly states that deserialization validation is minimal and defers all cryptographic checks. An unprivileged peer can send a crafted `PerasCert` with a forged BLS aggregate signature to boost an arbitrary block, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — three converging gaps:**

**Gap 1 — Serialization explicitly defers cryptographic checks.**
`Ouroboros/Consensus/Peras/Cert/V1.hs` carries a module-level note:

> "NOTE: the validation performed during serialization is minimal, and does not cover any of additional semantic and cryptographic checks that must be performed on the certificate later on." [1](#0-0) 

The `FromCBOR PerasCert` instance decodes `pcRoundNo`, `pcBoostedBlock`, `pcVoters`, and `pcSignature` (the BLS aggregate signature) purely structurally — no signature verification is performed. [2](#0-1) 

**Gap 2 — `implAddCert` has an explicit TODO for the missing validation.**
The `PerasCertDB` implementation's `implAddCert` function, which is the final write gate before a certificate is stored and its boost weight applied, carries:

```
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
``` [3](#0-2) 

The function proceeds to insert the certificate unconditionally (subject only to a duplicate-round-number check), with no BLS verification.

**Gap 3 — `processCerts` delegates to the degenerate placeholder `validatePerasCert`.**
The inbound diffusion path calls `processCerts` with `validatePerasCert mkPerasParams` as the validation callback: [4](#0-3) 

`validatePerasCert` is defined in the `BlockSupportsPeras` type class. The only active instance is the degenerate placeholder:

```
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
``` [5](#0-4) 

This degenerate instance's `data PerasCert blk` does not even carry a signature field, confirming that no BLS verification is possible through this path.

**End-to-end exploit path:**

1. Attacker connects as a peer and speaks the `PerasCertDiffusion` mini-protocol.
2. Attacker sends a `PerasCert` with `pcBoostedBlock` pointing to an attacker-controlled (or minority) block and a fabricated `pcSignature`.
3. The inbound handler calls `processCerts` → `validatePerasCert` (degenerate no-op) → `addPerasCertAsync` → `chainSelSync` → `implAddCert`.
4. The certificate is stored in `PerasCertDB` and its boost weight is applied via `implGetWeightSnapshot`.
5. `chainSelectionForBlock` is triggered for the boosted block; the node may switch to the attacker's chain. [6](#0-5) 

---

### Impact Explanation

A malicious peer with no privileged access can forge a Peras certificate for any block hash and round number. Because the BLS aggregate signature (`pcSignature`) is never verified, the forged certificate is indistinguishable from a legitimate one. The certificate's boost weight is applied in chain selection, potentially causing the honest node to prefer a non-canonical chain. This is a **bypass of Peras certificate/signature validation that enables unauthorized certificate acceptance and chain selection manipulation** — matching the Critical/High impact tier.

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is wired into the production node-to-node stack. Any peer that can establish a connection can submit certificates. No stake, keys, or operator access are required. The degenerate instance and the TODO in `implAddCert` confirm the missing check is not a conditional feature flag but an unimplemented code path present in the production binary.

---

### Recommendation

1. Implement BLS aggregate signature verification in `validatePerasCert` for the concrete Cardano/Peras instance before the `PerasCertDiffusion` protocol is activated on any network. The cryptographic primitives (`verifyAggregateVoteSignature`, `batchVerifyVRFOutputs`) are already defined in `Ouroboros/Consensus/Peras/Crypto/BLS.hs` and `Ouroboros/Consensus/Committee/Crypto/BLS.hs`.
2. Remove the degenerate `BlockSupportsPeras` instance or gate it behind a compile-time flag that cannot be used in production builds.
3. Resolve the TODO in `implAddCert` (`PerasCertDB/Impl.hs:167`) before enabling the protocol on any live network.
4. Add a property test asserting that a certificate with an invalid BLS signature is rejected by `processCerts`.

---

### Proof of Concept

**Deterministic reasoning (no live network required):**

1. Construct a `PerasCert` CBOR payload with:
   - `pcRoundNo`: any valid round number not yet in the node's `PerasCertDB`
   - `pcBoostedBlock`: the `RealPoint` of a minority-chain block
   - `pcVoters`: a minimal valid bitmap (one voter bit set, empty non-persistent list)
   - `pcSignature`: 48 zero bytes (invalid BLS point)

2. Send this payload via the `PerasCertDiffusion` inbound protocol.

3. Observe: `processCerts` calls `validatePerasCert mkPerasParams` (degenerate instance, returns `Right` unconditionally), then calls `addPerasCertAsync`. `implAddCert` inserts the certificate without any signature check (confirmed by the TODO at line 167 of `PerasCertDB/Impl.hs`).

4. `chainSelSync` triggers `chainSelectionForBlock` for the boosted block. If the boosted block's chain weight plus the Peras boost exceeds the current selection's weight, the node switches chains.

5. The forged certificate is now stored in `PerasCertDB` and its boost weight persists across subsequent chain selection rounds.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
