### Title
Missing High-S Normalization in MPC Signature Conversion Produces Invalid Bitcoin/Zcash Transactions - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
`SignatureResponse::to_btc_signature()` converts the raw ECDSA signature returned by the NEAR Chain Signatures MPC service into a Bitcoin `Signature` without normalizing the `s` scalar to the lower half of the secp256k1 curve. Bitcoin (BIP66/BIP141) and Zcash require low-s signatures in all script paths. A high-s signature causes the constructed transaction to be rejected by every network node, permanently stalling the withdrawal and locking the user's nBTC inside the bridge contract with no self-service recovery path.

### Finding Description

`SignatureResponse::to_btc_signature()` assembles the compact `(r, s)` bytes from the MPC response and passes them directly to `bitcoin::secp256k1::ecdsa::Signature::from_compact()`:

```rust
// chain_signature.rs L41-L49
pub fn to_btc_signature(&self) -> Signature {
    let r_hex = self.big_r.affine_point[2..].to_string();
    let s_hex = self.s.scalar.clone();
    let r = hex::decode(r_hex).expect("Invalid r hex");
    let s = hex::decode(s_hex).expect("Invalid s hex");
    let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
        .expect("Invalid signature");
    Signature::sighash_all(signature)
}
```

`from_compact` accepts any `s ∈ [1, n-1]`; it does **not** enforce `s ≤ n/2`. A grep across the entire production codebase confirms there is no call to `normalize_s()` anywhere.

This converted signature is consumed in two places without any intervening check:

**Bitcoin path** — `bitcoin_utils/psbt_wrapper.rs` L162-L163:
```rust
self.psbt.inputs[sign_index].final_script_witness =
    Some(Witness::p2wpkh(&signature.to_btc_signature(), &public_key));
```

**Zcash path** — `zcash_utils/psbt_wrapper.rs` L492-L493:
```rust
let script_sig = bitcoin::script::Builder::new()
    .push_slice(signature.to_btc_signature().serialize())
```

Both paths are reached from `sign_btc_transaction_callback` in `chain_signature.rs` L168:
```rust
psbt.save_signature(sign_index, signature, public_key);
```

The NEAR Chain Signatures MPC service returns raw secp256k1 ECDSA scalars and does not guarantee that `s` is in the lower half of the curve order. Approximately half of all signing outputs will have `s > n/2`.

### Impact Explanation

When the MPC service returns a high-s signature the bridge stores the malformed transaction bytes in `btc_pending_info.tx_bytes_with_sign` and advances the state to `PendingVerify`. The signed transaction is broadcast (via the `SignedBtcTransaction` event) but every Bitcoin/Zcash full node rejects it because BIP66 (DER encoding) and BIP141/BIP146 (segwit script validation) mandate low-s. The transaction never confirms. The relayer cannot call `verify_withdraw` successfully, so the bridge never reaches the burn step. The user's nBTC tokens were already transferred to the bridge at the start of the withdrawal (`ft_transfer_call`) and are now permanently locked inside it. Recovery requires privileged operator intervention to construct and sign a replacement transaction — a stuck bridge state matching the Medium impact tier.

### Likelihood Explanation

Any user initiating a standard withdrawal triggers the MPC signing path. The NEAR Chain Signatures service returns raw ECDSA signatures with no low-s guarantee; statistically ~50 % of signatures will have `s > n/2`. No special attacker capability is required — ordinary bridge usage is sufficient to encounter this condition. The absence of any `normalize_s` call (confirmed by exhaustive grep) means every withdrawal is at risk.

### Recommendation

In `SignatureResponse::to_btc_signature()`, call `normalize_s()` on the parsed signature before wrapping it:

```rust
pub fn to_btc_signature(&self) -> Signature {
    let r = hex::decode(self.big_r.affine_point[2..].to_string()).expect("Invalid r hex");
    let s = hex::decode(self.s.scalar.clone()).expect("Invalid s hex");
    let mut sig = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
        .expect("Invalid signature");
    sig.normalize_s(); // enforce low-s as required by BIP66/BIP141
    Signature::sighash_all(sig)
}
```

This single change covers both the Bitcoin and Zcash paths because both call `to_btc_signature()`.

### Proof of Concept

1. User calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)` — nBTC transferred to bridge.
2. Bridge calls `internal_sign_btc_transaction`, which calls the NEAR Chain Signatures MPC service.
3. MPC returns a `SignatureResponse` where `s > 0x7FFFFFFFFFFFFFFFFFFFFFFFFFFFFFFF5D576E7357A4501DDFE92F46681B20A0` (upper-half s, ~50 % probability).
4. `sign_btc_transaction_callback` calls `psbt.save_signature(...)` → `to_btc_signature()` → `from_compact(r‖s)` with no normalization.
5. `extract_tx_bytes_with_sign()` serializes the transaction with the high-s witness.
6. `SignedBtcTransaction` event is emitted; relayer broadcasts the transaction.
7. Every Bitcoin node rejects the transaction (BIP66 / BIP141 violation).
8. Relayer cannot produce a valid Merkle inclusion proof; `verify_withdraw` always fails.
9. User's nBTC remains locked in the bridge with no self-service recovery.

        &mut self,
        sign_index: usize,
        signature: SignatureResponse,
        public_key: bitcoin::secp256k1::PublicKey,

        let script_sig = bitcoin::script::Builder::new()
            .push_slice(signature.to_btc_signature().serialize())
            .push_key(&bitcoin::PublicKey::new(public_key))
            .into_script();

        let prevout = self.vin[sign_index].prevout().clone();
        let sequence = self.vin[sign_index].sequence();
        self.vin[sign_index] =
            ZcashTxIn::from_parts(prevout, Script(Code(script_sig.to_bytes())), sequence);
    }
