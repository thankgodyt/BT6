### Title
Any Caller Can Submit a Refund Request for Another User's UTXO with an Attacker-Controlled Refund Address — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

`internal_request_refund` (and its callback `request_refund_callback`) contains no check that the caller is the owner of the deposit UTXO being refunded. An unprivileged attacker can submit a refund request for any victim's UTXO, supplying the attacker's own BTC address as the `refund_address`, and after the timelock elapses, execute the refund to steal the victim's BTC.

### Finding Description

`internal_request_refund` accepts a caller-supplied `deposit_msg` and `refund_address`: [1](#0-0) 

The only constraint on `refund_address` is that if `deposit_msg.refund_address` is `Some(...)`, the provided address must match it: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case — users do not always pre-specify a refund address), the caller may supply **any** BTC address as `refund_address` with no restriction.

In `request_refund_callback`, the only integrity check is that the output's `script_pubkey` matches the deposit address derived from `deposit_msg`: [3](#0-2) 

Because `deposit_msg` is embedded in the Bitcoin transaction (publicly visible on-chain), an attacker can reconstruct any victim's `deposit_msg`, pass the script_pubkey check, and register a refund request keyed to the victim's UTXO with the attacker's own `refund_address`: [4](#0-3) 

Once stored, a second refund request for the same UTXO is blocked: [5](#0-4) 

This means the victim cannot submit their own legitimate refund request after the attacker has front-run them.

### Impact Explanation

After `unsafe_refund_timelock_sec` elapses (the longer timelock applied when `deposit_msg.refund_address` is `None`), the attacker calls `execute_refund`, which builds and signs a refund transaction paying the attacker's BTC address. The victim's deposited BTC is permanently redirected to the attacker. This constitutes a **significant theft of user funds** (Critical impact). Even if the DAO rejects the request, the victim's refund is blocked for the entire timelock duration (Medium DoS impact).

### Likelihood Explanation

- `deposit_msg` is public on-chain data embedded in the Bitcoin deposit transaction; any observer can reconstruct it.
- Users who do not pre-specify `deposit_msg.refund_address` (the common case) are fully exposed.
- The only mitigation is the DAO rejecting the request within `unsafe_refund_timelock_sec`. If the DAO is not actively monitoring, the attack succeeds silently.
- No special privileges, leaked keys, or third-party compromise are required — only a standard NEAR account.

### Recommendation

Add an ownership check in the public `request_refund` entry point (in the `api/` layer) or inside `internal_request_refund` to verify that `env::predecessor_account_id()` matches the `receiver_id` embedded in `deposit_msg`. Alternatively, require that `deposit_msg.refund_address` is always pre-set at deposit time and enforce the match unconditionally, removing the ability for a third party to supply an arbitrary `refund_address`.

```rust
// In internal_request_refund, add:
require!(
    env::predecessor_account_id() == deposit_msg.receiver_id,
    "Only the deposit receiver may request a refund"
);
```

### Proof of Concept

1. Alice sends BTC to the bridge, embedding her `deposit_msg` (with `receiver_id = alice.near`, `refund_address = None`) in the transaction.
2. Bob observes Alice's Bitcoin transaction on-chain and extracts her `deposit_msg`.
3. Bob calls `request_refund(deposit_msg = alice_deposit_msg, refund_address = "bob_btc_address", tx_bytes = alice_tx_bytes, vout = 0, proof = ...)` with sufficient attached deposit.
4. `request_refund_callback` verifies the proof and the script_pubkey — both pass because the UTXO genuinely belongs to the address derived from `alice_deposit_msg`.
5. The refund request is stored with `refund_address = "bob_btc_address"`.
6. Alice attempts to call `request_refund` for the same UTXO — it panics with "Refund request already exists for this UTXO".
7. After `unsafe_refund_timelock_sec`, Bob calls `execute_refund`, which builds a refund transaction paying Bob's BTC address and requests an MPC signature.
8. Alice's BTC is sent to Bob. [5](#0-4) [6](#0-5)

    /// elapse before this refund can be executed. Shared by the Bitcoin and
    /// Zcash `execute_refund` entrypoints.
    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
