Audit Report

## Title
Unchecked `.detach()` on Relayer Repayment in Fast-Transfer Finalization Causes Permanent Fund Loss and Escrow Mis-accounting — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge repays a fast-transfer relayer via `send_tokens(...).detach()` — a fire-and-forget cross-contract call with no callback. All state mutations (decrementing `locked_tokens`, marking the fast transfer and inbound transfer as finalised) are committed before the call and are never reverted if the call fails. A failed token transfer permanently destroys the relayer's pre-paid funds and leaves `locked_tokens` permanently under-counted, freezing the corresponding surplus tokens inside the bridge contract with no recovery path.

## Finding Description

**`process_fin_transfer_to_other_chain` (lines 1980–2054)**

The function commits the following state mutations unconditionally before the fire-and-forget call:

1. `add_fin_transfer(...)` — inserts the inbound transfer ID into `finalised_transfers` (irreversible; re-submission panics with `TransferAlreadyFinalised`). [1](#0-0) 

2. `unlock_tokens_if_needed(origin_chain, token, amount)` — decrements `locked_tokens[(origin_chain, token)]` by the full transfer amount. [2](#0-1) 

3. `send_tokens(...).detach()` — schedules `ft_transfer` (or `mint`) to the relayer with no result inspection. [3](#0-2) 

4. `mark_fast_transfer_as_finalised(...)` — sets `finalised = true` on the fast-transfer entry (irreversible; re-finalisation panics with `FastTransferAlreadyFinalised`). [4](#0-3) 

If `send_tokens` fails (e.g., `ft_transfer` panics because the relayer has no storage registration for the token), all four mutations remain committed. The relayer never receives repayment, and `locked_tokens` is permanently under-counted by `amount_without_fee`.

**`utxo_fin_transfer_fast` (lines 2518–2548)**

The identical pattern appears in the UTXO fast-transfer path. The code carries an explicit developer acknowledgment of the unresolved failure case: [5](#0-4) 

Inside `utxo_fin_transfer_fast`, `mark_fast_transfer_as_finalised` (or `remove_fast_transfer` for NEAR-destined) is called before `send_tokens(...).detach()`: [6](#0-5) 

**Contrast with the correctly handled path**

`process_fin_transfer_to_near` uses `.then(callback)` chaining `fin_transfer_send_tokens_callback`, which on failure calls `revert_lock_actions`, `remove_fin_transfer`, and emits a `FailedFinTransferEvent`: [7](#0-6) [8](#0-7) 

The other-chain and UTXO fast-transfer paths have no equivalent recovery.

**Why `send_tokens` can fail**

For non-deployed (native) tokens with an empty `msg`, `send_tokens` dispatches `ft_transfer`. `ft_transfer` panics if the recipient account has no storage registration for that token contract: [9](#0-8) 

A relayer that has not called `storage_deposit` on the specific bridged token contract before being used as a fast-transfer relayer will trigger this failure silently.

**Why the escrow mis-accounting is permanent**

`unlock_tokens` enforces `available >= amount` before decrementing. After a silent failure, `locked_tokens[(origin_chain, token)]` is under-counted. Any future legitimate `unlock_tokens` call for the full amount will hit the `InsufficientLockedTokens` guard and revert, permanently freezing the surplus tokens inside the bridge: [10](#0-9) 

## Impact Explanation

This is a **Critical** impact matching two allowed scopes:

- **Permanent loss of bridged funds**: The relayer pre-paid `amount_without_fee` tokens to the user on the destination chain. If `send_tokens` fails silently, the relayer never receives repayment from the bridge escrow. The tokens remain physically inside the bridge contract but are unaccounted for.
- **Escrow mis-accounting / permanent token freeze**: `locked_tokens[(origin_chain, token)]` is decremented without a corresponding actual outflow. The surplus tokens are permanently frozen inside the bridge with no administrative recovery path, as there is no function to re-increment `locked_tokens` for an already-finalised transfer.

## Likelihood Explanation

The failure condition — `ft_transfer` panicking due to missing storage registration — is a standard, well-known NEAR failure mode. Any relayer account that has not explicitly called `storage_deposit` on the specific token contract will trigger it. The UTXO path carries a developer `// TODO` comment confirming the team is aware the scenario is reachable. The fast-transfer feature is a live, publicly accessible code path reachable by any registered relayer. The failure can also occur for deployed tokens if the `mint` call fails (e.g., paused token contract). The condition is not exotic and requires no attacker — it can be triggered accidentally by a legitimate relayer.

## Recommendation

Mirror the pattern used in `process_fin_transfer_to_near`: replace `.detach()` with `.then(callback)` in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`. The callback should, on failure:
1. Re-increment `locked_tokens[(origin_chain, token)]` by the amount that was decremented.
2. Un-mark the fast transfer as finalised (or re-insert it if it was removed).
3. Remove the inbound transfer from `finalised_transfers` (or keep it and allow retry).

Alternatively, perform all state mutations only inside the success branch of the callback, keeping the pre-call state intact until the cross-contract call result is confirmed.

## Proof of Concept

1. Trusted relayer `R` registers as a fast-transfer relayer and calls `ft_transfer_call` on a non-deployed (native) token with a `FastFinTransferMsg` targeting a non-NEAR destination. `R` has **not** called `storage_deposit` on the token contract for its own account.
2. `fast_fin_transfer_to_other_chain` runs: `add_fast_transfer`, `burn_tokens_if_needed`, `lock_tokens_if_needed`, `add_transfer_message` all commit to state. `locked_tokens[(origin_chain, token)]` is incremented.
3. A separate relayer submits the finalization proof via `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_other_chain`.
4. `add_fin_transfer` inserts the transfer ID into `finalised_transfers`. `unlock_tokens_if_needed` decrements `locked_tokens[(origin_chain, token)]` by `amount`. `send_tokens(token, R, amount_without_fee, "").detach()` fires `ft_transfer` to `R`. `mark_fast_transfer_as_finalised` sets `finalised = true`.
5. `ft_transfer` panics: `R` has no storage registration. The panic is silently swallowed because `.detach()` discards the result.
6. `R` never receives tokens. `locked_tokens` is permanently under-counted by `amount_without_fee`. The fast transfer entry is permanently `finalised = true`. The inbound transfer is permanently in `finalised_transfers`. Any future `unlock_tokens` call for the full legitimate amount hits `InsufficientLockedTokens` and reverts. No recovery is possible.
