### Title
Peras Vote Signature Message Hash Lacks Explicit Network Context, Enabling Cross-Network Replay — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function, which produces the message hash for all Peras BLS vote signatures and aggregate certificate signatures, does not include any network-specific identifier (network magic, genesis hash, or chain ID) in the hashed content. The `KeyScope` mechanism that was designed to carry a network identifier is documented as "later instantiated with usage and network id (e.g. PERAS/MAINNET)" but its actual enforcement is not present in the production signing path. A valid Peras vote or certificate signature produced on one Cardano network can therefore be presented verbatim on a second network that shares any block in its history, bypassing Peras vote/certificate verification.

---

### Finding Description

`hashVoteSignature` constructs the 48-byte message that every Peras committee member signs and that every verifier checks:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
```

The three fields encoded are: the Peras round number (8 bytes), the slot of the boosted block (8 bytes), and the 32-byte block hash. No network magic, genesis hash, or any other chain-discriminating value is included. [1](#0-0) 

This same hash is used in three places:

- `signVote` / `verifyVoteSignature` (individual vote path)
- `verifyAggregateVoteSignature` (certificate path) [2](#0-1) [3](#0-2) 

The BLS signing layer does carry a `KeyScope` field that is augmented into the BLS context:

```haskell
instance HasBLSContext SIGN where
  blsCtx _ keyScope =
    minSigSignatureDST { blsSignContextAug = Just ("VOTE:" <> keyScope <> ":V0") }
``` [4](#0-3) 

The comment on `KeyScope` reads: *"Key scope, later instantiated with usage and network id (e.g. PERAS/MAINNET)"*. The word "later" is significant: no production code path in the repository sets this scope to a network-specific value before calling `signWithRole` or `verifyWithRole`. The scope is a property of the deserialized key (`privateKeyScope` / `publicKeyScope`), and `rawDeserialisePrivateKey` / `rawDeserialisePublicKey` accept whatever `ByteString` the caller supplies. [5](#0-4) 

If the scope is empty or a fixed non-network-specific string, the BLS augmentation becomes `"VOTE::V0"` on every network, providing no cross-network discrimination.

---

### Impact Explanation

**Impact class**: Bypass of Peras voting/certificate checks enabling unauthorized vote or certificate acceptance.

A Peras certificate accepted on the wrong network directly affects chain selection: `ValidatedPerasCert` carries a `vpcCertBoost` weight that is added to the boosted block's chain weight, potentially causing an honest node to prefer a chain it should not.

Concrete attack path:
1. Network A (e.g., mainnet) and network B (e.g., a testnet forked from mainnet at block `B`) share block `B` with identical hash.
2. A stake pool operator whose cold key is registered on both networks (common for operators running preview/preprod nodes) participates in Peras on network A and signs a vote for block `B` in round `R`.
3. An adversary captures the `PerasVote` message from the network A gossip layer and replays it verbatim on network B.
4. Network B's `verifyVoteSignature` / `verifyAggregateVoteSignature` recomputes `hashVoteSignature(R, B)` — identical to network A — and the BLS verification passes because the key scope is the same (or empty) on both networks.
5. The replayed vote contributes to a quorum certificate on network B for a block that was legitimately voted for only on network A.

The `processCerts` inbound handler accepts any batch of certificates that pass `validateCert`; a replayed certificate that passes cryptographic verification will be stored and used in chain selection. [6](#0-5) 

---

### Likelihood Explanation

**Medium.** The conditions required are:

- Peras is deployed on at least two Cardano networks simultaneously (mainnet + any testnet).
- At least one stake pool operator registers the same Peras BLS key on both networks (a common operational pattern today for KES/VRF keys).
- The `KeyScope` is not set to a network-discriminating value at key-generation time (the current code provides no enforcement of this).
- Both networks share at least one block hash (guaranteed for any testnet forked from mainnet).
- The Peras round number `R` is the same on both networks at the time of the attack (likely if both networks use the same Peras parameters).

None of these conditions require privileged access, key compromise, or majority stake.

---

### Recommendation

1. **Include network magic in `hashVoteSignature`**: Add the `NetworkMagic` (or genesis hash) as an explicit field in the byte builder, analogous to how Byron's `ContextDSIGN` mandates `ProtocolMagicId`:

```haskell
hashVoteSignature networkMagic roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (4 + 8 + 8 + 32)
    $ networkMagicBytes <> roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
```

2. **Enforce `KeyScope` at key-generation time**: Require that `PerasPrivateKey` / `PerasPublicKey` are always constructed with a scope that encodes the network magic (e.g., `"PERAS/" <> show networkMagic`), and validate that the scope matches the node's configured network magic before any signing or verification operation.

3. **Apply the same fix to `hashVRFInput`**: The VRF election input also omits network context; the epoch nonce provides implicit binding but explicit network context is safer. [7](#0-6)

### Proof of Concept

```
Setup:
  - Network A: mainnet, genesis block G_A, block B at slot 1000 (hash H_B)
  - Network B: testnet forked from mainnet at block B, same H_B
  - Pool P: registered on both networks with the same PerasPrivateKey (scope = "")
  - Both networks: same PerasParams, so round R = slot_to_round(1000) is identical

Step 1 (Network A):
  Pool P calls signVote sk R (PerasBoostedBlock (RealPoint 1000 H_B))
  => sig = BLS.signWithRole @SIGN sk (hashVoteSignature R (RealPoint 1000 H_B))
  => hashVoteSignature = Hash(word64BE(R) || word64BE(1000) || H_B)
  => BLS context aug = "VOTE::V0"  (scope is empty)

Step 2 (Attacker):
  Captures PerasVote { pvRoundNo=R, pvBoostedBlock=RealPoint 1000 H_B,
                       pvSeatIndex=S, pvEligibilityProof=Persistent, pvSignature=sig }
  from Network A's gossip.

Step 3 (Network B):
  Attacker submits the same PerasVote to Network B's object diffusion layer.
  verifyVoteSignature pk R (RealPoint 1000 H_B) sig
  => recomputes hashVoteSignature R (RealPoint 1000 H_B)  -- identical to Network A
  => BLS context aug = "VOTE::V0"                          -- identical to Network A
  => verification PASSES
  => vote is accepted and counted toward quorum on Network B
```

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
