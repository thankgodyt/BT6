### Title
Unauthenticated `request_refund` Allows Any Caller to Front-Run and Redirect BTC Refunds to an Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `request_refund` endpoint in the satoshi-bridge contract performs no check that the caller is the intended deposit recipient (`deposit_msg.recipient_id`). When a deposit's `DepositMsg` carries no pre-authorized `refund_address`, any unprivileged NEAR account can submit a refund request for a victim's stuck UTXO and supply an attacker-controlled Bitcoin address. After the `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and the bridge's MPC pipeline sends the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, payable function with no caller-identity guard beyond the pause check: [1](#0-0) 

The only conditional access check inside the function body is for the optional `gas_fee` parameter (DAO/Operator only). The `deposit_msg.recipient_id` — the NEAR account that should receive nBTC — is never compared against `env::predecessor_account_id()`. [2](#0-1) 

Inside `internal_request_refund`, the `refund_address` parameter is accepted verbatim whenever `deposit_msg.refund_address` is `None`: [3](#0-2) 

The callback verifies only that the transaction output's `script_pubkey` matches the address derived from `deposit_msg` — it does not verify who submitted the request: [4](#0-3) 

A duplicate-request guard exists, but it only prevents a second request for the same UTXO after one is already stored — it does not prevent an attacker from being first: [5](#0-4) 

`execute_refund` is also fully public (no caller restriction), so after the timelock the attacker can trigger the MPC signing pipeline themselves: [6](#0-5) 

The resulting `BTCPendingInfo` records the attacker as the `caller` and the attacker's Bitcoin address as the refund destination: [7](#0-6) 

---

### Impact Explanation

A victim's BTC deposit UTXO — already locked in the bridge's MPC-controlled address — is redirected to an attacker-controlled Bitcoin address. The victim receives neither nBTC (the deposit was never finalized) nor their BTC back (the refund was hijacked). This constitutes a **significant loss of user funds** and maps to the "Critical / significant loss, theft, or permanent locking of user funds" impact class. In practice the `unsafe_refund_timelock_sec` gives the DAO/Operator a window to reject, but the victim has no independent recourse: `reject_refund` is restricted to DAO/Operator, and the victim cannot finalize the deposit themselves (they are not a trusted relayer). [8](#0-7) 

---

### Likelihood Explanation

All inputs the attacker needs are publicly observable:

- The victim's `DepositMsg` is public — it is the pre-image of the deposit address path, derivable from the deposit address itself.
- The BTC transaction bytes and Merkle inclusion proof are on-chain and available to any Bitcoin node.

The attacker does not need to front-run in the traditional mempool sense; they simply need to call `request_refund` before the victim does. Because many users whose deposits fail to finalize may wait days or weeks before attempting a refund, the attacker has a wide window. The anti-spam attached-deposit requirement is a minor deterrent (it is not refunded), but it does not prevent a motivated attacker. [9](#0-8) 

---

### Recommendation

Add a caller-identity check inside `request_refund` (or `internal_request_refund`) that requires `env::predecessor_account_id() == deposit_msg.recipient_id`. Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) so the refund destination is committed at deposit time and cannot be supplied by an arbitrary caller. The analog fix in the referenced MechMarketplace report was to restrict the `create` endpoint to the multisig of the service ID; the equivalent here is to restrict `request_refund` to the deposit's intended recipient.

---

### Proof of Concept

1. Victim sends BTC to the bridge using a `DepositMsg` with `refund_address: None` and `recipient_id: victim.near`. The deposit is never finalized (relayer failure).
2. Attacker observes the Bitcoin transaction on-chain, reconstructs the `DepositMsg` from the deposit address, and obtains the Merkle proof.
3. Attacker calls:
   ```
   request_refund(
     deposit_msg = <victim's DepositMsg>,
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's tx>,
     vout = <victim's vout>,
     proof = <valid Merkle proof>,
     gas_fee = None
   )
   ```
   with the required attached NEAR storage deposit.
4. `request_refund_callback` succeeds: the output `script_pubkey` matches the deposit address derived from the victim's `DepositMsg`; no check on caller identity is performed. A `RefundRequest` is stored with `refund_address = "attacker_btc_address"`.
5. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), the attacker calls `execute_refund(utxo_storage_key)`.
6. The bridge constructs a PSBT spending the victim's deposit UTXO to `"attacker_btc_address"` and submits it to the MPC chain-signatures pipeline. The victim's BTC is sent to the attacker.

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
