Audit Report

## Title
Relayer's Fronted Tokens Permanently Lost When `send_tokens().detach()` Fails During Fast Transfer Finalization - (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge irrevocably commits fast-transfer state before firing the relayer-reimbursement token transfer with `.detach()` and no callback. If the `ft_transfer` promise fails, the relayer who fronted tokens to the user permanently loses those funds with no on-chain recovery path.

## Finding Description

**Path 1 — `process_fin_transfer_to_other_chain`**

At line 1985, `add_fin_transfer` inserts the transfer ID into `finalised_transfers`. [1](#0-0) 

In the fast-transfer branch (lines 2028–2040), `send_tokens(...).detach()` is called with no callback, then `mark_fast_transfer_as_finalised` commits state synchronously. [2](#0-1) 

No entry is added to `pending_transfers` in this branch — only the `else` branch (non-fast-transfer) calls `add_transfer_message`. [3](#0-2) 

**Path 2 — `utxo_fin_transfer_fast`**

When `destination == Near`, `remove_fast_transfer` is called before `send_tokens(...).detach()`. When `destination != Near`, `mark_fast_transfer_as_finalised` is called before the detached send. In both sub-cases, state is committed before the promise executes. [4](#0-3) 

The developers themselves flagged this as unresolved with a TODO comment at the call site. [5](#0-4) 

**Why recovery is impossible after failure:**

- `finalised_transfers` already contains the transfer ID → retry of `fin_transfer` panics with `ERR_TRANSFER_ALREADY_FINALISED` via `add_fin_transfer`. [6](#0-5) 
- The fast transfer is either removed or marked `finalised = true` → re-entry into any fast-transfer finalization path panics with `ERR_FAST_TRANSFER_ALREADY_FINALISED`. [7](#0-6) 
- No pending transfer was inserted → `claim_fee` / `remove_transfer_message` panics with `ERR_TRANSFER_NOT_EXIST`. [8](#0-7) 

Additionally, `send_tokens` always subtracts `SEND_TOKENS_CALLBACK_GAS` from remaining gas even when no callback is registered, potentially leaving insufficient gas for the actual transfer. [9](#0-8) 

## Impact Explanation

A relayer who fronted tokens to a user during a fast transfer permanently loses those tokens if the reimbursement `ft_transfer` fails. The bridge contract holds the tokens but provides no admin escape hatch, no retry function, and no `claim_fee` path applicable to this state. This constitutes **permanent freezing of bridged funds**, matching the Critical impact scope.

## Likelihood Explanation

The `ft_transfer` can fail under realistic conditions reachable by the relayer itself or by external circumstances: (1) the relayer's account lacks a storage deposit for the specific token contract — common for newly deployed bridge tokens; (2) the token contract is paused or temporarily unavailable at the moment `fin_transfer` is processed; (3) insufficient gas forwarded due to the unconditional `SEND_TOKENS_CALLBACK_GAS` subtraction in `send_tokens`. None of these require attacker privileges or unrealistic assumptions. The relayer is a legitimate participant in the bridge protocol.

## Recommendation

Replace `.detach()` with a proper callback in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`. The callback should detect failure and either revert the fast-transfer state (un-finalise / re-insert the record) so the relayer can retry, or store the owed amount in a claimable mapping the relayer can withdraw later. The correct model already exists in `process_fin_transfer_to_near`, which chains `send_tokens` to `fin_transfer_send_tokens_callback` and reverts lock actions on failure. [10](#0-9) 

## Proof of Concept

1. Relayer R executes a fast transfer for cross-chain transfer T (EVM → Solana), fronting tokens to the user on NEAR.
2. R calls `fin_transfer` with the EVM proof; `process_fin_transfer_to_other_chain` is entered.
3. `add_fin_transfer` inserts T into `finalised_transfers` (line 1985).
4. Fast transfer status is found; `send_tokens(token, R, amount, "").detach()` is scheduled (line 2029–2039).
5. `mark_fast_transfer_as_finalised` commits `finalised = true` (line 2040).
6. The detached `ft_transfer` promise fails (e.g., R has no storage deposit for the token).
7. R attempts to retry `fin_transfer` → panics `ERR_TRANSFER_ALREADY_FINALISED` (line 2229).
8. R attempts `claim_fee` → panics `ERR_TRANSFER_NOT_EXIST` (line 2221, no pending transfer was added).
9. R's fronted tokens remain permanently locked in the bridge contract with no recovery path.
