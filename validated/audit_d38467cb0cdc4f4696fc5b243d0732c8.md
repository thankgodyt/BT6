### Title
Accumulated NEAR Anti-Spam Fees From `request_refund` and `execute_refund` Are Permanently Locked With No Withdrawal Path - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/api/view.rs`)

---

### Summary
The `satoshi-bridge` contract collects non-refundable NEAR deposits from any caller of `request_refund` (2 NEAR each) and `execute_refund` (1 NEAR each). These NEAR tokens accumulate in the contract's on-chain balance but there is no function anywhere in the contract to withdraw them. The NEAR is permanently locked, analogous to the reported pattern of a contract that can receive native tokens but provides no withdrawal path.

---

### Finding Description

Two permissionless, `#[payable]` entry points collect mandatory NEAR deposits that are explicitly documented as non-refundable:

**`request_refund`** requires `env::attached_deposit() >= required_balance_for_request_refund()`, which returns a hardcoded **2 NEAR**: [1](#0-0) 

The inline comment states: *"the deposit is NOT refunded — it covers request storage and acts as an anti-spam fee."* The actual storage cost for a normal deposit (1–2 inputs, ~500 bytes) is ~0.005 NEAR, so the overwhelming majority of the 2 NEAR is a pure fee that stays in the contract. [2](#0-1) 

**`execute_refund`** requires `env::attached_deposit() >= required_balance_for_execute_refund()`, which returns a hardcoded **1 NEAR**: [3](#0-2) 

Again, the comment states the deposit is NOT refunded. [4](#0-3) 

Both functions are publicly callable (no role restriction on `request_refund`; `execute_refund` is also permissionless after the timelock): [5](#0-4) [6](#0-5) 

The only NEAR-withdrawal-adjacent function in the contract is `withdraw_protocol_fee`, which operates exclusively on the `cur_available_protocol_fee` field — an nBTC-denominated accounting variable — and calls `internal_withdraw_protocol_fee` for nBTC tokens, not NEAR: [7](#0-6) 

No `withdraw_near`, `transfer_near`, or equivalent function exists anywhere in the production contract surface.



---

### Impact Explanation

Every call to `request_refund` locks 2 NEAR and every call to `execute_refund` locks 1 NEAR permanently inside the contract. Over the operational lifetime of the bridge — especially given that refunds are a permissionless path any NEAR account can trigger — these amounts accumulate with no recovery path for the protocol. The DAO cannot reclaim these funds even via governance. This constitutes permanent locking of protocol-adjacent funds and matches the **Medium** impact category: *"Harmful smart-contract behavior without direct funds theft, including... stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

The refund path is publicly reachable by any NEAR account that can submit a valid BTC transaction proof. The `request_refund` function has no role restriction. Each invocation irreversibly locks 2 NEAR. Even under normal bridge operation, legitimate refund requesters contribute to the permanently locked balance. The likelihood is **Medium** — the path is reachable in normal operation, not just adversarial scenarios.

---

### Recommendation

Add a DAO-gated function to withdraw accumulated NEAR from the contract balance, for example:

```rust
#[payable]
#[access_control_any(roles(Role::DAO))]
pub fn withdraw_near(&mut self, amount: NearToken, recipient: AccountId) -> Promise {
    assert_one_yocto();
    Promise::new(recipient).transfer(amount)
}
```

Alternatively, if the anti-spam fee is intentional, document explicitly that these NEAR tokens are permanently burned/locked and consider whether the amounts are appropriately sized given the irrecoverability.

---

### Proof of Concept

1. Any NEAR account calls `request_refund` with a valid BTC deposit proof, attaching 2 NEAR. The function checks `env::attached_deposit() >= required_balance_for_request_refund()` (2 NEAR) and proceeds. The 2 NEAR is credited to the contract's account balance.
2. After the timelock, any NEAR account calls `execute_refund` for the same request, attaching 1 NEAR. Again, 1 NEAR is credited to the contract's balance.
3. The refund is finalized via `verify_refund_finalize_callback`, which removes the `RefundRequest` from storage — freeing the storage-staking portion — but the excess anti-spam NEAR (the bulk of the 2+1 NEAR) remains in the contract's balance.
4. No function in the contract allows the DAO or any account to transfer this NEAR out. `withdraw_protocol_fee` only moves nBTC-denominated fees. The NEAR is permanently locked. [8](#0-7)

#[near]
impl Contract {
    #[private]
    pub fn verify_refund_finalize_callback(&mut self, tx_id: String) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_pending_verify_tx();

        let account_id = btc_pending_info.account_id.clone();

        // A refund spends exactly one deposit UTXO, whose key is the refund request
        // key. More than one input would be abnormal for a refund.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        // Refund confirmed on-chain → drop the request so no further execute_refund
        // is possible. If it was already removed, this is harmlessly a no-op.
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_keys[0]);

        // Clean up: remove pending info
        self.internal_remove_btc_pending_info(&tx_id);
        self.internal_unwrap_mut_account(&account_id)
            .btc_pending_verify_list
            .remove(&tx_id);

        true
    }

        let total_protocol_fee = self.data().cur_available_protocol_fee;

        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
