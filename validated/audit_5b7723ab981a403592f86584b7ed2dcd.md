### Title
Stub `validatePerasCert` Implementation Unconditionally Accepts All Inbound Peras Certificates, Bypassing Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that unconditionally returns `Right` (success) for every certificate, performing no cryptographic or structural checks. This stub is the exact function wired into the production Peras certificate diffusion mini-protocol handler. Any unprivileged peer can send crafted certificates for arbitrary blocks and rounds; they will pass "validation" and be stored in the `PerasCertDB`, where they influence Peras-weighted chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate for inbound Peras certificates. The universal instance — explicitly labelled "degenerate instance for all blks to get things to compile" — implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature check, no committee membership check, no round-number bounds check — every certificate is unconditionally accepted. [1](#0-0) 

This stub is passed directly as the `validateCert` argument in the production certificate pool writer:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this function on every inbound certificate and, because it always returns `Right`, adds every certificate to the database via `ChainDB.addPerasCertAsync`: [3](#0-2) 

The Peras cert diffusion mini-protocol is fully wired into the production node-to-node protocol stack in `mkHandlers`, using `makePerasCertPoolWriterFromChainDB`: [4](#0-3) 

It is registered as a live mini-protocol in both `initiator` and `initiatorAndResponder` bundles: [5](#0-4) [6](#0-5) 

Once a certificate is stored, `chainSelSync` triggers `chainSelectionForBlock` for the boosted block, causing the node to re-evaluate chain selection with the adversarially injected weight: [7](#0-6) 

The analog to the external report is exact: just as `revoke_freeze_authority` exists but is never invoked (leaving freeze authority active), `validatePerasCert` exists and is invoked but its body is a no-op stub (leaving certificate authority checks absent).

---

### Impact Explanation

**Impact: Critical** — Bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection manipulation.

When Peras weighting is active, an adversary can inject certificates boosting any block in the VolatileDB. Because `vpcCertBoost` is set to `perasWeight mkPerasParams` (15 blocks worth of weight) for every accepted certificate, a single crafted certificate can make an adversarial fork appear heavier than the honest chain, causing an honest node to switch to it. This is a direct bypass of the Peras certificate/vote check listed in the allowed Critical impact scope. [8](#0-7) 

---

### Likelihood Explanation

**Likelihood: Medium.**

The Peras cert diffusion mini-protocol is already wired into the production node-to-node stack and active for any peer speaking the negotiated protocol version. The attack requires only that a peer send a well-formed `PerasCert` message (a round number and a block point) — no key material, no stake, no privileged access. The CHANGELOG notes that "if Peras is disabled (which is the default), there is no observable difference," meaning the chain-selection impact is gated on Peras being enabled. However, the certificate acceptance and storage path is unconditionally active, and the stub will silently accept all certificates the moment Peras weighting is turned on. [9](#0-8) 

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS/committee signature over `(electionId, candidate)` using the committee's verification keys for the claimed round.
2. That the claimed voters are eligible committee members with non-zero stake for that round.
3. That the boosted block's slot falls within the valid range for the certificate's round number.

The `EveryoneVotes` committee already provides a reference implementation of proper certificate verification (`implVerifyCert`) that checks aggregate signatures and committee membership: [10](#0-9) 

Until real validation is implemented, the Peras cert diffusion mini-protocol should not be enabled in production builds, or inbound certificates should be silently dropped rather than accepted unconditionally.

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to a production node and negotiates a `NodeToNodeVersion` that includes the `perasCertDiffusionProtocol`.
2. Peer sends a `PerasCert` message containing an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to a block hash present in the target node's VolatileDB.
3. `objectDiffusionInbound` → `processCerts` → `validatePerasCert mkPerasParams` returns `Right` unconditionally.
4. The certificate is stored via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` calls `chainSelectionForBlock` for the boosted block, re-running chain selection with the injected `perasWeight` (15) added to the adversarial fork's weight.
6. If the adversarial fork is within `k` blocks of the current tip and the injected weight tips the comparison, the honest node switches to the adversarial chain.

implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
