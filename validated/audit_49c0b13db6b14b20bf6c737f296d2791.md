### Title
Hardcoded Mainnet-Only `HistoricityCutoff` in `mkGenesisConfig` Bypasses Genesis Historicity Check on Non-Mainnet Chains - (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes the `HistoricityCutoff` to a literal computed from Cardano mainnet constants (`k=2160`, `f=0.05`, `slotLength=1s`) at the point of initialization, without accepting the actual chain's security parameter, active-slot coefficient, or slot length as inputs. No override field exists in `GenesisConfigFlags`. On any chain whose stability window differs from mainnet's 36 hours (e.g., a private testnet with `k=10`, `f=0.5`), the cutoff is wildly wrong, and an unprivileged peer can send crafted `MsgRollBackward`/`MsgAwaitReply` ChainSync messages that are far older than the actual stability window without being disconnected, defeating the Genesis historicity defense.

---

### Finding Description

In `mkGenesisConfig (Just cfg)`, the `gcHistoricityCutoff` field is set unconditionally to a literal:

```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
``` [1](#0-0) 

The comment confirms this is a mainnet-specific constant: `"Duration in seconds of one Cardano mainnet Shelley stability window (3k/f slots times one second per slot) plus one extra hour as a safety margin."` The value encodes `k=2160`, `1/f=20`, `slotLength=1s`, yielding 133,200 seconds (≈37 hours).

`mkGenesisConfig` takes only `Maybe GenesisConfigFlags` as its sole argument: [2](#0-1) 

`GenesisConfigFlags` exposes override fields for every other Genesis parameter (`gcfBlockFetchGracePeriod`, `gcfBucketCapacity`, `gcfBucketRate`, `gcfCSJJumpSize`, `gcfGDDRateLimit`) but has **no field for `HistoricityCutoff`**: [3](#0-2) 

The design document explicitly acknowledges this: *"MaxCaughtUpAge and HistoricityCutoff are indeed constants in the implementation."*

The `HistoricityCutoff` is consumed in `runWith` to construct the `historicityCheck` passed to every ChainSync client: [4](#0-3) 

The check itself disconnects a peer only when `historicityCutoff < actualRollbackAge`: [5](#0-4) 

The `HistoricityCutoff` must be **at least** the chain's actual stability window (`3k/f` seconds) to be correct. On a private testnet with `k=10`, `f=0.5`, `slotLength=1s`, the actual stability window is 60 seconds, but the hardcoded cutoff is 133,200 seconds — a factor of 2,200× too large. The check becomes effectively disabled for that chain.

---

### Impact Explanation

**High.** On any non-mainnet chain (private testnet, custom deployment) where the actual stability window is shorter than 37 hours, the historicity check is rendered inoperative. An adversarial peer can:

1. Send a `MsgRollBackward` rolling back to a header that is, say, 1 hour old — far beyond the actual stability window (e.g., 60 s) but well within the hardcoded 37-hour cutoff.
2. The syncing node does **not** disconnect (`historicityCutoff < actualRollbackAge` is false).
3. The adversary remains connected and can serve a historical chain forking far in the past.
4. This bypasses the Genesis historicity defense, allowing the adversary to keep the syncing node anchored to a historical fork, weakening the LoE/GDD chain-selection guarantees and potentially causing the node to select a non-canonical chain.

The `HistoricityCutoff` is documented as a necessary bound to prevent adversarial peers from forcing the syncing node to process the entire historical chain: [6](#0-5) 

---

### Likelihood Explanation

Any operator running Genesis on a non-mainnet chain (private testnet, pre-production environment, custom Cardano fork) with different `k`, `f`, or slot length is affected. The `enableGenesisConfigDefault` path is the standard way to enable Genesis, and it unconditionally uses the hardcoded value with no way to override it through `GenesisConfigFlags`. An adversarial peer needs only to craft a `MsgRollBackward` message pointing to a header older than the actual stability window — a trivially constructable ChainSync message.

---

### Recommendation

1. Remove the hardcoded literal from `mkGenesisConfig`. Instead, derive `HistoricityCutoff` from the actual chain's `SecurityParam k`, active-slot coefficient `f`, and slot length — analogous to how `SL.computeStabilityWindow` is used in `mkShelleyGlobals`.
2. Add a `gcfHistoricityCutoff :: Maybe NominalDiffTime` override field to `GenesisConfigFlags`, consistent with how all other Genesis parameters are handled.
3. At minimum, expose the constant as a named, documented value (e.g., `mainnetHistoricityCutoff`) rather than an inline literal, so non-mainnet deployments can identify and override it.

---

### Proof of Concept

**Setup:** Private testnet, `k=10`, `f=0.5`, `slotLength=1s`. Actual stability window = `3 * 10 / 0.5 * 1s = 60s`. Genesis enabled via `enableGenesisConfigDefault`.

**Hardcoded cutoff in effect:**
```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
-- = 133,200 seconds ≈ 37 hours
-- Actual required cutoff: 60 seconds
``` [7](#0-6) 

**Attack:** Adversarial peer sends `MsgRollBackward` to a header with `slotTime` = `now - 3600s` (1 hour ago). `actualRollbackAge = 3600s`. Check: `133200 < 3600` → **False** → peer is **not disconnected**. The adversary remains connected and can serve a chain forking 1 hour in the past, far beyond the 60-second stability window, defeating the historicity defense entirely.
