### Title
Unconditional Certificate Acceptance in `validatePerasCert` Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the default `BlockSupportsPeras` instance unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. This function is the sole gatekeeper called by `processCerts` before accepting peer-supplied Peras certificates into the `PerasCertDB` and triggering chain selection. Any unprivileged peer can therefore inject a crafted certificate claiming to boost any arbitrary block, causing the receiving node to add Peras weight to that block and potentially switch to a fork it would otherwise reject.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No signature is verified, no committee membership is checked, no round validity is enforced, and no boosted-block existence is confirmed. Every certificate — regardless of content — is wrapped in `ValidatedPerasCert` and returned as `Right`.

**Attacker-controlled entry path:**

The `makePerasCertPoolWriterFromChainDB` function wires `validatePerasCert mkPerasParams` directly as the validation callback passed to `processCerts`: [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate from a peer. Because `validatePerasCert` always returns `Right`, the `partitionEithers` branch that would throw `PerasCertValidationError` and disconnect the peer is **never reached**: [3](#0-2) 

Every certificate passes, is timestamped, and forwarded to `ChainDB.addPerasCertAsync`.

**Chain selection consequence:**

`chainSelSync` processes the certificate, adds it to `PerasCertDB`, and — if the boosted block is in the `VolatileDB` — immediately calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

The `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is the full Peras weight boost. This weight is then used in `constructPreferableCandidates` via the `PerasWeightSnapshot`, causing the node to prefer the boosted fork over its current chain: [5](#0-4) 

**Exploit flow:**

1. Attacker connects to a target node as a normal peer (no keys required).
2. Attacker sends a crafted `PerasCert` over the Peras certificate diffusion mini-protocol, with `pcCertRound` set to any round and `pcCertBoostedBlock` pointing to a block on a minority fork already present in the target's `VolatileDB`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..., vpcCertBoost = perasWeight params}`.
4. The certificate is added to `PerasCertDB` and `chainSelectionForBlock` is triggered for the boosted block.
5. The node's chain selection now treats the minority-fork block as having full Peras weight, potentially switching away from the honest majority chain.

---

### Impact Explanation

**Impact: High — Chain selection manipulation via unauthorized certificate acceptance.**

The Peras protocol's weight boost is the mechanism by which a quorum of committee members can make a chain "sticky" and resistant to rollback. By injecting a forged certificate with no valid committee signatures, an unprivileged peer can unilaterally apply this weight boost to any block in the node's `VolatileDB`. This causes the node to prefer a non-canonical fork over the honest chain, violating the chain selection invariant that only legitimately certified blocks receive Peras weight. The node may permanently diverge from the honest majority chain for the duration the forged certificate remains in `PerasCertDB`.

This maps to the allowed impact scope: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

**Likelihood: High.**

The attacker precondition is simply being a connected peer — no keys, no stake, no privileged access. The Peras certificate diffusion mini-protocol is a standard peer-to-peer channel. The `validatePerasCert` stub is the active production code path (not a test mock), confirmed by its use in `makePerasCertPoolWriterFromChainDB` which is the production writer. The `TODO` comment and linked issue (`cardano-peras/issues/120`) confirm the stub was intentionally shipped without the security-critical validation logic.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real verification that checks:
1. The aggregate BLS signature over the certificate covers the claimed `(electionId, candidate)` pair.
2. The signers are members of the voting committee for the claimed round (using the `VotingCommittee` API already present in `Ouroboros.Consensus.Committee.Class`).
3. The aggregate weight of the signers meets the quorum threshold.
4. The `pcCertRound` is within the valid window relative to the current chain tip.

Until this is implemented, the `processCerts` path should refuse all inbound certificates from peers (or the Peras certificate diffusion mini-protocol should not be enabled in production).

```

let craftedCert = PerasCert
      { pcCertRound     = PerasRoundNo 42          -- any round
      , pcCertBoostedBlock = minorityForkBlockPoint -- any block in target's VolatileDB
      }

-- Attacker sends [craftedCert] via the Peras cert diffusion mini-protocol.
-- On the receiving node:
--   processCerts ... (validatePerasCert mkPerasParams) ... [craftedCert]
--   => validatePerasCert mkPerasParams craftedCert
--   => Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = perasWeight mkPerasParams })
--   => cert added to PerasCertDB, chainSelectionForBlock triggered for minorityForkBlockPoint
--   => node may switch to minority fork
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
