### Title
Peras Certificate Validation Unconditionally Bypassed — Crafted Peer Certificates Accepted Without Cryptographic Checks - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` function in the degenerate `BlockSupportsPeras` instance always returns `Right` (success) for any certificate, regardless of content. This is the exact structural analog to the Beanstalk bug: a validation result is computed (the function exists and is called) but the actual check is never applied — the wrong value (`Right` unconditionally) is returned instead of the real validation outcome. Because this stub is wired into the live certificate ingestion path, any unprivileged peer can inject arbitrary Peras certificates that are stored in `PerasCertDB` and subsequently used to manipulate chain selection weight.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mechanism for cryptographically and semantically validating inbound Peras certificates. The degenerate instance that covers all block types unconditionally returns `Right ValidatedPerasCert` without performing any check:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is not isolated to tests. It is the live implementation used by `processCerts` in the production object-diffusion inbound path:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` rejects a batch only when `validateCert` returns `Left`. Since `validatePerasCert` never returns `Left`, every certificate from every peer is accepted:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Accepted certificates are stored in `PerasCertDB`. `implGetWeightSnapshot` then derives a `PerasWeightSnapshot` from all stored certificates:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

This snapshot is consumed directly by `chainSelectionForBlock` and `preferAnchoredCandidate` during chain selection:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [5](#0-4) 

The `wsvTotalWeight` used in `preferCandidate` is `blockNo + weightBoost`, so injected certificates directly shift which chain is selected:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5)

### Impact Explanation

**Critical — Bypass of Peras certificate verification enabling unauthorized chain-weight manipulation.**

An adversary who can send Peras certificates via the object-diffusion mini-protocol (any unprivileged peer) can boost arbitrary blocks to any weight. Because `validatePerasCert` never rejects a certificate, the adversary's certificates are stored and their weight boosts are applied during `preferAnchoredCandidate`. This can cause an honest node to prefer an adversarial chain over the canonical honest chain, constituting a chain-selection safety failure.

---

### Likelihood Explanation

**High.** The attack requires only that a peer send crafted `PerasCert` objects over the object-diffusion mini-protocol. No key compromise, stake majority, or privileged access is needed. The entire path from peer input to chain selection weight is wired up in production source files with no guard other than the bypassed `validatePerasCert`.

---

### Recommendation

- **Short term:** Replace the unconditional `Right` stub in `validatePerasCert` with actual cryptographic and semantic validation (signature verification, round-number bounds, boosted-block existence checks) before the Peras certificate ingestion path is reachable from external peers.
- **Long term:** Add an invariant test asserting that `validatePerasCert` rejects certificates with invalid signatures, wrong round numbers, or non-existent boosted blocks. Document the expected security properties of the `PerasCertDB` and the chain-selection weight invariants it must uphold.

---

### Proof of Concept

1. Connect to a node as an unprivileged peer via the object-diffusion mini-protocol.
2. Send a batch of `PerasCert` objects with `pcCertBoostedBlock` pointing to any block on an adversarial fork and `pcCertRound` set to a round not yet in the DB.
3. `processCerts` calls `validatePerasCert mkPerasParams` on each certificate. Since `validatePerasCert` always returns `Right`, all certificates pass.
4. Each certificate is stored in `PerasCertDB` via `addPerasCertAsync`.
5. `implGetWeightSnapshot` builds a `PerasWeightSnapshot` that includes the injected boosts.
6. On the next call to `chainSelectionForBlock`, `preferAnchoredCandidate` uses this snapshot. The adversarial fork's `wsvTotalWeight` is inflated by the injected boosts, causing the node to switch to the adversarial chain.
