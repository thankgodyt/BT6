### Title
Inverted Boolean in `noCertsFromTwoRoundsAgo` Suppresses Peras Certificate Inclusion in Rounds 0–1 — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Cert/Inclusion.hs`)

---

### Summary

The `noCertsFromTwoRoundsAgo` predicate in the Peras certificate-inclusion logic returns `Bool False` when `currRoundNo < 2`, accompanied by a comment that reads "this is vacuously false." The correct value is `Bool True` (vacuously true): when the node is in round 0 or 1, no round two steps prior exists, so the snapshot trivially contains no certificate from two rounds ago, satisfying the predicate. Because `needCertRules` is a conjunction that short-circuits on the first `False`, this inversion unconditionally suppresses certificate inclusion in every Peras round 0 and round 1. An adversary who corrects this single line in their own node can include valid certificates in those rounds while honest nodes cannot, giving the adversary a persistent Peras weight advantage at the start of every Peras epoch.

---

### Finding Description

`needCertRules` is the conjunction that governs whether a block forger must embed a Peras certificate:

```haskell
needCertRules pciv =
  noCertsFromTwoRoundsAgo pciv
    :/\: latestCertSeenIsNotExpired pciv
    :/\: latestCertSeenIsNewerThanLatestCertOnChain pciv
``` [1](#0-0) 

The first conjunct is `noCertsFromTwoRoundsAgo`. Its semantics, as stated in its own Haddock comment, is: *"we haven't seen a certificate from two rounds ago."* This is a positive predicate — it is `True` when the snapshot lacks a cert from two rounds ago, which is the condition that triggers inclusion. [2](#0-1) 

The early-exit branch for `currRoundNo < 2` reads:

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously false.
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool False
``` [3](#0-2) 

The comment and the value are both wrong. When `currRoundNo < 2`, rounds −2 and −1 do not exist, so the snapshot trivially contains no certificate from two rounds ago. The predicate "no certs from two rounds ago" is therefore **vacuously true**, not vacuously false. The correct branch is:

```haskell
-- vacuously true: rounds -2 and -1 do not exist
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo := Bool True
```

Because `evalPred` short-circuits a conjunction on the first `False`, the buggy `Bool False` causes `needCert` to return `DoNotIncludeCert` for every block forged in rounds 0 and 1, regardless of whether a valid, unexpired, newer-than-on-chain certificate is available. [4](#0-3) 

The test-suite model in `Test/Consensus/Peras/Cert/Inclusion.hs` replicates the same inversion:

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then False          -- same bug
    else not ((currRoundNo - 2) `Set.member` certIds)
``` [5](#0-4) 

Because `prop_needCert` compares the production implementation against this model, the test passes despite the shared inversion — exactly the pattern described in the external report. [6](#0-5) 

---

### Impact Explanation

Peras certificates carry a weight boost that is the primary mechanism by which Peras strengthens chain selection beyond the standard Praos longest-chain rule. The `needCert` / `needCertRules` path is invoked exclusively during block forging; there is no symmetric validation gate that rejects a peer's block for *including* a certificate in rounds 0–1.

Consequence: an adversary who corrects the single `Bool False → Bool True` in their own node will include valid Peras certificates in blocks they forge during rounds 0 and 1. Honest nodes running the unpatched code will not. The adversary's blocks therefore carry the full Peras weight boost while honest blocks do not. Honest nodes, applying `preferAnchoredCandidate` with Peras weights, will prefer the adversary's heavier chain over the honest chain at the start of every Peras epoch. [7](#0-6) 

This is a chain-selection bug that lets an adversary make honest nodes prefer a less-secure (adversary-controlled) chain beyond the intended Peras security assumptions, matching the **High** impact tier.

---

### Likelihood Explanation

Peras is not yet enabled on any production era (`eraPerasRoundLength = HardFork.NoPerasEnabled` in all current era params). [8](#0-7) 

When Peras is activated, the bug will be present in every unpatched node. The fix is a one-line change visible to any reader of the source. An adversary who discovers it before or shortly after Peras activation can exploit it with any non-zero stake (block production probability is proportional to stake). No key compromise, social engineering, or majority stake is required. Likelihood is **Medium** once Peras is deployed.

---

### Recommendation

In `noCertsFromTwoRoundsAgo`, change the early-exit branch from `Bool False` to `Bool True` and correct the comment:

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously TRUE: those rounds do
-- not exist, so the snapshot trivially contains no cert from two rounds ago.
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo := Bool True
```

Apply the same correction to the model in `Test/Consensus/Peras/Cert/Inclusion.hs` (`then False` → `then True`). Add a targeted QuickCheck case that fixes `currRoundNo = 0` or `1`, provides a valid unexpired certificate newer than the on-chain cert, and asserts that `needCert` returns `IncludeCert`.

---

### Proof of Concept

Construct a `PerasCertInclusionView` with:
- `currRoundNo = 1`
- `latestCertSeen` = a certificate from round 0 (unexpired, `lcsCertRound = 0`)
- `latestCertOnChain = Origin` (no cert on chain yet)
- `certIds = Set.empty` (no cert from round −1 in snapshot, trivially)

All three conditions of `needCertRules` should be satisfied:
1. `noCertsFromTwoRoundsAgo`: round −1 does not exist → vacuously true → **should be `True`, is `False`**
2. `latestCertSeenIsNotExpired`: `currRoundNo (1) <= _A + 0` → true for any `_A >= 1`
3. `latestCertSeenIsNewerThanLatestCertOnChain`: `Origin` case → `Bool True`

Expected result: `IncludeCert`. Actual result with buggy code: `DoNotIncludeCert`, because `noCertsFromTwoRoundsAgo` short-circuits the conjunction with `Bool False`. [9](#0-8)

-- | noCertsFromTwoRoundsAgo: we haven't seen a certificate from two rounds ago
noCertsFromTwoRoundsAgo ::
  PerasCertInclusionView cert blk ->
  Pred PerasCertInclusionRule
noCertsFromTwoRoundsAgo
  PerasCertInclusionView
    { currRoundNo
    , certIds
    }
    -- We cannot have possibly seen a certificate from two rounds ago if we are
    -- in round 0 or 1. In that case, this is vacuously false.
    | currRoundNo < 2 =
        NoCertsFromTwoRoundsAgo currRoundNo
          := Bool False
    -- If we are in round 2 or higher, check whether our certificate snapshot
    -- contains a certificate from two rounds ago.
    | otherwise =
        NoCertsFromTwoRoundsAgo currRoundNo
          := Not (Bool containsCertFromTwoRoundsAgo)
   where
    containsCertFromTwoRoundsAgo =
      (currRoundNo - 2) `Set.member` certIds
