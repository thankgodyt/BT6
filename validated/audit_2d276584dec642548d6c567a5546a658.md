### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Adversarial Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic validation. An unprivileged peer can therefore inject crafted `PerasCert` messages that boost arbitrary blocks — including blocks on adversarial forks — into the node's `PerasWeightSnapshot`. Because chain selection directly uses these weights to decide which chain to prefer, the attacker can make an honest node switch to a non-canonical chain without holding any stake or keys.

---

### Finding Description

**Vulnerability class:** Chain-selection bug via certificate-validation bypass.

**Root cause — stub validator always succeeds:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate — regardless of its cryptographic content, the identity of the alleged signers, or whether a quorum was ever reached — is accepted and assigned the protocol-configured boost weight. No signature, quorum, or round-validity check is performed.

**Network entry path — production certificate ingest:**

`processCerts` in the Peras certificate object-pool writer calls `validatePerasCert mkPerasParams` directly on every certificate received from a peer: [2](#0-1) 

After passing this no-op validator, the certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`, which stores it in `PerasCertDB` and triggers chain selection.

**Weight snapshot construction — adversarial boost enters chain selection:**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every stored certificate, including adversarially injected ones: [3](#0-2) 

**Chain selection uses the snapshot without further validation:**

`preferAnchoredCandidate` calls `weightedSelectView`, which calls `weightBoostOfFragment` on the snapshot, and compares `wsvTotalWeight` values to decide whether to switch chains: [4](#0-3) 

`wsvTotalWeight` is `PerasWeight (unBlockNo wsvBlockNo) <> wsvWeightBoost`, where `PerasWeight` is `Word64` with `Sum Word64` (modular) addition — no overflow guard exists at this layer. [5](#0-4) 

**Rollback boundary also affected:**

`takeVolatileSuffix` uses `totalWeightOfFragment` (which includes the adversarially inflated boost) to determine which blocks are immutable. Inflated weights can cause the volatile/immutable boundary to be computed incorrectly: [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send one certificate per Peras round (deduplicated by round number in `implAddCert`) boosting blocks on an adversarial fork. Each accepted certificate adds `perasWeight params = 15` to the adversarial chain's weight. Over the ~24 rounds that fit within a `k`-block window (at `perasRoundLength = 90` slots), the attacker can inject up to ~360 units of artificial weight, enough to make a shorter adversarial chain appear heavier than the honest chain in `preferAnchoredCandidate`. The node then switches to the adversarial fork. Additionally, the inflated `totalWeightOfFragment` used by `takeVolatileSuffix` can misplace the immutable tip, potentially allowing rollback of blocks that should be finalized.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production codebase. Any peer that can connect to the node can send `PerasCert` messages. The stub is the only validation gate before certificates reach chain selection. No stake, keys, or special privileges are required. The attack requires only crafting a valid CBOR-encoded `PerasCert` structure targeting a block on an adversarial fork.

---

### Recommendation

1. Implement `validatePerasCert` with real cryptographic validation: verify that the certificate carries a valid aggregate signature from a quorum of eligible committee members for the claimed round, as specified in the Peras design document (tracked in [tweag/cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120)).
2. Until real validation is in place, gate the Peras certificate ingest path so that it is disabled in any deployment where the stub is the active instance.
3. Add an overflow guard in `wsvTotalWeight` analogous to the guard already present in `pureTryAddTx` for `ByteSize32`.

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate mini-protocol.
2. Construct a `PerasCert` with `pcCertRound = r` (any round not yet in the node's `PerasCertDB`) and `pcCertBoostedBlock = blockPoint adversarialBlock` where `adversarialBlock` is a block on a shorter adversarial fork.
3. Send the certificate. `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right ValidatedPerasCert{vpcCertBoost = 15}` unconditionally.
4. The certificate is stored. `implGetWeightSnapshot` now includes `(adversarialBlock, PerasWeight 15)`.
5. Repeat for each available round (up to ~24 rounds per `k`-window), accumulating ~360 units of artificial weight on the adversarial fork.
6. When the node next runs chain selection (triggered by `addPerasCertAsync`), `preferAnchoredCandidate` computes `wsvTotalWeight` for both chains. The adversarial chain's boosted weight exceeds the honest chain's length-based weight, and `ShouldSwitch` is returned.
7. The node adopts the adversarial fork.
