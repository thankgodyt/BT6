### Title
Legacy Version-1 PSBT Defaults to Stale `BranchId::Nu6_1` After Nu6_2 Activation, Producing Invalid Sighash and Locking Bridge UTXOs — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

### Summary

`PsbtWrapper::deserialize` hard-codes `BranchId::Nu6_1` for any PSBT whose serialized version byte is `< 2`. After the Zcash network activates Nu6_2, any such legacy PSBT still in `btc_pending_infos` will have its sighash computed against the wrong consensus branch ID. The resulting signature is cryptographically valid for Nu6_1 but invalid on Nu6_2, so the broadcast transaction is rejected by every Nu6_2 node and the bridge UTXO is never spent.

### Finding Description

`PsbtWrapper::to_bytes()` always emits `version = 3` today: [1](#0-0) 

However, `deserialize` explicitly handles the legacy `version == 1` case by falling back to a hardcoded branch ID: [2](#0-1) 

That stale `branch_id` is stored in the `PsbtWrapper` struct field and is never refreshed against the live network state. When `get_hash_to_sign` is later called, it passes `self.branch_id` verbatim into `WrappedTransaction::to_zcash_tx`: [3](#0-2) 

`to_zcash_tx` embeds that branch ID into `TransactionData::from_parts`, which is then consumed by `signature_hash`: [4](#0-3) [5](#0-4) 

The Zcash v5 sighash algorithm (ZIP-244) commits to the consensus branch ID. A signature produced over a Nu6_1 digest is invalid under Nu6_2 consensus rules and will be rejected by the network.

### Impact Explanation

Once all inputs of a legacy PSBT are signed with the wrong sighash, `sign_btc_transaction_callback` calls `btc_pending_info.to_pending_verify_stage()` and stores the bad `tx_bytes_with_sign`: [6](#0-5) 

The transaction is broadcast but rejected by every Nu6_2 node. The bridge UTXO is never consumed. Because the PSBT has already advanced to the verify stage, the normal RBF/cancel path is no longer available without operator intervention. The bridge-controlled ZEC in those UTXOs is effectively locked — matching the **Critical** impact category: *permanent locking of user or protocol funds*.

### Likelihood Explanation

- `sign_btc_transaction` carries no caller role-check; any account can invoke it on any pending PSBT ID (discoverable via `get_btc_pending_infos_paged`): [7](#0-6) 

- The `deserialize` code explicitly handles `version == 1`, confirming that version-1 PSBTs were produced by a prior deployment and can still reside in contract state.
- The trigger is the Nu6_2 network activation — a scheduled, predictable event. Any version-1 PSBT that survives in `btc_pending_infos` across that boundary will be signed with the wrong branch ID the next time `sign_btc_transaction` is called, whether by a relayer or any other caller.

### Recommendation

In `PsbtWrapper::deserialize`, replace the static fallback with a runtime lookup of the current consensus branch ID, or reject version-1 PSBTs outright after Nu6_2 activation. A minimal fix:

```rust
} else {
    // Version-1 PSBTs predate the branch_id field.
    // Callers must supply the current height so the correct BranchId can be derived.
    get_branch_id(current_height, config)
};
```

Alternatively, add a migration step that re-serializes all version-1 PSBTs in state to version 3 with the correct branch ID before Nu6_2 activates.
