### Title
TOCTOU Race in `migrate_to_new_token` Allows nBTC Theft via Balance Manipulation Between Query and Callback - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

### Summary

`internal_migrate_to_new_token` reads live `ft_balance_of` and `ft_total_supply` from the old nBTC token via cross-contract calls, then uses those stale snapshots in the `migrate_to_new_token_mint` callback to mint equivalent amounts on the new token. Because NEAR cross-contract calls are not atomic, any nBTC holder included in the `accounts` list can transfer tokens to another listed account between the query receipt and the callback receipt. The callback's `sum == total_supply` invariant still passes (both values were snapshotted at the same earlier point), but the minted distribution is wrong: the sender is minted their pre-transfer (inflated) balance on the new token, while the recipient is minted their pre-transfer (deflated) balance. The attacker permanently steals nBTC from the recipient.

### Finding Description

`internal_migrate_to_new_token` fires parallel cross-contract queries for `ft_total_supply` and `ft_balance_of(account)` for every account in the caller-supplied list: [1](#0-0) 

The callback `migrate_to_new_token_mint` sums the queried balances and enforces `sum == total_supply`: [2](#0-1) 

It then mints those queried amounts to the new token: [3](#0-2) 

In NEAR, receipts are processed asynchronously. Between the query receipt (which snapshots balances) and the callback receipt (which acts on them), other transactions execute normally. An attacker who is in the `accounts` list can call `ft_transfer(victim, X)` on the old nBTC token in this window. Because both the attacker's and victim's balances were queried at the same earlier moment, `sum` still equals `total_supply` and the check passes — but the minted amounts reflect the pre-transfer state, not the actual state at callback time.

The `nbtc.burn` path is not affected because `burn_amount` is fixed in `BTCPendingInfo` at withdrawal initiation time and is not read from live balances: [4](#0-3) 

The vulnerability is exclusively in the migration's reliance on stale cross-contract balance reads.

### Impact Explanation

**Critical — Significant theft of user funds.**

Concrete scenario (simplified):
- Alice: 1 000 old nBTC. Bob: 500 old nBTC. Total supply: 1 500.
- MigrationOperator calls `migrate_to_new_token(new_token, [Alice, Bob])`.
- Query snapshot: Alice=1 000, Bob=500, total=1 500.
- Alice immediately calls `ft_transfer(Bob, 500)` on the old token (processed before the callback).
- Actual state at callback time: Alice=500, Bob=1 000, total=1 500.
- Callback: sum=1 500 (queried), total=1 500 (queried) → check passes.
- New token minted: Alice=1 000, Bob=500.
- After migration: Alice holds 1 000 new nBTC (should be 500). Bob holds 500 new nBTC (should be 1 000). Alice stole 500 nBTC from Bob.

The old token is deprecated after migration (`nbtc_account_id` is updated to the new token), so Bob's 1 000 old nBTC tokens are stranded and worthless for bridge purposes. [5](#0-4) 

### Likelihood Explanation

**Medium-High.** Any nBTC holder included in the `accounts` list (which for a complete migration is every holder) can execute this attack. The attacker only needs to:
1. Monitor the blockchain for the `migrate_to_new_token` transaction.
2. Submit an `ft_transfer` on the old nBTC token before the callback receipt is processed.

NEAR's asynchronous receipt model makes this window reliably exploitable: the query and callback are separate receipts, and user transactions can be interleaved between them. No special privileges are required beyond holding nBTC tokens.

### Recommendation

Do not rely on live cross-contract balance reads for migration accounting. Instead, use one of the following approaches:

1. **Snapshot-and-lock**: Pause all nBTC transfers (via the existing `#[pause]` mechanism) before initiating migration, so balances cannot change between query and callback.
2. **Internal snapshot**: Have the old nBTC contract expose a dedicated migration view that returns a frozen snapshot of all balances atomically, or perform the migration in a single atomic transaction if the account count is small enough.
3. **Verify at callback time**: Re-query each account's balance inside the callback and use the fresher values, accepting that the total-supply check must also be re-read in the same callback (though this still has a smaller TOCTOU window).

### Proof of Concept

1. MigrationOperator calls `migrate_to_new_token(new_token, [alice, bob])` with Alice holding 1 000 nBTC and Bob holding 500 nBTC.
2. The query receipt fires, snapshotting Alice=1 000, Bob=500, total=1 500.
3. Alice calls `nbtc.ft_transfer(bob, 500)` — this receipt is processed before `migrate_to_new_token_mint`.
4. `migrate_to_new_token_mint` executes: sum=1 500 == total=1 500 → passes; mints Alice=1 000, Bob=500 on new token.
5. After migration: Alice has 1 000 new nBTC (net gain of 500); Bob has 500 new nBTC (net loss of 500). Bob's 1 000 old nBTC are stranded. [6](#0-5) [7](#0-6)

    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }
