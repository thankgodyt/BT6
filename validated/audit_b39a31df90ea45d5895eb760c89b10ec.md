### Title
nBTC Minted to Bridge Balance Before Registration Check in `safe_mint`, Causing Orphaned Supply and Permanent User Fund Loss — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `safe_mint()`, nBTC tokens are unconditionally minted to the bridge's own balance **before** checking whether the recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` early, leaving the minted tokens orphaned in the bridge's balance. The depositing user receives no nBTC while their BTC is locked in the bridge's UTXO pool, with no on-chain recovery path.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes `internal_deposit` to the bridge's own account unconditionally at line 112, then checks recipient registration at line 114:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    // ...
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← always mints

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← early return, tokens stay in bridge
    }
    // transfer to user only if registered
    ...
}
``` [1](#0-0) 

When the recipient is **not** registered:

1. `internal_deposit(&self.bridge_id, amount)` executes — nBTC total supply increases by `amount`, bridge balance increases by `amount`.
2. The registration check fails — function returns `PromiseOrValue::Value(U128(0))` immediately.
3. No transfer to the user occurs. The minted tokens are orphaned in the bridge's balance with no attribution to the depositor.

The bridge's callback receives `U128(0)`. Depending on how the bridge interprets this return value (as "mint failed" vs. "0 tokens minted"), two bad outcomes are possible:

- **Outcome A**: Bridge treats `U128(0)` as failure and allows a BTC refund. User recovers BTC, but the bridge now holds `amount` nBTC that was minted without a corresponding locked BTC backing — **supply inflation**.
- **Outcome B**: Bridge treats `U128(0)` as success. User permanently loses their BTC deposit with no nBTC received and no on-chain recovery path — **permanent user fund loss / stuck bridge state**.

In both cases, the nBTC total supply is inflated relative to the BTC actually backing it. [2](#0-1) 

---

### Impact Explanation

- **Supply accounting failure**: nBTC is minted (total supply increases) but the tokens are not delivered to the user and are not tied to any deposit record. The bridge's nBTC balance grows without a corresponding user credit.
- **Permanent user fund loss / stuck state**: The user's BTC is locked in the bridge's UTXO pool. The user holds no nBTC and has no on-chain mechanism to recover their deposit.
- **Matches allowed impact**: "Medium — Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."

---

### Likelihood Explanation

NEAR Protocol requires explicit storage registration for NEP-141 token accounts. New users depositing BTC who have not previously interacted with the nBTC contract will not have a registered account. This is a realistic and common scenario for first-time bridge users, making this path publicly reachable without any privileged access.

---

### Recommendation

Move the registration check **before** `internal_deposit`. Only mint tokens after confirming the recipient account exists, or register the account automatically (funded by the attached storage deposit) before minting:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // fail before any state change
    }
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer to user
}
``` [1](#0-0) 

---

### Proof of Concept

1. User sends BTC to the bridge deposit address.
2. Relayer calls `verify_deposit_v2` / `safe_verify_deposit` on the satoshi-bridge; the Light Client validates the Merkle proof.
3. Bridge calls `safe_mint(user_account_id, amount, None)` on the nBTC contract.
4. `safe_mint` executes `internal_deposit(&self.bridge_id, amount)` — nBTC total supply increases by `amount`, bridge nBTC balance = `amount`.
5. `safe_mint` checks `self.token.accounts.get(&user_account_id)` → `None` (user never registered storage).
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — early exit, no transfer.
7. **Result**: User holds 0 nBTC. Bridge holds `amount` orphaned nBTC. User's BTC is locked in the bridge UTXO pool. No on-chain recovery path exists for the user. [2](#0-1)
