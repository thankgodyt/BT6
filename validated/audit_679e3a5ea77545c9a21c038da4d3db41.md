### Title
Unconditional Peras Certificate Acceptance Bypasses Chain-Selection Weight Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that accepts every inbound `PerasCert` unconditionally, without consulting any ledger view, stake distribution, or cryptographic proof. Because accepted certificates are immediately used to inflate the Peras weight of an attacker-chosen block in chain selection, an unprivileged peer can make an honest node permanently prefer a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` instance for all block types provides a default `validatePerasCert` that always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production diffusion layer. `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` as the sole gate before storing a certificate:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` is the handler registered for every inbound Peras-cert diffusion connection in the node-to-node layer: [3](#0-2) 

Once stored, `implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every certificate in the DB, using the attacker-supplied `pcCertBoostedBlock` as the boosted point:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

That snapshot is consumed by `takeVolatileSuffix` and `totalWeightOfFragment` during chain selection, so the fake boost directly influences which chain the node considers heaviest. [5](#0-4) 

The analog to the CometBFT height-mismatch is precise: the original bug uses vote-extension data anchored at height N-1 while comparing it against stake data at height N, producing an incorrect voting-power view. Here, `validatePerasCert` uses *no* ledger view at all — the certificate is accepted without any epoch-anchored stake snapshot, committee membership proof, or aggregate signature check — which is a strictly worse instance of the same class: the "current" view of committee authority is entirely absent from the validation path.

---

### Impact Explanation

**Critical — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

A single crafted certificate from one peer is sufficient to inject an arbitrary weight boost for any block point the attacker chooses. Because `takeVolatileSuffix` uses the Peras weight snapshot to determine the volatile suffix kept for rollback, and `totalWeightOfFragment` uses it to compare candidate chains, the attacker can make the node's chain-selection logic prefer a non-canonical fork over the honest chain, constituting a consensus safety failure reachable by an unprivileged peer.

---

### Likelihood Explanation

The attack requires only a standard node-to-node connection. No stake, keys, or operator access are needed. The `makePerasCertPoolWriterFromChainDB` path is active in the production diffusion layer for every peer that speaks the Peras-cert diffusion sub-protocol. The stub is self-documented as incomplete (`TODO: perform actual validation`), confirming the absence of any compensating control.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS/committee signature against the committee derived from the epoch-anchored stake snapshot for the round encoded in `pcCertRound`.
2. Confirms that the signing committee members hold sufficient combined stake to meet the quorum threshold (using the same epoch's `PerasVoteStakeDistr`, not a static or empty distribution).
3. Checks that `pcCertBoostedBlock` refers to a block within the valid Peras boost window for that round.

Until the full implementation is ready, the stub should at minimum reject all inbound certificates (return `Left`) rather than accept them, to prevent the chain-selection manipulation described above.

---

### Proof of Concept

```
1. Attacker connects to an honest node via the node-to-node protocol.

2. Attacker sends a PerasCert message:
     PerasCert { pcCertRound    = <any round>
               , pcCertBoostedBlock = <point on attacker's fork> }

3. makePerasCertPoolWriterFromChainDB calls:
     validatePerasCert mkPerasParams cert
   which returns Right unconditionally (SupportsPeras.hs:353-358).

4. processCerts calls:
     ChainDB.addPerasCertAsync chainDB (WithArrivalTime now validatedCert)
   storing the certificate in PerasCertDB.

5. implGetWeightSnapshot (PerasCertDB/Impl.hs:207-214) builds a
   PerasWeightSnapshot that maps <attacker's fork point> → perasWeight params.

6. On the next chain-selection event, takeVolatileSuffix / totalWeightOfFragment
   (Peras/Weight.hs:361-377) includes the fake boost when comparing the honest
   chain against the attacker's fork.

7. If perasWeight params is large enough relative to the honest chain's length
   advantage, the node switches to the attacker's non-canonical fork.
```
