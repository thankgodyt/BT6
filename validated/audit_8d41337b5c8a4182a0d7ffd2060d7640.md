Audit Report

## Title
`MetadataPayload::to_borsh()` Missing Chain Binding Enables Cross-Chain `deploy_token` Signature Replay — (`starknet/src/bridge_types.cairo`)

## Summary
`MetadataPayload::to_borsh()` serializes token metadata with no chain identifier, producing byte-for-byte identical Borsh encodings across every OmniBridge deployment that shares the same `omni_bridge_derived_address`. Because `_verify_borsh_signature` checks only that the keccak digest was signed by the stored derived address, a valid `deploy_token` signature obtained for one deployment unconditionally passes verification on any other deployment sharing that address, allowing an attacker to register and deploy an unauthorized bridge token without chain-specific MPC consent.

## Finding Description
`MetadataPayload::to_borsh()` ( [1](#0-0) ) encodes only a payload-type byte, token ID, name, symbol, and decimals — no chain identifier. By contrast, `TransferMessagePayload::to_borsh(chain_id: u8)` ( [2](#0-1) ) explicitly appends `chain_id` at two positions, binding the payload to a specific destination chain. `deploy_token` calls `payload.to_borsh()` with no chain argument ( [3](#0-2) ) and passes the result directly to `_verify_borsh_signature`. That function computes `keccak(borsh_bytes)` and verifies the Ethereum ECDSA signature against `self.omni_bridge_derived_address.read()` ( [4](#0-3) ) with no additional domain separator. The `omni_bridge_derived_address` is a constructor parameter, not derived per-chain inside the contract ( [5](#0-4) ). Consequently, for any two deployments sharing the same MPC-derived address, the Borsh bytes — and therefore the keccak digest — are identical for the same token metadata, and a signature valid on deployment A is equally valid on deployment B.

## Impact Explanation
An attacker replaying a valid `(signature, payload)` tuple on a second deployment causes the bridge to: (1) accept the signature as legitimate MPC authorization; (2) write the token mapping into `near_to_starknet_token` and `starknet_to_near_token`; (3) deploy a bridge token contract that the bridge can freely `mint` and `burn`. Any subsequent legitimate `fin_transfer` for that NEAR token ID on the target chain will mint to the attacker-registered contract. This constitutes an authorization bypass enabling deployer-equivalent actions without chain-specific MPC consent, matching the Critical scope for unauthorized token deployment and authorization bypass.

## Likelihood Explanation
The precondition — two deployments sharing the same `omni_bridge_derived_address` — is the standard production configuration for NEAR MPC-based bridges, where a single derived Ethereum address is used across all supported chains. `deploy_token` signatures are observable on-chain via emitted `DeployToken` events ( [6](#0-5) ) or obtainable by any user who triggers the MPC flow on chain A. No privileged access is required.

## Recommendation
Pass `omni_bridge_chain_id` into `MetadataPayload::to_borsh()` and append it to the serialized bytes, mirroring the pattern in `TransferMessagePayload::to_borsh()`:

```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);  // bind to destination chain
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
```

Update `deploy_token` to pass `self.omni_bridge_chain_id.read()` to `to_borsh`, and update the MPC signing logic to include the destination chain ID when producing `deploy_token` signatures.

## Proof of Concept
1. Deploy `OmniBridge` at `B_A` with `omni_bridge_chain_id = 1`, `omni_bridge_derived_address = MPC_ADDR`.
2. Deploy `OmniBridge` at `B_B` with `omni_bridge_chain_id = 2`, `omni_bridge_derived_address = MPC_ADDR` (same key).
3. Obtain a valid `(signature_A, payload)` for `deploy_token` on `B_A` by observing the on-chain `DeployToken` event or triggering the MPC flow for chain A.
4. Call `B_B.deploy_token(signature_A, payload)`.
5. `payload.to_borsh()` produces identical bytes on both contracts; `_verify_borsh_signature` passes on `B_B`; the token is deployed without any chain-B MPC authorization.
6. Assert `B_B.get_token_address(payload.token) != 0` — token is live on chain B with no legitimate MPC approval.
