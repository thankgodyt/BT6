### Title
Unconditional `validatePerasCert` Acceptance Bypasses Peras Certificate Validation, Enabling Unauthorized Chain Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance unconditionally accepts every inbound `PerasCert` as valid, performing zero cryptographic or structural checks. An unprivileged peer can craft a certificate for any block and any round, have it accepted by `validatePerasCert`, stored in the `PerasCertDB`, and used to trigger `chainSelectionForBlock` with a full Peras boost weight — causing an honest node to prefer an adversary-chosen chain without any legitimate quorum having been reached.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate before a received `PerasCert` is stored and acted upon. The only deployed instance — explicitly labelled a "degenerate instance for all blks to get things to compile" — implements this gate as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is verified, no quorum of votes is checked, no round-number bounds are enforced, and no eligibility proof is examined. The function returns `Right` for every possible input.

This result flows directly into the network inbound path. `makePerasVotePoolWriterFromChainDB` (and the `VoteDB` variant) calls `processCerts`, which calls `validatePerasCert mkPerasParams` on every certificate received from a peer:

```haskell
(validatePerasCert mkPerasParams)
(void . ChainDB.addPerasCertAsync chainDB)
``` [2](#0-1) 

`processCerts` partitions results into errors and successes; because `validatePerasCert` never returns `Left`, every cert is classified as valid and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`chainSelSync` then processes the cert: after a slot-age check it adds the cert to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block, giving it the full `perasWeight` boost:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is the full configured Peras boost weight assigned to the adversary-chosen block in chain selection — with no legitimate quorum behind it.

The analog to the external report is exact: just as the DeFi contract skips the collateral accumulation loop for zero-balance assets so that `totalCollateralInUSD >= borrowAmountInUSD` trivially holds as `0 >= 0`, here the validation function skips all checks so that `validatePerasCert cert` trivially holds as `Right cert` for every input.

### Impact Explanation

An unprivileged peer can make an honest node assign full Peras boost weight to any block the attacker chooses, without any legitimate quorum of stake-weighted votes having been cast. This directly bypasses the Peras certificate/vote verification mechanism. In chain selection, a boosted adversarial fork can outweigh the honest chain, causing the node to switch to and extend a non-canonical chain. This constitutes:

- **Bypass of Peras certificate validation** — the entire purpose of `validatePerasCert` is to ensure only legitimately quorum-backed certificates influence chain selection; the current implementation makes this check vacuous.
- **Chain selection manipulation** — an attacker with no stake can cause an honest node to prefer an adversarial chain by injecting a crafted cert for any block in the VolatileDB.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a `PerasCert` message. The `PerasCert` type contains only a `PerasRoundNo` and a `Point blk` (slot + hash), both of which are trivially constructable. No key material, VRF proof, or BLS aggregate signature is required to craft a valid-looking `PerasCert` under the current degenerate instance. The only guard is the slot-age check in `chainSelSync` (the boosted block must not be older than the immutable tip), which is easily satisfied by targeting a recent block already in the VolatileDB.

---

### Recommendation

Replace the degenerate `validatePerasCert` pass-through with a real implementation that:

1. Verifies the BLS aggregate signature over the certificate's round number and boosted block point against the claimed committee public keys.
2. Confirms that the certificate represents a quorum of stake-weighted votes (i.e., total stake ≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
3. Validates that the round number falls within the expected window relative to the current slot.
4. Checks voter eligibility proofs (VRF outputs for non-persistent committee members).

Until a real implementation is available, inbound certificates from peers should be rejected entirely rather than accepted unconditionally, to prevent the current bypass from being exploited.

---

### Proof of Concept

1. Connect to a target node via the ObjectDiffusion mini-protocol for Peras certificates.
2. Identify a recent block `B` in the node's VolatileDB (e.g., by observing ChainSync headers). Let `B` be on an adversarial fork that the node has not yet adopted.
3. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B) }` for any round `r`.
4. Send the cert to the node. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. `chainSelSync` adds the cert to `PerasCertDB` and calls `chainSelectionForBlock` for `B` with the full Peras boost.
6. The node's chain selection now treats `B`'s chain as having quorum support; if the boost is sufficient to overcome the honest chain's length advantage, the node switches to the adversarial fork.
