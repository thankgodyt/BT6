### Title
Silent Fallthrough in Legacy `ft_transfer` Locks nBTC in the Token Contract When `withdraw_relayer` Is Unset - (File: contracts/nbtc/src/lib.rs)

### Summary

The overridden `ft_transfer` in the nBTC contract contains a legacy Near Intents bridging path. When a user sends tokens to `receiver_id = nbtc_contract` with a `"WITHDRAW_TO:"` memo but `withdraw_relayer` is not configured, the function silently falls through and transfers the tokens to the nBTC contract's own balance. The nBTC contract has no mechanism to recover tokens held in its own account, permanently locking user funds.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `ft_transfer` implementation overrides the NEP-141 standard to support a legacy Near Intents withdrawal flow:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);  // correct path
        }
        // ← NO else-branch: falls through silently
    }

    self.token.ft_transfer(receiver_id, amount, memo);  // receiver_id == nbtc contract itself
}
```

When `withdraw_relayer` is not set (i.e., `read_withdraw_relayer_address()` returns `None`), the inner `if let` block is skipped and execution falls through to `self.token.ft_transfer(receiver_id, amount, memo)`. At this point `receiver_id` is still `env::current_account_id()` — the nBTC contract itself. The tokens are deposited into the nBTC contract's own token balance.

The nBTC contract has no function to recover tokens from its own balance:

- `burn()` calls `self.token.internal_withdraw(&self.bridge_id, ...)` — it only withdraws from `bridge_id`, not from `current_account_id()`.
- There is no admin rescue, sweep, or recovery function anywhere in the contract.
- The nBTC contract cannot initiate an outbound `ft_transfer` on itself.

For the transfer to succeed rather than panic, the nBTC contract must be registered as a token holder. This is achievable by any party via the public `storage_deposit` function, which accepts any `account_id`.

The `withdraw_relayer` is stored in raw contract storage via `env::storage_write` and is never initialized in the `new()` constructor — only via the separate `set_withdraw_relayer_address` call. This creates a deployment window during which the contract is live but the relayer is not yet configured.

### Impact Explanation

Any nBTC transferred to the nBTC contract's own address via the legacy `ft_transfer` path (when `withdraw_relayer` is unset) is permanently locked. There is no on-chain recovery path. The only remediation would be a contract upgrade, which requires privileged operator action. This constitutes permanent locking of user funds.

### Likelihood Explanation

The `withdraw_relayer` is not set in the `new()` constructor, creating a deployment window. Additionally, any user familiar with the Near Intents legacy flow who calls `ft_transfer(receiver_id=nbtc_contract, memo="WITHDRAW_TO:...")` during this window — or if the relayer is ever misconfigured — will lose their tokens. An attacker can pre-register the nBTC contract as a token holder via `storage_deposit` to ensure the transfer succeeds rather than panics, making the trap deterministic.

### Recommendation

Add an explicit `else` branch (or a `require!`) when `withdraw_relayer` is `None` to revert the transaction instead of silently falling through:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
    return self.token.ft_transfer(relayer, amount, memo);
}
```

Additionally, initialize `withdraw_relayer` in the `new()` constructor so there is no unconfigured window.

### Proof of Concept

1. Deploy the nBTC contract via `new()` — `withdraw_relayer` is not set.
2. Any party calls `storage_deposit(account_id: Some(nbtc_contract_id))` to register the nBTC contract as a token holder.
3. A user holding nBTC calls:
   ```
   nbtc.ft_transfer(
       receiver_id = nbtc_contract_id,
       amount = 1_000_000,
       memo = Some("WITHDRAW_TO:bc1q...")
   )
   ```
   with 1 yoctoNEAR attached.
4. The condition `receiver_id == env::current_account_id()` is true; `memo.starts_with("WITHDRAW_TO:")` is true.
5. `read_withdraw_relayer_address()` returns `None` — the inner `return` is skipped.
6. `self.token.ft_transfer(nbtc_contract_id, 1_000_000, memo)` executes — tokens move from the user to the nBTC contract's own balance.
