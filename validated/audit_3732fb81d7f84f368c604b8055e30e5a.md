### Title
`min_withdraw_amount` Guard Applied to `DepositProtocolFee` in `ft_on_transfer` — (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

---

### Summary

`ft_on_transfer` enforces `min_withdraw_amount` on every incoming token transfer before inspecting the message type. This means the check is applied to `DepositProtocolFee` messages as well as `Withdraw` messages, even though the minimum-withdrawal floor is semantically irrelevant to protocol-fee deposits. Any attempt to deposit protocol fees in an amount below `min_withdraw_amount` will panic and revert, permanently blocking that deposit path for small amounts.

---

### Finding Description

In `ft_on_transfer`, the guard

```rust
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
```

is placed unconditionally before the `match message { … }` dispatch. [1](#0-0) 

`ft_on_transfer` handles two distinct message variants: [2](#0-1) 

- `TokenReceiverMessage::DepositProtocolFee` — accumulates tokens into the protocol-fee pool; no withdrawal semantics.
- `TokenReceiverMessage::Withdraw { … }` — initiates a BTC withdrawal; the minimum-amount floor is meaningful here.

The `min_withdraw_amount` config field is documented exclusively as the minimum for user withdrawals: [3](#0-2) 

Because the guard fires before the message is decoded, a `DepositProtocolFee` call carrying any amount below `min_withdraw_amount` panics with `"Invalid amount"`. The tokens are returned to the sender by the NEP-141 `ft_transfer_call` rollback, so no funds are lost, but the deposit path is permanently broken for sub-threshold amounts.

This is the direct analog of the lottery `lpDeposit()` bug: a single guard is applied to a multi-purpose entry point, blocking a legitimate action (`DepositProtocolFee`) that has nothing to do with the condition being enforced (`min_withdraw_amount`).

---

### Impact Explanation

- The `cur_available_protocol_fee` pool cannot be topped up with amounts below `min_withdraw_amount`.
- If the pool is depleted and only sub-threshold replenishment is available, protocol-fee-funded operations stall until a sufficiently large deposit is made.
- No funds are stolen; the revert is clean. Impact is **Low** — publicly reachable invariant violation / stuck-state in a production bridge path without direct theft. [4](#0-3) 

---

### Likelihood Explanation

Any NEAR account holding nBTC can call `ft_transfer_call` with a `DepositProtocolFee` message. The trigger requires only that the deposited amount is below the configured `min_withdraw_amount`. This is a realistic operational scenario (e.g., sweeping a small residual balance into the fee pool). Likelihood is **Low-to-Medium** given the permissionless entry path.

---

### Recommendation

Move the `min_withdraw_amount` guard inside the `Withdraw` match arm so it only applies to withdrawal messages:

```rust
fn ft_on_transfer(...) -> PromiseOrValue<U128> {
    let amount = amount.into();
    let message = serde_json::from_str::<TokenReceiverMessage>(&msg).expect("INVALID MSG");
    let token_id = env::predecessor_account_id();
    require!(token_id == self.internal_config().nbtc_account_id, "Invalid token_id");
    match message {
        TokenReceiverMessage::DepositProtocolFee => { /* no min_withdraw_amount check */ ... }
        TokenReceiverMessage::Withdraw { .. } => {
            require!(amount >= self.internal_config().min_withdraw_amount, "Invalid amount");
            ...
        }
    }
}
```

---

### Proof of Concept

1. `min_withdraw_amount` is configured to `10_000` satoshis (a typical value).
2. An operator calls `ft_transfer_call` on the nBTC contract targeting the bridge, with `amount = 5_000` and `msg = '"DepositProtocolFee"'`.
3. `ft_on_transfer` fires; the unconditional `require!(5_000 >= 10_000, "Invalid amount")` panics.
4. The NEP-141 standard rolls back the transfer; the 5,000 satoshis are returned.
5. `cur_available_protocol_fee` is not updated; the fee pool remains unfunded.
6. Expected correct behavior: the deposit should succeed and add 5,000 satoshis to the protocol-fee pool, since `min_withdraw_amount` is irrelevant to fee deposits. [5](#0-4)
