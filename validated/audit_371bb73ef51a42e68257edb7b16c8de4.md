Audit Report

## Title
Fire-and-Forget Relayer Reimbursement with Unconditional State Finalisation Causes Permanent Loss of Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary
In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge permanently marks a fast transfer as finalised (or removes its record entirely) before confirming that the reimbursement token transfer to the relayer succeeded. The token transfer is dispatched with `.detach()`, so any failure is silently swallowed. Once the state is consumed, no retry path exists and the relayer's reimbursement tokens remain locked inside the bridge contract with no recovery mechanism.

## Finding Description

**`process_fin_transfer_to_other_chain` (L1980–2054):**

`unlock_tokens_if_needed` decrements the bridge's locked-token accounting at L1997–2001, then at L2029–2039 `send_tokens` is called with `.detach()`, and immediately at L2040 `mark_fast_transfer_as_finalised` writes `finalised = true` unconditionally:

```rust
// L2028-2040
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, U128(...), "").detach(); // fire-and-forget
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // unconditional
}
```

`mark_fast_transfer_as_finalised` (L2270–2277) sets `status.finalised = true` and re-inserts the record. The guard at L2010–2013 (`require!(!status.finalised, ...)`) then permanently blocks any re-attempt.

**`utxo_fin_transfer_fast` (L2518–2561):**

State is cleared *before* the detached send:

```rust
// L2529-2548
let amount = if fast_transfer.get_destination_chain() == ChainKind::Near {
    self.remove_fast_transfer(&fast_transfer.id()); // record deleted
    fast_transfer.amount
} else {
    self.mark_fast_transfer_as_finalised(&fast_transfer.id()); // finalised
    ...
};
self.send_tokens(..., fast_transfer_status.relayer, amount, "").detach(); // fire-and-forget
```

In the `ChainKind::Near` branch, `remove_fast_transfer` (L2279–2295) completely deletes the record, making the loss unrecoverable even in principle.

**Contrast with the correct pattern used in `process_fin_transfer_to_near` (L1867–1978):**

That function calls `send_tokens(...).then(fin_transfer_send_tokens_callback(...))` at L1957–1977. The callback at L1692–1746 inspects the promise result and reverts state (burns tokens, reverts lock actions, removes the fin-transfer record) on failure. The same callback-based approach is used in `fast_fin_transfer_to_near_callback` (L838–893) via `resolve_fast_transfer`. The two "other chain" paths are the only ones that skip this pattern.

**Why `send_tokens` can fail silently:**

`send_tokens` (L2056–2118) dispatches `ft_transfer` (L2103–2106) for non-deployed tokens, which requires the recipient to have NEP-141 storage registered on the token contract. A relayer who burned their entire balance of a token (as happens in `fast_fin_transfer_to_other_chain` at L932) may have 0 remaining balance; token contracts that auto-unregister at zero balance will reject the subsequent `ft_transfer`. For deployed tokens, `mint` (L2097–2101) is called on the external token contract — any panic there has the same silent effect. Because the promise is detached, neither failure propagates back to the bridge.

## Impact Explanation

When `send_tokens` fails after `.detach()`:

1. The locked-token accounting has already been decremented by `unlock_tokens_if_needed`.
2. The fast-transfer record is permanently finalised or deleted.
3. The reimbursement tokens remain inside the bridge contract with no accounting entry and no code path to release them.

This constitutes **permanent freezing of bridged funds** — specifically the relayer's pre-paid tokens that the bridge held in escrow for reimbursement. This matches the Critical allowed impact: *"permanent freezing of bridged funds across NEAR … flows."*

## Likelihood Explanation

The failure mode does not require any privileged compromise or external collusion. It is reachable through normal bridge operation:

- A trusted relayer executes a fast transfer to a non-NEAR destination via `fast_fin_transfer_to_other_chain`, which burns the relayer's token balance on NEAR (L932). After burning, the relayer's balance for that token is zero.
- Some NEP-141 token contracts automatically unregister accounts whose balance reaches zero, or the relayer may explicitly unregister to reclaim storage deposit.
- When canonical `fin_transfer` is later called for the same transfer ID, `process_fin_transfer_to_other_chain` attempts `ft_transfer` to the relayer. The call fails because the relayer has no storage registration.
- The failure is invisible to the bridge; the fast transfer is already finalised.

The scenario requires no victim mistake beyond normal operational behaviour (burning tokens, reclaiming storage). It is repeatable for every non-NEAR-destination fast transfer where the relayer's post-burn balance is zero.

## Recommendation

Replace the `.detach()` pattern in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast` with a callback that inspects the promise result before committing state, mirroring the existing `fin_transfer_send_tokens_callback` / `resolve_fast_transfer` pattern:

1. Call `send_tokens(...)` without `.detach()`.
2. Chain a `.then(Self::ext(...).reimburse_relayer_callback(&fast_transfer_id, ...))`.
3. Inside the callback, call `mark_fast_transfer_as_finalised` (or `remove_fast_transfer`) only if the promise succeeded.
4. On failure, leave the fast-transfer record untouched so the reimbursement can be retried, and re-lock the tokens in accounting.

`mark_fast_transfer_as_finalised` and `remove_fast_transfer` must never be called before the token transfer is confirmed.

## Proof of Concept

1. Deploy the bridge on a local NEAR testnet with a standard NEP-141 token that auto-unregisters at zero balance.
2. Register trusted relayer R. R acquires 100 units of token T and registers storage on T's contract.
3. R calls `fast_fin_transfer` for transfer ID `X` with a non-NEAR destination. `fast_fin_transfer_to_other_chain` burns R's 100 T tokens (L932). R's balance is now 0; the token contract unregisters R.
4. Call `fin_transfer` for transfer ID `X` (canonical proof). `fin_transfer_callback` routes to `process_fin_transfer_to_other_chain`. The bridge finds the fast-transfer record for `X`, calls `send_tokens(T, R, 100, "").detach()`, then calls `mark_fast_transfer_as_finalised`.
5. The `ft_transfer` to R fails (no storage registration). Because the promise was detached, the bridge does not observe the failure.
6. Assert: `get_fast_transfer_status(X).finalised == true` — no retry possible. Assert: bridge contract holds 100 T with no accounting entry. R has received 0 T. Funds are permanently frozen.
