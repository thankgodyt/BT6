### Title
Race Condition in `request_refund` Async Callback Allows Attacker to Front-Run and Redirect User's BTC Refund — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a publicly callable two-step async operation. Between the initial call and its callback, an attacker who observes the user's pending transaction can submit a competing `request_refund` for the same UTXO with an attacker-controlled `refund_address`. If the attacker's callback resolves first, the refund request is permanently registered with the attacker's BTC address, the user's callback hard-reverts, and the user's NEAR storage deposit is forfeited with no recovery path.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is publicly callable (it carries `#[payable]` and `#[pause]` but **not** `#[trusted_relayer]` on the function itself, unlike `verify_deposit_v2` which explicitly carries `#[trusted_relayer]`): [1](#0-0) 

The function delegates to `internal_request_refund`, which fires an async cross-contract call to the BTC Light Client and chains a callback: [2](#0-1) 

The storage deposit is consumed immediately and is explicitly **non-refundable**: [3](#0-2) 

In `request_refund_callback`, the code itself acknowledges the race window with a comment, but the only response is a hard revert: [4](#0-3) 

The `refund_address` validation only fires when `deposit_msg.refund_address` is `Some`. When it is `None` (the common case for standard deposits), **any caller may supply any BTC address**: [5](#0-4) 

**Attack path:**

1. User submits `request_refund(deposit_msg, user_btc_addr, tx_bytes, vout, proof)` where `deposit_msg.refund_address` is `None`. The call is visible on-chain immediately (NEAR transactions are public before their callbacks resolve).
2. Attacker observes the pending call and submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof)`. The `deposit_msg` and `tx_bytes` are fully visible in the user's transaction arguments.
3. NEAR cross-contract calls take multiple blocks to resolve. If the attacker's callback resolves first (attacker submitted in the same block or an earlier block), `refund_requests` is populated with `attacker_btc_addr`.
4. The user's callback hits the duplicate check and hard-reverts: `"Refund request already exists for this UTXO"`.
5. The user's non-refundable NEAR storage deposit is lost. The refund request now points to the attacker's BTC address.

After `unsafe_refund_timelock_sec` elapses, anyone may call `execute_refund`, which reads `refund_request.refund_address` and builds the PSBT paying that address: [6](#0-5) 

---

### Impact Explanation

**Certain (Medium):** The user's `request_refund` callback hard-reverts. The non-refundable NEAR storage deposit is permanently lost. The user must resubmit and pay again.

**Conditional (Critical):** If the DAO/Operator does not reject the attacker's refund request within `unsafe_refund_timelock_sec`, `execute_refund` is called and the full BTC deposit is sent to the attacker's address. The DAO has no on-chain signal distinguishing a legitimate request from an attacker-injected one — both carry a valid Light Client proof for the same UTXO.

---

### Likelihood Explanation

NEAR cross-contract calls resolve over multiple blocks (typically 2–4). An attacker who observes the user's `request_refund` transaction in block N can submit a competing call in block N or N+1, before either callback resolves. The `deposit_msg`, `tx_bytes`, `vout`, and `proof` are all supplied as plain call arguments and are fully visible on-chain. No privileged access, leaked key, or off-chain coordination is required. The only constraint is submitting before the user's callback resolves, which is a realistic window.

---

### Recommendation

Mirror the fix recommended in the reference report: instead of hard-reverting when the refund request already exists, check whether the existing request's `refund_address` matches the caller's. If it matches, return gracefully and refund the storage deposit. If it does not match, refund the storage deposit and emit an event, leaving the existing request intact. Additionally, consider requiring `deposit_msg.refund_address` to be set at deposit time so the refund destination is fixed before any `request_refund` can be submitted.

---

           satoshi-bridge::request_refund(deposit_msg, "bc1q_attacker...", tx_bytes, 0, proof)

Block N+2 (attacker callback resolves first):
  satoshi-bridge::request_refund_callback(deposit_msg, "bc1q_attacker...", ...)
    → refund_requests["txid@0"] = RefundRequest { refund_address: "bc1q_attacker...", ... }
    → OK

  satoshi-bridge::request_refund_callback(deposit_msg, "bc1q_user...", ...)
    → require!(!refund_requests.contains_key("txid@0"))  ← PANICS
    → User's NEAR deposit is lost; no refund.

After unsafe_refund_timelock_sec:
  Anyone → satoshi-bridge::execute_refund("txid@0", ...)
    → builds PSBT paying "bc1q_attacker..."
    → MPC signs → BTC sent to attacker

    pub fn request_refund(

        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,

            );

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,

        )
    }
