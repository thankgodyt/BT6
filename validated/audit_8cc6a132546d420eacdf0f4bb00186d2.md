### Title
Unvalidated `refund_address` in `request_refund_callback` causes `execute_refund` to panic and temporarily locks deposit UTXOs — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

`request_refund_callback` stores the caller-supplied `refund_address` string verbatim without parsing it through `Address::parse`. Later, `build_refund_output` calls `Address::parse(...).expect("Invalid refund address")`, which panics on any malformed string. Because `execute_refund` is a public, unpermissioned entry point, any caller can trigger this panic repeatedly, permanently blocking the refund path for that UTXO until a DAO/Operator calls `reject_refund`.

---

### Finding Description

**Entry point — `request_refund` is public:**

`request_refund` carries only `#[payable]` and `#[pause]` guards; it has no `#[trusted_relayer]` attribute on the function itself. The `#[trusted_relayer]` on the impl block is the system-wide macro configuration (see `lib.rs` lines 175-179), not a per-method gate. Individual methods that are actually gated carry their own `#[trusted_relayer]` (e.g., `verify_refund_finalize`, `remove_refund_pending_tx_id`). `request_refund`, `reject_refund`, and `execute_refund` do not. [1](#0-0) 

**`request_refund_callback` does not validate `refund_address`:**

The only address-related check in the callback is:
```rust
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
```
This verifies that the *deposit transaction output* matches the bridge's deposit address — it says nothing about `refund_address`. The `refund_address` string is stored as-is into `RefundRequest.refund_address` with zero parsing. [2](#0-1) 

**`build_refund_output` panics on an invalid address:**

```rust
let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
    .expect("Invalid refund address");
```
`Address::parse` returns `Err(String)` for any unrecognised format; `.expect(...)` converts that into a NEAR `env::panic_str`, aborting the transaction. [3](#0-2) 

**`execute_refund` calls `build_refund_output` unconditionally:**

`execute_refund` → `internal_execute_refund` → `build_refund_output`. Every call panics as long as the stored `refund_address` is unparseable, and the `RefundRequest` is never removed on panic (state rollback), so the UTXO stays locked. [4](#0-3) 

---

### Impact Explanation

The deposit UTXO is stuck in `refund_requests` and cannot be refunded. `execute_refund` panics on every call. The only escape is a privileged `reject_refund` call by DAO/Operator, which removes the request but does not return funds to the user — the user must then re-submit a new `request_refund` with a valid address. This constitutes **attacker-triggered temporary locking of bridged funds requiring operator intervention** (Medium scope). [5](#0-4) 

---

### Likelihood Explanation

- `request_refund` is callable by any NEAR account (no role gate, no whitelist).
- The attacker only needs to know a valid deposit transaction (publicly visible on-chain) and supply `refund_address = "garbage"`.
- If `deposit_msg.refund_address` is `None` (the common case for standard deposits), there is no pre-authorized address to enforce, so any string is accepted.
- The attack is cheap: one `request_refund` call with sufficient attached NEAR for storage. [6](#0-5) 

---

### Recommendation

Validate `refund_address` inside `request_refund_callback` (or `internal_request_refund`) before storing it:

```rust
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This ensures that any address accepted at request time is guaranteed to be parseable at execution time, eliminating the panic path entirely. [7](#0-6) 

---

### Proof of Concept

1. Observe a real deposit transaction `tx_bytes` to the bridge (publicly visible on Bitcoin).
2. Call `request_refund(deposit_msg, "NOT_A_VALID_ADDRESS", tx_bytes, vout, proof, None)` with sufficient attached NEAR.
3. `request_refund_callback` passes: the deposit output's `script_pubkey` matches the bridge's deposit address; `refund_address` is stored verbatim.
4. Wait for `config.unsafe_refund_timelock_sec` to elapse.
5. Call `execute_refund(utxo_storage_key, None)`.
6. `build_refund_output` calls `Address::parse("NOT_A_VALID_ADDRESS", chain).expect(...)` → **panic**.
7. The `RefundRequest` remains in `refund_requests`; the UTXO is locked until DAO/Operator calls `reject_refund`. [8](#0-7)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
    }
