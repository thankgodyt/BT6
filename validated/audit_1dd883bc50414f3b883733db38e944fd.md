### Title
`safe_mint` silently returns `U128(0)` after minting tokens to bridge balance when recipient account is unregistered — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the nBTC contract mints tokens to the bridge's own balance **before** checking whether the recipient account is registered. When the recipient is unregistered, the function returns `U128(0)` without reverting. Because NEAR cross-contract state changes are committed independently, the bridge's callback panic (on receiving `U128(0)`) reverts only the bridge's own state, while the nBTC tokens already minted to the bridge's balance remain committed. This produces a broken-callback / stuck-state condition requiring operator intervention.

---

### Finding Description

In `contracts/nbtc/src/lib.rs` lines 100–124, `safe_mint` executes in this order:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted to bridge

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));                   // ← silent early return, no revert
}
``` [1](#0-0) 

The function is documented (via the `verify_deposit_v2` docstring) as the "safe deposit" path that "reverts the whole transaction if minting fails (no lost & found)". [2](#0-1) 

However, `safe_mint` does **not** revert — it returns `U128(0)` after state has already been mutated. In NEAR's async cross-contract call model, the nBTC contract's state change (tokens deposited to `bridge_id`) is committed the moment `safe_mint` returns. When the bridge's callback subsequently panics on the `U128(0)` result (the expected "failure" signal), only the bridge's own state is rolled back; the nBTC contract's minted balance is not.
