### Title
`checkPreferTheirsOverOurs` Ignores Peras Weights, Enabling Incorrect Peer Disconnection During Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer's header exceeds the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to disconnect. This check unconditionally uses `emptyPerasWeightSnapshot` (zero Peras weight) instead of the real `PerasWeightSnapshot` from the ChainDB. When Peras is enabled, this causes the node to evaluate chain preference using only block count, not total Peras weight, producing the wrong disconnect decision. An adversary can exploit this to cause an honest node to disconnect from peers serving the Peras-preferred chain while remaining connected to a chain that is longer by block count but lighter by total Peras weight — a direct chain-selection bypass.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever the forecast horizon is exceeded and the node must decide whether to keep waiting for a peer or disconnect:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

The `emptyPerasWeightSnapshot` constant is defined as a `PerasWeightSnapshot` with an empty map — it contributes zero weight boost to every block:

```haskell
emptyPerasWeightSnapshot :: PerasWeightSnapshot blk
emptyPerasWeightSnapshot = PerasWeightSnapshot Map.empty
``` [2](#0-1) 

By contrast, the actual chain selection in `ChainSel.hs` and `compareAnchoredFragments` uses the real `PerasWeightSnapshot` from the ChainDB, which includes all Peras certificate boosts:

```haskell
compareAnchoredFragments cfg weights frag1 frag2
  | isEmptyPerasWeightSnapshot weights = ...  -- block-count only
  | otherwise =
      case AF.intersect frag1 frag2 of
        Just (_, _, oursSuffix, candSuffix) ->
          compare
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix)
``` [3](#0-2) 

Under Peras, `totalWeight = blockCount + perasBoost`. The `SecurityParam` is also reinterpreted as a weight bound, not a pure block count:

```haskell
-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
``` [4](#0-3) 

The disconnect guard and the actual chain selection therefore use **different comparison functions** when Peras is active. The TODO comment in the source explicitly acknowledges this divergence and flags it for removal.

---

### Impact Explanation

**Scenario — adversary exploits the mismatch:**

1. Honest peer H serves a chain of block count 99 with Peras boosts totalling weight 200 → total weight 299.
2. Adversarial peer A serves a chain of block count 101 with no Peras boosts → total weight 101.
3. A header from H exceeds the forecast horizon. `checkPreferTheirsOverOurs` evaluates using `emptyPerasWeightSnapshot`: H's block count 99 < our block count 100 → `shouldSwitch = False` → **H is disconnected**.
4. A header from A also exceeds the forecast horizon. `checkPreferTheirsOverOurs` evaluates: A's block count 101 > 100 → `shouldSwitch = True` → **A is kept**.
5. The node eventually validates A's headers and runs real chain selection. A's total weight 101 < our total weight (100 + our own boosts). The node does not switch, but it has already lost its connection to H, the Peras-preferred chain.

The node is now unable to adopt the Peras-preferred chain because the only peer serving it was disconnected. This violates the chain-selection invariant that the node should converge on the chain with the highest total Peras weight.

**Impact class:** High — chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical (Peras-lighter) chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

Peras is currently disabled by default (`emptyPerasWeightSnapshot` is used throughout when Peras is off, so there is no observable difference today). However:

- The code path is in production files and will be exercised as soon as Peras is enabled.
- The TODO comment (`https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is wrong but have not yet fixed it.
- The attack requires only that an adversary serve a chain longer by block count than the honest Peras-heavy chain — no key compromise, no stake majority, no privileged access.
- The GSM `candidateOverSelection` check in the LoE/GDD path also uses `emptyPerasWeightSnapshot` for the same reason, widening the surface. [5](#0-4) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the real `PerasWeightSnapshot` read from the ChainDB (the same snapshot used by `chainSelection`). The check must use the same comparison function as actual chain selection to remain consistent:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis = do
  weights <- getPerasWeightSnapshot cdb   -- read real snapshot
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This is exactly what the linked issue (`cardano-peras/issues/64`) tracks. The fix must be applied before Peras is enabled on any network.

### Proof of Concept

```
Setup (Peras enabled, k = 100):
  Our chain:   blocks 1..100, Peras boost on block 50 = +150  → total weight 250
  Peer H:      blocks 1..99,  Peras boost on block 60 = +200  → total weight 299
  Peer A:      blocks 1..101, no Peras boosts                 → total weight 101

Step 1: H sends header 100 (beyond forecast horizon).
  checkPreferTheirsOverOurs with emptyPerasWeightSnapshot:
    H block count 99 < our block count 100 → ShouldNotSwitch → disconnect H.

Step 2: A sends header 102 (beyond forecast horizon).
  checkPreferTheirsOverOurs with emptyPerasWeightSnapshot:
    A block count 101 > our block count 100 → ShouldSwitch → keep A.

Step 3: Forecast horizon advances. Node validates A's headers.
  Real chain selection: A total weight 101 < our total weight 250 → no switch.

Result: Node stays on its current chain (weight 250).
        Node can never adopt H's chain (weight 299, the Peras-preferred chain)
        because H was disconnected and will not reconnect within the same session.
        The adversary (A) successfully prevented the node from converging on the
        Peras-preferred chain using only a longer-by-block-count chain.
``` [6](#0-5) [7](#0-6)

compareAnchoredFragments cfg weights frag1 frag2
  -- Optimize the case where Peras is disabled.
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition frag1 frag2) $
        case (frag1, frag2) of
          (Empty _, Empty _) ->
            -- The fragments intersect but are equal: their anchors must be equal,
            -- and hence the fragments represent the same chain. They are therefore
            -- equally preferable.
            EQ
          (Empty anchor, _ :> tip') ->
            -- Since the fragments intersect, but the first one is empty, its anchor
            -- must lie somewhere along the the second. If it is the tip, the two
            -- fragments represent the same chain and are equally preferable. If
            -- not, the second chain is a strict extension of the first and is
            -- therefore strictly preferable.
            if blockPoint tip' == AF.castPoint (AF.anchorToPoint anchor)
              then EQ
              else LT
          (_ :> tip, Empty anchor') ->
            -- This case is symmetric to the previous
            if blockPoint tip == AF.castPoint (AF.anchorToPoint anchor')
              then EQ
              else GT
          (_ :> tip, _ :> tip') ->
            -- Case 4
            compare
              (selectView cfg (getHeader1 tip))
              (selectView cfg (getHeader1 tip'))
  | otherwise =
      case AF.intersect frag1 frag2 of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          compare
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix)

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).

-- total weight @2 + 2 * 14 = 30@.
