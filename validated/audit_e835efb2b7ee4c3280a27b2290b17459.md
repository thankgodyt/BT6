### Title
Missing Transfer Hook Extra Accounts in `transfer_checked` CPI Causes Permanent Vault Fund Lock — (File: `solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

---

### Summary

The Solana `bridge_token_factory` program calls `transfer_checked` in both `init_transfer` and `finalize_transfer` without providing the extra accounts required by the SPL Token-2022 Transfer Hook extension. The project's own `SECURITY.md` acknowledges this limitation but misclassifies it as "denial, not fund loss." A malicious token creator can exploit the asymmetry between the two instructions to permanently freeze bridged funds in the vault.

---

### Finding Description

Both `init_transfer` and `finalize_transfer` invoke `anchor_spl::token_2022::transfer_checked` using a bare `CpiContext` that contains only the four standard accounts (`from`, `to`, `authority`, `mint`). No transfer hook extra accounts are ever resolved or appended.

**`init_transfer.rs` (Solana → NEAR, lock path):**

```rust
transfer_checked(
    CpiContext::new(
        self.token_program.to_account_info(),
        TransferChecked {
            from: self.from.to_account_info(),
            to: vault.to_account_info(),
            authority: self.user.to_account_info(),
            mint: self.mint.to_account_info(),
        },
    ),
    ...
)?;
``` [1](#0-0) 

**`finalize_transfer.rs` (NEAR → Solana, release path):**

```rust
transfer_checked(
    CpiContext::new_with_signer(
        self.token_program.to_account_info(),
        TransferChecked {
            from: vault.to_account_info(),
            to: self.token_account.to_account_info(),
            authority: self.authority.to_account_info(),
            mint: self.mint.to_account_info(),
        },
        &[&[AUTHORITY_SEED, &[self.config.bumps.authority]]],
    ),
    ...
)?;
``` [2](#0-1) 

The `SECURITY.md` acknowledges the gap but asserts "denial, not fund loss":

> **Token-2022 tokens with transfer hooks are not supported** — Transfer hook extra account metas are not included in instruction account sets. Affected tokens will fail at runtime (denial, not fund loss). [3](#0-2) 

This classification is **incorrect** for the following attack scenario, which exploits the asymmetry between the two instructions:

**Attack path:**

1. A malicious token creator deploys a Token-2022 mint with the `TransferHook` extension present but with `hook_program_id = None`. With no hook program set, SPL Token-2022 skips hook invocation, so all transfers succeed normally.
2. The creator calls `log_metadata` to register the token on the bridge. This creates the vault PDA. No validation of the `TransferHook` extension is performed. [4](#0-3) 

3. Legitimate users call `init_transfer` to lock tokens in the vault (Solana → NEAR direction). Because the hook program is still `None`, `transfer_checked` succeeds and tokens accumulate in the vault.
4. The NEAR bridge mints the corresponding bridged tokens to users on NEAR.
5. The attacker (as mint authority) calls `spl_token_2022`'s `UpdateTransferHook` instruction to set a real hook program on the mint.
6. Users attempt to bridge back (NEAR → Solana). The NEAR bridge burns their NEAR tokens.
7. The relayer calls `finalize_transfer` on Solana to release tokens from the vault. The `transfer_checked` CPI now fails because the hook program is active but no hook extra accounts are provided. The instruction reverts.
8. The nonce is not consumed (transaction reverted), but **no retry can ever succeed** because the `FinalizeTransfer` account struct has no mechanism to accept or forward transfer hook extra accounts to the CPI. The vault tokens are permanently locked. [5](#0-4) 

There is no admin recovery instruction that can drain the vault. The only exit path for vault funds is `finalize_transfer`.

---

### Impact Explanation

**Critical — Permanent freezing of bridged funds.**

Users who bridged native Token-2022 tokens from Solana to NEAR and then attempt to bridge back suffer a double loss: their NEAR-side tokens are burned by the NEAR bridge, and their Solana-side tokens remain permanently locked in the vault PDA with no recovery path. The vault can accumulate funds from multiple users before the hook is activated, amplifying the impact.

---

### Likelihood Explanation

**Medium.**

- Token-2022 with `TransferHook` is a supported and documented SPL extension.
- The `TransferHook` extension allows the mint authority to update the hook program at any time via `UpdateTransferHook`.
- The attack requires a deliberate malicious token creator, but no privileged bridge role is needed — `log_metadata` is permissionless.
- The `SECURITY.md` itself confirms the missing hook account support, meaning the vulnerable code path is confirmed present in production. [6](#0-5) 

---

### Recommendation

**Option A (preferred):** In `log_metadata`, inspect the mint's Token-2022 extensions and reject registration if the `TransferHook` extension is present (regardless of whether the hook program is currently `None`), since the hook program can be set at any future time by the mint authority.

**Option B:** Add full transfer hook support to both `init_transfer` and `finalize_transfer` by resolving the extra account metas from the mint's `TransferHook` extension and appending them to the `CpiContext` via `with_remaining_accounts`, mirroring the pattern used by `spl_transfer_hook_interface::onchain::add_extra_accounts_for_execute_cpi`.

---

### Proof of Concept

```
1. Create Token-2022 mint M with TransferHook extension, hook_program_id = None.
2. Call log_metadata(M) → vault PDA V is created. No extension check performed.
3. User A calls init_transfer(M, amount=1000) → transfer_checked(A→V) succeeds (hook=None).
   NEAR bridge mints 1000 bridged-M to user A on NEAR.
4. Attacker calls UpdateTransferHook(M, hook_program_id = <malicious_hook>).
5. User A calls ft_on_transfer on NEAR bridge to bridge back 1000 bridged-M.
   NEAR bridge burns 1000 bridged-M. Transfer event emitted.
6. Relayer calls finalize_transfer(M, amount=1000, recipient=A).
   transfer_checked(V→A_token_account) → SPL Token-2022 invokes hook → hook accounts
   missing from CPI context → instruction fails.
7. Relayer retries indefinitely; always fails. Nonce not consumed (tx reverted each time).
8. 1000 tokens permanently locked in vault V. User A's NEAR tokens are burned.
   No admin instruction exists to recover vault funds.
``` [7](#0-6) [8](#0-7)
