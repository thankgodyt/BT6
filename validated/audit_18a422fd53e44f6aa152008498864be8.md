### Title
Caller-Controlled `gas_fee` in `request_refund` Can Permanently Lock User BTC - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`internal_request_refund` accepts a caller-supplied `gas_fee: Option<u128>` whose only validation is that it is less than the deposit amount. An unprivileged attacker who knows a victim's `DepositMsg` can call `request_refund` with `gas_fee = Some(1)`, storing a refund request with a 1-satoshi Bitcoin transaction fee. Once `execute_refund` is subsequently called, the UTXO is inserted into `verified_deposit_utxo`. If the operator then rejects the poisoned request, the UTXO remains in `verified_deposit_utxo` and `request_refund_callback` permanently blocks any new refund request for that UTXO, locking the victim's BTC forever.

### Finding Description

`internal_request_refund` passes the caller-supplied `gas_fee` through to the callback with only one guard:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

`gas_fee = Some(1)` trivially satisfies `1 < deposit_amount`. The value is then stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,
    ...
};
``` [2](#0-1) 

`refund_execution_inputs` later uses `refund_request.gas_fee` as the actual Bitcoin miner fee (input value minus output value):

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
``` [3](#0-2) 

A 1-satoshi fee is far below the minimum relay fee rate on Bitcoin (~1–2 sat/vbyte × ~200 bytes = ~200–400 sat minimum), so the broadcast transaction is never mined.

When `execute_refund` is called (callable by anyone after the timelock), `finalize_refund_with_psbt` marks the UTXO as verified:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

After the operator rejects the poisoned request via `internal_reject_refund` (which removes it from `refund_requests`), any attempt to create a new refund request hits this check in `request_refund_callback`:

```rust
require!(
    !self
        .data()
        .verified_deposit_utxo
        .contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
``` [5](#0-4) 

Unlike `load_refund_request_for_execute`, this check has **no** `|| refund_request.executed` escape hatch. With the refund request gone (rejected), the `executed` flag is inaccessible, and the UTXO is permanently blocked from any new refund request. The victim's BTC is irrecoverably locked.

### Impact Explanation

The victim's BTC deposit UTXO becomes permanently unrecoverable:
- `verify_deposit` is blocked because the UTXO is in `verified_deposit_utxo`.
- A new `request_refund` is blocked by the same `verified_deposit_utxo` check.
- `execute_refund` can only be re-called while the (now-rejected) refund request still exists.

This constitutes **permanent locking of user funds**, matching the Critical impact tier: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

The attack requires the attacker to know the victim's `DepositMsg`. Since the deposit address is derived from the `DepositMsg` hash and BTC transactions are public, the `DepositMsg` is typically shared with relayers and may be embedded in the BTC transaction (e.g., OP_RETURN). No privileged access is required. The attacker only needs to attach sufficient NEAR for storage and submit a valid light-client proof — both are publicly accessible operations. The `unsafe_refund_timelock_sec` delay gives the operator a window to reject, but if `execute_refund` is called before rejection (by the attacker or anyone else after the timelock), the permanent lock is triggered.

### Recommendation

1. **Enforce a minimum `gas_fee`**: Reject any caller-supplied `gas_fee` below `self.get_refund_gas_fee()` (the operator-configured default). Only allow values at or above the configured minimum.
2. **Restrict who can supply `gas_fee`**: Require the caller to be the original depositor (match `deposit_msg.account_id` against `env::predecessor_account_id()`) or a privileged role before accepting a non-default `gas_fee`.
3. **Allow recovery after rejection**: When a refund request is rejected, also remove the corresponding entry from `verified_deposit_utxo` (or add a separate "refund-executed" set distinct from "deposit-verified") so that a new refund request can be created.

### Proof of Concept

1. Victim sends 0.01 BTC to their deposit address. The deposit cannot proceed (e.g., bridge paused).
2. Attacker obtains the victim's `DepositMsg` (from OP_RETURN or relayer gossip) and the raw BTC transaction bytes.
3. Attacker calls `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, gas_fee: Some(1))`.
4. `request_refund_callback` stores `RefundRequest { gas_fee: 1, ... }`. Check `1 < 1_000_000` passes.
5. After `unsafe_refund_timelock_sec` elapses, attacker (or anyone) calls `execute_refund`.
6. `finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo` and broadcasts a refund tx with 1-satoshi fee — never mined.
7. Operator notices the stuck refund and calls `reject_refund` → refund request deleted.
8. Operator attempts `request_refund` again for the same UTXO → `request_refund_callback` panics: `"UTXO already verified via deposit"`.
9. Victim's 0.01 BTC is permanently locked with no recovery path.
