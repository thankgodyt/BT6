Audit Report

## Title
`_pause` Full-Replacement Semantics Silently Clear Pause Bits, Enabling `deployToken` Bypass After `pauseAll()` — (`evm/src/omni-bridge/contracts/SelectivePausableUpgradable.sol`)

## Summary

`_pause(flags)` performs a full assignment (`$._pausedFlags = flags`) rather than a bitwise OR accumulation. After `pauseAll()` sets all three pause bits to `0b111`, a subsequent `pause(PAUSED_FIN_TRANSFER | PAUSED_INIT_TRANSFER)` replaces the stored value with `0b011`, silently clearing `PAUSED_DEPLOY_TOKEN`. Because no separate `unpause` function exists, this replacement is the only mechanism available to selectively manage pause state, making the clearing of unintended bits a natural consequence of normal admin operation. An external caller holding a valid pre-issued MPC signature can then invoke `deployToken` and permanently bind a token address during an active emergency pause.

## Finding Description

**Root cause — `_pause` is a setter, not an accumulator:**

`SelectivePausableUpgradable._pause` at line 115 assigns the caller-supplied bitmask directly:

```solidity
$._pausedFlags = flags;   // full replacement
``` [1](#0-0) 

`OmniBridge.pause` passes the caller-supplied value straight through with no OR-accumulation: [2](#0-1) 

`pauseAll()` sets `_pausedFlags = 7` (all three bits): [3](#0-2) 

Flag layout: [4](#0-3) 

**No `unpause` function exists.** The contract exposes only `pause(flags)` and `pauseAll()`. An admin who wants to selectively unpause one flag while keeping others active *must* call `pause(remaining_flags)`. This makes the replacement semantic the only available tool for fine-grained pause management, and makes the accidental clearing of unintended bits a predictable operational outcome, not a contrived mistake.

**Exploit sequence:**

| Step | Call | `_pausedFlags` |
|------|------|----------------|
| 1 | `pauseAll()` | `0b111` = 7 |
| 2 | `pause(PAUSED_FIN_TRANSFER \| PAUSED_INIT_TRANSFER)` = `pause(3)` | `0b011` = 3 — **bit 2 cleared** |
| 3 | `paused(PAUSED_DEPLOY_TOKEN)` = `(3 & 4) != 0` | **`false`** |

After step 2, `deployToken`'s guard passes: [5](#0-4) 

The only remaining check is a valid ECDSA signature from `nearBridgeDerivedAddress`. Pre-issued metadata signatures for queued token deployments are a normal part of the bridge's token-onboarding flow. An external caller (relayer or attacker) replaying such a signature can complete the call.

Token registration is then permanently written: [6](#0-5) 

## Impact Explanation

This is a **pause bypass** and **unauthorized token binding** within the Critical scope. A new `BridgeToken` ERC1967 proxy is deployed and permanently bound to a NEAR token ID during an active emergency pause. Once `finTransfer` is later unpaused, `finTransfer` will mint tokens to any recipient for that token address because `isBridgeToken[proxy] == true`: [7](#0-6) 

If the emergency was triggered by a signing-key incident, a pre-issued signature can be replayed to bind a malicious or duplicate token, enabling unauthorized minting once the pause is lifted. This matches the Critical impact class: *pause bypass that lets an attacker execute bridge/token/deployer actions*, and *token metadata binding confusion that changes protocol balances*.

## Likelihood Explanation

- The absence of a dedicated `unpause` function means `pause(subset_flags)` is the only mechanism for selective pause management. An admin performing routine pause adjustment after `pauseAll()` will naturally call `pause(PAUSED_FIN_TRANSFER | PAUSED_INIT_TRANSFER)` — the function signature gives no indication this also unpauses `PAUSED_DEPLOY_TOKEN`.
- Pre-issued metadata signatures for pending token deployments are a realistic precondition in normal bridge operation.
- No attacker-controlled privileged role is required. The external caller only needs a valid pre-issued signature, which is a standard artifact of the token-onboarding flow.
- The window is created by the admin's own legitimate operational call, not by any attacker action.

## Recommendation

Separate pause accumulation from selective unpause:

```solidity
function _pause(uint256 flags) internal virtual {
    SelectivePausableStorage storage $ = _getSelectivePausableStorage();
    $._pausedFlags |= flags;   // additive only
    emit Paused(_msgSender(), $._pausedFlags);
}

function _unpause(uint256 flags) internal virtual {
    SelectivePausableStorage storage $ = _getSelectivePausableStorage();
    $._pausedFlags &= ~flags;  // selective clear
    emit Unpaused(_msgSender(), $._pausedFlags);
}
```

Expose a corresponding `unpause(uint256 flags)` external function gated by `DEFAULT_ADMIN_ROLE`. This makes pause and unpause explicit, independent operations and eliminates the silent clearing of unintended bits.

## Proof of Concept

```solidity
// Setup: deploy OmniBridge, grant roles to admin
bridge.pauseAll();
assert(bridge.paused(PAUSED_DEPLOY_TOKEN));   // true — all paused

// Admin performs routine selective pause adjustment
bridge.pause(PAUSED_FIN_TRANSFER | PAUSED_INIT_TRANSFER); // = pause(3)
assert(!bridge.paused(PAUSED_DEPLOY_TOKEN));  // TRUE — deployToken is now open

// External caller replays a pre-issued valid MPC signature
address token = bridge.deployToken(validSig, metadata);

// Token is permanently registered
assert(bridge.nearToEthToken(metadata.token) == token);
assert(bridge.isBridgeToken(token));

// finTransfer is still paused — minting deferred until unpause
// Once unpaused, finTransfer will mint for this token without restriction
```

A local Foundry test can reproduce this exactly: deploy the contract, call `pauseAll()`, call `pause(3)`, verify `paused(PAUSED_DEPLOY_TOKEN)` returns `false`, then call `deployToken` with a signature generated from a test MPC key to confirm successful token registration.
