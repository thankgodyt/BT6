### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic checks. An unprivileged peer can send a crafted certificate boosting any block on an adversarial fork, which is accepted as "validated," stored in the `PerasCertDB`, and fed directly into chain selection — potentially causing an honest node to switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate received from a peer is stored and acted upon. The default instance (labeled as a "degenerate instance for all blks to get things to compile") implements this gate as an unconditional pass-through:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }

No override of this instance exists for Cardano blocks in the production code. The production certificate ingestion path in `makePerasCertPoolWriterFromChainDB` explicitly calls `validatePerasCert mkPerasParams` as the validation function passed to `processCerts`:

```haskell

``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass (which they always do), forwards them to `addCert` — which is `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which adds it to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

The boost weight applied is `perasWeight = 15` from `mkPerasParams`: [5](#0-4) 

The checks that are entirely absent from `validatePerasCert` include:
- BLS aggregate signature verification over the claimed voter set
- Committee membership and eligibility verification (VRF-based sortition for non-persistent members)
- Quorum threshold check (≥ 3/4 stake + safety margin)
- Round number plausibility relative to the current chain state

The concrete `PerasCert` type in `Peras.Cert.V1` carries all the fields needed for these checks (`pcSignature`, `pcVoters`, `pcRoundNo`, `pcBoostedBlock`), and the `WFALS`/`EveryoneVotes` committee implementations in `Committee/WFALS.hs` and `Committee/EveryoneVotes.hs` provide `implVerifyCert` that performs them — but none of this is wired into the production inbound path. [6](#0-5) 

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A Peras certificate boost of weight 15 is added to the chain-selection weight of the boosted block. An adversary who controls a minority fork can send a crafted certificate naming any block on that fork. The node accepts it without verification, stores it, and re-runs chain selection with the artificial weight boost applied. If the adversarial fork is within `k` blocks of the current tip and the boost tips the weight comparison, the node switches to the adversarial chain. Because the `PerasCertDB` persists the certificate, the boost is durable across chain-selection re-runs until the certificate is garbage-collected.

---

### Likelihood Explanation

**High.** The Peras certificate diffusion mini-protocol is an externally reachable network endpoint. Any peer that connects can send a `[PerasCert]` batch. The crafted certificate requires only a valid CBOR encoding of `PerasCert` (round number + block point), which is trivially constructable. No cryptographic material, stake, or privileged access is required. The only existing filter is a deduplication check on `pcCertRound` — an attacker simply uses a fresh round number for each attempt.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature (`pcSignature`) over the claimed election ID and boosted block using the aggregate verification key derived from the declared voter set.
2. Verifies each voter's committee membership and eligibility (persistent membership check or VRF-based sortition proof for non-persistent members) against the current stake distribution.
3. Checks that the total stake of the declared voters meets the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
4. Validates the round number is plausible relative to the current chain state.

The `implVerifyCert` functions already implemented in `Committee/WFALS.hs` and `Committee/EveryoneVotes.hs` provide the correct template. The `PerasCfg` passed to `validatePerasCert` must be extended to carry the current stake distribution and committee parameters needed for these checks. [7](#0-6) 

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to a target node as a peer via the Peras certificate diffusion mini-protocol.
2. Construct a `PerasCert` with:
   - `pcCertRound` = any round number not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` (slot + hash) of a block on a competing minority fork
3. Send the certificate batch to the target node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = PerasWeight 15}` unconditionally.
5. The certificate is forwarded to `ChainDB.addPerasCertAsync`.
6. `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block.
7. Observe via the node's chain-selection trace that it now considers the minority fork's block to have weight boosted by 15, potentially switching to the adversarial chain. [8](#0-7) [9](#0-8)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
