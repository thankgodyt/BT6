Audit Report

## Title
`init_transfer` Accepts Transfers That `sign_transfer` Permanently Rejects Due to Missing Decimal-Normalization Guard — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` validates only that `fee < amount`, burns/locks the user's tokens, and stores the transfer in `pending_transfers`. `sign_transfer` later applies `normalize_amount(amount - fee, decimals)` and requires the result to be `> 0`. When `amount - fee` is smaller than the decimal-normalization divisor (`10^(origin_decimals - decimals)`), `normalize_amount` returns `0`, `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, and the transfer can never be completed. Because no cancel or admin-removal path exists for pending transfers, the user's tokens are permanently frozen.

## Finding Description

**Root cause — missing pre-flight normalization check in `init_transfer`:**

`init_transfer` stores the transfer after only one fee guard:

```rust
// near/omni-bridge/src/lib.rs:554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It then burns or locks the full `amount` and writes the record to `pending_transfers` via `init_transfer_internal`.

`sign_transfer` later applies decimal normalization before signing:

```rust
// near/omni-bridge/src/lib.rs:475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` performs integer floor-division:

```rust
// near/omni-bridge/src/lib.rs:2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token where `origin_decimals > decimals` (e.g., a NEAR-native token with 24 origin decimals bridged to a 6-decimal representation on the destination chain, giving a divisor of `10^18`), any transfer where `amount - fee < 10^(origin_decimals - decimals)` will produce `normalize_amount == 0` and cause `sign_transfer` to panic unconditionally.

**No recovery path exists.** The only ways a pending transfer is removed are:
- `sign_transfer_callback` — only reached if `sign_transfer` succeeds (impossible here).
- `claim_fee_callback` — requires a proof of a completed destination-chain finalization (impossible since signing never happens).
- `remove_transfer_message_without_refund` — internal, only called on storage-check failure inside `init_transfer_internal`.

There is no `cancel_transfer`, no admin removal function, and `update_transfer_fee` can only *increase* the fee, making `amount - fee` smaller and the situation worse.

**Exploit flow:**

1. Token `T` is registered with `origin_decimals = 24`, `decimals = 6` (divisor = `10^18`).
2. User calls `ft_transfer_call` on token `T` with `amount = 500_000_000_000_000_000` (< `10^18`) and `fee = 0`.
3. `init_transfer` check: `0 < 500_000_000_000_000_000` — passes.
4. Tokens are burned/locked; transfer stored in `pending_transfers`.
5. Any relayer calls `sign_transfer` for this transfer ID.
6. `normalize_amount(500_000_000_000_000_000, {origin:24, decimals:6}) = 0`.
7. `require!(0 > 0)` — panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
8. Transfer is permanently stuck; tokens are permanently lost.

## Impact Explanation

Permanent freezing of bridged funds. The user's tokens are burned or locked by the bridge contract and can never be recovered because the only signing path is permanently blocked. This matches the Critical impact class: *permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows.*

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a sub-threshold amount on any token whose `origin_decimals > decimals`. The condition is reachable accidentally (user sends dust) or deliberately (attacker griefs themselves or tests the bridge). No special role, key, or external condition is required beyond a registered token with a decimal gap. The likelihood scales with the number of high-decimal tokens registered on the bridge.

## Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before burning/locking tokens and storing the transfer:

```rust
// After computing transfer_message, before init_transfer_internal:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().unwrap_or(0),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

Alternatively, add a general-purpose admin function to remove stuck pending transfers and refund the storage owner, as a defense-in-depth measure.

## Proof of Concept

**Minimal local unit/integration test plan:**

1. Deploy the bridge with a mock NEP-141 token registered with `origin_decimals = 24`, `decimals = 6`.
2. Call `ft_transfer_call` with `amount = 1` (1 yoctoNEAR-equivalent), `fee = 0`, valid EVM recipient.
3. Assert `init_transfer` succeeds and `get_transfer_message` returns the stored transfer.
4. Assert the token balance of the bridge increased by `amount` (tokens locked).
5. Call `sign_transfer` for the resulting `transfer_id`.
6. Assert the call panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Assert `get_transfer_message` still returns the transfer (not removed — permanently stuck).
8. Assert no recovery path exists (no cancel, fee update cannot help, claim_fee requires proof of completed finalization).
