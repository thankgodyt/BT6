### Title
Wrong Taylor Series Error Bound (`boundX = 3`) in `localSortitionNumSeats` Causes Incorrect Peras Non-Persistent Seat Counts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

### Summary

`localSortitionNumSeats` calls `taylorExpCmpFirstNonLower 3 orders (-lambda)` to determine how many Peras voting seats a non-persistent committee member is entitled to. The function's own contract requires `boundX = e^{|x|}` for correct error bounds, but `3` is hardcoded. In the leader-check context from which this constant was copied, `|x| ≤ 0.05` so `e^{0.05} ≈ 1.05 < 3` is safe. In the local-sortition context `|x| = lambda = numNonPersistentVoters × voterStake / totalNonPersistentStake`, which can be arbitrarily large, making `3` a severely wrong scale. The code itself flags this with an open TODO.

### Finding Description

In `localSortitionNumSeats` (lines 93–99):

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; should be e^lambda
      orders
      (-lambda)
```

The function contract at line 121 states:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
```

`x = -lambda`, so `boundX` must be `e^lambda`. The error term inside `decideOne` is:

```haskell
errorTerm = abs (err' * boundX)   -- line 175
```

When `boundX < e^lambda`, `errorTerm` underestimates the true Taylor-series remainder. The two decision branches then fire prematurely:

- `cmp >= acc' + errorTerm` → declares "ABOVE" (Stop) too early → returns a lower index than correct → voter gets fewer seats than entitled.
- `cmp < acc' - errorTerm` → declares "BELOW" too early → skips to the next threshold → voter may get more seats than entitled.

The direction of the error is VRF-output-dependent and unpredictable.

`lambda` is computed at lines 66–70:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
```

For a 100-voter non-persistent committee and a voter holding 10 % of non-persistent stake, `lambda = 10` and `e^10 ≈ 22 026 ≫ 3`. The error bound is off by a factor of ~7 342.

The constant `3` was copied from `checkLeaderNatValue` (cardano-ledger), where `|x| = σ · |ln(1−f)| ≤ 0.05` for `f = 0.05`, making `3` a safe over-estimate. In the local-sortition context the domain is completely different, and the code acknowledges this at lines 86–92:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
```

The same incorrect call appears in both the self-check path (`implCheckShouldVote`, line 286) and the verification path (`implVerifyVote`, line 376; `implVerifyCert`, line 529). Because both paths call the same function with the same wrong constant, voter and verifier agree on the (incorrect) seat count, so the incorrect value is accepted as valid.

### Impact Explanation

The seat count returned by `localSortitionNumSeats` directly determines a non-persistent committee member's voting weight in Peras (`implEligiblePartyVoteWeight`, lines 426–429). An incorrect seat count means the voting-power distribution across non-persistent members diverges from the wFA^LS specification. Depending on the direction of the error for a given VRF output:

- A voter whose seat count is inflated can contribute more voting weight than the protocol allows, potentially reaching the Peras quorum threshold with fewer co-voters than required, enabling unauthorized certificate acceptance.
- A voter whose seat count is deflated is systematically under-represented, weakening the honest-majority guarantee.

Both effects corrupt the Peras certificate-verification invariant, which falls under the "Peras voting or certificate checks" impact category.

**Severity: High** — the bug is in production code, is triggered for any non-persistent voter with `lambda > ln(3) ≈ 1.099`, and directly corrupts the Peras voting-power calculation used in certificate verification.

### Likelihood Explanation

The threshold `lambda > ln(3) ≈ 1.099` is crossed whenever a voter holds more than `ln(3) / numNonPersistentVoters` of the non-persistent stake. For a 10-voter non-persistent committee this is any voter with more than ~11 % of non-persistent stake — a realistic scenario in any non-uniform stake distribution. The bug fires on every vote-verification call for such voters, with no special preconditions beyond normal protocol participation.

### Recommendation

Replace the hardcoded `3` with the correct bound `e^lambda`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

Because `lambda` is already computed as a `FixedPoint`, `exp` can be approximated with the same fixed-point arithmetic used elsewhere in the module, or the bound can be computed conservatively as `exp (fromRational (toRational lambda))`.

### Proof of Concept

Consider a non-persistent committee of size 10 with a voter holding 20 % of non-persistent stake:

```
lambda = 10 × 0.20 = 2.0
e^lambda = e^2 ≈ 7.389
boundX used = 3
```

At Taylor iteration `n = 3`, `err' ≈ x^3/3! = (-2)^3/6 ≈ -1.333`. The correct error term is `|err' × e^2| ≈ 9.85`; the computed error term is `|err' × 3| ≈ 4.0`. The algorithm may declare convergence when the partial sum is still 4–10 units away from the true value of `e^{-2} ≈ 0.135`, causing it to return the wrong seat index. Both `implVerifyVote` (line 376) and `implVerifyCert` (line 529) accept the resulting incorrect `numSeats` value, permanently recording the wrong voting weight in the `EligibilityWitness`.
