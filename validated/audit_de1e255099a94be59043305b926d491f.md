### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. An unprivileged peer can therefore inject arbitrary, fabricated Peras certificates over the network miniprotocol. Each accepted certificate boosts the chain-selection weight of an attacker-chosen block, potentially causing honest nodes to prefer a non-canonical adversarial chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a Peras certificate before it is stored and used to influence chain selection. The catch-all instance — explicitly labelled a "degenerate instance for all blks to get things to compile" — implements this gate as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the **only** instance in scope for all concrete block types (the comment at line 318 confirms it is a universal catch-all): [2](#0-1) 

The production inbound-certificate pipeline calls this function directly. `processCerts` in the object-diffusion layer validates every inbound certificate batch with `validatePerasCert mkPerasParams`: [3](#0-2) 

`processCerts` itself passes the result straight through: if `validateCert` returns `Right` for every certificate in the batch, all are timestamped and forwarded to `addCert`: [4](#0-3) 

Once a certificate is stored, `addPerasCertAsync` triggers chain selection for the boosted block: [5](#0-4) 

Chain selection computes `wsvTotalWeight` as `BlockNo + wsvWeightBoost`, so a certificate that boosts a block on an adversarial fork directly increases that fork's selection weight: [6](#0-5) 

The same pattern applies to `validatePerasVote`, which skips all cryptographic checks and only looks up the voter in the stake distribution: [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block on an adversarial fork. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and used to boost that block's chain-selection weight by `perasWeight params`. If the adversarial fork is within the rollback window (`k` blocks) and the weight boost is sufficient to overcome the honest chain's block-count lead, the honest node will switch to the adversarial chain. This is a **bypass of Peras certificate validation** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical/High" impact tier: bypass of Peras certificate checks that enables unauthorized certificate acceptance and causes an honest node to prefer a non-canonical chain.

---

### Likelihood Explanation

The attack requires only a network connection to the target node. No keys, stake, or operator access are needed. The Peras certificate miniprotocol is an externally reachable entry point. The stub is the universal instance for all block types, so there is no code path that performs real validation. Likelihood is **High** for any deployment where the Peras certificate diffusion miniprotocol is active.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic and semantic validation before the Peras certificate diffusion miniprotocol is enabled in any production or testnet deployment. At minimum, the implementation must:

1. Verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. Verify each voter's eligibility proof (VRF for non-persistent, seat index for persistent members).
3. Verify that the aggregate stake of the signers exceeds the quorum threshold.
4. Reject certificates whose `pcCertRound` is outside the valid window relative to the current chain tip.

The concrete V1 certificate type (`Ouroboros.Consensus.Peras.Cert.V1`) already carries the necessary fields (`pcSignature`, `pcVoters`) for these checks: [8](#0-7) 

Until real validation is wired in, the miniprotocol should be disabled or gated behind a feature flag.

---

### Proof of Concept

**Analog mapping to the external report:**

| Teller Finance | Ouroboros Consensus |
|---|---|
| `calculateNextDueDate` caps at `endOfLoan`, never updating after repayment | `validatePerasCert` always returns `Right`, never checking anything |
| Attacker repays loan (sets `amountOwed = 0`), then calls liquidation at 1× instead of 8× | Attacker sends crafted certificate, bypasses all checks, certificate is stored and boosts adversarial block |
| Auction/pricing mechanism bypassed | Certificate validation mechanism bypassed |
| Attacker gains collateral at below-market cost | Attacker causes honest node to prefer adversarial chain |

**Attack sequence:**

1. Attacker connects to an honest node via the Peras certificate miniprotocol.
2. Attacker constructs `PerasCert { pcCertRound = r, pcCertBoostedBlock = adversarialBlockPoint }` for a block on a fork within `k` blocks of the honest tip.
3. Attacker sends the certificate batch to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
5. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` triggers `chainSelectionForBlock` for `adversarialBlockPoint`.
6. `weightedSelectView` computes the adversarial fork's weight as `BlockNo(adversarialTip) + perasWeight params`.
7. If this exceeds the honest chain's weight, `preferCandidate` returns `ShouldSwitch`, and the node adopts the adversarial chain. [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
