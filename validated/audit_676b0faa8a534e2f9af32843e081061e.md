### Title
`finalize_refund_with_psbt` Permanently Blocks Intended Refund Re-execution via `btc_pending_id` Collision — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

`finalize_refund_with_psbt` inserts a `BTCPendingInfo` record keyed by `btc_pending_id` during the first call to `execute_refund`. The code comment explicitly states that `execute_refund` can be called again to re-create the refund transaction (e.g., after a consensus branch change or fee-stuck scenario). However, the hard `require!` guard on `btc_pending_infos.insert` permanently prevents any subsequent call from succeeding, because the same deterministic `btc_pending_id` is re-derived from the same PSBT inputs. The re-execution path that `load_refund_request_for_execute` deliberately unlocks via the `executed == true` bypass is therefore unreachable, leaving the user's deposit UTXO in a permanently stuck state.

### Finding Description

`execute_refund` calls `finalize_refund_with_psbt`, which performs three irreversible state mutations in sequence:

1. Inserts a new `BTCPendingInfo` into `btc_pending_infos` under `btc_pending_id` with a hard `require!` that panics if the key already exists.
2. Inserts `utxo_storage_key` into `verified_deposit_utxo`, blocking any future `verify_deposit` or `request_refund` for the same UTXO.
3. Sets `refund_request.executed = true` and re-saves the request. [1](#0-0) 

The comment immediately before step 3 reads:

> "Keep the request (so `execute_refund` can be called again to re-create the transaction) but mark it executed" [2](#0-1) 

`load_refund_request_for_execute` was specifically written to honour this intent: it allows re-entry when `refund_request.executed == true`, bypassing the `verified_deposit_utxo` guard. [3](#0-2) 

However, on any subsequent call to `execute_refund`, the PSBT is rebuilt from the same fixed inputs (same deposit UTXO outpoint, same refund address, same gas fee stored in `RefundRequest`), producing the identical `btc_pending_id`. The `require!` at line 366 then panics with `"pending info already exist"`, making re-execution permanently impossible. [1](#0-0) 

The `btc_pending_id` is derived deterministically from the PSBT content via `psbt.get_pending_id()`. [4](#0-3) 

Because `RefundRequest` stores a fixed `gas_fee` and `refund_address`, the PSBT — and therefore `btc_pending_id` — is identical across all re-execution attempts. [5](#0-4) 

### Impact Explanation

Once `execute_refund` has been called once:

- The deposit UTXO is permanently marked in `verified_deposit_utxo` — it can never be deposited or have a new refund request accepted.
- The `BTCPendingInfo` is locked in `PendingSign` or `PendingVerify` stage with no rollback path.
- `execute_refund` can never be called again (panics on `btc_pending_id` collision).
- `internal_remove_refund_pending_tx_id` cannot clean up the orphaned `BTCPendingInfo` because it requires the refund request to be absent, but the request is still present with `executed = true`. [6](#0-5) 

The only operator escape hatch is `reject_refund`, which removes the refund request, after which `internal_remove_refund_pending_tx_id` can remove the `BTCPendingInfo`. But `verified_deposit_utxo` is never cleared, so the deposit UTXO remains permanently blocked — the user's BTC is irrecoverable through any on-chain mechanism. [7](#0-6) 

**Impact:** Medium — stuck bridge state requiring operator intervention; user's deposited BTC is permanently inaccessible on-chain if the first refund transaction fails to confirm and the operator cleans up.

### Likelihood Explanation

The stuck state is triggered whenever the first refund transaction becomes invalid after `execute_refund` succeeds:

- A Bitcoin/Zcash chain reorganization removes the block containing the broadcast refund transaction.
- The refund transaction is evicted from the mempool due to low fees or mempool congestion.
- The MPC signing produces a valid signature but the broadcast transaction is never confirmed.

Chain reorganizations and fee-stuck transactions are routine operational events on both Bitcoin and Zcash. The refund flow has no RBF mechanism (unlike withdrawals, which have `WithdrawUserRbf` and `WithdrawCancelRbf` states), so there is no alternative recovery path. [8](#0-7) 

**Likelihood:** Low-Medium — requires an external chain event, but such events are not rare on live networks.

### Recommendation

Remove the `require!(...is_none(), "pending info already exist")` guard in `finalize_refund_with_psbt` when `refund_request.executed == true`, and instead remove the stale `BTCPendingInfo` (and its account reference) before inserting the new one. Alternatively, add a dedicated `retry_execute_refund` entry point that explicitly cleans up the prior `BTCPendingInfo` before re-running `finalize_refund_with_psbt`. Also add a `clear_verified_deposit_utxo` operator function to allow recovery when a refund is rejected after execution.

### Proof of Concept

1. User deposits BTC to a bridge deposit address derived from a `DepositMsg`.
2. User calls `request_refund` with a valid inclusion proof → `RefundRequest` stored with `executed = false`.
3. After the timelock, user calls `execute_refund` → `finalize_refund_with_psbt` runs:
   - `btc_pending_infos.insert(btc_pending_id, ...)` succeeds (first call).
   - `verified_deposit_utxo.insert(utxo_storage_key)` marks the UTXO.
   - `refund_request.executed = true` is saved.
4. MPC signs the refund transaction; it is broadcast to the Bitcoin network.
5. A chain reorganization occurs; the block containing the refund transaction is orphaned.
6. User calls `execute_refund` again to re-create the transaction:
   - `load_refund_request_for_execute` passes (because `executed == true` bypasses the `verified_deposit_utxo` check).
   - `finalize_refund_with_psbt` is called again with the same inputs.
   - `btc_pending_infos.insert(btc_pending_id, ...)` finds the key already present → `require!` panics: `"pending info already exist"`.
7. Re-execution is permanently blocked. The user's BTC is stuck in the deposit address with no on-chain recovery path. [9](#0-8)

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
    }
