### Title
`safe_mint` mints tokens to bridge balance before checking recipient registration, permanently inflating nBTC supply and stranding user deposit funds when recipient account is unregistered — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the nBTC token contract performs `internal_deposit` to the bridge's own balance *before* checking whether the intended recipient account is registered. When the recipient is unregistered, the function returns `U128(0)` without burning the already-minted tokens. This silently inflates the nBTC total supply and leaves the minted tokens permanently stranded in the bridge's nBTC balance, with no recovery path for the depositing user.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124) follows a mint-before-check pattern:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    // ...
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← returns 0, tokens NOT burned
    }
    // transfer to account_id only if registered
}
``` [1](#0-0) 

`internal_deposit` increases the bridge's nBTC balance and the global total supply atomically. When the recipient is unregistered, the early return at line 115 exits without any compensating `internal_withdraw` or burn. The minted tokens remain in the bridge's nBTC balance indefinitely.

Contrast this with `mint_inner`, which correctly registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id); // ← registers first
    }
    self.token.internal_deposit(account_id, amount.into());
``` [2](#0-1) 

`safe_mint` does neither: it does not register the account nor does it burn the tokens on the failure path.

The `burn` function withdraws exclusively from `self.bridge_id`:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
``` [3](#0-2) 

This means the stranded tokens in the bridge's balance are indistinguishable from legitimately held bridge tokens and can be consumed by any subsequent `burn` call, allowing BTC to be released against nBTC that was never properly credited to a user.

---

### Impact Explanation

**Supply/accounting failure — Medium severity.**

- The nBTC total supply increases by `amount` with no corresponding user credit. The bridge's nBTC balance is silently inflated.
- The depositing user's BTC is locked in the bridge but they receive 0 nBTC — a stuck state requiring operator intervention to diagnose and remediate.
- The orphaned tokens in the bridge's balance are eligible to be burned by any future `burn` call (which withdraws from `bridge_id`), meaning a subsequent withdrawal could consume them to release BTC that was never legitimately backed — a supply-below-backed-BTC condition.

This matches the allowed impact: *"Medium. Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

---

### Likelihood Explanation

The NEP-141 storage-registration requirement is a NEAR-specific prerequisite that is not enforced at the Bitcoin deposit layer. Any user who sends BTC to a bridge deposit address without having previously called `storage_deposit` on the nBTC contract will trigger this path. First-time bridge users and users interacting via third-party tooling that omits the registration step are realistic victims. The bridge calls `safe_mint` (not `mint`) for this flow, so the bug is on the active code path.

---

### Recommendation

Move the registration check *before* `internal_deposit`, mirroring `mint_inner`:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // fail before any mint
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, auto-register the account (as `mint_inner` does) so the transfer always succeeds. If the early-return semantic is intentional, add a compensating `internal_withdraw` on the failure branch to keep total supply consistent.

---

### Proof of Concept

1. User Alice sends BTC to her bridge deposit address without calling `storage_deposit` on the nBTC contract.
2. A relayer submits the Merkle proof; the bridge verifies it and calls `nbtc.safe_mint(alice, 100_000, None)`.
3. `internal_deposit(&bridge_id, 100_000)` executes — bridge's nBTC balance: +100 000, total supply: +100 000.
4. `accounts.get(&alice)` returns `None` → function returns `U128(0)`.
5. Alice has 0 nBTC. Her BTC is locked. The bridge holds 100 000 phantom nBTC.
6. Later, any `burn(bob, 100_000, ...)` call drains those phantom tokens from `bridge_id`, releasing 100 000 sat of BTC to Bob without Bob having deposited anything — total supply drops back to zero but the BTC backing is now short by 100 000 sat. [4](#0-3)
