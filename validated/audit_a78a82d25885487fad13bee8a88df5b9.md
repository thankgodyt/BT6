### Title
Arithmetic Underflow Panic in `check_withdraw_psbt` Reachable via Public `ft_on_transfer` Path — (`contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

An unprivileged user can trigger a u128 underflow panic in `check_withdraw_psbt` by submitting a crafted PSBT through the public `ft_on_transfer` → `Withdraw` path. The gas-fee range guard that would reject the malformed PSBT is ordered **after** the unguarded arithmetic, so the panic fires before any bounds check can reject the input. With `overflow-checks = true` confirmed in the workspace `Cargo.toml`, the subtraction panics in release mode.

---

### Finding Description

In `contracts/satoshi-bridge/src/psbt.rs`, `check_withdraw_psbt` computes two sequential u128 subtractions with no prior bounds check:

```rust
// line 238
let gas_fee = total_input_amount - total_output_amount;

// line 242 — first potential underflow
let max_received_amount = amount - withdraw_fee - gas_fee;

// line 243 — second potential underflow
let min_received_amount = max_received_amount - config.min_change_amount;
``` [1](#0-0) 

The only guard that would catch an out-of-range `gas_fee` is placed **after** both subtractions:

```rust
// line 252-258 — too late
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, ...
);
``` [2](#0-1) 

**Underflow path 1 (line 242):** The attacker submits a PSBT whose outputs sum to nearly zero (e.g., a single 1-satoshi user output, no change). Because `total_input_amount` is fixed by the bridge's UTXOs and is approximately equal to `amount`, `gas_fee ≈ amount`. Then `amount - withdraw_fee - gas_fee` wraps below zero and panics before the gas-fee range check can fire.

**Underflow path 2 (line 243):** The attacker sets `gas_fee` within the valid `[min_btc_gas_fee, max_btc_gas_fee]` range but chooses a value such that `amount - withdraw_fee - gas_fee < config.min_change_amount`. This makes `max_received_amount` a small positive number, and the subsequent subtraction of `config.min_change_amount` underflows. This window exists whenever `min_withdraw_amount < withdraw_fee + max_btc_gas_fee + min_change_amount`, which is a realistic configuration.

The entry point is fully public:

```
nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)
  → bridge.ft_on_transfer(sender, amount, msg)   [line 23, token_receiver.rs]
    → create_btc_pending_info(...)               [line 71, token_receiver.rs]
      → check_withdraw_psbt_valid(...)           [line 90, token_receiver.rs]
        → check_withdraw_psbt(...)               [line 25, psbt.rs]
          → PANIC at line 242 or 243
``` [3](#0-2) [4](#0-3) 

The `min_withdraw_amount` guard at line 31 of `token_receiver.rs` only ensures `amount >= min_withdraw_amount`; it does not ensure `amount - withdraw_fee - gas_fee >= config.min_change_amount`. [5](#0-4) 

---

### Impact Explanation

**The claimed impact of permanent nBTC loss is incorrect.** The nBTC contract delegates `ft_transfer_call` to the standard `near_contract_standards::FungibleToken` implementation, which schedules `ft_resolve_transfer` as a callback after `ft_on_transfer`. [6](#0-5) [7](#0-6) 

When `ft_on_transfer` panics, the NEP-141 `ft_resolve_transfer` callback detects the failed promise and refunds the full transferred amount to the sender. NEAR also rolls back all state mutations (including the UTXO removal performed by `generate_vutxos`) on panic. Therefore, **no nBTC is lost and no bridge state is corrupted**.

The real impact is a **publicly reachable panic-driven fault**: any user can cause their own withdrawal to abort with a runtime panic rather than a graceful `require!` rejection. This violates the invariant that PSBT validation must not panic on any combination of valid-range inputs, and it produces a worse user experience and harder-to-diagnose failure mode than a clean error message.

This maps to: **Low — Publicly reachable invariant-violation / panic-driven fault in production bridge/token paths without direct theft.**

---

### Likelihood Explanation

The attack requires only a valid nBTC balance and the ability to call `ft_transfer_call`. No privileged role, leaked key, or external dependency is needed. The PSBT output amounts are fully attacker-controlled. The vulnerable arithmetic is on the hot withdrawal path and is reachable on every withdrawal attempt. Likelihood is **High** for triggering the panic, though the financial impact is limited to a failed transaction.

---

### Recommendation

Add explicit pre-checks before the subtractions in `check_withdraw_psbt`:

```rust
// After computing gas_fee at line 238:
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].", ...)
);
require!(
    amount >= withdraw_fee + gas_fee,
    "amount does not cover withdraw_fee + gas_fee"
);
let max_received_amount = amount - withdraw_fee - gas_fee;
require!(
    max_received_amount >= config.min_change_amount,
    "max_received_amount is below min_change_amount"
);
let min_received_amount = max_received_amount - config.min_change_amount;
```

Move the gas-fee `require!` from line 252 to immediately after line 238, and add the two additional guards before lines 242–243. This converts all three potential panics into clean, user-readable rejections. [8](#0-7)

### Proof of Concept

Concrete numeric example for **underflow path 2** (gas_fee within valid range):

| Parameter | Value |
|---|---|
| `amount` | 10 000 sat |
| `withdraw_fee` | 100 sat |
| `config.min_btc_gas_fee` | 500 sat |
| `config.max_btc_gas_fee` | 9 000 sat |
| `config.min_change_amount` | 1 000 sat |
| `config.min_withdraw_amount` | 10 000 sat |

Attacker submits a PSBT where `total_output_amount = 900` sat (user output = 900 sat, no change):

```
gas_fee = total_input_amount - 900 ≈ 10 000 - 900 = 9 100
```

Wait — 9 100 > `max_btc_gas_fee` (9 000), so path 1 fires first. Adjust: attacker sets user output = 1 000 sat:

```
gas_fee = 10 000 - 1 000 = 9 000   ✓ (== max_btc_gas_fee, passes range check)
max_received_amount = 10 000 - 100 - 9 000 = 900
min_received_amount = 900 - 1 000  → UNDERFLOW PANIC  (line 243)
```

The gas-fee range check at line 252 would have passed (9 000 ≤ 9 000), but the panic at line 243 fires first. The transaction aborts; `ft_resolve_transfer` refunds the 10 000 sat nBTC to the user. [9](#0-8)
