### Title
Missing Runtime Guard Allows `post_actions` to Be Silently Dropped When `safe_deposit` Is Also Set — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

`DepositMsg` carries a code-comment invariant that `post_actions` must be `None` whenever `safe_deposit` is `Some`. This invariant is enforced in one direction (the non-safe path rejects `safe_deposit`) but **never enforced in the safe path**. A depositor can therefore construct a `DepositMsg` with both fields populated, obtain a deposit address that encodes both fields, send BTC to it, and have the relayer submit it — whereupon `post_actions` is silently discarded and only the `safe_deposit` path executes.

---

### Finding Description

**`DepositMsg` struct comment (unenforced invariant):** [6](#0-5) 

The comment says `post_actions` must be `None` when `safe_deposit` is present, but there is no `require!` enforcing this.

**`get_deposit_path` serializes the full struct:** [3](#0-2) 

Because `post_actions` uses `#[serde(skip_serializing_if = "Option::is_none")]`, a `DepositMsg` with `post_actions=Some([...])` serializes to a different JSON string than one with `post_actions=None`, producing a **different SHA-256 path** and therefore a **different deposit address**.

**`verify_deposit_v2` routing — safe path taken when `safe_deposit.is_some()`:** [5](#0-4) 

**`internal_safe_verify_deposit_entry` — path computed from full `deposit_msg`, then `post_actions` discarded:** [4](#0-3) 

The path is computed from the full `deposit_msg` (including `post_actions`), so the BTC address check passes. But then only `safe_deposit_msg` is extracted and forwarded; `post_actions` is never read again.

**Contrast: the non-safe path has the symmetric guard, the safe path does not:** [2](#0-1) 

`internal_verify_deposit_entry` explicitly `require!`s `safe_deposit.is_none()`. No equivalent `require!(deposit_msg.post_actions.is_none(), ...)` exists in `internal_safe_verify_deposit_entry`.

---

### Impact Explanation

A user who:
1. Calls `get_user_deposit_address` with `{safe_deposit=Some(...), post_actions=Some([...])}`,
2. Sends BTC to the resulting address, and
3. Has the relayer submit `verify_deposit_v2` with the same `deposit_msg`

will receive nBTC minted via the safe path, but their `post_actions` (e.g., an `ft_transfer_call` into a DeFi protocol) will never execute. The deposit address uniquely encodes both fields, but execution only honours one — violating the invariant that the address fully encodes the intended execution path.

The user still holds their nBTC and can manually execute the cross-contract calls, so there is no permanent fund loss. The impact is a broken, unexpected execution path: the user's atomic deposit-and-stake (or similar) flow silently degrades to a plain mint.

---

### Likelihood Explanation

The `verify_deposit_v2` entrypoint is gated by `#[trusted_relayer]`, but the depositor fully controls the `deposit_msg` content (via `get_user_deposit_address`). The relayer submits whatever `deposit_msg` the user provided. No off-chain or on-chain validation currently rejects a dual-field `DepositMsg` before submission. Any user who mistakenly (or deliberately) sets both fields triggers the silent discard.

---

### Recommendation

Add a runtime guard at the top of `internal_safe_verify_deposit_entry` (mirroring the existing guard in `internal_verify_deposit_entry`):

```rust
require!(
    deposit_msg.post_actions.is_none(),
    "post_actions must be None when safe_deposit is set"
);
```

This makes the documented invariant enforceable on-chain and prevents the address-encoding/execution mismatch.

---

### Proof of Concept

```rust
// Path for {safe_deposit=Some, post_actions=None}
let msg_a = DepositMsg {
    recipient_id: "alice.near".parse().unwrap(),
    post_actions: None,
    extra_msg: None,
    safe_deposit: Some(SafeDepositMsg { msg: "{}".to_string() }),
    refund_address: None,
};

// Path for {safe_deposit=Some, post_actions=Some([...])}
let msg_b = DepositMsg {
    post_actions: Some(vec![PostAction { receiver_id: "defi.near".parse().unwrap(), amount: U128(1000), memo: None, msg: "stake".to_string(), gas: None }]),
    ..msg_a.clone()
};

assert_ne!(get_deposit_path(&msg_a), get_deposit_path(&msg_b)); // different addresses
// verify_deposit_v2(msg_b, ...) routes to internal_safe_verify_deposit_entry
// → post_actions silently dropped, only safe_deposit executes
```
