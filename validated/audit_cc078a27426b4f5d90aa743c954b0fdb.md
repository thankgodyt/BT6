Audit Report

## Title
Fee-on-Transfer Token Causes `locked_tokens` Mis-Accounting and Bridge Insolvency - (File: near/omni-bridge/src/lib.rs)

## Summary
The NEAR bridge's `ft_on_transfer` → `init_transfer` → `init_transfer_internal` flow records the NEP-141 nominal `amount` directly into `locked_tokens` and the `TransferMessage` without verifying the actual balance received. For fee-on-transfer NEAR-origin tokens, the bridge receives `amount - fee` but commits to releasing `amount` on the destination chain. When the user bridges back, `ft_transfer(recipient, amount)` panics because the bridge only holds `amount - fee`, the unlock is not reverted, the transfer is finalized, and the tokens are permanently stranded.

## Finding Description
**Root cause:** `ft_on_transfer` passes the nominal `amount` parameter directly to `init_transfer`, which stores it verbatim in `TransferMessage` at L540–543. `init_transfer_internal` then calls `lock_tokens_if_needed(destination_chain, token_id, amount.0)` at L1853–1857. For a NEAR-origin token sent to EVM, `get_token_origin_chain(token_id)` returns `ChainKind::Near` while `chain_kind` is EVM — they differ, so `lock_tokens` executes and increments the counter by the nominal `amount`, not the actual received `amount - fee`.

**Return path failure:** In `process_fin_transfer_to_near`, `unlock_tokens_if_needed` is called synchronously at L1881–1885, decrementing `locked_tokens` by `amount` before `send_tokens` is dispatched. `send_tokens` then calls `ft_transfer(recipient, amount_without_fee())` at L1957–1966. Because the bridge only holds `amount - fee` tokens, `ft_transfer` panics.

**No revert on failure:** `fin_transfer_send_tokens_callback` calls `is_refund_required`. When `is_ft_transfer_call = false` (plain `ft_transfer`), `is_refund_required` unconditionally returns `false` at L1800–1803, so `revert_lock_actions` is never called. The unlock stands, the transfer is marked finalized, and `amount - fee` tokens are permanently stranded in the bridge with no recipient.

**Asymmetric documentation:** `evm/SECURITY.md` explicitly acknowledges fee-on-transfer tokens are unsupported on the EVM side. `near/CLAUDE.md` contains no equivalent acknowledgment or guard for NEAR-origin tokens, and no on-chain enforcement exists.

## Impact Explanation
This is a concrete instance of **escrow mis-accounting causing permanent freezing of bridged funds**. Each deposit of a fee-on-transfer NEAR-origin token inflates `locked_tokens` relative to actual holdings. On return withdrawal, `ft_transfer` panics, the transfer is finalized with no delivery, and the shortfall accumulates. Across multiple users, the bridge's collateral pool for that token drains entirely; later legitimate withdrawals fail permanently. This matches the critical impact class: "Balance manipulation, escrow mis-accounting… that changes user or protocol balances" resulting in permanent, irreversible loss of bridged funds.

## Likelihood Explanation
An unprivileged external actor can trigger this by: (1) deploying a fee-on-transfer NEP-141 token on NEAR, (2) deploying a corresponding token on a supported foreign chain, and (3) submitting a valid cross-chain proof to `bind_token` (which is not admin-gated per the claim). A more passive path exists if any legitimately registered token later upgrades to add fee-on-transfer behavior — no further attacker action is required and all existing users of that token are affected. The exploit is repeatable and requires no privileged access, no MPC compromise, and no validator collusion.

## Recommendation
After `ft_on_transfer` is invoked, determine the actual balance delta rather than trusting the `amount` parameter. Concretely: record `ft_balance_of(env::current_account_id())` before the transfer (via a pre-transfer snapshot or a cross-contract query in the callback) and use the delta as the canonical locked amount in `TransferMessage` and `locked_tokens`. Alternatively, enforce at the protocol level that fee-on-transfer tokens are unsupported for NEAR-origin paths — mirror the EVM-side acknowledgment in `evm/SECURITY.md` with an on-chain allowlist or explicit guard in `init_transfer_internal` — and document this restriction clearly in `near/CLAUDE.md`.

## Proof of Concept
1. Deploy NEP-141 token `FeeToken` on NEAR that burns 1% on every `ft_transfer`.
2. Register `FeeToken` with the bridge via `bind_token` using a valid EVM-side proof; this initializes `locked_tokens[(Eth, FeeToken)] = 0`.
3. Alice calls `ft_transfer_call(bridge, 1000, init_transfer_msg)`.
   - `FeeToken` burns 10; bridge receives 990.
   - `ft_on_transfer` is called with `amount = 1000`.
   - `init_transfer_internal` stores `amount = 1000` in `TransferMessage`; `lock_tokens_if_needed` sets `locked_tokens[(Eth, FeeToken)] = 1000`.
   - MPC signs for 1000 on EVM; EVM mints 1000 to Alice.
4. Alice bridges 1000 back from EVM to NEAR.
   - EVM burns 1000; NEAR `fin_transfer` is called with `amount = 1000`.
   - `unlock_tokens_if_needed` decrements `locked_tokens[(Eth, FeeToken)]` to 0 (passes, counter was 1000).
   - `ft_transfer(Alice, 1000)` panics — bridge only holds 990.
   - `fin_transfer_send_tokens_callback` runs; `is_refund_required(false)` returns `false`; lock actions not reverted.
   - Transfer finalized; Alice receives 0 tokens; 990 tokens permanently stranded.
5. Repeat with additional users to drain the pool entirely.
