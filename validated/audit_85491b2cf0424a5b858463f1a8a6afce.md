### Title
Peras Quorum Bypass via Absolute/Relative Stake Unit Mismatch in `stakeAboveThreshold` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (sourced from the ledger's absolute stake distribution) directly against `perasQuorumStakeThreshold` (a relative/normalized `Rational` fraction of total committee stake), without any normalization step. This unit mismatch means any single committee member whose absolute ledger stake exceeds the relative threshold value (e.g., any voter with > 0.75 lovelace when the threshold is `0.75`) can unilaterally forge a Peras certificate, bypassing the quorum requirement entirely.

### Finding Description

`stakeAboveThreshold` is the sole gate for quorum decisions in the Peras voting pipeline:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The `PerasVoteStake` assigned to a vote comes from `lookupPerasVoteStake`, which performs a raw `Map.lookup` on `PerasVoteStakeDistr` — no normalization is applied:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [2](#0-1) 

The `PerasVoteStakeDistr` is sourced directly from the ledger stake distribution (absolute lovelace values) and passed into the vote pool writer without normalization:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

The code's own comment acknowledges the ambiguity: *"there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)."* [4](#0-3) 

The quorum threshold in `PerasParams` is a `Rational` fraction (e.g., `0.75` meaning 75% of total committee stake): [5](#0-4) 

When absolute ledger stake (e.g., `1_000_000` lovelace) is compared against a relative threshold (e.g., `0.75`), the condition `1_000_000 >= 0.75` is trivially true. Every single vote from any committee member with non-trivial stake would immediately satisfy `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just` and `updateCandidateVoteState` to forge a certificate: [6](#0-5) 

### Impact Explanation

**High.** A single committee member can forge a Peras certificate for any block of their choosing with a single vote. This certificate is stored in `PerasVoteDB`/`ChainDB` and applied as a `PerasWeight` boost to that block during chain selection via `weightBoostOfFragment` / `totalWeightOfFragment`. Honest nodes receiving this fraudulent certificate would prefer the adversarially boosted chain over the canonical chain, constituting a chain selection bug that lets an unprivileged peer (any eligible committee member) make honest nodes prefer a non-canonical or less-secure chain beyond the intended security assumptions of Peras. [7](#0-6) [8](#0-7) 

### Likelihood Explanation

**Medium.** The entry path is the Peras vote diffusion miniprotocol, reachable by any eligible committee member (a stake pool operator). The attacker does not need leaked keys, admin access, or a stake majority — only committee membership. The bug is triggered automatically by the normal vote submission flow. The condition is always satisfied when absolute stake values are used, so no special crafting is needed beyond submitting a valid vote.

### Recommendation

Normalize `PerasVoteStake` to a relative value (dividing each voter's absolute stake by the total committee stake) before storing it in `PerasVoteStakeDistr` or before calling `stakeAboveThreshold`. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform normalization internally. The existing TODO comment in `stakeAboveThreshold` already identifies this requirement; it must be resolved before Peras is activated on any network. [9](#0-8) 

### Proof of Concept

1. A committee member with absolute ledger stake `S` (e.g., `S = 1_000_000` lovelace) submits a `PerasVote` for block `B` in round `R` via the vote diffusion miniprotocol.
2. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote`.
3. `validatePerasVote` calls `lookupPerasVoteStake vote stakeDistr`, returning `PerasVoteStake (1_000_000 % 1)`.
4. The vote is stored as `ValidatedPerasVote { vpvVoteStake = PerasVoteStake (1_000_000 % 1) }`.
5. `updateCandidateVoteState` calls `votesReachQuorum cfg [vote]`.
6. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake (1_000_000 % 1))`.
7. The check `1_000_000 >= 0.75 + 0` evaluates to `True`.
8. A `ValidatedPerasCert` is forged for block `B` in round `R` with a single vote.
9. The certificate is added to `ChainDB`, boosting block `B`'s weight by `perasWeight` in all subsequent chain selection comparisons.
10. Honest nodes receiving this certificate via the cert diffusion protocol adopt the boosted chain, diverging from the canonical chain. [10](#0-9) [11](#0-10)
