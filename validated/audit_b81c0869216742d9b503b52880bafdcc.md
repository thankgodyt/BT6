### Title
Missing Revert on Unconfigured Legacy Withdrawal Path Permanently Locks User nBTC — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `ft_transfer` override in the `nbtc` contract contains a legacy withdrawal path for Near Intents. When a user sends nBTC to the nbtc contract itself with a `"WITHDRAW_TO:..."` memo but the `withdraw_relayer` address has never been configured, the code silently falls through and executes a standard `ft_transfer` to `env::current_account_id()` — the nbtc contract itself. If the nbtc contract's own account has been registered as a token holder (which any account can trigger via the public `storage_deposit`), the tokens are transferred into the contract's own balance with no recovery path, permanently locking user funds.

---

### Finding Description

The `ft_transfer` implementation in `contracts/nbtc/src/lib.rs` intercepts transfers where `receiver_id == env::current_account_id()` and the memo starts with `"WITHDRAW_TO:"`:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);  // ← fallthrough
}
``` [1](#0-0) 

When the outer condition is satisfied but `withdraw_relayer` is `None` (not yet configured), the inner `if let Some(...)` block is skipped and execution falls through to the unconditional `self.token.ft_transfer(receiver_id, amount, memo)`. At this point `receiver_id` is still `env::current_account_id()` — the nbtc contract itself — so the tokens are transferred into the contract's own token balance.

The constructor only registers `bridge_id` as a token holder:

```rust
contract.token.internal_register_account(&contract.bridge_id);
``` [2](#0-1) 

The nbtc contract's own account ID is not registered. However, `storage_deposit` is a public function inherited from `StorageManagement` and accepts any `account_id`:

```rust
fn storage_deposit(
    &mut self,
    account_id: Option<AccountId>,
    registration_only: Option<bool>,
) -> StorageBalance {
    self.token.storage_deposit(account_id, registration_only)
}
``` [3](#0-2) 

Any external actor can call `storage_deposit(Some(nbtc_contract_id), ...)` to register the nbtc contract as a token holder, enabling the fallthrough transfer to succeed. Once tokens land in the nbtc contract's own balance, there is no `rescue`, `recover`, or administrative sweep function. The `burn` function only withdraws from `bridge_id`:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
``` [4](#0-3) 

There is no mechanism to recover tokens held by `env::current_account_id()` itself.

---

### Impact Explanation

User nBTC tokens are permanently locked inside the nbtc contract with no recovery path. This constitutes a significant, irreversible loss of user funds. The locked nBTC remains in total supply but is unspendable, breaking the 1:1 backing invariant between circulating nBTC and BTC held in the UTXO pool.

**Impact category:** Critical — Significant loss and permanent locking of user funds.

---

### Likelihood Explanation

Two preconditions must hold simultaneously:

1. `withdraw_relayer` has not been configured (e.g., the bridge is deployed without Near Intents support, or the address was never set).
2. The nbtc contract's own account has been registered as a token holder via the public `storage_deposit`.

Precondition 2 costs only a small NEAR storage deposit and can be set up by any actor at any time. Precondition 1 is a realistic deployment state — `set_withdraw_relayer_address` is not called in the constructor and there is no enforcement that it must be set before the contract is used. A user following legacy Near Intents documentation, or any user who mistakenly sends nBTC to the nbtc contract address with a `WITHDRAW_TO:` memo, triggers the loss.

**Likelihood:** Medium — requires one operator omission (no relayer configured) and one cheap permissionless setup step.

---

### Recommendation

Add an explicit revert when the legacy withdrawal condition is matched but `withdraw_relayer` is not configured, instead of silently falling through:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .expect("withdraw_relayer not configured; legacy withdrawal unavailable");
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
```

This ensures that any user attempting the legacy flow when the relayer is unconfigured receives an immediate, recoverable error rather than losing their tokens.

---

### Proof of Concept

1. The nbtc contract is deployed. `set_withdraw_relayer_address` is never called (`withdraw_relayer` = `None`).
2. Attacker calls `storage_deposit(Some(nbtc_contract_id), Some(true))` with sufficient NEAR. The nbtc contract's own account is now a registered token holder with 0 balance.
3. Alice holds 1,000,000 satoshis of nBTC and wants to withdraw to her Bitcoin address. She follows the Near Intents legacy flow and calls:
   ```
   ft_transfer(
     receiver_id = nbtc_contract_id,
     amount = 1_000_000,
     memo = Some("WITHDRAW_TO:bc1qalice...")
   )
   ```
4. Inside `ft_transfer`: `receiver_id == env::current_account_id()` ✓, memo starts with `"WITHDRAW_TO:"` ✓ → enters the legacy branch.
5. `read_withdraw_relayer_address()` returns `None` → inner block skipped.
6. Falls through to `self.token.ft_transfer(nbtc_contract_id, 1_000_000, memo)`.
7. The nbtc contract's account is registered (step 2), so the transfer succeeds. Alice's 1,000,000 nBTC are now held by the nbtc contract itself.
8. No function in the nbtc contract can move tokens out of `env::current_account_id()`'s balance. Alice's funds are permanently lost.
