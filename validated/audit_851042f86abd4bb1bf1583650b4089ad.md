### Title
Peras Quorum Certificate Bypass via Stake Unit Mismatch in `stakeAboveThreshold` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function in the Peras voting subsystem compares a `PerasVoteStake` value against the `PerasQuorumStakeThreshold` without enforcing that both values are expressed in the same unit (absolute vs. relative/normalized). The code itself documents this as an unresolved assumption. If a caller supplies an absolute ledger stake (e.g., lovelace counts) where a normalized fraction is expected, the comparison is meaningless: an absolute stake value will always exceed a threshold expressed as a small fraction (e.g., `3/4`), causing every collection of votes — including a single adversarial vote — to be treated as having reached quorum, and a Peras certificate to be forged and accepted for an invalid or adversary-chosen block.

---

The quorum check then directly compares the raw `Rational` from `PerasVoteStake` against the raw `Rational` from `PerasQuorumStakeThreshold`:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum

-- current implementation of 'PerasParams', this function only makes sense when

And `votesReachQuorum` is called by `updateCandidateVoteState` in the vote aggregation engine:

The `PerasVoteStake` assigned to a vote is taken directly from the `PerasVoteStakeDistr` lookup — a map whose values are populated externally by callers. The `validatePerasVote` implementation simply copies whatever `Rational` is stored in the distribution into the validated vote without any normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right
        ValidatedPerasVote
          { vpvVote = vote
          , vpvVoteStake = stake
          }
``` [5](#0-4) 

In the production diffusion path, the `PerasVoteStakeDistr` is currently passed as `pure (PerasVoteStakeDistr mempty)` (empty), but the comment explicitly states this is a placeholder pending real ledger plumbing:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [6](#0-5) 

When the real ledger stake distribution is wired in (as the TODO demands), if the absolute lovelace values from the ledger are placed into `PerasVoteStakeDistr` without normalization by total stake, then `stakeAboveThreshold` will compare an absolute lovelace count (e.g., `1_000_000_000_000`) against a normalized threshold (e.g., `3 % 4`). The absolute value will always be `>= threshold`, so **a single vote from any registered pool** will satisfy quorum.

---

### Impact Explanation

**High — Bypass of Peras certificate/vote quorum check that enables unauthorized certificate acceptance.**

A Peras certificate attests that a specific block has been endorsed by a quorum (≥ 3/4 of stake) of the voting committee. The certificate is used to boost a block's chain weight by `perasWeight`, causing honest nodes to prefer the boosted chain in chain selection. If the quorum check is bypassed, an adversary can forge a valid-looking certificate for any block — including a block on a minority or adversarial fork — with only a single vote. This causes honest nodes to permanently prefer the adversary's chain, constituting a chain-selection safety failure.

---

### Likelihood Explanation

**Medium.** The vulnerability is latent: the production diffusion path currently uses an empty `PerasVoteStakeDistr`, which causes all votes to be rejected (no stake found → `Left PerasValidationErr`). However, the code explicitly marks this as a temporary placeholder with a TODO to wire in real ledger stake. When that wiring is implemented — which is a required step for Peras to function — if the implementer places absolute ledger stake values (lovelace) into the distribution without normalizing by total stake, the mismatch will be silently introduced. The code comment on `PerasVoteStake` itself acknowledges the ambiguity has not been resolved. An unprivileged peer sending a single vote for any registered pool ID would trigger the bypass.

---

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes for absolute stake (e.g., `AbsoluteStake`) and normalized/relative stake (e.g., `RelativeStake` in `[0,1]`). `PerasVoteStake` should be `RelativeStake` and `PerasQuorumStakeThreshold` should also be `RelativeStake`, making a unit mismatch a compile-time error.

2. **Normalize at the validation boundary.** `validatePerasVote` (or the `PerasVoteStakeDistr` construction site) must divide each voter's absolute ledger stake by the total committee stake before storing it in `PerasVoteStakeDistr`. This normalization must happen before `stakeAboveThreshold` is ever called.

3. **Remove the TODO assumption.** Replace the comment in `stakeAboveThreshold` with an enforced invariant (e.g., a `assert (stake <= 1)` guard or a type-level proof) so that any future caller supplying out-of-range values fails loudly.

---

### Proof of Concept

**Setup:** A private testnet with Peras enabled. The ledger stake distribution is wired into `PerasVoteStakeDistr` using raw lovelace values (e.g., pool A has `1_000_000_000_000` lovelace). `PerasQuorumStakeThreshold` is set to `3 % 4` (the intended 75% of normalized stake).

**Attack sequence:**

1. Adversary controls pool A (any registered pool, even with 0.01% of total stake).
2. Adversary sends a single `PerasVote` for a block on their minority fork.
3. The receiving node calls `validatePerasVote`, which looks up pool A in `PerasVoteStakeDistr` and retrieves `PerasVoteStake (1_000_000_000_000 % 1)`.
4. `votesReachQuorum` calls `stakeAboveThreshold` with `stake = 1_000_000_000_000`, `quorumThreshold = 3 % 4`. The check `1_000_000_000_000 >= 3 % 4` is `True`.
5. `forgePerasCert` is called, producing a `ValidatedPerasCert` for the adversary's block with full `perasWeight` boost.
6. Chain selection now prefers the adversary's boosted fork over the honest chain, causing a safety failure.

The root cause — comparing values of incompatible units — is directly analogous to the reported Solidity bug where `totalPrivateSold` (1e24) was compared against `totalSupplyInValue` (1e18), causing the wrong branch to always be taken. [2](#0-1) [1](#0-0) [5](#0-4) [7](#0-6)
