### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates, Bypassing All Cryptographic and Semantic Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a deliberate stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or semantic checks. This stub is wired directly into the production inbound certificate processing path (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can send crafted `PerasCert` objects via the Peras certificate diffusion mini-protocol; every such certificate will be accepted, stored in the ChainDB, and used to apply a chain-weight boost (`PerasWeight 15`) to an attacker-chosen block, corrupting chain selection.

---

### Finding Description

**Root cause — stub validator always returns `Right`:**

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate for inbound certificates. The only deployed instance is the universal one:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance covers **all** block types (`instance StandardHash blk => BlockSupportsPeras blk`), including the production `CardanoBlock`. [2](#0-1) 

No signature is verified, no committee membership is checked, no round-number bounds are enforced, and no boosted-block existence is confirmed. The certificate's `pcCertBoostedBlock :: Point blk` field is accepted verbatim.

**Production inbound path wires the stub directly:**

`makePerasCertPoolWriterFromChainDB` — the production writer used by the Peras certificate diffusion mini-protocol — passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then calls this callback on every peer-supplied certificate not already in the DB, and on success calls `ChainDB.addPerasCertAsync`: [4](#0-3) 

**Chain selection consumes the boost:**

`PerasWeight` is used directly in chain selection weight. `mkPerasParams` sets `perasWeight = PerasWeight 15`, meaning each accepted certificate boosts its target block by 15 units of chain weight. The `SecurityParam` documentation confirms this weight is what governs rollback limits in Peras: [5](#0-4)

### Impact Explanation

**Impact: Critical** — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.

An unprivileged peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` (any block point on any fork) and any `pcCertRound`.
2. Send it via the Peras certificate diffusion mini-protocol.
3. The node accepts it unconditionally, stores it in the `PerasCertDB` / `ChainDB`, and applies a `PerasWeight 15` boost to the attacker-chosen block.
4. Chain selection now treats the attacker's preferred fork as heavier, potentially causing the honest node to switch to a non-canonical chain.

Because the boost is additive and the attacker can send certificates for multiple rounds, the cumulative weight advantage can exceed the security parameter `k`, causing the node to permanently prefer an adversarially chosen chain. This is a direct consensus safety failure: an honest node accepts an invalid ledger state derived from a chain that was never legitimately certified.

---

### Likelihood Explanation

**Likelihood: High.** The Peras certificate diffusion mini-protocol is a public, unauthenticated peer-to-peer channel. Any node that connects to the victim can send `PerasCert` messages. No stake, no keys, and no prior relationship are required. The stub is present in the current production codebase with explicit `TODO` comments acknowledging it is incomplete, confirming the attack surface is live.

---

### Recommendation

1. **Implement real cryptographic validation in `validatePerasCert`**: verify the committee membership proof, the BLS/VRF signature over the certificate content, and that `pcCertBoostedBlock` refers to a block that actually exists on a known chain within the valid round window.
2. **Block the production path until validation is complete**: replace `validatePerasCert mkPerasParams` in `makePerasCertPoolWriterFromChainDB` with a function that rejects all certificates until a real implementation is available, rather than accepting all of them.
3. **Add a round-number bounds check**: reject certificates whose `pcCertRound` is outside the current Peras window before any further processing.
4. **Enforce `pcCertBoostedBlock` existence**: verify the boosted block point is present in the local ChainDB before applying any weight boost.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer → Peras cert diffusion mini-protocol
     → ObjectDiffusion handler
     → makePerasCertPoolWriterFromChainDB.opwAddObjects

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
