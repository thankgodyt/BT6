### Title
Stub `validatePerasCert` unconditionally accepts all peer-supplied Peras certificates, enabling any unprivileged peer to inject arbitrary weight boosts into `PerasWeightSnapshot` and steer chain selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation is a placeholder that always returns `Right` for any certificate, regardless of content. Because this stub is wired into the live Peras certificate diffusion mini-protocol, any unprivileged peer can inject certificates that boost arbitrary block points into the `PerasCertDB`. The resulting `PerasWeightSnapshot` is used directly for chain selection and for computing the immutability boundary (`takeVolatileSuffix`). An attacker who sends enough crafted certificates can make a competing chain appear heavier than the honest chain, causing the node to switch to it.

---

### Finding Description

**Root cause — stub validation always succeeds**

The `BlockSupportsPeras` typeclass instance for all `blk` defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No cryptographic signature check, no committee-membership check, and no round-range check is performed. Every certificate from every peer is accepted.

**Reachable entry path — production diffusion wiring**

`makePerasCertPoolWriterFromChainDB` is the writer used by the live node-to-node Peras certificate diffusion handler. It calls `processCerts` with the stub as its validation function:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

This is wired into the live node-to-node protocol handler:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

**Snapshot construction from accepted certificates**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every certificate stored in `PerasCertDB`:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds) ]
``` [4](#0-3) 

**Snapshot used for chain selection and immutability boundary**

`getCurrentChainLike` applies `takeVolatileSuffix` with the live weight snapshot to determine which blocks are immutable:

```haskell
weights <- forgetFingerprint <$> getPerasWeightSnapshot cdb
takeVolatileSuffix weights k <$> getCurChain
``` [5](#0-4) 

`chainSelSync` reads the same snapshot and passes it to `weightedSelectView` → `preferCandidate` to decide whether to switch chains:

```haskell
<*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [6](#0-5) 

`wsvTotalWeight` is the sum of block number and weight boost; chain selection prefers the heavier chain:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [7](#0-6) 

**Deduplication only prevents duplicate round numbers, not duplicate boosted blocks**

`implAddCert` deduplicates by `PerasRoundNo` only:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
``` [8](#0-7) 

An attacker can send one certificate per distinct round number, each boosting the same target block. With `perasWeight = 15` (the default from `mkPerasParams`) and `k = 2160` on mainnet, only ⌈2160/15⌉ = 144 crafted certificates are needed to accumulate a weight boost equal to the full security parameter `k`.

---

### Impact Explanation

**High — chain selection bug.** An unprivileged peer can make an honest node prefer a non-canonical chain by injecting crafted `PerasCert` objects that boost a block on the attacker's chain. The `PerasWeightSnapshot` plays the role of the oracle snapshot in the external report: it is supposed to reflect legitimately certified boosts, but because validation is a no-op, it can be steered to reflect attacker-chosen values. Once the attacker's chain accumulates enough injected weight to exceed the honest chain's total weight, `preferCandidate` returns `ShouldSwitch` and the node adopts the attacker's chain. Additionally, injecting boosts onto the current chain's blocks shrinks the volatile suffix computed by `takeVolatileSuffix`, potentially preventing legitimate rollbacks.

---

### Likelihood Explanation

**High.** The attack path is fully reachable via the standard Peras certificate diffusion mini-protocol, which is enabled in the production node-to-node handler. No special privileges, stake, or key material are required. The attacker only needs to establish a normal peer connection and send well-formed (but cryptographically unsigned) `PerasCert` messages. The stub is not gated behind a feature flag.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's cryptographic signature, confirms the signer is a legitimate committee member for the claimed round, and checks that the boosted block is within the valid age window.
2. Until real validation is in place, gate the Peras certificate diffusion mini-protocol behind a feature flag that is disabled by default in production builds.
3. Add a check in `processCerts` / `implAddCert` that the boosted block point actually exists in the local VolatileDB or ImmutableDB before accepting the certificate, as a defence-in-depth measure against phantom-block boosting.

---

### Proof of Concept

1. Establish a peer connection to the target node using the Peras certificate diffusion mini-protocol (`hPerasCertDiffusionClient`).
2. Send a batch of `PerasCert` values, each with a distinct `pcCertRound` (to bypass the round-number deduplication in `implAddCert`) and `pcCertBoostedBlock` set to a block point on an attacker-controlled fork.
3. Each certificate passes `validatePerasCert` (which unconditionally returns `Right`) and is stored in `PerasCertDB` via `addPerasCertAsync`.
4. After 144 such certificates (144 × 15 = 2160 = k on mainnet), `implGetWeightSnapshot` returns a `PerasWeightSnapshot` that assigns weight 2160 to the attacker's target block.
5. When `chainSelSync` next runs for a block on the attacker's fork, `weightedSelectView` computes `wsvTotalWeight` for the candidate as `blockNo + 2160`, which exceeds the honest chain's total weight.
6. `preferCandidate` returns `ShouldSwitch`; the node adopts the attacker's chain.
