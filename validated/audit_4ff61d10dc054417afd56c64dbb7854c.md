### Title
`NeutralNonce` Epoch Nonce Degenerates VRF Input to Slot-Only Hash, Enabling Predictable Leader Schedule - (File: `ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos/VRF.hs`)

---

### Summary

In `mkInputVRF`, when the epoch nonce is `NeutralNonce`, the function appends `mempty` (zero bytes) instead of the 32-byte nonce hash. The VRF input degenerates to `Hash(slot_bytes)` — a value that is fully public, fully predictable, and identical for the same slot number across every epoch. This is the direct structural analog of the static AES-GCM nonce: a cryptographic parameter that is supposed to be unique and unpredictable per invocation is instead constant. An adversary who registers a stake pool (obtains a VRF key) on a network whose epoch nonce is `NeutralNonce` can precompute their VRF outputs for every slot in every future epoch, enabling long-range leader-schedule grinding attacks on chain selection.

---

### Finding Description

`mkInputVRF` constructs the VRF input by concatenating the 8-byte slot number with the 32-byte epoch nonce hash:

```haskell
mkInputVRF (SlotNo slot) eNonce =
  InputVRF
    . Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 32)
    $ BS.word64BE slot
      <> ( case eNonce of
             NeutralNonce -> mempty          -- ← zero bytes appended
             Nonce h -> BS.byteStringCopy (Hash.hashToBytes h)
         )
```

When `eNonce = NeutralNonce`, the builder emits only 8 bytes (the slot), so the hash is computed over `slot_bytes` alone. The resulting `InputVRF` is `Hash(slot_bytes)` — a value that:

1. Is fully determined by the public slot number.
2. Is identical for slot `N` in every epoch (since the nonce contributes nothing).
3. Can be computed by any observer without any secret material.

The epoch nonce reaches `NeutralNonce` in two concrete paths:

- **Byron→Shelley transition**: `translateChainDepStateByronToShelley` initialises `ticknStateEpochNonce = tpraosInitialNonce`. If `tpraosInitialNonce = SL.NeutralNonce` (the value used in `mkSimpleTestProtocolInfo` and any private testnet that omits a genesis-derived nonce), the epoch nonce is `NeutralNonce` for the entire first Shelley epoch.
- **Any network configured with `NeutralNonce` as the initial nonce**: the `tpraosInitialNonce` field of `TPraosParams` is operator-supplied; a private testnet or a new Cardano-based chain starting directly in the Shelley era with `NeutralNonce` will have this condition for its first epoch.

The degenerate VRF input is then used directly in the leader-eligibility check:

```haskell
VRF.verifyCertified () vrfK (mkInputVRF slot eta0) vrfCert
  ?! VRFKeyBadProof slot eta0 vrfCert
```

Because `mkInputVRF slot NeutralNonce = mkInputVRF slot NeutralNonce` for every epoch, a pool operator can precompute `evalCertified () (mkInputVRF slotN NeutralNonce) vrfSignKey` for every future slot `slotN` without waiting for the epoch nonce to be revealed.

A secondary instance of the same pattern appears in the Peras committee tiebreaker:

```haskell
epochNonceBytes =
  case epochNonce of
    NeutralNonce -> mempty   -- ← tiebreaker reduces to Hash(poolId) only
    Nonce h -> BS.byteStringCopy (Hash.hashToBytes h)
```

The comment on `wFATiebreakerWithEpochNonce` explicitly states the epoch nonce is included "to avoid giving an adversary an edge to manipulate the tiebreaking in their favor, as they cannot predict the epoch nonce in advance." With `NeutralNonce`, this guarantee is void: the tiebreaker ordering is purely a function of public, static pool IDs, allowing an adversary to choose pool IDs that guarantee persistent committee seats.

---

### Impact Explanation

**Chain selection / leader-schedule grinding (High).**

With a predictable VRF input (`Hash(slot)`), a pool operator can precompute their VRF output for every slot in every future epoch. They can therefore:

1. Determine their complete future leader schedule offline, before the epoch nonce is published.
2. Selectively produce or withhold blocks in slots where they are leader, maximising their chain-weight advantage.
3. Execute long-range grinding attacks: by knowing which future slots they will lead, they can plan forks that accumulate more chain weight than honest nodes, causing honest nodes to prefer the adversarial chain.

This violates the core Praos security assumption that the leader schedule is unpredictable until the epoch nonce is finalised (the randomness stabilisation window). The impact is a chain selection failure that lets an adversary make honest nodes prefer a non-canonical chain beyond the intended security assumptions.

For the Peras tiebreaker, the impact is that an adversary can register pools with chosen IDs to deterministically obtain persistent committee seats, weakening the Peras voting security model.

---

### Likelihood Explanation

**Low for Cardano mainnet** (the initial nonce is derived from the Shelley genesis config hash, which is non-neutral in practice). **Moderate for private testnets and new Cardano-based chains**: `mkSimpleTestProtocolInfo` passes `SL.NeutralNonce` directly, and any operator who omits a genesis-derived nonce or explicitly sets `tpraosInitialNonce = NeutralNonce` triggers the condition. The code explicitly handles `NeutralNonce` as a valid runtime value, confirming it is a reachable state. An adversary who knows a target network uses `NeutralNonce` (e.g., by inspecting the genesis config) can exploit this without any privileged access beyond registering a stake pool.

---

### Recommendation

**Short term:** Replace `NeutralNonce -> mempty` with a fixed 32-byte domain separator (e.g., 32 zero bytes) so the VRF input is always 40 bytes regardless of the epoch nonce:

```haskell
NeutralNonce -> BS.byteStringCopy (BS.replicate 32 0)
```

This preserves the existing behaviour for `NeutralNonce` networks while ensuring the VRF input domain is always the same size and is not trivially precomputable.

**Long term:** Audit all cryptographic input-construction functions for the `NeutralNonce -> mempty` pattern (it also appears in `hashVRFInput` in `Peras/Crypto/BLS.hs` and `wFATiebreakerWithEpochNonce` in `Committee/WFA.hs`). Establish a policy that `NeutralNonce` must never silently reduce the entropy of a cryptographic input to zero; it should always contribute a fixed, non-empty domain tag.

### Proof of Concept

1. Start a private Shelley testnet with `tpraosInitialNonce = SL.NeutralNonce` (as done in `mkSimpleTestProtocolInfo`).
2. Register a stake pool and obtain its VRF signing key.
3. For any future slot `s`, compute:
   ```haskell
   let input = mkInputVRF (SlotNo s) NeutralNonce
       cert  = VRF.evalCertified () input vrfSignKey
   ```
   This is identical to the value the node will compute when it reaches slot `s` in any epoch, because `mkInputVRF s NeutralNonce = Hash(word64BE s)` — a constant per slot, independent of epoch.
4. Observe that `vrfLeaderValue (Proxy @StandardCrypto) cert` is the same for slot `s` in every epoch. The pool's leader eligibility for slot `s` is therefore fully determined before the epoch begins, enabling the grinding attack described above.
