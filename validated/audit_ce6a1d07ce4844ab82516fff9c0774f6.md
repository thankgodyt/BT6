Audit Report

## Title
Unchecked `safeTransferFrom` in `initTransfer` Allows Malicious ERC-20 to Trigger Unauthorized NEAR-Side Minting Without Depositing Collateral — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer` calls `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount)` for non-bridge, non-custom-minter tokens without verifying that the bridge's actual balance increased. A malicious ERC-20 that returns `true` from `transferFrom` without moving tokens satisfies `SafeERC20`'s only check (no revert, boolean true), causing OmniBridge to emit a fully-formed `InitTransfer` event with zero real collateral deposited. Because `logMetadata` is permissionless, any attacker can register the malicious token on NEAR via `deploy_token`, then have a trusted relayer relay the fraudulent `InitTransfer` proof to `fin_transfer`, which mints the full claimed amount to the attacker.

## Finding Description

**Step 1 — Permissionless token registration.**
`logMetadata` (L224–232, `OmniBridge.sol`) has no access control. Any caller can pass an arbitrary `tokenAddress`; the function reads `name()`, `symbol()`, `decimals()` from it and emits `BridgeTypes.LogMetadata` from the OmniBridge contract address (the registered factory). On NEAR, `deploy_token` (L1138–1144, `lib.rs`) is also unrestricted (no `#[trusted_relayer]`); it calls `verify_proof` on the EVM receipt and then `deploy_token_callback` (L1148–1175), which checks only that the emitter matches the registered factory — a check that passes because OmniBridge itself emitted the event. The malicious token is now registered in `token_decimals`.

**Step 2 — Fake custody in `initTransfer`.**
For tokens that are neither `isBridgeToken` nor have a `customMinters` entry, `initTransfer` (L406–412, `OmniBridge.sol`) executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

`SafeERC20.safeTransferFrom` only requires the call not to revert and any returned boolean to be `true`. A malicious token satisfies both while transferring nothing. The function then unconditionally emits `BridgeTypes.InitTransfer` (L427–436) with the full `amount`, from the registered factory address.

**Step 3 — NEAR-side minting.**
`fin_transfer` on NEAR (L673–696, `lib.rs`) calls `verify_proof` on the EVM receipt (cryptographically valid — the event was genuinely emitted by OmniBridge) and then `fin_transfer_callback` (L700–746). The callback checks:
- Factory match (L708–713): passes — emitter is OmniBridge.
- Token decimals exist (L715–718): passes — token was registered in Step 1.

No check verifies that OmniBridge's actual ERC-20 balance increased. `process_fin_transfer_to_near` then mints the full `amount` to the attacker's NEAR account.

**Why existing guards fail.**
`SafeERC20` is not a balance-change guard; it is a return-value normalizer. The NEAR prover verifies the cryptographic integrity of the EVM receipt, not the economic integrity of the transfer. The `#[trusted_relayer]` gate on `fin_transfer` does not block the attack: automated relayers relay all valid events from the registered factory and have no mechanism to distinguish a malicious token from a legitimate one; relaying a valid `InitTransfer` receipt is their normal operation.

## Impact Explanation

An attacker mints an unbounded quantity of a NEAR-side bridged token without depositing any EVM-side collateral. This is unauthorized minting of bridged funds — a concrete match for the allowed critical impact "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds." The bridge's escrow accounting becomes permanently inflated relative to actual custody, and any NEAR-side value extracted (DEX sales, collateral use, peer-to-peer exchange) represents a direct loss to the protocol and its users.

## Likelihood Explanation

Both `logMetadata` and `initTransfer` are permissionless public functions callable by any EOA. `deploy_token` on NEAR is also unrestricted. The only external dependency is a trusted relayer relaying a valid `InitTransfer` receipt — which is the relayer's designed behavior and requires no attacker privilege or relayer cooperation beyond normal operation. Deploying a ~20-line malicious ERC-20 is the only prerequisite. The attack is fully self-contained and repeatable with increasing amounts.

## Recommendation

In `initTransfer`, record the bridge's balance before and assert it increased by at least `amount` after:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
require(
    IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore >= amount,
    "Transfer amount mismatch"
);
```

Additionally, consider adding a token allowlist so only pre-approved ERC-20 addresses can be passed to `initTransfer`, eliminating the malicious-token registration vector through `logMetadata` entirely.

## Proof of Concept

1. **Deploy malicious ERC-20** — `transferFrom` always returns `true` without moving tokens; `name()`, `symbol()`, `decimals()` return valid non-empty values.
2. **Register on EVM** — Call `OmniBridge.logMetadata(maliciousToken)`. `LogMetadata` is emitted from the registered factory address.
3. **Register on NEAR** — Submit the EVM receipt proof to `deploy_token` on the NEAR hub. `deploy_token_callback` verifies the emitter is the registered factory and calls `deploy_token_internal`, storing decimals in `token_decimals`.
4. **Fake deposit** — Call `OmniBridge.initTransfer(maliciousToken, 1_000_000e18, 0, 0, "near:attacker.near", "")`. `safeTransferFrom` returns `true` without transferring. `InitTransfer` is emitted with `amount = 1_000_000e18`.
5. **Claim on NEAR** — A trusted relayer submits the EVM receipt proof to `fin_transfer`. `fin_transfer_callback` passes the factory check and the decimals lookup, then mints `1_000_000e18` of the NEAR token to `attacker.near`.
6. Steps 4–5 are repeatable indefinitely with increasing amounts.
