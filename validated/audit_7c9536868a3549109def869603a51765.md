### Title
Whitelisted Post-Action Receivers Without Msg Templates Accept Arbitrary Messages, Bypassing Intended Call Restrictions — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
The `check_deposit_msg` function validates `post_action` messages against a per-receiver template list, but only when templates have been configured. When a receiver is whitelisted in `post_action_receiver_id_white_list` but has no entry in `post_action_msg_templates`, the message content check is silently skipped. Any depositor can then pass an arbitrary `msg` to that whitelisted receiver, analogous to the M-07 pattern where a whitelist is not fully scoped to its intended target.

### Finding Description

In `check_deposit_msg`, the msg-template validation is guarded by an `if let Some(...)`:

```rust
// deposit_msg.rs lines 117-144
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validate msg against templates ...
    if !is_match {
        // reject
        return None;
    }
}
// If no templates exist for this receiver_id, execution falls through
// with no msg validation at all.
``` [1](#0-0) 

The two whitelists are independent: `post_action_receiver_id_white_list` (an `IterableSet<AccountId>`) controls which receivers are allowed, while `post_action_msg_templates` (an `IterableMap<AccountId, HashSet<String>>`) optionally constrains what messages may be sent to each receiver. [2](#0-1) 

The DAO manages these two structures through separate admin calls (`extend_post_action_receiver_id_white_list` and `extend_post_action_msg_templates`), and there is no enforcement that a receiver must have templates before it can be used. [3](#0-2) [4](#0-3) 

This is the direct analog to M-07: in M-07, a function selector whitelist is not scoped to a specific revenue contract, so a selector approved for an innocent contract can be used on a malicious one. Here, a receiver-ID whitelist is not scoped to specific message content when no templates are registered, so any message can be routed to a whitelisted DeFi protocol.

### Impact Explanation

After a BTC deposit is verified, the bridge calls `ft_transfer_call` on the nBTC token contract, forwarding the attacker-controlled `msg` to the whitelisted receiver's `ft_on_transfer` handler. If the whitelisted receiver (e.g., a lending protocol or DEX) interprets the `msg` to trigger privileged or harmful actions — such as borrowing on behalf of another account, executing a swap at an unfavorable rate, or manipulating another user's position — those actions execute with the depositor's nBTC as the transferred amount. The bridge's intended policy of restricting callable behavior via templates is entirely bypassed for any receiver that has not yet had templates configured. This constitutes a bypass of bridge limits or policies, and can cause harmful smart-contract behavior in whitelisted protocols without direct theft from the bridge itself.

### Likelihood Explanation

The operational gap is realistic: the DAO whitelists a receiver to enable a new integration, but configures templates later (or not at all, believing the receiver-ID check is sufficient). Any depositor — an unprivileged NEAR account — can exploit this window by crafting a `DepositMsg` with a `post_action` targeting the template-less whitelisted receiver and an arbitrary `msg`. No special role or leaked key is required; the only prerequisite is that at least one whitelisted receiver lacks a template entry.

### Recommendation

Require that every whitelisted receiver has at least one msg template before it can be used in a `post_action`. In `check_deposit_msg`, replace the optional `if let Some(...)` guard with a mandatory check:

```rust
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .ok_or_else(|| /* emit event and return None */)?;
// then validate msg against msg_templates
```

Alternatively, enforce at the admin level that `extend_post_action_receiver_id_white_list` requires a simultaneous non-empty template set, preventing a receiver from ever being whitelisted without message constraints.

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["burrowland.near"])` — no templates are added.
2. Attacker sends BTC to a deposit address derived from a `DepositMsg` containing:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "burrowland.near",
       "amount": "1000000",
       "msg": "<arbitrary msg triggering unintended burrowland action>",
       "gas": "50000000000000"
     }]
   }
   ```
3. Relayer calls `verify_deposit_v2` with the BTC proof.
4. `check_deposit_msg` passes: `burrowland.near` is whitelisted, and because `post_action_msg_templates.get("burrowland.near")` returns `None`, the `if let Some(...)` block is skipped entirely — no msg validation occurs.
5. The bridge mints nBTC and calls `ft_transfer_call` on the nBTC contract with the attacker's arbitrary `msg`, which is forwarded to `burrowland.near`'s `ft_on_transfer`, executing the unintended action. [5](#0-4)

    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
