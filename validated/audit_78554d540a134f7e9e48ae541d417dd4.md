### Title
Integer Division Truncation in `get_protocol_and_relayer_fee` Silently Zeros Protocol Fee Share - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`BridgeFee::get_fee` correctly applies a `fee_min` floor to prevent zero-fee truncation for the total fee — mirroring the fix applied to `HackerGold.sol` in the referenced report. However, the companion function `get_protocol_and_relayer_fee` performs a second integer division with no analogous floor, silently truncating `protocol_fee` to zero whenever `fee_amount * protocol_fee_rate < MAX_RATIO (10 000)`. The relayer then receives the entire fee while the protocol receives nothing, violating the configured fee-split invariant on every affected deposit and withdrawal.

### Finding Description
`BridgeFee` in `contracts/satoshi-bridge/src/config.rs` exposes two fee helpers:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,          // ← floor prevents zero-fee truncation
    )
}

pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    // ↑ no floor — truncates to 0 when fee_amount * protocol_fee_rate < 10 000
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
``` [1](#0-0) 

`get_protocol_and_relayer_fee` is called in two production paths:

**Deposit path** — `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`:
```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
``` [2](#0-1) 

**Withdrawal path** — `contracts/satoshi-bridge/src/nbtc/burn.rs`:
```rust
let (protocol_fee, relayer_fee) = config
    .withdraw_bridge_fee
    .get_protocol_and_relayer_fee(btc_pending_info.withdraw_fee);
``` [3](#0-2) 

In both callbacks the protocol-fee counters are only updated when `protocol_fee.0 > 0`:

```rust
if protocol_fee.0 > 0 {
    self.data_mut().acc_collected_protocol_fee += protocol_fee.0;
    self.data_mut().cur_available_protocol_fee += protocol_fee.0;
}
``` [4](#0-3) [5](#0-4) 

When `protocol_fee` truncates to zero the guard is never entered, the protocol-fee ledger is not credited, and the relayer silently absorbs the entire fee.

`assert_valid` only bounds `fee_rate` and `protocol_fee_rate`; it does not enforce that `fee_min * protocol_fee_rate >= MAX_RATIO`: [6](#0-5) 

### Impact Explanation
The configured `protocol_fee_rate` share of every deposit/withdrawal fee is silently redirected to the relayer instead of the protocol treasury. `acc_collected_protocol_fee` and `cur_available_protocol_fee` are under-counted, breaking the on-chain fee-accounting invariant. No user funds are stolen, but the protocol permanently loses its entitled fee revenue on every affected operation, and the relayer is over-compensated without any on-chain signal.

### Likelihood Explanation
The condition `fee_amount * protocol_fee_rate < 10 000` is reachable whenever `fee_amount` equals `fee_min` and `fee_min` is small. Example: `fee_min = 1 000` satoshis, `protocol_fee_rate = 9` (0.09 %) → `1 000 × 9 / 10 000 = 0`. Any relayer submitting a deposit whose computed fee lands at `fee_min` triggers the truncation. Because `fee_min` is a governance-settable parameter with no lower-bound constraint relative to `MAX_RATIO / protocol_fee_rate`, this is reachable in normal operation.

### Recommendation
Add a minimum-one floor to `protocol_fee` inside `get_protocol_and_relayer_fee` when `protocol_fee_rate > 0`, mirroring the `fee_min` floor already present in `get_fee`:

```rust
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let mut protocol_fee =
        fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    if self.protocol_fee_rate > 0 && protocol_fee == 0 && fee_amount > 0 {
        protocol_fee = 1; // prevent full truncation to zero
    }
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
```

Alternatively, add a validation in `assert_valid` that `fee_min * protocol_fee_rate >= MAX_RATIO` whenever both are non-zero, so the misconfiguration is rejected at setup time.

### Proof of Concept
1. Operator calls `set_deposit_bridge_fee(fee_min=1000, fee_rate=100, protocol_fee_rate=9)`.
2. User deposits `min_deposit_amount` satoshis (just above the threshold).
3. Bridge computes `deposit_fee = get_fee(deposit_amount) = fee_min = 1 000`.
4. `get_protocol_and_relayer_fee(1 000)` → `protocol_fee = 1 000 × 9 / 10 000 = 0`, `relayer_fee = 1 000`.
5. `nbtc.mint(user, mint_amount, protocol_fee=0, relayer, relayer_fee=1000)` is called.
6. `mint_callback`: `protocol_fee.0 == 0` → `acc_collected_protocol_fee` and `cur_available_protocol_fee` are **not** incremented.
7. Relayer receives the full 1 000-satoshi fee; protocol treasury receives 0 instead of its configured 0.09 % share.
8. Repeated across many deposits, the protocol-fee ledger diverges from the true collected amount with no on-chain alert.
