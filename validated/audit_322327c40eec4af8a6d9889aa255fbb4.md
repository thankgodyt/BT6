### Title
Incorrect Taylor-Expansion Error Bound in Peras Local Sortition Seat Calculation Grants Excess Voting Seats - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` computes how many non-persistent Peras voting seats a pool is granted via local sortition. It calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`, but the function's own contract requires `boundX = e^{|x|}` for correct error bounds. When the Poisson parameter `lambda` exceeds `ln(3) ≈ 1.1`, the error bound is underestimated, causing the function to prematurely classify thresholds as "not certainly below" and grant the voter more seats than they are entitled to. This inflated seat count propagates directly into `implVerifyVote` and `implVerifyCert`, where it is used to accept votes and certificates with inflated weight.

---

### Finding Description

`localSortitionNumSeats` computes the expected number of non-persistent committee seats for a voter:

```haskell
lambda :: FixedPoint
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [1](#0-0) 

It then calls:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- <-- hardcoded, should be e^lambda
      orders
      (-lambda)
``` [2](#0-1) 

The function signature and its own inline documentation state:

```haskell
-- | boundX = e^{|x|} for correct error estimation
taylorExpCmpFirstNonLower ::
  a ->   -- boundX = e^{|x|}
``` [3](#0-2) 

Inside `decideOne`, the error term is:

```haskell
errorTerm = abs (err' * boundX)
``` [4](#0-3) 

When `boundX = 3 < e^lambda` (i.e., `lambda > ln(3) ≈ 1.1`), `errorTerm` is smaller than the true Taylor remainder. The decision rule:

```haskell
| cmp >= acc' + errorTerm = Stop   -- "not certainly below" → grants seat
| cmp < acc' - errorTerm = Below   -- "certainly below"     → denies seat
``` [5](#0-4) 

With an underestimated `errorTerm`, values of `cmp` that lie within the true uncertainty band but above the underestimated band are prematurely classified as "not certainly below" (`Stop`), returning a seat index that is too high. The code itself acknowledges this is unresolved:

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
--
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
``` [6](#0-5) 

The `3` was copied from `checkLeaderNatValue` in the Ledger, where it is safe because the Praos leader-check argument `|x| = sigma * |ln(1-f)|` is always much less than 1 for any realistic pool stake `sigma` and active-slot coefficient `f`. For local sortition, `lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake` can easily exceed 1.1 — for example, with 100 non-persistent voters and a pool holding 2% of non-persistent stake, `lambda = 2`, giving `e^lambda ≈ 7.4 >> 3`.

The inflated `expectedSeats` is then used directly in vote and certificate verification:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure $
      WFALSNonPersistentMember ...
``` [7](#0-6) 

And in vote-weight computation:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [8](#0-7)

### Impact Explanation

An attacker who is a registered pool with non-persistent committee candidacy and `lambda > ln(3)` will have their seat count overestimated by `localSortitionNumSeats`. Because `VoteWeight` is proportional to `numSeats * stake / totalNonPersistentStake`, the attacker's effective voting power is inflated beyond what their stake entitles them to. Across multiple elections in an epoch, this systematic overcount allows the attacker to:

1. **Bypass Peras vote/certificate authorization**: votes and certificates that should be rejected (because the voter's true seat count is 0 or lower) are accepted by `implVerifyVote` and `implVerifyCert`.
2. **Gain disproportionate influence over Peras certificate formation**: with inflated weight, the attacker can push a certificate for a block of their choice over the quorum threshold, or block honest certificates from forming.

This matches the allowed impact: *Bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance.*

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.1` is met whenever:

```
numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.1
```

With a target committee size of, say, 500 and a pool holding 0.3% of non-persistent stake, `lambda ≈ 1.5`. This is a realistic scenario for any moderately-sized pool on a network with a large committee. The error is systematic (not probabilistic) and reproducible for any pool whose `lambda` exceeds the threshold. No special privileges, key compromise, or social engineering are required — any registered pool that qualifies as a non-persistent committee candidate can trigger this path by simply submitting a vote.

---

### Recommendation

Replace the hardcoded `3` with the correct bound `e^lambda`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

This matches the contract stated in `taylorExpCmpFirstNonLower`'s own documentation and is consistent with how `checkLeaderNatValue` in the Ledger is used (where `3` happens to be a safe overestimate because `|x| << 1`). Alternatively, if `exp lambda` is too expensive, use a tighter analytical upper bound on `lambda` derived from the protocol parameters and cap it accordingly, with a proof that the cap is always `>= e^lambda`.

### Proof of Concept

Consider a network with:
- `numNonPersistentVoters = 100`
- A pool with `voterStake / totalNonPersistentStake = 0.03` → `lambda = 3.0`, `e^lambda ≈ 20.1`

The `orders` list for a VRF output `normalizedVRFOutput = 0.04`:
- `orders[0] = 0.04 / 3.0 ≈ 0.01333`

The true value `e^{-3} ≈ 0.04979`. Since `0.04979 > 0.01333`, the voter correctly gets at least 1 seat.

Now consider `normalizedVRFOutput = 0.001`:
- `orders[0] = 0.001 / 3.0 ≈ 0.000333`
- True comparison: `e^{-3} ≈ 0.04979 > 0.000333` → voter gets ≥1 seat (correct)

Now consider `normalizedVRFOutput = 0.06`:
- `orders[0] = 0.06 / 3.0 = 0.02`
- True comparison: `e^{-3} ≈ 0.04979 > 0.02` → voter gets ≥1 seat (correct)
- `orders[1] = 2 * 0.02 / 3.0 ≈ 0.01333`
- True comparison: `e^{-3} ≈ 0.04979 > 0.01333` → voter gets ≥2 seats (correct)

Now consider a borderline case where `e^{-lambda}` is just barely below `orders[i]`. With `boundX = 3` instead of `e^3 ≈ 20.1`, the error term `errorTerm = |err' * 3|` is ~6.7× smaller than the true error `|err' * 20.1|`. A value of `cmp` that lies within the true uncertainty band `[acc' - 20.1*|err'|, acc' + 20.1*|err'|]` but above the underestimated band `acc' + 3*|err'|` will be classified as `Stop` (grants seat) when the Taylor series has not yet converged. This is the direct analog of the EIP-4626 `previewWithdraw` rounding-down bug: a calculation that should be conservative instead favors the voter over the protocol. [9](#0-8)
