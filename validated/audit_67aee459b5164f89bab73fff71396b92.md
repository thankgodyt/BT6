### Title
Peras Quorum Check Unit Mismatch Enables Unauthorized Certificate Forging with Minimal Stake — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function, which is the sole gatekeeper deciding whether accumulated votes reach quorum and a Peras certificate should be forged, performs a direct numeric comparison between `PerasVoteStake` (accumulated vote stake, potentially in absolute lovelace units from the ledger) and `PerasQuorumStakeThreshold` (a relative fraction, e.g. `3/4`). The code itself documents this unit mismatch with an explicit TODO. Because `validatePerasVote` assigns the raw value from the `PerasVoteStakeDistr` — which is populated from the ledger's absolute stake distribution — to `vpvVoteStake` without any normalization, a single vote from any registered pool with even 1 lovelace of stake produces a `PerasVoteStake` value (e.g. `1_000_000_000_000`) that trivially satisfies `stake >= 3/4 + 2/100`, causing a certificate to be forged immediately.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.

  stake >= quorumThreshold + safetyMargin

### Impact Explanation

When the `PerasVoteStakeDistr` is populated with absolute lovelace values from the ledger (e.g. a pool with 1 ADA = `1_000_000_000_000` lovelace), the comparison inside `stakeAboveThreshold` becomes:

```
1_000_000_000_000 >= (3/4) + (2/100)   →   True
```

This means a **single vote** from any registered pool — regardless of how small its actual stake fraction is — immediately satisfies the quorum check, causing `votesReachQuorum` to return `Just` and `updateCandidateVoteState` to forge a certificate. The forged certificate is then accepted by the node (the `validatePerasCert` implementation also accepts all certificates unconditionally) and applied to chain selection, boosting the attacker's chosen block by `perasWeight = 15` chain-length units.

This constitutes a **bypass of Peras certificate/vote verification** — specifically the quorum threshold — enabling unauthorized certificate acceptance and chain-selection manipulation. [8](#0-7) 

---

### Likelihood Explanation

The attack path is reachable by any registered stake pool operator submitting a vote via the standard Peras vote mini-protocol. The `makePerasVotePoolWriterFromChainDB` function is the production entry point for inbound votes and calls `validatePerasVote mkPerasParams sd vote` where `sd` is the live ledger stake distribution. No special privileges, key compromise, or stake majority are required — any pool with even 1 lovelace of registered stake can trigger the condition. The unit mismatch is self-documented in the codebase as an unresolved design question, meaning no concrete normalization step exists anywhere in the call chain.

---

### Recommendation

1. **Enforce normalization at the boundary.** `stakeAboveThreshold` must not accept raw `PerasVoteStake` values. Either:
   - Change `stakeAboveThreshold` to accept the total committee stake and normalize internally: `stake / totalCommitteeStake >= quorumThreshold + safetyMargin`, or
   - Normalize `PerasVoteStake` to a relative fraction at the point of assignment in `validatePerasVote` before it is stored in `ValidatedPerasVote`.

2. **Introduce a newtype distinction** between absolute ledger stake (`LedgerStake`) and normalized vote weight (`RelativeVoteStake`) so the type system prevents the comparison from compiling when units differ.

3. **Resolve the open design question** documented in the `PerasVoteStake` NOTE comment before the Peras protocol is activated on any network.

---

### Proof of Concept

Given:
- `mkPerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`
- A pool `P` has 1 ADA = `1_000_000_000_000` lovelace in the ledger stake distribution
- `PerasVoteStakeDistr` is populated with this absolute value: `Map.singleton (PerasVoterId poolKeyHash) (PerasVoteStake 1_000_000_000_000)`

Attack sequence:
1. Pool `P` submits a `PerasVote` for any block `B` in round `R` via the network.
2. `processVotes` calls `validatePerasVote mkPerasParams sd vote` → returns `Right ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1_000_000_000_000 }`.
3. `updateCandidateVoteState` calls `votesReachQuorum` → `totalVoteStake = PerasVoteStake 1_000_000_000_000`.
4. `stakeAboveThreshold`: `1_000_000_000_000 >= 3/4 + 2/100` → `True`.
5. `forgePerasCert` is called → certificate for block `B` is forged with `vpcCertBoost = PerasWeight 15`.
6. The certificate is added to the ChainDB and applied to chain selection, boosting `B` by 15 chain-length units regardless of whether `B` has honest majority support. [9](#0-8) [7](#0-6)
