### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate Without Cryptographic Validation, Enabling Unprivileged Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production catch-all `BlockSupportsPeras` instance for all Cardano blocks contains a stub `validatePerasCert` that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic checks. When Peras is enabled, an unprivileged peer can inject arbitrary fake certificates via the object diffusion protocol. Each accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection for the boosted block. Because chain selection now weighs candidate fragments by Peras boost weight rather than length alone, a crafted certificate can cause an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validation always succeeds**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` lines 318–358 define the only `BlockSupportsPeras` instance in the codebase. It is a catch-all for every block type that has `StandardHash` (i.e., all Cardano blocks):

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params   -- full boost assigned unconditionally
        }
```

No signature, committee-membership, or round-number check is performed. The function always returns `Right`.

**Inbound certificate processing uses this stub**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` lines 118–133 wire the stub directly into the production object-pool writer that handles peer-supplied certificates:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)          -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB) -- ← triggers chain sel
          certs
    ...
    }
```

`processCerts` (lines 164–173) calls `validateCert` on every incoming certificate; because the stub never returns `Left`, every certificate passes and is forwarded to `addPerasCertAsync`.

**`addPerasCertAsync` triggers chain selection**

`ChainDB.API.hs` line 441–443 documents the effect:

> `addPerasCertAsync` — Asynchronously insert a certificate to the DB. If this leads to a fork to be weightier than our current selection, this will trigger a fork switch.

`ChainSel.hs` lines 483–531 implement this: after adding the certificate to `PerasCertDB`, the code calls `chainSelectionForBlock` for the boosted block, giving it the full `perasWeight` boost in the weighted chain comparison.

**Chain selection is weight-based when Peras is active**

The CHANGELOG records: *"Make the ChainDB aware of the PerasCertDB, and modify the chain selection function accordingly. In practice, it means that the candidate fragment is now selected based on its Peras weight, instead of its length."*

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block in the node's VolatileDB (e.g., a block on a minority fork). Because `validatePerasCert` always returns `Right`, the certificate is accepted and stored. `chainSelSync` then calls `chainSelectionForBlock` for the boosted block, adding `perasWeight params` to its fragment's weight. If that weight exceeds the current selection's weight, the node switches to the non-canonical fork — a chain-selection safety failure caused entirely by an unauthenticated network message.

This matches the **High** impact category: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The Peras object diffusion protocol and the `makePerasCertPoolWriterFromChainDB` code path are present in the production codebase. The CHANGELOG notes Peras is *"disabled by default"*, but the stub is the **only** `validatePerasCert` implementation for all block types; there is no per-era override. Any deployment that enables Peras (including private testnets or future mainnet activation) immediately exposes this path. The attack requires only a TCP connection to the object-diffusion port — no stake, no keys, no prior knowledge of the chain.

---

### Recommendation

1. Implement real cryptographic validation in `validatePerasCert` (BLS signature verification, committee-membership proof, round-number bounds) before enabling Peras on any network.
2. Add a compile-time or runtime guard that prevents `makePerasCertPoolWriterFromChainDB` from being instantiated with the stub implementation.
3. Track the linked issue (`cardano-peras#120`) as a **security blocker** for Peras activation, not merely a TODO.

---

### Proof of Concept

1. Connect to a Peras-enabled node via the object-diffusion mini-protocol.
2. Send a `PerasCert { pcCertRound = r, pcCertBoostedBlock = p }` where `p` is the tip of a minority fork present in the node's VolatileDB.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
4. `addPerasCertAsync chainDB cert` enqueues the certificate; `chainSelSync` processes it and calls `chainSelectionForBlock` for the boosted block.
5. The minority fork's fragment now carries `perasWeight` extra weight; if this exceeds the current selection's weight, the node switches to the non-canonical chain.
