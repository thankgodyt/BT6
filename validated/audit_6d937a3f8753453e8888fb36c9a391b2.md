### Title
Stub `validatePerasVote` Accepts Forged Votes Without BLS Signature Verification, Enabling Vote Front-Running and Suppression - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasVote` implementation in `BlockSupportsPeras` is an acknowledged stub that only checks stake-distribution membership and never verifies the BLS vote signature. Because vote deduplication in `PerasVoteDB` is keyed on `PerasVoteId = (roundNo, voterId)` — which does not include the voted-for block — an unprivileged peer can front-run any legitimate committee member's vote by submitting a structurally valid but cryptographically forged vote for a different block. The legitimate vote then arrives and is silently dropped as a duplicate, suppressing the honest voter's choice for that round.

### Finding Description

`validatePerasVote` is the sole gate between an inbound network vote and the `PerasVoteDB`. Its current body is:

```haskell

validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

It ignores `_params` entirely and never calls `verifyVoteSignature` (defined in `CryptoSupportsVoteSigning`). The BLS signing/verification machinery exists and is correct:

```haskell
signVote sk roundNo boostedBlock =
  PerasBLSCryptoVoteSignature . BLS.signWithRole @SIGN sk
    $ hashVoteSignature roundNo boostedBlock

verifyVoteSignature pk roundNo boostedBlock (PerasBLSCryptoVoteSignature sig) =
  BLS.verifyWithRole @SIGN pk (hashVoteSignature roundNo boostedBlock) sig
``` [2](#0-1) 

but it is never invoked during inbound vote processing.

The deduplication key `PerasVoteId` contains only `(pviRoundNo, pviVoterId)` — the block target is absent:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [3](#0-2) 

`implAddVote` in `PerasVoteDB.Impl` uses this key to silently discard any vote whose `(roundNo, voterId)` pair is already present:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [4](#0-3) 

`processVotes` — the inbound handler called from both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` — filters already-known IDs and then calls the stub validator:

```haskell
let votesNotAlreadyInDb =
      filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
mapM validateVote votesNotAlreadyInDb
``` [5](#0-4) 

### Impact Explanation

An unprivileged peer can:

1. Observe the public `PerasVoterId` (stake-pool key hash) of any eligible committee member V for round R — this is derivable from the public stake distribution.
2. Craft a `PerasVote` with `pvVoteVoterId = V`, `pvVoteRound = R`, `pvVoteBlock = attacker_chosen_block`, and an arbitrary garbage BLS signature.
3. Deliver this forged vote to the victim node before V's legitimate vote arrives.
4. `validatePerasVote` accepts it (stake-distribution lookup succeeds; signature is never checked).
5. The DB stores it under `PerasVoteId{pviRoundNo=R, pviVoterId=V}`.
6. V's legitimate vote arrives and is silently dropped as `PerasVoteAlreadyInDB`.

By front-running enough committee members, the attacker can:
- Prevent quorum from being reached for the honest canonical block (vote suppression), stalling Peras finality.
- Steer quorum toward an attacker-chosen block if the attacker can front-run a quorum-sized subset of the committee.

This is a **bypass of Peras vote signature verification** enabling unauthorized vote acceptance, matching the "Critical — bypass of VRF/KES/certificate/signature validation" impact class.

### Likelihood Explanation

The attack requires only a network connection to a Cardano node running Peras. Committee membership is deterministic and publicly computable from the stake distribution. No key material, admin access, or stake majority is needed. The attacker simply needs to deliver the forged vote before the legitimate one, which is straightforward given that the object-diffusion mini-protocol propagates votes peer-to-peer and an adversarial peer is directly connected.

### Recommendation

1. **Implement BLS signature verification inside `validatePerasVote`**: call `verifyVoteSignature` (from `CryptoSupportsVoteSigning`) against the voter's public key retrieved from the committee/stake-distribution context. Reject any vote whose signature does not verify.
2. **Implement BLS aggregate-signature verification inside `validatePerasCert`**: the parallel stub `validatePerasCert` also accepts every certificate unconditionally and must be fixed.
3. Track the open issue `cardano-peras#120` referenced in the TODO comments and treat it as a security-critical item, not merely a correctness improvement.

implAddVote perasCfg PerasVoteDbEnv{pvdeTracer, pvdeState} vote = do
  let voteId = getPerasVoteId vote
  addPerasVoteRes <- do
    WithFingerprint pvds fp <- readTVar pvdeState
    (res, pvds') <- addOrIgnoreVote pvds voteId
    writeTVar pvdeState (WithFingerprint pvds' (succ fp))

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
