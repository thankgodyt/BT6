Audit Report

## Title
Missing `token::authority` Constraint on `from` Account Allows Delegate to Bridge Victim's Tokens — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary
The `InitTransfer` account struct constrains `from` only by `token::mint` and `token::token_program`, with no `token::authority = user` constraint. Because SPL Token's `transfer_checked` and `burn` accept either the token account owner or an approved delegate as the signing authority, any attacker who holds a valid SPL delegation over a victim's token account can supply `from = victim_ata` and `user = attacker` (signer), causing the bridge to lock or burn the victim's tokens and emit a Wormhole message crediting an attacker-controlled NEAR account.

## Finding Description
The `from` account is declared at lines 34–39 with only mint and token-program constraints:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    // ← no token::authority = user
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

`user` is declared as a `Signer` with only a system-program owner check (line 60–64), with no constraint tying it to `from.owner`. Anchor's account-validation layer therefore never checks `from.owner == user.key()`.

In `process()`, the native-token path issues:

```rust
TransferChecked {
    from: self.from.to_account_info(),
    to: vault.to_account_info(),
    authority: self.user.to_account_info(),   // attacker signs
    mint: self.mint.to_account_info(),
}
```

and the bridged-token path issues:

```rust
Burn {
    mint: self.mint.to_account_info(),
    from: self.from.to_account_info(),
    authority: self.user.to_account_info(),   // attacker signs
}
```

SPL Token's `transfer_checked` and `burn` instructions accept **either** the token account's `owner` **or** an approved `delegate` as the authority. If the victim has ever called `spl_token::approve` granting the attacker (or a program the attacker controls) delegate authority over their ATA, both CPIs succeed with `from = victim_ata` and `authority = attacker`. After the tokens are moved, the Wormhole message is posted with:

```rust
self.common.post_message(payload.serialize_for_near((
    self.common.sequence.sequence,
    self.user.key(),   // attacker's pubkey recorded as sender
    self.mint.key(),
))?)?;
```

The attacker fully controls `payload.recipient`, so NEAR-side finalization releases the tokens to an attacker-controlled NEAR account. There is no guard anywhere in `InitTransfer::process` that checks `from.owner == user.key()`.

## Impact Explanation
This directly matches the Critical allowed impact: **Stealing or permanent loss of bridged funds**. On the native-token path, the victim's SPL tokens are irreversibly locked in the bridge vault while the attacker receives equivalent tokens on NEAR. On the bridged-token path, the victim's tokens are burned and the attacker receives equivalent tokens on NEAR. In both cases the victim suffers a permanent, unrecoverable loss of their SPL tokens with no on-chain recourse.

## Likelihood Explanation
SPL token delegations are a standard, widely-used mechanism across DEXes, lending protocols, and other DeFi applications. Any user who has ever called `spl_token::approve` granting delegate authority to a wallet or program that the attacker controls is vulnerable. The attacker requires no privileged access, no key compromise, and no admin role — only possession of a pre-existing delegation. The attack is fully on-chain, permissionless, and repeatable for every victim whose delegation remains active.

## Recommendation
Add `token::authority = user` to the `from` account constraint in `InitTransfer`:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    token::authority = user,   // enforce from.owner == user.key()
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

Anchor will enforce `from.owner == user.key()` at account-validation time, before any CPI is attempted, closing the delegation-drain path entirely.

## Proof of Concept
Using the existing Mollusk test harness in `solana/programs/bridge_token_factory/tests/mollusk/test_init_transfer.rs`:

1. Create `victim_ata` with `owner = victim`, funded with tokens.
2. Have `victim` call `spl_token::approve(victim_ata, delegate = attacker, amount = X)`.
3. Construct an `init_transfer` instruction with:
   - `from = victim_ata`
   - `user = attacker` (marked as signer)
   - `payload.recipient = "attacker.near"`
4. Submit the instruction signed by `attacker`.
5. Assert `victim_ata.amount` decreased by `X`.
6. Assert `vault.amount` increased by `X` (native path) or mint supply decreased (bridged path).
7. Assert the emitted Wormhole message encodes `sender = attacker.pubkey` and `recipient = "attacker.near"`.

The SPL Token CPI at lines 90–102 (native) and 110–120 (bridged) will succeed because `attacker` is a valid delegate of `victim_ata`. No guard in `InitTransfer::process` checks `from.owner == user.key()`.
