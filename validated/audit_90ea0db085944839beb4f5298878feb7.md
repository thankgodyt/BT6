Looking at the full execution path and the actual code in `orchard_policy.rs`, `psbt_wrapper.rs`, `contract_methods.rs`, and `psbt.rs`.

**Key facts established:**

1. `read_v5_bundle` only **parses** the bundle bytes — it does not verify the Halo2 proof. [1](#0-0) 

2. `recover_output_with_ovk` is a symmetric decryption using the OVK — it succeeds if the note ciphertext was encrypted with `BRIDGE_OVK = [0u8; 32]`, completely independent of whether the Halo2 proof is valid. [2](#0-1) 

3. `BRIDGE_OVK` is hardcoded to all-zeroes and is public. [3](#0-2) 

4. `validate_orchard_bundle` checks `value_balance` as a parsed field against the decrypted note value — no cryptographic enforcement. [4](#0-3) 

5. The nZEC is **NOT burned** at `ft_on_transfer` time. Tokens are transferred to the bridge balance and only burned after `verify_withdraw` is called with an on-chain proof. [5](#0-4) 

**The question's stated impact is factually wrong:** it claims "nZEC burned but ZEC not released." In reality, nZEC is never burned unless `verify_withdraw` succeeds. If the Zcash transaction is rejected, `verify_withdraw` is never called, and the nZEC remains stuck in the bridge's balance — not burned, but inaccessible to the user.

**The actual impact is a stuck bridge state:** nZEC locked in bridge balance, UTXOs consumed, requiring operator intervention to cancel. The cancel/RBF mechanism exists and can recover funds, but requires operator action.

**However, the core observation is correct:** `read_v5_bundle` does not verify the Halo2 proof, and an attacker who knows `BRIDGE_OVK` (it is public) can construct a bundle with a valid note ciphertext for value X, `value_balance = -X`, and a garbage Halo2 proof. This passes all bridge checks but is rejected by the Zcash network.

### Title
No-proof Orchard bundle accepted by bridge, resulting in stuck nZEC state — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary
The bridge parses Orchard bundles via `read_v5_bundle` and validates them using `recover_output_with_ovk` + a `value_balance` field check, but **never verifies the Halo2 proof**. Because `BRIDGE_OVK` is a public constant (`[0u8; 32]`), any attacker can construct a bundle with a correctly-encrypted note ciphertext and a matching `value_balance` field, but with an invalid (garbage) Halo2 proof. The bridge accepts this bundle; the resulting Zcash transaction is rejected by the Zcash network; nZEC is stuck in the bridge's balance indefinitely until an operator manually cancels.

### Finding Description
`extract_orchard_bundle` calls `read_v5_bundle` which deserializes the bundle structure including the proof bytes, but performs no proof verification. [1](#0-0) 

`recover_output_with_ovk` is a symmetric AEAD decryption keyed on `BRIDGE_OVK`. It succeeds whenever the note ciphertext was encrypted with that key, regardless of whether the Halo2 proof is valid or whether the note commitment in the action actually commits to that value. [2](#0-1) 

`validate_orchard_bundle` then checks that `value_balance == -note_value` — both values come from parsed/decrypted fields, not from a verified proof. [4](#0-3) 

`BRIDGE_OVK` is a public constant, so any caller can encrypt a note ciphertext for any value X to any recipient address using standard Orchard note encryption. [3](#0-2) 

The `check_withdraw_psbt` path calls `check_psbt_chain_specific` which calls `validate_orchard_bundle`, but no step in the chain verifies the Halo2 proof. [6](#0-5) [7](#0-6) 

### Impact Explanation
The nZEC is transferred to the bridge balance at `ft_on_transfer` time (not burned). It is only burned after `verify_withdraw` confirms on-chain inclusion. If the Zcash transaction is invalid and never confirmed, `verify_withdraw` is never called, and the nZEC is permanently stuck in the bridge's balance — inaccessible to the user and not backed by released ZEC. Recovery requires operator intervention via the cancel mechanism.

**Impact: Medium** — stuck bridge state requiring operator intervention; user nZEC is locked in bridge balance with no automatic recovery path.

### Likelihood Explanation
The attack requires only that the attacker:
1. Know `BRIDGE_OVK` (it is a public constant: `[0u8; 32]`)
2. Construct a standard Orchard note ciphertext for value X to their own address using `BRIDGE_OVK`
3. Set `value_balance = -X`
4. Provide correctly-sized but invalid proof bytes

All four steps are achievable by any unprivileged user with knowledge of the Orchard note encryption scheme (which is fully documented). The test helper `gen_ua_and_orchard_bundle_hex_with_key` in the test suite demonstrates exactly how to construct such a bundle. [8](#0-7) 

### Recommendation
The bridge must verify the Halo2 proof before accepting an Orchard bundle. Call `bundle.verify_proof(&vk)` (using the Orchard verifying key) inside `extract_orchard_bundle` after parsing, and reject the bundle if proof verification fails. This is the only way to cryptographically enforce that `value_balance` and the note commitments are consistent.

Alternatively, if proof verification is too expensive for the NEAR runtime, the bridge should document that it relies on the relayer to only broadcast valid transactions and add a monitoring/alerting path so that stuck states are detected and cancelled promptly.

### Proof of Concept
```
1. Attacker calls nbtc.ft_transfer(bridge, X, WithdrawMsg{

       }),
       input: [valid_utxo],
       output: [change_output],
   })

2. malformed_bundle is constructed as:
   - 1 action with note ciphertext encrypted with BRIDGE_OVK=[0u8;32] for value X
     to attacker's Orchard address (standard Orchard note encryption)
   - value_balance = -X (set as a raw field)
   - proof bytes = [0u8; PROOF_SIZE]  (garbage, correctly sized)

3. Bridge flow:
   ft_on_transfer → ft_on_transfer_withdraw_chain_specific
   → ft_on_transfer_callback → PsbtWrapper::new
   → extract_orchard_bundle: read_v5_bundle parses OK, recover_output_with_ovk
     decrypts note → value=X, recipient=attacker_addr  ✓
   → validate_orchard_bundle: value_balance=-X == -X  ✓, recipient matches  ✓
   → check_withdraw_psbt: amount accounting passes  ✓
   → BTCPendingInfo created, nZEC locked in bridge balance

4. Chain Signatures signs the Zcash transaction (transparent inputs + malformed Orchard bundle)
5. Relayer broadcasts transaction to Zcash network
6. Zcash network rejects: Halo2 proof is invalid
7. verify_withdraw is never called
8. nZEC remains stuck in bridge balance; user has lost X nZEC
```
