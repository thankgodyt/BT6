### Title
Unconditional `validatePerasCert` Acceptance Bypasses All Certificate Validation, Enabling Unauthorized Chain-Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right` — accepting every inbound Peras certificate without performing any cryptographic, quorum, or structural check. An unprivileged peer can send a crafted `PerasCert` pointing to any block, have it accepted as valid, and cause the receiving node to apply a chain-weight boost to that block, potentially switching to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` catch-all instance in `SupportsPeras.hs` implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the only `BlockSupportsPeras` instance in the codebase (a catch-all `instance StandardHash blk => BlockSupportsPeras blk`), so it applies to all block types including production Cardano blocks. [2](#0-1) 

The inbound certificate processing path in `processCerts` calls this function directly:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [3](#0-2) 

`processCerts` validates each certificate and, if all pass, adds them to the ChainDB. Since `validatePerasCert` always returns `Right`, every certificate from every peer passes validation unconditionally. [4](#0-3) 

Once added to the `PerasCertDB`, the certificate triggers `chainSelSync` → `chainSelectionForBlock` for the boosted block, applying `perasWeight` (default: 15 blocks) to its chain weight: [5](#0-4) 

The `ValidatedPerasCert` wrapper type is designed to carry the invariant that the certificate has been verified; the stub breaks this invariant silently. [6](#0-5) 

**Analog to the external report:** In the DODO bug, `if(zrc20 != _ETH_ADDRESS_)` caused `transferFrom` validation to be skipped entirely for native tokens. Here, the `validatePerasCert` stub causes all certificate validation to be skipped for every certificate — the same pattern of a branch/implementation that should enforce a security invariant but does not.

---

### Impact Explanation

An unprivileged peer can:
1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on a fork.
2. Send it via the Peras certificate object-diffusion mini-protocol.
3. The receiving node accepts it unconditionally (no signature, no quorum, no round check).
4. The boosted block gains `perasWeight = 15` extra chain weight.
5. If the fork's total weight now exceeds the current selection, the node switches chains — preferring a non-canonical, potentially adversarially-controlled chain.

This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The certificate object-diffusion mini-protocol is a public, peer-reachable network endpoint. Any connected peer can send arbitrary `PerasCert` messages. No stake, keys, or special privileges are required. The attack requires only knowledge of a block hash in the VolatileDB (obtainable via ChainSync) and sending a single crafted message. Likelihood is **High** once Peras is active on a live network.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation that checks:
- The certificate's aggregate BLS signature against the claimed voter set.
- That the voter set's total stake meets the quorum threshold (`stakeAboveThreshold`).
- That the certificate's round number is within the valid window.
- That the boosted block's slot satisfies `perasBlockMinSlots`.

Until the real implementation is in place, inbound certificates from peers should be rejected entirely (return `Left PerasValidationErr` unconditionally) rather than accepted unconditionally, to prevent the chain-selection bypass.

---

### Proof of Concept

```
1. Attacker node connects to honest node via the Peras cert diffusion mini-protocol.
2. Attacker observes a block hash H on a fork F via ChainSync.
3. Attacker sends: PerasCert { pcCertRound = R, pcCertBoostedBlock = H }
4. Honest node calls validatePerasCert mkPerasParams cert
   → always returns Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }
5. chainSelSync adds cert to PerasCertDB, triggers chainSelectionForBlock for H.
6. Fork F now has weight(F) + 15 > weight(current chain).
7. Honest node switches to fork F — a non-canonical chain chosen by the attacker.
``` [7](#0-6) [8](#0-7)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
