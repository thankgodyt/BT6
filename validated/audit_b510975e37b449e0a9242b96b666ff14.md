### Title
`sync_chain_signatures_root_public_key` Is One-Shot and Cannot Be Re-Synced After MPC Key Rotation — (`contracts/satoshi-bridge/src/api/management.rs`)

### Summary

The `satoshi-bridge` contract stores the MPC root public key (`chain_signatures_root_public_key`) exactly once via `sync_chain_signatures_root_public_key`. A hard `require!` guard prevents any subsequent re-sync. Because `ConfigUpdate` also omits this field, there is no path to update the stored key after initial sync. If the NEAR Chain Signatures MPC contract rotates its root public key, all withdrawal signing and deposit-address derivation will permanently break, locking every bridge-controlled UTXO.

### Finding Description

`sync_chain_signatures_root_public_key` in `contracts/satoshi-bridge/src/api/management.rs` enforces a one-time-only constraint:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    require!(
        self.internal_config()
            .chain_signatures_root_public_key
            .is_none(),
        "Already sync"   // ← permanently blocks re-sync
    );
    self.sync_chain_signatures_root_public_key_promise()
}
``` [1](#0-0) 

Once the key is set, the only other mutation path is `update_config`, which applies a `ConfigUpdate`. However, `ConfigUpdate` does not include `chain_signatures_root_public_key` or `chain_signatures_account_id` as updatable fields: [2](#0-1) 

The stored key is used in every critical bridge operation. `generate_public_key` reads it to derive all deposit addresses and PSBT signing keys:

```rust
pub fn generate_public_key(&self, path: &str) -> Vec<u8> {
    let mpc_pk = crypto_shared::near_public_key_to_affine_point(
        self.internal_config()
            .chain_signatures_root_public_key
            .clone()
            .expect("Missing chain_signatures_root_public_key"),
    );
    ...
}
``` [3](#0-2) 

`internal_sign_btc_transaction` uses `generate_btc_public_key` (which calls `generate_public_key`) to construct the PSBT payload and then calls the MPC contract to sign it: [4](#0-3) 

`sign_btc_transaction_callback` re-derives the public key from the stored root key to verify the returned signature: [5](#0-4) 

If the MPC contract rotates its root public key, the bridge continues to derive addresses and construct PSBTs from the old stale key, while the MPC contract signs with the new key. The signature verification in the callback will fail for every withdrawal, and every UTXO locked in the bridge becomes permanently inaccessible.

### Impact Explanation

**Critical — Permanent locking of all bridge-controlled BTC/ZEC funds.**

After an MPC root key rotation:
1. `generate_utxo_chain_address` derives addresses from the stale key. Deposits sent to those addresses are still controlled by the old MPC key, which the MPC contract no longer holds.
2. `internal_sign_btc_transaction` constructs PSBTs using the stale derived public key. The MPC contract signs with the new key. The signature does not match the stale public key embedded in the PSBT, so `sign_btc_transaction_callback` cannot finalize any withdrawal.
3. There is no admin path to update `chain_signatures_root_public_key` without a full contract redeployment and migration, which itself requires careful state handling.

All bridge-controlled UTXOs become permanently locked. This matches the allowed impact: *"Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

NEAR's Chain Signatures MPC protocol is an active, evolving system. Key rotation is a standard operational practice for MPC networks (e.g., resharing, validator set changes, protocol upgrades). The NEAR documentation and MPC design explicitly anticipate key version changes (the `key_version` field in `SignRequest` already signals this). A root public key rotation is a realistic, non-hypothetical event. Once it occurs, the impact is immediate and irreversible without a contract upgrade.

### Recommendation

Remove the `is_none()` guard from `sync_chain_signatures_root_public_key` so that DAO can re-sync the root public key at any time:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    // Remove: require!(self.internal_config().chain_signatures_root_public_key.is_none(), "Already sync");
    self.sync_chain_signatures_root_public_key_promise()
}
```

Additionally, add `chain_signatures_root_public_key` and `chain_signatures_account_id` to `ConfigUpdate` so the DAO can update the MPC contract address and trigger a re-sync in a single atomic operation. When the root key changes, the `change_address` (derived from the root key) must also be re-derived, which `sync_root_public_key_callback` already handles correctly.

### Proof of Concept

1. Bridge is deployed and `sync_chain_signatures_root_public_key` is called once. `chain_signatures_root_public_key` is now `Some(old_key)`.
2. NEAR MPC protocol rotates its root public key. The chain signatures contract now returns `new_key` from `public_key()`.
3. DAO calls `sync_chain_signatures_root_public_key` again. The call panics with `"Already sync"` at line 273.
4. DAO calls `update_config` with a `ConfigUpdate` attempting to set the new key — the field does not exist in `ConfigUpdate`, so it cannot be set.
5. A user initiates a withdrawal via `ft_transfer_call`. The bridge calls `internal_sign_btc_transaction`, which constructs a PSBT using `generate_btc_public_key` (derived from `old_key`). The MPC contract signs with `new_key`. `sign_btc_transaction_callback` re-derives the public key from `old_key` and calls `psbt.save_signature(sign_index, signature, old_derived_pubkey)`. The signature is invalid for `old_derived_pubkey` — the withdrawal cannot complete.
6. All pending and future withdrawals are permanently stuck. All bridge UTXOs are permanently locked.

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
