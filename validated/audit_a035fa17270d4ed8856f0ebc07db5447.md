### Title
Peras Certificate Pre-Injection Bypasses Legitimate Certificate via "Already-in-DB" Skip - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

### Summary

`processCerts` silently discards any inbound Peras certificate whose round number is already present in the `PerasCertDB`. Because the production `validatePerasCert` implementation is an unconditional stub that always returns `Right`, an unprivileged peer can inject a certificate for any round with an arbitrary `pcCertBoostedBlock` before the legitimate certificate arrives. The legitimate certificate is then permanently silenced, and the attacker-controlled certificate drives chain selection — an exact structural analog to the Uniswap pool pre-initialization attack.

### Finding Description

**Root cause 1 — stub validation always accepts:**

`validatePerasCert` in `BlockSupportsPeras.hs` is explicitly marked TODO and unconditionally wraps any certificate as valid:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

**Root cause 2 — "already in DB" silently drops the legitimate certificate:**

`processCerts` reads the current set of round numbers from the DB and filters out any certificate whose round is already present, *before* any validation of the incoming certificate:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
``` [2](#0-1) 

This is called from the production `makePerasCertPoolWriterFromChainDB` path, which is the live network-facing writer: [3](#0-2) 

**Root cause 3 — one-cert-per-round invariant in `implAddCert`:**

`implAddCert` enforces that only one certificate per round is ever stored:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
``` [4](#0-3) 

The design comment in `ChainDB.API` justifies this by asserting "certificate equivocation is impossible": [5](#0-4) 

That assumption is violated while `validatePerasCert` is a stub.

**Root cause 4 — injected certificate triggers chain selection:**

When a certificate is successfully added via `chainSelSync`, chain selection is triggered for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [6](#0-5) 

The attacker's certificate thus permanently occupies round R's slot and causes the node to boost the attacker's block by `perasWeight` (default: 15 blocks of weight) in every subsequent chain selection comparison.

**Additionally**, the `opwHasObject` field of the `ObjectPoolWriter` is also keyed on round number: [7](#0-6) 

The inbound ObjectDiffusion protocol uses `opwHasObject` to pre-acknowledge objects already in the pool, meaning the node will not even *request* the legitimate certificate for round R from honest peers once the attacker's certificate occupies that slot. [8](#0-7) 

### Impact Explanation

An unprivileged peer can permanently inject a Peras certificate for any round, pointing `pcCertBoostedBlock` at an attacker-controlled block. This certificate:

1. Passes the stub `validatePerasCert` unconditionally.
2. Occupies the round's slot in the `PerasCertDB`, silencing any legitimate certificate for that round.
3. Triggers chain selection that boosts the attacker's block by `perasWeight` (15 blocks of weight).
4. Prevents the node from ever fetching the legitimate certificate from honest peers.

This constitutes a bypass of Peras certificate validation enabling unauthorized certificate acceptance and a chain selection manipulation that can cause an honest node to prefer a non-canonical, adversarially-boosted chain — matching the "Critical/High" impact tiers in the allowed scope.

### Likelihood Explanation

The attack requires only a standard peer connection and sending one crafted `PerasCert` message before the legitimate certificate propagates. No stake, keys, or operator access are needed. The stub validation makes the attack trivially reliable in the current codebase.

### Recommendation

1. **Implement real `validatePerasCert` validation** (tracking issue `cardano-peras/issues/120`) before any production deployment of the Peras diffusion path. The "already in DB" skip is only safe when equivocation is cryptographically impossible, which requires complete signature/committee validation.
2. **Do not silently skip** certificates for rounds already in the DB without first verifying the incoming certificate is identical to the stored one. If they differ, this is equivocation and should be treated as a punishable protocol violation (peer disconnection), not a silent no-op.
3. **Gate the ObjectDiffusion miniprotocol** for Peras certificates behind a feature flag that is disabled until validation is complete, to prevent the stub path from being reachable on any network where Peras is active.

### Proof of Concept

```
1. Attacker peer connects to an honest node via the ObjectDiffusion miniprotocol.
2. Attacker sends PerasCert { pcCertRound = R, pcCertBoostedBlock = attackerBlock }
   for some current round R.
3. processCerts:
     alreadyInDb = {} (round R not yet seen)
     certsNotAlreadyInDb = [attackerCert]
     validatePerasCert mkPerasParams attackerCert = Right ValidatedPerasCert{...}  -- stub
     addCert (WithArrivalTime now validatedAttackerCert)
       -> PerasCertDB stores round R -> attackerBlock
       -> chainSelectionForBlock triggered for attackerBlock
          (attackerBlock gains +15 blocks of Peras weight)
4. Legitimate certificate for round R arrives from honest peer:
     alreadyInDb = {R}
     certsNotAlreadyInDb = []   -- legitimate cert silently dropped
     no validation, no addition, no chain selection correction
5. Node permanently prefers any chain containing attackerBlock
   over an equally-long honest chain, by perasWeight = 15 blocks.
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
