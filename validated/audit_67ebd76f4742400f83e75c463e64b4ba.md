### Title
Passive UTXO Management Constraints Can Permanently Block User BTC Withdrawals Under Normal Bridge Conditions - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary

The `check_withdraw_psbt_valid` function enforces passive UTXO management constraints that can block all user BTC withdrawals when the bridge's UTXO count falls below `passive_management_lower_limit`. Under this condition, every withdrawal PSBT must have more change outputs than inputs (`input_num < change_num`). When the change amount is too small to split into the required number of valid change outputs, the withdrawal is structurally impossible, locking users out of their BTC until operator intervention.

### Finding Description

In `check_withdraw_psbt_valid`, the bridge enforces passive UTXO management constraints on every user withdrawal:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
``` [1](#0-0) 

When `utxo_num < passive_management_lower_limit`, every withdrawal must produce more change outputs than it consumes inputs. For a typical withdrawal with 1 input UTXO, the user must create at least 2 change outputs. However, each change output is subject to two additional constraints enforced in `check_withdraw_psbt`:

1. Each change output must be `>= min_change_amount`
2. Each change output must be `< min_input_amount` (the smallest input UTXO value) [2](#0-1) 

If the total change amount `C = UTXO_value - withdrawal_amount - gas_fee - withdraw_fee` satisfies `C < 2 * min_change_amount`, it is mathematically impossible to split `C` into 2 valid change outputs. The withdrawal panics and reverts. The user's nBTC is returned by the NEP-141 callback, but their BTC remains locked in the bridge's UTXO pool with no path to withdrawal.

Additionally, `max_change_number` caps the total number of change outputs: [3](#0-2) 

If `max_change_number = 1` and the passive management constraint simultaneously requires `input_num < change_num` (i.e., at least 2 change outputs for 1 input), the withdrawal is unconditionally blocked regardless of amounts.

The `utxo_num` computed in `check_withdraw_psbt_valid` represents the total UTXO count before the withdrawal (the pool after input removal plus the inputs themselves): [4](#0-3) 

This means the constraint fires based on the current bridge UTXO count, which can fall below `passive_management_lower_limit` through ordinary bridge usage (many withdrawals reducing the pool).

The entry point is the public `ft_on_transfer` callback, reachable by any nBTC holder via `ft_transfer_call`: [5](#0-4) 

### Impact Explanation

When the bridge UTXO count falls below `passive_management_lower_limit`, all user withdrawals that cannot satisfy `input_num < change_num` with valid change amounts are blocked. Users holding nBTC cannot redeem their BTC. The bridge enters a stuck state requiring operator intervention (DAO must adjust `passive_management_lower_limit` or perform active UTXO management to restore the count). This matches **Medium: stuck bridge state requiring operator intervention** and **attacker-triggered temporary locking of bridged funds**.

### Likelihood Explanation

The UTXO count naturally decreases as users withdraw BTC. If the bridge processes a burst of withdrawals (each consuming 1 UTXO and producing 1 change UTXO, net-neutral, or consuming 1 UTXO with no change, net-negative), the count can fall below `passive_management_lower_limit`. An adversary holding nBTC can deliberately accelerate this by making many small withdrawals that consume UTXOs without producing change (or producing minimal change), pushing the count below the threshold and blocking all subsequent users. The `passive_management_lower_limit` and `passive_management_upper_limit` are configurable but must satisfy `lower < upper`: [6](#0-5) 

If these are set to operationally realistic values (e.g., lower=5, upper=50), the bridge can reach the blocking state through normal usage.

### Recommendation

1. **Monitor UTXO count** and emit warnings when approaching `passive_management_lower_limit`; proactively trigger active UTXO management before the threshold is breached.
2. **Decouple passive management from user withdrawals**: enforce the UTXO-count constraints only as a soft advisory or apply them only to relayer-submitted PSBTs, not to user-initiated withdrawals.
3. **Provide a fallback withdrawal path** that bypasses passive management constraints when the user's change amount cannot satisfy the split requirement, routing the excess to a single change output.
4. **Set `passive_management_lower_limit` conservatively low** relative to expected minimum UTXO pool size to reduce the probability of the blocking condition being reached.

### Proof of Concept

1. Bridge is configured with `passive_management_lower_limit = 3`, `min_change_amount = 600`, `max_change_number = 2`.
2. Bridge UTXO pool contains 3 UTXOs of 100,000 sats each.
3. Two users withdraw, each consuming 1 UTXO and producing 1 change UTXO. Pool now has 3 UTXOs (2 change + 1 original). Count still = 3.
4. One more withdrawal consumes 1 UTXO with no change (exact match). Pool = 2 UTXOs. `utxo_num = 2 < 3 = passive_management_lower_limit`.
5. Alice now tries to withdraw 99,000 sats using the remaining 100,000-sat UTXO. Change = 100,000 - 99,000 - gas_fee - withdraw_fee ≈ 500 sats.
6. `check_withdraw_psbt_valid` requires `input_num (1) < change_num`. Alice must produce 2 change outputs. But 500 sats cannot be split into 2 outputs each `>= 600` sats.
7. The `require!(input_num < change_num, ...)` fires, the transaction panics, Alice's nBTC is returned, but her BTC remains locked in the bridge pool with no valid withdrawal path until the DAO intervenes. [1](#0-0) [7](#0-6)
