### Title
Peras Vote Diffusion Handler Registered with Hardcoded Empty Stake Distribution Causes All Inbound Votes to Be Rejected and Peers Disconnected — (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`)

---

### Summary

The production `mkHandlers` function wires the `hPerasVoteDiffusionClient` miniprotocol handler with `pure (PerasVoteStakeDistr mempty)` as the stake distribution. Because `validatePerasVote` uses this distribution to look up each voter's stake, and an empty map always returns `Nothing`, **every inbound Peras vote fails validation**. The `processVotes` function then throws `PerasVoteValidationError`, which disconnects the sending peer. No Peras certificate can ever be forged from received votes, completely breaking the Peras chain-weight boosting mechanism. The code comment at the call site explicitly acknowledges this consequence.

---

### Finding Description

In `NodeToNode.hs`, `mkHandlers` constructs the live node handler record. The `hPerasVoteDiffusionClient` field calls `makePerasVotePoolWriterFromChainDB` and passes `pure (PerasVoteStakeDistr mempty)` as the `getStakeDistrSTM` argument:

```haskell
, hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      ( makePerasVotePoolWriterFromChainDB
          systemTime
          -- TODO: when actual plumbing for Peras is ready, we will have to
          -- extract the committee selection data from the chainDB to pass
          -- it here, instead of relying on an empty the stake distribution.
          --
          -- Note that the empty stake distribution will cause all votes to
          -- be considered invalid.
          (pure (PerasVoteStakeDistr mempty))
          getChainDB
      )
```

This is the **only** production instantiation of the Peras vote inbound handler. The analogous situation to the GMXV2 report is exact: the handler is **registered** (the miniprotocol is active and accepts connections), but the **required implementation** (actual committee/stake data) is absent, replaced by a stub that guarantees failure.

The validation chain is:

1. `makePerasVotePoolWriterFromChainDB` calls `processVotes` with a validator that reads the stake distribution via `getStakeDistrSTM` and calls `validatePerasVote`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

2. `validatePerasVote` in `SupportsPeras.hs` performs a map lookup:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

With `PerasVoteStakeDistr mempty`, `lookupPerasVoteStake` always returns `Nothing`, so every vote produces `Left PerasValidationErr`.

3. `processVotes` collects all errors and throws:

```haskell
(errs, _) ->
  throw (PerasVoteValidationError errs)
```

The thrown `PerasVoteValidationError` is an `Exception`, which propagates up through `objectDiffusionInbound` and causes the peer connection to be torn down (as documented in the comment: *"which should make us disconnect from the distant peer"*).

---

### Impact Explanation

**High — Chain selection bug that makes an honest node operate below its intended security assumptions.**

The Peras protocol is designed to boost chain weight via certificates forged from quorum-reaching vote batches. With all inbound votes rejected:

- No `ValidatedPerasVote` is ever stored in the `PerasVoteDB`.
- No quorum is ever reached; no `ValidatedPerasCert` is ever forged from received votes.
- `ChainDB.addPerasVoteWithAsyncCertHandling` is never called with a valid vote, so the `PerasCertDB` receives no certificates from the vote path.
- Chain selection in `ChainSel.hs` never receives a `ChainSelAddPerasCert` event from this path, so the Peras chain-weight boost is permanently absent.
- Every honest peer that sends Peras votes is disconnected, degrading the node's view of the Peras vote pool.

The node silently falls back to pure Praos chain selection, operating with weaker settlement guarantees than the protocol intends. An adversary aware of this condition can exploit the longer effective settlement window that Peras was designed to close.

---

### Likelihood Explanation

**High.** This is unconditional: the empty `mempty` map is hardcoded in the production `mkHandlers` call path. There is no runtime flag, configuration option, or era-gating that could supply a non-empty distribution. Every node built from this codebase that activates the Peras vote diffusion miniprotocol will exhibit this behaviour on every inbound vote from every peer.

---

### Recommendation

Replace `pure (PerasVoteStakeDistr mempty)` with an `STM` action that reads the actual committee selection / stake distribution from the `ChainDB` (or a dedicated Peras state component), as the TODO comment already prescribes. Until that plumbing is complete, the Peras vote diffusion miniprotocol should either be disabled at the version-negotiation layer or the handler should be wired to a no-op writer that does not validate against an empty distribution, so that peers are not spuriously disconnected.

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
