### Title
Missing `refund_address` Validation at Request Time Enables Attacker-Triggered Temporary Fund Lock - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` accepts and stores any arbitrary string as `refund_address` without validating it as a parseable BTC address for the configured chain. Address parsing only occurs later in `build_refund_output` during `execute_refund`, which panics on an invalid address. An unprivileged NEAR account can exploit this to permanently block a victim's refund path for a specific UTXO until DAO intervention.

### Finding Description
In `internal_request_refund`, the `refund_address` string is passed through three checks: (1) sufficient attached deposit, (2) tx size limit, and (3) optional match against `deposit_msg.refund_address`. None of these checks verify that `refund_address` is a syntactically valid BTC/ZEC address for the bridge's configured chain. [1](#0-0) 

The address is then forwarded through the Light Client callback and stored verbatim in `RefundRequest.refund_address`: [2](#0-1) 

Validation only occurs in `build_refund_output`, called during `execute_refund`, which calls `Address::parse(...).expect("Invalid refund address")` — a hard panic: [3](#0-2) 

Because `request_refund_callback` also enforces uniqueness per UTXO: [4](#0-3) 

once a malicious request is stored, no second `request_refund` for the same UTXO can succeed, and `execute_refund` will always panic.

### Impact Explanation
An attacker who observes a victim's `deposit_msg` (emitted as an on-chain event by `get_user_deposit_address`) can race to call `request_refund` with `refund_address = ""` or any garbage string before the victim does. The result:

- The UTXO is locked inside the refund system; the victim's own `request_refund` is rejected with "Refund request already exists for this UTXO".
- `execute_refund` always panics, so the refund can never be executed.
- The victim's BTC remains unreachable via the refund path until a DAO/Operator calls `reject_refund`.

This matches **Medium — attacker-triggered temporary locking of bridged funds** requiring operator intervention to resolve. [5](#0-4) 

### Likelihood Explanation
- `request_refund` is a public, payable function callable by any NEAR account willing to pay the storage deposit.
- The victim's `deposit_msg` is publicly observable from the `LogDepositAddress` event emitted by `get_user_deposit_address`.
- The attacker only needs to front-run the victim's `request_refund` call, which is straightforward on NEAR where transaction ordering is visible in the mempool.
- The attacker's only cost is the non-refundable storage deposit.

### Recommendation
Validate `refund_address` as a parseable address for the configured chain at the beginning of `internal_request_refund`, before the Light Client cross-contract call is dispatched:

```rust
// In internal_request_refund, after the existing require! checks:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the validation already applied to `target_btc_address` in `Config::target_script_pubkey`: [6](#0-5) 

### Proof of Concept
1. Alice deposits BTC to her bridge address (derived from her `deposit_msg`). The `LogDepositAddress` event reveals her `deposit_msg`.
2. The deposit is not yet finalized by the relayer.
3. Attacker calls `request_refund(alice_deposit_msg, refund_address="INVALID", tx_bytes, vout, proof, None)` with sufficient attached deposit.
4. Light Client verification passes (it only checks transaction inclusion, not the refund address).
5. `request_refund_callback` stores `RefundRequest { refund_address: "INVALID", ... }`.
6. Alice calls `request_refund` — fails: `"Refund request already exists for this UTXO"`.
7. Anyone calls `execute_refund` — panics: `"Invalid refund address"` inside `build_refund_output`.
8. Alice's BTC is locked in the refund system until DAO calls `reject_refund`. [7](#0-6)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
