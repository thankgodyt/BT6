### Title
`partialLedgerConfigConway` Ignores `triggerHardForkDijkstra` and Hardcodes `TriggerHardForkNotDuringThisExecution`, Permanently Preventing the Conway→Dijkstra Era Transition — (File: `ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

In `protocolInfoCardano`, the `CardanoHardForkTriggers'` pattern synonym exposes seven trigger fields — one per Shelley-based era — including `triggerHardForkDijkstra`. However, the pattern match inside `protocolInfoCardano` only binds six of those fields, silently dropping `triggerHardForkDijkstra`. As a result, `partialLedgerConfigConway` is constructed with the hardcoded value `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`. This is a direct copy-paste analog of the original report: one setter (the Conway ledger config) updates the wrong "variable" (a hardcoded no-op trigger) while the intended variable (`triggerHardForkDijkstra`) is silently ignored.

---

### Finding Description

The `CardanoHardForkTriggers'` pattern synonym is defined with seven fields: [1](#0-0) 

Inside `protocolInfoCardano`, the destructuring of `cardanoHardForkTriggers` only binds six of those fields — `triggerHardForkDijkstra` is absent: [2](#0-1) 

Every other era's ledger config correctly passes the trigger for the *next* era. For example, Babbage correctly uses `triggerHardForkConway`: [3](#0-2) 

But Conway's ledger config hardcodes `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`: [4](#0-3) 

`TriggerHardForkNotDuringThisExecution` is the correct value only for the *last* era (Dijkstra), where there is no successor: [5](#0-4) 

The `singleEraTransition` function in the HFC uses the trigger embedded in the partial ledger config to decide when to advance the telescope to the next era. With `TriggerHardForkNotDuringThisExecution` in the Conway config, `singleEraTransition` always returns `Nothing` for the Conway→Dijkstra boundary, so `extendToSlot` never crosses that boundary regardless of what `triggerHardForkDijkstra` was set to. [6](#0-5) 

---

### Impact Explanation

When the Dijkstra transition epoch arrives on the network, nodes running this code will:

1. Never call `extendToSlot` across the Conway→Dijkstra boundary.
2. Reject every valid Dijkstra-era block received from peers, because the HFC `applyBlockLedgerResult` will see a block from the "wrong era" (Dijkstra) while the node's telescope is still in Conway.
3. Permanently diverge from the canonical chain, constituting a hard-fork era transition bug that breaks cross-era consensus for production Cardano nodes.

This matches the **High** impact category: *"Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes."* [7](#0-6) 

---

### Likelihood Explanation

This bug is latent but deterministic: it activates automatically the moment the Dijkstra transition epoch is reached on any network (mainnet, testnet, or private testnet) where `triggerHardForkDijkstra` is set to a non-`TriggerHardForkNotDuringThisExecution` value. No attacker action is required. Any peer that sends a valid Dijkstra-era block to a node running this code will cause that node to reject it and diverge. The entry path is a standard block diffusion message from an unprivileged peer after the transition epoch.

---

### Recommendation

In `protocolInfoCardano`, bind `triggerHardForkDijkstra` in the pattern match and use it in `partialLedgerConfigConway`:

```haskell
-- Before (buggy):
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    TriggerHardForkNotDuringThisExecution

-- After (correct):
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    (toTriggerHardFork triggerHardForkDijkstra)
```

Also add `triggerHardForkDijkstra` to the destructuring of `cardanoHardForkTriggers` at line 604–612.

---

### Proof of Concept

On a private testnet, set `triggerHardForkDijkstra = CardanoTriggerHardForkAtEpoch 5` and `triggerHardForkConway = CardanoTriggerHardForkAtEpoch 4`. Observe that:

1. The node transitions from Babbage → Conway at epoch 4 (correct, because `partialLedgerConfigBabbage` uses `triggerHardForkConway`).
2. The node **never** transitions from Conway → Dijkstra at epoch 5, because `partialLedgerConfigConway` ignores `triggerHardForkDijkstra` and uses `TriggerHardForkNotDuringThisExecution`.
3. Any Dijkstra-era block received from a correctly-configured peer is rejected with `HardForkLedgerErrorWrongEra`, causing a permanent chain split. [2](#0-1) [4](#0-3)
