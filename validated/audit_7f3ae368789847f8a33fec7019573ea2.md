### Title
`safe_mint` Silently Traps User nBTC in Bridge Balance When Recipient Is Unregistered — (`contracts/nbtc/src/lib.rs`)

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own balance (`bridge_id`) before checking whether the intended recipient (`account_id`) is registered. If the recipient is not registered, the function returns `U128(0)` without transferring the tokens, leaving them permanently trapped in the bridge's nBTC balance with no on-chain recovery path visible in the nBTC contract itself.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes `internal_deposit` to the bridge's own account unconditionally, then checks registration:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← silent return, tokens NOT transferred
    }
    ...
}
``` [1](#0-0) 

The tokens are credited to `bridge_id` (the bridge contract's own nBTC balance) at line 112, before the registration check at line 114. If `account_id` is unregistered, the function returns `U128(0)` and the tokens remain in the bridge's balance with no transfer to the user.

Contrast this with the non-safe `mint` path, which uses `mint_inner` and auto-registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
}
``` [2](#0-1) 

`safe_mint` deliberately skips auto-registration (to support `ft_transfer_call` semantics), but the consequence is that the minted supply is irrecoverably separated from the user when the account is absent.

The nBTC contract's `new()` only registers `bridge_id`:

```rust
contract.token.internal_register_account(&contract.bridge_id);
``` [3](#0-2) 

No other account is pre-registered. Any `recipient_id` in a `DepositMsg` that has not previously called `storage_deposit` on the nBTC contract will trigger this silent failure.

### Impact Explanation

When `safe_mint` returns `U128(0)`:
- The nBTC supply has been inflated (tokens minted to `bridge_id`).
- The user's `recipient_id` balance is unchanged — they received nothing.
- The deposited BTC UTXO is consumed and marked verified by the bridge.
- The minted nBTC sits in the bridge's own token balance with no dedicated withdrawal or `lost_found` path visible in the nBTC contract.

The `lost_found` mechanism in the bridge (`token_transfer.rs`) is triggered only by a failed `ft_transfer` callback (`transfer_nbtc_callback`), not by a `U128(0)` return from `safe_mint`. [4](#0-3) 

This matches the allowed impact: **permanent burning below backed supply** (nBTC minted but not delivered, BTC locked) and **broken callback rollback** (the `U128(0)` return is not equivalent to a failed promise that triggers rollback).

### Likelihood Explanation

Any user who deposits BTC using the `safe_verify_deposit` path with a `DepositMsg.recipient_id` that has not registered storage on the nBTC contract will trigger this. This is a realistic scenario for:
- New users who have never interacted with the nBTC contract.
- Users specifying a smart-contract account as recipient that has not called `storage_deposit`.
- Integrators constructing deposit messages programmatically without pre-registering the recipient.

The entry path is fully unprivileged: a user constructs a `DepositMsg`, sends BTC on-chain, and a relayer submits the proof. No privileged access is required.

### Recommendation

Move `internal_deposit` to occur **after** the registration check, or auto-register the account (matching `mint_inner` behavior), or revert instead of returning `U128(0)` when the recipient is unregistered:

```rust
// Option A: auto-register (matches mint_inner)
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
}
self.token.internal_deposit(&self.bridge_id, amount.into());

// Option B: revert on unregistered recipient
require!(
    self.token.accounts.get(&account_id).is_some(),
    "Recipient account not registered"
);
self.token.internal_deposit(&self.bridge_id, amount.into());
```

If silent failure is intentional, the bridge's `safe_verify_deposit` callback must explicitly detect `U128(0)` and credit the amount to `lost_found` for the user, mirroring the `transfer_nbtc_callback` pattern.

### Proof of Concept

1. Alice has BTC but has never registered storage on the nBTC contract.
2. Alice constructs `DepositMsg { recipient_id: "alice.near", ... }` and sends BTC to the bridge deposit address.
3. A relayer calls `safe_verify_deposit` with the Merkle proof.
4. The bridge calls `safe_mint("alice.near", amount, msg)` on the nBTC contract.
5. `internal_deposit(&bridge_id, amount)` executes — nBTC supply increases, bridge balance increases.
6. `self.token.accounts.get(&"alice.near")` returns `None` — Alice is not registered.
7. `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
8. Alice's nBTC balance: 0. Bridge's nBTC balance: +amount. Alice's BTC: gone.
9. No `lost_found` entry is created for Alice because no `transfer_nbtc_callback` was invoked. [5](#0-4)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    #[private]
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
