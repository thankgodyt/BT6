### Title
`PerasVoteId` Excludes Voted Block, Enabling Vote-Slot Squatting That Silently Drops Legitimate Votes — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`PerasVoteId` is constructed from only `(roundNo, voterId)`, omitting the voted block (`pvVoteBlock`). Because the `PerasVoteDB` uses this ID as the uniqueness key for deduplication, two structurally distinct votes — same voter, same round, but different target blocks — share the same ID. Combined with a stub `validatePerasVote` that performs no signature verification, an unprivileged peer can send a crafted vote carrying a legitimate voter's ID but targeting a wrong block. This occupies the voter's ID slot in the DB, causing the legitimate vote to be silently dropped as `PerasVoteAlreadyInDB`. If enough voters are affected, quorum is never reached, no Peras certificate is generated, and chain selection is degraded.

---

### Finding Description

**Root cause — incomplete identifier construction:**

`PerasVoteId` is defined as:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
``` [1](#0-0) 

The `getPerasVoteId` instance builds this ID from only the round number and voter ID, explicitly omitting `pvVoteBlock`:

```haskell
instance HasPerasVoteId (PerasVote blk) blk where
  getPerasVoteId vote =
    PerasVoteId
      { pviRoundNo = pvVoteRound vote
      , pviVoterId = pvVoteVoterId vote
      }
``` [2](#0-1) 

**Deduplication uses this incomplete ID:**

`implAddVote` in `PerasVoteDB.Impl` checks `pvdsVoteIds` (a `Set (PerasVoteId blk)`) before inserting. If the ID is already present, the vote is silently discarded:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [3](#0-2) 

The model explicitly acknowledges the assumption this creates:

> *"NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body)."* [4](#0-3) 

**Stub validation allows forged voter IDs:**

`validatePerasVote` — the only production implementation — performs no signature check. It accepts any vote whose `pvVoteVoterId` appears in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [5](#0-4) 

The `PerasVote` type at the consensus layer carries no signature field, so the consensus-layer deduplication path has no way to distinguish a crafted vote from a legitimate one:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [6](#0-5) 

**Inbound processing silently skips already-known IDs:**

`processVotes` (the entry point for votes received from peers) checks `alreadyInDbSTM` before validation. A crafted vote that arrives first and passes the stub validation will occupy the slot; the legitimate vote arriving later is skipped without error: [7](#0-6) 

---

### Impact Explanation

**High — Chain selection degradation via Peras certificate suppression.**

Peras certificates boost the weight of a block in chain selection. If an attacker prevents quorum from being reached for the correct block in a round, no certificate is generated, and the block receives no Peras weight boost. An adversary who squats the vote slots of enough committee members (whose IDs are publicly derivable from the stake distribution) can systematically suppress certificate generation, weakening the security guarantees Peras is designed to provide and potentially causing honest nodes to prefer a less-secure chain.

---

### Likelihood Explanation

**Low.** The attack requires:
1. Sending crafted votes before legitimate votes arrive (a race condition over the network).
2. Knowing which pool IDs are in the current committee (derivable from the public stake distribution).
3. The current stub `validatePerasVote` makes forging trivial; once real BLS signature verification is wired in, the attack becomes cryptographically infeasible unless the attacker holds a voter's private key.

The likelihood is low in a production deployment with proper signature validation, but is currently trivially exploitable in the codebase as-is.

---

### Recommendation

1. **Include `pvVoteBlock` in `PerasVoteId`** so that two votes from the same voter for the same round but different blocks are treated as distinct objects (equivocating votes), not as duplicates. The deduplication key should be `(roundNo, voterId, votedBlock)` or the full vote content.

2. **Implement real signature verification in `validatePerasVote`** before votes are admitted to the DB. The concrete `V1.PerasVote` carries a BLS signature; this must be verified against the voter's public key (from the stake distribution) before the vote is accepted.

3. **Reject equivocating votes explicitly** (same voter, same round, different block) rather than silently dropping them, so that equivocation is observable and can be penalised.

---

### Proof of Concept

```
Attacker (peer P) knows voter V is in the committee for round R.

1. P crafts PerasVote { pvVoteRound = R, pvVoteBlock = B_attacker, pvVoteVoterId = V }
   — no signature required; validatePerasVote only checks stake distribution membership.

2. P sends this vote to honest node N before V's legitimate vote arrives.

3. N calls processVotes → validatePerasVote succeeds (V is in stake distribution)
   → implAddVote inserts voteId = PerasVoteId { pviRoundNo = R, pviVoterId = V }
      into pvdsVoteIds.

4. V's legitimate vote PerasVote { pvVoteRound = R, pvVoteBlock = B_correct, pvVoteVoterId = V }
   arrives at N.

5. implAddVote computes voteId = PerasVoteId { pviRoundNo = R, pviVoterId = V }
   → Set.member voteId pvdsVoteIds == True
   → returns PerasVoteAlreadyInDB; legitimate vote is silently dropped.

6. V's stake is not counted toward quorum for B_correct.
   Repeat for enough voters → quorum never reached → no Peras certificate for B_correct
   → B_correct receives no Peras weight boost → chain selection is degraded.
``` [8](#0-7) [1](#0-0)
