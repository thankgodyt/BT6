### Title
DAO Can Set Arbitrarily Large `refund_timelock_sec` / `unsafe_refund_timelock_sec` to Permanently Lock All Pending Refund Requests — (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary

The `update_config` function allows the DAO to update `refund_timelock_sec` and `unsafe_refund_timelock_sec` to any arbitrary `u64` value with no upper-bound validation. Because `execute_refund` reads these values from the **current** config at call time — not from the config that existed when the refund request was created — a DAO config change retroactively applies to every pending `RefundRequest`. Setting either timelock to `u64::MAX` permanently blocks all existing refund requests, trapping users' BTC/ZEC in bridge deposit addresses with no recovery path.

---

### Finding Description

**Step 1 — No upper-bound on timelock parameters.**

`Config` declares two timelock fields: [1](#0-0) 

`assert_valid()` only enforces the ordering invariant `refund_timelock_sec <= unsafe_refund_timelock_sec`; it imposes no ceiling: [2](#0-1) 

**Step 2 — DAO can update these values at any time.**

`update_config` is restricted to `Role::DAO` and immediately applies the new values via `ConfigUpdate::apply`: [3](#0-2) 

`ConfigUpdate::apply` uses a `set_if_some!` macro that writes the new value directly into the live config with no additional validation beyond `assert_valid()`: [4](#0-3) 

**Step 3 — Timelock is read from current config at execution time, not at request-creation time.**

`resolve_execute_refund_timelock` fetches the timelock from the live config every time `execute_refund` is called: [5](#0-4) 

`load_refund_request_for_execute` then evaluates the elapsed time against that live value: [6](#0-5) 

`RefundRequest` records `created_at_sec` at request time but stores no snapshot of the timelock that was in effect: [7](#0-6) 

Because the timelock is always sourced from the current config, any increase takes immediate retroactive effect on every pending request.

---

### Impact Explanation

A user who sent BTC/ZEC to a bridge deposit address but cannot complete the deposit (e.g., wrong `DepositMsg` parameters) has exactly one recovery path: `request_refund` → wait for timelock → `execute_refund`. If the DAO raises `refund_timelock_sec` or `unsafe_refund_timelock_sec` to `u64::MAX` after requests are already queued, the condition `now >= created_at_sec + u64::MAX` can never be satisfied. Every pending `RefundRequest` is permanently frozen. The underlying BTC/ZEC remains unspendable in the deposit address (the bridge holds the signing key via MPC), constituting permanent loss of user funds.

**Allowed impact matched:** *Medium — attacker-triggered permanent locking of bridged funds* and *Critical — permanent loss of user funds* depending on the magnitude of locked value.

---

### Likelihood Explanation

The DAO role is a single NEAR account (not a multi-sig or on-chain governance system by default). A compromised DAO key, an insider threat, or a governance capture event is sufficient. No user interaction is required beyond having an existing pending refund request. The default timelocks are 2 days and 14 days respectively, so there will routinely be live requests in the window.

---

### Recommendation

1. **Add an upper-bound constant** in `assert_valid()`, e.g. `MAX_REFUND_TIMELOCK_SEC = 30 * 24 * 3600` (30 days), and `require!(self.unsafe_refund_timelock_sec <= MAX_REFUND_TIMELOCK_SEC, ...)`.
2. **Snapshot the timelock at request creation time** — store the effective `timelock_sec` inside `RefundRequest` and use that stored value in `load_refund_request_for_execute`, so config changes only affect future requests.
3. Alternatively, allow config increases to apply only to newly created requests (i.e., compare against `created_at_sec` using the timelock value that was active at creation).

---

### Proof of Concept

```
1. User sends 0.5 BTC to a bridge deposit address with an incorrect DepositMsg.
   The deposit cannot be finalized.

2. User calls request_refund(...) with a valid Merkle proof.
   → request_refund_callback stores RefundRequest {
         created_at_sec: T,          // e.g. block timestamp = 1_000_000
         refund_address: "bc1q...",  // pre-authorized (deposit_msg.refund_address = Some)
         ...
     }

3. DAO calls update_config({ refund_timelock_sec: "18446744073709551615" })
   → ConfigUpdate::apply writes u64::MAX into config.refund_timelock_sec.
   → assert_valid() passes (only checks refund_timelock_sec <= unsafe_refund_timelock_sec,
     so DAO also sets unsafe_refund_timelock_sec = u64::MAX).

4. User waits the original 2-day timelock and calls execute_refund(utxo_storage_key).
   → resolve_execute_refund_timelock reads config.refund_timelock_sec = u64::MAX.
   → load_refund_request_for_execute checks:
         now (e.g. 1_200_000) >= 1_000_000 + 18_446_744_073_709_551_615
         → FALSE → panic "Refund timelock has not passed yet"

5. User can never satisfy the condition. BTC is permanently locked.
   The only escape (reject_refund by DAO/RefundOperator) is controlled by the
   same party that set the infinite timelock.
```
