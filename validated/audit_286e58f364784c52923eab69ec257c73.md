### Title
Whitelisted Receiver Without `msg_templates` Bypasses Post-Action Message Validation — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

`check_deposit_msg` validates `post_action.msg` against approved templates only when `post_action_msg_templates` contains an entry for the receiver. When a receiver is on the whitelist but has **no** entry in `post_action_msg_templates`, the `if let Some(msg_templates)` branch is never entered, and any attacker-supplied `msg` passes validation unconditionally.

---

### Finding Description

In `check_deposit_msg`, after confirming the receiver is whitelisted, the msg-template guard is:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validate msg against templates — only reached when templates exist
    ...
    if !is_match {
        return None;
    }
}
// falls through with arbitrary msg when templates map returns None
``` [1](#0-0) 

The two management operations that govern this state are independent:

- `extend_post_action_receiver_id_white_list` — adds a receiver to the whitelist
- `extend_post_action_msg_templates` — separately adds templates for a receiver [2](#0-1) 

There is no enforcement that adding a receiver to the whitelist requires simultaneously setting templates. A receiver can legally exist in `post_action_receiver_id_white_list` with no corresponding entry in `post_action_msg_templates`. In that state, `post_action_msg_templates.get(&receiver_id)` returns `None`, the `if let Some` block is skipped, and `check_deposit_msg` returns `Some(post_actions)` carrying the attacker-controlled `msg`.

The validated `post_actions` are then forwarded through `internal_mint_promise` → `ext_nbtc::mint` → `ft_transfer_call` to the whitelisted receiver with the arbitrary msg intact. [3](#0-2) [4](#0-3) 

---

### Impact Explanation

The receiver contract's `ft_on_transfer` is invoked with a fully attacker-controlled `msg`. Any DeFi protocol on the whitelist that dispatches logic based on the msg content (e.g., swap routing, vault operations, cross-contract calls) can be driven into unintended states. Depending on the receiver's logic, this can result in:

- Attacker-directed routing of the transferred nBTC within the receiver protocol
- Triggering of privileged or unintended code paths in the receiver contract
- Locking or misdirection of the bridged nBTC

This matches the **Medium** impact class: harmful smart-contract behavior without direct theft from the bridge itself, but with potential for stuck or misdirected bridged funds.

---

### Likelihood Explanation

The precondition — a receiver on the whitelist with no templates — is a reachable deployment state. The DAO may:

1. Add a receiver to the whitelist in preparation for later template configuration (leaving a window of exposure).
2. Intentionally add a "fully trusted" receiver without templates, not realizing this removes all msg constraints for that receiver.

The attacker path is entirely unprivileged: submit a BTC deposit whose `DepositMsg` encodes a `post_actions` array targeting the template-less whitelisted receiver with a crafted `msg`. No role, key, or operator access is required beyond a valid BTC deposit.

---

### Recommendation

Enforce that a receiver must have at least one template registered before it can be used in a `post_action`. Two complementary fixes:

1. **In `check_deposit_msg`**: treat a missing templates entry as a rejection, not a pass-through:

```rust
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .ok_or_else(|| /* emit InvalidPostAction, return None */)?;
// then validate msg against msg_templates
```

2. **In `extend_post_action_receiver_id_white_list`** (or a combined admin call): require that at least one template is provided at the time the receiver is whitelisted, so the two maps are always kept in sync.

---

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list([receiver.near])` — no call to `extend_post_action_msg_templates`.
2. Attacker submits a valid BTC deposit with:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "receiver.near",
       "amount": "1000",
       "msg": "<arbitrary attacker-controlled payload>"
     }]
   }
   ```
3. `check_deposit_msg` is called: whitelist check passes; `post_action_msg_templates.get("receiver.near")` returns `None`; `if let Some` block is skipped; function returns `Some(post_actions)`.
4. `ft_transfer_call("receiver.near", 1000, "<arbitrary payload>")` executes.
5. `receiver.near`'s `ft_on_transfer` receives the attacker-controlled msg and may execute unintended logic.

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn extend_post_action_receiver_id_white_list(&mut self, receiver_ids: Vec<AccountId>) {
        assert_one_yocto();
        for receiver_id in receiver_ids {
            let is_success = self
                .data_mut()
                .post_action_receiver_id_white_list
                .insert(receiver_id.clone());
            require!(
                is_success,
                format!("Already exist receiver_id: {}", receiver_id)
            );
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn remove_post_action_receiver_id_white_list(&mut self, receiver_ids: Vec<AccountId>) {
        assert_one_yocto();
        for receiver_id in receiver_ids {
            let is_success = self
                .data_mut()
                .post_action_receiver_id_white_list
                .remove(&receiver_id);
            require!(is_success, format!("Invalid receiver_id: {}", receiver_id));
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn set_pending_tx_limit(&mut self, account_id: AccountId, max_pending: Option<u32>) {
        assert_one_yocto();
        if let Some(max_pending) = max_pending {
            require!(max_pending >= 1, "Invalid max_pending value");
            self.data_mut()

            require!(
                prev.is_some(),
                format!("Invalid account_id: {}", account_id)
            );
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
