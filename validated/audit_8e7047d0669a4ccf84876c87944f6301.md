### Title
`validatePerasCert` Unconditionally Accepts Any Inbound Peras Certificate Without Validation, Enabling Adversarial Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right` — it performs zero cryptographic or structural checks on any inbound Peras certificate. Because this is the production instance wired into both `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB`, any unprivileged peer can inject arbitrary crafted certificates via the object diffusion mini-protocol. Each accepted certificate boosts the weight of an attacker-chosen block by `perasWeight` (default: 15) in chain selection, allowing an adversary to make an honest node prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate received from a peer is stored and used to influence chain selection. The universal instance — the only production instance — implements this gate as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is structurally identical to the Stakehouse bug: instead of a guard that always reverts, this guard always passes. No quorum check, no committee membership check, no aggregate signature verification, and no round-number sanity check is performed. The function accepts every certificate unconditionally.

This stub is wired directly into the production certificate ingest path. Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  (validatePerasCert mkPerasParams)   -- always returns Right
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

Inside `processCerts`, the validation result is the sole gate before a certificate is stored:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, the error branch is unreachable. Every certificate from every peer is stored.

Once stored, each accepted certificate contributes its `pcCertBoostedBlock` point to the `PerasWeightSnapshot`, which is read directly by chain selection:

```haskell
(,,)
  <$> (forgetFingerprint <$> readTVar cdbInvalid)
  <*> Query.getCurrentChain cdb
  <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [4](#0-3) 

Chain selection then uses `preferAnchoredCandidate`, which computes `wsvTotalWeight = blockNo + weightBoost` and switches to whichever chain has the higher total weight:

```haskell
case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
  LT -> ShouldSwitch (Heavier $ ...)
  ...
``` [5](#0-4) 

The default `perasWeight` is 15, meaning each injected certificate adds 15 weight units to the attacker's chosen block. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send crafted `PerasCert` objects with arbitrary `pcCertRound` and `pcCertBoostedBlock` fields. Because `validatePerasCert` always returns `Right`, these are stored without any check. Each stored certificate boosts the weight of the attacker-specified block by 15 in chain selection. By sending `N` certificates for different rounds (each with a unique `pcCertRound` to bypass the deduplication check on `pcdsCertIds`), the attacker accumulates `15 * N` weight units on a chosen block. This can cause an honest node to prefer a non-canonical or adversarially-controlled chain over the honest chain, violating chain selection safety.

This matches the allowed impact: **bypass of Peras certificate verification enabling unauthorized certificate acceptance**, and **chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The attack requires only that the Peras object diffusion mini-protocol is active and that the attacker can connect as a peer — no keys, no stake, no privileged access. The attacker constructs a `PerasCert` with a chosen `pcCertBoostedBlock` and a fresh `pcCertRound`, serializes it, and sends it. The deduplication check only filters certificates whose round number is already in the DB, so the attacker can use any unused round number. The attack is repeatable and requires no brute force.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation that checks:
1. The certificate's aggregate signature against the claimed committee members' verification keys.
2. That the claimed voters form a valid quorum (total stake ≥ threshold).
3. That the `pcCertRound` is within the valid range relative to the current slot/epoch.
4. That the `pcCertBoostedBlock` refers to a block that actually exists and is old enough (≥ `perasBlockMinSlots`).

Until the full cryptographic committee selection scheme is in place, at minimum enforce structural invariants (round number bounds, block point existence) and reject certificates from peers that cannot be verified, rather than accepting all of them unconditionally. [7](#0-6)

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects and the object diffusion mini-protocol for Peras certificates is established.
2. Attacker constructs a `PerasCert` with:
   - `pcCertRound = PerasRoundNo 9999` (any round not yet in the DB)
   - `pcCertBoostedBlock = <point of a block on an adversarial fork>`
3. Attacker sends this certificate to the target node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
5. The certificate is stored in `PerasCertDB` / `ChainDB`.
6. `getPerasWeightSnapshot` now includes the adversarial block with weight 15.
7. Chain selection calls `preferAnchoredCandidate` with the updated snapshot; if the adversarial chain's total weight (`blockNo + 15*N`) exceeds the honest chain's total weight, the node switches.
8. Repeat with `pcCertRound = 10000, 10001, ...` to accumulate arbitrary weight. [8](#0-7) [9](#0-8) [10](#0-9)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
