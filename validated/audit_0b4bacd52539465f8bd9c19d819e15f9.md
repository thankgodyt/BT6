### Title
Stale `branch_id` in `PsbtWrapper` Causes Zcash Transaction Rejection Across Network Upgrade Boundary — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

---

### Summary

`PsbtWrapper` freezes the Zcash consensus `branch_id` at PSBT construction time and serializes it into `psbt_hex`. When `sign_btc_transaction` is called later, the stored `branch_id` is deserialized verbatim with no re-validation against the current Zcash chain height. If a network upgrade activates between PSBT construction and signing, the sighash is computed with the old `branch_id`, producing a transaction that the Zcash network will reject. The bridge UTXOs remain unspent but the withdrawal state is stuck, requiring operator intervention via RBF.

---

### Finding Description

**Root cause — construction:**

In `ft_on_transfer_callback`, `PsbtWrapper::new` is called with `last_block_height` (the Zcash height at callback time): [1](#0-0) 

Inside `PsbtWrapper::new`, `branch_id` is computed once and stored in the struct: [2](#0-1) 

`get_branch_id` delegates to `Chain::get_branch_id`, which maps the Zcash block height to `BranchId::Nu6`, `Nu6_1`, or `Nu6_2` using hardcoded activation heights (mainnet Nu6_1 = 3,146,400; Nu6_2 = 3,364,600): [3](#0-2) 

The `branch_id` is serialized as a single byte (`7`=Nu6, `8`=Nu6_1, `9`=Nu6_2) into `psbt_hex`: [4](#0-3) 

**Root cause — signing:**

`sign_btc_transaction` calls `internal_sign_btc_transaction`, which calls `btc_pending_info.get_psbt()`: [5](#0-4) 

`get_psbt()` calls `PsbtWrapper::deserialize`, which reads back the stored byte and reconstructs the `branch_id` with no reference to the current Zcash height: [6](#0-5) 

`get_hash_to_sign` then uses `self.branch_id` (the stale value) to build the sighash: [7](#0-6) 

The same stale `branch_id` is embedded in the final `TransactionData` passed to `signature_hash`: [8](#0-7) 

There is no guard anywhere in the signing path that re-derives `branch_id` from the current Zcash height and compares it to the stored value.

---

### Impact Explanation

A Zcash V5 transaction's `nConsensusBranchId` field must match the active consensus branch at broadcast time. A transaction signed with `BranchId::Nu6` (byte `7`) after the Nu6_1 activation height (3,146,400 mainnet) will be rejected by every Zcash node. The bridge contract has no mechanism to detect this rejection. The result is:

- The signed `tx_bytes_with_sign` is stored and a `SignedBtcTransaction` event is emitted, but the transaction cannot be included in any block.
- The bridge UTXOs referenced by the PSBT remain unspent but are locked in a `PendingVerify` state.
- The user's nZEC is locked in the bridge contract pending a verification that can never succeed.
- Operator intervention (RBF via `withdraw_rbf_chain_specific` / `from_original_psbt`) is required to recover; `from_original_psbt` correctly re-derives `branch_id` from `current_height` at RBF time, so recovery is possible but not automatic. [9](#0-8) 

---

### Likelihood Explanation

The Nu6_1 and Nu6_2 activation heights are public, hardcoded constants. Any user who monitors the Zcash chain can time a withdrawal to be constructed at height `Nu6_1 - 1`. The PSBT then sits in `BTCPendingInfo` storage until the relayer calls `sign_btc_transaction`. Because the relayer is a separate actor and signing is not atomic with PSBT construction, there is a realistic window — especially if the relayer is slow, paused, or if the bridge is under load — for signing to occur after the upgrade. The attack requires no privileged access: `ft_on_transfer` is a public NEP-141 entry point.

---

### Recommendation

Re-derive `branch_id` from the current Zcash block height at signing time (inside `internal_sign_btc_transaction` or `get_hash_to_sign`) and assert it matches the stored value. If they differ, abort signing and require the operator to issue an RBF with the correct `branch_id`. Alternatively, always re-compute `branch_id` from the current height at signing time rather than trusting the stored value, since the stored value is only needed for serialization fidelity.

---

### Proof of Concept

1. At Zcash mainnet height 3,146,399, user calls `ft_on_transfer` → `ft_on_transfer_callback` → `PsbtWrapper::new` stores `branch_id = BranchId::Nu6` (byte `7`) in `psbt_hex`.
2. Zcash network activates Nu6_1 at height 3,146,400.
3. Relayer calls `sign_btc_transaction` → `internal_sign_btc_transaction` → `get_psbt()` deserializes byte `7` → `BranchId::Nu6`.
4. `get_hash_to_sign` computes sighash with `BranchId::Nu6`; MPC signs it.
5. `sign_btc_transaction_callback` stores the signed bytes and emits `SignedBtcTransaction`.
6. Relayer broadcasts the transaction; every Zcash node rejects it because `nConsensusBranchId` does not match the active Nu6_1 branch.
7. Bridge UTXOs remain locked; user's nZEC is stuck; operator must trigger RBF.
