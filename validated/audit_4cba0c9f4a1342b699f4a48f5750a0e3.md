Audit Report

## Title
`is_refund_required` Ignores Promise Failure for Plain `ft_transfer` and `mint`, Permanently Freezing Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call` is `false`, without inspecting the promise result. When `send_tokens` dispatches a plain `ft_transfer` (non-deployed token, empty `msg`) or a `mint` without a message (deployed token, empty `msg`), a failure in the underlying call causes `fin_transfer_send_tokens_callback` to silently take the success path: `locked_tokens` stays decremented, the nonce remains permanently in `finalised_transfers`, `FinTransferEvent` is emitted, and the relayer fee is paid — while the recipient receives nothing and no on-chain recovery path exists.

## Finding Description

In `process_fin_transfer_to_near`, two irreversible state mutations occur **before** `send_tokens` is called:

1. `add_fin_transfer` inserts the transfer nonce into `finalised_transfers` (L1875). This set has no admin removal function, so the nonce is permanently consumed.
2. `unlock_tokens_if_needed` decrements `locked_tokens` (L1881–1885). This represents the bridge's accounting of its obligations.

`send_tokens` then dispatches one of four calls. When `msg` is empty and the token is non-deployed, it calls `ft_transfer` (L2102–2106). When `msg` is empty and the token is deployed, it calls `mint` with `None` (L2094–2101). In both cases, `is_ft_transfer_call` is set to `!msg.is_empty()` = `false` at the call site (L1973).

The callback `fin_transfer_send_tokens_callback` calls `is_refund_required(false)` (L1702). The function short-circuits at L1800–1802 and returns `false` without reading the promise result at all:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

Because `is_refund_required` returns `false`, the else-branch at L1719–1746 fires unconditionally:
- `revert_lock_actions` is **not** called → `locked_tokens` stays decremented even though tokens were never delivered.
- `remove_fin_transfer` is **not** called → the nonce stays in `finalised_transfers` and cannot be replayed.
- `FinTransferEvent` is emitted and the relayer fee is paid as if the transfer succeeded.

The same blind spot exists in `resolve_utxo_fin_transfer` (L1024–1025) and `resolve_fast_transfer` (L906), which also call `is_refund_required(is_ft_transfer_call)` and take the same silent-success path when `msg` is empty.

Notably, the wNEAR unwrap path (`near_withdraw_callback`, L1047–1050) correctly checks the promise result and panics on failure — demonstrating that the pattern for safe failure handling is known and applied selectively, but omitted for plain `ft_transfer` and `mint`.

## Impact Explanation

**Non-deployed (locked) tokens** (e.g., NEAR-native USDC bridged to Ethereum and returning): The bridge holds the tokens in its own account. If `ft_transfer` fails, the tokens remain locked inside the bridge contract. `locked_tokens` is decremented (the bridge believes it has fewer obligations than it actually does), the nonce is consumed, and the user's funds are permanently frozen. This is direct balance mis-accounting and permanent fund freeze — matching the critical impact class of "permanent freezing of bridged funds" and "escrow mis-accounting."

**Deployed (minted) tokens**: If `mint` fails (e.g., token contract paused), no tokens are created on NEAR, but the source-chain lock/burn is already committed and the nonce is consumed. The user loses their bridged value permanently.

There is no admin rescue function to remove a consumed nonce from `finalised_transfers` or to force-deliver tokens to a stranded recipient. The `set_locked_tokens` DAO function can correct the accounting number, but cannot restore the consumed nonce or deliver the tokens.

## Likelihood Explanation

Any NEP-141 token whose `ft_transfer` or `mint` can revert under reachable conditions triggers this path. The entry point is the public `fin_transfer` function, callable by any relayer with a valid proof. Concrete realistic scenarios:

1. **Pausable tokens**: USDC, USDT, and many bridged stablecoins implement a pause mechanism. If the NEAR-side token is paused at the moment `fin_transfer` executes, `ft_transfer` reverts and funds are frozen. This is a non-bridge-admin action.
2. **Blocklist tokens**: Tokens that block specific addresses (including the bridge contract itself) cause `ft_transfer` to revert.
3. **Malicious token deployer**: The bridge accepts any NEP-141 token. A deployer can register a token whose `ft_transfer` reverts conditionally, then trigger `fin_transfer` to permanently consume the nonce and strand funds.

The condition is reachable by an unprivileged external actor (relayer submitting a valid proof) combined with a token-side state change (pause) that is entirely outside bridge-admin control.

## Recommendation

`is_refund_required` must inspect the promise result even when `is_ft_transfer_call` is `false`. A failed promise should be treated as requiring a revert:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                near_sdk::serde_json::from_slice::<U128>(&value)
                    .map_or(false, |amount| amount.0 == 0)
            }
            Err(_) => false,
        }
    } else {
        // For plain ft_transfer / mint: treat a failed promise as requiring refund
        env::promise_result_checked(0, 0).is_err()
    }
}
```

Additionally, `fin_transfer_send_tokens_callback` must call `remove_fin_transfer` and `revert_lock_actions` on any detected failure, mirroring the existing `ft_transfer_call` refund path. The same fix must be applied to `resolve_utxo_fin_transfer` and `resolve_fast_transfer`.

## Proof of Concept

1. NEAR-native USDC is locked on NEAR and bridged to Ethereum. `locked_tokens[(Eth, usdc)]` = 1000.
2. The USDC token contract on NEAR is paused by its administrator (a realistic, non-bridge-admin action).
3. A relayer submits a valid `fin_transfer` proof for a 1000 USDC return transfer from Ethereum to NEAR.
4. `process_fin_transfer_to_near` runs:
   - `add_fin_transfer` inserts the nonce into `finalised_transfers` (irreversible, L1875).
   - `unlock_tokens_if_needed` decrements `locked_tokens[(Eth, usdc)]` to 0 (L1881–1885).
   - `send_tokens` dispatches `ft_transfer(recipient, 1000)` — this **fails** because USDC is paused (L2102–2106).
5. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
6. `is_refund_required(false)` returns `false` without reading the promise result (L1800–1802).
7. The else-branch fires: `FinTransferEvent` is emitted, relayer fee is paid, no revert occurs (L1719–1746).
8. Final state: `locked_tokens[(Eth, usdc)] = 0` (wrong — bridge still holds 1000 USDC), nonce consumed, recipient balance unchanged. The 1000 USDC are permanently frozen inside the bridge contract with no on-chain recovery mechanism.

A unit test can be written using NEAR SDK test utilities: mock a token contract whose `ft_transfer` panics, call `fin_transfer` with a valid proof, and assert that after the callback `locked_tokens` is still decremented and `finalised_transfers` contains the nonce while the recipient balance is zero.
