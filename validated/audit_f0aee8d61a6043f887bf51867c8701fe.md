### Title
Peras Vote and Certificate Signature Validation Completely Bypassed in Degenerate `BlockSupportsPeras` Instance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance used for all block types performs no cryptographic signature verification for Peras votes or certificates. `validatePerasVote` only checks stake distribution membership, and `validatePerasCert` unconditionally returns `Right`. An unprivileged peer can send crafted votes for any block target via the ObjectDiffusion mini-protocol; these votes are accepted, accumulated, and can trigger forged Peras certificates that manipulate chain selection through the Peras boosting mechanism.

---

### Finding Description

The `BlockSupportsPeras` type class defines the interface for Peras vote and certificate validation. A degenerate catch-all instance is provided for all `StandardHash blk` types, explicitly marked as a temporary scaffold:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

Within this instance, the `PerasVote blk` data type carries **no signature field** — only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId`:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

The `validatePerasVote` implementation only checks whether the voter ID appears in the stake distribution. No signature is present, and none is verified:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

`validatePerasCert` is even weaker — it unconditionally returns `Right` for every certificate, performing zero validation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

This degenerate instance is the one actually invoked in the production inbound vote processing path. `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` both call `validatePerasVote mkPerasParams sd vote` directly:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

The `processVotes` function, which is the entry point for all inbound peer votes, feeds directly into this validation: [6](#0-5) 

Note that the concrete `V1.PerasVote` type (used in the WFALS/EveryoneVotes committee implementations) does carry a `pvSignature` field and its corresponding `implVerifyVote` does perform BLS signature verification. However, the `BlockSupportsPeras` instance used in the production node pipeline is the degenerate one above, not the committee-layer implementation. [7](#0-6) 

---

### Impact Explanation

**Critical. Bypass of Peras voting and certificate checks enabling unauthorized vote and certificate acceptance.**

An attacker who knows any valid `PerasVoterId` present in the current stake distribution can craft a `PerasVote` for any block of their choosing. Because `validatePerasVote` only checks stake distribution membership and performs no signature verification, the vote passes validation and is stored in the `PerasVoteDB`. Once enough such crafted votes accumulate to reach quorum (which `votesReachQuorum` checks purely by summing stake), `forgePerasCert` is triggered — and that too is a stub that always returns `Right` — producing a `ValidatedPerasCert` that boosts the attacker-chosen block in chain selection. This allows an unprivileged peer to steer an honest node's chain selection toward an attacker-controlled fork, constituting a consensus safety failure.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras votes is a publicly reachable network endpoint. Any connected peer can submit crafted `PerasVote` messages. The only prerequisite is knowledge of a `PerasVoterId` (a stake pool key hash) present in the current stake distribution, which is public ledger state. No key material, operator access, or stake majority is required. The degenerate instance is the active code path for all block types until a proper instance is wired in.

---

### Recommendation

1. Remove or gate the degenerate `instance StandardHash blk => BlockSupportsPeras blk` so it cannot be resolved for production block types. Replace it with a proper instance that wires the WFALS/EveryoneVotes committee verification logic (`implVerifyVote`, `implVerifyCert`) into `validatePerasVote` and `validatePerasCert`.
2. Add a signature field to the stub `PerasVote blk` data type, or ensure the production instance uses `V1.PerasVote` with its `pvSignature` field.
3. Ensure `validatePerasCert` verifies the aggregate BLS signature over the declared voters and candidate block before returning `Right`.
4. Track resolution under the referenced issue (https://github.com/tweag/cardano-peras/issues/120) and block deployment of the Peras diffusion path until validation is complete.

---

### Proof of Concept

On a private testnet with the Peras ObjectDiffusion protocol enabled, an attacker peer can:

1. Read the current `PerasVoteStakeDistr` from the public ledger state to obtain valid `PerasVoterId` values.
2. Construct `PerasVote` objects targeting an attacker-chosen block, using any known voter IDs, with arbitrary (or absent) signature fields.
3. Submit these votes via the ObjectDiffusion inbound handler. `processVotes` calls `validatePerasVote mkPerasParams sd vote`; since the degenerate instance only checks `lookupPerasVoteStake`, all votes pass.
4. Once the accumulated `vpvVoteStake` of accepted votes exceeds the quorum threshold in `votesReachQuorum`, `forgePerasCert` is called — the stub always returns `Right` — producing a `ValidatedPerasCert` boosting the attacker's chosen block.
5. The `ValidatedPerasCert` is stored and applied to chain selection, causing the honest node to prefer the attacker-designated chain over the canonical one.

The root cause is structurally identical to the Beranames finding: critical fields of the validation struct (the vote signature) are omitted from the validation check, allowing any peer to submit structurally valid-looking objects that bypass authorization.
