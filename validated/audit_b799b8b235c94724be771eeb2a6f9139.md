### Title
Premature Token Minting Before Storage-Registration Check in `safe_mint` Causes Irrecoverable Supply Inflation — (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC token contract unconditionally mints tokens into the bridge's own account (`bridge_id`) **before** checking whether the intended recipient has a registered storage slot. When the recipient is unregistered the function returns `U128(0)` without burning the already-minted tokens, permanently inflating the nBTC total supply and leaving the minted amount stranded in `bridge_id` with no in-contract recovery path.

### Finding Description

`safe_mint` is the minting entry-point used by the safe-deposit flow (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`). Its body is:

```rust
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(&mut self, account_id: AccountId, amount: U128, msg: Option<String>)
    -> PromiseOrValue<U128>
{
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");
    self.token.internal_deposit(&self.bridge_id, amount.into());   // ← supply inflated HERE

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                     // ← early return, no burn
    }
    // … transfer to account_id …
}
```

`internal_deposit` atomically increases both `bridge_id`'s balance and the global `total_supply`. The registration check comes **after** that mutation. If the check fails the function returns the sentinel value `U128(0)` — it does **not** call `internal_withdraw` or any burn to undo the deposit. The nBTC contract's state is now permanently inconsistent: total supply is higher than the sum of all user balances.

The contrast with the normal `mint` path is instructive: `mint_inner` auto-registers any account before depositing, so it never leaves orphaned supply. `safe_mint` deliberately skips auto-registration (to honour the "revert on failure" contract), but it performs the deposit first, making the revert impossible within the same call.

Because `safe_mint` does not panic — it returns `U128(0)` — the satoshi-bridge callback that receives this value cannot roll back the nBTC state change; cross-contract state changes in NEAR are not automatically reverted when a downstream call returns a non-panic value. The bridge callback would need to issue an explicit `burn` XCC to undo the inflation, but no such compensating call is visible in the token contract itself.

### Impact Explanation

- **nBTC total supply is permanently inflated** by the deposited amount. The minted tokens sit in `bridge_id`'s balance, not backed by any user's BTC deposit that was successfully credited.
- The user who triggered the safe-deposit receives zero nBTC despite their BTC being locked on-chain.
- If the bridge callback does not mark the UTXO as unverified, the user's BTC is also permanently unrecoverable (the UTXO would be marked verified, blocking a retry).
- Even if the UTXO is left unverified, the orphaned supply in `bridge_id` persists until a privileged operator manually calls `burn`, which is not a documented recovery procedure.

This matches the **Medium** impact class: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

### Likelihood Explanation

The safe-deposit path is the integration path for Omni Bridge and similar protocols. Any user whose NEAR account has not yet called `storage_deposit` on the nBTC contract before initiating a safe-deposit will trigger this path. This is a realistic operational scenario (e.g., a first-time user bridging BTC via Omni Bridge before their nBTC storage slot is funded). Likelihood is **Low-Medium**.

### Recommendation

Move `internal_deposit` to **after** the registration check, or replace it with a pattern that only mints once delivery is confirmed:

```rust
pub fn safe_mint(&mut self, account_id: AccountId, amount: U128, msg: Option<String>)
    -> PromiseOrValue<U128>
{
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // … transfer to account_id …
}
```

This ensures that if the recipient is unregistered, no supply is created and the bridge callback can cleanly treat the call as a no-op without needing a compensating burn.

### Proof of Concept

1. Alice sends BTC to her deposit address using the safe-deposit flow (`deposit_msg.safe_deposit = Some(..)`).
2. Alice has never called `storage_deposit` on the nBTC contract, so `self.token.accounts.get(&alice)` returns `None`.
3. The relayer calls `verify_deposit_v2`; the bridge eventually calls `safe_mint(alice, amount, msg)` on the nBTC contract.
4. `internal_deposit(&bridge_id, amount)` executes — nBTC `total_supply` increases by `amount`, `bridge_id` balance increases by `amount`.
5. The registration check fires: `alice` is unregistered → function returns `U128(0)`.
6. No burn is issued. The nBTC contract's `total_supply` is now `amount` higher than the sum of all registered user balances.
7. The bridge callback receives `U128(0)`. It cannot roll back the nBTC state change. Alice receives 0 nBTC; the `amount` of nBTC is stranded in `bridge_id` indefinitely. [1](#0-0) [2](#0-1) [3](#0-2)
