### Title
Attacker Can Front-Run `request_refund` With Arbitrary `refund_address` to Steal Victim's BTC - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`request_refund` is a publicly callable function that accepts an arbitrary `deposit_msg` (including any `recipient_id`) and, when `deposit_msg.refund_address` is `None`, also accepts a caller-supplied `refund_address`. An attacker who observes a victim's unfinalized deposit can call `request_refund` first with the victim's `deposit_msg` but the attacker's own `refund_address`. This creates a refund request keyed to the victim's UTXO that routes BTC to the attacker. The victim's own subsequent `request_refund` call is then blocked by the duplicate-key guard. After the `unsafe_refund_timelock_sec` window (default 14 days), the attacker can call `execute_refund` and receive the victim's BTC — unless the DAO/Operator actively monitors and rejects the request in time.

### Finding Description

`request_refund` has no check that the caller is the `deposit_msg.recipient_id` or any party authorized by the depositor: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` this guard is skipped entirely, so the caller may supply any BTC address as `refund_address`. The resulting `RefundRequest` is stored keyed by `utxo_storage_key` (`{tx_id}@{vout}`): [3](#0-2) 

A subsequent call for the same UTXO is rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

The `refund_address` stored in the request is what `execute_refund` → `finalize_refund_with_psbt` uses to build the Bitcoin output — it is never re-validated against the original depositor: [5](#0-4) 

The only time-based mitigation is `unsafe_refund_timelock_sec` (default **14 days**), which is longer than the normal `refund_timelock_sec` (default 2 days) specifically to give the DAO/Operator time to reject suspicious requests: [6](#0-5) [7](#0-6) 

This is an operational safeguard, not a code-level fix. If the DAO/Operator is inattentive, overwhelmed, or the key is unavailable, the attacker executes the refund after the timelock and receives the victim's BTC.

### Impact Explanation

**Primary (guaranteed):** The victim's UTXO slot is occupied by the attacker's refund request. The victim cannot submit their own `request_refund` for the same UTXO. Their BTC is temporarily locked — they cannot recover it through the refund path without DAO/Operator intervention (`reject_refund`).

**Secondary (conditional on DAO/Operator inaction):** After `unsafe_refund_timelock_sec`, the attacker calls `execute_refund`, which builds a Bitcoin transaction paying the attacker's `refund_address`. The victim's BTC is permanently stolen.

This matches **Medium** (attacker-triggered temporary locking of bridged funds) with escalation to **Critical** (significant loss of user funds) if the operator window is missed.

### Likelihood Explanation

All inputs the attacker needs are publicly observable:
- `deposit_msg` is emitted on-chain by `get_user_deposit_address` via `Event::LogDepositAddress`.
- The BTC transaction bytes and vout are on the Bitcoin blockchain.
- A Merkle proof can be constructed by any Bitcoin node operator.

The attacker pays only the NEAR storage deposit (`required_balance_for_request_refund`). There is no other barrier. The attack is viable against any deposit whose `deposit_msg.refund_address` is `None` and that has not yet been finalized by `verify_deposit`.

### Recommendation

Require that the caller of `request_refund` is either the `deposit_msg.recipient_id` or that `deposit_msg.refund_address` is pre-set (non-`None`). When `deposit_msg.refund_address` is `None`, disallow third-party submission entirely, or bind the `refund_address` to the caller and require the caller to be the `recipient_id`:

```rust
// Option A: require caller == recipient_id when no pre-authorized refund address
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only recipient can request refund without a pre-authorized refund_address"
    );
}
```

Alternatively, mandate that `deposit_msg.refund_address` is always set at deposit-address-generation time, removing the `None` path entirely.

### Proof of Concept

1. Alice generates a deposit address with `deposit_msg.refund_address = None`. The `deposit_msg` and deposit address are emitted as a NEAR event.
2. Alice sends 1 BTC to the deposit address. The relayer never calls `verify_deposit` (relayer is down).
3. Attacker observes Alice's `deposit_msg` from NEAR events and the BTC transaction from the Bitcoin blockchain.
4. Attacker calls `request_refund(alice_deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)` with sufficient NEAR attached deposit.
5. `request_refund_callback` verifies the Merkle proof, confirms the script_pubkey matches Alice's deposit address, and stores `RefundRequest { refund_address: attacker_btc_address, created_at_sec: now, ... }` keyed by Alice's UTXO.
6. Alice calls `request_refund(alice_deposit_msg, alice_btc_address, ...)` — panics with `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` (14 days), attacker calls `execute_refund(utxo_storage_key, None)`.
8. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `attacker_btc_address` and submits it for MPC signing.
9. Alice's 1 BTC is sent to the attacker.
