### Title
Stub `validatePerasCert` Always Accepts Any Peer-Injected Certificate, Enabling Unauthorized `latestCertSeen` Manipulation and Chain Selection Deviation via Peras Weight Boost — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate, regardless of round number, boosted block, or any cryptographic content. An unprivileged peer can exploit the object-diffusion protocol to inject a crafted `PerasCert` with an arbitrarily large `pcCertRound`. Because the certificate passes validation, it is stored in `PerasCertDB` and monotonically advances `pcdsLatestCertSeen` to the injected round. This permanently blocks the victim node from satisfying Peras voting rules VR-1A and VR-2A, and simultaneously triggers `chainSelectionForBlock` for the attacker-chosen boosted block, potentially causing the node to prefer a non-canonical fork.

---

### Finding Description

**Root cause — stub validation always succeeds**

The default `BlockSupportsPeras` instance, used for all block types, contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is not test code — it is the production instance in the `src/` tree, and it is the instance invoked by the object-diffusion inbound path.

**Attacker-controlled entry path — `processCerts`**

Inbound certificates from any peer flow through `processCerts` in the object-diffusion layer:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` filters out already-known round numbers, then calls `validatePerasCert` on the remainder. Because the stub always returns `Right`, every novel certificate from any peer is accepted and forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

**State mutation 1 — monotonic `latestCertSeen` poisoning**

`implAddCert` updates `pcdsLatestCertSeen` monotonically by round number:

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [4](#0-3) 

An attacker who injects a certificate with `pcCertRound = maxBound` permanently sets `latestCertSeen` to that round. The `PerasCertDB` API documents this field as: *"This field impacts voting directly because having seen a certificate is a precondition for voting in any round except for the very first one."* [5](#0-4) 

**State mutation 2 — chain selection triggered for attacker-chosen block**

`chainSelSync` for a `ChainSelAddPerasCert` event calls `chainSelectionForBlock` for the boosted block whenever that block is in the VolatileDB but not on the current chain:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [6](#0-5) 

The injected certificate carries `vpcCertBoost = perasWeight params`, a non-zero weight boost. If the attacker's chosen block is on a fork that is slightly shorter than the current chain, the Peras weight boost can tip chain selection in favour of that fork.

**Voting rules blocked by poisoned `latestCertSeen`**

VR-1A requires `currRoundNo == latestCertSeenRound + 1`:

```haskell
vr1a1 =
  case latestCertSeen of
    NotOrigin cert ->
      currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
``` [7](#0-6) 

VR-2A requires `latestCertSeenRound + R ≤ currRoundNo`. With `latestCertSeen` set to `maxBound`, neither VR-1A nor VR-2A can ever be satisfied again, permanently suppressing the node's Peras vote production.

---

### Impact Explanation

**Chain selection deviation (High):** An unprivileged peer injects a certificate boosting a block on a competing fork. Because `validatePerasCert` is a stub, the certificate is accepted, assigned the full `perasWeight` boost, and chain selection is re-run for the boosted block. If the fork is within the Peras weight margin of the current chain, the node switches to the attacker-chosen fork — a non-canonical chain — without any stake or cryptographic backing from the attacker. This matches the allowed scope: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

**Peras certificate validation bypass (Critical):** Any peer can inject a certificate for any round, any block, with no signature, no stake proof, and no committee membership check. This is a complete bypass of Peras certificate checks, matching: *"Critical. Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."*

**Voting suppression (secondary):** Injecting a far-future round certificate permanently poisons `latestCertSeen`, blocking VR-1A and VR-2A and preventing the node from ever casting a Peras vote again without a restart and DB wipe.

---

### Likelihood Explanation

Any node that has enabled the Peras object-diffusion protocol (i.e., any node running the code with Peras diffusion active) is reachable by any peer. No stake, no keys, and no privileged access are required. The attacker only needs to establish a peer connection and send a single well-formed `PerasCert` CBOR message with an arbitrary round number and an arbitrary block point. The stub validation guarantees acceptance.

---

### Recommendation

1. **Remove the stub and enforce real validation before merging Peras into any production-facing build.** `validatePerasCert` must verify the certificate's cryptographic proof of quorum (committee signatures/VRF proofs), the round number is within the current or recent window, and the boosted block is on a known chain.
2. **Gate `latestCertSeen` updates on round-number plausibility.** Reject certificates whose `pcCertRound` exceeds `currentRound + maxFutureRounds` to prevent monotonic poisoning.
3. **Restrict `processCerts` to only accept certificates whose `pcCertRound` is within the active voting window**, analogous to how `depositFor` was fixed to only allow the owner to update the lock duration.
4. **Do not expose the Peras object-diffusion inbound path in production builds until full validation is in place.** The current TODO at issue #120 and the "degenerate instance" note at issue #73 confirm this is known incomplete work; the risk is that the stub is reachable from the network before those issues are resolved.

### Proof of Concept

**Attacker preconditions:** peer connection to a Cardano node with Peras object diffusion enabled; no stake, no keys.

**Step 1 — Craft a certificate with a far-future round and an adversarial block point:**
```
PerasCert { pcCertRound = 0xFFFFFFFFFFFFFFFF
           , pcCertBoostedBlock = <point of a block on a competing fork in victim's VolatileDB> }
```

**Step 2 — Send via the Peras certificate object-diffusion mini-protocol.**

**Step 3 — `processCerts` calls `validatePerasCert mkPerasParams cert`**, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally. [8](#0-7) 

**Step 4 — `implAddCert` stores the certificate and sets `pcdsLatestCertSeen = cert` (round `maxBound`).** [9](#0-8) 

**Step 5 — `chainSelSync` calls `chainSelectionForBlock` for the boosted block.** If the fork carrying that block is within `perasWeight` of the current chain, the node switches forks. [10](#0-9) 

**Step 6 — All subsequent voting checks read `latestCertSeen = maxBound`.** VR-1A (`currRoundNo == maxBound + 1`) and VR-2A (`maxBound + R ≤ currRoundNo`) are permanently unsatisfiable. The node never casts another Peras vote. [11](#0-10)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

```haskell
-- | VR-1A: the voter has seen the certificate for the previous round, and the
-- certificate was received in the first X slots after the start of the round.
perasVR1A ::
  HasPerasCertRound cert =>
  PerasVotingView cert ->
  Pred PerasVotingRule
perasVR1A
  PerasVotingView
    { perasParams
    , currRoundNo
    , latestCertSeen
    } =
    VR1A := vr1a1 :/\: vr1a2
   where
    -- The latest certificate seen is from the previous round
    vr1a1 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its round number
        NotOrigin cert ->
          currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
        -- We have never seen a certificate ==> check if we are voting in round 0
        Origin ->
          currRoundNo :==: PerasRoundNo 0

    -- The latest certificate seen was received within X slots from the start
    -- of its round
    vr1a2 =
      case latestCertSeen of
        -- We have seen a certificate ==> check its arrival time
        NotOrigin cert ->
          lcsArrivalSlot cert :<=: lcsRoundStartSlot cert + _X
        -- We have never seen a certificate ==> vacuously true
        Origin ->
          Bool True

    _X =
      SlotNo $
        unPerasCertArrivalThreshold $
          perasCertArrivalThreshold perasParams
