### Title
`revalidateHeader` silently accepts invalid header envelopes in production builds — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` guards its entire envelope validity check with `assertWithMsg`, which is a **compile-time no-op** when the `asserts` Cabal flag is absent — the default in production builds. In production, the check that verifies block number, slot number, previous hash, and checkpoint is computed but its result is unconditionally discarded. If `revalidateHeader` is called with a header that fails the envelope check (e.g., during LedgerDB replay of a crafted or corrupted ImmutableDB), the failure is silently swallowed and a `HeaderState` with the wrong `AnnTip` is returned. This is the direct structural analog of using `return` instead of `revert` on failure: execution continues and state changes persist.

---

### Finding Description

**`assertWithMsg` is a no-op in production.** [1](#0-0) 

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

`ENABLE_ASSERTIONS` is only defined when the `asserts` Cabal flag is set via `cpp-options: -DENABLE_ASSERTIONS`. [2](#0-1) 

The default `cabal.project` does **not** include `cabal/asserts.cabal`, so the flag is absent in standard production builds. [3](#0-2) 

**`revalidateHeader` relies entirely on `assertWithMsg` for its envelope check.** [4](#0-3) 

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← no-op in production
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' = reupdateChainDepState ...   -- skips VRF/KES checks
  envelopeCheck  = runExcept $ withExcept show $
    validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

In production, `envelopeCheck` is evaluated but its `Left` branch is never acted upon. The function unconditionally returns `HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'` — a `HeaderState` built from the incoming header regardless of whether the block number, slot, previous hash, or checkpoint is valid.

**`revalidateHeader` is called on every block replayed from the ImmutableDB at node startup.** [5](#0-4) 

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
  where
    ledgerResult = reapplyBlockLedgerResult evs (configLedger $ getExtLedgerCfg cfg) blk tickedLedgerState
    hdr          = revalidateHeader (getExtLedgerCfg cfg) ledgerView (getHeader blk) tickedHeaderState
```

`reapplyBlockLedgerResult` is the `initReapplyBlock` callback used by `replayStartingWith` during LedgerDB initialisation: [6](#0-5) 

Every block streamed from the ImmutableDB passes through `revalidateHeader` with assertions disabled.

---

### Impact Explanation

An attacker who can supply a crafted ImmutableDB (a "DB/snapshot input in a local reproduction") containing a block whose header has an invalid envelope — wrong block number, non-monotone slot, broken hash chain, or checkpoint mismatch — will cause `revalidateHeader` to silently return a `HeaderState` embedding the wrong `AnnTip`. This corrupted `ExtLedgerState` becomes the durable starting point for all subsequent chain selection. Downstream calls to `validateHeader` (which do propagate errors) will then operate against a mismatched base state, causing the node to permanently reject valid successor blocks or accept an attacker-controlled fork, constituting durable use of the wrong ledger state without operator fault.

Additionally, `reupdateChainDepState` (which skips VRF/KES verification) is called unconditionally with the crafted header's `ValidateView`. For Praos, this updates `praosStateEvolvingNonce` and `praosStateCandidateNonce` with the attacker-controlled VRF output, poisoning the epoch nonce used for all future leader-eligibility checks. [7](#0-6) 

---

### Likelihood Explanation

The ImmutableDB stores blocks with CRC checksums, so random bit-flip corruption is caught. However, an attacker who replaces an entire block file with a crafted block (computing a fresh, valid CRC for the new content) bypasses the checksum entirely. The ImmutableDB does not authenticate block provenance beyond the CRC. On the next node startup, `replayStartingWith` streams the crafted block, `reapplyBlockLedgerResult` calls `revalidateHeader`, and the envelope failure is silently discarded. No operator action is required to trigger the corrupted replay; the node simply restarts normally.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with a proper error-propagating return type, mirroring `validateHeader`:

```haskell
-- Before (production no-op):
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'

-- After (always enforced):
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left err -> error ("revalidateHeader: envelope invariant violated: " <> err)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

Or, preferably, change the return type to `Either (HeaderEnvelopeError blk) (HeaderState blk)` and propagate the error to callers, forcing `reapplyBlockLedgerResult` to handle the failure explicitly rather than silently continuing.

---

### Proof of Concept

1. Sync a node until several blocks are flushed to the ImmutableDB.
2. Stop the node.
3. Locate a chunk file in the ImmutableDB directory. Replace one stored block's header bytes so that `blockNo` is incremented by 2 (skipping a block number), then recompute the CRC for the modified entry so the ImmutableDB checksum passes.
4. Restart the node (production build, no `asserts` flag).
5. `replayStartingWith` streams the crafted block; `reapplyBlockLedgerResult` calls `revalidateHeader`; `envelopeCheck` returns `Left "UnexpectedBlockNo ..."` but `assertWithMsg` discards it; the node stores an `ExtLedgerState` whose `headerState` has `annTipBlockNo` advanced by 2 instead of 1.
6. All subsequent `validateHeader` calls for the next honest block will fail with `UnexpectedBlockNo` (expected N+1, got N+1 against a base of N+2), permanently stalling the node's chain selection without any operator-visible error at the replay stage. [8](#0-7) [1](#0-0)
