### Title
Unprivileged Third-Party Can Hijack `execute_refund` Ownership, Temporarily Locking Depositor's Refund UTXO — (`contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`, `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`execute_refund` has no caller-ownership guard. Any unprivileged account (Bob) can call it for Alice's refund request. The resulting `BTCPendingInfo` is stamped with Bob's `account_id`, consuming Bob's pending-sign slot. Because the `btc_pending_id` is deterministic (derived from the fixed PSBT content), Alice's subsequent `execute_refund` calls panic with `"pending info already exist"`, and she cannot remove Bob's stale entry without operator intervention.

---

### Finding Description

**Entrypoint — `execute_refund` is open to any caller.**

`execute_refund` in `api/bridge.rs` carries only `#[payable]` and `#[pause]`; it has no `#[trusted_relayer]` attribute on the function itself and no ownership check: [1](#0-0) 

`resolve_execute_refund_timelock` explicitly handles the non-privileged case by applying a longer timelock — confirming the function is intentionally open to any caller — but never restricts who may proceed: [2](#0-1) 

**Caller becomes owner of `BTCPendingInfo`.**

`internal_execute_refund` captures `env::predecessor_account_id()` as `caller` and passes it directly to `finalize_refund_with_psbt`: [3](#0-2) 

`finalize_refund_with_psbt` stamps the `BTCPendingInfo` with that caller and inserts the `btc_pending_id` into the caller's `btc_pending_sign_ids`: [4](#0-3) 

**Alice is blocked from re-executing.**

The `btc_pending_id` is derived from the PSBT content (deterministic: same deposit UTXO outpoint + same refund output to Alice's fixed `refund_address`). If Bob's `BTCPendingInfo` already occupies that key, Alice's `execute_refund` panics: [5](#0-4) 

**Alice cannot remove Bob's pending info.**

`remove_refund_pending_tx_id` is `#[trusted_relayer]`-gated (Alice cannot call it), and additionally requires the refund request to be absent — but the request remains active (`executed = true`) until finalized: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

Alice's refund UTXO is temporarily locked. She cannot re-execute her own refund while Bob's `BTCPendingInfo` occupies the deterministic `btc_pending_id`. Resolution requires the DAO/Operator to call `reject_refund` (removing the request), followed by a trusted relayer calling `remove_refund_pending_tx_id` to clear Bob's stale entry, after which Alice must re-submit a new `request_refund` (paying the storage deposit again). This matches **Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention**.

Note: Alice's BTC is not redirected — the `refund_address` is fixed in the `RefundRequest` at submission time — but her ability to manage her own refund lifecycle is broken until operators intervene.

---

### Likelihood Explanation

The attack requires only attaching the storage deposit and knowing the `utxo_storage_key` (publicly observable from `RefundRequested` events). No privileged role, leaked key, or external dependency is needed. Any NEAR account can execute it after the timelock elapses.

---

### Recommendation

Add a caller-ownership check in `execute_refund` or `resolve_execute_refund_timelock`. The simplest fix: require `env::predecessor_account_id()` to match the original depositor (stored in the `RefundRequest`, e.g. via a `requester_id` field added at `request_refund` time), or restrict `execute_refund` to the depositor, DAO, and `RefundOperator`. Alternatively, if permissionless execution is desired, pass the `RefundRequest`'s stored depositor as the `BTCPendingInfo` owner instead of `env::predecessor_account_id()`.

---

### Proof of Concept

```
State setup:
  Alice calls request_refund(deposit_msg, refund_address, tx_bytes, vout, proof)
  → RefundRequest stored at utxo_storage_key; RefundRequested event emitted

Attack:
  Bob (unprivileged) calls execute_refund(utxo_storage_key, None)
  after unsafe_refund_timelock_sec has elapsed, attaching required_balance_for_execute_refund()

Assert:
  btc_pending_infos[btc_pending_id].account_id == Bob   ✓
  Bob.btc_pending_sign_ids contains btc_pending_id       ✓

Alice attempts re-execution:
  Alice calls execute_refund(utxo_storage_key, None)
  → finalize_refund_with_psbt tries insert with same btc_pending_id
  → panics: "pending info already exist"                 ✓

Alice attempts cleanup:
  Alice calls remove_refund_pending_tx_id(btc_pending_id)
  → rejected: #[trusted_relayer] gate                    ✓
  (even a trusted relayer would fail: refund request still active)

Resolution requires:
  DAO calls reject_refund(utxo_storage_key)
  trusted relayer calls remove_refund_pending_tx_id(btc_pending_id)
  Alice re-submits request_refund (paying storage deposit again)
```

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
