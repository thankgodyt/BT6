Audit Report

## Title
Non-Atomic `burn.and(mint)` with No Failure Callback in `swap_migrated_token` Causes Permanent Loss or Unauthorized Minting of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` dispatches `burn` and `mint` as two independent parallel NEAR receipts via `Promise::and()`, then `.detach()`es the combined promise with no failure callback. Because `ft_on_transfer` simultaneously returns `U128(0)`, the NEP-141 protocol will never refund the sender's old tokens. Any failure of either receipt leaves the token supply in an irrecoverably inconsistent state: a failed `mint` after a successful `burn` permanently destroys user funds; a failed `burn` after a successful `mint` creates unauthorized new tokens.

## Finding Description
In `ft_on_transfer`, the `SwapMigratedToken` branch calls:

```rust
self.swap_migrated_token(sender_id, token_id, amount)
    .detach();
PromiseOrPromiseIndexOrValue::Value(U128(0))
```

`swap_migrated_token` constructs:

```rust
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
```

`Promise::and()` schedules both calls as independent action receipts. NEAR's receipt execution model does not roll back one receipt if the other fails — they execute in separate shards/blocks with no atomicity guarantee. Neither call uses `.with_static_gas()` despite the constants `BURN_TOKEN_GAS` and `MINT_TOKEN_GAS` being defined elsewhere in the file, so gas allocation is inherited from the parent call and can be insufficient. The `.detach()` removes any callback that could observe failure. Returning `U128(0)` from `ft_on_transfer` tells the NEP-141 `ft_transfer_call` mechanism that zero tokens should be refunded — the old tokens are irrevocably held by the bridge from this point forward.

Existing checks are insufficient: the `#[pause]` guard on `ft_on_transfer` only blocks the entire function when paused; it does not protect against the non-atomicity within the `SwapMigratedToken` branch. There is no `#[private]` callback anywhere in the contract for this flow.

## Impact Explanation
- **Permanent loss of bridged funds (Critical):** If `mint` fails (e.g., bridge not storage-registered on the new token contract, gas exhaustion, or a panic in the new token's `mint` implementation), `burn` has already executed and the user's old tokens are permanently destroyed with zero new tokens issued. This is an irreversible, direct loss of bridged user funds.
- **Unauthorized minting (Critical):** If `burn` fails while `mint` succeeds, the user receives new tokens without surrendering old ones, inflating the new token supply and breaking the 1:1 migration invariant. Both outcomes fall within the Critical allowed impact scope.

## Likelihood Explanation
The trigger path (`old_token.ft_transfer_call(bridge, amount, "SwapMigratedToken")`) requires no privilege — any token holder of a migrated token can invoke it. The most realistic failure condition is a missing storage deposit: NEP-141 tokens require `storage_deposit` before an account can hold a balance; if the bridge has not pre-registered on the new token contract, `mint` panics immediately with a storage error. This is a common operational gap during migrations. Gas exhaustion is a secondary realistic vector since no explicit gas is attached to either call.

## Recommendation
Replace the parallel pattern with a sequential, callback-guarded chain:

1. Call `burn` first with `.with_static_gas(BURN_TOKEN_GAS)`.
2. In a `#[private]` callback, check `PromiseResult` — if `burn` succeeded, call `mint` with `.with_static_gas(MINT_TOKEN_GAS)`.
3. In a second `#[private]` callback, check `PromiseResult` — if `mint` failed, re-mint the old tokens back to the user or store a claimable refund record.
4. Do not `.detach()` the promise chain; keep it attached so the NEP-141 return value can be used as a last-resort refund signal if needed.

Additionally, ensure the bridge contract calls `storage_deposit` on the new token contract before any migration is activated.

## Proof of Concept
1. Admin registers migration: `migrated_tokens[old_token] = new_token`.
2. Bridge has **not** called `storage_deposit` on `new_token` for itself.
3. User calls `old_token.ft_transfer_call(bridge_account, amount, "\"SwapMigratedToken\"")`.
4. `ft_on_transfer` returns `U128(0)` — old tokens are irrevocably consumed by the bridge.
5. `swap_migrated_token` dispatches `burn.and(mint).detach()`.
6. `burn` receipt executes successfully: bridge's `old_token` balance is destroyed.
7. `mint` receipt executes: `new_token` panics with "ERR_ACCOUNT_NOT_REGISTERED" (no storage deposit).
8. No callback exists; no refund path exists.
9. User has lost `amount` of `old_token` and received 0 `new_token`. Funds are permanently destroyed.

To reproduce locally: deploy two NEP-141 token contracts (`old_token`, `new_token`), deploy the bridge, register the migration, skip `storage_deposit` on `new_token`, invoke `ft_transfer_call` with `SwapMigratedToken`, and observe that `burn` succeeds while `mint` panics, with no recovery.
