### Title
u128 overflow panic in `check_deposit_msg` total_amount accumulation permanently blocks deposit finalization — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
An unprivileged depositor can craft a `DepositMsg` with two `post_actions` each carrying `amount = u128::MAX/2 + 1`. Because `overflow-checks = true` is set in the workspace release profile, the plain `total_amount += post_action.amount.0` on the second loop iteration panics, aborting `verify_deposit` before any UTXO state is written. The deposit UTXO becomes permanently unprocessable on-chain.

### Finding Description
In `check_deposit_msg` (`deposit_msg.rs`, line 85), `total_amount` is accumulated with unchecked `+=`. The workspace `Cargo.toml` sets `overflow-checks = true` for the release profile, so this compiles to a checked addition that traps on overflow in the WASM runtime. With two post_actions each having `amount = u128::MAX/2 + 1`, the sum on the second iteration equals `u128::MAX + 1`, triggering a panic. This function is called synchronously in `internal_verify_deposit` (line 58 of `deposit.rs`) before the light-client promise is chained. A panic here reverts the entire call, leaving no UTXO record. Every subsequent relay attempt with the same DepositMsg panics identically.

### Impact Explanation
The depositor's BTC is permanently locked at the deposit address. The bridge has no record of the UTXO (since the panic reverts all state writes), so no normal refund path through the bridge can be triggered. The relayer wastes gas on every retry. This is a stuck-state/panic-driven fault with no direct theft — fitting the **Low** severity band: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
Requires: (1) at least one whitelisted `receiver_id` in `post_action_receiver_id_white_list` (expected in any production deployment with DeFi integrations), (2) the first post_action's `msg` to pass the template check (attacker can use an empty string if no template is configured, or a valid template value if one is). The depositor fully controls the DepositMsg and the relayer is forced to submit it verbatim. Likelihood is **medium** once the whitelist is populated.

### Recommendation
Replace the unchecked addition with a checked or saturating variant:

```rust
total_amount = total_amount
    .checked_add(post_action.amount.0)
    .unwrap_or(u128::MAX); // saturate; the > actual_mintable_amount check below will reject it
```

Or use `saturating_add`. Either way, the existing guard at line 181 (`if total_amount > actual_mintable_amount`) will then correctly reject the oversized total without panicking.
