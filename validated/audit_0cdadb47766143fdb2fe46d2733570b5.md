### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Causes Stale Chain-Selection Disconnect Decision When Peras Is Active — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer's header is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to disconnect from that peer. This function compares the peer's candidate fragment against the local selection using `preferAnchoredCandidate`, but it **always passes `emptyPerasWeightSnapshot`** (zero weights) instead of the live `PerasWeightSnapshot` from the `PerasCertDB`. When Peras is enabled and certificates have been issued, this stale/empty snapshot causes the comparison to ignore all Peras weight boosts, producing an incorrect chain-preference decision. The result is that the node may disconnect from peers offering the canonical (shorter-but-heavier) chain and remain connected to peers offering a non-canonical (longer-but-lighter) chain, ultimately adopting the wrong chain.

This is the direct analog of H-03: in H-03 a snapshot (`callDebt`) is taken once and used later without reflecting a subsequent state change (`creditMultiplier` mark-down); here a hardcoded "snapshot" (`emptyPerasWeightSnapshot`) is used in place of the live Peras weight state, producing incorrect decisions whenever the actual weight state differs from zero.

---

### Finding Description

The `checkPreferTheirsOverOurs` function is invoked inside `readLedgerStateHelper` whenever the forecast horizon is exceeded and the node must decide whether to keep waiting for a peer or disconnect:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero; never reads live PerasCertDB
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The `preferAnchoredCandidate` function has two code paths: when `isEmptyPerasWeightSnapshot weights` is true it compares fragments purely by block count; when false it uses `weightedSelectView` which incorporates Peras boosts. [2](#0-1) 

By always passing `emptyPerasWeightSnapshot`, the function always takes the block-count-only path, regardless of what certificates are actually present in the `PerasCertDB`. The live snapshot is available via `getPerasWeightSnapshot` on the `ChainDbView` and is correctly used everywhere else in the chain-selection pipeline. [3](#0-2) 

The `PerasCertDB.getWeightSnapshot` STM action returns the live weights and is already wired into the `ChainDB` API. [4](#0-3) 

The chain-selection loop in `chainSelectionForBlock` and `chainSelSync` correctly reads the live snapshot via `Query.getPerasWeightSnapshot cdb` before calling `preferAnchoredCandidate`. [5](#0-4) 

The `checkPreferTheirsOverOurs` path is the only call site that substitutes `emptyPerasWeightSnapshot` instead of the live value.

---

### Impact Explanation

When Peras is enabled and certificates have been issued, the Peras weight boost can make a shorter chain heavier than a longer chain. The `checkPreferTheirsOverOurs` guard is supposed to disconnect from peers whose chain the node would never adopt. With `emptyPerasWeightSnapshot`:

- **Scenario A (false disconnect):** A peer offers a chain that is shorter in block count but heavier in Peras weight (the canonical chain under Peras). `preferAnchoredCandidate` with empty weights returns `ShouldNotSwitch` (peer's chain is shorter), so the node throws `CandidateTooSparse` and disconnects. The node loses its connection to the canonical chain.

- **Scenario B (false retention):** An adversary offers a chain that is longer in block count but lighter in Peras weight (non-canonical). `preferAnchoredCandidate` with empty weights returns `ShouldSwitch` (adversary's chain is longer), so the node does not disconnect and continues waiting. The node may eventually adopt the non-canonical chain.

Both scenarios cause the node to prefer a less-secure chain beyond the intended Peras security assumptions. This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

---

### Likelihood Explanation

This bug is latent until Peras is activated on a network. The CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference." [6](#0-5)  Once Peras is enabled, any peer whose header arrives beyond the forecast horizon triggers this code path. The developers have already acknowledged the issue with a `TODO` comment referencing `https://github.com/tweag/cardano-peras/issues/64`, confirming it is a known defect in production code. No special privileges, key compromise, or majority stake are required — any unprivileged peer can send a header beyond the forecast horizon.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the `PerasCertDB`, consistent with how `chainSelectionForBlock` and `chainSelSync` obtain it. Since `checkPreferTheirsOverOurs` runs inside an STM transaction, the live snapshot can be read atomically via `getPerasWeightSnapshot` on the `ChainDbView` that is already in scope in `checkTime`'s closure. This mirrors the pattern used in the main chain-selection path.

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Issue a Peras certificate boosting block `B` on chain `C_heavy` (shorter block count, higher total weight).
3. Connect an honest node `N` to two peers: peer `P1` serving `C_heavy` and peer `P2` serving `C_long` (longer block count, no Peras boost, non-canonical).
4. Arrange for `P1`'s next header to arrive beyond `N`'s forecast horizon (e.g., by creating a slot gap larger than `3k/f`).
5. `N` calls `checkPreferTheirsOverOurs` for `P1`. With `emptyPerasWeightSnapshot`, `C_heavy` appears shorter → `ShouldNotSwitch` → `N` throws `CandidateTooSparse` and disconnects from `P1`.
6. `N` remains connected to `P2` and eventually adopts `C_long`, the non-canonical chain.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->

            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
