Audit Report

## Title
Detached Promise in `ft_on_transfer` for `SwapMigratedToken` Silently Discards User Tokens on Failure - (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `ft_on_transfer`, the `SwapMigratedToken` branch calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)` to the NEP-141 token contract, signaling that all transferred tokens are consumed. The detached promise executes `burn.and(mint)` as two parallel cross-contract calls with no callback. If the `mint` call fails for any reason after `burn` succeeds, the user's old tokens are permanently destroyed with no new tokens minted and no refund path.

## Finding Description
In `ft_on_transfer` (lines 275–279 of `near/omni-bridge/src/lib.rs`):

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

`swap_migrated_token` (lines 2738–2753) constructs:

```rust
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
```

`Promise::and` in NEAR schedules both sub-promises to run in parallel. They are independent: `burn` can succeed while `mint` fails. Since the combined promise is `.detach()`ed, there is no callback to observe the outcome. The NEP-141 token contract has already been told `U128(0)` — zero tokens to refund — so the full `amount` is considered consumed by the bridge regardless of what happens in the detached promise chain.

Concrete failure modes for `mint`:
- The recipient (`sender_id`) has no storage registration on the new token contract (only the bridge itself is storage-registered during `migrate_deployed_token` at lines 1651–1655).
- The new token contract panics for any internal reason.
- Gas exhaustion in the mint cross-contract call.

In all these cases: old tokens are burned, new tokens are never minted, and the user has no recourse. The bridge holds no record of the failure.

The `storage_withdraw` and `storage_unregister` detached-transfer instances in `storage.rs` (lines 209, 235) are lower severity because native NEAR transfers to existing accounts do not fail in practice, unlike cross-contract token minting which requires prior storage registration.

## Impact Explanation
Permanent, irrecoverable loss of bridged user tokens. Any user who calls `ft_transfer_call` on a migrated old token targeting the bridge with `msg = "SwapMigratedToken"` and whose `mint` call fails loses their entire `amount`. This directly matches the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR."* The loss is caused entirely by code in this repository, not an external dependency.

## Likelihood Explanation
Medium. The `SwapMigratedToken` path is reachable by any unprivileged token holder via a standard `ft_transfer_call`. The failure condition — unregistered storage for the recipient on the new token — is the default state for any user who has not previously interacted with the new token contract. `migrate_deployed_token` only registers the bridge contract itself for storage on the new token (lines 1651–1655), not individual users. During a migration window, many users will be in exactly this state. The exploit is repeatable and requires no special privileges.

## Recommendation
Replace the fire-and-forget `.detach()` with a callback that checks the promise result and refunds the user on failure, following the same pattern used in `resolve_fast_transfer` and `resolve_utxo_fin_transfer`:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id.clone(), token_id, amount)
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(SWAP_MIGRATED_TOKEN_CALLBACK_GAS)
                .swap_migrated_token_callback(sender_id, amount),
        )
        .into()
}
```

The callback should return `amount` (triggering a refund) on failure and `U128(0)` on success. Alternatively, ensure storage is pre-registered for the recipient on the new token before the mint is attempted, though this does not eliminate all failure modes (gas exhaustion, contract panics).

## Proof of Concept
1. DAO calls `migrate_deployed_token(Eth, old_token.near, new_token.near)`. Bridge registers only itself for storage on `new_token.near`.
2. User holds `1_000_000` units of `old_token.near` and has never interacted with `new_token.near` (no storage registration).
3. User calls `ft_transfer_call` on `old_token.near` with `receiver_id = bridge`, `amount = 1_000_000`, `msg = "\"SwapMigratedToken\""`.
4. Bridge's `ft_on_transfer` fires `swap_migrated_token(user, old_token.near, 1_000_000).detach()` and returns `U128(0)`.
5. NEP-141 token contract sees `0` returned → does not refund → `1_000_000` units transferred to bridge and consumed.
6. Detached promise runs: `burn(1_000_000)` on `old_token.near` succeeds (bridge held the tokens). `mint(user, 1_000_000)` on `new_token.near` fails because user has no storage registration.
7. No callback fires. Bridge state is unchanged. User's `1_000_000` tokens are permanently lost.

Reproducible as a local integration test using `near-workspaces`: deploy a mock `new_token` that requires storage registration before minting, skip registering the test user, execute the above call sequence, and assert the user's balance on both tokens is zero with no refund emitted.
