### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the `BlockSupportsPeras` instance unconditionally returns `Right` (success) for every inbound Peras certificate, performing no cryptographic or semantic validation whatsoever. Because accepted certificates are fed directly into chain selection and add a configurable weight boost (`perasWeight = 15` by default) to the boosted block's chain fragment, any unprivileged peer can craft a certificate that boosts a block on a shorter fork and cause an honest node to abandon its canonical chain in favour of that fork.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for accepting a peer-supplied certificate. The sole production instance (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`) implements it as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No quorum check, no aggregate-signature verification, no round-number bounds check, and no check that the boosted block actually exists on any known chain is performed. The function assigns the full `perasWeight` boost (15 by default) to every certificate it receives. [2](#0-1) 

The inbound certificate path in the production node-to-node handler wires this stub directly into the ChainDB:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound ...
        (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `(validatePerasCert mkPerasParams)` as the validation function:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [4](#0-3) 

`processCerts` passes every certificate that clears the stub to `ChainDB.addPerasCertAsync`: [5](#0-4) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which, if the boosted block is present in the VolatileDB and not already on the current chain, calls `chainSelectionForBlock` for that block: [6](#0-5) 

Chain selection then compares the fork's total weight against the current chain using `preferAnchoredCandidate`, which incorporates the fraudulent boost via `weightedSelectView` → `weightBoostOfFragment`: [7](#0-6) [8](#0-7) 

The total weight comparison is `blockNo + weightBoost`. A fraudulent certificate with `vpcCertBoost = 15` makes a fork that is up to 15 blocks shorter than the honest chain appear heavier, triggering a chain switch.

---

### Impact Explanation

An unprivileged peer can cause an honest node to roll back its canonical chain and adopt a shorter but validly-structured fork, provided:

1. The attacker has (or can diffuse) a valid fork that diverges within the last `k` blocks.
2. The attacker sends a crafted `PerasCert` whose `pcCertBoostedBlock` points to a block on that fork that is already in the node's VolatileDB.

Because `validatePerasCert` never rejects any certificate, the attacker can assign an arbitrary boost to any block in the VolatileDB. With the default `perasWeight = 15`, a fork that is up to 15 blocks shorter than the honest chain will be preferred after a single fraudulent certificate. Multiple certificates for the same round are deduplicated by round number, but the attacker can use different round numbers to accumulate boosts across multiple blocks on the same fork, amplifying the effect.

This is a **chain selection safety failure**: an honest node is made to prefer a non-canonical, less-secure chain solely due to a peer-supplied message that bypasses all cryptographic authorization checks.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is a standard node-to-node protocol, reachable by any peer that can establish a connection. No stake, no keys, and no prior relationship with the target node are required. The attacker only needs to:

- Connect to the target node.
- Send a CBOR-encoded `PerasCert` with a `pcCertBoostedBlock` pointing to any block already in the node's VolatileDB.

The VolatileDB contents are partially inferrable from the ChainSync protocol (the node advertises its tip and accepts headers from peers). The attack is therefore straightforward to mount from any peer on the network once Peras is enabled.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with one that performs full cryptographic validation of the aggregate vote signature, verifies that the certificate's round number is within the valid range, and confirms that the quorum threshold was met by eligible committee members. Until real validation is implemented, the certificate diffusion handler should not be wired into the production `ChainDB` path. The TODO at `https://github.com/tweag/cardano-peras/issues/120` tracks this work and must be resolved before Peras is enabled on any network where peers are not fully trusted.

---

### Proof of Concept

**Setup:** Two nodes, A (honest) and B (attacker). Both are synced to the same chain tip at block height H.

1. Attacker B withholds one block it produces at slot S, creating a fork F of height H+1 that diverges from A's chain at height H.
2. B sends the fork block to A via BlockFetch. A stores it in its VolatileDB but does not switch (fork is same length as current chain, `ShouldNotSwitch EQ`).
3. B constructs a `PerasCert`:
   ```
   PerasCert { pcCertRound = 42, pcCertBoostedBlock = blockPoint(fork_block) }
   ```
   No valid aggregate signature is needed — the struct contains only a round number and a block point.
4. B sends this certificate to A via the Peras cert diffusion mini-protocol.
5. A's `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCertBoost = 15 })` unconditionally.
6. A calls `addPerasCertAsync`, which enqueues `ChainSelAddPerasCert`.
7. `chainSelSync` finds the fork block in the VolatileDB, calls `chainSelectionForBlock`.
8. `preferAnchoredCandidate` computes: fork total weight = H+1 (blockNo) + 15 (boost) = H+16; honest chain total weight = H+1 + 0 = H+1. Fork wins.
9. A switches to B's fork, rolling back its canonical chain. [9](#0-8) [10](#0-9) [11](#0-10)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
