### Title
Peras Weight Bypass in ChainSync Forecast-Horizon Disconnect Check - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when evaluating whether a peer's chain is preferred beyond the forecast horizon. This mirrors the GMX pattern exactly: just as GMX skips virtual-impact logic when one token lacks virtual inventory, Ouroboros skips Peras-weight-based chain comparison when the weight snapshot is empty — and here it is *always* empty by construction.

---

### Finding Description

When a header received from a peer is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to keep syncing or disconnect (`CandidateTooSparse`). The function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
-- Client.hs lines 1834–1851
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty; real weights never consulted
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

Inside `preferAnchoredCandidate`, the first branch fires whenever `isEmptyPerasWeightSnapshot weights` is true, falling back to a pure block-count comparison and completely skipping the Peras-weighted path:

```haskell
-- AnchoredFragment.hs lines 186–213
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- simple selectView / block-count comparison only
      ...
  | otherwise =
      -- weighted comparison using Peras certificate boosts
      case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                               (weightedSelectView cfg weights candSuffix) of ...
``` [2](#0-1) 

Because `emptyPerasWeightSnapshot` is always passed, `isEmptyPerasWeightSnapshot` is always `True`, and the weighted branch is never reached. The real weight snapshot — which *is* correctly maintained and used elsewhere (e.g., `NodeKernel.hs` line 299–310 reads it from `ChainDB.getPerasWeightSnapshot`) — is never consulted here. [3](#0-2) 

The structural parallel to the GMX bug is exact:

| GMX | Ouroboros |
|---|---|
| `if (!hasVirtualInventoryTokenA \|\| !hasVirtualInventoryTokenB) return priceImpactUsd;` | `if isEmptyPerasWeightSnapshot weights = ... (no Peras weights)` |
| One token missing virtual inventory → entire virtual-impact skipped | Empty snapshot passed → entire Peras-weighted comparison skipped |
| Attacker routes through a market where one token has no virtual inventory | Attacker presents a chain that is longer in blocks but lighter in Peras weight |

---

### Impact Explanation

**High — chain selection / Genesis-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

Scenario:

1. The honest node's current chain has a Peras certificate boost (total weight = block count + Peras boost).
2. A malicious peer presents a fork that is longer in raw block count but carries no Peras certificate boost, making it lighter in total weight.
3. `checkPreferTheirsOverOurs` evaluates the fork using only block count (empty weights). It concludes `ShouldSwitch` (their chain is longer) and returns `pure ()` — the node does **not** disconnect.
4. With actual Peras weights the correct answer would be `ShouldNotSwitch` (our chain is heavier), triggering `CandidateTooSparse` and disconnecting.

The node is therefore kept in a perpetual syncing state with a peer offering a non-canonical chain. This directly undermines the Genesis protocol's security guarantee: the Genesis State Machine relies on the node being able to identify and disconnect from peers whose chains are not preferred. A node that cannot disconnect from such peers may be held in `PreSyncing`/`CaughtUp` limbo, delaying or preventing convergence to the canonical chain.

---

### Likelihood Explanation

**Medium-High.** Any unprivileged peer on the network can trigger this path by:

1. Connecting to a target node via the standard ChainSync mini-protocol (no special privileges required).
2. Presenting a chain whose tip is beyond the target node's forecast horizon (a normal condition during initial sync or after a long slot gap).
3. Ensuring the presented chain is longer in block count than the node's current selection but carries no Peras certificate boost.

No key compromise, stake majority, or operator access is required. The attacker only needs to control a single peer connection and craft a valid (but non-canonical) chain fragment.

---

### Recommendation

Pass the actual `PerasWeightSnapshot` from the ChainDB into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`. The snapshot is already available in the `ChainSyncClientEnv` (or can be threaded through from the `ChainDB`), and the GSM code in `NodeKernel.hs` demonstrates the correct pattern:

```haskell
-- NodeKernel.hs lines 299–310 (correct pattern)
getCandidateOverSelection = do
    weights <- ChainDB.getPerasWeightSnapshot chainDB
    pure $ \(headers, _lst) state ->
      ...
      GSM.WhetherCandidateIsBetter $
        shouldSwitch
          ( preferAnchoredCandidate
              (configBlock cfg)
              (forgetFingerprint weights)   -- ← real weights
              headers
              (csCandidate state)
          )
``` [3](#0-2) 

The same pattern should be applied in `checkPreferTheirsOverOurs`. The existing TODO comment (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) acknowledges the issue but does not fix it; until the check is removed, it must use real weights.

---

### Proof of Concept

**Entry path (unprivileged peer → vulnerable code):**

```
Peer (N2N ChainSync)
  → ChainSync.Client.handleRollForward / handleMsgRollForward
  → intersectsWithCurrentChain / checkTime
  → projectLedgerView returns Nothing (header beyond forecast horizon)
  → checkPreferTheirsOverOurs kis
      → preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag
          → isEmptyPerasWeightSnapshot emptyPerasWeightSnapshot = True
          → falls into block-count-only branch
          → ShouldSwitch (their chain is longer in blocks)
      → pure ()   ← node does NOT disconnect
``` [4](#0-3) 

**Correct path (if real weights were used):**

```
preferAnchoredCandidate cfg realWeights ourFrag theirFrag
  → isEmptyPerasWeightSnapshot realWeights = False
  → weightedSelectView applied to both fragments
  → oursSuffix has Peras boost → ShouldNotSwitch
  → throwSTM CandidateTooSparse   ← node disconnects correctly
``` [5](#0-4)
