### Title
`execute_refund` Re-Execution Deadlock via Deterministic `btc_pending_id` Collision — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

The design explicitly allows `execute_refund` to be called again after a consensus branch change (chain reorg) when `refund_request.executed == true`. However, the re-execution path unconditionally panics because the old `BTCPendingInfo` is never removed before a new one is inserted, and the `btc_pending_id` is fully deterministic (it is the Bitcoin txid of the unsigned transaction, which is identical for the same inputs and outputs). The result is a permanent deadlock: `execute_refund` always panics, `remove_refund_pending_tx_id` is blocked by the still-active refund request, and the only operator escape path (rejecting the refund request) permanently marks the deposit UTXO as verified, making the user's BTC unrecoverable.

---

### Finding Description

**Step 1 — `btc_pending_id` is deterministic.**

`get_pending_id()` computes the Bitcoin txid of the unsigned transaction: [1](#0-0) 

For a refund, the PSBT is always built from the same `outpoint` (deposit txid + vout) and the same `refund_output` (same amount, same address): [2](#0-1) 

So every call to `execute_refund` for the same refund request produces the same `btc_pending_id`.

**Step 2 — First `execute_refund` succeeds.**

`finalize_refund_with_psbt` inserts the `BTCPendingInfo`, marks the UTXO in `verified_deposit_utxo`, and sets `refund_request.executed = true`: [3](#0-2) 

**Step 3 — `load_refund_request_for_execute` allows re-entry when `executed == true`.**

The guard that normally blocks re-execution (UTXO already in `verified_deposit_utxo`) is bypassed when `executed` is true: [4](#0-3) 

This is the intended re-execution path for branch changes.

**Step 4 — Second `execute_refund` panics.**

`finalize_refund_with_psbt` does not remove the old `BTCPendingInfo` before inserting a new one. Because the id is identical, `insert` returns `Some(old_value)` and the `require!` fires: [5](#0-4) 

**Step 5 — `remove_refund_pending_tx_id` is also blocked.**

The cleanup function requires the refund request to be gone first: [6](#0-5) 

But the refund request is still present (it is only removed by `verify_refund_finalize_callback` on confirmation, or by operator rejection).

**Step 6 — Operator rejection permanently locks the UTXO.**

If an operator calls `reject_refund`, the refund request is removed but `verified_deposit_utxo` is **not** cleared: [7](#0-6) 

After rejection, `remove_refund_pending_tx_id` can clean up the `BTCPendingInfo`, but the UTXO key remains in `verified_deposit_utxo` forever. A subsequent `request_refund_callback` is then blocked: [8](#0-7) 

The user's BTC deposit is permanently inaccessible.

---

### Impact Explanation

After the first `execute_refund` succeeds and the refund transaction fails to confirm (chain reorg, mempool eviction, etc.):

- `execute_refund` always panics on re-call — the intended recovery path is broken.
- `remove_refund_pending_tx_id` is blocked while the refund request exists.
- The only operator escape (reject the refund request) permanently marks the deposit UTXO as verified, blocking both `verify_deposit` and any future `request_refund` for the same UTXO.
- The user's BTC is permanently locked at the bridge deposit address with no on-chain or contract-level recovery path.

This is **permanent locking of user funds**.

---

### Likelihood Explanation

Bitcoin chain reorganizations are a normal operational event, especially for transactions with few confirmations. The developers explicitly anticipated this scenario (the comment in `finalize_refund_with_psbt` says "re-creating the refund tx, e.g. after a consensus branch change"), but the implementation does not handle it. No privileged access is required — `execute_refund` is a public, payable function callable by anyone. [9](#0-8) 

---

### Recommendation

Before inserting the new `BTCPendingInfo` in `finalize_refund_with_psbt`, check whether an entry for the same `btc_pending_id` already exists and remove it (along with its account-level tracking entries) before proceeding. Alternatively, generate a unique `btc_pending_id` per execution attempt (e.g., by mixing in a nonce or block height) so that re-execution always produces a fresh id. Additionally, ensure that `reject_refund` (or a dedicated cleanup path) also removes the UTXO from `verified_deposit_utxo` when the refund was executed by the bridge itself (i.e., `executed == true`), so the user can submit a new refund request after cancellation.

### Proof of Concept

```
State setup:
  refund_requests["txA@0"] = RefundRequest { executed: false, ... }
  verified_deposit_utxo = {}
  btc_pending_infos = {}

Call 1: execute_refund("txA@0", ...)
  → load_refund_request_for_execute: passes (executed=false, timelock ok)
  → builds PSBT(input=txA:0, output=refund_addr/amount)
  → btc_pending_id = txid(PSBT) = "X"
  → finalize_refund_with_psbt:
      btc_pending_infos.insert("X", ...) → None ✓
      verified_deposit_utxo.insert("txA@0")
      refund_requests["txA@0"].executed = true

[Refund tx "X" is signed, broadcast, but the block is reorged — tx never confirms]

Call 2: execute_refund("txA@0", ...)  ← intended re-execution after branch change
  → load_refund_request_for_execute:
      verified_deposit_utxo.contains("txA@0") = true
      refund_request.executed = true  → check passes ✓
  → builds same PSBT(input=txA:0, output=refund_addr/amount)
  → btc_pending_id = txid(PSBT) = "X"  ← identical
  → finalize_refund_with_psbt:
      btc_pending_infos.insert("X", ...) → Some(old) ← PANIC "pending info already exist"

remove_refund_pending_tx_id("X"):
  → refund_requests.contains_key("txA@0") = true → PANIC "refund request still active"

→ DEADLOCK: neither path can make progress without operator intervention.
→ Operator calls reject_refund("txA@0"):
    refund_requests.remove("txA@0") ✓
    verified_deposit_utxo still contains "txA@0"
→ remove_refund_pending_tx_id("X") now succeeds, cleans up BTCPendingInfo
→ But verified_deposit_utxo["txA@0"] is permanent:
    request_refund_callback: "UTXO already verified via deposit" → BLOCKED
    verify_deposit: also blocked
→ User's BTC permanently locked.
```
