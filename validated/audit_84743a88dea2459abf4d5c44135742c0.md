### Title
Peras Certificate Validation Unconditionally Returns Success, Allowing Unprivileged Peer to Manipulate Chain Selection - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs)

### Summary

The universal `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as a function that unconditionally returns `Right` (success) without performing any cryptographic or structural validation. This is the instance wired into the production Peras certificate diffusion mini-protocol handler. An unprivileged peer can send crafted `PerasCert` objects that are accepted without any check, added to the `PerasCertDB`, and used to boost arbitrary blocks in chain selection, potentially causing honest nodes to prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` always succeeds:**

The degenerate `BlockSupportsPeras` instance, explicitly labelled as a placeholder for all `StandardHash blk` types, implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no committee membership check, no VRF proof check, and no round-number plausibility check is performed. Every certificate, regardless of content, is wrapped in `ValidatedPerasCert` and returned as `Right`. The `PerasCert blk` data type in this instance carries only a round number and a block point — no cryptographic fields exist to validate even if the TODO were resolved: [2](#0-1) 

**This instance is the one used in production.** The `instance StandardHash blk => BlockSupportsPeras blk` declaration is a universal overlapping instance that applies to every block type, including the Cardano block type: [3](#0-2) 

**The production network handler wires this directly into the inbound certificate diffusion path:**

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`: [5](#0-4) 

**`processCerts` relies entirely on the return value of `validateCert` to gate admission:**

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [6](#0-5) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is admitted.

**Admitted certificates trigger chain selection.** Once added via `ChainDB.addPerasCertAsync`, the ChainDB runs `chainSelectionForBlock` for the boosted block: [7](#0-6) 

The boost weight applied is `perasWeight mkPerasParams = 15`: [8](#0-7) 

### Impact Explanation

**Impact: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker peer can craft a `PerasCert` naming any block point as `pcCertBoostedBlock`. That block receives a weight boost of 15 in chain selection. If the attacker targets a block on a minority fork, the honest node may switch to that fork, diverging from the canonical chain. Because the `PerasCert` type in this instance carries no cryptographic fields, there is no way for the node to distinguish a legitimate certificate from a fabricated one. The attack is repeatable across rounds and requires no stake, no keys, and no privileged access — only a peer connection.

### Likelihood Explanation

**Likelihood: High.** The Peras certificate diffusion mini-protocol is active in the production node-to-node handler. Any connected peer can send `PerasCert` messages. The attacker needs only to know a valid block hash and slot number (both publicly observable on-chain) to construct a certificate that boosts a fork block. No cryptographic material is required. The TODO comment and the linked issue (`cardano-peras/issues/120`) confirm the missing validation is a known gap, not an intentional design choice.

### Recommendation

1. **Short term:** Gate the `opwAddObjects` path in `makePerasCertPoolWriterFromChainDB` so that it rejects all certificates until a real `validatePerasCert` implementation is in place. A safe interim implementation would be `validatePerasCert _ _ = Left PerasValidationErr`, refusing all inbound certificates rather than accepting all of them.

2. **Medium term:** Implement `validatePerasCert` with full cryptographic checks: committee membership, aggregate BLS signature verification (`verifyAggregateVoteSignature`), VRF output verification (`batchVerifyVRFOutputs`), and round-number plausibility against the current ledger view — mirroring the checks already present in `implVerifyCert` for the WFALS committee.

3. **Long term:** Replace the universal degenerate `instance StandardHash blk => BlockSupportsPeras blk` with a proper era-specific instance for Cardano blocks that carries the full cryptographic certificate structure (`Cert crypto WFALS`) and delegates to `implVerifyCert`.

### Proof of Concept

1. Establish a peer connection to a target node running the Peras-enabled consensus code.
2. Observe the tip of a minority fork via ChainSync; record its `Point` (slot + hash).
3. Construct a `PerasCert` with `pcCertRound = <any unused round>` and `pcCertBoostedBlock = <fork tip point>`.
4. Send the certificate via the `ObjectDiffusion` protocol (`hPerasCertDiffusionClient`).
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert cert 15)` unconditionally.
6. The certificate is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is called.
7. `chainSelSync` runs `chainSelectionForBlock` for the fork-tip block with a weight boost of 15.
8. If the fork is within `k` blocks of the current tip and the boost tips the chain-selection comparison, the node switches to the fork — diverging from the canonical chain without any honest quorum having voted.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
