### Title
Recipient Account Not Validated Against Signed Payload in Solana `FinalizeTransfer` — (`solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

### Summary

The Solana `FinalizeTransfer` instruction verifies the MPC signature over the `FinalizeTransferPayload` but never checks that the `recipient` account passed in the instruction matches the `recipient` encoded in the signed payload. Any caller can substitute an arbitrary Solana pubkey as the `recipient` account while reusing a valid signed payload, redirecting bridged tokens to themselves instead of the intended beneficiary.

### Finding Description

The `FinalizeTransfer` accounts struct declares `recipient` as a fully unconstrained `UncheckedAccount`:

```rust
/// CHECK: this can be any type of account
pub recipient: UncheckedAccount<'info>,
``` [1](#0-0) 

The `token_account` — the actual destination of the bridged tokens — is derived as the associated token account of whichever `recipient` pubkey the caller supplies:

```rust
#[account(
    init_if_needed,
    payer = common.payer,
    associated_token::mint = mint,
    associated_token::authority = recipient,   // ← caller-controlled
    ...
)]
pub token_account: Box<InterfaceAccount<'info, TokenAccount>>,
``` [2](#0-1) 

Inside `process()`, the nonce is consumed and tokens are transferred/minted to `self.token_account` (i.e., the ATA of the caller-supplied `recipient`), but there is **no assertion** that `self.recipient.key()` equals `data.recipient` (the recipient encoded in the MPC-signed payload):

```rust
pub fn process(&mut self, data: FinalizeTransferPayload) -> Result<()> {
    UsedNonces::use_nonce(...)?;          // replay protection only
    // tokens go to self.token_account derived from self.recipient
    transfer_checked(...)?;               // no recipient validation
    // ...
}
``` [3](#0-2) 

The `FinalizeTransferResponse` posted back to NEAR omits the actual recipient entirely, so NEAR cannot detect the substitution:

```rust
let payload = FinalizeTransferResponse {
    token: self.mint.key(),
    amount: data.amount,
    fee_recipient: data.fee_recipient.unwrap_or_default(),
    transfer_id: data.transfer_id,   // recipient field absent
}
``` [4](#0-3) 

This is structurally identical to the C-01 pattern: the code validates the *type/authenticity* of the operation (MPC signature over the payload) but not the *specific parameter* (the recipient address), allowing an attacker to supply an arbitrary value for that parameter.

By contrast, the EVM `finTransfer` avoids this because the entire `TransferMessagePayload` — including `recipient` — is covered by the MPC signature, and the EVM contract verifies the signature over the exact payload it acts on, leaving no room to substitute a different recipient.

### Impact Explanation

A malicious relayer (or any Solana account that can submit the instruction) who obtains a valid `SignedPayload<FinalizeTransferPayload>` — which is public once broadcast — can:

1. Intercept or observe the signed payload for a victim's inbound transfer.
2. Re-submit `finalize_transfer` with their own pubkey as `recipient`.
3. The nonce is consumed (preventing the legitimate finalization), and the full token amount is minted/transferred to the attacker's ATA.
4. The victim receives nothing; NEAR sees a valid `FinalizeTransferResponse` and considers the transfer complete.

This constitutes complete, permanent theft of bridged funds for every inbound NEAR→Solana transfer.

### Likelihood Explanation

The signed payload is broadcast on-chain (Wormhole VAA or direct submission) and is therefore observable by any network participant. No privileged access, key compromise, or collusion is required. Any relayer applicant or public Solana caller can exploit this on every finalization.

### Recommendation

Add an explicit constraint in the `FinalizeTransfer` accounts struct (or an assertion in `process()`) that enforces `self.recipient.key() == data.recipient`:

```rust
// In accounts struct:
#[account(address = data.payload.recipient @ ErrorCode::InvalidRecipient)]
pub recipient: UncheckedAccount<'info>,

// Or in process():
require!(
    self.recipient.key() == data.recipient,
    ErrorCode::InvalidRecipient
);
```

This mirrors the EVM approach where the recipient is part of the signed payload and the signature check implicitly validates it.

### Proof of Concept

1. Alice initiates a NEAR→Solana transfer of 1000 USDC, specifying her Solana address `alice_pubkey` as recipient.
2. NEAR MPC signs a `FinalizeTransferPayload` with `recipient = alice_pubkey`, `amount = 1000`, `destination_nonce = N`.
3. The signed payload is broadcast (e.g., via Wormhole VAA or relayer submission).
4. Attacker Bob observes the signed payload before Alice's relayer finalizes it.
5. Bob calls `finalize_transfer` with the valid signed payload but passes `bob_pubkey` as the `recipient` account.
6. Anchor derives `token_account` as Bob's ATA; `process()` mints 1000 USDC to Bob's ATA.
7. Nonce `N` is marked used; Alice's relayer's subsequent attempt reverts with `NonceAlreadyUsed`.
8. Alice loses 1000 USDC with no recourse; NEAR records the transfer as finalized.
