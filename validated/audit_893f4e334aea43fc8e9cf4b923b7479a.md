### Title
Unprivileged Caller Can Submit `request_refund` for Any User's Deposit with Attacker-Controlled `refund_address`, Enabling Temporary Locking or BTC Theft - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` has no caller restriction and no check that the caller is the intended deposit recipient. Any NEAR account can submit a refund request for any confirmed BTC deposit, supplying an arbitrary `refund_address`. This creates a `RefundRequest` that blocks duplicate requests for the same UTXO and, if the DAO fails to reject within the 14-day `unsafe_refund_timelock_sec`, allows the attacker to redirect the user's BTC to their own address via the MPC signing pipeline.

Inside `internal_request_refund`, the only guard on `refund_address` is: [2](#0-1) 

This check is skipped entirely when `deposit_msg.refund_address` is `None` — the common case for standard deposits, since `refund_address` is an optional field: [3](#0-2) 

When the check is skipped, the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`: [4](#0-3) 

`execute_refund` is also unrestricted (no caller check): [5](#0-4) 

Because `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies the longer `unsafe_refund_timelock_sec` (14 days by default): [6](#0-5) 

After the timelock, `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to the stored `refund_address` (the attacker's BTC address), marks the UTXO as verified (blocking any later `verify_deposit`), and submits it to the MPC for signing: [7](#0-6) 

The default `unsafe_refund_timelock_sec` is 14 days: [8](#0-7) 

### Impact Explanation

**Primary (Medium):** The attacker forces the user's deposit UTXO into a pending refund state. Only one refund request can exist per UTXO at a time (`"Refund request already exists for this UTXO"`), so the legitimate user cannot submit their own refund request while the attacker's is active. The user's BTC is locked for up to 14 days pending DAO intervention.

**Secondary (Critical if DAO fails):** If the DAO/Operator does not call `reject_refund` within 14 days, the attacker calls `execute_refund`, the bridge constructs a PSBT paying the attacker's BTC address, the MPC signs it, and the user's BTC is permanently redirected to the attacker. The UTXO is then inserted into `verified_deposit_utxo`, permanently blocking any subsequent `verify_deposit` for that transaction.

### Likelihood Explanation

- `deposit_msg` is public (it is the hash preimage used to derive the deposit address, observable on-chain and in bridge events).
- The BTC transaction and Merkle proof are public on-chain data.
- The attacker must pay a non-refundable NEAR storage deposit, providing a spam deterrent but not a security barrier.
- The DAO has 14 days to reject, but if monitoring is delayed or the DAO is unresponsive, the attack succeeds.
- The relayer can race to call `verify_deposit` before `execute_refund` is called (since the UTXO is not yet in `verified_deposit_utxo` after `request_refund`), but if the relayer is slow or offline, the attacker wins the race after 14 days.

### Recommendation

1. **Restrict the caller**: Require `env::predecessor_account_id() == deposit_msg.recipient_id` inside `request_refund` or `request_refund_callback`, so only the intended NEAR recipient can submit a refund for their own deposit.
2. **Require a pre-authorized refund address**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None` from unprivileged callers, limiting permissionless refunds to deposits that embedded a `refund_address` at deposit time.
3. **Gate with `#[trusted_relayer]`**: Add `#[trusted_relayer]` to the `request_refund` function itself (not just the impl block) to restrict it to whitelisted relayers, consistent with how `verify_deposit` is protected.

### Proof of Concept

1. User sends 1 BTC to the deposit address derived from `deposit_msg = {recipient_id: "user.near", refund_address: None, ...}`.
2. BTC transaction is confirmed on-chain with sufficient confirmations.
3. Attacker observes `deposit_msg`, `tx_bytes`, `vout`, and Merkle proof from public chain data.
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = {recipient_id: "user.near", refund_address: None},
     refund_address = "attacker_btc_address",
     tx_bytes = <confirmed tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   with the required NEAR storage deposit attached.
5. `request_refund_callback` validates the transaction inclusion and script match, then stores `RefundRequest { refund_address: "attacker_btc_address", created_at_sec: now, ... }`.
6. DAO does not call `reject_refund` within 14 days.
7. Attacker calls `execute_refund(utxo_storage_key, None)`.
8. `finalize_refund_with_psbt` builds a PSBT paying ~1 BTC (minus gas fee) to `"attacker_btc_address"`, inserts the UTXO into `verified_deposit_utxo` (blocking any future `verify_deposit`), and submits to MPC for signing.
9. MPC signs the transaction; attacker broadcasts it.
10. User's 1 BTC is stolen; `verify_deposit` for this transaction is permanently blocked.

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,

        )
    }
