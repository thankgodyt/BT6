### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Submitted Peras Certificate Without Signature Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right` — it performs zero cryptographic or structural validation. Any unprivileged peer connected via the Peras certificate diffusion mini-protocol can submit a crafted `PerasCert` for an arbitrary block, have it accepted as "validated," and cause the receiving node to boost that block's chain-selection weight, potentially switching to a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The `BlockSupportsPeras` instance (the only production instance, applied to all `StandardHash blk`) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

It unconditionally wraps any incoming `PerasCert` in `Right ValidatedPerasCert`. No signature is checked, no quorum is verified, no round/slot bounds are enforced, and no committee membership is confirmed. [1](#0-0) 

**Attacker-controlled entry path — Peras cert diffusion mini-protocol:**

The production node-to-node handler wires the inbound Peras certificate diffusion client directly to `makePerasCertPoolWriterFromChainDB`, which calls `validatePerasCert` before adding to the `ChainDB`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, any `PerasCert` sent by a peer passes "validation" and is forwarded to `ChainDB.addPerasCertAsync` as a `ValidatedPerasCert`.

**Downstream effect — unauthorized chain selection:**

Once a `ValidatedPerasCert` is added to the `PerasCertDB`, `chainSelSync` triggers chain selection. The boosted block receives the `perasWeight` boost in `preferAnchoredCandidate`, which can cause the node to switch to a chain it would otherwise not prefer: [3](#0-2) 

The `PerasCert` data type contains only a round number and a block point — both fully attacker-controlled over the wire: [4](#0-3) 

**Contrast with `validatePerasVote` (partially mitigated in production):**

`validatePerasVote` also lacks signature verification, but the production diffusion handler passes an empty `PerasVoteStakeDistr mempty`, causing all inbound votes to be rejected at the stake-lookup step. No such mitigation exists for `validatePerasCert` — it returns `Right` regardless of any input. [5](#0-4) [6](#0-5) 

**Analog to the external report:**

The external report's root cause is that `claim(id)` in `VestedZeroNFT` does not check `msg.sender == ownerOf(id)`, so any caller can trigger a penalty on behalf of another user. The analog here is that `validatePerasCert` does not check any cryptographic proof of the certificate's legitimacy, so any peer can submit a certificate for any block and have it accepted as authoritative, triggering chain selection side-effects the honest node did not authorize.

### Impact Explanation

An unprivileged peer with a standard node-to-node connection can submit a crafted `PerasCert` pointing to any block currently in the receiving node's VolatileDB. The certificate is accepted without any verification and the boosted block receives the Peras weight boost in chain selection. If the boosted block is on a fork, the node may switch away from the canonical chain. This constitutes a **bypass of Peras certificate verification** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of certificate/vote verification checks" impact category.

### Likelihood Explanation

Any peer that can establish a node-to-node connection (no stake, no keys, no special privileges required) can exploit this. The Peras cert diffusion mini-protocol is wired up in the production `NodeToNode.hs` handler. The attacker only needs to know a valid block hash present in the target node's VolatileDB (observable via ChainSync) and send a `PerasCert` pointing to it. No cryptographic material is needed because none is checked.

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation that verifies:
1. The aggregate BLS signature over the certificate's `(electionId, candidate)` pair against the declared voters' public keys (using `verifyAggregateVoteSignature` from `CryptoSupportsAggregateVoteSigning`).
2. That the declared voters constitute a valid quorum (sufficient stake above the threshold).
3. That the certificate's round number and boosted block point are within acceptable bounds relative to the current ledger state.

Until full validation is implemented, the inbound Peras cert diffusion handler should reject all externally received certificates (analogous to how the vote handler uses an empty stake distribution to reject all votes), rather than accepting them unconditionally. [7](#0-6) 

### Proof of Concept

**Attacker preconditions:** A standard node-to-node TCP connection to the target node. No keys, no stake.

**Steps:**
1. Connect to the target node and run ChainSync to learn a block hash `H` currently in its VolatileDB (any block on a competing fork works best).
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point with hash H>`.
3. Send this `PerasCert` via the Peras cert diffusion mini-protocol (`objectDiffusionOutbound` → `objectDiffusionInbound` on the target).
4. The target calls `validatePerasCert` → returns `Right ValidatedPerasCert` unconditionally.
5. The cert is enqueued via `addPerasCertAsync` → `chainSelSync` → `chainSelectionForBlock` is triggered.
6. The block at `H` now carries `perasWeight` boost; if it is on a fork, `preferAnchoredCandidate` may now prefer it over the current selection, causing the node to switch chains.

**Expected outcome:** The target node switches its chain selection to the attacker-chosen fork without any legitimate quorum of Peras voters having voted for it. [8](#0-7)
