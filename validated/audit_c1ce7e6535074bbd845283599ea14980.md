Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Message-Account Pre-funding and Yield-Path Resume — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `NativeFeeRestricted` role check in `init_transfer` is placed only in the second operand of a short-circuit `||` condition. A restricted account can bypass it entirely by pre-funding the deterministic message-storage virtual account before calling `ft_transfer_call`, causing `try_to_transfer_balance_from_message_account` to succeed and short-circuit past the role check. An independent second bypass exists in `init_transfer_resume`, the yield-path callback, which contains no `NativeFeeRestricted` check at all, allowing a restricted account to complete a transfer with `native_fee > 0` via a two-transaction sequence.

## Finding Description

**Root cause — fast path.** In `init_transfer`, the storage-payment branch is selected by:

```rust
if self.try_to_transfer_balance_from_message_account(...).is_ok()   // first operand
   || (self.has_storage_balance(...) && (native_fee == 0 || !NativeFeeRestricted))  // second operand
``` [1](#0-0) 

The `NativeFeeRestricted` check lives exclusively in the second operand. Rust's short-circuit evaluation means that if the first operand evaluates to `Ok`, the role check is never reached.

`try_to_transfer_balance_from_message_account` returns `Ok` when the virtual message-storage account is registered with sufficient balance to cover `native_fee` and the combined balance (message account + signer) meets `required_storage_payer_balance + native_fee`. [2](#0-1) 

The message-storage account ID is a SHA-256 hash of `(token, amount, recipient, fee, sender, msg, external_id)` — all fields known to the attacker before the transfer is submitted. [3](#0-2) 

`storage_deposit` accepts an arbitrary `account_id` parameter and is callable by anyone, with no restriction on which account ID is funded. [4](#0-3) 

**Fast-path exploit flow:**
1. Restricted account A computes the deterministic message-storage account ID for a transfer with `native_fee = X > 0`.
2. A calls `storage_deposit(account_id = <message_storage_account_id>)` depositing enough NEAR to cover storage + X.
3. A calls `ft_transfer_call` with `native_token_fee = X`.
4. Inside `ft_on_transfer` → `init_transfer`, `try_to_transfer_balance_from_message_account` returns `Ok` (pre-funded in step 2).
5. The `||` short-circuits; `NativeFeeRestricted` is never checked.
6. `init_transfer_internal` stores the transfer with `fee.native_fee = X`.

**Root cause — yield path.** `init_transfer_resume` is the yield-path callback invoked when `storage_deposit` is called on the message-storage account after a yielded transfer. It contains no `NativeFeeRestricted` check:

```rust
pub fn init_transfer_resume(...) -> U128 {
    self.remove_promise(&message_storage_account_id);
    if let Err(err) = self.try_to_transfer_balance_from_message_account(...) {
        return transfer_message.amount;  // refund only
    }
    self.init_transfer_internal(transfer_message, storage_owner)  // no role check
}
``` [5](#0-4) 

**Yield-path exploit flow:**
1. Restricted account A calls `ft_transfer_call` with `native_fee = X > 0` without pre-funding the message account.
2. The fast-path condition is false (message account not registered; role check blocks second operand) → yield branch is taken; transfer is stored in `init_transfer_promises`.
3. A calls `storage_deposit(account_id = <message_storage_account_id>)` with enough NEAR.
4. `storage_deposit` calls `resume_promise`, which fires `init_transfer_resume`.
5. `init_transfer_resume` calls `try_to_transfer_balance_from_message_account` (now succeeds) and then `init_transfer_internal` — no role check anywhere in this path.
6. Transfer is finalized with `fee.native_fee = X`.

## Impact Explanation

This is a concrete role bypass matching the allowed Critical impact class: "authorization bypass, role bypass… that lets an attacker execute bridge… actions." The `NativeFeeRestricted` role is the protocol's sole mechanism to prevent designated accounts from attaching native-token fees to outbound NEAR-origin transfers. Both bypass paths allow a restricted account to submit and finalize a transfer with an arbitrary `native_fee`, causing the bridge to route that NEAR amount to the relayer's `fee_recipient` upon `sign_transfer`/`claim_fee`. The attacker self-funds the fee via the pre-deposit, so the mechanism is self-contained and requires no victim cooperation. The restriction is fully nullified for any account willing to pre-deposit.

## Likelihood Explanation

The message-storage account ID is fully deterministic from public, attacker-controlled transfer parameters. No special privileges, no third-party cooperation, and no timing constraints are required for the fast-path variant. The yield-path variant requires only two sequential transactions. Both paths are reachable through the standard `ft_transfer_call` → `ft_on_transfer` public entry point. The existing test suite in `near/omni-tests/src/native_fee_role.rs` only exercises the second-operand (direct storage balance) path and does not cover either bypass. [6](#0-5) 

## Recommendation

**Fast-path fix:** Apply the `NativeFeeRestricted` guard regardless of which storage path succeeds. Replace the current condition with:

```rust
if (self.try_to_transfer_balance_from_message_account(...).is_ok()
    || self.has_storage_balance(&signer_id, required_storage_balance.saturating_add(...)))
   && (init_transfer_msg.native_token_fee.0 == 0
       || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()))
```

This ensures the role check is always evaluated before entering `init_transfer_internal`, regardless of which storage-payment path is taken.

**Yield-path fix:** Add the role check at the top of `init_transfer_resume` before calling `try_to_transfer_balance_from_message_account`:

```rust
if transfer_message.fee.native_fee.0 > 0
    && self.acl_has_role(Role::NativeFeeRestricted.into(), storage_owner.clone())
{
    return transfer_message.amount;
}
```

Since `storage_owner` is the original `signer_id` captured at yield time, this correctly enforces the restriction on the resume path.

## Proof of Concept

**Fast-path PoC (single transaction):**
1. Admin grants `NativeFeeRestricted` to account A.
2. A computes `message_storage_account_id` from `TransferMessageStorageAccount { token, amount, recipient, fee: Fee { fee: 0, native_fee: X }, sender: A, msg: "" }.id(None)`.
3. A calls `storage_deposit(account_id = <message_storage_account_id>)` depositing `required_balance_for_account + required_balance_for_init_transfer + X` yoctoNEAR.
4. A calls `ft_transfer_call` on the token contract with `native_token_fee = X`.
5. Verify: `get_transfer_message` returns a stored transfer with `fee.native_fee = X`; the `NativeFeeRestricted` check was never evaluated.

**Yield-path PoC (two transactions):**
1. Admin grants `NativeFeeRestricted` to account A; A has only bare-minimum bridge storage.
2. A calls `ft_transfer_call` with `native_token_fee = X` — transfer yields (role check blocks fast path).
3. A calls `storage_deposit(account_id = <message_storage_account_id>)` with sufficient NEAR.
4. `resume_promise` fires `init_transfer_resume`; transfer is finalized with `fee.native_fee = X`.
5. Verify: `get_transfer_message` returns the stored transfer with `fee.native_fee = X`.

A minimal integration test can be structured analogously to the existing `zcash_stale_transfer_poc.rs` test, which already demonstrates the yield/resume flow and virtual-account pre-funding pattern. [7](#0-6)

            },

    pub(crate) fn try_to_transfer_balance_from_message_account(
        &mut self,
        account_id: &AccountId,
        native_fee: NearToken,
        storage_payer: &AccountId,
        required_storage_payer_balance: NearToken,
    ) -> Result<(), StorageError> {
        let balance = self
            .accounts_balances
            .get(account_id)
            .ok_or(StorageError::MessageAccountNotRegistered)?;

        if balance.total < native_fee {
            return Err(StorageError::NotEnoughBalanceForFee);
        }

        let mut storage = self
            .accounts_balances
            .get(storage_payer)
            .ok_or(StorageError::SignerNotRegistered)?;

        storage.available = storage.available.saturating_add(balance.total);

        if storage.available < required_storage_payer_balance.saturating_add(native_fee) {
            return Err(StorageError::SignerNotEnoughBalance);
        }

        self.accounts_balances.insert(storage_payer, &storage);
        self.accounts_balances.remove(account_id);
        Ok(())
    }
