Audit Report

## Title
Unhandled `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary
When finalizing an inbound transfer to a NEAR recipient with no message payload, `send_tokens` dispatches a plain `ft_transfer`. The callback `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`, causing `is_refund_required` to return `false` unconditionally without inspecting the promise result. If `ft_transfer` fails for any reason, the bridge treats delivery as successful: the transfer ID remains permanently in `finalised_transfers`, locked-token accounting is updated as if delivery succeeded, and `FinTransferEvent` is emitted — but the recipient never receives their tokens and no recovery path exists.

## Finding Description

**Step 1 — Transfer is marked finalised before delivery.**
`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, inserting the transfer ID into `finalised_transfers` before `send_tokens` is ever attempted. [1](#0-0) 

**Step 2 — `send_tokens` uses `ft_transfer` when `msg` is empty.**
When the transfer carries no message (the common case for standard bridging), `send_tokens` dispatches a plain `ft_transfer` call rather than `ft_transfer_call`. [2](#0-1) 

**Step 3 — Callback is registered with `is_ft_transfer_call = false`.**
The argument `!msg.is_empty()` evaluates to `false` for message-less transfers, so the callback receives `is_ft_transfer_call = false`. [3](#0-2) 

**Step 4 — `is_refund_required(false)` never inspects the promise result.**
When `is_ft_transfer_call` is `false`, the function returns `false` unconditionally, bypassing any check of whether the preceding `ft_transfer` promise succeeded or failed. [4](#0-3) 

**Step 5 — Callback always takes the "success" path.**
Because `is_refund_required` returns `false`, `fin_transfer_send_tokens_callback` proceeds to emit `FinTransferEvent` and pay the relayer fee regardless of whether the recipient actually received tokens. [5](#0-4) 

**Step 6 — Recovery path is never reached.**
`revert_lock_actions` and `remove_fin_transfer` are only called inside the `if Self::is_refund_required(...)` branch, which is never entered for plain `ft_transfer`. The transfer ID stays in `finalised_transfers` permanently with no replay possible. [6](#0-5) 

## Impact Explanation
If `ft_transfer` fails (token contract paused, blacklist rejection, custom transfer logic panic, or gas exhaustion), the outcome is: the transfer is permanently finalised and cannot be re-submitted; the bridge's internal locked-token accounting is updated as if delivery succeeded (since `revert_lock_actions` is skipped); `FinTransferEvent` is emitted signalling completion to the origin chain; and the recipient receives nothing with no recovery path. This constitutes permanent freezing of bridged funds, matching the Critical impact scope.

## Likelihood Explanation
The trigger requires `ft_transfer` to fail after storage registration is confirmed. Realistic triggers include: a bridged token contract with a pause mechanism (common in DeFi) being paused between proof submission and delivery; a token contract with custom `ft_transfer` logic that rejects transfers under certain conditions (blacklisting, transfer limits); or gas exhaustion if `FT_TRANSFER_GAS` is insufficient for a particular token's implementation. Any user who initiates a foreign-to-NEAR transfer with no message (the default path) is exposed. No special privileges are required; the condition can be triggered by any token admin action or token contract behavior that causes `ft_transfer` to fail.

## Recommendation
In `fin_transfer_send_tokens_callback`, always inspect the promise result regardless of `is_ft_transfer_call`. When `is_ft_transfer_call` is `false`, check `env::promise_result(0)` for failure. If the `ft_transfer` promise failed, execute the same recovery path as the `ft_transfer_call` refund case: call `burn_tokens_if_needed`, call `revert_lock_actions`, call `remove_fin_transfer`, and emit `FailedFinTransferEvent`. This mirrors the existing recovery logic already present for the `ft_transfer_call` case and ensures that a failed plain `ft_transfer` is handled symmetrically.

## Proof of Concept

1. Register a NEP-141 token with the bridge that has a pause mechanism.
2. Initiate a transfer from Ethereum to a NEAR account with no message payload (standard bridge flow).
3. Relayer submits the proof via `fin_transfer`; `add_fin_transfer` inserts the transfer ID into `finalised_transfers`.
4. Before the scheduled `ft_transfer` executes, the token admin pauses the token contract.
5. `ft_transfer` panics; the NEAR promise fails.
6. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` without reading the promise result.
8. Callback emits `FinTransferEvent` and pays the relayer fee.
9. The transfer ID remains in `finalised_transfers`; `revert_lock_actions` is never called; the recipient's tokens are permanently frozen in the bridge with no recovery path.

A unit test can be written against the NEAR sandbox: deploy a mock NEP-141 token that panics on `ft_transfer`, submit a `fin_transfer` with an empty `msg`, and assert that after the callback the transfer ID is still in `finalised_transfers`, `FinTransferEvent` was emitted, and the recipient balance is zero.
