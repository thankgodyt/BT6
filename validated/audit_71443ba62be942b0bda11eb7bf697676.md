### Title
Multiple Concurrent RBF PendingSign Entries Per Original Withdraw TX - (`contracts/satoshi-bridge/src/rbf/withdraw.rs`)

### Summary

`internal_withdraw_rbf` contains no guard preventing multiple `WithdrawUserRbf` entries from being simultaneously inserted into `btc_pending_infos` in `PendingSign` state for the same original tx. The only limit is `rbf_num_limit`. An unprivileged user (the original withdraw owner) can call `withdraw_rbf` up to `rbf_num_limit` times with distinct PSBTs while the original tx remains in `WithdrawOriginal/PendingVerify`, causing MPC to sign all of them — each spending the same UTXOs.

---

### Finding Description

**Entrypoint:** `internal_withdraw_rbf` in `contracts/satoshi-bridge/src/rbf/withdraw.rs`.

The function performs these checks before creating a new RBF entry:

1. `account_id == original_tx.account_id` — owner check (attacker passes trivially as the withdraw owner)
2. `assert_not_canceled()` — checks `cancel_rbf_reserved.is_none()`
3. `assert_withdraw_original_pending_verify_tx()` — checks the original tx is `WithdrawOriginal` in `PendingVerify` stage [1](#0-0) 

Critically, **none of these checks ask whether an existing RBF entry is already in `PendingSign` state**. The original tx's stage is never mutated by `internal_withdraw_rbf` — only `max_gas_fee` and `last_rbf_time_sec` are updated via `update_max_gas_fee`. [2](#0-1) 

In `set_rbf_pending_info`, the only enforcement is:
- The new `btc_pending_id` (derived from PSBT content) must not already exist in `btc_pending_infos`
- The set `rbf_txs[original_id]` must not already contain this id
- `rbf_txs.len() <= rbf_num_limit` [3](#0-2) 

Since each PSBT with different outputs produces a different `btc_pending_id`, an attacker can submit up to `rbf_num_limit` distinct PSBTs in sequence, each passing all guards, each inserted as a separate `WithdrawUserRbf/PendingSign` entry.

---

### Impact Explanation

All `rbf_num_limit` RBF entries are inserted into `btc_pending_infos` and forwarded to MPC for signing via `sign_btc_transaction_callback`. MPC produces `rbf_num_limit` valid signed transactions, all spending the **same UTXOs**. Only one can be confirmed on-chain. The remaining entries become stale `PendingVerify` entries in `btc_pending_infos`.

Cleanup via `internal_clear_invalid_pending_verify_rbf` requires the original tx to no longer appear in `rbf_txs`: [4](#0-3) 

Until the original tx is fully finalized and removed from `rbf_txs`, stale RBF entries cannot be cleaned up, leaving the bridge in a state requiring operator intervention. The recipient address is validated by `check_withdraw_rbf_psbt_valid`, so fund redirection is not possible — but MPC signing capacity is wasted and bridge state becomes inconsistent.

**Impact: Medium** — stuck bridge state requiring operator intervention; bypass of the intended invariant that only one RBF tx should be pending sign per original tx.

---

### Likelihood Explanation

The attacker is the original withdraw owner — a fully unprivileged public user. The path requires only submitting `rbf_num_limit` sequential `withdraw_rbf` calls with distinct PSBTs (different output amounts or change values). No privileged access, leaked keys, or external dependencies are needed. `rbf_num_limit` is a small integer (u8), making this trivially executable.

---

### Recommendation

In `internal_withdraw_rbf`, before calling `set_rbf_pending_info`, check that no existing entry in `rbf_txs[original_btc_pending_verify_id]` is currently in `PendingSign` state. Alternatively, enforce that `rbf_txs[original_id]` is empty (or all existing entries are in `PendingVerify`) before inserting a new one.

---

### Proof of Concept

```
1. User initiates withdraw → original tx enters WithdrawOriginal/PendingVerify.
2. User calls withdraw_rbf(original_id, psbt_1) → RBF entry rbf_id_1 inserted, PendingSign.
3. User calls withdraw_rbf(original_id, psbt_2) → RBF entry rbf_id_2 inserted, PendingSign.
   (original tx still WithdrawOriginal/PendingVerify — no state change from step 2)
4. Repeat up to rbf_num_limit times with distinct PSBTs.
5. MPC signs all rbf_num_limit entries.
6. rbf_num_limit valid signed transactions spending the same UTXOs exist.
7. Only one can be finalized via verify_withdraw; the rest are stuck until operator cleanup.
```

Assert: `btc_pending_infos` contains `rbf_num_limit` distinct `WithdrawUserRbf` entries all referencing the same original tx id, all in `PendingSign` (then `PendingVerify` after signing).
