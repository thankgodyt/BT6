### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares the raw sum of `PerasVoteStake` values directly against a relative quorum threshold (`3/4 + safety_margin`), but the normalization step that would convert absolute ledger stake into relative (fractional) stake is explicitly acknowledged as missing. This is the structural analog of the Ajna M-19 bug: a tally accumulation is compared against a threshold expressed in different units, making the quorum check incorrect and bypassable.

---

### Finding Description

The Peras quorum check is implemented in `stakeAboveThreshold`:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake        = unPerasVoteStake voteStake          -- raw Rational
  quorumThreshold = unPerasQuorumStakeThreshold ...  -- 3/4
  safetyMargin    = ...                              -- 2/100
```

The function's own TODO comment explicitly documents the unit mismatch:

> *"this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."* [1](#0-0) 

The quorum threshold is set to `3/4` (a relative fraction of total stake): [2](#0-1) 

`PerasVoteStake` values are accumulated by simple addition in `updateTargetVoteTally`:

```haskell
(votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
``` [3](#0-2) 

This accumulated total is then passed directly to `stakeAboveThreshold` in `votesReachQuorum`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

The production vote-processing path assigns stake from `PerasVoteStakeDistr` via `validatePerasVote` without any normalization step:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

The `PerasVoteStakeDistr` is populated from the ledger stake distribution, which holds absolute lovelace values. The comment on `PerasVoteStake` itself acknowledges there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake": [6](#0-5) 

---

### Impact Explanation

When `PerasVoteStakeDistr` is populated with absolute ledger stake values (e.g., lovelace amounts on the order of millions or billions), the sum of even a single voter's `PerasVoteStake` will be astronomically larger than the relative threshold `0.77` (`3/4 + 2/100`). As a result, `stakeAboveThreshold` returns `True` after the very first vote is added to any tally, causing `votesReachQuorum` to immediately forge a `ValidatedPerasCert` for whatever block that single voter voted for.

This completely bypasses the intended `3/4`-of-total-stake quorum requirement. Any unprivileged peer that holds any positive stake and can send a syntactically valid `PerasVote` can cause the local node to forge and accept a Peras certificate for an arbitrary block, boosting that block's chain weight by `perasWeight` (default: 15 blocks). This directly corrupts chain selection, causing honest nodes to prefer an adversarially chosen chain over the canonical one.

The impact matches: **Critical — Bypass of Peras voting/certificate checks that enables unauthorized certificate acceptance.**

---

### Likelihood Explanation

The entry path is fully reachable by an unprivileged peer: the peer sends a `PerasVote` message over the miniprotocol, which is processed by `processVotes` → `validatePerasVote` (assigns absolute stake from ledger distribution) → `PerasVoteDB.addVote` → `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold`. No special privileges, key compromise, or majority stake are required. The bug is triggered by the first vote from any eligible voter. [7](#0-6) 

---

### Recommendation

Normalize `PerasVoteStake` values to relative (fractional) form before they are stored in `PerasVoteStakeDistr` or before they are passed to `stakeAboveThreshold`. Concretely, divide each voter's absolute ledger stake by the total stake of the voting committee before constructing `PerasVoteStakeDistr`. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, removing the implicit unit assumption. The TODO comment at line 155–161 of `SupportsPeras.hs` already identifies exactly this fix. [8](#0-7) 

---

### Proof of Concept

Assume a stake distribution where voter `V` holds `1_000_000` lovelace (1 ADA) out of a total supply of `45_000_000_000_000_000` lovelace. The `PerasVoteStakeDistr` is populated with the absolute value `PerasVoteStake (1_000_000 % 1)`.

1. Peer sends `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = V }`.
2. `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake (1_000_000 % 1)`.
3. `updateTargetVoteTally` sets `ptvtTotalStake = PerasVoteStake (1_000_000 % 1)`.
4. `votesReachQuorum` calls `stakeAboveThreshold`:
   - `stake = 1_000_000`
   - `quorumThreshold + safetyMargin = 3/4 + 2/100 = 0.77`
   - `1_000_000 >= 0.77` → **True**
5. `forgePerasCert` is called, producing a `ValidatedPerasCert` for `adversarialBlock` with boost weight 15.
6. Chain selection now prefers any chain containing `adversarialBlock` over honest chains lacking the boost, with no legitimate quorum having been reached.
