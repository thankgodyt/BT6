Audit Report

## Title
Inverted Refund Condition in `is_refund_required` Enables Double-Spend and Replay on UTXO `ft_transfer_call` Finalization - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`Contract::is_refund_required` returns `true` (refund required) when the inner `ft_transfer_call` result is `0` — the exact NEP-141 signal for full success — and `false` when the result is non-zero (tokens unused). This inversion causes every successful UTXO-to-NEAR `ft_transfer_call` finalization to simultaneously deliver tokens to the recipient and trigger a full refund to the UTXO connector, while also erasing the finalization record and enabling unlimited replay from a single UTXO proof.

## Finding Description

`is_refund_required` at line 1791 reads the promise result of the inner `send_tokens` call (an `ft_transfer_call` to the NEAR recipient) and evaluates:

```rust
amount.0 == 0   // line 1791
```

Under NEP-141, `ft_transfer_call` resolves to the amount refunded back to the sender (i.e., the unused amount returned by `ft_on_transfer` on the recipient contract):
- Result `0` → recipient consumed all tokens → **no refund needed**
- Result `N > 0` → N tokens unused → **refund N tokens**

The code returns `true` (refund required) precisely when `amount == 0`, i.e., when the inner transfer **succeeded**. The misleading comment ("refund if the used token amount is zero") further confirms the author confused "used" with "refund/unused."

`resolve_utxo_fin_transfer` acts on this result:

```rust
// lines 1025-1030
if Self::is_refund_required(is_ft_transfer_call) {
    self.remove_fin_utxo_transfer(          // erases finalization record
        &utxo_fin_transfer_msg.get_transfer_id(origin_chain),
        storage_owner,
    );
    amount                                  // returns full amount as ft_on_transfer refund signal
}
```

The return value of `resolve_utxo_fin_transfer` propagates up through `utxo_fin_transfer_to_near_callback` (which returns `PromiseOrValue<U128>`) as the bridge's `ft_on_transfer` return value. The outer token contract's `ft_resolve_transfer` interprets this non-zero return as "all tokens unused" and refunds the full amount to the UTXO connector.

Exploit path:
1. Attacker deploys `attacker.near` with `ft_on_transfer` returning `"0"` (standard NEP-141 success).
2. Attacker submits a valid UTXO proof with a non-empty `msg` field (`is_ft_transfer_call = true`).
3. `utxo_fin_transfer` records the finalization via `add_fin_utxo_transfer`, then chains to `utxo_fin_transfer_to_near_callback`.
4. `send_tokens` executes inner `ft_transfer_call` → `attacker.near::ft_on_transfer` returns `"0"` → recipient receives tokens.
5. `resolve_utxo_fin_transfer` is called. `is_refund_required` reads result `0`, evaluates `0 == 0 → true`, calls `remove_fin_utxo_transfer` (deletes finalization record), returns `amount`.
6. Outer `ft_resolve_transfer` sees return value `= amount`, refunds full amount to UTXO connector. `attacker.near` already holds the tokens from step 4.
7. Finalization record deleted in step 5 → attacker resubmits the same UTXO proof → unlimited minting.

The inverse case (recipient returns non-zero, transfer failed) causes `is_refund_required` to return `false`, suppressing the refund and permanently locking tokens. [1](#0-0) [2](#0-1) [3](#0-2) 

## Impact Explanation

**Critical.** Two concrete allowed impacts are triggered simultaneously:

1. **Double-spend / unauthorized minting**: The recipient receives bridged tokens from the inner `ft_transfer_call`, and the UTXO connector receives a full refund of those same tokens from the outer `ft_resolve_transfer`. Tokens are created out of thin air on the NEAR side on every successful finalization with a non-empty `msg`.
2. **Cross-chain replay enabling double-spending**: `remove_fin_utxo_transfer` deletes the entry from `finalised_utxo_transfers`, bypassing the "already finalised" guard on subsequent submissions of the same UTXO proof. A single UTXO can be finalized an unlimited number of times.

Both impacts match the Critical scope: "double-spending, unauthorized minting" and "Cross-chain replay... enabling invalid finalization or double-spending." [4](#0-3) 

## Likelihood Explanation

**High.** The trigger is the normal happy path: a UTXO-to-NEAR `ft_transfer_call` finalization where the recipient's `ft_on_transfer` returns `"0"` (the correct NEP-141 success response). No privileged access, no key compromise, no race condition, and no victim mistake is required. Any attacker can deploy a compliant recipient contract and submit a valid UTXO proof through the public `utxo_fin_transfer` entry point. [5](#0-4) 

## Recommendation

Invert the condition in `is_refund_required`. The value read from the promise result is the **unused** (refund) amount returned by `ft_on_transfer`; a refund is required when this value is **non-zero**:

```rust
// Correct: refund is required when the receiver returned unused tokens (amount > 0)
amount.0 != 0
```

Update the comment at line 1789–1790 to clarify that `amount` is the unused/refund amount, not the consumed amount. [5](#0-4) 

## Proof of Concept

**Minimal contract-call sequence (private testnet):**

1. Deploy token contract `token.near` (NEP-141 with `ft_transfer_call` / `ft_resolve_transfer`).
2. Deploy bridge contract `bridge.near` with the vulnerable code.
3. Deploy `attacker.near` with `ft_on_transfer` always returning `"0"`.
4. Fund UTXO connector with `N` tokens; configure bridge with UTXO connector.
5. Call `bridge.near::utxo_fin_transfer` with a valid UTXO proof, `recipient = attacker.near`, non-empty `msg`.
6. Observe: `attacker.near` balance = `N` (inner transfer succeeded); UTXO connector balance restored to `N` (outer refund triggered); `finalised_utxo_transfers` entry absent.
7. Resubmit the same UTXO proof → repeat step 6 → unlimited minting confirmed.

**Invariant test:** Assert that after a successful `utxo_fin_transfer` with non-empty `msg`, `finalised_utxo_transfers` contains the transfer ID (it will not, proving the record was incorrectly deleted) and that the UTXO connector balance decreased by `N` (it will not, proving the double-spend). [6](#0-5)

    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {
            match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                        // Normal case: refund if the used token amount is zero
                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                        amount.0 == 0
                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }
