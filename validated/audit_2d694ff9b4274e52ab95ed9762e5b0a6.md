### Title
Unconditional `validatePerasCert` Stub Accepts Any Crafted Peras Certificate Without Cryptographic Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production default instance of `validatePerasCert` in `BlockSupportsPeras` is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or committee-authorization checks. An unprivileged peer can send a crafted `PerasCert` boosting any arbitrary block; the node will accept it as a `ValidatedPerasCert` and use it to influence chain selection, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must verify a Peras certificate before it is stored and used for chain selection. The default instance (the only instance present in this codebase, explicitly labelled a "degenerate instance for all blks to get things to compile") is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every field of the certificate — the claimed round number, the claimed boosted block, and any aggregate BLS signature or VRF eligibility proof — is silently ignored. The function always produces a `ValidatedPerasCert` carrying the full configured `perasWeight` boost.

The analogous stub for `validatePerasVote` also skips all cryptographic checks (signature, VRF eligibility, committee membership), performing only a stake-distribution lookup:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

Once a `ValidatedPerasCert` is produced, it flows directly into `chainSelSync` via `addPerasCertAsync`, where it is stored in the `PerasCertDB` and immediately triggers chain selection for the boosted block: [3](#0-2) 

The `PerasWeightSnapshot` used during chain selection then applies the boost from the fraudulent certificate to the attacker-chosen block, potentially making a non-canonical fork appear heavier than the honest chain. [4](#0-3) 

The certificate diffusion inbound handler in the production node-to-node stack calls `makePerasCertPoolWriterFromChainDB`, which feeds received certs through `validatePerasCert` before handing them to `addPerasCertAsync`: [5](#0-4) 

Because `validatePerasCert` always succeeds, the entire cryptographic gate is absent.

---

### Impact Explanation

This is a **bypass of Peras certificate validation** that enables unauthorized certificate acceptance. A single unprivileged peer can inject a `PerasCert` claiming to boost any block in the VolatileDB. The receiving node will:

1. Accept the cert as fully validated.
2. Store it in the `PerasCertDB`.
3. Trigger chain selection for the boosted block, potentially switching to a fork that carries the fraudulent boost weight.

This directly maps to the **Critical** impact category: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."* It also maps to **High**: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

The analog to the TempleDAO report is exact: just as `_stakeFor` and `_withdrawFor` failed to re-validate the delegation state before modifying vote power, `validatePerasCert` fails to validate the certificate's authorization state (committee quorum, aggregate BLS signature, round binding) before granting it chain-selection weight.

---

### Likelihood Explanation

Peras is not enabled by default in the current codebase (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However:

- The diffusion mini-protocol handlers for Peras certificates are wired into the production `NodeToNode` stack unconditionally.
- Once an operator enables Peras (or when it is enabled by default in a future release), any peer that can open a node-to-node connection can exploit this immediately with a single crafted message.
- No stake, no keys, and no prior knowledge of the chain state are required beyond knowing a valid block hash in the target node's VolatileDB (obtainable via the ChainSync protocol).

---

### Recommendation

Replace the stub `validatePerasCert` default instance with a real implementation that:

1. Verifies the aggregate BLS signature over `(electionId, candidate)` against the aggregate verification key derived from the declared committee members' public keys.
2. Verifies each declared voter's eligibility (persistent: wFA seat check; non-persistent: VRF output and local sortition threshold).
3. Verifies that the total weight of verified voters meets the quorum threshold.
4. Binds the certificate to the correct epoch nonce and round number.

Until the full implementation is ready, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), consistent with the approach already taken for votes in the production `NodeToNode` handler (which uses `pure (PerasVoteStakeDistr mempty)` to reject all votes): [6](#0-5) 

---

### Proof of Concept

**Private testnet sequence (Peras enabled):**

1. Node A connects to honest Node B via the node-to-node Peras certificate diffusion mini-protocol.
2. Node A observes (via ChainSync) that Node B's VolatileDB contains block `H` on a minority fork at point `P`.
3. Node A crafts a `PerasCert { pcCertRound = r, pcCertBoostedBlock = P }` with arbitrary (invalid) content.
4. Node A sends the crafted cert to Node B through the `hPerasCertDiffusionClient` handler.
5. Node B calls `validatePerasCert` on the cert; the stub returns `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
6. Node B stores the cert in its `PerasCertDB` and calls `chainSelectionForBlock` for block `H`.
7. Chain selection now sees block `H` carrying a full Peras boost weight; if this exceeds the honest chain's weight, Node B switches to the minority fork. [7](#0-6) [8](#0-7)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
