### Title
Silent Envelope Validation Bypass in `revalidateHeader` via No-Op `assertWithMsg` in Production Builds - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`)

---

### Summary

`assertWithMsg`, the sole mechanism used to enforce the envelope check inside `revalidateHeader`, is compiled to a **complete no-op** in every production build because the `asserts` Cabal flag defaults to `False`. The envelope check — which validates block-number consecutiveness, slot-number monotonicity, hash-chain integrity, and checkpoint matching — is silently discarded. Any block that reaches `reapplyBlockLedgerResult` with a malformed envelope is accepted without error, exactly mirroring the external report's pattern of a call that returns an error code the caller never inspects.

---

### Finding Description

**Root cause — `assertWithMsg` is unconditionally a no-op in production:**

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a          -- always reached in production
```

`ENABLE_ASSERTIONS` is only defined when the `asserts` flag is set, and that flag **defaults to `False`**:

```
-- ouroboros-consensus.cabal
flag asserts
  description: Enable assertions
  manual: False
  default: False          -- never active in a standard production build
```

**Affected call-site — `revalidateHeader`:**

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $          -- ← silently discarded in production
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' =
    reupdateChainDepState                -- skips expensive VRF/KES checks by design
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck :: Either String ()
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` checks:
- `UnexpectedBlockNo` — block numbers must be consecutive
- `UnexpectedSlotNo` — slot numbers must be strictly increasing
- `UnexpectedPrevHash` — the `prevHash` field must match the actual tip hash
- `CheckpointMismatch` — the block hash must match any configured checkpoint

All four checks produce a `Left` value on failure. In production, `assertWithMsg (Left …)` returns the second argument unchanged — the new `HeaderState` is returned as if validation succeeded.

**Production call path — `reapplyBlockLedgerResult`:**

`revalidateHeader` is invoked from `reapplyBlockLedgerResult` in `Extended.hs`, which is the function used by the LedgerDB during chain selection (switching to a new candidate chain) and during ledger-state replay from snapshots. Both paths are reachable from network-delivered blocks.

---

### Impact Explanation

If a block with a malformed envelope (wrong block number, broken `prevHash` link, or mismatched checkpoint hash) reaches `reapplyBlockLedgerResult`, the node will:

1. Compute `envelopeCheck = Left "…"` inside `revalidateHeader`.
2. Pass that `Left` to `assertWithMsg`, which returns the new `HeaderState` unchanged.
3. Proceed to update the ledger state as if the block were valid.

This can cause the node to maintain a ledger state derived from a chain with a broken hash chain or non-consecutive block numbers — a direct ledger-state corruption / invalid-chain-acceptance outcome. Because `reupdateChainDepState` also skips VRF/KES re-verification, `revalidateHeader` provides **zero** cryptographic or structural guarantees in production.

The impact maps to the allowed scope:
> **High. ChainDB, ImmutableDB, VolatileDB, LedgerDB, snapshot, or LSM corruption/replay/rollback bug that causes durable use of the wrong ledger state or permanent acceptance/rejection of a valid chain without operator fault.**

---

### Likelihood Explanation

The primary guard is `validateHeader` (used in the ChainSync client and in `applyBlockLedgerResult`), which does throw on envelope errors. `revalidateHeader` is intended as a cheaper re-check for already-validated blocks. However:

- The guarantee that "the block was already validated" is enforced **only** by the disabled assertion. No type-level or runtime enforcement exists in production.
- Any bug in the validation pipeline (e.g., a race between block storage and chain selection, or a future refactor that calls `reapplyBlockLedgerResult` on a block that bypassed `validateHeader`) silently removes all envelope checks.
- The `DBAnalyser` tool calls `revalidateHeader` directly on disk-resident blocks; corrupted on-disk data would pass silently.
- The `asserts` flag is `manual: False`, so operators cannot easily enable it without modifying their build configuration; the documentation notes it as a temporary benchmarking aid, not a production setting.

Likelihood is **medium**: the primary path is protected, but the silent-failure design means any single upstream bypass propagates undetected.

---

### Recommendation

1. **Replace `assertWithMsg` with a hard error in `revalidateHeader`**: the envelope check is cheap (no crypto); there is no performance justification for making it assertion-only. Use `runExcept (validateEnvelope …) >>= either (throwIO . HeaderEnvelopeError) pure` or equivalent.

2. **Alternatively, enforce the invariant at the type level**: introduce a `ValidatedHeader blk` newtype that can only be constructed by `validateHeader`, and require `revalidateHeader` to accept only `ValidatedHeader blk`. This makes the "already validated" precondition structurally impossible to violate.

3. **Audit all other `assertWithMsg` call-sites in production `src/` paths** (`ChainSync/Client.hs`, `AnchoredFragment.hs`, `HardFork/Combinator/AcrossEras.hs`) for the same pattern.

4. **Set `default: True` for the `asserts` flag**, or at minimum document clearly that production deployments run without any of these checks active.

---

### Proof of Concept

**Step 1.** A peer delivers a sequence of headers. The ChainSync client validates them with `validateHeader` (full check, throws on error) and stores the corresponding blocks in the VolatileDB.

**Step 2.** Suppose a bug (or future refactor) causes a block `B` with `prevHash = wrongHash` to be stored in the VolatileDB without passing through `validateHeader` — for example, via a direct `putBlock` call that bypasses the client.

**Step 3.** Chain selection fires and calls `chainSelectionForBlock` → `reapplyBlockLedgerResult` → `revalidateHeader` on block `B`.

**Step 4.** Inside `revalidateHeader`:
```
envelopeCheck = Left "UnexpectedPrevHash …"
assertWithMsg (Left "…") newHeaderState
-- In production: assertWithMsg _ a = a
-- Returns: newHeaderState   ← validation error silently discarded
```

validateEnvelope ::
  forall blk.
  ValidateEnvelope blk =>
  TopLevelConfig blk ->
  LedgerView (BlockProtocol blk) ->
  -- | Old tip
  WithOrigin (AnnTip blk) ->
  Header blk ->
  Except (HeaderEnvelopeError blk) ()
validateEnvelope cfg ledgerView oldTip hdr = do
  unless (actualBlockNo == expectedBlockNo) $
    throwError $
      UnexpectedBlockNo expectedBlockNo actualBlockNo
  unless (actualSlotNo >= expectedSlotNo) $
    throwError $
      UnexpectedSlotNo expectedSlotNo actualSlotNo
  unless (checkPrevHash' (annTipHash <$> oldTip) actualPrevHash) $
    throwError $
      UnexpectedPrevHash (annTipHash <$> oldTip) actualPrevHash
  validateIfCheckpoint (topLevelConfigCheckpoints cfg) hdr
  withExcept OtherHeaderEnvelopeError $
    additionalEnvelopeChecks cfg ledgerView hdr
 where
  checkPrevHash' ::
    WithOrigin (HeaderHash blk) ->
    ChainHash blk ->
    Bool
  checkPrevHash' Origin GenesisHash = True
  checkPrevHash' (NotOrigin h) (BlockHash h') = h == h'
  checkPrevHash' _ _ = False
