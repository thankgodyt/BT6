Audit Report

## Title
Parallel `burn.and(mint)` in `swap_migrated_token` Causes Permanent Token Loss When Mint Fails — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` schedules `burn` and `mint` as parallel, independent NEAR promises via `burn.and(mint)` with no sequential dependency and no error-handling callback. The promise is immediately detached, so no result is ever observed. If `mint` panics — which it will whenever the recipient has no storage registration on the new token — `burn` still executes, permanently destroying the user's old tokens while issuing no new tokens.

## Finding Description
**Entry point:** `ft_on_transfer` handles `SwapMigratedToken` by calling `swap_migrated_token`, detaching the returned promise, and returning `U128(0)` — meaning the bridge retains all received tokens and issues no refund to the NEP-141 transfer. [1](#0-0) 

**Parallel promise construction:** Inside `swap_migrated_token`, `burn.and(mint)` is used: [2](#0-1) 

In NEAR SDK, `Promise::and()` schedules both sub-promises to execute in parallel. Neither depends on the other's success or failure. There is no `.then(callback)` to observe results.

**Failure path in `mint`:** The `mint` implementation (with `msg: None`) calls `self.token.internal_deposit(&account_id, amount.into())`: [3](#0-2) 

NEAR's standard `FungibleToken::internal_deposit` panics with "The account X is not registered" if the recipient has no storage deposit on the new token. This panic causes the `mint` cross-contract call to fail.

**`burn` is unaffected by `mint`'s failure:** Because the two are parallel (not sequential), `burn` executes regardless: [4](#0-3) 

The bridge contract is the predecessor of `burn`, so `internal_withdraw` removes the old tokens from the bridge's balance. Those tokens are gone. No new tokens were minted. No refund path exists because the promise was detached and `ft_on_transfer` already returned `U128(0)`.

**No existing guard:** There is no pre-check for storage registration on the new token before the swap is initiated, and no callback to detect and recover from `mint` failure.

## Impact Explanation
Permanent, unrecoverable loss of bridged user funds. Old tokens are burned from the bridge's custody; new tokens are never issued. This directly matches the critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR."*

## Likelihood Explanation
Any user who initiates a `SwapMigratedToken` flow without first calling `storage_deposit` on the new token triggers this. Storage registration is a non-obvious prerequisite that the protocol does not enforce or auto-provision. The condition is reachable by any unprivileged token holder through a standard `ft_transfer_call` on the old token. It is repeatable and requires no special attacker capability — it can occur accidentally or be induced by a griever who front-runs a victim's swap to unregister their storage (if the new token allows it).

## Recommendation
Replace the parallel `burn.and(mint)` pattern with a sequential chain and a recovery callback:

1. **Sequential execution**: Use `burn.then(mint_callback)` so `mint` is only attempted after `burn` succeeds, and the callback can verify `mint`'s result.
2. **Recovery on mint failure**: In the callback, if `mint` failed, re-mint the old tokens back to the bridge and return them to the user via `ft_transfer`.
3. **Pre-registration**: Alternatively, include a `storage_deposit` call for the recipient on the new token as the first step in the chain, funded by an attached deposit from the user, before attempting `burn`.
4. **Do not detach**: Remove `.detach()` so the promise result propagates back through `ft_on_transfer`, enabling the NEP-141 refund mechanism (`U128(amount)` return) to fire on failure.

## Proof of Concept
1. Deploy old token and new token; register the bridge as controller of both; add the migration mapping via `add_migrated_token`.
2. Register the user on the old token and mint them `1000` units.
3. **Do not** call `storage_deposit` for the user on the new token.
4. User calls `old_token.ft_transfer_call(bridge, 1000, '\"SwapMigratedToken\"')`.
5. `ft_on_transfer` returns `U128(0)` — bridge keeps all 1000 old tokens.
6. `burn` executes: bridge's 1000 old tokens are destroyed.
7. `mint` executes: panics because user is not registered on new token.
8. Observe: user's old token balance = 0, new token balance = 0, bridge old token balance = 0. Funds are permanently lost.
