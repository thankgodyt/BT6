### Title
Peras Quorum Threshold Bypass via Missing Stake Normalization in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function compares accumulated `PerasVoteStake` values — which are sourced directly from the ledger stake distribution without normalization — against a relative quorum threshold (`3/4`). Because the normalization step from absolute ledger stake to relative committee stake is explicitly unimplemented (documented as a TODO with no agreed-upon formula), any voter whose absolute stake value exceeds `0.77` (i.e., essentially every voter with positive stake) can cause quorum to be declared with a single vote, forging a Peras certificate and bypassing the quorum requirement entirely.

---

### Finding Description

**Root cause — `stakeAboveThreshold`:** [1](#0-0) 

The function performs a direct numeric comparison:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

The quorum threshold is the relative value `3/4 = 0.75` (plus a safety margin of `2/100`), giving an effective threshold of `0.77`. [2](#0-1) 

The `PerasVoteStake` fed into this comparison comes from `validatePerasVote`, which is an explicit stub that performs no cryptographic validation and simply looks up the voter's entry in `PerasVoteStakeDistr`: [3](#0-2) 

The code itself documents that the normalization step is unresolved: [4](#0-3) 

Because "there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee", the `PerasVoteStakeDistr` is populated with raw ledger stake values (e.g., lovelace amounts). A voter holding even 1 lovelace has `PerasVoteStake = 1`, and `1 >= 0.77` is `True`. Quorum is declared on the first vote.

**Reachable call chain:**

An inbound vote from an unprivileged peer enters via `processVotes`: [5](#0-4) 

After passing the stub `validatePerasVote`, the vote is stored and aggregated: [6](#0-5) 

`updateCandidateVoteState` then calls `votesReachQuorum`: [7](#0-6) 

`votesReachQuorum` calls `stakeAboveThreshold` with the unnormalized total: [8](#0-7) 

When `stakeAboveThreshold` returns `True`, `forgePerasCert` is called immediately, producing a `ValidatedPerasCert` that is returned as `AddedPerasVoteAndGeneratedNewCert`: [9](#0-8) 

---

### Impact Explanation

A single crafted `PerasVote` message from any peer whose `PerasVoterId` appears in the stake distribution (with any positive absolute stake) causes the node to immediately forge a Peras certificate for an attacker-chosen block. That certificate carries a `PerasWeight` boost (default: 15) applied during chain selection, causing honest nodes to prefer the adversarially boosted chain. This is a direct bypass of the Peras voting/certificate quorum check — the security property that requires ≥ 3/4 of committee stake to agree before a certificate is issued.

---

### Likelihood Explanation

The attack requires only:
1. The attacker's `PerasVoterId` (a `KeyHash StakePool`) appears in the `PerasVoteStakeDistr` with any positive stake value.
2. The attacker sends one well-formed `PerasVote` message over the object-diffusion mini-protocol.

No cryptographic key material is required because `validatePerasVote` is a stub that performs no signature or eligibility verification. [10](#0-9) 

This is reachable on any private testnet or local reproduction running the current codebase.

---

### Recommendation

1. **Normalize before comparing.** Before calling `stakeAboveThreshold`, divide each voter's absolute ledger stake by the total stake in the distribution to produce a value in `[0, 1]`. Alternatively, change `stakeAboveThreshold` to accept the full `PerasVoteStakeDistr` and perform normalization internally, as the TODO comment already suggests.

2. **Implement real vote validation.** Replace the stub `validatePerasVote` with actual BLS signature verification and VRF-based eligibility proof verification (the infrastructure for which already exists in `Ouroboros.Consensus.Committee.WFALS` and `Ouroboros.Consensus.Peras.Crypto.BLS`) before the Peras vote path is enabled on any network.

---

### Proof of Concept

On a private testnet with Peras object diffusion enabled:

1. Obtain any `PerasVoterId` (pool key hash) present in the current `PerasVoteStakeDistr` with positive absolute stake (e.g., 1,000,000 lovelace).
2. Construct a `PerasVote { pvVoteRound = r, pvVoteBlock = targetBlock, pvVoteVoterId = victimId }` for any desired block.
3. Submit it via the Peras vote mini-protocol to a node.
4. Because `validatePerasVote` does not check signatures, the vote passes validation with `vpvVoteStake = 1000000`.
5. `stakeAboveThreshold` evaluates `1000000 >= 0.77` → `True`.
6. `forgePerasCert` is called; the node emits `AddedPerasVoteAndGeneratedNewCert cert`.
7. The certificate boosts `targetBlock` by `PerasWeight 15` in chain selection on that node.
