### Title
Arithmetic Underflow Panic in `check_withdraw_psbt` via Crafted PSBT Outputs — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

An unprivileged user can trigger an arithmetic underflow panic in `check_withdraw_psbt` by supplying a PSBT whose outputs sum to more than the referenced input UTXOs. With `overflow-checks = true` in the release profile, the bare subtraction at line 238 panics instead of returning a clean error. The panic is reachable through the fully public `ft_transfer_call → ft_on_transfer → create_btc_pending_info → check_withdraw_psbt_valid → check_withdraw_psbt` path.

---

### Finding Description

In `contracts/satoshi-bridge/src/psbt.rs`, `check_withdraw_psbt` computes:

```rust
let gas_fee = total_input_amount - total_output_amount;   // line 238
```

`total_input_amount` is fixed by the bridge's own UTXO set (derived from `vutxos`). `total_output_amount` is accumulated from attacker-supplied PSBT outputs. The output-validation loop (lines 192–215) enforces per-output constraints but **no constraint on the sum of all outputs relative to the total input amount**:

- Each change output must be `< min_input_amount` (the smallest single input UTXO).
- There is no guard that `total_output_amount <= total_input_amount` before the subtraction.

**Concrete example** — bridge has one UTXO of 1 000 sats (`min_input_amount = 1 000`):

| Output | Script | Value | Passes per-output check? |
|--------|--------|-------|--------------------------|
| 1 | target address | 900 sats | ✓ (target output) |
| 2 | change address | 999 sats | ✓ (999 < 1 000) |

`total_output_amount = 1 899 > total_input_amount = 1 000` → subtraction panics.

The `change_num <= max_change_number` guard that could limit multiple change outputs lives in `check_withdraw_psbt_valid` (line 44–47 of `psbt.rs`), which is called **after** `check_withdraw_psbt` returns — it is never reached. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

`overflow-checks = true` is confirmed in the workspace release profile: [5](#0-4) 

---

### Impact Explanation

**Severity: Low.**

The panic propagates up through `ft_on_transfer`. Under NEP-141 `ft_transfer_call` semantics, when `ft_on_transfer` panics the token contract's `ft_resolve_transfer` treats the used amount as 0 and **refunds the full nBTC amount to the sender**. The nBTC contract delegates directly to `near-contract-standards`' `internal_ft_resolve_transfer`, which implements this standard refund behaviour: [6](#0-5) 

Additionally, because the panic occurs within a single NEAR receipt, **all state mutations made earlier in the same call** (including the UTXO removal performed by `generate_vutxos`) are atomically reverted. Bridge UTXOs are not lost.

The net result is:
- The withdrawal fails with a panic instead of a clean `require!` error.
- The user's nBTC is refunded by the NEP-141 resolver.
- Bridge UTXO state is unchanged.
- No funds are lost or locked.

The impact is a publicly reachable invariant violation (panic instead of graceful rejection) in a production bridge path, without direct theft — matching the **Low** tier of the allowed impact scope.

---

### Likelihood Explanation

Any account holding nBTC can trigger this by calling `nbtc.ft_transfer_call` with a `Withdraw` message whose outputs sum to more than the referenced input UTXOs. No privileged role is required. The attacker recovers their nBTC via the NEP-141 refund, so the cost is only NEAR gas. Likelihood is **High** for the panic itself, but the absence of fund loss keeps overall severity Low.

---

### Recommendation

Add an explicit guard before the subtraction in `check_withdraw_psbt`:

```rust
require!(
    total_output_amount <= total_input_amount,
    format!(
        "Total output amount ({}) exceeds total input amount ({})",
        total_output_amount, total_input_amount
    )
);
let gas_fee = total_input_amount - total_output_amount;
```

This converts the panic into a clean, user-readable rejection consistent with all other validation in the function. [7](#0-6)

### Proof of Concept

1. Bridge has one UTXO: `txid=AAAA…, vout=0, amount=1_000 sats`.
2. Attacker holds ≥ `min_withdraw_amount` nBTC.
3. Attacker calls `nbtc.ft_transfer_call(bridge, amount, msg)` where `msg` is:
   ```json
   {"Withdraw": {
     "target_btc_address": "<valid target>",
     "input": [{"txid": "AAAA…", "vout": 0}],
     "output": [
       {"value": 900, "script_pubkey": "<target script>"},
       {"value": 999, "script_pubkey": "<change script>"}
     ],
     "max_gas_fee": null,
     "chain_specific_data": null
   }}
   ```
4. Execution path: `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`.
5. At line 238: `1_000 - 1_899` overflows → panic with `overflow-checks = true`.
6. `ft_resolve_transfer` refunds the attacker's nBTC. Assert: no `require!` fires before the subtraction for the sum-exceeds-input case. [8](#0-7) [9](#0-8)
