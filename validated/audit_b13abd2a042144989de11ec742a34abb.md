### Title
Peras Vote and Certificate Validation Bypass via Stub `validatePerasVote`/`validatePerasCert` Always Accepting Any Input — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance implements `validatePerasVote` and `validatePerasCert` as stubs that skip all cryptographic and structural validation. `validatePerasVote` accepts any vote whose voter ID appears in the stake distribution without verifying a signature. `validatePerasCert` unconditionally returns success for every certificate. An unprivileged peer can exploit this to forge votes for any staked voter, manufacture a quorum, and produce a certificate that boosts an arbitrary block in chain selection — directly analogous to the airdrop's missing finalization check that allowed premature and repeated claims.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` provides stub implementations for both vote and certificate validation:

**`validatePerasVote` — no signature check:** [1](#0-0) 

The function accepts any vote as long as the `pvVoteVoterId` field resolves to an entry in the stake distribution. No cryptographic proof of authorship is required. The `PerasVote` data type in this instance carries no signature field at all: [2](#0-1) 

**`validatePerasCert` — unconditional success:** [3](#0-2) 

Every certificate, regardless of content, is wrapped in `Right ValidatedPerasCert` and returned as valid.

Both stubs carry explicit `TODO` comments acknowledging the missing validation, referencing issue `#120`: [4](#0-3) 

The `implAddVote` function in `PerasVoteDB/Impl.hs` carries the same acknowledgement: [5](#0-4) 

The inbound vote processing pipeline in `ObjectPool/PerasVote.hs` calls `validatePerasVote` as the sole gate before adding votes to the database: [6](#0-5) 

Once votes pass this gate, `implAddVote` accumulates them into `pvdsRoundVoteStates` and calls `updatePerasRoundVoteStates`. When the accumulated stake crosses the quorum threshold, a certificate is forged and returned: [7](#0-6) 

The deduplication guard in `addOrIgnoreVote` only prevents the same `(roundNo, voterId)` pair from being inserted twice: [8](#0-7) 

Because there is no signature check, an attacker can submit one forged vote per staked voter per round, covering the entire stake distribution and trivially reaching quorum.

---

### Impact Explanation

**Critical — Bypass of Peras voting and certificate checks enabling unauthorized certificate acceptance.**

A forged certificate produced by this path is a `ValidatedPerasCert` carrying a `vpcCertBoost` weight. This boost is consumed by chain selection to prefer the certified block over competing candidates. An attacker who manufactures a quorum for an arbitrary block causes honest nodes to weight that block's chain above the canonical chain, constituting a chain-selection safety failure reachable by an unprivileged peer with no stake of their own.

---

### Likelihood Explanation

**High.** The catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` applies to every block type that has `StandardHash` unless a more specific instance is defined. The TODO comment explicitly states this is a degenerate placeholder "to get things to compile." No more specific `BlockSupportsPeras` instance for `CardanoBlock` was found in the searched scope. The inbound vote diffusion path (`makePerasVotePoolWriterFromChainDB` / `makePerasVotePoolWriterFromVoteDB`) is wired into the live node and is reachable by any connected peer.

---

### Recommendation

1. **`validatePerasVote`**: Implement full cryptographic signature verification against the voter's public key derived from the stake distribution. The `PerasVote` data type must carry a signature field; votes without a valid signature must be rejected with a typed `PerasValidationErr`.
2. **`validatePerasCert`**: Implement structural and cryptographic certificate verification (aggregate signature check, quorum threshold check, round/block consistency) before wrapping in `ValidatedPerasCert`.
3. **`implAddVote`**: Resolve the noted TODO and add any additional per-vote invariant checks (e.g., round bounds, block point reachability) before accumulating votes toward quorum.
4. Replace the catch-all stub instance with a concrete `BlockSupportsPeras CardanoBlock` instance that provides real implementations.

---

### Proof of Concept

1. Attacker connects to an honest node as a peer via the ObjectDiffusion mini-protocol for Peras votes.
2. Attacker reads the current `PerasVoteStakeDistr` (publicly available via the ledger state query interface) to enumerate all staked voter IDs.
3. For a target round `r` and a chosen block point `p` (e.g., the attacker's own fork tip), the attacker constructs `PerasVote { pvVoteRound = r, pvVoteBlock = p, pvVoteVoterId = v }` for each voter `v` in the stake distribution — no private key required.
4. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote` for each crafted vote. Because `lookupPerasVoteStake` finds `v` in the distribution, every vote returns `Right ValidatedPerasVote`.
5. Each validated vote is timestamped and passed to `addVote` / `ChainDB.addPerasVoteWithAsyncCertHandling`.
6. `implAddVote` → `updatePerasRoundVoteStates` accumulates stake. Once total stake exceeds the quorum threshold, `VoteGeneratedNewCert cert` is returned and the certificate is stored.
7. The certificate boosts block `p` in chain selection. The honest node now prefers the attacker's fork, diverging from the canonical chain. [9](#0-8) [10](#0-9)

```haskell
-- | Process a batch of inbound Peras votes received from a peer.
--
-- Votes whose ID is already present in the database (as determined by
-- @alreadyInDbSTM@) are silently skipped. The remaining votes are validated;
-- if /any/ vote in the batch fails validation, the entire batch is rejected
-- by throwing a 'PerasVoteInboundException' (which should make us disconnect
-- from the distant peer, see 'withPeer' bracket function from
-- `ouroboros-network`). Otherwise, each valid vote is timestamped with the
-- current wall-clock time and added to the database via @addVote@.
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
