Audit Report

## Title
Missing Re-Check of `finalised_transfers` in `fast_fin_transfer_to_near_callback` Enables Double-Spend — (File: near/omni-bridge/src/lib.rs)

## Summary

`fast_fin_transfer` (NEAR recipient path) checks `finalised_transfers` as a guard but returns without writing to `fast_transfers`, deferring that write to `fast_fin_transfer_to_near_callback`. During the async window between these two NEAR receipts, `fin_transfer_callback` → `process_fin_transfer_to_near` can execute, find `fast_transfers` empty, send bridge-minted/unlocked tokens to the original recipient, and write to `finalised_transfers`. When `fast_fin_transfer_to_near_callback` subsequently executes, it does not re-check `finalised_transfers`, calls `add_fast_transfer` (which only checks `fast_transfers`, now still empty), and sends the relayer's pre-funded tokens to the same recipient a second time, producing a double-spend.

## Finding Description

**Root cause — no re-check of `finalised_transfers` in the callback:**

`fast_fin_transfer` performs its only guard at lines 778–780:

```rust
if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
```

For a NEAR recipient it then builds an async promise chain (lines 812–827) and returns. `fast_transfers` is **not written** at this point.

`fast_fin_transfer_to_near_callback` (lines 838–893) contains no call to `is_unified_transfer_finalised`. Its only uniqueness guard is `add_fast_transfer` (lines 854–856), which checks only the `fast_transfers` map:

```rust
require!(
    self.fast_transfers.insert(...).is_none(),
    BridgeError::FastTransferAlreadyPerformed.as_ref()
);
```

`process_fin_transfer_to_near` (lines 1875–1901) calls `add_fin_transfer` first (line 1875), writing to `finalised_transfers`, then reads `fast_transfers` (line 1879). If `fast_transfers` is empty it sends tokens to the original recipient and the transfer is marked finalized.

**Race sequence (NEAR async model):**

| Receipt | Action | State after |
|---------|--------|-------------|
| R1 | `fast_fin_transfer` → guard passes, promise chain scheduled | `fast_transfers` = ∅, `finalised_transfers` = ∅ |
| R2 | `fin_transfer` submitted with valid proof | — |
| R3 | `fin_transfer_callback` → `process_fin_transfer_to_near` → `fast_transfers` = ∅ → **sends bridge tokens to recipient** → `add_fin_transfer` writes to `finalised_transfers` | `finalised_transfers` = {id}, `fast_transfers` = ∅ |
| R4 | `fast_fin_transfer_to_near_callback` → `add_fast_transfer` succeeds (no entry in `fast_transfers`) → **sends relayer tokens to recipient again** | `fast_transfers` = {id} |

The two maps are checked and written in separate receipts with no cross-map re-validation.

## Impact Explanation

Double-spending of bridged funds: the recipient receives tokens twice — once from the bridge's locked/minted supply via `process_fin_transfer_to_near`, and once from the relayer's pre-funded balance via `fast_fin_transfer_to_near_callback`. This directly matches the Critical impact class: *stealing, loss, double-spending, or unauthorized minting of bridged funds*.

## Likelihood Explanation

Any party holding a valid cross-chain proof (including the recipient themselves) can call `fin_transfer` immediately after observing `fast_fin_transfer` on-chain. NEAR's async receipt model guarantees a multi-receipt window between `fast_fin_transfer` and its callback. The attack requires no special privileges, no validator collusion, and no key compromise — only the ability to submit a standard `fin_transfer` call with a legitimately obtained proof. It is repeatable for every transfer that uses the fast-finalization path.

## Recommendation

Add a re-check of `is_unified_transfer_finalised` at the top of `fast_fin_transfer_to_near_callback`, before `add_fast_transfer` is called. If the transfer has already been finalized (i.e., `process_fin_transfer_to_near` ran first), the callback must panic and refund the relayer rather than proceed with token delivery. Alternatively, write a sentinel entry to `fast_transfers` synchronously inside `fast_fin_transfer` (before the promise is created) so that `process_fin_transfer_to_near` can detect the in-flight fast transfer and redirect funds to the relayer even before the callback executes.

## Proof of Concept

1. Deploy the bridge on a local NEAR sandbox.
2. Register a token and bind it across chains.
3. Submit a cross-chain transfer; obtain a valid proof.
4. Call `fast_fin_transfer` from a relayer account (NEAR recipient). Observe that `fast_transfers` is still empty after this call returns.
5. In the same block (before the callback receipt is processed), call `fin_transfer` with the valid proof from any account.
6. Allow all receipts to process in order: `fin_transfer_callback` executes first (R3 above), then `fast_fin_transfer_to_near_callback` (R4).
7. Check the recipient's token balance: it will be double the expected amount, confirming two independent token deliveries for the same transfer ID.
