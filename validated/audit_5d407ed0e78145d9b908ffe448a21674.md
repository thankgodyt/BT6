### Title
Peras Certificate and Vote Validation Stubs Accept All Inbound Objects Without Cryptographic Signature Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as an unconditional `Right` (no checks whatsoever) and implements `validatePerasVote` by checking only stake-distribution membership — a weaker "approval" check — without verifying the cryptographic signature on the vote. Both functions are called directly from network-facing inbound processing code (`processCerts`, `processVotes`). An unprivileged peer can therefore inject arbitrary forged Peras certificates and votes that are accepted into the ChainDB, bypassing all cryptographic authorization.

---

### Finding Description

The catch-all instance in `SupportsPeras.hs` provides the live implementations of `validatePerasCert` and `validatePerasVote` that are wired into the production object-diffusion pipeline:

**`validatePerasCert` — unconditional acceptance:**
```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```
Every certificate received from every peer is returned as `Right` — no round-number bounds check, no quorum proof, no aggregate-signature verification.

**`validatePerasVote` — membership check only, no signature:**
```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```
A vote is accepted if and only if the claimed `pvVoteVoterId` appears in the stake distribution. The BLS signature field `pvSignature` is never verified. Any peer that knows a pool's public key hash (which is public information) can forge votes on behalf of that pool.

These functions are called directly from the network-facing inbound handlers:

- `processCerts` in `PerasCert.hs` calls `validatePerasCert mkPerasParams` on every batch of certificates received from a peer.
- `processVotes` in `PerasVote.hs` calls `validatePerasVote mkPerasParams sd vote` on every batch of votes received from a peer.

Accepted objects are then added to the ChainDB via `ChainDB.addPerasCertAsync` and `ChainDB.addPerasVoteWithAsyncCertHandling`, where they influence chain selection through the Peras weight-boost mechanism.

The structural parallel to M-12 is exact: M-12 accepted NFT operations based on ERC-721 *approval* (a weaker permission) rather than *ownership* (actual custody). Here, `validatePerasVote` accepts votes based on *stake-distribution membership* (a weaker "approval" — the pool is registered) rather than *possession of the BLS signing key* (actual ownership). `validatePerasCert` is even weaker: it performs no check at all.

---

### Impact Explanation

A malicious peer can:

1. **Forge Peras certificates** for arbitrary rounds and arbitrary block targets. Because `validatePerasCert` always returns `Right`, every forged certificate is stored in the ChainDB and its `vpcCertBoost` weight is applied to chain selection. An attacker can manufacture a certificate that boosts a minority or adversarial chain above the honest chain, causing an honest node to switch to a non-canonical chain.

2. **Forge Peras votes** for any pool whose key hash appears in the current stake distribution (all registered pools are public). Because `validatePerasVote` never checks the BLS signature, an attacker can submit votes attributed to high-stake pools, manufacture a false quorum, trigger certificate forging from those fake votes, and again distort chain selection.

Both paths lead to **unauthorized Peras certificate acceptance**, which is explicitly listed in the allowed impact scope as a Critical finding: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

- The entry path is a standard peer-to-peer mini-protocol connection. Any node on the network that speaks the Peras object-diffusion protocol can send crafted certificate or vote batches.
- No stake, no keys, and no privileged access are required. The attacker only needs to know pool key hashes, which are published on-chain.
- The stub implementations are wired into the live `processCerts`/`processVotes` pipeline with no feature flag or guard that would disable them in production builds.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation — verify the aggregate BLS signature over the claimed round number and boosted block hash against the aggregate public key derived from the committee members listed in the certificate, and check that the certificate's round number is within the expected window.

2. **`validatePerasVote`**: After confirming stake-distribution membership, verify the BLS signature `pvSignature` against the voter's public key and the canonical vote message `(pvRoundNo, pvBoostedBlock)`. For non-persistent committee members, also verify the VRF eligibility proof `pvEligibilityProof`.

3. Until full validation is implemented, gate the Peras object-diffusion handlers behind a feature flag so that the stub code is not reachable in production deployments.

---

### Proof of Concept

**Forged certificate injection:**

```
1. Attacker connects to an honest node via the Peras certificate mini-protocol.
2. Attacker constructs:
     cert = PerasCert { pcCertRound = <current round>, pcCertBoostedBlock = <attacker's block> }
3. Attacker sends [cert] to the honest node.
4. processCerts calls validatePerasCert mkPerasParams cert
   → returns Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
   (no signature, no quorum proof checked)
5. ChainDB.addPerasCertAsync stores the certificate.
6. Chain selection applies the weight boost to the attacker's block,
   causing the honest node to prefer the attacker's chain.
```

**Forged vote injection (leading to false quorum):**

```
1. Attacker enumerates registered pool key hashes from the on-chain stake distribution.
2. For each pool hk_i with stake σ_i, attacker constructs:
     vote_i = PerasVote { pvVoteRound = R, pvVoteBlock = <attacker's block>,
                          pvVoteVoterId = hk_i,
                          pvSignature = <arbitrary bytes> }
3. Attacker sends [vote_1 .. vote_n] to the honest node.
4. processVotes calls validatePerasVote for each vote_i:
   → lookupPerasVoteStake succeeds (hk_i is in the distribution)
   → BLS signature is never checked
   → vote_i accepted with stake σ_i
5. Once Σ σ_i exceeds the quorum threshold, votesReachQuorum returns Just,
   a certificate is forged for the attacker's block, and chain selection
   boosts that block's weight.

-- | Process a batch of inbound Peras certificates received from a peer.
--
-- Certificates whose round number is already present in the database (as
-- determined by @alreadyInDbSTM@) are silently skipped. The remaining
-- certificates are validated; if /any/ certificate in the batch fails
-- validation, the entire batch is rejected by throwing a
-- 'PerasCertInboundException' (which should make us disconnect from the distant
-- peer, see 'withPeer' bracket function from `ouroboros-network`). Otherwise,
-- each valid certificate is timestamped with the current wall-clock time and
-- added to the database via @addCert@.
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
