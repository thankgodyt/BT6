### Title
Rounding-Down in `normalize_amount` Allows Permanent Freezing of Bridged Funds — (`near/omni-bridge/src/lib.rs`)

### Summary

The `normalize_amount` helper uses floor (integer) division to scale a token amount from its NEAR-side decimal representation to its origin-chain decimal representation. When a user initiates a transfer with an amount smaller than the scaling factor (`10^(origin_decimals - decimals)`), `normalize_amount` returns `0`. The tokens are already locked/burned on NEAR at this point. The only downstream guard (`amount_to_transfer > 0` in `sign_transfer`) causes the relayer's signing call to revert, but does **not** refund the user. No cancel/refund path was found in the codebase, leaving the funds permanently frozen in the bridge contract.

---

### Finding Description

`normalize_amount` performs floor division: [1](#0-0) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 18` and `decimals = 6`, `diff_decimals = 12`. Any `amount < 10^12` normalizes to `0`.

The `init_transfer` path (called from `ft_on_transfer`) locks/burns the user's tokens and stores the `TransferMessage`, but only validates that `fee < amount`: [2](#0-1) 

It does **not** check whether `normalize_amount(amount - fee) > 0` before locking funds.

The zero-amount guard exists only in `sign_transfer`, which is called later by a trusted relayer: [3](#0-2) 

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

When this `require!` fires, the transaction reverts, but the `TransferMessage` is **not** removed and the locked tokens are **not** returned. The transfer is permanently stuck.

---

### Impact Explanation

Bridged funds are permanently frozen in the NEAR bridge contract. The user's tokens are locked/burned on NEAR with no corresponding mint/unlock on the destination chain, and no recovery path. This matches the allowed impact: *"permanent freezing of bridged funds."*

---

### Likelihood Explanation

Any user who sends a token amount below the decimal-scaling threshold triggers this. For a token with 12 decimal difference (e.g., 18 origin / 6 NEAR), any transfer of less than `10^12` base units (i.e., less than `0.000001` of the token in 18-decimal terms) normalizes to zero. This is reachable by an ordinary user making a small or dust transfer, not just a sophisticated attacker.

---

### Recommendation

Add a normalization check inside `init_transfer` (before locking tokens), mirroring the pattern from the Surge Protocol fix — reject the transfer early rather than after funds are already escrowed:

```rust
let normalized = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0).expect("fee < amount already checked"),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This ensures the revert happens before any token lock/burn, so no funds are at risk.

---

### Proof of Concept

1. A token is registered with `origin_decimals = 18`, `decimals = 6` (diff = 12).
2. User calls `ft_on_transfer` transferring `amount = 500_000_000_000` (< `10^12`) with `fee = 0`.
3. `init_transfer` passes the `fee < amount` check and locks the tokens.
4. Relayer calls `sign_transfer`; `normalize_amount(500_000_000_000, {18,6})` = `500_000_000_000 / 10^12` = `0`.
5. `require!(amount_to_transfer > 0, ...)` panics; transaction reverts.
6. `TransferMessage` remains in storage; tokens remain locked with no refund path. [4](#0-3) [3](#0-2) [2](#0-1)
