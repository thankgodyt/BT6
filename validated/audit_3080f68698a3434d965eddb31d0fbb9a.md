### Title
Fee Bypass via Integer Division Truncation When `fee_min` Is Zero — (File: `contracts/satoshi-bridge/src/config.rs`)

---

### Summary

The `BridgeFee::get_fee` function computes fees using integer division. When `fee_min = 0` and `fee_rate > 0`, any deposit or withdrawal whose satoshi amount is below `MAX_RATIO / fee_rate` produces a fee of exactly zero due to truncation. The `assert_valid()` function does not enforce a relationship between `fee_min` and `fee_rate`, and `min_deposit_amount` / `min_withdraw_amount` are independent config values that are not constrained to exceed the truncation threshold. A user who controls the deposited BTC amount can therefore deliberately stay below the truncation threshold and pay no fee at all.

---

### Finding Description

`BridgeFee::get_fee` is defined as:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
``` [1](#0-0) 

`MAX_RATIO` is `10000`. When `fee_min = 0` and `fee_rate > 0`, the expression `amount * fee_rate / MAX_RATIO` truncates to `0` for any `amount < MAX_RATIO / fee_rate`. The `std::cmp::max` then returns `max(0, 0) = 0`, so the caller pays no fee.

The deposit path calls this directly:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
``` [2](#0-1) 

The only guard against tiny deposits is `min_deposit_amount`, but that threshold is configured independently and is not required to exceed `MAX_RATIO / fee_rate`:

```rust
if deposit_amount < config.min_deposit_amount {
    // unavailable UTXO path — no minting
} else {
    let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
``` [3](#0-2) 

`BridgeFee::assert_valid()` only checks that `fee_rate < MAX_RATIO` and `protocol_fee_rate <= MAX_RATIO`; it does **not** enforce `fee_min > 0` when `fee_rate > 0`, nor does it enforce `fee_min >= MAX_RATIO / fee_rate`:

```rust
pub fn assert_valid(&self) {
    require!(self.fee_rate < MAX_RATIO, "Invalid fee_rate");
    require!(
        self.protocol_fee_rate <= MAX_RATIO,
        "Invalid protocol_fee_rate"
    );
}
``` [4](#0-3) 

The same pattern applies to the withdrawal path: `withdraw_bridge_fee.get_fee(amount)` is called in `create_btc_pending_info`, and `min_withdraw_amount` is checked independently in `ft_on_transfer`. [5](#0-4) [6](#0-5) 

---

### Impact Explanation

When an operator configures `fee_rate > 0` with `fee_min = 0` (a plausible configuration when a percentage-only fee model is intended), any user who deposits or withdraws an amount below `MAX_RATIO / fee_rate` satoshis pays zero fee. The bridge mints the full deposited amount with no fee deducted, permanently bypassing the protocol's fee policy for those transactions. This maps to **Medium — bypass of bridge fee policy**.

---

### Likelihood Explanation

The default `deposit_bridge_fee` in the unit environment already has `fee_min = 0`:

```rust
deposit_bridge_fee: BridgeFee {
    fee_min: 0,
    fee_rate: 0,
    protocol_fee_rate: 9000,
},
``` [7](#0-6) 

If an operator later enables percentage fees by setting `fee_rate > 0` via `update_config` without also setting `fee_min`, the vulnerability is immediately live. The `ConfigUpdate` path applies changes and calls `assert_valid()`, which does not catch this misconfiguration. [8](#0-7) 

Bitcoin satoshi amounts are user-controlled (the user chooses how much BTC to send to the deposit address), so an attacker can deliberately craft a deposit at exactly `min_deposit_amount` satoshis and, if that value is below `MAX_RATIO / fee_rate`, receive a full mint with zero fee.

---

### Recommendation

1. Add a validation in `BridgeFee::assert_valid()` that requires `fee_min >= MAX_RATIO / fee_rate` (or equivalently, `fee_min * MAX_RATIO >= fee_rate`) whenever `fee_rate > 0`, ensuring the minimum fee always covers the truncation threshold.
2. Alternatively, add a check in `get_fee` that returns an error (or panics) if the computed fee is zero but `fee_rate > 0`, mirroring the fix suggested in the referenced report.
3. Document and enforce that `min_deposit_amount` must exceed `MAX_RATIO / fee_rate` when a non-zero `fee_rate` is configured.

---

### Proof of Concept

Assume operator sets `deposit_bridge_fee = BridgeFee { fee_min: 0, fee_rate: 5, protocol_fee_rate: 9000 }` (0.05% fee) and `min_deposit_amount = 1000` satoshis.

- Truncation threshold: `MAX_RATIO / fee_rate = 10000 / 5 = 2000` satoshis.
- Attacker deposits exactly `1000` satoshis (above `min_deposit_amount`, so the normal mint path is taken).
- `deposit_fee = 1000 * 5 / 10000 = 0` (truncates to zero).
- `mint_amount = 1000 - 0 = 1000`.
- Attacker receives `1000` nBTC with zero fee deducted. [1](#0-0) [9](#0-8)
