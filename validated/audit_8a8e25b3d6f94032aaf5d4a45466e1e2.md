Audit Report

## Title
Detached `send_tokens` with prior state mutation in `utxo_fin_transfer_fast` causes unrecoverable loss of relayer's fronted tokens — (`near/omni-bridge/src/lib.rs`)

## Summary

`utxo_fin_transfer_fast` unconditionally removes or marks the fast-transfer record as finalised before attempting to repay the relayer, and the repayment call is `.detach()`ed with no callback or rollback path. If `send_tokens` fails for any reason, the fast-transfer record is permanently gone and the relayer's fronted tokens are unrecoverable. The developers explicitly acknowledged this unresolved risk with a `// TODO` comment at the call site.

## Finding Description

In `utxo_fin_transfer_fast` (lib.rs:2518–2561):

**Step 1 — Irreversible state mutation (lines 2529–2540):**
For NEAR-destination transfers, `remove_fast_transfer` is called at line 2530, permanently deleting the record. For other-chain destinations, `mark_fast_transfer_as_finalised` is called at line 2533. Both mutations are unconditional and occur before any repayment attempt.

**Step 2 — Fire-and-forget repayment (lines 2542–2548):**
`send_tokens` is called and immediately `.detach()`ed. Its result is never observed. There is no `.then(callback)` to restore state on failure, unlike the analogous `fast_fin_transfer_to_near_callback` path (lines 877–892) which correctly chains a `resolve_fast_transfer` callback.

**Step 3 — Developer acknowledgement (line 2484):**
The call site in `utxo_fin_transfer` contains an explicit `// TODO: check how to deal with failed send_tokens` comment, confirming the unresolved failure case.

**Step 4 — Trigger path:**
The BTC connector (gated by `sender_id == &config.connector`, lines 2471–2474) calls `ft_transfer_call` with a matching UTXO payload. This is a normal production path triggered by real Bitcoin transaction finalization, not an admin-only operation.

`send_tokens` (lines 2056–2117) has multiple code paths. For deployed/bridged tokens (which BTC on NEAR is), it calls `mint` on the token contract. For native (non-deployed) tokens, it calls `ft_transfer`, which requires NEP-141 storage registration. Either path can fail: `mint` can fail if the token contract is paused, the bridge loses minting authority, or storage is required; `ft_transfer` fails if the relayer has no storage deposit. In all failure cases, the state has already been mutated with no rollback.

## Impact Explanation

When `send_tokens` fails after `remove_fast_transfer` or `mark_fast_transfer_as_finalised` has executed, the fast-transfer record is gone. There is no mechanism to re-attempt repayment or restore the record. The relayer permanently loses the BTC tokens they fronted for the fast transfer. This is a concrete, permanent loss of bridged funds — matching the Critical scope: *permanent loss of bridged funds across Bitcoin-routed flows*.

## Likelihood Explanation

The failure condition is realistic: NEP-141 `ft_transfer` requires storage registration; a relayer whose storage deposit has lapsed or was never registered for the specific BTC token will cause the inner transfer to panic. For the `mint` path, token contract pausing or loss of minting authority are operational conditions that have occurred on other bridges. The TODO comment confirms the developers are aware the failure case is unhandled. The trigger (BTC connector finalizing a UTXO) is a routine production event, not a contrived one.

## Recommendation

- Move `remove_fast_transfer` / `mark_fast_transfer_as_finalised` into a callback that executes only after `send_tokens` resolves successfully, following the pattern already used in `fast_fin_transfer_to_near_callback` (lines 877–892) which chains `resolve_fast_transfer`.
- Alternatively, keep the state mutation but add a recovery callback: on `send_tokens` failure, restore the fast-transfer record so the relayer can be repaid in a subsequent call.
- Verify or force the relayer's storage registration for the token before mutating fast-transfer state.

## Proof of Concept

1. Register a fast transfer for a UTXO ID where the relayer account (`relayer.near`) either (a) has no storage deposit for the BTC token (native token path) or (b) the BTC token contract is paused (deployed token path).
2. Have the BTC connector call `ft_transfer_call` with the matching UTXO data, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
3. Observe: `remove_fast_transfer` executes at line 2530 (fast-transfer record deleted from state).
4. Observe: `send_tokens(...).detach()` at lines 2542–2548 fires but the inner transfer fails (panic or revert inside the token contract).
5. Assert: fast-transfer record is gone; `relayer.near` token balance is unchanged. The relayer's fronted tokens are unrecoverable.
6. Confirm: calling `utxo_fin_transfer` again with the same UTXO data hits the non-fast path (no fast-transfer record exists), so no re-attempt of relayer repayment is possible. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    fn send_tokens(
        &self,
        token: AccountId,
        recipient: AccountId,
        amount: U128,
        msg: &str,
    ) -> Promise {
        let ft_transfer_call_gas = env::prepaid_gas()
            .saturating_sub(env::used_gas())
            .saturating_sub(SEND_TOKENS_CALLBACK_GAS) // TODO: not all send_tokens callbacks has the same gas.
            .saturating_sub(MINT_TOKEN_GAS)
            .min(FT_TRANSFER_CALL_GAS);

        let is_deployed_token = self.is_deployed_token(&token);

        if token == self.wnear_account_id && msg.is_empty() {
            // Unwrap wNEAR and transfer NEAR tokens
            ext_wnear_token::ext(self.wnear_account_id.clone())
                .with_static_gas(WNEAR_WITHDRAW_GAS)
                .with_attached_deposit(ONE_YOCTO)
                .near_withdraw(amount)
                .then(
                    Self::ext(env::current_account_id())
                        .with_static_gas(NEAR_WITHDRAW_CALLBACK_GAS)
                        .near_withdraw_callback(recipient, NearToken::from_yoctonear(amount.0)),
                )
        } else if is_deployed_token {
            let deposit = if msg.is_empty() {
                NO_DEPOSIT
            } else {
                ONE_YOCTO
            };

            require!(
                ft_transfer_call_gas >= MIN_FT_TRANSFER_CALL_GAS,
                BridgeError::NotEnoughGasForTokenTransfer(ft_transfer_call_gas).as_ref()
            );

            ext_token::ext(token)
                .with_attached_deposit(deposit)
                .with_static_gas(MINT_TOKEN_GAS.saturating_add(ft_transfer_call_gas))
                .mint(
                    recipient,
                    amount,
                    (!msg.is_empty()).then(|| msg.to_string()),
                )
        } else if msg.is_empty() {
            ext_token::ext(token)
                .with_attached_deposit(ONE_YOCTO)
                .with_static_gas(FT_TRANSFER_GAS)
                .ft_transfer(recipient, amount, None)
        } else {
            require!(
                ft_transfer_call_gas >= MIN_FT_TRANSFER_CALL_GAS,
                BridgeError::NotEnoughGasForTokenTransfer(ft_transfer_call_gas).as_ref()
            );

            ext_token::ext(token)
                .with_attached_deposit(ONE_YOCTO)
                .with_static_gas(ft_transfer_call_gas)
                .ft_transfer_call(recipient, amount, None, msg.to_string())
        }
