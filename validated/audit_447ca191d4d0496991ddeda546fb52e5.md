Audit Report

## Title
Dust Transfers Below Minimum Representable Unit Permanently Lock User Funds Due to Missing Normalization Validation in `init_transfer` - (File: near/omni-bridge/src/lib.rs)

## Summary

The `init_transfer` function accepts any transfer where `fee < amount` without verifying that `normalize_amount(amount - fee, decimals) > 0`. When a user initiates a transfer with an amount smaller than the scaling factor between origin and destination decimals, tokens are immediately locked or burned on NEAR inside `init_transfer_internal`, but the subsequent `sign_transfer` call always panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` because the normalized amount is zero. Since `sign_transfer` panics before reaching the MPC call, `sign_transfer_callback` never fires, the transfer message is never removed from `pending_transfers`, and no public cancel or refund function exists — resulting in permanent, irrecoverable loss of the bridged funds.

## Finding Description

`normalize_amount` uses floor division, truncating any sub-unit remainder: [1](#0-0) 

`sign_transfer` enforces that the normalized amount is non-zero before making the MPC call: [2](#0-1) 

However, `init_transfer` only checks `fee < amount` with no normalization guard: [3](#0-2) 

Tokens are locked or burned unconditionally inside `init_transfer_internal` before any normalization check can occur: [4](#0-3) 

`sign_transfer_callback` only removes the transfer message on a successful MPC response and only when `fee.is_zero()`. When `sign_transfer` panics (before the MPC call is ever dispatched), the callback never fires: [5](#0-4) 

No public `cancel_transfer` or refund function exists in the contract. The transfer message remains in `pending_transfers` indefinitely, and the locked/burned tokens have no recovery path.

## Impact Explanation

This constitutes permanent freezing of bridged funds, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows"* and *"decimal/normalization abuse … that changes user or protocol balances."* For any token pair where `origin_decimals > decimals` (e.g., a NEAR token with 24 decimals bridged to an EVM chain registered with 18 decimals, scaling factor `10^6`), any transfer of fewer than `10^6` base units results in a normalized amount of zero, permanently locking the user's tokens in escrow (native tokens) or permanently burning them (deployed bridge tokens) with no on-chain recovery mechanism.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` on a NEAR token with an amount below the scaling factor threshold. No special access or privileges are required. The decimal gap between NEAR tokens (commonly 24 decimals) and EVM tokens (commonly 6 or 18 decimals) creates scaling factors of `10^6` to `10^18`, meaning amounts below those thresholds silently round to zero. A user unfamiliar with decimal normalization, or one using a UI that does not enforce a minimum transfer amount, can accidentally trigger permanent fund loss. The condition is fully reachable through normal public contract calls.

## Recommendation

Add a normalization check inside `init_transfer` (or in `ft_on_transfer` before tokens are locked/burned) to verify that `normalize_amount(amount - fee, decimals) > 0` for the destination chain. The `token_decimals` mapping and destination chain are already available at that point. The guard that currently exists only in `sign_transfer` (lines 475–485) must be moved earlier, to `init_transfer`, before `init_transfer_internal` is called and tokens are locked or burned:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

## Proof of Concept

1. Register a NEAR token with `origin_decimals = 24`, `decimals = 18` for an EVM destination (scaling factor = `10^6`).
2. Call `ft_transfer_call` with `amount = 500_000` (below the `10^6` threshold) and `fee = 0`.
3. `init_transfer` accepts the transfer: `fee (0) < amount (500_000)` passes. [3](#0-2) 
4. `init_transfer_internal` stores the transfer message and locks 500,000 tokens in bridge escrow. [4](#0-3) 
5. A trusted relayer calls `sign_transfer` for this transfer ID.
6. `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 }) = 500_000 / 10^6 = 0`. [1](#0-0) 
7. `require!(amount_to_transfer > 0)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`; the MPC call is never dispatched. [6](#0-5) 
8. `sign_transfer_callback` never fires; the transfer message remains in `pending_transfers` forever; the 500,000 tokens are permanently locked with no recovery path. [5](#0-4)
