### Title
Peras Quorum Check Compares Incommensurable Units — `stakeAboveThreshold` Mixes Absolute Ledger Stake with Relative Threshold - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares the accumulated `PerasVoteStake` (a bare `Rational` that may carry absolute ledger-stake units) directly against `perasQuorumStakeThreshold` (a `Rational` that is defined as a relative/normalized fraction of total committee stake). The code itself documents this as an unresolved unit-mismatch problem. When the real Cardano ledger stake distribution is wired in to replace the current `PerasVoteStakeDistr mempty` placeholder, the comparison will be numerically wrong in the same way the external report's formula was wrong: the effective quorum threshold will be either trivially satisfied by a single vote (if absolute lovelace values >> 0.75) or permanently unsatisfiable (if the threshold is set as an absolute value while votes carry relative fractions).

---

### Finding Description

`PerasVoteStake` is declared as a bare `Rational` with an explicit NOTE that the correct unit conversion from ledger stake to committee vote weight is unresolved:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [1](#0-0) 

`stakeAboveThreshold` then directly compares the sum of these `PerasVoteStake` values against `perasQuorumStakeThreshold` (also a `Rational`), with a TODO explicitly warning that the comparison is only valid when both sides are in the same units:

> "this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units … Under the current implementation of 'PerasParams', this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

`votesReachQuorum` calls `stakeAboveThreshold` with the raw sum of `vpvVoteStake` fields from all votes, with no normalization step: [3](#0-2) 

`validatePerasVote` (the degenerate instance used for all blocks) simply looks up the stake from `PerasVoteStakeDistr` and assigns it verbatim to `vpvVoteStake`, performing no unit conversion: [4](#0-3) 

`PerasVoteStakeDistr` is a `Map PerasVoterId PerasVoteStake` with no invariant enforcing normalization: [5](#0-4) 

The production network handler currently passes `PerasVoteStakeDistr mempty` (empty map) as a placeholder, so all votes are currently rejected. The TODO comment confirms this will be replaced with real ledger data:



The WFALS committee implementation computes `VoteWeight` differently for persistent vs non-persistent members: persistent members receive their raw absolute ledger stake, while non-persistent members receive stake normalized by total non-persistent stake. This mixed representation makes the unit mismatch even more acute when the committee output is eventually fed into `PerasVoteStakeDistr`: [6](#0-5) 

---

### Impact Explanation

**Scenario A — absolute ledger stake fed into `PerasVoteStakeDistr`:**

If the ledger stake distribution is wired in with absolute lovelace values (e.g., a pool with 1 billion lovelace has `PerasVoteStake = 1_000_000_000`), and `perasQuorumStakeThreshold` is set to a relative value such as `3 % 4` (0.75), then:

```
stake (1_000_000_000) >= quorumThreshold (0.75) + safetyMargin
```

is trivially `True` for any voter with positive stake. A **single vote** from any committee member would satisfy `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to be called. An adversary who is a committee member can forge a Peras certificate for any block — including a minority or adversarial chain — with only their own vote, bypassing the intended ≥ 3/4 quorum requirement entirely. The forged certificate boosts that block's chain weight via `vpcCertBoost`, directly corrupting chain selection.

**Scenario B — relative threshold fed as absolute:**

If `perasQuorumStakeThreshold` is set to an absolute value (e.g., `750_000_000`) while votes carry relative fractions (e.g., `1 % 4`), the comparison `0.25 >= 750_000_000` is permanently `False`. No certificate is ever forged, disabling the Peras finality boost entirely.

Both scenarios constitute a bypass of the Peras certificate/vote verification check.

---

### Likelihood Explanation

The bug is currently latent because the production code passes `PerasVoteStakeDistr mempty`, causing all votes to be rejected at the `lookupPerasVoteStake` step before `stakeAboveThreshold` is ever reached. However:

1. The TODO comments in both `PerasVoteStake` and `stakeAboveThreshold` confirm this is a known open problem that will be resolved when real ledger plumbing is added.
2. The WFALS committee already computes `VoteWeight` in mixed units (absolute for persistent, normalized for non-persistent), making it likely that whoever wires up the real stake distribution will inadvertently pass absolute values.
3. The type system provides no protection: `PerasVoteStake`, `PerasQuorumStakeThreshold`, and `PerasQuorumStakeThresholdSafetyMargin` are all `newtype` wrappers over `Rational` with no phantom unit tags, so the compiler cannot catch the mismatch.
4. The entry path is fully unprivileged: any peer can send `PerasVote` messages over the `PerasVoteDiffusion` miniprotocol, which are processed by `makePerasVotePoolWriterFromChainDB` → `processVotes` → `validatePerasVote` → `stakeAboveThreshold`. [7](#0-6) 

---

### Recommendation

1. **Enforce units at the type level.** Introduce phantom-typed wrappers distinguishing absolute from relative stake, e.g.:
   ```haskell
   newtype AbsoluteStake = AbsoluteStake Rational
   newtype RelativeStake = RelativeStake Rational  -- invariant: in [0,1]
   ```
   Make `PerasVoteStake` carry `RelativeStake` and `PerasQuorumStakeThreshold` carry `RelativeStake`. The compiler will then reject any attempt to compare absolute values against the threshold.

2. **Normalize in `validatePerasVote`.** Change the `validatePerasVote` signature to accept the total committee stake alongside `PerasVoteStakeDistr`, and divide each voter's absolute stake by the total before storing it in `vpvVoteStake`.

3. **Alternatively, normalize in `stakeAboveThreshold`.** Accept the total committee stake as an additional parameter and perform the division inside the function, as the existing TODO suggests.

4. **Resolve the WFALS mixed-unit output.** The `implEligiblePartyVoteWeight` function returns absolute stake for persistent members and normalized stake for non-persistent members. This must be unified before the output is used to populate `PerasVoteStakeDistr`.

---

### Proof of Concept

The following illustrates the unit mismatch. With `mkPerasParams` defaults and a `PerasVoteStakeDistr` populated from a real ledger distribution (absolute lovelace), a single vote from a pool with 1 ADA (1,000,000 lovelace) would satisfy the quorum check:

```haskell
-- perasQuorumStakeThreshold mkPerasParams = some Rational like 3/4
-- A pool with 1 ADA absolute stake:
let voteStake = PerasVoteStake (1_000_000 % 1)
-- stakeAboveThreshold compares:
-- 1_000_000 >= (3/4) + safetyMargin
-- => True  (quorum "reached" with a single vote)
stakeAboveThreshold mkPerasParams voteStake  -- returns True
```

This is the direct analog of the external report's formula error: `votesReceived >= tokensRequested_ + _getSliceOfNonTreasury(minThresholdPercentage)` mixed absolute token amounts with percentage-of-different-base values, causing the required vote percentage to be far lower than intended. Here, `stake >= quorumThreshold` mixes absolute ledger units with a relative fraction, causing the quorum to be trivially satisfied. [8](#0-7) [9](#0-8)

implEligiblePartyVoteWeight ::
  VotingCommittee crypto WFALS ->
  EligibilityWitness crypto WFALS ->
  VoteWeight
implEligiblePartyVoteWeight committee = \case
  -- Persistent members have their voting power equal to their stake
  WFALSPersistentMember
    _seatIndex
    (LedgerStake stake) ->
      VoteWeight stake
  -- Non-persistent members have their voting power proportional to their
  -- number of seats granted by local sortition and their stake (normalized
  -- by the total non-persistent stake)
  WFALSNonPersistentMember
    _seatIndex
    (LedgerStake stake)
    _vrfOutput
    numSeats ->
      VoteWeight $
        fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
          * stake
          / nonPersistentStake
     where
      TotalNonPersistentStake (Cumulative (LedgerStake nonPersistentStake)) =
        totalNonPersistentStake committee
