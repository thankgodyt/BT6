### Title
Non-Strict Slot Inequality in PBFT `updateChainDepState` Enables Double-Signing at Epoch-Boundary Slots — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Protocol/PBFT.hs`)

---

### Summary

`updateChainDepState` in `PBFT.hs` uses a non-strict inequality (`>=`) to guard against out-of-order slots. The formal Byron specification uses a strict inequality (`<`), requiring each new regular block's slot to be **strictly greater** than the last signed slot. The discrepancy is explicitly flagged with an unresolved `FIXME` comment and is acknowledged in the `DualByron` test suite. It creates a reachable path by which a Byzantine PBFT delegate can insert two regular blocks at the same epoch-boundary slot — separated by an EBB — and have both accepted by the node.

---

### Finding Description

In `updateChainDepState` for `PBftValidateRegular` blocks:

```haskell
-- FIXME confirm that non-strict inequality is ok in general.
-- It's here because EBBs have the same slot as the first block of their
-- epoch.
unless (NotOrigin slot >= S.lastSignedSlot state) $
  throwError PBftInvalidSlot
``` [1](#0-0) 

The check accepts any block where `slot == lastSignedSlot`. `lastSignedSlot` is computed only from regular blocks — EBBs are processed via `PBftValidateBoundary` and return the state unchanged, so they never advance `lastSignedSlot`:

```haskell
lastSignedSlot :: PBftState c -> WithOrigin SlotNo
lastSignedSlot PBftState{..} =
  case inWindow of
    _ :|> signer -> NotOrigin (pbftSignerSlotNo signer)
    _otherwise -> Origin
``` [2](#0-1) [3](#0-2) 

The `validateEnvelope` layer independently enforces slot ordering, but it explicitly **permits** the same slot when the previous block is an EBB:

```haskell
minimumNextSlotNo _ (TipInfoIsEBB _ prevIsEBB) (TipInfoIsEBB _ curIsEBB) s =
  case (prevIsEBB, curIsEBB) of
    (IsEBB, IsNotEBB) -> s        -- EBB followed by regular: same slot OK
    _otherwise -> succ s
``` [4](#0-3) 

This means the two checks together create a gap: `validateEnvelope` allows `slot == prevSlot` when the predecessor is an EBB, and the PBFT check allows `slot == lastSignedSlot` due to `>=`. The combination permits a chain of the form:

```
regular_block(slot=S) → EBB(slot=S) → regular_block(slot=S)
```

where S is an epoch-boundary slot (`S mod epochSlots == 0`). The `additionalEnvelopeChecks` for Byron only rejects EBBs at non-boundary slots:

```haskell
when (fromIsEBB newIsEBB && not (canBeEBB actualSlotNo)) $
  throwError $ UnexpectedEBBInSlot actualSlotNo
 where
  canBeEBB (SlotNo s) = s `mod` epochSlots == 0
``` [5](#0-4) 

So an EBB at an epoch-boundary slot S is always structurally valid, even when a regular block at slot S already precedes it.

The `DualByron` test suite explicitly documents the spec/implementation divergence:

> "the PBFT implementation tests the slot progression with `<=` to accommodate EBBs whereas the executable STS spec uses `<`" [6](#0-5) 

The test works around this by discarding any run where a node forges in slot 0, because the spec would emit `PBFTFailure (SlotNotAfterLastBlock (Slot 0) (Slot 0))` while the implementation accepts it.

---

### Impact Explanation

A Byzantine PBFT delegate can craft and broadcast a chain containing two regular blocks at the same epoch-boundary slot, separated by an EBB. Both blocks carry valid PBFT signatures from the same delegate key. The node accepts the chain because:

1. `validateEnvelope` passes for the second regular block (EBB → regular at same slot is explicitly allowed).
2. The PBFT slot check passes because `slot >= lastSignedSlot` holds with equality.

This constitutes **double-signing** at the same slot — a direct violation of the PBFT invariant that each slot has at most one regular block. The accepted chain diverges from what the formal Byron specification would accept, breaking the cross-implementation consensus invariant. Additionally, the `pbftWindowExceedsThreshold` check may not catch this because two signings by the same key in a window of size `k` may not exceed the configured threshold (typically `floor(0.22 * k)`).

This maps to: **High — header-state bug that lets a peer make an honest node accept a chain that violates the protocol's security invariants.**

---

### Likelihood Explanation

The attack requires a Byzantine PBFT delegate key — one of the small set of genesis-delegated keys in the Byron era. This is not an unprivileged attacker, but it is a realistic threat model for a compromised or malicious core node operator. Epoch-boundary slots are deterministic and publicly known. The EBB is unsigned and can be constructed by anyone. Once the prerequisites are met, the attack is mechanical.

---

### Recommendation

Replace the non-strict inequality with a strict one:

```haskell
-- Before (line 350):
unless (NotOrigin slot >= S.lastSignedSlot state) $
  throwError PBftInvalidSlot

-- After:
unless (NotOrigin slot > S.lastSignedSlot state) $
  throwError PBftInvalidSlot
``` [1](#0-0) 

The `validateEnvelope` layer already handles the EBB edge case correctly via `minimumNextSlotNo` — it allows the same slot only when the predecessor is an EBB. The PBFT slot check does not need to duplicate this leniency; it should enforce strict monotonicity independently. If strict `>` is confirmed to break any legitimate chain configuration, the correct fix is to document the invariant precisely and add a targeted exception rather than leaving the inequality unconfirmed.

---

### Proof of Concept

**Setup**: Byron network, epoch size = E slots, adversary controls delegate key for slot S where `S mod E == 0`.

**Steps**:

1. Adversary signs `regular_block_A` at slot S. Chain: `... → regular_block_A(slot=S)`. `lastSignedSlot = S`.
2. Adversary constructs `EBB(slot=S)` (unsigned). Chain: `... → regular_block_A(slot=S) → EBB(slot=S)`. `lastSignedSlot` unchanged = S.
3. Adversary signs `regular_block_B` at slot S. Sends the chain to an honest node via ChainSync.
4. Node calls `validateHeader` on `regular_block_B`:
   - `validateEnvelope`: `oldTip` is `EBB(slot=S)`, `prevIsEBB = IsEBB`, `curIsEBB = IsNotEBB` → `minimumNextSlotNo` returns S → `actualSlotNo S >= expectedSlotNo S` ✓
   - `updateChainDepState`: `NotOrigin S >= lastSignedSlot S` → `S >= S` → True ✓ (would be False with strict `>`)
5. Node accepts the chain with two regular blocks at slot S. [7](#0-6) [8](#0-7)
