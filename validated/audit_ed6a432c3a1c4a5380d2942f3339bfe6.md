### Title
Stale Supply Snapshot in `migrate_to_new_token` Allows Newly Minted nBTC to Be Permanently Orphaned - (File: contracts/satoshi-bridge/src/nbtc/migration.rs)

### Summary

`internal_migrate_to_new_token` fires parallel cross-contract queries (`ft_total_supply` + `ft_balance_of` for each account) against the old token, then uses those results in a callback to mint equivalent balances on the new token. Because the bridge does not pause deposit processing during the async window between the query and the callback, a deposit that lands in that window mints new nBTC on the old token that is not captured in the snapshot. The `sum == total_supply` integrity check passes on the stale snapshot, the migration completes, and the newly minted tokens are permanently orphaned on the old token with no recovery path.

### Finding Description

`internal_migrate_to_new_token` issues all queries in one batch:

```rust
let mut queries = ext_nbtc::ext(old_token.clone())
    .with_static_gas(GAS_FOR_FT_QUERY)
    .ft_total_supply();
for account in &accounts {
    queries = queries.and(
        ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_balance_of(account.clone()),
    );
}
``` [1](#0-0) 

All queries execute atomically in the same block (block N). The callback `migrate_to_new_token_mint` runs in a later block. Between block N and the callback block, `verify_deposit` (or `verify_deposit_v2`) can be called by a trusted relayer for a user not in the `accounts` list, minting new nBTC on the old token.

In the callback, the integrity check is:

```rust
let total_supply = Self::parse_ft_result(0);
// ...
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [2](#0-1) 

Both `total_supply` and `sum` are from the stale block-N snapshot, so the check passes even though the actual old-token supply has grown. The migration then mints only the block-N balances on the new token and calls `migrate_to_new_token_resolve`, which switches `nbtc_account_id` to the new token:

```rust
self.internal_mut_config().nbtc_account_id = new_token.clone();
``` [3](#0-2) 

After this point:
- The bridge mints/burns exclusively on the new token.
- The newly deposited user holds nBTC on the old token that the bridge will never burn.
- The corresponding BTC UTXO is locked in the bridge's UTXO set (added during `mint_callback`).
- There is no on-chain recovery path; the user's BTC is permanently inaccessible without manual operator intervention.

`verify_deposit` has no migration-in-progress guard: [4](#0-3) 

And `migrate_to_new_token` does not pause the bridge or set any flag that would block concurrent deposits: [5](#0-4) 

### Impact Explanation

A user who sends BTC to the bridge during the migration window receives nBTC on the old token. After migration completes, that nBTC is worthless (the bridge will not accept it for withdrawal) and the backing BTC UTXO is permanently locked in the bridge. This is a permanent, irrecoverable loss of user funds without operator intervention, matching the **Medium** impact class: *stuck bridge state requiring operator intervention* and *permanent burning below backed supply*.

### Likelihood Explanation

The async window between the query receipt and the callback receipt spans at least one NEAR block (~1 second). On an active bridge, a relayer processing a queued deposit during this window is a realistic, non-adversarial event. No special attacker action is required — a normal user depositing BTC at an unfortunate moment is sufficient.

### Recommendation

Before firing the cross-contract queries, the bridge should atomically prevent new mints on the old token. The safest approach is to pause the bridge (or at minimum the deposit functions) before calling `migrate_to_new_token`, and unpause only after `migrate_to_new_token_resolve` completes. Alternatively, `internal_migrate_to_new_token` should set a migration-in-progress flag in contract state that `verify_deposit_callback` checks before minting, rejecting any mint attempt while migration is pending.

### Proof of Concept

1. Bridge has 10 holders with total nBTC supply = S on old token. Operator calls `migrate_to_new_token(new_token, [holder0..holder9])`.
2. Block N: queries fire — snapshot captures `total_supply = S`, `balance[i]` for each holder.
3. Block N+1: A relayer calls `verify_deposit` for a new user (charlie, not in the accounts list). `verify_deposit_callback` inserts charlie's UTXO into `verified_deposit_utxo` and calls `mint(charlie, Y)` on the old token. Old token supply becomes S + Y.
4. Block N+2: `migrate_to_new_token_mint` callback runs. `total_supply = S` (stale), `sum = S` (stale). Check passes. Mints S tokens across holders on new token.
5. `migrate_to_new_token_resolve` sets `nbtc_account_id = new_token`.
6. Charlie holds Y nBTC on old token. Bridge uses new token. Charlie cannot withdraw BTC (bridge burns from new token only). Charlie's Y BTC UTXO is permanently locked in the bridge's UTXO set.
