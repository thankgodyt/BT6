### Title
Missing Dust-Threshold Guard on Refund Output Allows Permanently Stuck Unbroadcastable Refund Transaction — (`contracts/satoshi-bridge/src/refund.rs` / `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

`request_refund_callback` only enforces `resolved_gas_fee < amount`; it does not enforce `amount - gas_fee >= 546` (Bitcoin P2WPKH dust threshold). An unprivileged attacker who deposits an amount in the narrow window `(max_btc_gas_fee, max_btc_gas_fee + 546)` satoshis can trigger a refund whose output value is 1–545 satoshis. `build_refund_output` creates that sub-dust `TxOut` without complaint, `finalize_refund_with_psbt` inserts it into `btc_pending_infos`, and after signing the resulting transaction is permanently rejected by every Bitcoin node as non-standard, leaving the UTXO locked and the pending-sign slot consumed.

---

### Finding Description

**Entry point — `request_refund` (public, unprivileged):**

`request_refund` is in a `#[trusted_relayer]` impl block, but the attribute is not repeated on the function itself (unlike `verify_deposit`, `verify_deposit_v2`, `verify_withdraw_v2`, etc., which all carry `#[trusted_relayer]` on the function). `execute_refund` in the same block is explicitly documented as callable by anyone after the timelock. The `gas_fee` parameter is restricted to DAO/Operator, but passing `None` is unrestricted. [1](#0-0) 

**Default gas fee = `max_btc_gas_fee`:**

When `gas_fee` is `None`, the resolved fee is `config.max_btc_gas_fee`. [2](#0-1) [3](#0-2) 

**Only guard in `request_refund_callback` is `resolved_gas_fee < amount`:**

There is no check that `amount - resolved_gas_fee >= 546`. [3](#0-2) 

**`refund_execution_inputs` only checks `refund_amount > 0`:**

A value of 1–545 satoshis passes this guard. [4](#0-3) 

**`build_refund_output` creates the `TxOut` with no dust check:**

The sub-dust value is written directly into the PSBT output. [5](#0-4) 

**`finalize_refund_with_psbt` inserts the pending info and marks the UTXO verified:**

The UTXO is added to `verified_deposit_utxo`, blocking any future `verify_deposit`, and the `BTCPendingInfo` is inserted into `btc_pending_infos`, consuming a pending-sign slot. [6](#0-5) 

**`min_deposit_amount` is not checked in the refund path:**

The config field exists but is only enforced during `verify_deposit`, not `request_refund_callback`. [7](#0-6) 

---

### Impact Explanation

After signing, the transaction has a P2WPKH output below 546 satoshis. Bitcoin's standardness rules reject such outputs at the mempool layer on every node. The transaction can never be broadcast or confirmed. The result:

- The deposit UTXO is permanently locked (`verified_deposit_utxo` prevents `verify_deposit`; the refund request stays with `executed = true` preventing re-execution with a different amount).
- The `BTCPendingInfo` slot is permanently occupied, consuming bridge pending-sign capacity.
- The user's BTC is permanently unrecoverable through the normal refund path.

This matches the **Low** allowed impact: "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

---

### Likelihood Explanation

The attack window is narrow: the deposit must fall in `(max_btc_gas_fee, max_btc_gas_fee + 546)` satoshis — a 545-satoshi range. `max_btc_gas_fee` is publicly readable from the contract config. The attacker must send a real on-chain Bitcoin transaction in that range and wait for confirmation and the refund timelock. This is low-effort for a motivated attacker (costs a few hundred satoshis) and can be repeated for each new deposit address path.

---

### Recommendation

Add a dust-threshold guard in `request_refund_callback` immediately after computing `resolved_gas_fee`:

```rust
const BTC_DUST_THRESHOLD: u128 = 546;
require!(
    amount.saturating_sub(resolved_gas_fee) >= BTC_DUST_THRESHOLD,
    "Refund amount after gas fee is below Bitcoin dust threshold"
);
```

Alternatively, add the same check in `refund_execution_inputs` alongside the existing `refund_amount > 0` guard: [4](#0-3) 

---

### Proof of Concept

1. Read `config.max_btc_gas_fee` from the contract (e.g., 50 000 satoshis).
2. Send a Bitcoin transaction paying `50 200` satoshis to the bridge deposit address derived from a chosen `deposit_msg`.
3. Wait for confirmation. Call `request_refund` with `gas_fee = None`. `request_refund_callback` checks `50 000 < 50 200` → passes. Stores `RefundRequest { amount: 50200, gas_fee: 50000 }`.
4. Wait for `unsafe_refund_timelock_sec`. Call `execute_refund`.
5. `refund_execution_inputs` computes `refund_amount = 50200 - 50000 = 200`. `require!(200 > 0)` passes.
6. `build_refund_output` creates `TxOut { value: 200 sat, script_pubkey: P2WPKH }`.
7. `finalize_refund_with_psbt` inserts `BTCPendingInfo` and marks UTXO verified.
8. After MPC signing, broadcast attempt is rejected by every Bitcoin node: output value 200 < 546 satoshis (non-standard dust).
9. The refund is permanently stuck; the UTXO is permanently locked.
