### Title
State Not Updated Before Cross-Contract Call in `sign_btc_transaction` Enables Duplicate Signing and Griefing — (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`internal_sign_btc_transaction` checks `signatures[sign_index].is_none()` but does **not** update that field before dispatching the cross-contract call (XCC) to `chain_signatures`. The signature slot is only written inside `sign_btc_transaction_callback`. Because `sign_btc_transaction` has no ownership check, any unprivileged account can call it for any pending info, racing the legitimate owner's call, causing the owner's callback to panic and their attached deposit (the chain-signatures fee) to be permanently lost.

---

### Finding Description

In `internal_sign_btc_transaction` the guard is:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
// … no state write here …
self.sign_promise(SignRequest { payload, path, key_version })
    .then(Self::ext(…).sign_btc_transaction_callback(…))
``` [1](#0-0) 

The slot `signatures[sign_index]` is only written in the callback:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
btc_pending_info.signatures[sign_index] = Some(signature.clone());
``` [2](#0-1) 

Between the initial call and the callback, the slot remains `None` in on-chain state. A second call to `sign_btc_transaction` for the same `(btc_pending_sign_id, sign_index)` pair will pass the guard and dispatch a second XCC to `chain_signatures`, forwarding a second attached deposit.

`sign_btc_transaction` carries no ownership check — any NEAR account may call it for any pending info:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
``` [3](#0-2) 

The attached deposit is forwarded unconditionally to `chain_signatures` in `sign_promise`:

```rust
ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
    .with_static_gas(GAS_FOR_SIGN_CALL)
    .with_attached_deposit(env::attached_deposit())
    .sign(request)
``` [4](#0-3) 

Once `chain_signatures` has received and processed the request, the deposit cannot be recovered. When the second callback fires and hits `require!(… .is_none(), "Already signed")`, the callback panics, rolling back its own state changes but **not** the already-completed XCC or its deposit transfer.

---

### Impact Explanation

Any user who calls `sign_btc_transaction` for a `btc_pending_sign_id` that is already mid-flight (XCC dispatched, callback not yet executed) will have their attached deposit permanently transferred to `chain_signatures` and their callback panic with "Already signed". This is a publicly reachable fault in the production signing path that causes direct financial loss (the chain-signatures fee) to the victim without any fund theft from the bridge itself.

Severity: **Low** — "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

---

### Likelihood Explanation

The attack requires no privilege. An attacker monitors on-chain state for `BTCPendingInfo` entries in `PendingSign` stage, then calls `sign_btc_transaction` for the target entry before the legitimate owner's callback completes. NEAR's asynchronous XCC model guarantees a window of at least one block between the initial call and the callback, making the race reliably exploitable.

---

### Recommendation

Apply the Checks-Effects-Interactions pattern: mark `signatures[sign_index]` as "in-flight" (e.g., a sentinel `Some(placeholder)`) **before** dispatching the XCC to `chain_signatures`, and validate/overwrite it in the callback. Alternatively, restrict `sign_btc_transaction` so that only the account recorded in `btc_pending_info.account_id` (or a designated relayer) may call it.

---

### Proof of Concept

1. Victim initiates a withdrawal; `BTCPendingInfo` with `btc_pending_id = P` is created with `signatures = [None]`.
2. Attacker calls `sign_btc_transaction(P, 0, v)` with attached deposit `D_a`. Guard `signatures[0].is_none()` → `true`. XCC₁ dispatched to `chain_signatures`; `D_a` transferred.
3. Victim calls `sign_btc_transaction(P, 0, v)` with attached deposit `D_v`. Guard `signatures[0].is_none()` → still `true` (callback not yet run). XCC₂ dispatched; `D_v` transferred.
4. XCC₁ callback (`sign_btc_transaction_callback`): `signatures[0].is_none()` → `true`; sets `signatures[0] = Some(sig_a)`. State saved.
5. XCC₂ callback: `signatures[0].is_none()` → `false`; `require!` panics "Already signed". Callback state rolled back. `D_v` is **not** returned — it was already consumed by `chain_signatures` in step 3.
6. Victim loses `D_v` with no recourse.
