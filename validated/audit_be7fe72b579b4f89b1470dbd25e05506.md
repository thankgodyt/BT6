### Title
Peras Quorum Threshold Bypass via Unit Mismatch in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function, which gates Peras certificate forging, directly compares an accumulated `PerasVoteStake` value against the relative quorum threshold (`3/4`) without any normalization. The code itself acknowledges in a TODO comment that this comparison is only correct when both operands are in the same units (both relative/normalized). Because `PerasVoteStake` is populated from the ledger's absolute stake distribution without normalization, the comparison is meaningless: if absolute lovelace values are used, any voter with stake > 0.77 lovelace single-handedly reaches quorum, allowing unauthorized Peras certificate forging and chain-weight manipulation.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the `stakeAboveThreshold` function performs the quorum check:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The `PerasVoteStake` fed into this function is obtained from `PerasVoteStakeDistr` via `lookupPerasVoteStake` inside `validatePerasVote`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [2](#0-1) 

The `PerasVoteStakeDistr` maps `PerasVoterId -> PerasVoteStake`, where `PerasVoteStake` is an opaque `Rational`. The code explicitly acknowledges there is no defined conversion from the ledger's absolute stake to the relative vote stake:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [3](#0-2) 

Meanwhile, `perasQuorumStakeThreshold` is hardcoded as a relative value `3/4`:

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
``` [4](#0-3) 

The `stakeAboveThreshold` result directly controls certificate forging in `updateCandidateVoteState`:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [5](#0-4) 

The full production call chain from an inbound peer vote to certificate forging is:

1. Peer sends a `PerasVote` via the ObjectDiffusion miniprotocol.
2. `makePerasVotePoolWriterFromChainDB` → `processVotes` validates the vote using `validatePerasVote mkPerasParams sd vote`.
3. `validatePerasVote` assigns the raw stake from `PerasVoteStakeDistr` to `vpvVoteStake` with no normalization.
4. The vote is added to the `PerasVoteDB` via `ChainDB.addPerasVoteWithAsyncCertHandling`.
5. `updatePerasRoundVoteState` → `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold` compares the raw stake against `3/4 + 2/100 = 0.77`. [6](#0-5) 

This is the same root cause as the external report: a formula that assumes two quantities share the same scale/units when they do not, producing an incorrect threshold comparison.

---

### Impact Explanation

**Impact: High** — Bypass of Peras certificate/vote verification checks.

If `PerasVoteStakeDistr` is populated with absolute ledger stake values (e.g., lovelace), then any voter whose absolute stake exceeds `0.77` (which is true for any voter with more than 0.77 lovelace, i.e., essentially every real voter) will single-handedly satisfy the quorum check. This allows a single adversarial vote to forge a Peras certificate for an arbitrary block. A forged certificate boosts the certified block's chain weight by `perasWeight = 15`, causing honest nodes to prefer the adversary's chain over the canonical chain. This constitutes an unauthorized Peras certificate acceptance and a chain-selection manipulation beyond the intended security assumptions.

---

### Likelihood Explanation

**Likelihood: Medium** — The code is in an active development state with explicit TODO markers, but the production code path from peer vote ingestion through `stakeAboveThreshold` to certificate forging is fully wired. The unit mismatch is acknowledged in the source code itself. Any deployment that populates `PerasVoteStakeDistr` with raw ledger stake values (the natural source) will trigger the bug. The `mkPerasParams` default is already deployed with the relative threshold `3/4`, making the mismatch concrete rather than hypothetical.

---

### Recommendation

Normalize `PerasVoteStake` to a relative (fractional) value before it is stored in `PerasVoteStakeDistr` or before `stakeAboveThreshold` is called. Concretely, either:

1. Change `stakeAboveThreshold` to accept the total stake of the distribution and divide internally:
   ```haskell
   stakeAboveThreshold params totalStake voteStake =
     (unPerasVoteStake voteStake / unPerasVoteStake totalStake)
       >= quorumThreshold + safetyMargin
   ```
2. Or normalize `PerasVoteStake` at the point of construction in `validatePerasVote`, dividing each voter's absolute stake by the total stake in `PerasVoteStakeDistr` before assigning `vpvVoteStake`.

The fix mirrors the recommendation in the external report: pass the normalization context as an explicit argument rather than assuming it is already applied.

---

### Proof of Concept

1. Populate `PerasVoteStakeDistr` with absolute lovelace values as returned by the Cardano ledger (e.g., voter A has `1_000_000` lovelace = 1 ADA).
2. An adversary sends a single `PerasVote` for their preferred block via the ObjectDiffusion miniprotocol.
3. `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake (1000000 % 1)` to the vote.
4. `stakeAboveThreshold` evaluates `1000000 >= 3/4 + 2/100 = 0.77` → `True`.
5. `votesReachQuorum` returns `Just`, and `forgePerasCert` produces a certificate boosting the adversary's block by weight 15.
6. Honest nodes running chain selection now prefer the adversary's chain, which has been artificially boosted beyond the honest chain's weight. [7](#0-6) [5](#0-4) [8](#0-7)
