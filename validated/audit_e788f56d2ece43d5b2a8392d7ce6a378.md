### Title
Users Cannot Self-Finalize Refund State — Permanent Stuck State Without Trusted Relayer Cooperation - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
After a user successfully executes a BTC refund and the refund transaction is signed and broadcast, the final cleanup step — `verify_refund_finalize` — is gated behind the `#[trusted_relayer]` role. A regular bridge user has no way to finalize their own refund state. If the trusted relayer is unavailable or uncooperative, the user's `BTCPendingInfo` and refund request remain permanently in storage, consuming their pending-sign capacity and blocking future bridge operations.

### Finding Description
The refund lifecycle consists of four steps:

1. `request_refund` — public, callable by anyone
2. `execute_refund` — public, callable by anyone after the timelock
3. `sign_btc_transaction` — public, callable by anyone
4. `verify_refund_finalize` — **restricted to `#[trusted_relayer]` only**

After step 3, the refund transaction is signed and broadcast to Bitcoin. The user's BTC is on its way back. However, the bridge's on-chain state is not cleaned up until step 4 is called. Specifically:

- `BTCPendingInfo` remains in `btc_pending_infos` in `PendingVerify` state
- The refund request remains in `refund_requests` with `executed = true`
- The UTXO key remains in `verified_deposit_utxo`
- The user's `btc_pending_verify_list` retains the entry

The only two functions that can clean up this state are both restricted to trusted relayers:

```rust
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn verify_refund_finalize(&mut self, tx_id: String, proof: TxInclusionProof) -> Promise { ... }

#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn remove_refund_pending_tx_id(&mut self, tx_id: String) { ... }
```

There is no user-callable path to clean up a completed refund's pending state. [1](#0-0) [2](#0-1) 

The `finalize_refund_with_psbt` function, called during `execute_refund`, inserts the `BTCPendingInfo` and marks the UTXO as verified, but provides no user-accessible cleanup path: [3](#0-2) 

The `require_pending_sign_capacity` check at line 342 means a stuck pending entry directly consumes the user's capacity quota: [4](#0-3) 

### Impact Explanation
If the trusted relayer is unavailable or refuses to call `verify_refund_finalize`, the user's bridge state is permanently stuck:

- The `BTCPendingInfo` is never removed, consuming the user's pending-sign capacity
- The user cannot initiate new withdrawals or refunds if their capacity is exhausted
- The user cannot self-rescue: `execute_refund` called again fails with `"pending info already exist"` because the PSBT ID is deterministic and the entry already exists
- Only a trusted relayer can resolve the state via `verify_refund_finalize` or `remove_refund_pending_tx_id`

This matches the allowed impact: **Medium — stuck bridge state requiring operator intervention**. [5](#0-4) 

### Likelihood Explanation
The likelihood is medium. The trusted relayer is an off-chain service that is expected to monitor Bitcoin and call `verify_refund_finalize` when a refund transaction confirms. However:

- If the relayer service experiences downtime, a bug, or is decommissioned, all in-flight refunds become permanently stuck
- A user who has already received their BTC back has no incentive to chase the relayer, but their bridge capacity remains consumed
- The dependency is structural and cannot be worked around by the user [6](#0-5) 

### Recommendation
Expose a permissionless `verify_refund_finalize` path that any caller can invoke for a refund that is in `PendingVerify` state, analogous to how `execute_refund` is permissionless after the timelock. The proof-of-inclusion check already provides the necessary trustless verification — the trusted-relayer gate adds no security benefit for the finalization step, since the Bitcoin light client independently validates the Merkle proof.

Alternatively, add a user-callable `cleanup_finalized_refund` function that removes a `BTCPendingInfo` entry when the corresponding refund request is already gone (confirmed on-chain by other means), similar to the existing `remove_refund_pending_tx_id` but without the relayer restriction.

### Proof of Concept
1. Alice sends BTC to her deposit address and the transaction confirms on Bitcoin.
2. Alice calls `request_refund` with a valid Merkle proof — succeeds, refund request stored.
3. Timelock elapses; Alice calls `execute_refund` — succeeds, `BTCPendingInfo` created in `PendingSign`.
4. Alice calls `sign_btc_transaction` — succeeds, transaction signed and broadcast, state moves to `PendingVerify`.
5. The refund transaction confirms on Bitcoin; Alice's BTC is returned.
6. Alice attempts to call `verify_refund_finalize` — **fails**: `"Relayer is not active"` (trusted relayer gate).
7. Alice attempts `execute_refund` again — **fails**: `"pending info already exist"` (deterministic PSBT ID collision).
8. Alice's `BTCPendingInfo` remains in storage indefinitely, consuming her pending-sign capacity. She cannot initiate new withdrawals or refunds until a trusted relayer calls `verify_refund_finalize` or `remove_refund_pending_tx_id` on her behalf. [7](#0-6) [8](#0-7)

    /// Remove a leftover refund pending transaction. Only allowed once its refund
    /// request is gone — i.e. the refund was finalized via another candidate or
    /// rejected — in which case this pending tx can never confirm (its UTXO is
    /// spent or the refund was cancelled) and is just stale state to clean up.
    pub(crate) fn internal_remove_refund_pending_tx_id(&mut self, tx_id: String) {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_related();

        // A refund spends exactly one deposit UTXO, whose key is the refund request key.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        require!(
            !self
                .data()
                .refund_requests
                .contains_key(&utxo_storage_keys[0]),
            "refund request still active"
        );

        let account_id = btc_pending_info.account_id.clone();
        self.internal_remove_btc_pending_info(&tx_id);
        let account = self.internal_unwrap_mut_account(&account_id);
        account.btc_pending_sign_ids.remove(&tx_id);
        account.btc_pending_verify_list.remove(&tx_id);
    }

    ) -> PromiseOrValue<bool> {

        btc_pending_info.assert_pending_sign();

                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),

                return PromiseOrValue::Value(true);
            }
        }
