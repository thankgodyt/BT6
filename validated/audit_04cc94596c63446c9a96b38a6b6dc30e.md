### Title
Frontrunning `request_refund` with Inflated `gas_fee` Causes Near-Total Loss of User BTC Deposit — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `request_refund` function accepts a caller-supplied `gas_fee` parameter with only a single weak bound (`gas_fee < amount`). Because the UTXO key is deterministic and the function is publicly callable, an attacker who observes a user's pending `request_refund` transaction can race it with the same BTC proof but a near-maximum `gas_fee`. The attacker's call lands first, the user's call is rejected ("Refund request already exists for this UTXO"), and the stored refund request carries the attacker's inflated fee — leaving the user with 1 satoshi (or a sub-dust output that can never be broadcast).

### Finding Description

`internal_request_refund` in `contracts/satoshi-bridge/src/refund.rs` accepts an optional `gas_fee`:

```rust
pub(crate) fn internal_request_refund(
    &self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<u128>,   // ← attacker-controlled
) -> Promise {
``` [1](#0-0) 

The only validation applied to the caller-supplied value is:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [2](#0-1) 

And the minimum refund check is:

```rust
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

So `gas_fee = amount − 1` passes both checks, leaving `refund_amount = 1 satoshi`.

In `request_refund_callback`, a duplicate submission is hard-rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

Once `execute_refund` is called (by anyone after the timelock), `finalize_refund_with_psbt` permanently marks the UTXO as verified:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [5](#0-4) 

After that, `verify_deposit` is also blocked for the same UTXO, so the user cannot recover their funds via the deposit path either.

The public API exposes `gas_fee` as the final optional argument, confirmed by integration tests:

```rust
context.request_refund(
    "alice", deposit_msg, TARGET_ADDRESS, tx_bytes, vout,
    blockhash, 1, vec![],
    None   // ← gas_fee; attacker passes amount-1 instead
)
``` [6](#0-5) 

### Impact Explanation

**Medium — attacker-triggered near-total loss of user BTC deposit without direct theft.**

The attacker sets `gas_fee = deposit_amount − 1`. The resulting refund PSBT has a 1-satoshi output, which is below the Bitcoin dust limit (~546 sat for P2PKH). The broadcast will be rejected by the Bitcoin network. The NEAR contract has already marked the UTXO as verified and removed the ability to re-request a refund or mint nBTC. The user's BTC is permanently inaccessible without DAO intervention to manually clear state. The attacker receives nothing; the loss goes to miners (or is simply unrecoverable if the transaction is never broadcastable).

### Likelihood Explanation

**Medium.** NEAR transactions are visible before block finalization. An attacker monitoring the network for `request_refund` calls can copy the BTC proof parameters, substitute a near-maximum `gas_fee`, and submit their transaction in the same or next block. No privileged access is required. The only cost to the attacker is the NEAR storage deposit required by `request_refund` (`required_balance_for_request_refund()`), which is a small fixed amount.

### Recommendation

1. **Remove the caller-supplied `gas_fee` parameter entirely.** The gas fee should be determined solely by the protocol (`self.get_refund_gas_fee()`) and not be overridable by the caller.
2. If operator override is needed, gate it behind `Role::DAO` or `Role::Operator`.
3. Add a minimum `refund_amount` floor (e.g., above the Bitcoin dust limit) to prevent economically invalid refund transactions from being constructed.

### Proof of Concept

```
1. Alice sends 100,000 sat to her deposit address.
2. Alice submits request_refund(deposit_msg, refund_addr, tx_bytes, 0, proof, None).
   → Transaction is in-flight (visible on NEAR network).
3. Attacker copies all parameters, sets gas_fee = 99_999.
   → Attacker's request_refund lands first.
   → RefundRequest stored: amount=100_000, gas_fee=99_999, refund_amount=1 sat.
4. Alice's request_refund arrives → panics: "Refund request already exists for this UTXO".
5. After timelock, attacker (or anyone) calls execute_refund(utxo_storage_key).
   → PSBT built with 1-sat output (below dust limit).
   → verified_deposit_utxo now contains the key.
6. Relayer attempts to broadcast the refund tx → Bitcoin network rejects (dust output).
7. Alice cannot call request_refund again (request exists).
   Alice cannot call verify_deposit (UTXO marked verified).
   Alice's 100,000 sat is permanently inaccessible without DAO intervention.
```
