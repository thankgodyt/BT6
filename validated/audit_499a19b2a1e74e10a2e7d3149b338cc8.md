### Title
`csLatestSlot` Can Be Reset to an Arbitrarily Lower Value by a Peer, Inflating GDD Upper-Bound and Bypassing Genesis Density Disconnection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`csLatestSlot` in `ChainSyncState` is a ratchet-like field that the Genesis Density Disconnection (GDD) governor relies on to determine whether a peer has already sent a header beyond the Genesis window. Because the field is updated via **direct assignment** (no `max`), a peer can reset it to an arbitrarily lower slot by rolling back and then sending a header at a lower slot. This inflates the peer's GDD `upperBound`, preventing the GDD from disconnecting an adversarial peer that should be disconnected, and allowing it to stall the node's LoE fragment and chain selection.

---

### Finding Description

`csLatestSlot` is defined in `ChainSyncState` as:

```haskell
csLatestSlot :: !(StrictMaybe (WithOrigin SlotNo))
-- ^ When the client receives a new header, it updates this field before
-- processing it further, and the latest slot may refer to a header beyond
-- the forecast horizon while the candidate fragment isn't extended yet, to
-- signal to GDD that the density is known up to this slot.
``` [1](#0-0) 

The setter wired up in `bracketChainSyncClient` is:

```haskell
csvSetLatestSlot =
    modifyTVar csHandleState . \ls s -> s{csLatestSlot = SJust ls}
``` [2](#0-1) 

This is a **plain record update** — no `max` is taken against the existing value. Every time `rollForward` receives a header it unconditionally calls:

```haskell
atomically (setLatestSlot dynEnv (NotOrigin slotNo))
``` [3](#0-2) 

Because ChainSync allows rollbacks followed by roll-forwards at lower slots, a peer can:

1. Send a header at slot `S1 ≥ firstSlotAfterGenesisWindow` → `csLatestSlot = S1`
2. Issue a valid rollback (within `k` blocks)
3. Send a header at slot `S2 < firstSlotAfterGenesisWindow` → `csLatestSlot` is **overwritten** with `S2`

After step 3, `csLatestSlot` is lower than it was after step 1.

The GDD governor's `densityDisconnect` function uses `csLatestSlot` to compute `hasBlockAfter`:

```haskell
latestSlot <- toList (csLatestSlot state)
let hasBlockAfter =
      max (AF.headSlot candidateSuffix) latestSlot
        >= NotOrigin firstSlotAfterGenesisWindow
    potentialSlots =
      if hasBlockAfter
        then 0
        else unknownTrailingSlots
    upperBound = lowerBound + potentialSlots
``` [4](#0-3) 

When `hasBlockAfter = False` (because `csLatestSlot` was reset below the genesis window boundary), `potentialSlots = unknownTrailingSlots > 0`, which inflates `upperBound`. The GDD only disconnects a peer when its `upperBound` is strictly less than the `lowerBound` of the best peer. By inflating `upperBound`, the adversarial peer avoids disconnection.

The GDD fingerprint also watches `csLatestSlot` to decide when to re-evaluate:

```haskell
GDDSyncing $
  Map.map (\css -> (csLatestSlot css, csIdling css)) gddCtxStates
``` [5](#0-4) 

Resetting `csLatestSlot` to a lower value also triggers a spurious GDD re-evaluation with a now-inflated upper bound, compounding the effect.

---

### Impact Explanation

The GDD is the core Genesis security mechanism that disconnects adversarial peers serving sparser chains. By manipulating `csLatestSlot` downward, an adversarial peer can permanently avoid GDD disconnection. This stalls the LoE (Limit on Eagerness) fragment, which in turn prevents the node from selecting blocks on the honest chain beyond the LoE tip. The node is held in a degraded chain-selection state where it cannot advance past the adversarial peer's stalled LoE contribution — a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended Genesis security assumptions.

**Impact: High** — chain selection / Genesis security bypass triggered by an unprivileged peer via crafted ChainSync messages.

---

### Likelihood Explanation

Any connected peer can send a valid rollback followed by a roll-forward at a lower slot. This is a normal ChainSync operation and requires no special privileges, no key compromise, and no stake majority. The adversarial peer only needs to be connected to the victim node during initial chain synchronisation (the `Syncing` GSM state), which is exactly when the GDD is active. The attack is repeatable: the peer can keep resetting `csLatestSlot` every time the GDD is about to disconnect it.

**Likelihood: Medium** — requires a connected adversarial peer during syncing, which is a realistic scenario for an eclipse or long-range attack.

---

### Recommendation

Apply a `max` when updating `csLatestSlot`, analogous to the `pauseTranche = max(borrowTier, pauseTranche)` fix in the reference report:

```haskell
csvSetLatestSlot =
    modifyTVar csHandleState . \ls s ->
      s { csLatestSlot = SJust (max ls (fromSMaybe Origin (csLatestSlot s))) }
```

This ensures `csLatestSlot` is monotonically non-decreasing across the lifetime of a ChainSync session, preserving the GDD invariant that once a peer has demonstrated knowledge of a slot beyond the genesis window, that fact cannot be retracted. [6](#0-5) 

---

### Proof of Concept

**Setup:** Node is syncing (`GsmState = Syncing`). Genesis window ends at slot `W`. Honest peer has `lowerBound = 10` blocks in the genesis window. Adversarial peer has `lowerBound = 3` blocks.

**Without the bug:** GDD sees adversarial peer's `upperBound = 3 + 0 = 3` (because `csLatestSlot = W+5 ≥ W`, so `hasBlockAfter = True`, `potentialSlots = 0`). Since `3 < 10`, the adversarial peer is disconnected. LoE advances. Node selects the honest chain.

**With the attack:**
1. Adversarial peer sends header at slot `W+5` → `csLatestSlot = W+5`, `hasBlockAfter = True`.
2. Adversarial peer sends `MsgRollBackward` to a point before slot `W`.
3. Adversarial peer sends header at slot `W-10` → `csLatestSlot` is **overwritten** to `W-10`.
4. Now `hasBlockAfter = False` (since `max(W-10, W-10) = W-10 < W`).
5. `potentialSlots = unknownTrailingSlots = W - (W-10) = 10`.
6. `upperBound = 3 + 10 = 13 > 10`. GDD does **not** disconnect the adversarial peer.
7. LoE fragment does not advance. Node cannot select blocks on the honest chain beyond the LoE tip.
8. Adversarial peer repeats steps 1–3 indefinitely to keep `csLatestSlot` suppressed. [7](#0-6) [8](#0-7)

  densityBounds = do
    (peer, candidateSuffix) <- candidateSuffixes
    let (clippedFragment, _) =
          AF.splitAtSlot firstSlotAfterGenesisWindow candidateSuffix
    state <- maybeToList (states Map.!? peer)
    -- Skip peers that haven't sent any headers yet.
    -- They should be disconnected by timeouts instead.
    latestSlot <- toList (csLatestSlot state)
    let idling = csIdling state

        -- Is there a block after the end of the Genesis window?
        hasBlockAfter =
          max (AF.headSlot candidateSuffix) latestSlot
            >= NotOrigin firstSlotAfterGenesisWindow

        -- If the slot of the latest header we know of is _after_ the end of
        -- the Genesis window (either because the candidate fragment extends
        -- beyond it or because we are waiting to validate a header beyond the
        -- forecast horizon that we already received), there can be no headers
        -- in between and 'potentialSlots' is 0.
        potentialSlots =
          if hasBlockAfter
            then 0
            else unknownTrailingSlots

        -- Number of trailing slots in the genesis window that could have
        -- headers which haven't been sent yet
        unknownTrailingSlots =
          unSlotNo $
            -- cannot underflow as the fragment is clipped to the genesis window
            firstSlotAfterGenesisWindow - succWithOrigin (AF.headSlot clippedFragment)

        -- The number of blocks within the Genesis window we know with certainty
        lowerBound = fromIntegral $ AF.length clippedFragment

        upperBound = lowerBound + potentialSlots

        -- The number of blocks we know to be on the candidate chain after
        -- the intersection, not limited to the Genesis window.
        totalBlockCount = fromIntegral (AF.length candidateSuffix)

        -- Does the peer have more than k known blocks in _total_ after the intersection?
        -- If not, it is not qualified to compete by density (yet).
        offersMoreThanK = totalBlockCount > unNonZero k

    pure
      ( peer
      , DensityBounds
          { clippedFragment = AF.mapAnchoredFragment hwtHeader clippedFragment
          , offersMoreThanK
          , lowerBound
          , upperBound
          , hasBlockAfter
          , latestSlot
          , idling
          }
      )
