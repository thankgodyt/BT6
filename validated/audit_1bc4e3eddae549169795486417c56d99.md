### Title
Unguarded fallthrough in `ft_transfer` panics when withdraw relayer is unset, breaking the legacy Near Intents withdrawal path — (`contracts/nbtc/src/lib.rs`)

### Summary

When `WITHDRAW_RELAYER_ADDRESS` is absent from storage, any registered nBTC holder can trigger a panic in `ft_transfer` by sending to the nBTC contract's own account ID with a `WITHDRAW_TO:` memo. The fallthrough at line 195 calls `self.token.ft_transfer(env::current_account_id(), …)`, but the nBTC contract itself is never registered as a token holder, causing the standard NEP-141 `internal_deposit` to panic.

### Finding Description

`Contract::ft_transfer` implements a legacy Near Intents withdrawal intercept: [1](#0-0) 

When both conditions are true (`receiver_id == env::current_account_id()` and memo starts with `"WITHDRAW_TO:"`), the code checks for a configured relayer: [2](#0-1) 

If `read_withdraw_relayer_address()` returns `None` (relayer not set or cleared), the `if let Some(…)` block is skipped entirely — there is no `else` branch, no early return, and no error. Execution falls through to: [3](#0-2) 

Here `receiver_id` is still `env::current_account_id()` (the nBTC contract itself). The standard `FungibleToken::ft_transfer` → `internal_transfer` → `internal_deposit` panics because the nBTC contract account is never registered as a token holder. The constructor only registers `bridge_id`: [4](#0-3) 

The relayer address is stored in raw storage and can be absent at any point — either before `set_withdraw_relayer_address` is first called, or if it is ever cleared: [5](#0-4) 

### Impact Explanation

- The caller's transaction panics and reverts; their tokens are not transferred (no permanent fund loss).
- The legacy Near Intents withdrawal path (`ft_transfer` to self with `WITHDRAW_TO:` memo) is completely non-functional for any user who attempts it while the relayer is unset.
- This is a publicly reachable panic-driven fault in a production bridge token path, matching the **Low** allowed impact scope.

### Likelihood Explanation

The precondition (relayer not set) is realistic: it applies to any freshly deployed contract before `set_withdraw_relayer_address` is called, and to any period after the relayer address is cleared. Any registered nBTC holder can trigger it with a single `ft_transfer` call attaching 1 yoctoNEAR.

### Recommendation

Add an explicit guard in the fallthrough case. When the withdraw-relayer intercept conditions are met but no relayer is configured, the function should either reject the call with a clear error or skip the intercept and proceed with a normal transfer to a valid registered receiver — not silently fall through to a transfer targeting the unregistered contract account:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
self.token.ft_transfer(receiver_id, amount, memo);
```

1. Deploy nBTC contract without calling `set_withdraw_relayer_address`.
2. Register a user account and mint nBTC to it.
3. Call `ft_transfer(nbtc_contract_id, amount, Some("WITHDRAW_TO:bc1qxxx"))` with 1 yoctoNEAR attached from the registered holder.
4. Observe the transaction panics with "The account `nbtc_contract_id` is not registered" from `internal_deposit` inside the standard NEP-141 implementation.

    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // Legacy bridging flow used by Near Intents
        if receiver_id == env::current_account_id()
            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))

            if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
                return self.token.ft_transfer(withdraw_relayer, amount, memo);

        }

    }
