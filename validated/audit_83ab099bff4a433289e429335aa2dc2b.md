### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation — Peer-Injected Fake Certs Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used in production unconditionally accepts every peer-provided Peras certificate by returning `Right` from `validatePerasCert` without performing any cryptographic or semantic checks. Both production pool-writer paths (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) wire this stub directly into the inbound certificate handler. An unprivileged peer can therefore inject arbitrary `PerasCert` objects — with any round number and any boosted-block point — that are stored in the `PerasCertDB` / `ChainDB` and used to influence chain selection.

### Finding Description

**Root cause — stub validator always returns `Right`:**

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate for inbound certificates. The only deployed instance is the degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no quorum check, no round-number bounds check, no boosted-block existence check — every certificate is unconditionally promoted to `ValidatedPerasCert`.

**Production wiring — both pool writers use this stub:**

`makePerasCertPoolWriterFromChainDB` (the comment explicitly marks this as the production path) passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`makePerasCertPoolWriterFromCertDB` carries the identical stub: [3](#0-2) 

**Inbound handler — `processCerts` trusts the validator result:**

`processCerts` partitions the batch into `(errors, validatedCerts)`. Because `validatePerasCert` never produces an error, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addCert`: [4](#0-3) 

**Chain-selection side-effect:**

`makePerasCertPoolWriterFromChainDB` calls `ChainDB.addPerasCertAsync chainDB`, which triggers chain-selection re-evaluation with the injected certificate's `vpcCertBoost` applied to the attacker-chosen `pcCertBoostedBlock`. [5](#0-4) 

The `PerasCert` data type carries a `pcCertRound` and a `pcCertBoostedBlock` (a `Point blk`), both entirely peer-controlled: [6](#0-5) 

### Impact Explanation

**Impact: High — chain-selection manipulation by an unprivileged peer.**

A malicious peer can craft a `PerasCert` that names any block point as `pcCertBoostedBlock`. After injection, that block receives a `PerasWeight` boost of `perasWeight mkPerasParams = 15` in chain selection. Because the Peras weight is additive to the chain's score, an adversary can make an honest node prefer a shorter or non-canonical fork over the honest chain, violating the chain-selection invariant that the heaviest honest chain is always preferred. This matches the allowed impact: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

It also matches: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

### Likelihood Explanation

Any peer that can establish an ObjectDiffusion connection and send a `PerasCert` message triggers this path. No stake, no keys, no prior authentication is required. The only prerequisite is that the Peras ObjectDiffusion mini-protocol is enabled on the target node, which is the case whenever the Peras feature flag is active. The code is in the production source tree (not a test library), and both pool-writer constructors are wired into the diffusion layer.

### Recommendation

1. **Replace the stub with real validation.** The `validatePerasCert` implementation must verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)`, confirm the voter set meets the quorum stake threshold (`perasQuorumStakeThreshold`), and check that `pcCertBoostedBlock` refers to a block that actually exists on a known chain. The `V1.PerasCert` type already carries `pcVoters` and `pcSignature` fields for this purpose. [7](#0-6) 

2. **Validate round-number bounds.** Reject certificates whose `pcCertRound` is in the future beyond the current wall-clock round or older than `perasCertMaxRounds` rounds ago.

3. **Validate the boosted block.** Reject certificates whose `pcCertBoostedBlock` does not correspond to a block present in the VolatileDB or ImmutableDB.

4. **Remove the degenerate catch-all instance** once the real Cardano-specific instance is in place, to prevent the stub from silently being used for any new block type.

### Proof of Concept

**Attacker-controlled inputs:**
```
pcCertRound      = PerasRoundNo <any value>
pcCertBoostedBlock = Point { slot = <target slot>, hash = <target block hash> }
pcVoters         = <empty or garbage>
pcSignature      = <garbage BLS aggregate>
```

**Execution path:**
1. Peer sends a batch containing the crafted `PerasCert` via the ObjectDiffusion protocol.
2. `makePerasCertPoolWriterFromChainDB.opwAddObjects` calls `processCerts`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`.
4. The degenerate instance returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }` — no error.
5. `addCert (WithArrivalTime now validatedCert)` is called → `ChainDB.addPerasCertAsync chainDB`.
6. Chain selection re-runs; the target block now carries a boost of 15, potentially making it preferred over the honest tip.

**Expected (correct) outcome:** Step 3 should return `Left (PerasValidationErr ...)` due to invalid signature/quorum, and `processCerts` should throw `PerasCertValidationError`, disconnecting the peer.

**Actual outcome:** The certificate is accepted and stored; chain selection is influenced by the attacker's chosen block.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
