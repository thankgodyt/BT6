Let me check the NEP-141 standard `ft_transfer` behavior and whether the nbtc contract's own account can be registered.

### Title
`ft_transfer` WITHDRAW_TO Fallthrough Permanently Locks Tokens in nBTC Contract When No Relayer Is Set — (`contracts/nbtc/src/lib.rs`)

---

### Summary

When `withdraw_relayer_address` is not set in storage (the default state after deployment), calling `ft_transfer(receiver_id=nbtc_contract, amount=X, memo=Some("WITHDRAW_TO:anything"))` silently falls through to a plain `self.token.ft_transfer(nbtc_contract, X, memo)`. This deposits tokens into the nbtc contract's own FT account. No function in the contract can release those tokens, permanently locking them.

---

### Finding Description

The custom `ft_transfer` override in `contracts/nbtc/src/lib.rs` implements a "legacy bridging flow" redirect:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
        // ← NO else-branch: falls through silently
    }
    self.token.ft_transfer(receiver_id, amount, memo);  // receiver_id == nbtc contract
}
``` [1](#0-0) 

When `read_withdraw_relayer_address()` returns `None` (storage key `WITHDRAW_RELAYER_ADDRESS` is absent), the inner `if let Some(...)` block is skipped and execution falls to line 195, calling `self.token.ft_transfer(nbtc_contract, X, memo)` — a plain NEP-141 transfer into the contract's own FT account. [2](#0-1) 

`set_withdraw_relayer_address` is never called in the constructor — the storage key is absent by default: [3](#0-2) 

The nbtc contract's own account is not pre-registered in the FT storage (only `bridge_id` is), but `storage_deposit` is public and permissionless, so any caller can register `nbtc_contract` as a valid FT recipient before executing the attack. [4](#0-3) 

---

### Impact Explanation

Tokens transferred into the nbtc contract's own FT account are irrecoverable:

- `burn()` only calls `internal_withdraw(&self.bridge_id, ...)` — it cannot touch the nbtc contract's own account balance. [5](#0-4) 
- No admin, controller, or bridge function exists to transfer tokens out of the nbtc contract's own FT account.
- The nbtc contract does not implement `ft_on_transfer`, so `ft_transfer_call` to itself would also fail.

Result: user tokens are permanently burned below backed supply, violating the bridge invariant that every `WITHDRAW_TO` memo triggers a bridge withdrawal.

---

### Likelihood Explanation

- **Default state is vulnerable**: `withdraw_relayer_address` is not set in `new()`, so every freshly deployed contract is immediately exploitable until the controller calls `set_withdraw_relayer_address`. [6](#0-5) 
- **No privilege required**: any token holder with 1 yoctoNEAR can call `ft_transfer`.
- **One trivial prerequisite**: register the nbtc contract's own FT account via the public `storage_deposit` — a single permissionless call.
- **Self-inflicted but unrecoverable**: a user following the Near Intents legacy flow documentation would naturally call `ft_transfer(nbtc_contract, X, "WITHDRAW_TO:btc_address")` and lose funds permanently if the relayer is not yet configured.

---

### Recommendation

Add an explicit `else` branch (or a `require!`) to reject the call when the relayer is not set:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("WITHDRAW_RELAYER_NOT_SET"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
```

This ensures the WITHDRAW_TO path either succeeds via the relayer or reverts atomically, never silently depositing into the contract's own account.

---

### Proof of Concept

1. Deploy nbtc contract without calling `set_withdraw_relayer_address`.
2. Call `storage_deposit(account_id = Some(nbtc_contract), registration_only = None)` with sufficient NEAR to register the nbtc contract's own FT account.
3. As any token holder, call `ft_transfer(receiver_id = nbtc_contract, amount = 1000, memo = Some("WITHDRAW_TO:bc1qanything"))` with 1 yoctoNEAR attached.
4. Assert `ft_balance_of(nbtc_contract)` increased by 1000.
5. Assert caller's balance decreased by 1000.
6. Assert no bridge withdrawal was initiated.
7. Assert no function call can recover the 1000 tokens — `burn()` from `bridge_id` does not touch `nbtc_contract`'s balance.
