Audit Report

## Title
Unregistered-Token `init_transfer` Burns/Locks Funds With No Recovery Path — (File: near/omni-bridge/src/lib.rs)

## Summary
`init_transfer()` increments the per-chain destination nonce and irreversibly burns or locks user tokens before verifying that the transferred token has a registered address on the destination chain. `sign_transfer()` hard-panics with `FailedToGetTokenAddress` when the token mapping is absent, leaving the transfer permanently stuck in `pending_transfers` with no on-chain recovery path.

## Finding Description
`init_transfer()` performs only two validations before mutating state: the destination chain is not `ChainKind::Near`, and `fee < amount`. It does not call `get_token_address()` to confirm the token is registered on the destination chain.

Immediately after those checks, both `self.current_origin_nonce` and the per-chain `destination_nonce` are incremented and written to persistent storage via `get_next_destination_nonce()`, which calls `self.destination_nonces.insert()` with no rollback path. [1](#0-0) 

`get_next_destination_nonce()` writes the incremented value to persistent storage unconditionally. [2](#0-1) 

`init_transfer_internal()` then burns deployed tokens and locks native tokens, returning `U128(0)` — no NEP-141 refund — on the happy path. [3](#0-2) 

The only place the token-registration check exists is in `sign_transfer()`, called after the burn/lock, which hard-panics with `FailedToGetTokenAddress` when the mapping is absent. [4](#0-3) 

A grep search for `cancel_transfer`, `refund_transfer`, and `recover_transfer` in `lib.rs` returns no matches, confirming there is no on-chain recovery function. [5](#0-4) 

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**, which falls squarely within the Critical allowed impact scope. Deployed (bridged) tokens destroyed by `burn_tokens_if_needed` cannot be re-minted without a valid MPC-signed `finTransfer`. Native NEAR tokens trapped in `locked_tokens` accounting cannot be unlocked without a completed transfer. Because `sign_transfer()` panics for unregistered tokens, neither path can ever complete. The only theoretical recovery requires an admin to manually register the token on the destination chain out-of-band, with no on-chain guarantee. [6](#0-5) 

## Likelihood Explanation
The entry point is the standard NEP-141 `ft_transfer_call` flow, callable by any token holder without special privileges. The scenario is realistic during token-listing rollouts where a token is registered on some destination chains but not yet on others (e.g., registered on Ethereum but not yet on Solana). No on-chain guard in `init_transfer()` prevents this. The bridge UI or SDK cannot substitute for a missing contract-level check. [7](#0-6) 

## Recommendation
Add a registration check at the top of `init_transfer()`, before any nonce increment or token operation:

```rust
require!(
    self.get_token_address(
        init_transfer_msg.get_destination_chain(),
        token_id.clone(),
    ).is_some(),
    BridgeError::TokenNotRegistered.as_ref()
);
```

This ensures nonce increments and token burns/locks only occur for transfers that can actually be completed. [1](#0-0) 

## Proof of Concept
1. Token `usdc.near` is registered on `ChainKind::Eth` but **not** on `ChainKind::Sol`.
2. User calls `usdc.near::ft_transfer_call(bridge, 1_000_000, InitTransfer { recipient: OmniAddress::Sol(...), fee: 0, ... })`.
3. `ft_on_transfer` → `init_transfer()`:
   - Chain check passes (Sol ≠ Near).
   - `destination_nonces[Sol]` incremented 0 → 1 and written to storage.
   - `init_transfer_internal()` called; storage balance OK; `lock_tokens_if_needed(Sol, usdc.near, 1_000_000)` executes; returns `U128(0)`.
4. NEP-141 refund = 0 → bridge keeps all 1 USDC.
5. Relayer calls `sign_transfer({origin_chain: Near, origin_nonce: N})`:
   - `get_token_address(Sol, usdc.near)` → `None` → `env::panic_str(FailedToGetTokenAddress)`.
6. Transfer remains in `pending_transfers` indefinitely; 1 USDC is permanently frozen with no on-chain recovery.

A unit test can reproduce this by: (a) initializing the contract, (b) registering `usdc.near` only for `ChainKind::Eth`, (c) simulating `ft_on_transfer` targeting `ChainKind::Sol`, (d) asserting the return value is `U128(0)`, and (e) asserting that a subsequent `sign_transfer` call panics with `FailedToGetTokenAddress`. [4](#0-3)

    fn get_next_destination_nonce(&mut self, chain_kind: ChainKind) -> Nonce {
        if chain_kind == ChainKind::Near {
            return 0;
        }

        let mut payload_nonce = self.destination_nonces.get(&chain_kind).unwrap_or_default();

        payload_nonce += 1;

        self.destination_nonces.insert(&chain_kind, &payload_nonce);

        payload_nonce
    }
