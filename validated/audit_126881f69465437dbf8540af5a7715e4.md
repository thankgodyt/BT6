### Title
Griefing Attack on Withdrawal Initiation via UTXO Race Condition — (`contracts/satoshi-bridge/src/utxo.rs`)

### Summary
`remove_vutxo_by_psbt` iterates over caller-specified UTXOs and calls `env::panic_str` if any UTXO is absent from the live set. Because the PSBT inputs are constructed off-chain against a snapshot of the UTXO set, a racing transaction that consumes one of those UTXOs before the victim's `ft_transfer_call` is processed will cause the victim's `ft_on_transfer` callback to panic, reverting the withdrawal. An unprivileged attacker with any nBTC balance can exploit this to repeatedly block a target user's withdrawals at negligible cost.

### Finding Description

`remove_vutxo_by_psbt` in `contracts/satoshi-bridge/src/utxo.rs` iterates over every UTXO key encoded in the PSBT and hard-panics if any key is missing: [1](#0-0) 

This function is called unconditionally from `generate_vutxos`: [2](#0-1) 

which is the first operation inside `create_btc_pending_info`, the handler invoked by `ft_on_transfer` when a user initiates a withdrawal: [3](#0-2) 

The same path is taken for operator-initiated active UTXO management: [4](#0-3) 

**Race condition**: A user constructs a PSBT referencing UTXOs from the current on-chain set (state `S`). Between the moment the PSBT is built and the moment `ft_on_transfer` executes, another transaction can consume one or more of those UTXOs (state `S'`). When `remove_vutxo_by_psbt` runs against `S'`, it panics on the missing key, causing `ft_on_transfer` to abort. The NEP-141 `ft_transfer_call` mechanism then refunds the nBTC to the caller, but the withdrawal attempt is entirely lost.

**Attacker path**: An attacker holding any nBTC observes the victim's pending `ft_transfer_call` (the PSBT inputs are visible in the transaction arguments). The attacker submits their own `ft_transfer_call` referencing the same UTXO(s). If the attacker's transaction is ordered before the victim's within the same or a subsequent block, the attacker's withdrawal succeeds (consuming the UTXO), and the victim's withdrawal panics. The attacker's nBTC is converted to BTC — no net loss to the attacker. The victim's nBTC is returned, but the victim is forced to retry. The attacker can repeat this for every retry, indefinitely blocking the victim's withdrawals.

### Impact Explanation

The victim's nBTC is not permanently destroyed — it is returned by the NEP-141 refund mechanism. However, if the attacker continuously races every retry, the victim is permanently unable to withdraw as long as the attacker participates. If the attacker also races active UTXO management transactions (same code path), the operator's ability to consolidate UTXOs is also blocked. This constitutes attacker-triggered temporary (and potentially indefinite) locking of bridged funds, matching the **Medium** impact tier.

### Likelihood Explanation

- Any nBTC holder can execute this attack; no privileged role is required.
- NEAR transaction ordering within a block is observable and influenceable by submitting transactions quickly.
- The attacker's cost is only NEAR gas; their nBTC is exchanged for BTC (no loss).
- The victim has no recourse other than waiting for the attacker to stop or for new UTXOs to appear that the attacker has not yet targeted.

Likelihood: **Medium**.

### Recommendation

Replace the hard panic in `remove_vutxo_by_psbt` with a graceful error return, and propagate that error up through `generate_vutxos` and `create_btc_pending_info` so that `ft_on_transfer` returns `"0"` (the standard NEP-141 signal to refund the caller) instead of panicking. This eliminates the griefing surface while preserving the correct refund behaviour. Alternatively, validate that all required UTXOs exist atomically before beginning any removal, and surface a clean error if any are missing.

### Proof of Concept

1. Alice holds 100 000 nBTC. She queries the UTXO set and finds UTXO `X` (500 000 sat). She constructs a PSBT referencing `X` and calls `nbtc.ft_transfer_call(bridge, 100000, Withdraw{input:[X], ...})`.
2. Bob (attacker, holds 1 nBTC) observes Alice's pending transaction. He immediately calls `nbtc.ft_transfer_call(bridge, 1, Withdraw{input:[X], ...})` with a minimal valid output.
3. Bob's transaction is processed first. `remove_vutxo_by_psbt` removes `X` from `utxos`. Bob's withdrawal succeeds; he receives BTC.
4. Alice's transaction is processed next. `remove_vutxo_by_psbt` calls `env::panic_str("UTXO X not exist")`.
5. `ft_on_transfer` panics → `ft_transfer_call` reverts → Alice's 100 000 nBTC is returned to her, but no withdrawal is created.
6. Bob repeats step 2 for every UTXO Alice tries. Alice can never complete a withdrawal. [1](#0-0) [3](#0-2)

    pub fn remove_vutxo_by_psbt(&mut self, psbt: &PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let mut utxo_storage_keys = vec![];
        let vutxos = psbt
            .get_utxo_storage_keys()
            .into_iter()
            .map(|utxo_storage_key| {
                utxo_storage_keys.push(utxo_storage_key.clone());
                self.data_mut()
                    .utxos
                    .remove(&utxo_storage_key)
                    .unwrap_or_else(|| {
                        env::panic_str(&format!("UTXO {} not exist", utxo_storage_key))
                    })
            })
            .collect::<Vec<_>>();
        (utxo_storage_keys, vutxos)
    }

    pub fn generate_vutxos(&mut self, psbt: &mut PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let (utxo_storage_keys, vutxos) = self.remove_vutxo_by_psbt(psbt);

        let input_utxo = vutxos
            .iter()
            .map(|v| TxOut {
                value: Amount::from_sat(v.get_amount()),
                script_pubkey: self
                    .generate_utxo_chain_address(&v.get_path())
                    .script_pubkey()
                    .expect("Invalid address"),
            })
            .collect();

        psbt.set_input_utxo(input_utxo);

        (utxo_storage_keys, vutxos)
    }
