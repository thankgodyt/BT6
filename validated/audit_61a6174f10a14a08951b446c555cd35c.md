### Title
Incomplete Peras Certificate Validation Enables Weight Accumulation to Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The `implAddCert` function in `PerasCertDB.Impl.hs` carries an explicit TODO noting that non-trivial validation logic is absent. The current check only deduplicates by round number. Simultaneously, `implGetWeightSnapshot` builds the `PerasWeightSnapshot` by summing the boost of every certificate in the database via `Map.insertWith (<>)`, meaning multiple certificates from distinct rounds that all target the same block accumulate unbounded weight on that block. An unprivileged peer can exploit this by diffusing a sequence of crafted certificates—each with a unique round number so each passes the deduplication guard—all boosting the same adversarial block. The resulting inflated weight causes `takeVolatileSuffix` to shrink the honest node's volatile suffix and `preferCandidate` to switch to the adversarial chain.

### Impact Explanation

An adversary who can inject N certificates (each with a unique round number, each boosting the same adversarial block B) causes the `PerasWeightSnapshot` to record weight `N × boost_weight` for B. If `N × boost_weight + chain_length_of_adversarial_chain > total_weight_of_honest_chain`, `preferCandidate` returns `ShouldSwitch`, and the honest node adopts the adversarial chain. Additionally, `takeVolatileSuffix` may advance the immutable tip past the fork point, permanently preventing rollback to the honest chain. This is a **chain selection error** and a **ChainDB/LedgerDB corruption** scenario: the node durably accepts the wrong chain without any operator fault.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is reachable by any connected peer. The deduplication guard in `implAddCert` only rejects a certificate whose round number is already present; it does not reject certificates whose boosted block is already boosted by a prior certificate from a different round. Because `validatePerasCert` is called with a placeholder `mkPerasParams` (explicitly marked TODO), the quorum and committee checks are not enforced at the network boundary. A single adversarial peer can therefore diffuse a batch of syntactically valid certificates with distinct round numbers and the same target block, all of which will be accepted and accumulated. No stake majority is required under the current incomplete validation.

---

### Recommendation

1. **Enforce equivocation rejection in `implAddCert`**: before inserting a certificate, check that no existing certificate in `pcdsCertsByTicket` targets a different block for the same round. The state-machine test already documents this invariant as a precondition but does not enforce it in production code.

2. **Complete the validation plumbing**: replace the `validatePerasCert mkPerasParams` placeholder with the actual per-era Peras parameters so that quorum threshold and committee-membership checks are enforced before any certificate reaches the DB.

3. **Cap per-block weight accumulation**: `addToPerasWeightSnapshot` should reject or ignore a second certificate boosting a block that already has a recorded weight, or at minimum bound the total weight per point to a single `boost_weight` value, since the Peras protocol guarantees at most one quorum per round and each round boosts at most one block.

### Proof of Concept

```
Adversary peer connects via ObjectDiffusion (Peras certificate diffusion).

Adversary constructs N certificates:
  cert_i = { roundNo = i, boostedBlock = adversarial_block_B, boost = W }
  for i in [1 .. N], where N × W > k + honest_chain_length

Each cert_i has a unique roundNo, so Set.member roundNo pcdsCertIds == False
  => implAddCert inserts all N certs into pcdsCertsByTicket.

implGetWeightSnapshot iterates Map.elems pcdsCertsByTicket:
  mkPerasWeightSnapshot accumulates:
    weightByPoint[adversarial_block_B] = N × W   (via Map.insertWith (<>))

takeVolatileSuffix on the honest chain:
  totalWeightOfFragment snap honest_chain = honest_length + 0  (no boosts on honest chain)
  totalWeightOfFragment snap adversarial_chain = adv_length + N×W  >> k

preferCandidate:
  wsvTotalWeight(adversarial) > wsvTotalWeight(honest)
  => ShouldSwitch => node adopts adversarial chain

takeVolatileSuffix on adversarial chain:
  volatile suffix shrinks to near-empty
  => immutable tip advances past fork point
  => rollback to honest chain permanently blocked
```
