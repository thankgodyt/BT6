### Title
Zcash `execute_refund` Commits State in Callback, Enabling Concurrent Double-Execution and Stuck Bridge State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

On the Zcash code path, `execute_refund` performs all its guard checks synchronously in the initial call but commits critical state (via `finalize_refund_with_psbt`) only inside a `#[private]` callback that fires after a cross-contract call. This violates the check-effect-interaction pattern. An unprivileged caller can submit two `execute_refund` transactions for the same refund request before either callback is processed, causing both to pass the guards and both callbacks to attempt state commitment. If the two calls supply different `chain_specific_data` (Orchard bundles), both callbacks succeed, creating two independent `BTCPendingInfo` entries for the same deposit UTXO. Both are forwarded to the MPC signer, both receive signatures, and both are broadcast to the Zcash network. Only one can confirm; the other is permanently stuck, requiring operator intervention to clean up.

### Finding Description

`execute_refund` is a public, permissionless function (gated only by a timelock and a storage deposit):

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

`resolve_execute_refund_timelock` reads the refund request and verifies the timelock but **does not mutate any state**. The Zcash-specific `internal_execute_refund` then makes a cross-contract call (e.g., to validate the Orchard bundle), and only in the resulting `#[private]` callback does it call `finalize_refund_with_psbt`. This is explicitly documented in the code:

> `caller` is the account that will own the pending info — it must be passed explicitly because **on Zcash this runs inside a `#[private]` callback where `predecessor` is the contract itself**.

`finalize_refund_with_psbt` is where all state mutations occur:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());

refund_request.executed = true;
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

The guard in `load_refund_request_for_execute` that is supposed to prevent double-execution reads this state:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

Because this state is only written in the callback, **both concurrent calls read `executed = false` and `verified_deposit_utxo` not containing the key**, and both pass the guard.

The only downstream protection is:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

This prevents a collision only when both calls produce an identical PSBT ID. On Zcash, the PSBT ID is derived from the full PSBT content, which includes the `chain_specific_data` (Orchard bundle). An attacker who supplies two structurally distinct but individually valid Orchard bundles across the two calls will produce two different PSBT IDs, causing both callbacks to succeed and both `BTCPendingInfo` entries to be inserted.

### Impact Explanation

Two independent `BTCPendingInfo` records are created for the same deposit UTXO. Both are forwarded to the MPC chain-signature pipeline, both receive valid ECDSA signatures, and both signed transactions are broadcast to the Zcash network. A UTXO can only be spent once; the transaction that confirms first spends the UTXO, and the second transaction becomes permanently invalid. The second `BTCPendingInfo` remains in contract storage with no path to finalization via `verify_refund_finalize` (the on-chain proof will never exist for the losing transaction). This constitutes a stuck bridge state requiring operator intervention to manually clean up the orphaned pending info.

This matches the allowed medium impact: **stuck bridge state requiring operator intervention**.

### Likelihood Explanation

The attack is reachable by any unprivileged NEAR account that holds a valid, timelock-expired refund request. The attacker simply submits two `execute_refund` transactions in the same block (or in consecutive blocks before the first callback receipt is processed). NEAR's asynchronous receipt model guarantees a window between the initial call and its callback during which a second call to the same function is processed against the pre-callback state. No privileged access, leaked keys, or external dependency compromise is required.

### Recommendation

Apply the check-effect-interaction pattern: commit the critical state guard **before** the cross-contract call, not in the callback. Specifically, set `refund_request.executed = true` and insert the UTXO into `verified_deposit_utxo` at the start of `internal_execute_refund` (synchronously, before any cross-contract call is dispatched). If the subsequent cross-contract call or callback fails, roll back via a failure handler. Alternatively, add an explicit in-progress flag (e.g., `executing: bool`) to `RefundRequest` that is set synchronously at the start of `execute_refund` and cleared on callback failure, preventing any concurrent second call from passing the guard.

### Proof of Concept

1. Attacker submits `request_refund` for a deposit UTXO and waits for the timelock to expire.
2. Attacker submits two `execute_refund` transactions in the same NEAR block, each with a distinct but individually valid Zcash `chain_specific_data` (Orchard bundle A and Orchard bundle B).
3. Both transactions are processed before either callback fires. Both call `resolve_execute_refund_timelock` → `load_refund_request_for_execute`. Both read `executed = false` and `verified_deposit_utxo` not containing the key. Both pass the guard.
4. Both dispatch cross-contract calls. Both callbacks fire (in subsequent blocks). Each callback calls `finalize_refund_with_psbt` with a different PSBT (different Orchard bundle → different PSBT ID).
5. Callback A: inserts `BTCPendingInfoA`, sets `verified_deposit_utxo`, sets `executed = true`. Succeeds.
6. Callback B: inserts `BTCPendingInfoB` (different ID, no collision), sets `verified_deposit_utxo` (idempotent), sets `executed = true`. Also succeeds.
7. Both pending infos enter the MPC signing pipeline. Both receive signatures. Both signed transactions are broadcast. Only one confirms; the other is permanently orphaned in contract state. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
