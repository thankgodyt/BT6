### Title
Unconditional Acceptance of Peer-Supplied Peras Certificates Bypasses Certificate Validation and Enables Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every peer-supplied Peras certificate, performing no cryptographic, structural, or eligibility checks. Any unprivileged peer can send a crafted `PerasCert` naming any block in the VolatileDB as the boosted block. The certificate is accepted, stored in the `PerasCertDB`, and immediately used to trigger chain selection with an inflated Peras weight boost, potentially causing the node to prefer a non-canonical fork over the honest chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub in production:**

The only `BlockSupportsPeras` instance in the codebase is the blanket instance for all `StandardHash blk`. Its `validatePerasCert` implementation always returns `Right`:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No check is performed on:
- The aggregate BLS signature over the election identifier and boosted block hash
- The eligibility of the claimed voters (VRF proofs, seat indices, stake)
- The round number's validity relative to the current epoch nonce
- The boosted block's relationship to any known chain

**Production inbound path — peer-supplied certs reach `validatePerasCert` directly:**

`makePerasCertPoolWriterFromChainDB` wires the stub directly into the object-diffusion inbound handler:

```haskell
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [2](#0-1) 

`processCerts` partitions results and adds every cert that passes `validateCert` (which always passes) to the database: [3](#0-2) 

**Chain selection consequence — fraudulent cert triggers `chainSelectionForBlock`:**

`chainSelSync` processes the newly added cert. The only guard is a slot-age check against the immutable tip. If the boosted block is in the VolatileDB, chain selection is triggered unconditionally:

```haskell
    -- Trigger chain selection for the boosted block.
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Weight inflation — fraudulent cert's boost enters `WeightedSelectView`:**

`preferAnchoredCandidate` computes `wsvTotalWeight = BlockNo + wsvWeightBoost` for each fragment. The weight boost is read from the `PerasWeightSnapshot`, which is derived from the `PerasCertDB` that now contains the fraudulent cert. A fork containing the attacker-chosen block gains `perasWeight params` additional weight: [5](#0-4) [6](#0-5)

### Impact Explanation

**Impact: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker controlling a single peer can craft a `PerasCert` that names any block currently in the target node's VolatileDB as the boosted block. Because `validatePerasCert` performs no checks, the cert is accepted and its `perasWeight` boost is added to every chain fragment containing that block. If the boosted block is on a minority fork, the node's `preferAnchoredCandidate` comparison may now return `ShouldSwitch` for that fork, causing the node to abandon the canonical chain and adopt the attacker-chosen fork. This directly violates the Peras security assumption that only legitimately certified blocks receive a weight boost.

---

### Likelihood Explanation

**Likelihood: High** — once the Peras object-diffusion mini-protocol is active on the network, any peer can send a `PerasCert` message. No stake, no keys, and no prior relationship with the target node are required. The attack requires only knowledge of a block hash present in the target's VolatileDB (obtainable via ChainSync headers) and the ability to connect as a peer. The stub is explicitly marked as incomplete with a TODO referencing issue #120, confirming the missing validation is a known gap, not an intentional design choice.

---

### Recommendation

Replace the stub `validatePerasCert` with a full implementation that:
1. Verifies the aggregate BLS signature (`pcSignature`) over `hash(pcRoundNo, pcBoostedBlock)` against the aggregate verification key derived from the claimed voters' public keys in the stake distribution.
2. Verifies each voter's eligibility proof (VRF output for non-persistent members, seat-index bounds for persistent members) against the epoch nonce for `pcRoundNo`.
3. Checks that `pcRoundNo` falls within the valid range relative to the current chain state.
4. Checks that the quorum threshold is met by the claimed voters' combined stake.

Until the full implementation is ready, the Peras certificate inbound handler should reject all externally received certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all.

---

### Proof of Concept

**Setup:** Node N is running with Peras enabled. Its VolatileDB contains block B on a minority fork F (shorter than the canonical chain C by fewer blocks than `perasWeight params` in weight units).

**Steps:**

1. Attacker peer A connects to node N via the Peras certificate object-diffusion mini-protocol.
2. A sends a single `PerasCert` message:
   - `pcCertRound` = any valid-looking round number
   - `pcCertBoostedBlock` = the `RealPoint` of block B (slot + hash, obtainable from ChainSync)
   - `pcVoters` = any non-empty bitmap
   - `pcSignature` = any bytes (not checked)
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
4. The cert is stored in `PerasCertDB` via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` finds B in the VolatileDB and calls `chainSelectionForBlock` for B.
6. `constructPreferableCandidates` computes `weightedSelectView` for fork F: `wsvTotalWeight(F) = blockNo(F_tip) + perasWeight params`.
7. If `wsvTotalWeight(F) > wsvTotalWeight(C)`, `preferAnchoredCandidate` returns `ShouldSwitch`, and node N switches to fork F.

**Expected outcome:** Node N adopts the attacker-chosen minority fork F, diverging from the canonical chain, without the attacker possessing any stake or cryptographic keys.
