### Title
User-Supplied `gas_fee` Bypasses Minimum Gas Fee Policy in Refund Requests — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` public entrypoint accepts a user-controlled `gas_fee: Option<u128>` parameter. In `request_refund_callback`, the only validation applied is that the fee is strictly less than the deposit amount. There is no lower-bound check against the protocol's configured `min_btc_gas_fee`. An unprivileged caller can supply `gas_fee = Some(0)` (or any sub-minimum value), causing the resulting BTC refund transaction to carry zero fee, making it unminable. Once `execute_refund` is called, the deposit UTXO is permanently marked as verified, blocking any future `verify_deposit` and permanently locking the victim's funds.

---

### Finding Description

**Root cause — missing lower-bound validation on user-supplied `gas_fee`:**

In `request_refund_callback`, the resolved fee is accepted with only an upper-bound check:

```rust
// contracts/satoshi-bridge/src/refund.rs:549-553
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

Any value from `0` to `amount - 1` is accepted. The protocol's `min_btc_gas_fee` (and `max_btc_gas_fee`) configured in `Config` are never consulted here: [2](#0-1) 

**Downstream effect — zero-fee refund transaction:**

When `execute_refund` is later called, `refund_execution_inputs` computes the refund output value as:

```rust
// contracts/satoshi-bridge/src/refund.rs:280-283
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
``` [3](#0-2) 

With `gas_fee = 0`, `refund_amount = deposit_amount`. The resulting Bitcoin transaction has `output_value = input_value`, meaning the implicit miner fee is zero. Such a transaction will not be relayed or mined.

**Permanent UTXO lock — `verified_deposit_utxo` insertion:**

Inside `finalize_refund_with_psbt`, the deposit UTXO is unconditionally inserted into `verified_deposit_utxo` to block a later `verify_deposit`:

```rust
// contracts/satoshi-bridge/src/refund.rs:377-380
// Mark UTXO as verified to prevent verify_deposit later
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

Once this insertion occurs, `verify_deposit` is permanently blocked for that UTXO. The stored `gas_fee` in the `RefundRequest` cannot be updated after creation, so re-calling `execute_refund` (which is permitted when `executed == true`) still produces the same zero-fee transaction. There is no code path to remove an entry from `verified_deposit_utxo`. [5](#0-4) 

---

### Impact Explanation

An attacker who observes a victim's deposit on-chain can call `request_refund` with `gas_fee = Some(0)`, wait for the timelock, then call `execute_refund`. The deposit UTXO is permanently marked as verified, `verify_deposit` is blocked forever, the refund transaction is never mined, and the victim's BTC is permanently locked in the bridge with no recovery path. This matches **Critical: Significant loss or permanent locking of user funds**.

---

### Likelihood Explanation

- No privileged access is required; any NEAR account can call `request_refund` for any on-chain deposit UTXO.
- Deposit transactions are publicly visible on the Bitcoin blockchain, giving the attacker all required inputs (`tx_bytes`, `vout`, `proof`).
- The only defense is the DAO rejecting the refund request before `execute_refund` is called, but the attacker can call `execute_refund` immediately after the timelock expires, leaving a narrow reaction window.
- The attack is cheap (only requires a NEAR storage deposit) and repeatable against any deposit.

---

### Recommendation

Add a minimum gas fee check in `request_refund_callback`, validating the user-supplied value against the protocol's configured floor:

```rust
let config = self.internal_config();
require!(
    resolved_gas_fee >= u128::from(config.min_btc_gas_fee),
    "Gas fee below protocol minimum"
);
require!(
    resolved_gas_fee <= u128::from(config.max_btc_gas_fee),
    "Gas fee above protocol maximum"
);
```

This mirrors the analog fix in the original report: just as `IchiVaultSpell` should validate `strategyId` against the user's actual collateral, the bridge should validate the user-supplied `gas_fee` against the protocol's configured bounds rather than accepting any value below the deposit amount.

---

### Proof of Concept

1. Victim deposits 100,000 satoshis to the bridge; the deposit transaction is visible on-chain.
2. Attacker calls `request_refund(deposit_msg, attacker_or_victim_address, tx_bytes, vout, proof, gas_fee=Some(0))`.
3. `request_refund_callback` stores a `RefundRequest` with `gas_fee = 0` and `amount = 100_000`. The only check (`0 < 100_000`) passes.
4. After the timelock elapses, attacker calls `execute_refund(utxo_storage_key, ...)`.
5. `refund_execution_inputs` computes `refund_amount = 100_000 - 0 = 100_000`.
6. `finalize_refund_with_psbt` inserts the UTXO key into `verified_deposit_utxo` and creates a PSBT with output = 100,000 sat (zero miner fee).
7. The refund transaction is broadcast but never mined.
8. `verify_deposit` for this UTXO now permanently fails (`"UTXO already verified via deposit, cannot refund"` / deposit blocked).
9. Victim's 100,000 satoshis are permanently locked with no recovery path.
