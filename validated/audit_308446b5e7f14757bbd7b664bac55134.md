### Title
Missing BTC Address Validation in `request_refund_callback` Causes Permanently Stuck Refund Requests — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund_callback` stores a `refund_address` string in `RefundRequest` without validating it as a parseable BTC address. The parse only happens later in `build_refund_output` via `.expect("Invalid refund address")`. An unprivileged caller can submit a refund request with an invalid BTC address that passes the equality guard, permanently wedging the request and requiring DAO/Operator to manually reject it.

---

### Finding Description

**Entrypoint — `request_refund` is publicly callable.**

`request_refund` sits in a `#[trusted_relayer] #[near] impl Contract` block, but the method itself carries only `#[payable]` and `#[pause]` — no per-method `#[trusted_relayer]` attribute. Every method in that block that actually requires a trusted relayer has the attribute on the method itself (e.g. `verify_refund_finalize`, `remove_refund_pending_tx_id`). `request_refund`, `execute_refund`, and `reject_refund` do not, so they are open to any caller. [1](#0-0) 

**Guard in `internal_request_refund` — equality check only, no address parse.**

When `deposit_msg.refund_address` is `Some(x)`, the only check is that `x == refund_address`. There is no call to `Address::parse` at this point. [2](#0-1) 

**`request_refund_callback` stores the raw string unconditionally.**

After the light-client inclusion proof succeeds, the callback stores `RefundRequest { refund_address, ... }` with no address-format validation. [3](#0-2) 

**`build_refund_output` panics on the invalid address.**

When `execute_refund` is later called, `build_refund_output` calls `Address::parse(refund_address, ...)` and immediately `.expect("Invalid refund address")`, which panics and aborts the transaction. [4](#0-3) [5](#0-4) 

---

### Impact Explanation

- `execute_refund` panics every time it is called for the stuck request; the refund can never proceed.
- The UTXO is blocked from a second `request_refund` (duplicate check in the callback).
- The request can only be cleared by a privileged `reject_refund` call from DAO or Operator, or by a permissionless `reject_refund` after `verify_deposit` finalises the same UTXO.
- The attacker's non-refundable 2 NEAR storage deposit is burned.
- This matches the **Medium** impact: *attacker-triggered temporary locking of bridged funds requiring operator intervention*.

---

### Likelihood Explanation

- The attacker only needs to have made (or control) a real BTC deposit to the address derived from a `deposit_msg` that embeds an invalid `refund_address`. Because `deposit_msg.refund_address` is part of the hashed path, the attacker must have deliberately sent BTC to that specific derived address.
- The 2 NEAR anti-spam deposit is the only cost; it is non-refundable by design, so the attacker accepts this loss.
- The attack is fully self-contained and locally testable.

---

### Recommendation

Validate `refund_address` as a parseable BTC address **before** storing the `RefundRequest`. Add the check in `internal_request_refund` (before the async light-client call) or at the top of `request_refund_callback`:

```rust
// In internal_request_refund or request_refund_callback, before storing:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the existing validation in `build_refund_output` but moves it to the write path so invalid addresses are rejected eagerly.

---

### Proof of Concept

```rust
// 1. Attacker constructs deposit_msg with an invalid refund address
let deposit_msg = DepositMsg {
    recipient_id: "attacker.near".parse().unwrap(),
    refund_address: Some("not_a_btc_address".to_string()),
    ..Default::default()
};

// 2. Attacker sends BTC to the address derived from this deposit_msg,
//    then calls request_refund — equality check passes because both sides
//    are "not_a_btc_address"
contract.request_refund(
    deposit_msg,
    "not_a_btc_address".to_string(),
    tx_bytes,
    vout,
    valid_proof,
    None,
);
// request_refund_callback stores RefundRequest { refund_address: "not_a_btc_address" }

// 3. After timelock elapses, anyone calls execute_refund
contract.execute_refund(utxo_storage_key, None);
// → build_refund_output calls Address::parse("not_a_btc_address", chain)
// → returns Err(...)
// → .expect("Invalid refund address") PANICS
// → request is permanently stuck; DAO/Operator must reject it manually
```
