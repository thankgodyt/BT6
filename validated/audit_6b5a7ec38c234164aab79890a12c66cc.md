### Title
Hardcoded `HistoricityCutoff` Derived from Mainnet-Only Parameters Causes Premature Honest-Peer Disconnection on Non-Mainnet Chains, Weakening Genesis Chain Selection - (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes the `HistoricityCutoff` as `3 * 2160 * 20 + 3600` seconds, embedding Cardano mainnet-specific constants (`k = 2160`, `f = 0.05`, 1-second Shelley slot length). On any chain whose actual stability window exceeds this value — e.g., a chain with a larger security parameter `k` or a smaller active-slot coefficient `f` — the cutoff is **too small**. The ChainSync historicity check will then disconnect honest peers that legitimately send `MsgRollBackward` or `MsgAwaitReply` for headers within the real stability window, stripping the syncing node of honest connections and leaving it exposed to adversarial chain selection.

---

### Finding Description

In `mkGenesisConfig`, the `gcHistoricityCutoff` field is set unconditionally to a single hardcoded wall-clock duration:

```haskell
-- Duration in seconds of one Cardano mainnet Shelley stability window
-- (3k/f slots times one second per slot) plus one extra hour as a
-- safety margin.
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
``` [1](#0-0) 

The three embedded constants are:
- `2160` — Cardano mainnet security parameter `k`
- `20` — `1/f` where `f = 0.05` is the mainnet active-slot coefficient
- `1` (implicit) — Shelley slot length in seconds

The product `3 × 2160 × 20 = 129,600 s ≈ 36 h` is the Shelley stability window on mainnet. Adding `3,600 s` gives `133,200 s ≈ 37 h`.

The `HistoricityCutoff` type is a `NominalDiffTime` (wall-clock seconds):

```haskell
newtype HistoricityCutoff = HistoricityCutoff
  { getHistoricityCutoff :: NominalDiffTime }
``` [2](#0-1) 

Its specification requires it to be **at least the maximum stability-window duration across all eras** of the chain being synced:

```
-- This should be set to at least the maximum duration (across all eras) of a
-- stability window (the number of slots in which at least @k@ blocks are
-- guaranteed to arise).
``` [3](#0-2) 

The enforcement logic in `mkCheck` compares the wall-clock age of the rolled-back header against this cutoff and throws `HistoricityException` (causing disconnection) when the age exceeds it:

```haskell
let actualRollbackAge = arrivalTime `diffRelTime` slotTime
pure $
  when (historicityCutoff < actualRollbackAge) $
    throwError HistoricityException { ... }
``` [4](#0-3) 

This check is active in both `PreSyncing` and `Syncing` GSM states:

```haskell
getCurrentGsmState >>= \case
  PreSyncing -> judgeRollback msg hswt
  Syncing    -> judgeRollback msg hswt
  CaughtUp   -> pure $ Right ()
``` [5](#0-4) 

The design documentation explicitly acknowledges that `HistoricityCutoff` is a constant that does **not** adapt to chain parameters, unlike `Sgen`:

> "One caveat: MaxCaughtUpAge and HistoricityCutoff are indeed constants in the implementation, but Sgen is actually implemented to vary as the chain transitions eras." [6](#0-5) 

---

### Impact Explanation

On a chain where the actual stability window exceeds 133,200 seconds — for example:
- `k = 5,000`, `f = 0.05`, 1-second slots → stability window = `3 × 5000 × 20 = 300,000 s ≈ 83 h`
- `k = 2,160`, `f = 0.01`, 1-second slots → stability window = `3 × 2160 × 100 = 648,000 s ≈ 7.5 days`

…an honest caught-up peer can legitimately send a `MsgRollBackward` rewinding a header that is, say, 200,000 seconds old (well within the real stability window). The syncing node's `HistoricityCutoff` of 133,200 s is smaller than 200,000 s, so `judgeMessageHistoricity` fires `HistoricityException` and the node disconnects from that honest peer.

If this false-positive disconnection affects enough honest peers, the Honest Availability Assumption (HAA) is no longer satisfied. The GSM transitions to `PreSyncing`, which sets the LoE anchor to the ImmutableDB tip — the most conservative possible position. Adversarial peers that remain connected can then serve a denser-looking but non-canonical chain within the Genesis window, causing the syncing node to select it over the honest chain. This is a chain-selection safety failure triggered entirely by crafted (or naturally occurring) rollback messages from an unprivileged peer.

**Impact classification: High** — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The vulnerability is latent on any non-mainnet deployment (private testnet, permissioned chain, or future Cardano network with adjusted `k` or `f`) that enables Genesis (`mkGenesisConfig (Just ...)`) without explicitly overriding `gcHistoricityCutoff`. The `enableGenesisConfigDefault` convenience constructor calls `mkGenesisConfig $ Just defaultGenesisConfigFlags` directly, propagating the hardcoded value with no warning. [7](#0-6) 

The design document notes the community could increase the settlement-time upper bound, which would require `HistoricityCutoff` to increase accordingly — confirming the developers themselves foresee this becoming incorrect. [8](#0-7) 

---

### Recommendation

Replace the hardcoded literal with a value derived from the chain's actual consensus configuration at runtime. The `GenesisConfig` is already constructed with access to the `TopLevelConfig` (which carries `k`, `f`, and per-era slot lengths via `EraParams`). The correct formula is:

```
historicityCutoff = max_over_all_eras(stabilityWindow_era_in_seconds) + safetyMargin
```

where `stabilityWindow_era_in_seconds = (3 * k / f) * slotLength_seconds` for Praos eras and `2 * k * slotLength_seconds` for Byron. This mirrors how `Sgen` is already computed dynamically per era. [9](#0-8) 

At minimum, add a runtime assertion in `mkGenesisConfig` that the provided (or defaulted) `HistoricityCutoff` is not less than the maximum stability-window duration derivable from the supplied chain configuration, and emit a loud warning or error when it is.

---

### Proof of Concept

**Setup:** Private testnet with `k = 5000`, `f = 0.05`, 1-second slots. Actual Shelley stability window = `3 × 5000 × 20 × 1 s = 300,000 s`. Genesis enabled via `enableGenesisConfigDefault`.

**Hardcoded cutoff:** `3 × 2160 × 20 + 3600 = 133,200 s`.

**Trigger sequence:**

1. Syncing node connects to honest peer H and adversarial peer A.
2. H is serving the canonical chain. At some point H sends `MsgRollBackward` to a point whose slot onset is 200,000 seconds ago (legitimate — within the real 300,000 s stability window).
3. `judgeMessageHistoricity` in `mkCheck` computes `actualRollbackAge = 200,000 s > historicityCutoff = 133,200 s` and throws `HistoricityException`. [4](#0-3) 

4. The ChainSync client catches `HistoricityError` and disconnects from H. [10](#0-9) 

5. With H gone, the HAA is no longer satisfied; the GSM transitions to `PreSyncing`.
6. A is now the only connected peer. A serves a non-canonical but denser-looking chain within the Genesis window. The syncing node selects it.
