### Title
Permissionless `request_refund` Allows Front-Running to Redirect Refund Funds or Temporarily Lock Victim's BTC - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
Any unprivileged NEAR account can call `request_refund` for any UTXO with an arbitrary `refund_address` when `deposit_msg.refund_address` is `None`. An attacker who observes a victim's pending `request_refund` call can submit an identical call with their own BTC address first, consuming the shared UTXO key and causing the victim's call to fail. After `unsafe_refund_timelock_sec`, the attacker can call `execute_refund` and redirect the victim's BTC to their own address. The DAO can reject the request during the timelock, but if it does not act, the theft completes.

### Finding Description

**Root cause — no caller binding when `deposit_msg.refund_address` is `None`:**

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no access control and imposes no restriction on who may supply the `refund_address` parameter when `deposit_msg.refund_address` is `None`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
// If deposit_msg.refund_address is None → any caller, any refund_address
``` [1](#0-0) 

**Shared resource — UTXO key claimed first-come-first-served:**

`request_refund_callback` inserts the refund request keyed by `{tx_id}@{vout}` and rejects any subsequent call for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

The stored `refund_address` is whatever the winning caller supplied: [3](#0-2) 

**Execution path — anyone can trigger `execute_refund` after the timelock:**

`execute_refund` has no caller restriction. After `unsafe_refund_timelock_sec` elapses, any account (including the attacker) can call it: [4](#0-3) 

The timelock for the `refund_address`-is-None case is the longer `unsafe_refund_timelock_sec`, explicitly designed to give the DAO time to reject — but the DAO is not guaranteed to act: [5](#0-4) 

**Finalization — BTC is sent to the stored `refund_address`:**

`finalize_refund_with_psbt` builds the refund transaction paying `refund_request.refund_address`, which is the attacker's address if the attacker won the race: [6](#0-5) 

### Impact Explanation

- **If the DAO does not reject within `unsafe_refund_timelock_sec`**: The attacker calls `execute_refund`, the MPC signs a transaction paying the attacker's BTC address, and the victim's deposited BTC is permanently transferred to the attacker. This is **Critical** — significant loss of user funds.
- **If the DAO rejects in time**: The victim must resubmit `request_refund` and wait through the full timelock again. The victim's BTC is temporarily locked and the victim loses their storage deposit. This is **Medium** — attacker-triggered temporary locking of bridged funds.

### Likelihood Explanation

- `request_refund` is a public, permissionless function. All inputs (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are observable from the NEAR transaction being submitted by the victim and from the public Bitcoin chain.
- NEAR does not order transactions by gas price, but an attacker monitoring the NEAR RPC mempool can submit their transaction in the same or an earlier block, making the race winnable without any privileged access.
- The attack requires no special capability: attach the required NEAR storage deposit, copy the victim's proof, substitute a different `refund_address`. Cost is minimal.
- The DAO mitigation is operational, not cryptographic — it depends on active monitoring of every refund request, which is not guaranteed.

### Recommendation

Bind the `refund_address` to the deposit recipient at request time. The simplest fix is to require that when `deposit_msg.refund_address` is `None`, the caller must be `deposit_msg.recipient_id` (the NEAR account that was to receive nBTC), or require `deposit_msg.refund_address` to always be pre-set (non-`None`) so the address is committed at deposit-address-derivation time and cannot be overridden by a third party.

### Proof of Concept

1. Alice sends 1 BTC to the deposit address derived from `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`.
2. Alice calls `request_refund("alice.near", "bc1q_alice...", tx_bytes, vout, proof, None)` attaching the required NEAR storage deposit.
3. Attacker observes Alice's pending NEAR transaction (all parameters are visible in the RPC mempool).
4. Attacker immediately calls `request_refund("alice.near", "bc1q_attacker...", tx_bytes, vout, proof, None)` with the same proof but their own BTC address, attaching the required NEAR deposit.
5. Attacker's `request_refund_callback` executes first; the UTXO key `{alice_txid}@{vout}` is stored with `refund_address = "bc1q_attacker..."`.
6. Alice's `request_refund_callback` panics: `"Refund request already exists for this UTXO"`. Alice's storage deposit is consumed.
7. The DAO does not notice (or is offline). After `unsafe_refund_timelock_sec`, the attacker calls `execute_refund("{alice_txid}@{vout}", None)`.
8. The bridge builds a refund PSBT paying `"bc1q_attacker..."`, the MPC signs it, and 1 BTC (minus gas fee) is sent to the attacker. Alice's BTC is stolen.
