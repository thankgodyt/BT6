Audit Report

## Title
Cross-Chain Replay of `deploy_token`/`deployToken` Signatures Due to Missing Chain ID in Signed Payload — (`starknet/src/omni_bridge.cairo`, `evm/src/omni-bridge/contracts/OmniBridge.sol`, `near/omni-bridge/src/lib.rs`)

## Summary

The NEAR MPC signs a `MetadataPayload` containing only `{ prefix, token, name, symbol, decimals }` with no destination chain identifier. Both the EVM `deployToken` and Starknet `deploy_token` functions reconstruct and verify the identical Borsh-encoded bytes against the same NEAR-derived ECDSA key. A single valid signature obtained from one chain's deployment transaction can be replayed verbatim on every other supported chain, causing unauthorized token deployment and subsequent unauthorized NEAR-side token binding without operator intent.

## Finding Description

**NEAR signing side** (`near/omni-bridge/src/lib.rs`, `log_metadata_callback`): The `MetadataPayload` hashed and sent to the MPC signer contains only five fields — `prefix`, `token`, `name`, `symbol`, `decimals` — with no chain ID, nonce, or destination identifier. [1](#0-0) 

`log_metadata` itself accepts only a `token_id` with no destination chain parameter, so the resulting signature is inherently chain-agnostic. [2](#0-1) 

**EVM verification** (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `deployToken`): The EVM contract reconstructs the exact same five-field Borsh blob and verifies it against `nearBridgeDerivedAddress`. No chain ID is mixed in. [3](#0-2) 

**Starknet verification** (`starknet/src/bridge_types.cairo`, `MetadataPayloadImpl::to_borsh`): The Starknet `to_borsh()` produces the identical byte sequence: `PayloadType::Metadata | token | name | symbol | decimals`. [4](#0-3) 

**Contrast with `fin_transfer`**: `TransferMessagePayload::to_borsh` on Starknet takes an explicit `chain_id: u8` parameter and embeds it twice in the signed bytes, binding the signature to a specific chain. [5](#0-4) 

The EVM `finTransfer` similarly embeds `omniBridgeChainId` twice in the Borsh-encoded payload before hashing. [6](#0-5) 

The `deploy_token` path has no equivalent chain binding. Because both EVM and Starknet verify against the same NEAR MPC-derived key, a signature that passes on one chain passes on every other chain using the same payload format.

**NEAR `bind_token` / `bind_token_callback`**: After a replayed `deploy_token` emits a `DeployToken` event on the target chain, anyone can call `bind_token` (which is callable by unprivileged users when not paused) to submit proof of that event to NEAR. [7](#0-6) 

The only guard in `bind_token_callback` is that the emitter address matches the registered factory for that chain. [8](#0-7) 

Since the `DeployToken` event was emitted by the legitimate registered factory contract on the target chain (the Starknet or EVM bridge contract itself), this check passes unconditionally. NEAR then registers the token for the target chain without the operator ever authorizing deployment on that chain. [9](#0-8) 

**Starknet `deploy_token`**: The function verifies the Borsh signature and deploys the token if `existing_token.is_zero()`. No chain-specific check exists. [10](#0-9) 

## Impact Explanation

This is a **Critical** chain/domain separation flaw enabling unauthorized bridge actions and potential permanent freezing of bridged funds:

1. **Authorization bypass**: An attacker can deploy a bridge token on any supported chain using a signature the operator only intended for one specific chain. This constitutes an unauthorized deployer-equivalent action.
2. **Unauthorized NEAR-side binding**: After the replayed deployment, the attacker can call `bind_token` to register the token on NEAR for the unintended chain, permanently altering bridge state without operator authorization.
3. **Permanent fund freezing**: Once the token is registered on NEAR for the unintended chain, users who call `initTransfer` on that chain lock real assets. If the bridge is not operationally ready (no relayers, incorrect decimal mappings, no release path configured), those assets are permanently frozen with no recovery mechanism.

This matches the allowed Critical impact: *"Cross-chain replay... or chain/domain separation flaw enabling invalid finalization"* and *"Unauthorized transaction, authorization bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

## Likelihood Explanation

The attack requires zero privilege:
- Read a publicly visible `deployToken` or `deploy_token` transaction on any supported chain (trivially observable).
- Submit the identical `(signatureData, metadata)` calldata to a different chain's bridge contract.
- Call `bind_token` on NEAR with proof of the resulting `DeployToken` event.

No keys, no admin access, no MEV infrastructure, no victim interaction required. Any unprivileged observer can execute this immediately after the legitimate deployment transaction is confirmed on the source chain. The attack is repeatable across every supported chain that shares the same payload format.

## Recommendation

Include the destination chain ID in the `MetadataPayload` signed by the NEAR MPC, mirroring the pattern already used in `TransferMessagePayload`:

- **NEAR side** (`log_metadata` / `log_metadata_callback`): Add a `destination_chain: ChainKind` parameter to `log_metadata` and include it as a field in `MetadataPayload` before Borsh-serializing and hashing for MPC signing.
- **EVM side** (`deployToken`): Append `bytes1(omniBridgeChainId)` to `borshEncoded` before computing `keccak256`.
- **Starknet side** (`MetadataPayloadImpl::to_borsh`): Add a `chain_id: u8` parameter (matching the `TransferMessagePayloadImpl::to_borsh` pattern) and append it to the Borsh bytes.

This ensures a signature issued for chain A is cryptographically invalid on chain B.

## Proof of Concept

**Step 1**: Observe a confirmed `deployToken(signatureData, metadata)` call on the EVM bridge for token `"token.near"` with `name="Token"`, `symbol="TKN"`, `decimals=18`. Extract `signatureData` from the transaction calldata.

**Step 2**: The signed bytes on EVM are:
```
keccak256(Borsh(0x01 | "token.near" | "Token" | "TKN" | 0x12))
```
No chain ID. The Starknet `MetadataPayload::to_borsh()` produces the identical byte sequence for the same inputs.

**Step 3**: Submit `deploy_token(signatureData, MetadataPayload { token: "token.near", name: "Token", symbol: "TKN", decimals: 18 })` to the Starknet bridge contract.

**Step 4**: `_verify_borsh_signature` passes (same NEAR-derived key, same hash). `existing_token.is_zero()` passes (not yet deployed on Starknet). Token is deployed and `DeployToken` event is emitted by the legitimate Starknet factory address.

**Step 5**: Call `bind_token` on NEAR with a proof of the Starknet `DeployToken` event. The factory check in `bind_token_callback` passes because the emitter is the registered Starknet factory. NEAR registers `"token.near"` for `ChainKind::Strk` without the operator ever authorizing Starknet deployment.

**Step 6**: Any user who subsequently calls `initTransfer` on Starknet locks real assets. If the bridge is not operationally ready for Starknet, those assets are permanently frozen.

A local integration test can demonstrate Steps 3–5 by deploying both contracts on a local testnet, performing a legitimate EVM deployment, and replaying the extracted signature on the Starknet contract followed by a NEAR `bind_token` call with a mock prover.

        fn deploy_token(ref self: ContractState, signature: Signature, payload: MetadataPayload) {
            assert(!_is_paused(@self, PAUSE_DEPLOY_TOKEN), 'ERR_DEPLOY_TOKEN_PAUSED');

            _verify_borsh_signature(ref self, @payload.to_borsh(), signature);

            let token_id_hash = compute_keccak_byte_array(@payload.token);
            let existing_token = self.near_to_starknet_token.read(token_id_hash);
            assert(existing_token.is_zero(), 'ERR_TOKEN_ALREADY_DEPLOYED');

            let decimals = _normalizeDecimals(payload.decimals);

            let mut constructor_calldata: Array<felt252> = array![];
            (payload.name.clone(), payload.symbol.clone(), decimals)
                .serialize(ref constructor_calldata);

            // Use the low part of the u256 hash to ensure it fits in felt252
            let salt: felt252 = token_id_hash.low.into();
            let (contract_address, _) = deploy_syscall(
                self.bridge_token_class_hash.read(), salt, constructor_calldata.span(), false,
            )
                .unwrap_syscall();

            self.starknet_to_near_token.write(contract_address, payload.token.clone());
            self.near_to_starknet_token.write(token_id_hash, contract_address);

            self
                .emit(
                    Event::DeployToken(
                        DeployToken {
                            token_address: contract_address,
                            near_token_id: payload.token,
                            name: payload.name,
                            symbol: payload.symbol,
                            decimals,
                            origin_decimals: payload.decimals,
                        },
                    ),
                )
        }
