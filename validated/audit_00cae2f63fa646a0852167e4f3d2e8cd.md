### Title
ChainSync Client Disconnects from Peras-Boosted Canonical Chain Due to Empty Weight Snapshot in `checkPreferTheirsOverOurs` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When Peras is enabled, the ChainSync client's `checkPreferTheirsOverOurs` guard uses a hardcoded `emptyPerasWeightSnapshot` instead of the live `PerasWeightSnapshot` when deciding whether to disconnect from a peer. This creates a systematic inconsistency: chain selection (`chainSelSync`) evaluates candidates with real Peras weights, but the ChainSync client evaluates peer chains with zero Peras weights. An unprivileged attacker serving a longer-but-lighter chain can cause an honest node to disconnect from honest peers serving the canonical (Peras-heavier) chain, leaving the node on a non-canonical, lighter chain.

---

### Finding Description

In `checkPreferTheirsOverOurs`, the ChainSync client checks whether a peer's candidate fragment is preferred over the node's current chain. If not, it throws `CandidateTooSparse` and disconnects:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

Meanwhile, `chainSelSync` and `constructPreferableCandidates` use the live `PerasWeightSnapshot` from `cdbPerasCertDB` for all chain comparisons:

```haskell
(succsOf, lookupBlockInfo, curChain, weights) <- atomically $ do
  ...
  <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [2](#0-1) 

The `preferAnchoredCandidate` function, when given a non-empty `PerasWeightSnapshot`, computes `wsvTotalWeight = BlockNo + PerasWeightBoost` and compares chains by total weight, not just length: [3](#0-2) 

The `PerasWeightSnapshot` is populated by `implAddCert` in `PerasCertDB.Impl`, which maps each certified block to its boost weight: [4](#0-3) 

The `getPerasWeightSnapshot` query is available as an STM action on the ChainDB: [5](#0-4) 

The `BlockFetchConsensusInterface` already reads the live snapshot for download decisions: [6](#0-5) 

The inconsistency is therefore isolated to `checkPreferTheirsOverOurs`.

### Impact Explanation

**Concrete attack scenario (when Peras is enabled):**

| | Node's current chain H | Attacker's chain C_A | Honest peer's chain C_P |
|---|---|---|---|
| Block length | 10 | 11 | 9 |
| Peras boost | 0 | 0 | +5 |
| Total weight | 10 | 11 | 14 |

1. `checkPreferTheirsOverOurs` for honest peer P: C_P has length 9 < H's length 10 → `emptyPerasWeightSnapshot` sees C_P as not preferred → **disconnect from P** (CandidateTooSparse).
2. `checkPreferTheirsOverOurs` for attacker A: C_A has length 11 > H's length 10 → stays connected to A.
3. Node downloads C_A's blocks; `chainSelSync` with real weights: C_A weight 11 > H weight 10 → **switches to C_A**.
4. Node is now on C_A (weight 11) instead of the canonical C_P (weight 14).

The node has been steered onto a non-canonical, lighter chain. This violates the Peras security guarantee that the heaviest chain wins. The node's selection diverges from the honest majority's canonical chain.

**Impact class**: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

- Peras is not yet enabled on Cardano mainnet but is an active development target in this repository (the `PerasCertDB`, `PerasVoteDB`, and `WeightedSelectView` infrastructure is fully implemented and wired into `chainSelSync`).
- The TODO comment at the vulnerable line explicitly acknowledges the issue: `-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`.
- No special privileges are required: any peer connection is sufficient to trigger the disconnect of honest peers.
- The attacker only needs to serve a chain that is one block longer than the victim's current chain, which is trivially achievable by any block-producing node.
- The attack window is the period between a Peras certificate arriving (boosting the honest chain) and the node reconnecting to honest peers — during which the node may adopt the attacker's lighter chain.

**Likelihood**: Medium once Peras is activated; the preconditions are realistic and the attacker entry path (peer connection) is fully unprivileged.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` read from the ChainDB. Since `checkPreferTheirsOverOurs` already runs inside an STM transaction, the snapshot can be read atomically alongside the other state:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis = do
  WithFingerprint weights _ <- getPerasWeightSnapshot chainDB  -- live snapshot
  if shouldSwitch $
       preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

This aligns the ChainSync client's peer-retention decision with the same weight function used by `chainSelSync`, eliminating the inconsistency. The referenced issue (`cardano-peras/issues/64`) should be resolved before Peras activation.

### Proof of Concept

**Private testnet sequence:**

1. Start a node N synced to chain H (10 blocks, no Peras certs, weight = 10).
2. Connect honest peer P serving chain C_P (9 blocks, 1 Peras cert boosting block 7 by +5, total weight = 14).
3. Connect attacker peer A serving chain C_A (11 blocks, no Peras certs, total weight = 11).
4. Observe: N's ChainSync client calls `checkPreferTheirsOverOurs` for P with `emptyPerasWeightSnapshot`; C_P length 9 < H length 10 → `CandidateTooSparse` → disconnect from P.
5. Observe: N's ChainSync client stays connected to A (C_A length 11 > H length 10).
6. N downloads C_A; `chainSelSync` with real weights: 11 > 10 → switches to C_A.
7. N is now on C_A (weight 11), not C_P (weight 14). The canonical chain has been abandoned.
