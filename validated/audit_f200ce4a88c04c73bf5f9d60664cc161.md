### Title
User Can Permanently Block Protocol's `cancel_withdraw` by Keeping `pending_sign_capacity` at Limit — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`cancel_withdraw` checks `require_pending_sign_capacity` against the **original withdrawer's** account before creating the cancel RBF. Because the default limit is 1 and a user can freely initiate a new withdraw (via the public `ft_on_transfer` path) after their original withdraw moves to `PendingVerify` stage, they can keep their `btc_pending_sign_ids` perpetually full, causing every `cancel_withdraw` call on their stuck withdrawal to panic. The DAO/Operator has no bypass path.

### Finding Description

In `contracts/satoshi-bridge/src/api/bridge.rs` lines 285–299:

```rust

        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    self.require_pending_sign_capacity(&user_account_id);   // ← checked on the victim user
    self.cancel_withdraw_chain_specific(...);
}
``` [1](#0-0) 

`require_pending_sign_capacity` panics if `pending_sign_count() >= get_max_pending_sign_txs(account_id)`: [2](#0-1) 

The default limit is 1: [3](#0-2) 

`cancel_withdraw` is only reachable when the original tx is in `PendingVerify` stage (enforced by `assert_withdraw_original_pending_verify_tx`): [4](#0-3) 

At that point, the original withdraw ID has already been removed from `btc_pending_sign_ids` by `sign_btc_transaction_callback`: [5](#0-4) 

So `btc_pending_sign_ids` is empty (count=0) when the original withdraw is stuck. The user exploits this window by calling `ft_on_transfer` to initiate a new withdraw B, which inserts B's ID into `btc_pending_sign_ids` (count=1): [6](#0-5) 

Now `1 < 1` is false, and every subsequent `cancel_withdraw(A)` call panics. The user sustains the attack by repeating this cycle.

### Impact Explanation

The bridge's UTXOs consumed by the stuck withdrawal remain permanently locked from the protocol's perspective — `cancel_withdraw` is the only mechanism to reclaim them via RBF. The DAO/Operator has no in-protocol bypass: `cancel_withdraw` unconditionally calls `require_pending_sign_capacity` with no role-based skip path. The only remediation is for the DAO to call `set_pending_tx_limit` to raise the user's limit, but this is a reactive, per-user manual action that the attacker can race against by immediately initiating another withdraw after the limit is raised and their current pending sign tx is signed. [7](#0-6) 

Impact category: **Medium** — attacker-triggered stuck bridge state requiring operator intervention; bridge UTXOs are locked until the DAO manually intervenes per-user.

### Likelihood Explanation

The attack path is entirely public: `ft_on_transfer` is open to any nBTC holder. The user only needs to hold enough nBTC to keep one pending withdraw alive. The cost is low (gas + bridge fees for repeated withdrawals). The attack is deterministic and locally testable.

### Recommendation

Remove `require_pending_sign_capacity` from `cancel_withdraw` (and `cancel_active_utxo_management`). The cancel RBF is a **protocol-initiated** recovery action, not a user-initiated action. The capacity guard exists to prevent users from spamming pending sign slots; it should not apply when the DAO/Operator is forcibly reclaiming stuck UTXOs. Alternatively, add a role-gated bypass: if `predecessor_account_id` holds `Role::DAO` or `Role::Operator`, skip the capacity check.

### Proof of Concept

```
1. alice sends nBTC via ft_on_transfer → withdraw A created, btc_pending_sign_ids = {A}
2. relayer calls sign_btc_transaction(A) for all inputs → A moves to PendingVerify,

3. A is stuck (block_timestamp - A.create_time_sec > max_btc_tx_pending_sec)
4. alice sends nBTC via ft_on_transfer → withdraw B created, btc_pending_sign_ids = {B}
5. DAO calls cancel_withdraw(A) → require_pending_sign_capacity panics:
   "Too many pending sign transactions"
6. alice repeats step 4 whenever B is signed, keeping btc_pending_sign_ids = {B}
