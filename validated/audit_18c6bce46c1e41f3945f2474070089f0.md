### Title
Tokens Permanently Burned/Locked When `normalize_amount(amount - fee) == 0` Due to Missing Pre-Check in `init_transfer` — (`near/omni-bridge/src/lib.rs`)

---

### Summary

The NEAR bridge contract burns or locks user tokens during `init_transfer` without verifying that the post-normalization transfer amount is non-zero. A subsequent call to `sign_transfer` always panics with `InvalidAmountToTransfer` for such transfers, leaving the funds permanently frozen with no recovery path.

---

### Finding Description

The outbound transfer flow (NEAR → EVM/Solana/Starknet) is a two-step process:

**Step 1 — `init_transfer` (via `ft_on_transfer`):**
The only fee validation performed is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

After this check passes, `init_transfer_internal` immediately burns deployed tokens or locks native tokens:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(...);
``` [2](#0-1) 

**Step 2 — `sign_transfer`:**
The relayer calls `sign_transfer`, which computes the normalized amount and enforces:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

`normalize_amount` uses floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [4](#0-3) 

**The gap:** `init_transfer` only checks `fee < amount`, but never checks that `normalize_amount(amount - fee) > 0`. The normalization check only occurs in `sign_transfer`, after the tokens are already burned or locked. When `sign_transfer` panics, the transfer message remains in `pending_transfers` indefinitely and the burned tokens are unrecoverable.

---

### Impact Explanation

**Concrete scenario:**
- A NEAR-native token has `origin_decimals = 24` on NEAR and `decimals = 6` on the EVM destination. The decimal difference is 18.
- A user sends `amount = 5 × 10^17` (0.5 of the smallest NEAR unit), `fee = 0`.
- `init_transfer` passes: `0 < 5×10^17` ✓. Tokens are burned.
- `sign_transfer` computes: `normalize_amount(5×10^17) = 5×10^17 / 10^18 = 0`. Panics with `InvalidAmountToTransfer`.
- The transfer message stays in `pending_transfers`. The burned tokens are gone permanently.

For **deployed (bridge) tokens**, `burn_tokens_if_needed` destroys the tokens on-chain — there is no recovery regardless of any administrative action. For **locked native tokens**, the funds are frozen in the bridge contract with no user-callable cancel path visible in the contract.

---

### Likelihood Explanation

This is reachable by any unprivileged user who calls `ft_transfer_call` on a token contract pointing to the bridge. The user controls `amount` and `fee`. Any amount below the decimal-normalization threshold (e.g., less than `10^(origin_decimals - dest_decimals)` after fee subtraction) triggers the condition. For tokens with large decimal differences (e.g., 24 vs 6 = factor of `10^18`), the threshold is substantial and easy to hit accidentally or deliberately. No special role or privilege is required.

---

### Recommendation

Add a normalization check inside `init_transfer` (before burning/locking) to reject transfers where the post-fee normalized amount would be zero:

```rust
// After computing transfer_message, before burning/locking:
let token_address = self.get_token_address(destination_chain, token_id.clone());
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().unwrap_or(0),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the guard already present in `sign_transfer` and prevents tokens from being burned/locked into an uncompletable state.

---

### Proof of Concept

1. Register a token pair where `origin_decimals = 24`, `dest_decimals = 6` (diff = 18).
2. Call `ft_transfer_call` on the token contract with `receiver_id = omni-bridge`, `amount = "999999999999999999"` (< 10^18), `msg = InitTransferMsg { fee: 0, ... }`.
3. Observe: `ft_on_transfer` → `init_transfer` succeeds, `InitTransferEvent` is emitted, tokens are burned.
4. Call `sign_transfer` with the resulting `transfer_id`.
5. Observe: transaction panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. The transfer message remains in `pending_transfers`. The burned tokens are permanently lost. [5](#0-4) [6](#0-5)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
