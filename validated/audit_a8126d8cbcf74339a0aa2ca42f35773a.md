### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Unauthorized Chain-Selection Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, regardless of content. When Peras is enabled, an unprivileged peer can inject a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` via the ObjectDiffusion mini-protocol. The stub passes it as "validated," it is stored in the `PerasCertDB`, and chain selection is re-run with a full weight boost applied to the attacker-chosen block — a direct analog to the reported "parallel setter bypass" pattern where the intended validation gate is structurally present but effectively absent.

---

### Finding Description

**Root cause — the validation stub**

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gating function before a certificate may be stored or used in chain selection. The only instance in the codebase is the universal catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub wraps *any* `PerasCert` — regardless of round number, boosted-block hash, committee membership, or cryptographic proof — in a `ValidatedPerasCert` and returns `Right`. No check can ever fail.

**Inbound peer path — the "setCap" equivalent**

Certificates received from peers flow through `processCerts`, which is wired as the `opwAddObjects` handler in `makePerasCertPoolWriterFromChainDB`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validatePerasCert` on each certificate and, if all pass, forwards them to `addPerasCertAsync`: [3](#0-2) 

Because the stub always returns `Right`, every peer-supplied certificate passes this gate unconditionally.

**Chain-selection consequence**

`addPerasCertAsync` enqueues the certificate for synchronous processing by `chainSelSync`: [4](#0-3) 

`chainSelSync` for `ChainSelAddPerasCert` adds the certificate to `PerasCertDB` and, if the boosted block is not already on the current chain, triggers a full chain-selection run with the new weight snapshot: [5](#0-4) 

The `PerasWeightSnapshot` used during chain selection is derived directly from the stored certificates: [6](#0-5) 

**The `PerasCert` fields the attacker controls**

```haskell
data PerasCert blk = PerasCert
  { pcCertRound      :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk   -- attacker-chosen block hash + slot
  }
``` [7](#0-6) 

The attacker sets `pcCertBoostedBlock` to any block in the VolatileDB. The stub assigns `vpcCertBoost = perasWeight params` — the full configured Peras weight — to that block.

**Analog to the reported pattern**

| External report | Ouroboros analog |
|---|---|
| `setCap` — high-level setter with zero-address check | `processCerts` — inbound handler with `validatePerasCert` gate |
| `setParameter` — low-level setter, no check, callable directly | `validatePerasCert` stub — always `Right`, gate is structurally present but absent in effect |
| Attacker calls `setParameter` directly, bypassing `setCap` | Attacker sends any `PerasCert`; stub passes it through `processCerts` as if validated |

### Impact Explanation

**Severity: High — chain-selection manipulation**

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's VolatileDB (e.g., a block on an adversarial fork).
2. Send it via the ObjectDiffusion mini-protocol.
3. The stub accepts it; `chainSelSync` applies a `perasWeight`-sized boost to the adversarial block.
4. Chain selection now compares the honest chain against the adversarially boosted fork using `preferAnchoredCandidate`, which incorporates Peras weights.
5. If the boost is sufficient, the node switches to the adversarial fork.

This satisfies: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

It also satisfies: *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

Requires Peras to be enabled via `rnFeatureFlags`. Peras is currently an experimental feature not enabled on mainnet. However, on any private testnet or staging environment where Peras is active, any connected peer can exploit this with a single crafted message — no keys, no stake, no prior knowledge beyond the target block's hash and slot number (both observable from ChainSync).

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before Peras is enabled in any networked environment. At minimum, the implementation must verify:

- The certificate's round number is within the valid acceptance window (`perasCertMaxRounds`).
- The boosted block exists and its slot satisfies `perasBlockMinSlots`.
- The certificate carries a valid quorum proof (committee membership + cryptographic signatures).

Until real validation is implemented, `validatePerasCert` should return `Left PerasValidationErr` by default (fail-closed), not `Right` (fail-open). The `processCerts` function already has the correct structure to reject invalid certificates — the fix is solely in the `validatePerasCert` implementation. [8](#0-7) 

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe a block hash `H` and slot `S` on an adversarial fork via ChainSync.
2. Construct `PerasCert { pcCertRound = <current round>, pcCertBoostedBlock = BlockPoint S H }`.
3. Send it to the target node via the ObjectDiffusion certificate mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` (currently `PerasWeight 15`).
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` adds it to `PerasCertDB` and re-runs chain selection.
6. The adversarial fork now carries a weight boost of 15 blocks. If the honest chain and adversarial fork are within 15 blocks of each other in length, the node switches to the adversarial fork. [9](#0-8)
