### Title
Missing Network Identifier in Peras Vote Signature Hash Enables Cross-Network Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

The `hashVoteSignature` function in `Ouroboros.Consensus.Peras.Crypto.BLS` constructs the signed message for Peras BLS vote signatures using only the round number, boosted block slot, and boosted block hash — with no network identifier included. The sole protection against cross-network replay is the `KeyScope` mechanism embedded in the BLS augmentation string, but `KeyScope` is an unenforced free-form `ByteString` that is never validated against the node's actual `NetworkMagic`. A committee member whose BLS key pair is registered on two networks with the same scope (e.g., mainnet and a testnet fork) will produce vote signatures that are cryptographically valid on both networks, enabling an unprivileged peer to replay observed votes and certificates across networks.

---

### Finding Description

`hashVoteSignature` in `Ouroboros.Consensus.Peras.Crypto.BLS` encodes only three fields into the message that is signed:

```
roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
``` [1](#0-0) 

No network magic, genesis hash, or any other chain-specific identifier is included. The only mechanism intended to provide network separation is the `KeyScope`, which is embedded in the BLS augmentation string as `"VOTE:" <> keyScope <> ":V0"`: [2](#0-1) 

`KeyScope` is defined as a plain `ByteString` with the comment "later instantiated with usage and network id (e.g. PERAS/MAINNET)": [3](#0-2) 

The scope is set at key-loading time via `rawDeserialisePrivateKey scope bs` and stored in the key struct. It is never compared against the node's `NetworkMagic` at any point in the vote signing or verification path. `verifyVoteSignature` reconstructs the BLS context from `publicKeyScope pk` — the scope embedded in the registered committee key — not from any runtime network parameter: [4](#0-3) 

The same gap exists in `hashVRFInput`, which also omits any network identifier from the VRF election input hash: [5](#0-4) 

Certificate verification in both `WFALS.implVerifyCert` and `EveryoneVotes.implVerifyCert` ultimately calls `verifyAggregateVoteSignature`, which delegates to `BLS.verifyWithRole @SIGN` using the scope from the registered key — again with no cross-check against the node's network identity: [6](#0-5) 

---

### Impact Explanation

If a committee member's BLS key pair is registered on two networks with the same `KeyScope` value (which follows naturally from reusing the same key file, since the scope is stored in the key), any vote or certificate produced on network A is cryptographically valid on network B. An unprivileged peer that observes a valid `PerasVote` or `PerasCert` on one network can submit it verbatim on another. The receiving node will pass `verifyVoteSignature` / `verifyAggregateVoteSignature` because the BLS context is identical. This constitutes a bypass of Peras voting and certificate checks, satisfying the **Critical** impact class: unauthorized vote/certificate acceptance without any key compromise.

---

### Likelihood Explanation

The attack requires a committee member to use the same BLS key pair on two networks. This is an operator-level mistake, but the code provides no guard against it: there is no API that derives the scope from `NetworkMagic`, no runtime assertion that the scope matches the network, and no documentation warning that reusing a key across networks is unsafe. Given that Peras is a new protocol and operators will be setting up keys for the first time across mainnet and multiple testnets, accidental key reuse with an identical scope is a realistic operational scenario. Likelihood is **Medium**.

---

### Recommendation

Include a network-specific identifier in `hashVoteSignature` and `hashVRFInput`. The natural choice is the node's `NetworkMagic` (already used as a domain separator in Byron block signing via `ProtocolMagicId`) or the genesis hash. For example:

```haskell
hashVoteSignature networkMagic roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (4 + 8 + 8 + 32)
    $ networkMagicBytes <> roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
  where
    networkMagicBytes = BS.word32BE (unNetworkMagic networkMagic)
    ...
```

Alternatively, enforce at key-loading time that the `KeyScope` is derived from the node's `NetworkMagic` (e.g., `"PERAS/" <> show networkMagic`), and validate incoming votes/certificates against the expected scope before cryptographic verification.

---

### Proof of Concept

1. Committee member Alice generates one BLS key pair and registers it on both Cardano mainnet and the Preview testnet. The key file encodes scope `"PERAS/MAINNET"` (or any fixed string) on both networks.
2. In Peras round `R`, Alice votes for block `B` (slot `S`, hash `H`) on mainnet. Her node calls `signVote perasVoteSignKey R B`, producing signature `σ` over `hashVoteSignature R B` with BLS context `"VOTE:PERAS/MAINNET:V0"`.
3. An attacker observes Alice's `PerasVote` message on the mainnet gossip layer.
4. The attacker submits the identical `PerasVote` to a Preview testnet node. The testnet node looks up Alice's public key from its own committee (same key, same scope `"PERAS/MAINNET"`), reconstructs the same BLS context, and calls `verifyVoteSignature`. The verification succeeds because the signed bytes are identical.
5. If round `R` is active on Preview and block hash `H` coincidentally or adversarially exists there, the replayed vote contributes toward a quorum. Enough such replayed votes allow forging a `PerasCert` that boosts a block on Preview that was never legitimately voted for on that network, corrupting chain selection. [7](#0-6) [8](#0-7)
