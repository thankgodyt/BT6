### Title
Unauthenticated Refund Address Redirection: Any Caller Can Redirect an Unfinalized Deposit's BTC Refund to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The deposit flow cryptographically binds the BTC deposit address to `deposit_msg.recipient_id`, ensuring nBTC is minted only to the intended NEAR recipient. However, the refund flow (`request_refund`) imposes no analogous ownership check: any caller can supply a victim's `deposit_msg` alongside an arbitrary attacker-controlled BTC `refund_address`. If the DAO/Operator fails to reject the request within the `unsafe_refund_timelock_sec` window, the victim's unfinalized BTC is permanently redirected to the attacker.

### Finding Description

**Deposit side — recipient is locked in:**

The deposit address is derived deterministically from the full `deposit_msg` (including `recipient_id`) via `get_deposit_path`:

```rust
// deposit_msg.rs line 49-52
pub fn get_deposit_path(deposit_msg: &DepositMsg) -> String {
    let deposit_msg_string = serde_json::to_string(&deposit_msg).unwrap();
    hex::encode(env::sha256(deposit_msg_string.as_bytes()))
}
``` [1](#0-0) 

The `get_user_deposit_address` call emits a `LogDepositAddress` event that publishes the full `deposit_msg` on-chain, making it observable by any party:

```rust
// api/bridge.rs lines 462-472
pub fn get_user_deposit_address(&self, deposit_msg: DepositMsg) -> String {
    let path = get_deposit_path(&deposit_msg);
    let deposit_address = self.generate_utxo_chain_address(&path).to_string();
    Event::LogDepositAddress {
        deposit_msg,
        path,
        deposit_address: deposit_address.clone(),
    }
    .emit();
    deposit_address
}
``` [2](#0-1) 

**Refund side — no ownership check:**

`internal_request_refund` accepts any caller-supplied `refund_address` without verifying that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`. The only guard is: if `deposit_msg.refund_address` was pre-set, the caller's `refund_address` must match it. When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the caller freely chooses the BTC destination:

```rust
// refund.rs lines 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

The `request_refund_callback` only verifies that the BTC output script matches the deposit address derived from `deposit_msg` — it does **not** verify the caller's identity:

```rust
// refund.rs lines 516-525
let path = get_deposit_path(&deposit_msg);
let deposit_address = self.generate_utxo_chain_address(&path);
let deposit_script_pubkey = deposit_address
    .script_pubkey()
    .expect("Invalid deposit address");
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
``` [4](#0-3) 

The timelock logic explicitly acknowledges the risk of an unverified caller-supplied address by applying a longer `unsafe_refund_timelock_sec`, but this is only a soft mitigation relying on active DAO/Operator monitoring:

```rust
// refund.rs lines 223-227
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [5](#0-4) 

**The inconsistency:** The deposit path enforces `recipient_id` ownership by construction (the deposit address is a hash of the full `deposit_msg`). The refund path enforces nothing about who the caller is relative to `recipient_id`, creating an asymmetry directly analogous to the reported Solana bug.

### Impact Explanation

An attacker who observes a victim's `LogDepositAddress` event (or reconstructs the `deposit_msg` from any on-chain source) can submit a `request_refund` with the victim's `deposit_msg` and the attacker's own BTC address. If the DAO/Operator does not actively monitor and reject the request before `unsafe_refund_timelock_sec` elapses, `execute_refund` will build and sign a BTC transaction paying the attacker. The victim's deposited BTC — which was never minted as nBTC — is permanently lost with no recourse. This constitutes a **critical** loss of user funds.

### Likelihood Explanation

**Medium.** The preconditions are:
1. A deposit that was never finalized (relayer outage, network congestion, or deliberate griefing are realistic triggers).
2. The attacker observes the victim's `deposit_msg` from the public `LogDepositAddress` event emitted by `get_user_deposit_address`.
3. The DAO/Operator fails to reject the malicious refund request within `unsafe_refund_timelock_sec` — plausible during high-volume periods or if monitoring is not 24/7.

All three conditions are reachable by an unprivileged NEAR account with no special access.

### Recommendation

Add an explicit ownership check in `internal_request_refund` (or its public wrapper `request_refund`) that asserts the caller is the intended recipient:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient may request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always pre-set at deposit time (i.e., reject refund requests where `deposit_msg.refund_address` is `None`), eliminating the caller-supplied address path entirely.

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The contract emits `LogDepositAddress` containing the full `deposit_msg` — publicly visible on-chain.
2. Alice sends BTC to the returned deposit address.
3. The relayer fails to finalize the deposit (e.g., outage). Alice's BTC sits unfinalized at the bridge-controlled address.
4. Bob reads Alice's `deposit_msg` from the `LogDepositAddress` event and the BTC transaction proof from the Bitcoin blockchain.
5. Bob calls `request_refund(deposit_msg=Alice's, refund_address="bob_btc_addr", tx_bytes=..., vout=..., proof=...)`, attaching the required NEAR storage deposit.
6. `request_refund_callback` verifies the BTC output matches Alice's deposit address — it passes. The refund request is stored with `refund_address = "bob_btc_addr"`.
7. The DAO/Operator does not notice or reject the request within `unsafe_refund_timelock_sec`.
8. After the timelock, `execute_refund` is called. The bridge constructs and MPC-signs a BTC transaction paying `"bob_btc_addr"`.
9. Alice's BTC is permanently transferred to Bob. Alice cannot recover it.
