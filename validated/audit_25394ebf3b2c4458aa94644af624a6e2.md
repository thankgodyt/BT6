### Title
Peras Quorum Check Unit Mismatch Allows Single-Vote Certificate Forgery - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares accumulated `PerasVoteStake` values — frozen at validation time from the `PerasVoteStakeDistr` — against `perasQuorumStakeThreshold`, a fixed relative (normalized) value in `PerasParams`, without any normalization step. When the `PerasVoteStakeDistr` is populated with absolute ledger stake values (the natural representation), the comparison `absolute_stake >= relative_threshold` is trivially satisfied by any single vote from a pool with positive stake, bypassing the quorum requirement entirely and enabling unauthorized Peras certificate forging.

---

### Finding Description

The analog to the oDAO "stale votes / shrinking denominator" class is a **unit mismatch between the vote tally numerator and the quorum threshold denominator** in the Peras voting subsystem.

**Root cause — `stakeAboveThreshold`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

`PerasVoteStake` is a `Rational` whose value is taken directly from the `PerasVoteStakeDistr` map at vote-validation time:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

The `vpvVoteStake` is then **frozen** inside the `ValidatedPerasVote` and accumulated in `ptvtTotalStake` by `updateTargetVoteTally`: [3](#0-2) 

That accumulated total is what `votesReachQuorum` → `stakeAboveThreshold` compares against the relative threshold: [4](#0-3) 

The `PerasVoteStakeDistr` note confirms the ambiguity:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [5](#0-4) 

When the map is populated with absolute ledger stake (e.g., lovelace counts), a single voter with stake `1_000_000_000` satisfies `1_000_000_000 >= 0.75 + safetyMargin` trivially, declaring quorum with one vote.

**Parallel to the oDAO bug:**

| oDAO | Peras |
|---|---|
| Votes from ex-members remain in the tally (numerator stays high) while member count (denominator) shrinks | `vpvVoteStake` is frozen in absolute units (numerator inflated) while `perasQuorumStakeThreshold` is a relative fraction (denominator equivalent is 1.0) |
| Quorum threshold is artificially lowered | Quorum threshold is trivially crossed by any positive-stake voter |

Both bugs share the same class: **the vote tally and the quorum threshold are not expressed in commensurable units**, allowing the threshold to be bypassed.

---

### Impact Explanation

When `PerasVoteStakeDistr` is populated with absolute stake values (the natural ledger representation), `stakeAboveThreshold` returns `True` for any single vote from a pool with positive stake. This causes `updateCandidateVoteState` to immediately call `forgePerasCert`, producing a `ValidatedPerasCert` for the attacker's chosen block: [6](#0-5) 

That certificate is then added to the ChainDB via `addPerasVoteWithAsyncCertHandling` → `addPerasCertAsync`, triggering chain selection with an adversarially boosted block: [7](#0-6) 

This is a **bypass of Peras certificate quorum verification** enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "bypass of certificate/vote verification" impact class.

---

### Likelihood Explanation

**Currently**: The production diffusion handler hard-codes `pure (PerasVoteStakeDistr mempty)` as the stake distribution, causing all inbound votes to fail `validatePerasVote` (voter not found in empty map). The vulnerability is therefore **not exploitable today**. [8](#0-7) 

**When Peras plumbing is completed**: The TODO comment at that call site explicitly states the empty distribution is a placeholder and will be replaced with real committee selection data. At that point, any pool operator with positive stake can send a single vote over the `hPerasVoteDiffusionClient` mini-protocol and immediately forge a certificate for an arbitrary block, with no further preconditions. Likelihood becomes **high**.

---

### Recommendation

`stakeAboveThreshold` must normalize the accumulated `PerasVoteStake` before comparing it to the relative threshold. Concretely:

1. Pass the total stake of the committee (or the full `PerasVoteStakeDistr`) into `stakeAboveThreshold` so it can compute `accumulated_absolute_stake / total_committee_stake` before comparing against `perasQuorumStakeThreshold`.
2. Alternatively, normalize each `vpvVoteStake` to a relative value at validation time in `validatePerasVote`, ensuring the invariant is enforced at the boundary where votes enter the system.
3. Add a type-level or runtime invariant that `PerasVoteStake` values stored in `ValidatedPerasVote` are always relative (normalized), so the assumption in `stakeAboveThreshold` is guaranteed rather than merely documented.

This mirrors the oDAO recommendation: track the correct denominator alongside the vote tally so the threshold comparison is always meaningful.

---

### Proof of Concept

**Setup**: Populate `PerasVoteStakeDistr` with one entry: `{ poolA -> PerasVoteStake 1_000_000 }`. Use `mkPerasParams` defaults where `perasQuorumStakeThreshold = 0.75`.

**Step 1**: Peer sends one `PerasVote` for poolA targeting block B in round R.

**Step 2**: `processVotes` calls `validatePerasVote mkPerasParams distr vote`. `lookupPerasVoteStake` returns `Just (PerasVoteStake 1_000_000)`. Vote is accepted with `vpvVoteStake = 1_000_000`.

**Step 3**: `implAddVote` calls `updatePerasRoundVoteStates`. `updateCandidateVoteState` calls `votesReachQuorum cfg [vote]`. `stakeAboveThreshold` evaluates `1_000_000 >= 0.75 + safetyMargin` → `True`.

**Step 4**: `forgePerasCert` is called. A `ValidatedPerasCert` for block B in round R is produced with `vpcCertBoost = perasWeight params`.

**Step 5**: `addPerasVoteWithAsyncCertHandling` returns `AddedPerasVoteAndGeneratedNewCert cert` and calls `addPerasCertAsync`, queuing a chain-selection event that boosts block B.

**Result**: One vote from one pool bypasses the quorum requirement (intended: ≥75% of committee stake), forging a certificate for an adversarially chosen block and influencing chain selection. [9](#0-8) [10](#0-9)

    { ptvtVotes
    , ptvtTarget
    , ptvtTotalStake
