### Title
Incorrect `boundX` Constant in `localSortitionNumSeats` Causes Incorrect Peras Voting Seat Allocation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

The `localSortitionNumSeats` function in `LS.hs` passes a hardcoded constant `3` as the `boundX` error-bound parameter to `taylorExpCmpFirstNonLower`, but the function's own specification requires `boundX = e^{|x|}`. Since `x = -lambda`, the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the error bounds are underestimated, causing the Taylor-expansion comparison to produce incorrect seat counts for Peras non-persistent voting committee members. This is the direct analog of M-07: a formula in the code deviates from its own specification, producing systematically wrong results for a large subset of realistic inputs.

---

### Finding Description

`localSortitionNumSeats` determines how many non-persistent committee seats a voter is granted via local sortition (the wFA^LS scheme). The core computation is:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake

orders :: [FixedPoint]
orders =
  (fromRational normalizedVRFOutput / lambda)
    : zipWith (\k prev -> k * prev / lambda) [2 ..] orders

expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3        -- ← hardcoded boundX
      orders
      (-lambda)
``` [1](#0-0) 

The `taylorExpCmpFirstNonLower` function's own documentation states:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

The `x` argument is `-lambda`, so `|x| = lambda`, and the correct `boundX` is `e^lambda`. The code passes `3` instead.

The `errorTerm` inside `decideOne` is computed as:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX < e^lambda`, `errorTerm` is underestimated. The two decision branches then fire with too-narrow uncertainty intervals:

- `cmp >= acc' + errorTerm` (fires too easily → premature "not certainly below" → voter gets **fewer** seats than deserved)
- `cmp < acc' - errorTerm` (fires too easily → premature "certainly below" → voter gets **more** seats than deserved)

The direction of the error for any specific voter depends on whether their VRF-derived threshold `orders[i]` falls just above or just below `e^(-lambda)`. Both directions are reachable.

The developers themselves flag this as an open question:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3) 

The `3` was copied from `checkLeaderNatValue` in `cardano-ledger`, where `x = -sigma * ln(1-f)` and `sigma ≤ 1`, `f ≤ 1`, so `|x|` is always small and `e^{|x|} ≤ e^1 < 3` is a valid conservative bound. For `localSortitionNumSeats`, `lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake` has no such bound: with 10 non-persistent voters and a voter holding 20% of non-persistent stake, `lambda = 2.0`, giving `e^lambda ≈ 7.39 ≫ 3`.

---

### Impact Explanation

The result of `localSortitionNumSeats` is used directly in both vote verification and certificate verification:

```haskell
-- implVerifyVote / implVerifyCert
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure $ WFALSNonPersistentMember seatIndex voterStake vrfOutput nonZeroNumSeats
``` [5](#0-4) 

**Security direction (more seats than deserved):** When the underestimated `errorTerm` causes the "certainly below" branch to fire prematurely for `orders[0]`, the function skips past the zero-seat threshold and returns `Just 1` (or higher). A voter whose VRF output is below the Poisson threshold is incorrectly accepted as a committee member. This constitutes a bypass of Peras non-persistent committee eligibility checks, enabling unauthorized vote and certificate acceptance.

**Correctness direction (fewer seats than deserved):** When the underestimated `errorTerm` causes the "not certainly below" branch to fire prematurely, the voter is denied seats they legitimately earned, weakening the Peras quorum and potentially preventing valid certificates from forming.

Both directions affect chain selection: Peras certificates boost chain weight via `wsvTotalWeight`, so incorrect certificate acceptance or rejection directly influences which chain a node selects. [6](#0-5) 

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is easily satisfied. With a committee of 10 non-persistent voters and any single voter holding more than ~11% of non-persistent stake, `lambda > 1.099`. With 20 voters and 6% stake, the same holds. These are realistic parameters for a live Peras deployment. The bug affects every election in every epoch where such a voter participates, not just adversarially crafted inputs.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

If `exp` on `FixedPoint` is unavailable, use a conservative integer ceiling: `ceiling (exp (toRational lambda))`, or clamp `lambda` to a maximum value that keeps `e^lambda ≤ 3` and document the restriction explicitly.

---

### Proof of Concept

**Parameters:** `numNonPersistentVoters = 10`, `voterStake / totalNonPersistentStake = 0.2`

**Computed lambda:** `lambda = 10 * 0.2 = 2.0`

**Correct boundX:** `e^2.0 ≈ 7.389`

**Actual boundX used:** `3`

**Underestimation factor:** `7.389 / 3 ≈ 2.46×`

For a voter whose `normalizedVRFOutput` places `orders[0]` within `errorTerm` of `e^(-lambda) = e^(-2) ≈ 0.1353`:

- Correct `errorTerm ≈ |err'| * 7.389` → comparison is inconclusive, more Taylor terms computed
- Actual `errorTerm ≈ |err'| * 3` → comparison fires definitively in the wrong direction

Depending on which side of `e^(-lambda)` the threshold falls, the voter is either incorrectly granted a seat (security impact: unauthorized vote) or incorrectly denied a seat (correctness impact: lost voting power). Both outcomes are reachable without any attacker-controlled input beyond the voter's own registered stake and VRF key.
