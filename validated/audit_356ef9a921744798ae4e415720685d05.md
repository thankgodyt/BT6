### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Validation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound Peras certificate, performing zero cryptographic or semantic checks. This placeholder is wired directly into the production node-to-node Peras certificate diffusion inbound handler. Any unprivileged peer can inject arbitrary `PerasCert` values that are accepted without verification, causing the node to store and act on fraudulent certificates that boost adversarial blocks' chain weight.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The only concrete implementation of `validatePerasCert` is the universal instance:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance covers every block type (`instance StandardHash blk => BlockSupportsPeras blk`). No signature, quorum, round-number, or boosted-block validity check is performed. Every certificate is stamped `ValidatedPerasCert` with the full `perasWeight` boost. [2](#0-1) 

**Propagation into the production inbound handler:**

`makePerasCertPoolWriterFromChainDB` passes this stub directly as the validation function:

```haskell
(validatePerasCert mkPerasParams)
``` [3](#0-2) 

`processCerts` then accepts every certificate that passes this check and stores it via `ChainDB.addPerasCertAsync`: [4](#0-3) 

This writer is wired into the live node-to-node protocol stack as `hPerasCertDiffusionClient`:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [5](#0-4) 

**Exploit path:**

1. An unprivileged peer connects to a node via the standard node-to-node Peras certificate diffusion miniprotocol.
2. The peer sends a crafted `PerasCert` with `pcCertBoostedBlock` pointing to an adversarial block of the attacker's choice.
3. `processVotes`/`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert cert (perasWeight mkPerasParams))` unconditionally.
4. The certificate is stored in the ChainDB via `addPerasCertAsync`.
5. The adversarial block now carries a `perasWeight = 15` boost in chain selection, causing honest nodes to prefer it over the canonical chain.

**Contrast with the analogous vote path:**

The vote inbound handler at least attempts a stake-distribution lookup (though it uses an empty `PerasVoteStakeDistr mempty` in production, causing all votes to be rejected): [6](#0-5) 

Certificates have no such guard at all — `validatePerasCert` ignores both `_params` and the stake distribution entirely.

### Impact Explanation

A `ValidatedPerasCert` carries `vpcCertBoost :: PerasWeight` which is used by the Peras chain-selection logic to add weight to a specific block. By injecting arbitrary certificates, an attacker can boost any block — including one on an adversarial fork — causing honest nodes to prefer a non-canonical chain. This is a **Critical** bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection manipulation by any unprivileged peer.

### Likelihood Explanation

The Peras certificate diffusion miniprotocol is part of the production node-to-node handler stack. Any peer that can establish a node-to-node connection can send certificates. No stake, key, or privilege is required. The stub is a universal instance with no conditional guard, so the bypass is deterministic and 100% reliable once the Peras miniprotocol is active.

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic verification: check the aggregate vote signature attesting the quorum, verify the round number is within the valid window, and confirm the boosted block exists on a known chain. Until real validation is implemented, the certificate diffusion inbound handler should reject all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all.

### Proof of Concept

A malicious peer sends a single `PerasCert` message over the Peras certificate diffusion miniprotocol:

```
PerasCert
  { pcCertRound      = <any round number>
  , pcCertBoostedBlock = <point of adversarial block>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert
  { vpcCert      = PerasCert { pcCertRound = <any>, pcCertBoostedBlock = <adversarial> }
  , vpcCertBoost = PerasWeight 15   -- from mkPerasParams
  }
``` [7](#0-6) 

The certificate is stored and the adversarial block gains a weight boost of 15, sufficient to override the canonical chain in Peras chain selection, without the attacker holding any stake or keys.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
