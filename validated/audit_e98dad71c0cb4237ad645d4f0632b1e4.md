### Title
Unprotected `new()` Initializer on nBTC Token Contract Allows Attacker to Seize Controller and Bridge Roles, Enabling Unauthorized Minting — (File: contracts/nbtc/src/lib.rs)

### Summary
The `nbtc` contract's `new()` initializer has no caller restriction. Any NEAR account can call it during the window between contract deployment and the legitimate operator's initialization transaction. An attacker who frontruns this call can set themselves as both `controller` and `bridge_id`, then call `mint()` to create unlimited nBTC.

### Finding Description
`Contract::new()` in `contracts/nbtc/src/lib.rs` accepts arbitrary `controller` and `bridge_id` parameters and writes them directly to state. Its only guard is:

```rust
require!(!env::state_exists(), "Already initialized");
```

There is no check that `env::predecessor_account_id()` equals any authorized deployer. [1](#0-0) 

In NEAR Protocol, deploying a contract (`DeployContract` action) and calling its initializer are two separate transactions unless explicitly batched into one atomic batch transaction. If the operator submits them as two independent transactions — which is the pattern shown throughout this codebase's setup code — there is a block-level window between them. Any NEAR account can observe the deployment on-chain and race to call `new()` first with attacker-controlled arguments:

```
controller = attacker.near
bridge_id  = attacker.near
```

Once state is written, the legitimate operator's `new()` call fails with `"Already initialized"`, and the attacker owns the contract.

The `assert_bridge()` helper that guards `mint()`, `safe_mint()`, and `burn()` is:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
``` [2](#0-1) 

Because the attacker set `bridge_id = attacker.near`, they satisfy this check and can call `mint()` directly:

```rust
pub fn mint(
    &mut self,
    mint_account_id: AccountId,
    mint_amount: U128,
    ...
) {
    self.assert_bridge();
    self.mint_inner(&mint_account_id, mint_amount);
    ...
}
``` [3](#0-2) 

The same `assert_controller()` guard on `set_controller()` and `upgrade_and_migrate()` is also bypassed because the attacker controls `controller`. [4](#0-3) 

### Impact Explanation
**Critical.** An attacker who wins the initialization race becomes the sole `bridge_id` and `controller` of the nBTC NEP-141 token. They can:
- Call `mint()` with arbitrary `mint_account_id` and `mint_amount`, creating unbacked nBTC out of thin air.
- Call `burn()` to destroy legitimate users' balances.
- Call `upgrade_and_migrate()` to replace the contract code entirely.

This constitutes unauthorized minting of nBTC and complete theft/destruction of user funds — matching the Critical tier of the allowed impact scope.

### Likelihood Explanation
**Medium.** NEAR has ~1-second block times and a public RPC. An attacker monitoring for `DeployContract` actions on the known `nbtc.bridge.near` account ID can submit a competing `new()` call in the very next block. No special privilege is required — only a funded NEAR account. The attack is straightforward to automate.

### Recommendation
Batch the `DeployContract` action and the `new()` function call into a single atomic NEAR batch transaction. In the NEAR CLI / near-workspaces pattern this means:

```
account.batch(contract_id)
    .deploy(wasm_bytes)
    .call(Function::new("new").args_json(init_args))
    .transact()
```

This ensures no block exists in which the contract is deployed but uninitialized. Optionally, add a caller restriction inside `new()`:

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

### Proof of Concept
1. Operator submits TX₁: `DeployContract` to `nbtc.bridge.near` (wasm bytes only, no init call).
2. Attacker observes TX₁ in block N and submits TX₂ in block N+1:
   ```
   nbtc.bridge.near::new(
       controller = "attacker.near",
       bridge_id  = "attacker.near",
       name = "nBTC", symbol = "nBTC", decimals = 8
   )
   ```
3. TX₂ passes `require!(!env::state_exists())` because state is still empty. [5](#0-4) 
4. Operator's TX₃ (`new(controller=bridge-ops.near, bridge_id=satoshi-bridge.near, ...)`) panics with `"Already initialized"`.
5. Attacker calls `mint(mint_account_id="attacker.near", mint_amount=U128(u128::MAX), ...)` — `assert_bridge()` passes because `predecessor == bridge_id == "attacker.near"`. [6](#0-5) 
6. Attacker holds unbacked nBTC and can transfer or sell it, draining value from the bridge ecosystem.
