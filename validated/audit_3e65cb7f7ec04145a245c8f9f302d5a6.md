### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Inject Arbitrary Certificates and Manipulate Chain Selection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing no cryptographic or quorum verification. The inbound certificate processing pipeline (`processCerts`) calls this stub directly in production. An unprivileged peer can therefore send a crafted `PerasCert` for any round and any block point, have it accepted and stored in the `PerasCertDB`, and cause the receiving node to apply an illegitimate boost weight to an attacker-chosen block during chain selection.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate for all inbound Peras certificates. The universal instance that is compiled into production code implements this method as an unconditional stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into both production certificate pool writers. `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` both pass `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  (validatePerasCert mkPerasParams)   -- always Right
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [2](#0-1) 

Inside `processCerts`, the only pre-validation guard is a round-number deduplication check (`alreadyInDb`). For any round not yet in the database, the certificate is passed to `validatePerasCert`, which always succeeds, and the certificate is then stored:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2) 

The stored certificate is then used to build a `PerasWeightSnapshot` that directly influences chain selection by assigning boost weight to the certificate's `pcCertBoostedBlock`. [4](#0-3) 

The `PerasCert blk` type itself carries only a round number and a block point — no aggregate BLS signature, no quorum proof, no voter set:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [5](#0-4) 

There is no mechanism to verify that the certificate was produced by a legitimate quorum of committee members, nor any check that the boosted block actually exists or is on a valid chain.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point as `pcCertBoostedBlock` for any round not yet in the local database. The certificate passes `validatePerasCert` unconditionally, is stored in the `PerasCertDB`, and its boost weight (`perasWeight params`) is applied to the attacker-chosen block in the `PerasWeightSnapshot`. Chain selection uses this snapshot to prefer chains containing boosted blocks. The attacker can therefore steer an honest node's chain selection toward a non-canonical or adversarially-controlled chain without holding any stake, keys, or committee membership. This constitutes a chain-selection manipulation reachable by any peer connected via the object-diffusion mini-protocol.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. No authentication, stake, or key material is required to send a `PerasCert` message. The only barrier is the round-number deduplication check, which an attacker trivially bypasses by targeting rounds not yet seen by the victim node (e.g., future rounds or rounds in a fresh node's empty database). The attack requires only a network connection and knowledge of a target block hash.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the aggregate BLS signature over the claimed voter set and confirms that the total stake of the voter set exceeds the quorum threshold, before accepting any inbound certificate.
2. Until the real implementation is in place, the production certificate pool writers (`makePerasCertPoolWriterFromCertDB`, `makePerasCertPoolWriterFromChainDB`) should not be deployed in a network-facing configuration.
3. Track the concrete `V1.PerasCert` type (which carries `pcSignature` and `pcVoters`) through the `BlockSupportsPeras` class so that the validation function has access to the cryptographic material it needs.

---

### Proof of Concept

1. Attacker connects to an honest node via the Peras object-diffusion mini-protocol.
2. Attacker constructs `PerasCert { pcCertRound = R, pcCertBoostedBlock = attackerBlock }` for a round `R` not yet in the victim's `PerasCertDB`.
3. Attacker sends this certificate to the victim node.
4. `processCerts` filters out already-known rounds; `R` is new, so the certificate proceeds to `validatePerasCert mkPerasParams`.
5. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
6. The certificate is stored in the `PerasCertDB` and `attackerBlock` receives `perasWeight params` boost in the `PerasWeightSnapshot`.
7. Chain selection now prefers chains containing `attackerBlock`, diverging from the canonical chain.
