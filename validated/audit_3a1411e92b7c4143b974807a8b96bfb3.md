### Title
Hardcoded Empty Stake Distribution Causes All Peras Votes to Be Permanently Rejected — (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`)

### Summary
In `mkApps` within `NodeToNode.hs`, the `hPerasVoteDiffusionClient` handler passes `pure (PerasVoteStakeDistr mempty)` — a permanently empty stake-distribution map — as the required committee-weight parameter to `makePerasVotePoolWriterFromChainDB`. The code comment explicitly acknowledges the consequence: *"the empty stake distribution will cause all votes to be considered invalid."* Because `validatePerasVote` looks up each voter's weight in this map and always finds nothing, every inbound Peras vote fails validation. `processVotes` then throws `PerasVoteInboundException`, disconnecting the sending peer. No Peras certificate is ever assembled from network-received votes, permanently disabling the Peras chain-selection boost on any node running this code.

### Finding Description
In `mkApps` (NodeToNode.hs lines 391–410), the `hPerasCertDiffusionClient` handler correctly calls `makePerasCertPoolWriterFromChainDB systemTime getChainDB`, but the `hPerasVoteDiffusionClient` handler calls `makePerasVotePoolWriterFromChainDB` with a hardcoded `pure (PerasVoteStakeDistr mempty)` instead of the real stake distribution from the ChainDB:

```haskell
, hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      ( makePerasVotePoolWriterFromChainDB
          systemTime
          -- Note that the empty stake distribution will cause all votes to
          -- be considered invalid.
          (pure (PerasVoteStakeDistr mempty))   -- ← root cause
          getChainDB
      )
``` [1](#0-0) 

Inside `makePerasVotePoolWriterFromChainDB` (ObjectPool/PerasVote.hs line 141), each vote is validated via:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [2](#0-1) 

`validatePerasVote` calls `lookupPerasVoteStake`, which does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. With an empty map this always returns `Nothing`, causing every vote to fail validation. [3](#0-2) 

`processVotes` (ObjectPool/PerasVote.hs lines 178–201) then hits the error branch unconditionally:

```haskell
(errs, _) ->
  throw (PerasVoteValidationError errs)
``` [4](#0-3) 

This exception disconnects the sending peer. No vote is ever stored, no certificate is ever formed, and the Peras chain-selection boost is permanently disabled.

The `PerasVoteDiffusion` miniprotocol is unconditionally included in `NodeToNodeProtocols` — it is not gated behind a feature flag — so the broken handler is always active: [5](#0-4) 

### Impact Explanation
The Peras protocol boosts chain selection by attaching certificate-backed weight to blocks. With all inbound votes permanently rejected, no certificates are ever assembled from peer-diffused votes. The node's chain selection therefore never applies the Peras boost, operating as if Peras were entirely absent. This degrades chain-selection security to pure Praos/TPraos, below the intended security assumptions of a Peras-enabled node. An adversary aware of this can present a competing fork that would normally lose under Peras-boosted chain selection but wins under the degraded Praos-only selection, constituting a chain-selection bug beyond the intended security assumptions.

Additionally, any honest peer that sends valid Peras votes will be disconnected by the receiving node (because the exception is thrown and caught by the `withPeer` bracket), causing repeated disconnections from legitimate Peras-participating peers.

### Likelihood Explanation
The `PerasVoteDiffusion` miniprotocol is unconditionally enabled in `NodeToNodeProtocols` for all node-to-node connections. Any peer running a Peras-enabled node will send votes through this protocol. Every such vote triggers the bug. The root cause is a single hardcoded `mempty` in the production code path, not a configuration or operator error. No special attacker capability is required — normal protocol operation is sufficient to trigger it.

### Recommendation
Replace `pure (PerasVoteStakeDistr mempty)` with an STM action that reads the actual stake distribution from the ChainDB or ledger state, as the TODO comment already prescribes. Until the full committee-selection plumbing is ready, the Peras vote diffusion protocol should either be gated behind a `CardanoFeatureFlag` (consistent with how other experimental features are handled) or the vote writer should silently drop votes rather than throw a peer-disconnecting exception, to avoid breaking connectivity with honest Peras peers.

### Proof of Concept
1. Node A runs with the production `mkApps` handler (hardcoded `PerasVoteStakeDistr mempty`).
2. Node B (Peras-enabled) connects to Node A and sends a batch of valid Peras votes via the `PerasVoteDiffusion` miniprotocol.
3. Node A calls `processVotes` with `getStakeDistrSTM = pure (PerasVoteStakeDistr mempty)`.
4. `lookupPerasVoteStake` returns `Nothing` for every vote → all votes fail validation.
5. `processVotes` throws `PerasVoteInboundException` → Node A disconnects from Node B.
6. No certificate is formed; the Peras chain-selection boost is never applied on Node A.
7. Repeated for every peer: Node A is permanently unable to accumulate Peras certificates from the network, operating without Peras security guarantees for the lifetime of the process.
