Audit Report

## Title
Missing Self-Address Guard in `ACTION_TRANSFER` Allows Permanent Token Stranding at `address(this)` — (File: `evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`coreReceiveWithData` in `HyperliquedBridgeToken` dispatches `ACTION_TRANSFER` without validating that the decoded `recipient` is not `address(this)`. Any HyperCore user can craft a `sendToEvmWithData` payload routing tokens into the token contract itself. A subsequent `ACTION_INIT_TRANSFER` call burns only its own `amount` from `address(this)`, leaving the earlier deposit permanently stranded with no on-chain recovery path.

## Finding Description

In `HlBridgeToken.sol` lines 120–122, the `ACTION_TRANSFER` branch decodes `recipient` from user-supplied `data` and calls `_update(_systemAddress, recipient, amount)` with no guard against `recipient == address(this)`: [1](#0-0) 

In the `ACTION_INIT_TRANSFER` branch (lines 123–135), the contract moves `amount` from `_systemAddress` to `address(this)`, then calls `OmniBridge.initTransfer(address(this), amount128, ...)` — where `amount128` is only the current call's amount, not the full balance of `address(this)`: [2](#0-1) 

`OmniBridge.initTransfer` recognises the token as a `BridgeToken` and calls `BridgeToken(tokenAddress).burn(msg.sender, amount)` for exactly `amount`, not the full balance: [3](#0-2) 

`BridgeToken.burn` calls `_burn(account, value)` for exactly `value`: [4](#0-3) 

There is no sweep, rescue, or admin-withdrawal function anywhere in `HyperliquedBridgeToken` or `BridgeToken`.

**Exploit sequence:**

1. Attacker calls `sendToEvmWithData` with `data = 0x00 || abi.encode(tokenContractAddress)` and `amount = X`. The system address relays this to `coreReceiveWithData`, executing `_update(_systemAddress, address(this), X)`. The token contract now holds X tokens.
2. Any user calls `sendToEvmWithData` with `data = 0x01 || abi.encode(fee, recipient, message)` and `amount = Y` (Y ≠ X). The system address relays this, executing `_update(_systemAddress, address(this), Y)` (contract holds X + Y), then `burn(address(this), Y)` (contract holds X).

After both calls, X tokens are permanently locked in the `HyperliquedBridgeToken` contract.

## Impact Explanation

X tokens are permanently frozen at `address(this)` with no recovery path short of a UUPS proxy upgrade. The HyperCore-side pool (`_systemAddress`) has already been debited, creating permanent accounting drift: HyperCore believes X tokens were transferred to HyperEVM, but they are locked in the contract with no corresponding user credit. This is a direct, irrecoverable loss of bridged funds, matching the Critical impact class: **permanent freezing of bridged funds**.

## Likelihood Explanation

The only access gate is `msg.sender != _systemAddress`. The system address is a trusted relay that forwards whatever `data` a HyperCore user supplies via `sendToEvmWithData` — as explicitly documented in the contract's NatSpec. No special privilege is required beyond being a HyperCore user. The two calls do not need to be from the same user or in the same transaction, and the exploit is trivially repeatable.

## Recommendation

Add a self-address guard in the `ACTION_TRANSFER` branch:

```solidity
if (action == ACTION_TRANSFER) {
    address recipient = abi.decode(tail, (address));
    require(recipient != address(this), "InvalidRecipient");
    _update(_systemAddress, recipient, amount);
}
```

Additionally, in `ACTION_INIT_TRANSFER`, burn the full balance of `address(this)` rather than exactly `amount128` to prevent any pre-existing balance from being silently stranded:

```solidity
uint128 fullBalance = balanceOf(address(this)).toUint128();
IOmniBridgeInitTransfer(owner()).initTransfer(
    address(this),
    fullBalance,
    fee,
    0,
    recipient,
    message
);
```

## Proof of Concept

```solidity
// Setup: HyperliquedBridgeToken deployed, _systemAddress seeded with 1500 tokens
// tokenAddress = address(token)

// Step 1: system address calls ACTION_TRANSFER with recipient = tokenAddress, amount = 500
bytes memory data1 = abi.encodePacked(
    uint8(0), // ACTION_TRANSFER
    abi.encode(tokenAddress)
);
vm.prank(systemAddress);
token.coreReceiveWithData(attacker, bytes32(0), 0, 500, 0, data1);
assertEq(token.balanceOf(tokenAddress), 500);

// Step 2: system address calls ACTION_INIT_TRANSFER with amount = 1000
bytes memory data2 = abi.encodePacked(
    uint8(1), // ACTION_INIT_TRANSFER
    abi.encode(uint128(10), "near:alice.near", "")
);
vm.prank(systemAddress);
token.coreReceiveWithData(attacker, bytes32(0), 0, 1000, 0, data2);
// OmniBridge.initTransfer burns 1000 from tokenAddress
// token.balanceOf(tokenAddress) == 500  <-- permanently stranded
assertEq(token.balanceOf(tokenAddress), 500);
```
