### Title
Accumulated NEAR Deposits from `request_refund` and `execute_refund` Are Permanently Locked with No Withdrawal Path - (File: contracts/satoshi-bridge/src/refund.rs, contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `satoshi-bridge` contract collects mandatory NEAR deposits via `request_refund` and `execute_refund`. These deposits accumulate in the contract's balance with no function available to withdraw them, permanently locking real NEAR value.

### Finding Description
Two public entry points require callers to attach NEAR:

**`request_refund`** (bridge.rs line 508) calls `internal_request_refund`, which enforces:
```rust
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
```
The function's own documentation states: *"The deposit is NOT refunded — it covers request storage and acts as an anti-spam fee."*

**`execute_refund`** (bridge.rs line 580) calls `resolve_execute_refund_timelock`, which enforces:
```rust
require!(
    env::attached_deposit() >= self.required_balance_for_execute_refund(),
    "Insufficient deposit for storage"
);
```
No refund of this deposit is issued either.

Both deposits flow into the contract's own NEAR balance. When the associated storage is later freed — e.g., `internal_reject_refund` removes the `RefundRequest` entry, or `verify_refund_finalize_callback` removes it after on-chain confirmation — the freed storage stake remains in the contract's balance and is never returned to the caller.

The only NEAR-adjacent withdrawal function in the management API is `withdraw_protocol_fee` (management.rs line 21), which transfers **nBTC tokens**, not NEAR. There is no `withdraw_near`, `recover_near`, or equivalent function anywhere in the contract.

### Impact Explanation
Every successful `request_refund` call and every `execute_refund` call permanently locks a non-trivial amount of NEAR in the contract. Over the bridge's lifetime, as refund requests are submitted, executed, and finalized/rejected, the contract accumulates NEAR with no recovery path. This is a stuck-state issue: real value (NEAR) is irreversibly locked in a production bridge contract.

**Impact: Low** — No BTC/nBTC is at risk; the stuck asset is NEAR paid as anti-spam/storage fees. Matches: *"Low. Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
**Likelihood: Low-Medium.** The refund system is a normal operational path. Any user whose BTC deposit was never finalized can call `request_refund` with a valid Light Client proof. Each such call permanently locks NEAR. The accumulation grows monotonically with bridge usage.

### Recommendation
Add a DAO-gated `withdraw_near(amount: NearToken, recipient: AccountId)` function that transfers accumulated NEAR from the contract balance to a designated recipient. Alternatively, refund excess NEAR to the caller when storage is freed (e.g., in `internal_reject_refund` and `verify_refund_finalize_callback`).

### Proof of Concept

1. User calls `request_refund` with a valid BTC proof, attaching `required_balance_for_request_refund()` NEAR. [1](#0-0) 

2. The NEAR deposit is accepted and kept; the `RefundRequest` is stored. [2](#0-1) 

3. DAO later calls `reject_refund`, which removes the `RefundRequest` entry and frees its storage — but the NEAR is not returned. [3](#0-2) 

4. Similarly, `execute_refund` requires its own NEAR deposit with no refund. [4](#0-3) 

5. After `verify_refund_finalize_callback` removes the request, the NEAR from both calls remains locked. [5](#0-4) 

6. The only withdrawal function in the management API transfers nBTC, not NEAR — confirming no recovery path exists. [6](#0-5)

        let total_protocol_fee = self.data().cur_available_protocol_fee;
