Audit Report

## Title
Decimal-Normalization Dust Permanently Locked When `fee = 0` — (File: near/omni-bridge/src/lib.rs)

## Summary
When a user initiates a NEAR → foreign-chain transfer with `fee = 0`, `normalize_amount` floor-divides the locked amount to fit the destination chain's lower precision, silently truncating a sub-unit remainder ("dust"). Because the full pre-truncation amount is locked/burned on NEAR and the transfer record is deleted immediately after MPC signing in the `fee = 0` path, the dust has no recipient and no recovery path — it is permanently frozen in the bridge escrow.

## Finding Description
`normalize_amount` performs integer floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

In `init_transfer_internal`, the **full** pre-normalization amount is locked or burned:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

In `sign_transfer` (L475-480), only `normalize_amount(amount_without_fee())` is included in the MPC-signed payload sent to the destination chain — the truncated value.

**Fee > 0 path (safe):** `claim_fee_callback` computes `fee = transfer_message.amount.0 - denormalized_amount` (L1131), which naturally absorbs the dust and pays it to the relayer.

**Fee = 0 path (vulnerable):** `sign_transfer_callback` deletes the transfer record immediately after signing:

```rust
// near/omni-bridge/src/lib.rs L655-658
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
```

After removal there is no pending `claim_fee` call and no other code path that can recover the dust. The remainder `X − denormalize(normalize(X))` is permanently frozen in the NEAR bridge escrow with no withdrawal, refund, or sweep function.

## Impact Explanation
This constitutes **permanent freezing of bridged user funds**, matching the Critical impact tier: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows." For tokens with a 12-decimal gap (e.g., 18 NEAR decimals vs. 6 EVM decimals, a common USDC-like configuration), the maximum dust per transfer is `10^12 − 1` base units. Every user who sends a non-divisible amount with `fee = 0` permanently loses that dust — it is locked in the NEAR bridge contract with no recovery path.

## Likelihood Explanation
The `fee` field is user-supplied and zero is a natural default for self-relayed or protocol-subsidised transfers. Any unprivileged token holder who calls `ft_transfer_call` (the public `ft_on_transfer` entry point) with a non-round amount and `fee = 0` triggers the loss. No special role, no admin key, and no race condition is required. The condition is repeatable across every such transfer.

## Recommendation
Before locking/burning tokens in `init_transfer_internal`, round the transfer amount down to the nearest multiple of `10^(origin_decimals − decimals)` and return the dust to the sender immediately (or reject amounts that are not already aligned). This ensures `locked_amount == denormalize(normalize(locked_amount))` is always an invariant. Alternatively, in `sign_transfer_callback` for the `fee = 0` case, compute the dust and release it to the original sender before removing the transfer record.

## Proof of Concept
1. Token `T` is registered with `origin_decimals = 18`, `decimals = 6` (12-decimal gap; scale factor = `10^12`).
2. User calls `ft_transfer_call` on the NEAR token contract, sending `amount = 1_000_000_000_001` (1 unit + 1 base unit) to the bridge with `fee = 0`.
3. `init_transfer_internal` locks `1_000_000_000_001` base units on NEAR (L1853-1857).
4. `sign_transfer` normalizes: `normalize_amount(1_000_000_000_001, {18,6}) = 1` (i.e., `1_000_000` in 6-decimal representation); MPC signs this value.
5. `sign_transfer_callback` sees `fee.is_zero()` and calls `remove_transfer_message` — the record is deleted (L656-657).
6. The destination chain receives `1` unit; the `1` base-unit dust (`1_000_000_000_001 − 1_000_000_000_000 = 1`) remains locked in the NEAR bridge escrow forever with no function to recover it.
