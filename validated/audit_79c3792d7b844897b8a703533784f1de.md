### Title
Corrupted UTXO Storage via tx_bytes Replacement with Zero Bytes Causes Permanent UTXO Lock - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
In `internal_safe_verify_deposit_entry`, when `tx_bytes.len() > 10000`, the transaction bytes are silently replaced with `vec![0u8; 300]` (300 zero bytes) before being stored in the UTXO. This corrupts the stored UTXO data, making the UTXO permanently unusable for future withdrawal PSBT construction, effectively locking the deposited BTC in the bridge.

### Finding Description
The `internal_safe_verify_deposit_entry` function contains a size check on the submitted `tx_bytes`: [1](#0-0) 

Despite the log message saying "truncating to 300 bytes", the code does **not** truncate — it replaces the entire `tx_bytes` with 300 zero bytes (`vec![0u8; 300]`). The deposit amount and `script_pubkey` verification are performed against the original `tx_bytes` (decoded into `transaction` before this branch executes), so the deposit passes all validation checks. However, the UTXO is then stored with the zeroed bytes: [2](#0-1) 

When the bridge later attempts to use this UTXO for a withdrawal, it calls `WrappedTransaction::decode(tx_bytes, &config.chain).expect("Deserialization tx_bytes failed")` on the zeroed bytes (e.g., in `verify_withdraw_burn_callback`): [3](#0-2) 

Decoding 300 zero bytes as a Bitcoin transaction will fail, causing a panic. The UTXO remains in the bridge's UTXO set but is permanently unusable. This is the direct analog to the ERC820 `insize` bug: an incorrect size/buffer parameter causes stored data to be silently corrupted, leading to a stuck state — here, `vec![0u8; 300]` instead of the real transaction bytes, just as `0x08` instead of `0x24` caused the wrong data to be passed to the called function.

The `MAX_BOOL_RESULT` and related constants used in promise result reading are correctly sized: [4](#0-3) 

The bug is specifically the `vec![0u8; 300]` replacement, not those constants.

### Impact Explanation
The deposited BTC is locked in the bridge's UTXO set but cannot be used for any withdrawal. The user receives nBTC tokens (minting succeeds because it occurs after the UTXO is stored), but the underlying BTC UTXO is permanently stuck. If multiple such UTXOs accumulate, the bridge's available UTXO pool is depleted, blocking all withdrawals. This matches the allowed impact: permanent locking of user or protocol funds, and stuck bridge state requiring operator intervention (Medium).

### Likelihood Explanation
Bitcoin transactions exceeding 10,000 bytes are uncommon but valid — transactions with many inputs (e.g., consolidation transactions) can exceed this size. The `safe_verify_deposit` path is a public bridge entry point reachable by any proof submitter or bridge user. A user who legitimately deposits via a large Bitcoin transaction, or a relayer who submits such a proof, will trigger this path without any malicious intent, permanently locking the funds. No privileged access is required.

### Recommendation
Replace the zero-byte replacement with a hard rejection:

```rust
if tx_bytes.len() > 10000 {
    env::panic_str("tx_bytes too large: exceeds 10000 bytes");
}
```

Storing corrupted zero bytes silently is strictly worse than rejecting the deposit outright. If large transactions must be supported, the full `tx_bytes` must be stored without modification.

### Proof of Concept
1. Construct a Bitcoin transaction with `> 10,000` bytes (e.g., a consolidation transaction with many inputs) that sends BTC to a bridge deposit address.
2. Call the public `safe_verify_deposit` entry point with the large `tx_bytes` and a valid Merkle proof.
3. The deposit passes validation — amount and `script_pubkey` are verified from the original decoded `transaction`.
4. The UTXO is stored with `vec![0u8; 300]` as `tx_bytes`. [5](#0-4) 
5. Any subsequent withdrawal attempt that selects this UTXO will panic at `WrappedTransaction::decode(tx_bytes, ...).expect("Deserialization tx_bytes failed")`. [3](#0-2) 
6. The BTC is permanently locked in the bridge's UTXO set; the user holds nBTC with no redeemable backing UTXO.
