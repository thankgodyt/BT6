### Title
Peras Vote Validation Does Not Restrict to Active Committee Members — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasVote` implementation in the `BlockSupportsPeras` instance accepts any vote whose sender appears in the stake distribution, without verifying committee membership for the current round, without checking the vote signature, and without validating the round number. This is the direct analog of the external report: just as `execute_redelegate_proxy` does not restrict redelegation to active validators, `validatePerasVote` does not restrict vote acceptance to active committee members.

---

### Finding Description

The `BlockSupportsPeras` instance for `StandardHash blk` — the only production instance — implements `validatePerasVote` as follows:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The `_params` argument (the `PerasCfg`, which carries committee-selection parameters, round boundaries, and quorum thresholds) is discarded entirely. The sole check is `lookupPerasVoteStake`, which is a plain `Map.lookup` on the voter's ID in the stake distribution:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [2](#0-1) 

Three critical checks are absent:

1. **No cryptographic signature verification** — the vote body is never authenticated against the voter's key.
2. **No active-committee-membership check** — any pool present in the stake distribution is accepted, regardless of whether it was selected into the voting committee for the specific round.
3. **No round-number or block-target validation** — the vote's `pvVoteRound` and `pvVoteBlock` fields are never checked against the current protocol state.

This is structurally identical to the external report's root cause: an operation that must be restricted to an active/eligible set proceeds with only a coarse membership check (stake distribution presence vs. active-validator set).

The inbound path is the Peras vote diffusion mini-protocol. In `NodeToNode.hs`, `hPerasVoteDiffusionClient` calls `makePerasVotePoolWriterFromChainDB`, which wires `validatePerasVote` as the sole validator for every batch of votes received from a peer:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` then adds every vote that passes this check to the `PerasVoteDB`, where it contributes to quorum accounting and can trigger certificate forging: [4](#0-3) 

---

### Impact Explanation

Once a vote passes `validatePerasVote` it is treated as a `ValidatedPerasVote` carrying a real stake weight. The `PerasVoteDB` aggregates these weights per `(round, block-target)` pair. When the accumulated weight crosses the quorum threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced. That certificate boosts the targeted block's chain-selection weight, causing honest nodes to prefer it over competing forks.

Because `validatePerasVote` does not check committee membership, an attacker who controls pools collectively holding enough stake to exceed the quorum threshold — but whose pools were **not** selected into the active committee for the round — can still forge a valid certificate for an arbitrary block. This constitutes a bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance, which falls squarely within the "Critical" allowed impact scope.

---

### Likelihood Explanation

The current production wiring in `NodeToNode.hs` passes `PerasVoteStakeDistr mempty` (an empty map) as the stake distribution:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [5](#0-4) 

With an empty distribution, `lookupPerasVoteStake` always returns `Nothing`, so every vote fails validation and the vulnerability is not currently exploitable on a live network. However, this is an explicitly acknowledged temporary placeholder. The moment the real stake distribution is plumbed in — a planned, necessary step for Peras deployment — the incomplete `validatePerasVote` becomes directly exploitable by any peer connected via the vote diffusion mini-protocol, with no further preconditions.

---

### Recommendation

Before wiring a real stake distribution into the vote diffusion path, `validatePerasVote` must be replaced with a full implementation that:

1. **Verifies the vote signature** against the voter's registered public key.
2. **Checks active committee membership** for the specific round, using the committee-selection data derived from `PerasCfg` and the epoch nonce (analogous to how `doValidateVRFSignature` checks pool presence in `lvPoolDistr` before accepting a block header).
3. **Validates the round number** against the current protocol state to reject stale or future-round votes.
4. **Validates the block target** to ensure the voted-upon block is a known, plausible candidate.

The `_params` argument must be used, not discarded.

---

### Proof of Concept

1. Connect to a node as a peer via the Peras vote diffusion mini-protocol (the `hPerasVoteDiffusionClient` handler in `NodeToNode.hs`).
2. Obtain the current `PerasVoteStakeDistr` (e.g., by observing the ledger state). Identify pools with sufficient combined stake to exceed the quorum threshold but that were **not** selected into the active committee for the target round.
3. Craft `PerasVote` objects for those pools, targeting an arbitrary block in the current round. No valid signatures are required because `validatePerasVote` performs no signature check.
4. Send the crafted votes to the node. `processVotes` calls `validatePerasVote` for each; since the voter IDs appear in the stake distribution, all votes pass and are added to the `PerasVoteDB` with their full stake weights.
5. Once the accumulated stake crosses the quorum threshold, `forgePerasCert` is triggered, producing a `ValidatedPerasCert` that boosts the attacker-chosen block's chain-selection weight.
6. The node now prefers the attacker-chosen block over the canonical chain tip.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
