### Title
Missing Vote Stake Normalization in Peras Quorum Check Enables Unauthorized Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares accumulated `PerasVoteStake` directly against `perasQuorumStakeThreshold` without normalizing the vote stake by the total committee stake. The code itself documents this missing scaling step in two separate TODO/NOTE comments. If `PerasVoteStakeDistr` is populated with absolute ledger stake values (which is what the ledger layer provides), the comparison is dimensionally inconsistent — analogous to multiplying by a ratio numerator while omitting the denominator — and quorum can be reached with far fewer votes than the protocol requires.

---

### Finding Description

`stakeAboveThreshold` performs a direct numeric comparison:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The function's own documentation states the assumption it relies on but does not enforce:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type itself carries a companion NOTE:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [3](#0-2) 

The vote stake value is assigned during `validatePerasVote` by a direct lookup from `PerasVoteStakeDistr` with no normalization applied:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [4](#0-3) 

The validated stake then flows directly into `votesReachQuorum`, which calls `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [5](#0-4) 

`votesReachQuorum` is the gate that triggers certificate forging in `updateCandidateVoteState`: [6](#0-5) 

The `PerasVoteStakeDistr` is supplied at runtime via `getStakeDistrSTM`, which is wired from the ledger's pool distribution. The ledger's `IndividualPoolStake.individualPoolStake` is a `Rational` representing each pool's fraction of **total** stake, not its fraction of the **voting committee** stake. The correct denominator for the quorum comparison is the total committee stake, not the total network stake. Because the committee is a strict subset of all pools, these two denominators differ, and the missing division step means the accumulated vote stake is systematically under-scaled relative to the threshold — or, if absolute lovelace values are ever passed, over-scaled by many orders of magnitude.

---

### Impact Explanation

**Scenario A — absolute values passed (most dangerous):** If `PerasVoteStakeDistr` is populated with raw lovelace amounts (e.g., a pool holding 1 ADA = 1 000 000 lovelace), then `stake = 1 000 000` while `quorumThreshold = 0.75`. The condition `1 000 000 >= 0.75` is always true. A single vote from any registered pool — regardless of its actual share — causes `votesReachQuorum` to return `Just`, a `ValidatedPerasCert` is forged, and the boosted block is accepted into chain selection. This is a complete bypass of the Peras quorum requirement.

**Scenario B — relative-to-total-stake values passed:** If `individualPoolStake` (already a fraction of total stake) is used directly, the sum of all committee votes equals `totalCommitteeStake / totalNetworkStake`, which is typically well below 0.75. Quorum can never be reached, permanently disabling Peras certificate production and its chain-selection boost, degrading the protocol's security guarantees.

Both scenarios represent a bypass of Peras voting/certificate checks caused by the missing normalization step, matching the "Critical — bypass of Peras voting or certificate checks enabling unauthorized certificate acceptance" and "High — chain selection bug" impact categories.

---

### Likelihood Explanation

The Peras protocol extension is under active development. The two TODO/NOTE comments are present in production source files (not tests), and the `getStakeDistrSTM` injection point has no type-level enforcement of normalization. Any pool operator — an unprivileged network participant — can submit votes via the Peras vote miniprotocol. The `processVotes` entry point accepts votes from peers, validates them through `validatePerasVote`, and adds them to the vote database, making the full path reachable without operator compromise. [7](#0-6) 

---

### Recommendation

1. **Enforce units at the type level.** Introduce distinct newtypes for absolute stake and normalized (relative) stake so that `stakeAboveThreshold` cannot accidentally receive an un-normalized value.
2. **Normalize at the validation boundary.** In `validatePerasVote` (or in the function that populates `PerasVoteStakeDistr`), divide each pool's ledger stake by the total committee stake before storing it as `PerasVoteStake`.
3. **Resolve the open TODO.** The NOTE on `PerasVoteStake` and the TODO on `stakeAboveThreshold` document an unresolved design question. This must be resolved before the Peras protocol is enabled on any live network.

---

### Proof of Concept

Given `mkPerasParams` defaults and a `PerasVoteStakeDistr` populated with absolute lovelace values:

```
pool A: 1 ADA = 1_000_000 lovelace  →  PerasVoteStake = 1_000_000
perasQuorumStakeThreshold = 0.75 (relative)
safetyMargin = 0 (default)

stakeAboveThreshold:
  stake = 1_000_000
  threshold = 0.75
  1_000_000 >= 0.75  →  True
```

A single vote from pool A causes `votesReachQuorum` to return `Just`, `updateCandidateVoteState` to call `forgePerasCert`, and the resulting `ValidatedPerasCert` to be stored and applied as a chain-selection boost — all without the intended ¾-of-committee-stake quorum being satisfied.

  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
