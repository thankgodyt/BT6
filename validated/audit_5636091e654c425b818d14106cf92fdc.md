### Title
Attacker Can Redirect BTC Refund to Arbitrary Address When `deposit_msg.refund_address` Is `None` - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None`, the `request_refund` function accepts any caller-supplied `refund_address` without ownership or authorization checks. Because `request_refund` is permissionless, an attacker can front-run the victim and register a refund request pointing to the attacker's own BTC address, permanently redirecting the victim's deposited BTC.

---

### Finding Description

`DepositMsg.refund_address` is an `Option<String>` field — it is explicitly optional and may be `None`. [1](#0-0) 

In `internal_request_refund`, the only guard on the caller-supplied `refund_address` parameter is a conditional check that fires **only when** `deposit_msg.refund_address` is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`, this block is skipped entirely. The caller-supplied `refund_address` is forwarded to `request_refund_callback` and stored verbatim into the `RefundRequest`: [3](#0-2) 

The stored `refund_address` is later used directly to construct the Bitcoin output in `build_refund_output`, which pays the refund UTXO to that address: [4](#0-3) 

`request_refund` is a public, permissionless function — the documentation explicitly states "Anyone who knows the deposit_msg can request a refund." There is no check that the caller is the original depositor or the intended recipient. [5](#0-4) 

The `request_refund_callback` does verify that the BTC transaction output matches the deposit address derived from `deposit_msg`, but this only proves the UTXO is real — it does not validate who is entitled to receive the refund: [6](#0-5) 

A "first-come, first-served" deduplication check prevents a second refund request for the same UTXO, meaning whoever registers first wins: [7](#0-6) 

---

### Impact Explanation

**Critical — permanent theft of user BTC funds.**

An attacker who calls `request_refund` before the victim, supplying their own BTC address as `refund_address`, will have that address stored as the sole refund destination. Once the timelock passes and `execute_refund` is called, the bridge's MPC-signed Bitcoin transaction pays the attacker's address. The victim's deposited BTC is permanently lost with no recovery path.

---

### Likelihood Explanation

**Medium.** The preconditions are realistic:

1. **`deposit_msg.refund_address: None`** — The field is optional and the codebase explicitly supports and tests this case (`test_refund_no_refund_address`). Users who do not know their BTC refund address at deposit time, or who use a dApp that omits this field, are vulnerable.
2. **Relayer fails to finalize the deposit** — Relayer downtime, network issues, or a user who changes their mind are all documented scenarios.
3. **Attacker learns the `deposit_msg`** — `get_user_deposit_address` is a public view call; its arguments are visible on-chain. The BTC deposit transaction is also publicly visible, and the `deposit_msg` can be reconstructed by scanning NEAR for matching `get_user_deposit_address` calls.
4. **Attacker front-runs the victim** — Since `request_refund` is permissionless and the UTXO is public, the attacker simply submits the call with their own address before the victim does. [2](#0-1) 

---

### Recommendation

When `deposit_msg.refund_address` is `None`, the contract should either:

1. **Require the caller to be the `recipient_id`** — Only the NEAR account named in `deposit_msg.recipient_id` should be permitted to supply an arbitrary `refund_address` when none was pre-committed.
2. **Or require `deposit_msg.refund_address` to always be `Some`** — Make the field mandatory so the refund destination is always committed at deposit-address-generation time and cannot be overridden by a third party.

Option 1 is the minimal fix; option 2 eliminates the ambiguity entirely.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The call and its arguments are publicly visible on NEAR.
2. Alice sends 1 BTC to the returned deposit address. The BTC transaction is publicly visible on-chain.
3. The relayer goes offline; `verify_deposit` is never called.
4. Attacker observes Alice's `deposit_msg` from step 1 and the BTC transaction from step 2.
5. Attacker calls `request_refund(alice_deposit_msg, "attacker_btc_address", tx_bytes, vout, proof)`.
6. In `internal_request_refund`, `deposit_msg.refund_address` is `None`, so the guard at line 154 is skipped. The attacker's address passes through unchecked.
7. `request_refund_callback` verifies the UTXO is real (script matches `deposit_msg` hash) — it passes, because the `deposit_msg` is genuine.
8. `RefundRequest { refund_address: "attacker_btc_address", ... }` is stored. The deduplication check now blocks any subsequent `request_refund` for this UTXO.
9. After the timelock, attacker calls `execute_refund`. The bridge builds and MPC-signs a Bitcoin transaction paying `attacker_btc_address`.
10. Alice's 1 BTC is permanently transferred to the attacker. [2](#0-1) [7](#0-6) [3](#0-2)

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
