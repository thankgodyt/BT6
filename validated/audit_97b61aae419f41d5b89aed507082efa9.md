### Title
Repeated MPC Sign Requests Without In-Flight Guard in `sign_btc_transaction` — (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary
`sign_btc_transaction` dispatches an MPC sign request to NEAR Chain Signatures but sets no "signing in progress" flag before the async call. The only guard — `signatures[sign_index].is_none()` — is only written in the callback. Any unprivileged caller can invoke `sign_btc_transaction` multiple times for the same `sign_index` before the MPC callback returns, dispatching multiple duplicate sign requests to the MPC service at no cost.

### Finding Description
In `internal_sign_btc_transaction`, the function reads `btc_pending_info.signatures[sign_index].is_none()` as a guard before dispatching the MPC call: [1](#0-0) 

The signature slot is only written inside `sign_btc_transaction_callback`: [2](#0-1) 

Between the moment `sign_btc_transaction` is called and the moment the MPC callback returns, `signatures[sign_index]` remains `None`. Every concurrent or rapid-sequential call to `sign_btc_transaction` with the same `btc_pending_sign_id` and `sign_index` passes the guard and dispatches a fresh MPC sign request: [3](#0-2) 

`sign_btc_transaction` is public with no access control and no caller restriction: [4](#0-3) 

The `sign_promise` helper forwards `env::attached_deposit()` to the MPC contract on every call: [5](#0-4) 

This is the direct analog of the `prepareSettleRaffles` griefing pattern: a public function triggers an expensive external async request, the "already in progress" state is only recorded in the callback, and no flag prevents re-entry during the async window.

### Impact Explanation
**Low — publicly reachable invariant violation and griefing of the MPC service.**

- Multiple MPC sign requests are dispatched for the identical `(payload, path, key_version)` tuple, wasting MPC network resources.
- Any NEAR attached by the caller is forwarded to the MPC on each call; if the MPC does not refund failed/duplicate requests, those deposits are lost.
- The first successful callback sets `signatures[sign_index]`; all subsequent callbacks panic at `require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed")`, reverting without corrupting bridge state — so there is no direct fund theft.
- However, the MPC provider observes multiple in-flight requests for the same payload and could selectively delay or withhold fulfillment, stalling the signing pipeline and requiring operator intervention to recover.

### Likelihood Explanation
High reachability. `sign_btc_transaction` is a public, permissionless function. The `btc_pending_sign_id` is emitted in the `GenerateBtcPendingInfo` event and is observable by any on-chain watcher. Any NEAR account can call the function with 0 attached NEAR (the function is `#[payable]` but imposes no minimum deposit), making the attack essentially free for the attacker.

### Recommendation
Set a per-`sign_index` "signing in progress" flag atomically before dispatching the MPC call, and clear it in the callback (on both success and failure). For example, add a `signing_in_progress: Vec<bool>` field to `BTCPendingInfo`, set `signing_in_progress[sign_index] = true` before `sign_promise(...)`, and reset it to `false` in `sign_btc_transaction_callback` if the MPC call fails. Reject any call to `sign_btc_transaction` where `signing_in_progress[sign_index]` is already `true`.

### Proof of Concept
1. A user initiates a withdrawal; `ft_on_transfer` creates a `BTCPendingInfo` with `signatures = [None, None]` and emits `GenerateBtcPendingInfo { btc_pending_id }`.
2. An attacker observes `btc_pending_id` from the event log.
3. The attacker submits N rapid calls to `sign_btc_transaction(btc_pending_id, 0, 0)` with 0 attached NEAR.
4. Each call reaches `internal_sign_btc_transaction`, reads `signatures[0].is_none() == true` (the callback has not yet returned), and dispatches a new MPC sign request.
5. N MPC sign requests are now in flight for the same `(payload, path)`.
6. The first MPC callback to return sets `signatures[0] = Some(sig)` and advances the state.
7. The remaining N-1 callbacks panic at `require!(signatures[0].is_none(), "Already signed")`, reverting without effect — but the MPC has already processed N requests.
8. If the MPC does not refund the attached deposits from the N-1 failed callbacks, those NEAR tokens are lost. The signing pipeline may be stalled if the MPC throttles or rejects the legitimate request due to the flood. [6](#0-5) [7](#0-6)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }

    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
