### Title
`internal_verify_deposit` per-UTXO `get_confirmations` check allows batch-split deposits to bypass higher confirmation tiers — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
`internal_verify_deposit` calls `get_confirmations` with only the individual UTXO's satoshi amount. When the `confirmations_strategy` is configured with multiple tiers (e.g., 2 confirmations for amounts < 10,000,000 sat, 6 confirmations for amounts ≥ 10,000,000 sat), a depositor can split a large deposit into N smaller UTXOs — each individually below the higher-tier threshold — so that every individual deposit is verified against the lower confirmation count. The bridge mints nBTC for the full aggregate value after only the minimum number of confirmations, bypassing the elevated confirmation requirement that exists to guard against double-spend attacks on high-value deposits.

### Finding Description
In `internal_verify_deposit`, the number of required confirmations is determined solely by the individual UTXO's `deposit_amount`:

```rust
// deposit.rs:30-31
let confirmations = if deposit_msg.extra_msg.is_none() {
    self.get_confirmations(config, deposit_amount)
```

`get_confirmations` (delegating to `Config::get_confirmations`) iterates the sorted `confirmations_strategy` keys and returns the tier whose key is the first one strictly greater than `satoshi_amount`:

```rust
// config.rs:208-210
for key in &keys {
    if *key > satoshi_amount {
        return u64::from(...);
    }
}
```

There is no cross-UTXO or cross-deposit aggregation. Each call to `verify_deposit` / `verify_deposit_v2` is evaluated in isolation. A user who wants to deposit an amount `A` that would fall into a higher confirmation tier can instead send `N` BTC transactions each carrying `A/N` satoshis (each strictly below the tier boundary), submit `N` separate `verify_deposit` calls, and have every one of them verified against the lower confirmation count. The `verified_deposit_utxo` guard only prevents re-submission of the same UTXO; it does not prevent multiple distinct UTXOs from being submitted in parallel.

The same per-UTXO pattern appears in `internal_request_refund` (`refund.rs:168`) and `internal_verify_active_utxo_management` (`active_utxo_management.rs:20`), but the deposit path is the primary user-facing entry point.

### Impact Explanation
The `confirmations_strategy` is the bridge's primary defence against BTC double-spend attacks on high-value deposits. Requiring more confirmations for larger amounts means a reorganisation attack must be deeper (and therefore more expensive) to succeed. By splitting a large deposit into sub-threshold UTXOs, an attacker reduces the required reorganisation depth from, say, 6 blocks to 2 blocks for the full deposited value. If a double-spend succeeds, nBTC is minted against BTC that is subsequently reversed on-chain, permanently inflating nBTC supply beyond its BTC backing — a direct loss of protocol funds. This maps to **Medium: bypass of bridge limits or policies** (the confirmation policy is a bridge-enforced limit; the double-spend itself is an external step that requires hash power, making Critical classification inappropriate).

### Likelihood Explanation
The bypass is trivially reachable by any unprivileged NEAR account acting as depositor: they control the BTC transaction structure and can create as many sub-threshold UTXOs as needed. The only prerequisite is that the operator has deployed a multi-tier `confirmations_strategy` (the config struct and `get_confirmations` logic are explicitly designed for multiple tiers; a single-tier deployment collapses the issue). The subsequent double-spend requires significant hash power, but the confirmation bypass itself is zero-cost to the attacker.

### Recommendation
Aggregate the deposited satoshi amount per recipient (or per deposit-address path) across all pending/unconfirmed UTXOs before computing the required confirmation count, and apply the highest applicable tier to the aggregate. Alternatively, document explicitly that the confirmation policy is intentionally per-UTXO and accept the residual risk, adjusting tier boundaries accordingly.

### Proof of Concept
1. Configure `confirmations_strategy: {"10000000": 2, "100000000": 6}` (2 confirmations for < 10 M sat, 6 for ≥ 10 M sat).
2. Attacker wants to deposit 50,000,000 sat (5 × 9,999,999 sat = 49,999,995 sat, each below 10 M sat threshold).
3. Attacker broadcasts 5 BTC transactions, each paying 9,999,999 sat to their deposit address.
4. After 2 BTC confirmations, attacker (or a relayer) calls `verify_deposit` / `verify_deposit_v2` for each UTXO.
5. Each call passes `get_confirmations(config, 9_999_999)` → returns 2 (the low tier).
6. Bridge mints ~49,999,995 sat worth of nBTC after only 2 confirmations.
7. Attacker attempts a 2-block chain reorganisation to double-spend all 5 transactions; if successful, nBTC supply exceeds BTC backing by ~49,999,995 sat.
8. A single 50,000,000 sat deposit would have required 6 confirmations, making the same reorganisation attack 3× more expensive.

```rust
    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
```
