### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates, Enabling Unauthorized Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, regardless of content. Because this function is the sole cryptographic gate between the peer-facing Peras certificate diffusion mini-protocol and the `PerasCertDB` / chain-selection pipeline, any unprivileged peer can inject an arbitrary `PerasCert` that boosts any block in the VolatileDB, causing the honest node to prefer a non-canonical chain. The analog to the OptimismHubConnector bug is exact: a message-processing path that skips origin/authenticity verification allows fraudulent state to be inserted.

---

### Finding Description

**Root cause — the no-op validator**

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a stub implementation of `validatePerasCert` that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No committee membership check, no quorum signature verification, no round-number sanity check, and no boosted-block eligibility check is performed. The function wraps the raw peer-supplied `PerasCert` directly into a `ValidatedPerasCert` and returns it as valid.

**Attacker-controlled entry path**

The node-to-node diffusion layer wires the Peras certificate inbound handler directly to `makePerasCertPoolWriterFromChainDB`, which calls `processCerts` with the stub validator:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [2](#0-1) 

Inside `makePerasCertPoolWriterFromChainDB`, the validation call is:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` filters out already-known round numbers (the only guard), then calls `validateCert` on each remaining certificate. Because the stub always returns `Right`, every new-round certificate passes:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [4](#0-3) 

**Chain-selection consequence**

Each accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. The `chainSelSync` handler then adds the certificate to `PerasCertDB` and, if the boosted block is present in the VolatileDB, calls `chainSelectionForBlock` for that block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The boost weight applied is `perasWeight mkPerasParams = 15`, which is added to the chain weight of the boosted block's chain. This can tip chain selection in favour of a non-canonical fork.

**The `PerasCertDB.addCert` layer adds no validation either** — it only deduplicates by round number:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do ...
``` [6](#0-5)

### Impact Explanation

**High — chain-selection manipulation by an unprivileged peer.**

An attacker who is a connected peer can craft a `PerasCert` with:
- `pcCertRound` set to any round not yet in the local `PerasCertDB`, and
- `pcCertBoostedBlock` pointing to any block hash present in the node's VolatileDB (learnable via ChainSync).

The certificate is accepted without any cryptographic check, stored, and triggers chain selection that adds `perasWeight = 15` to the target block's chain. If the attacker's chosen block is on a minority fork, the honest node may switch to that fork, diverging from the canonical chain. This satisfies the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**High.** The Peras certificate diffusion mini-protocol is a standard node-to-node protocol, reachable by any peer that can establish a connection. No stake, no keys, and no operator access are required. The attacker only needs to know a block hash present in the target node's VolatileDB (trivially obtained via ChainSync) and to send a single well-formed `PerasCert` CBOR message with a fresh round number. The stub is the active production code path, not a test shim.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. Committee membership and VRF/KES eligibility of each signer.
2. Quorum threshold (≥ 3/4 of committee stake, per `perasQuorumStakeThreshold`).
3. That the boosted block's slot satisfies `perasBlockMinSlots` and falls within the valid round window.
4. That the certificate round number is consistent with the current chain state.

Until the real implementation is ready, the inbound handler in `makePerasCertPoolWriterFromChainDB` should reject all externally received certificates (return a hard error or drop them silently) rather than forwarding them to chain selection with a no-op validator. The existing TODO comment at `SupportsPeras.hs:350` and the tracking issue `cardano-peras/issues/120` confirm this is a known placeholder, but the production wiring in `NodeToNode.hs` makes it an active vulnerability.

---

### Proof of Concept

1. Connect to a target node as a standard peer (node-to-node protocol).
2. Observe a block hash `H` on a minority fork via ChainSync (the block must be in the target's VolatileDB).
3. Send a `PerasCert` message via the Peras certificate diffusion protocol with:
   - `pcCertRound = R` (any round not yet in the target's `PerasCertDB`)
   - `pcCertBoostedBlock = H`
4. The target node's `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = 15}` unconditionally.
5. The certificate is stored in `PerasCertDB` and `chainSelectionForBlock` is triggered for block `H`.
6. Chain selection now adds weight 15 to the chain containing `H`. If that chain was previously equal to or within 15 weight units of the canonical chain, the node switches to the minority fork.
