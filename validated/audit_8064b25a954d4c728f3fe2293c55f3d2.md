### Title
Missing Chain ID in `deployToken` Signed Payload Enables Cross-Chain Replay Attack - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/bridge_types.cairo`)

### Summary

The `deployToken` function in both the EVM and Starknet bridge contracts does not include the destination chain ID in the signed payload. In contrast, `finTransfer` correctly binds its signature to the destination chain via `omniBridgeChainId`. Because the same `nearBridgeDerivedAddress` (derived from the same NEAR MPC key) is used across all supported chains, a valid NEAR-signed `deployToken` message for one chain can be replayed verbatim on any other chain that shares the same borsh encoding format.

### Finding Description

**EVM `OmniBridge.sol` — `deployToken`** constructs its signed payload as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No `omniBridgeChainId` is included. [1](#0-0) 

Compare this to `finTransfer`, which correctly embeds `omniBridgeChainId` twice (for token address and recipient chain binding): [2](#0-1) 

**Starknet `bridge_types.cairo` — `MetadataPayloadImpl::to_borsh`** similarly omits chain ID:

```cairo
fn to_borsh(self: @MetadataPayload) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
``` [3](#0-2) 

This is called from `deploy_token` without any chain ID argument: [4](#0-3) 

Whereas `fin_transfer` correctly passes `self.omni_bridge_chain_id.read()`: [5](#0-4) 

The borsh encoding structure for `deployToken` is byte-for-byte identical between EVM and Starknet: `[0x01 || borsh(token) || borsh(name) || borsh(symbol) || decimals]`. Both verify the keccak256 of this encoding against the same Ethereum-style `nearBridgeDerivedAddress`. The Starknet CLAUDE.md even explicitly documents chain ID binding as a security property for `fin_transfer` but makes no such claim for `deploy_token`: [6](#0-5) 

### Impact Explanation

An attacker who observes a legitimate `deployToken` transaction on any supported chain (Ethereum, Arbitrum, Base, Polygon, BNB, Starknet, Abstract) can extract the signature and payload and replay it on every other chain that shares the same `nearBridgeDerivedAddress`. This results in:

1. **Unauthorized bridge token deployment**: Bridge tokens are deployed on chains where NEAR never authorized them. Deploying bridge tokens is an admin-equivalent action gated by NEAR MPC signature; the replay bypasses this gate entirely.
2. **Permanent blocking of legitimate deployment**: Once `nearToEthToken[metadata.token]` is set on a chain via replay, the legitimate `deployToken` call reverts with `"ERR_TOKEN_EXIST"` (EVM) or `'ERR_TOKEN_ALREADY_DEPLOYED'` (Starknet), permanently preventing the authorized deployment of that token on that chain.
3. **Corrupted token registry**: If the NEAR bridge processes `DeployToken` events from foreign chains to update its internal token-address registry, the replayed event would cause NEAR to register the attacker-triggered token address as the canonical address for that token on the target chain, potentially misdirecting future `finTransfer` operations.

This satisfies the allowed impact: *"Unauthorized transaction, authorization bypass, role bypass... that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."*

### Likelihood Explanation

- The same NEAR MPC key (and thus the same `nearBridgeDerivedAddress`) is used across all chains by design.
- The bridge is deployed on multiple EVM chains (Ethereum, Arbitrum, Base, Polygon, BNB) and Starknet simultaneously.
- Any `deployToken` transaction is publicly visible on-chain; no privileged access is needed to extract the signature.
- The attacker only needs to submit the same calldata to the bridge contract on a different chain — a trivial operation requiring no special capability.

### Recommendation

Include the destination chain ID in the `deployToken` signed payload, mirroring the pattern already used in `finTransfer`. For EVM:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // ADD THIS
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

For Starknet, update `MetadataPayloadImpl::to_borsh` to accept and embed `chain_id`, and pass `self.omni_bridge_chain_id.read()` from `deploy_token`, exactly as `fin_transfer` does.

### Proof of Concept

1. NEAR MPC signs a `deployToken` payload for Ethereum (`omniBridgeChainId = 0x01`) for token `"usdc.near"` with name `"USD Coin"`, symbol `"USDC"`, decimals `6`. The borsh bytes are: `[0x01, <borsh("usdc.near")>, <borsh("USD Coin")>, <borsh("USDC")>, 0x06]`. NEAR produces signature `S`.

2. Attacker observes the Ethereum `deployToken(S, payload)` transaction.

3. Attacker submits the identical call `deployToken(S, payload)` to the Arbitrum `OmniBridge` contract (same `nearBridgeDerivedAddress`, same borsh encoding, no chain ID in hash).

4. `ECDSA.recover(keccak256(borshEncoded), S) == nearBridgeDerivedAddress` passes on Arbitrum.

5. A bridge token for `"usdc.near"` is deployed on Arbitrum without NEAR authorization. `nearToEthToken["usdc.near"]` is now set on Arbitrum.

6. Any subsequent legitimate attempt by NEAR to deploy USDC on Arbitrum reverts with `"ERR_TOKEN_EXIST"`.

7. The same signature `S` can be replayed on Base, Polygon, BNB, and Starknet for the same result.
