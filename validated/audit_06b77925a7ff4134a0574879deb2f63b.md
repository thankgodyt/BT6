Audit Report

## Title
Silent Failure of `ft_transfer`/`mint` in `fin_transfer_send_tokens_callback` Causes Permanent Loss of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call` is `false`, without inspecting the promise result. Since `is_ft_transfer_call` is set to `!msg.is_empty()` (i.e., `false` when `msg` is empty), any failure of the downstream `ft_transfer` or `mint` call is silently treated as success. The transfer nonce is permanently consumed, `FinTransferEvent` is emitted, and the recipient receives nothing — with no recovery path.

## Finding Description

**Root cause — `is_refund_required` ignores promise result for non-`ft_transfer_call` paths:**

At `lib.rs:1800-1802`, when `is_ft_transfer_call` is `false`, the function returns `false` unconditionally:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

**Dispatch path — `is_ft_transfer_call` is `false` when `msg` is empty:**

At `lib.rs:1973`, `fin_transfer_send_tokens_callback` is registered with `!msg.is_empty()` as `is_ft_transfer_call`. When `msg` is empty, this is `false`. The `send_tokens` function then dispatches either `mint` (deployed token, `lib.rs:2094-2101`) or `ft_transfer` (native/locked token, `lib.rs:2103-2106`) — both plain calls, not `ft_transfer_call`.

**Nonce consumed before the call:**

At `lib.rs:1875`, `add_fin_transfer` records the transfer ID as finalised *before* `send_tokens` is invoked. If the downstream call fails, there is no mechanism to replay it.

**Callback silently succeeds on failure:**

At `lib.rs:1702`, `fin_transfer_send_tokens_callback` branches on `is_refund_required`. Since it returns `false`, the `else` branch at `lib.rs:1719-1746` executes: fee is paid out and `FinTransferEvent` is logged. `remove_fin_transfer` is never called, so the transfer ID remains permanently finalised with no tokens delivered.

The identical flaw exists in `resolve_fast_transfer` (`lib.rs:906`) and `resolve_utxo_fin_transfer` (`lib.rs:1025`), which also call `is_refund_required(is_ft_transfer_call)` and take no corrective action when the promise fails silently.

**Existing checks are insufficient:** The only guard is `is_refund_required` itself, which explicitly skips promise inspection for the non-`ft_transfer_call` case. There is no fallback, no retry, and no event that would allow off-chain recovery.

## Impact Explanation

This is a **permanent loss of bridged funds**. A user's tokens are locked/burned on the source chain. On NEAR, the proof nonce is consumed and the transfer is marked finalised. If `ft_transfer` or `mint` fails for any reason, the user's funds are irrecoverably lost: the source-chain lock cannot be reversed (nonce consumed by the prover), and the NEAR-side transfer cannot be retried (transfer ID already finalised). This matches the allowed critical impact: *permanent freezing / loss of bridged funds across chains*.

## Likelihood Explanation

The trigger requires only that the destination token contract's `ft_transfer` or `mint` call fails. Realistic, documented causes include:

- A stablecoin (USDC, USDT) paused by its issuer — a well-documented, real-world event that has occurred multiple times.
- A bridge token whose `mint` panics due to an edge case (e.g., overflow, access control).
- Insufficient gas allocated to the token call.

No attacker action is required; the failure can be caused by the token issuer or by a contract bug. Any user bridging tokens through the standard `fin_transfer` flow is exposed. The condition is entirely within the bridge's own callback logic.

## Recommendation

`is_refund_required` must check the promise result even when `is_ft_transfer_call` is `false`. A failed promise (i.e., `Err` from `env::promise_result_checked`) must be treated as requiring a refund/revert:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => serde_json::from_slice::<U128>(&value)
                .map(|a| a.0 == 0)
                .unwrap_or(false),
            Err(_) => true, // promise failed → refund required
        }
    } else {
        // ft_transfer or mint: refund if the promise failed
        env::promise_result_checked(0, 0).is_err()
    }
}
```

Additionally, the `Err(_) => false` branch in the `is_ft_transfer_call = true` path (`lib.rs:1797-1798`) should also return `true` to handle unexpected promise failures consistently. The same fix must be applied to `resolve_fast_transfer` and `resolve_utxo_fin_transfer`.

## Proof of Concept

1. User initiates a USDC transfer from Ethereum to NEAR via `initTransfer` on `OmniBridge.sol` — USDC is locked on Ethereum.
2. Relayer submits a valid proof to `fin_transfer` on the NEAR bridge.
3. `fin_transfer_callback` decodes the proof and calls `process_fin_transfer_to_near`.
4. `add_fin_transfer` is called at `lib.rs:1875` — transfer ID is now permanently finalised.
5. `send_tokens` dispatches `ft_transfer(recipient, amount)` (or `mint`) with `msg = ""`, so `is_ft_transfer_call = false`.
6. USDC on NEAR is paused; `ft_transfer` panics/fails.
7. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
8. `is_refund_required(false)` returns `false` at `lib.rs:1800-1802` without reading the promise result.
9. The `else` branch at `lib.rs:1719` executes: fee is paid, `FinTransferEvent` is emitted.
10. Recipient balance: 0. Transfer nonce: consumed. Source-chain lock: irreversible. Funds: permanently lost.

**Test plan:** Deploy a mock token contract whose `ft_transfer` always panics. Call `fin_transfer` with a valid proof targeting that token. Assert that after `fin_transfer_send_tokens_callback` completes, the recipient balance is 0 and the transfer ID is still present in `fin_transfers` (i.e., `remove_fin_transfer` was never called) — confirming the silent failure.
