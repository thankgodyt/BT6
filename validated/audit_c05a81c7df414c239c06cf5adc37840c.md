### Title
`csLatestSlot` Not Reset on `MsgRollBackward` Causes Permanently Stale Density Bounds in GDD, Enabling Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`ChainSyncState.csLatestSlot` is updated (increased) every time a peer sends a `MsgRollForward`, but is **never reset** when the peer sends `MsgRollBackward`. This is the direct analog of the reported Solidity bug: an accumulator that only records upticks and silently ignores downticks, causing permanent divergence between the tracked value and reality. The Genesis Density Disconnection (GDD) governor reads `csLatestSlot` to compute density bounds for every peer; a stale high value collapses a peer's density upper-bound to its lower-bound, making an honest peer that legitimately rolled back appear to have already committed to a sparse density. An adversarial peer with a marginally higher block count in the genesis window can then trigger GDD to disconnect the honest peer, causing the syncing node to adopt the adversary's chain.

---

### Finding Description

**Root cause — the one-sided update:**

In `rollForward`, the very first action after receiving a `MsgRollForward` is:

```haskell
-- Client.hs line 1499
atomically (setLatestSlot dynEnv (NotOrigin slotNo))
```

`setLatestSlot` resolves to `csvSetLatestSlot` wired in `bracketChainSyncClient`:

```haskell
-- Client.hs line 388
csvSetLatestSlot =
    modifyTVar csHandleState . \ls s -> s{csLatestSlot = SJust ls}
```

This unconditionally writes the new (higher) slot into `csLatestSlot`.

The `recvMsgRollBackward` handler, however, performs no symmetric reset:

```haskell
-- Client.hs lines 1459-1469
recvMsgRollBackward = \intersection theirTip -> do
    (idlingStop idling >> lbResume loPBucket)
    let intersection' :: Point blk
        intersection' = castPoint intersection
    traceWith tracer $ TraceRolledBack intersection'
    continueWithState kis $
      rollBackward mkPipelineDecision n intersection' (Their theirTip)
```

There is no call to `setLatestSlot` (or any equivalent) with the intersection slot. `csLatestSlot` therefore retains the slot of the last forwarded header, which may be far beyond the genesis window.

The field's own documentation confirms the asymmetry:

```haskell
-- State.hs lines 72-76
csLatestSlot :: !(StrictMaybe (WithOrigin SlotNo))
-- ^ When the client receives a new header, it updates this field before
-- processing it further, and the latest slot may refer to a header beyond
-- the forecast horizon while the candidate fragment isn't extended yet, to
-- signal to GDD that the density is known up to this slot.
```

"When the client receives a new header" — rollback is never mentioned.

**How the stale value corrupts GDD accounting:**

`densityDisconnect` in `Governor.hs` reads `csLatestSlot` as `latestSlot` and computes:

```haskell
-- Governor.hs lines 401-413
hasBlockAfter =
    max (AF.headSlot candidateSuffix) latestSlot
      >= NotOrigin firstSlotAfterGenesisWindow

potentialSlots =
    if hasBlockAfter
      then 0
      else unknownTrailingSlots

upperBound = lowerBound + potentialSlots
```

After a rollback, `candidateSuffix` is trimmed back to the intersection, but `latestSlot` is still the old high value. If that old value is ≥ `firstSlotAfterGenesisWindow`, then `hasBlockAfter = True` and `potentialSlots = 0`, collapsing the density interval to `[lowerBound, lowerBound]`.

The disconnect guard for a non-idling peer (rollback clears the idling flag at line 1460) is:

```haskell
-- Governor.hs line 486
guard $ lb1 >= (if idling0 then lb0 else ub0)
```

With the stale slot, `ub0 = lb0`, so peer0 is disconnected whenever `lb1 >= lb0`. Without the stale slot, `ub0 = lb0 + potentialSlots`, so peer0 is only disconnected when `lb1 >= lb0 + potentialSlots`. The adversary's required advantage shrinks from `potentialSlots` blocks to zero.

---

### Impact Explanation

**Classification:** High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

An adversarial peer (peer1) that serves a chain with `lb1 ≥ lb0` blocks in the genesis window can cause GDD to disconnect an honest peer (peer0) that recently rolled back, even though peer0 still has `potentialSlots` worth of headers it has not yet sent. Once peer0 is disconnected, the node's LoE fragment advances based on peer1's chain, and chain selection may adopt the adversary's fork. The divergence is durable: `csLatestSlot` is only corrected the next time peer0 sends a `MsgRollForward`, but by then the connection may already be severed.

---

### Likelihood Explanation

Rollbacks are routine in normal Cardano operation (short forks, era transitions, pipelining). A peer that has sent headers beyond the genesis window and then rolls back — a common pattern during initial sync — will always leave `csLatestSlot` stale. An adversary needs only a marginally denser fragment in the genesis window than the honest peer's post-rollback lower bound, which is achievable without a stake majority.

---

### Recommendation

In `recvMsgRollBackward` (or at the start of the internal `rollBackward` function), reset `csLatestSlot` to the slot of the intersection point, mirroring the `setLatestSlot` call in `rollForward`:

```haskell
recvMsgRollBackward = \intersection theirTip -> do
    (idlingStop idling >> lbResume loPBucket)
    let intersection' = castPoint intersection
    atomically (setLatestSlot dynEnv (pointSlot intersection'))  -- add this
    traceWith tracer $ TraceRolledBack intersection'
    continueWithState kis $
      rollBackward mkPipelineDecision n intersection' (Their theirTip)
```

This ensures `csLatestSlot` always reflects the actual latest slot the peer has committed to, keeping GDD density bounds accurate across rollbacks.

### Proof of Concept

```
Genesis window: slots 0–800 (sgen = 800)
firstSlotAfterGenesisWindow = 801

Step 1 – Honest peer A sends headers up to slot 1000:
  csLatestSlot[A] = 1000
  AF.headSlot(candidateSuffix[A]) = 1000

Step 2 – Honest peer A sends MsgRollBackward to slot 500:
  AF.headSlot(candidateSuffix[A]) = 500   (fragment trimmed)
  csLatestSlot[A] = 1000                  (NOT reset — the bug)
  lowerBound[A] = 4  (blocks in genesis window after rollback)
  potentialSlots should be = 801 - 501 = 300
  hasBlockAfter = max(500, 1000) >= 801 = True  (stale!)
  potentialSlots = 0  (wrong)
  upperBound[A] = 4 + 0 = 4

Step 3 – Adversarial peer B serves a chain with 5 blocks in genesis window:
  lowerBound[B] = 5

Step 4 – GDD evaluates: lb1=5 >= ub0=4  → disconnect peer A  ✓ (bug triggered)

Without the bug:
  upperBound[A] = 4 + 300 = 304
  lb1=5 >= ub0=304  → False  → peer A NOT disconnected  ✓ (correct)

Result: node disconnects from honest peer A and may adopt adversary B's chain.
