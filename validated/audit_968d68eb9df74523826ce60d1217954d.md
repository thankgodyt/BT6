Audit Report

## Title
Parallel `burn.and(mint)` in `swap_migrated_token` Causes Permanent Token Loss When Mint Fails — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` schedules `burn` and `mint` as two independent parallel NEAR action receipts via `burn.and(mint)` with no sequential dependency and no error-handling callback. If the `mint` call panics (e.g., the recipient is not storage-registered on the new token), the `burn` still executes and permanently destroys the user's old tokens while no new tokens are issued. The promise is detached and `ft_on_transfer` already returned `U128(0)`, so there is no refund path.

## Finding Description
**Entry point** — `ft_on_transfer` handles `SwapMigratedToken` by immediately returning `U128(0)` (bridge keeps all received tokens, no refund) and detaching the swap promise:

```rust
// near/omni-bridge/src/lib.rs L275-279
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

**Parallel promise construction** — `swap_migrated_token` builds two independent cross-contract calls and joins them with `.and()`:

```rust
// near/omni-bridge/src/lib.rs L2749-2752
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
```

In NEAR's execution model, `promise_a.and(promise_b)` schedules both as separate action receipts that execute independently. A failure in one does not prevent the other from executing.

**`mint` failure path** — `mint` with `msg = None` calls `internal_deposit`:

```rust
// near/omni-token/src/lib.rs L140-143
} else {
    self.token.internal_deposit(&account_id, amount.into());
    PromiseOrValue::Value(amount)
}
```

`internal_deposit` in NEAR's standard `FungibleToken` panics if `account_id` has no storage registration. Any user who has not called `storage_deposit` on the new token before swapping will trigger this panic.

**`burn` executes regardless** — `burn` withdraws from `predecessor_account_id()` (the bridge contract, which holds the old tokens after `ft_transfer_call`):

```rust
// near/omni-token/src/lib.rs L146-151
fn burn(&mut self, amount: U128) {
    self.assert_controller();
    self.token.internal_withdraw(&env::predecessor_account_id(), amount.into());
}
```

Because `burn` and `mint` are parallel receipts, `burn` executes and succeeds even when `mint` panics. The old tokens are permanently destroyed. No callback exists to detect the failure or restore state.

## Impact Explanation
Permanent, irreversible loss of user funds. The user's old tokens are burned and no new tokens are minted. This matches the Critical impact class: *"loss … or permanent freezing of bridged funds."* The lost amount equals the full swap amount with no recovery mechanism.

## Likelihood Explanation
Any unprivileged token holder can trigger this accidentally or be induced to trigger it. The precondition — not having a storage deposit on the new token — is the default state for any user who has not explicitly pre-registered. No attacker capability beyond holding old migrated tokens is required. The scenario is repeatable for every such user.

## Recommendation
Replace the parallel `burn.and(mint)` pattern with a sequential promise chain that only burns after a successful mint, or adds a callback to re-mint (or refund) on failure:

```rust
// Option A: sequential — mint first, then burn on success
mint.then(ext_self::ext(env::current_account_id()).on_mint_success(old_token, amount))

// Option B: parallel with result callback
burn.and(mint).then(ext_self::ext(env::current_account_id())
    .on_swap_complete(sender_id, old_token, new_token, amount))
```

The callback must inspect promise results via `env::promise_result` and, if `mint` failed, either re-issue the mint after the user registers storage or refund the equivalent old tokens. Additionally, `ft_on_transfer` should not return `U128(0)` unconditionally — it should only keep the tokens once the swap is confirmed successful.

## Proof of Concept
1. Deploy old token and new token contracts with the bridge as controller.
2. Register the user's storage on the old token but **not** on the new token.
3. User calls `ft_transfer_call` on the old token, sending `N` tokens to the bridge with `msg = "SwapMigratedToken"`.
4. `ft_on_transfer` returns `U128(0)`; the detached promise fires `burn.and(mint)`.
5. `burn` receipt executes: bridge's old-token balance decreases by `N` (tokens destroyed).
6. `mint` receipt executes: `internal_deposit` panics because user has no storage on new token; receipt fails silently.
7. Observe: user's old-token balance is 0, new-token balance is 0, bridge holds 0 old tokens. Funds are permanently lost.

This can be demonstrated with a NEAR sandbox integration test using `workspaces-rs` by omitting the `storage_deposit` call on the new token before step 3.
