### Title
Order-of-Operations Bug in `safe_mint`: Tokens Minted to Bridge Before Account Existence Check — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `safe_mint`, `internal_deposit` is called to mint tokens into `bridge_id`'s balance **before** the function checks whether `account_id` has a registered storage account. If the account does not exist, the function returns `U128(0)` and exits — but the tokens are already committed to `bridge_id`'s balance. This is a direct order-of-operations analog to the reported Streamr bug: a state-gating check is evaluated against stale (pre-update) state, leaving the contract in an inconsistent condition.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes as follows:

```rust
// Line 112 — state is mutated FIRST
self.token.internal_deposit(&self.bridge_id, amount.into());

// Line 114 — check happens AFTER the deposit
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));  // exits, tokens already minted to bridge_id
}
``` [1](#0-0) 

The `internal_deposit` call on line 112 permanently increases `bridge_id`'s token balance. The account-existence check on line 114 is the gate that determines whether those tokens are forwarded to the user. Because the gate fires **after** the state mutation, a failure path (account absent) leaves `bridge_id` holding tokens that were never transferred — with no automatic rollback and no in-function burn call.

The standard `mint` path avoids this entirely by using `mint_inner`, which calls `internal_register_account` before `internal_deposit`, ensuring the recipient always exists before any balance is credited. [2](#0-1) 

`safe_mint` deliberately skips registration (it is the caller's responsibility to pre-register storage), but it does not move the existence check before the deposit, creating the inconsistency.

---

### Impact Explanation

When `safe_mint` returns `U128(0)` due to a missing account, the nBTC contract has already committed new tokens to `bridge_id`. In NEAR's asynchronous cross-contract call model, the state change inside `safe_mint` is finalized at the point of return; the bridge's callback receives the `0` result but cannot atomically revert the nBTC contract's storage. Unless the bridge callback explicitly issues a subsequent `burn` call (which requires a separate cross-contract call and its own gas budget), the minted tokens remain stranded in `bridge_id` indefinitely.

The user's BTC is locked in the bridge's MPC-controlled Bitcoin address (the deposit UTXO is marked verified), yet they receive zero nBTC. This constitutes a permanent loss of the user's deposited BTC value from their perspective, and a backed-supply inflation on the nBTC side (tokens exist in `bridge_id` with no corresponding user claim), matching the **Medium** impact class: *broken callback rollback / stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

The `safe_deposit` flow (triggered via `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`) is the production path used by integrations such as Omni Bridge. The relayer is expected to pre-register the recipient's storage, but:

- A user whose storage registration was subsequently unregistered (via `storage_unregister`) between deposit and mint would trigger this path.
- A relayer bug or race condition that submits the deposit proof before storage is registered would trigger this path.
- Any third-party dApp integrating the safe-deposit flow that fails to pre-register storage would trigger this path.

No privileged access is required; the triggering condition is reachable by any user whose NEAR account lacks an nBTC storage slot at the moment `safe_mint` executes.

---

### Recommendation

Move the account-existence check **before** the `internal_deposit` call, mirroring the fix applied in the Streamr report (move the validation before the state-mutating operation):

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check FIRST, before any state mutation
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    // Only mint after confirming the recipient exists
    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

This ensures that if the recipient account is absent, no tokens are minted and no inconsistent state is created.

---

### Proof of Concept

1. User deposits BTC to a safe-deposit address (e.g., via Omni Bridge integration).
2. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
3. Bridge verifies the deposit via the light client and calls `safe_mint(account_id, amount, msg)` on the nBTC contract.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `bridge_id`'s nBTC balance increases by `amount`. [3](#0-2) 
5. `safe_mint` then checks `self.token.accounts.get(&account_id).is_none()` — the user has no storage slot. [4](#0-3) 
6. The function returns `PromiseOrValue::Value(U128(0))`. The nBTC state change (step 4) is committed.
7. The bridge callback receives `0`. Without an explicit `burn` cross-contract call in the callback, `amount` nBTC tokens remain stranded in `bridge_id`.
8. The deposit UTXO is marked verified (`verified_deposit_utxo`), blocking any future refund path for the user's BTC.
9. Result: user's BTC is permanently locked; they hold zero nBTC; `bridge_id` holds unbacked tokens.
