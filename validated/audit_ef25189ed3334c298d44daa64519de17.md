Audit Report

## Title
Permanent Fund Freeze via `normalize_amount` Floor-Division Rounding to Zero in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` burns or locks the full token amount before any decimal-normalization check is applied. When `amount_without_fee < 10^(origin_decimals − decimals)`, the floor division in `normalize_amount` returns 0, causing `sign_transfer` to panic with `InvalidAmountToTransfer`. Because no cancel or refund path exists, the user's tokens are permanently destroyed or frozen with no recovery mechanism.

## Finding Description

**Root cause — `normalize_amount` floor division:** [1](#0-0) 

For a token with `origin_decimals = 24` and `decimals = 6` (diff = 18), any `amount_without_fee < 10^18` produces 0. This is not an underflow — it is a silent zero result from valid arithmetic on a valid decimal configuration.

**`init_transfer` has no minimum-amount guard:** [2](#0-1) 

Only `fee.fee < amount` is enforced. There is no check that `amount - fee >= 10^diff_decimals` for the target chain.

**Tokens are burned/locked and `U128(0)` returned before `sign_transfer` is ever called:** [3](#0-2) 

`burn_tokens_if_needed` dispatches a detached burn promise (fire-and-forget): [4](#0-3) 

Returning `U128(0)` to the `ft_transfer_call` callback means the token contract refunds nothing to the user. The tokens are gone from the user's perspective at this point.

**`sign_transfer` checks for zero only in a separate, later transaction:** [5](#0-4) 

The panic here does not revert `init_transfer`; NEAR promise execution is already complete and the state change is committed.

**No cancel/refund path exists.** A grep for `cancel_transfer` across the entire repository returns zero matches. `update_transfer_fee` only allows the fee to increase: [6](#0-5) 

Increasing the fee reduces `amount_without_fee` further, making the zero-normalization condition worse, not better. There is no escape from the stuck state.

**CLAUDE.md false-positive item #2 does not cover this case:** [7](#0-6) 

That item addresses integer underflow when `origin_decimals < decimals`. This vulnerability involves a valid (non-underflowing) decimal configuration where `normalize_amount` silently returns 0 — a distinct and unaddressed scenario.

## Impact Explanation

Permanent freezing or destruction of bridged funds. For any token pair where `origin_decimals > decimals` (the standard case), a user who initiates a transfer with `amount_without_fee < 10^(origin_decimals − decimals)` will have their tokens burned (if bridge-deployed) or locked indefinitely (if native) with no on-chain recovery path. This directly matches the allowed Critical impact: *permanent freezing of bridged funds* and *decimal/normalization abuse that changes user or protocol balances*.

## Likelihood Explanation

Low-to-medium. The exploit path is reachable by any unprivileged user via the standard `ft_transfer_call` public interface — no special role or key is required. For tokens with large decimal gaps (e.g., USDC at diff = 18), the threshold is `10^18` NEAR-side smallest units, which is non-trivial but reachable by accident (users specifying raw amounts) or by deliberate griefing with a dust-sized balance. The condition is repeatable and requires no coordination.

## Recommendation

1. **Add a minimum-amount guard in `init_transfer_internal`** (before burning/locking) that rejects transfers where `amount_without_fee < 10^(origin_decimals − decimals)` for the target chain, returning the full amount to the caller so the `ft_transfer_call` refund path can return tokens to the user.
2. **Alternatively, add a `cancel_transfer` function** allowing the original sender to reclaim locked tokens for a pending transfer that has not yet been signed, subject to a time-lock or relayer-absence condition. For burned tokens, a mint-back mechanism would be required.

## Proof of Concept

**Setup:** USDC registered with `origin_decimals = 24`, `decimals = 6` → `diff_decimals = 18`.

1. User calls `ft_transfer_call(bridge, amount = 5×10^17, msg = <InitTransferMsg to EVM>)` on the USDC token contract.
2. Token contract calls `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `fee.fee < amount` passes (e.g., fee = 0).
   - `burn_tokens_if_needed` dispatches a detached burn of `5×10^17` tokens.
   - Returns `U128(0)` → token contract refunds 0 to user. Tokens are gone.
3. Relayer calls `sign_transfer(transfer_id, ...)`:
   - `amount_without_fee = 5×10^17`.
   - `normalize_amount(5×10^17, {24, 6}) = 5×10^17 / 10^18 = 0`.
   - `require!(0 > 0, ...)` → **panic: `InvalidAmountToTransfer`**.
4. No further call can complete this transfer. `update_transfer_fee` can only raise the fee. No `cancel_transfer` exists.
5. The `5×10^17` USDC tokens are **permanently destroyed**.

**Test plan:** Write a NEAR integration test that registers a token with `origin_decimals = 24` / `decimals = 6`, calls `ft_transfer_call` with `amount = 5×10^17`, asserts `ft_on_transfer` returns `U128(0)`, then calls `sign_transfer` and asserts it panics with `InvalidAmountToTransfer`. Confirm the token balance of the user and bridge are both reduced with no refund.
