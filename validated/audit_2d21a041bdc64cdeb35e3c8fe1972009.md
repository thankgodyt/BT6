### Title
`safe_mint` Does Not Emit `FtMint` Event, Causing Incorrect NEP-141 Supply Accounting — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract increases the token total supply via `internal_deposit` but never emits an `FtMint` event. This is the direct NEAR analog of the Celo `creditTo`/`debitFrom` missing-Transfer-event bug: any indexer or client reconstructing nBTC supply from on-chain events will compute a lower total supply than actually exists for every deposit processed through the safe-deposit flow.

---

### Finding Description

The nBTC contract exposes two minting paths:

**Path 1 — `mint` → `mint_inner` (correct):**

`mint_inner` calls `internal_deposit` and immediately emits `FtMint`:

```rust
// contracts/nbtc/src/lib.rs  lines 341-352
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    ...
    self.token.internal_deposit(account_id, amount.into());
    near_contract_standards::fungible_token::events::FtMint {
        owner_id: account_id,
        amount,
        memo: None,
    }
    .emit();   // ← event emitted
}
``` [1](#0-0) 

**Path 2 — `safe_mint` (missing event):**

`safe_mint` calls `internal_deposit` to credit `bridge_id` (increasing total supply) but emits **no** `FtMint` event before delegating to `ft_transfer` / `ft_transfer_call`:

```rust
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    ...
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ← NO FtMint emitted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }
    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)   // emits FtTransfer only
    } else {
        self.ft_transfer(account_id, amount, None);            // emits FtTransfer only
        PromiseOrValue::Value(amount)
    }
}
``` [2](#0-1) 

The subsequent `ft_transfer` / `ft_transfer_call` emits only an `FtTransfer` event (bridge → user). No `FtMint` event is ever produced for the supply-creation step.

**Entry path:** Any user submitting a valid BTC deposit proof via `safe_verify_deposit` causes the bridge to call `safe_mint` on the nBTC contract:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs  lines 409-418
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_MINT_CALL)
    .with_attached_deposit(NearToken::from_yoctonear(1))
    .safe_mint(recipient_id.clone(), mint_amount, msg)
    ...
``` [3](#0-2) 

---

### Impact Explanation

Every successful `safe_verify_deposit` call mints nBTC tokens (increases `total_supply`) without emitting an `FtMint` event. Indexers, wallets, and DeFi protocols that reconstruct nBTC total supply or per-account balances by replaying NEP-141 events will compute a supply lower than the actual on-chain supply. This is a publicly reachable invariant violation in the production token path: the event log is permanently inconsistent with the actual token state for all safe-deposit mints.

Impact: **Low** — publicly reachable invariant-violation in production bridge/token paths without direct theft.

---

### Likelihood Explanation

The `safe_verify_deposit` function is a public entry point callable by any bridge user submitting a deposit proof. Every deposit processed through this path (as opposed to `verify_deposit_v2`) silently omits the `FtMint` event. The likelihood is **high** that this path is exercised in production, since it is the designated flow for safe deposits with storage pre-payment. [4](#0-3) 

---

### Recommendation

Emit `FtMint` inside `safe_mint` immediately after `internal_deposit`, mirroring `mint_inner`:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
near_contract_standards::fungible_token::events::FtMint {
    owner_id: &self.bridge_id,
    amount,
    memo: None,
}
.emit();
```

This ensures every supply-creation operation is reflected in the event log, consistent with the NEP-141 events extension and the contract's own `mint_inner` pattern.

---

### Proof of Concept

1. User calls `safe_verify_deposit` with a valid BTC Merkle proof.
2. Bridge verifies the proof and calls `safe_mint(recipient_id, mint_amount, msg)` on the nBTC contract.
3. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `total_supply` increases by `amount`, `bridge_id` balance increases by `amount`. No `FtMint` event is emitted.
4. `safe_mint` then calls `ft_transfer(recipient_id, amount, None)` — an `FtTransfer { old_owner_id: bridge_id, new_owner_id: recipient_id, amount }` event is emitted.
5. An indexer replaying events sees only an `FtTransfer` from bridge to user, with no preceding `FtMint`. The indexer's computed `total_supply` does not increase, while the actual on-chain `total_supply` does. The discrepancy grows with every safe-deposit processed. [5](#0-4) [1](#0-0)
