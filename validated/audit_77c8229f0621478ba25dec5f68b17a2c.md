### Title
Missing Vote Stake Normalization in Peras Quorum Threshold Check Enables Certificate Forgery - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function, which is the sole quorum gate for forging Peras certificates, explicitly documents that it assumes `PerasVoteStake` and `perasQuorumStakeThreshold` are expressed in the same units (both relative/normalized), but enforces no such invariant. If `PerasVoteStake` values are populated from the ledger as absolute stake quantities while the threshold remains a relative `Rational` (e.g., `0.75`), the comparison is between incompatible units. Any single vote from a voter with positive absolute stake would trivially satisfy the check, allowing a certificate to be forged with a single vote and bypassing the quorum requirement entirely.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs the quorum check:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake    = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
```

The function's own documentation acknowledges the invariant is unverified:

> **TODO**: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally. [1](#0-0) 

The `PerasVoteStake` type is a bare `Rational` with no unit tag:

```haskell
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [2](#0-1) 

The companion note on `PerasVoteStake` states there is **no consensus on how to normalize** from absolute ledger stake to relative committee stake:

> NOTE: At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake). [3](#0-2) 

`stakeAboveThreshold` is called in two production paths:

1. `votesReachQuorum` — the gate that decides whether to forge a certificate: [4](#0-3) 

2. `updateLoserVoteState` — the guard that detects a second winner in a round: [5](#0-4) 

`votesReachQuorum` is called from `updateCandidateVoteState`, which is the hot path for every incoming vote: [6](#0-5) 

The `PerasQuorumStakeThreshold` is a relative `Rational` (e.g., `0.75`): [7](#0-6) 

If `PerasVoteStakeDistr` is populated from the ledger with absolute lovelace-scale values (e.g., `500_000_000_000`), then `stake >= 0.75 + margin` evaluates to `500_000_000_000 >= 0.75`, which is always `True`. A single vote from any voter with positive stake immediately satisfies the quorum check.

---

### Impact Explanation

**Impact: High — Bypass of Peras certificate/vote checks.**

If the unit mismatch is present at runtime, any single incoming `PerasVote` from a voter with positive ledger stake causes `votesReachQuorum` to return `Just`, triggering `forgePerasCert`. The resulting `ValidatedPerasCert` is stored in the `PerasCertDB` and applied to chain selection via `PerasWeightSnapshot`, boosting the attacker's chosen block by `perasWeight`. This directly corrupts the Peras chain-selection invariant: a block that should not have been certified receives a boost, potentially causing honest nodes to prefer a non-canonical chain.

---

### Likelihood Explanation

**Likelihood: Medium.**

The TODO comment is present in production code and explicitly states normalization is not performed inside the function. The natural way to populate `PerasVoteStakeDistr` from the Cardano ledger is with absolute stake values (lovelace). The mismatch is latent and will manifest as soon as a concrete Cardano integration wires up the ledger stake distribution without a normalization step. Any peer that is a registered stake pool (i.e., appears in the ledger stake distribution with positive stake) can trigger the path by sending a single well-formed `PerasVote` message.

---

### Recommendation

1. **Enforce units at the type level**: introduce distinct newtypes for absolute ledger stake and normalized committee stake so the compiler rejects mixing them.
2. **Normalize inside `stakeAboveThreshold`**: accept the total committee stake as an additional parameter and divide `PerasVoteStake` by it before comparing, eliminating the caller-side invariant.
3. **Alternatively**, store only pre-normalized `PerasVoteStake` values in `PerasVoteStakeDistr` and enforce normalization at the point of construction (when the distribution is built from the ledger).

---

### Proof of Concept

Assume `perasQuorumStakeThreshold = 0.75`, `perasQuorumStakeThresholdSafetyMargin = 0.01`, and `PerasVoteStakeDistr` is populated with absolute lovelace values so that voter `V` has `PerasVoteStake = 500_000_000_000 % 1`.

1. Attacker (pool `V`) sends one `PerasVote` for block `B` in round `R`.
2. Node calls `validatePerasVote`, looks up `V` in `PerasVoteStakeDistr`, sets `vpvVoteStake = 500_000_000_000 % 1`.
3. `updateCandidateVoteState` calls `votesReachQuorum` with this single vote.
4. `stakeAboveThreshold` evaluates `500_000_000_000 >= 0.75 + 0.01` → `True`.
5. `forgePerasCert` is called; a `ValidatedPerasCert` for block `B` is produced.
6. The certificate is stored and applied; block `B` receives a `perasWeight` boost in chain selection.
7. Honest nodes following the boosted chain prefer `B` over competing forks, achieving the attacker's chain-selection goal with a single vote instead of the required quorum.
