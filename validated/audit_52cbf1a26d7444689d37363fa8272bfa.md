Audit Report

## Title
`finish_withdraw_v2` Missing Pause Guard Allows Transfer Initiation When Bridge Is Paused — (File: near/omni-bridge/src/lib.rs)

## Summary

`finish_withdraw_v2` is a public function callable by any registered legacy bridge token contract that initiates an outbound transfer without checking the bridge's pause state. Every other transfer-initiation entry point is guarded by `#[pause(except(roles(Role::DAO)))]`, but this function carries no such attribute. When the bridge is paused in response to a security incident, users can still burn their NEAR-side legacy tokens and create pending transfer records, while `sign_transfer` remains paused and unable to complete them — permanently freezing the burned funds if the bridge is shut down.

## Finding Description

All critical transfer-initiation paths in the contract are protected:

- `ft_on_transfer` at L252: `#[pause(except(roles(Role::DAO, Role::UnrestrictedDeposit)))]`
- `sign_transfer` at L446: `#[pause(except(roles(Role::DAO)))]`
- `fin_transfer` at L672: `#[pause(except(roles(Role::DAO)))]`
- `claim_fee` at L1056: `#[pause(except(roles(Role::DAO)))]`

`finish_withdraw_v2` at L1314–1354 has no `#[pause]` attribute:

```rust
#[allow(clippy::needless_pass_by_value)]
pub fn finish_withdraw_v2(
    &mut self,
    #[serializer(borsh)] sender_id: &AccountId,
    ...
) {
    let token_id = env::predecessor_account_id();
    require!(self.is_deployed_token(&token_id),);
    ...
    self.add_transfer_message(transfer_message.clone(), sender_id.clone());
    self.update_storage_balance(env::current_account_id(), ...);
    env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
}
```

The only guard is `is_deployed_token`, which returns `true` for any account in `deployed_tokens` or `deployed_tokens_v2` — a set maintained for backward compatibility with legacy bridge tokens. The function increments `current_origin_nonce`, allocates a `destination_nonce`, stores a `TransferMessage` in `pending_transfers`, and emits `InitTransferEvent`, all without consulting the pause flag. Storage for the pending transfer is charged to `env::current_account_id()` (the bridge contract), not the sender.

## Impact Explanation

This is a concrete pause bypass (critical impact class: "pause bypass that lets an attacker execute bridge-equivalent actions") and a permanent freezing of bridged funds (critical impact class: "permanent freezing of bridged funds"). When the bridge is paused in response to a security incident, the admin's intent is to halt all new transfer activity. This function defeats that intent: tokens are burned on the NEAR side, a pending transfer is recorded, but `sign_transfer` is paused so no relayer can complete the transfer. If the bridge is permanently shut down — the realistic outcome of a severe incident — the burned tokens are irrecoverable.

## Likelihood Explanation

The precondition is simply that a legacy bridge token exists in `deployed_tokens` or `deployed_tokens_v2`, which is true by design for backward compatibility. Any user holding such tokens can trigger the path by calling the legacy token's `withdraw` function, which burns their balance and calls `finish_withdraw_v2` as a cross-contract callback. No special role, permission, or privileged access is required. The bridge being paused is itself the triggering condition, making this exploitable precisely when the pause mechanism is most needed.

## Recommendation

Add the same pause guard used on every other transfer-initiation path:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn finish_withdraw_v2(...) { ... }
```

Additionally, charge storage costs to `sender_id` rather than `env::current_account_id()` to prevent repeated calls from exhausting bridge storage at no cost to the caller.

## Proof of Concept

1. Admin pauses the bridge via the `PauseManager` role in response to a security incident.
2. User holds tokens in a legacy deployed bridge token (e.g., `eth-<token>.factory.bridge.near`) registered in `deployed_tokens`.
3. User calls the legacy token's `withdraw(amount, recipient_eth_address)`.
4. The legacy token burns the user's balance and calls `finish_withdraw_v2` on the bridge with `sender_id`, `amount`, and `recipient`.
5. `finish_withdraw_v2` executes without reverting — no pause check — increments `current_origin_nonce`, stores a `TransferMessage` in `pending_transfers`, and emits `InitTransferEvent`.
6. The user's NEAR-side tokens are now burned. `sign_transfer` is paused, so no relayer can complete the transfer.
7. If the bridge is permanently shut down, the user's funds are permanently frozen.

    #[allow(clippy::needless_pass_by_value)]
    pub fn finish_withdraw_v2(
        &mut self,
        #[serializer(borsh)] sender_id: &AccountId,
        #[serializer(borsh)] amount: u128,
        #[serializer(borsh)] recipient: String,
    ) {
        let token_id = env::predecessor_account_id();
        require!(self.is_deployed_token(&token_id),);

        self.current_origin_nonce += 1;
        let destination_nonce = self.get_next_destination_nonce(ChainKind::Eth);

        let transfer_message = TransferMessage {
            origin_nonce: self.current_origin_nonce,
            token: OmniAddress::Near(token_id),
            amount: U128(amount),
            recipient: OmniAddress::Eth(
                H160::from_str(&recipient).near_expect(BridgeError::InvalidRecipientAddress),
            ),
            fee: Fee {
                fee: U128(0),
                native_fee: U128(0),
            },
            sender: OmniAddress::Near(sender_id.clone()),
            msg: String::new(),
            destination_nonce,
            origin_transfer_id: None,
        };

        let required_storage_balance =
            self.add_transfer_message(transfer_message.clone(), sender_id.clone());

        self.update_storage_balance(
            env::current_account_id(),
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
    }
