### Title
Refund Amount Can Fall Below Bitcoin Dust Limit After Gas Fee Deduction, Permanently Locking User Funds - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
The refund flow validates only that `gas_fee < deposit_amount` (i.e., refund amount > 0), but never checks that the resulting refund output meets Bitcoin's dust limit. When `execute_refund` is called, the UTXO is permanently inserted into `verified_deposit_utxo` (blocking future deposits), while the dust-valued refund transaction is rejected by Bitcoin nodes and can never be confirmed. The user's BTC is permanently locked with no on-chain recovery path.

### Finding Description

**Root cause — missing dust-limit check in `request_refund_callback`:**

In `request_refund_callback`, the only guard on the refund amount is: [1](#0-0) 

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

This only ensures `refund_amount > 0`. There is no check that `amount - resolved_gas_fee >= DUST_LIMIT` (≈546 satoshis for P2PKH, 294 for P2WPKH). The request is stored with whatever `gas_fee` was resolved.

**Root cause — same gap in `refund_execution_inputs`:** [2](#0-1) 

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

Again, only `> 0`. A 1-satoshi refund passes this check.

**Permanent UTXO lock in `finalize_refund_with_psbt`:**

When `execute_refund` succeeds, the UTXO is unconditionally inserted into `verified_deposit_utxo`: [3](#0-2) 

```rust
// Mark UTXO as verified to prevent verify_deposit later
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
```

`verified_deposit_utxo` is a `LookupSet<String>` with no removal function exposed anywhere in the contract. Once inserted, the UTXO is permanently blocked from `verify_deposit`. [4](#0-3) 

**`reject_refund` does not undo the `verified_deposit_utxo` insertion:** [5](#0-4) 

`internal_reject_refund` only removes the entry from `refund_requests`; it does not touch `verified_deposit_utxo`. So even if the DAO rejects the refund after `execute_refund`, the UTXO remains permanently blocked.

**Fee structure that enables the scenario:**

`BridgeFee.get_fee` enforces a `fee_min` floor: [6](#0-5) 

The `max_btc_gas_fee` config field sets the upper bound for gas fees: [7](#0-6) 

If `max_btc_gas_fee` is configured close to `min_deposit_amount`, the window `(max_btc_gas_fee, max_btc_gas_fee + DUST_LIMIT)` produces dust refund outputs.

### Impact Explanation

A user whose BTC deposit falls in the range `(max_btc_gas_fee, max_btc_gas_fee + DUST_LIMIT)` satoshis will:
1. Be unable to mint nBTC (deposit below `min_deposit_amount`).
2. Have their refund PSBT created and MPC-signed, but the resulting Bitcoin transaction rejected by all standard nodes (dust output).
3. Have their UTXO permanently blocked from both `verify_deposit` and any future `execute_refund` (gas fee is fixed at request time; re-executing produces the same dust tx).
4. Have no on-chain recovery path without a contract upgrade.

This matches **Critical — significant loss or permanent locking of user funds**.

### Likelihood Explanation

The scenario is reachable by any unprivileged user who sends a small BTC deposit. The entry path is fully public: `request_refund` is `#[payable]` with no role restriction, and `execute_refund` is similarly open after the timelock. The only configuration requirement is that `max_btc_gas_fee` be within ~546 satoshis of `min_deposit_amount`, which is a realistic production configuration (e.g., `min_deposit_amount = 10 000 sat`, `max_btc_gas_fee = 9 500 sat`).

### Recommendation

Add a minimum viable output check in `request_refund_callback` before storing the request:

```rust
const DUST_LIMIT: u128 = 546; // satoshis, P2PKH
require!(
    amount.saturating_sub(resolved_gas_fee) >= DUST_LIMIT,
    "Refund amount after gas fee is below dust limit"
);
```

Apply the same guard in `refund_execution_inputs` as a defense-in-depth assertion. This mirrors the recommendation in the original report: validate the post-fee state before committing to the operation.

### Proof of Concept

1. Protocol configured with `min_deposit_amount = 10 000 sat`, `max_btc_gas_fee = 9 500 sat`.
2. User sends a real BTC transaction of **9 800 satoshis** to a deposit address.
3. Relayer cannot call `verify_deposit` — amount is below `min_deposit_amount`.
4. User calls `request_refund` (public, payable) with the transaction bytes and a valid Merkle proof.
5. `request_refund_callback` resolves `gas_fee = 9 500 sat`; check `9 500 < 9 800` passes; request stored.
6. After the timelock, anyone calls `execute_refund`.
7. `refund_execution_inputs` computes `refund_amount = 9 800 − 9 500 = 300 sat`; check `300 > 0` passes.
8. `finalize_refund_with_psbt` builds a PSBT with a 300-satoshi output, inserts the UTXO into `verified_deposit_utxo`, and marks the request `executed = true`.
9. MPC signs the transaction; the signed tx is broadcast but rejected by Bitcoin nodes (300 sat < 546 sat dust limit).
10. `verify_refund_finalize` can never succeed; `verified_deposit_utxo` permanently blocks `verify_deposit`.
11. User's 9 800 satoshis are permanently locked with no recovery path short of a contract upgrade.
