### Title
User Can Block Operator's `cancel_withdraw` by Front-Running with a New Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

The `cancel_withdraw` function enforces `require_pending_sign_capacity` against the **user's** account before creating the CancelRbf pending transaction. A user whose withdrawal has already advanced to `PendingVerify` state (freeing their pending-sign slot) can front-run the operator's `cancel_withdraw` call by initiating a fresh withdrawal, filling that slot and causing the capacity check to revert. This lets the user indefinitely block the operator from canceling a stuck withdrawal, keeping bridge UTXOs locked.

### Finding Description

`cancel_withdraw` is a privileged operator function that cancels a stuck withdrawal via RBF:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    self.require_pending_sign_capacity(&user_account_id);   // ← blocking check
    self.cancel_withdraw_chain_specific(
        user_account_id,
        original_btc_pending_verify_id,
        output,
        None,
    );
}

`require_pending_sign_capacity` checks that the user's `btc_pending_sign_ids` count is strictly less than their configured limit:

```rust
pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
    require!(
        self.get_account(account_id)...
            .pending_sign_count()
            < self.get_max_pending_sign_txs(account_id),
        "Too many pending sign transactions"
    );
}
``` [2](#0-1) 

The default per-account limit is **1**:

```rust
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)
}

**Attack path:**

1. User initiates withdrawal W1 → `btc_pending_sign_ids = {W1}` (count = 1).
2. MPC signs W1 → W1 moves to `PendingVerify`; `btc_pending_sign_ids = {}` (count = 0).
3. Operator observes W1 is stuck and prepares `cancel_withdraw(W1)`.
4. User front-runs by calling `ft_on_transfer` with a new withdrawal W2 → `btc_pending_sign_ids = {W2}` (count = 1).
5. Operator's `cancel_withdraw(W1)` hits `require_pending_sign_capacity`: `1 < 1` → **false** → reverts with "Too many pending sign transactions".
6. W2 is signed → moves to `PendingVerify`; user immediately initiates W3 → count = 1 again.
7. Repeat indefinitely.

The user can sustain this loop as long as they hold nBTC to fund successive withdrawals. On NEAR, where transaction ordering is deterministic and latency is low, front-running is straightforward.

The analog to the external report is direct: just as a user lists vesting to the marketplace to move it into the VestingManager and block the token issuer's `transferVesting` amount check, here the user initiates a new withdrawal to fill their pending-sign slot and block the operator's `require_pending_sign_capacity` check inside `cancel_withdraw`.

### Impact Explanation

The operator cannot cancel the stuck withdrawal W1. The UTXOs committed to W1 remain locked inside `btc_pending_infos` and are unavailable to the bridge for other operations (consolidation, new withdrawals). This constitutes attacker-triggered temporary locking of bridged funds and a stuck bridge state that cannot be resolved by the operator without an out-of-band DAO action (`set_pending_tx_limit`).

**Severity: Medium** — matches "attacker-triggered temporary locking of bridged funds" and "stuck bridge state requiring operator intervention."

### Likelihood Explanation

Any user with a withdrawal in `PendingVerify` state and additional nBTC can execute this. The attack requires no special knowledge, no leaked keys, and no privileged access. NEAR's fast block times make front-running practical. The user has a clear economic incentive: avoid the gas fee charged by `cancel_withdraw` and keep their original withdrawal alive in hopes it confirms on Bitcoin.

### Recommendation

Remove `require_pending_sign_capacity` from `cancel_withdraw` (and its RBF sibling `cancel_active_utxo_management`), or introduce a separate privileged-bypass path so that DAO/Operator-initiated cancellations are not subject to the user-facing pending-sign cap. The cap exists to prevent users from flooding the MPC signer; it should not gate operator safety actions.

### Proof of Concept

```
1. Alice holds 2 nBTC.
2. Alice calls ft_on_transfer(bridge, 1 nBTC, Withdraw{W1}).
   → btc_pending_sign_ids = {W1}
3. MPC signs W1; W1 moves to PendingVerify.
   → btc_pending_sign_ids = {}
4. Operator prepares cancel_withdraw(W1).
5. Alice front-runs: ft_on_transfer(bridge, 1 nBTC, Withdraw{W2}).
   → btc_pending_sign_ids = {W2}
6. Operator's cancel_withdraw(W1) reverts: "Too many pending sign transactions".
7. MPC signs W2; W2 moves to PendingVerify.
   → btc_pending_sign_ids = {}
   (Alice claims W2's nBTC back via lost_found if it is also canceled, or waits for it to confirm.)
8. Alice repeats from step 5 to keep blocking the operator.
