### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural validation. Because this function is wired directly into the production Peras certificate inbound pipeline, any unprivileged peer can inject an arbitrary crafted `PerasCert` that will be accepted, stored in `PerasCertDB`, and applied as a chain-selection weight boost — without ever having earned a quorum of votes.

This function accepts any `PerasCert` value unconditionally — no signature verification, no quorum proof, no committee membership check, no round-number sanity check. The `ValidatedPerasCert` wrapper is supposed to be evidence that a certificate passed all required checks; here it is issued for free.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any `pcCertBoostedBlock` (any block point) and any `pcCertRound`. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its `perasWeight` boost is applied to the targeted block in chain selection. This allows the attacker to:

1. **Artificially boost an adversarial fork**: by injecting a certificate that boosts a block on a minority or adversarial chain, the attacker can make that chain appear heavier than the honest chain, causing honest nodes to switch to it.
2. **Render the Peras quorum mechanism meaningless**: the entire purpose of requiring a quorum of stake-weighted votes before issuing a certificate is bypassed — any single peer can manufacture the equivalent of a quorum certificate.
3. **Trigger spurious chain switches**: repeated injection of certificates for different blocks can cause oscillating chain selection, destabilizing the node's view of the canonical chain.

This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only the ability to connect to a node as a peer and send a well-formed `PerasCert` message over the Peras certificate mini-protocol. No keys, no stake, no prior chain knowledge beyond a target block point is needed. The `PerasCert` type contains only a `PerasRoundNo` and a `Point blk` (slot + hash), both of which are public information observable from the chain. The attack is therefore trivially executable by any network peer.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The aggregate BLS signature over the certificate covers the claimed `(roundNo, boostedBlock)` pair.
- The signing keys belong to eligible committee members for the claimed round (verified against the stake distribution snapshot).
- The aggregate stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold`).
- The `pcCertRound` is within an acceptable window relative to the current chain tip.

Until a real implementation is available, the Peras certificate inbound mini-protocol should be disabled or the `processCerts` path should reject all inbound certificates rather than accepting them unconditionally.

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate object-diffusion mini-protocol.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversarial block>`.
3. Send the certificate to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` unconditionally.
5. The certificate is passed to `ChainDB.addPerasCertAsync`, which enqueues `ChainSelAddPerasCert`.
6. `chainSelSync` processes the message: the adversarial block's weight in `PerasWeightSnapshot` is incremented by `perasWeight`.
7. On the next chain selection evaluation, `preferAnchoredCandidate` now considers the adversarial fork heavier than the honest chain, and the node switches to it. [6](#0-5) [7](#0-6) [8](#0-7)

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
