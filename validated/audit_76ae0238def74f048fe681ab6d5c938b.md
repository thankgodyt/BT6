Audit Report

## Title
Missing `#[pause]` Guard on `deploy_token` Renders Token-Deployer Pause Ineffective - (File: `near/token-deployer/src/lib.rs`)

## Summary

`TokenDeployer` derives `Pausable` and configures a `PauseManager` role, but its sole state-mutating entry point `deploy_token` carries no `#[pause]` attribute. As a result, pausing the token-deployer has zero effect on token deployments. An external user can submit a valid cross-chain proof to the omni-bridge's (unpaused) `deploy_token`, which calls through to the token-deployer as `Controller`, bypassing the token-deployer's pause state entirely.

## Finding Description

`TokenDeployer` explicitly derives `Pausable` and registers `PauseManager`: [1](#0-0) 

The `deploy_token` function carries only an access-control guard — no `#[pause]` check: [2](#0-1) 

By contrast, the omni-bridge's own `deploy_token` correctly applies `#[pause(except(roles(Role::DAO)))]`: [3](#0-2) 

The omni-bridge's pause guard only protects the omni-bridge contract. When the token-deployer is paused independently (e.g., a flaw in `global_code_hash` is discovered), the omni-bridge — if not simultaneously paused — can still call through to the token-deployer via `ext_deployer::ext(...).deploy_token(...)`: [4](#0-3) 

The token-deployer then executes unconditionally, creating a new account and initializing it with the current `global_code_hash`: [5](#0-4) 

The exploit path is reachable by an unprivileged external user: the omni-bridge's `deploy_token` is a public function gated only by proof verification. Any user who can supply a valid cross-chain `LogMetadata` proof can trigger the full call chain into the token-deployer, regardless of the token-deployer's pause state.

## Impact Explanation

This is a concrete pause bypass matching the Critical allowed impact: *"pause bypass that lets an attacker execute bridge, token, deployer, or admin-equivalent actions."* The token-deployer's `PauseManager` role and `Pausable` derivation establish the clear security invariant that pausing the contract stops token deployments. That invariant is broken. During an emergency where the token-deployer is paused (e.g., a discovered vulnerability in the deployed token contract code or a pending `global_code_hash` rotation), the omni-bridge can still trigger new token deployments, potentially deploying tokens from a known-vulnerable code hash. This is deployer-equivalent action executed in violation of the operator's emergency pause.

## Likelihood Explanation

The scenario requires the token-deployer to be paused while the omni-bridge is not — a realistic selective-pause operational state. The `PauseManager` role exists precisely to allow targeted pausing of individual components. Once in this state, any external user with a valid cross-chain proof (a normal bridge user or relayer) can trigger the bypass through the omni-bridge's public `deploy_token`. No privileged access is required on the attacker's side; the omni-bridge acts as `Controller` automatically. The condition is repeatable for every valid proof submitted while the token-deployer is paused.

## Recommendation

Add a `#[pause]` guard to `deploy_token` in `near/token-deployer/src/lib.rs`, consistent with the pattern used in the omni-bridge. Whether to include a DAO exception should be decided based on operational requirements:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
#[access_control_any(roles(Role::Controller, Role::LegacyController))]
pub fn deploy_token(&mut self, account_id: AccountId, metadata: &BasicMetadata) -> Promise {
```

## Proof of Concept

1. Deploy the token-deployer with the omni-bridge as `Controller` and a test account as `PauseManager`.
2. Call `pa_pause_feature` (or equivalent `near-plugins` pause entry point) on the token-deployer from the `PauseManager` account to pause it.
3. Confirm the omni-bridge is **not** paused.
4. From any external account, call the omni-bridge's `deploy_token` with a valid `LogMetadata` proof for a new token.
5. Observe the omni-bridge calls `ext_deployer::ext(deployer).deploy_token(token_id, metadata)` and the token-deployer executes unconditionally — a new token account is created despite the token-deployer being paused.
6. Confirm that adding `#[pause]` to the token-deployer's `deploy_token` causes the call to panic with a pause error under the same conditions.
