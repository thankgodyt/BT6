Audit Report

## Title
Unvalidated Destination Chain in `init_transfer` Enables Permanent Locking of User Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function performs only a single chain-level check — that the recipient chain is not `Near` — before locking or burning the user's tokens and inserting the transfer into `pending_transfers`. If the destination chain has no registered factory or token mapping, the subsequent `sign_transfer` call panics before reaching the MPC signer, and no public cancellation or refund path exists to recover the locked funds.

## Finding Description
At lines 531–534, `init_transfer` validates only that the recipient chain is not `Near`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

No check is made against `self.factories` (chain → registered factory) or `self.token_id_to_address` (chain × token → foreign address). After this check, `init_transfer_internal` is called (line 583 or 645), which locks or burns the user's tokens and stores the transfer in `pending_transfers`.

When a relayer later calls `sign_transfer`, execution reaches lines 462–469:

```rust
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

Because no token address is registered for the unsupported destination chain, this panics. The panic occurs before the MPC signing call, so `sign_transfer_callback` is never reached and the transfer is never removed from `pending_transfers`.

The only paths that call `remove_transfer_message` are:
- `sign_transfer_callback` (lines 655–658): only removes on successful signing with zero fee — unreachable here since signing panics.
- `claim_fee_callback` (line 1094): requires a valid proof from the destination chain and a registered factory (lines 1088–1091) — impossible for an unsupported chain.

No `cancel_transfer` or timeout-based refund function exists anywhere in `lib.rs`.

The `ChainKind` enum in `omni-types/src/lib.rs` includes variants such as `Fogo`, `Abs`, `HyperEvm`, and `Strk` that may have no factory deployed. Since these variants are part of the contract's own type system, a user or front-end can reasonably select them expecting support.

## Impact Explanation
Any user who initiates a transfer to a `ChainKind` variant with no registered factory will have their tokens permanently locked in the bridge with no recovery path. This constitutes direct, irreversible loss of bridged funds — matching the critical impact class of "permanent freezing of bridged funds."

## Likelihood Explanation
The entry path is fully unprivileged: any token holder can call `ft_transfer_call` on any NEP-141 token, specifying the bridge as receiver and an `InitTransfer` message with any `ChainKind` recipient. The `ChainKind` enum is a small, fixed set of named variants visible in the contract's type definitions, making it trivial for a user or a buggy front-end to select a chain that is recognized by the type system but has no factory registered. No special role or key is required.

## Recommendation
Add a factory-existence check inside `init_transfer` before any tokens are locked:

```rust
require!(
    self.factories.contains_key(&init_transfer_msg.get_destination_chain()),
    BridgeError::InvalidRecipientChain.as_ref()
);
```

Additionally, implement a `cancel_transfer` function allowing the original sender to reclaim locked tokens for transfers that have been pending beyond a configurable timeout, as defense-in-depth.

## Proof of Concept
1. Assume `ChainKind::Fogo` has no factory registered in `self.factories`.
2. User calls `ft_transfer_call` on a NEAR NEP-141 token with `receiver_id` set to the omni-bridge contract and `msg` set to `BridgeOnTransferMsg::InitTransfer` with `recipient` on `ChainKind::Fogo`.
3. `ft_on_transfer` → `init_transfer` executes. The check at lines 531–534 passes (Fogo ≠ Near).
4. `init_transfer_internal` is called; user's tokens are locked/burned. The transfer is inserted into `pending_transfers`.
5. A relayer calls `sign_transfer` for this transfer ID.
6. `get_token_address(ChainKind::Fogo, token_id)` returns `None`; the contract panics with `FailedToGetTokenAddress` at lines 462–469.
7. `sign_transfer_callback` is never reached. The transfer remains in `pending_transfers` indefinitely.
8. `claim_fee_callback` is also blocked: the factory check at lines 1088–1091 fails because no factory is registered for `Fogo`.
9. No `cancel_transfer` function exists. User's tokens are permanently lost.
