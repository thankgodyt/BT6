### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Adversarial Chain Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation unconditionally accepts every inbound `PerasCert` without performing any cryptographic, structural, or committee-membership check. The peer identity available at the miniprotocol handler level is never forwarded to the validation callback. An unprivileged peer can send a crafted certificate for any block, which will be accepted and used to boost that block's weight in chain selection, potentially causing honest nodes to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the sole validation gate for inbound Peras certificates. The only production instance — applied to all block types — unconditionally returns `Right` for every certificate it receives:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired directly into the production cert-diffusion inbound handler. The full call chain is:

**Step 1.** `hPerasCertDiffusionClient` in `mkHandlers` constructs the inbound handler by calling `objectDiffusionInbound` with `makePerasCertPoolWriterFromChainDB systemTime getChainDB`. The `peer :: ConnectionId addr` argument is available here but is only used for tracing — it is never forwarded to the writer or the validator. [2](#0-1) 

**Step 2.** `makePerasCertPoolWriterFromChainDB` builds an `ObjectPoolWriter` whose `opwAddObjects` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function. [3](#0-2) 

**Step 3.** `processCerts` calls `validateCert` on every cert not already in the DB. Because `validatePerasCert` always returns `Right`, every cert passes. [4](#0-3) 

**Step 4.** Each accepted cert is passed to `addPerasCertAsync`, which enqueues it for chain selection. Chain selection then applies the `perasWeight` boost (currently 15 blocks) to the adversarially chosen block. [5](#0-4) 

The `ObjectPoolWriter` interface carries no peer identity field, so even if a real validator were installed, it would have no way to authenticate the source of the certificate: [6](#0-5) 

The `PerasCertDiffusion` protocol is included in both `initiator` and `initiatorAndResponder` bundles, making it reachable from any connecting peer: [7](#0-6)

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

A crafted `PerasCert` with an attacker-chosen `pcCertBoostedBlock` is accepted without any signature, quorum, or committee-membership check. The cert is stored in the `PerasCertDB` and triggers `addPerasCertAsync`, which feeds into chain selection. The boosted block receives a weight of `perasWeight mkPerasParams = 15`, which can tip chain selection toward the adversarial fork. Because the cert is persisted, the effect survives node restarts until the cert is garbage-collected. [8](#0-7) 

---

### Likelihood Explanation

**High.** The `PerasCertDiffusion` miniprotocol is unconditionally wired into the production node-to-node application stack. Any peer that completes the handshake and speaks this protocol can send a crafted cert. No privileged keys, stake, or special role is required. The attacker needs only a standard TCP connection to a node that has the Peras feature flag enabled.

---

### Recommendation

1. **Implement real validation in `validatePerasCert`**: verify the aggregate BLS signature against the committee's public keys, confirm that the signers form a valid quorum (≥ 3/4 + safety margin of total stake), and check that the boosted block exists on a known chain.

2. **Pass the peer identity into the `ObjectPoolWriter`**: extend `opwAddObjects` (or add a separate `opwAddObjectsFromPeer`) to carry the `ConnectionId` so that per-peer rate limiting and source authentication can be enforced at the validation layer.

3. **Gate the protocol on feature-flag readiness**: until full validation is implemented, the `PerasCertDiffusion` protocol should be disabled or should reject all inbound certs rather than accepting them unconditionally.

---

### Proof of Concept

```
1. Attacker connects to a Cardano node with the PerasCertDiffusion protocol enabled.

2. Attacker sends a PerasCert message:
     PerasCert { pcCertRound    = <any round number>
               , pcCertBoostedBlock = <Point of adversarial block> }

3. processCerts calls validatePerasCert mkPerasParams cert
   => unconditionally returns Right (ValidatedPerasCert { vpcCertBoost = 15 })

4. The cert is enqueued via addPerasCertAsync and processed by chainSelSync.

5. Chain selection adds weight 15 to the adversarial block.
   If the adversarial fork's cumulative weight now exceeds the honest tip,
   the node switches to the adversarial chain.

6. The node is now on a non-canonical chain, breaking consensus safety.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
