### Title
Missing Access Control on `sign_btc_transaction` Allows Any Caller to Trigger MPC Signing of Arbitrary Pending Transactions - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

---

### Summary

`sign_btc_transaction` in the bridge contract carries no role-based access control. Any unprivileged NEAR account can invoke it against any `btc_pending_sign_id`, forcing the MPC chain-signature service to sign inputs for withdrawal or refund transactions they do not own. This is the direct analog of the reported `PolicyTerminationBlueprint` pattern: a sensitive, state-advancing operation is callable by anyone.

---

### Finding Description

Every other state-advancing bridge function is guarded by either `#[trusted_relayer]` or `#[access_control_any(roles(...))]`:

| Function | Guard |
|---|---|
| `verify_deposit_v2` | `#[trusted_relayer]` |
| `verify_withdraw_v2` | `#[trusted_relayer]` |
| `verify_active_utxo_management_v2` | `#[trusted_relayer]` |
| `cancel_withdraw` | `#[access_control_any(roles(Role::DAO, Role::Operator))]` |
| `active_utxo_management` | `#[access_control_any(roles(Role::DAO, Role::Operator))]` |

`sign_btc_transaction` carries **only** `#[payable]` and `#[pause(except(roles(Role::DAO)))]`: [1](#0-0) 

Inside the function body there is no check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. The code retrieves the pending info, asserts it is in the `PendingSign` state, and immediately delegates to `internal_sign_btc_transaction`: [2](#0-1) 

The `#[trusted_relayer]` macro (applied at the `impl` block level for other groups) is **absent** from this `impl` block: [3](#0-2) 

Compare with the deposit/withdraw group, which opens with `#[trusted_relayer]` before `#[near]`: [4](#0-3) 

The CLAUDE.md design note confirms the intended pattern — `#[trusted_relayer]` is the expected decorator for relayer-callable functions: [5](#0-4) 

---

### Impact Explanation

Once an attacker calls `sign_btc_transaction` for a victim's `btc_pending_sign_id`, the MPC service signs that PSBT input. When all inputs are signed the bridge assembles the final `tx_bytes_with_sign` and the transaction is ready to broadcast. At that point:

1. **RBF cancellation is blocked.** `withdraw_rbf` (the user's only self-service cancel path) checks `assert_pending_sign` — once the state advances past `PendingSign` the user can no longer replace the transaction. An attacker who races ahead of a user's intended RBF call locks the user into the original transaction.

2. **Operator cancel is also impeded.** `cancel_withdraw` similarly requires the pending info to still be in the sign stage; a fully-signed transaction bypasses that window.

3. **Refund transactions are equally exposed.** Refund `BTCPendingInfo` entries go through the same `sign_btc_transaction` path. An attacker can force-sign a refund before the DAO/Operator has a chance to reject the underlying `RefundRequest`, causing the MPC to commit to a refund address that might still be under review.

The PSBT outputs are fixed at creation time, so direct fund redirection is not possible. The impact is **forced, premature commitment** to a transaction the owner or operator intended to cancel or modify — matching the "attacker-triggered temporary locking of bridged funds / bypass of bridge policies" medium impact class, with a plausible path to stuck-state requiring operator intervention.

---

### Likelihood Explanation

The function is fully public on mainnet. No token, deposit, or special account is required beyond the NEAR gas/storage deposit that `#[payable]` implies. An attacker only needs to observe a `GenerateBtcPendingInfo` event (emitted on every withdrawal and refund) to obtain a valid `btc_pending_sign_id`. The race window exists for every pending transaction in the system. [6](#0-5) 

---

### Recommendation

Add `#[trusted_relayer]` to the `sign_btc_transaction` impl block (consistent with the deposit/withdraw groups), or apply `#[access_control_any(roles(Role::DAO, Role::UnrestrictedRelayer, Role::Operator))]` directly to the function. Either change restricts callers to whitelisted relayers while preserving the existing `UnrestrictedRelayer` bypass path used in tests.

---

### Proof of Concept

1. Alice calls `ft_on_transfer` with a `Withdraw` message. The bridge emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Alice's BTC price moves; she decides to cancel and prepares a `withdraw_rbf` call.
3. Attacker observes the event and front-runs Alice by calling:
   ```
   sign_btc_transaction("abc123", 0, 0)
   ```
   No role or ownership check prevents this call.
4. The MPC signs input 0. If there is only one input, `tx_bytes_with_sign` is now populated and the state advances out of `PendingSign`.
5. Alice's `withdraw_rbf` call now fails (`assert_pending_sign` panics) — she cannot cancel.
6. The signed transaction is broadcast; Alice's funds are sent to the original target address at the original fee, contrary to her intent. [7](#0-6)

```rust
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
```
