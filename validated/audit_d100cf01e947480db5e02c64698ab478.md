### Title
Peras Quorum Check Compares Unnormalized Vote Stake Against Relative Threshold, Enabling Trivial Certificate Forgery - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras quorum check in `stakeAboveThreshold` directly compares the accumulated `PerasVoteStake` of received votes against the relative `PerasQuorumStakeThreshold` parameter without enforcing that both values are expressed in the same unit. The code itself acknowledges this in a `TODO` comment. When the `PerasVoteStakeDistr` is populated with absolute ledger stakes (the natural representation from the ledger), the comparison is dimensionally incoherent: any pool whose absolute stake exceeds the fractional threshold (e.g., 0.75) trivially passes, allowing a single vote from any non-trivial pool to forge a Peras certificate for an adversarially chosen block. This is the direct analog of the AuraLocker M-03 finding: a cumulative threshold expressed in one unit (relative) is compared against individual contributions expressed in another unit (absolute), skewing the entire voting mechanism.

---

### Finding Description

**Root cause — `stakeAboveThreshold`:** [1](#0-0) 

The function compares `unPerasVoteStake voteStake` directly against `perasQuorumStakeThreshold + safetyMargin`. The comment explicitly states the precondition that both must be in the same units (both relative), but this is **not enforced** anywhere in the type system or at the call site.

**`PerasVoteStake` has no normalization invariant:** [2](#0-1) 

`PerasVoteStake` is a bare `Rational` newtype. The comment acknowledges "there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote." No normalization is applied before the value is stored in `ValidatedPerasVote`.

**Vote stake is assigned directly from `PerasVoteStakeDistr` without normalization:** [3](#0-2) 

`validatePerasVote` looks up the voter's stake from the distribution and stores it verbatim. If the distribution contains absolute ledger stakes (e.g., lovelace amounts or un-normalized rationals), those values flow directly into `vpvVoteStake`.

**WFALS committee selection produces inconsistent units:** [4](#0-3) 

`implEligiblePartyVoteWeight` returns the raw `LedgerStake` for persistent members (absolute) but normalizes by `totalNonPersistentStake` for non-persistent members. When these heterogeneous weights are summed and compared against the relative `PerasQuorumStakeThreshold`, the result is undefined.

**The quorum threshold is a relative value:** [5](#0-4) 

`PerasQuorumStakeThreshold` is documented as a relative (normalized) value. The safety margin is also relative. The comparison in `stakeAboveThreshold` only makes sense when `PerasVoteStake` is also relative.

**Certificate forging path:** [6](#0-5) 

`votesReachQuorum` calls `stakeAboveThreshold` to decide whether to forge a certificate. If the comparison is trivially true (absolute stake >> relative threshold), a certificate is forged for any single vote.

**Production wiring currently uses empty distribution (placeholder):** [7](#0-6) 

The production node-to-node handler passes `PerasVoteStakeDistr mempty`, which currently rejects all votes. The comment explicitly states this is a placeholder pending real plumbing. When that plumbing is completed, if absolute ledger stakes are used to populate the distribution (the natural representation), the quorum check becomes trivially bypassable.

---

### Impact Explanation

**Impact: High — Chain selection bug enabling unauthorized certificate acceptance.**

A Peras certificate boosts the chain weight of the block it certifies. If `stakeAboveThreshold` is trivially satisfied because absolute ledger stakes are compared against a fractional threshold (e.g., a pool with 1,000,000 lovelace stake passes `1000000 >= 0.75`), then:

1. Any stake pool operator can forge a valid Peras certificate for an arbitrary block by submitting a single vote via the Peras vote diffusion mini-protocol.
2. The forged certificate is accepted by `implAddVote` in `PerasVoteDB.Impl` and stored as a legitimate `AddedPerasVoteAndGeneratedNewCert`.
3. The boosted block gains `perasWeight` additional chain weight, causing honest nodes to prefer the adversarially-chosen chain over the canonical one.
4. This constitutes a chain selection failure: an unprivileged peer (any stake pool operator) can make honest nodes adopt a non-canonical chain without controlling a stake majority. [8](#0-7) 

---

### Likelihood Explanation

**Likelihood: Medium.**

The bug is not currently exploitable because the production code uses an empty `PerasVoteStakeDistr`, rejecting all votes. However:

- The Peras feature is under active development and the empty distribution is explicitly a temporary placeholder.
- When the plumbing is completed, the natural implementation is to populate `PerasVoteStakeDistr` with absolute ledger stakes from the epoch snapshot — which is exactly the misconfiguration that triggers the bug.
- The code's own `TODO` comment confirms the normalization step is missing and unresolved.
- The WFALS committee selection already produces inconsistent units (absolute for persistent, normalized for non-persistent), making it likely that the first integration will use absolute values.
- No type-level or runtime guard prevents the mismatch from occurring silently.

---

### Recommendation

1. **Enforce normalization at the boundary.** `stakeAboveThreshold` should either accept the total stake distribution and normalize internally, or the type `PerasVoteStake` should carry a phantom tag distinguishing absolute from relative values, making the mismatch a compile-time error.

2. **Normalize in `validatePerasVote`.** When assigning `vpvVoteStake`, divide the looked-up stake by the total stake in the distribution to produce a relative value before storing it.

3. **Unify WFALS vote weights.** `implEligiblePartyVoteWeight` must normalize persistent member weights by total stake (not just non-persistent total) so that all `VoteWeight` values are relative and comparable against the relative quorum threshold.

4. **Add an assertion or property test** that the sum of all `PerasVoteStake` values in any `PerasVoteStakeDistr` equals 1 (or is bounded by 1), enforcing the relative invariant.

---

### Proof of Concept

The mismatch is directly deducible from the code:

1. `PerasQuorumStakeThreshold` is a `Rational` intended to represent a fraction of total stake (e.g., `0.75`).
2. `PerasVoteStake` is an unconstrained `Rational` — it can hold absolute ledger stake (e.g., `1000000` lovelace).
3. `stakeAboveThreshold` computes `stake >= quorumThreshold + safetyMargin`, i.e., `1000000 >= 0.75 + 0.01` → `True`.
4. `votesReachQuorum` calls `stakeAboveThreshold` with the sum of `vpvVoteStake` from a single vote.
5. Result: a single vote from any pool with absolute stake > threshold trivially forges a certificate.
6. The certificate is stored and used to boost chain weight in chain selection, causing honest nodes to prefer the adversarially-boosted chain. [1](#0-0) [9](#0-8) [4](#0-3)

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin

    unPerasQuorumStakeThreshold

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
  allVotesMatchTarget target =
    all ((== (getPerasVoteTarget target)) . getPerasVoteTarget)

implEligiblePartyVoteWeight ::
  VotingCommittee crypto WFALS ->
  EligibilityWitness crypto WFALS ->
  VoteWeight
implEligiblePartyVoteWeight committee = \case
  -- Persistent members have their voting power equal to their stake
  WFALSPersistentMember
    _seatIndex
    (LedgerStake stake) ->
      VoteWeight stake
  -- Non-persistent members have their voting power proportional to their
  -- number of seats granted by local sortition and their stake (normalized
  -- by the total non-persistent stake)
  WFALSNonPersistentMember
    _seatIndex
    (LedgerStake stake)
    _vrfOutput
    numSeats ->
      VoteWeight $
        fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
          * stake
          / nonPersistentStake
     where
      TotalNonPersistentStake (Cumulative (LedgerStake nonPersistentStake)) =
        totalNonPersistentStake committee
