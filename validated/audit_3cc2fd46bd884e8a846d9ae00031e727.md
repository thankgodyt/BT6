### Title
LoP Bucket Level Reset to Full Capacity on Every GSM State Transition Allows Adversarial Peer to Bypass Limit-on-Patience - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`updateLopBucketConfig` in `Client.hs` unconditionally resets the Limit-on-Patience (LoP) leaky-bucket level to the **full capacity** on every GSM state transition, discarding however many tokens the peer had already consumed. An adversarial peer that has nearly exhausted its LoP budget can trigger a `Syncing → PreSyncing → Syncing` GSM cycle (by briefly dropping below the Honest Availability Assumption threshold) to receive a completely fresh 200-second stalling budget. Repeating this cycle lets the peer stall the syncing node indefinitely, preventing the GDD from disconnecting it and the LoE anchor from advancing, which blocks the node from ever selecting the honest chain.

---

### Finding Description

The LoP bucket is managed by `LeakyBucket` (`Ouroboros/Consensus/Util/LeakyBucket.hs`). Its `updateConfig` primitive accepts a function `f :: (Rational, Config m) -> (Rational, Config m)` that receives the **current** `(level, config)` and returns the **new** `(level, config)`. The returned level is then clamped to `[0, newCapacity]` before being written back. [1](#0-0) 

The caller in `bracketChainSyncClient`, `updateLopBucketConfig`, passes a lambda that **ignores** the old `(level, config)` entirely (`\_ ->`), and always returns `(LeakyBucket.capacity config, config)` — i.e., the new level is always the **full capacity** of the new configuration: [2](#0-1) 

The code's own comment acknowledges this: *"NOTE: The new level is currently the maximal capacity of the bucket; maybe we want to change that later."*

`updateLopBucketConfig` is registered as `cschOnGsmStateChanged` in every `ChainSyncClientHandle` and is called atomically by the NodeKernel whenever the GSM writes a new state. The GSM can transition `Syncing → PreSyncing` whenever the Honest Availability Assumption (HAA) is no longer satisfied, and back `PreSyncing → Syncing` as soon as it is re-satisfied. [3](#0-2) 

When the GSM enters `PreSyncing`, `lopBucketConfig` maps this to `dummyConfig` (capacity 0, rate 0), clamping the level to 0. When the GSM re-enters `Syncing`, `lopBucketConfig` maps this to the full active config (capacity `csbcCapacity = 100,000` tokens), and the reset lambda sets the level back to `100,000` — regardless of how depleted it was before. [4](#0-3) 

---

### Impact Explanation

The LoP is a core Genesis security component. Its purpose is to force adversarial peers to reveal their chain's sparseness within a bounded time window (`TCAP / TDRIP = 100,000 / 500 = 200 s` on mainnet), so the GDD can disconnect them and allow the LoE anchor to advance toward the honest chain. [5](#0-4) 

If an adversarial peer can reset its LoP budget at will, the GDD never accumulates enough evidence to disconnect it. The LoE anchor is therefore permanently stalled at the adversarial peer's intersection, and the syncing node cannot select the honest chain. This is a **chain-selection failure** that lets an unprivileged peer prevent an honest node from converging to the canonical chain, beyond the intended security assumptions of the Genesis design.

---

### Likelihood Explanation

The attack requires only a single adversarial peer that:
1. Is connected to the syncing node during `Syncing` state (normal operation).
2. Can cause the HAA to become temporarily unsatisfied — achievable by disconnecting (reducing the peer count below the HAA threshold) and then reconnecting.

No stake, no keys, no admin access, and no protocol-level forgery are required. The adversarial peer is a standard unprivileged network participant. The GSM `Syncing ↔ PreSyncing` oscillation is a documented, expected transition path. [6](#0-5) 

---

### Recommendation

Preserve the current bucket level (capped by the new capacity) when updating the configuration, exactly as the `LeakyBucket.updateConfig` primitive is designed to support. Replace the ignoring lambda with one that threads the old level through:

```haskell
-- Before (resets to full capacity on every GSM transition):
updateLopBucketConfig lopBucket gsmState =
  LeakyBucket.updateConfig lopBucket $ \_ ->
    let config = lopBucketConfig gsmState
     in (LeakyBucket.capacity config, config)

-- After (preserves consumed tokens; clamp in updateConfig handles cap reduction):
updateLopBucketConfig lopBucket gsmState =
  LeakyBucket.updateConfig lopBucket $ \(oldLevel, _) ->
    let config = lopBucketConfig gsmState
     in (oldLevel, config)
```

The `clamp (0, newCapacity) newLevel` already present inside `LeakyBucket.updateConfig` ensures the preserved level never exceeds the new capacity. [7](#0-6) 

One additional consideration: when transitioning **from** an inactive config (`dummyConfig`, capacity 0) **to** an active `Syncing` config, the clamped old level will be 0, which would immediately trigger `onEmpty` (peer disconnection). The fix should therefore also handle this edge case — for example, by only preserving the level when the previous config was also active (non-dummy), and resetting to full capacity only when activating from a previously inactive state.

---

### Proof of Concept

1. Node starts in `PreSyncing`. Adversarial peer `A` connects.
2. GSM transitions `PreSyncing → Syncing` (HAA satisfied). `updateLopBucketConfig` is called with `Syncing`; bucket level set to `100,000`.
3. Peer `A` withholds headers. Bucket drains at 500 tokens/s. After 190 s, level ≈ 5,000 (10 s from empty).
4. Peer `A` disconnects. HAA is no longer satisfied. GSM transitions `Syncing → PreSyncing`. `updateLopBucketConfig` called with `PreSyncing`; bucket level clamped to 0 (dummyConfig capacity = 0).
5. Peer `A` reconnects. HAA satisfied again. GSM transitions `PreSyncing → Syncing`. `updateLopBucketConfig` called with `Syncing`; bucket level **reset to 100,000**.
6. Peer `A` has a fresh 200-second budget. Repeat from step 3.

The GDD never disconnects peer `A` because the LoP never empties. The LoE anchor never advances past peer `A`'s stale intersection. The syncing node cannot select the honest chain. [8](#0-7) [9](#0-8) [10](#0-9)

The transitions are triggered as follows.

- The nominal path consists of a cycle among the three states.
   - The GSM transitions from PreSyncing to Syncing when the Diffusion Layer indicates the HAA is satisfied.
   - The GSM transitions from Syncing to CaughtUp when every peer simultaneously indicates that is has no subsequent headers to send and the syncing node has selected a chain no worse than any received header.
     This trigger is notably not time based, because an adversary is free to create an alternative chain with a very young tip in order to cause the node to lower its defenses by selecting it.
     This is especially true in the context of an adversarial CSJ Dynamo (see below), which has a temporarily disproportionate influence over the syncing nodes selection.
   - The GSM transitions from CaughtUp to PreSyncing only when the node's selection is older than MaxCaughtUpAge (eg the node was offline for a few hours).
     The MaxCaughtUpAge duration is a parameter of this design; see [Parameter Tuning](#parameter-tuning) below for constraints on it.
     Moreover, this transition is delayed by some small random duration (eg <5 minutes) in order to avoid an undesired simultaneity amongst honest nodes within a struggling honest network.
- But that path is not necessarily guaranteed.
   - The GSM transitions from Syncing to PreSyncing if the Diffusion Layer indicates the HAA is no longer satisfied.

### The Limit on Patience Component

Link to code: [Token bucket](https://github.com/IntersectMBO/ouroboros-consensus/blob/43c1fef4631d7a00879974e785c2291175a5f0dc/ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/LeakyBucket.hs#L30), [ChainSync integration](https://github.com/input-output-hk/ouroboros-consensus/blob/43c1fef4631d7a00879974e785c2291175a5f0dc/ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs#L1905)

If a peer claims to have subsequent headers, they must send them promptly.
Otherwise, a disagreement amongst two peers might suffice to prevent the LoE anchor from advancing but not suffice for the GDD to make a decision.

This is in tension with the fact that any honest peer will inevitably exhibit some bursts of latency --- even just garbage collection could cause it, eg, whether that collection be on the local node or on the remote peer.

To accomodate this tension, the LoP is implemented as a token bucket.
The bucket drips unless the peer has most recently sent MsgAwaitReply or their latest header is beyond the syncing node's forecast range.
If the bucket is ever empty, the LoP disconnects from the peer.
A token is added to the bucket whenever the peer sends a valid header that is longer (a la the block number) than any header they had previously sent, but it's discarded if the bucket is already full.

The rate TDRIP at which the bucket drips and its maximum capacity TCAP are design parameters that must be tuned, see [Parameter Tuning](#parameter-tuning) below.

This component contibutes to Sync Liveness because it forces a peer to enable a GDD decision within a duration of at most TDRIP × (TCAP + L), where L is the number of headers that can be in their alternative chain's GDD window before the GDD disconnects them.
Parameter Tuning will ensure this is less than one minute per adversarial peer, for example.
