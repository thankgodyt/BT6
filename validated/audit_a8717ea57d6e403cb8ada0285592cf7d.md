### Title
Peras Certificate Validation Bypass via Unconditional `validatePerasCert` Stub — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The global degenerate `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) without performing any cryptographic or structural verification of Peras certificates. This is the exact analog of the external report's pattern: a critical two-step operation has its second step (the actual verification/forwarding) missing. Any certificate received from an unprivileged peer via the ObjectDiffusion mini-protocol is accepted as valid, allowing an adversary to inject fabricated certificates that manipulate chain selection weight and cause a node to prefer a non-canonical chain.

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the method responsible for verifying that a received Peras certificate is legitimately signed by a quorum of committee members before it is accepted into the node's state. The global degenerate instance — applied to all block types including production Cardano blocks — implements this as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production certificate ingest pipeline. `makePerasCertPoolWriterFromChainDB` — the writer used when the ChainDB is the backend — passes this stub as the validation function to `processCerts`:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass (which they always do), forwards them to `addCert`: [3](#0-2) 

The accepted certificate is then added to the `PerasCertDB` and triggers chain selection via `addPerasCertAsync`: [4](#0-3) 

`chainSelectionForBlock` is called for the boosted block, potentially switching the node to a non-canonical chain whose weight is artificially inflated by the fabricated certificate: [5](#0-4) 

The analog to the external report is direct: the external bug deducts a fee (step 1) but never transfers it to the treasury (step 2 missing). Here, the validation function is invoked (step 1) but the actual cryptographic verification (step 2) is absent — the certificate is accepted and forwarded to chain selection regardless of its legitimacy.

Additionally, the companion stub `getPerasCertInBlock _ = Nothing` means certificates embedded in on-chain blocks are never extracted, so the ledger state's `shelleyLedgerLatestPerasCertRound` is never updated from on-chain data for production Cardano block types: [6](#0-5) 

The `TestBlock` implementation explicitly documents this bypass: [7](#0-6) 

### Impact Explanation

**Impact: Critical / High.** When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` pointing to any block on a non-canonical fork. Because `validatePerasCert` always returns `Right`, the certificate bypasses all committee-membership and signature checks, is stored in the `PerasCertDB`, and causes `chainSelectionForBlock` to re-evaluate chain selection with the fabricated weight boost applied. This directly enables:

- **Bypass of Peras certificate validation** — unauthorized certificate acceptance without any cryptographic check (Critical per allowed scope: "Bypass of… Peras voting or certificate checks… that enables unauthorized… certificate acceptance").
- **Chain selection manipulation** — an honest node is made to prefer a non-canonical or adversarially-chosen chain (High per allowed scope: "Chain selection… bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain").

### Likelihood Explanation

**Likelihood: High (conditional on Peras being enabled).** The attack requires no special privileges — any peer reachable via the ObjectDiffusion mini-protocol can send certificates. The validation stub is unconditional and has no feature-flag guard at the call site. The CHANGELOG confirms Peras is disabled by default, but any operator enabling it is immediately exposed. The attack path is fully automated and requires no brute force.

### Recommendation

1. Implement real cryptographic validation in `validatePerasCert` — verify committee membership, vote signatures, and quorum threshold before accepting any certificate.
2. Until real validation is implemented, gate `makePerasCertPoolWriterFromChainDB` (and `makePerasCertPoolWriterFromCertDB`) behind the Peras feature flag so the stub is never reachable in a Peras-enabled node.
3. Implement `getPerasCertInBlock` for production Cardano block types so that on-chain certificates are correctly extracted and credited to the ledger state.

### Proof of Concept

1. Configure a node with Peras enabled.
2. Connect as an unprivileged peer via the ObjectDiffusion mini-protocol.
3. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to a block on a non-canonical fork that is present in the node's VolatileDB.
4. Send the certificate batch to the node.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → always returns `Right ValidatedPerasCert{…}`.
6. The certificate is forwarded to `addPerasCertAsync` → enqueued in `cdbChainSelQueue`.
7. `chainSelSync` processes `ChainSelAddPerasCert`, adds the cert to `PerasCertDB`, and calls `chainSelectionForBlock` for the boosted block.
8. Chain selection now sees the non-canonical fork as having higher Peras weight; the node switches to it.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
