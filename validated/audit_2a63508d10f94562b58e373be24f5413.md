### Title
Incorrect `shelleyAfterVoting` Block Counting Causes Premature Era Transition Detection During Chain Growth Violations - (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `ShelleyTransition` counts **all** blocks after the voting deadline within an epoch, but the intended behavior is to count only blocks within the **first stability window** after the voting deadline. During a Chain Growth violation, this causes the Hard Fork Combinator to prematurely report `TransitionKnown` when it should suppress the transition (`TransitionUnknown`), producing an incorrect `EpochInfo` and `LedgerView` used for header validation and slot/time translations — breaking cross-era consensus invariants.

---

### Finding Description

In `applyHelper`, the `shelleyAfterVoting` counter is incremented for every block whose slot is at or after `votingDeadline`: [1](#0-0) 

The `votingDeadline` is computed as: [2](#0-1) 

So `votingDeadline = startOfNextEpoch - 2 * swindow`. The counter therefore accumulates blocks from **both** the first stability window (`[votingDeadline, votingDeadline + swindow)`) and the second stability window (`[votingDeadline + swindow, startOfNextEpoch)`).

The design intent, documented explicitly in `civic_time.md`, is:

> "Silently ignore the on-chain governance … if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth). **(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)**" [3](#0-2) 

The `ShelleyTransition` type's own comment describes the intended semantics: [4](#0-3) 

The counter is consumed by `singleEraTransition` (via `mostRecentTransitionInfo`) to produce `TransitionKnown` or `TransitionUnknown`: [5](#0-4) 

When `TransitionKnown` is returned, `reconstructSummary` includes the next era's parameters in the `EpochInfo`: [6](#0-5) 

This `EpochInfo` is then used in three security-critical paths:

1. **Header validation** — `additionalEnvelopeChecks` uses `epochInfoPrecomputedTransitionInfo` derived from the transition info to validate that a header is in the correct era: [7](#0-6) 

2. **Ledger view forecasting** — `ledgerViewForecastAt` uses the `EpochInfo` to determine whether a slot is in the current or next era, and which stake distribution to use: [8](#0-7) 

3. **Era extension during ticking** — `extendToSlot` uses `epochInfoLedger` (derived from the same transition info) to decide whether to translate the ledger state into the next era: [9](#0-8) 

---

### Impact Explanation

When a Chain Growth violation occurs (the first stability window after the voting deadline has fewer than k+1 blocks), the bug causes `shelleyAfterVoting` to reach k+1 by counting blocks from the second stability window. This makes `singleEraTransition` return `Just epoch` (transition stable) when it should return `Nothing` (transition suppressed).

Consequences:

- The `EpochInfo` prematurely includes the next era's slot length and epoch size.
- `ledgerViewForecastAt` forecasts into the next era using the wrong stake distribution (next era's instead of current era's).
- The ChainSync client validates incoming headers using this incorrect `LedgerView`, potentially **accepting headers from the next era that are actually invalid** (because the transition could still be rolled back), or **rejecting valid current-era headers** (because the node believes it is already in the next era).
- Nodes that correctly detect the Chain Growth violation suppress the transition and remain in the current era, while nodes affected by this bug proceed with the transition — creating a **chain split** between nodes on the same chain.

This breaks the `RollbackInsensitiveTranslations` invariant: a rollback that removes the transition-confirming blocks would change the era, but the node has already committed to the next era's parameters for header validation.

---

### Likelihood Explanation

This bug is triggered when:
1. The on-chain governance has enacted an era transition (protocol version bump).
2. The stability window immediately after the voting deadline (`[votingDeadline, votingDeadline + swindow)`) contains fewer than k+1 blocks — a Chain Growth violation.
3. But the total post-deadline block count within the epoch reaches k+1 by including blocks from the second stability window.

This requires a Chain Growth violation, which can occur during network partitions or when an adversary with significant (but not majority) stake deliberately produces a sparse chain in the critical window. The bug is self-documented as a known issue in the codebase, confirming it is a real defect in production code.

---

### Recommendation

Restrict the `shelleyAfterVoting` counter to only increment for blocks whose slot falls within the first stability window after the voting deadline:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline && blockSlot blk < votingDeadline + swindow
     then succ
     else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

This ensures the counter only reflects blocks in the window that the Chain Growth property guarantees will contain k+1 blocks on an honest chain, matching the intended Iteration 4 behavior described in `civic_time.md`.

---

### Proof of Concept

Consider an epoch with `swindow = 3k/f` slots and a governance outcome enacted before the voting deadline:

- `votingDeadline = startOfNextEpoch - 2*swindow`
- First stability window `[votingDeadline, votingDeadline + swindow)`: contains only `k/2` blocks (Chain Growth violation in this window).
- Second stability window `[votingDeadline + swindow, startOfNextEpoch)`: contains `k+1` blocks (normal density).

**Current behavior**: `shelleyAfterVoting` reaches `k/2 + (k+1) > k`, so `singleEraTransition` returns `Just epoch`. The HFC reports `TransitionKnown`. The `EpochInfo` extends into the next era. Header validation uses the next era's stake distribution.

**Intended behavior**: Only the first stability window counts. Since it has `k/2 < k+1` blocks, the transition should be suppressed. `singleEraTransition` should return `Nothing`. The HFC should report `TransitionUnknown`. Header validation should use the current era's stake distribution.

**Result**: A node affected by this bug accepts headers validated against the next era's stake distribution, while a correctly-behaving node rejects them (or vice versa), causing a consensus split.

reconstructSummary ::
  History.Shape xs ->
  -- | At the tip
  TransitionInfo ->
  HardForkState f xs ->
  History.Summary xs
reconstructSummary (History.Shape shape) transition (HardForkState st) =
  History.Summary $ go shape st
 where
  go ::
    Exactly xs' EraParams ->
    Telescope (K Past) (Current f) xs' ->
    NonEmpty xs' EraSummary
  go ExactlyNil t = case t of {}
  go (ExactlyCons params ss) (TS (K Past{..}) t) =
    NonEmptyCons (EraSummary pastStart (EraEnd pastEnd) params) $ go ss t
  go (ExactlyCons params ss) (TZ Current{..}) =
    case transition of
      TransitionKnown epoch ->
        -- We haven't reached the next era yet, but the transition is
        -- already known. The safe zone applies from the start of the
        -- next era.
        let currentEnd = History.mkUpperBound params currentStart epoch
            nextStart = currentEnd
         in case ss of
              ExactlyCons nextParams _ ->
                NonEmptyCons
                  EraSummary
                    { eraStart = currentStart
                    , eraParams = params
                    , eraEnd = EraEnd currentEnd
                    }
                  $ NonEmptyOne
                    EraSummary
                      { eraStart = nextStart
                      , eraParams = nextParams
                      , eraEnd =
                          applySafeZone
                            nextParams
                            nextStart
                            (boundSlot nextStart)
                      }
