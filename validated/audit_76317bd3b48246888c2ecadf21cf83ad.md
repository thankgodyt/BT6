Audit Report

## Title
Dust Transfer Permanently Freezes User Funds Due to Missing Pre-Normalization Validation — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` burns or locks user tokens on NEAR before any check that the transferred amount normalizes to a non-zero value on the destination chain. When a user sends an amount that normalizes to zero (e.g., less than `10^18` yoctoNEAR-units of a 24-decimal token bridging to a 6-decimal destination), the tokens are permanently frozen: `sign_transfer` will always revert with `InvalidAmountToTransfer`, and no cancel or refund path exists.

## Finding Description

`normalize_amount` uses floor division: [1](#0-0) 

For a 24-decimal NEAR token bridging to a 6-decimal destination, the divisor is `10^18`. Any amount below `10^18` base units normalizes to zero.

The `ft_on_transfer` → `init_transfer` path constructs a `TransferMessage` and only validates `fee < amount`: [2](#0-1) 

It then calls `init_transfer_internal`, which burns or locks the full token amount and stores the transfer in `pending_transfers`, returning `U128(0)` to the NEP-141 callback (tokens are consumed): [3](#0-2) 

Later, when a relayer calls `sign_transfer`, the normalization check fires: [4](#0-3) 

This `require!` panics the entire transaction. Because the panic occurs before the MPC signing call, `sign_transfer_callback` is never reached, the transfer is never removed from `pending_transfers`, and the tokens are permanently lost.

`update_transfer_fee` cannot rescue the transfer: it requires `fee < amount`, so the maximum achievable `amount_without_fee` is `1`, which still normalizes to zero when the decimal gap is `10^18`: [5](#0-4) 

The `normalize_amount` docstring acknowledges that "When fee = 0, dust stays locked/burned" but this refers to sub-unit remainder dust, not to the entire amount normalizing to zero. No cancel or refund function exists in the contract.

## Impact Explanation

This is a **permanent freezing of bridged funds** — a concrete Critical impact. The tokens are burned/locked on NEAR, the `pending_transfers` entry can never be finalized (every `sign_transfer` call panics), and there is no administrative or user-accessible recovery path. This directly matches the allowed Critical scope: "permanent freezing of bridged funds."

## Likelihood Explanation

The scenario requires no special privileges. Any user calling the public `ft_transfer_call` → `ft_on_transfer` path with an amount below the normalization threshold triggers it. For a 24-decimal NEAR token bridging to a 6-decimal EVM chain, the threshold is `10^18` base units (i.e., less than 1 full token). Users unfamiliar with decimal precision differences can easily hit this. No frontrunning or external coordination is required.

## Recommendation

Add a normalization check inside `init_transfer_internal` (or `init_transfer`) before burning/locking tokens. Look up the destination token's `Decimals` and assert the normalized amount is non-zero, mirroring the guard already present in `sign_transfer`:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This check must occur before `burn_tokens_if_needed` / `lock_tokens_if_needed`.

## Proof of Concept

1. Deploy a NEAR token `token.near` with `origin_decimals = 24`; register it in the bridge with `decimals = 6` on Ethereum (normalization factor = `10^18`).
2. User calls `ft_transfer_call` on `token.near` with `amount = 500_000_000_000_000_000` (0.5 tokens, below `10^18`), targeting the bridge with an `InitTransfer` message to an Ethereum recipient and `fee = 0`.
3. `init_transfer` passes the `fee < amount` check. `init_transfer_internal` burns the 0.5 tokens and stores the transfer in `pending_transfers`. `ft_on_transfer` returns `U128(0)` — tokens are gone from the user.
4. Relayer calls `sign_transfer` for this transfer. `normalize_amount(500_000_000_000_000_000, Decimals { origin_decimals: 24, decimals: 6 })` = `500_000_000_000_000_000 / 10^18` = `0`. The `require!(amount_to_transfer > 0)` panics.
5. The transfer remains in `pending_transfers` indefinitely. The 0.5 tokens are permanently burned with no recovery path.

A local integration test can confirm this by: (a) registering the token with the decimal mismatch, (b) calling `ft_transfer_call` with a sub-threshold amount, (c) asserting `ft_on_transfer` returns `U128(0)`, and (d) asserting every subsequent `sign_transfer` call panics with `InvalidAmountToTransfer`.
