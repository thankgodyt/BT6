### Title
Shielded-Only Unified Address as `refund_address` Causes Panic in `execute_refund_callback` Transparent Path — (`contracts/satoshi-bridge/src/network.rs`, `refund.rs`, `zcash_utils/refund.rs`)

### Summary

`request_refund_callback` stores any syntactically valid Zcash address as `refund_address` with no check that it can produce a transparent `script_pubkey`. When `execute_refund` is later called without `chain_specific_data` (the transparent path), `execute_refund_callback` calls `build_refund_output` → `Address::script_pubkey()`, which returns `Err("No receiver found in address")` for a Unified Address that contains only an Orchard receiver. The `.expect("Invalid refund script_pubkey")` call panics, aborting the callback and leaving the refund request permanently unexecutable via the transparent path.

---

### Finding Description

**Step 1 — Accepting the shielded-only UA at request time.**

`request_refund_callback` stores `refund_address` verbatim. There is no call to `Address::parse` or `script_pubkey` to validate that the address is usable on the transparent path: [1](#0-0) 

**Step 2 — Transparent-path branch in `execute_refund_callback`.**

When `chain_specific_data` is `None`, `orchard_bundle` is `None`, so the code takes the transparent branch and calls `build_refund_output`: [2](#0-1) 

**Step 3 — `build_refund_output` panics.**

`build_refund_output` calls `Address::parse` (succeeds, returns `Address::Unified`) then `.expect("Invalid refund script_pubkey")` on the result of `script_pubkey()`: [3](#0-2) 

**Step 4 — `script_pubkey()` returns `Err` for Orchard-only UAs.**

The `Address::Unified` arm iterates receivers looking only for `Receiver::P2pkh` or `Receiver::P2sh`. If neither is present (Orchard-only UA), it falls through and returns `Err("No receiver found in address")`: [4](#0-3) 

**Step 5 — `execute_refund` is public and unprivileged.**

`execute_refund` carries only `#[pause]` — no role gate — so any account can call it: [5](#0-4) 

---

### Impact Explanation

The NEAR callback panics before any state mutation in `finalize_refund_with_psbt`. The refund request remains in storage with `executed = false`. Every subsequent call to `execute_refund` without `chain_specific_data` on this request will also panic. The transparent refund path is permanently broken for this request.

The shielded path (passing a valid Orchard bundle via `chain_specific_data`) is still reachable, so funds are not unconditionally lost — but only if the requester can construct a valid Zcash Orchard bundle paying to the Orchard receiver. If they cannot (e.g., they submitted the UA expecting transparent behavior), the deposit UTXO is permanently stuck.

**Impact class: Low** — publicly reachable panic-driven fault in a production bridge path; no direct theft, but potential permanent locking of user funds if the shielded path is also unavailable to the requester.

---

### Likelihood Explanation

Any user can call `request_refund` with a shielded-only UA (the bridge accepts it without validation), then call `execute_refund` without `chain_specific_data`. The panic is deterministic and reproducible. Likelihood is **medium** given that Zcash users commonly use shielded-only UAs and may not know the bridge requires a transparent receiver for the transparent refund path.

---

### Recommendation

Validate `refund_address` at `request_refund_callback` time: call `Address::parse` and then `script_pubkey()` on the result, and reject the request if it returns an error. This ensures that any stored `refund_address` is always usable on the transparent path before the request is committed to storage.

Alternatively, if shielded-only UAs are intentionally supported, document that `execute_refund` without `chain_specific_data` is not valid for such addresses and add an explicit `require!` guard at the top of `execute_refund_callback` that checks `script_pubkey()` succeeds before proceeding, returning a clean error instead of panicking.

---

### Proof of Concept

1. Construct a Zcash Unified Address containing only an Orchard receiver (no `P2pkh`/`P2sh` component).
2. Call `request_refund` with this UA as `refund_address` and a valid BTC deposit proof. The callback stores it without error.
3. After the timelock, call `execute_refund(utxo_storage_key, None)` (no `chain_specific_data`).
4. Observe that `execute_refund_callback` panics with `"Invalid refund script_pubkey"` at: [6](#0-5) 

5. Confirm the refund request remains in storage with `executed = false` and the transparent path is permanently broken for this UTXO.

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
