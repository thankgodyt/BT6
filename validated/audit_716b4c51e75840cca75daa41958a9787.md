`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance used in production unconditionally returns `Right` from `validatePerasCert` for every certificate received from a peer, performing zero cryptographic or structural validation. The production node-to-node handler wires this stub directly into the inbound certificate diffusion path. An unprivileged peer can therefore send a crafted `PerasCert` naming any block as the boosted target; the node accepts it as a `ValidatedPerasCert` carrying a full `PerasWeight 15` boost and immediately triggers chain selection for the boosted block, potentially causing the node to prefer a non-canonical fork.

---

### Finding Description

`BlockSupportsPeras` is a typeclass whose `validatePerasCert` method is the sole gate between a raw, peer-supplied `PerasCert` and a `ValidatedPerasCert` that carries a chain-selection weight boost. The only deployed instance is the catch-all degenerate one:

```haskell

      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always PerasWeight 15

`processCerts` calls `validateCert` (bound to `validatePerasCert mkPerasParams`) on every inbound certificate not already in the DB. Because the function always returns `Right`, every certificate passes and is forwarded to `addPerasCertAsync`: [4](#0-3) 

`chainSelSync` then processes the certificate: it adds it to the `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block, re-evaluating whether the fork containing that block is now preferred: [5](#0-4) 

Chain selection compares fragments by `length + weightBoostOfFragment`. A `PerasWeight 15` boost means a fork 15 blocks shorter than the canonical chain can be made to appear heavier. [6](#0-5) 

The analog to the ERC721 bug is exact: `delegate()` validates its input while `delegateBySig()` does not, creating inconsistent state that breaks downstream operations. Here, `validatePerasCert` is the validation gate that is supposed to reject invalid certificates, but the deployed implementation skips all checks, allowing any peer-supplied certificate to flow into chain selection as if it were legitimately validated.

---

### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized chain selection manipulation.**

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB. The node accepts it without any signature, committee-membership, or round-number check, stores it in the `PerasCertDB`, and re-runs chain selection with the fake boost applied. If the attacker's target block is on a fork that is within `PerasWeight 15` (= 15 block-lengths) of the canonical tip, the node will switch to that fork. This directly violates the Peras security assumption that only legitimately certified blocks receive a weight boost.

---

### Likelihood Explanation

Any peer that can establish a node-to-node connection and negotiate the `PerasCertDiffusion` mini-protocol can exploit this. No stake, no keys, and no prior knowledge beyond the target block's hash (obtainable from the public chain) are required. The attack is deterministic and requires sending a single well-formed CBOR-encoded `PerasCert` message.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature against the claimed voter set.
2. Checks that the voter set constitutes a valid quorum (≥ 3/4 of total stake) using the committee selection data for the relevant epoch.
3. Validates the round number against the current Peras state (not expired, not in cooldown, etc.).

Until real validation is in place, the inbound certificate diffusion handler should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them. The current TODO comment at `https://github.com/tweag/cardano-peras/issues/120` tracks this work.

---

### Proof of Concept

1. Attacker connects to victim node via the node-to-node protocol and negotiates `PerasCertDiffusion`.
2. Attacker observes a fork block `B_fork` in the VolatileDB (e.g., via `ChainSync`) that is at most 15 blocks behind the canonical tip.
3. Attacker sends a single `PerasCert { pcCertRound = <any fresh round>, pcCertBoostedBlock = blockPoint B_fork }`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }`.
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for `B_fork`.
6. `weightBoostOfFragment` now adds 15 to every candidate fragment containing `B_fork`; if `B_fork`'s chain was within 15 of the canonical chain, the node switches to the fork. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM

      mapM_

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
