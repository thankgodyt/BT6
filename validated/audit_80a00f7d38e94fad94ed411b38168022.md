### Title
Imprecise Chain-Preference Comparison in `checkPreferTheirsOverOurs` Uses Empty Peras Weight Snapshot, Causing Incorrect Peer Disconnection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect a peer whose header is beyond the forecast horizon. This causes the comparison to ignore all Peras weight boosts and fall back to a raw block-number comparison. When the candidate chain is heavier by total Peras weight but shorter by raw block count, the node incorrectly concludes the candidate is not preferred and disconnects the peer with `CandidateTooSparse`, causing the node to remain on a lighter, non-canonical chain.

---

### Finding Description

When the ChainSync client receives a header beyond the forecast horizon, it calls `readLedgerStateHelper`, which — on receiving `Nothing` from the ledger-view projection — calls `checkPreferTheirsOverOurs` before retrying:

```
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
```

`checkPreferTheirsOverOurs` then calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

Inside `preferAnchoredCandidate`, when `isEmptyPerasWeightSnapshot weights` is `True`, the function takes the non-Peras branch and compares only `selectView` (block number + VRF tiebreaker) at the tips:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      ...
      (_ :> ourTip, _ :> theirTip) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (selectView cfg (getHeader1 ourTip))
          (selectView cfg (getHeader1 theirTip)) of ...
  | otherwise =
      ... weightedSelectView cfg weights oursSuffix ...
      ... weightedSelectView cfg weights candSuffix ...
``` [2](#0-1) 

The Peras-aware path computes `wsvTotalWeight = blockNo + weightBoost`, so a chain with fewer blocks but large Peras boosts can be heavier:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [3](#0-2) 

By contrast, the actual chain-selection path in `chainSelectionForBlock` correctly reads the live `PerasWeightSnapshot` from the ChainDB:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [4](#0-3) 

The two code paths are therefore inconsistent: `chainSelectionForBlock` uses the real snapshot; `checkPreferTheirsOverOurs` always uses the empty one.

---

### Impact Explanation

**Impact: High — Chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain.**

Consider the following scenario under active Peras:

1. Our chain has raw block count N with no (or few) Peras boosts → total weight ≈ N.
2. A peer serves a canonical chain with raw block count M < N but with Peras certificate boosts summing to B, such that M + B > N (i.e., the canonical chain is heavier by total weight).
3. The peer sends a header that is beyond the forecast horizon (a legitimate occurrence during sync or after a slot gap).
4. `checkPreferTheirsOverOurs` fires, compares only raw block numbers (M < N), concludes `ShouldNotSwitch`, and throws `CandidateTooSparse`.
5. The node disconnects from the peer serving the canonical chain.
6. The node remains on its current lighter chain, which is non-canonical under Peras chain selection.

This is a direct chain-selection error: the node rejects the heavier canonical chain and retains a lighter non-canonical one, violating the Peras chain-order invariant that `wsvTotalWeight` governs preference.

---

### Likelihood Explanation

**Likelihood: Medium.**

- The bug is triggered by any peer sending a header beyond the forecast horizon while Peras weight boosts are active — a normal operational condition once Peras is deployed.
- No special privileges, key material, or stake majority are required; any unprivileged peer can trigger the code path simply by serving a valid Peras-boosted chain.
- The developers have already acknowledged the issue with a `TODO` comment referencing `https://github.com/tweag/cardano-peras/issues/64`, confirming awareness but no fix yet in this codebase.
- The bug only manifests when Peras certificates are actively boosting blocks and the boosted chain happens to be shorter in raw block count than the local chain — a realistic but not constant condition.

---

### Recommendation

Pass the live `PerasWeightSnapshot` (obtained from `Query.getPerasWeightSnapshot` or equivalent) into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`, mirroring the pattern already used in `chainSelectionForBlock`. This ensures the forecast-horizon disconnection check uses the same chain-order metric as the actual chain-selection logic, eliminating the inconsistency.

---

### Proof of Concept

**Setup:** Peras is active; the live `PerasWeightSnapshot` contains a boost of weight B for a block at point P on the candidate chain.

**Trigger sequence:**

1. Honest peer connects and advertises a candidate chain fragment `theirFrag` whose tip has `blockNo = M`.
2. Our current chain `ourFrag` has tip `blockNo = N`, where `M < N` but `M + B > N` (candidate is heavier by total Peras weight).
3. Peer sends a header at slot S that is beyond the forecast horizon (i.e., `forecastFor forecast S` returns `OutsideForecastRange`).
4. `readLedgerStateHelper` receives `Nothing` from `prj lst` and calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` compares `selectView` at tips: `M < N` → `ShouldNotSwitch GT`.
6. `checkPreferTheirsOverOurs` throws `CandidateTooSparse`, disconnecting the peer.
7. Node remains on the lighter chain (total weight N) instead of adopting the heavier canonical chain (total weight M + B > N).

**Root cause line:** `emptyPerasWeightSnapshot` at [5](#0-4) 

**Correct weight path (not used here):** [6](#0-5)

          (Empty ourAnchor, _ :> theirTip) ->
