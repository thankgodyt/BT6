Audit Report

## Title
Non-Atomic Token Swap in `swap_migrated_token` Causes Permanent User Fund Loss - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `swap_migrated_token` function issues a detached parallel promise (`burn.and(mint).detach()`) while `ft_on_transfer` immediately returns `U128(0)`, causing the NEP-141 contract to consume all of the user's old tokens before the mint resolves. If `mint` fails — which happens whenever the recipient is not registered on the new token contract — the user's old tokens are permanently burned with no new tokens minted and no recovery path.

## Finding Description
When a user calls `ft_transfer_call` on `old_token` with the `SwapMigratedToken` message, the bridge's `ft_on_transfer` handler dispatches to `swap_migrated_token` and immediately returns `U128(0)`:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
``` [1](#0-0) 

Returning `U128(0)` tells the NEP-141 contract to refund zero tokens — all transferred tokens are consumed by the bridge — before the detached promise resolves.

`swap_migrated_token` then schedules two parallel cross-contract calls:

```rust
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
``` [2](#0-1) 

In NEAR, `Promise::and` schedules both sub-promises independently and in parallel. If `mint` panics, `burn` still executes. Because the combined promise is `.detach()`ed, there is no callback to detect failure and trigger a refund.

The `mint` function calls `internal_deposit(&account_id, amount.into())`: [3](#0-2) 

`internal_deposit` from `near-contract-standards` panics if `account_id` is not registered on the token contract. Users holding old tokens at migration time are not automatically registered on the new token contract, so this panic is the default outcome for any user who has not explicitly called `storage_deposit` on `new_token` beforehand.

A secondary failure path exists because `migrate_deployed_token` also detaches its `storage_deposit` call on `new_token`: [4](#0-3) 

If a user submits their `ft_transfer_call` before this detached `storage_deposit` is processed, the bridge itself has no storage on `new_token`, causing `mint` to fail even for users who are registered.

## Impact Explanation
Any user who calls `ft_transfer_call` on `old_token` with `SwapMigratedToken` and whose `mint` fails will permanently lose their old tokens. The old tokens are burned from the bridge's balance, and no new tokens are minted. This is a direct, permanent loss of bridged funds — the user's balance is reduced with no corresponding credit. This matches the Critical allowed impact: permanent loss of bridged funds across NEAR token flows.

## Likelihood Explanation
The failure condition for unregistered storage on `new_token` is the default state for any user who holds old tokens at migration time. No attacker is required — any ordinary user who attempts the swap without first registering on `new_token` will silently and permanently lose their funds. The race condition with the detached `storage_deposit` adds an additional failure window immediately after `migrate_deployed_token` is called. Both conditions are reachable by any unprivileged token holder through standard public contract calls.

## Recommendation
1. Replace the detached parallel promise with a sequential, callback-guarded flow: mint first, and only burn on confirmed mint success. This ensures atomicity.
2. Alternatively, do not return `U128(0)` from `ft_on_transfer` for `SwapMigratedToken` until the full promise chain has been verified via a callback; return the full `amount` on failure to trigger a NEP-141 refund.
3. Before accepting the swap, verify the recipient has storage registered on `new_token` via `storage_balance_of`, and reject (return full `amount`) if not registered.

## Proof of Concept
1. DAO calls `migrate_deployed_token(Eth, old_token, new_token)`. The `storage_deposit` on `new_token` is detached and pending.
2. Alice holds 1000 `old_token` and has not registered storage on `new_token`. She calls `ft_transfer_call(bridge, 1000, "SwapMigratedToken")` on `old_token`.
3. Bridge's `ft_on_transfer` returns `U128(0)` immediately — Alice's 1000 `old_token` are consumed by the NEP-141 contract (no refund).
4. The detached `burn.and(mint)` executes in parallel: `burn` succeeds (bridge's balance of `old_token` is reduced by 1000), `mint` panics because Alice is not registered on `new_token` (`internal_deposit` panics).
5. Alice has lost 1000 `old_token` and received 0 `new_token`. No callback exists to detect the failure. No recovery path exists.
