### Title
Missing Access Control on `clear_invalid_pending_verify_rbf` Allows Any Caller to Invoke Privileged Off-Chain Cleanup — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` are explicitly documented as being driven by an **off-chain program**, yet carry no role-based access control. Any unprivileged NEAR account can call them. This is the direct analog of the `SDLVesting::stakeReleasableTokens` vulnerability: a function intended for a trusted automated actor is left open to the public.

---

### Finding Description

In `contracts/satoshi-bridge/src/api/bridge.rs`, the two cleanup functions are decorated only with `#[pause]` — no `#[trusted_relayer]`, no `#[access_control_any]`, no caller assertion:

```rust
/// Since there can be many RBFs, removing all RBF pending info at once after verifying
/// the transaction on-chain might not have enough gas.
/// Therefore, the off-chain program uses this interface to perform the cleanup.
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) {
    self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
}

#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
``` [1](#0-0) 

The inline comment explicitly states the caller is an **off-chain program** — the same trust assumption that `SDLVesting::stakeReleasableTokens` made about its staking bot. Every other privileged operational function in the same file is gated: `cancel_withdraw` and `active_utxo_management` carry `#[access_control_any(roles(Role::DAO, Role::Operator))]`, and deposit/withdraw verification functions carry `#[trusted_relayer]`. [2](#0-1) [3](#0-2) 

The RBF lifecycle creates multiple `BTCPendingInfo` entries per withdrawal (original + one per fee-bump). After the winning transaction is confirmed on-chain via `verify_withdraw`, the superseded entries become stale. The off-chain program is supposed to call `clear_invalid_pending_verify_rbf` only at that point. Because there is no access control, an attacker can call it at any time — including **before** the winning transaction is confirmed.

---

### Impact Explanation

If `internal_clear_invalid_pending_verify_rbf` removes a `BTCPendingInfo` entry without first asserting that the original transaction has already been finalized on-chain, an attacker can:

1. **Front-run the off-chain program** and delete a still-live RBF pending entry.
2. The corresponding `btc_pending_sign_ids` / `btc_pending_verify_list` bookkeeping on the user's account becomes inconsistent.
3. The withdrawal can no longer be finalized via `verify_withdraw` (the pending info it looks up is gone), permanently locking the user's funds in the bridge — the nBTC was already burned on NEAR when the withdrawal was initiated, and the BTC transaction can no longer be acknowledged by the contract.

This matches the **Medium** allowed impact: *attacker-triggered temporary (or permanent) locking of bridged funds* and *stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

The entry point is fully public — no deposit, no whitelist, no role. Any NEAR account can submit a transaction calling `clear_invalid_pending_verify_rbf` with any string argument. An attacker monitoring the mempool (or simply polling view functions) can identify active RBF pending IDs and race the legitimate off-chain cleanup call. The attack requires no special knowledge beyond a valid `btc_pending_verify_id`, which is derivable from public bridge events.

---

### Recommendation

Apply the same access-control pattern used by every other operator-level function in the file:

```rust
#[payable]
#[access_control_any(roles(Role::DAO, Role::Operator))]
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) {
    self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
}

#[payable]
#[access_control_any(roles(Role::DAO, Role::Operator))]
#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
```

Alternatively, add the off-chain cleanup bot's account to the relayer whitelist and apply `#[trusted_relayer]`, consistent with how `verify_withdraw` and `verify_deposit` are protected.

---

### Proof of Concept

```javascript
// Attacker observes an active RBF pending ID from bridge events or view calls
const activePendingId = await bridge.get_btc_pending_info({ btc_pending_id: knownId });
// Pending entry exists and withdrawal is in-flight (not yet verified on-chain)

// Attacker calls the unguarded cleanup function before the off-chain program does
await bridge.clear_invalid_pending_verify_rbf(
  { btc_pending_verify_id: knownId },
  { gas: "30000000000000" }
);

// Now the pending info is gone. When the legitimate relayer calls verify_withdraw:
// → internal_unwrap_btc_pending_info panics: "btc pending info not found"
// → The withdrawal can never be finalized; user's nBTC is already burned.
// → Funds are permanently locked unless the DAO manually intervenes.
```
