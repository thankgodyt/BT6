### Title
`validatePerasCert` Always Returns `Right` — Peras Certificate Verification Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance in the codebase — implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or structural verification. This stub is wired directly into the production inbound Peras certificate diffusion path. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` and `pcCertRound`, have it accepted without any check, and cause the receiving node's chain selection to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate for all inbound certificates. The sole instance in the codebase is the degenerate one:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is checked, no committee membership is verified, no round-number bounds are enforced. Every cert is unconditionally promoted to `ValidatedPerasCert`.

**Production inbound path wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` — the production writer used by the node — passes `validatePerasCert mkPerasParams` as the validation function to `processCerts`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound cert and, if all return `Right`, adds them to the ChainDB: [3](#0-2) 

**The handler is reachable from any peer:**

`hPerasCertDiffusionClient` is wired into the `perasCertDiffusionProtocol` miniprotocol for every node-to-node connection: [4](#0-3) 

The `objectDiffusionInbound` handler calls `opwAddObjects` (which calls `processCerts`) on every batch of objects received from a peer: [5](#0-4) 

**Chain selection is affected by accepted certs:**

`addPerasCertAsync` enqueues the cert into the ChainDB's chain-selection queue. The CHANGELOG confirms: "the candidate fragment is now selected based on its Peras weight, instead of its length." A cert with an attacker-chosen `pcCertBoostedBlock` directly influences which chain the node considers heaviest. [6](#0-5) 

**End-to-end exploit path:**

1. Attacker connects to a victim node as a normal peer (no privileges required).
2. Attacker sends a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = <attacker-chosen block point>` via the `perasCertDiffusionProtocol`.
3. `objectDiffusionInbound` collects the cert and calls `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. `addPerasCertAsync chainDB` enqueues the cert.
6. Chain selection applies the Peras weight boost to the attacker-chosen block, potentially switching the node's preferred chain to a non-canonical fork.
7. The attacker can repeat for any round number not yet in the DB (the only deduplication check is `Set.member roundNo alreadyInDb`). [7](#0-6)

### Impact Explanation

**Severity: Critical — Peras certificate verification bypass.**

When the Peras feature flag is active, any unprivileged peer can inject an arbitrary number of forged `PerasCert` objects (one per round number). Each accepted cert applies a Peras weight boost to an attacker-chosen block. Because chain selection now uses Peras weights, the node can be made to prefer a non-canonical or adversarially-constructed chain over the honest chain. This directly violates the Peras security property that only legitimately quorum-certified blocks receive a weight boost.

The only existing guard — deduplication by round number — does not prevent the attack; the attacker simply uses a fresh round number for each injection. [8](#0-7) 

---

### Likelihood Explanation

**High.** The `perasCertDiffusionProtocol` is negotiated with every peer that supports the Peras NTN version. No stake, no key material, and no prior relationship is required. The attacker only needs to establish a standard peer connection and send a well-formed CBOR-encoded `PerasCert`. The degenerate instance is the only one compiled into the node binary; there is no override path that would invoke real verification.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:

1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed committee members' keys.
2. That the signers collectively hold stake above the quorum threshold for the relevant epoch.
3. That `pcCertRound` falls within the expected range relative to the current slot.

Until real verification is implemented, the `perasCertDiffusionProtocol` inbound handler should reject all externally received certificates (or the protocol should not be enabled in production). The `EveryoneVotes` committee abstraction already defines `verifyCert` with the correct interface; the missing step is wiring it into `makePerasCertPoolWriterFromChainDB` instead of the degenerate instance. [9](#0-8)

### Proof of Concept

```
Attacker node (no stake, no keys)
  │
  │  TCP connection via perasCertDiffusionProtocol
  ▼
Victim node
  objectDiffusionInbound
    └─ opwAddObjects [PerasCert { pcCertRound = 42, pcCertBoostedBlock = <fork tip> }]
         └─ processCerts
              └─ validatePerasCert mkPerasParams cert
                   └─ Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
                        └─ addPerasCertAsync chainDB
                             └─ chainSelSync: applies Peras weight to <fork tip>
                                  └─ node switches preferred chain to attacker-chosen fork
```

The only prerequisite is a valid peer connection. The `PerasCert` CBOR encoding is public: [10](#0-9)
