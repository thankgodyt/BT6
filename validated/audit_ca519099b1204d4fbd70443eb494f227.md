### Title
Peras Certificate Verification Unconditionally Bypassed via Stub `validatePerasCert` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types provides a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Both production inbound-certificate handlers (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) are wired directly to this stub. An unprivileged peer can therefore inject an arbitrary `PerasCert` — with any round number and any boosted block point — and the receiving node will accept it as fully valid, add it to the `PerasCertDB`, and use it to influence chain selection.

---

### Finding Description

**Root cause — stub instance always returns `Right`:**

In `SupportsPeras.hs`, the catch-all `BlockSupportsPeras blk` instance (lines 318–389) is explicitly labelled a "degenerate instance … to get things to compile". Its `validatePerasCert` method ignores every field of the certificate and unconditionally wraps it in `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature check, no round-number bounds check, no boosted-block existence check, and no committee-membership check is performed.

**Production wiring — both cert-pool writers use the stub:**

`makePerasCertPoolWriterFromCertDB` (line 103) and `makePerasCertPoolWriterFromChainDB` (line 126) both pass `validatePerasCert mkPerasParams` as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

**Inbound processing path — every cert from every peer is accepted:**

`processCerts` calls `validateCert` on each certificate not already in the DB. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every cert is forwarded to `addCert`: [4](#0-3) 

The `makePerasCertPoolWriterFromChainDB` variant then calls `ChainDB.addPerasCertAsync`, which feeds the fake cert into chain selection.

**Analog to the reported EIP712 bug:**

The external report describes `__EIP712_init` never being called, leaving `HASHEDNAME`/`HASHEDVERSION` uninitialized so that `castVoteBySig` accepts signatures over the wrong domain. Here, `validatePerasCert` is the analogous "initializer that was never implemented": the verification state (signature check, committee check, round bounds) is entirely absent, so the function accepts every certificate regardless of its content.

---

### Impact Explanation

**Critical — Bypass of Peras certificate/vote checks enabling unauthorized certificate acceptance.**

A malicious peer can craft a `PerasCert` that names any block at any round as the Peras winner. Because `validatePerasCert` always returns `Right`, the node accepts the certificate, stores it in the `PerasCertDB`, and applies the configured `perasWeight` boost to the attacker-chosen block during chain selection. This lets an unprivileged peer make an honest node prefer a non-canonical chain by artificially boosting a minority or adversarial fork, directly violating Peras chain-selection safety.

---

### Likelihood Explanation

**High.** The attack requires only a standard peer connection — no keys, no stake, no operator access. The ObjectDiffusion mini-protocol is reachable from any connected peer. The stub is wired into both production cert-pool writers (not just test helpers), and the TODO comments confirm the real validation logic has not yet been substituted in.

---

### Recommendation

Replace the stub `validatePerasCert` in the `BlockSupportsPeras` instance with a real implementation that verifies:
1. The aggregate BLS/committee signature over `(electionId, candidate)`.
2. Voter eligibility (persistent seat index bounds or non-persistent VRF proof).
3. Round-number plausibility relative to the current ledger view.

Until the real implementation is ready, the production cert-pool writers (`makePerasCertPoolWriterFromCertDB`, `makePerasCertPoolWriterFromChainDB`) should not be deployed on any network where Peras certificates carry chain-selection weight, or should be gated behind a feature flag that is disabled by default.

---

### Proof of Concept

1. Connect a peer to a node running this code.
2. Send a `PerasCert` message via the ObjectDiffusion mini-protocol with:
   - `pcCertRound` = any round number
   - `pcCertBoostedBlock` = the `Point` of an adversarial minority-fork block
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
4. `ChainDB.addPerasCertAsync` stores the cert; chain selection applies the `perasWeight` boost to the adversarial block.
5. If the boost is large enough, the node switches to the adversarial fork.

No cryptographic material, stake, or operator credentials are required.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
