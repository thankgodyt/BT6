### Title
Silent Detached Burn on `safe_mint_callback` Failure Frees UTXO for Double-Minting — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when the downstream `safe_mint` call fails (returns 0, meaning the downstream contract consumed 0 tokens), the bridge simultaneously removes the UTXO from the `verified_deposit_utxo` guard **and** fires a `burn` call with `.detach()`. Because the minted tokens reside with `recipient_id` (not with the bridge), the burn targeting `env::current_account_id()` fails. Since the call is detached, the failure is silently discarded. The UTXO guard is now clear, allowing a relayer to re-submit the same UTXO and mint a second batch of unbacked nBTC.

---

### Finding Description

`safe_mint_callback` is the callback for the `safe_mint` cross-contract call made during the safe-deposit flow. Its failure branch is:

```rust
} else {
    self.data_mut()
        .verified_deposit_utxo
        .remove(&pending_utxo_info.utxo_storage_key);   // (A) guard lifted

    ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
        .with_static_gas(GAS_FOR_BURN_CALL)             // only 5 TGas
        .burn(
            env::current_account_id(),                  // (B) burns from bridge, not recipient
            mint_amount,
            relayer_account_id,
            U128(0),
        )
        .detach();                                       // (C) failure silently ignored

    Promise::new(env::signer_account_id())
        .transfer(self.required_balance_for_safe_deposit())
        .detach();
}
``` [1](#0-0) 

**Step (A)** — The UTXO key is removed from `verified_deposit_utxo`. This is the sole on-chain guard that prevents the same Bitcoin UTXO from being deposited twice. After removal, `verify_deposit_callback` will accept the same UTXO again because its `require!` check uses `insert`, which only panics when the key is *already present*: [2](#0-1) 

**Step (B)** — The burn targets `env::current_account_id()` (the bridge contract itself). However, after a `safe_mint` failure the minted tokens are held by `recipient_id`, not by the bridge. The nBTC contract's `ft_transfer_call` mechanism refunds unconsumed tokens to the original holder (`recipient_id`). The bridge holds zero of those tokens, so the burn call will fail with an insufficient-balance error.

**Step (C)** — The burn promise is `.detach()`-ed. NEAR's promise model means the failure of a detached promise is never observed by the contract. There is no callback, no retry, and no state rollback. The `mint_amount` nBTC tokens remain live with `recipient_id`, permanently unbacked.

The `is_refund_required` helper confirms the trigger condition: it returns `true` (causing `is_success = false`) precisely when `safe_mint` returns `0`, i.e., when the downstream `ft_on_transfer` consumed zero tokens and the nBTC contract refunded them to `recipient_id`: [3](#0-2) 

The `GAS_FOR_BURN_CALL` constant is only 5 TGas, providing a second independent failure path even if the bridge somehow held the tokens: [4](#0-3) 

---

### Impact Explanation

**Critical — Unauthorized minting / unbacked nBTC supply.**

After one failed `safe_mint`:
- `mint_amount` nBTC tokens exist with `recipient_id`, backed by nothing (the burn silently failed).
- The UTXO guard is cleared.

A relayer (the same or a different one) can immediately call `verify_deposit_v2` with the identical UTXO. `verify_deposit_callback` will re-insert the key and trigger a second mint. The recipient ends up with `2 × mint_amount` nBTC backed by a single BTC UTXO. Repeated exploitation inflates the nBTC supply without limit relative to the locked BTC.

---

### Likelihood Explanation

**Medium.** `verify_deposit_v2` is gated by `#[trusted_relayer]`, so an external attacker cannot call it directly. [5](#0-4) 

However, the burn failure is **deterministic and unconditional** whenever `safe_mint` returns 0: the bridge never holds the minted tokens in this code path, so the burn always fails. Any legitimate scenario where a whitelisted downstream contract rejects the transfer (contract paused, storage exhausted, business-logic rejection) silently produces unbacked tokens and a freed UTXO. A compromised or malicious trusted relayer can exploit this deliberately by choosing a downstream contract that reliably returns 0.

---

### Recommendation

1. **Do not remove the UTXO from `verified_deposit_utxo` before confirming the burn succeeded.** Move the `remove` call into a burn callback, executing it only on burn success.
2. **Replace `.detach()` with a proper callback** (analogous to `mint_callback`) that handles burn failure by keeping the UTXO in `verified_deposit_utxo` and/or crediting the amount to `lost_found`.
3. **Increase `GAS_FOR_BURN_CALL`** or compute it dynamically; 5 TGas is insufficient for a storage-touching burn on a live nBTC contract.

---

### Proof of Concept

1. Attacker deposits BTC to a bridge-derived address.
2. Trusted relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)` targeting a whitelisted downstream contract.
3. The downstream contract's `ft_on_transfer` returns `U128(0)` (consumed 0 tokens).
4. `safe_mint` returns `0`; `is_refund_required()` returns `true`; `is_success = false`.
5. `safe_mint_callback` executes the failure branch:
   - Removes UTXO from `verified_deposit_utxo` — guard cleared.
   - Fires `burn(bridge, mint_amount)` with `.detach()` — fails silently because bridge holds 0 of those tokens.
6. `mint_amount` nBTC tokens remain live with `recipient_id`, unbacked.
7. Relayer calls `verify_deposit_v2` again with the same UTXO and `deposit_msg` (standard, non-safe deposit this time).
8. `verify_deposit_callback` inserts the UTXO key (succeeds, since it was removed in step 5) and calls `internal_mint_promise`.
9. A second `mint_amount` (minus fee) nBTC is minted to `recipient_id`.
10. `recipient_id` holds ≈ `2 × mint_amount` nBTC; only one BTC UTXO was ever locked. [6](#0-5)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }

        Ok(value) => {

                // Normal case: refund if the used token amount is zero

                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }

        Err(_) => false,
    }
}
