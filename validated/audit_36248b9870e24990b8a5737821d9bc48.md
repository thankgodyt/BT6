### Title
Unrestricted `request_refund` Allows Any Caller to Front-Run and Redirect a User's BTC Deposit to an Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

`request_refund` in `api/bridge.rs` carries no ownership check: any unprivileged NEAR account can call it for any on-chain deposit whose `deposit_msg.refund_address` is `None` and supply an arbitrary BTC `refund_address`. Because the callback enforces only that the transaction output matches the deposit address derived from `deposit_msg` — not that the caller is the depositor — an attacker who front-runs the legitimate user's call locks the UTXO into a refund request pointing to the attacker's BTC address. If DAO/Operator does not actively reject the request before `unsafe_refund_timelock_sec` elapses, the attacker can call `execute_refund` and receive the user's BTC.

### Finding Description

`request_refund` is a public, payable function gated only by the `#[pause]` macro and an optional `gas_fee` role check: [1](#0-0) 

Inside `internal_request_refund`, the only caller-identity check is whether `deposit_msg.refund_address` (a field embedded in the original BTC transaction) matches the supplied `refund_address`. When that field is `None`, the caller may supply **any** BTC address: [2](#0-1) 

The callback verifies only that the transaction output script matches the deposit address derived from `deposit_msg`; it never checks that `env::predecessor_account_id()` equals `deposit_msg.account_id` or any other ownership field: [3](#0-2) 

A duplicate-request guard prevents a second `request_refund` for the same UTXO: [4](#0-3) 

This means whichever caller wins the race owns the refund request — and therefore controls the `refund_address` stored in it.

The stored `refund_address` is later used verbatim to build the BTC output in `build_refund_output`: [5](#0-4) 

`execute_refund` is also callable by any account (no ownership check, only `#[pause]`): [6](#0-5) 

### Impact Explanation

**Critical.** If the attacker's `request_refund` call lands before the legitimate user's, the UTXO is locked to the attacker's BTC address. After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and the bridge's MPC pipeline constructs and signs a transaction paying the attacker's address. The user's BTC deposit is permanently lost. This matches the allowed impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

**Medium.** The `deposit_msg` is embedded in the OP_RETURN output of the BTC deposit transaction and is therefore publicly visible on-chain. Any observer can reconstruct it, supply a valid Merkle proof (also public), and call `request_refund` with their own BTC address. The only on-chain mitigation is that DAO/Operator can call `reject_refund` before `unsafe_refund_timelock_sec` expires: [7](#0-6) 

This is an operational dependency, not a code-level protection. A monitoring gap, delayed response, or targeted spam of many simultaneous malicious requests across multiple UTXOs can exhaust the operator's capacity to reject in time.

### Recommendation

Add an ownership check inside `request_refund` (or its callback) that requires `env::predecessor_account_id() == deposit_msg.account_id` **or** that the caller holds a privileged role (DAO/Operator/RefundOperator). Alternatively, when `deposit_msg.refund_address` is `None`, restrict `request_refund` to the depositor's NEAR account and to privileged roles, mirroring the pattern already used for `gas_fee`:

```rust
// In request_refund_callback, after verifying the script_pubkey:
let caller = env::predecessor_account_id();
let is_privileged = self.acl_has_any_role(
    vec![Role::DAO.into(), Role::Operator.into(), Role::RefundOperator.into()],
    caller.clone(),
);
if deposit_msg.refund_address.is_none() {
    require!(
        caller == deposit_msg.account_id || is_privileged,
        "Only the depositor or a privileged role may request a refund without a pre-authorized address"
    );
}
```

### Proof of Concept

1. Alice deposits 1 BTC to the bridge with `deposit_msg = { account_id: "alice.near", refund_address: None, … }`. The OP_RETURN in the BTC transaction encodes this `deposit_msg` publicly.
2. The relayer fails to call `verify_deposit` (network issue, or attacker delays it).
3. Bob (attacker) reads the BTC transaction, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { account_id: "alice.near", refund_address: None, … },
     refund_address = "bc1q<bob_address>",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid Merkle proof>,
     gas_fee = None,
   )
   ```
   with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the proof and script_pubkey, finds no duplicate, and stores `RefundRequest { refund_address: "bc1q<bob_address>", created_at_sec: now, … }`.
5. Alice tries to call `request_refund` — it panics: *"Refund request already exists for this UTXO"*.
6. After `unsafe_refund_timelock_sec` elapses (and assuming DAO/Operator did not reject), Bob calls `execute_refund(utxo_storage_key)`.
7. The bridge builds a BTC transaction paying `bc1q<bob_address>` and submits it to the MPC pipeline. Alice's 1 BTC is sent to Bob.

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```

```rust
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
```
