### Title
Peras Vote Signature Verification Bypass via Stub `validatePerasVote` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` function is a stub that accepts any vote from a known stake-pool voter without verifying the BLS vote signature. An unprivileged peer can submit crafted `PerasVote` messages carrying any valid `PerasVoterId` (a publicly-known ledger key hash) but with an entirely absent or forged BLS signature. These votes pass validation, are accepted into the `PerasVoteDB`, and are counted toward the Peras quorum threshold. If enough such votes accumulate, a fraudulent `ValidatedPerasCert` is forged and used to boost an attacker-chosen block in chain selection.

### Finding Description

**Root cause — stub validation in the universal `BlockSupportsPeras` instance:**

The file `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` contains the only deployed `BlockSupportsPeras` instance (lines 320–389). Its own comment acknowledges it is a placeholder:

```
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

The `validatePerasVote` method in this instance performs no BLS signature check whatsoever:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The only check is `lookupPerasVoteStake vote stakeDistr` — whether the `pvVoteVoterId` field of the incoming vote appears in the current stake distribution. The `PerasVote` type carries no BLS signature field at all in this instance:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

**Attacker-controlled entry path — `processVotes` in the ObjectDiffusion mini-protocol:**

Inbound votes arrive via the ObjectDiffusion peer-to-peer mini-protocol. `processVotes` in `ObjectPool/PerasVote.hs` is the production handler:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb =
          filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  ...
``` [3](#0-2) 

The `validateVote` callback supplied by both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` is:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

This resolves to the stub `validatePerasVote` above. No BLS verification is ever invoked on the inbound vote path.

**Deduplication uses `(roundNo, voterId)` — not the vote body:**

The `PerasVoteId` used for deduplication is:

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo  :: !PerasRoundNo
  , pviVoterId  :: !PerasVoterId
  }
``` [5](#0-4) 

The model explicitly acknowledges the equivocation assumption it relies on:

> "NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body)." [6](#0-5) 

Because `validatePerasVote` never checks the BLS signature, this assumption is trivially violated by any peer: an attacker can send a vote with a legitimate `voterId` but for an attacker-chosen `pvVoteBlock`, and it will be accepted as long as no vote from that voter for that round is already in the DB.

**Certificate forging from accepted votes:**

Once enough forged votes accumulate in `PerasVoteDB`, `updatePerasRoundVoteStates` triggers `forgePerasCert` (also a stub that always returns `Right`), producing a `ValidatedPerasCert` that boosts the attacker's chosen block in chain selection. [7](#0-6) 

### Impact Explanation

**Critical — Bypass of Peras vote signature verification enabling unauthorized certificate acceptance.**

An unprivileged peer with no keys can:
1. Enumerate valid `PerasVoterId` values from the public ledger stake distribution.
2. Craft `PerasVote` messages for any block in any round, using those voter IDs.
3. Submit them via the ObjectDiffusion mini-protocol.
4. Have them accepted into `PerasVoteDB` without any BLS signature check.
5. Trigger fraudulent `ValidatedPerasCert` generation once the quorum threshold is crossed.
6. Cause honest nodes to boost an attacker-chosen block in Peras chain selection, potentially overriding the honest chain.

This directly matches the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

### Likelihood Explanation

**High.** The entry point is the standard ObjectDiffusion peer-to-peer mini-protocol, reachable by any connecting peer. The `PerasVoterId` values needed to craft votes are public ledger data. The stub `validatePerasVote` is the only deployed instance for all block types. No privileged access, leaked keys, or cryptographic breaks are required. The only precondition is that the attacker's votes arrive before the legitimate voter's vote for the same `(roundNo, voterId)` pair.

### Recommendation

1. **Implement real BLS signature verification** in `validatePerasVote`. The cryptographic infrastructure already exists in `Ouroboros.Consensus.Peras.Crypto.BLS` (`verifyVoteSignature`, `verifyAggregateVoteSignature`) and the `CryptoSupportsVoteSigning` class. The stub must be replaced before Peras is enabled on any network.
2. **Include the vote signature in `PerasVote`** for the production instance (analogous to `pvSignature` in `Ouroboros.Consensus.Peras.Vote.V1.PerasVote`).
3. **Track the full vote body hash** (not just `(roundNo, voterId)`) as the deduplication key, or explicitly reject equivocating votes (same ID, different target) rather than silently ignoring them.
4. **Resolve issue #120** (`https://github.com/tweag/cardano-peras/issues/120`) before any network deployment.

### Proof of Concept

Attacker connects as a peer and sends via ObjectDiffusion:

```
PerasVote
  { pvVoteRound   = <current round R>
  , pvVoteBlock   = <attacker-chosen block hash B>
  , pvVoteVoterId = <any PerasVoterId from the public stake distribution>
  }
```

`processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote`. Since `pvVoteVoterId` is in `stakeDistr`, `lookupPerasVoteStake` returns `Just stake`, and the vote is accepted as `ValidatedPerasVote` with no BLS check. Repeating this for enough distinct voter IDs (each with stake above the quorum threshold) causes `updatePerasRoundVoteStates` to forge a `ValidatedPerasCert` boosting block B, influencing chain selection on the honest node. [8](#0-7)
