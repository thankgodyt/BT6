### Title
Single Invalid Peras Certificate in a Batch Silently Discards All Valid Certificates, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` — the inbound handler for Peras certificates received over the ObjectDiffusion mini-protocol — rejects an **entire batch** and silently discards all valid certificates whenever **any single certificate** in the batch fails validation. An unprivileged peer can exploit this to suppress valid Peras certificates for the canonical chain from a node's `PerasCertDB`, while separately delivering a valid certificate for an adversarial chain, causing the node to apply a Peras boost only to the adversarial block and potentially prefer a non-canonical chain.

---

### Finding Description

The root cause is in `processCerts`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->                                   -- valid certs silently dropped
      throw (PerasCertValidationError errs)
``` [1](#0-0) 

`partitionEithers` correctly separates valid (`_`) from invalid (`errs`) certificates, but the second branch discards the valid set entirely. The comment in the code acknowledges this is intentional ("reject the whole batch"), but the consequence is that an adversary who controls one peer can prevent any valid certificate in a mixed batch from ever reaching `addCert`.

This function is wired into the production path via `makePerasCertPoolWriterFromChainDB`, which is the writer used by the live node: [2](#0-1) 

The `addCert` callback ultimately calls `ChainDB.addPerasCertAsync`, which feeds into `chainSelSync` / `chainSelectionForBlock` and updates the `PerasWeightSnapshot` used by `preferAnchoredCandidate` during chain selection: [3](#0-2) 

The Peras weight snapshot is read during every chain selection comparison: [4](#0-3) 

**Current dormancy caveat**: The `validatePerasCert` implementation used in both pool writers is currently a stub that unconditionally returns `Right`: [5](#0-4) 

The TODO at issue #120 explicitly plans to replace this with real cryptographic validation. The structural flaw in `processCerts` is already present and will become exploitable the moment real validation is wired in. The `EveryoneVotes` committee scheme already has a concrete `implVerifyCert` that can return `Left` errors: [6](#0-5) 

---

### Impact Explanation

Peras certificates boost specific blocks by adding `vpcCertBoost` weight to them in `PerasWeightSnapshot`. `preferAnchoredCandidate` uses this snapshot when comparing candidate chains. If a node holds a certificate for adversarial block Y but not for canonical block X, chain selection may prefer the adversarial chain. This is a **chain selection bug** that lets an unprivileged peer cause an honest node to prefer a non-canonical chain beyond the intended Peras security assumptions — matching the **High** impact tier.

---

### Likelihood Explanation

Medium. Once real `validatePerasCert` is deployed, the attack requires:
1. Adversarial peer A sends `[cert_X_canonical, crafted_invalid_cert]` — `cert_X_canonical` is silently dropped, peer A is disconnected.
2. Adversarial peer B (separate connection) sends `[cert_Y_adversarial]` — accepted cleanly.
3. The node now boosts block Y but not block X, potentially switching to the adversarial fork.

No stake majority, key compromise, or operator access is needed. Any peer reachable over the ObjectDiffusion mini-protocol can trigger step 1.

---

### Recommendation

Add valid certificates before throwing for the invalid ones, mirroring the escrow pattern recommended in the original report:

```haskell
(errs, validatedCerts) -> do
  -- Still add the valid certs before disconnecting
  mapM_ (addCert . WithArrivalTime now) validatedCerts
  throw (PerasCertValidationError errs)
```

This ensures valid certificates are never silently discarded regardless of what else is in the batch, while still disconnecting from peers that send invalid certificates.

---

### Proof of Concept

1. Real `validatePerasCert` is deployed (per TODO #120).
2. Canonical chain has block X with a valid Peras certificate `cert_X`.
3. Adversary controls peer A (which holds `cert_X`) and peer B.
4. Peer A sends batch `[cert_X, forged_invalid_cert]` to the victim node.
5. `processCerts` runs `partitionEithers`: result is `([err], [cert_X])`.
6. Second branch fires: `throw (PerasCertValidationError [err])` — `cert_X` is in `_`, discarded.
7. Victim disconnects from peer A; `cert_X` never reaches `PerasCertDB`.
8. Peer B sends `[cert_Y_adversarial]` (a legitimately quorum-backed cert for a competing block Y).
9. `processCerts` succeeds; `cert_Y` is added via `addCert → addPerasCertAsync → chainSelSync`.
10. `PerasWeightSnapshot` now boosts block Y but not block X.
11. `preferAnchoredCandidate` may select the adversarial fork over the canonical chain. [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
