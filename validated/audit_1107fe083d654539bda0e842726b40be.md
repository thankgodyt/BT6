### Title
Missing Proof-of-Possession Enforcement Before BLS Public Key Aggregation Enables Rogue Key Attack on Peras Certificate Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

---

### Summary

`aggregatePublicKeys` in `BLS.hs` carries an explicit but **unenforced** precondition that all input keys must have had their Proof-of-Possession (PoP) verified before aggregation. The production call site `aggregateVoteVerificationKeys` in `PerasBLSCrypto` calls `aggregatePublicKeys` directly without performing any PoP check. This omission enables the classical BLS rogue key attack: an adversary who registers a crafted pool BLS key (the additive inverse of a legitimate voter's key) can manipulate the aggregate verification key used in `implVerifyCert`, causing an invalid Peras certificate to pass signature verification.

---

### Finding Description

**Root cause — unenforced precondition in `aggregatePublicKeys`:**

`aggregatePublicKeys` documents two preconditions in its comment but enforces only one (same scope). The second — that PoP has already been verified for every input key — is never checked inside the function, and the function name `uncheckedAggregateVerKeysDSIGN` (the underlying primitive it calls) makes this explicit. [1](#0-0) 

**Call site — no PoP verification before aggregation:**

`PerasBLSCrypto`'s `aggregateVoteVerificationKeys` calls `BLS.aggregatePublicKeys` directly, with no call to `BLS.verifyProofOfPossession` anywhere in the path: [2](#0-1) 

The `verifyProofOfPossession` function is defined and exported but is not invoked in any production code path found in the repository. [3](#0-2) 

**Vulnerable downstream consumer — `implVerifyCert`:**

`implVerifyCert` in `WFALS.hs` collects voter public keys from the stake distribution, calls `aggregateVoteVerificationKeys` to build an aggregate key, and then verifies the certificate's aggregate signature against it. If any input key is a rogue key, the aggregate key is silently corrupted. [4](#0-3) 

The same pattern exists in `EveryoneVotes.hs`: [5](#0-4) 

**Attack mechanics (rogue key attack on BLS aggregate signatures):**

For BLS MinSig (keys in G2, signatures in G1), an attacker who observes a legitimate voter's key `pk_victim` registers a pool with key `pk_rogue = -pk_victim + pk_attacker_real`. When the certificate verifier aggregates all voter keys:

```
agg_key = pk_victim + pk_rogue + pk_others
        = pk_victim + (-pk_victim + pk_attacker_real) + pk_others
        = pk_attacker_real + pk_others
```

The attacker can now produce a valid aggregate signature over `pk_attacker_real + pk_others` using only their own real signing key, making a certificate appear to carry the victim's vote when it does not. This is precisely the attack that PoP is designed to prevent, and it is why the precondition exists in the first place.

---

### Impact Explanation

An unprivileged adversary who registers a stake pool with a crafted BLS vote verification key can cause `implVerifyCert` to accept a forged Peras certificate — one that falsely attests the participation of a legitimate committee member. This is a **bypass of Peras certificate signature verification**, enabling unauthorized certificate acceptance. Under the allowed impact scope this is **Critical**: bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance.

---

### Likelihood Explanation

Pool registration is a normal, permissionless protocol operation requiring only a deposit (no stake majority, no privileged access). The attacker needs to:
1. Observe the BLS public keys of registered pools (public ledger data).
2. Compute the negation of a target key in G2 (trivial elliptic curve arithmetic).
3. Register a pool with the crafted key.

Once the rogue pool is in the stake distribution and included in a voting committee, every certificate verification that includes both the victim and the attacker traverses the vulnerable path. The attack is deterministic and requires no brute force.

---

### Recommendation

Enforce the PoP precondition at the call site before aggregation. In `aggregateVoteVerificationKeys` (and the analogous VRF key aggregation path), verify each key's PoP before passing the key list to `aggregatePublicKeys`. Alternatively, refactor `aggregatePublicKeys` to accept a list of `(PublicKey r, ProofOfPossession)` pairs and verify PoP internally, making it impossible to call without satisfying the precondition. The `verifyProofOfPossession` primitive is already present in the module and only needs to be wired into the aggregation path. [6](#0-5) 

---

### Proof of Concept

1. Observe the BLS `SIGN` public key `pk_victim` of a legitimate registered pool from the ledger state.
2. Compute `pk_rogue = -pk_victim + pk_attacker_real` in G2 (BLS12-381).
3. Register a new stake pool with `pk_rogue` as its BLS vote verification key. No PoP check is enforced at registration or at certificate verification time in this codebase.
4. Wait for both pools to appear in the same `extWFAStakeDistr` and be included in a voting committee.
5. Forge a Peras certificate that lists both `seatIndex_victim` and `seatIndex_attacker` as voters, with an aggregate signature produced solely by `sk_attacker_real`.
6. Submit the certificate. `implVerifyCert` calls `aggregateVoteVerificationKeys` → `BLS.aggregatePublicKeys` → `uncheckedAggregateVerKeysDSIGN`, producing `agg_key = pk_attacker_real + pk_others`. The subsequent `verifyAggregateVoteSignature` call succeeds, and the certificate is accepted as if the victim voted. [7](#0-6) [2](#0-1)

```haskell
-- | Aggregate multiple public keys into a single one.
--
-- PRECONDITION: all keys must have the same scope.
--
-- PRECONDITION: this assumes that proofs of possession have already been
-- verified for all keys in advance.
aggregatePublicKeys ::
  NE [PublicKey r] ->
  Either String (PublicKey r)
aggregatePublicKeys keys@(firstKey :| restKeys) = do
  -- Ensure all keys have the same scope before aggregation
  when (any (/= publicKeyScope firstKey) (fmap publicKeyScope restKeys)) $
    Left "Cannot aggregate public keys with different scopes"
  aggKey <-
    uncheckedAggregateVerKeysDSIGN
      . fmap unPublicKey
      . NonEmpty.toList
      $ keys
  pure $
    PublicKey
      { unPublicKey = aggKey
      , publicKeyScope = publicKeyScope firstKey
      }
```
