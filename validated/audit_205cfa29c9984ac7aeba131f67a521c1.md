### Title
Missing `refund_address` Format Validation in `request_refund_callback` Allows Attacker to Permanently Block Victim's Refund by Front-Running with an Invalid Address - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund_callback` stores the caller-supplied `refund_address` into persistent state without validating it as a well-formed Bitcoin/Zcash address. Because `request_refund` is callable by any unprivileged account and does not require the caller to be the deposit recipient, an attacker can front-run a victim's refund request with an invalid address. The invalid address passes all on-chain checks and is stored. When `execute_refund` is later called, `build_refund_output` panics on the malformed address, making the refund permanently unexecutable until a DAO/Operator manually rejects the poisoned request.

---

### Finding Description

`request_refund` is a public, unprivileged entry point (no `#[trusted_relayer]` attribute on the method itself, only `#[payable]` and `#[pause]`): [1](#0-0) 

Inside `internal_request_refund`, the only checks on `refund_address` are:

1. If `deposit_msg.refund_address` is `Some`, the provided address must match it.
2. No format/parsability check is performed. [2](#0-1) 

The address is then forwarded to `request_refund_callback` as a raw `String`: [3](#0-2) 

Inside `request_refund_callback`, the `refund_address` is stored directly into the `RefundRequest` with no address-format validation: [4](#0-3) 

The duplicate-request guard means only one `RefundRequest` can exist per UTXO: [5](#0-4) 

The address is only parsed — with a hard `.expect()` panic — when `execute_refund` later calls `build_refund_output`: [6](#0-5) 

A NEAR panic reverts all state changes in that call, so the poisoned `RefundRequest` remains in storage and `execute_refund` will keep failing on every retry. Recovery requires a privileged `reject_refund` call: [7](#0-6) 

---

### Impact Explanation

**Medium — attacker-triggered temporary locking of bridged funds.**

A victim whose deposit was never finalized via `verify_deposit` (e.g., amount below `min_deposit_amount`, wrong output, or any other reason the normal deposit path is unavailable) relies entirely on the refund system to recover their BTC. An attacker who front-runs with a poisoned `RefundRequest`:

- Occupies the only slot for that UTXO (duplicate guard).
- Renders `execute_refund` permanently broken for that UTXO.
- Forces the victim to wait for DAO/Operator intervention via `reject_refund`.

Until the DAO acts, the victim's BTC is stuck with no self-service recovery path.

---

### Likelihood Explanation

**Medium.**

- `request_refund` is callable by any NEAR account with a storage deposit attached.
- The victim's `deposit_msg` is frequently public: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`, and relayer calls to `verify_deposit` also expose it on-chain.
- The BTC inclusion proof is public on the Bitcoin blockchain.
- The attacker's only cost is the storage deposit required by `required_balance_for_request_refund()`.
- No special knowledge or privileged access is required beyond observing NEAR and Bitcoin chain data.

---

### Recommendation

Validate `refund_address` as a parseable address for the configured chain **before** the Light Client cross-contract call, inside `internal_request_refund`. This mirrors the pattern already used in `build_refund_output` and `string_to_script_pubkey`:

```rust
// In internal_request_refund, before the verify_transaction_inclusion_promise call:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

Failing early (before the Light Client call) prevents the invalid address from ever reaching storage and avoids wasting the cross-contract gas.

---

### Proof of Concept

1. Victim deposits BTC to their bridge address. The deposit is unfinalized (e.g., below `min_deposit_amount`). The victim's `deposit_msg` is visible on-chain via a prior `get_user_deposit_address` event.
2. Attacker calls `request_refund(deposit_msg, "NOT_A_VALID_BTC_ADDRESS", tx_bytes, vout, proof, None)` with the required storage deposit attached.
3. `internal_request_refund` passes: storage deposit is sufficient, `tx_bytes` length is within bounds, `deposit_msg.refund_address` is `None` so no match check fires.
4. Light Client confirms the BTC transaction is included.
5. `request_refund_callback` fires: deposit script matches, UTXO not yet verified, no duplicate — the `RefundRequest` with `refund_address = "NOT_A_VALID_BTC_ADDRESS"` is inserted.
6. Victim calls `request_refund` with a valid address → **panics**: `"Refund request already exists for this UTXO"`.
7. Anyone calls `execute_refund(utxo_storage_key, None)` → `build_refund_output` calls `Address::parse("NOT_A_VALID_BTC_ADDRESS", chain).expect(...)` → **panics**: `"Invalid refund address"`. State is reverted; the poisoned request remains.
8. Victim's BTC is locked until DAO calls `reject_refund`, after which the victim must re-submit their own request and wait for the full timelock again.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
