### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that is an acknowledged stub: it unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. Because this instance is the one wired into the production Peras certificate ingest path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject arbitrary Peras certificates via the object-diffusion mini-protocol. Those certificates are stored in the `PerasCertDB`/`ChainDB` and immediately influence chain selection by applying a weight boost to the attacker-chosen block, allowing the peer to steer the node toward a non-canonical chain.

### Finding Description

**Root cause — stub validation that always succeeds:**

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate for accepting inbound certificates. The only concrete instance in the codebase is the catch-all `instance StandardHash blk => BlockSupportsPeras blk`, whose implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, round-number, or boosted-block checks are performed. The function returns `Right` for every input unconditionally.

**Ingest path — production code calls this stub:**

`makePerasCertPoolWriterFromChainDB` (the production writer used by the node kernel) passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` partitions the results of calling that callback on every inbound certificate. Because the callback always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is unconditionally forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain-selection consequence:**

A `ValidatedPerasCert` carries a `vpcCertBoost` weight drawn from `perasWeight params`. Once stored in the `PerasCertDB`, this boost is applied during Peras chain selection to the block identified by `pcCertBoostedBlock`. An attacker who controls the `pcCertBoostedBlock` field can therefore make the node assign extra weight to any block of their choosing, causing it to prefer a fork that would otherwise lose chain selection.

The `PerasCert` data type contains only a round number and a block point — both fully attacker-controlled fields with no cryptographic binding: [4](#0-3) 

### Impact Explanation

**Impact class:** Critical — bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain-selection manipulation.

An unprivileged peer can cause an honest node to assign Peras weight boosts to arbitrary blocks. Because Peras weight is used to prefer one chain fragment over another during chain selection, the attacker can steer the node away from the canonical chain toward an adversarial fork. This breaks the chain-selection security guarantee that Peras is designed to strengthen, and constitutes acceptance of invalid consensus objects (forged certificates) without any cryptographic authorization.

### Likelihood Explanation

The Peras object-diffusion mini-protocol is reachable by any connected peer without authentication. The stub is the only instance in the codebase and is explicitly wired into the production `ChainDB`-backed writer. Any peer that sends a well-formed CBOR-encoded `PerasCert` message (two fields: a round number and a block point) will have it accepted. No key material, stake, or special privilege is required.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS/committee signature over the certificate's `(electionId, candidate)` pair, using the committee's public keys for the claimed round.
2. That the claimed voters constitute a quorum of the committee for that round.
3. That `pcCertBoostedBlock` refers to a block that actually exists on a known chain and is within the valid boosting window for the round.
4. That the round number is within the acceptable range (not replayed from a past round, not from the far future).

Until the real implementation is available, the stub should at minimum reject all inbound certificates (return `Left PerasValidationErr`) rather than accept them all, so that the attack surface is closed while the feature is incomplete.

### Proof of Concept

1. Connect to a Cardano node (private testnet or any node with Peras object diffusion enabled) as an unprivileged peer via the Peras certificate object-diffusion mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversarial fork block>`.
3. Send the certificate in a batch via `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` unconditionally.
5. The certificate is stored in the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. On the next chain-selection cycle, the boosted block receives extra Peras weight, causing the node to prefer the attacker's fork over the honest chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
