### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate Without Cryptographic Verification, Enabling Unauthorized Chain Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the codebase provides a `validatePerasCert` implementation that unconditionally returns `Right` for every certificate it receives, performing no actual validation whatsoever. An unprivileged peer can submit arbitrary Peras certificates via the object-diffusion miniprotocol; each will be accepted, stored in the `PerasCertDB`, and applied as a chain-weight boost during chain selection — allowing the peer to steer an honest node toward a non-canonical chain without holding legitimate quorum.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must be passed before a certificate is stored and used for chain-weight boosts. The only instance in the codebase is the blanket default:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function ignores every field of `cert` and returns `Right` unconditionally, assigning the full configured `perasWeight` boost to whatever certificate was supplied.

This return value flows directly into `processCerts`, the inbound handler for the Peras certificate diffusion miniprotocol:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter ...
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate a peer sends passes the `([], validatedCerts)` branch and is handed to `addCert`, which stores it in the `PerasCertDB`.

Chain selection then reads the stored certificates via `getPerasWeightSnapshot` and uses them to compute `weights` that directly influence which candidate chain is preferred:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [3](#0-2) 

The `weights` are then passed into `constructPreferableCandidates` and `compareChainDiffs`, so a certificate for block `B` causes `B`'s chain to be ranked higher than it would otherwise be.

**Analog to the original report.** The original bug describes a postman who supplies just enough gas for the top-level call to succeed while sub-calls fail silently, yet still collects the delivery fee. Here, `validatePerasCert` is the "top-level call" — it always succeeds (returns `Right`) — while the actual sub-checks (BLS aggregate signature verification, committee eligibility, round-number consistency, quorum threshold) are silently absent. The peer "collects the fee" in the form of a chain-weight boost applied to a block of their choosing, without having assembled a legitimate quorum.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point and any round number, send it over the Peras certificate diffusion miniprotocol, and have it accepted as a `ValidatedPerasCert` with full `perasWeight` boost. By targeting a block on a minority fork, the attacker can make an honest node's chain-selection logic rank that fork above the canonical chain, causing the node to switch to a non-canonical chain. This satisfies the **Critical** impact class: "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance," and the **High** class: "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."

---

### Likelihood Explanation

The Peras certificate diffusion miniprotocol is implemented in production code and is wired into the running node's networking stack. The `BlockSupportsPeras` blanket instance is the only instance; no era-specific override exists. Any peer that can open a connection to the node can send certificates. The only mitigating factor is that Peras is still being rolled out, so the weight boost may be zero if `perasWeight` is configured to zero in current deployments. Once Peras is live with a non-zero weight, the attack is immediately exploitable by any peer.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:
1. Verifies the aggregate BLS (or equivalent) signature over the certificate's round number and boosted-block point against the claimed committee members.
2. Checks that the signers form a valid quorum under the current committee selection for the stated round.
3. Verifies the round number is within an acceptable window relative to the current chain tip.

Until a real implementation is available, the node should refuse to process inbound certificates entirely (e.g., return `Left PerasValidationErr` unconditionally) rather than accept them all.

---

### Proof of Concept

1. Connect to a node with Peras diffusion enabled.
2. Construct a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a minority-fork block>`.
3. Send it via the Peras certificate object-diffusion miniprotocol.
4. `processCerts` calls `validatePerasCert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
5. The certificate is stored in `PerasCertDB`.
6. On the next chain-selection run, `getPerasWeightSnapshot` returns a non-zero weight for the minority-fork block.
7. `compareChainDiffs` ranks the minority fork above the canonical chain; the node switches. [4](#0-3) [5](#0-4) [6](#0-5)

  now <- systemTimeCurrent systemTime
