Audit Report

## Title
Fee-on-Transfer Token Escrow Under-Collateralization in `initTransfer` - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`OmniBridge.initTransfer` emits the caller-supplied `amount` in the `InitTransfer` event without comparing the contract's actual token balance before and after `safeTransferFrom`. For fee-on-transfer ERC20 tokens, the bridge escrow receives fewer tokens than `amount`, but the NEAR side finalizes the full `amount`, permanently under-collateralizing the EVM escrow and eventually causing `finTransfer` to revert for legitimate users.

## Finding Description
In `initTransfer` (lines 406–411), for tokens that are neither bridge tokens nor custom-minter tokens, the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

No balance snapshot is taken before or after this call. Immediately after, the function emits (lines 427–436):

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // always caller-supplied, never the actual received delta
    fee,
    nativeFee,
    recipient,
    message
);
```

For a fee-on-transfer token, `address(this)` receives `amount - transfer_fee`, but the event records `amount`. The NEAR prover reads this event as the authoritative proof of locked value and finalizes a release of `amount` tokens to the recipient. There is no token whitelist or registration gate in `initTransfer` that would prevent a fee-on-transfer token from reaching the `else` branch; any ERC20 token not mapped in `customMinters` or `isBridgeToken` falls through to this path.

When bridging back, `finTransfer` (lines 351–354) executes:

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount   // the full original amount, not the reduced escrowed amount
);
```

The escrow holds less than `payload.amount`, so this call will eventually revert once the accumulated deficit exceeds the remaining balance, permanently freezing legitimate users' funds.

The same pattern exists in `starknet/src/omni_bridge.cairo` (lines 304–306), where `transfer_from` is called with the caller-supplied `amount` and the `InitTransfer` event is emitted with the same `amount` (lines 322–323) without a balance delta check.

## Impact Explanation
This is a concrete instance of **escrow mis-accounting and permanent freezing of bridged funds**, both of which are explicitly listed critical impacts. Each `initTransfer` call with a fee-on-transfer token creates a deficit equal to the transfer fee. The deficit accumulates across calls. When the escrow balance falls below the sum of outstanding NEAR-side claims, `finTransfer` reverts for honest users, permanently freezing their funds. Additionally, prior to insolvency, the attacker (or any user of such a token) receives more value on NEAR than was locked on EVM, constituting direct theft of value from the escrow pool.

## Likelihood Explanation
`initTransfer` is a fully public, permissionless function. No admin action, privileged role, or prior registration is required to call it with an arbitrary ERC20 token. Fee-on-transfer tokens (tokens with built-in transfer taxes) are common in DeFi. Any token holder can trigger this path by calling `initTransfer` with such a token that is not already mapped as a bridge token or custom minter. The exploit is repeatable with no cooldown or rate limit.

## Recommendation
Record the contract's token balance before and after `safeTransferFrom` and use the delta as the canonical locked amount in both the emitted event and any internal accounting:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint128 received = uint128(IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore);
// replace `amount` with `received` in initTransferExtension call and InitTransfer emit
```

Apply the equivalent balance-delta pattern to the Starknet `init_transfer` function in `starknet/src/omni_bridge.cairo`.

## Proof of Concept
1. Deploy an ERC20 token with a 1% transfer fee (fee-on-transfer).
2. Do **not** register it as a bridge token or custom minter (it will fall into the `else` branch automatically).
3. Call `initTransfer(feeToken, 1000, 0, 0, "attacker.near", "")`.
4. The bridge receives 990 tokens; the `InitTransfer` event records `amount = 1000`.
5. The NEAR prover reads the event; NEAR bridge mints/releases 1000 tokens to `attacker.near`.
6. Attacker gained 10 tokens of unbacked value on NEAR.
7. Repeat N times; EVM escrow deficit grows to `N × 10`.
8. A legitimate user who bridged 990 real tokens and attempts `finTransfer` for 990 will succeed early, but once the cumulative deficit exceeds the remaining escrow balance, subsequent `safeTransfer` calls revert — those users' funds are permanently frozen.

A local invariant/fuzz test can confirm this: deploy the bridge, deploy a fee-on-transfer ERC20, call `initTransfer` repeatedly, then assert `IERC20(token).balanceOf(bridge) >= sum_of_emitted_amounts` — this assertion will fail after the first call.
