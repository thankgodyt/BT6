### Title
Missing Deadline/Expiry Check in `sign_btc_transaction` Allows Anyone to Force-Sign Stale Pending Withdrawals — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is a public, payable function with no caller-ownership check and no deadline/expiry check against `max_btc_tx_pending_sec`. Any unprivileged NEAR account can call it for any pending withdrawal at any time. When a withdrawal's gas fee becomes stale (BTC fee market has moved), an attacker can force-sign the pending transaction, broadcasting it to Bitcoin with an outdated fee. The user cannot cancel while the withdrawal is in `PendingSign` state, and `cancel_withdraw` is restricted to `Role::DAO` or `Role::Operator`. The user's nBTC is locked until they perform a costly RBF or until the DAO/Operator intervenes.

---

### Finding Description

When a user initiates a withdrawal via `ft_transfer_call`, the bridge creates a `BTCPendingInfo` record in `PendingSign` state with a gas fee fixed at creation time (`create_time_sec` is recorded but never enforced as an expiry).

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` performs only two checks:

```rust
let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
btc_pending_info.assert_pending_sign();   // only checks stage, not time or caller
```

There is no check that:
- `env::predecessor_account_id() == btc_pending_info.account_id` (anyone can call it)
- `nano_to_sec(env::block_timestamp()) <= btc_pending_info.create_time_sec + max_btc_tx_pending_sec` (no expiry)

By contrast, `internal_cancel_withdraw` and `internal_cancel_active_utxo_management` both enforce the `max_btc_tx_pending_sec` guard:

```rust
require!(
    nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
        > self.internal_config().max_btc_tx_pending_sec,
    "Please wait user rbf"
);
```

This guard exists only in the cancel paths, not in the signing path. The `max_btc_tx_pending_sec` field is referenced in exactly two production source files — `rbf/cancel_withdraw.rs` and `rbf/cancel_active_utxo_management.rs` — and never in `api/chain_signatures.rs`.

Additionally, `cancel_withdraw` is gated behind `#[access_control_any(roles(Role::DAO, Role::Operator))]`, so the user cannot self-rescue; they are entirely dependent on privileged operators.

---

### Impact Explanation

**Medium — Attacker-triggered temporary locking of bridged funds.**

1. Alice initiates a withdrawal with `gas_fee = 10,000 sats`. Her nBTC is transferred to the bridge and locked.
2. The BTC fee market spikes. Alice wants to cancel, but `cancel_withdraw` requires `PendingVerify` state — she cannot cancel while in `PendingSign`.
3. An attacker calls `sign_btc_transaction(alice_pending_id, 0, 0)` with the required NEAR deposit. The MPC signs the PSBT with the stale 10,000-sat fee and the signed transaction is broadcast to Bitcoin.
4. The transaction does not confirm (fee too low). Alice's nBTC is now locked in `PendingVerify` state.
5. Alice can attempt a user-RBF (`withdraw_rbf`) to increase the fee, but this requires additional NEAR gas and a new MPC signing round. If she cannot or does not do so, she must wait for `max_btc_tx_pending_sec` (default 24 hours) before the DAO/Operator can call `cancel_withdraw` to return her nBTC.

The user's bridged funds are temporarily locked and require either a costly RBF or privileged operator intervention to recover.

---

### Likelihood Explanation

**Medium.** `sign_btc_transaction` is a fully public, permissionless function. Any NEAR account can call it for any `btc_pending_sign_id` by attaching the required NEAR deposit for the MPC signing fee. No special role, leaked key, or privileged access is needed. The attack is economically bounded by the MPC signing cost but is otherwise trivially executable.

---

### Recommendation

1. **Add a caller-ownership check** in `sign_btc_transaction` so only the withdrawal owner (or a whitelisted relayer role) can trigger signing:

```rust
require!(
    env::predecessor_account_id() == btc_pending_info.account_id
        || self.acl_has_role(Role::Relayer.into(), env::predecessor_account_id()),
    "Not authorized to sign this transaction"
);
```

2. **Add a deadline/expiry check** in `sign_btc_transaction` mirroring the guard already present in the cancel paths:

```rust
require!(
    nano_to_sec(env::block_timestamp())
        <= btc_pending_info.create_time_sec + self.internal_config().max_btc_tx_pending_sec,
    "Pending transaction has expired"
);
```

3. **Allow users to cancel their own `PendingSign` withdrawals** without waiting for the DAO, so they are not dependent on privileged operators when conditions change.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
