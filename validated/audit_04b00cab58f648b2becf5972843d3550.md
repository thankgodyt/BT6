### Title
Peras Quorum Check Unit/Scale Mismatch Enables Certificate Acceptance Bypass - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The `stakeAboveThreshold` function compares `PerasVoteStake` directly against `PerasQuorumStakeThreshold` without enforcing unit consistency. An explicit TODO comment in the production source acknowledges that `PerasVoteStake` may be in absolute ledger units (lovelace) while the quorum threshold is a relative fraction in `[0,1]`. If the units are mismatched, the comparison always evaluates to `True` for any non-trivial stake, allowing any Peras certificate to pass the quorum check regardless of actual committee participation.

### Finding Description
`stakeAboveThreshold` performs a bare `Rational` comparison:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake         = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin  = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
``` [1](#0-0) 

The immediately preceding NOTE comment states:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)." [2](#0-1) 

The TODO comment on `stakeAboveThreshold` itself says:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The fix described in the TODO has not been applied. `stakeAboveThreshold` is called in the production aggregation path: [4](#0-3) 

The quorum threshold stored in `PerasParams` is a `Rational` in `[0,1]` (e.g., `0.75` for 75%): [5](#0-4) 

If `PerasVoteStake` is accumulated as absolute lovelace (e.g., `1_000_000_000_000`) and the threshold is `0.75`, the comparison `1_000_000_000_000 >= 0.75 + margin` is trivially `True`. This is the exact same class of bug as the external report: a value stored in one scale (absolute lovelace) is used in arithmetic that expects a different scale (normalized fraction), producing a permanently wrong result.

### Impact Explanation
If `PerasVoteStake` is absolute and the threshold is relative, `stakeAboveThreshold` returns `True` for every certificate regardless of actual quorum. Any Peras certificate — even one signed by a single committee member with negligible stake — passes the quorum check. This constitutes a **bypass of Peras voting/certificate checks**: an unprivileged peer can submit a certificate with far fewer votes than required, and the node will accept it, apply the associated chain-weight boost, and potentially prefer a less-secure chain. This falls squarely under the "Critical — bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" impact class.

### Likelihood Explanation
The NOTE explicitly states there is no agreed-upon normalization procedure. The TODO states the normalization has not been applied. `stakeAboveThreshold` is called in production `Aggregation.hs`. Any node receiving a Peras certificate over the network will invoke this path. An adversary who is a committee member (selected by stake) can submit a certificate with only their own vote; if the scale mismatch is present, it will be accepted.

**Caveat**: I was unable to read `Aggregation.hs` in full detail to confirm whether the caller normalizes `PerasVoteStake` before the call. If the caller does normalize, the bug is latent rather than active. The TODO and NOTE together strongly suggest normalization is not yet enforced at the call site.

### Recommendation
Either:
1. Normalize `PerasVoteStake` to a fraction of total committee stake before passing it to `stakeAboveThreshold`, or
2. Refactor `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, making the unit contract impossible to violate at call sites.

Add a type-level distinction (e.g., `newtype NormalizedPerasVoteStake`) to prevent future callers from accidentally passing absolute stake.

### Proof of Concept
Suppose total committee stake is `10^12` lovelace, quorum threshold is `0.75`, and an adversary holds `10^9` lovelace (0.1% of stake). If `PerasVoteStake` is accumulated as absolute lovelace:

```
voterStake  = 10^9          -- absolute lovelace
threshold   = 0.75          -- relative fraction
safetyMargin = 0.05

stakeAboveThreshold: 10^9 >= 0.75 + 0.05 = 0.80  →  True
```

The adversary's single-voter certificate passes the quorum check, the block receives a Peras weight boost, and the node may prefer the adversary's chain over the honest chain — a chain-selection safety failure triggered by a crafted certificate from an unprivileged peer.
