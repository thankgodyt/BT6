### Title
Publicly Reachable `unwrap()` Panic in `Transaction::output()` via `request_refund` — (`contracts/satoshi-bridge/src/zcash_utils/transaction.rs`)

### Summary

`Transaction::output()` unconditionally calls `.unwrap()` on `transparent_bundle()`. Any caller can submit a valid Zcash V5 transaction that has no transparent bundle (e.g., a shielded-to-shielded Orchard-only transfer) as `tx_bytes` in `request_refund`, causing a panic before any state is written. The panic is reachable from a public, unprivileged entrypoint.

### Finding Description

`Transaction::output()` is implemented as:

```rust
pub fn output(&self) -> Vec<TxOut> {
    let outputs = self.inner_tx.transparent_bundle().unwrap().vout.clone();
    ...
}
``` [1](#0-0) 

`transparent_bundle()` returns `Option<&Bundle<...>>`. For a valid Zcash V5 transaction that carries only an Orchard bundle and no transparent inputs/outputs, this returns `None`, and `.unwrap()` panics.

This is called unconditionally in `internal_request_refund`:

```rust
let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
``` [2](#0-1) 

And again in `request_refund_callback`:

```rust
let output = &transaction.output()[vout];
``` [3](#0-2) 

The public entrypoint is `request_refund`, which sits in a `#[trusted_relayer]` impl block but does **not** carry its own `#[trusted_relayer]` attribute on the function itself: [4](#0-3) 

Test evidence confirms this: non-relayer accounts ("alice", "bob") call `request_refund` successfully in multiple integration tests, and failures are rejected with domain-specific errors (e.g., `"refund_address does not match"`, `"Refund request already exists"`), never with a relayer-whitelist error. [5](#0-4) 

`Transaction::decode()` accepts any valid Zcash V5 transaction regardless of bundle composition: [6](#0-5) 

So a well-formed Orchard-only transaction passes `decode()` and then panics at `output()`.

### Impact Explanation

The panic aborts the NEAR receipt before any state is written. In NEAR, a panicking `#[payable]` function returns the attached deposit to the caller — so the storage deposit is **not** permanently lost (the question's claim on this point is incorrect). The panic also does not affect other users' refund requests or any bridge state. There is no unauthorized minting, fund theft, or permanent state corruption.

The real impact is: any account can cause individual `request_refund` calls to abort by supplying a shielded-only Zcash transaction. This is a publicly reachable panic in production bridge code with no direct fund loss.

### Likelihood Explanation

Constructing a valid Zcash V5 Orchard-only transaction is straightforward using standard Zcash libraries. No privileged access, leaked key, or third-party compromise is required. The attacker only needs to attach the required storage deposit (which is returned on panic), making repeated attempts free.

### Recommendation

Replace the bare `.unwrap()` with an explicit error path:

```rust
pub fn output(&self) -> Vec<TxOut> {
    let bundle = self.inner_tx.transparent_bundle()
        .unwrap_or_else(|| near_sdk::env::panic_str(
            "ERR_NO_TRANSPARENT_BUNDLE: transaction has no transparent outputs"
        ));
    bundle.vout.clone().into_iter().map(...).collect()
}
```

This converts the opaque panic into a clear, recoverable error message and prevents the DoS vector.

### Proof of Concept

1. Construct a minimal Zcash V5 transaction with only an Orchard bundle and no transparent bundle (using `zcash_primitives::transaction::TransactionData::from_parts` with `transparent_bundle = None` and a non-`None` Orchard bundle).
2. Serialize it with `tx.write(...)`.
3. Call `request_refund` on the bridge contract with these bytes as `tx_bytes`, any `vout`, and a valid-looking `proof` struct.
4. The call reaches `internal_request_refund` → `WrappedTransaction::decode` succeeds → `transaction.output()` calls `transparent_bundle().unwrap()` on `None` → NEAR receipt panics.
5. Observe the receipt aborts; the attached deposit is returned; no state is written.
