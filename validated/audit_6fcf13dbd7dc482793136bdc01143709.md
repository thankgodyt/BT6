Looking at the exact production code path described in the question.

### Title
Silent Discard of `post_actions` When `safe_deposit` Is Also Set in `DepositMsg` — (`contracts/satoshi-bridge/src/deposit_msg.rs` / `btc_light_client/deposit.rs`)

---

### Summary

`internal_safe_verify_deposit_entry` does not enforce the documented invariant that `post_actions` must be `None` when `safe_deposit` is present. Because `get_deposit_path` serializes the full `DepositMsg` (including `post_actions`), a depositor who sets both fields gets a unique deposit address that encodes `post_actions`, but those actions are silently discarded at execution time — the address and the execution path diverge.

---

### Finding Description

**Documented invariant, not enforced at runtime.**

The `DepositMsg` struct comment states:

> "If this field [safe_deposit] is present, the legacy post_actions field must be None" [1](#0-0) 

There is no `require!` that enforces this in `internal_safe_verify_deposit_entry`.

**Path computation includes `post_actions`.**

`get_deposit_path` serializes the entire `DepositMsg` to JSON and SHA-256 hashes it. Because `post_actions` uses `#[serde(skip_serializing_if = "Option::is_none")]`, a `DepositMsg` with `post_actions = Some([...])` serializes differently from one with `post_actions = None`, producing a different hash and therefore a different BTC deposit address. [2](#0-1) [3](#0-2) 

**Routing in `verify_deposit_v2` ignores `post_actions` in the safe path.**

`verify_deposit_v2` branches solely on `deposit_msg.safe_deposit.is_some()`: [4](#0-3) 

`internal_safe_verify_deposit_entry` then computes the path from the full `deposit_msg` (line 186, which includes `post_actions` if set), passes the path check, but then extracts only `safe_deposit_msg` and discards `post_actions` entirely: [5](#0-4) [6](#0-5) 

**Asymmetric guard.** `internal_verify_deposit_entry` explicitly rejects `safe_deposit` when present: [7](#0-6) 

No symmetric guard exists in `internal_safe_verify_deposit_entry` to reject `post_actions`.

---

### Impact Explanation

A user who:
1. Calls the public `get_user_deposit_address` with `{safe_deposit=Some(...), post_actions=Some([...])}`,
2. Sends BTC to the resulting address (which encodes both fields in its path),
3. Has the relayer submit `verify_deposit_v2` with the same `DepositMsg`,

will receive nBTC minted via the safe deposit path, but their `post_actions` (e.g., an `ft_transfer_call` into a DeFi protocol) will never execute. The deposit address uniquely encodes `post_actions` in its derivation path, but the execution path silently drops them. The user is not permanently stuck — they retain the minted nBTC and can manually execute the intended cross-contract calls — so there is no fund loss. The impact is a broken execution invariant: the deposit address no longer uniquely encodes the intended execution path.

---

### Likelihood Explanation

Requires a user to construct a `DepositMsg` violating the documented invariant (both fields set), and requires the trusted relayer to forward that exact `DepositMsg` to `verify_deposit_v2` without off-chain validation. The relayer is role-gated (`#[trusted_relayer]`), so the user cannot trigger this directly. If the relayer validates `deposit_msg` before submission, the path is unreachable in practice. If the relayer faithfully forwards whatever `deposit_msg` the user provided (e.g., by reading it from the BTC OP_RETURN or an off-chain registry), the path is reachable. Likelihood is low but non-zero.

---

### Recommendation

Add a symmetric guard at the top of `internal_safe_verify_deposit_entry`, mirroring the guard in `internal_verify_deposit_entry`:

```rust
require!(
    deposit_msg.post_actions.is_none(),
    "post_actions not supported in safe_verify_deposit"
);
```

This makes the contract enforce the documented invariant at runtime rather than relying on off-chain relayer validation.

---

### Proof of Concept

```
path_A = get_deposit_path(DepositMsg { safe_deposit: Some(...), post_actions: None, ... })
path_B = get_deposit_path(DepositMsg { safe_deposit: Some(...), post_actions: Some([...]), ... })
assert path_A != path_B   // different BTC deposit addresses

// User sends BTC to address(path_B)
// Relayer calls verify_deposit_v2 with the same DepositMsg (both fields set)
// Contract: safe_deposit.is_some() → routes to internal_safe_verify_deposit_entry
// internal_safe_verify_deposit_entry: path check passes (BTC is at address(path_B))
// post_actions silently dropped; only safe_deposit_msg used
// Result: nBTC minted, post_actions never executed
```

No privileged bypass is needed beyond the relayer faithfully forwarding the user-supplied `DepositMsg`.
