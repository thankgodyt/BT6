Audit Report

## Title
Missing Pre-Validation of Normalized Transfer Amount in `init_transfer` Permanently Locks User Tokens - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts and locks user tokens without verifying that `normalize_amount(amount - fee) > 0`. When the net amount is below the decimal scaling factor, `sign_transfer` always panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` before the MPC call is made. Because no user-accessible cancel or refund path exists for pending transfers, the locked tokens are permanently frozen in the bridge contract.

## Finding Description
`normalize_amount` performs floor division, truncating any sub-unit remainder: [1](#0-0) 

`init_transfer` stores the `TransferMessage` in `pending_transfers` with only a `fee < amount` check — no check that `normalize_amount(amount - fee) > 0`: [2](#0-1) 

Later, `sign_transfer` (callable only by a trusted relayer) computes the normalized amount and enforces it is non-zero: [3](#0-2) 

If the normalized amount is 0, `sign_transfer` panics **before** the MPC signing call at L508 is ever made. Because `sign_transfer_callback` is only invoked as a callback to the MPC call, it is never reached, and `remove_transfer_message` is never called: [4](#0-3) 

A search of the codebase confirms there is no `cancel_transfer` or user-accessible function that removes a pending transfer and refunds the sender. The `remove_transfer_message` call sites are all gated behind successful MPC signing or admin-level operations. The code comment at L2781–2783 acknowledges dust locking for remainders but does not address the case where the entire normalized amount is zero: [5](#0-4) 

## Impact Explanation
**Permanent freezing of bridged funds** — a concrete Critical impact in the allowed scope. Any user whose `amount - fee` is less than the decimal scaling factor (`10^(origin_decimals - decimals)`) will have their tokens locked in the bridge with no recovery path. For a standard NEAR→EVM pairing (`origin_decimals = 24`, `decimals = 18`), the scaling factor is `10^6`, meaning any net transfer below 1,000,000 base units triggers the lock. The tokens cannot be recovered because no cancel/refund mechanism exists for pending transfers.

## Likelihood Explanation
Any unprivileged user can trigger this via `ft_transfer_call` on any registered token. No special role or access is required. Users unfamiliar with decimal normalization mechanics (e.g., setting a fee close to their transfer amount, or sending a small test amount) will encounter this accidentally. The condition is repeatable and affects any token pair where `origin_decimals > decimals`.

## Recommendation
In `init_transfer`, before accepting tokens (i.e., before storing the `TransferMessage`), add a pre-validation check:

```rust
if let Some(token_address) = self.get_token_address(destination_chain, &token_id) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        require!(
            Self::normalize_amount(
                amount.0.saturating_sub(init_transfer_msg.fee.0),
                decimals
            ) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

If the check fails, `ft_on_transfer` must return the full `amount` so the token contract refunds the user before any state is mutated.

## Proof of Concept
1. Token `token.near` is registered with `origin_decimals = 24`, `decimals = 18` (scaling factor = `10^6`).
2. User calls `ft_transfer_call` on `token.near` with `amount = 500_000`, `fee = 0`.
3. Bridge's `ft_on_transfer` calls `init_transfer`; the only guard (`fee < amount`, i.e., `0 < 500_000`) passes. The `TransferMessage` is stored in `pending_transfers` and `U128(0)` is returned — bridge retains all 500,000 tokens.
4. Trusted relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(500_000, Decimals { origin_decimals: 24, decimals: 18 }) = 500_000 / 1_000_000 = 0`.
6. `require!(0 > 0, ERR_INVALID_AMOUNT_TO_TRANSFER)` panics. The MPC call at L508 is never made.
7. `sign_transfer_callback` is never invoked; `remove_transfer_message` is never called.
8. The `TransferMessage` remains in `pending_transfers` indefinitely. The user's 500,000 tokens are permanently locked with no recovery path. [6](#0-5)
