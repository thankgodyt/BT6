### Title
Peras Certificate Validation Uses Hardcoded Stub Parameters and Performs No Cryptographic Checks, Enabling Unauthorized Chain Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` — performing zero cryptographic or semantic checks. The inbound certificate handler in the object-diffusion mini-protocol compounds this by passing a hardcoded default parameter bundle (`mkPerasParams`) instead of ledger-derived Peras configuration. Any unprivileged peer can therefore inject an arbitrary `PerasCert` (any round, any boosted block) that passes "validation", is stored in the `PerasCertDB`, and triggers chain selection with fabricated weight, potentially causing the node to switch to a non-canonical fork.

---

### Finding Description

**Root cause 1 — stub `validatePerasCert` always succeeds:**

The universal `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No BLS aggregate-signature verification, no committee-membership check, no quorum-stake check, no round-validity check, no VRF eligibility proof check — the function unconditionally wraps any peer-supplied `PerasCert` in a `ValidatedPerasCert`. [1](#0-0) 

**Root cause 2 — hardcoded `mkPerasParams` used as the "config" for validation:**

Both production pool-writer constructors pass the hardcoded default `mkPerasParams` to `validatePerasCert` instead of any ledger-derived or chain-specific Peras configuration:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

`mkPerasParams` is a compile-time constant with no connection to the actual ledger state or on-chain governance parameters. [4](#0-3) 

**Attacker-controlled entry path:**

The `processCerts` function is the inbound handler for `PerasCert` objects received from peers via the object-diffusion mini-protocol. It calls `validateCert` (bound to `validatePerasCert mkPerasParams`) on each received certificate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [5](#0-4) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted.

**Chain selection consequence:**

Once accepted, the certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. The chain-selection loop then looks up the boosted block in the `VolatileDB` and calls `chainSelectionForBlock` for it, potentially switching the node's selection to a fork that now appears heavier due to the fabricated boost. [6](#0-5) 

The `PerasWeightSnapshot` used in `preferAnchoredCandidate` during chain comparison is derived directly from the `PerasCertDB`, which now contains the attacker-injected certificate. [7](#0-6) 

The `WeightedSelectView` comparison adds `wsvWeightBoost` (from the fake certificate) to `wsvBlockNo`, so a shorter fork with a fabricated boost can defeat the honest longer chain. [8](#0-7) 

---

### Impact Explanation

**Impact: High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

An unprivileged peer connected via the object-diffusion mini-protocol can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block currently in the target node's `VolatileDB`. The certificate bypasses all validation, is stored in the `PerasCertDB`, and causes chain selection to re-evaluate the boosted block's fork with an inflated weight. If the fabricated `PerasWeight` (drawn from the hardcoded `mkPerasParams.perasWeight = 15`) is sufficient to tip the comparison, the node switches to the attacker-chosen fork. The attacker can repeat this for successive rounds to persistently steer the node's selection away from the canonical chain.

---

### Likelihood Explanation

**Likelihood: High.** The object-diffusion mini-protocol is reachable by any peer without authentication. The `PerasCert` wire format is minimal (round number + block point), trivially constructable. The only guard is a duplicate-round check (`Set.member roundNo certIds`), which is bypassed by using a fresh round number. No stake, no key material, and no cryptographic proof is required from the attacker.

---

### Recommendation

1. **Implement real `validatePerasCert`**: Replace the stub with actual BLS aggregate-signature verification, committee-membership and VRF-eligibility proof checks, and quorum-stake threshold enforcement as specified in the Peras design (CIP-0140 / the Peras design report). The `PerasCert.V1` module already defines the concrete BLS types needed. [9](#0-8) 

2. **Thread ledger-derived Peras config**: Replace the hardcoded `mkPerasParams` argument in both `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` with the actual `PerasCfg blk` obtained from the current ledger state (analogous to how `LedgerView` is obtained via `ledgerViewForecastAt`). This is the direct analog of "use officially sponsored or verified price feeds."

3. **Add a `PerasCertDB.implAddCert` validation gate**: The `TODO` comment at line 167–168 of `PerasCertDB/Impl.hs` acknowledges missing validation logic; this should be resolved before Peras is enabled in production. [10](#0-9) 

---

### Proof of Concept

**Preconditions:** Peras is enabled on the target node; the attacker is a connected peer in the object-diffusion mini-protocol session.

**Steps:**

1. Attacker observes (or guesses) a block hash `H` present in the target node's `VolatileDB` on a minority fork at slot `S`.
2. Attacker constructs:
   ```
   PerasCert { pcCertRound = <any fresh round not yet in DB>, pcCertBoostedBlock = BlockPoint S H }
   ```
3. Attacker sends this certificate via the object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }`.
5. Certificate is stored in `PerasCertDB`; `addPerasCertAsync` is called.
6. `chainSelSync` retrieves the boosted block header from `VolatileDB` and calls `chainSelectionForBlock`.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the fork containing `H` as `blockNo(H) + 15`; if this exceeds the honest chain's `blockNo(tip)`, the node switches forks.
8. Attacker repeats with increasing round numbers to accumulate additional weight boosts, permanently biasing the node's chain selection toward the attacker-chosen fork.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
