### Title
Unvalidated `refund_address` Stored at Request Time Causes Deferred Panic in `build_refund_output`, Temporarily Sticking the UTXO — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

When `deposit_msg.refund_address` is `None`, `internal_request_refund` skips all address validation and stores the caller-supplied `refund_address` string verbatim. A chain-incorrect address (e.g., a Bitcoin testnet bech32 address submitted against a mainnet-configured bridge) passes every request-time check, is persisted in `RefundRequest`, and then causes `build_refund_output` to hard-panic via `.expect("Invalid refund address")` when `execute_refund` is later called. The NEAR transaction reverts, the stuck request remains in storage, and the duplicate-request guard blocks any new `request_refund` for the same UTXO until a privileged operator calls `reject_refund`.

---

### Finding Description

**Step 1 — Request phase: no address validation when `deposit_msg.refund_address` is `None`**

In `internal_request_refund`, the only address consistency check is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(msg_refund_address == &refund_address, ...);
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` the entire block is skipped. No format check, no chain check, no `Address::parse` call is performed on `refund_address` at this stage.

**Step 2 — Callback: address stored without validation**

`request_refund_callback` verifies the deposit script matches the `deposit_msg`-derived address, but stores `refund_address` as a raw string with no chain validation:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← stored verbatim, never parsed
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [2](#0-1) 

**Step 3 — Execution phase: hard panic**

`internal_execute_refund` calls `build_refund_output`, which calls `Address::parse` against the configured chain and panics on failure:

```rust
let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
    .expect("Invalid refund address");
``` [3](#0-2) 

`Address::parse` for `BitcoinMainnet` rejects a testnet bech32 address with "Bech32 HRP mismatch: expected 'bc', got 'tb'": [4](#0-3) 

**Step 4 — Stuck state**

The NEAR transaction reverts. `refund_requests` still holds the stuck entry. `verified_deposit_utxo` is NOT updated (the panic occurs before `finalize_refund_with_psbt`). A subsequent `request_refund` for the same UTXO is blocked by:

```rust
require!(!self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO");
``` [5](#0-4) 

---

### Impact Explanation

The UTXO is stuck in a state where `execute_refund` always panics and no new `request_refund` can be submitted. The stuck state is **not permanent**: a DAO/Operator can call `reject_refund` → `internal_reject_refund` to remove the entry, after which a valid request can be re-submitted. [6](#0-5) 

The design explicitly anticipates caller-supplied addresses being suspicious: `unsafe_refund_timelock_sec` (a longer timelock) is applied precisely to give the DAO/Operator time to review and reject such requests. [7](#0-6) 

Impact is therefore **Low**: a publicly reachable panic-driven stuck-state in a production bridge path, requiring operator intervention to resolve, with no direct theft of funds.

---

### Likelihood Explanation

The precondition — a deposit whose `deposit_msg.refund_address` is `None` — is a supported and documented usage (the `refund_address` parameter to `request_refund` was introduced precisely for this case). Any unprivileged caller who can observe the original `deposit_msg` (e.g., from the `LogDepositAddress` event) and obtain a valid inclusion proof can trigger this. Likelihood is **Low-to-Medium** given the required knowledge of the target deposit's `deposit_msg`.

---

### Recommendation

Validate `refund_address` against the configured chain at request time, inside `internal_request_refund` (before the light-client promise is dispatched), so an invalid address is rejected immediately with a clear error rather than deferred to a panic at execution time:

```rust
// After the deposit_msg consistency check:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This eliminates the deferred panic and prevents the stuck-request state entirely.

---

### Proof of Concept

1. Configure bridge for `BitcoinMainnet`.
2. Alice deposits with `deposit_msg = { refund_address: None, ... }`.
3. Attacker (or Alice) calls `request_refund(deposit_msg, refund_address="tb1pt34385rvqtyuz6muh9hr5ed4fy0cx89zz0faxm6dhku0vqp2pxxs0ymh7y", ...)` with a valid inclusion proof.
4. `request_refund_callback` succeeds; the testnet address is stored in `RefundRequest`.
5. After the timelock, anyone calls `execute_refund`.
6. `build_refund_output` panics: `"Invalid refund address: Bech32 HRP mismatch: expected 'bc', got 'tb'"`.
7. Transaction reverts; UTXO is stuck until DAO/Operator calls `reject_refund`. [8](#0-7)
