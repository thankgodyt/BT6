### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect a Victim's BTC Refund to an Attacker-Controlled Address — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` carries no caller-identity check. When a deposit's `deposit_msg.refund_address` field is `None`, any NEAR account can call `request_refund` for a victim's on-chain UTXO and supply an arbitrary attacker-controlled BTC address as `refund_address`. Because the first stored request wins (a duplicate is rejected), the attacker permanently redirects the refund before the legitimate user can act. After the `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund`, causing the MPC to sign a Bitcoin transaction that pays the attacker's address.

---

### Finding Description

**Entry point — `request_refund` (bridge.rs line 510):**

The public function carries only `#[payable]` and `#[pause]` attributes. The `#[trusted_relayer]` annotation appears on the surrounding `impl` block (line 480), but functions within that same block that are *actually* restricted to trusted relayers — `verify_refund_finalize` (line 602) and `remove_refund_pending_tx_id` (line 622) — carry the attribute again at the function level. `request_refund`, `reject_refund`, and `execute_refund` do not, confirming the impl-level annotation does not gate individual functions. Any NEAR account may call `request_refund`. [1](#0-0) 

**Missing caller authentication in `internal_request_refund` (refund.rs line 137):**

`internal_request_refund` never reads `env::predecessor_account_id()`. The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), this block is skipped entirely and any `refund_address` string is accepted. [2](#0-1) 

**First-writer-wins storage in `request_refund_callback` (refund.rs line 544):**

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

Once the attacker's request is stored, the legitimate user's subsequent call reverts here. The attacker's `refund_address` is now the only one on record. [3](#0-2) 

**`execute_refund` is also open to any caller (bridge.rs line 582):**

After `unsafe_refund_timelock_sec` elapses, anyone — including the attacker — can call `execute_refund`. `finalize_refund_with_psbt` builds the PSBT using `refund_request.refund_address` (the attacker's address) and submits it to the MPC for signing. [4](#0-3) [5](#0-4) 

---

### Impact Explanation

The attacker receives the victim's BTC deposit (minus the gas fee). This is a direct, permanent theft of user funds from the bridge. The `unsafe_refund_timelock_sec` window gives the DAO/Operator a chance to call `reject_refund`, but this is a reactive, off-chain monitoring dependency — not a protocol-level guarantee. If the DAO does not notice or act in time, the BTC is irreversibly sent to the attacker's address once the MPC signs and the transaction confirms on Bitcoin.

**Allowed impact matched:** *Critical — significant theft of user funds.*

---

### Likelihood Explanation

All information the attacker needs is publicly available:

1. The victim's BTC deposit transaction (and thus `tx_bytes`, `vout`, and the proof) is visible on the Bitcoin blockchain.
2. The `deposit_msg` is either embedded in the BTC transaction (OP_RETURN) or visible in any prior NEAR call to `get_user_deposit_address`.
3. The attacker does not need to frontrun in the strict mempool sense — they can simply monitor Bitcoin for unfinalized deposits and submit `request_refund` before the legitimate user does, at any time before the UTXO is claimed.

The only friction is the NEAR storage deposit required by `request_refund` and the `unsafe_refund_timelock_sec` window during which the DAO can reject. Neither is a reliable security barrier.

---

### Recommendation

1. **Require caller to be `deposit_msg.recipient_id`** when `deposit_msg.refund_address` is `None`. Only the intended nBTC recipient should be able to nominate an arbitrary BTC refund address.
2. **Alternatively, require `deposit_msg.refund_address` to always be set** (make it non-optional) so the BTC destination is committed at deposit time and cannot be overridden by any caller.
3. If the open-caller design is intentional, at minimum enforce that `refund_address` is authenticated against `deposit_msg.recipient_id`'s registered BTC key or require a signed attestation.

---

### Proof of Concept

1. Victim sends BTC to a deposit address derived from `deposit_msg = { recipient_id: "victim.near", refund_address: None, ... }`.
2. The deposit is never finalized (relayer delay, stuck state, etc.).
3. Attacker observes the Bitcoin UTXO on-chain, reconstructs `deposit_msg` and the Merkle proof.
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   — `internal_request_refund` skips the `refund_address` check because `deposit_msg.refund_address` is `None`. [2](#0-1) 
5. `request_refund_callback` verifies the proof, confirms the output script matches the deposit address, and stores `RefundRequest { refund_address: "attacker_btc_address", ... }`. [6](#0-5) 
6. Victim's subsequent `request_refund` call reverts: `"Refund request already exists for this UTXO"`. [3](#0-2) 
7. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund`. The PSBT is built paying `"attacker_btc_address"`, MPC signs it, and BTC is sent to the attacker. [7](#0-6)
