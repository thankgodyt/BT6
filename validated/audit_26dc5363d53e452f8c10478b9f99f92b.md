### Title
Per-Account Pending Withdrawal Limit Bypassed via Multi-Account nBTC Transfer - (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary
The bridge enforces a per-account limit on concurrent pending sign transactions via `pending_tx_limits`. Because this limit is keyed on `sender_id` (the NEAR account calling `ft_transfer_call`), any user can bypass it by distributing nBTC across multiple fresh NEAR accounts and initiating a withdrawal from each. This allows an attacker to lock far more bridge UTXOs than the policy intends, exhausting the pool and temporarily blocking legitimate withdrawals.

### Finding Description
In `create_btc_pending_info` (`contracts/satoshi-bridge/src/api/token_receiver.rs`), the bridge checks the per-account pending limit before creating a withdrawal:

```rust
let max_pending = self.get_max_pending_sign_txs(&sender_id);
let account = self.internal_unwrap_or_create_mut_account(&sender_id);
require!(
    account.pending_sign_count() < max_pending,
    "Too many pending sign transactions"
);
``` [1](#0-0) 

`get_max_pending_sign_txs` returns the per-account limit, defaulting to **1** for any account not explicitly configured:

```rust
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)
}
``` [2](#0-1) 

The limit is only set by DAO via `set_pending_tx_limit` for specific accounts: [3](#0-2) 

When a pending withdrawal is created, the UTXOs specified in the `input` field are **removed from the bridge's available UTXO pool** and stored in the `BTCPendingInfo`: [4](#0-3) 

These UTXOs remain locked until the Bitcoin transaction is confirmed on-chain and `verify_withdraw` is called. A fresh NEAR account has zero pending sign transactions, so the `require!` check always passes for it.

**Attack path:**
1. Attacker holds nBTC.
2. Attacker creates N fresh NEAR accounts (cheap on NEAR — a few cents each).
3. Attacker transfers a withdrawal-sized amount of nBTC to each fresh account via `ft_transfer` on the nBTC contract.
4. Each fresh account calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message specifying distinct bridge UTXOs as `input`.
5. Each call passes the `pending_sign_count() < max_pending` check (count is 0, limit is 1) and locks the specified UTXOs.
6. The bridge's available UTXO pool is exhausted; legitimate users' withdrawal attempts panic with `"UTXO {} not exist"`.

The `sender_id` in `ft_on_transfer` is the account that called `ft_transfer_call`, not the original token holder, so there is no cross-account tracking: [5](#0-4) 

### Impact Explanation
The bridge's UTXO pool is a shared, finite resource. Exhausting it via many concurrent pending withdrawals (each from a distinct fresh account) temporarily prevents all other users from initiating withdrawals. This is a **bypass of bridge limits/policies and attacker-triggered temporary locking of bridged funds** (Medium). The locked UTXOs are eventually released when the attacker's Bitcoin transactions confirm, but the disruption window can span hours to days depending on Bitcoin mempool conditions and whether the attacker uses RBF to delay confirmation.

### Likelihood Explanation
NEAR account creation costs fractions of a cent. The attacker only needs enough nBTC to cover N minimum-withdrawal amounts. The bridge's UTXO count is bounded by its operational history, so a determined attacker with moderate nBTC holdings can exhaust it. No privileged access is required — only standard `ft_transfer` and `ft_transfer_call` calls available to any token holder.

### Recommendation
- Track pending sign counts globally or against a canonical identity (e.g., the BTC target address or a registered NEAR account) rather than purely per `sender_id`.
- Alternatively, enforce a global cap on total concurrent pending sign transactions across all accounts, independent of per-account limits.
- Consider requiring a minimum NEAR storage deposit per pending withdrawal to raise the cost of the multi-account attack.

### Proof of Concept
```
// Attacker setup: attacker holds 10 nBTC, bridge has 10 UTXOs
for i in 0..10:
    fresh_account = create_near_account(f"attacker-sybil-{i}.near")
    nbtc.ft_transfer(fresh_account, min_withdraw_amount)

// Each fresh account initiates a withdrawal locking one bridge UTXO
for i in 0..10:
    // pending_sign_count() == 0 for each fresh account → check passes
    nbtc.ft_transfer_call(
        receiver_id = bridge,
        amount = min_withdraw_amount,
        msg = Withdraw { input: [bridge_utxo[i]], ... },
        caller = fresh_account[i]
    )

// Bridge UTXO pool is now empty
// Legitimate user attempts withdrawal → panics: "UTXO {} not exist"
```

    pub fn set_pending_tx_limit(&mut self, account_id: AccountId, max_pending: Option<u32>) {
        assert_one_yocto();
        if let Some(max_pending) = max_pending {
            require!(max_pending >= 1, "Invalid max_pending value");
            self.data_mut()
                .pending_tx_limits
                .insert(account_id, max_pending);
        } else {
            let prev = self.data_mut().pending_tx_limits.remove(&account_id);
            require!(
                prev.is_some(),
                format!("Invalid account_id: {}", account_id)
            );
        }
    }

    pub fn remove_vutxo_by_psbt(&mut self, psbt: &PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let mut utxo_storage_keys = vec![];
        let vutxos = psbt
            .get_utxo_storage_keys()
            .into_iter()
            .map(|utxo_storage_key| {
                utxo_storage_keys.push(utxo_storage_key.clone());
                self.data_mut()
                    .utxos
                    .remove(&utxo_storage_key)
                    .unwrap_or_else(|| {
                        env::panic_str(&format!("UTXO {} not exist", utxo_storage_key))
                    })
            })
            .collect::<Vec<_>>();
        (utxo_storage_keys, vutxos)
    }
