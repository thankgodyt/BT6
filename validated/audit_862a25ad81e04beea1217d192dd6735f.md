### Title
Peras Certificate Verification Bypass Enables Unauthorized Chain-Selection Weight Injection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production catch-all `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally accepts every inbound `PerasCert` without performing any cryptographic, committee-membership, or quorum check. An unprivileged peer can send a crafted certificate naming any block in the volatile DB, inject an arbitrary weight boost into the live `PerasWeightSnapshot`, and trigger a chain-selection re-run that may cause the node to switch to a non-canonical fork.

---

### Finding Description

**Root cause — stub validation that always succeeds** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the only `BlockSupportsPeras` instance in the codebase; it is a catch-all over `StandardHash blk` and is therefore the instance used for every block type when Peras is enabled.

**Inbound path — any peer reaches this code**

When a peer sends a `PerasCert` via the object-diffusion mini-protocol, `processCerts` calls `validatePerasCert mkPerasParams` on it: [2](#0-1) 

Because `validatePerasCert` always returns `Right`, every certificate passes, is timestamped, and is forwarded to `ChainDB.addPerasCertAsync`.

**TOCTOU analog to the original vulnerability**

The original bug: `queue.reward` is zero at *provision* time (`updateEnclave`), then raised by the attacker before *distribution* (`failEnclave` reads the live value).

The analog here follows the same three-step pattern:

| Step | Original | Analog |
|---|---|---|
| **Provision** | `updateEnclave` called with zero reward | Block arrives; chain selection runs without any cert boost |
| **Manipulation** | `setAttestationQueueConfig` raises `queue.reward` | Attacker sends a fake `PerasCert` naming a block on a competing fork |
| **Distribution** | `failEnclave` reads the now-inflated live `queue.reward` | `chainSelSync` reads the updated live `PerasWeightSnapshot` and re-runs chain selection |

In `chainSelSync` for `ChainSelAddPerasCert`, the cert is first added to the `PerasCertDB` (updating the live weight snapshot), and then `chainSelectionForBlock` is called: [3](#0-2) 

Chain selection reads the weight snapshot from the live `PerasCertDB` at that moment: [4](#0-3) 

The `preferAnchoredCandidate` function then uses the injected boost when comparing the fork against the current chain: [5](#0-4) 

**What the attacker controls**

The `PerasCert` type lets the attacker freely choose the boosted block: [6](#0-5) 

The boost magnitude is fixed by the node's `perasWeight params` configuration, but the attacker picks the target. By naming a block on a fork that is slightly shorter than the current chain, and if `perasWeight params` exceeds the chain-length difference, the node will switch to the fork.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Send a `PerasCert` for any block in the volatile DB (arbitrary round number, arbitrary boosted-block point).
2. The certificate is accepted without any signature, committee-membership, or quorum verification.
3. The targeted block receives a weight boost of `perasWeight params` in the live `PerasWeightSnapshot`.
4. Chain selection re-runs; if the boosted fork's total weight now exceeds the current chain's weight, the node switches to the non-canonical fork.

This is a **bypass of Peras certificate checks** that enables unauthorized chain-selection weight manipulation, matching the "Critical — bypass of Peras voting or certificate checks enabling unauthorized certificate acceptance" impact class.

---

### Likelihood Explanation

**Medium.** Peras is not enabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"), which limits the current attack surface. However, the feature is under active development and the stub is in production source. Once Peras is enabled on any node, the attack requires only:

1. Connecting to the node as a peer via the object-diffusion mini-protocol (no special privileges).
2. Knowing the `Point` of a block on a competing fork in the volatile DB (observable from the network).
3. Sending a single crafted `PerasCert` message.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that verifies:

- Cryptographic signatures from committee members.
- Committee membership and eligibility for the claimed round.
- That the aggregate stake of signers meets the quorum threshold (`stakeAboveThreshold`).
- Round-number freshness (cert is not for a round already finalized or too far in the future).

Until real validation is in place, Peras should remain disabled in any deployment where the stub instance is the only implementation.

---

### Proof of Concept

1. Start a node with Peras enabled (`rnFeatureFlags` / `eraPerasRoundLength` set).
2. Connect as an unprivileged peer via the object-diffusion mini-protocol.
3. Observe a block hash `H` on a competing fork present in the node's volatile DB (e.g., via `getPerasWeightSnapshot` returning an empty snapshot for `H`).
4. Craft a `PerasCert { pcCertRound = <any valid round>, pcCertBoostedBlock = BlockPoint <slot> H }` and send it.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right` → cert forwarded to `addPerasCertAsync`.
6. `chainSelSync` processes `ChainSelAddPerasCert`: adds cert to `PerasCertDB`, reads updated `PerasWeightSnapshot` (now includes boost for `H`), calls `chainSelectionForBlock`.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the fork including the injected boost; if it exceeds the current chain's weight, the node switches to the non-canonical fork.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
