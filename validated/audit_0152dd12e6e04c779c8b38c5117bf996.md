### Title
EVM Bridge Escrow Mis-Accounting for Fee-on-Transfer Tokens in `initTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer()` emits the caller-supplied `amount` in the `InitTransfer` event without verifying the actual number of tokens received. For fee-on-transfer (deflationary) ERC20 tokens, the bridge escrow receives fewer tokens than `amount`, but the cross-chain message records `amount`. The NEAR bridge processes the event's `amount` verbatim, causing the destination chain to mint or unlock more tokens than the EVM bridge actually holds, permanently undercollateralizing the escrow.

---

### Finding Description

In `OmniBridge.sol`, the standard ERC20 branch of `initTransfer` performs:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-supplied value
);
``` [1](#0-0) 

Immediately after, without any balance-before/after check, the function emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,          // same caller-supplied value, not actual received amount
    fee,
    nativeFee,
    recipient,
    message
);
``` [2](#0-1) 

The `InitTransfer` event's `amount` field is the authoritative value consumed by the NEAR bridge. In `fin_transfer_callback`, the NEAR contract decodes the proven event and constructs a `TransferMessage` directly from `init_transfer.amount`:

```rust
let transfer_message = TransferMessage {
    amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
    ...
};
``` [3](#0-2) 

There is no mechanism on the NEAR side to independently verify that the EVM bridge actually received `amount` tokens — it trusts the event log entirely. For a fee-on-transfer token, the EVM bridge receives `amount - transfer_fee` but the cross-chain message authorizes release of `amount`.

---

### Impact Explanation

**Critical — Escrow mis-accounting / loss of bridged funds.**

Each `initTransfer` call with a fee-on-transfer token creates a deficit of `transfer_fee` tokens in the EVM bridge escrow. The destination chain mints or unlocks the full `amount`, but the EVM bridge only holds `amount - transfer_fee`. After repeated transfers, the EVM bridge's token reserves are insufficient to honor legitimate withdrawal requests from users bridging back. Honest users who bridged tokens in the normal way will be unable to withdraw their funds, constituting a direct loss of bridged assets.

The `BridgeTypes.InitTransfer` event definition confirms `amount` is a `uint128` field taken directly from the function parameter with no adjustment: [4](#0-3) 

---

### Likelihood Explanation

**Medium.** Any ERC20 token that (a) is not registered as a `isBridgeToken` and (b) is not assigned a `customMinters` entry — i.e., the standard escrow path — and (c) implements a transfer fee is exploitable. The attacker requires no special role or privilege; `initTransfer` is a public, unpaused entry point callable by any address. The attacker simply needs to use or deploy a fee-on-transfer ERC20 token that the bridge accepts for bridging. [5](#0-4) 

---

### Recommendation

Measure the actual received amount using a balance-before/after pattern, and use that measured value in the emitted event and all downstream accounting:

```solidity
} else {
    uint256 beforeBalance = IERC20(tokenAddress).balanceOf(address(this));
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
    uint128 actualReceived = uint128(
        IERC20(tokenAddress).balanceOf(address(this)) - beforeBalance
    );
    amount = actualReceived; // shadow with actual received
}
```

Then use `amount` (now the actual received value) in the `InitTransfer` event emission. This ensures the cross-chain message authorizes exactly what the bridge holds.

---

### Proof of Concept

1. Deploy or use an existing ERC20 token with a 1% transfer fee.
2. Call `OmniBridge.initTransfer(tokenAddress, 1000, 0, 0, "recipient.near", "")`.
3. The bridge receives 990 tokens (`safeTransferFrom` deducts 1% fee).
4. The emitted `InitTransfer` event records `amount = 1000`.
5. A relayer submits proof of this event to the NEAR bridge via `fin_transfer`.
6. `fin_transfer_callback` constructs a `TransferMessage` with `amount = 1000` and the MPC signs it.
7. The destination chain releases 1000 tokens to the recipient.
8. The EVM bridge escrow is short by 10 tokens.
9. Repeating this 100 times drains 1000 tokens from the bridge's reserves, making it unable to honor legitimate withdrawals of that token. [6](#0-5) [7](#0-6)
