Audit Report

## Title
Fee-on-Transfer Token Mis-Accounting in `initTransfer` Causes EVM Escrow Under-Collateralization - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.sol`'s `initTransfer` function transfers a caller-supplied `amount` from the sender via `safeTransferFrom` and immediately emits an `InitTransfer` event carrying that same nominal `amount`, without measuring the actual tokens received. For fee-on-transfer ERC20 tokens, the contract receives `amount - transfer_fee` while the event records `amount`. The NEAR bridge finalizes the full nominal `amount` on the destination chain, permanently over-issuing relative to the EVM escrow. The identical structural flaw exists in `starknet/src/omni_bridge.cairo`.

## Finding Description

In `initTransfer`, the `else` branch — reached for any ERC20 that is neither a bridge token nor a custom-minter token — executes:

```solidity
// OmniBridge.sol lines 406-412
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount
    );
}
```

No balance snapshot is taken before or after this call. Immediately after, the function emits:

```solidity
// OmniBridge.sol lines 427-436
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,   // nominal caller-supplied value, not actual received
    fee,
    nativeFee,
    recipient,
    message
);
```

For a fee-on-transfer token, the bridge receives `amount - token_fee` but the event records `amount`. The NEAR prover verifies this event and passes `amount` to `fin_transfer`, minting or unlocking the full nominal `amount` on NEAR. The EVM escrow is under-collateralized by `token_fee` per operation.

When any user later bridges tokens back from NEAR to EVM, `finTransfer` executes:

```solidity
// OmniBridge.sol lines 351-354
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
```

`payload.amount` is the full nominal amount signed by the NEAR bridge. If the EVM escrow holds less than this (due to accumulated deficits), `safeTransfer` reverts, permanently freezing the user's funds — they burned tokens on NEAR but receive nothing on EVM.

The identical pattern in `starknet/src/omni_bridge.cairo` lines 303–307 calls `transfer_from(caller, get_contract_address(), amount.into())` and then emits `amount` in the `InitTransfer` event at lines 316–330, with no actual-received-amount check.

## Impact Explanation

**Critical — escrow mis-accounting and permanent freezing of bridged funds.** Each `initTransfer` with a fee-on-transfer token inflates the NEAR-side supply relative to the EVM-side escrow. The deficit compounds across operations. Eventually, `finTransfer` calls on the EVM side revert because the bridge cannot satisfy `safeTransfer(recipient, payload.amount)`, permanently freezing funds for all users of that token. This matches the allowed impact class: "Balance manipulation, escrow mis-accounting... that changes user or protocol balances" and "permanent freezing of bridged funds."

## Likelihood Explanation

The `else` branch in `initTransfer` imposes no whitelist restriction — any ERC20 not in `isBridgeToken` or `customMinters` reaches this path. An unprivileged user needs only to call `initTransfer` with a fee-on-transfer token that is recognized on both the EVM and NEAR sides. Fee-on-transfer tokens are a well-established token class (e.g., STA, REFLECT, tokens with configurable tax mechanisms). No special role, privileged access, or victim mistake is required. The operation is repeatable, compounding the deficit with each call.

## Recommendation

Record the contract's token balance before and after `safeTransferFrom` and use the delta as the canonical bridged amount in the emitted event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// Cast actualReceived to uint128 with overflow check; use in event and downstream accounting
```

Apply the same fix to `starknet/src/omni_bridge.cairo`'s `init_transfer`. Alternatively, add an on-chain guard that reverts if `actualReceived != amount`, explicitly rejecting fee-on-transfer tokens.

## Proof of Concept

1. Deploy or use any ERC20 token with a 1% transfer fee that is recognized as a native token on the EVM OmniBridge (not in `isBridgeToken`, not in `customMinters`).
2. Call `OmniBridge.initTransfer(tokenAddress, 1000, 0, 0, "near:alice.near", "")` with `amount = 1000`.
3. The bridge receives `990` tokens (1% fee deducted by the token contract); the `InitTransfer` event records `amount = 1000`.
4. The NEAR prover verifies the event; NEAR `fin_transfer` mints `1000` tokens to `alice.near`.
5. Alice bridges `1000` tokens back from NEAR to EVM: NEAR burns `1000`, EVM `finTransfer` attempts `safeTransfer(alice_evm, 1000)`.
6. The EVM bridge holds only `990` → `safeTransfer` reverts → Alice's `1000` NEAR-side tokens are burned with no EVM-side release (permanent fund loss).
7. Repeating steps 2–4 multiple times compounds the deficit, eventually causing all subsequent `finTransfer` calls for this token to fail, freezing all users' bridged funds.

A local integration test can demonstrate this with a mock ERC20 that deducts a configurable fee in `transferFrom`, calling `initTransfer` and then `finTransfer` to observe the revert.
