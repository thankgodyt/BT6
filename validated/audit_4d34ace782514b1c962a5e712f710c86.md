### Title
Peras Certificate Validation Unconditionally Accepts Any Certificate Due to Degenerate Instance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a function that always returns `Right` (success) regardless of certificate content. This is the direct analog of the external report's "incorrect constant value" class: instead of a threshold set too permissively, the entire validation gate is hardwired to pass. Any peer that can deliver a crafted `PerasCert` to a node running with Peras enabled will have it unconditionally accepted, allowing unauthorized chain-weight boosts and chain-selection manipulation.

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all `BlockSupportsPeras` instance is defined for every `StandardHash blk`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function unconditionally constructs a `ValidatedPerasCert` and wraps it in `Right`, assigning the full configured `perasWeight` boost to every certificate without inspecting the certificate's round number, boosted block point, quorum proof, or any other field. No more-specific instance overrides this for production block types, so this degenerate path is the live code path for all blocks.

The `perasWeight` default is `PerasWeight 15` in `mkPerasParams`: [2](#0-1) 

`maxRollbackWeight` converts the security parameter `k` directly to a `PerasWeight`: [3](#0-2) 

Chain selection in `takeVolatileSuffix` uses total weight (block count + boost) against `maxRollbackWeight`: [4](#0-3) 

Because `validatePerasCert` never rejects, an adversary can inject certificates that boost arbitrary blocks, shifting the weight comparison in chain selection without possessing any legitimate stake, VRF key, or quorum of votes.

### Impact Explanation

This is a **Critical bypass of Peras certificate/vote checks**. An unprivileged peer can craft a `PerasCert` pointing at any block and deliver it via the Peras object-diffusion miniprotocol. The node will call `validatePerasCert`, receive `Right`, record the boost in its `PerasWeightSnapshot`, and subsequently prefer chains containing that block over chains that are longer by up to `perasWeight` blocks. With repeated injections an adversary can accumulate boosts sufficient to make an adversarial fork appear heavier than the honest chain, causing the node to permanently select the wrong chain — a consensus safety failure.

### Likelihood Explanation

Peras is implemented in production source files and wired into the ChainDB state machine (the `AddPerasCert` command path is exercised in the state-machine tests). Any deployment that enables Peras — including private testnets and future mainnet activation — exposes this path. The entry point is the Peras certificate diffusion miniprotocol, reachable by any connected peer without credentials.

### Recommendation

Replace the degenerate `validatePerasCert` stub with a real implementation that verifies: (1) the certificate's round number is within the accepted window, (2) the boosted block point exists and satisfies `perasBlockMinSlots`, (3) a valid quorum of signed votes backs the certificate, and (4) the certificate is not in a cooldown/ignoring period. Until a real implementation is ready, the function should return `Left PerasValidationErr` unconditionally so that no certificate is accepted rather than all certificates being accepted.

### Proof of Concept

1. Connect to a node with Peras enabled on a private testnet.
2. Craft a `ValidatedPerasCert` with `pcCertBoostedBlock` pointing at a block on an adversarial fork and `vpcCertBoost = PerasWeight (k-1)` (just below the rollback limit).
3. Deliver it via the Peras certificate diffusion channel.
4. The node calls `validatePerasCert`, which returns `Right` unconditionally.
5. The boost is recorded in `PerasWeightSnapshot`; `totalWeightOfFragment` now scores the adversarial fork higher than the honest chain by `k-1` weight units.
6. Chain selection switches to the adversarial fork, and the node cannot roll back because the total weight of the adversarial suffix now equals `k`.
