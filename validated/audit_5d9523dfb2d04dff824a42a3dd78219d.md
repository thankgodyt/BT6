### Title
Unconditional `validatePerasCert` Stub Allows Unprivileged Peer to Inject Forged Peras Certificates via ObjectDiffusion, Materially Weakening Chain Selection Authorization — (`Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (accepting every certificate without any cryptographic or semantic check). This stub is wired directly into the production ObjectDiffusion inbound handler. Any unprivileged peer connected via `NodeToNodeV_16` can send a `PerasCert blk` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB, and the node will store it and trigger chain selection with a `perasWeight = 15` boost for the adversarially chosen block.

---

### Finding Description

**Step 1 — The stub.**

The default `BlockSupportsPeras` instance at `SupportsPeras.hs:320` is explicitly marked as a temporary degenerate instance ("TODO: degenerate instance for all blks to get things to compile"). Its `validatePerasCert` implementation: [1](#0-0) 

unconditionally returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` for every input, regardless of the cert's `pcCertBoostedBlock`, voter bitmap, or any aggregate signature. The `PerasCert blk` data type for this instance has no signature field at all: [2](#0-1) 

**Step 2 — Production wiring.**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation function: [3](#0-2) 

This writer is wired directly into the `hPerasCertDiffusionClient` handler in the production `NodeToNode` handler setup: [4](#0-3) 

**Step 3 — `processCerts` accepts everything.**

`processCerts` calls `validateCert` on each inbound cert and, since the stub always returns `Right`, the `([], validatedCerts)` branch is always taken: [5](#0-4) 

Every cert is then passed to `ChainDB.addPerasCertAsync`.

**Step 4 — Chain selection is triggered.**

`chainSelSync` for `ChainSelAddPerasCert` stores the cert in the `PerasCertDB` and, if the boosted block is present in the VolatileDB, immediately triggers `chainSelectionForBlock` for that block: [6](#0-5) 

**Step 5 — The boost is applied.**

`chainSelectionForBlock` reads the `PerasWeightSnapshot` (which now includes the injected cert's boost) and uses it in `preferAnchoredCandidate` / `constructPreferableCandidates`: [7](#0-6) 

The boost weight is `perasWeight = 15` from `mkPerasParams`: [8](#0-7) 

**Note on `V1.hs`:** The `fromCompactRepr` function in `V1.hs` is used only for deserializing `PerasCertVoters` within the concrete BLS-based cert type, which is **not** the type used in the production path. The production path uses the default instance's `PerasCert blk` (no signature field). The attacker does not need to forge a BLS signature — they only need to send a valid CBOR-encoded `PerasCert blk` (a 2-element list: round number + block point). [9](#0-8) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert blk` with `pcCertBoostedBlock` pointing to any block in the VolatileDB. The node will store the cert and apply a weight-15 boost to that block during chain selection. If the adversarially boosted block is on a competing fork, the honest node may switch to that fork, materially weakening block authorization. This matches the **Medium** scope: a public miniprotocol flaw that materially weakens certificate authorization without relying on DoS.

---

### Likelihood Explanation

The ObjectDiffusion miniprotocol is enabled for `NodeToNodeV_16` (per the changelog) and is fully wired in production. Any peer that can establish a `NodeToNodeV_16` connection can exploit this. No key compromise, stake majority, or privileged access is required. The exploit requires only constructing a minimal valid-CBOR `PerasCert blk` (two CBOR fields: a round number and a block point).

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's public keys before accepting any certificate. Until the real implementation is ready, the inbound handler should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them. The TODO at `SupportsPeras.hs:350-352` and `PerasCert.hs:103,125-126` must be resolved before this code is deployed on any network where Peras certificate diffusion is active.

---

### Proof of Concept

```haskell
-- Construct a minimal forged PerasCert targeting an adversarial block
-- known to be in the peer's VolatileDB (e.g., obtained via ChainSync).
let forgedCert = PerasCert
      { pcCertRound      = PerasRoundNo 42          -- any round not yet in DB
      , pcCertBoostedBlock = BlockPoint slot adversarialHash
      }

-- Encode as CBOR (2-element list per the Serialise instance)
-- and send via the ObjectDiffusion miniprotocol (NodeToNodeV_16).
-- processCerts will call (validatePerasCert mkPerasParams forgedCert)
-- which unconditionally returns Right, storing the cert and triggering
-- chainSelectionForBlock for adversarialHash with weight boost = 15.
```

The cert will be stored (`AddedPerasCertToDB`) and, if `adversarialHash` is in the VolatileDB, `chainSelectionForBlock` will be called immediately, potentially switching the node to the adversarially boosted chain.
