### Title
Peras Certificate Validation Bypass via Degenerate `BlockSupportsPeras` Instance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance, which applies to all `StandardHash blk` types including production Cardano blocks, implements `validatePerasCert` as a function that unconditionally returns `Right` — accepting every inbound certificate without any cryptographic verification. When Peras is enabled, an unprivileged peer can send a crafted certificate that bypasses all validation, is stored in the `PerasCertDB`, and triggers chain selection for an adversary-chosen block.

---

### Finding Description

`BlockSupportsPeras` defines the `validatePerasCert` method as the gating check before a certificate is stored and acted upon. The degenerate instance — which is the only instance in the codebase and therefore the one used for production Cardano blocks — is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function ignores the certificate content entirely and always succeeds. The instance declaration itself is explicitly marked as a placeholder:

```haskell
-- TODO degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [2](#0-1) 

The production inbound certificate processing path in `processCerts` calls this validation function directly:

```haskell
(validatePerasCert mkPerasParams)
``` [3](#0-2) 

`processCerts` is the function that processes all inbound Peras certificates received from peers. It calls `validateCert` on each certificate, and if validation succeeds (which it always does), the certificate is timestamped and added to the database: [4](#0-3) 

Once a certificate is in the `PerasCertDB`, `chainSelSync` in `ChainSel.hs` uses it to trigger chain selection for the boosted block: [5](#0-4) 

The `ChainDB` API exposes `addPerasCertAsync`, which is the entry point from the network layer: [6](#0-5)

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and used to boost the weight of the attacker-chosen block in chain selection. If the boosted block is present in the `VolatileDB`, `chainSelectionForBlock` is immediately triggered. This can cause an honest node to prefer a non-canonical or adversary-controlled chain over the honest chain, constituting a **chain selection safety failure** triggered by an unprivileged peer with no stake requirement.

This is the direct analog of the TSS report: just as a TSS node could remove its deposit and still be elected because the deposit check was absent at the point of election, here a Peras certificate can be accepted and acted upon because the cryptographic validity check is absent at the point of certificate ingestion.

---

### Likelihood Explanation

Peras is currently disabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However, the infrastructure is wired into the production `ChainDB` and `ObjectDiffusion` code paths and is designed to be enabled. Once enabled, the attack requires only that the adversary send a well-formed `PerasCert` CBOR message — no stake, no keys, no cryptographic capability. The attack is trivially executable by any connected peer.

---

### Recommendation

1. **Before enabling Peras in production**, replace the degenerate `validatePerasCert` with a Cardano-specific instance that performs full cryptographic verification of the certificate's aggregate BLS signature and VRF proofs against the epoch's stake distribution and nonce (as implemented in `WFALS.implVerifyCert`).
2. As an immediate defensive measure, the degenerate instance should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that enabling Peras without a real implementation fails closed rather than open.
3. Track completion via the referenced issue `cardano-peras#120`.

---

### Proof of Concept

With Peras enabled on a private testnet:

1. Connect a malicious peer to an honest node.
2. Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of a block on an adversarial fork present in the honest node's VolatileDB>`.
3. Send the certificate via the ObjectDiffusion mini-protocol.
4. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
5. The certificate is stored in `PerasCertDB` and `chainSelSync` triggers `chainSelectionForBlock` for the adversarial block.
6. The honest node's chain selection now assigns extra Peras weight to the adversarial fork and may switch to it, diverging from the canonical chain.

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
