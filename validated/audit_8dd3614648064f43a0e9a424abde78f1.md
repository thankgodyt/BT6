### Title
TOCTOU Race in `request_refund_callback` Permanently Loses User's 2 NEAR Attached Deposit — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

A TOCTOU race condition exists between `internal_request_refund` dispatching `verify_transaction_inclusion` and `request_refund_callback` executing. If a trusted relayer finalizes the same UTXO via `verify_deposit` / `verify_deposit_v2` in the intervening blocks, `request_refund_callback` panics with `"UTXO already verified via deposit"`. Because the 2 NEAR attached deposit was received by the contract in the original call (before the promise chain), NEAR's callback-revert semantics do not refund it. The user loses 2 NEAR and no `RefundRequest` is ever stored.

---

### Finding Description

**Entry point — public, unprivileged:**

`request_refund` is `#[payable]` with no `#[trusted_relayer]` guard on the function itself. Other functions in the same `impl` block (`reject_refund`, `execute_refund`) are explicitly callable by anyone, confirming the macro on the `impl` block does not gate individual functions. [1](#0-0) 

**Deposit received in the original call, no state written:**

`internal_request_refund` is `&self` (immutable). It checks the attached deposit, then immediately fires the cross-contract promise chain. The 2 NEAR deposit is transferred to the contract's balance at call entry; no storage is written yet. [2](#0-1) 

**Race window — `verify_deposit_callback` inserts into `verified_deposit_utxo`:**

Between the `verify_transaction_inclusion` cross-contract call and `request_refund_callback`, a trusted relayer can call `verify_deposit` / `verify_deposit_v2` for the same UTXO. Its callback unconditionally inserts the UTXO key into `verified_deposit_utxo`. [3](#0-2) 

**Callback panics, deposit is not refunded:**

`request_refund_callback` checks `verified_deposit_utxo` and panics if the UTXO is already present. The callback's state changes are reverted, but the 2 NEAR deposit — already in the contract's balance from the original call — is not returned. [4](#0-3) 

**No recovery path exists.** `claim_lost_found` is for nBTC, not NEAR. There is no function to reclaim a deposit whose `request_refund_callback` panicked. [5](#0-4) 

**Deposit amount — 2 NEAR:** [6](#0-5) 

---

### Impact Explanation

The user's 2 NEAR attached deposit is permanently absorbed by the contract. No `RefundRequest` is created, so the user cannot proceed with the refund. The BTC deposit itself is unaffected (the relayer's `verify_deposit` minted nBTC normally), but the user has lost 2 NEAR with no recourse.

This matches the allowed Medium impact: **broken callback rollback** — the callback fails but the deposit is not rolled back.

---

### Likelihood Explanation

The race window is realistic:

- A user calls `request_refund` believing `verify_deposit` was never called (e.g., relayer was slow, user changed mind).
- The relayer independently observes the confirmed BTC transaction and calls `verify_deposit` — its normal duty.
- Both cross-contract calls are in-flight simultaneously across a few NEAR blocks.
- No coordination or malice is required; this is ordinary concurrent bridge operation.

The scenario is low-to-medium probability in practice (requires the relayer to act during the specific window), but it is fully reachable without any privileged access by the user.

---

### Recommendation

Pass the original caller's `AccountId` as a parameter to `request_refund_callback`. On the `"UTXO already verified via deposit"` branch, instead of panicking, transfer the attached deposit back to the caller via `Promise::new(caller).transfer(env::attached_deposit())` and return `false`. This preserves the anti-spam property for successful requests while correctly refunding users who lose the race.

Alternatively, check `verified_deposit_utxo` synchronously at the start of `internal_request_refund` (before the promise chain) and panic immediately if the UTXO is already finalized — this refunds the deposit because the original call panics before succeeding.

       "UTXO already verified via deposit"   // ← PANIC
   );
   → Callback reverts. No RefundRequest stored.
   → Alice's 2 NEAR is permanently in the contract's balance.
   → No claim_lost_found or other recovery path exists.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
