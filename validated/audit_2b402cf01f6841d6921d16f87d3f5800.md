### Title
`checkPreferTheirsOverOurs` Ignores Peras Certificate Weights at Forecast Horizon, Causing Incorrect Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer's header exceeds the local forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect. This function unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate`, discarding all Peras certificate boosts. When Peras is enabled and the canonical chain is shorter by block count but heavier by Peras weight, the node incorrectly concludes the peer's chain is not preferred and disconnects with `CandidateTooSparse`, permanently preventing adoption of the canonical chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` (i.e., the requested slot is beyond the forecast horizon). The function compares the peer's fragment against the local selection using `preferAnchoredCandidate`, but hard-codes `emptyPerasWeightSnapshot` as the weight argument:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero weight, ignores all Peras certs
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`. When the snapshot is empty it falls back to a pure block-count comparison via `selectView`; when non-empty it uses `weightedSelectView` which incorporates Peras certificate boosts. [2](#0-1) 

Because `emptyPerasWeightSnapshot` is always passed, the Peras-weight branch is never reached in `checkPreferTheirsOverOurs`, regardless of how many certificates have been accumulated in the live `PerasWeightSnapshot` stored in the ChainDB.

The actual Peras weight snapshot is read from `cdbPerasWeightSnapshot` during normal chain selection in `chainSelectionForBlock`: [3](#0-2) 

That snapshot is never consulted in `checkPreferTheirsOverOurs`.

---

### Impact Explanation

When Peras is active, a certificate boosts a block's weight by a value derived from the security parameter `k`. A chain that is one block shorter than the local selection but carries a single valid certificate can be the canonical chain under Peras chain-order rules. If such a chain's tip slot falls beyond the current forecast horizon, `checkPreferTheirsOverOurs` evaluates it as block-count-only shorter, returns `ShouldNotSwitch`, and the node fires `throwSTM CandidateTooSparse`, permanently disconnecting from the peer.

The node then remains on the lighter (non-canonical) chain. This is a **chain selection bug that causes an honest node to prefer a non-canonical, less-secure chain** — matching the "High" impact tier: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*.

---

### Likelihood Explanation

The trigger conditions are:

1. Peras is enabled in the era configuration (not the current mainnet default, but the code is production-integrated and the feature is actively being deployed).
2. A peer's chain tip slot exceeds the local forecast horizon — a normal occurrence during sync or after a slot gap larger than the stability window.
3. The peer's chain is shorter by block count but heavier by Peras weight — the exact scenario Peras is designed to produce when a certificate is issued for a block on a shorter fork.

No privileged access, key compromise, or stake majority is required. Any honest peer serving the canonical Peras-boosted chain can trigger the disconnection.

---

### Recommendation

Replace the hard-coded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from `cdbPerasWeightSnapshot` (the same snapshot used in `chainSelectionForBlock`). The snapshot must be passed into the ChainSync client's closure or read atomically from the shared `TVar`. The existing TODO comment (`https://github.com/tweag/cardano-peras/issues/64`) already tracks this; the fix should be prioritised before Peras is enabled on any production network.

---

### Proof of Concept

1. Enable Peras in the era configuration with a non-zero round length.
2. Construct two chains forking at block `B`:
   - **Chain A** (local): `B → C → D` (length 2 after fork, no certificate).
   - **Chain B** (peer): `B → E` (length 1 after fork, carries a valid Peras certificate boosting `E` with weight > 1 block equivalent).
3. Under correct Peras chain-order, Chain B is canonical (heavier total weight).
4. Arrange for the peer to send header `E` at a slot beyond the local forecast horizon (e.g., after a large empty-slot gap).
5. `projectLedgerView` returns `Nothing` for slot of `E`.
6. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
7. `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` compares block counts: Chain A tip block-no > Chain B tip block-no → `ShouldNotSwitch`.
8. `throwSTM CandidateTooSparse` fires; the peer is disconnected.
9. The node remains permanently on Chain A (the lighter, non-canonical chain) and never adopts Chain B. [4](#0-3) [5](#0-4) [6](#0-5)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"

          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
