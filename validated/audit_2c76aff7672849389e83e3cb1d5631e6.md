### Title
Lack of Access Control on `sign_btc_transaction` Allows Anyone to Force-Sign Any Pending Transaction — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` has no caller verification. Any unprivileged NEAR account can trigger MPC signing for any pending transaction (withdrawal, refund, or UTXO management) owned by another user, bypassing the owner's ability to RBF or cancel, and potentially locking bridged funds if a wrong `key_version` is supplied.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` accepts a `btc_pending_sign_id`, `sign_index`, and `key_version` but never checks that `env::predecessor_account_id()` equals `btc_pending_info.account_id`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ← NO require!(env::predecessor_account_id() == btc_pending_info.account_id)
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
``` [1](#0-0) 

The outer `impl` block carries only `#[near]` — no `#[trusted_relayer]`, no `#[access_control_any]`, and no `assert_one_yocto()` inside the function body. The function is freely callable by any NEAR account at zero deposit cost.

Every pending transaction (`BTCPendingInfo`) records its owner in `account_id`:

```rust
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
    state: PendingInfoState::Refund(OriginalState {
        stage: PendingInfoStage::PendingSign,
        ...
    }),
};
``` [2](#0-1) 

Once `sign_btc_transaction` is called and the MPC produces a signature, the pending info transitions out of `PendingSign` state. The user's `withdraw_rbf` path requires `PendingSign` state, so after a forced signing the user can no longer fee-bump or cancel their own transaction.

---

### Impact Explanation

**Attack vector 1 — Force-sign to block RBF/cancellation (Medium):**  
An attacker calls `sign_btc_transaction(victim_pending_id, 0, correct_key_version)`. The MPC signs the transaction at the original fee rate. The pending info moves to `PendingVerify`. The victim can no longer call `withdraw_rbf` (which asserts `PendingSign` state). If Bitcoin mempool fees have risen, the transaction may be stuck for an extended period, temporarily locking the user's bridged BTC. Operator intervention (`cancel_withdraw`) is required to unblock.

**Attack vector 2 — Force-sign with wrong `key_version` (Medium→Critical boundary):**  
An attacker calls `sign_btc_transaction(victim_pending_id, 0, wrong_key_version)`. The MPC signs with a key that does not correspond to the deposit address's derivation path. The resulting Bitcoin transaction carries an invalid witness, making it unconfirmable on-chain. `verify_withdraw` / `verify_refund_finalize` will never succeed. The victim's nBTC remains escrowed in the bridge contract indefinitely until DAO/Operator manually cancels the pending info via `cancel_withdraw` or `cancel_active_utxo_management`. [3](#0-2) [4](#0-3) 

---

### Likelihood Explanation

High. The function is public, requires no deposit, and accepts any `btc_pending_sign_id` string. An attacker only needs to observe emitted `GenerateBtcPendingInfo` events (or query `get_btc_pending_infos_paged`) to enumerate all valid IDs. No privileged role or leaked key is required. [5](#0-4) 

---

### Recommendation

Add an owner check at the top of `sign_btc_transaction`, mirroring the pattern used in `withdraw_rbf` (which correctly derives `account_id` from `env::predecessor_account_id()`):

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    require!(
        env::predecessor_account_id() == btc_pending_info.account_id,
        "Only the transaction owner can sign"
    );
    ...
}
``` [6](#0-5) 

---

### Proof of Concept

1. Alice calls `ft_transfer_call` on nBTC to initiate a withdrawal. The bridge creates a `BTCPendingInfo` with `account_id = alice` and emits `GenerateBtcPendingInfo { account_id: "alice", btc_pending_id: "abc123" }`.
2. Attacker observes the event and calls:
   ```
   sign_btc_transaction("abc123", 0, 999)   // wrong key_version
   ```
   No deposit required. The call succeeds because there is no `require!(predecessor == btc_pending_info.account_id)`.
3. The MPC signs with key version 999, producing an invalid witness for Alice's deposit address.
4. The signed transaction is broadcast but never confirms on Bitcoin.
5. Alice's nBTC remains locked in the bridge. `verify_withdraw` will never succeed. Alice cannot RBF (state is no longer `PendingSign`). Only DAO/Operator can unblock via `cancel_withdraw`. [1](#0-0) [4](#0-3)
