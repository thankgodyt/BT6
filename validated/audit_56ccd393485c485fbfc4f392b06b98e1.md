Let me check for any admin recovery functions for `unavailable_utxos` or `verified_deposit_utxo`.

### Title
`unavailable_utxo_callback` Permanently Locks UTXOs After `min_deposit_amount` Is Lowered via `update_config` — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

`unavailable_utxo_callback` inserts a sub-minimum UTXO's key into the `verified_deposit_utxo` replay-protection set. If the DAO later lowers `min_deposit_amount` via `update_config`, a subsequent `verify_deposit` call for the same UTXO routes to `verify_deposit_callback`, which panics on the duplicate insert. No recovery path exists: the UTXO is permanently stuck in `unavailable_utxos` with no nBTC minted and no refund possible.

---

### Finding Description

**Step 1 — sub-minimum UTXO routed to `unavailable_utxo_callback`.**

In `internal_verify_deposit`, the branch at line 45 checks `deposit_amount < config.min_deposit_amount` at call time and schedules `unavailable_utxo_callback`: [1](#0-0) 

**Step 2 — `unavailable_utxo_callback` inserts into `verified_deposit_utxo`.**

The callback unconditionally inserts the UTXO key into the replay-protection set and then stores the UTXO in `unavailable_utxos`. No nBTC is minted. [2](#0-1) 

**Step 3 — DAO lowers `min_deposit_amount`.**

`update_config` applies `ConfigUpdate` fields unconditionally; `min_deposit_amount` can be set to any value, including one below the already-processed UTXO's balance: [3](#0-2) [4](#0-3) 

**Step 4 — second `verify_deposit` panics.**

With the new lower threshold, `internal_verify_deposit` now routes the same UTXO to `verify_deposit_callback`. That callback attempts to insert the same key into `verified_deposit_utxo`, which already contains it, and the `require!` fires: [5](#0-4) 

**Step 5 — refund path is also blocked.**

`request_refund_callback` checks `verified_deposit_utxo` and rejects any refund request for a key already present: [6](#0-5) 

Even if a refund request were somehow created, `load_refund_request_for_execute` blocks execution for the same reason: [7](#0-6) 

**No admin recovery function exists.** The entire `management.rs` surface contains no method to remove an entry from `verified_deposit_utxo` or to promote a UTXO from `unavailable_utxos` to the main `utxos` pool. [8](#0-7) 

---

### Impact Explanation

The affected UTXO is permanently stuck:
- It sits in `unavailable_utxos` — not in the main `utxos` pool, so no nBTC is ever minted.
- It is in `verified_deposit_utxo` — blocking both a fresh `verify_deposit` and any `request_refund` / `execute_refund`.
- The user's BTC is locked at the chain-signatures-controlled deposit address with no on-chain path to recover it without a contract upgrade.

This matches the **Medium** impact category: attacker-triggered (or governance-triggered) permanent locking of bridged funds, requiring operator intervention to recover.

---

### Likelihood Explanation

The scenario requires two independent events: (a) a relayer submitting a valid proof for a sub-minimum UTXO, and (b) the DAO later lowering `min_deposit_amount`. Both are normal, non-malicious operations. The DAO lowering the minimum is a routine governance action (e.g., responding to BTC price changes or protocol growth). Any UTXO that was processed before the config change and landed in `unavailable_utxos` is silently and permanently bricked. The number of affected UTXOs scales with how many sub-minimum deposits occurred before the config change.

---

### Recommendation

`unavailable_utxo_callback` should **not** insert into `verified_deposit_utxo`. The replay-protection set is meant to mark UTXOs that have been fully finalized (nBTC minted or refund executed). A sub-minimum UTXO is neither; it should remain re-processable. The fix is to remove the `verified_deposit_utxo.insert` call from `unavailable_utxo_callback` and instead rely on the `unavailable_utxos` map itself as the idempotency guard (i.e., check whether the key already exists in `unavailable_utxos` before inserting, and revert if so). This preserves replay protection for the unavailable path without permanently blocking future deposit attempts after a config change.

---

### Proof of Concept

```
1. Deploy bridge with min_deposit_amount = 10_000 sat.
2. User sends 5_000 sat to their deposit address.
3. Relayer calls verify_deposit with valid merkle proof.
   → internal_verify_deposit: 5_000 < 10_000 → schedules unavailable_utxo_callback.
   → unavailable_utxo_callback:
       verified_deposit_utxo.insert("txid@0") → true (success)
       unavailable_utxos.insert("txid@0", utxo)
4. DAO calls update_config({ min_deposit_amount: "4000" }).
5. Relayer calls verify_deposit again for the same UTXO.
   → internal_verify_deposit: 5_000 >= 4_000 → schedules verify_deposit_callback.
   → verify_deposit_callback:
       verified_deposit_utxo.insert("txid@0") → false (already present)
       require! fires → PANIC: "Already deposit utxo"
6. User calls request_refund for the same UTXO.
   → request_refund_callback:
       verified_deposit_utxo.contains("txid@0") → true
       require! fires → PANIC: "UTXO already verified via deposit"
Result: 5_000 sat permanently locked. No nBTC minted. No refund possible.
```

impl Contract {
    /// Withdraw a specified amount of protocol fee to the owner’s account.
    ///
    /// # Arguments
    ///
    /// * `amount` - Specify the amount to withdraw; if not specified, it will be the full amount.
    ///
    /// # Returns
    ///
    /// bool - Whether the Withdraw was successful.
    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn withdraw_protocol_fee(&mut self, amount: Option<U128>) -> Promise {
        assert_one_yocto();
        let total_protocol_fee = self.data().cur_available_protocol_fee;
        let amount = amount.map_or(total_protocol_fee, |v| v.0);
        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
        self.internal_withdraw_protocol_fee(amount)
    }
}
