### Title
Stale Gas Fee in Refund Request Causes Permanently Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `gas_fee` for a BTC refund transaction is fixed at `request_refund` time and stored immutably in `RefundRequest`. A mandatory timelock of 2–14 days must elapse before `execute_refund` can be called. During this window, BTC fee market conditions can change significantly. When `execute_refund` finally runs, the refund PSBT is built using the stale stored `gas_fee`, producing an under-fee'd transaction that will not confirm on Bitcoin. After `execute_refund` runs, the deposit UTXO is inserted into `verified_deposit_utxo`, blocking both a re-request of the refund and a `verify_deposit`. There is no on-chain path to update the `gas_fee` of an existing `RefundRequest`, leaving the user's funds in a stuck state that requires operator intervention to resolve.

### Finding Description

**Step 1 – Fee is fixed at request time.**

In `request_refund_callback`, the gas fee is resolved once and stored permanently in the `RefundRequest`: [1](#0-0) 

The `gas_fee` field of `RefundRequest` has no setter; the struct is written once and read verbatim at execution time.

**Step 2 – Mandatory timelock guarantees a delay.**

`resolve_execute_refund_timelock` enforces a minimum wait of `refund_timelock_sec` (default 2 days) for pre-authorized refunds and `unsafe_refund_timelock_sec` (default 14 days) for caller-supplied addresses before `execute_refund` may proceed: [2](#0-1) [3](#0-2) 

**Step 3 – Execution uses the stale fee.**

`refund_execution_inputs` computes `refund_amount = refund_request.amount - refund_request.gas_fee` using the fee locked in at request time, with no reference to the current BTC fee market: [4](#0-3) 

The resulting PSBT is broadcast with this stale fee. If BTC fees have risen during the 2–14 day window, the transaction will be below the mempool minimum fee rate and will not confirm.

**Step 4 – UTXO is locked after `execute_refund`, blocking re-request.**

`finalize_refund_with_psbt` inserts the deposit UTXO into `verified_deposit_utxo` immediately after building the PSBT: [5](#0-4) 

`request_refund_callback` rejects any new refund request for a UTXO already in `verified_deposit_utxo`: [6](#0-5) 

So once `execute_refund` has run, the user cannot re-request a refund with a higher fee.

**Step 5 – Re-running `execute_refund` does not help.**

The `executed` flag allows `execute_refund` to be called again to rebuild the PSBT (e.g., after a chain reorganization): [7](#0-6) 

But the rebuilt PSBT still uses the same stale `gas_fee` from the stored `RefundRequest`. There is no parameter to override it.

**Step 6 – Operator rejection does not restore the user's ability to re-request.**

`internal_reject_refund` removes the `RefundRequest` entry but does **not** remove the UTXO from `verified_deposit_utxo`: [8](#0-7) 

After rejection, the UTXO remains in `verified_deposit_utxo`, so `request_refund_callback` will still reject a new refund request for the same UTXO. The user's deposit is permanently inaccessible via the refund path, and `verify_deposit` is also blocked because the UTXO is already in `verified_deposit_utxo`.

**Step 7 – No RBF path exists for refund transactions.**

The `PendingInfoState::Refund` variant carries an `OriginalState` with `max_gas_fee` and `last_rbf_time_sec` fields, but there is no `refund_rbf` entry point in the RBF module: [9](#0-8) 



The RBF directory contains only `withdraw.rs`, `cancel_withdraw.rs`, `active_utxo_management.rs`, and `cancel_active_utxo_management.rs`. Refund transactions have no fee-bump path.

### Impact Explanation

A user whose refund was requested during a low-fee period and whose `execute_refund` is called during a high-fee period ends up with:
- A refund PSBT that will not confirm on Bitcoin (under-fee'd).
- Their deposit UTXO locked in `verified_deposit_utxo`, blocking both re-request of the refund and `verify_deposit`.
- No on-chain mechanism to update the fee or escape the stuck state without operator intervention.

This matches the **Medium** allowed impact: *stuck bridge state requiring operator intervention*.

### Likelihood Explanation

BTC fee market is highly volatile; fees routinely spike 10–100× during periods of congestion (e.g., Ordinals/Runes activity). The 2–14 day mandatory timelock is a guaranteed delay that makes fee staleness a near-certainty during any significant market event. Any user who requests a refund during a low-fee period is exposed. No attacker action is required; ordinary market conditions trigger the stuck state.

### Recommendation

1. **Allow `execute_refund` to accept an updated `gas_fee` parameter** that overrides the stored value, subject to `min_btc_gas_fee ≤ new_fee ≤ max_btc_gas_fee` and `new_fee < deposit_amount`.
2. **Add an RBF path for refund transactions** analogous to `internal_withdraw_rbf`, so a stuck refund PSBT can be fee-bumped without rebuilding the entire request.
3. **When `internal_reject_refund` is called on an already-executed refund**, also remove the UTXO from `verified_deposit_utxo` so the user can re-request with a higher fee.
4. **Validate the caller-supplied `gas_fee` against `config.min_btc_gas_fee`** in `request_refund_callback` to prevent trivially under-fee'd requests from being stored.

### Proof of Concept

1. BTC fee market is at 5 sat/vB. User calls `request_refund` with `gas_fee = None`; the protocol resolves it to `get_refund_gas_fee()` (e.g., 5000 sat for a ~1000-vB tx). The `RefundRequest` is stored with `gas_fee = 5000`.
2. The 14-day `unsafe_refund_timelock_sec` begins.
3. During the 14-day window, BTC fees spike to 200 sat/vB (mempool minimum rises to ~200 000 sat for the same tx).
4. After the timelock, anyone calls `execute_refund`. `refund_execution_inputs` computes `refund_amount = deposit_amount - 5000`. The PSBT is built with a 5000-sat fee.
5. The PSBT is signed by MPC and broadcast. Miners reject it (fee rate ~5 sat/vB, far below the 200 sat/vB minimum). The transaction is never confirmed.
6. `finalize_refund_with_psbt` has already inserted the UTXO into `verified_deposit_utxo`. The user cannot call `request_refund` again (blocked at line 535–540). Re-running `execute_refund` rebuilds the same under-fee'd PSBT. The operator can call `reject_refund`, but the UTXO remains in `verified_deposit_utxo`, so the user still cannot re-request. The deposit is permanently inaccessible.

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
