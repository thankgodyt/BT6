Audit Report

## Title
Stale `MetadataPayload` Signatures Remain Valid After `set_metadata`, Enabling Foreign-Chain Token Deployment With Incorrect Decimals — (`near/omni-types/src/lib.rs`, `near/omni-bridge/src/lib.rs`, `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`MetadataPayload` contains no nonce, timestamp, or version field, so any MPC-signed metadata signature is valid indefinitely. If a token's decimals are legitimately updated via `set_metadata` after a signature has been emitted on-chain, an unprivileged attacker can replay the old signed payload to `deployToken` on any EVM or Starknet chain where the token has not yet been deployed, permanently anchoring the wrong decimal value. All subsequent cross-chain transfers to that chain use the stale decimals for normalization, causing permanent, unrecoverable fund loss.

## Finding Description

**Root cause — `MetadataPayload` has no replay-prevention field.**

The struct at `near/omni-types/src/lib.rs` L694–702 contains only `prefix`, `token`, `name`, `symbol`, and `decimals`. There is no nonce, block height, timestamp, or version. A valid MPC signature over this struct is valid forever and on every chain. [1](#0-0) 

**Step 1 — `log_metadata_callback` signs and publicly emits the payload.**

`near/omni-bridge/src/lib.rs` L341–384 constructs a `MetadataPayload` from the current `ft_metadata()`, requests an MPC signature, and emits the signed payload as a NEAR event log. Any observer can capture it. [2](#0-1) 

**Step 2 — `set_metadata` freely updates decimals with no signature invalidation.**

`near/omni-token/src/lib.rs` L156–188 updates `metadata.decimals` with only an `assert_controller()` guard. There is no check that a `MetadataPayload` has already been signed, no version bump, and no invalidation of prior signatures. [3](#0-2) 

**Step 3 — EVM `deployToken` replay guard is insufficient.**

`evm/src/omni-bridge/contracts/OmniBridge.sol` L151–158 verifies the MPC signature and then checks `!isBridgeToken[nearToEthToken[metadata.token]]`. On a chain where the token has not yet been deployed, `nearToEthToken[metadata.token]` returns `address(0)` and `isBridgeToken[address(0)]` is `false`, so the check passes. There is no nonce or version check on the metadata signature itself. [4](#0-3) 

**Step 4 — SECURITY.md confirms signatures are intentionally chain-agnostic.**

`evm/SECURITY.md` L10 explicitly states: "Metadata signatures are intentionally chain-agnostic — one NEAR-side signature deploys the same token on all EVM chains." This design means a stale signature is equally valid on every EVM chain where the token has not yet been deployed. [5](#0-4) 

**Step 5 — Starknet `deploy_token` has the same gap.**

`starknet/src/omni_bridge.cairo` L202–209 verifies the signature and then checks `existing_token.is_zero()`. No nonce or version check on the metadata signature. [6](#0-5) 

**Step 6 — Stale decimals are permanently stored and used for normalization.**

`near/omni-bridge/src/lib.rs` L471–480 reads `token_decimals` (set at deployment time) and passes it to `normalize_amount` for every `sign_transfer` call. If the stored decimals are wrong, every transfer to that chain is mis-normalized. [7](#0-6) 

## Impact Explanation

This is a **Critical** impact matching "decimal/normalization abuse that changes user or protocol balances." When a token is deployed on Chain B with stale decimals (e.g., 18 instead of the current 6), `normalize_amount` applies a 10^12 scaling error to every transfer. A user sending 1.0 token (1,000,000 raw units at decimals=6) receives 0 tokens on Chain B (1,000,000 / 10^12 rounds to zero). The `token_decimals` mapping is set at deployment and never updated, making this permanent and unrecoverable for every transfer routed through that chain's token address.

## Likelihood Explanation

- `log_metadata` is permissionless; signed payloads are emitted as public NEAR events and can be captured by any observer.
- Metadata updates (especially decimal corrections during token migration or rebranding) are a documented, legitimate controller/DAO operation.
- The vulnerability window is any chain where the token has not yet been deployed at the time of the metadata update — a realistic scenario during phased multi-chain rollouts.
- No admin compromise is required. The attacker only needs the publicly emitted signed event and the ability to call `deployToken` (also permissionless per `evm/SECURITY.md` L8) on the target chain. [8](#0-7) 

## Recommendation

1. **Add a monotonic `metadata_version` counter** to `OmniToken` state. Include it in `MetadataPayload`. Increment it on every `set_metadata` call. EVM/Starknet `deployToken` should reject payloads whose version does not match the current one (verified via a NEAR view call or an on-chain registry updated by the relayer).
2. **Alternatively, add a block-height or timestamp field** to `MetadataPayload` and have `deployToken` reject payloads older than a configurable window.
3. **At minimum**, add an on-chain guard in `set_metadata` that blocks updates once a `MetadataPayload` has been signed (e.g., a `metadata_signed` flag), or require a new `log_metadata` call to supersede any prior signature before `set_metadata` is permitted.

## Proof of Concept

```
1. Deploy OmniToken with decimals=18, name="Alpha", symbol="ALP".
2. Call bridge.log_metadata(token_id).
   → ft_metadata() returns {name="Alpha", symbol="ALP", decimals=18}
   → MPC signs MetadataPayload{token, name="Alpha", symbol="ALP", decimals=18}
   → Signed payload emitted as NEAR event. Attacker captures it.
3. Controller calls omni_token.set_metadata(decimals=Some(6)).
   → assert_controller() passes (legitimate DAO operation).
   → ft_metadata() now returns decimals=6.
   → No prior signature is invalidated.
4. Token is deployed on Chain A (correctly, via a fresh log_metadata call) with decimals=6.
5. Token has NOT yet been deployed on Chain B.
6. Attacker submits old signed payload (decimals=18) to Chain B's OmniBridge.deployToken().
   → ECDSA.recover(hashed, signatureData) == nearBridgeDerivedAddress ✓ (valid MPC sig)
   → !isBridgeToken[nearToEthToken[token]] == true ✓ (not yet deployed on B)
   → Token deployed on Chain B with decimals=18.
   → token_decimals[chainB_token_address] = 18 stored permanently.
7. User transfers 1.0 token (1_000_000 raw units, decimals=6) from NEAR to Chain B.
   → normalize_amount(1_000_000, stored_decimals=18)
   → 1_000_000 / 10^(18-6) = 1_000_000 / 10^12 = 0 (integer division)
   → require(amount_to_transfer > 0) reverts, or user receives 0 tokens.
   → Funds are permanently lost or transfers are permanently bricked for Chain B.
```
