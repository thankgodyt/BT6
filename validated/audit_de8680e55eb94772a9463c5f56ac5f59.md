### Title
Unvalidated `sign_index` Causes Index-Out-of-Bounds Panic in `sign_btc_transaction` - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary
`sign_btc_transaction` accepts a caller-controlled `sign_index: usize` with no upper-bound check. Any caller can supply `sign_index >= signatures.len()` against any known `btc_pending_sign_id`, triggering a Rust index-out-of-bounds panic inside `internal_sign_btc_transaction`, aborting the transaction and burning the caller's attached NEAR deposit.

---

### Finding Description

`sign_btc_transaction` is a `#[payable]` public entry point with no ACL guard beyond the pause check. [1](#0-0) 

It passes `sign_index` directly to `internal_sign_btc_transaction` without any bounds validation. [2](#0-1) 

Inside `internal_sign_btc_transaction`, `sign_index` is used as a direct array subscript on two `Vec` fields:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),  // panics if OOB
    "Already signed"
);
...
let path = btc_pending_info.vutxos[sign_index].get_path();  // panics if OOB
``` [3](#0-2) 

Both `signatures` and `vutxos` are sized to `psbt.get_input_num()` at pending-info creation time:

```rust
signatures: vec![None; need_signature_num],
``` [4](#0-3) 

There is no `require!(sign_index < btc_pending_info.signatures.len(), ...)` guard anywhere between the public entry point and the array accesses. Rust's default indexing panics on out-of-bounds, which in NEAR translates to `env::panic_str` — aborting the transaction and consuming the attached deposit.

---

### Impact Explanation

- **Panic is publicly reachable**: any account (no role required) can call `sign_btc_transaction` with a known `btc_pending_sign_id` (emitted as an on-chain event at creation) and `sign_index = N` where `N >= input_count`.
- **Attached deposit is lost**: the function is `#[payable]`; callers must attach NEAR to cover the MPC signing fee. On panic the deposit is not refunded.
- **No state corruption**: NEAR rolls back storage writes on panic, so the `BTCPendingInfo` itself is unaffected. The impact is limited to wasted gas and deposit for the caller.

Impact classification: **Low** — publicly reachable panic-driven fault in a production bridge path without direct theft.

---

### Likelihood Explanation

- `btc_pending_sign_id` values are broadcast via `Event::GenerateBtcPendingInfo` and are trivially observable.
- No role, key, or privileged access is required.
- The only cost to the attacker is the attached deposit they themselves lose; they can grief any pending-sign transaction owner by racing to call with an OOB index (though state is rolled back, the legitimate user's pending info is unaffected — the griefing is limited to wasting the attacker's own deposit).

---

### Recommendation

Add an explicit bounds check at the top of `internal_sign_btc_transaction` (or at the public entry point) before any array access:

```rust
require!(
    sign_index < btc_pending_info.signatures.len(),
    "sign_index out of bounds"
);
```

This converts the uncontrolled panic into a clean, refund-eligible `require!` failure.

---

### Proof of Concept

```rust
// Pseudocode unit test
let mut contract = setup_contract_with_one_input_psbt(); // signatures.len() == 1
let id = create_pending_sign_for_alice(&mut contract);

// sign_index == 1 is out of bounds for a 1-input PSBT
let result = std::panic::catch_unwind(|| {
    contract.sign_btc_transaction(id, /*sign_index=*/ 1, /*key_version=*/ 0)
});
assert!(result.is_err(), "expected index-out-of-bounds panic");
```

Calling `sign_btc_transaction` with `sign_index = signatures.len()` on a valid `PendingSign` `BTCPendingInfo` panics at `btc_pending_info.signatures[sign_index]` rather than returning an error, confirming the vulnerability. [5](#0-4)
