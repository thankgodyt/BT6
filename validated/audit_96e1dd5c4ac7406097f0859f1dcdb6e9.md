### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unbounded Weight Accumulation on Attacker-Controlled Forks - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance ships a `validatePerasCert` implementation that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks. Because the Peras cert object-diffusion mini-protocol is wired into the live ChainDB pipeline, any unprivileged peer can inject arbitrarily many fake certificates, each boosting the same fork block. Since the weight snapshot accumulates boosts additively across rounds, the attacker can inflate the apparent weight of any volatile block without bound, causing the honest node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (the comment calls it "degenerate instance for all blks to get things to compile"). No signature, no committee membership, no round-number plausibility, and no boosted-block validity check is performed.

**Entry path — peer-supplied certs reach `validatePerasCert` directly:**

`makePerasCertPoolWriterFromChainDB` wires `validatePerasCert mkPerasParams` as the sole validator for inbound certificates received over the node-to-node Peras cert diffusion mini-protocol:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls this validator and, if it returns `Right`, immediately timestamps and forwards the cert to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Weight accumulation — multiple fake certs for different rounds stack on the same block:**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` by iterating over every cert in `pcdsCertsByTicket` and calling `mkPerasWeightSnapshot`, which uses `addToPerasWeightSnapshot` with `Map.insertWith (<>)`: [4](#0-3) 

```haskell

  PerasWeightSnapshot . Map.insertWith (<>) pt weight . getPerasWeightSnapshot
``` [5](#0-4) 

Because `implAddCert` deduplicates only by **round number** (not by boosted block), an attacker can send N certs for N distinct rounds, all pointing to the same fork block. Each accepted cert contributes `perasWeight params` to that block's accumulated weight.

**Chain selection uses the inflated weight snapshot:**

`constructPreferableCandidates` reads the weight snapshot and passes it to `preferAnchoredCandidate`, which compares `wsvTotalWeight` (block number + weight boost): [6](#0-5) [7](#0-6) 

Once the accumulated fake weight exceeds the length difference between the current chain and the attacker's fork, `chainSelectionForBlock` switches the node to the fork: [8](#0-7)

### Impact Explanation

An unprivileged peer can cause an honest node to abandon its current canonical chain and adopt a shorter, non-canonical fork by injecting fake Peras certificates. Because weight accumulates additively across rounds with no upper bound enforced at the validation layer, the attacker can overcome any length deficit on their fork. This is a **bypass of Peras certificate validation** that directly enables **unauthorized chain selection manipulation**, matching the "Critical — bypass of certificate/signature validation" and "High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain" impact categories.

---

### Likelihood Explanation

The Peras cert object-diffusion mini-protocol is fully wired into the live ChainDB pipeline. Any peer that can connect to the node can send `PerasCert` messages. No stake, no key material, and no prior relationship is required. The attacker only needs to know a recent volatile block hash on a fork they control (or any fork in the VolatileDB). The attack is deterministic and requires no brute force.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before the Peras cert diffusion mini-protocol is enabled on any network. At minimum, verify the BLS aggregate signature over `(roundNo, boostedBlock)` against the committee's aggregate public key, and verify each member's VRF election proof. The BLS primitives already exist in `Ouroboros.Consensus.Peras.Crypto.BLS`.

2. **Gate the mini-protocol** behind a feature flag that is disabled until validation is complete, so the stub cannot be reached from the network.

3. **Add a per-block weight cap** in `addToPerasWeightSnapshot` or in `implAddCert` to bound the total boost any single block can accumulate, as a defense-in-depth measure against future validation gaps.

---

### Proof of Concept

1. Attacker connects to a target node running this codebase with Peras cert diffusion enabled.
2. Attacker identifies a volatile block `B_fork` on a fork that is `D` blocks shorter than the node's current chain tip.
3. Attacker sends `ceil(D / perasWeight) + 1` fake `PerasCert` messages, each with a distinct `pcCertRound` and `pcCertBoostedBlock = B_fork`.
4. Each cert passes `validatePerasCert` (always `Right`) and is stored in `PerasCertDB` under a unique ticket number.
5. `implGetWeightSnapshot` returns a snapshot where `B_fork` has accumulated weight `(ceil(D / perasWeight) + 1) * perasWeight > D`.
6. The next call to `chainSelectionForBlock` for any block on the fork computes `wsvTotalWeight(fork) > wsvTotalWeight(current chain)` and switches the node to the attacker's fork.
7. The node has now permanently adopted a non-canonical chain without the attacker possessing any stake, keys, or valid committee membership.
