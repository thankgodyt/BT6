### Title
Missing Access Control on `sign_btc_transaction` Allows Any Account to Corrupt MPC Signing with Arbitrary `key_version` - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

---

### Summary

The `sign_btc_transaction` function in the `satoshi-bridge` contract is publicly callable by any NEAR account. It lacks any role-based access control, mirroring the exact vulnerability class of the external report (missing `onlyMsc`-equivalent guard). An unprivileged attacker can call it with a wrong `key_version`, causing the MPC to produce a signature for the wrong key. That invalid signature is stored and blocks re-signing via the "Already signed" guard, moving the pending transaction to `PendingVerify` with invalid bytes and temporarily locking user funds.

---

### Finding Description

`sign_btc_transaction` is decorated only with `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. It carries no `#[access_control_any]` and no `#[trusted_relayer]` attribute — neither on the function nor on its enclosing `impl` block. [1](#0-0) 

Compare this to the deposit-verification functions in `bridge.rs`, which explicitly carry `#[trusted_relayer]` on both the `impl` block and each individual function: [2](#0-1) [3](#0-2) 

`sign_btc_transaction` has no such guard. The function accepts a caller-supplied `key_version: u32` and forwards it verbatim to the MPC `sign` call: [4](#0-3) 

The MPC uses `key_version` to select which key derivation to apply. If the attacker supplies a wrong version (e.g., `1` instead of `0`), the MPC produces a valid ECDSA signature but for a different derived key than the one that controls the UTXO. That signature is stored unconditionally in `btc_pending_info.signatures[sign_index]`: [5](#0-4) 

Once stored, the "Already signed" guard blocks any subsequent legitimate signing attempt for that input: [6](#0-5) 

When all inputs are "signed" (with the corrupted signature), `is_all_signed()` returns `true`, `extract_tx_bytes_with_sign()` serializes the PSBT with the invalid signature, and the pending info transitions to `PendingVerify` stage with bytes that will be rejected by the Bitcoin network: [7](#0-6) 

---

### Impact Explanation

The corrupted pending info is now in `PendingVerify` state with invalid signed bytes. The relayer cannot successfully broadcast the transaction to Bitcoin, and `verify_withdraw_v2` / `verify_refund_finalize` will never succeed because the transaction will never confirm on-chain.

- **Withdrawals**: The user may call `withdraw_rbf` to create a replacement transaction, but this requires operator cooperation and additional gas fees, constituting attacker-triggered temporary locking of bridged funds.
- **Refunds**: Recovery requires a trusted relayer to call `remove_refund_pending_tx_id` (which is `#[trusted_relayer]`-gated) to clear the corrupted entry before `execute_refund` can be retried. Until that happens, the user's BTC deposit is locked in the bridge UTXO. [8](#0-7) 

**Impact class**: Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

NEAR transactions are fully public. An attacker can monitor the chain for `GenerateBtcPendingInfo` events, immediately call `sign_btc_transaction` with the emitted `btc_pending_id`, `sign_index = 0`, and `key_version = 1` (or any non-zero value), racing the legitimate relayer. Since the attacker only needs to win the race for a single input on a single-input PSBT (the common case for withdrawals and refunds), this is straightforward. The attacker pays only their own gas and the MPC signing deposit — no special privilege is required. [9](#0-8) 

---

### Recommendation

Add `#[trusted_relayer]` (or `#[access_control_any(roles(Role::DAO, Role::Operator))]`) to `sign_btc_transaction`, consistent with how `verify_deposit_v2`, `verify_withdraw_v2`, and `verify_refund_finalize` are protected. The signing step is a privileged bridge operation and must not be open to arbitrary callers. [10](#0-9) 

---

### Proof of Concept

```
// Attacker monitors NEAR for GenerateBtcPendingInfo events.
// Upon seeing a new pending sign ID for a user withdrawal:

near call <satoshi_bridge_account> sign_btc_transaction \
  '{
    "btc_pending_sign_id": "<victim_pending_id>",
    "sign_index": 0,
    "key_version": 1
  }' \
  --accountId attacker.near \
  --deposit 1  // forward to MPC as required
```

1. MPC signs the PSBT input with key version 1 (wrong key).
2. `sign_btc_transaction_callback` stores the invalid signature; `signatures[0]` is now `Some(...)`.
3. Legitimate relayer calls `sign_btc_transaction(..., key_version: 0)` → panics: "Already signed".
4. `is_all_signed()` returns `true`; pending info moves to `PendingVerify` with invalid tx bytes.
5. Relayer broadcasts the transaction → Bitcoin rejects it (invalid signature).
6. `verify_withdraw_v2` is never callable successfully; user's nBTC is burned but BTC is not released until operator intervenes.

    pub fn sign_btc_transaction(

                        .btc_pending_sign_ids

                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
