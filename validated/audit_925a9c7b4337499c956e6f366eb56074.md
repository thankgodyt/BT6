### Title
Peras Certificate Round-Number Reuse After Garbage Collection Enables Unauthorized Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

`implGarbageCollect` in `PerasCertDB/Impl.hs` recomputes `pcdsCertIds` from the post-GC certificate map, permanently erasing the memory of which Peras round numbers have already been used. Because `implAddCert` uses `pcdsCertIds` as its sole deduplication guard, a round number that was GC'd can be re-submitted by an unprivileged peer. Combined with the degenerate `validatePerasCert` instance that unconditionally returns `Right` for all blocks, any peer can inject a fresh certificate for a previously-seen round, boosting an arbitrary volatile block and manipulating chain selection.

---

### Finding Description

**Root cause 1 — incorrect state update in `implGarbageCollect`:**

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs
gc :: PerasCertDbState blk -> PerasCertDbState blk
gc PerasCertDbState{ pcdsCertsByTicket, pcdsLastTicketNo, pcdsLatestCertSeen } =
  let pcdsCertsByTicket' =
        Map.filter
          (\cert -> pointSlot (getPerasCertBoostedBlock cert) >= NotOrigin slotNo)
          pcdsCertsByTicket
      pcdsCertIds' =
        Set.fromList (getPerasCertRound <$> Map.elems pcdsCertsByTicket')
   in PerasCertDbState
        { pcdsCertIds = pcdsCertIds'   -- ← recomputed; GC'd rounds are GONE
        , pcdsCertsByTicket = pcdsCertsByTicket'
        , pcdsLastTicketNo = pcdsLastTicketNo
        , pcdsLatestCertSeen = pcdsLatestCertSeen
        }
``` [1](#0-0) 

`pcdsCertIds` is documented as "in sync with `pcdsCertsByTicket`", so after GC it no longer contains the round numbers of removed certificates. The Peras protocol requires each round to produce at most one certificate; `pcdsCertIds` is the only enforcement mechanism for this invariant.

**Root cause 2 — deduplication guard reads the now-incomplete `pcdsCertIds`:**

This catch-all instance is the one in effect for all block types that do not override it. `processCerts` calls `validatePerasCert` before adding a certificate to the DB; because it always returns `Right`, any crafted certificate passes. [4](#0-3) 

**Chain-selection consequence:**

`getWeightSnapshot` derives the `PerasWeightSnapshot` directly from `pcdsCertsByTicket`. After a re-injected certificate is accepted, the snapshot includes a boost for the attacker-chosen block. `preferAnchoredCandidate` and `compareAnchoredFragments` use this snapshot to compare candidate fragments; a boosted adversarial block can tip the comparison in favour of a non-canonical chain. ### Impact Explanation

An unprivileged peer that has observed a round R certificate being garbage-collected (the boosted block crossed the immutable tip) can re-submit a new certificate for round R targeting any volatile block. Because `validatePerasCert` accepts it unconditionally and `pcdsCertIds` no longer blocks round R, the certificate is stored and its boost is included in every subsequent `getWeightSnapshot`. Chain selection then treats the attacker's chosen block as heavier by `perasWeight params`, potentially causing the honest node to switch to a non-canonical chain. This is a **High** chain-selection manipulation: an unprivileged peer can make an honest node prefer a less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attacker-controlled entry path is the Peras certificate mini-protocol (`processCerts` / `addPerasCertAsync`), reachable from any connected peer. GC is triggered routinely as the immutable tip advances, so GC'd round numbers accumulate over time. The degenerate `validatePerasCert` instance is the production default for all block types lacking a specific override. No special keys, stake majority, or operator access is required.

---

### Recommendation

1. **Separate "seen rounds" from "live certificates"**: maintain a dedicated `pcdsSeenRoundIds :: Set PerasRoundNo` that is never pruned by GC. Use this set — not `pcdsCertIds` — as the deduplication guard in `implAddCert`.

2. **Implement real certificate validation**: replace the degenerate `validatePerasCert` stub with cryptographic and semantic checks (BLS aggregate signature verification, committee membership, round-number bounds) before any certificate is admitted to the DB.

3. **Enforce the invariant at the type level**: consider making `pcdsCertIds` a derived view of `pcdsCertsByTicket` only for weight-snapshot purposes, while keeping a separate immutable set for deduplication.

---

### Proof of Concept

```
1. Node receives cert C1 for round R boosting immutable block B_old (slot S_old).
   → pcdsCertIds = {R}, pcdsCertsByTicket = {t1 → C1}

2. Immutable tip advances past S_old; GC is called with slotNo > S_old.
   → pcdsCertsByTicket' = {} (C1 filtered out)
   → pcdsCertIds' = Set.fromList [] = {}   ← R is gone

3. Attacker sends crafted cert C2 for round R boosting volatile block B_adv.
   processCerts: R ∉ alreadyInDb (getCertIds returns {})
   validatePerasCert C2 → Right (no checks performed)
   implAddCert: R ∉ pcdsCertIds → AddedPerasCertToDB
   → pcdsCertIds = {R}, pcdsCertsByTicket = {t2 → C2}

4. getWeightSnapshot returns boost for B_adv.
   preferAnchoredCandidate: adversarial fragment containing B_adv
   now has higher total weight → node switches to adversarial chain.
```
