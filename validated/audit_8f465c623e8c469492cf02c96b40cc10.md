### Title
Missing BTC Address Validation in `request_refund` Allows Storing Unparseable Refund Address, Causing Stuck Refund State — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` and its callback `request_refund_callback` store a `RefundRequest` with a raw `refund_address` string without ever validating it as a parseable BTC address. When `execute_refund` is later called, `build_refund_output` calls `Address::parse(...).expect("Invalid refund address")`, which panics on an invalid address. The refund request becomes permanently stuck and requires DAO/Operator intervention to reject.

---

### Finding Description

**Entry point — `request_refund` is publicly callable:**

The method lives in a `#[trusted_relayer]`-annotated impl block, but the attribute on the impl block is not a gate for all methods — only methods with `#[trusted_relayer]` on the method itself are gated (e.g., `verify_refund_finalize`, `remove_refund_pending_tx_id`). `request_refund` carries only `#[payable]` and `#[pause(...)]`, making it callable by any account. [1](#0-0) 

**Equality check is not an address validity check:**

`internal_request_refund` checks that `deposit_msg.refund_address` (if set) equals the provided `refund_address`. Passing `deposit_msg.refund_address = Some("invalid_btc_address")` and `refund_address = "invalid_btc_address"` trivially satisfies this check. Alternatively, passing `deposit_msg.refund_address = None` skips the check entirely. Neither path validates that the string is a parseable BTC address. [2](#0-1) 

**`request_refund_callback` stores the raw string without validation:**

After light-client verification succeeds, the callback constructs and persists a `RefundRequest` with the raw `refund_address` string. No address parsing is attempted here. [3](#0-2) 

**`build_refund_output` panics on an invalid address:**

When `execute_refund` is eventually called, it reaches `build_refund_output`, which calls `Address::parse(refund_address, ...).expect("Invalid refund address")`. For an invalid string this panics, aborting the transaction and leaving the `RefundRequest` in storage indefinitely. [4](#0-3) [5](#0-4) 

---

### Impact Explanation

- The `RefundRequest` is permanently stuck in `refund_requests` storage; `execute_refund` will always panic for it.
- The BTC deposit UTXO is not marked `verified_deposit_utxo` (that only happens inside `finalize_refund_with_psbt`, which is never reached), so `verify_deposit` can still be called — but if the relayer is unavailable or the deposit window has passed, the only recovery path is the refund flow, which is now broken.
- DAO/Operator must call `reject_refund` to clean up the stuck request before a legitimate refund can be re-submitted.
- The attacker's 2 NEAR storage deposit is non-refundable (by design), so the cost to the attacker is ~2 NEAR per griefed UTXO.

This matches the **Medium** scope: *attacker-triggered temporary locking of bridged funds requiring operator intervention*.

---

### Likelihood Explanation

- `request_refund` is publicly callable with no role gate.
- The attacker only needs a valid BTC transaction proof (or can target any unfinalized deposit they observe on-chain).
- The attack is cheap (~2 NEAR per request) and requires no special knowledge beyond a valid UTXO.
- The `unsafe_refund_timelock_sec` path (when `deposit_msg.refund_address` is `None`) gives DAO/Operator a longer window to reject, but the window is not guaranteed to be monitored, and the invalid address is not surfaced as an error until `execute_refund` is called.

---

### Recommendation

Validate `refund_address` as a parseable BTC address at the earliest possible point — inside `internal_request_refund`, before the light-client cross-contract call is dispatched:

```rust
// In internal_request_refund, after the equality check:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This ensures the address is rejected at submission time, the attached NEAR deposit is returned (the call reverts), and no stuck state is ever created.
