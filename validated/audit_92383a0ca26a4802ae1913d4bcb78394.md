### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound Peras certificate without performing any cryptographic or committee-membership verification. Because the node-to-node diffusion handler feeds certificates from any connected peer directly through this stub validator, an unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing the victim node to re-run chain selection and potentially switch to a non-canonical fork.

---

### Finding Description

**Root cause — stub validator always returns `Right`:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the only concrete `BlockSupportsPeras` instance (the universal one that covers all block types) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is checked, no committee quorum is verified, no round-number bounds are enforced, and no boosted-block existence is confirmed. Every `PerasCert` value, regardless of content, is wrapped in `ValidatedPerasCert` and returned as valid.

**Attacker-reachable entry path — node-to-node cert diffusion handler:**

In `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`, the `hPerasCertDiffusionClient` handler is wired to `makePerasCertPoolWriterFromChainDB`, which calls `validatePerasCert` on every certificate received from a peer before forwarding it to `ChainDB.addPerasCertAsync`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [2](#0-1) 

Any peer that speaks the `PerasCertDiffusion` mini-protocol can submit certificates. There is no prior authentication gate.

**Downstream effect — chain selection re-run with attacker-controlled weight:**

`ChainDB.addPerasCertAsync` enqueues the accepted certificate for processing by `chainSelSync`. The chain-selection logic then applies the certificate's boost weight to the target block and re-evaluates whether a fork switch is warranted:

```haskell
addPerasCertAsync CDB{cdbTracer, cdbChainSelQueue} =
  addPerasCertToQueue (TraceAddPerasCertEvent >$< cdbTracer) cdbChainSelQueue
``` [3](#0-2) 

The `chainSelSync` handler for `ChainSelAddPerasCert` calls `chainSelectionForBlock` on the boosted block, which uses `preferAnchoredCandidate` with the updated `PerasWeightSnapshot`. Because `wsvTotalWeight` adds the certificate's `vpcCertBoost` (set to `perasWeight params` by the stub) to the block number, a crafted certificate can make a minority-fork block appear heavier than the honest chain tip. [4](#0-3) 

The `WeightedSelectView` comparison used during chain selection is:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

A sufficiently large `perasWeight` value in the injected certificate can override the honest chain's block-number advantage.

---

### Impact Explanation

**Impact: High — chain selection manipulation by an unprivileged peer.**

An attacker who can establish a node-to-node connection (any public peer) can:

1. Craft a `PerasCert` naming any block hash as the boosted block and any round number.
2. Submit it via the `PerasCertDiffusion` mini-protocol.
3. The victim node accepts it unconditionally (stub validator), stores it in `PerasCertDB`, and re-runs chain selection.
4. If the attacker also controls or has pre-seeded the boosted block in the victim's `VolatileDB`, the victim switches to the attacker's fork.

This constitutes a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain, matching the **High** impact tier: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Peras is currently disabled by default on mainnet, but the diffusion handlers and chain-selection code are compiled and wired unconditionally. The vulnerability is fully exploitable on any private testnet or future deployment where Peras is enabled. The attacker requires only a standard peer connection — no keys, no stake, no privileged access. The exploit is deterministic and requires no brute force.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS/committee signature over `(electionId, candidate)`.
2. Confirms the claimed voters form a quorum (total stake ≥ threshold) using the epoch's committee selection data.
3. Checks that the certificate's round number falls within the current or recent epoch window.
4. Confirms the boosted block point exists and is within the volatile window.

Until the real implementation is ready, the `hPerasCertDiffusionClient` handler should refuse to process any inbound certificates (return an error or silently drop them), rather than accepting them through a no-op validator. The analogous vote path already documents this intent with its empty-stake-distribution guard. [6](#0-5) 

---

### Proof of Concept

**Setup:** Private testnet with Peras enabled. Two nodes: honest node H and attacker node A. H's current chain tip is block `B_honest` at block number 100.

**Steps:**

1. A connects to H via the node-to-node protocol and negotiates `PerasCertDiffusion`.
2. A has previously sent (or H has independently received) a valid block `B_fork` at block number 95 on a minority fork; `B_fork` is in H's `VolatileDB`.
3. A crafts:
   ```
   PerasCert { pcCertRound = 999, pcCertBoostedBlock = point(B_fork) }
   ```
4. A sends this cert to H via the `PerasCertDiffusion` mini-protocol.
5. H calls `validatePerasCert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
6. H stores the cert and re-runs chain selection. The fork containing `B_fork` now has total weight `95 + perasWeight` vs. honest chain weight `100 + 0`. If `perasWeight > 5`, H switches to the minority fork.
7. H's selection is now on the attacker-controlled fork, diverging from the honest network.

**Expected (correct) behavior:** Step 5 should fail with a certificate verification error, and H should disconnect from A.

**Observed (buggy) behavior:** The certificate is accepted unconditionally, and chain selection is re-run with attacker-supplied weight.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
