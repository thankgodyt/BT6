### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain Weight Boost and Round Slot Preemption — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` for every input, performing zero cryptographic or structural verification. Any unprivileged peer can send a crafted `PerasCert` for any round number boosting any block of their choice. Because `PerasCertDB` stores at most one certificate per round and silently ignores subsequent ones, the attacker's cert permanently occupies that round's slot before the legitimate cert arrives. The attacker-chosen block then receives a Peras weight boost that influences chain selection, potentially causing honest nodes to prefer a non-canonical fork.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** `BlockSupportsPeras` instance in the codebase (the degenerate catch-all instance). It accepts every `PerasCert` unconditionally, assigning it the full configured Peras weight boost.

**Inbound path — peer-supplied certs reach this stub via `processCerts`:** [2](#0-1) 

The `ObjectPoolWriter` for Peras certificates, wired into the NTN ObjectDiffusion mini-protocol, calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function. Because that function always returns `Right`, every cert from every peer passes.

**First-writer-wins slot preemption — `PerasCertDB` stores one cert per round:** [3](#0-2) 

`AddPerasCertResult` has two constructors: `AddedPerasCertToDB` and `PerasCertAlreadyInDB`. The DB comment explicitly states: *"the two certificates must be identical because certificate equivocation is impossible."* That invariant is violated by the stub — equivocation is trivially possible when no signature is checked.

**Chain selection consequence — the injected cert boosts the attacker's block:** [4](#0-3) 

`addPerasCertAsync` enqueues the accepted cert for chain selection. The resulting `PerasWeightSnapshot` gives the attacker-chosen block a weight boost, which `preferAnchoredCandidate` uses when comparing candidate chains. [5](#0-4) 

**End-to-end exploit path:**

1. Attacker connects as an NTN peer.
2. Attacker crafts a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = B_fork` (a block on a minority fork). `PerasCert` is fully serialisable. [6](#0-5) 
3. The cert is received by `processCerts`, which filters out rounds already in the DB, then calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The cert is stored in `PerasCertDB` for round R and `addPerasCertAsync` triggers chain selection.
5. `PerasWeightSnapshot` now carries a boost for `B_fork`. If `B_fork`'s boosted chain becomes heavier than the honest chain, the node switches.
6. The legitimate cert for round R subsequently arrives but is silently dropped as `PerasCertAlreadyInDB`, permanently locking in the attacker's boost.

---

### Impact Explanation

This is a **bypass of Peras certificate validation** that enables unauthorized Peras weight boosts and chain selection manipulation. An unprivileged peer can preempt any round's certificate slot with a cert boosting an attacker-controlled block. The honest node may then adopt a non-canonical fork that the attacker's cert made heavier. The "first-writer-wins" nature of `PerasCertDB` makes the effect permanent for that round — the legitimate cert is irrecoverably blocked. This falls under the **Critical** allowed impact: *"Bypass of … certificate/signature validation … that enables unauthorized … certificate acceptance"* and the **High** impact: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The attack requires only a standard NTN peer connection and the ability to send a serialised `PerasCert` message via the ObjectDiffusion mini-protocol before the legitimate cert arrives. No cryptographic keys, no stake, and no privileged access are needed. The `PerasCert` type is a plain data structure with no embedded proof of committee membership. Any peer on the network can mount this attack.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's aggregate BLS signature against the claimed committee members and the epoch's stake distribution before the Peras protocol is activated in production. Until then, the `PerasCertDB` assumption that *"certificate equivocation is impossible"* is not upheld, and the first-writer-wins slot preemption is exploitable by any peer.

### Proof of Concept

```
1. Attacker connects as NTN peer to an honest node.

2. Attacker constructs:
     cert = PerasCert
       { pcCertRound        = R          -- any round not yet in DB
       , pcCertBoostedBlock = B_fork     -- a block on a minority fork
       }

3. Attacker sends cert via ObjectDiffusion mini-protocol.

4. Node executes processCerts:
     alreadyInDb = {}  (round R not yet seen)
     certsNotAlreadyInDb = [cert]
     validatePerasCert mkPerasParams cert
       => Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
     addCert (WithArrivalTime now validatedCert)
       => AddedPerasCertToDB

5. addPerasCertAsync enqueues cert; chain selection runs;
   PerasWeightSnapshot now boosts B_fork.

6. Legitimate cert for round R arrives later:
     addCert => PerasCertAlreadyInDB  (silently dropped)

7. Honest node's chain selection permanently uses attacker's boost for round R.
```
