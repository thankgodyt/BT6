### Title
Unpermissioned `new()` Initialization Allows Front-Running to Seize `controller`/`bridge_id` Roles and Mint Arbitrary nBTC — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `nbtc` token contract's `new()` initializer is a public, unpermissioned function that accepts attacker-supplied `controller` and `bridge_id` parameters. If the WASM is deployed without atomically calling `new()` in the same batch transaction, any NEAR account can race to call `new()` first, install themselves as both `controller` and `bridge_id`, and subsequently invoke `mint()` to create arbitrary nBTC tokens.

---

### Finding Description

`contracts/nbtc/src/lib.rs` exposes the following initializer:

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    name: String,
    symbol: String,
    icon: Option<String>,
    decimals: u8,
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    ...
}
``` [1](#0-0) 

The only guard is `!env::state_exists()` — there is no check that `env::predecessor_account_id()` is the contract account itself, a DAO, or any other trusted party. The `controller` and `bridge_id` fields are written verbatim from the caller's arguments.

All privileged operations on the token contract gate on exactly these two fields:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
fn assert_controller(&self) {
    let caller = env::predecessor_account_id();
    require!(caller == self.controller, "ERR_MISSING_PERMISSION");
}
``` [2](#0-1) 

`mint()`, `burn()`, and `safe_mint()` are all gated solely on `assert_bridge()`:

```rust
pub fn mint(&mut self, mint_account_id: AccountId, mint_amount: U128, ...) {
    self.assert_bridge();
    self.mint_inner(&mint_account_id, mint_amount);
    ...
}
``` [3](#0-2) 

`upgrade_and_migrate()` — which redeploys the contract WASM — is gated solely on `assert_controller()`:

```rust
pub fn upgrade_and_migrate(&self) {
    self.assert_controller();
    let code = env::input().unwrap_or_else(|| env::panic_str("ERR_NO_INPUT"));
    let promise_id = env::promise_batch_create(&env::current_account_id());
    env::promise_batch_action_deploy_contract(promise_id, &code);
    ...
}
``` [4](#0-3) 

In NEAR Protocol, deploying a WASM and calling `new()` are two separate actions. They can be batched atomically, but if the deployment transaction does not include the `new()` call in the same batch, a one-block window exists between the deploy landing on-chain and the legitimate operator's initialization transaction. Any account that observes the deploy transaction can submit a `new()` call in the very next block.

No production deployment script is present in the repository that demonstrates atomic deploy+init for the initial deployment of `nbtc`. The only production script (`migrate/create_proposal.sh`) covers upgrades via `upgrade_and_migrate`, not the initial deployment. [5](#0-4) 

The `satoshi-bridge` `new()` function carries the same structural flaw — it is unpermissioned and grants `predecessor_account_id()` full DAO/super-admin rights — but the `nbtc` token contract is the more direct path to unauthorized minting. [6](#0-5) 

---

### Impact Explanation

An attacker who wins the initialization race on `nbtc`:

1. Becomes `bridge_id` → can call `mint()` with any `mint_account_id` and `mint_amount`, creating unbacked nBTC out of thin air.
2. Becomes `controller` → can call `upgrade_and_migrate()` to replace the contract WASM with arbitrary code, permanently compromising the token.
3. Can call `set_controller()` and `set_withdraw_relayer_address()` to lock out the legitimate operator permanently.

This satisfies **Critical — Unauthorized minting of nBTC** and **Critical — Bypass of bridge authorization controls with real security impact**.

---

### Likelihood Explanation

NEAR transactions are publicly visible on-chain the moment they are included in a block. An attacker monitoring the chain for a `DeployContract` action targeting the `nbtc` account can immediately submit a `new()` call in the following block. No special privilege, leaked key, or off-chain coordination is required — only a funded NEAR account and knowledge of the expected token parameters (name, symbol, decimals are all public).

---

### Recommendation

Enforce that `new()` can only be called by the contract account itself (i.e., `env::predecessor_account_id() == env::current_account_id()`), or require the deployer to batch the `DeployContract` action and the `new()` function call in a single NEAR batch transaction. The latter is the standard safe pattern:

```rust
deployer
    .batch(nbtc_account_id)
    .deploy(&wasm_bytes)
    .call(Function::new("new").args_json(init_args))
    .transact()
    .await?;
```

Alternatively, add an explicit permission guard at the top of `new()`:

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

---

### Proof of Concept

1. Legitimate operator submits `DeployContract` for `nbtc.bridge.near` in block N. The transaction lands; the contract has code but no state.
2. Attacker observes block N, constructs a `FunctionCall` to `nbtc.bridge.near::new` with `controller = attacker.near`, `bridge_id = attacker.near`, and submits it in block N+1.
3. Attacker's `new()` call executes first (or races successfully). `env::state_exists()` is `false`, so the check passes. State is written with `controller = attacker.near`, `bridge_id = attacker.near`.
4. Legitimate operator's subsequent `new()` call fails with `"Already initialized"`.
5. Attacker calls `nbtc.bridge.near::mint` from `attacker.near` (satisfying `assert_bridge()`), minting arbitrary nBTC to any recipient. [3](#0-2) [7](#0-6)

    pub fn upgrade_and_migrate(&self) {
        self.assert_controller();

        // Receive the code directly from the input to avoid the
        // GAS overhead of deserializing parameters
        let code = env::input().unwrap_or_else(|| env::panic_str("ERR_NO_INPUT"));
        // Deploy the contract code.
        let promise_id = env::promise_batch_create(&env::current_account_id());
        env::promise_batch_action_deploy_contract(promise_id, &code);
        // Call promise to migrate the state.
        // Batched together to fail upgrade if migration fails.
        env::promise_batch_action_function_call(
            promise_id,
            "migrate",
            b"",
            NO_DEPOSIT,
            env::prepaid_gas()
                .saturating_sub(env::used_gas())
                .saturating_sub(OUTER_UPGRADE_GAS),
        );
        env::promise_return(promise_id);
    }
