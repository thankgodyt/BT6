### Title
Caller-Controlled `refund_address` in `request_refund` Enables BTC Theft When `deposit_msg.refund_address` Is `None` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user deposits BTC without pre-authorizing a refund address (`deposit_msg.refund_address = None`), any unprivileged NEAR account can call `request_refund` and supply an arbitrary attacker-controlled Bitcoin address as `refund_address`. After the `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention, `execute_refund` can be called by anyone, causing the bridge's MPC service to sign and broadcast a Bitcoin transaction sending the deposited BTC to the attacker's address rather than the legitimate depositor.

### Finding Description

`request_refund` is a public, permissionless function callable by any NEAR account. It accepts a `refund_address: String` parameter that is stored verbatim in the `RefundRequest` and later used to construct the Bitcoin output in `build_refund_output`.

The only guard against an arbitrary `refund_address` is a conditional check in `internal_request_refund`: [1](#0-0) 

This check enforces address consistency **only when** `deposit_msg.refund_address` is `Some`. When it is `None` — which is the common case for users who did not pre-authorize a refund destination — the check is entirely skipped, and the caller's supplied `refund_address` is accepted without any ownership or authorization verification.

The `refund_address` is then stored in the `RefundRequest`: [2](#0-1) 

And later used verbatim to construct the Bitcoin output that the MPC service signs: [3](#0-2) 

The only protocol-level mitigation is a longer timelock (`unsafe_refund_timelock_sec`) applied when `deposit_msg.refund_address` is `None`, explicitly designed to give DAO/Operator time to reject suspicious requests: [4](#0-3) 

This is a trust-based, not a cryptographic, defense. If DAO/Operator is offline, slow, or misses the event, the attacker waits out the timelock and calls `execute_refund` to redirect the BTC.

### Impact Explanation

If the attack succeeds, the depositor's BTC is permanently sent to the attacker's Bitcoin address. The bridge's MPC service signs the transaction constructed from the attacker-supplied `refund_address`, and once broadcast and confirmed on Bitcoin, the funds are irrecoverable. This constitutes a **Critical** impact: significant, permanent theft of user funds.

### Likelihood Explanation

The attack requires:
1. A deposit where `deposit_msg.refund_address = None` (common — users who do not pre-authorize a refund address).
2. The relayer failing to call `verify_deposit` (e.g., relayer downtime, network congestion, or the user intentionally not finalizing).
3. The attacker observing the deposit on-chain and reconstructing `deposit_msg` from the `LogDepositAddress` event emitted by `get_user_deposit_address`. [5](#0-4) 

4. DAO/Operator failing to reject the malicious `request_refund` within `unsafe_refund_timelock_sec`.

Steps 1–3 are straightforward for any on-chain observer. Step 4 is the only defense, and it is operationally fragile. Likelihood is **Medium**.

### Recommendation

- Require that `refund_address` is always pre-committed inside `deposit_msg` (i.e., `deposit_msg.refund_address` must be `Some`). Reject `request_refund` calls where `deposit_msg.refund_address` is `None` and the caller is not the original depositor or a privileged role.
- Alternatively, if permissionless refund requests without a pre-authorized address must be supported, require the caller to prove ownership of the `refund_address` (e.g., via a signed message), or restrict `execute_refund` for such requests to DAO/Operator only.
- At minimum, emit a high-priority on-chain event and enforce that `unsafe_refund_timelock_sec` is long enough to guarantee DAO/Operator review before execution.

### Proof of Concept

1. Alice deposits 1 BTC to the bridge address derived from:
   ```json
   { "recipient_id": "alice.near", "refund_address": null }
   ```
   The `LogDepositAddress` event is emitted publicly.

2. The relayer goes offline; `verify_deposit` is never called.

3. Attacker Eve observes the deposit on Bitcoin and the `LogDepositAddress` event on NEAR. She reconstructs `deposit_msg` and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: null },
     refund_address = "bc1q<eve_address>",
     tx_bytes = <alice's deposit tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   The check at `refund.rs:154` is skipped because `deposit_msg.refund_address` is `None`. The `RefundRequest` is stored with `refund_address = "bc1q<eve_address>"`.

4. Eve waits for `unsafe_refund_timelock_sec`. DAO/Operator does not reject.

5. Eve calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying Alice's 1 BTC to Eve's address via `build_refund_output`, the MPC service signs it, and the transaction is broadcast.

6. Alice's 1 BTC is permanently transferred to Eve's Bitcoin address. [6](#0-5) [1](#0-0) [7](#0-6)

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
