Audit Report

## Title
Permanent Token Freeze: `init_transfer` Accepts Funds That `sign_transfer` Will Always Reject Due to Missing Normalization Check — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates only that `fee < amount` before locking user tokens in the bridge contract. `sign_transfer` additionally requires `normalize_amount(amount - fee) > 0`, which fails with integer division when `amount - fee` is below the decimal-normalization divisor. Because `update_transfer_fee` enforces fees can only increase and no cancel/refund path exists, any transfer accepted by `init_transfer` whose net amount normalizes to zero results in permanently frozen funds with no recovery.

## Finding Description

**Constraint 1 — `init_transfer` (L554–557):**

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

This is the only fee validation at initiation time. Any positive `amount − fee` passes. Tokens are immediately locked/burned in `init_transfer_internal` (L1850–1857). [1](#0-0) [2](#0-1) 

**Constraint 2 — `sign_transfer` (L475–485):**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` performs integer floor division by `10^(origin_decimals - decimals)`. For a token with 24 NEAR-side decimals and 6 destination decimals, the divisor is `10^18`. Any `amount − fee < 10^18` yields `0` and causes a permanent panic. [3](#0-2) [4](#0-3) 

**No recovery path:**

`update_transfer_fee` enforces `fee.fee >= current_fee.fee`, so fees can only increase, making `amount − fee` smaller. There is no public cancel or refund function. `sign_transfer_callback` only removes the pending transfer when `fee.is_zero()` — which is not the case here. `claim_fee` requires a proof of finalization from the destination chain, which is impossible since `sign_transfer` never succeeds. [5](#0-4) [6](#0-5) 

## Impact Explanation

User tokens are transferred to the bridge contract during `ft_on_transfer` → `init_transfer` → `init_transfer_internal`. For deployed tokens they are burned; for native tokens they are held by the bridge. In both cases, `sign_transfer` permanently reverts with `ERR_INVALID_AMOUNT_TO_TRANSFER`, no cross-chain message is ever signed, and no finalization proof can be generated. The funds are irrecoverably frozen. This matches the critical impact: **permanent freezing of bridged funds**. [7](#0-6) 

## Likelihood Explanation

The condition is reachable by any unprivileged user on any token where `origin_decimals > decimals` — a standard configuration (e.g., USDC: 24 NEAR-side vs. 6 Ethereum-side, divisor `10^18`). A user who sets a fee such that `amount − fee < 10^18` — plausible when trying to maximize relayer incentive on a small transfer — will trigger the deadlock. No special role, key, or external condition is required beyond initiating a standard outbound transfer via `ft_transfer_call`. [8](#0-7) 

## Recommendation

Add the normalization check inside `init_transfer`, before tokens are locked, mirroring the check already present in `sign_transfer`:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This ensures any transfer whose net amount normalizes to zero is rejected before funds are locked.

## Proof of Concept

1. Token has 24 decimals on NEAR, 6 on Ethereum → divisor = `10^18`.
2. User calls `ft_transfer_call` with `amount = 2 × 10^18`, `fee = 10^18 + 1`.
3. `init_transfer`: `10^18 + 1 < 2 × 10^18` → **passes**. Tokens locked in bridge.
4. Relayer calls `sign_transfer`.
5. `amount_without_fee() = 10^18 − 1`.
6. `normalize_amount(10^18 − 1) = (10^18 − 1) / 10^18 = 0` (integer division).
7. `require!(0 > 0)` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
8. User's `2 × 10^18` tokens are permanently frozen. `update_transfer_fee` can only increase the fee, worsening the situation. No cancel path exists. [4](#0-3) [9](#0-8)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
