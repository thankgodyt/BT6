### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Allows Unprivileged Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance, which applies to all block types via a catch-all `StandardHash blk =>` constraint, implements `validatePerasCert` as a stub that unconditionally returns `Right` — i.e., it accepts every certificate without performing any cryptographic or structural validation. Similarly, `validatePerasVote` only checks stake-distribution membership and skips signature verification entirely. When Peras is enabled, an unprivileged peer can submit a crafted certificate (or enough crafted votes to forge one) that boosts any block already in the VolatileDB, causing the honest node's chain selection to prefer a non-canonical chain.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all instance reads:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }

  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

`validatePerasCert` wraps any incoming `PerasCert` in `ValidatedPerasCert` unconditionally. `validatePerasVote` only checks that the claimed voter ID appears in the stake distribution; it does not verify any cryptographic signature, so an attacker who knows a legitimate voter ID can impersonate that voter.

These `Validated*` wrappers are the gatekeepers used throughout the chain-selection path. In `ChainSel.hs`, `chainSelSync` for `ChainSelAddPerasCert` calls `PerasCertDB.addCert` with the already-`Validated` certificate and then triggers `chainSelectionForBlock` for the boosted block:

```haskell
certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
...
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
```

The weight snapshot from `PerasCertDB.getWeightSnapshot` is then fed into `preferAnchoredCandidate` / `compareChainDiffs` during every chain-selection run, so a fraudulent certificate's boost is applied to every subsequent candidate comparison.

---

### Impact Explanation

An unprivileged peer can:

1. Deliver a valid block `B` (passes all existing header and ledger validation) so that `B` lands in the VolatileDB.
2. Craft a `PerasCert` claiming to certify `B` for any round, with any content — no signature is checked.
3. Submit the certificate via the Peras miniprotocol. `validatePerasCert` returns `Right` unconditionally, producing a `ValidatedPerasCert` that is stored in `PerasCertDB` and reflected in the weight snapshot.
4. Chain selection now assigns `B` a Peras weight boost (`vpcCertBoost = perasWeight params`). If this boost is sufficient to make the chain ending at `B` preferred over the honest chain, the node switches to the attacker's fork.

Alternatively, the attacker can impersonate legitimate voters (knowing only their IDs, not their keys) to accumulate enough stake-weighted votes to trigger `AddedPerasVoteAndGeneratedNewCert`, which internally calls `forgePerasCert` (also a stub that always succeeds) and then `addPerasCertAsync`, achieving the same outcome without even needing a pre-crafted certificate.

This is a direct analog to the reported "immediate permissionless finalization": just as anyone could call `finalize_block` without a challenge period, here anyone can submit a certificate that immediately and unconditionally boosts a block in chain selection, bypassing the quorum and cryptographic requirements that are the entire security basis of the Peras weight mechanism.

Impact class: **Critical — Bypass of Peras certificate/vote verification that enables unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

Peras is disabled by default (`"Note that if Peras is disabled (which is the default), there is no observable difference"`), so the attack surface is limited to nodes that explicitly enable Peras. However, the degenerate instance is present in production source files (not test or benchmark code), applies to all block types via the catch-all constraint, and is the only instance in scope for Cardano blocks unless a more specific instance is added. Any operator or testnet deployment that enables Peras is immediately vulnerable. The attack requires no special privileges, no stake, and no cryptographic material beyond knowledge of a voter ID in the stake distribution.

---

### Recommendation

1. Remove or guard the catch-all `instance StandardHash blk => BlockSupportsPeras blk` so that it cannot be used for production block types without an explicit, fully-validated instance.
2. Implement `validatePerasCert` to verify the certificate's cryptographic proof (committee VRF/signature) before wrapping it in `ValidatedPerasCert`.
3. Implement `validatePerasVote` to verify the vote's cryptographic signature, not merely the voter's presence in the stake distribution.
4. Until full validation is implemented, gate the Peras code paths so that `addPerasCertAsync` and `addPerasVoteWithAsyncCertHandling` are unreachable when Peras is disabled, preventing accidental exposure.

### Proof of Concept

**Setup**: A private testnet with Peras enabled (non-default configuration).

**Steps**:

1. Observe a block `B` (hash `H`, slot `S`) arrive in the VolatileDB of the target node.
2. Construct a `PerasCert` value:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = BlockPoint S H }
   ```
3. Submit this certificate to the target node via the Peras certificate miniprotocol.
4. `validatePerasCert` is called; because the degenerate instance always returns `Right`, the certificate is stored in `PerasCertDB` with boost weight `perasWeight params`.
5. `chainSelectionForBlock` is triggered for `B`; `preferAnchoredCandidate` now sees `B`'s chain as heavier than the honest chain by `perasWeight params`.
6. The node switches its selection to the chain ending at `B`.
