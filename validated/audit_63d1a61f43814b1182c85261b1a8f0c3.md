## Title
`is_refund_required` Returns `false` on Promise Failure, Permanently Locking Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
When `ft_transfer_call` or `ft_transfer` dispatched by `send_tokens` fails with a NEAR promise error, `is_refund_required` returns `false` via the `Err(_) => false` branch, causing `fin_transfer_send_tokens_callback` to take the success path. This skips `revert_lock_actions` and `remove_fin_transfer`, leaving `locked_tokens` permanently under-counted and the finalization record permanently set, with no on-chain recovery path for the user's funds.

## Finding Description
The `process_fin_transfer_to_near` function performs three state mutations before dispatching the token transfer:

1. `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (replay prevention).
2. `unlock_tokens_if_needed` decrements `locked_tokens[(origin_chain, token)]` and records a `LockAction::Unlocked`.
3. `send_tokens` dispatches `ft_transfer_call` (non-empty `msg`) or `ft_transfer` (empty `msg`) to the token contract.

The callback `fin_transfer_send_tokens_callback` calls `is_refund_required(is_ft_transfer_call)` to decide whether to clean up:

```rust
// near/omni-bridge/src/lib.rs L1784-1804
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    amount.0 == 0
                } else {
                    false  // Unexpected case: don't refund
                }
            }
            Err(_) => false,  // BUG: promise failure treated as success
        }
    } else {
        false  // ft_transfer path: never refunds regardless of outcome
    }
}
```

**`ft_transfer_call` path (`is_ft_transfer_call = true`):** If the token contract panics (e.g., paused, minimum-amount guard, gas exhaustion), NEAR returns a `Failed` promise result. `env::promise_result_checked` returns `Err(_)`, and `is_refund_required` returns `false`. The callback takes the success branch: `revert_lock_actions` is not called, `remove_fin_transfer` is not called, and `FinTransferEvent` is emitted. The tokens remain in the bridge's account (NEAR atomically reverts the failed cross-contract call), but the finalization record blocks any re-submission.

**`ft_transfer` path (`is_ft_transfer_call = false`):** `is_refund_required` unconditionally returns `false` regardless of the promise outcome. If `ft_transfer` fails, the same broken state results.

The only admin function that touches `locked_tokens` is `set_locked_tokens` (DAO/TokenLockController role), which can correct the accounting. However, there is no public or privileged function to remove an entry from `finalised_transfers`. `remove_fin_transfer` is a private internal function called only from `fin_transfer_send_tokens_callback` when `is_refund_required` returns `true`. Without a contract upgrade, the finalization record cannot be cleared, and the user cannot re-submit the transfer.

## Impact Explanation
For non-deployed (locked) tokens bridging back to NEAR:
- **Permanent fund freeze**: Tokens remain in the bridge's account. The finalization record in `finalised_transfers` blocks re-submission with `BridgeError::TransferAlreadyFinalised`. No admin escape hatch exists to remove the record without a contract upgrade.
- **Escrow mis-accounting**: `locked_tokens[(origin_chain, token)]` is permanently decremented below the bridge's actual token balance. Over time, this allows the bridge to over-unlock tokens on future transfers, breaking the escrow invariant and enabling effective theft of other users' locked funds.
- **False success event**: `FinTransferEvent` is emitted, misleading off-chain relayers and indexers.

This matches the Critical allowed impact classes: permanent freezing of bridged funds and balance/escrow mis-accounting that changes user and protocol balances.

## Likelihood Explanation
The `Err` branch is reachable by any unprivileged user whose transfer coincides with a condition that causes the destination token contract to panic. No attacker privilege is required. Concrete realistic triggers include: a token contract with a pause mechanism (common in production NEP-141 tokens) being paused between proof submission and callback execution; a minimum-transfer-amount guard rejecting the bridged amount; gas exhaustion inside the token contract's `ft_transfer_call` logic; or a token contract upgrade between proof submission and callback. These are all normal operational conditions, not adversarial constructions.

## Recommendation
Change the `Err` branch in `is_refund_required` to return `true`, treating a failed promise as requiring cleanup:

```rust
Err(_) => true,  // Promise failure: treat as refund-required
```

Additionally, the `else { false }` branch for unparseable `Ok` results should also return `true` for the same reason. For the `ft_transfer` path (`is_ft_transfer_call = false`), the callback should check the promise result and trigger cleanup on failure, rather than unconditionally taking the success path. A dedicated admin function to remove a finalization record (with appropriate access control) should also be added as a recovery mechanism.

## Proof of Concept
1. Deploy a NEP-141 token contract with a `pause` function. Register it as a non-deployed (locked) token in the bridge. Pre-populate `locked_tokens[(Eth, token)]` with a sufficient balance.
2. A user initiates a cross-chain transfer from Ethereum to a NEAR recipient with a non-empty `msg` field, producing a valid proof.
3. Before the relayer calls `fin_transfer`, pause the token contract.
4. The relayer calls `fin_transfer` with the valid proof. `process_fin_transfer_to_near` executes: `add_fin_transfer` inserts the transfer ID into `finalised_transfers`; `unlock_tokens_if_needed` decrements `locked_tokens`; `send_tokens` dispatches `ft_transfer_call` to the paused token contract.
5. The token contract panics (paused). The promise result is `Failed`. NEAR atomically reverts the token transfer; tokens remain in the bridge.
6. `fin_transfer_send_tokens_callback` is invoked. `is_refund_required(true)` hits `Err(_) => false` and returns `false`.
7. The callback takes the success path: `revert_lock_actions` is skipped, `remove_fin_transfer` is skipped, `FinTransferEvent` is emitted.
8. Observable state: `is_transfer_finalised(transfer_id)` returns `true` (blocking re-submission); `get_locked_tokens(Eth, token)` returns a value lower than the bridge's actual token balance; the user has not received any tokens; no on-chain recovery path exists without a contract upgrade.

A unit test can reproduce this by calling `fin_transfer_send_tokens_callback` directly with `is_ft_transfer_call = true` and a `PromiseResult::Failed` in the mock environment, then asserting that `locked_tokens` is unchanged and `is_transfer_finalised` returns `false` — both assertions will fail against the current code.
