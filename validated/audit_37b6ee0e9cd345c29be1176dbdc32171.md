### Title
`safe_mint` permanently locks nBTC tokens in the bridge contract when the recipient account is unregistered — (`contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nbtc contract unconditionally mints tokens to `bridge_id` first, then checks whether the intended recipient is registered. If the recipient has no storage account, the function silently returns `U128(0)` without burning the already-minted tokens, without adding them to any recovery map, and without emitting any event. The minted nBTC is permanently stranded in the bridge contract's own token balance with no on-chain path to recover it.

---

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` executes in this order:

1. **Mint unconditionally to `bridge_id`** (line 112):
   ```rust
   self.token.internal_deposit(&self.bridge_id, amount.into());
   ```
2. **Check recipient registration** (lines 114–116):
   ```rust
   if self.token.accounts.get(&account_id).is_none() {
       return PromiseOrValue::Value(U128(0));
   }
   ```
3. **Transfer to recipient** (lines 118–123) — only reached if the account exists.

When the recipient is unregistered the function returns early at step 2. The tokens minted in step 1 remain in `bridge_id`'s nbtc balance. No rollback (`internal_withdraw`) is performed, no entry is written to the bridge contract's `lost_found` map, and no event is emitted. The bridge contract's accounting fields (`cur_available_protocol_fee`, `acc_collected_protocol_fee`, etc.) are also untouched, so the stranded balance is invisible to any existing operator tooling. [1](#0-0) 

The `lost_found` map in the bridge contract is only populated by `transfer_nbtc_callback` when an outbound `ft_transfer` fails — it is never populated by the `safe_mint` early-return path. [2](#0-1) 

The bridge contract's protocol-fee accounting fields track only explicitly collected fees; stranded `safe_mint` tokens are not reflected there either. [3](#0-2) 

---

### Impact Explanation

Every call to `safe_mint` where the recipient NEAR account has not registered storage with the nbtc contract causes the corresponding nBTC amount to be minted into `bridge_id`'s token balance and then abandoned. Because the bridge contract has no function that specifically targets and recovers these untracked tokens, they are effectively permanently locked. The circulating nBTC supply is inflated relative to the amount actually held by users, breaking the 1:1 BTC-backing invariant without a corresponding burn. Recovery requires a manual DAO upgrade or a bespoke operator action against an untracked balance — i.e., stuck bridge state requiring operator intervention.

**Allowed impact matched:** *Medium — broken callback rollback; stuck bridge state requiring operator intervention.*

---

### Likelihood Explanation

`safe_mint` is the integration path used by Omni Bridge and similar dApps. Any deposit routed through that path where the recipient NEAR account has not called `storage_deposit` on the nbtc contract will trigger the bug. This is a realistic and recurring condition: new users bridging for the first time via an aggregator often have not pre-registered with the underlying token contract. No attacker action is required; ordinary user behaviour is sufficient.

---

### Recommendation

Before returning `U128(0)`, burn the already-minted tokens so the supply remains consistent:

```rust
if self.token.accounts.get(&account_id).is_none() {
    // Roll back the mint — recipient is not registered.
    self.token.internal_withdraw(&self.bridge_id, amount.into());
    return PromiseOrValue::Value(U128(0));
}
```

Alternatively, write the stranded amount into the bridge contract's `lost_found` map (requires a cross-contract callback) so that operators can detect and recover it, and emit a `LostFoundNbtc`-style event for observability.

---

### Proof of Concept

1. Alice deposits BTC to a bridge address derived from her NEAR account `alice.near`.
2. `alice.near` has never called `storage_deposit` on the nbtc contract.
3. The relayer calls `verify_deposit`; the bridge calls `safe_mint(alice.near, 100_000, None)`.
4. `internal_deposit(&bridge_id, 100_000)` executes — 100 000 satoshis of nBTC are minted to `bridge_id`.
5. `self.token.accounts.get(&alice.near)` returns `None`.
6. `safe_mint` returns `U128(0)` immediately.
7. `bridge_id`'s nbtc balance is now 100 000 units higher than any accounting field tracks.
8. Alice receives no nBTC. The bridge has no record of the stranded tokens. No event is emitted. The tokens cannot be recovered without a manual DAO intervention. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
```
