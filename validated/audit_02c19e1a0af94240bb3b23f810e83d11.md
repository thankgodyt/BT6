### Title
`validatePerasCert` Unconditionally Accepts All Inbound Peras Certificates While `validatePerasVote` Has a Validation Guard — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right` — it accepts every certificate without any check — while `validatePerasVote` at least performs a stake-distribution lookup before accepting a vote. Both functions are wired into the live node-to-node protocol handlers (`hPerasCertDiffusionClient`). An unprivileged peer can therefore send arbitrarily crafted Peras certificates that bypass all validation, are stored in the `PerasCertDB`, and trigger chain-selection for any block the adversary names as the "boosted" block.

---

### Finding Description

**Root cause — missing validation guard in `validatePerasCert`**

The universal instance of `BlockSupportsPeras` (the only instance in the codebase) defines:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of content, is wrapped in `Right` and returned as `ValidatedPerasCert`. No cryptographic check, no round-number sanity check, no boosted-block existence check, nothing.

**Contrast with `validatePerasVote`**

The sibling function in the same instance does perform a guard:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

A vote is rejected if the voter is absent from the stake distribution. The production wiring in `NodeToNode.hs` even passes an empty stake distribution (`pure (PerasVoteStakeDistr mempty)`), so every inbound vote is rejected. Certificates have no equivalent guard and are always accepted. [3](#0-2) 

**Attacker-controlled entry path**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`: [4](#0-3) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, calls `addCert` (which is `ChainDB.addPerasCertAsync`): [5](#0-4) 

`addPerasCertAsync` feeds the certificate into `chainSelSync`, which stores it in `PerasCertDB` and then calls `chainSelectionForBlock` for the block named in the certificate's `pcCertBoostedBlock` field: [6](#0-5) 

The full path from an unauthenticated peer message to chain-selection is therefore:

```
peer sends PerasCert message
  → objectDiffusionInbound (NodeToNode.hs hPerasCertDiffusionClient)
  → makePerasCertPoolWriterFromChainDB.opwAddObjects
  → processCerts … (validatePerasCert mkPerasParams)   ← always Right
  → ChainDB.addPerasCertAsync
  → chainSelSync / chainSelectionForBlock
```

---

### Impact Explanation

**Severity: Critical — bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

A peer with no stake and no valid keys can craft a `PerasCert` naming any block hash as `pcCertBoostedBlock`. Because `validatePerasCert` always returns `Right`, the certificate is stored and chain selection is triggered for that block. If the adversary has previously diffused a competing header chain whose tip is the named block, the Peras weight boost from the fake certificate may cause the honest node to prefer that chain over the canonical one, constituting a chain-selection safety failure driven entirely by unauthenticated network input.

This maps directly to the allowed impact: *"Critical. Bypass of … certificate/signature validation … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is wired into the live node-to-node handler set (`hPerasCertDiffusionClient`) and is reachable by any peer that negotiates a node-to-node version supporting it. No privilege, stake, or key material is required. The adversary only needs to connect to the target node and send a well-formed CBOR-encoded `PerasCert` message. The inconsistency (votes rejected, certificates accepted) means the missing guard is not a symmetric placeholder — it is a structural omission.

---

### Recommendation

Replace the stub `validatePerasCert` body with real validation before the Peras certificate diffusion protocol is enabled in production. At minimum, the implementation must:

1. Verify the aggregate BLS/KES signature over the certificate's `(electionId, candidate)` pair against the committee's aggregate verification key.
2. Verify that each claimed voter seat index is within bounds and has non-zero stake.
3. Verify that the certificate's round number is within the acceptable window relative to the current chain tip.
4. Verify that `pcCertBoostedBlock` refers to a block that actually exists on a known chain fragment.

Until real validation is in place, the certificate diffusion handler should be disabled or the `validatePerasCert` stub should return `Left PerasValidationErr` unconditionally (mirroring the effective behaviour of `validatePerasVote` with an empty stake distribution) to prevent unauthenticated certificates from influencing chain selection.

---

### Proof of Concept

1. Connect to a target node that has the Peras certificate diffusion protocol enabled.
2. Craft a `PerasCert` with `pcCertRound = 1` and `pcCertBoostedBlock` set to the hash of a block on a competing fork that the adversary has already diffused via ChainSync.
3. Send the certificate via the `ObjectDiffusion` mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{…}` unconditionally.
5. `ChainDB.addPerasCertAsync` stores the certificate and calls `chainSelectionForBlock` for the adversary-chosen block.
6. If the adversary's fork now has greater Peras-weighted chain order than the honest chain, the node switches to the adversarial fork — a chain-selection safety failure triggered by a single unauthenticated network message.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
