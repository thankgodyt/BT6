### Title
`safe_mint` Mints Tokens to Bridge Before Checking Destination Registration, Causing Permanent Token Lockup When Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

`safe_mint` in the nbtc contract performs an irreversible `internal_deposit` to `bridge_id` **before** checking whether the destination `account_id` is registered. If the account is unregistered, the function silently returns `U128(0)` without reverting. Because this is a cross-contract call from the bridge, the nbtc state mutation cannot be rolled back by the bridge's callback, leaving the minted tokens permanently stranded in the bridge's own account while the user's BTC deposit is consumed.

---

### Finding Description

The two-step sequence inside `safe_mint` is:

```rust
// Step 1 — irreversible state mutation
self.token.internal_deposit(&self.bridge_id, amount.into());

// Step 2 — guard that should have come first
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));   // silent early-return, no revert
}
``` [1](#0-0) 

`internal_deposit` writes directly to the nbtc contract's on-chain storage. In NEAR's asynchronous execution model, state changes made inside a callee contract are committed to that contract's shard independently of what the caller's callback does. Even if the bridge's callback panics upon receiving `U128(0)`, the nbtc contract's storage is **not** rolled back. The `amount` tokens are now credited to `bridge_id` with no corresponding transfer to the user and no entry in the `lost_found` ledger. [2](#0-1) 

The `lost_found` recovery path is only wired into `transfer_nbtc_callback`; `safe_mint` has no equivalent safety net. [3](#0-2) 

---

### Impact Explanation

**Stuck / permanently locked user funds (Medium → Critical depending on bridge callback behaviour).**

- The user's BTC deposit UTXO is consumed by the bridge (marked verified on the Bitcoin light-client side).
- The user receives zero nBTC.
- The minted tokens accumulate silently in `bridge_id`'s nbtc balance with no automated recovery path.
- If the bridge callback does *not* panic on `U128(0)` (i.e., it treats 0 as a successful no-op), the deposit is also marked verified on the NEAR side, making the loss permanent and unrecoverable without DAO intervention.
- If the bridge callback *does* panic, the bridge-side deposit state is reverted but the nbtc tokens remain minted to the bridge — a supply/accounting divergence that grows with every such failed deposit. [1](#0-0) 

---

### Likelihood Explanation

Any user who deposits BTC to a bridge-derived address without first registering their NEAR account in the nbtc contract triggers this path. NEP-141 storage registration is a separate, explicit step (`storage_deposit`) that many users omit, especially when interacting through third-party integrations or scripts. The `safe_mint` entrypoint is specifically documented as the path used by integrations such as Omni Bridge, making cross-integration deposits with unregistered receiver accounts a realistic production scenario. [4](#0-3) 

---

### Recommendation

Move the registration guard **before** the `internal_deposit` call, or replace the silent early-return with an explicit `env::panic_str` / `require!` so the entire NEAR transaction (including the nbtc state mutation) is atomically reverted:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Guard FIRST — before any state mutation
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    // Only mint once we know the destination can receive
    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
}
```

Alternatively, panic instead of returning 0 so the bridge's cross-contract call fails cleanly and the bridge can handle the failure in its callback without a stranded token balance.

---

### Proof of Concept

1. Alice deposits 0.01 BTC to her bridge-derived address on Bitcoin.
2. Alice has **not** called `storage_deposit` on the nbtc contract; her account is unregistered.
3. The relayer submits the Merkle inclusion proof; the bridge verifies it and calls `safe_mint("alice.near", 1_000_000, None)` on the nbtc contract.
4. nbtc executes `internal_deposit(&bridge_id, 1_000_000)` — 1 000 000 satoshi-units are now credited to the bridge's own nbtc balance.
5. nbtc checks `accounts.get("alice.near")` → `None` → returns `U128(0)`.
6. The bridge's callback receives `U128(0)`. Regardless of whether it panics or succeeds:
   - **Panic path:** bridge-side deposit state is reverted, but nbtc tokens remain minted to bridge (supply inflation, stuck funds).
   - **Success path:** deposit is marked verified, Alice's BTC is permanently locked, she holds zero nBTC.
7. No `lost_found` entry is created; no automated recovery exists. DAO manual intervention is required. [3](#0-2) [2](#0-1)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
