### Title
Peras Vote and Certificate Signature Verification Bypass Allows Unauthorized Vote Injection and Fraudulent Chain Boosting - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` performs no cryptographic signature verification — it only checks that the claimed voter ID exists in the stake distribution. The `PerasVote blk` data type carries no signature field at all. Any unprivileged peer can craft a vote claiming to be any registered stake pool, inject it via the object diffusion mini-protocol, and have it accepted into the `PerasVoteDB`. If enough such fake votes are injected for the same target, a fraudulent `PerasCert` is forged and accepted, causing chain selection to boost a non-canonical chain. `validatePerasCert` unconditionally returns `Right` for every certificate, compounding the issue.

---

### Finding Description

**Root cause — missing signature field and no cryptographic check in `validatePerasVote`:**

The degenerate `BlockSupportsPeras blk` instance (explicitly marked as the production instance for all block types until concrete Cardano plumbing is in place) defines `PerasVote blk` with three fields:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- just a KeyHash StakePool
  }
```

There is no signature field. [1](#0-0) 

The `validatePerasVote` implementation only looks up the voter ID in the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` is a pure `Map.lookup` on the voter ID — no cryptographic check of any kind. [3](#0-2) 

`validatePerasCert` unconditionally returns `Right` for every certificate without any checks:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

**Production entry path — object diffusion mini-protocol:**

Both `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` call `processVotes` with `validatePerasVote mkPerasParams sd vote` as the validation function. [5](#0-4) 

`processVotes` receives inbound votes from peers, calls the stub validator, and on success adds them to the `PerasVoteDB` via `ChainDB.addPerasVoteWithAsyncCertHandling`. [6](#0-5) 

Similarly, `makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` — the unconditional `Right` stub. [7](#0-6) 

**Exploit flow:**

1. Attacker connects to a node as an unprivileged peer via the object diffusion mini-protocol.
2. Attacker reads the current stake distribution (public information) to enumerate registered pool IDs.
3. Attacker crafts `PerasVote` messages with `pvVoteVoterId` set to legitimate pool key hashes, targeting a chosen block.
4. `processVotes` calls `validatePerasVote`; the stub accepts each vote because the voter ID exists in the stake distribution.
5. Votes accumulate in `PerasVoteDB`. When `votesReachQuorum` is satisfied with fake votes, `forgePerasCert` is called and a fraudulent `PerasCert` is produced.
6. The fraudulent certificate is added to the `ChainDB` and triggers chain selection with a boost weight, causing the node to prefer a non-canonical chain.

The concrete `Peras.Vote.V1.PerasVote` type (used by `WFALS`/`EveryoneVotes` committee implementations) does carry a `pvSignature` field and proper verification. [8](#0-7)  However, the production diffusion path uses the `BlockSupportsPeras blk` associated type, which is the signature-less stub. [9](#0-8) 

---

### Impact Explanation

**Critical. Bypass of Peras vote and certificate verification that enables unauthorized vote acceptance and fraudulent certificate creation.**

An unprivileged peer can impersonate any registered stake pool's vote without possessing its private key. By injecting enough fake votes to reach quorum, the attacker causes the node to forge and accept a fraudulent `PerasCert` that boosts a non-canonical chain. This directly violates the Peras protocol's chain-selection security guarantee: the boost weight from a fraudulent certificate causes an honest node to irreversibly prefer a weaker or attacker-controlled chain over the canonical one. This is a consensus safety failure reachable from any peer connection.

---

### Likelihood Explanation

**High.** The object diffusion mini-protocol is an externally reachable network endpoint. The stake distribution is public. The attacker needs only to know registered pool key hashes (trivially obtained from the ledger state) and send crafted `PerasVote` messages. No keys, credentials, or privileged access are required. The stub validation is wired into both the `PerasVoteDB`-backed and `ChainDB`-backed production writers.

---

### Recommendation

1. Add a cryptographic signature field to the `PerasVote blk` associated data type in the `BlockSupportsPeras` instance, mirroring the `pvSignature` field in `Peras.Vote.V1.PerasVote`.
2. Implement `validatePerasVote` to verify the BLS signature against the voter's public key (derived from the pool's registered VRF/cold key), not merely check stake distribution membership.
3. Implement `validatePerasCert` to verify the aggregate signature over the claimed voter set before returning `Right`.
4. Until these checks are implemented, gate the object diffusion inbound path for Peras votes and certificates so that it is not reachable from untrusted peers.

---

### Proof of Concept

```
1. Connect to a node as a peer via the object diffusion mini-protocol.
2. Query the ledger state to obtain the PerasVoteStakeDistr (public).
3. For each registered pool ID P_i with stake s_i:
     Craft PerasVote { pvVoteRound = R, pvVoteBlock = B, pvVoteVoterId = P_i }
     Send to the node via the object diffusion inbound handler.
4. processVotes calls validatePerasVote for each vote.
   validatePerasVote succeeds for every P_i present in the stake distribution
   (no signature check; PerasVote carries no signature field).
5. Votes accumulate in PerasVoteDB. Once sum(s_i) >= quorum threshold,
   votesReachQuorum returns Just, forgePerasCert is called, and a PerasCert
   boosting block B in round R is produced and added to the ChainDB.
6. Chain selection applies the boost weight from the fraudulent certificate,
   causing the node to prefer the attacker-chosen chain over the canonical one.
```

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
