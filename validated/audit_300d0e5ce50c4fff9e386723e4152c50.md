### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or committee-membership checks. Because this function is the sole validation gate in the production inbound Peras certificate diffusion path, any unprivileged peer can send a crafted `PerasCert` pointing to an arbitrary block, have it accepted as a `ValidatedPerasCert` with full boost weight, and cause the receiving node's chain-selection logic to artificially prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

In `SupportsPeras.hs`, the only `BlockSupportsPeras` instance (the universal `StandardHash blk =>` instance, explicitly marked "degenerate instance for all blks to get things to compile") implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This always returns `Right`, wrapping the caller-supplied `cert` verbatim with the full configured boost weight, regardless of whether the certificate carries valid committee signatures, a valid VRF proof, a legitimate quorum, or even a plausible round number.

**Production wiring — the stub is the live inbound validator:**

`makePerasCertPoolWriterFromChainDB` in `ObjectPool/PerasCert.hs` constructs the production inbound pool writer and passes `validatePerasCert mkPerasParams` directly as the validation callback:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
```

This writer is wired into the live `hPerasCertDiffusionClient` handler in `NodeToNode.hs`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
```

**Inbound processing — no rejection path exists:**

`processCerts` in `ObjectPool/PerasCert.hs` calls `validateCert` on each received certificate and only rejects a batch when at least one `Left` is returned. Because `validatePerasCert` never returns `Left`, every certificate from every peer passes:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
```

**Chain-selection consequence:**

Once accepted, the certificate is forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. `chainSelSync` in `ChainSel.hs` then adds the cert to `PerasCertDB`, updates the `PerasWeightSnapshot`, and re-runs chain selection for the boosted block. Chain selection uses `WeightedSelectView`, which compares `wsvTotalWeight = blockNo + weightBoost`. A crafted certificate can therefore inflate the weight of any block in the VolatileDB, making a non-canonical fork appear heavier than the honest chain.

### Impact Explanation

An unprivileged peer can submit a `PerasCert` that:
1. Names any block in the receiving node's VolatileDB as `pcCertBoostedBlock`.
2. Claims any `pcCertRound` not yet present in the `PerasCertDB` (one cert per round is accepted).
3. Receives the full `perasWeight` boost unconditionally.

Because `wsvTotalWeight` drives `preferCandidate` in `WeightedSelectView`, a sufficiently large boost can cause the node to switch away from the honest chain to a fork that would otherwise be rejected. This is a **chain-selection integrity failure** triggered entirely by a crafted network message from an unprivileged peer, matching the "High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" impact category.

### Likelihood Explanation

The attack requires only a standard node-to-node connection and knowledge of a block hash in the target node's VolatileDB (obtainable via ChainSync). No keys, stake, or privileged access are needed. The `PerasCertDiffusion` mini-protocol is enabled for `NodeToNodeV_16` and is wired unconditionally in the production `mkHandlers` path. The only natural limit is the one-cert-per-round constraint in `PerasCertDB`, but an attacker can exhaust many rounds by sending one crafted cert per round.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real check before the Peras certificate diffusion path is active in production. At minimum, the validation must verify:
- Committee membership and quorum (sufficient aggregate stake from eligible voters).
- Cryptographic signatures (aggregate BLS / VRF proofs as defined by the committee scheme).
- Round-number plausibility relative to the current slot.

Until real validation is implemented, the `hPerasCertDiffusionClient` handler should either be disabled (gated behind a feature flag that is off by default) or `processCerts` should be made to reject all inbound certificates unconditionally when the stub is in place. The analogous `validatePerasVote` stub has a partial guard (it rejects votes whose voter ID is absent from the stake distribution), but `validatePerasCert` has no guard at all.

### Proof of Concept

1. Attacker connects to a target node via the `PerasCertDiffusion` ObjectDiffusion mini-protocol (NodeToNodeV_16).
2. Attacker learns a block hash `H` at slot `S` from the target's VolatileDB via ChainSync.
3. Attacker constructs `PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint S H }` for any round `R` not yet in the target's `PerasCertDB`.
4. Attacker sends the cert via the ObjectDiffusion inbound protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`.
6. The cert is added to `PerasCertDB`; `chainSelSync` triggers chain selection for block `H`.
7. `PerasWeightSnapshot` now records `perasWeight` boost for `H`; any fragment containing `H` gains that weight in `wsvTotalWeight`.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
