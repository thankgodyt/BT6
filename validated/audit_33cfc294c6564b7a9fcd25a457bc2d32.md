### Title
Peras Vote Signature Verification Bypass in `validatePerasVote` Enables Voter Impersonation and Quorum Disruption — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasVote` implementation accepts inbound Peras votes from peers without verifying any cryptographic signature. The associated `PerasVote blk` data type carries no signature field at all. A single unprivileged peer can flood the `PerasVoteDB` with fake votes claiming to be any voter in the stake distribution. Because `PerasVoteId = (voterId, roundNo)` is the sole deduplication key in `implAddVote`, each real voter's subsequent legitimate vote for that round is silently dropped as `PerasVoteAlreadyInDB`, preventing quorum from being reached and blocking certificate forging.

---

### Finding Description

**Root cause — missing signature field and no cryptographic check in `validatePerasVote`**

The `PerasVote blk` associated data type defined in the catch-all `BlockSupportsPeras` instance carries only three fields — round number, target block, and a plain `PerasVoterId` — with no signature:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- no signature field
  }
``` [1](#0-0) 

The corresponding `validatePerasVote` implementation only performs a stake-distribution membership lookup; it performs no cryptographic verification whatsoever:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

Any vote whose `pvVoteVoterId` appears in the stake distribution map is unconditionally accepted as `ValidatedPerasVote`.

**Attacker-controlled entry path — `PerasVoteDiffusion` mini-protocol**

The production node-to-node handler wires the inbound `PerasVoteDiffusion` client directly to `makePerasVotePoolWriterFromChainDB`, which calls `processVotes` → `validatePerasVote` for every batch of votes received from a peer:

```haskell
hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      ( makePerasVotePoolWriterFromChainDB
          systemTime
          (pure (PerasVoteStakeDistr mempty))   -- TODO: replace with real data
          getChainDB
      )
``` [3](#0-2) 

The `processVotes` function validates each vote and, if all pass, adds them to the DB. No signature is checked at any point in this pipeline: [4](#0-3) 

**Deduplication mechanism that turns fake votes into a voter-silencing weapon**

`implAddVote` in `PerasVoteDB` uses `PerasVoteId = {pviRoundNo, pviVoterId}` as the sole deduplication key. Once a vote for voter X in round R is stored — regardless of whether it was forged by a malicious peer — any subsequent vote with the same `(X, R)` pair is silently discarded:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds  -- silently dropped
  | otherwise                            = tryAddVote pvds voteId
``` [5](#0-4) 

**End-to-end exploit flow**

1. Malicious peer connects to a victim node via the standard node-to-node `PerasVoteDiffusion` protocol.
2. For every legitimate voter ID visible in the stake distribution, the attacker constructs a `PerasVote blk` with that voter's `PerasVoterId`, an arbitrary `pvVoteBlock`, and the current round number. No signature is required.
3. `processVotes` calls `validatePerasVote` for each fake vote. Because the voter IDs are present in the stake distribution, all pass and are stored in `PerasVoteDB`.
4. When the real committee members later broadcast their legitimate votes, `implAddVote` finds their `(voterId, roundNo)` already in `pvdsVoteIds` and returns `PerasVoteAlreadyInDB` — the real votes are silently discarded.
5. No target accumulates enough stake to satisfy `stakeAboveThreshold`, so no certificate is forged for that round. [6](#0-5) 

**Note on current production state:** The production wiring currently passes `PerasVoteStakeDistr mempty` as the stake distribution, which causes `lookupPerasVoteStake` to return `Nothing` for every vote, making `validatePerasVote` reject all votes. This is an acknowledged placeholder (the inline TODO comment reads *"the empty stake distribution will cause all votes to be considered invalid"*). It is a separate incomplete-plumbing TODO, not a security control. The signature-bypass vulnerability is structurally present in the production code path and becomes fully exploitable the moment the real stake distribution is wired in. [7](#0-6) 

---

### Impact Explanation

**Classification: Critical — Bypass of Peras vote signature validation enabling unauthorized vote acceptance.**

An unprivileged peer with a standard node-to-node connection can impersonate every committee member for a given round by sending unsigned fake votes. This silences all legitimate voters via the deduplication guard, prevents quorum from being reached, and blocks certificate forging. Because Peras certificates are the mechanism by which blocks receive a stake-weighted boost in chain selection, sustained suppression of certificates degrades the finality guarantees of the Peras protocol and can cause honest nodes to diverge from the intended canonical chain.

The impact directly matches the allowed scope: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote … acceptance."*

---

### Likelihood Explanation

**Currently low; structurally high once plumbing is complete.**

The attack is not exploitable today because the production code passes an empty stake distribution, causing all inbound votes to be rejected. However, the empty distribution is an explicitly acknowledged TODO with a tracked issue (`cardano-peras/issues/73`, `#120`). Once the real committee selection data is plumbed in — the stated next step — the vulnerability becomes trivially exploitable by any peer that can open a node-to-node connection, requiring no special privileges, no key material, and no stake.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote blk`** (analogous to the concrete `PerasVote` type in `Peras.Vote.V1` which already carries `pvSignature :: VoteSignature PerasBLSCrypto`). [8](#0-7) 

2. **Verify the signature inside `validatePerasVote`** before accepting a vote, using the voter's public key looked up from the committee/stake distribution — mirroring the pattern already implemented in `implVerifyVote` for `EveryoneVotes` and `WFALS`. [9](#0-8) 

3. **Do not merge the real stake-distribution plumbing** (replacing `PerasVoteStakeDistr mempty`) until step 2 is complete, to avoid opening the attack window.

---

### Proof of Concept

**Precondition:** Two nodes running with a non-empty `PerasVoteStakeDistr` (i.e., after the TODO in `NodeToNode.hs` is resolved).

**Steps:**

```
-- Attacker constructs, for each voter ID `vid` in the stake distribution
-- and the current round `r`, a fake vote with an arbitrary block target:
let fakeVote = PerasVote
      { pvVoteRound   = r
      , pvVoteBlock   = someArbitraryPoint   -- any point; no signature binds it
      , pvVoteVoterId = vid
      }
-- Attacker sends all fake votes to the victim node via PerasVoteDiffusion.
-- processVotes calls validatePerasVote for each:
--   lookupPerasVoteStake fakeVote stakeDistr = Just stake  (vid is in the map)
--   => Right (ValidatedPerasVote fakeVote stake)           (accepted, no sig check)
-- implAddVote stores PerasVoteId{pviRoundNo=r, pviVoterId=vid} in pvdsVoteIds.
```

**Result:** When the real committee member `vid` later sends their legitimate vote for round `r`, `implAddVote` finds `PerasVoteId{r, vid}` already in `pvdsVoteIds` and returns `PerasVoteAlreadyInDB`. The legitimate vote is discarded. With all committee members silenced, `stakeAboveThreshold` is never satisfied, no certificate is forged for round `r`, and the Peras boosting mechanism is permanently disrupted for that round. processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
