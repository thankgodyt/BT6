Audit Report

## Title
Missing `omniBridgeChainId` in `deployToken` Signed Payload Enables Cross-Chain Replay — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
The `deployToken` function constructs its borsh-encoded signed payload without including `omniBridgeChainId`, while `finTransfer` includes it twice. Because all OmniBridge deployments across chains share the same `nearBridgeDerivedAddress`, a valid MPC-signed metadata signature accepted on chain A is cryptographically identical and accepted on every other OmniBridge instance, allowing any observer to replay a legitimate `deployToken` call across all chains without MPC authorization.

## Finding Description
In `deployToken` (L142–148), the signed payload is:

```
PayloadType::Metadata | token | name | symbol | decimals
``` [1](#0-0) 

`omniBridgeChainId` is absent. `MetadataPayload` itself carries no chain-scoping field: [2](#0-1) 

By contrast, `finTransfer` embeds `omniBridgeChainId` at two positions in its payload (L294, L297): [3](#0-2) 

After signature recovery, the only guards in `deployToken` are:
1. `ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress` — produces the same result on every chain sharing the same MPC key.
2. `!isBridgeToken[nearToEthToken[metadata.token]]` — only prevents re-deployment on the **same** chain instance. [4](#0-3) 

There is no nonce, no destination-chain field, and no contract-address binding in the metadata payload. An attacker who observes a legitimate `deployToken` transaction on chain A can submit the identical `(signatureData, metadata)` to chain B, C, etc., and each call will pass `ECDSA.recover` and the `isBridgeToken` guard (since the token has not yet been deployed on those chains).

## Impact Explanation
This is a concrete chain/domain separation flaw. The replay:
1. Deploys an unauthorized `ERC1967Proxy` on chain B and registers it in `nearToEthToken[metadata.token]`.
2. Permanently blocks any future legitimate `deployToken` for that NEAR token on chain B (`ERR_TOKEN_EXIST`).
3. If NEAR subsequently routes transfers for that token to chain B (which it may, since the token appears deployed), legitimately MPC-signed `finTransfer` calls will mint against the attacker-triggered proxy — creating token supply on chain B that MPC never explicitly authorized for that chain.

This matches the allowed Critical impact: **cross-chain replay / chain-domain separation flaw enabling unauthorized token deployment and potential unauthorized minting of bridged funds**.

## Likelihood Explanation
The precondition — multiple OmniBridge instances sharing the same `nearBridgeDerivedAddress` — is the intended production topology. `omniBridgeChainId` exists precisely to differentiate these instances, but is not used in `deployToken`. Any publicly observable `deployToken` transaction on one chain is immediately replayable on all others by any unprivileged external user with no privileged access, leaked keys, or MPC collusion required. The function is `external payable` with no access control beyond the signature check.

## Recommendation
Include `omniBridgeChainId` in the borsh-encoded payload verified in `deployToken`, mirroring the pattern in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

The NEAR MPC signing logic must be updated in lockstep to include the destination chain ID when producing metadata signatures. The same fix must be applied to the Starknet `deploy_token` and Solana `deploy_token` implementations, which have the same omission.

## Proof of Concept
Deploy two `OmniBridge` instances with `omniBridgeChainId = 1` and `omniBridgeChainId = 2` but the same `nearBridgeDerivedAddress` (matching production topology). Construct the borsh payload exactly as the contract does (without chain ID), sign it with the MPC key, and call `deployToken` on instance A. Then submit the identical `(signatureData, metadata)` to instance B. The call succeeds: `ECDSA.recover` returns `nearBridgeDerivedAddress`, the `isBridgeToken` guard passes (token not yet deployed on B), and a new proxy is registered in `nearToEthToken` on chain B without MPC ever authorizing a chain-B deployment. The submitted Forge test (`ReplayDeployTokenTest.testReplay`) directly demonstrates this path.
