### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Validation, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production instance of `validatePerasCert` for all `StandardHash blk` blocks unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Any unprivileged peer can send a crafted `PerasCert` pointing at any block in the VolatileDB; the certificate is accepted, stored, and immediately fed into chain selection, granting the targeted block a configurable weight boost (default: 15 block-lengths of weight). This allows an adversary to make an honest node prefer a non-canonical chain without holding any stake, keys, or committee membership.

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must verify a Peras certificate before it is stored and acted upon. The universal instance for all `StandardHash blk` blocks implements this gate as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate-signature check, no committee-membership check, no quorum check, and no round-validity check is performed. The stub is not confined to tests; it is the only instance in the codebase and is wired directly into the production node-to-node diffusion path.

**Attacker-controlled entry path:**

1. A peer connects via the Peras certificate diffusion mini-protocol. In `NodeToNode.hs`, the inbound handler is wired as:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [2](#0-1) 

2. `makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validator:

```haskell
(validatePerasCert mkPerasParams)
``` [3](#0-2) 

3. `processCerts` calls `validateCert` on each inbound certificate. Because `validatePerasCert` always returns `Right`, every certificate passes: [4](#0-3) 

4. The accepted certificate is added to `PerasCertDB` and triggers `chainSelSync` → `chainSelectionForBlock` for the boosted block: [5](#0-4) 

5. Chain selection computes `WeightedSelectView` using `wsvTotalWeight = blockNo + wsvWeightBoost`. The forged certificate injects `perasWeight params` (default: 15) into the weight of the targeted block, potentially making a shorter or non-canonical fork appear heavier than the honest chain: [6](#0-5) 

The default `perasWeight` is 15 block-lengths: [7](#0-6) 

### Impact Explanation

An unprivileged peer with no stake, no KES/VRF keys, and no committee membership can craft a `PerasCert` naming any block hash currently in the victim node's VolatileDB. The certificate is accepted unconditionally, stored, and causes chain selection to re-evaluate with the targeted block receiving a +15 weight boost. Because the security parameter `k` is expressed in the same `PerasWeight` units, a single forged certificate can shift the chain-selection outcome by the equivalent of 15 honest blocks. An adversary who can send multiple certificates for different rounds can accumulate boosts sufficient to make the node permanently prefer an adversarial fork over the honest chain, constituting a **chain-selection safety failure** that lets an unprivileged peer cause an honest node to prefer a non-canonical chain beyond the intended security assumptions.

**Severity: High** — matches "Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

### Likelihood Explanation

The vulnerability is reachable by any peer that can establish a Peras certificate diffusion connection. No privileged access, no stake, and no cryptographic material are required. The only precondition is that the targeted block hash exists in the victim's VolatileDB, which is trivially discoverable via the ChainSync protocol. The attack is deterministic and repeatable.

### Recommendation

1. Implement real cryptographic validation in `validatePerasCert` before the Peras certificate diffusion mini-protocol is enabled in production. At minimum, verify the BLS aggregate signature against the claimed committee members and confirm that the signers collectively hold sufficient stake to meet the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).

2. Until real validation is implemented, gate the Peras certificate diffusion mini-protocol behind a feature flag so that it is not reachable from untrusted peers on production nodes.

3. Track the open issue referenced in the TODO comments (`https://github.com/tweag/cardano-peras/issues/120`) as a security-critical blocker before any production deployment.

### Proof of Concept

A private-testnet reproduction:

1. Start a node with Peras certificate diffusion enabled (as wired in `NodeToNode.hs`).
2. Connect a malicious peer that sends a `PerasCert` with `pcCertRound = 0` and `pcCertBoostedBlock` set to the hash of any block on a minority fork currently in the victim's VolatileDB.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCertBoost = PerasWeight 15 })` unconditionally.
4. `chainSelSync` triggers `chainSelectionForBlock` for the boosted block.
5. `WeightedSelectView` now scores the minority fork's tip as `blockNo + 15`, which exceeds the honest chain's score if the honest chain leads by fewer than 15 blocks.
6. The node switches to the adversarial fork. [1](#0-0) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
