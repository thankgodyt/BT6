### Title
Peras Vote Validation Skips Cryptographic Proof Checks, Enabling Unauthorized Certificate Acceptance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` default implementation in `BlockSupportsPeras` only checks whether the claimed voter has stake in the distribution. It explicitly ignores the `_params` argument that carries the cryptographic parameters needed to verify the BLS signature and VRF eligibility proof. An unprivileged peer connected via the object-diffusion mini-protocol can therefore send votes whose cryptographic proofs are entirely fabricated. Because the only gate is a stake-table lookup, those votes pass validation, accumulate in the vote pool, and — once enough forged votes for the same target block are received — trigger `forgePerasCert`, which also skips validation. The resulting certificate boosts the target block's chain-selection weight on the receiving node, causing it to prefer a chain that was never legitimately certified.

---

### Finding Description

**Root cause — `validatePerasVote` ignores the eligibility proof** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The first argument `_params` (the `PerasCfg` that carries cryptographic parameters) is discarded with a wildcard. The only check performed is `lookupPerasVoteStake`, which confirms that the claimed voter ID appears in the stake distribution. It does **not** verify:

- the BLS signature on the vote message,
- the VRF eligibility proof (`pvEligibilityProof` in `PerasVote.V1`), or
- committee-membership criteria.

A voter ID is public information (a stake-pool key hash). Any peer that knows a valid voter ID can fabricate a `PerasVote` for an arbitrary target block and have it accepted.

**Root cause — `forgePerasCert` also skips validation** [2](#0-1) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasForgeErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
forgePerasCert params votes =
  return $
    ValidatedPerasCert
      { vpcCert = PerasCert { ... }
      , vpcCertBoost = perasWeight params
      }
```

The certificate is forged unconditionally from whatever votes were passed in, without re-checking their cryptographic validity.

**Attacker-controlled entry path — `processVotes`** [3](#0-2) 

`processVotes` is the inbound handler for votes received from remote peers over the object-diffusion mini-protocol. It calls `validateVote` (which resolves to `validatePerasVote`) for each vote not already in the database, and adds every vote that returns `Right` to the pool:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _)            -> throw (PerasVoteValidationError errs)
```

Because `validateVote` only checks stake, every forged vote for a known voter ID passes and is stored. The downstream `updatePerasRoundVoteStates` / `updateCandidateVoteState` path then calls `forgePerasCert` once the accumulated (forged) stake crosses the quorum threshold. [4](#0-3)

### Impact Explanation

**Severity: Critical / High**

Once a certificate is forged for an attacker-chosen block, `PerasWeightSnapshot` gives that block an elevated chain-selection weight. The receiving node will prefer the boosted chain over an equally-long or slightly-longer honest chain, constituting an unauthorized chain-selection manipulation. This is a direct bypass of Peras voting and certificate checks that enables unauthorized certificate acceptance — matching the allowed impact scope: *"Bypass of… Peras voting or certificate checks… that enables unauthorized… vote, or certificate acceptance."*

---

### Likelihood Explanation

**Likelihood: High**

- The attack requires only a network connection to a node running the object-diffusion mini-protocol — no keys, no stake, no operator access.
- Voter IDs (stake-pool key hashes) are public on-chain data.
- The attacker needs to send enough forged votes (each attributed to a different known voter ID) to exceed the quorum threshold. The number of required votes is bounded by the committee size, which is a protocol parameter.
- No cryptographic barrier exists because `_params` is discarded.

---

### Recommendation

Replace the wildcard `_params` binding with actual cryptographic verification before accepting a vote:

1. Verify the BLS signature (`pvSignature`) over the canonical encoding of `(pvRoundNo, pvBoostedBlock)` using the public key associated with `pvVoterId`.
2. Verify the VRF eligibility proof (`pvEligibilityProof`) against the current epoch nonce and the committee-selection parameters in `PerasCfg`.
3. Confirm committee membership (persistent vs. non-persistent seat) before accepting the vote.

Only after all three checks pass should the vote be wrapped in `ValidatedPerasVote` and forwarded to `addVote`.

---

### Proof of Concept

1. Connect to a target node's object-diffusion endpoint.
2. Obtain the current stake distribution (public on-chain data) and identify voter IDs with sufficient stake.
3. Construct `PerasVote` messages for a chosen target block, using valid voter IDs but arbitrary (invalid) `pvSignature` and `pvEligibilityProof` fields.
4. Send a batch of such votes via the object-diffusion mini-protocol.
5. `processVotes` calls `validatePerasVote` for each; since `_params` is ignored and the voter IDs are in the stake table, all votes return `Right ValidatedPerasVote`.
6. `updatePerasRoundVoteStates` accumulates the forged stake; once the quorum threshold is crossed, `forgePerasCert` issues a `ValidatedPerasCert` for the attacker-chosen block.
7. The certificate is stored and the block's chain-selection weight is boosted, causing the node to prefer the attacker's target chain.

  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
