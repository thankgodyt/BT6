### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Allows Unprivileged Peer to Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. This stub is wired directly into the production `makePerasCertPoolWriterFromChainDB` path, which is the handler invoked for every Peras certificate received from a remote peer via the `ObjectDiffusion` mini-protocol. When Peras is enabled, any unprivileged peer can inject an arbitrary `PerasCert` (with any round number and any boosted-block point) that will be accepted, stored, and used to reweight chain fragments during chain selection, allowing the attacker to steer the node toward a non-canonical fork.

### Finding Description

**Root cause — stub validation always succeeds:**

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `Block/SupportsPeras.hs` defines `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, committee membership, round-number range, or boosted-block existence check is performed. Every certificate is unconditionally promoted to `ValidatedPerasCert`.

**Production inbound path uses this stub:**

`makePerasCertPoolWriterFromChainDB` — the writer used for every peer-supplied certificate in the node-to-node `ObjectDiffusion` handler — passes `validatePerasCert mkPerasParams` as the validation function:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls this function on every certificate not already in the DB, and on success immediately forwards the result to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Chain selection uses the injected weight:**

`chainSelSync` processes the accepted certificate by looking up the boosted block in the VolatileDB and calling `chainSelectionForBlock` for it: [4](#0-3) 

Chain selection then uses `forksAtMostKWeight` and `compareAnchoredFragments`, both of which consume the `PerasWeightSnapshot` that now includes the attacker-injected boost: [5](#0-4) 

**Security parameter `k` is weight-based when Peras is active:**

With Peras enabled, `k` is interpreted as a maximum rollback *weight*, not a block count: [6](#0-5) 

An attacker-injected certificate boost on a block that sits on a competing fork increases that fork's weight, potentially making it preferred over the honest chain without the attacker needing any stake or signing keys.

**End-to-end exploit path:**

1. Attacker connects as a normal peer (no keys required).
2. Attacker sends a `PerasCert` via the `ObjectDiffusion` mini-protocol with `pcCertRound` set to a round not yet in the DB and `pcCertBoostedBlock` pointing to a block on a competing fork already present in the victim node's VolatileDB.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The certificate is stored and `addPerasCertAsync` triggers chain selection.
5. `chainSelectionForBlock` is called for the boosted block; the `PerasWeightSnapshot` now includes the fake boost.
6. `compareAnchoredFragments` sees the fork as heavier than the current chain and the node switches to the attacker-chosen fork.

### Impact Explanation

**High — chain selection manipulation.** An unprivileged peer can cause an honest node to prefer a non-canonical fork by injecting fake Peras certificates that are accepted without any cryptographic validation. This violates the chain-selection invariant that only legitimately certified blocks receive weight boosts, and can cause the node to permanently diverge from the honest chain when Peras is enabled. The `k`-weight rollback bound can also be undermined: by boosting a block on the current chain's suffix, an attacker can inflate the suffix weight beyond `k`, preventing the node from ever switching to a better honest chain.

### Likelihood Explanation

**Medium.** Peras is disabled by default (`rnFeatureFlags`) but is a production feature under active deployment. The stub is in a non-test production file, is explicitly wired into the production `makePerasCertPoolWriterFromChainDB` path, and is reachable by any peer that can establish a node-to-node connection. No stake, keys, or privileged access is required. The TODO comment and linked issue (`cardano-peras/issues/120`) confirm the gap is known but unresolved.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The certificate's aggregate BLS signature against the declared committee members' verification keys (using `implVerifyCert` from `EveryoneVotes` or `WFALS` as appropriate).
- That the declared voters form a valid quorum (stake above threshold).
- That `pcCertRound` falls within the expected range relative to the current slot.
- That `pcCertBoostedBlock` refers to a block that actually exists and is old enough (satisfying `PerasBlockMinSlots`).

Until the real implementation is in place, the Peras feature flag must not be enabled in any environment reachable by untrusted peers.

### Proof of Concept

```
1. Run a node with Peras enabled (rnFeatureFlags).
2. Ensure the node's VolatileDB contains two competing forks A and B,
   where B is shorter/lighter than A (so A is currently selected).
3. Connect as an unprivileged peer via the ObjectDiffusion mini-protocol.
4. Send a PerasCert { pcCertRound = <any unseen round>,
                      pcCertBoostedBlock = <tip of fork B> }.
5. processCerts calls validatePerasCert → Right (no checks).
6. addPerasCertAsync triggers chainSelectionForBlock for B's tip.
7. compareAnchoredFragments now sees B's weight > A's weight.
8. Node switches selection to fork B.
Expected: node rejects the certificate with a validation error.
Actual:   node accepts it and switches to the attacker-chosen fork.
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14. In the latter case, the chain fragment has
-- total weight @2 + 2 * 14 = 30@.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
  deriving (Eq, Generic, NoThunks, ToCBOR, FromCBOR)
  deriving Show via Quiet SecurityParam

-- | The maximum amount of weight we can roll back.
maxRollbackWeight :: SecurityParam -> PerasWeight
maxRollbackWeight = PerasWeight . unNonZero . maxRollbacks
