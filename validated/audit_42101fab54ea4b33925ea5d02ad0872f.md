Audit Report

## Title
Native ETH Delivery Revert in `finTransfer` Permanently Freezes Bridged Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
When `finTransfer` is called to deliver native ETH to a smart-contract recipient that reverts on ETH receipt, the entire transaction reverts, rolling back the `completedTransfers[destinationNonce] = true` write. Because the recipient address is immutably embedded in the MPC-signed payload, no future call with the same valid payload can ever succeed. The user's source-chain tokens are permanently locked with no recovery path.

## Finding Description
In `finTransfer` (line 287), the destination nonce is marked used before ETH delivery:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
```

For native ETH transfers (`tokenAddress == address(0)`), lines 319–322 then attempt:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
```

If `payload.recipient` is a contract without a payable `receive()`/`fallback()`, the low-level `call` returns `success = false` and the function reverts with `FailedToSendEther()`. Solidity's revert semantics roll back **all** state changes in the transaction, including the nonce write at line 287 — the nonce is never consumed.

The recipient is part of the Borsh-encoded, MPC-signed payload (line 298: `Borsh.encodeAddress(payload.recipient)`). Altering the recipient invalidates the signature. There is no admin override, no alternative-recipient claim function, and no mechanism to mark the nonce as used without delivering ETH. Every subsequent `finTransfer` call with the same valid payload hits the identical revert. The `evm/SECURITY.md` (L-05) explicitly confirms that native ETH delivery via `finTransfer` with `tokenAddress=address(0)` is an intended production flow, ruling out any "unsupported behavior" exclusion.

## Impact Explanation
Permanent freezing of bridged native ETH, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR, EVM … flows."* Tokens locked or burned on the source chain (NEAR) are irrecoverable because the EVM finalization step can never complete for a non-payable contract recipient. The contract holds no per-user ETH balance; there is no escape hatch.

## Likelihood Explanation
Smart-contract recipients are a normal, intended use case for a bridge — multisigs, protocol treasuries, DeFi vaults, and proxy contracts are all common targets. Many such contracts do not implement a payable `receive()` function. A single `initTransfer` call on the source chain with such a recipient is sufficient to trigger the permanent freeze. No attacker capability is required; the affected user triggers it themselves through a standard bridge flow.

## Recommendation
Apply the pull-over-push pattern for native ETH delivery: on a failed `call`, do not revert. Instead, record the unclaimed amount in a mapping keyed by `destinationNonce` (or `(destinationNonce, recipient)`), mark the nonce as used, and expose a separate `claimEth(uint64 destinationNonce)` function allowing the recipient (or an admin-designated fallback) to withdraw. This preserves replay protection while eliminating the permanent-freeze path.

Alternatively, enforce EOA-only recipients for native ETH at finalization time with `require(payload.recipient.code.length == 0, "ETH recipient must be EOA")`, so the failure mode is surfaced before source-chain funds are committed.

## Proof of Concept
1. Deploy a contract `NoReceive` with no `receive()` or `fallback()` on the target EVM chain.
2. On NEAR, call `initTransfer` with `tokenAddress = address(0)` and `recipient = address(NoReceive)`. Source-chain ETH is locked/burned.
3. The NEAR MPC network signs a `TransferMessagePayload` embedding `NoReceive` as `recipient`.
4. A relayer calls `OmniBridge.finTransfer(signatureData, payload)`.
5. Execution reaches line 319: `payload.recipient.call{value: payload.amount}("")` returns `success = false`.
6. Line 322 reverts with `FailedToSendEther()`. The `completedTransfers[destinationNonce]` write (line 287) is rolled back.
7. Every subsequent `finTransfer` call with the same valid payload repeats steps 5–6. No other function can consume the nonce or release the ETH. Source-chain funds are permanently frozen.

A local Foundry test can reproduce this in a single test function: deploy `OmniBridge`, fund it with ETH, deploy `NoReceive`, construct a valid signed payload targeting `NoReceive`, call `finTransfer`, assert revert, assert `completedTransfers[nonce] == false`, and assert the ETH remains in the bridge contract with no claimable path.
