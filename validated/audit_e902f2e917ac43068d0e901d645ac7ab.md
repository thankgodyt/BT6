### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Crafted Certificate — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default implementation of `validatePerasCert` in the `BlockSupportsPeras` typeclass unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. An unprivileged peer on a private testnet running Peras can craft an arbitrary certificate for any block and have it accepted by an honest node, allowing the attacker to inject fake Peras certificate boosts and manipulate chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` defines `validatePerasCert` as the entry point for validating Peras certificates received from peers. The default implementation, annotated with a TODO referencing an open issue, is a stub that unconditionally wraps the input certificate in a `ValidatedPerasCert` and returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The companion `PerasValidationErr` type is itself a placeholder with no actual error variants, confirming that no real validation path exists:

```haskell
data PerasValidationErr blk
    = PerasValidationErr
    deriving stock (Show, Eq)
``` [2](#0-1) 

The analog to the external report is direct: just as `verifyThresholds` validates some fields of the agreement but omits the suspended-status check, `validatePerasCert` is the validation gate for incoming Peras certificates but omits **all** checks — no round-number bounds, no quorum threshold, no cryptographic signature verification over the certificate body. Any certificate that arrives over the wire is immediately promoted to a `ValidatedPerasCert` carrying a full `perasWeight` boost.

The `validatePerasVote` default implementation has the same structural problem — it checks only whether the voter appears in the stake distribution but performs no cryptographic verification of the vote's signature:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [3](#0-2) 

---

### Impact Explanation

Peras certificates carry a `perasWeight` boost that directly influences chain selection. The `ValidatedPerasCert` produced by `validatePerasCert` is the type consumed downstream by the chain-selection and weight-snapshot logic. Because the stub always returns `Right`, a peer can:

1. Fabricate a `PerasCert` pointing to any block of their choosing.
2. Have it accepted as a `ValidatedPerasCert` with full boost weight.
3. Cause an honest node to prefer a non-canonical or attacker-controlled chain over the honest chain.

This is a **bypass of Peras certificate verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance" and "High: Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical … chain" impact categories.

---

### Likelihood Explanation

Any peer that can reach a node running Peras (e.g., on a private testnet or a future mainnet deployment) can trigger this path by sending a well-formed but cryptographically invalid `PerasCert` over the Peras object-diffusion mini-protocol. No special privileges, keys, or stake are required. The stub is the **only** validation gate before the certificate is treated as trusted.

---

### Recommendation

**Short term:** Replace the stub body of `validatePerasCert` with real validation: verify the certificate's cryptographic proof, check that the round number is within the valid window, and confirm the quorum threshold is met before constructing a `ValidatedPerasCert`. Similarly, add signature verification to `validatePerasVote`.

**Long term:** Resolve the open issue referenced in the TODO comments (cardano-peras#120) and expand the test suite with adversarial certificate inputs — crafted certificates with invalid signatures, out-of-range round numbers, and insufficient quorum — to cover the unhappy paths that are currently untested.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect an adversarial peer to an honest node via the Peras object-diffusion mini-protocol.
2. Construct a `PerasCert` whose `pcCertBoostedBlock` points to an attacker-controlled block (e.g., a fork tip that is shorter than the honest chain).
3. Send the certificate to the honest node.
4. The node calls `validatePerasCert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate boost is applied; the honest node's chain-selection logic now weights the attacker's fork higher than the honest chain.
6. The honest node switches to the attacker's fork, diverging from the canonical chain. [1](#0-0)
