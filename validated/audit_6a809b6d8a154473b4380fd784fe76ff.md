### Title
Missing Setter for `change_address` Permanently Blocks All Withdrawals - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
The `Config.change_address` field is required to be `None` at contract initialization, but neither `ConfigUpdate` nor any management function provides a way to set it afterward. Because `get_change_script_pubkey()` panics when `change_address` is `None`, every withdrawal operation will panic, permanently locking all user funds in the bridge.

### Finding Description
The `Config` struct holds a `change_address: Option<String>` field that is used in every BTC/ZEC PSBT construction to route change outputs back to the bridge. [1](#0-0) 

At initialization, the contract explicitly enforces that `change_address` must be `None`: [2](#0-1) 

The only post-deployment configuration path is `update_config`, which applies a `ConfigUpdate` struct. Inspecting `ConfigUpdate` shows every tunable field **except** `change_address`: [3](#0-2) 

The `ConfigUpdate::apply` method correspondingly never writes to `config.change_address`: [4](#0-3) 

No standalone `set_change_address` function exists in `management.rs`. The only analogous pattern — a dedicated setter for a field excluded from `ConfigUpdate` — is `sync_chain_signatures_root_public_key`, which exists for `chain_signatures_root_public_key` but has no equivalent for `change_address`. [5](#0-4) 

As a result, `get_change_script_pubkey()` will always panic: [6](#0-5) 

### Impact Explanation
Every withdrawal PSBT construction calls `get_change_script_pubkey()`. With `change_address` permanently `None`, every withdrawal panics with `"ERR_CONFIG: change_address not configured"`. Users can deposit BTC and receive nBTC, but can never redeem it. All bridged funds are permanently locked. This matches: **Critical — significant permanent locking of user or protocol funds**, and at minimum **Medium — stuck bridge state requiring operator intervention** (which is impossible here because no operator path exists to set the value).

### Likelihood Explanation
Likelihood is **High**. The condition is triggered on every single withdrawal attempt by any user. There is no code path that sets `change_address` after deployment, so the bridge is broken from the moment it is deployed.

### Recommendation
Add `change_address: Option<String>` to `ConfigUpdate` and handle it in `ConfigUpdate::apply`, or introduce a dedicated DAO-gated `set_change_address` function in `management.rs`, mirroring the pattern used for `sync_chain_signatures_root_public_key`.

### Proof of Concept
1. Deploy the `satoshi-bridge` contract with any valid `Config` where `change_address: None` (the only accepted initial state).
2. Attempt to call `update_config` with a `ConfigUpdate` containing a `change_address` value — the field does not exist in the struct, so it is silently ignored.
3. Any user calls `ft_transfer_call` on the nbtc contract to initiate a withdrawal.
4. The bridge reaches PSBT construction and calls `config.get_change_script_pubkey()`.
5. The call panics: `"ERR_CONFIG: change_address not configured"`.
6. The withdrawal reverts; the user's nBTC is returned (if the callback handles it), but no BTC is ever released. The bridge is permanently unable to process withdrawals. [6](#0-5) [3](#0-2) [2](#0-1)
