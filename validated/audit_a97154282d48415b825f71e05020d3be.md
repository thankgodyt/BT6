### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Always Returning `Right` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance defines `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or committee-membership checks. This function is wired directly into the production Peras certificate diffusion inbound handler in `NodeToNode.hs`. Any unprivileged peer can therefore inject arbitrary Peras certificates into the node's `ChainDB` without possessing committee membership, quorum, or any valid cryptographic proof. This is the direct analog to `RM_UpdateReward` having no access control: the function that is supposed to gate privileged state changes (certificate acceptance) has no authorization enforcement at all.

### Finding Description

**Root cause — `validatePerasCert` stub:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all `BlockSupportsPeras` instance (which applies to all block types, including production Cardano blocks) defines:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No committee membership check, no quorum check, no aggregate signature verification, and no cryptographic proof is performed. Every certificate is accepted and assigned the full `perasWeight` boost.

**Production wiring — cert diffusion inbound handler:**

In `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`, the production node-to-node handler registers the Peras certificate diffusion inbound path:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` calls `validatePerasCert` (following the same pattern as `makePerasVotePoolWriterFromChainDB` which calls `validatePerasVote`). Because `validatePerasCert` always returns `Right`, every certificate received from any peer passes "validation" and is stored in the `ChainDB` via `ChainDB.addPerasVoteWithAsyncCertHandling` (or the cert equivalent).

**Contrast with the vote path:**

The vote inbound handler at least attempts validation against a stake distribution:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

The cert path has no equivalent check — `validatePerasCert` ignores both `params` and `cert` content and returns `Right` unconditionally.

**`BlockSupportsPeras` is a catch-all instance:**

The comment at line 318–319 reads: `-- TODO: degenerate instance for all blks to get things to compile`. This instance applies to every block type, meaning no concrete Cardano block type overrides it with a real implementation. [4](#0-3) 

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate verification enabling unauthorized certificate acceptance.**

An unprivileged peer can craft and send a `PerasCert` with any `pcCertRound` and `pcCertBoostedBlock` values. Because `validatePerasCert` returns `Right` unconditionally, the certificate is accepted as `ValidatedPerasCert` with the full `perasWeight` boost and stored in the `ChainDB`. This:

1. **Corrupts the Peras certificate database** with certificates that were never legitimately produced by a quorum of committee members.
2. **Manipulates chain selection** — Peras certificates apply a boost weight (`perasWeight`) to the boosted block's chain. An attacker can boost an arbitrary block (including a non-canonical or adversarial fork) by injecting a forged certificate, causing honest nodes to prefer a chain they should not.
3. **Breaks the Peras security invariant** that only blocks certified by a legitimate quorum of committee members receive a boost.

This matches the allowed impact: *"Critical. Bypass of… certificate/signature validation… that enables unauthorized… certificate acceptance."*

### Likelihood Explanation

Any peer that can establish a node-to-node connection and negotiate the Peras cert diffusion miniprotocol version can exploit this. No keys, stake, or committee membership are required. The attacker only needs to:

1. Connect to a target node.
2. Send a `PerasCert` message with an arbitrary `pcCertRound` and `pcCertBoostedBlock`.
3. The certificate is accepted unconditionally.

The Peras miniprotocol is registered in the production handler without a version gate that would prevent activation. The code is in production files, not test or mock files.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS/DSIGN signature over the certificate against the committee's public keys.
2. Checks that the signers constitute a quorum (total stake ≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
3. Verifies that each signer is a registered committee member in the current epoch's stake distribution.
4. Rejects the certificate with a concrete `PerasValidationErr` variant if any check fails.

Until a real implementation is available, the Peras cert diffusion inbound handler should be disabled or gated behind a feature flag that is off by default in production.

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a production Cardano node with Peras cert diffusion enabled.
2. Attacker sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = adversarialForkTip }` via the `hPerasCertDiffusionClient` miniprotocol channel.
3. The node calls `makePerasCertPoolWriterFromChainDB`, which calls `validatePerasCert params cert`.
4. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` — no checks performed.
5. The certificate is stored in `ChainDB` with full boost weight.
6. Chain selection now treats `adversarialForkTip` as boosted, potentially causing the node to prefer the attacker's fork over the honest canonical chain.

**Deterministic reasoning:** `validatePerasCert _params cert = Right (ValidatedPerasCert cert (perasWeight params))` — the function body contains no conditional, no lookup, and no cryptographic call. It is structurally impossible for it to return `Left` regardless of the certificate content. [5](#0-4) [2](#0-1)
