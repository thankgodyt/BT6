### Title
Shielded-Only Zcash Unified Address as `refund_address` Permanently Locks User Funds in `build_refund_output` - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `build_refund_output` function unconditionally calls `.script_pubkey().expect(...)` on any parsed Zcash address. A shielded-only Unified Address (UA) — one with only Orchard/Sapling receivers and no transparent receiver — parses successfully but yields no `ScriptBuf`, causing a panic. Because `request_refund` stores the `refund_address` string without validating that it has a transparent receiver, any user who supplies a shielded-only UA as their refund address will have their deposit permanently locked: `execute_refund` will always panic and can never complete.

### Finding Description

`internal_request_refund` accepts a `refund_address: String` from the caller and stores it verbatim in a `RefundRequest` without any address-type validation: [1](#0-0) 

The only check performed is that if `deposit_msg.refund_address` is pre-set, the caller-supplied value must match it — there is no check that the address actually has a transparent receiver: [2](#0-1) 

Later, when `execute_refund` is called, it invokes `build_refund_output`, which calls `Address::parse()` (succeeds for any valid Zcash UA) and then unconditionally unwraps `script_pubkey()`: [3](#0-2) 

For a shielded-only UA, `script_pubkey()` returns `Err("No receiver found in address")` — the same error documented in the codebase's own test fixture: [4](#0-3) 

The withdrawal flow already has a fix for this exact problem: `target_script_pubkey()` returns `Option<ScriptBuf>` and the PSBT validation loop handles `None` gracefully: [5](#0-4) [6](#0-5) 

The refund path has no equivalent protection. The `.expect("Invalid refund script_pubkey")` at line 300 will always panic for shielded-only UAs, making the refund permanently unexecutable.

### Impact Explanation

A user whose deposit was never finalized (e.g., the relayer never called `verify_deposit`) submits a `request_refund` with a shielded-only Zcash UA as `refund_address`. The request is stored successfully. Every subsequent call to `execute_refund` panics inside `build_refund_output`. The deposit UTXO is never spent by a refund transaction, and the user's BTC/ZEC is permanently locked in the bridge-controlled deposit address with no recovery path. This matches the **Critical** impact category: permanent locking of user funds.

### Likelihood Explanation

Shielded-only Zcash UAs are valid, widely-used addresses on Zcash mainnet (the codebase itself uses one as a test fixture). A user who prefers privacy may naturally supply such an address as their refund destination. The `request_refund` API accepts it without error, giving no indication that `execute_refund` will later be impossible. The vulnerability is reachable by any unprivileged user with a valid Zcash deposit.

### Recommendation

Validate the `refund_address` at `request_refund` time (or at the latest in `request_refund_callback`) by parsing it and confirming `script_pubkey()` returns `Ok(...)`. Reject shielded-only UAs with a clear error message, mirroring the pattern already used in `target_script_pubkey`. Alternatively, extend the Zcash refund path to support Orchard-bundle refunds for shielded-only UAs, analogous to the Orchard withdrawal flow.

### Proof of Concept

1. On Zcash, user sends ZEC to a deposit address derived from a `DepositMsg` with `refund_address` set to a shielded-only UA (e.g., `u15a97e324mck...` — the same address used in the existing test at `config.rs:437`).
2. The relayer never calls `verify_deposit` (deposit is unfinalized).
3. User calls `request_refund` with the shielded-only UA as `refund_address`. `request_refund_callback` stores it without error.
4. After the timelock, anyone calls `execute_refund`. Execution reaches `build_refund_output`:
   - `Address::parse(shielded_only_ua, ZcashMainnet)` → `Ok(Address::Unified { ... })`
   - `.script_pubkey()` → `Err("No receiver found in address")`
   - `.expect("Invalid refund script_pubkey")` → **panic**
5. The call reverts. The refund request remains in storage but can never be executed. The user's ZEC is permanently locked.

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
