### Title
Unregistered Recipient in `safe_mint` Permanently Locks User Deposit and Inflates Bridge nBTC Balance — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account **before** checking whether the intended recipient is registered. When the recipient is unregistered, the function silently returns `U128(0)` and exits, leaving the freshly minted nBTC permanently stranded in the bridge's balance. The depositing user's BTC remains locked in the bridge with no nBTC issued to them and no automatic recovery path, creating a persistent supply/accounting imbalance analogous to the ZetaChain initial-liquidity imbalance: the on-chain nBTC total supply grows beyond the sum of all user-accessible balances.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← silent early return
    }
    // transfer to account_id only if registered
    ...
}
``` [1](#0-0) 

Step 1 (`internal_deposit` to `bridge_id`) unconditionally increases the nBTC total supply and credits the bridge's own balance. Step 2 checks registration and, on failure, returns without transferring anything to the user. The result is:

- **nBTC total supply** increases by `amount`.
- **bridge_id balance** increases by `amount`.
- **User balance** remains zero.
- **User's BTC** is locked in the bridge UTXO set with no corresponding nBTC issued.

The bridge's `burn` function withdraws exclusively from `bridge_id`:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
``` [2](#0-1) 

This means the stranded tokens silently inflate the pool of bridge-held nBTC that is drawn upon during subsequent withdrawal burns, creating an accounting drift: the bridge's BTC custody and the nBTC supply become misaligned.

By contrast, the `mint` function (used for the standard deposit path) calls `mint_inner`, which auto-registers the account before depositing, so it never produces this stuck state:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
}
``` [3](#0-2) 

`safe_mint` deliberately skips this auto-registration (it is designed for a "safe" cross-contract call path), but it performs the mint step before the registration check, inverting the correct order.

---

### Impact Explanation

**Medium — stuck bridge state requiring operator intervention; supply/accounting invariant broken.**

- The nBTC total supply permanently exceeds the sum of all user-accessible balances by the amount of every failed `safe_mint` call.
- The affected user's BTC deposit is locked in the bridge with no nBTC issued and no automatic refund triggered.
- The excess nBTC sitting in `bridge_id` is indistinguishable from legitimately held bridge tokens, so it can be silently consumed by future `burn` calls for other users' withdrawals, causing the bridge's BTC reserves to become under-collateralised relative to outstanding nBTC supply.
- Recovery requires manual operator intervention to identify and reconcile the discrepancy.

---

### Likelihood Explanation

NEAR storage registration is a separate, explicit step that many users omit, especially when interacting programmatically or via a dApp that does not enforce pre-registration. Any deposit whose `recipient_id` has never called `storage_deposit` on the nBTC contract will trigger this path. The condition is reachable by any unprivileged user with no special knowledge or tooling.

---

### Recommendation

Move the registration check **before** the mint, or use the same auto-registration pattern as `mint_inner`:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Guard BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer to account_id
}
```

Alternatively, trigger a refund to the depositor's BTC address (via the existing refund mechanism) whenever `safe_mint` would return `U128(0)`, so no BTC is permanently locked.

---

### Proof of Concept

1. Deploy the nBTC contract and the satoshi-bridge contract in a local NEAR sandbox.
2. Create a NEAR account `alice.near` but do **not** call `storage_deposit` on the nBTC contract for `alice.near`.
3. Send BTC to alice's bridge deposit address; have a relayer submit a valid `TxInclusionProof`.
4. The bridge calls `safe_mint(alice.near, amount, None)` on the nBTC contract.
5. Observe: `ft_total_supply()` increases by `amount`; `ft_balance_of(alice.near)` returns `0`; `ft_balance_of(bridge_id)` increases by `amount`.
6. Alice's BTC UTXO is now marked as processed in `verified_deposit_utxo` — it cannot be re-submitted — and alice holds no nBTC.
7. The bridge's nBTC balance is inflated; a subsequent `burn` call for an unrelated withdrawal will draw from this inflated balance, under-collateralising the bridge's BTC reserves by `amount` satoshis.
