### Title
Unvalidated `refund_address` in `request_refund_callback` Causes Permanently Stuck Refund Request — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund_callback` stores a user-supplied `refund_address` verbatim without validating it as a parseable BTC/ZEC address for the configured chain. When `execute_refund` is later called, `build_refund_output` unconditionally calls `.expect("Invalid refund address")` on the parse result, causing a panic that permanently blocks execution of that refund request. The stuck request can only be cleared by DAO/Operator intervention or by the user first finalizing the deposit via `verify_deposit`.

---

### Finding Description

**Step 1 — Acceptance without validation.**

`request_refund_callback` performs several checks (output script matches deposit address, gas fee < amount, no duplicate request) but never validates that `refund_address` is a well-formed address for the bridge's configured chain: [1](#0-0) 

The `refund_address` string is stored verbatim in the `RefundRequest` with no format check.

**Step 2 — Deferred panic in `build_refund_output`.**

When `execute_refund` is later called, it eventually reaches `build_refund_output`, which parses the stored address using `.expect()`: [2](#0-1) 

If `refund_address` is malformed, wrong-network (e.g., mainnet address on testnet), or otherwise unparseable, `Address::parse` returns an error and `.expect("Invalid refund address")` panics. Every subsequent call to `execute_refund` for this UTXO will panic identically.

**Step 3 — Stuck state.**

The `RefundRequest` remains in `refund_requests` storage. `execute_refund` always panics before reaching `finalize_refund_with_psbt`, so the UTXO is never inserted into `verified_deposit_utxo`. The only escape paths are:

- DAO/Operator calls `reject_refund` (privileged).
- The user calls `verify_deposit` to finalize the deposit, after which `is_already_deposited` becomes `true` and anyone can call `reject_refund`. [3](#0-2) 

The user's attached storage deposit (required by `internal_request_refund`) is non-refundable by design, so it is lost regardless. [4](#0-3) 

---

### Impact Explanation

A refund request for a specific UTXO becomes permanently unexecutable via the normal path. The UTXO is not marked verified, so `verify_deposit` remains callable, but the refund path is blocked until operator intervention or the user self-resolves via deposit finalization. This is a publicly reachable panic-driven stuck state in a production bridge path. User funds (BTC on-chain) are not directly lost, but the refund mechanism for that UTXO is broken and requires privileged action to clean up.

**Impact level: Low** — publicly reachable stuck-state / panic-driven fault in production bridge/token paths without direct theft.

---

### Likelihood Explanation

Any NEAR account can call `request_refund` (it is a public, payable function gated only by a storage deposit). Providing an invalid `refund_address` — e.g., a mainnet address when the bridge is configured for testnet, a Zcash address on a Bitcoin bridge instance, or a random string — is trivially achievable. The attacker pays the storage deposit (anti-spam fee) but permanently blocks `execute_refund` for that UTXO until operator cleanup. This is a low-cost griefing vector.

---

### Recommendation

Validate `refund_address` as a parseable, chain-correct address inside `request_refund_callback` before storing the `RefundRequest`. Reuse the same `Address::parse` call that `build_refund_output` performs, and `require!` it succeeds:

```rust
// In request_refund_callback, before constructing RefundRequest:
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the validation already present in `build_refund_output` and ensures that any address stored in a `RefundRequest` is guaranteed to be parseable at execution time.

---

### Proof of Concept

1. Alice has a BTC deposit at a bridge-controlled address (UTXO confirmed on-chain).
2. Alice calls `request_refund` with `refund_address = "not_a_valid_address"` and attaches the required storage deposit. She supplies a valid Merkle proof.
3. `request_refund_callback` fires: the output script check passes, `gas_fee < amount` passes, and the `RefundRequest` is stored with `refund_address = "not_a_valid_address"`.
4. After the timelock, anyone calls `execute_refund(utxo_storage_key, None)`.
5. `execute_refund` → `internal_execute_refund` → `refund_execution_inputs` (succeeds) → `build_refund_output("not_a_valid_address", ...)` → `Address::parse` returns `Err` → `.expect("Invalid refund address")` **panics**.
6. The call reverts. The `RefundRequest` remains in storage. Step 5 can be repeated indefinitely with the same result.
7. The UTXO is never inserted into `verified_deposit_utxo`. Alice cannot self-service the cleanup via `reject_refund` unless she first calls `verify_deposit` to finalize the deposit.
8. DAO/Operator must call `reject_refund` to unblock the UTXO. [5](#0-4) [2](#0-1)

    /// Parse the original deposit transaction and compute the refund economics.
    pub(crate) fn refund_execution_inputs(
        &self,
        refund_request: &RefundRequest,
    ) -> RefundExecutionInputs {
        let config = self.internal_config();
        let transaction =
            crate::WrappedTransaction::decode(&refund_request.tx_bytes.0, &config.chain)
                .expect("Deserialization tx_bytes failed");
        let txid = transaction.compute_txid();
        let outpoint = OutPoint {
            txid,
            vout: u32::try_from(refund_request.vout)
                .unwrap_or_else(|_| env::panic_str("vout overflow")),
        };
        let deposit_output = transaction.output()[refund_request.vout].clone();

        let refund_amount = refund_request
            .amount
            .checked_sub(refund_request.gas_fee)
            .expect("Deposit amount too small to cover gas fee");
        require!(refund_amount > 0, "Refund amount is zero after gas fee");

        RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        }
    }

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
