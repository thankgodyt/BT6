Audit Report

## Title
Zero-Normalized Amount Causes Permanent Transfer Lock — (`near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates an outbound NEAR→EVM transfer with an amount that floor-divides to zero after decimal normalization, the transfer is committed to `pending_transfers` and the user's tokens are burned/locked inside `init_transfer_internal`. Every subsequent call to `sign_transfer` permanently reverts with `InvalidAmountToTransfer`, and no user-callable cancellation path exists, resulting in permanent freezing of the bridged funds.

## Finding Description
`normalize_amount` at L2784–2787 applies floor division over the decimal gap between origin and destination chains:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 24` and `decimals = 18` (gap = 6), any amount below `1_000_000` yocto-units normalizes to `0`.

`init_transfer_internal` (L1829–1865) commits the transfer to storage via `add_transfer_message`, then burns/locks tokens, and returns `U128(0)` — signalling full consumption to the NEP-141 contract — **without any pre-check that the post-normalization amount is non-zero**. The zero-amount guard exists only in `sign_transfer` at L482–485:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This guard fires **after** the transfer is already stored and tokens consumed. The only removal paths for a `pending_transfers` entry (`claim_fee_callback`, `fin_transfer_callback`) require proof of destination-chain finalization that will never exist for a transfer that can never be signed. There is no user-callable cancel or refund function.

The code comment at L2781–2783 acknowledges "dust stays locked/burned" when `fee = 0`, but this refers to sub-unit remainders, not the case where the **entire** amount normalizes to zero — a distinct and more severe scenario where the user receives nothing on either chain.

## Impact Explanation
This constitutes permanent freezing of bridged funds — an explicitly listed Critical impact. The NEP-141 contract receives `U128(0)` from `ft_on_transfer`, so it does not refund the sender. The transfer entry is permanently stuck in `pending_transfers` with no signing path and no cancellation path. The user's tokens are irretrievably lost.

## Likelihood Explanation
Any unprivileged user can trigger this by calling `ft_transfer_call` on a registered NEAR token with an amount below the minimum transferable unit. For the common 24→18 decimal pairing, amounts below `1_000_000` yocto-units (a plausible "dust" or rounding-error scenario) silently trigger the bug. The `ft_on_transfer` call succeeds and returns no error to the sender, so the loss is not immediately apparent.

## Recommendation
Add a normalization check inside `init_transfer_internal` (or at the top of `ft_on_transfer`) before the transfer is committed to storage. If the normalized amount is zero, return the full amount to the caller as a refund:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` but places it at the correct, earlier point in the lifecycle — before tokens are burned/locked and before the transfer is committed to storage.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18`.
2. Call `ft_transfer_call` on that token, sending `500_000` yocto-units to the bridge with a valid `InitTransferMsg` (fee = 0).
3. `ft_on_transfer` invokes `init_transfer_internal`: transfer is stored in `pending_transfers`, 500,000 units are burned/locked, `U128(0)` is returned (full consumption).
4. Call `sign_transfer` for the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin: 24, decimals: 18})` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0, …)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Repeat step 4 indefinitely — it always reverts. The 500,000 yocto-units are permanently locked with no recovery path.
