### Title
`revalidateHeader` Envelope Check Computed But Never Enforced in Production — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full envelope validation (`envelopeCheck`) — covering block number, slot number, previous hash, and checkpoint hash — but wraps it in `assertWithMsg`, which is a **compile-time no-op in production builds**. The check is never enforced at runtime unless the binary is compiled with the `ENABLE_ASSERTIONS` CPP flag, which is not the default. This is the direct analog of the ShortLongSpell `sellSlippage` bug: a protective check is computed (or not even evaluated, due to Haskell's lazy semantics) but never applied.

---

### Finding Description

`assertWithMsg` is defined in `Ouroboros/Consensus/Util/Assert.hs`:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

When `ENABLE_ASSERTIONS` is absent (the default), the only active equation is `assertWithMsg _ a = a`. The first argument is **never forced** (Haskell is lazy) and its result is **never inspected**. The function unconditionally returns `a`.

`revalidateHeader` in `HeaderValidation.hs` relies on this for its entire envelope check:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` checks:
- Block numbers are consecutive (`UnexpectedBlockNo`)
- Slot numbers are strictly increasing (`UnexpectedSlotNo`)
- The previous hash matches the current tip (`UnexpectedPrevHash`)
- The block hash matches any configured checkpoint (`CheckpointMismatch`)
- Any block-specific `additionalEnvelopeChecks`

All of these checks are silently discarded in production. `chainDepState'` is always returned via `reupdateChainDepState`, which itself intentionally skips VRF/KES signature verification (correct for reapplication), but the envelope invariants are supposed to be enforced by `assertWithMsg` — and they are not.

`revalidateHeader` is called from production code in `Ouroboros/Consensus/Ledger/Extended.hs`, which is on the critical path for chain selection and ledger state management.

---

### Impact Explanation

The envelope check enforces structural chain invariants: hash linkage, block number monotonicity, slot monotonicity, and checkpoint pinning. If `revalidateHeader` is invoked with a header that violates any of these — for example, a header whose `prevHash` does not match the current tip, or a header at a checkpoint block number with a wrong hash — the violation is silently ignored and the `HeaderState` is updated as if the header were valid.

This can lead to:
- **Hash-chain breakage**: a header with a forged `prevHash` is accepted, corrupting the chain linkage stored in `HeaderState`.
- **Checkpoint bypass**: a header at a checkpoint block number with a different hash than the configured checkpoint is accepted, defeating the checkpoint protection entirely.
- **Block number / slot invariant violation**: a header with a non-consecutive block number or a non-increasing slot is accepted, breaking downstream assumptions about chain structure.

Any of these outcomes can cause the node to build on or prefer an invalid chain, constituting a chain-selection or ledger-state corruption bug reachable via a crafted sequence of headers from an unprivileged peer.

---

### Likelihood Explanation

`revalidateHeader` is documented as being called only for "previously validated" headers. However:

1. The precondition is enforced only by convention, not by the type system. There is no `Validated (Header blk)` wrapper that would prevent calling `revalidateHeader` on an unvalidated header.
2. During fork switching in chain selection, headers from one fork may be revalidated against a `HeaderState` derived from a different fork, where the `prevHash` or block number relationship differs.
3. A crafted peer that sends a valid-looking header sequence followed by a rollback and a subtly different fork can trigger the revalidation path with a header that fails the envelope check.
4. The `ENABLE_ASSERTIONS` flag is not set in standard Cardano node builds, so the protection is absent in all deployed nodes.

---

### Recommendation

Replace `assertWithMsg envelopeCheck` in `revalidateHeader` with a hard enforcement that cannot be compiled away. Either:

1. Use `either (error . ("revalidateHeader: envelope check failed: " ++)) id envelopeCheck` unconditionally (preserving the crash-on-violation semantics but making it unconditional), or
2. Return `Except (HeaderEnvelopeError blk) (HeaderState blk)` from `revalidateHeader` and enforce the check at the call site, mirroring `validateHeader`.

The `assertWithMsg` pattern should not be used for any check that is a necessary correctness invariant on the consensus-critical path, only for pure debug assertions that are provably unreachable in correct code.

### Proof of Concept

**Step 1 — `assertWithMsg` is a no-op in production:** [1](#0-0) 

Without `ENABLE_ASSERTIONS`, the only active equation is `assertWithMsg _ a = a`. The `Either String ()` first argument is never evaluated and never inspected.

**Step 2 — `revalidateHeader` wraps its entire envelope check in `assertWithMsg`:** [2](#0-1) 

`envelopeCheck` calls `validateEnvelope`, which enforces block number, slot, prev-hash, and checkpoint invariants. In production, `assertWithMsg envelopeCheck` reduces to `id`, so `HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'` is returned unconditionally.

**Step 3 — `validateEnvelope` contains the checks that are bypassed:** [3](#0-2) 

All four checks (`UnexpectedBlockNo`, `UnexpectedSlotNo`, `UnexpectedPrevHash`, `CheckpointMismatch`) are computed inside `envelopeCheck` but their results are discarded by `assertWithMsg` in production.

**Step 4 — Contrast with `validateHeader`, which enforces the same check unconditionally:** [4](#0-3) 

`validateHeader` uses `withExcept HeaderEnvelopeError $ validateEnvelope ...` inside an `Except` monad, so a failure is a hard error. `revalidateHeader` uses `assertWithMsg`, so the same failure is silently ignored in production.
