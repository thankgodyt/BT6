### Title
Orchard Bundle ZK Proof Never Verified — Bridge Accepts Structurally Plausible but Cryptographically Invalid Bundles, Causing Stuck Withdrawals - (File: contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs)

---

### Summary

The bridge's Orchard bundle validation pipeline (`extract_orchard_bundle` + `validate_orchard_bundle`) deserializes the bundle, recovers the output note using the hardcoded all-zeroes bridge OVK, and checks the recipient address and `value_balance` field. It never calls any Orchard proof verifier or binding-signature verifier. Because every checked field (`value_balance`, the encrypted note, `recipient_addr`) is fully attacker-controlled, a user can submit a withdrawal with a structurally coherent but cryptographically invalid Orchard bundle. The bridge accepts it, the MPC signs the resulting Zcash transaction, and the Zcash network rejects the transaction. The user's nZEC tokens remain locked in the bridge indefinitely, requiring privileged operator intervention to cancel.

---

### Finding Description

**Root cause — `extract_orchard_bundle` (orchard_policy.rs lines 38–78):**

`read_v5_bundle` only deserializes bytes; `ProofSizeEnforcement::Strict` only enforces the byte-length of the proof field, not its cryptographic validity. [1](#0-0) 

After deserialization, the bridge recovers the output note with the hardcoded all-zeroes OVK: [2](#0-1) 

Because `BRIDGE_OVK = [0u8; 32]` is a public constant, any attacker can encrypt a note with it and guarantee `recover_output_with_ovk` succeeds. [3](#0-2) 

**Root cause — `validate_orchard_bundle` (orchard_policy.rs lines 86–117):**

The two checks performed are:
1. `orchard.recipient_addr() == expected_addr_bytes` — the recovered address, which the attacker chose when encrypting the note.
2. `value_balance == -amount` — the `value_balance` field in the bundle header, which the attacker writes directly.

Neither check involves the Halo2 proof bytes or the Orchard binding signature. [4](#0-3) 

**Root cause — `proof_size_enforcement` (psbt_wrapper.rs lines 550–555):**

The helper only selects `ProofSizeEnforcement::Strict` vs `Unenforced`; neither variant triggers cryptographic proof verification. [5](#0-4) 

**Attacker-controlled fields that bypass all checks:**

| Field | Who sets it | Bridge check |
|---|---|---|
| Halo2 proof bytes | Attacker | None |
| Binding signature | Attacker | None |
| `value_balance` header field | Attacker | Compared to `amount` (also attacker-set) |
| Note ciphertext (decrypts to `amount`, `recipient_addr`) | Attacker (encrypted with public all-zeroes OVK) | Compared to `target_btc_address` |

An attacker constructs a bundle where all four fields are internally consistent but the Halo2 proof is garbage. Every bridge check passes; the Zcash network rejects the transaction.

---

### Impact Explanation

When the Zcash network rejects the transaction:

- The user's nZEC tokens remain locked inside the bridge (held from `ft_on_transfer`, never burned because `verify_withdraw` is never called).
- The `BTCPendingInfo` entry persists in bridge state.
- Recovery requires a privileged `cancel_withdraw` call (DAO or Operator role), which itself triggers another MPC signing round.

This matches the allowed Medium impact: **"stuck bridge state requiring operator intervention"** and **"attacker-triggered temporary locking of bridged funds."**

A single attacker can open many such stuck withdrawals simultaneously (each costs only the attacker's own nZEC), multiplying the operator burden and potentially delaying legitimate withdrawals that compete for the same UTXO pool.

---

### Likelihood Explanation

- **Reachable by any unprivileged user**: the entry point is `ft_transfer_call` on the nZEC token, which any token holder can call.
- **No special knowledge required**: the Orchard bundle format is public, the bridge OVK is a public constant (`[0u8; 32]`), and the `value_balance` field is a plain integer in the serialized bundle.
- **Low cost per attack**: the attacker only needs to hold nZEC; the tokens are not destroyed (they are stuck, not burned), so the attacker retains economic interest in recovering them via the cancel path.

---

### Recommendation

1. **Verify the Orchard proof on-chain** using the `orchard` crate's `Bundle::verify_proof` (or equivalent Halo2 verifier) before accepting the bundle. This is computationally expensive on NEAR but is the only way to guarantee the proof is valid without relying on the Zcash network.

2. **Alternatively, verify the binding signature** (`Bundle::binding_validating_key` + `redjubjub` verify), which is cheaper and proves `value_balance` is correctly committed.

3. **If on-chain proof verification is infeasible**, document the design decision explicitly and ensure the cancel/RBF path is fully automated (not requiring manual operator intervention) so stuck withdrawals are resolved without human action.

4. **Replace `BRIDGE_OVK = [0u8; 32]`** with a non-public key derived from the bridge's MPC key material, so that only the bridge can recover its own Orchard outputs.

pub fn extract_orchard_bundle(
    orchard_bundle_bytes: Option<Vec<u8>>,
    proof_size_enforcement: ProofSizeEnforcement,
) -> Result<Option<ParsedOrchardBundle>, String> {
    if let Some(orchard_bundle_bytes) = orchard_bundle_bytes {
        let mut reader = Cursor::new(orchard_bundle_bytes);
        let bundle = read_v5_bundle(&mut reader, proof_size_enforcement)
            .map_err(|_| "Failed to read orchard bundle".to_string())?
            .ok_or_else(|| "Orchard bundle is empty".to_string())?;

        // Check action count first per Orchard protocol requirements
        if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
            return Err(format!(
                "Orchard bundle must have {} actions, got {}",
                EXPECTED_ACTIONS_NUMBER,
                bundle.actions().len()
            ));
        }

        // Since we require exactly 1 action, directly recover the single output
        let ovk = orchard::keys::OutgoingViewingKey::from(BRIDGE_OVK);
        let (note, addr, _memo) = bundle
            .recover_output_with_ovk(0, &ovk)
            .ok_or_else(|| "Failed to recover Orchard output with bridge OVK".to_string())?;

        let value = note.value().inner();
        if value == 0 {
            return Err("Orchard output value must be non-zero".to_string());
        }

        Ok(Some(ParsedOrchardBundle {
            bundle,
            output: OrchardOutput {
                amount: value,
                recipient_addr: addr.to_raw_address_bytes(),
            },
        }))
    } else {
        Ok(None)
    }
}

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())
