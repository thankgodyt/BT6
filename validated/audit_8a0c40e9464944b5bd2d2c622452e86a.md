### Title
Missing Pause Check on `reject_refund` Allows State Mutation During Emergency Pause - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `reject_refund` function in the `satoshi-bridge` contract is publicly callable and permanently deletes refund requests from contract state, yet it carries no `#[pause]` guard. Every other state-mutating public entry point in the same file is decorated with `#[pause(except(roles(Role::DAO)))]`. During an emergency pause, an unprivileged caller can still invoke `reject_refund` and irreversibly remove refund requests, violating the pause invariant and potentially destroying user-submitted refund state that the operator intended to protect.

### Finding Description
The contract derives `Pausable` and applies `#[pause(except(roles(Role::DAO)))]` consistently across all state-mutating bridge functions: [1](#0-0) [2](#0-1) [3](#0-2) 

`reject_refund`, however, has no such annotation: [4](#0-3) 

The function has a permissionless execution path: any caller may invoke it when `is_already_deposited` is true — i.e., when the UTXO key is present in `verified_deposit_utxo` and the stored request has `executed == false`: [5](#0-4) 

`internal_reject_refund` then unconditionally removes the entry from `refund_requests`: [6](#0-5) 

### Impact Explanation
When the contract is paused — typically in response to a discovered vulnerability or abnormal state — operators expect all user-facing state mutations to be frozen. Because `reject_refund` bypasses the pause, an attacker can permanently delete refund requests during the pause window. A refund request represents a user's only on-chain record of their right to recover BTC that was never finalized as a deposit. Deleting it is irreversible: `internal_reject_refund` removes the entry with no recovery path. If the pause was triggered precisely because `verified_deposit_utxo` contains incorrect entries (e.g., due to a light-client or proof-verification bug), an attacker can exploit the permissionless path to cancel legitimate refund requests for affected UTXOs before operators can intervene, leaving users unable to recover their BTC.

**Impact: Low** — publicly reachable invariant violation (pause bypass) in a production bridge path; no direct theft under normal conditions, but can cause permanent loss of refund state and stuck user funds in an emergency scenario where the pause was triggered by a verification anomaly.

### Likelihood Explanation
The permissionless path of `reject_refund` is reachable by any NEAR account without any special role. The only precondition is that a refund request exists for a UTXO that is also present in `verified_deposit_utxo` with `executed == false`. This race condition (deposit verified after refund requested) is an explicitly documented and handled scenario in the codebase. The window is narrow under normal operation but becomes exploitable precisely when the contract is paused — the moment when an attacker has the most incentive to act before operators can respond.

### Recommendation
Add `#[pause(except(roles(Role::DAO)))]` to `reject_refund`, consistent with every other state-mutating public function in `bridge.rs`:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn reject_refund(&mut self, utxo_storage_key: String) {
```

This ensures that during an emergency pause, only the DAO can reject refund requests, preserving user-submitted state until operators have assessed and resolved the situation.

### Proof of Concept
1. User calls `request_refund` for UTXO `abc@0`; `request_refund_callback` stores the request with `executed = false`.
2. Concurrently, `verify_deposit` is called for the same UTXO and succeeds; `verified_deposit_utxo` now contains `abc@0`.
3. An anomaly is detected; the `PauseManager` calls `pa_pause` to halt the contract.
4. All functions decorated with `#[pause]` now revert for unprivileged callers.
5. Attacker calls `reject_refund("abc@0")`. Because `verified_deposit_utxo.contains("abc@0")` is `true` and `executed == false`, `is_already_deposited` evaluates to `true`, the `require!` passes, and `internal_reject_refund` permanently removes the refund request — with no pause check blocking the call.
6. The user's refund request is gone. If the pause was triggered because the deposit verification was later found to be erroneous (e.g., the nBTC mint failed silently), the user has no on-chain record to recover their BTC. [4](#0-3) [6](#0-5)

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
    }
```
