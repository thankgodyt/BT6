### Title
Unguarded `nbtc::new()` Initialization Allows Frontrunning During Token Migration, Granting Attacker Full Control of Active nBTC Token - (File: contracts/nbtc/src/lib.rs)

### Summary

The `nbtc` token contract's `new()` initializer has no caller restriction. Any unprivileged NEAR account can call it before the legitimate deployer if the contract is deployed and initialized in separate transactions. During the `migrate_to_new_token` flow, the bridge does not verify the new token's `controller` before completing the migration. An attacker who frontruns `new()` with themselves as `controller` (but the legitimate bridge as `bridge_id`) will pass all bridge-side checks, causing the migration to complete successfully with the attacker in control of the now-active nBTC token. The attacker can then call `upgrade_and_migrate` — which only checks `assert_controller()` — to deploy arbitrary WASM and mint unlimited nBTC.

---

### Finding Description

**Root cause — `contracts/nbtc/src/lib.rs`, `new()` (lines 58–91):**

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    // No check on env::predecessor_account_id()
    ...
}
```

The only guard is `!env::state_exists()`. There is no restriction on *who* may call `new()`. Any account can supply arbitrary `controller` and `bridge_id` values before the legitimate deployer does.

**Attack path through `migrate_to_new_token`:**

The bridge's `migrate_to_new_token` flow (`contracts/satoshi-bridge/src/nbtc/migration.rs`) requires the new nBTC contract to be deployed to a fresh account *before* the migration is triggered. The bridge then calls `mint` on the new token and, if successful, atomically updates its internal config to point to the new token:

```rust
// migration.rs line 118-119
require!(is_promise_success(), "Migration mint failed");
self.internal_mut_config().nbtc_account_id = new_token.clone();
```

The bridge performs **no verification of the new token's `controller`** at any point in `internal_migrate_to_new_token`, `migrate_to_new_token_mint`, or `migrate_to_new_token_resolve`. It only checks that `mint` calls succeed, which they will as long as `bridge_id` is set to the bridge's account ID.

**Upgrade escalation — `contracts/nbtc/src/migrate.rs`, `upgrade_and_migrate()` (lines 78–99):**

```rust
pub fn upgrade_and_migrate(&self) {
    self.assert_controller();   // only check
    let code = env::input()...;
    env::promise_batch_action_deploy_contract(promise_id, &code);
    ...
}
```

Once the attacker is `controller` of the live nBTC token, they can deploy arbitrary WASM to the nBTC contract account, enabling unlimited minting.

---

### Impact Explanation

**Critical.** The complete attack results in unauthorized minting of nBTC:

1. Attacker deploys arbitrary WASM to the nBTC contract (via `upgrade_and_migrate` as controller).
2. The new WASM can mint nBTC to any account without restriction.
3. Attacker redeems minted nBTC through the bridge's withdrawal flow to claim real BTC.

This constitutes unauthorized minting and theft of underlying BTC funds.

---

### Likelihood Explanation

**Medium-High.** The token migration is a documented, planned operational event (`migrate_to_new_token` with `Role::MigrationOperator`). The new nBTC contract must be deployed to a fresh account before the migration is triggered. NEAR transactions are public; any observer can detect a `deploy_contract` action to a new account and submit a `new()` call in the next block before the protocol's initialization transaction lands. The attacker's transaction cost is a single function call; the protocol's cost is redeployment or, if undetected, loss of control over the live token.

---

### Recommendation

Add a caller restriction to `new()` so only the contract's own account (i.e., the deployer) can initialize it:

```rust
#[init]
pub fn new(controller: AccountId, bridge_id: AccountId, ...) -> Self {
    require!(!env::state_exists(), "Already initialized");
    require!(
        env::predecessor_account_id() == env::current_account_id(),
        "Only the contract account may initialize"
    );
    ...
}
```

Alternatively, deploy and initialize atomically in a single batch transaction (deploy + function call), which eliminates the frontrunning window entirely. Additionally, `migrate_to_new_token` should verify the new token's `controller` matches the expected DAO/bridge account before proceeding.

---

### Proof of Concept

1. Protocol deploys new nBTC WASM to `new-nbtc.near` (transaction A, observed on-chain).
2. Attacker submits `new-nbtc.near::new({ controller: "attacker.near", bridge_id: "satoshi-bridge.near", ... })` (transaction B, frontruns protocol's init).
3. Protocol's own `new()` call fails with "Already initialized"; attacker's initialization is in effect.
4. `MigrationOperator` calls `satoshi-bridge.near::migrate_to_new_token({ new_token: "new-nbtc.near", accounts: [...] })`.
5. Bridge queries old token balances, then calls `new-nbtc.near::mint(...)` for each holder — succeeds because `bridge_id = "satoshi-bridge.near"` matches `env::predecessor_account_id()`.
6. `migrate_to_new_token_resolve` sees `is_promise_success() == true`, sets `nbtc_account_id = "new-nbtc.near"`. Migration complete.
7. Attacker calls `new-nbtc.near::upgrade_and_migrate(malicious_wasm)` — passes `assert_controller()` because `controller = "attacker.near"`.
8. Malicious WASM is deployed; attacker mints arbitrary nBTC and withdraws real BTC.

    pub fn upgrade_and_migrate(&self) {
        self.assert_controller();

        // Receive the code directly from the input to avoid the
        // GAS overhead of deserializing parameters
        let code = env::input().unwrap_or_else(|| env::panic_str("ERR_NO_INPUT"));
        // Deploy the contract code.
        let promise_id = env::promise_batch_create(&env::current_account_id());
        env::promise_batch_action_deploy_contract(promise_id, &code);
        // Call promise to migrate the state.
        // Batched together to fail upgrade if migration fails.
        env::promise_batch_action_function_call(
            promise_id,
            "migrate",
            b"",
            NO_DEPOSIT,
            env::prepaid_gas()
                .saturating_sub(env::used_gas())
                .saturating_sub(OUTER_UPGRADE_GAS),
        );
        env::promise_return(promise_id);
    }
