### Title
Missing `refund_address` chain-format validation in `request_refund_callback` causes permanently un-executable `RefundRequest` — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund_callback` stores `refund_address` without validating it against the bridge's configured chain. When `execute_refund` later calls `build_refund_output`, `Address::parse` panics on the cross-chain address. The `RefundRequest` is permanently stuck in `refund_requests` and can never be executed via the refund path. Recovery requires DAO/Operator intervention (`reject_refund`) or the relayer calling `verify_deposit`.

### Finding Description
`internal_request_refund` only checks that `refund_address` matches `deposit_msg.refund_address` as a raw string — no call to `Address::parse` validates the address format against `config.chain`. [5](#0-4) 

`request_refund_callback` stores the address verbatim: [1](#0-0) 

At execution time, `build_refund_output` calls `Address::parse(refund_address, config.chain.clone()).expect("Invalid refund address")`. For a Litecoin address on a Bitcoin bridge, base58 decode succeeds but neither the P2PKH prefix `[0x00]` nor the P2SH prefix `[0x05]` matches the Litecoin prefix `[0x30]`, so `parse` returns `Err(...)` and `.expect` panics: [8](#0-7) [3](#0-2) 

### Impact Explanation
The `RefundRequest` is stored and can never be executed via `execute_refund`. The deposit UTXO is **not** permanently locked — `verify_deposit` can still be called (it does not check `refund_requests`), which mints nBTC and marks the UTXO in `verified_deposit_utxo`. After that, anyone can call `reject_refund` to clean up the stuck request. However, until one of these operator/relayer actions occurs, the refund path is broken and the bridge state is inconsistent. This matches **Medium** impact: stuck bridge state requiring operator intervention.

### Likelihood Explanation
Any unprivileged user can trigger this by embedding a cross-chain address in `DepositMsg.refund_address` and calling `request_refund`. No special role is required. The attacker must fund the deposit address with real BTC, so there is a cost, but the attack is straightforward and locally testable.

### Recommendation
Validate `refund_address` against `config.chain` at the earliest possible point — in `internal_request_refund` before the light-client cross-contract call, or at minimum in `request_refund_callback` before storing the `RefundRequest`:

```rust
// In internal_request_refund or request_refund_callback:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This ensures any `RefundRequest` stored on-chain is always executable.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
