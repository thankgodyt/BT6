### Title
Missing Access Control on `sign_btc_transaction` Allows Attacker-Controlled `key_version` to Corrupt Withdrawal Signing — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is a public, permissionless function that accepts a fully attacker-controlled `key_version` parameter. Any NEAR account can call it against any pending withdrawal. If an attacker front-runs the legitimate relayer with a `key_version` that the MPC service accepts but that differs from the expected one, the MPC service produces a signature from the wrong key. That signature is stored in the PSBT slot, which is then permanently sealed by an "Already signed" guard. The resulting Bitcoin transaction is cryptographically invalid and can never be confirmed, permanently locking the user's nBTC in the bridge.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries only `#[payable]` and `#[pause]` — no `#[trusted_relayer]`, no `#[access_control_any]`, and no `env::predecessor_account_id()` check: [1](#0-0) 

Compare this with every deposit and withdrawal verification entry-point, which all carry `#[trusted_relayer]`: [2](#0-1) 

The `key_version` argument is forwarded verbatim into the MPC sign request: [3](#0-2) 

In the callback, the public key used to embed the signature into the PSBT is derived from the UTXO path — **not** from `key_version`: [4](#0-3) 

So if the MPC service signs with a key that corresponds to a different `key_version`, the resulting signature is stored against the wrong public key. Once stored, the slot is permanently sealed: [5](#0-4) 

When all inputs are "signed" (even with invalid signatures), the state machine advances to `PendingVerify` and the signed transaction bytes are finalized: [6](#0-5) 

The resulting Bitcoin transaction is cryptographically invalid and will be rejected by every Bitcoin node.

---

### Impact Explanation

The user's nBTC was already transferred to the bridge at withdrawal initiation (`ft_on_transfer`). After the signing is corrupted, the bridge holds an invalid signed transaction that can never confirm on Bitcoin. The user's nBTC is stuck in the bridge. Recovery requires a privileged `cancel_withdraw` call by DAO or Operator: [7](#0-6) 

This matches the allowed impact: **Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.**

---

### Likelihood Explanation

NEAR transactions are publicly observable before finalization. An attacker monitoring the mempool for `BTCPendingInfo` creation events can immediately call `sign_btc_transaction` with a crafted `key_version` before the legitimate relayer. The attack requires no special privilege, no leaked key, and no capital — only the gas cost of one NEAR transaction. The MPC chain-signatures protocol is designed to support key rotation via `key_version`, so the service is expected to accept values other than 0.

---

### Recommendation

Add a `#[trusted_relayer]` attribute (consistent with all other bridge entry-points) or an explicit `env::predecessor_account_id()` check to restrict callers of `sign_btc_transaction`. Additionally, validate `key_version` against a protocol-configured expected value stored in `Config` rather than accepting it as a free parameter from the caller.

---

### Proof of Concept

1. User calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message, creating a `BTCPendingInfo` in `PendingSign` state with `btc_pending_id = X`.
2. Attacker observes the `GenerateBtcPendingInfo` event for `X`.
3. Attacker calls:
   ```
   sign_btc_transaction(btc_pending_sign_id = X, sign_index = 0, key_version = 999)
   ```
   attaching the required yoctoNEAR deposit.
4. The bridge calls `ext_chain_signatures::sign` with `key_version = 999`. If the MPC service accepts this version, it returns a signature produced by a key that does not match the PSBT's expected public key.
5. `sign_btc_transaction_callback` stores the invalid signature at `signatures[0]`. The "Already signed" guard now blocks any future legitimate signing attempt for input 0.
6. If the withdrawal has only one input, `is_all_signed()` returns `true`, `extract_tx_bytes_with_sign()` is called, and the state advances to `PendingVerify` with an invalid transaction.
7. The relayer submits `verify_withdraw_v2` with this transaction's ID; Bitcoin light-client verification fails because the transaction never confirms.
8. The user's nBTC remains locked in the bridge indefinitely. Only a DAO/Operator `cancel_withdraw` can recover the funds.
