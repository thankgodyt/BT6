### Title
`PerasVote` and `PerasCert` Lack Signature Fields and Validation Is a No-Op Stub, Enabling Unauthorized Peras Vote/Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance — which is the only instance wired into the production inbound-processing pipeline — defines `PerasVote blk` and `PerasCert blk` without any cryptographic signature field, and implements `validatePerasVote` / `validatePerasCert` as stubs that perform no signature verification. Any unprivileged peer can therefore inject arbitrary Peras votes and certificates over the network that will be accepted, stored, and used to influence chain selection via Peras weight boosts.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines the data types and validation functions for Peras votes and certificates. A catch-all default instance is provided for all `StandardHash blk` types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  data PerasVote blk = PerasVote
    { pvVoteRound  :: PerasRoundNo
    , pvVoteBlock  :: Point blk
    , pvVoteVoterId :: PerasVoterId   -- no signature field
    }

  data PerasCert blk = PerasCert
    { pcCertRound        :: PerasRoundNo
    , pcCertBoostedBlock :: Point blk  -- no aggregate signature field
    }
``` [1](#0-0) 

Neither `PerasVote blk` nor `PerasCert blk` carries a cryptographic signature. The corresponding validation functions are explicit stubs:

```haskell
  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
``` [2](#0-1) 

`validatePerasCert` unconditionally returns `Right` for every certificate. `validatePerasVote` only checks that the claimed voter ID appears in the stake distribution — it performs no signature check because there is no signature to check.

These stub validators are directly wired into the production inbound processing pipeline. `makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB` pass them as the `validateVote` / `validateCert` callbacks:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2)

`processVotes` and `processCerts` receive batches of inbound network messages, call these validators, and on success store the results in the `PerasVoteDB` / `PerasCertDB` and trigger chain selection: [5](#0-4) [6](#0-5) 

A concrete `V1.PerasVote` type with a proper `pvSignature` field exists in `Peras/Vote/V1.hs`, and the `WFALS`/`EveryoneVotes` committee implementations do verify signatures. However, these are not connected to the `BlockSupportsPeras` instance used by the production pipeline — the catch-all default instance is what is actually invoked. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can craft and send `PerasVote blk` messages claiming any voter ID that appears in the stake distribution. Because `validatePerasVote` only checks stake-distribution membership and never verifies a signature, the vote is accepted as `ValidatedPerasVote` and stored. Once enough such fake votes accumulate to cross the quorum threshold, `updatePerasRoundVoteStates` generates a `ValidatedPerasCert`, which is then submitted to `addPerasCertAsync` and processed by chain selection. [8](#0-7) 

Separately, a peer can send a `PerasCert blk` directly. Because `validatePerasCert` always returns `Right`, every certificate is unconditionally accepted and forwarded to `addPerasCertAsync`, which can trigger a chain-selection fork switch to a block boosted by the fake certificate. [9](#0-8) 

The Peras weight boost is designed to make a boosted block's chain preferred over an unboosted chain of equal or greater length. An attacker who can inject a certificate for an arbitrary block can therefore cause an honest node to switch to a non-canonical chain, breaking chain-selection safety.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's Peras object-diffusion miniprotocol endpoint. No keys, stake, or privileged access are needed. The attacker only needs to know a valid `PerasVoterId` (a `KeyHash StakePool`), which is public on-chain data. The `PerasCert` attack requires even less: the attacker sends a certificate with any round number and block point, and it is accepted unconditionally.

---

### Recommendation

1. Add a cryptographic signature field to the `PerasVote blk` and `PerasCert blk` data types in the default `BlockSupportsPeras` instance, mirroring the concrete `V1.PerasVote` type which already carries `pvSignature :: VoteSignature PerasBLSCrypto`.
2. Replace the stub `validatePerasVote` and `validatePerasCert` implementations with real signature verification before these paths are reachable from the network. The `implVerifyVote` / `implVerifyCert` functions in `Committee/WFALS.hs` and `Committee/EveryoneVotes.hs` provide the correct reference implementation.
3. Until the concrete Cardano `BlockSupportsPeras` instance is implemented, gate the inbound Peras vote/certificate miniprotocol behind a feature flag so it is not reachable from untrusted peers.

---

### Proof of Concept

1. Connect to a node's Peras object-diffusion miniprotocol endpoint.
2. Enumerate any `PerasVoterId` (stake pool key hash) present in the current stake distribution — this is public ledger data.
3. Send a batch of `PerasVote blk` messages, each claiming that voter ID, targeting the same `(pvVoteRound, pvVoteBlock)`. No signature is required.
4. `processVotes` calls `validatePerasVote`, which passes the stake-distribution check and returns `Right` for each vote.
5. Once the accumulated `vpvVoteStake` crosses the quorum threshold, `updatePerasRoundVoteStates` generates a `ValidatedPerasCert` for the attacker-chosen block.
6. The certificate is submitted to `addPerasCertAsync`, which triggers chain selection. The boosted block's chain is now preferred, causing the node to switch to the attacker-chosen fork.

Alternatively, send a single `PerasCert blk` message with any `pcCertRound` and `pcCertBoostedBlock`. `validatePerasCert` returns `Right` unconditionally, the certificate is stored, and chain selection is triggered immediately. [10](#0-9)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
