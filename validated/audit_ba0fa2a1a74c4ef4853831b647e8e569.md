### Title
Incorrect `boundX` Constant in Taylor-Series Error Bound Causes Wrong Peras Committee Seat Assignment - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds, but `x = -lambda` (the Poisson parameter), so the correct value is `e^{lambda}`. For any voter whose expected seat count `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, causing the Taylor-series comparison to terminate with a wrong result. This is the direct analog of the Fuji Protocol white-paper bug: a wrong arithmetic constant in a critical formula produces incorrect outputs that diverge from the protocol specification.

---

### Finding Description

`localSortitionNumSeats` determines how many non-persistent Peras voting-committee seats a pool is granted via local sortition. It computes `lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake` and then calls:

```haskell
taylorExpCmpFirstNonLower
  3          -- boundX  ← MUST be e^{|x|} = e^{lambda}
  orders
  (-lambda)
``` [1](#0-0) 

The function's own documentation states:

> IMPORTANT: boundX must be e^{|x|} for correct error bounds [2](#0-1) 

The error term used inside `decideOne` is `errorTerm = abs(err' * boundX)`. [3](#0-2) 

When `lambda > ln(3) ≈ 1.099`, `e^{lambda} > 3`, so `boundX = 3` underestimates the true error bound. This causes `errorTerm` to be too small, making both the `Stop` branch (`cmp >= acc' + errorTerm`) and the `Below` branch (`cmp < acc' - errorTerm`) fire prematurely. The algorithm can therefore return an incorrect seat count — either granting seats to a pool that should receive none, or denying seats to a pool that should receive some.

The code itself acknowledges the problem with a TODO comment:

> TODO(peras): evaluate whether the limit used below (3) makes sense in this context … Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234 [4](#0-3) 

`lambda` exceeds `ln(3)` whenever a pool holds more than roughly 11% of the total non-persistent stake in a committee with 10 non-persistent seats (e.g., `lambda = 10 × 0.2 = 2.0`, giving `e^{lambda} ≈ 7.39` vs. the hardcoded `3`). This is a realistic scenario for any moderately large stake pool.

---

### Impact Explanation

`localSortitionNumSeats` is called in three security-critical paths:

1. **`implCheckShouldVote`** — decides whether the local node should cast a Peras vote.
2. **`implVerifyVote`** — verifies an incoming vote from a peer; a non-zero seat count is required for the vote to be accepted.
3. **`implVerifyCert`** — verifies a Peras certificate; each non-persistent voter's contribution is accepted only if their seat count is non-zero. [5](#0-4) [6](#0-5) 

A false-positive result (seat count > 0 when the correct answer is 0) allows an ineligible pool to have its vote or certificate contribution accepted. This is a **bypass of Peras voting committee eligibility checks**, enabling unauthorized block-boosting votes or certificates to be accepted by honest nodes. This falls squarely within the allowed impact scope: *bypass of certificate/vote checks that enables unauthorized vote or certificate acceptance*.

---

### Likelihood Explanation

- The condition `lambda > ln(3)` is met by any pool with more than ~11% of non-persistent stake in a 10-seat non-persistent committee, which is realistic on a live network.
- The attacker controls their VRF output (within the range produced by their key) and can select slots/elections where the incorrect error bound produces a favorable outcome.
- No privileged access, key compromise, or stake majority is required — only a pool with moderate stake and a crafted VRF output that lands in the region where the underestimated error bound flips the seat-count decision.
- The entry path is a crafted `WFALSNonPersistentVote` or `WFALSCert` message received over the network, processed by `implVerifyVote` / `implVerifyCert`.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct value `e^{lambda}`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^{lambda}
      orders
      (-lambda)
```

This matches the contract stated in the function's own documentation and eliminates the divergence between the specification (Poisson-based local sortition) and the implementation.

---

### Proof of Concept

Consider a committee with `numNonPersistentVoters = 10` and a pool holding 20% of non-persistent stake (`voterStake / totalNonPersistentStake = 0.2`):

- `lambda = 10 × 0.2 = 2.0`
- Correct `boundX = e^{2.0} ≈ 7.389`
- Actual `boundX = 3`
- Underestimate factor ≈ 2.46×

The first threshold is `orders[0] = normalizedVRFOutput / lambda`. For a VRF output near the boundary `normalizedVRFOutput ≈ lambda × e^{-lambda} = 2.0 × e^{-2.0} ≈ 0.2707`, the correct Taylor-series comparison would require many terms to resolve, but with `boundX = 3` the error bound is too tight and the algorithm terminates early. Depending on which side of the boundary the premature termination falls, the pool either receives 1 seat (false positive) or 0 seats (false negative). An attacker who can probe elections can identify VRF outputs that trigger the false-positive branch and submit votes or certificates that honest nodes will incorrectly accept. [7](#0-6)
