Audit Report

## Title
Unbound `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Relayer Fees - (File: near/omni-bridge/src/lib.rs)

## Summary
`sign_transfer` accepts a caller-controlled `fee_recipient: Option<AccountId>` parameter with no validation that it matches `env::predecessor_account_id()` or any stored value. Any trusted relayer can call `sign_transfer` on any pending non-zero-fee transfer, embed an arbitrary `fee_recipient` into the MPC-signed payload, submit that signature to the destination chain, and then call `claim_fee` on NEAR to collect the full relayer fee — diverting it from the legitimate relayer who serviced the transfer.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `sign_transfer` (decorated `#[trusted_relayer]`) accepts `fee_recipient: Option<AccountId>` from the caller and embeds it verbatim into `TransferMessagePayload` at line 498 with no check that it equals `env::predecessor_account_id()`:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    fee_recipient,   // taken directly from caller, never validated
    ...
};
```

The only validation performed is on the `fee` amount (lines 455–460), not on `fee_recipient`. The MPC signer then signs the full payload including the attacker-chosen `fee_recipient`.

In `sign_transfer_callback` (lines 655–658), the transfer message is only removed from storage when `fee.is_zero()`. For non-zero-fee transfers the message persists, meaning multiple trusted relayers can each obtain a valid MPC signature over the same transfer with different `fee_recipient` values.

On the destination chain, `OmniBridge.sol::finTransfer` verifies the MPC signature over the borsh-encoded payload (which includes `feeRecipient`) and marks the nonce as used. Back on NEAR, `claim_fee_callback` (lines 1079–1086) extracts `fee_recipient` from the on-chain proof and requires it to equal `predecessor_account_id`:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

Because the attacker embedded their own account as `fee_recipient` at signing time, this check passes trivially. The fee is then disbursed to the attacker via `send_fee_internal` (line 1133).

## Impact Explanation
This is a concrete fee mis-accounting impact: relayer fees — which are deducted from the user's locked/burned tokens — are permanently diverted to an attacker-controlled account. The user's transfer completes correctly (recipient and amount come from stored state, not from the caller), but the fee portion of the user's tokens is mis-accounted to the attacker rather than the legitimate relayer. This matches the allowed critical impact: *"fee mis-accounting… that changes user or protocol balances."*

## Likelihood Explanation
Becoming a trusted relayer requires only staking the configured amount (default 1,000 NEAR) and waiting the waiting period (default ~7 days). No admin approval is required by default — the DAO can reject applications but is not required to review them. Once trusted, the attacker can monitor the NEAR chain for any pending `TransferMessage` with a non-zero fee and call `sign_transfer` with `fee_recipient` set to their own account. The attack is fully on-chain, requires no off-chain coordination, is repeatable for every pending transfer, and is profitable at scale. The window of opportunity is not limited to a single block because the transfer message persists in storage for non-zero-fee transfers after signing.

## Recommendation
Bind `fee_recipient` to the caller inside `sign_transfer`. Replace the caller-supplied parameter with `env::predecessor_account_id()`, or add an explicit equality check before constructing the payload:

```rust
if let Some(ref recipient) = fee_recipient {
    require!(
        recipient == &env::predecessor_account_id(),
        BridgeError::InvalidFeeRecipient.as_ref()
    );
}
```

This ensures that only the relayer who calls `sign_transfer` can designate themselves (or an account they control) as the fee recipient, preventing any other trusted relayer from injecting an arbitrary address.

## Proof of Concept
```
Precondition: Attacker stakes ≥ 1,000 NEAR, waits the waiting period, becomes trusted relayer R2.

1. A pending TransferMessage exists: {transfer_id: T, fee: {fee: 100, ...}, recipient: <user>, ...}

2. R2 calls:
     sign_transfer(T, Some("r2.near"), Some(Fee{fee:100,...}))
   No check prevents R2 from setting fee_recipient = "r2.near".

3. MPC signs payload: {transfer_id:T, recipient:<user>, fee_recipient:"r2.near", amount:X, ...}
   sign_transfer_callback: fee is non-zero → transfer message NOT removed from storage.

4. R2 submits the signed payload to OmniBridge.sol via finTransfer().
   - completedTransfers[destinationNonce] = true  (nonce consumed)
   - Tokens released to <user>'s recipient address ✓
   - FinTransfer event emitted with feeRecipient="r2.near"

5. R2 generates an EVM Merkle proof of the FinTransfer event.

6. R2 calls claim_fee on NEAR with this proof.
   - claim_fee_callback: fee_recipient from proof = "r2.near" == predecessor_account_id ✓
   - R2 receives 100 tokens.

7. Legitimate relayer R1 attempts sign_transfer or claim_fee:
   - sign_transfer succeeds (message still in storage) but any finTransfer call fails
     (NonceAlreadyUsed) since the nonce was consumed in step 4.
   - R1 receives nothing. Fee is permanently diverted to R2.

Reproducible as a NEAR sandbox integration test by deploying the bridge contract,
registering two trusted relayers, initiating a transfer with non-zero fee, having R2
call sign_transfer with fee_recipient="r2.near" before R1, completing finTransfer,
and asserting R2 receives the fee while R1 receives nothing.
```
