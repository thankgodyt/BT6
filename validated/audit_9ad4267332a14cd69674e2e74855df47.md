Audit Report

## Title
Transfer Permanently Stuck When Normalized Amount Rounds to Zero — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` burns or locks user tokens and stores the transfer in `pending_transfers` without verifying that `normalize_amount(amount - fee) > 0`. `sign_transfer` then enforces this check after the fact, causing an unconditional panic with no recovery path. The burned or locked tokens are permanently unrecoverable.

## Finding Description
**Phase 1 — `init_transfer` (lines 523–619):** The only amount validation is `transfer_message.fee.fee < transfer_message.amount` at line 554. No normalization check is performed. The function proceeds to call `init_transfer_internal`, which burns (for bridge-deployed tokens) or locks (for native tokens) the user's funds, and stores the `TransferMessage` in `pending_transfers`. [1](#0-0) 

**Phase 2 — `sign_transfer` (lines 447–521):** `normalize_amount` is called at line 475 using floor division: [2](#0-1) 

For any token where `origin_decimals > decimals` (e.g., 24 vs 18, divisor = 10^6), any `amount_without_fee < 10^6` normalizes to zero. The `require!` at line 482 then panics unconditionally on every future call to `sign_transfer` for that transfer ID: [3](#0-2) 

**No recovery path:** `remove_transfer_message` inside `sign_transfer_callback` is only reached when MPC signing succeeds and `fee.is_zero()`. Since `sign_transfer` panics at line 482 before the MPC call at line 508 is ever made, `sign_transfer_callback` is never invoked: [4](#0-3) 

The transfer record remains in `pending_transfers` forever. The code's own inline comment at line 2781–2783 acknowledges that when `fee = 0`, sub-unit amounts "stay locked/burned," but does not address the case where the entire `amount_without_fee` normalizes to zero, leaving the transfer in an unresolvable stuck state: [5](#0-4) 

## Impact Explanation
For bridge-deployed tokens, the token is burned on NEAR in `init_transfer_internal` and the corresponding mint on the destination chain never occurs — permanent total loss of the transferred amount. For native NEAR-origin tokens, the amount is locked in the bridge contract with no unlock path — permanent freezing of bridged funds. Both outcomes match the Critical allowed impact: *permanent freezing of bridged funds across NEAR*.

## Likelihood Explanation
Any token registered with `origin_decimals > decimals` (a standard configuration, e.g., 24-decimal origin mapped to 18 NEAR decimals, divisor = 10^6) is affected. Any user sending fewer than `10^(origin_decimals - decimals)` units with `fee = 0` triggers the bug. The entry point is the standard NEP-141 `ft_transfer_call`, callable by any token holder with no special privileges. The condition can be reached accidentally (dust/small transfers) or deliberately by a griefing attacker.

## Recommendation
Add the normalization check inside `init_transfer` before `init_transfer_internal` is called, mirroring the guard already present in `sign_transfer`:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This must be placed after `token_address` is resolved but before `init_transfer_internal` is invoked, so that tokens are never burned or locked for an amount that cannot be bridged.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = 10^6).
2. User calls `ft_transfer_call` sending `amount = 500_000` units, `fee = 0`.
3. `ft_on_transfer` → `init_transfer`: check `0 < 500_000` passes; `init_transfer_internal` burns 500,000 tokens; transfer stored in `pending_transfers`.
4. Relayer calls `sign_transfer`: `normalize_amount(500_000, {24, 18}) = 500_000 / 1_000_000 = 0`; `require!(0 > 0, ...)` panics at line 482.
5. MPC call at line 508 is never reached; `sign_transfer_callback` is never invoked; `remove_transfer_message` is never called.
6. Transfer is permanently stuck; 500,000 burned tokens are unrecoverable.

A unit test can reproduce this by: (a) registering a token with the above decimals, (b) calling `init_transfer` with `amount = 500_000` and `fee = 0`, (c) asserting the transfer is stored in `pending_transfers`, (d) calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`, and (e) asserting the transfer record still exists and no unlock/mint occurred.
