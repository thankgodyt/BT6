### Title
`validatePerasVote` Stub Misses Cryptographic Signature Verification, Enabling Forged Vote Acceptance and Unauthorized Certificate Generation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate catch-all `BlockSupportsPeras` instance implements `validatePerasVote` by only checking stake-distribution membership, entirely omitting cryptographic signature verification. An unprivileged peer can forge votes for any voter ID present in the stake distribution. These forged votes are accepted, stored, and counted toward quorum. Once quorum is reached, a `ValidatedPerasCert` is generated and used to boost a peer-chosen block in chain selection, potentially causing honest nodes to prefer a non-canonical chain. A companion stub, `validatePerasCert`, unconditionally returns `Right` for every certificate, compounding the issue.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` provides stub implementations of both `validatePerasVote` and `validatePerasCert`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [1](#0-0) 

The function accepts a vote as `ValidatedPerasVote` if and only if the voter ID appears in the stake distribution. It does **not** verify the cryptographic vote signature, the VRF eligibility proof, or any other cryptographic property. The `_params` argument is discarded entirely.

The companion stub is even more permissive:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

This unconditionally returns `Right` for every certificate, performing zero validation.

The production inbound-vote path in `makePerasVotePoolWriterFromChainDB` calls `processVotes` with the validation function:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` then adds every vote that passes this stub check to the `PerasVoteDB`: [4](#0-3) 

Inside `implAddVote`, once quorum is reached via `updatePerasRoundVoteStates`, a `ValidatedPerasCert` is generated and returned as `AddedPerasVoteAndGeneratedNewCert cert`: [5](#0-4) 

That certificate is then forwarded to `addPerasCertAsync` in the ChainDB, which updates the `PerasWeightSnapshot` used by `preferAnchoredCandidate` during chain selection: [6](#0-5) 

The analog to the external report is exact: `validatePerasVote` updates the validated-vote accounting state (stores the vote, increments quorum counters) but misses calling the corresponding cryptographic verification step — precisely as `_applyPlatformFeeCloseErc20Gmx()` updated `pendingTokenWithdrawals` but missed calling `tokenTransferPlatformLogic()`.

---

### Impact Explanation

An unprivileged peer that knows any voter ID present in the current stake distribution can:

1. Craft `PerasVote` objects with that voter ID targeting an attacker-chosen block.
2. Send them via the object-diffusion mini-protocol; `processVotes` accepts them because `validatePerasVote` only checks stake-distribution membership.
3. Repeat for enough distinct voter IDs to reach the quorum threshold.
4. A `ValidatedPerasCert` is generated, boosting the attacker-chosen block in the `PerasWeightSnapshot`.
5. Honest nodes running chain selection with `preferAnchoredCandidate` now weight the attacker's target block more heavily and may switch to a non-canonical chain.

This is a **bypass of Peras vote/certificate verification** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" and "High: chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain" impact categories.

---

### Likelihood Explanation

The attack requires only:
- Knowledge of any voter ID in the public stake distribution (publicly observable on-chain).
- The ability to connect as a peer and send object-diffusion messages (no privileged access).
- Sending enough forged votes to reach quorum (bounded by the quorum threshold, not by any cryptographic secret).

No keys, no admin access, and no stake majority are required.

---

### Recommendation

Replace the stub `validatePerasVote` implementation with a full cryptographic check that:
1. Verifies the vote signature against the voter's public key from the stake distribution.
2. For non-persistent committee members, verifies the VRF eligibility proof.
3. Checks all other `PerasValidationErr` variants documented in the TODO.

Similarly, `validatePerasCert` must verify the aggregate BLS signature over the certificate before returning `Right`. Until these checks are implemented, the stub instance should not be reachable from any live peer-facing code path.

### Proof of Concept

```
Attacker (unprivileged peer):
  1. Observe stake distribution → extract voter IDs v1, v2, ..., vN
  2. For each vi, craft PerasVote { pvVoteRound = R, pvVoteBlock = attacker_block, pvVoteVoterId = vi }
     (no valid signature needed — validatePerasVote ignores _params and only checks lookupPerasVoteStake)
  3. Send batch to honest node via object-diffusion protocol
  4. processVotes calls validatePerasVote for each → all pass (voter IDs exist in stake distr)
  5. implAddVote accumulates votes; once quorum reached → AddedPerasVoteAndGeneratedNewCert cert
  6. cert boosts attacker_block in PerasWeightSnapshot
  7. preferAnchoredCandidate now weights attacker_block's chain higher
  8. Honest node may switch to attacker's non-canonical chain
```

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
