### Title
Permissionless `execute_refund` Front-Running Allows Attacker to Permanently Stall Any User's Refund - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` is callable by any NEAR account after the timelock elapses. An attacker who observes a pending `execute_refund` call can front-run it with the same `utxo_storage_key`. This causes the attacker's `BTCPendingInfo` (keyed by a deterministic PSBT ID) to be inserted first. The legitimate user's subsequent call then panics with `"pending info already exist"`. If the attacker never calls `sign_btc_transaction`, the refund is permanently stalled and requires DAO/Operator intervention to resolve.

---

### Finding Description

`execute_refund` is defined inside a `#[trusted_relayer] #[near] impl Contract` block but carries no role-gating of its own — only a timelock check for non-privileged callers. Test `test_refund_execute_twice_different_account` confirms that an unprivileged account (`bob`) can call `execute_refund` after the timelock passes. [1](#0-0) 

Inside `finalize_refund_with_psbt`, the `BTCPendingInfo` is inserted into `btc_pending_infos` keyed by `btc_pending_id`, which is derived deterministically from the PSBT content (same inputs, same refund output, same address). The insert is guarded by:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [2](#0-1) 

Because the PSBT is deterministic, both the attacker and the legitimate user would produce the **same** `btc_pending_id`. Whoever calls `execute_refund` first wins the insert; the second caller panics.

The `BTCPendingInfo` stores `account_id = caller`. Only the owning account can call `sign_btc_transaction` to advance the MPC signing pipeline. If the attacker owns the entry and never signs, the refund is frozen. [3](#0-2) 

Re-execution is blocked because `load_refund_request_for_execute` permits re-entry when `executed == true`, but `finalize_refund_with_psbt` immediately fails again on the duplicate-key check while the attacker's entry remains in `btc_pending_infos`. [4](#0-3) 

The stale entry cannot be self-cleaned: `internal_remove_refund_pending_tx_id` requires the refund request to already be gone (finalized), which cannot happen while the refund is stuck. [5](#0-4) 

---

### Impact Explanation

A user's BTC deposit is locked in the bridge's deposit address indefinitely. The refund cannot proceed without DAO/Operator intervention to cancel the attacker's stale `BTCPendingInfo`. This matches: **Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.**

The attacker cannot redirect funds (the `refund_address` is fixed in the `RefundRequest` set during `request_refund`) but can freeze the refund pipeline for any targeted UTXO.

---

### Likelihood Explanation

High. After the timelock elapses, `execute_refund` is callable by any NEAR account. All inputs needed to construct the call (`utxo_storage_key`) are observable on-chain from the `RefundRequested` event. No privileged key or special capability is required. The attacker only needs to submit the transaction before the legitimate user. [6](#0-5) 

---

### Recommendation

Bind the `BTCPendingInfo` creation to the original requester. Store the `requester` (the `predecessor_account_id()` at `request_refund` time) in `RefundRequest`, then inside `finalize_refund_with_psbt` require that `env::predecessor_account_id() == refund_request.requester` (or that the caller is DAO/Operator). This mirrors the external report's fix of using `msg.sender` instead of a caller-supplied address, ensuring only the original requester (or a privileged role) can create the `BTCPendingInfo`.

Alternatively, allow `execute_refund` to overwrite an existing `BTCPendingInfo` for the same UTXO when the existing entry has been idle (unsigned) beyond a configurable timeout, so the legitimate user can reclaim control without operator help.

---

### Proof of Concept

1. Alice deposits BTC; a trusted relayer calls `request_refund` on her behalf. `RefundRequested` event is emitted with `utxo_storage_key = "txid@0"`.
2. Timelock elapses.
3. Attacker observes Alice's pending `execute_refund("txid@0")` call in the NEAR mempool and submits the identical call first.
4. `finalize_refund_with_psbt` runs with `caller = attacker`, inserting `BTCPendingInfo { account_id: attacker, btc_pending_id: X, ... }`.
5. Alice's `execute_refund("txid@0")` executes next; `finalize_refund_with_psbt` tries to insert the same `btc_pending_id = X` → panics `"pending info already exist"`.
6. Attacker never calls `sign_btc_transaction`. Alice's BTC is frozen in the deposit address.
7. Alice cannot call `execute_refund` again (same panic). `internal_remove_refund_pending_tx_id` is blocked because the `RefundRequest` is still active. Only DAO/Operator can cancel the attacker's pending entry.
