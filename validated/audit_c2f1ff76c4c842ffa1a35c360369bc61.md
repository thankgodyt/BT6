### Title
`chain_signatures_root_public_key` Is Write-Once and Cannot Be Updated After Initial Sync - (File: contracts/satoshi-bridge/src/api/management.rs)

### Summary
`sync_chain_signatures_root_public_key` enforces a one-time-write guard that permanently prevents the MPC root public key from being refreshed. Because every BTC address derivation and every PSBT signing operation in the bridge depends on this stored key, a rotation of NEAR's chain-signatures root public key renders all future withdrawals and refunds permanently broken with no on-chain recovery path.

### Finding Description
`sync_chain_signatures_root_public_key` in `contracts/satoshi-bridge/src/api/management.rs` contains the following guard:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    require!(
        self.internal_config()
            .chain_signatures_root_public_key
            .is_none(),
        "Already sync"
    );
    self.sync_chain_signatures_root_public_key_promise()
}
``` [1](#0-0) 

Once `chain_signatures_root_public_key` is set to `Some(...)` by `sync_root_public_key_callback`, the `is_none()` check causes every subsequent call to `sync_chain_signatures_root_public_key` to panic with `"Already sync"`. There is no alternative function to overwrite or clear the stored key, and `ConfigUpdate` (the only other config-mutation path) does not include `chain_signatures_root_public_key` as an updatable field. [2](#0-1) [3](#0-2) 

The stored key is the sole input to every derived BTC public key and deposit address in the bridge:

```rust
pub fn generate_public_key(&self, path: &str) -> Vec<u8> {
    let mpc_pk = crypto_shared::near_public_key_to_affine_point(
        self.internal_config()
            .chain_signatures_root_public_key
            .clone()
            .expect("Missing chain_signatures_root_public_key"),
    );
    ...
}
``` [4](#0-3) 

`generate_btc_public_key` and `generate_utxo_chain_address` both call `generate_public_key`, and `internal_sign_btc_transaction` calls `generate_btc_public_key` to build the public-key list used to compute the PSBT hash-to-sign and to save the returned signature. [5](#0-4) 

### Impact Explanation
When NEAR's chain-signatures MPC network rotates its root public key (a documented operational event), the bridge continues to derive BTC public keys from the stale stored key. The MPC network signs using the new key, so the signatures it returns correspond to a different public key than the one the bridge computed. `psbt.save_signature` stores a signature that does not match the PSBT's expected public key, causing `psbt.extract_tx_bytes_with_sign` to produce an invalid transaction. Every withdrawal and refund signing attempt fails permanently. All user funds locked in bridge-controlled UTXOs become inaccessible without a contract upgrade. This matches the **Medium** impact class: stuck bridge state requiring operator intervention, with all in-flight and future withdrawals blocked.

### Likelihood Explanation
NEAR's chain-signatures protocol explicitly supports key versioning (`key_version` field in `SignRequest`) precisely because root key rotation is an anticipated operational event. The bridge already passes `key_version` as a caller-supplied parameter, acknowledging that multiple key versions may exist. Once a rotation occurs, the bridge has no on-chain mechanism to recover; a contract upgrade is the only remediation. [6](#0-5) 

### Recommendation
Remove the `is_none()` guard so that `sync_chain_signatures_root_public_key` can be called again after a key rotation:

```rust
pub fn sync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    // Remove the require! that blocks re-sync
    self.sync_chain_signatures_root_public_key_promise()
}
```

Additionally, consider storing the active `key_version` alongside the root public key so that signing requests automatically use the correct version after a rotation.

### Proof of Concept
1. DAO calls `sync_chain_signatures_root_public_key` (with 1 yoctoNEAR). `sync_root_public_key_callback` sets `chain_signatures_root_public_key = Some(old_key)` and derives `change_address` from `old_key`.
2. NEAR's MPC network rotates its root public key to `new_key`.
3. DAO attempts to call `sync_chain_signatures_root_public_key` again to refresh the stored key. The call panics: `"Already sync"`.
4. A user initiates a withdrawal: `ft_transfer_call` → `ft_on_transfer` → `internal_sign_btc_transaction`. The bridge calls `generate_btc_public_key(path)` which derives a public key from `old_key`. It then calls `sign_promise` asking the MPC to sign with `new_key` (via `key_version`).
5. The MPC returns a signature produced under `new_key`. `sign_btc_transaction_callback` calls `generate_btc_public_key` again (still using `old_key`) and passes the mismatched public key to `psbt.save_signature`. The resulting transaction is cryptographically invalid.
6. Every subsequent withdrawal and refund signing attempt fails in the same way. All bridge-controlled UTXOs are permanently inaccessible without a contract upgrade. [7](#0-6) [8](#0-7)

            BtcPublicKey::from_slice(&public_key_bytes).expect("Invalid public key bytes");

            .to_string()
            .parse()
            .unwrap()
    }
