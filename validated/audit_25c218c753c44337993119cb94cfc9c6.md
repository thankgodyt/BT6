### Title
Mixed Transparent + Orchard Withdrawal Causes Accounting Mismatch and Stuck Withdrawal State — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

### Summary

`PsbtWrapper::new` has no mutual-exclusion guard between a non-empty transparent `output` vector and a non-`None` `orchard_bundle_bytes`. When both are supplied, `add_extra_outputs` pushes the Orchard amount into `actual_received_amounts` on top of the already-populated transparent output amounts, producing a vector with more than one entry and a sum that does not match the user's deposited `amount`, causing the withdrawal to be rejected and the user's nZEC to be stuck in the bridge.

### Finding Description

**Entry point — `ft_on_transfer_callback`:** [1](#0-0) 

The callback receives user-controlled `output: Vec<TxOut>` and `chain_specific_data: Option<ChainSpecificData>` (which carries `orchard_bundle_bytes`). Both are passed directly to `PsbtWrapper::new`.

**No mutual-exclusion guard in `PsbtWrapper::new`:** [2](#0-1) 

The only check is `!output.is_empty() || orchard_bundle_bytes.is_some()`. There is no `require!(output.is_empty() || orchard_bundle_bytes.is_none(), ...)` guard. An attacker can supply both a non-empty transparent `output` vector **and** a valid Orchard bundle simultaneously.

**`add_extra_outputs` unconditionally appends the Orchard amount:** [3](#0-2) 

When called during `check_withdraw_psbt` / `create_btc_pending_info`, this pushes `orchard.amount()` into `actual_received_amounts` regardless of whether transparent outputs are already present. The result is a vector with `len > 1` whose sum is `transparent_total + orchard_amount`.

**`check_psbt_chain_specific` does not enforce mutual exclusion either:** [4](#0-3) 

It validates the Orchard bundle recipient address when `has_orchard_bundle()` is true, but never asserts that `vout` must be empty in that case.

### Impact Explanation

The user deposits `amount` nZEC. The bridge expects to burn exactly `amount`. With both transparent outputs and an Orchard bundle present, `actual_received_amounts` sums to `transparent_total + orchard_amount`. Unless the attacker crafts these to sum exactly to `amount` (which would still produce an on-chain-invalid Zcash transaction), the accounting check fails and the withdrawal is rejected — leaving the user's nZEC locked in the bridge with no automatic refund path. This is a **Medium** impact: permanent or long-term locking of user funds requiring operator intervention.

### Likelihood Explanation

The path is fully public: any user calling `ft_transfer_call` with a crafted `msg` containing both a non-empty `output` array and a valid `orchard_bundle_bytes` field reaches this code. No privileged role is required.

### Recommendation

Add a mutual-exclusion guard at the top of `PsbtWrapper::new`:

```rust
require!(
    output.is_empty() || orchard_bundle_bytes.is_none(),
    "cannot specify both transparent outputs and an Orchard bundle"
);
```

And mirror the same check in `from_original_psbt`.

### Proof of Concept

1. Call `ft_transfer_call` on the nZEC token contract, transferring `X` nZEC to the bridge with a `msg` JSON containing:
   - `input`: one valid UTXO outpoint
   - `output`: one transparent `TxOut` with value `Y` (0 < Y < X)
   - `chain_specific_data.orchard_bundle_bytes`: a valid Orchard bundle encoding amount `Z` (0 < Z, Y + Z ≠ X)
2. `ft_on_transfer_callback` constructs `PsbtWrapper` with both fields populated — no panic.
3. `add_extra_outputs` appends `Z` to `actual_received_amounts`, which already contains `Y`.
4. The accounting check sees `Y + Z ≠ X`, rejects the withdrawal, and the `X` nZEC remain locked in the bridge.

**Caveat:** I was unable to read `create_btc_pending_info` and `check_withdraw_psbt` directly (those files were not returned in the available reads), so the exact line where the sum-vs-amount comparison occurs is unconfirmed. However, the invariant violation in `PsbtWrapper::new` and `add_extra_outputs` is confirmed from the production source, and the downstream accounting failure is the only consistent outcome given the mismatch.
