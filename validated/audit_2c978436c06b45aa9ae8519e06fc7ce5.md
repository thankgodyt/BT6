Audit Report

## Title
Detached `burn` Call in `init_transfer_internal` Emits `InitTransferEvent` Without Guaranteed Token Destruction — (File: near/omni-bridge/src/lib.rs)

## Summary
`burn_tokens_if_needed` schedules a cross-contract `burn` via `.detach()`, meaning its result is never verified. Because `InitTransferEvent` is emitted in the same receipt — before the detached burn receipt executes — any burn failure is silently discarded while the event is already committed on-chain, allowing relayers to mint tokens on the destination chain without the corresponding NEAR-side supply being destroyed.

## Finding Description
`burn_tokens_if_needed` (L1806–1813) issues a cross-contract `burn` with `.detach()` and a budget of only `BURN_TOKEN_GAS = Gas::from_tgas(3)` (L72):

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // result never checked
    }
}
```

`init_transfer_internal` (L1829–1865) calls this helper and then immediately emits `InitTransferEvent` in the same receipt:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);  // L1851
self.lock_tokens_if_needed(...);
// ...
env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string()); // L1863
U128(0)
```

In NEAR's execution model, `.detach()` schedules the burn as a separate receipt that runs **after** the current function returns. `env::log_str` (which commits `InitTransferEvent`) executes in the current receipt. There is no callback, no revert path, and no on-chain signal if the burn receipt fails. The same structural flaw exists in `fin_transfer_send_tokens_callback` (L1702–1718) for the refund path.

`MINT_TOKEN_GAS` is already 5 TGas (L73) for the analogous mint operation, making the 3 TGas burn budget comparatively tight. The project's own `CLAUDE.md` (L228) explicitly flags: *"Detached promises should only be used for non-critical operations"* — burning bridged token supply is a critical operation.

## Impact Explanation
If the detached burn receipt fails after `InitTransferEvent` has been emitted:
- The user's tokens are **not** destroyed on NEAR; they remain in the bridge contract's balance.
- Relayers observing `InitTransferEvent` call `finTransfer` on the destination chain, minting the equivalent amount.
- The result is **token supply inflation / double-spending**: the same economic value exists simultaneously on NEAR (un-burned, held by the bridge) and on the destination chain (freshly minted).

This matches the critical impact class: *"unauthorized minting or balance manipulation that changes user or protocol balances."*

## Likelihood Explanation
Under normal conditions with a minimal `burn` implementation, 3 TGas may be sufficient. However, the failure mode is realistic because: (1) 3 TGas leaves almost no headroom beyond cross-contract call overhead; (2) any token contract upgrade adding storage operations, hooks, or events would push the call over the limit; (3) the failure is completely silent — no callback, no revert, no on-chain error — making detection and recovery impossible without off-chain monitoring. An unprivileged user triggers this path via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer_internal` flow.

## Recommendation
Replace the detached burn with a chained callback that verifies success before emitting `InitTransferEvent`. Move `env::log_str(InitTransferEvent …)` into the callback and revert (refund the user) if the burn promise failed. Also increase `BURN_TOKEN_GAS` to at least 5–10 TGas to match `MINT_TOKEN_GAS` and comparable token operations.

```rust
ext_token::ext(token_id.clone())
    .with_static_gas(BURN_TOKEN_GAS)
    .burn(transfer_message.amount)
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(INIT_TRANSFER_EMIT_GAS)
            .init_transfer_emit_callback(transfer_message, storage_owner),
    )
```

## Proof of Concept
1. Deploy a bridge-deployed `omni-token` on NEAR localnet.
2. Call `ft_transfer_call(bridge, 1000, init_transfer_msg)` as a normal user.
3. Inside `ft_on_transfer` → `init_transfer_internal`: `burn_tokens_if_needed` schedules a detached burn receipt with 3 TGas; `InitTransferEvent` is emitted in the current receipt; `ft_on_transfer` returns `U128(0)` — tokens are not refunded.
4. Simulate burn receipt failure by deploying a token contract whose `burn` function panics, or by adding enough logic to exceed 3 TGas.
5. Observe: the burn receipt fails silently; the bridge contract retains the 1000 tokens.
6. A relayer observing `InitTransferEvent` calls `finTransfer` on the EVM side, minting 1000 tokens to the destination recipient.
