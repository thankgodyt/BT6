### Title
Peras Certificate Verification Bypass via Unconditional `validatePerasCert` Stub Allows Unprivileged Peer to Displace Legitimate Certificates and Corrupt Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the production `BlockSupportsPeras` instance unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. This is the only implementation wired into the production Peras certificate diffusion path (`makePerasCertPoolWriterFromChainDB`). Because the `PerasCertDB` stores at most one certificate per round and silently drops duplicates, a malicious peer that races to inject a fabricated certificate for round R before the legitimate one arrives permanently displaces the legitimate certificate for that round. Chain selection then uses the attacker-supplied boost, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

**Structural parallel to the external report.** In the external report, `setClientOwner` lacks a check that the target address already holds a privileged name, so an "unrequired" client can overwrite a "required" client's privilege. Here, `validatePerasCert` lacks any check on the certificate's authenticity, so an unprivileged peer can inject a fake certificate that occupies a round slot before the legitimate certificate arrives, permanently removing the legitimate certificate's chain-selection boost.

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The sole implementation of `validatePerasCert` for all block types is the default instance in `SupportsPeras.hs`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the **only** definition of `validatePerasCert` in the entire codebase (confirmed by grep: the symbol appears only in `SupportsPeras.hs` and the call sites in `PerasCert.hs`). The error type is equally hollow:

```haskell
data PerasValidationErr blk
  = PerasValidationErr   -- single constructor, no fields
``` [2](#0-1) 

**Production call site — `makePerasCertPoolWriterFromChainDB`:**

**`processCerts` — the gate that never closes:**

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validateCert` is `validatePerasCert mkPerasParams` which always returns `Right`, the `([], validatedCerts)` branch is always taken and every inbound certificate is unconditionally stored.

**`PerasCertDB` enforces first-writer-wins per round:**

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    writeTVar pcdbState ...
    pure AddedPerasCertToDB
``` [5](#0-4) 

Once a certificate for round R is stored, any subsequent certificate for the same round — including the legitimate one — is silently dropped as `PerasCertAlreadyInDB`.

**Network entry point confirmed:**

The `makePerasCertPoolWriterFromChainDB` writer is wired into the node-to-node `PerasCertDiffusion` mini-protocol handler (`aPerasCertDiffusionClient` in `NodeToNode.hs`), which is reachable by any connecting peer. [6](#0-5) 

---

### Impact Explanation

A malicious peer that wins the race for round R installs a `PerasCert` boosting an arbitrary block B′ of its choosing. The `PerasWeightSnapshot` used by chain selection then carries a boost for B′ instead of the canonical block B. Depending on the Peras weight parameters, this can cause the node to prefer a fork containing B′ over the honest chain, constituting a chain selection error triggered by an unprivileged peer with no keys or stake.

This maps to the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

The attack requires only a network connection and the ability to send a well-formed `PerasCert` message (two fields: a round number and a block point) before the legitimate certificate for that round arrives. No cryptographic material, stake, or operator access is needed. The `PerasCert` wire type carries no signature field in the stub instance, so the attacker constructs a valid on-wire message trivially. The race window is the propagation delay of the legitimate certificate across the network, which is non-zero and exploitable by a peer with low latency to the target node.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the Peras diffusion path is enabled in production. At minimum, validate the aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's public keys, verify voter eligibility proofs, and check that the quorum threshold is met. The concrete `V1.PerasCert` type already carries `pcSignature` and `pcVoters` fields for this purpose. [7](#0-6) 

2. **Remove or gate the stub instance.** The `-- TODO: degenerate instance for all blks to get things to compile` comment acknowledges this is temporary. The stub should be replaced with a proper Cardano-specific instance before the protocol is activated, or the diffusion path should be disabled behind a feature flag until then. [8](#0-7) 

3. **Add a property test** that sends a certificate with an invalid signature through `processCerts` and asserts it is rejected. The absence of such a test is the direct analog to the unit-test gap noted in the external report.

---

### Proof of Concept

```
Setup:
  - Node N running with Peras enabled, connected to honest peers H and malicious peer M.
  - Honest peers H hold a legitimate certificate C_legit for round R,
    boosting canonical block B (on the honest chain).
  - Attacker controls peer M and a fork block B' (not on the canonical chain).

Attack sequence:
  1. M connects to N via the node-to-node PerasCertDiffusion mini-protocol.
  2. M sends PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B') }.
  3. processCerts calls validatePerasCert mkPerasParams on M's cert.
     → validatePerasCert always returns Right; cert passes "validation".
  4. implAddCert checks: roundNo R not yet in pcdsCertIds → stores M's cert.
     PerasCertDB now contains: { R → boost(B') }.
  5. Honest peers H later send C_legit { pcCertRound = R, pcCertBoostedBlock = point(B) }.
  6. implAddCert checks: roundNo R already in pcdsCertIds → returns PerasCertAlreadyInDB.
     C_legit is silently discarded.
  7. getWeightSnapshot returns boost for B' (not B).
  8. Chain selection compares honest chain (containing B) against fork (containing B'):
     fork receives Peras boost weight; honest chain does not.
     Node may switch to the fork, accepting B' as part of its preferred chain.
```
