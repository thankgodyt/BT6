### Title
Incorrect `boundX` Constant in Peras Local Sortition Taylor-Expansion Seat-Count Check Causes Incorrect Vote Authorization - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3` instead of the mathematically required `e^lambda`. The function's own contract comment states `boundX must be e^{|x|}` for correct error bounds. For any non-persistent Peras voter whose Poisson parameter `lambda > ln(3) ≈ 1.099`, the error term is underestimated, causing the Taylor-expansion comparison to make incorrect "BELOW" decisions and return a higher seat count than the voter deserves. Because `implVerifyVote` and `implVerifyCert` call `localSortitionNumSeats` to authorize incoming votes and certificates, this is a reachable formula/implementation mismatch that can accept votes that should be rejected.

---

### Finding Description

`localSortitionNumSeats` determines how many non-persistent committee seats a Peras voter is granted by comparing their normalized VRF output against Poisson-distribution thresholds via a Taylor-expansion of `e^x`:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; comment says this must be e^{|x|}
      orders
      (-lambda)
``` [1](#0-0) 

The function's contract is explicit:

```haskell
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
taylorExpCmpFirstNonLower ::
  -- | boundX = e^{|x|} for correct error estimation
  a ->
``` [2](#0-1) 

With `x = -lambda`, the required value is `e^lambda`. The error term computed inside `decideOne` is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX = 3 < e^lambda` (i.e., `lambda > ln 3 ≈ 1.099`), `errorTerm` is smaller than the true Taylor-series remainder. The "BELOW" guard:

```haskell
| cmp < acc' - errorTerm = Below (n + 1) err' acc' divisor'
```

fires prematurely, causing the algorithm to classify a threshold as "certainly below `e^{-lambda}`" when it is not. Each such misclassification advances the seat counter by one, so the voter is granted more seats than the Poisson distribution warrants.

The developers acknowledge the uncertainty in a TODO comment:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3) 

`lambda` is computed as:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [5](#0-4) 

A voter holding more than `ln(3)/numNonPersistentVoters ≈ 1.1%` of the total non-persistent stake (with a 100-seat committee) already exceeds the threshold. Larger committees or more concentrated stake distributions push the threshold even lower.

---

### Impact Explanation

`localSortitionNumSeats` is called in three production paths:

1. **`implCheckShouldVote`** – the voter's own eligibility check before forging a vote.
2. **`implVerifyVote`** – verifying an incoming non-persistent vote; a non-zero seat count is required to accept the vote.
3. **`implVerifyCert`** – verifying an incoming Peras certificate; each non-persistent voter's seat count is verified. [6](#0-5) [7](#0-6) 

An inflated seat count means:
- A vote or certificate from a voter who should have zero seats passes the `nonZero numSeats` guard and is accepted.
- A voter with legitimately one seat is credited with two or more, multiplying their voting weight.

Both outcomes weaken Peras vote/certificate authorization, qualifying as a **Medium** impact under the allowed scope: *"Public node API or miniprotocol flaw that … materially weakens … vote, certificate … authorization."*

---

### Likelihood Explanation

The condition `lambda > ln(3)` is met whenever a non-persistent voter's proportional stake exceeds `ln(3) / numNonPersistentVoters`. For a 100-seat non-persistent committee this is ~1.1% of total non-persistent stake — a realistic threshold for any moderately large pool. The issue is deterministic (not probabilistic): every node computes the same inflated seat count, so the incorrect authorization is accepted network-wide without disagreement. No key compromise or stake majority is required; any registered pool operator whose stake crosses the threshold is affected on every election.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound `e^lambda`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} where x = -lambda
      orders
      (-lambda)
```

This matches the contract stated in the function's own documentation and the analogous approach used in `checkLeaderNatValue` in `cardano-ledger`. The existing GitHub issue (#234) should be resolved with this fix.

---

### Proof of Concept

**Setup:** Non-persistent committee of 50 seats, total non-persistent stake = 100 ADA, voter stake = 3 ADA.

```
lambda = 50 * 3 / 100 = 1.5
e^lambda = e^1.5 ≈ 4.48
boundX used = 3  (< 4.48, so error bound is underestimated)
```

**Trace through `decideOne` for threshold `orders[0]`:**

With `x = -1.5`, the Taylor partial sums converge to `e^{-1.5} ≈ 0.2231`. Suppose `orders[0] = 0.230` (just above `e^{-1.5}`). With the correct `boundX = 4.48`, `errorTerm` is large enough that the algorithm remains uncertain and continues iterating. With `boundX = 3`, `errorTerm` is smaller; the "BELOW" guard `cmp < acc' - errorTerm` fires, classifying `orders[0]` as certainly below `e^{-1.5}` — incorrectly advancing the seat count from 0 to 1.

The voter submits a `WFALSNonPersistentVote` with `numSeats = 1`. `implVerifyVote` calls `localSortitionNumSeats`, gets `1`, passes the `nonZero` check, and accepts the vote — even though the correct seat count is 0.
