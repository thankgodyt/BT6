### Title
Peras Certificate Validation Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production `BlockSupportsPeras` typeclass instance used for all block types contains a stub `validatePerasCert` that unconditionally returns `Right` (success) without performing any cryptographic or structural validation. This stub is wired directly into the live Peras certificate ingest path (`PerasCert.hs`), meaning any Peras certificate received from an unprivileged peer is accepted, stored in the `PerasCertDB`, and used to boost blocks in chain selection — with zero verification.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gating function for accepting inbound Peras certificates. A catch-all degenerate instance is provided for every `StandardHash blk`:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }

The `processCerts` function in `PerasCert.hs` calls `validateCert` on each inbound certificate and only rejects a batch when at least one certificate returns `Left`. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is stored:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Once stored, certificates are consumed by `implGetWeightSnapshot` in `PerasCertDB/Impl.hs`, which builds the `PerasWeightSnapshot` used to boost blocks during chain selection:

```haskell

``` [5](#0-4) 

A parallel stub exists for `validatePerasVote` — it performs no cryptographic signature check, only a stake-distribution membership lookup — and `getPerasCertInBlock` always returns `Nothing`, meaning certificates embedded in blocks are never extracted:

```haskell

### Impact Explanation

An unprivileged peer connected via the ObjectDiffusion miniprotocol can craft and send arbitrary `PerasCert` values — with any `pcCertRound` and any `pcCertBoostedBlock` — and the receiving node will accept them unconditionally, store them in the `PerasCertDB`, and apply their weight boost to the targeted block during chain selection. This constitutes a **bypass of Peras certificate validation** that enables unauthorized certificate acceptance and can cause an honest node to prefer a non-canonical or attacker-chosen chain over the legitimate heaviest chain, violating Peras chain-selection safety.

### Likelihood Explanation

Any peer that can establish an ObjectDiffusion connection (i.e., any node-to-node peer) can exploit this. No stake, no keys, and no privileged access are required. The code is on the active production path — `makePerasCertPoolWriterFromChainDB` is wired into `NodeToNode.hs` — so the vulnerability is reachable in any deployment that has Peras object diffusion enabled.

### Recommendation

1. Replace the degenerate `validatePerasCert` stub with a real implementation that verifies the certificate's cryptographic proof, committee membership, and round/block consistency before returning `Right`.
2. Similarly implement real cryptographic verification in `validatePerasVote`.
3. Implement `getPerasCertInBlock` to extract certificates embedded in blocks once the HFC plumbing is in place.
4. Until real validation is implemented, the degenerate instance should not be used in any production ingest path; the `processCerts`/`processVotes` callers should require a properly instantiated `BlockSupportsPeras` constraint rather than falling through to the catch-all stub.

### Proof of Concept

1. Connect a malicious peer to a target node via the ObjectDiffusion miniprotocol.
2. Send a `PerasCert` with `pcCertRound = R` and `pcCertBoostedBlock = P` where `P` is any block point the attacker wishes to boost (e.g., a minority-fork block).
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which unconditionally returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })`.
4. The certificate is stored in `PerasCertDB` via `addCert`.
5. `implGetWeightSnapshot` includes the forged certificate's boost in the `PerasWeightSnapshot`.
6. Chain selection now applies the attacker-specified boost to the attacker-chosen block, potentially causing the node to prefer a non-canonical chain.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
