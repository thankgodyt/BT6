### Title
Empty `PerasVoteStakeDistr` Hardcoded in Vote Diffusion Handler Makes All Peras Votes Unconditionally Invalid - (`File: ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Network/NodeToNode.hs`)

---

### Summary

The production node-to-node vote diffusion handler passes a hardcoded empty `PerasVoteStakeDistr mempty` as the stake distribution for validating inbound Peras votes. Because vote validation performs a map lookup against this distribution, every vote received from every peer fails validation unconditionally. This makes it impossible for any Peras round to accumulate enough validated stake to reach quorum via peer vote diffusion, permanently disabling the Peras chain-boosting mechanism. Additionally, the validation failure path throws a `PerasVoteInboundException`, which disconnects the sending peer.

---

### Finding Description

In `hPerasVoteDiffusionClient`, the production handler for the Peras vote diffusion mini-protocol, the `STM m PerasVoteStakeDistr` action supplied to `makePerasVotePoolWriterFromChainDB` is hardcoded to `pure (PerasVoteStakeDistr mempty)`: [1](#0-0) 

The code comment itself acknowledges the consequence: *"Note that the empty stake distribution will cause all votes to be considered invalid."*

The call chain that makes every vote fail:

1. `makePerasVotePoolWriterFromChainDB` stores `getStakeDistrSTM = pure (PerasVoteStakeDistr mempty)` and uses it inside `processVotes` to validate each inbound vote: [2](#0-1) 

2. `validatePerasVote` calls `lookupPerasVoteStake`, which does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. With an empty map this always returns `Nothing`, so the function always returns `Left PerasValidationErr`: [3](#0-2) 

3. `processVotes` treats any validation failure as a fatal error and throws `PerasVoteValidationError`, which disconnects the sending peer: [4](#0-3) 

The `stakeAboveThreshold` quorum check in `votesReachQuorum` is therefore never reached for any vote received over the network — the vote is rejected before it can contribute stake toward quorum: [5](#0-4) 

---

### Impact Explanation

The Peras protocol extends Ouroboros with a stake-weighted voting mechanism: when a quorum of committee members vote for the same block in a round, a certificate is forged and that block receives a chain-selection boost. This boost is the core security property Peras adds — it makes it significantly harder for an adversary to roll back a certified block.

Because the stake distribution is always empty, no vote received from any peer can ever be validated, no `ValidatedPerasVote` is ever produced, and `votesReachQuorum` can never return `Just`. Consequently:

- No Peras certificate can ever be formed from peer-received votes.
- The chain-boosting mechanism of Peras is completely disabled for all nodes running this code.
- The chain selection security guarantees that Peras is designed to provide are absent.

This matches the allowed impact scope: *"High. Chain selection... bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions"* — specifically, the absence of Peras certificates means the chain is less secure than the protocol's stated security assumptions.

A secondary effect is that any peer sending Peras votes is disconnected (`PerasVoteInboundException`), which can be triggered by any unprivileged peer.

---

### Likelihood Explanation

The entry path is the standard Peras vote diffusion mini-protocol (`hPerasVoteDiffusionClient`), which is active in every node-to-node connection that negotiates a protocol version supporting Peras. Any peer that sends a syntactically valid `PerasVote` message triggers the path. No special privileges, keys, or stake are required. The code is in the production diffusion layer and is exercised on every node that participates in Peras vote diffusion.

---

### Recommendation

Replace the hardcoded `pure (PerasVoteStakeDistr mempty)` with an `STM` action that reads the actual epoch stake distribution from the `ChainDB` (or the committee selection context once that plumbing is complete). The stake distribution must correspond to the epoch in which the vote's round falls, consistent with how `ExtWFAStakeDistr` is constructed at epoch boundaries for the `WFALS`/`EveryoneVotes` committee schemes. [6](#0-5) 

Until the full committee selection plumbing is ready, the node should at minimum not disconnect peers for sending votes that fail validation against a known-empty distribution — the validation failure should be treated as a transient "not yet ready" condition rather than a peer misbehaviour.

---

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
