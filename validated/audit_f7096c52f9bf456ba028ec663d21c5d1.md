### Title
`validatePerasCert` Stub Unconditionally Accepts All Inbound Peras Certificates, Enabling Chain-Selection Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance ships a degenerate `validatePerasCert` implementation that unconditionally returns `Right` for every certificate, performing zero cryptographic or committee checks. This function is wired directly into the live node-to-node Peras certificate diffusion inbound handler. Any unprivileged peer can therefore inject an arbitrary `PerasCert` boosting any block in the VolatileDB, causing the receiving node to trigger chain selection with an attacker-controlled weight boost and potentially switch to a non-canonical fork.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub in production code:** [1](#0-0) 

The `BlockSupportsPeras` class defines `validatePerasCert` as the mandatory gate before a certificate may be stored or acted upon: [2](#0-1) 

The only deployed instance (the "degenerate instance for all blks to get things to compile") ignores `params` and `cert` entirely and always returns `Right`:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No committee membership check, no aggregate-signature verification, no round-number bounds check, and no quorum check is performed.

**Exploit path — peer → diffusion → `processCerts` → chain selection:**

The production node wires the inbound Peras certificate diffusion handler in `NodeToNode.hs`: [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is explicitly documented as the production path (not the test path): [4](#0-3) 

Inside `processCerts`, the stub is called as the sole validation gate: [5](#0-4) 

Because `validatePerasCert` always returns `Right`, every certificate passes, is timestamped, and is forwarded to `ChainDB.addPerasCertAsync`. Inside `chainSelSync`, the certificate immediately triggers `chainSelectionForBlock` for the attacker-nominated block: [6](#0-5) 

The weight boost applied is `perasWeight params` — a non-zero value drawn from `PerasParams` — which can tip chain selection in favour of the boosted block.

### Impact Explanation

**Impact category:** High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

An adversary with a single peer connection can:
1. Craft a `PerasCert` whose `pcCertBoostedBlock` points to any block currently in the node's VolatileDB (i.e., any block within the last `k` blocks of any known fork).
2. Send it via the Peras certificate diffusion mini-protocol.
3. The node accepts it unconditionally, stores it, and re-runs chain selection with the artificial weight boost.
4. If the boosted block is on a competing fork, the node may switch away from the canonical chain.

This violates the chain-selection security invariant: the Peras weight boost is supposed to be granted only to blocks that have received a quorum of committee-signed votes; without that check, the boost is freely forgeable.

### Likelihood Explanation

Any peer that speaks the Peras certificate diffusion sub-protocol can trigger this. No stake, no keys, and no prior knowledge of the chain are required beyond knowing a valid block hash in the target node's VolatileDB (obtainable via ChainSync). The Peras diffusion handler is active whenever the node-to-node version supports it, making this reachable from any connected peer on a private testnet or any future mainnet deployment of Peras.

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that verifies:
- The certificate's aggregate BLS/committee signature against the registered committee public keys for the claimed round.
- That the number of signing committee members meets the quorum threshold.
- That the round number is within the valid window relative to the current chain tip.
- That the boosted block hash is consistent with the claimed round's election target.

Until the real implementation is ready, the inbound handler should reject all certificates (return `Left PerasValidationErr` unconditionally) rather than accept all of them, so that the stub cannot be exploited.

### Proof of Concept

On a private two-node testnet with Peras diffusion enabled:

1. Attacker node connects to victim node.
2. Attacker observes a competing fork block hash `H` via ChainSync.
3. Attacker constructs:
   ```haskell
   fakeCert = PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = BlockPoint <slot> H }
   ```
4. Attacker sends `[fakeCert]` via the object-diffusion inbound protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams fakeCert` → `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
6. `ChainDB.addPerasCertAsync` stores the cert and fires `chainSelectionForBlock` for block `H`.
7. If `H` is on a fork whose weight (including the boost) now exceeds the current selection, the victim node switches chains. [7](#0-6) [8](#0-7) [5](#0-4) [3](#0-2) [6](#0-5)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
