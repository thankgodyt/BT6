### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates Without Cryptographic Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which applies to **all** block types, implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound Peras certificate without performing any cryptographic check. Any unprivileged peer can send a crafted `PerasCert` claiming to boost an arbitrary block in an arbitrary round, and the node will store it and apply its weight boost to chain selection without ever verifying that the certificate was legitimately derived from a quorum of eligible voters.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate before it is stored and used to influence chain selection. The sole concrete instance in production code is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This function is called directly in the production network-inbound path. `makePerasCertPoolWriterFromChainDB` wires it into `processCerts`, which is the handler for all Peras certificates received from peers over the ObjectDiffusion mini-protocol:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` applies `validateCert` to every new certificate and, if all pass, adds them to the ChainDB. Because `validatePerasCert` always returns `Right`, every certificate passes: [3](#0-2) 

The accepted certificate is stored with `vpcCertBoost = perasWeight params` — the full configured Peras weight — and is subsequently used by chain selection to boost the block identified in `pcCertBoostedBlock`.

The analog to the external report is exact: just as `token_pool_pda` was accepted as a mutable authority without verifying it was derived from the expected seeds, `PerasCert` is accepted as a valid quorum certificate without verifying it was derived from a legitimate set of eligible voters (i.e., no BLS aggregate signature check, no voter eligibility proof check, no VRF output check). The `PerasCert` data type in this instance carries only `pcCertRound` and `pcCertBoostedBlock` — no cryptographic fields at all — so the "validation" function has nothing to check and trivially succeeds.

Similarly, `validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution; it performs no signature verification:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [4](#0-3) 

A peer can impersonate any registered stake pool voter without possessing its BLS private key.

---

### Impact Explanation

**High — Chain selection error via unauthorized Peras certificate acceptance.**

Peras certificates apply a configurable weight boost (`perasWeight`) to a specific block. Chain selection in the consensus layer uses these boosts when comparing candidate fragments. An attacker who can inject a certificate boosting a non-canonical block can cause an honest node to prefer that block over the legitimate chain tip, constituting a chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

The `BlockSupportsPeras` class is the intended enforcement point for certificate authenticity. With `validatePerasCert` returning `Right` unconditionally, this enforcement point is entirely absent.

---

### Likelihood Explanation

**Medium.** The Peras ObjectDiffusion mini-protocol is wired into the production `NodeKernel` path. Any peer that speaks the Peras certificate diffusion sub-protocol can send crafted certificates. No stake, no key material, and no prior knowledge beyond the target block's `Point` is required. The only limiting factor is that Peras is not yet activated on Cardano mainnet; however, the code is present and active in private testnets and pre-production environments where this attack is immediately exploitable.

---

### Recommendation

Replace the degenerate `validatePerasCert` implementation with a real one that:

1. Verifies the BLS aggregate signature (`pcSignature`) over `(pcCertRound, pcBoostedBlock)` against the aggregate public key derived from the claimed voters.
2. Verifies each voter's eligibility proof (VRF output and seat index) against the epoch nonce and the registered stake distribution.
3. Confirms that the number of verified voters meets the quorum threshold.

Until a real implementation is in place, the Peras certificate inbound path should be disabled or gated behind a feature flag so that no peer-supplied certificate can influence chain selection.

The real cryptographic primitives already exist in the codebase (`verifyAggregateVoteSignature`, `batchVerifyVRFOutputs` in `PerasBLSCrypto`) and are used correctly in the committee-level tests; they simply are not wired into `validatePerasCert`. [5](#0-4) 

---

### Proof of Concept

1. Connect to a node running with Peras certificate diffusion enabled (private testnet or pre-production).
2. Observe the current chain tip `T` and a competing block `B` on a shorter fork.
3. Craft a `PerasCert { pcCertRound = R, pcCertBoostedBlock = pointOf(B) }` for any round `R`.
4. Send this certificate via the Peras ObjectDiffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. The certificate is stored in the ChainDB and the next chain selection run applies `perasWeight` as a boost to block `B`.
7. If `perasWeight` exceeds the block-count difference between the canonical chain and the fork, the node switches to the attacker-chosen fork.

No cryptographic material is required. The attacker needs only to know the `Point` (slot + hash) of the target block, which is publicly observable on the network.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
