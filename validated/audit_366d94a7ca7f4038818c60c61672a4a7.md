Audit Report

## Title
Unprivileged Caller Can Trigger MPC Signing of Arbitrary Token Metadata, Enabling Fake Token Deployment on Destination Chains - (File: near/omni-bridge/src/lib.rs)

## Summary
`log_metadata` in the NEAR bridge contract is callable by any unprivileged account. It accepts any `token_id`, fetches its metadata via cross-contract call, and unconditionally requests an MPC signature over the resulting `MetadataPayload`. That signed payload is the exact artifact consumed by `deployToken` on EVM (and equivalent flows on other chains) to deploy a new bridge token, with no check that the NEAR token is legitimate or registered.

## Finding Description
The impl block at line 245 carries `#[trusted_relayer(bypass_roles(...), manager_roles(...), config_roles(...))]`, which configures the macro but does **not** enforce caller restrictions on every function inside it — as evidenced by `ft_on_transfer` (line 252) which must remain open to any token contract. Enforcement requires the function-level `#[trusted_relayer]` attribute. `sign_transfer` (line 444) carries it; `log_metadata` (line 316) does not. [1](#0-0) [2](#0-1) [3](#0-2) 

The callback validates only that `name` and `symbol` are non-empty, then unconditionally calls the MPC signer: [4](#0-3) [5](#0-4) 

On the EVM side, `deployToken` verifies only that the signature was produced by `nearBridgeDerivedAddress` and that the token has not already been deployed — no check that the NEAR token ID is registered or legitimate: [6](#0-5) [7](#0-6) 

## Impact Explanation
An attacker who controls a NEAR account (e.g., `fake-usdc.near`) can deploy a contract returning `name="USD Coin"`, `symbol="USDC"`, `decimals=6` from `ft_metadata()`. They call `log_metadata`, receive a valid MPC-signed `MetadataPayload`, and submit it to `deployToken` on Ethereum. A new ERC-20 named "USD Coin (USDC)" is deployed and registered in `nearToEthToken`. Because the attacker controls `fake-usdc.near`, they can mint arbitrary amounts, bridge them to Ethereum to receive the fake ERC-20, and sell it to users who mistake it for the legitimate USDC bridge token. This is token metadata binding confusion that directly enables unauthorized minting and sale of fraudulent bridge tokens, matching the Critical allowed impact: *token metadata binding confusion that changes user or protocol balances*, and *unauthorized transaction / signer verification bypass that lets an attacker execute bridge/token/deployer actions*.

## Likelihood Explanation
The attack requires only a NEAR account and gas to cover MPC signing fees. No privileged role, no stake, no leaked key is needed. The attacker fully controls the metadata returned by their token contract. The barrier is minimal and the attack is repeatable for any token name/symbol combination not yet deployed.

## Recommendation
Add a function-level `#[trusted_relayer]` attribute to `log_metadata`, matching the pattern used by `sign_transfer`, `fin_transfer`, and `claim_fee`. Alternatively, require that `token_id` is already present in `token_address_to_id` or `deployed_tokens` before triggering MPC signing, ensuring only tokens that have gone through the legitimate registration flow can have their metadata signed.

## Proof of Concept
1. Attacker deploys a NEAR contract at `fake-usdc.near` implementing `ft_metadata()` returning `name="USD Coin"`, `symbol="USDC"`, `decimals=6`.
2. Attacker calls `omni-bridge.near::log_metadata("fake-usdc.near")` with sufficient attached deposit for MPC gas. No access control blocks this call.
3. `log_metadata_callback` validates only that name/symbol are non-empty — both pass.
4. The bridge calls `v1.signer::sign(keccak256(borsh(MetadataPayload{prefix:Metadata, token:"fake-usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})))`.
5. MPC returns a valid ECDSA signature; `sign_log_metadata_callback` emits `LogMetadataEvent{signature, metadata_payload}`.
6. Attacker reads the signature from the event log and calls `OmniBridge.deployToken(signature, {token:"fake-usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})` on Ethereum.
7. `ECDSA.recover` succeeds; `isBridgeToken[nearToEthToken["fake-usdc.near"]]` is false (first deployment); a new ERC-20 "USD Coin (USDC)" is deployed and mapped to `fake-usdc.near`.
8. Attacker mints `fake-usdc.near` tokens on NEAR, bridges them to Ethereum, and sells the resulting fake ERC-20 to users who mistake it for the legitimate USDC bridge token.
