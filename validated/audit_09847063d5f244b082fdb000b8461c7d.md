Audit Report

## Title
Inverted Success/Failure Condition in `submit_transfer_to_btc_connector_callback` Permanently Locks Fee Tokens — (File: near/omni-bridge/src/btc.rs)

## Summary
In `submit_transfer_to_btc_connector_callback`, the branch condition at line 111 uses `result.0 > 0` to detect success, but under NEP-141 `ft_transfer_call` semantics `result.0 > 0` means the receiver is **refunding** tokens (failure). The two branches are therefore swapped: on every successful NEAR → BTC/Zcash outbound transfer the fee tokens are never disbursed and remain permanently locked inside the bridge contract, while on every failed transfer the fee is incorrectly paid to the relayer.

## Finding Description
`submit_transfer_to_utxo_chain_connector` deducts the fee from the forwarded amount and calls `ft_transfer_call` with only `amount = total - fee`, leaving the fee tokens inside the bridge contract. [1](#0-0) [2](#0-1) 

The callback is then responsible for disbursing those fee tokens. Under NEP-141, `ft_transfer_call` returns the number of tokens the receiver is **refunding** to the sender: `0` means the connector accepted everything (success); `> 0` means a partial or full refund (failure). The condition at line 111 is:

```rust
if matches!(call_result, Ok(result) if result.0 > 0) {
    // fires on FAILURE — incorrectly pays fee
    self.send_fee_internal(...)
} else {
    // fires on SUCCESS — incorrectly re-queues transfer
    self.add_transfer_message(...)
}
``` [3](#0-2) 

On a successful transfer (`result.0 == 0`), the `else` branch executes: `add_transfer_message` re-inserts the transfer into `pending_transfers` even though the underlying tokens have already been forwarded to the UTXO connector. `send_fee_internal` is never called, so the fee tokens accumulate in the bridge with no disbursement path. [4](#0-3) 

On a failed transfer (`result.0 > 0`), the `if` branch executes: `send_fee_internal` is called, paying the relayer a fee for a transfer that did not complete, and the transfer is **not** re-queued for retry. [5](#0-4) 

## Impact Explanation
Every successful NEAR → Bitcoin/Zcash outbound transfer where `fee.fee > 0` results in the fee tokens being permanently locked inside the bridge contract. `send_fee_internal` calls `unlock_tokens_if_needed`, which is never reached on the success path, leaving `locked_tokens` accounting permanently overstated. [6](#0-5) 

The stale re-inserted `pending_transfers` entry cannot be successfully re-submitted because the underlying tokens have already been sent to the UTXO connector; the only recovery path is a DAO-level intervention. This constitutes **permanent freezing of bridged funds** (fee tokens) across Bitcoin and Zcash flows, matching the Critical impact scope.

## Likelihood Explanation
The bug is triggered on **every** successful UTXO outbound transfer with a non-zero fee. Any trusted relayer calling `submit_transfer_to_utxo_chain_connector` on a valid pending BTC/Zcash transfer triggers it automatically during normal bridge operation. No special attacker action, victim mistake, or external condition is required beyond a standard bridge transfer completing successfully.

## Recommendation
Invert the condition so that `result.0 == 0` (connector accepted all tokens) triggers fee disbursement:

```rust
// CORRECT: result.0 == 0 means the connector used all tokens (success)
if matches!(call_result, Ok(result) if result.0 == 0) {
    let token_fee = transfer_msg.fee.fee.0;
    self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
} else {
    // Failure: re-queue the transfer
    let required_storage_balance =
        self.add_transfer_message(transfer_msg, transfer_owner.clone());
    self.update_storage_balance(
        transfer_owner,
        required_storage_balance,
        NearToken::from_yoctonear(0),
    );
    PromiseOrValue::Value(())
}
``` [3](#0-2) 

## Proof of Concept
1. A user initiates a NEAR → BTC transfer with `fee = 1000` tokens and `amount = 10000`.
2. A trusted relayer calls `submit_transfer_to_utxo_chain_connector`. The bridge removes the pending transfer and calls `ft_transfer_call` with `amount = 9000`. The 1000 fee tokens remain in the bridge.
3. The BTC connector successfully processes the withdrawal and returns `U128(0)` (used all 9000 tokens).
4. `submit_transfer_to_btc_connector_callback` receives `Ok(U128(0))`. The condition `result.0 > 0` is **false**, so the `else` branch executes: `add_transfer_message` re-inserts the transfer into `pending_transfers`.
5. `send_fee_internal` is never called. The 1000 fee tokens remain locked in the bridge contract indefinitely with no disbursement path.
6. `unlock_tokens_if_needed` is never called, leaving `locked_tokens` accounting overstated by 1000 tokens.
7. The stale pending entry cannot be re-submitted (tokens are already gone to the connector). Recovery requires a DAO-level `transfer_token_as_dao` call.
