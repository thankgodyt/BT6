### Title
TOCTOU Race in `sign_btc_transaction` Allows Duplicate MPC Dispatch, Causing Callback Panic and Attached-Deposit Loss - (`contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`internal_sign_btc_transaction` performs a read-only `is_none()` guard on `signatures[sign_index]` but writes no in-flight marker before dispatching the MPC promise. Two concurrent calls for the same `(btc_pending_sign_id, sign_index)` can both pass the guard, both dispatch MPC sign promises, and when the callbacks land the second one panics — permanently losing the NEAR deposit that was already forwarded to the MPC contract.

---

### Finding Description

`sign_btc_transaction` is a public, payable function gated only by a pause check: [1](#0-0) 

`internal_sign_btc_transaction` reads the pending info and checks the slot is empty, but makes **no state write** before dispatching the promise: [2](#0-1) 

The attached deposit is forwarded directly to the MPC contract in the same promise: [3](#0-2) 

When the callback fires it re-checks the same guard: [4](#0-3) 

Because NEAR cross-contract calls are asynchronous, two transactions can both read `signatures[sign_index] == None` before either callback lands. The first callback writes the signature and succeeds; the second callback hits the `require!` and panics. A panic in a NEAR callback reverts only the callback's own state changes — it does **not** undo the already-executed MPC `sign` call, so the deposit forwarded in that call is irrecoverably consumed.

---

### Impact Explanation

- The NEAR deposit attached to the second `sign_btc_transaction` call is permanently lost.
- The `BTCPendingInfo` state is left consistent (the first callback completed), but the second caller's funds are gone with no refund path.
- Matches **Low**: publicly reachable panic-driven fault in a production bridge path without direct theft of bridged BTC.

---

### Likelihood Explanation

`sign_btc_transaction` has no caller restriction beyond the pause flag — any account can invoke it for any known `btc_pending_sign_id`. MPC signing introduces a multi-block latency window during which a second call trivially races the first. An attacker can grief a legitimate user by front-running their signing call, causing the user's callback to panic and their deposit to be lost.

---

### Recommendation

Set an in-flight marker atomically with the pre-call check. The simplest fix is to write a sentinel value (e.g., a dedicated `InFlight` variant) into `signatures[sign_index]` inside `internal_sign_btc_transaction` **before** dispatching the promise:

```rust
// in internal_sign_btc_transaction, after the is_none() check:
let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
require!(btc_pending_info.signatures[sign_index].is_none(), "Already signed or in-flight");
btc_pending_info.signatures[sign_index] = Some(SignatureResponse::InFlight); // sentinel
```

This makes the guard atomic with the dispatch: any concurrent call will see a non-`None` slot and abort before forwarding a deposit to MPC.

---

### Proof of Concept

```
1. A BTCPendingInfo with id=X, sign_index=0, signatures=[None] exists in PendingSign stage.
2. Attacker submits TX_A: sign_btc_transaction(X, 0, kv) with deposit D1.
   - internal_sign_btc_transaction reads signatures[0] == None → passes guard.
   - Dispatches MPC sign promise; no write to signatures[0].
3. Before TX_A's callback lands, attacker (or victim) submits TX_B: sign_btc_transaction(X, 0, kv) with deposit D2.
   - signatures[0] is still None → passes guard.
   - Dispatches second MPC sign promise; D2 forwarded to MPC.
4. Callback_A fires: signatures[0] = Some(sig); state may transition to PendingVerify. Returns true.
5. Callback_B fires: require!(signatures[0].is_none()) → PANICS.
   - D2 is not refunded; it was consumed by the MPC contract in step 3.
```
