### Title
Peras Vote Eligibility Checks Bypassed in `validatePerasVote` — Ineligible Votes Accepted and Counted Toward Quorum - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasVote` function in the Peras vote inbound processing pipeline only verifies that a voter has stake in the stake distribution. It does not verify the vote signature, committee membership, or any of the CIP-0140 voting eligibility rules (VR-1A, VR-1B, VR-2A, VR-2B). An unprivileged peer can send crafted `PerasVote` messages for any pool ID with known stake, and those votes will be accepted, accumulated in `PerasVoteDB`, and — if enough are injected — trigger fraudulent certificate generation for an attacker-chosen block, directly manipulating Peras-weighted chain selection.

### Finding Description

The Peras vote inbound path is:

1. A peer sends `PerasVote` objects over the object-diffusion mini-protocol.
2. `processVotes` in `ObjectPool/PerasVote.hs` calls `validateVote` on each new vote.
3. `validateVote` is bound to `validatePerasVote` from `BlockSupportsPeras`.
4. Validated votes are timestamped and inserted into `PerasVoteDB` via `addVote`.
5. `implAddVote` calls `updatePerasRoundVoteStates`, which forges a `ValidatedPerasCert` when accumulated stake crosses the quorum threshold.

The root cause is in `validatePerasVote`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The function accepts any vote whose voter ID appears in the stake distribution, regardless of:
- **Vote signature**: no cryptographic verification is performed; the `_params` argument is discarded.
- **Committee membership**: the WFALS/EveryoneVotes committee eligibility check (`verifyVote`) is never called on the inbound path.
- **Voting rule eligibility**: `isPerasVotingAllowed` (VR-1A/VR-1B/VR-2A/VR-2B from `Peras/Voting/Rules.hs`) is only used to decide whether the *local* node should vote; it is never applied to validate incoming votes from peers.

A parallel TODO in `implAddVote` confirms the validation gap is acknowledged but unresolved:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddVote perasCfg PerasVoteDbEnv{...} vote = ...
```

The stake distribution is public ledger data. An attacker can enumerate all pool IDs with positive stake, craft `PerasVote` messages for those IDs targeting any block of their choice, and submit them to any node. No private key material is required because signature verification is absent.

### Impact Explanation

When the injected votes accumulate enough stake to exceed the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert`, producing a `ValidatedPerasCert` that boosts the attacker-chosen block's weight in chain selection. This constitutes an unauthorized Peras certificate acceptance: a certificate is forged for a block that was never legitimately voted upon by the committee. Nodes that receive this certificate will prefer the boosted chain over competing honest chains, enabling an unprivileged peer to steer chain selection to an arbitrary block.

**Severity: Critical** — maps directly to "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."

### Likelihood Explanation

The attack requires only:
1. Network access to connect to a target node (unprivileged peer).
2. Knowledge of pool IDs with positive stake (public from the ledger state).
3. Ability to send `PerasVote` messages over the object-diffusion mini-protocol.

No key compromise, stake majority, or operator access is needed. The pool IDs and their stake weights are observable by any participant. The attack is deterministic and reproducible on any private testnet running the Peras extension.

### Recommendation

1. **Enforce signature verification** in `validatePerasVote`: call the committee's `verifyVote` (from `VotingCommittee`) on every inbound vote before accepting it.
2. **Enforce voting rule eligibility** on inbound votes: apply `isPerasVotingAllowed` (or an equivalent receiver-side check) to reject votes that violate VR-1A/VR-1B/VR-2A/VR-2B.
3. **Resolve the tracked issues**: address `https://github.com/tweag/cardano-peras/issues/120` before the Peras extension is deployed to production.

### Proof of Concept

On a private testnet with Peras enabled:

1. Query the ledger for all pool IDs with positive stake (e.g., `poolId_A`, `poolId_B`, …).
2. Craft `PerasVote { pvVoteRound = R, pvVoteBlock = <target_block_hash>, pvVoteVoterId = poolId_X }` for enough pool IDs to exceed the quorum threshold.
3. Submit the batch to a target node via the Peras vote object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote` for each vote; each passes because `lookupPerasVoteStake` finds the pool ID in the stake distribution.
5. `implAddVote` → `updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` returns `Just` → `forgePerasCert` produces a `ValidatedPerasCert` for `<target_block_hash>`.
6. The node now treats `<target_block_hash>` as Peras-certified and prefers any chain extending it over competing honest chains.

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

updateCandidateVoteState cfg vote oldState =
  let
    newVoteTally = updateTargetVoteTally vote (ptvsVoteTally oldState)
    voteList = forgetArrivalTime <$> Map.elems (ptvtVotes newVoteTally)
   in
    case votesReachQuorum cfg voteList of
      Just votesWithQuorum -> do
        cert <- forgePerasCert cfg votesWithQuorum
        pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
      Nothing -> do
        pure $ RemainedCandidate (PerasTargetVoteCandidate newVoteTally)
