### Title
`shelleyAfterVoting` Counts All Post-Deadline Blocks Instead of Only Those in the Stability Window, Enabling Premature Era Transition Under Chain Growth Violation — (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `ShelleyTransitionInfo` accumulates every block whose slot is at or after the voting deadline, without any upper bound. The design intent (Iteration 4 in `civic_time.md`) is to count **only** blocks within the stability window immediately following the voting deadline (`[votingDeadline, votingDeadline + swindow)`). Because the code counts all blocks in `[votingDeadline, ∞)`, the Chain Growth violation guard in `shelleyTransition` is incorrect: an era transition can be triggered even when the stability window itself contained fewer than `k+1` blocks, violating the `DespiteChainGrowthViolation` invariant the HFC was designed to uphold.

---

### Finding Description

`ShelleyTransitionInfo` holds a single counter:

```haskell
newtype ShelleyTransition = ShelleyTransitionInfo
  { shelleyAfterVoting :: Word32
  -- ^ The number of blocks in this epoch past the voting deadline
  ...
  }
``` [1](#0-0) 

In `applyHelper`, the counter is incremented for every block whose slot is at or after `votingDeadline`:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [2](#0-1) 

The voting deadline is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [3](#0-2) 

With `swindow = 3k/f`, this places the voting deadline at `6k/f` slots before the epoch boundary. The **stability window** after the voting deadline spans only the first `3k/f` slots after that deadline, i.e., `[votingDeadline, votingDeadline + swindow)` = `[startOfNextEpoch − 6k/f, startOfNextEpoch − 3k/f)`. Blocks in the remaining `[startOfNextEpoch − 3k/f, startOfNextEpoch)` window are **outside** the stability window and should not be counted.

The era-transition guard in `shelleyTransition` then checks:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
``` [4](#0-3) 

Because `shelleyAfterVoting` includes blocks beyond the stability window, this guard can be satisfied even when the stability window itself contained fewer than `k+1` blocks. The design documentation explicitly acknowledges this as a bug:

> (TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.) [5](#0-4) 

Additionally, the counter is **never reset at an epoch boundary** within an era. It is only zeroed when the ledger state is translated to a new era:

```haskell
, shelleyLedgerTransition = ShelleyTransitionInfo 0
``` [6](#0-5) 

This means blocks from a previous epoch's post-deadline window can satisfy the `>= k` guard for a subsequent epoch's transition check, even if that subsequent epoch's stability window has zero qualifying blocks.

---

### Impact Explanation

The HFC's Iteration 4 design requires that an era transition be **suppressed** when the stability window after the voting deadline contains fewer than `k+1` blocks (a Chain Growth violation). This suppression is the mechanism that prevents the node from committing to a time translation that could be invalidated by a rollback.

With the bug, the suppression fails: if `shelleyAfterVoting` has accumulated `≥ k` from blocks outside the stability window (or from a prior epoch), `singleEraTransition` returns `Just epochNo` and the HFC transitions to the new era. The node then uses the new era's slot length and epoch size for all subsequent time translations. If a rollback later undoes the transition (which is possible precisely because Chain Growth was violated), the node holds stale, incorrect time-translation state. This violates the `ImmutableTranslations` invariant and can cause the node to accept blocks it should reject, or reject blocks it should accept, constituting a **hard-fork / era-transition ledger-view bug that breaks cross-era consensus invariants**. [7](#0-6) 

---

### Likelihood Explanation

The bug is latent in every production Cardano node. It is triggered only when Praos Chain Growth is violated in the stability window immediately following the voting deadline — a condition that can arise from a network partition or from an adversary temporarily withholding blocks (without requiring a stake majority). On mainnet, Chain Growth violations are rare but not impossible; the design explicitly anticipates them (the entire `DespiteChainGrowthViolation` requirement exists for this reason). The bug is self-documented in the codebase as a known, unfixed issue.

---

### Recommendation

Restrict the `shelleyAfterVoting` increment to blocks that fall strictly within the stability window after the voting deadline:

```haskell
shelleyAfterVoting =
    ( if blockSlot blk >= votingDeadline
         && blockSlot blk <  votingDeadline + SlotNo swindow
      then succ
      else id
    ) $ shelleyAfterVoting tickedShelleyLedgerTransition
```

Additionally, consider resetting the counter to `0` whenever a new epoch begins (i.e., when `blockEpoch > prevEpoch`), so that stale counts from prior epochs cannot satisfy the guard for a later epoch's transition check.

---

### Proof of Concept

1. A Cardano node is in era `E` (e.g., Babbage). A governance vote to transition to era `E+1` (Conway) passes before the voting deadline of epoch `N`.
2. A network partition occurs during the stability window `[votingDeadline_N, votingDeadline_N + 3k/f)`. Only `k−1` blocks are produced in that window — a Chain Growth violation. The HFC **should** suppress the transition.
3. However, in epoch `N−1`, the node had already seen `k` blocks after epoch `N−1`'s voting deadline, so `shelleyAfterVoting = k` going into epoch `N`.
4. `shelleyTransition` evaluates `shelleyAfterVoting >= k` → `True`, and returns `Just (N+1)`.
5. The HFC transitions to era `E+1`. The node begins using `E+1`'s slot/epoch parameters for time translations.
6. The partition resolves; a competing chain (which did not transition) has more blocks. The node rolls back past the voting deadline, undoing the transition.
7. The node is now in era `E` again but had already issued time translations anchored to era `E+1` parameters — a violation of `ImmutableTranslations` that can cause incorrect header/block validation for any slot translated during step 5. [8](#0-7) [9](#0-8) [10](#0-9)

  - {ImmutableTranslations}.
    Because of humans' general assumptions about time, it would be prohibitively confusing if the node (even its internal interfaces) might give different translations of the same slots/civic times.
    So a switch from `t1` to `t2` for the result of some translation is unacceptable.
    At the very least, the node should refuse to do a translation that might be invalidated by on-chain governance in the meantime (eg several weeks into the future).

  - {NonemptyForecastRange}.
    On the other hand, the node should be able to translate slot/civic times slightly ahead of its tip.
    At the very least, some users presumably want some capacity to plan ahead (eg to smartly schedule their node's brief downtime).

  - {RollbackInsensitiveTranslations}.
    As a specific subcase of the first requirement, the node should even refuse to do translations that might be invalidated by a rollback.

  - {MonotonicTranslations}.
    It would also be too confusing if a node agreed to translate some slot/civic time and then subsequently refused to translate that same slot/civic time.
    So `Just t1 -> Nothing` is also unacceptable for some translation, not merely `Just t1 -> Just t2`.

  - {DespiteChainGrowthViolation}[^Anachrony].
    All of the above must hold even in the presence of a Chain Growth violation, except switching from a chain that violates Chain Growth to one that does not is allowed to violate the RollbackInsensitiveTranslations subcase of ImmutableTranslations.
