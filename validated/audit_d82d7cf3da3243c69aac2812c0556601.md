### Title
Tokens Minted to Bridge Before Registration Check in `safe_mint` Causes Permanent Fund Loss — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function calls `internal_deposit` to mint nBTC to the bridge's own account **before** checking whether the intended recipient (`account_id`) is registered with the token contract. If the recipient is unregistered, the function silently returns `U128(0)` and exits — but the tokens have already been minted into the bridge's balance with no recovery path. The user's BTC remains locked in the bridge's Bitcoin address while the corresponding nBTC is permanently stranded in the bridge's NEAR balance.

---

### Finding Description

In `contracts/nbtc/src/lib.rs` at lines 101–124, `safe_mint` executes the following sequence:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints FIRST

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← exits without transferring
    }
    ...
``` [1](#0-0) 

The call to `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the bridge's nBTC balance and the token's total supply unconditionally. The registration check (`self.token.accounts.get(&account_id).is_none()`) only occurs **after** this state mutation. When the recipient is unregistered, the function returns `U128(0)` — the minted tokens remain in the bridge's balance and there is no `lost_found` entry, no event, and no operator-facing recovery hook for this path.

This contrasts with the sibling `mint_inner` helper (lines 341–352), which auto-registers any account before depositing, ensuring tokens always reach their destination:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
``` [2](#0-1) 

`safe_mint` is the path used when the bridge deposit message includes a `safe_deposit` or post-action `msg` field (i.e., the user wants tokens forwarded into a DeFi protocol on mint). The `assert_bridge()` guard confirms only the bridge contract can call it, but any bridge-initiated deposit targeting an unregistered recipient triggers the bug.

---

### Impact Explanation

**Impact: Critical — Permanent locking of user funds.**

When `safe_mint` is called for an unregistered `account_id`:

1. `internal_deposit(&self.bridge_id, amount)` increases the bridge's nBTC balance and the global total supply.
2. The function returns `U128(0)` — no transfer, no `lost_found` credit, no event.
3. The user's BTC is locked in the bridge's Bitcoin-side derived address (the deposit is already confirmed on-chain).
4. The minted nBTC is stranded in the bridge's NEAR balance with no documented recovery mechanism.

The result is a permanent mismatch: backed BTC is locked, but the corresponding nBTC is neither delivered to the user nor recoverable by them. This satisfies the allowed impact criterion: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

**Likelihood: Medium.**

Any user who deposits BTC with a `safe_deposit` message targeting a NEAR account that has not yet paid the nBTC storage deposit will trigger this path. New users integrating with DeFi protocols via the `safe_deposit` flow are the most natural victims — they may not know they must pre-register with the nBTC contract before initiating a deposit. The deposit transaction is irreversible once confirmed on Bitcoin, so there is no user-side recovery.

---

### Recommendation

Move the registration check **before** the `internal_deposit` call, mirroring the pattern used by `mint_inner`:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );

    // Check registration BEFORE minting anything
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    ...
```

Alternatively, emit a `LostFoundNbtc`-style event and credit the bridge's `lost_found` map so an operator can recover the stranded tokens on behalf of the user.

---

### Proof of Concept

1. User deposits BTC to the bridge's derived address with a `DepositMsg` containing a `safe_deposit` field (triggering the `safe_mint` path).
2. Relayer submits `verify_deposit` with a valid Merkle proof; the bridge verifies it and calls `safe_mint(user_account_id, amount, Some(msg))` on the nBTC contract.
3. `self.token.internal_deposit(&self.bridge_id, amount.into())` executes — nBTC total supply increases, bridge balance increases.
4. `self.token.accounts.get(&user_account_id).is_none()` returns `true` — the user never paid the nBTC storage deposit.
5. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no transfer, no event, no `lost_found` entry.
6. The user's BTC is permanently locked in the bridge's Bitcoin address; the minted nBTC is permanently stranded in the bridge's NEAR balance. [3](#0-2)
