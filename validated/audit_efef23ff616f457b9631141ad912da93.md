### Title
Silently Discarded Envelope Validation Result in `revalidateHeader` Allows Corrupted Header State to Persist Undetected - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full envelope check (block number, slot number, prev-hash) but wraps the result in `assertWithMsg`, which is a **compile-time no-op** in production builds. The check result is silently discarded, meaning `revalidateHeader` unconditionally returns a new `HeaderState` regardless of whether the envelope is valid. This is called from `reapplyBlockLedgerResult` in `ExtLedgerState`, which is the code path used during LedgerDB replay from snapshots and chain-selection fork switches.

---

### Finding Description

`revalidateHeader` in `HeaderValidation.hs` is the "fast path" revalidation used when a block is known to have been previously validated. It intentionally skips expensive cryptographic checks (`reupdateChainDepState` instead of `updateChainDepState`), but it is supposed to retain the cheap structural envelope check as a safety net:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
``` [1](#0-0) 

The `envelopeCheck` value is computed by running `validateEnvelope` (which checks block number, slot number, and prev-hash), but it is passed to `assertWithMsg`:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [2](#0-1) 

Without the `ENABLE_ASSERTIONS` CPP flag — which is a debug-only flag, not set in production — the second equation `assertWithMsg _ a = a` always fires. The `Either String ()` result of the envelope check is **pattern-matched away and discarded**. The function returns the new `HeaderState` unconditionally, regardless of whether the envelope check passed or failed.

This is called from `reapplyBlockLedgerResult` for `ExtLedgerState`:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
  where
    ...
    hdr =
      revalidateHeader
        (getExtLedgerCfg cfg)
        ledgerView
        (getHeader blk)
        tickedHeaderState
``` [3](#0-2) 

The `reapplyBlockLedgerResult` path is exercised during:
1. **LedgerDB initialization** — replaying blocks from the ImmutableDB after loading a snapshot.
2. **Chain-selection fork switches** — reapplying blocks already in the VolatileDB when switching to a fork.

The `envelopeCheck` value is computed but its `Left` branch is never reachable in production: [4](#0-3) 

---

### Impact Explanation

If a block that fails the envelope check (wrong block number, wrong slot, or wrong prev-hash) reaches `revalidateHeader` — for example due to ImmutableDB on-disk corruption, a snapshot written with a corrupted `HeaderState`, or a future bug in the code constructing the `Ticked (HeaderState blk)` — the failure is silently swallowed in production. The function returns a `HeaderState` whose `headerStateTip` is set to the corrupted block's `AnnTip` and whose `chainDepState` is updated via `reupdateChainDepState` as if the block were valid.

This corrupted `ExtLedgerState` is then committed to the LedgerDB. Subsequent blocks are validated against this wrong `HeaderState`, meaning:
- The `oldTip` passed to `validateEnvelope` for the next block is wrong, causing legitimate blocks to be rejected or illegitimate blocks to pass the prev-hash check.
- The `ChainDepState` (nonce state for Praos/TPraos) is advanced from a wrong base, corrupting epoch nonce computation and potentially allowing unauthorized leader eligibility.

This maps to: **High — LedgerDB/snapshot corruption/replay bug that causes durable use of the wrong ledger state.**

---

### Likelihood Explanation

The precondition for `reapplyBlockLedgerResult` is that the block was previously validated. Under normal operation this holds. However:

- **ImmutableDB on-disk corruption** (hardware fault, filesystem bug) can corrupt a stored block's header fields after initial validation. The ImmutableDB's own integrity check (`checkIntegrity`) is only run during `ValidateAllChunks` policy, not `ValidateMostRecentChunk` (the default). A corrupted block that passes the ImmutableDB parser but has a wrong prev-hash or block number would reach `revalidateHeader` with no envelope enforcement in production.
- **Snapshot corruption** can cause the `tickedHeaderState` passed to `revalidateHeader` to be inconsistent with the block being replayed, again silently accepted.

Likelihood is **Low-Medium**: requires storage-layer corruption, but the missing production-time check removes the only safety net that would catch it before it corrupts the live `ExtLedgerState`.

---

### Recommendation

The envelope check in `revalidateHeader` should not be gated behind `ENABLE_ASSERTIONS`. Since `validateEnvelope` is cheap (pure comparisons of block numbers, slot numbers, and hashes), it should be enforced unconditionally, matching the pattern used in `validateHeader`:

```haskell
-- Current (production no-op):
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'

-- Recommended:
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left err -> error $ "revalidateHeader: envelope check failed: " <> err
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

Alternatively, if the intent is to keep `revalidateHeader` total and non-throwing, it should return `Either (HeaderEnvelopeError blk) (HeaderState blk)` so callers are forced to handle the failure case, analogous to how `validateHeader` returns `Except (HeaderError blk) (HeaderState blk)`.

---

### Proof of Concept

1. `assertWithMsg` is defined as a CPP-conditional no-op: [2](#0-1) 

2. `revalidateHeader` wraps the envelope check in `assertWithMsg`, meaning in production the `envelopeCheck` result is computed and immediately discarded: [5](#0-4) 

3. `revalidateHeader` is called unconditionally from `reapplyBlockLedgerResult` for `ExtLedgerState`, which is the replay/fork-switch path: [3](#0-2) 

4. The contrast with `validateHeader` (the full-validation path) shows the intended pattern — it uses `Except` and propagates errors to callers: [6](#0-5) 

In a private testnet, corrupt a block in the ImmutableDB (flip bits in the prev-hash field of a stored block header) and restart the node with `ValidateMostRecentChunk` policy. The node will replay the corrupted block through `reapplyBlockLedgerResult` → `revalidateHeader`. In a production build (no `ENABLE_ASSERTIONS`), the envelope check failure is silently discarded and the node continues with a corrupted `ExtLedgerState`. In a debug build (with `ENABLE_ASSERTIONS`), the node crashes with an error message from `assertWithMsg`.
