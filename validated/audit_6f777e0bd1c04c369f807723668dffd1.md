### Title
Chain Selection Error via Missing Peras Weight in Forecast-Horizon Candidate Evaluation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to keep waiting for a header that is beyond the forecast horizon. When Peras is active, this ignores certificate-based weight boosts entirely, reducing the comparison to a pure block-count comparison. An adversary that has caused the local node to adopt a longer-but-lighter fork can thereby cause the node to disconnect from every honest peer whose canonical Peras-boosted chain is shorter in block count, permanently locking the node onto the adversarial fork.

---

### Finding Description

When `projectLedgerView` returns `Nothing` (the incoming header is beyond the current forecast horizon), the ChainSync client enters a retry loop and calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect:

```haskell
-- Client.hs ~1834
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty, ignores Peras boosts
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` has two code paths: when `isEmptyPerasWeightSnapshot weights` is true it falls back to a pure `selectView`/block-number comparison; when false it computes `weightedSelectView` which sums `BlockNo + PerasWeight` for each fragment suffix. [2](#0-1) 

By hardcoding `emptyPerasWeightSnapshot`, the check always takes the block-number-only path, regardless of whether Peras certificates have boosted blocks on the peer's fragment. Everywhere else in the codebase — `ChainSel.hs`, `BlockFetch/ClientInterface.hs`, `NodeKernel.hs` — the real `PerasWeightSnapshot` is threaded through and used. [3](#0-2) [4](#0-3) 

The `emptyPerasWeightSnapshot` constant is defined as a trivially empty map: [5](#0-4)

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain.**

Attack sequence (private-testnet or future mainnet with Peras active):

1. The adversary serves a fork `F_adv` that is longer in block count than the current canonical chain `F_hon`, but carries no Peras certificate boosts. The node adopts `F_adv` as its current selection (`ourFrag`).
2. The honest chain `F_hon` accumulates Peras certificate boosts, making `totalWeight(F_hon) > totalWeight(F_adv)` even though `blockNo(F_hon) < blockNo(F_adv)`.
3. An honest peer advertises a tip on `F_hon` that is beyond the node's current forecast horizon (the intersection with `F_adv` is far back). The node enters the retry loop and calls `checkPreferTheirsOverOurs`.
4. Because `emptyPerasWeightSnapshot` is used, the comparison reduces to `blockNo(F_hon_tip) vs blockNo(F_adv_tip)`. Since `F_adv` is longer, `shouldSwitch` returns `ShouldNotSwitch`, and the node throws `CandidateTooSparse`, disconnecting from the honest peer.
5. If all honest peers are disconnected for the same reason, the node is permanently stuck on `F_adv` — the adversarial, lighter fork — even though `F_hon` is the canonical chain under Peras chain-order rules.

This is the consensus analog of the missing `minAmountOut` slippage parameter: the chain-preference check lacks the "Peras weight floor" that would prevent the node from discarding a heavier canonical chain simply because it is shorter in raw block count.

---

### Likelihood Explanation

Requires Peras to be active (currently deployable on a private testnet; planned for mainnet). The adversary needs only to have previously served a longer-but-lighter fork that the node adopted — a standard long-range or eclipse-style setup. No key compromise, stake majority, or operator action is required. The TODO comment in the source (`// TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers recognise the check is incorrect under Peras but have not yet removed or fixed it.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` that is already available in the surrounding `ChainSync` client environment (the same snapshot used by `ChainSel` and `BlockFetch`). Alternatively, remove the check entirely as the TODO suggests, since the correct long-term behaviour is to keep waiting rather than disconnecting when the forecast horizon is the only obstacle.

---

### Proof of Concept

```
Private testnet, Peras enabled, security parameter k=2160.

1. Start node N with empty chain.
2. Adversary A serves fork F_adv: 100 blocks, no Peras certs.
   N adopts F_adv (ourFrag = F_adv, blockNo tip = 100).

3. Honest peer H serves fork F_hon: 98 blocks, but blocks 50–98
   each carry a Peras certificate boost of weight 10.
   totalWeight(F_hon) = 98 + (49 × 10) = 588
   totalWeight(F_adv) = 100 + 0         = 100
   Under Peras chain order, F_hon is canonical.

4. H advertises tip at slot S_hon which is beyond N's forecast
   horizon (intersection with F_adv is at block 40, and
   S_hon > forecastAt + stabilityWindow).

5. N calls checkPreferTheirsOverOurs:
     preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag
   → isEmptyPerasWeightSnapshot = True → block-number path
   → selectView(ourTip).blockNo = 100 > selectView(theirTip).blockNo = 98
   → ShouldNotSwitch GT
   → throwSTM CandidateTooSparse  ← N disconnects from H

6. N remains on F_adv (the adversarial, lighter fork) indefinitely.
   If all honest peers are similarly disconnected, N never selects F_hon.
```

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of

              ShouldNotSwitch o -> ShouldNotSwitch o
