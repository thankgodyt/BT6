Audit Report

## Title
`HyperliquedBridgeToken` 3-arg `mint()` Override Routes Bridged Tokens to `_systemAddress` Instead of Recipient in `finTransfer` — (File: `evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`HyperliquedBridgeToken` overrides the 3-arg `mint(address, uint256, bytes)` to implement HyperCore spot-balance accounting: after `_mint(account, value)` it immediately calls `_update(account, _systemAddress, value)`, an ERC-20 internal transfer that moves the entire minted balance from the recipient to `_systemAddress`. When `OmniBridge.finTransfer` is called for this token with a non-empty `payload.message`, it dispatches to this 3-arg override, causing the intended recipient to receive zero tokens while `_systemAddress` absorbs the full bridged amount. The nonce is consumed and `FinTransfer` is emitted, so the transfer cannot be replayed or refunded through normal bridge flows.

## Finding Description

**Root cause — `HlBridgeToken.sol` lines 76–83:**

```solidity
function mint(
    address account,
    uint256 value,
    bytes memory          // message is silently ignored
) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value); // full balance immediately re-routed
}
``` [1](#0-0) 

`_mint` credits `account` with `value` tokens; `_update` is the OpenZeppelin ERC-20 internal transfer hook that immediately moves all `value` tokens from `account` to `_systemAddress`. The `bytes memory` parameter is unnamed and completely ignored, so no routing information from the caller is preserved on-chain.

**Registration path — `OmniBridge.sol` lines 88–97:**

`addCustomToken(nearTokenId, hlTokenAddress, address(0), 18)` sets `isBridgeToken[hlTokenAddress] = true` and `customMinters[hlTokenAddress] = address(0)`. [2](#0-1) 

**Dispatch logic — `OmniBridge.sol` lines 331–349:**

```solidity
} else if (customMinters[payload.tokenAddress] != address(0)) {
    // skipped — customMinter is address(0)
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(
            payload.recipient, payload.amount, payload.message   // ← triggers bug
        );
    }
}
``` [3](#0-2) 

Any non-empty `payload.message` causes the 3-arg override to be called. The override mints tokens to `payload.recipient` and then immediately transfers them all to `_systemAddress`. The `payload.message` content is irrelevant — even a single byte triggers this path.

**Why existing checks fail:** Signature verification by `nearBridgeDerivedAddress` only authenticates the payload; it does not constrain the `message` field to any specific format or value. The `isBridgeToken` guard correctly identifies the token but does not distinguish between HyperEVM-bound and HyperCore-bound transfers. The `message.length == 0` branch check is the sole dispatch criterion, and it is insufficient.

**On-chain release mechanism is absent:** `coreReceiveWithData` — the only function that moves tokens out of `_systemAddress` — requires `msg.sender == _systemAddress` and a specifically formatted `data` payload (action byte + ABI-encoded parameters). [4](#0-3) 

The `message` passed to `finTransfer` is not forwarded to `coreReceiveWithData` anywhere in the on-chain code. There is no on-chain path by which the bridge can recover or redirect the tokens once they are at `_systemAddress`.

## Impact Explanation

**Critical — permanent loss of bridged funds.** Any user who includes a non-empty `message` in a cross-chain transfer whose destination token is `HyperliquedBridgeToken` will have their entire bridged amount diverted to `_systemAddress`. The destination nonce is marked used (`completedTransfers[nonce] = true`) and `FinTransfer` is emitted, making the transfer unreplayable through normal bridge flows. This directly matches the allowed impact class: *permanent freezing / loss of bridged funds* and *escrow mis-accounting that changes user balances*.

## Likelihood Explanation

**Medium.** The `message` field is a standard, user-exposed parameter in `initTransfer` on every supported chain. Users integrating with DeFi protocols, attaching memos, or using the message field for cross-chain routing (e.g., the `ACTION_INIT_TRANSFER` path in `coreReceiveWithData`) will trigger this path. No special privilege is required — any unprivileged user who includes a non-empty `message` in a transfer targeting a `HyperliquedBridgeToken` destination triggers the bug. The relayer faithfully carries the message through to `finTransfer`, and the MPC signature covers the full payload including the message.

## Recommendation

1. **Preferred fix:** In `OmniBridge.finTransfer`, always call the 2-arg `mint(recipient, amount)` for `isBridgeToken` tokens, regardless of `message.length`. The HyperCore accounting path should only be triggered via `coreReceiveWithData`, not via `finTransfer`.
2. **Alternative:** Register `HyperliquedBridgeToken` with a dedicated `customMinter` contract that correctly separates the HyperEVM direct-mint path (no message) from the HyperCore accounting path (with message), ensuring the `message` content is validated and the recipient is correctly resolved before any `_update` to `_systemAddress`.
3. **Minimum mitigation:** Override the 3-arg `mint()` in `HyperliquedBridgeToken` so that when called by the bridge owner it mints directly to the recipient without the `_update` re-route. The HyperCore `_update` should only occur via `coreReceiveWithData`.

## Proof of Concept

1. Deploy `HyperliquedBridgeToken` and register: `addCustomToken(nearTokenId, hlTokenAddress, address(0), 18)` → `isBridgeToken[hlTokenAddress] = true`, `customMinters[hlTokenAddress] = address(0)`.
2. A user on NEAR calls `initTransfer` / `ft_on_transfer` with `message = "x"` (any single non-empty byte), targeting a HyperEVM recipient address.
3. The relayer collects the MPC-signed payload and submits it to `OmniBridge.finTransfer`.
4. Signature verification passes; `completedTransfers[nonce]` is set to `true`.
5. Dispatch: `customMinters[hlTokenAddress] == address(0)` → skip custom minter; `isBridgeToken[hlTokenAddress] == true` → enter bridge token branch; `payload.message.length > 0` → call 3-arg `mint(recipient, amount, message)`.
6. Inside `HyperliquedBridgeToken.mint`: `_mint(recipient, amount)` credits recipient; `_update(recipient, _systemAddress, amount)` immediately moves all tokens to `_systemAddress`.
7. `FinTransfer` event emitted. Recipient ERC-20 balance: **0**. `_systemAddress` balance: **+amount**. Nonce consumed. No on-chain recovery path exists.
