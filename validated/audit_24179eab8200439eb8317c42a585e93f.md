### Title
Unprivileged Front-Running of `request_refund` Allows Attacker to Redirect BTC Refunds to Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
Any NEAR account can call `request_refund` for any unprocessed Bitcoin deposit. When the original `deposit_msg` does not contain a `refund_address`, the caller freely supplies the BTC destination. Because only the first successful call per UTXO is accepted, an attacker who observes a pending `request_refund` transaction (or simply monitors the Bitcoin chain for unprocessed deposits) can race the legitimate user and register their own BTC address as the refund destination, locking the legitimate user out and potentially redirecting the BTC to the attacker.

### Finding Description

`internal_request_refund` accepts a caller-supplied `refund_address` and only enforces that it matches `deposit_msg.refund_address` when that optional field is set:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a BTC return address), any caller may pass any BTC address. The callback then enforces a first-writer-wins rule:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

All inputs needed to construct a valid `request_refund` call — `deposit_msg` (embedded in the Bitcoin OP_RETURN), `tx_bytes`, `vout`, and the Merkle inclusion proof — are publicly visible on the Bitcoin blockchain. There is no check that the caller is the original depositor or the `recipient_id` named in `deposit_msg`.

The `resolve_execute_refund_timelock` function itself acknowledges the risk by applying a longer `unsafe_refund_timelock_sec` for this case, explicitly to give the DAO time to reject:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [3](#0-2) 

However, this is a reactive, operator-dependent mitigation, not a protocol-level access control.

### Impact Explanation

If the DAO/RefundOperator does not reject the attacker's request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the bridge constructs and signs a Bitcoin transaction paying the attacker's BTC address. The legitimate depositor permanently loses their BTC. Even if the DAO does reject, the legitimate user's own `request_refund` call has already failed ("Refund request already exists"), leaving their funds stuck until the DAO acts — requiring operator intervention to restore the normal flow.

This matches: **Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**, with escalation to **Critical — significant loss of user funds** if the DAO fails to monitor and reject in time.

### Likelihood Explanation

- All required inputs are publicly available on the Bitcoin blockchain.
- No special role, key, or privilege is required.
- The attack is profitable whenever the deposit amount exceeds the gas fee.
- NEAR block times are ~1 second, giving an attacker ample opportunity to submit before or concurrently with the legitimate user.
- Deposits where users omit `refund_address` (the default/common path) are universally vulnerable.

### Recommendation

1. **Bind `request_refund` to the depositor**: Require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`, or require the caller to prove ownership of the deposit (e.g., sign a challenge with the BTC key that funded the deposit address).
2. **Require pre-committed refund address**: Treat a missing `deposit_msg.refund_address` as non-refundable via the public path; only allow `execute_refund` for deposits that pre-committed a `refund_address`.
3. **Alternatively, restrict `request_refund` to whitelisted relayers** (similar to `verify_deposit`) and have the relayer verify the caller's identity off-chain before submitting.

### Proof of Concept

1. Alice sends 0.01 BTC to her deposit address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: null }`. The deposit is never processed by a relayer.
2. Alice constructs a `request_refund` call with her own BTC address `alice_btc_addr` and submits it to NEAR.
3. Attacker Bob observes Alice's pending transaction (or independently scans the Bitcoin chain for unprocessed deposits). Bob submits `request_refund` with the same `deposit_msg`, `tx_bytes`, `vout`, and proof, but with `refund_address = bob_btc_addr`. Bob's transaction is included first.
4. Alice's transaction fails: `"Refund request already exists for this UTXO"`. [4](#0-3) 
5. Bob waits for `unsafe_refund_timelock_sec` to elapse. If the DAO does not call `reject_refund`, Bob calls `execute_refund`.
6. The bridge builds and MPC-signs a Bitcoin transaction paying `bob_btc_addr` the full deposit minus gas fee. [5](#0-4) 
7. Alice's 0.01 BTC is permanently redirected to Bob.

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
