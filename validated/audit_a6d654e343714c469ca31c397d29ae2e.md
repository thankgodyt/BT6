### Title
Unconditional Peras Certificate Acceptance Due to Missing Validation in `validatePerasCert` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer can inject arbitrary Peras certificates via the object-diffusion mini-protocol, causing those certificates to be stored in the `PerasCertDB` and applied as chain-selection weight boosts, potentially causing a node to prefer a non-canonical chain.

### Finding Description
The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for accepting inbound Peras certificates. The universal instance that covers all block types is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is the **only** instance in production code. It accepts every certificate unconditionally and assigns it the full `perasWeight` boost (default: 15). The function signature promises validation but the body performs none.

This function is called directly in the production inbound-certificate processing path:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    }
``` [2](#0-1) 

`processCerts` partitions results into valid/invalid; since `validatePerasCert` never produces a `Left`, every certificate from every peer is accepted and timestamped: [3](#0-2) 

Accepted certificates are stored in `PerasCertDB` and their weight snapshot is read during both initial chain selection and per-block chain selection: [4](#0-3) 

The `PerasWeightSnapshot` derived from these certificates is passed to `preferAnchoredCandidate`, which uses it to compare candidate chains. A certificate boosting block `B` by weight 15 can tip chain selection in favour of any chain containing `B`.

### Impact Explanation
An unprivileged peer that speaks the Peras certificate object-diffusion mini-protocol can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` (any `Point blk`). Because `validatePerasCert` always returns `Right`, the certificate passes the validation gate, is stored in `PerasCertDB`, and its boost weight is applied during chain selection. By targeting a block on a minority or adversarial fork, the attacker can cause an honest node to prefer a non-canonical chain — a chain-selection safety failure. This matches the allowed impact: **bypass of Peras certificate checks that enables unauthorized certificate acceptance** and a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

### Likelihood Explanation
The Peras object-diffusion mini-protocol infrastructure is wired into the production `NodeKernel` and `ChainDB`. Any peer that successfully completes the Peras cert mini-protocol handshake can send certificates. No special privileges, keys, or stake are required. The only prerequisite is a network connection to the target node. Likelihood is **High** once Peras is enabled on a live network; the code path is already present and active in the repository.

### Recommendation
Replace the stub with a real implementation that checks, at minimum:
1. The certificate's `pcCertRound` is within the valid window relative to the current slot.
2. The `pcCertBoostedBlock` refers to a block that actually exists in the node's chain or VolatileDB.
3. The certificate carries a valid aggregate signature from a quorum of eligible committee members (cryptographic verification).

Until a real implementation is available, `validatePerasCert` should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the stub's failure mode is safe rather than unsafe.

### Proof of Concept
1. Connect to a target node that has the Peras cert mini-protocol enabled.
2. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point on an adversarial fork>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCertBoost = 15 })`.
4. `ChainDB.addPerasCertAsync` stores the certificate; `PerasCertDB.getWeightSnapshot` now includes a +15 boost for the adversarial block.
5. On the next chain selection event, `preferAnchoredCandidate` uses the boosted weight, potentially selecting the adversarial fork over the canonical chain. [5](#0-4) [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
