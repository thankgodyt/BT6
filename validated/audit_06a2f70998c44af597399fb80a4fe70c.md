### Title
Unified Address with transparent+Orchard receivers causes `require!(len==1)` panic in `check_withdraw_psbt`, creating stuck withdrawal state — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary
An unprivileged user can supply a Zcash Unified Address with both a transparent receiver and an Orchard receiver as `target_btc_address`, combined with a PSBT containing both a transparent output to the transparent receiver and an Orchard bundle paying the Orchard receiver. This causes `actual_received_amounts` to accumulate two entries, panicking the `require!(actual_received_amounts.len() == 1)` guard in `check_withdraw_psbt`.

### Finding Description
In `check_withdraw_psbt` (`psbt.rs` lines 184–223):
- `target_address_script_pubkey` returns `Some(transparent_script)` for a UA with a transparent receiver (per the inline comment, `None` is only for shielded-only UAs).
- The transparent output matching the transparent receiver is pushed to `actual_received_amounts` (len=1).
- `add_extra_outputs` then unconditionally pushes the Orchard bundle amount (len=2).
- `require!(actual_received_amounts.len() == 1)` panics.

`validate_orchard_bundle` (which could theoretically reject mismatched bundles) is called at line 260, **after** the panicking guard, so it provides no protection here.

### Impact Explanation
The relayer's signing transaction panics and reverts. The user's withdrawal remains in a pending state with funds locked. No theft or unauthorized minting occurs. Impact is a stuck withdrawal state requiring operator intervention to cancel/refund.

### Likelihood Explanation
Any user initiating a Zcash withdrawal can supply a UA with both receiver types and a PSBT with both output types. The parameters are fully user-controlled through the public `ft_on_transfer` path. However, the attacker harms only their own withdrawal (burns their own tokens to create an unprocessable request).

### Recommendation
In `check_withdraw_psbt`, before calling `add_extra_outputs`, check whether `actual_received_amounts` is already non-empty (i.e., a transparent user output was found). If so, reject the PSBT with a clear error rather than allowing `add_extra_outputs` to push a second entry. Alternatively, enforce at PSBT construction time that a UA with a transparent receiver must not also include an Orchard bundle paying the same UA.

### Proof of Concept
1. Construct a Zcash Unified Address `UA` with both a transparent receiver `T` and an Orchard receiver `O`.
2. Call `ft_on_transfer` on the bridge with `target_btc_address = UA`, `output = [TxOut { script_pubkey: script_for_T, value: X }]`, and `chain_specific_data.orchard_bundle_bytes = valid_orchard_bundle_paying_O`.
3. The bridge stores the pending withdrawal. When the relayer calls `check_withdraw_psbt_valid`, `actual_received_amounts` accumulates `[X, orchard_amount]` and `require!(len==1)` panics.
