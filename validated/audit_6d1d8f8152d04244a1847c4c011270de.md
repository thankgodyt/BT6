### Title
Missing Freshness Check on `get_last_block_height()` Allows Stale Block Height to Drive Wrong Zcash `branch_id` and Expired `expiry_height` - (File: `contracts/satoshi-bridge/src/btc_light_client/mod.rs`)

---

### Summary

The Zcash withdrawal path calls `get_last_block_height()` on the BTC light client to determine the Zcash consensus `branch_id` and `expiry_height` for every PSBT it constructs. There is no staleness check on the returned height. If the light client's reported height lags behind the real Zcash chain tip — for example, because relayers have stopped submitting headers — the bridge silently constructs transactions with the wrong consensus branch ID or an already-expired `expiry_height`. Those transactions are rejected by the Zcash network, the withdrawal can never be finalized, and the user's nBTC tokens are permanently locked inside the bridge contract.

---

### Finding Description

`get_last_block_height_promise()` issues a cross-contract call to the external BTC light client and returns whatever height that contract currently stores:

```rust
// contracts/satoshi-bridge/src/btc_light_client/mod.rs  lines 201-206
pub fn get_last_block_height_promise(&self) -> Promise {
    let config = self.internal_config();
    ext_btc_light_client::ext(config.btc_light_client_account_id.clone())
        .with_static_gas(GAS_FOR_GET_LAST_BLOCK_HEIGHT)
        .get_last_block_height()
}
```

The callback `ft_on_transfer_callback` receives this value and uses it immediately — with no freshness guard — to derive both the consensus branch ID and the expiry height:

```rust
// contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs  lines 110-136
pub fn ft_on_transfer_callback(
    ...
    #[callback_unwrap] last_block_height: u32,
) -> U128 {
    let expiry_height = self.get_expiry_height(&chain_specific_data, last_block_height);
    ...
    let psbt = PsbtWrapper::new(
        input, output, orchard_bundle,
        expiry_height,
        last_block_height,          // drives branch_id
        ...
    );
    ...
}
```

Inside `PsbtWrapper::new`, `get_branch_id(current_height, config)` maps the height to one of `BranchId::Nu6 / Nu6_1 / Nu6_2`:

```rust
// contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs  lines 543-545
fn get_branch_id(current_height: u32, config: &Config) -> BranchId {
    config.chain.get_branch_id(current_height)
}
```

The same stale height is fed into every RBF and cancel path through the same `get_last_block_height_promise()` → callback pattern defined by the `define_rbf_callback!` macro:

```rust
// contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs  lines 24-34
let _ = self.get_last_block_height_promise().then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_RBF_CALL_BACK)
        .$callback_name(...),
);
```

There is no stored "last accepted height", no timestamp comparison, and no minimum-height guard anywhere in the production path.

---

### Impact Explanation

**Scenario A — wrong `branch_id` across a network upgrade.**
If the light client has not been updated since before a Zcash network upgrade (e.g., Nu6 → Nu6_1 → Nu6_2 activation height), `get_branch_id` returns the pre-upgrade branch ID. The signed transaction carries the wrong `consensus_branch_id` field and is unconditionally rejected by every Zcash full node. The withdrawal can never be confirmed.

**Scenario B — expired `expiry_height`.**
`expiry_height` is set to `last_block_height + expiry_height_gap`. If `last_block_height` is many blocks behind the real chain tip, the computed expiry height may already be in the past. Zcash nodes reject transactions whose `expiry_height` is less than the current block height.

In both scenarios the withdrawal flow stalls:
- The user's nBTC tokens were transferred to the bridge at the start of `ft_on_transfer` and are held there.
- `verify_withdraw` is never called because the Zcash transaction is never mined.
- Every RBF and cancel attempt re-uses the same stale height, producing the same invalid transaction.
- The nBTC tokens are permanently locked in the bridge contract with no user-accessible recovery path.

This matches the allowed impact: **Medium — stuck bridge state requiring operator intervention** (and potentially **Critical** if the operator cannot recover the locked nBTC, constituting significant permanent locking of user funds).

---

### Likelihood Explanation

The BTC light client is updated by off-chain relayers. Relayer downtime, a missed network-upgrade deployment, or a deliberate griefing pause are all realistic. Zcash has had multiple network upgrades (Nu5, Nu6, Nu6_1, Nu6_2) in recent years; the bridge already encodes three distinct branch IDs, confirming that upgrade transitions are an expected operational event. A staleness window of even a few hundred blocks is enough to cross an activation height and trigger the wrong branch ID.

---

### Recommendation

After receiving `last_block_height` from the light client, validate that it is within an acceptable freshness window before using it to construct any transaction. A concrete approach:

1. Store `last_accepted_block_height` and `last_accepted_block_timestamp_sec` in `ContractData` each time a deposit proof is successfully verified (the light client must be live for that to succeed).
2. In `ft_on_transfer_callback` (and every RBF/cancel callback), add:

```rust
let now = nano_to_sec(env::block_timestamp());
require!(
    now - self.data().last_accepted_block_timestamp_sec < MAX_BLOCK_HEIGHT_STALENESS_SEC,
    "Light client block height is stale; withdrawal paused"
);
require!(
    last_block_height >= self.data().last_accepted_block_height,
    "Light client reported a regressed block height"
);
```

Alternatively, expose a configurable `max_block_height_staleness_sec` in `Config` (analogous to Chainlink's heartbeat) and enforce it at every point where `last_block_height` is consumed.

### Proof of Concept

1. Light client is at height H (e.g., 2,999,999 — one block before Nu6_2 activation at 3,000,000).
2. Relayers stop submitting headers; light client stays at H.
3. Real Zcash chain advances past 3,000,000 (Nu6_2 activates).
4. User calls `nbtc.ft_transfer_call(bridge, 1_000_000, WithdrawMsg{...})`.
   - nBTC tokens transferred to bridge balance.
5. Bridge calls `get_last_block_height()` → returns H = 2,999,999.
6. `get_branch_id(2_999_999, config)` → `BranchId::Nu6_1` (pre-upgrade).
7. `expiry_height` = 2,999,999 + gap (e.g., 100) = 3,000,099 — may already be below real tip.
8. PSBT is constructed with `branch_id = Nu6_1`; Chain Signatures signs it.
9. Relayer broadcasts to Zcash network → **rejected** (`consensus_branch_id` mismatch or expired).
10. User attempts RBF → same stale height → same rejection.
11. User attempts cancel → same stale height → same rejection.
