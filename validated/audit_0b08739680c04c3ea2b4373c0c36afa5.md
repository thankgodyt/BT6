### Title
Unverified MPC Signature in `sign_btc_transaction_callback` Combined with Missing Caller Access Control on `sign_btc_transaction` Enables Attacker to Permanently Lock Victim's Bridged Funds - (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

`sign_btc_transaction` in `api/chain_signatures.rs` has no caller access control — any NEAR account can invoke it for any pending transaction with any `key_version`. The `sign_btc_transaction_callback` in `chain_signature.rs` accepts the MPC-returned `SignatureResponse` and embeds it into the PSBT without performing any cryptographic verification that the signature is valid for the expected payload and derived public key. An attacker can front-run a victim's signing call with a wrong `key_version`, causing the MPC to sign with a different key than the one used to derive the BTC address. The bridge blindly accepts and stores this invalid signature, and the "Already signed" guard prevents the legitimate user from re-signing, permanently locking their funds.

---

### Finding Description

**Root cause 1 — Missing access control on `sign_btc_transaction`:** [1](#0-0) 

The function is `#[payable]` and `#[pause]`-gated but has **no check** that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. Any NEAR account can call it with any `btc_pending_sign_id` and any `key_version`.

**Root cause 2 — `key_version` is fully attacker-controlled and not validated:** [2](#0-1) 

The `key_version` supplied by the caller is forwarded verbatim to the MPC `sign` call. The bridge's own key derivation (`generate_btc_public_key`) uses only `path` — it does **not** incorporate `key_version`: [3](#0-2) 

So if the MPC signs with `key_version=N` (N ≠ 0), it produces a signature under a different private key than the one whose public key is embedded in the PSBT.

**Root cause 3 — No signature verification in the callback:** [4](#0-3) 

The callback:
- Deserializes the `SignatureResponse` (line 142–143)
- Derives the expected `public_key` from `path` (lines 145–152)
- Immediately stores the signature and calls `psbt.save_signature(sign_index, signature, public_key)` (line 168)

There is **no step** that calls `secp256k1::verify(payload, signature, public_key)`. The `payload` (the sighash computed in `internal_sign_btc_transaction`) is not even passed to the callback, making verification impossible as currently structured.

**Root cause 4 — "Already signed" guard prevents re-signing:** [5](#0-4) 

Once the attacker's invalid signature is stored, the legitimate user's subsequent call to `sign_btc_transaction` for the same `sign_index` is rejected with `"Already signed"`.

---

### Impact Explanation

An attacker who front-runs a victim's `sign_btc_transaction` call with a wrong `key_version` causes the MPC to produce a signature under a different key. The bridge accepts this signature without verification, embeds it into the PSBT, and — once all inputs are signed — transitions the `BTCPendingInfo` to `PendingVerify` stage: [6](#0-5) 

The resulting `tx_bytes_with_sign` contains an invalid witness/script-sig. When broadcast to Bitcoin, the transaction is rejected by the network. The victim's UTXOs were already removed from the bridge's UTXO set when the pending info was created, so they cannot be re-used. For **refund transactions** (`PendingInfoState::Refund`), there is no `cancel_withdraw` or RBF path available — `cancel_withdraw` and `withdraw_rbf` both reject non-withdraw states: [7](#0-6) 

The victim's BTC is permanently locked in the bridge with no on-chain recovery path short of DAO intervention. For withdrawal transactions, `cancel_withdraw` is restricted to `Role::DAO` or `Role::Operator`: [8](#0-7) 

**Impact class:** Critical — permanent locking of user or protocol funds; chain-signature/PSBT construction failure enabling unauthorized redirection of bridge-controlled funds.

---

### Likelihood Explanation

- `btc_pending_sign_id` values are public on-chain state (stored in `btc_pending_infos`, queryable by anyone).
- The attack requires a single NEAR transaction call with no special privileges.
- The attacker only needs to submit their call before the victim's signing call — a standard front-running scenario on NEAR.
- No funds are required beyond NEAR gas and the MPC signing deposit.
- The attacker incurs no punishment.

---

### Recommendation

1. **Add caller access control to `sign_btc_transaction`**: Require `env::predecessor_account_id() == btc_pending_info.account_id` (or a whitelisted relayer role).

2. **Validate `key_version`**: Store the expected `key_version` in `BTCPendingInfo` at creation time and reject calls with a mismatched value.

3. **Verify the MPC signature in the callback**: Pass the `payload` (sighash) to the callback and perform `secp256k1::verify(payload, &signature.to_btc_signature(), &public_key)` before storing the signature. Reject and do not store the signature if verification fails.

---

### Proof of Concept

```
// Attacker observes victim's btc_pending_sign_id = "abc123" on-chain
// Victim's pending tx has 1 input (sign_index=0), correct key_version=0

// Attacker front-runs with wrong key_version
attacker.call(bridge, "sign_btc_transaction", {
    btc_pending_sign_id: "abc123",
    sign_index: 0,
    key_version: 999,   // wrong version → MPC signs with different key
})

// MPC signs with key at (path, key_version=999) ≠ key at (path, key_version=0)
// sign_btc_transaction_callback accepts the signature without verification
// signatures[0] = Some(invalid_signature)  ← stored
// psbt.save_signature(0, invalid_signature, correct_public_key)  ← embedded

// Victim now calls sign_btc_transaction with correct key_version=0
victim.call(bridge, "sign_btc_transaction", {
    btc_pending_sign_id: "abc123",
    sign_index: 0,
    key_version: 0,
})
// → PANICS: "Already signed"

// If single-input tx: is_all_signed() == true → moves to PendingVerify
// tx_bytes_with_sign contains invalid signature → rejected by Bitcoin
// Victim's BTC permanently locked; no on-chain recovery for Refund state
```
