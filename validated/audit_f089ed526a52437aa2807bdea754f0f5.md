Audit Report

## Title
Unguarded Token Loss in `SwapMigratedToken` Branch of `ft_on_transfer` — No Refund on Swap Failure - (File: `near/omni-bridge/src/lib.rs`)

## Summary

The `SwapMigratedToken` branch of `ft_on_transfer` schedules a parallel `burn.and(mint)` promise, immediately detaches it, and returns `U128(0)` to the NEP-141 layer. Because NEAR cross-contract receipts are not atomic across receipt boundaries, a successful `burn` receipt cannot be rolled back if the subsequent `mint` receipt panics. With no failure callback and no refund signal to the NEP-141 layer, the user's old tokens are permanently destroyed with zero new tokens minted.

## Finding Description

In `near/omni-bridge/src/lib.rs` at lines 275–279, the `SwapMigratedToken` arm unconditionally detaches the swap promise and returns `U128(0)`:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

The `swap_migrated_token` helper at lines 2738–2753 schedules both cross-contract calls in parallel via `burn.and(mint)`:

```rust
fn swap_migrated_token(&mut self, sender_id: AccountId, old_token: AccountId, amount: U128) -> Promise {
    let new_token = self.migrated_tokens.get(&old_token)
        .near_expect(BridgeError::TokenNotMigrated);
    let burn = ext_token::ext(old_token).burn(amount);
    let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
    burn.and(mint)
}
```

`Promise::and` in NEAR SDK schedules two independent action receipts. Each receipt executes in its own transaction context; a panic in one does not roll back the other. The `burn` receipt calls `OmniToken::burn`, which invokes `internal_withdraw` on the bridge's balance of `old_token` — this is committed once the receipt succeeds. The `mint` receipt calls `OmniToken::mint` with `msg: None`, which calls `internal_deposit(&account_id, amount)` on the new token. `internal_deposit` panics if `account_id` has no storage registration on the new token contract (standard NEP-141 behavior). When that panic occurs, the mint receipt fails and is reverted, but the burn receipt is already finalized and cannot be undone. The `U128(0)` return value was already committed to the NEP-141 `ft_transfer_call` resolver, so no refund is triggered.

Contrast with `init_transfer_internal` at lines 1838–1848, which explicitly returns `transfer_message.amount` on any internal failure, causing the NEP-141 layer to refund the caller. No equivalent guard exists for `SwapMigratedToken`.

## Impact Explanation

This constitutes a permanent, irreversible loss of bridged funds for the affected user. The user's `N` old tokens are burned (bridge's balance reduced by `N` on `old_token`), zero new tokens are minted, and no refund path exists. This matches the allowed critical impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR."*

## Likelihood Explanation

Any unprivileged user holding pre-migration tokens can trigger this by calling `old_token.ft_transfer_call(receiver_id: bridge, amount: N, msg: "\"SwapMigratedToken\"")` without first calling `storage_deposit` on the new token contract. Storage registration is a separate, non-obvious prerequisite in NEAR's NEP-141 model. The `migrated_tokens` map is DAO-controlled, but the DAO cannot enforce that every user registers storage before migrating. No privileged access is required; the scenario is realistic and repeatable.

## Recommendation

Replace the fire-and-forget pattern with a sequential promise chain that mints first and only burns on confirmed mint success, or add a `then` callback on `burn.and(mint)` that, on any failure, re-mints the old tokens back to the sender (or triggers a refund via a separate mechanism). The safest restructuring is: `mint → callback → if mint succeeded, burn; else refund`. At minimum, follow the pattern of `init_transfer_internal`: return `amount` from `ft_on_transfer` on any detectable precondition failure (e.g., check storage registration before scheduling any cross-contract calls).

## Proof of Concept

1. DAO registers `migrated_tokens[old_token] = new_token`.
2. User holds `N` units of `old_token` and has **not** called `storage_deposit` on `new_token`.
3. User calls `old_token.ft_transfer_call(receiver_id: bridge, amount: N, msg: "\"SwapMigratedToken\"")`.
4. Bridge's `ft_on_transfer` fires: `swap_migrated_token` schedules `burn(N).and(mint(user, N, None))`, detaches the joint promise, returns `U128(0)`.
5. NEP-141 resolver sees `U128(0)` → bridge keeps all `N` old tokens (no refund to user).
6. `burn(N)` receipt executes on `old_token`: bridge's balance reduced by `N` — committed.
7. `mint(user, N, None)` receipt executes on `new_token`: `internal_deposit` panics because `user` has no storage registration — receipt reverts, no tokens minted.
8. Result: `N` old tokens permanently burned, `0` new tokens received, no refund. Funds are irreversibly lost.

A local integration test using `near-workspaces` can reproduce this by deploying two `OmniToken` instances, registering only the bridge (not the user) on the new token, and asserting that after the `ft_transfer_call` the user's balance on both tokens is zero.
