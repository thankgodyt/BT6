Audit Report

## Title
Integer Division in `normalize_amount` Permanently Locks User Funds When Transfer Amount Is Below Decimal Precision Threshold — (File: near/omni-bridge/src/lib.rs)

## Summary

`normalize_amount` uses floor integer division to scale a token amount from origin-chain precision to destination-chain precision. When a user initiates a transfer with `amount - fee` smaller than `10^(origin_decimals - decimals)`, the normalized result is `0`. The `sign_transfer` function panics with `InvalidAmountToTransfer` every time it is called for this transfer — but the user's tokens are already locked in the bridge with no on-chain recovery path.

## Finding Description

`normalize_amount` performs floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

`sign_transfer` calls this and panics if the result is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
``` [2](#0-1) 

`init_transfer` only validates `fee < amount` before accepting tokens:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [3](#0-2) 

There is no check that `amount - fee` is at least `10^(origin_decimals - decimals)`. When storage and balance checks pass, `init_transfer_internal` stores the transfer in `pending_transfers`, calls `lock_tokens_if_needed`, and returns `U128(0)` — signaling to the NEP-141 token contract to keep all tokens: [4](#0-3) 

`ft_on_transfer` propagates this return value via `as_return()`, so the token contract retains the full transferred amount with no refund: [5](#0-4) 

Every subsequent call to `sign_transfer` for this `transfer_id` will always panic at the same guard. `sign_transfer_callback` only removes the transfer message when MPC signing succeeds and `fee.is_zero()`:

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
``` [6](#0-5) 

Since `sign_transfer` panics before the MPC call is ever made, this callback is never reached. There is no public `cancel_transfer` function. `claim_fee_callback` requires a valid proof from the destination chain (impossible since the transfer was never signed or executed). `update_transfer_fee` enforces `fee.fee >= current_fee.fee`, so the fee can only be increased — making `amount_without_fee` smaller and keeping the normalized result at zero: [7](#0-6) 

The transfer message and locked tokens are permanently stranded in `pending_transfers`.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, matching the critical impact class. Any user who initiates a NEAR → foreign-chain transfer with `amount - fee` below the minimum representable unit on the destination chain permanently loses their tokens. The tokens are locked in the bridge contract with no on-chain mechanism to recover them. Concrete example: token registered with `origin_decimals = 24`, `decimals = 18` (divisor = 1,000,000); user sends `amount = 500,000` with `fee = 0`; `normalize_amount(500_000, diff=6) = 0`; `sign_transfer` panics; 500,000 base units are permanently locked.

## Likelihood Explanation

The condition is reachable by any unprivileged user who calls `ft_transfer_call` on the token contract with a small amount and a valid `InitTransferMsg`. No special role or permission is required to initiate the transfer. Tokens with a large decimal difference between origin and destination chains (e.g., NEAR's 24-decimal tokens bridged to chains that register them at 18 decimals) have a minimum transferable unit of 1,000,000 base units. A user who sends any amount below this threshold triggers the permanent lock. This is a realistic user mistake, particularly for tokens with high decimal differences.

## Recommendation

Add a validation in `init_transfer` (before `init_transfer_internal` is called) that `normalize_amount(amount - fee, decimals) > 0`. This requires looking up the destination token's decimals at init time, mirroring the lookup already performed in `sign_transfer`. The check must be placed before tokens are accepted so that `ft_on_transfer` returns the full amount to the sender on failure.

```rust
// In init_transfer, before calling init_transfer_internal:
if let Some(token_address) = self.get_token_address(destination_chain, token_id) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        require!(
            Self::normalize_amount(amount_without_fee, decimals) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (6-decimal difference, divisor = 1,000,000).
2. Call `ft_transfer_call` on the token contract with `amount = 500_000` and `msg` encoding an `InitTransferMsg` with `fee = U128(0)` and a valid EVM recipient.
3. `init_transfer` accepts the tokens: `0 < 500_000` passes the only guard.
4. `init_transfer_internal` stores the transfer in `pending_transfers`, calls `lock_tokens_if_needed`, and returns `U128(0)` — tokens are locked.
5. Trusted relayer calls `sign_transfer` for this `transfer_id`.
6. `normalize_amount(500_000, diff=6) = 500_000 / 1_000_000 = 0` → `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`.
7. No MPC call is made; `sign_transfer_callback` is never reached; transfer message stays in `pending_transfers`.
8. Repeat step 5 indefinitely — always panics. Tokens are permanently locked with no recovery path.
9. Verify: call `get_transfer_message` for the `transfer_id` — it returns the stored message, confirming the entry is never removed.

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
