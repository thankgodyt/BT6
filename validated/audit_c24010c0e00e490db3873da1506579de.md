Audit Report

## Title
Token-2022 Transfer Fee Extension Causes Vault Under-Crediting vs. Cross-Chain Message Amount — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

In `InitTransfer::process`, `transfer_checked` is called with `payload.amount` as the transfer quantity. When the mint carries a Token-2022 `TransferFeeConfig` extension, the SPL runtime silently withholds the fee inside the vault's token account, so the vault's usable balance increases by only `amount - fee`. The Wormhole message is then posted with the unmodified `payload.amount`, causing NEAR to finalize a release of `amount` while only `amount - fee` is actually locked on Solana. `log_metadata` creates the vault permissionlessly with no check for `TransferFeeConfig`, making the entire attack path self-contained.

## Finding Description

In `InitTransfer::process`, the native-token branch calls:

```rust
transfer_checked(
    CpiContext::new(
        self.token_program.to_account_info(),
        TransferChecked { from, to: vault, authority, mint },
    ),
    payload.amount.try_into()...,
    self.mint.decimals,
)?;
``` [1](#0-0) 

No code reads back the vault's actual post-transfer balance. Immediately after, the Wormhole message is posted with the unmodified `payload`:

```rust
self.common.post_message(payload.serialize_for_near((
    self.common.sequence.sequence,
    self.user.key(),
    self.mint.key(),
))?)?;
``` [2](#0-1) 

The serialized message encodes `self.amount` directly — the original caller-supplied value, not the net received amount:

```rust
self.amount.serialize(&mut writer)?;
``` [3](#0-2) 

The vault is created permissionlessly in `log_metadata` via `init_if_needed`. The `process()` function unpacks the mint with `StateWithExtensions` and calls `get_extension::<MetadataPointer>()`, but never calls `get_extension::<TransferFeeConfig>()` and never rejects mints carrying a transfer fee extension: [4](#0-3) 

The vault account constraint in `log_metadata` is: [5](#0-4) 

`SECURITY.md` acknowledges transfer **hooks** as a known non-issue (runtime denial, not fund loss) but makes no mention of transfer **fees**: [6](#0-5) 

Transfer fees are fundamentally different from hooks: `transfer_checked` succeeds without any extra accounts, producing no runtime error — only a silent balance discrepancy. A grep across all Solana program source confirms there is no `TransferFeeConfig` check anywhere in the program.

## Impact Explanation

This is a concrete instance of **escrow mis-accounting** matching the allowed critical impact class: "Balance manipulation, escrow mis-accounting, fee mis-accounting … that changes user or protocol balances."

For every `init_transfer` on a mint with an `f` basis-point transfer fee:
- Vault receives: `amount × (1 − f/10000)`
- Wormhole message claims: `amount`
- NEAR releases: `amount`
- Protocol loss per transfer: `amount × f/10000`

At 10% fee and `amount = 1_000_000`, NEAR releases 1,000,000 while only 900,000 are locked. Repeated transfers drain the NEAR-side escrow relative to the Solana vault, enabling an attacker to extract more assets from NEAR than were ever deposited on Solana — a direct, repeatable theft of bridged funds.

## Likelihood Explanation

The attack requires no admin access, key compromise, or external collusion. All three steps are permissionless on-chain operations:
1. Create a Token-2022 mint with `TransferFeeConfig` (standard Solana CLI/SDK call).
2. Call `log_metadata` to register the vault — succeeds because there is no fee-extension check.
3. Call `init_transfer` repeatedly with any amount.

The attacker can be the sole participant and can repeat the exploit indefinitely until the NEAR-side escrow is drained.

## Recommendation

**Option A (preferred — fix in `InitTransfer::process`):** After `transfer_checked`, read back the vault's actual token balance (or compute the withheld fee via `TransferFeeConfig::calculate_epoch_fee`) and use the **net received amount** in the Wormhole message instead of `payload.amount`.

**Option B (defense-in-depth — fix in `log_metadata`):** When `token_program == token_2022::ID`, unpack the mint with `StateWithExtensions` and call `get_extension::<TransferFeeConfig>()`. If the extension is present, return an error to prevent registration of fee-bearing mints as native vault tokens. This mirrors the existing pattern for `MetadataPointer` inspection already present in `log_metadata::process`.

Both options should be applied together for defense in depth.

## Proof of Concept

1. On localnet, create a Token-2022 mint with `TransferFeeConfig` at 1000 bps (10%).
2. Call `log_metadata` — succeeds; vault PDA is created with no rejection.
3. Call `init_transfer` with `amount = 1_000_000`.
4. Assert `vault.amount == 900_000` (actual credited balance) vs. Wormhole payload `amount == 1_000_000` (reported).
5. On the NEAR side, finalize the transfer — NEAR releases 1,000,000 units while only 900,000 are locked in the Solana vault.
6. Repeat to drain the NEAR escrow by 10% per round-trip.

A Mollusk-based unit test can demonstrate steps 1–4 entirely in-process by constructing a Token-2022 mint account with the `TransferFeeConfig` extension packed into its data, passing it through the existing `run_init_transfer` harness, and asserting the vault balance post-instruction against the Wormhole message payload captured from the instruction result.     pub fn process(&mut self) -> Result<()> {
        let (name, symbol) = if self.token_program.key() == token_2022::ID {
            let mint_account_info = self.mint.to_account_info();
            let mint_data = mint_account_info.try_borrow_data()?;
            let mint_with_extension =
                StateWithExtensions::<spl_token_2022::state::Mint>::unpack(&mint_data)?;

            if let Ok(metadata_pointer) = mint_with_extension.get_extension::<MetadataPointer>() {
                if metadata_pointer.metadata_address.0 == self.mint.key() {
                    // Embedded metadata
                    let metadata =
                        mint_with_extension.get_variable_len_extension::<TokenMetadata>()?;
                    (metadata.name, metadata.symbol)
                } else if metadata_pointer.metadata_address.0 != Pubkey::default() {
                    // Third-party metadata
                    self.parse_metadata_account(metadata_pointer.metadata_address.0)?
                } else {
                    // No metadata
                    (String::default(), String::default())
                }
            } else {
                // No metadata pointer extension found
                (String::default(), String::default())
            }
        } else {
            // Only metaplex is supported for the classic SPL tokens
            self.parse_metadata_account(
                Pubkey::find_program_address(
                    &[
                        METADATA_SEED,
                        MetaplexID.as_ref(),
                        &self.mint.key().to_bytes(),
                    ],
                    &MetaplexID,
                )
                .0,
            )?
        };
