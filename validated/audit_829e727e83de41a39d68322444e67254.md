Looking at the `withdraw_rbf` public entry point in `bridge.rs` and comparing it with `cancel_withdraw`, there is a clear ownership-check discrepancy that is directly analogous to the reported vulnerability class.

### Title
Any NEAR Account Can Trigger RBF on Another User's Pending Withdrawal — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` is a public, unpermissioned function that accepts an arbitrary `original_btc_pending_verify_id`. It uses `env::predecessor_account_id()` (the caller) as the acting account without verifying that the caller owns the referenced pending withdrawal. Any NEAR account can invoke it against any other user's in-flight withdrawal, disrupting or hijacking the RBF flow.

### Finding Description

`withdraw_rbf` is documented as "The user actively increases the gas fee of the Withdraw transaction to accelerate it," implying it should only be callable by the withdrawal's owner. However, the implementation takes the caller's identity unconditionally:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // caller, not owner
    self.require_pending_sign_capacity(&account_id);  // checks caller's capacity

    self.withdraw_rbf_chain_specific(
        account_id,                          // caller becomes the RBF owner
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
``` [1](#0-0) 

Contrast this with `cancel_withdraw`, which explicitly looks up the original withdrawal owner from the stored `BTCPendingInfo` and uses that identity throughout:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();                              // owner fetched from state
    self.require_pending_sign_capacity(&user_account_id);
    self.cancel_withdraw_chain_specific(
        user_account_id, ...
    );
}
``` [2](#0-1) 

`BTCPendingInfo` stores the original initiator in its `account_id` field, which is set at withdrawal creation time: [3](#0-2) 

`withdraw_rbf` never reads or validates this field against `env::predecessor_account_id()`.

### Impact Explanation

An attacker (Bob) can call `withdraw_rbf` targeting Alice's `original_btc_pending_verify_id`. The RBF transaction is created under Bob's `account_id`, Bob supplies the `output` vector (which specifies the transaction outputs), and Alice's original pending withdrawal is superseded. At minimum this disrupts Alice's in-flight withdrawal and forces operator intervention to recover the stuck state. Depending on whether `withdraw_rbf_chain_specific` validates the output's target BTC address against the original withdrawal record, the impact could escalate to redirection of bridge-controlled BTC funds to an attacker-controlled address — a critical outcome.

**Impact: Medium** (attacker-triggered disruption/temporary locking of bridged funds; potential escalation to critical if output is not re-validated).

### Likelihood Explanation

`withdraw_rbf` is a public, payable-free, role-free function callable by any NEAR account. No special privilege, leaked key, or social engineering is required. The attacker only needs to know a victim's `btc_pending_id`, which is emitted as a public on-chain event (`GenerateBtcPendingInfo`) at withdrawal creation. [4](#0-3) 

**Likelihood: Medium.**

### Recommendation

Mirror the pattern used in `cancel_withdraw`: fetch the original withdrawal owner from `BTCPendingInfo.account_id` and assert it equals `env::predecessor_account_id()` before proceeding.

```rust
pub fn withdraw_rbf(...) {
    let caller = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the withdrawal owner can submit an RBF");
    self.require_pending_sign_capacity(&owner);
    self.withdraw_rbf_chain_specific(owner, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Alice calls `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`, creating a `BTCPendingInfo` with `account_id = alice` and `btc_pending_id = "abc"`. The `GenerateBtcPendingInfo` event is emitted publicly.
2. Bob observes the event and learns `btc_pending_id = "abc"`.
3. Bob calls `withdraw_rbf("abc", [malicious_output], None)`.
4. `env::predecessor_account_id()` returns Bob. `require_pending_sign_capacity(&bob)` passes (Bob has no pending txs).
5. `withdraw_rbf_chain_specific(bob, "abc", malicious_output, ...)` executes with Bob as the acting account and Bob-supplied outputs, superseding Alice's withdrawal without her consent. [1](#0-0) [2](#0-1)
