### Title
Silent Token Lock When `withdraw_relayer_address` Is Unset in Legacy `ft_transfer` Flow — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `ft_transfer` override in the nBTC contract implements a legacy withdrawal path for Near Intents. When the `withdraw_relayer_address` is not configured, the code silently falls through and transfers the caller's tokens to the nBTC contract itself instead of reverting, permanently locking user funds with no recovery path.

---

### Finding Description

`contracts/nbtc/src/lib.rs` overrides the NEP-141 `ft_transfer` to intercept a legacy withdrawal signal:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);
}
``` [1](#0-0) 

When `receiver_id == env::current_account_id()` and `memo` starts with `"WITHDRAW_TO:"`, the intent is to redirect tokens to a configured relayer. However, if `read_withdraw_relayer_address()` returns `None` (the address was never set), the inner `if let Some` branch is skipped and execution falls through to the unconditional `self.token.ft_transfer(receiver_id, amount, memo)` call — where `receiver_id` is still `env::current_account_id()`, i.e., the nBTC contract itself. [2](#0-1) 

`set_withdraw_relayer_address` is never called in the constructor `new()`, so the address starts as `None` and must be explicitly configured post-deployment. [3](#0-2) 

The nBTC contract has no function that allows the controller or bridge to recover tokens sitting in the contract's own token balance. The `burn` function only withdraws from `self.bridge_id`: [4](#0-3) 

**Analog to NIL_POOL_ID:** Just as `getStakingPoolIdOfMaker` returns `NIL_POOL_ID` for an unconfirmed maker and the caller proceeds without checking for nil, `read_withdraw_relayer_address()` returns `None` when unconfigured and the caller proceeds without checking — executing a harmful transfer instead of reverting.

---

### Impact Explanation

Tokens transferred to the nBTC contract's own balance are permanently locked. No privileged role (`controller`, `bridge_id`) has a code path to withdraw or burn tokens held under the contract's own account entry. This constitutes permanent burning below backed supply: nBTC supply is reduced from the user's perspective while the underlying BTC remains locked in the bridge, breaking the 1:1 backing invariant.

---

### Likelihood Explanation

Medium. The `withdraw_relayer_address` is optional and not initialized in `new()`. Any deployment window where the address is not yet set — or any chain/environment where the legacy Near Intents flow is not used and the address is intentionally left unset — exposes every user who attempts the legacy `ft_transfer` withdrawal to permanent token loss. The call is fully permissionless: any nBTC holder can invoke `ft_transfer` with a 1 yoctoNEAR attachment.

---

### Recommendation

Add an explicit revert when `withdraw_relayer_address` is `None` and the legacy signal is detected, rather than silently falling through:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer address not configured"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
self.token.ft_transfer(receiver_id, amount, memo);
```

This mirrors the fix recommended for NIL_POOL_ID: revert on the sentinel/None value rather than proceeding with a harmful default action.

---

### Proof of Concept

1. Deploy the nBTC contract without calling `set_withdraw_relayer_address` (the default state after `new()`).
2. A user holds nBTC and calls:
   ```
   ft_transfer(
     receiver_id = <nbtc_contract_account_id>,
     amount     = 1_000_000,
     memo       = Some("WITHDRAW_TO:bc1q...")
   )
   ```
   with 1 yoctoNEAR attached (standard NEP-141 requirement).
3. `receiver_id == env::current_account_id()` → `true`; `memo.starts_with("WITHDRAW_TO:")` → `true`.
4. `read_withdraw_relayer_address()` returns `None` → inner branch skipped.
5. Execution reaches `self.token.ft_transfer(receiver_id, amount, memo)` with `receiver_id` still equal to the nBTC contract.
6. `1_000_000` nBTC units are credited to the nBTC contract's own token balance.
7. No `burn`, `withdraw`, or admin function can recover these tokens — they are permanently locked, reducing backed supply below total supply.
