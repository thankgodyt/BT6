### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, regardless of content or cryptographic correctness. This stub is wired directly into the live Peras certificate diffusion inbound handler, meaning any unprivileged peer can inject arbitrary `PerasCert` objects that are accepted as `ValidatedPerasCert` and used to influence chain selection via Peras weight boosts.

---

### Finding Description

**Root cause — stub validator always succeeds:**

The only production `BlockSupportsPeras` instance is a catch-all `instance StandardHash blk => BlockSupportsPeras blk`. Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS signature check, no committee membership check, no round-number bounds check — every certificate is accepted.

**Inbound network path — stub is called on peer-supplied data:**

`makePerasCertPoolWriterFromChainDB` is the production writer used by the `PerasCertDiffusion` inbound handler. It passes `validatePerasCert mkPerasParams` as the validator to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound cert; because the stub always returns `Right`, every cert passes and is added to the `PerasCertDB` as a `ValidatedPerasCert`: [3](#0-2) 

**This writer is wired into the live node-to-node handler:**

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain selection consequence — accepted cert triggers fork switch:**

Once a `ValidatedPerasCert` is added to the `PerasCertDB`, `chainSelSync` processes it. It checks only that the boosted block is not older than the immutable tip and is present in the VolatileDB. If both conditions hold, it calls `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The `PerasWeightSnapshot` derived from accepted certificates is used in chain selection comparisons. A certificate boosting a block on a candidate chain gives that chain extra Peras weight, potentially making it preferred over the current chain. [6](#0-5) 

---

### Impact Explanation

**High — chain selection manipulation.** An unprivileged peer can craft a `PerasCert` pointing to any block currently in the target node's VolatileDB. Because `validatePerasCert` never rejects any certificate, the cert is accepted as `ValidatedPerasCert` and its Peras weight boost is applied to that block during chain selection. If the boosted block is on a candidate chain that is otherwise equal to or slightly shorter than the current chain, the weight boost may cause the node to switch to that candidate chain — an honest node is made to prefer a non-canonical or attacker-chosen chain without any legitimate quorum of committee votes.

---

### Likelihood Explanation

**Medium.** The `PerasCertDiffusion` mini-protocol is active in the production node-to-node handler. Any peer that can establish a connection can send `PerasCert` messages. The attack requires the Peras weight boost (`perasWeight params`) to be large enough to tip chain selection, which depends on the configured `PerasParams`. The attack is straightforward to execute once Peras is active on the network.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before the `PerasCertDiffusion` protocol is enabled in production. At minimum, verify the BLS aggregate signature against the committee's public keys for the claimed round, and check committee membership and quorum threshold.
2. **Gate the protocol behind a feature flag** until the real implementation (as partially defined in `Ouroboros.Consensus.Peras.Cert.V1`) is wired into the `BlockSupportsPeras` instance.
3. **Do not rely on the `TODO` comment** as a safety signal — the stub is already reachable from the live network handler.

---

### Proof of Concept

1. Connect to a target node as a peer via the node-to-node protocol.
2. Send a `PerasCert` message via the `PerasCertDiffusion` protocol with `pcCertRound` set to any round number and `pcCertBoostedBlock` pointing to a block hash known to be in the target node's VolatileDB (obtainable via ChainSync).
3. The cert reaches `processCerts`, which calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{...}`.
4. The cert is added to the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` processes `ChainSelAddPerasCert`: the boosted block is found in the VolatileDB, `chainSelectionForBlock` is called.
6. Chain selection now accounts for the Peras weight boost on the attacker-chosen block. If the candidate chain containing that block is otherwise competitive, the node switches to it — a chain selection outcome determined by an unauthenticated peer message rather than a legitimate committee quorum.
