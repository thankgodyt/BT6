### Title
`is_structure_equal` Validates Only JSON Structure, Not Values, Allowing Bypass of `post_action_msg_templates` Policy - (File: `contracts/satoshi-bridge/src/json_utils.rs`)

---

### Summary

The `is_structure_equal` function used to validate `PostAction.msg` against DAO-whitelisted templates checks only JSON key names and value **types**, never actual **values**. This is the direct analog of the external report's finding: just as `Swap1InchHook.inspect()` excludes `amount` and `minReturn` from its whitelisted arguments, `is_structure_equal` excludes all primitive values from its template comparison. Any user can craft a `DepositMsg` whose `post_action.msg` passes template validation while carrying arbitrary field values (e.g., `min_return: 0`, `recipient: "<attacker>"`, `token_id: "<malicious_token>"`), causing the bridge to execute whitelisted receiver contracts with parameters the DAO never approved.

---

### Finding Description

`check_deposit_msg` in `deposit_msg.rs` enforces that each `PostAction.msg` structurally matches at least one DAO-registered template: [1](#0-0) 

The structural comparison is delegated to `is_structure_equal`: [2](#0-1) 

The critical lines are:

```rust
(Value::String(_), Value::String(_)) => true,   // any string == any string
(Value::Number(_), Value::Number(_)) => true,   // any number == any number
(Value::Bool(_), Value::Bool(_)) => true,        // any bool == any bool
(Value::Null, _) => true,                        // null = unconstrained
``` [3](#0-2) 

So a template `{"Execute":{"actions":[{"IncreaseCollateral":{"token_id":"","amount":"","max_amount":""}}]}}` — exactly as registered in the unit tests for Burrowland — will match **any** JSON object that has the same keys and the same primitive types, regardless of what values those keys carry. [4](#0-3) 

After validation passes, the bridge mints nBTC and calls `nbtc.mint(…, post_actions)`. The nBTC contract's `handle_post_action` then executes `ft_on_transfer` on the whitelisted receiver with the user-supplied `msg` verbatim: [5](#0-4) 

The `msg` string passed to `ft_on_transfer` is exactly what the user embedded in the `DepositMsg` — no further sanitization occurs. [6](#0-5) 

---

### Impact Explanation

The `post_action_msg_templates` system exists precisely to restrict which operations whitelisted receiver contracts can be instructed to perform. Because `is_structure_equal` ignores primitive values, that restriction is illusory for any JSON-encoded message. A user can:

1. Set `min_return: 0` on a whitelisted DEX integration, making the swap sandwich-able with zero slippage protection.
2. Set `recipient` / `to` / `beneficiary` to an arbitrary address on any whitelisted contract that routes output based on the `msg`, redirecting the user's minted nBTC to an attacker.
3. Set `token_id` to a malicious token on a whitelisted lending protocol (e.g., Burrowland's `IncreaseCollateral`), depositing collateral for an unintended asset.

This constitutes a **bypass of bridge limits or policies**: the DAO's template whitelist does not actually constrain the values of parameters passed to whitelisted contracts, contrary to its stated purpose.

---

### Likelihood Explanation

The attack requires no privileged role. Any NEAR account can construct a `DepositMsg` with arbitrary `post_actions.msg` values, derive the corresponding BTC deposit address, send BTC to it, and have a trusted relayer submit `verify_deposit`. The deposit address derivation (`get_deposit_path`) hashes the full `DepositMsg`, so the manipulated `msg` is baked into the address the user funds — the relayer simply submits what the user prepared. [7](#0-6) 

The only prerequisite is that at least one receiver is whitelisted and has templates registered — a normal operational state.

---

### Recommendation

For non-`null` primitive values in a template, `is_structure_equal` should require an exact match rather than a type-only match:

```rust
(Value::String(t), Value::String(i)) => t == i,
(Value::Number(t), Value::Number(i)) => t == i,
(Value::Bool(t),   Value::Bool(i))   => t == i,
(Value::Null, _) => true,   // null remains the "wildcard" sentinel
```

This preserves the existing `null`-as-wildcard convention (rule 5 in the current doc comment) while ensuring that non-null primitive values in a template act as exact constraints. DAO operators who want to allow any value for a field (e.g., `amount`) should set that field to `null` in the template.

---

### Proof of Concept

**Setup**: DAO registers Burrowland as a whitelisted receiver with the template:
```
{"Execute":{"actions":[{"IncreaseCollateral":{"token_id":"","amount":"","max_amount":""}}]}}
```
(This is the exact template used in the existing unit tests.)

**Attack**:
1. Attacker constructs a `DepositMsg` with:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "burrowland.near",
       "amount": "50000",
       "msg": "{\"Execute\":{\"actions\":[{\"IncreaseCollateral\":{\"token_id\":\"evil_token.near\",\"amount\":\"999999999999\",\"max_amount\":\"999999999999\"}}]}}"
     }]
   }
   ```
2. Attacker derives the BTC deposit address from this `DepositMsg` and sends BTC to it.
3. Trusted relayer calls `verify_deposit` / `verify_deposit_v2` with the attacker's `DepositMsg`.
4. `check_deposit_msg` calls `is_structure_equal` on the `msg` against the template. All three fields (`token_id`, `amount`, `max_amount`) are strings in both template and input → returns `true`. [8](#0-7) 

5. Bridge mints nBTC and calls `nbtc.mint(…, post_actions)`.
6. `handle_post_action` calls `burrowland.ft_on_transfer(attacker.near, 50000, "{…evil_token…}")`.
7. Burrowland processes `IncreaseCollateral` for `evil_token.near` — an operation the DAO template was never intended to authorize. [6](#0-5)

```rust
pub fn is_structure_equal(template: &Value, input: &Value) -> bool {
    match (template, input) {
        (Value::Object(t_obj), Value::Object(i_obj)) => {
            for (key, t_val) in t_obj {
                if let Some(i_val) = i_obj.get(key) {
                    if !is_structure_equal(t_val, i_val) {
                        return false;
                    }
                }
            }
            // The input must not contain fields that are not defined in the template.
            for key in i_obj.keys() {
                if !t_obj.contains_key(key) {
                    return false;
                }
            }
            true
        }
        (Value::Array(t_arr), Value::Array(i_arr)) => {
            if t_arr.is_empty() {
                return i_arr.is_empty();
            }
            for i_item in i_arr {
                let mut matched = false;
                for t_item in t_arr {
                    if is_structure_equal(t_item, i_item) {
                        matched = true;
                        break;
                    }
                }
                if !matched {
                    return false;
                }
            }
            true
        }
        (Value::String(_), Value::String(_)) => true,
        (Value::Number(_), Value::Number(_)) => true,
        (Value::Bool(_), Value::Bool(_)) => true,
        (Value::Null, _) => true, // When a key’s value is not restricted, set its value to null.
        _ => false,
    }
```

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();
