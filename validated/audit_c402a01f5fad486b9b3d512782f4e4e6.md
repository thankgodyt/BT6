Audit Report

## Title
Precision Loss in `normalize_amount` Permanently Freezes Small-Amount NEAR-Outbound Transfers — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`normalize_amount` uses integer floor division to scale token amounts from NEAR's higher-precision representation to a lower-precision destination chain representation. When a user initiates a transfer with an amount below the normalization threshold (`amount < 10^(origin_decimals - decimals)`), the division truncates to zero. Every subsequent `sign_transfer` call for that transfer ID panics with `InvalidAmountToTransfer`, while the tokens remain permanently locked or burned in the bridge contract with no cancel or refund path.

## Finding Description

`normalize_amount` is defined as:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

`sign_transfer` calls this and panics if the result is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

The token locking and burning happen **before** `sign_transfer` is ever called, inside `init_transfer_internal`:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [3](#0-2) 

`init_transfer_internal` returns `U128(0)` on success, meaning the NEP-141 `ft_transfer_call` callback receives zero — no refund is issued to the user. [4](#0-3) 

The only guard at the `init_transfer` entry point is `fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [5](#0-4) 

There is no pre-normalization check. No `cancel_transfer`, `withdraw`, or recovery function exists anywhere in the contract — a search for such functions returns no matches. The `sign_transfer_callback` only removes the transfer message when signing **succeeds** and the fee is zero; a panic in `sign_transfer` leaves the pending transfer entry intact indefinitely. [6](#0-5) 

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, which is explicitly listed in the critical impact scope. For a native NEAR token with `origin_decimals = 24` mapped to an EVM token with `decimals = 18` (`diff_decimals = 6`), any transfer of fewer than `1,000,000` yocto-units (i.e., less than 1 unit in EVM terms) is irreversibly lost. The tokens are locked in the bridge's `locked_tokens` map (or burned if a deployed bridge token), the `pending_transfers` entry persists forever, and every `sign_transfer` call for that ID will always panic. The user has no recourse.

## Likelihood Explanation

The condition is reachable by any unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` public flow. No special role, leaked key, or privileged access is required. Any token pair where `origin_decimals > decimals` is affected — a common configuration (NEAR 24-decimal tokens bridged to 6-decimal or 18-decimal EVM tokens). A user sending a "small" amount (e.g., less than 1 full EVM unit) triggers the bug. The EVM `initTransfer` enforces only `fee < amount` with no minimum floor, so the same class of bug is reachable from the EVM side for tokens with the inverse decimal relationship.

## Recommendation

Add a normalization check **before** locking or burning tokens. The earliest safe enforcement point is inside `init_transfer` (or `init_transfer_internal`), immediately after constructing the `TransferMessage` and before calling `burn_tokens_if_needed` / `lock_tokens_if_needed`. Pre-compute `normalize_amount(amount_without_fee, decimals)` and reject the call (returning the full amount as a refund) if the result is zero. This mirrors the existing `fee < amount` guard and ensures no tokens are committed to a transfer that can never be signed.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`).
2. Call `ft_transfer_call` on the NEAR token contract with `amount = 999_999` yocto-units, targeting the bridge with a valid `InitTransferMsg` (fee = 0, valid EVM recipient).
3. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`: the transfer message is stored in `pending_transfers`, tokens are locked via `lock_tokens_if_needed`, and `U128(0)` is returned (no refund).
4. Relayer calls `sign_transfer` for the resulting `TransferId`.
5. `normalize_amount(999_999, {origin_decimals: 24, decimals: 18})` → `999_999 / 1_000_000 = 0`.
6. `require!(amount_to_transfer > 0)` panics with `InvalidAmountToTransfer`; all state changes in this call are reverted, but the transfer message and locked tokens from step 3 are unaffected.
7. Repeat step 4 indefinitely — the result is always the same panic.
8. The `999_999` yocto-units are permanently locked in the bridge with no recovery path.

A local unit test can reproduce this directly using the existing `Contract::normalize_amount` test harness in `near/omni-bridge/src/tests/lib_test.rs` by adding a case with `amount = 999_999` and `{origin_decimals: 24, decimals: 18}` and asserting the result is `0`, then tracing through `init_transfer_internal` to confirm tokens are committed before the zero-check in `sign_transfer`. [7](#0-6)
