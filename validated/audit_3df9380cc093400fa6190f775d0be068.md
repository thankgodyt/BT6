### Title
`assertWithMsg` Envelope Check in `revalidateHeader` Is a No-Op in Production Builds, Silently Bypassing Header Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/Assert.hs`, `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` guards its envelope check (block number, slot, hash chain) with `assertWithMsg`, which is compiled to a complete no-op in production builds because the `asserts` Cabal flag defaults to `False`. This is structurally identical to the reported ERC20 pattern: a critical check's return value is silently discarded, and execution proceeds unconditionally as if the check passed. In production, `revalidateHeader` performs **zero validation** — neither envelope nor protocol-level (KES/VRF) checks — on any header it processes.

---

### Finding Description

`assertWithMsg` is defined with a CPP guard:

```haskell
-- Assert.hs
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
```

`ENABLE_ASSERTIONS` is only set when the `asserts` Cabal flag is enabled. That flag defaults to `False`:

```
flag asserts
  description: Enable assertions
  manual: False
  default: False
```

In every production build, `assertWithMsg _ a = a` — the `Either String ()` result is unconditionally discarded.

`revalidateHeader` relies entirely on this guard for its envelope check:

```haskell
-- HeaderValidation.hs:539-561
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' =
    reupdateChainDepState ...   -- intentionally skips KES/VRF

  envelopeCheck :: Either String ()
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
```

`validateEnvelope` checks block number consecutiveness, slot monotonicity, and hash chain linkage. In production, the result of this check is computed but never acted upon. `reupdateChainDepState` also intentionally skips KES/VRF checks by design. The net result: **`revalidateHeader` in production accepts any header unconditionally**.

The sole production call site is `reapplyBlockLedgerResult` in `Extended.hs`:

```haskell
-- Extended.hs:213-227
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
  (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
 where
  ledgerResult = reapplyBlockLedgerResult evs (configLedger ...) blk tickedLedgerState
  hdr = revalidateHeader (getExtLedgerCfg cfg) ledgerView (getHeader blk) tickedHeaderState
```

This is invoked during:
1. **ImmutableDB replay at node startup** — every block in the immutable chain is replayed through `reapplyBlockLedgerResult`.
2. **Chain selection reapplication** — blocks in the `prevApplied` set (previously validated blocks) are reapplied via `ReapplyRef`/`ReapplyVal` paths in `Forker.validate`.

---

### Impact Explanation

**High. ChainDB/ImmutableDB replay bug that causes durable use of the wrong ledger state.**

If the ImmutableDB contains a block whose header has a corrupted envelope — wrong block number, wrong slot, or broken hash chain linkage — `revalidateHeader` will silently accept it in production, updating the `ExtLedgerState.headerState` with incorrect data. The node then continues building on this corrupted `HeaderState`, which is persisted as the new ledger state. All subsequent header validation (via `validateHeader`) uses the corrupted `HeaderState` as its base, meaning the `oldTip` used in `validateEnvelope` is wrong, causing the node to accept or reject future headers incorrectly.

This is a durable corruption: the wrong `HeaderState` is committed to the LedgerDB and used for all future chain selection decisions.

---

### Likelihood Explanation

**Medium.** The trigger requires the ImmutableDB to contain a block with a corrupted header envelope. This can occur via:
- A storage-layer bug that corrupts a block's header fields on disk (the ImmutableDB's `checkIntegrity` checks block body hash, not header field semantics).
- A crafted on-disk snapshot paired with a mismatched ImmutableDB segment (e.g., from a snapshot-converter or db-synthesizer tool producing inconsistent output).
- A bug in the `prevApplied` tracking that causes a block to be reapplied against a different `ChainDepState` than the one it was originally validated against (e.g., after a fork switch where rollback is incomplete).

The `asserts` flag is documented as `manual: False, default: False`, meaning it is off in all standard node deployments. The `cabal/asserts.cabal` override file enables it for development/CI builds only, not production.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with an unconditional enforcement that does not depend on a compile-time flag. The envelope check is cheap (pure comparison of block numbers, slot numbers, and hashes) and should always run:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case runExcept $ withExcept show $
         validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr of
    Left err -> error ("revalidateHeader: envelope check failed: " <> err)
    Right () ->
      HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' = reupdateChainDepState ...
```

Alternatively, if the performance cost is a concern, use a dedicated always-on guard (not CPP-gated) that at minimum checks hash chain linkage, since that is the invariant most critical to chain integrity.

### Proof of Concept

**Root cause chain:**

1. `ouroboros-consensus.cabal` line 36–37: `asserts` flag defaults to `False`, so `ENABLE_ASSERTIONS` is never defined in production. [1](#0-0) 

2. `Assert.hs` lines 9–13: Without `ENABLE_ASSERTIONS`, `assertWithMsg _ a = a` — the error branch is compiled away entirely. [2](#0-1) 

3. `HeaderValidation.hs` lines 539–561: `revalidateHeader` wraps its only validation call (`envelopeCheck`) in `assertWithMsg`. In production this is `id`, so the `Left` branch of `envelopeCheck` is never observed. [3](#0-2) 

4. `Extended.hs` lines 213–227: `reapplyBlockLedgerResult` calls `revalidateHeader` for every block replayed from the ImmutableDB or reapplied during chain selection. With the envelope check silently discarded, a block with a corrupted header (wrong block number, slot, or prev-hash) produces a valid-looking `HeaderState` that is committed to the `ExtLedgerState`. [4](#0-3) 

5. `Protocol.Abstract.hs` lines 184–201: The contract for `reupdateChainDepState` explicitly states "no validation checks should be performed," so there is no fallback protocol-level check either. [5](#0-4) 

**Concrete scenario:** A node restarts after ImmutableDB corruption (e.g., a block's `blockNo` field is incremented by 1 due to a storage write error). On replay, `revalidateHeader` is called for that block. `envelopeCheck` returns `Left "UnexpectedBlockNo ..."`. In production, `assertWithMsg (Left ...) result = result` — the error is discarded, and the corrupted `HeaderState` (with the wrong `AnnTip` block number) is stored in the `ExtLedgerState`. All subsequent `validateEnvelope` calls use this wrong `AnnTip` as `oldTip`, causing the node to reject the next legitimately valid block (whose block number is now "unexpected") or accept a block with a skipped block number.
