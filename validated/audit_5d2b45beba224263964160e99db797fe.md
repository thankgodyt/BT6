### Title
Unprivileged Caller Can Redirect Any User's BTC Refund to an Attacker-Controlled Address via `request_refund` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

The `request_refund` function in the `satoshi-bridge` contract is callable by any NEAR account. When a deposit was made with `deposit_msg.refund_address = None`, the function accepts an arbitrary `refund_address` from the caller with no check that the caller is the deposit recipient or is otherwise authorized. An attacker who observes the publicly emitted deposit event can front-run the legitimate user's refund request and register an attacker-controlled BTC address as the refund destination. Once the 14-day `unsafe_refund_timelock_sec` elapses without DAO intervention, the attacker can call `execute_refund` and permanently redirect the victim's BTC to themselves.

---

### Finding Description

**Root cause — missing caller authorization in `request_refund`:**

`request_refund` is a public, permissionless entry point (subject only to the `#[pause]` guard and a small anti-spam NEAR deposit): [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` this branch is skipped entirely, so the caller-supplied `refund_address` is stored verbatim with no ownership check: [3](#0-2) 

**Attacker entry path:**

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, … })`. The contract emits a `LogDepositAddress` event containing the full `deposit_msg`. [4](#0-3) 

2. Alice sends BTC to the derived address. The transaction is confirmed on Bitcoin.

3. Bob (attacker) reads the emitted event, reconstructs Alice's `deposit_msg`, and calls:
   ```
   request_refund(deposit_msg=alice_msg, refund_address=bob_btc_addr, tx_bytes=…)
   ```
   The Light Client proof is valid (the tx is real), `deposit_msg.refund_address` is `None`, so no address check fires. The refund request is stored with `refund_address = bob_btc_addr`.

4. Alice attempts the same call with her own BTC address — it panics with `"Refund request already exists for this UTXO"`: [5](#0-4) 

5. Because `deposit_msg.refund_address` is `None`, the `unsafe_refund_timelock_sec` (14 days) applies: [6](#0-5) 

6. If the DAO/Operator does not call `reject_refund` within 14 days, Bob calls `execute_refund` and the bridge's MPC pipeline signs a Bitcoin transaction sending Alice's BTC to Bob's address.

---

### Impact Explanation

If the DAO fails to monitor and reject the malicious refund request within the 14-day window, the victim's entire deposited BTC is permanently transferred to the attacker's Bitcoin address. The bridge's MPC signing pipeline will construct and sign a valid Bitcoin transaction paying the attacker. There is no on-chain mechanism for Alice to recover the funds after `execute_refund` completes. This constitutes **significant, permanent theft of user funds** — a Critical bridge impact.

---

### Likelihood Explanation

- Deposits with `refund_address: None` are a supported and documented flow (the "unsafe refund" path).
- The `get_user_deposit_address` event is public and observable by any NEAR RPC client, giving the attacker the exact `deposit_msg` needed.
- The attacker only needs to pay the small anti-spam NEAR deposit (`required_balance_for_request_refund`) and provide a valid Light Client proof (the tx is already on-chain).
- The 14-day window is a partial mitigation, but it relies entirely on the DAO actively monitoring every refund request and being able to distinguish legitimate from malicious ones — an operational assumption that can fail.
- The `#[trusted_relayer]` macro on the impl block only adds extra BTC confirmations for non-whitelisted callers; it does not block the call. [7](#0-6) 

---

### Recommendation

Restrict `request_refund` so that when `deposit_msg.refund_address` is `None`, only the `deposit_msg.recipient_id` (the intended NEAR beneficiary) may supply the `refund_address`. Add a check such as:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may specify refund_address when not pre-authorized"
    );
}
```

Alternatively, require `deposit_msg.refund_address` to always be set at deposit time (enforced in `get_user_deposit_address`) so the permissionless path is always safe.

---

### Proof of Concept

```
# Step 1 – Alice creates a deposit address with no pre-authorized refund address
alice.call("get_user_deposit_address", {
  deposit_msg: { recipient_id: "alice.near", refund_address: null, ... }
})
# → emits LogDepositAddress event with full deposit_msg

# Step 2 – Alice sends 1 BTC to the derived address (confirmed on Bitcoin)

# Step 3 – Bob front-runs Alice's refund request
bob.call("request_refund", {
  deposit_msg: { recipient_id: "alice.near", refund_address: null, ... },  // copied from event
  refund_address: "bc1q_BOB_CONTROLLED_ADDRESS",
  tx_bytes: <valid_proof>,
  vout: 0,
  proof: <valid_light_client_proof>,
  gas_fee: null
}, deposit=required_balance_for_request_refund())
# → succeeds; refund request stored with refund_address = bob's address

# Step 4 – Alice's attempt fails
alice.call("request_refund", { ..., refund_address: "bc1q_ALICE_ADDRESS", ... })
# → panics: "Refund request already exists for this UTXO"

# Step 5 – DAO does not reject within 14 days

# Step 6 – Bob executes the refund
bob.call("execute_refund", { utxo_storage_key: "<tx_id>@0", ... },
         deposit=required_balance_for_execute_refund())
# → bridge MPC signs a Bitcoin tx paying 1 BTC to bob's address
# Alice's BTC is permanently stolen
```
