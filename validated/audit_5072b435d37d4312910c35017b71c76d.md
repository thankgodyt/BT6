Audit Report

## Title
Missing Pre-flight Token Registration Check in `init_transfer` Causes Permanent Fund Freezing - (File: near/omni-bridge/src/lib.rs)

## Summary
`init_transfer` unconditionally consumes user tokens and stores the transfer in `pending_transfers` without verifying that the token is registered on the destination chain. If the token is absent from the destination chain mapping, every subsequent `sign_transfer` call panics at `get_token_address`, and no user-initiated code path exists to remove the transfer or recover the tokens, resulting in permanent freezing of bridged funds.

## Finding Description
When a user calls `ft_transfer_call` on a NEP-141 token with the bridge as receiver, `ft_on_transfer` dispatches to `init_transfer`. The function validates only that the recipient chain is not NEAR, then unconditionally increments the nonce, stores the `TransferMessage` in `pending_transfers`, and returns `U128(0)`, consuming all tokens: [1](#0-0) 

No check is made that the token is registered on the destination chain at this point. Later, when a relayer calls `sign_transfer`, the contract attempts to resolve the token address and panics if it is absent: [2](#0-1) 

The only code paths that call `remove_transfer_message` are:
1. `sign_transfer_callback` — only when `fee.is_zero()` **and** MPC signing succeeds.
2. `claim_fee_callback` — only after a successful on-chain proof of finalization. [3](#0-2) 

Because `sign_transfer` always panics when the token is unregistered, neither callback is ever reached. A search across the entire contract confirms no `cancel_transfer`, `refund_transfer`, or equivalent public function exists anywhere in the codebase.

## Impact Explanation
This directly matches the Critical allowed impact: **permanent freezing of bridged funds**. A user whose tokens are consumed by `init_transfer` for an unregistered destination token has no mechanism — user-initiated or time-based — to recover those tokens. The funds remain locked in the bridge contract indefinitely unless an admin separately registers the token (which is not guaranteed and is not a user-controlled action).

## Likelihood Explanation
The scenario is reachable by any unprivileged user through the standard `ft_transfer_call` public interface. No special privileges, leaked keys, or admin involvement are required to trigger the freeze. The condition is realistic during token onboarding: a user may attempt to bridge a token to a chain where the mapping has not yet been registered via `bind_token` or `deploy_token`. The contract provides no feedback at deposit time that the transfer will be permanently stuck, making this a plausible user error with irreversible consequences.

## Recommendation
1. **Add a pre-flight check in `init_transfer`** that calls `get_token_address` for the destination chain before consuming tokens, and returns `U128(amount)` (refunding the user) if the token is not registered.
2. **Add a `cancel_transfer` function** that allows the original sender (stored as `transfer.sender`) to remove a pending transfer from `pending_transfers` and receive a refund, provided the transfer has not yet been signed or finalized.
3. Optionally, add a time-based expiry so that transfers pending beyond a configurable window can be cancelled by the sender.

## Proof of Concept
1. Token `usdc.near` is registered on `ChainKind::Eth` but not on `ChainKind::Arb`.
2. User calls `usdc.near::ft_transfer_call(bridge, 1000, msg)` where `msg` specifies a recipient on Arbitrum.
3. `ft_on_transfer` → `init_transfer`: nonce incremented, `TransferMessage` stored in `pending_transfers`, `U128(0)` returned — 1000 USDC consumed by the bridge.
4. Relayer calls `sign_transfer(transfer_id, ...)`.
5. Inside `sign_transfer`, `get_token_address(ChainKind::Arb, usdc.near)` returns `None`, triggering `env::panic_str(BridgeError::FailedToGetTokenAddress)`.
6. Step 4–5 repeats indefinitely; `sign_transfer_callback` is never reached; `remove_transfer_message` is never called.
7. The user's 1000 USDC is permanently locked with no user-accessible recovery path.

A local integration test can reproduce this by: (a) deploying the bridge contract, (b) registering `usdc.near` only on `ChainKind::Eth`, (c) calling `ft_transfer_call` with an Arbitrum recipient, (d) asserting the transfer is stored in `pending_transfers`, (e) calling `sign_transfer` and asserting it panics with `FailedToGetTokenAddress`, and (f) asserting no cancel/refund function exists to recover the tokens.
