### Title
Peras Certificate Validation Is a No-Op Stub — Any Inbound Certificate from an Unprivileged Peer Is Unconditionally Accepted - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every certificate received from a peer, performing zero threshold or cryptographic checks. The same instance's `validatePerasVote` only checks stake-distribution membership and ignores round-number bounds and signatures entirely. Both stubs are wired into the live inbound-processing paths used by the Peras object-diffusion mini-protocol, so any connected peer can inject certificates with arbitrary round numbers and boosted-block points that are accepted as valid and applied to chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` is unconditionally `Right`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No check is performed on `pcCertRound` (the round number, a `PerasRoundNo` / `Word64`), `pcCertBoostedBlock` (the block point being boosted), or any quorum-signature proof. The function is the production implementation of the `BlockSupportsPeras` class method — it is not a test stub.

**Root cause — `validatePerasVote` ignores round number and signatures:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

The only check is whether the voter ID appears in the stake distribution. `pvVoteRound` (the round number) is never range-checked, and no cryptographic signature on the vote is verified.

**These stubs are the live inbound-processing path.** Both `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` call `processCerts` with `validatePerasCert mkPerasParams` as the validator:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  (validatePerasCert mkPerasParams)   -- ← always Right
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [3](#0-2) 

`processCerts` partitions results into valid/invalid; since `validatePerasCert` never returns `Left`, every certificate passes and is timestamped and stored:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

The same pattern applies to votes via `makePerasVotePoolWriterFromChainDB` → `processVotes` → `validatePerasVote mkPerasParams sd vote`. [5](#0-4)

### Impact Explanation

A `PerasCert` carries a `pcCertRound :: PerasRoundNo` and a `pcCertBoostedBlock :: Point blk`. When accepted, the certificate is stored in the `PerasCertDB` / `ChainDB` and its `vpcCertBoost` (derived from `perasWeight params`) is applied to the boosted block during chain selection. Because `validatePerasCert` never rejects anything, an adversary can:

1. Craft a `PerasCert` with `pcCertRound = maxBound` (or any arbitrary round) and `pcCertBoostedBlock` pointing to a block on an adversarial fork.
2. Deliver it via the Peras certificate diffusion mini-protocol.
3. The node accepts it, stores it, and applies the weight boost to the adversarial block during chain selection.
4. If the boost is large enough to tip the `preferAnchoredCandidate` comparison, the node switches to the adversarial chain — a chain-selection safety failure.

This directly matches the allowed impact class: **"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."**

The `PerasWeight` boost is non-trivial: `perasWeight params` is the configured Peras boost weight, which by design is large enough to influence chain selection (that is the entire point of Peras certificates). [6](#0-5) 

---

### Likelihood Explanation

**High.** The entry point is the standard Peras object-diffusion mini-protocol, reachable by any peer the node connects to. No special privileges, keys, or stake are required — the attacker only needs a network connection. The stub is in production source (not a test file), is compiled into the node binary, and the `TODO` comments referencing issue #120 confirm the validation was intentionally deferred, not accidentally omitted from a test.

---

### Recommendation

Implement real validation in `validatePerasCert` before the Peras certificate diffusion path is enabled in production:

1. **Round-number bounds**: reject certificates whose `pcCertRound` is not within a valid window relative to the current chain tip's Peras round (analogous to the `slippage` threshold the original report recommends).
2. **Quorum-signature proof**: verify that the certificate is backed by a valid quorum of stake-weighted signatures from the correct voting committee for that round.
3. **Block-point validity**: verify that `pcCertBoostedBlock` refers to a block that exists on a known chain fragment and is within the allowed boosting window.
4. Apply the same round-number and signature checks to `validatePerasVote`.

---

### Proof of Concept

An attacker peer sends a single `PerasCert` message via the object-diffusion protocol:

```haskell
PerasCert
  { pcCertRound       = PerasRoundNo maxBound   -- extreme value, no threshold check
  , pcCertBoostedBlock = adversarialBlockPoint   -- any block point
  }
```

Execution path:

1. `makePerasCertPoolWriterFromChainDB` → `processCerts` is called with the batch.
2. `validatePerasCert mkPerasParams cert` is called — returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
3. `partitionEithers` sees zero errors; `addCert (WithArrivalTime now validatedCert)` is called.
4. `ChainDB.addPerasCertAsync chainDB` stores the certificate.
5. Chain selection reads the certificate's boost and applies `vpcCertBoost` to `adversarialBlockPoint`, potentially causing the node to prefer the adversarial chain. [7](#0-6) [8](#0-7)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
