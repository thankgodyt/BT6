Audit Report

## Title
Blacklisted EVM Recipient Permanently Freezes Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
When a user bridges tokens from NEAR to an EVM chain, the MPC signature cryptographically binds the destination `recipient` address. If that address is subsequently blacklisted by the destination token (e.g., USDC, USDT), every call to `finTransfer` reverts — rolling back the nonce marking — but the transfer can never succeed because the recipient is immutably fixed in the signed payload. No mechanism exists to re-sign with a different recipient or to cancel the transfer and recover the NEAR-side locked tokens, resulting in permanent freezing of bridged funds.

## Finding Description

**Root cause — nonce rollback + fixed recipient + no recovery path:**

In `OmniBridge.sol::finTransfer`, the nonce is marked used at line 287 before the token transfer:

```solidity
completedTransfers[payload.destinationNonce] = true;   // line 287
// ... signature verification ...
IERC20(payload.tokenAddress).safeTransfer(             // line 351
    payload.recipient,
    payload.amount
);
``` [1](#0-0) [2](#0-1) 

If `safeTransfer` reverts (e.g., USDC blacklist check), Solidity rolls back the entire transaction including the `completedTransfers` write. The nonce is never consumed, so the transfer is not "used up" — but it can never succeed either.

The recipient is embedded in the MPC-signed payload in `sign_transfer`:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    recipient: transfer_message.recipient,   // fixed at init_transfer time
    ...
};
``` [3](#0-2) 

The `recipient` field of `TransferMessage` is set at `init_transfer` time and there is no function to update it. `update_transfer_fee` only modifies the `fee` field: [4](#0-3) 

No `cancel_transfer` or refund function exists anywhere in `near/omni-bridge/src/lib.rs`. The NEAR-side tokens remain locked in the bridge contract indefinitely.

The same structural issue exists in the Starknet path, where `_set_transfer_finalised` is called before the transfer and a failed `transfer` causes a full revert: [5](#0-4) 

## Impact Explanation

Tokens locked or burned on NEAR during `init_transfer` are permanently unrecoverable if the designated EVM recipient becomes blacklisted in the destination token after the transfer is initiated. This constitutes **permanent freezing of bridged funds**, matching the critical allowed impact class: *"permanent freezing of bridged funds across NEAR, EVM, Starknet."*

## Likelihood Explanation

USDC and USDT — two of the most commonly bridged assets — maintain on-chain blacklists actively enforced by Circle and Tether. Regulatory actions, sanctions enforcement, or exchange-driven freezes can blacklist an address at any time after a bridge transfer is initiated but before `finTransfer` is called. The user has no control over when blacklisting occurs relative to their bridge transaction. This is a realistic, documented scenario given the regulatory environment.

## Recommendation

1. **Add a cancel/refund path on NEAR**: Introduce a `cancel_transfer` function that, after a configurable timeout or upon explicit user request (verified against the stored `TransferMessage.sender`), burns the destination-nonce entry and refunds the locked/burned tokens to the original sender on NEAR.

2. **Allow recipient override on retry**: Permit the original sender (verified via the stored `TransferMessage.sender`) to request a new MPC signature with a different recipient address, consuming or invalidating the old nonce entry.

3. **Alternatively, use a pull pattern on EVM**: Instead of pushing tokens directly to `payload.recipient` in `finTransfer`, credit the amount to a claimable balance mapping keyed by `(nonce, recipient)`. The recipient (or a delegate) can then pull the tokens separately, isolating transfer failures from nonce consumption.

## Proof of Concept

1. Alice holds 10,000 USDC on NEAR and calls `ft_transfer_call` to bridge to her EVM address `0xAlice`. Tokens are locked on NEAR; `TransferMessage` is stored with `recipient = OmniAddress::Evm(0xAlice)`.
2. A trusted relayer calls `sign_transfer`; the MPC network signs a payload containing `recipient = 0xAlice` at `near/omni-bridge/src/lib.rs:497`.
3. Before the relayer submits `finTransfer` on EVM, Circle blacklists `0xAlice`.
4. The relayer calls `OmniBridge.finTransfer(signature, payload)`. Execution reaches `IERC20(usdc).safeTransfer(0xAlice, amount)` at line 351, which reverts with `"Blacklisted"`.
5. The entire EVM transaction reverts. `completedTransfers[nonce]` is rolled back to `false`.
6. Every subsequent attempt to call `finTransfer` with the same signed payload reverts identically.
7. No function exists to re-sign with a different recipient or to cancel the transfer and recover the NEAR-side tokens.
8. Alice's 10,000 USDC equivalent is permanently frozen in the NEAR bridge contract.

**Minimal test plan**: Deploy a mock ERC-20 with a blacklist. Lock tokens on a NEAR localnet fork. Obtain an MPC signature for a blacklisted recipient. Call `finTransfer` on a local EVM fork — confirm it reverts and `completedTransfers[nonce]` remains `false`. Confirm no on-chain path exists to recover the NEAR-side tokens.

    pub fn update_transfer_fee(&mut self, transfer_id: TransferId, fee: UpdateFee) {

                    BridgeError::SenderCanUpdateTokenFeeOnly.as_ref()
                );

                    .0

                    BridgeError::InvalidAttachedDeposit.as_ref()
