Audit Report

## Title
`sign_transfer()` Normalisation-to-Zero Check Placed After Irreversible Token Burn/Lock — Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal()` burns or locks user tokens before any check that the normalised transfer amount is non-zero. `sign_transfer()` then performs `require!(amount_to_transfer > 0, …)` in a separate NEAR transaction; if floor-division truncates the amount to zero, this `require!` always panics. Because NEAR atomicity does not span transactions, the tokens are already irreversibly destroyed and no refund or cancel path exists, permanently destroying the user's funds.

## Finding Description

**Step 1 — `init_transfer_internal` (called from `ft_on_transfer` → `init_transfer`):**

Tokens are burned or locked unconditionally once storage accounting succeeds:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
}
```

The only fee guard at this stage is:

```rust
// L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

There is no check that `normalize_amount(amount_without_fee, decimals) > 0`.

**Step 2 — `sign_transfer` (separate transaction, called by a trusted relayer):**

```rust
// L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` uses floor division:

```rust
// L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token where `origin_decimals > decimals` (e.g., 24 on NEAR, 18 on EVM — a 6-decimal gap, threshold = 1 000 000), any `amount_without_fee < 10^(origin_decimals − decimals)` truncates to zero. The `require!` panics every time `sign_transfer` is called for that transfer ID.

**No recovery path exists.** `sign_transfer_callback` only logs on success and provides no refund:

```rust
// L648-668
pub fn sign_transfer_callback(…) {
    if let Ok(signature) = call_result {
        if fee.is_zero() { self.remove_transfer_message(…); }
        env::log_str(…);
    }
    // no else branch, no refund, no unlock
}
```

No `cancel_transfer`, `unlock_tokens`, or user-accessible refund function exists in the contract for this scenario. The `normalize_amount` doc comment acknowledges "When fee = 0, dust stays locked/burned" but this refers to sub-unit remainders, not the case where the entire amount normalises to zero and `sign_transfer` is permanently bricked for that transfer.

## Impact Explanation

- **Bridge-deployed tokens:** burned in `init_transfer_internal` and permanently destroyed; the user loses the full transferred amount with no recovery.
- **Native tokens:** locked in `init_transfer_internal` and permanently frozen; `sign_transfer` always panics so the locked balance can never be released.

Both outcomes match the Critical allowed impact: *permanent freezing or loss of bridged funds across NEAR/EVM flows*.

## Likelihood Explanation

The condition is reachable by any unprivileged token holder who calls `ft_transfer_call` with an amount below the decimal-gap threshold. The `init_transfer` fee guard (`fee < amount`) explicitly permits `amount_without_fee = 1`, which normalises to 0 for any token with a 6+ decimal gap. The trusted relayer then calls `sign_transfer()` as part of normal protocol operation (not a privileged attack); the relayer is not acting maliciously and has no on-chain signal to skip the call. Any token registered with `origin_decimals > decimals` is permanently affected for any sub-threshold deposit.

## Recommendation

Move the `normalize_amount > 0` guard into `init_transfer` (or `init_transfer_internal`) **before** `burn_tokens_if_needed` / `lock_tokens_if_needed` are called. Concretely, after constructing `transfer_message` and resolving `token_address` and `decimals`, add:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the fix suggested in M-07 and ensures the transfer is rejected atomically before any irreversible state change.

## Proof of Concept

Given a token with `origin_decimals = 24`, `decimals = 18` (threshold = 1 000 000):

1. Alice calls `ft_transfer_call` on the token contract with `amount = 500_000`, `fee = 0`, targeting the bridge.
2. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`: 500 000 units are burned; `TransferMessage` is stored. Transaction succeeds.
3. Trusted relayer calls `sign_transfer(transfer_id, …)`:
   - `amount_without_fee = 500_000`
   - `normalize_amount(500_000, {origin:24, dest:18}) = 500_000 / 10^6 = 0`
   - `require!(0 > 0, …)` → **panic**
4. `sign_transfer` panics on every invocation. Alice's 500 000 units are permanently burned. The `TransferMessage` remains in `pending_transfers` forever with no callable exit path.

A local integration test using `near-workspaces-rs` can reproduce this by: deploying the bridge with a mock MPC signer, registering a token with `origin_decimals=24`/`decimals=18`, calling `ft_transfer_call` with `amount=500_000`, then asserting that `sign_transfer` panics and that the user's token balance is not restored.
