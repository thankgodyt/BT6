### Title
Missing `utxo_storage_key` in `VerifyDepositDetails` Event Allows Off-Chain Tools to Misidentify Which Deposit Was Verified - (File: contracts/satoshi-bridge/src/event.rs)

### Summary
The `VerifyDepositDetails` event omits the `utxo_storage_key` — the bridge's unique per-deposit identifier (`{tx_id}@{vout}`) — making it impossible for off-chain indexers or monitoring tools to unambiguously correlate the event to a specific deposit UTXO. When a user has two concurrent pending deposits of equal amount to the same recipient, an off-chain consumer of this event cannot determine which UTXO was actually verified and minted, mirroring the missing-nonce class of the reference report.

### Finding Description

Every deposit UTXO in the bridge is uniquely identified by its `utxo_storage_key`, computed as `{tx_id}@{vout}` and used as the primary key in `verified_deposit_utxo`, `refund_requests`, and `utxos`. [1](#0-0) 

After the light-client callback confirms inclusion, `mint_callback` emits `VerifyDepositDetails`: [2](#0-1) 

The same event is emitted in `safe_mint_callback` for safe-deposit paths: [3](#0-2) 

The event definition contains only `recipient_id`, `mint_amount`, `protocol_fee`, `relayer_fee`, and `success` — **no `utxo_storage_key`**: [4](#0-3) 

By contrast, every refund-lifecycle event correctly carries the `utxo_storage_key`: [5](#0-4) 

The deposit event is therefore the only lifecycle event that lacks the unique deposit identifier, creating an ambiguity gap for any off-chain consumer.

### Impact Explanation

An off-chain tool (indexer, monitoring system, or the protocol's own deposit-triage code) that relies on `VerifyDepositDetails` to track deposit state cannot distinguish between two deposits of equal `mint_amount` to the same `recipient_id`. Misidentification can cause the tool to:

1. Mark the wrong UTXO as "verified" in its local state, leaving the actually-verified UTXO treated as still-pending.
2. Attempt to submit a `request_refund` for the already-verified UTXO — which will revert on-chain (`"UTXO already verified via deposit"`), but the tool's state remains corrupted.
3. Fail to submit a `request_refund` for the genuinely unverified UTXO, leaving the user's deposited BTC permanently locked in the bridge with no refund path.

This constitutes a **Low** impact: a publicly reachable stuck-state in production bridge deposit paths without direct theft, matching the allowed scope.

### Likelihood Explanation

The condition requires a single user to have two concurrent pending deposits of identical satoshi value to the same `recipient_id`. This is realistic for any user who sends two equal-sized deposits before either is finalized (e.g., retrying a deposit they believe failed). The event is emitted on every successful deposit, so the surface is always reachable by any bridge user without any privileged access.

### Recommendation

**Short term:** Add `utxo_storage_key` to `VerifyDepositDetails` so every emission is unambiguously tied to a single deposit UTXO. Apply the same fix to `VerifyWithdrawDetails` (which similarly omits `tx_id`, the unique withdrawal identifier). [6](#0-5) 

**Long term:** Audit every bridge event to ensure each carries the minimal set of unique identifiers needed for off-chain consumers to reconstruct state without ambiguity, and document the expected event-to-state mapping for integrators.

### Proof of Concept

1. Alice sends two BTC deposits of exactly 0.01 BTC each to the same derived deposit address (same `recipient_id`, same `mint_amount` after fees).
2. Relayer calls `verify_deposit_v2` for deposit A (`tx_id=A`, `vout=0`). Light-client confirms; `mint_callback` fires, minting nBTC and emitting:
   ```json
   { "event": "verify_deposit_details", "data": [{ "recipient_id": "alice.near", "mint_amount": "990000", "success": true, ... }] }
   ```
   No `utxo_storage_key` is present.
3. An off-chain indexer, seeing only `recipient_id` and `mint_amount`, records deposit B as the verified one (arbitrary tie-breaking).
4. The indexer now believes deposit A is still unverified and submits `request_refund` for deposit A's `utxo_storage_key`. The call reverts: `"UTXO already verified via deposit"`.
5. The indexer, confused, does not submit `request_refund` for deposit B. Deposit B's 0.01 BTC remains locked in the bridge with no refund path and no minted nBTC — a permanent stuck-state for the user's funds.

The root cause is solely the missing `utxo_storage_key` field in `VerifyDepositDetails` at: [4](#0-3) 

emitted from: [2](#0-1) 

and: [3](#0-2)
