### Title
Peras Certificate Validation Bypass Allows Arbitrary Chain-Weight Injection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic checks. Any unprivileged peer can inject crafted certificates that assign a Peras weight boost to an arbitrary block, directly influencing chain selection in their favour.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate is stored and its weight boost applied to chain selection. The only concrete instance in production is the degenerate catch-all instance at line 320:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This function returns `Right` for every certificate regardless of its content. No checks are performed on:
- The aggregate BLS signature over the election identifier and boosted block
- Whether the claimed voters are legitimate committee members for the stated round
- Whether the round number is plausible given the current chain state
- Whether the boosted block actually exists on any known chain

The same degenerate instance also skips vote-signature verification in `validatePerasVote`:

```haskell
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

Only the voter ID's presence in the stake distribution is checked; the cryptographic signature on the vote is never verified.

These stub implementations are wired directly into the live certificate and vote diffusion paths. `processCerts` in the Peras certificate object pool calls `validatePerasCert mkPerasParams` as its sole validation gate before storing a certificate:

```haskell

``` [3](#0-2)

### Impact Explanation

Peras certificates provide a `perasWeight` boost to the block they reference during chain selection. A node that has accepted a fake certificate for block `B` will treat `B`'s chain as heavier than an equally-long honest chain that lacks such a certificate. Because `validatePerasCert` always returns `Right`, an attacker can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block on any fork.
2. Deliver it via the Peras certificate diffusion mini-protocol.
3. The certificate passes `processCerts` validation unconditionally and is stored.
4. Chain selection now applies the weight boost to the attacker's chosen block, potentially causing the honest node to prefer a non-canonical chain.

Similarly, because `validatePerasVote` does not verify vote signatures, an attacker who knows any legitimate voter ID (publicly visible in the stake distribution) can forge votes for that voter, accumulate a fake quorum, and trigger local certificate generation for an arbitrary target block — all without holding any private key.

This matches the **High** impact class: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only a network connection to a running node and knowledge of the Peras mini-protocol wire format. No stake, no private keys, and no privileged access are needed. The degenerate instance is the only instance in the codebase and is used unconditionally in both the `PerasCertDB`-backed and `ChainDB`-backed production writers.

---

### Recommendation

1. **`validatePerasCert`**: Implement full cryptographic validation — verify the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the public keys of the claimed voters, confirm each claimed voter is a legitimate committee member for the stated round, and check that the round number is within the expected window.

2. **`validatePerasVote`**: In addition to the stake-distribution lookup, verify the BLS vote signature over `(pvVoteRound, pvVoteBlock)` using the voter's public key retrieved from the committee.

3. Until real implementations are in place, the degenerate instance should reject all inbound certificates and votes (`Left PerasValidationErr`) rather than accept them, so that the stub cannot be exploited on any network where Peras diffusion is active.

---

### Proof of Concept

An attacker connects to a node via the Peras certificate diffusion mini-protocol and sends:

```
PerasCert
  { pcCertRound    = <any round number>
  , pcCertBoosted  = <slot and hash of attacker's preferred block>
  , pcVoters       = <any non-empty voter set>
  , pcSignature    = <zeroed / garbage BLS aggregate signature>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which executes:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [7](#0-6) 

The certificate is accepted, stored, and its `perasWeight` boost is applied to the attacker's chosen block in chain selection — with no signature ever verified and no committee membership ever checked.
