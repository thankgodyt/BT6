### Title
Missing Ownership Check in `withdraw_rbf` Allows Any Caller to Hijack Another User's Pending Withdrawal - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `withdraw_rbf` function, which is documented as a user-initiated operation to increase the gas fee on their own pending withdrawal, performs no check that `env::predecessor_account_id()` is the owner of the `original_btc_pending_verify_id` being modified. An unprivileged attacker can supply a victim's pending withdrawal ID and attacker-controlled `output` to create a new RBF `BTCPendingInfo` entry attributed to the attacker's account, disrupting the victim's withdrawal state.

### Finding Description
`withdraw_rbf` is a public, pausable function with no role restriction and no ownership assertion:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // attacker's account
    self.require_pending_sign_capacity(&account_id);  // capacity check only, not ownership

    self.withdraw_rbf_chain_specific(
        account_id,                          // attacker becomes owner of new RBF entry
        original_btc_pending_verify_id,      // victim's pending ID, unchecked
        output,                              // attacker-controlled outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

Every other mutating operation on a pending withdrawal that is not restricted to DAO/Operator explicitly derives the acting account from the stored `BTCPendingInfo.account_id`. For example, `cancel_withdraw` is gated to `Role::DAO` or `Role::Operator` and still reads the original owner from the stored record before acting: [2](#0-1) 

`withdraw_rbf` skips both the role gate and the ownership derivation. The `require_pending_sign_capacity` call only enforces that the *attacker's* account has room for another pending sign entry — it does not verify that the attacker owns `original_btc_pending_verify_id`. [1](#0-0) 

The `BTCPendingInfo` struct records the true owner in `account_id`: [3](#0-2) 

No code path between `withdraw_rbf` and `withdraw_rbf_chain_specific` compares `env::predecessor_account_id()` against `btc_pending_info.account_id`.

### Impact Explanation
The attacker-supplied `account_id` (their own) is passed as the owner of the newly created RBF `BTCPendingInfo`. The attacker also supplies the `output` vector, which defines the transaction outputs of the replacement transaction. Depending on the validation inside `withdraw_rbf_chain_specific`, this can range from:

- **Medium (confirmed):** The attacker creates a new RBF pending entry attributed to themselves for a victim's withdrawal, corrupting the victim's pending-sign accounting, consuming the victim's UTXO set in an attacker-controlled PSBT, and leaving the victim's original withdrawal in an indeterminate state — an attacker-triggered stuck/locked bridge state requiring operator intervention.
- **Critical (conditional):** If `withdraw_rbf_chain_specific` does not re-validate that the `target_btc_address` in the attacker-supplied `output` matches the original withdrawal destination, the attacker can redirect the victim's BTC to an address they control, constituting direct theft of user funds.

The minimum confirmed impact matches: **"Medium. Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds."**

### Likelihood Explanation
The function is fully public — no role, no relayer whitelist, no `assert_one_yocto`. Any NEAR account can call it at any time. The only prerequisite is knowing a valid `btc_pending_sign_id` in `PendingSign` stage, which is observable on-chain via `btc_pending_infos` events (`GenerateBtcPendingInfo`). [4](#0-3) 

### Recommendation
Add an ownership assertion immediately after loading the pending info, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(...) {
    let account_id = env::predecessor_account_id();
    let pending = self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
    require!(
        pending.account_id == account_id,
        "Only the withdrawal owner can submit an RBF"
    );
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept
1. Alice calls `ft_transfer_call` on the nBTC contract, triggering `ft_on_transfer` → `create_btc_pending_info`. A `BTCPendingInfo` entry is created with `account_id = alice`, `btc_pending_id = X`, and `target_btc_address = alice_btc_addr`. Event `GenerateBtcPendingInfo { btc_pending_id: X }` is emitted on-chain.
2. Attacker observes the event and learns `X`.
3. Attacker calls `withdraw_rbf(original_btc_pending_verify_id = X, output = [TxOut { value: ..., script_pubkey: attacker_btc_script }], ...)`.
4. Inside `withdraw_rbf`, `account_id = attacker`. No ownership check is performed. `withdraw_rbf_chain_specific(attacker, X, attacker_output, ...)` is called.
5. A new RBF `BTCPendingInfo` is created with `account_id = attacker` and the attacker-controlled `output`. Alice's original pending entry is linked to this RBF candidate.
6. Alice's withdrawal is now in a state she did not authorize, controlled by the attacker's account. At minimum, Alice's withdrawal is stuck. If output validation is absent, the replacement transaction pays the attacker's BTC address. [1](#0-0) [5](#0-4)
