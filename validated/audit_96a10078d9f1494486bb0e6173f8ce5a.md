### Title
`shelleyAfterVoting` Accumulates All Post-Deadline Blocks Instead of Only Stability-Window Blocks, Causing Premature Era Transition During Chain Growth Violation - (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `ShelleyTransition` counter `shelleyAfterVoting` is intended to count only the blocks that fall within the stability window immediately after the voting deadline (`[votingDeadline, votingDeadline + swindow)`). Instead, the implementation counts **all** blocks after `votingDeadline` with no upper-slot bound. This is the direct consensus analog of M-12: a "greater-than-or-equal" check gates entry, but the full uncapped value is used in the subsequent state accumulation rather than the bounded portion. The result is that the Hard Fork Combinator (HFC) can declare an era transition as "certain" and proceed to the next era even when the stability window after the voting deadline contains fewer than `k+1` blocks — the exact Chain Growth violation scenario in which the HFC is supposed to suppress the transition.

---

### Finding Description

`ShelleyTransition` is a `Word32` counter embedded in every `ShelleyLedgerState`. Its sole purpose is to let the HFC know when the last pre-deadline block is immutable (i.e., at least `k` blocks have been applied after the voting deadline), so that the era transition can be safely announced.

The counter is incremented in `applyHelper`:

```haskell
shelleyAfterVoting =
    -- We count the number of blocks that have been applied after the
    -- voting deadline has passed.
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

The condition is `blockSlot blk >= votingDeadline` — an unbounded `>=` check with no upper-slot ceiling. Every block in the epoch after the deadline increments the counter, including blocks in the second stability window `[votingDeadline + swindow, startOfNextEpoch)`.

The project's own documentation explicitly flags this as a bug:

> "(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)"

The correct condition should be `blockSlot blk >= votingDeadline && blockSlot blk < votingDeadline + swindow`, so that only the first `swindow` slots after the deadline contribute to the counter.

The `votingDeadline` is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
```

So the epoch has `10k/f` slots, the deadline is `6k/f` slots before the epoch end, and the stability window is `3k/f` slots. The bug causes blocks in the second `3k/f`-slot window (slots `[votingDeadline + swindow, startOfNextEpoch)`) to be counted, inflating `shelleyAfterVoting` beyond what the stability-window-only count would produce.

---

### Impact Explanation

The HFC's `singleEraTransition` for Shelley-based eras gates the era-transition announcement on `shelleyAfterVoting >= k`. When Chain Growth is violated specifically in the first stability window after the deadline (i.e., fewer than `k+1` blocks in `[votingDeadline, votingDeadline + swindow)`) but not in the full `6k/f`-slot post-deadline range, the inflated counter still reaches `k`. The HFC therefore:

1. Announces the era transition as certain and irreversible.
2. Transitions the node to the next era.
3. Begins applying next-era blocks and producing next-era time translations.

Meanwhile, the last pre-deadline block is still within the rollback window (fewer than `k` blocks have been applied after it in the stability window). A subsequent rollback that removes that block would leave the node in an incoherent ledger state: it has already committed to the next era, but the governance outcome that triggered the transition is no longer on the canonical chain. This breaks the `ImmutableTranslations` and `RollbackInsensitiveTranslations` invariants the HFC is designed to uphold, and can cause divergent era state between nodes that experienced the Chain Growth violation and those that did not — a cross-era consensus split.

**Impact category**: High — Hard-fork/era-transition mismatch that breaks cross-era consensus and ledger invariants for production Cardano nodes.

---

### Likelihood Explanation

Chain Growth violations in a single stability window (while the full post-deadline epoch window remains healthy) can occur during:

- Temporary network partitions that isolate a subset of stake pools for `3k/f` slots (~18 hours on mainnet) but resolve before the epoch ends.
- Coordinated but sub-majority stake-pool downtime in the relevant window.

These are rare but realistic operational events. No stake majority, key compromise, or privileged access is required to trigger the condition; it arises from natural network behaviour. Once triggered, the bug fires deterministically on every node that processes the affected chain, making the impact systemic rather than isolated.

---

### Recommendation

Cap the counter increment to the stability window:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline
          && blockSlot blk < votingDeadline + SlotNo swindow
       then succ
       else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

This ensures `shelleyAfterVoting` only counts blocks in `[votingDeadline, votingDeadline + swindow)`, matching the intended Iteration 4 semantics described in `civic_time.md`: suppress the era transition if and only if the stability window after the deadline contains fewer than `k+1` blocks.

**Scenario**: Suppose `k = 2160`, `swindow = 3k/f = 129600` slots. A network partition causes only 2000 blocks to appear in `[votingDeadline, votingDeadline + 129600)` (Chain Growth violation: fewer than `k+1 = 2161`). However, 161 additional blocks arrive in `[votingDeadline + 129600, startOfNextEpoch)` before the epoch ends. The buggy counter reaches `2000 + 161 = 2161 >= k`, so the HFC announces the era transition. The correct counter (stability-window-only) would read `2000 < 2161`, suppressing the transition. The node transitions to the next era while the last pre-deadline block remains rollback-eligible, breaking cross-era consensus invariants.
