Audit Report

## Title
ERC-1155 Tokens Permanently Locked When `initTransfer1155` Is Called Without Prior `logMetadata1155` Registration — (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`initTransfer1155` accepts and escrows ERC-1155 tokens without verifying that the token has been registered via `logMetadata1155`. When a relayer submits the resulting EVM proof to NEAR, `fin_transfer_callback` unconditionally panics with `BridgeError::TokenDecimalsNotFound` for the unregistered token. No EVM-side refund or rescue path exists, leaving the tokens locked in the bridge contract.

## Finding Description

`initTransfer1155` (lines 439–490 of `OmniBridge.sol`) computes a `deterministicToken` address, pulls ERC-1155 tokens from the caller via `safeTransferFrom`, and emits `InitTransfer` — all without checking whether `multiTokens[deterministicToken].tokenAddress` has been populated. [1](#0-0) 

`logMetadata1155` is the sole writer to `multiTokens[deterministicToken]`. [2](#0-1) 

On the NEAR side, `fin_transfer_callback` performs a hard `near_expect` on `token_decimals` for the token address carried in the proof. If the token was never registered, this panics unconditionally, reverting the NEAR transaction. [3](#0-2) 

No EVM-side rescue, refund, or emergency-withdrawal function exists in `OmniBridge.sol` — a grep for `rescue`, `refund`, `withdraw`, and `emergency` returns zero matches. [4](#0-3) 

## Impact Explanation

ERC-1155 tokens transferred via `initTransfer1155` without a preceding `logMetadata1155` are locked in the EVM bridge contract with no on-chain recovery path. The NEAR-side processing fails unconditionally. If the EVM light-client prover marks the receipt as consumed on the first failed attempt, the proof cannot be resubmitted even after the token is later registered, making the freeze permanent. This constitutes permanent freezing of bridged funds, matching the Critical allowed impact class. [5](#0-4) 

## Likelihood Explanation

`logMetadata1155` and `initTransfer1155` are separate, permissionless, externally callable functions with no enforced ordering. Any user or front-end that omits the registration step triggers this condition. The existing test suite itself calls `initTransfer1155` without a prior `logMetadata1155` and asserts success, confirming the path is reachable in practice. [6](#0-5) 

## Recommendation

Add a guard at the top of `initTransfer1155` that reverts if the token has not been registered:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
if (multiTokens[deterministicToken].tokenAddress == address(0)) {
    revert ERC1155NotRegistered();
}
```

This mirrors the consistency check already present in `logMetadata1155`. [7](#0-6) 

## Proof of Concept

1. Deploy `OmniBridge` and a standard ERC-1155 contract; mint tokens to `user` and approve the bridge.
2. Call `initTransfer1155(erc1155, tokenId, amount, 0, 0, "victim.near", "")` **without** calling `logMetadata1155` first. The call succeeds; tokens are now held by the bridge.
3. A relayer submits the EVM receipt proof to the NEAR bridge via `fin_transfer`.
4. NEAR's `fin_transfer_callback` panics at `self.token_decimals.get(&init_transfer.token).near_expect(BridgeError::TokenDecimalsNotFound)`.
5. The NEAR transaction reverts; the ERC-1155 tokens remain locked in the EVM bridge with no recovery path.
6. The existing test at line 191–194 of `OmniBridge1155.test.ts` already demonstrates step 2 succeeding without registration, confirming the precondition is trivially reachable. [6](#0-5) [3](#0-2)
