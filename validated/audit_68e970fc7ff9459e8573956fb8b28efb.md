### Title
`hashVoteSignature` Does Not Commit to a Network/Chain Identifier, Enabling Cross-Fork Peras Vote Replay — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

---

### Summary

`hashVoteSignature` in `Ouroboros.Consensus.Peras.Crypto.BLS` constructs the BLS-signed message for a Peras vote using only the round number, the boosted block's slot, and the boosted block's hash. No network magic, genesis hash, or epoch nonce is included. This is the direct analog of the external report's `hashAssignment()` omitting `address(this)` and `block.chainId`: a valid vote signature produced on one Cardano network (or one side of a chain fork) is cryptographically valid on any other network or fork where the same `(roundNo, boostedBlock)` tuple exists.

---

### Finding Description

`hashVoteSignature` is defined as:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
``` [1](#0-0) 

The signed payload is exactly 48 bytes: 8 bytes of round number, 8 bytes of boosted-block slot, 32 bytes of boosted-block hash. No network magic, no genesis hash, no epoch nonce, and no chain-specific context is mixed in.

This function is the sole input to both `signVote` and `verifyVoteSignature`:

```haskell
signVote sk roundNo boostedBlock =
  PerasBLSCryptoVoteSignature
    . BLS.signWithRole @SIGN sk
    $ hashVoteSignature roundNo boostedBlock

verifyVoteSignature pk roundNo boostedBlock (PerasBLSCryptoVoteSignature sig) =
  BLS.verifyWithRole @SIGN pk (hashVoteSignature roundNo boostedBlock) sig
``` [2](#0-1) 

The `PerasVote` structure carries additional fields — `pvSeatIndex` and `pvEligibilityProof` — that are transmitted over the wire but are **not** covered by the BLS signature:

```haskell
data PerasVote = PerasVote
  { pvRoundNo          :: !PerasRoundNo
  , pvBoostedBlock     :: !PerasBoostedBlock
  , pvSeatIndex        :: !PerasSeatIndex
  , pvEligibilityProof :: !PerasVoteEligibilityProof
  , pvSignature        :: !(VoteSignature PerasBLSCrypto)
  }
``` [3](#0-2) 

The companion `hashVRFInput` (used for non-persistent committee eligibility) does include the epoch nonce, but falls back to an empty contribution when the nonce is `NeutralNonce` (the first epoch):

```haskell
epochNonceBytes =
  case epochNonce of
    NeutralNonce -> mempty
    Nonce h -> BS.byteStringCopy (Hash.hashToBytes h)
``` [4](#0-3) 

So in the first epoch, even the VRF eligibility proof is network-agnostic.

---

### Impact Explanation

A BLS vote signature `sig = BLS.sign(SK_V, hashVoteSignature(R, B))` is valid on **every** network or chain fork where the same `(R, B)` pair is meaningful. The concrete attack path:

1. A chain fork occurs (e.g., a network partition, a testnet that shares genesis with mainnet, or a deliberate adversarial fork). Both sides share a common prefix of blocks with identical hashes.
2. A legitimate Peras committee member casts a vote for block `B` (in the shared prefix) during round `R` on fork A.
3. An unprivileged peer relays that vote verbatim to nodes on fork B.
4. On fork B, `verifyVoteSignature` passes — the BLS signature is over the same 48-byte hash — and the vote is accepted as valid.
5. If enough such votes are replayed (reaching quorum), a Peras certificate is forged on fork B for a block that was only legitimately voted for on fork A.
6. That certificate boosts fork B's chain-selection weight, causing honest nodes to prefer the wrong fork.

In the first epoch (`NeutralNonce`), the VRF eligibility proofs for non-persistent committee members are also replayable across forks, since `hashVRFInput` contributes zero bytes for the nonce. This means the full committee's votes — both persistent and non-persistent — can be replayed without any chain-specific binding.

The impact class is **Critical / High**: bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation by an unprivileged peer who merely relays intercepted vote messages.

---

### Likelihood Explanation

The attack is realistic in two scenarios:

- **Chain fork / network partition**: Both sides of a fork share a common block-hash prefix. Any vote cast for a block in that prefix before the fork is replayable on the other side. No key compromise is required; the attacker only needs to be a peer on both sides of the fork.
- **Testnet mirroring mainnet**: Cardano preview/preprod networks share genesis parameters and initial stake distributions with mainnet. In the first epoch (`NeutralNonce`), committee selection is identical across these networks, making votes fully replayable.

The attacker needs no special privileges — only the ability to observe votes on one network and relay them to another. Vote messages are propagated via the Peras miniprotocol to all connected peers.

---

### Recommendation

Include a chain-specific binding in `hashVoteSignature`. The epoch nonce (`η₀`) is already available at vote-signing time and is chain-specific after the first epoch. A genesis hash or network magic should also be mixed in to cover the first-epoch `NeutralNonce` case:

```haskell
hashVoteSignature networkMagic epochNonce roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (4 + 32 + 8 + 8 + 32)
    $ networkMagicBytes
      <> epochNonceBytes
      <> roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
```

This mirrors the fix applied in the external report (adding `metaHash`, `parentMetaHash`, `address(this)`, and `block.chainId` to the assignment hash) and is consistent with how `mkInputVRF` in Praos binds the VRF proof to the epoch nonce. [5](#0-4)

### Proof of Concept

```
Network A (mainnet, epoch 0, NeutralNonce):
  - Committee member V (BLS key SK_V / PK_V) is at seat index 5
  - V votes: pvRoundNo=1, pvBoostedBlock=B (slot=100, hash=0xABCD...)
  - sig = BLS.sign(SK_V, hashVoteSignature(1, B))
    = BLS.sign(SK_V, Hash(word64BE(1) || word64BE(100) || 0xABCD...))

Network B (preview, epoch 0, NeutralNonce, same genesis):
  - Same committee composition (same NeutralNonce + same initial stake)
  - V is also at seat index 5 with the same BLS key PK_V
  - Block B exists in the shared prefix (same hash 0xABCD...)
  - Attacker relays the vote to network B peers

  verifyVoteSignature PK_V 1 B sig
    = BLS.verify(PK_V, Hash(word64BE(1) || word64BE(100) || 0xABCD...), sig)
    = True  ✓  (identical hash, no network binding)

  → Vote is accepted on network B; if quorum is reached via replayed votes,
    a Peras certificate is forged, boosting block B on network B.
``` [1](#0-0) [3](#0-2)
