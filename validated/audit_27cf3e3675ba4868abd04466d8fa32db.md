Audit Report

## Title
Permanent Fund Loss via Decimal Normalization Truncation to Zero in `sign_transfer` - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`normalize_amount` uses floor division to convert a NEAR-native token amount to destination-chain precision. When `origin_decimals > decimals`, any transfer amount below the divisor threshold truncates to zero. Because tokens are irreversibly burned or locked inside `init_transfer_internal` before any relayer calls `sign_transfer`, and `sign_transfer` panics on a zero normalized amount with no cancel or refund path, the user's funds are permanently frozen.

## Finding Description

`normalize_amount` at `near/omni-bridge/src/lib.rs` L2784–2787 computes:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token where `origin_decimals > decimals`, amounts below `10^(origin_decimals - decimals)` floor-divide to zero.

`sign_transfer` (L447–521) is the only path to advance a NEAR-origin transfer. It calls `normalize_amount` at L475–480 and then enforces `require!(amount_to_transfer > 0, ...)` at L482–485. If the result is zero, the function panics.

This panic occurs **after** `init_transfer_internal` (L1829–1865) has already:
- Stored the transfer in `pending_transfers` via `add_transfer_message` (L1835)
- Issued a fire-and-forget `.detach()` burn call for bridge-deployed tokens (L1806–1812)
- Incremented the locked-token counter for native tokens (L1853–1857)

`init_transfer` itself only checks `fee.fee < amount` (L554–557); there is no pre-flight check that `normalize_amount(amount_without_fee, decimals) > 0`.

`remove_transfer_message` is only reachable via `sign_transfer_callback` (L657, on MPC success), `claim_fee_callback` (L1094, after proof verification), or `submit_transfer_to_utxo_chain_connector` (BTC path only). None of these are reachable when `sign_transfer` itself panics. There is no `cancel_transfer` or admin-recovery function anywhere in the contract.

## Impact Explanation

The user's tokens are permanently burned (bridge-deployed tokens) or permanently locked (native tokens) on NEAR. The transfer record remains in `pending_transfers` indefinitely. Every subsequent `sign_transfer` call for that transfer ID will always revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`. This constitutes **permanent freezing of bridged funds**, matching the allowed Critical impact: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation

The condition is reachable by any unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` → `init_transfer_internal` flow. No special role is required to initiate a transfer. The user does not need to call `sign_transfer` themselves (which is `#[trusted_relayer]`-gated); they only need to submit a transfer with an amount that normalizes to zero. A trusted relayer will then be permanently unable to sign it.

Concrete example: a token registered with `Decimals { decimals: 18, origin_decimals: 24 }` (divisor = 10^6). Any transfer of fewer than 1,000,000 base units (a plausible dust amount) triggers the loss. For tokens with `decimals: 6, origin_decimals: 24` (divisor = 10^18), the threshold is enormous and affects any transfer below 10^18 base units. The `init_transfer` entry point imposes no minimum-amount check relative to the normalization divisor.

## Recommendation

1. **Add a pre-flight check in `init_transfer`** (before `init_transfer_internal` is called) that verifies `normalize_amount(amount - fee, decimals) > 0`. Reject the transfer immediately and return the tokens to the user if this check fails. This requires looking up `token_decimals` at the `init_transfer` stage.
2. Alternatively, enforce a protocol-level minimum transfer amount of `10^(origin_decimals - decimals)` at the `ft_on_transfer` / `init_transfer` entry point.
3. Add a `cancel_transfer` escape hatch callable by the original sender for transfers stuck in `pending_transfers` with no valid signing path, which reverses the burn/lock and removes the pending record.

## Proof of Concept

**Setup**: Token registered with `Decimals { decimals: 18, origin_decimals: 24 }` (divisor = 1,000,000). Token is a bridge-deployed token (present in `deployed_tokens`).

**Step 1** — User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`:
- `ft_on_transfer` → `init_transfer` → `init_transfer_internal`
- `burn_tokens_if_needed` issues `.detach()` burn of 500,000 tokens — irreversible
- `lock_tokens_if_needed` increments locked counter by 500,000
- Transfer stored in `pending_transfers`; function returns `U128(0)` — success from user's perspective

**Step 2** — Trusted relayer calls `sign_transfer(transfer_id, ...)`:
- `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 })` = `500_000 / 1_000_000` = **0**
- `require!(0 > 0, ERR_INVALID_AMOUNT_TO_TRANSFER)` → **panics**

**Result**: 500,000 tokens are burned on NEAR. The transfer can never be signed. No refund mechanism exists. Funds are permanently lost.

**Unit test plan**: In `near/omni-bridge/src/tests/lib_test.rs`, add a test that registers a token with `decimals=18, origin_decimals=24`, calls `ft_on_transfer` with `amount=500_000`, asserts the transfer is stored in `pending_transfers`, then calls `sign_transfer` and asserts it panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, then asserts the transfer remains in `pending_transfers` with no recovery path.
