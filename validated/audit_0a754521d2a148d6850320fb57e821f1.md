### Title
`checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot` Instead of Actual Peras Weights, Causing Incorrect Peer Disconnection During Chain Selection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `ChainSync/Client.hs`, the function `checkPreferTheirsOverOurs` — which decides whether to disconnect from a peer whose candidate chain is beyond the forecast horizon — evaluates chain preference using a hardcoded `emptyPerasWeightSnapshot` (zero Peras certificate weights) instead of the actual live Peras weight snapshot. This is the direct analog of the DYAD bug: a guard condition checks the wrong "type" of value. When Peras is active and a candidate chain carries certificate boosts that make it the canonical chain despite being shorter in block count, the check incorrectly concludes the candidate is not preferred, disconnects from the honest peer, and the node fails to adopt the canonical chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked by the ChainSync client whenever a received header is beyond the forecast horizon. Its purpose is: if the candidate chain is not preferred over our current chain, disconnect immediately (we will never select it). If it is preferred, block and retry until our chain advances enough to forecast the header. [1](#0-0) 

The preference test is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← WRONG: always zero Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

`preferAnchoredCandidate` has two code paths depending on whether the weight snapshot is empty: [2](#0-1) 

- **Empty weights path** (triggered here): compares only `selectView` at the tip — i.e., pure block number. A shorter candidate chain is never preferred.
- **Non-empty weights path**: computes `weightedSelectView` over the suffix after the intersection, incorporating Peras certificate boosts. A shorter chain with sufficient certificate weight can be preferred.

Because `emptyPerasWeightSnapshot` is always passed, the non-empty path is never reached. The actual live Peras weight snapshot is maintained in the ChainDB and used correctly everywhere else in chain selection: [3](#0-2) [4](#0-3) 

The `emptyPerasWeightSnapshot` value is defined as a map with no entries: [5](#0-4) 

---

### Impact Explanation

When Peras is active and a peer's candidate chain is beyond the forecast horizon:

1. The candidate chain may be shorter in block count than our current chain but carry Peras certificate boosts that make it the canonical chain under the Peras-weighted chain order.
2. `checkPreferTheirsOverOurs` evaluates preference with zero weights, sees the candidate as shorter, concludes `ShouldNotSwitch`, and throws `CandidateTooSparse` — disconnecting from the peer.
3. The node never retries to adopt this chain. It remains on a less-preferred (non-canonical) chain.
4. An adversary holding a longer but unboosted chain can exploit this: by being the peer the node stays connected to, the adversary's chain is adopted while the honest peer offering the canonical Peras-boosted chain is disconnected.

This is a **High** chain-selection bug: an unprivileged peer interaction (crafted chain fragment beyond the forecast horizon) causes an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

Peras is implemented in production code paths (not test-only) and the weight infrastructure is already wired into `ChainDB`. The bug is triggered whenever:
- Peras certificates are being issued (Peras is active on the network), and
- A candidate chain is beyond the forecast horizon (a normal occurrence during syncing or after a large slot gap), and
- The canonical chain has Peras certificate boosts that make a shorter chain preferred.

The TODO comment at the call site (`TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers recognize this check is incorrect under Peras but have not yet resolved it.

---

### Recommendation

Pass the actual live Peras weight snapshot to `preferAnchoredCandidate` inside `checkPreferTheirsOverOurs`, consistent with how it is used in `chainSelection` and `constructPreferableCandidates`. The snapshot must be read from the ChainDB state (e.g., via `getPerasWeightSnapshot`) within the same STM transaction. If the check is to be removed entirely (as the TODO suggests), it should be removed before Peras is activated on any network where certificate boosts affect chain selection.

---

### Proof of Concept

Consider a private testnet with Peras active:

1. Node A holds chain `C_A` of length 100 with no Peras boosts.
2. Peer B offers chain `C_B` of length 98 but with Peras certificate boosts totalling weight > 2, making `C_B` the canonical chain under the Peras-weighted order.
3. `C_B`'s tip is beyond Node A's forecast horizon (e.g., due to a slot gap).
4. `checkPreferTheirsOverOurs` is called. With `emptyPerasWeightSnapshot`, it compares block numbers: 100 vs 98. `C_B` is not preferred. Node A throws `CandidateTooSparse` and disconnects from Peer B.
5. Node A remains on `C_A`, the non-canonical chain, violating Peras chain-selection safety. [6](#0-5)
