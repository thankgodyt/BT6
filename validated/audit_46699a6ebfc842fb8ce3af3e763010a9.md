Audit Report

## Title
3-arg `mint` in `HyperliquedBridgeToken` Silently Redirects All Bridged Tokens to `_systemAddress` on NEAR→HyperEVM Finalization with Non-Empty Message — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`OmniBridge.finTransfer` dispatches to the 3-arg `mint(address, uint256, bytes)` whenever `payload.message.length > 0` for any `isBridgeToken`-registered token. `HyperliquedBridgeToken` overrides this function to call `_mint(account, value)` immediately followed by `_update(account, _systemAddress, value)`, producing a net balance change of zero for the declared recipient. All minted tokens land at `_systemAddress`. The nonce is consumed and NEAR marks the transfer complete, leaving the recipient with a permanent total loss of bridged funds.

## Finding Description

**Root cause — semantic mismatch between `OmniBridge` dispatch and `HyperliquedBridgeToken` accounting model.**

`OmniBridge.finTransfer` selects the 3-arg mint path purely on `payload.message.length > 0`:

```solidity
// OmniBridge.sol L337-349
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(
            payload.recipient, payload.amount, payload.message
        );
    }
}
```

The nonce is consumed **before** the mint call at L287 (`completedTransfers[payload.destinationNonce] = true`).

`HyperliquedBridgeToken` overrides the 3-arg `mint` with HyperCore pool-parking logic:

```solidity
// HlBridgeToken.sol L76-83
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);              // account += value, totalSupply += value
    _update(account, _systemAddress, value); // account -= value, _systemAddress += value
}
```

Net effect on `account`: `+value − value = 0`. All tokens land at `_systemAddress`.

The NatSpec at L29-31 explicitly documents that the 3-arg path is intended **only** for HyperCore-bound minting (spot-balance tracking), not for regular HyperEVM recipient delivery. `OmniBridge` has no awareness of this semantic distinction and selects the path solely on `message.length`.

**Exploit path:**
1. `HyperliquedBridgeToken` is registered as `isBridgeToken[tokenAddress] = true` in `OmniBridge`.
2. A NEAR user initiates a transfer to a HyperEVM address with any non-empty `message` field (memo, routing hint, application data).
3. The MPC signs the full payload including `message` — a legitimate, valid signature.
4. The relayer calls `OmniBridge.finTransfer(sig, payload)`.
5. `completedTransfers[nonce]` is set to `true` (L287) — nonce consumed, no re-finalization possible.
6. `isBridgeToken` branch is entered; `message.length > 0` → 3-arg `mint` is called.
7. `HyperliquedBridgeToken.mint(recipient, amount, message)` executes: `_mint` then `_update` → `recipient.balanceOf == 0`, `_systemAddress.balanceOf += amount`.
8. NEAR has already locked/burned origin tokens. No refund path exists.

**Existing checks are insufficient:** The MPC signature check (L311) validates the payload as legitimate — it does not guard against semantic misrouting. The `onlyOwner` modifier on `mint` is satisfied because `OmniBridge` is the owner. No other guard exists.

## Impact Explanation

Permanent, total loss of bridged funds for any NEAR→HyperEVM transfer involving a `HyperliquedBridgeToken` where the user attaches a non-empty `message`. The recipient receives zero tokens. The `_systemAddress` accrues the full amount. The nonce is irrevocably consumed. NEAR considers the transfer finalized. This is a concrete instance of **permanent loss/freezing of bridged funds** — a Critical allowed impact under the NEAR Omni Bridge scope.

## Likelihood Explanation

No special attacker capability is required. The `message` field is a standard, user-controlled field in the NEAR bridge transfer flow. Any legitimate user who attaches a memo, routing hint, or application-layer payload to a NEAR→HyperEVM transfer triggers this path. The MPC signature covers the full payload and is valid; no signature bypass is needed. The relayer submits the finalization in the normal flow. A malicious actor can also deliberately trigger this against any victim by front-running or by being the originating NEAR sender. The condition is trivially satisfiable.

## Recommendation

The 3-arg `mint` in `HyperliquedBridgeToken` must not redirect tokens to `_systemAddress` when called from `OmniBridge.finTransfer`. Two concrete fixes:

1. **Override `mint(address, uint256, bytes)` in `HyperliquedBridgeToken` to behave identically to the 2-arg version** — i.e., call only `_mint(account, value)` without the subsequent `_update`. The HyperCore pool-parking logic belongs exclusively in `coreReceiveWithData`, not in the NEAR→EVM finalization path.

2. **Alternatively**, add a token-type check in `OmniBridge.finTransfer` so that tokens implementing the HyperLiquid accounting model always use the 2-arg mint during `finTransfer`, regardless of `message.length`.

//    so that isBridgeToken[token] == true and OmniBridge is the owner.

// 3. MPC signs the payload (legitimate signature, message field included).
// 4. Relayer calls OmniBridge.finTransfer(sig, payload) where payload.message = "hello".
// 5. completedTransfers[nonce] = true  (L287, before mint)
// 6. isBridgeToken branch entered; message.length > 0 → 3-arg mint called.
// 7. HyperliquedBridgeToken.mint(freshEOA, amount, "hello"):
//      _mint(freshEOA, amount)              → freshEOA.balance = amount
//      _update(freshEOA, _systemAddress, amount) → freshEOA.balance = 0
// Assert: token.balanceOf(freshEOA) == 0                  ✓
// Assert: token.balanceOf(_systemAddress) == amount        ✓
