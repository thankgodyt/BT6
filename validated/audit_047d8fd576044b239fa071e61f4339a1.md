### Title
Unguarded `new()` Initializer Allows Frontrun Takeover of `nbtc` Token Contract, Enabling Unauthorized Minting — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `nbtc` token contract's `new()` initializer imposes no caller restriction. Any account can call it before the legitimate deployer does. If an attacker frontruns this call and supplies their own account as `bridge_id`, they gain the sole authority to call `mint()` and `safe_mint()`, enabling unlimited unauthorized minting of nBTC. The same pattern exists in `satoshi-bridge`'s `new()`, where the caller is unconditionally granted the DAO super-admin role.

---

### Finding Description

In NEAR, deploying a contract and initializing it are two separate on-chain actions. Unless the deployer uses a single atomic batch transaction (`DeployContract` + `FunctionCall` in one batch), there is a window between the moment the contract bytecode is live and the moment `new()` is called. During this window, any NEAR account can call `new()` on the freshly deployed contract.

The `nbtc` contract's initializer is:

```rust
// contracts/nbtc/src/lib.rs:58-91
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    ...
    contract.token.internal_register_account(&contract.bridge_id);
    contract
}
```

The only guard is `require!(!env::state_exists())`. There is no check that `env::predecessor_account_id()` equals the contract account or any trusted deployer. An attacker who calls `new()` first wins: they set `bridge_id` to their own account and `controller` to their own account.

The `mint()` and `safe_mint()` functions gate access exclusively on `self.assert_bridge()`, which resolves to `env::predecessor_account_id() == self.bridge_id`. With `bridge_id` under attacker control, the attacker can mint arbitrary amounts of nBTC to any registered account.

The same structural issue exists in `satoshi-bridge`:

```rust
// contracts/satoshi-bridge/src/lib.rs:182-230
#[init]
pub fn new(config: Config) -> Self {
    ...
    contract.acl_init_super_admin(env::predecessor_account_id());
    contract.acl_grant_role(Role::DAO.into(), env::predecessor_account_id());
    ...
}
```

Whoever calls `new()` first becomes the DAO super-admin with full control over the bridge.

---

### Impact Explanation

**Critical — Unauthorized minting of nBTC.**

If an attacker frontruns `new()` on the `nbtc` contract:

1. They set `bridge_id = attacker_account`.
2. They call `mint(victim_account, U128(MAX), ...)` — `assert_bridge()` passes because `predecessor == bridge_id == attacker`.
3. Unlimited nBTC is minted, unbacked by any real BTC deposit.
4. The legitimate deployer's subsequent `new()` call fails with "Already initialized", leaving the attacker in permanent control.

Recovery requires the deployer to use a full-access key on the contract account to forcibly overwrite storage — a complex, non-atomic remediation that itself may be raced.

---

### Likelihood Explanation

NEAR does not expose a traditional public mempool, which reduces but does not eliminate frontrunning risk. The attack window exists whenever the deployer submits `DeployContract` and `FunctionCall("new")` as two separate transactions rather than one atomic batch. A validator node, a co-located observer, or any party who monitors the chain for new contract deployments can submit a competing `new()` call in the same or the immediately following block. The test harness itself demonstrates the two-step pattern (deploy then call `new()` separately), suggesting the production deployment may follow the same flow.

---

### Recommendation

Ensure that contract deployment and initialization are performed atomically in a single NEAR batch transaction:

```
batch(contract_account_id)
  .deploy(wasm_bytes)
  .call(Function::new("new").args_json(init_args))
  .transact()
```

Alternatively, add a caller restriction inside `new()`:

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

This mirrors the fix described in the external report: moving initialization logic into the constructor (here, the atomic batch) so no separate, race-able transaction is needed.

---

### Proof of Concept

1. Deployer submits `DeployContract` for `nbtc` in transaction T1 (block N).
2. Attacker observes T1 on-chain and submits in block N+1:
   ```
   nbtc_contract.call("new")
     .args_json(json!({
       "controller": attacker.id(),
       "bridge_id": attacker.id(),
       "name": "nBTC", "symbol": "nBTC",
       "icon": null, "decimals": 8
     }))
     .transact()
   ```
3. Attacker's `new()` is processed first; state is written with `bridge_id = attacker`.
4. Deployer's `new()` call fails: `"Already initialized"`.
5. Attacker registers a victim account via `storage_deposit`, then calls:
   ```
   attacker_account.call(nbtc_contract.id(), "mint")
     .args_json(json!({
       "mint_account_id": victim.id(),
       "mint_amount": "1000000000000",
       "protocol_fee": "0",
       "relayer_account_id": attacker.id(),
       "relayer_fee": "0",
       "post_actions": null
     }))
     .transact()
   ```
6. `assert_bridge()` passes (`predecessor == attacker == bridge_id`); nBTC is minted with no BTC backing.
