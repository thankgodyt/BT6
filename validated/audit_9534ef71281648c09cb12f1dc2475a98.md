### Title
`sign_btc_transaction_callback` MPC Failure Leaves Withdrawal Permanently Stuck in `PendingSign` with No Operator Cleanup Path — (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

When the MPC signing call fails inside `sign_btc_transaction_callback`, the callback silently returns `false` without removing the pending-sign entry from the account or from `btc_pending_infos`. The withdrawal remains in `PendingSign` stage indefinitely. Because the default per-user pending-sign limit is 1, the user's slot is permanently occupied and they cannot initiate any new withdrawal. No operator-accessible function exists to clean up an *original* withdrawal transaction stuck in `PendingSign`, so the user's locked nBTC and their withdrawal capacity can only be recovered through DAO-level intervention.

---

### Finding Description

**Root cause — `sign_btc_transaction_callback` silent no-op on failure**

```
contracts/satoshi-bridge/src/chain_signature.rs  lines 134–213
```

The callback's failure branch is:

```rust
} else {
    false   // MPC signing failed — nothing is cleaned up
}
```

On success the callback removes the pending ID from `account.btc_pending_sign_ids` and transitions the pending info to `PendingVerify`. On failure it does neither. The pending info stays in `PendingSign` stage and the account's `btc_pending_sign_ids` set still contains the ID.

**Capacity gate — `require_pending_sign_capacity`**

```
contracts/satoshi-bridge/src/account.rs  lines 113–123
```

```rust
pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
    require!(
        self.get_account(account_id)
            ...
            .pending_sign_count()
            < self.get_max_pending_sign_txs(account_id),
        "Too many pending sign transactions"
    );
}
```

`get_max_pending_sign_txs` defaults to **1** for every account that has not been explicitly granted a higher limit.

```
contracts/satoshi-bridge/src/account.rs  lines 105–111
```

```rust
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)   // default = 1
}
```

`pending_sign_count()` counts the length of `btc_pending_sign_ids`. Because the failed callback never removes the ID, the count stays at 1 and every subsequent call to `create_btc_pending_info` or `finalize_refund_with_psbt` panics with "Too many pending sign transactions".

**No operator cleanup path for original withdrawals in `PendingSign`**

Every existing cleanup function is scoped to a different state or transaction type:

| Function | Restriction |
|---|---|
| `cancel_withdraw` | Requires `WithdrawOriginal / PendingVerify` stage |
| `withdraw_rbf` | Requires `WithdrawOriginal / PendingVerify` stage |
| `clear_invalid_pending_verify_rbf` | Only removes RBF-variant pending infos |
| `remove_refund_pending_tx_id` | Only removes `Refund`-state pending infos |

```
contracts/satoshi-bridge/src/api/bridge.rs  lines 285–298, 430–446, 614–626
```

An original withdrawal stuck in `PendingSign` cannot be cancelled, RBF'd, or administratively removed by any currently deployed function. The only recovery paths are:

1. MPC eventually succeeds on a retry of `sign_btc_transaction`.
2. DAO raises the per-user limit via `set_pending_tx_limit` (unblocks new withdrawals but does not recover the locked nBTC or the stuck pending info).
3. A contract upgrade adds a new cleanup function.

---

### Impact Explanation

When MPC signing fails and does not recover:

* The user's nBTC transferred to the bridge via `ft_transfer_call` remains locked in the bridge contract with no refund path.
* The user's pending-sign slot (capacity 1 by default) is permanently occupied, blocking all future withdrawals.
* The stuck `BTCPendingInfo` entry and the stale `btc_pending_sign_ids` entry accumulate in contract storage.
* Recovery requires privileged DAO action (limit increase or contract upgrade), matching the "stuck bridge state requiring operator intervention" medium-impact category.

---

### Likelihood Explanation

MPC signing failures are a realistic operational event: the NEAR Chain Signatures network can return an error due to network partitions, key-version mismatches, gas exhaustion in the MPC contract, or transient infrastructure faults. Any such failure on the first (or any intermediate) input of a multi-input PSBT triggers this path. Because the default limit is 1, a single failed signing call is sufficient to permanently block a user's withdrawal capacity.

---

### Recommendation

1. **Add a cleanup function** for original withdrawal transactions stuck in `PendingSign`. It should verify the pending info is in `PendingSign` stage, remove it from `btc_pending_infos` and from `account.btc_pending_sign_ids`, and return the locked nBTC to the user (or route it to `lost_found`). Access should be restricted to `Role::DAO` or `Role::Operator`.

2. **Alternatively**, make `sign_btc_transaction_callback` handle the failure case explicitly: on MPC failure, remove the pending info and refund the nBTC, analogous to how `cancel_withdraw` returns funds via `lost_found`.

3. **Emit an event** on MPC signing failure so off-chain monitors can detect stuck withdrawals promptly.

### Proof of Concept

```
1. Alice calls ft_transfer_call(bridge, 100_000, Withdraw{...})
   → ft_on_transfer → create_btc_pending_info
   → alice.btc_pending_sign_ids = {"pending_id_A"}
   → alice.pending_sign_count() = 1  (== limit)

2. Alice calls sign_btc_transaction("pending_id_A", 0, 0)
   → internal_sign_btc_transaction → sign_promise(MPC)
   → MPC call fails (network error / gas / version mismatch)
   → sign_btc_transaction_callback returns false
   → NO cleanup: btc_pending_sign_ids still = {"pending_id_A"}

3. Alice calls ft_transfer_call(bridge, 50_000, Withdraw{...})
   → ft_on_transfer → create_btc_pending_info
   → require_pending_sign_capacity panics:
      "Too many pending sign transactions"
   → nBTC from step 1 remains locked; new withdrawal rejected.

4. Operator calls cancel_withdraw("pending_id_A", ...)
   → assert_withdraw_original_pending_verify_tx() panics:
      pending info is PendingSign, not PendingVerify
   → no recovery possible without DAO intervention.
```
