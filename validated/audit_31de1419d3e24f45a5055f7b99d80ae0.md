Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Message Account Pre-funding — (`near/omni-bridge/src/lib.rs`)

## Summary
The `NativeFeeRestricted` role check in `init_transfer` is placed exclusively inside the right-hand operand of a short-circuit `||` expression. A restricted account can pre-fund the deterministically-derived message account, causing the left-hand branch to return `Ok` and the role check to be silently skipped. A second bypass exists in `init_transfer_resume`, which contains no `NativeFeeRestricted` check at all, allowing the yield path to also be exploited.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` evaluates the following condition at lines 566–584:

```rust
if self
    .try_to_transfer_balance_from_message_account(
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()                                          // branch A
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
                                                      // branch B — only location of the check
```

`try_to_transfer_balance_from_message_account` (defined in `near/omni-bridge/src/storage.rs` at lines 260–290) returns `Ok(())` when the message account exists and holds sufficient balance to cover both storage and the native fee. Because Rust's `||` short-circuits, if branch A succeeds, branch B — and therefore the `acl_has_role(NativeFeeRestricted)` check — is never evaluated.

The message account ID is computed deterministically via `transfer_message.calculate_storage_account_id(...)` at line 562–563, so any caller can derive it off-chain before submitting the transfer. A `NativeFeeRestricted` account can call `storage_deposit` on the bridge for that account ID, depositing enough to cover storage plus the desired `native_token_fee`, then call `ft_transfer_call` with `native_token_fee > 0`. Branch A succeeds, `init_transfer_internal` is called, and the transfer is registered with the non-zero native fee.

The second bypass path is `init_transfer_resume` (lines 621–646). This callback is invoked when the yield path fires. It calls `try_to_transfer_balance_from_message_account` and, if that succeeds, calls `init_transfer_internal` unconditionally — with no `NativeFeeRestricted` check anywhere in the function. A restricted account can trigger the yield path (by not pre-funding initially), then fund the message account, and `init_transfer_resume` will proceed with `native_token_fee > 0` without any role enforcement.

The existing test in `near/omni-tests/src/native_fee_role.rs` (`test_native_fee_restriction`) only exercises the branch-B path (signer's own storage balance) and does not cover the message-account pre-funding path, so the bypass is not caught by the current test suite.

## Impact Explanation
This is a concrete role bypass matching the allowed critical impact: "role bypass that lets an attacker execute bridge actions that the protocol explicitly prohibits for that account class." The `NativeFeeRestricted` role is a bridge-level access control mechanism whose sole purpose is to prevent designated accounts from attaching a non-zero `native_token_fee` to outbound bridge transfers. The bypass renders this control completely ineffective, allowing a restricted account to register bridge transfers with arbitrary native fees, which are then paid to relayers upon `sign_transfer`.

## Likelihood Explanation
The bypass requires no privileged access and no victim interaction. The message account address is fully deterministic and computable off-chain from the transfer parameters. The attacker needs only two transactions: a `storage_deposit` for the message account and a `ft_transfer_call` with `native_token_fee > 0`. Any account that has been granted `NativeFeeRestricted` and is aware of this code path can exploit it immediately and repeatedly.

## Recommendation
Move the `NativeFeeRestricted` check to the top of `init_transfer`, before the branch-A / branch-B split, so it gates the entire function unconditionally:

```rust
require!(
    init_transfer_msg.native_token_fee.0 == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
    BridgeError::NativeFeeRestricted.as_ref()
);
```

Apply the same guard at the start of `init_transfer_resume`, using `storage_owner` as the signer identity and `transfer_message.fee.native_fee.0` as the fee value, before calling `try_to_transfer_balance_from_message_account`.

## Proof of Concept
1. Admin grants `NativeFeeRestricted` to `alice.near`.
2. `alice.near` computes `message_storage_account_id` deterministically from the intended transfer parameters (token, recipient, nonce, etc.) using the same logic as `calculate_storage_account_id`.
3. `alice.near` calls `storage_deposit` on the bridge contract specifying `account_id = message_storage_account_id`, depositing enough to cover `required_storage_balance + native_token_fee` (e.g., storage cost + 1 NEAR).
4. `alice.near` calls `ft_transfer_call` on the token contract targeting the bridge, with `msg` containing `native_token_fee = 1 NEAR`.
5. Inside `init_transfer`, `try_to_transfer_balance_from_message_account` finds the pre-funded message account with sufficient balance and returns `Ok(())`.
6. The `||` short-circuits; `acl_has_role(NativeFeeRestricted)` at line 580 is never reached.
7. `init_transfer_internal` is called and the transfer is stored with `native_fee = 1 NEAR`.
8. A relayer calls `sign_transfer`; the MPC signature is produced over a payload that includes the fee, and the relayer collects 1 NEAR upon finalization — a bridge action the protocol explicitly prohibited for `alice.near`.
