### Title
BLS `KeyScope` Domain Separator Not Bound to Network Identity, Enabling Cross-Network Peras Vote Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/Crypto/BLS.hs`)

### Summary

The `KeyScope` type in the BLS committee crypto module is the direct analog of EIP712's `verifyingContract` field. It is designed to provide domain separation for all Peras BLS vote signatures, VRF outputs, and proofs of possession. However, the scope is a caller-supplied runtime `ByteString` that is **not stored in the serialized key format** and is **never validated against the expected network identifier** during verification. If the scope is absent, empty, or inconsistent across deployments, a valid Peras vote or VRF eligibility proof produced on one network (e.g., preprod) is cryptographically indistinguishable from one on another (e.g., mainnet), enabling cross-network vote replay that bypasses Peras certificate verification.

### Finding Description

`KeyScope` is defined as a plain `ByteString` with the comment: *"Key scope, later instantiated with usage and network id (e.g. PERAS/MAINNET)"*. [1](#0-0) 

The scope is embedded into the BLS signing context augmentation string for all three key roles: [2](#0-1) 

Signing uses `privateKeyScope sk` and verification uses `publicKeyScope pk` — whatever was stored in the key at deserialization time: [3](#0-2) 

**Critical structural flaw**: `rawSerialisePublicKey` serializes only the raw elliptic-curve key bytes — the scope is **not** included in the wire format: [4](#0-3) 

Consequently, `rawDeserialisePublicKey` requires the caller to supply the scope as an external parameter: [5](#0-4) 

There is no code in the production `PerasBLSCrypto` module that sets or validates the scope against the expected network identifier. The module defines `PerasPrivateKey` and `PerasPublicKey` containing `BLS.PrivateKey SIGN`, `BLS.PrivateKey VRF`, `BLS.PublicKey SIGN`, and `BLS.PublicKey VRF`, but assigns no scope: [6](#0-5) 

The `signVote` and `verifyVoteSignature` implementations delegate entirely to `BLS.signWithRole` / `BLS.verifyWithRole`, which use whatever scope is embedded in the key: [7](#0-6) 

The same pattern applies to VRF evaluation and batch VRF verification: [8](#0-7) 

The `coercePrivateKey` / `coercePublicKey` helpers use `coerce`, which silently propagates whatever scope was set at deserialization time across key-role boundaries: [9](#0-8) 

### Impact Explanation

If the scope is set to an empty string, a generic placeholder, or any value that is identical across multiple Cardano networks (mainnet, preprod, preview), then:

1. **Cross-network vote replay**: A Peras vote or VRF eligibility proof signed by a committee member on preprod is a valid BLS signature under the same signing context as mainnet. An unprivileged peer that receives such a vote can relay it verbatim to a mainnet node. The `verifyVoteSignature` / `verifyAggregateVoteSignature` / `batchVerifyVRFOutputs` checks will all pass, because the signing context augmentation string is identical on both networks.

2. **Peras certificate forgery**: A quorum of preprod votes for a preprod block hash could be assembled into a certificate and submitted to a mainnet node. If the boosted block hash happens to collide with a mainnet block (or if the attacker controls the preprod chain), the certificate passes all cryptographic checks and the mainnet node incorrectly boosts a non-canonical chain.

3. **VRF eligibility bypass**: A non-persistent committee member's VRF output from preprod, signed under the same scope, passes `evalVRF` verification on mainnet, granting the member seats they are not entitled to on mainnet.

This directly maps to the "Bypass of Peras voting or certificate checks" impact category.

### Likelihood Explanation

The phrase *"later instantiated with usage and network id (e.g. PERAS/MAINNET)"* in the source comment is a design note indicating the scope is not yet hardcoded. The only concrete instantiation visible in the codebase is the test harness, which uses the literal string `"TEST"`: [10](#0-9) 

No production call site sets the scope to a network-specific value. If the production key-loading code supplies an empty scope or a shared placeholder, all nodes on all networks will use the same signing context, making cross-network replay trivially possible for any peer that participates in Peras on a test network and also connects to mainnet.

### Recommendation

1. **Hardcode the network-specific scope** as a compile-time or protocol-level constant rather than a caller-supplied runtime parameter. For example, define `perasMainnetScope :: KeyScope = "PERAS/MAINNET"` and use it unconditionally in `PerasBLSCrypto`.
2. **Include the scope in the serialized key format** so that a key deserialized from the ledger carries its own scope, and the verifier can reject keys whose scope does not match the expected network identifier.
3. **Add a scope-validation step** in `verifyWithRole` (or in the committee verification layer) that asserts `publicKeyScope pk == expectedScope` before proceeding with cryptographic verification.
4. **Mirror the fix from the referenced report**: just as the EIP712 fix replaced a mutable, caller-supplied address with the immutable `address(this)`, replace the mutable `KeyScope` parameter with an immutable, protocol-level network identifier.

### Proof of Concept

```
Attacker setup (preprod):
  1. Register a BLS SIGN key with scope "" (empty, or whatever the production
     deserialization code supplies) on preprod.
  2. Participate in a Peras election on preprod for round R, boosted block B_preprod.
  3. Collect a quorum of votes: each vote is
       sig_i = BLS.signWithRole @SIGN sk_i (hashVoteSignature R B_preprod)
     under context "VOTE::V0" (empty scope).

Replay on mainnet:
  4. Submit the same votes to a mainnet node.
  5. The mainnet node loads the public keys from the ledger with scope ""
     (same empty scope, because the scope is not stored on-chain).
  6. verifyVoteSignature calls BLS.verifyWithRole @SIGN pk_i
       (hashVoteSignature R B_preprod) sig_i
     under context "VOTE::V0" — identical to the signing context.
  7. Verification succeeds. The mainnet node accepts the certificate for
     a block that does not exist on mainnet, corrupting its Peras weight
     snapshot and chain-selection state.
```

The root cause is the absence of any network-binding in the BLS signing context, directly analogous to the `verifyingContract` misconfiguration in the referenced EIP712 report.
