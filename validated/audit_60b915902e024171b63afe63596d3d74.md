### Title
Unconditional `validatePerasCert` Acceptance Enables Unauthorized Certificate-Driven Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) without performing any validation. This is the function called on every inbound Peras certificate received from a peer via the object-diffusion mini-protocol. Because no cryptographic, structural, or quorum check is applied, any unprivileged peer can send a crafted `PerasCert` that boosts an arbitrary block, causing the receiving node to apply a weight boost to that block during chain selection and potentially switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate that must be passed before a certificate is stored and its weight boost applied to chain selection. The production instance (the only instance, used for all block types) is:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function is wired directly into the production inbound-certificate pipeline via `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this function on every certificate received from a peer and, if it returns `Right`, immediately timestamps and stores the certificate:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted.

Once stored, `chainSelSync` processes the certificate: it adds it to the `PerasCertDB`, reads the updated `PerasWeightSnapshot`, and triggers `chainSelectionForBlock` for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection then compares fragments using `WeightedSelectView`, where `wsvTotalWeight = blockNo + weightBoost`. A certificate contributes `perasWeight params = PerasWeight 15` to the boosted block's chain:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
``` [5](#0-4) 

The `PerasCertDB` stores at most one certificate per round number, but there are many rounds, so an attacker can inject one certificate per round, each adding 15 weight units to an arbitrary block on an adversarial fork.

The analog to the Zap.sol bug is exact: just as `outAmount` was computed and used without being checked against `minOut`, here the certificate content is accepted and its weight boost applied without being checked against any validity criterion (quorum proof, cryptographic signature, round validity, or boosted-block existence on the honest chain).

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

When Peras is enabled, an attacker controlling any peer connection can:

1. Craft a `PerasCert` with `pcCertRound = r` and `pcCertBoostedBlock = <adversarial fork block>`.
2. Send it via the object-diffusion mini-protocol.
3. `validatePerasCert` returns `Right` unconditionally; the cert is stored.
4. `chainSelSync` triggers chain selection for the boosted block.
5. The adversarial fork's `wsvTotalWeight` is inflated by `PerasWeight 15` per injected certificate.
6. If the adversarial fork is within `k` blocks of the current tip and the weight boost overcomes the honest chain's block-count lead, the node switches to the adversarial fork.

Multiple certificates across multiple rounds can accumulate enough weight to cause the node to permanently prefer a non-canonical chain, violating the chain-selection safety guarantee.

---

### Likelihood Explanation

**High.** The entry path requires only a peer connection — no keys, no stake, no privileged access. The `validatePerasCert` function is not partially implemented; it is a complete no-op that always succeeds. Any peer that can reach the object-diffusion endpoint can exploit this. The only limiting factor is that Peras must be enabled by the operator, but the code is present in production files and the pipeline is fully wired.

---

### Recommendation

Implement the actual certificate validation in `validatePerasCert`. At minimum, the function must verify:

1. **Quorum proof**: the certificate must carry a proof that a quorum of eligible voters (above `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`) signed the boosted block for the claimed round.
2. **Cryptographic signatures**: each voter's signature must be verified against the registered stake-pool VRF/KES key.
3. **Round validity**: `pcCertRound` must correspond to a valid Peras round relative to the current ledger state.
4. **Boosted block age**: `pcCertBoostedBlock` must satisfy `perasBlockMinSlots` and `perasCertMaxRounds` constraints.

Until this is implemented, the `validatePerasCert` stub must not be reachable from any peer-facing code path. The `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` functions should not be wired to the stub implementation in any configuration where Peras is enabled.

---

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight
-- could be cached, but then we need to be careful to maintain the invariant
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker
      ]

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of
        ShouldSwitch r -> ShouldSwitch (WeightedSelectViewTiebreak r)
        ShouldNotSwitch o -> ShouldNotSwitch o
      GT -> ShouldNotSwitch GT
