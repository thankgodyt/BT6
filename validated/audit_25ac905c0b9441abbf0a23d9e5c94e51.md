### Title
Attacker Can Frontrun `request_refund` to Redirect Victim's BTC to Attacker-Controlled Address — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `request_refund` function is publicly callable by any NEAR account and uses a first-write-wins pattern keyed on `utxo_storage_key`. When a victim's `deposit_msg` has `refund_address: None`, any caller may supply an arbitrary `refund_address`. An attacker who submits a refund request before the legitimate user locks in the attacker's address for the entire 14-day `unsafe_refund_timelock_sec` window. The victim is then blocked from submitting their own request, and after the timelock the attacker can call `execute_refund` to redirect the victim's BTC to the attacker's wallet.

---

### Finding Description

`request_refund` is a public, payable function with no caller restriction beyond a small NEAR storage deposit: [1](#0-0) 

When `deposit_msg.refund_address` is `None`, the only validation on the caller-supplied `refund_address` is that it is a parseable Bitcoin address. There is no check that the caller is the original depositor: [2](#0-1) 

The callback enforces a strict first-write-wins rule: once a refund request exists for a `utxo_storage_key`, all subsequent `request_refund` calls for the same UTXO are rejected: [3](#0-2) 

The stored `refund_address` is then used verbatim when `execute_refund` is called after the timelock: [4](#0-3) 

The `unsafe_refund_timelock_sec` (default 14 days) is applied to all requests where `deposit_msg.refund_address` was `None`, giving the DAO/Operator a window to reject suspicious requests — but this is a trusted, manual intervention, not a trustless protection: [5](#0-4) 

The only permissionless rejection path requires the UTXO to already be verified via `verify_deposit`, which is precisely the condition that does not hold when a refund is needed: [6](#0-5) 

---

### Impact Explanation

An attacker who successfully frontruns the victim's `request_refund` call locks in the attacker's Bitcoin address as the refund destination. After the 14-day timelock, `execute_refund` is callable by anyone and routes the victim's BTC to the attacker's address. The victim has no trustless recourse: they cannot submit a competing refund request (blocked by the duplicate check), and they cannot permissionlessly reject the attacker's request (blocked because the UTXO was never verified via deposit). This constitutes direct, permanent theft of user BTC — a Critical impact under the allowed scope.

---

### Likelihood Explanation

All inputs required for the attack are publicly available:

- The victim's `deposit_msg` is emitted as a NEAR event when `get_user_deposit_address` is called, and is also visible in the parameters of any `verify_deposit_v2` call.
- The `tx_bytes` and Merkle `proof` are public Bitcoin blockchain data.
- The only cost to the attacker is the NEAR storage deposit required by `request_refund`.

The attack window is the period between a BTC deposit being confirmed on Bitcoin and `verify_deposit_v2` being called by a relayer. Deposits that fail to be processed (e.g., due to relayer downtime, minimum amount not met, or user error) are the primary target. The attacker does not need to win a same-block race; they only need to submit their transaction before the victim thinks to call `request_refund`. This is a realistic, low-cost attack.

---

### Recommendation

Bind the refund request to the caller's identity when `deposit_msg.refund_address` is `None`. Store `env::predecessor_account_id()` as the authorized executor at request time and require that only that account (or DAO/Operator) can call `execute_refund` for that request. Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) so the refund destination is committed at deposit time and cannot be overridden by a third party.

---

### Proof of Concept

1. Victim deposits BTC to a bridge address derived from `deposit_msg { recipient_id: "victim.near", refund_address: None, ... }`. The `deposit_msg` is emitted as a NEAR event.
2. The relayer does not call `verify_deposit_v2` (e.g., the deposit is below `min_deposit_amount` or the relayer is offline).
3. Attacker observes the unprocessed deposit on Bitcoin and the `deposit_msg` from NEAR events.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)` with a small NEAR storage deposit attached.
5. `request_refund_callback` succeeds: the refund request is stored with `refund_address = attacker_btc_address`.
6. Victim calls `request_refund` with their own `refund_address` → panics: `"Refund request already exists for this UTXO"`.
7. DAO/Operator does not notice or does not act within 14 days.
8. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_storage_key, None)`.
9. The bridge builds and signs a Bitcoin transaction paying `attacker_btc_address`. Victim's BTC is stolen.
