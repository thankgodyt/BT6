Audit Report

## Title
Missing Chain ID in `deployToken` Signature Hash Enables Cross-Chain Replay of Deployment Signatures - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
The `deployToken` function in `OmniBridge.sol` constructs a Borsh-encoded hash for MPC signature verification that omits `omniBridgeChainId`, while `finTransfer` explicitly binds its hash to the destination chain via `omniBridgeChainId`. A valid `deployToken` signature obtained from one EVM chain (e.g., Ethereum) can be replayed verbatim on any other EVM chain (e.g., Arbitrum, Base) to deploy tokens without NEAR explicitly authorizing deployment on those chains. The same structural flaw exists in the Starknet and Solana implementations.

## Finding Description

**Root cause — EVM (`OmniBridge.sol`):**

In `deployToken()` (L142–153), the Borsh-encoded hash is:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No `omniBridgeChainId` is included. In contrast, `finTransfer()` (L289–298) includes `omniBridgeChainId` twice, binding the signature to the specific destination chain.

**Root cause — NEAR signing side (`near/omni-bridge/src/lib.rs`):**

The `log_metadata_callback` (L341–366) constructs a `MetadataPayload` with only `prefix`, `token`, `name`, `symbol`, and `decimals` — no chain ID — and submits this to the MPC signer. The resulting signature is therefore chain-agnostic by construction.

**Root cause — Starknet (`starknet/src/bridge_types.cairo`):**

`MetadataPayloadImpl::to_borsh()` (L36–44) encodes only `PayloadType::Metadata`, token, name, symbol, and decimals — no chain ID. The Starknet `CLAUDE.md` (L45) explicitly documents chain ID binding for `fin_transfer` but makes no such claim for `deploy_token`, confirming the omission is structural.

**Root cause — Solana (`solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`):**

`DeployTokenPayload::serialize_for_near()` (L19–26) serializes only `IncomingMessageType::Metadata` and the payload fields — no chain ID.

**Exploit flow:**

1. NEAR's `log_metadata` is called for `"token.near"`. NEAR MPC signs a chain-agnostic `MetadataPayload` and emits a `LogMetadataEvent` with the signature.
2. A relayer calls `deployToken(signature, payload)` on Ethereum. The signature is publicly visible in calldata.
3. Attacker extracts the signature from the Ethereum transaction.
4. Attacker calls `deployToken(signature, payload)` on Arbitrum with identical arguments.
5. `OmniBridge.sol::deployToken()` computes the same hash (no chain ID) and `ECDSA.recover` passes.
6. `"token.near"` is deployed on Arbitrum; `isBridgeToken`, `ethToNearToken`, `nearToEthToken` are updated; a `DeployToken` event is emitted.
7. A relayer submits a proof of this `DeployToken` event to NEAR's `bind_token()`. The `bind_token_callback` checks only that the emitter is a registered factory for that chain (`self.factories.get(&deploy_token.emitter_address.get_chain()) == Some(deploy_token.emitter_address)`), which passes if Arbitrum is a supported chain.
8. NEAR registers `"token.near"` as deployed on Arbitrum and begins signing `finTransfer` payloads for Arbitrum — a chain NEAR never explicitly authorized for this token.

**Existing checks are insufficient:**

- The `isBridgeToken[nearToEthToken[metadata.token]]` check (L155–158) only prevents re-deployment on the *same* chain instance; it does not prevent replay on a different chain.
- The `bind_token_callback` factory check verifies the emitter is a known factory but does not verify that NEAR authorized deployment of this specific token on this specific chain.

## Impact Explanation

This is a confirmed chain/domain separation flaw. The NEAR MPC's signature over a `MetadataPayload` is intended to authorize deployment of a specific token; the chain specificity is supposed to be enforced by the signed hash. Because `omniBridgeChainId` is absent from the `deployToken` hash, a single MPC signature authorizes deployment on every EVM chain simultaneously. An unprivileged attacker can replay any publicly observed `deployToken` signature across all EVM chains (Ethereum, Arbitrum, Base, BNB, HyperEVM, Abs), deploying tokens on chains where NEAR has not granted authorization. Once NEAR's `bind_token` processes the resulting `DeployToken` event from the unauthorized chain, it registers the token there and begins signing `finTransfer` payloads for that chain — enabling token flows to a chain the NEAR MPC never explicitly approved. This matches the allowed impact: **cross-chain replay / chain/domain separation flaw enabling invalid finalization**.

## Likelihood Explanation

High. The `deployToken` signature is publicly available in transaction calldata on any EVM chain where the token has already been deployed. No privileged access, leaked keys, or admin compromise is required. The only precondition is that a valid `deployToken` signature exists for the target token on any one EVM chain — which is true for every token already deployed through the bridge. The attack is repeatable for every token and every additional EVM chain.

## Recommendation

Include `omniBridgeChainId` in the Borsh-encoded hash for `deployToken` signature verification in `evm/src/omni-bridge/contracts/OmniBridge.sol`, mirroring the pattern used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // ← add chain binding
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the equivalent fix to:
- `MetadataPayloadImpl::to_borsh()` in `starknet/src/bridge_types.cairo` (L36–44), adding the chain ID parameter analogously to `TransferMessagePayloadImpl::to_borsh()`.
- `DeployTokenPayload::serialize_for_near()` in `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs` (L19–26), adding `SOLANA_OMNI_BRIDGE_CHAIN_ID` to the serialized bytes.
- The NEAR `log_metadata_callback` in `near/omni-bridge/src/lib.rs` (L341–366) must include the target chain ID in the `MetadataPayload` so the MPC signs a chain-specific hash.

## Proof of Concept

**Minimal hardhat test (EVM):**

```typescript
// Deploy OmniBridge on two simulated chains (chainId=0 for Ethereum, chainId=1 for Arbitrum)
// Use the same testWallet as nearBridgeDerivedAddress on both

// 1. Obtain a valid deployToken signature for chainId=0 (Ethereum)
const { signature, payload } = metadataSignature("token.near");
await omniBridgeEthereum.deployToken(signature, payload);

// 2. Replay the identical signature on chainId=1 (Arbitrum)
// OmniBridgeArbitrum computes the same hash (no chain ID) → ECDSA.recover passes
await omniBridgeArbitrum.deployToken(signature, payload);
// Expect: DeployToken event emitted on Arbitrum — token deployed without NEAR authorization
```

This test requires no privileged access and demonstrates the replay with publicly available calldata. The `metadataSignature` helper in `evm/tests/helpers/signatures.ts` (L85–106) already constructs the chain-agnostic hash, confirming the test is directly reproducible against the existing test suite.
