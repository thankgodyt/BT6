### Title
Hardcoded `emptyPerasWeightSnapshot` in ChainSync Client Candidate Comparison Ignores Peras Certificate Boosts, Causing Incorrect Peer Disconnection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` instead of reading the actual accumulated Peras weight snapshot from the `PerasCertDB`. This is a direct structural analog to the reported bug: a configurable/mutable value (the live weight snapshot) is ignored in favour of a hardcoded constant (the empty snapshot), making the entire certificate-accumulation subsystem invisible to this specific comparison. When Peras is active, a peer offering the canonical chain — which may be shorter in block count but heavier in Peras weight — is incorrectly classified as offering a non-preferable chain and disconnected from.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked by the ChainSync client when a received header is beyond the forecast horizon. Its purpose is to decide whether to keep or drop the peer: if the candidate chain is not preferable to the node's current chain, the node throws `CandidateTooSparse` and disconnects.

The comparison is delegated to `preferAnchoredCandidate`, which accepts a `PerasWeightSnapshot blk` parameter. When that snapshot is non-empty, `preferAnchoredCandidate` computes the intersection of the two fragments and compares their total Peras-weighted lengths. When the snapshot is empty, it falls back to a pure block-count comparison.

`checkPreferTheirsOverOurs` always passes `emptyPerasWeightSnapshot`:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded constant, never the live snapshot
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...

Meanwhile, the `PerasCertDB` continuously accumulates validated certificates and exposes a live weight snapshot via `getWeightSnapshot`:

The ChainDB API exposes this snapshot for chain selection:

```haskell

The main chain selection path in `ChainSel.hs` correctly reads and uses the live snapshot via `weights` passed through `ChainSelEnv`. Only `checkPreferTheirsOverOurs` ignores it. [4](#0-3) 

The `preferAnchoredCandidate` function explicitly branches on whether the snapshot is empty:

```haskell

      -- fast path: block-count comparison only
      ...
  | otherwise =

      ...
``` [5](#0-4) 

Because `emptyPerasWeightSnapshot` is always passed, the fast path is always taken, and Peras boosts are never considered.

---

### Impact Explanation

**Classification: High — Chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain.**

Under Peras, the canonical chain is the one with the greatest total weight (block count + sum of certificate boosts). A chain that is shorter in block count but carries one or more Peras certificate boosts can be heavier than a longer chain without boosts.

When a peer offers such a chain and the tip header is beyond the forecast horizon, `checkPreferTheirsOverOurs` compares only block counts. The boosted-but-shorter candidate is classified as non-preferable, `CandidateTooSparse` is thrown, and the peer is disconnected. The node remains on its current, lighter chain.

Concretely:
- The node's current chain has length N, no boosts → total weight N.
- A peer offers a chain of length N−1 with one certificate boost of weight W > 1 → total weight N−1+W > N.
- `checkPreferTheirsOverOurs` sees N−1 < N, classifies the candidate as non-preferable, and disconnects.
- The node is now isolated from the canonical chain.

This is a direct chain-selection safety failure: an honest node rejects the canonical chain and retains a non-canonical one, violating the Peras security guarantee.

---

### Likelihood Explanation

The bug is latent until Peras is enabled via `rnFeatureFlags`. Once enabled, it is triggered whenever:
1. A peer's chain tip is beyond the forecast horizon (a normal occurrence during sync or after a slot gap), **and**
2. The canonical chain carries at least one Peras certificate boost that makes it heavier than the node's current chain despite being shorter in block count.

Condition (2) is the normal operating state of Peras — certificates are produced every round. Any honest peer offering the canonical chain in this state would be disconnected. The attacker entry path requires no special privileges: any network peer can trigger this by serving the canonical chain.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the `PerasCertDB` (or passed in from the ChainSync client's environment). The existing `getPerasWeightSnapshot` STM action on the `ChainDB` API is the correct source. The TODO comment at the call site (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) acknowledges the problem; the fix should either remove the check entirely (as the TODO suggests) or, if the check must be retained, supply the actual weight snapshot so that Peras-boosted candidates are correctly classified as preferable.

---

### Proof of Concept

1. Enable Peras (`rnFeatureFlags` includes Peras).
2. Let the node sync to chain C of length N with no Peras boosts (total weight N).
3. Connect a peer offering chain C′ of length N−1 with one certificate boost of weight 2 (total weight N+1 > N). Arrange for the tip of C′ to be beyond the forecast horizon of the node's current ledger state.
4. `checkPreferTheirsOverOurs` is invoked. It calls `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag`. Because `isEmptyPerasWeightSnapshot emptyPerasWeightSnapshot` is `True`, the fast path compares block counts: N−1 < N → `ShouldNotSwitch`. The condition `shouldSwitch (...)` is `False`.
5. `throwSTM (CandidateTooSparse ...)` is executed; the peer is disconnected.
6. The node remains on C (weight N) and never adopts C′ (weight N+1), the canonical chain. [6](#0-5) [5](#0-4) [7](#0-6)
