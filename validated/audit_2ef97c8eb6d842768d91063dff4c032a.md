### Title
`validatePerasCert` Stub Unconditionally Returns `Right`, Bypassing All Peras Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` class defines `validatePerasCert` as the validation gate for inbound Peras certificates. The production inbound-certificate pipeline (`processCerts`) calls this function before storing any certificate. However, the only concrete instance of `validatePerasCert` is a stub that unconditionally returns `Right` — performing zero cryptographic or semantic checks. Any certificate sent by an unprivileged peer is therefore accepted, stored in the `PerasCertDB`, and allowed to influence chain selection by boosting an arbitrary block.

This is the direct analog of the GDACurve finding: a dedicated validation function exists (`validateSpotPrice` / `validatePerasCert`), but the update path that actually stores the value (`getBuyInfo`/`getSellInfo` / `processCerts → addCert`) bypasses the real constraint check because the validation function itself is a no-op stub.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` as the required validation entry-point:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only instance — a universal `StandardHash blk` catch-all — is:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every certificate, regardless of content, is wrapped in `Right ValidatedPerasCert` and returned as valid.

The production inbound pipeline in `processCerts` calls this function on every certificate received from a peer before storing it:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` is bound to `validatePerasCert mkPerasParams` — the stub — `partitionEithers` always produces `([], validatedCerts)`, so every certificate is unconditionally added.

Both production pool writers pass this stub:

```haskell

(validatePerasCert mkPerasParams)
``` [3](#0-2) 

Once stored, the certificate is consumed by `implGetWeightSnapshot` to build the `PerasWeightSnapshot` used in chain selection:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

Chain selection then uses these weights to compare candidate chains:

```haskell
assert (all (shouldSwitch . preferAnchoredCandidate bcfg weights curChain . Diff.getSuffix . fst) chainDiffs)
``` [5](#0-4)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any `PerasRoundNo` and any `Point blk` as the boosted block. Because `validatePerasCert` never rejects anything, the certificate is stored and its `vpcCertBoost` (drawn from `perasWeight params`) is added to the weight of the named block in every subsequent chain-selection comparison. By boosting a block on a minority fork, the attacker can make an honest node's `preferAnchoredCandidate` prefer that fork over the canonical chain, causing the node to switch to a non-canonical chain. This is a bypass of Peras certificate/vote-check validation that enables unauthorized certificate acceptance and a chain-selection deviation beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only that the Peras object-diffusion mini-protocol is active and that the attacker can establish a peer connection — both conditions that hold for any node with Peras enabled. No stake, keys, or operator access are needed. The attacker-controlled entry path is: peer connection → `ObjectDiffusion` inbound handler → `opwAddObjects` → `processCerts` → `validatePerasCert` (stub, always `Right`) → `addCert` → `PerasCertDB` → `getWeightSnapshot` → `chainSelection`. The stub is present in the current production codebase; the only gate is whether Peras rounds are enabled in the era configuration.

---

### Recommendation

Replace the stub with real validation before the Peras mini-protocol is activated. At minimum, `validatePerasCert` must verify:

1. The certificate's `pcCertRound` is within the acceptable window (not from a future or expired round).
2. The `pcCertBoostedBlock` references a block that is plausibly on a valid chain (slot and hash sanity).
3. The aggregate BLS signature over `(electionId, boostedBlock)` verifies against the claimed committee members' keys.
4. The set of signers constitutes a quorum of the committee for that round.

Until these checks are in place, the `validatePerasCert` call in `processCerts` provides no security guarantee, and the `ValidatedPerasCert` wrapper is a false assurance of validity.

---

### Proof of Concept

1. Run a node with Peras rounds enabled (non-zero `PerasRoundLength` in era params).
2. From a second process, open a peer connection and send a `PerasCert` message with:
   - `pcCertRound = <any round not yet in the DB>`
   - `pcCertBoostedBlock = <point of a block on a minority fork>`
3. Observe that `processCerts` calls `validatePerasCert`, receives `Right`, and calls `addCert`.
4. Query `getWeightSnapshot`; the minority-fork block now carries `perasWeight` boost.
5. Introduce a candidate chain containing that block; `preferAnchoredCandidate` will now prefer it over the canonical chain due to the injected weight, causing the node to switch forks. [6](#0-5) [7](#0-6) [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
