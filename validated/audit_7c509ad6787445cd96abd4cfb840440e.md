### Title
Peras Certificate Verification Bypass Allows Any Peer to Inject Arbitrary Chain-Weight Boosts — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` (success) for every certificate it receives, performing no actual cryptographic or structural validation. Because the Peras certificate inbound diffusion handler (`hPerasCertDiffusionClient`) is wired to this stub validator for all connected peers, any unprivileged peer can send a crafted `PerasCert` over the node-to-node `PerasCertDiffusion` miniprotocol. The certificate is accepted, stored in the `PerasCertDB`, and triggers chain selection with an attacker-controlled Peras weight boost applied to an arbitrary block, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub validator always returns `Right`:**

The `BlockSupportsPeras` instance in `SupportsPeras.hs` is explicitly marked as a degenerate placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every `PerasCert` — regardless of its content, round number, boosted block, or whether any quorum of committee members actually signed it — is wrapped in `ValidatedPerasCert` and assigned the full `perasWeight` boost.

**Inbound path — any peer triggers this validator:**

`makePerasCertPoolWriterFromChainDB` (the production cert inbound writer) calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` passes every cert that is not already in the DB through `validateCert`. Since `validateCert` always returns `Right`, all certs pass and are forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

**Network wiring — exposed to all peers:**

`hPerasCertDiffusionClient` in `mkHandlers` wires `makePerasCertPoolWriterFromChainDB` directly to the node-to-node `PerasCertDiffusion` inbound miniprotocol for every connected peer:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain selection impact:**

`chainSelSync` processes the queued cert: it adds it to `PerasCertDB` and then calls `chainSelectionForBlock` for the attacker-specified `pcCertBoostedBlock`. The Peras weight boost (`vpcCertBoost = perasWeight params`) is applied to that block's chain fragment during candidate comparison, potentially causing the node to switch to a non-canonical chain: [5](#0-4) 

---

### Impact Explanation

**Severity: High — Chain selection bug enabling non-canonical chain preference.**

When Peras is enabled, an unprivileged peer can:
1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the VolatileDB (e.g., a block on a minority fork).
2. Send it over the `PerasCertDiffusion` miniprotocol.
3. The cert bypasses all validation (stub always returns `Right`).
4. The cert is stored and triggers `chainSelectionForBlock` for the attacker-chosen block.
5. That block's chain fragment receives the full `perasWeight` boost, making it appear heavier than the honest canonical chain.
6. The node switches to the attacker-boosted fork.

This directly violates the Peras security invariant: only certificates backed by a genuine quorum of committee members should influence chain selection. An attacker with no stake and no committee membership can manufacture the same chain-selection effect as a legitimate quorum certificate.

---

### Likelihood Explanation

**Likelihood: Medium** (conditional on Peras being enabled).

- Peras is disabled by default per the CHANGELOG ("if Peras is disabled (which is the default), there is no observable difference").
- When Peras is enabled (e.g., in a private testnet or future mainnet activation), the attack requires only a standard peer connection — no keys, no stake, no privileged access.
- The attacker needs to know a valid `HeaderHash` for a block in the target node's VolatileDB (obtainable via ChainSync) to construct a plausible `pcCertBoostedBlock`.
- The `PerasCertDiffusion` miniprotocol is fully wired and reachable from any connected peer when the feature flag is active.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real certificate validation before enabling Peras in any production or testnet environment. At minimum, the validation must verify:
1. The certificate covers a genuine quorum of eligible committee members (by stake weight).
2. Each member's vote signature is cryptographically valid.
3. All votes target the same `(round, block)` pair.
4. The round number is within the acceptable window.

The existing `TODO` at `https://github.com/tweag/cardano-peras/issues/120` tracks this. Until it is resolved, the `PerasCertDiffusion` miniprotocol should not be enabled in any environment where untrusted peers can connect.

---

### Proof of Concept

**Private-testnet sequence (no privileged access required):**

1. Enable Peras on a private testnet node (`rnFeatureFlags` includes the Peras cert diffusion flag).
2. Connect as a peer via the node-to-node protocol.
3. Obtain a block hash `H` from a minority fork via ChainSync (the target node's VolatileDB contains it).
4. Construct a `PerasCert`:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = BlockPoint <slot> H }
   ```
5. Send it over the `PerasCertDiffusion` inbound channel.
6. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }`.
7. `ChainDB.addPerasCertAsync` queues the cert; `chainSelSync` adds it to `PerasCertDB` and calls `chainSelectionForBlock` for block `H`.
8. The chain containing `H` now has extra Peras weight; if it exceeds the current selection's weight, the node switches to the attacker-chosen fork. [6](#0-5) [7](#0-6) [4](#0-3) [5](#0-4)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
