### Title
Front-Running Griefing on `request_refund` Allows Attacker to Redirect Victim's BTC Refund Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` function is publicly callable and stores a refund request keyed by `utxo_storage_key = generate_utxo_storage_key(tx_id, vout)`. This key is derived entirely from public Bitcoin data (transaction ID and output index) and does not include the caller's identity. When `deposit_msg.refund_address` is `None`, the `refund_address` parameter is not validated against the caller. An attacker can observe a victim's pending `request_refund` call, front-run it with the same proof but a different `refund_address`, causing the victim's callback to revert and storing the attacker's address as the refund destination. After the timelock, the attacker (or anyone) can call `execute_refund`, triggering MPC signing to send the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, payable function with no caller-identity restriction: [1](#0-0) 

It delegates to `internal_request_refund`, which only validates `refund_address` against `deposit_msg.refund_address` when the latter is `Some`: [2](#0-1) 

When `deposit_msg.refund_address` is `None`, any caller can supply any `refund_address`. The callback then computes the storage key from the Bitcoin transaction ID and `vout` — both public, observable data — with no caller component: [3](#0-2) 

The callback then enforces uniqueness on this key: [4](#0-3) 

If the attacker's transaction lands first, the victim's callback panics with `"Refund request already exists for this UTXO"`. The attacker's `RefundRequest` is stored with `refund_address = attacker_btc_addr`: [5](#0-4) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` (also publicly callable) can be invoked by anyone, triggering `finalize_refund_with_psbt` which builds a PSBT paying `refund_amount` to the stored `refund_address` and submits it to MPC for signing: [6](#0-5) 

The `deposit_path` used to derive the signing key is taken from the `deposit_msg` (which the attacker copied verbatim from the victim), so MPC will sign a valid transaction sending the victim's BTC to the attacker's address.

---

### Impact Explanation

**Medium (escalating to Critical).**

Primary impact: The attacker can persistently block a victim from ever successfully submitting a `request_refund` by front-running every attempt. The victim's BTC remains locked in the deposit address indefinitely — attacker-triggered temporary locking of bridged funds.

Escalation path to Critical: If the DAO/Operator does not reject the attacker's fraudulent refund request within `unsafe_refund_timelock_sec`, anyone can call `execute_refund`, causing the MPC network to sign a Bitcoin transaction that sends the victim's BTC to the attacker's address. This constitutes unauthorized release of user BTC.

---

### Likelihood Explanation

**Medium.** NEAR transactions are observable before finalization. The attacker needs only to copy the victim's `deposit_msg`, `tx_bytes`, `vout`, and `proof` parameters while substituting their own `refund_address`. The attack requires no special privileges, no leaked keys, and no majority network control. The only mitigation is DAO intervention within the `unsafe_refund_timelock_sec` window, which is an operational dependency rather than a protocol guarantee. The attacker can repeat the front-run after each DAO rejection, making the DoS persistent.

---

### Recommendation

Bind the refund request to the caller's identity. Two options:

1. **Include `predecessor_account_id()` in the refund request storage key** so each caller has an independent slot. Combine with a check that only the original requester (or DAO) can call `execute_refund` for their slot.

2. **Require `deposit_msg.refund_address` to always be `Some`** for `request_refund`. Since the deposit address is derived from `deposit_msg` (including `refund_address`), a pre-committed refund address is cryptographically bound to the deposit. The existing check at line 154–158 already enforces this when set, making front-running with a different address impossible.

Option 2 is the simpler fix and directly mirrors the recommendation in the reference report (include the caller-specific value in the deterministic identifier).

---

### Proof of Concept

1. Alice deposits BTC to the address derived from `deposit_msg = {recipient_id: alice.near, refund_address: None, ...}`.
2. The deposit is never finalized by a relayer.
3. Alice calls `request_refund(deposit_msg, refund_address="alice_btc_addr", tx_bytes, vout, proof, None)`.
4. Attacker observes the pending NEAR transaction and submits `request_refund(deposit_msg, refund_address="attacker_btc_addr", tx_bytes, vout, proof, None)` with higher priority (NEAR supports transaction ordering by nonce/gas).
5. Attacker's `request_refund_callback` runs first: `utxo_storage_key = "{tx_id}@{vout}"` is inserted into `refund_requests` with `refund_address = "attacker_btc_addr"`.
6. Alice's `request_refund_callback` runs: `require!(!self.data().refund_requests.contains_key(&utxo_storage_key), ...)` panics → Alice's transaction reverts.
7. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund("{tx_id}@{vout}", None)`.
8. `finalize_refund_with_psbt` builds a PSBT spending Alice's deposit UTXO, paying `refund_amount` to `"attacker_btc_addr"`, and submits to MPC.
9. MPC signs using the path derived from Alice's `deposit_msg` (which the attacker copied exactly).
10. The signed transaction is broadcast; Alice's BTC is sent to the attacker.
