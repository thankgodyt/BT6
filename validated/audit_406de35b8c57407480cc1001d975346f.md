Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC-1155 `safeTransferFrom` Enables Unauthorized Minting on NEAR — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` at the top of the function but reads it again — from storage — after an external call to an untrusted, caller-supplied ERC-1155 token address. A malicious ERC-1155 token can reenter `initTransfer1155` during its `safeTransferFrom` implementation, causing both the reentrant and original invocations to emit `InitTransfer` with the same nonce while locking zero tokens. The NEAR bridge processes the event and mints tokens on NEAR with no corresponding collateral locked on EVM.

## Finding Description

`initTransfer1155` accepts any arbitrary `tokenAddress` without checking whether it is a registered or trusted token. The function increments `currentOriginNonce` at line 448, then makes an external call to the untrusted token at lines 458–464, then reads `currentOriginNonce` again from storage at lines 471 and 483:

```solidity
// Line 448
currentOriginNonce += 1;          // storage write: nonce = N

// Lines 458–464
IERC1155(tokenAddress).safeTransferFrom(   // ← untrusted external call
    msg.sender, address(this), tokenId, amount, ""
);

// Lines 471, 483 — storage read AFTER external call
initTransferExtension(..., currentOriginNonce, ...);
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...);
```

A malicious ERC-1155 token can implement `safeTransferFrom` to call back directly into `initTransfer1155` (bypassing `onERC1155Received` entirely). The bridge's `onERC1155Received` guard at lines 522–535 only rejects direct ERC-1155 sends where `operator != address(this)`; it does not prevent reentrancy through a malicious token's custom `safeTransferFrom` body.

There is no `nonReentrant` modifier on `initTransfer1155`. The two `slither-disable` comments in the file (lines 161, 318) suppress static-analysis warnings on unrelated functions and provide zero runtime protection.

**Attack trace (initial `currentOriginNonce = 0`):**

| Step | Context | Action | `currentOriginNonce` |
|---|---|---|---|
| 1 | Original call | `+= 1` | **1** |
| 2 | Malicious token | reenters `initTransfer1155` | — |
| 3 | Reentrant call | `+= 1` | **2** |
| 4 | Malicious token | does NOT reenter; transfers 0 tokens | — |
| 5 | Reentrant call | reads `currentOriginNonce = 2`; emits `InitTransfer(nonce=2)` | **2** |
| 6 | Original call resumes | reads `currentOriginNonce = 2`; emits `InitTransfer(nonce=2)` | **2** |

Result: two `InitTransfer` events with `nonce=2`, nonce 1 never emitted, zero tokens locked on EVM. NEAR bridge processes `nonce=2` once and mints the full `amount` of tokens.

## Impact Explanation

An unprivileged attacker can mint an arbitrary amount of bridged ERC-1155-backed tokens on NEAR without locking any collateral on EVM. This is unauthorized minting of bridged funds — a direct match for the Critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, … flows."* The attacker can repeat the attack indefinitely, draining NEAR-side liquidity.

## Likelihood Explanation

The attack requires only: (1) deploying a malicious ERC-1155 contract, and (2) calling the public `initTransfer1155` function. No privileged role, no victim mistake, no external dependency, and no collusion is required. The function is callable by any EOA or contract on any supported EVM chain. The attack is fully repeatable.

## Recommendation

Apply the checks-effects-interactions pattern: cache the nonce in a local variable immediately after incrementing it, and use that local variable for all subsequent reads, so reentrancy cannot alter the value observed by the original call:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // cache in local variable

IERC1155(tokenAddress).safeTransferFrom(...);  // external call

initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Additionally, add OpenZeppelin's `ReentrancyGuard` (or `ReentrancyGuardUpgradeable`) and apply `nonReentrant` to `initTransfer1155`. Note that `initTransfer` (ERC-20 path, lines 373–437) has the same storage-read-after-external-call pattern and should be audited for any ERC-777/callback-enabled token paths as well.

## Proof of Concept

Deploy the following malicious ERC-1155 token and call `initTransfer1155` once:

```solidity
contract MaliciousERC1155 {
    OmniBridge bridge;
    bool reentered;

    function safeTransferFrom(
        address, address, uint256, uint256, bytes memory
    ) external {
        if (!reentered) {
            reentered = true;
            // Reentrant call — transfers 0 tokens, increments nonce to 2
            bridge.initTransfer1155(address(this), 0, amount, fee, nativeFee, recipient, "");
        }
        // Both calls return here having transferred 0 tokens
    }
    // ... minimal ERC-1155 stubs
}
```

Expected observable state after the two calls complete:
- Two `InitTransfer` events emitted, both with `nonce = 2`.
- `currentOriginNonce == 2` on-chain; nonce 1 has no corresponding event.
- Zero ERC-1155 tokens held by the bridge.
- NEAR relayer processes `nonce=2` and mints `amount` tokens on NEAR.

A Foundry invariant test asserting `bridge.currentOriginNonce() == number_of_InitTransfer_events_emitted` will fail after a single reentrant call, confirming the bug.
