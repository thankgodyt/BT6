### Title
Stub `validatePerasCert` Accepts Any Peras Certificate Without Cryptographic or Chain-Context Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` default instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every certificate it receives, performing no BLS aggregate-signature verification and no check that the boosted block belongs to the current chain. An unprivileged peer can therefore send a crafted Peras certificate that is accepted as "validated," triggering chain selection for an arbitrary block and potentially causing the node to prefer a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` class defines a certificate-validation method `validatePerasCert`. The only concrete instance in the production source tree is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function signature is:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The stub ignores the certificate's content entirely and always produces a `ValidatedPerasCert`. No check is performed on:

1. **BLS aggregate signature** — `PerasCert.V1` carries a `pcSignature :: AggregateVoteSignature PerasBLSCrypto` that is never verified. [2](#0-1) 
2. **Chain-context binding** — `pcBoostedBlock :: Point blk` is never checked to belong to the node's current chain or any chain the node has seen. [3](#0-2) 
3. **Voter eligibility** — the voters bitmap and their eligibility proofs inside `PerasCertVoters` are never validated against the stake distribution.

The `ValidatedPerasCert` wrapper is the type consumed by `addPerasCertAsync` / `addPerasCertSync` in the ChainDB API:

```haskell
addPerasCertSync ::
  IOLike m =>
  ChainDB m blk -> WithArrivalTime (ValidatedPerasCert blk) -> m AddPerasCertChainSelOutcome
``` [4](#0-3) 

Once a `ValidatedPerasCert` reaches `chainSelSync`, the ChainDB triggers chain selection for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The only guard before that point is a slot-age check (`pointSlot boostedBlock < AF.anchorToSlotNo immTip`) and a duplicate check — neither verifies the certificate's cryptographic authenticity or chain membership. [6](#0-5) 

**Analog to the external report:** Just as Spartan's `mintSynth` accepted any valid synth address without `require(iSYNTH(synthOut).LayerONE() == TOKEN)`, `validatePerasCert` accepts any certificate without verifying that its BLS signature is valid and that its boosted block belongs to the current chain context. The missing check is the consensus-layer equivalent of `LayerONE() == TOKEN`.

---

### Impact Explanation

An attacker who can send Peras certificates to a node (via the Peras mini-protocol) can:

1. Forge a certificate claiming a quorum voted for a block on a fork chain.
2. The stub `validatePerasCert` wraps it in `ValidatedPerasCert` unconditionally.
3. `chainSelSync` triggers `chainSelectionForBlock` for the attacker-chosen block.
4. The boosted block receives `vpcCertBoost = perasWeight params` extra weight in `preferAnchoredCandidate`, potentially making the fork preferred over the honest chain.

This constitutes a **chain-selection manipulation**: an unprivileged peer can make an honest node prefer a non-canonical chain by injecting a certificate with a fabricated BLS signature, bypassing the entire Peras quorum-certificate security guarantee.

---

### Likelihood Explanation

The Peras mini-protocol is a new addition and the degenerate instance is explicitly marked as a production placeholder (not test-only). Any peer that can establish a connection and speak the Peras sub-protocol can send a crafted certificate. No stake, keys, or operator access is required. The attack is deterministic and requires only a single crafted message.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:

1. Verifies the BLS aggregate signature over `(pcRoundNo, pcBoostedBlock)` against the aggregate public key derived from the eligible voters in `pcVoters`.
2. Checks that `pcBoostedBlock` is a point on a chain the node has seen (i.e., its hash is present in the VolatileDB or ImmutableDB).
3. Verifies each voter's eligibility proof against the current stake distribution.

Until the real implementation is in place, the Peras certificate ingestion path (`addPerasCertAsync`) should be gated behind a feature flag that is disabled by default.

---

### Proof of Concept

```
1. Attacker node connects to victim node and speaks the Peras mini-protocol.

2. Attacker constructs a PerasCert with:
     pcRoundNo      = <current round>
     pcBoostedBlock = <point of a block on attacker's fork>
     pcVoters       = <arbitrary bitmap>
     pcSignature    = <random bytes — never checked>

3. Attacker sends the certificate to the victim.

4. Victim calls validatePerasCert on the received cert.
   Due to the stub, it returns:
     Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

5. Victim calls addPerasCertAsync with the "validated" cert.

6. chainSelSync runs:
   - slot-age check passes (attacker chose a recent block)
   - duplicate check passes (first time this round number is seen)
   - chainSelectionForBlock is called for the attacker's fork block

7. preferAnchoredCandidate now sees the fork block with extra Peras weight,
   potentially switching the victim's selection to the attacker's fork.
``` [1](#0-0) [7](#0-6)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
