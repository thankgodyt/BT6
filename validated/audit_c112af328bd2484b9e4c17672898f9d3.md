### Title
`withdraw_rbf` Uses Caller Identity Instead of Pending-Info Owner Identity, Enabling Unauthorized RBF of Any User's Withdrawal — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`withdraw_rbf` captures `env::predecessor_account_id()` (the caller) and passes it directly as the owning account to `withdraw_rbf_chain_specific`, without ever verifying that the caller is the owner of the pending withdrawal identified by `original_btc_pending_verify_id`. The sibling function `cancel_withdraw` performs this check correctly by first fetching the owner from the stored `BTCPendingInfo`. The discrepancy is a direct analog of the reported `settleAskTaker` bug: the wrong identity is used for authorization.

---

### Finding Description

In `contracts/satoshi-bridge/src/api/bridge.rs`, `withdraw_rbf` (lines 258–274) does the following:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not pending-info owner
    self.require_pending_sign_capacity(&account_id);  // ← capacity checked for caller

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller passed as "owner" of new RBF tx
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
``` [1](#0-0) 

Compare this with `cancel_withdraw` (lines 283–299), which correctly resolves the owner from the stored pending info before proceeding:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id          // ← owner fetched from pending info
        .clone();
    self.require_pending_sign_capacity(&user_account_id);
    self.cancel_withdraw_chain_specific(user_account_id, ...);
}
``` [2](#0-1) 

`BTCPendingInfo` stores the true owner in its `account_id` field: [3](#0-2) 

Because `withdraw_rbf` never reads `btc_pending_info.account_id` and never asserts `caller == btc_pending_info.account_id`, any NEAR account can invoke it against any other user's pending withdrawal. The caller-supplied `output` (which specifies the BTC destination addresses and amounts) is then used to construct the replacement PSBT, and the new `BTCPendingInfo` is attributed to the attacker rather than the original owner.

---

### Impact Explanation

An attacker who calls `withdraw_rbf` on a victim's pending withdrawal can supply an `output` that redirects the BTC to an attacker-controlled address. The replacement PSBT is signed by the MPC network (which signs whatever valid PSBT is presented), and the resulting transaction, once broadcast, sends the victim's BTC to the attacker. This constitutes unauthorized redirection of bridge-controlled funds — a critical impact matching "Chain-signature, PSBT, or transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds."

---

### Likelihood Explanation

`withdraw_rbf` is a public, unpermissioned function (no `#[access_control_any]` guard, no `assert_one_yocto`). Any NEAR account can call it at any time against any pending withdrawal that is in the `PendingVerify` stage. Pending withdrawals are publicly observable on-chain via `btc_pending_infos`. The attacker only needs to know the `original_btc_pending_verify_id` (a public map key) and have enough NEAR for gas. Likelihood is high.

---

### Recommendation

Mirror the pattern used in `cancel_withdraw`: fetch the owner from the stored `BTCPendingInfo` and assert the caller matches before proceeding.

```diff
 pub fn withdraw_rbf(
     &mut self,
     original_btc_pending_verify_id: String,
     output: Vec<TxOut>,
     chain_specific_data: Option<ChainSpecificData>,
 ) {
-    let account_id = env::predecessor_account_id();
-    self.require_pending_sign_capacity(&account_id);
+    let account_id = self
+        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
+        .account_id
+        .clone();
+    require!(
+        env::predecessor_account_id() == account_id,
+        "Only the withdrawal owner can submit an RBF"
+    );
+    self.require_pending_sign_capacity(&account_id);

     self.withdraw_rbf_chain_specific(
         account_id,
         original_btc_pending_verify_id,
         output,
         chain_specific_data,
     );
 }
```

### Proof of Concept

1. Alice calls `ft_on_transfer` (Withdraw) and a `BTCPendingInfo` is created with `account_id = alice`, `btc_pending_id = X`, and `output[0].script_pubkey` paying Alice's BTC address.
2. The MPC signs the PSBT; the pending info transitions to `PendingVerify`.
3. Bob (attacker) calls `withdraw_rbf(X, [TxOut { value: alice_amount - fee, script_pubkey: bob_btc_address }], None)`.
4. Because `withdraw_rbf` uses `env::predecessor_account_id()` (Bob) without checking it against `btc_pending_info.account_id` (Alice), the call succeeds.
5. A new RBF `BTCPendingInfo` is created, attributed to Bob, with Bob's BTC address as the output.
6. The MPC signs the replacement PSBT; the replacement transaction is broadcast and confirmed, sending Alice's BTC to Bob. [1](#0-0) [2](#0-1)
