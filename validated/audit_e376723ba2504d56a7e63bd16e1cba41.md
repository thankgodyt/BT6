Audit Report

## Title
`locked_tokens` Mis-Accounting and Relayer Fund Loss via Fire-and-Forget `send_tokens` in Fast-Transfer Finalization — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, the bridge irrevocably mutates `locked_tokens` accounting and marks the fast transfer as finalised **before** the token disbursement to the relayer, which is dispatched with `.detach()`. If `send_tokens` fails, the relayer's pre-paid funds are permanently lost, the fast-transfer record is closed with no retry path, and `locked_tokens` is left in a corrupted state that can permanently block future `fin_transfer` completions for the affected token/chain pair.

## Finding Description

**`process_fin_transfer_to_other_chain` (lines 1997–2040):**

The function executes in this order:

1. `unlock_tokens_if_needed(origin_chain, token, amount)` — decrements `locked_tokens[(origin_chain, token)]` [1](#0-0) 

2. `lock_tokens_if_needed(destination_chain, token, fee)` — increments `locked_tokens[(destination_chain, token)]` [2](#0-1) 

3. `send_tokens(...).detach()` — fires the token transfer to the relayer and **discards the result** [3](#0-2) 

4. `mark_fast_transfer_as_finalised(fast_transfer.id())` — permanently closes the record immediately after the detached call, with no callback [4](#0-3) 

Because `.detach()` drops the promise result, any failure of `send_tokens` (token contract paused, panic, insufficient gas) is silently swallowed. Steps 1, 2, and 4 are **not reverted**.

**`utxo_fin_transfer_fast` (lines 2518–2548):**

The same pattern: `mark_fast_transfer_as_finalised` is called before `send_tokens(...).detach()`, and the codebase itself contains an explicit `// TODO: check how to deal with failed send_tokens` comment at the call site acknowledging the gap. [5](#0-4) [6](#0-5) 

**Contrast with the NEAR-recipient path (`process_fin_transfer_to_near`, lines 1957–1977):**

This path correctly chains `send_tokens` with a `fin_transfer_send_tokens_callback` that calls `revert_lock_actions` on failure, restoring `locked_tokens` and removing the transfer record. [7](#0-6) [8](#0-7) 

**`locked_tokens` is the bridge's sole on-chain invariant** linking token custody to cross-chain obligations: [9](#0-8) 

The `unlock_tokens` function enforces `available >= amount` before decrementing; if `locked_tokens` is under-counted, future legitimate unlocks will panic with `ERR_INSUFFICIENT_LOCKED_TOKENS`: [10](#0-9) 

While a `set_locked_tokens` admin function exists for DAO/`TokenLockController` to manually correct accounting, it does not restore the relayer's lost funds, since the fast-transfer record is permanently finalised with no retry path. [11](#0-10) 

## Impact Explanation

**Permanent relayer fund loss.** The fast-transfer relayer pre-paid the recipient out of their own balance. When `fin_transfer` is called to reimburse them, `send_tokens` may fail silently. The fast transfer is marked finalised (no retry path), so the relayer's tokens are permanently lost. This is a concrete, irreversible loss of bridged funds.

**Permanent `locked_tokens` corruption.** `locked_tokens[(origin_chain, token)]` is decremented without the corresponding tokens leaving the bridge. The bridge now holds more tokens than `locked_tokens` accounts for. Subsequent `unlock_tokens` calls for the same `(origin_chain, token)` pair will eventually hit `ERR_INSUFFICIENT_LOCKED_TOKENS` even though the bridge physically holds the tokens, permanently blocking all future legitimate `fin_transfer` completions for that token/chain pair — a permanent freezing of bridged user funds.

These impacts match the allowed Critical scope: **loss of bridged funds** and **escrow mis-accounting that changes user or protocol balances**.

## Likelihood Explanation

The trigger requires a fast transfer to be in flight when `fin_transfer` is called, and `send_tokens` to fail. Realistic failure modes:

- The token contract (e.g., USDC, USDT) is **paused by its issuer** between fast-transfer execution and canonical `fin_transfer` — a well-documented operational event for regulated stablecoins, not a depegging event.
- The token contract panics due to a bug or upgrade.
- Insufficient gas forwarded to the detached promise: the gas budget calculation uses `saturating_sub`, which can produce a very small value, and the `require!(ft_transfer_call_gas >= MIN_FT_TRANSFER_CALL_GAS, ...)` guard inside `send_tokens` will then **panic the entire transaction**, causing the outer call to fail — but since the accounting mutations already committed, they are not rolled back. [12](#0-11) 

Fast transfers are a core, publicly accessible bridge feature reachable by any trusted relayer via `ft_on_transfer` → `fast_fin_transfer`. The TODO comment in the codebase confirms the developers are aware of the gap.

## Recommendation

Replace the `.detach()` pattern in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast` with a chained callback mirroring the existing `fin_transfer_send_tokens_callback` pattern:

- Chain `send_tokens` with a new callback (e.g., `fast_transfer_send_tokens_callback`) that, on failure, calls `revert_lock_actions` to restore `locked_tokens` and calls `remove_fast_transfer` (or un-finalises the record) so the relayer can retry.
- Move `mark_fast_transfer_as_finalised` into the **success branch** of the callback, not before the promise resolves.
- In `utxo_fin_transfer_fast`, apply the same pattern, resolving the existing TODO.

## Proof of Concept

1. Relayer R executes `fast_fin_transfer` for a USDC transfer from Ethereum to Solana, pre-paying the Solana recipient. `locked_tokens[(Eth, USDC)]` = 1000; fast transfer recorded.
2. USDC contract is paused by Circle.
3. Any relayer calls `fin_transfer` with the canonical Ethereum proof.
4. `fin_transfer_callback` → `process_fin_transfer_to_other_chain`:
   - `unlock_tokens_if_needed(Eth, USDC, 1000)` → `locked_tokens[(Eth, USDC)]` = 0
   - `lock_tokens_if_needed(Sol, USDC, fee)` → `locked_tokens[(Sol, USDC)]` += fee
   - `send_tokens(USDC, R, 1000 - fee, "").detach()` → **fails silently** (USDC paused)
   - `mark_fast_transfer_as_finalised(...)` → fast transfer closed permanently
5. Relayer R never receives their USDC. `locked_tokens[(Eth, USDC)]` = 0 despite the bridge still holding 1000 USDC. All future `fin_transfer` calls for USDC from Ethereum fail with `ERR_INSUFFICIENT_LOCKED_TOKENS`, permanently freezing those user funds.

**Test plan:** Write a NEAR integration test that (a) registers a fast transfer, (b) pauses the mock token contract, (c) calls `fin_transfer` with a valid proof, and (d) asserts that `get_locked_tokens(Eth, USDC)` is 0 while the bridge's token balance is still 1000, and that a subsequent `fin_transfer` for the same token/chain panics with `ERR_INSUFFICIENT_LOCKED_TOKENS`.
