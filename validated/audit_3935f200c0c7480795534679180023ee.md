### Title
Unpermissioned `sign_btc_transaction` Allows Any Caller to Poison a Signature Slot with a Wrong `key_version`, Permanently Blocking Withdrawal Signing - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` carries no caller access control. Any NEAR account can race the legitimate relayer to submit a signing request for any pending withdrawal input, supplying an arbitrary `key_version`. If the MPC accepts the call and the attacker's callback resolves first, the signature slot is permanently marked as signed with an invalid (wrong-key) signature. The legitimate relayer is then blocked by the "Already signed" guard and cannot correct the slot. The resulting PSBT contains an invalid signature, the Bitcoin transaction cannot be broadcast, and the withdrawal is stuck until the operator cancels it — temporarily locking the user's nBTC inside the bridge contract.

### Finding Description

`sign_btc_transaction` is the public entry point for MPC signing of each PSBT input: [1](#0-0) 

There is no `#[access_control_any]` guard, no `assert_one_yocto`, and no check that `env::predecessor_account_id()` matches the withdrawal owner or any whitelisted relayer. The function is callable by any NEAR account.

Inside `internal_sign_btc_transaction`, the only guard is a pre-MPC-call check that the slot is still empty: [2](#0-1) 

Because this check runs **before** the asynchronous MPC call, two concurrent callers (attacker and relayer) both pass it when the slot is still `None`. Both MPC signing requests are dispatched in parallel. Whichever callback resolves first wins the slot.

In the callback, the signature is stored unconditionally if the MPC call succeeded, with no validation that the returned signature is correct for the UTXO's expected public key: [3](#0-2) 

The `key_version` supplied by the caller is forwarded verbatim to the MPC: [4](#0-3) 

If the attacker supplies a `key_version` that the MPC accepts but that corresponds to a different key than the one that controls the UTXO, the stored signature is cryptographically invalid for that input. The slot is now permanently locked ("Already signed"), and the legitimate relayer's subsequent callback is rejected: [5](#0-4) 

When all slots are eventually "signed" (some with poisoned signatures), `is_all_signed()` triggers extraction of the transaction bytes. The resulting Bitcoin transaction carries at least one invalid signature and will be rejected by the Bitcoin network.

The per-account pending-sign limit (default 1) means the user's account is also blocked from initiating a new withdrawal until the stuck pending info is cleaned up: [6](#0-5) 

### Impact Explanation

The user's nBTC is transferred to the bridge contract at withdrawal initiation and is not burned until `verify_withdraw` succeeds. With the signing permanently stuck, the nBTC remains locked inside the bridge contract. The user cannot initiate a new withdrawal (pending-sign capacity is exhausted). Recovery requires operator intervention to cancel the transaction after `max_btc_tx_pending_sec` elapses. This matches **Medium — attacker-triggered temporary locking of bridged funds**.

### Likelihood Explanation

- `sign_btc_transaction` is fully permissionless; any NEAR account can call it.
- NEAR block times are ~1 second; an attacker monitoring the chain can submit their transaction in the same block as the relayer's, making the race realistic.
- The attack scales: a single attacker can target every new withdrawal by watching `GenerateBtcPendingInfo` events.
- Exploitability is conditional on the production MPC accepting a non-zero `key_version`. If the MPC rejects unknown key versions, the callback returns `false` and the slot remains empty (no harm done). This conditionality reduces likelihood but does not eliminate it, as key version 1 may be a valid future version accepted by the MPC.

### Recommendation

1. **Add caller access control** to `sign_btc_transaction`: restrict it to a whitelisted relayer set or to the withdrawal owner, analogous to how `verify_deposit` uses `confirmations_delta` to penalise non-whitelisted callers.
2. **Validate `key_version`** against a contract-configured expected version before dispatching the MPC call, rejecting any value that does not match.
3. **Allow re-signing a slot** if the stored signature fails on-chain validation, or add an operator-callable function to clear a poisoned signature slot without requiring a full cancellation.

### Proof of Concept

1. Alice initiates a withdrawal with two UTXOs as inputs, creating a `BTCPendingInfo` with `signatures: [None, None]`.
2. Attacker observes the `GenerateBtcPendingInfo` event and immediately calls `sign_btc_transaction(pending_id, 0, 999)` (wrong `key_version`), attaching the required deposit.
3. Relayer calls `sign_btc_transaction(pending_id, 0, 0)` (correct `key_version`) in the same or next block.
4. Both MPC calls are dispatched. If the attacker's callback resolves first, `signatures[0]` is set to a signature produced under key version 999 (a different key than the UTXO's controlling key).
5. Relayer's callback hits `require!(signatures[0].is_none(), "Already signed")` and returns `false`.
6. Relayer signs slot 1 correctly. `is_all_signed()` returns `true`; the PSBT is extracted with an invalid signature for input 0.
7. The signed transaction is broadcast to Bitcoin but rejected (invalid signature).
8. Alice's nBTC remains locked in the bridge. Her account's `btc_pending_sign_ids` is non-empty, blocking new withdrawals. Operator must wait for `max_btc_tx_pending_sec` to cancel.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
