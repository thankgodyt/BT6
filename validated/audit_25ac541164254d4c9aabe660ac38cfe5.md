### Title
Degenerate `BlockSupportsPeras` Instance Unconditionally Accepts Any Peras Certificate Without Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance for `StandardHash blk` implements `validatePerasCert` to unconditionally return `Right` (success) without performing any cryptographic or semantic validation. Because this instance is the only one in the codebase (it is explicitly marked as a TODO placeholder for all block types), any crafted Peras certificate submitted by an unprivileged peer is accepted as valid, enabling unauthorized chain-weight manipulation via bogus certificate boosts.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory entry point for validating Peras certificates before they influence chain selection. The sole, catch-all instance (lines 320–389 of `SupportsPeras.hs`) implements this function as:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No checks are performed on:
- The certificate's round number (whether it corresponds to a valid current or past round)
- The boosted block's existence or position on the chain
- Any aggregate BLS signature validity
- Whether the certificate was issued by a legitimate quorum of committee members

The analog to the Spigot vulnerability is direct. In the Spigot, `mapping(bytes4 => bool)` was not scoped to a specific contract address, so any contract could be called with a whitelisted selector. Here, `validatePerasCert` is not scoped to any specific round, epoch, or cryptographic context — any certificate passes validation regardless of its provenance. Just as the Spigot's whitelist was a single-dimensional key when it needed to be two-dimensional (selector → contract), the certificate validation here is zero-dimensional: it accepts everything unconditionally.

A secondary, structurally identical issue exists in `AcrossEpochs.hs`. The function `getVotingCommitteeForElection`, which is supposed to scope a committee lookup to a specific `ElectionId`, ignores its `_electionId` argument entirely and throws `error "TODO: implement getVotingCommitteeForElection"`. This means the election-ID-to-committee binding — the exact scoping that prevents cross-election certificate reuse — is absent. However, since this path crashes rather than silently bypasses, its primary observable impact is a node crash (DoS), which is disqualified per the rules. The `validatePerasCert` path is the exploitable one.

---

### Impact Explanation

A validated `PerasCert` contributes a `vpcCertBoost` (chain weight boost equal to `perasWeight params`) to the block it references. If any certificate is accepted without validation, an adversary can:

1. Craft a `PerasCert` with `pcCertRound = anyRound` and `pcCertBoostedBlock = someArbitraryBlock` (including a non-canonical or attacker-controlled block).
2. Submit it to an honest node via the Peras certificate diffusion miniprotocol.
3. The node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
4. The boosted block gains artificial chain weight equal to `perasWeight params`.
5. The honest node's chain selection may prefer the artificially boosted (non-canonical) chain over the honest chain.

This is a chain selection manipulation attack. It matches the **High** impact category: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The degenerate instance is a Haskell catch-all (`instance StandardHash blk => BlockSupportsPeras blk`). No more specific `BlockSupportsPeras` instance exists in the repository for the production Cardano block type — the TODO comment and linked issue (`tweag/cardano-peras#73`) confirm this is the only active implementation. Any peer connected via the Peras certificate diffusion protocol can trigger this path by sending a single crafted certificate message. No special privileges, keys, or stake are required.

---

### Recommendation

Implement a proper `BlockSupportsPeras` instance for the production Cardano block type that:

1. Verifies the certificate's round number is within the valid range for the current epoch.
2. Verifies the boosted block exists and is on the node's preferred chain.
3. Verifies the aggregate BLS signature against the committee's public keys for the correct epoch.
4. Verifies that the certificate was issued by a legitimate quorum of committee members (matching the `implVerifyCert` logic already present in `WFALS.hs`).
5. Implements `getVotingCommitteeForElection` in `AcrossEpochs.hs` to properly scope committee selection to the `ElectionId`, using a two-dimensional lookup (`ElectionId → Epoch → Committee`) rather than the current stub.
