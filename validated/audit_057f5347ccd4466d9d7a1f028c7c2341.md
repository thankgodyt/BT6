### Title
Unvalidated `refund_address` Accepted at `request_refund` Causes `.expect()` Panic in `build_refund_output`, Blocking Zcash Refund Execution - (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` stores an attacker-supplied `refund_address` string with no format validation. When `execute_refund` later calls `build_refund_output`, it calls `Address::parse(refund_address, config.chain).expect("Invalid refund address")`. For a Zcash Regtest address submitted against a `ZcashMainnet`/`ZcashTestnet` deployment, `Address::parse` returns `Err`, and `.expect()` panics, reverting the NEAR transaction. The refund request remains in storage, so every subsequent `execute_refund` call for that UTXO also panics. The DAO can reject and re-create the request, but the attacker can immediately re-submit another malformed request, creating a continuous griefing loop that requires ongoing operator intervention.

### Finding Description

**Step 1 — Public entrypoint, no address validation.**

`request_refund` is `#[payable]` and `#[pause(except(roles(Role::DAO)))]` with no method-level `#[trusted_relayer]` guard (the block-level `#[trusted_relayer]` on the enclosing `impl` is a no-op: `verify_refund_finalize` in the same block carries its own method-level `#[trusted_relayer]`, and `reject_refund` in the same block has internal role checks — both would be redundant if the block-level attribute already gated access). [1](#0-0) 

`internal_request_refund` and `request_refund_callback` perform no format check on `refund_address`; the string is stored verbatim in `RefundRequest.refund_address`. [2](#0-1) 

**Step 2 — `Address::parse` returns `Err` for a Regtest address.**

`zcash_chain_from_network` explicitly returns `Err` for `NetworkType::Regtest`: [3](#0-2) 

`Address::parse` for `ZcashMainnet`/`ZcashTestnet` calls `ZcashAddress::try_from_encoded` (which succeeds for any syntactically valid Zcash address, including Regtest) and then `convert_if_network::<Self>(NetworkType::Main)`. Because the address carries `NetworkType::Regtest`, `convert_if_network` invokes `try_from_transparent_p2pkh` (or the unified/p2sh variant), which calls `zcash_chain_from_network(Regtest)` → `Err`, propagating a `ConversionError`. `Address::parse` maps this to `Err(String)`. [4](#0-3) 

**Step 3 — `.expect()` in `build_refund_output` panics.** [5](#0-4) 

`build_refund_output` is called from both the Bitcoin refund path: [6](#0-5) 

and the Zcash transparent refund path: [7](#0-6) 

The panic reverts the NEAR transaction. The refund request is not removed (removal only happens in `verify_refund_finalize_callback` or `reject_refund`), so every subsequent `execute_refund` call for the same UTXO panics identically.

---

### Impact Explanation

The deposit UTXO's refund pipeline is stuck. The DAO can call `reject_refund` to remove the bad request and then re-submit `request_refund` with a valid address. However, the attacker can immediately re-submit another `request_refund` with a new malformed address (the only cost is the attached storage deposit). This creates a continuous griefing loop requiring ongoing operator intervention to keep the refund unblocked. No funds are directly stolen, but user funds are temporarily locked and the refund pipeline for the affected UTXO is degraded until the operator wins the race.

---

### Likelihood Explanation

- `request_refund` is publicly callable with only a NEAR storage deposit as cost.
- No address format validation exists at submission time.
- The Regtest address encoding is well-documented and trivially constructable.
- The panic path is deterministic and locally reproducible.
- The griefing loop is cheap: each re-submission costs only the storage deposit.

---

### Recommendation

Validate `refund_address` format at `request_refund_callback` time (before storing it) by calling `Address::parse` and returning an error if it fails, rather than deferring parsing to `execute_refund`. Replace the `.expect()` in `build_refund_output` with proper error propagation so that a bad stored address causes a graceful `require!` failure rather than a panic.

### Proof of Concept

1. Deploy the Zcash bridge with `config.chain = ZcashMainnet`.
2. Make a real ZEC deposit without setting `deposit_msg.refund_address`.
3. Call `request_refund` with `refund_address = "zregtestsapling..."` (any valid Regtest Zcash address encoding) and a valid `tx_bytes`/`proof` for the deposit.
4. `request_refund_callback` stores the request without validating the address.
5. Call `execute_refund` for the UTXO storage key.
6. `build_refund_output` calls `Address::parse("zregtestsapling...", ZcashMainnet)` → `zcash_chain_from_network(Regtest)` → `Err` → `.expect("Invalid refund address")` → **panic**.
7. The NEAR transaction reverts; the refund request remains in storage.
8. Every subsequent `execute_refund` call panics identically.
9. DAO calls `reject_refund`; attacker immediately re-calls `request_refund` with another Regtest address → loop repeats. [8](#0-7) [9](#0-8)
