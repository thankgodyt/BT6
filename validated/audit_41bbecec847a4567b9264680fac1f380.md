Audit Report

## Title
Zero-Normalized Amount Causes Permanent Transfer Lock — (`near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates an outbound NEAR→EVM transfer with an amount smaller than `10^(origin_decimals − decimals)`, `init_transfer_internal` commits the transfer to `pending_transfers` and burns/locks the user's tokens before any normalization check occurs. Every subsequent call to `sign_transfer` permanently reverts with `InvalidAmountToTransfer` because the normalized amount is zero. No cancellation or refund path exists, so the funds are frozen forever.

## Finding Description
`normalize_amount` performs floor division: `amount / 10^(origin_decimals − decimals)`. For a token registered with `origin_decimals = 24` and `decimals = 18`, any amount below `1_000_000` yocto-units produces `0`.

The only zero-amount guard is inside `sign_transfer` (lines 482–485), which executes *after* `init_transfer_internal` has already:
1. Inserted the transfer into `pending_transfers` via `add_transfer_message`.
2. Burned or locked the user's tokens via `burn_tokens_if_needed` / `lock_tokens_if_needed`.
3. Returned `U128(0)` to the NEP-141 contract, signalling full consumption of the transferred tokens.

`init_transfer_internal` contains no pre-check that `normalize_amount(amount_without_fee, decimals) > 0`. Once stored, the only removal paths for a `pending_transfers` entry are `claim_fee_callback` and `fin_transfer_callback`, both of which require proof of destination-chain finalization that will never exist for a transfer that can never be signed. There is no user-callable cancel or refund function.

## Impact Explanation
User NEP-141 tokens (or wNEAR) are permanently frozen inside the bridge contract. The NEP-141 contract receives `0` as the refund amount from `ft_on_transfer`, so it does not return tokens to the sender. Every call to `sign_transfer` for the affected `transfer_id` reverts unconditionally. This constitutes permanent freezing of bridged funds — a concrete match for the critical impact category "permanent freezing of bridged funds."

## Likelihood Explanation
Any unprivileged user can trigger this by calling `ft_transfer_call` on a registered NEAR token with a small amount. For the common 24→18 decimal pairing, amounts below `1_000_000` yocto-units (a plausible "dust" or rounding-error amount) silently trigger the bug. The `ft_on_transfer` call succeeds and returns no error to the sender, so the user receives no on-chain indication that their funds are lost.

## Recommendation
Add a normalization check inside `init_transfer_internal` (or at the entry of `ft_on_transfer`) before the transfer is committed to storage. If the normalized amount is zero, return the full amount to the caller as a refund:

```rust
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` but places it at the correct, earlier point in the lifecycle — before tokens are burned or locked and before the transfer is committed to storage.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18`.
2. Call `ft_transfer_call` on that token, sending `500_000` yocto-units to the bridge with a valid `InitTransferMsg` (fee = 0).
3. `ft_on_transfer` succeeds; the transfer is stored in `pending_transfers`; 500,000 units are burned/locked; `U128(0)` is returned to the NEP-141 contract (no refund).
4. Call `sign_transfer` for the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin: 24, decimals: 18})` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0, …)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. Repeat step 4 indefinitely — it always reverts. The 500,000 yocto-units are permanently locked with no recovery path.
