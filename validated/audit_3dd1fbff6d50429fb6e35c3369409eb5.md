### Title
User Exit/Claim Methods Blocked by `#[pause]` Modifier — Malicious or Compromised PauseManager Can Permanently Lock User Funds - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `claim_lost_found` and `execute_refund` functions in the `satoshi-bridge` contract carry a `#[pause(except(roles(Role::DAO)))]` attribute. A `PauseManager`-role holder can pause the contract and prevent users from recovering nBTC already held in the `lost_found` ledger or from executing approved refund requests. If the DAO key is subsequently lost or ownership is renounced while the contract remains paused, those user funds are permanently locked with no recovery path.

### Finding Description

The contract is decorated with `Pausable` from `near-plugins` and exposes a `PauseManager` role that can pause all functions not explicitly exempted. [1](#0-0) 

Two user-facing exit/recovery functions carry the pause guard:

**1. `claim_lost_found`** — recovers nBTC that was already transferred into the bridge and placed in the `lost_found` ledger (e.g., after a `cancel_withdraw` whose refund callback failed): [2](#0-1) 

The `lost_found` map holds nBTC that has already left the user's wallet and is sitting inside the bridge contract. The only way to retrieve it is through this function.

**2. `execute_refund`** — executes a previously approved refund request, sending the deposit UTXO back to the user's BTC address: [3](#0-2) 

Users pay a non-refundable storage deposit when calling `request_refund`, and their BTC UTXO is already locked in the bridge's script address. If `execute_refund` is blocked, the BTC cannot be returned.

**3. `ft_on_transfer` (withdrawal initiation)** — the NEP-141 callback that processes a user's `ft_transfer_call` to initiate a BTC withdrawal: [4](#0-3) 

When paused, this reverts and the NEP-141 standard returns the tokens to the sender, so this case causes temporary denial-of-service rather than permanent lock. However, combined with the above two cases, the overall exit surface is fully blocked.

The `PauseManager` role is separate from `DAO` and is granted at initialization: [5](#0-4) 

The `except(roles(Role::DAO))` carve-out means only the DAO can bypass the pause — ordinary users cannot call `claim_lost_found` or `execute_refund` while the contract is paused.

### Impact Explanation

**Medium — attacker-triggered temporary or permanent locking of bridged user funds.**

- Funds in `lost_found` are nBTC already transferred out of the user's wallet and held by the bridge. Pausing `claim_lost_found` makes them irrecoverable for the duration of the pause.
- BTC UTXOs backing pending refund requests are locked in the bridge's script address. Pausing `execute_refund` prevents the MPC signing pipeline from returning them.
- If the DAO key is lost or ownership is renounced while the contract is paused, both categories of funds are permanently locked with no on-chain recovery mechanism.

### Likelihood Explanation

**Low** — requires a malicious or compromised `PauseManager`-role holder. The role is granted at initialization to the deployer and can be extended to other accounts via `add_super_admin`. A compromised operator key or a rogue insider is the realistic trigger. The scenario where ownership is subsequently renounced (making the lock permanent) is an additional escalation step.

### Recommendation

Remove `#[pause(except(roles(Role::DAO)))]` from `claim_lost_found` and `execute_refund` (and consider `ft_on_transfer`). These are user-exit paths that should remain callable regardless of contract pause state. Pause logic should be restricted to deposit/mint entry points (`verify_deposit_v2`, `ft_on_transfer` for new withdrawals) while always allowing users to recover funds already committed to the bridge.

### Proof of Concept

1. User calls `ft_transfer_call` → bridge's `ft_on_transfer` processes a `Withdraw` message → withdrawal is later cancelled via `cancel_withdraw` → the nBTC refund callback fails → nBTC is recorded in `data.lost_found[user]`.
2. A `PauseManager` account calls `pa_pause_feature("claim_lost_found")` (or a global pause).
3. User calls `claim_lost_found` → the `#[pause]` macro checks the paused state → the call panics with a pause error.
4. User's nBTC remains locked in `data.lost_found` with no alternative recovery function available.
5. If the DAO key is subsequently lost or `acl_revoke_super_admin` is called on all admins, the pause cannot be lifted and the funds are permanently locked.

The same sequence applies to `execute_refund`: after `request_refund` is accepted and the timelock passes, a paused contract blocks the MPC signing step, leaving the user's BTC UTXO stranded in the bridge script address indefinitely. [2](#0-1) [3](#0-2)
