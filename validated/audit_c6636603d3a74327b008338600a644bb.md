### Title
`safe_mint` Permanently Traps nBTC in Bridge When Recipient Storage Account Is Unregistered — (`contracts/nbtc/src/lib.rs`)

### Summary
When `safe_mint` is called for a recipient who has not performed `storage_deposit` on the nBTC contract, the function mints the full token amount to the bridge's own balance and returns `U128(0)` to the caller. The satoshi-bridge receives a successful cross-contract call result of 0 and has no mechanism to distinguish this from a zero-amount mint. The minted tokens are permanently stranded in the bridge's nBTC balance, and the user's BTC deposit is consumed without the user ever receiving nBTC.

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` (lines 101–124) executes in two phases:

**Phase 1 — unconditional mint to bridge:**
```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
```
This always runs, crediting the full `amount` to the satoshi-bridge's nBTC balance.

**Phase 2 — conditional transfer to user:**
```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
// ft_transfer / ft_transfer_call to account_id
```
If the recipient has no registered storage account, the function returns `U128(0)` immediately. No transfer occurs. No error is raised. The tokens remain in the bridge's balance.

The satoshi-bridge's only recovery path for stranded nBTC is `transfer_nbtc_callback` in `token_transfer.rs` (lines 54–75), which adds to `lost_found` only when the underlying promise **fails**:

```rust
if !promise_success {
    self.data_mut()
        .lost_found
        .entry(account_id.clone())
        ...
}
```

A successful `safe_mint` returning `U128(0)` is a **successful** promise result. The bridge's deposit callback sees success and does not invoke the `lost_found` path. The user's deposit is silently discarded.

### Impact Explanation

The user's BTC UTXO is consumed by the bridge's deposit verification flow and added to the bridge's available UTXO pool. The corresponding nBTC is minted to the bridge's own balance. The user receives zero nBTC and has no on-chain recourse: there is no `lost_found` entry, no refund path, and no admin function in the nBTC contract to transfer the stranded tokens back. This constitutes a **permanent, complete loss of the user's BTC deposit** — matching the "significant loss or permanent locking of user funds" critical impact category.

### Likelihood Explanation

NEP-141 storage registration is a prerequisite that many users overlook, especially first-time bridge users or users interacting via integrations that do not auto-register. The deposit flow on the Bitcoin side (sending BTC to a derived address) does not enforce or verify that the NEAR recipient has pre-registered on the nBTC contract. Any user who deposits BTC before calling `storage_deposit` on the nBTC contract will trigger this path. The condition is reachable by any unprivileged user with no special access required.

### Recommendation

Remove the silent early-return. Instead, either:

1. **Revert if unregistered:** Do not call `internal_deposit` at all if `account_id` is unregistered, so the bridge's deposit callback sees a failure and can handle it (e.g., via `lost_found` or a retry).
2. **Auto-register:** Call `internal_register_account(&account_id)` before `internal_deposit`, funded by the attached deposit, so the transfer always succeeds.
3. **Populate `lost_found` on zero return:** In the satoshi-bridge's `safe_mint` callback, treat a `U128(0)` return as a failed delivery and add the amount to `lost_found[account_id]` so the user can later claim their tokens after registering.

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address on the Bitcoin network.
2. Alice has **not** called `storage_deposit` on the nBTC contract.
3. A relayer submits the inclusion proof; the satoshi-bridge verifies it and calls `nbtc.safe_mint(alice, 1_000_000, None)`.
4. Inside `safe_mint`: `internal_deposit(&bridge_id, 1_000_000)` runs — bridge's nBTC balance increases by 1,000,000.
5. `self.token.accounts.get(&alice)` returns `None` → function returns `U128(0)`.
6. The satoshi-bridge's deposit callback receives a **successful** promise result of `0`. No `lost_found` entry is created for Alice.
7. Alice's BTC UTXO is now in the bridge's available pool. Alice has 0 nBTC. The 1,000,000 nBTC units sit permanently in the bridge's own balance with no recovery path.

```rust
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
```
