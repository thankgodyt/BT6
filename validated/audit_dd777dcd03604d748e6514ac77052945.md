### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance used for all block types contains a stub `validatePerasCert` implementation that unconditionally accepts every inbound Peras certificate without performing any cryptographic or structural verification. Any unprivileged peer connected via the Peras cert diffusion miniprotocol can inject arbitrary certificates into the node's `PerasCertDB`, triggering false chain-weight boosts and corrupting chain selection.

---

### Finding Description

The vulnerability class in the reference report is **missing caller-identity enforcement**: a function accepts a caller-supplied parameter (the `from` address) as the authoritative identity instead of verifying the actual sender, allowing any caller to act on behalf of an arbitrary identity. The direct analog here is that `validatePerasCert` accepts a caller-supplied `PerasCert` value as authoritative without verifying any cryptographic proof of the sender's identity or the certificate's legitimacy.

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve every inbound certificate before it is stored. The catch-all instance covering all block types is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub returns `Right` for every certificate regardless of its content. The `PerasCert` type carries only a round number and a block point — no aggregate signature, no quorum proof, no committee membership witness — and the stub does not check any of these. [2](#0-1) 

This stub is wired directly into the production cert-diffusion inbound handler via `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is then passed directly to `objectDiffusionInbound` in `mkHandlers`, the function that builds all live node-to-node protocol handlers:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

`processCerts`, the inbound batch processor, calls `validateCert` on each certificate not already in the database and stores every certificate that passes:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [5](#0-4) 

Because `validateCert` is the stub that always returns `Right`, every certificate sent by any peer passes this check and is stored.

---

### Impact Explanation

Peras certificates are the mechanism by which the Peras protocol assigns weight boosts to blocks during chain selection. A stored `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`, which is added to the block number of the boosted block's fragment when comparing candidate chains via `WeightedSelectView`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5) 

An attacker who injects a forged certificate for a round and block of their choosing causes the victim node to assign an artificial weight boost to that block. This can make the victim prefer a non-canonical or adversary-controlled chain over the honest chain, constituting a chain-selection safety failure. The impact matches: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The Peras cert diffusion miniprotocol is open to any peer that establishes a node-to-node connection. No authentication, stake ownership, or prior relationship is required. The `PerasCert` wire type is trivially constructable (round number + block point). The attacker needs only to:

1. Connect to the target node.
2. Send a `PerasCert` with a chosen `pcCertRound` and `pcCertBoostedBlock`.
3. The certificate passes `validatePerasCert` unconditionally and is stored.

This is directly analogous to the reference report's frontrunning attack: just as any caller could supply an arbitrary `from` address to `mintSynth()`, any peer can supply an arbitrary `PerasCert` to the cert diffusion handler and have it accepted.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The aggregate BLS/committee signature over the certificate's `(electionId, candidate)` pair.
- That the claimed voters form a valid quorum (sufficient stake) according to the on-chain stake distribution for the relevant epoch.
- That the boosted block point is a known, valid block on the node's chain.

Until real cryptographic plumbing is in place, the cert diffusion inbound handler should reject all inbound certificates rather than accept them unconditionally, to avoid the false-weight-boost attack surface.

---

### Proof of Concept

1. Attacker node connects to victim via the Peras cert diffusion miniprotocol (enabled by `hPerasCertDiffusionClient` in `mkHandlers`).
2. Attacker sends a `PerasCert { pcCertRound = r, pcCertBoostedBlock = p }` where `p` is the tip of an adversary-controlled fork.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The certificate is stored via `ChainDB.addPerasCertAsync`, triggering chain-selection re-evaluation.
5. `weightedSelectView` now assigns the full Peras weight boost to the adversary's fork, causing the victim to switch to it. [7](#0-6) [5](#0-4) [4](#0-3)
