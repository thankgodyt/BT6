### Title
Peras Certificate Validation Bypass via No-Op `validatePerasCert` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional `Right` — it performs zero cryptographic checks on any incoming Peras certificate. This is the only instance in the codebase. The production object-diffusion path calls this function before adding certificates to the `PerasCertDB` and triggering chain selection. An unprivileged peer can therefore inject arbitrary crafted Peras certificates that are accepted without any signature, committee-membership, or VRF verification, and those certificates can shift chain selection toward a non-canonical chain.

---

### Finding Description

**Root cause — no-op `validatePerasCert`:**

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory certificate-validation gate: [1](#0-0) 

The only instance in the entire codebase is the degenerate universal instance, explicitly marked as a placeholder: [2](#0-1) 

The implementation unconditionally returns `Right` with the certificate and the configured boost weight, skipping every check: aggregate BLS signature verification, committee-membership verification, VRF proof verification for non-persistent voters, round-number sanity, and boosted-block existence. No Cardano-specific override exists — `grep` for `validatePerasCert` returns only `SupportsPeras.hs` (definition) and `ObjectPool/PerasCert.hs` (call site).

**Production call path:**

`makePerasCertPoolWriterFromChainDB` — the writer used in the live object-diffusion layer — passes `validatePerasCert mkPerasParams` directly to `processCerts`: [3](#0-2) 

`processCerts` partitions the batch by the result of `validateCert`. If all results are `Right`, every certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which adds it to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block, potentially switching the node's selected chain: [5](#0-4) 

**Analog to the reported issue:**

In BazaarManagerBlast, `configureClaimableGas` is called (setup) but no `claimGas` method exists (missing enforcement). Here, `validatePerasCert` is called (setup) but the implementation never enforces any cryptographic invariant (missing enforcement). The configured validation gate is present in the call graph but does nothing.

---

### Impact Explanation

**Critical / High.** An unprivileged peer that speaks the Peras object-diffusion mini-protocol can send a batch of certificates with arbitrary `pcCertRound` and `pcCertBoostedBlock` fields. Because `validatePerasCert` always returns `Right`, every certificate passes validation and is inserted into the `PerasCertDB`. Each accepted certificate carries the full `perasWeight` boost. If the boosted block is present in the `VolatileDB`, chain selection is immediately re-run with the fraudulent boost applied, and the node may switch to a non-canonical fork that would otherwise lose the honest chain-selection comparison. This constitutes:

- **Bypass of Peras certificate checks enabling unauthorized certificate acceptance** (Critical scope).
- **Chain-selection manipulation letting an unprivileged peer make an honest node prefer a non-canonical chain** (High scope).

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer without any privileged key material. The only precondition is that Peras is enabled in the node configuration (the CHANGELOG notes it is off by default today, but the production code path is wired and the feature is actively being deployed). Once enabled, exploitation requires only sending a well-formed CBOR-encoded `PerasCert` with a chosen `pcCertBoostedBlock` pointing to a block already in the peer's `VolatileDB`.

---

### Recommendation

Replace the degenerate `validatePerasCert` implementation with a real cryptographic check before the feature is enabled in production. Concretely:

1. Implement a proper `BlockSupportsPeras (CardanoBlock c)` instance (or the appropriate era-specific instance) that verifies the aggregate BLS signature against the reconstructed committee public key, verifies committee-membership and stake for each listed voter, and verifies VRF proofs for non-persistent voters.
2. Remove the universal `instance StandardHash blk => BlockSupportsPeras blk` or restrict it to a compile-time error so that missing instances are caught at build time rather than silently falling back to the no-op.
3. Track resolution of the linked issue (`cardano-peras/issues/120`) as a hard prerequisite for enabling Peras on any network.

---

### Proof of Concept

1. Connect to a node with Peras enabled as an ordinary peer.
2. Craft a `PerasCert` value with `pcCertRound = <any round>` and `pcCertBoostedBlock = <hash of a block known to be in the peer's VolatileDB on a minority fork>`.
3. Send the certificate via the Peras object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate is added to `PerasCertDB`; `chainSelSync` re-runs chain selection with the fraudulent boost weight applied to the minority fork.
6. If the boosted fork's weighted length now exceeds the honest chain's weighted length, the node switches to the attacker-chosen fork — accepting a non-canonical chain without any legitimate quorum of Peras votes.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
