### Title
Unauthenticated MPC Signing Trigger Allows Any Account to Force-Complete Any Pending Withdrawal — (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

---

### Summary

`sign_btc_transaction` performs no ownership check against the caller. Any unprivileged NEAR account can supply a known `btc_pending_sign_id` and trigger MPC signing for another user's pending withdrawal or refund transaction, directly analogous to the reported pattern of performing a privileged action using only an identifier with no authentication layer.

---

### Finding Description

`sign_btc_transaction` is the public entry point that drives the chain-signatures MPC to produce a Bitcoin ECDSA signature for a pending PSBT: [1](#0-0) 

The function retrieves the `BTCPendingInfo` keyed by `btc_pending_sign_id`, asserts it is in the `PendingSign` state, and immediately calls `internal_sign_btc_transaction`. At no point is `env::predecessor_account_id()` compared to `btc_pending_info.account_id`. The internal implementation confirms the same absence: [2](#0-1) 

The `btc_pending_sign_id` is the PSBT-derived pending ID emitted publicly in the `GenerateBtcPendingInfo` event at withdrawal creation time: [3](#0-2) 

Once all inputs are signed, the callback emits the fully-signed transaction bytes in a `SignedBtcTransaction` event and transitions the record to `PendingVerify`, at which point the user can no longer invoke `withdraw_rbf` to cancel or redirect the transaction: [4](#0-3) 

The user's only self-service cancellation path is `withdraw_rbf`; `cancel_withdraw` is gated to `Role::DAO` or `Role::Operator`: [5](#0-4) [6](#0-5) 

---

### Impact Explanation

Once an attacker force-completes signing, the signed transaction bytes are public (emitted on-chain) and can be broadcast to Bitcoin by anyone. The user loses the ability to cancel or RBF their withdrawal. If the user had submitted an incorrect `target_btc_address` or changed their mind, the attacker's action permanently locks the outcome: the BTC is irrevocably committed to the address encoded in the PSBT at creation time, with no operator-free recovery path. This constitutes attacker-triggered permanent locking of bridged funds and stuck bridge state requiring operator intervention.

**Impact: Medium**

---

### Likelihood Explanation

The `btc_pending_sign_id` is derived from the PSBT and broadcast in the `GenerateBtcPendingInfo` on-chain event at the moment of withdrawal creation. Any observer of NEAR chain events can collect all live pending IDs. The attacker must attach a small NEAR deposit (forwarded to the chain-signatures contract as the MPC fee), which is a negligible cost. No privileged role, leaked key, or off-chain coordination is required.

**Likelihood: High**

---

### Recommendation

Add a caller-ownership assertion at the top of `sign_btc_transaction`, before any state reads or cross-contract calls:

```rust
let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
require!(
    env::predecessor_account_id() == btc_pending_info.account_id
        || self.acl_has_any_role(
            vec![Role::DAO.into(), Role::UnrestrictedRelayer.into()],
            env::predecessor_account_id()
        ),
    "Not authorized to sign this transaction"
);
```

This mirrors the pattern already used in `cancel_withdraw` and `active_utxo_management`, where the acting account is either the record owner or a privileged role.

---

### Proof of Concept

1. Alice calls `ft_on_transfer` on the nBTC token contract with a `Withdraw` message specifying `target_btc_address = "bc1q…alice"`. The bridge creates a `BTCPendingInfo` with `account_id = alice.near` and emits `GenerateBtcPendingInfo { btc_pending_id: "deadbeef…" }`.

2. Alice realizes she entered the wrong BTC address and prepares to call `withdraw_rbf("deadbeef…", corrected_output)`.

3. Bob, an unprivileged NEAR account, observes the `GenerateBtcPendingInfo` event and calls:
   ```
   sign_btc_transaction(
       btc_pending_sign_id: "deadbeef…",
       sign_index: 0,
       key_version: 0
   )
   ```
   with sufficient attached NEAR for the MPC fee.

4. The MPC produces a valid ECDSA signature. The `sign_btc_transaction_callback` stores it, and if all inputs are now signed, transitions the record to `PendingVerify` and emits `SignedBtcTransaction` with the raw signed transaction bytes.

5. Alice's `withdraw_rbf` call now fails because the record is no longer in `PendingSign` state. Bob (or any observer) broadcasts the signed transaction to Bitcoin. Alice's BTC is irrevocably sent to the wrong address with no self-service recovery.

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
