### Title
`stakeAboveThreshold` compares unnormalized `PerasVoteStake` against a relative quorum threshold without normalization, enabling Peras certificate forgery with insufficient stake — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` directly compares the sum of `PerasVoteStake` values against the relative quorum threshold (`3/4 + 2/100 = 0.77`) without normalizing by the total committee stake. The code itself documents this as an unresolved design gap. If `PerasVoteStakeDistr` is populated with absolute ledger stake values (the natural representation from the ledger), any single vote from a pool with more than 0.77 lovelace of stake would exceed the threshold, allowing a Peras certificate to be forged for any block without the required 3/4 of total stake. This is the direct analog of the external report's static denominator bug: the denominator (total stake) is absent from the quorum comparison, making the threshold either trivially reachable or permanently unreachable depending on the unit of the stored stake values.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

The function compares the raw sum of `PerasVoteStake` values against the relative quorum threshold:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake        = unPerasVoteStake voteStake          -- sum of per-voter stakes
  quorumThreshold = unPerasQuorumStakeThreshold ...  -- 3/4 (relative)
  safetyMargin    = ...                              -- 2/100 (relative)
```

The code's own comment explicitly flags the unit mismatch:

> *"TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally."*

A second comment on `PerasVoteStake` itself admits:

> *"NOTE: At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake)."*

`PerasVoteStakeDistr` is a `Map PerasVoterId PerasVoteStake` populated externally via `STM m PerasVoteStakeDistr`. There is no enforcement that the stored values are normalized. If they are absolute lovelace values (the natural representation from the Cardano ledger), then `totalVoteStake` after a single vote from a pool with, say, 1 billion lovelace of stake would be `1_000_000_000 % 1`, which is vastly greater than `0.77`, and `stakeAboveThreshold` would return `True` immediately.

**Quorum check call chain (reachable from the network):**

1. Peer sends a `PerasVote` over the network mini-protocol.
2. `processVotes` in `ObjectPool/PerasVote.hs` calls `validatePerasVote mkPerasParams sd vote` — the degenerate instance only checks that the voter ID is present in the stake distribution; no signature is verified.
3. The validated vote is added to the `PerasVoteDB` via `addVote`.
4. `implAddVote` calls `updatePerasRoundVoteStates`, which calls `updateCandidateVoteState`, which calls `votesReachQuorum`, which calls `stakeAboveThreshold`.
5. If the stored `PerasVoteStake` is absolute, the threshold is exceeded on the first vote, and `forgePerasCert` is called, producing a `ValidatedPerasCert`.

**Analog to the external report:**

| External report (DeXe) | This codebase (Ouroboros Consensus) |
|---|---|
| `_nftInfo.totalPowerInTokens` is a static initial value used as the quorum denominator | `PerasVoteStake` values are stored without normalization; the total committee stake is never used as a denominator |
| `ERC721Power.totalPower()` can drop to zero, making the denominator over-inflated | If `PerasVoteStake` is absolute, the numerator (sum of votes) is over-inflated relative to the relative threshold |
| Result: quorum impossible to reach | Result: quorum trivially reachable with a single vote (or permanently unreachable if values are tiny fractions) |

### Impact Explanation

**Critical — Bypass of Peras voting/certificate checks.**

If `PerasVoteStakeDistr` is populated with absolute ledger stake values, a single crafted vote from any known stake pool ID (all pool IDs are public on-chain) would cause `stakeAboveThreshold` to return `True`, triggering `forgePerasCert`. The resulting `ValidatedPerasCert` would boost the chain weight of an arbitrary block by `perasWeight = 15` slots, directly affecting chain selection. An adversary could:

- Force honest nodes to prefer an adversarially chosen block by boosting it with a fraudulent certificate.
- Disrupt the Peras cooldown/ignoring-round state machine by injecting certificates for arbitrary rounds.

This constitutes a bypass of Peras certificate verification and a chain-selection manipulation, matching the "Critical — Bypass of certificate/vote verification checks" and "High — Chain selection bug" impact categories.

---

### Likelihood Explanation

**Medium-High.** The entry path is fully reachable from an unprivileged peer:

1. The `processVotes` function is wired into the network layer and accepts votes from any connected peer.
2. The degenerate `validatePerasVote` instance performs no signature verification — only a map lookup on the voter ID.
3. Stake pool IDs are public information derivable from the ledger state.
4. The normalization gap is explicitly documented as unresolved, meaning it is not a transient oversight but a structural design gap that will persist until explicitly fixed.

The only mitigating factor is that the `BlockSupportsPeras` instance is currently a placeholder stub (marked with multiple `TODO` comments), so Peras voting is not yet active on mainnet. However, the production infrastructure (`PerasVoteDB`, `processVotes`, `stakeAboveThreshold`) is already wired into the node and will be activated as Peras is deployed.

---

### Recommendation

1. **Normalize `PerasVoteStake` before comparison.** `stakeAboveThreshold` must divide the accumulated vote stake by the total committee stake before comparing against the relative threshold. The total committee stake must be passed in or computed from the `PerasVoteStakeDistr`.

2. **Enforce units at the type level.** Introduce distinct newtypes for absolute stake (`AbsolutePerasVoteStake`) and relative stake (`RelativePerasVoteStake`) so that the compiler prevents passing absolute values to `stakeAboveThreshold`.

3. **Resolve the open design question.** The comment "no consensus from researchers/engineers on how we go from absolute to relative stake" must be resolved before Peras is activated. The normalization formula must be specified and implemented.

4. **Add signature validation to `validatePerasVote`.** The degenerate instance that skips signature verification must be replaced before activation.

---

### Proof of Concept

The following illustrates the unit mismatch. Assume `PerasVoteStakeDistr` is populated with absolute lovelace values (e.g., pool A has 500 million ADA = `500_000_000_000_000` lovelace):

```
-- Stored in PerasVoteStakeDistr:
poolA -> PerasVoteStake (500_000_000_000_000 % 1)

-- After one vote from poolA:
totalVoteStake = PerasVoteStake (500_000_000_000_000 % 1)

-- stakeAboveThreshold check:
stake           = 500_000_000_000_000 % 1
quorumThreshold = 3 % 4              -- 0.75
safetyMargin    = 2 % 100            -- 0.02

-- Result:
500_000_000_000_000 >= 0.77  →  True  -- quorum "reached" with 1 vote
```

A single vote from any pool with any meaningful stake would forge a certificate. The adversary only needs to know a valid pool ID (public information) and send a `PerasVote` message with that ID, since the degenerate `validatePerasVote` performs no signature check. votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
