### Title
Unconditional Certificate Acceptance in `validatePerasCert` Bypasses All Peras Certificate Validation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. This function is wired directly into the production certificate-diffusion path (`makePerasCertPoolWriterFromChainDB`), meaning any unprivileged peer can inject arbitrary `PerasCert` objects — with any `pcCertRound` and `pcCertBoostedBlock` — that are accepted as `ValidatedPerasCert` and stored in the `ChainDB`, affecting chain selection via the Peras boost weight.

### Finding Description

The `BlockSupportsPeras` instance (labeled a "degenerate instance for all blks to get things to compile") implements `validatePerasCert` as an unconditional accept:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is not confined to tests. The production certificate-diffusion writer `makePerasCertPoolWriterFromChainDB` passes `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` applies `validateCert` to every inbound certificate from a peer. Because `validatePerasCert` always returns `Right`, the `partitionEithers` check never produces any errors, and every certificate — regardless of content — is timestamped and forwarded to `addCert`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

The accepted `ValidatedPerasCert` carries a `vpcCertBoost` weight (`perasWeight params`) that is used in chain selection to boost the certified block. The `PerasCert` data type contains only `pcCertRound` and `pcCertBoostedBlock` — both fully attacker-controlled — with no signature, no committee membership proof, and no quorum attestation checked at any point in this path. ### Impact Explanation

**Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance.**

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block (including an adversarial fork tip) and an arbitrary `pcCertRound`. Because `validatePerasCert` never rejects anything, this certificate is stored as `ValidatedPerasCert` with a full `vpcCertBoost` weight. Chain selection then treats the targeted block as having received a legitimate Peras quorum boost, potentially causing an honest node to prefer a non-canonical or adversarially-controlled chain over the honest chain — a direct Peras safety failure.

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is a standard peer-to-peer diffusion channel. Any connected peer — no credentials required — can send a batch of `PerasCert` objects. The only existing guard is a duplicate-round-number check (`Set.member roundNo certIds`), which an attacker trivially bypasses by using a fresh `pcCertRound` value. The stub is wired into both the `PerasCertDB`-backed and `ChainDB`-backed production writers.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS/committee signature over `(pcCertRound, pcCertBoostedBlock)`.
2. That the signers constitute a valid quorum of the committee for the given round.
3. That `pcCertBoostedBlock` refers to a block that exists and is old enough (≥ `perasBlockMinSlots`).

Until the real implementation is available, the production `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` writers should refuse all inbound certificates rather than accept them unconditionally, to avoid silently corrupting chain-selection state.

### Proof of Concept

1. Connect a peer to a node running the ObjectDiffusion certificate-diffusion mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <any fresh round>` and `pcCertBoostedBlock = <tip of an adversarial fork>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
4. `addCert` stores the certificate in the `ChainDB` via `ChainDB.addPerasCertAsync`.
5. Chain selection now sees the adversarial fork tip as carrying a 15-weight Peras boost, potentially making it preferred over the honest chain tip.
