### Title
Missing Cryptographic Signature Verification in `validatePerasVote` and `validatePerasCert` Allows Unauthorized Peras Vote and Certificate Acceptance — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production-active catch-all `BlockSupportsPeras` instance for all blocks implements `validatePerasVote` with no cryptographic signature check and `validatePerasCert` that unconditionally returns `Right`. An unprivileged peer can craft `PerasVote` messages claiming to be from any registered stake pool and have them accepted as valid, accumulating fabricated stake weight until quorum is reached and a certificate is forged for an attacker-chosen block. This is a direct bypass of Peras voting and certificate authorization.

---

### Finding Description

**Root cause — missing authorization check in the degenerate `BlockSupportsPeras` instance:**

The file `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines a catch-all instance that applies to every block type:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

The `PerasVote blk` data type defined in this instance carries **no signature field**:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- only a pool key hash; no signature
  }
``` [2](#0-1) 

`validatePerasVote` therefore performs only a stake-distribution membership lookup — it checks whether `pvVoteVoterId` exists in the map, assigns that pool's stake, and returns `Right`. No cryptographic proof that the sender controls the pool's key is ever demanded:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

`validatePerasCert` is even weaker — it accepts every certificate unconditionally:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

**Contrast with the correct implementations:** The `EveryoneVotes` and `WFALS` committee schemes both call `verifyVoteSignature` against the pool's registered public key before accepting a vote, and verify an aggregate BLS signature before accepting a certificate. [5](#0-4) [6](#0-5) 

**Production entry path — inbound vote and certificate handlers:**

Both `makePerasVotePoolWriterFromChainDB` and `makePerasVotePoolWriterFromVoteDB` call `validatePerasVote mkPerasParams sd vote`, which resolves to the degenerate instance above: [7](#0-6) 

`makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams`, which always returns `Right`: [8](#0-7) 

`processVotes` accepts all votes that pass `validateVote` and adds them to the ChainDB: [9](#0-8) 

**Exploit flow:**

1. Attacker connects to a node as an ordinary peer via the Peras vote diffusion mini-protocol.
2. Attacker sends a batch of `PerasVote` messages, each with `pvVoteVoterId` set to the `KeyHash StakePool` of a different high-stake pool. No signing key is required.
3. `processVotes` calls `validatePerasVote`, which finds each pool in the stake distribution and returns `Right ValidatedPerasVote` with that pool's full stake weight.
4. The `PerasVoteDB` accumulates these fabricated votes. `updatePerasRoundVoteStates` sums their stake; once the quorum threshold is crossed, `forgeCert` is called and a `ValidatedPerasCert` is produced for the attacker's chosen block.
5. The certificate is added to the ChainDB via `addPerasVoteWithAsyncCertHandling`, boosting the attacker's block in chain selection.
6. For certificates sent directly: `validatePerasCert` returns `Right` unconditionally, so any crafted certificate is immediately accepted and stored. [10](#0-9) 

---

### Impact Explanation

**Severity: Critical — Bypass of Peras voting and certificate checks.**

An unprivileged peer with no stake and no cryptographic keys can:

- Forge votes on behalf of any registered stake pool by simply naming their `PerasVoterId`.
- Accumulate enough fabricated stake weight to reach quorum and cause the node to forge a Peras certificate for an attacker-chosen block.
- Alternatively, send a crafted `PerasCert` directly; it is accepted unconditionally.

The accepted certificate boosts the attacker's block in chain selection, enabling unauthorized chain preference manipulation. This breaks the core Peras safety guarantee that only legitimately elected committee members can influence which block is boosted.

This matches the allowed impact: *"Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

**High.** The vulnerable code is the active production instance for all block types (no more-specific Cardano instance overrides it). Any peer reachable via the Peras vote diffusion mini-protocol can trigger this path with a single crafted message batch. No stake, no keys, and no privileged access are required — only a network connection to a node that has Peras diffusion enabled.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote blk`** in the degenerate instance (or replace the degenerate instance with a concrete Cardano-era instance) so that `validatePerasVote` can verify the vote was signed by the pool's registered key.
2. **Implement real validation in `validatePerasCert`** — at minimum verify the certificate's round number, boosted block, and aggregate BLS signature against the declared voters' registered public keys, mirroring `implVerifyCert` in `EveryoneVotes` or `WFALS`.
3. Until a concrete instance is in place, **gate the Peras vote/cert diffusion mini-protocol** so it is not reachable from untrusted peers in production builds.

---

### Proof of Concept

```
-- Attacker constructs N votes, one per high-stake pool, with no signing key:
let forgedVotes =
      [ PerasVote
          { pvVoteRound   = currentRound
          , pvVoteBlock   = attackerBlock
          , pvVoteVoterId = PerasVoterId poolKeyHash  -- any registered pool
          }
      | poolKeyHash <- Map.keys (unPerasVoteStakeDistr stakeDistr)
      ]

-- Send forgedVotes to the target node via the Peras vote diffusion protocol.
-- processVotes calls validatePerasVote for each; each passes because
-- lookupPerasVoteStake finds the pool in the distribution.
-- Once accumulated stake exceeds quorum, the node forges a certificate
-- for attackerBlock and boosts it in chain selection.
```

The `PerasVote blk` type carries no `pvSignature` field, so there is nothing for `validatePerasVote` to check beyond the stake-distribution lookup. [11](#0-10)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
