### Title
Unbounded Peras Weight Accumulation via Stub Certificate Validation Enables Adversarial Chain Selection Dominance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function is a stub that unconditionally returns `Right` for every inbound `PerasCert`, performing no cryptographic or quorum validation. Because the `PerasCertDB` deduplicates certificates only by round number, an unprivileged peer can send an unbounded number of crafted certificates — each with a distinct round number but all boosting the same adversarial block — causing that block's entry in the `PerasWeightSnapshot` to accumulate an arbitrarily large `PerasWeight`. The Peras chain-selection comparison `wsvTotalWeight = blockNo + weightBoost` is then dominated by this inflated boost, causing an honest node to prefer a short adversarial fork over the longer honest chain.

---

### Finding Description

**Root cause — stub validation always accepts:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every `PerasCert` received from the network is unconditionally wrapped in `Right`. No committee membership, BLS signature, quorum proof, or round-to-slot consistency is checked.

**Network entry path — `processCerts` calls the stub:** [2](#0-1) [3](#0-2) 

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` call `validatePerasCert mkPerasParams` on every inbound certificate batch. Because the stub always succeeds, every crafted certificate passes and is forwarded to `addCert` / `addPerasCertAsync`.

**Deduplication only by round number — same block can be boosted N times:** [4](#0-3) 

`implAddCert` rejects a certificate only if its `PerasRoundNo` is already present in `pcdsCertIds`. An attacker who sends certificates for round 1, 2, 3, … N — all with `pcCertBoostedBlock = adversarialBlock` — will have every one accepted, because each carries a fresh round number.

**Weight accumulation — duplicate boosted-block entries are summed:** [5](#0-4) 

`addToPerasWeightSnapshot` uses `Map.insertWith (<>)`, so N certificates all pointing to the same block accumulate `N × perasWeight params` for that point in the snapshot.

**Chain selection dominated by inflated weight:** [6](#0-5) 

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
```

`preferCandidate` switches to the candidate chain when `wsvTotalWeight cand > wsvTotalWeight ours`. With an accumulated boost of `N × B` on a 1-block adversarial fork, the adversarial chain wins as soon as `1 + N×B > honest_block_count`.

**`implGetWeightSnapshot` materialises the accumulated weight directly into chain selection:** [7](#0-6) 

Every call to `getWeightSnapshot` rebuilds the snapshot from all stored certificates, so the inflated weight is immediately visible to `chainSelectionForBlock`.

---

### Impact Explanation

An unprivileged peer can force an honest node to switch to an adversarial fork of length 1 (or any length shorter than the honest chain) by sending enough crafted `PerasCert` messages — one per distinct round number — all boosting the adversarial tip. The accumulated `wsvWeightBoost` grows without bound, eventually exceeding the honest chain's `wsvBlockNo`, causing `preferCandidate` to return `ShouldSwitch`. This is a **chain-selection safety failure**: the node permanently adopts a non-canonical chain driven entirely by fake certificates, not by honest block production.

This is the direct analog of the oracle manipulation in the external report: just as one pool's inflated TVL dominates the weighted oracle average, one adversarial block's inflated `PerasWeight` dominates the weighted chain comparison, making all other chains contribute negligibly.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's object-diffusion endpoint. No stake, no keys, no admin access. The attacker sends a stream of `PerasCert` objects with incrementing `PerasRoundNo` values and a fixed `pcCertBoostedBlock` pointing to their adversarial block. The stub validation at `validatePerasCert` accepts all of them. The only rate-limiting factor is the size of the `TBQueue` backing `cdbChainSelQueue`, which is a bounded queue but not a per-peer rate limit. The attack is therefore trivially reachable from any peer.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` (tracked at `cardano-peras/issues/120`): verify committee membership, BLS aggregate signature, and that the certificate's round maps to a valid slot window.
2. **Cap per-block weight accumulation** in `PerasWeightSnapshot`: a single block should receive at most one boost per round, and the total boost for any block should be bounded by the protocol's `perasWeight` parameter times the maximum number of rounds in the volatile window.
3. **Deduplicate by boosted block, not only by round**: `implAddCert` should reject a certificate whose `pcCertBoostedBlock` already has a certificate in the DB for the same round, preventing the same block from accumulating weight from multiple rounds.
4. **Add a per-peer rate limit** on inbound `PerasCert` messages in `processCerts` to limit the blast radius before full validation is in place.

  - Node A: honest node running Peras-enabled ouroboros-consensus
  - Node B: adversarial peer

        the common ancestor with Node A's chain (which has, say, 100 blocks).

Step 2: Node B connects to Node A via the object-diffusion mini-protocol
        (PerasCert channel).

Step 3: Node B sends 100 crafted PerasCert messages:
          for r in [1..100]:
            PerasCert { pcCertRound = PerasRoundNo r
                      , pcCertBoostedBlock = point(adversarialBlock) }

Step 4: processCerts calls validatePerasCert on each → all return Right
        (stub, no validation).

Step 5: implAddCert accepts each (distinct round numbers), storing 100 entries
        in pcdsCertsByTicket, all with pcCertBoostedBlock = adversarialBlock.

Step 6: implGetWeightSnapshot builds PerasWeightSnapshot:
          adversarialBlock → PerasWeight (100 × perasWeight params)
        e.g., with perasWeight = 15: adversarialBlock → PerasWeight 1500

Step 7: chainSelectionForBlock is triggered for adversarialBlock.
        wsvTotalWeight(adversarial) = 1 + 1500 = 1501
        wsvTotalWeight(honest)      = 100 + 0  = 100
        preferCandidate returns ShouldSwitch → Node A adopts the adversarial fork.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

implAddCert ::

  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)
    pure addPerasCertRes

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight
-- could be cached, but then we need to be careful to maintain the invariant
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker
      ]

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of
        ShouldSwitch r -> ShouldSwitch (WeightedSelectViewTiebreak r)
        ShouldNotSwitch o -> ShouldNotSwitch o
      GT -> ShouldNotSwitch GT
