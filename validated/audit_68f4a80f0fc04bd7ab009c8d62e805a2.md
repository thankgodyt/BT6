### Title
Excess Attached NEAR Deposit Permanently Stuck in Bridge Contract — (`File: contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The publicly callable `execute_refund` function is `#[payable]` and enforces only a minimum attached-deposit check (`attached_deposit >= required_balance_for_execute_refund()`). Any NEAR attached above that minimum is silently absorbed by the bridge contract with no refund path. Because the bridge has no mechanism to sweep or return untracked NEAR, the excess is permanently locked.

### Finding Description

`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is decorated `#[payable]` and is publicly callable (no role restriction): [1](#0-0) 

It delegates immediately to `resolve_execute_refund_timelock`, which performs only a lower-bound check on the attached deposit: [2](#0-1) 

There is no upper-bound check (`== required_balance`) and no `Promise::new(predecessor).transfer(excess)` refund anywhere in the call chain. The same pattern applies to `request_refund`: [3](#0-2) [4](#0-3) 

The only NEAR recovery function in the contract is `withdraw_protocol_fee`, which drains `cur_available_protocol_fee` — a separately tracked accounting field that is never credited with excess attached deposits: [5](#0-4) 

Excess attached NEAR therefore has no recovery path and is permanently locked in the bridge contract.

### Impact Explanation

Any NEAR account that calls `execute_refund` or `request_refund` with an attached deposit larger than the required minimum permanently loses the excess NEAR to the bridge contract. The bridge contract has no sweep, no excess-refund logic, and no admin function that can recover untracked NEAR. This constitutes a publicly reachable stuck-funds condition on a production bridge path.

**Impact: Low** — loss of user NEAR (not BTC/nBTC), no direct theft of bridged assets, but funds are permanently irrecoverable.

### Likelihood Explanation

Any unprivileged NEAR account can call `execute_refund` after the timelock passes. A user who over-attaches NEAR (e.g., due to a wallet UI rounding up, a script error, or uncertainty about the exact required balance) will silently lose the excess. The `required_balance_for_execute_refund()` value is not a round number and is subject to change with storage costs, making exact attachment non-trivial for callers who do not query the view function first.

### Recommendation

Add an explicit excess-refund after the minimum check in both `execute_refund` and `request_refund`:

```rust
let attached = env::attached_deposit();
let required = self.required_balance_for_execute_refund();
require!(attached >= required, "Insufficient deposit for storage");
let excess = attached.as_yoctonear().saturating_sub(required.as_yoctonear());
if excess > 0 {
    Promise::new(env::predecessor_account_id())
        .transfer(NearToken::from_yoctonear(excess))
        .detach();
}
```

Alternatively, enforce an exact-match check (`attached == required`) to reject over-attached calls outright.

### Proof of Concept

1. Query `required_balance_for_execute_refund()` — suppose it returns `X` yoctoNEAR.
2. Call `execute_refund(utxo_storage_key, None)` with attached deposit `X + 1_000_000_000_000_000_000_000` (1 mNEAR extra).
3. The `require!(attached >= required)` check passes.
4. The function proceeds normally; no refund of the extra 1 mNEAR is issued.
5. The bridge contract balance increases by 1 mNEAR; `cur_available_protocol_fee` is unchanged.
6. `withdraw_protocol_fee` cannot recover it; no other admin path exists.
7. The 1 mNEAR is permanently locked in the bridge contract.

        let total_protocol_fee = self.data().cur_available_protocol_fee;
