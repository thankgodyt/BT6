### Title
`validatePerasCert` Stub Unconditionally Accepts All Peras Certificates, Bypassing Chain-Selection Security - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally accepts every inbound Peras certificate from any peer, stamping a boost weight derived from a hardcoded `mkPerasParams` rather than the actual protocol configuration. Because the boost value is frozen at acceptance time and never re-evaluated against current parameters, an unprivileged peer can inject arbitrary certificates that boost arbitrary blocks, causing chain selection to prefer a non-canonical chain. This is the direct Ouroboros Consensus analog of the external report's pattern: a threshold/parameter is applied (or not applied) at acceptance time and cached, but is never re-checked at the point where the cached value actually influences the security-critical decision.

---

### Finding Description

**Root cause 1 — complete validation bypass.**

The `BlockSupportsPeras` typeclass method `validatePerasCert` is implemented as a stub that always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No aggregate BLS signature, quorum threshold, committee membership, or round-number check is performed. Every certificate is accepted. [1](#0-0) 

**Root cause 2 — hardcoded parameters at acceptance time, stale boost stored permanently.**

Both production pool-writer constructors call `validatePerasCert mkPerasParams` — the hardcoded default — instead of the actual node configuration:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

The accepted certificate is stored in `PerasCertDB` with `vpcCertBoost = perasWeight mkPerasParams` (currently `PerasWeight 15`). This value is frozen at acceptance time. [4](#0-3) 

**Root cause 3 — chain selection reads the frozen boost, never the current parameter.**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` by reading `getPerasCertBoost cert` directly from every stored `ValidatedPerasCert`:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [5](#0-4) 

`weightedSelectView` then uses this snapshot to compute `wsvWeightBoost` for chain comparison: [6](#0-5) 

Chain selection prefers the candidate with the higher `wsvTotalWeight = blockNo + weightBoost`: [7](#0-6) 

If `perasWeight` is later changed (e.g., via a protocol update that wires up the real configuration), all previously stored certificates retain their old `vpcCertBoost` and continue to influence chain selection with the stale weight — exactly the pattern from the external report.

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block as `pcCertBoostedBlock`. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored with `vpcCertBoost = PerasWeight 15`, and immediately used by chain selection. If the attacker's target block is on a fork, the fork's total weight increases by 15, potentially exceeding the canonical chain's weight and causing the honest node to switch to the non-canonical chain. This is a chain-selection safety failure triggered by an unprivileged peer with no keys or stake.

Additionally, when the actual `perasWeight` is eventually wired up (replacing `mkPerasParams`), any certificates already stored under the old hardcoded weight will carry stale boost values that do not reflect the current protocol parameters, causing persistent chain-selection divergence from the intended security model.

---

### Likelihood Explanation

The attack path requires only a TCP connection to the node and the ability to send a valid CBOR-encoded `PerasCert` message over the object-diffusion mini-protocol. No cryptographic keys, stake, or special privileges are needed. The `processCerts` function is the sole gatekeeper and it delegates entirely to the stub validator. [8](#0-7) 

---

### Recommendation

1. **Implement `validatePerasCert` properly**: verify the aggregate BLS signature, confirm that the set of voters satisfies the quorum threshold against the current stake distribution, and check committee membership eligibility before returning `Right`.

2. **Wire up the actual `PerasCfg`**: replace the hardcoded `mkPerasParams` in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` with the real node configuration so that `vpcCertBoost` reflects the live `perasWeight`.

3. **Re-evaluate stored boost values on parameter change**: analogous to the fix in the external report, chain selection should either re-validate stored certificates against the current `perasWeight` at query time, or invalidate and re-process stored certificates whenever `perasWeight` changes, so that stale boost values cannot persist across protocol updates.

### Proof of Concept

```
1. Attacker connects to a Peras-enabled node via the object-diffusion mini-protocol.

2. Attacker constructs a PerasCert:
     pcCertRound      = <any round not yet in the DB>
     pcCertBoostedBlock = <Point of a block on a competing fork>

3. processCerts calls (validatePerasCert mkPerasParams) on the cert.
   validatePerasCert always returns:
     Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }

4. The cert is stored in PerasCertDB with vpcCertBoost = 15.

5. implGetWeightSnapshot reads getPerasCertBoost cert = 15 for the fork block.

6. weightedSelectView computes wsvTotalWeight(fork) = blockNo(fork) + 15.

7. If wsvTotalWeight(fork) > wsvTotalWeight(canonical), chain selection switches
   to the fork, accepting a non-canonical chain.
```
