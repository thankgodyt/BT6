### Title
Peras Vote and Certificate Cryptographic Validation Entirely Absent — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass provides the only implementations of `validatePerasVote` and `validatePerasCert` in the codebase. Both implementations carry explicit TODO comments acknowledging they perform no actual cryptographic validation. `validatePerasVote` accepts any vote whose voter ID appears in the stake distribution, without verifying the BLS signature or the VRF eligibility proof. `validatePerasCert` accepts any certificate unconditionally. An unprivileged peer can therefore inject forged votes (and certificates) that carry a valid voter ID but an entirely fabricated signature, causing the local node to accept them, accumulate them toward quorum, and potentially forge a certificate boosting an attacker-chosen block.

---

### Finding Description

`validatePerasVote` is the sole implementation of the typeclass method (confirmed: `grep_search` finds the symbol only in `SupportsPeras.hs` and the call-site in `PerasVote.hs`):

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The `_params` argument (which carries the Peras configuration, including cryptographic parameters) is discarded. The concrete `PerasVote` type defined in `Vote/V1.hs` carries two fields that are never inspected here:

- `pvSignature :: VoteSignature PerasBLSCrypto` — the BLS signature over the election identifier and vote message.
- `pvEligibilityProof :: PerasVoteEligibilityProof` — for non-persistent committee members, a VRF proof of eligibility.

`validatePerasCert` is equally hollow:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

The inbound path that reaches these stubs is `processVotes` in `PerasVote.hs`, which is called by the Peras vote diffusion mini-protocol for every batch of votes received from a peer. [1](#0-0) 

`processVotes` calls `validateVote` on each incoming vote; any vote that passes is timestamped and inserted into the `PerasVoteDB`, where it accumulates toward a quorum threshold. [2](#0-1) 

The concrete `PerasVote` type that travels over the wire carries the full BLS signature and eligibility proof: [3](#0-2) 

None of those fields are ever verified before the vote is admitted.

---

### Impact Explanation

A Peras certificate boosts a specific block's chain weight, directly influencing chain selection. If an attacker can inject enough forged votes — each carrying a real voter ID drawn from the public stake distribution but a fabricated BLS signature — the node will accumulate them to quorum and call `forgePerasCert`, producing a `ValidatedPerasCert` that boosts an attacker-chosen block. `forgePerasCert` is equally unvalidated (same TODO, same issue reference). The result is unauthorized certificate acceptance and a chain-selection deviation: the node prefers a block it should not prefer, constituting a consensus safety failure reachable by any unprivileged peer that can speak the Peras vote diffusion mini-protocol. [4](#0-3) 

---

### Likelihood Explanation

The entry point is the Peras vote diffusion mini-protocol, which is externally reachable by any peer. The attacker needs only a valid voter ID, which is derivable from the public stake distribution. No key material, operator access, or stake majority is required. The only prerequisite is that the Peras vote diffusion layer is active on the target node. The code is in the main production source tree (not in a test or unstable library), and `processVotes` is wired into the live `PerasVoteDB` path. [5](#0-4) 

---

### Recommendation

1. Implement real BLS signature verification inside `validatePerasVote`, verifying `pvSignature` over the canonical encoding of `(pvRoundNo, pvBoostedBlock)` using the voter's registered BLS verification key.
2. For non-persistent committee members, verify the VRF eligibility proof in `pvEligibilityProof` against the epoch nonce and the voter's registered VRF key.
3. Implement real certificate verification inside `validatePerasCert`, checking that the aggregate BLS signature in `pcSignature` is valid over the claimed voter set and that the voter set meets the quorum threshold.
4. Resolve the tracked issue at `https://github.com/tweag/cardano-peras/issues/120` before enabling the Peras vote diffusion mini-protocol on any network-connected node.

---

### Proof of Concept

1. Obtain the current stake distribution from a running node (public via the local state query mini-protocol).
2. Pick any `PerasVoterId` (pool key hash) present in the distribution.
3. Construct a `PerasVote` (V1 encoding) with:
   - `pvRoundNo` = any current round number,
   - `pvBoostedBlock` = hash of the attacker's preferred block,
   - `pvSeatIndex` = any seat index,
   - `pvEligibilityProof` = `PersistentPerasVoteEligibilityProof` (requires no proof),
   - `pvSignature` = 48 zero bytes (invalid BLS signature).
4. Send this vote to the target node via the Peras object-diffusion mini-protocol.
5. `processVotes` → `validateVote` → `validatePerasVote`: the vote passes because `lookupPerasVoteStake` finds the voter ID in the distribution.
6. The vote is inserted into `PerasVoteDB` with the full stake weight of the chosen pool.
7. Repeat with different voter IDs until the accumulated stake exceeds the quorum threshold; `forgePerasCert` is called and a certificate boosting the attacker's block is stored and diffused. [6](#0-5) [7](#0-6)

-- | Process a batch of inbound Peras votes received from a peer.
--
-- Votes whose ID is already present in the database (as determined by
-- @alreadyInDbSTM@) are silently skipped. The remaining votes are validated;
-- if /any/ vote in the batch fails validation, the entire batch is rejected
-- by throwing a 'PerasVoteInboundException' (which should make us disconnect
-- from the distant peer, see 'withPeer' bracket function from
-- `ouroboros-network`). Otherwise, each valid vote is timestamped with the
-- current wall-clock time and added to the database via @addVote@.
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
