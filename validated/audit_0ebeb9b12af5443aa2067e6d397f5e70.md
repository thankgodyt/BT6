### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Causes Incorrect Peras Non-Persistent Seat Count When `lambda > ln(3)` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

### Summary

In `localSortitionNumSeats`, the Taylor-expansion comparator `taylorExpCmpFirstNonLower` is called with a hardcoded `boundX = 3`. The function's own contract states that `boundX` **must** equal `e^{|x|}` for correct error bounds. Here `x = -lambda`, so the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, and the comparator can misclassify a threshold as "certainly below" when it is not, granting a non-persistent voter more seats than their VRF output entitles them to. This is the direct analog of the Curve bug: an incorrect arithmetic constant causes a computation to produce wrong results under a reachable input condition.

### Finding Description

`localSortitionNumSeats` computes `lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake` and then calls:

```haskell
taylorExpCmpFirstNonLower
  3          -- ← hardcoded; must be e^lambda per the function's contract
  orders
  (-lambda)
``` [1](#0-0) 

The function's own inline documentation is explicit:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

Inside `decideOne`, the error term is computed as:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX < e^lambda` (i.e., `lambda > ln(3)`), `errorTerm` is smaller than the true remainder of the Taylor series. The two decision branches become:

- `cmp >= acc' + errorTerm` fires too early → `Stop` returned (voter gets *fewer* seats than deserved)
- `cmp < acc' - errorTerm` fires too early → `Below` returned (voter gets *more* seats than deserved)

The second branch is the security-relevant one: a threshold `orders[i]` that is actually **above** `e^(-lambda)` is misclassified as certainly below it, so the comparator advances to the next threshold and awards the voter an extra seat.

The developers themselves flag this with a TODO acknowledging the value may be wrong:

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
``` [4](#0-3) 

The `3` was apparently copied from `checkLeaderNatValue` in the Ledger, where it is a **maximum iteration count**, not a `boundX` value — a category error that produces a silent arithmetic mistake.

### Impact Explanation

`localSortitionNumSeats` is called in two vote-verification paths:

1. **`implVerifyVote`** — verifies that a non-persistent voter presenting a `WFALSNonPersistentVote` is eligible.
2. **`implVerifyCert`** — verifies every non-persistent voter listed in a `WFALSCert`. [5](#0-4) [6](#0-5) 

If `localSortitionNumSeats` returns a non-zero count when the correct value is zero, the check `case nonZero numSeats of { Nothing -> Left (ZeroNonPersistentSeats …) }` passes, and the vote or certificate is accepted. This is a bypass of the Peras non-persistent committee eligibility check, enabling unauthorized vote or certificate acceptance.

### Likelihood Explanation

`lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake`. The threshold `ln(3) ≈ 1.099` is crossed whenever a voter holds more than `1.099 / numNonPersistentVoters` of the non-persistent stake. With a committee of 5 non-persistent seats, any voter with more than ~22% of the non-persistent stake produces `lambda > ln(3)`. With 10 seats, the threshold is ~11%. These are realistic stake concentrations. The attacker controls their own stake (a ledger-observable quantity) and submits a crafted vote or certificate message over the standard node-to-node miniprotocol — no key compromise or operator access is required.

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound `e^lambda`, computed using the existing `FixedPoint` arithmetic:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} where x = -lambda
      orders
      (-lambda)
```

Alternatively, if `exp` is not available for `FixedPoint`, compute an upper bound via the same Taylor-expansion infrastructure already present in the codebase, or import `Cardano.Ledger.BaseTypes.expFixedPoint`.

### Proof of Concept

Let `numNonPersistentVoters = 5`, `voterStake / totalNonPersistentStake = 0.4`, giving `lambda = 2.0`. Then `e^lambda ≈ 7.389`, but `boundX = 3`. The error bound is underestimated by a factor of ~2.46.

Choose a `normalizedVRFOutput` such that `orders[0] = normalizedVRFOutput / 2.0` is slightly above `e^(-2.0) ≈ 0.1353`. With the correct error bound the comparator would correctly classify `orders[0]` as above `e^(-lambda)` and return 0 seats. With `boundX = 3`, `errorTerm` is too small; the condition `cmp < acc' - errorTerm` fires prematurely, classifying `orders[0]` as "certainly below" and advancing to `orders[1]`, returning 1 seat instead of 0. The attacker submits a `WFALSNonPersistentVote` with this VRF output; `implVerifyVote` calls `localSortitionNumSeats`, receives `LocalSortitionNumSeats 1`, passes the `nonZero` check, and accepts the vote — despite the voter being ineligible under the correct computation.
