Audit Report

## Title
Partial `ft_on_transfer` Refund Permanently Locks Bridged Tokens in `omni-bridge` Contract — (File: near/omni-bridge/src/lib.rs)

## Summary

`is_refund_required()` only triggers a bridge-state revert when `ft_transfer_call` reports zero tokens used. When a recipient's `ft_on_transfer` returns a partial unused amount, the NEP-141 token contract refunds those tokens back to the bridge, but all three callback paths (`fin_transfer_send_tokens_callback`, `resolve_fast_transfer`, `resolve_utxo_fin_transfer`) treat the transfer as fully successful. The partially refunded tokens accumulate in the bridge contract with no automatic recovery path, permanently freezing bridged funds.

## Finding Description

When a cross-chain transfer includes a non-empty `msg` field, `send_tokens()` calls `ft_transfer_call` on the token contract. Under NEP-141, `ft_on_transfer` returns the number of tokens **not used** (refund amount); the token contract refunds those tokens back to the bridge and returns the number of tokens **used** (`amount - refund_amount`) to the bridge's callback.

`is_refund_required()` reads this result and only triggers a revert when the used amount equals exactly zero: [1](#0-0) 

If a recipient uses 998 out of 999 tokens and returns 1 unused, `ft_transfer_call` reports `998` used. `is_refund_required` sees `998 != 0` and returns `false`. All three callbacks then proceed as if the transfer fully succeeded:

- **`fin_transfer_send_tokens_callback`** (L1702): emits `FinTransferEvent`, pays fee to relayer. [2](#0-1) 
- **`resolve_fast_transfer`** (L906): removes fast transfer record, returns `U128(0)`. [3](#0-2) 
- **`resolve_utxo_fin_transfer`** (L1025): emits `UtxoTransferEvent`, returns `U128(0)`. [4](#0-3) 

The 1 token refunded by the NEP-141 contract to the bridge address is never forwarded to the original sender. The bridge's `locked_tokens` accounting is already decremented (for native tokens) or bridge tokens already minted (for deployed tokens) before `ft_transfer_call`, so the accounting does not reflect the stuck balance. The only recovery path is a DAO-privileged call, which is not automatic.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**: tokens that are partially rejected by the recipient's `ft_on_transfer` are locked inside the `omni-bridge` contract indefinitely. The original cross-chain sender receives fewer tokens than were bridged with no automatic recourse. This matches the Critical allowed impact: *permanent freezing of bridged funds across NEAR flows*.

## Likelihood Explanation

Any user who initiates a cross-chain transfer with a non-empty `msg` field targeting a NEAR contract that partially consumes tokens (e.g., a DEX or lending protocol that accepts only part of the offered tokens) triggers this path. The user controls the `msg` and recipient fields on the source chain. No special privileges are required. The bridge provides no protection against partial refunds, and the NEP-141 standard explicitly permits `ft_on_transfer` to return a non-zero partial refund amount.

## Recommendation

Replace the binary `is_refund_required` check with a function that returns the actual used amount. In each of the three callback functions:

- If `used_amount == 0`: full revert (existing behavior).
- If `0 < used_amount < sent_amount`: partial refund — forward `sent_amount - used_amount` back to the original sender (or burn if it is a deployed bridge token).
- If `used_amount == sent_amount`: full success (existing behavior).

This requires passing the original sender's address through to the callbacks so the partial refund can be forwarded.

## Proof of Concept

The existing integration test at `near/omni-tests/src/fin_transfer.rs` already demonstrates the bug: [5](#0-4) 

With `amount = 1000`, `fee = 1`, and `return_value = U128(1)` (1 token returned unused by recipient):
- `expected_recipient_balance: 998` — recipient received 998 tokens
- `expected_relayer_balance: 1` — relayer received fee
- `expected_locker_balance: 1` — **1 token permanently stuck in bridge**

The bridge emits `FinTransferEvent` (success) despite 1 token being silently absorbed. This test is runnable locally and directly reproduces the impact without any additional setup.

    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {
            match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                        // Normal case: refund if the used token amount is zero
                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                        amount.0 == 0
                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }
