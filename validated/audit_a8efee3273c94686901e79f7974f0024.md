Audit Report

## Title
Fee Transfer to Relayer Silently Fails While `locked_tokens` Accounting Is Already Updated — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `fin_transfer_send_tokens_callback`, the fee payment to the relayer for non-deployed (custodied) tokens uses `ft_transfer(...).detach()` — a fire-and-forget call with no success check. If this transfer fails (e.g., a non-reverting NEP-141 token, or a panicking call due to unregistered storage), the fee tokens remain permanently stuck in the bridge while `locked_tokens` has already been decremented by the full transfer amount (principal + fee). The `FinTransferEvent` is emitted unconditionally, falsely signaling complete success and creating a permanent, unrecoverable accounting discrepancy.

## Finding Description

**Step 1 — `process_fin_transfer_to_near`** calls `unlock_tokens_if_needed` with the **full** `transfer_message.amount` (principal + fee), permanently decrementing `locked_tokens` before any token movement occurs: [1](#0-0) 

**Step 2** — The principal (`amount_without_fee`) is sent to the recipient via `send_tokens(...).then(fin_transfer_send_tokens_callback(...))`. This leg has a proper callback: [2](#0-1) 

**Step 3 — Inside `fin_transfer_send_tokens_callback`**, on the success branch, the fee portion is dispatched to the relayer via a **detached** `ft_transfer` with no result observation: [3](#0-2) 

**Step 4** — `FinTransferEvent` is emitted unconditionally immediately after, regardless of whether the fee transfer succeeded: [4](#0-3) 

If the `ft_transfer` fails — either because the token is non-standard and returns without panicking, or because the call panics (e.g., fee recipient's storage was unregistered between the earlier storage-balance check and this callback) — the fee tokens remain in the bridge contract. In both failure modes, `locked_tokens` was already decremented by the full amount in Step 1, creating a permanent discrepancy: the bridge holds `fee` tokens with no accounting entry and no recovery path through normal bridge operations.

The storage-balance check for the fee recipient occurs in `process_fin_transfer_to_near` (lines 1919–1933), before `send_tokens` is dispatched. The actual fee `ft_transfer` occurs one cross-contract call later, inside the callback. Any state change to the fee recipient's storage registration between these two points is not re-validated. [5](#0-4) 

The `unlock_tokens` function in `token_lock.rs` confirms the decrement is immediate and unconditional: [6](#0-5) 

## Impact Explanation

This is a concrete **escrow mis-accounting and fee mis-accounting** impact matching the Critical allowed scope. `locked_tokens` permanently underestimates the actual tokens held by the bridge (decremented by `amount`, but only `amount_without_fee` left the bridge). The `fee` tokens are stranded with no accounting entry and no on-chain recovery path. The `FinTransferEvent` falsely signals that the full transfer — including fee delivery — succeeded, causing off-chain relayer infrastructure and indexers to record the fee as paid when it was not. The DAO can correct `locked_tokens` via `set_locked_tokens`, but cannot extract the stranded tokens without a dedicated rescue function.

## Likelihood Explanation

Non-deployed (custodied) tokens registered via `bind_token` are external NEAR contracts not controlled or audited by the bridge. The `bind_token_callback` validates only that the proof originates from a known factory; it does not validate that the NEAR-side token contract is a compliant NEP-141 implementation: [7](#0-6) 

An attacker can deploy a non-standard NEP-141 token on NEAR (one that returns without panicking on a failed `ft_transfer`, analogous to ERC-20 tokens that return `false`), register it through the normal `log_metadata` → `deploy_token` → `bind_token` flow, and trigger the vulnerability by initiating a transfer with a non-zero fee. Additionally, any standard NEP-141 token whose fee recipient unregisters storage between the storage-balance check and the callback `ft_transfer` will also trigger the accounting discrepancy via a panicking (but detached and ignored) cross-contract call.

## Recommendation

Replace the detached fee `ft_transfer` with a chained callback that verifies success. If the fee transfer fails, the callback should re-lock the fee amount in `locked_tokens` to restore accounting consistency:

```rust
// Instead of:
ext_token::ext(token)
    .with_attached_deposit(ONE_YOCTO)
    .with_static_gas(FT_TRANSFER_GAS)
    .ft_transfer(fee_recipient.clone(), transfer_message.fee.fee, None)
    .detach();

// Use a chained callback:
ext_token::ext(token)
    .with_attached_deposit(ONE_YOCTO)
    .with_static_gas(FT_TRANSFER_GAS)
    .ft_transfer(fee_recipient.clone(), transfer_message.fee.fee, None)
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(FEE_TRANSFER_CALLBACK_GAS)
            .fee_transfer_callback(token, fee_amount, chain_kind),
    );
```

The `fee_transfer_callback` should call `lock_tokens` to re-lock the fee amount in `locked_tokens` if the promise result indicates failure, and emit a corrective event. The `FinTransferEvent` should only be emitted after confirming the fee transfer succeeded (or after the corrective re-lock).

## Proof of Concept

1. Deploy a non-standard NEP-141 token `bad_token.near` on NEAR that implements metadata correctly but whose `ft_transfer` returns `U128(0)` without panicking when the transfer would fail.
2. Call `log_metadata` on the bridge for `bad_token.near`, then `deploy_token` on a foreign chain, then `bind_token` on NEAR. Confirm `locked_tokens` entry is created.
3. Set `locked_tokens` for `(Eth, bad_token.near)` to `1000` via `set_locked_tokens` (simulating prior lock-in).
4. Call `fin_transfer` with `amount = 1000`, `fee = 100`, `recipient = alice.near`, `fee_recipient = relayer.near`. Confirm `process_fin_transfer_to_near` runs: `locked_tokens` decrements to `900` (full amount unlock).

   Wait — actually `unlock_tokens_if_needed` decrements by the full `amount` (1000), so `locked_tokens` goes to `0`.

5. `send_tokens` delivers `900` units to `alice.near`. The callback `fin_transfer_send_tokens_callback` fires.
6. Inside the callback, `ft_transfer(relayer.near, 100, None).detach()` is called. `bad_token.near` returns without panicking. The `100` fee tokens remain in `bad_token.near`'s balance for the bridge contract.
7. `FinTransferEvent` is emitted.
8. **Invariant check**: `get_locked_tokens(Eth, bad_token.near)` returns `0`, but the bridge contract's balance in `bad_token.near` is `100`. The accounting discrepancy is permanent.

A near-workspaces integration test can reproduce this by deploying a mock NEP-141 token whose `ft_transfer` silently no-ops, running the full `fin_transfer` flow, and asserting that `get_locked_tokens` returns `0` while the bridge's token balance is `100`.

    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }
