### Title
Attacker Can Front-Run `request_refund` to Redirect User's BTC Refund to Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable with no caller-identity check. When a user's `DepositMsg` has `refund_address = None`, any attacker who observes the user's pending NEAR transaction can front-run it — supplying the same on-chain proof but substituting their own BTC address — and permanently redirect the user's BTC refund to themselves.

---

### Finding Description

`request_refund` is declared inside a `#[trusted_relayer]` impl block but carries **no** `#[trusted_relayer]` attribute on the function itself:

```rust
// bridge.rs line 480 – impl block has #[trusted_relayer]
#[trusted_relayer]
#[near]
impl Contract {
    ...
    // line 510 – function has NO #[trusted_relayer]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
```

The codebase's own test setup confirms that `#[trusted_relayer]` on the function is what enforces access control — tests explicitly grant `UnrestrictedRelayer` to accounts so they can call functions that carry the attribute on the function itself. Functions like `verify_refund_finalize` (line 602) and `remove_refund_pending_tx_id` (line 622) carry `#[trusted_relayer]` on the function; `request_refund`, `reject_refund`, and `execute_refund` do not, making them publicly callable.

The only caller check inside `request_refund` is gated on `gas_fee.is_some()`:

```rust
if gas_fee.is_some() {
    let caller = env::predecessor_account_id();
    require!(
        self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller),
        "Only DAO or Operator can specify custom gas_fee"
    );
}
```

When `gas_fee = None`, there is **zero** caller-identity enforcement.

The `refund_address` parameter is only validated against `deposit_msg.refund_address` when that field is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

For the common case where `deposit_msg.refund_address = None` (standard deposits), the caller may supply **any** BTC address as `refund_address` with no restriction.

The callback then stores the attacker-supplied address verbatim:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // attacker's BTC address
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

And the duplicate-request guard blocks the legitimate user from ever filing their own request:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

After `unsafe_refund_timelock_sec` elapses, `execute_refund` (also publicly callable) builds and signs a BTC transaction paying the attacker's address, permanently draining the deposit UTXO.

---

### Impact Explanation

**Critical — theft of user BTC.**

The attacker redirects the entire deposit UTXO (minus gas fee) to their own Bitcoin address. The victim cannot file a competing refund request (duplicate guard), cannot call `reject_refund` (requires DAO/Operator role or a prior `verify_deposit` on the same UTXO), and has no self-service recovery path. The only mitigation is DAO/Operator intervention within `unsafe_refund_timelock_sec`, which is not guaranteed and requires the operator to notice the attack.

---

### Likelihood Explanation

**High.** All inputs needed to front-run are public:
- `tx_bytes` and `vout` are on the Bitcoin blockchain.
- `proof` (Merkle path, block hash, coinbase proof) is derivable from any Bitcoin node.
- `deposit_msg` is embedded in the deposit address derivation and is observable from the victim's pending NEAR transaction.

The attacker pays only the storage deposit required by `required_balance_for_request_refund()` — a small NEAR amount — and gains the full BTC deposit value. The attack is profitable for any non-trivial deposit.

---

### Recommendation

Bind the refund request to the NEAR account that owns the deposit. The simplest fix is to require that `env::predecessor_account_id() == deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`, or alternatively require `deposit_msg.refund_address` to always be set (pre-authorized in the deposit message) so the `refund_address` check at line 154–158 always fires. A secondary fix is to add `#[trusted_relayer]` to `request_refund` so only whitelisted relayers can submit it, consistent with the pattern used for `verify_refund_finalize`.

```rust
// Option A: bind to recipient
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund without a pre-authorized refund address"
    );
}
```

---

### Proof of Concept

1. Alice sends 1 BTC to the bridge deposit address derived from `DepositMsg { recipient_id: alice.near, refund_address: None, ... }`.
2. The deposit is never finalized (e.g., wrong amount).
3. Alice constructs a `request_refund` NEAR transaction with `refund_address = "alice_btc_address"` and broadcasts it.
4. Attacker observes Alice's pending transaction in the NEAR mempool, extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof`.
5. Attacker calls `request_refund` with identical `deposit_msg`/`tx_bytes`/`vout`/`proof` but `refund_address = "attacker_btc_address"` and `gas_fee = None`.
6. Attacker's transaction is accepted; `refund_requests["<txid>@<vout>"]` is created with `refund_address = attacker_btc_address`.
7. Alice's transaction reverts: `"Refund request already exists for this UTXO"`.
8. After `unsafe_refund_timelock_sec`, attacker (or anyone) calls `execute_refund("txid@vout", None)`.
9. Bridge builds and MPC-signs a BTC transaction paying `attacker_btc_address` the full deposit minus gas fee.
