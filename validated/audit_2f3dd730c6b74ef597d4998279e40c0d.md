### Summary

`Ouroboros.Consensus.HardFork.History.Util` is a custom arithmetic module providing slot/epoch addition and subtraction used throughout consensus-critical hard fork era boundary computation. The addition functions (`addSlots`, `addEpochs`, `addPerasRounds`) carry **no overflow protection whatsoever**. The subtraction/counting functions (`countSlots`, `countEpochs`, `countPerasRounds`, `subSlots`) carry only `assert`-based underflow guards that are **disabled by default** in production builds. The test suite explicitly avoids large values to prevent triggering these overflows, which is itself an acknowledgment of the risk. No dedicated unit tests exist for these arithmetic functions. If overflow or underflow is triggered during era boundary computation, the resulting corrupted `SlotNo`/`EpochNo` values propagate into the hard fork summary, causing nodes to compute wrong era transitions and diverge on chain selection.

```haskell

countSlots (SlotNo to) (SlotNo fr) = assert (to >= fr) $ to - fr

### Impact Explanation

If `addSlots` or `addEpochs` overflows during `mkUpperBound`, the computed `boundSlot` or `boundEpoch` of an era wraps to a small value. The hard fork summary then contains a corrupted era boundary. All subsequent slot-to-epoch and slot-to-time conversions performed by `Qry.hs` use this corrupted summary. Nodes that compute the summary correctly (e.g., those with asserts enabled that crash rather than silently wrap) will diverge from nodes that silently wrap, producing a **cross-era consensus split**: different nodes believe different eras are active at the same slot, causing them to apply different validation rules and reject each other's blocks.

If `countSlots` underflows in `slotToEpochBound` (assert disabled in production), the result is a near-`maxBound Word64` value. `divMod` on this value produces a huge `epochs` count, and `addEpochs` then overflows, placing the next era's start at epoch `0` or another wrong value. This corrupts the era transition schedule for all nodes that process the affected block.

This maps to: **Hard-fork, era transition mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.**

---

### Likelihood Explanation

**Medium.** Two realistic trigger paths exist:

1. **Overflow via large era parameters**: An era with a very large epoch size (e.g., `eraEpochSize` near `maxBound Word64 / inEraEpochs`) causes `inEraEpochs * unEpochSize eraEpochSize` to overflow silently in `mkUpperBound`. Era parameters are set by on-chain governance, but the multiplication `inEraEpochs * unEpochSize eraEpochSize` at line 135 of `Summary.hs` is itself unguarded.

2. **Underflow via crafted transition slot**: If a ledger bug (or a future ledger change) allows a transition slot announcement at a slot before the current era's `boundSlot`, `countSlots hiSlot (boundSlot lo)` underflows in production (assert is a no-op). The transition slot comes from on-chain update proposals, which are submitted by unprivileged peers as transactions. The ledger is the primary guard, but the consensus layer provides no secondary arithmetic guard.

The test suite's deliberate avoidance of large values confirms the development team is aware of the overflow risk but has not addressed it with runtime-safe arithmetic.

---

### Recommendation

1. Replace the raw `Word64` arithmetic in `addSlots`, `addEpochs`, `addPerasRounds` with checked addition that throws a recoverable error (e.g., `Maybe`/`Either`) or uses `Natural` with explicit bounds checks, rather than silently wrapping.
2. Replace `assert`-based underflow guards in `countSlots`, `countEpochs`, `countPerasRounds`, `subSlots` with unconditional runtime checks (e.g., `when (to < fr) $ error ...` or returning `Maybe`) so they are active regardless of the `asserts` flag.
3. Add dedicated unit tests for `Util.hs` covering boundary values (`maxBound`, `0`, near-overflow inputs) to match the analog of the SafeMath report's recommendation.
4. Add a property test that `invariantSummary` holds for all summaries produced by `mkUpperBound` with arbitrary (bounded) inputs, exercising the arithmetic paths.

mkUpperBound EraParams{..} lo hiEpoch =
  Bound
    { boundTime = addRelTime inEraTime $ boundTime lo
    , boundSlot = addSlots inEraSlots $ boundSlot lo
    , boundEpoch = hiEpoch
    , boundPerasRound = addPerasRounds <$> inEraPerasRounds <*> boundPerasRound lo
    }
 where
  inEraEpochs, inEraSlots :: Word64
  inEraEpochs = countEpochs hiEpoch (boundEpoch lo)
  inEraSlots = inEraEpochs * unEpochSize eraEpochSize

  inEraPerasRounds :: PerasEnabled Word64
  inEraPerasRounds = div <$> PerasEnabled inEraSlots <*> (unPerasRoundLength <$> eraPerasRoundLength)

  inEraTime :: NominalDiffTime
  inEraTime = fromIntegral inEraSlots * getSlotLength eraSlotLength

-- Given the 'SlotNo' of the first /slot/ in which a transition could take
-- place, compute the first /epoch/ in which this could happen (since
-- transitions only take place at epoch boundaries). If the 'SlotNo' happens
-- to be the first slot in an epoch, it will be that 'EpochNo'; if it isn't,
-- however, it will be the /next/ epoch.
slotToEpochBound :: EraParams -> Bound -> SlotNo -> EpochNo
slotToEpochBound EraParams{eraEpochSize = EpochSize epochSize} lo hiSlot =
  addEpochs
    (if inEpoch == 0 then epochs else epochs + 1)
    (boundEpoch lo)
 where
  slots = countSlots hiSlot (boundSlot lo)
  (epochs, inEpoch) = slots `divMod` epochSize
