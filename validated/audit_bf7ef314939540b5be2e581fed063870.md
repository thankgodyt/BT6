### Title
Any Caller Can Redirect Another User's Unfinalized BTC Deposit Refund to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`request_refund` contains no check that the caller is the original depositor (`deposit_msg.recipient_id`). When a deposit was made with `deposit_msg.refund_address == None`, any unprivileged NEAR account can submit a refund request for that deposit and supply an attacker-controlled BTC address as the refund destination. After the `unsafe_refund_timelock_sec` elapses, anyone can call `execute_refund` to send the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, permissionless function (no `#[trusted_relayer]` attribute on the method itself, only `#[payable]` and `#[pause]`):

```rust
// bridge.rs:507-534
#[allow(clippy::too_many_arguments)]
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
```

The only validation of `refund_address` inside `internal_request_refund` is:

```rust
// refund.rs:154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This check is a no-op when `deposit_msg.refund_address` is `None` — the common case for standard deposits. There is no check that `env::predecessor_account_id()` equals `deposit_msg.recipient_id`. The `DepositMsg` struct confirms `refund_address` is optional:

```rust
// deposit_msg.rs:26-27
// BTC address for refund if deposit is never finalized.
#[serde(skip_serializing_if = "Option::is_none")]
pub refund_address: Option<String>,
```

The `request_refund_callback` stores the attacker-supplied `refund_address` verbatim into the `RefundRequest`:

```rust
// refund.rs:564-574
let refund_request = RefundRequest {
    deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
    utxo_storage_key: utxo_storage_key.clone(),
    tx_bytes,
    vout,
    amount,
    refund_address,   // ← attacker-controlled
    gas_fee: resolved_gas_fee,
    created_at_sec: nano_to_sec(env::block_timestamp()),
    executed: false,
};
```

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless (`#[payable]` + `#[pause]` only), and `build_refund_output` pays the stored `refund_address` directly:

```rust
// refund.rs:294-308
pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
    let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
        .expect("Invalid refund address");
    ...
    TxOut { value: Amount::from_sat(...), script_pubkey: refund_script_pubkey }
}
```

The only intended protection is the longer `unsafe_refund_timelock_sec` window, which is explicitly designed to give DAO/Operator time to reject suspicious requests. This is a monitoring-dependent, off-chain control — not an on-chain authorization check.

---

### Impact Explanation

An attacker can steal the full BTC value of any unfinalized deposit whose `deposit_msg.refund_address` is `None`. The attacker pays only the small, non-refundable storage deposit as an anti-spam fee. The stolen amount is the full deposit value minus the gas fee, which can be arbitrarily large. This constitutes **significant theft of user funds** — a Critical bridge impact.

---

### Likelihood Explanation

- Unfinalized deposits are a normal operational occurrence (relayer downtime, user error, network congestion).
- The `deposit_msg` for any deposit is fully reconstructable from on-chain events (`LogDepositAddress`, `RefundRequested`), so the attacker needs no privileged information.
- The attacker only needs to pay the storage deposit (a small NEAR amount) and wait for `unsafe_refund_timelock_sec`.
- The DAO/Operator must actively monitor all refund requests and reject malicious ones within the timelock window — a liveness assumption that can fail.
- No special role, leaked key, or third-party compromise is required.

Likelihood: **High**.

---

### Recommendation

Add an on-chain authorization check in `request_refund` (or `internal_request_refund`) that enforces the caller is the original depositor when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the original depositor can request a refund without a pre-authorized refund_address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` is always `Some` for permissionless refund requests, and restrict the `None` path to privileged callers only.

---

### Proof of Concept

1. Alice deposits BTC on-chain with:
   ```json
   { "recipient_id": "alice.near", "refund_address": null }
   ```
   The deposit address is derived from this `DepositMsg` hash and is publicly logged via `LogDepositAddress`.

2. The deposit is never finalized (relayer is slow, or Alice sent to the wrong address).

3. Bob observes the on-chain event, reconstructs Alice's `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: null },
     refund_address = "bob_btc_address",
     tx_bytes = <Alice's deposit tx>,
     vout = <Alice's output index>,
     proof = <valid Merkle proof>,
     gas_fee = null
   )
   ```
   attaching the required storage deposit in NEAR.

4. The light client verifies the transaction inclusion. `request_refund_callback` stores `refund_address = "bob_btc_address"` in the `RefundRequest` for Alice's UTXO. No caller identity check fires because `deposit_msg.refund_address` is `None`.

5. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not reject), Bob (or anyone) calls `execute_refund(utxo_storage_key, None)`.

6. `internal_execute_refund` calls `build_refund_output("bob_btc_address", refund_amount)`, constructs a PSBT paying Bob's address, and submits it to the MPC signing pipeline.

7. The signed transaction is broadcast to Bitcoin. Alice's BTC is sent to Bob's address. Alice receives nothing. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
