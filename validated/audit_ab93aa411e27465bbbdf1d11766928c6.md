### Title
Missing Setter for `chain_signatures_account_id` in `ConfigUpdate` Prevents Recovery if MPC Contract Address Changes - (File: contracts/satoshi-bridge/src/config.rs)

### Summary

`ConfigUpdate` — the only mechanism for post-deployment configuration changes — omits `chain_signatures_account_id`. If the NEAR chain-signatures MPC contract is ever redeployed at a new address, the bridge has no on-chain path to update this field, permanently breaking all withdrawal, refund, and UTXO-management signing operations and locking user funds.

### Finding Description

`Config` stores three critical external contract addresses: [1](#0-0) 

`ConfigUpdate`, the struct applied by `update_config`, exposes setters for two of them (`btc_light_client_account_id` and `nbtc_account_id`) but is entirely missing `chain_signatures_account_id`: [2](#0-1) 

The `apply` method therefore never touches `chain_signatures_account_id`: [3](#0-2) 

Every signing call reads `chain_signatures_account_id` directly from config at call time: [4](#0-3) [5](#0-4) 

There is also a compounding issue: `sync_chain_signatures_root_public_key` enforces a one-time-only guard (`is_none()` check), so the root public key derived from the MPC contract can never be re-synced after initial setup either: [6](#0-5) 

### Impact Explanation

`chain_signatures_account_id` is the target of every MPC signing cross-contract call: `sign_btc_transaction`, `sign_btc_transaction_callback`, and the root-public-key sync. If the MPC contract migrates to a new address, all of the following operations fail permanently:

- User withdrawals (`ft_on_transfer` → `sign_btc_transaction`)
- Refund executions (`execute_refund`)
- UTXO consolidation / active management

Funds already locked in pending-sign state cannot be signed and therefore cannot be released. New withdrawals cannot be initiated. The bridge enters a stuck state requiring a full contract upgrade — a process that itself takes time and may be blocked by the upgrade timelock — during which user funds are inaccessible.

This matches: **Medium — stuck bridge state requiring operator intervention** / **Medium — attacker-triggered temporary locking of bridged funds** (the "attacker" here is the external event of MPC contract migration combined with the missing setter).

### Likelihood Explanation

NEAR's chain-signatures MPC service is an actively evolving protocol. Contract upgrades or address changes are operationally plausible. The bridge already acknowledges this class of risk for `btc_light_client_account_id` and `nbtc_account_id` by including them in `ConfigUpdate`; the omission of `chain_signatures_account_id` is an inconsistency that leaves the most critical dependency unupdatable.

### Recommendation

Add `chain_signatures_account_id: Option<AccountId>` to `ConfigUpdate` and handle it in `apply` with the same `set_if_some!` macro used for the other account IDs. Similarly, remove the `is_none()` guard from `sync_chain_signatures_root_public_key` (or add a separate force-resync function restricted to `Role::DAO`) so the root public key can be refreshed if the MPC contract is redeployed.

### Proof of Concept

1. Bridge is deployed; `config.chain_signatures_account_id = "v1.signer.near"`.
2. NEAR chain-signatures MPC migrates to `"v2.signer.near"`.
3. DAO calls `update_config` with any `ConfigUpdate` — `chain_signatures_account_id` is not a field, so the call succeeds but the address remains `"v1.signer.near"`.
4. Any user calls `ft_transfer_call` to initiate a withdrawal; the bridge creates a pending-sign entry and calls `sign_btc_transaction`.
5. `sign_promise` dispatches a cross-contract call to `"v1.signer.near"` — the old, defunct contract.
6. The call fails; `sign_btc_transaction_callback` receives a failed promise; the pending-sign entry remains stuck.
7. The user's nBTC has been debited but no BTC is ever sent; funds are locked until a full contract upgrade is deployed and the upgrade timelock expires. [4](#0-3) [2](#0-1)
