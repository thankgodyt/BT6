### Title
Incorrect `boundX` Constant in Local Sortition Seat Calculation Causes Wrong Peras Committee Seat Counts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`, but the function's contract requires `boundX = e^{|x|}` for correct error bounds. When the Poisson parameter `lambda` exceeds `ln(3) ≈ 1.099`, the supplied constant is smaller than the required `e^lambda`, causing the error term to be underestimated and the Taylor comparison to terminate early with an incorrect seat count. This is the direct analog of the UniswapOracle formula-ordering bug: a wrong constant in a security-critical numeric formula produces incorrect results.

---

### Finding Description

`localSortitionNumSeats` computes how many non-persistent Peras voting seats a pool is entitled to via a Poisson-based local sortition check. The Poisson parameter is:

```
lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake
```

The seat count is determined by comparing the voter's normalized VRF output against Poisson CDF thresholds using a Taylor-expansion comparison:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; must be e^{|x|} = e^lambda
      orders
      (-lambda)
``` [1](#0-0) 

The `taylorExpCmpFirstNonLower` function's own documentation states:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

The error term used to decide convergence is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `lambda > ln(3) ≈ 1.099`, `e^lambda > 3`, so `boundX = 3` underestimates the true error bound. The convergence band `[acc' - errorTerm, acc' + errorTerm]` is narrower than it should be, causing the algorithm to make a definitive ABOVE/BELOW decision before the Taylor series has converged to sufficient precision. The result is an incorrect seat count for any voter whose `lambda` exceeds this threshold.

The code itself acknowledges uncertainty about this constant with a TODO:

```haskell
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
``` [4](#0-3)

### Impact Explanation

`localSortitionNumSeats` is called in three security-critical paths in `WFALS.hs`:

1. **`implVerifyVote`** — verifies that a non-persistent voter's claimed seat count is valid before accepting their vote.
2. **`implVerifyCert`** — verifies the seat count of every non-persistent voter in a Peras certificate before accepting it.
3. **`implCheckShouldVote`** — determines how many seats the local node is entitled to. [5](#0-4) [6](#0-5) 

An incorrect seat count has two failure modes:

- **False positive (more seats than deserved):** The verifier accepts a vote or certificate where the voter claims more seats than the correct computation would grant. This inflates the voter's effective voting weight (`VoteWeight = numSeats * stake / totalNonPersistentStake`), potentially allowing a minority-stake adversary to satisfy a quorum threshold they should not reach, enabling unauthorized Peras certificate acceptance.
- **False negative (fewer seats than deserved):** A legitimate voter's vote or certificate is rejected because the verifier computes zero seats for them, breaking liveness of the Peras fast-finality protocol. [7](#0-6) 

---

### Likelihood Explanation

`lambda = numNonPersistentVoters * voterStake / totalNonPersistentStake`. The threshold `lambda > ln(3) ≈ 1.099` is crossed whenever a voter holds more than `1.099 / numNonPersistentVoters` of the total non-persistent stake. With a typical non-persistent committee size of, say, 10, any voter with more than ~11% of non-persistent stake triggers the bug. This is a realistic stake fraction for a moderately large pool. Any peer that submits a vote or certificate is an unprivileged entry point; no key compromise or admin access is required.

---

### Recommendation

Replace the hardcoded `3` with the correct value `e^lambda`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp (fromRational (toRational lambda)))  -- e^{|x|} = e^lambda
      orders
      (-lambda)
```

Since `FixedPoint` may not expose `exp` directly, compute the bound using the same fixed-point arithmetic already available in the module, or use a sufficiently conservative upper bound derived from the known maximum of `lambda` (which is bounded by `numNonPersistentVoters`).

---

### Proof of Concept

Consider a non-persistent committee with `numNonPersistentVoters = 5` and a voter holding 40% of non-persistent stake:

```
lambda = 5 * 0.4 = 2.0
e^lambda = e^2 ≈ 7.389
boundX supplied = 3  (underestimate by factor ~2.46)
```

The `errorTerm` at each Taylor step is scaled by `3` instead of `7.389`. For a VRF output `u` that falls in the range where the true `e^{-lambda}` is within the correct error band of the `k`-th Poisson threshold but outside the underestimated band, `decideOne` will return `Stop` (ABOVE) or `Below` prematurely. Concretely, if the correct answer is `expectedSeats = 1` but the underestimated error band causes the algorithm to classify the first threshold as ABOVE at an earlier Taylor term, the function returns `expectedSeats = 0`, and `implVerifyVote` rejects the vote with `ZeroNonPersistentSeats`. Conversely, if the algorithm prematurely classifies the second threshold as ABOVE, it returns `expectedSeats = 2` when only 1 seat is deserved, and `implVerifyCert` accepts a certificate with inflated voting weight.
