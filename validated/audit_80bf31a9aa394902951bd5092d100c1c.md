Audit Report

## Title
Unvalidated `output` Field in Relayer-Supplied BTC Withdrawal Message Enables Fund Redirection — (`File: near/omni-bridge/src/btc.rs`)

## Summary
`submit_transfer_to_utxo_chain_connector` validates only the `target_btc_address` string from the relayer-supplied `TokenReceiverMessage::Withdraw`, while wildcarding both `input` and `output` fields. The original `msg` string — containing unvalidated `output` entries that dictate actual Bitcoin transaction destinations — is forwarded verbatim to the BTC connector. A malicious trusted relayer can pass the on-chain address check while supplying `output` entries whose `script_pubkey` values redirect funds to an attacker-controlled Bitcoin address, causing permanent loss of bridged BTC.

## Finding Description
In `near/omni-bridge/src/btc.rs`, the function destructures the relayer-supplied message as:

```rust
if let TokenReceiverMessage::Withdraw {
    target_btc_address,
    input: _,
    output: _,
    max_gas_fee,
} = message
{
    require!(
        btc_address == target_btc_address,
        BridgeError::IncorrectTargetUtxoAddress.as_ref()
    );
``` [1](#0-0) 

Both `input` and `output` are explicitly discarded with `_`. The only validation performed is a string equality check between the stored recipient address and the relayer-supplied `target_btc_address`. After this check, the original raw `msg` string — which still contains the unvalidated `output` entries — is forwarded verbatim:

```rust
ext_token::ext(btc_account_id)
    .with_attached_deposit(ONE_YOCTO)
    .with_static_gas(FT_TRANSFER_CALL_GAS)
    .ft_transfer_call(self.get_utxo_chain_connector(chain_kind), amount, None, msg)
``` [2](#0-1) 

The `TxOut` struct contains a `script_pubkey` field that determines the actual Bitcoin recipient: [3](#0-2) 

The BTC connector uses these `output` entries to construct and broadcast the Bitcoin transaction. Because the bridge never verifies that any `TxOut.script_pubkey` in `output` corresponds to `target_btc_address`, the relayer can craft a message where `target_btc_address` is the legitimate user's address (passing the `require!` check) while `output` contains attacker-controlled `script_pubkey` values.

## Impact Explanation
This constitutes a direct, permanent loss of bridged funds. The transfer record is removed via `self.remove_transfer_message(transfer_id)` before the cross-contract call, and the BTC connector broadcasts a Bitcoin transaction paying the attacker's script. The user's nBTC tokens are consumed, the bridge state is cleared, and the Bitcoin is irreversibly sent to the wrong address. This matches the Critical impact class: *Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows.* [4](#0-3) 

## Likelihood Explanation
The function is gated by `#[trusted_relayer]`, configured with `manager_roles(Role::DAO, Role::RelayerManager)`. Crucially, the trusted relayer role is **not** admin-only — it is a permissionless staking mechanism. Any account can call `apply_for_trusted_relayer` with sufficient NEAR stake and, after a configurable waiting period, automatically becomes a trusted relayer: [5](#0-4) 

The `trusted_relayer` macro configuration confirms the bypass and manager roles: [6](#0-5) 

An attacker who stakes the required NEAR, waits for the activation period, and becomes a trusted relayer can exploit this on any pending BTC withdrawal without further privilege escalation. The attack is repeatable for every pending withdrawal.

## Recommendation
After destructuring `TokenReceiverMessage::Withdraw`, validate that:
1. At least one `TxOut` in `output` has a `script_pubkey` that encodes `target_btc_address` (convert the Bitcoin address to its expected script form and compare).
2. The sum of matching output values equals the expected transfer amount (accounting for fees).

Reject the call if no output matches the stored recipient address. Constructing the validated `msg` from the on-chain stored transfer data (rather than accepting a raw relayer-supplied string) would be a stronger fix, eliminating the relayer's ability to inject arbitrary output entries entirely.

## Proof of Concept
1. User initiates a BTC withdrawal via `ft_transfer_call` on the nBTC token with `recipient = "btc:bc1q<user_address>"`. A `TransferMessage` is stored with `transfer_id = {origin_chain: Near, origin_nonce: 1}`.

2. Attacker stakes sufficient NEAR via `apply_for_trusted_relayer`, waits for the activation period, and becomes a trusted relayer.

3. Attacker calls `submit_transfer_to_utxo_chain_connector` with:
   ```json
   {
     "transfer_id": {"origin_chain": "Near", "origin_nonce": 1},
     "msg": "{\"Withdraw\":{\"target_btc_address\":\"bc1q<user_address>\",\"input\":[],\"output\":[{\"value\":7486,\"script_pubkey\":\"<attacker_p2wpkh_script>\"}],\"max_gas_fee\":null}}",
     "fee_recipient": null,
     "fee": null
   }
   ```

4. The bridge checks `btc_address == target_btc_address` → passes (user address matches). `input: _` and `output: _` are ignored.

5. The original `msg` (with attacker's `script_pubkey`) is forwarded to the BTC connector via `ft_transfer_call`. The BTC connector constructs and broadcasts a Bitcoin transaction paying `<attacker_p2wpkh_script>`. The user's funds are permanently lost.

A local integration test can be written against the sandbox environment (following the pattern in `near/omni-tests/src/utxo_fin_transfer.rs`) using a mock BTC connector that records the received `msg` and asserts that the `script_pubkey` in the forwarded `output` differs from the address derived from `target_btc_address`.
