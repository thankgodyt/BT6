Looking at the exact code path described, I need to trace: fee collection → migration → withdrawal attempt.

### Title
Protocol Fee Counters Not Reset on Migration — Old-Token Fees Permanently Unwithdrawable After `migrate_to_new_token_resolve` — (`contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

`migrate_to_new_token_resolve` switches `nbtc_account_id` to the new token but leaves `cur_available_protocol_fee` and `acc_collected_protocol_fee` reflecting amounts denominated in the **old** token. After migration, `withdraw_protocol_fee` issues an `ft_transfer` against the **new** token contract, which the bridge holds no protocol-fee balance in. Every attempt fails, the callback restores the counter, and the old-token fees are permanently inaccessible through the bridge's normal withdrawal path.

---

### Finding Description

**Step 1 — Fee collection (pre-migration)**

During normal deposit/withdraw operations, the bridge's `mint_callback` and `verify_withdraw_burn_callback` credit the bridge's own balance on the old nBTC token contract and mirror that in the counters: [1](#0-0) [2](#0-1) 

After N deposits/withdrawals the bridge holds `cur_available_protocol_fee` worth of **old** nBTC tokens.

**Step 2 — Migration completes**

`migrate_to_new_token_resolve` does exactly one state mutation: [3](#0-2) 

It does **not** reset `cur_available_protocol_fee`, does not include the bridge's own protocol-fee balance in the migration mint batch, and provides no mechanism to transfer the bridge's old-token holdings to the new token. The migration mint loop only covers the `accounts` list supplied by the caller: [4](#0-3) 

**Step 3 — Withdrawal attempt post-migration**

`withdraw_protocol_fee` reads the stale counter and calls `internal_withdraw_protocol_fee`: [5](#0-4) 

`internal_withdraw_protocol_fee` issues `ft_transfer` against `self.internal_config().nbtc_account_id` — now the **new** token: [6](#0-5) 

The bridge holds zero new-token protocol fees. The transfer fails. The callback restores the counter: [7](#0-6) 

The cycle repeats on every subsequent call. The old-token fees remain locked in the bridge's balance on the old token contract with no built-in recovery path.

---

### Impact Explanation

All protocol fees accumulated before migration are permanently inaccessible through the bridge's normal `withdraw_protocol_fee` path. The bridge contract has no function to call `ft_transfer` on an arbitrary (old) token contract. Recovery requires a contract upgrade. This constitutes permanent locking of protocol funds.

---

### Likelihood Explanation

Any migration event — an intended, documented operation — triggers this condition automatically. No adversarial action is required beyond the DAO executing a migration. The DAO has no in-contract way to detect or prevent the loss at migration time.

---

### Recommendation

In `migrate_to_new_token_resolve`, before switching `nbtc_account_id`:

1. If `cur_available_protocol_fee > 0`, mint an equivalent amount of new tokens to the bridge contract (or transfer old-token fees to a DAO-controlled address) as part of the migration batch.
2. Alternatively, zero out `cur_available_protocol_fee` and `acc_collected_protocol_fee` in `migrate_to_new_token_resolve` and emit an event so the DAO can recover old-token fees out-of-band before finalising the migration.
3. Add an explicit check in `withdraw_protocol_fee` (or a separate `withdraw_legacy_protocol_fee` entry point) that handles the old token address when a migration has occurred.

---

### Proof of Concept

```
1. Relayer calls deposit flow → mint_callback credits cur_available_protocol_fee = F (old token).
2. DAO calls internal_migrate_to_new_token(new_token, [user_accounts]).
   → migrate_to_new_token_resolve sets nbtc_account_id = new_token.
   → cur_available_protocol_fee still = F.
3. DAO calls withdraw_protocol_fee(None).
   → cur_available_protocol_fee decremented to 0.
   → ft_transfer(new_token, DAO, F) issued.
   → new_token.ft_transfer fails (bridge balance = 0 on new token).
   → withdraw_protocol_fee_callback restores cur_available_protocol_fee = F.
4. Repeat step 3 indefinitely — counter always bounces back, fees never leave.
5. Old-token balance of bridge on old token contract remains = F, permanently locked.
```
