### Title
Peras Certificate Validation Bypass Enables Unauthorized Chain Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic or structural validation. Because this stub is wired directly into the production certificate ingestion path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject a crafted certificate that boosts an arbitrary block's chain weight, triggering chain selection for a non-canonical fork. Once the certificate is stored in the `PerasCertDB` it cannot be revoked, mirroring the external report's pattern of an irreversible commitment made without the required validation gate.

### Finding Description

`validatePerasCert` in the default `StandardHash blk => BlockSupportsPeras blk` instance always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No committee membership check, no aggregate signature verification, no quorum proof, and no round-number sanity check is performed. The function is not isolated to tests; it is the validator passed directly into the production network ingestion path:

```haskell

          (void . ChainDB.addPerasCertAsync chainDB)

``` [2](#0-1) 

`processCerts` calls the validator and, because it always returns `Right`, immediately timestamps and forwards every certificate to `addCert`: [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which stores it in the `PerasCertDB` and immediately calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

Chain selection then compares fragments using `WeightedSelectView`, where `wsvTotalWeight = blockNo + weightBoost`. A fraudulent boost can make a shorter fork appear heavier than the honest chain: [5](#0-4) 

The `PerasCertDB` enforces one certificate per round (`PerasCertAlreadyInDB` causes an early exit). Once a fraudulent certificate is stored for a given round, no revocation path exists — the honest certificate for that round is permanently locked out, directly mirroring the external report's irrevocable-commitment pattern. [6](#0-5) 

### Impact Explanation

An unprivileged peer can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block currently in the node's `VolatileDB`. The certificate bypasses all validation, is stored permanently for its round, and causes `chainSelectionForBlock` to re-evaluate chain preference with the fraudulent weight boost applied. If the boosted block is on a fork, the node may switch to that fork, accepting a non-canonical chain. This constitutes a **High** chain-selection bug: an unprivileged peer makes an honest node prefer a less-secure chain beyond the intended security assumptions of Ouroboros Praos/Peras.

### Likelihood Explanation

The `ObjectDiffusion` mini-protocol for Peras certificates is a live network-facing component. Any connected peer can send a `PerasCert` message. The stub is not guarded by a feature flag at the validation call site — the `TODO` comment and the GitHub issue reference confirm the missing validation is a known gap in the current production code, not a deliberate design choice. Exploitation requires only the ability to connect to a node and send a well-formed (but cryptographically invalid) certificate object.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's aggregate signature against the claimed committee members.
2. That the signers form a valid quorum (stake ≥ threshold) drawn from the correct epoch's stake distribution.
3. That `pcCertRound` is within the expected window relative to the current slot.
4. That `pcCertBoostedBlock` refers to a block that was actually a valid candidate in that round.

Until the real validator is in place, the `makePerasCertPoolWriterFromChainDB` path should reject all inbound certificates (return a hard error or drop them silently) rather than forwarding them with a no-op check.

### Proof of Concept

1. Connect to a target node running with Peras enabled.
2. Identify a block hash `H` in the node's VolatileDB that is on a fork shorter than the current selection.
3. Send a `PerasCert` message via the ObjectDiffusion mini-protocol with:
   - `pcCertRound` = any round not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = `BlockPoint slotOf(H) H`
4. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
5. The certificate is stored in the `PerasCertDB` and `chainSelSync` calls `chainSelectionForBlock` for block `H`.
6. `compareAnchoredFragments` now computes `wsvTotalWeight` for the fork containing `H` as `blockNo(H) + perasWeight`, which may exceed the honest chain's total weight.
7. The node switches to the fork, accepting a non-canonical chain. [1](#0-0) [7](#0-6) [8](#0-7) [9](#0-8)
