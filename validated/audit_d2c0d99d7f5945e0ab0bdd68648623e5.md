### Title
Peras Quorum Check Compares Unnormalized Absolute Vote Stake Against Relative Threshold — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value (sourced from the ledger's absolute stake distribution) directly against `perasQuorumStakeThreshold` (a relative `Rational` fraction). No normalization step divides the accumulated vote stake by the total stake before the comparison. This is the consensus-layer analog of the M-05 decimal normalization bug: two quantities in incompatible units are compared without conversion, producing a systematically wrong quorum decision.

---

### Finding Description

`stakeAboveThreshold` performs the quorum check for Peras certificate forging:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (...)
``` [1](#0-0) 

The code itself carries an explicit TODO acknowledging the unit mismatch:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` fed into this function originates from `PerasVoteStakeDistr`, which is populated from the ledger's absolute stake (lovelace). The companion note on `PerasVoteStake` states: "At the moment there is no consensus from researchers/engineers on how we go from the **absolute** stake of a voter in the ledger to the **relative** stake of their vote in the voting committee." [3](#0-2) 

Meanwhile, `perasQuorumStakeThreshold` is a `Rational` in the unit interval `[0,1]` (e.g., `0.75` for 75% of total stake): [4](#0-3) 

The call site in `votesReachQuorum` sums raw `vpvVoteStake` values and passes the total directly to `stakeAboveThreshold` with no normalization:

```haskell
totalVoteStake    = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [5](#0-4) 

`validatePerasVote` assigns the raw ledger stake directly as `vpvVoteStake` without any normalization: [6](#0-5) 

The `PerasVoteStakeDistr` is injected from outside via `getStakeDistrSTM`, with a comment noting it currently reads from the raw ledger stake distribution: [7](#0-6) 

---

### Impact Explanation

**Unit mismatch direction 1 — trivial quorum (critical):** If `PerasVoteStakeDistr` holds absolute lovelace values (e.g., a voter with 1,000,000 lovelace has `PerasVoteStake = 1000000`), then `stake = 1000000` is compared against `quorumThreshold = 0.75`. The condition `1000000 >= 0.75` is always true. A single vote from any committee member with any positive stake immediately satisfies quorum, allowing a Peras certificate to be forged for an arbitrary block with just one vote. This certificate carries a `PerasWeight` chain-selection boost, causing honest nodes to prefer the adversarially boosted chain over the canonical chain — a chain-selection safety failure.

**Unit mismatch direction 2 — quorum never reached (if values are fractional but not summing correctly):** If values are stored as per-voter fractions of total stake but the total stake denominator differs from what the threshold assumes, quorum may never be reachable, permanently blocking certificate production.

The critical path is direction 1: unauthorized Peras certificate forging → chain weight inflation → honest nodes adopt adversary's chain.

---

### Likelihood Explanation

The entry path is fully reachable by an unprivileged peer. A peer sends a crafted `PerasVote` via the object diffusion mini-protocol → `processVotes` → `validatePerasVote` (which only checks committee membership, not stake normalization) → `votesReachQuorum` → `stakeAboveThreshold`. No special privileges, keys, or stake majority are required. The bug is active whenever `PerasVoteStakeDistr` is populated with absolute lovelace values, which is the current implementation path as documented by the in-code comments.

---

### Recommendation

Normalize `PerasVoteStake` to a relative fraction before the quorum comparison. Either:

1. Divide the accumulated vote stake by the total stake of the full `PerasVoteStakeDistr` inside `stakeAboveThreshold` (change its signature to accept the distribution), or
2. Normalize each voter's stake entry when constructing `PerasVoteStakeDistr` (divide each absolute lovelace value by the total lovelace in the distribution before storing).

The correct invariant is: `sum (map unPerasVoteStake allVoters) == 1`, matching the unit of `perasQuorumStakeThreshold`.

---

### Proof of Concept

Assume total network stake = 10,000,000,000 lovelace. A voter with 1,000,000 lovelace is assigned `PerasVoteStake = 1000000 % 1` (absolute). `perasQuorumStakeThreshold = 3 % 4` (0.75, relative). The check becomes:

```
1000000 >= (3/4) + safetyMargin
```

This is `True` for any reasonable `safetyMargin`. A single vote from this voter (holding only 0.01% of total stake) satisfies quorum. `votesReachQuorum` returns `Just votesWithQuorum`, `forgePerasCert` is called, and a `ValidatedPerasCert` is produced for an adversarially chosen block. This certificate is stored in `PerasVoteDB` and propagated, boosting the adversary's block by `perasWeight` in chain selection, causing honest nodes to switch to the adversary's chain.
