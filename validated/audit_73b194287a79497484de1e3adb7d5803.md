### Title
Attacker Can Redirect BTC Refunds to Their Own Address via Unguarded `request_refund` — (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `request_refund` function is publicly callable and accepts a caller-supplied `refund_address` with no verification that the caller owns the deposit UTXO. When `deposit_msg.refund_address` is `None`, any attacker can submit a refund request for a victim's stuck deposit and redirect the BTC to the attacker's own address. The only mitigation is an off-chain DAO rejection window, which is not a reliable on-chain guard.

### Finding Description
When a BTC deposit is never finalized on NEAR (e.g., the recipient NEAR account does not exist), anyone may call `request_refund` to initiate a return of the BTC. The function signature is:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // fully caller-controlled
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [1](#0-0) 

The function verifies the BTC transaction via the light client and checks that the output script matches the deposit address derived from `deposit_msg`, but it performs **no check that the caller is the intended beneficiary of the deposit** (e.g., the `deposit_msg.account_id`).

The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), this block is skipped entirely and any caller-supplied `refund_address` is accepted and stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // attacker-controlled value persisted here
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

A duplicate-request guard prevents a second submission for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

So once the attacker's request is stored, the legitimate user's subsequent `request_refund` call is rejected. After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also publicly callable:

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [5](#0-4) 

The BTC is then sent to `refund_request.refund_address` — the attacker's address — via the MPC signing pipeline.

The longer `unsafe_refund_timelock_sec` is the only mitigation, giving DAO/Operator time to call `reject_refund`. This is an off-chain, human-dependent control, not an on-chain ownership check. [6](#0-5) 

### Impact Explanation
**Critical.** An attacker can permanently redirect a victim's BTC refund to their own Bitcoin address. The stolen amount equals the full deposit value minus the gas fee. The victim's `request_refund` call is blocked by the duplicate-request guard, and the victim has no on-chain recourse once the attacker's request is stored and the timelock expires.

### Likelihood Explanation
**Medium.** Stuck deposits (BTC sent to a bridge address that is never finalized on NEAR) occur naturally when users make mistakes (e.g., invalid NEAR account ID in `deposit_msg`). All information needed to construct the attack — `deposit_msg`, `tx_bytes`, `vout`, and the Merkle proof — is publicly derivable from the Bitcoin blockchain. The attacker does not need to front-run; they can simply submit the malicious `request_refund` before the victim does. The only barrier is the DAO's ability to detect and reject the request within the `unsafe_refund_timelock_sec` window, which is an operational dependency, not a cryptographic guarantee.

### Recommendation
1. **Require `deposit_msg.refund_address` to always be set** at deposit time. This encodes the refund destination in the deposit address derivation path itself, making it impossible for any caller to override it.
