### Title
`min_withdraw_amount` Check Permanently Locks nBTC Tokens Minted Below the Withdrawal Threshold - (File: `contracts/satoshi-bridge/src/api/token_receiver.rs`)

### Summary

The `ft_on_transfer` entry point for withdrawals enforces a hard `min_withdraw_amount` floor on every withdrawal attempt. Because no invariant is enforced between `min_deposit_amount` and `min_withdraw_amount`, a user can legitimately deposit BTC, receive a minted nBTC balance that is below `min_withdraw_amount`, and then be permanently unable to withdraw those tokens without operator intervention.

### Finding Description

In `ft_on_transfer`, the bridge unconditionally rejects any withdrawal where the transferred amount is below `min_withdraw_amount`:

```rust
// contracts/satoshi-bridge/src/api/token_receiver.rs
require!(
    amount >= self.internal_config().min_withdraw_amount,
    "Invalid amount"
);
``` [1](#0-0) 

The deposit path in `internal_verify_deposit` mints `mint_amount = deposit_amount - deposit_fee` to the user, provided `deposit_amount >= min_deposit_amount`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs
if deposit_amount < config.min_deposit_amount {
    // routes to unavailable UTXO — no mint
} else {
    let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
    let mint_amount = deposit_amount - deposit_fee;
    ...
}
``` [2](#0-1) 

`Config::assert_valid()` validates many field relationships but contains **no check** that `min_deposit_amount - max_deposit_fee >= min_withdraw_amount`: [3](#0-2) 

This gap means a user who deposits `deposit_amount` in the range `[min_deposit_amount, min_withdraw_amount + deposit_fee)` will receive `mint_amount < min_withdraw_amount` nBTC. The `ft_on_transfer` check then permanently blocks any withdrawal of those tokens.

The test configuration itself demonstrates the gap concretely: `min_deposit_amount = 20000` and `min_withdraw_amount = 70000` with `fee_rate = 0` and `fee_min = 0`, meaning a user depositing exactly 20 000 satoshis receives 20 000 nBTC but can never withdraw it. [4](#0-3) 

Additionally, because nBTC is a standard NEP-141 token, any user can receive an arbitrary sub-minimum balance via a plain `ft_transfer` from another account, creating the same stuck state without any deposit at all. [5](#0-4) 

### Impact Explanation

nBTC tokens minted to a user whose balance falls below `min_withdraw_amount` are permanently unwithdrawable. The user's BTC value is locked in the nBTC contract with no self-service escape path: `ft_on_transfer` rejects the withdrawal, there is no alternative withdrawal route, and `claim_lost_found` only covers failed cancel-withdraw refunds, not sub-minimum balances. Recovery requires the DAO to lower `min_withdraw_amount` (operator intervention). This constitutes permanent locking of user funds — a Medium impact matching "stuck bridge state requiring operator intervention."

### Likelihood Explanation

The likelihood is medium. The configuration gap is structural: `Config::assert_valid()` never enforces `min_deposit_amount - max_fee >= min_withdraw_amount`. Any deployment where `min_deposit_amount < min_withdraw_amount` (a common operational choice to allow small deposits while requiring larger withdrawals for Bitcoin dust reasons) will silently trap users who deposit near the minimum. The test configuration already exhibits this exact gap. No attacker action is required; an ordinary user depositing a small but valid amount triggers the condition.

### Recommendation

Add a validation in `Config::assert_valid()` that enforces:

```
min_deposit_amount - max_possible_deposit_fee >= min_withdraw_amount
```

Concretely:

```rust
let max_deposit_fee = deposit_bridge_fee.get_fee(min_deposit_amount);
require!(
    min_deposit_amount.saturating_sub(max_deposit_fee) >= min_withdraw_amount,
    "min_deposit_amount minus max deposit fee must be >= min_withdraw_amount"
);
``` [3](#0-2) 

This ensures that any user who successfully deposits the minimum amount will always receive enough nBTC to meet the withdrawal threshold.

### Proof of Concept

1. Deploy the bridge with `min_deposit_amount = 20_000`, `min_withdraw_amount = 70_000`, `deposit_bridge_fee = { fee_min: 0, fee_rate: 0 }` (matching the existing test config).
2. User Alice sends 20 000 satoshis to her deposit address.
3. Relayer calls `verify_deposit`; `internal_verify_deposit` sees `deposit_amount (20_000) >= min_deposit_amount (20_000)`, computes `mint_amount = 20_000 - 0 = 20_000`, and mints 20 000 nBTC to Alice.
4. Alice calls `nbtc.ft_transfer_call(bridge, 20_000, WithdrawMsg{...})`.
5. `ft_on_transfer` fires: `require!(20_000 >= 70_000)` → **panics with "Invalid amount"**. The transfer is refunded by the NEP-141 resolver, but Alice's 20 000 nBTC remain in her account with no withdrawal path.
6. Alice's nBTC are permanently locked unless the DAO lowers `min_withdraw_amount`. [6](#0-5) [7](#0-6)
