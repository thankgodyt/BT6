### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate Without Cryptographic Verification - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs)

### Summary
The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every input certificate, performing zero cryptographic or structural identity verification. This function is wired directly into the production Peras certificate inbound processing path (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can therefore inject an arbitrary `PerasCert` claiming to boost any block, and it will be accepted, timestamped, and stored in the `PerasCertDB` — and subsequently used to influence chain selection — without any signer identity or quorum proof check.

### Finding Description

**Root cause — `SupportsPeras.hs` lines 350–358:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is a **universal instance** (`instance StandardHash blk => BlockSupportsPeras blk`, line 320) that covers every concrete block type. The comment labels it a "degenerate instance for all blks to get things to compile" (line 318). No signature, no quorum check, no committee membership check — the raw attacker-supplied `cert` is wrapped in `ValidatedPerasCert` and returned as trusted.

**Production call path — `PerasCert.hs` lines 118–137:**

```haskell

    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime

    }
```

The inline comment "for actual production use" (line 89) distinguishes this writer from the test-only `makePerasCertPoolWriterFromCertDB`. `processCerts` (lines 164–185) calls `validateCert` on every inbound certificate; if all pass (they always do), each is timestamped and forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection side-effects.

**Analog to the reference bug:** The original NEAR bug used `signer_account_id()` — the original transaction originator — instead of `predecessor_account_id()` — the immediate, verifiable caller — for access control. Here the analog is that the code uses *no* identity at all: the certificate's claimed boosted block and round number are accepted as authoritative without verifying the identity of the signers (committee members) or the validity of their aggregate proof. The "wrong identity" is the absence of any identity check.

**End-to-end exploit path:**
1. Attacker connects as an unprivileged peer via the Peras certificate object-diffusion mini-protocol.
2. Attacker crafts a `PerasCert { pcCertRound = r, pcCertBoostedBlock = p }` where `p` is the tip of a minority or attacker-controlled fork.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert{..}`.
4. `ChainDB.addPerasCertAsync` stores the certificate; `PerasCertDB` now records a Peras boost for block `p` in round `r`.
5. `getWeightSnapshot` returns a weight snapshot that assigns `perasWeight` to `p`.
6. Chain selection uses this snapshot to prefer the boosted fork over the honest canonical chain.

### Impact Explanation

**High.** This is a chain-selection bug triggered by an unprivileged peer via a crafted network message. A Peras certificate boost can cause an honest node to prefer a non-canonical or attacker-controlled chain over the honest chain, violating the Peras security assumption that only quorum-certified blocks receive a weight boost. Because the `PerasCertDB` deduplicates by round number (one certificate per round), the first accepted fake certificate for a given round permanently locks in the attacker's chosen boosted block for that round, and a legitimate certificate for the same round arriving later is silently dropped.

### Likelihood Explanation

**Medium.** The Peras certificate diffusion mini-protocol is wired into the production `NodeKernel` via `makePerasCertPoolWriterFromChainDB`. Any peer that can open a connection to the node can submit certificates. No stake, no key material, and no prior relationship is required. The only constraint is that Peras must be active (the round clock must be running); once it is, the attack is trivially repeatable.

### Recommendation

Replace the stub with real validation before the Peras round clock is activated. At minimum, `validatePerasCert` must:
1. Verify the aggregate BLS vote signature against the declared voter set and election ID.
2. Verify that each declared voter is an eligible committee member (persistent or non-persistent via VRF proof).
3. Verify that the aggregate stake of the declared voters meets the quorum threshold.

Until real validation is implemented, the certificate inbound path should reject all certificates (return `Left PerasValidationErr`) rather than accept all of them, so that the stub fails safe rather than fails open.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
