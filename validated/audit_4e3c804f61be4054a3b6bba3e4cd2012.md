### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Fake Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural validation whatsoever. This stub is wired directly into the live `hPerasCertDiffusionClient` handler via `makePerasCertPoolWriterFromChainDB`. Any unprivileged peer connected over the node-to-node protocol can send crafted `PerasCert` messages that are accepted without question, stored in the `PerasCertDB`, and fed into chain selection, where the injected weight boost can cause the node to prefer a non-canonical fork.

---

### Finding Description

**Root cause — always-`Right` certificate validator:**

The degenerate `BlockSupportsPeras` instance (the only instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its content, is wrapped in `Right` and assigned the full `perasWeight`. No signature, committee membership, round validity, or quorum check is performed.

**Wiring into the live peer handler:**

`makePerasCertPoolWriterFromChainDB` passes this stub directly as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

This writer is then passed to `objectDiffusionInbound` in the production `hPerasCertDiffusionClient` handler, which is the responder for every inbound peer connection:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

**`processCerts` accepts all certificates that pass the stub:**

`processCerts` calls `validateCert` on each new certificate. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

**Chain selection is triggered with the injected boost:**

`chainSelSync` processes the queued certificate: it stores it in `PerasCertDB` and, if the boosted block is in the `VolatileDB`, immediately calls `chainSelectionForBlock` for that block: [5](#0-4) 

**Chain selection uses the injected weight:**

`WeightedSelectView.preferCandidate` compares `wsvTotalWeight`, which is `PerasWeight(blockNo) + wsvWeightBoost`. A fake certificate adds `perasWeight params` to the boosted block's fragment weight, potentially making a shorter fork appear heavier than the honest chain: [6](#0-5) 

---

### Impact Explanation

**Severity: High — chain selection manipulation via unauthorized certificate acceptance.**

An unprivileged peer can inject a `PerasCert` that boosts any block in the node's `VolatileDB`. Because `validatePerasCert` never rejects anything, the certificate is stored and its weight boost is applied during chain selection. If the boosted block is on a fork that is currently shorter than the honest chain, the added `perasWeight` can flip the `wsvTotalWeight` comparison, causing the node to roll back to and adopt the attacker-chosen fork. This is a direct bypass of the Peras certificate verification check — the exact check that is supposed to prevent unauthorized chain-weight manipulation — and matches the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, as well as *bypass of Peras certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

**Realistic and low-barrier.** Any node that has the Peras certificate diffusion miniprotocol enabled (wired in unconditionally in `NodeToNode.hs`) accepts inbound connections from peers. No keys, stake, or privileged access are required. The attacker only needs to:
1. Establish a standard node-to-node connection.
2. Send a `PerasCert` message with a crafted `pcCertBoostedBlock` pointing to a block already in the target node's `VolatileDB`.

The `processCerts` deduplication check (line 166) only prevents re-injection of a certificate for the same round number, so one certificate per round is sufficient to permanently alter chain selection for that round.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- The certificate's BLS/committee aggregate signature against the registered committee for the claimed round.
- That the claimed round number is within the valid window relative to the current slot.
- That the boosted block hash corresponds to a block that was actually a valid candidate in that round.

Until real validation is implemented, the `hPerasCertDiffusionClient` handler should not be wired into production node builds, or should be gated behind a feature flag that is disabled by default. The `-- TODO replace when actual plumbing is in place` comment at line 126 of `PerasCert.hs` and the linked issue (cardano-peras#120) confirm the team is aware the stub is incomplete, but the handler is already live and reachable.

---

### Proof of Concept

**Setup:** Two nodes, A (honest) and B (attacker). Node A has a current chain of length N and a fork of length N-2 in its `VolatileDB` (e.g., received via normal block diffusion but not selected).

**Steps:**

1. Attacker B connects to node A over the node-to-node protocol with Peras cert diffusion enabled.
2. B sends a `PerasCert` message:
   - `pcCertRound` = any round number not yet in A's `PerasCertDB`
   - `pcCertBoostedBlock` = the tip of the N-2 fork block (hash known from public chain data)
3. On A, `hPerasCertDiffusionClient` → `objectDiffusionInbound` → `opwAddObjects` → `processCerts` → `validatePerasCert` returns `Right` unconditionally.
4. `ChainDB.addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` stores the cert and calls `chainSelectionForBlock` for the fork tip.
6. `WeightedSelectView.preferCandidate` computes: fork weight = `(N-2) + perasWeight` vs honest weight = `N + 0`. If `perasWeight > 2`, the fork wins and node A rolls back to the attacker-chosen chain.

**Expected outcome:** Node A switches to the attacker-chosen fork, diverging from the honest chain.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
