### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Victim's Unfinalized BTC Deposit to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` performs no check that the caller is the intended recipient of the deposit. When a victim's `DepositMsg` was constructed with `refund_address: None`, any unprivileged NEAR account can call `request_refund` supplying the victim's `deposit_msg` together with an attacker-controlled BTC `refund_address`. After the `unsafe_refund_timelock_sec` window elapses, the attacker calls `execute_refund` and the bridge MPC pipeline sends the victim's BTC to the attacker's address.

### Finding Description

`request_refund` is a public, permissionless function (no `#[trusted_relayer]` guard, unlike `verify_deposit`, `verify_withdraw`, and `verify_refund_finalize`): [1](#0-0) 

The only address-consistency check inside `internal_request_refund` is: [2](#0-1) 

This check only fires when `deposit_msg.refund_address` is `Some(...)`. When it is `None`, the caller-supplied `refund_address` is accepted verbatim with no ownership verification whatsoever. The `deposit_msg.recipient_id` field — the NEAR account that owns the deposit — is never compared against `env::predecessor_account_id()`.

After the request is stored, `execute_refund` is equally permissionless: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `unsafe_refund_timelock_sec` (default 14 days) instead of the shorter `refund_timelock_sec`: [4](#0-3) [5](#0-4) 

After the timelock, `internal_execute_refund` builds the PSBT paying `refund_request.refund_address` — the attacker's address — and submits it to the MPC signing pipeline: [6](#0-5) 

### Impact Explanation

A victim deposits BTC to a bridge address derived from a `DepositMsg` with `refund_address: None`. If `verify_deposit` is never called (relayer outage, user changed mind, etc.), the attacker:

1. Reconstructs the victim's public `deposit_msg` (the deposit address is derived deterministically from it via `get_deposit_path`).
2. Calls `request_refund(victim_deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)`.
3. Waits 14 days.
4. Calls `execute_refund(utxo_storage_key, None)`.

The bridge MPC signs and broadcasts a Bitcoin transaction paying the victim's BTC to the attacker's address. The victim's funds are permanently lost. This matches **Critical — Significant loss or theft of user funds**.

### Likelihood Explanation

The conditions are realistic:
- Deposits without a pre-authorized `refund_address` are the common case (the field is optional and `skip_serializing_if = "Option::is_none"`).
- Relayer downtime or user abandonment of a deposit is a documented scenario (the entire refund flow exists for this reason).
- All inputs needed to call `request_refund` (the `deposit_msg`, `tx_bytes`, Merkle proof) are derivable from public Bitcoin chain data and the NEAR event log (`Event::LogDepositAddress`).
- The 14-day window is a social/operational defense, not a cryptographic one; a DAO that does not actively monitor every refund request will miss the attack.

### Recommendation

Add a caller-authorization check in `request_refund` (or `internal_request_refund`) when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    let caller = env::predecessor_account_id();
    require!(
        caller == deposit_msg.recipient_id,
        "Only the deposit recipient may request a refund with a custom refund address"
    );
}
```

Alternatively, remove the `refund_address: None` path entirely and require every deposit that wants refund eligibility to pre-authorize a BTC address in `deposit_msg.refund_address` at deposit time.

### Proof of Concept

1. Alice deposits 1 BTC to the bridge using `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The relayer never calls `verify_deposit`.
2. Attacker (Bob) observes the BTC transaction on-chain and the `LogDepositAddress` NEAR event, reconstructing Alice's exact `deposit_msg`.
3. Bob calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
     refund_address = "bc1q_attacker_address",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid Merkle proof>,
     gas_fee = None
   )
   ```
   This passes all checks: the script_pubkey of `tx_bytes[vout]` matches the deposit address derived from Alice's `deposit_msg`, and there is no caller check.
4. After 14 days, Bob calls `execute_refund(utxo_storage_key, None)`.
5. The bridge builds and MPC-signs a Bitcoin transaction paying Alice's 1 BTC (minus gas fee) to Bob's address. Alice's funds are stolen. [7](#0-6) [8](#0-7)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
