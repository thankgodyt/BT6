Audit Report

## Title
Unhandled `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call` is `false`, without inspecting the actual promise result of the dispatched `ft_transfer`. If `ft_transfer` fails for a non-deployed token with an empty `msg`, the callback silently enters the success branch: the transfer ID remains in the finalized set (blocking replay), the locked-token counter stays decremented, and the tokens remain stranded in the bridge contract with no recovery path.

## Finding Description

In `process_fin_transfer_to_near`, three state mutations occur before the token delivery resolves:

1. `add_fin_transfer` (line 1875) — marks the transfer ID as finalized.
2. `unlock_tokens_if_needed` (line 1881–1885) — decrements the locked-token counter.
3. `send_tokens` (line 1957–1977) — for a non-deployed token with empty `msg`, dispatches `ft_transfer` (line 2102–2106) and chains `fin_transfer_send_tokens_callback` with `is_ft_transfer_call = !msg.is_empty()` = `false`.

Inside the callback (line 1702), `is_refund_required(false)` is called. The function at lines 1800–1802 unconditionally returns `false` for the non-`ft_transfer_call` path without reading the promise result at all:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

When `ft_transfer` fails, the callback enters the `else` branch (line 1719): `revert_lock_actions` is not called, `remove_fin_transfer` is not called, and the fee is dispatched with `.detach()`. The transfer ID is permanently finalized, the locked-token counter is permanently decremented, and the tokens remain physically in the bridge contract with no accounting entry and no admin escape hatch for per-user recovery.

The revert path at lines 1712–1718 (`revert_lock_actions` + `remove_fin_transfer`) is structurally unreachable for any non-`ft_transfer_call` delivery, regardless of whether `ft_transfer` succeeded or failed.

## Impact Explanation

This is a **Critical** impact matching "permanent freezing of bridged funds across NEAR." For any non-deployed (natively locked) NEP-141 token whose `ft_transfer` can revert after storage registration is confirmed:

| State field | Expected after success | Actual after silent failure |
|---|---|---|
| `finalised_transfers` | transfer ID present | transfer ID present (replay blocked) |
| `locked_tokens[chain][token]` | decremented | decremented (mis-accounting) |
| recipient token balance | credited | unchanged |
| bridge token balance | decremented | unchanged (tokens stranded) |

The user's bridged funds are permanently frozen. No re-submission is possible because replay protection blocks it. No admin function exists to recover stranded tokens for a specific user.

## Likelihood Explanation

The trigger requires a non-deployed NEP-141 token whose `ft_transfer` can revert after the relayer has satisfied the storage-deposit pre-check. Realistic triggers include token-level pause (USDC, USDT expose `pause`/`freeze` callable by the token issuer) or per-account blocklists (common in regulated stablecoins). A pause activated between the relayer's `fin_transfer` call and the inner `ft_transfer` execution satisfies the condition. The relayer role is unprivileged and publicly callable; no admin compromise is required. The recipient is the user who initiated the cross-chain transfer.

## Recommendation

Extend `is_refund_required` to inspect the `ft_transfer` promise result even when `is_ft_transfer_call` is `false`. On failure (`Err`), return `true` to trigger the existing revert path:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Err(_) => true, // ft_transfer or ft_transfer_call panicked → revert
        Ok(value) if is_ft_transfer_call => {
            near_sdk::serde_json::from_slice::<U128>(&value)
                .map_or(false, |a| a.0 == 0)
        }
        Ok(_) => false, // ft_transfer succeeded
    }
}
```

This ensures `revert_lock_actions` and `remove_fin_transfer` are called on any delivery failure, restoring escrow accounting and allowing the transfer to be retried once the token contract is unpaused or the blocklist entry is removed.

## Proof of Concept

1. User initiates a transfer of a pausable non-deployed token (e.g., bridged USDC) from Ethereum to NEAR.
2. The token issuer pauses the USDC contract on NEAR (or adds the recipient to the blocklist).
3. A relayer calls `fin_transfer` with a valid proof and correct `storage_deposit_actions` (recipient has storage registered).
4. `process_fin_transfer_to_near` runs: `add_fin_transfer` fires (line 1875), `unlock_tokens_if_needed` decrements the locked counter (line 1881–1885), `send_tokens` dispatches `ft_transfer` (line 2102–2106).
5. `ft_transfer` fails (USDC contract paused / recipient blocked).
6. `fin_transfer_send_tokens_callback` runs with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` (line 1800–1802) without inspecting the promise result.
8. Callback enters the success branch (line 1719): fee dispatched with `.detach()`, no state revert.
9. **Result**: transfer ID is finalized (replay blocked), locked-token counter is decremented, USDC tokens remain stranded in the bridge contract, user balance is zero. No recovery path exists.
