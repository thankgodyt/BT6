### Title
Unvalidated `refund_address` in `request_refund` Enables Attacker-Triggered Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund` entry point accepts a `refund_address: String` parameter and stores it verbatim in a `RefundRequest` without validating that it is a parseable BTC/ZEC address. Address parsing is deferred to `execute_refund` → `build_refund_output`, where an invalid address causes a hard panic. An unprivileged attacker can front-run a legitimate user's refund by submitting a request with a syntactically invalid address, permanently blocking the victim's refund path until a DAO operator manually rejects the poisoned request.

### Finding Description
`internal_request_refund` performs three checks before storing a `RefundRequest`:

1. Sufficient attached deposit for storage.
2. `tx_bytes` length ≤ `MAX_REQUEST_REFUND_TX_BYTES`.
3. If `deposit_msg.refund_address` is `Some`, the `refund_address` parameter must equal it. [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a refund address), check 3 is skipped entirely. The `refund_address` string is forwarded to `request_refund_callback` and stored without any format or network-validity check: [2](#0-1) 

The validation only occurs later, inside `build_refund_output`, which is called by `execute_refund`: [3](#0-2) 

`Address::parse(...).expect("Invalid refund address")` panics on any non-parseable string, reverting the entire `execute_refund` call and leaving the `RefundRequest` intact in storage.

Because `request_refund` has no caller-identity check (any NEAR account may call it for any UTXO), and because `deposit_msg` fields are public (emitted in events), an attacker can race the victim to submit a request for the victim's UTXO with a garbage `refund_address`. [4](#0-3) 

Once stored, a second `request_refund` for the same UTXO is rejected: [5](#0-4) 

### Impact Explanation
The victim's BTC is already locked in the bridge-controlled deposit address (they sent it expecting either a deposit or a refund). With the refund path poisoned:

- `execute_refund` panics every time it is called for that UTXO.
- The victim cannot submit a new `request_refund` ("Refund request already exists for this UTXO").
- If the relayer is also unavailable (the scenario that motivated the refund), `verify_deposit` cannot be called either.
- The victim's BTC remains locked until a DAO/RefundOperator account calls `reject_refund` to remove the poisoned entry.

This matches the allowed Medium impact: **attacker-triggered temporary locking of bridged funds** and **stuck bridge state requiring operator intervention**.

### Likelihood Explanation
- `deposit_msg` contents are public (logged in `Event::LogDepositAddress` and `Event::RefundRequested`).
- The attacker only needs to pay the anti-spam storage deposit (≈ 2 NEAR) to execute the attack.
- NEAR transaction ordering is deterministic within a block; a well-timed submission or a simple mempool watch is sufficient to front-run the victim.
- The attack is most effective when the relayer is down (exactly when users need refunds), making it a targeted griefing vector.

### Recommendation
Validate `refund_address` as a parseable address for the configured chain at the beginning of `internal_request_refund`, before the cross-contract call to the light client:

```rust
// In internal_request_refund, after the existing checks:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the validation already present in `build_refund_output` and eliminates the window between storage and execution where an invalid address can cause a stuck state.

### Proof of Concept
1. Alice sends 100 000 sat to the deposit address derived from `DepositMsg { recipient_id: alice, refund_address: None, ... }`. The relayer goes offline; Alice needs a refund.
2. Bob observes Alice's `deposit_msg` from on-chain events and her BTC transaction.
3. Bob calls `request_refund(alice_deposit_msg, "NOT_A_VALID_ADDRESS", alice_tx_bytes, 0, proof, None)` with the required NEAR deposit. The `deposit_msg.refund_address` is `None`, so the matching check is skipped. `request_refund_callback` stores `RefundRequest { refund_address: "NOT_A_VALID_ADDRESS", ... }`. [6](#0-5) 

4. Alice calls `request_refund` → rejected: "Refund request already exists for this UTXO".
5. Anyone calls `execute_refund(utxo_key)` → `build_refund_output` calls `Address::parse("NOT_A_VALID_ADDRESS", chain).expect(...)` → **panic**, transaction reverts, `RefundRequest` remains. [3](#0-2) 

6. Alice's BTC is stuck until a DAO account calls `reject_refund(utxo_key)`.

    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())

                "Only DAO or Operator can specify custom gas_fee"
            );

        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
