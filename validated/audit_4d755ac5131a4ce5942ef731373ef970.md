### Title
Invalid Peras Vote in Batch Causes Silent Discard of All Valid Votes in the Same Batch - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

### Summary

The `processVotes` function in the Peras vote inbound path rejects an **entire batch** of votes when any single vote in the batch fails validation, silently discarding all valid votes in the same batch. An unprivileged peer can exploit this by mixing one crafted invalid vote into a batch of otherwise valid votes relayed from honest committee members, causing the victim node to permanently lose those valid votes. If the victim node cannot recover them from other peers in time, it fails to reach quorum, no Peras certificate is generated, the boosted block loses its Peras weight, and the node's chain selection diverges from the rest of the network.

The same structural flaw exists in the analogous `processCerts` function in `PerasCert.hs`.

### Finding Description

In `processVotes`:

```haskell
case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    -- Some votes are invalid => reject the whole batch
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```

The `(errs, _)` arm discards the second component of `partitionEithers` — the valid votes — whenever at least one vote fails validation. [1](#0-0) 

The function is called from both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`, which are the production inbound handlers for Peras votes received over the object-diffusion mini-protocol. [2](#0-1) 

Vote validation (`validatePerasVote`) currently only checks that the voter ID is present in the stake distribution; it does not yet verify the vote signature (explicitly marked TODO). [3](#0-2) 

This means a vote with an unknown voter ID (or, once signature checking is added, a vote with a forged/invalid signature) is sufficient to poison an entire batch.

The identical pattern exists in `processCerts`:

```haskell
(errs, _) ->
  throw (PerasCertValidationError errs)
``` [4](#0-3) 

### Impact Explanation

Peras certificates boost the weight of a block in chain selection. [5](#0-4) 

If a victim node never accumulates enough valid votes to reach quorum, no certificate is generated for the round, the boosted block does not receive its Peras weight, and the node's `compareAnchoredFragments` call will rank chains differently from nodes that did receive the certificate. [6](#0-5) 

This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain by suppressing the Peras weight boost that the rest of the network applies.

### Likelihood Explanation

The attack requires no special privileges. Any peer participating in the object-diffusion mini-protocol can send a batch of votes. Constructing a vote with an unknown voter ID is trivial. The attacker only needs to be one of the victim's vote-diffusion peers and to send the poisoned batch before the victim receives the valid votes from other peers. In a sparse or adversarially partitioned network, this is straightforward.

### Recommendation

Replace the all-or-nothing batch rejection with per-vote handling: validate each vote independently, add the valid ones to the pool, and only disconnect (or penalize) the peer for the invalid ones. This mirrors the fix recommended in the reference report — do not let control flow over one invalid item suppress processing of the remaining valid items.

```haskell
-- Instead of:
case partitionEithers validationResults of
    ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _)            -> throw (PerasVoteValidationError errs)

-- Prefer:
case partitionEithers validationResults of
    ([], validatedVotes) -> mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, validatedVotes) -> do
        mapM_ (addVote . WithArrivalTime now) validatedVotes
        throw (PerasVoteValidationError errs)
```

Apply the same fix to `processCerts`.

### Proof of Concept

1. Honest committee members A, B, C cast votes for block P in round R. Their votes propagate to a relay peer M (controlled by the attacker).
2. M constructs a synthetic `PerasVote` with a `pvVoteVoterId` not present in the current stake distribution (guaranteed to fail `validatePerasVote`).
3. M sends a single batch `[voteA, voteB, voteC, fakevote]` to victim node V via the object-diffusion protocol.
4. `processVotes` calls `partitionEithers` on the four validation results: three `Right` values and one `Left`.
5. The `(errs, _)` branch fires; `voteA`, `voteB`, `voteC` are silently discarded. V disconnects from M.
6. If M was V's only source for those votes (e.g., in a low-connectivity scenario or during the brief window before other peers relay them), V never accumulates quorum for round R.
7. No certificate is generated for P on V. V's chain selection does not apply the Peras weight boost to P, causing V to prefer a different tip than the rest of the network. [7](#0-6) [8](#0-7)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
