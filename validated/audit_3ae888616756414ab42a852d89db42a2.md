### Title
Intra-batch duplicate `PerasRoundNo` not checked in `processCerts`, allowing a malicious peer to inject equivocating Peras certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` deduplicates inbound Peras certificates only against the DB state fetched once at the start of the function. It performs no intra-batch uniqueness check on `PerasRoundNo`. A malicious peer can craft a single batch containing two certificates for the same round number — an equivocating cert (boosting block Y) followed by the legitimate cert (boosting block X). Both entries survive the filter, both pass the stub `validatePerasCert` (which unconditionally returns `Right`), and both are forwarded to `addCert`. The `PerasCertDB` stores whichever cert arrives first and silently discards the second. By placing the equivocating cert first in the batch, the attacker permanently poisons the cert DB for that round, causing the node to boost the wrong block during chain selection.

---

### Finding Description

`processCerts` fetches the set of already-known round numbers once, atomically, at the top of the function:

```haskell
alreadyInDb <- atomically alreadyInDbSTM
let certsNotAlreadyInDb =
      filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
``` [1](#0-0) 

If the incoming `certs` list contains two entries sharing the same `PerasRoundNo`, both survive the filter because neither is yet in `alreadyInDb`. The function then validates every surviving cert and, on all-success, adds them sequentially:

```haskell
([], validatedCerts) ->
  mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [2](#0-1) 

The current `validatePerasCert` implementation is an explicit stub that unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [3](#0-2) 

`implAddCert` in `PerasCertDB.Impl` does guard against duplicate round numbers within its own STM transaction, so the second `addCert` call returns `PerasCertAlreadyInDB` and is silently discarded:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do ...
``` [4](#0-3) 

The result is that **whichever cert appears first in the peer-supplied batch wins**. The attacker controls batch ordering.

The same structural flaw exists in `processVotes` for the `PerasVoteId` key:

```haskell
let votesNotAlreadyInDb =
      filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
mapM validateVote votesNotAlreadyInDb
``` [5](#0-4) 

The state machine test model explicitly acknowledges that equivocating certificates (same round, different boosted block) must be rejected, but enforces this only as a test precondition, not in production code:

```haskell
-- We should reject equivocating certificates, that is, certificates
-- for the same round but boosting different blocks.
p cert' =
  getPerasCertRound cert /= getPerasCertRound cert'
    || getPerasCertBoostedBlock cert == getPerasCertBoostedBlock cert'
``` [6](#0-5) 

---

### Impact Explanation

Peras certificates directly influence chain selection by assigning a boost weight to a specific block. A cert stored for round R that boosts block Y instead of the legitimate block X causes the node to prefer a chain containing Y over the canonical chain containing X. This is a chain-selection bug triggered by an unprivileged peer via a crafted object-diffusion batch, matching the **High** impact category: "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

The `makePerasCertPoolWriterFromChainDB` production path passes the poisoned cert directly to `ChainDB.addPerasCertAsync`, which triggers chain selection side-effects:

```haskell
(void . ChainDB.addPerasCertAsync chainDB)
``` [7](#0-6) 

---

### Likelihood Explanation

The object-diffusion mini-protocol is a public, peer-facing interface. Any connected peer can send a crafted batch. No stake, key material, or operator access is required. The stub `validatePerasCert` removes the only other gate that might have caught the equivocating cert. Likelihood is **Medium**: the Peras protocol is not yet deployed on mainnet, but the code is in the production path and the attack requires only a single malformed network message.

---

### Recommendation

Add an intra-batch uniqueness check on `PerasRoundNo` inside `processCerts` before validation. If the batch contains two or more entries with the same round number, treat it as a protocol violation and throw `PerasCertInboundException` (disconnecting the peer), consistent with how invalid certs are already handled. The same fix should be applied to `processVotes` for `PerasVoteId`.

```haskell
-- After filtering against alreadyInDb, before validation:
let roundNos = map getPerasCertRound certsNotAlreadyInDb
    hasDuplicates = length roundNos /= Set.size (Set.fromList roundNos)
when hasDuplicates $ throw (PerasCertValidationError [])
```

Additionally, once `validatePerasCert` is fully implemented (tracked in issue #120), it should explicitly reject equivocating certificates as a second line of defence.

---

### Proof of Concept

1. Honest node is connected to a malicious peer via the object-diffusion mini-protocol.
2. Malicious peer constructs a batch: `[cert_round5_blockY, cert_round5_blockX]` where `blockY ≠ blockX`.
3. Peer calls `opwAddObjects` on the node's `ObjectPoolWriter`, delivering the batch to `processCerts`.
4. `alreadyInDb` is fetched; round 5 is not present, so both certs pass the `filter`.
5. `validatePerasCert` (stub) returns `Right` for both.
6. `mapM_` calls `addCert` for `cert_round5_blockY` first; `implAddCert` stores it and inserts round 5 into `pcdsCertIds`.
7. `mapM_` calls `addCert` for `cert_round5_blockX`; `implAddCert` finds round 5 already in `pcdsCertIds` and returns `PerasCertAlreadyInDB` — silently discarded.
8. The node's cert DB now permanently associates round 5 with `blockY`. Chain selection boosts `blockY` instead of the canonical `blockX`.
9. Any subsequent honest peer sending the legitimate `cert_round5_blockX` is silently ignored because round 5 is already in the DB. [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
