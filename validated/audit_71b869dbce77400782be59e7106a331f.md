### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Certificate — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the `BlockSupportsPeras` typeclass default implementation is a stub that unconditionally returns `Right` (success) for every certificate, performing no cryptographic or structural verification. This stub is wired directly into the production `hPerasCertDiffusionClient` handler via `makePerasCertPoolWriterFromChainDB`. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and block hash; the node will accept it, store it in the `PerasCertDB`, and potentially apply its Peras weight boost during chain selection.

---

### Finding Description

**Vulnerability class (from external report):** A critical security function is defined but never properly implemented or wired into the dispatch mechanism, making the security check permanently non-functional. In the external report, `acceptOwnership()` was never added to the diamond's function selector cut. Here, `validatePerasCert` is wired into the production pipeline but its implementation is a stub that always succeeds — the verification step is structurally present but functionally absent.

**Root cause — `validatePerasCert` stub:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the default implementation of `validatePerasCert` unconditionally accepts every certificate:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature, quorum, round-number, or boosted-block validity check is performed. The `PerasValidationErr` type exists but is never populated with real error variants, and the function always returns `Right`. [2](#0-1) 

**Production wiring — `hPerasCertDiffusionClient`:**

`makePerasCertPoolWriterFromChainDB` (called with `systemTime` and `getChainDB`) is passed directly as the `ObjectPoolWriter` to `objectDiffusionInbound` inside `hPerasCertDiffusionClient` in `mkHandlers`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [3](#0-2) 

This handler is registered in the production `initiatorAndResponder` function as `perasCertDiffusionProtocol`, making it reachable by any connecting peer: [4](#0-3) 

**Contrast with vote handling:**

The analogous vote path (`hPerasVoteDiffusionClient`) at least attempts validation against a stake distribution, but uses `pure (PerasVoteStakeDistr mempty)` — an empty map — causing all votes to be rejected. The cert path has no such guard at all; it accepts everything. [5](#0-4) 

**Accepted certs influence chain selection:**

The `ChainDB` API exposes `getPerasWeightSnapshot` and `addPerasCertAsync`, which are used to apply Peras weight boosts during chain selection. A cert accepted via the stub flows through `addPerasCertAsync` and is reflected in `getPerasWeightSnapshot`. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` containing an arbitrary `pcCertRound` and `pcCertBoostedBlock` (any block hash). Because `validatePerasCert` always returns `Right`, the certificate is stored in the `PerasCertDB` and its Peras weight boost is applied to the targeted block during chain selection. This allows an attacker to make an honest node prefer a non-canonical or adversarially chosen chain by boosting a block that would otherwise lose chain selection. This maps to:

> **Critical/High.** Bypass of Peras certificate verification checks that enables unauthorized certificate acceptance and chain selection manipulation by an unprivileged peer.

---

### Likelihood Explanation

The `perasCertDiffusionProtocol` is fully wired into the production `initiatorAndResponder` bundle and `mkHandlers`. Any peer that connects and speaks `NodeToNodeV_16` (or later) can send `PerasCert` messages. No authentication, stake ownership, or key possession is required. The attack path is direct and requires no special privileges.

---

### Recommendation

1. **Do not deploy `hPerasCertDiffusionClient` in production until `validatePerasCert` performs real cryptographic verification** (aggregate BLS signature check, quorum check, round-number bounds check, boosted-block existence check).
2. Until proper validation is implemented, gate the `perasCertDiffusionProtocol` behind a feature flag that is disabled by default, analogous to how `EnableNewTxSubmissionProtocol` gates the new TX submission path.
3. Implement concrete `PerasValidationErr` variants (tracked in issue #120) and ensure `validatePerasCert` returns `Left` for any certificate that fails cryptographic or structural checks.

---

### Proof of Concept

A node running with `NodeToNodeV_16` support accepts the `perasCertDiffusionProtocol`. An attacker connects as a peer and sends a `PerasCert` with:
- `pcCertRound = maxBound` (or any round)
- `pcCertBoostedBlock = <hash of attacker-chosen block>`

Because `validatePerasCert` always returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`, the cert is stored via `addPerasCertAsync`. The `getPerasWeightSnapshot` STM action now returns a snapshot that boosts the attacker-chosen block. If the Peras weight boost is large enough relative to the chain density difference, the honest node's chain selection will prefer the attacker's targeted chain over the canonical chain.
