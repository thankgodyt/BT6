Audit Report

## Title
Dust transfers normalizing to zero are permanently locked/burned with no recovery path — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts, burns or locks user tokens, and stores the transfer in `pending_transfers` without verifying that the post-normalization amount is non-zero. When a user bridges a dust amount whose normalized value rounds to zero under integer division, the tokens are irrecoverably destroyed (deployed tokens) or locked (native tokens), and every subsequent `sign_transfer` call for that transfer ID permanently reverts with `InvalidAmountToTransfer`. No user-accessible cancel or refund path exists.

## Finding Description
`sign_transfer` normalizes the transfer amount to the destination chain's decimal precision and enforces a non-zero guard:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` uses floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 18` and `decimals = 6`, any `amount < 10^12` produces `normalize_amount(...) = 0`. The guard in `sign_transfer` proves this is a reachable code path.

`init_transfer` (L523–618) constructs the `TransferMessage` and calls `init_transfer_internal` with no equivalent normalization check. `init_transfer_internal` (L1829–1865) unconditionally:
1. Inserts the transfer into `pending_transfers` via `add_transfer_message`
2. Calls `burn_tokens_if_needed` for deployed tokens — permanently destroying them
3. Calls `lock_tokens_if_needed` for native tokens
4. Returns `U128(0)`, so `ft_on_transfer` refunds nothing to the caller

Once stored, the only removal paths are `remove_transfer_message` (called inside `claim_fee_callback`, which requires a valid `fin_transfer` proof from the destination chain — impossible since `sign_transfer` always reverts) and `remove_transfer_message_without_refund` (called only on storage-balance failure or non-NEAR token, neither of which applies here). There is no `cancel_transfer` or user-accessible refund function.

The code comment on `normalize_amount` (L2781–2783) acknowledges dust behavior: *"When fee = 0, dust stays locked/burned."* This refers to the sub-unit remainder from normalization, not the case where the entire transferred amount normalizes to zero — a materially more severe outcome.

## Impact Explanation
For deployed (bridged) tokens: `burn_tokens_if_needed` permanently destroys the user's tokens. Even DAO intervention cannot restore burned supply. For native NEAR tokens: tokens are held by the bridge contract with no user-accessible recovery path. In both cases the user suffers permanent, unrecoverable loss of bridged funds, matching the critical impact class of **permanent freezing/loss of bridged assets**.

## Likelihood Explanation
Any unprivileged user can trigger this by calling `ft_transfer_call` with a dust amount on any token whose NEAR decimal count exceeds the destination chain's decimal count. No special role or permission is required. The condition is met whenever `amount < 10^(origin_decimals − decimals)`, a realistic edge case for tokens with large decimal mismatches (e.g., 18 vs. 6). The attack is repeatable and requires no coordination.

## Recommendation
Inside `init_transfer` (or at the start of `init_transfer_internal`), compute the normalized amount using the same `normalize_amount` logic used in `sign_transfer`. If the result is zero, return the full token amount to the caller (triggering a refund via `ft_on_transfer`) before any tokens are burned or locked and before the transfer is inserted into `pending_transfers`.

## Proof of Concept
1. Register a token with `origin_decimals = 18` on NEAR and `decimals = 6` on Ethereum.
2. User calls `ft_transfer_call` sending `amount = 1` yocto with an `InitTransfer` message targeting Ethereum (fee = 0).
3. `init_transfer` → `init_transfer_internal`: the fee check `fee < amount` passes (0 < 1); `burn_tokens_if_needed` burns 1 yocto; transfer is stored in `pending_transfers`; `ft_on_transfer` returns `U128(0)` — no refund.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(1, Decimals { decimals: 6, origin_decimals: 18 })` = `1 / 10^12 = 0`.
6. `require!(0 > 0, BridgeError::InvalidAmountToTransfer)` panics — call reverts.
7. `claim_fee_callback` is unreachable (no valid destination-chain proof can exist). No other code path removes this transfer or recovers the burned tokens. The user's funds are permanently lost.
