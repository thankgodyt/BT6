### Title
Degenerate `BlockSupportsPeras` Instance Unconditionally Accepts Any Peras Certificate Without Cryptographic Validation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a degenerate, no-op implementation of `validatePerasCert` that unconditionally returns `Right` (success) for every certificate it receives, skipping all cryptographic and semantic checks. An unprivileged peer that can submit a crafted `PerasCert` to a node running this instance will have it accepted as fully valid, enabling unauthorized Peras certificate acceptance and illegitimate chain boosting.

---

### Finding Description

The file `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines a catch-all `BlockSupportsPeras` instance for any `StandardHash blk`:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Within this instance, `validatePerasCert` is implemented as:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This function accepts **any** `PerasCert` value — regardless of its round number, boosted block target, voter set, or aggregate BLS signature — and wraps it in a `ValidatedPerasCert` with the full configured `perasWeight`. No signature verification, no quorum check, no round-number sanity check, and no membership check is performed.

The same instance also provides a `validatePerasVote` that only checks stake-distribution membership by voter ID but **never verifies the BLS vote signature**:

```haskell
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
```

A peer that knows any legitimate `PerasVoterId` present in the stake distribution can submit a vote with a forged BLS signature and have it accepted.

Additionally, `forgePerasCert` constructs a `ValidatedPerasCert` from any quorum of votes without verifying the aggregate signature, and `getPerasCertInBlock` always returns `Nothing`, meaning no certificate ever extracted from a received block is checked.

---

### Impact Explanation

A Peras certificate, once accepted as `ValidatedPerasCert`, carries a `vpcCertBoost` weight equal to `perasWeight params`. This boost is applied during chain selection to prefer the boosted block over competing forks. Because `validatePerasCert` always succeeds, an unprivileged peer can:

1. Craft an arbitrary `PerasCert` targeting any block hash and any round number.
2. Submit it to a node.
3. Have the node treat it as a fully validated certificate with maximum boost weight.
4. Cause the node to prefer the attacker-chosen chain over the honest canonical chain.

This is a **bypass of Peras certificate verification** that enables unauthorized certificate acceptance and illegitimate chain selection influence — matching the Critical/High impact scope: *"Bypass of… certificate/vote verification… that enables unauthorized block, vote, or certificate acceptance"* and *"Chain selection… bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The degenerate instance is the **only** `BlockSupportsPeras` instance in the repository for production block types (it covers all `StandardHash blk`). The TODO comments reference open issues acknowledging the missing validation. Any node that activates the Peras code path with this instance in place is immediately vulnerable. The attacker needs no keys, no stake, and no privileged access — only the ability to send a well-formed CBOR-encoded `PerasCert` to a peer's miniprotocol endpoint.

---

### Recommendation

Replace the degenerate `validatePerasCert` body with a real implementation that:
- Verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)`.
- Checks that the voter set meets the quorum threshold.
- Validates each voter's committee membership and eligibility proof.
- Rejects certificates whose `pcCertRound` is outside the acceptable window.

Similarly, `validatePerasVote` must verify the BLS vote signature before accepting a vote. The degenerate instance should be removed or gated behind a compile-time flag that prevents it from being linked into production binaries until the real implementation is complete.

---

### Proof of Concept

1. Obtain any `PerasParams` configuration (public, from genesis config).
2. Choose any target block hash `h` on a fork the attacker wishes to boost.
3. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = h }` with an arbitrary (e.g., all-zero) aggregate BLS signature.
4. Serialize it to CBOR and deliver it to a node via the Peras miniprotocol.
5. The node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
