### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural validation. This is the direct analog of the external report's pattern: just as `checkCreateFeesSent` trivially passes when `_depositChainIds.length == 0` (making `fees = 0`), `validatePerasCert` trivially passes for every possible certificate input. Any entity that can submit a `PerasCert` to the node receives a full `PerasWeight` chain-selection boost for an arbitrary block of their choosing, without needing to demonstrate quorum, valid aggregate signatures, or eligible voters.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate for accepting Peras certificates. The production instance (the only instance, applied to all `StandardHash blk`) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub skips every check that a real certificate verifier must perform:
- No aggregate BLS signature verification over the claimed voter set
- No check that the claimed voters were actually eligible committee members
- No check that the claimed voters' combined stake meets the quorum threshold (`perasQuorumStakeThreshold = 3/4` by default)
- No check that the referenced `pcCertBoostedBlock` exists or is on any known chain
- No check that `pcCertRound` is within a valid window

The result is that the function always produces a `ValidatedPerasCert` carrying the full configured `PerasWeight` boost (`perasWeight = 15` in `mkPerasParams`). [2](#0-1) 

The `ValidatedPerasCert` type is the trust boundary: downstream chain-selection logic consumes it as proof that a certificate is legitimate and applies the boost unconditionally. [3](#0-2) 

The companion stub `forgePerasCert` also always returns `Right`, meaning even the local certificate-forging path (triggered when votes reach quorum) bypasses any forge-time invariant checks: [4](#0-3) 

The `PerasVoteDB` implementation calls `forgePerasCert` directly when `votesReachQuorum` returns `Just`, and the resulting `ValidatedPerasCert` is stored and propagated: [5](#0-4) 

The `votesReachQuorum` function itself does guard against an empty vote list and does check `stakeAboveThreshold`, so the quorum gate for locally aggregated votes is intact: [6](#0-5) 

However, `validatePerasCert` is the entry point for **externally received** certificates (e.g., certificates embedded in blocks or delivered via a future certificate-diffusion miniprotocol). Because it always returns `Right`, the quorum gate in `votesReachQuorum` is entirely bypassed for the external path.

The inbound vote processing path (`processVotes`) does call `validatePerasVote`, which at minimum checks that the voter appears in the stake distribution: [7](#0-6) 

But `validatePerasCert` has no equivalent gate at all.

### Impact Explanation

**Severity: High — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

A crafted `PerasCert` pointing to any block (including an adversarially chosen non-canonical block) will be accepted as a `ValidatedPerasCert` with the full `PerasWeight = 15` boost. Chain selection in Peras uses this boost to prefer the boosted block over competing chains. An adversary who can inject a certificate for a minority or invalid chain causes honest nodes to assign it a higher chain weight, potentially making them switch to or extend a non-canonical chain. This directly violates the Peras safety guarantee that only blocks backed by genuine quorum (≥ 3/4 of committee stake) receive a boost.

### Likelihood Explanation

**Likelihood: High.**

The stub is the only production implementation of `validatePerasCert` — there is no other instance. The TODO comment and linked GitHub issue (`#120`) confirm this is a known incomplete state, not a deliberate design choice. Any code path that calls `validatePerasCert` on an externally supplied certificate (present or future) is immediately exploitable. The `ChainDB` state machine already exercises `AddPerasCert` as a reachable operation: [8](#0-7) 

### Recommendation

Replace the stub with a real implementation that:
1. Verifies the aggregate BLS signature in the certificate against the claimed voter set.
2. Checks each claimed voter against the current committee (via `checkShouldVote` / `isPersistentMember` / local sortition).
3. Verifies that the combined stake of the claimed voters satisfies `stakeAboveThreshold` (i.e., ≥ `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
4. Validates that `pcCertBoostedBlock` is a known block and `pcCertRound` is within the valid acceptance window.

Until issue `#120` is resolved, `validatePerasCert` should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the fail-safe direction is rejection rather than acceptance.

### Proof of Concept

```haskell
-- Attacker constructs a certificate for an arbitrary block at an arbitrary round
let fakeCert = PerasCert
      { pcCertRound      = PerasRoundNo 999999
      , pcCertBoostedBlock = someAdversarialBlockPoint
      }

-- validatePerasCert unconditionally accepts it
let Right validatedCert = validatePerasCert mkPerasParams fakeCert
-- validatedCert = ValidatedPerasCert
--   { vpcCert      = fakeCert
--   , vpcCertBoost = PerasWeight 15   -- full boost, no quorum required
--   }

-- The validated cert is now indistinguishable from a legitimately quorum-backed cert
-- and will be used by chain selection to boost someAdversarialBlockPoint
```

The root cause is structurally identical to the external report: `checkCreateFeesSent` computes `fees = createFees * 0 = 0` when the length is zero, trivially satisfying `msg.value >= 0`; `validatePerasCert` computes `Right cert` for every input, trivially satisfying the validation gate. [9](#0-8)

votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
