### Title
Users Cannot Self-Cancel Stuck Withdrawals, Forcing Fee Acceptance or Indefinite nBTC Lock - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The `cancel_withdraw` function is gated exclusively to `Role::DAO` and `Role::Operator`. A user who initiates a withdrawal (nBTC → BTC) has no mechanism to cancel their own pending withdrawal and recover their locked nBTC. If BTC network fees spike beyond what the user's `transfer_amount` can cover, the user cannot perform RBF either, leaving their nBTC permanently locked until a privileged operator intervenes.

---

### Finding Description

When a user initiates a withdrawal via `ft_transfer_call` with a `WithdrawMsg`, their nBTC tokens are held by the bridge contract. The bridge constructs a PSBT and requests an MPC signature. Once the withdrawal enters `PendingVerify` state, the user's only self-service option is `withdraw_rbf` — a fee bump that reduces the amount of BTC they receive.

The critical gap is that there is **no user-initiated cancellation path**. The only cancellation function is:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs, lines 282-299
#[payable]
#[access_control_any(roles(Role::DAO, Role::Operator))]
#[pause(except(roles(Role::DAO)))]
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    ...
    self.cancel_withdraw_chain_specific(...);
}
```

This is restricted to `Role::DAO` or `Role::Operator` only. [1](#0-0) 

The user's only self-service path is `withdraw_rbf`, which bumps the gas fee but deducts it from the user's `transfer_amount`:

```rust
// contracts/satoshi-bridge/src/rbf/withdraw.rs, lines 57-61
let (actual_received_amount, gas_fee) =
    self.check_withdraw_rbf_psbt_valid(original_tx_btc_pending_info, &withdraw_rbf_psbt);
btc_pending_info.gas_fee = gas_fee;
btc_pending_info.actual_received_amount = actual_received_amount;
btc_pending_info.burn_amount = actual_received_amount + gas_fee;
``` [2](#0-1) 

The RBF validation enforces that the recipient address is unchanged and the output count matches the original — the user cannot redirect funds back to themselves. [3](#0-2) 

When BTC fees spike so high that `gas_fee > transfer_amount - withdraw_fee`, the user's `actual_received_amount` reaches zero and RBF becomes economically impossible. At that point:

1. The user cannot call `cancel_withdraw` (no role).
2. The user cannot do RBF (no remaining balance to cover fees).
3. The DAO/Operator cancellation path requires `cur_available_protocol_fee >= excess_gas_fee`, which may also be insufficient.

```rust
// contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs, lines 55-68
let excess_gas_fee = gas_fee
    .saturating_sub(btc_pending_info.transfer_amount - btc_pending_info.withdraw_fee);
if excess_gas_fee > 0 {
    require!(
        self.acl_has_role(Role::DAO.into(), predecessor_account_id),
        "gas fee exceeds the user's balance, only the owner is allowed to cancel"
    );
    require!(
        self.data().cur_available_protocol_fee >= excess_gas_fee,
        "Insufficient protocol fee"
    );
``` [4](#0-3) 

The refund system (`request_refund` / `execute_refund`) is scoped exclusively to unfinalized **deposits** (BTC → nBTC), not to stuck **withdrawals** (nBTC → BTC). [5](#0-4) 

---

### Impact Explanation

A user's nBTC is locked in the bridge with no user-initiated recovery path. If the DAO/Operator is unavailable, slow, or the protocol fee pool is drained, the user's funds are permanently stuck. This matches: **Medium — stuck bridge state requiring operator intervention, with attacker-triggered (fee-spike-triggered) temporary or permanent locking of bridged funds.**

---

### Likelihood Explanation

BTC fee spikes are a well-documented, recurring phenomenon (e.g., Ordinals inscription waves, halving periods). During such events, a withdrawal initiated at low fees can become economically unresolvable by the user alone. The scenario requires no attacker — it is triggered by ordinary network conditions. Likelihood is **Medium**.

---

### Recommendation

Implement a user-initiated cancellation function that allows the withdrawal owner to cancel their own pending withdrawal after a configurable timelock (e.g., `max_btc_tx_pending_sec`), returning their nBTC minus any fees already consumed. This mirrors the fix described in the referenced Connext PR 2456: giving users a self-service escape hatch when they do not wish to accept the cost of proceeding.

```rust
// Pseudocode for user-initiated cancel
pub fn user_cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    let info = self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
    require!(info.account_id == env::predecessor_account_id(), "Not owner");
    require!(
        nano_to_sec(env::block_timestamp()) - info.create_time_sec
            > self.internal_config().max_btc_tx_pending_sec,
        "Timelock not expired"
    );
    // proceed with cancel logic (no excess protocol fee allowed for user-initiated path)
    self.cancel_withdraw_chain_specific(...);
}
```

### Proof of Concept

1. User calls `ft_transfer_call(bridge, 1_000_000 nBTC, WithdrawMsg{...})`. Bridge holds 1,000,000 nBTC; withdrawal enters `PendingVerify`.
2. BTC network fees spike 100×. The original PSBT's gas fee is now far below the required fee for confirmation.
3. User calls `withdraw_rbf` with a new PSBT. `check_withdraw_psbt` computes `gas_fee = 999_000`, `actual_received_amount = 0`. The user is forced to accept receiving 0 BTC, or the validation rejects the PSBT entirely if the math underflows.
4. User attempts `cancel_withdraw` → reverts: `"Caller is not authorized"` (no `Role::DAO` or `Role::Operator`). [6](#0-5) 
5. DAO is slow to respond; `cur_available_protocol_fee` is zero → DAO's own `cancel_withdraw` call reverts: `"Insufficient protocol fee"`. [7](#0-6) 
6. User's 1,000,000 nBTC remains locked in the bridge indefinitely with no self-service recovery path.
