### Title
Any Account Can Trigger `withdraw_rbf` on Another User's Pending Withdrawal, Redirecting BTC Funds — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary
The `withdraw_rbf` function does not verify that the caller owns the pending withdrawal identified by `original_btc_pending_verify_id`. Any unprivileged NEAR account can call `withdraw_rbf` with a victim's pending withdrawal ID and attacker-controlled `output` destinations, causing the MPC to sign a replacement BTC transaction that redirects the victim's BTC to an attacker-chosen address.

---

### Finding Description

`withdraw_rbf` is a public, unprivileged function that allows a user to bump the fee on their own pending BTC withdrawal via Replace-By-Fee. The function accepts an arbitrary `original_btc_pending_verify_id` and a caller-supplied `output` vector (which determines where the BTC is sent in the replacement transaction).

The function derives `account_id` from `env::predecessor_account_id()` (the caller) and immediately passes it — along with the attacker-supplied `original_btc_pending_verify_id` — to `withdraw_rbf_chain_specific`, **without ever checking that the pending withdrawal identified by `original_btc_pending_verify_id` belongs to the caller**:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // attacker's account
    self.require_pending_sign_capacity(&account_id);  // checks attacker's capacity, not victim's

    self.withdraw_rbf_chain_specific(
        account_id,                          // attacker's account
        original_btc_pending_verify_id,      // victim's pending withdrawal ID
        output,                              // attacker-controlled BTC outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

The privileged counterpart `cancel_withdraw` demonstrates the correct pattern: it **first fetches the owner from the pending info** and uses that as the authoritative account ID, rather than blindly trusting the caller:

```rust
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    self.require_pending_sign_capacity(&user_account_id);
    ...
}
``` [2](#0-1) 

The asymmetry is the root cause: `cancel_withdraw` (privileged) correctly resolves the owner from the pending info; `withdraw_rbf` (public) does not. The `require_pending_sign_capacity` call in `withdraw_rbf` operates on the **caller's** account, not the victim's, so an attacker with no pending transactions trivially passes this guard.

The `BTCPendingInfo` struct records the true owner in its `account_id` field: [3](#0-2) 

No check at the `withdraw_rbf` entry point compares `env::predecessor_account_id()` against `btc_pending_info.account_id`.

---

### Impact Explanation

**Critical.** An attacker who successfully calls `withdraw_rbf` on a victim's pending withdrawal with attacker-controlled `output` causes the MPC chain-signature layer to sign a replacement BTC transaction whose outputs redirect the victim's BTC to an attacker-chosen address. Once the replacement transaction is broadcast and confirmed on Bitcoin, the victim's funds are permanently lost. This matches the allowed critical impact: *"Chain-signature, PSBT, or transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds."*

---

### Likelihood Explanation

**High.** `withdraw_rbf` is a public, permissionless function with no attached-deposit requirement and no role guard. Pending withdrawal IDs (`btc_pending_id`) are emitted as on-chain events (`GenerateBtcPendingInfo`), making them trivially discoverable by any observer. An attacker needs only to:

1. Monitor NEAR events for a victim's `btc_pending_id`.
2. Call `withdraw_rbf(victim_pending_id, [attacker_output], ...)` from any NEAR account with no pending transactions. [4](#0-3) 

---

### Recommendation

Before calling `withdraw_rbf_chain_specific`, fetch the pending info and assert that its `account_id` matches the caller:

```diff
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();
+   let pending_info = self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
+   require!(
+       pending_info.account_id == account_id,
+       "Only the owner of the pending withdrawal can submit an RBF"
+   );
    self.require_pending_sign_capacity(&account_id);

    self.withdraw_rbf_chain_specific(
        account_id,
        original_btc_pending_verify_id,
        output,
        chain_specific_data,
    );
}
```

This mirrors the pattern already used correctly in `cancel_withdraw`.

### Proof of Concept

```
// Attacker (bob.near) observes alice.near's pending withdrawal ID from on-chain events.
// alice.near has a pending BTC withdrawal of 1 BTC to her own address.

// Bob calls withdraw_rbf with Alice's pending ID and his own BTC address as output:
near call satoshi-bridge.near withdraw_rbf '{
  "original_btc_pending_verify_id": "<alice_pending_id>",
  "output": [{"value": 99900000, "script_pubkey": "<bob_btc_address_script>"}],
  "chain_specific_data": null
}' --accountId bob.near

// Result:
// - MPC signs a replacement transaction paying Bob's BTC address
// - Alice's 1 BTC is redirected to Bob
// - Alice's original pending withdrawal is superseded by the RBF
// - Alice loses her funds permanently
```
