Audit Report

## Title
Blacklisted ERC-20 Recipient Permanently Freezes Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`finTransfer` in `OmniBridge.sol` writes `completedTransfers[nonce] = true` before calling `safeTransfer`, but because the transfer and the nonce write are in the same atomic transaction, a revert from a blacklisted recipient (e.g., USDC/USDT) rolls back the nonce flag. Every subsequent relay attempt reverts identically, permanently blocking finalization. Because the NEAR side has already burned or locked the tokens in `init_transfer_internal` with no public cancellation entry point, the funds are irrecoverably frozen.

## Finding Description
**EVM — `finTransfer` revert loop:**

`completedTransfers[payload.destinationNonce]` is set to `true` at line 287, before any token movement. [1](#0-0) 

For a native ERC-20 held in the bridge vault (e.g., USDC), the delivery path is: [2](#0-1) 

If `payload.recipient` is on the USDC blacklist, `safeTransfer` reverts unconditionally. The EVM runtime rolls back the entire transaction, including the `completedTransfers[nonce] = true` write. The nonce is never consumed, so every relay retry reverts for the same reason — an infinite revert loop.

**NEAR — tokens committed before EVM finalization:**

`init_transfer_internal` burns bridged tokens (or increments the locked-token counter) and emits `InitTransferEvent` before the relayer ever touches the EVM side: [3](#0-2) 

The only internal helpers that remove a pending transfer — `remove_transfer_message` and `remove_transfer_message_without_refund` — are private `fn` methods, never exposed as `#[near_bindgen]` public entry points: [4](#0-3) 

There is no `cancel_transfer`, `refund_transfer`, or emergency-recovery public function in the contract. Once `InitTransferEvent` is emitted, the NEAR-side state is final with no recovery path.

**Starknet — identical structure:**

`fin_transfer` in `omni_bridge.cairo` calls `_set_transfer_finalised` before the token transfer, then asserts success. A failed transfer reverts the whole call including the nonce write, producing the same permanent revert loop: [5](#0-4) 

## Impact Explanation
Permanent freezing of bridged funds. Tokens burned or locked on NEAR can never be delivered to the EVM recipient and cannot be reclaimed by the sender. This matches the allowed critical impact: *"permanent freezing of bridged funds across NEAR, EVM … flows."* The `evm/SECURITY.md` known-issues list does not acknowledge this scenario. [6](#0-5) 

## Likelihood Explanation
USDC and USDT — both of which implement address blacklists — are primary bridging targets on every supported EVM chain (Ethereum, Arbitrum, Base, Polygon). A recipient can be blacklisted by Circle/Tether at any time after the user submits `init_transfer` on NEAR but before the relayer finalises on EVM. No privileged access is required: any ordinary user who sends to an address that later becomes blacklisted (e.g., due to sanctions enforcement, exchange compliance action, or a compromised wallet) triggers the freeze. The blacklist check is enforced unconditionally inside the USDC token contract and cannot be bypassed by the bridge.

## Recommendation
Replace the direct-push delivery in `finTransfer` with a pull pattern:

1. Instead of calling `safeTransfer(payload.recipient, payload.amount)` directly, credit the amount to a per-recipient claimable balance mapping inside the bridge contract and mark the nonce as consumed.
2. Expose a separate `claimTokens(address token)` function that the recipient calls to pull their balance.
3. This isolates a blacklisted recipient: only their own claim fails; all other `finTransfer` calls succeed normally, and the nonce is consumed.

For the NEAR side, add a DAO-gated `cancel_outbound_transfer(transfer_id)` entry point that re-mints (for bridged tokens) or unlocks (for native tokens) the original amount back to the sender when a cross-chain delivery is provably undeliverable.

## Proof of Concept
1. Alice holds 10,000 USDC on NEAR (bridged token). She calls `ft_transfer_call` targeting the NEAR bridge contract with recipient `0xBob` on Ethereum.
2. `init_transfer_internal` burns Alice's 10,000 USDC on NEAR and emits `InitTransferEvent`. [3](#0-2) 
3. Before the relayer acts, Circle blacklists `0xBob` (e.g., sanctions enforcement).
4. The relayer calls `finTransfer` on `OmniBridge.sol` with `payload.recipient = 0xBob`.
5. `completedTransfers[nonce] = true` is written, then `IERC20(USDC).safeTransfer(0xBob, 10000e6)` reverts — USDC's transfer hook rejects blacklisted addresses. [7](#0-6) 
6. The EVM transaction reverts entirely; `completedTransfers[nonce]` is rolled back to `false`.
7. Every subsequent relay attempt reverts identically. The nonce is never consumed.
8. Alice's 10,000 USDC are permanently burned on NEAR. There is no `cancel_transfer` or refund path. Funds are irrecoverably frozen.

**Minimal test plan:** Deploy a mock ERC-20 with a blacklist toggle. Call `finTransfer` with a blacklisted recipient. Assert the transaction reverts and `completedTransfers[nonce]` remains `false`. Confirm no NEAR-side recovery function exists by enumerating all `#[near_bindgen]` public entry points in `lib.rs`.

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
