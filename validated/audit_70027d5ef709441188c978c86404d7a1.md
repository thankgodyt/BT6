### Title
Incorrect `EXPECTED_ACTIONS_NUMBER` Constant Causes All Orchard (Shielded ZEC) Withdrawals to Permanently Fail — (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary

The constant `EXPECTED_ACTIONS_NUMBER` in `orchard_policy.rs` is set to `1`, but the Orchard protocol enforces a minimum of **2** actions per bundle (the orchard crate's `MIN_ACTIONS = 2`, referenced by the code's own comment). The validation check rejects any bundle that does not have exactly 1 action. Because the standard Orchard builder always pads to at least 2 actions for privacy, every legitimately constructed Orchard bundle fails this check, permanently breaking all shielded ZEC withdrawals and leaving user nZEC tokens stuck in the bridge.

---

### Finding Description

In `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`, the constant and its enforcement are:

```rust
/// Minimum number of actions required in an Orchard bundle per the Orchard protocol.
/// The Orchard builder automatically pads bundles to meet this minimum for privacy.
/// See: https://github.com/zcash/orchard/blob/main/src/builder.rs#L36
pub const EXPECTED_ACTIONS_NUMBER: usize = 1;
``` [1](#0-0) 

This constant is used in `extract_orchard_bundle` with an exact-equality check:

```rust
if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
    return Err(format!(
        "Orchard bundle must have {} actions, got {}",
        EXPECTED_ACTIONS_NUMBER,
        bundle.actions().len()
    ));
}
``` [2](#0-1) 

The code's own comment references `https://github.com/zcash/orchard/blob/main/src/builder.rs#L36`, which is precisely where the orchard crate defines `MIN_ACTIONS = 2`. The Orchard builder pads every bundle to at least 2 actions for privacy — a 1-output withdrawal produces 1 real action + 1 dummy action = 2 total. The constant `1` is therefore incorrect; the correct value is `2`.

`extract_orchard_bundle` is called from `PsbtWrapper::new`, which panics on any error:

```rust
let orchard = orchard_policy::extract_orchard_bundle(
    orchard_bundle_bytes,
    proof_size_enforcement(get_branch_id(current_height, config)),
)
.unwrap_or_else(|_| {
    env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: failed to extract Orchard bundle")
});
``` [3](#0-2) 

---

### Impact Explanation

When a user initiates a shielded ZEC withdrawal via `ft_transfer_call`, their nZEC tokens are immediately transferred to the bridge contract. The bridge's `ft_on_transfer` returns `0` (keeps all tokens). The relayer then attempts to submit a PSBT containing a standard Orchard bundle. Because every standard Orchard bundle has 2 actions, `extract_orchard_bundle` always returns an error, `env::panic_str` fires, and the relayer's PSBT submission transaction reverts. The user's nZEC tokens remain locked in the bridge with no path to completion — a stuck bridge state requiring operator intervention.

This matches: **Medium — stuck bridge state requiring operator intervention**, and also **Zcash-specific validation failure that enables permanent loss**.

---

### Likelihood Explanation

Every attempt to withdraw nZEC to a shielded (Orchard) Zcash address triggers this path. The standard orchard builder unconditionally pads to `MIN_ACTIONS = 2`. There is no workaround available to a legitimate relayer using the standard library. Likelihood is **High** for any Zcash bridge deployment with shielded withdrawal support enabled.

---

### Recommendation

Change the constant to match the actual Orchard protocol minimum:

```rust
pub const EXPECTED_ACTIONS_NUMBER: usize = 2;
```

Additionally, consider whether the check should be `!=` (exact) or `<` (minimum), depending on whether the bridge intends to support bundles with more than 2 actions in the future.

---

### Proof of Concept

1. User calls `nztc.ft_transfer_call(bridge_id, amount, msg)` to initiate a shielded ZEC withdrawal. Tokens are transferred to the bridge; `ft_on_transfer` returns `0`, keeping them there.
2. Relayer constructs a Zcash transaction with an Orchard bundle using the standard `orchard::builder::Builder`. For a single output, the builder produces **2 actions** (1 real + 1 dummy pad).
3. Relayer calls the bridge's PSBT submission function, passing the 2-action Orchard bundle bytes.
4. `PsbtWrapper::new` calls `extract_orchard_bundle(Some(orchard_bundle_bytes), ...)`.
5. Inside `extract_orchard_bundle`: `bundle.actions().len()` returns `2`; the check `2 != 1` is `true`.
6. The function returns `Err("Orchard bundle must have 1 actions, got 2")`.
7. `unwrap_or_else` calls `env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: ...")` — the transaction panics and reverts.
8. The user's nZEC tokens remain locked in the bridge. No further PSBT submission can succeed without a contract upgrade. The bridge is stuck for all shielded ZEC withdrawals.
