### Title
Tokens Permanently Locked When `init_transfer` Targets an Unconfigured Destination Chain — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The NEAR `omni-bridge` contract's `init_transfer` path burns or locks user tokens before performing any validation that the destination chain is properly configured (token registered, factory set). If a user initiates a transfer to a `ChainKind` for which the bridged token has no registered address, the tokens are irrecoverably committed on NEAR while the transfer can never be completed — an exact structural analog to the OmniXMultisender "optimistic peer assumption" bug.

---

### Finding Description

`init_transfer` (called via `ft_on_transfer`) performs only one destination-chain check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

No check is made that:
- the token is registered for the destination chain (`token_id_to_address` has an entry for `(destination_chain, token_id)`), or
- the destination chain has a configured factory or prover.

Execution then falls through to `init_transfer_internal`, which **irrevocably commits the user's tokens** — burning them if they are a deployed bridge token, or locking them in the escrow — and stores the `TransferMessage` in `pending_transfers`:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [2](#0-1) 

The transfer is now stored and the tokens are gone from the user's balance. The only way to complete the transfer is for a relayer to call `sign_transfer`. That function immediately attempts:

```rust
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
``` [3](#0-2) 

If the token is not registered for the destination chain, `sign_transfer` panics unconditionally with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`. The transfer message remains in `pending_transfers` indefinitely. There is no `cancel_transfer`, `refund_transfer`, or any other user-callable recovery path in the contract.

The `BridgeError` enum confirms no "cancel" error variant exists, and no public function removes a pending transfer except `sign_transfer_callback` (only reached after a successful MPC signing) and `claim_fee_callback` (only reached after a successful proof): [4](#0-3) 

The `ChainKind` enum contains 13 variants (`Eth`, `Sol`, `Arb`, `Base`, `Bnb`, `Btc`, `Zcash`, `Pol`, `HyperEvm`, `Strk`, `Abs`, `Fogo`, `Near`), all of which are accepted by `OmniAddress` parsing: [5](#0-4) 

A user can freely construct an `OmniAddress` for any of these chains and pass it as the `recipient` in `InitTransferMsg`. The bridge accepts it without checking whether the token or chain is operationally configured.

---

### Impact Explanation

**Critical — permanent freezing of bridged funds.**

Once `init_transfer_internal` executes, the user's tokens are burned (deployed/bridged tokens) or locked (native tokens). If the destination chain has no registered token address, `sign_transfer` will always panic, leaving the `TransferMessage` permanently in `pending_transfers` with no user-accessible recovery. The funds are frozen until the team manually registers the token for that chain — and if the chain has no deployed bridge contract at all, the funds are permanently lost even if the token is later registered, because there is no counterpart contract to receive the MPC-signed payload.

---

### Likelihood Explanation

**Low.** In normal front-end usage, the UI only presents chains and tokens that are fully configured. However, the contract is directly callable by any NEAR account via `ft_transfer_call`. A user interacting directly with the contract (e.g., via CLI or SDK) can specify any `ChainKind` recipient. This is identical in likelihood profile to the original report: "most users will interact directly through the front-end application where misconfiguration is highly unlikely" — but the on-chain path is fully open to direct callers.

---

### Recommendation

Before burning or locking tokens in `init_transfer_internal`, validate that the token is registered for the destination chain:

```rust
require!(
    self.get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    ).is_some(),
    BridgeError::FailedToGetTokenAddress.as_ref()
);
```

This mirrors the fix applied in the OmniXMultisender report: revert on unsupported/unconfigured destinations rather than optimistically proceeding and locking funds.

---

### Proof of Concept

1. Token `foo.near` is registered for `ChainKind::Eth` but **not** for `ChainKind::Fogo`.
2. User calls `ft_transfer_call` on `foo.near` with:
   ```json
   {
     "receiver_id": "omni-bridge.near",
     "amount": "1000000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"fogo:2xNweLHLqbS9YpP3UyaPrxKqgqoC6yPBFyuLxA8qtgr4\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
3. `init_transfer` passes the only guard (`get_chain() != Near`). [1](#0-0) 
4. `init_transfer_internal` burns/locks 1,000,000 units of `foo.near` and stores the `TransferMessage`. [6](#0-5) 
5. Relayer calls `sign_transfer` for the new `TransferId`.
6. `get_token_address(ChainKind::Fogo, "foo.near")` returns `None` → contract panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`. [3](#0-2) 
7. The transfer message remains in `pending_transfers`. The user's 1,000,000 tokens are burned/locked with no recovery path.

```rust
    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
