### Title
Peras Certificate Deduplication Uses Round-Number-Only Predicate, Allowing Adversarial Certificate to Permanently Suppress Honest Certificate — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` deduplicates inbound Peras certificates using only the round number as the identity key. Because the production `validatePerasCert` implementation is a stub that unconditionally returns `Right` (valid), an unprivileged peer can send a crafted certificate for any round number before the honest certificate arrives. The honest certificate is then permanently filtered out without ever being validated or stored, and chain selection is left boosting the adversary's block instead of the canonical one.

---

### Finding Description

**Root cause — incorrect existence predicate in `processCerts`**

`processCerts` in `PerasCert.hs` (lines 164–173) implements the following logic:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM          -- (1) snapshot of round-number set
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs  -- (2) filter by round only
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
```

The predicate at step (2) is `roundNo ∈ alreadyInDb`. This is an **incomplete identity check**: it treats any two certificates that share a round number as duplicates, regardless of which block they boost. Two certificates for the same round but different boosted blocks are semantically distinct objects, but the filter discards the second one silently and permanently — it is never validated, never stored, and never considered for chain selection.

**Enabling condition — stub `validatePerasCert` always returns `Right`**

The degenerate `BlockSupportsPeras` instance in `BlockSupportsPeras.hs` (lines 350–358) provides the `validatePerasCert` implementation used by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

Every certificate received from every peer passes this check unconditionally. No cryptographic verification of the boosted-block hash, the voter set, or the aggregate BLS signature is performed.

**End-to-end exploit path**

1. Adversary connects to the node via the ObjectDiffusion mini-protocol and sends certificate `C_adv` for round `R` boosting adversarial block `B_adv`.
2. `processCerts` is invoked: `alreadyInDb = {}`, so `C_adv` passes the round-number filter.
3. `validatePerasCert C_adv` returns `Right` (stub). `C_adv` is stored in `PerasCertDB` with round `R`.
4. Honest peer later sends certificate `C_hon` for round `R` boosting canonical block `B_hon`.
5. `processCerts` is invoked: `alreadyInDb = {R}`. `C_hon` is filtered out at line 166. It is never validated, never stored.
6. `getWeightSnapshot` returns a `PerasWeightSnapshot` that includes only `C_adv`'s boost for `B_adv`.
7. `preferAnchoredCandidate` in `ChainSel.hs` uses this snapshot; the adversarial chain containing `B_adv` receives the Peras weight boost while the canonical chain containing `B_hon` receives none.

---

### Impact Explanation

**Severity: High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended Peras security assumptions.

The Peras weight boost is the mechanism by which Peras accelerates finality: a certificate for round `R` adds `perasWeight` to the chain containing the boosted block, making it preferred over equally-long competing chains. By injecting a certificate that boosts an adversarial block and suppressing the honest certificate, the adversary causes the node's `preferAnchoredCandidate` to return `ShouldSwitch` toward the adversarial chain. This directly undermines the chain-selection invariant that the node should follow the heaviest (most-boosted) honest chain.

---

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is a standard peer-to-peer path; any connected peer can submit certificates via `opwAddObjects`. No privileged access, key material, or stake is required. The stub `validatePerasCert` is the production implementation for all block types (the `StandardHash blk` instance covers the entire Cardano block family). The attack requires only that the adversary's certificate for round `R` arrives before the honest one — a trivially achievable timing condition for any peer that connects early or during syncing.

---

### Recommendation

1. **Fix the existence predicate**: Deduplicate certificates by their full identity — `(roundNo, boostedBlockHash)` — not by round number alone. A certificate for round `R` boosting block `B1` and a certificate for round `R` boosting block `B2` are distinct objects and must be treated independently.

2. **Replace the stub `validatePerasCert`**: Implement real cryptographic validation (aggregate BLS signature verification, voter eligibility, quorum threshold) before any certificate is stored or used in chain selection. The stub at `BlockSupportsPeras.hs:353–358` must not be reachable from any network-facing code path.

3. **Perform deduplication and validation atomically**: The snapshot of `alreadyInDb` and the subsequent `addCert` should be part of the same STM transaction to eliminate the TOCTOU window between the existence check and the insertion.

---

### Proof of Concept

```
Private testnet with two peers A (honest) and B (adversary):

1. B connects to the node under test via ObjectDiffusion.
2. B calls opwAddObjects with [PerasCert { pcCertRound = R, pcCertBoostedBlock = B_adv }].
   → processCerts: alreadyInDb = {}, cert passes filter.
   → validatePerasCert returns Right (stub).
   → PerasCertDB now contains cert for round R boosting B_adv.

3. A connects and calls opwAddObjects with [PerasCert { pcCertRound = R, pcCertBoostedBlock = B_hon }].
   → processCerts: alreadyInDb = {R}, cert is filtered out at line 166.
   → B_hon receives zero Peras weight.

4. Observe getWeightSnapshot: only B_adv has weight perasWeight.
5. Observe preferAnchoredCandidate: the chain containing B_adv is preferred over the chain
   containing B_hon when both have equal block count, confirming chain-selection manipulation.
```
