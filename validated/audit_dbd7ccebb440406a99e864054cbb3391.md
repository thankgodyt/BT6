### Title
Peras Certificate Validation Bypass Enables Arbitrary Chain Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. Because this stub is wired into the live peer-facing certificate ingestion path (`processCerts`), any unprivileged peer can inject crafted Peras certificates that boost an arbitrary block, inflating that chain's `wsvTotalWeight` and causing honest nodes to switch to an adversarial fork.

---

### Finding Description

The `BlockSupportsPeras` class exposes `validatePerasCert` as the mandatory gate before a certificate is stored and its weight applied to chain selection. The only concrete instance in the codebase is the degenerate catch-all:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is called directly in the production peer-facing ingestion path `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` filters out round numbers already in the DB, then calls `validateCert` on every remaining certificate. Because `validatePerasCert` always returns `Right`, every certificate from every peer is accepted as `ValidatedPerasCert` and forwarded to `addCert` / `ChainDB.addPerasCertAsync`. [3](#0-2) 

Once stored, `implGetWeightSnapshot` builds a `PerasWeightSnapshot` from every certificate in the DB: [4](#0-3) 

`weightedSelectView` then computes `wsvWeightBoost` from that snapshot for every candidate fragment: [5](#0-4) 

`preferCandidate` compares `wsvTotalWeight` (block number **plus** weight boost) to decide whether to switch chains: [6](#0-5) 

The analogy to the external report is direct: just as the attacker inflated the `queue.reward` value between its capture and its payout to drain funds, here an attacker inflates `wsvWeightBoost` by injecting fake certificates between block receipt and chain selection, causing the node to prefer an adversarial fork.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block on an adversarial fork. Because `validatePerasCert` never rejects anything, the certificate is stored and its boost (`perasWeight params`) is added to that block's chain weight. If the injected boost is large enough, `preferCandidate` returns `ShouldSwitch`, and the honest node abandons the canonical chain in favour of the adversarial one. This is a **bypass of Peras certificate/vote checks enabling unauthorized certificate acceptance and chain selection manipulation** — squarely within the Critical/High allowed impact scope.

---

### Likelihood Explanation

Peras is disabled by default; the attack surface opens only when an operator enables it. However, the degenerate instance is the **only** `validatePerasCert` implementation present in the codebase, and the TODO comment explicitly acknowledges that real validation has not yet been written. Once Peras is enabled, exploitation requires nothing beyond a standard peer connection — no keys, no stake, no special privileges.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that:
1. Verifies the aggregate BLS signature (`pcSignature`) against the aggregated public keys of the claimed voters.
2. Checks that the voter set meets the quorum threshold for the given round.
3. Validates each voter's eligibility proof (`PerasVoteEligibilityProof`) — VRF proof for non-persistent members, committee membership for persistent members.
4. Confirms that `pcCertRound` and `pcCertBoostedBlock` are consistent with the current epoch nonce and chain state.

Until this is done, Peras must not be enabled in any environment reachable by untrusted peers.

---

### Proof of Concept

1. Connect to a node with Peras enabled (e.g., a private testnet with `eraPerasRoundLength` set).
2. Craft a `PerasCert blk` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <tip of adversarial fork>`.
3. Deliver it via the ObjectDiffusion mini-protocol. `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right (ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams })` unconditionally. [7](#0-6) 
4. `addCert` stores the certificate; `implGetWeightSnapshot` includes the boost in the next `PerasWeightSnapshot`. [8](#0-7) 
5. `chainSelSync` triggers chain selection for the boosted block. [9](#0-8) 
6. `weightedSelectView` computes the adversarial fragment's `wsvTotalWeight` as `blockNo + injectedBoost`; `preferCandidate` returns `ShouldSwitch`; the honest node adopts the adversarial chain. [6](#0-5)
