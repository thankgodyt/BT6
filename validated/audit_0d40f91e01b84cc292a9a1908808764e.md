### Title
Peras Certificate Verification Bypass Enables Adversarial Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the universal `BlockSupportsPeras` instance is a stub that unconditionally accepts every inbound Peras certificate without performing any cryptographic or committee-membership verification. An unprivileged peer can send a crafted `PerasCert` boosting any block on an adversarial fork; the certificate passes "validation", is stored in the `PerasCertDB`, and triggers Peras-weighted chain selection that can cause the honest node to switch to the adversarial fork.

---

### Finding Description

**Root cause — stub validator always returns `Right`**

The `BlockSupportsPeras` instance for all block types implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its claimed round, boosted block, committee membership, or aggregate signature, is accepted and assigned the full configured `perasWeight`. No committee-membership check, no aggregate-signature verification, and no VRF-output check is performed.

**Inbound path — `processCerts` calls the stub**

When a peer sends certificates via the object-diffusion mini-protocol, `makePerasCertPoolWriterFromChainDB` wires the stub directly into the inbound processing pipeline:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` reads the set of already-known round numbers atomically, filters out duplicates, calls the stub validator (which always succeeds), and adds every remaining certificate to the `PerasCertDB`: [3](#0-2) 

**Chain-selection consequence — forged boost triggers fork switch**

`chainSelSync` for `ChainSelAddPerasCert` reads the current chain, adds the certificate to `PerasCertDB`, and then calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

`chainSelectionForBlock` reads the `PerasWeightSnapshot` (which now includes the forged boost) and compares candidate fragments using `preferAnchoredCandidate`: [5](#0-4) 

The `WeightedSelectView` comparison uses `wsvTotalWeight = blockNo + weightBoost`, so a sufficiently large forged boost makes an adversarial fork appear heavier than the honest chain: [6](#0-5) 

The `PerasWeightSnapshot` is built directly from all stored certificates with no post-storage re-validation: [7](#0-6) 

**Analog to the reported vulnerability class**

The Berachef bug is a *queued-state bait-and-switch*: a validator publicly queues a cutting board to attract stakeholders, then replaces it before activation, redirecting rewards. The analog here is: Peras certificates are the "queued state" that is supposed to represent an unforgeable committee decision boosting a specific block. Because validation is a no-op stub, an adversary can forge that queued state (a certificate boosting any block) and inject it before chain selection runs, redirecting the node's chain preference to an adversarial fork — exactly the same pattern of manipulating a pending/queued authoritative signal before it is acted upon.

---

### Impact Explanation

When Peras is enabled, any connected peer can send a `PerasCert` with:
- `pcCertRound` set to any unused round number (deduplication is by round number only)
- `pcCertBoostedBlock` pointing to a block on an adversarial fork
- The boost is automatically set to `perasWeight params` (the full configured weight)

If the adversarial fork's total weight (block count + forged boost) exceeds the honest chain's weight, the node switches to the adversarial fork. This constitutes:

- **Bypass of Peras certificate/signature validation** enabling unauthorized certificate acceptance (Critical per scope)
- **Chain-selection manipulation** letting an unprivileged peer make an honest node prefer a non-canonical chain (High per scope)

The `SecurityParam` is reinterpreted as a weight bound under Peras, so a single forged certificate with boost ≥ `k` can make a fork that is `k` blocks shorter appear heavier, bypassing the rollback-weight guard entirely. [8](#0-7) 

---

### Likelihood Explanation

Peras is not enabled by default (`eraPerasRoundLength` is `NoPerasEnabled` unless explicitly configured), so mainnet nodes are not currently exposed. However:

- Any private testnet or development network that enables Peras is immediately vulnerable.
- The object-diffusion mini-protocol for Peras certificates is fully wired into the production node kernel.
- No stake, no keys, and no prior relationship with the target node are required — any peer that can establish a connection can send crafted certificates.
- The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is a known incomplete stub in production code, not an isolated test artifact.

---

### Recommendation

1. **Do not enable Peras in any network until `validatePerasCert` performs real cryptographic and committee-membership verification.** The WFALS committee validation logic (aggregate signature verification, VRF output checks, seat-index bounds) already exists in `Ouroboros.Consensus.Committee.WFALS` and must be wired into `validatePerasCert` before Peras is activated.
2. Add a runtime guard that refuses to process inbound Peras certificates if the real validator is not yet wired up (i.e., treat the stub as a hard error rather than a silent pass).
3. Resolve `cardano-peras/issues/120` before any Peras-enabled deployment.

---

### Proof of Concept

1. Connect to a node with Peras enabled (non-default configuration).
2. Send a `PerasCert` via the object-diffusion mini-protocol:
   - `pcCertRound = <any round not yet in the DB>`
   - `pcCertBoostedBlock = <block point on an adversarial fork>`
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}` unconditionally.
4. `implAddCert` stores the certificate; `implGetWeightSnapshot` now includes the forged boost for the adversarial block.
5. `chainSelSync (ChainSelAddPerasCert ...)` calls `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial fork including the forged boost; if it exceeds the honest chain's weight, `switchTo` is called and the node adopts the adversarial fork.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
```

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14. In the latter case, the chain fragment has
-- total weight @2 + 2 * 14 = 30@.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
  deriving (Eq, Generic, NoThunks, ToCBOR, FromCBOR)
  deriving Show via Quiet SecurityParam

-- | The maximum amount of weight we can roll back.
maxRollbackWeight :: SecurityParam -> PerasWeight
maxRollbackWeight = PerasWeight . unNonZero . maxRollbacks
