### Title
No User-Initiated Cancel Mechanism for Pending Outbound Transfers Causes Permanent Token Loss - (File: near/omni-bridge/src/lib.rs)

### Summary

The NEAR Omni Bridge has no cancel or refund function for outbound transfers stored in `pending_transfers`. Once a user's tokens are burned or locked during `init_transfer_internal`, the only path to completion is through a relayer calling `sign_transfer`. If `sign_transfer` permanently panics for a given transfer (e.g., because the normalized transfer amount is zero), the tokens are irrecoverably lost with no user-accessible recovery path.

### Finding Description

When a user initiates an outbound transfer via `ft_on_transfer` → `init_transfer` → `init_transfer_internal`, two irreversible actions occur:

1. For bridge-deployed tokens: `burn_tokens_if_needed` burns the user's tokens.
2. For native tokens: `lock_tokens_if_needed` locks them in the bridge.

The transfer is then stored in `pending_transfers`. [1](#0-0) 

Completion requires a relayer to call `sign_transfer`, which calls `normalize_amount` and then enforces:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [2](#0-1) 

If `normalize_amount` returns 0 (e.g., when the user's amount minus fee is smaller than the decimal scaling factor between NEAR and the destination chain), `sign_transfer` panics every time it is called for that transfer. The transfer remains in `pending_transfers` indefinitely. [3](#0-2) 

Critically, `sign_transfer_callback` only removes the transfer from `pending_transfers` on **successful** signing when the fee is zero:

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
``` [4](#0-3) 

There is no `cancel_transfer`, `refund_transfer`, or any user-callable function to remove a stuck entry from `pending_transfers` and return the underlying tokens. A grep across all production source files confirms zero such functions exist. [5](#0-4) 

The `storage_unregister` function blocks unregistration when pending transfers exist, so the user cannot even recover their storage deposit:

```rust
require!(
    storage.total.saturating_sub(storage.available)
        == self.required_balance_for_account(),
    BridgeError::StoragePendingTransfers.as_ref()
);
``` [6](#0-5) 

### Impact Explanation

A user who sends a token amount that passes `init_transfer`'s only validation (`fee < amount`) but whose normalized value on the destination chain is 0 will have their tokens permanently burned or locked with no recovery path. The bridge accepts the transfer, destroys the tokens, and provides no mechanism to undo this. This constitutes **permanent freezing of bridged funds** triggered entirely by an unprivileged user action.

### Likelihood Explanation

Any token pair where NEAR-side decimals significantly exceed destination-chain decimals (e.g., 24 vs. 6, an 18-order-of-magnitude difference) creates a large "dust" range where amounts pass `init_transfer` validation but normalize to 0. A user sending a small amount — whether by mistake or due to a UI rounding error — triggers this permanently. The condition is reachable on any supported EVM chain where tokens have 6 or 8 decimals.

### Recommendation

1. **Short term:** Add a pre-check in `init_transfer_internal` (or `init_transfer`) that computes `normalize_amount` and rejects the transfer (returning the tokens) if the result is 0, before burning or locking anything.
2. **Short term:** Implement a user-callable `cancel_transfer` function that allows the transfer owner to remove their entry from `pending_transfers` and recover locked tokens (or re-mint burned tokens), callable only when the transfer has not yet been signed.
3. **Long term:** Model and document all transfer states (pending, signed, claimed, stuck) and implement test cases covering each terminal state, including the zero-normalized-amount case.

### Proof of Concept

1. Token `T` has 24 decimals on NEAR and 6 decimals on Ethereum (scaling factor = 10^18).
2. User calls `ft_transfer_call` sending `amount = 500` (500 yocto-units) of token `T` to the bridge with `fee = 0`.
3. `init_transfer` passes: `fee (0) < amount (500)`. ✓
4. `init_transfer_internal` burns 500 units of `T` and stores the transfer in `pending_transfers`.
5. Relayer calls `sign_transfer`. `normalize_amount(500, decimals{24,6})` = `500 / 10^18` = `0` (integer division).
6. `require!(amount_to_transfer > 0, ...)` panics. Transfer stays in `pending_transfers`.
7. Every subsequent `sign_transfer` call panics identically.
8. User has no `cancel_transfer` to call. `storage_unregister` is blocked by `StoragePendingTransfers`.
9. The 500 units of `T` are permanently burned with no recovery. [7](#0-6) [8](#0-7)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
