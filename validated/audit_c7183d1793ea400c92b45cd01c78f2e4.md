### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Unauthorized Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that always returns `Right` — unconditionally accepting every certificate without any cryptographic or structural check. Any unprivileged peer can send a crafted `PerasCert` via the object diffusion mini-protocol, have it accepted as "validated," and cause the receiving node to apply a Peras weight boost to an arbitrary block during chain selection. This is the direct analog of the ERC777 bug: just as `operatorSend()`/`operatorBurn()` bypassed the lock-period check because those entry points were never overridden, here the `validatePerasCert` entry point is never properly implemented — the check is structurally present but always passes.

---

### Finding Description

**Root cause — the stub implementation**

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory validation gate for all inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The universal instance (the only active instance for all block types) implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This unconditionally wraps any certificate in `Right`, bypassing all validation. The `PerasCert` type in this instance carries no cryptographic proof field whatsoever:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

**Attacker-controlled entry path**

The object diffusion mini-protocol writer for Peras certificates wires `validatePerasCert mkPerasParams` directly as the validator passed to `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert <$> certsNotAlreadyInDb`. Because `validatePerasCert` always returns `Right`, every certificate in the batch passes: [4](#0-3) 

Each accepted certificate is then forwarded to `ChainDB.addPerasCertAsync`, which triggers chain selection and applies the Peras weight boost to `pcCertBoostedBlock`. [5](#0-4) 

**The analog pattern**

| ERC777 bug | Ouroboros analog |
|---|---|
| `transfer()`, `send()`, `burn()` check lock period | `processCerts` calls `validateCert` before accepting |
| `operatorSend()`, `operatorBurn()`, `transferFrom()` bypass the check | `validatePerasCert` is the "overridden" function — but its body is a stub that always returns `Right`, so the check is structurally present but never enforced |
| Fix: override missing functions to include the check | Fix: implement actual cryptographic verification inside `validatePerasCert` |

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block — including a block on an adversarial fork — and send it via the object diffusion mini-protocol. The receiving node will:

1. Accept the certificate unconditionally (no signature, no committee membership, no round-number check).
2. Store it in `PerasCertDB` with a weight boost equal to `perasWeight params`.
3. Trigger chain selection, which now considers the adversarial fork block as having extra Peras weight.

If the boost is sufficient to make the adversarial fork heavier than the honest chain, the node switches forks. This is a **bypass of Peras certificate checks enabling unauthorized chain selection manipulation** — matching the Critical/High impact categories: bypass of Peras certificate validation and a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

The object diffusion mini-protocol is active and reachable by any peer without privileged access, stake, or cryptographic material. The attacker only needs to connect as a normal peer and send a well-formed (but cryptographically fabricated) `PerasCert` CBOR message. No brute force is required; the stub accepts the very first crafted certificate sent.

---

### Recommendation

Implement proper cryptographic validation inside `validatePerasCert` before the Peras object diffusion protocol is enabled in production:

1. Verify the aggregate BLS signature in the certificate against the committee's aggregated public keys.
2. Verify that each claimed voter is a legitimate committee member for the stated round.
3. Verify that the `pcCertRound` and `pcCertBoostedBlock` are consistent with the current chain state (e.g., the boosted block exists and is within the valid window).
4. Until a real implementation exists, the universal instance should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the protocol fails closed rather than open. [6](#0-5)

### Proof of Concept

**Setup:** A private testnet with one honest node running the Peras-enabled consensus layer.

**Steps:**

1. Connect to the honest node as a peer via the object diffusion mini-protocol for Peras certificates.
2. Construct a `PerasCert` CBOR payload with:
   - `pcCertRound`: any valid `PerasRoundNo`
   - `pcCertBoostedBlock`: the `Point` of a block on an adversarial fork (or any block the attacker wants boosted)
3. Send the crafted certificate batch to the node.
4. The node executes: `processCerts` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert cert weight)` — the certificate passes with no rejection.
5. `ChainDB.addPerasCertAsync` is called; chain selection applies the Peras weight boost to the adversarial block.
6. If the boosted weight exceeds the honest chain's weight, the node switches to the adversarial fork.

**Expected (correct) behavior:** The certificate should be rejected with a `PerasCertValidationError` because no valid aggregate BLS signature is present.

**Actual behavior:** The certificate is accepted and stored; chain selection is influenced by the attacker-controlled boost. [7](#0-6)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
