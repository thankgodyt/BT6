Audit Report

## Title
Unconstrained `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Relayer Fees - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`sign_transfer` accepts a caller-supplied `fee_recipient: Option<AccountId>` with no validation that the caller has any claim to that address. Any active trusted relayer can call `sign_transfer` on any pending fee-bearing transfer, inject their own account as `fee_recipient`, obtain a valid MPC-signed payload, submit it to the destination chain, and then call `claim_fee` on NEAR to collect the fee — permanently depriving the legitimate relayer of their reward.

## Finding Description
`sign_transfer` is gated by `#[trusted_relayer]` but imposes no constraint on who the `fee_recipient` may be:

```rust
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,   // fully caller-controlled
    fee: &Option<Fee>,
) -> Promise {
```

The caller-supplied value is placed verbatim into `TransferMessagePayload`:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    fee_recipient,   // no binding to env::predecessor_account_id()
    ...
};
```

The MPC network signs this payload. The resulting signature is broadcast as a `SignTransferEvent`. On the EVM destination, `finTransfer` consumes the nonce and emits a `FinTransfer` event whose `feeRecipient` field is taken directly from the signed payload. Back on NEAR, `claim_fee_callback` enforces only that the caller of `claim_fee` matches the `fee_recipient` recorded in the EVM event:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

Because the attacker controls `fee_recipient` at signing time, they trivially satisfy this check. For fee-bearing transfers, the pending transfer record is **not** removed after signing:

```rust
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
```

This means the attacker can call `sign_transfer` at any time while the transfer is pending, before or after the legitimate relayer, and obtain a valid competing signature. Whichever signature is submitted to the EVM first consumes the destination nonce (EVM `completedTransfers[nonce] = true`), making the other signature permanently worthless. The `claim_fee_callback` then removes the NEAR transfer record, so the legitimate relayer has no recourse.

## Impact Explanation
This is fee mis-accounting / unauthorized fund redirection. A malicious trusted relayer can steal 100% of the relayer fee from every pending NEAR-origin transfer destined for EVM, Solana, or Starknet. The fee is paid on NEAR via `claim_fee` to whichever account appears as `fee_recipient` in the MPC-signed payload that was finalized on the destination chain. Once the attacker's `finTransfer` is accepted and `claim_fee` is called, the fee is irrecoverably redirected. This matches the allowed critical impact: "fee mis-accounting… that changes user or protocol balances."

## Likelihood Explanation
Becoming a trusted relayer requires staking 1,000 NEAR and waiting ~7 days. However, an attacker who can steal fees from every other relayer indefinitely has a clear economic incentive to meet this bar. NEAR has no public mempool, so there is no race condition in the traditional sense — the attacker simply monitors on-chain pending transfers and calls `sign_transfer` with their own `fee_recipient` at any time. The attack is deterministic, repeatable, and requires no victim mistake.

## Recommendation
Bind `fee_recipient` to the caller inside `sign_transfer`. Replace the caller-supplied parameter with `env::predecessor_account_id()`, or add an explicit guard:

```rust
if let Some(ref recipient) = fee_recipient {
    require!(
        recipient == &env::predecessor_account_id(),
        "fee_recipient must be the caller"
    );
}
```

This ensures only the relayer who actually calls `sign_transfer` can be named as the fee beneficiary in the MPC-signed payload.

## Proof of Concept

1. User initiates a NEAR→EVM transfer with a non-zero fee. A `TransferMessage` is stored in `pending_transfers`.
2. Legitimate relayer `alice.near` intends to call `sign_transfer(transfer_id, fee_recipient: Some("alice.near"), fee: Some(...))`.
3. Malicious trusted relayer `eve.near` calls `sign_transfer(transfer_id, fee_recipient: Some("eve.near"), fee: Some(...))` — no check prevents this.
4. MPC signs a `TransferMessagePayload` with `fee_recipient = "eve.near"`. The `SignTransferEvent` is emitted.
5. `eve.near` submits the signed payload to the EVM `finTransfer`. The EVM marks `completedTransfers[destinationNonce] = true` and emits `FinTransfer(... feeRecipient="eve.near")`.
6. `eve.near` calls `claim_fee` on NEAR with proof of the EVM `FinTransfer` event. `claim_fee_callback` reads `fee_recipient = "eve.near"` from the proof, checks `fee_recipient == predecessor_account_id` (both `"eve.near"`), passes, removes the transfer record, and pays the fee to `eve.near`.
7. `alice.near`'s signature is now useless: the EVM nonce is consumed and the NEAR transfer record is deleted. The fee is permanently lost to `alice.near`.

**Minimal integration test plan:** Deploy the locker with a mock MPC signer and mock prover. Register two trusted relayers (`alice` and `eve`). Initiate a NEAR→ETH transfer with a non-zero fee. Have `eve` call `sign_transfer` with `fee_recipient = eve`. Submit the signed payload to the mock EVM (or simulate the `claim_fee` proof directly).
