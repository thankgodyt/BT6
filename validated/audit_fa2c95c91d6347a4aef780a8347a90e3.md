Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Yield/Resume Path — (`near/omni-bridge/src/lib.rs`)

## Summary

The `NativeFeeRestricted` role check in `init_transfer` is embedded inside one branch of a storage-routing conditional, not at the function entry point. When a restricted account submits a transfer with `native_fee > 0` and no pre-funded message account, neither branch of the OR is satisfied, execution falls into the yield path, and `init_transfer_resume` — which contains no role check — later stores the transfer with the non-zero native fee unconditionally. A second bypass exists via pre-funding the message account, which causes the first branch to succeed without ever evaluating the role check.

## Finding Description

In `init_transfer`, the storage-routing branch is:

```rust
if self.try_to_transfer_balance_from_message_account(...).is_ok()   // Branch 1 — no role check
    || (self.has_storage_balance(...) && (native_fee == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))  // Branch 2 — role checked
{
    self.init_transfer_internal(transfer_message, signer_id)
} else {
    // yield path — no role check
    env::promise_yield_create("init_transfer_resume", ...)
}
``` [1](#0-0) 

For a `NativeFeeRestricted` account with `native_fee > 0` and sufficient storage balance but no pre-funded message account:
- Branch 1 returns `Err` (message account not registered) → false
- Branch 2 evaluates `has_storage_balance = true` AND `(false || !true)` = false → false
- Execution enters the yield path

`init_transfer_resume` contains no `NativeFeeRestricted` check:

```rust
pub fn init_transfer_resume(...) -> U128 {
    self.remove_promise(&message_storage_account_id);
    if let Err(err) = self.try_to_transfer_balance_from_message_account(...) { ... }
    self.init_transfer_internal(transfer_message, storage_owner)  // stores native_fee unconditionally
}
``` [2](#0-1) 

`init_transfer_internal` stores the transfer message including `native_fee` and deducts it from the storage owner's balance: [3](#0-2) 

The second bypass (pre-funding) works because Branch 1 (`try_to_transfer_balance_from_message_account`) succeeds when the message account already has a balance, and the role check in Branch 2 is never evaluated. The message account ID is derived deterministically from the transfer message fields including the predictable `current_origin_nonce`. [4](#0-3) 

The existing integration tests in `native_fee_role.rs` only exercise the direct path (sender's storage balance), not the yield path, so the bypass is untested: [5](#0-4) 

## Impact Explanation

This is a confirmed role bypass. `NativeFeeRestricted` is a first-class access-control role defined in the contract's `Role` enum: [6](#0-5) 

The bypass allows a restricted account to embed an arbitrary `native_fee` in a cross-chain transfer. The native fee is deducted from the attacker's storage balance and credited to the relayer at `sign_transfer` time. This constitutes an authorization/role bypass that lets the attacker execute a bridge action — initiating a transfer with a native fee — that the protocol's access-control system explicitly prohibits. This matches the allowed critical impact: "authorization bypass, role bypass... that lets an attacker execute bridge... actions."

## Likelihood Explanation

Any account that has been assigned the `NativeFeeRestricted` role can trigger this. The attacker only needs to call `ft_transfer_call` with `native_fee > 0` (standard bridge interaction) and then call `storage_deposit` on the bridge contract with the virtual message account ID (a permissionless, standard NEAR storage operation). The virtual account ID is logged by the contract and is also deterministically computable. No privileged access beyond holding the restricted role is required, and the exploit is repeatable.

## Recommendation

Move the `NativeFeeRestricted` check to a standalone guard at the top of `init_transfer`, before any storage-routing branching:

```rust
require!(
    init_transfer_msg.native_token_fee.0 == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()),
    BridgeError::NativeFeeNotAllowed.as_ref()
);
```

This ensures the restriction is enforced regardless of which storage-payment path is taken (direct, pre-funded message account, or yield/resume), eliminating the structural inconsistency.

## Proof of Concept

1. Admin calls `acl_grant_role` with `role: "NativeFeeRestricted"` and `account_id: attacker.near`.
2. `attacker.near` calls `storage_deposit` on the bridge to register their account (but does NOT deposit enough to cover `native_fee`).
3. `attacker.near` calls `ft_transfer_call` on a registered token with `msg = InitTransferMsg { native_token_fee: U128(1_000_000_000_000_000_000_000_000), fee: U128(0), recipient: "eth:0x...", ... }`.
4. Branch 1 fails (no message account). Branch 2 fails (role check). Execution enters the yield path. The contract logs the virtual message account ID.
5. `attacker.near` (or any third party) calls `storage_deposit` on the bridge with `account_id = <virtual message account id>`, depositing enough to cover storage + native fee.
6. The yield fires; `init_transfer_resume` runs, `try_to_transfer_balance_from_message_account` succeeds, and `init_transfer_internal` stores the transfer with `native_fee = 1e24 yoctoNEAR`.
7. A relayer calls `sign_transfer`; the native fee is paid out to the relayer, bypassing the `NativeFeeRestricted` restriction entirely.

A sandbox integration test mirroring `test_native_fee_restriction` but using the yield path (omitting the sender's storage deposit for the native fee, then depositing to the virtual account) would reproduce this on a local NEAR sandbox.

        let result = env
            .initialize_transfer(
                transfer_amount,
                native_fee,
                token_fee,
                false, // Should fail
            )

        );

            .initialize_transfer(

                true, // Should succeed

            .await?
            .unwrap();

        assert_eq!(
