### Title
nBTC Token Migration Proceeds Without Pausing Old Token, Enabling Front-Running to Cause Incorrect Minting on New Token - (File: `contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

The `internal_migrate_to_new_token` function in the satoshi-bridge contract performs a multi-block asynchronous migration of nBTC balances to a new token contract. It fires parallel cross-contract calls to snapshot `ft_total_supply` and `ft_balance_of` for every holder, then mints equivalent balances on the new token. Neither the migration code nor the nbtc token contract enforces or even supports pausing the old token during this process. Because NEAR cross-contract calls are not atomic and execute across multiple blocks, a window exists between the balance snapshot and the minting callback where transfers on the old token can corrupt the snapshot, causing incorrect per-account minting on the new token and permanently stranding funds for some users.

---

### Finding Description

`internal_migrate_to_new_token` in `contracts/satoshi-bridge/src/nbtc/migration.rs` schedules all balance queries as parallel promises using `.and()`: [1](#0-0) 

These receipts all execute in block N+1. The callback `migrate_to_new_token_mint` is then scheduled for block N+2. The only integrity check is: [2](#0-1) 

This check verifies that the sum of captured balances equals the captured total supply. However, it does **not** prevent the following race: if a transfer between two accounts **both in the accounts list** occurs in block N+1 (after the queries execute) or block N+2 (before the callback executes), the sum still equals total supply (transfers are supply-neutral), the check passes, but the minted amounts reflect stale pre-transfer or post-transfer balances inconsistently.

More critically, if Alice (in the list) transfers to Carol (**not** in the list) in this same window:
- Alice's captured balance (from block N+1) is her pre-transfer amount (too high)
- Carol is absent from the list and receives nothing on the new token
- The sum still equals total supply (supply-neutral transfer), so the check at line 78–81 passes
- Alice is minted more nBTC than she holds; Carol's tokens are permanently stranded on the deprecated old token

The nbtc token contract has **no pause mechanism** whatsoever — it implements no `Pausable` trait and exposes no pause function: [3](#0-2) 

The satoshi-bridge itself is `Pausable` (via `near-plugins`): [4](#0-3) 

But the old nbtc token contract cannot be paused at all, so there is no mechanism to freeze transfers during migration even if the operator wanted to.

The minting callback then issues `mint` calls on the new token using the stale, inconsistent snapshot: [5](#0-4) 

Finally, `migrate_to_new_token_resolve` switches the bridge's active token to the new contract: [6](#0-5) 

After this point, the old token is abandoned. Any user whose tokens were transferred to them from a listed account during the snapshot window — and who was not themselves in the list — permanently loses access to their funds.

---

### Impact Explanation

- **Wrong per-account minting**: Accounts in the list can be minted more nBTC than they actually hold at migration time.
- **Permanent fund loss**: Accounts not in the list that received transfers from listed accounts during the snapshot window hold tokens on the old (now-abandoned) token with no recourse.
- **Total supply preserved but distribution corrupted**: The sum check only validates aggregate supply, not per-account correctness, so the inconsistency is silent and undetected by the contract.

This matches: **Medium — harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply or stuck bridge state requiring operator intervention**, and potentially **Critical — significant loss or permanent locking of user funds** for the accounts whose tokens are stranded.

---

### Likelihood Explanation

The attack window is the block gap between when balance queries execute (block N+1) and when the minting callback executes (block N+2). On NEAR, this is a predictable, observable window. An attacker monitoring the chain can:
1. Detect the migration initiation in block N.
2. Know that balance snapshots execute in block N+1.
3. Submit a transfer transaction targeting block N+1 (after queries) or block N+2 (before callback).

This is a realistic front-running attack on NEAR, where block times are ~1 second and mempool visibility is public. The `MigrationOperator` role is required to initiate migration, but no privileged role is required to exploit it — any nBTC holder can execute the transfer.

---

### Recommendation

- **Short term**: Add a check in `internal_migrate_to_new_token` that verifies the old token is paused before proceeding. Since the current nbtc token has no pause mechanism, add a `pause` / `is_paused` function to `contracts/nbtc/src/lib.rs` (gated to the controller) and assert it is active at migration start.
- **Long term**: Redesign the migration to be atomic where possible, or use a two-phase commit (freeze → snapshot → mint → unfreeze) with explicit on-chain state tracking to prevent any transfers during the snapshot window.

---

### Proof of Concept

1. `MigrationOperator` calls `migrate_to_new_token(new_token, [alice, bob])` in block N.
2. In block N+1, the bridge's parallel receipts execute: `ft_total_supply()` → 1000, `ft_balance_of(alice)` → 600, `ft_balance_of(bob)` → 400.
3. Also in block N+1 (after the query receipts), Alice calls `ft_transfer(carol, 200)` on the old nbtc token. Carol is not in the accounts list.
4. In block N+2, `migrate_to_new_token_mint` fires: `sum = 600 + 400 = 1000 == total_supply`. Check passes.
5. New token mints: Alice ← 600 nBTC, Bob ← 400 nBTC. Total minted = 1000.
6. `migrate_to_new_token_resolve` sets `nbtc_account_id = new_token`. Old token is abandoned.
7. **Result**: Alice holds 400 on old token + 600 on new token. Bob holds 400 on new token. Carol holds 200 on old token with no new-token equivalent. Alice has 200 extra nBTC on the new token; Carol's 200 nBTC are permanently stranded. [7](#0-6) [8](#0-7) [9](#0-8)

    pub(crate) fn internal_migrate_to_new_token(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> Promise {
        let old_token = self.internal_config().nbtc_account_id.clone();
        require!(
            new_token != old_token,
            "New token must differ from the current token"
        );

        let mut queries = ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_total_supply();
        for account in &accounts {
            queries = queries.and(
                ext_nbtc::ext(old_token.clone())
                    .with_static_gas(GAS_FOR_FT_QUERY)
                    .ft_balance_of(account.clone()),
            );
        }

        let callback_gas = Gas::from_gas(
            GAS_FOR_MIGRATION_MINT_CALL_BACK.as_gas()
                + GAS_FOR_MIGRATION_RESOLVE_CALL_BACK.as_gas()
                + GAS_FOR_MINT_ACTION.as_gas() * accounts.len() as u64,
        );
        queries.then(
            Self::ext(env::current_account_id())
                .with_static_gas(callback_gas)
                .migrate_to_new_token_mint(new_token, accounts),
        )
    }

#[near]
impl FungibleTokenCore for Contract {
    #[payable]
    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // Legacy bridging flow used by Near Intents
        if receiver_id == env::current_account_id()
            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
        {
            if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
                return self.token.ft_transfer(withdraw_relayer, amount, memo);
            }
        }

        self.token.ft_transfer(receiver_id, amount, memo);
    }

    #[payable]
    fn ft_transfer_call(
        &mut self,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) -> PromiseOrValue<U128> {
        self.token.ft_transfer_call(receiver_id, amount, memo, msg)
    }

    fn ft_total_supply(&self) -> U128 {
        self.token.ft_total_supply()
    }

    fn ft_balance_of(&self, account_id: AccountId) -> U128 {
        self.token.ft_balance_of(account_id)
    }
}
