### Title
`execute_refund` Cannot Be Re-Executed After First Execution Due to Stale `btc_pending_info` — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`execute_refund` is explicitly designed to be callable multiple times (e.g., after a consensus branch change), but the second call always panics with `"pending info already exist"` because the `BTCPendingInfo` created by the first call is never removed before the second call attempts to insert a new one with the same key.

### Finding Description

`finalize_refund_with_psbt` inserts a new `BTCPendingInfo` keyed by `btc_pending_id` (derived deterministically from the PSBT inputs and outputs) and requires the slot to be empty: [1](#0-0) 

At the same time, the code explicitly keeps the refund request alive after the first execution (setting `executed = true`) so that `execute_refund` can be called again: [2](#0-1) 

And `load_refund_request_for_execute` explicitly permits re-entry when `executed == true`: [3](#0-2) 

The contradiction: the pre-execution checks pass on the second call, but `finalize_refund_with_psbt` panics because the first `BTCPendingInfo` (keyed by the same deterministic `btc_pending_id`) is still present in `btc_pending_infos`.

There is no path to remove the stale pending info while the refund request is still active. `remove_refund_pending_tx_id` explicitly blocks removal while the request exists: [4](#0-3) 

The only operator escape hatch is to call `reject_refund` (which removes the request) and then `remove_refund_pending_tx_id` — but this cancels the refund entirely, forcing the user to restart from scratch.

### Impact Explanation

When the first refund transaction is not confirmed on-chain (low fee, network congestion, or a Zcash consensus branch change — the exact scenario the re-execution path was designed for), the user cannot call `execute_refund` again to rebuild the transaction. Their BTC/ZEC remains locked in the deposit UTXO with no self-service recovery path. Operator intervention is required to cancel and restart the refund. This matches the **Medium** allowed impact: *stuck bridge state requiring operator intervention*.

### Likelihood Explanation

The scenario is realistic and was explicitly anticipated by the developers (the comment on line 395–397 names "consensus branch change" as a use case). For Zcash, the `last_block_height` parameter fed into the PSBT changes with every block, so the `btc_pending_id` may differ on the second call — but the old pending info still occupies the slot under the original key, and the `require_pending_sign_capacity` guard may also block re-entry. For Bitcoin, the PSBT is built from the same outpoint and refund output, making the `btc_pending_id` identical and the panic deterministic. Any user whose refund transaction stalls hits this path.

### Recommendation

Before inserting the new `BTCPendingInfo` in `finalize_refund_with_psbt`, check whether a stale entry already exists for the same UTXO and remove it (along with its `btc_pending_sign_ids` / `btc_pending_verify_list` bookkeeping). Alternatively, expose a privileged `clear_stale_refund_pending_info` method that operators can call without having to cancel the refund request, preserving the user's place in the queue.

### Proof of Concept

1. User submits a refund request for UTXO `X`; timelock elapses.
2. User calls `execute_refund("X@0", …)` → `finalize_refund_with_psbt` inserts `btc_pending_info` keyed by `btc_pending_id = Y`; `refund_requests["X@0"].executed` is set to `true`.
3. MPC signs the transaction; the signed tx is broadcast but never confirms (e.g., fee too low).
4. User calls `execute_refund("X@0", …)` again to rebuild with a higher fee.
5. `load_refund_request_for_execute` passes (`executed == true` satisfies the `verified_deposit_utxo` check).
6. `finalize_refund_with_psbt` attempts `btc_pending_infos.insert(Y, …)` → returns `Some(…)` (old entry still present) → `require!(… .is_none(), "pending info already exist")` **panics**.
7. The refund is permanently stuck; the user cannot recover their BTC without operator cancellation.
