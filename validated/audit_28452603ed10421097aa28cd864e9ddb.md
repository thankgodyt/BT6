### Title
Accumulated NEAR Storage Deposits Are Never Returned After Refund Request Removal — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
Users who call `request_refund` and `execute_refund` must attach NEAR tokens as storage deposits. When those refund requests are later finalized (`verify_refund_finalize_callback`) or rejected (`internal_reject_refund`), the on-chain storage is freed but the attached NEAR deposits are never returned to the callers. No NEAR withdrawal mechanism exists anywhere in the visible production contract code. The NEAR tokens are permanently locked in the contract's balance.

### Finding Description
`internal_request_refund` enforces a mandatory NEAR deposit:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
``` [1](#0-0) 

`resolve_execute_refund_timelock` (called by `execute_refund`) enforces a second mandatory NEAR deposit:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_execute_refund(),
    "Insufficient deposit for storage"
);
``` [2](#0-1) 

Both deposits are accepted to cover NEAR storage staking costs. When the refund lifecycle ends, the storage is freed in two paths:

**Path 1 — finalization:** `verify_refund_finalize_callback` removes the refund request and the pending info, freeing the staked storage, but issues no `Promise::new(depositor).transfer(amount)` call:

```rust
self.data_mut().refund_requests.remove(&utxo_storage_keys[0]);
self.internal_remove_btc_pending_info(&tx_id);
``` [3](#0-2) 

**Path 2 — rejection:** `internal_reject_refund` removes the refund request, again freeing storage with no NEAR returned:

```rust
self.data_mut()
    .refund_requests
    .remove(&utxo_storage_key)
    .is_some()
``` [4](#0-3) 

The `ContractData` struct tracks nBTC protocol-fee accounting fields (`acc_collected_protocol_fee`, `cur_available_protocol_fee`, etc.) but has no field for accumulated NEAR deposits, confirming there is no accounting or return mechanism for them: [5](#0-4) 

The only token-transfer helper in `token_transfer.rs` moves nBTC, not NEAR: [6](#0-5) 

### Impact Explanation
Every completed or rejected refund operation permanently locks the caller's NEAR storage deposit inside the contract. Because the refund flow is publicly reachable (any NEAR account can call `request_refund` for a valid BTC deposit), these deposits accumulate over time with no recovery path. This constitutes a permanent, irreversible loss of user funds (NEAR tokens) with no operator escape hatch.

**Impact: Medium** — harmful smart-contract behavior causing permanent locking of user funds without direct theft of BTC/nBTC.

### Likelihood Explanation
Every user who goes through the refund path (a normal, documented bridge operation) is affected. The entry point is fully public and requires no special role. Likelihood is **High** — it triggers on every refund lifecycle completion or rejection.

### Recommendation
Return the storage deposit to the original depositor when the refund request is removed. Track the depositor and the deposit amount at request time, then issue a transfer on removal:

```rust
// In verify_refund_finalize_callback / internal_reject_refund:
Promise::new(original_depositor).transfer(NearToken::from_yoctonear(stored_deposit));
```

Alternatively, adopt NEAR's standard storage-management pattern (NEP-145) so users can explicitly register, deposit, and withdraw their storage balance.

### Proof of Concept
1. Alice calls `request_refund(...)` attaching `required_balance_for_request_refund()` NEAR (e.g., 2 NEAR for a large `tx_bytes` payload up to the 200 KB cap).
2. The refund request is stored on-chain; Alice's NEAR is absorbed into the contract balance.
3. A `RefundOperator` calls `internal_reject_refund(utxo_storage_key)`. The entry is removed from `refund_requests`, freeing the storage.
4. No NEAR is transferred back to Alice. Her deposit is permanently locked in the contract.
5. Repeating across many users causes cumulative, irrecoverable NEAR loss with no admin withdrawal function available. [7](#0-6)
