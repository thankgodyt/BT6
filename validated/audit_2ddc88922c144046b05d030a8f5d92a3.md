### Title
Stub `validatePerasCert`/`validatePerasVote` unconditionally accepts all Peras votes and certificates, enabling unauthorized certificate forging and chain selection manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The only `BlockSupportsPeras` instance in the codebase is a catch-all stub that implements `validatePerasCert` as an unconditional `Right` (always accepts) and `validatePerasVote` without any BLS signature or VRF eligibility proof verification. An unprivileged peer can send crafted votes via the object diffusion mini-protocol that pass this stub validation, accumulate to forge certificates, and manipulate chain selection by boosting arbitrary blocks. This is structurally analogous to the external report's self-referential refund bypass: the validation function is supposed to verify that a vote comes from a distinct, credentialed committee member, but the stub skips that verification entirely, making the "credential check" a no-op — just as `refund(account, account, ...)` injects no real value.

---

### Finding Description

**Root cause — stub validation in the only `BlockSupportsPeras` instance:**

`SupportsPeras.hs` declares a catch-all instance for all block types:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

`validatePerasCert` unconditionally returns `Right` for every certificate — no aggregate BLS signature verification, no VRF output batch verification, no round-number or boosted-block validity checks:

```haskell
  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

`validatePerasVote` only checks whether the voter ID appears in the stake distribution (`lookupPerasVoteStake`). It does **not** verify:
- The BLS vote signature (`pvSignature` in `V1.PerasVote`)
- The VRF eligibility proof (`pvEligibilityProof`) for non-persistent committee members
- Round number validity or the existence/validity of the target block

```haskell
  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
``` [3](#0-2) 

**Production ingestion path — `processVotes` calls the stub directly:**

In `ObjectPool/PerasVote.hs`, `makePerasVotePoolWriterFromChainDB` wires the stub `validatePerasVote` into the live vote ingestion path for votes received from peers via the object diffusion mini-protocol:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

`processVotes` validates all votes in a batch atomically and, if all pass, timestamps and adds them to the DB: [5](#0-4) 

**Self-referential analog to the external report:**

The external report's vulnerability: `refund(account, account, ...)` is a self-transfer that injects no real value, so the shortage is never covered. The structural analog here: `validatePerasVote` is supposed to verify that the vote comes from a *distinct, credentialed* committee member (a third party with a valid BLS key and VRF proof). The stub skips that verification entirely. Any peer can claim to be any committee member — acting as both the "voter" and the "verifier" of their own eligibility — and the validation passes without injecting any real cryptographic proof. The "credential check" is a no-op, just as the self-transfer was.

**Certificate forging path:**

Once enough crafted votes accumulate in `PerasVoteDB`, `updatePerasRoundVoteStates` forges a certificate when the quorum threshold is crossed: [6](#0-5) 

The forged certificate is then added asynchronously to the ChainDB via `addPerasCertAsync`, triggering chain selection: [7](#0-6) 

Chain selection uses the Peras weight snapshot to boost blocks with certificates, potentially causing the node to prefer the attacker's chain: [8](#0-7)

### Impact Explanation

An unprivileged peer can forge Peras certificates for arbitrary blocks by sending crafted votes with valid voter IDs (public information from the stake distribution) but invalid/absent BLS signatures. The forged certificate boosts the attacker's chosen block in chain selection, causing honest nodes to prefer a non-canonical chain. This is a **bypass of Peras voting and certificate checks that enables unauthorized certificate acceptance and chain selection manipulation** — matching the "Critical" impact category (bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance) and the "High" impact category (chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain).

---

### Likelihood Explanation

High. Any peer reachable via the object diffusion mini-protocol can send crafted votes. No special privileges, keys, or stake are required. The only prerequisite is knowing a valid voter ID from the stake distribution, which is public on-chain data. The attacker needs to send enough votes to exceed the quorum threshold, which is a function of the configured `PerasParams` — achievable by impersonating multiple committee members from the public stake distribution.

---

### Recommendation

1. Implement actual BLS aggregate signature verification in `validatePerasCert` (using the `CryptoSupportsAggregateVoteSigning` interface already defined in `Committee/Crypto.hs`).
2. Implement BLS vote signature verification and VRF eligibility proof verification in `validatePerasVote` (using `CryptoSupportsVoteSigning`).
3. Until these are implemented, disable the object diffusion protocol for Peras votes and certificates in production, or gate it behind a feature flag that is off by default.
4. Track the open issue referenced in the TODOs: `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

1. Connect to a node via the object diffusion mini-protocol (no privileges required).
2. Read the `PerasVoteStakeDistr` (public stake distribution data).
3. For each committee member ID in the distribution, craft a `PerasVote` (`V1.PerasVote`) with:
   - Valid `pvVoteVoterId` / `pvSeatIndex` (from the stake distribution)
   - Arbitrary or zeroed `pvSignature` (not verified by the stub)
   - `PersistentPerasVoteEligibilityProof` (no VRF proof required by the stub)
   - `pvBoostedBlock` set to the attacker's chosen block hash
4. Send these votes to the node via the object diffusion protocol.
5. `processVotes` calls `validatePerasVote` on each vote; the stub accepts them because the voter IDs are in the stake distribution.
6. Votes are added to `PerasVoteDB` as `ValidatedPerasVote` with their real stake weights.
7. When the accumulated stake exceeds the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for the attacker's block.
8. `addPerasCertAsync` adds the certificate to the ChainDB, triggering chain selection.
9. Chain selection boosts the attacker's block, potentially causing the node to switch to the attacker's chain.

Alternatively, for the certificate path: send a crafted `PerasCert` directly via the object diffusion protocol; `validatePerasCert` accepts it unconditionally (`Right` always), bypassing all aggregate signature and VRF verification.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
