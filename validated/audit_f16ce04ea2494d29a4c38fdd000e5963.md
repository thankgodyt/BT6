### Title
Stub `validatePerasCert` Allows Any Peer to Pre-Register a Fraudulent Peras Certificate, Permanently Blocking the Honest Certificate and Corrupting Chain-Selection Boost Weight - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound certificate. Combined with the `PerasCertDB`'s first-writer-wins semantics (one certificate per round, duplicates silently ignored), an unprivileged peer can send a crafted `PerasCert` for any round R boosting an attacker-chosen block before the honest certificate arrives. The honest certificate is then permanently silenced as `PerasCertAlreadyInDB`, and chain selection permanently uses the attacker's fraudulent boost weight for that round.

---

### Finding Description

**Root cause — stub validation:**

`validatePerasCert` in the universal `BlockSupportsPeras` instance always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

**Inbound path — stub is wired into production cert processing:**

`processCerts` (called by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) passes every inbound peer certificate through this stub:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

Because `validateCert` always returns `Right`, the `partitionEithers` branch that would throw `PerasCertValidationError` and disconnect the peer is never taken; every certificate from every peer is accepted and forwarded to `addCert`. [4](#0-3) 

**First-writer-wins semantics in `implAddCert`:**

`implAddCert` stores the first certificate seen for a given `PerasRoundNo` and silently returns `PerasCertAlreadyInDB` for every subsequent certificate for the same round, regardless of which block it boosts:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    writeTVar pcdbState ...
    pure AddedPerasCertToDB
``` [5](#0-4) 

**Broken assumption in the ChainDB API:**

The `AddPerasCertPromise` comment explicitly relies on the assumption that certificate equivocation is impossible:

> "If the PerasCertDB did already contain a certificate for this round, the certificate is ignored (as the two certificates must be identical because certificate equivocation is impossible)." [6](#0-5) 

This assumption is violated by the stub: since no cryptographic proof is checked, any peer can forge an equivocating certificate that passes "validation."

**Chain selection consumes the corrupted weight snapshot:**

`chainSelSync` reads the `PerasCertDB` weight snapshot and uses it to trigger chain selection for the boosted block. If the fraudulent certificate's boosted block is on a minority fork, chain selection will prefer that fork over the honest canonical chain: [7](#0-6) 

**The state-machine test acknowledges the equivocation gap:**

The `PerasCertDB` state-machine test explicitly excludes equivocating certificates from its precondition, confirming the DB has no equivocation guard:

```haskell
-- We should reject equivocating certificates, that is, certificates
-- for the same round but boosting different blocks.
AddCert cert -> all p model.certs
  where
    p cert' =
      getPerasCertRound cert /= getPerasCertRound cert'
        || getPerasCertBoostedBlock cert == getPerasCertBoostedBlock cert'
``` [8](#0-7) 

The production inbound path has no equivalent guard.

---

### Impact Explanation

An unprivileged peer can permanently corrupt the Peras boost weight for any round on a target node. The Peras boost (`perasWeight = PerasWeight 15`) is a significant additive weight applied during chain selection. By pre-registering a fraudulent certificate for round R that boosts an attacker-controlled block B_attacker, the attacker causes the node's chain selection to assign that boost to B_attacker's chain instead of the honest chain. This can cause the node to prefer a shorter or non-canonical chain over the honest canonical chain, constituting a chain-selection safety failure reachable by any unprivileged peer.

**Impact class**: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only that the attacker's certificate for round R arrives at the target node before the honest certificate for round R. Since the attacker controls when it sends its message and can target nodes that have not yet received the honest certificate (e.g., nodes that are slightly behind in cert propagation, or nodes the attacker is directly connected to), this is a realistic race condition. No stake, keys, or privileged access are required. Likelihood: **Medium** (requires timing advantage, but the attacker fully controls the timing of its own messages).

---

### Recommendation

1. **Implement `validatePerasCert` with real cryptographic validation** (resolving issue #120) before the Peras certificate diffusion path is enabled in production. The stub must verify the certificate's BLS/committee signature and quorum proof.

2. **Add an equivocation guard in `implAddCert`**: when a certificate for a round already exists and the new certificate boosts a *different* block, the new certificate must be rejected (and the peer disconnected), not silently ignored. The current silent-ignore is only safe if validation is complete.

3. **Make the `processCerts` TOCTOU window safe**: the `alreadyInDb` snapshot and the `addCert` call are not atomic. While `implAddCert` handles duplicates, the equivocation case is not handled between the snapshot and the write.

---

### Proof of Concept

On a private testnet with two nodes A (honest) and B (attacker):

1. At the start of Peras round R, before the honest certificate propagates, B sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = B_attacker }` to A via the object-diffusion mini-protocol.
2. A's `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right` unconditionally.
3. A's `implAddCert` stores the fraudulent cert; `pcdsCertIds` now contains R.
4. The honest certificate for round R arrives. `implAddCert` returns `PerasCertAlreadyInDB`; the honest cert is discarded.
5. A's `getWeightSnapshot` returns `B_attacker → PerasWeight 15`.
6. When A's chain selection runs, it assigns the Peras boost to B_attacker's chain, causing A to switch to or prefer B_attacker's fork over the honest canonical chain. [1](#0-0) [4](#0-3) [5](#0-4)
