### Title
Chain-Selection Guard Ignores Peras Weight Boosts While Actual Selection Uses Them — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the chain sync client uses `emptyPerasWeightSnapshot` (zero Peras weight boosts) to decide whether to disconnect from a peer whose headers are beyond the forecast horizon. The actual chain selection in `ChainSel.hs` uses the real `PerasWeightSnapshot` (including Peras boosts). This two-metric mismatch — identical in structure to the external report — means an honest node can be forced to disconnect from a peer serving a heavier Peras-boosted chain, leaving the node on a lighter, non-canonical chain.

---

### Finding Description

**Guard path — uses empty weights (metric A):**

In `Client.hs`, `checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever a header is beyond the forecast horizon and the node is blocking on `retry`. The guard calls `preferAnchoredCandidate` with `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← metric A: block-number only
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` reduces to a pure block-number comparison; Peras weight boosts are invisible. If the candidate has the same or fewer blocks than ours but is heavier due to Peras boosts, the guard evaluates to `ShouldNotSwitch` and throws `CandidateTooSparse`, disconnecting the peer.

**Execution path — uses real weights (metric B):**

In `ChainSel.hs`, the actual chain-selection assertion and sort both use the live `weights` snapshot:

```haskell
assert
  ( all
      (shouldSwitch . preferAnchoredCandidate bcfg weights curChain . Diff.getSuffix . fst)
      chainDiffs
  )
``` [2](#0-1) 

`weights` is the real `PerasWeightSnapshot`, so `wsvTotalWeight = blockNo + weightBoost` governs the comparison.

**The structural mismatch:**

| Site | Weights used | Comparison basis |
|---|---|---|
| `checkPreferTheirsOverOurs` (guard) | `emptyPerasWeightSnapshot` | block number only |
| `chainSelection` (execution) | real `PerasWeightSnapshot` | block number + Peras boosts |

This is the direct analog of the external report: the guard uses one metric to decide safety, while the actual operation uses a different metric. The guard does not guarantee the execution outcome.

The `SecurityParam` comment itself acknowledges the dual interpretation: [3](#0-2) 

And `WeightedSelectView` confirms that `wsvTotalWeight` is the authoritative comparison value: [4](#0-3) 

---

### Impact Explanation

When Peras is active, a peer can serve a chain whose Peras-boosted total weight exceeds our chain's total weight, yet whose raw block count is equal to or less than ours. When those headers are beyond the forecast horizon, `checkPreferTheirsOverOurs` fires, ignores the boosts, concludes the candidate is not preferred, and disconnects with `CandidateTooSparse`. The node never downloads the blocks, never runs the real chain-selection comparison, and remains on the lighter chain. This is a chain-selection divergence: an honest node is made to prefer a non-canonical, less-secure chain over the heavier Peras-boosted canonical chain, driven entirely by a crafted (or naturally occurring) header sequence from an unprivileged peer.

---

### Likelihood Explanation

The preconditions are: (1) Peras is enabled and producing boosts, (2) a peer's chain has equal or fewer blocks than ours but higher total weight due to boosts, and (3) those headers are beyond the current forecast horizon. All three are normal operating conditions in a Peras-enabled network during periods of slot gaps or chain-sync lag. The in-code `TODO` comment explicitly flags this as a known defect (`https://github.com/tweag/cardano-peras/issues/64`), confirming the developers recognise the inconsistency. No key compromise, stake majority, or privileged access is required.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` so the guard uses the same metric as the actual chain selection. Alternatively, remove the check entirely as the TODO proposes, and instead bound the wait by a timeout or LoP-bucket mechanism that does not depend on chain preference. Either way, the guard and the execution path must use the same weight metric.

---

### Proof of Concept

1. Peras is active; block `B` at slot `S` has received a Peras boost of weight `W`.
2. Our chain tip is at block number `N`; the peer's chain tip is also at block number `N` but includes `B`, giving it total weight `N + W > N`.
3. The peer sends the header for a block at slot `S' > S` that is beyond the current forecast horizon.
4. `readLedgerStateHelper` calls `projectLedgerView`, which returns `Nothing` (outside forecast range).
5. `checkPreferTheirsOverOurs` is invoked; it calls `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag`.
6. With empty weights, both fragments have total weight `N`; `preferCandidate` returns `ShouldNotSwitch`.
7. `throwSTM CandidateTooSparse` fires; the peer is disconnected.
8. The real `chainSelection` path, which would have computed `N + W > N` and switched, is never reached.
9. The node remains on the lighter chain, diverging from nodes that did not hit the forecast-horizon gate.
