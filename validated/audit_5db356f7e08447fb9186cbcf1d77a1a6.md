### Title
Missing Era Discriminator Check in `interpretQueryIfCurrentLookup` / `interpretQueryIfCurrentTraverse` Allows Wrong-Era UTxO Queries to Succeed - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/Combinator/Ledger/Query.hs`)

---

### Summary

`interpretQueryIfCurrentLookup` and `interpretQueryIfCurrentTraverse` omit the era-mismatch guard for the `QZ` (first-era) case that the `QFNoTables` sibling `interpretQueryIfCurrent` correctly enforces. An unprivileged client connected via the `LocalStateQuery` mini-protocol can send a `QueryIfCurrent` query tagged for an earlier era (e.g., Shelley) while the node's ledger tip is in a later era (e.g., Conway), and instead of receiving the expected `Left MismatchEraInfo` rejection, receives a `Right` result computed against the wrong ledger state.

---

### Finding Description

`interpretQueryIfCurrent` (the `QFNoTables` path) has four exhaustive cases:

```haskell
go (c :* _) (QZ qry) (Z (Flip st)) =          -- era matches: answer
    Right $ answerPureBlockQuery c qry st
go (_ :* cs) (QS qry) (S st) =                 -- recurse deeper
    first shiftMismatch $ go cs qry st
go _ (QZ qry) (S st) =                         -- QZ but ledger is later era: REJECT
    Left $ MismatchEraInfo $ ML (queryInfo qry) (...)
go _ (QS qry) (Z (Flip st)) =                  -- QS but ledger is first era: REJECT
    Left $ MismatchEraInfo $ MR (hardForkQueryInfo qry) (ledgerInfo st)
``` [1](#0-0) 

`interpretQueryIfCurrentLookup` and `interpretQueryIfCurrentTraverse` have only **three** cases — the critical fourth case (`QZ` query against a later-era ledger state) is absent:

```haskell
go (idx :* _) (c :* _) (QZ qry) _ =           -- ← wildcard ignores ledger era
    Right <$> answerBlockQueryHFLookup idx c qry forker
go (_ :* idx) (_ :* cs) (QS qry) (S st) =
    first shiftMismatch <$> go idx cs qry st
go _ _ (QS qry) (Z (Flip st)) =
    pure $ Left $ MismatchEraInfo $ MR (hardForkQueryInfo qry) (ledgerInfo st)
-- MISSING: go _ _ (QZ qry) (S st) = pure $ Left $ MismatchEraInfo $ ML ...
``` [2](#0-1) 

The same structural omission exists in `interpretQueryIfCurrentTraverse`: [3](#0-2) 

These two functions are dispatched from `answerBlockQueryLookup` / `answerBlockQueryTraverse` inside the `BlockSupportsLedgerQuery` instance: [4](#0-3) 

Which is called by `answerQuery` for `SQFLookupTables` and `SQFTraverseTables` footprints: [5](#0-4) 

Which is invoked directly by the `LocalStateQuery` server for every client query: [6](#0-5) 

---

### Impact Explanation

A client sends `QueryIfCurrentShelley GetUTxO` (a `QFLookupTables` query, encoded as `QueryIfCurrent (QS (QZ q))`) while the node's ledger tip is in the Conway era. The recursion in `interpretQueryIfCurrentLookup` peels off `QS` layers until it reaches `QZ q` with the ledger state still pointing to a later era. The wildcard `_` in the `QZ` arm causes `answerBlockQueryHFLookup` to be called with the Shelley era index and config against the Conway-era forker. The function returns `Right <result>` instead of `Left MismatchEraInfo`. The client receives UTxO data computed through the wrong era's query lens, silently bypassing the era-authorization check that `QueryIfCurrent` is designed to enforce. Wallets or tooling relying on this result to construct or validate transactions receive materially incorrect ledger state, weakening state-query authorization on the public node-to-client API.

**Impact: Medium** — public node API flaw that materially weakens state-query authorization without requiring DoS.

---

### Likelihood Explanation

Any unprivileged client connected via the `LocalStateQuery` mini-protocol can trigger this by sending a `QueryIfCurrent` query with a `QFLookupTables` or `QFTraverseTables` footprint for an era earlier than the current ledger tip. No special keys, stake, or operator access are required. The Cardano mainnet has been in post-Shelley eras for years, making the mismatch condition permanently satisfied for Shelley-era UTxO queries.

---

### Recommendation

Add the missing era-mismatch guard to both `interpretQueryIfCurrentLookup` and `interpretQueryIfCurrentTraverse`, mirroring the `QFNoTables` version:

```haskell
-- In interpretQueryIfCurrentLookup / interpretQueryIfCurrentTraverse:
go _ _ (QZ qry) (S st) =
    pure $ Left $ MismatchEraInfo $ ML (queryInfo qry)
                                       (hcmap proxySingle (ledgerInfo . unFlip) st)
```

This makes the era-check behaviour consistent across all three query footprints (`QFNoTables`, `QFLookupTables`, `QFTraverseTables`).

---

### Proof of Concept

1. Connect a client to a Conway-era node via the `LocalStateQuery` mini-protocol.
2. Acquire the volatile tip.
3. Send `BlockQuery (QueryIfCurrentShelley GetUTxO)` — a `QFLookupTables` query.
4. **Expected**: `Left (MismatchEraInfo ...)` (era mismatch, Shelley query against Conway ledger).
5. **Actual**: `Right <utxo_result>` — the query is answered against the Conway ledger state using the Shelley era index and config, silently bypassing the `QueryIfCurrent` era guard.

The root cause is the wildcard `_` on line 407 of `Ledger/Query.hs` that discards the ledger-state era discriminator, directly analogous to the missing `to_endpoint == Local` check in the original report. [7](#0-6)
