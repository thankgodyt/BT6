### Title
Missing Vote Stake Normalization Before Quorum Threshold Comparison Enables Unauthorized Peras Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a raw `PerasVoteStake` value directly against `perasQuorumStakeThreshold` (a relative `Rational`, e.g. `3/4`) without normalizing the vote stake to the same unit. The code itself documents this in a TODO comment. When the production stake-distribution plumbing is connected, an unprivileged peer can send a single crafted vote whose absolute stake exceeds `3/4`, causing the node to immediately forge a Peras certificate for an attacker-chosen block, bypassing the quorum requirement entirely.

---

### Finding Description

`PerasQuorumStakeThreshold` is defined as a relative fraction of total committee stake (default `3/4`):

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
``` [1](#0-0) 

`stakeAboveThreshold` compares the raw `PerasVoteStake` directly against this relative threshold with no normalization step:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
``` [2](#0-1) 

The code itself acknowledges the unit mismatch in a TODO comment immediately above the function:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The comment on `PerasVoteStake` itself confirms the ambiguity — there is no agreed-upon conversion from absolute ledger stake to the relative committee stake that the quorum threshold expects: [4](#0-3) 

`validatePerasVote` stores the raw value from `PerasVoteStakeDistr` directly into `vpvVoteStake` without any normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [5](#0-4) 

`votesReachQuorum` then sums these unnormalized stakes and passes the total directly to `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [6](#0-5) 

The production inbound vote handler in `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote` with whatever `PerasVoteStakeDistr` is provided, and the current placeholder is `PerasVoteStakeDistr mempty` (empty map, so all votes fail lookup). However, the TODO comment in `NodeToNode.hs` explicitly states this will be replaced with real ledger stake data:

> "when actual plumbing for Peras is ready, we will have to extract the committee selection data from the chainDB to pass it here, instead of relying on an empty the stake distribution." [7](#0-6) [8](#0-7) 

---

### Impact Explanation

When the real ledger stake distribution is connected (the explicitly planned next step), `PerasVoteStakeDistr` will contain absolute lovelace values (e.g., a pool with 1,000,000 ADA has stake ≈ 10¹² lovelace). These values are compared directly against the relative threshold `3/4`. Since any absolute lovelace value >> `3/4`, **a single vote from any pool with positive stake immediately satisfies the quorum check**, causing the node to forge a Peras certificate for the block the attacker voted for. This is a complete bypass of the Peras quorum requirement: unauthorized certificate acceptance for an attacker-chosen block, which directly undermines the chain-boosting security guarantee of the Peras protocol.

Conversely, if the distribution is populated with relative-but-unnormalized values (e.g., relative to total chain stake rather than committee stake), the comparison is still wrong and quorum may never be reachable, permanently disabling certificate creation.

---

### Likelihood Explanation

The vulnerability is latent today (the empty `PerasVoteStakeDistr mempty` placeholder prevents exploitation) but is guaranteed to activate when the planned ledger stake plumbing is connected — a step explicitly described as a TODO in the production code. Any unprivileged peer participating in the Peras vote diffusion miniprotocol is the attacker-controlled entry point. No special keys, admin access, or stake majority is required; the attacker only needs to be a recognized voter in the stake distribution (i.e., operate a stake pool with any positive stake).

---

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` before comparison. Two correct approaches:

1. **Normalize at lookup time**: when building `PerasVoteStakeDistr`, divide each voter's absolute ledger stake by the total committee stake so that all stored values are already relative fractions in `[0,1]`.
2. **Normalize at comparison time**: change `stakeAboveThreshold` to accept the total committee stake as an additional parameter and divide `unPerasVoteStake voteStake` by it before comparing against `perasQuorumStakeThreshold`.

Additionally, enforce at the type level (e.g., a `newtype RelativeStake` vs `AbsoluteStake`) that the two sides of the comparison are always in the same unit, eliminating the possibility of a future regression.

---

### Proof of Concept

Assume the real ledger stake distribution is connected and a pool `P` has 1,000,000 ADA (= 10¹² lovelace). The `PerasVoteStakeDistr` entry for `P` is `PerasVoteStake (10^12 % 1)`.

1. Attacker (pool `P`) sends a `PerasVote` for block `B` via the vote diffusion miniprotocol.
2. `validatePerasVote` looks up `P` in `PerasVoteStakeDistr`, finds `PerasVoteStake (10^12 % 1)`, stores it as `vpvVoteStake`.
3. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (10^12 % 1)`.
4. `stakeAboveThreshold` evaluates: `10^12 >= 3/4 + 2/100` → `True`.
5. A `ValidatedPerasVotesWithQuorum` is produced for block `B` with a single vote.
6. `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting block `B`.
7. The certificate is accepted into the ChainDB and propagated, boosting an attacker-chosen block with a fraudulent Peras certificate.
