### Title
Hardcoded Mainnet Parameters in `gcHistoricityCutoff` Weaken Genesis Historicity Check on Non-Mainnet Networks - (File: `ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` hardcodes Cardano mainnet values for `k` (2160) and slot length (20 s/slot, i.e. `1/f`) when computing `gcHistoricityCutoff`, instead of deriving them from the actual network's genesis configuration. On any non-mainnet network (testnets, private networks) with different security parameters or slot lengths, the historicity cutoff is wrong, weakening or breaking the Genesis historicity defence that protects syncing nodes from long-range adversarial chains.

---

### Finding Description

In `mkGenesisConfig`, the `gcHistoricityCutoff` field is set unconditionally to:

```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
```

The inline comment confirms the assumption:

> "Duration in seconds of one Cardano mainnet Shelley stability window (3k/f slots times one second per slot) plus one extra hour as a safety margin." [1](#0-0) 

The literal `2160` is the mainnet security parameter `k`, and `20` is the mainnet Shelley slot length in seconds (1 slot/s × 20 s/slot = 20). The correct formula is `3 * k / f` slots × slot-length-in-seconds, but neither `k`, `f`, nor the slot length are passed into `mkGenesisConfig`. The function's only input is `Maybe GenesisConfigFlags`, which carries only feature flags and tuning knobs: [2](#0-1) 

The actual genesis parameters (`sgSecurityParam`, `sgActiveSlotsCoeff`, `sgSlotLength`) are available in the `ShelleyGenesis` record and are used correctly elsewhere — for example, `shelleyEraParams` derives `eraGenesisWin` from `SL.computeStabilityWindow`: [3](#0-2) 

and `praosRandomnessStabilisationWindow` is computed from the same genesis fields: [4](#0-3) 

But `gcHistoricityCutoff` ignores all of this and uses the hardcoded mainnet constants.

The `HistoricityCutoff` value is consumed by the `HistoricityCheck` module to decide whether a header received from a peer is "too old" relative to the current wall-clock time. Headers older than the cutoff are rejected as historic. This is a first-line Genesis defence against adversaries who pre-mine a long chain in the past and present it to a syncing node. [5](#0-4) 

---

### Impact Explanation

**Impact: High**

The `HistoricityCutoff` is a security parameter of the Genesis protocol, not a performance knob. Using the wrong value has two failure modes:

1. **Cutoff too large (permissive) — security regression.** On a testnet with, e.g., `k = 100` and 1 s/slot, the correct cutoff is `3 × 100 × 20 + 3600 ≈ 9 600 s`. The hardcoded value is `3 × 2160 × 20 + 3600 = 133 200 s` — roughly 14× too large. An adversary can present headers up to 133 200 seconds old (instead of the intended 9 600 s), bypassing the historicity check entirely. This allows a long-range adversarial chain to be served to a syncing node without triggering the check, weakening the Genesis security guarantee beyond its intended assumptions and potentially causing the node to follow a non-canonical chain.

2. **Cutoff too small (restrictive) — honest headers rejected.** On a network with larger `k` or longer slot lengths, the cutoff is too small. Valid headers from honest peers that are within the correct stability window are rejected as "too historic", causing the node to disconnect from honest peers and potentially stall syncing.

Both failure modes are reachable by any unprivileged peer simply by sending crafted or legitimate headers over the ChainSync mini-protocol.

---

### Likelihood Explanation

**Likelihood: Low**

Cardano mainnet uses exactly `k = 2160` and 1 s/slot, so the hardcoded value is correct there. The issue only manifests on non-mainnet networks (preview, preprod, private testnets, or any future network with different parameters). However, Genesis is specifically being deployed and tested on such networks first, making this a realistic exposure path during the Genesis rollout phase.

---

### Recommendation

Pass the actual network genesis parameters (`k`, active slot coefficient `f`, slot length) into `mkGenesisConfig` (or compute `gcHistoricityCutoff` at a higher call site where the `TopLevelConfig` or `ShelleyGenesis` is available) and replace the hardcoded expression with:

```haskell
gcHistoricityCutoff =
  Just $ HistoricityCutoff $
    round (fromIntegral (3 * k) / f * slotLengthInSeconds) + safetyMargin
```

mirroring the pattern already used in `shelleyEraParams` and `praosRandomnessStabilisationWindow`.

---

### Proof of Concept

1. Spin up a private Cardano testnet with `sgSecurityParam = 100` and `sgSlotLength = 1s` (standard testnet values).
2. Enable Genesis (`enableGenesisConfigDefault`). The node will set `gcHistoricityCutoff = 133 200 s`.
3. The correct cutoff for this network is `3 × 100 × 20 + 3600 = 9 600 s`.
4. As an adversary, pre-mine a chain whose tip slot corresponds to a wall-clock time between 9 600 s and 133 200 s ago.
5. Serve this chain to the syncing node via ChainSync. The historicity check passes (the headers are within the hardcoded 133 200 s window), even though they should have been rejected under the network's actual security parameters.
6. The GDD governor now operates on a chain that the historicity check was supposed to have already filtered out, weakening the overall Genesis security guarantee for this node.
