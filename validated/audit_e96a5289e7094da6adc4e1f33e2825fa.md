Audit Report

## Title
`MpcOmniProver` hardcodes pre-finality levels for Abstract chain and Starknet, enabling reorg-based double-spend — (File: `near/omni-prover/mpc-omni-prover/src/lib.rs`)

## Summary
`MpcOmniProver::init()` permanently inserts `EvmFinality::Latest` for `ChainKind::Abs` and `StarknetFinality::AcceptedOnL2` for `ChainKind::Strk` into the finalities map. Because `verify_proof()` enforces an exact equality match against the stored finality, all Abstract and Starknet proofs are structurally required to use these pre-finality states. A depositor on Abstract chain (a ZKsync-based L2) or Starknet can obtain a valid MPC-signed proof before the source-chain block is settled on L1, claim bridged tokens on NEAR, and then benefit from a sequencer reorg that erases the original deposit — resulting in a double-spend of bridge funds.

## Finding Description
In `init()`, two finality levels are hardcoded with no runtime override path:

```rust
finalities.insert(ChainKind::Abs, MpcFinality::Evm(EvmFinality::Latest));
finalities.insert(
    ChainKind::Strk,
    MpcFinality::Starknet(StarknetFinality::AcceptedOnL2),
);
``` [1](#0-0) 

`verify_proof()` looks up the stored finality and enforces an exact match before forwarding to the MPC network:

```rust
require!(
    Self::request_matches_finality(&payload_v1.request, finality),
    ProverError::FinalityMismatch.as_ref()
);
``` [2](#0-1) 

`request_matches_finality` performs strict equality — `args.finality == *finality` — so a proof with `EvmFinality::Finalized` for Abstract chain is rejected; only `EvmFinality::Latest` is accepted: [3](#0-2) 

The only mutation path, `set_finality`, is `#[private]`, meaning NEAR SDK enforces `predecessor_account_id == current_account_id`. No method in the contract issues a self-call to `set_finality`, so the finality values are immutable without a full contract upgrade: [4](#0-3) 

Abstract chain (`ChainKind::Abs`, chainId 2741) is confirmed as a ZKsync-based EVM L2 (`zksync: true`) in the hardhat config: [5](#0-4) 

On ZKsync-based L2s, `Latest` refers to the most recently produced sequencer block, which has not yet been proven or settled on Ethereum L1. The sequencer can reorg its own blocks before L1 settlement. The test suite confirms the contrast: Ethereum mainnet proofs use `EvmFinality::Finalized`, while Abstract testnet proofs use `EvmFinality::Latest`: [6](#0-5) 

For Starknet, `AcceptedOnL2` means the transaction is accepted by the Starknet sequencer but not yet proven on Ethereum L1. The test fixture for the generic Starknet request uses the stronger `AcceptedOnL1`, while the Starknet Sepolia integration fixture uses `AcceptedOnL2` — matching the stored finality: [7](#0-6) [8](#0-7) 

## Impact Explanation
This is a **Critical** double-spend / theft of bridge funds. An attacker who deposits on Abstract chain or Starknet can obtain a valid MPC-signed proof at the pre-finality state, claim bridged tokens on NEAR, and then benefit from a sequencer reorg that erases the original deposit. The NEAR bridge has no mechanism to reverse a completed mint after a source-chain reorg. This directly matches the allowed Critical impact: "Stealing, loss, double-spending, unauthorized minting … of bridged funds."

## Likelihood Explanation
Abstract chain is a ZKsync-based L2 where the window between a `Latest` block and L1 finalization can span minutes to hours. Starknet sequencer reorgs before L1 proof are similarly documented. The attack does not require the attacker to force a reorg — it requires only that a reorg occurs (naturally or via sequencer operator action) within the window after the MPC signature is obtained and the NEAR mint is completed. Steps 1–3 of the exploit (deposit, obtain MPC signature, claim on NEAR) are fully within the control of any unprivileged bridge user. The reorg dependency lowers likelihood from "trivially exploitable" to "high" given the known architectural properties of ZKsync-based L2s and Starknet pre-L1 states.

## Recommendation
1. Change `ChainKind::Abs` finality from `EvmFinality::Latest` to `EvmFinality::Finalized` (or at minimum `EvmFinality::Safe`), matching the treatment of Ethereum mainnet.
2. Change `ChainKind::Strk` finality from `StarknetFinality::AcceptedOnL2` to `StarknetFinality::AcceptedOnL1`, requiring L1 settlement before a Starknet proof is accepted.
3. Make `set_finality` callable by a privileged admin role (e.g., DAO or owner account) rather than only by the contract itself, so finality levels can be adjusted without a full contract upgrade.

## Proof of Concept
```
// Attacker flow for Abstract chain:

// Step 1: Deposit 1000 USDC on Abstract chain (ZKsync L2, chainId 2741)
//   → InitTransfer event emitted in block N (Latest, not yet proven on L1)

// Step 2: Construct MpcVerifyProofArgs with:
//   sign_payload.request = ForeignChainRpcRequest::Abstract(EvmRpcRequest {
//       finality: EvmFinality::Latest,   // matches stored finality → passes require!()
//       tx_id: <deposit_tx_hash>,
//       extractors: [Log { log_index: <deposit_log_index> }],
//   })

// Step 3: Call mpc_omni_prover.verify_proof(borsh(args))
//   → verify_proof() passes the finality check (Latest == Latest)
//   → MPC network reads the event from block N (Latest) and signs the payload
//   → verify_callback() succeeds, returns ProverResult::InitTransfer

// Step 4: Submit ProverResult to NEAR bridge locker
//   → NEAR bridge mints 1000 bridged USDC to attacker's NEAR account

// Step 5: Abstract chain sequencer reorgs block N before L1 proof submission
//   → Deposit transaction is removed from canonical chain
//   → Attacker's 1000 USDC is returned / never actually locked

// Result: Attacker holds 1000 USDC on Abstract chain + 1000 bridged USDC on NEAR
//         Bridge escrow is undercollateralized by 1000 USDC
```

Unit test confirming the finality enforcement (from `tests.rs`): `test_request_matches_finality_abstract_match` passes with `EvmFinality::Latest` and `test_request_matches_finality_abstract_mismatch` confirms `EvmFinality::Finalized` is rejected — proving that only the weak finality level is accepted by the contract as deployed.     fn request_matches_finality(request: &ForeignChainRpcRequest, finality: &MpcFinality) -> bool {
        match (request, finality) {
            (
                ForeignChainRpcRequest::Ethereum(args) | ForeignChainRpcRequest::Abstract(args),
                MpcFinality::Evm(finality),
            ) => args.finality == *finality,
            (ForeignChainRpcRequest::Starknet(args), MpcFinality::Starknet(finality)) => {
                args.finality == *finality
            }
            _ => false,
        }
    }
```
