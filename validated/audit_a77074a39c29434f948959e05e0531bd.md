### Title
Unbounded `deposit_msg_json` in `RefundRequest` Causes Storage Cost to Exceed `required_balance_for_request_refund` — (`contracts/satoshi-bridge/src/deposit_msg.rs` / `src/refund.rs`)

---

### Summary

`required_balance_for_request_refund` is sized to cover only `tx_bytes` (up to `MAX_REQUEST_REFUND_TX_BYTES` = 200 KB ≈ 2 NEAR). It does not account for `deposit_msg_json`, which is the full JSON serialization of the caller-supplied `DepositMsg` stored verbatim in every `RefundRequest`. Because no size limit is enforced on `DepositMsg` string fields (`extra_msg`, `safe_deposit.msg`, `PostAction.memo`, `PostAction.msg`) in the refund path, an unprivileged user can inflate `deposit_msg_json` to several hundred KB or more, making the actual storage cost of the `RefundRequest` exceed the 2 NEAR anti-spam deposit and causing the protocol to subsidize the excess.

---

### Finding Description

**Step 1 — No size guard on `DepositMsg` in the refund path.**

`internal_request_refund` enforces exactly one size check:

```rust
require!(
    tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
    "tx_bytes too large for refund request"
);
``` [1](#0-0) 

There is no corresponding check on the size of `deposit_msg` or any of its string fields. `check_deposit_msg` (which validates `post_actions` structure) is never called in the refund path — confirmed by the absence of any call to it in `refund.rs`. [2](#0-1) 

**Step 2 — `request_refund_callback` stores the full `DepositMsg` as a JSON string.**

```rust
let refund_request = RefundRequest {
    deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
    ...
    tx_bytes,
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

`deposit_msg_json` is a `String` field inside `RefundRequest`, serialized with Borsh and stored on-chain. Its size is entirely determined by the caller-supplied `DepositMsg`. [4](#0-3) 

**Step 3 — `required_balance_for_request_refund` ignores `deposit_msg_json` size.**

The comment and value are calibrated only for `tx_bytes`:

> "storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). … tx_bytes is capped at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR." [5](#0-4) 

The `~442 bytes` overhead figure does not include a large `deposit_msg_json`. If the attacker supplies a `DepositMsg` with `extra_msg: Some("A".repeat(200_000))`, `deposit_msg_json` alone adds ~200 KB ≈ 2 NEAR of storage on top of the `tx_bytes` contribution, for a total of ~4 NEAR against a 2 NEAR deposit.

**Step 4 — Attacker-controlled fields with no size bound.**

`DepositMsg.extra_msg`, `SafeDepositMsg.msg`, `PostAction.memo`, and `PostAction.msg` are all `String` or `Option<String>` with no declared maximum length: [6](#0-5) 

NEAR's function-call argument limit (~4 MB) is the only practical ceiling, giving a worst-case `deposit_msg_json` of several MB and a storage cost of tens of NEAR against the fixed 2 NEAR deposit.

---

### Impact Explanation

Every `RefundRequest` whose `deposit_msg_json` exceeds ~200 KB causes the protocol to pay for storage beyond what the anti-spam deposit covers. The deposit is non-refundable, so the protocol bears the excess permanently. The invariant stated in the `required_balance_for_request_refund` comment — that 2 NEAR covers the worst-case storage of a refund request — is violated. No funds are stolen; the impact is protocol-subsidized on-chain storage inflation.

---

### Likelihood Explanation

The path is fully permissionless: any user who can send a dust BTC transaction to the derived address (cost: one BTC transaction fee) and attach 2 NEAR can trigger this. The attacker loses 2 NEAR per request but can force the protocol to absorb several NEAR of excess storage per call. Repeated calls multiply the subsidy. The attack requires no privileged role, no leaked key, and no third-party compromise.

---

### Recommendation

Add a size cap on `deposit_msg` string fields in `internal_request_refund`, analogous to the existing `tx_bytes` cap:

```rust
let deposit_msg_json = serde_json::to_string(&deposit_msg).unwrap();
require!(
    deposit_msg_json.len() <= MAX_DEPOSIT_MSG_JSON_BYTES,
    "deposit_msg too large for refund request"
);
```

Size `MAX_DEPOSIT_MSG_JSON_BYTES` to match the remaining storage budget after accounting for `tx_bytes` (e.g., 4 KB is more than sufficient for any legitimate `DepositMsg`). Alternatively, add per-field length checks on `extra_msg`, `safe_deposit.msg`, `PostAction.memo`, and `PostAction.msg` at the point of deserialization or at the top of `internal_request_refund`. Update the `required_balance_for_request_refund` comment to reflect the true worst-case storage once both caps are in place.

---

### Proof of Concept

```
1. Construct DepositMsg {
       recipient_id: "alice.near",
       extra_msg: Some("A".repeat(200_000)),   // 200 KB, no limit enforced
       post_actions: None,
       safe_deposit: None,
       refund_address: Some("bc1q..."),
   }

2. Call get_user_deposit_address(deposit_msg) → derive deposit BTC address.

3. Send dust BTC (e.g., 546 sat) to that address; wait for confirmation.

4. Call request_refund(deposit_msg, refund_address, tx_bytes[~500 B], vout, proof)
   with attached deposit = 2 NEAR (exactly required_balance_for_request_refund()).

5. request_refund_callback fires:
   - get_deposit_path(&deposit_msg) hashes the full JSON → 64-char hex path (fixed size, no issue here)
   - deposit_msg_json = serde_json::to_string(&deposit_msg) → ~200 KB string
   - RefundRequest { deposit_msg_json[~200 KB], tx_bytes[~500 B], ... } inserted into storage

6. Actual storage consumed:
   - deposit_msg_json:  ~200,000 bytes  → ~2.00 NEAR
   - tx_bytes:          ~500 bytes      → ~0.005 NEAR
   - other fields:      ~442 bytes      → ~0.004 NEAR
   - Total:             ~200,942 bytes  → ~2.01 NEAR

   required_balance_for_request_refund() = 2 NEAR
   Excess subsidized by protocol:         ~0.01 NEAR (this example)

   With extra_msg = "A".repeat(3_900_000) (near NEAR 4 MB arg limit):
   deposit_msg_json alone → ~3.9 MB → ~39 NEAR
   Attacker pays 2 NEAR, protocol absorbs ~37 NEAR excess per request.
```

The invariant `required_balance_for_request_refund accurately bounds the storage cost of a refund request` is concretely violated.

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
