Audit Report

## Title
ERC1155 `safeTransferFrom` Callback Causes Unrescuable Finalization Failure, Permanently Freezing Bridged Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

In `OmniBridge.finTransfer`, ERC1155 token delivery uses `IERC1155.safeTransferFrom` (lines 324–330), which by EIP-1155 mandate calls `onERC1155Received` on any contract recipient and reverts if the selector is not returned. When the signed `payload.recipient` is a contract that does not implement `IERC1155Receiver`, every finalization attempt reverts. Because the MPC signature cryptographically binds the recipient address (line 298), no alternative finalization is possible, and the NEAR-side tokens — already burned or locked — are permanently frozen.

## Finding Description

`finTransfer` marks the nonce at line 287 and then calls:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,   // contract without IERC1155Receiver
    multiToken.tokenId,
    payload.amount,
    ""
);
```

The call is not wrapped in a `try/catch`. When `payload.recipient` is a non-compliant contract, the ERC1155 token's internal `_checkOnERC1155Received` reverts, unwinding the entire transaction including the nonce mark. The nonce therefore remains unconsumed, but the signed payload encodes `payload.recipient` in the Borsh message (line 298) that is verified against `nearBridgeDerivedAddress` (line 311). No on-chain path exists to substitute a different recipient without a new MPC signature. The contract exposes no admin rescue function, no alternative-recipient override, and no fallback transfer path for ERC1155. Every subsequent relay attempt with the same signed payload produces the same revert, indefinitely.

The ETH path (lines 317–322) has an analogous issue, but ERC1155 is more severe: ETH rejection is an explicit contract choice, whereas ERC1155 rejection is the default for the vast majority of deployed contracts (multisigs, DeFi vaults, account-abstraction wallets) that simply never implemented the hook.

## Impact Explanation

This directly matches the allowed Critical impact: **permanent freezing of bridged funds**. The NEAR-side tokens are consumed at transfer initiation. The EVM bridge holds the ERC1155 tokens indefinitely with no mechanism to release them. The contract has no admin rescue, no alternative-recipient path, and no refund trigger. The `evm/SECURITY.md` known-issues list does not acknowledge this condition.

## Likelihood Explanation

ERC1155 bridging is a first-class, production feature (`initTransfer1155` / `finTransfer` with `multiTokens` mapping). Any unprivileged user who specifies a contract address as the EVM recipient — a common and legitimate pattern (Gnosis Safe, any DeFi protocol, any AA wallet) — triggers the freeze. No attacker capability is required; the victim need only choose a contract recipient that lacks `IERC1155Receiver`. The condition is repeatable and deterministic.

## Recommendation

Wrap the `safeTransferFrom` call in a `try/catch`:

```solidity
try IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this), payload.recipient, multiToken.tokenId, payload.amount, ""
) {
    // success
} catch {
    // Do NOT consume the nonce; emit a FinTransferFailed event
    completedTransfers[payload.destinationNonce] = false;
    emit FinTransferFailed(payload.destinationNonce, payload.recipient);
    return;
}
```

Additionally, introduce a protocol-level mechanism (either an admin-callable rescue function that redirects to an alternate recipient given a valid MPC signature, or a NEAR-side refund path triggered by a `FinTransferFailed` event) so that funds are never irrecoverably locked when finalization fails.

## Proof of Concept

1. Deploy a minimal ERC1155 token and register it via `logMetadata1155`.
2. Deploy a contract `NoHook` that does not implement `IERC1155Receiver`.
3. Call `initTransfer1155` from NEAR (or simulate the NEAR-side burn).
4. Obtain a valid MPC-signed `TransferMessagePayload` with `recipient = address(NoHook)`.
5. Call `OmniBridge.finTransfer(sig, payload)`.
6. Observe revert: `NoHook` does not return `onERC1155Received.selector`.
7. Confirm `completedTransfers[nonce]` is `false` (nonce cleared by revert).
8. Repeat step 5 — identical revert every time.
9. Confirm ERC1155 tokens remain in the bridge contract with no callable rescue path.
10. Confirm NEAR-side tokens are consumed and no refund event is emitted.
