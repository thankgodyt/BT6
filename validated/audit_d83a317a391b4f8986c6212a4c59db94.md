### Title
Race Between `request_refund_callback` and `verify_deposit_callback` Allows Permissionless `reject_refund` That Burns the Requester's Storage Deposit — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

When `request_refund_callback` executes before `verify_deposit_callback` for the same UTXO, the refund request is stored with `executed=false` while the UTXO is subsequently inserted into `verified_deposit_utxo` by the deposit callback. This leaves the contract in a state where `reject_refund` is permissionlessly callable by anyone, causing the refund requester to permanently lose their attached NEAR storage deposit.

---

### Finding Description

Two independent NEAR promise chains can have their callbacks interleaved across blocks:

**Chain A:** `request_refund` → `verify_transaction_inclusion` → `request_refund_callback`
**Chain B:** `verify_deposit` → `verify_transaction_inclusion` → `verify_deposit_callback`

**`request_refund_callback`** checks `verified_deposit_utxo` at the moment it executes:

```rust
// refund.rs:534-541
// Double-check not finalized (could have been verified between request and callback)
require!(
    !self
        .data()
        .verified_deposit_utxo
        .contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
```

If this callback runs **before** `verify_deposit_callback`, the check passes and the refund request is stored with `executed: false`: [1](#0-0) 

Then `verify_deposit_callback` runs and inserts the UTXO into `verified_deposit_utxo` and mints nBTC: [2](#0-1) 

The contract now holds both: a `refund_requests` entry with `executed=false` **and** the same key in `verified_deposit_utxo`.

`reject_refund` is a public, unpermissioned function that allows anyone to reject when `is_already_deposited` is true:

```rust
// api/bridge.rs:553-567
let executed = self
    .data()
    .refund_requests
    .get(&utxo_storage_key)
    .map(|r| RefundRequest::from(r).executed)
    .unwrap_or(false);
let is_already_deposited = !executed
    && self
        .data()
        .verified_deposit_utxo
        .contains(&utxo_storage_key);
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
``` [3](#0-2) 

After the race: `executed=false` and `verified_deposit_utxo` contains the key → `is_already_deposited=true` → the `require!` passes for any caller. `internal_reject_refund` removes the refund request without returning the storage deposit: [4](#0-3) 

The NEAR attached to `request_refund` (enforced by `required_balance_for_request_refund()`) is permanently consumed by the contract and never returned. [5](#0-4) 

---

### Impact Explanation

The refund requester loses their NEAR storage deposit. The deposit is documented as non-refundable (anti-spam fee + storage cost), but the design intent is that it is consumed only when the request is legitimately processed or rejected by a privileged actor. In this race, an unprivileged third party can trigger the rejection and the user loses their NEAR with no recourse. No BTC or nBTC is lost — the deposit is correctly minted — but the user's NEAR is silently burned.

---

### Likelihood Explanation

NEAR processes receipts from independent transaction chains in a deterministic but interleaved order across blocks. Both `request_refund` and `verify_deposit` are submitted by different actors (user and relayer) for the same UTXO — a scenario explicitly anticipated by the codebase's own documentation (`doc/refund-race-deposit-wins-flow.md`). The callback ordering where `request_refund_callback` precedes `verify_deposit_callback` is a natural outcome of NEAR's receipt scheduling when both light-client calls resolve in the same block. No special privileges or key compromise are required.

---

### Recommendation

In `request_refund_callback`, after storing the refund request, immediately check whether `verified_deposit_utxo` now contains the key (a second read after the insert) and if so, remove the just-inserted request and refund the attached deposit to the caller. Alternatively, atomically gate the insert on the absence of the UTXO in `verified_deposit_utxo` and return the deposit on failure rather than panicking, so the user's NEAR is not consumed when the race is lost.

---

### Proof of Concept

Interleave callback execution in a unit test:

1. Submit `request_refund` for UTXO `txid@0` — light-client mock returns `true`.
2. Submit `verify_deposit` for the same UTXO — light-client mock returns `true`.
3. Execute `request_refund_callback` first (before `verify_deposit_callback`):
   - Assert `refund_requests` contains `txid@0` with `executed=false`.
4. Execute `verify_deposit_callback`:
   - Assert `verified_deposit_utxo` contains `txid@0`.
   - Assert nBTC minted.
5. Call `reject_refund("txid@0")` from an unprivileged account:
   - Assert it succeeds (no panic).
   - Assert `refund_requests` no longer contains `txid@0`.
   - Assert the refund requester's NEAR balance did not increase (deposit not returned).

The invariant "a refund requester must not lose their storage deposit due to a concurrent deposit verification" is violated at step 5.
