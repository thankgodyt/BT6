### Title
Missing ECDSA Low-S Normalization in MPC Signature Conversion Produces Non-Standard Bitcoin Transactions, Permanently Locking Withdrawal Funds — (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

The `to_btc_signature()` method in `chain_signature.rs` converts a raw MPC `SignatureResponse` into a Bitcoin ECDSA signature using `secp256k1::ecdsa::Signature::from_compact`. This function accepts any mathematically valid `(r, s)` pair but does **not** normalize `s` to its low-half form. Bitcoin's consensus rules (BIP-66, enforced network-wide since July 2015) mandate that all signatures use a low-s value (`s ≤ n/2`). A high-s signature causes the signed transaction to be rejected by every Bitcoin node, making the withdrawal permanently unbroadcastable while the bridge remains in a stuck `PendingVerify` state with the user's nBTC already burned.

---

### Finding Description

In `chain_signature.rs`, `to_btc_signature()` constructs a Bitcoin signature directly from the MPC response bytes:

```rust
let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
    .expect("Invalid signature");
Signature::sighash_all(signature)
```

`from_compact` validates only that `r` and `s` are in `[1, n-1]`; it does **not** enforce `s ≤ n/2`. Neither `from_compact` nor `Signature::sighash_all` calls `normalize_s()`. The NEAR Chain Signatures MPC service is a threshold ECDSA scheme that can return either a low-s or a high-s value — both are algebraically valid ECDSA signatures. Approximately half of all signing operations will produce a high-s value.

When `sign_btc_transaction_callback` receives a high-s `SignatureResponse`, it stores it verbatim, calls `psbt.save_signature(sign_index, signature, public_key)`, serializes the PSBT, and — once all inputs are signed — calls `psbt.extract_tx_bytes_with_sign()` and emits `Event::SignedBtcTransaction`. The pending info is moved to `PendingVerify` stage. The relayer then attempts to broadcast the raw transaction bytes to the Bitcoin network, where every node rejects it as non-standard (BIP-66 violation). The transaction can never confirm, so `verify_refund_finalize` / the withdrawal finalization callback is never triggered, and the bridge state is permanently stuck. [1](#0-0) [2](#0-1) 

---

### Impact Explanation

**Medium — Stuck bridge state requiring operator intervention.**

Once all inputs of a withdrawal PSBT are signed with a high-s signature, the bridge transitions the pending info to `PendingVerify` and removes it from the account's `btc_pending_sign_ids`. The signed transaction bytes are emitted on-chain and stored in `btc_pending_info.tx_bytes_with_sign`. Because the transaction is permanently invalid on the Bitcoin network, the withdrawal can never be finalized. The user's nBTC is burned (or locked pending burn) and the corresponding BTC UTXOs are consumed from the bridge's available set, with no recovery path short of operator intervention (e.g., a DAO-authorized state migration or RBF replacement with a corrected signature). [3](#0-2) 

---

### Likelihood Explanation

**Medium.** ECDSA threshold signing schemes produce `s` values that are uniformly distributed over `[1, n-1]`. Without explicit low-s normalization, roughly 50% of signing operations yield a high-s value. Every withdrawal that triggers a high-s MPC response will produce an unbroadcastable transaction. This is not a rare edge case; it is an expected outcome of normal MPC operation on any withdrawal.

---

### Recommendation

After `from_compact` succeeds, call `normalize_s()` on the resulting signature before wrapping it:

```rust
let (normalized, _was_high_s) = signature.normalize_s();
Signature::sighash_all(normalized)
```

`bitcoin::secp256k1::ecdsa::Signature::normalize_s()` returns the low-s canonical form and a boolean indicating whether normalization was applied. This is the standard fix used by all production Bitcoin signing libraries and wallets. [1](#0-0)

### Proof of Concept

1. **User** calls `ft_transfer_call` on the nBTC contract, transferring nBTC to the bridge to initiate a withdrawal. The bridge records a `BTCPendingInfo` in `PendingSign` state.

2. **Relayer** calls `sign_btc_transaction(btc_pending_sign_id, sign_index=0, key_version)`. The bridge calls `sign_promise(SignRequest { payload, path, key_version })` to the MPC contract and chains `sign_btc_transaction_callback`.

3. **MPC** returns a `SignatureResponse` where `s > n/2` (high-s). This occurs with ~50% probability per signing call.

4. **`sign_btc_transaction_callback`** executes:
   - Calls `signature.to_btc_signature()` → `from_compact([r || s])` → no normalization → high-s `Signature` stored.
   - `psbt.save_signature(0, signature, public_key)` embeds the high-s signature into the PSBT.
   - `psbt.extract_tx_bytes_with_sign()` serializes the transaction with the high-s signature.
   - `Event::SignedBtcTransaction { tx_bytes }` is emitted.
   - `btc_pending_info.to_pending_verify_stage()` moves state to `PendingVerify`.

5. **Relayer** broadcasts `tx_bytes` to the Bitcoin network. Every node rejects the transaction: `mandatory-script-verify-flag-failed (Non-canonical DER signature)` (BIP-66).

6. The bridge is stuck: the `BTCPendingInfo` remains in `PendingVerify`, the UTXOs are consumed, and the user's nBTC is burned with no corresponding BTC release. Operator intervention is required. [1](#0-0) [4](#0-3)

    pub fn to_btc_signature(&self) -> Signature {
        let r_hex = self.big_r.affine_point[2..].to_string();
        let s_hex = self.s.scalar.clone();
        let r = hex::decode(r_hex).expect("Invalid r hex");
        let s = hex::decode(s_hex).expect("Invalid s hex");
        let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
            .expect("Invalid signature");
        Signature::sighash_all(signature)
    }

    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }
