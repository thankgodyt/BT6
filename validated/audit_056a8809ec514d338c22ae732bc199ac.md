### Title
Unconditional `validatePerasCert` Acceptance Enables Forged-Certificate Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) for every inbound Peras certificate, performing zero cryptographic or protocol-level checks. Because this stub is wired directly into the production network ingest path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject an arbitrary forged certificate that the node will accept, store, and act upon during chain selection — potentially causing the node to switch to a non-canonical fork.

---

### Finding Description

In `SupportsPeras.hs`, the default instance of `BlockSupportsPeras` provides a stub `validatePerasCert` that always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature check, no quorum check, no round-number bounds check, no committee membership check — the function wraps any `PerasCert` in a `ValidatedPerasCert` and returns it as valid.

This stub is not isolated to tests. It is the live validator passed to `processCerts` in both production pool-writer constructors:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` is the inbound-certificate handler for the Peras certificate ObjectDiffusion mini-protocol. It calls `validateCert` on every certificate received from a peer, and if all pass (which they always do), it adds them to the database: [3](#0-2) 

Once a `ValidatedPerasCert` is stored, `chainSelSync` processes it: it adds the certificate to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block, giving it the full `PerasWeight` boost in chain selection: [4](#0-3) 

The analog to the reported bug is exact: just as `computeVote` silently emits `VoteResults` when it should fail (no valid votes, wrong policy), `validatePerasCert` silently returns `Right` when it should fail (no valid quorum, no valid aggregate signature, no valid committee membership). Both functions produce a misleading "success" result that downstream logic treats as authoritative.

---

### Impact Explanation

An attacker who can connect as a peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block in the VolatileDB. The node will:

1. Accept the certificate without any cryptographic check.
2. Store it in the `PerasCertDB`.
3. Trigger `chainSelectionForBlock` for the boosted block, adding `perasWeight` to its chain weight.

If the boosted block is on a competing fork, the node may switch to that fork. Because `PerasWeight` is designed to be large enough to overcome honest-chain density advantages (that is the entire point of the Peras boost), a single forged certificate can be sufficient to flip chain selection. This lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The attack requires only a peer connection and the ability to send a well-formed (but cryptographically unsigned) `PerasCert` message over the Peras certificate diffusion mini-protocol. No key material, no stake, no operator access is needed. The stub is the only validator in the production code path and carries explicit `TODO` markers acknowledging it is incomplete. Any node running this code with Peras certificate diffusion enabled is reachable.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the aggregate BLS signature over the `(electionId, candidate)` pair using the declared voters' aggregated public keys (as already implemented in `implVerifyCert` for `EveryoneVotes` and `WFALS`).
2. Checks that the declared voters constitute a valid quorum (total stake above `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
3. Validates committee membership for each declared voter against the epoch's stake distribution.
4. Checks that `pcCertRound` is within the valid window (`perasCertMaxRounds`).

Until the real implementation is in place, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the node does not act on unverified certificates.

---

### Proof of Concept

**Setup**: A private testnet with Peras certificate diffusion enabled. Attacker connects as a peer.

**Crafted message**: A `PerasCert` with:
- `pcCertRound = <any round not yet in the DB>`
- `pcCertBoostedBlock = <Point of a block on a competing fork in the VolatileDB>`

**Execution path**:

1. Peer sends the crafted `PerasCert` via the ObjectDiffusion mini-protocol.
2. `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams cert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })`. [5](#0-4) 
3. `processCerts` calls `addCert` → `ChainDB.addPerasCertAsync`. [6](#0-5) 
4. `chainSelSync` processes the cert, looks up the boosted block in the VolatileDB, and calls `chainSelectionForBlock` with the full `PerasWeight` boost. [7](#0-6) 
5. Chain selection now prefers the fork containing the boosted block, causing the node to switch away from the canonical chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
