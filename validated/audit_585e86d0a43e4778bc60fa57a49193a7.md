### Title
Tokens Permanently Locked When Transfer Amount Is Below Decimal Normalization Threshold - (`near/omni-bridge/src/lib.rs`)

### Summary

The `normalize_amount` function uses floor division to scale token amounts from NEAR's native precision to the destination chain's precision. When a user initiates a transfer with an amount smaller than `10^(origin_decimals - decimals)`, the tokens are locked in the bridge during `init_transfer`, but `sign_transfer` subsequently panics with `InvalidAmountToTransfer` because the normalized amount is zero. There is no cancel or refund path for pending transfers, so the user's funds are permanently frozen.

### Finding Description

`normalize_amount` performs integer floor division: [1](#0-0) 

`init_transfer` locks the full token amount and stores the transfer message without verifying that the amount survives normalization: [2](#0-1) 

Only later, in `sign_transfer`, is the normalized amount checked: [3](#0-2) 

At this point the tokens are already locked. `sign_transfer` is gated behind `#[trusted_relayer]`, so the user cannot call it themselves to trigger a refund path. The `sign_transfer_callback` only removes the transfer message when the MPC signing *succeeds* and fee is zero: [4](#0-3) 

Because `sign_transfer` panics before the MPC call is ever made, the callback is never reached, the transfer message stays in `pending_transfers`, and the locked tokens have no recovery path.

The code comment acknowledges dust loss but only for the sub-unit remainder case, not for the case where the *entire* amount rounds to zero: [5](#0-4) 

The `update_transfer_fee` function cannot help the user recover because it only allows the fee to be *increased*, not decreased, and increasing the fee makes `amount_without_fee()` smaller, not larger: [6](#0-5) 

### Impact Explanation

A user who sends an amount below the normalization threshold has their tokens permanently frozen in the bridge contract. This satisfies the "permanent freezing of bridged funds" critical impact category. The loss is not dust — for a NEAR token (24 decimals) bound to a 6-decimal destination chain, `diff_decimals = 18`, so any transfer below `10^18` yoctoNEAR (1 NEAR) is entirely lost.

### Likelihood Explanation

The scenario is reachable by any unprivileged bridge user via the public `ft_transfer_call` → `ft_on_transfer` → `init_transfer` path. No special role is required to initiate the transfer. The only precondition is that the token pair has a non-trivial decimal difference (`origin_decimals > decimals`), which is the normal case for NEAR tokens (24 decimals) bridging to EVM or other chains. A user unfamiliar with the normalization mechanics can easily trigger this by sending a "small" amount.

### Recommendation

Add a normalization check inside `init_transfer` (before locking tokens) to reject transfers whose `amount_without_fee()` would normalize to zero:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        require!(
            Self::normalize_amount(
                transfer_message.amount_without_fee().unwrap_or(0),
                decimals,
            ) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

This mirrors the existing guard in `sign_transfer` but places it *before* tokens are locked, so the `ft_on_transfer` callback can return the full amount to the token contract and the user is refunded atomically.

### Proof of Concept

1. A NEAR-native token is registered with `origin_decimals = 24`, `decimals = 6` (diff = 18).
2. User calls `ft_transfer_call` sending `5 × 10^17` yoctoNEAR (0.5 NEAR) with `fee = 0`.
3. `init_transfer` stores the transfer message and returns `U128(0)` — tokens are locked.
4. Trusted relayer calls `sign_transfer`.
5. `normalize_amount(5×10^17, {24, 6}) = 5×10^17 / 10^18 = 0` (floor division).
6. `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`.
7. The NEAR transaction fails; the transfer message remains in `pending_transfers`; the 0.5 NEAR is permanently locked with no cancel or refund mechanism available to the user. [1](#0-0) [3](#0-2) [2](#0-1)

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
