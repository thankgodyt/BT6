### Title
Refund Address Accepted Without Format Validation at Request Time, Enabling Attacker-Triggered Stuck Refund State - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `refund_address` string accepted by `request_refund` is stored verbatim in `RefundRequest` without any format validation. The address-parsing code (`Address::parse`) exists and is called, but only later inside `execute_refund` → `build_refund_output`. Submitting an unparseable address causes `execute_refund` to panic unconditionally, leaving the refund request in a stuck state that requires a DAO/Operator `reject_refund` call to resolve.

---

### Finding Description

**Where validation is deferred (not applied at request time):**

In `request_refund_callback`, the `refund_address` is stored as a raw string with no format check: [1](#0-0) 

The only check performed is an equality comparison against `deposit_msg.refund_address` when that optional field is `Some`: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for user-supplied refund addresses), any string — including a syntactically invalid address — passes through and is persisted.

**Where the validation code actually lives (execution time, too late):**

`build_refund_output`, called from `internal_execute_refund`, is the first place `Address::parse` is invoked: [3](#0-2) 

If the stored `refund_address` is invalid, `.expect("Invalid refund address")` panics, aborting `execute_refund`. The `RefundRequest` remains in storage with `executed = false`, and `finalize_refund_with_psbt` is never reached, so the UTXO is never added to `verified_deposit_utxo` by the refund path.

**The public entry point is reachable by any NEAR account:**

`request_refund` is `#[payable]` with no role restriction for the `gas_fee = None` case: [4](#0-3) 

Any unprivileged account that can pay the storage deposit and supply a valid Light Client proof can call this function.

---

### Impact Explanation

Once a refund request with an invalid `refund_address` is stored for a given UTXO key, the following hold simultaneously:

1. `execute_refund` panics every time it is called for that key (the bad address is never corrected in storage).
2. A second `request_refund` for the same UTXO is blocked by the duplicate check in `request_refund_callback`.
3. The refund request can only be removed by a DAO or Operator calling `reject_refund`. [5](#0-4) 

This is a **stuck bridge state requiring operator intervention**, matching the Medium impact tier. The victim's BTC remains locked in the deposit UTXO until either the DAO rejects the bad request or the victim separately calls `verify_deposit` to mint nBTC (which then allows permissionless rejection via `is_already_deposited`). [6](#0-5) 

---

### Likelihood Explanation

- `request_refund` is publicly callable by any NEAR account with an attached storage deposit.
- The `deposit_msg` used to derive a deposit address is emitted as a public on-chain event (`LogDepositAddress`), so an attacker can reconstruct it for any unfinalized deposit.
- The BTC transaction proof is also public on-chain data.
- The attacker must pay the storage deposit (a non-trivial anti-spam cost), but the deposit is explicitly **not refunded** per the contract documentation.
- The attack is therefore low-cost relative to the disruption caused.

---

### Recommendation

Validate `refund_address` format using `Address::parse` inside `request_refund_callback` (or `internal_request_refund`) before persisting the `RefundRequest`. Reject the callback with a clear error if parsing fails. This mirrors the validation already present in `build_refund_output` and ensures the invariant "every stored `refund_address` is parseable" holds from the moment of storage.

```rust
// In request_refund_callback, before constructing RefundRequest:
let config = self.internal_config();
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

---

### Proof of Concept

1. Alice deposits BTC to a bridge address derived from `deposit_msg` (with `deposit_msg.refund_address = None`). The deposit is never finalized via `verify_deposit`.
2. Attacker observes the `LogDepositAddress` event, reconstructs Alice's `deposit_msg`, and obtains the on-chain BTC transaction proof.
3. Attacker calls `request_refund(deposit_msg, "NOT_A_VALID_BTC_ADDRESS", tx_bytes, vout, proof, None)` with the required storage deposit attached.
4. The Light Client verifies the proof. `request_refund_callback` stores a `RefundRequest` with `refund_address = "NOT_A_VALID_BTC_ADDRESS"` — no format check is performed.
5. After the timelock, anyone calls `execute_refund(utxo_storage_key, None)`. Inside `build_refund_output`, `Address::parse("NOT_A_VALID_BTC_ADDRESS", chain).expect(...)` panics. The call reverts.
6. Alice's UTXO is now stuck: `execute_refund` always panics, and no second refund request can be submitted for the same UTXO key.
7. A DAO/Operator must call `reject_refund` to unblock the UTXO, constituting required operator intervention. [7](#0-6) [8](#0-7)

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```

```rust
    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
```
