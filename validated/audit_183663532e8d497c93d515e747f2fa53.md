### Title
`is_refund_required()` Misclassifies Successful `ft_on_transfer` as Failed Mint, Enabling nBTC Double-Mint — (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary

The `safe_mint_callback` in the satoshi-bridge uses a helper `is_refund_required()` to decide whether a `safe_mint` call succeeded. The helper treats any `U128(0)` return from `safe_mint` as a failure, but `safe_mint` also returns `U128(0)` when `ft_transfer_call` succeeds and the receiver's `ft_on_transfer` consumes all tokens. This causes the bridge to incorrectly remove the UTXO from `verified_deposit_utxo`, unlocking the same BTC deposit for re-submission and enabling unauthorized double-minting of nBTC.

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` has two distinct code paths:

1. **Unregistered account** — returns `PromiseOrValue::Value(U128(0))` immediately.
2. **Registered account with `msg`** — calls `ft_transfer_call`, which returns the amount *not used* (refunded). If `ft_on_transfer` consumes all tokens it returns `0`, so `ft_resolve_transfer` returns `0`, and `safe_mint` resolves to `U128(0)`. [1](#0-0) 

The `is_refund_required()` helper in `deposit.rs` cannot distinguish these two cases: [2](#0-1) 

It returns `true` whenever the promise result deserializes to `U128(0)`. When that happens, `safe_mint_callback` sets `is_success = false` and:

1. **Removes** the UTXO key from `verified_deposit_utxo` — the only replay guard.
2. **Burns** `mint_amount` from the bridge's own balance (detached, so a panic there does not roll back step 1). [3](#0-2) 

Because the UTXO key is removed, the same BTC proof can be re-submitted via `safe_verify_deposit` (or `verify_deposit`), which re-inserts the key and mints a second batch of nBTC for the same on-chain satoshis. [4](#0-3) 

### Impact Explanation

**Critical — Unauthorized minting of nBTC.** A single BTC UTXO can be used to mint nBTC twice: once via the initial `safe_verify_deposit` (tokens land in the attacker's receiver contract via `ft_on_transfer`) and again after the UTXO guard is incorrectly cleared. The total nBTC supply exceeds the BTC held by the bridge, breaking the 1:1 backing invariant. Additionally, the detached `burn` call destroys `mint_amount` from the bridge's own balance (protocol fees), causing direct loss of protocol funds.

### Likelihood Explanation

Any user who:
1. Deploys a NEAR contract whose `ft_on_transfer` returns `0` (i.e., consumes all received tokens — the normal success case for any DeFi receiver), and
2. Provides that contract as `recipient_id` with a non-empty `safe_deposit.msg` in `DepositMsg`,

will trigger the bug whenever a trusted relayer submits the corresponding BTC proof. The `DepositMsg` is fully user-controlled (it is the input to `get_user_deposit_address`). The relayer does not validate `msg` content. Omni Bridge itself, the primary intended caller of `safe_verify_deposit`, uses `ft_on_transfer` and would naturally return `0` on success, making this triggerable in normal production usage.

### Recommendation

`is_refund_required()` must distinguish the two `U128(0)` cases. The cleanest fix is to have `safe_mint` return a sentinel value (e.g., `U128::MAX`) for the unregistered-account path instead of `U128(0)`, and treat any other `U128(0)` result (successful `ft_on_transfer`) as success. Alternatively, check account registration inside `safe_mint_callback` before deciding to remove the UTXO guard.

### Proof of Concept

1. Attacker deploys contract `evil.near` whose `ft_on_transfer` always returns `"0"` (uses all tokens).
2. Attacker calls `get_user_deposit_address` with `DepositMsg { recipient_id: "evil.near", safe_deposit: Some(SafeDepositMsg { msg: "trigger" }), ... }`.
3. Attacker sends 1 BTC to the derived address; transaction confirms on-chain.
4. Trusted relayer calls `safe_verify_deposit` with the proof and the attacker's `DepositMsg`.
5. Bridge calls `safe_mint("evil.near", 100_000, Some("trigger"))` → `ft_transfer_call` → `evil.near::ft_on_transfer` returns `"0"` → `safe_mint` resolves to `U128(0)`.
6. `is_refund_required()` returns `true`; `safe_mint_callback` removes the UTXO key from `verified_deposit_utxo` and fires a detached burn of 100,000 from bridge balance.
7. `evil.near` already holds 100,000 nBTC from step 5.
8. Relayer (or attacker if they hold `UnrestrictedRelayer`) re-submits the same BTC proof via `safe_verify_deposit`. The UTXO key is absent from `verified_deposit_utxo`, so the `insert` succeeds and a second mint of 100,000 nBTC is issued.
9. Net result: 200,000 nBTC minted for 100,000 satoshis; bridge balance reduced by 100,000 nBTC (protocol fees destroyed).

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }

fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
