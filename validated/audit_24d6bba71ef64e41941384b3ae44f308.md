Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` function in the `BlockSupportsPeras` instance unconditionally returns `Right` (success) for every inbound Peras certificate, performing zero cryptographic or semantic checks. This is the live production code path invoked when a peer sends a certificate over the Peras certificate mini-protocol. Any crafted certificate — with an arbitrary round number, arbitrary boosted block, and no valid aggregate BLS signature — is accepted and stored, directly influencing chain selection.

---

### Finding Description

The `BlockSupportsPeras` instance in `SupportsPeras.hs` provides the degenerate stub implementation used for all block types:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function accepts `params` and `cert`, computes nothing, and immediately wraps the certificate in `Right ValidatedPerasCert`. No aggregate BLS signature is verified, no round number is checked against the current epoch, no boosted block is validated against the chain, and no VRF eligibility proof is examined.

This stub is wired directly into the production inbound certificate processing pipeline. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` partitions results into errors and successes; since `validatePerasCert` always returns `Right`, every certificate passes and is added to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2)

### Impact Explanation

Peras certificates are used in chain selection to boost the weight of a specific block. A `ValidatedPerasCert` carries a `vpcCertBoost` derived from `perasWeight params`, which is applied during chain selection to prefer the boosted block. An adversary who can inject arbitrary certificates can cause an honest node to prefer a non-canonical chain by boosting an attacker-chosen block. This is a **High** impact chain-selection manipulation: an unprivileged peer can make an honest node prefer a less-secure or non-canonical chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The attack requires only network connectivity to a node running the Peras certificate mini-protocol. No keys, stake, or privileged access are needed. The attacker sends a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The certificate passes validation unconditionally and is stored. The likelihood is **High** given the zero-barrier entry path and the fact that this is the active production code path (not a test stub gated behind a feature flag).

---

### Recommendation

1. Implement full cryptographic validation in `validatePerasCert`: verify the aggregate BLS signature over `(roundNo, boostedBlock)` using the committee's aggregate verification key, verify all VRF eligibility proofs for non-persistent voters, and check that the round number falls within the valid window for the current epoch.
2. Implement full signature verification in `validatePerasVote`: call `verifyVoteSignature` against the voter's registered verification key.
3. Populate `bhviewPrevEpochNonce` in `ProtocolHeaderSupportsLedger (Praos c)` with `praosStatePreviousEpochNonce` so that certificate validators can reconstruct the correct VRF election input.
4. Remove or gate the degenerate `instance StandardHash blk => BlockSupportsPeras blk` behind a compile-time flag so it cannot be used in production builds.

---

### Proof of Concept

1. Connect to a node over the Peras certificate mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = <target round>` and `pcCertBoostedBlock = <attacker-chosen block point>`. No valid aggregate BLS signature is required.
3. Send the certificate. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The certificate is stored in the `PerasCertDB` / `ChainDB`.
5. Chain selection now applies the boost weight to the attacker-chosen block, causing the node to prefer it over the canonical chain tip. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
