### Title
Caller-Supplied `gas_fee` in `request_refund` Is Unbounded, Enabling Near-Total Loss of User Deposit Funds - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `request_refund` flow accepts a caller-supplied `gas_fee: Option<u128>` parameter that is stored verbatim in the `RefundRequest` and later used to compute the amount returned to the depositor (`refund_amount = deposit_amount - gas_fee`). The only validation applied is `resolved_gas_fee < amount`. There is no upper-bound check against `config.max_btc_gas_fee`, which is enforced on every other gas-fee path in the bridge. Because `request_refund` is a publicly reachable entry point and the deposit transaction is visible on-chain, any unprivileged actor can front-run the legitimate user and submit a refund request with `gas_fee = amount - 1`, causing the MPC-signed refund transaction to pay `amount - 1` satoshis as a Bitcoin miner fee and deliver only 1 satoshi to the user.

### Finding Description

In `request_refund_callback` the resolved gas fee is stored without any ceiling check:

```rust
// contracts/satoshi-bridge/src/refund.rs  (lines 549-553)
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

The stored value is later used directly to compute the refund amount in `refund_execution_inputs`:

```rust
// contracts/satoshi-bridge/src/refund.rs  (lines 280-284)
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
```

The only guard is `refund_amount > 0`, so a `gas_fee` of `amount - 1` passes every check and produces a 1-satoshi refund output while the remaining `amount - 1` satoshis become the Bitcoin miner fee in the MPC-signed transaction.

Contrast this with the withdrawal PSBT validation path, which enforces a strict two-sided bound:

```rust
// contracts/satoshi-bridge/src/psbt.rs  (lines 252-258)
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!(
        "Invalid gas fee ({}). valid range: [{}, {}].",
        gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
```

The refund path has no equivalent upper-bound enforcement.

The `gas_fee` value is not part of the `deposit_msg` that is embedded in the Bitcoin transaction (and thus cryptographically committed to by the depositor). It is a free parameter supplied by whoever calls `request_refund`. Because the deposit transaction is publicly visible on Bitcoin and the `deposit_msg` can be reconstructed from it, any NEAR account can call `request_refund` for any pending deposit before the legitimate user does.

### Impact Explanation

A malicious actor who front-runs the user's `request_refund` call with `gas_fee = deposit_amount - 1` causes the bridge's MPC to sign and broadcast a Bitcoin transaction that:
- Pays 1 satoshi to the user's refund address
- Pays `deposit_amount - 1` satoshis as the miner fee

The user loses essentially their entire deposit. This constitutes a significant, permanent loss of user funds with no recovery path once the Bitcoin transaction confirms.

### Likelihood Explanation

- `request_refund` is a public bridge entry point with no role restriction visible in `internal_request_refund`.
- The deposit transaction is publicly visible on the Bitcoin blockchain; the `deposit_msg` is derivable from it.
- The attack requires no special privilege, no leaked key, and no operator collusion.
- The DAO can reject suspicious refund requests via `internal_reject_refund`, but when `deposit_msg.refund_address` is pre-set the timelock is only `refund_timelock_sec` (default 2 days), giving a narrow window for detection and response.
- The attacker does not need to profit directly; the goal is destruction of user funds (or collusion with a miner to capture the inflated fee).

### Recommendation

Apply the same gas-fee bounds used in the withdrawal PSBT path to the refund path. In `request_refund_callback`, after resolving `resolved_gas_fee`, add:

```rust
let config = self.internal_config();
require!(
    resolved_gas_fee >= config.min_btc_gas_fee && resolved_gas_fee <= config.max_btc_gas_fee,
    format!(
        "Refund gas fee ({}) out of valid range [{}, {}]",
        resolved_gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
```

This mirrors the existing enforcement in `check_withdraw_psbt` and `check_psbt_output_all_change_address` and closes the discrepancy.

### Proof of Concept

1. User deposits 1,000,000 satoshis to a bridge address derived from a `deposit_msg` that includes `refund_address: Some("bc1q…user…")`.
2. The deposit is never finalized (relayer is offline).
3. Attacker observes the deposit on Bitcoin, reconstructs `deposit_msg` and `tx_bytes`.
4. Attacker calls `request_refund(deposit_msg, "bc1q…user…", tx_bytes, vout, proof, Some(999_999))`.
5. `request_refund_callback` resolves `resolved_gas_fee = 999_999`. Check: `999_999 < 1_000_000` → passes. `RefundRequest { gas_fee: 999_999, amount: 1_000_000, … }` is stored.
6. After 2-day timelock, `execute_refund` is called. `refund_execution_inputs` computes `refund_amount = 1_000_000 - 999_999 = 1`. Check: `1 > 0` → passes.
7. A PSBT is built: 1 input (1,000,000 sat), 1 output (1 sat to user). Miner fee = 999,999 sat.
8. MPC signs the transaction; it is broadcast to Bitcoin.
9. User receives 1 satoshi. 999,999 satoshis are destroyed as miner fees. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
