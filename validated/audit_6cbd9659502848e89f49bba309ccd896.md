### Title
`initTransfer1155()` Locks ERC1155 Tokens Without Validating `multiTokens` Mapping, Causing Permanent Fund Loss - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary

`OmniBridge.sol` supports ERC1155 token bridging via two separate functions: `logMetadata1155()` (which registers the token by setting `multiTokens[deterministicToken]` and emitting `LogMetadata` for NEAR-side registration) and `initTransfer1155()` (which locks tokens and emits `InitTransfer`). However, `initTransfer1155()` does not validate that `logMetadata1155()` has been called first. A user who calls `initTransfer1155()` without the prior `logMetadata1155()` call permanently locks their ERC1155 tokens with no recovery path.

### Finding Description

`initTransfer1155()` computes the `deterministicToken` address, locks the ERC1155 tokens via `safeTransferFrom`, and emits `InitTransfer` — but never checks or sets `multiTokens[deterministicToken]`: [1](#0-0) 

The `multiTokens[deterministicToken]` mapping is exclusively set by `logMetadata1155()`: [2](#0-1) 

`finTransfer()` — the only function that can release locked ERC1155 tokens — branches on `multiToken.tokenAddress != address(0)`. If the mapping is absent, it falls through to the ERC20 branch and calls `IERC20(deterministicToken).safeTransfer(...)`, which reverts because `deterministicToken` is a hash-derived pseudo-address, not a real ERC20 contract: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` requires the token to be registered in `token_decimals` (populated by the `LogMetadata` event from `logMetadata1155()`). Without that registration, the NEAR-side call panics with `TokenDecimalsNotFound`, meaning no wrapped tokens are ever minted and no return transfer is ever initiated: [4](#0-3) 

The existing test suite confirms this gap: the "validates ERC1155 receiver hooks" test calls `initTransfer1155()` directly without `logMetadata1155()` and observes that tokens are locked — but does not verify recoverability: [5](#0-4) 

### Impact Explanation

ERC1155 tokens sent via `initTransfer1155()` without a prior `logMetadata1155()` call are permanently frozen in the bridge contract. The NEAR side cannot process the inbound transfer (token not registered), so no wrapped tokens are minted and no return leg is ever created. `finTransfer()` cannot release the locked tokens because `multiTokens[deterministicToken]` is unset, causing it to attempt an ERC20 transfer on a non-existent contract and revert. There is no admin rescue path or refund mechanism. This constitutes permanent, irrecoverable loss of bridged funds.

### Likelihood Explanation

`initTransfer1155()` is a public, permissionless function. The correct two-step flow (`logMetadata1155` → `initTransfer1155`) is not enforced at the contract level. Any user who calls `initTransfer1155()` directly — a natural action given the function name — without knowing to call `logMetadata1155()` first will permanently lose their tokens. The SECURITY.md confirms the bridge is "fully permissionless," meaning no gating prevents this call sequence.

### Recommendation

Add a guard in `initTransfer1155()` that requires the `multiTokens[deterministicToken]` mapping to already be populated before accepting the token lock:

```solidity
function initTransfer1155(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    ...
    address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);

    // Require logMetadata1155 to have been called first
    if (multiTokens[deterministicToken].tokenAddress == address(0)) {
        revert ERC1155NotRegistered();
    }

    IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
    ...
}
```

Alternatively, `initTransfer1155()` can atomically call the registration logic itself (setting `multiTokens` and emitting `LogMetadata`) if the mapping is not yet set, mirroring the idempotent behavior of `logMetadata1155()`.

### Proof of Concept

1. Deploy `OmniBridge` and an ERC1155 token. Do **not** call `logMetadata1155()`.
2. Approve the bridge and call `initTransfer1155(erc1155, tokenId, amount, 0, 0, "victim.near", "")`.
3. Observe: ERC1155 tokens are transferred to the bridge (`erc1155.balanceOf(bridge, tokenId) == amount`).
4. Observe: `multiTokens[deterministicToken].tokenAddress == address(0)` — mapping is unset.
5. NEAR-side `fin_transfer` panics with `TokenDecimalsNotFound` — no wrapped tokens minted.
6. Attempt `finTransfer()` with `payload.tokenAddress = deterministicToken` — reverts at `IERC20(deterministicToken).safeTransfer(...)` because `deterministicToken` is not an ERC20.
7. Tokens are permanently locked with no recovery path.

        }
