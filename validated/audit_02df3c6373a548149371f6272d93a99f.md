Audit Report

## Title
Re-entrancy in `initTransfer1155` Causes `originNonce` Collision and Permanent Freezing of Bridged Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` at the top of the function but reads `currentOriginNonce` again — from storage — after the external `IERC1155.safeTransferFrom` call when passing it to `initTransferExtension` and `emit InitTransfer`. A malicious ERC-1155 token can re-enter `initTransfer1155` inside its own `safeTransferFrom` body, advance `currentOriginNonce` a second time, and cause the outer call to emit `InitTransfer` with the same `originNonce` as the inner call. The NEAR side processes the first event and permanently ignores the second, locking the outer call's tokens in the EVM bridge with no recovery path.

## Finding Description

In `initTransfer1155` (lines 448–489 of `OmniBridge.sol`):

```
currentOriginNonce += 1;                          // (1) storage write: nonce = N
...
IERC1155(tokenAddress).safeTransferFrom(          // (2) external call to untrusted token
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...)  // (3) re-reads storage: may be N+1
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)  // (4) re-reads storage: may be N+1
``` [1](#0-0) 

The nonce is snapshotted into storage at step (1) but never captured into a local variable. Steps (3) and (4) re-read `currentOriginNonce` from storage after the external call at step (2), which is the re-entrancy window.

**Why the `onERC1155Received` guard does not block this:**

The guard at lines 522–534 checks `operator != address(this)` and reverts if the operator is not the bridge itself. [2](#0-1) 

However, this callback is invoked by the token contract *after* the transfer logic completes. A malicious token's `safeTransferFrom` can re-enter `initTransfer1155` *before* calling `onERC1155Received`. The re-entrant (inner) call then invokes `safeTransferFrom` on the malicious token a second time; on this second call the token transfers normally and calls `onERC1155Received` with `operator == address(this)` (the bridge is the caller of `safeTransferFrom`), so the guard passes. Control then unwinds back to the outer call, which reads the already-advanced `currentOriginNonce`.

**Exact state trace:**

```
currentOriginNonce = 5 (before attack)

Outer: initTransfer1155(MaliciousERC1155, ...)
  (1) currentOriginNonce = 6
  (2) MaliciousERC1155.safeTransferFrom → re-enters initTransfer1155
        Inner: initTransfer1155(MaliciousERC1155, ...)
          (1) currentOriginNonce = 7
          (2) MaliciousERC1155.safeTransferFrom → transfers normally
              → onERC1155Received(operator=bridge) ✓ passes
          (3) initTransferExtension(..., nonce=7)
          (4) emit InitTransfer(originNonce=7)   ← INNER
        returns
      → onERC1155Received(operator=bridge) ✓ passes
  (3) initTransferExtension(..., currentOriginNonce=7)  ← reads 7, not 6
  (4) emit InitTransfer(originNonce=7)   ← OUTER, DUPLICATE

Result: nonce 6 never emitted; nonce 7 emitted twice
```

The same structural flaw exists in `initTransfer` for ERC-777 tokens (lines 407–412 and 418/430), where the `tokensToSend` hook on `msg.sender` provides the re-entry point. [3](#0-2) 

This directly violates the documented invariant in `evm/CLAUDE.md`:

> "State before external calls: Always mutate state … before any external call … This is the primary reentrancy defense." [4](#0-3) 

## Impact Explanation

The NEAR contract reconstructs each transfer using `origin_nonce` from the parsed EVM event as a unique identifier. Two `InitTransfer` events with identical `originNonce` are indistinguishable to the NEAR prover: it processes the first and permanently ignores the second. The outer call's tokens are locked inside the EVM bridge contract. There is no admin-recovery function and no mechanism to re-submit the proof. This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation

The attack requires no privileged access:
1. Deploy a malicious ERC-1155 token (permissionless).
2. Call the permissionless `logMetadata1155` to register it with the bridge.
3. Call `initTransfer1155` with the malicious token.

No admin keys, MPC compromise, front-running, or external dependency failure are required. Any unprivileged user can execute this on-chain, and the attack is repeatable.

## Recommendation

Capture `currentOriginNonce` into a local variable immediately after incrementing, before any external call, and use only that local variable in `initTransferExtension` and `emit`:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // snapshot before external calls

IERC1155(tokenAddress).safeTransferFrom(...);

initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Apply the same fix to `initTransfer`. Alternatively, add OpenZeppelin's `ReentrancyGuard` (`nonReentrant` modifier) to both functions. Both mitigations should be applied together for defense in depth.

## Proof of Concept

Deploy `MaliciousERC1155` whose `safeTransferFrom` implementation:
- On the first invocation (outer call): re-enters `initTransfer1155` with the same parameters, then on return calls `onERC1155Received(operator=address(bridge))` to satisfy the guard.
- On the second invocation (inner call): transfers tokens normally and calls `onERC1155Received(operator=address(bridge))`.

**Invariant test (Foundry):**

```solidity
function testReentrancyNonceCollision() public {
    MaliciousERC1155 mal = new MaliciousERC1155(bridge);
    bridge.logMetadata1155(address(mal), 1);

    uint64 nonceBefore = bridge.currentOriginNonce();
    mal.attack(); // calls initTransfer1155, re-enters once

    // Invariant: every emitted originNonce must be unique
    // Assert: two InitTransfer events were emitted with the same originNonce
    // Assert: nonceBefore+1 was never emitted (gap)
    // Assert: nonceBefore+2 was emitted twice
}
```

The test confirms that `currentOriginNonce` advances to `nonceBefore+2` while only `nonceBefore+1` was consumed by the outer call's token transfer, and both events carry `originNonce = nonceBefore+2`.
