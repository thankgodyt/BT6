### Title
`initTransfer` Uses Caller-Supplied `amount` Instead of Actual Balance Increase, Enabling Escrow Mis-Accounting - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.initTransfer` performs a `safeTransferFrom` to pull ERC20 tokens from the caller but then emits the `InitTransfer` event (and publishes the Wormhole cross-chain message) using the caller-supplied `amount` parameter rather than the actual balance increase received by the contract. For fee-on-transfer ERC20 tokens, the bridge records and relays a larger amount than it actually holds, permanently undercollateralizing the escrow and enabling loss of funds for later withdrawers.

---

### Finding Description

In `initTransfer`, when the token is a plain ERC20 (not a bridge token or custom minter), the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // ← caller-controlled parameter
);
``` [1](#0-0) 

Immediately after, without re-reading the contract's actual balance, the function emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,          // ← same caller-controlled parameter, not actual received amount
    fee,
    nativeFee,
    recipient,
    message
);
``` [2](#0-1) 

The same unchecked `amount` is forwarded to `initTransferExtension`, which in the `OmniBridgeWormhole` subclass publishes it verbatim into the Wormhole VAA payload:

```solidity
Borsh.encodeUint128(amount),   // ← inflated amount in cross-chain message
``` [3](#0-2) 

The NEAR `omni-bridge` contract reads this event/VAA to determine how many tokens to mint or release on the destination chain. Because the recorded amount exceeds what the EVM bridge actually holds, the escrow is undercollateralized by exactly the fee deducted by the token on every such transfer.

---

### Impact Explanation

Every `initTransfer` call with a fee-on-transfer ERC20 token causes the bridge to:
1. Receive `amount - transfer_fee` tokens into its escrow.
2. Record and relay `amount` tokens to the destination chain.
3. Mint or release `amount` tokens to the recipient on NEAR (or another chain).

The deficit accumulates with each transfer. Eventually the bridge's EVM-side token balance is insufficient to honor all outstanding withdrawal claims, causing the last withdrawers to lose funds. This is a direct, permanent loss of bridged funds — matching the **Critical: balance manipulation / escrow mis-accounting** impact class.

---

### Likelihood Explanation

Any unprivileged user can call `initTransfer` with any ERC20 token address that the bridge accepts as a plain (non-bridge, non-custom-minter) token. Fee-on-transfer tokens exist on mainnet (e.g., tokens with reflection mechanics, tokens with protocol fees). The bridge has no whitelist preventing such tokens from being used in the plain ERC20 path (lines 406–412). The attacker needs only to hold such a token and call the public `initTransfer` function. [4](#0-3) 

---

### Recommendation

Measure the actual balance increase after the transfer and use that value for the event and cross-chain message:

```solidity
} else {
    uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
    uint128 actualReceived = uint128(
        IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore
    );
    require(fee < actualReceived, "InvalidFee");
    amount = actualReceived;   // shadow with actual received amount
}
```

All downstream uses of `amount` (the extension call and the event emission) will then reflect the true escrowed quantity.

---

### Proof of Concept

1. Deploy or use any ERC20 token that deducts a 1% fee on every transfer (fee-on-transfer token).
2. Call `OmniBridge.initTransfer(tokenAddress, 1000, 0, 0, "recipient.near", "")`.
3. The bridge receives 990 tokens (1% fee deducted by the token contract).
4. The `InitTransfer` event is emitted with `amount = 1000`.
5. The Wormhole VAA (via `OmniBridgeWormhole.initTransferExtension`) encodes `amount = 1000`.
6. The NEAR bridge finalizes the transfer and releases 1000 tokens to the recipient.
7. The EVM bridge escrow is now short by 10 tokens.
8. Repeat N times; the bridge becomes insolvent by `N × 10` tokens, and the last N users to withdraw on the EVM side cannot reclaim their funds. [5](#0-4) [6](#0-5)
