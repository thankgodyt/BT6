### Title
Chain Selection Ignores Peras Weight Storage in `checkPreferTheirsOverOurs`, Causing Incorrect Peer Disconnection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` (zero weights) when calling `preferAnchoredCandidate`, ignoring the actual Peras certificate weights stored in the separate `PerasCertDB`. This is structurally identical to the reported bug: a local field that is always zero when an alternative storage is active is used directly, without consulting that alternative storage. When Peras is active and certificates exist, the function can incorrectly conclude a peer's chain is not preferred and disconnect from it, causing the node to fail to adopt the canonical (heavier) chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked when a header from a peer is beyond the forecast horizon. Its purpose is to disconnect from peers whose chain is definitively not preferred — to avoid waiting indefinitely for a forecast that will never arrive. It calls `preferAnchoredCandidate` to compare the peer's fragment against ours:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero, ignores PerasCertDB
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

The `preferAnchoredCandidate` function branches on whether the weight snapshot is empty. When it is empty (as hardcoded here), it falls back to a pure block-number comparison. When it is non-empty, it uses the full Peras-weighted suffix comparison:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-number-only comparison
      ...
  | otherwise =
      -- weighted suffix comparison using PerasCertDB weights
      ...
``` [2](#0-1) 

The actual Peras weights are stored in `PerasCertDB`, a separate storage component. The `ChainDB` API exposes `getPerasWeightSnapshot` which reads from `PerasCertDB`:

```haskell
getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
-- ^ Get the 'PerasWeightSnapshot', representing the Peras weight boosts for
-- all blocks newer than the current immutable tip.
``` [3](#0-2) 

`getPerasWeightSnapshot` is implemented by delegating to `PerasCertDB.getWeightSnapshot`: [4](#0-3) 

The `PerasCertDB` computes the weight snapshot from all stored certificates: [5](#0-4) 

The CHANGELOG confirms that chain selection was updated to use `PerasCertDB` weights, but `checkPreferTheirsOverOurs` was not updated accordingly:

> "Make the `ChainDB` aware of the `PerasCertDB`, and modify the chain selection function accordingly. In practice, it means that the candidate fragment is now selected based on its Peras weight, instead of its length." [6](#0-5) 

The structural analog to the reported bug is exact:

| Reported Bug | This Finding |
|---|---|
| `pool.amount` (always 0 when shared_escrow active) | `emptyPerasWeightSnapshot` (always 0, ignores PerasCertDB) |
| `shared_escrow` account (alternative storage) | `PerasCertDB` (alternative storage for Peras weights) |
| Incorrect pool closure | Incorrect peer disconnection / failure to adopt canonical chain |

---

### Impact Explanation

When Peras is active and certificates have been received, a peer may serve a chain that is heavier by Peras weight but not strictly longer by block count. `checkPreferTheirsOverOurs` evaluates this chain using only block count (because `emptyPerasWeightSnapshot` forces the block-number-only path in `preferAnchoredCandidate`). It concludes the peer's chain is not preferred and throws `CandidateTooSparse`, disconnecting from the peer.

The node then fails to adopt the canonical chain (the one with greater Peras weight). The node remains on a less-preferred chain, diverging from the canonical selection. This is a **High** chain selection bug: an honest node is made to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

This requires Peras to be active (it is under active development and planned for deployment per the CHANGELOG). Once Peras is active, the scenario arises naturally whenever: (1) Peras certificates have been issued for blocks on a peer's chain, (2) the peer's chain is heavier by Peras weight but not longer by block count, and (3) the peer's headers exceed the forecast horizon. Condition (3) is a normal operational scenario documented in the code. No adversarial action is required — an honest peer serving the canonical chain triggers the bug.

---

### Recommendation

`checkPreferTheirsOverOurs` must read the actual `PerasWeightSnapshot` from `PerasCertDB` (via `getPerasWeightSnapshot` on the `ChainDB` API) and pass it to `preferAnchoredCandidate` instead of `emptyPerasWeightSnapshot`. The `ChainDB` API already exposes this in STM, making it composable with the existing `atomically` call in `readLedgerStateHelper`. The existing TODO comment (`https://github.com/tweag/cardano-peras/issues/64`) acknowledges the check is problematic; the fix is to use the real weights rather than remove the check entirely.

---

### Proof of Concept

1. Peras is active; a certificate is issued boosting block `B` on a peer's chain.
2. The peer's chain has the same block count as ours but greater Peras weight (due to the certificate for `B`).
3. The peer sends a header beyond the local forecast horizon.
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` uses block-number-only comparison → returns `ShouldNotSwitch` (equal block count).
6. `shouldSwitch` returns `False` → `throwSTM CandidateTooSparse` fires.
7. The node disconnects from the peer serving the canonical (heavier) chain.
8. The node remains on the lighter chain, diverging from the canonical selection. [7](#0-6) [8](#0-7)

        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o

            (projectChainOrderConfig cfg)
