Audit Report

## Title
Non-Atomic `burn.and(mint)` in `swap_migrated_token` Causes Permanent Token Loss on Mint Failure — (File: near/omni-bridge/src/lib.rs)

## Summary
`swap_migrated_token` schedules a burn of the old token and a mint of the new token as two parallel, independent NEAR promises via `Promise::and()`. The resulting joint promise is `.detach()`ed in `ft_on_transfer`, so any mint failure is silently discarded. If the recipient is not registered (no storage deposit) in the new token contract, `internal_deposit` panics, the mint promise fails, but the burn has already executed and is irreversible — the user permanently loses their tokens.

## Finding Description

**`ft_on_transfer` (near/omni-bridge/src/lib.rs:275-279):**
The `SwapMigratedToken` branch calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)`, meaning the bridge retains the old tokens and no refund is issued regardless of what happens to the joint promise. [1](#0-0) 

**`swap_migrated_token` (near/omni-bridge/src/lib.rs:2749-2752):**
Both the `burn` and `mint` cross-contract calls are composed with `Promise::and()`, which schedules them in parallel. Neither sub-promise depends on the other's outcome; there is no rollback if one fails. [2](#0-1) 

**`mint` in omni-token (near/omni-token/src/lib.rs:140-142):**
When `msg` is `None`, `mint` calls `self.token.internal_deposit(&account_id, amount.into())` directly. The NEAR SDK's `FungibleToken::internal_deposit` panics if `account_id` has no storage registration, causing the mint promise to fail. [3](#0-2) 

**`migrate_deployed_token` (near/omni-bridge/src/lib.rs:1651-1655):**
Only the bridge contract itself is registered in the new token via `storage_deposit`. No user registration is performed, and no guard in `swap_migrated_token` or `ft_on_transfer` checks whether `sender_id` is registered in the new token before issuing the burn. [4](#0-3) 

**`burn` in omni-token (near/omni-token/src/lib.rs:146-150):**
`burn` calls `internal_withdraw` from the bridge's balance in the old token. Since the bridge holds the tokens (returned `U128(0)` in `ft_on_transfer`), this succeeds unconditionally and is irreversible. [5](#0-4) 

Execution sequence:
1. User calls `old_token.ft_transfer_call(bridge, amount, "SwapMigratedToken")`.
2. NEP-141 transfers `amount` from user to bridge; `ft_on_transfer` is invoked.
3. Bridge returns `U128(0)` → bridge permanently holds old tokens.
4. `burn(old_token, amount)` executes → bridge's old-token balance is destroyed. Irreversible.
5. `mint(new_token, sender_id, amount, None)` executes → `internal_deposit` panics (sender not registered) → promise fails.
6. `.detach()` means the failure is never observed by the bridge.
7. User has lost `amount` of old tokens and received 0 new tokens. Permanent loss.

## Impact Explanation
This is a concrete, permanent loss of bridged funds on NEAR during a legitimate, production-facing migration flow. Old tokens are burned from the bridge's balance (irreversible), and new tokens are never minted to the user. The user's funds are permanently destroyed with no recovery path. This matches the critical impact class: "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR."

## Likelihood Explanation
The migration flow is DAO-callable (`migrate_deployed_token`) and user-callable (`ft_transfer_call` with `SwapMigratedToken`). NEP-141 storage registration is a separate, non-obvious prerequisite that many users will not know to perform before swapping. There is no on-chain guard, pre-check, or documentation enforcing registration before the swap. The loss is triggered accidentally (not only by a malicious actor), making it a high-likelihood event during any real migration. Any user who calls `swap_migrated_token` without first calling `storage_deposit` on the new token loses their entire transferred amount.

## Recommendation
Replace the parallel `burn.and(mint)` with a sequential, callback-guarded pattern:
1. Call `mint(new_token, sender_id, amount, None)` first.
2. In the callback, check success: if mint succeeded, call `burn(old_token, amount)`; if mint failed, refund the old tokens to `sender_id` via `ft_transfer`.

Alternatively, before issuing any promises, verify that `sender_id` is registered in the new token via a `storage_balance_of` view call (using a cross-contract call with a callback), and abort (causing `ft_resolve_transfer` to refund the full amount) if not registered.

The `.detach()` on the joint promise must be replaced with a proper callback that handles partial failure.

## Proof of Concept
```
# Localnet test (no mainnet interaction)
1. Deploy old_token (omni-token), new_token (omni-token), bridge.
2. DAO calls bridge.migrate_deployed_token(chain, old_token, new_token).
3. Register sender in old_token; mint 1000 old tokens to sender.
4. Do NOT call new_token.storage_deposit for sender.
5. sender calls old_token.ft_transfer_call(bridge, 1000, "SwapMigratedToken").
6. Assert: sender's old_token balance = 0 (burned from bridge's balance).
7. Assert: sender's new_token balance = 0 (mint panicked, promise failed).
8. Assert: bridge's old_token balance = 0 (burned).
9. Net result: 1000 tokens permanently destroyed.
```
