### Title
Whitelisted Upgradeable (Proxy) Post-Action Receiver Can Steal User nBTC After Upgrade — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

The `post_action_receiver_id_white_list` in the satoshi-bridge accepts any NEAR `AccountId` without verifying whether the target contract is upgradeable (a proxy). If a previously-safe whitelisted contract is later upgraded to a malicious implementation, it can steal freshly minted nBTC from any user who specifies a `PostAction` targeting it during a BTC deposit.

---

### Finding Description

The bridge allows depositors to embed `post_actions` in their `DepositMsg`. Each `PostAction` specifies a `receiver_id` that must appear in `post_action_receiver_id_white_list`. After a successful deposit proof, the nBTC contract executes each post action by transferring nBTC from the deposit recipient to the whitelisted receiver and calling `ft_on_transfer` on it.

**Step 1 — Whitelist admission with no proxy guard.**

`extend_post_action_receiver_id_white_list` (DAO-gated) inserts any `AccountId` into the set with no check for whether the target contract is upgradeable: [1](#0-0) 

**Step 2 — Deposit validation only checks set membership.**

`check_deposit_msg` enforces that `receiver_id` is in the whitelist, but performs no structural check on the target contract: [2](#0-1) 

**Step 3 — nBTC is transferred and `ft_on_transfer` is called on the whitelisted receiver, fire-and-forget.**

`handle_post_action` in the nBTC contract does `internal_transfer` then calls `ft_on_transfer` on the receiver, with the entire chain `.detach()`-ed — meaning the deposit is already finalized and no rollback is possible: [3](#0-2) 

The `ft_resolve_transfer` callback only refunds unused tokens if the receiver returns a non-zero value. A malicious upgraded contract simply returns `0` from `ft_on_transfer`, claiming it consumed all tokens, and the nBTC is permanently transferred to it.

**Step 4 — `handle_post_actions` detaches every post action.** [4](#0-3) 

Because each call is `.detach()`-ed, a malicious receiver's behavior cannot revert the deposit or trigger any bridge-level recovery.

---

### Impact Explanation

A whitelisted proxy contract that is upgraded to a malicious implementation can steal 100% of the nBTC allocated to it in any user's `PostAction`. The deposit is already finalized on-chain before the post-action executes, so there is no rollback path. This constitutes **direct theft of user funds** (Critical impact: significant loss of user funds).

---

### Likelihood Explanation

**Low-to-Medium.** The DAO must first whitelist a contract that is later upgraded maliciously. This is realistic: DeFi protocols that are legitimate at whitelist time can be compromised, rug-pulled, or have their upgrade keys stolen. The bridge has no on-chain mechanism to detect or prevent this. Users who embed `post_actions` in their deposits (a supported and documented feature) are exposed without any warning.

---

### Recommendation

1. **Do not whitelist upgradeable (proxy) contracts** in `post_action_receiver_id_white_list`. Add an explicit code comment and/or a DAO-process requirement to verify that any candidate contract is non-upgradeable before calling `extend_post_action_receiver_id_white_list`.
2. Consider adding an on-chain check (e.g., querying the target contract's code hash at whitelist time and storing it, then re-verifying at execution time) to detect if the whitelisted contract has been upgraded since admission.
3. Document this risk prominently in the whitelist management functions.

---

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["malicious-proxy.near"])` — at this point the contract is benign.
2. The contract owner upgrades `malicious-proxy.near` to a malicious implementation whose `ft_on_transfer` always returns `"0"` (claims all tokens used) and immediately re-transfers them to the attacker.
3. Alice deposits 1 BTC with `DepositMsg { recipient_id: "alice.near", post_actions: [{ receiver_id: "malicious-proxy.near", amount: 100_000_000, ... }] }`.
4. `verify_deposit_v2` succeeds; nBTC is minted; `handle_post_actions` fires.
5. `handle_post_action` calls `internal_transfer("alice.near" → "malicious-proxy.near", 100_000_000)` then `ft_on_transfer(...)`.
6. The malicious contract drains the tokens and returns `"0"`.
7. `ft_resolve_transfer` sees `0` unused tokens — no refund. Alice's nBTC is stolen. [2](#0-1) [5](#0-4)

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();
