### Title
Missing `refund_address` Format Validation Allows Attacker to Permanently Brick a User's Refund Request — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

`internal_request_refund` / `request_refund_callback` store a caller-supplied `refund_address` string into `RefundRequest` without validating it as a well-formed Bitcoin/Zcash address. Because only one refund request can exist per UTXO, an attacker who front-runs with an invalid address permanently blocks the legitimate user's refund. When `execute_refund` is later called, `build_refund_output` panics on the invalid address, leaving the request stuck and requiring DAO intervention to reject it.

### Finding Description

`internal_request_refund` accepts a free-form `refund_address: String` from any caller. The only check performed is a string-equality comparison against `deposit_msg.refund_address` when that optional field is `Some`; no Bitcoin/Zcash address format validation is performed in either `internal_request_refund` or the downstream `request_refund_callback`. [1](#0-0) 

`request_refund_callback` then stores the unvalidated string verbatim into `RefundRequest.refund_address`: [2](#0-1) 

A duplicate-request guard prevents any second refund request for the same UTXO: [3](#0-2) 

When `execute_refund` is later called, `build_refund_output` attempts to parse the stored address and panics unconditionally on failure: [4](#0-3) 

Because `RefundRequest` is immutable once inserted, the panic cannot be avoided without DAO intervention.

### Impact Explanation

A user who deposited BTC with `deposit_msg.refund_address = None` (no pre-authorized refund address) and whose deposit was never finalized on NEAR is entitled to a refund. An attacker who submits `request_refund` first with a syntactically invalid address (e.g., `"not_an_address"`) occupies the single refund-request slot for that UTXO. Every subsequent call to `execute_refund` panics. The legitimate user cannot open a replacement request. The UTXO and the user's BTC remain locked until a DAO/RefundOperator calls `internal_reject_refund` to clear the poisoned entry.

This matches the Medium impact: **attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**.

### Likelihood Explanation

- The attack requires no special role; any NEAR account can call `request_refund` and pay the small storage deposit.
- Deposits with `deposit_msg.refund_address = None` are the common case (users who do not pre-specify a refund address).
- Front-running on NEAR is straightforward: the attacker monitors the mempool or the light-client proof submission and races to call `request_refund` first.
- Cost to the attacker is only the storage deposit (a few NEAR), which is refunded on rejection.

### Recommendation

Validate `refund_address` as a well-formed address for the configured chain before storing it. Add a call to `config.string_to_script_pubkey(&refund_address)` (which already exists and panics on invalid input) inside `internal_request_refund`, before the light-client cross-contract call is dispatched. This ensures an invalid address is rejected immediately with a clean error rather than being persisted and causing a later panic in `execute_refund`. [5](#0-4) 

### Proof of Concept

1. User A sends BTC to a deposit address derived from `DepositMsg { recipient_id: "user_a.near", refund_address: None, ... }`. The deposit is never finalized on NEAR (relayer is slow or the proof is not submitted).
2. Attacker calls `request_refund(deposit_msg=<same DepositMsg>, refund_address="INVALID", tx_bytes=<valid tx>, vout=0, proof=<valid proof>, gas_fee=None)` with sufficient attached NEAR.
3. Light-client verification succeeds (the BTC transaction is real). `request_refund_callback` stores `RefundRequest { refund_address: "INVALID", ... }` for the UTXO key.
4. User A attempts `request_refund(...)` with a valid address → rejected: `"Refund request already exists for this UTXO"`.
5. Anyone calls `execute_refund(utxo_storage_key)` → `build_refund_output` calls `Address::parse("INVALID", chain).expect("Invalid refund address")` → **panic**, transaction reverts.
6. User A's BTC is locked until a DAO account calls `reject_refund(utxo_storage_key)`. [3](#0-2) [6](#0-5)

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
