### Title
`validatePerasCert` Unconditionally Returns `Right` Without Cryptographic Verification, Allowing Any Peer to Inject Arbitrary Peras Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that always returns `Right` — accepting every certificate unconditionally. Because the Peras certificate diffusion mini-protocol is wired directly to this stub validator in the production node-to-node handler, any unprivileged peer can inject a crafted `PerasCert` for any round and any block. The receiving node accepts it as cryptographically valid, stores it in `PerasCertDB`, and applies its chain-selection boost weight, potentially causing the node to prefer a non-canonical chain.

### Finding Description

**Root cause — stub validator always succeeds:**

In `SupportsPeras.hs`, the universal `instance StandardHash blk => BlockSupportsPeras blk` implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the only `BlockSupportsPeras` instance in the codebase (it is the universal instance for all `StandardHash blk`). It performs zero cryptographic checks — no aggregate BLS signature verification, no VRF proof verification, no committee membership check.

**Production wiring — the stub is the live validator:**

`makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` passes this stub as the `validateCert` argument to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is wired into the production `hPerasCertDiffusionClient` handler in `NodeToNode.hs`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

**The gate that never closes — `processCerts`:**

`processCerts` calls `validateCert` on each inbound certificate. If all pass, they are timestamped and added to the DB. Since `validatePerasCert` always returns `Right`, every peer-submitted certificate passes:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [4](#0-3) 

**Chain selection consequence:**

Once accepted, the certificate is added via `addPerasCertAsync`, which enqueues it for chain selection. The `PerasCertDB` weight snapshot is then used by chain selection to boost the block named in the certificate: [5](#0-4) 

**Analog to the reported vulnerability:**

The external report describes `AmpleEarnRouter` calling `setMerkleRoots()` directly, bypassing the `_msgSenderOnlyEVCAccountOwner()` authorization check. The analog here is structurally identical: `processCerts` calls `validatePerasCert` as the sole authorization gate before accepting a certificate as `ValidatedPerasCert`. Because `validatePerasCert` always returns `Right`, the gate is permanently open — any peer-submitted certificate is accepted as if it were cryptographically valid, exactly as any caller could set merkle roots through the unguarded router.

### Impact Explanation

**High.** An unprivileged peer can craft a `PerasCert` naming any block at any round and send it over the `PerasCertDiffusion` mini-protocol. The receiving node accepts it without any cryptographic check, stores it in `PerasCertDB`, and applies its boost weight to chain selection. This allows the attacker to make an honest node prefer a non-canonical or adversarially chosen chain, violating the chain-selection security assumptions of the Peras protocol. If multiple nodes are affected simultaneously, this can cause a consensus split.

### Likelihood Explanation

**High.** The `PerasCertDiffusion` mini-protocol is open to all connected peers. No special keys, stake, or privileges are required. The attack path is a single crafted message over an already-established peer connection. The stub validator is the only production implementation and is unconditionally active.

### Recommendation

1. Implement actual cryptographic validation in `validatePerasCert` — verifying the aggregate BLS signature, VRF proofs, and committee membership — before the `PerasCertDiffusion` mini-protocol is active on any production or testnet node.
2. Until real validation is in place, the `hPerasCertDiffusionClient` handler should reject all inbound certificates (e.g., by using a writer that always throws `PerasCertValidationError`), mirroring the existing behavior for votes where the empty stake distribution causes all votes to be rejected.
3. Track this under the existing issue referenced in the TODO comments (`cardano-peras/issues/120`) and gate the mini-protocol activation on completion of that work.

### Proof of Concept

1. Establish a peer connection to a target node running this codebase.
2. Negotiate the `PerasCertDiffusion` mini-protocol.
3. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of any block, including a non-canonical one>`.
4. The node's `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}`.
5. The certificate is added to `PerasCertDB` via `addPerasCertAsync` and chain selection is triggered.
6. The boosted block gains weight in `getWeightSnapshot`; if the boosted chain is heavier than the current selection, the node switches to it — even if it is non-canonical.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
