### Title
Permissionless `request_refund` with caller-supplied `refund_address` allows any attacker to redirect victim's BTC refund to attacker-controlled address - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`request_refund` accepts a caller-supplied `refund_address` without verifying that the caller is the intended deposit recipient. Because `deposit_msg` values are publicly broadcast via on-chain NEAR events, any attacker can race to submit `request_refund` for a victim's unverified deposit UTXO, substituting their own BTC address. The victim's subsequent `request_refund` call panics with "Refund request already exists for this UTXO", and after the timelock the attacker (or anyone) calls `execute_refund`, causing the bridge's MPC to sign a BTC transaction that sends the victim's funds to the attacker's address.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is a public, permissionless function. It accepts a `deposit_msg` (which identifies the deposit address) and a separate `refund_address` (where the BTC refund should be sent). The only constraint on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` — the common case for standard deposits — **any caller can supply any BTC address**. There is no check that the caller is the `recipient_id` embedded in `deposit_msg`.

The `deposit_msg` is not secret. Every time a user calls `get_user_deposit_address`, the contract emits a `LogDepositAddress` event containing the full `deposit_msg`:

```rust
Event::LogDepositAddress {
    deposit_msg,
    path,
    deposit_address: deposit_address.clone(),
}.emit();
``` [2](#0-1) 

An attacker monitoring NEAR events therefore learns every victim's `deposit_msg`. The attacker also monitors the Bitcoin chain for deposits to those addresses. When a deposit is unverified (minting failed or is delayed), the attacker calls `request_refund` first, supplying the victim's `deposit_msg` and the attacker's own BTC address.

In `request_refund_callback`, the contract verifies the UTXO belongs to the deposit address derived from `deposit_msg`, but never checks who the caller is:

```rust
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
``` [3](#0-2) 

The callback then stores the refund request with the attacker's BTC address:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker's BTC address
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [4](#0-3) 

When the victim subsequently calls `request_refund`, the callback panics:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [5](#0-4) 

The victim's attached NEAR deposit (anti-spam fee) is consumed and not returned.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is callable by anyone with no access control:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
``` [6](#0-5) 

`finalize_refund_with_psbt` then builds a PSBT paying `refund_request.refund_address` — the attacker's address — and submits it to the MPC for signing:

```rust
let refund_address = refund_request.refund_address.clone();
...
let refund_output = self.build_refund_output(&refund_address, refund_amount);
``` [7](#0-6) [8](#0-7) 

The MPC signs and the BTC is irreversibly sent to the attacker.

---

### Impact Explanation

**Critical.** The attacker receives the victim's BTC. The victim's deposit UTXO is spent by the bridge's MPC to the attacker's address. The victim has no recourse once `execute_refund` is called and the BTC transaction is broadcast. This constitutes unauthorized release of bridge-controlled BTC funds.

Secondary: the victim also loses the NEAR storage deposit attached to their failed `request_refund` call.

---

### Likelihood Explanation

**Medium-High.**

- `deposit_msg` values are fully public via on-chain NEAR events — no off-chain knowledge is required.
- The attacker only needs to submit `request_refund` before the victim, not before a relayer. The window is any time between the deposit appearing on Bitcoin and the victim calling `request_refund` — potentially hours or days.
- The attack requires no privileged role, no leaked key, and no special infrastructure beyond monitoring NEAR events and the Bitcoin chain.
- The `unsafe_refund_timelock_sec` gives DAO/Operator a window to reject, but the DAO/Operator must actively monitor all refund requests and identify malicious ones. A missed or delayed rejection results in permanent loss.
- The attacker's only cost is the NEAR storage deposit for `request_refund`, which is negligible relative to the BTC value at stake.

---

### Recommendation

1. **Bind `refund_address` to the deposit recipient.** In `request_refund_callback`, require that `env::predecessor_account_id()` equals `deposit_msg.recipient_id`, or require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the BTC destination is fixed at deposit time and cannot be overridden by a third party.

2. **Alternatively**, require a signature from `deposit_msg.recipient_id`'s NEAR key authorizing the specific `refund_address`, so only the legitimate owner can register a refund destination.

3. **Short-term mitigation**: emit an alert event whenever a `request_refund` caller differs from `deposit_msg.recipient_id`, and ensure the DAO/Operator has automated monitoring to reject such requests within the timelock window.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. NEAR emits `LogDepositAddress` with the full `deposit_msg`.
2. Alice sends 1 BTC to the derived deposit address.
3. The relayer's `verify_deposit` call fails (e.g., nBTC minting reverts). The UTXO is **not** added to `verified_deposit_utxo`.
4. Bob monitors NEAR events, sees Alice's `deposit_msg`, and sees the unverified BTC deposit on-chain.
5. Bob calls `request_refund(deposit_msg=alice_msg, refund_address="bob_btc_addr", tx_bytes=..., vout=0, proof=...)` with the required NEAR storage deposit attached.
6. `request_refund_callback` verifies the UTXO belongs to Alice's deposit address (it does), finds no existing refund request, and stores `RefundRequest { refund_address: "bob_btc_addr", ... }`.
7. Alice calls `request_refund` with her own BTC address. The callback panics: `"Refund request already exists for this UTXO"`. Alice loses her NEAR deposit.
8. After `unsafe_refund_timelock_sec` (assuming DAO/Operator does not reject), Bob calls `execute_refund("txid@0", None)`.
9. `finalize_refund_with_psbt` builds a PSBT paying 1 BTC (minus gas fee) to `"bob_btc_addr"` and submits to MPC.
10. MPC signs; the transaction is broadcast. Alice's 1 BTC is permanently transferred to Bob.
