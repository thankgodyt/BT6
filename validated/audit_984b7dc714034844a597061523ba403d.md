### Title
Insufficient Finality Level for Abstract (L2) and Starknet Chains Enables Double-Spend via Reorg - (File: `near/omni-prover/mpc-omni-prover/src/lib.rs`)

### Summary

`MpcOmniProver` is initialized with `EvmFinality::Latest` for `ChainKind::Abs` (Abstract, a ZKsync-based EVM L2) and `StarknetFinality::AcceptedOnL2` for `ChainKind::Strk`. Both finality levels represent pre-finalization states that are susceptible to sequencer-level reorganization. Because the bridge mints NEAR tokens upon proof acceptance, an attacker who can cause a source-chain reorg after proof submission can double-spend: recover their locked tokens on the source chain while retaining the minted NEAR tokens.

### Finding Description

In `MpcOmniProver::init()`, the hardcoded finality map is:

```rust
finalities.insert(ChainKind::Abs, MpcFinality::Evm(EvmFinality::Latest));
finalities.insert(
    ChainKind::Strk,
    MpcFinality::Starknet(StarknetFinality::AcceptedOnL2),
);
``` [1](#0-0) 

`verify_proof()` enforces that the caller's submitted `sign_payload` must carry a finality field that exactly matches the configured value via `request_matches_finality()`:

```rust
require!(
    Self::request_matches_finality(&payload_v1.request, finality),
    ProverError::FinalityMismatch.as_ref()
);
``` [2](#0-1) 

The check compares the finality field in the caller-supplied payload against the stored configuration:

```rust
fn request_matches_finality(request: &ForeignChainRpcRequest, finality: &MpcFinality) -> bool {
    match (request, finality) {
        (
            ForeignChainRpcRequest::Ethereum(args) | ForeignChainRpcRequest::Abstract(args),
            MpcFinality::Evm(finality),
        ) => args.finality == *finality,
``` [3](#0-2) 

This means the prover **enforces** that the proof uses `EvmFinality::Latest` for Abstract and `StarknetFinality::AcceptedOnL2` for Starknet — it actively rejects proofs at stronger finality levels. The test suite confirms this is intentional:

```rust

    EvmRpcRequest {
        tx_id: abs_testnet_tx_id(),
        extractors: vec![EvmExtractor::Log { log_index: 3 }],
        finality: EvmFinality::Latest,
    }
}
``` [4](#0-3) 

**Abstract (ChainKind::Abs):** Abstract is a ZKsync-based EVM L2 (confirmed by `zksync: true` in the hardhat config): [5](#0-4) 

On ZKsync-based L2s, `Latest` corresponds to blocks that have been sequenced but not yet committed or proven on Ethereum L1. These blocks carry no cryptographic finality guarantee and can be reorganized by the sequencer before L1 commitment. The bridge accepts a proof at this level and mints NEAR tokens, but the underlying lock event on Abstract may not yet be irreversible.

**Starknet (ChainKind::Strk):** `StarknetFinality::AcceptedOnL2` means the transaction is accepted by the Starknet sequencer but has not yet been proven and verified on Ethereum L1. Starknet's own documentation distinguishes `ACCEPTED_ON_L2` (sequencer-confirmed, reorgable) from `ACCEPTED_ON_L1` (L1-proven, irreversible). The test for Starknet explicitly uses `AcceptedOnL1` as the "correct" finality for a generic test request, yet the production configuration uses the weaker `AcceptedOnL2`: [6](#0-5) 

### Impact Explanation

An attacker who can cause a source-chain reorg (e.g., by exploiting a sequencer bug, or by being the sequencer operator on a permissioned L2) after a bridge proof has been submitted and accepted on NEAR can:

1. Lock tokens on Abstract or Starknet and submit the `initTransfer` event proof to the NEAR bridge.
2. The `MpcOmniProver` accepts the proof at `Latest`/`AcceptedOnL2` and the NEAR bridge mints bridged tokens to the attacker's NEAR account.
3. The attacker causes a reorg of the source chain, removing the lock transaction. The attacker's tokens on Abstract/Starknet are restored.
4. The attacker now holds both the minted NEAR tokens and the original source-chain tokens — a complete double-spend.

This results in **loss of bridged funds** and **unauthorized minting** of NEAR-side tokens backed by no actual locked collateral, directly breaking the bridge's escrow invariant.

### Likelihood Explanation

Abstract is a ZKsync-based L2 with a centralized sequencer. `Latest` blocks have no L1 commitment and can be reorganized before the batch is submitted to Ethereum. Starknet similarly uses a centralized sequencer for `AcceptedOnL2` state. While exploiting this requires influence over the L2 sequencer, the bridge's security model should not rely on sequencer honesty for chains where stronger finality (`EvmFinality::Finalized` / `StarknetFinality::AcceptedOnL1`) is available and already used for other chains (e.g., `ChainKind::Eth` uses `EvmFinality::Finalized` in tests). The contrast between Ethereum's `Finalized` and Abstract's `Latest` in the same codebase makes this a deliberate but unsafe design choice.

### Recommendation

- For `ChainKind::Abs`: Change the configured finality to `MpcFinality::Evm(EvmFinality::Finalized)` or at minimum `EvmFinality::Safe`. For a ZKsync-based L2, true finality requires the state root to be committed and proven on Ethereum L1.
- For `ChainKind::Strk`: Change the configured finality to `MpcFinality::Starknet(StarknetFinality::AcceptedOnL1)`, which requires the Starknet state to be proven and verified on Ethereum L1 before the bridge accepts the proof.

```rust
// Recommended fix in MpcOmniProver::init()
finalities.insert(ChainKind::Abs, MpcFinality::Evm(EvmFinality::Finalized));
finalities.insert(
    ChainKind::Strk,
    MpcFinality::Starknet(StarknetFinality::AcceptedOnL1),
);
```

### Proof of Concept

1. Attacker calls `initTransfer` on the Abstract bridge contract, locking 1000 USDC.
2. The transaction lands in Abstract block N (sequenced, not yet committed to L1).
3. Attacker (or a relayer) constructs `MpcVerifyProofArgs` with `ForeignChainRpcRequest::Abstract(EvmRpcRequest { finality: EvmFinality::Latest, ... })` and calls `fin_transfer` on the NEAR bridge.
4. `MpcOmniProver::verify_proof()` passes `request_matches_finality` (since `Latest == Latest`) and calls `mpc_contract.verify_foreign_transaction`. The MPC network reads the log at `Latest` and signs the payload.
5. `verify_callback` succeeds; NEAR bridge mints 1000 bridged USDC to the attacker's NEAR account.
6. Before Abstract block N's batch is committed to Ethereum L1, the attacker causes a sequencer reorg (e.g., via a sequencer bug or by being the sequencer). Block N is replaced; the `initTransfer` transaction is gone. The attacker's 1000 USDC on Abstract is restored.
7. Attacker holds 1000 USDC on Abstract **and** 1000 bridged USDC on NEAR. The bridge's escrow is insolvent by 1000 USDC. [1](#0-0) [7](#0-6)

    #[allow(clippy::needless_pass_by_value)]
    pub fn verify_proof(&self, #[serializer(borsh)] input: Vec<u8>) -> Promise {
        let args = MpcVerifyProofArgs::try_from_slice(&input).near_expect(ProverError::ParseArgs);

        let sign_payload = ForeignTxSignPayload::try_from_slice(&args.sign_payload)
            .near_expect(ProverError::ParseArgs);

        let ForeignTxSignPayload::V1(ref payload_v1) = sign_payload;

        let chain_kind = Self::request_to_chain_kind(&payload_v1.request)
            .near_expect(ProverError::UnsupportedChain);

        let finality = self
            .finalities
            .get(&chain_kind)
            .near_expect(ProverError::UnsupportedChain);

        require!(
            Self::request_matches_finality(&payload_v1.request, finality),
            ProverError::FinalityMismatch.as_ref()
        );

        let request_args = VerifyForeignTransactionRequestArgs {
            request: payload_v1.request.clone(),
            domain_id: DomainId(FOREIGN_TX_DOMAIN_ID),
            payload_version: ForeignTxPayloadVersion::V1,
        };

        ext_mpc_contract::ext(self.mpc_contract_id.clone())
            .with_static_gas(VERIFY_FOREIGN_TX_GAS)
            .with_attached_deposit(ONE_YOCTO)
            .verify_foreign_transaction(request_args)
            .then(
                Self::ext(near_sdk::env::current_account_id())
                    .with_static_gas(VERIFY_CALLBACK_GAS)
                    .verify_callback(args.proof_kind, args.sign_payload, chain_kind),
            )
    }
