### Title
Permissionless `sign_btc_transaction` with Attacker-Controlled `key_version` Permanently Corrupts Pending Withdrawal Signatures — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is callable by any NEAR account with no caller restriction. It accepts an attacker-controlled `key_version` parameter that is forwarded verbatim to the MPC signing service. The callback stores whatever signature the MPC service returns without validating that it corresponds to the key version used to construct the PSBT. Once stored, the signature slot is permanently locked ("Already signed"). If the MPC service accepts a wrong `key_version` (e.g., during key rotation when multiple versions are live), the stored signature is cryptographically invalid for the PSBT, the BTC transaction can never be broadcast, and the user's nBTC is frozen inside the bridge contract.

---

`sign_btc_transaction` in `api/chain_signatures.rs` carries no access-control attribute and no caller check:

    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,          // ← fully attacker-controlled
) -> PromiseOrValue<bool> {
``` [1](#0-0) 

`internal_sign_btc_transaction` passes `key_version` directly to the MPC service without any validation against the version that was used when the PSBT was constructed:

```rust
self.sign_promise(SignRequest {
    payload,
    path,
    key_version,   // ← forwarded as-is
})
``` [2](#0-1) 

The callback `sign_btc_transaction_callback` stores the returned signature unconditionally and then permanently locks the slot:

```rust
btc_pending_info.signatures[sign_index] = Some(signature.clone());
``` [3](#0-2) 

The guard that prevents a second signing attempt is checked both in the public entry point and in the callback:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
``` [4](#0-3) 

There is no subsequent validation that the stored signature is consistent with the public key embedded in the PSBT. The PSBT was built using the public key derived from the MPC root key for the **correct** `key_version`; a signature produced under a different `key_version` uses a different root key and is therefore invalid for that PSBT.

Once the slot is filled with an invalid signature, `is_all_signed()` may return `true` and `extract_tx_bytes_with_sign()` will produce a transaction that Bitcoin nodes will reject. The `BTCPendingInfo` transitions to `PendingVerify` stage, but `verify_withdraw_v2` can never succeed because the on-chain transaction ID will never appear in a Bitcoin block. [5](#0-4) 

---

### Impact Explanation

When a user initiates a withdrawal via `ft_transfer_call`, the nBTC is transferred to the bridge contract and held there until `verify_withdraw_v2` burns it after on-chain confirmation. If the signature slot is permanently corrupted:

- The BTC transaction is unbroadcastable; the UTXO remains locked in the bridge's unavailable pool.
- The nBTC is frozen inside the bridge contract (not burned, not returned).
- The user has lost access to both assets.

Recovery requires privileged operator action (`cancel_withdraw` by DAO/Operator, which itself spawns a new signing round that the attacker could also front-run, or a contract upgrade). This matches the **Medium** impact class: stuck bridge state requiring operator intervention, with escalation risk toward critical if the attacker also corrupts the cancel-RBF signing round.

---

### Likelihood Explanation

NEAR Chain Signatures supports key rotation via the `key_version` field. During any rotation window where both the old and new key versions are accepted by the MPC service, an attacker can supply the non-current version and receive a valid MPC signature that is cryptographically wrong for the PSBT. The attack requires no special privilege — only the ability to submit a NEAR transaction — and the target `btc_pending_sign_id` is publicly observable on-chain as soon as the withdrawal is initiated.

---
