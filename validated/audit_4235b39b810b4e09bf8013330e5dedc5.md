### Title
ChainSync Client Uses `emptyPerasWeightSnapshot` Instead of Actual Peras Weights in `checkPreferTheirsOverOurs`, Causing Incorrect Chain Selection Decisions — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs`, the ChainSync client hardcodes `emptyPerasWeightSnapshot` — an empty, zero-weight placeholder — instead of the live Peras certificate weight snapshot when calling `preferAnchoredCandidate`. This is the direct analog of the UniProxy bug: a pre-computed default value is used downstream instead of the actual computed result. When Peras is active and the canonical chain is heavier due to certificate boosts but shorter in raw block count, the node incorrectly classifies the canonical chain as non-preferable and disconnects from peers serving it, causing the node to remain on a non-canonical chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked by the ChainSync client whenever a peer's header is beyond the forecast horizon and the node must decide whether to keep waiting (the candidate is preferable) or disconnect (the candidate is not preferable):

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty weights, not actual weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` has two branches: when `isEmptyPerasWeightSnapshot weights` is true it compares chains by raw block count (`selectView`); when false it compares by `weightedSelectView` which incorporates Peras certificate boosts. [2](#0-1) 

By passing `emptyPerasWeightSnapshot`, the code always takes the block-count branch, ignoring any live Peras certificate boosts. The actual Peras weight snapshot is maintained and correctly used in `constructPreferableCandidates` and `switchTo` in `ChainSel.hs`: [3](#0-2) [4](#0-3) 

The `emptyPerasWeightSnapshot` value is defined as a zero-entry map: [5](#0-4) 

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical chain.**

When Peras is active, a chain can be *heavier* (preferred) due to certificate boosts even if it is *shorter* in raw block count. Consider:

- **Canonical chain C₁**: 10 blocks, but boosted by Peras certificates → total weight W₁ > W₂
- **Non-canonical chain C₂** (node's current selection): 12 blocks, no boosts → total weight W₂

A peer serves a header from C₁ that is beyond the forecast horizon. `checkPreferTheirsOverOurs` is called. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares by block count only: C₁ has 10 blocks vs C₂'s 12 → `ShouldNotSwitch`. The node disconnects from the peer offering C₁.

The node remains on C₂ — the non-canonical chain — and disconnects from every peer offering the canonical Peras-boosted chain C₁ whenever those headers happen to be beyond the forecast horizon. This is a durable chain selection divergence for the duration of the condition.

---

### Likelihood Explanation

**Medium.** Peras is currently disabled by default (`Note that if Peras is disabled (which is the default), there is no observable difference` per the CHANGELOG). However, the code is production-deployed and the feature flag can be enabled. Once Peras is active, the scenario requires:

1. A canonical chain that is preferred due to certificate boosts but shorter in block count than the node's current selection (a realistic scenario during a fork where one branch accumulates certificates).
2. A peer serving a header from that chain that is beyond the forecast horizon (a normal occurrence during syncing or when the node's chain is behind).

Both conditions are reachable by any unprivileged peer without any key compromise or operator action. The TODO comment at line 1841 explicitly acknowledges the issue is known and unresolved. [6](#0-5) 

---

### Recommendation

Pass the live `PerasWeightSnapshot` into `checkPreferTheirsOverOurs` from the `ChainDbView` or a dedicated STM read, mirroring how `constructPreferableCandidates` and `switchTo` already receive the actual `weights` parameter. Alternatively, remove the check entirely as the TODO comment proposes (see `https://github.com/tweag/cardano-peras/issues/64`), since the check is described as ephemeral and its removal is already planned.

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Produce chain C₁ (10 blocks) and accumulate Peras certificate boosts so its total weight exceeds chain C₂ (12 blocks, no boosts).
3. Connect a node currently on C₂ to a peer serving C₁.
4. Arrange for the peer's next header to be beyond the node's forecast horizon (e.g., by introducing a slot gap larger than the stability window).
5. `checkTime` calls `projectLedgerView`, which returns `Nothing` (beyond forecast horizon).
6. `checkPreferTheirsOverOurs` is called; `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` compares 10 blocks vs 12 blocks → `ShouldNotSwitch`.
7. The node throws `CandidateTooSparse` and disconnects from the peer.
8. The node remains on C₂ despite C₁ being the canonical, heavier chain. [1](#0-0)
