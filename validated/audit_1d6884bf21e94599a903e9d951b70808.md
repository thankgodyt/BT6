### Title
`shelleyAfterVoting` Counts All Post-Deadline Blocks Instead of Only Those in the Stability Window, Enabling Premature Era Transition During Chain Growth Violation — (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `applyHelper` accumulates every block whose slot falls at or after the voting deadline, spanning the full `2 * stabilityWindow` slots before the epoch boundary. The intended behavior — explicitly documented as a known bug in `civic_time.md` — is to count only blocks in the **first** stability window after the voting deadline. Because the counter is too wide, a crafted or naturally-occurring chain that violates Chain Growth inside the stability window but has enough blocks in the trailing `swindow` slots can push `shelleyAfterVoting >= k`, causing the Hard Fork Combinator to signal an era transition that it should instead suppress. This produces a divergent ledger-era view between nodes, breaking cross-era consensus.

---

### Finding Description

**Root cause — `applyHelper` in `Ledger.hs`**

When a Shelley-based block is applied, `applyHelper` updates `shelleyAfterVoting`:

```haskell
shelleyAfterVoting =
    -- We count the number of blocks that have been applied after the
    -- voting deadline has passed.
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
``` [1](#0-0) 

The `votingDeadline` is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
``` [2](#0-1) 

This means the counter increments for **any** block in the slot range `[startOfNextEpoch − 2·swindow, startOfNextEpoch)` — a span of `2 * swindow` slots. The stability window is only the first `swindow` of those slots: `[startOfNextEpoch − 2·swindow, startOfNextEpoch − swindow)`.

**Threshold check — `shelleyTransition` in `ShelleyHFC.hs`**

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
``` [3](#0-2) 

Once this guard passes, `singleEraTransition` returns `Just epochNo`, and the HFC commits to the era transition.

**Intended behavior (Iteration 4) — `civic_time.md`**

The design document explicitly states the intended rule and acknowledges the implementation diverges from it:

> "Silently ignore the on-chain governance … if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth). **(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)**" [4](#0-3) 

The `ShelleyTransitionInfo` comment in the ledger state definition also describes the correct intent — counting k blocks post-deadline to ensure the last pre-deadline block is no longer rollback-able: [5](#0-4) 

**The discrepancy**: blocks in the trailing `swindow` slots (`[startOfNextEpoch − swindow, startOfNextEpoch)`) are counted by the implementation but must not be counted per the design. Those blocks cannot prove that the governance outcome in the stability window is rollback-resistant.

---

### Impact Explanation

The `shelleyAfterVoting >= k` guard is the sole gating condition that prevents the HFC from signalling an era transition when Chain Growth is violated in the stability window. When the bug fires:

1. The HFC calls `singleEraTransition` → `shelleyTransition` → returns `Just epochNo` (era transition confirmed).
2. `reconstructSummaryLedger` extends the HFC summary with the new era bound.
3. The node begins using the next era's ledger rules, slot-to-time translations, and forecast horizon.
4. Nodes that correctly implement the intended behavior (or that observed a denser stability window) remain in the current era.
5. The two populations of nodes now disagree on which era is active, producing **cross-era consensus divergence**: blocks valid under one era's rules are invalid under the other's, and time/slot translations diverge.

This matches the allowed impact scope: **High — hard-fork/era-transition bug that breaks cross-era consensus or ledger invariants for production Cardano nodes.** [6](#0-5) 

---

### Likelihood Explanation

The bug is triggered when a chain satisfies both conditions simultaneously:

- **Condition A**: Fewer than `k+1` blocks in `[votingDeadline, votingDeadline + swindow)` — a Chain Growth violation in the stability window (e.g., caused by a network partition lasting up to ~18 hours on mainnet).
- **Condition B**: Enough blocks in the trailing `swindow` slots `[votingDeadline + swindow, startOfNextEpoch)` to push `shelleyAfterVoting >= k`.

Condition B is easily satisfied: with `swindow = 3k/f` and `f = 1/20`, the expected block count in `swindow` slots is `3k/f · f = 3k`, far exceeding `k`. So whenever Condition A holds naturally (network partition, eclipse attack, or adversarially-crafted low-density fork), Condition B is almost certainly met by honest block production in the trailing window.

An adversary with minority stake can serve such a chain via the ChainSync miniprotocol without requiring a stake majority or key compromise. No operator action is needed; the bug fires automatically as blocks are applied.

Likelihood: **Low-to-Medium** (requires a Chain Growth violation, which is outside normal Praos assumptions but is a realistic edge case during partitions or targeted eclipse attacks).

---

### Recommendation

Restrict the `shelleyAfterVoting` increment to blocks whose slot falls strictly within the stability window after the voting deadline:

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline
          && blockSlot blk < votingDeadline + SlotNo swindow
       then succ
       else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

This aligns the implementation with the Iteration 4 design described in `civic_time.md`: the HFC suppresses the era transition if and only if the stability window itself (not the full post-deadline span) contains fewer than `k+1` blocks.

Additionally, the threshold should be `>= k + 1` (not `>= k`) to match the `civic_time.md` specification of "k+1 blocks", though this is a separate off-by-one concern.

### Proof of Concept

Private-testnet sequence demonstrating the divergence:

1. Configure a two-node private testnet with `k = 10`, `f = 0.5`, `swindow = 60` slots, epoch length `= 200` slots.
2. Voting deadline = slot `200 − 2·60 = 80`. Stability window = slots `[80, 140)`. Trailing window = slots `[140, 200)`.
3. Arrange for only 5 blocks (< k+1 = 11) to be produced in slots `[80, 140)` — simulating a partition.
4. Allow normal block production in slots `[140, 200)`, producing ~30 blocks, pushing `shelleyAfterVoting` to ≥ 10.
5. Observe: `shelleyTransition` returns `Just epochNo` and the HFC transitions to the next era.
6. A corrected node (counting only stability-window blocks) keeps `shelleyAfterVoting = 5 < 10` and stays in the current era.
7. The two nodes now disagree on the active era; blocks produced by the transitioned node are rejected by the non-transitioned node.

The attacker-controlled entry path is the ChainSync miniprotocol: the adversary serves the low-density-stability-window chain to a victim node, which applies it block-by-block through `applyBlockLedgerResult` → `applyHelper`, accumulating the inflated `shelleyAfterVoting` count and triggering the premature transition.
