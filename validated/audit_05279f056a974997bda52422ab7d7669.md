### Title
Cancelled Withdrawal Can Still Be Signed and Executed — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

When `cancel_withdraw` is called by a DAO/Operator to cancel a pending withdrawal, the original `WithdrawOriginal` `BTCPendingInfo` entry is not removed and its `stage` is not changed — only the `cancel_rbf_reserved` field is set. Because `sign_btc_transaction` never checks this cancellation flag, any caller can still sign the original transaction after cancellation, allowing the withdrawal to proceed on Bitcoin despite the cancel.

---

### Finding Description

`cancel_withdraw` (restricted to `Role::DAO` or `Role::Operator`) is the bridge's mechanism to abort an in-flight withdrawal via a Replace-By-Fee cancel transaction. Internally it calls `do_cancel` on the original `BTCPendingInfo`: [1](#0-0) 

`do_cancel` only mutates three fields on the `OriginalState` — `max_gas_fee`, `last_rbf_time_sec`, and `cancel_rbf_reserved`. Critically, **the `stage` field is left as `PendingInfoStage::PendingSign`** and the entry remains in `btc_pending_infos`.

The bridge exposes a helper to assert cancellation status: [2](#0-1) 

However, `sign_btc_transaction` — the public, unpermissioned entry point for MPC signing — performs only two checks before proceeding to sign:

1. `assert_pending_sign()` — passes because `stage` was never changed.
2. An RBF-specific guard that only fires when `get_original_tx_id()` returns `Some(...)` — irrelevant for the original `WithdrawOriginal` transaction, which returns `None`. [3](#0-2) 

There is **no call to `assert_not_canceled()`** anywhere in the signing path. After `cancel_withdraw` is called, the original `WithdrawOriginal` entry is still in `PendingSign` stage, still present in `btc_pending_infos`, and fully signable by any NEAR account.

Once all inputs are signed, `sign_btc_transaction_callback` advances the state to `PendingVerify` and emits the signed transaction bytes: [4](#0-3) 

The signed original withdrawal transaction can then be broadcast to Bitcoin. If it confirms before the cancel-RBF transaction, the withdrawal is final on-chain and the bridge's cancel is rendered completely ineffective.

---

### Impact Explanation

The `cancel_withdraw` control — the only mechanism the bridge has to abort an in-flight withdrawal — is bypassable by any unprivileged NEAR account (including the withdrawal initiator). After a DAO/Operator cancel, the original withdrawal transaction can still be signed and broadcast. If it confirms on Bitcoin before the cancel-RBF, the withdrawal executes and the bridge's cancellation authority is nullified. This constitutes a **bypass of bridge authorization controls** with real security impact: the bridge cannot enforce withdrawal cancellations, which are a critical safety valve (e.g., for stopping withdrawals to compromised addresses or during security incidents).

**Severity: Medium** — Bypass of bridge policy/control without direct theft of third-party funds.

---

### Likelihood Explanation

The withdrawal initiator has a direct financial incentive to call `sign_btc_transaction` on the original pending ID immediately after observing a `cancel_withdraw` on-chain. The original pending ID is deterministic (derived from the PSBT hash) and publicly observable via events. `sign_btc_transaction` has no role restriction and requires only a NEAR attached deposit. The race is straightforward and requires no special knowledge or tooling.

---

### Recommendation

Add an `assert_not_canceled()` guard in `sign_btc_transaction` before dispatching the MPC sign call, so that a cancelled original transaction cannot be signed:

```rust
// In sign_btc_transaction, after assert_pending_sign():
if btc_pending_info.get_original_tx_id().is_none() {
    // Original transaction — check it has not been cancelled
    btc_pending_info.assert_not_canceled();
}
```

Alternatively, when `cancel_withdraw` is called, transition the original `BTCPendingInfo` to a terminal/cancelled stage so that `assert_pending_sign()` itself rejects further signing attempts.

---

### Proof of Concept

1. User calls `ft_on_transfer` with a `Withdraw` message → `WithdrawOriginal` entry created in `btc_pending_infos` with `stage = PendingSign`, `cancel_rbf_reserved = None`.
2. DAO/Operator calls `cancel_withdraw(original_id, ...)` → `do_cancel` sets `cancel_rbf_reserved = Some(...)` on the original; a new `WithdrawCancelRbf` entry is created. The original entry **remains** in `btc_pending_infos` with `stage = PendingSign`.
3. User (or any NEAR account) calls `sign_btc_transaction(original_id, 0, key_version)`:
   - `assert_pending_sign()` → passes (stage unchanged).
   - `get_original_tx_id()` → `None` (original tx, not RBF) → RBF guard skipped.
   - No `assert_not_canceled()` call → proceeds to MPC sign.
4. MPC returns a signature; `sign_btc_transaction_callback` stores it, and when all inputs are signed, emits `SignedBtcTransaction` with the full signed tx bytes and advances to `PendingVerify`.
5. The signed original withdrawal transaction is broadcast to Bitcoin. If it confirms before the cancel-RBF, the withdrawal is irreversible on-chain and the bridge's cancel is defeated. [5](#0-4) [6](#0-5)

    pub fn do_cancel(&mut self, gas_fee: u128, cancel_rbf_reserved: u128) {
        match self.state.borrow_mut() {
            PendingInfoState::WithdrawOriginal(state) => {
                state.max_gas_fee = gas_fee;
                state.last_rbf_time_sec = Some(nano_to_sec(env::block_timestamp()));
                state.cancel_rbf_reserved = Some(cancel_rbf_reserved.into());
            }
            PendingInfoState::ActiveUtxoManagementOriginal(state) => {
                state.max_gas_fee = gas_fee;
                state.last_rbf_time_sec = Some(nano_to_sec(env::block_timestamp()));
                state.cancel_rbf_reserved = Some(cancel_rbf_reserved.into());
            }
            _ => env::panic_str("Not original tx"),
        }
    }

    pub fn get_cancel_rbf_reserved(&self) -> Option<U128> {
        match &self.state {
            PendingInfoState::WithdrawOriginal(state) => state.cancel_rbf_reserved,
            PendingInfoState::ActiveUtxoManagementOriginal(state) => state.cancel_rbf_reserved,
            _ => env::panic_str("Not original tx"),
        }
    }

    pub fn assert_not_canceled(&self) {
        require!(self.get_cancel_rbf_reserved().is_none(), "already canceled");
    }
