### Title
Unconditional Peras Certificate Acceptance Bypasses Chain-Selection Weight Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` (success) for every peer-supplied Peras certificate, performing zero cryptographic or semantic validation. Because the production inbound-certificate pipeline (`makePerasCertPoolWriterFromChainDB`) calls this stub directly, any unprivileged peer connected via the Peras ObjectDiffusion mini-protocol can inject an arbitrary `PerasCert` — with any round number and any boosted-block pointer — into the local ChainDB. The injected certificate immediately contributes a `PerasWeight 15` boost to the targeted block during chain selection, allowing the attacker to make the node prefer a non-canonical chain that is up to 15 blocks shorter than the honest chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` the default `BlockSupportsPeras` instance (which covers all block types until a concrete override is provided) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every certificate, regardless of its content, is returned as `Right` — i.e., unconditionally accepted. No quorum check, no committee-membership check, no signature verification, and no round-number plausibility check is performed.

**Attacker-controlled entry path:**

`makePerasCertPoolWriterFromChainDB` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` is the production writer used when Peras is enabled. It wires `validatePerasCert mkPerasParams` as the sole validation gate for inbound peer certificates:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

`processCerts` (same file, lines 164–185) calls this function on every certificate received from a peer. If the function returns `Right`, the certificate is immediately added to the ChainDB via `ChainDB.addPerasCertAsync`. Because `validatePerasCert` always returns `Right`, every peer-supplied certificate passes.

**Chain-selection impact:**

`mkPerasParams` sets `perasWeight = PerasWeight 15`. Chain selection computes `totalWeightOfFragment = blockCount + weightBoostOfFragment`, where `weightBoostOfFragment` sums the `PerasWeight` of all boosted blocks in the fragment. A single injected certificate therefore adds 15 weight units to the adversarial chain, making it preferred over an honest chain that is up to 15 blocks longer.

**End-to-end exploit flow:**

1. Attacker connects to a Peras-enabled node via the ObjectDiffusion mini-protocol (no credentials required).
2. Attacker sends a `PerasCert { pcCertRound = <current round>, pcCertBoostedBlock = <adversarial block point> }`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The certificate is stored in the ChainDB's `PerasCertDB`.
5. On the next chain-selection run, `weightBoostOfFragment` adds `PerasWeight 15` to the adversarial fragment.
6. If the adversarial chain's `totalWeight` exceeds the honest chain's `totalWeight`, the node switches to the adversarial chain.

---

### Impact Explanation

**Severity: High** — matches "Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

A single fake certificate shifts the chain-selection balance by 15 weight units. An adversary who controls a fork that is up to 15 blocks shorter than the honest chain can cause a Peras-enabled node to adopt that fork. This breaks the fundamental Peras security guarantee that only a quorum-certified block should receive a weight boost. In practice it enables:

- A node to roll back up to 15 honest blocks and adopt an adversarial chain.
- Potential double-spend if the adversarial chain contains conflicting transactions that were already considered confirmed on the honest chain.
- Persistent chain divergence between nodes that received the fake certificate and those that did not.

---

### Likelihood Explanation

**Moderate** — Peras is currently disabled by default (`rnFeatureFlags`), so the ObjectDiffusion mini-protocol for certificates is not started on mainnet today. However:

- The code is in production files, not test stubs.
- Peras is actively being developed for deployment on Cardano mainnet.
- Once Peras is enabled (even in a private testnet or early deployment), any peer can exploit this with a single crafted message — no keys, no stake, no prior relationship required.
- The TODO comment and linked issue (`cardano-peras/issues/120`) confirm the stub is known but not yet replaced.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validation function that checks:

1. **Quorum**: the certificate must be backed by votes from committee members whose combined stake exceeds the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
2. **Signatures**: each constituent vote must carry a valid cryptographic signature from a registered committee member.
3. **Round plausibility**: `pcCertRound` must correspond to a round that is within the acceptable window relative to the current chain tip.
4. **Block existence**: `pcCertBoostedBlock` must point to a block that is actually present in the local VolatileDB or ImmutableDB.

Until the real implementation is in place, the node should refuse to start the Peras ObjectDiffusion mini-protocol (i.e., keep Peras disabled) rather than accepting certificates with a no-op validator.
