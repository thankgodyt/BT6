### Title
Any depositor can bypass the deposit bridge fee via the unguarded `safe_deposit` path in `verify_deposit_v2` — (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`verify_deposit_v2` selects between a fee-charging path and a fee-free path based solely on the caller-controlled `deposit_msg.safe_deposit` field. No role or access-control check gates the fee-free path. Any NEAR account can generate a deposit address with `safe_deposit: Some(...)`, send BTC to it, and call `verify_deposit_v2` to receive the full deposit amount as nBTC without paying the `deposit_bridge_fee`.

### Finding Description
In `verify_deposit_v2`, the routing decision is:

```rust
if deposit_msg.safe_deposit.is_some() {
    self.internal_safe_verify_deposit_entry(...)   // mints full deposit_amount, zero fee
} else {
    self.internal_verify_deposit_entry(...)        // mints deposit_amount − deposit_fee
}
``` [1](#0-0) 

The standard path deducts the fee before minting:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
``` [2](#0-1) 

The safe path mints the raw `deposit_amount` with no deduction:

```rust
.verify_safe_deposit_callback(
    recipient_id,
    deposit_amount.into(),   // full amount, no fee subtracted
    deposit_msg.msg,
    pending_utxo_info,
)
``` [3](#0-2) 

`internal_safe_verify_deposit_entry` enforces only an attached NEAR storage deposit — no role check:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_safe_deposit(),
    "Insufficient deposit for storage"
);
``` [4](#0-3) 

`DepositMsg.safe_deposit` is a plain optional field with no privileged-caller enforcement: [5](#0-4) 

The `BridgeFee::get_fee` function shows the fee is non-trivial when `fee_rate > 0` or `fee_min > 0`: [6](#0-5) 

### Impact Explanation
The protocol loses the entire `deposit_bridge_fee` on every deposit that uses the `safe_deposit` path. The depositor receives `deposit_amount` nBTC instead of `deposit_amount − deposit_fee` nBTC. Because the BTC is genuinely deposited, the nBTC supply remains backed, so this is a fee-revenue loss rather than unbacked minting. This matches the allowed Medium impact: **bypass of bridge fee policy**.

### Likelihood Explanation
The exploit requires only:
1. Attaching sufficient NEAR for storage (a small, fixed cost).
2. Including `safe_deposit: Some(SafeDepositMsg { msg: "" })` in `DepositMsg`.

No privileged role, leaked key, or complex setup is needed. Any depositor who reads the contract ABI can discover and use this path. The `#[trusted_relayer]` decorator on `verify_deposit_v2` adjusts confirmation counts for non-whitelisted callers but does not block function access, as confirmed by `get_confirmations` allowing any predecessor with only a higher confirmation delta: [7](#0-6) 

### Recommendation
Gate the `safe_deposit` dispatch in `verify_deposit_v2` behind an explicit allowlist of authorized integration accounts (e.g., the Omni Bridge contract ID). Reject calls where `deposit_msg.safe_deposit.is_some()` and `env::predecessor_account_id()` is not in that allowlist. Alternatively, remove the dual-path dispatch from `verify_deposit_v2` entirely and keep the fee-free path only in the dedicated `safe_verify_deposit` family of functions, which can then be restricted via `#[access_control_any(roles(...))]`.

### Proof of Concept
**Standard path (fee charged):**
1. `get_user_deposit_address({ recipient_id: alice, safe_deposit: None, ... })` → address A
2. Send 1 000 000 sat to address A.
3. Call `verify_deposit_v2({ ..., safe_deposit: None }, ...)`.
4. Alice receives `1 000 000 − deposit_fee` nBTC.

**Exploit path (fee bypassed):**
1. `get_user_deposit_address({ recipient_id: alice, safe_deposit: Some({ msg: "" }), ... })` → address B
2. Send 1 000 000 sat to address B.
3. Call `verify_deposit_v2({ ..., safe_deposit: Some({ msg: "" }) }, ...)` with attached NEAR ≥ `required_balance_for_safe_deposit()`.
4. Alice receives `1 000 000` nBTC — the full amount, zero fee deducted.

The protocol collects `deposit_fee` in step 4 of the standard path and zero in the exploit path, directly analogous to the DEX report where the protocol receives less fee than it should because the fee-calculation surface is manipulable by the user.
