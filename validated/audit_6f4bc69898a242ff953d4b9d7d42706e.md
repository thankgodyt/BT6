### Title
Peras Vote Voter Identity Is Self-Declared With No Cryptographic Binding, Allowing Any Peer to Forge Votes on Behalf of Any Stake Pool - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `PerasVote` data type carries a `pvVoteVoterId` field that is entirely self-declared by the submitting peer. The production `validatePerasVote` implementation only checks that the claimed voter ID exists in the stake distribution; it performs no cryptographic verification that the vote was actually signed by the claimed pool's key. Any unprivileged peer connected via the ObjectDiffusion mini-protocol can submit votes claiming to be any registered stake pool, accumulate fraudulent quorum weight, and cause honest nodes to accept invalid Peras certificates that incorrectly boost arbitrary blocks.

---

### Finding Description

**Root cause — missing signature field and missing signature check**

The `PerasVote` data type contains no signature field whatsoever:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- self-declared, no proof
  }
``` [1](#0-0) 

The production `validatePerasVote` implementation (the catch-all `instance StandardHash blk => BlockSupportsPeras blk`) only performs a map lookup against the stake distribution using the voter ID supplied by the peer:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` is simply:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [3](#0-2) 

There is no step that verifies a cryptographic signature binding the vote content to the claimed pool's key. The voter identity is accepted at face value.

**Production ingestion path**

`processVotes` — called from both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` — invokes `validatePerasVote` as the sole gate before persisting a vote:

```haskell
(\vote -> getStakeDistrSTM >>= \sd ->
    pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) [5](#0-4) 

Once a batch of votes passes this check, each vote is timestamped and stored. Stored votes are later aggregated by `votesReachQuorum` to determine whether a Peras certificate should be forged:

```haskell
votesReachQuorum cfg votes =
  ...
  | not votesHaveEnoughStake -> Nothing
  | otherwise -> Just ValidatedPerasVotesWithQuorum { ... }
``` [6](#0-5) 

The quorum check sums `vpvVoteStake` values that were assigned during `validatePerasVote` — i.e., the stake of the *claimed* pool, not a cryptographically proven one.

**Analog to the external report**

The external report's root cause is that `srcChainSender_` is embedded in a cross-chain message as `msg.sender` with no cryptographic binding, so a subsequent hop treats the embedded value as authoritative and skips the allowance check. Here, `pvVoteVoterId` is embedded in the `PerasVote` wire message with no cryptographic binding, and `validatePerasVote` treats the embedded value as authoritative and skips any signature check — the exact same identity-confusion pattern.

---

### Impact Explanation

An unprivileged peer can:

1. Enumerate all registered stake pools from the public ledger state.
2. Craft `PerasVote` messages claiming to be high-stake pools, targeting any block the attacker wishes to boost.
3. Submit these votes via the ObjectDiffusion mini-protocol to any honest node.
4. Each forged vote passes `validatePerasVote` and is stored with the victim pool's stake weight.
5. Once the accumulated forged stake exceeds the quorum threshold, `votesReachQuorum` returns `Just`, and `forgePerasCert` is called, producing a `ValidatedPerasCert` for the attacker's chosen block.
6. The fraudulent certificate boosts the attacker's chosen block, directly influencing chain selection on the victim node.

This is a **Critical** bypass of Peras voting and certificate checks: an unprivileged peer causes an honest node to accept an invalid Peras certificate for a block that has no legitimate quorum, corrupting the chain-selection outcome without any key compromise.

---

### Likelihood Explanation

The attack requires only a standard peer connection over the ObjectDiffusion mini-protocol — no privileged keys, no stake, no prior relationship. The stake distribution of all registered pools is public on-chain data. The attacker needs only to know which pools have enough combined stake to exceed the quorum threshold (also a public parameter), construct well-formed CBOR-encoded `PerasVote` messages, and send them. The `PerasVote` serialisation format is straightforward (round number, block point, voter key hash). This is fully reachable from an external, zero-privilege attacker.

---

### Recommendation

1. **Add a signature field to `PerasVote`**: The data type must include a cryptographic signature (e.g., a VRF proof or a BLS/Ed25519 signature) over `(pvVoteRound, pvVoteBlock)` produced with the pool's registered signing key.

2. **Verify the signature in `validatePerasVote`**: The validation must recover the claimed pool's verification key from the ledger state and verify the signature before accepting the vote. Only if the signature is valid should the vote be stored with the pool's stake weight.

3. **Align with the WFALS/EveryoneVotes committee model**: The existing `Committee.Class` and `Committee.WFALS` modules already implement proper `verifyVote` with cryptographic checks. The `PerasVote` path should be unified with or replaced by this committee-based verification path rather than maintaining a parallel, signature-free code path.

---

### Proof of Concept

**Setup**: A private testnet with two nodes (honest node H, attacker node A). The ledger state contains pool P with 40% of total stake (above the quorum threshold).

**Steps**:

1. Attacker A connects to honest node H via the ObjectDiffusion (PerasVote) mini-protocol.
2. A constructs a `PerasVote` message:
   - `pvVoteRound = <current Peras round>`
   - `pvVoteBlock = <point of attacker's preferred block>`
   - `pvVoteVoterId = PerasVoterId (keyHash of pool P)` — claimed, not proven
3. A sends this vote to H.
4. H calls `processVotes`, which calls `validatePerasVote mkPerasParams stakeDistr vote`.
5. `lookupPerasVoteStake` finds pool P in the stake distribution and returns its 40% stake.
6. The vote is stored as `ValidatedPerasVote { vpvVote = vote, vpvVoteStake = 0.40 }`.
7. `votesReachQuorum` is called; total stake (0.40) exceeds the quorum threshold.
8. `forgePerasCert` produces a `ValidatedPerasCert` boosting the attacker's chosen block.
9. Chain selection on H now treats the attacker's block as boosted, preferring it over the honest chain.

**Expected outcome**: H accepts a Peras certificate for a block that pool P never actually voted for, with no key material from pool P involved. [7](#0-6)

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
