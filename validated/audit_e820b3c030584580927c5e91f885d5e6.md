Audit Report

## Title
Conflicting Access Control on `claim_fee` Permanently Locks Fee Tokens When `fee_recipient` Is Not a Trusted Relayer — (`near/omni-bridge/src/lib.rs`)

## Summary
`claim_fee` enforces two independently unsatisfiable access-control constraints: the caller must be a trusted relayer (via `#[trusted_relayer]`), and the caller must equal the `fee_recipient` embedded in the MPC-signed proof (via `require!(fee_recipient == *predecessor_account_id)`). Because `sign_transfer` accepts any arbitrary NEAR `AccountId` as `fee_recipient`, any transfer whose `fee_recipient` is not itself a trusted relayer produces a permanently unclaimable fee, freezing those tokens in the contract indefinitely.

## Finding Description
`claim_fee` at line 1054–1064 carries the `#[trusted_relayer]` attribute, restricting callers to active staked relayers or accounts holding the `DAO`/`UnrestrictedRelayer` bypass roles:

```rust
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise {
```

Inside `claim_fee_callback` at line 1083–1086, a second independent guard requires the caller to equal the `fee_recipient` from the proof:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

`sign_transfer` at line 447–500 accepts any arbitrary `fee_recipient: Option<AccountId>` with no restriction to trusted relayers:

```rust
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,
    fee: &Option<Fee>,
) -> Promise {
```

The two constraints are simultaneously satisfiable **only** when `fee_recipient` is itself a trusted relayer or DAO account. In every other case:
- The designated `fee_recipient` cannot call `claim_fee` — blocked by `#[trusted_relayer]`.
- Any trusted relayer who calls `claim_fee` is blocked by `require!(fee_recipient == *predecessor_account_id)` in the callback.
- The DAO bypasses `#[trusted_relayer]` but is still blocked by the same `require!` unless the DAO account is the `fee_recipient`.

`send_fee_internal` — which releases locked tokens and mints/transfers the fee — is only reachable through `claim_fee_callback` at line 1133 (for EVM transfers). There is no rescue path.

## Impact Explanation
When `claim_fee` is permanently blocked for a transfer, `remove_transfer_message` is never called (the `pending_transfers` entry persists forever), `unlock_tokens_if_needed` is never called (the `locked_tokens` accounting is never decremented for the fee portion), and the fee tokens locked when the user called `ft_transfer_call` are never minted or transferred to anyone. This constitutes **permanent freezing of bridged funds** (the fee slice of every affected transfer), matching the critical impact class of permanent freezing of bridged funds across NEAR/EVM flows.

## Likelihood Explanation
Two realistic, attacker-reachable paths exist requiring no admin compromise:

**Path A — Relayer designates a non-relayer treasury/multisig as `fee_recipient`.** A trusted relayer calls `sign_transfer` with `fee_recipient = Some("treasury.near")` where `treasury.near` is not a staked relayer. This is a natural operational pattern (routing fees to a shared treasury). The fee is immediately and permanently unclaimable.

**Path B — Relayer resigns before claiming accumulated fees.** A trusted relayer signs many transfers with `fee_recipient = Some(themselves)`, then calls `resign_trusted_relayer`. They are no longer a trusted relayer. Every pending fee claim is now permanently blocked: they fail `#[trusted_relayer]`, and no other account can satisfy `fee_recipient == predecessor_account_id`.

Both paths are reachable by an ordinary trusted relayer through normal public contract calls.

## Recommendation
Remove the `#[trusted_relayer]` restriction from `claim_fee`. The `fee_recipient` is already authenticated by the MPC-signed payload and verified by the prover, so no additional caller-identity gate is needed — any caller presenting a valid proof for a transfer where they are the `fee_recipient` should be permitted to claim. Alternatively, add a DAO-callable rescue function that can forward a locked fee to the recorded `fee_recipient` without requiring the `fee_recipient` to be the caller.

## Proof of Concept
1. Trusted relayer calls `sign_transfer` with `fee_recipient = Some("treasury.near")` where `treasury.near` has no trusted-relayer stake.
2. MPC signs the payload; the signed transaction is submitted to the EVM chain; the EVM bridge finalizes the transfer.
3. `treasury.near` calls `claim_fee` → rejected by `#[trusted_relayer]` (not a staked relayer). *(line 1055)*
4. The original trusted relayer calls `claim_fee` → `claim_fee_callback` panics with `OnlyFeeRecipientCanClaim` because `fee_recipient ("treasury.near") != predecessor_account_id (relayer.near)`. *(line 1083–1086)*
5. DAO calls `claim_fee` → passes `#[trusted_relayer]` bypass, but `claim_fee_callback` panics with `OnlyFeeRecipientCanClaim` because `fee_recipient ("treasury.near") != predecessor_account_id (dao.near)`. *(line 1083–1086)*
6. `send_fee_internal` is never reached *(line 1133)*; the fee tokens remain locked in the contract with no callable path to release them.
