### Title
Tokens Permanently Stuck in Bridge Account When Recipient is Unregistered in `safe_mint` — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge account first, then attempts to transfer them to the recipient. If the recipient's NEAR account is not registered in the nBTC token contract, the function silently returns `U128(0)` without transferring the tokens, leaving the minted nBTC permanently stuck in the bridge account with no attribution to the depositor and no recovery path.

---

### Finding Description

In `safe_mint`, the function unconditionally mints `amount` tokens into `self.bridge_id` via `internal_deposit`, then checks whether the recipient account is registered: [1](#0-0) 

The critical sequence is:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — tokens are minted into the bridge account's balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient is not registered, the function exits immediately. [2](#0-1) 

The minted tokens remain in the bridge account. There is no `lost_found` entry created, no event emitted for the stuck amount, and no mechanism to attribute or recover these tokens for the original depositor. The `lost_found` map and its recovery logic exist only in `transfer_nbtc_callback`, which is a separate code path not reached by `safe_mint`. [3](#0-2) 

This is structurally analogous to the reference report: just as `removeListing` burned tokens that the listing owner had not yet withdrawn, `safe_mint` mints tokens that are then silently abandoned in the bridge account when the recipient is unregistered — the user's deposited BTC is consumed by the bridge flow, but no nBTC is ever delivered or recoverable.

---

### Impact Explanation

A user who deposits BTC (or ZEC) to the bridge but whose NEAR account is not registered in the nBTC token contract will have their deposit fully processed on the bridge side (the UTXO is consumed and marked verified), but will receive zero nBTC. The minted nBTC tokens accumulate in the bridge account's balance with no on-chain record linking them to the depositor. The user suffers a permanent, total loss of their deposited funds with no recourse.

This matches the allowed impact: **Critical — Significant loss, theft, destruction, or permanent locking of user funds.** [2](#0-1) 

---

### Likelihood Explanation

NEAR NEP-141 storage registration is a prerequisite for receiving tokens, but it is a separate, manual step that many users — especially new users, users bridging to a fresh account, or users relying on a dApp that does not pre-register them — may omit. The `safe_mint` entrypoint is a production code path callable by the bridge contract. Any deposit whose recipient account is unregistered at the moment `safe_mint` executes will silently destroy the user's funds. No privileged access is required; the trigger is simply the absence of a storage registration call.

---

### Recommendation

- **Short term:** Before minting to the bridge account, check whether the recipient is registered. If not, either (a) register the account automatically (paying the storage cost from the attached deposit), or (b) record the owed amount in a `lost_found`-style map keyed by `account_id` so the user can claim it after registering. Do not mint tokens that cannot be delivered.
- **Long term:** Add an invariant check (e.g., via integration tests or formal verification) that the total nBTC supply in the bridge account never exceeds the sum of tracked protocol fees plus explicitly recorded lost-found balances, ensuring no tokens can silently accumulate without attribution.

---

### Proof of Concept

1. Alice deposits 0.01 BTC to the bridge-derived address for her NEAR account `alice.near`.
2. A relayer submits `verify_deposit` with a valid Merkle proof; the bridge processes the deposit and calls `safe_mint("alice.near", 1_000_000, None)` on the nBTC contract.
3. `alice.near` has never called `storage_deposit` on the nBTC contract, so `self.token.accounts.get(&account_id).is_none()` is `true`.
4. `self.token.internal_deposit(&self.bridge_id, 1_000_000)` executes — 1,000,000 satoshi-units of nBTC are minted into the bridge account.
5. The function returns `PromiseOrValue::Value(U128(0))` immediately.
6. Alice's BTC UTXO is marked as verified and cannot be refunded. Alice holds 0 nBTC. The 1,000,000 nBTC units sit in the bridge account with no record linking them to Alice. [1](#0-0)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
