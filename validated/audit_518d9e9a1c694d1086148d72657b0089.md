### Title
Peras Quorum Check Compares Unnormalized Absolute Stake Against Relative Threshold, Enabling Unauthorized Certificate Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value — sourced from the ledger's absolute stake distribution — directly against a relative quorum threshold (a `Rational` fraction between 0 and 1), without normalization. The function's own documentation acknowledges this unit mismatch as an unresolved TODO. Because absolute ledger stake values (in lovelace, potentially millions to billions) are orders of magnitude larger than any relative threshold, the quorum check is trivially satisfied by any single vote, allowing an unprivileged peer to cause unauthorized Peras certificates to be forged.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` is the sole gate for Peras quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake     = unPerasVoteStake voteStake
  quorumThreshold =
    unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin =
    unPerasQuorumStakeThresholdSafetyMargin
      (perasQuorumStakeThresholdSafetyMargin params)
```

The function's own documentation states the root cause explicitly:

> **TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units. That is, both are either absolute or relative (normalized) values. Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally.** [1](#0-0) 

The `PerasVoteStake` type comment confirms normalization is absent:

> **At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee (given that the quorum is expressed as a relative value of the voting committee total stake).** [2](#0-1) 

The `PerasVoteStakeDistr` is populated from the ledger's pool distribution (absolute lovelace values). The `PerasQuorumStakeThreshold` is a relative `Rational` (e.g., `3/4`). When `validatePerasVote` looks up a voter's stake, it stores the raw absolute value directly into `ValidatedPerasVote.vpvVoteStake`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

This absolute value then flows into `votesReachQuorum` → `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

The same mismatch is present in `updateLoserVoteState`, which uses `stakeAboveThreshold` to detect the error condition of a loser target exceeding quorum: [5](#0-4) 

The production entry point is `processVotes`, called from `makePerasVotePoolWriterFromChainDB`, which accepts votes from any peer via the ObjectDiffusion mini-protocol: [6](#0-5) 

---

### Impact Explanation

This is a bypass of the Peras quorum/certificate check. Because absolute ledger stake (e.g., `1_000_000` lovelace for a small pool) is compared against a relative threshold (e.g., `0.75`), the condition `1_000_000 >= 0.75` is always `True`. Any single vote from any peer with any positive stake immediately satisfies quorum, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to be called. The resulting `ValidatedPerasCert` carries a `PerasWeight` boost that is applied during chain selection. An adversary can therefore boost any block of their choice with a single vote, making their preferred chain appear heavier to honest nodes and potentially causing chain selection to diverge from the canonical chain.

---

### Likelihood Explanation

The attack requires only that the adversary participate in the Peras vote diffusion protocol and send a single well-formed `PerasVote` message. No special privileges, keys, or stake majority are required. The `processVotes` function accepts votes from any connected peer, validates them (the validation only checks that the voter is in the stake distribution, not that the stake is normalized), and immediately adds them to the vote aggregation state. The unit mismatch is structural and always present until normalization is implemented.

---

### Recommendation

Before calling `stakeAboveThreshold`, normalize each voter's `PerasVoteStake` by dividing by the total stake in `PerasVoteStakeDistr`. Alternatively, modify `stakeAboveThreshold` to accept the full `PerasVoteStakeDistr` and perform normalization internally, so the comparison is always between two values in the same unit (both relative fractions summing to ≤ 1).

---

### Proof of Concept

1. Adversary peer sends a `PerasVote` for block `B` in round `R` via ObjectDiffusion.
2. `processVotes` calls `validatePerasVote mkPerasParams sd vote`.
3. `lookupPerasVoteStake` returns the voter's absolute ledger stake, e.g., `PerasVoteStake (1_000_000 % 1)`.
4. `ValidatedPerasVote { vpvVoteStake = PerasVoteStake (1_000_000 % 1) }` is stored.
5. `updateCandidateVoteState` calls `votesReachQuorum cfg [vote]`.
6. `stakeAboveThreshold params (PerasVoteStake (1_000_000 % 1))` evaluates `1_000_000 >= 0.75 + safetyMargin` → `True`.
7. `forgePerasCert` is called; a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` is produced for block `B`.
8. The certificate is stored and applied during chain selection, boosting `B` by `PerasWeight` regardless of actual quorum support.
