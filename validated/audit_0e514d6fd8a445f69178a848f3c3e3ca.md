### Title
VRF Signing Key Stored in Plaintext on Disk and in Unprotected Heap Memory With No Secure Alternative — (File: `ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos/Common.hs`)

---

### Summary

The Praos/TPraos block-forging path loads the VRF signing key from an unencrypted on-disk file and stores it for the entire node lifetime in a normal (non-mlocked) Haskell heap field `praosCanBeLeaderSignKeyVRF`. Unlike the KES signing key, which has a secure `PraosCredentialsAgent` path that keeps the key off disk and in mlocked memory, **no secure alternative exists for the VRF key**. Additionally, `SigningKey VrfKey` derives `Show` via `UsingRawBytesHex`, meaning the raw key bytes can be inadvertently emitted to logs or error output.

---

### Finding Description

**Step 1 — Key loaded from plaintext file.**

`readLeaderCredentialsSingleton` in `Cardano/Node/Protocol/Shelley.hs` reads the VRF signing key directly from a JSON/CBOR TextEnvelope file with no encryption:

```haskell
vrfSKey <-
  firstExceptT FileError (newExceptT $ readFileTextEnvelope (AsSigningKey AsVrfKey) vrfFile)
```

The same path is taken by `readLeaderCredentialsBulk` via `parseEnvelope (AsSigningKey AsVrfKey) scVrf`. The `bulk-creds-k2.json` test fixture confirms the on-disk format is unencrypted CBOR hex (e.g., `"cborHex": "584040c0bd2d..."`). [1](#0-0) 

**Step 2 — Key stored in normal heap memory for the node's lifetime.**

`mkPraosLeaderCredentials` places the deserialized `vrfKey` directly into `PraosCanBeLeader.praosCanBeLeaderSignKeyVRF`, a strict field in a long-lived data structure:

```haskell
data PraosCanBeLeader c = PraosCanBeLeader
  { praosCanBeLeaderColdVerKey :: !(SL.VKey BlockIssuer)
  , praosCanBeLeaderSignKeyVRF :: !(SignKeyVRF (VRF c))   -- ← raw key, no mlock
  , praosCanBeLeaderCredentialsSource :: !(PraosCredentialsSource c)
  }
```

There is no `forgetSignKeyVRF` call, no mlocking, and no equivalent of `PraosCredentialsAgent` for VRF. The key lives in the GHC heap for the entire process lifetime and can be swapped to disk by the OS. [2](#0-1) 

**Step 3 — `Show` instance leaks raw key bytes.**

`SigningKey VrfKey` derives `Show` via `UsingRawBytesHex`:

```haskell
newtype SigningKey VrfKey
  = VrfSigningKey (Crypto.SignKeyVRF (VRF StandardCrypto))
  deriving (Show, IsString) via UsingRawBytesHex (SigningKey VrfKey)
```

Any code path that prints or logs a `SigningKey VrfKey` value (e.g., in an exception handler or debug trace) will emit the full raw key bytes in hex. [3](#0-2) 

**Step 4 — KES key path explicitly self-documents the same problem.**

The `PraosCredentialsUnsound` constructor's own comment acknowledges the violation:

> *"This uses `KES.UnsoundPureSignKeyKES`, which does not provide mlocking guarantees, **violating the rule that KES secrets must never be stored on disk**, but allows the sign key to be loaded from a local file."*

KES has a mitigation path (`PraosCredentialsAgent`). VRF has none. [4](#0-3) 

---

### Impact Explanation

The VRF signing key is the credential that proves a stake pool's leader eligibility for a given slot (`checkIsLeader` calls `VRF.evalCertified () rho' praosCanBeLeaderSignKeyVRF`). An attacker who obtains this key can:

1. Compute valid VRF proofs for any slot where the pool is elected.
2. Forge `PraosIsLeader` witnesses and produce blocks that pass all consensus validation checks, because the VRF output and the cold verification key hash will match the registered pool.
3. Equivocate — produce competing blocks in the same slot — causing chain forks and potentially double-spend scenarios.

This constitutes a **bypass of leader eligibility** and enables **unauthorized block acceptance** by honest nodes.

**Impact: Medium–Critical** (sensitive consensus-state exposure enabling leader eligibility bypass).

---

### Likelihood Explanation

The VRF key file is a standard operator-managed file (`shelley-vrf-key` or the bulk credentials JSON). It is:
- Stored unencrypted on the block-producer's filesystem.
- Readable by any process running as the same OS user as the node.
- Included in unencrypted filesystem backups.
- Potentially exposed via misconfigured file permissions, a co-located service with a path-traversal bug, or a compromised backup pipeline.

The `Show` instance additionally creates a log-leakage vector that requires no filesystem access at all — only access to log aggregation output.

Likelihood: **Medium** (requires local filesystem read access or log access, which is a realistic attacker position for a co-hosted or cloud-deployed block producer).

---

### Recommendation

**Short term:**
- Remove the `Show` instance (or replace it with a redacted version) for `SigningKey VrfKey` and `SigningKey UnsoundPureKesKey` so raw key bytes cannot be emitted to logs.
- Enforce strict file-permission checks (mode `0400`, owned by the node user) on VRF and KES key files at startup.

**Long term:**
- Introduce a VRF agent analogous to `PraosCredentialsAgent` / `kes-agent` that keeps the VRF signing key in mlocked memory on a separate process, never writing it to the GHC heap or to disk in plaintext.
- Until a VRF agent exists, document clearly that the VRF key file must be treated with the same sensitivity as a hardware security module credential, and provide tooling to detect world-readable key files.

---

### Proof of Concept

1. Start a Cardano block-producer node using `readLeaderCredentialsSingleton` with `--shelley-vrf-key /path/to/vrf.skey`.
2. As a local attacker with read access to the node's working directory (e.g., same Unix group, or access to a backup):
   ```bash
   cat /path/to/vrf.skey
   # {"type":"VrfSigningKey_PraosVRF","description":"VRF Signing Key",
   #  "cborHex":"584040c0bd2dd8acfaded1d93c4844c2130058f86067af2e065dd3ae001e964a5f18..."}
   ```
3. Decode the CBOR hex to recover the raw 64-byte VRF signing key.
4. Use `rawDeserialiseSignKeyVRF` (exposed via `SerialiseAsRawBytes (SigningKey VrfKey)`) to reconstruct the key in a forging process.
5. Call `VRF.evalCertified () rho' stolenVrfKey` for any target slot to produce a valid `PraosIsLeader` proof, then forge a block that passes `updateChainDepState` on all honest peers.

The `bulk-creds-k2.json` test fixture in the repository already demonstrates that VRF signing keys are stored in this exact plaintext CBOR hex format. [5](#0-4) [6](#0-5)
