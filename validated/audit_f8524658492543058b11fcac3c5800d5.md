Audit Report

## Title
TOCTOU Race Between `fast_fin_transfer` Promise Chain and `process_fin_transfer_to_near` Enables Double-Delivery of Bridged Tokens — (File: near/omni-bridge/src/lib.rs)

## Summary

`fast_fin_transfer` (NEAR recipient path) checks `finalised_transfers` as a guard but defers the write to `fast_transfers` until `fast_fin_transfer_to_near_callback` executes in a future NEAR receipt. During the window between these two receipts, a concurrent `fin_transfer` call can complete its own callback, find `fast_transfers` empty, send bridge-unlocked tokens to the original recipient, and write to `finalised_transfers`. When `fast_fin_transfer_to_near_callback` subsequently executes, it does not re-check `finalised_transfers`, successfully inserts into `fast_transfers`, and sends the relayer's pre-funded tokens to the same recipient a second time, producing a double-delivery of bridged funds.

## Finding Description

**Root cause — deferred state write with no re-check in callback:**

`fast_fin_transfer` checks `finalised_transfers` at lines 778–780:

```rust
if self.is_unified_transfer_finalised(&fast_fin_transfer_msg.transfer_id) {
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
``` [1](#0-0) 

For a NEAR recipient, the function then returns a promise chain without writing anything to `fast_transfers`:

```rust
Self::check_or_pay_ft_storage(&deposit_action, ...)
    .then(Self::ext(...).fast_fin_transfer_to_near_callback(...))
    .into()
``` [2](#0-1) 

The actual `fast_transfers` write occurs only inside the callback:

```rust
let required_balance = self
    .add_fast_transfer(fast_transfer, relayer_id, storage_payer.clone())
    .saturating_add(ONE_YOCTO);
``` [3](#0-2) 

`fast_fin_transfer_to_near_callback` contains **no check** against `finalised_transfers` or `is_unified_transfer_finalised`. Its only uniqueness guard is `add_fast_transfer`'s insert-or-panic on `fast_transfers`, which is a separate map. [4](#0-3) 

**Concurrent path — `process_fin_transfer_to_near`:**

`process_fin_transfer_to_near` first calls `add_fin_transfer`, which atomically inserts into `finalised_transfers` and panics if already present:

```rust
let mut required_balance = self.add_fin_transfer(&transfer_message.get_transfer_id());
``` [5](#0-4) 

It then reads `fast_transfers` to decide the recipient:

```rust
let fast_transfer_status = self.get_fast_transfer_status(&fast_transfer.id());
let (recipient, msg, fee_recipient) = match fast_transfer_status {
    Some(status) => { /* redirect to relayer */ }
    None => (recipient, transfer_message.msg.clone(), predecessor_account_id.clone()),
};
``` [6](#0-5) 

If `fast_transfers` is still empty (because `fast_fin_transfer_to_near_callback` has not yet executed), the `None` branch fires: bridge-unlocked/minted tokens are sent to the **original recipient**, and `finalised_transfers` is written. [7](#0-6) 

`add_fin_transfer` uses a set insert with a uniqueness panic, so it cannot be called twice for the same transfer ID: [8](#0-7) 

`add_fast_transfer` uses a map insert with an `is_none()` check, so it also cannot be called twice for the same fast-transfer ID — but these two maps are **independent**: [9](#0-8) 

**Race window (NEAR async receipt model):**

| Receipt | Event |
|---------|-------|
| R1 | Trusted relayer calls `fast_fin_transfer` → guard passes, promise chain scheduled, `fast_transfers` still empty |
| R2 | Any party submits `fin_transfer` with valid proof |
| R3 | `fin_transfer_callback` → `process_fin_transfer_to_near` → `fast_transfers` empty → **bridge tokens sent to recipient** → `finalised_transfers` written |
| R4 | `fast_fin_transfer_to_near_callback` → `add_fast_transfer` succeeds (no conflict in `fast_transfers`) → **relayer's tokens sent to same recipient** |

In R4, `finalised_transfers` already contains the transfer ID, but the callback never checks it, so the second token delivery proceeds unconditionally.

## Impact Explanation

**Double-spending of bridged funds (Critical).** The recipient receives tokens twice:

- **First delivery (R3):** `process_fin_transfer_to_near` unlocks or mints tokens from the bridge's controlled supply and sends them to the recipient.
- **Second delivery (R4):** `fast_fin_transfer_to_near_callback` sends the relayer's pre-funded tokens to the same recipient.

The bridge's locked-token accounting is broken: tokens that should have been routed to the relayer as reimbursement are instead sent to the recipient, and the relayer's own fronted tokens are also lost to the recipient. This matches the Critical impact class: double-spending of bridged funds.

## Likelihood Explanation

The exploit requires:
1. A trusted relayer legitimately calls `fast_fin_transfer` for a NEAR recipient (normal protocol operation).
2. Any party (including an unprivileged external user) submits `fin_transfer` with a valid cross-chain proof before `fast_fin_transfer_to_near_callback` executes.

Step 2 is permissionless — `fin_transfer` accepts any caller with a valid proof, and the proof is publicly derivable from the source-chain event. The window spans at least one NEAR block (~1 second), which is sufficient for a monitoring bot to detect the `fast_fin_transfer` call and submit `fin_transfer`. The race is repeatable for every fast transfer targeting a NEAR recipient.

## Recommendation

Add a re-check of `finalised_transfers` at the start of `fast_fin_transfer_to_near_callback`, before `add_fast_transfer` and before any token transfer:

```rust
if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
    // fin_transfer already settled; abort without sending tokens
    env::panic_str(BridgeError::TransferAlreadyFinalised.to_string().as_str());
}
```

Alternatively, write a sentinel entry into `fast_transfers` (or a dedicated pending-fast-transfer set) **synchronously inside `fast_fin_transfer`** before returning the promise, so that `process_fin_transfer_to_near` observes it and redirects tokens to the relayer even if the callback has not yet executed. Either approach closes the unsynchronized window between the guard check and the state write.

## Proof of Concept

**Private-testnet transaction sequence:**

1. Deploy the bridge contract on a NEAR localnet.
2. Register a trusted relayer account and fund it with token balance.
3. Initiate a cross-chain transfer from a source chain (or simulate the proof).
4. Call `fast_fin_transfer` from the trusted relayer for a NEAR recipient. Observe that `fast_transfers` is still empty after this call returns (before the callback receipt executes).
5. In the same block or the immediately following block, call `fin_transfer` with the valid proof from any unprivileged account.
6. Allow `fin_transfer_callback` → `process_fin_transfer_to_near` to execute. Verify that tokens are sent to the recipient and `finalised_transfers` is written.
7. Allow `fast_fin_transfer_to_near_callback` to execute. Verify that a second token transfer to the same recipient is emitted and `fast_transfers` now contains the entry.
8. Check the recipient's token balance: it equals twice the expected bridged amount, confirming the double-spend.
