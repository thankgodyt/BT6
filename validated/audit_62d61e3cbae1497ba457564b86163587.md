Audit Report

## Title
ERC1155 `safeTransferFrom` Callback Permanently Freezes Bridged Funds When Recipient Contract Rejects Tokens - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

In `OmniBridge.finTransfer`, ERC1155 tokens are delivered via `IERC1155.safeTransferFrom` (lines 324–330), which mandatorily invokes `onERC1155Received` on any contract recipient per EIP-1155. If the recipient contract does not implement `IERC1155Receiver` or reverts in the callback, the entire `finTransfer` transaction reverts. Because the MPC-signed payload cryptographically binds the recipient address (line 298, verified at line 311), no alternative finalization is possible on-chain, and the corresponding NEAR-side tokens — already burned or locked — are permanently frozen.

## Finding Description

`finTransfer` marks the nonce at line 287 (`completedTransfers[payload.destinationNonce] = true`) before executing the token transfer. For ERC1155 tokens (lines 323–330), it calls:

```solidity
IERC1155(multiToken.tokenAddress).safeTransferFrom(
    address(this),
    payload.recipient,
    multiToken.tokenId,
    payload.amount,
    ""
);
```

Per EIP-1155, `safeTransferFrom` to a contract address must call `onERC1155Received` and revert if the correct selector is not returned. If `payload.recipient` is a contract without `IERC1155Receiver` (e.g., Gnosis Safe, any DeFi protocol), the call reverts, unwinding the nonce mark. The nonce is therefore not permanently consumed, but the Borsh-encoded message signed by the MPC includes `payload.recipient` at line 298 and is verified at line 311:

```solidity
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

There is no on-chain mechanism to re-issue a signature with a corrected recipient. Every subsequent relay attempt with the same signed payload produces the same revert. The NEAR-side tokens were already consumed at `initTransfer1155` time (line 458: `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")`), and the bridge holds the EVM-side ERC1155 tokens with no release path. There is no `try/catch`, no fallback recipient, and no admin rescue function for this case.

## Impact Explanation

This directly matches the allowed Critical impact: **permanent freezing of bridged funds**. The NEAR-side tokens are consumed, the EVM-side tokens are held by the bridge contract with no release path, and the signed payload cannot be re-used with a different recipient. The user suffers a total, irrecoverable loss of their bridged ERC1155 assets.

## Likelihood Explanation

ERC1155 bridging is a fully supported, production feature (`initTransfer1155` / `finTransfer` with `multiTokens` mapping). No attacker capability is required — any unprivileged user who specifies a contract address as the EVM recipient triggers this path. Gnosis Safe (the most widely used multisig), account-abstraction wallets, and most DeFi contracts do not implement `IERC1155Receiver`. A user bridging ERC1155 tokens from NEAR to their multisig or protocol contract will permanently lose their funds. The condition is easily and unintentionally triggered.

## Recommendation

Wrap the `safeTransferFrom` call in a `try/catch` block. On failure, do not consume the nonce, emit a `FinTransferFailed` event, and preserve the signed payload for a subsequent rescue flow (e.g., admin-authorized alternative recipient or NEAR-side refund). Alternatively, add a protocol-level mechanism allowing MPC nodes to re-sign a `finTransfer` payload with a corrected recipient when the original finalization is provably impossible (e.g., after N failed relay attempts with on-chain evidence of revert).

## Proof of Concept

1. User holds ERC1155 token `T` (tokenId `42`) on NEAR (bridged from EVM via `initTransfer1155`).
2. User initiates a NEAR→EVM transfer specifying `recipient = address(GnosisSafe)` (a contract without `IERC1155Receiver`).
3. NEAR burns/locks the user's tokens and emits a cross-chain event.
4. Relayer calls `OmniBridge.finTransfer(sig, payload)` where `payload.tokenAddress` maps to the ERC1155 via `multiTokens`.
5. `completedTransfers[nonce] = true` is set (line 287), then `IERC1155(...).safeTransferFrom(bridge, GnosisSafe, 42, amount, "")` is called (line 324).
6. The ERC1155 contract calls `GnosisSafe.onERC1155Received(...)` — GnosisSafe does not implement it → reverts.
7. Entire `finTransfer` reverts; nonce is cleared.
8. Relayer retries with the same signed payload — identical revert every time.
9. User's NEAR-side tokens are gone; EVM-side tokens are locked in the bridge with no release path.

Local reproduction: deploy a mock ERC1155, a mock recipient contract without `IERC1155Receiver`, register the token via `logMetadata1155`, call `initTransfer1155` to deposit tokens, then call `finTransfer` with the mock recipient — observe the revert and confirm no rescue path exists.
