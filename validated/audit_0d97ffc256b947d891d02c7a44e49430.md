### Title
`validatePerasCert` Default Instance Accepts Any Certificate Without Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance, which applies to all block types including Cardano blocks, implements `validatePerasCert` as a function that unconditionally returns `Right` — accepting every certificate as valid without performing any cryptographic or structural verification. An unprivileged peer can submit a crafted Peras certificate boosting an arbitrary block, and the node will accept it as a `ValidatedPerasCert` and use it to influence chain selection.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate is stored and used to boost a block's chain-selection weight. The only instance in the codebase is the catch-all degenerate instance:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function takes any `PerasCert blk` and wraps it in `ValidatedPerasCert` with the full `perasWeight` boost, regardless of whether the certificate's aggregate BLS signature is valid, whether the claimed voters are eligible, or whether the boosted block point is coherent. No search of the repository found a more specific `BlockSupportsPeras` instance for `HardForkBlock`, `CardanoBlock`, or any Shelley-era block type, so this degenerate instance is the one compiled into production binaries.

The certificate then flows through the ObjectDiffusion pipeline:

The `ValidatedPerasCert` wrapper is the only guard between a raw peer-supplied certificate and chain selection. Because `validatePerasCert` always produces `Right ValidatedPerasCert`, that wrapper provides no security guarantee.

This is the direct analog of the external report: just as `transferFrom` was called but the resulting balance was never verified (allowing a fake transfer to be accepted), here `validatePerasCert` is called but always returns success regardless of the certificate's actual cryptographic content.

### Impact Explanation

**High — Chain selection manipulation.** A malicious peer can craft a `PerasCert` claiming to boost any block in the VolatileDB. Because `validatePerasCert` accepts it unconditionally, the certificate is stored with full `perasWeight` and `chainSelectionForBlock` is triggered for the boosted block. If the boosted block is on a fork, the node may switch away from the canonical chain to a non-canonical one, violating chain-selection safety beyond the intended security assumptions of Ouroboros Peras.

### Likelihood Explanation

The degenerate instance is the only `BlockSupportsPeras` instance in the repository and is compiled into all production binaries. The ObjectDiffusion mini-protocol for Peras certificates is a peer-facing network endpoint reachable by any unprivileged node. No stake, key material, or operator access is required. The attacker only needs to connect as a peer and send a well-formed CBOR-encoded `PerasCert` pointing at a block already present in the target node's VolatileDB.

### Recommendation

Replace the unconditional `Right` in `validatePerasCert` with actual verification logic before the Peras certificate pipeline is active in production. At minimum, the implementation must:

1. Verify the aggregate BLS signature over the claimed election ID and candidate block using the public keys of the claimed voters.
2. Confirm each claimed voter's eligibility against the current voting committee (stake threshold, seat index bounds).
3. Confirm the boosted block point is structurally valid (non-genesis, within the volatile window).

Until a real implementation is in place, the `addPerasCertAsync` / `addPerasVoteWithAsyncCertHandling` entry points should reject all inbound certificates at the network boundary rather than forwarding them to `validatePerasCert`.

### Proof of Concept

1. Connect to a target node as a peer via the ObjectDiffusion mini-protocol.
2. Identify a block hash `H` present in the node's VolatileDB on a minority fork (obtainable via the ChainSync protocol).
3. Construct a `PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint slot H }` with arbitrary round number `R`.
4. Wrap it in `WithArrivalTime` and send it via the Peras certificate diffusion channel.
5. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. `PerasCertDB.addCert` stores the certificate; `chainSelectionForBlock` is called for block `H`.
7. If the fork containing `H` now has sufficient Peras weight, the node switches to it, diverging from the canonical chain. [5](#0-4)

    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
