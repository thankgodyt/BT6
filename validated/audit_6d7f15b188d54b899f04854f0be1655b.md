### Title
Decimal Normalization Truncation to Zero Permanently Freezes User Funds in NEAR→EVM Transfers - (`File: near/omni-bridge/src/lib.rs`)

### Summary

`normalize_amount` uses integer floor division. When a user initiates a NEAR→EVM transfer with an amount (minus fee) smaller than `10^(origin_decimals - decimals)`, the normalized amount truncates to zero. `init_transfer_internal` burns or locks the user's tokens in one transaction, but the subsequent `sign_transfer` call always panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` because the normalized amount is 0. There is no cancel or refund path for init transfers, so the user's funds are permanently frozen.

### Finding Description

`normalize_amount` performs integer division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a token with `origin_decimals = 18` (EVM) and `decimals = 6` (NEAR), `diff_decimals = 12`, so any `amount_without_fee < 10^12` normalizes to `0`.

`init_transfer` only validates `fee.fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It does **not** validate that `normalize_amount(amount - fee, decimals) > 0`. It then calls `init_transfer_internal`, which burns (deployed tokens) or locks (native tokens) the user's funds and stores the transfer message.

Later, when a relayer calls `sign_transfer`:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);

require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This always panics for the affected transfer. Because the burn/lock happened in a prior transaction, the revert of `sign_transfer` does not restore the tokens. The transfer message remains in storage but can never be signed. There is no cancel or refund function for init transfers.

### Impact Explanation

User funds are permanently frozen. Tokens are burned (for deployed bridge tokens) or locked (for native tokens) in `init_transfer_internal` and can never be recovered because `sign_transfer` will always revert for this transfer. This matches the allowed critical impact: **permanent freezing of bridged funds**.

### Likelihood Explanation

Any unprivileged user who calls `ft_transfer_call` with an amount below the decimal normalization threshold triggers this. For tokens with large decimal differences (e.g., 18 EVM decimals normalized to 6 NEAR decimals, a factor of 10^12), any transfer of fewer than 10^12 base units (e.g., less than 1 USDC equivalent for a 6-decimal token) is affected. Users unfamiliar with the normalization factor can easily trigger this accidentally. The only on-chain guard (`fee < amount`) does not prevent it.

### Recommendation

Add a normalization check inside `init_transfer` before burning/locking tokens:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().unwrap_or(0),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

Alternatively, enforce a protocol-level minimum transfer amount that accounts for the worst-case decimal normalization factor at order creation time.

### Proof of Concept

1. A token is registered with `origin_decimals = 18`, `decimals = 6` (diff = 12, factor = 10^12).
2. User calls `ft_transfer_call` sending `amount = 500_000_000_000` (5 × 10^11, below 10^12) with `fee = 0`.
3. `init_transfer` passes the only check: `0 < 500_000_000_000`. ✓
4. `init_transfer_internal` burns the 500_000_000_000 base units and stores the transfer message.
5. Relayer calls `sign_transfer` for this transfer.
6. `normalize_amount(500_000_000_000, {origin_decimals:18, decimals:6}) = 500_000_000_000 / 10^12 = 0`.
7. `require!(0 > 0, ...)` panics → transaction reverts.
8. Tokens remain burned. Transfer message remains in storage. No recovery path exists.
