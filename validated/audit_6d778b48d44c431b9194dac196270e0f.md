Audit Report

## Title
Native ETH `finTransfer` Always Reverts Due to Incorrect `msg.value` Forwarding in `finTransferExtension` — (`evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

## Summary

`OmniBridgeWormhole.finTransferExtension` forwards the full `msg.value` to Wormhole's `publishMessage`, but when `payload.tokenAddress == address(0)`, the base `OmniBridge.finTransfer` has already spent `payload.amount` wei sending ETH to the recipient before `finTransferExtension` is invoked. The contract's remaining balance is only `msg.value - payload.amount`, so the Wormhole call reverts due to insufficient ETH. Every native ETH cross-chain finalization via the Wormhole path is permanently impossible, freezing the locked ETH on the source chain.

## Finding Description

In `OmniBridge.finTransfer`, when `payload.tokenAddress == address(0)`, `payload.amount` wei is sent to the recipient before `finTransferExtension` is called: [1](#0-0) 

Control then passes to `finTransferExtension`: [2](#0-1) 

In `OmniBridgeWormhole`, `finTransferExtension` forwards the full `msg.value` to Wormhole: [3](#0-2) 

`msg.value` in Solidity always reflects the value attached to the original external call — it does not decrease as ETH is spent within the call. After `payload.amount` has been forwarded to the recipient, the contract holds only `msg.value - payload.amount` wei. Attempting to forward `msg.value` to Wormhole will always revert with an out-of-funds error when `payload.amount > 0`.

By contrast, `initTransfer` correctly computes the residual value before passing it to `initTransferExtension`: [4](#0-3) 

And `initTransferExtension` uses that pre-computed residual: [5](#0-4) 

`finTransferExtension` lacks the equivalent subtraction, making the two paths asymmetric.

Note also that `completedTransfers[payload.destinationNonce] = true` is set at line 287 before the ETH transfer and extension call: [6](#0-5) 

Because the entire transaction reverts when `finTransferExtension` reverts, this state change is rolled back — the nonce is never consumed, and the call can be retried indefinitely, but every attempt will revert for the same reason.

## Impact Explanation

This directly causes **permanent freezing of bridged native ETH** routed through `OmniBridgeWormhole`. A user locks ETH on the source chain via `initTransfer(address(0), ...)`. Every relayer attempt to call `finTransfer` on the destination `OmniBridgeWormhole` reverts. There is no cancellation or withdrawal path visible in the contract. The source-chain ETH is irrecoverably locked. This matches the allowed Critical impact: *permanent freezing of bridged funds across Wormhole-routed flows*.

## Likelihood Explanation

Any user who calls `initTransfer(address(0), ...)` on a deployed `OmniBridgeWormhole` instance triggers the freeze. No special role or collusion is required. The Wormhole variant is deployed on Arbitrum and Base, where the native token is ETH, making this path reachable in production. The relayer is a legitimate actor following the normal bridge flow; no attacker capability beyond initiating a standard bridge transfer is needed.

## Recommendation

In `finTransferExtension`, compute the Wormhole fee as the ETH remaining after the recipient payment, mirroring the pattern used in `initTransferExtension`:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload
) internal override {
    uint256 wormholeFee = payload.tokenAddress == address(0)
        ? msg.value - payload.amount
        : msg.value;

    bytes memory messagePayload = bytes.concat(
        bytes1(uint8(MessageType.FinTransfer)),
        bytes1(payload.originChain),
        Borsh.encodeUint64(payload.originNonce),
        bytes1(omniBridgeChainId),
        Borsh.encodeAddress(payload.tokenAddress),
        Borsh.encodeUint128(payload.amount),
        Borsh.encodeString(payload.feeRecipient)
    );
    // slither-disable-next-line reentrancy-eth
    _wormhole.publishMessage{value: wormholeFee}(
        wormholeNonce,
        messagePayload,
        _consistencyLevel
    );

    wormholeNonce++;
}
```

## Proof of Concept

1. Deploy `OmniBridgeWormhole` on Arbitrum Sepolia with a mock Wormhole contract that charges a fixed `wormholeFee`.
2. Call `initTransfer(address(0), 1 ether, 0, nativeFee, recipient, "")` with `msg.value = 1 ether + nativeFee + wormholeFee`. ETH is locked in the source-chain contract.
3. Obtain a valid NEAR bridge signature for the corresponding `TransferMessagePayload` with `tokenAddress == address(0)` and `amount == 1 ether`.
4. A relayer calls `finTransfer(sig, payload)` attaching `msg.value = 1 ether + wormholeFee` (the minimum needed: `payload.amount` for the recipient plus `wormholeFee` for Wormhole).
5. `OmniBridge.finTransfer` sends `1 ether` to the recipient — contract balance drops to `wormholeFee`.
6. `finTransferExtension` attempts `_wormhole.publishMessage{value: msg.value}` = `{value: 1 ether + wormholeFee}` — reverts because only `wormholeFee` remains.
7. The entire transaction reverts; the source-chain ETH remains permanently locked with no recovery path.
