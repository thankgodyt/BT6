Audit Report

## Title
`swap_migrated_token` Executes Non-Atomic Burn-and-Mint with Detached Promise, Causing Permanent Token Loss on Mint Failure — (File: `near/omni-bridge/src/lib.rs`)

## Summary

The `swap_migrated_token` function schedules a `burn.and(mint)` promise pair and immediately `.detach()`es it, so the bridge never inspects the outcome. Because NEAR cross-contract calls execute as independent receipts with no atomicity guarantee, a successful `burn` is never rolled back if the subsequent `mint` panics. Any user who is not storage-registered in the new token contract will permanently lose their entire old-token balance with no refund path.

## Finding Description

**Step 1 — Bridge retains all tokens and detaches the swap promise.**

In `ft_on_transfer` (lines 275–279), when `msg = "SwapMigratedToken"`, the bridge returns `U128(0)` to the old token contract, meaning it keeps all transferred tokens. The swap promise is immediately `.detach()`ed:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

There is no callback registered on the detached promise; the bridge will never learn whether the swap succeeded or failed.

**Step 2 — Burn and mint are independent, non-atomic receipts.**

`swap_migrated_token` (lines 2738–2753) constructs two independent cross-contract calls joined with `Promise::and()`:

```rust
let burn = ext_token::ext(old_token).burn(amount);
let mint = ext_token::ext(new_token).mint(sender_id, amount, None);
burn.and(mint)
```

In NEAR's execution model, `Promise::and()` schedules both sub-promises as separate action receipts. They execute independently; a failure in `mint` does not roll back the already-committed `burn` receipt.

**Step 3 — `mint` panics for unregistered accounts.**

`OmniToken::mint` with `msg = None` (lines 140–143) calls:

```rust
self.token.internal_deposit(&account_id, amount.into());
```

`internal_deposit` panics if `account_id` has no storage registration in the token contract.

**Step 4 — `migrate_deployed_token` only registers the bridge itself.**

`migrate_deployed_token` (lines 1651–1655) calls `storage_deposit` exclusively for `env::current_account_id()` (the bridge):

```rust
ext_token::ext(new_token.clone())
    .storage_deposit(&env::current_account_id(), Some(true))
    .detach();
```

Individual token holders are never registered in the new token contract by this flow.

**Result:** The old tokens are burned from the bridge's balance (which received them via the `U128(0)` return), the mint panics, and the bridge — having detached the promise — never detects the failure. The user's funds are permanently destroyed.

## Impact Explanation

This is a **Critical** impact: permanent, irreversible loss of bridged funds on NEAR. Any holder of old (migrated) tokens who has not previously registered in the new token contract will lose their entire balance when attempting the intended swap. The loss is caused entirely by the bridge contract's own logic — no external dependency is required. This matches the allowed impact class: *"loss … or permanent freezing of bridged funds."*

## Likelihood Explanation

`migrate_deployed_token` is a DAO-only setup step, but the vulnerable swap path is fully open to any unprivileged user. The failure condition — not being storage-registered in the new token — is the default state for any user who acquired old tokens before the migration or who simply never interacted with the new token contract. This is a realistic and common scenario, not an edge case. The exploit is repeatable for every such user and requires no special capability beyond holding old tokens.

## Recommendation

1. **Add a callback**: Replace `.detach()` with a proper callback on `burn.and(mint)`. In the callback, if either sub-promise failed, re-mint the old tokens back to the user or transfer them from the bridge's retained balance.
2. **Sequential approach**: Burn in the first call, then mint in a callback; if the mint fails, transfer the old tokens back to the user from the bridge's balance (which still holds them at that point).
3. **Pre-register the user**: Before burning, call `storage_deposit` for `sender_id` on the new token contract as part of the swap flow, funded by an attached deposit from the user or from protocol reserves.

## Proof of Concept

1. DAO calls `migrate_deployed_token(origin_chain, old_token, new_token)`. Bridge is registered in `new_token`; no users are.
2. User holds `N` units of `old_token` and has never called `storage_deposit` on `new_token`.
3. User calls `old_token.ft_transfer_call(bridge_account, N, None, "\"SwapMigratedToken\"")`.
4. Bridge's `ft_on_transfer` returns `U128(0)` — bridge now holds `N` old tokens.
5. Detached promise fires: `old_token.burn(N)` succeeds (bridge's balance is withdrawn); `new_token.mint(user, N, None)` panics inside `internal_deposit` because user has no storage registration.
6. No callback exists; bridge state is unchanged except the old tokens are gone. User receives nothing.
7. **Verification**: A local integration test using `near-workspaces-rs` can deploy both token contracts (without registering the test user in `new_token`), execute the `ft_transfer_call`, await all receipts, and assert that the user's balance in both `old_token` and `new_token` is zero while the total supply of `old_token` decreased by `N` and `new_token` total supply is unchanged.
