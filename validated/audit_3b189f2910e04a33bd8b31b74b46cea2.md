### Title
Unconditional Peras Certificate Acceptance Bypasses Certificate Validation, Enabling Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production Peras certificate inbound pipeline calls `validatePerasCert` to authenticate certificates received from peers before adding them to the `PerasCertDB` and triggering chain selection. However, the universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right` — accepting every certificate regardless of its content. An unprivileged peer can therefore send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block in the VolatileDB, causing the victim node to run chain selection for that block with an artificial weight boost, potentially switching to a non-canonical fork.

---

### Finding Description

**Analog to the external report:** The flash loan vulnerability's root cause is that `receiveFlashLoan` checks the immediate caller (the flash loan module) but not whether the flash loan was initiated by the contract itself, allowing an attacker to inject arbitrary `userData` into the callback. The analog here is that `processCerts` checks that the certificate arrived through the proper miniprotocol channel (ObjectDiffusion), but the actual content validation — `validatePerasCert` — is a stub that always returns `Right`, allowing any peer to inject a certificate with arbitrary content.

**Root cause — `validatePerasCert` is a no-op stub:**

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` with `pcCertBoostedBlock` pointing to any block currently in the victim's VolatileDB (i.e., any recently received but not yet immutable block). Because `validatePerasCert` always returns `Right`, the certificate is accepted without any cryptographic or committee-membership check. The certificate is stored in the `PerasCertDB` and `chainSelectionForBlock` is triggered for the boosted block. The Peras weight boost (`perasWeight params`) is applied to that block's chain, potentially making a minority fork heavier than the current selection and causing the node to switch chains.

This is a **Critical** bypass of Peras certificate validation that enables unauthorized certificate acceptance and chain selection manipulation by any unprivileged peer.

---

### Likelihood Explanation

The `PerasCertDiffusion` miniprotocol is a standard node-to-node protocol available to every connected peer. No special privileges, keys, or stake are required. Any peer that can establish a connection can send a crafted certificate. The attack requires only knowledge of a block hash present in the victim's VolatileDB, which is publicly observable via the ChainSync protocol.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic and committee-membership validation before the Peras certificate diffusion protocol is enabled in production. At minimum, until real validation is implemented, the inbound handler should reject all certificates (return `Left` unconditionally) rather than accept all of them. The TODO at `https://github.com/tweag/cardano-peras/issues/120` tracks this work and must be resolved before the feature is activated.

---

### Proof of Concept

1. Attacker connects to victim node as a peer (standard node-to-node connection).
2. Attacker observes a block hash `H` on a minority fork via ChainSync.
3. Attacker sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = H }` via the `PerasCertDiffusion` miniprotocol.
4. Victim's `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
5. Certificate is stored in `PerasCertDB` and `addPerasCertAsync` is called.
6. `chainSelSync` finds block `H` in the VolatileDB and calls `chainSelectionForBlock` with the boosted weight.
7. If the boosted chain is now heavier than the current selection, the victim switches to the attacker's preferred fork.
