Audit Report

## Title
`locked_tokens` Escrow Mis-Accounting via Silent `send_tokens` Failure in Fast-Transfer Finalization — (File: `near/omni-bridge/src/lib.rs`)

## Summary

In `process_fin_transfer_to_other_chain`, the bridge irrevocably mutates its `locked_tokens` escrow ledger and permanently marks a fast transfer as finalised before dispatching the relayer reimbursement via `send_tokens(...).detach()`. Because the cross-contract call is detached with no success callback, any failure of the underlying `ft_transfer` is silently swallowed. This contrasts directly with the NEAR-recipient path (`process_fin_transfer_to_near`), which correctly wraps `send_tokens` in a `fin_transfer_send_tokens_callback` that calls `revert_lock_actions` on failure.

## Finding Description

`process_fin_transfer_to_other_chain` (lines 1980–2054) performs three irreversible state mutations before or immediately after dispatching the token transfer:

1. `unlock_tokens_if_needed(origin_chain, token, amount)` — decrements `locked_tokens[(origin, token)]`
2. `lock_tokens_if_needed(destination_chain, token, fee)` — increments `locked_tokens[(dest, token)]`
3. `send_tokens(...).detach()` — fires the cross-contract `ft_transfer` with no callback
4. `mark_fast_transfer_as_finalised(...)` — permanently sets `status.finalised = true` [1](#0-0) 

For non-deployed (locked) tokens, `send_tokens` with an empty `msg` issues an NEP-141 `ft_transfer`: [2](#0-1) 

`ft_transfer` panics — and thus the promise fails — if the recipient has no storage registered on the token contract, or if the token contract enforces a blacklist (USDC, USDT). Because the call is `.detach()`-ed, the bridge never observes the failure.

The NEAR-recipient path (`process_fin_transfer_to_near`) demonstrates the correct pattern: it saves the `LockAction` returned by `unlock_tokens_if_needed`, passes it to `fin_transfer_send_tokens_callback`, and calls `revert_lock_actions` on failure: [3](#0-2) [4](#0-3) [5](#0-4) 

`revert_lock_actions` correctly inverts each `LockAction`: [6](#0-5) 

No equivalent revert path exists in `process_fin_transfer_to_other_chain`.

## Impact Explanation

When `send_tokens` fails silently:

- **`locked_tokens[(origin, token)]`** is permanently decremented by `amount` even though the relayer never received the tokens. The bridge's escrow record now claims fewer tokens are locked on the origin chain than actually are, directly corrupting the invariant that `locked_tokens` equals the bridge's real on-chain holdings.
- **`locked_tokens[(dest, token)]`** is permanently incremented by `fee` even though no fee transfer occurred, inflating the destination-chain escrow counter.
- **The fast transfer is permanently marked as finalised**, so the relayer can never retry the reimbursement.
- **The relayer loses their pre-funded tokens.** They transferred their own tokens to the recipient during the fast transfer and are entitled to reimbursement during finalization. With the transfer silently failing and the state permanently committed, those tokens are unrecoverable.

The corrupted `locked_tokens` ledger propagates to all future bridge operations: subsequent `fin_transfer` calls from the origin chain will hit `ERR_INSUFFICIENT_LOCKED_TOKENS` for amounts that should be valid, and the inflated destination counter misrepresents the bridge's solvency on that chain. This matches the allowed critical impact: **escrow mis-accounting that changes user or protocol balances** and **permanent freezing of bridged funds**. [7](#0-6) 

## Likelihood Explanation

The bridge explicitly supports USDC and USDT as collateral tokens, both of which implement NEP-141 blacklists. If a relayer's NEAR account is blacklisted by the token issuer between the time they execute a fast transfer and the time `fin_transfer` is called, `ft_transfer` will panic and the promise will fail. Because the call is detached, the bridge never detects this. The same failure occurs if the relayer's account lacks storage registration on the specific token contract at finalization time (e.g., the relayer transferred all their tokens out and unregistered storage between the fast transfer and finalization). Both conditions are reachable without any admin compromise and are known operational characteristics of USDC/USDT.

## Recommendation

Replace the fire-and-forget `.detach()` pattern with a callback that reverts the `locked_tokens` mutations and un-finalises the fast transfer if `send_tokens` fails, mirroring the existing `fin_transfer_send_tokens_callback` / `revert_lock_actions` pattern already used in the NEAR-recipient path.

Concretely:
1. Capture the `LockAction`s returned by `unlock_tokens_if_needed` and `lock_tokens_if_needed`.
2. Introduce a new `#[private]` callback (e.g., `resolve_fin_transfer_to_other_chain_callback`) that receives the `LockAction`s, the fast transfer ID, and the transfer message.
3. In the callback, check the promise result; on failure, call `revert_lock_actions` and un-mark the fast transfer as finalised (or remove it from the finalised set).
4. Chain `send_tokens(...).then(Self::ext(...).resolve_fin_transfer_to_other_chain_callback(...))` instead of `.detach()`. [8](#0-7) 

## Proof of Concept

1. Token is a non-deployed NEP-141 (e.g., USDC) with a blacklist. `locked_tokens[(Eth, usdc)]` = 1,000,000.
2. Relayer calls `ft_transfer_call` → `fast_fin_transfer` → `fast_fin_transfer_to_near_callback` → sends 999,000 USDC to recipient. Fast transfer recorded with `relayer = relayer.near`.
3. Circle blacklists `relayer.near` on the USDC contract.
4. Any trusted relayer submits the EVM receipt to `fin_transfer`. `fin_transfer_callback` routes to `process_fin_transfer_to_other_chain`.
5. `unlock_tokens_if_needed(Eth, usdc, 1,000,000)` → `locked_tokens[(Eth, usdc)]` = 0. Committed.
6. `lock_tokens_if_needed(destination, usdc, fee)` → `locked_tokens[(dest, usdc)]` += fee. Committed.
7. `send_tokens(usdc, relayer.near, 999,000, "").detach()` → USDC `ft_transfer` panics (blacklisted). Promise fails. Bridge never sees the failure.
8. `mark_fast_transfer_as_finalised(...)` → fast transfer permanently finalised.
9. Result: `locked_tokens[(Eth, usdc)]` = 0 (should still be 1,000,000 held by bridge), relayer lost 999,000 USDC, fast transfer cannot be retried. [9](#0-8)

    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }

    pub fn revert_lock_actions(&mut self, lock_actions: &[LockAction]) {
        for lock_action in lock_actions {
            match lock_action {
                LockAction::Locked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.unlock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unlocked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.lock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unchanged => {}
            }
        }
    }
