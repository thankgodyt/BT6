### Title
Peras Chain-Weight Underestimation in `checkPreferTheirsOverOurs` Causes Incorrect Chain Selection Disconnection - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs)

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client evaluates whether a candidate chain is preferred over the local chain using a hardcoded `emptyPerasWeightSnapshot`, completely ignoring any Peras weight boosts on the candidate. This mirrors the Sushi `balanceOfToken` pattern exactly: a two-step pessimistic formula is used where a direct, accurate formula is available. The result is that a candidate chain whose total Peras weight exceeds the local chain's weight — but whose raw block count does not — is incorrectly judged as non-preferred, causing the node to disconnect from the peer and permanently miss adopting the heavier canonical chain.

### Finding Description

`checkPreferTheirsOverOurs` is invoked when a header from an upstream peer falls beyond the forecast horizon. Its purpose is to decide whether to keep the connection open (candidate is preferred) or disconnect (candidate is not preferred). The implementation is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero weight boost
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
```

`preferAnchoredCandidate` with a non-empty `PerasWeightSnapshot` computes the comparison over the suffix after the intersection, using `weightedSelectView` which sums `wsvBlockNo + wsvWeightBoost`. With `emptyPerasWeightSnapshot`, `weightBoostOfFragment` always returns `mempty`, so `wsvTotalWeight` reduces to block count alone.

Consider a concrete scenario:
- **Local chain**: 100 blocks, 0 Peras boosts → total weight = 100
- **Candidate chain**: 99 blocks, 2 Peras boosts of weight 1 each → total weight = 101

The candidate is canonically heavier. But `checkPreferTheirsOverOurs` compares 99 vs 100 (block count only), concludes the candidate is not preferred, and throws `CandidateTooSparse`, disconnecting from the peer. The node never adopts the heavier chain.

The Sushi analog is exact: `balanceOfToken` computed `balances[addr] * sushiBalance / sourceShares` (two-step, underestimates) instead of `balances[addr] * ISushi(sushiAddr).balanceOf(sushiBar) / totalShares` (direct, accurate). Here, `emptyPerasWeightSnapshot` plays the role of the pessimistic intermediate step — it discards the boost component that would make the candidate's weight accurate.

### Impact Explanation

When a peer's candidate chain has Peras boosts that push its total weight above the local chain's weight, but its raw block count is lower, `checkPreferTheirsOverOurs` incorrectly disconnects from that peer. The node remains on a chain with lower total Peras weight — a less-secure chain under the Peras security model. In Peras, total weight (block count + boost) is the canonical chain-selection metric; a node that ignores boosts in this check can be made to permanently prefer a lighter chain over the canonical heavier one. This satisfies the **High** impact criterion: a chain-selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical, less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

Any peer whose chain has received legitimate Peras certificate boosts — but whose block count is momentarily behind the local chain — can trigger this path simply by serving a header that falls beyond the forecast horizon (a large slot gap, which is normal during low-density periods). No key compromise, stake majority, or privileged access is required. The peer need only be a standard Peras-participating node whose chain happens to be in this configuration. The TODO comment acknowledges the check is known-problematic (`https://github.com/tweag/cardano-peras/issues/64`), confirming the developers recognise the issue exists in production code.

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` obtained from the `PerasCertDB` (the same snapshot used in `chainSelectionForBlock` and `initialChainSelection`). The comparison should mirror the full `preferAnchoredCandidate` call used elsewhere in chain selection, so that Peras boosts are accounted for when deciding whether to keep or drop a peer connection. The linked issue (`#64`) proposes removing the check entirely; if that is the chosen resolution, the removal must happen before Peras is activated on any network where the weight-boost parameter is non-zero.

### Proof of Concept

1. Node A (honest) has a local chain of 100 blocks, no Peras boosts; total weight = 100.
2. Node B (peer, no special privileges) has a chain of 99 blocks with two Peras certificates each granting boost weight 1; total weight = 101.
3. Node B serves a header to Node A whose slot falls beyond Node A's forecast horizon, triggering `checkPreferTheirsOverOurs`.
4. `preferAnchoredCandidate … emptyPerasWeightSnapshot ourFrag theirFrag` compares block counts: 100 vs 99 → `ShouldNotSwitch`.
5. Node A throws `CandidateTooSparse` and disconnects from Node B.
6. Node A remains on its 100-weight chain; the canonical 101-weight chain is never adopted.
7. Any subsequent block built on Node B's chain extends the weight gap, making Node A's chain progressively less secure relative to the canonical chain. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
