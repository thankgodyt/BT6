Based on my review of the actual code, I can now validate this claim.

**Key findings confirmed:**

1. **EVM `deployToken`** (`OmniBridge.sol` L142-148): Hash = `PayloadType.Metadata | encodeString(token) | encodeString(name) | encodeString(symbol) | bytes1(decimals)` — no chain ID.

Audit Report

## Title
`deployToken`/`deploy_token` MetadataPayload Signature Lacks Chain Binding, Enabling Cross-Chain Replay — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/omni_bridge.cairo`)

## Summary
The Borsh-encoded hash used to authorize token deployments in `deployToken` (EVM) and `deploy_token` (Starknet) contains no destination chain identifier. Both chains share the same NEAR MPC-derived signing key and produce byte-for-byte identical hash inputs for the same `(token, name, symbol, decimals)` tuple. A valid signature extracted from a public `deployToken` transaction on EVM can be replayed verbatim on Starknet, deploying the token on Starknet without any MPC authorization for that chain and permanently blocking the legitimate deployer.

## Finding Description

**EVM root cause (`OmniBridge.sol` L142–153):**
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```
No `omniBridgeChainId` is included.

**Starknet root cause (`bridge_types.cairo` L36–44):**
```cairo
fn to_borsh(self: @MetadataPayload) -> ByteArray {
    borsh_bytes.append_byte(PayloadType::Metadata.into()); // 0x01
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
}
```
`to_borsh()` takes no `chain_id` parameter; `deploy_token` calls it as `payload.to_borsh()` with no argument (`omni_bridge.cairo` L205).

**Contrast with `fin_transfer`:** `TransferMessagePayload.to_borsh(chain_id: u8)` embeds `chain_id` at two positions (`bridge_types.cairo` L67, L70). EVM `finTransfer` embeds `omniBridgeChainId` twice (`OmniBridge.sol` L294, L297). The `deployToken` path has no equivalent binding.

**Encoding equivalence:** Both `Borsh.encodeString` (EVM) and `borsh::encode_byte_array` (Starknet) produce standard Borsh wire format: 4-byte LE length prefix + raw UTF-8 bytes. The `PayloadType::Metadata` discriminant is `0x01` on both chains. Hash inputs are byte-for-byte identical for the same `(token, name, symbol, decimals)` tuple.

**NEAR signing:** `MetadataPayload` in `near/omni-types/src/lib.rs` has no chain ID field. The MPC signs the same payload regardless of which destination chain the deployment is intended for, using a single fixed `SIGN_PATH`.

**Exploit path:**
1. Attacker observes a confirmed `deployToken(signatureData, metadata)` call on EVM (fully public calldata).
2. Attacker extracts `signatureData` and `metadata`.
3. Attacker calls `deploy_token(signature, payload)` on Starknet with identical values.
4. `_verify_borsh_signature` passes: hash is identical, signing key is the same.
5. Token is deployed and `near_to_starknet_token[token_id_hash]` is permanently written (`omni_bridge.cairo` L224–225).
6. Every subsequent legitimate `deploy_token` call for the same NEAR token ID reverts with `ERR_TOKEN_ALREADY_DEPLOYED` (`omni_bridge.cairo` L209).

**Existing checks are insufficient:** The only guard in `deploy_token` is the duplicate-deployment check (`existing_token.is_zero()`), which the attacker's replay satisfies on first call. There is no nonce, no chain binding, and no access control on `deploy_token`.

## Impact Explanation

This is a **cross-chain replay / chain-domain separation flaw** and an **authorization bypass** allowing an unprivileged attacker to execute token-deployer-equivalent actions on Starknet using a signature the MPC issued only for EVM. Concretely:

- **Authorization bypass**: The MPC authorized deployment on chain A; the attacker uses that authorization to deploy on chain B without any additional MPC approval.
- **Permanent blocking**: Once the replay succeeds, `near_to_starknet_token` is permanently populated. The legitimate deployer can never deploy the canonical version of that token on Starknet; every attempt reverts with `ERR_TOKEN_ALREADY_DEPLOYED`.
- **Unauthorized bridge token creation**: The attacker-deployed contract on Starknet is controlled by the bridge, which will mint tokens into it during `fin_transfer` calls. The token owner has no control over when or whether their token appears on Starknet.

This matches the allowed critical impact: *"Cross-chain replay … or chain/domain separation flaw enabling invalid finalization"* and *"authorization bypass … that lets an attacker execute … token deployer … actions."*

## Likelihood Explanation

**High.** The attack requires zero privileged access. All inputs (signature bytes and metadata payload) are visible in the calldata of any public `deployToken` transaction on EVM. The replay is a single contract call on Starknet. Any NEAR token that has been deployed on EVM but not yet on Starknet is permanently at risk from the moment its EVM deployment transaction is confirmed. The attack is repeatable for every such token.

## Recommendation

Include the destination chain ID in the `MetadataPayload` hash, mirroring the pattern already used in `finTransfer`/`fin_transfer`.

**EVM (`OmniBridge.sol`):**
```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // add chain binding
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

**Starknet (`bridge_types.cairo`):**
```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);   // add chain binding
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    ...
}
```
And update `deploy_token` to call `payload.to_borsh(self.omni_bridge_chain_id.read())`.

**NEAR signing:** Update `MetadataPayload` to include a `destination_chain` field and include it in the Borsh-serialized payload before MPC signing, so each signature is cryptographically bound to a single destination chain.

## Proof of Concept

**Minimal test plan (local fork / Starknet devnet):**

1. Deploy both the EVM `OmniBridge` (chain ID = 1) and the Starknet `OmniBridge` (chain ID = 2) with the same `nearBridgeDerivedAddress` / `omni_bridge_derived_address`.
2. On EVM, call `deployToken(sig, {token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6})` with a valid MPC-derived signature. Record `sig` from calldata.
3. On Starknet, call `deploy_token(sig, {token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6})` using the identical `sig` extracted from step 2.
4. Assert the call succeeds (no `InvalidSignature` revert) and `get_token_address("usdc.near")` returns a non-zero address.
5. Attempt a legitimate `deploy_token` call on Starknet with a freshly MPC-signed payload for the same token; assert it reverts with `ERR_TOKEN_ALREADY_DEPLOYED`.

The existing test helper `build_deploy_token_message` in `starknet/tests/test_contract.cairo` (L83–92) confirms the hash structure and can be used directly to construct the replayed call.
