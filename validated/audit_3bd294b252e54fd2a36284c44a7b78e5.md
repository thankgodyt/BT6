### Title
Peras Certificate Validation Stub Unconditionally Accepts All Certificates, Enabling Cooldown Bypass via Adversarial Certificate Injection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the `BlockSupportsPeras` instance is a stub that unconditionally accepts every certificate without performing any cryptographic or semantic validation. An unprivileged peer can exploit this via the ObjectDiffusion mini-protocol to inject a crafted certificate with an arbitrary round number into the local node's `PerasCertDB`. Because `latestCertSeen` is derived directly from this database, the adversary can manipulate the inputs to the Peras voting rules (VR-1A, VR-1B, VR-2A) and cause a node that is in a cooldown period to vote prematurely — bypassing the cooldown mechanism entirely.

---

### Finding Description

The Peras protocol enforces a cooldown period after a failed quorum round. A node may only resume voting when either:
- **VR-1**: it has seen the certificate for the immediately preceding round in time (VR-1A) and the candidate block extends the most recently certified block (VR-1B), or
- **VR-2**: the last certificate seen is at least R (`PerasIgnoranceRounds` = 487) rounds old (VR-2A) **and** the last certificate on chain is exactly c·K (`PerasCooldownRounds` = 1928) rounds old (VR-2B).

The `latestCertSeen` input to these rules is read directly from `PerasCertDB.getLatestCertSeen`, which returns the certificate with the highest round number ever added to the database.

Certificates are added to the database via `processCerts` in `PerasCert.hs`, which calls `validatePerasCert` to validate each inbound certificate before storing it. However, the production implementation of `validatePerasCert` is a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This stub accepts every certificate unconditionally, regardless of cryptographic validity, committee membership, quorum threshold, or round number plausibility.

An adversary peer can therefore:

1. Send a crafted `PerasCert` with `pcCertRound = currRoundNo - 1` and `pcCertBoostedBlock` pointing to any block in the immutable prefix (which is treated as vacuously extending the chain by `candidateBlockExtendsCert`).
2. `processCerts` calls `validatePerasCert mkPerasParams` → always `Right` → certificate is stored.
3. `pcdsLatestCertSeen` in `PerasCertDbState` is updated to this certificate (since its round number is the highest seen).
4. When the victim node evaluates voting rules, `latestCertSeen = NotOrigin cert` with `getPerasCertRound cert = currRoundNo - 1`.
5. VR-1A1 passes: `currRoundNo == (currRoundNo - 1) + 1`.
6. VR-1A2 passes: arrival time is stamped as `now` (wall clock), and the round start slot is computed from the injected round number.
7. VR-1B passes: `lcsCandidateBlockExtendsCert = True` because the boosted block is in the immutable prefix (`CertWithImmutableBlock`).
8. The node votes via VR-1, bypassing the cooldown entirely.

This is the direct analog of the `recoverUnstaking()` no-cooldown bug: just as a staker could cycle between unstaked and staked states to selectively participate in reward distributions without waiting for the cooldown, an adversary here can inject a fake certificate to make a node in cooldown selectively vote in any round of their choosing.

---

### Impact Explanation

This is a **bypass of Peras voting certificate verification checks**. The cooldown period is a core safety property of the Peras protocol: it ensures sufficient chain quality and common prefix have been established before voting resumes after a failed quorum. Premature voting caused by adversarial certificate injection can:

- Cause a node to cast votes for blocks that do not satisfy the chain-quality and common-prefix requirements of the cooldown exit conditions.
- If multiple nodes are simultaneously manipulated (e.g., by broadcasting the crafted certificate to all peers), contribute to an unauthorized quorum that boosts a block that should not be boosted.
- Undermine the Peras finality guarantee, since the boosted block's weight advantage is predicated on the cooldown having been properly observed.

This falls under: **Critical — Bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance.**

---

### Likelihood Explanation

The attack path is fully reachable from an unprivileged peer with no special privileges:

1. The ObjectDiffusion mini-protocol is a standard peer-to-peer protocol open to any connected peer.
2. `processCerts` is called for every batch of inbound certificates received via this protocol.
3. The stub `validatePerasCert` is the only gate between a peer-supplied certificate and the `PerasCertDB`.
4. No stake, key material, or operator access is required.

The only constraint is that the adversary must be a connected peer, which is the normal operating condition of any Cardano node.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real implementation that validates:
- Cryptographic signatures over the certificate (BLS aggregate signature or equivalent).
- That the signing committee was legitimately elected for the claimed round.
- That the quorum stake threshold was met.
- That the boosted block exists and is consistent with the claimed round.
- That the round number is within a plausible range relative to the current chain tip.

Until this is done, the `PerasCertDB` should not be used as the source of `latestCertSeen` for voting rule evaluation in any environment where adversarial peers are possible.
