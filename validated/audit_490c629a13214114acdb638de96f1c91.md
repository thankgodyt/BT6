### Title
Unchecked `.detach()` on `burn()` in `safe_mint_callback` Enables Silent Failure and Re-Deposit Double-Mint — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when the `safe_mint` flow determines that minted tokens must be burned back (because the receiver returned them unused), the bridge fires the `burn()` cross-contract call with `.detach()`. The result is never observed. If the burn fails for any reason, the UTXO is simultaneously removed from the `verified_deposit_utxo` replay-protection set, leaving the bridge with unbacked nBTC tokens and an open UTXO slot that can be re-submitted for a second mint.

---

### Finding Description

`safe_mint_callback` is the `#[private]` callback that runs after `safe_mint` completes on the nBTC contract. It calls `is_refund_required()` to decide whether the minted tokens need to be burned back. [1](#0-0) 

When `is_success` is `false` (i.e., `safe_mint` returned `U128(0)`, meaning the receiver returned all tokens unused and they are now back in the bridge's account), the function:

1. **Removes the UTXO from the replay-protection set** (`verified_deposit_utxo`): [2](#0-1) 

2. **Fires `burn()` with `.detach()`** — the promise result is never checked: [3](#0-2) 

3. **Fires `Promise::transfer()` with `.detach()`** — the NEAR storage-deposit refund is also unchecked: [4](#0-3) 

The `burn()` function on the nBTC contract calls `internal_withdraw` against the bridge's own balance: [5](#0-4) 

If `burn()` panics or runs out of gas, the failure is silently swallowed because `.detach()` discards the promise result. At that point:

- The UTXO is **not** in `verified_deposit_utxo` (it was removed in step 1).
- The UTXO is **not** in the active UTXO set (it was never added, since `is_success` was `false`).
- The nBTC tokens are **still in the bridge's account** (the burn did not execute).

Because `verified_deposit_utxo` no longer contains the UTXO key, a subsequent call to `verify_deposit` (or `safe_verify_deposit`) with the same Bitcoin transaction passes the replay-protection check: [6](#0-5) 

A second successful deposit flow then mints a fresh batch of nBTC tokens to the recipient **and** stores the UTXO in the active set — while the first (unburned) batch of tokens already sits in the bridge account. The result is two units of nBTC backed by one BTC UTXO.

The `is_refund_required` logic confirms that the only path that triggers the burn is when `safe_mint` returned `U128(0)`: [7](#0-6) 

And `safe_mint` returns `U128(0)` when the recipient account does not exist (early return) or when `ft_resolve_transfer` resolves to 0 used tokens: [8](#0-7) 

---

### Impact Explanation

**Critical.** A silent burn failure leaves unbacked nBTC tokens in the bridge's account and reopens the UTXO for re-deposit. A second successful `safe_verify_deposit` call for the same Bitcoin UTXO mints a second batch of nBTC, producing circulating supply that exceeds the BTC held by the bridge. This is an unauthorized reminting / supply-inflation attack that directly violates the bridge's 1:1 backing invariant.

---

### Likelihood Explanation

**Medium.** The burn failure requires the nBTC `burn()` call to fail after `safe_mint_callback` has already removed the UTXO from the replay set. Realistic triggers include:

- Gas exhaustion in the callback: `safe_mint_callback` is allocated `GAS_FOR_MINT_CALL_BACK` gas; if the preceding `safe_mint` chain consumed more gas than expected, the remaining budget for the detached `burn()` call may be insufficient.
- A future nBTC contract upgrade that introduces a panic path in `burn()`.
- Any transient condition that causes the nBTC contract to reject the call.

Because the failure is silent and the UTXO slot is immediately reopened, an attacker who can observe the failed burn (e.g., by watching on-chain events or the absence of a burn event) can immediately re-submit the deposit proof.

---

### Recommendation

Replace the fire-and-forget `.detach()` pattern on the `burn()` call with a chained callback that checks the result, analogous to how `safe_mint_callback` itself is chained after `safe_mint`. If the burn fails, the callback should either re-insert the UTXO into `verified_deposit_utxo` (to prevent re-deposit) or panic to surface the error. The NEAR SDK's `Promise` chaining with a `#[private]` callback is the correct analog to OpenZeppelin's `Address.sendValue` / result-checked `.call()` recommended in the external report.

Similarly, the `Promise::transfer(...).detach()` storage-deposit refund should be checked or replaced with a pattern that guarantees the refund reaches the correct account.

---

### Proof of Concept

1. Attacker (or any user) calls `safe_verify_deposit` for a valid BTC UTXO, attaching the required storage deposit. The BTC light client confirms the transaction.
2. `safe_mint_callback` runs. `safe_mint` returns `U128(0)` (e.g., because the recipient account is not registered in the nBTC contract, triggering the early-return path at `nbtc/src/lib.rs:114-116`).
3. `is_refund_required()` returns `true`. The callback removes the UTXO from `verified_deposit_utxo` and fires `burn(...).detach()`.
4. The `burn()` call fails silently (e.g., gas exhaustion). No burn event is emitted. The nBTC tokens remain in the bridge's account.
5. The attacker (or any relayer) calls `safe_verify_deposit` again with the same `tx_bytes` and `vout`. The replay-protection check at line 369-374 passes because `verified_deposit_utxo` no longer contains the key.
6. A second `safe_mint` executes successfully (this time the recipient is registered). Fresh nBTC tokens are minted to the recipient and the UTXO is stored in the active set.
7. Result: two batches of nBTC in circulation backed by one BTC UTXO — unbacked supply inflation.

    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                // Normal case: refund if the used token amount is zero
                // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                amount.0 == 0
            } else {
                // Unexpected case: don't refund
                false
            }
        }
        // Unexpected case: don't refund
        Err(_) => false,
    }
}
