### Title
Missing Minimum Gas Fee Validation on User-Supplied `gas_fee` in Refund Flow — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
The bridge config defines `min_btc_gas_fee` (and `max_btc_gas_fee`) as enforced protocol limits for BTC transaction fees. However, when a user supplies a custom `gas_fee` in `request_refund`, the `request_refund_callback` only checks that `gas_fee < amount` — it never validates the value against `min_btc_gas_fee`. An unprivileged user can set `gas_fee = 0`, causing the eventual refund transaction to carry zero miner fee, making it unconfirmable on Bitcoin. After `execute_refund` is called (permissionlessly, post-timelock), the deposit UTXO is permanently marked as verified and the user's funds are stuck.

### Finding Description

**Root cause — `request_refund_callback` in `refund.rs`:**

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The only guard is `gas_fee < amount`. The protocol's `min_btc_gas_fee` (and `max_btc_gas_fee`) from `Config` are never consulted here.

**The `min_btc_gas_fee` / `max_btc_gas_fee` limits exist in `Config` and are validated on config updates, but only for BTC withdrawal transactions — not for the user-supplied refund gas fee:** [2](#0-1) 

**How `gas_fee` becomes the BTC miner fee:** In `refund_execution_inputs`, `refund_amount = deposit_amount − gas_fee`. In `build_refund_output`, the single output pays `refund_amount` to the user. The implicit BTC transaction fee is therefore `input_value − output_value = gas_fee`. Setting `gas_fee = 0` produces a zero-fee transaction. [3](#0-2) 

**After `execute_refund` (callable by anyone post-timelock), `finalize_refund_with_psbt` permanently marks the UTXO as verified:**

```rust
// Mark UTXO as verified to prevent verify_deposit later
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

The `gas_fee` is frozen in the stored `RefundRequest` and cannot be changed. Re-calling `execute_refund` rebuilds the same zero-fee transaction. The UTXO is now permanently blocked from deposit processing, and the refund transaction will never confirm. [5](#0-4) 

### Impact Explanation

**Medium — Attacker-triggered permanent locking of user funds / stuck bridge state requiring operator intervention.**

After the attack:
- The deposit UTXO is marked `verified_deposit_utxo` (blocking any future `verify_deposit` for it).
- The refund transaction has 0 fee and will never be mined.
- The user's deposited BTC is permanently inaccessible unless the operator manually rejects the refund request — but even after rejection, the UTXO remains marked as verified, so the deposit path is also closed.

The bridge's `min_btc_gas_fee` policy is bypassed entirely for the refund path.

### Likelihood Explanation

**Medium.** Any user who has made a deposit and wants to request a refund can supply `gas_fee = Some(0)` directly in the `request_refund` call. No privileged access is required. The user only needs to wait for the `refund_timelock_sec` (default 2 days for pre-authorized addresses, 14 days for unsafe) before calling `execute_refund`. The operator has this window to reject, but the vulnerability exists because the protocol itself does not enforce the limit — it relies entirely on operator vigilance.

### Recommendation

In `request_refund_callback`, validate the resolved gas fee against the protocol's configured bounds before storing the `RefundRequest`:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
let config = self.internal_config();
require!(
    resolved_gas_fee >= config.min_btc_gas_fee,
    "Gas fee below protocol minimum"
);
require!(
    resolved_gas_fee <= config.max_btc_gas_fee,
    "Gas fee above protocol maximum"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

This mirrors the existing `BridgeFee::assert_valid()` pattern used for withdrawal fees and closes the analog gap to the MAX_TTL class of missing-bounds-check vulnerabilities. [6](#0-5) 

### Proof of Concept

1. User deposits BTC to their bridge address; the deposit UTXO is `txid:vout`.
2. User calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee = Some(0))` with a valid light-client proof.
3. `request_refund_callback` passes the only check (`0 < amount`) and stores `RefundRequest { gas_fee: 0, ... }`.
4. After `refund_timelock_sec` elapses, user (or anyone) calls `execute_refund(utxo_storage_key, ...)`.
5. `refund_execution_inputs` computes `refund_amount = amount − 0 = amount`; `build_refund_output` creates a single output paying the full deposit to the user.
6. The resulting BTC transaction has `fee = input − output = 0`. It is broadcast but never mined.
7. `finalize_refund_with_psbt` inserts `utxo_storage_key` into `verified_deposit_utxo`.
8. The deposit UTXO is now permanently blocked from both the deposit path and the refund path. User funds are stuck.
