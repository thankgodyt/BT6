The vulnerability is real. Here is the full analysis:

### Title
Unguarded `Zatoshis::from_u64(...).unwrap()` on user-supplied `TxOut` value panics for amounts above Zcash supply cap — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

### Summary

In the Zcash bridge path, `PsbtWrapper::new` converts each user-supplied `bitcoin::TxOut` output value to a `Zatoshis` using `Zatoshis::from_u64(o.value.to_sat()).unwrap()`. `Zatoshis::from_u64` returns `None` for any value exceeding the Zcash supply cap (2,100,000,000,000,000 zatoshis). An unprivileged user can submit a `TxOut` with a value above this cap, causing an unhandled `unwrap()` panic inside the `ft_on_transfer_callback`. The NEP-141 refund mechanism returns the tokens, but the error is never surfaced gracefully.

### Finding Description

The offending line is in `PsbtWrapper::new`: [1](#0-0) 

```rust
ZcashTxOut::new(
    Zatoshis::from_u64(o.value.to_sat()).unwrap(),  // panics if value > 2_100_000_000_000_000
    Script(Code(o.script_pubkey.to_bytes())),
)
```

The same pattern appears in `from_original_psbt` and `set_input_utxo`: [2](#0-1) [3](#0-2) 

The `bitcoin::Amount::from_sat(u64)` constructor accepts any `u64` with no MAX_MONEY enforcement, so a user can freely construct a `TxOut` with `value = bitcoin::Amount::from_sat(2_100_000_000_000_001)` (or any value above the Zcash cap). When this flows into `PsbtWrapper::new`, `Zatoshis::from_u64` returns `None` and `.unwrap()` panics.

### Attack Path

1. User calls `nbtc.ft_transfer_call(bridge, amount, msg)` where `msg` is a `TokenReceiverMessage::Withdraw` containing a `TxOut` with `value > 2_100_000_000_000_000` satoshis. [4](#0-3) 

2. `ft_on_transfer_withdraw_chain_specific` schedules `ft_on_transfer_callback` as a cross-contract call, passing the user-supplied `output` unchanged: [5](#0-4) 

3. Inside `ft_on_transfer_callback`, `PsbtWrapper::new` is called with the attacker-controlled `output`: [6](#0-5) 

4. `Zatoshis::from_u64(2_100_000_000_000_001).unwrap()` panics. The callback fails. NEP-141's `ft_resolve_transfer` refunds the tokens to the sender.

### Impact Explanation

The panic is publicly reachable from any user without any privilege. The impact is Low: the `ft_on_transfer_callback` aborts, the NEP-141 refund mechanism returns the tokens, but the failure is not surfaced as a meaningful error. The invariant that invalid output values must be rejected gracefully (not via panic) is violated. No funds are permanently lost.

### Likelihood Explanation

Any user can trigger this by crafting a `TxOut` with a value above 2,100,000,000,000,000 satoshis in the JSON `msg` of `ft_transfer_call`. No special role or access is required. The `bitcoin::Amount` type imposes no MAX_MONEY constraint in `from_sat`, so the value passes deserialization without rejection.

### Recommendation

Replace all `.unwrap()` calls on `Zatoshis::from_u64` with explicit error handling that calls `env::panic_str` with a descriptive message, or use `require!` to validate the value before conversion:

```rust
let zatoshis = Zatoshis::from_u64(o.value.to_sat())
    .unwrap_or_else(|| env::panic_str("ERR_INVALID_OUTPUT_VALUE: exceeds Zcash supply cap"));
```

This applies to all four call sites in `psbt_wrapper.rs`: [7](#0-6) [8](#0-7) [2](#0-1) [3](#0-2)
