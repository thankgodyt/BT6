### Title
NEAR Deposit Permanently Trapped in Bridge Contract When `deploy_token` Deployer Call Fails — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The `deploy_token` function is `#[payable]` and accepts a NEAR deposit to cover bridge storage costs and token account deployment. When the downstream deployer cross-contract call fails (a realistic scenario when the deposit is insufficient for WASM code storage), the `deploy_token_by_deployer_callback` cleans up state but never refunds the caller's NEAR. The deposit is permanently trapped in the bridge contract.

---

### Finding Description

`deploy_token` (callable by any unprivileged user when not paused) accepts an attached NEAR deposit and passes it through `deploy_token_callback` into `deploy_token_internal`: [1](#0-0) 

Inside `deploy_token_internal`, the deposit is split:
- `required_deposit` is consumed for bridge-side storage (maps, sets)
- `attached_deposit - required_deposit` is forwarded to the `TokenDeployer` contract [2](#0-1) 

When the deployer call fails (e.g., `LackBalance` because the forwarded amount is insufficient to cover WASM code storage for the new token account), the NEAR runtime automatically refunds `attached_deposit - required_deposit` back to the bridge contract's balance. The callback `deploy_token_by_deployer_callback` is then invoked: [3](#0-2) 

This callback removes the state entries (freeing the `required_deposit` storage), but **neither the refunded deployer amount nor the freed storage NEAR is ever returned to the original caller**. There is no `Self::refund(predecessor, ...)` call in the failure branch. The bridge contract's `refund` helper exists and is used elsewhere: [4](#0-3) 

Compare with `bind_token`, which correctly chains a `bind_token_refund` callback to return unused deposit to the caller: [5](#0-4) 

`deploy_token` has no equivalent refund step.

---

### Impact Explanation

The caller permanently loses their entire attached NEAR deposit. The NEAR accumulates in the bridge contract's balance with no recovery mechanism for users. This is a direct, irreversible loss of bridged-ecosystem funds for any user who triggers a failed deployment.

---

### Likelihood Explanation

The contract exposes `required_balance_for_deploy_token()` as the canonical minimum deposit: [6](#0-5) 

This estimate includes bridge storage costs and `NEP141_DEPOSIT` but **does not include WASM code storage** for the new token account. The integration test suite explicitly confirms that sending exactly this minimum causes the deployer call to fail: [7](#0-6) 

Any user who queries `required_balance_for_deploy_token()` and uses that value as their deposit will trigger the failure path and lose their NEAR. This is the natural, documented usage pattern.

---

### Recommendation

In the failure branch of `deploy_token_by_deployer_callback`, refund the original caller's full deposit. The original caller's account ID and the deposit amount must be threaded through as callback arguments (as is done in `bind_token` → `bind_token_refund`). Alternatively, add a trailing refund callback analogous to `bind_token_refund` that always runs and returns any remaining balance to the predecessor.

---

### Proof of Concept

1. User calls `required_balance_for_deploy_token()` → receives value `V` (does not include WASM code storage).
2. User calls `deploy_token(args)` with `V` NEAR attached.
3. `deploy_token_internal` keeps `required_deposit ≤ V` for bridge storage; forwards `V - required_deposit` to `TokenDeployer::deploy_token`.
4. `TokenDeployer::deploy_token` attempts `Promise::new(token_id).create_account().transfer(V - required_deposit)...` — fails with `LackBalance` because WASM code storage requires additional NEAR.
5. NEAR runtime refunds `V - required_deposit` to the bridge contract's balance.
6. `deploy_token_by_deployer_callback` is called with `Err`; removes state entries (freeing `required_deposit` storage) but issues no `Self::refund(...)` to the caller.
7. User's wallet balance is reduced by `V` NEAR permanently; the bridge contract balance increases by `V` with no user-accessible recovery path.

    pub fn deploy_token_by_deployer_callback(
        &mut self,
        token_address: &OmniAddress,
        token_id: AccountId,
    ) -> PromiseOrValue<()> {
        if env::promise_result_checked(0, usize::MAX).is_ok() {
            ext_token::ext(token_id)
                .with_static_gas(STORAGE_DEPOSIT_GAS)
                .with_attached_deposit(NEP141_DEPOSIT)
                .storage_deposit(&env::current_account_id(), Some(true))
                .into()
        } else {
            self.deployed_tokens.remove(&token_id);
            self.deployed_tokens_v2.remove(&token_id);
            self.token_id_to_address
                .remove(&(token_address.get_chain(), token_id));
            self.token_address_to_id.remove(token_address);
            self.token_decimals.remove(token_address);
            PromiseOrValue::Value(())
        }
    }
