### Title
Off-by-one gas boundary allows deterministic partial post-action execution — (`contracts/nbtc/src/lib.rs`)

### Summary

There is a concrete off-by-one discrepancy between the bridge's gas floor for post-actions and the gas guard inside `handle_post_action`. The bridge permits exactly 30 Tgas (inclusive lower bound), but `handle_post_action` requires **strictly more than** 30 Tgas. A depositor can craft a deposit message where the first post-action carries exactly 30 Tgas (passes bridge validation, always panics in `handle_post_action`) while the second carries ≥31 Tgas (passes both). Because both sub-calls are dispatched as independent detached promises, the second executes regardless of the first's failure, producing deterministic partial execution.

---

### Finding Description

**Bridge-side gas floor** (`contracts/satoshi-bridge/src/deposit_msg.rs`):

```
const MIN_PER_POST_ACTIONS_GAS: Gas = Gas::from_tgas(30);   // line 8
...
if gas.as_gas() < MIN_PER_POST_ACTIONS_GAS.as_gas() { ... return None; }  // line 157
```

The check is strict `<`, so `gas = 30 Tgas` satisfies `30 < 30 == false` → **passes validation**. [1](#0-0) [2](#0-1) 

**Token-contract gas guard** (`contracts/nbtc/src/lib.rs`):

```
const GAS_FOR_FT_TRANSFER_CALL: Gas = Gas::from_tgas(30);   // line 32
...
require!(env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL, "More gas is required");  // line 393-396
```

The check is strict `>`, so `prepaid_gas = 30 Tgas` satisfies `30 > 30 == false` → **panics**. [3](#0-2) [4](#0-3) 

**Dispatch is fully detached** — each `handle_post_action` is a separate independent receipt:

```rust
Self::ext(env::current_account_id())
    .with_static_gas(gas)
    .handle_post_action(...)
    .detach();   // lines 372-375
``` [5](#0-4) 

In NEAR, a panicking detached receipt does **not** roll back sibling receipts. The second `handle_post_action` receipt executes unconditionally.

---

### Impact Explanation

A depositor crafts:

| post_action | gas | bridge validation | `handle_post_action` |
|---|---|---|---|
| [0] transfer 20 000 to dapp1 | 30 Tgas | ✅ passes (`30 < 30` is false) | ❌ panics (`30 > 30` is false) |
| [1] transfer 20 000 to dapp2 | 31 Tgas | ✅ passes | ✅ succeeds |

Result: tokens are minted to `mint_account_id`; post-action 0 silently fails (tokens stay with recipient); post-action 1 executes. Any dApp integration that commits to both post-actions executing atomically (e.g., a two-leg DeFi operation where leg 0 is a fee payment and leg 1 is a collateral deposit) is broken. The depositor retains the tokens that were supposed to flow through leg 0 while leg 1 still fires.

This fits: **Low — publicly reachable invariant-violation, panic-driven fault in production bridge/token paths without direct theft.**

---

### Likelihood Explanation

The exploit requires only a crafted deposit message — a fully public, unprivileged input. The exact gas value (30 Tgas) is a single integer in the JSON deposit message embedded in the BTC transaction. No privileged access, leaked keys, or external dependency compromise is needed. [6](#0-5) 

---

### Recommendation

Align the two boundaries. Either:

1. Change the bridge floor to `MIN_PER_POST_ACTIONS_GAS = Gas::from_tgas(31)` (or use `<=` in the bridge rejection check), **or**
2. Change the `handle_post_action` guard to `>=` (`require!(env::prepaid_gas() >= GAS_FOR_FT_TRANSFER_CALL, ...)`).

The comment on line 146 of `deposit_msg.rs` already states the intent is **inclusive** ("between 30 Tgas and 100 Tgas, inclusive"), so option 2 (making the token-contract guard `>=`) is the minimal, intent-preserving fix. [7](#0-6) 

---

### Proof of Concept

```
deposit_msg = {
  recipient_id: "alice.near",
  post_actions: [
    { receiver_id: "dapp1.near", amount: "20000", msg: "", gas: "30000000000000" },  // 30 Tgas
    { receiver_id: "dapp2.near", amount: "20000", msg: "", gas: "31000000000000" }   // 31 Tgas
  ]
}
```

1. Bridge `check_deposit_msg`: both pass (`30 < 30` is false; `31 < 30` is false). ✅
2. `mint()` fires → `handle_post_actions` dispatches two detached receipts.
3. Receipt 0 (`prepaid_gas = 30 Tgas`): `require!(30 > 30)` → **panic**. Tokens stay with alice.
4. Receipt 1 (`prepaid_gas = 31 Tgas`): `require!(31 > 30)` → passes. `internal_transfer(alice → dapp2, 20000)` executes.
5. Assert: `ft_balance_of(dapp1) == 0`, `ft_balance_of(dapp2) == 20000`, `ft_balance_of(alice) == minted - 20000`.

Partial execution is deterministic and repeatable.
