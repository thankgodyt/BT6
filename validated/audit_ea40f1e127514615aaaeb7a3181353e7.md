### Title
`triggerHardForkDijkstra` Silently Dropped in `protocolInfoCardano`, Permanently Preventing Conway→Dijkstra Era Transition - (File: `ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

In `protocolInfoCardano`, the `CardanoHardForkTriggers'` record is destructured in the `where` clause but `triggerHardForkDijkstra` is omitted from the pattern. As a consequence, `partialLedgerConfigConway` is hardcoded to `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`. The `singleEraTransition` for the Conway era therefore unconditionally returns `Nothing`, so the Hard Fork Combinator never schedules the Conway→Dijkstra transition regardless of what the on-chain governance has decided. Any node running this code will permanently stay in the Conway era and reject Dijkstra-era blocks, diverging from nodes that correctly transition.

---

### Finding Description

`protocolInfoCardano` builds per-era partial ledger configs. Every era except the last must embed the trigger for the *next* era's hard fork. The established pattern is:

| Era | Trigger embedded |
|---|---|
| Byron | `toTriggerHardFork triggerHardForkShelley` |
| Shelley | `toTriggerHardFork triggerHardForkAllegra` |
| Allegra | `toTriggerHardFork triggerHardForkMary` |
| Mary | `toTriggerHardFork triggerHardForkAlonzo` |
| Alonzo | `toTriggerHardFork triggerHardForkBabbage` |
| Babbage | `toTriggerHardFork triggerHardForkConway` |
| **Conway** | **`TriggerHardForkNotDuringThisExecution`** ← wrong |
| Dijkstra | `TriggerHardForkNotDuringThisExecution` ← correct (last era) | [1](#0-0) [2](#0-1) 

The root cause is that the `where` clause destructures `CardanoHardForkTriggers'` without binding `triggerHardForkDijkstra`: [3](#0-2) 

Because `triggerHardForkDijkstra` is never bound, it cannot be passed to `partialLedgerConfigConway`, so the code falls back to the hardcoded `TriggerHardForkNotDuringThisExecution`.

The `SingleEraBlock` instance for `ShelleyBlock` dispatches on the trigger stored in the partial ledger config: [4](#0-3) 

When the trigger is `TriggerHardForkNotDuringThisExecution`, `singleEraTransition` returns `Nothing` unconditionally, so the HFC never schedules the epoch at which Conway ends and Dijkstra begins.

The `CardanoHardForkTriggers'` pattern and `triggerHardForkDijkstra` field are fully defined and wired through the configuration path: [5](#0-4) 

The correct behavior is confirmed by the test-example ledger config, which correctly assigns `TriggerHardForkAtEpoch (History.boundEpoch dijkstraStartBound)` to the Conway slot and `TriggerHardForkNotDuringThisExecution` only to Dijkstra: [6](#0-5) 

---

### Impact Explanation

When on-chain Conway governance increments the major protocol version to 12 (Dijkstra's `eraProtVerLow`), nodes running this code will never observe `singleEraTransition` returning `Just` for the Conway era. The HFC will not schedule the Conway→Dijkstra boundary. Those nodes will:

1. Remain in the Conway era indefinitely.
2. Reject any Dijkstra-era block headers as belonging to an unrecognised era, causing them to diverge from the canonical chain.
3. Produce a permanent, irrecoverable chain split relative to correctly-updated peers.

This matches the **High** impact category: *Hard-fork, era transition, ledger-view, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.*

---

### Likelihood Explanation

The trigger fires automatically when on-chain Conway governance raises the major protocol version to 12. No special attacker capability is required; any peer that has already transitioned to Dijkstra and sends a valid Dijkstra-era block will expose the divergence. The misconfiguration is present in the production `protocolInfoCardano` path used by every Cardano node.

---

### Recommendation

Bind `triggerHardForkDijkstra` in the `CardanoHardForkTriggers'` destructuring and pass it to `partialLedgerConfigConway`:

```diff
  cardanoHardForkTriggers =
    CardanoHardForkTriggers'
      { triggerHardForkShelley
      , triggerHardForkAllegra
      , triggerHardForkMary
      , triggerHardForkAlonzo
      , triggerHardForkBabbage
      , triggerHardForkConway
+     , triggerHardForkDijkstra
      }

  partialLedgerConfigConway =
    mkPartialLedgerConfigShelley
      transitionConfigConway
-     TriggerHardForkNotDuringThisExecution
+     (toTriggerHardFork triggerHardForkDijkstra)
```

### Proof of Concept

1. Construct a `CardanoProtocolParams` with `triggerHardForkDijkstra = CardanoTriggerHardForkAtDefaultVersion` (protocol version 12).
2. Call `protocolInfoCardano` and inspect `partialLedgerConfigConway` inside the resulting `TopLevelConfig`.
3. Observe that `shelleyTriggerHardFork` is `TriggerHardForkNotDuringThisExecution` rather than `TriggerHardForkAtVersion 12`.
4. Simulate a ledger state in which Conway governance has adopted protocol version 12; call `singleEraTransition` on it with the Conway partial ledger config.
5. Observe that it returns `Nothing` — the transition is never scheduled — while the same call with the corrected trigger returns `Just <dijkstra-epoch>`. [7](#0-6)
