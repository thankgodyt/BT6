### Title
Unbounded `deposit_msg_json` in `request_refund_callback` Exhausts Fixed 20 Tgas Budget, Permanently Locking User BTC — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `request_refund_callback` function is allocated a fixed gas budget of 20 Tgas but must Borsh-serialize and write a `RefundRequest` to storage whose `deposit_msg_json` field is unbounded. The `DepositMsg` fields `extra_msg: Option<String>` and `safe_deposit: Option<SafeDepositMsg>` (with `msg: String`) carry no size limit anywhere in the refund path. A user who created a deposit with a sufficiently large `extra_msg` or `safe_deposit.msg` and whose deposit was never finalized will find that every `request_refund` call exhausts the callback's gas, the refund request is never persisted, and their BTC is permanently locked with no recovery path.

### Finding Description

**Fixed gas budget for the callback** [1](#0-0) 

`GAS_FOR_REQUEST_REFUND_CALLBACK` is 20 Tgas. The callback is scheduled with `.with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)`. [2](#0-1) 

**Unbounded `deposit_msg_json` stored in the callback**

Inside `request_refund_callback`, the full `DepositMsg` is JSON-serialized and stored verbatim as `deposit_msg_json` in the `RefundRequest`: [3](#0-2) 

`DepositMsg` contains two unbounded string fields: [4](#0-3) 

Neither `extra_msg` nor `safe_deposit.msg` is validated for size anywhere in the refund code path. The only size guard in `check_deposit_msg` covers `post_actions` count and gas, and is only invoked during `verify_deposit`, not during `request_refund`. [5](#0-4) 

**The codebase itself documents the gas ceiling**

The comment for `MAX_REQUEST_REFUND_TX_BYTES` explicitly states that the 20 Tgas callback runs out of gas around ~250 KB of total stored data: [6](#0-5) 

`tx_bytes` is capped at 200 KB, leaving only ~50 KB of headroom for all other `RefundRequest` fields combined. A `deposit_msg_json` exceeding ~50 KB (trivially achieved with a large `extra_msg`) pushes the total Borsh payload past the gas ceiling even when `tx_bytes` is small.

**No recovery path once the callback fails**

If `request_refund_callback` panics out of gas, NEAR rolls back all state changes in that receipt. The `refund_requests` map is never updated. The deposit UTXO remains unspendable by the bridge (no refund request exists to drive `execute_refund`), and `verify_deposit` is blocked if the deposit was already marked verified. The operator's `internal_reject_refund` requires the request to already exist: [7](#0-6) 

There is no privileged escape hatch to recover BTC from a deposit whose refund callback permanently fails.

### Impact Explanation

A user who embedded a large `extra_msg` (or `safe_deposit.msg`) in their `DepositMsg` and whose deposit was never finalized (e.g., amount below `min_deposit_amount`, or a dApp-driven deposit that failed post-action validation) cannot obtain a refund. Because the deposit address is derived from the hash of the exact `DepositMsg`, the user cannot substitute a smaller message — they must supply the original large `DepositMsg`, which always exhausts the 20 Tgas callback. Their BTC is permanently locked in the bridge-controlled MPC address with no on-chain recovery path. This matches **Critical — significant permanent locking of user funds** or at minimum **Medium — broken callback rollback / stuck bridge state requiring operator intervention** (with no operator remedy available).

### Likelihood Explanation

The `extra_msg` field is explicitly designed for dApp extensibility. A dApp or user embedding metadata (e.g., a JSON payload, a cross-chain message, or an application-layer identifier) could easily produce a `deposit_msg_json` exceeding 50 KB. The deposit flow imposes no size guard on `extra_msg` at any stage. Any deposit that is not finalized (below minimum, failed post-action, or simply unprocessed) then becomes permanently unrefundable. Likelihood is **Low-to-Medium**: not a common path, but a realistic one for dApp integrations using `extra_msg` for structured metadata.

### Recommendation

1. **Add a size cap on `deposit_msg_json` in `internal_request_refund`** before the light-client call, analogous to `MAX_REQUEST_REFUND_TX_BYTES`:
   ```rust
   let deposit_msg_json = serde_json::to_string(&deposit_msg).unwrap();
   require!(
       deposit_msg_json.len() <= MAX_REQUEST_REFUND_DEPOSIT_MSG_BYTES,
       "deposit_msg too large for refund request"
   );
   ```
2. **Size `MAX_REQUEST_REFUND_DEPOSIT_MSG_BYTES`** so that `deposit_msg_json.len() + tx_bytes.len()` stays well below the ~250 KB gas ceiling of the 20 Tgas callback (e.g., cap `deposit_msg_json` at 4 KB, matching realistic OP_RETURN-derived payloads).
3. **Alternatively**, increase `GAS_FOR_REQUEST_REFUND_CALLBACK` to accommodate larger payloads, and update `required_balance_for_request_refund` to scale with actual payload size.

### Proof of Concept

1. Construct a `DepositMsg` with `extra_msg` set to a ~100 KB string (e.g., `"A".repeat(100_000)`).
2. Derive the deposit address via `get_deposit_path(&deposit_msg)` → `generate_utxo_chain_address(&path)`.
3. Send a small BTC amount (below `min_deposit_amount`) to that address so `verify_deposit` will never succeed.
4. Call `request_refund` with the large `deposit_msg`, valid `tx_bytes` (small), and a valid Merkle proof.
5. The light-client cross-contract call succeeds; `request_refund_callback` is invoked with 20 Tgas.
6. Inside the callback, `serde_json::to_string(&deposit_msg)` produces a ~100 KB string; Borsh-serializing and writing the full `RefundRequest` to `refund_requests` exhausts the 20 Tgas budget; the callback panics.
7. The refund request is never stored. Repeating step 4 always produces the same outcome. The user's BTC is permanently locked.
