### Title
Tokens Minted to Bridge Balance Without Delivery When Recipient Unregistered in `safe_mint` - (File: contracts/nbtc/src/lib.rs)

### Summary

`safe_mint` in the nBTC token contract calls `internal_deposit` to mint tokens into the bridge's own balance **before** checking whether the recipient account has registered storage. If the recipient is unregistered, the function returns `U128(0)` and exits — leaving the freshly minted tokens permanently credited to the bridge's balance with no on-contract recovery path for the depositing user.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

1. Mints `amount` tokens into `bridge_id`'s balance via `internal_deposit` (total supply increases).
2. Checks whether `account_id` has a registered storage slot.
3. If the slot is absent, **returns `U128(0)` immediately** — the minted tokens remain in `bridge_id`'s balance. [1](#0-0) 

The critical ordering flaw: [2](#0-1) 

`internal_deposit` is an irreversible in-memory ledger credit. Once it executes, the nBTC total supply has grown. The subsequent early return does not roll it back. The nBTC contract has no "pending mint" or "claimable balance" map for unregistered recipients, so those tokens are silently absorbed into the bridge's own balance.

### Impact Explanation

- The depositing user's BTC UTXO is consumed by the bridge's deposit verification flow (marked in `verified_deposit_utxo`), yet the user receives **zero nBTC**.
- The bridge's nBTC balance is inflated by the undelivered amount, creating a supply/accounting discrepancy between on-chain BTC held and nBTC in circulation.
- No function in the nBTC contract allows the user to later claim the minted-but-undelivered tokens; the only recovery path would require privileged operator intervention.
- This matches the **Medium** impact class: broken callback rollback / stuck bridge state requiring operator intervention, and permanent burning below backed supply. [3](#0-2) 

### Likelihood Explanation

Any user who sends BTC to the bridge without first calling `storage_deposit` on the nBTC contract will trigger this path. NEAR storage registration is a non-obvious prerequisite that many users omit, especially when interacting programmatically or via a third-party dApp that does not pre-register storage. The entry path is fully unprivileged: the user only needs to send a valid BTC deposit and have the relayer call `verify_deposit`.

### Recommendation

Reverse the order of operations: check whether `account_id` is registered **before** calling `internal_deposit`. If the account is unregistered, either revert with a clear error (forcing the caller to register first) or credit the amount to a claimable `lost_found`-style map keyed by `account_id` so the user can retrieve tokens after registering.

```rust
// Correct order
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // no mint has occurred yet
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... proceed with transfer
```

### Proof of Concept

1. User sends BTC to the bridge deposit address derived from their NEAR account `alice.near`.
2. `alice.near` has **not** called `storage_deposit` on the nBTC contract.
3. Relayer calls `safe_verify_deposit` (or equivalent) on the satoshi-bridge; the bridge verifies the Merkle proof and calls `nbtc.safe_mint(alice.near, amount, None)`.
4. Inside `safe_mint`: `internal_deposit(&bridge_id, amount)` executes — nBTC total supply increases by `amount`, all credited to `bridge_id`.
5. `self.token.accounts.get(&alice.near)` returns `None` → function returns `U128(0)`.
6. The bridge's deposit UTXO is marked verified; `alice.near` receives 0 nBTC; the `amount` tokens are silently held in the bridge's own balance with no user-facing recovery. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
