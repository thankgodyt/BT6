### Title
Zeroed `tx_bytes` After Validation in Safe Deposit Path Permanently Corrupts Bridge UTXO Pool Entry — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary

In `internal_safe_verify_deposit_entry`, the deposit address and amount are validated against the original `tx_bytes`, but then `tx_bytes` is silently replaced with 300 zero bytes when the transaction exceeds 10,000 bytes. The UTXO is subsequently stored in the bridge's spendable pool with these zeroed bytes. When the bridge later selects this UTXO for a withdrawal, the PSBT is built with invalid witness data, the signed transaction is rejected by Bitcoin, and the UTXO is permanently stuck — requiring operator intervention to recover.

### Finding Description

In `internal_safe_verify_deposit_entry`, the deposit address check and amount computation occur against the original `tx_bytes`: [1](#0-0) 

Immediately after, `tx_bytes` is mutated: [2](#0-1) 

The log message says "truncating to 300 bytes," but the code produces `vec![0u8; 300]` — 300 zero bytes — not a truncation of the original data. The UTXO is then constructed with these zeroed bytes: [3](#0-2) 

This `PendingUTXOInfo` (carrying the zeroed UTXO) is passed through the callback chain. In `safe_mint_callback`, on a successful mint, the UTXO is unconditionally inserted into the bridge's spendable pool: [4](#0-3) 

The `tx_bytes` field of a UTXO is used as the previous-transaction witness data when building a PSBT input for a withdrawal. With zeroed bytes, the PSBT encodes an invalid previous output. The MPC service will sign the payload derived from this invalid PSBT, producing a signature that is cryptographically valid for the wrong data. The resulting Bitcoin transaction will be rejected by the network, leaving the UTXO permanently locked in `PendingVerify` state.

The parallel to M-18 is direct: the key parameter (`tx_bytes`) is validated before mutation, mutated to a semantically different value, and the post-mutation value is stored without re-validating that it remains fit for its downstream purpose (PSBT construction and signing).

### Impact Explanation

The bridge's spendable UTXO pool gains an entry whose `tx_bytes` are all zeros. Any withdrawal that selects this UTXO will produce an invalid Bitcoin transaction. The UTXO's on-chain value is not immediately lost (the bridge's MPC key still controls the actual Bitcoin UTXO), but the bridge contract's state is corrupted: the UTXO is locked in a pending withdrawal that can never confirm, and the bridge cannot automatically recover it. Manual operator intervention is required to remove the stuck pending info and re-register the UTXO with correct bytes (if such an admin path exists). This matches the **Medium** impact class: stuck bridge state requiring operator intervention.

### Likelihood Explanation

The trigger condition is a Bitcoin deposit transaction exceeding 10,000 bytes. A standard P2PKH input is ~148 bytes, so this requires roughly 67+ inputs in a single deposit transaction. While unusual for ordinary users, it is reachable by any unprivileged actor who controls enough UTXOs and is willing to pay the on-chain fees. The attacker receives nBTC in return (the mint succeeds), so the net cost is only the Bitcoin transaction fees, not the deposited principal.

### Recommendation

The safe deposit path should **reject** transactions whose `tx_bytes` exceed the storage limit rather than silently replacing them with zeros:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes too large for safe deposit"
);
```

If storage reduction is genuinely needed, the bytes must be truncated correctly (`tx_bytes[..300].to_vec()`) and the UTXO must be marked as non-spendable so it is never selected for withdrawals. The simplest and safest fix is the hard rejection above.

### Proof of Concept

1. Construct a Bitcoin transaction with 70+ inputs (≥10,001 bytes) sending funds to the bridge's deposit address derived from a chosen `DepositMsg`.
2. Call `safe_verify_deposit` (the public entry point) with this transaction, a valid Merkle inclusion proof, and sufficient attached NEAR for storage.
3. The bridge validates the deposit address and amount against the original bytes (passes), then replaces `tx_bytes` with `vec![0u8; 300]`.
4. After the light-client callback confirms inclusion, `safe_mint_callback` mints nBTC to the caller and calls `internal_set_utxo`, inserting the zeroed UTXO into the bridge's spendable pool.
5. A subsequent withdrawal that selects this UTXO builds a PSBT with invalid previous-transaction data, obtains an MPC signature over the wrong payload, and broadcasts a transaction that Bitcoin nodes reject.
6. The UTXO remains locked in `PendingVerify` state indefinitely; the bridge requires operator intervention to recover. [5](#0-4)

    pub(crate) fn internal_safe_verify_deposit_entry(
        &mut self,
        deposit_msg: DepositMsg,
        tx_bytes: Vec<u8>,
        vout: usize,
        tx_block_blockhash: String,
        tx_index: u64,
        merkle_proof: Vec<String>,
        coinbase_proof: Option<(String, Vec<String>)>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_safe_deposit(),
            "Insufficient deposit for storage"
        );

        let path = get_deposit_path(&deposit_msg);
        let safe_deposit_msg = deposit_msg
            .safe_deposit
            .unwrap_or_else(|| env::panic_str("safe_deposit is required in safe_verify_deposit"));

        let transaction = WrappedTransaction::decode(&tx_bytes, &self.internal_config().chain)
            .expect("Deserialization tx_bytes failed");
        let deposit_amount = transaction.output()[vout].value.to_sat().into();
        require!(deposit_amount > 0, "Invalid deposit_amount");
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_address_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_address_script_pubkey == transaction.output()[vout].script_pubkey,
            "Invalid deposit tx_bytes"
        );

        let tx_bytes = if tx_bytes.len() > 10000 {
            env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
            vec![0u8; 300]
        } else {
            tx_bytes
        };

        let utxo = UTXO {
            path,
            tx_bytes,
            vout,
            balance: transaction.output()[vout].value.to_sat(),
        };
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id.clone(),
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        self.internal_safe_verify_deposit(
            deposit_amount,
            tx_block_blockhash,
            tx_index,
            merkle_proof,
            coinbase_proof,
            PendingUTXOInfo {
                tx_id,
                utxo_storage_key,
                utxo,
            },
            deposit_msg.recipient_id,
            safe_deposit_msg,
        )
    }
