Audit Report

## Title
Resigned or Forcibly-Removed Relayer Cannot Claim Pending Bridge Fees, Permanently Freezing Fee Tokens - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`claim_fee` carries two independent access restrictions: a `#[trusted_relayer]` gate and a `fee_recipient == predecessor_account_id` check inside `claim_fee_callback`. A relayer who signed transfers (embedding themselves as `fee_recipient`) and subsequently resigned via `resign_trusted_relayer` or was forcibly removed via `reject_relayer_application` can no longer satisfy the first restriction. No substitute caller can satisfy both restrictions simultaneously, leaving the transfer message in `pending_transfers` indefinitely and permanently freezing the fee tokens locked in the bridge contract.

## Finding Description

`claim_fee` at `near/omni-bridge/src/lib.rs` L1054–1064 carries `#[trusted_relayer]` as a method-level attribute inside the impl block configured with `bypass_roles(Role::DAO, Role::UnrestrictedRelayer)`:

```rust
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise {
    self.verify_proof(args.chain_kind, args.prover_args).then(
        Self::ext(env::current_account_id())
            .with_attached_deposit(env::attached_deposit())
            .with_static_gas(CLAIM_FEE_CALLBACK_GAS)
            .claim_fee_callback(&env::predecessor_account_id()),
    )
}
```

The `predecessor_account_id` at call time is forwarded to `claim_fee_callback`. Inside the callback (L1083–1086), a second independent check enforces:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

where `fee_recipient` is the account embedded in the on-chain proof — the relayer who called `sign_transfer`.

**Restriction 1** (`#[trusted_relayer]`): After `resign_trusted_relayer` or `reject_relayer_application`, the relayer's trusted status is immediately revoked. Integration tests confirm this: `is_trusted_relayer` returns `false` after either operation.

**Restriction 2** (`fee_recipient == predecessor_account_id`): Even accounts with `Role::DAO` or `Role::UnrestrictedRelayer` (which bypass Restriction 1) cannot satisfy this check, because their account ID does not match the resigned relayer's account ID embedded in the proof.

The two restrictions together create a deadlock: the only account that can satisfy both is the original relayer, who can no longer satisfy Restriction 1. `remove_transfer_message` at L1094 is only called inside `claim_fee_callback`, so the entry in `pending_transfers` is never removed. For non-deployed tokens, the fee amount is tracked in `locked_tokens` and the underlying tokens remain in the bridge contract with no removal path.

`sign_transfer_callback` at L656–658 shows that transfer messages with non-zero fees are kept in `pending_transfers` after signing:

```rust
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
```

Only zero-fee transfers are cleaned up at signing time; all non-zero-fee transfers remain and are subject to this freeze.

## Impact Explanation

Permanent freezing of bridged funds. The fee portion of every pending NEAR→Foreign transfer signed by the resigned or rejected relayer is irrecoverably locked inside the bridge contract. For non-deployed (externally-issued) tokens, the fee slice of each transfer amount is real user-locked value that cannot be recovered. The `locked_tokens` accounting is permanently inflated. This matches the Critical allowed impact: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."

## Likelihood Explanation

Realistic and triggerable by an unprivileged external user. Any account meeting the stake requirement can become a trusted relayer, sign transfers designating itself as `fee_recipient`, and then resign — recovering its stake while leaving all signed pending transfers permanently frozen. The DAO-forced removal path (`reject_relayer_application`) can also trigger this without the relayer's cooperation. The window between `sign_transfer` and `claim_fee` spans the entire cross-chain finalization period (minutes to hours depending on chain congestion), making the race condition easy to exploit.

## Recommendation

Remove the `#[trusted_relayer]` gate from `claim_fee`, replacing it with a check that the caller is the `fee_recipient` recorded in the proof — which `claim_fee_callback` already enforces. Trusted-relayer status is a prerequisite for *signing* transfers but should not be required for *collecting already-earned fees*. Alternatively, allow a designated fallback address (e.g., the DAO or a configurable sweep address) to claim fees on behalf of removed relayers, or add an admin function to remove stale `pending_transfers` entries and return locked tokens.

## Proof of Concept

1. Relayer `R` calls `apply_for_trusted_relayer` with ≥ 1000 NEAR stake and waits for the activation period.
2. User initiates a NEAR→Ethereum transfer with a non-zero fee; a `pending_transfers` entry is created.
3. `R` calls `sign_transfer(transfer_id, fee_recipient = R, fee = ...)`. The MPC signature embeds `R` as `fee_recipient` in the payload. Because `fee` is non-zero, `sign_transfer_callback` does NOT remove the transfer message.
4. The MPC signature is delivered to Ethereum; the destination contract finalizes the transfer.
5. Before calling `claim_fee`, `R` calls `resign_trusted_relayer`. `R`'s stake is returned; `is_trusted_relayer(R)` returns `false`.
6. `R` attempts `claim_fee(args)` — the `#[trusted_relayer]` macro panics. The DAO attempts `claim_fee(args)` — passes Restriction 1 via `bypass_roles`, but `claim_fee_callback` panics at `fee_recipient (R) != predecessor_account_id (DAO)`.
7. The transfer message remains in `pending_transfers` forever; the fee tokens are permanently frozen in the bridge contract with no removal path.

**Minimal integration test plan:** Extend `near/omni-tests/src/relayer_staking.rs` — set up a trusted relayer, call `sign_transfer` with a non-zero fee, call `resign_trusted_relayer`, then assert that `claim_fee` panics and `get_transfer_message` still returns the entry.
