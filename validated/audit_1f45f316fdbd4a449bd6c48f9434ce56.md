Audit Report

## Title
Fee-on-Transfer Token Escrow Over-Crediting in `initTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.sol`'s `initTransfer` function transfers tokens using the caller-supplied `amount` and emits `InitTransfer` with that same `amount`, without measuring the actual tokens received. For fee-on-transfer ERC-20 tokens, the contract receives fewer tokens than `amount`, but the NEAR-side relayer reads the event and mints or unlocks the full `amount`, permanently over-crediting the recipient and leaving the EVM escrow undercollateralized.

## Finding Description
In the regular-token branch of `initTransfer` (lines 407–411), the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount
);
```

No balance snapshot is taken before or after this call. The event is then emitted at lines 427–436 with the same caller-supplied `amount`. There is no token whitelist — `isBridgeToken[tokenAddress]` is only set for bridge-deployed tokens, and any arbitrary ERC-20 falls through to the escrow branch. On the NEAR side, `fin_transfer_callback` (lines 722–725) constructs a `TransferMessage` using `init_transfer.amount` directly from the decoded event, denormalizes it, and mints or unlocks that full amount to the recipient. The EVM `finTransfer` function (lines 350–354) later attempts `safeTransfer(recipient, payload.amount)` using the same over-stated amount.

## Impact Explanation
This is a concrete escrow mis-accounting / balance manipulation impact matching the Critical allowed scope. The EVM escrow holds `amount - transfer_fee` tokens but has issued a `amount`-token claim on NEAR. When any user bridges the same token back from NEAR to EVM, `finTransfer` calls `safeTransfer(recipient, amount)` against an escrow that is short by `transfer_fee` tokens per prior exploit call. Repeated exploitation drains the EVM escrow entirely for that token, causing permanent loss of bridged funds for honest users.

## Likelihood Explanation
Any unprivileged external user can call `initTransfer` with any ERC-20 token address — there is no whitelist enforced in the base `OmniBridge` contract and no check that the token is non-deflationary. Fee-on-transfer tokens are a deployed and well-known token class. A single call is sufficient to create a discrepancy; the attacker profits by receiving more tokens on NEAR than they deposited on EVM.

## Recommendation
Record the contract's token balance before and after `safeTransferFrom` and use the actual received amount:

```solidity
} else {
    uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
    uint128 received = uint128(IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore);
    require(received == amount, "Fee-on-transfer tokens not supported");
    // use `received` in the event and extension call instead of `amount`
}
```

Alternatively, enforce a token whitelist that reverts on any token not explicitly registered via `deployToken` or `addCustomToken`.

## Proof of Concept
1. Deploy or use any ERC-20 that deducts a 1% fee on every transfer.
2. Approve `OmniBridge` for `1000` tokens.
3. Call `initTransfer(tokenAddress, 1000, 0, 0, "recipient.near", "")`.
4. The bridge receives `990` tokens; `safeTransferFrom` deducts 10 as a transfer fee.
5. The emitted `InitTransfer` event records `amount = 1000`.
6. The NEAR relayer submits the proof; `fin_transfer_callback` denormalizes and mints `1000` tokens to `recipient.near`.
7. The EVM bridge holds only `990` tokens but has issued a `1000`-token claim on NEAR.
8. When any user bridges `1000` tokens back from NEAR to EVM, `finTransfer` attempts `safeTransfer(recipient, 1000)` but only `990` tokens are available, causing a revert or draining another user's deposit.
