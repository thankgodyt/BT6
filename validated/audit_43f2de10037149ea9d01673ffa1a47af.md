### Title
Insufficient Peras Vote Validation Allows Forged Votes to Manipulate Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` checks only stake-distribution membership (the aggregate condition) while entirely omitting cryptographic vote-signature verification (the component condition). This is the direct structural analog of the reported DeFi bug: an aggregate invariant is enforced while a critical per-component invariant is silently skipped. When Peras is enabled, any unprivileged peer that knows a valid `PerasVoterId` (publicly visible on-chain) can forge votes for that voter, accumulate enough stake to reach quorum, cause a certificate to be generated, and thereby boost an arbitrary block in chain selection — making honest nodes prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares two validation entry points:

```haskell
validatePerasCert :: PerasCfg blk -> PerasCert blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote :: PerasCfg blk -> PerasVoteStakeDistr -> PerasVote blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The only production instance in the codebase is the catch-all degenerate instance:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [1](#0-0) 

`validatePerasCert` unconditionally returns `Right` for any certificate. `validatePerasVote` only checks that the voter ID is present in the stake distribution; it performs no cryptographic verification whatsoever.

The degenerate `PerasVote blk` type has no signature field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

The downstream quorum check `votesReachQuorum` then verifies two conditions — same target and total stake above threshold — but relies entirely on the upstream `validatePerasVote` to have established individual vote legitimacy, which it does not:

```haskell
votesReachQuorum cfg votes =
  (v0 : vs)
    | not (allVotesMatchTarget v0 vs) -> Nothing   -- condition 1: same target
    | not votesHaveEnoughStake        -> Nothing   -- condition 2: aggregate stake
    | otherwise -> Just ValidatedPerasVotesWithQuorum{...}
    -- condition 3 (individual signature validity): NEVER CHECKED
``` [3](#0-2) 

This is the precise structural analog of the reported DeFi bug:

| | External Report | This Finding |
|---|---|---|
| Aggregate check | Total collateral ≥ 150% ✓ | Total vote stake ≥ quorum threshold ✓ |
| Component check | Exogenous collateral ≥ 100% ✗ | Individual vote signature valid ✗ |
| Consequence | Fractionally-collateralised vault survives | Forged votes survive and forge certificates |

The inbound vote processing path calls `validatePerasVote` directly:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

Once a forged vote passes `validatePerasVote`, it is timestamped and inserted into the `PerasVoteDB`. When enough forged votes accumulate, `updateCandidateVoteState` calls `votesReachQuorum`, which returns `Just`, and `forgePerasCert` produces a `ValidatedPerasCert`. That certificate is then submitted to `chainSelSync`, which adds it to the `PerasCertDB` and triggers chain selection for the boosted block: [5](#0-4) 

Chain selection then uses `preferAnchoredCandidate`, which — when the weight snapshot is non-empty — compares `weightedSelectView` values. The boosted block receives `perasWeight = 15` additional weight (default), which can tip the comparison in favour of the attacker's chain: [6](#0-5) 

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Enumerate valid `PerasVoterId` values from the public stake distribution.
2. Craft `PerasVote` objects with those IDs targeting any desired block.
3. Send them via the object-diffusion mini-protocol; `processVotes` accepts them because `validatePerasVote` passes the stake-membership check.
4. Accumulate enough forged votes to exceed the quorum threshold (`perasQuorumStakeThreshold = 3/4` by default).
5. Trigger automatic certificate forging and insertion into `PerasCertDB`.
6. Cause `chainSelectionForBlock` to run for the boosted block, giving it `perasWeight = 15` extra weight.
7. Honest nodes switch to the attacker's chain, constituting a chain-selection safety failure.

This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

- Peras is disabled by default; the attack surface is limited to nodes that explicitly enable it.
- However, Peras is an active development target and will be enabled in future deployments; the vulnerable code is already on the production code path.
- `PerasVoterId` values are `KeyHash StakePool` — publicly visible on-chain — so no privileged information is required.
- The attack requires only sending well-formed `PerasVote` wire messages; no key material, stake, or special access is needed.
- The TODO comment and linked issue (#120) confirm the team is aware the validation is a placeholder, but the code is already wired into the live diffusion and chain-selection pipeline.

---

### Recommendation

1. Add a cryptographic signature field to `PerasVote blk` (analogous to `WFALSPersistentVote`/`EveryoneVotesVote` in the `Committee` modules).
2. Implement `validatePerasVote` to verify that signature against the voter's public key from the stake distribution before producing a `ValidatedPerasVote`.
3. Implement `validatePerasCert` to verify the certificate's aggregate signature and confirm it represents a genuine quorum.
4. Until these are implemented, gate the object-diffusion inbound path for Peras votes/certs behind the Peras feature flag so that the degenerate instance is never reachable from the network.

---

### Proof of Concept

```
1. Enable Peras in node configuration (non-default).
2. Query the stake distribution to obtain valid PerasVoterId values
   (KeyHash StakePool — public on-chain data).
3. Craft N PerasVote { pvVoteRound = r, pvVoteBlock = targetBlock,
                       pvVoteVoterId = knownVoterId_i } messages
   where sum(stake_i) >= perasQuorumStakeThreshold + safetyMargin.
4. Send them via the Peras object-diffusion mini-protocol.
5. processVotes calls validatePerasVote for each; all pass because
   lookupPerasVoteStake finds the voter ID in the stake distribution.
6. Votes are inserted into PerasVoteDB; updatePerasRoundVoteStates
   calls votesReachQuorum, which returns Just (total stake >= threshold).
7. forgePerasCert produces a ValidatedPerasCert boosting targetBlock.
8. chainSelSync adds the cert to PerasCertDB and calls
   chainSelectionForBlock for targetBlock.
9. preferAnchoredCandidate now computes weightedSelectView with
   perasWeight=15 boost on targetBlock; the attacker's chain is preferred.
10. The honest node switches to the attacker's non-canonical chain.
```

votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }

  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
