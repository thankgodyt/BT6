Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 `safeTransferFrom` Callback Enables Unauthorized NEAR-Side Minting Without Locking EVM Assets - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` increments `currentOriginNonce` and then makes an external call to an attacker-supplied `tokenAddress` via `IERC1155.safeTransferFrom` before emitting `InitTransfer`, with no reentrancy guard. A malicious ERC1155 contract can re-enter `initTransfer1155` during `safeTransferFrom`, causing multiple `InitTransfer` events to be emitted by the legitimate OmniBridge contract with distinct nonces while locking zero actual ERC1155 tokens. The NEAR bridge processes each event and mints tokens to the attacker's recipient, resulting in unbacked minting.

## Finding Description
`initTransfer1155` (lines 439–490) has no `nonReentrant` modifier and no check that `tokenAddress` is a registered token. The execution order is:

1. `currentOriginNonce += 1` — state mutation (line 448)
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — external call to attacker-controlled contract (lines 458–464)
3. `initTransferExtension(...)` and `emit BridgeTypes.InitTransfer(...)` — event emission (lines 468–489)

During step 2, the malicious token's `safeTransferFrom` can call `bridge.initTransfer1155(...)` directly, re-entering the function. Each re-entrant call increments `currentOriginNonce` and eventually emits a new `InitTransfer` event with a unique nonce. No ERC1155 tokens are ever transferred to the bridge.

The `onERC1155Received` guard at lines 522–535 checks `operator != address(this)` and reverts if the operator is not the bridge. This does not prevent the attack: the malicious token bypasses it by calling `initTransfer1155` directly (not via the standard ERC1155 callback path), and when it does invoke `onERC1155Received`, it passes `operator = msg.sender = address(bridge)`, satisfying the check.

`logMetadata1155` (lines 234–270) carries no role restriction and no pause guard, making it callable by any unprivileged user to register an arbitrary ERC1155 address. However, even this step is not strictly required for the reentrancy — `initTransfer1155` itself imposes no check that `tokenAddress` is registered in `multiTokens`.

## Impact Explanation
Each fraudulent `InitTransfer` event is genuinely emitted by the OmniBridge contract with a unique `currentOriginNonce`. The NEAR bridge verifies events by checking the emitter address against the registered factory; since the events are authentic, they pass verification. For each event, the NEAR bridge mints tokens to the attacker's specified recipient. Zero ERC1155 tokens are locked on the EVM side. This is direct escrow mis-accounting and unauthorized minting of bridged assets — a concrete Critical impact matching the allowed scope.

## Likelihood Explanation
The attack requires no privileges, no admin compromise, and no off-chain collusion. Any external user can deploy a malicious ERC1155 contract, call the permissionless `logMetadata1155`, and then call `initTransfer1155` with `msg.value = 0` and `nativeFee = 0` (making `extensionValue = 0`, which satisfies the base `initTransferExtension` check). The attack is repeatable and fully on-chain.

## Recommendation
Import and inherit `ReentrancyGuardUpgradeable` from OpenZeppelin and apply the `nonReentrant` modifier to `initTransfer1155` (and `initTransfer` for defense-in-depth):

```solidity
function initTransfer1155(...) external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) {
```

Additionally, add a check at the start of `initTransfer1155` that `multiTokens[deterministicToken].tokenAddress != address(0)` to ensure only registered ERC1155 tokens can be transferred, further restricting the attack surface.

## Proof of Concept
1. Deploy `MaliciousERC1155(bridgeAddress)` whose `safeTransferFrom` re-enters `bridge.initTransfer1155(...)` up to N times before calling `onERC1155Received(bridge_address, ...)` to satisfy the operator check.
2. Call `bridge.logMetadata1155(maliciousERC1155, tokenId)` — no role required.
3. Call `bridge.initTransfer1155(maliciousERC1155, tokenId, amount, 0, 0, "attacker.near", "")` with `msg.value = 0`.
4. Observe N+1 `InitTransfer` events emitted with distinct nonces and zero ERC1155 tokens held by the bridge.
5. Submit proofs to the NEAR bridge for each event; NEAR mints N+1 × amount tokens to `attacker.near`.

A local Foundry test can confirm this by deploying the harness `OmniBridge1155Harness`, a malicious ERC1155 stub, and asserting that `currentOriginNonce` advances by more than 1 and that the bridge's ERC1155 balance remains 0 after the call.
