### Title
Peras Certificate Validation Stub Unconditionally Accepts All Certificates, Enabling Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` type class defines `validatePerasCert` and `validatePerasVote` as the gatekeepers for Peras certificates and votes before they influence chain selection. The only concrete instance in the codebase is a degenerate stub that unconditionally accepts every certificate without performing any cryptographic verification. An unprivileged peer can therefore inject an arbitrary Peras certificate over the object-diffusion mini-protocol, causing the receiving node to apply a fabricated weight boost to any block of the attacker's choosing and potentially switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`**

The sole `BlockSupportsPeras` instance, explicitly labelled a "degenerate instance for all blks to get things to compile", implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No BLS aggregate-signature check, no voter-eligibility check, no quorum check — every certificate is unconditionally promoted to `ValidatedPerasCert` and assigned the full `perasWeight` boost. [1](#0-0) 

The same instance's `validatePerasVote` only checks whether the voter ID appears in the stake distribution; it never verifies the BLS vote signature:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

This is the **only** instance of `BlockSupportsPeras` in the production source tree; no Cardano-era-specific override exists. [3](#0-2) 

**Inbound certificate processing — the validation function is the sole gate**

`processCerts` in the object-diffusion layer calls the injected `validateCert` function (which resolves to `validatePerasCert`) on every certificate received from a peer. If the call returns `Right`, the certificate is immediately timestamped and written to the `PerasCertDB`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` always returns `Right`, every certificate a peer sends passes this gate.

**Chain selection consumes the injected boost**

`chainSelSync` in `ChainSel.hs` processes each newly-added certificate by triggering `chainSelectionForBlock` for the boosted block, using the certificate's weight to re-evaluate all candidate fragments:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The `WeightedSelectView` used for comparison adds `wsvWeightBoost` (sourced from the certificate's `vpcCertBoost`) to the block number, so a fake certificate with a large boost can make a shorter, non-canonical chain appear heavier than the honest chain:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) + wsvWeightBoost wsv
``` [6](#0-5) 

**End-to-end exploit path**

1. Attacker connects as an ordinary peer (no special privileges required).
2. Attacker crafts a `PerasCert` (or `PerasVote`) naming any block hash and any round number.
3. The certificate is sent via the object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert`; the stub returns `Right` unconditionally.
5. The certificate is stored in `PerasCertDB` with the full `perasWeight` boost.
6. `chainSelSync` triggers chain selection for the boosted block.
7. The honest node's `WeightedSelectView` now sees the attacker-chosen block as having higher total weight than the canonical tip.
8. The node switches to the non-canonical chain.

The `PerasCertDB` stores at most one certificate per round, so the attacker can inject one fake boost per Peras round — enough to continuously steer chain selection away from the canonical chain.

---

### Impact Explanation

**Severity: High — Chain selection manipulation.**

When Peras is enabled, an unprivileged peer can make an honest node permanently prefer a non-canonical chain by injecting fabricated certificates. Because the boost is additive and unbounded by any signature check, a single fake certificate per round is sufficient to keep a shorter adversarial chain preferred over the honest chain. This violates the chain-selection safety property of Ouroboros Praos/Peras and can lead to divergent chain views across honest nodes.

---

### Likelihood Explanation

Peras is not enabled by default (`Note that if Peras is disabled (which is the default), there is no observable difference`), so the vulnerability is not exploitable on a standard deployment today. However, the production code path is fully wired: the `PerasCertDB` is integrated into `ChainDB`, chain selection already uses `WeightedSelectView`, and the object-diffusion layer already accepts inbound certificates. Any operator who enables Peras — or any future release that enables it by default — immediately exposes this bypass to every connected peer. The exploit requires no keys, no stake, and no prior knowledge beyond a valid peer connection.

---

### Recommendation

1. **Implement real cryptographic validation in `validatePerasCert`**: verify the BLS aggregate signature over `(pcRoundNo, pcBoostedBlock)` against the aggregate public key derived from `pcVoters`, and verify each voter's eligibility proof (VRF output for non-persistent members). The concrete types and hashing logic already exist in `Ouroboros.Consensus.Peras.Cert.V1` and `Ouroboros.Consensus.Peras.Crypto.BLS`. [7](#0-6) 

2. **Implement real signature verification in `validatePerasVote`**: call `verifyVoteSignature` (already defined in `CryptoSupportsVoteSigning`) against the voter's public key before accepting a vote. [8](#0-7) 

3. **Gate Peras activation on complete validation**: do not allow Peras to be enabled in any deployment until the TODO items tracked in `cardano-peras#73` and `cardano-peras#120` are resolved and the degenerate instance is replaced.

---

### Proof of Concept

With Peras enabled, a peer node can execute the following sequence (pseudocode):

```haskell
-- Craft a certificate boosting an arbitrary block on a minority fork
let fakeCert = PerasCert
      { pcCertRound    = currentRound          -- any valid round
      , pcCertBoostedBlock = pointOfMinorityForkTip  -- attacker-chosen block
      , pcVoters       = emptyVoters           -- ignored by validatePerasCert
      , pcSignature    = zeroBLSSig            -- ignored by validatePerasCert
      }

-- Send via object-diffusion mini-protocol to the target node
sendPerasCert targetNode fakeCert
-- validatePerasCert returns Right unconditionally
-- PerasCertDB stores the cert; chain selection re-runs
-- wsvTotalWeight(minorityFork) = blockNo + perasWeight > wsvTotalWeight(canonicalChain)
-- Node switches to minority fork
```

The stub at lines 350–358 of `SupportsPeras.hs` is the single point of failure: removing the `Right` shortcut and replacing it with actual BLS verification closes the vulnerability entirely. [1](#0-0)
