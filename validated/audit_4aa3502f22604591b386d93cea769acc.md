### Title
Attacker Can Front-Run `request_refund` to Redirect BTC Refunds to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a deposit's `DepositMsg` does not include a pre-authorized `refund_address`, any unprivileged caller can submit a `request_refund` for that UTXO with an arbitrary `refund_address`. An attacker who observes a victim's pending refund request (or independently discovers an unverified deposit on the Bitcoin blockchain) can race to register the same UTXO's refund with their own address, blocking the victim's request and — if the DAO fails to reject the attacker's request within the `unsafe_refund_timelock_sec` window — redirecting the BTC to the attacker.

### Finding Description

`internal_request_refund` validates `refund_address` against `deposit_msg.refund_address` only when the latter is `Some`: [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), the provided `refund_address` is accepted without any ownership check. Because the Bitcoin Merkle proof is fully public data, any observer can reconstruct the exact call parameters and submit `request_refund` first with their own address.

In `request_refund_callback`, the first writer wins: a duplicate submission panics with `"Refund request already exists for this UTXO"`: [2](#0-1) 

The victim's callback panics, their NEAR storage deposit is consumed by the contract, and the attacker's `RefundRequest` — keyed to the same `utxo_storage_key` — is now the only live entry. The attacker's request carries `unsafe_refund_timelock_sec` before `execute_refund` can be called, giving the DAO a window to call `internal_reject_refund`. However, this is an operational control, not a cryptographic one. [3](#0-2) 

### Impact Explanation

If the DAO does not reject the attacker's request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund`, which calls `finalize_refund_with_psbt` and builds a signed Bitcoin transaction paying the attacker's address the full deposit amount minus gas fee. The victim's BTC is permanently redirected. Even if the DAO does reject in time, the victim's NEAR storage deposit is lost and their refund is blocked until they re-submit (which will succeed only after the attacker's request is removed).

**Impact: Medium** (attacker-triggered stuck/blocked refund state requiring operator intervention; escalates to Critical theft of BTC if DAO fails to act).

### Likelihood Explanation

- All required inputs (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are derivable from public Bitcoin blockchain data — no secret is needed.
- The attacker does not need to observe the victim's NEAR transaction; they can independently scan for unverified deposit UTXOs and race to register them.
- The only mitigation is the DAO's `reject_refund` call within `unsafe_refund_timelock_sec`, which is an off-chain operational dependency.

**Likelihood: Medium.**

### Recommendation

Bind the `refund_address` to the caller at registration time and allow only the original registrant (or a privileged role) to execute the refund. Alternatively, require that `deposit_msg.refund_address` always be set (non-optional) so the refund destination is committed on-chain in the Bitcoin transaction itself, removing the free `refund_address` parameter entirely. At minimum, record `env::predecessor_account_id()` in the `RefundRequest` and enforce in `execute_refund` that only that account (or a privileged role) may execute it.

### Proof of Concept

1. Alice sends BTC to a deposit address derived from a `DepositMsg` with `refund_address: None`. The deposit is never minted (e.g., wrong amount, light-client not yet synced).
2. Alice calls `request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)`.
3. Attacker observes Alice's pending NEAR transaction (or independently finds the unverified UTXO on Bitcoin). Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with higher gas priority.
4. Attacker's `request_refund_callback` succeeds; `refund_requests[utxo_key]` is stored with `refund_address = attacker_btc_addr`.
5. Alice's callback panics: `"Refund request already exists for this UTXO"`. Alice's NEAR storage deposit is lost.
6. DAO does not notice or is slow. After `unsafe_refund_timelock_sec` elapses, attacker calls `execute_refund(utxo_key, ...)`.
7. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `attacker_btc_addr` and requests an MPC signature. Alice's BTC is stolen. [4](#0-3) [5](#0-4)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
