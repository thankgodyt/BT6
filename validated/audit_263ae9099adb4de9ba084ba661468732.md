### Title
Shielded ZEC Withdrawals Permanently Broken Due to `EXPECTED_ACTIONS_NUMBER=1` Rejecting All Standard Orchard Bundles — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary

`EXPECTED_ACTIONS_NUMBER` is set to `1`, but the code's own comment acknowledges the Orchard reference builder pads every bundle to a minimum of 2 actions for privacy. The exact-equality guard in `extract_orchard_bundle` therefore rejects every standard Orchard bundle, making shielded ZEC withdrawals permanently non-functional. Funds are not permanently locked (NEP-141 refunds on callback panic), but the entire shielded-withdrawal feature is broken for all users.

### Finding Description

`EXPECTED_ACTIONS_NUMBER` is defined as `1`: [1](#0-0) 

The comment on lines 13–15 explicitly states that the Orchard builder automatically pads bundles to meet a minimum action count for privacy, referencing `orchard/src/builder.rs#L36`. The actual `MIN_ACTIONS` constant in the Orchard crate is `2`, meaning any bundle built with the reference builder for a single real output will contain 2 actions (1 real + 1 dummy).

The guard at line 49 uses strict equality: [2](#0-1) 

A bundle with 2 actions fails this check and returns `Err`. In `PsbtWrapper::new`, that `Err` is converted to a hard panic: [3](#0-2) 

This panic occurs inside `ft_on_transfer_callback`, the `#[private]` NEAR callback invoked from the withdrawal path: [4](#0-3) 

The full public call chain is:

```
ft_on_transfer (token_receiver.rs:23)
  → ft_on_transfer_withdraw_chain_specific (contract_methods.rs:221)
    → ft_on_transfer_callback [callback] (contract_methods.rs:110)
      → PsbtWrapper::new (psbt_wrapper.rs:124)
        → extract_orchard_bundle (orchard_policy.rs:38)
          → bundle.actions().len() != 1  →  Err  →  env::panic_str
```

### Impact Explanation

Every shielded ZEC withdrawal submitted by an unprivileged user via `ft_on_transfer` with an Orchard bundle built by any standard wallet will be rejected. The feature is completely non-functional.

**Funds are not permanently locked.** Per NEP-141 semantics, when `ft_on_transfer` returns a `Promise` and that promise panics, the FT contract's `ft_resolve_transfer` refunds the transferred nZEC to the sender. The user loses gas but recovers their tokens. The impact is therefore **Medium**: the shielded-withdrawal feature is permanently broken for all users, requiring operator intervention (contract upgrade) to fix, but there is no direct fund theft or permanent loss.

### Likelihood Explanation

Likelihood is **High** given the condition is triggered by every standard Orchard bundle. Any user attempting a shielded withdrawal with a real wallet will hit this immediately. The code's own comment contradicts the constant value, confirming this is an unintentional bug rather than a deliberate design choice.

### Recommendation

Change the guard from a strict equality to a minimum check, consistent with the Orchard protocol's actual `MIN_ACTIONS = 2`:

```rust
// orchard_policy.rs
pub const MIN_EXPECTED_ACTIONS_NUMBER: usize = 2;

if bundle.actions().len() < MIN_EXPECTED_ACTIONS_NUMBER {
    return Err(format!(
        "Orchard bundle must have at least {} actions, got {}",
        MIN_EXPECTED_ACTIONS_NUMBER,
        bundle.actions().len()
    ));
}
```

Also update `recover_output_with_ovk` logic to iterate over all actions rather than hardcoding index `0`, since the real output may not be at position 0 when dummy actions are present.

### Proof of Concept

1. Build an Orchard bundle using the reference `orchard` crate with one real output to the bridge's Unified Address.
2. Serialize the bundle bytes.
3. Call `ft_on_transfer` on the nZEC FT contract with a `Withdraw` message containing those bytes in `chain_specific_data.orchard_bundle_bytes`.
4. Observe that `ft_on_transfer_callback` panics with `ERR_INVALID_ORCHARD_BUNDLE`.
5. Observe that `ft_resolve_transfer` refunds the nZEC (no permanent lock, but withdrawal is impossible).
6. Assert `bundle.actions().len() == 2` in a local Rust test using the Orchard builder with one real spend/output — this directly confirms the mismatch with `EXPECTED_ACTIONS_NUMBER = 1`.
