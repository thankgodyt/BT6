Audit Report

## Title
Permissionless Trusted-Relayer Auto-Promotion Enables Fee Theft via Unbound `fee_recipient` in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary

Any account can call `apply_for_trusted_relayer` with a 1,000 NEAR deposit and, after `waiting_period_ns` (default 7 days) elapses with no DAO rejection, automatically becomes a trusted relayer. Once trusted, the attacker calls `sign_transfer` on any pending transfer and supplies an arbitrary `fee_recipient`, which is embedded verbatim into the MPC-signed `TransferMessagePayload`. On the destination chain the fee is paid to the attacker's address; the legitimate relayer who serviced the transfer receives nothing. The stake is fully recovered via `resign_trusted_relayer` with no withdrawal delay, making the net economic cost zero beyond gas.

## Finding Description

**Auto-promotion path:** `apply_for_trusted_relayer` records a `RelayerApplication` with the block timestamp. `is_trusted_relayer` returns `true` once `waiting_period_ns` has elapsed — no DAO vote is required. The DAO may call `reject_relayer_application` to cancel a pending application and seize the stake, but if it does not act within the window the applicant is silently promoted. This is confirmed by the integration test `test_apply_auto_promote_relayer`.

**Unbound `fee_recipient` in `sign_transfer`:** The function signature is:

```rust
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,
    fee: &Option<Fee>,
) -> Promise {
```

The only validation performed on `fee` is that it matches the stored transfer message amount (lines 455–460). There is no check that `fee_recipient` matches any stored value, and no check that the caller is the relayer who originally submitted the transfer. The caller-supplied value is placed directly into `TransferMessagePayload` (line 498) and the MPC network signs it:

```rust
let transfer_payload = TransferMessagePayload {
    ...
    fee_recipient,   // ← attacker-controlled
    ...
};
```

**Fee distribution:** On the destination chain the signed payload is used to finalize the transfer; the `fee_recipient` field in the payload determines who receives the fee. On NEAR, `claim_fee_callback` reads `fee_recipient` from the destination-chain proof and enforces `fee_recipient == predecessor_account_id` (lines 1083–1086), so only the account named in the signed payload can claim the fee. A legitimate relayer whose transfer was front-signed by the attacker with `fee_recipient=attacker` cannot claim the fee.

**Stake recovery:** `resign_trusted_relayer` returns the full stake immediately with no withdrawal delay, as confirmed by `test_resign_relayer`. The attacker's net cost is zero beyond gas.

## Impact Explanation

This is fee mis-accounting that directly changes relayer and protocol balances, matching the allowed Critical impact class. The principal transfer amounts reach the correct recipients (the prover still validates proofs), but the entire fee layer for any transfer signed by the attacker is redirected. Legitimate relayers who submitted and serviced transfers lose all fee compensation for those transfers. The attack is repeatable across every pending transfer in the bridge.

## Likelihood Explanation

The entry path is fully permissionless — any account with 1,000 NEAR can execute it. The 7-day waiting period is the only friction, and the DAO must actively monitor and reject every application within that window to prevent promotion. During periods of high bridge activity, aggregate pending fees easily exceed the opportunity cost of locking 1,000 NEAR for 7 days. No privileged access, leaked keys, or external dependency failure is required.

## Recommendation

1. **Bind `fee_recipient` at transfer initiation.** Store the intended `fee_recipient` inside `TransferMessage` when `init_transfer` is called, and in `sign_transfer` use only the stored value — reject any caller-supplied override.
2. **Add a withdrawal delay after `resign_trusted_relayer`.** The stake should remain locked for a challenge period (e.g., equal to `waiting_period_ns`) so it is at risk if misbehavior is detected before the relayer exits.
3. **Require explicit DAO approval** before an applicant becomes trusted, removing the auto-promotion path entirely, or at minimum emit an on-chain event that triggers mandatory DAO review.
4. **Enforce a minimum stake-to-maximum-extractable-fee ratio** so the economic cost of the attack always exceeds the maximum fee value extractable during the stake lock period.

## Proof of Concept

```
1. Attacker calls apply_for_trusted_relayer with 1,000 NEAR deposit.
   → RelayerApplication recorded; waiting_period_ns = 604_800_000_000_000 ns (7 days).
   → DAO does not call reject_relayer_application within 7 days.

2. After 7 days, is_trusted_relayer(attacker) returns true automatically.
   (Confirmed by test_apply_auto_promote_relayer in near/omni-tests/src/relayer_staking.rs:79-161)

3. Attacker enumerates all pending transfers via on-chain events / indexer.

4. For each transfer_id with a non-zero fee, attacker calls:
     sign_transfer(
       transfer_id = <victim_transfer_id>,
       fee_recipient = Some(attacker_account),
       fee = <fee stored in transfer message>
     )
   → fee parameter passes the stored-fee equality check (lib.rs:455-460).
   → TransferMessagePayload is constructed with fee_recipient = attacker (lib.rs:491-500).
   → MPC signs the payload.
   → On the destination chain the fee is paid to attacker, not the legitimate relayer.
   → Legitimate relayer cannot call claim_fee because claim_fee_callback enforces
     fee_recipient == predecessor_account_id (lib.rs:1083-1086), and the signed
     proof names the attacker.

5. Attacker calls resign_trusted_relayer.
   → Full 1,000 NEAR stake returned immediately (confirmed by test_resign_relayer,
     near/omni-tests/src/relayer_staking.rs:295-369).
   → Net cost: zero (minus gas). Net gain: all stolen fees.

Reproducible test: extend test_apply_auto_promote_relayer to (a) create a pending
transfer with a non-zero fee, (b) fast-forward past waiting_period_ns, (c) call
sign_transfer from the attacker with fee_recipient=attacker, (d) assert the
legitimate relayer's claim_fee call fails with OnlyFeeRecipientCanClaim.
```
