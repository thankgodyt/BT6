### Title
`shelleyAfterVoting` Counter Counts All Post-Deadline Blocks Instead of Only Those Within the Stability Window, Enabling Premature Era Transition Under Chain Growth Violation - (`File: ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

`applyHelper` in `Ledger.hs` increments `shelleyAfterVoting` for every block whose slot is at or after `votingDeadline`, with no upper-bound cutoff at `votingDeadline + stabilityWindow`. The intended design (Iteration 4, documented in `civic_time.md`) requires counting only blocks **within the stability window** after the voting deadline. Because the upper-bound slot is never checked, the counter can reach `k` via blocks that fall entirely outside the stability window, causing `shelleyTransition` to signal an era transition even when the stability window itself contained fewer than `k+1` blocks — the exact Chain Growth violation scenario the design is meant to suppress.

---

### Finding Description

`ShelleyTransition` holds a single field `shelleyAfterVoting :: Word32`, described as "the number of blocks in this epoch past the voting deadline." [1](#0-0) 

In `applyHelper`, the counter is incremented with:

```haskell
(if blockSlot blk >= votingDeadline then succ else id) $
  shelleyAfterVoting tickedShelleyLedgerTransition
``` [2](#0-1) 

The `votingDeadline` is computed as `startOfNextEpoch - 2 * stabilityWindow`, and `stabilityWindow` is available in scope: [3](#0-2) 

The condition `blockSlot blk >= votingDeadline` has **no upper bound**. The intended Iteration 4 design requires counting only blocks in `[votingDeadline, votingDeadline + stabilityWindow)`. The missing check is `blockSlot blk < votingDeadline + stabilityWindow`. This is explicitly acknowledged as a bug in the project's own documentation:

> "(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)" [4](#0-3) 

`shelleyTransition` then uses this counter to gate the era transition signal:

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
return newPParamsEpochNo
``` [5](#0-4) 

Because `shelleyAfterVoting` accumulates blocks from the entire post-deadline tail of the epoch — not just the stability window — it reaches `k` even when the stability window itself contained fewer than `k+1` blocks.

---

### Impact Explanation

The security argument for the era transition is: once `k` blocks have been observed after the voting deadline, the last pre-deadline block is immutable and the voting outcome cannot be rolled back. Iteration 4 tightens this to: those `k` blocks must lie within the stability window, because only then does Chain Growth guarantee rollback-safety of the voting outcome.

When the stability window has fewer than `k+1` blocks (a Chain Growth violation), the correct behavior is to suppress the era transition. The buggy counter instead continues accumulating blocks from beyond the stability window and eventually fires the transition. At that point, the voting outcome is **not** rollback-safe: a rollback of up to `k` blocks could reach before the voting deadline and change the governance outcome. Nodes that have already committed to the new era will diverge from nodes that correctly suppressed the transition, breaking cross-era consensus. [6](#0-5) 

---

### Likelihood Explanation

A Chain Growth violation within the stability window is within the Praos adversarial threat model: an adversary controlling a meaningful fraction of stake (well below 50%) can probabilistically suppress block production in a targeted slot window. The adversary needs only to cause fewer than `k` blocks to appear in the `[votingDeadline, votingDeadline + stabilityWindow)` window while allowing normal chain growth afterward. Once the buggy counter reaches `k` via post-stability-window blocks, the premature transition is committed. This is a crafted-chain/network-message attack requiring no privileged access.

---

### Recommendation

Add an upper-bound slot check in `applyHelper` so that only blocks within the stability window after the voting deadline are counted:

```haskell
shelleyAfterVoting =
  ( if blockSlot blk >= votingDeadline
       && blockSlot blk < votingDeadline + SlotNo swindow
    then succ
    else id
  ) $ shelleyAfterVoting tickedShelleyLedgerTransition
```

This aligns the implementation with the Iteration 4 design described in `civic_time.md` and ensures the `shelleyAfterVoting >= k` guard in `shelleyTransition` only fires when the stability window itself contains at least `k` blocks, preserving the rollback-safety invariant. [7](#0-6) 

---

### Proof of Concept

**Setup:** epoch length = `10k/f` slots, stability window = `3k/f` slots, `k = 2160` (mainnet). Voting deadline = `startOfNextEpoch - 2 * stabilityWindow`.

1. Adversary causes a Chain Growth violation: only `k - 1 = 2159` blocks appear in `[votingDeadline, votingDeadline + stabilityWindow)`.
2. After the stability window, normal chain growth resumes. One more block arrives at slot `votingDeadline + stabilityWindow + 1`.
3. `applyHelper` increments `shelleyAfterVoting` for this block (slot `>= votingDeadline`, no upper bound check).
4. `shelleyAfterVoting` reaches `k = 2160`.
5. `shelleyTransition` evaluates `guard $ shelleyAfterVoting >= fromIntegral k` → `True`.
6. `singleEraTransition` returns `Just epochNo`, signaling the HFC to schedule the era transition.
7. The stability window had only `k - 1` blocks, so the voting outcome is **not** rollback-safe. A rollback of `k` blocks can still reach before the voting deadline and alter the governance outcome, while the node has already committed to the new era. [5](#0-4) [8](#0-7)
