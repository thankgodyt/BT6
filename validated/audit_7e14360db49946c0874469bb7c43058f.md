Audit Report

## Title
Reentrancy in `initTransfer1155` Allows Duplicate Nonce Emission with Zero Token Lockup — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` increments `currentOriginNonce` at the top of the function but reads it again — after an untrusted external call to `IERC1155.safeTransferFrom` — when emitting `InitTransfer` and calling `initTransferExtension`. No `nonReentrant` guard exists anywhere in the contract. A malicious ERC-1155 token can reenter `initTransfer1155` during `safeTransferFrom`, causing both the reentrant and original invocations to emit `InitTransfer` with the same nonce (nonce=2) while locking zero tokens on EVM, enabling the NEAR bridge to mint tokens with no corresponding collateral.

## Finding Description

`currentOriginNonce` is a storage variable declared at line 45:

```solidity
uint64 public currentOriginNonce;
```

In `initTransfer1155` (L448), the nonce is incremented first:

```solidity
currentOriginNonce += 1;   // storage: nonce = N
```

Then an untrusted external call is made (L458–464):

```solidity
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender, address(this), tokenId, amount, ""
);
```

Then `currentOriginNonce` is read again from storage (L471, L483) — **after** the external call — for both `initTransferExtension` and `emit BridgeTypes.InitTransfer`.

A malicious ERC-1155 token controls the body of `safeTransferFrom` entirely. It can reenter `initTransfer1155` before returning. The `onERC1155Received` guard at L522–535 only blocks direct sends (checks `operator != address(this)`); it does not prevent reentrancy into `initTransfer1155` itself, and a malicious token need not call `onERC1155Received` at all.

**Attack trace (initial `currentOriginNonce = 0`):**

| Step | Context | Action | `currentOriginNonce` |
|---|---|---|---|
| 1 | Original call | `+= 1` | **1** |
| 2 | Original call | calls `safeTransferFrom` → malicious token reenters | — |
| 3 | Reentrant call | `+= 1` | **2** |
| 4 | Reentrant call | calls `safeTransferFrom` → malicious token does NOT reenter, transfers 0 tokens | — |
| 5 | Reentrant call | reads `currentOriginNonce = 2`, emits `InitTransfer(nonce=2)` | 2 |
| 6 | Original call resumes | reads `currentOriginNonce = 2`, emits `InitTransfer(nonce=2)` | 2 |

Result: two `InitTransfer` events both carrying `nonce=2`; nonce=1 is never emitted; zero tokens are locked in either invocation because the malicious token's `safeTransferFrom` never performs an actual balance transfer.

No `nonReentrant` modifier or `ReentrancyGuard` import exists anywhere in the EVM contract suite — confirmed by exhaustive grep across all `.sol` files. The two `slither-disable-next-line reentrancy-no-eth` comments (L161) suppress static-analysis warnings only; they provide zero runtime protection.

## Impact Explanation
This directly matches the allowed critical impact: **unauthorized minting / balance manipulation — nonce/replay misuse that changes user or protocol balances**. The NEAR bridge relayer observes `InitTransfer(nonce=2)` and processes it, minting ERC-1155-equivalent tokens on NEAR. No collateral is held on EVM. The attacker receives bridged tokens on NEAR for free. Nonce=1 is permanently skipped, also corrupting the nonce sequence for all subsequent legitimate transfers.

## Likelihood Explanation
Any unprivileged user can deploy a malicious ERC-1155 contract (no admin permission required) and call the public `initTransfer1155` function directly. `initTransfer1155` performs no token-registration or whitelist check before invoking `safeTransferFrom`. The attack is repeatable: each invocation can produce a fresh duplicate-nonce pair. No victim interaction, no front-running dependency, and no privileged role is needed.

## Recommendation
Apply a `nonReentrant` modifier (OpenZeppelin `ReentrancyGuardUpgradeable`) to `initTransfer1155` (and symmetrically to `initTransfer` and `finTransfer` which also make external calls). Additionally, cache the incremented nonce in a local variable immediately after the increment and use only the local variable thereafter, eliminating the storage re-read after the external call:

```solidity
uint64 nonce = currentOriginNonce + 1;
currentOriginNonce = nonce;
// ... external call ...
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Both fixes together (reentrancy guard + local nonce cache) are required for defense in depth.

## Proof of Concept
Deploy a Foundry test with a malicious ERC-1155 stub:

```solidity
contract MaliciousERC1155 {
    OmniBridge bridge;
    bool reentered;

    function safeTransferFrom(address, address, uint256, uint256, bytes memory) external {
        if (!reentered) {
            reentered = true;
            // reenter with same params; transfers 0 tokens in both calls
            bridge.initTransfer1155(address(this), 0, 1e18, 0, 0, "attacker.near", "");
        }
        // return without transferring anything
    }
    // ... minimal ERC-1155 interface stubs ...
}
```

1. Deploy `OmniBridge` and `MaliciousERC1155`.
2. Call `bridge.initTransfer1155(address(malicious), 0, 1e18, 0, 0, "attacker.near", "")`.
3. Assert: two `InitTransfer` events are emitted, both with `originNonce = 2`; `currentOriginNonce == 2`; bridge holds 0 ERC-1155 tokens.
4. Confirm nonce=1 was never emitted by checking event logs.

The EVM-side invariant violation (duplicate nonce, zero lockup) is fully demonstrable in a local Foundry unit test without requiring a live NEAR environment.
