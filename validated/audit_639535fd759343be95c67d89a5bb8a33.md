### Title
Missing Timeout for `FoundIntersection` (PreObjector) Jumper State Allows Adversarial Peers to Stall LoE Anchor Indefinitely - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client/Jumping.hs`)

---

### Summary

The ChainSync Jumping (CSJ) state machine contains a `FoundIntersection` jumper sub-state (the "PreObjector" role) that has no timeout mechanism and no Limit-on-Patience (LoP) bucket leaking. A peer in this state is permanently blocked in `nextInstruction` waiting for a jump instruction that will never arrive, while the LoP bucket is paused. Two coordinated adversarial peers acting as Dynamo and Objector can exploit this to keep the honest `FoundIntersection` peer dormant indefinitely, preventing the LoE anchor from advancing and stalling the syncing node's chain selection.

---

### Finding Description

The `ChainSyncJumpingJumperState` type defines three sub-states for a Jumper peer:

- `Happy` — waiting for the next jump from the Dynamo
- `LookingForIntersection` — bisecting to find the exact disagreement point
- `FoundIntersection` — intersection found; peer is dormant, waiting to be promoted to Objector [1](#0-0) 

Once a peer reaches `FoundIntersection`, the `nextInstruction` function blocks it on `retry_` because `nextJumpVar` is `Nothing` (cleared by `lookForIntersection`): [2](#0-1) 

The Dynamo only writes new jump instructions to `Happy{}` jumpers, never to `FoundIntersection` jumpers: [3](#0-2) 

The LoP bucket is explicitly **paused** while a peer waits in `nextInstruction`: [4](#0-3) 

The only escape from `FoundIntersection` is promotion to Objector via `electNewObjector`, which is only triggered when the current Objector is disengaged or disconnected: [5](#0-4) 

The design document explicitly acknowledges this deadlock scenario and the fact that it "might last a very long time": [6](#0-5) 

The follow-up work section further acknowledges the residual issue with PreObjector timeouts remains unresolved: [7](#0-6) 

---

### Impact Explanation

When an honest peer is in `FoundIntersection` state and the current Objector is adversarial:

1. The honest peer's ChainSync client is blocked in `nextInstruction` with LoP paused — it cannot send or receive headers.
2. The adversarial Dynamo and Objector can each send a header just beyond the forecast range, causing the LoP bucket to stop leaking for them as well.
3. The LoE anchor cannot advance because the honest peer's candidate fragment is frozen.
4. The syncing node cannot select the honest chain beyond the LoE anchor, violating Sync Safety: the node may permanently prefer the adversarial chain served by the Dynamo and Objector over the honest chain held dormant in the `FoundIntersection` peer.

This maps to: **High — chain selection bug that lets unprivileged peers make an honest syncing node prefer a non-canonical chain beyond the intended security assumptions.**

---

### Likelihood Explanation

- Requires two coordinated adversarial peers (Dynamo + Objector), both reachable as ordinary unprivileged upstream peers.
- No stake, keys, or privileged access required.
- The scenario is explicitly described in the design document as a real attack vector, not a theoretical one.
- The relaxed GDD trigger is intended to mitigate it, but the follow-up work section confirms the PreObjector timeout tightening is still outstanding, leaving a residual window.

---

### Recommendation

Introduce a wall-clock timeout for the `FoundIntersection` jumper state, analogous to the `intersectTimeout` used for the `LookingForIntersection` phase. If a peer remains in `FoundIntersection` longer than a configurable deadline without being promoted to Objector, it should be disconnected. This directly mirrors the recommendation in the external report: introduce a mechanism to blame/evict a peer that has been stuck in an intermediate state for too long.

The design document itself calls this out: [7](#0-6) 

---

### Proof of Concept

**Setup:** Syncing node with Genesis enabled (LoE + GDD + CSJ active). Three peers: one honest (H), two adversarial (A1 = Dynamo, A2 = Objector).

1. A1 becomes Dynamo and serves headers up to the forecast range.
2. H disagrees with A1's chain at some point, goes through `LookingForIntersection`, and reaches `FoundIntersection`. H is now dormant — `nextJumpVar` is `Nothing`, LoP is paused.
3. A2 is promoted to Objector (older intersection than H's).
4. A1 and A2 each send one header just beyond the forecast range. Per the LoP design, the bucket stops leaking for both: [8](#0-7) 

5. The relaxed GDD trigger requires A1 to have sent a header beyond the GDD window to disconnect A2. If A1 and A2 coordinate to both stay just at the boundary, neither is disconnected.
6. H remains in `FoundIntersection` indefinitely — no timeout fires, no LoP fires, `electNewObjector` is never called.
7. The LoE anchor is frozen at the intersection of A1 and A2's chains. The syncing node cannot select the honest chain. [9](#0-8)

data ChainSyncJumpingJumperState blk
  = -- | The jumper is happy with the dynamo, and we hold the jump info of the
    -- last accepted jump.
    Happy JumperInitState !(Maybe (JumpInfo blk))
  | -- | The jumper disagrees with the dynamo and we are searching where exactly
    -- that happens. All we know is a point where the jumper agrees with the
    -- dynamo and a point where the jumper disagrees with the dynamo, carried by
    -- this constructor.
    --
    -- INVARIANT: The tip of the fragment in the good jump info (first argument)
    -- is in the fragment of the bad jump info or is an ancestor of it.
    LookingForIntersection !(JumpInfo blk) !(JumpInfo blk)

    -- The init state indicates the initialization to use for the objector in
    -- case this jumper is promoted.

-- | Look into all dissenting jumper and promote the one with the oldest

electNewObjector ::
  MonadSTM m =>
  Context m peer blk ->
  STM m (TraceCsjReason -> TraceEventCsj peer blk)
electNewObjector context =
  NoLongerObjector <$> do
    peerStates <- toList <$> cschcSeq (handlesCol context)
    dissentingJumpers <- collectDissentingJumpers peerStates
    let sortedJumpers = sortOn (pointSlot . fst . snd) dissentingJumpers
    case sortedJumpers of
      [] -> pure Nothing
      (peer, (badPoint, (initState, goodJumpInfo, handle))) : _ -> do
        writeTVar (cschJumping handle) $ Objector initState goodJumpInfo badPoint
        pure $ Just peer

```markdown
There are two possible deadlocks introduced by CSJ.
Both can be resolved by implementing additional disconnections according to Genesis density comparisons.

- Without CSJ, the GDD is always comparing each peer to the best header chain a HAA-satisfying peer can provide.
  With CSJ, the HAA-satisfying peers might instead be dormant as PreObjectors, with the Dynamo and Objector both adversarial.

  There's no guarantee in that scenario that the competing header chains of the Dynamo and Objector will (eventually) include more than Kcp headers.
  Since that is one of the plain GDD's required conjuncts, the syncing node would be stuck.
  This state might last a very long time, violating Sync Liveness, since the Dynamo and Objector could each send a header beyond the forecast range in order to also avoid the LoP.

  To prevent this attack, the GDD trigger is relaxed for the sake of CSJ.
  Specifically, Q does not need to have sent more than Kcp (valid) headers after the LoE anchor if P has already sent a header beyond the GDD window.

  It's safe to make the GDD disconnect in more scenarios, as long as it will still never disconnect from an HAA-satisfying peer outside of a disaster scenario.
  In this case, if there has been no disaster and P satisfies the HAA, then Praos Chain Growth ensures P's chain will have more than Kcp headers in the GDD window.
  If this relaxed GDD were to disconnect from P, then Q must have at least as many headers as P, and so the plain GDD's conjunct would also have been satisfied.

- Similarly, if the HAA-satisfying peers are all dormant, then it's possible that the node's selection is simultaneously longer than every peer's header chain and also branches off from some proper prefix of the LoE anchor.
  This is an unusual scenario, but may arise, for example, if the previous Dynamo recently disconnected (which implies it did not satisfy the HAA).
  In this case, the DBF logic would idle, since no peer's header chain is better than the selection --- the node would not select the peers' blocks even if they did somehow arrive, since they're worse than the current selection.
  Moreover, deadlock is possible, since the Dynamo and Objector forecast ranges' do not necessarily include the entire GDD window.
  Thus the GDD is not necessarily able to make a decision between them, just as in the previous deadlock.
```
