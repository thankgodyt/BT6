### Title
Chain Selection Bypass via Ignored Peras Weight Boosts in `checkPreferTheirsOverOurs` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client evaluates whether a candidate chain is preferable to the local chain using `emptyPerasWeightSnapshot` — permanently ignoring all Peras vote-certificate weight boosts. This is structurally identical to the reported Solidity bug: a function that should return `base + accumulated_delta` returns only `base`, causing a validation gate to fire incorrectly. Here, the gate is `CandidateTooSparse`, which disconnects the peer. When the canonical chain has fewer blocks but higher Peras-boosted weight than the local chain, the node disconnects from every peer offering it, locking itself onto a lighter, non-canonical chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is the ChainSync client's guard that rejects candidate chains that are not preferable to the local chain:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always ignores Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

`preferAnchoredCandidate` has two code paths gated on `isEmptyPerasWeightSnapshot`:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- compares only by SelectView (BlockNo) — no weight boost
      ...
  | otherwise =
      -- uses weightedSelectView: BlockNo + PerasWeightBoost
      case AF.intersect ours cand of
        Just (_, _, oursSuffix, candSuffix) ->
          preferCandidate cfg
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix)
``` [2](#0-1) 

By hardcoding `emptyPerasWeightSnapshot`, `checkPreferTheirsOverOurs` always takes the first branch and compares chains by raw `BlockNo` only. The total weight of a fragment is defined as:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [3](#0-2) 

The function returns only `wsvBlockNo` (the base), discarding `wsvWeightBoost` (the accumulated Peras delta) — exactly the `position.collateral` vs `position.collateral + pnlWithFees` pattern.

Every other chain-comparison call site in the same module correctly passes the live snapshot:

```haskell
chainSelectionForBlock cdb@CDB{..} blockCache hdr punish = electric $ do
  (invalid, curChain, weights) <-
    atomically $
      (,,)
        <$> ...
        <*> Query.getCurrentChain cdb
        <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
  ...
  ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [4](#0-3) [5](#0-4) 

The inconsistency is that the ChainSync client gate uses stale (empty) weights while the downstream chain-selection engine uses live weights. The gate fires first and severs the connection before chain selection can evaluate the candidate.

---

### Impact Explanation

**Classification**: High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

When Peras is active, a fork can produce two branches:

| Branch | Blocks | Peras boosts | Total weight |
|--------|--------|--------------|--------------|
| Canonical (A) | 10 | 5 | 15 |
| Adversarial (B) | 12 | 0 | 12 |

1. The adversary serves branch B (12 blocks). `checkPreferTheirsOverOurs` passes (12 > 10 by `BlockNo`) → node adopts B.
2. Honest peers serve branch A (10 blocks, weight 15). `checkPreferTheirsOverOurs` fails (10 < 12 by `BlockNo`) → `CandidateTooSparse` → node disconnects from all honest peers.
3. Node is permanently locked on branch B (total weight 12), which is lighter than the canonical chain (total weight 15).

This constitutes a durable chain-selection error: the node accepts an invalid (lighter) chain and rejects the canonical one, violating the Peras chain-selection invariant that the heaviest chain wins.

---

### Likelihood Explanation

- **Peras activation**: Peras is implemented and the weight infrastructure is live in this codebase; the protocol is designed for production deployment.
- **Fork scenario**: Any natural or adversarially induced fork where one branch accumulates Peras certificates while the other grows longer by block count triggers the bug.
- **Adversary capability**: The adversary needs only enough stake to produce a chain longer (by block count) than the Peras-boosted canonical branch — no key compromise, no stake majority, no social engineering required. A crafted sequence of blocks from an unprivileged peer is sufficient.
- **The TODO comment** (`TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers recognize this check is incorrect in the Peras context but have not yet removed it.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` threaded through the ChainSync client environment, consistent with how `chainSelectionForBlock` and `constructPreferableCandidates` already use it. Alternatively, remove the check entirely as the TODO suggests, since downstream chain selection already performs the correct weighted comparison.

---

### Proof of Concept

**Setup** (private testnet, Peras active):

1. Run two honest nodes A and B sharing a common prefix of 100 blocks.
2. Induce a fork: node A's branch grows to 110 blocks and accumulates 10 Peras certificates (total weight 120); adversary's branch grows to 115 blocks with no Peras certificates (total weight 115).
3. Connect a victim node (current chain = adversary's 115-block branch) to node A.
4. Node A sends headers for its 110-block branch. `checkPreferTheirsOverOurs` evaluates: `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag(115) theirFrag(110)` → `ShouldNotSwitch` (110 < 115 by `BlockNo`) → `throwSTM CandidateTooSparse`.
5. Victim disconnects from node A.
6. Victim remains on the adversary's 115-block branch (weight 115) and never adopts the canonical 110-block branch (weight 120).

The root cause is the hardcoded `emptyPerasWeightSnapshot` at line 1842 of `ChainSync/Client.hs`, which causes the function to return the block-count-only comparison (the "base") instead of the block-count-plus-Peras-boost comparison (the "base + accumulated delta"). [6](#0-5)
