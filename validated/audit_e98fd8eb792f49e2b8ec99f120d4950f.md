### Title
`revalidateHeader` Silently Accepts Any Header in Production Builds Due to Compile-Gated Envelope Check — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` is the "fast-path" re-validation function used during chain selection when a header is assumed to have been previously validated. In production builds (compiled without `-DENABLE_ASSERTIONS`), the only guard on the envelope check — `assertWithMsg envelopeCheck` — is a **compile-time no-op**. Combined with `reupdateChainDepState` unconditionally skipping all cryptographic checks, the function returns a freshly constructed `HeaderState` without performing **any** validation whatsoever. This is the direct structural analog of the `StaticHyVM` finding: a call that silently "succeeds" regardless of whether the underlying precondition holds.

---

### Finding Description

`revalidateHeader` is defined in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
 where
  chainDepState' =
    reupdateChainDepState
      (configConsensus cfg)
      (validateView (configBlock cfg) hdr)
      (blockSlot hdr)
      (tickedHeaderStateChainDep st)

  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [1](#0-0) 

`assertWithMsg` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [2](#0-1) 

Without the `ENABLE_ASSERTIONS` compile flag (the default for production node builds), `assertWithMsg` unconditionally returns its second argument, discarding the `Either String ()` result entirely. The `envelopeCheck` — which validates block number consecutiveness, slot monotonicity, and hash chain linkage — is computed but its result is **thrown away**.

`reupdateChainDepState` is separately documented and implemented to skip all cryptographic checks (KES/VRF signature verification) by design:

> "Re-apply a header to the same 'ChainDepState' we have been able to successfully apply to before. Since a header can only be applied to a single, specific, 'ChainDepState', if we apply a previously applied header again it will be applied in the very same 'ChainDepState', and therefore can't possibly fail. It is worth noting that since we already know that the header is valid w.r.t. the provided 'ChainDepState', no validation checks should be performed." [3](#0-2) 

The result: in production, `revalidateHeader` constructs and returns a `HeaderState` for **any** header passed to it, with zero envelope or cryptographic validation.

The `prev` set used in `mkAps` to decide whether to use `ReapplyRef`/`ReapplyVal` (which triggers the reapply path) is populated from `validBlockPoints`, which tracks blocks successfully applied to the ledger: [4](#0-3) 

This set tracks **block** application success, not independent header-state validation. The `revalidateHeader` precondition ("validated before w.r.t. the same exact `HeaderState`") is enforced only by the now-disabled `assertWithMsg`.

---

### Impact Explanation

If `revalidateHeader` is invoked with a header whose envelope is inconsistent with the current `HeaderState` — e.g., a header with a non-consecutive block number, a non-monotone slot, or a broken hash chain — the function silently produces a `HeaderState` as if the header were valid. This corrupted `HeaderState` is then used downstream in chain selection and header-state history tracking.

The `HeaderStateHistory` maintained by the ChainSync client is built from these `HeaderState` values. An incorrect `HeaderState` in the history can cause the node to:
- Accept a candidate chain fragment whose headers do not form a valid chain
- Advance `mostRecentIntersection` to a point that does not correspond to a real validated intersection
- Make chain-selection decisions based on a corrupted header-state history

This maps to the **High** impact category: a header-state bug that lets a crafted on-disk or network input make an honest node prefer a non-canonical or less-secure chain.

---

### Likelihood Explanation

The precondition for `revalidateHeader` — that the header was previously validated against the exact same `HeaderState` — is maintained by the consensus layer's own logic under normal operation. The `prev` set in `mkAps` is populated from blocks that passed full ledger validation, which is a strong guarantee.

However, the risk is non-null in two realistic scenarios:

1. **VolatileDB/ImmutableDB corruption or replay**: During node initialization, blocks are replayed from the ImmutableDB using `reapplyBlockLedgerResult` (which calls `revalidateHeader` via `reapplyExtLedgerState`). If the ImmutableDB contains a block whose header does not satisfy the envelope invariants (e.g., due to silent corruption that passed CRC checks but not hash-chain checks), `revalidateHeader` will silently accept it in production.

2. **Fork-switch race**: During chain selection, the `prev` set is computed from a snapshot of the ledger state. A concurrent fork switch can cause the `prev` set to include points from a chain that is no longer the current chain, potentially causing `revalidateHeader` to be called with a header from a different fork against a `HeaderState` it was never validated against.

The likelihood is **low** for an unprivileged remote peer to directly trigger this, but **medium** for a crafted on-disk input (e.g., a corrupted snapshot or ImmutableDB chunk file that passes CRC but fails hash-chain checks).

---

### Recommendation

- **Short term**: Replace `assertWithMsg envelopeCheck` in `revalidateHeader` with a proper runtime check that is always active in production. The envelope check is cheap (no cryptography) and should not be gated behind a compile flag. At minimum, use `error` unconditionally on failure rather than `assertWithMsg`.

- **Long term**: Audit all uses of `assertWithMsg` in production consensus code paths to identify other checks that are silently disabled in production builds. Consider whether the `ENABLE_ASSERTIONS` flag should be enabled by default in production node builds, or whether critical invariant checks should be promoted to always-on runtime checks.

### Proof of Concept

**Root cause** — `assertWithMsg` is a no-op in production: [2](#0-1) 

**Call site** — `revalidateHeader` relies on `assertWithMsg` as its only envelope guard: [5](#0-4) 

**`reupdateChainDepState` for Praos** — skips all KES/VRF checks, only updates nonces and OCert counters: [6](#0-5) 

**`mkAps` decision logic** — uses block-level `prev` set to decide reapply vs. apply, conflating block validation with header-state validation: [4](#0-3) 

**Concrete scenario**: A node initializes from an ImmutableDB chunk file that has been silently corrupted such that block N's `prevHash` field does not match block N-1's hash, but the CRC32 checksum still passes (e.g., two bytes were swapped symmetrically). During replay, `reapplyBlockLedgerResult` calls `revalidateHeader` for each block. In production, `assertWithMsg` discards the `Left` result from `validateEnvelope` (which would catch the hash-chain break), and the node builds its entire in-memory `HeaderStateHistory` on top of a corrupted chain, permanently diverging from the canonical chain without any error or log message.
