Audit Report

## Title
Decimal Normalization to Zero Permanently Freezes User Funds - (File: near/omni-bridge/src/lib.rs)

## Summary
`init_transfer` burns or locks user tokens before validating that the normalized transfer amount is non-zero. When a user sends an amount smaller than the decimal normalization factor (e.g., any amount below `10^(origin_decimals - decimals)`), the full token amount is consumed at `init_transfer` time, but `sign_transfer` unconditionally reverts with `InvalidAmountToTransfer` for that transfer ID. No public cancel or refund function exists, leaving the funds permanently frozen.

## Finding Description
`normalize_amount` performs floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`init_transfer` validates only that `fee < amount`:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It does not check that `normalize_amount(amount - fee, decimals) > 0`. Control then flows to `init_transfer_internal`, which burns or locks the full amount and returns `U128(0)` (no refund):

```rust
// near/omni-bridge/src/lib.rs L1850-1864
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
} else { ... }
U128(0)
```

Later, when a relayer calls `sign_transfer`, the normalized amount is computed and checked:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

For any transfer where the raw amount is below the normalization factor, this `require!` always panics. The transfer message remains in `pending_transfers` indefinitely. A search for `pub fn cancel`, `pub fn refund`, and `pub fn withdraw_transfer` in `lib.rs` returns no matches — there is no public recovery path.

The existing code comment at L2781–2783 acknowledges that "dust stays locked/burned" when `fee = 0`, but this refers to the sub-unit remainder of a larger amount that still normalizes to a positive value. It does not cover the distinct case where the entire `amount_without_fee` normalizes to zero, which makes `sign_transfer` permanently unreachable for that transfer.

## Impact Explanation
This causes **permanent freezing of bridged funds**: tokens are burned (for deployed bridge tokens) or locked (for native tokens) at `init_transfer` time, but the corresponding transfer can never be finalized because `sign_transfer` unconditionally reverts. This matches the allowed critical impact: *permanent freezing of bridged funds* and *decimal/normalization abuse that changes user or protocol balances*.

## Likelihood Explanation
Any unprivileged user can trigger this via `ft_transfer_call` on NEAR. The required conditions are: (1) a token registered with `origin_decimals > decimals` (e.g., 24 vs. 18, a common configuration), and (2) the user sends `amount_without_fee < 10^(origin_decimals - decimals)`. This can happen accidentally when a user sends a "dust" amount. No special privileges or external collusion are required.

## Recommendation
Add a normalization check in `init_transfer` (before tokens are burned/locked) to reject transfers whose normalized amount is zero:

```rust
// In init_transfer, after building transfer_message and before calling init_transfer_internal:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the existing check in `sign_transfer` (L482–485) and ensures tokens are never burned/locked for a transfer that can never be finalized.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = `10^6 = 1_000_000`).
2. User calls `ft_transfer_call` with `amount = 500_000` and `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (`0 < 500_000` ✓).
4. `init_transfer_internal` burns/locks `500_000` tokens and returns `U128(0)` — tokens consumed, no refund.
5. Relayer calls `sign_transfer` for this transfer ID.
6. `normalize_amount(500_000, Decimals { origin_decimals: 24, decimals: 18 })` = `500_000 / 1_000_000` = `0`.
7. `require!(0 > 0, ...)` → panics with `InvalidAmountToTransfer`.
8. The transfer message remains in `pending_transfers`; the `500_000` tokens are permanently lost with no recovery path.
