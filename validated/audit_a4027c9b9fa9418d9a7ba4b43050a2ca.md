### Title
Unvalidated `refund_address` stored at `request_refund_callback` time causes `build_refund_output` to panic at `execute_refund` time, permanently locking the deposit UTXO until operator rejection — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

`request_refund_callback` stores the caller-supplied `refund_address` as a raw string with no address-format or chain-compatibility check. `build_refund_output`, called only at `execute_refund` time, performs the first validation via two panicking `.expect()` calls. An unprivileged attacker can submit a syntactically valid but script-less address (e.g., a Zcash Unified Address carrying only an Orchard receiver) and permanently wedge the refund request: every subsequent `execute_refund` call panics, the request persists in storage, and the deposit UTXO is locked until a DAO/Operator manually calls `reject_refund`.

### Finding Description

**Step 1 — Attacker calls `request_refund` with a Zcash Orchard-only Unified Address.**

`request_refund` is publicly callable (no `#[trusted_relayer]` at the function level, only at the impl level which does not gate all functions in the block). [1](#0-0) 

**Step 2 — `request_refund_callback` stores the address without any validation.**

The callback verifies the light-client proof, checks the output script matches the deposit address, and checks for duplicates — but never calls `Address::parse()` on `refund_address`. The raw string is stored verbatim. [2](#0-1) 

**Step 3 — `execute_refund` (transparent path) calls `build_refund_output`.**

For the Zcash bridge, `execute_refund_callback` takes the transparent branch when `orchard_bundle.is_none()` and calls `build_refund_output`. [3](#0-2) 

**Step 4 — `build_refund_output` panics on the Orchard-only Unified Address.**

`Address::parse()` succeeds — a Unified Address with only an Orchard receiver is syntactically valid Zcash. But `script_pubkey()` iterates the receiver list, finds no `P2pkh` or `P2sh` receiver, and returns `Err("No receiver found in address")`. The `.expect()` panics. [4](#0-3) [5](#0-4) 

**Step 5 — The refund request persists; the UTXO is locked.**

Because `finalize_refund_with_psbt` is never reached, `verified_deposit_utxo` is never updated and the `RefundRequest` entry is never removed. Every future `execute_refund` call (transparent path) panics identically. The deposit UTXO is stuck until a DAO/Operator calls `reject_refund`. [6](#0-5) 

**The same panic path exists on the Bitcoin bridge** for any non-Bitcoin address (wrong chain prefix/HRP), where `Address::parse(..., Chain::BitcoinMainnet).expect("Invalid refund address")` panics at the parse step. [7](#0-6) 

### Impact Explanation

The deposit UTXO is locked in a refund request that can never be executed. The attacker's own funds are frozen until a DAO/Operator manually intervenes to call `reject_refund`. After rejection the user may resubmit with a valid address, so funds are not permanently destroyed — but the bridge invariant "every stored refund request is executable after the timelock" is violated, and operator intervention is mandatory. This matches **Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention**.

### Likelihood Explanation

The attack requires the attacker to control the deposit (they must have sent BTC/ZEC to the bridge address derived from their `deposit_msg`), so they are locking their own funds. The practical harm is forcing operator attention and blocking the refund pipeline for that UTXO. The path is fully local-testable with no external dependencies.

### Recommendation

Validate `refund_address` against the configured chain inside `request_refund_callback` before storing the request. Specifically, call `Address::parse(&refund_address, config.chain.clone())` and, for the transparent path, additionally call `.script_pubkey()` to confirm a non-`Err` result. Reject the callback (return `false`) if either check fails, so the invariant "every stored refund request is executable" is enforced at storage time rather than deferred to execution time.

### Proof of Concept

```

1. Construct a Zcash Unified Address containing ONLY an Orchard receiver
   (no P2PKH, no P2SH component).  Such an address is valid Zcash syntax
   and passes ZcashAddress::try_from_encoded() successfully.

2. Call request_refund(deposit_msg, orchard_only_ua_string, tx_bytes, vout, proof, None)
   with a valid deposit tx and proof.  request_refund_callback stores the
   address without calling Address::parse().

3. Wait for the timelock to elapse, then call execute_refund(utxo_storage_key, None)
   (transparent path, no chain_specific_data).

4. execute_refund_callback calls build_refund_output(&refund_request.refund_address, …).
   Address::parse() returns Ok(Address::Unified { … }).
   script_pubkey() iterates receivers, finds no P2pkh/P2sh, returns
   Err("No receiver found in address").
   .expect("Invalid refund script_pubkey") panics.

5. The NEAR transaction reverts; the RefundRequest entry remains in storage.
   Repeat step 3 — it panics every time.
   Only a DAO/Operator reject_refund call can unblock the UTXO.
```

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
