### Title
Permissionless `execute_refund` Allows Any Caller to Hijack Refund Signing Rights, Permanently Locking Victim's BTC — (File: `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs`)

---

### Summary

`execute_refund` is callable by any NEAR account after the timelock. The caller becomes the `account_id` owner of the resulting `BTCPendingInfo`. On Bitcoin the refund PSBT is fully deterministic, so a second call by the victim produces the same txid and is rejected with "pending info already exist." An attacker who front-runs the victim's `execute_refund` call acquires exclusive signing rights over the refund transaction and can refuse to sign, permanently locking the victim's BTC with no on-chain recovery path.

---

### Finding Description

`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` (line 582) carries no restriction on who the caller may be:

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
```

`internal_execute_refund` in `contracts/satoshi-bridge/src/bitcoin_utils/refund.rs` (lines 18–44) captures `env::predecessor_account_id()` as the `caller` and passes it directly to `finalize_refund_with_psbt`:

```rust
let caller = env::predecessor_account_id();
self.finalize_refund_with_psbt(
    caller, refund_request, psbt, refund_amount, utxo_storage_key,
);
```

`finalize_refund_with_psbt` in `contracts/satoshi-bridge/src/refund.rs` (lines 315–402) stores the `BTCPendingInfo` with `account_id: caller.clone()` and inserts the UTXO into `verified_deposit_utxo`:

```rust
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
};
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
```

On Bitcoin the PSBT is fully deterministic (same outpoint + same output → same txid). A second call to `execute_refund` for the same request rebuilds an identical PSBT, hits the `"pending info already exist"` guard, and panics. The victim cannot re-execute.

The `verified_deposit_utxo` insertion also permanently blocks `verify_deposit` for that UTXO. The only operator recovery path — `reject_refund` followed by `remove_refund_pending_tx_id` — removes the request and the pending info but leaves the UTXO in `verified_deposit_utxo`, so neither `verify_deposit` nor a fresh `execute_refund` can ever succeed. No function exists to remove an entry from `verified_deposit_utxo`. Recovery requires a contract upgrade.

---

### Impact Explanation

An attacker who calls `execute_refund` before the victim acquires exclusive signing rights over the refund transaction. If the attacker refuses to call `sign_btc_transaction`, the victim's BTC remains locked in the bridge-controlled UTXO indefinitely. The operator's only cleanup path (reject + remove) leaves the UTXO permanently blocked in `verified_deposit_utxo`, making the BTC unrecoverable without a contract upgrade. This constitutes **permanent locking of user funds**.

---

### Likelihood Explanation

- `execute_refund` is fully permissionless after the timelock; any NEAR account qualifies.
- The attacker needs only 1 NEAR attached deposit (non-refundable, per `required_balance_for_execute_refund`).
- The timelock window (hours to days) gives the attacker ample time to observe the on-chain `RefundRequested` event and front-run the victim.
- The attacker does not need to be registered; `finalize_refund_with_psbt` auto-creates the account if absent.
- Cost to attacker: ~1 NEAR. Damage: victim's entire BTC deposit.

---

### Recommendation

1. **Restrict `execute_refund` to the original depositor** (the account that called `request_refund`) or to the BTC `refund_address` owner, or to privileged roles. Store the requesting account in `RefundRequest` and enforce `env::predecessor_account_id() == refund_request.requester` (or allow DAO/Operator as fallback).
2. **Alternatively**, decouple signing ownership from the executor: always assign `BTCPendingInfo.account_id` to the original depositor regardless of who calls `execute_refund`, so the victim retains signing rights.
3. **Add a timeout/cancel mechanism** for stuck refund `BTCPendingInfo` entries that allows the DAO to reassign or cancel them without permanently poisoning `verified_deposit_utxo`.

---

### Proof of Concept

1. Victim deposits BTC to a bridge address derived from `DepositMsg { refund_address: Some("bc1qvictim...") }`.
2. Victim calls `request_refund(deposit_msg, "bc1qvictim...", tx_bytes, vout, proof, None)` with 1 NEAR attached → `RefundRequest` stored on-chain.
3. Timelock (`refund_timelock_sec`) elapses.
4. **Attacker** calls `execute_refund(utxo_storage_key, None)` with 1 NEAR attached.
   - `internal_execute_refund` runs; `caller = attacker`.
   - `finalize_refund_with_psbt` creates `BTCPendingInfo { account_id: attacker }`.
   - `verified_deposit_utxo` now contains `utxo_storage_key`.
   - `refund_requests[utxo_storage_key].executed = true`.
5. Attacker does **not** call `sign_btc_transaction` → refund transaction is never signed or broadcast.
6. Victim calls `execute_refund(utxo_storage_key, None)`:
   - `load_refund_request_for_execute` passes (timelock elapsed; `executed == true` bypasses the `verified_deposit_utxo` guard).
   - `finalize_refund_with_psbt` builds the identical PSBT (same outpoint + output → same txid).
   - `btc_pending_infos.insert(...)` returns `Some(...)` → **panics** with `"pending info already exist"`.
7. Victim's BTC is permanently locked. `verify_deposit` is also blocked by `verified_deposit_utxo`. No recovery without a contract upgrade. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
