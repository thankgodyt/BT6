### Title
Unconditional Peras Certificate and Vote Acceptance Without Cryptographic Validation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function accepts every inbound Peras certificate unconditionally (always returns `Right`), and `validatePerasVote` performs no cryptographic signature check — it only verifies that the voter ID appears in the stake distribution. Both functions are called on the hot path for every certificate and vote received from an unprivileged peer over the `PerasCertDiffusion` and `PerasVoteDiffusion` mini-protocols. A single malicious peer can therefore inject a certificate boosting any arbitrary block, or accumulate enough fake votes to forge a quorum certificate for a non-canonical block, causing the victim node to switch its preferred chain.

### Finding Description

The `BlockSupportsPeras` instance (the only production instance, gated by `StandardHash blk`) implements `validatePerasCert` and `validatePerasVote` as stubs:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right
        ValidatedPerasVote
          { vpvVote = vote
          , vpvVoteStake = stake
          }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`validatePerasCert` performs **zero checks** — it wraps any certificate in `Right` regardless of its content. `validatePerasVote` only checks that `pvVoteVoterId` is present in the stake distribution; it does not verify the cryptographic signature binding the voter's key to the `(pvVoteRound, pvVoteBlock)` pair.

These functions are the sole validation gate in `processCerts` and `processVotes`, which are called for every batch of objects received from a peer:

```haskell
(validatePerasCert mkPerasParams)
``` [3](#0-2) 

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

After passing this non-existent gate, certificates are forwarded directly to `ChainDB.addPerasCertAsync`, which triggers `chainSelSync`. That function looks up the boosted block in the VolatileDB and, if found, calls `chainSelectionForBlock` — potentially switching the node's preferred chain:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

For votes, once enough fake votes accumulate (all claiming to be from legitimate stakers), `updatePerasRoundVoteStates` reaches quorum and `forgePerasCert` produces a certificate that is then fed into the same `addPerasCertAsync` path.

The `PerasCertDiffusion` and `PerasVoteDiffusion` mini-protocols are exposed to every connected peer over the node-to-node network layer:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [6](#0-5) 

```haskell
, hPerasVoteDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      ( makePerasVotePoolWriterFromChainDB
          systemTime
          (pure (PerasVoteStakeDistr mempty))
          getChainDB
      )
``` [7](#0-6) 

Note that the vote path is currently wired with an **empty stake distribution** (`PerasVoteStakeDistr mempty`), meaning `validatePerasVote` will reject all votes at the network layer for now. However, `validatePerasCert` is unconditionally accepting, and the vote path will become exploitable once the stake distribution is wired in (which is the intended next step per the TODO comments).

### Impact Explanation

**Critical.** An unprivileged peer can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the victim's VolatileDB. Because `validatePerasCert` always returns `Right`, the certificate is accepted and added to the `PerasCertDB`. `chainSelSync` then triggers chain selection for the boosted block, potentially causing the node to switch to a non-canonical or adversary-controlled fork. The Peras certificate boost is specifically designed to provide finality-like guarantees; bypassing its cryptographic verification directly undermines consensus safety. This matches the allowed impact: "Bypass of … certificate/signature validation … that enables unauthorized … certificate acceptance."

### Likelihood Explanation

**High.** The attack requires only a standard node-to-node connection. Any peer that can connect to the victim node can send crafted `PerasCert` messages. No stake, keys, or special privileges are required. The `PerasCertDiffusion` protocol is active on every node-to-node connection.

### Recommendation

1. Implement real cryptographic validation in `validatePerasCert`: verify the aggregate BLS/committee signature over `(pcCertRound, pcCertBoostedBlock)` against the known committee's aggregate verification key for that round.
2. Implement real cryptographic signature verification in `validatePerasVote`: verify the voter's individual signature over `(pvVoteRound, pvVoteBlock)` using the verification key associated with `pvVoteVoterId` in the committee.
3. Until (1) is implemented, the `processCerts` path should not accept certificates from untrusted peers, or should be gated behind a feature flag that is disabled by default.
4. Track the referenced issue (`cardano-peras/issues/120`) as a security-critical blocker before enabling Peras on any network that accepts connections from untrusted peers.

### Proof of Concept

A malicious peer connects to a victim node and sends a single `PerasCert` message over the `PerasCertDiffusion` mini-protocol:

```
PerasCert
  { pcCertRound    = <any valid round number>
  , pcCertBoostedBlock = <Point of a block the attacker wants boosted,
                          e.g., a minority-fork block already in the
                          victim's VolatileDB>
  }
```

1. The message is received by `aPerasCertDiffusionClient` and forwarded to `makePerasCertPoolWriterFromChainDB`.
2. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
3. The validated certificate is passed to `ChainDB.addPerasCertAsync`.
4. `chainSelSync` looks up the boosted block in the VolatileDB, finds it, and calls `chainSelectionForBlock`.
5. If the boosted block is on a fork that is now heavier than the current selection (due to the Peras weight boost), the node switches chains.

No cryptographic material, stake, or operator access is required. [1](#0-0) [8](#0-7) [9](#0-8)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
