### Title
Round-Number-Based Certificate Deduplication Combined with Stub Validation Allows Unprivileged Peer to Poison PerasCertDB and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The `PerasCertDB` deduplicates Peras certificates using only the `PerasRoundNo` (round number) as the key — a coarser identifier than the full certificate content (round number + boosted block point). Simultaneously, the production `validatePerasCert` implementation is a stub that unconditionally accepts every certificate. An unprivileged peer can exploit both flaws together: by sending a crafted certificate for round R boosting an arbitrary block B1 before the legitimate certificate for round R (boosting the canonical block B2) arrives, the attacker permanently poisons the PerasCertDB. The legitimate certificate is silently dropped as `PerasCertAlreadyInDB`, and chain selection is skewed toward the attacker-chosen block.

---

### Finding Description

**Root cause 1 — Round-number-only deduplication in `implAddCert`:**

In `Impl.hs`, the `implAddCert` function checks for duplicates using only the round number:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
```

The `pcdsCertIds` field is a `Set PerasRoundNo`, not a set of full certificate identities. Two certificates for the same round but boosting different blocks are treated as identical for deduplication purposes. [1](#0-0) 

The same coarse filter is applied in `processCerts`, the network-facing inbound handler:

```haskell
let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
```

Here `alreadyInDb` is a `Set PerasRoundNo`, so any certificate whose round number is already present is silently discarded before validation even runs. [2](#0-1) 

The `opwHasObject` predicate used by the object-diffusion inbound protocol to pre-acknowledge already-known objects also uses round number alone:

```haskell
opwHasObject = do
  certIds <- ChainDB.getPerasCertIds chainDB
  pure $ \roundNo -> Set.member roundNo certIds
``` [3](#0-2) 

**Root cause 2 — Stub `validatePerasCert` unconditionally accepts every certificate:**

The production `BlockSupportsPeras` instance's `validatePerasCert` is a placeholder that always returns `Right`:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

This stub is wired into both production pool writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [5](#0-4) [6](#0-5) 

**Combined exploit path:**

1. Attacker connects as an unprivileged peer via the Peras certificate object-diffusion mini-protocol.
2. Attacker sends `PerasCert { pcCertRound = R, pcCertBoostedBlock = B1 }` where B1 is any block (e.g., a weaker fork tip or a non-existent block).
3. `processCerts` checks `alreadyInDb` — round R is absent, so the cert is not filtered.
4. `validatePerasCert` is called — stub returns `Right` unconditionally.
5. `addCert` stores the certificate; `pcdsCertIds` now contains round R.
6. The legitimate certificate `PerasCert { pcCertRound = R, pcCertBoostedBlock = B2 }` (the canonical one) arrives later.
7. `processCerts` filters it out: `Set.member R alreadyInDb` is `True` → silently dropped as `PerasCertAlreadyInDB`.
8. `getWeightSnapshot` now returns a boost for B1 instead of B2.
9. Chain selection in `chainSelSync` uses this snapshot to compare candidate chains, potentially preferring the attacker-chosen fork. [7](#0-6) 

The `getLatestCertSeen` field — which is a direct precondition for Peras voting rules VR-1A and VR-1B — is also set from the poisoned certificate, corrupting the node's voting behavior. [8](#0-7) 

---

### Impact Explanation

**Severity: High — Chain selection manipulation.**

An unprivileged peer can permanently install a certificate for any Peras round that boosts an arbitrary block. Because the PerasCertDB is keyed by round number and the first writer wins, the legitimate certificate for that round is silently and permanently rejected. The node's chain selection weight snapshot is corrupted, causing it to assign Peras boost weight to the attacker-chosen block rather than the canonical one. This can make the node prefer a non-canonical or less-secure chain, violating the Peras protocol's safety guarantee that certified blocks receive additional finality weight.

Additionally, `getLatestCertSeen` is poisoned, which directly gates the Peras voting rules (VR-1A requires the latest cert seen to be from the previous round; VR-1B requires the voted block to extend the latest certified block). A poisoned `latestCertSeen` can suppress legitimate votes or cause the node to vote on the wrong block.

---

### Likelihood Explanation

**High.** The attack requires only a network connection to the target node. No stake, no keys, no privileged access. The stub `validatePerasCert` removes the only cryptographic barrier. The attacker simply needs to send a well-formed `PerasCert` CBOR message for the target round before the legitimate certificate arrives — a straightforward race that can be won by any peer with low latency to the victim.

---

### Recommendation

1. **Fix the identifier granularity**: Change `pcdsCertIds` from `Set PerasRoundNo` to a set or map keyed on the full certificate identity `(PerasRoundNo, Point blk)`. Deduplication should be leaf-based (full content), not address-based (round number only). This mirrors the fix recommended in the external report: track by the actual leaf (full cert) rather than by the coarser address (round number).

2. **Implement `validatePerasCert`**: Replace the stub with real cryptographic validation (quorum proof, committee membership, BLS/DSIGN signature verification). Until this is done, no certificate received from a peer should be trusted.

3. **Reject equivocating certificates explicitly**: When a certificate for round R arrives and a different certificate for round R already exists (same round, different boosted block), this is an equivocation. The node should disconnect from the peer that sent the equivocating certificate rather than silently dropping it.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
