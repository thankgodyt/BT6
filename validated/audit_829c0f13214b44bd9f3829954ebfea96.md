Peras Certificate and Vote Validation Unconditionally Accepts All Inputs Without Cryptographic Checks - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance ships `validatePerasCert` as an unconditional `Right` (accepts every certificate without any cryptographic check) and `validatePerasVote` as a pure stake-distribution lookup with no signature or committee-membership proof verification. Both functions are the live production implementations called by the inbound object-diffusion pipeline. When Peras is enabled via `rnFeatureFlags`, any unprivileged peer can submit arbitrarily crafted certificates and votes that pass "validation" and are stored in the `PerasCertDB`/`PerasVoteDB`, where they influence chain-selection weight boosts.

---

### Finding Description

`validatePerasCert` in the default `BlockSupportsPeras` instance unconditionally returns `Right`:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

`validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution; it performs no cryptographic proof verification (no BLS/VRF signature check, no committee-eligibility proof):

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

These are the exact functions wired into the live inbound pipelines. `processCerts` in the object-diffusion layer calls the caller-supplied `validateCert` (which resolves to `validatePerasCert`) and adds every certificate that returns `Right`: [3](#0-2) 

`processVotes` does the same for votes via `validateVote` (which resolves to `validatePerasVote`): [4](#0-3) 

The `makePerasVotePoolWriterFromChainDB` wiring passes `validatePerasVote mkPerasParams sd vote` directly, confirming the default stub is the live validator: [5](#0-4) 

Accepted votes accumulate in `implAddVote`, which itself carries a matching TODO acknowledging the absence of real validation logic: [6](#0-5) 

Once a quorum of (unverified) votes is reached, `updatePerasRoundVoteStates` forges a certificate and stores it. That certificate then provides a `perasWeight` boost to the boosted block during chain selection, directly affecting which chain the node prefers. [7](#0-6) 

The `BlockSupportsPeras` class contract requires `validatePerasCert` and `validatePerasVote` to be the gatekeepers before any certificate or vote is treated as `Validated*`: [8](#0-7)

### Impact Explanation

**Impact: Critical — Bypass of Peras voting and certificate checks enabling unauthorized certificate acceptance.**

When Peras is enabled via `rnFeatureFlags`, an unprivileged peer can:

1. Craft a `PerasCert` for any round and any block point.
2. Send it via the object-diffusion mini-protocol.
3. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB` with a full `perasWeight` boost.
5. Chain selection now treats the attacker-chosen block as having a weight advantage, causing honest nodes to prefer a non-canonical or adversarially-chosen chain.

For votes: an attacker who knows any voter ID present in the current stake distribution can submit fake votes for that voter without possessing the voter's private key. Submitting enough fake votes (one per distinct voter ID in the distribution) causes `votesReachQuorum` to return `Just`, forging a certificate for an arbitrary block. [9](#0-8) 

This directly satisfies the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … vote, or certificate acceptance."*

---

### Likelihood Explanation

**Likelihood: High (conditional on Peras being enabled).**

- The vulnerability requires Peras to be activated via `rnFeatureFlags`. This is a runtime flag, not a compile-time guard; any operator who enables Peras (the intended production use case for this code path) is immediately exposed.
- The attacker entry path is the standard node-to-node object-diffusion mini-protocol — no special privileges, no key material, no stake required.
- The stake distribution is public on-chain data, so enumerating valid voter IDs for the vote-forgery path requires no privileged access.
- The attack is deterministic and requires no brute force.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation: verify the aggregate BLS/committee signature over `(roundNo, boostedBlock)`, verify that the signers constitute a valid quorum of the elected committee for that round, and verify each signer's committee-eligibility proof. Return `Left` for any failure.

2. **`validatePerasVote`**: In addition to the stake-distribution lookup, verify the voter's cryptographic eligibility proof (VRF output proving committee membership) and the vote's signature over `(roundNo, votedBlock)` using the voter's registered key. Return `Left PerasValidationErr` if any check fails.

3. Until full validation is implemented, gate the entire Peras inbound pipeline (both `processCerts` and `processVotes`) behind a compile-time or runtime guard that prevents the stub implementations from being reachable in any node that connects to untrusted peers.

---

### Proof of Concept

**Certificate forgery (private testnet):**

```
1. Start a Peras-enabled node (rnFeatureFlags includes Peras).
2. Connect a crafted peer that sends a PerasCert with:
     pcCertRound  = <current Peras round>
     pcCertBoostedBlock = <attacker-chosen block point>
   via the object-diffusion protocol.
3. Observe: processCerts calls validatePerasCert, which returns Right.
4. The certificate is stored in PerasCertDB.
5. Chain selection now applies perasWeight to the attacker-chosen block.
6. The honest node switches to (or refuses to leave) the attacker-chosen chain.
```

**Vote-based certificate forgery (private testnet):**

```
1. Read the current PerasVoteStakeDistr from the node's public state.
2. For each voter ID in the distribution, send a PerasVote:
     pvVoteRound  = <current round>
     pvVoteBlock  = <attacker-chosen block>
     pvVoteVoterId = <voter ID from distribution>
   (no valid signature or eligibility proof required).
3. processVotes calls validatePerasVote, which returns Right for each
   voter ID found in the distribution.
4. Once enough votes accumulate, votesReachQuorum returns Just,
   updatePerasRoundVoteStates forges a ValidatedPerasCert for the
   attacker-chosen block, and chain selection is manipulated.
```

-- It returns 'Nothing' if either of these conditions is not met.
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
