### Title
Silent nBTC Loss in `safe_mint` When Recipient Has No NEP-141 Storage Registration — (File: `contracts/nbtc/src/lib.rs`)

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account (`bridge_id`) before checking whether the intended recipient has NEP-141 storage registered. If the recipient has no storage, the function silently returns `U128(0)` without transferring the minted tokens, leaving them permanently stranded in the bridge account with no on-chain recovery path.

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` follows a push pattern that fails silently:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    // Step 1: tokens are minted INTO the bridge account
    self.token.internal_deposit(&self.bridge_id, amount.into());

    // Step 2: if recipient has no storage, return silently — tokens stay in bridge_id
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    // Step 3 (only reached if storage exists): push tokens to recipient
    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
``` [1](#0-0) 

The critical flaw is the ordering: `internal_deposit` to `bridge_id` happens unconditionally at line 112, before the storage check at line 114. When the check fails, the function returns `U128(0)` — no transfer, no event, no revert, no recovery entry. The minted supply is now backed by tokens sitting in the bridge account that are not attributed to any user.

Contrast this with the sibling `mint_inner` helper, which auto-registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);
    }
    self.token.internal_deposit(account_id, amount.into());
    ...
}
``` [2](#0-1) 

`mint_inner` never silently drops tokens. `safe_mint` does.

The deposit flow in the satoshi-bridge calls into the nBTC contract to mint tokens for the depositing user. The wiki's sequence diagram explicitly maps the deposit callback to `contracts/nbtc/src/lib.rs:115`, which falls inside `safe_mint`. Any user who deposits BTC to a bridge address derived from their NEAR account ID, but who has not yet registered storage for the nBTC token, will trigger this silent-loss path.

### Impact Explanation

When `safe_mint` silently returns without transferring:

- The user's BTC is locked in the bridge's UTXO set (the deposit is marked verified in `verified_deposit_utxo`).
- The corresponding nBTC is minted to `bridge_id` and is not attributed to the user anywhere in contract state.
- There is no `LostFound` entry (that mechanism exists only in `transfer_nbtc_callback` in `token_transfer.rs`, not in `safe_mint`).
- There is no emitted event indicating the failure.
- The user has no on-chain mechanism to claim or recover the tokens. [3](#0-2) 

The result is a **permanent loss of user funds**: the deposited BTC is consumed, the nBTC is minted but unreachable by the user, and the bridge's total supply is inflated relative to what users actually hold. This matches the allowed impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

NEP-141 storage registration is a prerequisite that many new NEAR users are unaware of. A user who:

1. Generates a deposit address via the bridge UI/API,
2. Sends BTC to that address,
3. Has not separately called `storage_deposit` on the nBTC contract,

will silently lose their deposit. This is a realistic, unprivileged, user-triggered path requiring no special access or coordination. The attacker role here is simply "any BTC depositor without prior nBTC storage registration."

### Recommendation

Apply the same pattern used by `mint_inner`: auto-register the recipient account before depositing, or revert if registration is not possible. Alternatively, adopt a pull pattern: mint to `bridge_id`, record the pending amount in a claimable mapping keyed by `account_id`, and let the user claim after registering storage. At minimum, if the storage check fails, the function must revert (not silently return) so the bridge's cross-contract call can handle the failure and avoid marking the deposit as finalized.

```rust
// Option A: auto-register (mirrors mint_inner)
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
}
self.token.internal_deposit(&self.bridge_id, amount.into());

// Option B: pull pattern — store in claimable map, revert deposit finalization on failure
```

### Proof of Concept

1. Deploy the nBTC contract and the satoshi-bridge contract.
2. Create a NEAR account `alice.near` but do **not** call `storage_deposit` on the nBTC contract for `alice.near`.
3. Send BTC to the deposit address derived from `alice.near`'s account ID.
4. A relayer calls `verify_deposit` on the satoshi-bridge; the light-client proof passes; the bridge calls `safe_mint("alice.near", amount, None)` on the nBTC contract.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, amount)` executes — nBTC is minted to the bridge account.
6. `self.token.accounts.get(&"alice.near")` returns `None` — the early return fires, returning `U128(0)`.
7. `alice.near` receives zero nBTC. The deposit UTXO is marked verified. The minted tokens remain in `bridge_id` with no recovery entry and no emitted failure event.
8. `alice.near`'s BTC is permanently lost. [4](#0-3)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
