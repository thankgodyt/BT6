### Title
`safe_mint_callback` Treats `safe_mint` Panic as Permanent Success, Consuming User UTXO Without Minting Tokens — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In the safe-deposit path (`verify_deposit_v2` with `safe_deposit: Some(...)` / `safe_verify_deposit`), the bridge marks the deposit UTXO as consumed in `verified_deposit_utxo` before the cross-contract `safe_mint` call completes. The callback `safe_mint_callback` uses `is_refund_required()` to decide whether to roll back. That helper returns `false` (no rollback) for **any** non-zero-return outcome, including a panic from `safe_mint`. Because NEAR reverts nbtc state on a panicked promise but does **not** revert the bridge's already-committed `verified_deposit_utxo` insertion, a panicked `safe_mint` leaves the UTXO permanently consumed with zero nBTC minted for the user.

---

### Finding Description

**Step 1 — UTXO marked consumed before mint completes**

In `verify_safe_deposit_callback`, the UTXO is inserted into `verified_deposit_utxo` synchronously, then `safe_mint` is scheduled as a cross-contract call: [1](#0-0) 

The `verified_deposit_utxo.insert(...)` state change is committed to the bridge's storage when this callback transaction completes. The subsequent `safe_mint` call runs in a separate NEAR transaction.

**Step 2 — `is_refund_required()` conflates panic with non-zero return**

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0   // only this branch triggers rollback
            } else {
                false           // non-parseable → no rollback
            }
        }
        Err(_) => false,        // panic → no rollback  ← BUG
    }
}
``` [2](#0-1) 

The comment explicitly documents the flaw:

> "Any other outcome (non-zero amount, unparseable payload, **panic**) is treated as 'UTXO spent, no refund' — for safety, to avoid a potential double spend."

When `safe_mint` panics, NEAR reverts all nbtc state changes (no tokens minted), but the bridge's `verified_deposit_utxo` entry is already committed. `is_refund_required()` returns `false`, so `is_success = true`.

**Step 3 — UTXO added to bridge pool, no tokens minted**

With `is_success = true`, `safe_mint_callback` adds the UTXO to the bridge's available pool: [3](#0-2) 

The user's deposit UTXO is now in the bridge's spendable UTXO set. No nBTC was minted. The user cannot retry (`verified_deposit_utxo` blocks re-submission). The BTC is permanently absorbed into the bridge's pool.

**Contrast with the standard `mint_callback`**

The standard deposit path correctly rolls back on failure: [4](#0-3) 

The safe path lacks an equivalent rollback for the panic case.

---

### Impact Explanation

When `safe_mint` panics:
- The user's BTC UTXO is permanently added to the bridge's available UTXO pool.
- Zero nBTC tokens are minted for the user.
- The UTXO key is in `verified_deposit_utxo`, blocking any future `verify_deposit` retry.
- The user loses their entire BTC deposit with no recourse.

This is a permanent, irrecoverable loss of user funds — matching **Critical: Significant loss, theft, destruction, or permanent locking of user or protocol funds**.

---

### Likelihood Explanation

The `safe_deposit` path is actively used by Omni Bridge integration (`verify_deposit_v2` with `safe_deposit: Some(...)`). `safe_mint` can panic due to:

1. **Gas exhaustion**: If the downstream `ft_on_transfer` in the Omni Bridge receiver consumes more gas than the 90 Tgas budget allows, `safe_mint` panics.
2. **nbtc contract invariant violation**: Any panic inside `safe_mint` (e.g., storage registration failure, arithmetic overflow) triggers the bug.
3. **Receiver contract panic**: If the Omni Bridge's `ft_on_transfer` panics for any reason (e.g., unexpected message format crafted by the depositor), `safe_mint` reverts.

A depositor can influence the `msg` field passed through `safe_deposit`, which is injected into the `ft_on_transfer` call via `inject_utxo_id_in_msg`. A malformed or oversized message that causes the Omni Bridge receiver to panic provides a user-reachable trigger path. [5](#0-4) 

---

### Recommendation

Replace the `Err(_) => false` arm in `is_refund_required()` with `Err(_) => true`. A panicked `safe_mint` guarantees no tokens were minted; rolling back the UTXO and allowing retry is safe and correct:

```rust
fn is_refund_required() -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Ok(value) => {
            if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                amount.0 == 0
            } else {
                true  // unparseable → treat as failure, refund
            }
        }
        Err(_) => true,  // panic → tokens definitely not minted, refund
    }
}
```

The double-spend concern cited in the comment does not apply to the panic case: NEAR's atomicity guarantees that a panicked `safe_mint` leaves zero tokens minted, so rolling back `verified_deposit_utxo` and allowing a retry is safe.

---

### Proof of Concept

1. User sends BTC to a deposit address derived from a `DepositMsg` with `safe_deposit: Some(SafeDepositMsg { ... })` and a `msg` field that will cause the Omni Bridge's `ft_on_transfer` to panic (e.g., a malformed JSON payload).
2. Relayer calls `verify_deposit_v2(deposit_msg, tx_bytes, vout, proof)`.
3. `verify_safe_deposit_callback` runs: `verified_deposit_utxo.insert(utxo_key)` is committed; `safe_mint(recipient, amount, Some(malformed_msg))` is scheduled.
4. `safe_mint` calls `ft_transfer_call` on the nbtc token, which calls `ft_on_transfer` on the Omni Bridge receiver. The receiver panics on the malformed `msg`. `safe_mint` reverts — zero tokens minted.
5. `safe_mint_callback` runs: `promise_result_checked` returns `Err` → `is_refund_required() = false` → `is_success = true` → `internal_set_utxo(utxo_key, utxo)` executes.
6. Result: user's BTC UTXO is in the bridge's available pool; user holds zero nBTC; `verified_deposit_utxo` contains `utxo_key` blocking any retry. Funds permanently lost.
