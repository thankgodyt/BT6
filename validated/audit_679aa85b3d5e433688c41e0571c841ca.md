### Title
Premature State Update in `safe_mint` Permanently Locks User Funds When Recipient Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account (`internal_deposit` to `bridge_id`) **before** checking whether the intended recipient is registered. If the recipient has no storage account, the function returns `U128(0)` without transferring the newly minted tokens, leaving them permanently stranded in the bridge's balance with no recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` follows this sequence:

1. **State updated first** — `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the bridge's token balance and the total supply.
2. **Recipient registration checked after** — `if self.token.accounts.get(&account_id).is_none()` is evaluated only after the mint.
3. **Silent early return** — if the recipient is unregistered, the function returns `PromiseOrValue::Value(U128(0))` with no transfer and no rollback of the minted tokens. [1](#0-0) 

This is structurally identical to the reported vulnerability: state (token supply / bridge balance) is committed before the transfer step, and the transfer step is then silently skipped, leaving the minted tokens orphaned in the bridge's account.

The `mint` function, by contrast, calls `mint_inner` which registers the account if absent and deposits directly — it does not share this flaw. [2](#0-1) 

### Impact Explanation
- The user's BTC is locked in the bridge (the deposit was accepted and verified on-chain).
- The corresponding nBTC is minted to the bridge's own balance and is irrecoverable — there is no `lost_found` entry, no revert, and no admin recovery hook for this path.
- The bridge's nBTC balance silently inflates without any user owning those tokens, breaking the 1:1 BTC-backing invariant.

This matches **Critical — Significant loss or permanent locking of user funds**.

### Likelihood Explanation
Any deposit whose `account_id` recipient has not called `storage_deposit` on the nBTC contract will trigger this path. This is a realistic scenario for:
- First-time users who deposit BTC before registering their NEAR account on the token contract.
- Users who specify a recipient account ID that has never interacted with the nBTC contract.

The entry point is the normal bridge deposit flow (`verify_deposit` → bridge → `safe_mint`), reachable by any unprivileged BTC depositor.

### Recommendation
Move the registration check **before** the `internal_deposit` call, or revert (panic) if the recipient is unregistered rather than silently returning zero:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // No tokens minted yet — safe to return
    }
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... rest of transfer logic
}
```

Alternatively, auto-register the recipient (as `mint_inner` does) or revert so the bridge can handle the failure and refund the depositor.

### Proof of Concept
1. Deploy the nBTC contract; do **not** call `storage_deposit` for `user.near`.
2. Have the bridge call `safe_mint(account_id: "user.near", amount: 1_000_000, msg: None)`.
3. Observe: `ft_balance_of("bridge.near")` increases by `1_000_000`; `ft_balance_of("user.near")` remains `0`; `ft_total_supply` increased by `1_000_000`.
4. There is no function to recover the stranded tokens from the bridge's balance back to the user. [3](#0-2)
