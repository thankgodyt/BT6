The management API (`management.rs`) confirms the two operations are **independent and non-atomic**: `extend_post_action_receiver_id_white_list` (lines 163–175) and `extend_post_action_msg_templates` (lines 210–231) have no cross-enforcement. A receiver can be whitelisted with zero templates.

### Title
Whitelisted `post_action` receiver with no `msg_templates` entry allows attacker-controlled arbitrary `msg` to bypass validation — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
`check_deposit_msg` skips msg-template validation entirely when `post_action_msg_templates` has no entry for a whitelisted `receiver_id`. An unprivileged attacker can submit a `DepositMsg` with an arbitrary `msg` targeting such a receiver, and the bridge will execute `ft_transfer_call` to that receiver with the attacker-controlled msg after minting nBTC.

### Finding Description
In `check_deposit_msg`, the receiver-id whitelist check is a hard gate, but the msg-template check is wrapped in `if let Some(msg_templates) = ...`: [1](#0-0) 

If `post_action_msg_templates.get(&post_action.receiver_id)` returns `None` — which happens whenever the DAO added the receiver to the whitelist without calling `extend_post_action_msg_templates` — the entire validation block is skipped and execution falls through to `Some(post_actions)` at line 191. [2](#0-1) 

The two management operations are independent: [3](#0-2) [4](#0-3) 

There is no invariant enforced at the contract level that a whitelisted receiver must have at least one template. The `post_action_receiver_id_white_list` and `post_action_msg_templates` are separate `IterableSet`/`IterableMap` fields with no coupling: [5](#0-4) 

The validated (or unvalidated) `post_actions` are then passed directly into `internal_mint_promise` → `ext_nbtc::mint(... post_actions)`: [6](#0-5) [7](#0-6) 

### Impact Explanation
The attacker-controlled `msg` is forwarded verbatim to `ft_transfer_call` on the whitelisted receiver contract. The receiver's `ft_on_transfer` implementation interprets this msg. If the receiver contract has any msg-driven logic (e.g., routing, swap, withdrawal commands), the attacker can trigger unintended behavior — including locking or misdirecting the transferred nBTC — without the bridge's template guard ever firing. This matches the Medium impact class: harmful cross-contract behavior without direct bridge-level theft, but with potential for stuck or misdirected bridged funds.

### Likelihood Explanation
The precondition — a receiver on the whitelist with no templates — is operationally realistic. The DAO may add a receiver as a preparatory step before configuring templates, or may intentionally omit templates for a receiver believed to be "safe." There is no on-chain enforcement preventing this state. Any unprivileged user can then exploit the gap by submitting a valid BTC deposit with a crafted `DepositMsg`.

### Recommendation
Enforce that a whitelisted receiver **must** have at least one template before the post_action is accepted. Either:
1. In `check_deposit_msg`, treat a `None` template entry for a whitelisted receiver as a validation failure (return `None` with an `InvalidPostAction` event), or
2. In `extend_post_action_receiver_id_white_list`, require that templates are provided atomically at whitelist-addition time.

Option 1 is the minimal fix:

```rust
// Replace the if-let with a mandatory lookup:
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .unwrap_or_else(|| {
        Event::InvalidPostAction { index: Some(index), err_msg: "No msg templates for receiver.".to_string() }.emit();
        return None; // propagate None from check_deposit_msg
    });
// then validate msg against msg_templates
```

### Proof of Concept
1. DAO calls `extend_post_action_receiver_id_white_list(["victim.near"])` — no `extend_post_action_msg_templates` call for `victim.near`.
2. Attacker submits a BTC deposit with `DepositMsg { recipient_id: attacker, post_actions: [{ receiver_id: "victim.near", amount: X, msg: "<arbitrary attacker payload>" }] }`.
3. `check_deposit_msg` reaches line 117: `post_action_msg_templates.get("victim.near")` returns `None`; the `if let Some(...)` block is not entered.
4. Function returns `Some(post_actions)` at line 191 with the arbitrary msg intact.
5. After BTC proof verification, `ft_transfer_call("victim.near", X, "<arbitrary attacker payload>")` executes, triggering `victim.near::ft_on_transfer` with the attacker-controlled msg. [8](#0-7)

    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
