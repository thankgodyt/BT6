### Title
`safe_mint` Silently Strands nBTC When Recipient Account Is Unregistered — (`contracts/nbtc/src/lib.rs`)

---

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function unconditionally mints nBTC tokens into `bridge_id`'s balance before checking whether the intended recipient account is registered. If the recipient is not registered, the function returns `U128(0)` and exits — leaving the freshly minted tokens permanently sitting in `bridge_id` with no `lost_found` entry, no recovery event, and no refund path inside `safe_mint` itself.

---

### Finding Description

`safe_mint` is the deposit-path minting entry point called by the bridge after a BTC deposit is verified. Its execution order is:

1. **Mint unconditionally into `bridge_id`** — `self.token.internal_deposit(&self.bridge_id, amount.into())` [1](#0-0) 

2. **Check recipient registration** — if the recipient account has no storage slot, return `PromiseOrValue::Value(U128(0))` immediately. [2](#0-1) 

3. **Only then** attempt `ft_transfer` or `ft_transfer_call` to the user. [3](#0-2) 

When step 2 short-circuits, the tokens already credited to `bridge_id` are never moved. `safe_mint` emits no event, creates no `lost_found` entry, and provides no mechanism for the user to later claim those tokens. Compare this with `mint_inner`, which auto-registers any account before depositing: [4](#0-3) 

And compare with `transfer_nbtc_callback`, which explicitly creates a `lost_found` entry when an nBTC transfer fails: [5](#0-4) 

`safe_mint` does neither. The return value of `U128(0)` signals to the bridge callback that zero tokens were forwarded, but the tokens are already in `bridge_id`'s balance. Whether the bridge callback recovers them depends entirely on code in `btc_light_client/deposit.rs` that was not reachable in this analysis — but `safe_mint` itself provides no safety net.

---

### Impact Explanation

A user who deposits BTC to their derived bridge address without having previously registered their NEAR account for nBTC storage will have their deposit verified on-chain, nBTC minted into `bridge_id`, and then receive nothing. The tokens sit in `bridge_id`'s balance with no on-chain record linking them to the depositor. Without operator intervention to manually track and re-issue the tokens, the user's BTC is effectively lost. This matches the **Medium** impact class: broken callback rollback / stuck bridge state requiring operator intervention, and potentially escalates to **Critical** (significant loss of user funds) if the bridge callback does not create a `lost_found` entry.

---

### Likelihood Explanation

Any first-time depositor who has not separately called `storage_deposit` on the nBTC contract before sending BTC will trigger this path. NEAR storage registration is a non-obvious prerequisite that many users will miss. The entry path is fully unprivileged: any NEAR account holder can deposit BTC and reach `safe_mint` through the normal deposit flow.

---

### Recommendation

Apply one of the following fixes inside `safe_mint` itself, before returning:

1. **Auto-register** the recipient account (as `mint_inner` does) so the transfer always succeeds.
2. **Create a `lost_found` entry** for the minted amount when the recipient is unregistered, mirroring the pattern in `transfer_nbtc_callback`.
3. **Invert the order**: check registration first; only call `internal_deposit` if the account exists (or after registering it), so no tokens are minted into `bridge_id` on a path that cannot complete the transfer.

---

### Proof of Concept

1. User sends BTC to their bridge deposit address without registering their NEAR account on the nBTC contract.
2. Relayer submits a valid Merkle proof to `verify_deposit` on the bridge.
3. Bridge verifies the proof and calls `safe_mint(user_account_id, amount, msg)` on the nBTC contract.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — tokens are now in `bridge_id`. [1](#0-0) 
5. `self.token.accounts.get(&account_id).is_none()` returns `true` — user is not registered. [2](#0-1) 
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` with no `lost_found` entry, no event, and no refund.
7. Tokens remain in `bridge_id`. User's BTC is locked in the bridge UTXO set. User receives nothing and has no on-chain path to recover their nBTC.
