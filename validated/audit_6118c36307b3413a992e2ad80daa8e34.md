### Title
Peras BLS Vote Signature Lacks Network-Specific Domain Separation, Enabling Cross-Network Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

### Summary

The `hashVoteSignature` function used to produce and verify Peras BLS vote signatures does not include any network-specific identifier (network magic, genesis hash, or chain ID) in the signed message. The only domain separator is the `KeyScope` embedded in the BLS key itself, but this scope is never validated against the node's actual network configuration at verification time. This mirrors the Hermez `_checkSig` pattern: a signature schema that allows replay across different network instances.

### Finding Description

`hashVoteSignature` in `PerasBLSCrypto` constructs the signed message as:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash . Hash.hashWith id . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
```

The message is `(roundNo || boostedBlockSlot || boostedBlockHash)` — no network magic, no genesis hash, no chain ID. [1](#0-0) 

The BLS signing context does include a `KeyScope` augmentation string (`"VOTE:" <> keyScope <> ":V0"`), which is the design's intended domain separator: [2](#0-1) 

However, `KeyScope` is defined as a plain `ByteString` stored inside the key struct itself:

```haskell
-- | Key scope, later instantiated with usage and network id (e.g. PERAS/MAINNET)
type KeyScope = ByteString

data PrivateKey r = PrivateKey
  { unPrivateKey    :: !(SignKeyDSIGN BLS12381MinSigDSIGN)
  , privateKeyScope :: !KeyScope
  }
``` [3](#0-2) 

The scope is set at key-deserialization time by the caller (`rawDeserialisePrivateKey scope bs`) and is never validated against the node's running network configuration during `verifyVoteSignature` or `verifyAggregateVoteSignature`. The verifier simply reads back `publicKeyScope pk` from whatever key object it holds: [4](#0-3) 

The production `PerasBLSCrypto` instance calls `BLS.signWithRole @SIGN sk $ hashVoteSignature roundNo boostedBlock` and `BLS.verifyWithRole @SIGN pk (hashVoteSignature roundNo boostedBlock) sig` with no additional network binding: [5](#0-4) 

A grep across the entire repository shows `rawDeserialisePrivateKey` and `rawDeserialisePublicKey` are only called in test code (with scopes `"TEST"` and `"ROUNDTRIP"`). There is no production call site that enforces a network-specific scope value, and no runtime check that `publicKeyScope pk` matches the node's `NetworkMagic`.

### Impact Explanation

If two Cardano network instances (e.g., mainnet and a private testnet) load BLS committee keys with the same `KeyScope` value — which is entirely possible since there is no enforcement — a Peras vote signature produced on one network is cryptographically valid on the other. An attacker who controls a parallel network instance can:

1. Lure a legitimate committee member into registering the same BLS key and casting votes on the attacker-controlled network.
2. Replay those vote signatures verbatim on the target network (same `roundNo`, same `boostedBlock` hash, same key scope).
3. Forge or inflate a Peras certificate on the target network, causing honest nodes to accept a certificate they should not, bypassing the Peras voting quorum requirement.

This is a bypass of certificate/signature validation that allows unauthorized certificate acceptance — within the allowed impact scope.

### Likelihood Explanation

Medium. The attack requires the victim's BLS key to be registered on both networks and the `KeyScope` to be identical across them. Since there is no enforcement of network-specific scopes in the codebase, any deployment that reuses keys across networks (e.g., a testnet mirror of mainnet committee keys, or a fork) is vulnerable. The comment "e.g. PERAS/MAINNET" is aspirational, not enforced.

### Recommendation

**Short term:** In `hashVoteSignature` (and `hashVRFInput`), include the network magic (or genesis hash) as a mandatory prefix in the hashed message, analogous to how Byron's `ContextDSIGN ByronDSIGN = (ProtocolMagicId, VerKeyDSIGN ByronDSIGN)` binds every signature to the protocol magic: [6](#0-5) 

**Long term:** At `verifyVoteSignature` and `verifyAggregateVoteSignature` call sites, assert that `publicKeyScope pk` equals the node's configured network scope, so a key deserialized with the wrong scope is rejected at verification time rather than silently accepted.

### Proof of Concept

1. Deploy two Peras-enabled Cardano networks, both loading committee BLS keys with `rawDeserialisePrivateKey "PERAS/MAINNET" keyBytes` (identical scope).
2. On network A (attacker-controlled), committee member Bob casts a vote for `(roundNo=42, boostedBlock=X)`.
3. The resulting `PerasBLSCryptoVoteSignature` is a raw BLS signature over `hashVoteSignature 42 X` under context `"VOTE:PERAS/MAINNET:V0"`.
4. On network B (target), Bob's public key is registered with the same scope. Submit the vote message with Bob's signature from step 3.
5. `verifyVoteSignature` on network B calls `BLS.verifyWithRole @SIGN pk (hashVoteSignature 42 X) sig` — the context is identical, the message is identical, verification succeeds.
6. Aggregate enough such replayed votes to meet the quorum threshold and forge a valid `PerasBLSCryptoAggregateVoteSignature` certificate on network B. [5](#0-4) [7](#0-6)
