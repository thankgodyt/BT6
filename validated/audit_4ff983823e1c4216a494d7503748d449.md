### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Returns `Right`, Enabling Unauthorized Certificate Acceptance and Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass defines the interface for Peras certificate and vote validation. A single degenerate stub instance applies to **all** block types. Its `validatePerasCert` method unconditionally returns `Right` — accepting every certificate without any cryptographic or semantic check. This stub is wired directly into the production chain-selection path (`makePerasCertPoolWriterFromChainDB`). An unprivileged peer can send a crafted Peras certificate over the network; it will be accepted, stored in the `PerasCertDB`, and, if it references a block in the VolatileDB, will trigger chain selection for that block — bypassing the Peras certificate authorization entirely.

---

### Finding Description

**Root cause — unconditional `Right` in `validatePerasCert`:** [1](#0-0) 

The comment at line 318 is explicit: *"TODO: degenerate instance for all blks to get things to compile"*. The `validatePerasCert` implementation at lines 353–358 always returns `Right` with a `ValidatedPerasCert` constructed from the untouched input certificate and the static `perasWeight` parameter. No signature check, no committee membership check, no round-number sanity check, no boosted-block existence check is performed.

**Production call site — `makePerasCertPoolWriterFromChainDB`:** [2](#0-1) 

Lines 125–126 pass `validatePerasCert mkPerasParams` as the validation callback. The comment *"TODO replace when actual plumbing is in place"* confirms this is the live production path, not a test shim.

**`processCerts` — the inbound network handler:** [3](#0-2) 

`processCerts` calls `validateCert` (the stub) on every certificate received from a peer. Because the stub always returns `Right`, every certificate passes and is forwarded to `addCert`.

**Chain selection triggered by the accepted certificate:** [4](#0-3) 

`chainSelSync` (lines 483–532) processes the accepted certificate: it looks up the boosted block in the VolatileDB and calls `chainSelectionForBlock` for it. A forged certificate that references any block already in the VolatileDB will therefore trigger a chain-selection pass for that block, potentially causing the node to switch to a different (but still structurally valid) chain.

**Companion incompatibility — `getPerasCertInBlock` always returns `Nothing`:** [5](#0-4) 

Because `getPerasCertInBlock _ = Nothing`, the Shelley ledger's `shelleyLedgerLatestPerasCertRound` field is never updated from on-chain blocks: [6](#0-5) 

This means the Peras cooldown-period coordination (`getLatestPerasCertRound`) is permanently broken for production Cardano blocks — the system claims to support Peras certificate extraction from blocks but the infrastructure is not in place, directly mirroring the external report's incompatibility pattern.

---

### Impact Explanation

**Primary (Critical — certificate validation bypass):** An unprivileged peer can craft an arbitrary `PerasCert` (any round number, any boosted block hash) and submit it via the object-diffusion mini-protocol. The stub accepts it unconditionally. If the boosted block is present in the VolatileDB, chain selection is re-run for it. By choosing a block on a competing fork, an attacker can cause an honest node to switch away from the canonical chain to a less-secure or adversarially-chosen fork — without holding any stake, keys, or committee membership. This is a direct bypass of Peras voting/certificate authorization.

**Secondary (High — broken Peras chain selection):** Because `getPerasCertInBlock` always returns `Nothing`, the `shelleyLedgerLatestPerasCertRound` field is never populated from on-chain data. The `LedgerSupportsPeras` instance for `ShelleyBlock` therefore always returns `Nothing` from `getLatestPerasCertRound`, making the cooldown-period logic permanently inoperative. The protocol claims to support Peras certificate-based chain selection but the necessary infrastructure is absent, breaking the feature entirely.

---

### Likelihood Explanation

Any peer that can open an object-diffusion connection to the node can exploit the primary issue. No stake, no keys, no committee seat, and no prior knowledge of the chain state beyond the VolatileDB contents (which are gossiped) is required. The attack is trivially automatable. The secondary issue is triggered by normal block application and requires no adversarial action at all.

---

### Recommendation

1. **Remove or gate the degenerate `BlockSupportsPeras` instance.** Until the HFC plumbing is complete, the instance should either be absent (forcing a compile error that surfaces the gap) or should reject all certificates with an explicit `Left` error rather than accepting them unconditionally.

2. **Implement real cryptographic validation in `validatePerasCert`.** At minimum, verify the BLS aggregate signature against the claimed voters and the election identifier before accepting a certificate.

3. **Implement `getPerasCertInBlock` for `CardanoBlock`/`ShelleyBlock`.** The HFC plumbing referenced in the TODO at line 387 must be completed before Peras chain selection can function correctly.

4. **Add a feature flag guard.** Until validation is complete, `processCerts` should refuse to accept any certificate when Peras is not fully initialized, rather than silently accepting everything.

---

### Proof of Concept

```
1. Attacker connects to a target node via the object-diffusion mini-protocol
   (standard peer connection, no special privileges required).

2. Attacker observes the VolatileDB tip via ChainSync to learn a recent
   block hash H on a competing fork F.

3. Attacker constructs a PerasCert { pcCertRound = R, pcCertBoostedBlock = H }
   for any round R not yet in the PerasCertDB.

4. Attacker sends the certificate to the node.

5. processCerts calls validatePerasCert mkPerasParams cert
   → always returns Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight })

6. The certificate is stored in PerasCertDB.

7. chainSelSync looks up H in the VolatileDB, finds it, and calls
   chainSelectionForBlock for H.

8. If fork F is now heavier (by Peras weight) than the current selection,
   the node switches to F — a chain the attacker chose, without any
   legitimate Peras committee participation.

  ObjectPoolWriter
    { opwObjectId = getPerasCertRound
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          -- We do not want to block the writer thread on waiting for ChainSel

          -- certs to the ChainDB and ignore the returned promise.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
