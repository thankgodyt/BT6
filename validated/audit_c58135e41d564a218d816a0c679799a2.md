### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Produces Wrong Peras Local-Sortition Seat Count for Large-Stake Voters — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own documentation states `boundX` **must equal `e^|x|`** for correct error bounds. The argument `x` is `-lambda`, so the correct bound is `e^lambda`. When `lambda > ln(3) ≈ 1.099` — a realistic condition for any non-persistent voter holding more than roughly `11 %` of the total non-persistent stake in a 10-seat committee — the error term is systematically underestimated. This causes the Taylor-expansion convergence test to make wrong ABOVE/BELOW decisions, granting an ineligible voter non-zero seats. Because the same function is used in both `implCheckShouldVote` (voter side) and `implVerifyVote` / `implVerifyCert` (verifier side), an attacker who discovers their VRF output lands in the ambiguous region can submit a vote or contribute to a certificate that the verifier incorrectly accepts.

---

### Finding Description

**Root cause — wrong scaling constant passed to the error-bound computation.**

`taylorExpCmpFirstNonLower` approximates `e^x` via a Taylor series and uses `errorTerm = abs(err' * boundX)` to decide whether the partial sum has converged:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
taylorExpCmpFirstNonLower boundX cmps x =
  goList 1000 0 x 1 1 0 cmps
``` [1](#0-0) 

The convergence guard inside `decideOne` is:

```haskell
errorTerm = abs (err' * boundX)
``` [2](#0-1) 

`errorTerm` bounds the maximum remaining contribution of all future Taylor terms. For `e^x` with `x = -lambda`, the tail is bounded by `|err'| * e^lambda`. If `boundX < e^lambda`, the bound is too tight: the algorithm believes it has converged before it actually has.

The call site hardcodes `boundX = 3`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← should be exp lambda
      orders
      (-lambda)
``` [3](#0-2) 

The developers themselves flag this with a TODO:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. ...
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3) 

`lambda` is computed as:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [5](#0-4) 

With a 10-seat non-persistent committee and a voter holding 15 % of the non-persistent stake, `lambda = 1.5`, so `e^lambda ≈ 4.48 > 3`. The `3` constant was copied from `checkLeaderNatValue` in the ledger, where `lambda = f * sigma` is always tiny (active-slot coefficient times pool stake fraction). In the local-sortition context `lambda` is proportional to committee size and can easily exceed `ln(3)`.

**Consequence of the underestimated error term.**

When `errorTerm` is too small, the interval `[acc' − errorTerm, acc' + errorTerm]` is narrower than the true uncertainty. The guard

```
cmp >= acc' + errorTerm  →  Stop  (ABOVE: voter gets a seat)
```

becomes easier to satisfy. A threshold `cmp` that truly lies above `e^(-lambda)` (meaning the voter should NOT get a seat) can be incorrectly classified as ABOVE, granting the voter a seat they are not entitled to.

**Affected call sites — all three are production verification paths.**

`implCheckShouldVote` (voter's own eligibility): [6](#0-5) 

`implVerifyVote` (peer vote verification): [7](#0-6) 

`implVerifyCert` (certificate verification): [8](#0-7) 

Because the same buggy function is used on both sides, a voter whose true seat count is 0 but whose VRF output lands in the ambiguous region will compute a non-zero seat count locally, submit a vote, and have it accepted by the verifier — which runs the identical buggy computation.

The `NormalizedVRFOutput` is produced by hashing the BLS signature and dividing by the maximum hash value:

```haskell
toNormalizedVRFOutput sig =
  NormalizedVRFOutput $
    fromIntegral (signatureNatural sig)
      / fromIntegral signatureNaturalMax
``` [9](#0-8) 

The VRF output is deterministic given the voter's key and the election input, so the voter can pre-compute whether the bug will fire for their specific output before submitting a vote.

---

### Impact Explanation

An attacker who controls a pool with sufficient stake to push `lambda` above `ln(3)` can, for elections where their deterministic VRF output falls in the ambiguous region, submit a vote or contribute to a certificate that the node's `implVerifyVote` / `implVerifyCert` incorrectly accepts. This is a bypass of the Peras local-sortition eligibility check: an ineligible non-persistent committee member's vote is accepted, inflating their voting power and potentially allowing a Peras certificate to be forged with insufficient legitimate stake. This matches the **Critical** impact class: bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance.

---

### Likelihood Explanation

The condition `lambda > ln(3) ≈ 1.099` is met whenever `numNonPersistentVoters * voterStake / totalNonPersistentStake > 1.099`. With a 10-seat non-persistent committee, any voter holding more than ~11 % of the non-persistent stake triggers the bug. Large stake pools — precisely the participants most likely to be non-persistent committee candidates — routinely exceed this threshold. The VRF output is deterministic, so the attacker can check offline whether their specific output falls in the ambiguous region before deciding to submit a vote.

---

### Recommendation

Replace the hardcoded `3` with the correct bound `exp lambda` (computed as a `FixedPoint`):

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

If `exp` is not available for `FixedPoint`, use a conservative integer upper bound derived from `lambda` (e.g., `ceiling (exp (toRational lambda))`). The `checkLeaderNatValue` analogy in the ledger is safe only because `lambda` there is always `f * sigma ≪ 1`; that assumption does not hold in the local-sortition context.

---

### Proof of Concept

1. Configure a Peras committee with `numNonPersistentVoters = 10`.
2. Create a pool holding 20 % of the total non-persistent stake → `lambda = 2.0 > ln(3)`.
3. Compute the pool's VRF output for a given `(epochNonce, electionId)`.
4. Evaluate `localSortitionNumSeats` with `boundX = 3` (current code) and with `boundX = exp 2.0 ≈ 7.39` (correct code).
5. Find a VRF output where the two computations disagree: the buggy code returns `numSeats > 0` while the correct code returns `numSeats = 0`.
6. Submit a `WFALSNonPersistentVote` with that VRF output; `implVerifyVote` calls the same buggy `localSortitionNumSeats` and accepts the vote.
7. Accumulate enough such votes to forge a `WFALSCert` that `implVerifyCert` accepts despite the voters being ineligible.
