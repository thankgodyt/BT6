### Title
`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate While `validatePerasVote` Enforces a Stake-Distribution Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance contains two parallel validation paths — one for votes and one for certificates — that apply inconsistent checks. `validatePerasVote` rejects a vote when the voter is absent from the stake distribution, but `validatePerasCert` unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer can therefore inject an arbitrary Peras certificate through the object-diffusion mini-protocol, have it accepted as "validated," and cause it to be stored and applied as a weight boost during chain selection.

---

### Finding Description

In `SupportsPeras.hs`, the `BlockSupportsPeras` instance provides the degenerate implementations used by all block types:

**`validatePerasCert`** — always succeeds, no checks performed: [1](#0-0) 

**`validatePerasVote`** — at minimum checks stake-distribution membership: [2](#0-1) 

The certificate path is wired directly into the production inbound-object pipeline. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` calls that callback on every inbound certificate and adds all that pass to the pool: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is stored. The resulting `ValidatedPerasCert` carries a `vpcCertBoost` drawn from `perasWeight params`: [5](#0-4) 

That boost is later consumed by chain selection via `PerasWeightSnapshot`, which is threaded through `ChainSelEnv`: [6](#0-5) 

The analog to the external report is exact: the scalar-kappa code path omits the `require(res >= 0)` guard that the vector-kappa path carries, producing divergent behaviour between two parallel paths. Here, the certificate path omits every guard that the vote path carries, so the two paths diverge in the same structural way.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any `pcCertBoostedBlock` (including a block on an adversary-controlled fork) and any `pcCertRound`. Because `validatePerasCert` never rejects, the certificate is stored as a `ValidatedPerasCert` with a full Peras weight boost. Chain selection then treats that boost as evidence of honest quorum, potentially causing an honest node to prefer a non-canonical chain over the true canonical chain. This matches the **High** allowed-impact category: *chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, and also the **Critical** category: *bypass of Peras certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

The attack requires only a network connection to a running node that has the Peras object-diffusion mini-protocol enabled. No keys, stake, or operator access are needed. The attacker sends a single well-formed CBOR-encoded `PerasCert` message; the node's inbound handler calls `validatePerasCert`, which always returns `Right`, and stores the certificate. The likelihood is **High** for any deployment where the Peras diffusion layer is active.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The certificate's cryptographic signature against the committee's aggregate key.
2. That the certified block (`pcCertBoostedBlock`) exists on a known chain and is within the valid round window.
3. That the round number (`pcCertRound`) is consistent with the current chain state.

Until a real implementation is available, the inbound certificate handler should reject all certificates rather than accept all of them, to avoid the asymmetry with `validatePerasVote`.

---

### Proof of Concept

1. Connect to a node with the Peras object-diffusion mini-protocol active.
2. Send a `PerasCert` message with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point on adversary fork>`.
3. Observe that `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}`.
4. The certificate is stored in the `PerasCertDB` / `ChainDB`.
5. On the next chain-selection event, the adversary fork receives the Peras weight boost, potentially causing the node to switch to the adversary's chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
