### Title
`safe_mint` Does Not Emit `FtMint` Event When Minting nBTC Tokens — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nbtc token contract increases the total token supply via `internal_deposit` but never emits the `FtMint` event required by NEP-141. This is a direct analog to the EIP-1155 compliance gap in the reference report: a state-changing mint path omits the mandatory event, causing off-chain consumers that rely on event-driven supply tracking to diverge from on-chain reality.

### Finding Description
The nbtc contract exposes two minting paths. The standard path uses `mint_inner`, which always emits `FtMint` after increasing supply: [1](#0-0) 

The safe-deposit path uses `safe_mint`, which calls `internal_deposit` on `self.bridge_id` — permanently increasing total supply — but never emits `FtMint` in any branch: [2](#0-1) 

Specifically:
- Line 112 (`self.token.internal_deposit(&self.bridge_id, amount.into())`) raises total supply unconditionally.
- If the recipient account is unregistered (line 114–116), the function returns `U128(0)` immediately — no event, no transfer. Supply is inflated with no corresponding event.
- If the recipient is registered, the function proceeds to `ft_transfer` / `ft_transfer_call` (lines 118–123), which emit `FtTransfer` but still no `FtMint`.

The `burn` function has a related but distinct issue: it emits `FtBurn` with `owner_id: &burn_account_id`, but the balance actually reduced is `self.bridge_id`'s: [3](#0-2) 

`internal_withdraw` is called on `self.bridge_id` (line 158–159), yet the event attributes the burn to `burn_account_id` (line 171). This misattributes every withdrawal burn in the event log.

### Impact Explanation
Any off-chain indexer, DeFi protocol, or bridge monitor that reconstructs nbtc circulating supply from NEP-141 events will undercount supply for every `safe_mint` call (no `FtMint` emitted) and misattribute the owner for every `burn` call (`burn_account_id` instead of `bridge_id`). This is the same class of harm described in the reference report: integrating protocols receive a structurally incorrect event stream and may act on wrong supply or ownership data. This maps to **Low** impact: a publicly reachable invariant violation in a production token path without direct fund theft.

### Likelihood Explanation
`safe_mint` is exercised on every safe-deposit flow (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`), a normal user-initiated operation. `burn` is exercised on every successful withdrawal verification. Both paths are triggered by ordinary, unprivileged bridge users with no special access required.

### Recommendation
1. In `safe_mint`, emit `FtMint { owner_id: &self.bridge_id, amount, memo: None }` immediately after `internal_deposit`, before any early return.
2. In `burn`, change the `FtBurn` event's `owner_id` from `&burn_account_id` to `&self.bridge_id`, since that is the account whose balance is actually reduced by `internal_withdraw`.

### Proof of Concept
**Missing `FtMint` in `safe_mint`:**
1. A relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
2. The bridge calls `nbtc.safe_mint(user, amount, msg)`.
3. `internal_deposit(&self.bridge_id, amount)` executes — total supply increases by `amount`.
4. No `FtMint` event is emitted in any branch.
5. An indexer summing `FtMint` events reports a supply lower than `ft_total_supply()` by `amount` for every safe deposit ever processed.

**Wrong `owner_id` in `FtBurn`:**
1. A user initiates a withdrawal via `ft_transfer_call`.
2. After on-chain confirmation, the bridge calls `nbtc.burn(user_account, burn_amount, relayer, relayer_fee)`.
3. `internal_withdraw(&self.bridge_id, burn_amount)` reduces `self.bridge_id`'s balance.
4. `FtBurn { owner_id: &user_account, amount: burn_amount }` is emitted.
5. An indexer tracking per-account burn history records the burn against `user_account`, not `bridge_id`, producing incorrect per-account supply attribution.

```rust
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```

```rust
    pub fn burn(
        &mut self,
        burn_account_id: AccountId,
        burn_amount: U128,
        relayer_account_id: AccountId,
        relayer_fee: U128,
    ) {
        self.assert_bridge();
        self.token
            .internal_withdraw(&self.bridge_id, burn_amount.into());
        if relayer_fee.0 > 0 {
            if self.token.accounts.get(&relayer_account_id).is_none() {
                self.token.internal_register_account(&relayer_account_id);
            }
            self.token.internal_transfer(
                &self.bridge_id,
                &relayer_account_id,
                relayer_fee.into(),
                None,
            );
        }
        near_contract_standards::fungible_token::events::FtBurn {
            owner_id: &burn_account_id,
            amount: burn_amount,
            memo: None,
        }
        .emit();
    }
```
