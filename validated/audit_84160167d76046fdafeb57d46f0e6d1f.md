### Title
Inconsistent Unit Mismatch in Peras Quorum Threshold Check Enables Certificate Forging Bypass - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares accumulated `PerasVoteStake` values (sourced from absolute ledger stake entries in `PerasVoteStakeDistr`) directly against `perasQuorumStakeThreshold`, which is a normalized relative `Rational` value (`3/4`). The two operands are in incompatible units. The code itself documents this mismatch with an explicit TODO. When the stake distribution is populated with absolute lovelace-scale values, the comparison trivially passes for any voter with stake > 0.75, allowing a single crafted vote to forge a Peras certificate and manipulate chain selection.

---

### Finding Description

`PerasVoteStake` is defined as a bare `Rational` wrapper with no enforced unit: [1](#0-0) 

The code's own NOTE explicitly states there is no consensus on whether this value is absolute (ledger lovelace) or relative (normalized fraction of total stake). The `stakeAboveThreshold` function then compares this value directly against `perasQuorumStakeThreshold`: [2](#0-1) 

The TODO on this function explicitly acknowledges the unit assumption is unverified and that normalization is not being performed before the call. The threshold is set to `3/4` (a relative value) in `mkPerasParams`: [3](#0-2) 

The `implEligiblePartyVoteWeight` function in `WFALS.hs` shows that persistent committee members receive a `VoteWeight` equal to their raw ledger stake (not normalized by total stake): [4](#0-3) 

When absolute ledger stake values (e.g., lovelace amounts in the range of billions) are stored in `PerasVoteStakeDistr` and looked up via `validatePerasVote`: [5](#0-4) 

...the comparison `stake >= 3/4` in `stakeAboveThreshold` is trivially satisfied by any voter with even 1 lovelace of stake. The `votesReachQuorum` function then returns `Just` and `forgePerasCert` is called: [6](#0-5) 

The production vote ingest path in `makePerasVotePoolWriterFromChainDB` currently uses `pure (PerasVoteStakeDistr mempty)` as a placeholder: [7](#0-6) 

The comment there explicitly states this is temporary and that real committee selection data will replace it. Once that plumbing is wired in with absolute ledger stake values, the unit mismatch becomes immediately exploitable.

---

### Impact Explanation

A forged Peras certificate boosts the chain weight of the targeted block by `perasWeight = 15`: [8](#0-7) 

An attacker who can send a single vote for an arbitrary block causes honest nodes to prefer that block's chain over the canonical chain, constituting a chain selection manipulation. This is a **High** impact: a chain selection bug triggered by an unprivileged peer via a crafted network vote, causing honest nodes to prefer a non-canonical or adversarially-chosen chain.

---

### Likelihood Explanation

The production code currently uses an empty `PerasVoteStakeDistr`, which causes all votes to fail validation (since `lookupPerasVoteStake` returns `Nothing`). However, the code is explicitly in transition — the TODO and the comment in `NodeToNode.hs` both confirm that real stake distribution data will be wired in. Once that happens, the unit mismatch becomes immediately exploitable with no additional preconditions. The vulnerability is latent but structurally guaranteed to activate upon the planned integration.

---

### Recommendation

Enforce a single unit for `PerasVoteStake` throughout the pipeline. The `stakeAboveThreshold` function must either:

1. Accept the total stake distribution and normalize `PerasVoteStake` internally before comparing against the relative threshold, or
2. Require that all callers normalize `PerasVoteStake` to a relative fraction before passing it in, enforced by a distinct newtype (e.g., `PerasNormalizedVoteStake`) that is only constructible via a normalization function.

The `PerasVoteStakeDistr` population path (in `implEligiblePartyVoteWeight` and the committee selection plumbing) must consistently produce normalized values before they are stored, so that the comparison in `stakeAboveThreshold` is always between two values in `[0, 1]`.

---

### Proof of Concept

**Setup:** Wire a real `PerasVoteStakeDistr` containing a single entry `(attackerVoterId, PerasVoteStake 1_000_000_000)` (1 billion lovelace, a realistic absolute stake value).

**Step 1:** Attacker sends a `PerasVote` for an arbitrary block `B` via the Peras vote diffusion miniprotocol.

**Step 2:** `validatePerasVote` looks up `attackerVoterId` in the distribution and returns `Right (ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1_000_000_000 })`.

**Step 3:** `votesReachQuorum` calls `stakeAboveThreshold` with `totalVoteStake = PerasVoteStake 1_000_000_000`.

**Step 4:** `stakeAboveThreshold` evaluates `1_000_000_000 >= 3/4 + 2/100`, which is `True`.

**Step 5:** `forgePerasCert` is called, producing a `ValidatedPerasCert` boosting block `B` by `perasWeight = 15`.

**Step 6:** The ChainDB accepts the certificate and chain selection now prefers any chain containing `B` over an equally-long honest chain, causing the node to diverge from the canonical chain. [9](#0-8) [3](#0-2)

-- | Check whether a given vote stake is above the quorum threshold.
--
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
