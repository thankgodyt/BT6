### Title
Unprivileged nBTC Holder Can Permanently Block Token Migration via Repeated Transfer Griefing — (`contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

The `migrate_to_new_token_mint` callback enforces a strict `sum == total_supply` invariant over a caller-supplied account list. Because the old nBTC token contract has no transfer-freeze mechanism, any token holder can repeatedly move their balance to a fresh account between migration attempts, causing the check to fail indefinitely.

---

### Finding Description

`migrate_to_new_token` (the privileged entry point) calls `internal_migrate_to_new_token`, which fires async cross-contract calls to query `ft_total_supply()` and `ft_balance_of(account)` for every account in the operator-supplied list. [1](#0-0) 

The callback `migrate_to_new_token_mint` sums those balances and requires the sum to equal the total supply:

```
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [2](#0-1) 

If **any** account holding tokens is absent from the list, `sum < total_supply` and the `require!` panics, reverting the entire migration attempt. No state is committed; the bridge's `nbtc_account_id` remains unchanged. [3](#0-2) 

The old nBTC token contract exposes a fully unrestricted `ft_transfer`:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    ...
    self.token.ft_transfer(receiver_id, amount, memo);
}
``` [4](#0-3) 

There is **no pause, freeze, or migration-lock** on this function anywhere in the nBTC contract.


**Attack loop:**

1. Attacker legitimately holds nBTC in account `A` (obtained via normal bridge deposit).
2. Operator enumerates all known holders and calls `migrate_to_new_token([..., A, ...])`.
3. Before (or during) the async callback window, attacker calls `ft_transfer` to move their entire balance from `A` to a fresh account `B` (paying ~0.00125 NEAR for storage registration).
4. Callback executes: `balance_of(A) == 0`, `balance_of(B)` was never queried → `sum < total_supply` → `require!` panics.
5. Operator retries with `B` added to the list.
6. Attacker transfers from `B` to `C`. Repeat from step 4.

Each iteration costs the attacker only one storage deposit (~0.00125 NEAR). The operator has no on-chain mechanism to freeze transfers or take an atomic snapshot.

---

### Impact Explanation

Migration is permanently deniable as long as the attacker is willing to pay trivial storage fees. The bridge cannot switch to the new token contract, which is the entire purpose of the migration path. This constitutes a stuck bridge state requiring operator intervention with no available on-chain remedy under the current code.

---

### Likelihood Explanation

Any nBTC holder — including one who acquired tokens through the normal public deposit flow — can execute this with no special privileges. The cost per blocking round is negligible (~0.00125 NEAR). The NEAR FungibleToken standard provides no enumeration of all accounts, so the operator cannot build a guaranteed-complete list off-chain either.

---

### Recommendation

Add a transfer-freeze flag to the old nBTC token contract that the bridge (as `bridge_id`) can set before initiating migration, blocking all `ft_transfer` / `ft_transfer_call` calls until migration completes or is aborted. Alternatively, implement a two-phase migration: first snapshot total supply and lock transfers, then enumerate holders and mint on the new token.

---

### Proof of Concept

```rust
// Pseudocode unit test
let attacker_account = "attacker.near";
let fresh_account    = "fresh.near";

// Operator attempts migration with known holders including attacker
bridge.migrate_to_new_token(new_token, vec![..., attacker_account]);

// Attacker front-runs or races the callback:
old_token.ft_transfer(fresh_account, attacker_balance);

// Callback fires: sum(balances) < total_supply → require! panics
// Migration reverted.

// Operator retries with fresh_account added:
bridge.migrate_to_new_token(new_token, vec![..., fresh_account]);

// Attacker transfers again to another_fresh_account
old_token.ft_transfer(another_fresh_account, attacker_balance);

// Migration reverted again. Loop is unbounded.
assert!(migration_never_completes());
```
