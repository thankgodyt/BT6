Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Pre-funded Message Storage Account — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `NativeFeeRestricted` role check in `init_transfer()` is placed exclusively inside branch B of a short-circuit `||` condition. Branch A — `try_to_transfer_balance_from_message_account` — carries no role check. Because `storage_deposit` is a public function that accepts any `account_id`, a `NativeFeeRestricted` account can pre-fund the deterministic message storage account before calling `ft_transfer_call`, causing branch A to succeed and the role check to be skipped entirely, allowing a non-zero `native_token_fee` to be attached to the bridge transfer.

## Finding Description
In `near/omni-bridge/src/lib.rs` at lines 566–584, `init_transfer()` selects the storage-payment path via:

```rust
if self
    .try_to_transfer_balance_from_message_account(   // branch A — no role check
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()
|| (self.has_storage_balance(...)
    && (init_transfer_msg.native_token_fee.0 == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
                                                     // branch B — role check here
```

The `NativeFeeRestricted` guard lives only in branch B. If branch A returns `Ok(())`, the `||` short-circuits and `init_transfer_internal` is called with the non-zero `native_token_fee` intact.

`try_to_transfer_balance_from_message_account` (lines 260–290 of `storage.rs`) only checks whether the message account has enough balance to cover `native_fee` and whether the storage payer has enough balance after the transfer — no role check is performed.

The `message_storage_account_id` is computed deterministically at line 562–563:
```rust
let message_storage_account_id = transfer_message
    .calculate_storage_account_id(init_transfer_msg.external_id.map(String::from));
```

`storage_deposit` (lines 141–169 of `storage.rs`) is a public payable function that accepts an arbitrary `account_id` parameter, allowing anyone to fund any account ID, including a not-yet-used message storage account.

## Impact Explanation
This is a concrete role bypass: the `NativeFeeRestricted` role is explicitly designed to prevent certain accounts from attaching a non-zero `native_token_fee` to bridge transfers (confirmed by the role definition at lines 113–129 and the test suite in `near/omni-tests/src/native_fee_role.rs`). The bypass allows a restricted account to attach an arbitrary native fee, which is emitted in the `InitTransferEvent` and used by relayers to prioritize processing. This constitutes an unauthorized bridge action via role bypass, matching the allowed Critical impact scope.

## Likelihood Explanation
The exploit requires only standard, publicly available contract calls with no privileged access, leaked keys, or external dependencies. The `message_storage_account_id` is fully derivable off-chain from public inputs. Any account holding the `NativeFeeRestricted` role can independently execute the two-step sequence (pre-fund + `ft_transfer_call`) on every transfer they initiate. The bypass is repeatable and unconditional.

## Recommendation
Hoist the role check outside the storage-path selection so it is unconditional:

```rust
let native_fee_allowed = init_transfer_msg.native_token_fee.0 == 0
    || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone());

require!(native_fee_allowed, BridgeError::OperationNotAllowed.as_ref());

if self
    .try_to_transfer_balance_from_message_account(...)
    .is_ok()
    || self.has_storage_balance(&signer_id, ...)
{
    ...
}
```

This ensures the `NativeFeeRestricted` check cannot be bypassed regardless of which storage-payment branch is taken.

## Proof of Concept
1. Alice holds the `NativeFeeRestricted` role on the bridge contract.
2. Alice constructs the `InitTransferMsg` with `native_token_fee > 0` and derives `message_storage_account_id` off-chain (deterministic from public inputs via `calculate_storage_account_id`).
3. Alice calls `storage_deposit` on the bridge contract with `account_id = message_storage_account_id`, depositing at least `native_token_fee + required_storage_balance` yoctoNEAR.
4. Alice calls `ft_transfer_call` on the token contract routing to the bridge with the crafted `InitTransferMsg`.
5. Inside `ft_on_transfer` → `init_transfer`, branch A (`try_to_transfer_balance_from_message_account`) succeeds because the message account is funded.
6. The `||` short-circuits; branch B (containing the `NativeFeeRestricted` check) is never evaluated.
7. `init_transfer_internal` is called with the non-zero `native_token_fee`, and `InitTransferEvent` is emitted with the fee intact — bypassing the role restriction.

A sandbox integration test can reproduce this by extending `near/omni-tests/src/native_fee_role.rs`: grant `NativeFeeRestricted` to the sender, pre-fund the computed message storage account via `storage_deposit`, then call `ft_transfer_call` with `native_token_fee > 0` and assert the returned transfer amount equals the full amount (success) and the emitted event contains the non-zero native fee.
