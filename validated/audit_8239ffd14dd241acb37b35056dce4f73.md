### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates, Enabling Forged-Certificate Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or committee-membership checks. Because this function is wired directly into the live peer-certificate ingestion path (`makePerasCertPoolWriterFromChainDB`), any unprivileged peer can inject arbitrarily forged `PerasCert` values that are accepted, stored in the `PerasCertDB`, and used to boost a chosen block's chain-selection weight by `PerasWeight 15` per certificate. This allows an attacker to manipulate chain selection on an honest node without holding any stake or cryptographic keys.

---

### Finding Description

**Root cause — unconditional `Right` in the production validation stub:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This is not a test helper — it is the sole `BlockSupportsPeras` instance, declared for all `StandardHash blk`: [2](#0-1) 

**Production ingestion path wires this stub directly:**

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate and, if all pass (which they always do), adds them to the ChainDB: [4](#0-3) 

**Chain selection is then triggered for the boosted block:**

`chainSelSync` receives the accepted certificate, looks up the boosted block in the `VolatileDB`, and calls `chainSelectionForBlock` for it: [5](#0-4) 

**The boost weight applied per forged certificate is `PerasWeight 15`:** [6](#0-5) 

**Chain selection compares `wsvTotalWeight = blockNo + weightBoost`:** [7](#0-6) 

**End-to-end exploit flow:**

1. Attacker peer connects via the ObjectDiffusion mini-protocol (no stake or keys required).
2. Attacker crafts a `PerasCert { pcCertRound = R, pcCertBoostedBlock = P }` targeting any block `P` in the victim node's `VolatileDB`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
4. The cert is stored in `PerasCertDB` and `addPerasCertAsync` is called.
5. `chainSelSync` looks up block `P` in `VolatileDB`, finds it, and calls `chainSelectionForBlock` for it.
6. The chain containing `P` now has `+15` total weight. If this exceeds the honest chain's weight, the node switches to the attacker-chosen fork.
7. The attacker can send one forged cert per round number (deduplication is by `PerasRoundNo` only), accumulating boosts across multiple rounds.

---

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

Because `validatePerasCert` never rejects any certificate, an attacker with no stake and no cryptographic keys can:

- Force an honest node to prefer a shorter or weaker fork by boosting a block on that fork. Each forged certificate adds `PerasWeight 15` to the total weight of the boosted chain. With `k = 2160` on Cardano mainnet, an attacker needs to inject roughly `2160 / 15 = 144` forged certificates (one per distinct round number) to overcome a `k`-block honest chain lead — a trivially cheap operation.
- Cause the node to roll back its current selection and switch to an attacker-controlled fork, violating the chain-selection invariant that only cryptographically valid Peras certificates may influence weight.
- Permanently anchor a forged boost in the `PerasCertDB` (deduplication prevents the honest certificate for the same round from being accepted later if the forged one arrived first), potentially locking out the legitimate certificate for that round.

This directly matches the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**High.** The ObjectDiffusion mini-protocol is reachable by any peer that can establish a connection to the node. No stake, no keys, and no privileged access are required. The attacker only needs to know a block hash present in the target node's `VolatileDB` (easily obtained via `ChainSync`). The forged certificate structure is trivially constructable: `PerasCert` contains only a `PerasRoundNo` (a `Word64`) and a `Point blk` (slot + hash). The stub is the sole production implementation and is unconditional — there is no code path that rejects a well-formed `PerasCert` value.

---

### Recommendation

Replace the stub with a real implementation that:

1. Verifies the aggregate vote signature over `(pcCertRound, pcCertBoostedBlock)` against the registered committee members' keys.
2. Checks that the signers collectively hold stake above the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
3. Verifies that each signer's VRF output proves committee eligibility for the given round.

Until the real implementation is available, the stub should be replaced with a hard rejection (`Left PerasValidationErr`) so that no peer-supplied certificate is accepted, rather than accepting all of them. The `TODO` at [issue #120](https://github.com/tweag/cardano-peras/issues/120) tracks this work and must be resolved before Peras certificate diffusion is enabled in production.

### Proof of Concept

**Setup:** A private two-node testnet with Peras enabled. Node A is the honest node; Node B is the attacker.

**Steps:**

1. Node B connects to Node A via the ObjectDiffusion mini-protocol for Peras certificates.
2. Node B observes Node A's current chain tip via `ChainSync` to learn a block hash `H` at slot `S` on a fork that is 10 blocks shorter than Node A's current selection.
3. Node B constructs and sends 15 `PerasCert` values:
   ```
   PerasCert { pcCertRound = R_i, pcCertBoostedBlock = BlockPoint S H }
   for R_i in [1..15]
   ```
4. Each cert passes `validatePerasCert` (returns `Right`) and is stored in Node A's `PerasCertDB`.
5. `chainSelSync` triggers `chainSelectionForBlock` for block `H` after each cert.
6. After 15 certs, the fork containing `H` has `weightBoost = 15 * 15 = 225`, which exceeds the honest chain's 10-block lead (`BlockNo` advantage = 10).
7. Node A switches to the attacker-chosen fork.

**Expected outcome without the fix:** Node A switches to the shorter, attacker-chosen fork.
**Expected outcome with the fix:** All 15 forged certs are rejected with `PerasValidationErr`; Node A remains on the honest chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
