### Title
Degenerate `validatePerasCert` Accepts Any Certificate Without Cryptographic Verification, Enabling Unprivileged Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass in `SupportsPeras.hs` ships a catch-all default instance (explicitly labelled a TODO stub) whose `validatePerasCert` implementation unconditionally accepts every incoming `PerasCert` and stamps it with the full configured `perasWeight` boost — performing zero cryptographic or quorum checks. When Peras is enabled, any unprivileged peer that can submit a `PerasCert` message can cause the receiving node to apply an unearned weight boost to an arbitrary block, directly manipulating chain selection in favour of a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub, lines 350–358:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always 15 blocks of weight
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository. It is a universal catch-all (`instance StandardHash blk => BlockSupportsPeras blk`) that covers every block type, including any future Cardano block, because no era-specific override exists. [2](#0-1) 

**What is missing:** The production WFALS committee implementation (`WFALS.hs`) shows what a correct `verifyCert` must do: traverse every voter's seat index against the stake distribution, check persistent/non-persistent membership, verify the aggregate BLS signature, and verify aggregate VRF outputs for non-persistent voters. [3](#0-2) 

None of those checks exist in the degenerate instance. The `PerasValidationErr` type is also a single opaque constructor with no variants, making it impossible to distinguish error cases even if validation were attempted. [4](#0-3) 

**Attack entry path:**

1. A peer submits a crafted `PerasCert` (arbitrary `pcCertRound`, arbitrary `pcCertBoostedBlock`) via the Peras certificate mini-protocol.
2. The receiving node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert{..., vpcCertBoost = perasWeight params}` unconditionally.
3. The `ValidatedPerasCert` is passed to `addPerasCertAsync` in the ChainDB API. [5](#0-4) 

4. `chainSelSync` processes the certificate, looks up the boosted block in the VolatileDB, and triggers `chainSelectionForBlock` for it. [6](#0-5) 

5. `preferAnchoredCandidate` computes `weightedSelectView`, which adds `perasWeight` (= 15) to the total weight of any fragment containing the boosted block. [7](#0-6) 

6. A chain that is up to 15 blocks shorter than the canonical chain is now preferred, causing the node to switch to a non-canonical fork.

**Analog to the external report:** Just as the Distributor contract's `_distribute` accepts an arbitrary `winners[]` array without validating that the addresses are legitimate contest participants, `validatePerasCert` accepts an arbitrary `PerasCert` without validating that the voters are legitimate committee members or that the aggregate signature is correct. In both cases, an authorized-but-crafted input bypasses all allocation/distribution guards.

---

### Impact Explanation

**Classification:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

With `perasWeight = 15` (the default), an attacker can make the victim node treat a fork that is up to 15 blocks shorter than the canonical chain as heavier. Because chain selection is the mechanism by which nodes agree on the canonical chain, this directly violates consensus safety: the victim node diverges from honest peers that have not received the forged certificate. If the attacker can deliver the certificate to a sufficient fraction of nodes, a network-wide split is possible.

---

### Likelihood Explanation

**Medium.** Peras is gated behind an experimental feature flag (`rnFeatureFlags`) and is disabled by default. However:
- The flag is a runtime configuration option, not a compile-time guard; any operator who enables it is immediately exposed.
- The degenerate instance is the **only** instance — there is no safe fallback.
- No cryptographic material is required from the attacker; the certificate structure (`pcCertRound :: Word64`, `pcCertBoostedBlock :: Point blk`) is trivially constructable.
- The CHANGELOG confirms the ChainDB is already wired to act on received certificates: *"Make the ChainDB aware of the PerasCertDB, and modify the chain selection function accordingly."* [8](#0-7) 

---

### Recommendation

Replace the degenerate stub with a real implementation that mirrors the WFALS `implVerifyCert` logic:

1. For each voter seat index in the certificate, look up the voter in the epoch's stake distribution via `getCandidateIfSeatWithinBounds`.
2. Verify persistent/non-persistent membership.
3. Aggregate the voters' verification keys and call `verifyAggregateVoteSignature`.
4. For non-persistent voters, batch-verify VRF outputs via `batchVerifyVRFOutputs`.
5. Compute the actual vote weight from verified voters only; reject the certificate if it does not meet the quorum threshold.
6. Only on full success, construct `ValidatedPerasCert` with the earned boost.

Until a real implementation is ready, `validatePerasCert` should return `Left PerasValidationErr` (reject all certificates) rather than `Right` (accept all certificates), so that enabling the feature flag does not silently open the attack surface.

implVerifyCert committee = \case
  WFALSCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    -- 3. optionally, their VRF verification keys and outputs (to verify the
    --    aggregate VRF output for non-persistent voters, if any)
    (members, voteVerificationKeys, optionalVRFKeysAndOutputs) <-
      fmap nonEmptyUnzip3 . flip traverse (NEMap.toAscList voters) $ \case
        -- Persistent voter
        (seatIndex, Nothing)
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
          , isPersistentMember seatIndex committee -> do
              let voterVoteVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              pure
                ( WFALSPersistentMember
                    seatIndex
                    voterStake
                , voterVoteVerificationKey
                , Nothing
                )
          | otherwise ->
              Left (NotAPersistentMember seatIndex)
        -- Non-persistent voter
        (seatIndex, Just vrfOutput)
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
          , not (isPersistentMember seatIndex committee) -> do
              let voterVoteVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              let voterVRFVerificationKey =
                    getVRFVerificationKey (Proxy @crypto) voterPublicKey
              let numSeats =
                    localSortitionNumSeats
                      (nonPersistentCommitteeSize committee)
                      (totalNonPersistentStake committee)
                      voterStake
                      (normalizeVRFOutput vrfOutput)
              case nonZero numSeats of
                Nothing ->
                  Left (ZeroNonPersistentSeats seatIndex)
                Just nonZeroNumSeats ->
                  pure
                    ( WFALSNonPersistentMember
                        seatIndex
                        voterStake
                        vrfOutput
                        nonZeroNumSeats
                    , voterVoteVerificationKey
                    , Just (voterVRFVerificationKey, vrfOutput)
                    )
          | otherwise ->
              Left (NotANonPersistentMember seatIndex)

    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)
        aggVerificationKey
        electionId
        candidate
        aggSig

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
