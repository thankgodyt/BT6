### Title
Missing Cryptographic Signature Verification in Peras Vote Validation Allows Voter Identity Spoofing - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance currently wired into the production Peras vote diffusion handler — defines a `PerasVote` type with no cryptographic signature field and a `validatePerasVote` function that accepts any vote whose claimed `pvVoteVoterId` appears in the stake distribution, without any proof that the sender controls that identity. This is the direct analog of the reported "insufficient validation of intermediate accounts" class: the voter identity field is passed through the diffusion pipeline and accepted on name alone, with no binding cryptographic check. When the stake distribution is properly wired in (as the in-code TODO explicitly anticipates), any unprivileged peer can forge votes for any stake pool, accumulate a quorum, and cause the node to generate a Peras certificate boosting an attacker-chosen block, manipulating chain selection.

### Finding Description

**Root cause — no signature field in `PerasVote`:**

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` defines:

```haskell
data PerasVote blk = PerasVote
    { pvVoteRound  :: PerasRoundNo
    , pvVoteBlock  :: Point blk
    , pvVoteVoterId :: PerasVoterId   -- claimed identity, no proof
    }
```

There is no `pvSignature` field. Compare with the concrete BLS vote type in `Peras/Vote/V1.hs` which does carry `pvSignature :: VoteSignature PerasBLSCrypto` — but that type is not yet wired into the `BlockSupportsPeras` typeclass. [1](#0-0) [2](#0-1) 

**Root cause — `validatePerasVote` performs only a stake-distribution membership check:**

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

`lookupPerasVoteStake` simply does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. No signature is checked; any vote whose `pvVoteVoterId` key exists in the map is unconditionally accepted as `ValidatedPerasVote`. [3](#0-2) [4](#0-3) 

**Production wiring — the degenerate instance is the active handler:**

`mkHandlers` in `NodeToNode.hs` wires `makePerasVotePoolWriterFromChainDB` as the inbound Peras vote handler. The stake distribution argument is currently `(pure (PerasVoteStakeDistr mempty))` — an explicit placeholder that the in-code comment acknowledges will be replaced with real committee data:

```
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [5](#0-4) 

The empty map is the only thing currently preventing exploitation; it is not a security control — it is a missing feature placeholder. Once the real stake distribution is plumbed in, `validatePerasVote` will accept any vote whose claimed voter ID appears in the distribution, with no cryptographic proof required.

**`validatePerasCert` is also unconditional:**

The same degenerate instance accepts every inbound certificate without any check:

```haskell
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

Unlike votes, the cert diffusion handler carries no empty-distribution guard, so this path is immediately reachable. [6](#0-5) 

### Impact Explanation

**Impact: Critical — Bypass of Peras voting and certificate checks enabling unauthorized vote and certificate acceptance.**

Once the stake distribution is populated (the stated next step per the TODO), an unprivileged peer can:

1. Enumerate any `PerasVoterId` present in the stake distribution (public information).
2. Craft `PerasVote` messages with that voter ID, any round number, and any target block point.
3. Send enough forged votes to satisfy `votesReachQuorum` (total stake ≥ quorum threshold).
4. Trigger `forgePerasCert`, producing a `ValidatedPerasCert` that boosts the attacker-chosen block's chain weight by `perasWeight`.
5. Chain selection then prefers the boosted block, causing the honest node to diverge from the canonical chain.

For `validatePerasCert`, the attack is simpler and already reachable: send a single crafted `PerasCert` for any block; it is accepted unconditionally and stored in the ChainDB, immediately boosting that block's weight.

### Likelihood Explanation

**Likelihood: High (for `validatePerasCert`); Medium-High (for `validatePerasVote` once stake distribution is live).**

- The cert path requires no precondition beyond network connectivity; `validatePerasCert` accepts all certs today.
- The vote path requires the stake distribution to be non-empty, which is the explicitly planned next development step per the in-code TODO and linked issue (`cardano-peras/issues/73`).
- No privileged access, leaked keys, or stake majority is required. Any peer reachable via the Peras vote/cert diffusion mini-protocol can trigger the attack.
- The `PerasVote` wire format is public and trivially constructable (three CBOR fields: round number, block point, voter key hash). [7](#0-6) 

### Recommendation

1. **Add a `pvSignature` field to the `PerasVote` data type** in the `BlockSupportsPeras` instance (or replace the degenerate instance with the concrete BLS-signed type from `Peras/Vote/V1.hs` before wiring in the real stake distribution).
2. **`validatePerasVote` must verify the cryptographic signature** over `(pvVoteRound, pvVoteBlock)` using the public key associated with `pvVoteVoterId` in the committee, analogous to `implVerifyVote` in `Committee/EveryoneVotes.hs` and `Committee/WFALS.hs`.
3. **`validatePerasCert` must not be a no-op.** It must verify the aggregate BLS signature over the certificate contents before accepting it.
4. Do not wire in the real stake distribution until signature verification is in place; the empty distribution is the only current guard against the vote-spoofing path. [8](#0-7) 

### Proof of Concept

**Vote spoofing (active once stake distribution is non-empty):**

1. Connect to a target node via the Peras vote diffusion mini-protocol.
2. Obtain the current `PerasVoteStakeDistr` (derivable from the public ledger state).
3. Pick any `PerasVoterId` with sufficient stake, e.g., `vid` with stake `s`.
4. Construct `N` distinct `PerasVote` messages (varying `pvVoteVoterId` across eligible pool IDs) all targeting the same `(pvVoteRound, pvVoteBlock)` until `sum(stakes) >= quorum`.
5. Send the batch via `objectDiffusionInbound`. Each vote passes `validatePerasVote` because `lookupPerasVoteStake` finds the voter ID in the distribution — no signature is checked.
6. `processVotes` stores all votes; `votesReachQuorum` triggers `forgePerasCert`; the resulting `ValidatedPerasCert` is stored in the ChainDB with `vpcCertBoost = perasWeight params`.
7. Chain selection now weights the attacker-chosen block higher than competing honest blocks.

**Certificate spoofing (immediately reachable):**

1. Connect to a target node via the Peras cert diffusion mini-protocol.
2. Construct `PerasCert { pcCertRound = r, pcCertBoostedBlock = p }` for any block point `p`.
3. Send it. `validatePerasCert` returns `Right` unconditionally; the cert is stored and boosts `p`'s chain weight immediately. [9](#0-8) [10](#0-9)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
