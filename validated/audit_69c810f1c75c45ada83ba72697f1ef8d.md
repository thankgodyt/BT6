### Title
Unconditional Peras Certificate Acceptance Enables Arbitrary Chain-Weight Inflation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic validation. Because the Peras weight boost derived from accepted certificates is used directly in chain selection (fragment comparison, rollback-depth check, and immutability boundary computation), an unprivileged peer can send a crafted certificate to inflate the weight of any block in the VolatileDB, causing the node to prefer an adversarial fork or to prematurely treat blocks as immutable.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate that must authenticate a certificate before it is stored and its weight boost applied. The only production instance of this class is the blanket `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs`. Its implementation is an acknowledged stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- full configured boost, unconditionally
      }
``` [1](#0-0) 

The production certificate ingest path in `makePerasCertPoolWriterFromChainDB` calls `processCerts` with this stub as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` accepts the entire batch when all certificates pass validation (which they always do), timestamps them, and adds them to the ChainDB via `addPerasCertAsync`. [3](#0-2) 

`addPerasCertAsync` triggers `chainSelSync`, which calls `chainSelectionForBlock` for the boosted block. [4](#0-3) 

The accepted certificate's boost is then reflected in the `PerasWeightSnapshot` used throughout chain selection:

1. **Fragment comparison** — `preferCandidate` in `WeightedSelectView` compares `wsvTotalWeight`, which sums `BlockNo` and `wsvWeightBoost`. A boosted adversarial fork can be preferred over a longer honest chain. [5](#0-4) 

2. **Rollback-depth check** — `forksAtMostKWeight` uses `totalWeightOfFragment` on the suffix of the current chain. Boosting blocks on the current chain inflates this weight, making the node refuse to roll back even when it should. [6](#0-5) 

3. **Immutability boundary** — `takeVolatileSuffix` uses `totalWeightOfFragment` to determine which blocks are buried under weight `k` and therefore immutable. A fake boost can cause blocks to be moved to the ImmutableDB prematurely, making them permanently unrollbackable. [7](#0-6) 

The security parameter `k` is now interpreted as a weight, not a block count, so a single fake certificate with boost `B` reduces the effective rollback depth by `B` blocks. [8](#0-7) 

---

### Impact Explanation

**High — Chain selection and rollback security bug.**

An unprivileged peer can:
- **Force a chain switch**: Send a certificate boosting a block on an adversarial fork. The fork's `wsvTotalWeight` exceeds the honest chain's, causing `preferCandidate` to return `ShouldSwitch`. The node adopts the adversarial chain.
- **Prevent a legitimate rollback**: Send a certificate boosting blocks on the current chain. `forksAtMostKWeight` will report that the honest candidate forks too deep (its weight exceeds `k`), causing the node to reject a valid longer chain.
- **Corrupt the ImmutableDB boundary**: A boosted block is counted as multiple units of weight in `takeVolatileSuffix`. Blocks that should remain volatile (rollbackable) are moved to the ImmutableDB, permanently locking in a potentially wrong chain state.

All three effects violate the core Ouroboros safety guarantee that an honest node will not permanently diverge from the canonical chain.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production node kernel. Any peer that can establish a connection and send a `PerasCert` message triggers this path. No stake, no keys, and no valid BLS signature are required — the stub accepts any syntactically well-formed certificate. The only deduplication is by `PerasRoundNo`; an attacker can use a fresh round number for each certificate. The attack requires only a single network message.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregate public key of the claimed committee members (as already implemented in `Ouroboros.Consensus.Peras.Crypto.BLS`).
2. Verifies that the claimed voters were actually elected to the committee for that round using the WFA/local-sortition scheme.
3. Verifies that the total stake of the signers exceeds the quorum threshold.

Until the real implementation is in place, the certificate ingest path should be disabled or the boost should not be applied to chain selection.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe that the honest chain tip is at block `B_honest` (block number `N`).
2. Construct an adversarial fork with tip `B_adv` at block number `N-1` (shorter than honest).
3. Craft a `PerasCert` with `pcCertRound = <fresh round>` and `pcCertBoostedBlock = blockPoint B_adv`.
4. Send the certificate to the target node via the Peras cert diffusion protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams` → `Right (ValidatedPerasCert { vpcCertBoost = perasWeight params })`.
6. `addPerasCertAsync` stores the cert; `chainSelSync` triggers `chainSelectionForBlock` for `B_adv`.
7. `weightedSelectView` computes `wsvTotalWeight` for the adversarial fragment as `(N-1) + perasWeight` (e.g., `N-1+15 = N+14`), which exceeds the honest chain's `N`.
8. `preferCandidate` returns `ShouldSwitch`; the node rolls back to `B_adv` and adopts the adversarial chain. [9](#0-8) [10](#0-9) [11](#0-10)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

      mapM_

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

takeVolatileSuffix ::
  forall blk h.
  (StandardHash blk, HasHeader h, HeaderHash blk ~ HeaderHash h) =>
  PerasWeightSnapshot blk ->
  -- | The security parameter @k@ is interpreted as a weight.
  SecurityParam ->

  | Map.null $ getPerasWeightSnapshot snap =
      -- Optimize the case where Peras is disabled.
      AF.anchorNewest (unPerasWeight k)
  | otherwise =
      takeLongestSuffix (totalWeightOfFragment snap) (<= k)

  k :: PerasWeight
