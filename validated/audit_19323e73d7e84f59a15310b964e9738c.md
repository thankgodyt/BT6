### Title
Missing `refund_address` Chain Validation at Submission Time Causes Permanently Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` accepts and stores a `refund_address` string without validating it against the bridge's configured chain. Validation only occurs inside `execute_refund` → `build_refund_output`, where an invalid address causes a hard panic. Any caller — including an attacker front-running a victim's refund — can lock a deposit UTXO in a permanently stuck refund state that requires DAO intervention to clear.

### Finding Description
In `internal_request_refund` (refund.rs:137–184), the `refund_address` parameter is accepted and forwarded to `request_refund_callback` with no format or chain check: [1](#0-0) 

Inside `request_refund_callback` (refund.rs:497–581), the address is stored verbatim into `RefundRequest.refund_address` with no validation: [2](#0-1) 

The only validation point is `build_refund_output` (refund.rs:294–308), which calls `Address::parse(refund_address, config.chain.clone()).expect("Invalid refund address")`. If the address is malformed or belongs to a different chain, this panics and reverts the entire `execute_refund` call: [3](#0-2) 

`Address::parse` enforces chain-specific HRP (for bech32) and prefix bytes (for base58), so a wrong-chain address — e.g., a Zcash address submitted to a Bitcoin-configured bridge — will always panic here: [4](#0-3) 

The public `request_refund` entry point in `api/bridge.rs` has no access control beyond the pause guard, so any unprivileged NEAR account can call it: [5](#0-4) 

The duplicate-request guard in `request_refund_callback` means only one refund request can exist per UTXO at a time: [6](#0-5) 

### Impact Explanation
Once a refund request with an invalid `refund_address` is stored, every call to `execute_refund` for that UTXO panics. The deposit UTXO is locked in `refund_requests`. No refund can proceed. The DAO must call `reject_refund` to clear the stuck entry before the legitimate user can re-submit. If the original deposit was never finalized (the reason for the refund), the user's BTC/ZEC is inaccessible until DAO intervention. This is a publicly reachable panic-driven stuck-state in a production bridge path.

### Likelihood Explanation
NEAR transactions are observable in the mempool. An attacker who sees a victim's `request_refund` call (which includes the `deposit_msg`, `tx_bytes`, `vout`, and proof — all public) can front-run it with the same proof but an invalid `refund_address` (e.g., a Zcash address on a Bitcoin bridge, or a random string). The attacker's only cost is the non-refundable storage deposit. The victim's refund is blocked until DAO intervention. Bitcoin deposit transactions are also fully public, so an attacker can proactively monitor for unfinalized deposits and race to submit a poisoned refund request before the victim does.

### Recommendation
Validate `refund_address` against the configured chain at the time of `request_refund` submission, before the light-client cross-contract call is made. Add the following check in `internal_request_refund`, after the existing `deposit_msg.refund_address` consistency check:

```rust
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This mirrors the validation already present in `build_refund_output` and ensures that an invalid address is rejected immediately, before any state is written.

### Proof of Concept
1. Alice deposits BTC to the bridge; the deposit is never finalized by a relayer.
2. Alice constructs a `request_refund` call with her valid Bitcoin `refund_address`, the correct `deposit_msg`, `tx_bytes`, `vout`, and a valid light-client proof.
3. Bob (attacker) observes Alice's pending NEAR transaction in the mempool. He submits an identical call but substitutes `refund_address` with `"zcash_mainnet_address_here"` (valid Zcash syntax, wrong chain) or any malformed string.
4. Bob's call is processed first. `request_refund_callback` verifies the light-client proof (valid), checks the output script (valid), and stores the `RefundRequest` with the invalid `refund_address`. No address validation occurs.
5. Alice's call fails: `"Refund request already exists for this UTXO"`.
6. Anyone calls `execute_refund` for Alice's UTXO → `build_refund_output` calls `Address::parse("zcash_mainnet_address_here", Chain::BitcoinMainnet)` → panics with `"Invalid refund address"`. The call reverts; no state changes.
7. Alice's BTC is inaccessible. The DAO must call `reject_refund` to clear the stuck entry. Alice then re-submits with her valid address, paying another storage deposit.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub fn parse(address: &str, chain: Chain) -> Result<Self, String> {
        if chain == Chain::ZcashMainnet || chain == Chain::ZcashTestnet {
            let addr = ZcashAddress::try_from_encoded(address)
                .map_err(|e| format!("Error on parsing ZCash Address: {e}"))?;

            let network = match chain {
                Chain::ZcashMainnet => zcash_protocol::consensus::NetworkType::Main,
                Chain::ZcashTestnet => zcash_protocol::consensus::NetworkType::Test,
                _ => unreachable!(),
            };

            return addr
                .convert_if_network::<Self>(network)
                .map_err(|e| e.to_string());
        }

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
