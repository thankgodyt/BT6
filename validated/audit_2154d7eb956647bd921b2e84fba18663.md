### Title
Premature Token Minting Before Account-Registration Check in `safe_mint` Causes Permanent Loss of User Deposit Funds — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

`safe_mint` in the nBTC token contract mints tokens to the bridge account **before** verifying that the recipient account is registered. If the recipient is unregistered, the function returns `U128(0)` without burning the already-minted tokens, leaving them permanently orphaned at the bridge while the user's BTC deposit is consumed with no nBTC issued.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes in this order:

```
Line 112: self.token.internal_deposit(&self.bridge_id, amount.into());  // tokens minted to bridge
Line 114: if self.token.accounts.get(&account_id).is_none() {
Line 115:     return PromiseOrValue::Value(U128(0));                     // early return — tokens NOT burned
Line 116: }
``` [1](#0-0) 

The state-mutation ordering is wrong: `internal_deposit` increases the bridge's nBTC balance and the total supply **before** the registration check is performed. When the check on line 114 fails (account not registered), the function returns immediately with zero, but the `amount` tokens already credited to `bridge_id` are never burned or reversed.

This is the direct analog of the SnapshotERC20Guild bug: a critical accounting operation (`_updateAccountSnapshot` / `internal_deposit`) is executed **before** the guard that determines whether the operation should proceed, leaving the contract in an inconsistent state when the guard triggers.

---

### Impact Explanation

- The user's BTC deposit is verified and the corresponding UTXO is consumed by the bridge.
- `amount` nBTC tokens are minted to `bridge_id` and remain there permanently.
- The user receives `U128(0)` — zero nBTC — with no recovery path inside `safe_mint`.
- The bridge's nBTC balance is inflated by `amount` without a corresponding user claim, breaking the 1:1 BTC-backing invariant. These orphaned tokens can later be used by the bridge for burns (withdrawals), effectively allowing the bridge to release BTC that was never properly redeemed.

**Impact class:** Critical — permanent loss of user funds and unauthorized inflation of the bridge's spendable nBTC balance.

---

### Likelihood Explanation

Any user who deposits BTC to the bridge without first calling `storage_deposit` on the nBTC contract to register their account will trigger this path. This is a realistic scenario for first-time users or users interacting via scripts/integrations that omit the registration step. The deposit flow is fully permissionless and requires no privileged access. [2](#0-1) 

---

### Recommendation

Move the registration check **before** `internal_deposit`, or burn/reverse the minted tokens when the early-return path is taken:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check FIRST, mint SECOND
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

Alternatively, if minting first is intentional, add `self.token.internal_withdraw(&self.bridge_id, amount.into())` before the early return so the total supply and bridge balance are restored.

---

### Proof of Concept

1. Alice deposits 0.01 BTC to her bridge-derived deposit address.
2. A relayer submits the Merkle inclusion proof; the bridge verifies it and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
3. `internal_deposit(&bridge_id, 1_000_000)` executes — bridge nBTC balance: `+1_000_000`, total supply: `+1_000_000`.
4. `self.token.accounts.get(&alice.near)` returns `None` (Alice never called `storage_deposit`).
5. `safe_mint` returns `U128(0)`. Alice receives 0 nBTC.
6. Alice's BTC UTXO is now in the bridge pool with no corresponding user claim. The bridge holds 1,000,000 nBTC that are not owed to any user, inflating its burnable balance. [3](#0-2)
