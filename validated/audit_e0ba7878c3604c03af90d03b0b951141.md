### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Victim's BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
When a user deposits BTC without embedding a `refund_address` in their `DepositMsg`, any unprivileged NEAR account can call `request_refund` for that deposit and supply an arbitrary attacker-controlled BTC address as the refund destination. The contract performs no authentication of the caller against the deposit's `recipient_id`, and the only protection is a longer `unsafe_refund_timelock_sec` window during which DAO/Operator must actively monitor and reject the malicious request. If they fail to do so, the victim's BTC is permanently redirected to the attacker.

### Finding Description

`request_refund` is a public, payable function with no caller-identity check: [1](#0-0) 

The only privileged check inside it is for the optional `gas_fee` parameter; the core refund submission path is open to any NEAR account. Inside `internal_request_refund`, the `refund_address` validation is conditional: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (which is a valid and common case — the field is `Option<String>` and `skip_serializing_if = "Option::is_none"`), the branch is skipped entirely and the caller-supplied `refund_address` is accepted without any ownership check: [3](#0-2) 

The refund address is then stored verbatim in the `RefundRequest` and later used as the Bitcoin output destination when `execute_refund` builds the PSBT: [4](#0-3) 

The system is aware of this risk and applies a longer `unsafe_refund_timelock_sec` when the deposit message has no pre-authorized address: [5](#0-4) 

However, this is a liveness-dependent mitigation, not a cryptographic one. If the DAO/Operator does not actively monitor and call `reject_refund` within the timelock window, the attacker can call `execute_refund` and the victim's BTC is sent to the attacker's address.

### Impact Explanation

A victim's BTC deposited to a bridge address derived from a `DepositMsg` with `refund_address: None` can be permanently stolen by any unprivileged attacker who submits a `request_refund` with their own BTC address before the legitimate user does. The victim's funds are redirected on-chain to the attacker's Bitcoin address with no on-chain recourse after `execute_refund` is signed by MPC and broadcast. This constitutes significant loss of user funds.

### Likelihood Explanation

All inputs needed to mount the attack are publicly observable: the `DepositMsg` is emitted in events (or reconstructable from the deposit address derivation), and the BTC transaction bytes are on the Bitcoin blockchain. The attacker only needs to pay the NEAR storage deposit for `request_refund` and wait out `unsafe_refund_timelock_sec`. The attack is viable whenever the DAO/Operator monitoring is delayed, offline, or overwhelmed by multiple simultaneous malicious requests.

### Recommendation

Require that the caller of `request_refund` is the `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. Only the NEAR account that originally designated itself as the nBTC recipient should be permitted to supply an arbitrary BTC refund address. When `deposit_msg.refund_address` is already set, the existing equality check is sufficient. Concretely, add inside `internal_request_refund`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may specify a refund address"
    );
}
```

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }` and sends BTC to the returned address.
2. The deposit is never finalized (relayer is offline, or Alice changed her mind).
3. Attacker Bob observes Alice's BTC transaction on-chain and reconstructs her `DepositMsg` (it is deterministically derived and emitted in events).
4. Bob calls `request_refund(deposit_msg=Alice's, refund_address="<Bob's BTC addr>", tx_bytes=Alice's tx, ...)` attaching the required NEAR storage deposit.
5. `internal_request_refund` passes: `deposit_msg.refund_address` is `None`, so the `require!` equality check is skipped; Bob's address is stored in the `RefundRequest`.
6. The contract applies `unsafe_refund_timelock_sec`. If DAO/Operator does not call `reject_refund` within this window, Bob calls `execute_refund`.
7. The bridge builds a PSBT paying Alice's BTC to Bob's address, MPC signs it, and Bob broadcasts it. Alice's BTC is permanently lost. [6](#0-5)

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
