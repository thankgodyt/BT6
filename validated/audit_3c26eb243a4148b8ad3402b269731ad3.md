Audit Report

## Title
Unchecked `send_tokens` Return Value in Fast-Transfer Finalization Causes Permanent Loss of Relayer Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `utxo_fin_transfer_fast` and `process_fin_transfer_to_other_chain`, the bridge irrevocably updates fast-transfer state (deleting or marking the record finalised) and then calls `send_tokens(...).detach()` with no callback. If the token transfer fails, the relayer's pre-funded tokens are permanently lost with no on-chain state remaining to enable recovery. The developers acknowledged this with a `// TODO: check how to deal with failed send_tokens` comment at the call site.

## Finding Description

**Path 1 — `utxo_fin_transfer_fast` (lines 2518–2561)**

The function first irrevocably mutates fast-transfer state:
- NEAR-destination: `self.remove_fast_transfer(&fast_transfer.id())` at line 2530 — record deleted from storage.
- Other-chain destination: `self.mark_fast_transfer_as_finalised(&fast_transfer.id())` at line 2533.

Then at lines 2542–2548 it calls:
```rust
self.send_tokens(
    fast_transfer.token_id.clone(),
    fast_transfer_status.relayer,
    amount,
    "",
)
.detach();
```
No callback is registered. The TODO comment at line 2484 explicitly flags this as unresolved.

**Path 2 — `process_fin_transfer_to_other_chain` (lines 2027–2040)**

At lines 2029–2039, `send_tokens(...).detach()` is called to reimburse the relayer, followed immediately by `self.mark_fast_transfer_as_finalised(&fast_transfer.id())` at line 2040. If `send_tokens` fails, the fast-transfer record is still marked finalised and the reimbursement is silently dropped.

**Contrast with the safe pattern used elsewhere**

Every other `send_tokens` call chains a `.then(callback)` that checks the result and reverts state on failure:
- Lines 877–892: `fast_fin_transfer_to_near_callback` → `.then(resolve_fast_transfer(...))`
- Lines 994–1011: `utxo_fin_transfer_to_near_callback` → `.then(resolve_utxo_fin_transfer(...))`
- Lines 1957–1977: `process_fin_transfer_to_near` → `.then(fin_transfer_send_tokens_callback(...))`

The two detached paths skip this entire safety net.

**Root cause in `send_tokens`**

`send_tokens` (lines 2056–2090) dispatches `ft_transfer` or `ft_transfer_call` on the token contract. Both can panic — most commonly when the recipient account has no storage deposit registered with the token contract. A panicking cross-contract call in a detached promise is silently discarded by the NEAR runtime; the calling contract receives no notification.

## Impact Explanation
A relayer who pre-funded a fast transfer permanently loses their bridged tokens if the reimbursement `send_tokens` call fails. The fast-transfer record is already deleted or finalised before the call, so there is no retry path and no on-chain state left to trigger recovery. This is a direct, permanent loss of bridged funds held by a legitimate bridge participant, matching the critical impact class: *permanent loss of bridged funds across NEAR flows*.

## Likelihood Explanation
The failure condition is realistic and requires no attacker: `ft_transfer` panics if the relayer account has not registered storage for the token contract. A relayer operating across many tokens may not have pre-registered storage for every token. Gas exhaustion in the detached promise is an additional independent failure mode. The bug is triggered by normal bridge operation — no adversarial action is required.

## Recommendation
Replace `.detach()` in both paths with a `.then(callback)` that inspects the promise result. On failure, the callback should re-insert the fast-transfer record (or credit the relayer's internal balance) so the reimbursement can be retried. This mirrors the pattern already used in `resolve_fast_transfer` (lines 896–912) and `fin_transfer_send_tokens_callback`. The existing `is_refund_required` helper and `revert_lock_actions` infrastructure can be reused for the recovery logic.

## Proof of Concept
1. Relayer executes a fast transfer for a BTC→NEAR transfer, pre-funding the recipient with bridged tokens.
2. UTXO connector calls `verify_deposit` → `ft_transfer_call` → `ft_on_transfer` → `utxo_fin_transfer` on the bridge.
3. A matching fast-transfer status is found; `utxo_fin_transfer_fast` is entered (line 2485).
4. `remove_fast_transfer` is called at line 2530 — the fast-transfer record is deleted from storage.
5. `send_tokens(fast_transfer.token_id.clone(), fast_transfer_status.relayer, amount, "").detach()` is called at lines 2542–2548.
6. The relayer's account has no storage registered for the token contract → `ft_transfer` panics inside the detached promise.
7. The bridge's `ft_on_transfer` returns `U128(0)` (success from the bridge's perspective), the UTXO transfer is marked complete, and the relayer's pre-funded tokens are permanently lost with no on-chain record remaining.

**Test plan**: Deploy a local NEAR testnet with the bridge contract and a standard NEP-141 token. Register storage for the recipient user but *not* for the relayer account. Execute a fast transfer as the relayer, then trigger UTXO finalization. Observe that `ft_on_transfer` returns 0 (success), the fast-transfer record is gone, and the relayer's token balance is unchanged — confirming permanent loss.
