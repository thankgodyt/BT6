### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole `BlockSupportsPeras` instance in the repository implements `validatePerasCert` as an unconditional stub that always returns `Right` (valid) without performing any cryptographic or structural check. Any unprivileged peer can send a crafted `PerasCert` message that is silently accepted, stored in the certificate pool, and applied as a chain-selection weight boost — potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` defines the interface for validating inbound Peras certificates and votes. The only instance in the codebase is a universal stub applied to every block type:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The function unconditionally returns `Right`, assigning the full `perasWeight params` boost to every certificate regardless of its content, origin, or cryptographic validity.

The live inbound handler `processCerts` calls this validator for every batch of certificates received from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` never produces a `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted and stored.

The stored certificates are then consumed by `getPerasWeightSnapshot`, which feeds `compareCandidateChains` in the BlockFetch client interface:

```haskell
readChainComparison :: STM m (WithFingerprint (ChainComparison (HeaderWithTime blk)))
readChainComparison =
  fmap mkChainComparison <$> getPerasWeightSnapshot chainDB
``` [3](#0-2) 

The same pattern applies to `validatePerasVote`, which checks only stake-distribution membership and performs no signature verification. The `PerasVote` type itself carries no signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [4](#0-3) 

Forged votes that pass the stake-distribution lookup can accumulate to quorum and trigger certificate forging entirely from peer-supplied data.

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block — including the tip of a weaker or shorter fork. Because `validatePerasCert` always succeeds, the certificate is stored with `vpcCertBoost = perasWeight params`. On the next chain-selection cycle, this boost is applied to the targeted fork's selection weight, potentially causing the node to rank a non-canonical chain above the honest canonical chain and switch to it. This is a chain-selection safety violation: an honest node is made to prefer a less-secure chain solely due to peer-supplied, unvalidated data — directly analogous to the external report's pattern of storing unvalidated external input that later corrupts authoritative state.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is wired into the node's network stack via `makePerasCertPoolWriterFromChainDB`, and `processCerts` is the live inbound handler. No special privileges, stake, or cryptographic keys are required — any connected peer can send a certificate message. The stub is the **only** `BlockSupportsPeras` instance in the repository; no more-specific override for `CardanoBlock` exists. The TODO comments confirm the validation logic is intentionally absent pending future work.

---

### Recommendation

**Short term:** Gate the Peras certificate diffusion mini-protocol behind a feature flag that is disabled by default until `validatePerasCert` and `validatePerasVote` implement real cryptographic checks (committee membership proof, BLS/VRF signature verification, round-number bounds). Add a runtime assertion or compile-time guard that prevents the protocol from being started with the stub instance.

**Long term:** Implement full certificate and vote validation per the Peras specification (CIP-0140), including committee selection verification, signature checks, and round-number consistency with the current ledger view. Document all privileged and unprivileged entry points into the Peras state machine to prevent analogous gaps in future protocol additions.

---

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the Peras certificate object-diffusion mini-protocol.
2. Construct a `PerasCert` with `pcCertBoostedBlock` set to the tip of a weaker fork (e.g., a chain that is one block shorter than the canonical tip).
3. Send the certificate in a batch to the target node.
4. `processCerts` calls `validatePerasCert cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB` with the full Peras boost weight.
6. On the next chain-selection cycle, `getPerasWeightSnapshot` includes the boost; `compareCandidateChains` ranks the weaker fork above the canonical chain.
7. The node switches to the weaker fork, diverging from the honest majority. [5](#0-4) [6](#0-5) [3](#0-2)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
