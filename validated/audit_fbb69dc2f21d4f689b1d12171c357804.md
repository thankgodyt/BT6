### Title
Pending-transaction UTXOs excluded from management-policy UTXO count, enabling passive-management bypass and active-management stuck state - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary
Both `check_withdraw_psbt_valid` and `check_active_management_psbt_valid` compute `utxo_num` as `self.data().utxos.len() + vutxos_len` — the available pool plus the current transaction's inputs. UTXOs already removed from the pool for other in-flight pending transactions (`btc_pending_infos`) are never counted. This mirrors the external report's class: committed funds are excluded from a policy-enforcement calculation, causing the enforced limit to diverge from the true protocol state.

### Finding Description

When a withdrawal or active-management operation is initiated, `generate_vutxos` immediately removes the selected UTXOs from `self.data().utxos` and stores them inside the resulting `BTCPendingInfo.vutxos`. [1](#0-0) 

Those UTXOs remain absent from the pool until the on-chain transaction is confirmed and change outputs are re-inserted. During that window every subsequent management-policy check reads a pool that is smaller than the true protocol UTXO count.

Both policy-enforcement functions reconstruct a pre-transaction count by adding back only the *current* transaction's inputs:

```rust
// psbt.rs – identical pattern in both functions
let utxo_num = self.data().utxos.len() + vutxos_len;
``` [2](#0-1) [3](#0-2) 

UTXOs locked in *other* pending transactions are never added back, so `utxo_num` systematically underestimates the true protocol UTXO count whenever concurrent pending transactions exist.

**Passive-management bypass (user-reachable):** [4](#0-3) 

If the true UTXO count exceeds `passive_management_upper_limit` but the stale `utxo_num` falls below it (because many UTXOs are locked in pending transactions), the consolidation requirement (`input_num > change_num`) is silently skipped. Any bridge user who holds nBTC can trigger this by initiating multiple withdrawals before submitting the one they want to bypass.

**Active-management stuck state (operator-reachable):** [5](#0-4) 

If the true UTXO count is above `active_management_upper_limit` (requiring consolidation) but `utxo_num` falls inside the normal band, the function panics with "Active management conditions are not met", blocking the operator from consolidating UTXOs until all pending transactions confirm.

The config comments confirm the design intent is the *total* protocol UTXO count: [6](#0-5) 

### Impact Explanation

**Passive-management bypass** — an unprivileged bridge user can submit a withdrawal that violates the configured UTXO-count policy (e.g., avoiding mandatory consolidation when the pool is over-populated). Over time this degrades UTXO health, increases future gas costs, and can push the pool into a state where subsequent withdrawals are forced to pay higher fees or fail gas-fee range checks. This is a bypass of bridge limits/policies.

**Active-management stuck state** — when many withdrawals are in-flight, the operator's `active_utxo_management` call panics even though the true UTXO count warrants consolidation. The bridge remains in a degraded UTXO state until all pending transactions confirm, requiring operator intervention.

### Likelihood Explanation

Normal bridge operation involves multiple concurrent withdrawals. Any period of moderate activity (several users withdrawing simultaneously) is sufficient to create the discrepancy. No special privileges are required for the passive-management bypass path; the user only needs nBTC tokens and the ability to call `ft_transfer_call`.

### Recommendation

Replace the stale `utxo_num` calculation with one that includes UTXOs committed in all pending transactions:

```rust
// Sum vutxos across all btc_pending_infos entries
let pending_utxo_count: u32 = self.data()
    .btc_pending_infos
    .values()
    .map(|v| BTCPendingInfo::from(v).vutxos.len() as u32)
    .sum();

let utxo_num = self.data().utxos.len()
    + vutxos_len          // current tx inputs (already removed from pool)
    + pending_utxo_count; // inputs locked in other pending txs
```

Apply this fix in both `check_withdraw_psbt_valid` and `check_active_management_psbt_valid`.

### Proof of Concept

1. Configure `passive_management_upper_limit = 3`.
2. Deposit 4 UTXOs into the bridge pool (`self.data().utxos.len() = 4`).
3. User A initiates a withdrawal consuming 2 UTXOs → pool drops to 2, those 2 UTXOs move into `btc_pending_infos`.
4. User B initiates a withdrawal consuming 1 UTXO:
   - `self.data().utxos.len() = 2`, `vutxos_len = 1`
   - `utxo_num = 2 + 1 = 3` — at the limit, consolidation check skipped
   - True protocol UTXO count = 2 (pool) + 2 (pending A) + 1 (current) = 5 > 3
   - The consolidation requirement (`input_num > change_num`) is never enforced.
5. User B's withdrawal completes without consolidating, leaving the bridge with fragmented UTXOs beyond the configured limit. [7](#0-6) [8](#0-7)

    pub fn remove_vutxo_by_psbt(&mut self, psbt: &PsbtWrapper) -> (Vec<String>, Vec<VUTXO>) {
        let mut utxo_storage_keys = vec![];
        let vutxos = psbt
            .get_utxo_storage_keys()
            .into_iter()
            .map(|utxo_storage_key| {
                utxo_storage_keys.push(utxo_storage_key.clone());
                self.data_mut()
                    .utxos
                    .remove(&utxo_storage_key)
                    .unwrap_or_else(|| {
                        env::panic_str(&format!("UTXO {} not exist", utxo_storage_key))
                    })
            })
            .collect::<Vec<_>>();
        (utxo_storage_keys, vutxos)
    }

    pub fn check_withdraw_psbt_valid(
        &self,
        target_btc_address: String,
        withdraw_change_address_script_pubkey: &ScriptBuf,
        withdraw_psbt: &PsbtWrapper,
        vutxos: &[VUTXO],
        amount: u128,
        withdraw_fee: u128,
        max_gas_fee: Option<U128>,
    ) -> (u128, u128) {
        let config = self.internal_config();
        let vutxos_len = u32::try_from(vutxos.len()).unwrap_or_else(|_| {
            env::panic_str("vutxos len overflow");
        });
        let utxo_num = self.data().utxos.len() + vutxos_len;
        let (input_num, change_num, actual_received_amount, gas_fee) = self.check_withdraw_psbt(
            withdraw_psbt,
            target_btc_address,
            withdraw_change_address_script_pubkey,
            vutxos,
            amount,
            withdraw_fee,
        );

        if let Some(max_gas_fee) = max_gas_fee {
            require!(
                gas_fee <= max_gas_fee.0,
                format!(
                    "Gas fee does not match the provided max fee (gas fee = {}; max gas fee = {})",
                    gas_fee, max_gas_fee.0
                )
            );
        }

        require!(
            change_num <= usize::from(config.max_change_number),
            format!("change_num must not exceed {}", config.max_change_number)
        );
        require!(
            input_num <= usize::from(config.max_withdrawal_input_number),
            format!(
                "input must not exceed {}",
                config.max_withdrawal_input_number
            )
        );

        if utxo_num < config.passive_management_lower_limit {
            require!(input_num < change_num, "require input_num < change_num");
        } else if utxo_num > config.passive_management_upper_limit {
            require!(input_num > change_num, "require input_num > change_num");
        }

        Event::WithdrawBtcDetail {
            cost_nbtc: amount.into(),
            withdraw_fee: withdraw_fee.into(),
            btc_gas_fee: gas_fee.into(),
            actual_received_amount: actual_received_amount.into(),
        }
        .emit();
        (actual_received_amount, gas_fee)
    }
