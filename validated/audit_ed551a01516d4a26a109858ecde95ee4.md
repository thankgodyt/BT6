### Title
Permissionless `request_refund` Allows Front-Running to Permanently Block Victim's Refund and Redirect BTC - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund` is a permissionless, public function that stores a refund request keyed by the deterministic `utxo_storage_key` (`{tx_id}@{vout}`). An attacker monitoring the NEAR transaction pool can front-run a victim's `request_refund` call, registering a malicious refund request with the attacker's own `refund_address` at the same key. The victim's subsequent callback then fails with "Refund request already exists for this UTXO," permanently blocking the victim's refund. After the `unsafe_refund_timelock_sec` window, the attacker can call `execute_refund` to redirect the victim's BTC to the attacker's address if the DAO fails to reject the malicious request in time.

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no caller-identity restriction beyond the `gas_fee` parameter check: [1](#0-0) 

The function is `#[payable]` and `#[pause(except(roles(Role::DAO)))]` — when the bridge is unpaused, any NEAR account can call it. The individual function does **not** carry a `#[trusted_relayer]` attribute, unlike `verify_deposit_v2` or `verify_withdraw_v2`, so it is not restricted to whitelisted relayers.

The storage key is computed deterministically in `request_refund_callback`: [2](#0-1) 

The key is `{tx_id}@{vout}`, fully predictable from the public Bitcoin transaction. The callback then enforces uniqueness: [3](#0-2) 

Critically, the `deposit_msg` is passed as a plain parameter and is visible in the NEAR transaction pool before inclusion. The `refund_address` parameter is only constrained when `deposit_msg.refund_address` is `Some(...)`: [4](#0-3) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the attacker can supply any `refund_address` of their choosing. The callback verifies only that the output script matches the deposit address derived from `deposit_msg`, not that the caller is the intended recipient: [5](#0-4) 

The attacker's malicious refund request is then stored with the attacker's `refund_address`: [6](#0-5) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also permissionless: [7](#0-6) 

`finalize_refund_with_psbt` builds and submits a PSBT spending the victim's deposit UTXO to the `refund_address` stored in the request — the attacker's address: [8](#0-7) 

The only defense is `reject_refund`, callable only by DAO/Operator: [9](#0-8) 

The victim cannot self-reject the attacker's malicious request. If the attacker keeps front-running every re-submission, the victim's BTC is permanently locked in the MPC-controlled deposit address with no recovery path.

### Impact Explanation

**Medium (DoS / permanent locking):** An attacker can unconditionally block any victim's `request_refund` by front-running it. The victim's BTC is locked in the MPC-controlled deposit address with no self-service recovery. The attacker can repeat the front-run on every re-submission, making the lock permanent without DAO intervention.

**Critical (conditional theft):** If the DAO/Operator fails to call `reject_refund` within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the MPC signs a transaction sending the victim's BTC to the attacker's address — a complete theft of user funds with no on-chain recourse.

### Likelihood Explanation

NEAR transactions are visible in the transaction pool before block inclusion. The attack requires only: (1) monitoring the pool for `request_refund` calls, (2) copying the `deposit_msg` and `tx_bytes`/`vout`/`proof` parameters, (3) substituting the attacker's `refund_address`, and (4) submitting with sufficient gas priority. No special privilege, key, or capital beyond the storage deposit is required. The storage deposit is returned on rejection, so the attacker's cost is minimal. The attack is repeatable on every victim re-submission.

### Recommendation

Bind the `refund_address` to the caller's identity when `deposit_msg.refund_address` is `None`. Specifically, require that `env::predecessor_account_id()` equals `deposit_msg.recipient_id` when no pre-authorized `refund_address` is embedded in the deposit message. This ensures only the intended recipient can register an arbitrary refund address, eliminating the front-running surface while preserving the DAO/Operator fast-track path for pre-authorized addresses.

Alternatively, store `env::predecessor_account_id()` in the `RefundRequest` and restrict `execute_refund` so that only the original requester (or DAO/Operator) can execute it.

### Proof of Concept

1. Victim Alice has a BTC deposit at `tx_id=abc123`, `vout=0` that was never finalized via `verify_deposit`. She submits:
   ```
   request_refund(deposit_msg={recipient_id:"alice.near", refund_address:None, ...},
                  refund_address="bc1q_alice_btc_address",
                  tx_bytes=<alice_tx>, vout=0, proof=<valid_proof>, gas_fee=None)
   ```

2. Attacker Bob sees this in the NEAR transaction pool. He copies all parameters but substitutes his own BTC address:
   ```
   request_refund(deposit_msg={recipient_id:"alice.near", refund_address:None, ...},
                  refund_address="bc1q_bob_btc_address",
                  tx_bytes=<alice_tx>, vout=0, proof=<valid_proof>, gas_fee=None)
   ```
   Bob submits with higher gas priority.

3. Bob's `request_refund_callback` executes first. The light-client proof is valid, the output script matches Alice's deposit address, and no duplicate exists yet. Bob's request is stored at key `abc123@0` with `refund_address = "bc1q_bob_btc_address"`.

4. Alice's `request_refund_callback` executes and panics: `"Refund request already exists for this UTXO"`. Alice's refund is blocked.

5. After `unsafe_refund_timelock_sec` passes (and if DAO does not call `reject_refund`), Bob calls `execute_refund("abc123@0", None)`. The bridge builds a PSBT spending Alice's deposit UTXO and sends it to the MPC for signing. The signed transaction pays Alice's BTC to Bob's address.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
