### Title
Arbitrary `key_version` in `sign_btc_transaction` Allows Any Caller to Corrupt MPC Signing and Permanently Lock Withdrawal Funds - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary

`sign_btc_transaction` accepts a caller-supplied `key_version: u32` that is passed directly to the NEAR Chain Signatures MPC without any validation against a stored or expected value. The function also has no ownership check — any unprivileged NEAR account can invoke it for any pending withdrawal. If an attacker calls it with a wrong `key_version` that the MPC accepts (e.g., during a key rotation), the resulting signature is stored in the signing slot, the slot is permanently marked "Already signed," and the PSBT is assembled with a signature that does not correspond to the deposit address's public key. The resulting Bitcoin transaction is cryptographically invalid and will never confirm on-chain, permanently locking the user's nBTC in the bridge contract until privileged operator intervention.

### Finding Description

`sign_btc_transaction` is a public, unpermissioned function: [1](#0-0) 

It accepts `key_version: u32` as a free parameter and passes it verbatim to the MPC: [2](#0-1) 

The `key_version` is never validated against any stored or expected value in `BTCPendingInfo`. The callback that stores the result derives the expected `public_key` from the UTXO path — not from `key_version` — but stores the MPC-returned signature unconditionally without verifying that the signature is valid for that public key: [3](#0-2) 

Once stored, the slot is permanently locked: [4](#0-3) 

There is no caller ownership check anywhere in `sign_btc_transaction` — `env::predecessor_account_id()` is never compared to `btc_pending_info.account_id`. Any NEAR account can call this for any pending transaction whose ID is observable from on-chain events (`GenerateBtcPendingInfo`): [5](#0-4) 

### Impact Explanation

When an attacker supplies a wrong `key_version` that the MPC accepts (e.g., `key_version = 1` during a key rotation while the deposit address was derived from `key_version = 0`):

1. The MPC signs the payload with the wrong key.
2. The callback stores the mismatched signature and marks the slot "Already signed."
3. The PSBT is assembled with a signature that does not satisfy the deposit address's script.
4. The Bitcoin transaction is cryptographically invalid; Bitcoin nodes reject it.
5. `verify_withdraw` can never succeed because the transaction will never confirm.
6. The user's nBTC (already transferred to the bridge via `ft_on_transfer`) is locked in the contract.
7. Recovery requires a privileged `cancel_withdraw` call from `Role::DAO` or `Role::Operator`: [6](#0-5) 

Without operator intervention the funds are permanently locked. **Impact: Medium (attacker-triggered locking of bridged funds requiring operator intervention), escalating to Critical if the operator does not act.**

### Likelihood Explanation

- `sign_btc_transaction` is callable by any NEAR account with no role restriction beyond the global pause flag.
- The `btc_pending_sign_id` is emitted publicly as a `GenerateBtcPendingInfo` event, so any observer can obtain it.
- The attack is cheap: one NEAR transaction with an attached deposit (for `#[payable]`).
- The window is open from the moment a withdrawal is initiated until the legitimate relayer signs — typically several seconds to minutes.
- The condition "MPC accepts the wrong key_version" is realistic during any key rotation, which is a planned operational event.

### Recommendation

1. **Validate `key_version` on-chain.** Store the expected `key_version` in `Config` or `BTCPendingInfo` and assert equality before forwarding to the MPC.
2. **Restrict callers.** Add an ownership check (`require!(env::predecessor_account_id() == btc_pending_info.account_id || is_trusted_relayer, ...)`), or apply `#[trusted_relayer]` to `sign_btc_transaction`.
3. **Verify the signature in the callback.** After receiving the MPC response, verify the ECDSA signature against the expected `public_key` before storing it, so a mismatched signature is rejected rather than persisted.

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call`. A `BTCPendingInfo` is created with `btc_pending_sign_id = "abc123"` and emits `GenerateBtcPendingInfo`.
2. Attacker observes the event and immediately calls:
   ```
   sign_btc_transaction("abc123", 0, 999)
   ```
   with `key_version = 999` (a future/rotated version the MPC accepts).
3. MPC signs the payload with key version 999 (a different key than the deposit address).
4. `sign_btc_transaction_callback` stores the signature at `signatures[0]` and marks it "Already signed."
5. Legitimate relayer calls `sign_btc_transaction("abc123", 0, 0)` — reverts with "Already signed."
6. If this was the only input, `is_all_signed()` returns `true`, the PSBT is finalized with the wrong signature, and the state transitions to `PendingVerify`.
7. The assembled Bitcoin transaction is invalid; it never confirms on-chain.
8. Alice's nBTC is locked in the bridge contract. Recovery requires `cancel_withdraw` from `Role::DAO`/`Role::Operator`. [7](#0-6) [8](#0-7)

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }
