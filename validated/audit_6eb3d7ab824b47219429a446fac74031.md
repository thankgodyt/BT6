### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Both production pool-writer paths (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) wire this stub directly into the inbound certificate processing pipeline. Any unprivileged peer can therefore inject a crafted `PerasCert` that boosts an arbitrary block, causing the receiving node to trigger chain selection in favour of that block and potentially prefer a non-canonical chain.

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No quorum check, no signature verification, no round-number bounds check, and no boosted-block validity check are performed. Every certificate is unconditionally promoted to `ValidatedPerasCert` and assigned the full `perasWeight`.

**Production wiring — both pool writers use this stub:** [2](#0-1) 

`makePerasCertPoolWriterFromCertDB` (line 103) and `makePerasCertPoolWriterFromChainDB` (line 126) both pass `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`. The `TODO` comment on both call sites acknowledges the placeholder is not yet replaced.

**`processCerts` feeds accepted certificates directly into the DB and chain selection:** [3](#0-2) 

After the stub returns `Right` for every certificate, `processCerts` timestamps each one and calls `addCert`, which stores it in `PerasCertDB`.

**Chain selection is then triggered for the boosted block:** [4](#0-3) 

`chainSelSync` calls `chainSelectionForBlock` for the block named in the accepted certificate, causing the node to re-evaluate its preferred chain with the injected boost weight applied.

**Exploit path:**
1. Attacker connects to a victim node as a normal peer via the Peras certificate diffusion mini-protocol.
2. Attacker crafts a `PerasCert` whose `pcCertBoostedBlock` points to any block the attacker wants to elevate (e.g., a block on a minority fork).
3. The certificate is sent to the victim node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
5. The certificate is stored in `PerasCertDB` and `chainSelSync` triggers `chainSelectionForBlock` for the boosted block.
6. The victim node now evaluates that block's chain with an extra `perasWeight = 15` boost, potentially switching away from the canonical chain.

### Impact Explanation

An unprivileged peer can make an honest node accept an arbitrary Peras certificate without any quorum, signature, or structural check. Because accepted certificates directly influence chain selection by adding `perasWeight` to the boosted block's chain, the attacker can steer the victim node toward a non-canonical or adversarially-controlled chain. This matches the **High** impact category: a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

The vulnerability is reachable by any peer that can connect to the node's Peras certificate diffusion endpoint — no keys, stake, or special privileges are required. The code is in the active production path (not gated by a feature flag or test-only build). The `TODO` comments confirm the stub is intentionally temporary but is currently live.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that enforces:
- Quorum: the certificate must be backed by a sufficient threshold of stake-weighted votes (`perasQuorumStakeThreshold`).
- Cryptographic signatures: each contributing vote must carry a valid signature from a registered committee member.
- Round-number bounds: the certificate's round must be within the accepted window relative to the current chain tip.
- Boosted-block validity: the referenced block must exist on a plausible chain extension, not an arbitrary point.

Until the real implementation is ready, the stub should at minimum reject all inbound certificates from peers (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the diffusion layer cannot be used to inject chain-selection weight.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
