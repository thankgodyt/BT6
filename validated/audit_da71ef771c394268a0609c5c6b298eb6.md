### Title
Peras Certificate Verification Bypass Allows Unprivileged Peer to Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation unconditionally accepts every inbound `PerasCert` without performing any cryptographic or structural verification. An unprivileged peer can send a crafted certificate that boosts any block of its choosing, causing the receiving node to artificially inflate that block's Peras weight and potentially switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`**

In `SupportsPeras.hs`, the `BlockSupportsPeras` instance for `StandardHash blk` implements `validatePerasCert` as a stub that unconditionally succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, quorum, committee membership, round validity, or boosted-block range check is performed. Every `PerasCert` value, regardless of content, is wrapped in `ValidatedPerasCert` and returned as valid.

**Attacker-controlled entry path — `processCerts` in the object diffusion layer**

`processCerts` in `PerasCert.hs` is the inbound handler for Peras certificates received from peers over the network. It calls `validatePerasCert mkPerasParams` directly:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, the `partitionEithers` branch in `processCerts` always takes the "all certs are valid" path:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Chain selection impact**

Every accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, which calls `chainSelSync` → `PerasCertDB.addCert`. The `PerasCertDB` then updates its `PerasWeightSnapshot`:

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot ...
``` [4](#0-3) 

Chain selection in `preferAnchoredCandidate` reads this snapshot and computes `wsvWeightBoost` for each fragment:

```haskell
wsvWeightBoost = weightBoostOfFragment weights frag
``` [5](#0-4) 

A fragment whose boosted block has been artificially inflated will be preferred over the honest canonical chain if its `wsvTotalWeight` exceeds the current selection's total weight.

**Analog to the external report**

The external report describes `_containsSetGuardianPayload()` checking ALL actions in a proposal and blocking guardian cancellation whenever `setGuardian` appears anywhere — a check that is too broad and prevents a legitimate protective action. The analog here is the inverse structural failure: `validatePerasCert` performs no check at all, so the protective gate (certificate verification) is entirely absent. In both cases, a single overly-permissive or overly-broad condition in a collection-processing function allows an attacker to bypass the intended authorization boundary.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on any fork and `pcCertRound` set to any round number. The receiving node will:

1. Accept the certificate without any cryptographic check.
2. Store it in `PerasCertDB`, permanently inflating the Peras weight of the attacker-chosen block by `perasWeight params`.
3. Trigger chain selection for the boosted block, potentially switching to a non-canonical fork.

This is a **Critical** bypass of Peras certificate/signature validation that enables unauthorized certificate acceptance and chain-selection manipulation, matching the allowed impact: *"Bypass of… certificate/signature validation… that enables unauthorized… certificate acceptance"* and *"Chain selection… bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The object diffusion mini-protocol is publicly reachable by any connected peer. No stake, keys, or special privileges are required. The only precondition is that the target node has Peras enabled. The exploit requires sending a single well-formed `PerasCert` CBOR message.

---

### Recommendation

Implement real cryptographic and structural verification inside `validatePerasCert` before enabling Peras in production. At minimum, the implementation must:

1. Verify the aggregate BLS signature over the certificate against the claimed committee members' public keys.
2. Confirm that the signers constitute a valid quorum (total stake ≥ `perasQuorumStakeThreshold`).
3. Validate that `pcCertRound` and `pcCertBoostedBlock` are within the protocol-permitted range relative to the current chain tip.
4. Reject certificates whose `pcCertBoostedBlock` is older than the immutable tip (this check exists in `chainSelSync` but not at the validation layer).

The `TODO` at issue `tweag/cardano-peras#120` tracks this work and must be resolved before the Peras feature flag is enabled on any production network.

### Proof of Concept

```
Attacker peer  →  [PerasCert { pcCertRound = R, pcCertBoostedBlock = <fork tip> }]
                                    ↓
                         processCerts (PerasCert.hs:164)
                                    ↓
                  validatePerasCert mkPerasParams cert
                  → Right ValidatedPerasCert { vpcCertBoost = perasWeight params }
                                    ↓
                  ChainDB.addPerasCertAsync  →  chainSelSync
                                    ↓
                  PerasCertDB.addCert  →  PerasWeightSnapshot updated
                                    ↓
                  preferAnchoredCandidate: wsvTotalWeight(fork) > wsvTotalWeight(honest)
                                    ↓
                  Node switches to attacker-chosen non-canonical fork
```

The attacker needs no stake, no keys, and no prior relationship with the target node — only a TCP connection and the ability to send a valid CBOR-encoded `PerasCert` message.
