Audit Report

## Title
Missing Pre-Lock Normalization Guard Causes Permanent Token Freeze — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` locks or burns user tokens before any check that the destination-chain normalized amount is non-zero. The only guard against a zero normalized amount lives in `sign_transfer`, which executes after the lock/burn. When that guard fires, the tokens are already irrecoverably consumed and no public cancel or refund path exists, permanently freezing the user's funds.

## Finding Description
`normalize_amount` applies integer floor division to convert a NEAR-side amount to destination-chain precision:

```rust
// near/omni-bridge/src/lib.rs L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any token whose NEAR-side `origin_decimals` exceeds its destination-chain `decimals` (e.g. 24 vs 6, divisor = `10^18`), any transfer amount below the divisor normalizes to zero.

`init_transfer` validates only `fee < amount` before proceeding: [1](#0-0) 

`init_transfer_internal` then immediately locks or burns the full amount with no normalization check: [2](#0-1) 

`burn_tokens_if_needed` fires as a detached promise (fire-and-forget), making the burn irreversible: [3](#0-2) 

The zero-amount guard appears only in `sign_transfer`, after the lock/burn has already occurred: [4](#0-3) 

When `sign_transfer` panics with `InvalidAmountToTransfer`, the transfer message remains in `pending_transfers` indefinitely. `remove_transfer_message` is internal-only and performs no unlock or un-burn: [5](#0-4) 

No public cancel or user-facing refund function exists. The only privileged escape valve is `set_locked_tokens` (DAO/TokenLockController), which adjusts accounting only and does not return tokens to users. The code's own comment acknowledges the dust-stays-locked behavior but does not guard against the entire amount normalizing to zero: [6](#0-5) 

## Impact Explanation
Any user who initiates a NEAR→EVM (or NEAR→other-chain) transfer with `amount - fee < 10^(origin_decimals − decimals)` permanently loses their tokens. For a token with 24 NEAR decimals and 6 EVM decimals the threshold is one full token unit (`10^18` base units). For deployed (bridged) tokens the burn is irreversible; for native tokens the locked-token accounting is permanently inflated with no user-facing unlock path. This constitutes **permanent freezing of bridged funds**, matching the critical allowed-impact scope.

## Likelihood Explanation
The `ft_transfer_call` entry point is fully public and requires no special role. The decimal gap is a fixed, on-chain-visible protocol parameter. The scenario arises organically from users sending small or "dust" cleanup amounts, and can also be triggered deliberately by any actor who reads the registered `token_decimals`. No privileged access, oracle manipulation, or external collusion is required.

## Recommendation
Add the normalization check **before** locking or burning tokens, either at the top of `init_transfer_internal` or inside `init_transfer` after the fee check, mirroring the existing guard in `sign_transfer`:

```rust
// Proposed addition at the start of init_transfer_internal, before burn/lock
if let OmniAddress::Near(ref token_id) = transfer_message.token {
    if let Some(token_address) = self.get_token_address(
        transfer_message.get_destination_chain(),
        token_id.clone(),
    ) {
        if let Some(decimals) = self.token_decimals.get(&token_address) {
            let normalized = Self::normalize_amount(
                transfer_message
                    .amount_without_fee()
                    .near_expect(BridgeError::InvalidFee),
                decimals,
            );
            require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
        }
    }
}
```

This fires before any state mutation and returns the tokens to the caller via the NEP-141 refund mechanism (returning `transfer_message.amount` from `init_transfer_internal`).

## Proof of Concept
1. Register a token with `origin_decimals = 24` (NEAR side) and `decimals = 6` (EVM side), giving a divisor of `10^18`.
2. Call `ft_transfer_call` on the NEP-141 token contract with `amount = 999_999_999_999_999_999` (just below `10^18`) and a valid EVM recipient. `init_transfer` accepts the call (`fee=0 < amount`), `init_transfer_internal` burns/locks the tokens, and emits `InitTransferEvent`.
3. A trusted relayer calls `sign_transfer` for the resulting transfer ID. `normalize_amount(999_999_999_999_999_999, {origin:24, dest:6}) = 0`; the call panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
4. The transfer message remains in `pending_transfers`; the tokens are burned/locked with no recovery path. The user has permanently lost their funds.
5. Reproducible as a unit test by directly calling `init_transfer_internal` with a crafted `TransferMessage` whose amount is below the divisor, then asserting that `locked_tokens` increased while `normalize_amount` returns zero, and confirming no public function can reverse the lock.
