Audit Report

## Title
Missing Token Registration Validation in `init_transfer` Allows Permanent Locking of User Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`ft_on_transfer` accepts any NEP-141 token and dispatches to `init_transfer` using `env::predecessor_account_id()` as the token identifier, with no check that the token is registered in `token_id_to_address`. The bridge retains all transferred tokens (returning `U128(0)` to the token contract), stores the transfer in `pending_transfers`, and then permanently blocks progress: `sign_transfer` panics with `FailedToGetTokenAddress` for any unregistered token, and no user-accessible cancellation path exists.

## Finding Description
`ft_on_transfer` (L253–263) passes `env::predecessor_account_id()` directly as `token_id` to `init_transfer` (L523–619). Inside `init_transfer`, the only guards are:
- Recipient chain must not be NEAR (L531–534)
- Fee must be strictly less than amount (L554–557)

No check is made against `token_id_to_address`. Execution proceeds to `init_transfer_internal` (L1829–1865), which calls `add_transfer_message` to insert the record into `pending_transfers` (L1834–1836). If the signer has sufficient storage balance, the function calls `burn_tokens_if_needed` (a no-op for non-deployed tokens) and `lock_tokens_if_needed`, then returns `U128(0)`, causing the NEP-141 token contract to keep the full transfer amount inside the bridge.

When a trusted relayer later calls `sign_transfer` (L447–521), the bridge attempts to resolve the foreign-chain address via `get_token_address` (L1360–1366), which performs `self.token_id_to_address.get(&(chain_kind, token))`. For an unregistered token this returns `None`, triggering `env::panic_str(BridgeError::FailedToGetTokenAddress…)` (L467–469). The transfer record remains in `pending_transfers` indefinitely. No public cancel or refund function is present in the contract.

## Impact Explanation
A user who calls `ft_transfer_call` on any unregistered NEP-141 token pointing at the bridge will have their tokens permanently locked inside the bridge contract. The transfer can never be signed, finalized, or refunded. This directly matches the critical allowed impact: *permanent freezing of bridged funds*.

## Likelihood Explanation
The attack surface is fully user-reachable with no privilege required. Any account can call `ft_transfer_call` on any NEP-141 token. Realistic triggering scenarios include: a user initiating a bridge transfer before the DAO has registered the token; a user mistyping the token account ID; or a token being delisted after a transfer is initiated. The `ft_on_transfer` entry point is public and unpermissioned (aside from the global pause), making accidental triggering straightforward and deliberate triggering trivial.

## Recommendation
Add a registration check at the top of `init_transfer`, before incrementing `current_origin_nonce` or storing any state. Because `ft_on_transfer` must return the number of tokens to refund, returning the full `amount` on a failed check causes the token contract to automatically refund the user — no separate cancel path is needed:

```rust
require!(
    self.token_id_to_address
        .get(&(init_transfer_msg.get_destination_chain(), token_id.clone()))
        .is_some(),
    BridgeError::TokenNotRegistered.as_ref()
);
```

This must be placed before `self.current_origin_nonce += 1` and before any call to `init_transfer_internal`.

## Proof of Concept
1. Deploy any NEP-141-compliant token `unregistered.token.near` not present in `token_id_to_address` on the bridge.
2. Register storage balance for the calling account on the bridge.
3. Call `ft_transfer_call` on `unregistered.token.near`:
   ```json
   {
     "receiver_id": "omni-bridge.near",
     "amount": "1000000",
     "msg": "{\"recipient\": \"Eth:0xDEAD...\", \"fee\": \"0\", \"native_token_fee\": \"0\"}"
   }
   ```
4. `ft_on_transfer` is invoked; `init_transfer` passes both guards (recipient is Eth, fee=0 < amount=1000000); `init_transfer_internal` inserts the record into `pending_transfers` and returns `U128(0)`, keeping all 1,000,000 tokens in the bridge.
5. Call `sign_transfer` with the resulting `TransferId`. The call panics at `get_token_address` → `FailedToGetTokenAddress` because `token_id_to_address` has no entry for `(Eth, unregistered.token.near)`.
6. Verify via `get_transfer_message` that the record still exists in `pending_transfers`. The 1,000,000 tokens are irrecoverable by the user.
