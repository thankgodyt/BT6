### Title
Silent tx_bytes Corruption in Safe Deposit Path Causes Permanent UTXO Locking - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
In `internal_safe_verify_deposit_entry`, when the submitted deposit transaction bytes exceed 10,000 bytes, the code silently replaces the real transaction bytes with 300 zero bytes before storing the UTXO in the bridge's pool. The deposit address validation and nBTC minting proceed normally on the real bytes, but the UTXO recorded on-chain is permanently corrupted. Any subsequent attempt by the bridge to spend that UTXO (withdrawal or refund) will operate on garbage input data, causing the operation to fail and leaving the underlying BTC permanently locked.

### Finding Description
The vulnerability is in `internal_safe_verify_deposit_entry`:

```rust
// contracts/satoshi-bridge/src/btc_light_client/deposit.rs lines 204-209
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]   // ← real bytes silently discarded; zeros stored instead
} else {
    tx_bytes
};
```

This branch executes **after** the deposit address and amount have been validated against the real bytes (lines 191–202), but **before** the UTXO is constructed and stored:

```rust
let utxo = UTXO {
    path,
    tx_bytes,   // ← 300 zero bytes when original tx > 10 000 bytes
    vout,
    balance: transaction.output()[vout].value.to_sat(),
};
```

The corrupted UTXO is then inserted into the bridge's live UTXO pool via `safe_mint_callback → internal_set_utxo`. The nBTC mint proceeds normally, so the user receives their tokens, but the bridge now holds a UTXO whose `tx_bytes` field is `[0u8; 300]`.

This code path is reachable from the current (non-deprecated) public entry point `verify_deposit_v2` whenever `deposit_msg.safe_deposit` is `Some(...)`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs lines 81-100
if deposit_msg.safe_deposit.is_some() {
    self.internal_safe_verify_deposit_entry(...)
}
```

The analog to the reported `rejectUnauthorized: false` pattern is exact: instead of rejecting an oversized transaction (or storing it faithfully), the code silently accepts the deposit and records an invalid UTXO — bypassing the integrity guarantee that every pooled UTXO has valid, spendable `tx_bytes`.

### Impact Explanation
When the bridge later selects the corrupted UTXO for a user withdrawal, `generate_vutxos` reconstructs the `TxOut` from `path` and `balance` (so the PSBT input amount/script is correct), but any PSBT layer that requires the full previous transaction — mandatory for legacy P2PKH inputs and used by some SegWit implementations for fee verification — will receive 300 zero bytes and either panic or produce an invalid PSBT. The MPC signing call will be issued against a malformed payload; the resulting signed transaction will be unbroadcastable. The user's nBTC is burned in the `verify_withdraw` flow, but the BTC never leaves the bridge address, permanently locking it. Even if the PSBT layer tolerates the zeroed bytes at signing time, the stored UTXO is irrecoverably corrupted: no operator path exists to repair `tx_bytes` after the fact, so the UTXO is stranded in the pool indefinitely.

**Allowed impact matched:** *Significant loss, theft, destruction, or permanent locking of user or protocol funds* (Critical) / *stuck bridge state requiring operator intervention* (Medium).

### Likelihood Explanation
A Bitcoin transaction exceeds 10,000 bytes when it consolidates roughly 40+ P2PKH inputs or 65+ P2WPKH inputs — unusual for a typical user deposit but entirely possible for exchange hot-wallet sweeps or consolidation transactions. No special role or privileged access is required; any public caller of `verify_deposit_v2` with `safe_deposit` set can trigger this path. The attacker does not need to craft the transaction themselves — they only need to submit a legitimately large on-chain transaction as the deposit proof.

### Recommendation
Remove the silent truncation entirely. Either:
- **Reject** oversized transactions with an explicit `require!` and a clear error message (e.g., `require!(tx_bytes.0.len() <= MAX_SAFE_DEPOSIT_TX_BYTES, "tx_bytes too large")`), consistent with how `request_refund` enforces `MAX_REQUEST_REFUND_TX_BYTES`; or
- Store the full `tx_bytes` regardless of size and rely on the existing NEAR storage-deposit mechanism to cover the cost.

Do not silently substitute zeros for real data in any code path that affects on-chain state.

### Proof of Concept
1. Construct or locate a valid Bitcoin transaction paying the bridge deposit address whose serialized size exceeds 10,000 bytes (e.g., a consolidation tx with ~50 P2WPKH inputs).
2. Call `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)`, supplying the large `tx_bytes` and a valid Merkle proof.
3. The light-client proof passes; `safe_mint_callback` fires; nBTC is minted to the recipient.
4. Inspect on-chain state: the stored UTXO has `tx_bytes = [0u8; 300]`.
5. Initiate a withdrawal that selects this UTXO. The PSBT is built with zeroed previous-transaction bytes; the MPC-signed transaction is invalid and cannot be broadcast.
6. Call `verify_withdraw` — it will never succeed because the transaction is not on-chain. The user's nBTC has been burned; the BTC remains locked at the bridge address with no recovery path. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
