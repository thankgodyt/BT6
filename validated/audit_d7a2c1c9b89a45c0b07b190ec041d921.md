### Title
Hardcoded Mainnet `HistoricityCutoff` in `mkGenesisConfig` Ignores Configured Security Parameter `k` and Active Slot Coefficient `f` - (`File: ouroboros-consensus-diffusion/src/ouroboros-consensus-diffusion/Ouroboros/Consensus/Node/Genesis.hs`)

---

### Summary

`mkGenesisConfig` in `Ouroboros.Consensus.Node.Genesis` unconditionally sets `gcHistoricityCutoff` to a literal computed from Cardano mainnet constants (`k=2160`, `f=1/20`, `slot_length=1s`), regardless of the actual security parameter `k`, active slot coefficient `f`, or slot length configured for the running node. On any non-mainnet deployment (private testnet, staging network, or a future network with different parameters), the historicity cutoff is miscalibrated, materially weakening the Genesis ChainSync security guarantees in a way that an unprivileged peer can exploit.

---

### Finding Description

In `mkGenesisConfig`, when Genesis is enabled, the `gcHistoricityCutoff` field is set as:

```haskell
gcHistoricityCutoff = Just $ HistoricityCutoff $ 3 * 2160 * 20 + 3600
``` [1](#0-0) 

The comment acknowledges this is the Cardano mainnet Shelley stability window (`3k/f` slots × 1 s/slot = `3 × 2160 × 20 = 129,600 s`) plus one hour. However, `mkGenesisConfig` accepts only `GenesisConfigFlags`, which contains no field for the security parameter `k`, the active slot coefficient `f`, or the slot length:

```haskell
data GenesisConfigFlags = GenesisConfigFlags
  { gcfEnableCSJ :: Bool
  , gcfEnableLoEAndGDD :: Bool
  , gcfEnableLoP :: Bool
  , gcfBlockFetchGracePeriod :: Maybe DiffTime
  , gcfBucketCapacity :: Maybe Integer
  , gcfBucketRate :: Maybe Integer
  , gcfCSJJumpSize :: Maybe SlotNo
  , gcfGDDRateLimit :: Maybe DiffTime
  }
``` [2](#0-1) 

There is no override field for `gcHistoricityCutoff` in `GenesisConfigFlags`. The hardcoded value is the only path.

The `HistoricityCutoff` is consumed by `mkCheck` in `HistoricityCheck.hs`, which disconnects a peer if the age of its `MsgRollBackward` or `MsgAwaitReply` exceeds the cutoff:

```haskell
pure $
  when (historicityCutoff < actualRollbackAge) $
    throwError HistoricityException { ... }
``` [3](#0-2) 

The `HistoricityCutoff` docstring explicitly states it must be set to at least the maximum stability window across all eras:

> "This should be set to at least the maximum duration (across all eras) of a stability window (the number of slots in which at least k blocks are guaranteed to arise)." [4](#0-3) 

The analogous CSJ jump size (`defaultCSJJumpSize`) also hardcodes `2 * 2160`, and the code itself acknowledges this is a known limitation:

```haskell
-- The larger Shelley forecast range (3 * 2160 * 20) works in more recent
-- ranges of slots, but causes syncing to block in Byron. A future
-- improvement would be to make this era-dynamic...
defaultCSJJumpSize = 2 * 2160 -- Byron forecast range
``` [5](#0-4) 

---

### Impact Explanation

**Case 1 — Testnet/private network with smaller `k` or larger `f` (stability window < 37 hours):**

The hardcoded cutoff of 37 hours is far larger than the actual stability window. An adversarial peer can send `MsgAwaitReply` when its chain tip is many stability windows old (e.g., hours old on a testnet where the stability window is seconds or minutes), and the node will not disconnect from it. This peer remains counted in the Limit on Eagerness (LoE) calculation. The LoE anchor is held at a very old point, preventing the node's chain selection from advancing. The Genesis Density Disconnector (GDD) may not resolve this because the adversarial peer's chain is not necessarily sparse relative to the stale LoE anchor. The historicity check — the intended defense — is effectively disabled.

**Case 2 — Network with larger `k` or smaller `f` (stability window > 37 hours):**

The hardcoded cutoff is smaller than the actual stability window. Honest peers that legitimately send `MsgRollBackward` or `MsgAwaitReply` within the real stability window are incorrectly disconnected. The node loses connections to honest peers and may be left connected only to adversarial peers, which can then serve a non-canonical chain that the node selects.

In both cases, the root cause is the same as the external report: a hardcoded constant is used where the configurable protocol parameter should be used.

---

### Likelihood Explanation

The vulnerability is triggered on any Cardano-compatible node deployment that:
1. Enables Genesis (`mkGenesisConfig (Just flags)`), and
2. Runs with `k ≠ 2160`, `f ≠ 1/20`, or `slot_length ≠ 1s`.

This includes all private testnets, staging networks, and any future network that changes `k` or `f`. The entry path requires only that an unprivileged peer send crafted ChainSync messages (`MsgAwaitReply` or `MsgRollBackward`), which is a standard part of the ChainSync mini-protocol. No special privileges, keys, or stake are required.

---

### Recommendation

`mkGenesisConfig` should accept the actual security parameter `k`, active slot coefficient `f`, and slot length as inputs, and compute `gcHistoricityCutoff` from them:

```haskell
-- Correct: derive from actual protocol parameters
gcHistoricityCutoff = Just $ HistoricityCutoff $
    fromIntegral (3 * unNonZero k) / f * slotLengthInSeconds + 3600
```

Alternatively, `GenesisConfigFlags` should include an optional override field for `gcHistoricityCutoff` (analogous to `gcfCSJJumpSize`), and the caller (e.g., `cardano-node`) should compute and pass the correct value based on the genesis configuration.

The CSJ jump size `defaultCSJJumpSize = 2 * 2160` has the same problem and should be similarly parameterized.

---

### Proof of Concept

1. Configure a private Cardano testnet with `k = 100` (stability window ≈ `3 × 100 × 20 = 6000 s ≈ 100 minutes`).
2. Enable Genesis on the syncing node using `enableGenesisConfigDefault`.
3. Connect an adversarial peer that sends `MsgAwaitReply` when its chain tip is 2 hours old (well within the hardcoded 37-hour cutoff, but 72× past the actual stability window).
4. Observe that `mkCheck` in `HistoricityCheck.hs` does **not** disconnect the peer, because `historicityCutoff (133200 s) > actualRollbackAge (7200 s)` is false — the check passes.
5. The adversarial peer remains in the LoE calculation with a stale chain tip, anchoring the LoE at an old point and preventing chain selection from advancing past it.

The correct behavior would be to disconnect the peer because `7200 s > 6000 s` (the actual stability window), but the hardcoded cutoff prevents this. [6](#0-5)
