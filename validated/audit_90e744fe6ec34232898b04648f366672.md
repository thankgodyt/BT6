### Title
Excess NEAR Attached to `execute_refund` Is Permanently Locked in the Bridge Contract — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` is a publicly callable, `#[payable]` function that enforces a minimum attached deposit via a `>=` check. Any NEAR attached beyond the required minimum is silently absorbed into the contract with no refund mechanism. This is a direct analog to the reported `>=`-overpayment pattern: the contract accepts excess funds but only consumes the exact required amount, leaving the remainder permanently locked.

---

### Finding Description

`execute_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is marked `#[payable]` and delegates to `resolve_execute_refund_timelock`, which enforces:

```rust
// contracts/satoshi-bridge/src/refund.rs, line 202-205
require!(
    env::attached_deposit() >= self.required_balance_for_execute_refund(),
    "Insufficient deposit for storage"
);
``` [1](#0-0) 

The `>=` operator permits any amount at or above the threshold. After this check, the function proceeds with PSBT construction and MPC signing — it never returns the excess NEAR to `env::predecessor_account_id()`. There is no `Promise::new(env::predecessor_account_id()).transfer(excess)` call anywhere in the `execute_refund` path. [2](#0-1) 

Contrast this with `request_refund`, whose documentation explicitly states: *"The deposit is NOT refunded — it covers request storage and acts as an anti-spam fee."* [3](#0-2) 

No equivalent design-intent statement exists for `execute_refund`, and the function's purpose (executing a refund for a user's stuck deposit) gives no reason to permanently consume excess NEAR.

---

### Impact Explanation

Any NEAR attached to `execute_refund` beyond `required_balance_for_execute_refund()` is permanently locked in the bridge contract. The contract has no sweep, no recovery function, and no event that tracks the excess. The locked amount equals `env::attached_deposit() − required_balance_for_execute_refund()` per call. This matches the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

---

### Likelihood Explanation

`execute_refund` is callable by any unprivileged NEAR account after the timelock elapses. [4](#0-3) 

Users who are uncertain of the exact required deposit (a common pattern when interacting with NEAR contracts via CLI or dApps that round up for safety) will routinely attach a small buffer. Each such call permanently loses the buffer. The likelihood is low-to-moderate: it requires no adversarial action, only normal user behavior.

---

### Recommendation

Two mitigations mirror those in the external report:

1. **Exact-match enforcement**: Replace `>=` with `==` so any overpayment reverts:
   ```rust
   require!(
       env::attached_deposit() == self.required_balance_for_execute_refund(),
       "Attached deposit must equal required storage balance"
   );
   ```

2. **Refund excess**: After the check, compute and return any surplus:
   ```rust
   let required = self.required_balance_for_execute_refund();
   let attached = env::attached_deposit();
   require!(attached >= required, "Insufficient deposit for storage");
   let excess = attached.saturating_sub(required);
   if excess > NearToken::from_yoctonear(0) {
       Promise::new(env::predecessor_account_id()).transfer(excess);
   }
   ```

Option 1 is simpler and eliminates ambiguity. Option 2 is more user-friendly.

---

### Proof of Concept

1. Alice wants to execute a refund for her stuck deposit. She is unsure of the exact required deposit and attaches `required_balance_for_execute_refund() + 0.5 NEAR` to be safe.
2. `resolve_execute_refund_timelock` passes the `>=` check.
3. The function completes successfully; the PSBT is built and MPC signing is requested.
4. Alice's 0.5 NEAR excess is now permanently held by the bridge contract — no event is emitted, no recovery path exists.
5. Repeated across many users (e.g., a dApp that always pads by 0.1 NEAR), the locked balance accumulates indefinitely. [5](#0-4)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
