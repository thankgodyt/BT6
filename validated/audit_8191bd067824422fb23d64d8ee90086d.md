### Title
Stub `validatePerasCert` Allows Crafted Peras Certificates to Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default implementation of `validatePerasCert` in the `BlockSupportsPeras` class is a no-op stub that unconditionally returns `Right` (success) for every certificate, regardless of its cryptographic or semantic validity. Because the `ValidatedPerasCert` wrapper is the sole gate before a certificate's weight boost is applied to chain selection, an unprivileged peer that sends a crafted `PerasCert` over the Peras object-diffusion mini-protocol can inject an arbitrary weight boost onto any block in the VolatileDB, causing the node to prefer a non-canonical fork.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` as the mandatory validation step that must produce a `ValidatedPerasCert` before a certificate may enter the system:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The default (and currently only shipped) implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature verification, no quorum check, no committee-membership check, and no round-number sanity check is performed. The `ValidatedPerasCert` type is supposed to be an unforgeable proof of validity, but the constructor is handed out freely.

The network entry point `processCerts` calls this function on every inbound certificate batch:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` always returns `Right`, every certificate in every batch passes, and the `addCert` callback inserts it into `PerasCertDB`. The `implAddCert` function itself carries a matching TODO confirming that no additional validation is performed there either:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert :: ...
``` [3](#0-2) 

Once the certificate is in `PerasCertDB`, `addPerasCertAsync` queues a `ChainSelAddPerasCert` message. `chainSelSync` processes it by first adding the cert to the DB and then calling `chainSelectionForBlock` for the boosted block:

```haskell
certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
...
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Inside `chainSelectionForBlock`, the weight snapshot is read atomically and used throughout chain selection:

```haskell
(invalid, curChain, weights) <-
  atomically $
    (,,)
      <$> (forgetFingerprint <$> readTVar cdbInvalid)
      <*> Query.getCurrentChain cdb
      <*> (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)
``` [5](#0-4) 

`implGetWeightSnapshot` derives the snapshot directly from all certificates in the DB, so the injected certificate's boost is immediately visible:

```haskell
let weights =
      mkPerasWeightSnapshot
        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [6](#0-5) 

The inflated weight is then used by `preferAnchoredCandidate` and `compareChainDiffs` to rank candidates, and by `Diff.rollbackExceedsSuffix` to filter them. A sufficiently large fake boost can make any fork in the VolatileDB appear heavier than the honest chain, causing the node to switch to it. [7](#0-6) 

The `Cert/V1.hs` module itself notes that deserialization performs only minimal structural checks and explicitly defers "semantic and cryptographic checks" to a later validation step that does not currently exist: [8](#0-7)

### Impact Explanation

An unprivileged peer can send a single crafted `PerasCert` message that boosts any block already in the node's VolatileDB by an arbitrarily large `PerasWeight`. Because `totalWeightOfFragment` adds this boost to the chain length when comparing candidates, the attacker can make the node's chain-selection logic prefer a minority or adversarial fork over the honest chain. This is a **chain-selection error** that lets an unprivileged peer cause an honest node to prefer a non-canonical chain, matching the "High" impact tier (chain selection bug beyond intended security assumptions) and potentially the "Critical" tier (bypass of Peras certificate checks enabling unauthorized certificate acceptance).

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is a public, unauthenticated network interface. Any peer that can connect to the node can send a `PerasCert` message. The stub validation requires zero cryptographic material — the attacker does not need any keys, stake, or committee membership. The only constraint is that the boosted block must already be in the VolatileDB, which is trivially satisfied by sending the block first via the normal block-fetch path. The TODO comments and the referenced issue (`tweag/cardano-peras#120`) confirm this is a known incomplete state, not a deliberate design choice.

---

### Recommendation

1. Implement `validatePerasCert` with full cryptographic checks: aggregate BLS signature verification over the round number and boosted block hash, committee-membership verification for each voter seat index, quorum-threshold enforcement, and round-number range checks against the current ledger state.
2. Remove the default stub implementation so that any block type that does not provide a real implementation fails to compile rather than silently accepting all certificates.
3. Add the missing validation logic in `implAddCert` (as noted by the TODO) to enforce invariants such as one certificate per round and boosted-block slot bounds relative to the immutable tip.
4. Consider rate-limiting or authenticating the Peras certificate diffusion channel until full validation is in place.

---

### Proof of Concept

**Private-testnet sequence:**

1. Start a node with the default `BlockSupportsPeras` instance (e.g., `TestBlock` or any instance that inherits the default `validatePerasCert`).
2. Connect an adversarial peer. Send a valid block `B_fork` on a minority fork via the normal block-fetch path so that `B_fork` lands in the node's VolatileDB.
3. Construct a `PerasCert` with `pcCertBoostedBlock = blockPoint B_fork` and `pcCertRound = <any round not yet in the DB>`. The certificate needs no valid signature or committee proof.
4. Send the crafted `PerasCert` to the node via the Peras object-diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert` → `Right (ValidatedPerasCert ...)` unconditionally.
6. The certificate is inserted into `PerasCertDB`; `addPerasCertAsync` queues `ChainSelAddPerasCert`.
7. `chainSelSync` calls `chainSelectionForBlock` for `B_fork`; the weight snapshot now includes the fake boost.
8. `preferAnchoredCandidate` ranks the fork above the honest chain; the node switches to `B_fork`.

The node has adopted a non-canonical chain driven entirely by a certificate that was never cryptographically verified — the direct analog of the Boba oracle's stale `marketPriceRatio` being used without on-demand verification.

    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
