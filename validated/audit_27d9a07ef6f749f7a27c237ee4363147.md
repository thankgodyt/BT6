### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` for every inbound certificate, performing no cryptographic or structural checks. This is the live code path used by `processCerts` in the production Peras certificate ObjectDiffusion writer. Any unprivileged peer can inject an arbitrary `PerasCert` (with any round number and any boosted block point) that will be accepted, stored in the ChainDB, and applied as a chain-weight boost during chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must reject invalid certificates before they enter the node's state. The degenerate instance — which is the only instance in the codebase and is used in all production paths — implements this method as an unconditional success:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production inbound certificate processing pipeline. Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `(validatePerasCert mkPerasParams)` as the `validateCert` argument to `processCerts`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, because the stub always returns `Right`, every certificate passes and is forwarded to `addCert` (or `ChainDB.addPerasCertAsync`):

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Once accepted, the certificate is stored and its boost (`vpcCertBoost = perasWeight params = PerasWeight 15`) is applied to the boosted block's chain weight during chain selection. The ChainDB API documents this explicitly:

> `addPerasCertAsync` — Asynchronously insert a certificate to the DB. If this leads to a fork to be weightier than our current selection, this will trigger a fork switch. [4](#0-3) 

The analog to the external report is direct: just as `ValidateBasic` is called for RPC-submitted messages but bypassed for hook-executed messages, here `validatePerasCert` is called in the inbound pipeline but its implementation performs no actual validation — the validation step exists structurally but is a no-op stub, producing the same bypass effect.

---

### Impact Explanation

A `PerasWeight` of 15 means a chain whose tip block holds a valid certificate is preferred over a competing chain that is up to 15 blocks shorter. An adversary who can inject a crafted `PerasCert` pointing to any `pcCertBoostedBlock` on a competing fork can cause an honest node to switch away from the canonical chain to a fork that is up to 15 blocks shorter. This is a chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Ouroboros protocol.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is reachable from any connected peer. No special privileges, keys, or stake are required. The attacker only needs to craft a `PerasCert` CBOR payload with a desired `pcCertRound` and `pcCertBoostedBlock` and send it via the inbound ObjectDiffusion channel. The `processCerts` function will call `validatePerasCert mkPerasParams cert`, which unconditionally returns `Right`, and the certificate will be stored and applied.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with actual validation logic that checks, at minimum:

1. **Committee membership** — the signers are eligible voters for the given round.
2. **Aggregate BLS signature** — the certificate carries a valid aggregate signature over `(pcCertRound, pcCertBoostedBlock)` from a quorum of eligible committee members.
3. **Round plausibility** — the certificate's round number is within the acceptable window relative to the current chain tip.

The BLS aggregate signature verification infrastructure already exists in `Ouroboros.Consensus.Peras.Crypto.BLS` (`verifyAggregateVoteSignature`, `batchVerifyVRFOutputs`). [5](#0-4) 

Until the real validation is implemented, the inbound ObjectDiffusion certificate writer should not be exposed to untrusted peers.

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate ObjectDiffusion mini-protocol.
2. Craft a `PerasCert` CBOR payload:
   - `pcCertRound`: any round number not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock`: the `Point` of a block on a competing fork that is up to 15 blocks behind the canonical tip
3. Send the certificate batch via the inbound ObjectDiffusion channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
5. The certificate is forwarded to `ChainDB.addPerasCertAsync`.
6. Chain selection re-runs; the competing fork now has a weight boost of 15, causing the node to switch to it. [6](#0-5) [7](#0-6)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
