### Title
Peras Certificate Validation Stub Always Accepts Any Certificate, Enabling Artificial Chain-Weight Injection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or structural checks. Because this is the **only** `BlockSupportsPeras` instance in the codebase, every certificate received from an unprivileged peer over the object-diffusion mini-protocol is accepted as valid. The accepted certificate is stored in the `PerasCertDB`, its boosted-block point is added to the `PerasWeightSnapshot`, and chain selection is immediately re-run for that block. An attacker can therefore inject arbitrary Peras weight onto any block in the VolatileDB, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must reject cryptographically invalid certificates before they influence chain selection. [1](#0-0) 

The sole concrete instance — explicitly marked as a temporary degenerate placeholder — implements this gate as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [2](#0-1) 

No signature verification, no round-number range check, no boosted-block existence check — every `PerasCert` is wrapped in `Right` and assigned the full configured `perasWeight`.

A `grep` for `instance.*BlockSupportsPeras` confirms this is the **only** instance in the repository; there is no overriding Cardano-specific instance.

The production inbound path in `makePerasCertPoolWriterFromChainDB` passes this stub directly as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then unconditionally adds every certificate that passes this non-check to the database: [4](#0-3) 

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` directly from every stored certificate, including the forged ones: [5](#0-4) 

`chainSelSync` then re-runs chain selection for the boosted block, using the inflated weight snapshot: [6](#0-5) 

Chain selection compares `wsvTotalWeight` — `BlockNo + weightBoost` — so a sufficiently large injected boost can make a shorter fork outweigh the honest chain: [7](#0-6) 

---

### Impact Explanation

This is a **High** chain-selection bug. An unprivileged peer can craft a `PerasCert` naming any block hash in the node's VolatileDB as `pcCertBoostedBlock`. Because `validatePerasCert` never rejects anything, the certificate is stored and its `perasWeight` is added to that block's chain weight. If the attacker sends enough certificates (one per round, since the DB deduplicates by round number), the cumulative boost can exceed the honest chain's `BlockNo` advantage, causing the node to irreversibly switch to a non-canonical fork. This satisfies the "chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" criterion.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer — no special privileges, keys, or stake are required. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` with an arbitrary `pcCertBoostedBlock`. The `PerasCert` type is fully serialisable: [8](#0-7) 

The only natural throttle is the per-round deduplication in `implAddCert`, which limits one certificate per `PerasRoundNo`. However, round numbers are a `Word64`, giving an attacker effectively unlimited distinct certificates to inject. [9](#0-8) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic validation before the Peras object-diffusion path is enabled in any network-connected build. At minimum, the implementation must verify:

1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the known committee public keys.
2. That `pcCertRound` falls within the current or recent Peras round window.
3. That the voter bitmap in the certificate represents a quorum of eligible committee seats.

Until a real implementation exists, the production pool-writer (`makePerasCertPoolWriterFromChainDB`) should not be wired into any node that accepts inbound connections, or the object-diffusion server for certificates should be disabled entirely.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
