### Title
Missing `refund_address` Validation Enables Attacker-Triggered Stuck Refund State - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `request_refund_callback` function stores the caller-supplied `refund_address` string into a `RefundRequest` without validating it as a well-formed Bitcoin/Zcash address. Address parsing is deferred until `execute_refund` → `build_refund_output`, where an invalid address causes an unconditional `panic!`. Because `request_refund` is publicly callable (no `#[trusted_relayer]` on the method), any unprivileged account can submit a refund request for any unfinalized deposit whose `deposit_msg.refund_address` is `None`, supplying a garbage `refund_address`. The resulting `RefundRequest` can never be executed; it is stuck until a DAO/Operator manually rejects it.

### Finding Description
`request_refund` (bridge.rs line 510) is a public, payable function. It calls `internal_request_refund`, which verifies the BTC transaction via the light client and then chains to `request_refund_callback`. Inside the callback the `refund_address` is stored verbatim:

```rust
// refund.rs line 564-574
let refund_request = RefundRequest {
    ...
    refund_address,   // ← stored without any format check
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [1](#0-0) 

Address parsing only happens later in `build_refund_output`:

```rust
// refund.rs line 296-297
let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
    .expect("Invalid refund address");   // ← panics here
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the only guard in `internal_request_refund` is skipped entirely:

```rust
// refund.rs line 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

So for any deposit whose `deposit_msg.refund_address` is `None`, an attacker can supply an arbitrary string as `refund_address` and the contract will accept and persist it.

### Impact Explanation
Once a `RefundRequest` with an invalid `refund_address` is stored, every call to `execute_refund` for that key panics inside `build_refund_output`. The victim's deposit UTXO is blocked from being refunded. The victim cannot self-service the situation: `reject_refund` requires DAO/Operator access or proof that the UTXO was already finalized via `verify_deposit`:

```rust
// bridge.rs line 564-567
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
``` [4](#0-3) 

The victim's BTC remains unrecoverable via the refund path until a DAO/Operator manually rejects the poisoned request. This is a stuck bridge state requiring operator intervention — matching the **Low** allowed impact ("publicly reachable panic-driven fault in production bridge/token paths without direct theft") and potentially **Medium** ("attacker-triggered temporary locking of bridged funds").

### Likelihood Explanation
- `request_refund` is publicly callable (no `#[trusted_relayer]` on the method).
- The deposit transaction and Merkle proof are public data on the Bitcoin blockchain.
- `deposit_msg` is deterministically derivable from the victim's NEAR account ID and other public parameters.
- The attacker must pay `required_balance_for_request_refund()` as a storage deposit (lost on rejection), making mass-griefing costly but targeted griefing feasible.
- The condition `deposit_msg.refund_address == None` is the common case for standard deposits.

### Recommendation
Validate `refund_address` as a well-formed chain address at the entry point, before the light-client cross-contract call is dispatched, so invalid addresses are rejected immediately:

```rust
// In internal_request_refund, before the verify_transaction_inclusion_promise call:
crate::network::Address::parse(&refund_address, self.internal_config().chain.clone())
    .unwrap_or_else(|_| env::panic_str("Invalid refund_address"));
```

This mirrors the validation already present in `build_refund_output` and eliminates the deferred-panic window.

### Proof of Concept
1. Victim sends BTC to a deposit address derived from `deposit_msg` with `refund_address: None`. The deposit is never finalized by a relayer.
2. Attacker observes the victim's `deposit_msg` and the on-chain BTC transaction.
3. Attacker calls `request_refund(deposit_msg, "NOT_A_VALID_ADDRESS", tx_bytes, vout, proof, None)` with the required storage deposit attached.
4. Light client verifies the transaction; `request_refund_callback` passes all checks (script_pubkey matches, UTXO not yet verified, no duplicate request) and stores `RefundRequest { refund_address: "NOT_A_VALID_ADDRESS", ... }`.
5. Anyone calls `execute_refund(utxo_storage_key, None)`. Inside `build_refund_output`, `Address::parse("NOT_A_VALID_ADDRESS", ...)` panics. The call reverts.
6. Step 5 repeats indefinitely — the refund is permanently stuck until a DAO/Operator calls `reject_refund`.
7. After rejection the victim can re-submit with a valid address, but required DAO/Operator intervention and the delay constitute a stuck-state fault reachable by any unprivileged account.
