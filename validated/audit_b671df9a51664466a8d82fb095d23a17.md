### Title
Unhandled `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Permanently Locks Bridged Tokens — (`File: near/omni-bridge/src/lib.rs`)

### Summary

When `process_fin_transfer_to_near` finalizes a transfer of a non-deployed (locked) NEAR-native token with an empty `msg`, `send_tokens` issues a plain `ft_transfer` call. The subsequent callback `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`. Because `is_refund_required(false)` unconditionally returns `false`, the callback never inspects the promise result of the `ft_transfer`. If the transfer fails — for example because the token contract enforces a blacklist or a pause — the callback silently proceeds to the "success" branch, logs a `FinTransferEvent`, and sends the fee to the relayer. The finalization nonce is already consumed and the locked-token accounting already updated, so the bridged tokens are permanently stranded in the bridge contract with no recovery path.

---

### Finding Description

**Root cause — `is_refund_required` ignores promise outcome for `ft_transfer`** [1](#0-0) 

`is_refund_required` only reads the promise result when `is_ft_transfer_call == true`. When the flag is `false` it unconditionally returns `false` ("no refund needed"), regardless of whether the underlying cross-contract call succeeded or panicked.

**State already committed before the transfer**

By the time `send_tokens` is called, `process_fin_transfer_to_near` has already:

1. Consumed the finalization nonce via `add_fin_transfer`: [4](#0-3) 

2. Updated locked-token accounting via `unlock_tokens_if_needed`: [5](#0-4) 

3. Charged the relayer's storage balance: [6](#0-5) 

None of these are rolled back when `ft_transfer` fails.

**Callback silently succeeds** [7](#0-6) 

Because `is_refund_required(false)` returns `false`, the `if` branch (which would burn tokens, revert lock actions, and remove the fin-transfer record) is never entered. The `else` branch sends the fee and emits `FinTransferEvent`, giving the appearance of a successful delivery.

---

### Impact Explanation

The bridged tokens remain in the bridge contract. The finalization nonce is consumed, so the proof cannot be replayed. There is no admin function to "un-finalize" a transfer or rescue stranded tokens. The result is **permanent, irrecoverable loss of the bridged funds** for the user.

---

### Likelihood Explanation

The NEAR ecosystem hosts NEP-141 tokens that implement transfer restrictions: blacklists (e.g., USDC.e, USDT.e wrappers, or any token following the same pattern), pause mechanisms, or allowlist-only transfers. Any such token that is locked in the bridge (i.e., a NEAR-native token bridged outbound to an EVM chain and then bridged back) is affected. An attacker or an inadvertently blacklisted user needs only to initiate a cross-chain transfer from the EVM side specifying a NEAR recipient that the token contract will reject. The relayer, acting in good faith, calls `fin_transfer`, the storage deposit check passes (the account is registered), but `ft_transfer` panics inside the token contract. The callback treats this as success.

---

### Recommendation

`fin_transfer_send_tokens_callback` must check the promise result unconditionally, not only when `is_ft_transfer_call == true`. Extend `is_refund_required` (or add a separate check) to detect a failed `ft_transfer` promise and, on failure, revert the lock actions and remove the fin-transfer record — mirroring the existing refund logic already present for the `ft_transfer_call` path. [8](#0-7)

### Proof of Concept

1. A NEAR-native token `TOKEN` with a blacklist is locked in the bridge (users have bridged it outbound to Ethereum).
2. Alice holds `TOKEN` on Ethereum. She initiates a transfer back to NEAR, specifying a NEAR recipient `bob.near` that is blacklisted by `TOKEN`.
3. A relayer calls `fin_transfer` with a `StorageDepositAction` for `bob.near`. The storage deposit succeeds — `bob.near` is registered for `TOKEN`.
4. `process_fin_transfer_to_near` runs:
   - `add_fin_transfer` consumes the nonce.
   - `unlock_tokens_if_needed` decrements the locked balance.
   - `send_tokens` issues `ft_transfer(bob.near, amount)`.
5. `TOKEN`'s `ft_transfer` panics because `bob.near` is blacklisted. The promise fails.
6. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false`. The callback enters the `else` branch, sends the fee to the relayer, and emits `FinTransferEvent`.
8. `TOKEN` remains in the bridge contract. The nonce is consumed. Alice's tokens are permanently lost. [1](#0-0) [3](#0-2) [9](#0-8)
