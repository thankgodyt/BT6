### Title
Silent Token Lock in `safe_mint` When Recipient Account Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary

`safe_mint` in the nBTC token contract mints tokens into the bridge's own balance **before** checking whether the recipient account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring or burning the already-minted tokens, permanently locking them in the bridge's nBTC balance with no on-chain recovery path.

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes `internal_deposit` to the bridge's own account unconditionally, then performs the registration check:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← early return; tokens already minted, never transferred
    }
    ...
}
``` [1](#0-0) 

The `internal_deposit` call on line 112 increases `bridge_id`'s nBTC balance by `amount`. [2](#0-1) 

If `account_id` has no registered storage slot, the function returns `PromiseOrValue::Value(U128(0))` on line 115 without any rollback of the deposit, without burning the tokens, and without placing them in any lost-and-found mapping. [3](#0-2) 

The nBTC contract has no function that allows the bridge to recover or burn tokens from its own balance in response to a failed `safe_mint`. The `burn` function withdraws from `bridge_id`'s balance, but it is only called during the verified-withdrawal flow — not as a rollback for a failed mint. [4](#0-3) 

The bridge's safe-deposit path (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`) is documented to "revert the whole transaction if minting fails." However, `safe_mint` returning `U128(0)` is a **successful** cross-contract call return, not a panic. The bridge callback receives a success result with value 0, which may not be treated as a revert condition, leaving the minted tokens permanently stranded in the bridge's nBTC balance. [5](#0-4) 

### Impact Explanation

Any BTC deposited via the safe-deposit flow where the recipient NEAR account has no nBTC storage registration results in:

- nBTC tokens minted to the bridge's own balance (total supply increases)
- User receives zero nBTC
- Tokens are permanently locked — no recovery function exists in the nBTC contract for this case
- The deposited BTC UTXO is marked as verified and cannot be refunded

This constitutes **permanent locking of user funds** and a **supply/accounting divergence** (total supply exceeds circulating supply accessible to users), matching the Critical impact category: *Significant loss, theft, destruction, or permanent locking of user or protocol funds.*

### Likelihood Explanation

The safe-deposit flow (used by Omni Bridge integrations) requires the caller to attach NEAR for the recipient's token storage. If the storage registration step is skipped, fails, or is executed in the wrong order relative to `safe_mint`, the recipient will be unregistered at the time `safe_mint` runs. Any user whose NEAR account has never interacted with the nBTC contract is unregistered by default. This is a realistic scenario for new users bridging BTC for the first time via an integrating dApp that does not pre-register storage.

### Recommendation

Move the registration check **before** `internal_deposit`, so no tokens are minted if the recipient is unregistered:

```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // return early, nothing minted
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

Alternatively, if minting first is required, add an explicit burn/rollback path when the recipient is unregistered, and emit an event so the bridge callback can detect and revert the deposit.

### Proof of Concept

1. User Alice sends BTC to her bridge deposit address via the Omni Bridge safe-deposit flow.
2. Alice has never registered storage in the nBTC contract (`self.token.accounts.get(&alice) == None`).
3. The bridge relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
4. The bridge cross-contract calls `safe_mint(alice, amount, Some(msg))` on the nBTC contract.
5. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount)` — bridge nBTC balance increases by `amount`.
6. `self.token.accounts.get(&alice)` returns `None` → function returns `PromiseOrValue::Value(U128(0))`.
7. The bridge callback receives a successful call result of `0`.
8. Alice's BTC UTXO is marked as `verified_deposit_utxo` — she cannot request a refund.
9. Alice holds 0 nBTC. The `amount` in nBTC is permanently locked in the bridge's own token balance with no recovery mechanism. [1](#0-0) [6](#0-5)
