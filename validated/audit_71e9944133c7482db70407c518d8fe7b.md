Audit Report

## Title
`denormalize_amount` Unchecked Multiplication Overflow Permanently Freezes Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `denormalize_amount` helper performs a bare `u128` multiplication without overflow protection. With `overflow-checks = true` set in the workspace release profile, any overflow panics the transaction. When `fin_transfer_callback` panics at the denormalization step, the source-chain tokens remain locked or burned while the NEAR-side transfer is never recorded as finalized, permanently freezing the bridged funds.

## Finding Description
`denormalize_amount` at line 2776–2779 performs an unchecked multiplication:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // panics on overflow
}
``` [1](#0-0) 

The workspace `[profile.release]` explicitly sets `overflow-checks = true` at line 31 of `near/Cargo.toml`, so Rust inserts a runtime trap on every integer arithmetic operation in release builds. [2](#0-1) 

In `fin_transfer_callback`, `denormalize_amount` is called at line 725 to construct `transfer_message`, before any state mutation records the transfer as finalized: [3](#0-2) 

`add_fin_transfer` (which inserts into `finalised_transfers`) is only called later inside `process_fin_transfer_to_near` at line 1875: [4](#0-3) 

Because the panic occurs before `add_fin_transfer`, the transfer ID is never recorded. The source-chain `initTransfer` transaction has already been mined and the tokens locked or burned. Resubmitting the same proof triggers the same overflow again, so the funds remain frozen until a DAO-approved contract upgrade is deployed.

The same unchecked call appears in `fast_fin_transfer` at line 770–771: [5](#0-4) 

And in `claim_fee_callback` at line 1122–1127: [6](#0-5) 

No existing guard checks the magnitude of `amount` before calling `denormalize_amount`.

## Impact Explanation
This constitutes **permanent freezing of bridged funds** across EVM and NEAR, matching the Critical allowed impact. For a token registered with 18 EVM decimals and 24 NEAR decimals (`diff_decimals = 6`), the overflow threshold is `u128::MAX / 10^6 ≈ 3.4 × 10^32` token units. Tokens such as SHIB (total supply ~5.89 × 10^32 units) and PEPE (~4.2 × 10^32 units) exceed this threshold. Any holder of more than ~340 trillion such tokens who bridges their full balance will have those tokens permanently locked on EVM while the NEAR callback panics and the transfer is never finalized.

## Likelihood Explanation
The `amount` field of the EVM `InitTransfer` event is a `uint128` set directly by the user when calling `initTransfer`. No privileged role is required. The relayer acts correctly by submitting a valid proof; the overflow is entirely a function of the user-supplied amount and the registered decimal configuration. The condition is reachable by any bridge user holding a sufficiently large balance of a high-supply token, either accidentally or deliberately.

## Recommendation
Replace the bare multiplication in `denormalize_amount` with a checked variant and propagate the error:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> Result<u128, BridgeError> {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    let multiplier = 10_u128.pow(diff_decimals);
    amount.checked_mul(multiplier).ok_or(BridgeError::AmountOverflow)
}
```

Propagate the `Result` in `fin_transfer_callback`, `fast_fin_transfer`, and `claim_fee_callback` so that an oversized amount causes a clean, recoverable rejection (returning an error nonce or refund) rather than a panic. This ensures the source-chain tokens are never locked without a corresponding NEAR-side record.

## Proof of Concept
Token registered with `decimals = 18` (EVM), `origin_decimals = 24` (NEAR), giving `diff_decimals = 6`.

1. User holds `4 × 10^32` EVM token units (~400 trillion whole tokens, within SHIB-class supply and within `uint128` range).
2. User calls `initTransfer` on the EVM bridge with `amount = 4 × 10^32`. EVM bridge burns those tokens and emits `InitTransfer`.
3. Relayer submits the proof to the NEAR bridge via `fin_transfer`.
4. `fin_transfer_callback` executes `denormalize_amount(4e32, Decimals { decimals: 18, origin_decimals: 24 })`:
   - `diff_decimals = 6`
   - `4e32 * 10^6 = 4e38`
   - `u128::MAX ≈ 3.4e38 < 4e38` → **overflow panic**
5. The NEAR callback reverts. `finalised_transfers` is not updated.
6. Resubmitting the same proof triggers the same overflow. The EVM burn is irreversible. The user's `4 × 10^32` tokens are permanently frozen until a DAO-approved contract upgrade is deployed.
