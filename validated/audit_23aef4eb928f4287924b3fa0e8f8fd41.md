### Title
`safe_mint` Mints nBTC to Bridge Before Checking Recipient Registration, Permanently Inflating Supply Without User Credit — (File: `contracts/nbtc/src/lib.rs`)

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function unconditionally mints nBTC tokens into the bridge's own account (`bridge_id`) before verifying that the intended recipient (`account_id`) is registered. If the recipient is not registered, the function returns `U128(0)` and exits — but the tokens already minted to `bridge_id` are permanently committed to NEAR state. Because NEAR cross-contract call state changes are not rolled back by a caller's callback panic, the nBTC total supply is inflated with no corresponding user credit, and the depositor's BTC remains locked on Bitcoin.

### Finding Description

`safe_mint` is the entry point for "safe deposit" flows (e.g., Omni Bridge integrations). Its implementation is:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));            // ← exits without transfer
    }
    ...
}
``` [1](#0-0) 

The `internal_deposit` call on line 112 increases the nBTC total supply and credits `bridge_id`. This state mutation is committed to the nbtc contract's storage the moment the function executes. The subsequent unregistered-account check on line 114 returns `U128(0)` — a silent no-op — without ever reversing the deposit.

In NEAR Protocol, each cross-contract call executes in its own receipt. Even if the satoshi-bridge callback panics upon receiving `U128(0)`, NEAR's execution model does **not** roll back state changes that occurred in a prior receipt (the nbtc contract's execution). The minted tokens remain in `bridge_id` permanently.

The analog to the ACOToken report is direct: just as a collateral owner could manipulate their token balance so that `_getAssignableAmount` returns 0 and they are silently skipped in the exercise loop, here a depositor whose account is absent from the nbtc registry is silently skipped in the credit step — tokens are "processed" (minted to bridge) but never delivered, and the accounting diverges from reality.

### Impact Explanation

- The nBTC total supply increases by `amount` with no corresponding user balance increase.
- The depositor's BTC is locked on Bitcoin; they receive zero nBTC.
- The bridge holds orphaned nBTC in `bridge_id` that is not backed by any pending withdrawal obligation, permanently inflating circulating supply relative to backed supply until a privileged operator manually burns the orphaned tokens.
- This matches the allowed medium impact: *"permanent burning below backed supply … or stuck bridge state requiring operator intervention."* [2](#0-1) 

### Likelihood Explanation

Any user who initiates a safe deposit (sets `safe_deposit: Some(...)` in their `DepositMsg`) without first registering their account in the nbtc contract triggers this path. This is a realistic scenario for first-time users of integrations like Omni Bridge. No adversarial intent is required; ordinary user error is sufficient. A malicious actor could also deliberately unregister their account (possible when balance is 0 via `storage_unregister`) immediately before a safe deposit is relayed, to cause intentional supply inflation. [3](#0-2) 

### Recommendation

Reverse the order of operations: check registration **before** minting. If the account is not registered, either auto-register it or revert with a clear error, so no tokens are minted until delivery is guaranteed:

```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // early exit BEFORE any mint
}
self.token.internal_deposit(&self.bridge_id, amount.into()); // mint only after check
```

Alternatively, use `internal_deposit` directly into `account_id` (auto-registering if needed) rather than staging through `bridge_id`.

### Proof of Concept

1. Alice sends 0.01 BTC to a deposit address derived from a `DepositMsg` with `safe_deposit: Some(OmniBridgeMsg { ... })` and `recipient_id: alice.near`.
2. Alice has never called `storage_deposit` on the nbtc contract, so `alice.near` is not in `token.accounts`.
3. The relayer submits the BTC inclusion proof to satoshi-bridge; satoshi-bridge calls `nbtc.safe_mint(alice.near, 1_000_000, Some(msg))`.
4. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — nBTC total supply increases by 1,000,000 satoshis, all credited to `bridge_id`.
5. `token.accounts.get(&alice.near)` returns `None`; function returns `U128(0)`.
6. The satoshi-bridge callback receives `U128(0)`. Even if it panics, the nbtc state change is not reverted.
7. Alice holds 0 nBTC. The bridge holds 1,000,000 orphaned nBTC. Alice's 0.01 BTC is locked on Bitcoin with no recovery path unless an operator manually intervenes. [1](#0-0)
