### Title
Stale `PerasCfg` Snapshot in `PerasVoteDB.implAddVote` Allows Peras Certificate Forging Under Outdated Quorum Parameters — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

---

### Summary

The `PerasVoteDB` is initialized with a fixed `PerasCfg` (containing the quorum stake threshold) captured once at DB creation time. Every subsequent call to `implAddVote` evaluates quorum against that static snapshot. Simultaneously, each `ValidatedPerasVote` carries a `vpvVoteStake` that is frozen at vote-validation time and is never re-checked against the current stake distribution. If either the Peras protocol parameters or the epoch stake distribution change while votes are still accumulating in the DB, the quorum decision is made against stale data — directly mirroring the "stale governance parameters" class from the external report.

---

### Finding Description

**Static `PerasCfg` capture at DB creation:**

`createDB` receives `pvdbaPerasCfg :: PerasCfg blk` and closes over it in the `implAddVote` action:

```haskell
-- PerasVoteDbArgs, line 127
pvdbaPerasCfg :: HKD f (PerasCfg blk)

-- createDB, line 157
addVote = implAddVote pvdbaPerasCfg env
```

`implAddVote` passes this static config directly to `updatePerasRoundVoteStates`:

```haskell
-- implAddVote, line 208
case updatePerasRoundVoteStates vote perasCfg (pvdsRoundVoteStates pvds) of
```

`updatePerasRoundVoteStates` → `updateCandidateVoteState` → `votesReachQuorum` → `stakeAboveThreshold` all consume the same frozen `PerasCfg`. If `perasQuorumStakeThreshold` or `perasQuorumStakeThresholdSafetyMargin` change (e.g., via a governance update), the DB never learns of the change.

**Stale `vpvVoteStake` in `ValidatedPerasVote`:**

`validatePerasVote` embeds the voter's stake at validation time:

```haskell
-- SupportsPeras.hs default instance, lines 363-369
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
```

This `vpvVoteStake` is accumulated in `updateTargetVoteTally` without any re-check:

```haskell
-- Aggregation.hs, line 456
(votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
```

Votes are garbage-collected by *target slot*, not by epoch, so votes validated under epoch-N stake weights can remain in the DB into epoch N+1. When a new vote arrives in epoch N+1, the quorum check sums the stale epoch-N stake weights alongside fresh ones.

**Acknowledged incompleteness:**

The implementation itself carries an explicit TODO at the exact entry point:

```haskell
-- PerasVoteDB/Impl.hs, lines 172-173
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
```

A second TODO in `SupportsPeras.hs` (lines 154–161) notes that `stakeAboveThreshold` assumes `PerasVoteStake` and the quorum threshold are expressed in the same units (both normalized), which is not enforced — creating an additional unit-mismatch path where the comparison is semantically undefined.

**Chain-selection consequence:**

A certificate forged by `updateCandidateVoteState` → `forgePerasCert` is returned to the caller and eventually reaches `chainSelSync` → `PerasCertDB.addCert`, which triggers chain selection for the boosted block via `chainSelectionForBlock`. The boost weight `vpcCertBoost = perasWeight params` is applied unconditionally once the certificate exists.

---

### Impact Explanation

A certificate forged under stale quorum parameters carries a `vpcCertBoost` that is applied to chain weight during `chainSelSync`. An honest node that receives this certificate will prefer the boosted chain over an equally-long unboosted chain. This constitutes a bypass of Peras certificate checks: a certificate is accepted and acted upon even though the votes backing it did not satisfy the *current* quorum threshold. The impact maps to:

> **Critical** — Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance, which in turn causes chain-selection divergence.

---

### Likelihood Explanation

In the current codebase `PerasCfg` is not dynamically updated at runtime (parameters are set via `mkPerasParams` at node startup), which limits immediate exploitability of the threshold-staleness path. However:

- The `vpvVoteStake` staleness path is structurally active today: votes survive across epoch boundaries because GC is slot-based, and the epoch stake distribution rotates every epoch.
- The explicit TODO at line 172 confirms the validation logic is intentionally incomplete pending future work.
- The unit-mismatch noted in `stakeAboveThreshold` means the quorum comparison may already be semantically incorrect depending on how `PerasVoteStakeDistr` is populated.
- As Peras moves toward production and governance-driven parameter updates are wired in, the threshold-staleness path becomes directly exploitable without any code change.

Likelihood: **Medium** (structurally present and partially active now; fully exploitable once parameter governance is wired).

---

### Recommendation

1. **Re-validate stake at aggregation time.** Do not rely on the `vpvVoteStake` embedded at validation time. Pass the current epoch's `PerasVoteStakeDistr` into `implAddVote` and re-derive each vote's weight before accumulating.

2. **Version the `PerasCfg` snapshot.** Analogous to the external report's `governance_state_version` counter: record the `PerasCfg` version (or a hash of the relevant fields) at vote-validation time and reject votes whose snapshot version differs from the current one at quorum-check time.

3. **Enforce unit consistency.** Address the `stakeAboveThreshold` TODO by normalizing `PerasVoteStake` against total active stake before comparing against the relative `perasQuorumStakeThreshold`.

4. **Scope GC to epoch boundaries.** Garbage-collect votes when the epoch they were validated in ends, preventing cross-epoch stake-weight accumulation.

---

### Proof of Concept

1. Node starts; `PerasVoteDB` is created with `PerasCfg` containing `perasQuorumStakeThreshold = 3/4`.
2. Epoch N: attacker controls voters with combined normalized stake 0.30 (below quorum). Their votes arrive and are validated; each `ValidatedPerasVote` carries `vpvVoteStake` reflecting epoch-N stake.
3. Epoch N+1 begins: honest stake redistribution raises the effective quorum to 0.80 of the new distribution. The attacker's epoch-N votes remain in `pvdsRoundVoteStates` (GC threshold not yet reached).
4. Honest voters contribute 0.50 of epoch-N-equivalent stake in epoch N+1. Their votes are validated with epoch-N+1 weights.
5. `implAddVote` accumulates: stale 0.30 (epoch N) + fresh 0.50 (epoch N+1) = 0.80 total against the frozen `perasQuorumStakeThreshold = 3/4`. Quorum fires.
6. `forgePerasCert` produces a `ValidatedPerasCert`; `chainSelSync` adds it to `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block.
7. The boosted block gains `perasWeight` chain-weight advantage, causing honest nodes to prefer it over a competing chain that legitimately satisfies the epoch-N+1 quorum — chain-selection divergence achieved without stake majority. ```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
