### Title
Stale-Balance Race in `migrate_to_new_token_mint` Allows Incorrect New-Token Distribution — (`contracts/satoshi-bridge/src/nbtc/migration.rs`)

---

### Summary

`internal_migrate_to_new_token` fires parallel cross-contract view calls (`ft_total_supply` + N × `ft_balance_of`) as separate NEAR receipts, then schedules `migrate_to_new_token_mint` as a subsequent callback. Because NEAR processes each receipt in a separate block-level step, any `ft_transfer` on the old token that executes between the view receipts and the callback receipt will cause `migrate_to_new_token_mint` to mint stale (pre-transfer) balances to the new token. The `sum == total_supply` guard does **not** catch this because a transfer between two accounts preserves the total supply.

---

### Finding Description

**Entrypoint (privileged trigger, public exploit window):**

`migrate_to_new_token` is gated by `MigrationOperator`/`DAO`, but once the migration is in flight, any token holder can call `ft_transfer` on the old token — a fully public NEP-141 call.

**Promise chain:** [1](#0-0) 

The `ft_total_supply` and all `ft_balance_of` calls are chained with `.and(...)`, producing independent receipts that are resolved before the callback. Between those receipts and the `migrate_to_new_token_mint` callback, the NEAR runtime can — and will — process other transactions.

**The guard that fails:** [2](#0-1) 

`sum == total_supply` only verifies that the queried per-account balances add up to the queried total supply. A transfer between two accounts does not change the total supply, so this check passes even when the per-account data is stale.

**Concrete race:**

| Step | Alice (in list) | Carol (not in list) | Total supply |
|------|----------------|---------------------|--------------|
| Query receipts processed | 100 | 0 | 150 |
| `ft_transfer` Alice→Carol (10) | 90 | 10 | 150 |
| `migrate_to_new_token_mint` callback | mints 100 to Alice | mints 0 to Carol | 150 |

`sum = 100 + 50 = 150 = total_supply` → check passes. Alice receives 10 extra new tokens; Carol's 10 old tokens are permanently stranded (unredeemable after `nbtc_account_id` is updated to the new token). [3](#0-2) 

---

### Impact Explanation

- The new token's **total supply equals the old token's total supply** — no unbacked inflation occurs.
- However, **individual allocations are wrong**: Alice receives more new tokens than her actual balance at mint time; Carol's tokens are permanently stranded on the old token and cannot be redeemed through the bridge after `nbtc_account_id` is switched.
- This is a publicly reachable invariant violation: the migration guarantee "every holder's new-token balance equals their old-token balance" is broken without any privileged action by the attacker.

---

### Likelihood Explanation

- The attack window is narrow (one or two NEAR blocks between query receipts and callback receipt), but it is deterministic and observable on-chain.
- Any token holder can submit an `ft_transfer` transaction targeting this window; no special role is required.
- Migrations are rare, announced events, making the window predictable.

---

### Recommendation

Lock or snapshot the old token before querying. The safest approach is to **pause the old token** (if it supports pausing) before initiating the migration, or to **burn old-token balances atomically** as part of the mint batch rather than leaving them intact. At minimum, re-query each account's balance inside `migrate_to_new_token_mint` (or use a single atomic cross-contract call that both reads and burns) so that the minted amount reflects the balance at mint time, not at query time.

---

### Proof of Concept

```
1. Deploy old token; mint 100 to Alice, 50 to Bob. Total supply = 150.
2. MigrationOperator calls migrate_to_new_token(new_token, [Alice, Bob]).
3. Query receipts are processed: ft_total_supply()=150, ft_balance_of(Alice)=100, ft_balance_of(Bob)=50.
4. Before the migrate_to_new_token_mint callback receipt executes,
   Alice calls ft_transfer(receiver_id=Carol, amount=10) on the old token.
5. migrate_to_new_token_mint callback executes:
   sum = 100 + 50 = 150 == total_supply → check passes.
   Mints 100 to Alice, 50 to Bob on new token.
6. Assert: new_token.ft_balance_of(Alice) == 100  (should be 90)
           new_token.ft_balance_of(Carol) == 0    (Carol has 10 stranded old tokens)
           new_token.ft_total_supply()    == 150  (correct, but distribution is wrong)
``` [4](#0-3)
