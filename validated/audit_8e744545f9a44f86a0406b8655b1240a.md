Audit Report

## Title
Missing Contract Existence Check in `initTransfer1155` Allows Silent No-Op Token Lock, Enabling Unauthorized NEAR Token Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` calls `IERC1155(tokenAddress).safeTransferFrom(...)` without verifying that `tokenAddress` has deployed code. In Solidity 0.8.x, a high-level call to a void function on an EOA returns `(success=true, returndata="")` and does not revert, because no return-data length check is inserted for functions with no return value. Zero ERC1155 tokens are transferred to the bridge, yet `InitTransfer` is emitted. The NEAR bridge treats any emitted `InitTransfer` from a registered factory as proof that tokens are held, and mints bridged tokens on NEAR against a non-existent EVM escrow, permanently breaking the 1:1 backing invariant.

## Finding Description

**Root cause — no `extcodesize` guard on the ERC1155 call:**

`initTransfer1155` dispatches directly through the `IERC1155` interface:

```solidity
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    tokenId,
    amount,
    ""
);
```

`IERC1155.safeTransferFrom` declares no return value. Solidity only inserts a `returndata.length > 0` check when a function has a return value; for void functions it only checks the `CALL` success flag. A `CALL` to an EOA always returns `(success=true, returndata="")`, so the call completes without reverting. No tokens move. Contrast with `SafeERC20.safeTransferFrom`, which uses `Address.functionCall` and explicitly asserts `address.code.length > 0`.

**Why `onERC1155Received` does not save the bridge:**

For a legitimate ERC1155 transfer, the token contract calls `onERC1155Received(operator=OmniBridge, ...)` on the bridge; the bridge's guard `if (operator != address(this))` passes because OmniBridge is the caller of `safeTransferFrom`. When `tokenAddress` is an EOA, the EOA executes no code, so `onERC1155Received` is never invoked — the guard is entirely bypassed.

**`logMetadata1155` also lacks a contract check:**

`logMetadata1155` stores `tokenAddress` in `multiTokens` and emits `LogMetadata` with no `extcodesize` verification, allowing an EOA to be registered as a valid ERC1155 token address and triggering NEAR-side token deployment.

**NEAR-side processing:**

`fin_transfer_callback` in `near/omni-bridge/src/lib.rs` verifies only that `init_transfer.emitter_address` matches a registered factory (the OmniBridge contract address — which it does) and that `token_decimals` contains the `deterministicToken` address (populated by the prior `logMetadata1155` → `deploy_token` flow). Both checks pass. The callback then calls `process_fin_transfer_to_near`, which mints NEAR-side bridged tokens to the attacker's account.

**Exploit flow:**

1. Attacker calls `logMetadata1155(EOA_address, tokenId)` — permissionless; stores EOA in `multiTokens`, emits `LogMetadata` from the registered OmniBridge factory address.
2. NEAR bridge processes the `LogMetadata` proof via `deploy_token` → `deploy_token_callback`; deploys a NEAR token for `deterministicToken` and populates `token_decimals`.
3. Attacker calls `initTransfer1155(EOA_address, tokenId, amount, 0, 0, "attacker.near", "")` — `IERC1155(EOA).safeTransferFrom(...)` silently succeeds; `InitTransfer` is emitted with `deterministicToken` as the token address.
4. NEAR bridge processes the `InitTransfer` proof via `fin_transfer` → `fin_transfer_callback`; factory check passes, decimals lookup succeeds, tokens are minted to `attacker.near`.

**Violated invariant (from `evm/CLAUDE.md`):**

> *Event–transfer atomicity: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit.*

## Impact Explanation

An unprivileged attacker mints an arbitrary quantity of NEAR-side bridged ERC1155 tokens backed by zero locked EVM tokens. This is unauthorized minting that permanently breaks the 1:1 backing invariant and constitutes direct theft of value from the bridge's liquidity pool when the attacker redeems the unbacked NEAR tokens for real assets on any connected chain. This matches the Critical impact class: *unauthorized minting of bridged funds*.

## Likelihood Explanation

The attack requires no special privileges, no victim interaction, and no external dependencies beyond a funded EVM account. Both `logMetadata1155` and `initTransfer1155` are fully permissionless public functions. The attack is repeatable with any fresh EOA address and any `tokenId`, producing a new `deterministicToken` each time. The only cost is gas and the NEAR storage deposit for `deploy_token`.

## Recommendation

Add an `extcodesize` check before the `safeTransferFrom` call in `initTransfer1155` (and symmetrically in `logMetadata1155`):

```solidity
require(tokenAddress.code.length > 0, "ERC1155: not a contract");
```

Alternatively, use OpenZeppelin's `Address.functionCall` wrapper, which performs this check internally, or add an ERC-165 `supportsInterface(IERC1155_ID)` call that will revert against an EOA.

## Proof of Concept

**Hardhat test outline:**

```typescript
it("mints NEAR tokens with zero ERC1155 locked via EOA tokenAddress", async () => {
  const eoaAddress = ethers.Wallet.createRandom().address; // no code
  const tokenId = 1n;
  const amount = 100n;

  // Step 1: register EOA as ERC1155 token — succeeds, no contract check
  await bridge.logMetadata1155(eoaAddress, tokenId);

  const deterministicToken = await bridge.deriveDeterministicAddress(eoaAddress, tokenId);

  // Step 2: initTransfer1155 with EOA — safeTransferFrom silently no-ops
  await expect(
    bridge.connect(attacker).initTransfer1155(
      eoaAddress, tokenId, amount, 0, 0, "attacker.near", ""
    )
  ).to.emit(bridge, "InitTransfer")
   .withArgs(attacker.address, deterministicToken, 1, amount, 0, 0, "attacker.near", "");

  // Confirm zero tokens held by bridge
  // (no ERC1155 contract exists at eoaAddress, so no balanceOf to check)
  // The emitted InitTransfer event is sufficient for the NEAR bridge to mint tokens
});
```

The emitted `InitTransfer` event from the registered OmniBridge factory address is sufficient for the NEAR prover to generate a valid `ProverResult::InitTransfer`, which `fin_transfer_callback` will accept and use to mint tokens.
