### Title
Unchecked Subtraction Before Gas-Fee Bounds Check Causes Panic-Revert in Withdrawal Path — (File: `contracts/satoshi-bridge/src/psbt.rs`)

### Summary
In `check_withdraw_psbt`, three bare subtractions execute before the gas-fee range check. Because `overflow-checks = true` is set in the workspace profile, any underflow panics immediately. A user who submits a `Withdraw` message whose output values exceed the selected UTXO inputs triggers the panic at line 238, reverting the entire `ft_on_transfer` call. The gas-fee bounds check that would have caught the invalid values only appears at line 252 — after the arithmetic has already been evaluated.

### Finding Description

`check_withdraw_psbt` computes three values with unchecked subtraction:

```rust
// psbt.rs line 238
let gas_fee = total_input_amount - total_output_amount;

// psbt.rs line 242
let max_received_amount = amount - withdraw_fee - gas_fee;

// psbt.rs line 243
let min_received_amount = max_received_amount - config.min_change_amount;
```

The guard that would bound `gas_fee` to a safe range appears only at lines 252–258:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, ...
);
```

Because `overflow-checks = true` is compiled into every release build (Cargo.toml line 27), any of the three subtractions panics instead of wrapping. The user-controlled `output: Vec<TxOut>` field in `TokenReceiverMessage::Withdraw` is summed into `total_output_amount` (line 194) with no upper-bound check before line 238. Setting the user-output value above `total_input_amount` makes `total_output_amount > total_input_amount`, triggering the underflow panic.

The call chain is fully public:

```
nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)
  → bridge.ft_on_transfer(sender, amount, msg)          [token_receiver.rs:23]
    → Contract::create_btc_pending_info(...)             [token_receiver.rs:71]
      → Contract::check_withdraw_psbt_valid(...)         [token_receiver.rs:90]
        → Contract::check_withdraw_psbt(...)             [psbt.rs:164]
          → line 238: total_input_amount - total_output_amount  ← PANIC
```

### Impact Explanation
The panic reverts the `ft_on_transfer` call. Under NEP-141 semantics the token transfer is rolled back and the user's nBTC is returned, so there is no fund loss. However, the panic surfaces as an opaque runtime error rather than a descriptive `require!` message, and any legitimate user whose dApp miscalculates output values receives the same confusing failure. This is a publicly reachable panic-driven fault in the production withdrawal path without direct theft.

**Severity: Low** — matches "Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."

### Likelihood Explanation
Any NEAR account holding nBTC can reach this path by calling `ft_transfer_call` with a crafted `Withdraw` message. No privileged role is required. The trigger is a single output value set above the selected UTXO total, which is trivially constructable.

### Recommendation
Move the gas-fee bounds check to immediately after line 238, before the dependent subtractions at lines 242–243:

```rust
let gas_fee = total_input_amount - total_output_amount;
// Validate gas_fee BEFORE using it in further subtractions
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({}). valid range: [{}, {}].",
            gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee)
);
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
```

Additionally, consider using `checked_sub` for lines 242–243 to produce clear error messages rather than opaque panics, consistent with the project's own arithmetic-safety guidance (CLAUDE.md line 69).

### Proof of Concept

1. Alice holds 10,000 sat worth of nBTC.
2. The bridge has a UTXO of 10,000 sat.
3. Alice calls `nbtc.ft_transfer_call(bridge, 10_000, json(Withdraw { target_btc_address: ALICE_ADDR, input: [utxo_outpoint], output: [TxOut { value: 20_000, script_pubkey: alice_script }], max_gas_fee: None, chain_specific_data: None }))`.
4. `ft_on_transfer` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`.
5. `total_input_amount = 10_000`, `total_output_amount = 20_000`.
6. Line 238: `10_000u128 - 20_000u128` underflows → runtime panic (overflow-checks = true).
