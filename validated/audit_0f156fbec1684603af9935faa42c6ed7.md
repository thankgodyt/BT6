Audit Report

## Title
Missing Normalization Check in `init_transfer` Permanently Freezes Dust Amounts — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` stores a pending transfer after only verifying `fee.fee < amount`, without checking whether `normalize_amount(amount − fee, decimals) > 0`. When the net amount rounds to zero under floor-division normalization (e.g., a 24-decimal NEAR token bridging to an 18-decimal EVM token), every subsequent `sign_transfer` call reverts with `InvalidAmountToTransfer`. No user-accessible cancellation path exists, so the deposited tokens are permanently locked in the bridge contract.

## Finding Description

In `ft_on_transfer`, the bridge dispatches to `init_transfer`, which constructs a `TransferMessage` and applies a single amount guard:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

This passes for any `amount = 1, fee = 0`. The transfer is then stored in `pending_transfers` and the function returns `U128(0)` to the NEP-141 runtime (via `init_transfer_internal`), meaning zero tokens are refunded to the caller — the full amount is retained by the bridge.

Later, `sign_transfer` performs the normalization check that `init_transfer` omits:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` performs integer floor-division by `10^(origin_decimals − decimals)`. For a token with `origin_decimals = 24` and `decimals = 18`, any `amount_without_fee < 10^6` produces zero. The `require!` then panics on every signing attempt.

The only other mutation paths for a pending transfer are:
- `update_transfer_fee` — can only increase the fee (L400: `fee.fee >= current_fee.fee`), cannot change the principal amount, and cannot unblock a zero-normalized transfer.
- `sign_transfer_callback` — only removes the transfer record after a *successful* MPC signature, which is unreachable here.
- `claim_fee_callback` — requires a proof from the destination chain, which is never generated because signing never succeeds.

No public `cancel_transfer` function exists (confirmed by exhaustive search). The only privileged escape hatch is `transfer_token_as_dao` (L1511–1530), which requires the DAO role and is not a user-accessible recovery path.

## Impact Explanation

This directly matches the critical impact class: **permanent freezing of bridged funds**. The user's tokens are transferred into the bridge at `ft_transfer_call` time. Because `ft_on_transfer` returns `U128(0)`, the NEP-141 runtime does not refund them. The transfer record sits in `pending_transfers` indefinitely with no user-reachable path to recover the funds. The DAO `transfer_token_as_dao` escape hatch requires privileged intervention and is not a systematic fix.

## Likelihood Explanation

Reachable by any unprivileged user via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow. No special role or privilege is required. The condition is easily triggered for any token pair with a decimal gap (e.g., wNEAR: 24 decimals on NEAR, 18 on EVM; gap = 6, so any `amount_without_fee < 1_000_000` yocto-units normalizes to zero). Frontend rounding errors or deliberate dust sends are realistic triggers.

## Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before storing the transfer message. Retrieve the destination token's `Decimals` and assert `normalize_amount(amount − fee, decimals) > 0`. If the check fails, return the full `amount` to the caller via the NEP-141 return value rather than storing an unsignable transfer:

```rust
// After the fee check in init_transfer:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let net = transfer_message.amount_without_fee()
            .near_expect(BridgeError::InvalidFee);
        require!(
            Self::normalize_amount(net, decimals) > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );
    }
}
```

When the check fails, the function should return `amount` (the full deposited value) so the NEP-141 runtime refunds the caller.

## Proof of Concept

1. A NEAR token `wNEAR` is registered with `origin_decimals = 24`, `decimals = 18` for the Ethereum destination.
2. Alice calls `ft_transfer_call` on `wNEAR` with `amount = 500_000` and `msg = InitTransfer { fee: 0, recipient: Eth(0x...) }`.
3. `ft_on_transfer` → `init_transfer`: the check `0 < 500_000` passes; the transfer is stored; `U128(0)` is returned, locking Alice's 500,000 yocto-wNEAR in the bridge.
4. A relayer calls `sign_transfer`. `normalize_amount(500_000, {decimals:18, origin_decimals:24})` = `500_000 / 10^6 = 0`.
5. `require!(0 > 0)` panics with `InvalidAmountToTransfer`. The call reverts.
6. Steps 4–5 repeat for every relayer attempt. `update_transfer_fee` cannot help (it cannot reduce the amount or change `origin_decimals`). Alice has no `cancel_transfer` to call. Her 500,000 yocto-wNEAR are permanently frozen.

A local unit test can reproduce this by: (a) registering a token with mismatched decimals, (b) calling `ft_on_transfer` with a dust amount, (c) asserting the transfer is stored, and (d) asserting `sign_transfer` panics with `InvalidAmountToTransfer` on every invocation.
