Audit Report

## Title
Missing Chain ID Binding in `deployToken` Signature Enables Cross-Chain Replay — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

The `deployToken` function in `OmniBridge.sol` constructs its borsh-encoded signed payload without including `omniBridgeChainId`. Because all deployed OmniBridge instances share the same `nearBridgeDerivedAddress`, a valid MPC-signed metadata signature produced for chain A is cryptographically indistinguishable from one intended for chain B. An attacker can replay any observed `deployToken` call across all other OmniBridge instances, causing unauthorized token deployment and corrupting the `nearToEthToken` mapping on those chains.

## Finding Description

In `deployToken`, the signed payload is:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
``` [1](#0-0) 

`omniBridgeChainId` is never included. The `MetadataPayload` struct itself carries no chain-scoping field: [2](#0-1) 

By contrast, `finTransfer` explicitly embeds `omniBridgeChainId` twice in its signed payload: [3](#0-2) 

The only post-signature guards in `deployToken` are:
1. `ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress` — identical on all chains sharing the same MPC key.
2. `!isBridgeToken[nearToEthToken[metadata.token]]` — only prevents re-deployment on the **same** chain instance. [4](#0-3) 

There is no nonce, no destination-chain field, and no contract-address binding in the metadata payload. The same flaw exists in the Starknet implementation, where `MetadataPayload.to_borsh()` also omits chain ID: [5](#0-4) 

While `TransferMessagePayload.to_borsh()` in Starknet correctly includes `chain_id` twice: [6](#0-5) 

The Solana `deploy_token` similarly passes `()` (no chain context) to `verify_signature`, unlike `finalize_transfer` which passes mint and recipient keys: [7](#0-6) 

**Exploit path:**
1. Attacker observes a legitimate `deployToken(signatureData, metadata)` transaction on chain A (e.g., Arbitrum).
2. Attacker submits the identical `(signatureData, metadata)` to chain B (e.g., Base).
3. `ECDSA.recover` succeeds because the digest is identical — `omniBridgeChainId` is absent.
4. `nearToEthToken[metadata.token]` on chain B is unset, so the `ERR_TOKEN_EXIST` guard passes.
5. A new `ERC1967Proxy` is deployed and registered in `nearToEthToken` on chain B without MPC ever authorizing a deployment for chain B.
6. Any subsequent legitimate `finTransfer` calls on chain B for that token will mint against this attacker-triggered proxy, creating token supply that NEAR MPC never explicitly authorized for chain B.

## Impact Explanation

This is a **chain/domain separation flaw enabling unauthorized token deployment and token metadata binding confusion**. The `nearToEthToken` mapping on chain B is permanently poisoned: the legitimate deployment is blocked by `ERR_TOKEN_EXIST`, and any NEAR-side transfers routed to chain B will mint against the replayed proxy. This constitutes unauthorized minting of bridged funds and token metadata binding confusion that changes protocol balances — matching the Critical allowed impact scope.

## Likelihood Explanation

The precondition — multiple OmniBridge instances sharing the same `nearBridgeDerivedAddress` — is the **intended production deployment topology**. The `omniBridgeChainId` field exists precisely to differentiate these instances but is unused in `deployToken`. Any publicly observable `deployToken` transaction on one chain is immediately replayable on all others by any unprivileged external user. No privileged access, leaked keys, or MPC collusion is required.

## Recommendation

Include `omniBridgeChainId` in the borsh-encoded payload verified in `deployToken`, mirroring the pattern already used in `finTransfer`:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    bytes1(omniBridgeChainId),          // add this
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

The NEAR MPC signing logic must be updated in lockstep to include the destination chain ID when producing metadata signatures. The same fix must be applied to the Starknet `MetadataPayload.to_borsh()` and the Solana `deploy_token` `verify_signature` call.

## Proof of Concept

The PoC provided in the submission is sound. Two `OmniBridge` instances are initialized with the same `nearBridgeDerivedAddress` but different `omniBridgeChainId` values (1 and 2). A signature produced for chain A passes `ECDSA.recover` on chain B because the digest is identical — `omniBridgeChainId` is absent from the signed payload. The `ERR_TOKEN_EXIST` guard on chain B passes because `nearToEthToken["wrap.testnet"]` is unset there. The call succeeds, deploying an unauthorized token proxy on chain B and setting `nearToEthToken["wrap.testnet"]` to it, blocking any future legitimate deployment for that token on chain B.
