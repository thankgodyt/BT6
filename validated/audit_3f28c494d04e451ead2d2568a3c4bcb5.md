### Title
Missing `consensus_branch_id` Validation in Zcash Transaction Decoder Allows Cross-Network Replay — (File: `contracts/satoshi-bridge/src/zcash_utils/transaction.rs`)

---

### Summary

The Zcash `Transaction::decode` function ignores its `_chain` parameter entirely and hardcodes `BranchId::Nu6_2`. After decoding, the bridge never validates that the `consensus_branch_id` embedded in the submitted Zcash V5 transaction matches the bridge's configured chain. This is the direct analog of the reported Shardeum `chainId` omission: the bridge accepts any Zcash transaction regardless of which network it was signed for, relying solely on the external light client for network discrimination.

---

### Finding Description

In Zcash V5 transactions (ZIP-225), the `consensus_branch_id` is encoded in the transaction header and cryptographically binds the transaction to a specific network upgrade and chain (mainnet vs. testnet). It is the Zcash equivalent of Ethereum's `chainId`.

The bridge's Zcash transaction decoder is:

```rust
// contracts/satoshi-bridge/src/zcash_utils/transaction.rs, lines 51-56
pub fn decode(data: &[u8], _chain: &network::Chain) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    let branch_id = BranchId::Nu6_2;          // hardcoded, chain ignored
    let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
    Ok(Self { inner_tx: tx })
}
``` [1](#0-0) 

The `_chain` parameter (note the underscore) is never used. For Zcash V5 transactions, `ZCashTransaction::read` reads the actual `consensus_branch_id` from the transaction bytes — the hardcoded `Nu6_2` hint is irrelevant for V5 parsing. The decoded `inner_tx` therefore carries whatever `consensus_branch_id` was in the submitted bytes, and the bridge never inspects it.

After decoding, the deposit entry points (`internal_verify_deposit_entry`, `internal_safe_verify_deposit_entry`) only check:

1. `deposit_amount > 0`
2. `transaction.output()[vout].script_pubkey == deposit_address_script_pubkey` [2](#0-1) 

Neither check involves the `consensus_branch_id`. The same omission exists in `internal_request_refund`: [3](#0-2) 

The bridge's `Chain` enum correctly distinguishes `ZcashMainnet` from `ZcashTestnet`: [4](#0-3) 

And `get_branch_id` correctly maps chain + block height to the right `BranchId`: [5](#0-4) 

But this logic is never applied to *validate incoming* transaction bytes — only to *construct outgoing* transactions (in `PsbtWrapper`). [6](#0-5) 

---

### Impact Explanation

A Zcash testnet transaction sent to a deposit address whose `script_pubkey` matches the mainnet bridge's deposit address (P2PKH `script_pubkey` is network-agnostic — it is `OP_DUP OP_HASH160 <hash> OP_EQUALVERIFY OP_CHECKSIG` regardless of mainnet/testnet) would pass the bridge contract's own validation entirely. The bridge contract provides **zero** defense-in-depth against cross-network replay. The only protection is the external `btc_light_client` contract, which is network-specific.

If the light client is misconfigured, compromised, or replaced (e.g., during a migration or upgrade), an attacker can submit a Zcash testnet transaction to a mainnet bridge and trigger unauthorized nZEC minting without depositing real mainnet ZEC. This matches the allowed impact: **Zcash-specific validation failure that enables unauthorized mint**.

---

### Likelihood Explanation

Under normal operation the light client blocks cross-network proofs, so exploitation requires the light client to also fail. However, the bridge contract is the last line of defense for a critical invariant (submitted transactions must belong to the configured chain), and it provides none. The risk is elevated during contract upgrades, light client migrations, or operator misconfiguration — all realistic operational events for a live bridge.

---

### Recommendation

After decoding, assert that the transaction's `consensus_branch_id` is consistent with the bridge's configured chain. Add a helper such as:

```rust
pub fn decode(data: &[u8], chain: &network::Chain) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    // For V5 the branch_id hint is unused; pass a sentinel.
    let tx = ZCashTransaction::read(&mut cursor, BranchId::Nu6_2)?;
    // Validate the branch_id embedded in the decoded transaction.
    let actual = tx.consensus_branch_id();
    let valid_ids = valid_branch_ids_for_chain(chain); // Nu6/Nu6_1/Nu6_2 for mainnet, etc.
    if !valid_ids.contains(&actual) {
        return Err(std::io::Error::new(
            std::io::ErrorKind::InvalidData,
            format!("consensus_branch_id {actual:?} does not match chain {chain:?}"),
        ));
    }
    Ok(Self { inner_tx: tx })
}
```

This mirrors EIP-155's requirement that `chainId` be checked before executing a transaction.

---

### Proof of Concept

1. Deploy the bridge configured for `ZcashMainnet`.
2. Obtain the deposit address for a `DepositMsg` (e.g., `recipient_id = alice.near`). The underlying P2PKH `script_pubkey` is identical on mainnet and testnet for the same MPC-derived key.
3. On **Zcash testnet**, send ZEC to that same P2PKH address (same bytes, different network prefix in display form only).
4. Call `verify_deposit_v2` on the mainnet bridge with the testnet `tx_bytes` and a fabricated/testnet proof.
5. `Transaction::decode` succeeds — the testnet `consensus_branch_id` is read from the bytes and stored in `inner_tx`, but never checked.
6. The `script_pubkey` comparison passes (P2PKH hash is network-agnostic).
7. The call proceeds to `verify_transaction_inclusion_promise` — the only gate that would reject it is the light client. If the light client is absent, misconfigured, or accepts the proof, nZEC is minted for free. [1](#0-0) [7](#0-6)

    pub fn get_branch_id(&self, block_height: u32) -> BranchId {

    }
