Audit Report

## Title
Missing `multiTokens` Registration Check in `initTransfer1155` Allows Permanent Freezing of ERC-1155 Tokens - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`initTransfer1155` accepts and locks any ERC-1155 token without verifying that the `(tokenAddress, tokenId)` pair has been previously registered via `logMetadata1155`. Because `finTransfer` only releases ERC-1155 tokens when `multiTokens[deterministicToken].tokenAddress != address(0)`, tokens bridged before registration are permanently unrecoverable on-chain.

## Finding Description

`logMetadata1155` (L243–255) is the only function that populates `multiTokens[deterministicToken]`. It sets `multiToken.tokenAddress` and `multiToken.tokenId` on first call and reverts on collision. `initTransfer1155` (L439–490) computes the same `deterministicToken` (L453–456) and immediately calls `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), ...)` (L458–464) with no guard on `multiTokens[deterministicToken].tokenAddress`. The `onERC1155Received` hook (L522–535) only rejects transfers where `operator != address(this)`; since `initTransfer1155` itself issues the `safeTransferFrom`, `operator` equals `address(this)` and the hook accepts the transfer. In `finTransfer` (L315–355), the ERC-1155 release branch at L323 is only entered when `multiToken.tokenAddress != address(0)`. If the mapping is zero, execution falls through to `IERC20(deterministicToken).safeTransfer(...)` (L351), which reverts because `deterministicToken` is a hash-derived address with no ERC-20 code. No refund or rescue function for ERC-1155 tokens exists anywhere in the contract.

## Impact Explanation

Any unprivileged caller who invokes `initTransfer1155` for an unregistered `(tokenAddress, tokenId)` pair causes their ERC-1155 tokens to be permanently locked in the bridge with no on-chain recovery path. This is a concrete instance of **permanent freezing of bridged funds**, which is an explicitly listed Critical impact in the allowed scope.

## Likelihood Explanation

`initTransfer1155` is fully permissionless and requires no special role. The `logMetadata1155` prerequisite is enforced only by off-chain convention; the contract imposes no ordering constraint. A user unfamiliar with the two-step flow, using a different `tokenId` than the one previously registered, or interacting directly with the contract (e.g., via a script or block explorer) will trigger the freeze without any on-chain warning. The scenario is repeatable for every distinct `(tokenAddress, tokenId)` pair.

## Recommendation

Add a registration guard at the top of `initTransfer1155`, before the `safeTransferFrom` call:

```solidity
address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
if (multiTokens[deterministicToken].tokenAddress == address(0)) {
    revert ERC1155NotRegistered();
}
```

This mirrors the collision check already present in `logMetadata1155` and ensures the NEAR side always has a registered token before EVM-side custody is taken.

## Proof of Concept

1. Deploy any ERC-1155 contract; mint `amount` tokens to `attacker`.
2. Call `bridge.initTransfer1155(erc1155Addr, tokenId, amount, 0, 0, "victim.near", "")` **without** a prior `bridge.logMetadata1155(erc1155Addr, tokenId)` call.
3. `safeTransferFrom` succeeds; `amount` tokens are now held by the bridge. `multiTokens[deterministicToken]` remains zero.
4. The NEAR relayer observes the `InitTransfer` event but finds no registered token for `deterministicToken`; the NEAR-side transfer fails and no signed `finTransfer` payload is produced.
5. If a `finTransfer` payload were somehow constructed with `payload.tokenAddress = deterministicToken`, execution reaches L351 (`IERC20(deterministicToken).safeTransfer(...)`) and reverts because `deterministicToken` has no ERC-20 code.
6. Tokens are permanently locked with no recovery path.
