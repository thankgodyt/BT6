### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production default instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right` — it accepts every inbound Peras certificate without any cryptographic or structural check. This instance is wired directly into the live node-to-node `PerasCertDiffusion` mini-protocol handler. Any unprivileged peer can therefore inject a crafted certificate boosting an arbitrary block, causing the victim node to trigger chain selection with inflated weight for that block and potentially switch to a non-canonical fork.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub in the universal instance:** [1](#0-0) 

The comment explicitly marks this as a "degenerate instance for all blks to get things to compile." The implementation:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

performs zero validation — no committee membership check, no BLS aggregate signature verification, no VRF eligibility proof, no quorum check. Every certificate, regardless of content, is returned as `ValidatedPerasCert` with the full configured `perasWeight`.

**Production wiring — this stub is the live inbound handler:**

`makePerasCertPoolWriterFromChainDB` is the production pool writer used for inbound peer certificates: [2](#0-1) 

It passes `validatePerasCert mkPerasParams` directly as the validation function to `processCerts`. Since `validatePerasCert` always returns `Right`, `processCerts` will always reach the "all certs are valid" branch and call `addCert` for every inbound certificate.

**This writer is wired into the live node-to-node protocol stack:** [3](#0-2) 

`hPerasCertDiffusionClient` calls `makePerasCertPoolWriterFromChainDB systemTime getChainDB` — this is the handler executed for every inbound Peras certificate from every connected peer.

**Accepted certificates trigger chain selection with boosted weight:** [4](#0-3) 

`chainSelSync` for `ChainSelAddPerasCert` adds the certificate to `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block. Chain selection uses `preferAnchoredCandidate` with the `PerasWeightSnapshot`, where the injected certificate's boost is added to the total weight of any chain containing the boosted block: [5](#0-4) 

A fork whose tip block is boosted by an attacker-injected certificate can therefore appear heavier than the honest canonical chain, causing the node to switch.

**Exploit flow:**

1. Attacker connects to a victim node as a normal peer (no special privileges required).
2. Attacker sends a crafted `PerasCert` message via the `PerasCertDiffusion` mini-protocol, specifying any `pcCertRound` and `pcCertBoostedBlock` pointing to a block on the attacker's fork.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The certificate is timestamped and passed to `ChainDB.addPerasCertAsync`.
5. `chainSelSync` adds it to `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` computes the attacker's fork as heavier due to the injected boost.
7. The node switches to the attacker's fork.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker with no stake and no cryptographic keys can cause a victim node to abandon the canonical chain and adopt an attacker-controlled fork. The `perasWeight` boost (e.g., 15 as seen in benchmarks) can exceed the block-count difference between the canonical chain and a shorter fork, making the fork appear heavier. This directly violates the Peras security invariant that only certificates backed by a quorum of eligible committee members should influence chain selection.

---

### Likelihood Explanation

Any peer that successfully negotiates the Peras-enabled node-to-node protocol version can send `PerasCert` messages. No stake, no keys, and no prior relationship with the victim node are required. The attacker only needs to know a valid block hash on a competing fork (observable from the public chain). The attack is deterministic and repeatable.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real check that verifies:
1. The certificate's aggregate BLS signature against the declared committee members' verification keys.
2. That the declared voters form a quorum (total stake ≥ threshold).
3. That each voter's VRF output proves eligibility for the claimed round.

Until the full cryptographic validation is implemented, the `PerasCertDiffusion` inbound handler should be disabled or gated behind a feature flag so that no peer-supplied certificate can influence chain selection. [6](#0-5) 

---

### Proof of Concept

**Private-testnet reproduction:**

1. Start two nodes (`A` = honest, `B` = attacker) on a private testnet with Peras protocol version negotiated.
2. Let both nodes sync to the same tip on the canonical chain.
3. From node `B`, craft a `PerasCert` CBOR message:
   - `pcCertRound`: any round number not yet in node `A`'s `PerasCertDB`
   - `pcCertBoostedBlock`: the tip of a shorter fork known to node `A`
4. Send this message to node `A` via the `PerasCertDiffusion` inbound channel.
5. `processCerts` on node `A` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{vpcCertBoost = perasWeight params}`.
6. `addPerasCertAsync` enqueues the certificate; `chainSelSync` triggers chain selection.
7. `preferAnchoredCandidate` computes the fork's total weight as `blockNo + perasWeight` vs. the canonical chain's `blockNo`; if the boost exceeds the block-count gap, node `A` switches to the fork.
8. Observe node `A`'s tip has moved to the attacker's fork without any legitimate quorum of committee votes. [7](#0-6)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
