### Title
Sub-Minimum BTC Deposits Permanently Locked When Deposit Amount Cannot Cover Refund Gas Fee - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user sends BTC to a bridge deposit address with an amount below `min_deposit_amount`, the bridge stores the UTXO as "unavailable" and mints no nBTC. The only recovery path is the refund system, but `request_refund_callback` hard-rejects any refund where `gas_fee >= amount`. For deposits small enough that the BTC transaction fee exceeds the deposit value, the user's BTC is permanently locked with no recovery mechanism.

### Finding Description
The deposit flow in `internal_verify_deposit` branches on `deposit_amount < config.min_deposit_amount`: [1](#0-0) 

When the amount is below the minimum, the UTXO is stored in the `unavailable_utxos` map via `unavailable_utxo_callback` — no nBTC is minted and the UTXO is not placed in the spendable `utxos` pool used by UTXO management.

The only recovery path for such a deposit is the refund system. However, `request_refund_callback` enforces: [2](#0-1) 

If `resolved_gas_fee >= amount`, the callback panics and the refund request is never stored. The `resolved_gas_fee` defaults to `get_refund_gas_fee()` (bounded below by `min_btc_gas_fee`) or is supplied by the caller, but the caller cannot set it below the actual BTC transaction fee needed to broadcast the refund.

The `unavailable_utxos` map is a dead-end store: active and passive UTXO management operate exclusively on the `utxos` map: [3](#0-2) 

There is no code path that moves an entry from `unavailable_utxos` back into `utxos`, nor any operator function to sweep or consolidate unavailable UTXOs. The `unhealthy_utxo_amount` consolidation threshold applies only to entries already in the spendable pool. [4](#0-3) 

### Impact Explanation
Any BTC deposit whose satoshi value is less than or equal to the BTC transaction fee required for a refund transaction is permanently locked. The bridge controls the deposit address via MPC chain signatures; the user has no key to spend the UTXO independently. The funds cannot be minted, refunded, or swept by any existing code path. This constitutes permanent locking of user funds.

### Likelihood Explanation
The bridge cannot prevent users from sending arbitrary amounts to derived deposit addresses — the address is derived from the user's NEAR account and is publicly computable. A user who accidentally sends dust (e.g., a wallet that rounds down, a test transaction, or a fee-estimation error) lands in this zone. With `min_deposit_amount` set to 20 000 satoshis in the test configuration and `min_btc_gas_fee` at 10 000 satoshis, any deposit in the range [1, 10 000] satoshis is permanently unrecoverable. As BTC fee rates rise, the stuck zone expands upward toward `min_deposit_amount`, potentially trapping deposits worth tens of dollars. [5](#0-4) 

### Recommendation
1. In `request_refund_callback`, when `gas_fee >= amount`, instead of panicking, store the refund request with `gas_fee = amount - 1` (i.e., the user receives 1 satoshi) or with `gas_fee = amount` and `refund_amount = 0`, and allow a privileged operator to finalize such requests by absorbing the gas cost from the protocol fee pool.
2. Alternatively, add an operator-callable `sweep_unavailable_utxo` that moves entries from `unavailable_utxos` into the spendable `utxos` pool so they can be consolidated via active UTXO management, with the proceeds credited to the original depositor's `lost_found` balance.
3. Document the stuck zone explicitly and consider lowering `min_deposit_amount` to be no greater than `min_btc_gas_fee` so that every deposit that fails the minimum check is at least refundable.

### Proof of Concept
1. Alice derives her bridge deposit address from her NEAR account ID.
2. Alice sends 5 000 satoshis to that address (below `min_deposit_amount = 20 000`).
3. A relayer calls `verify_deposit`; the bridge routes to `unavailable_utxo_callback` and stores the UTXO in `unavailable_utxos`. No nBTC is minted.
4. Alice calls `request_refund` with the deposit transaction and `gas_fee = None` (defaults to `get_refund_gas_fee()` which returns, say, 10 000 satoshis).
5. `request_refund_callback` evaluates `10 000 < 5 000` → **false** → panics with `"Gas fee must be less than deposit amount"`.
6. Alice tries again with `gas_fee = Some(4 999)` (just under her deposit). The refund PSBT is built, but the resulting BTC transaction pays only 1 satoshi to Alice and 4 999 satoshis as fee — economically irrational; no relayer will broadcast it, and even if broadcast, the 1-satoshi output is below Bitcoin's dust limit and will be rejected by miners.
7. Alice's 5 000 satoshis remain permanently locked in the bridge's MPC-controlled deposit address with no recovery path. [6](#0-5)
