Audit Report

## Title
Unguarded State Mutation Before Cross-Contract Fee Transfer Permanently Freezes Fee Tokens — (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `claim_fee_callback`, `remove_transfer_message` and `unlock_tokens_if_needed` execute and commit to state before the `ft_transfer` cross-contract call is dispatched. Because NEAR cross-contract calls execute in separate receipts, a failed `ft_transfer` (e.g., fee recipient not registered in the token contract) does not revert the already-committed state mutations. The fee tokens remain in the bridge's fungible-token balance with no automatic recovery path and no re-claimable transfer record.

## Finding Description

`claim_fee_callback` executes the following sequence in a single receipt:

1. **L1094** — `self.remove_transfer_message(fin_transfer.transfer_id)` permanently deletes the pending transfer record from `pending_transfers`.
2. **L1133** — `self.send_fee_internal(...)` is called, which at **L2684** calls `self.unlock_tokens_if_needed(...)`, decrementing `locked_tokens`.
3. **L2693–2697** — For non-deployed tokens, `ext_token::ext(token).ft_transfer(fee_recipient, ...)` is returned as a `PromiseOrValue::Promise`. There is **no `.then(callback)` chained** to this promise.

```rust
// near/omni-bridge/src/lib.rs L2693-2697
ext_token::ext(token)
    .with_static_gas(FT_TRANSFER_GAS)
    .with_attached_deposit(ONE_YOCTO)
    .ft_transfer(fee_recipient, U128(token_fee), None)
    .into()
```

If `ft_transfer` panics in its own receipt (e.g., because the fee recipient has no storage deposit in the token contract), NEAR's receipt model does not roll back the prior receipt's state. The result is:
- The transfer record is gone — `claim_fee` cannot be retried.
- `locked_tokens` is decremented — the bridge's accounting no longer tracks these tokens as locked.
- The fee tokens remain in the bridge's FT balance with no function to recover them.

Compare this to `fin_transfer_send_tokens_callback` (L1692–1746), which correctly handles failure by checking `is_refund_required` and calling `revert_lock_actions` before dispatching the fee transfer with `.detach()`. `claim_fee_callback` has no equivalent guard.

The `claim_fee` entry point is gated by `#[trusted_relayer]`, but the trusted-relayer system is open: any account can apply by staking NEAR and waiting a configurable period. A legitimate relayer may simply not have called `storage_deposit` on a particular token contract before claiming fees.

## Impact Explanation

Fee tokens that were legitimately locked in the bridge as part of a cross-chain transfer are permanently frozen in the bridge's fungible-token balance. The `locked_tokens` counter is also under-counted, creating a persistent accounting discrepancy. No public function exists to re-initiate the fee claim or recover the stuck tokens. This constitutes **permanent freezing of bridged funds**, matching the Critical impact class.

## Likelihood Explanation

Any active trusted relayer who has not registered (via `storage_deposit`) in a given token contract can trigger this by calling `claim_fee` for a transfer denominated in that token. The relayer controls the call and the condition is easy to satisfy inadvertently, especially for newly bridged tokens. The scenario is repeatable for every unregistered token/relayer combination.

## Recommendation

Chain a recovery callback after the `ft_transfer` promise, analogous to the pattern used in `fin_transfer_send_tokens_callback`. On failure, the callback should re-insert the transfer message and re-increment `locked_tokens`. Alternatively, perform the state mutations only inside a success callback, keeping the transfer record intact until the fee transfer is confirmed. Also consider requiring the caller to provide a storage-deposit action for the fee recipient (as `fin_transfer` does for the transfer recipient) before dispatching the fee transfer.

## Proof of Concept

1. Deploy the bridge and a standard NEP-141 token contract on a local sandbox.
2. Register a trusted relayer (stake NEAR, wait past the activation period). Do **not** call `storage_deposit` for the relayer on the token contract.
3. Initiate and finalize a cross-chain transfer to a non-NEAR chain so a `TransferMessage` with a non-zero fee is stored and `locked_tokens` is incremented.
4. Call `claim_fee` from the relayer account with a valid proof.
5. Observe: `claim_fee_callback` succeeds (transfer record deleted, `locked_tokens` decremented), but the subsequent `ft_transfer` receipt fails with a storage-not-registered panic.
6. Verify: `get_transfer_message` returns nothing (record gone), `get_locked_tokens` shows the decremented value, and the token balance of the bridge contract still holds the fee amount — confirming permanent freeze.
