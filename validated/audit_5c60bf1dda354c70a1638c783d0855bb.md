### Title
Unconditional `validatePerasCert` Stub Allows Peer-Crafted Certificates to Manipulate Peras Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing no cryptographic or semantic checks. This stub is wired directly into the production certificate-ingest path. An unprivileged peer can send a batch of crafted `PerasCert` messages — each claiming a distinct round number but all boosting the same fork block — and every one will be accepted. Because `addToPerasWeightSnapshot` accumulates weight additively per block point, the targeted block accrues unbounded Peras weight, causing the node to prefer a non-canonical chain.

---

### Finding Description

`validatePerasCert` is declared in the `BlockSupportsPeras` typeclass and is supposed to verify an inbound certificate's aggregate BLS signature, committee membership of all claimed voters, and the correspondence between the claimed voters and the actual votes cast in that round. The universal instance, however, is a stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

This stub is the only `BlockSupportsPeras` instance in the codebase (the comment on line 318 confirms it is the "degenerate instance for all blks"). [2](#0-1) 

The production certificate-ingest path calls this stub directly. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`: [3](#0-2) 

`processCerts` deduplicates only by round number (one cert per round), then calls `validateCert` on each new cert. Since `validatePerasCert` always returns `Right`, every cert whose round number is not already in the DB is accepted unconditionally: [4](#0-3) 

Each accepted certificate is forwarded to `chainSelSync`, which adds it to the `PerasCertDB` and triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

The weight snapshot accumulates boosts additively per block point via `Map.insertWith (<>)`: [6](#0-5) 

Chain selection then compares fragments by total weight (block number + accumulated boost): [7](#0-6) 

**Analog to the reported vulnerability:**

| Original (MetaVesT) | Analog (Ouroboros Consensus) |
|---|---|
| Consent applied to new set members who never voted | Certificate accepted without verifying that the claimed voters actually participated in the voting round for that block (no BLS aggregate signature check, no committee membership check) |
| Consent applied unlimited times to the same proposal | Peer sends N certificates for N distinct rounds all boosting the same fork block; deduplication is per-round only, so all N are accepted and each adds `perasWeight` to the same block point, giving it N × `perasWeight` unbounded boost |

---

### Impact Explanation

**High — chain selection manipulation.** An unprivileged peer can make an honest node permanently prefer a non-canonical fork. By sending a batch of crafted `PerasCert` messages (each with a unique `pcCertRound` but the same `pcCertBoostedBlock` pointing to a fork block), the attacker inflates that block's weight in the `PerasWeightSnapshot` without bound. `compareAnchoredFragments` then selects the artificially heavier fork over the honest chain, causing the node to diverge from the canonical chain. This satisfies the "High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain" criterion.

---

### Likelihood Explanation

**Medium.** Peras is currently gated behind a feature flag and is not yet active on mainnet. However, the code is present in production binaries and the attack requires only the ability to send well-formed (but semantically fabricated) `PerasCert` network messages — no keys, no stake, no special privileges. Any peer connected via the object-diffusion mini-protocol can trigger this path. Once Peras is enabled, exploitation is straightforward.

---

### Recommendation

1. **Implement real `validatePerasCert`**: Verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)`, verify that every claimed voter seat index is a legitimate committee member for that round, and verify that the aggregate signature covers exactly the claimed voter set. The concrete V1 certificate type in `Ouroboros.Consensus.Peras.Cert.V1` already carries the necessary fields (`pcSignature`, `pcVoters`) for this.

2. **Bound per-block boost accumulation**: Enforce that a given block point can receive at most one boost per Peras round (i.e., reject a certificate whose `pcCertBoostedBlock` already has a cert for a different round boosting it, or cap total accumulated weight per point). This prevents the unlimited-replay analog.

3. **Do not ship the stub in a Peras-enabled build**: Gate the feature flag so that `validatePerasCert` returning `Right` unconditionally is impossible in any configuration where the object-diffusion cert writer is active.

---

### Proof of Concept

```
Private testnet with Peras feature flag enabled.

1. Attacker connects to victim node as a peer via the object-diffusion mini-protocol.

2. Attacker identifies a fork block B (slot S, hash H) that is behind the honest tip.

3. Attacker constructs N PerasCert values:
     cert_i = PerasCert { pcCertRound = i, pcCertBoostedBlock = BlockPoint S H }
   for i = 1 .. N, where N > (honest_chain_length - fork_length).

4. Attacker sends all N certs in a single batch to the victim.

5. processCerts snapshots the existing cert IDs (empty or small set), finds all N
   rounds absent, calls validatePerasCert on each — all return Right — and adds
   all N certs to the PerasCertDB.

6. Each cert triggers chainSelSync → chainSelectionForBlock for block B.
   addToPerasWeightSnapshot accumulates N × perasWeight on point (S, H).

7. compareAnchoredFragments now sees the fork containing B as having total weight
   (fork_length + N × perasWeight) > honest_chain_length, and switches to the fork.

8. Victim node has adopted the non-canonical chain.
```

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
