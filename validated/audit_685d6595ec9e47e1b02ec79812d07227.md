### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate, Enabling Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a stub `validatePerasCert` implementation that **always returns `Right` (success)** without performing any cryptographic or structural checks. Because this function is the sole gate used by the production certificate-ingest path (`processCerts` in `PerasCert.hs`), any unprivileged peer can inject an arbitrary, unsigned Peras certificate over the object-diffusion mini-protocol. The forged certificate is accepted, stored, and its `PerasWeight` boost is applied during chain selection, allowing the attacker to steer an honest node toward a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory cryptographic gate for inbound Peras certificates: [1](#0-0) 

The universal instance that covers **all** block types is explicitly marked as a compile-time stub: [2](#0-1) 

The implementation body is:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature check, no round-number bounds check, no boosted-block existence check, no voter-set check — the function ignores every field of `cert` and unconditionally wraps it in `ValidatedPerasCert`.

This stub is wired directly into the production certificate-ingest path. Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate and only rejects a batch when at least one call returns `Left`: [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `(errs, _)` branch is unreachable and every certificate — regardless of content — is accepted and forwarded to `ChainDB.addPerasCertAsync`.

Once stored, the certificate's `vpcCertBoost` is applied to chain selection via `WeightedSelectView`: [5](#0-4) 

`preferCandidate` uses `wsvTotalWeight` (block number + weight boost) to decide whether to switch chains: [6](#0-5) 

---

### Impact Explanation

An attacker who can send a single crafted Peras certificate to a node (via the object-diffusion mini-protocol, which is open to any peer) can:

1. Forge a certificate for an arbitrary block on an adversarial fork, assigning it the full `perasWeight` boost.
2. The honest node accepts the certificate without any cryptographic check.
3. The boosted weight causes `preferCandidate` to return `ShouldSwitch`, making the node abandon its canonical chain in favour of the adversarial fork.

This is a **chain-selection manipulation** vulnerability: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended Peras security assumptions, matching the **High** impact category: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

It also matches the **Critical** category: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

**High.** The attack requires only:
- Network connectivity to a target node (any peer can send object-diffusion messages).
- Crafting a `PerasCert` CBOR payload with an arbitrary round number and block point — no cryptographic material is needed because the check is absent.

No privileged access, no key compromise, and no stake majority are required.

---

### Recommendation

1. **Implement real validation** in `validatePerasCert` before Peras is enabled on any network. At minimum, verify the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregated public keys of the claimed voter set, as already implemented for the `EveryoneVotes` and `WFALS` committee schemes in `Committee/EveryoneVotes.hs` and `Committee/WFALS.hs`.
2. **Remove or gate the universal stub instance** (tracked in [tweag/cardano-peras#73](https://github.com/tweag/cardano-peras/issues/73) and [#120](https://github.com/tweag/cardano-peras/issues/120)). Until a real implementation exists, the ingest path should reject all certificates rather than accept all of them.
3. **Add property tests** that send malformed/unsigned certificates to a node and assert they are rejected with a `PerasValidationErr`.

### Proof of Concept

```
Attacker (any peer)
  │
  │  ObjectDiffusion mini-protocol
  │  sends PerasCert { pcRoundNo = R, pcBoostedBlock = adversarialBlock }
  │  (no valid BLS signature required)
  ▼
makePerasCertPoolWriterFromChainDB
  └─ processCerts
       └─ validatePerasCert mkPerasParams cert
            └─ returns Right (ValidatedPerasCert cert (perasWeight params))
                 -- no check performed; cert accepted unconditionally
  └─ ChainDB.addPerasCertAsync cert
       └─ cert stored in PerasCertDB

Chain selection (next block arrival)
  └─ weightedSelectView computes wsvWeightBoost for adversarialFork
       └─ includes boost from forged cert
  └─ preferCandidate: wsvTotalWeight(adversarialFork) > wsvTotalWeight(canonicalChain)
       └─ ShouldSwitch → node switches to adversarial fork
```

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
