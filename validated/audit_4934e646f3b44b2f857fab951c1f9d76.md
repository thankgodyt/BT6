### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound Peras certificate, performing zero cryptographic or semantic validation. An unprivileged peer can inject a crafted certificate for any block hash and round number via the object-diffusion mini-protocol. The certificate bypasses all validation, is stored in the `PerasCertDB`, and triggers chain selection with an artificial weight boost, allowing the peer to steer an honest node toward a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate before any certificate is stored or acted upon. The degenerate catch-all instance (explicitly marked as a TODO placeholder) implements this gate as an unconditional success:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is checked, no round-number bounds are enforced, no boosted-block hash is authenticated, and no quorum threshold is verified. The function always returns `Right`, meaning every certificate — including one entirely fabricated by an attacker — is treated as `ValidatedPerasCert` carrying the full `perasWeight params` boost.

The inbound processing path in `processCerts` calls this validator and, on an all-`Right` result, immediately adds every certificate to the pool:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` never returns `Left`, the error branch is unreachable. Every certificate from every peer passes.

After storage, `chainSelSync` is invoked for the boosted block, potentially switching the node's preferred chain:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [3](#0-2) 

The Peras weight boost is then factored into `totalWeightOfFragment`, which adds `weightBoostOfFragment` on top of chain length when comparing candidate chains: [4](#0-3)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block hash and any round number. Because `validatePerasCert` always succeeds, the certificate is stored and the named block receives a weight boost equal to `perasWeight params`. If the attacker targets a block on a minority fork, the honest node's chain-selection logic may now prefer that fork over the canonical chain, causing the node to diverge from the honest majority. This is a **chain-selection manipulation** vulnerability: an attacker with no stake and no valid cryptographic material can influence which chain an honest node considers canonical, directly undermining the safety guarantees of the Peras protocol extension.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. The attacker needs only to send a well-formed CBOR-encoded `PerasCert` struct (round number + block point) — no keys, no stake, no quorum. The `processCerts` function is the sole validation gate before storage and chain selection, and it is fully bypassed. The attack is deterministic and requires no brute force.

---

### Recommendation

Replace the stub implementation with a real certificate validator that:
1. Verifies the aggregate BLS signature against the claimed voter set and the `(roundNo, boostedBlock)` message.
2. Checks that each claimed voter seat index is within the committee bounds for the relevant epoch.
3. Enforces the quorum threshold (total weight of valid voters ≥ required quorum).
4. Validates round-number monotonicity and expiry constraints.

Until the real implementation is ready, the stub should at minimum return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that no certificate from the network can influence chain selection.

---

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the object-diffusion mini-protocol for Peras certificates.
2. Construct a `PerasCert` value with:
   - `pcCertRound` = any round number not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of a block on a minority fork that the attacker wants the node to prefer
   - Any placeholder `pcVoters` and `pcSignature` fields (they are never checked)
3. Send the certificate batch to the node.
4. `processCerts` calls `validatePerasCert` → always `Right` → certificate stored.
5. `ChainDB.addPerasCertAsync` triggers `chainSelSync` → `chainSelectionForBlock` for the boosted block.
6. `totalWeightOfFragment` now gives the minority-fork chain additional weight equal to `perasWeight params`.
7. If the boosted weight tips the comparison, the node switches to the minority fork. [5](#0-4) [6](#0-5)
