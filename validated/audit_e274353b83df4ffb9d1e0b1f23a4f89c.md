### Title
Orchard Bundle Amount Unconstrained in Zcash RBF — Attacker Can Inflate Shielded Output Beyond Authorized Amount — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs` + `src/psbt.rs`)

---

### Summary

For Zcash shielded-only Unified Address withdrawals, the `check_withdraw_psbt` amount-range check is algebraically trivial with respect to the Orchard bundle amount. An unprivileged user who initiated a withdrawal can call the public `withdraw_rbf` endpoint with a new Orchard bundle encoding an arbitrarily larger amount. Every guard passes, and the bridge produces a signed PSBT that routes more ZEC to the shielded pool than was ever authorized.

---

### Finding Description

**Entry point** — `withdraw_rbf` is public and unprivileged: [1](#0-0) 

It calls `withdraw_rbf_chain_specific` (Zcash version, generated by `define_rbf_callback!`), which schedules `withdraw_rbf_callback`. That callback:

1. Accepts a fresh `chain_specific_data` (attacker-supplied `orchard_bundle_bytes`) from the caller.
2. Calls `generate_psbt_from_original_psbt_and_new_output` with the new bundle bytes, producing a new `PsbtWrapper` whose `orchard` field is set from the attacker's bundle.
3. Calls `internal_withdraw_rbf` → `check_withdraw_rbf_psbt_valid` → `check_withdraw_psbt`. [2](#0-1) 

**The broken amount check** — `check_withdraw_psbt` (lines 218, 238, 242–246):

For a shielded-only UA (no transparent receiver), `target_address_script_pubkey` is `None`, so every transparent output is treated as change. `add_extra_outputs` pushes `orchard_amount` into `actual_received_amounts` **and** adds it to `total_output_amount`: [3](#0-2) [4](#0-3) 

With the substitutions:
- `total_output_amount = change_amount + orchard_amount`
- `gas_fee = total_input_amount − change_amount − orchard_amount`
- `max_received_amount = transfer_amount − withdraw_fee − gas_fee = transfer_amount − withdraw_fee − total_input_amount + change_amount + orchard_amount`
- `actual_received_amount = orchard_amount`

The upper-bound check `actual_received_amount ≤ max_received_amount` reduces to:

```
orchard_amount ≤ transfer_amount − withdraw_fee − total_input_amount + change_amount + orchard_amount
⟹  0 ≤ transfer_amount − withdraw_fee − total_input_amount + change_amount
```

**`orchard_amount` cancels out entirely.** The check is trivially satisfied for any Orchard amount as long as `change_amount` is large enough. The lower-bound check simplifies identically. Neither bound constrains `orchard_amount` to `transfer_amount − withdraw_fee − gas_fee`.

**`check_withdraw_chain_specific` is a no-op for Zcash** — it adds zero additional validation: [5](#0-4) 

Compare with the Bitcoin version, which at least enforces a gas-fee increase: [6](#0-5) 

**`validate_orchard_bundle`** only checks recipient address and internal value-balance consistency — it does not compare `orchard_amount` against `transfer_amount`: [7](#0-6) 

**`from_original_psbt`** blindly accepts the attacker's new `orchard_bundle_bytes` with no cross-check against the original bundle's amount: [8](#0-7)

### Impact Explanation

The attacker can redirect ZEC from the bridge's transparent UTXO change output into their own shielded Orchard note. Concretely:

- Original withdrawal: `transfer_amount = 200 000 zat`, `withdraw_fee = 2 000`, `gas_fee = 10 000`, `orchard_amount = 188 000`, `change_amount = 302 000` (from a 500 000-zat UTXO).
- RBF attack: submit a new Orchard bundle with `orchard_amount = 498 000`, `change_amount = 1 000` (min dust), `gas_fee = 1 000` (min fee).
  - Gas-fee check: `500 000 − 1 000 − 498 000 = 1 000` — passes if `min_btc_gas_fee ≤ 1 000`.
  - Amount-range check: trivially passes (as shown above).
  - `validate_orchard_bundle`: passes (correct recipient, internally consistent value balance).
- The bridge signs and broadcasts a Zcash transaction paying **498 000 zat** to the attacker's shielded address, but only **200 000 nZEC** was ever burned.
- Net theft: up to `total_input_amount − min_btc_gas_fee − min_change_amount − original_orchard_amount` zatoshis per RBF call.

This is unauthorized release of bridge-controlled ZEC — a critical impact.

---

### Likelihood Explanation

- `withdraw_rbf` is public, requires no role, and is callable by any account that owns the pending withdrawal.
- Generating a valid Orchard bundle with an arbitrary amount and the correct recipient is straightforward (the attacker controls the spending key for their own address).
- The Halo2 proof is not verified on-chain by the NEAR contract; it is only verified by the Zcash network when the transaction is broadcast, which the attacker controls.
- No additional preconditions beyond having initiated a withdrawal.

---

### Recommendation

In `from_original_psbt` (or in the `withdraw_rbf_callback`), assert that the new Orchard bundle's recovered amount equals the original bundle's amount:

```rust
require!(
    new_psbt.get_orchard_output_amount()
        == original_tx_btc_pending_info.get_psbt().get_orchard_output_amount(),
    "RBF Orchard amount must match original"
);
```

Alternatively, implement `check_withdraw_chain_specific` for Zcash to enforce this invariant, mirroring the Bitcoin version's gas-fee-increase check but also adding an Orchard-amount consistency check.

### Proof of Concept

1. Alice initiates a withdrawal of 200 000 nZEC to a shielded-only UA. The original PSBT has `orchard_amount = 188 000`, `change_amount = 302 000`, `gas_fee = 10 000`.
2. Alice generates a new Orchard bundle (valid Halo2 proof, same recipient, `orchard_amount = 498 000`).
3. Alice calls `withdraw_rbf(original_id, [TxOut { value: 1_000, script_pubkey: change_addr }], Some(ChainSpecificData { orchard_bundle_bytes: inflated_bundle, expiry_height: valid }))`.
4. `check_withdraw_psbt` passes: `gas_fee = 500 000 − 1 000 − 498 000 = 1 000`; amount-range check trivially satisfied; `validate_orchard_bundle` passes.
5. `check_withdraw_chain_specific` is a no-op — no rejection.
6. Bridge stores a new `BTCPendingInfo` with `actual_received_amount = 498 000`, `burn_amount = 499 000`.
7. Relayer signs and broadcasts the Zcash transaction; Alice receives 498 000 zat in her shielded wallet.
8. Bridge burned only 200 000 nZEC but released 498 000 zat — **298 000 zat stolen**. [9](#0-8)

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())
