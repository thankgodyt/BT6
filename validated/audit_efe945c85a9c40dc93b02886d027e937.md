Audit Report

## Title
Unconstrained `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Redirect Transfer Fees — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`sign_transfer` accepts a caller-supplied `fee_recipient: Option<AccountId>` that is embedded verbatim into the MPC-signed `TransferMessagePayload` with no validation against stored transfer state. Because the transfer message is not removed from `pending_transfers` after signing for non-zero-fee transfers, any active trusted relayer can independently call `sign_transfer` for the same `transfer_id` with `fee_recipient` set to their own account, obtain a distinct but cryptographically valid MPC signature, and submit it to the destination chain first — permanently consuming the destination nonce and routing the fee to themselves.

## Finding Description

**Root cause — unconstrained `fee_recipient`:**

`sign_transfer` is gated by `#[trusted_relayer]` and accepts `fee_recipient: Option<AccountId>` with no check against any stored field in `TransferMessage`:

```rust
// near/omni-bridge/src/lib.rs L447-500
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,   // ← caller-controlled, never validated
    fee: &Option<Fee>,
) -> Promise {
    ...
    let transfer_payload = TransferMessagePayload {
        ...
        fee_recipient,   // ← placed verbatim into the signed payload
        ...
    };
```

The payload is hashed and forwarded to the MPC signer, so the resulting signature cryptographically commits to the attacker-chosen `fee_recipient`.

**Transfer message persists for non-zero fees:**

`sign_transfer_callback` only removes the pending transfer when the fee is zero:

```rust
// near/omni-bridge/src/lib.rs L655-658
if fee.is_zero() {
    self.remove_transfer_message(message_payload.transfer_id);
}
```

For any non-zero-fee transfer the entry stays in `pending_transfers`, so multiple trusted relayers can each call `sign_transfer` for the same `transfer_id` with different `fee_recipient` values and each receive a valid MPC signature.

**Fee is paid to whoever is named in the signed payload:**

On the EVM side, `finTransfer` Borsh-encodes `payload.feeRecipient` as part of the data it verifies against the MPC signature and emits it in the `FinTransfer` event. On the NEAR side, `claim_fee_callback` enforces:

```rust
// near/omni-bridge/src/lib.rs L1083-1086
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

The `fee_recipient` in the proof comes from the on-chain EVM event, which reflects whatever was in the signed payload. Whoever controls `fee_recipient` in the signed payload controls who can claim the fee on NEAR.

**Permissionless trusted-relayer entry:**

Any account can call `apply_for_trusted_relayer` with the required stake deposit and, after the waiting period, is automatically promoted. The stake is fully returned on `resign_trusted_relayer`, so the attacker's net cost is only gas.

**Exploit flow:**
1. User initiates a transfer with `fee = 100 tokens`; entry is stored in `pending_transfers`.
2. Attacker (active trusted relayer) calls `sign_transfer(transfer_id, fee_recipient = "attacker.near", fee = ...)`.
3. MPC produces a valid signature over `TransferMessagePayload { ..., fee_recipient: Some("attacker.near"), ... }`.
4. Attacker submits this signature to EVM `finTransfer` → `destinationNonce` is marked used, `FinTransfer` event emitted with `feeRecipient = "attacker.near"`.
5. Attacker calls NEAR `claim_fee` with proof of that event → passes the `fee_recipient == predecessor` check → receives the fee.
6. Legitimate relayer's subsequently obtained signature is permanently invalid (`NonceAlreadyUsed`); their fee is lost.

## Impact Explanation

This is a concrete fee mis-accounting issue that changes relayer and attacker balances on every targeted transfer. The attacker gains the full token fee (and native fee) that was intended for the legitimate relayer. The legitimate relayer's signature, though cryptographically valid, is permanently unusable once the destination nonce is consumed. This matches the allowed critical impact: **"fee mis-accounting… that changes user or protocol balances."**

## Likelihood Explanation

The barrier is economic: stake the configured NEAR amount (default 1 000 NEAR) and wait the waiting period (default 7 days). Because the stake is returned on voluntary resignation, the attacker's only real cost is gas. Any bridge with non-trivial fee settings and moderate transfer volume makes the attack profitable. No privileged access, leaked keys, or external dependency failure is required — only a public contract call from an account that has completed the permissionless staking process.

## Recommendation

Store `fee_recipient` inside `TransferMessage` at initiation time (in `init_transfer`) so it is fixed and cannot be overridden by the signing relayer. Alternatively, validate the caller-supplied `fee_recipient` against a stored or derived value in `sign_transfer`, or restrict `sign_transfer` so that only the transfer's original sender or a pre-registered relayer for that specific transfer can supply the `fee_recipient`.

## Proof of Concept

**Minimal integration test plan (NEAR sandbox):**

1. Deploy the bridge contract and configure `stake_required = 1 NEAR`, `waiting_period_ns = 0` (as done in `setup_trusted_relayer`).
2. Register two trusted relayers: `legitimate.near` and `attacker.near`.
3. User calls `ft_transfer_call` → `init_transfer`, creating a pending transfer with `fee = 1000`.
4. `attacker.near` calls `sign_transfer(transfer_id, fee_recipient = "attacker.near", fee = ...)` → receives MPC signature A.
5. `legitimate.near` calls `sign_transfer(transfer_id, fee_recipient = "legitimate.near", fee = ...)` → receives MPC signature B.
6. Submit signature A to EVM `finTransfer` → succeeds, `destinationNonce` consumed.
7. Submit signature B to EVM `finTransfer` → reverts with `NonceAlreadyUsed`.
8. `attacker.near` calls NEAR `claim_fee` with proof of step 6 event → receives fee.
9. `legitimate.near` attempts `claim_fee` → fails (transfer already removed by attacker's claim).
10. Assert `attacker.near` token balance increased by fee amount; `legitimate.near` balance unchanged.
