### Title
`protocolInfoCardano` silently drops `triggerHardForkDijkstra`, hardcoding `TriggerHardForkNotDuringThisExecution` for the Conway era and permanently blocking the Conway→Dijkstra hard-fork transition - (`File: ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

`protocolInfoCardano` destructures `CardanoHardForkTriggers'` with a record pattern that omits `triggerHardForkDijkstra`. As a result, `partialLedgerConfigConway` is built with the hardcoded value `TriggerHardForkNotDuringThisExecution` instead of `toTriggerHardFork triggerHardForkDijkstra`. The caller-supplied Dijkstra trigger is silently discarded. Because `singleEraTransition` for every `ShelleyBlock`-based era returns `Nothing` when `shelleyTriggerHardFork = TriggerHardForkNotDuringThisExecution`, the Conway era will never signal its end to the Hard Fork Combinator, and no node built on this `ProtocolInfo` will ever enter the Dijkstra era.

---

### Finding Description

`CardanoHardForkTriggers'` is a record pattern synonym with seven fields, one per Shelley-based era trigger:

```
triggerHardForkShelley, triggerHardForkAllegra, triggerHardForkMary,
triggerHardForkAlonzo, triggerHardForkBabbage, triggerHardForkConway,
triggerHardForkDijkstra
``` [1](#0-0) 

The `protocolInfoCardano` function destructures `CardanoHardForkTriggers'` but **omits `triggerHardForkDijkstra`** from the record pattern:

```haskell
cardanoHardForkTriggers =
  CardanoHardForkTriggers'
    { triggerHardForkShelley
    , triggerHardForkAllegra
    , triggerHardForkMary
    , triggerHardForkAlonzo
    , triggerHardForkBabbage
    , triggerHardForkConway
    -- triggerHardForkDijkstra is never bound
    }
``` [2](#0-1) 

Because `triggerHardForkDijkstra` is never bound, `partialLedgerConfigConway` cannot use it. Instead it is hardcoded to `TriggerHardForkNotDuringThisExecution`:

```haskell
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    TriggerHardForkNotDuringThisExecution   -- should be: toTriggerHardFork triggerHardForkDijkstra
``` [3](#0-2) 

Compare with every preceding era, which correctly threads the *next* era's trigger through:

| Era config | Trigger used |
|---|---|
| `partialLedgerConfigShelley` | `toTriggerHardFork triggerHardForkAllegra` |
| `partialLedgerConfigAllegra` | `toTriggerHardFork triggerHardForkMary` |
| `partialLedgerConfigMary` | `toTriggerHardFork triggerHardForkAlonzo` |
| `partialLedgerConfigAlonzo` | `toTriggerHardFork triggerHardForkBabbage` |
| `partialLedgerConfigBabbage` | `toTriggerHardFork triggerHardForkConway` |
| **`partialLedgerConfigConway`** | **`TriggerHardForkNotDuringThisExecution` ← BUG** |
| `partialLedgerConfigDijkstra` | `TriggerHardForkNotDuringThisExecution` ← correct (last era) | [4](#0-3) 

The `singleEraTransition` implementation for every `ShelleyBlock`-based era dispatches on `shelleyTriggerHardFork`:

```haskell
case shelleyTriggerHardFork pcfg of
  TriggerHardForkNotDuringThisExecution -> Nothing   -- era never ends
  TriggerHardForkAtEpoch epoch          -> Just epoch
  TriggerHardForkAtVersion v            -> shelleyTransition pcfg v ledgerState
``` [5](#0-4) 

With `TriggerHardForkNotDuringThisExecution` baked into the Conway partial ledger config, `singleEraTransition` for Conway always returns `Nothing`. The HFC therefore never records a `TransitionKnown` for the Conway→Dijkstra boundary, and the node is permanently stuck in the Conway era.

The caller-supplied `triggerHardForkDijkstra` (e.g. `CardanoTriggerHardForkAtDefaultVersion`, which resolves to `TriggerHardForkAtVersion 12`) is accepted by the API but silently discarded. [6](#0-5) 

---

### Impact Explanation

**High. Hard-fork era transition bug that breaks cross-era consensus for production Cardano nodes.**

When the on-chain governance process votes to raise the protocol version to 12 (Dijkstra), every honest peer will transition to the Dijkstra era. A node built on the buggy `protocolInfoCardano` will:

1. Never call `singleEraTransition` with a result other than `Nothing` for the Conway era.
2. Never record a `TransitionKnown` epoch for the Conway→Dijkstra boundary.
3. Reject all Dijkstra-era blocks received from peers, because the HFC will treat them as belonging to an unknown future era.
4. Prefer a shorter Conway chain over the longer Dijkstra chain, diverging from the honest majority.

This is a permanent, irrecoverable divergence without a node restart with corrected software.

---

### Likelihood Explanation

**High.** The bug is in the single production entry point `protocolInfoCardano` used by every Cardano node. The `triggerHardForkDijkstra` field is publicly exported and set by every caller (including `mkSomeConsensusProtocolCardano` in `cardano-node`), but the value is silently dropped. The Conway→Dijkstra transition is the next scheduled hard fork. No special attacker capability is required; the bug activates automatically when the on-chain protocol version reaches 12.

---

### Recommendation

1. Bind `triggerHardForkDijkstra` in the record pattern match inside `protocolInfoCardano`.
2. Replace the hardcoded `TriggerHardForkNotDuringThisExecution` in `partialLedgerConfigConway` with `toTriggerHardFork triggerHardForkDijkstra`, following the same pattern used by all preceding eras.
3. Add a property test that constructs a `ProtocolInfo` with `CardanoTriggerHardForkAtEpoch 0` for every era trigger and verifies that `singleEraTransition` returns `Just 0` for each non-final era's partial ledger config.

---
