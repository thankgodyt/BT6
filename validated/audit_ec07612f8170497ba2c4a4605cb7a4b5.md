### Title
Full Access Key Not Revoked on Controller Transfer Enables Unauthorized nBTC Minting — (File: `contracts/nbtc/src/migrate.rs`)

---

### Summary

The `nbtc` token contract exposes `attach_full_access_key`, callable by the current controller, which adds a NEAR full-access key to the contract account. When the controller is subsequently changed via `set_controller`, the previously added full-access key is never removed. The displaced controller retains the ability to sign arbitrary transactions as the contract account — including redeploying the contract with malicious code — enabling unauthorized minting of nBTC.

---

### Finding Description

`attach_full_access_key` in `contracts/nbtc/src/migrate.rs` allows the current controller to attach an arbitrary public key as a full-access key on the nbtc contract account: [1](#0-0) 

`set_controller` in `contracts/nbtc/src/lib.rs` allows the current controller to transfer control to a new account. It only updates the in-contract `self.controller` field and performs no cleanup of NEAR account-level access keys: [2](#0-1) 

The `assert_controller` guard enforces that only `self.controller` may call privileged contract methods: [3](#0-2) 

However, a NEAR full-access key operates at the **account level**, entirely outside the contract's application logic. A holder of a full-access key can sign any action batch — including `DeployContract` — without invoking any contract method and therefore without being subject to `assert_controller`. This means the old controller's key survives the controller transfer and remains fully operational.

---

### Impact Explanation

With the retained full-access key, the displaced controller can:

1. Deploy a replacement contract binary to the nbtc account that removes all access controls.
2. Call `mint` or `safe_mint` on the newly deployed code to mint arbitrary nBTC to any account.
3. Alternatively, call `set_controller` back to themselves on the original code, regaining application-level control as well.

This constitutes **unauthorized minting of nBTC** and a **complete bypass of bridge authorization and upgrade controls**, matching the Critical impact tier. [4](#0-3) 

---

### Likelihood Explanation

The precondition is that the current controller previously called `attach_full_access_key`. This function exists specifically for upgrade/migration workflows and is documented as such: [1](#0-0) 

The migration test (`test_migration_from_poa_via_full_access_key`) demonstrates the exact pattern: add a full-access key, perform an upgrade, then delete the key. If the deletion step is omitted — or if a controller adds a key for their own use and is later replaced — the key persists. Any controller rotation (e.g., DAO handover, compromise response) that does not explicitly delete all previously added keys leaves the contract exposed. Likelihood is **Medium** given the key must have been added first, but the scenario is a realistic operational step.

---

### Recommendation

1. **Remove all non-contract-added full-access keys inside `set_controller`**: Issue a `Promise::new(env::current_account_id()).delete_key(old_key)` for any key that was registered via `attach_full_access_key`. This requires tracking added keys in contract state.
2. **Track keys in state**: Store the set of keys added via `attach_full_access_key` so they can be enumerated and deleted on controller change.
3. **Alternatively**, remove `attach_full_access_key` entirely and rely solely on the `upgrade_and_migrate` contract-level upgrade path, which is already gated by `assert_controller`. [5](#0-4) 

---

### Proof of Concept

1. **Controller A** (current controller) calls:
   ```
   nbtc.attach_full_access_key({ public_key: "ed25519:ATTACKER_PK" })
   ```
   This adds `ATTACKER_PK` as a full-access key on the nbtc contract account. [6](#0-5) 

2. **Controller A** (or a DAO action) calls:
   ```
   nbtc.set_controller({ controller: "controller_b.near" })
   ```
   `self.controller` is updated to `controller_b.near`. The full-access key `ATTACKER_PK` is **not removed**. [7](#0-6) 

3. **Attacker** (holding the private key for `ATTACKER_PK`) constructs a NEAR transaction signed by `ATTACKER_PK` as the nbtc account, containing a `DeployContract` action with a malicious WASM that mints nBTC freely.

4. The malicious contract is deployed. The attacker calls `mint` on the now-replaced contract, minting nBTC to any address without holding any nBTC or BTC collateral.

5. Result: **unauthorized nBTC minting**, bypassing all bridge verification and authorization controls.

    pub fn upgrade_and_migrate(&self) {
        self.assert_controller();

        // Receive the code directly from the input to avoid the
        // GAS overhead of deserializing parameters
        let code = env::input().unwrap_or_else(|| env::panic_str("ERR_NO_INPUT"));
        // Deploy the contract code.
        let promise_id = env::promise_batch_create(&env::current_account_id());
        env::promise_batch_action_deploy_contract(promise_id, &code);
        // Call promise to migrate the state.
        // Batched together to fail upgrade if migration fails.
        env::promise_batch_action_function_call(
            promise_id,
            "migrate",
            b"",
            NO_DEPOSIT,
            env::prepaid_gas()
                .saturating_sub(env::used_gas())
                .saturating_sub(OUTER_UPGRADE_GAS),
        );
        env::promise_return(promise_id);
    }
