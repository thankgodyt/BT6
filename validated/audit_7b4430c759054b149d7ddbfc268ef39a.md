Audit Report

## Title
Reentrancy via ERC777 `tokensToSend` hook causes nonce collision and permanent fund loss - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
`OmniBridge.initTransfer` increments `currentOriginNonce` before the external token transfer but reads the storage variable again after the external call to populate `initTransferExtension` and emit `InitTransfer`. An ERC777 token's `tokensToSend` hook can reenter `initTransfer` during `safeTransferFrom`, causing both the inner and outer calls to emit `InitTransfer` with the same nonce (N+1), while nonce N is never emitted. The outer transfer's tokens are permanently locked in the bridge with no NEAR-side finalization path.

## Finding Description
In `OmniBridge.initTransfer`, the execution order is:

1. `currentOriginNonce += 1` at line 381 — nonce incremented to N, stored in contract storage.
2. External call at lines 407–411: `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount)` — for ERC777 tokens, the sender's registered `tokensToSend` hook fires here before the transfer completes.
3. Inside the hook, the attacker reenters `initTransfer`:
   - `currentOriginNonce += 1` — nonce incremented to N+1.
   - Inner `safeTransferFrom` completes (hook not re-triggered).
   - `initTransferExtension(..., currentOriginNonce=N+1, ...)` at line 418.
   - `emit InitTransfer(..., currentOriginNonce=N+1, ...)` at line 430 — inner event emitted with nonce N+1.
4. Outer call resumes after `safeTransferFrom` returns.
5. `initTransferExtension(..., currentOriginNonce=N+1, ...)` — reads the current storage value, now N+1.
6. `emit InitTransfer(..., currentOriginNonce=N+1, ...)` — outer event also emitted with nonce N+1.

The root cause is that `currentOriginNonce` is incremented before the external call (satisfying the write-before-call invariant) but is **read again from storage** after the external call for both `initTransferExtension` and `emit`. Under reentrancy, the storage value has been mutated by the inner call, so both calls use the same nonce. No `ReentrancyGuardUpgradeable` or `nonReentrant` modifier is present on `initTransfer`. The same structural flaw exists in `initTransfer1155` at lines 448 and 458–490, where `currentOriginNonce` is incremented before `IERC1155.safeTransferFrom` and read again after it.

The `evm/CLAUDE.md` invariant "State before external calls" is only partially satisfied: the nonce is written before the external call, but the post-call reads of `currentOriginNonce` at lines 418 and 430 break the invariant under reentrancy. This is not listed as a known or excluded issue in `evm/SECURITY.md`.

## Impact Explanation
- Nonce N (the outer call's intended nonce) is never emitted in any `InitTransfer` event. The outer transfer's tokens are locked in the bridge contract with no corresponding event the NEAR side can process.
- Nonce N+1 is emitted twice — once by the inner call and once by the outer call. The NEAR side processes the first occurrence and rejects the second as a replay.
- The outer transfer's tokens are **permanently frozen** in the bridge contract: the NEAR side will never finalize a transfer for nonce N (no event exists) and will reject nonce N+1 as a duplicate.

This matches the allowed Critical impact: permanent freezing of bridged funds and nonce/replay misuse that changes user and protocol balances.

## Likelihood Explanation
ERC777 tokens are ERC20-backward-compatible and deployed on Ethereum mainnet (e.g., imBTC, LUKSO LYX). An attacker can register themselves as the `tokensToSend` hook implementer for their own address via the ERC1820 registry — no admin privileges required. The `initTransfer` non-bridge-token path is fully permissionless. The attacker needs only to: (1) hold an ERC777 token accepted by the bridge, (2) register their address as the ERC1820 `tokensToSend` implementer, and (3) call `initTransfer` — the hook fires automatically during `safeTransferFrom`. The attack is repeatable and requires no victim cooperation.

## Recommendation
1. **Snapshot the nonce before external calls** and use the snapshot in `initTransferExtension` and `emit`:
   ```solidity
   uint64 originNonce = currentOriginNonce + 1;
   currentOriginNonce = originNonce;
   // ... external calls ...
   initTransferExtension(..., originNonce, ...);
   emit BridgeTypes.InitTransfer(..., originNonce, ...);
   ```
2. **Add `ReentrancyGuardUpgradeable`** and apply `nonReentrant` to both `initTransfer` and `initTransfer1155`.
3. Apply the nonce-snapshot fix identically to `initTransfer1155`.

## Proof of Concept
```
State: currentOriginNonce = 5

1. Attacker calls initTransfer(erc777Token, amount1, ...)
   → currentOriginNonce = 6  (line 381)
   → safeTransferFrom fires tokensToSend hook on attacker (lines 407–411)

2. Attacker's hook calls initTransfer(erc777Token, amount2, ...)
   → currentOriginNonce = 7  (line 381, inner call)
   → safeTransferFrom completes (no further hook)
   → initTransferExtension(..., nonce=7, ...)  (line 418, reads storage=7)
   → emit InitTransfer(nonce=7, amount=amount2)  (line 430, reads storage=7)

3. Outer call resumes
   → initTransferExtension(..., nonce=7, ...)  (line 418, reads storage=7, NOT 6)
   → emit InitTransfer(nonce=7, amount=amount1)  (line 430, reads storage=7)

Result:
- Two InitTransfer events with nonce 7 on EVM
- Nonce 6 never emitted → amount1 tokens permanently locked in bridge
- NEAR processes nonce 7 once (amount2), rejects second nonce 7 as replay
```

A Foundry invariant test can confirm this: deploy a mock ERC777 token whose `tokensToSend` hook reenters `initTransfer`, then assert that all emitted `InitTransfer` nonces are unique and contiguous. The invariant will break, demonstrating nonce 6 is skipped and nonce 7 is duplicated.
