### Title
Hardcoded `boundX = 3` in `taylorExpCmpFirstNonLower` Produces Incorrect Peras Non-Persistent Seat Counts When `lambda > ln(3)` - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds. Because `x = -lambda`, the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the error term `errorTerm = abs(err' * boundX)` is underestimated, causing the Taylor-series convergence check to fire prematurely on incorrect partial sums. The result is a wrong seat count returned to `implVerifyVote` and `implVerifyCert`, which use it as the sole gate for non-persistent Peras committee member eligibility.

---

### Finding Description

**Root cause — wrong arithmetic constant:**

```haskell
-- LS.hs lines 94-99
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- ← hardcoded; contract requires e^{|x|} = e^lambda
      orders
      (-lambda)
``` [1](#0-0) 

The function's own inline contract is explicit:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

The error term used inside `decideOne` is:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

When `boundX < e^lambda`, `errorTerm` is smaller than the true remainder bound. The two early-exit conditions:

```haskell
| cmp >= acc' + errorTerm = Stop          -- "definitely ABOVE" → grant seat
| cmp < acc' - errorTerm  = Below ...    -- "definitely BELOW" → skip seat
``` [4](#0-3) 

…both fire on partial sums that have not yet converged to `e^{-lambda}`. For `lambda = 5` (a voter holding ~50 % of non-persistent stake in a 10-voter committee), `e^5 ≈ 148.4` but `boundX = 3`, an underestimate by ×49. The oscillating partial sums of `e^{-5}` (which swing from +1 to −4 to +12.5 to −20.8 … before settling near 0.0067) can satisfy either condition prematurely, returning a seat count that is either too high or too low.

**`lambda` computation (correct order, but feeds the broken bound):**

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [5](#0-4) 

`lambda > ln(3)` whenever `voterStake / totalNonPersistentStake > ln(3) / numNonPersistentVoters`. For a 10-voter committee this threshold is ~11 % of non-persistent stake — easily reached by any moderately large pool.

**Downstream security gate — `implVerifyVote` and `implVerifyCert`:**

Both functions call `localSortitionNumSeats` and reject the vote/certificate if the result is zero:

```haskell
case nonZero numSeats of
  Nothing ->
    Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats ->
    pure $ WFALSNonPersistentMember ...
``` [6](#0-5) [7](#0-6) 

If `localSortitionNumSeats` returns a non-zero value for a voter whose true Poisson-CDF seat count is zero, the vote is accepted from an ineligible non-persistent committee member. Conversely, a legitimate voter may be silently excluded.

The code itself acknowledges the constant is unvalidated:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
``` [8](#0-7) 

---

### Impact Explanation

**Medium — materially weakens Peras vote and certificate authorization.**

When `lambda > ln(3)`, the seat-count gate in `implVerifyVote` / `implVerifyCert` can produce a wrong binary outcome (eligible ↔ ineligible). An ineligible non-persistent voter whose VRF output falls near a Poisson-CDF threshold can have their vote accepted; a legitimate voter can be silently excluded. Both outcomes corrupt the Peras quorum calculation, undermining the certificate validity check that is the core security property of the Peras fast-finality protocol.

---

### Likelihood Explanation

**Low.** The attacker must be a registered pool operator with `> ln(3)/numNonPersistentVoters` fraction of non-persistent stake (≈11 % in a 10-voter committee). They cannot control their VRF output; the wrong-bound error only manifests when the VRF output lands near a Poisson-CDF threshold during the partial-sum oscillation window. This is a probabilistic event across elections, not a deterministic exploit. However, the condition `lambda > ln(3)` is met by any moderately large pool, so the affected population is not negligible.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct bound:

```haskell
-- Correct: boundX = e^{lambda} as required by taylorExpCmpFirstNonLower's contract
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp (realToFrac lambda))   -- e^lambda, not 3
      orders
      (-lambda)
```

Alternatively, use the same approach as `checkLeaderNatValue` in `cardano-ledger`, which computes the bound correctly from the exponent argument. The open issue at https://github.com/tweag/cardano-peras/issues/234 should be resolved before the Peras protocol is activated on any network.

---

### Proof of Concept

**Concrete numerical example** (`lambda = 5`, `boundX = 3` vs correct `e^5 ≈ 148.4`):

1. Pool holds 50 % of non-persistent stake; `numNonPersistentVoters = 10` → `lambda = 5`.
2. `e^{-5} ≈ 0.00674`. Suppose `orders[0] = normalizedVRFOutput / lambda = 0.008` (just above `e^{-5}`; voter should get 0 seats).
3. After 3 Taylor iterations, partial sum `acc' ≈ −4.0` (series has not converged; true value is 0.00674).
4. With `boundX = 3`: `errorTerm = |err' * 3|`. If `err' ≈ 0.02`, `errorTerm = 0.06`. Check: `orders[0] = 0.008 < acc' − errorTerm = −4.06` → fires "definitely BELOW" → algorithm advances to `orders[1]`, eventually returning `numSeats ≥ 1` for a voter who should receive 0 seats.
5. With correct `boundX = e^5 ≈ 148.4`: `errorTerm = |0.02 * 148.4| = 2.97`. Check: `0.008 < −4.0 − 2.97 = −6.97` is false; `0.008 ≥ −4.0 + 2.97 = −1.03` is true → "definitely ABOVE" fires → returns 0 seats (correct).
6. The crafted vote with `seatIndex` in the non-persistent range and `vrfOutput` yielding `lambda = 5` and `normalizedVRFOutput ≈ 0.04` passes `implVerifyVote` on a node running the buggy code, but would be rejected by a node with the correct bound.
