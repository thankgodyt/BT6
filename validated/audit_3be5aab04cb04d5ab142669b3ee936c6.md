Audit Report

## Title
Pause Check Missing on `deploy_token` in Solana `bridge_token_factory` - (File: `solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program's `deploy_token` instruction performs no check against the `Config.paused` bitmask, while every other state-changing instruction (`finalize_transfer`, `finalize_transfer_sol`, `init_transfer`, `init_transfer_sol`) does. The EVM and Starknet equivalents both guard `deployToken`/`deploy_token` with an explicit pause check. When the bridge is paused via `ALL_PAUSED`, any holder of a previously collected valid MPC-signed `DeployTokenPayload` can still call `deploy_token` on Solana, bypassing the emergency freeze and executing a deployer-equivalent action.

## Finding Description
`constants.rs` defines the pause bitmask constants:
- `INIT_TRANSFER_PAUSED = 1 << 0`
- `FINALIZE_TRANSFER_PAUSED = 1 << 1`
- `ALL_PAUSED = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED`

No `DEPLOY_TOKEN_PAUSED` bit exists. [1](#0-0) 

The `pause` instruction sets `config.paused = ALL_PAUSED`, intending to freeze all bridge operations. [2](#0-1) 

`finalize_transfer`, `finalize_transfer_sol`, `init_transfer`, and `init_transfer_sol` all guard execution with a `require!` against the pause bitmask before proceeding. [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5) 

`deploy_token` contains no such guard — it proceeds directly to signature verification and token metadata initialization: [7](#0-6) 

By contrast, the EVM implementation guards `deployToken` with `whenNotPaused(PAUSED_DEPLOY_TOKEN)`: [8](#0-7) 

And the Starknet implementation asserts `!_is_paused(@self, PAUSE_DEPLOY_TOKEN)` at the top of `deploy_token`: [9](#0-8) 

## Impact Explanation
This is a **pause bypass** allowing a deployer-equivalent action during an emergency freeze. When `ALL_PAUSED` is set, the intent is to halt all bridge operations. Because `deploy_token` skips the pause check, an attacker can register a new token mapping and initialize its on-chain metadata on Solana while the bridge is fully paused. This matches the allowed critical impact: *"pause bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."* A token deployment during a pause could register a mapping the admin intended to block (e.g., for a token under active exploit), creating on-chain state that enables subsequent `finalize_transfer` calls once the bridge is unpaused.

## Likelihood Explanation
MPC-signed `DeployTokenPayload` messages are generated by the NEAR bridge and their signatures are emitted as public on-chain log events. Any observer can collect valid signed payloads before a pause event occurs. The exploit path is fully permissionless: call `deploy_token` on the Solana program with a previously collected valid signed payload. No admin compromise, key leak, or collusion is required.

## Recommendation
Introduce a `DEPLOY_TOKEN_PAUSED` bitmask constant in `constants.rs` and include it in `ALL_PAUSED`:

```rust
pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;
pub const ALL_PAUSED: u8 = INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED;
```

Then add the pause guard to `deploy_token` in `lib.rs`, consistent with the other instructions:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    require!(
        ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
        error::ErrorCode::Paused
    );
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

Also import `DEPLOY_TOKEN_PAUSED` in the `use super::constants` line in `lib.rs`. [10](#0-9) 

## Proof of Concept
1. Observe NEAR on-chain log events from `sign_log_metadata_callback` to collect a valid MPC-signed `DeployTokenPayload` for token `X`.
2. Admin calls `pause` on the Solana `bridge_token_factory`, setting `config.paused = ALL_PAUSED`. All `init_transfer` and `finalize_transfer` calls now revert.
3. Attacker calls `deploy_token` on the Solana program with the previously collected signed payload for token `X`.
4. The instruction executes successfully — no pause check is present — and token `X` is registered in the program's state with initialized metadata, bypassing the emergency freeze. [7](#0-6) 

A local integration test can confirm this by: (a) calling `pause`, (b) asserting `init_transfer` reverts with `Paused`, then (c) asserting `deploy_token` with a valid signed payload succeeds — demonstrating the inconsistency.
