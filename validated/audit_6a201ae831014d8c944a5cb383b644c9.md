### Title
Premature Unconditional Mint in `safe_mint` Leaves Tokens Stranded in Bridge Balance and Returns Misleading Zero — (File: contracts/nbtc/src/lib.rs)

---

### Summary

`safe_mint` in the nBTC token contract mints tokens to `bridge_id` **before** checking whether the intended recipient (`account_id`) has a registered storage account. When the recipient is unregistered, the function returns `U128(0)` and exits — but the newly minted tokens remain in `bridge_id`'s balance, permanently increasing total supply without the user ever receiving them.

---

### Finding Description

`safe_mint` executes in this order:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` tokens into `bridge_id`'s balance, increasing total supply.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient has no storage account, returns `U128(0)` immediately without burning or reversing the mint. [1](#0-0) 

The return value `U128(0)` is semantically indistinguishable from "no tokens were minted." Any bridge-side callback that interprets this as a failed or no-op mint — and therefore does **not** mark the deposit UTXO as consumed in `verified_deposit_utxo` — would allow the same BTC UTXO to be submitted again via `verify_deposit`, triggering a second call to `safe_mint` and a second unconditional mint. The first minted tokens remain stranded in `bridge_id`; the second batch is credited to the user. Total nBTC supply now exceeds the locked BTC by exactly `amount`.

The same stranding occurs on the `ft_transfer_call` path: if the downstream `ft_on_transfer` rejects the transfer, `ft_resolve_transfer` returns the tokens to `bridge_id` (the sender), not to a burn address, again leaving minted-but-unattributed tokens in the bridge balance. [2](#0-1) 

The `verified_deposit_utxo` guard lives in the bridge contract, not in the token contract: [3](#0-2) 

Whether it is set before or after the `safe_mint` callback determines whether double-minting is reachable. The token contract itself provides no protection.

---

### Impact Explanation

**Minimum (Medium):** Every call to `safe_mint` where the recipient is unregistered permanently increases total nBTC supply without the user receiving tokens. The stranded tokens accumulate in `bridge_id`, creating a backed-supply overcount that requires operator intervention to reconcile.

**Escalated (Critical):** If the bridge's deposit callback treats `U128(0)` as a non-event and leaves the UTXO unguarded in `verified_deposit_utxo`, an attacker (or any user whose storage account is absent) can trigger a second `verify_deposit` for the same BTC UTXO. The second `safe_mint` call mints a fresh `amount` of nBTC backed by no additional BTC — unauthorized minting of nBTC against a single locked UTXO.

---

### Likelihood Explanation

A NEAR account that has never called `storage_deposit` on the nBTC contract has no registered account. This is the default state for any new NEAR account. A depositor who sends BTC to a bridge address derived from an unregistered NEAR account ID will trigger this path on every deposit attempt. No special privileges are required; any unprivileged user can reach this state.

---

### Recommendation

Reverse the order of operations: check recipient registration **before** minting. If the recipient is unregistered, either revert (forcing the caller to register first) or mint directly to the recipient's account only after registration is confirmed. Do not mint to `bridge_id` as an intermediate step unless the subsequent transfer is guaranteed atomic and rollback-safe.

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");
    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // no tokens minted
    }
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Additionally, the bridge-side deposit callback must unconditionally mark the UTXO in `verified_deposit_utxo` regardless of the `safe_mint` return value, to prevent UTXO re-submission.

---

### Proof of Concept

1. Alice sends 0.01 BTC to a bridge deposit address derived from her NEAR account `alice.near`.
2. `alice.near` has never called `storage_deposit` on the nBTC contract — her account is unregistered.
3. A relayer calls `verify_deposit` on the bridge with a valid Merkle proof.
4. The bridge verifies the proof and calls `nbtc.safe_mint(alice.near, 1_000_000, None)`.
5. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — total supply increases by 1,000,000 satoshis worth of nBTC, credited to `bridge_id`.
6. `safe_mint` finds `alice.near` unregistered and returns `U128(0)`.
7. If the bridge callback treats `U128(0)` as a no-op and does not insert the UTXO into `verified_deposit_utxo`, the relayer (or Alice) can resubmit the same proof.
8. Step 4–6 repeat: another 1,000,000 nBTC is minted to `bridge_id`. On this second attempt, if Alice has since registered, the transfer succeeds and she receives 1,000,000 nBTC.
9. Total nBTC minted: 2,000,000. Total BTC locked: 0.01 (1,000,000 satoshis). Supply exceeds backing by 1,000,000 satoshis. [1](#0-0) [3](#0-2)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
