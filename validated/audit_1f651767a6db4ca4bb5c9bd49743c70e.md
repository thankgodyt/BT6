### Title
Silent Zero-Transfer in `safe_mint` Permanently Locks User BTC When Recipient Account Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own balance unconditionally, then silently returns `U128(0)` without transferring to the user if their account is not registered on the nBTC contract. Because the deposit UTXO is marked as verified before this call, the user's BTC is permanently locked with no refund path and no nBTC received.

### Finding Description

`safe_mint` in `contracts/nbtc/src/lib.rs` follows this sequence:

1. **Line 112** — `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally credits `amount` nBTC to the bridge's own token balance.
2. **Lines 114–116** — checks whether `account_id` is registered. If not, it immediately `return`s `PromiseOrValue::Value(U128(0))` — no transfer, no error, no event, no `lost_found` entry.
3. **Lines 119–122** — only if the account is registered does it call `ft_transfer` / `ft_transfer_call` to move the tokens from the bridge to the user. [1](#0-0) 

The deposit flow in `contracts/satoshi-bridge/src/btc_light_client/deposit.rs` calls `safe_mint` after the light-client proof is verified and the UTXO is recorded as verified in `verified_deposit_utxo`. Once that set is populated, `request_refund_callback` unconditionally blocks any refund for that UTXO: [2](#0-1) 

So the state after the attack is:
- Bridge's nBTC balance is inflated by `amount` (tokens minted but never forwarded).
- User's nBTC balance is 0.
- The deposit UTXO is in `verified_deposit_utxo`, permanently blocking a refund.
- The user's BTC is locked in the bridge-controlled address with no recovery path.

Contrast with `mint_inner`, which auto-registers any account before crediting it: [3](#0-2) 

`safe_mint` deliberately skips that auto-registration, but then silently discards the tokens instead of reverting or recording a `lost_found` entry (the `lost_found` pattern is used in `transfer_nbtc_callback` but not here): [4](#0-3) 

### Impact Explanation

A user whose NEAR account has not called `storage_deposit` on the nBTC contract before their BTC deposit is confirmed will:
- Receive **0 nBTC** for a confirmed, irreversible BTC deposit.
- Be **permanently unable to refund** the BTC because the UTXO is already in `verified_deposit_utxo`.
- Have no on-chain record (no `lost_found`, no event) to trigger operator recovery.

This constitutes a **critical, permanent loss of user funds** — the BTC is locked in the bridge-controlled address and the minted nBTC accrues silently to the bridge's own balance.

### Likelihood Explanation

The NEAR storage-registration requirement is a non-obvious prerequisite. A first-time user who generates a deposit address and sends BTC without first calling `storage_deposit` on the nBTC contract will trigger this path. No privileged access is required; any unprivileged depositor who omits the registration step is affected. The bridge UI or relayer does not enforce registration before accepting a deposit address request, making this a realistic user-reachable condition.

### Recommendation

Replace the silent early-return with one of:
1. **Revert** — `require!(self.token.accounts.get(&account_id).is_some(), "Recipient not registered")` before `internal_deposit`, so the bridge-level callback can handle the failure and record a `lost_found` entry.
2. **Auto-register** — mirror `mint_inner` and call `self.token.internal_register_account(&account_id)` before depositing, then transfer directly.
3. **`lost_found` fallback** — if the account is absent, record the amount in `lost_found` (as `transfer_nbtc_callback` does) so the user can claim later after registering.

### Proof of Concept

1. Alice generates a deposit address via the bridge (no prior `storage_deposit` on nBTC).
2. Alice sends 0.01 BTC to that address.
3. A relayer calls `verify_deposit` with a valid SPV proof.
4. The bridge's deposit callback marks the UTXO in `verified_deposit_utxo` and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 1_000_000)` succeeds; `accounts.get(&alice.near)` returns `None`; function returns `U128(0)`.
6. Alice's nBTC balance: **0**. Bridge's nBTC balance: **+1,000,000 satoshis**.
7. Alice calls `request_refund` → rejected: `"UTXO already verified via deposit"`.
8. Alice's 0.01 BTC is permanently locked. [5](#0-4) [2](#0-1)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
