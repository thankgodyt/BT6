### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Adversarial Chain Selection Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound `PerasCert`, performing no cryptographic, committee-membership, or quorum verification. Any unprivileged peer connected via the Peras certificate object-diffusion miniprotocol can send a crafted certificate naming any block as the boosted target. The certificate is accepted, stored in `PerasCertDB`, and immediately triggers chain selection for the named block. If the boosted block is on a competing fork and the configured `perasWeight` is large enough to overcome the current chain's block-number advantage, the honest node switches to the adversarial fork.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the sole `BlockSupportsPeras` instance used for all block types. No signature is checked, no committee membership is verified, no quorum threshold is enforced. The function always returns `Right`.

**Entry point — inbound certificate diffusion from a peer:**

`makePerasCertPoolWriterFromChainDB` wires this stub directly into the production object-diffusion writer that handles certificates arriving from remote peers:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate. Because the stub always returns `Right`, every certificate from every peer passes validation and is forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

**Chain selection consequence:**

`chainSelSync` processes the accepted certificate. After adding it to `PerasCertDB`, it calls `chainSelectionForBlock` for the block named in `pcCertBoostedBlock`:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `PerasWeightSnapshot` is rebuilt from all stored certificates and used in `weightBoostOfFragment` / `totalWeightOfFragment` during chain comparison:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

If the adversary's fork block receives a boost large enough that `totalWeight(adversary fork) > totalWeight(current chain)`, the node switches forks.

**Attacker-controlled fields in `PerasCert`:**

```haskell
data PerasCert blk = PerasCert
  { pcCertRound      :: PerasRoundNo   -- attacker chooses any unused round
  , pcCertBoostedBlock :: Point blk    -- attacker names any block hash/slot
  }
``` [6](#0-5) 

The boost magnitude (`vpcCertBoost = perasWeight params`) is taken from local node configuration, not from the certificate, so the attacker cannot inflate it. However, the attacker can send one certificate per unused `PerasRoundNo`, each boosting a different block on a competing fork, accumulating weight across multiple rounds.

**`PerasCertDB` deduplication only checks round number:**

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else ...
``` [7](#0-6) 

One certificate per round is accepted. An attacker with access to many unused round numbers can inject multiple boosts.

### Impact Explanation

**High — Chain selection bug.** When Peras is enabled, an unprivileged peer can make an honest node prefer a non-canonical or adversarially-controlled chain by sending crafted `PerasCert` messages that pass the stub validation. The node will switch to the adversarial fork if the accumulated boost weight exceeds the honest chain's block-number advantage. This violates the chain-selection invariant that only legitimately certified blocks should receive weight boosts, and can cause honest nodes to diverge from the canonical chain without any stake majority or key compromise.

### Likelihood Explanation

The Peras certificate object-diffusion miniprotocol is a public network interface reachable by any connected peer. No stake, key, or privileged access is required to send a `PerasCert` message. The only practical constraint is that Peras must be enabled (it is disabled by default per the CHANGELOG). Once enabled in production, any peer can exploit this immediately. The TODO comment and linked issue (`tweag/cardano-peras#120`) confirm the stub is a known placeholder, but the code is wired into the live chain-selection path.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate vote signature against the claimed committee members.
2. Confirms each claimed voter is a legitimate committee member for the given round (using the stake distribution snapshot for that epoch).
3. Confirms the aggregate stake of the voters meets the quorum threshold (`perasQuorumStakeThreshold`).
4. Verifies VRF outputs for non-persistent committee members (as already implemented in `WFALS.implVerifyCert`).

Until this is done, inbound certificates from untrusted peers should be rejected entirely, or Peras should remain disabled.

### Proof of Concept

With Peras enabled, an attacker peer:

1. Observes a competing fork block `B_adv` at `Point (SlotNo s, hash h)` in the VolatileDB of the victim node (or learns it via normal block diffusion).
2. Sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint s h }` for any round `R` not yet in the victim's `PerasCertDB`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. `ChainDB.addPerasCertAsync` is called; `chainSelSync` runs `chainSelectionForBlock` for `B_adv`.
5. `weightBoostOfFragment` adds `perasWeight params` to every fragment containing `B_adv`.
6. If `BlockNo(B_adv_tip) + perasWeight > BlockNo(honest_tip)`, the node switches to the adversarial fork.
7. Repeat with additional round numbers to accumulate further weight if a single boost is insufficient.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
