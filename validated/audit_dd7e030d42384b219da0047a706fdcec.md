### Title
Hardcoded `boundX = 3` in `localSortitionNumSeats` Produces Incorrect Taylor Error Bounds for Voters with `lambda > ln(3)`, Enabling Unauthorized Peras Vote Acceptance - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`. The function's own contract states `boundX` must equal `e^{|x|}` for correct error bounds; here `x = -lambda`, so the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099`, the error bound is underestimated, causing the Taylor convergence check to declare certainty prematurely. In the false-positive direction a voter who should receive 0 non-persistent seats may be granted ≥ 1, and because `implVerifyVote` and `implVerifyCert` call the same flawed function, the resulting vote or certificate passes verification.

### Finding Description

**Root cause.** `localSortitionNumSeats` computes the Poisson-based seat count by calling:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- boundX  ← hardcoded constant
      orders
      (-lambda)  -- x
``` [1](#0-0) 

The function's contract is explicit:

```
-- | boundX = e^{|x|} for correct error estimation
``` [2](#0-1) 

Because `x = -lambda`, the required value is `boundX = e^lambda`. The hardcoded `3` is only correct when `lambda = ln 3 ≈ 1.099`. For any `lambda > ln 3` the error term

```haskell
errorTerm = abs (err' * boundX)   -- boundX too small → errorTerm too small
``` [3](#0-2) 

is underestimated. The convergence guards then fire on a narrower interval than the true Taylor remainder justifies:

```haskell
| cmp >= acc' + errorTerm = Stop          -- ABOVE: grants seat
| cmp < acc' - errorTerm  = Below ...    -- BELOW: denies seat
``` [4](#0-3) 

When a voter's VRF-derived threshold falls in the zone `[e^{-lambda} - true_err, e^{-lambda} + true_err]` but outside the shrunken zone `[acc' - errorTerm, acc' + errorTerm]`, the function may declare ABOVE (granting a seat) when the correct answer is uncertain or BELOW (0 seats).

**`lambda > ln(3)` is realistic.** `lambda = numNonPersistentVoters × voterStake / totalNonPersistentStake`. With 100 non-persistent voters and a pool holding 2 % of non-persistent stake, `lambda = 2.0`; `e^2 ≈ 7.39`, so the error bound is underestimated by a factor of ~2.46. The developers themselves flag this uncertainty:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. ...
-- Tracked by this issue:
-- https://github.com/tweag/cardano-peras/issues/234
``` [5](#0-4) 

**Exploit path.** The same flawed function is called in all three verification sites:

1. `implCheckShouldVote` — pool decides to submit a vote it should not cast.
2. `implVerifyVote` — verifier accepts that vote because it recomputes the same wrong seat count.
3. `implVerifyCert` — verifier accepts a certificate containing such votes. [6](#0-5) [7](#0-6) 

Because both sides of the check use the same incorrect `boundX`, a false-positive seat grant is self-consistent: the pool submits a vote, and every honest verifier accepts it.

### Impact Explanation

A non-persistent committee member with `lambda > ln(3)` whose VRF output lands in the erroneously narrowed uncertain zone is granted ≥ 1 seat when the correct answer is 0. Their vote passes `implVerifyVote` and their contribution passes `implVerifyCert`. This is a bypass of Peras voting eligibility checks: an unauthorized vote is accepted by all honest nodes, inflating the effective quorum weight of the attacker's pool. Repeated across multiple elections this can allow a coalition of pools with `lambda > ln(3)` to push a Peras certificate to quorum that should not reach it, affecting chain-weight boosting and potentially chain selection.

This maps to the allowed impact: **bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance**.

### Likelihood Explanation

- `lambda > ln(3)` is reached by any pool holding more than `ln(3)/numNonPersistentVoters` of the non-persistent stake — a low bar for large pools.
- The attacker cannot choose their VRF output, but they can observe it before deciding to submit. If `localSortitionNumSeats` returns > 0 (due to the bug), they submit; the verifier uses the same function and accepts.
- The error grows with `lambda`: at `lambda = 3`, `e^3/3 ≈ 6.7×` underestimation; at `lambda = 5`, `e^5/3 ≈ 49.5×`. Larger pools face larger errors and wider uncertain zones.
- The bug is systematic — it fires on every election for every affected pool, not just occasionally.

### Recommendation

Replace the hardcoded `3` with the correct `e^lambda`:

```haskell
import Cardano.Ledger.BaseTypes (fpExp)   -- or equivalent

expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (fpExp lambda)   -- correct: e^{|x|} = e^lambda
      orders
      (-lambda)
```

Alternatively, follow the pattern used by `checkLeaderNatValue` in the Ledger, which passes the actual `e^{|x|}` bound rather than a constant, and resolve the open issue at https://github.com/tweag/cardano-peras/issues/234.

### Proof of Concept

Let `numNonPersistentVoters = 100`, `voterStake / totalNonPersistentStake = 0.03`, so `lambda = 3.0`. The correct `boundX = e^3 ≈ 20.09`; the code uses `3`.

For a VRF output `v` such that the first `orders` threshold `t₀ = v / lambda` satisfies:

```
e^{-3} - (|err'| × 20.09) ≤ t₀ < e^{-3} - (|err'| × 3)
```

the correct error bound classifies `t₀` as BELOW (0 seats), but the underestimated bound does not fire the BELOW branch. The function continues iterating and eventually hits `maxN == n` → `Stop` (ABOVE), returning `Just 0` → 1 seat. The pool submits a vote; `implVerifyVote` recomputes `localSortitionNumSeats` with the same inputs and the same wrong `boundX`, obtains 1 seat, and accepts the vote.
