### Title
Missing Caller Restriction on `sign_btc_transaction` Allows Any Account to Force-Sign Any Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary
`sign_btc_transaction` carries only a `#[pause]` decorator and no caller-identity check. Any NEAR account can invoke it against any `BTCPendingInfo` entry, forcing the MPC signing pipeline to advance (and ultimately broadcast) a withdrawal transaction that the legitimate owner may have intended to cancel or replace via RBF.

### Finding Description
`sign_btc_transaction` is the public entry point that drives the MPC chain-signature flow for every outbound BTC/ZEC withdrawal. Its only gate is the global pause flag:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
``` [1](#0-0) 

There is no check that `env::predecessor_account_id()` equals `btc_pending_info.account_id`. The `impl` block itself carries no `#[trusted_relayer]` macro (contrast with the `bridge.rs` impl blocks that do), and no `assert_one_yocto()` is present to prevent cheap batching. [2](#0-1) 

Every `BTCPendingInfo` entry is created with a publicly emitted `GenerateBtcPendingInfo` event that exposes the `btc_pending_id`: [3](#0-2) 

So any observer can enumerate all live pending IDs and call `sign_btc_transaction` against them.

The `#[trusted_relayer]` macro is applied to the sensitive deposit/withdraw-verify and refund-request entry points, confirming the project's pattern of restricting sensitive functions to whitelisted relayers: [4](#0-3) [5](#0-4) 

`sign_btc_transaction` is conspicuously absent from any such restriction.

### Impact Explanation
Once a user initiates a withdrawal via `ft_on_transfer`, their nBTC is held by the bridge and a `BTCPendingInfo` is created in `PendingSign` state. The user retains the ability to cancel or accelerate via `withdraw_rbf` (public) or `cancel_withdraw` (DAO/Operator) **before** the transaction is fully signed and broadcast.

An attacker who calls `sign_btc_transaction` for every input index of a victim's pending transaction drives the MPC service to produce all required signatures and broadcast the raw transaction to Bitcoin. Once broadcast, the user's window to cancel via RBF is closed. The funds are sent to the `target_btc_address` the user originally specified, so there is no direct theft — but the user's ability to abort a withdrawal they no longer want (e.g., fee spike, wrong address discovered late, desire to consolidate) is permanently bypassed by an unprivileged third party. This matches **Medium: Bypass of bridge limits or policies, or attacker-triggered forced state change without direct theft**.

### Likelihood Explanation
- `btc_pending_sign_id` values are broadcast as on-chain events and are trivially enumerable via view calls.
- The call requires no special role, no attached deposit, and no privileged key.
- A single NEAR account can iterate over all live pending IDs and call `sign_btc_transaction` for each input index in one batch transaction (no `assert_one_yocto()` barrier).
- Likelihood is **High**.

### Recommendation
Add a caller-identity check at the top of `sign_btc_transaction`, mirroring the pattern used elsewhere in the contract:

```rust
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();

+   // Only the transaction owner or a whitelisted relayer may advance signing.
+   let caller = env::predecessor_account_id();
+   require!(
+       caller == btc_pending_info.account_id
+           || self.acl_has_role(Role::UnrestrictedRelayer.into(), caller.clone())
+           || self.acl_has_role(Role::DAO.into(), caller),
+       "Unauthorized: only the withdrawal owner or a trusted relayer may sign"
+   );

    ...
}
```

Alternatively, apply the `#[trusted_relayer]` macro to the `impl` block containing `sign_btc_transaction`, consistent with the project's existing pattern for sensitive bridge operations.

### Proof of Concept
1. Alice calls `ft_on_transfer` on the nBTC contract with a `Withdraw` message, transferring 1 nBTC to the bridge. The bridge emits `GenerateBtcPendingInfo { account_id: "alice", btc_pending_id: "abc123" }`.
2. Alice decides she wants to cancel (e.g., BTC fees spiked) and prepares a `withdraw_rbf` call.
3. Attacker Eve observes the event, reads `btc_pending_id = "abc123"`, and immediately calls:
   ```
   sign_btc_transaction("abc123", 0, 0)
   sign_btc_transaction("abc123", 1, 0)   // if multi-input
   ```
   with no attached deposit and no special role.
4. The MPC service signs all inputs; the bridge assembles and broadcasts the raw BTC transaction.
5. Alice's `withdraw_rbf` call now either fails (pending info state changed) or is ineffective (transaction already in mempool with all signatures).
6. Alice's BTC is sent to her original `target_btc_address` — she has not lost funds, but her right to cancel the withdrawal has been irrevocably bypassed by an unprivileged third party.

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

                return PromiseOrValue::Value(true);
            }
        }
