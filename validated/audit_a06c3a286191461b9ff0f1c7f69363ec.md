Audit Report

## Title
Missing Destination-Chain Token Registration Validation in `init_transfer` Enables Permanent Fund Loss — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts outbound transfer requests without verifying that the destination chain has a registered token address in `token_id_to_address`. For bridge-deployed tokens, this causes `burn_tokens_if_needed` to fire and destroy tokens via a detached promise before any registration check can occur. The resulting pending transfer can never be completed by any relayer, and no user-accessible cancellation path exists, leaving funds permanently frozen or destroyed.

## Finding Description
`init_transfer` performs only one chain-level check — rejecting `ChainKind::Near` as a destination:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

No check is made that `self.factories` contains the destination chain or that `self.token_id_to_address` contains a `(destination_chain, token_id)` entry. Execution proceeds unconditionally to `init_transfer_internal`, which calls `burn_tokens_if_needed` for any bridge-deployed token:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // fires regardless of what follows
    }
}
```

The `.detach()` means the burn is dispatched and cannot be rolled back. `init_transfer_internal` then returns `U128(0)`, signalling to the NEP-141 contract that zero tokens should be refunded. The transfer is stored in `pending_transfers`.

Later, when any relayer calls `sign_transfer`, it attempts to resolve the token address for the destination chain:

```rust
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

`get_token_address` is a direct lookup into `token_id_to_address`:

```rust
pub fn get_token_address(&self, chain_kind: ChainKind, token: AccountId) -> Option<OmniAddress> {
    self.token_id_to_address.get(&(chain_kind, token))
}
```

If no mapping exists for the destination chain, `sign_transfer` panics unconditionally. The transfer remains in `pending_transfers` indefinitely. `token_id_to_address` is only populated through admin-gated operations (`deploy_token`, `bind_token`, `add_deployed_tokens`). There is no public user-callable function to cancel or withdraw a pending transfer.

## Impact Explanation
A user holding a bridge-deployed token (e.g., `eth.bridge.near`) who initiates a transfer to a chain where that token has no registered address (e.g., Starknet) will have their tokens permanently burned. The NEP-141 contract is told to keep the tokens (refund = 0), the burn fires asynchronously and is irreversible, and no relayer can ever call `sign_transfer` successfully for that transfer ID. The only recovery route is DAO intervention to register the token on the destination chain and complete the transfer — but this requires the destination-chain infrastructure to exist and the DAO to act, and cannot un-burn already-destroyed supply if the destination chain cannot receive the transfer. This constitutes permanent loss or permanent freezing of bridged funds, matching the critical impact scope.

## Likelihood Explanation
Any unprivileged user holding a bridge-deployed token can trigger this by calling `ft_transfer_call` with a syntactically valid but unregistered destination chain. The `OmniAddress` parser accepts all supported chain prefixes (`eth`, `sol`, `arb`, `base`, `bnb`, `pol`, `hlevm`, `abs`, `btc`, `zcash`, `strk`, `fogo`) without checking registration state. No admin compromise, key leak, or social engineering is required. The condition is reachable whenever a token is registered for some chains but not all — a normal operational state during incremental chain rollouts.

## Recommendation
Before burning or locking tokens in `init_transfer_internal`, verify that the destination chain has both a registered factory and a registered token address. This check should be placed in `init_transfer` (before storage allocation and before `init_transfer_internal` is called) so that the NEP-141 `ft_transfer_call` is fully reverted and the user's tokens are returned:

```rust
require!(
    self.factories.get(&init_transfer_msg.get_destination_chain()).is_some(),
    BridgeError::UnknownFactory.as_ref()
);
require!(
    self.get_token_address(
        init_transfer_msg.get_destination_chain(),
        token_id.clone(),
    ).is_some(),
    BridgeError::FailedToGetTokenAddress.as_ref()
);
```

Placing this before `init_transfer_internal` ensures that if either check fails, `ft_on_transfer` returns the full token amount as a refund and no burn or storage mutation occurs.

## Proof of Concept
1. Deploy the bridge with a bridge-deployed token `eth.bridge.near` registered only for `ChainKind::Eth` in `token_id_to_address`. No entry exists for `(ChainKind::Strk, eth.bridge.near)`.
2. As an unprivileged user, call `ft_transfer_call` on `eth.bridge.near` targeting the bridge contract, with message:
   ```json
   {"InitTransfer": {"recipient": "strk:0xdeadbeef...", "fee": "0", "native_token_fee": "0"}}
   ```
3. `ft_on_transfer` → `init_transfer`: the `ChainKind::Near` check passes (destination is Starknet). No factory or token-address check is performed.
4. `init_transfer_internal` is entered: `add_transfer_message` stores the transfer; `burn_tokens_if_needed` fires with `.detach()` — tokens are burned on `eth.bridge.near`; `lock_tokens_if_needed` returns `Unchanged` (no Starknet entry in `locked_tokens`); returns `U128(0)`.
5. `ft_transfer_call` receives refund = 0; user balance is permanently debited.
6. Any relayer calling `sign_transfer` for this `TransferId` panics at `get_token_address` — no `(Starknet, eth.bridge.near)` entry exists.
7. Transfer remains in `pending_transfers` indefinitely; burned tokens are unrecoverable without DAO intervention to register the token on Starknet and complete the transfer.

A unit test can be written against the existing test harness by calling `init_transfer_internal` directly with a `TransferMessage` whose recipient chain has no entry in `token_id_to_address`, asserting that `burn` was called and that a subsequent `sign_transfer` call panics with `FailedToGetTokenAddress`.
