### Title
Unauthenticated Refund Address Substitution Enables Theft of Unfinalized User Deposits — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` imposes no ownership check on the caller relative to the `deposit_msg.recipient_id`. Any NEAR account can submit a refund request for another user's unfinalized BTC/ZEC deposit and supply an attacker-controlled `refund_address`. After the `unsafe_refund_timelock_sec` elapses, the bridge's MPC pipeline sends the victim's native coins to the attacker's address.

---

### Finding Description

The deposit address is derived by hashing the full `DepositMsg` (including `recipient_id`) via `get_deposit_path`. This binding is cryptographically sound for the deposit path, but the refund path has no equivalent ownership gate.

`request_refund` (line 510, inside the second `#[trusted_relayer]` impl block at line 480) carries only `#[payable]` and `#[pause]` attributes on the method itself — no individual `#[trusted_relayer]` guard and no check that `env::predecessor_account_id() == deposit_msg.recipient_id`:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  line 510
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← attacker supplies their own BTC address
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
```

Inside `internal_request_refund` the only guard on `refund_address` is:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 154-158
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This guard is a no-op when `deposit_msg.refund_address` is `None` — the common case for ordinary users who did not pre-authorize a BTC return address. The callback `request_refund_callback` (line 497 in `refund.rs`) then stores the attacker-supplied address verbatim as `RefundRequest.refund_address`, which `execute_refund` later uses to build the MPC-signed Bitcoin transaction paying out to that address.

`execute_refund` (line 582 in `bridge.rs`) is also callable by any NEAR account after the timelock, so the attacker can trigger the payout themselves without operator assistance.

The victim's `deposit_msg` is publicly observable: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `DepositMsg` (line 465-470 in `bridge.rs`), and the BTC transaction and its Merkle proof are public blockchain data.

The `unsafe_refund_timelock_sec` (applied when `deposit_msg.refund_address` is `None`, line 226 in `refund.rs`) is the only protocol-level delay, but it is a monitoring window for the DAO/Operator to reject the request — not a cryptographic ownership proof. If the DAO/Operator fails to notice or act in time, the theft completes.

---

### Impact Explanation

**Critical — Significant theft of user or protocol funds.**

An attacker can redirect any unfinalized BTC/ZEC deposit to their own native-chain address. The victim loses their entire deposited amount minus the gas fee. The bridge's MPC pipeline signs and broadcasts a valid Bitcoin/Zcash transaction paying the attacker, making the loss irreversible once confirmed on-chain.

---

### Likelihood Explanation

**Medium.**

Prerequisites are all publicly available:
1. An unfinalized deposit exists (common: deposits below `min_deposit_amount` land in "unavailable UTXO" state; relayer delays; deposits whose `verify_deposit` was never called).
2. The victim's `DepositMsg` is recoverable from the `LogDepositAddress` on-chain event.
3. The BTC/ZEC transaction bytes and Merkle proof are public blockchain data.
4. The attacker must attach the NEAR storage deposit for `request_refund` (a small, fixed cost).
5. The attacker must wait for `unsafe_refund_timelock_sec` without the DAO/Operator rejecting the request.

No privileged access, leaked keys, or social engineering of the victim is required.

---

### Recommendation

Enforce that the caller of `request_refund` is the `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient may request a refund"
);
```

Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the BTC destination is committed at deposit time and cannot be overridden by a third party. The `unsafe_refund_timelock_sec` path (for caller-supplied addresses) should be removed or restricted to DAO/Operator only.

### Proof of Concept

**Setup**: Alice deposits 0.01 BTC to the address derived from:
```json
{ "recipient_id": "alice.near", "refund_address": null }
```
The `LogDepositAddress` event is emitted publicly. The deposit is never finalized (e.g., the relayer is offline).

**Attack**:
```bash
# Step 1 — Attacker submits refund request with their own BTC address
near call satoshi-bridge.near request_refund '{
  "deposit_msg": {"recipient_id": "alice.near"},
  "refund_address": "bc1qattacker...",
  "tx_bytes": "<alice_deposit_tx_base64>",
  "vout": 0,
  "proof": { ... },
  "gas_fee": null
}' --accountId attacker.near --deposit 0.1

# Step 2 — After unsafe_refund_timelock_sec passes, attacker executes the refund
near call satoshi-bridge.near execute_refund '{
  "utxo_storage_key": "<txid>@0",
  "chain_specific_data": null
}' --accountId attacker.near --deposit 0.01
```

The bridge's MPC service signs a Bitcoin transaction paying `bc1qattacker...` the full deposit amount minus the gas fee. Alice receives nothing.
