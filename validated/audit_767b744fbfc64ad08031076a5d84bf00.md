### Title
Inverted Vacuous Truth in `noCertsFromTwoRoundsAgo` Suppresses Peras Certificate Inclusion in Rounds 0 and 1, Masked by Identical Test-Model Bug — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Cert/Inclusion.hs`)

---

### Summary

The `noCertsFromTwoRoundsAgo` predicate in `Peras/Cert/Inclusion.hs` returns `Bool False` when `currRoundNo < 2`, but the semantically correct vacuous value is `True`. Because the predicate is part of a conjunction in `needCertRules`, this causes `needCert` to always return `DoNotIncludeCert` in Peras rounds 0 and 1, silently suppressing certificate inclusion even when a valid certificate is available and required by the protocol. The test model in `Test/Consensus/Peras/Cert/Inclusion.hs` contains the identical inversion, so `prop_needCert` passes while both the implementation and the model are wrong — a direct structural analog to the external report's finding that a test suite validates only against itself rather than against the specification.

---

### Finding Description

**Root cause — implementation:**

In `noCertsFromTwoRoundsAgo` the guard for early rounds reads:

```haskell
-- We cannot have possibly seen a certificate from two rounds ago if we are
-- in round 0 or 1. In that case, this is vacuously false.
| currRoundNo < 2 =
    NoCertsFromTwoRoundsAgo currRoundNo
      := Bool False
``` [1](#0-0) 

The predicate name is `noCertsFromTwoRoundsAgo` — it is `True` when there are **no** certificates from two rounds ago. In rounds 0 and 1, rounds −2 and −1 do not exist, so the condition is vacuously **True**. The comment misidentifies this as "vacuously false" and the implementation encodes that mistake as `Bool False`.

`needCertRules` is a conjunction:

```haskell
needCertRules pciv =
  noCertsFromTwoRoundsAgo pciv
    :/\: latestCertSeenIsNotExpired pciv
    :/\: latestCertSeenIsNewerThanLatestCertOnChain pciv
``` [2](#0-1) 

`evalPred` short-circuits on the first `False` branch of a conjunction:

```haskell
a :/\: b ->
  case go a of
    Left a' -> Left a' -- short-circuit
``` [3](#0-2) 

Therefore, whenever `currRoundNo < 2`, `needCert` unconditionally returns `DoNotIncludeCert`, regardless of whether a valid, non-expired, newer-than-on-chain certificate is available.

**Root cause — test model (masking the bug):**

The property test `prop_needCert` compares the implementation against a simplified model:

```haskell
noCertsFromTwoRoundsAgo =
  if currRoundNo < 2
    then False          -- ← same inversion as the implementation
    else not ((currRoundNo - 2) `Set.member` certIds)
``` [4](#0-3) 

Because the model and the implementation agree on the wrong answer, `prop_needCert` passes for all generated inputs, including rounds 0 and 1. The test suite provides no independent oracle — it is the exact structural failure the external report describes: tests that only confirm the code is self-consistent, not that it is correct.

---

### Impact Explanation

In the Peras protocol, certificates are included in blocks to boost chain weight. `needCert` is the sole gate that decides whether a block producer includes a certificate. With the bug active, no honest node running this code will ever include a certificate in Peras rounds 0 or 1.

An adversary running a corrected implementation (or any implementation that correctly evaluates the vacuous case as `True`) will include certificates in those rounds, producing blocks with a higher Peras weight. Honest nodes performing chain selection via `preferAnchoredCandidate` / `weightedSelectView` will observe the adversary's chain as strictly heavier and switch to it, even if the adversary's chain is otherwise non-canonical. This is a chain-selection bug: a crafted chain from an unprivileged peer causes honest nodes to prefer a less-secure chain beyond the intended security assumptions of the Peras weight mechanism.

**Impact class:** High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

---

### Likelihood Explanation

The bug fires deterministically at the start of every Peras epoch (rounds 0 and 1). It requires no special privileges: any peer running a corrected binary can produce heavier blocks in those rounds. The masking test model means the bug survives standard CI and is unlikely to be caught by routine review.

---

### Recommendation

1. **Fix the implementation:** Change `Bool False` to `Bool True` in the `currRoundNo < 2` guard of `noCertsFromTwoRoundsAgo`, and correct the comment from "vacuously false" to "vacuously true". [5](#0-4) 

2. **Fix the test model:** Change the `then False` branch in `needCertModel` to `then True`. [4](#0-3) 

3. **Add a regression unit test** that directly asserts `needCert` returns `IncludeCert` when `currRoundNo ∈ {0, 1}`, `latestCertOnChain = Origin`, and a valid non-expired certificate is available.

4. **Derive the model from the Agda specification** rather than re-implementing it in Haskell, to prevent the model and implementation from sharing the same conceptual mistake.

---

### Proof of Concept

Construct a `PerasCertInclusionView` with:
- `currRoundNo = 1`
- `latestCertSeen = LatestCertSeenView { lcsCert = cert_round_1, lcsCertRound = 1 }`
- `latestCertOnChain = Origin` (no cert on chain yet)
- `certIds = Set.empty` (no certs in database)
- `perasParams` with `perasCertMaxRounds = 10` (cert is not expired)

All three conditions of `needCertRules` should be satisfied:
1. `noCertsFromTwoRoundsAgo`: vacuously **True** (round −1 does not exist) → **implementation returns False**
2. `latestCertSeenIsNotExpired`: `1 ≤ 10 + 1` → True
3. `latestCertSeenIsNewerThanLatestCertOnChain`: `Origin` → True

Expected result per CIP-0140: `IncludeCert`
Actual result: `DoNotIncludeCert` — the conjunction short-circuits on the first predicate.

The same input fed to `needCertModel` also returns `shouldIncludeCert = False` (because the model has `then False`), so `prop_needCert` reports success, confirming the test provides no protection against this bug. [6](#0-5) [7](#0-6)
