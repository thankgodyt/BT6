### Title
Tokens Permanently Stuck in Bridge When Recipient Is Unregistered in `safe_mint` - (File: contracts/nbtc/src/lib.rs)

### Summary

`safe_mint` in the nBTC token contract calls `internal_deposit` to credit the bridge's own balance **before** checking whether the recipient account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the minted tokens, leaving them permanently locked in the bridge's balance with no recovery path.

### Finding Description

In `safe_mint` (contracts/nbtc/src/lib.rs, lines 100–124), the execution order is:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally mints `amount` nBTC into the bridge contract's own token balance.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the intended recipient has no registered storage slot, the function returns immediately with zero, abandoning the already-minted tokens. [1](#0-0) 

The minted tokens now sit in `bridge_id`'s balance. There is no `lost_found` entry created (unlike the standard `mint` path), no refund cross-contract call, and no owner-callable recovery function visible in the contract. The bridge's nBTC balance is inflated by `amount` with no corresponding user claim.

The standard `mint` path avoids this entirely by using `mint_inner`, which auto-registers the recipient before depositing: [2](#0-1) 

`safe_mint` deliberately skips auto-registration (to support the "revert on failure" semantic documented in CLAUDE.md), but the implementation does not revert — it silently succeeds after the irreversible state mutation.

### Impact Explanation

When `safe_verify_deposit` triggers `safe_mint` for a recipient who has not yet called `storage_deposit` on the nBTC contract:

- The user's BTC UTXO is consumed and added to the bridge's available UTXO set (the deposit is recorded as complete).
- `amount` nBTC is minted into the bridge's own balance and is permanently inaccessible to the user.
- The user receives zero nBTC.
- No `lost_found` record is created, so the standard recovery flow does not apply.
- The bridge's token balance exceeds the amount it can legitimately burn, breaking the 1:1 BTC-backing invariant.

This constitutes **permanent locking of user funds** — the user's BTC is locked in the bridge and their nBTC is unreachable. [3](#0-2) 

### Likelihood Explanation

Any user who sends BTC to a deposit address derived from a `DepositMsg` that names an unregistered NEAR account will trigger this path. This is a realistic scenario: a new user generates a deposit address before registering their nBTC storage slot, or a third-party integration (e.g., Omni Bridge) calls `safe_verify_deposit` for an account that has not yet paid the NEP-141 storage deposit. No privileged access is required — the attacker-controlled input is simply the `account_id` field in the `DepositMsg`.

### Recommendation

Move the registration check **before** the `internal_deposit` call, and either:

1. **Revert early** if the account is unregistered (matching the documented "revert on failure" semantic), so the entire `safe_verify_deposit` transaction rolls back and the deposit proof can be resubmitted after the user registers; or
2. **Auto-register** the account (mirroring `mint_inner`) before depositing, ensuring the transfer always succeeds.

Additionally, add a guarded owner-callable function to recover any tokens already stuck in the bridge's balance from past occurrences of this bug.

### Proof of Concept

1. User Alice generates a BTC deposit address from a `DepositMsg` naming her NEAR account `alice.near`.
2. Alice sends 1 BTC to that address but has **not** called `storage_deposit` on the nBTC contract.
3. A relayer calls `safe_verify_deposit` with Alice's transaction proof.
4. The bridge verifies the proof and calls `safe_mint(alice.near, 100_000_000, None)` on the nBTC contract.
5. `internal_deposit(&bridge_id, 100_000_000)` executes — 1 nBTC is minted into the bridge's balance.
6. `accounts.get(&alice.near).is_none()` → `true` → function returns `U128(0)`.
7. Alice's BTC UTXO is now in the bridge's available set; Alice holds 0 nBTC; 1 nBTC is permanently locked in the bridge contract with no recovery mechanism. [1](#0-0) [4](#0-3)
