### Title
Arithmetic Underflow Panic in `check_withdraw_psbt` Due to `gas_fee` Bounds Check Ordered After Dependent Subtraction — (File: `contracts/satoshi-bridge/src/psbt.rs`)

### Summary
In `check_withdraw_psbt`, the bridge computes `max_received_amount` and `min_received_amount` using `gas_fee` before validating that `gas_fee` is within its configured bounds. Because the project compiles with `overflow-checks = true`, a user-submitted PSBT that produces an out-of-range `gas_fee` causes an integer underflow panic before the bounds check is ever reached. This is the direct analog of the reported `bank::recall` assertion failure: an arithmetic invariant check that panics due to integer arithmetic properties rather than failing gracefully.

### Finding Description

In `contracts/satoshi-bridge/src/psbt.rs`, `check_withdraw_psbt` computes:

```rust
// line 238
let gas_fee = total_input_amount - total_output_amount;

// lines 242-243
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;

require!(
    actual_received_amount >= min_received_amount
        && actual_received_amount <= max_received_amount,
    ...
);

// gas_fee bounds check — lines 252-258, AFTER the arithmetic above
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [1](#0-0) 

The `gas_fee` bounds check is placed **after** the two subtractions that depend on it. With `overflow-checks = true` (confirmed in `CLAUDE.md`), two underflow paths exist:

**Path 1 — `amount - withdraw_fee - gas_fee` underflows:**
A user submits a PSBT whose outputs sum to a value small enough that `gas_fee = total_input_amount - total_output_amount` exceeds `amount - withdraw_fee`. The subtraction panics before the `gas_fee <= max_btc_gas_fee` guard is reached.

**Path 2 — `max_received_amount - config.min_change_amount` underflows:**
Even with a `gas_fee` within the configured bounds, if `amount - withdraw_fee - gas_fee < min_change_amount` (possible when `min_withdraw_amount - fee_min - max_btc_gas_fee < min_change_amount` in production), the second subtraction panics before the `actual_received_amount` range check fires. [2](#0-1) 

The `min_change_amount` field is a live, operator-configurable parameter: [3](#0-2) 

The config validation only requires `min_change_amount < max_change_amount` and `unhealthy_utxo_amount > min_change_amount`; it does not enforce that `min_withdraw_amount - fee_min - max_btc_gas_fee >= min_change_amount`: [4](#0-3) 

The entry point is `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt`. Any nBTC holder can reach this path by calling `nbtc.ft_transfer_call(bridge, amount, withdraw_msg)` with a crafted PSBT: [5](#0-4) [6](#0-5) 

### Impact Explanation

When the panic fires inside `ft_on_transfer` (a cross-contract call initiated by the nBTC contract's `ft_transfer_call`), the NEAR runtime rolls back all state mutations within that receipt. The nBTC contract's `ft_resolve_transfer` callback then refunds the user's tokens. No funds are permanently lost and no UTXOs are permanently locked. The impact is a publicly reachable panic-driven fault in the production withdrawal path: the withdrawal silently aborts instead of returning a descriptive error, and the user must retry. This matches the **Low** allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation

Any nBTC holder can trigger this without any privileged access. The attacker only needs to:
1. Hold any amount of nBTC ≥ `min_withdraw_amount`.
2. Construct a `Withdraw` PSBT whose transparent outputs sum to a value that places `gas_fee` outside the safe arithmetic range.

The PSBT structure is fully user-supplied via the `TokenReceiverMessage::Withdraw` message. No operator cooperation is required.

### Recommendation

Move the `gas_fee` bounds check to **before** the dependent subtractions, or use saturating/checked arithmetic with an explicit error:

```rust
let gas_fee = total_input_amount - total_output_amount;

// Validate gas_fee FIRST, before using it in further arithmetic
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({})...", gas_fee)
);

// Now safe to subtract
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .unwrap_or_else(|| env::panic_str("amount underflow after fee deduction"));
let min_received_amount = max_received_amount
    .checked_sub(config.min_change_amount)
    .unwrap_or(0); // treat underflow as 0 — no dust slack applies
```

Additionally, `Config::assert_valid` should enforce that `min_withdraw_amount` is large enough to cover `fee_min + max_btc_gas_fee + min_change_amount`, preventing the configuration itself from creating an impossible arithmetic state.

### Proof of Concept

**Setup (production-realistic config):**
- `min_withdraw_amount` = 70,000 sat
- `fee_min` = 50,000 sat, `fee_rate` = 0 → `withdraw_fee` = 50,000 for any withdrawal
- `max_btc_gas_fee` = 50,000 sat
- `min_change_amount` = 546 sat (standard Bitcoin dust threshold)

**Trigger Path 2 (gas_fee within bounds, but `max_received_amount - min_change_amount` underflows):**

1. Alice holds 70,000 nBTC.
2. Alice calls `nbtc.ft_transfer_call(bridge, 70000, withdraw_msg)` with a PSBT where:
   - One UTXO input of 70,000 sat.
   - One user output of 19,454 sat (= 70,000 − 50,000 − 546).
   - No change output.
   - `gas_fee` = 70,000 − 19,454 = 50,546 sat > `max_btc_gas_fee` (50,000).
3. Alternatively, set user output = 20,000 sat, `gas_fee` = 50,000 (within bounds).
   - `max_received_amount` = 70,000 − 50,000 − 50,000 = **underflow → panic** (Path 1).

**Trigger Path 1 directly:**
- Set user output to 1 sat, no change. `gas_fee` = 69,999. `amount - withdraw_fee - gas_fee` = 70,000 − 50,000 − 69,999 = **underflow → panic** before the `gas_fee <= max_btc_gas_fee` check fires.

In both cases `ft_on_transfer` panics, the NEAR runtime rolls back the UTXO removal, and the nBTC contract refunds Alice's 70,000 tokens — but the withdrawal fails with an opaque panic rather than a descriptive error.
