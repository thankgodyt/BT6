### Title
Asymmetric Vote-Weight Normalization in `implEligiblePartyVoteWeight` Inflates Non-Persistent Member Voting Power — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/WFALS.hs`)

---

### Summary

In the WFALS (Weighted Fait-Accompli with Local Sortition) Peras voting committee, `implEligiblePartyVoteWeight` computes vote weights with an asymmetric normalization: non-persistent members' weights are multiplied by their local-sortition seat count and then **divided** by `totalNonPersistentStake`, while persistent members' weights are their raw `LedgerStake` with **no corresponding division** by `totalPersistentStake`. This is a direct analog of the "Accidental Magnification" pattern: a multiplier (`numSeats`) is applied on one side and a divisor is present for one class of voter but absent for the other, producing vote weights in incompatible units. When these weights are accumulated and compared against the relative quorum threshold, the comparison is dimensionally inconsistent, inflating non-persistent members' effective voting power.

---

### Finding Description

`implEligiblePartyVoteWeight` in `WFALS.hs` computes:

**Persistent member** (lines 414–417):
```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight stake
```
The weight is the raw ledger stake — no normalization.

**Non-persistent member** (lines 421–432):
```haskell
WFALSNonPersistentMember _seatIndex (LedgerStake stake) _vrfOutput numSeats ->
  VoteWeight $
    fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
      * stake
      / nonPersistentStake
```
The weight is `numSeats × stake / totalNonPersistentStake`. [1](#0-0) 

The non-persistent formula normalizes by `totalNonPersistentStake`, producing a value in the range `[0, numSeats]`. The persistent formula does not normalize by `totalPersistentStake`, leaving the weight as a raw `Rational` stake value. If `LedgerStake` values are absolute (e.g., lovelace), persistent members contribute values orders of magnitude larger than the relative quorum threshold (e.g., `0.75`). If `LedgerStake` values are already relative fractions of total stake, non-persistent members' weights are inflated by a factor of `totalStake / nonPersistentStake` compared to persistent members' weights.

The quorum check in `stakeAboveThreshold` directly compares the accumulated `PerasVoteStake` against a relative threshold (`3/4 + safety margin`):

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

The code itself acknowledges the unit mismatch with a TODO comment:

> "TODO: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [3](#0-2) 

The quorum threshold is set to `3/4` relative: [4](#0-3) 

The root cause is the missing divisor for persistent members. The correct formula for persistent members should be `stake / totalPersistentStake` (mirroring the non-persistent normalization), so that both classes of voter contribute weights in the same unit (a fraction of their respective pool's total stake, scaled to be comparable to the relative quorum threshold).

---

### Impact Explanation

When vote weights from both persistent and non-persistent members are accumulated and compared against the relative quorum threshold:

- **If `LedgerStake` is absolute** (lovelace): a single persistent member with any non-zero stake contributes a weight far exceeding `0.75`, trivially satisfying quorum with a single vote. This completely bypasses the quorum requirement, allowing a single persistent committee member to unilaterally forge a Peras certificate for any block they choose.

- **If `LedgerStake` is relative** (fraction of total stake): non-persistent members' weights are inflated by `totalStake / nonPersistentStake` relative to persistent members. The sum of all vote weights does not equal `1` when all voters vote, making the `0.75` threshold meaningless. Non-persistent members can reach quorum with a smaller fraction of the intended stake.

In either case, the Peras certificate quorum check is bypassed or distorted. A forged certificate causes the boosted block to receive additional chain weight (`PerasWeight`), directly affecting chain selection. An adversary who can forge a certificate for a block on a minority chain can cause honest nodes to prefer that chain over the canonical one.

**Impact class**: Critical — bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The WFALS committee is the production Peras voting committee implementation. Votes arrive via the network miniprotocol from peers. Any peer that is a persistent committee member (deterministically assigned at epoch start based on stake) can send a single vote that, due to the missing normalization, trivially satisfies the quorum check if `LedgerStake` is absolute. If `LedgerStake` is relative, a non-persistent member selected via local sortition (probabilistic, based on stake) can exploit the inflated weight. No key compromise, admin access, or stake majority is required — only committee membership, which is a normal operational state for any stake pool.

---

### Recommendation

In `implEligiblePartyVoteWeight`, normalize persistent members' vote weights by `totalPersistentStake`, mirroring the non-persistent normalization:

```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight $ stake / persistentStake
  where
    TotalPersistentStake (Cumulative (LedgerStake persistentStake)) =
      totalPersistentStake committee
```

Additionally, resolve the TODO in `stakeAboveThreshold` by ensuring `PerasVoteStake` is always normalized to a relative value before the comparison, or by passing the total stake distribution into the function to perform normalization internally.

---

### Proof of Concept

Consider a committee with:
- 1 persistent member with `LedgerStake = 1_000_000_000` (1 billion lovelace, absolute)
- 10 non-persistent members each with `LedgerStake = 100_000_000`
- `totalNonPersistentStake = 1_000_000_000`
- Quorum threshold = `0.75`

**Persistent member vote weight** (current code):
`VoteWeight 1_000_000_000`

**Quorum check**:
`1_000_000_000 >= 0.75 + 0.02` → `True` ✓ (quorum reached with 1 vote)

**Correct behavior** (with normalization by `totalPersistentStake = 1_000_000_000`):
`VoteWeight (1_000_000_000 / 1_000_000_000) = VoteWeight 1.0`

Even with normalization, `1.0 >= 0.77` is still `True`, but this is because a single persistent member holds 100% of persistent stake. With a realistic distribution (e.g., persistent member holds 10% of total stake), the normalized weight would be `0.1`, which does not reach quorum alone — correctly requiring additional votes.

The attacker-controlled entry path: a persistent committee member sends a single `WFALSPersistentVote` to the target node. The node calls `implVerifyVote` → `implEligiblePartyVoteWeight` → accumulates `VoteWeight 1_000_000_000` → `stakeAboveThreshold` returns `True` → `forgeCert` is called → a `ValidatedPerasCert` with `vpcCertBoost = PerasWeight 15` is stored → chain selection now prefers any chain containing the boosted block by 15 extra weight units.
