Audit Report

## Title
Decimal-Normalization Dust Permanently Locked When `fee = 0` — (`near/omni-bridge/src/lib.rs`)

## Summary
When a NEAR → foreign-chain transfer is initiated with `fee = 0` and the token has more decimals on NEAR than on the destination chain, `normalize_amount`'s floor division silently truncates a sub-unit remainder ("dust"). The full pre-truncation amount is locked or burned on NEAR in `init_transfer_internal`, but `sign_transfer_callback` immediately deletes the transfer record when the fee is zero, leaving the dust with no recipient and no recovery path — it is permanently frozen inside the bridge escrow.

## Finding Description
`normalize_amount` performs integer floor division to convert a NEAR-native token amount to the destination chain's lower precision:

```rust
// near/omni-bridge/src/lib.rs L2784-2786
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

In `init_transfer`, `transfer_message.amount` is set to the raw user-supplied amount without any rounding: [2](#0-1) 

`init_transfer_internal` then locks or burns this full raw amount: [3](#0-2) 

`sign_transfer` normalizes only the amount that goes to the destination chain (L475–480), so the destination receives `normalize_amount(amount - fee)` tokens. When `fee = 0`, `sign_transfer_callback` immediately removes the transfer record:

```rust
// near/omni-bridge/src/lib.rs L655-658
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
``` [4](#0-3) 

After removal, no `claim_fee` call is possible. The `claim_fee_callback` path that absorbs dust into the fee (L1128–1131) is only reachable when the transfer record still exists, which requires `fee > 0`: [5](#0-4) 

The remainder `amount − denormalize(normalize(amount))` is permanently frozen in the NEAR bridge escrow with no withdrawal, refund, or sweep function available. The SECURITY.md referenced by the code comment contains no entry for this behavior.

## Impact Explanation
This constitutes permanent freezing of bridged user funds, matching the Critical impact tier: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows" and "decimal/normalization abuse… that changes user or protocol balances." For a 12-decimal gap (e.g., 18 NEAR decimals vs. 6 EVM decimals), the maximum dust per transfer is `10^12 − 1` NEAR-side base units. While small per transfer, the loss is irreversible and accumulates across every non-round transfer with `fee = 0`.

## Likelihood Explanation
The `fee` field is user-supplied; zero is the natural default for self-relayed or protocol-subsidized transfers. Any unprivileged token holder who calls `ft_transfer_call` (the public `ft_on_transfer` entry point) with a non-round amount and `fee = 0` triggers the loss. No special role, admin key, or race condition is required. The condition is repeatable across every such transfer.

## Recommendation
Before locking or burning tokens in `init_transfer_internal`, round the transfer amount down to the nearest multiple of `10^(origin_decimals − decimals)` and return the dust to the sender immediately (or reject amounts that are not already aligned). This ensures `locked_amount == denormalize(normalize(locked_amount))` is always an invariant. Alternatively, store the dust alongside the transfer record and release it to the sender when the transfer message is removed in `sign_transfer_callback` for the `fee = 0` case.

## Proof of Concept
1. Register token `T` with `origin_decimals = 18`, `decimals = 6` (scale factor = `10^12`).
2. User calls `ft_transfer_call` on the NEAR token contract, sending `amount = 1_000_000_000_001` (1 unit + 1 base unit) to the bridge with `fee = 0`.
3. `init_transfer_internal` locks `1_000_000_000_001` base units on NEAR.
4. `sign_transfer` computes `normalize_amount(1_000_000_000_001, {18,6}) = 1` and signs a payload for `1` destination-chain unit.
5. MPC signing succeeds; `sign_transfer_callback` sees `fee.is_zero()` and calls `remove_transfer_message` — the record is deleted.
6. The destination chain receives `1` unit (i.e., `1_000_000` in 6-decimal representation).
7. The `1` base-unit dust (`1_000_000_000_001 − 1_000_000_000_000 = 1`) remains locked in the NEAR bridge escrow forever; no function exists to recover it.

A local unit test can confirm this by calling `normalize_amount(1_000_000_000_001, Decimals { origin_decimals: 18, decimals: 6 })` and verifying the result is `1`, then tracing `init_transfer_internal` → `sign_transfer_callback` with `fee = Fee { fee: U128(0), native_fee: U128(0) }` to confirm `remove_transfer_message` is called and no dust-recovery path is executed.
