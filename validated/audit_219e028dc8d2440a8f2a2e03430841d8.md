### Title
Missing Cryptographic Signature Verification in Peras Vote and Certificate Validation Allows Unprivileged Peer to Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which applies to all block types, implements `validatePerasVote` without verifying the vote's cryptographic signature and implements `validatePerasCert` as an unconditional `Right`. An unprivileged peer can send crafted Peras votes claiming to be any eligible voter (voter IDs are public) and crafted certificates, both of which are accepted without any ownership or authenticity check. This is the direct analog of the external report's pattern: a function uses a resource (a voter identity or certificate) belonging to another party without verifying the caller is authorized to use it.

---

### Finding Description

The `BlockSupportsPeras` class defines two validation methods: `validatePerasVote` and `validatePerasCert`. The only concrete instance in the codebase is the degenerate catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

`validatePerasCert` unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural checks:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [2](#0-1) 

`validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution. It ignores `_params` entirely and never verifies the vote's cryptographic signature:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

Inbound votes from peers are processed by `processVotes`, which calls the `validateVote` callback — bound to `validatePerasVote` — on each received vote. If any vote fails, the batch is rejected and the peer is disconnected; if all pass, votes are stored as `ValidatedPerasVote` and fed into the quorum-tracking logic: [4](#0-3) 

Once enough `ValidatedPerasVote` entries accumulate to reach quorum, `implAddVote` calls `updatePerasRoundVoteStates`, which triggers `forgePerasCert` to produce a `ValidatedPerasCert`. That certificate is then used to boost a block's weight in Peras chain selection: [5](#0-4) 

The `forgePerasCert` degenerate implementation also performs no verification: [6](#0-5) 

The `CryptoSupportsVotingCommittee` class explicitly defines `forgeCert` without a `VotingCommittee` parameter, meaning it cannot verify votes against the committee at forging time. Verification is only available via `verifyCert`, which requires the committee and is never called in the inbound vote path: [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can:

1. Enumerate eligible voter IDs from the public stake distribution.
2. Craft `PerasVote` messages claiming to be those voters, with arbitrary or absent signatures.
3. Send the batch via the Peras vote diffusion mini-protocol. `validatePerasVote` accepts each vote because it only checks stake distribution membership — it never verifies the signature.
4. Once the attacker's fake votes accumulate to quorum, a `ValidatedPerasCert` is forged locally by the victim node, boosting the attacker's chosen block.
5. Alternatively, the attacker sends a crafted `PerasCert` directly; `validatePerasCert` returns `Right` unconditionally, granting the certificate's full weight boost.

The Peras weight boost directly influences chain selection. A successful attack causes honest nodes to prefer an attacker-chosen chain over the canonical chain, constituting a chain-selection safety failure driven entirely by an unprivileged network peer.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

- The degenerate instance is the **only** `BlockSupportsPeras` instance in the codebase; there is no more-specific instance for Cardano blocks.
- Voter IDs (`PerasVoterId`, wrapping a `KeyHash StakePool`) are fully public on-chain.
- The attack requires only a standard peer connection and knowledge of the current stake distribution — no keys, no stake, no operator access.
- The `processVotes` path is reachable from any connected peer via the object-diffusion mini-protocol.

Likelihood is **high** given the zero-barrier entry path, though Peras is still under active development and may not yet be enabled on mainnet.

---

### Recommendation

1. **`validatePerasVote`** must verify the cryptographic signature of the vote against the claimed voter's public key (retrieved from the stake distribution), not merely check that the voter ID is present. The `_params` argument should be used for this purpose.
2. **`validatePerasCert`** must perform actual certificate verification (aggregate signature check, quorum threshold, election ID binding) before returning `Right`.
3. **`forgePerasCert`** should only be called after all constituent votes have passed `validatePerasVote`, mirroring the pattern in `implForgeCert` / `implVerifyCert` in the `CryptoSupportsVotingCommittee` implementations.
4. The TODO stubs (`-- see https://github.com/tweag/cardano-peras/issues/120`) must be resolved before the Peras vote diffusion path is enabled on any network that processes real stake.

### Proof of Concept

```
Attacker (unprivileged peer):
  1. Reads stake distribution; finds eligible voter IDs V1, V2, ..., Vn.
  2. Constructs PerasVote { pvVoteRound = r, pvVoteBlock = B_attacker, pvVoteVoterId = Vi }
     for each Vi — no valid signature required.
  3. Sends batch to victim node via Peras vote diffusion protocol.
  4. processVotes calls validatePerasVote for each vote:
       validatePerasVote _params stakeDistr vote
         | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
     Each vote passes because Vi is in stakeDistr.
  5. implAddVote accumulates votes; quorum reached → forgePerasCert fires.
  6. ValidatedPerasCert for B_attacker is stored with full perasWeight boost.
  7. Chain selection now prefers B_attacker over the honest canonical tip.

Expected: votes rejected due to missing/invalid cryptographic signature.
Actual:   votes accepted; attacker-chosen block receives Peras weight boost.
```

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
