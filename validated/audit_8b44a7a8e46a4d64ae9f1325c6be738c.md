### Title
Peras Vote Verification Bypass: Missing Cryptographic Checks in `validatePerasVote` Allow Any Peer to Forge Quorum Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation performs no cryptographic verification of incoming votes. An unprivileged peer can send crafted `PerasVote` messages impersonating any registered stake pool without possessing the corresponding private key. By impersonating enough pools to exceed the quorum threshold, the attacker causes the receiving node to locally forge a `ValidatedPerasCert` for an adversarially chosen block, boosting that block's chain-selection weight by `perasWeight` (default: 15). This is a direct analog to the external report's pattern: an unchecked/unbounded parameter (zero `maximumPrice`) allows an attacker to gain unanimous control over a voting mechanism — here, the absence of any eligibility or signature check allows an attacker to gain unanimous Peras voting power with no stake at all.

---

### Finding Description

The catch-all `BlockSupportsPeras` instance (explicitly marked as a degenerate stub "for all blks to get things to compile") is the only instance in the codebase and is therefore used for all block types on the production network path.

**Root cause — `validatePerasVote` stub:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

The only check performed is whether the `pvVoteVoterId` (a `KeyHash StakePool`) exists in the local `PerasVoteStakeDistr`. There is no verification of:
- A cryptographic signature proving the sender controls the private key for that voter ID
- A VRF eligibility proof proving the pool was selected for the committee
- Any other authorization [1](#0-0) 

**Network entry path — `processVotes`:**

The production network-facing function `processVotes` in `ObjectPool/PerasVote.hs` calls this stub for every incoming vote batch from a peer. If validation passes (voter ID found in stake distribution), the vote is timestamped and added to the `PerasVoteDB`. [2](#0-1) 

**Quorum accumulation — `updatePerasRoundVoteStates`:**

Once votes accumulate in the `PerasVoteDB`, `updateCandidateVoteState` calls `votesReachQuorum`, which calls `stakeAboveThreshold`. When the total stake of accepted votes for a single block target exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin` (default: 3/4 + 2/100 = 77%), a `ValidatedPerasCert` is forged locally. [3](#0-2) [4](#0-3) 

**Compounding issue — `validatePerasCert` stub:**

The `validatePerasCert` implementation unconditionally accepts any certificate without any validation, meaning certificates received directly from peers via the Object Diffusion protocol are also accepted without cryptographic checks. [5](#0-4) 

**The acknowledged unit-mismatch in `stakeAboveThreshold`:**

An additional code comment explicitly acknowledges that `PerasVoteStake` and `perasQuorumStakeThreshold` may not be in the same units (absolute vs. relative), meaning the quorum comparison itself may be semantically incorrect depending on how the `PerasVoteStakeDistr` is populated. [6](#0-5) 

---

### Impact Explanation

A forged `ValidatedPerasCert` boosts the targeted block's chain-selection weight by `perasWeight` (default: 15). This is the Peras protocol's core chain-selection influence mechanism. An attacker who causes a node to forge a certificate for a non-canonical block causes that node to prefer the adversarial chain over the honest canonical chain, constituting a **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions** (High impact per scope).

The `PerasVoteId` deduplication (`(roundNo, voterId)`) limits the attacker to one fake vote per voter per round, but the attacker can impersonate as many distinct voter IDs as needed — the stake distribution is public. With combined stake ≥ 77% of the distribution, a single round of crafted votes is sufficient to forge a certificate. [7](#0-6) 

---

### Likelihood Explanation

- The stake distribution (`PerasVoteStakeDistr`) is derived from public ledger state; the attacker needs no private information.
- The attack requires only the ability to send network messages to a target node via the Object Diffusion mini-protocol.
- No stake, no keys, no special privileges are required.
- The `processVotes` function is the live production path for handling inbound Peras votes from peers.
- The deduplication check (`Set.member voteId alreadyInDb`) only prevents replaying the same `(roundNo, voterId)` pair — it does not prevent the attacker from submitting votes for many different voter IDs in the same round. [8](#0-7) 

---

### Recommendation

1. **Implement real cryptographic verification in `validatePerasVote`**: The vote must carry a signature over `(roundNo, blockPoint)` verifiable against the public key of the claimed `pvVoteVoterId`. For WFALS, an eligibility proof (VRF output) must also be verified. This is tracked in issue #120.

2. **Implement real cryptographic verification in `validatePerasCert`**: The certificate must carry an aggregate BLS signature verifiable against the public keys of the claimed voters, and the claimed voters must have combined stake above the quorum threshold.

3. **Resolve the `PerasVoteStake` unit ambiguity**: The `stakeAboveThreshold` function must either normalize `PerasVoteStake` before comparison or accept the total stake distribution to perform normalization internally, as the existing comment warns.

4. **Do not deploy the degenerate `BlockSupportsPeras` instance to production**: The stub instance (issue #73) must be replaced with a concrete Cardano-specific instance before Peras is activated on any network.

---

### Proof of Concept

1. Attacker queries the public ledger state to obtain `PerasVoteStakeDistr` — a map of `PerasVoterId → PerasVoteStake` for all registered stake pools.
2. Attacker selects a set of voter IDs whose combined `PerasVoteStake` values sum to ≥ 0.77 (quorum threshold 3/4 + safety margin 2/100).
3. Attacker selects a target block `B` (e.g., a block on a minority fork) and a round number `R`.
4. For each selected voter ID `V_i`, attacker sends a `PerasVote { pvVoteRound = R, pvVoteBlock = B, pvVoteVoterId = V_i }` to the target node via the Object Diffusion mini-protocol.
5. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote` for each vote. Since each `V_i` exists in `stakeDistr`, all votes pass validation and are added to the `PerasVoteDB`.
6. `updatePerasRoundVoteStates` accumulates the votes. When total stake ≥ 0.77, `votesReachQuorum` returns `Just`, and `forgePerasCert` produces a `ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` for block `B`.
7. The forged certificate boosts block `B`'s chain-selection weight by 15, potentially causing the target node's chain selection to prefer the adversarial fork over the canonical chain.

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
