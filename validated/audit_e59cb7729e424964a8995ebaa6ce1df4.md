### Title
Missing Failure Callback in `claim_lost_found` Causes Permanent Loss of User Funds - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
The `claim_lost_found` function removes a user's balance from the `lost_found` map before making a cross-contract call (XCC) to transfer nBTC tokens, but provides no failure callback to restore the balance if the XCC fails. If the nBTC transfer fails (e.g., the nBTC contract is paused during an upgrade), the user's funds are permanently erased from `lost_found` without being received.

### Finding Description
In `claim_lost_found` at `contracts/satoshi-bridge/src/api/bridge.rs` lines 451–460:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)          // ← state mutated: entry deleted
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)  // ← XCC, no .then() callback
}
```

The function:
1. **Deletes** the user's entry from `lost_found` (state committed to storage).
2. **Fires** an XCC to the nBTC contract via `internal_transfer_nbtc`.
3. **Returns** the raw `Promise` with no `.then(…)` failure callback.

In NEAR Protocol, state mutations from a function are committed to storage before any XCC resolves. If the nBTC `ft_transfer` XCC panics or fails (e.g., the nBTC contract is paused, storage is insufficient, or gas runs out), NEAR does **not** roll back the already-committed `lost_found.remove`. The user's balance is permanently destroyed.

A secondary instance of the same pattern exists in `verify_withdraw_burn_callback` at `contracts/satoshi-bridge/src/nbtc/burn.rs` lines 139–141, where a cancel-RBF refund is sent via a detached XCC with no failure callback:

```rust
if refund > 0 {
    self.internal_transfer_nbtc(&btc_pending_info.account_id, refund)
        .detach();   // ← no callback; if this fails, refund is silently lost
}
self.internal_remove_btc_pending_info(&tx_id);

### Impact Explanation
**Medium.** Fits the allowed impact class: *"broken callback rollback"* — permanent loss of user funds without direct theft. The `lost_found` map is the last-resort recovery store for nBTC that could not be delivered to users (e.g., after a failed `cancel_withdraw` RBF). If `claim_lost_found` is called while the nBTC contract is unavailable, the user's entire `lost_found` balance is silently destroyed. No operator intervention can recover it because the on-chain entry is gone and no event records the failed transfer amount. [1](#0-0) 

### Likelihood Explanation
**Low–Medium.** The nBTC contract and the satoshi-bridge contract are separate deployed contracts. The nBTC contract can be independently paused by the DAO (e.g., during a token migration or emergency). The bridge's own `#[pause]` guard does not protect against the nBTC contract being paused. A user who calls `claim_lost_found` during any window where the nBTC contract is paused or temporarily unavailable will permanently lose their funds. The `lost_found` balance is populated by the cancel-withdraw RBF path, so real user funds can accumulate there. [3](#0-2) 

### Recommendation
Add a `#[private]` failure callback that re-inserts the amount into `lost_found` if the transfer XCC fails:

```rust
pub fn claim_lost_found(&mut self) -> Promise {
    assert_one_yocto();
    let account_id = env::predecessor_account_id();
    let amount = self
        .data_mut()
        .lost_found
        .remove(&account_id)
        .expect("The account does not have lostfound");
    self.internal_transfer_nbtc(&account_id, amount)
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_CLAIM_LOST_FOUND_CALLBACK)
                .claim_lost_found_callback(account_id, U128(amount)),
        )
}

#[private]
pub fn claim_lost_found_callback(&mut self, account_id: AccountId, amount: U128) {
    if !is_promise_success() {
        // Restore the balance so the user can retry
        self.data_mut().lost_found.insert(account_id, amount.0);
    }
}
```

Apply the same fix to the detached refund transfer in `verify_withdraw_burn_callback`. [2](#0-1) 

### Proof of Concept
1. User's `cancel_withdraw` RBF completes; the nBTC refund transfer fails, so the bridge stores `amount` in `lost_found[user]`.
2. The DAO pauses the nBTC contract for a routine upgrade.
3. The user (unprivileged) calls `claim_lost_found` with 1 yoctoNEAR attached.
4. `lost_found.remove(&account_id)` executes and is **committed** to NEAR storage — the entry is gone.
5. `internal_transfer_nbtc` fires an XCC to the paused nBTC contract; the call panics.
6. NEAR does not roll back step 4 (already committed). No `.then()` callback exists to restore the entry.
7. The user's nBTC balance in `lost_found` is permanently destroyed; the user receives nothing. [1](#0-0)
