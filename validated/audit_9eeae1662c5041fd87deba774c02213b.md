### Title
Peras Certificate Validation Is a No-Op Stub — Any Peer-Crafted Certificate Is Unconditionally Accepted and Triggers Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The sole production implementation of `validatePerasCert` in the `BlockSupportsPeras` typeclass is a stub that unconditionally returns `Right` for every certificate received, performing no cryptographic, quorum, or structural validation whatsoever. When Peras is enabled, the production inbound handler `makePerasCertPoolWriterFromChainDB` calls this stub with hardcoded default parameters (`mkPerasParams`) instead of the actual configured parameters. Any unprivileged peer can therefore inject an arbitrary crafted `PerasCert` that is accepted, stored in the `PerasCertDB`, and used to artificially boost a chosen block's chain-selection weight, causing the honest node to prefer a non-canonical chain.

### Finding Description

**Root cause — unconditional `Right` in `validatePerasCert`:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a certificate before it is stored and used in chain selection. The only instance in the codebase is the catch-all default:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This always returns `Right`, accepting every certificate without any signature check, quorum check, committee membership check, or round-number sanity check. [1](#0-0) 

**Root cause — hardcoded `mkPerasParams` in the production inbound handler:**

The production inbound handler `makePerasCertPoolWriterFromChainDB`, which is wired directly into the node-to-node `hPerasCertDiffusionClient` handler, calls `validatePerasCert mkPerasParams` — using the hardcoded default parameters rather than any operator-configured value. Both call sites carry an explicit `-- TODO replace when actual plumbing is in place` comment:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**Attacker-controlled entry path:**

The `hPerasCertDiffusionClient` handler in `NodeToNode.hs` is wired unconditionally and calls `makePerasCertPoolWriterFromChainDB`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

Any peer that negotiates Peras support (controlled by `rnFeatureFlags` and the handshake `perasSupport` field) can send a `PerasCert` message over the `perasCertDiffusionProtocol` mini-protocol. The `processCerts` function calls `validateCert` on each received certificate; because `validatePerasCert` always returns `Right`, every certificate passes: [4](#0-3) 

**Chain selection impact:**

Each accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight mkPerasParams = PerasWeight 15`. This boost is stored in the `PerasCertDB` and fed into `weightBoostOfFragment` during chain selection via `WeightedSelectView`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

The `forksAtMostKWeight` rollback guard uses `maxRollbackWeight` (= `k` as `PerasWeight`), so a fake boost of 15 can cause the node to accept a rollback of up to 15 blocks of weight that it would otherwise reject: [6](#0-5) 

Chain selection is triggered immediately after the cert is stored via `ChainDB.addPerasCertAsync`: [7](#0-6) 

**Analogy to M-7:** In M-7, `createFeeDiscount` was never initialized so the discount feature was silently zero. Here, `validatePerasCert` is never implemented so the certificate validation feature is silently a no-op — both are critical security/economic parameters left as stubs with no functional implementation.

### Impact Explanation

**High. Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

A malicious peer with Peras support negotiated can:
1. Craft a `PerasCert` pointing to any block in the target node's VolatileDB.
2. Send it over the `perasCertDiffusionProtocol` mini-protocol.
3. The cert passes validation unconditionally and is stored with `vpcCertBoost = 15`.
4. Chain selection is re-triggered for the boosted block; the node may switch to a fork it would otherwise reject.
5. Nodes that did not receive the fake cert will not apply the boost, causing chain selection divergence between honest nodes — a consensus safety failure under Peras.

Additionally, because the same fake cert can be re-sent to multiple nodes selectively, an attacker can cause a subset of the network to prefer a different chain, breaking the Common Prefix property that Peras is designed to strengthen.

### Likelihood Explanation

Peras is an experimental feature gated behind `rnFeatureFlags` and is not enabled on mainnet today. However:
- The vulnerability is fully reachable on any private testnet or staging environment running Peras.
- The attack requires only a valid peer connection with Peras support negotiated — no keys, no stake, no privileged access.
- The exploit is deterministic and requires only sending a single well-formed CBOR-encoded `PerasCert` message.
- The `TODO` comments explicitly acknowledge the missing implementation, confirming this is a known incomplete stub shipped in production code. [8](#0-7) 

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before enabling Peras on any network. At minimum, validate: certificate round number is within the expected window, the boosted block point is structurally valid, and the aggregate signature over the committee votes is cryptographically correct.

2. **Remove the hardcoded `mkPerasParams`** in `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB`. The actual `PerasCfg blk` must be threaded from the node's `TopLevelConfig` so that operator-configured parameters are used. [9](#0-8) 

3. **Gate the Peras cert diffusion handler** so that it is only active when Peras is fully implemented and enabled, not merely when the feature flag is set.

4. **Add a runtime assertion** (or compile-time guard) that prevents `validatePerasCert` from being called with the stub implementation in a non-test context.

### Proof of Concept

On a private testnet with Peras enabled (`rnFeatureFlags` includes the Peras flag):

1. Connect to the target node as a peer with Peras support negotiated.
2. Identify a block `B` in the target's VolatileDB that is on a competing fork (e.g., one block behind the current tip on a side branch).
3. Construct a `PerasCert` CBOR message:
   ```
   PerasCert { pcCertRound = <any fresh round number>, pcCertBoostedBlock = blockPoint B }
   ```
4. Send it via the `perasCertDiffusionProtocol` mini-protocol.
5. **Expected result:** `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`. The cert is stored and `chainSelectionForBlock` is triggered for `B`. The node's chain selection now adds weight 15 to any chain containing `B`, potentially causing it to switch to the fork containing `B`.
6. **Observed divergence:** Other honest nodes that did not receive the fake cert do not apply the boost and remain on the canonical chain, producing a chain selection split.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
