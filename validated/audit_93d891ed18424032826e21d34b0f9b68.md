### Title
Missing Caller-Ownership Check in `request_refund` Allows Attacker to Redirect Victim's BTC Refund to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`internal_request_refund` never verifies that the caller is the intended recipient of the deposit (`deposit_msg.near_account_id`). When a deposit's `DepositMsg` carries no pre-authorized `refund_address`, any unprivileged account that knows the victim's `deposit_msg` can front-run the legitimate refund request and supply an attacker-controlled Bitcoin address, causing the bridge to refund the victim's BTC to the attacker.

---

### Finding Description

`internal_request_refund` accepts a caller-supplied `deposit_msg` and a caller-supplied `refund_address`: [1](#0-0) 

The only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for ordinary deposits), the branch is skipped entirely and the caller's arbitrary `refund_address` is accepted without restriction.

The callback that finalises the request only checks that the transaction output's `script_pubkey` matches the deposit address derived from the provided `deposit_msg`; it never checks that `env::predecessor_account_id()` equals `deposit_msg.near_account_id`: [3](#0-2) 

The accepted `refund_address` is then stored verbatim in the `RefundRequest` and later used as the Bitcoin destination when the refund transaction is built and signed: [4](#0-3) 

There is no point in the entire `request_refund → request_refund_callback` path where the bridge asserts `predecessor == deposit_msg.near_account_id`.

---

### Impact Explanation

An attacker who successfully front-runs the victim's refund request causes the bridge's MPC-signed Bitcoin transaction to pay the attacker's Bitcoin address instead of the victim's. The victim's deposited BTC is permanently transferred to the attacker. This is a direct, irreversible theft of user funds — matching the Critical impact class: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

The `deposit_msg` is not a secret:

1. The deposit address is derived deterministically from `deposit_msg` (including `near_account_id`). Anyone who observes the Bitcoin deposit address can reconstruct the `deposit_msg` if the derivation scheme is known (it is documented in the bridge).
2. If the victim previously attempted `verify_deposit` (even unsuccessfully), the `deposit_msg` is visible in NEAR transaction history.
3. A relayer or any on-chain observer can monitor Bitcoin for unverified deposits and race to submit `request_refund` first.

The `unsafe_refund_timelock_sec` gives the DAO a window to reject suspicious requests, but the DAO is not guaranteed to monitor every request, and the timelock is a delay — not a prevention. Once the timelock expires and `execute_refund` is called, the BTC is irreversibly sent to the attacker's address.

---

### Recommendation

Add an explicit ownership check at the start of `internal_request_refund` (or inside `request_refund_callback` where `deposit_msg` is validated):

```rust
require!(
    env::predecessor_account_id().as_str() == deposit_msg.near_account_id,
    "Caller is not the intended deposit recipient"
);
```

Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so that the refund destination is fixed at deposit time and cannot be overridden by an arbitrary caller.

---

### Proof of Concept

1. **Victim** generates a deposit address from `DepositMsg { near_account_id: "victim.near", refund_address: None, … }` and sends 1 BTC to it. The deposit is never verified (e.g., wrong proof, or the victim simply wants a refund).

2. **Attacker** observes the Bitcoin UTXO, reconstructs `deposit_msg` (derivable from the public deposit address), and calls `request_refund` with:
   - `deposit_msg` = victim's original `DepositMsg` (with `refund_address: None`)
   - `refund_address` = attacker's own Bitcoin address
   - `tx_bytes` + `proof` = the victim's deposit transaction and its Merkle proof

3. `request_refund_callback` verifies the proof and that the output script matches the deposit address derived from the victim's `deposit_msg`. Both checks pass. The `RefundRequest` is stored with `refund_address = attacker_btc_address`.

4. After `unsafe_refund_timelock_sec` elapses (assuming the DAO does not reject), anyone calls `execute_refund`. The bridge builds and MPC-signs a Bitcoin transaction paying 1 BTC (minus gas fee) to the attacker's address.

5. The victim receives nothing. The attacker receives the victim's BTC.
