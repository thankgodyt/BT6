Looking at the production token contract for an analog to the "silent discard of token operation" vulnerability class.

The key analog is in `contracts/nbtc/src/lib.rs` in the `safe_mint` function.

---

### Title
Silent Token Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account **before** checking whether the intended recipient has a storage registration. If the recipient is unregistered, the function silently returns `U128(0)` without reverting, leaving the freshly minted tokens permanently stranded in the bridge's balance and the user's BTC deposit unrecoverable without operator intervention.

### Finding Description
`safe_mint` executes in this order:

1. **Mint to bridge** (line 112): `self.token.internal_deposit(&self.bridge_id, amount.into());`
2. **Check recipient registration** (line 114): `if self.token.accounts.get(&account_id).is_none()`
3. **Silent early return** (line 115): `return PromiseOrValue::Value(U128(0));` [1](#0-0) 

The check at line 114 comes **after** the irreversible `internal_deposit` at line 112. When the recipient has no storage registration, the function returns zero without reverting, without emitting any error event, and without undoing the deposit. The minted tokens now sit in `bridge_id`'s balance with no automated path back to the user.

This is structurally identical to the external report's root cause: a token-management function silently discards the intended operation (there: allowance decrease; here: token delivery) while the side-effect (there: allowance unchanged; here: tokens minted to bridge) persists.

### Impact Explanation
- The user's BTC is locked in the bridge's deposit address on-chain.
- The user receives zero nBTC.
- The minted nBTC tokens accumulate in the bridge's own balance, inflating `bridge_id`'s balance relative to actual user-backed supply.
- Recovery requires a privileged operator to manually call `internal_transfer_nbtc` to redirect the stranded tokens, which is operator-gated and not guaranteed.

This matches the **Medium** impact category: *broken callback rollback / stuck bridge state requiring operator intervention*, and also touches *permanent burning below backed supply* if the stranded tokens are later consumed by the bridge's own fee or burn accounting. [2](#0-1) 

### Likelihood Explanation
Any user who deposits BTC to the bridge without first calling `storage_deposit` on the nBTC token contract will trigger this path. NEP-141 storage registration is a separate, non-obvious prerequisite that many users omit, especially when interacting programmatically or via a relayer that does not pre-register the recipient. The `safe_mint` function's name and the existence of the unregistered-account branch (line 114) confirm this is a known edge case, but the handling is incorrect.

### Recommendation
Reverse the order of operations: check recipient registration **before** minting to `bridge_id`. If the account is unregistered, either:
- Revert with a clear error, or
- Auto-register the account (as `mint_inner` does via `internal_register_account`) before depositing.

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

### Proof of Concept
1. User deposits BTC to the bridge without calling `storage_deposit` on the nBTC contract for their NEAR account.
2. Bridge verifies the deposit and calls `safe_mint(user_account, amount, msg)` on the nBTC contract.
3. `internal_deposit(&self.bridge_id, amount)` executes — `bridge_id`'s nBTC balance increases by `amount`.
4. `self.token.accounts.get(&user_account)` returns `None` (unregistered).
5. Function returns `U128(0)` — no transfer, no revert, no event.
6. User's BTC is locked in the bridge deposit address; user holds zero nBTC; `amount` nBTC is stranded in `bridge_id`.
7. Operator must manually invoke `internal_transfer_nbtc` to recover funds. [3](#0-2)

```rust
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```
