### Title
Unrestricted `sign_btc_transaction` Allows Any Caller to Trigger MPC Signing with Attacker-Controlled `key_version` — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` in the `satoshi-bridge` contract is publicly callable by any NEAR account. It accepts an attacker-controlled `key_version` parameter that is forwarded directly to the NEAR Chain Signatures MPC network. An attacker who observes a pending withdrawal can race the legitimate relayer, supplying a wrong `key_version` and causing the MPC to produce a signature for a different derived public key. The resulting signature is invalid for the Bitcoin UTXO's locking script, making the withdrawal transaction unbroadcastable and leaving the user's nBTC locked in the bridge until operator intervention.

---

### Finding Description

`sign_btc_transaction` carries only `#[payable]` and `#[pause(except(roles(Role::DAO)))]`:

```rust
// contracts/satoshi-bridge/src/api/chain_signatures.rs  lines 19-43
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
``` [1](#0-0) 

There is no `#[access_control_any]` and no `#[trusted_relayer]` decorator. Compare this with every other state-mutating bridge function: deposit verification carries `#[trusted_relayer]`, admin operations carry `#[access_control_any(roles(Role::DAO, Role::Operator))]`, and callbacks carry `#[private]`. [2](#0-1) [3](#0-2) 

The `key_version` value is passed verbatim to the NEAR Chain Signatures contract. In the NEAR MPC protocol, `key_version` selects which generation of the threshold key is used for derivation. A signature produced under `key_version = N` is valid only for the public key committed to by that version. The Bitcoin deposit address is derived from the bridge's MPC key at the version the bridge was configured with (typically 0). If the MPC signs with a different `key_version`, the resulting signature satisfies a different public key and is therefore invalid for the UTXO's `script_pubkey`.

The `btc_pending_sign_id` (the PSBT hash) is emitted publicly in a `GenerateBtcPendingInfo` event: [4](#0-3) 

Any observer can therefore learn the pending ID and race the relayer.

---

### Impact Explanation

After `sign_btc_transaction` is called with a wrong `key_version`, the MPC produces and returns a signature. That signature is stored in the PSBT's `signatures` array for the targeted `sign_index`. The state machine marks that input as signed. When the relayer later attempts to broadcast the fully-signed transaction, Bitcoin nodes reject it because the witness does not satisfy the UTXO's locking script. The user's nBTC tokens were already transferred to the bridge at withdrawal initiation (the NEP-141 `ft_transfer_call` flow moves tokens to the bridge before signing begins), so they are now held by the bridge with no valid Bitcoin transaction to finalize the withdrawal. Recovery requires privileged operator action (e.g., `cancel_withdraw` by DAO/Operator) to unwind the state.

This matches the allowed impact: **Medium — stuck bridge state requiring operator intervention** and **attacker-triggered temporary locking of bridged funds**. [5](#0-4) 

---

### Likelihood Explanation

Medium. The `GenerateBtcPendingInfo` event is emitted on-chain and is trivially observable. The attacker needs only to submit a single NEAR transaction before the relayer does. The relayer is an off-chain service with normal network latency; a front-running attacker on NEAR (where block times are ~1 second) can reliably win the race for high-value withdrawals. No special privilege or leaked key is required — only a funded NEAR account.

---

### Recommendation

Add `#[trusted_relayer]` (consistent with all other signing-related bridge entry points) or `#[access_control_any(roles(Role::DAO, Role::Operator))]` to `sign_btc_transaction`. Additionally, validate `key_version` against the bridge's configured expected key version before forwarding to the MPC, so even a privileged caller cannot accidentally supply a stale version.

---

### Proof of Concept

1. Alice calls `nbtc.ft_transfer_call(bridge, 100_000, WithdrawMsg{...})`. The bridge creates a PSBT and emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Attacker observes the event and immediately calls:
   ```
   bridge.sign_btc_transaction(
       btc_pending_sign_id = "abc123",
       sign_index = 0,
       key_version = 1,   // wrong version; bridge uses version 0
   )
   ```
3. The MPC signs input 0 under key version 1, producing a signature `sig_v1`. This signature is stored in the PSBT at `signatures[0]`.
4. The legitimate relayer later calls `sign_btc_transaction("abc123", 0, 0)`. Depending on whether the slot is already filled, the relayer's call either overwrites with the correct signature or is a no-op (if the state machine already advanced past this input).
5. If the attacker's signature is retained, the assembled Bitcoin transaction carries `sig_v1` for an input locked to the key-version-0 address. Bitcoin nodes reject the transaction as invalid.
6. Alice's nBTC remains locked in the bridge. Only a DAO/Operator `cancel_withdraw` can recover the state. [1](#0-0) [6](#0-5) [7](#0-6)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
