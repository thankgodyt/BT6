### Title
Caller-Supplied Refund Address Without Ownership Verification Enables BTC Theft When `deposit_msg.refund_address` Is None - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None`, any caller can invoke `request_refund` and supply an arbitrary attacker-controlled BTC address as the `refund_address`. Because there is no check that the caller is the original depositor, and because only one refund request can exist per UTXO, an attacker can front-run the victim's refund request and redirect the BTC to an address the victim does not control.

### Finding Description

The `DepositMsg` struct contains an optional `refund_address` field: [1](#0-0) 

When a deposit is never finalized, `request_refund` is the recovery path. Inside `internal_request_refund`, the only guard on the caller-supplied `refund_address` is: [2](#0-1) 

This check only fires when `deposit_msg.refund_address` is `Some`. When it is `None`, the caller-supplied `refund_address` is accepted unconditionally and stored verbatim in the `RefundRequest`: [3](#0-2) 

There is no verification that the caller is the original depositor or has any relationship to the deposit UTXO. The `deposit_msg` itself is public (it is emitted in events and used to derive the deposit address on-chain), so any observer can reconstruct it.

Furthermore, the refund request is keyed by `utxo_storage_key` and a duplicate check prevents a second request for the same UTXO: [4](#0-3) 

Once the attacker's request is stored, the victim cannot submit their own `request_refund` for the same UTXO. The victim also cannot call `reject_refund` because that requires DAO/Operator role or proof that the UTXO was already finalized via deposit: [5](#0-4) 

The only protection is the `unsafe_refund_timelock_sec` (default 14 days) and DAO/Operator intervention: [6](#0-5) [7](#0-6) 

After the 14-day window, `execute_refund` can be called by anyone to build and sign the refund PSBT, sending the BTC to the attacker's address: [8](#0-7) 

### Impact Explanation

If the DAO/Operator fails to reject the malicious refund request within `unsafe_refund_timelock_sec`, the BTC is permanently sent to the attacker's address via the MPC signing pipeline. The victim's BTC is irreversibly lost. Even if the DAO/Operator does reject it, the victim's funds are locked for the duration of the attack window and the victim suffers a forced delay in recovering their BTC.

This matches: **Critical — Significant loss, theft, or permanent locking of user funds** (if DAO/Operator is unavailable or slow), or **Medium — attacker-triggered temporary locking of bridged funds** (if DAO/Operator acts in time).

### Likelihood Explanation

- The `deposit_msg` for any unfinalized deposit is observable on-chain (emitted in events, used to derive the deposit address).
- The attacker only needs to attach the required NEAR storage deposit to call `request_refund`.
- Users who do not pre-specify `refund_address` in their `DepositMsg` (a common case, since the field is optional and `skip_serializing_if = "Option::is_none"`) are fully exposed.
- The 14-day window is a meaningful but not absolute mitigation — DAO/Operator unavailability, key compromise, or governance delay can allow the attack to succeed.

### Recommendation

1. **Require `deposit_msg.refund_address` to always be set** (make it non-optional). This eliminates the caller-supplied address path entirely and is the cleanest fix, analogous to the "mandatory parameter" suggestion in the external report.
2. Alternatively, if the optional field is kept, **require the caller of `request_refund` to prove ownership** — e.g., by requiring the caller's NEAR account to match `deposit_msg.recipient_id`, so only the intended nBTC recipient can initiate a refund.
3. **Allow the original depositor (`deposit_msg.recipient_id`) to reject a pending refund request** without requiring DAO/Operator role, so victims are not entirely dependent on operator intervention.

### Proof of Concept

1. Alice deposits BTC and generates a `DepositMsg` with `recipient_id: "alice.near"` and `refund_address: None`. The deposit address is derived and published on-chain.
2. The relayer goes offline; the deposit is never finalized.
3. Bob observes Alice's `DepositMsg` from on-chain events and calls:
   ```
   request_refund(
     deposit_msg = Alice's DepositMsg (refund_address: None),
     refund_address = "bc1q_bob_address",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid inclusion proof>,
     gas_fee = None
   )
   ```
4. The contract stores a `RefundRequest` with `refund_address = "bc1q_bob_address"`. Alice cannot submit her own request (duplicate check fails). Alice cannot reject Bob's request (not DAO/Operator, UTXO not deposited).
5. After 14 days, if DAO/Operator has not rejected the request, Bob calls `execute_refund`. The MPC pipeline signs a Bitcoin transaction sending Alice's BTC to Bob's address.
6. Alice's BTC is permanently lost. [9](#0-8) [10](#0-9)

impl Contract {
    /// Submit a refund request. Verifies the BTC transaction via Light Client first.
    /// If `deposit_msg.refund_address` is set, it must match the provided `refund_address`.
    /// If `deposit_msg.refund_address` is None, the provided `refund_address` is used.
    #[allow(clippy::too_many_arguments)]
    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
