Audit Report

## Title
Cross-Chain Replay of MPC-Signed MetadataPayload via Missing Chain Domain Separator in `deploy_token` — (`starknet/src/bridge_types.cairo`)

## Summary

`MetadataPayload::to_borsh()` in the Starknet OmniBridge produces byte-for-byte identical Borsh output to the EVM `deployToken` Borsh encoding, with no chain-domain separator. Because both the EVM and Starknet OmniBridge instances verify against the same `omni_bridge_derived_address` (the shared NEAR MPC secp256k1 key), a valid MPC signature obtained for an EVM `deployToken` call can be submitted unchanged to Starknet `deploy_token` and will pass `_verify_borsh_signature`, deploying a bridge token on Starknet without any Starknet-scoped MPC authorization.

## Finding Description

**Root cause — Starknet `MetadataPayload::to_borsh()` omits chain ID:**

`starknet/src/bridge_types.cairo` lines 36–44 encode: `[PayloadType::Metadata=1] | borsh_string(token) | borsh_string(name) | borsh_string(symbol) | [decimals]` — no chain identifier is included.

**EVM `deployToken` Borsh encoding is byte-for-byte identical:**

`evm/src/omni-bridge/contracts/OmniBridge.sol` lines 142–148 encode: `bytes1(Metadata=1) | Borsh.encodeString(token) | Borsh.encodeString(name) | Borsh.encodeString(symbol) | bytes1(decimals)` — the same structure.

**Starknet `deploy_token` calls `to_borsh()` with no chain_id:**

`starknet/src/omni_bridge.cairo` line 205: `_verify_borsh_signature(ref self, @payload.to_borsh(), signature);`

**`_verify_borsh_signature` verifies against the shared `omni_bridge_derived_address`:**

`starknet/src/omni_bridge.cairo` lines 398–406 compute `keccak256(borsh_bytes)` and call `verify_eth_signature(..., self.omni_bridge_derived_address.read())`. If both chains share the same derived address (the intended NEAR MPC design), the EVM-generated signature passes on Starknet.

**Contrast with `fin_transfer` — which correctly binds chain_id:**

`starknet/src/bridge_types.cairo` lines 61–70 show `TransferMessagePayload::to_borsh(chain_id: u8)` encodes `chain_id` twice. `starknet/src/omni_bridge.cairo` lines 252–254 pass `self.omni_bridge_chain_id.read()` into it.

**No replay protection on `deploy_token`:**

`starknet/src/omni_bridge.cairo` lines 207–209 only check `ERR_TOKEN_ALREADY_DEPLOYED` (same token_id on the same chain). A cross-chain replay deploys a token not yet existing on Starknet, so this guard does not fire. Unlike `fin_transfer`, there is no nonce bitmap (`completed_transfers`) for `deploy_token`.

**CLAUDE.md explicitly acknowledges chain_id binding as the replay-prevention mechanism** (`starknet/CLAUDE.md` line 45), but it is only applied to `TransferMessagePayload`, not `MetadataPayload`.

## Impact Explanation

An attacker who observes a legitimate MPC-signed `deployToken` transaction on EVM can extract the `(r, s, v)` signature and `MetadataPayload` fields, then submit them verbatim to Starknet `deploy_token`. The Starknet contract computes `keccak256(borsh(1 | token | name | symbol | decimals))`, which is identical to the EVM hash, and `verify_eth_signature` passes because the same `omni_bridge_derived_address` is configured on both chains. A bridge token is deployed on Starknet without any Starknet-scoped MPC signing event.

This is a **chain/domain separation flaw and MPC authorization bypass for the token deployer role**, matching the allowed critical impact: *"Unauthorized transaction, authorization bypass, role bypass, pause bypass, or signer/prover verification bypass that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions"* and *"Cross-chain replay … or chain/domain separation flaw enabling invalid finalization."*

## Likelihood Explanation

The precondition — both chains sharing the same `omni_bridge_derived_address` — is not a misconfiguration; it is the intended design of the NEAR MPC architecture, where one derived secp256k1 key signs for all chains. All EVM `deployToken` transactions are public on-chain, so the signature and payload are trivially observable. No privileged access is required. Any unprivileged external user can execute this attack by submitting a public contract call to Starknet `deploy_token`.

## Recommendation

Add the Starknet chain ID to `MetadataPayload::to_borsh()`, mirroring the pattern already used in `TransferMessagePayload::to_borsh()`:

```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);   // domain separator
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
```

Update `deploy_token` to pass `self.omni_bridge_chain_id.read()`, matching the `fin_transfer` pattern. The EVM and NEAR MPC signing infrastructure must also be updated to include the destination chain ID when producing MetadataPayload signatures.

## Proof of Concept

1. On EVM testnet, call `deployToken(sig, {token:"test.near", name:"Test", symbol:"TST", decimals:18})` with a test secp256k1 key as `nearBridgeDerivedAddress`. Record `(r, s, v)`.
2. Deploy a Starknet OmniBridge instance configured with the **same** `omni_bridge_derived_address` (same secp256k1 key).
3. Submit `deploy_token(Signature{r,s,v}, MetadataPayload{token:"test.near", name:"Test", symbol:"TST", decimals:18})` to the Starknet instance.
4. The call succeeds: `_verify_borsh_signature` passes because `keccak256(borsh(1|"test.near"|"Test"|"TST"|18))` is identical on both chains and the signer matches.
5. A bridge token is deployed on Starknet with no fresh MPC signing event for Starknet.

The existing test infrastructure in `starknet/tests/test_contract.cairo` lines 82–93 (`build_deploy_token_message`) and `evm/tests/helpers/signatures.ts` lines 85–107 (`metadataSignature`) already demonstrate the exact signing and verification path; the PoC requires only substituting a signature generated by the EVM test helper into the Starknet test, confirming the hash collision.
