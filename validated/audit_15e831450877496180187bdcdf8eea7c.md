### Title
Missing Vote Signature Validation in `validatePerasVote` Allows Forged Votes to Artificially Reach Peras Quorum — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` method in the `BlockSupportsPeras` class is a stub that only checks whether the voter has stake in the stake distribution, without verifying the vote's cryptographic signature or any other eligibility proof. An unprivileged peer can therefore forge `ValidatedPerasVote` values for any voter with positive stake, submit them to the node, and artificially drive the Peras quorum tally for an attacker-chosen block past the threshold — causing the node to forge and accept an invalid Peras certificate that boosts that block in chain selection.

---

### Finding Description

`validatePerasVote` is the sole gate that converts a raw `PerasVote` into a `ValidatedPerasVote`. The current production implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The function ignores `_params` entirely and performs no cryptographic check. Any `PerasVote` whose `pvVoteVoterId` maps to a positive stake entry passes validation and is returned as a `ValidatedPerasVote` carrying that stake weight.

The downstream `implAddVote` in `PerasVoteDB/Impl.hs` correctly deduplicates by `PerasVoteId = (roundNo, voterId)` using `pvdsVoteIds`:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
``` [2](#0-1) 

This deduplication prevents the *same* `(roundNo, voterId)` pair from being counted twice. However, it does not help when the attacker forges votes for *distinct* voter IDs — each forged vote carries a different `PerasVoteId` and passes the deduplication check. The attacker can enumerate as many eligible voter IDs as needed from the public stake distribution and forge a vote for each one, accumulating stake in `updateTargetVoteTally`:

```haskell
(pvaVotes', pvaTotalStake')
  | (Nothing, votes') <- swapVote vote ptvtVotes =
      (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
  | otherwise =
      (ptvtVotes, ptvtTotalStake)
``` [3](#0-2) 

Once the accumulated stake crosses the quorum threshold, `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` is stored and propagated: [4](#0-3) 

The `ValidatedPerasCert` boosts the attacker-chosen block in chain selection, making it resistant to rollback beyond the Peras security parameter.

The analogy to the external report is direct: just as `moveVotes()` lacked the `s_hasVotedByTokenId` check that `_update()` had — allowing a voter to inflate their own power — `validatePerasVote` lacks the signature check that the committee-level `verifyVote` implementations (`implVerifyVote` in `EveryoneVotes.hs` and `WFALS.hs`) correctly perform, allowing an attacker to inflate the total vote power toward quorum for any target. [5](#0-4) [6](#0-5)

### Impact Explanation

**Critical — Bypass of Peras voting/certificate checks.**

A node that accepts forged votes will forge a `ValidatedPerasCert` for an attacker-chosen block. That certificate is then used by the chain-selection logic to boost that block, making it effectively immune to rollback for the duration of the Peras boost window. This constitutes unauthorized certificate acceptance and a chain-selection manipulation reachable by any unprivileged peer that can submit votes to the node.

---

### Likelihood Explanation

**High.** The stake distribution is publicly observable on-chain. The `PerasVote` wire format is known. An attacker needs only to construct `PerasVote` records with valid voter IDs (drawn from the stake distribution) and submit them via the vote-submission miniprotocol. No key material, operator access, or stake majority is required. The number of forged votes needed equals the number of distinct voter IDs whose combined stake exceeds the quorum threshold.

---

### Recommendation

Replace the stub with a full implementation that:

1. Verifies the cryptographic signature on the vote body against the voter's registered verification key (analogous to `verifyVoteSignature` used in `implVerifyVote`).
2. For WFALS-style committees, additionally verifies the VRF eligibility proof.
3. Checks that the vote's `pvVoteRound` and `pvVoteBlock` are within acceptable bounds.

The committee-level `verifyVote` implementations in `EveryoneVotes.hs` and `WFALS.hs` already contain the correct cryptographic checks and should be consulted as the reference implementation.
