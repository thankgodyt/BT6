### Title
Chain-Selection Bypass via Hardcoded Empty Peras Weight Snapshot in `checkPreferTheirsOverOurs` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` instead of passing the actual Peras weight snapshot when deciding whether to disconnect from a peer whose header is beyond the forecast horizon. This is structurally identical to the H-06 root cause: a check uses the wrong reference value, making it too restrictive and blocking a legitimate state transition. When Peras is active, the check ignores certificate-derived weight boosts, causing the node to incorrectly disconnect from peers offering the canonical chain and remain on a non-canonical one.

---

### Finding Description

When a header arrives beyond the forecast horizon, the ChainSync client cannot yet validate it. Before blocking to wait for the ledger to advance, it calls `checkPreferTheirsOverOurs` to decide whether the candidate chain is even worth waiting for. If the candidate is not preferred over the node's current chain, the client throws `CandidateTooSparse` and disconnects.

The function is:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded empty, ignores Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

The rest of the chain-selection pipeline — `initialChainSelection`, `chainSelectionForBlock`, and `chainSelection` — all receive and use the real `weights :: PerasWeightSnapshot blk` parameter: [2](#0-1) [3](#0-2) 

`preferAnchoredCandidate` branches on whether the snapshot is empty. With a non-empty snapshot it computes `weightedSelectView` over the suffix after the intersection, incorporating Peras certificate boosts. With `emptyPerasWeightSnapshot` it falls back to a pure block-count comparison: [4](#0-3) 

`weightedSelectView` accumulates `weightBoostOfFragment` — the sum of all Peras certificate boosts on the fragment — into `wsvTotalWeight`, which is the primary sort key: [5](#0-4) 

So `checkPreferTheirsOverOurs` evaluates preference using only block count, while every other chain-selection site uses the full Peras-weighted comparison. This is the exact structural analog of H-06: the check uses the wrong reference value (`emptyPerasWeightSnapshot` instead of the live snapshot), making it too restrictive and blocking a legitimate state transition.

---

### Impact Explanation

When Peras is active and the canonical chain carries certificate weight boosts that make it heavier than the node's current chain by `wsvTotalWeight` but not by raw block count alone, `checkPreferTheirsOverOurs` returns `ShouldNotSwitch` (wrong answer) and throws `CandidateTooSparse`. The ChainSync client disconnects from the peer. The node stays on its current, non-canonical chain.

If every peer offering the canonical chain also happens to present a header beyond the forecast horizon at the moment of the check (a normal condition during syncing or after a slot gap), the node can be persistently stuck on the wrong chain. This is a **chain-selection bug that causes an honest node to prefer a non-canonical, less-secure chain**, matching the High impact tier.

---

### Likelihood Explanation

The condition requires:
1. Peras is active and has produced certificates that boost blocks on the canonical chain.
2. The canonical chain is heavier by Peras weight but not by raw block count (e.g., the canonical chain has the same or fewer blocks but carries certificate boosts).
3. A header on the canonical chain arrives beyond the forecast horizon (a normal occurrence during initial sync or after a network partition).

All three conditions are realistic once Peras is deployed. The TODO comment in the source explicitly acknowledges the problem and links to a tracking issue, confirming the developers recognise the inconsistency. [6](#0-5) 

---

### Recommendation

Pass the actual `PerasWeightSnapshot` (already available in the enclosing `ChainSyncClientEnv`) to `preferAnchoredCandidate` inside `checkPreferTheirsOverOurs`, replacing the hardcoded `emptyPerasWeightSnapshot`. Alternatively, remove the entire `checkPreferTheirsOverOurs` guard as the TODO suggests, since the Genesis density check already handles the underlying concern more correctly.

The fix is directly analogous to the H-06 mitigation: replace the wrong reference value with the correct one so the check evaluates the same state that the rest of the pipeline uses.

---

### Proof of Concept

1. Peras is active; certificates have been issued for blocks on the canonical chain, giving those blocks a non-zero `weightBoostOfFragment`.
2. The canonical chain has the same block count as the node's current chain but a higher `wsvTotalWeight` due to Peras boosts.
3. A peer sends a header on the canonical chain whose slot is beyond the current forecast horizon.
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` because `prj lst == Nothing`.
5. Inside `checkPreferTheirsOverOurs`, `preferAnchoredCandidate` is called with `emptyPerasWeightSnapshot`. Because `isEmptyPerasWeightSnapshot` is `True`, it falls back to the block-count path and returns `ShouldNotSwitch EQ` (or `GT` if the node's chain is longer by one block).
6. The guard fails; `throwSTM CandidateTooSparse` fires.
7. The ChainSync client disconnects from the peer.
8. The node remains on its current, non-canonical chain indefinitely if no other peer can serve the canonical chain without triggering the same condition.

The root cause — using the wrong reference value in a preference check — is identical to H-06's `fromLocked.end` vs `locked_.end` mistake, and the consequence is the same class of harm: a legitimate state transition (adopting the canonical chain) is blocked by an overly restrictive guard.

      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of

              ShouldNotSwitch o -> ShouldNotSwitch o
