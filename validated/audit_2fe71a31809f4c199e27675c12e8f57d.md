### Title
Silent nBTC Minting to Bridge Account When Recipient Is Unregistered in `safe_mint` - (File: contracts/nbtc/src/lib.rs)

### Summary

The `safe_mint` function in the nbtc contract unconditionally mints tokens to the bridge's own account **before** checking whether the intended recipient has a registered storage account. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens. Due to NEAR's cross-contract call semantics, the nbtc state change (the mint to `bridge_id`) is already committed and cannot be rolled back by the bridge's callback, leaving nBTC permanently stuck in the bridge's own token balance while the user's BTC remains locked in the bridge's UTXO pool.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124) executes in this order:

1. **Line 112** — `self.token.internal_deposit(&self.bridge_id, amount.into())` — tokens are minted into the bridge contract's own nbtc account.
2. **Lines 114–116** — only *after* minting does the function check whether `account_id` is registered:

```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
```

If the recipient is unregistered, the function returns `U128(0)` without ever transferring the freshly minted tokens. [1](#0-0) 

This is the direct analog of the external report's pattern: just as `stake` in SafEth silently accepted ETH and skipped all processing when `derivativeCount == 0`, `safe_mint` silently mints nBTC and skips the transfer when the recipient has no storage account.

In NEAR's execution model, the nbtc contract's state changes are finalized when its receipt completes. Even if the bridge's callback subsequently panics (which is the documented intent for safe-deposit failures — "reverts the whole transaction if minting fails"), **the nbtc contract's `internal_deposit` is not rolled back**. The tokens remain credited to `self.bridge_id` in the nbtc token ledger with no automatic recovery path.

The safe-deposit flow is triggered when `deposit_msg.safe_deposit` is `Some(..)` in `verify_deposit_v2`: [2](#0-1) 

The documented contract for this path is that the caller must pre-register the recipient's storage. If the recipient is not registered at call time, `safe_mint` silently inflates the bridge's nbtc balance instead of reverting cleanly. [3](#0-2) 

### Impact Explanation

- **nBTC supply inflation**: tokens are minted to the bridge's own account without a corresponding user-accessible balance, breaking the 1:1 BTC-backing invariant.
- **User BTC locked**: the deposit UTXO is consumed by the bridge's verification flow; the user receives no nBTC.
- **Stuck bridge state requiring operator intervention**: the bridge operator must manually call `burn` on the bridge's nbtc balance to restore the invariant; there is no automatic recovery (the safe-deposit path explicitly has no lost-and-found).

This matches the allowed Medium impact: *"Harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention."*

### Likelihood Explanation

The `recipient_id` inside `DepositMsg` is user-controlled — the user encodes it when generating their deposit address. A user who specifies a `recipient_id` that has never called `storage_deposit` on the nbtc contract (or whose account was closed) will trigger this path. The relayer submits the proof as-is and has no obligation to pre-validate recipient registration. Because the deposit address is derived from the full `DepositMsg`, the relayer cannot alter `recipient_id` without invalidating the proof, so the bridge processes whatever the user originally encoded.

### Recommendation

Move the registration check **before** `internal_deposit` so that no tokens are minted if the recipient is unregistered:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );

    // Guard BEFORE minting — no tokens are created if recipient is unregistered.
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

Alternatively, `require!` that the recipient is registered and let the whole call panic, which is consistent with the safe-deposit contract of "revert on failure."

### Proof of Concept

1. User generates a deposit address using a `DepositMsg` whose `recipient_id` is a NEAR account that has **never** called `storage_deposit` on the nbtc contract.
2. User sends BTC to that address.
3. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
4. Bridge verifies the proof and calls `safe_mint(recipient_id, amount, Some(msg))` on the nbtc contract.
5. `safe_mint` executes `internal_deposit(&self.bridge_id, amount)` — nBTC is minted to the bridge's own account (line 112).
6. `safe_mint` finds `recipient_id` unregistered and returns `PromiseOrValue::Value(U128(0))` (line 115).
7. The nbtc state change is committed; the bridge's callback may panic, but the mint is irreversible.
8. Result: `amount` nBTC sits in the bridge's nbtc balance, the user holds 0 nBTC, and their BTC is locked in the bridge's UTXO pool. The bridge operator must manually burn the surplus tokens to restore the 1:1 backing invariant. [4](#0-3)
