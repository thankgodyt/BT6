Audit Report

## Title
Premature Token State Registration Before Deployer Callback Enables Permanent Transfer Finalization With No Token Minting — (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `deploy_token_internal`, all token registration state (`token_id_to_address`, `token_address_to_id`, `token_decimals`, `deployed_tokens`) is written and `DeployTokenEvent` is emitted before the external deployer cross-contract call completes. During the async window between state write and deployer callback, a relayer can submit `fin_transfer` for the newly-registered token. Because `is_refund_required` never checks the `mint` promise result for non-`ft_transfer_call` paths, the transfer is permanently finalized in `finalised_transfers` with no tokens ever minted, causing irrecoverable loss of bridged funds.

## Finding Description

**Root cause — premature state write in `deploy_token_internal` (lines 2413–2453):**

The execution order within a single receipt is:
1. `add_token` writes `token_id_to_address`, `token_address_to_id`, and `token_decimals` (line 2414).
2. `deployed_tokens.insert` marks the token as deployed (line 2422).
3. `deployed_tokens_v2.insert` is written (line 2425).
4. `DeployTokenEvent` is emitted via `env::log_str` (line 2437).
5. Only then is `ext_deployer::ext(deployer).deploy_token(...)` dispatched (line 2446), with `deploy_token_by_deployer_callback` as the continuation.

Because NEAR processes cross-contract calls in separate receipts, there is a multi-block async window between step 4 (state written, event emitted) and the deployer receipt completing. During this window the token is fully registered in bridge storage but the token contract account does not yet exist on NEAR.

**Exploit path through `fin_transfer_callback` (lines 700–746):**

A relayer observing the `DeployTokenEvent` submits `fin_transfer` for a pending cross-chain transfer of the newly-registered token. Inside `fin_transfer_callback`:

- Line 715–718: `token_decimals.get(&init_transfer.token)` succeeds — the token is already registered.
- Line 1875: `add_fin_transfer` **permanently** inserts the transfer ID into `finalised_transfers` before any token operation.
- Lines 1957–1977: `send_tokens` is called, which at lines 2082–2101 detects `is_deployed_token = true` and dispatches `ext_token::ext(token).mint(recipient, amount, ...)` on the non-existent token account.
- The `mint` call fails (account does not exist).
- `fin_transfer_send_tokens_callback` is invoked (NEAR always calls callbacks regardless of promise outcome).

**Why `is_refund_required` fails to catch the mint failure (lines 1783–1803):**

`is_ft_transfer_call` is set to `!msg.is_empty()` at line 1973. For a plain transfer (empty `msg`), `is_ft_transfer_call = false`, and `is_refund_required(false)` unconditionally returns `false` (lines 1800–1803) without ever inspecting the `mint` promise result. Even for non-empty `msg` (`is_ft_transfer_call = true`), when `mint` fails, `env::promise_result_checked` returns `Err(_)`, which also maps to `false` (line 1798 — "Unexpected case: don't refund").

**Result:** The `else` branch at line 1719 executes unconditionally: `FinTransferEvent` is emitted (line 1745), the transfer ID remains permanently in `finalised_transfers`, and zero tokens are minted.

**Why the cleanup in `deploy_token_by_deployer_callback` does not help (lines 1189–1196):**

The cleanup only runs if the deployer call itself fails. It removes token registration maps but does **not** remove the `finalised_transfers` entry. If the deployer call eventually succeeds (the common case), no cleanup runs at all. Either way, the consumed transfer ID is never recoverable.

## Impact Explanation

This is a **Critical** impact matching "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows." The user's tokens are locked or burned on the source chain (EVM, Solana, etc.), the corresponding `fin_transfer` proof is consumed, the transfer ID is permanently recorded in `finalised_transfers` preventing any retry, and no tokens are ever minted on NEAR. The loss is irrecoverable.

## Likelihood Explanation

The `DeployTokenEvent` is emitted in the same receipt as the state writes, before the deployer receipt executes. Any relayer monitoring NEAR logs will observe this event and may immediately submit `fin_transfer` for a pending transfer of the newly-registered token. This is a realistic scenario during first-time bridging of a new token, where `deploy_token` and `fin_transfer` are expected to be submitted in close succession. No special privileges are required — any unprivileged relayer can trigger this through the public `fin_transfer` call.

## Recommendation

Move all token state writes (`add_token`, `deployed_tokens.insert`, `deployed_tokens_v2.insert`) and the `DeployTokenEvent` emission into `deploy_token_by_deployer_callback`, executing them only on the success branch (when `env::promise_result_checked(0, usize::MAX).is_ok()`). The `deploy_token_internal` function should only dispatch the deployer cross-contract call and pass the necessary metadata as callback arguments, writing no state until the deployer confirms success. This ensures the token is never visible to `fin_transfer_callback` until the token contract actually exists on NEAR.

## Proof of Concept

**Private-testnet transaction sequence:**

1. Deploy the omni-bridge contract and configure a deployer account and a prover.
2. Call `deploy_token` for a new EVM token. Observe that `DeployTokenEvent` is emitted in the same transaction receipt, and `token_decimals` / `deployed_tokens` are already populated, while the deployer callback receipt has not yet executed.
3. Before the deployer callback receipt executes (i.e., in the next block), submit `fin_transfer` with a valid prover proof for an `InitTransfer` of the same token to a NEAR recipient with an empty `msg`.
4. Observe that `fin_transfer_callback` succeeds (token decimals found), `add_fin_transfer` inserts the transfer ID into `finalised_transfers`, and `send_tokens` dispatches `mint` to the non-existent token account.
5. Observe that `fin_transfer_send_tokens_callback` executes the success branch (because `is_refund_required(false) == false`), emitting `FinTransferEvent`.
6. Verify: `finalised_transfers` contains the transfer ID (preventing retry), the recipient's token balance is zero, and the source-chain funds are permanently locked/burned.
