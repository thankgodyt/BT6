### Title
Unguarded `request_refund` Allows Any Caller to Register an Attacker-Controlled BTC Refund Address for Any Deposit UTXO — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is publicly callable with no caller-identity validation. When `deposit_msg.refund_address` is `None` (the common case), any NEAR account can submit a refund request for any unfinalized deposit UTXO and supply an arbitrary attacker-controlled BTC address as `refund_address`. Because only one request can exist per UTXO, the first caller wins. If the DAO/Operator fails to reject the malicious request within the 14-day `unsafe_refund_timelock_sec`, the depositor's BTC is permanently redirected to the attacker.

---

### Finding Description

`request_refund` carries only a `#[pause]` guard — no `#[access_control_any]`, no `#[trusted_relayer]` on the function itself, and no check that `env::predecessor_account_id()` is the legitimate depositor. [1](#0-0) 

The sole `refund_address` validation inside `internal_request_refund` is: [2](#0-1) 

This check is **entirely skipped** when `deposit_msg.refund_address` is `None`. There is no fallback that ties the supplied `refund_address` to the caller's identity.

The callback then verifies only that the deposit output's `script_pubkey` matches the address derived from `deposit_msg` — a check that passes for any caller who supplies the correct (publicly observable) `deposit_msg`: [3](#0-2)

### Impact Explanation

If the DAO/Operator does not reject the malicious request within 14 days, `execute_refund` sends the depositor's BTC permanently to the attacker's address. This is a direct, irreversible loss of user funds — matching the **Critical** impact class of "Significant loss, theft, destruction, or permanent locking of user or protocol funds." The 14-day `unsafe_refund_timelock_sec` is the only mitigation and relies entirely on DAO vigilance. [7](#0-6) 

---

### Likelihood Explanation

- All required inputs (`deposit_msg`, `tx_bytes`, `proof`) are publicly observable on the Bitcoin blockchain.
- The attack applies to every deposit where `deposit_msg.refund_address` is `None`, which is the default for standard deposits.
- The attacker's only cost is the non-refundable storage deposit for `request_refund`.
- Success requires DAO inaction for 14 days — plausible during high-volume periods, operational gaps, or if the DAO is not actively monitoring the `refund_requests` map.

Likelihood: **Medium** (significant mitigation exists, but the window is long and the attack is low-cost).

---

### Recommendation

1. **Add caller validation**: In `request_refund`, require that `env::predecessor_account_id()` matches the depositor's NEAR account (e.g., `deposit_msg.receiver_id` if that field exists), or restrict the function to trusted relayers/DAO when `deposit_msg.refund_address` is `None`.
2. **Require pre-authorized refund address**: Enforce that `deposit_msg.refund_address` is always `Some(...)` so the BTC destination is committed at deposit time and cannot be overridden by a third party.
3. **Automated monitoring**: Emit an alert event for every new refund request and implement off-chain monitoring to flag requests where the caller is not the depositor.

---

### Proof of Concept

1. Alice deposits BTC to the bridge with `deposit_msg = { receiver_id: "alice.near", refund_address: None, … }`. The deposit is never finalized via `verify_deposit`.
2. Eve observes Alice's deposit on Bitcoin and reconstructs `deposit_msg`, `tx_bytes`, and `proof` from public chain data.
3. Eve calls:
   ```
   request_refund(
     deposit_msg = alice_deposit_msg,   // public
     refund_address = "eve_btc_addr",   // attacker-controlled
     tx_bytes = alice_tx_bytes,         // public
     vout = 0,
     proof = alice_proof,               // public
     gas_fee = None
   )
   ```
   with sufficient attached NEAR for storage. The Light Client verifies the proof; `request_refund_callback` stores the request with `refund_address = "eve_btc_addr"`.
4. Alice subsequently calls `request_refund` with her own BTC address — it panics: `"Refund request already exists for this UTXO"`.
5. After 14 days (if DAO does not call `reject_refund`), Eve (or anyone) calls `execute_refund("alice_txid@0", None)`. The bridge builds a PSBT paying Alice's BTC to `"eve_btc_addr"`, signs it via MPC, and broadcasts it. Alice's BTC is permanently lost. [8](#0-7)

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
