### Title
Malicious or ETH-Rejecting Recipient Permanently Freezes Bridged Native ETH in `finTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.finTransfer()` delivers native ETH to `payload.recipient` via a raw `.call{value:}`. If the recipient is a contract that reverts on ETH receipt, the finalization always fails. Because the source-chain lock/burn is already irreversible and no refund path exists, the bridged ETH is permanently frozen.

---

### Finding Description

In `finTransfer()`, when `payload.tokenAddress == address(0)` (native ETH bridge), the contract executes:

```solidity
// OmniBridge.sol lines 317-322
if (payload.tokenAddress == address(0)) {
    // slither-disable-next-line arbitrary-send-eth
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
``` [1](#0-0) 

`payload.recipient` is a user-supplied EVM address embedded in the NEAR-signed `TransferMessagePayload`:

```solidity
struct TransferMessagePayload {
    ...
    address recipient;   // fully user-controlled
    ...
}
``` [2](#0-1) 

If `recipient` is a contract without a `receive()` function, or one that explicitly reverts on ETH receipt, every call to `finTransfer` for that transfer will revert with `FailedToSendEther()`. The destination nonce is marked completed at line 287 before the transfer attempt, but because the whole transaction reverts, the nonce is also rolled back — meaning the transfer is permanently unfinalizeable, not just temporarily blocked. [3](#0-2) 

There is no fallback delivery path, no WETH wrapping, and no refund mechanism back to the source chain.

---

### Impact Explanation

**Permanent freezing of bridged ETH funds.** The user's ETH is burned/locked on the source chain during `init_transfer` — an irreversible on-chain action. If `finTransfer` can never succeed (because the recipient always reverts), the ETH is lost with no recovery path. This satisfies the critical impact criterion: *permanent freezing of bridged funds*.

---

### Likelihood Explanation

Realistic. Common triggering scenarios:

1. **Accidental:** User specifies a multisig, DAO treasury, or smart-contract wallet that lacks a `receive()` function. This is a common mistake when bridging to contract addresses.
2. **Intentional self-grief:** User specifies a contract they control that is later upgraded to reject ETH, after the source-chain lock is confirmed.
3. **Third-party grief:** If a protocol or relayer is the one constructing the recipient field (e.g., in automated bridge flows), a malicious actor who can influence that field can freeze funds.

No admin compromise or privileged access is required — the recipient field is set by the unprivileged user who calls `init_transfer` on the source chain.

---

### Recommendation

Wrap the ETH as WETH before delivery, analogous to the fix in the referenced report. If the raw ETH transfer fails, fall back to depositing WETH to the recipient:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) {
        IWETH(WETH).deposit{value: payload.amount}();
        IERC20(WETH).safeTransfer(payload.recipient, payload.amount);
    }
}
```

This ensures delivery always succeeds regardless of the recipient's ETH-acceptance behavior, eliminating the permanent-freeze vector.

---

### Proof of Concept

1. User calls `init_transfer` on NEAR specifying `amount = 1 ETH` and `recipient = address(MaliciousContract)` where `MaliciousContract` has:
   ```solidity
   receive() external payable { revert("no ETH"); }
   ```
2. Source-chain ETH is locked/burned — irreversible.
3. Relayer constructs `TransferMessagePayload` with `tokenAddress = address(0)`, `amount = 1e18`, `recipient = address(MaliciousContract)`.
4. Relayer calls `finTransfer(signatureData, payload)` with `msg.value = 1e18`.
5. Execution reaches line 319: `payload.recipient.call{value: 1e18}("")` → recipient reverts → `FailedToSendEther()` is thrown → entire transaction reverts.
6. Relayer retries — same result every time.
7. The 1 ETH is permanently frozen: burned on source chain, undeliverable on destination chain, no refund mechanism exists. [4](#0-3)
