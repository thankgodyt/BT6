### Title
`validatePerasCert` Stub Unconditionally Returns `Right`, Bypassing Peras Certificate Validation and Enabling Adversarial Chain-Selection Manipulation - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance's `validatePerasCert` function is a stub that unconditionally returns `Right` (success) for every inbound certificate, regardless of content. This is the direct analog of the external report's "silently handled error" pattern: the validation infrastructure in `processCerts` is structurally correct and would reject invalid certificates if `validatePerasCert` ever returned `Left`, but because it never does, the rejection branch is permanently dead code. When Peras is enabled, any unprivileged peer can inject arbitrary certificates via the ObjectDiffusion mini-protocol, causing the node to boost attacker-chosen blocks in chain selection and potentially switch to a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

In the universal `BlockSupportsPeras` instance, `validatePerasCert` is implemented as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

It never inspects the certificate's cryptographic proof, round number plausibility, boosted-block validity, or any other field. It always wraps the raw, unvalidated `cert` in `ValidatedPerasCert` and returns `Right`.

**How the error path is silenced in `processCerts`:**

`processCerts` (the production inbound-certificate handler) is structurally sound: it calls `validateCert` on every new certificate and, if any returns `Left`, throws `PerasCertInboundException` to disconnect the peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validateCert` is `validatePerasCert mkPerasParams` and that function always returns `Right`, `partitionEithers` always produces `([], validatedCerts)`. The `(errs, _)` branch is permanently unreachable. Every certificate from every peer passes "validation."

**Production entry path:**

`makePerasCertPoolWriterFromChainDB` is the production writer used by the ObjectDiffusion mini-protocol. It wires `validatePerasCert mkPerasParams` directly into `processCerts`:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [3](#0-2) 

After passing the stub validator, each certificate is forwarded to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message: [4](#0-3) 

The background chain-selection thread then processes the certificate: it stores it in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block: [5](#0-4) 

**How injected certificates distort chain selection:**

`preferAnchoredCandidate` uses the `PerasWeightSnapshot` to compare candidate fragments. When Peras is enabled (`isEmptyPerasWeightSnapshot weights` is false), it computes `wsvTotalWeight = blockNo + weightBoost` for each fragment and prefers the heavier one: [6](#0-5) 

Each accepted certificate contributes `perasWeight params` (default: 15) to the boosted block's weight. An attacker who injects a certificate boosting a block on a shorter fork adds 15 weight units to that fork, potentially making it outweigh the honest canonical chain.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` naming any block as the boosted target. The certificate bypasses all validation, is stored in `PerasCertDB`, and triggers chain selection. The boosted block's fragment gains `perasWeight` (15) additional weight units. If the attacker's target block is on a fork that is within 15 weight units of the canonical chain, the node will switch to the non-canonical fork — a chain-selection safety failure caused entirely by a peer-supplied, cryptographically unverified certificate.

---

### Likelihood Explanation

Peras is not enabled by default (the CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference"). However, the vulnerability is present in production code paths — not test stubs — and will be fully exploitable the moment Peras is activated on any network. The attack requires only a single connected peer and a single malformed certificate message; no stake, keys, or prior knowledge of the chain is needed.

---

### Recommendation

1. **Do not ship `validatePerasCert` as a stub into any Peras-enabled deployment.** The function must verify the certificate's BLS/cryptographic proof, round number bounds, and boosted-block eligibility before returning `Right`.
2. Until real validation is implemented, add a runtime guard (e.g., `error` or a feature-flag check) inside `validatePerasCert` that prevents the stub from being called when Peras is enabled, so the gap is visible rather than silently permissive.
3. Track the open issue referenced in the TODO: `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

1. Enable Peras on a private testnet (set `eraPerasRoundLength` to a non-zero value in era params).
2. Connect an adversarial peer to an honest node via the ObjectDiffusion mini-protocol.
3. The adversary sends a `PerasCert` with `pcCertRound = R` (any round not yet in the DB) and `pcCertBoostedBlock = <point on a shorter fork>`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. `partitionEithers` yields `([], [validatedCert])` → `addCert` is called.
6. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`; the background thread stores the cert and calls `chainSelectionForBlock` for the boosted block.
7. `preferAnchoredCandidate` now computes `wsvTotalWeight` for the fork containing the boosted block as `blockNo + 15`, potentially exceeding the canonical chain's weight.
8. The honest node switches to the adversary's preferred fork.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
