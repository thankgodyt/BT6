### Title
Premature `internal_deposit` in `safe_mint` Permanently Locks nBTC When Recipient Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `nbtc::Contract::safe_mint`, the contract unconditionally mints nBTC into the bridge's own account **before** checking whether the intended recipient has a registered storage account. When the recipient is unregistered, the function silently returns `U128(0)` and exits, leaving the freshly minted tokens permanently stranded in the bridge account with no on-chain recovery path.

---

### Finding Description

`safe_mint` is the entry point used by the bridge for the "safe deposit" flow (triggered when a `DepositMsg` carries a `safe_deposit` field). Its body is:

```rust
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← (A) mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {          // ← (B) checks registration
        return PromiseOrValue::Value(U128(0));                    // ← (C) silent exit, tokens stuck
    }
    // transfer to account_id only reached when already registered
    ...
}
```

Step **(A)** increases `bridge_id`'s token balance by `amount`. Step **(B)** then discovers the recipient has no storage account. Step **(C)** returns zero without transferring anything. The `amount` tokens now reside in `bridge_id` with no corresponding credit to the depositor and no built-in mechanism in the nbtc contract to redirect or refund them.

Contrast this with `mint_inner`, which correctly guards registration before depositing:

```rust
// contracts/nbtc/src/lib.rs  lines 341-345
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);   // register first
    }
    self.token.internal_deposit(account_id, amount.into()); // then deposit
    ...
}
```

`safe_mint` inverts this order, creating the stuck-funds condition.

---

### Impact Explanation

When a user submits a BTC deposit using the safe-deposit path without having previously called `storage_deposit` on the nbtc contract:

1. Their BTC is locked on the Bitcoin network.
2. The bridge calls `safe_mint`; nBTC equal to the deposit amount is minted into `bridge_id`.
3. `safe_mint` returns `0` — the user receives nothing.
4. The minted nBTC sits in `bridge_id` indefinitely; the nbtc contract has no `lost_found` recovery function, and the bridge's `lost_found` map is a separate accounting layer that does not automatically reclaim tokens already credited to `bridge_id`.

This constitutes **permanent locking of user funds**: BTC is irreversibly locked on-chain, and the corresponding nBTC is inaccessible to the depositor.

---

### Likelihood Explanation

The safe-deposit flow is a documented, user-facing feature (the `safe_deposit` field in `DepositMsg`). Any user who:
- generates a deposit address with `safe_deposit` set, **and**
- has not called `storage_deposit` on the nbtc contract beforehand

will trigger this path. New users unfamiliar with the NEP-141 storage-registration requirement are the natural victims. No privileged access or special conditions are required beyond submitting a normal BTC deposit.

---

### Recommendation

Move the registration check **before** the `internal_deposit` call, mirroring the pattern used in `mint_inner`:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check first — do not mint if recipient is unregistered
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer logic
}
```

This ensures no tokens are minted when the recipient cannot receive them.

---

### Proof of Concept

1. Alice generates a deposit address with `safe_deposit: Some(SafeDepositMsg { msg: "".into() })` but does **not** call `storage_deposit` on the nbtc contract.
2. Alice sends 0.005 BTC to the derived address.
3. A relayer calls `verify_deposit_v2` with a valid Merkle proof.
4. The bridge calls `nbtc::safe_mint(alice, 500_000, None)`.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 500_000)` executes — bridge balance increases by 500 000 sat-units.
6. `self.token.accounts.get(&alice)` returns `None` → function returns `U128(0)`.
7. Alice's nbtc balance: **0**. Bridge nbtc balance: **+500 000** (unrecoverable via any nbtc-contract method). Alice's BTC: **locked**. [1](#0-0) [2](#0-1)
