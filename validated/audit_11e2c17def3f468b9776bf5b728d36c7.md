### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance provides a `validatePerasCert` implementation that unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic validation. This stub is wired directly into the live certificate ingest path (`processCerts`). Any unprivileged peer can therefore inject a crafted `PerasCert` naming an arbitrary block and round, have it accepted as valid, and cause the receiving node to re-run chain selection with an artificial Peras weight boost on that block — potentially switching the node to a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must be passed before a certificate influences chain state. The sole production instance (the "degenerate instance for all blks to get things to compile", tracked as issue #73) implements this gate as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is not isolated to tests. It is the function called by `processCerts` in both the `PerasCertDB`-backed and `ChainDB`-backed pool writers:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` is the inbound handler for certificates received over the network from untrusted peers. It filters out already-known round numbers, then calls `validateCert` on every new certificate. Because `validatePerasCert` always succeeds, every structurally well-formed `PerasCert` — regardless of whether it was produced by a legitimate quorum — is timestamped and forwarded to `addCert`: [4](#0-3) 

Once stored, the certificate is processed by `chainSelSync` in `ChainSel.hs`. The handler reads the boosted block from the VolatileDB and calls `chainSelectionForBlock` for it, giving it the full Peras weight boost (`vpcCertBoost = perasWeight params`): [5](#0-4) 

The `PerasCert` data type in the degenerate instance contains only a round number and a block point — no aggregate BLS signature, no voter set, no VRF outputs. There is nothing for a real validator to check even if one were present: [6](#0-5) 

The analog to the external report is direct: just as removing `ERC20VotesUpgradeable` eliminated the historical-snapshot guard that prevented double-counting of voting power, the removal of real certificate validation here eliminates the cryptographic guard that should prevent unauthorized Peras weight from being injected into chain selection.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A peer that can reach the object-diffusion certificate endpoint can:

1. Craft a `PerasCert` naming any block in the node's VolatileDB as `pcCertBoostedBlock` and any round number as `pcCertRound`.
2. The certificate passes `validatePerasCert` unconditionally and is stored in `PerasCertDB`.
3. `chainSelSync` re-runs chain selection for the boosted block, applying `perasWeight params` to it.
4. If the boosted block is on a competing fork, the node may switch to that fork, diverging from the canonical chain.

The `PerasWeightSnapshot` derived from the `PerasCertDB` is also used by the GSM's `getCandidateOverSelection` to compare candidate chains against the current selection, meaning the injected weight persists and affects all subsequent chain comparisons until the certificate is garbage-collected. [7](#0-6) 

---

### Likelihood Explanation

**High.** The vulnerable code is the only production instance of `BlockSupportsPeras`. It is unconditionally selected for all block types (`instance StandardHash blk => BlockSupportsPeras blk`). The object-diffusion certificate mini-protocol is reachable by any peer that can establish a node-to-node connection. No key material, stake, or privileged access is required — only the ability to send a well-formed CBOR-encoded `PerasCert` message. [8](#0-7) 

---

### Recommendation

1. **Do not use the degenerate `BlockSupportsPeras` instance in any network-connected code path.** Gate `processCerts` and `makePerasCertPoolWriterFromChainDB` behind a feature flag that is disabled until a real `validatePerasCert` implementation is in place.
2. Implement `validatePerasCert` to verify: (a) the aggregate BLS signature over the claimed voter set, (b) that the voter set constitutes a valid quorum under the epoch's stake distribution, and (c) VRF eligibility proofs for non-persistent voters — mirroring the full validation already specified in `implVerifyCert` for the `WFALS` committee scheme.
3. Until (2) is complete, reject all inbound certificates at the network boundary rather than accepting them unconditionally. [9](#0-8)

### Proof of Concept

**Private-testnet sequence (no stake, no keys required):**

1. Start a node with Peras enabled. The node uses the degenerate `BlockSupportsPeras` instance.
2. Connect a malicious peer via the node-to-node object-diffusion protocol.
3. The peer observes the node's VolatileDB (via ChainSync) to learn the hash and slot of a block `B` on a competing fork `F`.
4. The peer constructs:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <point of B> }
   ```
   encoded as valid CBOR.
5. The peer sends this certificate via the Peras certificate object-diffusion sub-protocol.
6. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
7. The certificate is stored; `chainSelSync` calls `chainSelectionForBlock` for `B` with the full Peras weight boost.
8. If `weight(F) + perasWeight > weight(current chain)`, the node switches to fork `F`.

The attacker needs only a valid TCP connection to the node's peer port and knowledge of a block hash in the node's VolatileDB — both trivially obtainable from the ChainSync protocol. [10](#0-9)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
