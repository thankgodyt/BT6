### Title
Peras Quorum Check Compares Unnormalized Absolute Vote Stake Against Relative Threshold, Enabling Unauthorized Certificate Forging — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras vote-quorum validation pipeline assigns raw ledger stake values to `ValidatedPerasVote.vpvVoteStake` without normalizing them, then compares the accumulated total against a relative quorum threshold. Because the two quantities are in incompatible units, a single vote from any registered stake pool whose absolute stake value exceeds the relative threshold (a condition that holds for virtually every pool when absolute lovelace values are used) is sufficient to trigger false quorum and forge an unauthorized Peras certificate.

---

### Finding Description

**Step 1 — `validatePerasVote` assigns raw stake without normalization.**

The default `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasVote` as:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

`lookupPerasVoteStake` performs a plain `Map.lookup` on `PerasVoteStakeDistr`, returning whatever `PerasVoteStake` (a raw `Rational`) is stored there. No normalization relative to the total stake distribution is performed. [1](#0-0) 

**Step 2 — The code itself documents the unit mismatch.**

The `stakeAboveThreshold` function carries an explicit TODO warning:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type comment reinforces this:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [3](#0-2) 

**Step 3 — `votesReachQuorum` sums raw stakes and calls `stakeAboveThreshold`.**

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
```

If `vpvVoteStake` values are absolute lovelace (e.g., `1_000_000_000`), their sum is compared against a relative threshold such as `0.75`. The comparison `1_000_000_000 >= 0.75` is always `True`, so quorum is declared after a single vote. [4](#0-3) 

**Step 4 — The same flaw propagates through `updateCandidateVoteState` and `updateLoserVoteState`.**

Both functions call `votesReachQuorum` / `stakeAboveThreshold` on the accumulated `ptvtTotalStake` without any normalization step. [5](#0-4) [6](#0-5) 

**Step 5 — The production inbound-vote path calls `validatePerasVote` with no normalization.**

`processVotes` (the function that handles votes arriving from peers) calls:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

`sd` is the raw `PerasVoteStakeDistr` from the ledger; no normalization is applied before or after. [7](#0-6) [8](#0-7) 

---

### Impact Explanation

When the `PerasVoteStakeDistr` is populated with absolute ledger stake values (the current state, per the documented TODO), any single vote from a registered stake pool whose absolute stake value exceeds the relative quorum threshold (e.g., `0.75`) causes `stakeAboveThreshold` to return `True`. This triggers `updateCandidateVoteState` to call `forgePerasCert`, producing a `ValidatedPerasCert` for the adversary's chosen block. That certificate is then stored in the `PerasVoteDB` and propagated to the `ChainDB`, where it applies a `PerasWeight` boost to the adversary's block. Chain selection then prefers the boosted block over the honest chain, constituting an unauthorized certificate acceptance and a chain-selection manipulation.

This matches the **Critical** allowed impact: "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance," and **High**: "Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."

---

### Likelihood Explanation

The entry path is a standard peer-to-peer vote message processed by `processVotes`. No special privileges are required beyond being a registered stake pool (i.e., having a `PerasVoterId` present in the stake distribution). Because the mismatch is structural — absolute values on one side, a relative threshold on the other — the condition is satisfied by essentially every registered pool, making exploitation trivially reproducible on any private testnet or node running the current code.

---

### Recommendation

Normalize `PerasVoteStake` to a relative value (fraction of total committee stake) before storing it in `ValidatedPerasVote.vpvVoteStake`. Concretely:

1. Pass the total stake of the voting committee into `validatePerasVote` (or compute it from `PerasVoteStakeDistr`).
2. Divide the voter's absolute stake by the total to obtain a normalized `PerasVoteStake` in `[0, 1]`.
3. Remove the TODO from `stakeAboveThreshold` once the invariant is enforced at the validation boundary.

Alternatively, change `stakeAboveThreshold` to accept the full `PerasVoteStakeDistr` and perform normalization internally, mirroring the fix pattern described in the existing TODO comment.

---

### Proof of Concept

On a private testnet with two nodes A (honest) and B (adversary, a registered stake pool):

1. Node B constructs a `PerasVote` for its preferred block at round `r`, signing it with its valid pool key.
2. Node B sends the vote to node A via the Peras vote mini-protocol.
3. Node A's `processVotes` calls `validatePerasVote mkPerasParams sd voteB`. Because `sd` maps B's `PerasVoterId` to its absolute lovelace stake (e.g., `500_000_000_000`), `vpvVoteStake = 500_000_000_000`.
4. `updateCandidateVoteState` calls `votesReachQuorum`, which computes `totalVoteStake = 500_000_000_000` and evaluates `stakeAboveThreshold`: `500_000_000_000 >= 0.75 + safetyMargin` → `True`.
5. `forgePerasCert` is called; a certificate boosting B's block is stored in node A's `PerasVoteDB`.
6. Node A's chain selection applies the `PerasWeight` boost to B's block and switches to B's chain, despite B holding far less than quorum stake. [9](#0-8) [10](#0-9) [11](#0-10)
