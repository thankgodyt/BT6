### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate, Enabling Unauthorized Chain-Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` for every certificate it receives, bypassing all cryptographic and structural checks. Because `processCerts` in the Peras certificate object-pool feeds directly into the `PerasCertDB`, and the `PerasCertDB` drives the weight boost applied during chain selection, an unprivileged peer can inject an arbitrary certificate that causes an honest node to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` as the gate that must be passed before a certificate is stored and its weight boost is applied. The only instance in the codebase is the catch-all:

```haskell
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub skips every check that the Peras security argument depends on:

| Check | Status |
|---|---|
| BLS aggregate-signature verification | **absent** |
| Quorum-threshold (total stake ≥ threshold) | **absent** |
| Round-number validity | **absent** |
| Boosted-block existence / era validity | **absent** |

The inbound processing pipeline in `processCerts` calls the supplied `validateCert` callback on every certificate received from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is never taken; every certificate is unconditionally forwarded to `addCert` and stored in the `PerasCertDB`.

Chain selection in `ChainSel.hs` imports `PerasCertDB.API` and uses a `PerasWeightSnapshot` to apply the stored weight boosts when comparing candidate fragments: [3](#0-2) [4](#0-3) 

A certificate that boosts block `B` causes `preferAnchoredCandidate` to rank any candidate whose suffix contains `B` higher than it would otherwise be ranked, potentially above the honest canonical chain.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that names any block as the boosted target and any round number, then send it over the Peras certificate diffusion mini-protocol. The stub accepts it without any cryptographic check. Once stored, the boost is applied unconditionally during every subsequent chain-selection comparison. If the attacker targets a block on a minority or adversarial fork, the honest node will rank that fork above the canonical chain and switch to it — a direct chain-selection safety failure.

This matches the allowed impact scope: **"Critical. Bypass of PBFT/Praos/TPraos/Peras voting or certificate checks that enables unauthorized certificate acceptance"** and **"High. Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions."**

---

### Likelihood Explanation

The Peras certificate diffusion infrastructure (`processCerts`, `processVotes`, `PerasCertDB`, `PerasVoteDB`) is fully implemented in production source files and wired into `ChainSel`. The stub is the only `validatePerasCert` implementation in the repository — there is no era-specific override for `CardanoBlock`. Any peer that can reach the Peras object-diffusion endpoint can exploit this without any key material, stake, or operator access. The only mitigating factor is that Peras is not yet activated on mainnet; however, the code is present and the diffusion layer is live in the codebase.

---

### Recommendation

1. **Reject all certificates by default** until a real implementation is ready: change the stub to `Left PerasValidationErr` so that no certificate can enter the `PerasCertDB` through the unvalidated path.
2. **Implement full validation** per the Peras specification: verify the BLS aggregate signature over `(roundNo, boostedBlock)`, check that the aggregate key was derived from a quorum of eligible committee members, and verify that the boosted block exists and is within the valid round window.
3. **Gate the diffusion endpoint** behind a feature flag that is disabled until validation is complete, consistent with how other in-development protocol extensions are handled.

---

### Proof of Concept

```
1. Establish a Peras certificate diffusion connection to a target node.

2. Construct a PerasCert:
     pcCertRound        = <any round number>
     pcCertBoostedBlock = <point of a block on an adversarial fork>

3. Send the certificate batch to the node via the object-diffusion protocol.

4. processCerts calls validatePerasCert, which returns
       Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })
   for the crafted certificate — no signature or quorum check is performed.

5. The certificate is stored in PerasCertDB.

6. On the next chain-selection run, preferAnchoredCandidate applies the weight
   boost to any candidate fragment containing the boosted block, causing the
   node to rank the adversarial fork above the canonical chain and switch to it.
```

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
