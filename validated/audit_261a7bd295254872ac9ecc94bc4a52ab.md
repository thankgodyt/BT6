### Title
`validatePerasCert` Always Returns `Right` (Constant Success), Bypassing Peras Certificate Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` always returns `Right` (unconditional success) without performing any actual cryptographic or protocol validation. This is directly analogous to the Derby `AaveProvider.exchangeRate` always returning the constant `1`: a function that should compute a meaningful result always returns a fixed constant, causing all downstream security checks to be silently bypassed. Any unprivileged peer can inject a crafted `PerasCert` boosting an arbitrary block, which is accepted unconditionally and used to manipulate Peras-weighted chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must verify a received Peras certificate before it is stored and used to boost a block's chain-selection weight. The universal instance (applied to all block types) implements this as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (the comment at line 318 explicitly marks it as the degenerate instance "for all blks to get things to compile"). It performs zero checks: no quorum verification, no committee membership check, no signature verification, no round/slot validity check. It always returns `Right`.

The inbound certificate processing path in the object diffusion layer calls this function directly on every certificate received from a peer:

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` partitions the results of `validateCert` into errors and successes. Because `validatePerasCert` always returns `Right`, the error partition is always empty and every certificate is unconditionally forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

Once added to the `PerasCertDB`, the certificate's boosted block is extracted and used to build the `PerasWeightSnapshot`, which directly feeds into `weightedSelectView` and `preferAnchoredCandidate` for chain selection: [4](#0-3) [5](#0-4) 

Chain selection then triggers for the boosted block: [6](#0-5)

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a crafted `PerasCert` naming any block as the boosted block for any round. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its `vpcCertBoost = perasWeight params` weight is added to the targeted block's chain-selection weight. This allows the attacker to:

1. **Artificially inflate the weight of a non-canonical fork**, causing an honest node to prefer it over the canonical chain — a chain-selection safety failure.
2. **Trigger spurious chain-selection re-evaluations** for attacker-chosen blocks, potentially causing the node to switch to a weaker or adversarial chain.
3. **Bypass the Peras quorum requirement entirely**: the entire purpose of certificate validation is to ensure that a certificate represents genuine quorum agreement among committee members. With validation always returning success, this invariant is destroyed.

This matches the **Critical** impact class: bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

- The Peras object diffusion mini-protocol is a **public, unauthenticated network endpoint** — any peer that connects can send `PerasCert` objects.
- The attacker needs only to construct a `PerasCert` with a chosen `pcCertRound` and `pcCertBoostedBlock` — no keys, no stake, no cryptographic material required.
- The only guard is the `Set.member roundNo (pcdsCertIds pcds)` deduplication check (one cert per round), which limits the attacker to one forged cert per round number, but Peras rounds are plentiful.
- Peras is currently disabled by default per the CHANGELOG, but the code path is fully wired and the vulnerability is latent, activating the moment Peras is enabled in any deployment or testnet. [7](#0-6) 

---

### Recommendation

Implement actual certificate validation in `validatePerasCert`. At minimum, the implementation must verify:

1. **Quorum**: the certificate must be backed by a sufficient number of valid votes from eligible committee members, with total stake exceeding the `perasQuorumStakeThreshold`.
2. **Committee membership**: each voter must be a member of the correct Peras voting committee for the given round, verified against the stake distribution snapshot.
3. **Cryptographic signatures**: each vote must carry a valid VRF/KES or BLS signature from the claimed voter.
4. **Round/slot validity**: the boosted block must be a valid target for the claimed round (within the correct slot range).

Until this is implemented, the `processCerts` inbound path should reject all externally received certificates when Peras is enabled, or Peras must not be enabled in any environment where untrusted peers can connect.

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to a target node as an unprivileged peer via the object diffusion mini-protocol.
2. Construct a `PerasCert` with:
   - `pcCertRound = <any round not yet in the DB>`
   - `pcCertBoostedBlock = <point of a block on a minority/adversarial fork>`
3. Send the certificate via the `PerasCert` object diffusion channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
5. The certificate is stored in `PerasCertDB`; `implGetWeightSnapshot` now returns a snapshot with the adversarial block boosted by `perasWeight params`.
6. `chainSelSync` triggers chain selection for the boosted block; `preferAnchoredCandidate` now computes a higher `wsvTotalWeight` for the adversarial fork.
7. The node switches to the adversarial chain. [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

              Nothing -> Just cert
              Just prev

          WithFingerprint
            PerasCertDbState
