### Title
Attacker Can Front-Run `execute_refund` to Permanently Hijack Victim's Refund Pending State - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`execute_refund` is a permissionless function callable by any NEAR account after the refund timelock expires. The caller's account ID is embedded in the resulting `BTCPendingInfo`. Because the `btc_pending_id` is derived deterministically from the PSBT content (independent of the caller), a second call for the same UTXO always fails with `"pending info already exist"`. An attacker who front-runs the victim's `execute_refund` call permanently blocks the victim from re-executing their refund, locking the victim's BTC indefinitely and requiring privileged operator intervention to resolve — at which point the only available resolution permanently destroys the victim's refund path.

---

### Finding Description

**Step 1 — Permissionless `execute_refund`**

`execute_refund` carries only `#[payable]` and `#[pause(except(roles(Role::DAO)))]` attributes. There is no `#[access_control_any]` or `#[trusted_relayer]` guard. Any NEAR account can call it for any pending refund request once the timelock has elapsed. [1](#0-0) 

**Step 2 — Caller's account ID is embedded in `BTCPendingInfo`**

Inside `finalize_refund_with_psbt`, the `BTCPendingInfo` is created with `account_id: caller.clone()`, where `caller = env::predecessor_account_id()`. The attacker's account ID becomes the owner of the pending signing slot. [2](#0-1) 

**Step 3 — `btc_pending_id` is deterministic and caller-independent**

The `btc_pending_id` is derived from `psbt.get_pending_id()`, which is a hash of the PSBT bytes. The PSBT is built entirely from the `RefundRequest` fields (deposit UTXO, refund address, refund amount, gas fee) — none of which depend on the caller. Two calls to `execute_refund` for the same UTXO always produce the same `btc_pending_id`. [3](#0-2) 

**Step 4 — Second call always fails**

The insert into `btc_pending_infos` is guarded by a uniqueness check. Because the attacker's call already inserted the entry under the same `btc_pending_id`, the victim's subsequent call panics with `"pending info already exist"`. [4](#0-3) 

**Step 5 — UTXO is marked verified, blocking all future paths**

`finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo`. This blocks both `verify_deposit` and any new `request_refund` for the same UTXO. [5](#0-4) 

**Step 6 — No automatic resolution path exists**

`internal_remove_refund_pending_tx_id` — the only function that can remove a stale refund pending info — requires the refund request to already be absent. But the refund request is kept alive (with `executed = true`) until `verify_refund_finalize_callback` succeeds, which requires the attacker to sign and broadcast the transaction. The attacker has no incentive to do so.
