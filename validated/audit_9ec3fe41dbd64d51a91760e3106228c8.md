### Title
Unauthenticated `request_refund` with Globally-Indexed UTXO State Allows Any Attacker to Preempt User's Refund and Redirect BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary

`request_refund` is callable by any NEAR account with no caller authentication. Refund requests are stored in a global map keyed by `utxo_storage_key` = `{tx_id}@{vout}`, not by caller. When a user's `deposit_msg.refund_address` is `None`, any caller may supply an arbitrary `refund_address`. An attacker who observes the user's deposit (via the publicly emitted `LogDepositAddress` event) can preempt the user's `request_refund` call by submitting the same `deposit_msg` with an attacker-controlled BTC address. This blocks the user's refund (DoS) and, if the DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`, allows the attacker to redirect the user's BTC to their own address.

### Finding Description

`request_refund` has no caller authentication: [1](#0-0) 

The function is explicitly documented as callable by anyone: [2](#0-1) 

Refund requests are stored in a global map keyed only by `utxo_storage_key` (`{tx_id}@{vout}`), with no caller component in the key: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, the caller-supplied `refund_address` is accepted without restriction: [4](#0-3) 

The duplicate check in the callback blocks any second submission for the same UTXO: [5](#0-4) 

The full `deposit_msg` (including `recipient_id` and `refund_address: None`) is publicly emitted in the `LogDepositAddress` event when the user calls `get_user_deposit_address`: [6](#0-5) 

**Attack path:**

1. User calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, ... })` — the full `deposit_msg` is emitted in the `LogDepositAddress` event.
2. User sends BTC to the deposit address; the Bitcoin transaction is public.
3. Attacker reconstructs the exact `deposit_msg` from the event and the Bitcoin transaction.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof)` before the user.
5. The `request_refund_callback` verifies the script_pubkey against the deposit address derived from `deposit_msg` — this passes because the attacker uses the identical `deposit_msg`. The attacker's `refund_address` is stored.
6. User's `request_refund` fails: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` — the user's BTC is sent to the attacker's address.

The `unsafe_refund_timelock_sec` is a partial mitigation: it gives DAO/Operator time to reject the malicious request. However, after each rejection the attacker can immediately re-submit, creating a persistent DoS. The user cannot reclaim their BTC through the refund path as long as the attacker keeps re-occupying the `utxo_storage_key`.

### Impact Explanation

**Minimum (DoS):** The attacker permanently blocks the user's refund by repeatedly preempting the `utxo_storage_key`. Every time DAO rejects the attacker's request, the attacker re-submits. The user's BTC is stuck in the bridge deposit address with no refund path available. This matches: *Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention.*

**Maximum (theft):** If DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the user's BTC is sent to the attacker's address. This matches: *Critical — significant loss or theft of user funds.*

### Likelihood Explanation

The attack requires:
- Observing the `LogDepositAddress` event (trivially public on NEAR).
- Observing the Bitcoin deposit transaction (trivially public on Bitcoin).
- Submitting a `request_refund` before the user, paying the NEAR storage deposit (a small, fixed cost).

The DoS variant (persistent re-submission after each DAO rejection) requires only repeated small NEAR payments. The theft variant requires DAO inaction for the duration of `unsafe_refund_timelock_sec`. The attack is realistic for any user who deposits BTC without a pre-authorized `refund_address` in their `deposit_msg`.

### Recommendation

Index refund requests by a composite key that includes the caller's NEAR account ID, analogous to the fix in the referenced report (`keccak256(batchMerkleRoot, msg.sender)`). For example, use `{tx_id}@{vout}@{predecessor_account_id}` as the storage key. This ensures that a frontrunner's request occupies a different key and does not block the legitimate user's submission. Alternatively, require that `deposit_msg.refund_address` is always pre-set (non-`None`) so that the `refund_address` is cryptographically bound to the deposit address derivation path and cannot be freely chosen by an attacker.

4. Alice calls request_refund(...) → PANIC: "Refund request already exists for this UTXO"

5. After unsafe_refund_timelock_sec, attacker calls execute_refund("abc123@0")
   → Alice's 1 BTC is sent to attacker_btc_address

    pub fn request_refund(

        refund_address: String,

        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
