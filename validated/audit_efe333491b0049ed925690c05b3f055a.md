### Title
Attached NEAR Deposit Silently Absorbed on Early Return in `sign_btc_transaction` — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary
`sign_btc_transaction` is marked `#[payable]` and is designed to forward `env::attached_deposit()` to the MPC chain-signatures contract for signing fees. However, an early-return path exists that cleans up a stale RBF pending transaction and returns `true` without forwarding or refunding the attached NEAR deposit. NEAR SDK does not automatically refund attached deposits on early returns, so the deposit is permanently absorbed by the bridge contract.

---

### Finding Description

In `api/chain_signatures.rs`, `sign_btc_transaction` is `#[payable]`: [1](#0-0) 

The normal execution path calls `internal_sign_btc_transaction`, which calls `sign_promise`: [2](#0-1) 

`sign_promise` forwards `env::attached_deposit()` verbatim to the MPC contract. This is the intended use of the attached NEAR.

However, before reaching `internal_sign_btc_transaction`, there is an early-return guard: [3](#0-2) 

When `get_original_tx_id()` returns `Some(original_tx_id)` and `check_btc_pending_info_exists(original_tx_id)` returns `false` (the original transaction was already verified and removed), the function cleans up the stale RBF pending info and returns `PromiseOrValue::Value(true)` — **without calling `sign_promise` and without refunding `env::attached_deposit()`**. The NEAR SDK does not automatically refund attached deposits; the deposit is permanently retained by the contract.

---

### Impact Explanation

Any user who calls `sign_btc_transaction` on an RBF pending transaction whose original transaction has already been finalized loses their entire attached NEAR deposit permanently. The contract silently absorbs it with no recourse for the user. This constitutes a direct, permanent loss of user funds (NEAR tokens) triggered by a publicly reachable code path.

---

### Likelihood Explanation

The scenario is a realistic race condition in normal bridge operation:

1. A user initiates a withdrawal → original `BTCPendingInfo` is created.
2. The user or operator calls `withdraw_rbf` → an RBF `BTCPendingInfo` is created with `original_tx_id` pointing to the original.
3. A relayer calls `verify_withdraw_v2` → the original `BTCPendingInfo` is removed after on-chain confirmation.
4. The user (or a relayer acting on behalf of the user) calls `sign_btc_transaction` on the RBF pending ID with NEAR attached for MPC fees.
5. The early-return path fires, the RBF pending info is cleaned up, and the attached NEAR is lost.

This is reachable by any unprivileged user who has an in-flight RBF withdrawal.

---

### Recommendation

Explicitly refund `env::attached_deposit()` to `env::predecessor_account_id()` before taking the early return:

```rust
if !self.check_btc_pending_info_exists(original_tx_id) {
    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
        .btc_pending_sign_ids
        .remove(&btc_pending_sign_id);
    self.internal_remove_btc_pending_info(&btc_pending_sign_id);
    // Refund any attached deposit that was not forwarded to MPC
    let deposit = env::attached_deposit();
    if deposit.as_yoctonear() > 0 {
        return Promise::new(env::predecessor_account_id())
            .transfer(deposit)
            .into();
    }
    return PromiseOrValue::Value(true);
}
```

---

### Proof of Concept

1. User calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message → `BTCPendingInfo` (`original_id`) is created with `PendingInfoState::WithdrawOriginal`.
2. User calls `withdraw_rbf(original_id, ...)` → RBF `BTCPendingInfo` (`rbf_id`) is created; its state encodes `original_tx_id = original_id`.
3. Relayer calls `verify_withdraw_v2(original_id, proof)` → after successful verification, `internal_remove_btc_pending_info(original_id)` is called; `original_id` no longer exists in `btc_pending_infos`.
4. User calls `sign_btc_transaction(rbf_id, 0, 0)` with 1 NEAR attached (standard MPC signing fee).
5. Inside `sign_btc_transaction`: `btc_pending_info.get_original_tx_id()` returns `Some(original_id)`; `check_btc_pending_info_exists(original_id)` returns `false`.
6. Early-return branch executes: `rbf_id` is removed from `btc_pending_sign_ids` and `btc_pending_infos`; function returns `PromiseOrValue::Value(true)`.
7. The 1 NEAR attached deposit is never forwarded to MPC and never refunded — it is permanently held by the bridge contract. [3](#0-2) [2](#0-1)
