### Title
Incomplete Peras Vote and Certificate Validation Skips Signature and Eligibility Proof Checks - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` unconditionally accepts every certificate (`Right` always), and `validatePerasVote` only checks stake presence while ignoring the BLS vote signature and VRF eligibility proof. An unprivileged peer can send crafted votes or certificates that bypass all cryptographic authorization, accumulate fake quorum, and trigger unauthorized chain-weight boosts that corrupt chain selection.

---

### Finding Description

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` is the only instance in the codebase and therefore applies to all block types including `CardanoBlock`. It contains three stub implementations, each explicitly marked with a TODO:

**`validatePerasCert` — always returns `Right`:**

```haskell

    Right
      ValidatedPerasCert
        { vpcCert = cert
```

Any `PerasCert` value, regardless of its content or cryptographic validity, is accepted and assigned a full chain-weight boost of `perasWeight params`. [1](#0-0)

### Impact Explanation

**`validatePerasCert` (Critical — Bypass of Peras certificate validation):**  
Any peer can craft a `PerasCert` pointing to an arbitrary block at an arbitrary round and have it accepted unconditionally. The accepted certificate carries `vpcCertBoost = perasWeight params`, which is fed directly into `preferAnchoredCandidate` / `compareChainDiffs` during chain selection. A peer can therefore make an honest node assign a large weight boost to a non-canonical chain, causing it to be preferred over the honest chain. [7](#0-6) 

**`validatePerasVote` (Critical — Bypass of Peras vote signature/eligibility verification):**  
Any peer whose `PerasVoterId` appears in the stake distribution (a public, on-chain value) can send votes with a forged BLS signature or a fabricated VRF eligibility proof. Because neither is checked, the vote is accepted as `ValidatedPerasVote` and its stake weight is counted toward quorum. An attacker who controls multiple voter IDs (or who simply replays known voter IDs with fake signatures) can manufacture a quorum, trigger `forgePerasCert`, and inject a certificate for an arbitrary block.

---

### Likelihood Explanation

The entry path is fully reachable by any unprivileged network peer: Peras votes and certificates are diffused over the node-to-node mini-protocol. No key material, operator access, or stake majority is required. The only prerequisite is knowing a `PerasVoterId` that appears in the current stake distribution, which is public on-chain data. The `validatePerasCert` path requires even less: zero knowledge of any valid voter identity.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate verification. At minimum, verify the aggregate BLS signature over the certificate's `(roundNo, boostedBlock)` payload against the public keys of the claimed voters, and verify that the claimed voters collectively hold sufficient stake.

2. **`validatePerasVote`**: After the existing stake-presence check, call `verifyVoteSignature` from `CryptoSupportsVoteSigning` to verify `pvSignature` against the voter's public key and the `(pvRoundNo, pvBoostedBlock)` payload. For non-persistent voters, additionally verify `pvEligibilityProof` via `evalVRF` in `VRFVerifyContext`.

3. **`implAddVote`**: Remove the TODO and enforce that only cryptographically validated votes enter the DB.

---

### Proof of Concept

1. Observe that `validatePerasCert` always returns `Right` regardless of input: [8](#0-7) 

2. Construct a `PerasCert` with `pcCertBoostedBlock` pointing to an adversarial block and `pcCertRound` set to the current round.

3. Submit it via the Peras certificate diffusion path. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.

4. The certificate is stored and its boost is applied in `preferAnchoredCandidate`, causing the node to prefer the adversarial chain over the honest chain.

5. For the vote path: construct a `PerasVote` with a known `pvVoteVoterId` (any voter in the stake distribution), set `pvVoteBlock` to the adversarial block, and supply an arbitrary (invalid) `pvSignature`. `validatePerasVote` checks only `lookupPerasVoteStake` and returns `Right`. Repeat with enough voter IDs to exceed the quorum threshold; `forgePerasCert` is triggered automatically by `updatePerasRoundVoteStates`. [9](#0-8)
