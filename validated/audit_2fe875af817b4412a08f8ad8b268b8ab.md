Audit Report

## Title
`fin_transfer_send_tokens_callback` Ignores `ft_transfer`/`mint` Failure, Permanently Freezing Inbound Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When an inbound transfer is finalized via `fin_transfer`, the transfer ID is committed to `finalised_transfers` via `add_fin_transfer` before token delivery executes. The callback `fin_transfer_send_tokens_callback` delegates failure detection to `is_refund_required`, which only inspects the promise result when `is_ft_transfer_call = true`. For all plain token delivery paths (`ft_transfer`, `mint`, wNEAR unwrap), `is_ft_transfer_call` is `false` and `is_refund_required` unconditionally returns `false` — meaning a failed delivery is silently treated as success, the transfer ID is never removed from `finalised_transfers`, and the user's funds are permanently frozen with no retry path.

## Finding Description

**Root cause — `is_refund_required` does not inspect the promise result for non-`ft_transfer_call` paths.**

`is_refund_required` at lines 1784–1804 only calls `env::promise_result_checked` when `is_ft_transfer_call = true`. For the `else` branch it returns `false` unconditionally:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

**State commitment before delivery.**

`process_fin_transfer_to_near` (line 1875) calls `add_fin_transfer` first, irrevocably writing the transfer ID to `finalised_transfers` in the same receipt as `fin_transfer_callback`. The token delivery (`send_tokens`) is a subsequent cross-contract call. NEAR's receipt model guarantees `add_fin_transfer`'s state change is committed before `send_tokens` executes.

**Token delivery paths that set `is_ft_transfer_call = false`.**

`send_tokens` (lines 2056–2117) dispatches:
- `ft_transfer` (lines 2102–2106) for non-deployed tokens with empty `msg`
- `mint` (lines 2094–2101) for deployed tokens with empty `msg`
- `near_withdraw` → `near_withdraw_callback` (lines 2071–2081) for wNEAR

All three paths correspond to `msg.is_empty() = true`, so `!msg.is_empty()` passed as `is_ft_transfer_call` at line 1973 is `false`.

**Callback takes the success path on failure.**

In `fin_transfer_send_tokens_callback` (lines 1700–1746), when `is_refund_required` returns `false`, the else-branch executes: fee is minted/transferred to the relayer and `FinTransferEvent` is emitted — regardless of whether `ft_transfer`/`mint` actually succeeded. `remove_fin_transfer` is never called.

**wNEAR sub-path.** If `near_withdraw` fails, `near_withdraw_callback` panics (line 1050), making the promise result seen by `fin_transfer_send_tokens_callback` a failure. But since `is_ft_transfer_call = false`, `is_refund_required` still returns `false` and the success path is taken.

**Retry is impossible.** Any subsequent call to `fin_transfer` with the same proof panics with `TransferAlreadyFinalised` because the transfer ID remains in `finalised_transfers`.

## Impact Explanation

This is a **Critical** impact matching "permanent freezing of bridged funds":

- **Native NEAR tokens (locked on outbound):** `unlock_tokens_if_needed` decreases `locked_tokens` accounting, but `ft_transfer` failed so the tokens remain in the bridge contract. The transfer is stuck in `finalised_transfers`. Tokens are permanently frozen with no recovery path.
- **Deployed/bridged tokens:** `mint` fails, no tokens are created for the user, yet the transfer is marked finalized. The user's cross-chain value is destroyed with no recourse.

## Likelihood Explanation

Any inbound transfer to a NEAR recipient is affected. No special privilege is required. Realistic failure triggers include:

1. **Token contract paused** — many NEP-141 tokens implement a pause mechanism. If paused between the storage-check receipt and the `ft_transfer` receipt, delivery fails silently.
2. **Recipient unregisters storage** — `storage_balance_of` and `ft_transfer` execute in separate receipts. A recipient (or griefing third party controlling the recipient account) can call `storage_unregister` in the window between the two receipts, causing `ft_transfer` to panic.
3. **Token contract bug or upgrade** — any panic in the token contract during `ft_transfer` or `mint` triggers the same silent-success path.

## Recommendation

1. In `is_refund_required`, add a check for the promise result when `is_ft_transfer_call = false`: call `env::promise_result_checked(0, …)` and return `true` on `Err(_)` to trigger the refund/revert path.
2. Alternatively, move `add_fin_transfer` into `fin_transfer_send_tokens_callback` so it is only committed after confirmed delivery.
3. For the wNEAR path, instead of panicking in `near_withdraw_callback`, return a result that `fin_transfer_send_tokens_callback` can inspect.

## Proof of Concept

1. A user bridges a native NEAR token from Ethereum back to NEAR (inbound transfer).
2. The token contract owner pauses the token contract (or the recipient calls `storage_unregister` after the storage check).
3. A relayer calls `fin_transfer` with a valid proof.
4. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` (line 1875) commits the transfer ID to `finalised_transfers`.
   - `unlock_tokens_if_needed` decreases `locked_tokens` accounting.
   - `send_tokens` dispatches `ft_transfer` on the paused token contract.
5. `ft_transfer` panics. The promise result is `Failed`.
6. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` (line 1800–1802) without inspecting the promise result.
8. The else-branch executes (lines 1719–1746): fee is sent to the relayer, `FinTransferEvent` is emitted.
9. The transfer ID is permanently in `finalised_transfers`. Any retry panics with `TransferAlreadyFinalised`.
10. The user's tokens are frozen in the bridge contract with no recovery mechanism.

**Minimal test plan:** Deploy a mock NEP-141 token with a `pause` flag that causes `ft_transfer` to panic when paused. Call `fin_transfer` with a valid proof, pause the token contract in the same block (or use a test harness to inject a failed promise result), then verify: (a) `finalised_transfers` contains the transfer ID, (b) the user received no tokens, (c) a second `fin_transfer` call with the same proof panics with `TransferAlreadyFinalised`.
