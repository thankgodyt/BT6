Audit Report

## Title
Missing Pre-Transfer Normalized-Amount Guard Causes Permanent Fund Freeze — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` / `init_transfer_internal` accepts and locks/burns user tokens without verifying that the post-fee amount, after decimal normalization to the destination chain, is greater than zero. `sign_transfer`, called later by a relayer, performs this check and panics with `InvalidAmountToTransfer` if the normalized amount is zero. Because no cancel or refund path exists for a stored pending transfer, any transfer whose normalized net amount rounds to zero results in permanently frozen funds.

## Finding Description

**Root cause — missing upstream guard:**

`init_transfer` (line 554) only checks `fee < amount`:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It never checks whether `normalize_amount(amount_without_fee(), decimals) > 0`. After passing this check, `init_transfer_internal` (line 1829) burns or locks the tokens and stores the `TransferMessage` in `pending_transfers`.

**Downstream rejection — `sign_transfer`:**

When a relayer later calls `sign_transfer` (line 447), it computes:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

If `normalize_amount` returns 0 (integer division truncation when the NEAR-side token has more decimals than the destination token), this `require!` panics and the call reverts. The stored `TransferMessage` is never removed and the locked/burned tokens are never recoverable.

**No recovery path:**

`sign_transfer_callback` only removes the transfer message on a successful MPC signature (line 656–657). There is no `cancel_transfer`, `refund_transfer`, or equivalent public function in the contract. The `update_fee` path (line 400) can only increase the fee, which makes `amount_without_fee` smaller — worsening the situation. The transfer is permanently stuck.

**Concrete trigger scenario:**

A NEAR-side token registered with 24 decimals bridging to an EVM chain where the token has 6 decimals uses a normalization divisor of 10^18. Any `amount_without_fee` value below 10^18 (i.e., less than 1 full token) normalizes to 0. A user bridging 999,999,999,999,999,999 units (just under 1 full token, fee = 0) passes the `fee < amount` check, has their tokens burned, and then every subsequent `sign_transfer` call reverts permanently.

## Impact Explanation

This is a **Critical** impact matching the allowed class: *permanent freezing of bridged funds*. User tokens are irreversibly burned or locked on NEAR with no mechanism to recover them. The bridge contract holds no residual liability — the tokens are gone from the user's perspective and cannot be finalized on the destination chain.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_transfer_call` with a small amount directed at a destination chain whose token has fewer decimals than the NEAR-side representation. No special role, leaked key, or colluding party is required. The condition is repeatable and deterministic: every `sign_transfer` attempt for the affected transfer ID will fail identically. Tokens with large decimal mismatches (e.g., 24 vs 6) have an 18-order-of-magnitude window where this applies.

## Recommendation

Add a normalized-amount check inside `init_transfer` (or at the entry of `init_transfer_internal`) before tokens are locked or burned:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
).near_expect(BridgeError::FailedToGetTokenAddress);

let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);

let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing guard in `sign_transfer` and ensures the transfer is rejected before any state mutation or token movement occurs.

## Proof of Concept

1. Register a NEAR-side token with 24 decimals mapped to an EVM token with 6 decimals (normalization divisor = 10^18).
2. Call `ft_transfer_call` with `amount = 1` and `fee = 0` targeting an EVM recipient. The `fee < amount` check passes; tokens are burned; `InitTransferEvent` is emitted.
3. Call `sign_transfer` with the resulting `transfer_id`. Observe panic: `InvalidAmountToTransfer`.
4. Repeat step 3 indefinitely — same result every time.
5. Confirm no public function exists to cancel or refund the transfer.
6. Confirm the token balance of the bridge contract (or the burn record) shows the tokens are gone.

A unit test in `near/omni-bridge/src/tests/lib_test.rs` can reproduce this by mocking `token_decimals` with a large decimal gap and asserting that `sign_transfer` panics while the transfer message remains in storage after the panic.
