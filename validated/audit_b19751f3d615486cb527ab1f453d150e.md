### Title
Off-by-one in `get_confirmations` tier-boundary comparison silently assigns wrong confirmation count to exact-boundary deposits - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
`Config::get_confirmations` uses a strict `>` comparison instead of `>=` when matching a deposit's satoshi amount against the sorted tier-boundary keys of `confirmations_strategy`. As a result, a deposit whose amount equals exactly one of the configured upper-limit keys is silently bumped into the next (higher) confirmation tier, requiring more confirmations than the operator intended for that amount.

### Finding Description
`get_confirmations` is the single function that translates a satoshi amount into the required Bitcoin confirmation count used by every deposit-verification and refund-verification call in the bridge. [1](#0-0) 

```rust
keys.sort_unstable();
for key in &keys {
    if *key > satoshi_amount {          // ← should be >=
        return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
    }
}
```

The field comment documents the intent: [2](#0-1) 

> `// Satoshi upper limit for amount checks -> confirmations`

Each key is the **inclusive upper limit** of a tier. With `>`, an amount that equals a key exactly fails the test (`key > amount` is `false`), falls through, and is matched by the next larger key — the next tier. With `>=` it would correctly stop at the intended tier.

Concrete example with two tiers `{"1000000": 3, "10000000": 6}`:

| Amount (sat) | `>` result | `>=` result |
|---|---|---|
| 999 999 | 3 ✓ | 3 ✓ |
| **1 000 000** | **6 ✗** | **3 ✓** |
| 1 000 001 | 6 ✓ | 6 ✓ |

`get_confirmations` is called in every deposit and refund verification path: [3](#0-2) [4](#0-3) 

The same `>` pattern also appears in both operator-cancel paths (`cancel_withdraw.rs` line 32–33 and `cancel_active_utxo_management.rs` line 31–32), where `elapsed > max_btc_tx_pending_sec` delays the cancellation window by one second relative to the configured limit, but the deposit-verification path is the highest-traffic and most user-visible instance. [5](#0-4) 

### Impact Explanation
Any deposit or refund whose satoshi amount lands exactly on a configured tier boundary is silently assigned the next tier's confirmation count. A relayer that computes the "correct" lower count and submits a proof will receive a rejection from the light-client verification call. The deposit is not permanently lost — the relayer can wait for the additional confirmations and resubmit — but the transaction fails on-chain, wastes gas, and violates the protocol's documented confirmation policy. If the boundary amount coincides with a common round value (e.g., 0.01 BTC = 1 000 000 sat), the failure is reproducible for every such deposit.

This maps to: **Low — publicly reachable invariant-violation in a production bridge path without direct theft.**

### Likelihood Explanation
The bug is always present and is triggered by any deposit or refund whose exact satoshi value equals a configured tier-boundary key. Operators commonly choose round satoshi values as tier boundaries, making accidental triggering plausible in normal operation. No special attacker capability is required; any ordinary bridge user whose deposit happens to land on the boundary will experience the failure.

### Recommendation
Replace the strict `>` with `>=` in `get_confirmations`:

```rust
// contracts/satoshi-bridge/src/config.rs
for key in &keys {
    if *key >= satoshi_amount {   // was: *key > satoshi_amount
        return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
    }
}
```

Apply the same correction to the `max_btc_tx_pending_sec` checks in `cancel_withdraw.rs` and `cancel_active_utxo_management.rs` (change `>` to `>=`) so the cancellation window opens exactly at the configured limit rather than one second after it.

### Proof of Concept
Given `confirmations_strategy = {"1000000": 3, "10000000": 6}`:

1. User deposits exactly 1 000 000 satoshi (0.01 BTC).
2. Bridge calls `get_confirmations(1_000_000)`.
3. Loop: `1_000_000 > 1_000_000` → `false`; falls through.
4. Next key: `10_000_000 > 1_000_000` → `true`; returns `6`.
5. Relayer waits for 3 confirmations (the intended tier) and calls `verify_deposit`.
6. Contract requires 6 confirmations; the proof is rejected.
7. Relayer must wait 3 more confirmations and resubmit, wasting gas and delaying the mint. [6](#0-5)

```rust
    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
```
