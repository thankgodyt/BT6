### Title
Unconditional `validatePerasCert` Acceptance Enables Unauthorized Peras Weight Boost and Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic validation. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` target; the certificate passes "validation", is stored in the database, and injects a `PerasWeight 15` boost into chain selection for the attacker-chosen block. This directly parallels the external report's pattern: data is encoded with specific parameters (round number, boosted block, quorum proof), but when that data is later "claimed" (processed by `processCerts`), no validation against those encoded parameters is enforced.

---

### Finding Description

**Root cause — `validatePerasCert` always succeeds:**

The universal instance for all `StandardHash blk` blocks is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No check is performed on:
- `pcCertRound` — whether the round number is within a valid range or corresponds to a real Peras round
- `pcCertBoostedBlock` — whether the boosted block actually exists on any known chain
- Quorum — whether the certificate was produced by a sufficient fraction of stake
- BLS aggregate signature — whether the cryptographic proof is valid

The concrete BLS certificate type in `Peras/Cert/V1.hs` carries a `pcSignature :: AggregateVoteSignature PerasBLSCrypto` and `pcVoters :: PerasCertVoters`, but the default instance's `PerasCert blk` type only stores `pcCertRound` and `pcCertBoostedBlock` — and even those are not checked. [2](#0-1) 

**Attacker-controlled entry path — `processCerts` in the production pool writer:**

The production path `makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [3](#0-2) 

`processCerts` applies `validateCert` to each inbound certificate and, if all pass, adds them to the ChainDB: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, every certificate from every peer passes this gate unconditionally.

**Chain selection impact — `PerasWeight 15` injected per fake certificate:**

`mkPerasParams` sets `perasWeight = PerasWeight 15`: [5](#0-4) 

Each accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params = PerasWeight 15`. This boost is recorded in the `PerasWeightSnapshot` and added to the total weight of any chain fragment containing the boosted block during chain selection. The Peras glossary confirms: a chain's *total weight* is its tip block number plus its weight boost, and this is what chain selection compares. [6](#0-5) 

---

### Impact Explanation

**High — Chain selection manipulation via unauthorized certificate acceptance.**

An unprivileged peer can send crafted `PerasCert` objects targeting any block point. Each accepted certificate injects `PerasWeight 15` into chain selection for the attacker-chosen block. By sending multiple certificates targeting the same block, the attacker can accumulate unbounded artificial weight on a non-canonical chain, causing an honest node to prefer it over the honest chain. This directly violates the Peras security assumption that only certificates backed by a quorum of honest stake can influence chain selection.

This matches the allowed impact scope: *"High. Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."* and *"Critical. Bypass of leader eligibility, VRF/KES/certificate/signature validation, PBFT/Praos/TPraos/Peras voting or certificate checks."*

---

### Likelihood Explanation

**High.** The entry point is the Peras certificate diffusion mini-protocol, reachable by any peer without credentials. The bypass requires only constructing a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` — no cryptographic material is needed. The `processCerts` deduplication only skips certificates whose `pcCertRound` is already in the database, so an attacker can inject one fake certificate per round number (of which there are unboundedly many). The TODO comment and linked issue confirm this is a known incomplete stub shipped in the production source tree.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a complete validation function that checks:
1. The certificate's round number is within the valid window relative to the current chain tip.
2. The `pcCertBoostedBlock` point exists on a known chain and satisfies the `perasBlockMinSlots` age requirement.
3. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` is cryptographically valid.
4. The voters represented in the certificate collectively hold stake above the quorum threshold (`perasQuorumStakeThreshold`).

Until this is implemented, the Peras certificate diffusion path should be disabled or gated behind a feature flag to prevent production nodes from accepting unauthenticated weight boosts.

---

### Proof of Concept

On a private testnet with Peras certificate diffusion enabled, a malicious peer constructs and sends:

```haskell
-- Craft a certificate boosting an arbitrary (possibly non-existent) block
let fakeCert = PerasCert
      { pcCertRound      = PerasRoundNo 9999
      , pcCertBoostedBlock = BlockPoint (SlotNo 1) someAdversarialHash
      }

-- Send via the Peras cert diffusion mini-protocol to the target node.
-- processCerts calls (validatePerasCert mkPerasParams fakeCert)
-- which returns Right unconditionally.
-- The cert is stored and vpcCertBoost = PerasWeight 15 is applied
-- to someAdversarialHash in chain selection.
```

Repeating with distinct `pcCertRound` values accumulates unbounded weight on the adversarial block, causing the honest node's chain selection to prefer the adversarial chain over the canonical one. [1](#0-0) [7](#0-6) [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
