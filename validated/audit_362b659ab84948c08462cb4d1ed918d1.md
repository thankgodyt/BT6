### Title
ChainSync Client Uses Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs`, Causing Incorrect Peer Disconnection Under Peras - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. When Peras is active and certificates have boosted blocks on a candidate chain, this function uses block-count-only comparison instead of total Peras weight. This creates a systematic mismatch between the disconnect decision and the actual chain selection decision in ChainDB, causing the node to incorrectly disconnect from peers offering a heavier (Peras-boosted) chain that is shorter by block count — preventing adoption of the canonical chain.

---

### Finding Description

**Root cause — `checkPreferTheirsOverOurs` ignores the live Peras weight snapshot:**

`checkPreferTheirsOverOurs` is called when a peer's header is beyond the forecast horizon. Its purpose is to disconnect from peers whose candidate chain is not preferred over the current selection (to avoid tracking peers the node will never switch to). It calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` falls into the `isEmptyPerasWeightSnapshot weights` branch and compares chains purely by block count (longest-chain rule):

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- ... pure block-count comparison via selectView ...
  | otherwise =
      -- ... full Peras-weighted comparison via weightedSelectView ...
``` [2](#0-1) 

**Contrast with ChainDB chain selection, which uses the real snapshot:**

The actual chain selection in `ChainDB` reads the live `PerasWeightSnapshot` from `cdbPerasCertDB` and passes it to `preferAnchoredCandidate` and `compareAnchoredFragments`:

```haskell
constructPreferableCandidates CDB{..} weights curChain ...
  ...
  ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [3](#0-2) 

The ChainDB API exposes `getPerasWeightSnapshot` for exactly this purpose:

```haskell
, getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
-- ^ Get the 'PerasWeightSnapshot', representing the Peras weight boosts for
-- all blocks newer than the current immutable tip.
``` [4](#0-3) 

**The mismatch:**

The `ChainDbView` record used by the ChainSync client does not expose `getPerasWeightSnapshot`, so `checkPreferTheirsOverOurs` cannot access the live weights. The disconnect decision and the actual chain selection decision therefore use different criteria — exactly the "configurable parameter changed but not enforced everywhere" pattern from the external report.

The `PerasWeightSnapshot` is the dynamic parameter that changes as certificates arrive (via `addPerasCertAsync` → `chainSelSync` → `PerasCertDB.addCert`), but `checkPreferTheirsOverOurs` is never updated to reflect it. [5](#0-4) 

---

### Impact Explanation

When Peras is enabled and certificates exist that boost blocks on a candidate chain:

**Scenario (incorrect disconnection from the heavier chain):**
1. Our current chain C₀ has block count N+1 and total Peras weight W₀.
2. A peer serves chain C₁ with block count N but total Peras weight W₁ > W₀ (due to certificates boosting blocks on C₁).
3. C₁'s headers are beyond the forecast horizon, triggering `checkPreferTheirsOverOurs`.
4. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares by block count only: C₁ (N) < C₀ (N+1) → `ShouldNotSwitch`.
5. The node throws `CandidateTooSparse` and disconnects from the peer.
6. But the real ChainDB chain selection would prefer C₁ (W₁ > W₀) and switch to it.

The node incorrectly disconnects from peers offering the canonical (heavier) chain and remains on the lighter chain. This is a chain selection error: the node prefers a less-secure chain beyond the intended Peras security assumptions.

**Scenario (false continuation — less severe):**
Conversely, if the candidate is longer by block count but lighter by Peras weight, `checkPreferTheirsOverOurs` does not disconnect (it sees the candidate as preferred), but ChainDB will not switch. The node wastes resources tracking a peer whose chain will never be selected.

---

### Likelihood Explanation

- Requires Peras to be enabled (the feature is implemented in production code and is being deployed).
- Requires at least one Peras certificate to have been received that boosts a block on a candidate chain shorter by block count than the current selection.
- The `checkPreferTheirsOverOurs` path is triggered during normal syncing whenever a peer's headers are beyond the forecast horizon — a routine condition during initial sync or after network partitions.
- The TODO comment and linked issue (`https://github.com/tweag/cardano-peras/issues/64`) confirm the developers are aware this is unresolved.
- No special privileges, keys, or stake are required; any peer serving a heavier-but-shorter chain triggers the bug.

---

### Recommendation

1. Add `getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))` to the `ChainDbView` record in `Client.hs`.
2. In `checkPreferTheirsOverOurs`, read the live snapshot via `getPerasWeightSnapshot` (stripping the fingerprint) and pass it to `preferAnchoredCandidate` instead of `emptyPerasWeightSnapshot`.
3. Ensure the `defaultChainDbView` wires this field from `ChainDB.getPerasWeightSnapshot`.

This mirrors how `readChainComparison` in `BlockFetch/ClientInterface.hs` already correctly reads the live snapshot:

```haskell
readChainComparison :: STM m (WithFingerprint (ChainComparison (HeaderWithTime blk)))
readChainComparison =
  fmap mkChainComparison <$> getPerasWeightSnapshot chainDB
``` [6](#0-5)

### Proof of Concept

**Setup:** Private testnet with Peras enabled. Two chains C₀ and C₁ fork at block B_fork.

1. C₀: B_fork → B1 → B2 → B3 (3 blocks after fork, no Peras boosts, total weight = 3).
2. C₁: B_fork → B1' → B2' (2 blocks after fork, B1' and B2' each boosted by a Peras certificate with `perasWeight = 15`, total weight = 2 + 30 = 32).
3. Node is on C₀. A peer serves C₁ headers. C₁'s tip is beyond the forecast horizon.
4. `checkPreferTheirsOverOurs` is called. With `emptyPerasWeightSnapshot`, it compares block counts: C₁ (2) < C₀ (3) → `ShouldNotSwitch` → throws `CandidateTooSparse` → disconnects.
5. ChainDB, if it had received C₁'s blocks, would compute: C₁ total weight 32 > C₀ total weight 3 → `ShouldSwitch` → would adopt C₁.
6. The node is permanently stuck on C₀ (the lighter, non-canonical chain) as long as all peers serving C₁ are disconnected via this path. [7](#0-6) [8](#0-7) [9](#0-8)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes

  -- Deliver promise indicating that we processed the cert.
  lift $ atomically $ putTMVar varProcessed certResult
```
