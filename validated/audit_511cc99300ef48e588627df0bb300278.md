### Title
Unguarded `new()` Initializer Grants Full DAO/Super-Admin to Any Front-Running Caller — (File: `contracts/satoshi-bridge/src/lib.rs`)

### Summary
The `satoshi-bridge` contract's `new()` initializer unconditionally grants super-admin, `DAO`, `PauseManager`, and `UnpauseManager` roles to `env::predecessor_account_id()` with no validation that the caller is the intended deployer. If contract deployment and initialization are not performed atomically in a single batch transaction, any NEAR account can call `new()` first and seize full administrative control of the bridge.

### Finding Description
In `contracts/satoshi-bridge/src/lib.rs`, the `#[init]` function `new()` performs the following role assignments unconditionally:

```rust
contract.acl_init_super_admin(env::predecessor_account_id());
contract.acl_grant_role(Role::DAO.into(), env::predecessor_account_id());
contract.acl_grant_role(Role::PauseManager.into(), env::predecessor_account_id());
contract.acl_grant_role(Role::UnpauseManager.into(), env::predecessor_account_id());
``` [1](#0-0) 

There is no check that `env::predecessor_account_id()` equals the intended owner or deployer account. The `#[init]` attribute only prevents the function from being called a second time after state is written — it does not restrict *who* may call it first.

In NEAR Protocol, contract deployment (`DeployContract` action) and initialization (`FunctionCall` to `new`) are separate actions. If they are submitted in separate transactions rather than as a single atomic batch, a window exists between deployment and initialization. An attacker monitoring the network can submit a `FunctionCall` to `new()` before the legitimate deployer does, passing any valid `Config` struct.

The `Config` struct is accepted as a caller-supplied parameter with no deployer-identity binding:

```rust
#[init]
pub fn new(config: Config) -> Self {
    config.assert_valid();
    ...
``` [2](#0-1) 

Once the attacker's call lands first, `acl_init_super_admin` sets the attacker as super-admin. All subsequent role-management functions — including `add_super_admin`, `extend_operators`, `extend_relayer_white_list`, and `update_config` — are gated on `Role::DAO`:

```rust
#[access_control_any(roles(Role::DAO))]
pub fn add_super_admin(&mut self, account_id: AccountId) {
``` [3](#0-2) 

The legitimate deployer, holding no role, cannot call any of these functions. The bridge is permanently under attacker control with no recovery path in the contract code itself.

The analog to the external report's "line #50" is `management.rs` line 50:

```rust
require!(is_success, "acl_grant_role UnpauseManager failed");
``` [4](#0-3) 

This line (and the entire `add_super_admin` function) becomes permanently unreachable for the legitimate deployer because they hold no `DAO` role after the front-run.

### Impact Explanation
An attacker who successfully front-runs `new()` gains:
- Full `DAO` role: can call `update_config` to redirect the `nbtc_contract_id` or `chain_signatures_contract_id` to attacker-controlled contracts, enabling unauthorized minting or redirection of bridge-controlled funds.
- `extend_operators` / `extend_relayer_white_list`: can whitelist attacker-controlled relayers to submit fraudulent deposit proofs.
- `PauseManager` / `UnpauseManager`: can freeze or unfreeze the bridge at will.
- `withdraw_protocol_fee`: can drain accumulated protocol fees.

This constitutes a complete bypass of bridge authorization controls and enables unauthorized minting/unlocking of nBTC — **Critical** impact. [5](#0-4) 

### Likelihood Explanation
Likelihood is **Low**. NEAR Protocol supports atomic batch transactions that combine `DeployContract` and `FunctionCall` actions in a single receipt, eliminating the window entirely if used correctly. However, the contract code itself provides no enforcement of this requirement. A deployer who uses two separate transactions (e.g., via a script, CI pipeline, or manual CLI steps) is vulnerable. The attack requires only the ability to submit a NEAR transaction — no special privileges.

### Recommendation
Add an owner/deployer check inside `new()`, or accept an explicit `owner_id: AccountId` parameter and assert it equals `env::predecessor_account_id()`. Alternatively, enforce atomic deployment by documenting and tooling the requirement that deployment and initialization must be submitted as a single batch transaction. A minimal fix:

```rust
#[init]
pub fn new(config: Config, owner_id: AccountId) -> Self {
    require!(
        env::predecessor_account_id() == owner_id,
        "Caller must be the intended owner"
    );
    ...
}
``` [6](#0-5) 

### Proof of Concept
1. Legitimate deployer submits `DeployContract` action for `satoshi-bridge` in transaction T1.
2. Attacker observes T1 is included and the contract is deployed but `new()` has not yet been called.
3. Attacker submits a `FunctionCall` to `new(config)` with a valid `Config` and their own account as `predecessor_account_id`.
4. Attacker's transaction lands before the deployer's initialization transaction.
5. `acl_init_super_admin(attacker)` executes; attacker holds super-admin and `DAO`.
6. Deployer's `new()` call panics: `"Already initialized"` (state exists).
7. Attacker calls `update_config` to set `nbtc_contract_id` to an attacker-controlled token contract.
8. All subsequent bridge deposits mint tokens on the attacker's contract instead of the legitimate nBTC contract. [7](#0-6)
