### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Allows Arbitrary Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate as valid. An unprivileged peer can send a crafted certificate over the object-diffusion mini-protocol that boosts any block it chooses. Because chain selection adds the certificate's `PerasWeight` boost to the block-number comparison, the attacker can make an honest node prefer a non-canonical, adversary-controlled chain.

---

### Finding Description

`validatePerasCert` in the universal `instance StandardHash blk => BlockSupportsPeras blk` is a stub that performs **no cryptographic or structural validation whatsoever**. It unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This instance is the **only** `BlockSupportsPeras` instance in the codebase (the comment at line 318 explicitly calls it "degenerate instance for all blks to get things to compile"), meaning it covers every production block type. [2](#0-1) 

The production inbound-certificate path in `makePerasCertPoolWriterFromChainDB` passes this stub directly as the validation function:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then calls this function on every certificate received from a peer; if all pass (which they always do), each is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`addPerasCertAsync` enqueues the certificate for the background chain-selection thread: [5](#0-4) 

`chainSelSync` then stores the certificate in `PerasCertDB` and calls `chainSelectionForBlock` for the boosted block: [6](#0-5) 

Chain selection uses `WeightedSelectView`, which computes `wsvTotalWeight = blockNo + wsvWeightBoost`. The boost comes directly from the `PerasWeightSnapshot` built from accepted certificates: [7](#0-6) 

The weight snapshot is populated from every certificate stored in `PerasCertDB`, with no re-validation at that stage: [8](#0-7) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that names any block as the boosted block and any round number. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its `perasWeight` boost is added to the named block's chain-selection weight. If the attacker's chosen block is on a fork that is otherwise shorter than the honest chain, the artificial weight boost can flip the comparison in `preferCandidate`, causing the honest node to switch to the adversarial fork. This is a **chain-selection error** that lets an unprivileged peer make an honest node prefer a non-canonical chain, matching the **High** impact tier.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is wired into the production node. Any connected peer can send a `PerasCert` message. No stake, keys, or special privileges are required. The stub is the only validation gate between the network and chain selection, and it never rejects anything.

---

### Recommendation

1. Implement real cryptographic validation inside `validatePerasCert`: verify the aggregate BLS signature over `(roundNo, boostedBlock)`, check committee membership and eligibility proofs, and confirm the round number is within the acceptable window.
2. Until the real implementation is ready, gate the object-diffusion certificate writer behind a feature flag so that the stub path is never reachable on a production node.
3. Track the concrete implementation work in the referenced issue (`cardano-peras/issues/120`) and block any Peras-enabled mainnet deployment on its resolution.

---

### Proof of Concept

**Setup:** Two nodes, A (honest) and B (attacker). Node A's current chain has tip at block `H` (block number 100). The attacker controls a fork `F` whose tip is at block number 98 (shorter by 2).

**Steps:**

1. Attacker connects to node A via the object-diffusion mini-protocol.
2. Attacker sends a `PerasCert` message:
   - `pcCertRound = <any valid-looking round>`
   - `pcCertBoostedBlock = <point of fork tip F>`
   - No valid BLS signature or eligibility proof needed.
3. Node A calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }`. [4](#0-3) 
4. The certificate is stored; `PerasWeightSnapshot` now maps `F`'s point to `perasWeight` (e.g., `PerasWeight 3`).
5. `chainSelectionForBlock` is triggered for `F`. `WeightedSelectView` computes:
   - Honest chain: `wsvTotalWeight = 100 + 0 = 100`
   - Fork F: `wsvTotalWeight = 98 + 3 = 101`
6. `preferCandidate` returns `ShouldSwitch` for fork F; node A switches to the adversarial chain. [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
