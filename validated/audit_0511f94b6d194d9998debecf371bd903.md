Audit Report

## Title
Replay of `fin_transfer` Proof After Recipient-Rejection Refund Enables Double-Spend — (File: near/omni-bridge/src/lib.rs)

## Summary

When a `fin_transfer` to a NEAR recipient uses `ft_transfer_call` (non-empty `msg`) and the recipient contract rejects the tokens (its `ft_on_transfer` returns the full amount, leaving used-amount = 0), `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which deletes the `TransferId` from `finalised_transfers` — the sole replay-protection set for inbound proofs. The prover contracts do not track consumed proofs. The identical foreign-chain proof can therefore be re-submitted, causing a second mint or unlock for a single on-chain lock event.

## Finding Description

The inbound finalization flow for a NEAR-recipient transfer is:

1. `fin_transfer` → `verify_proof` (prover) → `fin_transfer_callback` → `process_fin_transfer_to_near`
2. `add_fin_transfer` inserts the `TransferId` into `finalised_transfers` (replay guard). [1](#0-0) 
3. `send_tokens` issues `ft_transfer_call` when `msg` is non-empty.
4. `fin_transfer_send_tokens_callback` is invoked as the callback.

Inside `fin_transfer_send_tokens_callback`, `is_refund_required` returns `true` when the promise result (the "used amount" returned by `ft_transfer_call`) is 0 — which happens when the recipient's `ft_on_transfer` returns the full amount (rejection). [2](#0-1) 

In that branch, `remove_fin_transfer` is called unconditionally: [3](#0-2) 

`remove_fin_transfer` deletes the entry from `finalised_transfers` and refunds storage: [4](#0-3) 

After deletion, `add_fin_transfer` will succeed again for the same `TransferId` because `LookupSet::insert` returns `true` only when the key is new — and the key is now absent. [5](#0-4) 

Neither the MPC prover nor the Wormhole prover proxy maintains any record of previously consumed proofs; they only verify cryptographic validity of the submitted proof. [6](#0-5) [7](#0-6) 

`finalised_transfers` is therefore the only replay barrier, and it is cleared on refund. [8](#0-7) 

## Impact Explanation

This is a **Critical** double-spend / unauthorized minting impact. An attacker receives two token deliveries for a single foreign-chain lock event. For deployed (bridged-minted) tokens this inflates supply without a corresponding lock; for native locked tokens this drains the bridge escrow. Both outcomes directly match the allowed impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds"* and *"Cross-chain replay … enabling invalid finalization or double-spending."*

## Likelihood Explanation

- The attacker controls both the recipient address and the `msg` field when initiating the transfer on the EVM side — both are ordinary user-supplied inputs requiring no privilege.
- The `FailedFinTransferEvent` emitted at line 1716 is the natural signal for relayers to retry, making the second submission automatic without any social engineering.
- No admin compromise, key leak, MPC collusion, or NEAR validator reorg is required.
- The attack is repeatable: the attacker can cycle the malicious contract's accept/reject state to drain the escrow iteratively.

## Recommendation

Do **not** remove the `finalised_transfers` entry on a failed token delivery. The entry records that the foreign-chain event was consumed; that fact is permanent regardless of what happens on the NEAR side.

- Keep the `finalised_transfers` entry intact on refund (remove the `self.remove_fin_transfer(...)` call from the `is_refund_required` branch).
- Refund storage cost through a separate accounting mechanism (e.g., charge storage to the protocol or to the relayer who submitted the transfer, not to the per-transfer entry).
- If a retry of the token delivery is needed (e.g., recipient was not registered), implement a separate, authenticated `retry_fin_transfer` path that checks `finalised_transfers` is already set and does **not** re-accept the original proof.

## Proof of Concept

**Setup:**
- Deploy malicious NEAR contract `evil.near` whose `ft_on_transfer` returns the full `amount` on the first call and `0` on the second call.
- Initiate a transfer on EVM: `recipient = "evil.near"`, `msg = "x"` (non-empty).

**Step 1 — First `fin_transfer`:**
```
relayer → fin_transfer(proof)
  → fin_transfer_callback
    → process_fin_transfer_to_near
      → add_fin_transfer(transfer_id)          // finalised_transfers: {transfer_id}
      → send_tokens(ft_transfer_call, evil.near)
        → evil.near::ft_on_transfer returns amount  // used_amount = 0
      → fin_transfer_send_tokens_callback
        → is_refund_required = true            // amount.0 == 0
        → remove_fin_transfer(transfer_id)     // finalised_transfers: {}  ← guard cleared
        → emits FailedFinTransferEvent
```

**Step 2 — Replay (natural relayer retry):**
```
relayer → fin_transfer(same proof)             // proof still valid against light client
  → fin_transfer_callback
    → process_fin_transfer_to_near
      → add_fin_transfer(transfer_id)          // succeeds! finalised_transfers: {transfer_id}
      → send_tokens(ft_transfer_call, evil.near)
        → evil.near::ft_on_transfer returns 0  // accept
      → fin_transfer_send_tokens_callback
        → is_refund_required = false
        → tokens delivered to evil.near        // DOUBLE SPEND
```

**Minimal unit test plan** (extending the existing `test_fin_transfer_callback_refund_restores_locked_tokens` pattern):
1. Call `process_fin_transfer_to_near` with a non-empty `msg` and simulate `ft_on_transfer` returning `U128(amount)` (used = 0) → assert `finalised_transfers` no longer contains the `transfer_id` after `fin_transfer_send_tokens_callback`.
2. Call `process_fin_transfer_to_near` again with the identical `transfer_message` → assert it does **not** panic on `add_fin_transfer` (demonstrating the replay succeeds).
3. Simulate `ft_on_transfer` returning `U128(0)` (accept) on the second call → assert tokens are delivered a second time.

The existing test at line 1021 already confirms step 1 (locked tokens are restored and the refund path executes); extending it to check `finalised_transfers.contains(&transfer_id) == false` and then re-invoking `process_fin_transfer_to_near` would fully demonstrate the double-spend. [9](#0-8)
