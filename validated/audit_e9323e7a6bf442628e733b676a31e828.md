### Title
`initTransfer1155` Emits `InitTransfer` Without Actual Token Transfer for Non-Existent ERC-1155 Contracts — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`initTransfer1155` in `OmniBridge.sol` calls `IERC1155(tokenAddress).safeTransferFrom(...)` via a raw interface cast — not through OpenZeppelin's `SafeERC20` — with no contract-existence check. On the EVM, a low-level call to an address with no deployed code returns `success = true` with empty return data. Because `IERC1155.safeTransferFrom` is `void`, the empty return data is silently accepted, the call is treated as successful, and the `InitTransfer` event is emitted as if real tokens were locked. This directly violates the bridge's own documented security invariant.

---

### Finding Description

`initTransfer1155` at lines 439–490 of `OmniBridge.sol`:

```solidity
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    tokenId,
    amount,
    ""
);
// ...
emit BridgeTypes.InitTransfer(
    msg.sender,
    deterministicToken,
    currentOriginNonce,
    amount, ...
);
``` [1](#0-0) 

This is a direct interface cast, not `SafeERC20`. OpenZeppelin v5's `SafeERC20` (used for ERC-20 paths) calls `Address.functionCall` → `verifyCallResultFromTarget`, which checks `target.code.length == 0` and reverts with `AddressEmptyCode`. The ERC-1155 path has no such protection. [2](#0-1) 

The companion function `logMetadata1155` also performs **no existence check** on `tokenAddress` — it stores the `multiTokens` mapping and emits `LogMetadata` for any address, including undeployed ones:

```solidity
function logMetadata1155(address tokenAddress, uint256 tokenId) external payable {
    address deterministicToken = deriveDeterministicAddress(tokenAddress, tokenId);
    MultiTokenInfo storage multiToken = multiTokens[deterministicToken];
    if (multiToken.tokenAddress == address(0)) {
        multiToken.tokenAddress = tokenAddress;
        multiToken.tokenId = tokenId;
    }
    // ...
    emit BridgeTypes.LogMetadata(deterministicToken, Strings.toHexString(tokenAddress), "", 0);
}
``` [3](#0-2) 

The bridge's own `CLAUDE.md` states the invariant that is broken here:

> **Event–transfer atomicity**: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held. [4](#0-3) 

On the NEAR side, `fin_transfer_callback` trusts the emitted event entirely — it reads `init_transfer.token` and `init_transfer.amount` from the proven log and mints/unlocks accordingly, with no secondary verification that the EVM-side transfer actually occurred: [5](#0-4) 

---

### Impact Explanation

An attacker who can get the NEAR bridge to register a `deterministicToken` address (via `logMetadata1155` + NEAR `deploy_token`) can then call `initTransfer1155` with a non-existent or self-destructed ERC-1155 contract address and an arbitrarily large `amount`. The `IERC1155.safeTransferFrom` call succeeds silently (no code → EVM returns success), the `InitTransfer` event is emitted with the fake amount, and the NEAR bridge — treating the proven event as authoritative — mints or unlocks the corresponding NEAR-side tokens for the attacker. This constitutes unauthorized minting and theft of bridged funds.

---

### Likelihood Explanation

The attack requires two steps:

1. **Token registration on NEAR**: `logMetadata1155` emits `LogMetadata` with `symbol=""` and `decimals=0`. Whether NEAR's `deploy_token` accepts this (ERC-1155 tokens have no standard symbol) is uncertain from static analysis alone, but ERC-1155 metadata is intentionally non-standard, making a blanket symbol-empty rejection unlikely for this path.

2. **Self-destruct or pre-deploy knowledge**: The attacker either (a) deploys a malicious ERC-1155 with a self-destruct, registers it, self-destructs it, then calls `initTransfer1155`; or (b) predicts a future ERC-1155 address via CREATE2 and front-runs deployment. Both are realistic for a motivated attacker.

The `logMetadata1155` and `initTransfer1155` functions are fully permissionless — no admin role is required. [6](#0-5) 

---

### Recommendation

Add a contract-existence check in `initTransfer1155` before the `IERC1155.safeTransferFrom` call:

```solidity
require(tokenAddress.code.length > 0, "ERR_TOKEN_NOT_DEPLOYED");
```

Apply the same check in `logMetadata1155` before storing the mapping, to prevent registration of undeployed addresses. Additionally, consider using a wrapper analogous to `SafeERC20` for ERC-1155 calls that verifies the target has code before dispatching.

---

### Proof of Concept

1. Eve predicts the CREATE2 address `A` of a future ERC-1155 token (or deploys one with `selfdestruct`).
2. Eve calls `logMetadata1155(A, tokenId)` → mapping stored, `LogMetadata(deterministicToken, hex(A), "", 0)` emitted.
3. NEAR relayer submits proof of `LogMetadata` to NEAR `deploy_token`; NEAR deploys a bridged token for `deterministicToken`.
4. (If using self-destruct path) Eve self-destructs the ERC-1155 at `A`.
5. Eve calls `initTransfer1155(A, tokenId, 1_000_000e18, 0, 0, "eve.near", "")`.
   - `IERC1155(A).safeTransferFrom(eve, bridge, tokenId, 1_000_000e18, "")` → `A` has no code → EVM returns `(true, "")` → call succeeds silently.
   - `InitTransfer(eve, deterministicToken, nonce, 1_000_000e18, ...)` is emitted.
6. NEAR relayer submits proof of `InitTransfer` to NEAR `fin_transfer`.
7. NEAR `fin_transfer_callback` reads `amount = 1_000_000e18` from the proven log, mints 1,000,000 bridged tokens to `eve.near`.
8. Eve redeems the minted tokens for real assets on NEAR or another chain. [7](#0-6) [8](#0-7)

        address tokenAddress,

        uint128 amount,

        uint128 nativeFee,

        string calldata message
    ) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
        currentOriginNonce += 1;
        if (fee >= amount) {
            revert InvalidFee();
        }

        address deterministicToken = deriveDeterministicAddress(
            tokenAddress,
            tokenId
        );

        IERC1155(tokenAddress).safeTransferFrom(
            msg.sender,
            address(this),
            tokenId,
            amount,
            ""
        );

            msg.sender,
            deterministicToken,
            currentOriginNonce,
            amount,
            fee,
            nativeFee,
            recipient,
            message,
            extensionValue
        );

        emit BridgeTypes.InitTransfer(
            msg.sender,
            deterministicToken,
            currentOriginNonce,
            amount,
            fee,
            nativeFee,
