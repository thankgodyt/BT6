Audit Report

## Title
TOCTOU in `fast_fin_transfer_to_near_callback`: Finalization Not Re-Verified After Cross-Contract Call Enables Double-Spending — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`fast_fin_transfer` checks `is_unified_transfer_finalised` before issuing a cross-contract call to `check_or_pay_ft_storage`, creating a multi-block window. If `fin_transfer` executes during this window, it finalizes the transfer and sends tokens to the recipient. When `fast_fin_transfer_to_near_callback` subsequently runs, it does not re-check finalization status; `add_fast_transfer` succeeds because `fast_transfers` has no entry for this ID, and `send_tokens` fires a second time, delivering tokens twice while only one amount was locked on the source chain.

## Finding Description
**Time of Check:** `fast_fin_transfer` verifies the transfer is not finalized at L778-780, then immediately issues a cross-contract call at L812-826 that spans at least one additional NEAR block.

**Time of Use:** `fast_fin_transfer_to_near_callback` at L854-882 calls `add_fast_transfer` (L2253-2264), which only checks the `fast_transfers` map for duplicate entries — it does not consult `finalised_transfers`. If `fin_transfer` raced ahead during the window, `finalised_transfers` now contains the transfer ID, but `fast_transfers` does not, so `add_fast_transfer` succeeds and `send_tokens` executes.

**Why `fin_transfer` does not block the callback:** `process_fin_transfer_to_near` at L1875-1902 calls `add_fin_transfer` first (inserting into `finalised_transfers`), then reads `get_fast_transfer_status`. Because `add_fast_transfer` has not yet been called, `fast_transfer_status` is `None`, so tokens are sent to the original recipient rather than the relayer. `add_fin_transfer` at L2226-2234 prevents a second `fin_transfer` call but has no mechanism to abort the already-scheduled `fast_fin_transfer_to_near_callback`.

**Result:** Both `process_fin_transfer_to_near` and `fast_fin_transfer_to_near_callback` call `send_tokens` for the same transfer, producing a double-spend.

## Impact Explanation
For bridged (deployed) tokens, `send_tokens` calls `mint` on the token contract; the second mint creates tokens beyond what is locked on the source chain — unauthorized minting. For native (locked) tokens, the bridge transfers from its own reserves twice — direct loss of bridge funds. In both cases the recipient receives `2 × (amount − fee)` tokens while only `amount` was locked on the source chain. This matches the Critical allowed impact: double-spending and unauthorized minting of bridged funds.

## Likelihood Explanation
`fin_transfer` is gated by `#[trusted_relayer]`, so the race requires a trusted relayer to submit a valid proof during the multi-block external call window. A trusted relayer who is also the recipient (or colluding with the recipient) can deliberately sequence the two calls to profit: front `amount` tokens via `fast_fin_transfer`, then immediately submit `fin_transfer` with the valid proof, netting `amount − 2 × fee`. Even without malicious intent, any trusted relayer submitting `fin_transfer` for a transfer whose `fast_fin_transfer_to_near_callback` is in-flight will accidentally trigger the double-spend. The window is bounded by NEAR block time but is deterministically exploitable by a colluding relayer.

## Recommendation
Re-check `is_unified_transfer_finalised` at the start of `fast_fin_transfer_to_near_callback`, before calling `add_fast_transfer` or `send_tokens`. If the transfer has been finalized during the external call window, abort and return the relayer's fronted tokens:

```rust
pub fn fast_fin_transfer_to_near_callback(...) -> Promise {
    if self.is_unified_transfer_finalised(&fast_transfer.transfer_id) {
        // Refund relayer's fronted tokens instead of double-spending
        return self.send_tokens(
            fast_transfer.token_id.clone(),
            storage_payer,
            fast_transfer.amount,
            &String::new(),
        );
    }
    // ... existing logic
}
```

## Proof of Concept
1. A transfer originates on Ethereum (origin_chain: Eth, origin_nonce: N). A valid proof exists.
2. Trusted Relayer R (who is also the NEAR recipient) calls `ft_transfer_call` on the token contract, sending `amount` tokens to the bridge, triggering `fast_fin_transfer`.
3. `fast_fin_transfer` passes the `is_unified_transfer_finalised` check (returns false) and issues the `check_or_pay_ft_storage` cross-contract call. Execution suspends.
4. In the next NEAR block, before `fast_fin_transfer_to_near_callback` executes, Relayer R submits `fin_transfer` with the valid proof.
5. `fin_transfer` → `fin_transfer_callback` → `process_fin_transfer_to_near`: `add_fin_transfer` inserts into `finalised_transfers`; `get_fast_transfer_status` returns `None` (fast transfer not yet recorded); `send_tokens` mints/transfers `amount − fee` tokens to Relayer R as recipient.
6. `fast_fin_transfer_to_near_callback` executes: `add_fast_transfer` succeeds (no entry in `fast_transfers` for this ID); `send_tokens` mints/transfers another `amount − fee` tokens to Relayer R.
7. Relayer R receives `2 × (amount − fee)` tokens. Only `amount` was locked on the source chain. Net gain: `amount − 2 × fee`.
