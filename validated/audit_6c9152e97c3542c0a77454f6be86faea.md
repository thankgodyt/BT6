### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unprivileged Peras-Weight Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic checks. Because Peras certificates are diffused over the node-to-node network and fed directly into chain selection, any unprivileged peer can craft a certificate that boosts an arbitrary block on an adversarial fork, causing an honest node to prefer and switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must authenticate a received `PerasCert` before it is allowed to influence chain selection. The only instance in the codebase is a degenerate placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub always succeeds. The `processCerts` function in the Peras certificate object-diffusion pool writer calls this validator on every inbound certificate batch received from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

Because `validatePerasCert` never produces a `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted and forwarded to the ChainDB via `addPerasCertAsync`:

```haskell
(void . ChainDB.addPerasCertAsync chainDB)
``` [3](#0-2) 

Inside `chainSelSync`, the accepted certificate triggers `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection then calls `preferAnchoredCandidate` with the Peras weight snapshot, which compares chains by `wsvTotalWeight = blockNo + weightBoost`:

```haskell
| otherwise =
    case AF.intersect ours cand of
      ...
      Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (weightedSelectView cfg weights oursSuffix)
          (weightedSelectView cfg weights candSuffix) of
``` [5](#0-4) 

The weight boost injected by the crafted certificate is `perasWeight params` — the configured Peras boost value — applied to any block the attacker names in `pcCertBoostedBlock`.

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` naming any block in the node's VolatileDB as the boosted block. Because `validatePerasCert` performs no signature, committee-membership, quorum, or round-number checks, the certificate is accepted unconditionally. If the attacker names a block on an adversarial fork that is slightly shorter than the honest chain, the injected weight boost can make that fork's `wsvTotalWeight` exceed the honest chain's, causing the node to roll back and adopt the adversarial fork. This is a chain-selection integrity failure: an honest node is made to prefer a non-canonical, less-secure chain without any stake or key compromise by the attacker.

**Impact class (High):** Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is wired into the standard node-to-node protocol stack and is reachable by any connected peer:

```haskell
aPerasCertDiffusionClient
  version
  ExpandedInitiatorContext{eicConnectionId = them, ...}
  channel = do
    ...
    objectDiffusionInboundPeerPipelined
      (hPerasCertDiffusionClient version controlMessageSTM them)
``` [6](#0-5) 

No stake, key material, or privileged access is required. The attacker only needs a TCP connection to the target node and knowledge of a block hash in the node's VolatileDB (obtainable via ChainSync). The stub is the only `BlockSupportsPeras` instance in the codebase and is used in both the `PerasCertDB`-backed and `ChainDB`-backed pool writers.

---

### Recommendation

Replace the stub `validatePerasCert` with a complete implementation that verifies:

1. **BLS aggregate signature** over `(roundNo, boostedBlock)` using the aggregated public keys of the claimed committee members.
2. **VRF eligibility proofs** for each voter in `pcVoters`, confirming committee membership for the stated round.
3. **Quorum threshold**: total stake of verified voters exceeds the configured quorum.
4. **Round-number bounds**: the certificate's round is within the acceptable window relative to the current chain tip.

Until the full implementation is in place, the `PerasCertDiffusion` inbound handler should reject all certificates (return a validation error for every input) rather than accept them unconditionally, so that the stub cannot be exploited.

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to an honest node via the node-to-node protocol.
2. Attacker learns a block hash `H` on an adversarial fork (e.g., via ChainSync) that is within `k` blocks of the node's immutable tip.
3. Attacker sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint s H }` over the `PerasCertDiffusion` channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
5. `addPerasCertAsync` enqueues the certificate into `cdbChainSelQueue`.
6. `chainSelSync` retrieves the boosted block header from the VolatileDB and calls `chainSelectionForBlock`.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the adversarial fork including the injected boost; if `blockNo(fork) + boost > blockNo(honest)`, `ShouldSwitch` is returned.
8. The node rolls back to the fork point and adopts the adversarial chain.

**Root cause line:**
