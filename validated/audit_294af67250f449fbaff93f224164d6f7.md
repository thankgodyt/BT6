Audit Report

## Title
Missing `burn_tokens_if_needed` in `resolve_utxo_fin_transfer` Causes Deployed Token Supply Inflation — (File: near/omni-bridge/src/lib.rs)

## Summary

`resolve_utxo_fin_transfer` omits the `burn_tokens_if_needed` call that its structural counterpart `resolve_fast_transfer` performs. When the UTXO-chain token is a deployed bridge token (e.g., BTC deployed via `deploy_native_token`), the bridge mints new tokens to the recipient via `send_tokens` → `mint` and simultaneously retains the tokens sent by the UTXO connector, permanently inflating on-chain supply by `amount` on every successful UTXO → NEAR finalization.

## Finding Description

The UTXO fin-transfer-to-NEAR flow is:

```
ft_on_transfer (connector calls ft_transfer_call on bridge)
  └─ utxo_fin_transfer                    [checks sender == connector]
       └─ utxo_fin_transfer_to_near
            └─ utxo_fin_transfer_to_near_callback
                 └─ send_tokens → mint(recipient, amount)   [for deployed tokens]
                      └─ resolve_utxo_fin_transfer          [callback — no burn]
```

**Step 1 — Connector deposits tokens into bridge.** The UTXO connector calls `ft_transfer_call(bridge, amount, ..., UtxoFinTransfer{...})`. The bridge receives `amount` deployed BTC tokens. `utxo_fin_transfer` validates `sender_id == config.connector`. [1](#0-0) 

**Step 2 — `send_tokens` mints new tokens to recipient.** For a deployed token, `send_tokens` calls `mint(recipient, amount)`, creating `amount` brand-new tokens credited to the recipient. [2](#0-1) 

**Step 3 — `resolve_utxo_fin_transfer` does not burn.** In the success branch (`is_ft_transfer_call == false`, i.e., `msg` is empty), the callback only emits a log and returns `U128(0)`. There is no call to `burn_tokens_if_needed`. The `amount` tokens the connector deposited remain in the bridge's balance, permanently unburned. [3](#0-2) 

**Contrast with `resolve_fast_transfer`.** The structurally identical fast-transfer callback explicitly calls `burn_tokens_if_needed` with the comment *"Burn the tokens to ensure the locked tokens are not double-minted"*, then returns `U128(0)`. [4](#0-3) 

**`burn_tokens_if_needed` implementation.** It calls `burn(amount)` on the token contract, withdrawing from `predecessor_account_id` (the bridge), only when the token is in `deployed_tokens`. [5](#0-4) 

**`deploy_native_token` inserts into `deployed_tokens`.** Calling `deploy_native_token` for BTC/ZEC inserts the token into `deployed_tokens`, making `is_deployed_token` return `true` and activating the `mint` path in `send_tokens`. [6](#0-5) 

Net accounting per transfer:
- `+amount` minted to recipient (correct)
- `+amount` held by bridge (should be burned, but is not)
- Net supply inflation: `+amount` per transfer

## Impact Explanation

Every successful UTXO → NEAR finalization where the UTXO token is a deployed bridge token inflates the circulating supply by `amount`. The bridge accumulates a growing balance of tokens that were never burned. This constitutes **escrow/token-supply mis-accounting and unauthorized minting**: the bridge holds tokens representing unbacked supply, breaking the 1:1 peg between locked UTXO-chain assets and NEAR-side tokens. Repeated transfers inflate supply by N × amount, unbacked by any locked BTC/ZEC. This matches the Critical allowed impact: *"Balance manipulation, escrow mis-accounting … that changes user or protocol balances"* and *"unauthorized minting … of bridged funds."* [7](#0-6) 

## Likelihood Explanation

The UTXO connector is a trusted contract, but the bug fires on **normal bridge usage**. Any user who sends BTC/ZEC on the origin chain causes the connector to call `ft_transfer_call` on the bridge. No special privilege beyond being a normal bridge user is required. The bug fires on every successful UTXO → NEAR transfer where the token is deployed, making it continuously exploitable at scale with no attacker-specific precondition beyond using the bridge normally. [8](#0-7) 

## Recommendation

Add `self.burn_tokens_if_needed(token_id.clone(), amount)` unconditionally at the start of `resolve_utxo_fin_transfer`, mirroring `resolve_fast_transfer`:

```rust
pub fn resolve_utxo_fin_transfer(
    &mut self,
    token_id: AccountId,
    amount: U128,
    utxo_fin_transfer_msg: UtxoFinTransferMsg,
    origin_chain: ChainKind,
    storage_owner: &AccountId,
) -> U128 {
    // Burn the tokens received from the connector to prevent supply inflation
    self.burn_tokens_if_needed(token_id.clone(), amount);

    let is_ft_transfer_call = !utxo_fin_transfer_msg.msg.is_empty();
    if Self::is_refund_required(is_ft_transfer_call) {
        self.remove_fin_utxo_transfer(
            &utxo_fin_transfer_msg.get_transfer_id(origin_chain),
            storage_owner,
        );
        amount
    } else {
        env::log_str(...);
        U128(0)
    }
}
``` [4](#0-3) 

## Proof of Concept

1. Admin calls `deploy_native_token(ChainKind::Btc, "Bitcoin", "BTC", 8)` — BTC token inserted into `deployed_tokens`.
2. Admin calls `add_utxo_chain_connector(ChainKind::Btc, connector_id, btc_token_id, 8)`.
3. User sends 1 BTC on Bitcoin. Connector calls `ft_transfer_call(bridge, 100_000_000, ..., UtxoFinTransfer{recipient: Near("alice"), msg: ""})`.
4. Bridge receives 100_000_000 units of BTC token (deployed).
5. `utxo_fin_transfer_to_near_callback` → `send_tokens` → `mint(alice, 100_000_000)` — 100_000_000 new tokens minted to Alice.
6. `resolve_utxo_fin_transfer` returns `U128(0)` — bridge retains 100_000_000 BTC tokens, never burned.
7. BTC token total supply is inflated by 100_000_000 per transfer. Repeating N times inflates supply by N × amount, unbacked by any locked BTC.

A sandbox integration test can confirm this by: (a) deploying a native BTC token, (b) minting BTC tokens to the connector, (c) calling `verify_deposit` on the connector, (d) asserting `ft_total_supply` equals `2 × amount` (recipient balance + bridge balance) instead of `amount`. [9](#0-8)
