### Title
Peras Certificate Validation Bypass: `validatePerasCert` Stub Unconditionally Accepts Any Peer-Supplied Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` method unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or authorization checks. This stub is wired directly into the production peer-inbound certificate processing pipeline. Any unprivileged peer can therefore inject a crafted `PerasCert` for an arbitrary block, causing the receiving node to store it as a `ValidatedPerasCert` and trigger chain selection that may prefer a non-canonical chain.

---

### Finding Description

**Root cause — the stub:**

In the catch-all `BlockSupportsPeras` instance (which applies to every block type including `CardanoBlock`), `validatePerasCert` is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No BLS aggregate-signature check, no committee-membership check, no round-number validity check, and no boosted-block existence check are performed. The function wraps the raw, unverified `cert` directly into a `ValidatedPerasCert` and returns `Right`.

**Production call site — inbound certificate pool writer:**

`makePerasCertPoolWriterFromChainDB` passes this stub as the `validateCert` callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← stub always returns Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**Network entry point — node-to-node diffusion handler:**

`makePerasCertPoolWriterFromChainDB` is used directly in the node-to-node `hPerasCertDiffusionClient` handler, which is the live inbound path for certificates arriving from any peer:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

**Chain-selection consequence:**

Once `processCerts` calls `addCert` with the attacker-supplied `ValidatedPerasCert`, `chainSelSync` processes it via `addPerasCertAsync`. The certificate's `vpcCertBoost` (set to `perasWeight params`) is added to the `PerasWeightSnapshot` and used in `WeightedSelectView.wsvTotalWeight` to compare candidate chains:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

If the attacker's certificate boosts a block on a weaker candidate chain, that chain's total weight can exceed the current selection, causing the node to switch to it. [5](#0-4) 

**Analog to the external report:**

| JBToken | Ouroboros Consensus |
|---|---|
| `mint()` has `onlyOwner` guard | `validatePerasCert` is the authorization gate |
| `changeTokenOf` transfers ownership to any address | The stub instance removes all authorization checks |
| New owner mints arbitrary tokens | Any peer injects arbitrary certificates |
| Unauthorized token supply inflation | Unauthorized chain-weight manipulation |

### Impact Explanation

An unprivileged peer can craft a `PerasCert` pointing to any block (e.g., a block on a shorter or adversarial fork) and send it over the Peras certificate diffusion mini-protocol. The receiving node will:

1. Accept it unconditionally (no signature or committee check).
2. Store it in the `PerasCertDB` as a `ValidatedPerasCert` with a non-zero `vpcCertBoost`.
3. Trigger chain selection for the boosted block.
4. Potentially switch to the attacker's preferred chain if its boosted weight exceeds the current selection.

This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

The attack requires only a network connection to the target node and the ability to send a well-formed (but cryptographically unsigned) `PerasCert` CBOR message over the Peras certificate diffusion channel. No stake, no keys, and no special privileges are needed. The diffusion handler is active whenever the node runs with Peras certificate diffusion enabled. Likelihood is **High**.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the BLS aggregate signature over the `(electionId, candidate)` pair using the aggregated verification keys of the claimed committee members.
2. Checks that each claimed voter is a legitimate committee member for the given round (persistent or non-persistent, per the WFALS/EveryoneVotes scheme).
3. Verifies that the certificate's round number is within the acceptable window relative to the current chain tip.
4. Verifies that the boosted block point is known and on a plausible chain.

Until the full implementation is ready, the stub should at minimum return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that no peer-supplied certificate can influence chain selection. The analogous vote path already does this correctly by using an empty stake distribution that causes all votes to be rejected. [6](#0-5) 

---

### Proof of Concept

**Private-testnet reproduction sequence:**

1. Start a node with Peras certificate diffusion enabled.
2. Connect a malicious peer to the node's node-to-node port.
3. The malicious peer sends a `PerasCert` CBOR message (round number = any new round, boosted block = tip of a weaker fork the attacker controls) over the `PerasCertDiffusion` mini-protocol.
4. `objectDiffusionInbound` → `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams` returns `Right` unconditionally.
5. `addPerasCertAsync` stores the cert and calls `chainSelectionForBlock` for the boosted block.
6. `WeightedSelectView` now assigns the boosted block a `wsvWeightBoost = perasWeight params` advantage.
7. If the boosted block is on a candidate chain whose `wsvTotalWeight` now exceeds the current selection, the node switches chains.

The only constraint is that the boosted block must already be in the node's `VolatileDB` (line 520 of `ChainSel.hs`); if it is not, the cert is stored but chain selection is deferred until the block arrives — at which point the boost is applied automatically. [7](#0-6)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
