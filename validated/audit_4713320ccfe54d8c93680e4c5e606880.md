### Title
Unconditional `validatePerasCert` Acceptance Allows Unprivileged Peer to Inject Fake Weight Boosts and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Any unprivileged peer connected via the `perasCertDiffusionProtocol` mini-protocol can send a crafted `PerasCert` naming an arbitrary block, have it accepted as fully validated, and thereby inject a spurious Peras weight boost that distorts chain selection on the receiving node. This is the direct analog of the reported DAO Pool bug: just as that contract called `transferFrom` but never verified the resulting balance, this code calls `validatePerasCert` but the function never verifies anything about the certificate.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The `BlockSupportsPeras` instance for all `blk` is explicitly marked as a temporary placeholder ("degenerate instance for all blks to get things to compile"), but it is the only instance in the codebase and is used directly in the production certificate-ingestion path:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No quorum check, no committee-membership check, no BLS/aggregate-signature verification, no round-number plausibility check — every certificate is unconditionally promoted to `ValidatedPerasCert` carrying the full `perasWeight params` boost.

**Production wiring — the stub is called on every peer-supplied certificate:**

`makePerasCertPoolWriterFromChainDB` is the production writer used when Peras is enabled. It passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each new certificate and, if all pass (which they always do), adds them to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Chain-selection impact — fake boosts directly alter the preferred chain:**

`addPerasCertAsync` feeds the accepted certificate into `chainSelSync`, which triggers `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection uses `preferAnchoredCandidate`, which, when Peras is enabled (non-empty weight snapshot), compares fragments by `wsvTotalWeight = blockNo + weightBoost`:

```haskell
case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
  LT -> ShouldSwitch (Heavier $ ...)
  ...
``` [5](#0-4) 

A fake certificate boosting a block on a shorter adversarial fork can make `wsvTotalWeight(adversarial) > wsvTotalWeight(honest)`, causing the node to switch away from the canonical chain.

**Entry point — reachable by any unprivileged peer:**

The `perasCertDiffusionProtocol` is a standard node-to-node mini-protocol, negotiated in the handshake and available to any connecting peer when Peras is enabled via `rnFeatureFlags`:

```haskell
, perasCertDiffusionProtocol =
    (InitiatorProtocolOnly (MiniProtocolCb (\ctx -> aPerasCertDiffusionClient version ctx)))
``` [6](#0-5) 

No stake, no keys, no privileged access is required.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can inject one certificate per round (the deduplication check only filters by `PerasRoundNo`). Each accepted certificate assigns `perasWeight params` of additional weight to an attacker-chosen block. By targeting a block on a shorter adversarial fork, the attacker can make that fork's `wsvTotalWeight` exceed the honest chain's, causing the victim node to perform a chain switch. This constitutes a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical, less-secure chain beyond the intended security assumptions of Ouroboros Praos/Peras.

---

### Likelihood Explanation

Peras is currently disabled by default (`rnFeatureFlags` must explicitly include the Peras flag), so the attack surface is limited to nodes that opt in to the experimental feature. However, the code is fully wired into the production node path — no further integration work is needed for the vulnerability to be active. Any peer that successfully negotiates the Peras-enabled NTN version can immediately exploit this. The attack requires only the ability to open a TCP connection to the target node and send a single well-formed CBOR-encoded `PerasCert` message.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:

1. **Quorum**: the certificate attests that a sufficient number of eligible committee members voted for the boosted block in the claimed round.
2. **Aggregate signature**: the BLS/aggregate vote signature over `(electionId, candidate)` is valid against the aggregated verification keys of the claimed voters.
3. **Committee membership**: each claimed voter was actually elected to the committee for that round (VRF eligibility proof).
4. **Round plausibility**: the certificate's round number is consistent with the current slot and Peras round length.

Until the real implementation is ready, the `perasCertDiffusionProtocol` server/client should be disabled or the `processCerts` path should reject all externally received certificates when the real validation logic is absent, rather than accepting them unconditionally.

---

### Proof of Concept

**Setup**: a private testnet with Peras enabled (`rnFeatureFlags` contains the Peras flag), two honest nodes A and B, and an attacker node C.

1. Honest nodes A and B are on the canonical chain at block height H (block hash `h_honest`).
2. Attacker C mines a shorter fork of height H-5 (block hash `h_fork`) and serves it to A via ChainSync. A rejects it because `blockNo(h_fork) < blockNo(h_honest)`.
3. C sends a crafted `PerasCert` to A via `perasCertDiffusionProtocol`:
   ```
   PerasCert { pcCertRound = <current_round>, pcCertBoostedBlock = BlockPoint <slot> h_fork }
   ```
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored; `addPerasCertAsync` triggers `chainSelSync`.
6. `chainSelSync` calls `chainSelectionForBlock` for `h_fork`.
7. `preferAnchoredCandidate` computes:
   - `wsvTotalWeight(honest suffix) = (H - anchor) + 0`
   - `wsvTotalWeight(fork suffix) = (H-5 - anchor) + perasWeight`
   - If `perasWeight > 5`, `ShouldSwitch` is returned.
8. Node A rolls back 5 blocks and adopts the adversarial fork, diverging from the honest network.

**Expected outcome**: node A switches to the adversarial fork. **Correct outcome**: the certificate is rejected because no valid quorum of committee members signed it.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
