### Title
Unenforced `cschcAddHandle` PRECONDITION Desynchronizes Map/Sequence Views, Corrupting GDD and CSJ Chain-Selection State — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client/State.hs`)

---

### Summary

`ChainSyncClientHandleCollection` maintains two synchronized views of connected peers — a `Map` and a `StrictSeq` — and documents a PRECONDITION on `cschcAddHandle` that the peer must not already be present. The implementation never enforces this precondition. If the same peer is registered twice (e.g., via a rapid reconnect race), `Map.insert` silently overwrites the map entry while `Seq.|>` appends a second entry to the sequence. The subsequent `cschcRemoveHandle` removes only the first sequence occurrence via `Seq.spanl`, leaving a ghost entry in the sequence after the map entry is gone. The GDD governor reads exclusively from the map view while CSJ reads from the sequence view, so the two components operate on divergent peer sets, corrupting chain-selection and density-disconnect decisions.

---

### Finding Description

`newChainSyncClientHandleCollection` in `State.hs` constructs a `ChainSyncClientHandleCollection` whose comment at line 123 states:

> `-- PRECONDITION: The peer is not already in the collection`

The implementation of `cschcAddHandle` at lines 159–161 does not enforce this:

```haskell
, cschcAddHandle = \peer handle -> do
    modifyTVar handlesMap (Map.insert peer handle)  -- silently overwrites
    modifyTVar handlesSeq (Seq.|> (peer, handle))   -- always appends
``` [1](#0-0) [2](#0-1) 

`Map.insert` overwrites any existing entry for the key, while `Seq.|>` unconditionally appends, so a second call for the same peer leaves the map with one entry (the newer handle) and the sequence with two entries.

`cschcRemoveHandle` at lines 162–166 uses `Seq.spanl ((/= peer) . fst)` which stops at the **first** occurrence, so `Seq.drop 1 ys` removes only that first entry:

```haskell
, cschcRemoveHandle = \peer -> do
    modifyTVar handlesMap (Map.delete peer)
    modifyTVar handlesSeq $ \s ->
      let (xs, ys) = Seq.spanl ((/= peer) . fst) s
       in xs Seq.>< Seq.drop 1 ys
``` [3](#0-2) 

After the first connection's `deleteHandle` fires, the map is empty (`Map.delete` on the overwritten entry) but the sequence still holds the second handle — a ghost entry.

The two consumers of this collection use different views:

- **GDD governor** (`Governor.hs` line 113) receives `getHandles :: STM m (Map peer (ChainSyncClientHandle m blk))` — the map view — and uses it to build `gddCtxKillActions` and `gddCtxStates` for LoE and density-disconnect computation. [4](#0-3) 

- **CSJ governor** (`Jumping.hs`) reads `cschcSeq` to iterate over peers and elect dynamo/objector/jumper roles. [5](#0-4) 

The `cschcAddHandle` call sites in `Client.hs` are wrapped in `bracket_ insertHandle deleteHandle`, meaning the race window is between a reconnecting peer's new `insertHandle` STM commit and the old connection's `deleteHandle` STM commit running in a different thread: [6](#0-5) 

---

### Impact Explanation

After the desynchronization, GDD's `getGDDStateView` traverses only the map, so the ghost peer's candidate fragment is absent from `candidates`. The `sharedCandidatePrefix` / `densityDisconnect` computation therefore excludes that peer's chain, causing the LoE fragment to advance further than it should and suppressing a legitimate density-disconnect decision against that peer. [7](#0-6) [8](#0-7) 

Simultaneously, CSJ still sees the ghost entry in `cschcSeq` and may elect the stale handle as dynamo or objector, causing the node to wait for headers from a peer whose connection state is no longer tracked by GDD. This breaks the invariant that GDD and CSJ operate on the same peer set, which is the foundation of the Genesis security argument: GDD must be able to disconnect any peer that CSJ is using as dynamo/objector if that peer's chain is sparser. With the ghost entry, GDD cannot issue the kill action for a peer it no longer sees in the map, while CSJ continues to treat that peer as authoritative for chain selection.

This maps to: **High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions**, because the LoE can advance past the point where GDD would have blocked it, and the dynamo role can be held by a peer GDD has lost track of.

---

### Likelihood Explanation

The precondition violation requires the same logical peer to have two concurrent `ChainSyncClient` threads both past their `insertHandle` call before either's `deleteHandle` fires. This can occur when a peer disconnects and immediately reconnects: the network layer initiates a new outbound or inbound connection before the old connection's `bracket_` cleanup has committed its `cschcRemoveHandle` STM transaction. The STM operations are not guarded by any membership check, so the race window is the interval between the new `insertHandle` commit and the old `deleteHandle` commit. A malicious peer that repeatedly connects and disconnects at high frequency can widen this window. The likelihood is **low** under normal operation but non-negligible under adversarial rapid-reconnect behavior.

---

### Recommendation

Enforce the precondition inside the STM action by checking map membership before appending to the sequence:

```haskell
, cschcAddHandle = \peer handle -> do
    m <- readTVar handlesMap
    when (Map.member peer m) $
      error "cschcAddHandle: PRECONDITION violated – peer already in collection"
    modifyTVar handlesMap (Map.insert peer handle)
    modifyTVar handlesSeq (Seq.|> (peer, handle))
```

Because both `modifyTVar` calls and the membership check are in the same STM transaction, this is race-free. Alternatively, the caller sites in `Client.hs` should assert the precondition before calling `cschcAddHandle`, or the connection manager should guarantee at most one live `ChainSyncClient` per peer at any time and document that guarantee explicitly.

---

### Proof of Concept

```
1. Peer A connects (connection C1). insertHandle fires:
     map = {A: h1},  seq = [(A, h1)]

2. Peer A reconnects (connection C2) before C1's deleteHandle fires.
   insertHandle fires for C2:
     map = {A: h2},  seq = [(A, h1), (A, h2)]
   -- map now tracks h2; seq has both

3. C1's deleteHandle fires (cschcRemoveHandle A):
     Map.delete A  → map = {}
     Seq.spanl removes first occurrence of A → seq = [(A, h2)]
   -- map is empty; seq has ghost entry h2

4. GDD calls getHandles → empty map → peer A absent from LoE/density computation.
   CSJ calls cschcSeq → [(A, h2)] → elects A as dynamo.

5. GDD cannot issue cschGDDKill for A (not in killActions map).
   CSJ drives chain selection via A's stale/adversarial candidate fragment.
   LoE advances past the point GDD would have blocked, allowing the node
   to select blocks on A's chain that GDD would otherwise have rejected.
```
