Audit Report

## Title
Replay of `fin_transfer` Proof After Recipient-Rejection Refund Enables Double-Spend — (File: near/omni-bridge/src/lib.rs)

## Summary

When a `fin_transfer` to a NEAR recipient uses `ft_transfer_call` (non-empty `msg`) and the recipient contract rejects all tokens, `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which deletes the `TransferId` from `finalised_transfers` — the sole replay-protection barrier for inbound proofs. The identical foreign-chain proof can then be re-submitted, causing a second mint or unlock for a single on-chain lock event, resulting in unauthorized token minting or double-unlock of escrowed funds.

## Finding Description

The inbound finalization flow for a NEAR-recipient transfer is:

1. `fin_transfer` → `verify_proof` (cryptographic check only, no consumed-proof tracking) → `fin_transfer_callback` → `process_fin_transfer_to_near`
2. `add_fin_transfer` inserts the `TransferId` into `finalised_transfers` (the only replay guard).
3. `send_tokens` issues `ft_transfer_call` when `msg` is non-empty.
4. `fin_transfer_send_tokens_callback` is invoked as the callback.

Inside `fin_transfer_send_tokens_callback`, `is_refund_required` returns `true` when the `ft_transfer_call` result shows 0 tokens were used — which occurs when the recipient's `ft_on_transfer` returns the full amount (rejecting all tokens). In that branch:

```rust
// near/omni-bridge/src/lib.rs lines 1702-1718
if Self::is_refund_required(is_ft_transfer_call) {
    self.burn_tokens_if_needed(...);
    self.revert_lock_actions(&lock_actions);
    self.remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner);
    // emits FailedFinTransferEvent
}
```

`remove_fin_transfer` unconditionally removes the entry from `finalised_transfers`:

```rust
// near/omni-bridge/src/lib.rs lines 2322-2324
fn remove_fin_transfer(&mut self, transfer_id: &TransferId, storage_owner: &AccountId) {
    let storage_usage = env::storage_usage();
    self.finalised_transfers.remove(transfer_id);
```

After removal, `add_fin_transfer` will succeed again for the same `TransferId` because the set no longer contains it:

```rust
// near/omni-bridge/src/lib.rs lines 2226-2231
fn add_fin_transfer(&mut self, transfer_id: &TransferId) -> NearToken {
    let storage_usage = env::storage_usage();
    require!(
        self.finalised_transfers.insert(transfer_id),
        BridgeError::TransferAlreadyFinalised.as_ref()
    );
```

The provers (EVM light-client prover, Wormhole VAA prover, MPC prover) perform only cryptographic validity checks against the light-client state; none of them track which proofs have already been consumed. `finalised_transfers` is the only replay barrier in the system, and once it is cleared, the identical proof bytes are accepted a second time.

## Impact Explanation

This directly enables **unauthorized minting** (for bridge-deployed tokens) or **double-unlock of escrowed native tokens** — both are Critical impacts under the allowed scope. An attacker who controls the NEAR recipient contract receives two full token deliveries for a single foreign-chain lock event, permanently inflating the bridged token supply or draining the bridge escrow by the transfer amount.

## Likelihood Explanation

- The attacker controls both the recipient address and the `msg` field when initiating the transfer on the EVM side — both are ordinary user-supplied inputs with no privilege requirement.
- The `FailedFinTransferEvent` emitted after the first rejection is a natural signal for relayers to retry, making the second proof submission likely without any social engineering.
- The malicious recipient contract needs only to return the full amount from `ft_on_transfer` on the first call and `0` on the second call — trivial to implement.
- No admin compromise, key leak, MPC collusion, or validator collusion is required.

## Recommendation

Do **not** remove the `finalised_transfers` entry on a failed token delivery. The entry records that the foreign-chain event was consumed; that fact is permanent regardless of what happens on the NEAR side afterward. Specifically:

- Keep the `finalised_transfers` entry intact on refund in `fin_transfer_send_tokens_callback`.
- If token delivery fails, record the failure separately (e.g., a `failed_transfers` mapping keyed by `TransferId`) and allow the user to claim a refund through a separate, authenticated path that does not re-accept the original proof.
- The storage cost concern (currently the motivation for removing the entry) can be addressed by refunding storage from a different source or by accepting the storage cost as a protocol invariant.

## Proof of Concept

**Setup:**
- Deploy a malicious NEAR contract `evil.near` whose `ft_on_transfer` returns the full `amount` on the first call and `"0"` on the second call.
- Initiate a transfer on EVM: `recipient = "evil.near"`, `msg = "x"` (any non-empty string to trigger `ft_transfer_call`).

**Step 1 — First `fin_transfer`:**
```
relayer → fin_transfer(proof)
  → fin_transfer_callback
    → process_fin_transfer_to_near
      → add_fin_transfer(transfer_id)          // finalised_transfers: {transfer_id}
      → send_tokens via ft_transfer_call → evil.near::ft_on_transfer returns amount (reject)
      → fin_transfer_send_tokens_callback
        → is_refund_required = true
        → burn_tokens_if_needed / revert_lock_actions
        → remove_fin_transfer(transfer_id)     // finalised_transfers: {}  ← guard cleared
        → emits FailedFinTransferEvent
```

**Step 2 — Replay with same proof:**
```
relayer → fin_transfer(same proof)             // proof still valid against light client
  → fin_transfer_callback
    → process_fin_transfer_to_near
      → add_fin_transfer(transfer_id)          // succeeds! finalised_transfers: {transfer_id}
      → send_tokens via ft_transfer_call → evil.near::ft_on_transfer returns "0" (accept)
      → fin_transfer_send_tokens_callback
        → is_refund_required = false
        → tokens delivered to evil.near        // DOUBLE SPEND
```

A minimal integration test using `near-workspaces` can reproduce this by deploying a counter-based mock receiver contract, calling `fin_transfer` twice with the same borsh-serialized `ProverResult::InitTransfer` payload (as already done in `near/omni-tests/src/fin_transfer.rs`), and asserting that the second call succeeds and the recipient balance doubles.
