Audit Report

## Title
Native ETH Transfer to Non-Payable Contract Recipient Permanently Freezes Bridged Funds - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
In `OmniBridge.finTransfer`, the nonce is marked used at line 287 before the ETH delivery at lines 317–322. However, if `payload.recipient` is a contract without a `receive()` or `fallback()` function, the low-level `call` returns `success = false`, the function reverts with `FailedToSendEther()`, and Solidity's revert semantics roll back the nonce write along with all other state changes. Because the MPC-signed payload embeds the recipient address and cannot be altered, every subsequent relay attempt produces the identical revert, permanently freezing the ETH inside the bridge while the corresponding NEAR-side burn is already irreversible.

## Finding Description
`finTransfer` writes `completedTransfers[payload.destinationNonce] = true` at line 287, then at lines 317–322 executes:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
```

A revert at line 322 unwinds the entire transaction, including the nonce write at line 287. The Borsh-encoded payload signed by the MPC service (lines 289–313) includes `payload.recipient` verbatim; no relayer can substitute a different address without invalidating the ECDSA signature checked at line 311. There is no escrow, no admin recovery function, and no alternative finalization path for a failed ETH delivery. The `receive() external payable {}` on the bridge itself (line 574) is irrelevant — it only allows the bridge to receive ETH, not to rescue stuck funds.

## Impact Explanation
The user's NEAR tokens are burned or locked in a finalized, irreversible NEAR transaction. The corresponding ETH held by the bridge can never be delivered to the intended recipient and has no protocol-level recovery path. This constitutes **permanent freezing of bridged funds**, which is an explicitly listed Critical impact under the allowed scope.

## Likelihood Explanation
No attacker capability is required; the condition is triggerable by any bridge user, even accidentally. Contract addresses are routine recipients in DeFi: Gnosis Safe multisigs, DAO treasuries, protocol vaults, and smart-contract wallets are all commonly used as destination addresses, and many do not implement `receive()`. The user specifies the EVM recipient when initiating the transfer on NEAR, before any EVM-side validation can occur.

## Recommendation
Replace the push-payment pattern with a pull-payment (escrow) pattern: on a failed ETH delivery, credit the amount to a `mapping(address => uint256) claimable` mapping keyed by `payload.recipient` and mark the nonce as consumed. Provide a separate `claimEth(address recipient)` function allowing the recipient (or anyone on their behalf) to withdraw. This ensures the nonce is always consumed, the bridge's accounting remains consistent, and funds are never permanently frozen.

## Proof of Concept
1. Deploy a contract `NoReceive` with no `receive()` or `fallback()` on a local EVM fork.
2. On the NEAR side, initiate a native-ETH bridge transfer specifying `NoReceive`'s address as the EVM recipient; the NEAR-side burn completes.
3. The MPC service signs a `TransferMessagePayload` embedding `NoReceive`'s address.
4. Call `OmniBridge.finTransfer` with the signed payload and `msg.value == payload.amount`.
5. Execution reaches line 319: `NoReceive.call{value: amount}("")` returns `(false, "")`.
6. Line 322 reverts with `FailedToSendEther()`; the nonce write at line 287 is rolled back.
7. Repeat step 4 with the same signed payload — identical revert every time.
8. Assert: `completedTransfers[nonce] == false` (nonce never consumed), ETH balance of bridge unchanged, NEAR tokens permanently burned.
