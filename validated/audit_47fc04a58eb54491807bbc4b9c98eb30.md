### Title
Unbounded Caller-Supplied `gas_fee` in `request_refund` Allows Any Account to Destroy User Deposit Funds - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

The `request_refund` public entry point accepts a caller-supplied `gas_fee: Option<u128>` parameter that is validated only against `< amount` (the deposit value). There is no upper-bound check against `config.max_btc_gas_fee` or any other reasonable ceiling. Because `request_refund` is permissionless and only one refund request can exist per UTXO, an attacker can front-run a legitimate user's refund request with `gas_fee = amount - 1`, causing the user to receive back only 1 satoshi while the rest is consumed as a BTC miner fee.

### Impact Explanation

A user who deposited BTC and is entitled to a refund can have nearly their entire deposit destroyed (sent to BTC miners) by an unprivileged attacker. The attacker does not need any role or key — only a small NEAR storage deposit and knowledge of the deposit transaction (public on-chain). The user's funds are permanently lost: the BTC miner fee is irreversible once the refund transaction is broadcast and confirmed. This constitutes significant destruction of user funds.

**Impact: Critical** — Significant loss/destruction of user funds with no recovery path once the refund transaction is signed and broadcast.

---

### Likelihood Explanation

The attack requires the attacker to:
1. Monitor the Bitcoin blockchain for deposits to the bridge.
2. Reconstruct the `deposit_msg` (public or derivable from the deposit address).
3. Submit a valid Merkle inclusion proof (public blockchain data).
4. Front-run the legitimate user's `request_refund` call.

The DAO can reject a suspicious refund request via `internal_reject_refund`, but this requires active monitoring and timely intervention. For pre-authorized refund addresses the timelock is only 2 days (`DEFAULT_REFUND_TIMELOCK_SEC`), leaving a narrow window for the DAO to act.

**Likelihood: Low-Medium** — Requires on-chain monitoring and front-running, but no privileged access.

---

### Recommendation

Enforce an upper bound on the caller-supplied `gas_fee` in `request_refund`, analogous to the `max_btc_gas_fee` check already applied in the withdrawal path. Specifically:

1. In `request_refund_callback`, after resolving `gas_fee`, add:
   ```rust
   require!(
       resolved_gas_fee <= config.max_btc_gas_fee,
       "Gas fee exceeds max_btc_gas_fee"
   );
   ```
2. Alternatively, ignore the caller-supplied `gas_fee` entirely and always derive it from `get_refund_gas_fee()`, removing the `Option<u128>` parameter from the public API.

---

### Proof of Concept

1. Alice deposits 1,000,000 satoshi to her bridge deposit address with `deposit_msg.refund_address = Some("alice_btc_addr")`.
2. The deposit transaction is confirmed on Bitcoin.
3. Attacker observes the transaction on-chain, reconstructs Alice's `deposit_msg`, and calls `request_refund` with `gas_fee = 999_999` (one less than the deposit amount). The call passes the only check: `999_999 < 1_000_000`.
4. Alice calls `request_refund` — it reverts with `"Refund request already exists for this UTXO"`.
5. After the 2-day timelock, `execute_refund` is called. The PSBT is built with `refund_amount = 1_000_000 - 999_999 = 1` satoshi sent to Alice and `999_999` satoshi consumed as the BTC miner fee.
6. Alice receives 1 satoshi; 999,999 satoshi are permanently destroyed.
