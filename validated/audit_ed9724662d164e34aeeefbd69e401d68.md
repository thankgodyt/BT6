### Title
Missing Peras Certificate Cryptographic Verification Before Chain-Selection Weight Boost — (`Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

`implAddCert` in `PerasCertDB.Impl` stores incoming Peras certificates in the in-memory database and immediately makes their weight boost available to chain selection, but performs **no cryptographic verification** of the aggregate vote signature or voter eligibility. A developer-acknowledged TODO comment confirms the validation logic is intentionally absent. An unprivileged peer can therefore inject a crafted `ValidatedPerasCert` that boosts an arbitrary block's chain-selection weight, potentially causing an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — missing prerequisite check before a state-mutating operation**

The analog to the Notional M-1 bug is exact: just as Notional's `CompoundV2AssetAdapter` called `mint` without first calling `approve`, `implAddCert` mutates the certificate database and triggers chain selection without first calling any certificate-verification function.

`implAddCert` in `PerasCertDB.Impl`:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120

The only guard is a round-number deduplication check (`Set.member roundNo`). No aggregate-signature verification, no voter-eligibility check, and no boosted-block existence check is performed before the certificate is committed to the TVar and its weight is made available via `getWeightSnapshot`.

**The `ValidatedPerasCert` wrapper provides no actual validation**

In tests, `ValidatedPerasCert` is constructed directly from a raw `PerasCert` plus a weight value, with no cryptographic check:

```haskell
genValidatedPerasCert :: Gen (ValidatedPerasCert TestBlock)
genValidatedPerasCert =
  ValidatedPerasCert
    <$> genPerasCert
    <*> pure (perasWeight mkPerasParams)
``` [2](#0-1) 

The committee API *does* define `implVerifyCert` with full aggregate-signature verification: [3](#0-2) 

But this function is never called in the network-reception → `addCert` path.

**Chain selection is triggered directly from the unvalidated certificate**

`chainSelSync` in `ChainSel.hs` calls `PerasCertDB.addCert` and, if the certificate is new, immediately triggers `chainSelectionForBlock` for the boosted block:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  ...
  certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
  ...
  lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The weight snapshot used during chain selection is derived directly from the unverified certificate's `getPerasCertBoost` value: [5](#0-4) 

**Attacker-controlled entry path**

Peras certificates are diffused over the network via the `ObjectDiffusion` mini-protocol. The inbound writer (`makePerasCertPoolWriterFromCertDB`) feeds directly into `PerasCertDB.addCert` without an interposed verification step, as shown in the smoke test:

```haskell
inboundPoolWriter = makePerasCertPoolWriterFromCertDB mockSystemTime inboundPool
``` [6](#0-5) 

An unprivileged peer can therefore craft a `PerasCert` with an arbitrary `boostedBlock` and an inflated `perasWeight`, wrap it in `ValidatedPerasCert`, and send it over the diffusion channel. The receiving node will store it, compute a weight snapshot that includes the fake boost, and may switch to the adversary's preferred chain.

---

### Impact Explanation

**High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

By injecting a certificate with a large fake weight boost for a block on a minority fork, an adversary can cause an honest node to:

1. Compute a `PerasWeightSnapshot` that assigns inflated weight to the adversary's chosen block.
2. Trigger `chainSelectionForBlock` for that block.
3. Prefer the adversary's fork over the canonical chain, violating the chain-selection invariant of Ouroboros Peras.

This matches the allowed impact category: *"High. Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is a public, unauthenticated channel. Any peer can send a certificate. The missing check is explicitly acknowledged in the codebase (`TODO: we will need to update this method with non-trivial validation logic`), confirming the gap is real and not guarded elsewhere. Once Peras is activated on a network, every node running this code is reachable via this path.

---

### Recommendation

Before `implAddCert` commits a certificate to the TVar, call the committee's `verifyCert` function (e.g., `implVerifyCert` from `EveryoneVotes` or the equivalent for the active committee implementation) to verify the aggregate vote signature and voter eligibility. Only certificates that pass this check should be stored and used to influence chain selection. This mirrors the Notional fix pattern: add the prerequisite check (`approve`) before the state-mutating operation (`mint`/`addCert`).

```haskell
implAddCert env cert = do
  -- Prerequisite: verify certificate before storing
  case verifyCert committee cert of
    Left err -> pure (pure $ RejectedInvalidCert err)
    Right _  -> -- proceed with existing storage logic
```

---

### Proof of Concept

1. Connect to a node with Peras enabled as an unprivileged peer via the Peras cert diffusion mini-protocol.
2. Construct a `PerasCert` with `pcCertBoostedBlock` pointing to a block on a minority fork and `perasWeight` set to a value exceeding the canonical chain's weight advantage.
3. Wrap it in `ValidatedPerasCert` (no signature required by the current code) and send it.
4. Observe that `chainSelSync` calls `chainSelectionForBlock` for the boosted block and the node's `getWeightSnapshot` now includes the fake boost, causing it to prefer the minority fork.

The deterministic equivalent: in the `PerasCertDB` state-machine test (`Test/Ouroboros/Storage/PerasCertDB/StateMachine.hs`), the `precondition` for `AddCert` only rejects equivocating certificates (same round, different block); it does not require any cryptographic validity, confirming no verification gate exists in the current model. implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
