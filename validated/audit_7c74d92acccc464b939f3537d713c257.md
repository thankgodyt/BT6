### Title
Peras Certificate Signature Verification Bypass: `validatePerasCert` Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` function in the `BlockSupportsPeras` instance unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer connected via the object-diffusion mini-protocol can send a crafted `PerasCert` with an arbitrary round number and boosted-block pointer; the node will accept it, store it in the `PerasCertDB`, and apply its Peras chain-selection boost to the attacker-chosen block. This is a direct analog to the external report's "signature does not cover all parameters" class: here the signature is not checked at all.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into the production inbound path:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **universal** `BlockSupportsPeras` instance that applies to all block types: [2](#0-1) 

**Production inbound path — `processCerts` calls this stub directly:**

`makePerasCertPoolWriterFromChainDB` (the production writer used when the ChainDB is in play) passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` then calls this callback for every certificate received from a peer that is not already in the DB: [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the `partitionEithers` call at line 168 will always produce an empty error list, and every crafted certificate is unconditionally forwarded to `addCert` and stored in the `PerasCertDB`.

**Secondary finding — `validatePerasVote` skips BLS signature verification:**

`validatePerasVote` only checks whether the voter's ID appears in the stake distribution; it never calls `verifyVoteSignature` or any BLS primitive: [5](#0-4) 

The production vote-inbound path (`makePerasVotePoolWriterFromChainDB`) uses the same stub: [6](#0-5) 

The actual BLS signing and verification machinery exists and is correct (`hashVoteSignature`, `signVote`, `verifyVoteSignature` in `BLS.hs`), but it is never invoked on the inbound path: [7](#0-6) 

### Impact Explanation

**Critical — Bypass of Peras certificate/vote verification enabling unauthorized chain-selection manipulation.**

A certificate accepted by `validatePerasCert` is stored in the `PerasCertDB` and applied as a Peras boost weight (`vpcCertBoost = perasWeight params`) during chain selection. An attacker who can connect as a peer (no stake, no keys required) can:

1. Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <attacker-chosen block point>`.
2. Send it via the object-diffusion mini-protocol.
3. The node stores it as a `ValidatedPerasCert` and applies the full Peras boost to the attacker's chosen block.
4. Chain selection now prefers the attacker's block over the honest canonical chain, causing the node to diverge.

This satisfies the "High/Critical — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain" impact category.

For votes: any peer can forge votes attributed to any registered pool (whose pool key hash is in the stake distribution) without possessing the pool's BLS signing key, potentially manufacturing artificial quorum for an attacker-chosen block.

### Likelihood Explanation

**High.** The entry point is the standard object-diffusion mini-protocol, reachable by any peer that can establish a connection. No stake, no keys, and no privileged access are required. The attacker only needs to know a valid `PerasRoundNo` (observable from the chain) and a target block point. The stub is wired into the production `ChainDB`-backed writer path, not just a test helper.

### Recommendation

1. Implement real aggregate BLS signature verification inside `validatePerasCert`, verifying the `AggregateVoteSignature` against the aggregated public keys of the claimed voters and the `(roundNo, boostedBlock)` payload using `verifyAggregateVoteSignature` from `CryptoSupportsAggregateVoteSigning`.
2. Implement BLS vote-signature verification inside `validatePerasVote` by calling `verifyVoteSignature` with the voter's public key, `electionId`, and `candidate` before accepting the vote.
3. Until the real implementation is in place, gate the Peras object-diffusion writers behind a feature flag so that the stub is never reachable from an external peer on a live network.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
```
