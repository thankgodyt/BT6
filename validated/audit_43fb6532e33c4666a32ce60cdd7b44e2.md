### Title
Peras Certificate Validation Is a No-Op Stub, Allowing Unprivileged Peers to Boost Arbitrary Blocks and Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the catch-all `BlockSupportsPeras` instance unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic validation whatsoever. Because this degenerate instance is the only one currently wired into the production object-diffusion inbound path, any unprivileged peer can send a crafted `PerasCert` naming any block as the boosted block. The node accepts it, stores it in the `PerasCertDB`, and immediately triggers chain selection for the adversary-chosen block, granting it unearned Peras weight. This can cause an honest node to prefer a non-canonical or adversary-controlled chain over the legitimate chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a stub that always succeeds:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (the comment at line 319 reads "TODO: degenerate instance for all blks to get things to compile"). No specific instance exists for `CardanoBlock` or `ShelleyBlock`, so this catch-all is used for all block types. [2](#0-1) 

**Production inbound path wires this stub directly:**

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate; if all pass (they always do), each is timestamped and forwarded to `ChainDB.addPerasCertAsync`. [4](#0-3) 

**Chain selection is then triggered for the adversary-chosen block:**

```haskell
-- Trigger chain selection for the boosted block.
lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The boosted block's point is taken directly from the unvalidated certificate's `pcCertBoostedBlock` field: [6](#0-5) 

**Chain selection uses the injected weight to prefer candidates:**

`preferAnchoredCandidate` computes `weightedSelectView` over the candidate fragment, which sums `weightBoostOfPoint` for every block in the fragment. A fraudulently boosted block on a minority fork inflates that fork's `wsvTotalWeight`, potentially causing `ShouldSwitch`. [7](#0-6) 

**Analog to the Dinari bug:** In Dinari, `_cancelOrderAccounting` sends the refund to `orderRequest.recipient` (the wrong party) instead of `msg.sender` (the order creator), because the code uses the wrong identity field. Here, `validatePerasCert` grants the Peras boost to whichever block the *sender* names in `pcCertBoostedBlock` — the wrong party (an adversary-controlled block) receives the chain-weight credit — because the identity/eligibility of the certificate's voters is never checked.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's `VolatileDB` (e.g., a block on a minority fork the adversary controls).
2. The node accepts it unconditionally, stores it, and re-runs chain selection.
3. The adversary's fork now carries extra `PerasWeight`; if the boost is large enough relative to the honest chain's length advantage, `preferAnchoredCandidate` returns `ShouldSwitch` and the node adopts the adversary's chain.
4. This constitutes a **chain selection safety failure**: an honest node is made to prefer a non-canonical chain solely through a crafted network message, with no stake majority or key compromise required.

This matches the **High** allowed impact: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."* It also qualifies as **Critical** under *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

- Peras is currently disabled by default, but the code path is fully compiled and wired into the production node binary; enabling Peras activates the vulnerability immediately.
- No special privileges, keys, or stake are required — any connected peer can send a `PerasCert` object via the object-diffusion mini-protocol.
- The crafted certificate only needs to reference a block hash already present in the target node's `VolatileDB`; the adversary can learn these hashes via the standard `ChainSync` protocol.
- The `processCerts` function disconnects the peer only if validation *fails*; since validation always succeeds, the adversary is never disconnected and can repeat the attack.

---

### Recommendation

1. **Implement real `validatePerasCert` logic** for each concrete block type (Cardano/Shelley) before enabling Peras in production. At minimum, verify: (a) the certificate's round number is plausible, (b) the aggregate BLS signature over `(roundNo, boostedBlock)` is valid against the committee's aggregate public key, and (c) the voter set meets the quorum threshold. The `implVerifyCert` functions in `WFALS.hs` and `EveryoneVotes.hs` already implement this logic for the committee layer and should be plumbed through.
2. **Remove or gate the degenerate catch-all instance** so that any block type without a real implementation fails to compile rather than silently accepting all certificates.
3. **Add a guard in `processCerts`** that rejects certificates whose `pcCertBoostedBlock` slot is not within the current volatile window, as an additional defense-in-depth measure.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
