## Exact Code Path

**`cancel_withdraw`** in `bridge.rs` (lines 285–299) is operator-gated, but internally calls `require_pending_sign_capacity` on the **user's** account ID — not the operator's: [1](#0-0) 

**`require_pending_sign_capacity`** in `account.rs` panics if `pending_sign_count() >= get_max_pending_sign_txs()`. The default max is **1**: [2](#0-1) 

**`cancel_withdraw_chain_specific`** (via the `define_rbf_method!` macro) inserts a **new** entry into `btc_pending_sign_ids` after `internal_cancel_withdraw` returns — this is why the capacity check exists: [3](#0-2) 

**`do_cancel`** does **not** remove the original tx from `btc_pending_sign_ids` — it only updates state fields: [4](#0-3)

## Concrete Attack Sequence

`cancel_withdraw` requires the original tx to be in `PendingVerify` stage (signed and broadcast to Bitcoin). At that point, the original tx has already been moved out of `btc_pending_sign_ids` into `btc_pending_verify_list`. This means `pending_sign_count` drops back to 0, and the user can immediately initiate a **second** withdrawal via `ft_on_transfer`, which inserts a new entry into `btc_pending_sign_ids` (count = 1 = max).

Now when the operator calls `cancel_withdraw` on the stuck first withdrawal:

1. `require_pending_sign_capacity(&user_account_id)` checks `1 < 1` → **false** → panics with `"Too many pending sign transactions"`
2. The cancel is permanently blocked as long as the user keeps a pending sign tx alive.

The user can sustain this indefinitely by cycling new withdrawals through `ft_on_transfer` before each operator cancel attempt. The `create_btc_pending_info` guard only checks `pending_sign_count() < max_pending`: [5](#0-4)

## Assessment

### Title
Operator `cancel_withdraw` permanently blocked by user-controlled `pending_sign_count` — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` calls `require_pending_sign_capacity` on the **victim user's** account before creating the cancel-RBF pending info. A user can keep their `pending_sign_count` at the per-account maximum (default: 1) by maintaining a live pending-sign withdrawal, causing every operator cancel attempt to panic and revert.

### Finding Description
The `cancel_withdraw` function (bridge.rs:291) checks whether the user's account has room for one more pending-sign entry before creating the cancel-RBF transaction. However, the user can trivially fill that slot by initiating a new withdrawal via `ft_on_transfer` after their first withdrawal advances to `PendingVerify` (freeing the slot). The operator's call then hits `require_pending_sign_capacity` with `count == max`, which panics unconditionally. `do_cancel` never removes the original entry from `btc_pending_sign_ids`, so there is no race-free window for the operator.

### Impact Explanation
The operator cannot cancel a stuck withdrawal. The BTC UTXOs locked in the original pending transaction remain inaccessible, and the user's nBTC (already transferred to the bridge) cannot be refunded via the cancel path. This constitutes attacker-triggered locking of bridged funds requiring operator intervention that is structurally impossible to complete.

### Likelihood Explanation
The attack requires only a standard `ft_on_transfer` Withdraw call — a fully public, unprivileged entry point. The user needs no special role, no leaked key, and no external dependency. The timing window (between the original tx reaching `PendingVerify` and the operator's cancel attempt) is wide because the operator cancel is only allowed after `max_btc_tx_pending_sec` has elapsed.

### Recommendation
Remove the `require_pending_sign_capacity` check from `cancel_withdraw` (and `cancel_active_utxo_management`). The capacity guard is appropriate for user-initiated actions but must not gate privileged operator/DAO cancellation paths. The cancel-RBF pending info should be inserted unconditionally (or the original entry should be atomically removed from `btc_pending_sign_ids` before the capacity check).

### Proof of Concept
```
1. User calls ft_on_transfer(Withdraw{...}) → withdraw #1 enters PendingSign, btc_pending_sign_ids = {id1}
2. Relayer signs withdraw #1 → moves to PendingVerify, btc_pending_sign_ids = {} (slot freed)
3. User calls ft_on_transfer(Withdraw{...}) → withdraw #2 enters PendingSign, btc_pending_sign_ids = {id2}, count = 1 = max
4. After max_btc_tx_pending_sec, Operator calls cancel_withdraw(id1, output)
5. require_pending_sign_capacity(&user) checks 1 < 1 → false → panic("Too many pending sign transactions")
6. Repeat step 3 before each operator retry → cancel is permanently blocked
```
