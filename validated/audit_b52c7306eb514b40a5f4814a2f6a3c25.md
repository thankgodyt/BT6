Audit Report

## Title
3-arg `mint` in `HyperliquedBridgeToken` Silently Redirects All Bridged Tokens to `_systemAddress` on NEAR→HyperEVM Finalization with Non-Empty Message — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`OmniBridge.finTransfer` dispatches to the 3-arg `mint(address, uint256, bytes)` whenever `payload.message.length > 0` and the token is registered as a bridge token. `HyperliquedBridgeToken` overrides this function to call `_mint(account, value)` immediately followed by `_update(account, _systemAddress, value)`, producing a net balance change of zero for the declared recipient. All minted tokens land at `_systemAddress`. The nonce is consumed before the mint call, NEAR has already locked/burned the origin tokens, and no refund path exists — resulting in permanent, irrecoverable loss of the full bridged amount.

## Finding Description

**Root cause — dispatch logic in `OmniBridge.finTransfer`:**

When `isBridgeToken[payload.tokenAddress]` is true, the contract selects the mint overload purely on message length: [1](#0-0) 

The `payload.message` field is a user-controlled string included in the MPC-signed payload. A non-empty value (any memo, routing hint, or application-layer tag) routes execution to the 3-arg overload.

**`HyperliquedBridgeToken` 3-arg mint — destructive accounting:** [2](#0-1) 

`_mint(account, value)` increases `account`'s balance by `value`. The immediately following `_update(account, _systemAddress, value)` transfers that entire balance to `_systemAddress`. Net effect for `account`: **+value − value = 0**. `_systemAddress` receives the full amount.

**Base `BridgeToken` 3-arg mint (safe, not overridden correctly):** [3](#0-2) 

The base implementation simply mints to the recipient without any subsequent transfer. `HyperliquedBridgeToken` overrides this with the HyperCore pool-parking logic, which is semantically correct only when called from `coreReceiveWithData`, not from `finTransfer`.

**Nonce consumed before mint:** [4](#0-3) 

`completedTransfers[payload.destinationNonce]` is set to `true` before the mint call. The transfer cannot be re-finalized regardless of outcome.

**Design intent vs. actual dispatch:**

The NatSpec comment at lines 29–31 of `HlBridgeToken.sol` documents that the 3-arg mint is intended exclusively for the HyperCore accounting model — tokens minted to HyperCore are parked at `_systemAddress` to mirror the HyperCore-side balance: [5](#0-4) 

`OmniBridge.finTransfer` has no awareness of this semantic distinction. It selects the 3-arg path purely on `payload.message.length > 0`, which is a user-controlled field in any NEAR→HyperEVM transfer. A regular HyperEVM recipient with a non-empty `msg` field triggers the HyperCore accounting path, which is semantically wrong and financially destructive.

**`IBridgeToken` confirms the 3-arg overload is part of the interface:** [6](#0-5) 

`OmniBridge` legitimately calls it through the interface — no interface bypass or signature forgery is required.

## Impact Explanation

This is a **Critical** impact matching "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM." Concretely:

- `balanceOf(recipient)` = 0 after finalization despite being the declared beneficiary.
- `balanceOf(_systemAddress)` increases by the full bridged amount.
- `completedTransfers[destinationNonce]` = `true` — the nonce is consumed; no re-finalization is possible.
- NEAR has already locked/burned the origin tokens. No refund mechanism exists in any of the contracts.
- Full, permanent loss of bridged funds for every NEAR→HyperEVM transfer that includes a non-empty `message` field targeting an `HyperliquedBridgeToken`.

## Likelihood Explanation

- The `message` field is a standard, documented field in the NEAR bridge transfer flow, used for memos, routing hints, and application-layer tags.
- No special attacker capability is required. A legitimate user attaching any non-empty string to a NEAR→HyperEVM transfer triggers this path accidentally.
- The MPC signature covers the full payload including `message`; the signature is valid and no bypass is needed.
- The relayer submits the finalization in the normal flow.
- The condition is trivially satisfiable and repeatable across any number of transfers.

## Recommendation

The 3-arg `mint` in `HyperliquedBridgeToken` must not redirect tokens to `_systemAddress` when called from `OmniBridge.finTransfer`. Two concrete fixes:

1. **Override `mint(address, uint256, bytes)` in `HyperliquedBridgeToken` to behave identically to the 2-arg version** — i.e., call only `_mint(account, value)` without the subsequent `_update`. The HyperCore pool-parking logic belongs exclusively in `coreReceiveWithData`, not in the NEAR→EVM finalization path.

2. **Alternatively**, remove the `message`-based dispatch from `OmniBridge.finTransfer` for `HyperliquedBridgeToken` tokens, or add a token-type check (e.g., via an interface flag) so that HyperLiquid tokens always use the 2-arg mint during `finTransfer` regardless of message content.

## Proof of Concept

```solidity
// 1. Deploy HyperliquedBridgeToken registered as isBridgeToken in OmniBridge.
// 2. NEAR user initiates transfer to freshEOA with msg = "hello" (non-empty).
// 3. MPC signs the payload (legitimate signature, message field included).
// 4. Relayer calls OmniBridge.finTransfer(sig, payload) where payload.message = "hello".
// 5. completedTransfers[nonce] = true (line 287, before mint).
// 6. OmniBridge enters isBridgeToken branch, message.length > 0 → calls 3-arg mint.
// 7. HyperliquedBridgeToken.mint(freshEOA, amount, "hello"):
//      _mint(freshEOA, amount)              → freshEOA.balance = amount
//      _update(freshEOA, _systemAddress, amount) → freshEOA.balance = 0
// Assert: token.balanceOf(freshEOA) == 0                ✓
// Assert: token.balanceOf(_systemAddress) == amount      ✓
// Assert: completedTransfers[nonce] == true              ✓ (no re-finalization possible)
// NEAR transfer marked complete; funds permanently lost to _systemAddress.
```

A minimal Foundry unit test can reproduce this by deploying `HyperliquedBridgeToken`, registering it in `OmniBridge`, constructing a valid signed payload with a non-empty `message`, calling `finTransfer`, and asserting `balanceOf(recipient) == 0` and `balanceOf(_systemAddress) == amount`.
