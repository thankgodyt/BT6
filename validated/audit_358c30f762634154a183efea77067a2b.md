### Title
Unprivileged Caller Can Hijack Any Refund Execution, Locking Bridged Funds — (`contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`execute_refund` is callable by any unprivileged NEAR account for any pending refund request. It associates the resulting `BTCPendingInfo` with `env::predecessor_account_id()` (the caller), not with the original depositor. Because the PSBT is deterministic, a second call for the same UTXO always collides on the same `btc_pending_id` and panics with "pending info already exist." An attacker who races to call `execute_refund` first permanently blocks the legitimate depositor from managing their own refund, locking the bridged funds until DAO intervention.

### Finding Description
`execute_refund` in `api/bridge.rs` performs no check that `env::predecessor_account_id()` has any relationship to the refund request:

```rust
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

`resolve_execute_refund_timelock` only checks whether the caller is privileged (to decide the timelock duration); it does not restrict who may call `execute_refund` at all: [2](#0-1) 

Inside `finalize_refund_with_psbt`, the `BTCPendingInfo` is stamped with `account_id: caller.clone()` — whoever called `execute_refund`:

```rust
let btc_pending_info = BTCPendingInfo {
    account_id: caller.clone(),
    ...
};
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
self.internal_unwrap_mut_account(&caller)
    .btc_pending_sign_ids
    .insert(btc_pending_id.clone());
``` [3](#0-2) 

Because the PSBT is built deterministically from the same UTXO inputs and outputs, the `btc_pending_id` is identical for every caller. Once the attacker's call inserts the record, any subsequent call by the legitimate depositor panics on the `is_none()` guard. The attacker now owns the `BTCPendingInfo` and controls (or withholds) the signing step, while the original depositor is permanently locked out of managing their own refund.

### Impact Explanation
The depositor's BTC is locked in the bridge's MPC-controlled UTXO. The legitimate user cannot re-execute the refund (collision on `btc_pending_id`). If the attacker simply does not sign, the refund transaction is never broadcast and the funds remain stuck. Recovery requires DAO/Operator to reject the refund request and clean up the orphaned `BTCPendingInfo`, constituting mandatory operator intervention for every such attack. This matches **Medium — attacker-triggered temporary locking of bridged funds**.

### Likelihood Explanation
- `execute_refund` is explicitly documented as callable by anyone after the timelock.
- The timelock and UTXO key are observable on-chain; an attacker can front-run or simply call first.
- No special knowledge, tokens, or privileges are required — only a NEAR account and the `utxo_storage_key`.
- The attack is cheap (only the attached storage deposit is required).

### Recommendation
Record the original requester's NEAR account ID in `RefundRequest` at `request_refund` time. In `execute_refund`, require that `env::predecessor_account_id()` equals the stored requester, or is a privileged role (DAO / RefundOperator). This mirrors the pattern already used in `reject_refund`, which gates non-privileged callers to a specific condition.

### Proof of Concept

1. Alice calls `request_refund` for her unfinalized deposit; `RefundRequest` is stored with `refund_address = alice_btc_addr`.
2. The timelock elapses (publicly observable via block timestamp).
3. Attacker calls `execute_refund(alice_utxo_key, None)` before Alice does.
4. `finalize_refund_with_psbt` runs with `caller = attacker`; `BTCPendingInfo { account_id: attacker, ... }` is inserted under `btc_pending_id`.
5. Alice calls `execute_refund(alice_utxo_key, None)` — the PSBT is identical, `btc_pending_id` collides, and the call panics: **"pending info already exist"**.
6. Attacker never calls `sign_btc_transaction`; Alice's BTC remains locked in the bridge UTXO.
7. DAO must call `reject_refund` and remove the orphaned pending info before Alice can retry. [4](#0-3) [5](#0-4)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
