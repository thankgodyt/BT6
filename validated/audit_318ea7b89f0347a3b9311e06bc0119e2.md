### Title
`verify_withdraw_v2` / `verify_refund_finalize` use `btc_pending_sign_id` as both the on-chain storage key and the Bitcoin txid submitted to the light client — these are structurally different values, making withdrawal finalization permanently impossible — (`contracts/satoshi-bridge/src/chain_signature.rs`, `btc_light_client/withdraw.rs`, `refund.rs`)

---

### Summary

`Event::SignedBtcTransaction` emits `tx_id = btc_pending_sign_id`, which is the SHA-256 of concatenated PSBT sighash preimages. The same string is used as the storage key for `BTCPendingInfo`. When the trusted relayer calls `verify_withdraw_v2(tx_id, proof)` or `verify_refund_finalize(tx_id, proof)`, the contract passes that same `tx_id` directly to the Bitcoin light client as the Bitcoin transaction ID. Because `btc_pending_sign_id` is not the Bitcoin txid (double-SHA-256 of the serialized transaction), the light client Merkle-inclusion check will always fail. No withdrawal or refund can ever be finalized; user nBTC is permanently locked inside the bridge.

---

### Finding Description

**How `btc_pending_sign_id` is computed** [1](#0-0) 

`generate_btc_pending_sign_id` hashes the concatenated PSBT sighash preimages with a single SHA-256. This value is used as the map key in `btc_pending_infos` and is the only identifier the contract stores for a pending withdrawal.

**What the event emits** [2](#0-1) 

When all inputs are signed, `sign_btc_transaction_callback` emits `Event::SignedBtcTransaction` with `tx_id: btc_pending_sign_id.clone()`. The actual signed transaction bytes are present in `tx_bytes`, but the `tx_id` field is the preimage-hash identifier, not the Bitcoin txid.

**How `verify_withdraw_v2` uses `tx_id`** [3](#0-2) 

The relayer passes `tx_id` to `internal_verify_withdraw_entry`. [4](#0-3) 

`internal_verify_withdraw_entry` uses `tx_id` as the storage key (`internal_unwrap_btc_pending_info(&tx_id)`, line 45) **and** forwards the same string to `internal_verify_withdraw`, which passes it verbatim to `verify_transaction_inclusion_promise` as the Bitcoin txid.

**How the light client receives it** [5](#0-4) 

`ProofArgs::new` parses `tx_id` as a 32-byte hex string (with byte-reversal for endianness) and submits it to `verify_transaction_inclusion`. A correct Bitcoin light client checks that this value is the leaf of the Merkle tree in the given block. `btc_pending_sign_id` (SHA-256 of preimages) is never the leaf — the actual Bitcoin txid (double-SHA-256 of the serialized transaction) is.

**The same flaw in `verify_refund_finalize`** [6](#0-5) 

`internal_verify_refund_finalize` passes `tx_id` (= `btc_pending_sign_id`) directly to `verify_transaction_inclusion_promise`, producing the identical failure for refund transactions.

**The irresolvable conflict**

The `tx_id` parameter in both public endpoints must simultaneously satisfy two incompatible requirements:

| Requirement | Required value |
|---|---|
| Storage lookup (`internal_unwrap_btc_pending_info`) | `btc_pending_sign_id` (SHA-256 of preimages) |
| Light-client Merkle proof | Actual Bitcoin txid (double-SHA-256 of serialized tx) |

There is no single string that satisfies both. Passing `btc_pending_sign_id` → storage lookup succeeds, light client rejects. Passing the actual Bitcoin txid → storage lookup panics with "BTC pending info not exist".

---

### Impact Explanation

Every withdrawal and refund that reaches `PendingVerify` state is permanently stuck. The nBTC transferred by the user in `ft_on_transfer` is held by the bridge contract (the burn in `verify_withdraw_burn_promise` only executes after successful light-client verification, which never occurs). There is no on-chain path to recover the locked nBTC: `cancel_withdraw` creates an RBF transaction that goes through the same broken signing and verification pipeline.

This constitutes **permanent locking of user funds** across all withdrawals and refunds.

---

### Likelihood Explanation

The flaw is structural and deterministic — it affects every withdrawal and refund without exception. Any user who initiates a withdrawal via the public `ft_on_transfer` entry point triggers the broken pipeline. No special attacker action is required; the design itself prevents finalization.

---

### Recommendation

Separate the two identifiers. Store a mapping from `btc_pending_sign_id` → actual Bitcoin txid once the signed transaction bytes are available (computable from `tx_bytes_with_sign` via double-SHA-256 and byte-reversal). Expose the actual Bitcoin txid in `Event::SignedBtcTransaction` as a distinct field (e.g., `btc_txid`). Change `verify_withdraw_v2` and `verify_refund_finalize` to accept both a `pending_id: String` (for storage lookup) and a `tx_id: String` (for light-client verification), or derive the Bitcoin txid internally from the stored `tx_bytes_with_sign` rather than trusting the caller-supplied value.

---

### Proof of Concept

```
1. User calls ft_on_transfer(amount, withdraw_msg) → bridge holds nBTC,
   creates BTCPendingInfo keyed by btc_pending_sign_id = SHA256(preimages).

2. Relayer calls sign_btc_transaction → chain signatures sign each input.

3. sign_btc_transaction_callback fires:
   - tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign()
   - actual_btc_txid    = double_sha256(tx_bytes_with_sign).reverse()  // e.g. "aabbcc..."
   - btc_pending_sign_id = sha256(preimages)                           // e.g. "112233..."
   - Event::SignedBtcTransaction { tx_id: "112233...", tx_bytes: [...] } emitted
   - State → PendingVerify

4. Relayer broadcasts tx_bytes to Bitcoin; tx confirms with actual txid "aabbcc...".

5. Relayer calls verify_withdraw_v2(tx_id="112233...", proof={...merkle proof for "aabbcc..."...})
   → internal_unwrap_btc_pending_info("112233...") → OK (found)
   → verify_transaction_inclusion(tx_id=H256("112233..."), merkle_proof=[...])
   → light client checks: is "112233..." the Merkle leaf? NO → returns false
   → internal_verify_withdraw_callback panics: "verify_transaction_inclusion return false"
   → state remains PendingVerify, nBTC permanently locked.

6. Relayer tries verify_withdraw_v2(tx_id="aabbcc...", proof={...})
   → internal_unwrap_btc_pending_info("aabbcc...") → PANIC "BTC pending info not exist"

No valid tx_id exists that satisfies both lookups simultaneously.
```

pub fn generate_btc_pending_sign_id(payload_preimages: &[Vec<u8>]) -> String {
    let hash_bytes = env::sha256_array(
        payload_preimages
            .iter()
            .flatten()
            .copied()
            .collect::<Vec<u8>>(),
    );
    hex::encode(hash_bytes)
}

    pub fn new(

            confirmations,
        }

    pub(crate) fn internal_verify_refund_finalize(
        &self,
        tx_id: String,
        proof: TxInclusionProof,
        btc_pending_info: &BTCPendingInfo,
    ) -> Promise {
        let config = self.internal_config();
        let confirmations = self.get_confirmations(config, btc_pending_info.actual_received_amount);
        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id.clone(),
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_VERIFY_REFUND_CALLBACK)
                .verify_refund_finalize_callback(tx_id),
        )
    }
