### Title
Oversized `tx_bytes` in Safe-Deposit Path Permanently Locks Bridge BTC via Zeroed UTXO Storage - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the submitted `tx_bytes` exceed 10,000 bytes, the code silently replaces them with 300 zero bytes **after** the transaction has already been decoded and verified. The resulting UTXO — containing `tx_bytes = vec![0u8; 300]` — is stored permanently in the bridge's UTXO set. Because the bridge later decodes these stored bytes to construct withdrawal PSBTs, any UTXO stored this way can never be spent. The BTC is permanently locked at the bridge's on-chain address while the corresponding nBTC has already been minted and is freely circulating.

---

### Finding Description

In `internal_safe_verify_deposit_entry`, the transaction is decoded and fully validated from the original `tx_bytes` at lines 191–202. Then, at lines 204–209, a silent truncation occurs:

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]
} else {
    tx_bytes
};
``` [1](#0-0) 

The `UTXO` struct is then constructed using this zeroed `tx_bytes` while `balance` is taken from the already-decoded (correct) transaction:

```rust
let utxo = UTXO {
    path,
    tx_bytes,   // ← 300 zero bytes
    vout,
    balance: transaction.output()[vout].value.to_sat(),  // ← correct
};
``` [2](#0-1) 

On a successful `safe_mint`, `safe_mint_callback` calls `internal_set_utxo` with this corrupted UTXO:

```rust
self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
``` [3](#0-2) 

The UTXO is now permanently recorded in `verified_deposit_utxo` and the bridge's UTXO set with `tx_bytes = [0u8; 300]`. When the bridge later attempts to build a withdrawal PSBT using this UTXO as an input, it must decode `tx_bytes` to obtain the previous output's script and value. Decoding 300 zero bytes as a Bitcoin transaction will fail, making the UTXO permanently unspendable.

The `request_refund` path does **not** rescue this situation: refunds require a separate `request_refund` call with the original `tx_bytes`, but the UTXO is already in `verified_deposit_utxo`, so `request_refund_callback` will reject it:

```rust
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
``` [4](#0-3) 

---

### Impact Explanation

The bridge mints nBTC backed by BTC it can never spend. The affected UTXO's BTC is permanently locked at the bridge's on-chain Bitcoin address with no recovery path. As more such UTXOs accumulate, the bridge becomes progressively undercollateralized: outstanding nBTC exceeds the BTC the bridge can actually redeem. This matches **Critical — significant permanent locking of protocol funds**.

---

### Likelihood Explanation

A Bitcoin transaction with more than ~45 P2PKH inputs, or any moderately complex multi-input SegWit transaction, can exceed 10,000 bytes. A user who wants to consolidate many small UTXOs into a single bridge deposit — a realistic and common pattern — can easily produce such a transaction. The trusted relayer has no reason to reject it; it is a valid on-chain transaction. The relayer submits it via `verify_deposit_v2` with `safe_deposit = Some(..)`, and the truncation fires automatically. No special privileges are required beyond controlling the BTC transaction being deposited.

---

### Recommendation

Remove the truncation entirely. The 10,000-byte guard was added to avoid gas overruns in the 20 Tgas `request_refund_callback`, but `internal_safe_verify_deposit_entry` is a different code path with a 130 Tgas callback budget. If a size cap is still desired for storage cost reasons, **reject** oversized transactions with a hard `require!` rather than silently corrupting the stored bytes:

```rust
require!(
    tx_bytes.len() <= MAX_REQUEST_REFUND_TX_BYTES,
    "tx_bytes too large"
);
```

This mirrors the guard already present in `internal_request_refund`. [5](#0-4) 

---

### Proof of Concept

1. Construct a Bitcoin transaction with ~50 P2PKH inputs sending funds to the user's bridge deposit address. Raw `tx_bytes` will exceed 10,000 bytes.
2. Wait for the transaction to confirm with the required number of confirmations.
3. A trusted relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)` and the large `tx_bytes`.
4. `internal_safe_verify_deposit_entry` decodes the transaction correctly, verifies the output script, then replaces `tx_bytes` with `vec![0u8; 300]`.
5. The light client confirms inclusion; `verify_safe_deposit_callback` inserts the UTXO key into `verified_deposit_utxo` and calls `safe_mint`.
6. `safe_mint_callback` succeeds; `internal_set_utxo` stores the UTXO with zeroed `tx_bytes`. nBTC is minted to the recipient.
7. Any subsequent withdrawal attempt that selects this UTXO as an input will call `WrappedTransaction::decode(&utxo.tx_bytes, ...)` on 300 zero bytes, which panics or returns an error, making the UTXO permanently unspendable.
8. The bridge holds BTC it cannot access while the corresponding nBTC circulates freely, permanently reducing the bridge's redeemable collateral. [6](#0-5)
