### Title
Peras Certificate Validation Stub Always Accepts Any Peer-Supplied Certificate, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function is an unimplemented stub that unconditionally returns `Right` for every certificate, regardless of content. This stub is wired directly into the live node-to-node Peras certificate diffusion mini-protocol. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary boosted block point; the certificate will pass "validation," be stored in the `PerasCertDB`, and its fabricated weight boost will be applied during chain selection, potentially causing an honest node to prefer a non-canonical adversarial chain.

---

### Finding Description

**Root cause — stub validation always succeeds:**

The universal `BlockSupportsPeras` instance (covering all `StandardHash blk`) implements `validatePerasCert` as a no-op that wraps any input certificate in `Right ValidatedPerasCert` without performing any cryptographic or structural check:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The `BlockSupportsPeras` class declares `validatePerasCert` as the mandatory gate for accepting a `PerasCert` into the system: [2](#0-1) 

**Production wiring — stub used in the live network path:**

`makePerasCertPoolWriterFromChainDB` is the production inbound handler for Peras certificates received from peers. It passes `validatePerasCert mkPerasParams` as the validator to `processCerts`: [3](#0-2) 

`processCerts` calls `validateCert` on each inbound certificate and rejects the batch if any returns `Left`. Since the stub always returns `Right`, no certificate is ever rejected: [4](#0-3) 

This writer is registered as the live `hPerasCertDiffusionClient` handler in the node-to-node protocol stack: [5](#0-4) 

**Chain selection impact — fabricated boost applied:**

Once accepted, the certificate is stored in `PerasCertDB` and its `pcCertBoostedBlock` point is included in the `PerasWeightSnapshot` returned by `implGetWeightSnapshot`: [6](#0-5) 

The `PerasWeightSnapshot` is consumed by `getCandidateOverSelection` in `NodeKernel` during chain selection comparisons: [7](#0-6) 

`totalWeightOfFragment` adds the Peras boost on top of chain length, so a shorter adversarial fork whose tip has been "boosted" by a fabricated certificate can appear heavier than the honest chain: [8](#0-7) 

The `chainSelSync` path in `ChainSel` also triggers chain selection for the boosted block immediately upon certificate receipt: [9](#0-8) 

---

### Impact Explanation

**Impact: High** — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

A peer can craft a `PerasCert` naming any block point as the "boosted" block. Because `validatePerasCert` never checks committee membership, aggregate BLS signatures, VRF eligibility, or any other Peras-protocol invariant, the certificate is accepted unconditionally. The fabricated weight boost is then applied during chain selection. If the adversary's fork has a block that accumulates enough fabricated boost weight to exceed the honest chain's `totalWeightOfFragment`, the node will switch to the adversarial fork. This violates the Peras chain-selection security property that only legitimately certified blocks should receive weight boosts.

---

### Likelihood Explanation

**Likelihood: High** — The vulnerability is reachable by any peer that can establish a node-to-node connection. No credentials, stake, or special privileges are required. The Peras certificate diffusion mini-protocol is active on all nodes that have the Peras feature enabled. The attacker only needs to send a well-formed `PerasCert` message (a round number and a block point), which is trivially constructable from the public wire format. The stub is the only validation gate; there is no secondary check downstream.

---

### Recommendation

Implement the actual `validatePerasCert` logic in the `BlockSupportsPeras` instance (or in the Cardano-specific instance once the HFC plumbing referenced in issue #73 is in place). The implementation must verify:

1. The certificate's claimed committee membership against the on-chain stake distribution for the relevant Peras round.
2. The aggregate BLS/vote signature over the election ID and candidate block.
3. VRF eligibility proofs for non-persistent committee members (as implemented in `implVerifyCert` in `WFALS.hs`).
4. That the boosted block point corresponds to a block that actually exists on a known chain.

Until the full implementation is available, the `processCerts` inbound handler should refuse all inbound certificates rather than silently accepting them with a stub validator, to prevent the fabricated-boost attack surface from being live.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Establish a node-to-node connection to an honest Cardano node running with Peras enabled.
2. Initiate the Peras certificate diffusion mini-protocol (`hPerasCertDiffusionClient`).
3. Send a `PerasCert` message with:
   - `pcCertRound`: any `PerasRoundNo` not already in the node's `PerasCertDB`.
   - `pcCertBoostedBlock`: the `Point` of a block on an adversarial fork that the attacker wants the victim to prefer.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}` unconditionally. [10](#0-9) 
5. The certificate is stored in `PerasCertDB` and `chainSelSync` triggers chain selection for the boosted block.
6. `totalWeightOfFragment` now returns a higher weight for any fragment containing the adversarially boosted block, causing the node to prefer the adversarial fork if its boosted weight exceeds the honest chain's length. [11](#0-10)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
