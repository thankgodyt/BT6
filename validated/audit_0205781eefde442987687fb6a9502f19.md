### Title
Independent `post_action_receiver_id_white_list` and `post_action_msg_templates` Checks Allow Arbitrary Messages to Whitelisted Receivers — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

`check_deposit_msg()` validates `post_action` entries using two **independent** whitelists: `post_action_receiver_id_white_list` (which contracts may receive nBTC) and `post_action_msg_templates` (which messages are permitted per contract). A receiver can be added to the first whitelist with **no corresponding entry** in the second, causing message validation to be silently skipped. Any arbitrary `msg` is then accepted for that receiver, bypassing the intended message-level access control — a direct structural analog to the independent `callTo`/`approveTo`/`signature` checks described in the reference report.

---

### Finding Description

In `check_deposit_msg()`, the validation logic is:

1. Reject if `receiver_id` is not in `post_action_receiver_id_white_list`.
2. **Only if** `post_action_msg_templates` contains an entry for that `receiver_id`, validate `msg` against the stored templates. [1](#0-0) 

The critical branch is:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // msg is validated here
}
// if no templates exist, this block is entirely skipped — any msg passes
```

The two whitelists are managed by **separate, independent DAO operations**:

- `extend_post_action_receiver_id_white_list` — adds a receiver
- `extend_post_action_msg_templates` — adds message templates for a receiver [2](#0-1) 

There is no enforcement that templates must exist before a receiver is whitelisted, and no atomicity between the two operations. A receiver added to the first list without a corresponding entry in the second list receives **zero message-level restriction** — any `msg` string passes validation.

The `post_action_receiver_id_white_list` and `post_action_msg_templates` are stored as separate, unlinked data structures in `ContractData`: [3](#0-2) 

---

### Impact Explanation

When a whitelisted receiver has no registered templates, an attacker can embed any arbitrary `msg` in a `PostAction` targeting that receiver. After the bridge mints nBTC, it calls `ft_transfer_call` on the nBTC token contract, forwarding the attacker-controlled `msg` to the receiver's `ft_on_transfer` handler.

If the whitelisted receiver is a DeFi protocol (e.g., a lending or yield protocol) whose `ft_on_transfer` interprets `msg` to determine the beneficiary account, collateral target, pool, or action type, the attacker can:

- Deposit nBTC as collateral into another user's lending position, altering their health factor or liquidation threshold.
- Trigger protocol-level actions (e.g., repay, stake, route) on behalf of an arbitrary account.
- Cause the receiver contract to enter an unexpected state that harms other users.

The attacker can only redirect their **own** minted nBTC (bounded by `total_amount > actual_mintable_amount`), so direct theft of other users' bridge funds is not possible. However, the ability to invoke arbitrary cross-contract calls with attacker-controlled payloads against whitelisted DeFi contracts constitutes a bypass of the bridge's message-level access control policy, with potential for harmful downstream effects on other users of those contracts.

This matches the **Medium** impact class: *bypass of bridge limits or policies* and *harmful smart-contract behavior without direct funds theft*.

---

### Likelihood Explanation

The DAO controls both whitelists independently. There is no code-level guard preventing a receiver from being added to `post_action_receiver_id_white_list` without a corresponding `post_action_msg_templates` entry. This gap can arise from:

- Operational oversight (DAO adds a receiver but forgets to add templates).
- Intentional permissiveness (DAO trusts a receiver to handle any message), which still exposes the bridge to attacker-crafted payloads.

Once any such receiver exists on mainnet, any user can exploit the gap by constructing a `DepositMsg` with a crafted `post_action.msg` — no privileged access is required beyond sending BTC to the derived deposit address.

---

### Recommendation

Enforce that `post_action_msg_templates` must contain at least one template for a `receiver_id` before it can be added to `post_action_receiver_id_white_list`. Alternatively, treat the absence of templates as an **implicit deny-all** for `msg` (i.e., only allow an empty string `""` when no templates are registered), or require both operations to be performed atomically in a single DAO call that accepts `(receiver_id, templates)` as a pair.

The analog fix from the reference report applies directly: whitelist the `(receiver_id, msg_template)` pair as a unit, not as two independent sets.

---

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["lending.near"])` — adds `lending.near` as a permitted receiver.
2. DAO does **not** call `extend_post_action_msg_templates` for `lending.near` (oversight or intentional).
3. Attacker constructs:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "lending.near",
       "amount": "100000",
       "msg": "{\"action\":\"supply_collateral\",\"account_id\":\"victim.near\"}",
       "gas": "50000000000000"
     }]
   }
   ```
4. Attacker sends BTC to the deposit address derived from this `DepositMsg`.
5. Relayer calls `verify_deposit_v2` with a valid SPV proof.
6. `check_deposit_msg()` passes: `lending.near` is in `post_action_receiver_id_white_list`; the `if let Some(msg_templates)` branch is **not entered** because no templates exist; the arbitrary `msg` is accepted. [4](#0-3) 

7. Bridge mints nBTC to `attacker.near`, then calls `ft_transfer_call` on nBTC with the crafted `msg`.
8. `lending.near`'s `ft_on_transfer` receives the attacker-controlled payload and acts on `victim.near`'s account.

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn extend_post_action_receiver_id_white_list(&mut self, receiver_ids: Vec<AccountId>) {
        assert_one_yocto();
        for receiver_id in receiver_ids {
            let is_success = self
                .data_mut()
                .post_action_receiver_id_white_list
                .insert(receiver_id.clone());
            require!(
                is_success,
                format!("Already exist receiver_id: {}", receiver_id)
            );
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn remove_post_action_receiver_id_white_list(&mut self, receiver_ids: Vec<AccountId>) {
        assert_one_yocto();
        for receiver_id in receiver_ids {
            let is_success = self
                .data_mut()
                .post_action_receiver_id_white_list
                .remove(&receiver_id);
            require!(is_success, format!("Invalid receiver_id: {}", receiver_id));
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn set_pending_tx_limit(&mut self, account_id: AccountId, max_pending: Option<u32>) {
        assert_one_yocto();
        if let Some(max_pending) = max_pending {
            require!(max_pending >= 1, "Invalid max_pending value");
            self.data_mut()
                .pending_tx_limits
                .insert(account_id, max_pending);
        } else {
            let prev = self.data_mut().pending_tx_limits.remove(&account_id);
            require!(
                prev.is_some(),
                format!("Invalid account_id: {}", account_id)
            );
        }
    }

    #[payable]
    #[access_control_any(roles(Role::DAO))]
    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
