### Title
`safe_mint` Mints nBTC to Bridge Before Checking Recipient Registration, Leaving Tokens Stranded on Early Return - (File: contracts/nbtc/src/lib.rs)

### Summary

The `safe_mint` function in the `nbtc` token contract calls `internal_deposit` to mint tokens into the bridge's own account **before** checking whether the intended recipient account is registered. If the recipient is not registered, the function returns `PromiseOrValue::Value(U128(0))` immediately without burning or transferring the already-minted tokens. This leaves the nBTC total supply permanently inflated by `amount` with the tokens stranded in the bridge's own nBTC balance, while the user's BTC deposit is locked in the bridge's Bitcoin address.

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes the following sequence:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // (1) mints to bridge

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // (2) early return, no burn
    }
    // (3) transfer to user — never reached when account unregistered
    ...
}
```

Step (1) calls `internal_deposit`, which increases both `self.bridge_id`'s nBTC balance and the global total supply by `amount`. This state change is committed immediately in the NEAR execution context. Step (2) then returns `U128(0)` without burning the minted tokens. The bridge's callback receives `U128(0)` and, per the documented safe-deposit semantics ("reverts the whole transaction if minting fails"), is expected to undo the deposit — but the nBTC tokens already minted to the bridge's own account in the nBTC contract are a separate contract's state and cannot be rolled back by the bridge's callback unless it explicitly issues a `burn` cross-contract call. No such burn call is issued by the bridge's callback in this path.

The analog to the MasterChef bug is direct: both are **supply/accounting failures at a boundary condition**. MasterChef returns early without updating `accConcurPerShare` when `block.number >= endBlock`; `safe_mint` returns early without burning minted tokens when the recipient account is unregistered. In both cases, the accounting variable (accumulated rewards / total supply) is left in an incorrect state after the early return.

### Impact Explanation

- The nBTC total supply is permanently increased by `amount` with no corresponding user holding those tokens.
- The bridge's own nBTC balance grows by `amount`, breaking the backed-supply invariant (more nBTC in circulation than BTC redeemable by users).
- The user's BTC deposit UTXO is marked as `verified_deposit_utxo` by the bridge's deposit callback, permanently blocking any subsequent `request_refund` for that UTXO.
- The user receives zero nBTC and cannot recover their BTC through the refund system.
- This constitutes permanent loss of user funds (BTC locked, nBTC not received) and a broken callback rollback.

**Matched allowed impact:** Critical — significant loss and permanent locking of user funds; and Medium — broken callback rollback / stuck bridge state requiring operator intervention.

### Likelihood Explanation

The trigger condition is straightforward and reachable by any unprivileged user: deposit BTC to the bridge's derived address without first registering a storage account in the nBTC token contract, then have a relayer submit `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`. The nBTC token contract requires explicit `storage_deposit` registration before an account can hold tokens; a new user who skips this step (or whose account was deregistered) will hit this path. The safe-deposit flow is the primary path used by integrations such as Omni Bridge, making this a realistic scenario.

### Recommendation

Move the recipient-registration check **before** calling `internal_deposit`, so that no tokens are minted if the recipient is unregistered:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer to user
}
```

Alternatively, if minting-then-checking is intentional, add an explicit `internal_withdraw` (burn) from `self.bridge_id` on the early-return path to restore the total supply invariant.

### Proof of Concept

1. User deposits 0.01 BTC to the bridge's derived P2WPKH address on Bitcoin mainnet.
2. User does **not** call `storage_deposit` on the nBTC contract for their NEAR account.
3. Relayer calls `verify_deposit_v2(deposit_msg { safe_deposit: Some(..) }, tx_bytes, vout, proof)` on the bridge.
4. Bridge verifies the Merkle proof via the light client, marks the UTXO in `verified_deposit_utxo`, and cross-contract calls `nbtc.safe_mint(user_account, 1_000_000, None)`.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 1_000_000)` executes — bridge's nBTC balance increases by 1,000,000 satoshis, total supply increases by 1,000,000.
6. `self.token.accounts.get(&user_account)` returns `None` → function returns `U128(0)`.
7. Bridge callback receives `U128(0)`. No burn is issued against the nBTC contract.
8. Result: 1,000,000 nBTC stranded in bridge's own nBTC balance; user's BTC UTXO permanently locked (blocked from `request_refund` by `verified_deposit_utxo` membership); user holds 0 nBTC. [1](#0-0) [2](#0-1) [3](#0-2)
