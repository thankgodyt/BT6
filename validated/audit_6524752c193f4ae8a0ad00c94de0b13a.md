Audit Report

## Title
`fin_transfer_send_tokens_callback` Silently Treats Failed Token Delivery as Success, Permanently Locking Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

When finalizing an inbound transfer to a NEAR recipient, the bridge permanently records the transfer as finalized in `finalised_transfers` before token delivery resolves. If the subsequent `ft_transfer` or `near_withdraw` call fails, `fin_transfer_send_tokens_callback` unconditionally treats the failure as success — emitting `FinTransferEvent`, paying the relayer fee, and leaving the bridged tokens permanently locked inside the contract with no recovery path.

## Finding Description

**Step 1 — Permanent replay-prevention entry written before delivery:**
`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, inserting the transfer ID into `finalised_transfers` via `require!(self.finalised_transfers.insert(...))`. Any subsequent call with the same transfer ID will panic with `TransferAlreadyFinalised`. [1](#0-0) [2](#0-1) 

**Step 2 — Token delivery dispatched, callback registered:**
`send_tokens` is called (line 1957) and chained with `.then(fin_transfer_send_tokens_callback(..., !msg.is_empty(), ...))`. For non-deployed tokens with an empty `msg`, `is_ft_transfer_call = false`; for wNEAR, also `false`. [3](#0-2) 

**Step 3 — Callback has no `#[callback_result]` parameter:**
`fin_transfer_send_tokens_callback` (line 1692–1699) accepts no result parameter and never calls `env::promise_result_checked` directly. It delegates entirely to `is_refund_required(is_ft_transfer_call)`. [4](#0-3) 

**Step 4 — `is_refund_required` unconditionally returns `false` for all non-`ft_transfer_call` paths:**
When `is_ft_transfer_call` is `false`, the function returns `false` without reading the promise result at all, regardless of whether the preceding promise succeeded or failed. [5](#0-4) 

**Step 5 — Success branch executes unconditionally:**
With `is_refund_required` returning `false`, the `else` branch runs: the relayer fee is paid and `FinTransferEvent` is emitted. `remove_fin_transfer` is never called, so the transfer ID stays permanently in `finalised_transfers`. [6](#0-5) 

**Affected delivery paths:**

- **`ft_transfer` (non-deployed token, empty msg):** If the token contract rejects the transfer (e.g., blacklisted recipient), the promise fails silently. [7](#0-6) 

- **`near_withdraw` (wNEAR):** If `near_withdraw` fails, `near_withdraw_callback` calls `env::panic_str` (line 1050), making the promise result for `fin_transfer_send_tokens_callback` an error — but `is_refund_required(false)` still returns `false`. [8](#0-7) 

**Note on `ft_transfer_call` path:** Even here, if the promise itself errors (token contract panics before returning), `is_refund_required` returns `false` (line 1797–1798), so the same silent-success behavior applies. [9](#0-8) 

## Impact Explanation

**Critical — Permanent freezing of bridged funds.** For any inbound transfer to a NEAR recipient where token delivery fails: the transfer ID is irrevocably inserted into `finalised_transfers` (blocking all replays), the bridged tokens remain in the bridge contract with no admin recovery function, and the relayer fee is paid despite the recipient receiving nothing. This matches the allowed impact: *permanent freezing of bridged funds across NEAR*.

## Likelihood Explanation

**Medium.** No privileged attacker access is required. Realistic triggers include:

- **USDC/USDT recipient blacklisting:** Circle and Tether can blacklist NEAR addresses. A transfer initiated on the source chain before blacklisting, finalized on NEAR after, will have its `ft_transfer` rejected — permanently locking funds.
- **Token contract global pause:** USDC, USDT, and other regulated tokens have pause mechanisms. Any in-flight transfer finalized during a pause window is permanently lost.
- **wNEAR contract failure:** Any failure in `near_withdraw` (contract paused, insufficient balance) causes `near_withdraw_callback` to panic, and the wNEAR is permanently locked.

All triggers are caused by external token contract behavior outside the bridge's control, and none require attacker privileges.

## Recommendation

1. Add a `#[callback_result] call_result: Result<(), near_sdk::PromiseError>` parameter to `fin_transfer_send_tokens_callback` to capture the promise outcome for all delivery paths.
2. Extend `is_refund_required` (or replace it) to return `true` whenever the promise result is `Err(_)`, regardless of `is_ft_transfer_call`.
3. In the refund/revert branch, call `remove_fin_transfer` to allow re-submission, or emit `FailedFinTransferEvent` and provide a retry mechanism.
4. Apply the same fix to `resolve_utxo_fin_transfer` (lines 1016–1044), which has the identical structural flaw: `is_refund_required(is_ft_transfer_call)` is called with no promise-error handling for the non-`ft_transfer_call` path. [10](#0-9) 

## Proof of Concept

**Scenario: USDC recipient is blacklisted**

1. User initiates transfer of 10,000 USDC from Ethereum to `alice.near` via the EVM bridge contract.
2. Circle blacklists `alice.near` on the NEAR USDC contract.
3. A relayer submits the proof to `fin_transfer` on NEAR.
4. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (line 1875).
   - `send_tokens` dispatches `ft_transfer(alice.near, 10000 USDC)` (line 2103–2106).
5. The USDC contract rejects the transfer because `alice.near` is blacklisted. The promise fails.
6. `fin_transfer_send_tokens_callback` is called. `is_ft_transfer_call = false` (empty msg). `is_refund_required(false)` returns `false` unconditionally (line 1800–1803).
7. The callback emits `FinTransferEvent` (success) and pays the relayer fee (lines 1719–1745).
8. Any subsequent call to `fin_transfer` with the same proof panics with `TransferAlreadyFinalised` (line 2229–2230).
9. 10,000 USDC is permanently locked in the bridge contract. `alice.near` receives nothing.

**Test plan:** Deploy a mock NEP-141 token contract that rejects `ft_transfer` calls (simulating blacklisting). Call `fin_transfer` with a valid proof targeting the blacklisted account. Assert that: (a) `FinTransferEvent` is emitted, (b) the recipient balance is 0, (c) the bridge holds the full token amount, and (d) a second `fin_transfer` call with the same proof panics with `TransferAlreadyFinalised`.
