### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Certificate Without Cryptographic Verification — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance used for all block types provides a `validatePerasCert` implementation that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or structural checks. An unprivileged peer can send a crafted Peras certificate for any block, causing the receiving node to accept it and apply the full `perasWeight` boost to that block's chain weight, directly manipulating chain selection.

---

### Finding Description

In `SupportsPeras.hs`, the overlapping instance `instance StandardHash blk => BlockSupportsPeras blk` is explicitly described as a "degenerate instance for all blks to get things to compile" (referencing issue #73). Its `validatePerasCert` body is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the production instance for all block types. No signature over the certificate's `(roundNo, boostedBlock)` payload is checked, no voter set membership is verified, no quorum threshold is enforced, and no round-number bounds are validated. The function simply wraps the caller-supplied `cert` in a `ValidatedPerasCert` and assigns it the full protocol weight.

The accepted certificate is then processed by the `ObjectPool` for Peras certificates: [2](#0-1) 

and stored in `PerasCertDB`, from which `PerasWeightSnapshot` is derived and fed into chain selection: [3](#0-2) [4](#0-3) 

**Analog to the external report:** In the Tigris referral bug, `_referred[user]` defaults to `bytes32(0)` for every user, and an attacker registers `_referral[0x0] = attackerAddress` to become the default referral for all users. Here, `validatePerasCert` defaults to accepting every certificate (the "zero check" is the missing guard), so any peer can register an arbitrary block as the boosted target for any round, becoming the de-facto certificate authority for that round without holding any stake or keys.

---

### Impact Explanation

`PerasWeightSnapshot` is consumed by `preferAnchoredCandidate` and `compareChainDiffs` during chain selection: [5](#0-4) 

A crafted certificate that boosts an attacker-controlled block by `perasWeight params` can cause an honest node to prefer a shorter or non-canonical chain over the honest majority chain, constituting a **chain-selection safety failure**. The attacker does not need to hold any stake, VRF keys, or KES keys — only the ability to send a Peras certificate message to the target node.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

- The degenerate instance is the only `BlockSupportsPeras` instance in the production source tree; no era-specific override exists yet.
- The entry point is the Peras certificate mini-protocol, reachable by any connected peer without authentication.
- Exploitation requires only sending a well-formed CBOR-encoded `PerasCert` message; no key material is needed.
- Likelihood is **conditional on Peras being activated** on a network. On a Peras-enabled private testnet or future mainnet deployment, exploitation is straightforward.

---

### Recommendation

Replace the stub with a real implementation that:
1. Verifies the aggregate BLS signature over `hash(roundNo ∥ boostedBlock)` against the aggregated public keys of the claimed voters.
2. Checks that each claimed voter seat index is within bounds and corresponds to a registered stake pool in the current `PerasVoteStakeDistr`.
3. Enforces the quorum threshold: total stake of voters must exceed `perasQuorumThreshold params`.
4. Validates that `pcCertRound` falls within the current or recent Peras round window.
5. Rejects certificates whose `pcCertBoostedBlock` does not correspond to a known block in the local chain fragment.

The concrete BLS verification primitives already exist in `Ouroboros.Consensus.Peras.Crypto.BLS` and the committee verification logic in `Ouroboros.Consensus.Committee.WFALS` / `EveryoneVotes` can serve as a reference. [6](#0-5) [7](#0-6) 

---

### Proof of Concept

1. Connect to a Peras-enabled node as an unprivileged peer.
2. Construct a `PerasCert` (or the equivalent wire encoding) with:
   - `pcCertRound` = any current round number
   - `pcCertBoostedBlock` = hash of the attacker's preferred (possibly shorter) chain tip
   - `pcVoters` / `pcSignature` = arbitrary bytes (no verification is performed)
3. Send the certificate via the Peras certificate diffusion mini-protocol.
4. The node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB`; `PerasWeightSnapshot` is updated to reflect the boost.
6. On the next chain selection event, `preferAnchoredCandidate` applies the boost, and the node may switch to the attacker's preferred chain even if it is shorter than the honest chain.
