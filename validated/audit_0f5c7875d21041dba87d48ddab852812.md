### Title
Permanent Fund Loss via Decimal Normalization Truncation to Zero in `sign_transfer` - (File: `near/omni-bridge/src/lib.rs`)

### Summary

When a NEAR-origin token has a large decimal difference between its NEAR representation (`decimals`) and its origin-chain representation (`origin_decimals`), the `normalize_amount` floor-division in `sign_transfer` can produce zero. Because tokens are already burned or locked inside `init_transfer_internal` before `sign_transfer` is ever called, and no cancel/refund path exists for pending transfers, the user's funds are permanently lost.

### Finding Description

The bridge stores two decimal values per token in the `Decimals` struct: [1](#0-0) 

`normalize_amount` converts a NEAR-native amount to the destination-chain precision using floor division: [2](#0-1) 

In `sign_transfer`, this normalized value is checked to be non-zero before the MPC signing request is dispatched: [3](#0-2) 

If `amount_without_fee < 10^(origin_decimals - decimals)`, the division truncates to zero and `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`. This panic happens **after** the user's tokens have already been irreversibly consumed in `init_transfer_internal`: [4](#0-3) 

`burn_tokens_if_needed` issues a fire-and-forget `burn` call (`.detach()`), and `lock_tokens_if_needed` increments the locked-token counter — both are committed before any relayer ever calls `sign_transfer`. [5](#0-4) 

There is no `cancel_transfer` or admin-recovery function. `remove_transfer_message` is only invoked inside `sign_transfer_callback` (after a successful MPC signature) or `claim_fee_callback` — neither of which is reachable when `sign_transfer` itself panics: [6](#0-5) 

### Impact Explanation

The user's tokens are permanently burned (for bridge-deployed tokens) or permanently locked (for native tokens) on NEAR with no recovery path. This constitutes a **permanent freezing of bridged funds**. The transfer record stays in `pending_transfers` indefinitely, and every subsequent `sign_transfer` call for that transfer ID will always revert with the same error.

### Likelihood Explanation

The condition is reachable for any token pair where `origin_decimals > decimals`. A concrete, realistic example: NEAR's native token has 24 decimals on NEAR and is represented with 18 decimals on EVM chains (`diff = 6`, divisor = `10^6`). Any user who initiates a transfer of fewer than `1,000,000` base units (i.e., less than `1e-18` NEAR in EVM terms) will have their tokens permanently lost. For tokens with even larger differences (e.g., `origin_decimals=24`, `decimals=6`, divisor=`10^18`), the threshold is enormous. The `init_transfer` path imposes no minimum-amount check relative to the decimal normalization divisor, so any unprivileged user can self-inflict this loss by submitting a small transfer.

### Recommendation

1. **Add a pre-flight check in `init_transfer`** (before burning/locking) that verifies `normalize_amount(amount_without_fee, decimals) > 0`. Reject the transfer immediately and return the tokens to the user if this check fails.
2. Alternatively, enforce a protocol-level minimum transfer amount of `10^(origin_decimals - decimals)` at the `ft_on_transfer` / `init_transfer` entry point.
3. Consider adding a `cancel_transfer` escape hatch callable by the original sender for transfers stuck in `pending_transfers` with no valid signing path.

### Proof of Concept

**Setup**: Token registered with `Decimals { decimals: 18, origin_decimals: 24 }` (diff = 6, divisor = 1,000,000).

**Step 1** — User calls `ft_transfer_call` with `amount = 500_000` (fee = 0):
- `init_transfer_internal` is entered.
- `burn_tokens_if_needed` burns 500,000 tokens (detached, irreversible).
- `lock_tokens_if_needed` increments locked counter by 500,000.
- Transfer message stored in `pending_transfers`. Function returns `U128(0)` — success from the user's perspective.

**Step 2** — Relayer calls `sign_transfer(transfer_id, ...)`:
- `normalize_amount(500_000, Decimals { decimals: 18, origin_decimals: 24 })` = `500_000 / 1_000_000` = **0** (floor division).
- `require!(0 > 0, ...)` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.

**Result**: 500,000 tokens are burned/locked on NEAR. The transfer can never be signed. No refund mechanism exists. Funds are permanently lost. [7](#0-6) [8](#0-7) [4](#0-3)

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
