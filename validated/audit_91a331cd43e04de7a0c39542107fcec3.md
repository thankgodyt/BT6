### Title
ChainSync Client Disconnects from Peers Using Empty Peras Weight Snapshot When Header Is Beyond Forecast Horizon — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer's header is beyond the forecast horizon, the ChainSync client must decide whether to disconnect from that peer or keep waiting. This decision is made by `checkPreferTheirsOverOurs`, which calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the node's actual Peras certificate weight snapshot. As a result, the chain-selection comparison that guards peer disconnection ignores all Peras certificate boosts. A peer offering a chain that is equal in block-number length to the local selection but is strictly preferred under Peras weights will be incorrectly disconnected from, causing the honest node to remain on a less-secure chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` — i.e., the header's slot is outside the forecast range of the intersection ledger state. The function's purpose is to guard against a peer that is wasting the node's time by advertising a chain that can never be adopted:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← stale/empty state used for the decision
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
```

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` reduces to a pure block-number comparison. When Peras is active, the correct comparison must also account for certificate-boosted weight via the real `PerasWeightSnapshot`. The real snapshot is available in the `ChainSelEnv` / `NodeKernel` context and is passed to every other chain-selection call site in `ChainSel.hs` (e.g., `constructPreferableCandidates`, `chainSelection`, `sortCandidates`).

The structural parallel to the reported vulnerability is exact:

| Deriverse bug | Ouroboros analog |
|---|---|
| Liquidation decision made with stale edge price | Disconnect decision made with empty Peras weight snapshot |
| `check_funding_rate` / `check_soc_loss` update funds *after* the decision | Actual Peras weights exist and are used everywhere *except* this decision point |
| Result: unfair liquidation | Result: unfair disconnection from a Peras-preferred peer |

The root cause is in `readLedgerStateHelper` → `checkPreferTheirsOverOurs` at the call to `preferAnchoredCandidate` with `emptyPerasWeightSnapshot`.

---

### Impact Explanation

When Peras is active, two chains of equal block-number length can differ in Peras certificate weight. The canonical chain may be the one with more certificate weight, not the longer one. If a peer advertises such a chain and its tip slot happens to be beyond the current forecast horizon (a normal occurrence during initial sync or after a large slot gap), the node will:

1. Call `checkPreferTheirsOverOurs` with `emptyPerasWeightSnapshot`.
2. Compute `preferAnchoredCandidate` as block-number-only → `ShouldNotSwitch` (equal length).
3. Throw `CandidateTooSparse` and disconnect from the peer.
4. Remain on its current chain, which is less preferred under the Peras chain order.

If all honest peers advertising the Peras-boosted canonical chain happen to be in this code path simultaneously (e.g., during a burst of headers just past the forecast window), the node can be made to prefer a non-canonical, less-secure chain. This satisfies the "High" impact criterion: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*.

---

### Likelihood Explanation

- **Reachable by unprivileged peer**: Yes. Any peer can send a valid header whose slot is beyond the local forecast horizon; this is a normal network condition during sync.
- **Peras activation**: Peras is an active protocol extension in this codebase; the `PerasWeightSnapshot` is already threaded through all other chain-selection paths.
- **Trigger condition**: The peer's chain must be equal in block number to the local selection but strictly preferred under Peras weights (i.e., it carries a certificate boosting a block on that chain). This is a realistic scenario whenever a Peras certificate is issued near an epoch boundary or during a slot gap.
- **Severity amplifier**: The TODO comment (`// TODO: remove this entire check`) confirms the developers already recognize this code path is incorrect in the Peras context, raising confidence that the stale-snapshot path is a genuine defect rather than an intentional design choice.

Likelihood: **Low-Medium** (requires Peras active + specific certificate timing), but the impact when triggered is **High**.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` that is already available in the surrounding `ChainSelEnv` / `ConfigEnv` context — the same snapshot passed to `constructPreferableCandidates` and `chainSelection`. Alternatively, follow the TODO and remove the check entirely, relying on the LoP (Limit on Patience) bucket mechanism to bound how long the node waits for a peer beyond the forecast horizon.

---

### Proof of Concept

**Private-testnet sequence:**

1. Start a two-node private testnet with Peras enabled.
2. Node A is at tip block #100 (no Peras certificate on its chain suffix).
3. Node B has an alternative chain also at block #100 but carrying a Peras certificate that boosts its suffix weight above A's.
4. Node B's next header (block #101) falls in a slot beyond Node A's current forecast horizon (e.g., a large slot gap exists between #100 and #101).
5. Node A receives the header for #101 from Node B.
6. `projectLedgerView` returns `Nothing` (slot beyond forecast range).
7. `checkPreferTheirsOverOurs` is called; `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` compares block numbers only → both chains are at #100 → `ShouldNotSwitch`.
8. Node A throws `CandidateTooSparse` and disconnects from Node B.
9. Node A remains on its non-Peras-boosted chain, which is less preferred under the correct Peras chain order.

preferAnchoredCandidate ::
  forall blk h h'.
  ( BlockSupportsProtocol blk
  , HasCallStack
  , GetHeader1 h
  , GetHeader1 h'
  , HeaderHash (h blk) ~ HeaderHash blk
  , HeaderHash (h blk) ~ HeaderHash (h' blk)
  , HasHeader (h blk)
  , HasHeader (h' blk)
  ) =>
  BlockConfig blk ->
  -- | Peras weights used to judge this chain.
  PerasWeightSnapshot blk ->
  -- | Our chain
  AnchoredFragment (h blk) ->
  -- | Candidate
  AnchoredFragment (h' blk) ->
  ShouldSwitch (ReasonForSwitch' blk)
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
