### Title
Wormhole VAA `emitter_chain` Ignored — Chain Kind Derived from Attacker-Controlled Payload Enables Factory Check Bypass - (File: `near/omni-prover/wormhole-omni-prover-proxy/src/parsed_vaa.rs`)

---

### Summary

In `parsed_vaa.rs`, all four `TryInto` conversions from `ParsedVAA` construct the `emitter_address` using the chain kind extracted from the **payload's `token_address`** field — data the message sender controls — rather than from `self.emitter_chain`, the Wormhole-attested chain identifier in the VAA header. This is the direct structural analog to the reported bug: a partial identifier (address bytes only) is used where a full origin (chain kind + address bytes) is required, and the authoritative chain component is silently discarded.

---

### Finding Description

Every `TryInto<*Message>` implementation in `parsed_vaa.rs` constructs `emitter_address` as:

```rust
emitter_address: OmniAddress::new_from_slice(
    transfer.token_address.get_chain(),   // ← chain kind from PAYLOAD (attacker-controlled)
    &self.emitter_address,                // ← address bytes from VAA header (Wormhole-attested)
)?,
``` [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) 

The `ParsedVAA` struct carries `emitter_chain: u16` — the Wormhole-assigned chain ID of the actual source chain, set by the guardian network — but this field is **never consulted** when determining the chain kind of the emitter. [5](#0-4) 

Compare this to the EVM light-client prover, where the chain kind is passed as a trusted external parameter derived from the proof submission context, not from the event payload itself: [6](#0-5) 

The downstream factory authorization check in `fin_transfer_callback` and `claim_fee_callback` uses `emitter_address.get_chain()` to select which registered factory to compare against:

```rust
require!(
    self.factories
        .get(&init_transfer.emitter_address.get_chain())
        == Some(init_transfer.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
``` [7](#0-6) [8](#0-7) 

Because the chain kind in `emitter_address` is taken from the payload, an attacker controls which factory slot is looked up. The address bytes come from the VAA header (Wormhole-attested), but the chain dimension — which determines *which* factory entry is selected — is fully attacker-controlled.

---

### Impact Explanation

**Critical.** The factory check is the sole on-chain authorization gate preventing arbitrary Wormhole messages from finalizing bridge transfers. If an attacker can make `emitter_address.get_chain()` resolve to chain B while the actual VAA emitter is a contract they control on chain A, and if the address bytes of their contract on chain A equal the registered factory bytes for chain B, the check passes.

Cross-chain bridge protocols routinely deploy factory contracts at **identical addresses across all EVM chains** using CREATE2 with a fixed salt and deployer. If Omni Bridge follows this pattern (common for operational symmetry), then:

1. The registered factory address bytes are identical for Eth, Arb, Base, Bnb, Pol, HyperEvm, and Abs.
2. An attacker who deploys a malicious contract at that address on any chain where the factory has not yet been deployed (e.g., a newly added chain like HyperEvm or Abs before the legitimate factory is live) controls a contract whose address bytes match every other chain's factory.
3. The attacker emits a Wormhole message from that contract with `token_address` claiming any already-registered chain (e.g., `OmniAddress::Eth(...)`).
4. `emitter_address` is constructed as `OmniAddress::Eth(attacker_bytes)`.
5. `factories.get(&ChainKind::Eth) == Some(OmniAddress::Eth(attacker_bytes))` — passes, because `attacker_bytes == eth_factory_bytes`.
6. The attacker can finalize a fabricated `InitTransferMessage` with arbitrary `recipient`, `token`, and `amount`, minting or unlocking bridged tokens on NEAR with no corresponding source-chain deposit.

---

### Likelihood Explanation

**Medium.** The attack requires the attacker's contract address bytes to match a registered factory's bytes. This is realistic under two conditions that are both common in production bridge deployments:

- **Same-address factory deployment across chains** (CREATE2 with fixed salt): widely used by cross-chain protocols for operational symmetry.
- **Race window on newly added chains**: HyperEvm and Abs are listed as supported chains. If the factory has not yet been deployed on a new chain, an attacker who knows the expected address (observable from other chains) can deploy a malicious contract there first.

The attacker entry path is fully permissionless: deploying a contract and emitting a Wormhole message requires no special role.

---

### Recommendation

Replace `token_address.get_chain()` with a chain kind derived from `self.emitter_chain` (the Wormhole chain ID in the VAA header), using a validated mapping from Wormhole chain IDs to `ChainKind`. This ensures the chain dimension of `emitter_address` is Wormhole-attested rather than payload-supplied. Additionally, assert that the chain kind derived from `emitter_chain` matches the chain kind embedded in `token_address` to catch inconsistent payloads.

---

### Proof of Concept

**Precondition**: Omni Bridge factories are deployed at address `0xF00...` on Ethereum and Arbitrum (same address, CREATE2 pattern). The factory on HyperEvm has not yet been deployed.

1. Attacker deploys a malicious contract at `0xF00...` on HyperEvm (before the legitimate factory).
2. Attacker's contract calls the Wormhole core bridge on HyperEvm, emitting a message with Borsh-encoded `InitTransferWh` payload where:
   - `token_address = OmniAddress::Eth(some_registered_eth_token)`
   - `recipient = OmniAddress::Near(attacker_near_account)`
   - `amount = 1_000_000_000` (arbitrary)
   - `origin_nonce = <unused nonce>`
3. Wormhole guardians observe the message on HyperEvm and produce a signed VAA with `emitter_chain = HyperEvm_wormhole_id`, `emitter_address = 0xF00...`.
4. Attacker submits the VAA to the NEAR Wormhole prover proxy via `fin_transfer`.
5. `parsed_vaa.rs` constructs `emitter_address = OmniAddress::Eth(0xF00...)` (chain kind from payload, bytes from VAA header).
6. `fin_transfer_callback` checks `factories.get(&ChainKind::Eth) == Some(OmniAddress::Eth(0xF00...))` — **passes**.
7. The bridge mints/unlocks tokens to the attacker's NEAR account with no corresponding deposit on any source chain. [9](#0-8) [10](#0-9)

impl TryInto<InitTransferMessage> for ParsedVAA {
    type Error = String;

    fn try_into(self) -> Result<InitTransferMessage, String> {
        let transfer: InitTransferWh = borsh::from_slice(&self.payload).map_err(stringify)?;

        if transfer.payload_type != ProofKind::InitTransfer {
            return Err("Invalid proof kind".to_owned());
        }

        Ok(InitTransferMessage {
            token: transfer.token_address.clone(),
            amount: transfer.amount.into(),
            fee: Fee {
                fee: transfer.fee.into(),
                native_fee: transfer.native_fee.into(),
            },
            recipient: transfer.recipient.parse().map_err(stringify)?,
            origin_nonce: transfer.origin_nonce,
            sender: transfer.sender,
            msg: transfer.message,
            emitter_address: OmniAddress::new_from_slice(
                transfer.token_address.get_chain(),
                &self.emitter_address,
            )?,
        })
    }

                storage_deposit_actions,
            )
            .into()

            self.process_fin_transfer_to_other_chain(predecessor_account_id, transfer_message);
            PromiseOrValue::Value(destination_nonce)
        }
