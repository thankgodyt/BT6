Audit Report

## Title
Inverted Success/Failure Check in `submit_transfer_to_btc_connector_callback` Causes Permanent Fund Loss on BTC Withdrawal Failure - (File: near/omni-bridge/src/btc.rs)

## Summary

`submit_transfer_to_btc_connector_callback` in `near/omni-bridge/src/btc.rs` uses an inverted condition to distinguish BTC withdrawal success from failure. Under NEP-141, `ft_transfer_call` returns the number of tokens **not consumed** (refunded), so `result.0 > 0` means failure (tokens returned) and `result.0 == 0` means success (all tokens consumed). The current code sends the relayer fee on failure and re-inserts the transfer record on success — the exact opposite of correct behavior — causing permanent loss of user funds on any BTC withdrawal failure and ghost transfer records on success.

## Finding Description

In `submit_transfer_to_utxo_chain_connector`, the bridge computes `amount = total_amount - fee`, removes the transfer record from storage, and dispatches `ft_transfer_call(connector, amount, ...)` to the BTC connector:

```rust
// near/omni-bridge/src/btc.rs L39
let amount = U128(transfer.message.amount.0 - transfer.message.fee.fee.0);
// L84
self.remove_transfer_message(transfer_id);
// L88-100
ext_token::ext(btc_account_id)
    .ft_transfer_call(self.get_utxo_chain_connector(chain_kind), amount, None, msg)
    .then(Self::ext(...).submit_transfer_to_btc_connector_callback(...))
```

The callback at L111 reads:

```rust
if matches!(call_result, Ok(result) if result.0 > 0) {
    // sends fee to relayer
    self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
} else {
    // re-inserts transfer record
    self.add_transfer_message(transfer_msg, transfer_owner.clone());
    ...
}
```

Per NEP-141, the return value of `ft_transfer_call` is the amount refunded (not consumed):
- `result.0 > 0` → tokens returned to bridge → **withdrawal failed**
- `result.0 == 0` → all tokens consumed → **withdrawal succeeded**

The condition `result.0 > 0` matches the **failure** case, yet the code executes the fee-payment branch. The **success** case (`result.0 == 0`) falls into the `else` branch and re-inserts the transfer record into storage. This is directly inverted from the correct logic, as seen in the analogous `fin_transfer_send_tokens_callback` pattern in `lib.rs` where success sends the fee and failure reverts state.

## Impact Explanation

**On BTC withdrawal failure** (`result.0 > 0`, tokens returned):
1. The connector refunds `amount` (= `total_amount - fee`) tokens to the bridge.
2. The bridge now holds `total_amount` tokens (refunded `amount` + the `fee` portion never sent).
3. `send_fee_internal` is called, transferring `fee` tokens to the relayer — despite the withdrawal having failed.
4. The transfer record is **not restored**. The remaining `amount` (= `total_amount - fee`) tokens sit in the bridge contract with no associated transfer record and no recovery path.
5. The user permanently loses `total_amount - fee` tokens.

**On BTC withdrawal success** (`result.0 == 0`, all tokens consumed):
1. `add_transfer_message` re-inserts a ghost transfer record for a transfer whose tokens are already gone.
2. The relayer fee is never paid.
3. A relayer can attempt `submit_transfer_to_utxo_chain_connector` again on the ghost record; the `ft_transfer_call` will fail (bridge holds no tokens), but the ghost record persists, wasting storage and potentially causing repeated failed calls.

This constitutes permanent freezing of bridged funds and fee mis-accounting, matching the Critical allowed impact scope.

## Likelihood Explanation

BTC withdrawals can fail for entirely non-adversarial reasons: invalid or already-spent UTXOs, connector-side gas fee limits exceeded, network congestion, or connector contract bugs. No attacker action is required — any legitimate failure of the BTC connector's `ft_on_transfer` triggers the inverted callback. The affected code path is live for all BTC/Zcash UTXO chain withdrawals. The user who initiated the transfer has no ability to prevent or recover from this outcome.

## Recommendation

Invert the condition so that the fee is sent on success (`result.0 == 0`) and the transfer is restored on failure:

```rust
pub fn submit_transfer_to_btc_connector_callback(
    &mut self,
    transfer_msg: TransferMessage,
    transfer_owner: AccountId,
    fee_recipient: AccountId,
    #[callback_result] call_result: &Result<U128, PromiseError>,
) -> PromiseOrValue<()> {
-   if matches!(call_result, Ok(result) if result.0 > 0) {
+   if matches!(call_result, Ok(result) if result.0 == 0) {
        let token_fee = transfer_msg.fee.fee.0;
        self.send_fee_internal(&transfer_msg, fee_recipient, token_fee)
    } else {
        let required_storage_balance =
            self.add_transfer_message(transfer_msg, transfer_owner.clone());
        self.update_storage_balance(
            transfer_owner,
            required_storage_balance,
            NearToken::from_yoctonear(0),
        );
        PromiseOrValue::Value(())
    }
}
```

## Proof of Concept

1. User holds wrapped BTC on NEAR and initiates a BTC withdrawal via `ft_transfer_call` to the bridge, creating a `TransferMessage` with `total_amount = 1_000_000` and `fee = 10_000`.
2. A trusted relayer calls `submit_transfer_to_utxo_chain_connector`. The bridge removes the transfer record and calls `ft_transfer_call(connector, 990_000, ...)`.
3. The BTC connector's `ft_on_transfer` fails (e.g., UTXO already spent) and returns `990_000` (all tokens refunded).
4. `submit_transfer_to_btc_connector_callback` is invoked with `Ok(U128(990_000))`.
5. `result.0 = 990_000 > 0` → condition is true → `send_fee_internal` is called, transferring `10_000` tokens to the relayer.
6. The transfer record is **not** restored. The `990_000` returned tokens remain in the bridge with no associated record and no recovery mechanism.
7. The user has permanently lost `990_000` tokens.

A unit test can be written against the NEAR sandbox: deploy the bridge contract, mock a BTC connector whose `ft_on_transfer` returns the full amount, call `submit_transfer_to_utxo_chain_connector`, and assert post-callback that (a) the transfer record does not exist, (b) the relayer received the fee, and (c) the user's tokens are unrecoverable — confirming the inverted behavior.
