Audit Report

## Title
Minted Tokens Credited to Bridge Contract Instead of Intended Recipient in `OmniToken::mint()` When `msg` Is Non-Empty - (File: `near/omni-token/src/lib.rs`)

## Summary

In `OmniToken::mint()`, when `msg` is `Some`, `internal_deposit` credits the minted tokens to `env::predecessor_account_id()` (the bridge contract) rather than the intended `account_id`. The subsequent `ft_transfer_call` then uses the bridge contract as `sender_id`, so any partial refund from `ft_on_transfer` is returned to the bridge contract. The bridge's `fin_transfer_send_tokens_callback` then attempts to burn the full `amount_without_fee` from the bridge contract, but the bridge only holds the partial refund, causing the burn to fail and leaving the refunded tokens permanently stranded.

## Finding Description

In `near/omni-token/src/lib.rs` lines 135–139, the `Some(msg)` branch of `mint()` calls:

```rust
self.token
    .internal_deposit(&env::predecessor_account_id(), amount.into()); // bridge contract, not account_id

self.ft_transfer_call(account_id, amount, None, msg)
```

`env::predecessor_account_id()` inside `mint()` is the bridge contract (its sole authorized caller via `assert_controller()`). The NEAR FT standard's `ft_transfer_call` records `env::predecessor_account_id()` as `sender_id` for the subsequent `ft_resolve_transfer` callback. Because `mint()` is executing in the same call frame, `env::predecessor_account_id()` remains the bridge contract, so `sender_id = bridge_contract` in `ft_resolve_transfer`. Any unused tokens returned by the recipient's `ft_on_transfer` are refunded to the bridge contract, not to `account_id`.

The bridge's `send_tokens()` function at lines 2094–2101 is the sole caller of `mint()` with a non-empty `msg`, passing `recipient` as `account_id` and `Some(msg)` when the transfer carries a message. After `mint()` resolves, `fin_transfer_send_tokens_callback` (lines 1702–1710) checks `is_refund_required(is_ft_transfer_call)` and, if true, calls `burn_tokens_if_needed(token, amount_without_fee)`. However, the bridge contract only holds the partial refund (e.g., `amount / 2`), not the full `amount_without_fee`. The burn therefore fails or panics, and the partial refund tokens remain permanently stranded in the bridge contract's NEP-141 balance with no recovery path.

The `else` branch (lines 140–142) correctly uses `&account_id`, confirming the `Some(msg)` branch is the sole defect.

## Impact Explanation

This constitutes irreversible loss of bridged funds. When a cross-chain inbound transfer carries a non-empty `msg` and the recipient NEAR contract's `ft_on_transfer` returns a non-zero unused amount (a standard NEP-141 behavior), the refunded tokens accumulate in the bridge contract's token balance permanently. There is no function in the bridge contract to redistribute or recover these tokens. This directly matches the critical impact class: permanent freezing/loss of bridged funds.

## Likelihood Explanation

The `msg` field is a documented, user-controlled feature of the bridge protocol enabling composable cross-chain calls (e.g., "bridge and swap"). Any unprivileged user who initiates a cross-chain transfer with a non-empty `msg` targeting a NEAR DeFi contract that partially rejects the transfer triggers this loss. No special role, key compromise, or attacker privilege is required. Partial rejection by `ft_on_transfer` is a normal, expected NEP-141 behavior (e.g., a DEX that can only partially fill a swap). The path is fully reachable through public cross-chain transfer flows.

## Recommendation

Replace `env::predecessor_account_id()` with `account_id` in the `internal_deposit` call inside the `Some(msg)` branch of `mint()`:

```rust
if let Some(msg) = msg {
    self.token
        .internal_deposit(&account_id, amount.into()); // fix: use account_id

    self.ft_transfer_call(account_id, amount, None, msg)
}
```

This ensures minted tokens are always credited to the intended recipient, and any partial refund from `ft_on_transfer` is correctly returned to that recipient rather than to the bridge contract.

## Proof of Concept

1. Alice initiates a cross-chain transfer from Ethereum to NEAR with `msg = '{"action":"swap",...}'` targeting a NEAR DEX contract as recipient.
2. The bridge finalizes the transfer and calls `send_tokens(token, dex_contract, amount, msg)`.
3. `send_tokens` calls `ext_token::ext(token).mint(dex_contract, amount, Some(msg))`.
4. Inside `OmniToken::mint()`, `internal_deposit(&env::predecessor_account_id(), amount)` credits `amount` tokens to the **bridge contract**, not `dex_contract`.
5. `ft_transfer_call(dex_contract, amount, None, msg)` is called; the DEX's `ft_on_transfer` partially processes the swap and returns `unused = amount / 2`.
6. `ft_resolve_transfer` refunds `amount / 2` tokens to `sender_id = bridge_contract`.
7. `fin_transfer_send_tokens_callback` detects a partial result via `is_refund_required` and calls `burn_tokens_if_needed(token, amount_without_fee)` — but the bridge contract only holds `amount / 2`, so the burn fails.
8. `amount / 2` bridged tokens are permanently stranded in the bridge contract's NEP-141 balance with no recovery mechanism.

A local integration test can reproduce this by: deploying the token contract with the bridge as controller, calling `mint(dex_mock, amount, Some("swap"))` from the bridge, having `dex_mock.ft_on_transfer` return `amount / 2`, and asserting that `ft_balance_of(bridge_contract) == amount / 2` after resolution while `ft_balance_of(dex_mock) == amount / 2` and the burn call panics.
