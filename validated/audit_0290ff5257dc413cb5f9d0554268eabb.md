### Title
Silent Token Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract silently returns `U128(0)` when the recipient account has no storage registration, while the minted tokens remain permanently in the bridge's account with no `lost_found` entry and no revert signal to the caller.

---

### Finding Description

In `safe_mint`, the function first mints the full `amount` into the bridge's own account via `internal_deposit`, then checks whether the intended recipient is registered:

```rust
// contracts/nbtc/src/lib.rs  lines 112-116
self.token.internal_deposit(&self.bridge_id, amount.into());

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
``` [1](#0-0) 

When the recipient is unregistered the function returns `U128(0)` — a value that looks like "zero tokens used" — without reverting, without burning the already-deposited tokens, and without creating a `lost_found` entry. The tokens remain credited to `self.bridge_id` indefinitely.

The `lost_found` recovery path that exists elsewhere in the codebase is only triggered inside `transfer_nbtc_callback` when an `ft_transfer` cross-contract call fails:

```rust
// contracts/satoshi-bridge/src/token_transfer.rs  lines 61-68
if !promise_success {
    self.data_mut()
        .lost_found
        .entry(account_id.clone())
        .and_modify(|v| *v += amount.0)
        .or_insert(amount.0);
``` [2](#0-1) 

The early-return path in `safe_mint` never reaches any cross-contract call, so `lost_found` is never populated and the bridge has no programmatic record that a mint was attempted and silently dropped.

The analog to the external report is direct: just as `HolographERC721.safeTransferFrom` gates the `onERC721Received` callback on an ERC-165 check that many legitimate receivers do not implement — causing silent transfer failure — `safe_mint` gates the token delivery on a storage-registration check and silently discards the minted tokens when that check fails, instead of reverting so the caller can handle the failure.

---

### Impact Explanation

- Tokens are minted (total supply increases by `amount`) but never delivered to the user.
- The bridge's `bridge_id` account holds the orphaned tokens with no automated recovery.
- No `lost_found` entry is created, so the bridge contract has no on-chain record of the stuck funds.
- Manual operator intervention is required to identify and redistribute the tokens.
- If the deposit UTXO was already marked verified before `safe_mint` was called, the user also cannot trigger the refund path, leaving their BTC locked and their nBTC undelivered.

**Impact class:** Medium — stuck bridge state requiring operator intervention; minted supply exceeds tokens in circulation.

---

### Likelihood Explanation

NEAR's NEP-141 storage-registration requirement is a well-known prerequisite. Any user who deposits BTC before registering their account in the nBTC token contract (e.g., a first-time user, a smart-contract wallet, or a DeFi protocol that auto-generates deposit addresses) will trigger this path. No special privileges are required; the condition is reachable by any ordinary bridge user.

---

### Recommendation

Replace the silent early return with a hard revert so the bridge's callback can detect the failure and take corrective action (e.g., populate `lost_found` or refund the deposit):

```rust
require!(
    self.token.accounts.get(&account_id).is_some(),
    "safe_mint: recipient account is not registered"
);
```

Alternatively, auto-register the recipient account before the transfer (mirroring how `mint_inner` handles unregistered accounts at line 342–344) so that no deposit is silently discarded. [3](#0-2) 

---

### Proof of Concept

1. User sends BTC to their deposit address; the bridge verifies the Merkle proof and calls `safe_mint(user_account, amount, None)` on the nBTC contract.
2. `user_account` has never called `storage_deposit` on the nBTC contract, so `self.token.accounts.get(&user_account)` returns `None`.
3. `internal_deposit(&self.bridge_id, amount)` executes successfully — `amount` nBTC is credited to the bridge.
4. The registration check fires; the function returns `PromiseOrValue::Value(U128(0))`.
5. The bridge receives a success result (value `0`), interprets it as "0 tokens returned/unused," and proceeds normally.
6. The user holds 0 nBTC. The bridge holds `amount` extra nBTC with no `lost_found` record. The deposit UTXO is marked verified, blocking any refund path. [4](#0-3)

    pub fn safe_mint(

            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"

        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
