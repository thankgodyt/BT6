Audit Report

## Title
Small Transfer Amount Normalizes to Zero, Permanently Freezing User Funds in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

## Summary

When a user initiates a NEAR→EVM transfer with an amount that, after decimal normalization, rounds down to zero, their tokens are burned or locked inside `init_transfer_internal` before any normalization check occurs. Because `sign_transfer` always panics for such a transfer and no `cancel_transfer` or refund path exists, the user's funds are permanently frozen with no recovery mechanism.

## Finding Description

The bridge stores token decimal mappings as a `Decimals { decimals, origin_decimals }` pair. `normalize_amount` performs floor division:

```rust
// near/omni-bridge/src/lib.rs:2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

The function's own doc comment acknowledges: *"When fee = 0, dust stays locked/burned."* — but this refers only to sub-unit remainders, not to the case where the entire amount normalizes to zero. [2](#0-1) 

`sign_transfer` enforces a non-zero result after normalization:

```rust
// near/omni-bridge/src/lib.rs:475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

However, `init_transfer` only validates `fee < amount` — it does **not** pre-check that `normalize_amount(amount - fee) > 0`: [4](#0-3) 

Immediately after this check, `init_transfer_internal` burns (for deployed tokens) or locks (for native tokens) the full amount: [5](#0-4) 

The transfer is then stored in `pending_transfers`. A grep for `cancel_transfer` in `lib.rs` returns zero matches, and `remove_transfer_message_without_refund` (the only removal path) does not restore burned/locked tokens. Because `sign_transfer` will always panic for this transfer, no MPC signature is ever produced, no EVM `finTransfer` can occur, and the funds are permanently frozen.

## Impact Explanation

This constitutes **permanent freezing of bridged funds** — an explicitly listed Critical impact. Tokens are irreversibly burned or locked on NEAR with no on-chain recovery path. The `InvalidAmountToTransfer` error appears only once in the entire codebase (inside `sign_transfer`), confirming there is no alternative signing route. [6](#0-5) 

## Likelihood Explanation

NEAR tokens commonly use 24 decimals while their EVM counterparts use 18, making the minimum transferable unit `10^6` yocto-tokens (~0.000001 tokens). Any user who sends fewer than `10^6` yocto-units — whether by mistake, UI rounding, or a deliberate dust-amount submission — triggers the freeze. No privileged access is required; the path is fully reachable via the public `ft_transfer_call` callback. [7](#0-6) 

## Recommendation

Add a normalization check inside `init_transfer` (before `init_transfer_internal` is called) to reject transfers whose net amount normalizes to zero:

```rust
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::FailedToGetTokenAddress);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(amount_without_fee, decimals) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` and prevents tokens from being burned/locked for a transfer that can never be finalized. [4](#0-3) 

## Proof of Concept

1. Token `foo.near` has `origin_decimals = 24` on NEAR and `decimals = 18` on EVM (scaling factor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 500_000) and calls `init_transfer_internal`.
4. `burn_tokens_if_needed` burns 500,000 yocto-units of `foo.near` from the user.
5. Transfer is stored in `pending_transfers`.
6. Relayer calls `sign_transfer`. `normalize_amount(500_000, {origin_decimals:24, decimals:18}) = 500_000 / 10^6 = 0`.
7. `require!(amount_to_transfer > 0, ...)` panics — `sign_transfer` always fails for this transfer.
8. No MPC signature is produced; no EVM `finTransfer` can occur.
9. No `cancel_transfer` function exists; `remove_transfer_message_without_refund` does not restore burned tokens.
10. The 500,000 yocto-units are permanently lost.
