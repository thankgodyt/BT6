Peras Certificate and Vote Validation Unconditionally Bypassed — Any Peer Can Inject Fake Certificates to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance in the codebase — implements `validatePerasCert` and `validatePerasVote` as unconditional `Right` returns, performing zero cryptographic or structural validation. Because the object-diffusion inbound pipeline calls this validator directly before persisting certificates and triggering chain selection, any unprivileged peer can inject arbitrary Peras certificates that boost any block by any weight, causing the victim node to prefer a non-canonical chain.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote validation. The repository contains exactly one instance — a catch-all degenerate instance for any `StandardHash blk`:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The same unconditional acceptance applies to `validatePerasVote`.

This validator is invoked directly in the inbound certificate processing pipeline:

```haskell

    processCerts
      systemTime

`processCerts` partitions the batch into valid/invalid using this validator, and since the validator always returns `Right`, every certificate in every batch is unconditionally accepted:

```haskell

  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  ...
``` [3](#0-2) 

Once a certificate is accepted, `ChainDB.addPerasCertAsync` enqueues it for `chainSelSync`, which adds it to `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block:

```haskell
certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
...
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection then uses the `PerasWeightSnapshot` — which now includes the fake certificate's boost — to compare candidate fragments via `weightedSelectView` and `preferAnchoredCandidate`:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [5](#0-4) 

The `WeightedSelectView` comparison sums `BlockNo` and `wsvWeightBoost`, so a sufficiently large fake boost can make a shorter, non-canonical chain appear heavier than the honest chain:

```haskell

  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [6](#0-5)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` (any block in the VolatileDB) and an arbitrary round number. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its boost is applied to chain selection. By choosing a boost value large enough to overcome the honest chain's block-number advantage, the attacker causes the victim node to switch to a non-canonical fork. This is a **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**, matching the High/Critical impact scope.

---

### Likelihood Explanation

The attack requires only that the attacker be a connected peer and that the Peras object-diffusion protocol be active. No stake, keys, or operator access are needed. The attacker constructs a `PerasCert` pointing to any block already in the victim's VolatileDB and sets `vpcCertBoost` to a value exceeding the honest chain's lead. The degenerate instance is the only instance in the codebase; there is no Cardano-specific override that would restore validation.

---

### Recommendation

1. **Implement real validation** in `validatePerasCert` and `validatePerasVote` before the Peras object-diffusion protocol is enabled on any network. The validation must verify committee membership, quorum threshold, round eligibility, and cryptographic signatures per the Peras specification.
2. **Block the inbound pipeline** until a real validator is wired in. The `-- TODO replace when actual plumbing is in place` comment in `PerasCert.hs` should be treated as a hard blocker for production deployment.
3. **Add a type-level or runtime guard** that prevents the degenerate instance from being used in any non-test context, e.g., a separate `TestBlockSupportsPeras` class or a compile-time flag.

### Proof of Concept

1. Attacker connects to a victim node as a peer via the Peras object-diffusion mini-protocol.
2. Attacker observes that the victim's current chain tip is at block number N.
3. Attacker identifies a block B at block number M < N that is in the victim's VolatileDB (e.g., a recently orphaned fork block).
4. Attacker crafts `PerasCert { pcCertRound = freshRound, pcCertBoostedBlock = blockPoint B }` with a `vpcCertBoost` value W such that `M + W > N` (overcoming the honest chain's length advantage).
5. Attacker sends this certificate to the victim via the object-diffusion protocol.
6. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = W }` unconditionally.
7. The certificate is added to `PerasCertDB`; `chainSelSync` calls `chainSelectionForBlock` for block B.
8. `constructPreferableCandidates` computes `weightedSelectView` for the fork containing B; its `wsvTotalWeight = M + W > N`, so `preferAnchoredCandidate` returns `ShouldSwitch`.
9. `switchTo` commits the fork as the new chain, rolling back the honest tip.
10. The victim node now tracks a non-canonical chain chosen by the attacker.
