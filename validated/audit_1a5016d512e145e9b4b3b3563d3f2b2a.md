### Title
Stale (Empty) Peras Weight Snapshot in `checkPreferTheirsOverOurs` Enables Chain-Selection Bypass — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client hardcodes `emptyPerasWeightSnapshot` when comparing a peer's candidate chain against the node's current chain beyond the forecast horizon. This is structurally identical to the external report's root cause: a critical comparison is performed against stale (empty) state instead of the current state. When Peras is active, the comparison ignores all certificate boosts, causing a node to incorrectly disconnect from peers offering a legitimately heavier canonical chain and remain on an adversary-supplied lighter fork.

---

### Finding Description

When a header arrives beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to stay connected to the peer. If the peer's chain is judged "not preferable," the client throws `CandidateTooSparse` and disconnects. [1](#0-0) 

The comparison is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        emptyPerasWeightSnapshot   -- ← hardcoded empty; ignores all cert boosts
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

The `emptyPerasWeightSnapshot` constant contains no boosted points at all. [2](#0-1) 

The actual live snapshot is available via `getPerasWeightSnapshot` on the `PerasCertDB`, which is already used everywhere else in chain selection: [3](#0-2) 

`preferAnchoredCandidate` with a non-empty snapshot computes total weight as `blockNo + weightBoost`; with an empty snapshot it degrades to a pure block-count comparison: [4](#0-3) 

The TODO comment in the source acknowledges the problem but does not fix it:

```
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
emptyPerasWeightSnapshot
``` [5](#0-4) 

The structural parallel to the external report is exact: just as `uniClaimDeposit` minted shares against a stale `totalSupplyAmount` (before calling `accrue`), `checkPreferTheirsOverOurs` evaluates chain preference against a permanently-stale (always-zero) weight snapshot instead of the current one.

---

### Impact Explanation

Under Peras, a chain's canonical weight is `blockNo + Σ(cert boosts)`. A chain with fewer blocks but large certificate boosts can be strictly heavier than a longer chain with no boosts.

With `emptyPerasWeightSnapshot`, `checkPreferTheirsOverOurs` reduces to a pure block-count comparison. An adversary can exploit this as follows:

1. The adversary mines a fork with more blocks but zero Peras boosts.
2. The victim node adopts this fork (it is longer by block count).
3. Honest peers serve the canonical chain, which has fewer blocks but large Peras boosts making it heavier.
4. When honest peers' headers are beyond the forecast horizon, `checkPreferTheirsOverOurs` fires.
5. Using `emptyPerasWeightSnapshot`, the canonical chain appears "not preferable" (fewer blocks).
6. The victim disconnects from all honest peers (`CandidateTooSparse`).
7. The victim remains on the adversary's lighter, non-canonical fork.

This is a chain-selection error: an honest node is made to prefer a non-canonical, less-secure chain. It maps to the "High" impact tier: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.* [6](#0-5) 

---

### Likelihood Explanation

- **Peras must be enabled.** Peras is currently disabled by default (`emptyPerasWeightSnapshot` is the no-op path), so this is not exploitable on today's mainnet. Once Peras is activated, the condition becomes reachable.
- **Forecast horizon must be exceeded.** This occurs when there is a large slot gap between the intersection point and the peer's tip — a realistic scenario during syncing or after a long period of no blocks.
- **Adversary needs a longer-by-block-count fork.** No stake majority or key compromise is required; the adversary only needs to produce more blocks than the canonical chain has at the moment of the check.
- The code path is reachable by any unprivileged peer via the standard ChainSync mini-protocol.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from `PerasCertDB.getWeightSnapshot`. Since `checkPreferTheirsOverOurs` already executes inside an `STM` block (`readLedgerStateHelper` calls `atomically`), the snapshot can be read atomically alongside the other state:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot  -- read live snapshot
  if shouldSwitch $ preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
    then pure ()
    else throwSTM $ CandidateTooSparse ...
```

`getPerasWeightSnapshot` is already threaded through `ChainDbView` and used in every other chain-selection call site. [7](#0-6) 

Alternatively, if the check is to be removed entirely (as the TODO suggests), the removal should be accompanied by a proof that the remaining chain-selection logic is sufficient to prevent a node from staying connected to a peer whose chain can never be adopted.

---

### Proof of Concept

Private-testnet sequence (requires Peras enabled):

1. Configure a two-node private testnet with Peras active and a non-trivial certificate boost value.
2. Node A (victim) syncs from adversary node X, which serves a fork `F_adv` of length `L+1` blocks with zero Peras boosts.
3. Node A adopts `F_adv`.
4. Honest node B serves the canonical fork `F_canon` of length `L` blocks but with one Peras certificate boosting a block, giving `F_canon` total weight `L + boost > L + 1`.
5. Advance the slot clock so that B's next header is beyond the forecast horizon of A's intersection with `F_canon`.
6. Observe: `checkPreferTheirsOverOurs` fires on A; with `emptyPerasWeightSnapshot`, `F_canon` has apparent weight `L < L+1`; A throws `CandidateTooSparse` and disconnects from B.
7. Node A remains on `F_adv` (the lighter, non-canonical fork) indefinitely while B is disconnected. [8](#0-7) [9](#0-8)
