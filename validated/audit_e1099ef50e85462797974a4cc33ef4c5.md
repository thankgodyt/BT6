Audit Report

## Title
Missing `assert_one_yocto()` in `update_transfer_fee` Enables Function Call Key to Inflate Token Fee on Pending Transfer — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`update_transfer_fee` is `#[payable]` but contains no `assert_one_yocto()` guard. When the native-fee component is unchanged (`diff_native_fee == 0`), the deposit requirement resolves to exactly 0 yoctoNEAR, which a NEAR Function Call key can satisfy. A malicious or compromised dApp frontend holding a stored Function Call key for the bridge contract can silently inflate the token-fee field on any pending transfer belonging to the key's owner to `amount - 1`, causing the relayer to deliver 1 token unit to the destination chain while claiming the remainder as fee.

## Finding Description

`update_transfer_fee` at lines 386–436 of `near/omni-bridge/src/lib.rs` enforces the deposit constraint dynamically:

```rust
let diff_native_fee = fee.native_fee.0
    .checked_sub(current_fee.native_fee.0)
    .near_expect(BridgeError::LowerFee);

require!(
    NearToken::from_yoctonear(diff_native_fee) == env::attached_deposit(),
    BridgeError::InvalidAttachedDeposit.as_ref()
);
```

When an attacker submits `fee.native_fee == current_fee.native_fee`, `diff_native_fee` is `0`, so `env::attached_deposit()` must equal `NearToken::from_yoctonear(0)`. NEAR Function Call keys are protocol-level keys that can only sign transactions with **zero** attached deposit; they cannot attach any NEAR. A zero-deposit call therefore satisfies this check and is fully executable by a Function Call key.

The only other guard is the sender check at lines 404–409:

```rust
require!(
    fee.fee == current_fee.fee
        || OmniAddress::Near(env::predecessor_account_id()) == transfer.message.sender,
    BridgeError::SenderCanUpdateTokenFeeOnly.as_ref()
);
```

Because the Function Call key is scoped to the user's own account, `env::predecessor_account_id()` equals the transfer's `sender`, so this check passes unconditionally. The fee ceiling `fee.fee < transfer.message.amount` allows the attacker to set `fee.fee = amount - 1`.

After the fee is written, `sign_transfer` (lines 444–521) calls `transfer_message.amount_without_fee()`, which yields `1`. The MPC signer signs a payload for 1 token unit to the destination address. The relayer then claims `amount - 1` tokens as fee via `claim_fee`.

## Impact Explanation

This is a concrete instance of **fee mis-accounting / balance manipulation that changes user balances**, an explicitly listed Critical impact. Tokens already locked or burned in `init_transfer_internal` on the NEAR side are effectively stolen: the user receives 1 token unit on the destination chain while the relayer collects `transfer.amount - 1` as fee. No admin access, MPC compromise, or validator collusion is required.

## Likelihood Explanation

The attack requires three realistic conditions: (1) the user previously signed in to any dApp that requested a Function Call key for the omni-bridge contract — standard NEAR dApp onboarding; (2) that dApp is malicious or later compromised (e.g., via XSS or supply-chain attack on the frontend); (3) the user has a pending transfer. All three are plausible for an active bridge with real users. The attacker needs no privileged role, no leaked Full Access key, and no MPC access. The attack is repeatable for every pending transfer visible on-chain.

## Recommendation

Add `assert_one_yocto()` at the top of `update_transfer_fee`, consistent with the pattern already used in `storage_withdraw` and `storage_unregister`:

```rust
#[payable]
#[pause]
pub fn update_transfer_fee(&mut self, transfer_id: TransferId, fee: UpdateFee) {
    assert_one_yocto();
    // existing logic — adjust diff_native_fee check:
    // diff_native_fee = fee.native_fee.0.checked_sub(current_fee.native_fee.0)
    // attached_deposit check must subtract the mandatory 1 yocto before comparing,
    // or restructure to treat the 1 yocto as a separate authentication deposit.
```

This forces the call to require a non-zero deposit, which Function Call keys cannot provide, blocking the attack entirely.

## Proof of Concept

1. User signs in to `bridge-dapp.example`; browser stores a Function Call key for `omni-bridge.near` on the user's NEAR account.
2. User calls `ft_transfer_call` on their NEP-141 token contract, sending `1_000_000` tokens to `omni-bridge.near` with `msg = InitTransferMsg { recipient: "eth:0xVictim", fee: { fee: 0, native_fee: 0 } }`. Transfer stored with `transfer_id = T`.
3. Compromised `bridge-dapp.example` uses the stored Function Call key to call:
   ```json
   {
     "method": "update_transfer_fee",
     "args": { "transfer_id": "T", "fee": { "Fee": { "fee": "999999", "native_fee": "0" } } },
     "deposit": "0"
   }
   ```
   - `diff_native_fee = 0 - 0 = 0` → `attached_deposit == 0` ✓
   - `predecessor == sender` ✓
   - `999999 >= 0 && 999999 < 1000000` ✓
   - No `assert_one_yocto()` → call succeeds with Function Call key.
4. Relayer calls `sign_transfer(T, ...)`. `amount_without_fee = 1_000_000 - 999_999 = 1`. MPC signs payload for 1 token to `0xVictim`.
5. On the destination chain, `finTransfer` delivers 1 token unit to the user. Relayer claims 999,999 tokens as fee via `claim_fee`.

A local integration test can reproduce step 3 by calling `update_transfer_fee` with `attached_deposit = NearToken::from_yoctonear(0)` and `fee.fee = amount - 1` while `fee.native_fee` is unchanged, then asserting the stored fee equals `amount - 1` and `amount_without_fee() == 1`.
