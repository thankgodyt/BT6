Audit Report

## Title
Floor Division in `normalize_amount` Permanently Freezes Funds When Net Transfer Amount Is Below Decimal Normalization Unit — (`near/omni-bridge/src/lib.rs`)

## Summary

When a NEAR-originated transfer involves a token whose `origin_decimals` exceeds `dest_decimals`, any net transfer amount (after fee) smaller than `10^(origin_decimals − dest_decimals)` normalizes to zero via floor division in `normalize_amount`. The user's tokens are already burned or locked by `init_transfer_internal` before this check occurs. When a relayer subsequently calls `sign_transfer`, the zero-amount check panics and the transfer message remains in `pending_transfers` indefinitely with no public cancel or refund path.

## Finding Description

`init_transfer` validates only that `fee < amount` at lines 554–557, with no check that the normalized net amount is non-zero. Control then passes to `init_transfer_internal`, which at lines 1850–1857 calls `burn_tokens_if_needed` and `lock_tokens_if_needed` on the full `transfer_message.amount` — tokens are gone at this point.

Later, a trusted relayer calls `sign_transfer`. At lines 471–485, it fetches `decimals` for the destination token and calls `normalize_amount(amount_without_fee, decimals)`. `normalize_amount` at lines 2784–2787 performs integer floor division: `amount / 10^(origin_decimals − dest_decimals)`. If `amount_without_fee < 10^diff`, the result is `0` and `require!(amount_to_transfer > 0, ...)` panics — the cross-chain signing promise is never dispatched.

Because `sign_transfer_callback` at lines 655–658 is the only place that calls `remove_transfer_message` (and only on success), the transfer message is never cleaned up. No public cancel or user-initiated refund function exists for NEAR-originated pending transfers, confirmed by the absence of any such entry point in the contract.

## Impact Explanation

This is a concrete instance of **permanent freezing of bridged funds** — a Critical impact class. For any token registered with `origin_decimals > dest_decimals` (the standard NEAR-24 → EVM-18 configuration gives `diff = 6`, divisor = 1,000,000), any user who initiates a transfer with `amount_without_fee < 1,000,000` base units will have their tokens permanently burned or locked with no recovery path. The funds are not recoverable by the user, the relayer, or any non-admin party.

## Likelihood Explanation

Medium. The triggering condition requires only that a user submits a transfer whose net amount falls below the decimal normalization unit. The `init_transfer` guard (`fee < amount`) does not prevent this. A user unaware of the decimal difference, or one who sets a fee close to the transfer amount, can trigger this through a normal `ft_transfer_call` flow. The 24→18 decimal configuration is the standard NEAR-to-EVM setup, making this a realistic scenario. The amounts involved are small (sub-unit), but the loss is total and permanent for the affected transfer.

## Recommendation

Add a pre-flight normalization check in `init_transfer` (or at the start of `init_transfer_internal`) before tokens are burned or locked. The destination token's `Decimals` must be fetched and the following assertion enforced:

```rust
require!(
    Self::normalize_amount(amount_without_fee, decimals) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing check in `sign_transfer` at lines 482–485 but must be enforced **before** `burn_tokens_if_needed` and `lock_tokens_if_needed` are called.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 18` (divisor = 1,000,000).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes: `0 < 500_000`. ✓
4. `init_transfer_internal` burns 500,000 base units and stores the transfer message. Tokens are gone.
5. Relayer calls `sign_transfer(transfer_id, None, None)`.
6. `normalize_amount(500_000, {24, 18})` = `500_000 / 1_000_000` = `0`.
7. `require!(0 > 0, ...)` panics → `ERR_INVALID_AMOUNT_TO_TRANSFER`.
8. `sign_transfer_callback` is never reached; `remove_transfer_message` is never called.
9. Transfer message stays in `pending_transfers` forever. User's 500,000 base units are permanently burned.

A local integration test can reproduce this by: (a) deploying the bridge contract with a mock token registered at 24/18 decimals, (b) calling `ft_transfer_call` with the above parameters, (c) calling `sign_transfer` as a trusted relayer, and (d) asserting the panic and confirming the transfer message persists in storage while the token balance is reduced.
