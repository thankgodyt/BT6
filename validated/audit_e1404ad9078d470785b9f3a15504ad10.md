The report describes an **asymmetric state manipulation** bug where a "flat reference price" (oracle) is used instead of computing from actual pool state, allowing bypass of intended constraints. The analog in consensus would be a **ledger-view/forecast** that uses a stale or flat reference rather than actual current state, or a **chain selection** mechanism that can be manipulated via asymmetric inputs.

### Title
Peras Certificate Validation Stub Unconditionally Accepts All Certificates, Enabling Unauthorized Chain Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` (success) without performing any cryptographic or quorum verification. An unprivileged peer can send a crafted `PerasCert` boosting any block on an adversarial fork; the node will accept it, apply a weight boost to that fork, and may switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` default instance in `SupportsPeras.hs` is the only instance wired into the production diffusion path. Its `validatePerasCert` implementation is a placeholder that skips all validation:

```haskell

  Right
    ValidatedPerasCert

      , vpcCertBoost = perasWeight params
      }

This stub is directly invoked in the production inbound certificate processing path in `ObjectPool/PerasCert.hs`:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls this validator on every inbound certificate from a peer. Because it always returns `Right`, any certificate — regardless of whether it carries a valid BLS aggregate signature, valid voter eligibility proofs, or a legitimate quorum — is accepted and forwarded to `ChainDB.addPerasCertAsync`. [3](#0-2) 

Once accepted, `chainSelSync` in `ChainSel.hs` processes the certificate and triggers chain selection for the boosted block: [4](#0-3) 

The weight boost is applied via `weightBoostOfFragment`, which sums all boosted points on a candidate fragment: [5](#0-4) 

Chain selection then compares `wsvTotalWeight` (block number + weight boost) between the current chain and the candidate: [6](#0-5) 

A sufficiently large forged boost (`perasWeight params`, a fixed protocol parameter) can make an adversarial fork's total weight exceed the honest chain's, causing `preferCandidate` to return `ShouldSwitch`.

**Analog to the DEX bug:** The DEX geometric pool uses a flat oracle price independent of actual pool balances, allowing a virtual swap that bypasses price-impact constraints. Here, `validatePerasCert` uses a flat acceptance independent of actual certificate content, allowing a virtual quorum that bypasses the BLS aggregate signature and committee eligibility checks. In both cases, a reference value (oracle price / `perasWeight params`) is applied unconditionally, irrespective of whether the underlying state (pool reserves / cryptographic proof) justifies it.

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block on an adversarial fork as the boosted block. The node will:
1. Accept the certificate without verifying the BLS aggregate signature or voter eligibility.
2. Store it in `PerasCertDB` and trigger chain selection.
3. Apply a weight boost equal to `perasWeight params` to the adversarial fork.
4. Potentially switch to the adversarial chain if its boosted total weight exceeds the honest chain's.

This is a **Critical** bypass of Peras certificate/vote verification that enables unauthorized certificate acceptance and can cause an honest node to prefer a non-canonical chain — a consensus safety failure reachable by any unprivileged peer.

---

### Likelihood Explanation

The inbound certificate path is active whenever the Peras object diffusion mini-protocol is enabled. Any peer that can send `PerasCert` objects (no stake or key material required) can trigger this. The attacker only needs to know the `Point` of a block on an adversarial fork and the current `PerasRoundNo`. The boost magnitude is fixed at `perasWeight params`, a known protocol parameter. Likelihood is **High** once Peras is deployed on a network where this stub remains in place.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the BLS aggregate signature (`pcSignature`) over the canonical message `hash(pcRoundNo, pcBoostedBlock)` using the aggregated verification keys of the claimed voters.
2. Verifies each voter's VRF eligibility proof against the epoch nonce and committee selection parameters.
3. Checks that the total stake of the verified voters meets the quorum threshold (`perasQuorumStakeThreshold`).

Until the real implementation is in place, the inbound certificate path should reject all certificates (return `Left PerasValidationErr`) rather than accept them unconditionally.

---

### Proof of Concept

1. Node A is running with Peras enabled. Its current chain tip is at block `H` (honest chain, block number `N`).
2. Attacker constructs an adversarial fork with tip at block `A` (block number `N-1`) and a boosted block `B` somewhere on that fork.
3. Attacker sends a `PerasCert { pcRoundNo = r, pcBoostedBlock = point(B), pcVoters = <arbitrary>, pcSignature = <arbitrary> }` to node A.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcBoost = perasWeight params }`.
5. `chainSelSync` triggers chain selection for block `B`; `weightBoostOfFragment` adds `perasWeight params` to the adversarial fork's weight.
6. If `perasWeight params` is large enough (e.g., the default `PerasWeight 15` on a fork only 14 blocks shorter), `preferCandidate` returns `ShouldSwitch` and the node adopts the adversarial chain. [7](#0-6) [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
