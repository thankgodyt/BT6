### Summary

`getVotingCommitteeForElection` is declared, typed, and exported from `Ouroboros.Consensus.Committee.AcrossEpochs`, but its body is `error "TODO: implement getVotingCommitteeForElection"`. Every call to this function unconditionally throws an `ErrorCall` exception at runtime. Because this is the sole mechanism for resolving which `VotingCommittee` applies to a given `ElectionId` across epoch boundaries, any code path that invokes it — including Peras vote and certificate validation — will either crash the calling thread or, if the exception is caught and silently treated as `Nothing`, silently bypass the committee check entirely.

Despite the `do`-notation and the `Maybe` return type, `error` is not a `Maybe` value — it is a pure Haskell exception (`ErrorCall`) that escapes the `Maybe` monad and propagates up the call stack as an impure exception. The function is unconditionally broken for every possible input.

The surrounding module is purpose-built to support cross-epoch vote and certificate validation: `InterEpochVotingCommittee` stores both the current and previous epoch's `VotingCommittee`, and `getVotingCommitteeForElection` is the only exported function that maps an `ElectionId` to the correct committee. ---

### Impact Explanation

Two distinct failure modes exist depending on how the caller handles the exception:

1. **Committee-check bypass (Critical/High):** If the caller wraps the invocation in a generic exception handler and interprets the failure as `Nothing` (no committee found), the Peras vote or certificate is accepted without any committee-membership or signature verification. This is a direct bypass of Peras voting/certificate checks.

2. **Thread crash:** If the `ErrorCall` propagates unhandled, the validation thread terminates. Depending on supervisor logic, this can cause the node to permanently fail to process Peras votes or certificates for any cross-epoch election, breaking the Peras safety property that requires a quorum of committee signatures.

Both outcomes stem from the same root cause: the function body is a stub that was never implemented.

---

### Likelihood Explanation

**Medium.** The function is exported and is the only path through which cross-epoch committee resolution can occur. Any production deployment that activates the Peras protocol and receives a vote or certificate referencing an `ElectionId` from a prior epoch will trigger this code path. The Peras diffusion layer and certificate/vote handlers are already wired into the diffusion stack, so an unprivileged peer can craft or relay a valid-looking Peras object that exercises this path without any special privileges.

---

### Recommendation

Implement `getVotingCommitteeForElection` to correctly resolve the `ElectionId` against both `currEpochVotingCommittee` and `prevEpochVotingCommittee` in the `InterEpochVotingCommittee` record, returning `Nothing` only when the election genuinely does not correspond to either stored committee. Until the implementation is complete, the function should not be exported or called from any production validation path.
