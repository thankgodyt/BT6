### Title
`safe_mint` Mints nBTC to Bridge Before Verifying Recipient Registration, Creating Permanent Supply Inflation and Stuck User Funds — (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge's own account before checking whether the intended recipient is registered. If the recipient is unregistered, the function returns `U128(0)` without transferring, leaving the minted tokens permanently stuck in the bridge's account. This inflates the total supply without a corresponding user balance and creates a stuck bridge state requiring operator intervention.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124) executes in this order:

1. **Mint unconditionally to bridge** — `self.token.internal_deposit(&self.bridge_id, amount.into())` at line 112 increases both the bridge's balance and the global total supply by `amount`.
2. **Check recipient registration** — `self.token.accounts.get(&account_id).is_none()` at line 114.
3. **Early return on unregistered account** — `return PromiseOrValue::Value(U128(0))` at line 115, with no transfer and no burn. [1](#0-0) 

The minted tokens remain in the bridge's account. The total supply is permanently inflated by `amount` with no corresponding user balance. There is no subsequent burn or recovery path inside `safe_mint` itself.

This is the direct analog of the ERC20 `approve` race condition described in the report: in both cases a state mutation (allowance set / tokens minted) is committed before all preconditions are verified, leaving the system in an inconsistent intermediate state that cannot self-correct.

The `safe_mint` function is `pub` and gated only by `assert_bridge()`: [2](#0-1) [3](#0-2) 

The bridge contract is the sole caller. The bridge invokes `safe_mint` as part of the deposit flow after proof verification. If the depositing user's NEAR account is not registered in the nBTC contract (a separate NEP-141 `storage_deposit` step), the bridge triggers this path.

---

### Impact Explanation

**Medium — Stuck bridge state requiring operator intervention.**

- The user's BTC is locked in the Bitcoin network (the deposit was verified and accepted).
- The corresponding nBTC is minted to the bridge's account but never delivered to the user.
- The nBTC total supply is inflated by `amount` with no backing user balance, violating the 1:1 BTC-to-nBTC invariant.
- Recovery requires privileged operator action: either manually transferring the stuck tokens to the user after they register, or calling `burn` to deflate the supply — neither of which is automated.

This matches the allowed impact: *"stuck bridge state requiring operator intervention"* and *"permanent burning below backed supply."*

---

### Likelihood Explanation

**Low–Medium.** NEP-141 storage registration is a prerequisite that is separate from the deposit action. New users unfamiliar with NEAR's storage model may deposit BTC without first calling `storage_deposit` on the nBTC contract. The bridge does not enforce registration before calling `safe_mint`, and `safe_mint` itself does not enforce it before minting. Any such deposit silently triggers the stuck state.

---

### Recommendation

Reorder the check and the mint: verify that `account_id` is registered **before** calling `internal_deposit`. If the account is not registered, either revert the call entirely (forcing the caller to register first) or auto-register the account before minting.

```rust
// Correct ordering
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // no mint has occurred yet
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

Alternatively, auto-register:
```rust
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_register_account(&account_id);
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

---

### Proof of Concept

1. User deposits BTC to the bridge without calling `storage_deposit` on the nBTC contract (account unregistered).
2. Bridge proof-verifies the deposit and calls `safe_mint(user_account, amount, None)` on the nBTC contract.
3. `internal_deposit(&self.bridge_id, amount)` executes — bridge balance increases by `amount`, total supply increases by `amount`. [4](#0-3) 
4. `self.token.accounts.get(&user_account).is_none()` returns `true`. [5](#0-4) 
5. Function returns `U128(0)` — no transfer, no burn.
6. Result: `amount` nBTC is permanently stuck in the bridge's account; total supply is inflated; user's BTC is locked with no corresponding nBTC balance; operator must intervene manually.
