### Title
Hardcoded `mkPerasParams` Used Instead of Node Configuration in Peras Certificate Validation, Combined with Stub That Always Accepts Any Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass a hardcoded default `mkPerasParams` to `validatePerasCert` instead of the actual node's Peras configuration. Compounding this, the `validatePerasCert` implementation is a stub that unconditionally returns `Right` for any certificate, performing no cryptographic or semantic checks. Any unprivileged peer can therefore inject arbitrary Peras certificates that are accepted without validation, stored in the `PerasCertDB`, and used to boost arbitrary blocks during chain selection.

---

### Finding Description

In `PerasCert.hs`, both pool-writer constructors call:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [1](#0-0) [2](#0-1) 

Neither function accepts the actual Peras configuration as a parameter; instead, a hardcoded default `mkPerasParams` is substituted. This is the direct analog to the external report's bug: a wrong/default variable is used in place of the correct runtime value.

The `validatePerasCert` implementation (the degenerate `StandardHash blk` instance) is a stub that unconditionally returns `Right` regardless of the certificate's content:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [3](#0-2) 

No committee membership check, no cryptographic signature verification, and no quorum check is performed. The `params` argument is used only to extract `perasWeight params` for the boost value — and even that value is wrong because `mkPerasParams` is a hardcoded default rather than the node's actual configuration.

The `processCerts` function, which is the entry point for inbound peer certificates, calls this stub validator and, on success, stores the certificate via `addCert`: [4](#0-3) 

Stored certificates are then surfaced through `getWeightSnapshot` and used directly in chain selection comparisons via `preferAnchoredCandidate`: [5](#0-4) [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can craft and send Peras certificates for any block — including blocks on a minority or adversarial fork. Because `validatePerasCert` always returns `Right`, these certificates pass validation, are stored in the `PerasCertDB`, and their boost weight (derived from the wrong hardcoded `mkPerasParams`) is applied during chain selection. This allows a peer to make an honest node prefer a non-canonical chain by artificially boosting a fork's weight beyond the honest chain's weight, constituting a chain-selection safety failure.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer without authentication. The `opwAddObjects` callback in `makePerasCertPoolWriterFromChainDB` is invoked directly on inbound certificate batches. No stake, key, or privilege is required to trigger the vulnerable path. The only prerequisite is a peer connection, which is standard for any Cardano node.

---

### Recommendation

1. **Pass the actual Peras configuration** as a parameter to `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`, replacing the hardcoded `mkPerasParams`. This mirrors the fix in the external report: use the correct runtime value instead of a default placeholder.

2. **Implement real validation** in `validatePerasCert` before the Peras certificate diffusion path is enabled in production. The stub must verify committee membership, cryptographic signatures, and quorum thresholds before returning `Right`.

3. Until both fixes are in place, the object-diffusion endpoint for Peras certificates should not be exposed to untrusted peers.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to a node running the Peras object-diffusion mini-protocol.
2. Peer sends a batch of `PerasCert blk` values with arbitrary `pcCertRound` and `pcCertBoostedBlock` fields pointing to a fork block.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` for each certificate.
4. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
5. Each certificate is stored in `PerasCertDB` via `addCert`.
6. `implGetWeightSnapshot` returns a `PerasWeightSnapshot` that now includes boost weight for the attacker-chosen fork block.
7. On the next chain selection event, `preferAnchoredCandidate` uses this snapshot and may prefer the boosted fork over the honest chain. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
