### Title
Unprivileged Caller Can Redirect Any Unfinalized BTC Deposit Refund to an Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is a public function that accepts a caller-supplied `refund_address` (BTC address) with no check that the caller is the original depositor (`deposit_msg.recipient_id`). Any unprivileged NEAR account can submit a refund request for any unfinalized deposit and redirect the BTC to an attacker-controlled Bitcoin address.

### Finding Description
`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` (lines 510–535) is callable by any NEAR account. It accepts a `deposit_msg` (which encodes the intended recipient) and a separate `refund_address` (the BTC address to receive the refund). The only address-matching check is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This check is skipped entirely when `deposit_msg.refund_address` is `None` — the common case for standard deposits. There is no check that `env::predecessor_account_id() == deposit_msg.recipient_id`. The `request_refund_callback` (refund.rs lines 497–581) only verifies that the BTC transaction is included in the blockchain and that the output script matches the deposit address derived from `deposit_msg`. It does not verify the caller's identity.

The `deposit_msg` is not secret: it is hashed to derive the deposit address, and is typically embedded in the BTC transaction's OP_RETURN output (or observable from the relayer's public NEAR calls). An attacker can reconstruct it from the public Bitcoin blockchain.

### Impact Explanation
An attacker who observes an unfinalized BTC deposit can:
1. Extract the `deposit_msg` from the Bitcoin transaction's OP_RETURN.
2. Call `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)` before the legitimate user does.
3. After `unsafe_refund_timelock_sec` elapses (without DAO/Operator rejection), call `execute_refund`.
4. The bridge MPC signs a Bitcoin transaction sending the deposited BTC to the attacker's address.

This constitutes direct theft of user BTC funds — a Critical impact matching "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

### Likelihood Explanation
The `deposit_msg` is observable from the public Bitcoin blockchain (OP_RETURN) or from the relayer's public NEAR transactions. The attack window is any deposit that has not yet been finalized via `verify_deposit`. The only mitigation is the `unsafe_refund_timelock_sec` delay plus DAO/Operator rejection, which is an operational control, not a code-level guard. If the DAO/Operator is slow, unavailable, or overwhelmed by multiple simultaneous malicious requests, the attack succeeds. Likelihood is Medium.

### Recommendation
Add an authorization check in `internal_request_refund` (or its callback) requiring that the caller is the `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id
        || self.acl_has_any_role(vec![Role::DAO.into(), Role::Operator.into()], env::predecessor_account_id()),
    "Only the deposit recipient or a privileged role can request a refund"
);
```

This mirrors the fix recommended in the external report: instead of allowing an arbitrary address to be passed in by any caller, restrict who can initiate the refund and to which address.

### Proof of Concept

1. Alice sends 0.1 BTC to the bridge deposit address derived from `deposit_msg = {"recipient_id": "alice.near"}` (with `refund_address: None`). The deposit is not yet finalized.
2. Attacker Bob reads the Bitcoin transaction from the public blockchain, extracts the `deposit_msg` from the OP_RETURN, and obtains `tx_bytes` and a valid `proof`.
3. Bob calls:
   ```
   request_refund(
     deposit_msg = {"recipient_id": "alice.near"},
     refund_address = "bc1q_bob_address",
     tx_bytes = <alice's tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
4. Since `deposit_msg.refund_address` is `None`, the address check at refund.rs line 154–158 is skipped. The refund request is stored with `refund_address = "bc1q_bob_address"`.
5. After `unsafe_refund_timelock_sec` passes (assuming DAO/Operator does not reject), Bob calls `execute_refund`.
6. The bridge builds and MPC-signs a Bitcoin transaction paying Alice's 0.1 BTC (minus gas fee) to Bob's address. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }

    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );
