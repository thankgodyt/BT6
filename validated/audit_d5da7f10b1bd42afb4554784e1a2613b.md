Audit Report

## Title
Reentrancy via Malicious ERC1155 `safeTransferFrom` in `initTransfer1155` Enables Unauthorized Token Minting on NEAR — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` makes an external call to an attacker-controlled ERC1155 contract before emitting `InitTransfer`, with no `nonReentrant` guard. A malicious ERC1155 token can reenter `initTransfer1155` directly from within its `safeTransferFrom` implementation, causing N distinct `InitTransfer` events to be emitted with unique nonces but zero actual token deposits. The NEAR side treats each emitted event as proof of a locked deposit and mints the full `amount` for each, constituting unauthorized minting of bridged funds.

## Finding Description

`initTransfer1155` (lines 439–490) executes in this order:

1. `currentOriginNonce += 1` — state increment
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — **external call to attacker-controlled contract**
3. `initTransferExtension(...)` — internal (publishes Wormhole VAA in `OmniBridgeWormhole`)
4. `emit BridgeTypes.InitTransfer(...)` — event emission

The `onERC1155Received` guard (lines 522–535) checks `operator != address(this)` and reverts on direct ERC1155 sends. This guard is entirely irrelevant to the attack: a malicious ERC1155 token's `safeTransferFrom` is not required by any standard to call `onERC1155Received` on the recipient. The malicious token can instead call `bridge.initTransfer1155(...)` directly from within its `safeTransferFrom` body, bypassing the guard completely.

Because `currentOriginNonce` is incremented at the top of each call, each reentrant invocation receives a fresh, unique nonce. The `InitTransfer` event is emitted at the bottom of each stack frame, so N reentrant calls produce N distinct `InitTransfer` events — each with a different `originNonce` and an arbitrary `amount` — while the bridge holds zero actual ERC1155 tokens.

`logMetadata1155` (lines 234–270) carries no access-control modifier, so any user can register a malicious ERC1155 token without admin involvement.

In `OmniBridgeWormhole`, `initTransferExtension` (lines 118–150) calls `_wormhole.publishMessage` for each stack frame, meaning each reentrant invocation also posts a Wormhole VAA that the NEAR side will independently accept and process.

The CLAUDE.md invariant is explicit: *"InitTransfer must only be emitted in a code path where tokens have already been burned/locked in the same transaction."* Incrementing `currentOriginNonce` before the external call does not satisfy this invariant — it only ensures each reentrant call gets a distinct nonce, which the NEAR side treats as independent, valid transfers.

## Impact Explanation

Each emitted `InitTransfer` event is a real on-chain event. The NEAR light-client or Wormhole prover verifies each one as valid and the NEAR bridge mints the full `amount` to the attacker's NEAR address for each event. N reentrant calls produce N minting operations on NEAR while the bridge holds zero ERC1155 collateral. This is unauthorized minting and theft of bridged funds — a concrete match for the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

## Likelihood Explanation

The attack requires no admin access, no private key compromise, and no validator collusion. The attacker only needs to: (1) deploy a malicious ERC1155 contract, (2) call the permissionless `logMetadata1155` to register it, (3) wait for NEAR to deploy the corresponding token via standard bridge flow, and (4) call the public `initTransfer1155`. All entry points are unprivileged public functions. The attack is repeatable and scalable. Likelihood is high.

## Recommendation

1. Import `ReentrancyGuardUpgradeable` from OpenZeppelin and apply `nonReentrant` to `initTransfer1155` (and `initTransfer` for defense-in-depth). Update the storage gap accordingly.
2. Alternatively, restructure `initTransfer1155` to follow strict CEI: record the pre-call ERC1155 balance of the bridge, perform `safeTransferFrom`, assert the post-call balance increased by exactly `amount`, then proceed to `initTransferExtension` and `emit InitTransfer`.
3. As defense-in-depth, add a registry check in `initTransfer1155` requiring the token to have been previously registered via `logMetadata1155` (i.e., `multiTokens[deterministicToken].tokenAddress != address(0)`), which is already the case for the deterministic address mapping but should be enforced as a hard revert.

## Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface IBridge {
    function initTransfer1155(
        address tokenAddress, uint256 tokenId, uint128 amount,
        uint128 fee, uint128 nativeFee,
        string calldata recipient, string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IBridge public bridge;
    uint256 public reentrancyCount;
    uint256 public constant MAX_REENTRIES = 5;

    constructor(address _bridge) { bridge = IBridge(_bridge); }

    // Called by bridge during initTransfer1155 → safeTransferFrom
    function safeTransferFrom(
        address, address, uint256 tokenId, uint256, bytes calldata
    ) external {
        if (reentrancyCount < MAX_REENTRIES) {
            reentrancyCount++;
            // Reenter with inflated amount; onERC1155Received is never called
            bridge.initTransfer1155(
                address(this), tokenId, 1_000_000e18, 0, 0, "attacker.near", ""
            );
        }
        // Never transfers any tokens
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1e30; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function supportsInterface(bytes4) external pure returns (bool) { return true; }
}

// Steps:
// 1. Deploy MaliciousERC1155(bridgeAddress)
// 2. bridge.logMetadata1155(maliciousERC1155, tokenId)  ← no access control
// 3. Wait for NEAR to deploy the corresponding token
// 4. bridge.initTransfer1155(maliciousERC1155, tokenId, 1, 0, 0, "attacker.near", "")
//    → 6 InitTransfer events emitted (1 + 5 reentrant), each with a unique nonce
//    → NEAR mints 5 × 1_000_000e18 + 1 tokens to attacker.near
//    → Bridge holds 0 actual ERC1155 tokens
```

The `onERC1155Received` guard is never triggered because the malicious token's `safeTransferFrom` calls `initTransfer1155` directly rather than invoking the ERC1155 receiver callback. A local Foundry test can confirm this by deploying `MaliciousERC1155` against a fork of `OmniBridge`, calling `initTransfer1155`, and asserting that more than one `InitTransfer` event is emitted per transaction.
