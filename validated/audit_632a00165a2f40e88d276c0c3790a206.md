### Title
Incomplete `validatePerasVote` Allows Unauthorized Peras Certificate Forging via Crafted Peer Votes — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasVote` function omits all cryptographic checks (BLS signature, VRF eligibility proof) and all structural checks (block existence, round validity). An unprivileged peer can send votes for any block — including non-existent or adversarial ones — that pass this incomplete validation. If enough such votes accumulate to reach quorum, a `ValidatedPerasCert` is forged locally and injected into the `ChainDB`, causing chain selection to boost a non-canonical block.

---

### Finding Description

The production inbound vote handler `makePerasVotePoolWriterFromChainDB` in `PerasVote.hs` calls:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [1](#0-0) 

This delegates to the universal `BlockSupportsPeras` instance, which is explicitly marked as a degenerate placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [2](#0-1) 

The `validatePerasVote` implementation in that instance ignores `_params` entirely and only checks stake-distribution membership:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [3](#0-2) 

The following checks are entirely absent:
- **BLS signature verification** — `pvSignature` in the concrete `V1.PerasVote` type is never verified.
- **VRF eligibility proof** — `pvEligibilityProof` for non-persistent committee members is never verified.
- **Block existence** — `pvVoteBlock` is never checked against the local chain or VolatileDB.
- **Round validity** — `pvVoteRound` is never checked against the current Peras round. [4](#0-3) 

Equally, `validatePerasCert` unconditionally accepts any certificate:

```haskell
validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [5](#0-4) 

Once `processVotes` accepts a batch of votes, each is timestamped and passed to `addVote` in the `PerasVoteDB`: [6](#0-5) 

Inside `implAddVote`, if the accumulated stake for a target crosses the quorum threshold, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` and returns `AddedPerasVoteAndGeneratedNewCert`: [7](#0-6) 

That certificate is then injected into the `ChainDB` asynchronously via `addPerasCertAsync`:

```haskell
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)
``` [8](#0-7) 

The certificate boost then influences chain selection, causing the node to prefer the boosted block.

---

### Impact Explanation

This is a **Critical** bypass of Peras voting and certificate checks. An unprivileged peer can:

1. Craft votes for an arbitrary block (e.g., a non-existent or adversarially chosen block) using any voter ID that appears in the public stake distribution.
2. Send those votes via the object-diffusion mini-protocol; `validatePerasVote` passes them because no cryptographic material is checked.
3. Accumulate enough stake-weighted votes to trigger local certificate forging for the target block.
4. The forged certificate is injected into the `ChainDB` and boosts the target block's weight in chain selection.

The result is that an honest node can be made to prefer a non-canonical or adversarially chosen chain, violating Peras's core safety guarantee. This maps directly to the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance"* and *"chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The stake distribution is public on-chain information. An attacker needs only to enumerate committee members' voter IDs (also public) and send votes on their behalf. No cryptographic key material is required because the signature check is entirely absent. The attack is executable by any peer connected to the node via the object-diffusion protocol.

---

### Recommendation

1. **Implement full cryptographic validation** in `validatePerasVote`: verify the BLS signature over `(pvVoteRound, pvVoteBlock)`, verify the VRF eligibility proof for non-persistent members, and check the voter's seat index against the committee selection context.
2. **Implement full certificate validation** in `validatePerasCert`: verify the aggregate BLS signature and the list of voters.
3. **Add structural checks**: reject votes whose `pvVoteBlock` is not present in the local VolatileDB or ImmutableDB, and reject votes whose `pvVoteRound` does not correspond to the current Peras round.
4. **Remove the universal degenerate instance** (`instance StandardHash blk => BlockSupportsPeras blk`) from production code paths, or gate it behind a compile-time flag that is disabled for production builds, to prevent it from silently being used in place of a real implementation.

---

### Proof of Concept

1. Attacker observes the public stake distribution and identifies committee member voter IDs.
2. Attacker constructs `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialPoint, pvVoteVoterId = knownVoterId }` for each of N committee members whose combined stake exceeds the quorum threshold (3/4 of total stake + safety margin).
3. Attacker sends these votes to the target node via the object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each vote; since `lookupPerasVoteStake vote stakeDistr` succeeds for known voter IDs, all votes pass.
5. `implAddVote` accumulates stake; once quorum is reached, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` for `adversarialPoint`.
6. `addPerasCertAsync` injects the certificate into the `ChainDB`.
7. Chain selection now boosts `adversarialPoint` by `perasWeight = 15` blocks, causing the node to prefer a chain containing that block over the honest canonical chain.
