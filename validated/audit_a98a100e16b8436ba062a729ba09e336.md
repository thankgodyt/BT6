### Title
Unrestricted `request_refund` Allows Any Caller to Redirect Unfinalized BTC Deposits to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no per-function `#[trusted_relayer]` guard and no `#[access_control_any]` restriction. Any unprivileged NEAR account can call it, supply an attacker-controlled `refund_address`, and create a refund request against any real but unfinalized BTC deposit. After the timelock elapses, the same attacker calls the equally unrestricted `execute_refund` to trigger the MPC signing pipeline and redirect the locked BTC to their own address.

### Finding Description

The `#[trusted_relayer]` attribute on the `impl` block at line 480 of `bridge.rs` generates relayer-management infrastructure (add/remove whitelist entries) but does **not** inject a caller-check into every method it contains. The per-function `#[trusted_relayer]` attribute is what actually enforces the whitelist check. This is confirmed by the pattern in the first `impl` block (lines 5–478): functions that must be relayer-gated each carry their own `#[trusted_relayer]` (e.g. `verify_deposit`, `verify_withdraw_v2`, `verify_refund_finalize`), while functions intentionally open to any caller (e.g. `withdraw_rbf`, `claim_lost_found`) carry none. [1](#0-0) 

In the second `impl` block, `request_refund` (line 510), `execute_refund` (line 582), and `reject_refund` (line 544) have **no** individual `#[trusted_relayer]` attribute, while `verify_refund_finalize` (line 604) and `remove_refund_pending_tx_id` (line 624) do. The contrast is deliberate for the latter two but leaves the former three unguarded. [2](#0-1) 

`request_refund` accepts a caller-supplied `refund_address`. The only restriction on this field is: if `deposit_msg.refund_address` is already set, it must match. For any deposit whose `deposit_msg.refund_address` is `None` (the common case for standard deposits), the caller freely chooses the destination BTC address. [3](#0-2) 

The `request_refund_callback` verifies only that the BTC transaction output matches the deposit address derived from `deposit_msg`; it does not verify the identity of the caller or that the caller is the original depositor. [4](#0-3) 

After the timelock, `execute_refund` (also unrestricted) triggers `internal_execute_refund`, which builds a PSBT sending the UTXO to the stored `refund_address` and submits it to the MPC signing pipeline. [5](#0-4) 

### Impact Explanation

An attacker can steal BTC from any deposit that has not yet been finalized via `verify_deposit`. The BTC is bridge-controlled (held in the MPC-managed UTXO set) and is released to the attacker's address through the legitimate MPC signing path. This constitutes an unauthorized release of bridge-controlled BTC funds.

**Impact: Critical** — matches "Unauthorized minting, unlocking, release, or claiming of nBTC/nZEC or underlying BTC/ZEC" and "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

### Likelihood Explanation

- All BTC deposit transactions and their associated `deposit_msg` parameters are observable on-chain or from NEAR transaction history.
- Deposits are routinely unfinalized for the duration between the BTC confirmation and the relayer's `verify_deposit` call (minutes to hours).
- The attacker only needs to pay the small NEAR storage deposit required by `request_refund` as an anti-spam fee.
- No privileged key or special role is required.

**Likelihood: High** — any NEAR account can execute this with publicly available on-chain data.

### Recommendation

Add `#[trusted_relayer]` to `request_refund` individually, consistent with the pattern used for `verify_refund_finalize` and `remove_refund_pending_tx_id`. Alternatively, enforce that the `refund_address` must match `deposit_msg.refund_address` when set, and restrict `request_refund` to the original depositor (`deposit_msg.account_id`) when `deposit_msg.refund_address` is `None`. [6](#0-5) 

### Proof of Concept

1. User Alice sends 1 BTC to the bridge deposit address derived from her `deposit_msg` (with `refund_address: None`). The BTC transaction is confirmed on-chain.
2. Before the relayer calls `verify_deposit`, attacker Bob observes Alice's `deposit_msg` and `tx_bytes` from NEAR transaction history.
3. Bob calls `request_refund(deposit_msg=Alice's, refund_address="Bob's BTC address", tx_bytes=Alice's tx, vout=0, proof=valid_proof, gas_fee=None)` with the required NEAR storage deposit attached.
4. The light client verifies the BTC transaction is real. The refund request is stored with `refund_address = Bob's BTC address`.
5. After the timelock (`max_btc_tx_pending_sec`), Bob calls `execute_refund(utxo_storage_key=Alice's UTXO)`.
6. The bridge builds a PSBT sending Alice's 1 BTC to Bob's address, submits it to MPC for signing, and broadcasts it. Bob receives Alice's BTC. [7](#0-6)

    /// Submit a refund request for a deposit that was never finalized via `verify_deposit` or `safe_verify_deposit`.
    /// The BTC transaction is verified through the Light Client to prove the deposit exists.
    /// After the timelock period, anyone can call `execute_refund` to initiate the return.
    ///
    /// Requires an attached deposit of at least `required_balance_for_request_refund()`.
    /// The deposit is NOT refunded — it covers request storage and acts as an anti-spam fee.
    ///
    /// # Arguments
    ///
    /// * `deposit_msg` - The original deposit message. If `deposit_msg.refund_address` is set,
    ///   it must match the provided `refund_address`.
    /// * `refund_address` - BTC address to send the refund to. If `deposit_msg.refund_address`
    ///   is `None`, this value is used directly.
    /// * `tx_bytes` - BTC transaction bytes proving the deposit.
    /// * `vout` - Output index of the deposit in the transaction.
    /// * `proof` - Transaction inclusion proof for Light Client verification, bundling:
    ///   `tx_block_blockhash` (block hash containing the transaction), `tx_index`
    ///   (transaction index within the block), `merkle_proof` (Merkle proof of the
    ///   transaction), and the coinbase fields `coinbase_tx_id` and
    ///   `coinbase_merkle_proof` used to verify the block's coinbase.
    /// * `gas_fee` - Optional custom gas fee. Only DAO or Operator can set this.
    ///   If `None`, the default `config.max_btc_gas_fee` is used during `execute_refund`.
    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
