### Title
Peras Certificate Validation Bypass Allows Arbitrary Chain-Weight Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance unconditionally accepts every inbound Peras certificate without performing any cryptographic or semantic validation. An unprivileged peer can craft a certificate for any block and any round, have it accepted by `processCerts`, stored in `PerasCertDB`, and applied as a `PerasWeight 15` boost to chain selection — causing an honest node to prefer an adversarial chain over the canonical one.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate validation. A single catch-all instance covers every block type:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

`validatePerasCert` always returns `Right`, assigning the full `perasWeight` boost to every certificate regardless of its content. No signature, quorum, committee membership, round eligibility, or boosted-block validity check is performed.

This function is the validation gate used in the **production** object-diffusion writer:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions the results of `validateCert <$> certsNotAlreadyInDb`. Because `validatePerasCert` always returns `Right`, the left partition (errors) is always empty and every certificate is unconditionally added to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Once stored, each certificate contributes its boost to `PerasWeightSnapshot` via `addToPerasWeightSnapshot`, which accumulates weight per point using `Map.insertWith (<>)`: [4](#0-3) 

Chain selection then uses `wsvTotalWeight = BlockNo + wsvWeightBoost` to compare candidate chains: [5](#0-4) 

The default `perasWeight` is **15**, meaning each accepted forged certificate adds 15 blocks' worth of weight to the targeted chain: [6](#0-5)

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance and chain-selection manipulation.**

An attacker who can connect as a peer and send object-diffusion messages can:

1. Craft `PerasCert` objects targeting any block point and any round number.
2. Have each certificate accepted unconditionally by `validatePerasCert`.
3. Accumulate `PerasWeight` boosts on an adversarial block via `addToPerasWeightSnapshot`.
4. Trigger `chainSelectionForBlock` for the boosted block, causing the honest node to re-evaluate chain selection with the inflated weight.
5. If the adversarial chain's total weight (`BlockNo + accumulated boost`) exceeds the honest chain's total weight, the node switches to the adversarial chain.

Because one certificate per round is accepted (deduplication is by `PerasRoundNo`), an attacker can send N certificates for N distinct round numbers, each boosting the same adversarial block, accumulating `15 * N` extra weight. With enough rounds this overcomes any honest chain length advantage, constituting a consensus safety failure.

This is the direct analog of the DeFi report: the pool assumed 1:1 equivalence between assets (any asset could be deposited and redeemed at par); here the consensus layer assumes 1:1 equivalence between forged and legitimate certificates (any certificate is treated as valid and granted full boost weight).

---

### Likelihood Explanation

**Likelihood: High** for any deployment where the Peras object-diffusion mini-protocol is active (private testnet, staging, or future mainnet). The attacker needs only a peer connection — no stake, no keys, no privileged access. The exploit is deterministic and requires no brute force. The TODO comments confirm this is a known placeholder, not a deliberate design choice, making accidental activation in a non-mainnet environment realistic.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before enabling Peras on any network. At minimum, verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the committee's aggregate public key, check quorum membership, and verify round eligibility. The concrete certificate type with BLS fields already exists in `Ouroboros.Consensus.Peras.Cert.V1`.
2. **Gate the object-diffusion writer** so that `makePerasCertPoolWriterFromChainDB` is only instantiated when a real `BlockSupportsPeras` instance with actual validation is in scope, preventing the degenerate instance from being used in production.
3. **Add a round-number range check** in `processCerts` to reject certificates whose round number is implausibly far from the current round, limiting the number of distinct rounds an attacker can exploit.

---

### Proof of Concept

On a private testnet with Peras object diffusion enabled:

1. Attacker connects as a peer to an honest node.
2. Attacker constructs a `PerasCert` for each of rounds `r`, `r+1`, …, `r+N-1`, all with `pcCertBoostedBlock` pointing to the tip of the attacker's shorter adversarial chain `C_adv`.
3. Attacker sends the batch via the object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams` on each cert → all return `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }`.
5. Each cert is stored; `implGetWeightSnapshot` returns a snapshot with `PerasWeight (15 * N)` for the adversarial tip.
6. `chainSelectionForBlock` is triggered for the adversarial tip. `preferAnchoredCandidate` computes `wsvTotalWeight(C_adv) = blockNo(C_adv) + 15*N`. If `blockNo(C_adv) + 15*N > blockNo(honest_tip)`, the node switches to `C_adv`.
7. The honest node has accepted an invalid chain, constituting a consensus safety failure. [7](#0-6) [8](#0-7) [9](#0-8) [10](#0-9)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

  WithFingerprint pcds fp <- readTVar pcdbState
