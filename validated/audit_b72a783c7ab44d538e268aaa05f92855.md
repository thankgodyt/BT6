### Title
Unconditional Peras Certificate Acceptance Bypasses All Signature and Quorum Validation, Enabling Unauthorized Chain Boost Injection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or quorum verification. Any unprivileged peer can send a crafted `PerasCert` naming an arbitrary block, which the receiving node will accept and use to apply a Peras weight boost during chain selection, potentially causing it to prefer a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must vet every inbound Peras certificate before it is stored and used in chain selection. The sole production instance — a blanket `instance StandardHash blk => BlockSupportsPeras blk` — implements this gate as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No aggregate signature is checked, no quorum threshold is verified, no round-number bounds are enforced, and no boosted-block validity is confirmed. The function simply wraps the raw, peer-supplied `PerasCert` in a `ValidatedPerasCert` and returns it as valid.

This stub is wired directly into the production node-to-node diffusion layer. The inbound certificate handler calls `makePerasCertPoolWriterFromChainDB`, which invokes `validatePerasCert mkPerasParams` on every certificate received from a peer:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

The accepted `ValidatedPerasCert` is then added to the `PerasCertDB` via `ChainDB.addPerasCertAsync`, which can trigger a chain-selection re-evaluation that applies the Peras weight boost to the attacker-chosen block. [4](#0-3) 

The `PerasWeightSnapshot` consumed by chain selection is derived directly from the `PerasCertDB` contents: [5](#0-4)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with:
- `pcCertRound` set to any round number, and
- `pcCertBoostedBlock` pointing to any block (including one on a non-canonical fork).

The receiving node will accept it without any cryptographic check, store it, and apply a `perasWeight`-sized boost to the named block during chain selection. If the boost is large enough relative to the honest chain's length advantage, the node will switch to the adversarial fork. This is a direct chain-selection safety failure: an honest node is made to prefer a non-canonical chain by a single crafted network message, with no stake or key compromise required.

This maps to the allowed impact scope: **Bypass of Peras certificate checks that enables unauthorized certificate acceptance**, and **chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's node-to-node port and the ability to send a well-formed CBOR-encoded `PerasCert` message. No stake, no keys, no prior chain knowledge beyond the target block's `Point` is needed. The production diffusion handler is already wired to this code path. Likelihood is high for any node running this codebase with Peras diffusion enabled.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS/KES signature over `(electionId, candidate)` against the committee's aggregate verification key.
2. Confirms that the signers' combined stake meets the quorum threshold from `PerasParams`.
3. Validates that `pcCertRound` falls within the expected window and that `pcCertBoostedBlock` refers to a known, non-immutable block.

Until the real implementation is in place, the inbound certificate diffusion handler should reject all externally received certificates (analogous to how the vote handler currently rejects all votes via the empty `PerasVoteStakeDistr mempty` placeholder). [6](#0-5)

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to the victim node's node-to-node port and completes the handshake.
2. The node starts `hPerasCertDiffusionClient`, which calls `makePerasCertPoolWriterFromChainDB systemTime getChainDB`.
3. Attacker sends a `PerasCert` message with `pcCertRound = N` and `pcCertBoostedBlock = Point` of a block on an adversarial fork.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The cert is passed to `ChainDB.addPerasCertAsync`, stored in `PerasCertDB`, and the `PerasWeightSnapshot` is updated.
6. Chain selection re-runs with the boosted adversarial block; if the boost exceeds the honest chain's advantage, the node switches forks.

**Necessary vulnerable step:** `validatePerasCert` at line 353–358 of `SupportsPeras.hs` is the sole validation gate and it is a no-op. [7](#0-6)
