### Title
Unchecked `post_action.msg` Content When No Templates Are Configured Allows Arbitrary Messages to Whitelisted Receivers — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary

The `check_deposit_msg` function validates `post_actions` by checking the `receiver_id` against a whitelist, but the validation of the `msg` field is entirely optional: it only runs when `post_action_msg_templates` has been configured for that receiver. When no templates exist for a whitelisted receiver, any attacker-controlled `msg` is accepted without restriction and forwarded to the receiver via `ft_transfer_call`. This is the direct analog of the Magnetar finding — the dispatcher checks only the target address (whitelist), not the content of the call (message), allowing arbitrary payloads to reach whitelisted contracts.

### Finding Description

In `check_deposit_msg`, the receiver whitelist check is unconditional:

```rust
if !self.data().post_action_receiver_id_white_list.contains(&post_action.receiver_id) {
    // reject
    return None;
}
```

But the message-content check is wrapped in an `if let Some(...)` guard:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validate msg against templates
    if !is_match {
        return None;
    }
}
// ← If no templates exist for this receiver, execution falls through here
//   with post_action.msg completely unchecked.
``` [1](#0-0) 

When the DAO adds a contract to `post_action_receiver_id_white_list` without also populating `post_action_msg_templates` for it, the `msg` field is entirely attacker-controlled. The bridge will then call:

```
nbtc.ft_transfer_call(receiver_id, amount, attacker_msg)
```

which triggers `receiver_id.ft_on_transfer(bridge_contract, amount, attacker_msg)` with `sender_id = bridge_contract`. [2](#0-1) 

The bridge does block itself from being a `post_action` receiver:

```rust
if post_action.receiver_id == env::current_account_id() {
    return None;
}
``` [3](#0-2) 

This prevents the exact self-call chain from the Magnetar report, but the first half of that vulnerability — unchecked call content to whitelisted targets — is fully present.

### Impact Explanation

An attacker who deposits BTC can embed a `DepositMsg` with `post_actions` targeting any whitelisted receiver that lacks template configuration. The bridge will forward an arbitrary `msg` to that receiver with `sender_id = bridge_contract`. Because the bridge contract is the `sender_id`, any receiver that grants the bridge special trust (e.g., credits deposits to the bridge's internal account, or uses `msg` to determine the beneficiary of the deposited tokens) can be manipulated. Concretely:

- If the receiver uses `msg` to determine which account to credit the deposited nBTC to, the attacker can specify any beneficiary, redirecting their deposited nBTC to an arbitrary account at the receiver.
- If the receiver interprets `msg` as instructions for further operations (e.g., swap, lend, stake) and trusts `sender_id = bridge`, the attacker can trigger operations the bridge designers never intended.

This constitutes a bypass of the bridge's own policy (the template system exists precisely to restrict what messages can be sent to receivers) and can cause harmful smart-contract behavior at whitelisted receivers.

**Allowed impact category**: Medium — "Bypass of bridge limits or policies" and "Harmful smart-contract behavior without direct funds theft."

### Likelihood Explanation

The `post_action_msg_templates` map is a separate management call (`extend_post_action_msg_templates`) from the whitelist call (`extend_post_action_receiver_id_white_list`). [4](#0-3) 

It is realistic that a DAO operator adds a receiver to the whitelist without also configuring templates — the code does not enforce that templates must exist before a receiver is whitelisted. Any such receiver is immediately exploitable by any depositor.

### Recommendation

Enforce that `post_action_msg_templates` must be configured for every whitelisted receiver before the receiver can be used in `post_actions`. One approach: in `check_deposit_msg`, treat the absence of a template entry for a whitelisted receiver as a validation failure (i.e., change the `if let Some(...)` to a mandatory lookup that rejects the action if no templates exist). Alternatively, require that `extend_post_action_receiver_id_white_list` atomically also accepts an initial set of templates, making it impossible to whitelist a receiver without restricting its messages.

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list([defi_protocol.near])` but does **not** call `extend_post_action_msg_templates` for `defi_protocol.near`.
2. Attacker constructs a `DepositMsg`:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi_protocol.near",
       "amount": "100000",
       "msg": "<arbitrary attacker-controlled payload>"
     }]
   }
   ```
3. Attacker sends BTC to the address derived from this `DepositMsg` and has a relayer call `verify_deposit_v2`.
4. `check_deposit_msg` passes: `receiver_id` is whitelisted, no templates exist so `msg` is not checked.
5. Bridge mints nBTC and calls `nbtc.ft_transfer_call("defi_protocol.near", 100000, "<attacker payload>")`.
6. `defi_protocol.near.ft_on_transfer("bridge.near", 100000, "<attacker payload>")` executes with the bridge as `sender_id` and the attacker's arbitrary `msg`, triggering whatever operation the attacker encoded. [1](#0-0)

```rust
    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
