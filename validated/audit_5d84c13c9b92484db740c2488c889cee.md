### Title
Zcash `ft_on_transfer` Callback Panic Permanently Locks nZEC Tokens in Bridge — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`)

---

### Summary

The Zcash path of `ft_on_transfer` returns a `PromiseOrValue::Promise` before any state mutation. If the chained callback `ft_on_transfer_callback` panics (e.g., because the Orchard bundle has the wrong action count), NEP-141 `ft_resolve_transfer` semantics treat the failed promise as returning `U128(0)` — meaning "keep all tokens." No `BTCPendingInfo` is ever created, so the tokens are permanently locked in the bridge with no refund path.

---

### Finding Description

**Entry point — `ft_on_transfer` (`token_receiver.rs:51-65`)**

For a `Withdraw` message, the function immediately delegates to `ft_on_transfer_withdraw_chain_specific` with no prior state mutation. [1](#0-0) 

**Zcash chain-specific path — `ft_on_transfer_withdraw_chain_specific` (`zcash_utils/contract_methods.rs:221-246`)**

This function unconditionally returns `PromiseOrValue::Promise(...)`. It schedules two cross-contract calls (`get_last_block_height_promise` → `ft_on_transfer_callback`) and returns immediately. No state is written. [2](#0-1) 

**Callback — `ft_on_transfer_callback` (`zcash_utils/contract_methods.rs:110-137`)**

The callback calls `PsbtWrapper::new(...)`, which internally calls `orchard_policy::extract_orchard_bundle`. [3](#0-2) 

**Panic site — `PsbtWrapper::new` (`zcash_utils/psbt_wrapper.rs:77-83`)**

`extract_orchard_bundle` is called and its `Err` result is converted to a hard panic via `env::panic_str`: [4](#0-3) 

**Validation that triggers the panic — `extract_orchard_bundle` (`zcash_utils/orchard_policy.rs:49-55`)**

If the bundle has any number of actions other than `EXPECTED_ACTIONS_NUMBER == 1`, the function returns `Err(...)`: [5](#0-4) 

**NEP-141 callback semantics**

When `ft_on_transfer` returns a `Promise` and that promise fails (panics), the nZEC token contract's `ft_resolve_transfer` receives `PromiseResult::Failed`. The NEP-141 standard implementation treats a failed result as returning `U128(0)` — meaning zero tokens are refunded to the sender. All transferred tokens remain with the bridge contract.

Because `ft_on_transfer_callback` panicked before `create_btc_pending_info` was called, no `BTCPendingInfo` entry exists for those tokens. There is no pending ID, no refund timelock, and no operator-accessible handle to recover them. [6](#0-5) 

---

### Impact Explanation

Any user who calls `ft_transfer_call` on the nZEC contract targeting the bridge with a `Withdraw` message containing a malformed Orchard bundle (e.g., 2 actions instead of 1) will have their nZEC tokens permanently locked in the bridge contract. The tokens cannot be recovered because:

1. No `BTCPendingInfo` is created (panic before `create_btc_pending_info`).
2. No refund path exists in the bridge for tokens without a pending info entry.
3. The nZEC contract's `ft_resolve_transfer` keeps the tokens at the bridge address.

This constitutes **permanent, irrecoverable loss of user funds**.

---

### Likelihood Explanation

- The attack requires no privilege — any account holding nZEC can trigger it.
- The malformed input (2 actions in the Orchard bundle) is trivially constructable.
- The user may trigger this accidentally (e.g., a wallet that pads bundles for privacy) or deliberately as self-harm.
- There is no guard in `ft_on_transfer` or `ft_on_transfer_withdraw_chain_specific` that validates the bundle before returning the promise.

---

### Recommendation

Validate the Orchard bundle (at minimum, parse it and check action count) **synchronously inside `ft_on_transfer_withdraw_chain_specific`** before returning `PromiseOrValue::Promise`. If validation fails, return `PromiseOrValue::Value(U128(amount))` to refund the full amount immediately, consistent with how the BTC path handles invalid inputs via `require!` panics inside the synchronous `PromiseOrValue::Value` path. [7](#0-6) 

Alternatively, ensure that any panic inside `ft_on_transfer_callback` is caught and converted to a refund by restructuring the callback to return `U128(amount)` on error rather than panicking.

---

### Proof of Concept

1. Deploy the bridge and nZEC token contracts on a NEAR sandbox.
2. Mint nZEC to an attacker account.
3. Construct an Orchard bundle with exactly 2 actions (violating `EXPECTED_ACTIONS_NUMBER == 1`).
4. Call `ft_transfer_call` on the nZEC contract:
   - `receiver_id`: bridge contract
   - `amount`: any valid withdrawal amount
   - `msg`: `{"Withdraw": {"target_btc_address": "<valid_addr>", "input": [...], "output": [...], "max_gas_fee": null, "chain_specific_data": {"orchard_bundle_bytes": "<2-action bundle hex>", "expiry_height": <valid>}}}`
5. Wait for all promises to resolve.
6. **Assert**: nZEC balance of bridge contract increased by `amount`.
7. **Assert**: No `BTCPendingInfo` exists for the attacker's account.
8. **Assert**: Attacker's nZEC balance decreased by `amount` with no refund.

The tokens are permanently locked. The root cause is confirmed at:
- `zcash_utils/contract_methods.rs:231` — promise returned before validation
- `zcash_utils/psbt_wrapper.rs:81` — panic on invalid bundle
- `zcash_utils/orchard_policy.rs:49` — action count check that triggers the error [8](#0-7)

            target_btc_address.clone(),

            &psbt,
            &vutxos,
            amount,

            max_gas_fee,
        );

        let psbt_hex = psbt.serialize();

        let btc_pending_info = BTCPendingInfo {
            account_id: sender_id.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: amount,
            actual_received_amount,
            withdraw_fee,
            gas_fee,
            burn_amount: actual_received_amount + gas_fee,
            psbt_hex,
            vutxos,
            signatures: vec![None; need_signature_num],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),

                last_rbf_time_sec: None,

            }),
        };
        require!(
            self.data_mut()

                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),

        );
        self.internal_unwrap_mut_account(&sender_id)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());
        Event::UtxoRemoved { utxo_storage_keys }.emit();
        Event::GenerateBtcPendingInfo {
            account_id: &sender_id,
            btc_pending_id: &btc_pending_id,
        }
        .emit();
    }

    pub fn ft_on_transfer_callback(
        &mut self,
        sender_id: AccountId,
        amount: U128,
        target_btc_address: String,
        input: Vec<OutPoint>,
        output: Vec<TxOut>,
        max_gas_fee: Option<U128>,
        chain_specific_data: Option<ChainSpecificData>,
        #[callback_unwrap] last_block_height: u32,
    ) -> U128 {
        let expiry_height = self.get_expiry_height(&chain_specific_data, last_block_height);
        let orchard_bundle = chain_specific_data.map(|c| c.orchard_bundle_bytes.0);

        let psbt = PsbtWrapper::new(
            input,
            output,
            orchard_bundle,
            expiry_height,
            last_block_height,
            Some(target_btc_address.clone()),
            self.internal_config(),
        );

        self.create_btc_pending_info(sender_id, amount.0, target_btc_address, psbt, max_gas_fee);

        U128(0)
    }
