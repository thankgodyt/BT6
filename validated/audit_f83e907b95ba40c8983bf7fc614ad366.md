### Title
Hardcoded Peras Protocol Parameters in Production Certificate/Vote Validation and Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Params.hs`)

---

### Summary

`mkPerasParams` in `Ouroboros/Consensus/Peras/Params.hs` hardcodes all Peras protocol parameters — including `perasWeight = 15` (the chain-selection boost weight) and `perasQuorumStakeThreshold = 3/4` — and is wired directly into production code paths that process inbound certificates and votes from unprivileged peers, and that initialize the ChainDB. The hardcoded `perasWeight` value is assigned as the boost weight for every accepted `ValidatedPerasCert`, and this boost is then used by the chain-selection engine to compare candidate chains. Because the value is static and cannot reflect actual on-chain governance decisions, an adversary can exploit the fixed boost to cause a node to prefer a non-canonical chain.

---

### Finding Description

`mkPerasParams` is a zero-argument function that returns a fully hardcoded `PerasParams` bundle: [1](#0-0) 

The comment inside explicitly acknowledges the values are tentative and that the function should eventually depend on a concrete `BlockConfig`: [2](#0-1) 

Despite this, `mkPerasParams` is used in three production code paths:

**1. `completeChainDbArgs`** — the function called to fully initialize the `ChainDB` for a running node hardcodes `mkPerasParams` as the Peras configuration for the `PerasVoteDB`: [3](#0-2) 

**2. `makePerasCertPoolWriterFromChainDB`** — the production writer for inbound Peras certificates received from peers passes `mkPerasParams` directly to `validatePerasCert`: [4](#0-3) 

**3. `makePerasVotePoolWriterFromChainDB`** — the production writer for inbound Peras votes from peers passes `mkPerasParams` to `validatePerasVote`: [5](#0-4) 

The `validatePerasCert` implementation (currently a stub) unconditionally accepts every certificate and assigns the boost weight directly from the hardcoded parameter: [6](#0-5) 

This `vpcCertBoost` value flows into the `PerasCertDB` weight snapshot, which is then consumed by `weightBoostOfFragment` and `wsvTotalWeight` during chain selection: [7](#0-6) 

Chain selection in `preferAnchoredCandidate` compares `wsvTotalWeight` (block number + weight boost) between the current chain and candidates: [8](#0-7) 

The certificate processing path that triggers chain selection after a cert is accepted: [9](#0-8) 

---

### Impact Explanation

The hardcoded `perasWeight = 15` is assigned as the boost weight for every certificate accepted from a peer, regardless of what the actual Peras network parameters are. Because `wsvTotalWeight = blockNo + weightBoost`, a chain containing a boosted block gains exactly 15 extra weight units. An adversary who can send a crafted certificate pointing to a block on a shorter fork can cause the node to compute that fork's total weight as higher than the canonical chain's, triggering a chain switch. The hardcoded quorum threshold (`3/4`) similarly cannot adapt to actual network governance, meaning the quorum check in `votesReachQuorum` / `stakeAboveThreshold` uses a fixed value that may diverge from the real protocol parameters when Peras is deployed. [10](#0-9) 

This constitutes a **High** chain-selection bug: an unprivileged peer can supply a crafted certificate that, combined with the hardcoded boost weight, causes an honest node to prefer a non-canonical or adversary-controlled chain beyond the intended security assumptions.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is a public, peer-facing interface. Any connected peer can submit a `PerasCert` message. The stub `validatePerasCert` unconditionally accepts it. The hardcoded boost weight is then applied and chain selection is triggered. No special privileges, key material, or stake majority are required. Likelihood is **Medium** because Peras is not yet active on mainnet, but the production code paths are already wired and the vulnerability is present in the current codebase.

---

### Recommendation

1. Replace the hardcoded `mkPerasParams` call in `completeChainDbArgs`, `makePerasCertPoolWriterFromChainDB`, and `makePerasVotePoolWriterFromChainDB` with a parameter derived from the node's `TopLevelConfig` / `BlockConfig`, as the comment in `mkPerasParams` itself anticipates (`NOTE: in the future this will depend on a concrete 'BlockConfig'`).
2. Until the full plumbing is in place, at minimum gate the production use of `mkPerasParams` behind a feature flag so it cannot be reached on a live network.
3. Implement the actual `validatePerasCert` and `validatePerasVote` logic (currently stubs marked with `TODO: perform actual validation`) before enabling Peras on any network, so that the boost weight is only assigned to cryptographically valid certificates.

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
