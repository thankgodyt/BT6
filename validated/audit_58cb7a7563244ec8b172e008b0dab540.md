### Title
`HyperliquedBridgeToken` 3-arg `mint()` Override Routes Bridged Tokens to System Address Instead of Recipient in `finTransfer` — (File: `evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

---

### Summary

`HyperliquedBridgeToken` overrides the 3-arg `mint(address, uint256, bytes)` to implement HyperCore spot-balance accounting by immediately re-routing all minted tokens to `_systemAddress`. When `OmniBridge.finTransfer` is called for this token with a non-empty `message`, it invokes this 3-arg override, causing the intended recipient to receive zero tokens while `_systemAddress` absorbs the full bridged amount. Funds are permanently lost.

---

### Finding Description

`IBridgeToken` declares two `mint` overloads:

```solidity
function mint(address account, uint256 value) external;
function mint(address account, uint256 value, bytes memory message) external;
``` [1](#0-0) 

`BridgeToken` implements both: the 2-arg variant mints directly to the beneficiary; the 3-arg variant is `virtual` and also mints directly. [2](#0-1) 

`HyperliquedBridgeToken` overrides **only** the 3-arg variant to implement HyperCore accounting. After `_mint(account, value)` it immediately calls `_update(account, _systemAddress, value)`, which is an ERC-20 internal transfer that moves the entire minted balance from `account` to `_systemAddress`:

```solidity
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value); // recipient ends up with 0
}
``` [3](#0-2) 

`HyperliquedBridgeToken` is registered via `addCustomToken` with `customMinter = address(0)`, which sets `isBridgeToken[tokenAddress] = true` and leaves `customMinters[tokenAddress] = address(0)`. [4](#0-3) 

In `OmniBridge.finTransfer`, the dispatch logic is:

```solidity
} else if (customMinters[payload.tokenAddress] != address(0)) {
    // customMinter path — skipped because customMinter == address(0)
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(
            payload.recipient, payload.amount, payload.message
        );
    }
}
``` [5](#0-4) 

When `payload.message.length > 0`, the 3-arg `mint()` is called on `HyperliquedBridgeToken`. The override mints tokens to `payload.recipient` and then immediately transfers them all to `_systemAddress`. The `FinTransfer` event fires as if the transfer succeeded, but `payload.recipient` holds zero tokens.

---

### Impact Explanation

**Critical — permanent loss of bridged funds.** Any user who includes a non-empty `message` in a cross-chain transfer whose destination token is `HyperliquedBridgeToken` will have their entire bridged amount permanently diverted to `_systemAddress`. The nonce is consumed and the `FinTransfer` event is emitted, so the transfer cannot be replayed or refunded through normal bridge flows.

---

### Likelihood Explanation

**Medium.** The `message` field is a standard, user-controlled parameter exposed in `initTransfer` on every supported chain. Users integrating with DeFi protocols, attaching memos, or using the message field for routing (e.g., the `ACTION_INIT_TRANSFER` path in `coreReceiveWithData`) will trigger this path. The test suite itself uses non-empty messages in the `ACTION_INIT_TRANSFER` flow. [6](#0-5) 

---

### Recommendation

Do not rely on the `isBridgeToken` + 3-arg `mint()` dispatch for `HyperliquedBridgeToken`. Instead, register it with a dedicated `customMinter` contract that correctly separates the HyperEVM direct-mint path (no message) from the HyperCore accounting path (with message), or override the 3-arg `mint()` so that when called by the bridge owner it mints directly to the recipient without the `_update` re-route. The HyperCore routing should only occur via `coreReceiveWithData`, not via `finTransfer`.

---

### Proof of Concept

1. `HyperliquedBridgeToken` is deployed and registered: `addCustomToken(nearTokenId, hlTokenAddress, address(0), 18)` → `isBridgeToken[hlTokenAddress] = true`, `customMinters[hlTokenAddress] = address(0)`.
2. A user on NEAR calls `ft_on_transfer` / `sign_transfer` with `message = "ref=hypercore"` (non-empty), targeting the HyperEVM recipient.
3. The relayer submits the MPC-signed payload to `OmniBridge.finTransfer`.
4. Signature verification passes; nonce is marked used.
5. Dispatch: `customMinters[hlTokenAddress] == address(0)` → skip; `isBridgeToken[hlTokenAddress] == true` → enter branch; `payload.message.length > 0` → call 3-arg `mint(recipient, amount, message)`.
6. Inside `HyperliquedBridgeToken.mint`: `_mint(recipient, amount)` gives recipient `amount` tokens; `_update(recipient, _systemAddress, amount)` immediately moves all `amount` tokens to `_systemAddress`.
7. `FinTransfer` event emitted. Recipient balance: **0**. `_systemAddress` balance: **amount**. Funds are permanently lost. [3](#0-2) [7](#0-6)
