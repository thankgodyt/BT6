### Title
Missing Chain ID in `deployToken` Digest Enables Cross-Chain Replay of MPC Signatures - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

### Summary
The `deployToken` function in `OmniBridge.sol` constructs a Borsh-encoded digest that omits the destination chain identifier (`omniBridgeChainId`). Because the same NEAR MPC-derived address (`nearBridgeDerivedAddress`) is used across all EVM deployments, a valid MPC signature obtained for deploying a token on one EVM chain (e.g., Ethereum) can be replayed verbatim on any other EVM chain where OmniBridge is deployed (e.g., Arbitrum, Base). The same structural flaw exists in the Solana and Starknet bridge contracts. This is a direct analog to the reported `ecrecover` misuse pattern: a critical domain-binding field is absent from the signed digest, allowing a signature intended for one context to be accepted in another.

### Finding Description
In `OmniBridge.sol`, `deployToken()` constructs the signed digest as:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
bytes32 hashed = keccak256(borshEncoded);
if (ECDSA.recover(hashed, signatureData) != nearBridgeDerivedAddress) {
    revert InvalidSignature();
}
```

No chain ID, contract address, or any chain-specific domain separator is included in the digest. [1](#0-0) 

By contrast, `finTransfer()` correctly embeds `omniBridgeChainId` twice in its digest — once for the token address field and once for the recipient field — providing proper chain-domain separation: [2](#0-1) 

The same asymmetry exists in the Solana program. `DeployTokenPayload.serialize_for_near()` serializes only `IncomingMessageType::Metadata` followed by the token fields, with no `SOLANA_OMNI_BRIDGE_CHAIN_ID` in the digest: [3](#0-2) 

While `FinalizeTransferPayload.serialize_for_near()` explicitly writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` before both the mint and recipient fields: [4](#0-3) 

The same pattern holds in Starknet. `MetadataPayload.to_borsh()` encodes only the payload type byte, token, name, symbol, and decimals — no `chain_id`: [5](#0-4) 

While `TransferMessagePayload.to_borsh()` accepts and embeds `chain_id` in two positions: [6](#0-5) 

The Starknet `deploy_token` function passes `payload.to_borsh()` directly to `_verify_borsh_signature`, which hashes and verifies against `omni_bridge_derived_address` — with no chain binding in the message: [7](#0-6) 

The Solana `deploy_token` instruction calls `data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)`, where the `()` additional params confirm no chain-specific data is injected at verification time: [8](#0-7) 

### Impact Explanation
The NEAR MPC system derives a single secp256k1 key pair used as `nearBridgeDerivedAddress` / `derived_near_bridge_address` across all supported EVM chains. Because the `deployToken` digest contains only token metadata (type byte + token ID + name + symbol + decimals) with no chain discriminator, the keccak256 hash — and therefore the valid signature — is identical for every EVM chain deployment of OmniBridge.

An attacker who observes a legitimate `deployToken` call on Ethereum can extract the `signatureData` from the transaction calldata and immediately replay it against the Arbitrum, Base, or any other EVM OmniBridge instance. The `ECDSA.recover` check passes because the recovered address equals `nearBridgeDerivedAddress` on every chain. The token is then registered in `isBridgeToken`, `ethToNearToken`, and `nearToEthToken` mappings on the target chain without NEAR having explicitly authorized deployment there. [9](#0-8) 

This constitutes an **authorization bypass**: the attacker executes a deployer-equivalent privileged action (registering a canonical bridge token and its mint authority) on a chain for which the NEAR MPC never issued authorization. Additionally, because the guard `require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")` is a strict one-time check, the attacker-triggered deployment permanently occupies the token slot, blocking any future official deployment of that token on the targeted chain. [10](#0-9) 

### Likelihood Explanation
Exploitation requires no special privileges. The attacker only needs to:
1. Monitor any EVM chain for a `deployToken` transaction (publicly visible on-chain).
2. Copy the `signatureData` bytes from the calldata.
3. Submit the identical call to any other EVM OmniBridge deployment.

The signature is reusable indefinitely across all chains until the token is already deployed there. The attack is fully permissionless and requires no brute force, key compromise, or validator collusion.

### Recommendation
Include `omniBridgeChainId` (and optionally the contract address) in the `deployToken` Borsh-encoded digest, exactly as `finTransfer` already does. For EVM:

```solidity
bytes memory borshEncoded = bytes.concat(
    bytes1(uint8(BridgeTypes.PayloadType.Metadata)),
+   bytes1(omniBridgeChainId),          // chain domain separator
    Borsh.encodeString(metadata.token),
    Borsh.encodeString(metadata.name),
    Borsh.encodeString(metadata.symbol),
    bytes1(metadata.decimals)
);
```

Apply the equivalent fix in `DeployTokenPayload.serialize_for_near()` (Solana) and `MetadataPayload.to_borsh()` (Starknet) to write the respective chain ID constant before the token fields. The NEAR MPC signing path must be updated in lockstep to include the destination chain ID when producing `deployToken` signatures.

### Proof of Concept
1. Token `usdc.near` is deployed on Ethereum OmniBridge via a legitimate `deployToken(sigEth, {token:"usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})` call. `sigEth` is now publicly visible in the Ethereum transaction.
2. Attacker calls `deployToken(sigEth, {token:"usdc.near", name:"USD Coin", symbol:"USDC", decimals:6})` on the Arbitrum OmniBridge.
3. The Borsh encoding is byte-for-byte identical (no chain ID present), so `keccak256(borshEncoded)` is the same hash. `ECDSA.recover(hashed, sigEth)` returns `nearBridgeDerivedAddress`, passing the signature check.
4. `usdc.near` is registered as a bridge token on Arbitrum with a freshly deployed `BridgeToken` proxy — without any NEAR MPC authorization for Arbitrum.
5. Any subsequent legitimate attempt by the NEAR bridge to officially deploy `usdc.near` on Arbitrum reverts with `ERR_TOKEN_EXIST`, permanently locking the attacker-triggered deployment as the canonical bridge token on that chain.
