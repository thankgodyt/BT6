### Title
Degenerate `BlockSupportsPeras` instance omits all cryptographic verification, allowing any peer to inject forged Peras certificates that influence chain selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `instance StandardHash blk => BlockSupportsPeras blk` defines `validatePerasCert` to unconditionally return `Right` and defines `PerasCert`/`PerasVote` data types that carry **no signature fields at all**. The production certificate-ingestion path (`makePerasCertPoolWriterFromChainDB`) resolves to this instance for every block type, including Cardano mainnet blocks. An unprivileged peer can therefore send structurally well-formed but cryptographically forged Peras certificates that are accepted without any verification and stored in the ChainDB, where their boost weight directly influences chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class declares:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only instance in the codebase is the degenerate catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

The `PerasCert blk` type defined in this same instance contains only `pcCertRound` and `pcCertBoostedBlock` — **no aggregate BLS signature field** — so there is no cryptographic material to verify even if the function tried: [2](#0-1) 

The concrete `V1.PerasCert` type (used by the real WFALS/EveryoneVotes committee implementations) does carry a `pcSignature :: AggregateVoteSignature PerasBLSCrypto` field and the `implVerifyCert` functions in `WFALS.hs` and `EveryoneVotes.hs` perform full BLS aggregate-signature verification. However, those implementations are **not wired** to the `BlockSupportsPeras` class instance that the production ingestion path calls. [3](#0-2) [4](#0-3) 

The same structural problem applies to `validatePerasVote`: the degenerate `PerasVote blk` type has no `pvSignature` field, and the validation function only checks stake-distribution membership, never a BLS vote signature: [5](#0-4) 

---

### Impact Explanation

The production certificate writer for the ChainDB calls `validatePerasCert mkPerasParams` directly:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- resolves to the degenerate instance
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [6](#0-5) 

`processCerts` accepts every certificate that passes `validatePerasCert` and stores it in the ChainDB with a `vpcCertBoost = perasWeight params` weight: [7](#0-6) 

Stored certificates contribute boost weight to chain selection via `getWeightSnapshot`. An attacker who can send a certificate claiming to boost an arbitrary block (any `pcCertBoostedBlock`) will have that boost applied to chain selection without any committee membership or signature check. This enables an unprivileged peer to make an honest node prefer a non-canonical chain — a direct Peras voting/certificate check bypass.

The same path exists for votes: `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote`, which accepts any vote whose `pvVoteVoterId` appears in the public stake distribution, without verifying the BLS vote signature. Accumulating enough such forged votes triggers `forgePerasCert`, producing a locally-forged certificate that is then stored and applied to chain selection. [8](#0-7) 

---

### Likelihood Explanation

The Peras object-diffusion miniprotocol is active in the node binary. Any connected peer can send `PerasCert` or `PerasVote` messages. The attacker needs only:

1. Knowledge of the public stake distribution (on-chain, freely observable).
2. The ability to construct a `PerasCert` CBOR value with a chosen `pcCertRound` and `pcCertBoostedBlock` — no key material required, because the degenerate type carries no signature field.

No stake, no keys, no operator access, and no brute force are required.

---

### Recommendation

1. **Remove the catch-all `instance StandardHash blk => BlockSupportsPeras blk`** or replace it with a compile-time error so that every concrete block type must provide a real implementation.
2. **Wire the concrete `V1.PerasCert`/`V1.PerasVote` types and the `implVerifyCert`/`implVerifyVote` functions** from `WFALS.hs` and `EveryoneVotes.hs` into the `BlockSupportsPeras` instance for `CardanoBlock`.
3. **Add the aggregate BLS signature field** to the `PerasCert blk` and `PerasVote blk` associated data types in the real instance, mirroring `V1.PerasCert.pcSignature` and `V1.PerasVote.pvSignature`.
4. Until the real instance is in place, **disable the Peras certificate/vote ingestion path** at the network layer so that peers cannot submit objects that bypass validation.

---

### Proof of Concept

A peer on a private testnet sends a CBOR-encoded `PerasCert` with `pcCertRound = 1` and `pcCertBoostedBlock = <hash of attacker-chosen block>`. The receiving node's `processCerts` pipeline calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}` unconditionally. The certificate is stored in the ChainDB. `getWeightSnapshot` now returns a non-zero boost for the attacker-chosen block. Chain selection on the honest node applies this boost, potentially preferring the attacker's chain over the canonical one — without the attacker ever possessing a committee signing key. ```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
