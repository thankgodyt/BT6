### Title
Fee-on-Transfer Token Mis-Accounting in `initTransfer` Emits Inflated Amount to NEAR - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.sol`'s `initTransfer` function calls `safeTransferFrom` with the caller-supplied `amount` but emits the `InitTransfer` event using that same caller-supplied `amount` rather than the actual tokens received by the contract. For fee-on-transfer tokens, the bridge receives fewer tokens than `amount`, yet the NEAR side reads the event and mints/unlocks the full `amount` in vouchers, creating an unbacked surplus that can be exploited to drain other depositors' funds.

---

### Finding Description

In `initTransfer`, for non-bridge, non-custom-minter ERC-20 tokens, the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-supplied
);
```

and then immediately emits:

```solidity
emit BridgeTypes.InitTransfer(
    msg.sender,
    tokenAddress,
    currentOriginNonce,
    amount,         // same caller-supplied value — not actual received
    fee,
    nativeFee,
    recipient,
    message
);
```

No balance snapshot is taken before or after the transfer to compute the real received amount. The `InitTransfer` event is the **sole data source** the NEAR side uses to finalize the transfer (via light-client proof or Wormhole VAA). Whatever `amount` appears in the event is what NEAR mints or unlocks for the recipient.

The identical pattern exists in `starknet/src/omni_bridge.cairo`'s `init_transfer`:

```cairo
let success = IERC20Dispatcher { contract_address: token_address }
    .transfer_from(caller, get_contract_address(), amount.into());
// ...
self.emit(Event::InitTransfer(InitTransfer { amount, ... }))
```

---

### Impact Explanation

For a fee-on-transfer token with a `k%` fee:
- Bridge receives `amount * (1 - k/100)` tokens.
- NEAR mints `amount` vouchers.
- The bridge's ERC-20 balance is permanently short by `amount * k/100` per deposit.
- When later users redeem their vouchers via `finTransfer`, the bridge attempts `safeTransfer(recipient, amount)` but its actual balance is insufficient, causing the last redeemers to lose funds — a direct theft from other depositors.

This is a **Critical** escrow mis-accounting issue: the bridge issues more cross-chain claims than it holds collateral for, enabling theft of bridged funds.

---

### Likelihood Explanation

- `initTransfer` is a public, permissionless function callable by any user with any ERC-20 token address.
- Fee-on-transfer tokens are a well-known token class (e.g., STA, DEFX, and tokens with configurable fees). An attacker can also deploy a custom ERC-20 with a transfer fee and register it through the bridge's open token-registration path.
- No whitelist or token-type check prevents fee-on-transfer tokens from being used.
- The exploit requires only a standard `initTransfer` call — no privileged access, no front-running, no external dependency failure.

---

### Recommendation

Capture the contract's token balance before and after `safeTransferFrom` and use the delta as the authoritative amount in the event:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// use actualReceived (cast to uint128) in initTransferExtension and emit
```

Apply the same fix to `starknet/src/omni_bridge.cairo`'s `init_transfer`.

---

### Proof of Concept

1. Deploy ERC-20 token `T` with a 10% transfer fee.
2. User A calls `initTransfer(T, 1000, 0, 0, "alice.near", "")`.
3. `safeTransferFrom` deducts 1000 from User A; bridge receives only 900 (10% fee taken by token).
4. `InitTransfer` event emits `amount = 1000`.
5. NEAR light-client/Wormhole relayer submits proof; NEAR mints 1000 vouchers for `alice.near`.
6. User B similarly deposits 1000 T; bridge receives 900, NEAR mints 1000 more vouchers. Bridge holds 1800 T, 2000 vouchers outstanding.
7. User A redeems 1000 vouchers → bridge releases 1000 T. Bridge now holds 800 T, 1000 vouchers outstanding.
8. User B tries to redeem 1000 vouchers → bridge only holds 800 T → `safeTransfer` reverts or User B receives only 800 T, losing 200 T.
9. Attacker controlling User A has effectively stolen 200 T from User B.
