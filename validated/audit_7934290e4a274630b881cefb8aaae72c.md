**Full attack path:**

1. `hPerasCertDiffusionClient` in `NodeToNode.hs` (line 375-384) is always wired up and calls `makePerasCertPoolWriterFromChainDB`
2. `makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` (line 126) passes `validatePerasCert mkPerasParams` as the validator
3. `validatePerasCert` (line 353-358 in `SupportsPeras.hs`) is the catch-all default instance that unconditionally returns `Right` for any cert
4. `processCerts` (lines 164-185 in `PerasCert.hs`) accepts the cert and calls `addPerasCertAsync`
5. `chainSelSync` for `ChainSelAddPerasCert` (lines 483-532 in `ChainSel.hs`) processes the cert: if the boosted block is in the VolatileDB, it calls `chainSelectionForBlock` with that header
6. `implGetWeightSnapshot` (lines 203-214 in `PerasCertDB/Impl.hs`) builds the weight snapshot from ALL certs in the DB — including fake ones — and this snapshot is used in chain selection
7. `mkPerasParams` sets `perasWeight = PerasWeight 15` (line 172 in `Params.hs`), so each fake cert adds 15 weight units to the boosted block's chain

**Critical mitigating factor:**

The `takeVolatileSuffix` function in `Weight.hs` (lines 369-374) has an explicit optimization: `Map.null $ getPerasWeightSnapshot snap` → use standard behavior. But this only applies when the snapshot is empty. Once a fake cert is accepted, the snapshot is non-empty and the Peras-weighted chain selection path is activated.

**However**, the key question is whether the PerasCertDiffusion protocol is actually negotiated in production. The code is wired up unconditionally in `mkHandlers`, but the actual protocol activation depends on `NodeToNodeVersion` negotiation — which I cannot fully verify from the available code. Additionally, the entire Peras feature is explicitly marked as pre-production with multiple TODO references to issue #73 and #120.

### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate, Enabling Chain Selection Manipulation — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally returns `Right` for any certificate. An attacker connected via the `PerasCertDiffusion` NodeToNode protocol can send a fabricated certificate for any round number not yet in the DB, which will pass validation, be stored in the `PerasCertDB`, and — if the boosted block is present in the VolatileDB — trigger chain selection with an artificial weight boost of `PerasWeight 15`, potentially causing the node to prefer a minority fork.

### Finding Description

The catch-all default instance at `SupportsPeras.hs` line 320 applies to all block types (including `HardForkBlock` / Cardano blocks) until a real instance is provided: [1](#0-0) 

The stub validator is wired directly into the production inbound handler: [2](#0-1) 

`processCerts` applies this validator and, on success, calls `addPerasCertAsync`: [3](#0-2) 

`chainSelSync` then uses the cert's boosted block point to trigger chain selection if the block is in the VolatileDB: [4](#0-3) 

The `PerasCertDB` weight snapshot — which feeds directly into chain selection — is built from all stored certs, including fake ones: [5](#0-4) 

The `hPerasCertDiffusionClient` handler is unconditionally wired up in `mkHandlers`: [6](#0-5) 

### Impact Explanation

An unprivileged peer can send a `PerasCert` message with an arbitrary `pcCertBoostedBlock` pointing to any valid block in the VolatileDB. The fake cert passes the stub validator, is stored in the `PerasCertDB`, and adds `PerasWeight 15` (from `mkPerasParams`) to that block's chain weight. This can cause the node to switch to a minority fork that is up to 15 blocks shorter than the current chain — a direct chain selection manipulation. [7](#0-6) 

### Likelihood Explanation

The exploit requires:
- A NodeToNode connection (standard peer connection)
- The PerasCertDiffusion protocol to be negotiated (depends on `NodeToNodeVersion`)
- A target block already present in the victim's VolatileDB

The first two conditions are met for any connected peer once the protocol version is negotiated. The third is trivially satisfied since the attacker can observe which blocks the victim has via ChainSync. The stub is explicitly acknowledged as temporary (issue #73, #120) but is currently in the production code path.

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies the certificate's cryptographic signature and committee quorum before accepting it. Until real validation is implemented, the `PerasCertDiffusion` inbound handler should be disabled or gated behind a feature flag that is off by default, preventing untrusted peers from injecting certificates. [8](#0-7)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
