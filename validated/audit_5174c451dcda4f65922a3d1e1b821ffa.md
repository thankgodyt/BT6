Audit Report

## Title
Re-entrancy in `initTransfer` / `initTransfer1155` Causes `originNonce` Collision and Permanent Freezing of Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer` and `initTransfer1155` both increment `currentOriginNonce` before an external token-transfer call but then re-read the storage variable (not a local snapshot) when passing it to `initTransferExtension` and `emit InitTransfer`. A malicious ERC-1155 token can re-enter `initTransfer1155` inside its own `safeTransferFrom` body, advance `currentOriginNonce` a second time, and cause both the inner and outer calls to emit `InitTransfer` with the same `originNonce`. NEAR processes the first event and permanently ignores the second, locking the outer call's tokens in the bridge with no recovery path.

## Finding Description

**Root cause — `initTransfer1155`** (lines 448–489):

```solidity
currentOriginNonce += 1;                          // (1) storage becomes N
...
IERC1155(tokenAddress).safeTransferFrom(          // (2) external call — attacker-controlled
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...); // (3) re-reads storage (may be N+1)
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...); // same
```

A malicious ERC-1155 token can, inside its `safeTransferFrom` body (before returning), call `initTransfer1155` again. The inner call increments `currentOriginNonce` from N to N+1, makes a second (normal) `safeTransferFrom`, and emits `InitTransfer(originNonce=N+1)`. When control returns to the outer call, it reads `currentOriginNonce = N+1` and emits a second `InitTransfer(originNonce=N+1)`. Nonce N is never emitted.

**Root cause — `initTransfer`** (lines 381–436): identical pattern; an ERC-777 token fires `tokensToSend` on the sender during `safeTransferFrom`, allowing a malicious sender contract to re-enter `initTransfer` and advance the nonce before the outer call reads it.

**Why existing guards fail:**

The `onERC1155Received` guard (lines 522–535) checks `operator != address(this)` and reverts if the operator is not the bridge. In `initTransfer1155`, the bridge itself is the caller of `safeTransferFrom`, so `operator == address(this)` — the guard passes. Critically, the re-entry occurs *inside the malicious token's `safeTransferFrom` body*, before `onERC1155Received` is ever invoked, so the guard is entirely bypassed. There is no `nonReentrant` modifier on either function.

The documented invariant in `CLAUDE.md` (line 34) — *"Always mutate state … before any external call … This is the primary reentrancy defense"* — is violated because the nonce is incremented before the external call but then **re-read from storage** after it, rather than being captured in a local variable.

## Impact Explanation

The outer call's tokens are transferred to the bridge contract (the `safeTransferFrom` succeeded), but the `InitTransfer` event it emits carries `originNonce=N+1`, which is identical to the event already emitted by the inner call. The NEAR `fin_transfer_callback` reconstructs transfers using `origin_nonce` from the parsed EVM event; it processes the first occurrence and permanently ignores the second. The outer call's tokens are locked inside the EVM bridge contract with no admin-recovery function and no mechanism to re-submit the proof. This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation

For `initTransfer1155`: the attacker deploys a malicious ERC-1155 contract, calls the permissionless `logMetadata1155` (or skips it entirely — `initTransfer1155` does not require prior registration), then calls `initTransfer1155` with the malicious token. No admin keys, no MPC compromise, no front-running, and no external dependency failure are required. Any unprivileged user can execute this on-chain in three transactions.

For `initTransfer`: requires a malicious ERC-777 token and a malicious sender contract implementing `tokensToSend`; slightly more setup but equally permissionless.

## Recommendation

1. **Capture the nonce in a local variable immediately after incrementing**, before any external call, and use only that local variable thereafter:

```solidity
currentOriginNonce += 1;
uint64 nonce = currentOriginNonce;   // snapshot before external calls
...
IERC1155(tokenAddress).safeTransferFrom(...);
...
initTransferExtension(..., nonce, ...);
emit BridgeTypes.InitTransfer(..., nonce, ...);
```

Apply this fix to both `initTransfer` (lines 381–436) and `initTransfer1155` (lines 448–489) in `OmniBridge.sol`.

2. As defense-in-depth, add OpenZeppelin's `ReentrancyGuard` (`nonReentrant` modifier) to both functions.

## Proof of Concept

```
Deploy MaliciousERC1155 whose safeTransferFrom:
  - on first call: re-enters initTransfer1155 (inner call), then returns normally
  - on second call (inner): transfers tokens normally and returns

State trace (currentOriginNonce starts at 5):

Outer call: initTransfer1155(MaliciousERC1155, ...)
  (1) currentOriginNonce = 6
  (2) MaliciousERC1155.safeTransferFrom → re-enters initTransfer1155
        Inner call:
          (1) currentOriginNonce = 7
          (2) MaliciousERC1155.safeTransferFrom → transfers normally, returns
          (3) initTransferExtension(..., currentOriginNonce=7, ...)
          (4) emit InitTransfer(originNonce=7)   ← INNER event
        returns to outer safeTransferFrom
  (3) initTransferExtension(..., currentOriginNonce=7, ...)  ← reads 7, not 6
  (4) emit InitTransfer(originNonce=7)   ← OUTER event, SAME nonce

Result:
  - originNonce 6 never emitted → gap in sequence
  - originNonce 7 emitted twice → NEAR processes first, ignores second
  - Outer call's tokens locked in bridge permanently with no recovery path
```
