### Title
Migration Window Race: Old-Token Withdrawal Accepted Before `nbtc_account_id` Flip, Enabling BTC Release Without Valid Old-Token Burn — (`contracts/satoshi-bridge/src/nbtc/migration.rs`, `src/api/token_receiver.rs`, `src/nbtc/burn.rs`)

---

### Summary

`migrate_to_new_token_resolve` updates `nbtc_account_id` to the new token only after the mint batch succeeds. In NEAR's async receipt model, other transactions execute between the mint-batch receipt and the resolve-callback receipt. An attacker who holds old nBTC tokens can submit `old_token.ft_transfer_call(bridge, amount, Withdraw{…})` inside that window. `ft_on_transfer` accepts the call because `predecessor_account_id() == nbtc_account_id` (still the old token). UTXOs are removed from the bridge immediately. When `migrate_to_new_token_resolve` fires next, `nbtc_account_id` becomes the new token. Later, `verify_withdraw_burn_promise` calls `burn` on the **new** token contract for the attacker's account — and that burn **succeeds**, because the migration already minted the attacker an equal balance of new tokens. The net effect is that the attacker receives BTC while the bridge permanently holds worthless old tokens, constituting a double-spend of the attacker's original old-token balance.

---

### Finding Description

**Step 1 — Migration snapshot and mint batch**

`internal_migrate_to_new_token` queries every holder's old-token balance, then `migrate_to_new_token_mint` mints an equal amount of new tokens for each holder. The resolve callback is chained after the entire mint batch. [1](#0-0) 

`nbtc_account_id` is **not** changed until `migrate_to_new_token_resolve` executes: [2](#0-1) 

**Step 2 — NEAR async gap**

In NEAR's execution model, the resolve-callback receipt is queued when the last mint call completes, but it is processed in a subsequent block. Any transaction submitted between those two blocks executes with the **old** `nbtc_account_id` still in storage.

**Step 3 — `ft_on_transfer` token-id guard passes**

The only guard against a wrong token is: [3](#0-2) 

During the window `nbtc_account_id` is still the old token, so `predecessor_account_id() == nbtc_account_id` is true and the check passes.

**Step 4 — UTXOs removed synchronously (Bitcoin path)**

`ft_on_transfer_withdraw_chain_specific` for Bitcoin calls `create_btc_pending_info` and returns `PromiseOrValue::Value(U128(0))` immediately: [4](#0-3) 

Inside `create_btc_pending_info`, `generate_vutxos` removes the attacker-chosen UTXOs from the bridge's active UTXO set: [5](#0-4) 

**Step 5 — Migration completes; `nbtc_account_id = new_token`**

The resolve callback fires and flips the token pointer. The attacker now holds **new** tokens (minted for them in step 1) and the bridge holds their **old** tokens.

**Step 6 — Burn is called on the new token and succeeds**

After the BTC transaction is signed, broadcast, and confirmed, the trusted relayer calls `verify_withdraw`. The burn is dispatched against `nbtc_account_id` — now the new token: [6](#0-5) 

The new token contract burns from `btc_pending_info.account_id` (the attacker). Because the migration already minted the attacker an equal balance of new tokens, the burn **succeeds**. `verify_withdraw_burn_callback` finalises the withdrawal: [7](#0-6)

### Impact Explanation

The attacker started with X old tokens. The migration minted X new tokens for them. They then used the X old tokens a second time to initiate a withdrawal. After migration, X new tokens are burned (legitimately, from the attacker's new-token balance), and the BTC transaction is finalised. The attacker receives X BTC. The bridge permanently holds X worthless old tokens and has lost X BTC worth of UTXOs. This is a direct, critical theft of bridge-controlled BTC funds.

---

### Likelihood Explanation

- Migration is a rare but real operational event, announced on-chain.
- The attacker only needs to monitor for the `migrate_to_new_token_mint` callback receipt and submit one `ft_transfer_call` in the next NEAR block (~1 s window). A simple bot suffices.
- The attacker must hold old nBTC tokens — a normal user precondition.
- No privileged role is required; the exploit path is entirely through the public `ft_transfer_call` → `ft_on_transfer` NEP-141 interface.
- The mint batch itself spans multiple blocks (one receipt per account), giving the attacker a window proportional to the number of migrated accounts.

---

### Recommendation

1. **Set a migration-in-progress flag** at the start of `internal_migrate_to_new_token` and clear it in `migrate_to_new_token_resolve`. Add a guard in `ft_on_transfer` that rejects calls while the flag is set.
2. Alternatively, **accept both old and new token IDs** during migration and burn old tokens atomically inside the migration flow rather than leaving them in circulation.
3. **Pause withdrawals** (via the existing `pause` mechanism) for the duration of the migration, and unpause in `migrate_to_new_token_resolve`.
