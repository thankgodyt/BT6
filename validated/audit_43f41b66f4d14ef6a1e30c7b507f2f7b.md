### Title
Silent Token Loss in `safe_mint` When Recipient Account Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract mints tokens into the bridge's own balance first, then silently returns `U128(0)` without transferring them if the recipient account is not registered in the token contract. The minted tokens remain permanently stranded in the bridge's balance with no recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in two distinct steps:

1. **Step 1 (line 112):** `self.token.internal_deposit(&self.bridge_id, amount.into())` — tokens are unconditionally minted into the bridge's own token balance.
2. **Step 2 (lines 114–116):** If `account_id` has no registered storage slot, the function returns `PromiseOrValue::Value(U128(0))` immediately — no transfer is attempted, no event is emitted for the user, and no recovery entry is created. [1](#0-0) 

This is structurally analogous to the reported ERC20 vulnerability: instead of a `token.transfer()` reverting and locking state, here the transfer is silently skipped after supply has already been inflated into the bridge's balance. The contrast with the `mint` function is instructive — `mint` calls `mint_inner`, which auto-registers any unregistered account before depositing: [2](#0-1) 

`safe_mint` has no equivalent guard. The bridge's `transfer_nbtc_callback` does implement a `lost_found` recovery for cross-contract `ft_transfer` failures: [3](#0-2) 

But `safe_mint` never reaches a cross-contract transfer at all when the account is unregistered — it exits before any transfer is issued, so `lost_found` is never populated and no recovery is possible.

### Impact Explanation
Tokens are minted (total supply increases, bridge balance increases) but the user receives nothing. The minted amount is permanently stranded in the bridge's token balance. Because the BTC-side deposit is already confirmed on-chain before minting is triggered, the user's BTC is locked on Bitcoin while their nBTC is silently absorbed into the bridge. This constitutes a permanent loss of user funds matching: **Critical — significant loss or permanent locking of user funds**.

### Likelihood Explanation
Any user who initiates a deposit flow that routes through `safe_mint` without first registering their NEAR account in the nBTC token contract triggers this silently. Account registration is a separate prerequisite step (`storage_deposit`) that is easy to omit, especially for new users or programmatic integrations. The function is gated to the bridge (`assert_bridge`) so the entry path is the bridge's own deposit callback — a standard, publicly reachable bridge operation. [4](#0-3) 

### Recommendation
Mirror the `mint_inner` pattern inside `safe_mint`: auto-register the recipient account before minting, or revert with an explicit error if the account is not registered so the bridge-side callback can handle the failure and record the amount in `lost_found`. Do not mint supply into `bridge_id` before confirming the transfer can succeed.

### Proof of Concept
1. User submits a BTC deposit. The bridge verifies inclusion and calls `safe_mint(user_account_id, amount, msg)` on the nBTC contract.
2. `user_account_id` has never called `storage_deposit` on the nBTC contract, so `self.token.accounts.get(&account_id)` returns `None`.
3. `self.token.internal_deposit(&self.bridge_id, amount.into())` executes — `amount` nBTC is added to the bridge's balance and total supply increases.
4. The `is_none()` branch fires and the function returns `U128(0)`.
5. No `ft_transfer` is issued, no `lost_found` entry is created, no event is emitted for the user.
6. The user's BTC is locked on Bitcoin; their nBTC is permanently held in the bridge's own token balance with no callable recovery function. [5](#0-4)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
