Audit Report

## Title
Missing Pre-Transfer Normalization Check Permanently Locks Funds When Full Amount Rounds to Zero — (File: near/omni-bridge/src/lib.rs)

## Summary

`init_transfer` locks user tokens into `pending_transfers` without verifying that `normalize_amount(amount - fee) > 0`. When a user transfers an amount smaller than the decimal-scaling factor (e.g., fewer than `10^(origin_decimals - dest_decimals)` raw units), the entire post-fee amount normalizes to zero via floor division. `sign_transfer` then unconditionally panics with `InvalidAmountToTransfer`, and because there is no refund path triggered by this failure, the locked tokens are permanently frozen in the bridge contract.

## Finding Description

**Root cause — `normalize_amount` (lines 2784–2786):**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

Floor division truncates any amount smaller than `10^(origin_decimals - dest_decimals)` to zero. The function's own doc-comment (lines 2781–2783) acknowledges this: *"When fee = 0, dust stays locked/burned."* However, the comment frames this as small remainders ("dust"), not as the entire transfer amount normalizing to zero.

**Locking path — `init_transfer` (lines 554–557):**

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

This is the only amount validity check before tokens are debited and the transfer record is stored in `pending_transfers`. It does **not** verify `normalize_amount(amount - fee) > 0`. A transfer with `amount = 500` and `fee = 0` passes this check even when `normalize_amount(500)` = `500 / 10^12` = **0** for a token with 18 NEAR-side decimals and 6 destination-chain decimals.

**Failure path — `sign_transfer` (lines 475–485):**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`sign_transfer` (restricted to `#[trusted_relayer]`) will always panic for this transfer. The panic does not trigger any refund or cleanup of the `pending_transfers` entry. The `sign_transfer_callback` (lines 649–667) is only reached on MPC signing success; it is never invoked when `sign_transfer` itself panics before the MPC call.

**No recovery path exists.** `remove_transfer_message` is only called on successful `sign_transfer_callback` (when fee is zero) or via `claim_fee_callback`. Neither path is reachable for a transfer whose `sign_transfer` always panics. The tokens remain locked in `pending_transfers` indefinitely.

## Impact Explanation

Permanent freezing of bridged funds. Any user who initiates a NEAR-side transfer with a raw token amount smaller than `10^(origin_decimals - dest_decimals)` will have their tokens permanently locked in the bridge contract with no recovery mechanism. This directly matches the Critical impact class: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation

Any unprivileged user can trigger the locking step by calling `ft_transfer_call` with a small amount. The condition is reachable whenever the destination chain uses fewer decimals than the NEAR-side token representation — a common and standard configuration (e.g., 18 NEAR-side decimals → 6 EVM decimals, scaling factor = `10^12`). No special role, admin action, or external dependency is required to lock the funds. The trusted-relayer restriction on `sign_transfer` does not prevent the loss; it only means the relayer (not the user) triggers the final panic, but the outcome — permanently locked user funds — is the same.

## Recommendation

Enforce the minimum-amount constraint at `init_transfer` time, before tokens are debited, by adding:

```rust
require!(
    Self::normalize_amount(
        transfer_message.amount.0.saturating_sub(transfer_message.fee.fee.0),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This requires resolving the token's destination decimals at `init_transfer` time (as `sign_transfer` already does). Alternatively, add a refund path in `sign_transfer` that returns the locked tokens to the sender and removes the `pending_transfers` entry when `amount_to_transfer == 0`, instead of panicking.

## Proof of Concept

1. Register a token with `decimals = 6` (destination) and `origin_decimals = 18` (NEAR-side). Scaling factor = `10^12`.
2. User calls `ft_transfer_call` with `amount = 500`, `fee = 0`. The check `fee (0) < amount (500)` passes. 500 raw units are locked; the transfer is stored in `pending_transfers`.
3. Trusted relayer calls `sign_transfer` for this transfer.
4. `normalize_amount(500, {decimals: 6, origin_decimals: 18})` = `500 / 10^12` = **0**.
5. `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`. No MPC call is made. No callback fires.
6. The transfer record remains in `pending_transfers` forever. The 500 raw units are permanently locked with no refund path.

**Minimal unit test:**
```rust
#[test]
fn test_normalize_amount_rounds_to_zero() {
    assert_eq!(
        Contract::normalize_amount(500, Decimals { decimals: 6, origin_decimals: 18 }),
        0
    );
}
```
This confirms step 4. A sandbox integration test can confirm steps 2–6 by calling `ft_transfer_call` with `amount = 500` on a token registered with the above decimals, then calling `sign_transfer` and asserting it panics, while `get_transfer_message` still returns the entry.
