### Title
Peras Certificate Validation Stub Unconditionally Accepts All Certificates, Enabling Adversarial Chain Weight Inflation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the production `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` (success) for every certificate it receives, without performing any cryptographic or committee-membership checks. Any unprivileged peer can therefore inject arbitrary Peras certificates over the object-diffusion mini-protocol. Each accepted certificate is stored in `PerasCertDB`, contributes to the `PerasWeightSnapshot`, and inflates the chain-selection weight of whichever block the attacker names — including blocks on an adversarial fork. This is the direct analog of the DutchAuction bug: in that report the excess payment (`msg.value − currentPrice`) was attributed to the wrong party (the liquidated borrower) instead of being returned to the buyer; here the boost weight is attributed to fraudulent certificates (the wrong party) instead of being withheld from them.

---

### Finding Description

**Root cause — stub validator always returns `Right`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No committee-membership check, no quorum check, no BLS/signature verification is performed. Every `PerasCert` is wrapped in a `ValidatedPerasCert` carrying the full configured `perasWeight`.

**Inbound processing path — stub is wired into the live object-diffusion handler:**

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator on every certificate received from a peer; because it always returns `Right`, the `(errs, _)` branch that would disconnect the peer is never reached. [3](#0-2) 

**Storage — accepted certificates accumulate in `PerasCertDB`:**

`implAddCert` deduplicates only by round number. A certificate for a fresh round is always stored. [4](#0-3) 

**Weight snapshot — stored certificates directly feed chain selection:**

`implGetWeightSnapshot` builds a `PerasWeightSnapshot` from every certificate in the DB, mapping each `pcCertBoostedBlock` to its `vpcCertBoost`. [5](#0-4) 

**Chain selection — inflated snapshot changes which chain is preferred:**

`preferAnchoredCandidate` takes the Peras-active branch whenever `isEmptyPerasWeightSnapshot` is false, computing `weightedSelectView` over the suffix after the intersection. The total weight is `BlockNo(tip) + WeightBoost(suffix)`. [6](#0-5) 

`wsvTotalWeight` adds the absolute block number to the accumulated boost: [7](#0-6) 

A sufficiently large injected boost can make a shorter adversarial fork outweigh the honest chain.

**Rollback guard — also uses the inflated snapshot:**

`forksAtMostKWeight` uses `totalWeightOfFragment` with the same snapshot to decide whether a rollback is within the `k`-weight bound. Inflated weights on the adversarial suffix can make a deep rollback appear shallow. [8](#0-7)

### Impact Explanation

An unprivileged peer that can reach the object-diffusion endpoint can inject one certificate per Peras round, each naming any block point as `pcCertBoostedBlock`. Because `validatePerasCert` never rejects, every injected certificate is stored and contributes `perasWeight` to the snapshot. Once the snapshot is non-empty, chain selection switches to the Peras-weighted path. By targeting blocks on an adversarial fork, the attacker inflates that fork's total weight, potentially causing an honest node to:

1. **Prefer the adversarial fork** over the canonical chain (chain-selection safety failure).
2. **Accept a rollback deeper than `k`** if the adversarial suffix's inflated weight makes it appear within the `k`-weight bound.

This matches the **Critical** and **High** impact categories: bypass of Peras certificate checks enabling unauthorized certificate acceptance, and a chain-selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is wired into the live node code and reachable by any connected peer. The attacker needs only to send well-formed `PerasCert` CBOR messages with a crafted `pcCertBoostedBlock`. No key material, stake, or operator access is required. The TODO comments confirm the stub is intentional for the current development phase, but the inbound handler is already active, making the attack path reachable today on any node running this codebase with Peras enabled.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
- Committee membership of the signers for the given round.
- Quorum threshold on aggregated stake.
- BLS (or equivalent) aggregate signature over the certificate body.

Until real validation is in place, the inbound `processCerts` handler should reject all certificates (or the object-diffusion endpoint for Peras certificates should not be exposed) to prevent weight inflation. The `TODO` at `https://github.com/tweag/cardano-peras/issues/120` should be treated as a security-critical blocker before Peras is activated on any network where adversarial peers are possible.

---

### Proof of Concept

1. Connect to a node running this codebase with Peras object-diffusion enabled.
2. Send a batch of `PerasCert` messages via the object-diffusion inbound protocol, each with a distinct `pcCertRound` and `pcCertBoostedBlock` pointing to a block on an adversarial fork `F`.
3. `processCerts` calls `validatePerasCert mkPerasParams` on each; all return `Right ValidatedPerasCert{..}`.
4. Each certificate is stored in `PerasCertDB` via `implAddCert`.
5. `implGetWeightSnapshot` now returns a non-empty `PerasWeightSnapshot` mapping blocks on `F` to accumulated `perasWeight` boosts.
6. When the node next runs chain selection against a candidate containing those blocks, `preferAnchoredCandidate` enters the Peras-weighted branch. The adversarial fork's `wsvTotalWeight = BlockNo(tip) + Σ(injected boosts)` exceeds the honest chain's weight.
7. The node switches to the adversarial fork, accepting an invalid or non-canonical chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186

    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
