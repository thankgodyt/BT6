### Title
Server-Side Version Enforcement Absent on LocalStateQuery, Exposing Debug Consensus State to Any Local Client - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/LocalStateQuery/Server.hs`)

---

### Summary

The `localStateQueryServer` passes every decoded query directly to `answerQuery` with no server-side check of whether the query is permitted under the negotiated `NodeToClientVersion`. Version enforcement exists only in the client-side encoder. Any local process that connects to the node's Unix socket and uses a custom client implementation can therefore send any query — including the privileged debug queries `DebugLedgerConfig`, `DebugEpochState`, `DebugNewEpochState`, and `DebugChainDepState` — regardless of the version that was negotiated, materially weakening the state-query authorization model.

---

### Finding Description

The `Query blk` GADT defines four top-level queries and a family of `BlockQuery` sub-queries. Three of the top-level queries and several Shelley sub-queries are explicitly gated behind minimum `QueryVersion` or `ShelleyNodeToClientVersion` values:

- `DebugLedgerConfig` requires `QueryVersion3` (≥ `NodeToClientV_20`)
- `DebugEpochState`, `DebugNewEpochState`, `DebugChainDepState` are Shelley sub-queries with their own version gates [1](#0-0) 

The version gate is enforced only in `queryEncodeNodeToClient` (the **client-side** encoder) via `requireVersion`, which throws a `QueryEncoderUnsupportedQuery` exception before the bytes are sent: [2](#0-1) 

The **server-side** handler `localStateQueryServer` performs no such check. It decodes the incoming bytes into a `Query blk result` value and immediately calls `Query.answerQuery`: [3](#0-2) 

`answerQuery` dispatches on the query constructor with no version guard: [4](#0-3) 

The design is explicitly documented as intentional, following the "robustness principle": [5](#0-4) 

The decoder `queryDecodeNodeToClient` does enforce `requireVersion` for top-level queries (e.g., it rejects `DebugLedgerConfig` if `queryVersion < QueryVersion3`): [6](#0-5) 

However, a custom client that bypasses the standard encoder and writes raw CBOR bytes `[1, 4]` (the `DebugLedgerConfig` encoding) directly to the socket after negotiating `NodeToClientV_16` will have those bytes decoded successfully by the server's codec (because `queryDecodeNodeToClient` is called with the negotiated version, and the `requireVersion` check in the decoder will reject it — but see below for the Shelley sub-query path which has no such decoder-side check).

For Shelley sub-queries (`DebugEpochState` tag 8, `DebugNewEpochState` tag 12, `DebugChainDepState` tag 13), `decodeShelleyQuery` decodes them unconditionally with no version check at all: [7](#0-6) 

`blockQueryIsSupportedOnVersion` returns `const True` for all three debug queries, meaning the decoder accepts them on every version: [8](#0-7) 

Once decoded, the server answers them unconditionally. `DebugChainDepState` returns the full `ChainDepState proto` (the evolving nonce and candidate nonce for Praos/TPraos): [9](#0-8) 

`DebugLedgerConfig` returns `topLevelConfigLedger`, which for the Cardano HardFork block includes the full `ShelleyLedgerConfig` (genesis data, globals, translation context) for every era: [10](#0-9) 

---

### Impact Explanation

Any process with access to the node's local Unix socket — including a compromised wallet, a malicious CLI wrapper, or any co-located application — can connect, negotiate the lowest supported `NodeToClientVersion`, and then send raw CBOR for `DebugEpochState`, `DebugNewEpochState`, or `DebugChainDepState` without restriction. The server will answer all of them. This completely bypasses the version-based access-control model that is the only authorization layer protecting these debug endpoints. The `DebugChainDepState` result exposes the internal Praos/TPraos nonce state; `DebugLedgerConfig` exposes the full multi-era ledger configuration including genesis delegation data. This materially weakens state-query authorization on the node's public local API surface.

---

### Likelihood Explanation

The local socket is accessible to any process the operator has granted socket access to (cardano-cli, ogmios, Kupo, wallet backends, etc.). A compromised or malicious version of any such tool can trivially craft the four-byte CBOR payload for `DebugEpochState` (`[1, 8]` wrapped in the HardFork query envelope) and send it after a normal version negotiation. No cryptographic material or elevated privilege beyond socket access is required.

---

### Recommendation

Enforce version checks on the **server side** inside `localStateQueryServer` (or inside `answerQuery`) before dispatching to the query handler. The negotiated `NodeToClientVersion` is available at the point where the server is constructed (it is passed into `mkApps` / `aStateQueryServer`); it should be threaded into `handleQuery` and compared against `queryIsSupportedOnNodeToClientVersion` before calling `Query.answerQuery`. Queries that fail the server-side version check should return a protocol-level error rather than a result.

---

### Proof of Concept

1. Connect to the node's local socket and negotiate `NodeToClientV_16` (the minimum supported version, `QueryVersion2`).
2. Send the `MsgAcquire VolatileTip` message.
3. After receiving `MsgAcquired`, send a raw CBOR `MsgQuery` whose payload encodes `BlockQuery (QueryIfCurrent (QS (QZ DebugChainDepState)))` — tag sequence `[0, [1, [1, 13]]]` — which is a Shelley-era `DebugChainDepState` query.
4. The server decodes it via `decodeShelleyQuery` (no version check), dispatches to `answerPureBlockQuery`, and returns the full `ChainDepState proto` (Praos nonce state) in `MsgResult`.
5. Repeat with tag `[0, [1, [1, 12]]]` (`DebugNewEpochState`) to receive the complete `NewEpochState era` including all stake snapshots, reward accounts, and governance state — data that is supposed to require a higher negotiated version. [11](#0-10) [3](#0-2) [12](#0-11)

**File:** docs/website/contents/howtos/versioning_a_new_query.md (L69-71)
```markdown
The supported query versions are only enforced in the [Shelley query encoder][shelley-encodeNodeToClient], ie in code run by clients. The server will currently answer queries even if the negotiated version is not in the supported version range for that query (which might be the case with a custom client implementation, or when one forgot to enable experimental protocols), following the robustness principle (ie "be conservative in what you send, be liberal in what you accept").

As an example, consider a query $Q$ that is enabled after version $x$, and consider a connection between a client and a node that negotiated version $y$. If $y < x$, then the client will throw an exception before sending $Q$ as the negotiated version is too old, so the server probably won't understand the query. But if the server does actually understand the query, and the client uses a custom implementation that does not perform the check on $x$ and $y$, then the server will reply as normal despite $y < x$.
```
