### Title
Wrong `boundX` in Taylor-Series Convergence Loop Causes Incorrect Peras Committee Seat Count - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

### Summary

`localSortitionNumSeats` passes the hardcoded literal `3` as the `boundX` parameter to `taylorExpCmpFirstNonLower`. The function's own contract requires `boundX = e^{|x|}` for correct error bounds. Here `x = -lambda` where `lambda` is the Poisson parameter for local sortition, which can far exceed `ln(3) ≈ 1.099` for any non-trivial stakeholder. When `lambda > ln(3)`, the error term is underestimated, the Taylor-series comparison loop terminates prematurely with a wrong result, and the returned seat count is incorrect. Because `implVerifyVote` and `implVerifyCert` in `WFALS.hs` gate non-persistent vote acceptance on this seat count being non-zero, an ineligible voter can have their vote accepted, or an eligible voter's vote can be rejected, breaking Peras voting authorization.

### Finding Description

`taylorExpCmpFirstNonLower` approximates `e^x` via a Taylor series and uses an error bound to decide, for each threshold in `cmps`, whether the partial sum is definitively above or below `e^x`. The error bound at each step is:

```haskell
errorTerm = abs (err' * boundX)   -- LS.hs:175
```

The function's contract is explicit:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds
taylorExpCmpFirstNonLower ::
  -- | boundX = e^{|x|} for correct error estimation
  a ->
``` [1](#0-0) 

The call site passes `3` unconditionally:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- hardcoded, should be e^lambda
      orders
      (-lambda)
``` [2](#0-1) 

Here `x = -lambda`, so the correct `boundX` is `e^lambda`. The value `3` is valid only when `lambda <= ln(3) ≈ 1.099`. The Poisson parameter is:

```haskell
lambda = fromRational $
  fromIntegral numNonPersistentVoters * voterStake / totalNonPersistentStake
``` [3](#0-2) 

`lambda` scales with `numNonPersistentVoters`. With a committee of 100 non-persistent voters, any voter holding more than ~1.1% of the non-persistent stake produces `lambda > ln(3)`. With a committee of 500, the threshold drops to ~0.22%. These are routine configurations.

The code itself acknowledges the uncertainty with a TODO:

```
-- TODO(peras): evaluate whether the limit used below (3) makes sense in
-- this context. One possible starting point would be to understand why
-- @checkLeaderNatValue@ (in Ledger) also uses 3 as its own limit when
-- computing slot leadership proofs.
-- Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234
``` [4](#0-3) 

The `3` was copied from the Praos leader-election context (`checkLeaderNatValue`) where `x = -sigma * ln(1-f)` and `|x| <= f <= 0.2`, making `e^{0.2} ≈ 1.22 < 3` a valid conservative bound. That reasoning does not transfer to local sortition where `lambda` is unbounded above `ln(3)`.

**Mechanical effect of the wrong bound.** When `boundX < e^lambda`, `errorTerm` is too small, narrowing the "uncertain" zone `[acc' - errorTerm, acc' + errorTerm]`. `decideOne` then makes premature decisions:

- `cmp >= acc' + errorTerm → Stop` (declared ABOVE) even though `cmp < e^{-lambda}` → voter receives **more seats than deserved**
- `cmp < acc' - errorTerm → Below` even though `cmp >= e^{-lambda}` → voter receives **fewer seats than deserved** [5](#0-4) 

### Impact Explanation

`localSortitionNumSeats` is called in three security-critical paths in `WFALS.hs`:

**1. `implVerifyVote`** — non-persistent vote acceptance:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing -> Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats -> pure $ WFALSNonPersistentMember ...
``` [6](#0-5) 

If `localSortitionNumSeats` returns a non-zero value when the correct answer is zero, an ineligible non-persistent voter's vote is accepted. This is a direct bypass of Peras voting authorization.

**2. `implVerifyCert`** — certificate verification:

```haskell
let numSeats =
      localSortitionNumSeats
        (nonPersistentCommitteeSize committee)
        (totalNonPersistentStake committee)
        voterStake
        (normalizeVRFOutput vrfOutput)
case nonZero numSeats of
  Nothing -> Left (ZeroNonPersistentSeats seatIndex)
  Just nonZeroNumSeats -> pure (WFALSNonPersistentMember ...)
``` [7](#0-6) 

A certificate containing votes from ineligible non-persistent members passes verification.

**3. `implEligiblePartyVoteWeight`** — vote weight inflation:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake / nonPersistentStake
``` [8](#0-7) 

An inflated seat count directly multiplies the voter's effective voting power, allowing a single voter to exceed their stake-proportional share of the quorum threshold.

The combined effect is that a non-persistent committee candidate with `lambda > ln(3)` — a routine condition — can have their eligibility and vote weight computed incorrectly, enabling unauthorized certificate acceptance or quorum manipulation. This maps to the allowed impact: **bypass of Peras voting or certificate checks that enables unauthorized vote or certificate acceptance**.

### Likelihood Explanation

High. The condition `lambda > ln(3)` is met whenever `numNonPersistentVoters * (voterStake / totalNonPersistentStake) > 1.099`. With a 100-seat non-persistent committee, any voter with more than ~1.1% of the non-persistent stake triggers the bug. This is a normal operating condition for any moderately large stakeholder participating in Peras. No special privileges, key compromise, or social engineering are required — the voter only needs to submit a vote through the standard Peras miniprotocol.

### Recommendation

Replace the hardcoded `3` with the correct `e^lambda`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^{|x|} = e^lambda since x = -lambda
      orders
      (-lambda)
```

Since `lambda` is already a `FixedPoint`, `exp` must be the fixed-point exponential from `Cardano.Ledger.NonIntegral` (or equivalent). Alternatively, a conservative upper bound can be computed as `exp (ceiling lambda)` if a closed-form `exp` is unavailable, but the exact value is preferable. The TODO at line 86–92 should be resolved and the tracking issue closed.

### Proof of Concept

Consider:
- `numNonPersistentVoters = 10`
- `voterStake / totalNonPersistentStake = 0.2` (voter holds 20% of non-persistent stake)
- `lambda = 10 * 0.2 = 2.0`
- Correct `boundX = e^2.0 ≈ 7.389`; used `boundX = 3`

At Taylor step `n` with `x = -2.0`, the partial sum oscillates. The error bound at step `n` is `|x^{n+1}/(n+1)!| * e^{|x|}`. With `boundX = 3` instead of `7.389`, the error is underestimated by a factor of `7.389/3 ≈ 2.46`. At early steps (e.g., `n = 2`, partial sum `= 1 - 2 + 2 = 1`, true value `e^{-2} ≈ 0.135`), the error term with correct `boundX` is `|(-2)^3/6| * 7.389 ≈ 9.85`, correctly keeping the comparison uncertain. With `boundX = 3`, the error term is `≈ 4.0`, still large enough here. But for a threshold `orders[0] = normalizedVRFOutput / lambda` near `e^{-lambda}`, the premature narrowing of the error zone causes `decideOne` to return `Stop` (ABOVE) at an early iteration where the partial sum has not yet converged, yielding `expectedSeats = 1` when the correct answer is `0`. The voter then passes the `nonZero numSeats` gate in `implVerifyVote` and their vote is accepted. [2](#0-1) [9](#0-8) [10](#0-9)
