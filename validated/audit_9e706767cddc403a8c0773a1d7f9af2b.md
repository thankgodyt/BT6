### Title
`checkPreferTheirsOverOurs` Uses `emptyPerasWeightSnapshot` Instead of Real Peras Weights, Causing Incorrect Chain-Selection Disconnect Beyond the Forecast Horizon — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The ChainSync client's `checkPreferTheirsOverOurs` guard — invoked whenever a peer's header slot falls outside the current forecast horizon — evaluates chain preference using a hard-coded `emptyPerasWeightSnapshot`. The actual chain-selection logic in `ChainSel.hs` evaluates the same comparison using the real, non-empty `PerasWeightSnapshot`. When Peras certificates are active, the two evaluations can disagree: the guard may declare a peer's chain non-preferable (and disconnect) even though the real weighted comparison would declare it preferable and canonical. An unprivileged peer serving the canonical Peras-boosted chain can therefore be silently ejected, leaving the honest node permanently on a lighter, non-canonical fork.

---

### Finding Description

**Vulnerable site — `checkPreferTheirsOverOurs`:**

```haskell
-- Client.hs lines 1834-1857
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty, ignores Peras boosts
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
```

This function is reached inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` (the header is beyond the forecast horizon):

```haskell
-- Client.hs lines 1814-1817
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
```

**Correct site — `constructPreferableCandidates` in `ChainSel.hs`:**

```haskell
-- ChainSel.hs line 777
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
```

Here `weights` is the live `PerasWeightSnapshot` passed into the function, which contains real Peras certificate boosts.

**The two code paths inside `preferAnchoredCandidate`:**

```haskell
-- AnchoredFragment.hs lines 186-213
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- tip-only comparison: selectView on the head block (block number)
      ...
  | otherwise =
      -- suffix comparison: weightedSelectView sums block-number + Peras weights
      -- over the entire suffix after the intersection
      ...
```

When `weights` is empty (as in `checkPreferTheirsOverOurs`), the function compares only the tip block numbers of the two chains. When `weights` is non-empty (as in real chain selection), it compares the total weighted length of each chain's suffix after the intersection point. These two metrics can disagree whenever Peras certificates boost blocks on one fork but not the other.

**Concrete divergence scenario:**

| Dimension | `checkPreferTheirsOverOurs` | Real chain selection |
|---|---|---|
| Metric | Tip block number only | Block count + Peras certificate weights |
| Snapshot | `emptyPerasWeightSnapshot` | Live `PerasWeightSnapshot` |
| Outcome when peer chain is shorter by block count but heavier by Peras weight | `ShouldNotSwitch` → disconnect | `ShouldSwitch` → adopt |

### Impact Explanation

When Peras is active and the canonical chain carries Peras certificate boosts that make it heavier than the local selection despite having fewer blocks, the following sequence occurs:

1. A peer sends a header whose slot is beyond the current forecast horizon.
2. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` with `emptyPerasWeightSnapshot`.
3. The tip-only comparison finds the peer's chain shorter by block number → `ShouldNotSwitch`.
4. The node throws `CandidateTooSparse` and disconnects from the peer.
5. The actual chain-selection code, if it ever received those blocks, would compute a higher weighted suffix for the peer's chain and switch.
6. The node remains on the lighter, non-canonical fork.

This is a **High** chain-selection bug: an unprivileged peer serving the canonical chain can be ejected by an honest node, causing the node to prefer a non-canonical, less-secure chain beyond the intended security assumptions of the Peras protocol.

The reverse direction (peer chain longer by block count, our chain heavier by Peras weight) causes the node to wait indefinitely for a chain it will ultimately reject — a secondary liveness impact.

---

### Likelihood Explanation

- **Peras activation required.** The discrepancy is harmless while `PerasWeightSnapshot` is always empty (pre-Peras). Once Peras certificates are issued on-chain, the snapshot becomes non-empty and the divergence becomes reachable.
- **No special privileges needed.** Any peer can serve a valid chain with Peras-boosted blocks. No key compromise, stake majority, or operator action is required.
- **Forecast-horizon condition is routinely met.** During initial sync or after a long slot gap, headers routinely fall outside the forecast horizon, triggering `checkPreferTheirsOverOurs` on every such header.
- **Acknowledged by developers.** The inline `TODO` comment at line 1841 explicitly flags this check for removal (`https://github.com/tweag/cardano-peras/issues/64`), confirming the developers recognise the check is incorrect in the Peras setting.

---

### Recommendation

Replace the hard-coded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live `PerasWeightSnapshot` that is already available in the `ChainSelEnv` / `ChainDbView` context, so that the disconnect guard uses the same metric as the real chain-selection logic. Alternatively, follow the referenced issue and remove the check entirely, replacing it with a density-based Genesis guard that is Peras-weight-aware. Either way, the guard and the selection logic must agree on what "preferable" means.

---

### Proof of Concept

**Entry path (no special privileges):**

1. Peras is active; the local node's current selection contains blocks boosted by Peras certificates (non-empty `PerasWeightSnapshot`).
2. A remote peer (unprivileged) serves a chain that is the canonical chain: it is shorter by raw block count than the local selection but carries enough Peras certificate weight to be heavier in total.
3. The peer sends a header whose slot exceeds `forecastAt + stabilityWindow` of the intersection ledger state.
4. `checkTime` → `readLedgerState` → `projectLedgerView` returns `Nothing` (outside forecast range).
5. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`.
6. `preferAnchoredCandidate` takes the `isEmptyPerasWeightSnapshot` branch, compares tip block numbers, finds the peer's tip block number lower, returns `ShouldNotSwitch`.
7. `throwSTM CandidateTooSparse` fires; the peer is disconnected.
8. The node never downloads the canonical chain's blocks; it remains on the lighter fork.

          (Empty ourAnchor, _ :> theirTip) ->

            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))

              ShouldNotSwitch o -> ShouldNotSwitch o

      case AF.intersect ours cand of
