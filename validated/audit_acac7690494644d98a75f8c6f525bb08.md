Audit Report

## Title
Push-Based ETH and ERC-1155 Delivery in `finTransfer` Permanently Freezes Bridged Funds When Recipient Reverts - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.finTransfer()` delivers native ETH and ERC-1155 tokens to the recipient using a push pattern. If the recipient contract reverts on receipt, the entire transaction reverts — including the nonce-consumed write — and the transfer can never be finalized. Because the recipient address is cryptographically bound inside the MPC-signed payload, no relayer can substitute an alternative recipient. Tokens burned or locked on NEAR at initiation time are permanently unrecoverable, and ERC-1155 tokens held by the bridge contract are permanently frozen.

## Finding Description

In `finTransfer`, the nonce is marked consumed at line 287 before any asset transfer occurs: [1](#0-0) 

For native ETH, the push delivery at lines 319–322 calls the recipient with value. If the recipient's `receive`/`fallback` reverts, `revert FailedToSendEther()` unwinds the entire transaction, including the line-287 write: [2](#0-1) 

For ERC-1155, `safeTransferFrom` at lines 324–330 invokes `onERC1155Received` on the recipient. If the recipient does not implement `IERC1155Receiver`, the call reverts identically: [3](#0-2) 

The recipient address is Borsh-encoded into the signed payload at line 298 and the signature is verified at line 311: [4](#0-3) [5](#0-4) 

No relayer can alter `payload.recipient` without invalidating the MPC signature. Every future call with the same signed payload produces the identical revert. There is no pull-withdrawal mapping, no admin rescue function, and no `finTransferExtension` override that provides a fallback path: [6](#0-5) 

On the NEAR side, tokens are burned or locked at `init_transfer` time. There is no mechanism for NEAR to detect a permanently failing EVM finalization and issue a refund — the NEAR side only processes a `FinTransfer` event that is never emitted when EVM finalization always reverts.

## Impact Explanation

This matches the critical allowed impact: **permanent freezing of bridged funds**. For native ETH transfers, the user's NEAR-side tokens are permanently burned with no EVM delivery ever possible. For ERC-1155 transfers, the tokens held by the bridge contract (deposited during prior EVM→NEAR `initTransfer1155` flows) are permanently locked with no claimable path. No privileged action can recover either asset class.

## Likelihood Explanation

Smart contracts that do not implement a payable `receive`/`fallback` are ubiquitous: Gnosis Safe multisigs deployed without a payable fallback, ERC-20 token contracts, protocol vaults, and governance contracts. A user bridging native ETH directly into any such contract — a routine DeFi operation — triggers this condition without any on-chain warning. The scenario requires no privileged access, no attacker cooperation, and no exotic precondition; the user's own legitimate cross-chain transfer is sufficient. The ERC-1155 path is equally reachable: any recipient that does not implement `IERC1155Receiver` triggers the identical freeze.

## Recommendation

Replace the push pattern with a pull pattern for both asset types in `finTransfer`:

1. For native ETH: instead of `payload.recipient.call{value: payload.amount}("")`, credit `ethBalance[payload.recipient] += payload.amount` in a `mapping(address => uint256)` and add a public `withdrawETH()` function that sends `ethBalance[msg.sender]` to the caller and zeroes the balance.
2. For ERC-1155: wrap `safeTransferFrom` in a try/catch; on failure, record the pending transfer in a mapping keyed by recipient and add a `claimERC1155()` function for the recipient to pull the tokens.
3. In both cases, ensure `completedTransfers[payload.destinationNonce] = true` is never rolled back — the nonce must be consumed regardless of delivery success so the signed payload cannot be replayed once a pull record is created.

## Proof of Concept

**Native ETH path:**
1. Deploy `RevertingContract` with `receive() external payable { revert(); }`.
2. User initiates NEAR→EVM transfer of native ETH specifying `recipient = address(RevertingContract)`.
3. NEAR MPC signs `TransferMessagePayload` with `tokenAddress = address(0)`, `amount = X`, `recipient = address(RevertingContract)`.
4. Relayer calls `OmniBridge.finTransfer{value: X}(signatureData, payload)`.
5. Execution reaches line 319: `payload.recipient.call{value: X}("")` → callee reverts.
6. Line 322: `revert FailedToSendEther()` unwinds the entire transaction; `completedTransfers[nonce]` remains `false`.
7. Every subsequent call with the same signed payload produces the identical revert.
8. User's NEAR tokens are permanently burned; EVM delivery is permanently impossible.

**ERC-1155 path:**
1. Deploy `NoReceiverContract` without `IERC1155Receiver`.
2. User initiates NEAR→EVM transfer of an ERC-1155 token specifying `recipient = address(NoReceiverContract)`.
3. Relayer calls `finTransfer`; execution reaches line 324: `safeTransferFrom` calls `onERC1155Received` on `NoReceiverContract` → reverts.
4. Transaction unwinds; ERC-1155 tokens remain locked in the bridge contract permanently.

A local Foundry test can confirm both paths: deploy the reverting/non-receiver contracts, call `finTransfer` with a valid mock signature, and assert the transaction reverts and `completedTransfers[nonce]` is `false` after each attempt.
