### Title
Minimum Deposit Threshold Validated Against Gross Amount Before Fee Deduction - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
In `internal_verify_deposit`, the `min_deposit_amount` guard is applied to the raw `deposit_amount` before protocol fees are subtracted. After the check passes, `deposit_fee` is deducted to produce `mint_amount`. The net `mint_amount` is never re-validated against `min_deposit_amount`, so a deposit that satisfies the on-chain minimum check can result in nBTC being minted below the intended minimum threshold.

### Finding Description
`internal_verify_deposit` (deposit.rs L45) performs:

```rust
if deposit_amount < config.min_deposit_amount {
    // → unavailable_utxo_callback: no mint
} else {
    let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
    let mint_amount = deposit_amount - deposit_fee;   // net, never re-checked
    // … verify_deposit_callback mints mint_amount
}
```

`BridgeFee::get_fee` (config.rs L30–35) returns:

```rust
std::cmp::max(
    amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
    self.fee_min,   // flat minimum fee
)
```

When `fee_min > 0` (a flat-fee configuration), a deposit of exactly `min_deposit_amount` satoshis passes the gross check but yields:

```
mint_amount = min_deposit_amount − fee_min   <   min_deposit_amount
```

`mint_amount` is passed directly to `verify_deposit_callback` and minted without any re-check against `min_deposit_amount`. The integration test fixture sets `fee_min = 10_000` via `set_deposit_bridge_fee(10000, 0, 9000)`, confirming this is a live configuration path.

### Impact Explanation
The `min_deposit_amount` policy — documented as "The min amount must be met during verify_deposit, otherwise NBTC will not be minted for the user" — is bypassed at the net level. With `min_deposit_amount = 20_000` and `fee_min = 10_000`, a deposit of exactly 20_000 satoshis passes the guard but mints only 10_000 nBTC — 50 % of the stated minimum. The protocol's minimum-deposit guarantee is violated: deposits that should be economically unviable are processed and result in sub-minimum nBTC issuance. This is a bypass of a bridge policy limit (Medium allowed impact).

### Likelihood Explanation
Any unprivileged depositor can trigger this by sending exactly `min_deposit_amount` satoshis to their bridge deposit address and submitting a valid Merkle proof. No privileged role, leaked key, or external dependency compromise is required. The condition is reachable whenever `fee_min > 0`, which is the standard production fee configuration shown in the integration tests.

### Recommendation
After computing `mint_amount`, re-validate it against the minimum before proceeding to the callback:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
if mint_amount < config.min_deposit_amount {
    return promise.then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_UNAVAILABLE_UTXO_CALL_BACK)
            .unavailable_utxo_callback(recipient_id, pending_utxo_info),
    );
}
```

Alternatively, document and enforce a configuration invariant `fee_min < min_deposit_amount` inside `Config::assert_valid`.

### Proof of Concept
1. Deploy bridge with `min_deposit_amount = 20_000` and `deposit_bridge_fee = { fee_min: 10_000, fee_rate: 0, protocol_fee_rate: 9_000 }`.
2. Depositor sends exactly 20_000 satoshis to their derived bridge deposit address.
3. Relayer calls `verify_deposit` with a valid Merkle proof.
4. Gross check: `20_000 >= 20_000` → passes, enters the `else` branch.
5. Fee: `get_fee(20_000) = max(20_000 × 0 / 10_000, 10_000) = 10_000`.
6. `mint_amount = 20_000 − 10_000 = 10_000`.
7. `verify_deposit_callback` mints **10_000 nBTC** — below `min_deposit_amount` of 20_000.
8. The minimum-deposit policy is violated at the net level; the deposit that should have been routed to `unavailable_utxo_callback` instead produces sub-minimum nBTC issuance. [1](#0-0) [2](#0-1) [3](#0-2)
