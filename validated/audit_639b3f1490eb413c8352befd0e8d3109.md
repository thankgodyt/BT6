### Title
Silent downgrade from invalid-gas `post_action` to plain mint consumes deposit address without executing intended action — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
When a depositor submits a `DepositMsg` whose `post_action` carries `gas` below `MIN_PER_POST_ACTIONS_GAS` (30 Tgas), `check_deposit_msg` returns `None` and the bridge silently proceeds with a plain nBTC mint instead of rejecting the deposit. The UTXO is permanently consumed, so the user cannot retry with a corrected gas value.

### Finding Description
`check_deposit_msg` is designed to validate `post_actions` and return `None` on any validation failure. [1](#0-0) 

The caller, `internal_verify_deposit`, treats the `None` return identically to a `deposit_msg` that had no `post_actions` at all — it passes `None` straight into `verify_deposit_callback`: [2](#0-1) 

`verify_deposit_callback` forwards `post_actions` (now `None`) to `internal_mint_promise` without any guard: [3](#0-2) 

`internal_mint_promise` calls `ext_nbtc::mint` with `post_actions = None`, producing a plain mint: [4](#0-3) 

On callback success, the UTXO is permanently recorded and the deposit address is consumed: [5](#0-4) 

### Impact Explanation
The user's BTC is deposited and nBTC is minted to `recipient_id` without the intended `post_action` (e.g., a DeFi supply/collateral call). Because the UTXO is marked spent and the deposit address is derived from the exact `deposit_msg` hash (including the invalid gas value), the user cannot resubmit the same BTC output with a corrected gas value. The user receives nBTC but loses the ability to have the post-action executed, and the deposit address is permanently consumed. No funds are stolen, placing this squarely in the Low impact tier.

### Likelihood Explanation
Any unprivileged depositor can trigger this by constructing a `DepositMsg` with `post_action.gas = Some(Gas::from_tgas(29))` and sending BTC to the derived address. The relayer then calls the public `verify_deposit` entry point. No privileged access is required. The path is fully reachable in production.

### Recommendation
In `internal_verify_deposit`, distinguish between "no post_actions requested" (`deposit_msg.post_actions == None`) and "post_actions requested but invalid" (the `check_deposit_msg` return of `None` when `post_actions` was `Some`). When the user explicitly provided `post_actions` that fail validation, the deposit should be rejected (panic/require) rather than silently downgraded. One concrete fix: return a `Result` or a dedicated enum from `check_deposit_msg` so the caller can differentiate the two cases and `require!` on the invalid case. [6](#0-5)
