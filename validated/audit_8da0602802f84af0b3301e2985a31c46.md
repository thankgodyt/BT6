Audit Report

## Title
Token Transfer Failure in `finTransfer` Permanently Freezes Bridged Funds - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
In `OmniBridge.sol`, `finTransfer` performs direct token/ETH/ERC1155 transfers to `payload.recipient` with no fallback or pull-payment mechanism. If any transfer reverts — e.g., USDC blacklisting the recipient, or a contract recipient rejecting ETH — the entire transaction reverts atomically, leaving the nonce unconsumed. Because the recipient is cryptographically bound in the MPC-signed payload and no public cancel or refund function exists on the NEAR side, the user's funds are permanently frozen in the NEAR bridge contract with no recovery path.

## Finding Description
`finTransfer` marks the nonce at line 287 before performing the transfer: [1](#0-0) 

Then, depending on token type, it performs a direct transfer:

- Native ETH: `call{value: payload.amount}` with `revert FailedToSendEther()` on failure [2](#0-1) 
- ERC1155: `safeTransferFrom`, which reverts if recipient does not implement `IERC1155Receiver` [3](#0-2) 
- Native ERC20: `safeTransfer`, which reverts on USDC blacklist or other token-level rejection [4](#0-3) 

Because Solidity reverts are atomic, the nonce marking at line 287 is also rolled back. The nonce is therefore never permanently consumed, and the call can be retried indefinitely — but every retry produces the same revert. The recipient address is fixed in the MPC-signed Borsh-encoded payload: [5](#0-4) 

No new MPC signature can be obtained for a different recipient without a new NEAR-side transfer initiation. The original funds were already burned or locked on NEAR when the transfer was initiated. A search across the entire NEAR contract confirms there is no `cancel_transfer`, `refund_transfer`, or equivalent public function. The internal `remove_transfer_message` is not callable by users: [6](#0-5) 

The `pending_transfers` map retains the entry indefinitely, but no public interface allows the user to reclaim the locked/burned tokens. The identical pattern exists in the Starknet bridge, where `_set_transfer_finalised` is called before `IERC20Dispatcher.transfer`, and `assert(success, 'ERR_TRANSFER_FAILED')` reverts the whole transaction on failure.

## Impact Explanation
This constitutes permanent freezing of bridged funds across NEAR and EVM (and Starknet), which is explicitly listed as a Critical allowed impact. The user cannot recover funds, change the recipient, or retry with a different address. The NEAR-side tokens are irrecoverably locked.

## Likelihood Explanation
Low but non-zero and realistic. USDC — a major asset expected to be bridged — enforces a blacklist on every `transfer` and `transferFrom`. If a recipient address is blacklisted between transfer initiation on NEAR and EVM finalization, the transfer is permanently blocked. USDC blacklisting is a documented, recurring real-world event (OFAC compliance). Any token with blacklist functionality is subject to this scenario. The ETH-rejection variant (contract recipient with reverting `receive`) is reachable by any user specifying a smart-contract address. The ERC1155 variant is reachable by any recipient that does not implement `IERC1155Receiver`.

## Recommendation
Use the pull (claim) pattern: instead of pushing tokens directly to `payload.recipient`, store them in the contract under the recipient's address and expose a `claim(tokenAddress)` function. Alternatively, wrap the transfer in a `try/catch` and credit a claimable balance on failure:

```solidity
try IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount) {
    // success
} catch {
    claimable[payload.recipient][payload.tokenAddress] += payload.amount;
}
```

This ensures `finTransfer` always succeeds (consuming the nonce permanently), preventing fund lockup regardless of recipient-side token restrictions. Apply the same fix to the ETH, ERC1155, and Starknet transfer paths.

## Proof of Concept
1. User initiates a USDC transfer from NEAR to EVM, specifying EVM address `R`. NEAR burns/locks the USDC and stores a `TransferMessage` in `pending_transfers`.
2. The MPC network signs the transfer message, cryptographically binding `R` as recipient.
3. Between initiation and finalization, USDC blacklists `R` (e.g., OFAC compliance action).
4. A relayer calls `finTransfer(signature, payload)` on `OmniBridge.sol`.
5. `completedTransfers[payload.destinationNonce] = true` executes at line 287.
6. `IERC20(payload.tokenAddress).safeTransfer(R, amount)` reverts — USDC rejects transfers to blacklisted addresses.
7. The entire transaction reverts atomically, including the nonce marking. The nonce is unconsumed.
8. Every subsequent retry produces the same revert. The transfer can never be finalized.
9. No public function on NEAR allows the user to cancel the pending transfer or reclaim the locked USDC. Funds are permanently frozen.

To reproduce locally: deploy a mock ERC20 with a blacklist, initiate a bridge transfer, blacklist the recipient, then call `finTransfer` and observe the permanent revert loop with no recovery path.

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
