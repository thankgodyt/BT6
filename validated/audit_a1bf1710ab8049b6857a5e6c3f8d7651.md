### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The sole production instance of `BlockSupportsPeras` implements `validatePerasCert` as a stub that unconditionally returns `Right`, accepting every inbound certificate as valid. Because the `PerasWeightSnapshot` derived from accepted certificates is actively wired into `preferAnchoredCandidate` and `compareAnchoredFragments`, an unprivileged peer can send a crafted certificate that boosts an arbitrary block and cause the receiving node to prefer a non-canonical chain.

### Finding Description
The `BlockSupportsPeras` type class declares `validatePerasCert` as the gate that must approve a `PerasCert` before it is stored and used to influence chain selection. The only instance in the codebase is a universal degenerate instance:

```haskell

This stub is the `validateCert` argument passed to `processCerts` in the production writer `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls `validateCert` on every inbound certificate and, because the stub always returns `Right`, every certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

Once stored, the certificate's weight boost enters the `PerasWeightSnapshot`. That snapshot is read by `readChainComparison` in the BlockFetch client interface: [4](#0-3) 

and is consumed directly by `preferAnchoredCandidate` and `compareAnchoredFragments` during chain selection: [5](#0-4) 

The Peras path is taken whenever `isEmptyPerasWeightSnapshot weights` is false — i.e., as soon as any certificate has been accepted. At that point the standard tip-only comparison is replaced by the weighted comparison, and the attacker-controlled boost value (`perasWeight params`) is added to the total weight of whichever block the crafted certificate names. [6](#0-5) 

The structural parallel to the reported NTT Manager bug is exact: in both cases a required validity check (ordering of transceiver indices / cryptographic certificate validity) is absent at the point of acceptance, so the system commits to the input before the check that would have rejected it is ever reached.

### Impact Explanation
An unprivileged peer that can speak the object-diffusion mini-protocol sends one crafted `PerasCert` naming a block on a minority fork. The certificate passes the no-op validation, is stored in `PerasCertDB`, and its boost is reflected in the `PerasWeightSnapshot`. On the next chain-selection run, `preferAnchoredCandidate` computes the weighted total of the minority fork as `blockNo + boost`, which may exceed the honest chain's `blockNo`, causing the node to roll back to and adopt the minority fork. This is a chain-selection safety failure triggered by a single unauthenticated network message.

### Likelihood Explanation
The object-diffusion protocol for Peras certificates is wired into the production `NodeKernel` via `makePerasCertPoolWriterFromChainDB`. Any peer that establishes a connection and speaks the protocol can submit certificates. No stake, keys, or operator access are required. The only precondition is that the target node has the Peras object-diffusion handler enabled, which is the default in the current codebase.

### Recommendation
Until full cryptographic and committee-membership validation is implemented for `validatePerasCert`, the stub should return `Left PerasValidationErr` for all inputs rather than `Right`, so that no peer-supplied certificate can enter the weight snapshot. Alternatively, the object-diffusion handler for Peras certificates should be disabled at the network layer until the validation logic tracked in issue #120 is complete.

### Proof of Concept
1. Connect to a target node that has the Peras object-diffusion handler active.
2. Craft a `PerasCert` whose `pcCertBoostedBlock` names the tip of a minority fork that is `perasWeight params - 1` blocks shorter than the honest chain.
3. Send the certificate via the object-diffusion protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right` unconditionally.
5. The certificate is stored; `PerasWeightSnapshot` now maps the minority-fork tip to `perasWeight params`.
6. On the next chain-selection trigger, `preferAnchoredCandidate` computes the minority fork's total weight as `(blockNo_minority + perasWeight) > blockNo_honest`, returns `ShouldSwitch`, and the node rolls back to the minority fork.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
