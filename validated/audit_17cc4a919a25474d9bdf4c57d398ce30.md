Audit Report

## Title
Inverted Refund Condition in `is_refund_required` Enables Replay and Double-Spend on UTXO `ft_transfer_call` Finalization - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`Contract::is_refund_required` at line 1791 evaluates `amount.0 == 0`, which returns `true` (refund required) precisely when the inner `ft_transfer_call` succeeded (receiver consumed all tokens, returning unused amount of 0). This is the exact inversion of correct NEP-141 semantics. On every successful UTXO-to-NEAR `ft_transfer_call` finalization, `resolve_utxo_fin_transfer` incorrectly calls `remove_fin_utxo_transfer`, deleting the finalization record and enabling unlimited replay of the same UTXO proof, while also returning the full bridged amount as the unused-token signal to the outer token contract's `ft_resolve_transfer`, causing a double-spend.

## Finding Description

`is_refund_required` (lines 1784–1804) reads the promise result of the inner `ft_transfer_call` — the call from the bridge to the NEAR recipient. Under NEP-141, `ft_on_transfer` returns the **unused** token amount: `0` means all tokens were consumed (success, no refund needed); `N > 0` means N tokens are unused (refund N). The inner token contract's `ft_resolve_transfer` returns this same unused amount as the result of `ft_transfer_call`.

The condition at line 1791:
```rust
amount.0 == 0   // true when receiver consumed all tokens → incorrectly signals "refund required"
```
is inverted. It returns `true` on the normal success path and `false` when tokens are actually unused.

`resolve_utxo_fin_transfer` (lines 1016–1044) acts on this:
```rust
if Self::is_refund_required(is_ft_transfer_call) {
    self.remove_fin_utxo_transfer(...);  // deletes finalization record
    amount                               // returns full amount as "unused"
} else {
    // log success event
    U128(0)
}
```

On a successful inner transfer, `is_refund_required` returns `true`, so:
1. `remove_fin_utxo_transfer` deletes the entry from `finalised_utxo_transfers`, destroying the replay guard.
2. `resolve_utxo_fin_transfer` returns `amount` (the full bridged amount) as the promise result, which the outer token contract's `ft_resolve_transfer` interprets as "all tokens unused" and refunds to the UTXO connector.

The misleading comment at line 1789 ("refund if the **used** token amount is zero") further confirms the logic inversion — `amount` is the **unused** (refund) amount, not the used amount.

The inverse failure case (receiver returns N > 0, transfer failed): `is_refund_required` returns `false`, no refund is issued, the finalization record is kept, and tokens are permanently locked.

## Impact Explanation

**Critical.** Matches two allowed impact classes:

- **Cross-chain replay / double-spending**: Deletion of the finalization record via `remove_fin_utxo_transfer` on every successful transfer allows the same UTXO proof to be resubmitted to `utxo_fin_transfer`, bypassing the "already finalised" guard and re-minting tokens from a single UTXO — unlimited unauthorized minting.
- **Double-spend / balance manipulation**: The recipient receives bridged tokens from the inner `ft_transfer_call`, and simultaneously the outer token contract refunds the full amount to the UTXO connector because `resolve_utxo_fin_transfer` returns `amount` instead of `U128(0)`. Tokens are created out of thin air on the NEAR side.

The inverse case causes permanent freezing of bridged funds (tokens locked with no refund path).

## Likelihood Explanation

**High.** The trigger is the normal happy path: any UTXO-to-NEAR transfer with a non-empty `msg` field (so `is_ft_transfer_call = true`) where the recipient's `ft_on_transfer` returns `"0"` (the correct NEP-141 success response). No privileged access, key compromise, or race condition is required. An attacker deploys a minimal NEAR contract whose `ft_on_transfer` always returns `"0"`, submits a valid UTXO proof, and the bug activates automatically. The replay loop requires no additional conditions beyond the deleted finalization record.

## Recommendation

Invert the condition in `is_refund_required` at line 1791. The refund amount returned by `ft_on_transfer` (and propagated through `ft_transfer_call`) is the **unused** token amount; a refund is required when this value is **non-zero**:

```rust
// Correct: refund is required when the receiver returned unused tokens (amount > 0)
amount.0 != 0
```

Also correct the misleading comment at line 1789: `amount` is the unused/refund amount returned by `ft_on_transfer`, not the used amount.

## Proof of Concept

1. Attacker deploys `attacker.near` with `ft_on_transfer` always returning `"0"` (NEP-141 success).
2. Attacker initiates a Bitcoin transfer to `attacker.near` with a non-empty `msg` field.
3. Attacker submits the UTXO proof to `utxo_fin_transfer`. `add_fin_utxo_transfer` records the transfer as finalised.
4. `utxo_fin_transfer_to_near_callback` calls `send_tokens` → inner `ft_transfer_call` → `attacker.near::ft_on_transfer` returns `"0"` → inner `ft_resolve_transfer` returns `U128(0)`.
5. `resolve_utxo_fin_transfer` is called. `is_refund_required` reads promise result `0`, evaluates `0 == 0 → true`, calls `remove_fin_utxo_transfer` (deletes finalization record), returns `amount`.
6. Outer token contract's `ft_resolve_transfer` receives return value `amount`, interprets it as unused tokens, and refunds `amount` to the UTXO connector. `attacker.near` already holds the tokens from step 4 — double-spend complete.
7. Because the finalization record was deleted in step 5, attacker resubmits the same UTXO proof and repeats from step 3 — unlimited minting.

**Minimal invariant test**: assert that after a successful `ft_transfer_call` finalization (inner `ft_on_transfer` returns `"0"`), `finalised_utxo_transfers` still contains the transfer ID and `resolve_utxo_fin_transfer` returns `U128(0)`. Both assertions will fail with the current code.
