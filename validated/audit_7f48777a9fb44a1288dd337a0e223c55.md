### Title
Peras Certificate Validation Stub Unconditionally Accepts All Inbound Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is an acknowledged stub that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or eligibility checks. This stub is wired directly into the production inbound-certificate processing path (`processCerts`), meaning any unprivileged peer can submit a crafted Peras certificate with an arbitrary round number, arbitrary boosted-block hash, and no valid aggregate BLS signature or voter eligibility proofs, and the node will accept it, store it in the `PerasCertDB`, and use it to influence chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory gate for certificate acceptance:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only deployed instance — explicitly labelled a "degenerate instance for all blks to get things to compile" — implements this as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is not isolated to tests. Both production `ObjectPoolWriter` constructors — `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` — pass `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`: [2](#0-1) 

`processCerts` calls this callback on every inbound certificate from a peer. If the callback returns `Right` (which it always does), the certificate is timestamped and inserted into the database unconditionally: [3](#0-2) 

Once stored in the `PerasCertDB`, the certificate's `vpcCertBoost` weight is incorporated into the `PerasWeightSnapshot` used by `chainSelectionForBlock` and `initialChainSelection` to compare candidate chains: [4](#0-3) 

The checks that are entirely absent from the stub but required by the Peras protocol include:
- Aggregate BLS signature verification over `(roundNo, boostedBlockHash)`
- Voter eligibility proof (VRF-based committee sortition) for each claimed voter seat
- Quorum threshold: the claimed voter set must represent sufficient stake
- Round-number plausibility relative to the current chain tip

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcRoundNo` and `pcCertBoostedBlock` (any block hash, including one on a minority or adversarial fork), send it over the Peras object-diffusion mini-protocol, and the receiving node will:

1. Accept the certificate without any cryptographic check.
2. Store it in `PerasCertDB`, updating the `PerasWeightSnapshot`.
3. Apply the `perasWeight` boost to the attacker-chosen block during chain selection.

This directly enables **unauthorized Peras certificate acceptance** and **chain-selection manipulation**: the node may prefer a non-canonical chain that has been artificially boosted by a fake certificate, violating the Peras safety guarantee that only honestly-certified blocks receive a weight advantage.

This matches the allowed impact: *Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance*, and *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain*.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's Peras object-diffusion endpoint and the ability to send a well-formed (but cryptographically invalid) `PerasCert` CBOR message. No keys, stake, or prior chain knowledge beyond the target block hash are needed. The stub is the only deployed instance and is used in both the `PerasCertDB`-direct and `ChainDB`-integrated production paths. Likelihood is **High** for any deployment that activates the Peras diffusion layer.

---

### Recommendation

1. **Remove the stub instance** (`instance StandardHash blk => BlockSupportsPeras blk`) from production code or gate it behind a compile-time flag that is never set in production builds.
2. **Implement full certificate validation** in `validatePerasCert` before the Peras diffusion layer is enabled in production: verify the aggregate BLS signature, each voter's VRF-based eligibility proof against the registered committee, and the quorum threshold against the stake distribution.
3. Until a real implementation exists, **disable the Peras certificate inbound path** (`makePerasCertPoolWriterFromChainDB` / `makePerasCertPoolWriterFromCertDB`) so that no peer-supplied certificate can reach `processCerts`.

---

### Proof of Concept

1. Connect to a node's Peras object-diffusion port.
2. Send a CBOR-encoded `PerasCert` with:
   - `pcRoundNo = <any round>`
   - `pcCertBoostedBlock = <hash of a block on a minority fork>`
   - No valid signature field (the stub never inspects it).
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
4. The certificate is stored via `addCert perasCertDB` / `ChainDB.addPerasCertAsync`.
5. On the next call to `chainSelectionForBlock`, `preferAnchoredCandidate` reads the updated `PerasWeightSnapshot` and applies the attacker-specified boost, potentially switching the node's selected chain to the attacker-chosen fork. [5](#0-4) [6](#0-5) [7](#0-6)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
