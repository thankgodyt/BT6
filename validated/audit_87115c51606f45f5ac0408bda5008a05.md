Audit Report

## Title
`sign_transfer` Allows Unlimited Re-Signing with Arbitrary `fee_recipient`, Enabling Fee Theft by Any Trusted Relayer - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`sign_transfer` performs a read-only lookup of the pending transfer and immediately dispatches the MPC signing call without removing or locking the entry. For non-zero-fee transfers, `sign_transfer_callback` never removes the entry — it remains in `pending_transfers` until `claim_fee` is called — so any trusted relayer can call `sign_transfer` an unlimited number of times, across any number of blocks, with an arbitrary `fee_recipient`. This allows a malicious trusted relayer to obtain a valid MPC signature directing the fee to an attacker-controlled account and submit it to the destination chain ahead of the legitimate relayer's signature, stealing the fee.

## Finding Description
`sign_transfer` (L444–521) calls `get_transfer_message` (L1453–1459), which is a pure read-only `.get()` on `pending_transfers`. No removal, no sentinel, no in-flight flag is set before the MPC cross-contract call is dispatched:

```rust
let transfer_message = self.get_transfer_message(transfer_id); // read-only
// ... validation and payload construction ...
ext_signer::ext(self.mpc_signer.clone())
    .sign(SignRequest { payload, ... })
    .then(Self::ext(...).sign_transfer_callback(...))
```

`sign_transfer_callback` (L648–668) only removes the transfer when `fee.is_zero()`:

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
    // emit SignTransferEvent regardless
}
```

For non-zero-fee transfers the entry is never touched by `sign_transfer_callback`; it stays in `pending_transfers` until `claim_fee_callback` calls `remove_transfer_message` at L1094. This means `sign_transfer` can be called repeatedly — across any number of blocks — for the same `transfer_id`, each time producing a fresh, valid MPC signature.

The `fee_recipient` parameter is a caller-supplied `Option<AccountId>` (L450) that is embedded verbatim into `TransferMessagePayload` (L498) with no validation against the caller's identity or any stored value. Two calls with different `fee_recipient` values produce two cryptographically distinct, valid payloads and two valid MPC signatures.

`claim_fee_callback` (L1079–1086) enforces that only the account named as `fee_recipient` in the destination-chain proof can claim the fee on NEAR:

```rust
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

So whichever signature reaches the destination chain first determines who receives the fee — both on the destination chain and on NEAR.

## Impact Explanation
A malicious trusted relayer calls `sign_transfer(transfer_id=T, fee_recipient=ATTACKER, fee=F)` and obtains a valid MPC signature S-A. The legitimate relayer separately calls `sign_transfer(transfer_id=T, fee_recipient=LEGITIMATE, fee=F)` and obtains S-B. The attacker submits (payload-A, S-A) to the destination chain, which credits the fee to ATTACKER. The attacker then calls `claim_fee` on NEAR with proof of this finalization, and `claim_fee_callback` pays the fee to ATTACKER. The legitimate relayer's signature S-B is rendered worthless. This is direct, concrete fee theft — matching the allowed Critical impact class of "fee mis-accounting that changes user or protocol balances."

For zero-fee transfers, two `sign_transfer` calls in the same block both read the still-present entry and both enqueue MPC signing receipts before either callback fires. Both signatures are produced and emitted as `SignTransferEvent` log entries. The first callback removes the entry; the second callback's removal panics — but both valid signatures for the same `destination_nonce` have already been produced, creating a potential double-spend risk if destination-chain nonce enforcement has any gap.

## Likelihood Explanation
The `#[trusted_relayer]` macro is the only gate. Any external account that stakes the required amount (default 1,000 NEAR) and waits the waiting period (default 7 days) becomes a trusted relayer — this is an open, permissionless process. For non-zero-fee transfers, the attack does not require same-block execution, no front-running, no validator collusion, and no external dependency failure. The attacker simply calls `sign_transfer` with `fee_recipient` set to an attacker-controlled account at any time before the legitimate relayer's signature is submitted to the destination chain. The attack is deterministic and repeatable for every non-zero-fee transfer in the system.

## Recommendation
Remove the transfer from `pending_transfers` (or insert a "signing-in-progress" sentinel) **before** dispatching the MPC cross-contract call, mirroring the atomic insert-or-panic pattern used in `add_fin_transfer` (L2226–2234) and the pre-dispatch removal used in `submit_transfer_to_utxo_chain_connector` (L84 of `btc.rs`). If re-signing on failure must be supported, re-insert the transfer in `sign_transfer_callback` when `call_result` is `Err`, analogous to the UTXO connector callback pattern. Additionally, validate that `fee_recipient` matches the caller's account ID, or remove it as a caller-supplied parameter and derive it from `env::predecessor_account_id()`.

## Proof of Concept
**Non-zero-fee path (cross-block, no timing dependency):**

```
Block N:
  TX-A: attacker (trusted relayer) calls
        sign_transfer(transfer_id=T, fee_recipient=ATTACKER, fee=F)
        → get_transfer_message(T) succeeds (entry present, not removed)
        → enqueues MPC signing receipt R-A

Block N+1:
  R-A fires → sign_transfer_callback: fee != 0, entry NOT removed
            → emits SignTransferEvent(sig=S-A, fee_recipient=ATTACKER)

Block M (any later block, entry still present):
  TX-B: legitimate relayer calls
        sign_transfer(transfer_id=T, fee_recipient=LEGITIMATE, fee=F)
        → get_transfer_message(T) succeeds (entry still present)
        → enqueues MPC signing receipt R-B

Block M+1:
  R-B fires → sign_transfer_callback: fee != 0, entry NOT removed
            → emits SignTransferEvent(sig=S-B, fee_recipient=LEGITIMATE)

Attacker submits (payload-A, S-A) to destination chain
  → destination chain credits fee to ATTACKER
  → attacker calls claim_fee on NEAR with proof
  → claim_fee_callback: fee_recipient=ATTACKER == predecessor → pays fee to ATTACKER
  → remove_transfer_message(T) called — entry finally removed

Legitimate relayer's S-B is now worthless; fee stolen.
```

A private-testnet integration test can reproduce this by: (1) registering two trusted-relayer accounts, (2) initiating a transfer with non-zero fee, (3) calling `sign_transfer` from account A with `fee_recipient=A` and from account B with `fee_recipient=B` in separate transactions, (4) verifying both `SignTransferEvent` logs are emitted with distinct signatures, and (5) confirming that submitting A's signature to the destination chain and calling `claim_fee` with the resulting proof pays the fee to A rather than B.
