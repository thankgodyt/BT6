### Title
Deposit Splitting Bypasses Higher Confirmation Requirements for Large Amounts - (File: contracts/satoshi-bridge/src/config.rs)

### Summary
The `get_confirmations` function in `Config` determines the required number of Bitcoin confirmations based solely on the per-transaction deposit amount. When the bridge is configured with a multi-tier `confirmations_strategy` (e.g., 2 confirmations for amounts ≤ 1 BTC, 6 confirmations for amounts > 1 BTC), a depositor can bypass the higher confirmation requirement for large deposits by splitting a single large deposit into multiple smaller ones. This is the direct analog of the loan-splitting attack in the reference report: a threshold-based policy applied per-operation is defeated by dividing the operation.

### Finding Description

`Config::get_confirmations` in `contracts/satoshi-bridge/src/config.rs` (lines 196–220) implements a step-function lookup over the `confirmations_strategy` map:

```rust
pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
    // ...
    keys.sort_unstable();
    for key in &keys {
        if *key > satoshi_amount {
            return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
        }
    }
    // falls through to max key
}
```

The function is called in `internal_verify_deposit` (deposit.rs, line 31) with the individual transaction's `deposit_amount`:

```rust

    self.get_confirmations(config, deposit_amount)
    ...
```

The bridge's `confirmations_strategy` is explicitly documented as "Satoshi upper limit for amount checks → confirmations" and the contract exposes `set_confirmations_strategy` to configure multiple tiers. A realistic production configuration would be, for example:

| Tier upper bound | Confirmations |
|---|---|
| 10,000,000 sat (0.1 BTC) | 2 |
| 100,000,000 sat (1 BTC) | 6 |

**Attack path:**

1. Attacker wants to deposit 1 BTC (100,000,000 sat), which would normally require 6 confirmations.
2. Instead, attacker sends 10 separate Bitcoin transactions of 10,000,000 sat each to 10 different deposit addresses (each derived from their NEAR account with a different path/nonce).
3. Each transaction falls in the lower tier and requires only 2 confirmations.
4. After 2 confirmations, the attacker (or a relayer) calls `verify_deposit` for each transaction. The bridge mints nBTC for each.
5. The attacker now holds the full 1 BTC equivalent in nBTC, secured by only 2 confirmations per transaction instead of 6.
6. The attacker then attempts a 2-block Bitcoin reorg to double-spend all 10 transactions simultaneously (all placed in the same block or adjacent blocks), recovering the BTC while retaining the nBTC.

### Impact Explanation

The `confirmations_strategy` is the bridge's primary defense against Bitcoin double-spend attacks on large deposits. Higher confirmation counts for larger amounts reflect the higher economic incentive to reorg the chain. By splitting, an attacker reduces the effective confirmation requirement from 6 to 2 for what is economically equivalent to a 1 BTC deposit. A successful double-spend results in unauthorized minting of nBTC — the attacker retains nBTC while recovering the underlying BTC. This matches the allowed impact: **bypass of bridge verification controls with real security impact** and **unauthorized minting of nBTC**.

### Likelihood Explanation

The attack is reachable by any unprivileged bridge user with no special roles. The only external requirement is the ability to perform a short Bitcoin reorg (2 blocks), which is significantly easier than a 6-block reorg. On Bitcoin mainnet this remains difficult but not impossible for a well-resourced attacker; on testnet or smaller chains it is trivial. The splitting itself requires no special access — any user can send multiple small deposits. The bridge code explicitly supports multi-tier confirmation strategies, making this a realistic production configuration.

### Recommendation

The confirmation requirement should be determined by the **cumulative** value being deposited by a user within a time window, or alternatively the bridge should enforce a minimum confirmation count that is independent of amount (i.e., always require the maximum tier's confirmations). A simpler mitigation is to track per-user pending deposit totals and apply the confirmation tier based on the running total, not the individual transaction amount.

### Proof of Concept

**Configuration:**
```
confirmations_strategy: {"10000000": 2, "100000000": 6}
```

**Single large deposit (intended behavior):**
- Deposit 100,000,000 sat in one transaction → `get_confirmations(100_000_000)` → key `100000000` is NOT `> 100000000`, falls to max key → **6 confirmations required**

**Split deposit (attack):**
- 10 deposits of 10,000,000 sat each → `get_confirmations(10_000_000)` → key `10000000` is NOT `> 10000000`, key `100000000` IS `> 10000000` → **2 confirmations required per transaction**
- Total nBTC minted: equivalent to 100,000,000 sat, secured by only 2 confirmations each
- Attacker performs a 2-block reorg invalidating all 10 transactions → double-spend succeeds

    pub fn get_confirmations(&self, satoshi_amount: u128) -> u64 {
        require!(
            !self.confirmations_strategy.is_empty(),
            "confirmations_strategy is empty"
        );
        // The key is constrained to U64 during assignment, so it won't panic.
        let mut keys = self
            .confirmations_strategy
            .keys()
            .map(|k| k.parse::<u128>().unwrap())
            .collect::<Vec<_>>();
        keys.sort_unstable();
        for key in &keys {
            if *key > satoshi_amount {
                return u64::from(*self.confirmations_strategy.get(&key.to_string()).unwrap());
            }
        }
        let max_key = keys.last().unwrap();
        u64::from(
            *self
                .confirmations_strategy
                .get(&max_key.to_string())
                .unwrap(),
        )
    }
