Looking at the refund flow in `contracts/satoshi-bridge/src/refund.rs` and `contracts/satoshi-bridge/src/api/bridge.rs`, I can identify a valid analog to the missing-sanitization vulnerability class.

---

### Title
Missing Validation of `refund_address` at `request_refund` Time Enables Attacker-Triggered Stuck Refund State - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
When `deposit_msg.refund_address` is `None`, any NEAR account can call `request_refund` with an arbitrary (including invalid) Bitcoin address string. The address is accepted and stored without format validation. Validation only occurs later in `execute_refund` via a panicking `.expect()`, permanently blocking the refund path for that UTXO and requiring DAO/Operator intervention to recover.

### Finding Description

**Root cause — no address validation at acceptance time:**

In `internal_request_refund` (`refund.rs:137–184`), when `deposit_msg.refund_address` is `None`, the `refund_address` parameter is stored verbatim with zero format checking:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
// No else-branch: when refund_address is None, any string is accepted
``` [1](#0-0) 

The raw string is then stored in `RefundRequest.refund_address`: [2](#0-1) 

**Deferred validation panics at `execute_refund` time:**

Validation only happens in `build_refund_output` via a hard `.expect()`:

```rust
let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
    .expect("Invalid refund address");
``` [3](#0-2) 

A NEAR contract panic rolls back the `execute_refund` transaction entirely. The `RefundRequest` remains in storage with the invalid address, and `verified_deposit_utxo` is never updated (that only happens inside `finalize_refund_with_psbt`, which is never reached).

**Duplicate-request guard blocks the legitimate owner:**

Once the malicious request is stored, the original depositor cannot submit a corrected one:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

**Entry point is publicly reachable:**

`request_refund` carries no caller-identity restriction beyond the attached storage deposit. Integration tests confirm regular accounts ("alice", "bob") can call it directly: [5](#0-4) 

### Impact Explanation

**Low — publicly reachable stuck-state / panic-driven fault in production bridge/token paths without direct theft.**

An attacker who pays the anti-spam storage deposit can permanently block the refund path for any deposit UTXO whose `deposit_msg.refund_address` is `None`. The original depositor's BTC is locked in the refund flow — `execute_refund` always panics, and no new refund request can be submitted — until a DAO/Operator account calls `reject_refund`. This constitutes operator-intervention-required stuck bridge state.

### Likelihood Explanation

**Medium.** The preconditions are minimal:
- The attacker needs only a NEAR account and the storage deposit (public anti-spam fee).
- The `deposit_msg` is public information (emitted as an event by `get_user_deposit_address`).
- Any deposit where the user omitted `refund_address` in their `DepositMsg` is a valid target.

The attack is cheap, repeatable across many UTXOs, and requires no privileged access.

### Recommendation

Validate `refund_address` as a well-formed address for the configured chain at the point of acceptance in `internal_request_refund`, before the Light Client cross-contract call is dispatched. Use the existing `Address::parse` (returning `Result`) and `require!` on success, mirroring the pattern already used in `build_refund_output` and `config.rs::string_to_script_pubkey`: [6](#0-5) 

This ensures an invalid address is rejected immediately with a clear error, rather than being stored and causing a deferred panic.

### Proof of Concept

1. Alice deposits BTC with `DepositMsg { refund_address: None, recipient_id: alice, ... }`. The deposit is never finalized (relayer down).
2. Attacker calls `request_refund(deposit_msg=Alice's, refund_address="not_a_valid_btc_address", tx_bytes=..., vout=0, proof=...)` with the required storage deposit attached.
3. `internal_request_refund` passes: the `None`-branch skips address validation; the Light Client call succeeds; `request_refund_callback` stores `RefundRequest { refund_address: "not_a_valid_btc_address", ... }`.
4. After `unsafe_refund_timelock_sec`, anyone calls `execute_refund(utxo_storage_key)`.
5. `build_refund_output("not_a_valid_btc_address", ...)` → `Address::parse(...)` returns `Err(...)` → `.expect("Invalid refund address")` → NEAR contract panic → transaction rolled back.
6. Alice's UTXO is stuck: `execute_refund` always panics, and a new `request_refund` for the same UTXO is blocked by the duplicate guard. Alice must wait for DAO to call `reject_refund` before the deposit can be processed normally.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
