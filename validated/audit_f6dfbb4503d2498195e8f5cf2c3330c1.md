### Title
`shelleyAfterVoting` counts all post-deadline blocks instead of only those in the stability window, causing premature era transition during Chain Growth violations - (`ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `ShelleyTransition` accumulates every block whose slot is at or after the voting deadline, without any upper-bound cutoff at the end of the stability window. The project's own documentation explicitly flags this as a bug: the counter should only count blocks that fall within the one stability-window (`3k/f` slots) immediately after the voting deadline. Because the counter is too wide, the Hard Fork Combinator (HFC) can declare an era transition as "confirmed" even when Chain Growth was violated in the correct window, violating the `DespiteChainGrowthViolation` safety invariant and potentially causing divergent era-transition decisions.

---

### Finding Description

**Voting deadline and stability window geometry**

In `applyHelper` the voting deadline is computed as:

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch   -- swindow = 3k/f
```

So the deadline sits `6k/f` slots before the epoch boundary. The stability window after the deadline therefore spans slots `[votingDeadline, votingDeadline + 3k/f)`. Blocks in the final `3k/f` slots of the epoch (`[votingDeadline + 3k/f, epochEnd)`) are **outside** that window.

**The counter**

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

There is no upper-bound check. Every block from `votingDeadline` to the epoch boundary increments the counter, including blocks in the second half of the post-deadline period.

**The transition guard**

```haskell
guard $ shelleyAfterVoting >= fromIntegral k
```

If `k` blocks accumulate in the second `3k/f`-slot window (the one that is **not** the stability window), the guard fires even though the stability window itself may have contained fewer than `k` blocks — i.e., even though Chain Growth was violated in the window that matters.

**The documented intent**

`civic_time.md` line 205 states explicitly:

> (TODO this is today's intended behavior, but **a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window**.)

The intended Iteration-4 rule is:

> Silently ignore the on-chain governance if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth).

The current code does not implement this rule correctly.

---

### Impact Explanation

When Chain Growth is violated specifically in the `[votingDeadline, votingDeadline + 3k/f)` window but not in the later `[votingDeadline + 3k/f, epochEnd)` window, the counter reaches `k` using blocks from the wrong window. The HFC then calls `singleEraTransition` → `shelleyTransition` → returns `Just epochNo`, causing `reconstructSummaryLedger` / `reconstructSummary` to emit a `TransitionKnown` bound and commit the node to the next era.

A node that transitions under these conditions will:
1. Apply the new era's ledger rules to subsequent blocks.
2. Reject blocks that are valid under the old era's rules (or accept blocks that are only valid under the new era's rules).
3. Diverge from nodes that correctly withheld the transition, producing a cross-era consensus split.

This fits the **High** impact category: *hard-fork / era-transition mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes*.

---

### Likelihood Explanation

The scenario requires a Chain Growth violation confined to the first `3k/f`-slot window after the voting deadline while the second `3k/f`-slot window remains dense enough to accumulate `k` blocks. This can arise from:

- A natural network partition that resolves before the epoch boundary.
- An adversary with a non-majority but substantial stake fraction selectively withholding blocks during the stability window.

It does not require a stake majority. The probability is low under normal conditions but non-negligible during network stress events or targeted adversarial block-withholding.

---

### Recommendation

Add an upper-bound slot check so that only blocks within the stability window after the deadline are counted:

```haskell
shelleyAfterVoting =
    ( if blockSlot blk >= votingDeadline
         && blockSlot blk <  addSlots swindow votingDeadline
      then succ
      else id
    ) $ shelleyAfterVoting tickedShelleyLedgerTransition
```

This aligns the counter with the documented Iteration-4 intent and ensures the transition is only confirmed when Chain Growth holds in the correct window.

---

### Proof of Concept

Assume `k = 2160`, `f = 1/20`, `swindow = 3k/f = 129600` slots.

- Epoch length = `10k/f = 432000` slots.
- Voting deadline = `epochStart + 432000 − 259200 = epochStart + 172800`.
- Stability window after deadline: slots `172800 – 302400` (relative to epoch start).
- Second window: slots `302400 – 432000`.

**Scenario**:
1. Only 2000 blocks (< k = 2160) fall in slots `172800 – 302400` (Chain Growth violation in the stability window).
2. 2200 blocks (≥ k) fall in slots `302400 – 432000`.

**Current behaviour**: `shelleyAfterVoting` reaches 4200 total; the guard `>= 2160` fires; `singleEraTransition` returns `Just nextEpoch`; the HFC commits to the new era.

**Correct behaviour**: only the 2000 blocks in the stability window should be counted; the guard fails; the HFC silently ignores the governance outcome and stays in the current era.

A private testnet can reproduce this by configuring a low `k`, injecting a block-production gap in the first post-deadline window, and observing that `singleEraTransition` returns `Just` when it should return `Nothing`.
