### Title
Peras Certificate and Vote Validation Stub Unconditionally Accepts Any Certificate/Vote, Bypassing Cryptographic Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The catch-all `BlockSupportsPeras` instance for `StandardHash blk` implements `validatePerasCert` as an unconditional `Right` (always succeeds regardless of content) and `validatePerasVote` as a pure stake-distribution lookup with no signature verification. Because this is the only `BlockSupportsPeras` instance in the codebase, every call to `validatePerasCert` in the Peras certificate pipeline accepts any crafted certificate without performing any cryptographic check. This is the direct consensus analog of the `maxRedeem` bug: just as `maxRedeem` only reads a balance without executing the required redemption, `validatePerasCert` only wraps the certificate struct without executing the required BLS aggregate-signature verification.

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the sole `BlockSupportsPeras` instance is declared as a catch-all over `StandardHash blk`:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
```

`validatePerasCert` unconditionally returns `Right (ValidatedPerasCert ...)` for every input. It never inspects the `pcSignature` field (the BLS aggregate signature) or any other cryptographic material in the certificate. The real verification logic — `implVerifyCert` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/WFALS.hs` — exists but is never wired into any `BlockSupportsPeras` instance.

`validatePerasVote` only checks whether the voter's ID appears in the stake distribution (`lookupPerasVoteStake`). It does not verify the BLS vote signature (`pvSignature`) or the VRF eligibility proof (`pvEligibilityProof`) that non-persistent committee members must supply.

The `ValidatedPerasCert` and `ValidatedPerasVote` newtypes are the type-level proof that validation succeeded. Once a certificate passes `validatePerasCert`, it is stored in `PerasCertDB` and its `vpcCertBoost` weight is applied to chain selection via `getWeightSnapshot`. The chain-selection logic in `ChainSel.hs` trusts this weight unconditionally.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` that names any block as the boosted block and any round number, with a completely fabricated or zeroed `pcSignature`. Because `validatePerasCert` never checks the signature, the certificate is accepted, stored, and its weight boost is applied to chain selection. This allows the attacker to make an honest node assign arbitrarily large Peras weight to a block of the attacker's choosing, causing the node to prefer a non-canonical or adversarially-chosen chain over the honest chain. This is a chain-selection safety failure reachable by any unprivileged peer.

Similarly, a peer can forge votes for any committee member whose ID appears in the stake distribution, without possessing that member's BLS signing key or VRF key. Forged votes accumulate toward quorum, causing the node to forge a certificate for an attacker-chosen block.

### Likelihood Explanation

The Peras certificate and vote diffusion mini-protocol is designed to accept certificates and votes from any connected peer. No privileged access, key material, or stake majority is required. The attacker only needs to be a connected peer and know the structure of the `PerasCert`/`PerasVote` CBOR encoding. The stub has been in place since the Peras feature was introduced and is the only instance in the codebase.

### Recommendation

Wire the real cryptographic verification into the `BlockSupportsPeras` instance. For certificates, call `implVerifyCert` from `Ouroboros.Consensus.Committee.WFALS` (or the equivalent for the `EveryoneVotes` scheme) inside `validatePerasCert` before constructing `ValidatedPerasCert`. For votes, call `implVerifyVote` (which verifies the BLS signature and VRF proof) inside `validatePerasVote` before constructing `ValidatedPerasVote`. Until real validation is wired in, the Peras certificate and vote acceptance paths must not be exposed to untrusted peers.
