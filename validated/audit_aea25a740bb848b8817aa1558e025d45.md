### Title
Caller-Supplied `key_version` Not Committed in `btc_pending_sign_id` Allows Any Account to Grief Withdrawals with Invalid MPC Signatures - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is publicly callable by any NEAR account and accepts a caller-supplied `key_version` that is not committed to in the `btc_pending_sign_id`. A malicious actor can front-run a legitimate withdrawal signing call with a wrong `key_version`, causing the MPC to produce an invalid signature that is permanently stored, rendering the withdrawal transaction unbroadcastable and temporarily locking user funds.

---

### Finding Description

The `sign_btc_transaction` function accepts three parameters: `btc_pending_sign_id`, `sign_index`, and `key_version`. [1](#0-0) 

The `btc_pending_sign_id` is derived from the PSBT transaction ID via `psbt.get_pending_id()`: [2](#0-1) 

This computes the Bitcoin txid of the unsigned transaction, which commits to the transaction structure (inputs, outputs) but **not** to `key_version`. The function has no access control beyond the pause check — any NEAR account can call it for any pending transaction.

The `key_version` is passed directly to the MPC signing request without any validation or storage: [3](#0-2) 

In NEAR Chain Signatures, `key_version` selects which MPC key is used to sign. If a wrong `key_version` is used, the MPC produces a signature with a different key than the one expected for the UTXO's script pubkey. This invalid signature is then permanently stored: [4](#0-3) 

Once stored, the signature cannot be replaced due to the guard: [5](#0-4) 

This is the direct analog to the external report: the `btc_pending_sign_id` (the commitment) omits `key_version` (the security-critical parameter), allowing any caller — not just the account owner — to freely choose it. In the external report, the approved hash omitted `_proof`, allowing the last guardian to freely choose the proof data that determined liveness bond return. Here, the pending ID omits `key_version`, allowing any caller to freely choose the MPC key used to sign, determining whether the resulting transaction is valid on Bitcoin.

---

### Impact Explanation

A malicious actor can permanently invalidate any pending withdrawal transaction by front-running the legitimate signing call with a wrong `key_version`. The resulting Bitcoin transaction will be invalid (signature does not match the UTXO's expected public key) and cannot be broadcast. User funds (nBTC held by the bridge and the underlying UTXO) are locked until an operator calls `cancel_withdraw`: [6](#0-5) 

After cancellation, the user must claim from `lost_found` and loses the gas fee for the cancel transaction. This matches the allowed impact: **Medium — attacker-triggered temporary locking of bridged funds**.

---

### Likelihood Explanation

The attack requires no special privileges. Any NEAR account can call `sign_btc_transaction` for any pending transaction. The attacker only needs to monitor the blockchain for new `BTCPendingInfo` entries (emitted via `GenerateBtcPendingInfo` events) and submit a transaction with a wrong `key_version` before the legitimate caller. NEAR's public mempool and event system make this straightforward. The attack can be repeated for every withdrawal, making it a persistent griefing vector against all users.

---

### Recommendation

1. **Add access control** to `sign_btc_transaction` to restrict it to the account owner of the pending transaction (check `env::predecessor_account_id() == btc_pending_info.account_id`).
2. **Store the expected `key_version`** in `BTCPendingInfo` at creation time and validate it in `sign_btc_transaction`.
3. Alternatively, **commit `key_version` to the `btc_pending_sign_id`** so that a pending transaction is bound to a specific key version from the moment it is created.

---

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call` with a `Withdraw` message, creating `BTCPendingInfo` with `btc_pending_sign_id = X` and emitting a `GenerateBtcPendingInfo` event.
2. Mallory observes the event on-chain and immediately calls `sign_btc_transaction(X, 0, wrong_key_version)`.
3. The bridge calls the MPC with `key_version = wrong_key_version`; the MPC signs the sighash with a different key and returns a valid-looking `SignatureResponse`.
4. The callback stores the invalid signature: `btc_pending_info.signatures[0] = Some(invalid_sig)`.
5. Alice calls `sign_btc_transaction(X, 0, correct_key_version)` but receives `"Already signed"`.
6. When all inputs are "signed" (with invalid signatures), `tx_bytes_with_sign` is assembled and the state advances to `PendingVerify`.
7. The assembled Bitcoin transaction is invalid (wrong public key in witness) and is rejected by the Bitcoin network when broadcast.
8. Alice's nBTC remains locked in the bridge until an operator calls `cancel_withdraw`, after which Alice must claim from `lost_found` and bears the cancel gas fee. [7](#0-6)

```rust
    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }
```
