Audit Report

## Title
Uninitialized `_systemAddress` After `upgradeToken` to `HyperliquedBridgeToken` Permanently Burns Bridged Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary
`OmniBridge.upgradeToken` unconditionally passes `bytes("")` to `upgradeToAndCall`, so no post-upgrade initialization is performed. `HyperliquedBridgeToken` introduces `_systemAddress`, which is only written inside `initialize()` behind the `initializer` modifier and therefore cannot be set on an already-initialized proxy. After the upgrade `_systemAddress` is permanently `address(0)`, causing the 3-arg `mint` path to immediately burn every token it mints via `_update(account, address(0), value)`, resulting in irreversible loss of bridged funds.

## Finding Description
`OmniBridge.upgradeToken` is the designated admin path for upgrading deployed bridge-token proxies:

```solidity
// OmniBridge.sol L559-566
function upgradeToken(
    address tokenAddress,
    address implementation
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    require(isBridgeToken[tokenAddress], "ERR_NOT_BRIDGE_TOKEN");
    BridgeToken proxy = BridgeToken(tokenAddress);
    proxy.upgradeToAndCall(implementation, bytes(""));   // ← always empty
}
```

`HyperliquedBridgeToken` declares `_systemAddress` as a new storage variable:

```solidity
// HlBridgeToken.sol L35
address internal _systemAddress;
```

It is written exclusively inside `initialize()`, which is guarded by the `initializer` modifier:

```solidity
// HlBridgeToken.sol L53-74
function initialize(..., address systemAddress_, ...) external initializer {
    ...
    _systemAddress = systemAddress_;
    ...
}
```

Because the proxy was already initialized as a `BridgeToken` (version 1), OpenZeppelin's `initializer` modifier will revert any subsequent call to `initialize()`. No `reinitializer()` variant exists anywhere in the contract. After `upgradeToken` points the proxy at `HyperliquedBridgeToken`, `_systemAddress` is permanently `address(0)`.

The 3-arg `mint` override in `HyperliquedBridgeToken`:

```solidity
// HlBridgeToken.sol L76-83
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value);   // _systemAddress == address(0) → burn
}
```

`_update(account, address(0), value)` is the OpenZeppelin ERC20 burn path: it decrements `totalSupply` and emits `Transfer(account, address(0), value)`. The recipient receives zero tokens.

`finTransfer` dispatches to the 3-arg mint whenever `payload.message.length > 0`:

```solidity
// OmniBridge.sol L338-349
if (payload.message.length == 0) {
    IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
} else {
    IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount, payload.message);
}
```

`finTransfer` is a public function gated only by a valid ECDSA signature from `nearBridgeDerivedAddress` (L311). Any user who initiates a cross-chain transfer from NEAR with a non-empty message will produce a legitimately signed payload that any relayer can submit, triggering the burn.

Additionally, `coreReceiveWithData` is permanently bricked because `msg.sender` can never equal `address(0)`, so every call reverts with `NotSystemAddress` (L114), freezing the HyperCore→HyperEVM path for that token.

## Impact Explanation
Permanent, irreversible loss of bridged funds for any user who bridges with `message.length > 0` after the upgrade. Tokens are minted and immediately burned in the same transaction; bridge accounting marks the transfer complete; the user receives nothing. This matches the Critical impact class: *loss or permanent freezing of bridged funds across EVM flows*.

## Likelihood Explanation
`upgradeToken` is a routine admin operation explicitly provided for migrating bridge tokens. Upgrading an existing `BridgeToken` proxy to `HyperliquedBridgeToken` is the natural and intended migration path for Hyperliquid-specific tokens. The broken state is silent — the upgrade transaction succeeds with no revert. The bug manifests on the first `finTransfer` with a non-empty message, which is a standard user-initiated cross-chain transfer. No attacker capability is required; any ordinary user bridging with a message triggers the loss.

## Recommendation
Add a `reinitializer(2)` function to `HyperliquedBridgeToken`:

```solidity
function initializeV2(
    address systemAddress_,
    address hyperCoreDeployer_
) external reinitializer(2) {
    _systemAddress = systemAddress_;
    bytes32 slot = HYPER_CORE_DEPLOYER_SLOT;
    assembly { sstore(slot, hyperCoreDeployer_) }
    emit HyperCoreDeployerSet(hyperCoreDeployer_);
}
```

Update `OmniBridge.upgradeToken` to accept and forward initialization calldata:

```solidity
function upgradeToken(
    address tokenAddress,
    address implementation,
    bytes calldata initData
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    require(isBridgeToken[tokenAddress], "ERR_NOT_BRIDGE_TOKEN");
    BridgeToken(tokenAddress).upgradeToAndCall(implementation, initData);
}
```

## Proof of Concept
1. Admin deploys `BridgeToken` implementation and `HyperliquedBridgeToken` implementation.
2. `OmniBridge.deployToken` creates a `BridgeToken` proxy `P` (initialized, version 1).
3. Admin calls `OmniBridge.upgradeToken(P, hlImpl)`. Internally: `P.upgradeToAndCall(hlImpl, bytes(""))`. Upgrade succeeds; `_systemAddress` is `address(0)`.
4. User initiates a bridge transfer from NEAR targeting `P` with `message.length > 0`.
5. NEAR bridge signs the `TransferMessagePayload`; relayer submits `OmniBridge.finTransfer(sig, payload)`.
6. `finTransfer` calls `IBridgeToken(P).mint(recipient, amount, message)` — the 3-arg overload.
7. Inside `HyperliquedBridgeToken.mint`: `_mint(recipient, amount)` credits tokens; `_update(recipient, address(0), amount)` burns them all.
8. Recipient balance: 0. `totalSupply` unchanged net. Tokens permanently destroyed. Bridge marks transfer complete.

A Foundry integration test can reproduce this by: deploying both implementations, calling `deployToken` then `upgradeToken`, then calling `finTransfer` with a payload where `message = abi.encode(uint8(0), recipient)` and asserting `IERC20(P).balanceOf(recipient) == 0` after the call.
