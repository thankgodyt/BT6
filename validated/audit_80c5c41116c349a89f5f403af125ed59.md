Audit Report

## Title
Permanent Freezing of User Funds Due to Missing Pre-Validation of `normalize_amount` at Transfer Initiation — (File: near/omni-bridge/src/lib.rs)

## Summary

`init_transfer` locks or burns user tokens and inserts the transfer into `pending_transfers` without verifying that `normalize_amount(amount_without_fee)` will be non-zero. For tokens where `origin_decimals > decimals`, any transfer whose net amount after fee is less than `10^(origin_decimals − decimals)` will normalize to zero. The subsequent `sign_transfer` call permanently reverts with `ERR_INVALID_AMOUNT_TO_TRANSFER`, and because no public cancel or refund entry point exists for pending transfers, the user's tokens are irrecoverably frozen in the bridge.

## Finding Description

`normalize_amount` performs integer floor division:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

`sign_transfer` (L475–485) calls this on `amount_without_fee()` and hard-panics if the result is zero:

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`init_transfer` (L554–557) only checks `fee.fee < amount`; it does **not** verify that the normalized net amount will be positive:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

After this check passes, `init_transfer_internal` (L1835–1864) immediately inserts the transfer into `pending_transfers`, then burns or locks the tokens with no normalization guard.

`remove_transfer_message` is called internally only from `sign_transfer_callback` (L657) — and only when signing succeeds and fee is zero — and from `remove_transfer_message_without_refund` in early-exit error paths of `init_transfer_internal` itself. There is no public `cancel_transfer` or equivalent entry point. A transfer stuck in `pending_transfers` with a zero-normalizing amount can never be signed (sign always panics) and can never be removed by the user.

The code comment at L2781–2782 acknowledges dust truncation ("When fee = 0, dust stays locked/burned") but refers only to the sub-unit remainder after normalization, not to the case where the entire net amount normalizes to zero.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows." Any user who initiates a NEAR→EVM transfer for a token with `origin_decimals > decimals` and whose `amount_without_fee < 10^diff_decimals` will have their tokens permanently locked. No MPC signature is ever produced, no destination-chain event is ever emitted, and `claim_fee` cannot be invoked. Recovery requires a DAO-level contract upgrade.

## Likelihood Explanation

Tokens with a decimal gap between NEAR (commonly 24 decimals) and EVM chains (commonly 18 decimals) are a standard, expected bridge configuration, giving `diff_decimals = 6`. Any user transferring fewer than 1,000,000 base units net of fee (a plausible dust or test amount) triggers the freeze. The entry path is the fully public NEP-141 `ft_transfer_call` callback, requiring no special role or privilege. The condition is repeatable and deterministic.

## Recommendation

Add the normalization check inside `init_transfer`, before `init_transfer_internal` is called and before any state mutation occurs:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee()
            .near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the existing guard in `sign_transfer` but places it before any state mutation, so the NEP-141 transfer is simply refunded rather than locked.

## Proof of Concept

1. Deploy a token with `origin_decimals = 24`; register it in the bridge with `decimals = 18` (`diff_decimals = 6`).
2. Call `ft_transfer_call` on the token contract with `amount = 500_000` (< 10^6) and `msg` encoding an `InitTransfer` to an EVM recipient with `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 500_000); `init_transfer_internal` inserts the transfer into `pending_transfers` and locks the 500,000 tokens.
4. A trusted relayer calls `sign_transfer` for the resulting `transfer_id`.
5. `normalize_amount(500_000, {origin_decimals:24, decimals:18}) = 500_000 / 1_000_000 = 0`.
6. `require!(amount_to_transfer > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. The transfer remains in `pending_transfers` indefinitely; the 500,000 tokens are permanently locked with no user-accessible recovery path.
