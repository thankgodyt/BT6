### Title
Unchecked `burn()` Return in `safe_mint_callback` Leaves Unbacked nBTC in Bridge Balance — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `safe_mint_callback`, when `safe_mint` returns `U128(0)` (recipient not registered), the bridge fires a compensating `burn()` cross-contract call with `.detach()`. Because the result is never observed, a silent failure of that burn leaves freshly minted nBTC tokens stranded in the bridge's own balance with no BTC backing, and simultaneously removes the UTXO from `verified_deposit_utxo`, allowing the same proof to be re-submitted.

---

### Finding Description

`safe_verify_deposit` is the Omni-Bridge integration path. After the light-client proof is verified, `verify_safe_deposit_callback` calls `safe_mint` on the nBTC contract. `safe_mint` unconditionally deposits `amount` tokens into the bridge's own balance first, then checks whether the recipient account is registered: [1](#0-0) 

If the recipient is not registered, `safe_mint` returns `PromiseOrValue::Value(U128(0))` immediately — tokens are already in the bridge balance.

Back in `safe_mint_callback`, `is_refund_required()` detects the `U128(0)` return and sets `is_success = false`. The failure branch then:

1. Removes the UTXO from `verified_deposit_utxo` (making re-submission possible).
2. Fires `burn(...).detach()` — **result never checked**.
3. Fires `transfer(...).detach()` for the NEAR refund. [2](#0-1) 

The callback is allocated only `GAS_FOR_MINT_CALL_BACK = 10 TGas`: [3](#0-2) 

Within those 10 TGas the callback must execute its own logic, schedule the `burn` receipt (`GAS_FOR_BURN_CALL = 5 TGas`), and schedule the NEAR `transfer` receipt: [4](#0-3) 

If the burn receipt fails for any reason (gas exhaustion, nBTC contract panic, storage issue), the bridge has no callback to detect or recover from the failure. The tokens minted by `safe_mint` remain in the bridge's balance permanently, and the UTXO is absent from both `verified_deposit_utxo` and the bridge's UTXO set — meaning the same proof can be re-submitted to repeat the cycle.

Contrast this with the normal withdrawal burn path, which always attaches a checked callback: [5](#0-4) 

---

### Impact Explanation

If the detached `burn()` fails, nBTC tokens exist in the bridge's own balance without any corresponding BTC locked in the bridge's UTXO set. This inflates the circulating supply above the backed supply. Those tokens sit in the bridge balance and can interact with future withdrawal accounting (the bridge burns from its own balance during `verify_withdraw`), potentially allowing a future withdrawal to consume tokens that were never legitimately deposited. This is a broken callback rollback / supply-below-backed-supply scenario.

**Impact: Medium** — supply inflation without direct immediate theft, but the bridge's core accounting invariant (every nBTC is backed 1:1 by a locked UTXO) is violated.

---

### Likelihood Explanation

The trigger condition — a `safe_verify_deposit` call for a recipient account that is not registered on NEAR — is reachable by any public relayer or user. The Omni Bridge integration explicitly uses this path. Gas tightness in the 10 TGas callback window makes silent burn failure a realistic, not merely theoretical, outcome. No privileged access is required.

---

### Recommendation

Replace the fire-and-forget `.detach()` burn with a checked promise chain, exactly as done in `verify_withdraw_burn_promise`. Add a `safe_mint_burn_callback` that verifies `is_promise_success()` and, on failure, either panics (reverting the UTXO removal) or re-inserts the UTXO into `verified_deposit_utxo` and emits an alert event. Also increase `GAS_FOR_MINT_CALL_BACK` to accommodate the burn + transfer receipts safely.

---

### Proof of Concept

1. Attacker identifies a NEAR account ID that is **not** registered (no storage deposit) on the nBTC contract.
2. Attacker (or any relayer) sends BTC to the deposit address derived from a `DepositMsg` with `recipient_id = <unregistered_account>` and `safe_deposit = Some(SafeDepositMsg{...})`.
3. Relayer calls `safe_verify_deposit` with a valid `TxInclusionProof`.
4. `verify_safe_deposit_callback` passes light-client verification, inserts UTXO into `verified_deposit_utxo`, then calls `safe_mint`.
5. `safe_mint` deposits `amount` nBTC into bridge balance, finds recipient unregistered, returns `U128(0)`.
6. `safe_mint_callback` fires: `is_success = false`, UTXO removed from `verified_deposit_utxo`, `burn(...).detach()` scheduled with only 5 TGas headroom inside a 10 TGas callback.
7. If the burn receipt fails silently: bridge balance holds `amount` unbacked nBTC; UTXO is absent from `verified_deposit_utxo` (re-submittable); bridge UTXO set has no record of the BTC.
8. Relayer re-submits the same proof — step 3 repeats, accumulating more unbacked tokens each iteration. [6](#0-5)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }
