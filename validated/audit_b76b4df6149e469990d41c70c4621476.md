### Title
Unconditional Peras Certificate Acceptance Enables Arbitrary Chain-Selection Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production catch-all instance of `BlockSupportsPeras` implements `validatePerasCert` as an unconditional `Right`, accepting every inbound Peras certificate without any cryptographic or semantic verification. Because this validated certificate is then fed directly into chain selection, an unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

The default `BlockSupportsPeras` instance (the only instance in the codebase, used for all block types) implements `validatePerasCert` as follows:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function takes `params` (a `PerasCfg`) and `cert` (a `PerasCert`), uses `params` to compute the boost weight, and wraps `cert` unchanged into a `ValidatedPerasCert` — always returning `Right`. No aggregate BLS signature check, no voter eligibility proof, no round-number bounds check, and no verification that `pcCertBoostedBlock` refers to a block that actually exists or is on a valid chain is performed.

This is the direct analog of the Wonderland Prophet bug: just as those modules use the caller-supplied `_request` data to derive validation parameters (deadlines, tokens) without verifying the data matches the `requestId` embedded in `_dispute`, `validatePerasCert` uses the caller-supplied `params` to derive the boost weight without verifying any field of the caller-supplied `cert`.

The validated certificate is consumed by `processCerts`, which is wired into the live node-to-node inbound handler:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` partitions results into valid/invalid; since `validatePerasCert` never produces a `Left`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` event. `chainSelSync` then reads `getPerasCertBoostedBlock cert` directly from the attacker-controlled certificate and triggers `chainSelectionForBlock` for that block:

```haskell
boostedBlock :: Point blk
boostedBlock = getPerasCertBoostedBlock cert
...
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The certificate's boost weight (`vpcCertBoost = perasWeight params`) is then recorded in the `PerasWeightSnapshot` and used by `weightedSelectView` / `preferCandidate` to compare chain fragments: [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block hash — including a block on a minority fork or a block the attacker controls. The receiving node will:

1. Accept the certificate unconditionally.
2. Record the boost weight for the attacker-chosen block in its `PerasWeightSnapshot`.
3. Re-run chain selection, potentially switching to the attacker's preferred fork because its `wsvTotalWeight` now exceeds the honest chain's weight.

This is a **High** impact chain-selection manipulation: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

The attack requires only a TCP connection to the node's node-to-node port and the ability to send a well-formed CBOR-encoded `PerasCert` message over the Peras cert diffusion mini-protocol. No keys, stake, or operator access are needed. The vulnerable code path is active in the production diffusion layer (`NodeToNode.hs` wires `makePerasCertPoolWriterFromChainDB` into `hPerasCertDiffusionClient`). [6](#0-5) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` using the voter verification keys from the committee.
2. Checks each voter's eligibility proof (persistent membership or VRF output for non-persistent members).
3. Validates that `pcRoundNo` falls within the acceptable window relative to the current slot.
4. Verifies that `pcBoostedBlock` refers to a block that is plausibly on a valid chain (e.g., its slot is within the round's eligible range).

The existing `implVerifyCert` in `WFALS.hs` and `EveryoneVotes.hs` already implement the correct cryptographic checks at the committee layer; the `BlockSupportsPeras` instance must be updated to delegate to those checks rather than bypassing them.

---

### Proof of Concept

1. Connect to a node's node-to-node port.
2. Complete the handshake and negotiate the Peras cert diffusion mini-protocol.
3. Send a `PerasCert` with:
   - `pcCertRound` = any round number not yet in the node's cert DB.
   - `pcCertBoostedBlock` = the `Point` of a block on a minority fork that the attacker wants the node to prefer.
   - `pcVoters` / `pcSignature` = arbitrary bytes (never checked).
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams }`.
5. The certificate is added to `PerasCertDB`; `addPerasCertAsync` triggers `chainSelSync`.
6. `chainSelSync` reads `boostedBlock = getPerasCertBoostedBlock cert` (the attacker's chosen block) and calls `chainSelectionForBlock` for it.
7. The attacker's block now carries extra Peras weight in `PerasWeightSnapshot`, and `preferCandidate` may switch the node to the attacker's fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
