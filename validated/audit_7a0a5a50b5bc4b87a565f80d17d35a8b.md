### Title
Peras Certificate and Vote Validation Unconditionally Accepts All Inbound Objects Without Cryptographic Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance — which is the active instance for all block types — implements `validatePerasCert` as an unconditional `Right` return and `validatePerasVote` with no cryptographic signature check. Any unprivileged peer can inject crafted Peras certificates or forge votes attributed to legitimate stake-pool keys, bypassing all certificate and vote authorization checks. Because Peras certificates directly boost chain weight in `WeightedSelectView`-based chain selection, this allows an adversary to make an honest node prefer a non-canonical chain.

---

### Finding Description

The external report describes a missing property check at acceptance time: SPL tokens are accepted as collateral without verifying `freeze_authority`, a critical property that can later render the accepted object harmful. The analog in Ouroboros Consensus is that Peras certificates and votes are accepted into the protocol without verifying their critical property — cryptographic authenticity — at the point of ingest.

**`validatePerasCert` — unconditional acceptance:**

The default `BlockSupportsPeras` instance (the only instance present in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate, regardless of content, is wrapped in `Right ValidatedPerasCert` and assigned the full `perasWeight`. No round-number bounds, no quorum proof, no BLS/committee signature, no issuer eligibility check is performed. [1](#0-0) 

**`validatePerasVote` — stake-lookup only, no signature:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The only check is whether the claimed `PerasVoterId` appears in the stake distribution. No cryptographic proof that the sender controls the corresponding key is required. Any peer that knows a legitimate pool's `KeyHash` (public information on-chain) can forge votes attributed to that pool. [2](#0-1) 

**This is the sole instance for all block types:**

The instance declaration is `instance StandardHash blk => BlockSupportsPeras blk`, making it the universal default. No more-specific Cardano-block instance overrides it in the searched production sources. [3](#0-2) 

**Inbound path — votes from peers:**

`makePerasVotePoolWriterFromChainDB` is the production writer that processes peer-supplied votes. It calls `validatePerasVote` (the stub above) inside `processVotes`, then passes accepted votes directly to `ChainDB.addPerasVoteWithAsyncCertHandling`. When accumulated stake crosses the quorum threshold, `votesReachQuorum` / `forgePerasCert` produces a `ValidatedPerasCert` that is immediately submitted to `PerasCertDB` and triggers chain selection. [4](#0-3) [5](#0-4) 

**Inbound path — direct certificate injection:**

`addPerasCertAsync` in the `ChainDB` API accepts a `WithArrivalTime (ValidatedPerasCert blk)`. The `ValidatedPerasCert` wrapper is produced by `validatePerasCert`, which always returns `Right`. A peer-supplied certificate therefore enters `PerasCertDB` and triggers `chainSelSync` without any gate. [6](#0-5) [7](#0-6) 

**Chain selection impact:**

`WeightedSelectView` compares chains by `wsvTotalWeight = BlockNo + wsvWeightBoost`. A fraudulent certificate that boosts a block on an adversarial fork adds `perasWeight` to that fork's total weight, potentially making it heavier than the honest chain and causing a switch. [8](#0-7) 

---

### Impact Explanation

This is a **Critical** bypass of Peras certificate and vote verification. An unprivileged peer can:

1. **Direct certificate injection**: Send a `PerasCert` for any round and any block. `validatePerasCert` accepts it unconditionally. The certificate is stored in `PerasCertDB` and its boost is applied to chain selection immediately.
2. **Vote-based certificate forgery**: Send votes attributed to any pool key visible in the stake distribution (no signature required). Once the accumulated stake crosses the quorum threshold, the node itself forges a `ValidatedPerasCert` from the fraudulent votes and applies it to chain selection.

In both cases the honest node can be made to prefer a non-canonical, adversary-controlled fork, violating chain-selection safety.

---

### Likelihood Explanation

Peras is currently disabled by default (`"Note that if Peras is disabled (which is the default), there is no observable difference"` — CHANGELOG). However:

- The code is present and wired into the production `ChainDB` and object-diffusion paths.
- When Peras is enabled (e.g., on a private testnet or after a future mainnet activation), the vulnerability is immediately exploitable by any connected peer with no special privileges.
- Pool `KeyHash` values are public on-chain, so forging votes requires only knowledge of the stake distribution, which every node already holds.

---

### Recommendation

1. Implement real cryptographic validation inside `validatePerasCert`: verify the aggregated BLS/committee signature over the certificate fields, check that the certified round number is within the valid window, and confirm the boosted block point is plausible.
2. Implement real cryptographic validation inside `validatePerasVote`: verify the voter's signature over `(round, block, voterId)` using the key associated with the claimed `PerasVoterId` in the committee selection context (not just the stake distribution lookup).
3. Until full validation is implemented, gate the Peras object-diffusion ingest paths so that certificates and votes are rejected at the network boundary when Peras validation is not yet complete, rather than silently accepted.

---

### Proof of Concept

**Vote-forgery path (no keys needed):**

1. Obtain the current `PerasVoteStakeDistr` (available to every node via the ledger state).
2. Construct `N` `PerasVote` objects, each claiming a different `PerasVoterId` from the distribution, all targeting the same `(round, adversarial_block_point)`.
3. Submit them to the victim node via the Peras vote object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote` for each; every vote passes because `lookupPerasVoteStake` finds the claimed voter in the distribution.
5. Once accumulated stake exceeds the quorum threshold, `votesReachQuorum` returns `Just`, `forgePerasCert` produces a `ValidatedPerasCert`, and `chainSelSync` is triggered.
6. `WeightedSelectView` now scores the adversarial fork higher by `perasWeight`; the node switches to the non-canonical chain.

**Direct certificate path:**

1. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = adversarialPoint }` for any round `r` and any block point on an adversarial fork.
2. Submit it via the Peras certificate object-diffusion mini-protocol.
3. `validatePerasCert` returns `Right ValidatedPerasCert` unconditionally.
4. `chainSelSync` applies the boost and the node may switch forks. [9](#0-8) [4](#0-3) [7](#0-6)

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```

```haskell
-- | The total weight, ie the sum of 'wsvBlockNo' and 'wsvBoostedWeight'.
wsvTotalWeight :: WeightedSelectView proto -> PerasWeight
-- could be cached, but then we need to be careful to maintain the invariant
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
```
