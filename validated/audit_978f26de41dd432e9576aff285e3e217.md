### Title
Unprotected `new` Initializer on nBTC Token Contract Allows Any Caller to Seize `bridge_id` and Mint Unlimited nBTC - (File: contracts/nbtc/src/lib.rs)

### Summary

The `nbtc` token contract's `new` initializer accepts caller-supplied `controller` and `bridge_id` parameters with no check on `env::predecessor_account_id()`. If the contract is deployed in one transaction and initialized in a separate transaction — as shown in the test setup — any unprivileged NEAR account can race to call `new` first, install itself as `bridge_id`, and subsequently call `mint()` without restriction to create arbitrary nBTC.

### Finding Description

The `new` function in `contracts/nbtc/src/lib.rs` is decorated with `#[init]` (runs only when state does not yet exist) but contains no authorization check on the caller:

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    // No check: env::predecessor_account_id() is never validated
    let mut contract = Self { controller, bridge_id, ... };
    contract.token.internal_register_account(&contract.bridge_id);
    contract
}
``` [1](#0-0) 

The entire mint and burn authorization model rests on `bridge_id` being the legitimate satoshi-bridge contract:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
``` [2](#0-1) 

Both `mint()` and `burn()` call `assert_bridge()` as their sole guard: [3](#0-2) [4](#0-3) 

The test setup confirms that deployment and initialization are performed as two separate transactions, creating an observable window:

```rust
// Transaction 1: deploy WASM
nbtc.deploy(&std::fs::read("../../res/nbtc.wasm").unwrap()).await...

// Transaction 2 (separate): call new
nbtc_contract.call("new").args_json(json!({ "controller": root.id(), "bridge_id": bridge_contract.id(), ... })).transact().await...
``` [5](#0-4) [6](#0-5) 

### Impact Explanation

An attacker who calls `new` before the legitimate deployer sets:
- `bridge_id` = attacker's own account → `assert_bridge()` passes for the attacker, allowing unlimited calls to `mint()` and `burn()`
- `controller` = attacker's own account → full administrative control over the token (metadata, withdraw relayer, upgrade)

With `bridge_id` set to the attacker's account, the attacker can call `mint()` directly and credit any NEAR account with an arbitrary amount of nBTC. This constitutes **unauthorized minting** — a Critical impact under the allowed scope.

### Likelihood Explanation

In NEAR Protocol, contract deployment and initialization are routinely performed as separate transactions. Any account can query on-chain state to detect a deployed-but-uninitialized contract (state does not exist yet) and submit a competing `new` call in the next block. No mempool access or privileged information is required; the deployed WASM is publicly visible on-chain. The attack is straightforward and requires only a standard NEAR account with enough NEAR for gas.

### Recommendation

Restrict `new` to the contract's own account (i.e., the deployer) by adding a predecessor check at the top of the initializer:

```rust
#[init]
pub fn new(controller: AccountId, bridge_id: AccountId, ...) -> Self {
    require!(!env::state_exists(), "Already initialized");
    require!(
        env::predecessor_account_id() == env::current_account_id(),
        "Only the contract account may initialize"
    );
    ...
}
```

Alternatively, deploy and initialize atomically in a single batch transaction using `DeployContract` + function call, which eliminates the window entirely.

### Proof of Concept

1. Legitimate deployer sends **Transaction A**: deploys `nbtc.wasm` to account `nbtc.near`. State does not yet exist.
2. Attacker observes the chain, sees `nbtc.near` has code but no state.
3. Attacker sends **Transaction B** (before the deployer's init tx is included):
   ```json
   {
     "receiver_id": "nbtc.near",
     "method_name": "new",
     "args": {
       "controller": "attacker.near",
       "bridge_id": "attacker.near",
       "name": "Near BTC", "symbol": "NBTC", "decimals": 8
     }
   }
   ```
4. Transaction B is included first. `bridge_id` is now `attacker.near`.
5. Deployer's `new` call fails with `"Already initialized"`.
6. Attacker calls `mint(mint_account_id: "attacker.near", mint_amount: "21000000000000000", ...)` directly from `attacker.near` — `assert_bridge()` passes because `predecessor == bridge_id == attacker.near`.
7. Attacker receives unlimited nBTC with no BTC deposited. [7](#0-6)
