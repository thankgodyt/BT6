### Title
Asymmetric `max_change_amount` Validation in `check_withdraw_psbt` Allows Oversized Change UTXOs When `input_num <= change_num` - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary

In `check_withdraw_psbt`, the upper-bound check on change-output amounts (`max_change_amount`) is only enforced when `input_num > change_num`. When `input_num <= change_num` — a condition that is explicitly required by passive UTXO management when the pool is undersized — the `max_change_amount` guard is silently skipped. Any nBTC holder can craft a withdrawal PSBT that satisfies all other checks yet deposits change UTXOs into the bridge that exceed the configured maximum, permanently violating the UTXO-size invariant the bridge relies on for active management.

### Finding Description

`check_withdraw_psbt` in `contracts/satoshi-bridge/src/psbt.rs` validates change outputs in two separate places:

**Inside the per-output loop** (lines 197–206): only the lower bound is checked.
```rust
require!(
    output_value >= config.min_change_amount,
    "The change amount is too small"
);
```

**After the loop** (lines 227–237): the upper bound is checked **only when `input_num > change_num`**.
```rust
if input_num > change_num {
    require!(
        change_amounts
            .into_iter()
            .all(|v| v < config.max_change_amount),
        ...
    );
}
``` [1](#0-0) 

When `input_num <= change_num`, the `max_change_amount` upper bound is never enforced on any change output. This is the exact asymmetric-validation pattern from the external report: different logic paths apply different range checks, and one path omits the upper-bound guard entirely.

The passive UTXO management policy in `check_withdraw_psbt_valid` **requires** `input_num < change_num` when the pool is undersized:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
}
``` [2](#0-1) 

So the unguarded path is not a corner case — it is the **mandated** path during the most critical operational state (pool undersized, bridge actively trying to grow its UTXO set).

The only remaining per-output upper bound in the unguarded path is:

```rust
require!(
    signer_is_unrestricted || output_value < min_input_amount,
    ...
);
``` [3](#0-2) 

`min_input_amount` is the smallest UTXO selected as input. If the bridge holds UTXOs larger than `max_change_amount` (which is common — the bridge accumulates deposits of arbitrary size), a user can set each change output to just below `min_input_amount`, which may be far above `max_change_amount`, and the transaction passes all checks.

The attacker-controlled entry point is `ft_transfer_call` on the nBTC token, which triggers `ft_on_transfer` on the bridge. The user supplies the `input` (UTXOs to consume) and `output` (change TxOuts) directly in the `TokenReceiverMessage::Withdraw` payload:

```rust
TokenReceiverMessage::Withdraw {
    target_btc_address: ...,
    input: vec![OutPoint { txid, vout }],
    output: vec![TxOut { value: Amount::from_sat(oversized_change), script_pubkey: change_script }],
    ...
}
```

No privileged role is required. Any account holding nBTC can submit this.

### Impact Explanation

The bridge's active UTXO management (`check_active_management_psbt_valid` → `check_psbt_output_all_change_address`) enforces `max_change_amount` on every output:

```rust
require!(
    v.value.to_sat() > config.unhealthy_utxo_amount
        && u128::from(v.value.to_sat()) <= config.max_change_amount,
    "The output amount is not in the valid range"
);
``` [4](#0-3) 

Once an oversized UTXO is deposited into the bridge's UTXO set, it cannot be split via active management (the split outputs would need to be `<= max_change_amount`, but the single oversized input cannot be split into outputs that each satisfy the healthy-output lower bound while also staying under `max_change_amount` if the UTXO is large enough). The bridge's UTXO pool becomes permanently polluted with UTXOs that violate its own invariants, requiring operator intervention to remediate. This matches the **Medium** impact category: attacker-triggered stuck bridge state requiring operator intervention, and bypass of bridge UTXO-size limits.

### Likelihood Explanation

Any nBTC holder can trigger this. The attacker needs only to:
1. Hold any amount of nBTC.
2. Identify a bridge UTXO larger than `max_change_amount` (visible on-chain).
3. Submit a withdrawal with `input_num <= change_num` and change outputs sized just below `min_input_amount`.

The passive management lower-limit condition (`utxo_num < passive_management_lower_limit`) is a normal operational state the bridge enters whenever the UTXO pool shrinks, making the vulnerable code path regularly reachable.

### Recommendation

Remove the conditional guard and always enforce `max_change_amount` on every change output, regardless of the `input_num`/`change_num` relationship:

```rust
require!(
    change_amounts
        .iter()
        .all(|v| *v < config.max_change_amount),
    format!(
        "Any change amount should be less than {}",
        config.max_change_amount
    )
);
```

This mirrors the unified range-check fix recommended in the external report: apply the full `[min, max]` validation unconditionally rather than splitting it across asymmetric branches.

### Proof of Concept

1. Bridge has one UTXO of 5 000 000 sat; `max_change_amount` = 2 000 000 sat; `min_change_amount` = 1 000 sat; `passive_management_lower_limit` = 10 UTXOs (pool is undersized, so `input_num < change_num` is required).
2. Attacker holds 200 000 sat of nBTC.
3. Attacker calls `ft_transfer_call` with:
   - `input`: the 5 000 000-sat UTXO
   - `output`: two change TxOuts each of 2 400 000 sat (> `max_change_amount`, < `min_input_amount` = 5 000 000)
   - `target_btc_address`: attacker's BTC address receiving `5 000 000 - 4 800 000 - gas_fee` sat
4. `check_withdraw_psbt` runs: `input_num = 1`, `change_num = 2`, so `input_num <= change_num` → the `max_change_amount` branch is **not entered**. Each change output passes only the `>= min_change_amount` and `< min_input_amount` checks. The transaction is accepted.
5. Two 2 400 000-sat UTXOs (each exceeding `max_change_amount`) are registered in the bridge's UTXO set, permanently violating the UTXO-size invariant enforced by active management. [1](#0-0) [5](#0-4) [2](#0-1)
