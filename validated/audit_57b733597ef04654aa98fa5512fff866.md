### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect Unfinalized BTC Deposits to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` is a public, permissionless function. When `deposit_msg.refund_address` is `None`, there is no check that the caller is the `deposit_msg.recipient_id` or any other authorized party. Any observer who knows the `deposit_msg` and the Bitcoin transaction can call `request_refund` first with an attacker-controlled BTC address, permanently claiming the refund slot for that UTXO. The legitimate depositor's subsequent call is rejected with "Refund request already exists for this UTXO." After `unsafe_refund_timelock_sec` elapses, `execute_refund` (also public) sends the BTC to the attacker's address.

### Finding Description
`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` accepts a caller-supplied `refund_address` with no authorization check:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← attacker supplies this
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
    // only gas_fee requires privilege; refund_address is unchecked
    self.internal_request_refund(...)
}
```

Inside `internal_request_refund` (`contracts/satoshi-bridge/src/refund.rs`), the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), this block is skipped entirely and any `refund_address` is accepted. The callback then stores the attacker's address permanently:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // attacker's BTC address
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
```

A subsequent legitimate call for the same UTXO is blocked:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

After `unsafe_refund_timelock_sec`, `execute_refund` (also public, no caller restriction) builds and signs a BTC transaction paying the stored `refund_address` — the attacker's address.

The `deposit_msg` is not secret: it is submitted as a NEAR transaction argument (visible in the NEAR mempool and on-chain), and the Bitcoin transaction bytes (`tx_bytes`) and Merkle proof are fully public on the Bitcoin blockchain. An attacker needs only to observe Alice's `request_refund` call in the NEAR transaction pool and submit a competing call with the same `deposit_msg`/`tx_bytes`/`proof` but a different `refund_address`.

### Impact Explanation
If the attacker's `request_refund` lands before the legitimate depositor's (either by racing in the same block or by submitting first), the BTC deposit is permanently redirected to the attacker's Bitcoin address. The legitimate depositor loses their entire BTC deposit. The only on-chain safeguard is the `unsafe_refund_timelock_sec` window during which DAO/Operator can call `reject_refund`, but this is an operational control, not a protocol-level guarantee. If the operator misses the window, the loss is permanent and irreversible.

### Likelihood Explanation
The `deposit_msg` is observable in NEAR transaction arguments (public mempool and block explorer). The Bitcoin transaction data is fully public. An attacker monitoring the NEAR mempool for `request_refund` calls can immediately submit a competing call. NEAR does not use gas-price-based ordering, but transactions within the same block can be reordered by validators, and an attacker who submits before the victim has a high probability of landing first. Additionally, if the attacker knows the `deposit_msg` from an off-chain source (e.g., a dApp that displays it), they can call `request_refund` before the victim does, with no race required.

### Recommendation
Add an authorization check in `request_refund` (or `internal_request_refund`) that requires the caller to be `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient can request a refund without a pre-authorized refund address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` always be set at deposit time (enforced off-chain in the dApp), so the on-chain check `msg_refund_address == &refund_address` always applies and the caller cannot substitute an arbitrary address.

### Proof of Concept
1. Alice sends 1 BTC to the deposit address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`.
2. The deposit is never finalized by a relayer.
3. Alice prepares a `request_refund` call with `refund_address = "alice_btc_address"`.
4. Eve observes Alice's pending NEAR transaction in the mempool. Eve submits `request_refund(deposit_msg, "eve_btc_address", tx_bytes, vout, proof, None)` with the same `deposit_msg` and proof but `refund_address = "eve_btc_address"`.
5. Eve's transaction is included first. `request_refund_callback` stores `RefundRequest { refund_address: "eve_btc_address", ... }` for Alice's UTXO.
6. Alice's transaction fails: "Refund request already exists for this UTXO."
7. After `unsafe_refund_timelock_sec` elapses (and if DAO/Operator does not call `reject_refund`), anyone calls `execute_refund(utxo_storage_key, None)`.
8. The bridge MPC-signs a Bitcoin transaction paying 1 BTC (minus gas fee) to `"eve_btc_address"`. Alice's BTC is permanently stolen. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {

            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }

            // Refund address supplied by caller of `request_refund`: longer
