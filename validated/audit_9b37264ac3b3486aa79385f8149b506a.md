Audit Report

## Title
Blacklisted Recipient Permanently Freezes Bridged Non-Bridge Tokens in `finTransfer` - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.sol::finTransfer` dispatches non-bridge tokens (e.g., USDC, USDT) via `IERC20.safeTransfer` directly to `payload.recipient` with no fallback on failure. If the recipient is on the token's denylist, `safeTransfer` reverts, rolling back the entire transaction including the nonce mark. Because the MPC signature irrevocably encodes the blacklisted recipient and the NEAR-side tokens are already burned with the pending transfer entry removed, no on-chain recovery path exists, causing permanent freezing of the bridged funds.

## Finding Description

In `finTransfer`, the nonce is marked used at line 287 before the token dispatch, but Solidity atomicity means a revert in the transfer path rolls it back:

```solidity
// OmniBridge.sol L283-287
if (completedTransfers[payload.destinationNonce]) {
    revert NonceAlreadyUsed(payload.destinationNonce);
}
completedTransfers[payload.destinationNonce] = true;  // rolled back on revert
```

For non-bridge tokens (those not in `isBridgeToken`, `customMinters`, or `multiTokens`), the dispatch is:

```solidity
// OmniBridge.sol L350-354
} else {
    IERC20(payload.tokenAddress).safeTransfer(
        payload.recipient,
        payload.amount
    );
}
```

USDC and USDT implement on-chain blacklists; `safeTransfer` to a blacklisted address reverts unconditionally. Because the revert rolls back `completedTransfers[nonce]`, the nonce is never consumed, and every subsequent relay attempt produces the same revert.

The MPC signature is computed over a Borsh blob that includes `payload.recipient`:

```solidity
// OmniBridge.sol L295-298
Borsh.encodeAddress(payload.tokenAddress),
Borsh.encodeUint128(payload.amount),
bytes1(omniBridgeChainId),
Borsh.encodeAddress(payload.recipient),
```

No alternative recipient can be substituted without invalidating the signature.

On the NEAR side, `sign_transfer_callback` removes the pending transfer entry immediately after a successful MPC signature when the fee is zero:

```rust
// near/omni-bridge/src/lib.rs L655-658
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
```

There is no public `cancel_transfer`, `refund_transfer`, or equivalent function in the NEAR contract. The EVM contract has no admin token-rescue function (only UUPS upgrade capability). Once the NEAR-side entry is removed and the EVM-side `finTransfer` permanently reverts, the bridged USDC (held in the OmniBridge EVM contract) is irrecoverable.

## Impact Explanation

This satisfies the critical allowed impact: **permanent freezing of bridged funds**. The NEAR-side USDC is burned and the pending transfer entry is deleted; the EVM-side USDC remains locked inside the OmniBridge contract with no callable path to release it. The funds are neither accessible to the user nor recoverable by the protocol through any unprivileged on-chain action.

## Likelihood Explanation

USDC (Centre/Circle) and USDT (Tether) both maintain enforced on-chain blacklists. OFAC sanctions designations and exchange-level compliance actions regularly add addresses. A user can initiate a bridge transfer to an address that is clean at initiation time but blacklisted during the MPC signing latency window or before the relayer submits `finTransfer`. This is a realistic, non-negligible scenario for a bridge that explicitly supports USDC as a non-bridge token. The attack requires no privileged access and no victim mistake beyond using a subsequently-sanctioned address.

## Recommendation

Replace the direct push transfer with a pull pattern. Instead of calling `safeTransfer` inside `finTransfer`, record the claimable balance:

```solidity
pendingWithdrawals[payload.recipient][payload.tokenAddress] += payload.amount;
```

Provide a separate `claimTokens(address tokenAddress)` function. This decouples nonce finalization and event emission from token delivery, so a blacklisted recipient cannot block the protocol-level state transition. Alternatively, wrap the `safeTransfer` in a `try/catch` and, on failure, credit the amount to a `claimable[recipient][token]` mapping, analogous to the `claims[token]` pattern. The same fix should be applied to the native ETH path (lines 319-322) and the ERC-1155 path (lines 324-330).

## Proof of Concept

1. Alice holds USDC on NEAR (bridged from Ethereum). She calls `ft_on_transfer` to bridge 10,000 USDC back to `0xAlice`. NEAR burns her USDC and stores the `TransferMessage` in `pending_transfers`.
2. A relayer calls `sign_transfer`; MPC produces a signature over `{recipient: 0xAlice, token: USDC, amount: 10000, ...}`. Because `fee.is_zero()`, `sign_transfer_callback` calls `remove_transfer_message`, deleting the NEAR-side entry.
3. Before the relayer submits `finTransfer`, USDC's issuer blacklists `0xAlice`.
4. The relayer calls `OmniBridge.finTransfer(sig, payload)`. Execution reaches line 351: `IERC20(USDC).safeTransfer(0xAlice, 10000)`. The USDC contract reverts.
5. The entire EVM transaction reverts. `completedTransfers[nonce]` is rolled back to `false`.
6. Every subsequent relay attempt produces the same revert. The signature cannot be reused with a different recipient. No NEAR-side recovery path exists.
7. Alice's 10,000 USDC are permanently frozen inside the OmniBridge EVM contract.
