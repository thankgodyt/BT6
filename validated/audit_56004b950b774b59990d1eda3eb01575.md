### Title
Peras Certificate Validation Bypass Enables Unbounded Chain Weight Injection via Crafted Peer Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally accepts every inbound certificate (`Right` always). An unprivileged peer can send arbitrarily many crafted `PerasCert` objects through the object-diffusion mini-protocol. Each certificate is stored in the `PerasCertDB` and its boost is accumulated into the `PerasWeightSnapshot`. Because the weight snapshot feeds directly into `preferAnchoredCandidate` / `wsvTotalWeight`, the adversary can inflate the total weight of any chain fragment without bound, causing an honest node to prefer the adversary's chain over the honest chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub used in production:** [1](#0-0) 

The catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` is the only `BlockSupportsPeras` instance in the repository. Its `validatePerasCert` implementation always returns `Right`, performing zero cryptographic or semantic checks on the certificate's round number, boosted block, voter set, or aggregate signature.

**Production inbound path uses this stub directly:** [2](#0-1) 

`makePerasCertPoolWriterFromChainDB` — the production writer used when certificates arrive from peers — passes `validatePerasCert mkPerasParams` to `processCerts`. Because the validator always succeeds, every certificate a peer sends is accepted and stored.

**Accepted certificates accumulate weight without bound:** [3](#0-2) 

`addToPerasWeightSnapshot` uses `Map.insertWith (<>)`, so multiple certificates boosting the same block point accumulate their `PerasWeight` values additively. `implGetWeightSnapshot` rebuilds the snapshot from all stored certificates on every query. [4](#0-3) 

**Accumulated weight drives chain selection:** [5](#0-4) 

`wsvTotalWeight = BlockNo + wsvWeightBoost`. `preferCandidate` switches to the candidate whenever `wsvTotalWeight cand > wsvTotalWeight ours`. An adversary who injects N certificates each carrying `perasWeight = 15` for a single block accumulates a boost of `N × 15`, which can exceed the honest chain's block-number advantage. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can make an honest node permanently prefer a shorter, adversarially controlled chain over the honest chain by injecting enough fake certificates. This is a **chain-selection safety failure**: the node adopts a non-canonical chain without any stake-majority or key-compromise requirement. The analog to CCFrax1to1AMM is exact — just as the AMM's constant-sum invariant (k = a + b) can be completely drained because there is no price-reserve feedback, the Peras weight invariant (`total_weight = block_no + boost`) can be inflated without bound because there is no certificate authenticity check.

**Impact class:** Critical — bypass of Peras certificate validation enabling unauthorized chain weight acceptance and chain-selection divergence.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. No stake, no keys, and no prior knowledge of the chain are required — only the ability to craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The `processCerts` deduplication only filters by round number, so an adversary can send one certificate per round (up to `PerasCertMaxRounds = 487` rounds) and accumulate a boost of `487 × 15 = 7305` weight units on a single block, which is more than three times the mainnet security parameter `k = 2160`.

---

### Recommendation

1. **Short-term:** Gate `processCerts` so that it rejects all inbound certificates until a real `validatePerasCert` implementation is in place. The simplest safe default is to make the degenerate instance return `Left PerasValidationErr` unconditionally, disabling certificate acceptance until the cryptographic validation (BLS aggregate signature, committee eligibility, round/block consistency) is implemented.

2. **Long-term:** Implement `validatePerasCert` for the concrete Cardano block type using the `Ouroboros.Consensus.Peras.Cert.V1` types already present in the repository, verifying the aggregate BLS signature, the voter bitmap against the committee, and the round/block consistency rules before any certificate is stored or its boost applied to the weight snapshot.

---

### Proof of Concept

```
1. Connect to a syncing node as a peer via the object-diffusion mini-protocol.

2. Craft 487 PerasCert values:
     cert_i = PerasCert { pcCertRound = i, pcCertBoostedBlock = adversary_block_B }
   for i in [0 .. 486].

3. Send all 487 certs in a single batch to the node.

4. processCerts calls (validatePerasCert mkPerasParams cert_i) for each cert.
   validatePerasCert always returns Right, so all 487 certs are stored.

5. implGetWeightSnapshot builds a PerasWeightSnapshot where
     weightBoostOfPoint snap adversary_block_B = 487 * 15 = 7305.

6. preferAnchoredCandidate computes:
     wsvTotalWeight(adversary_chain) = blockNo(B) + 7305

   For a chain where B is at block number 1000:
     wsvTotalWeight = 1000 + 7305 = 8305

   The honest chain at block number 2160 (= k) has:
     wsvTotalWeight = 2160 + 0 = 2160

   Since 8305 > 2160, the node switches to the adversary's chain.
```
