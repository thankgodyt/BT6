### Title
Orchard-only Unified Address as `refund_address` panics in `build_refund_output` on transparent refund — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary

When a Zcash Unified Address containing **only** an Orchard receiver (no transparent P2PKH/P2SH receiver) is stored as `refund_address` in a `RefundRequest`, calling `execute_refund` with `chain_specific_data = None` (transparent path) causes `execute_refund_callback` to panic via `.expect("Invalid refund script_pubkey")`. The panic is publicly reachable. However, the funds are **not permanently stuck**: the shielded path (`chain_specific_data = Some(orchard_bundle)`) still works, and the DAO can reject the request.

---

### Finding Description

**Step 1 — Storing an Orchard-only UA as `refund_address`**

`request_refund` is publicly callable (no method-level `#[trusted_relayer]`, confirmed by tests where regular users call it). `internal_request_refund` validates only that `refund_address` matches `deposit_msg.refund_address` when set — it performs **no validation** that the address has a transparent receiver: [1](#0-0) 

The `request_refund_callback` stores the address verbatim: [2](#0-1) 

**Step 2 — `execute_refund` with `chain_specific_data = None`**

`execute_refund` is publicly callable: [3](#0-2) 

**Step 3 — Transparent branch calls `build_refund_output`**

In `execute_refund_callback`, when `orchard_bundle` is `None`, the transparent branch calls `build_refund_output`: [4](#0-3) 

**Step 4 — `build_refund_output` panics**

`build_refund_output` calls `Address::parse` (succeeds — Orchard-only UAs parse fine as `Address::Unified`), then calls `.script_pubkey()` which iterates receivers and finds no P2PKH/P2SH, returning `Err("No receiver found in address")`. The `.expect` then panics: [5](#0-4) 

**Step 5 — `script_pubkey()` returns `Err` for Orchard-only UA**

The `Unified` arm of `script_pubkey` only returns `Ok` for `Receiver::P2pkh` or `Receiver::P2sh`. An Orchard-only UA falls through to: [6](#0-5) 

The codebase itself documents this behavior in a test: [7](#0-6) 

---

### Impact Explanation

The panic occurs inside `execute_refund_callback` (`#[private]`). In NEAR, a panicking callback fails the receipt but does **not** roll back the `RefundRequest` (it was committed in a prior receipt). The request remains in storage.

**The impact is overstated in the question.** Funds are **not permanently stuck** because:
1. The **shielded path** (`chain_specific_data = Some(orchard_bundle)`) bypasses `build_refund_output` entirely and still works.
2. The DAO/Operator can call `reject_refund` to remove the request, after which the user can re-request with a transparent address.

The real impact is: **a publicly reachable panic in a production bridge path** that causes every transparent-refund attempt for this UTXO to fail, requiring either the shielded path or DAO intervention to recover.

---

### Likelihood Explanation

A user who sets an Orchard-only UA (e.g., from a privacy wallet) as `deposit_msg.refund_address` and later calls `execute_refund` with `chain_specific_data = None` will trigger this. No privileged role is required. The address parses successfully at request time, so no early rejection occurs.

---

### Recommendation

In `build_refund_output`, replace the `.expect("Invalid refund script_pubkey")` with a graceful `require!` or return an error, and add validation at `request_refund` time (or at `execute_refund` time before the callback) that rejects Orchard-only UAs when `chain_specific_data` is `None`.

Specifically, `build_refund_output` should propagate the `Err` from `script_pubkey()` as a `require!` failure rather than a panic:

```rust
let refund_script_pubkey = refund_addr
    .script_pubkey()
    .unwrap_or_else(|e| env::panic_str(&format!("Refund address has no transparent receiver: {e}")));
```

(This is already the pattern used in `target_script_pubkey` via `.ok()` — the same fix should be applied here.)

---

### Proof of Concept

```
1. Deploy bridge with ZcashMainnet config.
2. User creates DepositMsg { refund_address: Some(orchard_only_ua) }
   where orchard_only_ua = UA with only Orchard receiver (no P2PKH/P2SH).
3. User deposits ZEC to the derived deposit address.
4. User calls request_refund(deposit_msg, orchard_only_ua, tx_bytes, vout, proof, None).
   → request_refund_callback stores RefundRequest { refund_address: orchard_only_ua }.
5. After timelock, anyone calls execute_refund(utxo_storage_key, chain_specific_data=None).
   → execute_refund_callback → build_refund_output(orchard_only_ua, amount)
   → Address::parse succeeds → .script_pubkey() returns Err("No receiver found in address")
   → .expect("Invalid refund script_pubkey") PANICS.
6. Callback fails; RefundRequest remains in storage.
   Transparent refund is permanently broken for this UTXO.
   Recovery requires shielded path or DAO rejection.
```

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr

                u64::try_from(refund_amount)

            ),

        }
