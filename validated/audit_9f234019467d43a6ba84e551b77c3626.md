### Title
Missing `bridge_id` Account Registration in `migrate_from_poa` Breaks `safe_mint` and Withdrawal Flow - (File: `contracts/nbtc/src/migrate.rs`)

---

### Summary

The `migrate_from_poa` function in the nBTC contract migrates state from the legacy Near Intents (PoA) format to the new bridge format but omits registering `bridge_id` in the `FungibleToken`'s internal accounts map. The normal `new()` constructor explicitly performs this registration, but the migration path skips it. After migration, `safe_mint` panics on every call, and the withdrawal flow (user `ft_transfer_call` → bridge → `burn`) is broken because `bridge_id` is an unregistered account in the token.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `new()` constructor explicitly registers `bridge_id` in the token's accounts map:

```rust
contract.token.internal_register_account(&contract.bridge_id);
``` [1](#0-0) 

This is required because NEAR SDK's `FungibleToken::internal_deposit` and `internal_withdraw` both panic if the target account is not registered.

In `contracts/nbtc/src/migrate.rs`, `migrate_from_poa` constructs the new state from the old `NearIntentsState` (which has no `bridge_id` concept) and sets `controller`, `bridge_id`, `token`, and `metadata` — but never calls `internal_register_account` for `bridge_id`:

```rust
let new_state = Self {
    controller,
    bridge_id,
    token: state.token,
    metadata: LazyOption::new(StorageKey::Metadata, Some(state.metadata.get())),
};
``` [2](#0-1) 

The old `NearIntentsState` only carried `token` and `metadata`:

```rust
pub struct NearIntentsState {
    pub token: FungibleToken,
    pub metadata: Lazy<FungibleTokenMetadata>,
}
``` [3](#0-2) 

There is no `bridge_id` in the old state, so the migrated `FungibleToken` will never have `bridge_id` registered.

**Broken path 1 — `safe_mint`:**

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
``` [4](#0-3) 

`internal_deposit` on an unregistered account panics unconditionally in the NEAR SDK's `FungibleToken`. Every call to `safe_mint` after migration panics.

**Broken path 2 — Withdrawal flow (`ft_transfer_call` → `burn`):**

A user initiating a withdrawal calls `ft_transfer_call` with `receiver_id = bridge_id`. The NEAR SDK's `FungibleToken::ft_transfer_call` calls `internal_transfer`, which calls `internal_deposit` on the receiver. Because `bridge_id` is unregistered, this panics, preventing any nBTC from reaching the bridge and making `burn` unreachable:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
``` [5](#0-4) 

Note: the primary `mint` path is unaffected because `mint_inner` auto-registers accounts before depositing:

```rust
if self.token.accounts.get(account_id).is_none() {
    self.token.internal_register_account(account_id);
}
``` [6](#0-5) 

But `safe_mint` and the withdrawal flow have no such guard.

---

### Impact Explanation

After `migrate_from_poa` is executed:

- **`safe_mint` is permanently broken** — every invocation panics, making the legacy deposit path non-functional.
- **The entire withdrawal flow is broken** — users holding nBTC cannot transfer tokens to `bridge_id`, so no withdrawal can be initiated. nBTC balances are stuck until an operator manually registers `bridge_id` via `storage_deposit`.

This matches: **Medium — stuck bridge state requiring operator intervention**, and potentially **Critical — permanent locking of user funds** if the operator does not intervene promptly (users cannot redeem nBTC for BTC).

---

### Likelihood Explanation

`migrate_from_poa` is the designated migration path from the PoA (Near Intents) deployment to the new bridge. It is called exactly once during the production migration event. The bug is deterministic: every post-migration environment is affected. No special attacker action is needed — any user attempting a withdrawal after migration triggers the broken path.

---

### Recommendation

Add the missing account registration inside `migrate_from_poa`, mirroring what `new()` does:

```rust
// After constructing new_state, register bridge_id in the token
let mut new_state = Self {
    controller,
    bridge_id,
    token: state.token,
    metadata: LazyOption::new(StorageKey::Metadata, Some(state.metadata.get())),
};
new_state.token.internal_register_account(&new_state.bridge_id);
new_state
``` [2](#0-1) 

---

### Proof of Concept

1. Deploy the nBTC contract in the legacy Near Intents state (with `NearIntentsState` containing a `FungibleToken` and `metadata`).
2. Call `migrate_from_poa(controller, bridge_id, withdraw_relayer)`. The new `Contract` state is written with `bridge_id` set but **not registered** in `token.accounts`.
3. Have the bridge call `safe_mint(user_account, amount, None)`. The call panics at `self.token.internal_deposit(&self.bridge_id, amount.into())` because `bridge_id` is unregistered.
4. Have a user call `ft_transfer_call(bridge_id, amount, None, msg)` to initiate a withdrawal. The call panics inside `internal_transfer` → `internal_deposit` on the unregistered `bridge_id`.
5. The bridge is stuck: no withdrawals can be processed and `safe_mint` is non-functional until an operator calls `storage_deposit` for `bridge_id` to register it.
