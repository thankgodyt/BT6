### Title
Peras Certificate Validation Bypass: Default `validatePerasCert` Unconditionally Accepts Any Certificate — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal default instance of `BlockSupportsPeras` provides a `validatePerasCert` implementation that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or semantic checks. The production Object Diffusion pool writer for Peras certificates calls this default directly. An unprivileged peer can submit a crafted `PerasCert` over the network, have it accepted as `ValidatedPerasCert`, stored in the `PerasCertDB`, and used to artificially boost a non-canonical fork's weight in chain selection — causing an honest node to abandon the canonical chain.

### Finding Description

**Root cause — unconditional `Right` in the default instance:**

In `SupportsPeras.hs`, the catch-all instance `instance StandardHash blk => BlockSupportsPeras blk` provides the following default implementation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every field of the inbound `PerasCert` — including `pcCertRound` (the election identifier) and `pcCertBoostedBlock` (the block being boosted) — is accepted without any check. No aggregate BLS signature is verified, no committee membership is confirmed, no round-number bounds are enforced.

**Production call site — the ChainDB pool writer:**

`makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` passes this default directly as the validation function:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then calls this function on every inbound certificate from a peer:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `partitionEithers` call always produces an empty error list, and every certificate is unconditionally added.

**Chain selection consequence:**

Once a `ValidatedPerasCert` is added to the `PerasCertDB`, `addPerasCertAsync` enqueues it for chain selection processing. `chainSelSync` then calls `chainSelectionForBlock` for the boosted block: [4](#0-3) 

The Peras chain selection compares fragments by `wsvTotalWeight`, which is `BlockNo + weightBoost`. A forged certificate injects `perasWeight params` of artificial boost onto any attacker-chosen block: [5](#0-4) 

**Secondary issue — `validatePerasVote` also skips signature verification:**

The same default instance's `validatePerasVote` only checks stake distribution membership but never verifies the vote's cryptographic signature:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise = Left PerasValidationErr
``` [6](#0-5) 

An attacker who knows any registered pool ID (public information) can forge votes for that pool without its private key, accumulate quorum, and trigger internal certificate generation — the same chain-selection manipulation via a different path.

### Impact Explanation

**High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

A peer with no special privileges can:
1. Connect via the Object Diffusion mini-protocol (the standard Peras certificate diffusion channel).
2. Send a `PerasCert` with `pcCertBoostedBlock` pointing to any block on a competing fork.
3. The certificate is accepted, stored, and used to boost that fork's `wsvTotalWeight`.
4. If the artificial boost exceeds the honest chain's lead, the node switches to the attacker's fork.

This violates the chain selection security invariant: an honest node should only prefer a fork that is genuinely heavier under the Peras protocol rules. The forged certificate grants weight without any corresponding quorum of legitimate committee votes.

### Likelihood Explanation

**High.** The Object Diffusion mini-protocol is a standard peer-to-peer channel reachable by any connecting node. No privileged keys, stake, or operator access are required. The attacker only needs to craft a valid CBOR-encoded `PerasCert` structure (the serialization format is public) and send it. The TODO comment and linked issue (`cardano-peras/issues/120`) confirm this is a known placeholder, not a deliberate design choice, and the code is already wired into the production `ChainDB` pool writer path.

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before the Object Diffusion path is enabled in production. At minimum, verify the aggregate BLS signature against the claimed voter set and the claimed `(roundNo, boostedBlock)` message, using the committee's public keys from the ledger state.
2. **Implement signature verification in `validatePerasVote`** — membership in the stake distribution is necessary but not sufficient; the vote signature must be verified against the voter's registered BLS public key.
3. **Gate the Object Diffusion mini-protocol** behind the Peras feature flag so that the unvalidated path is unreachable when Peras is disabled.
4. **Add an invariant test** asserting that `validatePerasCert` rejects a certificate with an all-zero or random aggregate signature, to prevent regression.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer connects via Object Diffusion mini-protocol
  → sends [PerasCert { pcCertRound = R, pcCertBoostedBlock = <fork tip> }]
  → makePerasCertPoolWriterFromChainDB.opwAddObjects receives the list
  → processCerts calls (validatePerasCert mkPerasParams) on each cert
  → validatePerasCert returns Right (ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams })
  → partitionEithers sees zero errors → addCert stores the ValidatedPerasCert
  → addPerasCertAsync enqueues cert for chain selection
  → chainSelSync: chainSelectionForBlock runs for <fork tip>
  → wsvTotalWeight(<fork tip>) = blockNo(<fork tip>) + perasWeight > wsvTotalWeight(honest tip)
  → node switches to attacker's fork
```

The only precondition is that the attacker's fork tip block has been received by the target node (so it exists in the VolatileDB), which is achievable by a peer that also serves blocks via BlockFetch. The forged certificate requires no knowledge of any private key.
