Audit Report

## Title
Missing Pre-Normalization Validation in `init_transfer` Permanently Freezes Dust Amounts — (`near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` burns or locks user tokens on NEAR and stores the transfer in `pending_transfers` before any decimal-normalization check is performed. When the transferred amount (minus fee) normalizes to zero on the destination chain, `sign_transfer` will always panic with `InvalidAmountToTransfer`, the transfer can never be finalized, and the burned/locked tokens are permanently unrecoverable.

## Finding Description
The `init_transfer` function (reached via `ft_on_transfer`) constructs a `TransferMessage` and performs only one validation before committing funds:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

No lookup of `token_decimals` and no call to `normalize_amount` occurs here. Execution proceeds to `init_transfer_internal` (L1829), which burns or locks the full token amount and returns `U128(0)` to the NEP-141 callback — permanently consuming the tokens:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(...);
}
```

Later, when a relayer calls `sign_transfer`, the normalization check fires:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` uses floor division (`amount / 10^(origin_decimals - decimals)`). For a 24-decimal NEAR token bridging to a 6-decimal EVM destination, the divisor is `10^18`. Any `amount_without_fee < 10^18` yields zero, causing `require!` to panic. Because the panic occurs before the MPC signing call, `sign_transfer_callback` is never reached and the transfer is never removed from `pending_transfers`.

`update_transfer_fee` cannot rescue the transfer: it enforces `fee < amount` (L400), so the minimum achievable `amount_without_fee` is `1`, which still normalizes to zero across an 18-decimal gap.

No public cancel or user-callable refund function exists in the contract.

## Impact Explanation
User tokens are permanently burned or locked in the bridge with no finalization or recovery path. The `pending_transfers` entry persists indefinitely; `sign_transfer` always panics; `update_transfer_fee` cannot raise `amount_without_fee` above the normalization threshold. This is a concrete instance of **permanent freezing of bridged funds**, matching the Critical impact scope.

## Likelihood Explanation
The scenario requires no special privileges. Any user calling `ft_transfer_call` on a NEAR-native token with `origin_decimals > decimals` on the destination chain, with an amount below the normalization threshold, triggers the bug through the standard public bridge entry point. For a 24-to-6 decimal pair (e.g., a NEAR-native token bridging to USDC-scale EVM), the threshold is `10^18` base units — less than one full token. Users unfamiliar with decimal precision differences can easily hit this. The condition is repeatable and requires no frontrunning or coordination.

## Recommendation
Add a normalization guard inside `init_transfer` (or at the top of `init_transfer_internal`) before any tokens are burned or locked. Look up the destination token's `Decimals` and assert the normalized amount is non-zero:

```rust
let token_address = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This mirrors the guard already present in `sign_transfer` (L475-485) but moves it to before funds are committed.

## Proof of Concept
1. Register a NEAR-native token `token.near` with `origin_decimals = 24`, `decimals = 6` on Ethereum (normalization factor = `10^18`).
2. User calls `ft_transfer_call` on `token.near` with `amount = 5 * 10^17` (0.5 tokens, below `10^18`), targeting the bridge with an `InitTransfer` message specifying an Ethereum recipient and `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (L554-557). `init_transfer_internal` burns the 0.5 tokens and stores the transfer in `pending_transfers`. `ft_on_transfer` returns `U128(0)` — tokens are gone from the user.
4. Relayer calls `sign_transfer` for this transfer. `normalize_amount(5 * 10^17, Decimals { origin_decimals: 24, decimals: 6 })` = `5 * 10^17 / 10^18` = `0`. The `require!(amount_to_transfer > 0)` at L482-485 panics. The MPC call is never made; `sign_transfer_callback` is never reached.
5. The transfer remains in `pending_transfers` indefinitely. The 0.5 tokens are permanently burned with no recovery path. Repeating step 4 always produces the same panic. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)
