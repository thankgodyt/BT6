Audit Report

## Title
Unchecked Return Value of `burn` Cross-Contract Call via `.detach()` Enables Silent Burn Failure and Token Supply Inflation — (`near/omni-bridge/src/lib.rs`)

## Summary

`burn_tokens_if_needed` schedules a cross-contract `burn` call with `.detach()`, permanently discarding the promise result. If the burn fails for any reason, the bridge proceeds as if it succeeded: `InitTransferEvent` is emitted, the transfer record is stored, and a relayer can finalize the transfer on the destination chain — minting tokens there while the original tokens remain unburned in the bridge contract, inflating total supply.

## Finding Description

`burn_tokens_if_needed` (lines 1806–1813, `near/omni-bridge/src/lib.rs`) is the sole guard against double-minting for bridge-deployed tokens:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)   // 3 TGas — line 72
            .burn(amount)
            .detach();                          // result permanently discarded
    }
}
```

`BURN_TOKEN_GAS` is set to 3 TGas (line 72). `.detach()` severs the promise chain: the NEAR runtime never surfaces the burn outcome back to the bridge. Any failure — out-of-gas, panic inside the token contract, or storage inconsistency — is silently swallowed.

The function is invoked at four security-critical sites:

1. **`init_transfer_internal` (line 1851)**: After `burn_tokens_if_needed` returns (without awaiting the burn), the function unconditionally emits `InitTransferEvent` and returns `U128(0)` to `ft_transfer_call`, signalling all tokens were consumed. If the burn fails, tokens remain in the bridge while the event is on-chain.

2. **`resolve_fast_transfer` (line 904)**: The in-code comment reads *"Burn the tokens to ensure the locked tokens are not double-minted"* — explicitly acknowledging the burn is the guard against double-minting. A silent burn failure removes that guard entirely.

3. **`fast_fin_transfer_to_other_chain` (line 932)**: Burn is called before the transfer record is committed and the event emitted.

4. **`fin_transfer_send_tokens_callback` (lines 1702–1710)**: Burn is called in the refund path; silent failure leaves tokens stranded in the bridge while the transfer record is removed.

The token contract's `burn` function (lines 146–151, `near/omni-token/src/lib.rs`) calls `assert_controller()` then `internal_withdraw`. While the bridge is the controller, the call can fail if: (a) the 3 TGas budget is exhausted by runtime overhead in a deeply nested call stack, or (b) the bridge's registered balance in the token contract is zero or inconsistent due to a prior accounting error or race condition, causing `internal_withdraw` to panic.

The project's own security checklist (`near/CLAUDE.md`, line 228) explicitly flags this pattern: *"Detached promises should only be used for non-critical operations."* The burn is unambiguously a critical operation.

## Impact Explanation

**Critical — unauthorized token minting / token supply inflation of bridged assets.**

For bridge-deployed tokens (e.g., wETH, wSOL minted by the bridge on NEAR), the invariant is: tokens sent outbound must be burned on NEAR before equivalent tokens are minted on the destination chain. If the burn silently fails:

- The `InitTransferEvent` is already on-chain.
- A relayer submits the proof to the destination chain and mints `amount` tokens there.
- The original `amount` tokens remain unburned in the bridge contract on NEAR.
- Total circulating supply increases by `amount` — permanent inflation of the bridged token.

This matches the allowed critical impact: *"unauthorized minting… of bridged funds"* and *"balance manipulation… that changes user or protocol balances."*

## Likelihood Explanation

The entry point is `ft_transfer_call` on any bridge-deployed token — a fully public, unprivileged call available to any token holder. No special role or permission is required to initiate the transfer. The burn failure can be triggered by:

- **Gas exhaustion**: `BURN_TOKEN_GAS` is only 3 TGas. In a deeply nested call (`ft_transfer_call → ft_on_transfer → init_transfer_internal → burn`), the NEAR runtime's base cross-contract call overhead can consume a significant fraction of this budget, leaving insufficient gas for the token contract's execution.
- **Token contract state inconsistency**: If the bridge's registered balance in the token contract is zero or inconsistent (e.g., due to a prior accounting bug or race condition), `internal_withdraw` panics, the burn fails, and `.detach()` hides it.

Because the failure is silent, it may go undetected until the supply discrepancy is noticed on-chain.

## Recommendation

Replace `.detach()` with a proper callback that checks the burn result and reverts the transfer if the burn failed:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) -> Option<Promise> {
    if self.is_deployed_token(&token) {
        Some(
            ext_token::ext(token)
                .with_static_gas(BURN_TOKEN_GAS)
                .burn(amount)
        )
    } else {
        None
    }
}
```

In `init_transfer_internal`, chain the burn promise and add a callback that panics (causing the entire `ft_transfer_call` to refund) if the burn fails. In `resolve_fast_transfer` and `fast_fin_transfer_to_other_chain`, the burn result must be awaited before the transfer record is committed or the event is emitted. Additionally, increase `BURN_TOKEN_GAS` from 3 TGas to at least 10–15 TGas to provide a safe margin.

## Proof of Concept

1. Attacker holds `N` units of a bridge-deployed token (e.g., `weth.bridge.near`).
2. Attacker calls `ft_transfer_call(bridge.near, N, msg=InitTransfer{recipient: eth_address, ...})`.
3. Token contract transfers `N` tokens to `bridge.near` and calls `ft_on_transfer`.
4. Bridge calls `init_transfer_internal` → `burn_tokens_if_needed` → schedules `burn(N).detach()`.
5. Due to gas exhaustion or token contract panic, the burn fails — silently.
6. Bridge emits `InitTransferEvent{amount: N, recipient: eth_address}` and returns `U128(0)` to `ft_transfer_call` (no refund).
7. A relayer picks up the event and calls `finTransfer` on the EVM bridge, minting `N` wETH to `eth_address`.
8. Result: `N` wETH exist on Ethereum AND `N` weth tokens remain unburned in `bridge.near` — total supply inflated by `N`.

To reproduce locally: write a mock token contract whose `burn` function always panics, register it as a deployed token in the bridge, then execute the `ft_transfer_call` flow and verify that `InitTransferEvent` is emitted despite the burn failure, and that a subsequent `finTransfer` on the destination chain succeeds.
