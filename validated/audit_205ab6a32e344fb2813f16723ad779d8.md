### Title
Unprivileged Caller Hijacks Refund `BTCPendingInfo` Ownership via `execute_refund`, Permanently Locking Victim's BTC Until Operator Intervention - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/bitcoin_utils/refund.rs, contracts/satoshi-bridge/src/refund.rs)

---

### Summary

`execute_refund` is a permissionless function callable by any NEAR account for any pending refund request. The function assigns the resulting `BTCPendingInfo` to `env::predecessor_account_id()` (the caller), not to the original depositor. On Bitcoin, the refund transaction is deterministic (same inputs → same txid), so a second call by the victim fails with "pending info already exist." The victim's BTC is stuck: they cannot sign the refund (it belongs to the attacker's account) and cannot re-execute it (duplicate txid). Recovery requires DAO/Operator intervention.

---

### Finding Description

`execute_refund` has no access control — any NEAR account may call it for any `utxo_storage_key`: [1](#0-0) 

Inside `internal_execute_refund` (Bitcoin path), the caller is captured as `env::predecessor_account_id()` and forwarded to `finalize_refund_with_psbt`: [2](#0-1) 

`finalize_refund_with_psbt` creates the `BTCPendingInfo` with `account_id: caller.clone()` (the attacker) and inserts the pending id into the attacker's `btc_pending_sign_ids`: [3](#0-2) 

The attacker's account is auto-created if it does not exist, so no prior registration is required: [4](#0-3) 

The default pending-sign capacity is 1 per account, so the attacker can execute exactly one victim refund per attacker account (trivially bypassed with multiple accounts): [5](#0-4) 

On Bitcoin, the refund PSBT is built from fixed inputs (the deposit UTXO) and a fixed output (the `refund_address` stored in the `RefundRequest`). The resulting txid is therefore deterministic. A second call by the victim hits:

```
require!(
    self.data_mut().btc_pending_infos.insert(...).is_none(),
    "pending info already exist"
);
``` [6](#0-5) 

This is confirmed by the existing test comment: *"The second call therefore tries to insert an already-existing `BTCPendingInfo` and is rejected."*

The `reject_refund` permissionless path is also blocked because `executed == true` prevents the `is_already_deposited` shortcut: [7](#0-6) 

And `remove_refund_pending_tx_id` is blocked while the refund request still exists: [8](#0-7) 

---

### Impact Explanation

The victim's BTC deposit is locked in the refund pipeline:

1. The `BTCPendingInfo` is owned by the attacker — only the attacker can call `sign_btc_transaction` for it.
2. The victim cannot re-execute the refund (same Bitcoin txid → "pending info already exist").
3. The victim cannot self-service clean up the stale pending info (refund request is still active).
4. Recovery requires DAO/Operator to: (a) reject the refund request, (b) remove the stale pending info, after which the victim must re-submit `request_refund` and wait through the full timelock again.

The attacker has zero financial incentive to sign (the BTC would go to the victim's `refund_address` anyway), so the lock is indefinite without operator intervention.

**Matched impact:** Medium — attacker-triggered temporary locking of bridged funds requiring operator intervention.

---

### Likelihood Explanation

- `execute_refund` is fully permissionless and `#[payable]` only to cover a small storage deposit.
- Any NEAR account can call it for any refund request after the timelock passes.
- The attacker needs no special knowledge beyond the `utxo_storage_key` (a public `{txid}@{vout}` string emitted in the `RefundRequested` event).
- The attack is cheap (one NEAR transaction + storage deposit) and repeatable with multiple attacker accounts.

---

### Recommendation

Restrict `execute_refund` so that only the original depositor (the `recipient_id` from `deposit_msg`) or a privileged role (DAO/Operator/RefundOperator) may call it. If permissionless execution is desired for liveness (analogous to the Party protocol's rationale), assign the `BTCPendingInfo` to the original depositor's account rather than to `env::predecessor_account_id()`, so the depositor retains signing rights regardless of who triggers execution.

```rust
// In internal_execute_refund / finalize_refund_with_psbt:
// Replace:
let caller = env::predecessor_account_id();
// With:
let caller = refund_request.deposit_msg().recipient_id;
// (or enforce: require!(env::predecessor_account_id() == recipient_id || is_privileged))
```

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address. The relayer never calls `verify_deposit`.
2. Alice calls `request_refund(deposit_msg, "bc1q_alice...", tx_bytes, vout, proof, None)`. The `RefundRequested` event is emitted with `utxo_storage_key = "{txid}@0"`.
3. The timelock passes.
4. Attacker (Bob) calls `execute_refund("{txid}@0", None)` with the required storage deposit.
   - `internal_execute_refund` captures `caller = bob.near`.
   - `finalize_refund_with_psbt(bob.near, ...)` creates `BTCPendingInfo { account_id: bob.near, ... }`.
   - The pending id is inserted into Bob's `btc_pending_sign_ids`.
5. Alice calls `execute_refund("{txid}@0", None)`.
   - The Bitcoin refund PSBT is identical → same txid → `"pending info already exist"` → **reverts**.
6. Alice cannot call `sign_btc_transaction` (the pending info belongs to Bob).
7. Bob never signs. Alice's BTC is locked indefinitely.
8. Only DAO/Operator can unblock Alice by rejecting the refund request and removing the stale pending info, after which Alice must restart the entire refund flow.
