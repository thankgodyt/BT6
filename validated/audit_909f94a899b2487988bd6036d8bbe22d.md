### Title
Peras Certificate Validation Stub Always Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` for every certificate it receives, performing no cryptographic or semantic checks. Because this is the only instance currently wired into the production object-diffusion pipeline, any unprivileged peer can send a crafted `PerasCert` that names an arbitrary block as its boosted target. The certificate is accepted, stored in `PerasCertDB`, and its weight boost is immediately applied during chain selection, potentially causing an honest node to prefer an adversarial fork.

---

### Impact Explanation

An adversary who has already delivered a block to the target node's VolatileDB (via normal block diffusion) can send a crafted `PerasCert` naming that block as the boosted target. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored, and its weight boost is applied. Chain selection then re-evaluates the adversarial fork with an inflated `wsvTotalWeight`. If the boost is large enough (determined by `perasWeight mkPerasParams`, a placeholder value), the node switches to the adversarial fork, constituting a chain-selection safety failure driven entirely by a peer-supplied, unvalidated object.

**Impact class:** Critical — bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-weight manipulation that can cause an honest node to prefer a non-canonical chain.

---

### Likelihood Explanation

The attack requires only that the adversary (a) be a connected peer, (b) have previously diffused a block to the target node's VolatileDB, and (c) send a single crafted `PerasCert` message via the object-diffusion mini-protocol. No key material, stake majority, or privileged access is needed. The stub is the only validation gate in the production path and is explicitly acknowledged as incomplete via TODO comments referencing open issues.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before enabling the Peras object-diffusion pipeline in any production or pre-production environment. At minimum, verify the committee membership proof, the VRF/BLS signature over the target block, and that the boosted block's slot falls within the valid Peras round window.
2. **Remove or gate the degenerate `BlockSupportsPeras` instance** so that it cannot be reached by the production diffusion path until a real Cardano-specific instance is in place.
3. **Add a secondary validation check in `implAddCert`** (as noted by the existing TODO) so that the `PerasCertDB` itself rejects structurally invalid certificates even if the inbound pipeline is misconfigured.

---

### Proof of Concept

Private-testnet reproduction sequence:

1. Start a node with the Peras object-diffusion pipeline enabled (current default with the stub instance).
2. Diffuse a valid but minority-fork block `B_adv` to the target node so it lands in the VolatileDB.
3. From a peer connection, send a `PerasCert` message with `pcCertBoostedBlock = blockPoint B_adv` and any `pcCertRound`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
5. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
6. `chainSelSync` stores the cert, reads the boosted block from VolatileDB, and calls `chainSelectionForBlock` for `B_adv`.
7. `weightedSelectView` computes `wsvTotalWeight` for the adversarial fragment including the injected boost.
8. If `perasWeight mkPerasParams` exceeds the honest chain's length advantage, `preferCandidate` returns `ShouldSwitch` and the node adopts the adversarial fork.
