### Title
Unprivileged Attacker Can Front-Run `request_refund` to Redirect Victim's BTC Refund — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary
When a user's `deposit_msg.refund_address` is `None`, any unprivileged NEAR account can call `request_refund` for the same UTXO and supply an attacker-controlled `refund_address`. By front-running the legitimate user's transaction, the attacker creates the only permitted refund request for that UTXO and routes the victim's BTC to themselves.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is a public, payable function with no caller-identity restriction: [1](#0-0) 

The only validation on `refund_address` is: [2](#0-1) 

When `deposit_msg.refund_address` is `None` this check is skipped entirely, so the caller may supply any Bitcoin address. The stored `refund_address` is later used verbatim to build the refund output: [3](#0-2) [4](#0-3) 

A second hard constraint makes the attack decisive: only one refund request may exist per UTXO at a time: [5](#0-4) 

An attacker who observes a victim's pending `request_refund` transaction in the NEAR mempool can copy the `deposit_msg`, `tx_bytes`, `vout`, and `proof` fields, substitute `refund_address` with their own Bitcoin address, and submit with equal or higher priority. If the attacker's transaction is included first, the victim's transaction reverts with "Refund request already exists for this UTXO" and the stored request now points to the attacker's address.

The `unsafe_refund_timelock_sec` (default 14 days) applies when `deposit_msg.refund_address` is `None`: [6](#0-5) 

After the timelock, `execute_refund` is callable by anyone, including the attacker, who then receives the victim's BTC.

---

### Impact Explanation

**Critical path (DAO does not reject in time):** The attacker calls `execute_refund` after 14 days and receives the victim's full BTC deposit minus the default gas fee. This is direct theft of user funds.

**Medium path (DAO rejects):** The attacker can immediately re-submit a new malicious `request_refund` after each rejection, forcing the DAO to monitor and reject indefinitely. The victim's funds remain locked for as long as the attacker continues the griefing loop, constituting attacker-triggered temporary (potentially permanent) locking of bridged funds.

---

### Likelihood Explanation

- `request_refund` is a public function with no caller restriction; any NEAR account can invoke it.
- The attack only applies to deposits where `deposit_msg.refund_address` is `None`, which is a documented and common usage pattern (users who do not pre-authorize a refund address).
- The attacker needs the `deposit_msg` and Merkle proof, both of which are visible in the victim's pending NEAR transaction, making mempool-based front-running straightforward.
- NEAR's ~1-second block time makes front-running harder than on Ethereum but not infeasible, especially for validators or well-connected nodes.

---

### Recommendation

Restrict who may create a refund request for a given UTXO. The simplest fix is to require that the caller is the `deposit_msg.recipient_id` (the intended NEAR beneficiary of the deposit). Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) so the refund destination is fixed at deposit time and cannot be injected by a third party.

---

### Proof of Concept

1. Alice deposits BTC with `deposit_msg = { recipient_id: "alice.near", refund_address: None }`.
2. The deposit is never finalized (relayer does not call `verify_deposit`).
3. Alice constructs and broadcasts `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, vout, proof, None)` to the NEAR mempool.
4. Attacker observes Alice's pending transaction, extracts all parameters, and broadcasts `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)` with equal or higher priority.
5. Attacker's transaction is included first; Alice's reverts with "Refund request already exists for this UTXO".
6. The stored `RefundRequest.refund_address` is `"attacker_btc_addr"`.
7. After 14 days (if the DAO/Operator does not reject), the attacker calls `execute_refund`, and the bridge MPC signs a Bitcoin transaction paying Alice's deposit to the attacker's address.
8. Alice's BTC is permanently lost to the attacker.
