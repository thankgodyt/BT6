### Title
Hardcoded `required_balance_for_request_refund` and `required_balance_for_execute_refund` Cannot Be Adjusted, Blocking Refund Flows When NEAR Price Rises - (File: `contracts/satoshi-bridge/src/api/view.rs`)

### Summary
`required_balance_for_request_refund()` and `required_balance_for_execute_refund()` are hardcoded to 2 NEAR and 1 NEAR respectively with no setter. If NEAR's market price rises significantly, these mandatory attached deposits become prohibitively expensive relative to small BTC deposits, blocking users from initiating or executing the refund flow and leaving their BTC permanently locked in the bridge.

### Finding Description
Both refund entrypoints enforce a hardcoded minimum attached NEAR deposit:

`request_refund` (the permissionless entry to register a refund for an unfinalized deposit) requires: [1](#0-0) 

`execute_refund` (the permissionless entry to build and sign the refund PSBT) requires: [2](#0-1) 

These values are enforced as hard `require!` guards inside the internal refund logic: [3](#0-2) [4](#0-3) 

Neither value appears in `ConfigUpdate` and there is no setter anywhere in the contract: [5](#0-4) 

The `update_config` management function only applies fields present in `ConfigUpdate`, so these two thresholds are permanently fixed at deployment: [6](#0-5) 

### Impact Explanation
A user who deposited BTC but whose deposit was never finalized (e.g., the relayer never called `verify_deposit_v2`) must go through the refund flow to recover their BTC. If NEAR's price rises (historically it has reached $15–$20), the combined cost to `request_refund` (2 NEAR) and `execute_refund` (1 NEAR) can exceed the USD value of a small BTC deposit. The user is then economically blocked from recovering their funds. Because the deposits are explicitly non-refundable (the comments state "the deposit is NOT refunded"), there is no workaround. The BTC remains locked in the bridge-controlled address indefinitely.

This matches: **Low. Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft.**

### Likelihood Explanation
NEAR's price is volatile. At $10/NEAR the combined 3 NEAR cost is $30; at $20/NEAR it is $60. A user who deposited 0.001 BTC (≈$100 at $100k BTC) would pay 30–60% of their deposit value just to initiate a refund, making recovery economically irrational. This is a realistic market condition, not a theoretical one.

### Recommendation
Add the two thresholds to `Config` / `ConfigUpdate` so the DAO can adjust them as NEAR's price changes:

```rust
// In Config:
pub required_balance_for_request_refund: NearToken,
pub required_balance_for_execute_refund: NearToken,

// In ConfigUpdate:
pub required_balance_for_request_refund: Option<NearToken>,
pub required_balance_for_execute_refund: Option<NearToken>,
```

Replace the hardcoded `NearToken::from_near(2)` / `NearToken::from_near(1)` in `view.rs` with reads from config, and apply them in `ConfigUpdate::apply` with a validity check (e.g., `> 0`).

### Proof of Concept
1. Bridge is deployed with `required_balance_for_request_refund = 2 NEAR` and `required_balance_for_execute_refund = 1 NEAR`.
2. User deposits 0.001 BTC (≈$100). The relayer never calls `verify_deposit_v2`; the deposit is unfinalized.
3. NEAR price rises to $20. The user must attach 2 NEAR ($40) to call `request_refund` and 1 NEAR ($20) to call `execute_refund` — a combined $60 to recover $100 of BTC.
4. The `require!` at `refund.rs:147` and `refund.rs:203` will panic with "Insufficient deposit for storage" if the user attaches less.
5. No DAO action can lower these thresholds because no setter exists. The user's BTC remains locked.

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
