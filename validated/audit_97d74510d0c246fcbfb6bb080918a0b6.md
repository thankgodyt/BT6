Audit Report

## Title
Unvalidated `token_id` in `log_metadata` Allows Any Caller to Obtain MPC-Signed Metadata for Arbitrary NEAR Contracts, Enabling Fake Bridge Token Deployment on Foreign Chains - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`log_metadata` accepts an arbitrary NEAR `AccountId` with no check that it is a registered bridge token. The bridge calls `ft_metadata()` on the caller-supplied account and, if the call succeeds, submits the returned metadata to the MPC signer. The resulting MPC signature is the sole authorization mechanism accepted by the EVM (and Starknet) `deployToken` function, so an attacker who controls any NEAR account implementing `ft_metadata()` can obtain a valid bridge-signed metadata event and use it to deploy a fraudulent bridge token on any supported foreign chain.

## Finding Description

`log_metadata` in `near/omni-bridge/src/lib.rs` (lines 316–327) performs no allowlist or registry check on `token_id` before initiating the cross-contract call chain:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn log_metadata(&self, token_id: &AccountId) -> Promise {
    ext_token::ext(token_id.clone())
        .with_static_gas(LOG_METADATA_GAS)
        .ft_metadata()
        .then(...)
}
```

The callback `log_metadata_callback` (lines 336–339) applies only a trivial non-emptiness check on the returned metadata fields, then constructs a `MetadataPayload` and submits it to `self.mpc_signer` for signing (lines 353–360). No check against `self.token_id_to_address`, `self.token_address_to_id`, `self.deployed_tokens`, or any other registry is performed.

On the EVM side, `OmniBridge.deployToken` (lines 135–195 of `OmniBridge.sol`) accepts the signed payload and verifies only that `ECDSA.recover(hashed, signatureData) == nearBridgeDerivedAddress` (line 151) and that the token is not already deployed (lines 155–158). It then deploys a new ERC-20 proxy and registers the mapping `nearToEthToken[metadata.token] = bridgeTokenProxy`. The Starknet bridge (`omni_bridge.cairo`, lines 202–240) applies the same pattern: `_verify_borsh_signature` then deploy.

The exploit path:
1. Attacker deploys `fake-usdc.attacker.near` implementing `ft_metadata()` returning `{name: "USD Coin", symbol: "USDC", decimals: 6}`.
2. Attacker calls `log_metadata("fake-usdc.attacker.near")` on the bridge, attaching sufficient NEAR for MPC gas.
3. Bridge calls `ft_metadata()` on the attacker contract; the non-emptiness check passes.
4. Bridge submits `MetadataPayload{token: "fake-usdc.attacker.near", name: "USD Coin", symbol: "USDC", decimals: 6}` to MPC and receives a valid signature.
5. A `LogMetadataEvent` carrying the valid MPC signature is emitted.
6. Attacker calls `deployToken(signature, metadata)` on the EVM bridge; signature verification passes; a new ERC-20 "USD Coin (USDC)" is deployed and registered as the bridge representation of `fake-usdc.attacker.near`.

By contrast, the legitimate `bind_token` path (lines 1223–1300) requires a cryptographic proof from a registered factory address (`self.factories`), and `add_prover`/`add_factory` are gated behind `Role::DAO`. No equivalent guard exists for `log_metadata`.

## Impact Explanation

The MPC-signed `LogMetadataEvent` is the sole authorization credential accepted by `OmniBridge.deployToken` on EVM and `deploy_token` on Starknet. An attacker who obtains a valid signature over attacker-chosen metadata can:

- Deploy a fraudulent ERC-20 token on EVM that is indistinguishable from a legitimate bridge token at the signature-verification level, satisfying the **token metadata binding confusion** Critical impact class.
- List the fake token on DEXes; users who purchase it believing it is the legitimate bridge USDC and subsequently attempt to bridge it back to NEAR receive worthless `fake-usdc.attacker.near` tokens — a concrete, direct fund loss.
- Permanently pollute the bridge's `nearToEthToken` / `ethToNearToken` mappings with attacker-controlled entries, constituting an **unauthorized bridge action** (deploying a bridge token without going through the proof-based `bind_token` path).

Both "token metadata binding confusion that changes user or protocol balances" and "authorization bypass that lets an attacker execute bridge actions" are explicitly listed Critical impact classes.

## Likelihood Explanation

- `log_metadata` is callable by any NEAR account; the only gate is the global pause, which is not active in normal operation.
- Deploying a NEAR contract implementing `ft_metadata()` with arbitrary return values costs a trivial amount of NEAR (storage deposit only).
- The attacker must attach enough NEAR to cover MPC signing gas — a small, fixed cost.
- No privileged access, leaked keys, validator collusion, or social engineering is required to execute the on-chain steps. The attack is fully self-contained.
- Likelihood is **High**.

## Recommendation

Add a registry check at the start of `log_metadata` to ensure `token_id` is already registered in the bridge before proceeding:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn log_metadata(&self, token_id: &AccountId) -> Promise {
    require!(
        self.token_id_to_address.get(token_id).is_some()
            || self.is_deployed_token(token_id),
        BridgeError::TokenNotRegistered.as_ref()
    );
    ext_token::ext(token_id.clone())
        ...
}
```

Alternatively, maintain an explicit DAO-managed allowlist of `AccountId`s permitted to have their metadata signed, analogous to how `add_prover` and `add_factory` are gated behind `Role::DAO`.

## Proof of Concept

**Local integration test plan (near-workspaces):**

1. Deploy the bridge contract and a mock MPC signer in a sandbox worker.
2. Deploy an attacker-controlled NEAR contract `fake-usdc.attacker.near` that implements `ft_metadata()` returning `{name: "USD Coin", symbol: "USDC", decimals: 6}`.
3. Call `log_metadata("fake-usdc.attacker.near")` from an unprivileged account with sufficient attached NEAR for MPC gas.
4. Assert that the transaction succeeds and that a `LogMetadataEvent` is emitted containing a valid MPC signature over the fake metadata.
5. On the EVM side (Hardhat test), call `OmniBridge.deployToken(signature, {token: "fake-usdc.attacker.near", name: "USD Coin", symbol: "USDC", decimals: 6})`.
6. Assert that `ECDSA.recover` passes and a new ERC-20 proxy is deployed and registered in `nearToEthToken`.
7. Confirm that `nearToEthToken["fake-usdc.attacker.near"]` now points to the fraudulent token, and that `isBridgeToken[fraudulentAddress]` is `true`.

The existing Hardhat test `createToken` in `evm/tests/BridgeToken.ts` (lines 61–67) already demonstrates that a valid `metadataSignature` is sufficient to deploy a token — the only missing piece is showing that the NEAR bridge will produce such a signature for an unregistered account, which the NEAR-side integration test above demonstrates directly.
