### Title
Peras Certificate Validation Bypass via Stub `validatePerasCert` Always Returning `Right` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production object-diffusion inbound path for Peras certificates calls `validatePerasCert mkPerasParams` on every certificate received from a peer. The universal `BlockSupportsPeras` instance that backs this call is an explicitly acknowledged stub that unconditionally returns `Right` — accepting every certificate without performing any cryptographic, semantic, or committee-membership check. An unprivileged peer can therefore inject arbitrary `PerasCert` values (any round number, any boosted block) that are stored in the `PerasCertDB` / `ChainDB` and used to apply weight boosts during chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve an inbound certificate before it is stored. The sole concrete instance in the codebase is a degenerate catch-all:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }

This stub is directly wired into both production pool-writer paths:

```haskell

(validatePerasCert mkPerasParams)   -- makePerasCertPoolWriterFromChainDB

`processCerts` calls `validateCert` on each inbound certificate; if all pass (which they always do), they are timestamped and added to the database:

```haskell

  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts

Every accepted `ValidatedPerasCert` carries a `vpcCertBoost = perasWeight params` (currently `PerasWeight 15`). These boosts feed directly into the Peras-aware chain-selection weight, which is the basis for `maxRollbackWeight` and the `ChainOrder` comparison: [5](#0-4) 

---

### Impact Explanation

**Allowed impact class: Critical — Bypass of certificate/vote/signature validation that enables unauthorized certificate acceptance.**

An attacker who can send messages via the Peras object-diffusion mini-protocol can craft a `PerasCert` naming any `pcCertRound` and any `pcCertBoostedBlock` (including a block on an adversarial fork). Because `validatePerasCert` never rejects, the certificate is stored and its `PerasWeight 15` boost is applied to the named block during chain selection. By injecting certificates for blocks on a minority fork, an adversary can artificially inflate that fork's chain weight, potentially causing an honest node to prefer the adversarial chain over the honest chain — a chain-selection safety failure.

---

### Likelihood Explanation

The object-diffusion mini-protocol is reachable by any peer that can establish a connection to the node. No stake, keys, or operator access is required. The only prerequisite is knowing the wire format of `PerasCert`, which is fully specified by the `Serialise` instance in the same file. The stub has been present since the Peras feature branch was merged and is guarded only by a GitHub issue reference, not by a feature flag or era gate that would prevent it from being exercised on a live network.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real check that verifies at minimum:
1. The certificate's aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` is valid.
2. The signers are members of the elected committee for that round.
3. The combined stake of the signers meets the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).

Until the real implementation is ready, the inbound certificate pool writer should be disabled or gated behind an era/feature flag so that no peer-supplied certificate can influence chain selection.

---

### Proof of Concept

1. Connect to a node that has the Peras object-diffusion server enabled.
2. Send a `PerasCert` message with `pcCertRound = <target round>` and `pcCertBoostedBlock = <adversarial block point>`.
3. Observe via tracing that `AddedPerasCertToDB` is emitted — the certificate is stored without any rejection.
4. The stored certificate's `PerasWeight 15` boost is now applied to the adversarial block in subsequent chain-selection comparisons, making that block's chain heavier than an equal-length honest chain by 15 weight units.
