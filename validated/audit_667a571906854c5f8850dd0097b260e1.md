### Title
Re-execution of `execute_refund` Is Permanently Blocked After First Attempt, Locking User Funds — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`finalize_refund_with_psbt` immediately adds the deposit UTXO to `verified_deposit_utxo` and inserts a `BTCPendingInfo` entry the moment `execute_refund` is first called. If the resulting refund transaction is never confirmed on-chain (e.g., a Zcash transaction expires past its `expiry_height`, or the signed transaction is simply never broadcast), the user cannot re-execute the refund: the old `BTCPendingInfo` blocks a second insert, and that entry cannot be cleaned up because `internal_remove_refund_pending_tx_id` refuses to act while the refund request is still live. The UTXO is simultaneously barred from being re-deposited. The user's BTC/ZEC is permanently locked with no recovery path.

---

### Finding Description

**Step 1 — `execute_refund` marks the UTXO verified and creates a pending entry.**

`finalize_refund_with_psbt` (called from every `execute_refund` path) does two things before the refund transaction is ever confirmed on-chain:

```
// refund.rs:366-372  — blocks any second call with the same pending id
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [1](#0-0) 

```
// refund.rs:377-380  — permanently marks UTXO as "used"
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [2](#0-1) 

It then sets `executed = true` and re-saves the request so that `load_refund_request_for_execute` will permit a future re-execution call: [3](#0-2) 

**Step 2 — Re-execution is intended but structurally impossible.**

The `executed` field comment and `load_refund_request_for_execute` both document that re-execution is allowed when `executed == true` (e.g., after a Zcash consensus-branch change): [4](#0-3) [5](#0-4) 

However, `finalize_refund_with_psbt` will always panic with `"pending info already exist"` on the second call because the first `BTCPendingInfo` is still present and `btc_pending_id` is deterministic from the PSBT inputs/outputs.

**Step 3 — The old `BTCPendingInfo` cannot be removed.**

`internal_remove_refund_pending_tx_id` explicitly refuses to act while the refund request is still live:

```
// refund.rs:418-424
require!(
    !self
        .data()
        .refund_requests
        .contains_key(&utxo_storage_keys[0]),
    "refund request still active"
);
``` [6](#0-5) 

But the refund request is kept alive (with `executed = true`) precisely so re-execution can happen — creating a circular deadlock.

**Step 4 — Operator intervention cannot recover funds.**

An operator can call `internal_reject_refund` to remove the refund request, which then allows `internal_remove_refund_pending_tx_id` to clean up the stale `BTCPendingInfo`. However, the UTXO remains permanently in `verified_deposit_utxo`. With the refund request gone, `execute_refund` panics with `"Refund request not found"`, and `request_refund_callback` rejects any new request with `"UTXO already verified via deposit"`: [7](#0-6) 

There is no code path that removes an entry from `verified_deposit_utxo` outside of normal finalization. The user's funds are irrecoverable.

---

### Impact Explanation

**Critical — Permanent locking of user funds.**

Once `execute_refund` is called and the resulting transaction is not confirmed, the deposit UTXO is simultaneously:
- Blocked from being minted as nBTC (`verified_deposit_utxo` check in `verify_deposit`)
- Blocked from being re-refunded (`"pending info already exist"` in `finalize_refund_with_psbt`)
- Blocked from any new refund request (`"UTXO already verified via deposit"` in `request_refund_callback`)

The user's BTC or ZEC sitting at the bridge deposit address is permanently inaccessible.

---

### Likelihood Explanation

**Medium-High for Zcash, Low-Medium for Bitcoin.**

Zcash V5 transactions carry an `expiry_height` field. If the signed refund transaction is not broadcast and confirmed before that height, it becomes permanently invalid. The bridge's Zcash refund path fetches the current block height asynchronously to set this field: [8](#0-7) 

Any user who calls `execute_refund` on a Zcash UTXO and then fails to broadcast the signed transaction before expiry (due to network issues, wallet problems, or simply not knowing they must act quickly) will trigger this stuck state. For Bitcoin, transactions do not expire, but a user who never broadcasts the signed transaction (e.g., loses the signed bytes) faces the same deadlock.

---

### Recommendation

1. **Before inserting a new `BTCPendingInfo` in `finalize_refund_with_psbt`**, check whether an old entry with the same `btc_pending_id` already exists and remove it if `refund_request.executed == true`. This makes re-execution actually work as documented.
2. **Delay adding the UTXO to `verified_deposit_utxo`** until `verify_refund_finalize_callback` succeeds, not at `execute_refund` time. Use a separate "refund-in-progress" set to block concurrent `verify_deposit` calls during the signing window.
3. **Relax the guard in `internal_remove_refund_pending_tx_id`** to allow removal of a stale pending entry when `refund_request.executed == true`, so operators have a recovery path without needing to reject the entire refund request.

---

### Proof of Concept

1. User deposits ZEC to the bridge-controlled address → UTXO `A` (`txid@vout`).
2. User calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof)` → `RefundRequest` stored, `executed = false`.
3. Timelock elapses; user calls `execute_refund("txid@vout")`.
   - `finalize_refund_with_psbt` runs: `BTCPendingInfo` inserted, `verified_deposit_utxo` ← `"txid@vout"`, `executed = true`.
4. The Zcash refund transaction's `expiry_height` passes before the user broadcasts it → transaction is permanently invalid on Zcash.
5. User calls `execute_refund("txid@vout")` again to rebuild with a fresh `expiry_height`.
   - `load_refund_request_for_execute` passes (`executed == true` satisfies the `verified_deposit_utxo` check).
   - `finalize_refund_with_psbt` panics: **`"pending info already exist"`**.
6. User tries `internal_remove_refund_pending_tx_id(old_tx_id)` → panics: **`"refund request still active"`**.
7. Operator calls `internal_reject_refund("txid@vout")` → refund request removed.
8. User tries `request_refund(...)` for the same UTXO → `request_refund_callback` panics: **`"UTXO already verified via deposit"`**.
9. User's ZEC is permanently locked: the UTXO cannot be deposited, refunded, or recovered by any on-chain path.
