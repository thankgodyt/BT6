Audit Report

## Title
Unchecked Multiplication Overflow in `denormalize_amount` Causes Permanent Freezing of Bridged Funds — (`near/omni-bridge/src/lib.rs`)

## Summary

`denormalize_amount` uses a raw `*` operator on `u128` with no overflow guard. The release profile sets `overflow-checks = true`, so an overflow panics rather than wraps. When `fin_transfer_callback` panics, NEAR reverts only the callback's state changes — the prover has already marked the proof as consumed in a prior cross-contract call. The source-chain lock is irreversible and the proof cannot be re-submitted, permanently freezing the user's bridged funds.

## Finding Description

`denormalize_amount` at line 2776–2779 performs an unchecked multiplication:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))
}
``` [1](#0-0) 

The workspace release profile explicitly sets `overflow-checks = true` and `panic = "abort"`: [2](#0-1) 

This means any overflow in `denormalize_amount` causes an immediate abort/panic — silent wrapping is not possible.

`denormalize_amount` is called inside `fin_transfer_callback` at line 725 with the raw normalized amount parsed from the prover result:

```rust
amount: Self::denormalize_amount(init_transfer.amount.0, decimals).into(),
``` [3](#0-2) 

The `fin_transfer` function first calls `verify_proof` as a cross-contract call to the prover (which marks the proof as used in the prover's own state), then chains `fin_transfer_callback` as a subsequent promise: [4](#0-3) 

When `fin_transfer_callback` panics due to overflow, NEAR reverts only the callback's state changes. The prover's state — specifically the proof being marked as consumed — is in a separate contract and is **not** rolled back. The same proof cannot be re-submitted.

For a NEAR-origin token with `origin_decimals = 24` and `decimals = 18` (EVM), `diff_decimals = 6` and the multiplier is `10^6`. The overflow threshold is `u128::MAX / 10^6 ≈ 3.4 × 10^32`. The EVM `initTransfer` accepts `uint128 amount`, giving the full range up to `u128::MAX ≈ 3.4 × 10^38` — well above the overflow threshold.

`denormalize_fee` delegates to `denormalize_amount` and is equally affected: [5](#0-4) 

## Impact Explanation

This matches the allowed critical impact: **permanent freezing of bridged funds**. A user who initiates a transfer on EVM with an amount exceeding `u128::MAX / 10^(origin_decimals - decimals)` will have their source-chain tokens permanently locked in the EVM bridge contract. The proof is consumed, the NEAR-side callback reverts without crediting any tokens, and there is no recovery path. This is an irreversible loss of user funds caused by a broken decimal normalization accounting assumption.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `initTransfer` on the EVM contract with a `uint128` amount above the overflow threshold. No special role or privilege is required. The threshold is high for high-value tokens but is easily reachable for tokens with large supplies and low per-unit value (meme tokens, reward tokens, high-supply fungibles). The EVM contract imposes no upper-bound check on the `amount` parameter.

## Recommendation

Replace the raw arithmetic in `denormalize_amount` with checked operations that fail with a clear error before any state is mutated:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = decimals.origin_decimals
        .checked_sub(decimals.decimals)
        .expect("origin_decimals must be >= decimals")
        .into();
    let multiplier = 10_u128.checked_pow(diff_decimals)
        .expect("decimal multiplier overflow");
    amount.checked_mul(multiplier)
        .expect("denormalize_amount overflow")
}
```

Apply the same pattern to the subtraction `origin_decimals - decimals` in `normalize_amount` (line 2785). Additionally, consider enforcing an upper-bound on `amount` in `fin_transfer_callback` before calling `denormalize_amount`, so that oversized transfers are rejected with a recoverable error rather than an abort.

## Proof of Concept

1. Register a NEAR-origin token via `bind_token`. The stored `Decimals` will be `{ origin_decimals: 24, decimals: 18 }`, giving `diff_decimals = 6`.
2. On EVM, call `initTransfer(tokenAddress, amount = 3.5e32, fee = 0, ...)`. This amount is within `uint128` range but exceeds `u128::MAX / 10^6`.
3. A relayer submits the proof to NEAR `fin_transfer`.
4. `verify_proof` cross-contract call succeeds; the prover marks the proof as used.
5. `fin_transfer_callback` calls `denormalize_amount(3.5e32, { origin_decimals:24, decimals:18 })`.
6. `3.5e32 * 10^6` overflows `u128`; with `overflow-checks = true`, the contract panics/aborts.
7. NEAR reverts the callback's state changes. The prover's consumed-proof record is not reverted.
8. The user's EVM tokens remain locked in the EVM bridge contract with no recovery path.

A fuzz test targeting `denormalize_amount` with `amount > u128::MAX / 10^diff_decimals` will reproduce the panic deterministically.
