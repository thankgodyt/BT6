### Title
Byron EBB Chain-Identity Bypass: `protocolMagicId` Check Unconditionally Skipped for Epoch Boundary Blocks — (`File: ouroboros-consensus-cardano/src/byron/Ouroboros/Consensus/Byron/Ledger/Integrity.hs`)

---

### Summary

Byron Epoch Boundary Blocks (EBBs) carry no signature and no `protocolMagicId` field in their wire format. As a result, every chain-identity check in the consensus layer — `verifyHeaderIntegrity`, `verifyBlockIntegrity`, and `updateChainDepState` — unconditionally returns success for any EBB, regardless of which network it originated from. This is the direct analog of the Shardeum `chainId`-absent transaction replay: just as pre-EIP-155 Ethereum transactions have no `chainId` and can be replayed across chains, Byron EBBs have no signed chain-identity field and pass all network-identity checks on any Byron-compatible node.

---

### Finding Description

**Root cause — `verifyHeaderIntegrity` / `verifyBlockIntegrity`:**

`verifyHeaderIntegrity` explicitly documents that `CC.headerProtocolMagicId` is the only unsigned field in a regular Byron header and checks it manually. For EBBs (`CC.ABOBBoundaryHdr`), the check is skipped with an unconditional `True`:

```haskell
case byronHeaderRaw hdr of
  CC.ABOBBlockHdr h -> CC.headerProtocolMagicId h == protocolMagicId
  -- EBB, we can't check it
  CC.ABOBBoundaryHdr _ -> True
``` [1](#0-0) 

`verifyBlockIntegrity` delegates to `verifyHeaderIntegrity`, so it also returns `True` for every EBB: [2](#0-1) 

**Root cause — `updateChainDepState` (PBFT):**

During header validation via ChainSync, `updateChainDepState` for PBFT returns the existing state unchanged for any EBB, performing zero cryptographic or chain-identity checks:

```haskell
case toValidate of
  PBftValidateBoundary ->
    return state
``` [3](#0-2) 

**Root cause — `validateView` (BlockSupportsProtocol):**

The `validateView` instance for `ByronBlock` routes all EBBs to `pbftValidateBoundary`, which carries no chain-identity information into the PBFT validation pipeline: [4](#0-3) 

**`nodeCheckIntegrity` wiring:**

`nodeCheckIntegrity` for `ByronBlock` is `verifyBlockIntegrity . getByronBlockConfig`, so it returns `True` for all EBBs: [5](#0-4) 

The HardFork combinator dispatches `nodeCheckIntegrity` per-era, so the bypass propagates to `CardanoBlock` as well: [6](#0-5) 

`nodeCheckIntegrity` is wired into both the ImmutableDB and VolatileDB validation paths: [7](#0-6)

### Impact Explanation

`protocolMagicId` is the Byron equivalent of Ethereum's `chainId` — it is the sole chain-identity discriminator for Byron blocks. For regular blocks it is the only unsigned header field and is therefore checked manually. For EBBs the field does not exist in the wire format at all, so no chain-identity check is possible at the consensus layer.

Concrete consequences:

1. **ImmutableDB / VolatileDB startup validation**: After an unclean shutdown, `nodeCheckIntegrity` is the fallback integrity check when CRC32 checksums are unavailable. A cross-network EBB (e.g., a mainnet genesis EBB injected into a testnet node's database) passes this check unconditionally and is treated as a valid local block. The node then builds its chain state on top of it.

2. **ChainSync header pipeline**: An EBB received from a peer passes `updateChainDepState` with zero checks. The only remaining gate is the structural `prevHash` linkage in `validateEnvelope`. For a genesis EBB (`prevHash = GenesisHash`), even this structural check passes on any node starting from an empty chain, because `GenesisHash` is a universal sentinel value, not a network-specific hash.

3. **`nodeCheckIntegrity` used during VolatileDB→ImmutableDB copy**: When `GetVerifiedBlock` is called, `checkIntegrity` is invoked on the block before it is promoted to the ImmutableDB. An EBB from a different network passes this check and is permanently written to the immutable chain. [8](#0-7) 

The net effect is that the chain-identity guarantee provided by `protocolMagicId` is entirely absent for EBBs. Any EBB whose `prevHash` fits the local chain tip is accepted without any network-identity verification, materially weakening block authorization for this block class.

---

### Likelihood Explanation

**Moderate-low.** Three mitigating factors reduce likelihood:

- The DB marker file (`protocolMagicId` file) checked by `stdWithCheckedDB` prevents opening a database belonging to a different network on startup.
- The handshake network-magic check prevents peers from different networks from connecting under normal operation.
- For non-genesis EBBs, the `prevHash` must match the local chain tip, which is a structural (though not cryptographic) barrier.

However, the genesis EBB case removes the `prevHash` barrier entirely. A node syncing from genesis that receives a crafted genesis EBB from a peer (e.g., via a network-layer bug, a misconfigured relay, or a private testnet where the handshake check is relaxed) would accept it through all consensus-layer checks. Additionally, the ImmutableDB fallback path (CRC32 unavailable → `nodeCheckIntegrity`) is reachable after any unclean shutdown, which is a normal operational event.

---

### Recommendation

1. **Add a `protocolMagicId` check to EBB validation.** Although EBBs do not carry a signed `protocolMagicId` field in their `ABoundaryHeader`, the `reAnnotateBoundary` call at forge time does embed the magic in the serialised form. A check analogous to the regular-block path should be added to `verifyHeaderIntegrity` for the `ABOBBoundaryHdr` case, reading the magic from the re-annotated bytes.

2. **Reject EBBs whose `prevHash` does not match a known local block** at the `additionalEnvelopeChecks` level, rather than relying solely on the generic hash-linkage check in `validateEnvelope`.

3. **Document the residual risk** in `NodeInitStorage.nodeCheckIntegrity` that EBBs are uncheckable, so operators and auditors are aware of the gap.

### Proof of Concept

**Scenario: genesis EBB injection on a node syncing from scratch**

1. Node A (testnet, `protocolMagicId = 1097911063`) starts with an empty chain.
2. `nodeInitChainDB` calls `forgeEBB` to create the local genesis EBB and adds it to the ChainDB.
3. Attacker peer sends a `HeaderByron` wrapping a `CC.ABOBBoundaryHdr` genesis EBB constructed with mainnet's `protocolMagicId = 764824073`, `prevHash = GenesisHash`, `epoch = 0`, `blockNo = 0`.
4. `validateView` routes it to `pbftValidateBoundary` → `PBftValidateBoundary`.
5. `updateChainDepState` matches `PBftValidateBoundary` → `return state` (no check).
6. `validateEnvelope` checks: `headerPrevHash == GenesisHash` ✓, `blockNo == 0` ✓, `slotNo == 0` ✓.
7. `additionalEnvelopeChecks` checks only that the slot is an epoch boundary ✓.
8. Header is accepted; block is fetched and added to VolatileDB.
9. `nodeCheckIntegrity` is called → `verifyBlockIntegrity` → `verifyHeaderIntegrity` → `ABOBBoundaryHdr _ -> True` ✓.
10. Chain selection adopts the attacker's genesis EBB. All subsequent honest blocks whose `prevHash` points to the honest genesis EBB hash are now on a different fork from the node's perspective.

-- | Verify whether a header matches its signature.
--
-- Note that we cannot check this for an EBB, as an EBB contains no signature.
-- This function will always return 'True' for an EBB.
verifyHeaderSignature :: BlockConfig ByronBlock -> Header ByronBlock -> Bool
verifyHeaderSignature cfg hdr =
  case validateView cfg hdr of
    PBftValidateBoundary{} ->
      -- EBB, no signature to check
      True
    PBftValidateRegular fields signed contextDSIGN ->
      let PBftFields{pbftIssuer, pbftSignature} = fields
       in isRight $
            CC.Crypto.verifySignedDSIGN
              contextDSIGN
              pbftIssuer
              signed
              pbftSignature

-- | Verify whether a header is not corrupted.
--
-- The difference with 'verifyHeaderSignature' is that this function also
-- checks the integrity of the 'CC.headerProtocolMagicId' field, which is the
-- only field of a regular header that is not signed.
--
-- Note that we cannot check this for an EBB, as an EBB contains no signature.
-- This function will always return 'True' for an EBB.
verifyHeaderIntegrity :: BlockConfig ByronBlock -> Header ByronBlock -> Bool
verifyHeaderIntegrity cfg hdr =
  verifyHeaderSignature cfg hdr
    &&
    -- @CC.headerProtocolMagicId@ is the only field of a regular header that
    -- is not signed, so check it manually.
    case byronHeaderRaw hdr of
      CC.ABOBBlockHdr h -> CC.headerProtocolMagicId h == protocolMagicId
      -- EBB, we can't check it
      CC.ABOBBoundaryHdr _ -> True
 where
  protocolMagicId = byronProtocolMagicId cfg
