Audit Report

## Title
`deployToken()` Uses `create` Opcode, Enabling Reorg-Based Token Address Hijacking and Unauthorized Minting - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`deployToken()` deploys bridge token proxies via `new ERC1967Proxy(...)` (the `create` opcode), making the resulting address a function of the `OmniBridge` contract's nonce rather than the NEAR token identity. On EVM chains with documented reorg histories (BSC, Polygon — both confirmed deployment targets), an attacker can exploit a reorg to deploy a different token at the same address a legitimate token previously occupied. Because `finTransfer` authorizes minting solely by checking `isBridgeToken[payload.tokenAddress]` against the raw EVM address, a NEAR-signed `finTransfer` payload for Token A will successfully mint Token B tokens if Token B now occupies the same address after the reorg.

## Finding Description
In `OmniBridge.deployToken()` (lines 162–172), the proxy is deployed with:

```solidity
address bridgeTokenProxy = address(
    new ERC1967Proxy(
        tokenImplementationAddress,
        abi.encodeWithSelector(
            BridgeToken.initialize.selector,
            metadata.name,
            metadata.symbol,
            decimals
        )
    )
);
```

`new ERC1967Proxy(...)` compiles to the `create` opcode. The resulting address is `keccak256(rlp(OmniBridge_address, nonce))[12:]` — determined solely by the deployer's nonce, with no binding to `metadata.token`.

After deployment, the registry is updated (lines 190–192):

```solidity
isBridgeToken[address(bridgeTokenProxy)] = true;
ethToNearToken[address(bridgeTokenProxy)] = metadata.token;
nearToEthToken[metadata.token] = address(bridgeTokenProxy);
```

`finTransfer()` (lines 337–342) authorizes minting by checking the raw EVM address:

```solidity
} else if (isBridgeToken[payload.tokenAddress]) {
    IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
```

The `TransferMessagePayload` struct (BridgeTypes.sol line 9) encodes `tokenAddress` as a raw `address`, not as a NEAR token ID string. NEAR's MPC signs over this EVM address. After a reorg, if a different token occupies the same address, the original NEAR-signed payload remains cryptographically valid — the signed address is still `X`, `isBridgeToken[X]` is still true, and the nonce check at line 283 passes because `completedTransfers` was also reverted by the reorg.

The `evm/SECURITY.md` explicitly notes that `deployToken` is permissionless and that metadata signatures are chain-agnostic, meaning any party can obtain a valid NEAR-signed metadata payload for a token they control without any privileged access.

The existing guard at lines 155–158 (`require(!isBridgeToken[nearToEthToken[metadata.token]], "ERR_TOKEN_EXIST")`) only prevents re-deploying the same NEAR token ID — it does not prevent a different token from occupying the same EVM address after a reorg.

## Impact Explanation
This enables **unauthorized minting**: recipients of a legitimate `finTransfer` for Token A receive Token B tokens instead, because the NEAR-signed payload's `tokenAddress` field now points to Token B's proxy. Additionally, Token A's bridge path (`nearToEthToken["token-a"]`) is permanently absent after the reorg, **permanently freezing** all future Token A transfers through the bridge. Both outcomes — unauthorized minting and permanent freezing of bridged funds — match the Critical allowed impact scope.

## Likelihood Explanation
BSC and Polygon (both confirmed deployment targets per `.openzeppelin/bsc-testnet.json` and `.openzeppelin/polygon.json`) have documented reorg histories without requiring a 51% attack — natural reorgs from network latency suffice. The attacker requires only: (a) a legitimately obtained NEAR-signed metadata payload for any token they control (obtainable permissionlessly, as documented in `evm/SECURITY.md`), and (b) the ability to submit a `deployToken` call before the original transaction is re-mined after a reorg. No privileged access is required. The `completedTransfers` nonce map is also reverted by the reorg, so the `finTransfer` replay check does not protect against this scenario.

## Recommendation
Replace `new ERC1967Proxy(...)` with a `create2` deployment using a salt derived from the NEAR token ID, binding the proxy address to the token identity rather than the deployer nonce:

```solidity
bytes32 salt = keccak256(abi.encodePacked(metadata.token));
address bridgeTokenProxy = address(
    new ERC1967Proxy{salt: salt}(
        tokenImplementationAddress,
        abi.encodeWithSelector(
            BridgeToken.initialize.selector,
            metadata.name,
            metadata.symbol,
            decimals
        )
    )
);
```

With `create2`, the proxy address is a deterministic function of `metadata.token`. A reorg cannot place a different token at the same address, because the address is bound to the NEAR token ID rather than the deployer nonce.

## Proof of Concept
1. On a BSC or Polygon fork, deploy `OmniBridge` at address `B`; its nonce is `N`.
2. Legitimate relayer calls `deployToken(sigA, metadataA)` → Token A proxy deployed at address `X = create(B, N)`; bridge records `nearToEthToken["token-a"] = X`, `isBridgeToken[X] = true`.
3. NEAR's MPC observes the `DeployToken` event and signs a `finTransfer` payload for Token A at address `X` with destination nonce `D`. Relayer broadcasts this `finTransfer`.
4. Simulate a 1-block reorg removing both transactions. `OmniBridge` nonce reverts to `N`; `completedTransfers[D]` is cleared; `isBridgeToken[X]` is false.
5. Attacker calls `deployToken(sigB, metadataB)` (valid NEAR signature for attacker-controlled Token B) → Token B proxy deployed at `X` (same nonce `N`); bridge records `nearToEthToken["token-b"] = X`, `isBridgeToken[X] = true`.
6. Relayer re-broadcasts the original `finTransfer` for Token A at address `X` with nonce `D`.
7. `ECDSA.recover` succeeds (signed address is still `X`). `completedTransfers[D]` is false. `isBridgeToken[X]` is true. `IBridgeToken(X).mint(recipient, amount)` executes — minting Token B tokens to the recipient.
8. `nearToEthToken["token-a"]` is permanently absent; all future Token A transfers are bricked.
