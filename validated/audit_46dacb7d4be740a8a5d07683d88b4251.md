Audit Report

## Title
Unconstrained `fee_recipient` in `sign_transfer` Allows Any Trusted Relayer to Steal Transfer Fees — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`sign_transfer` accepts a caller-supplied `fee_recipient: Option<AccountId>` that is embedded verbatim into the MPC-signed `TransferMessagePayload` with no validation against any stored transfer state. Because `TransferMessage` never records a `fee_recipient` at initiation time, and because the transfer message is not removed from `pending_transfers` after signing for non-zero-fee transfers, any trusted relayer can call `sign_transfer` for any pending transfer with an arbitrary `fee_recipient`, obtain a cryptographically valid MPC signature, and submit it to the destination chain first — permanently consuming the destination nonce and stealing the fee from the legitimate relayer.

## Finding Description

`sign_transfer` is gated by `#[trusted_relayer]` and accepts `fee_recipient: Option<AccountId>` as a free parameter:

```rust
// near/omni-bridge/src/lib.rs L447-500
pub fn sign_transfer(
    &mut self,
    transfer_id: TransferId,
    fee_recipient: Option<AccountId>,   // ← no validation
    fee: &Option<Fee>,
) -> Promise {
    let transfer_message = self.get_transfer_message(transfer_id);
    // fee amount is validated, but fee_recipient is not
    ...
    let transfer_payload = TransferMessagePayload {
        ...
        fee_recipient,   // ← caller-supplied value placed directly here
        ...
    };
``` [1](#0-0) 

The `TransferMessage` struct stored in `pending_transfers` has no `fee_recipient` field, so there is no stored value to validate against: [2](#0-1) 

The payload (including the attacker-controlled `fee_recipient`) is hashed and sent to the MPC signer, producing a valid signature: [3](#0-2) 

`sign_transfer_callback` only removes the transfer message when the fee is zero. For any non-zero-fee transfer, the message remains in `pending_transfers`, allowing multiple trusted relayers to each call `sign_transfer` with different `fee_recipient` values and each receive a distinct but valid MPC signature: [4](#0-3) 

On the EVM side, `finTransfer` marks `completedTransfers[payload.destinationNonce] = true` on the first call and reverts with `NonceAlreadyUsed` on any subsequent call. The `feeRecipient` is part of the Borsh-encoded data verified against the MPC signature: [5](#0-4) 

Becoming a trusted relayer is permissionless: any account can call `apply_for_trusted_relayer` with the required stake deposit and, after the waiting period, is automatically promoted. The stake is fully returned on `resign_trusted_relayer`, so the attacker's net cost is only gas: [6](#0-5) 

## Impact Explanation

This is a concrete instance of **fee mis-accounting that changes relayer and attacker balances**. The attacker redirects the fee from the legitimate relayer to themselves on every targeted transfer. The user's principal transfer completes correctly (they receive `amount − fee` on the destination chain), but the legitimate relayer's subsequently obtained MPC signature is permanently invalidated because the destination nonce is already consumed. The attacker gains the full fee; the legitimate relayer loses it entirely. This matches the allowed Critical impact: "fee mis-accounting… that changes user or protocol balances."

## Likelihood Explanation

The barrier to entry is economic: the attacker must stake the configured NEAR amount (default 1,000 NEAR) and wait the configured period (default 7 days). However, since the stake is returned on voluntary resignation, the attacker's only real cost is gas. Any active bridge with non-trivial fee settings makes this profitable at scale. No privileged access, leaked keys, or external dependency failure is required — only a public `apply_for_trusted_relayer` call followed by `sign_transfer` calls targeting pending transfers.

## Recommendation

Store `fee_recipient` inside `TransferMessage` at initiation time (in `init_transfer`) so it is fixed and cannot be overridden by the signing relayer. Alternatively, in `sign_transfer`, validate the caller-supplied `fee_recipient` against a stored or derived value (e.g., require it equals `env::predecessor_account_id()`, or restrict it to a pre-registered relayer for that transfer). A complementary mitigation is to remove the transfer message from `pending_transfers` after the first successful signing regardless of fee amount, preventing multiple relayers from obtaining competing valid signatures for the same transfer.

## Proof of Concept

1. User calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer`, creating a pending transfer with `fee = 100 tokens`. `TransferMessage` is stored in `pending_transfers` with no `fee_recipient` field.
2. Attacker stakes 1,000 NEAR via `apply_for_trusted_relayer`, waits the waiting period, becomes a trusted relayer.
3. Attacker calls `sign_transfer(transfer_id, fee_recipient = Some("attacker.near"), fee = None)`. No validation rejects this — the fee amount check passes (fee matches stored value), and `fee_recipient` is unconstrained.
4. MPC network produces a valid signature over `TransferMessagePayload { ..., fee_recipient: Some("attacker.near"), ... }`.
5. Attacker submits this signature to EVM `finTransfer`. `completedTransfers[destinationNonce]` is set to `true`; fee is paid to `attacker.near`.
6. Legitimate relayer later calls `sign_transfer` and obtains their own valid MPC signature (transfer message was not removed because fee is non-zero). They submit to EVM, which reverts with `NonceAlreadyUsed` — their fee is permanently lost.
7. Attacker calls `resign_trusted_relayer`, recovering their 1,000 NEAR stake. Net cost: gas only.

    pub fn sign_transfer(
        &mut self,
        transfer_id: TransferId,
        fee_recipient: Option<AccountId>,
        fee: &Option<Fee>,
    ) -> Promise {
        let transfer_message = self.get_transfer_message(transfer_id);

        if let Some(fee) = &fee {
            require!(
                &transfer_message.fee == fee,
                BridgeError::InvalidFee.as_ref()
            );
        }

        let token_address = self
            .get_token_address(
                transfer_message.get_destination_chain(),
                self.get_token_id(&transfer_message.token),
            )
            .unwrap_or_else(|| {
                env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
            });

        let decimals = self
            .token_decimals
            .get(&token_address)
            .near_expect(BridgeError::TokenDecimalsNotFound);
        let amount_to_transfer = Self::normalize_amount(
            transfer_message
                .amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );

        require!(
            amount_to_transfer > 0,
            BridgeError::InvalidAmountToTransfer.as_ref()
        );

        let message = DestinationChainMsg::from_json(&transfer_message.msg)
            .and_then(|s| s.destination_msg())
            .unwrap_or_default();

        let transfer_payload = TransferMessagePayload {
            prefix: PayloadType::TransferMessage,
            destination_nonce: transfer_message.destination_nonce,
            transfer_id,
            token_address,
            amount: U128(amount_to_transfer),
            recipient: transfer_message.recipient,
            fee_recipient,
            message,
        };
