### Title
Unvalidated `refund_address` in `request_refund` Allows Attacker to Redirect Victim's BTC Refund — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user's `DepositMsg` has `refund_address: None`, any unprivileged NEAR account can call `request_refund` and supply an arbitrary attacker-controlled BTC address as the `refund_address`. Because the contract performs no ownership or identity check on this parameter, the attacker can front-run the legitimate depositor's own refund request, locking the victim out of submitting their own, and — if the DAO/Operator fails to reject within the 14-day `unsafe_refund_timelock_sec` — redirect the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, payable function callable by any NEAR account: [1](#0-0) 

Inside `internal_request_refund`, the only check on `refund_address` when `deposit_msg.refund_address` is `None` is that it is a syntactically valid BTC address for the configured chain (done later in `build_refund_output`). There is no check that the caller owns the deposit, that the address belongs to the depositor, or that the caller is the original `recipient_id`: [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the branch is skipped entirely and the attacker-supplied `refund_address` is stored verbatim: [3](#0-2) 

The stored `refund_address` is later used directly to construct the BTC output that pays the refund: [4](#0-3) 

Additionally, the callback enforces that only one refund request can exist per UTXO: [5](#0-4) 

This means a front-running attacker who submits first blocks the legitimate depositor from ever submitting their own request.

The `deposit_msg` is publicly observable: it is emitted in the `LogDepositAddress` event when the user calls `get_user_deposit_address`: [6](#0-5) 

The only mitigation in the design is the `unsafe_refund_timelock_sec` (default 14 days), which gives the DAO/Operator time to reject suspicious requests: [7](#0-6) [8](#0-7) 

---

### Impact Explanation

An attacker who front-runs the victim's `request_refund` call with an attacker-controlled `refund_address`:

1. **Blocks the victim** from submitting their own refund request (one request per UTXO enforced on-chain).
2. **Redirects the BTC refund** to the attacker's address if the DAO/Operator does not reject the request within 14 days.
3. **Forces DAO/Operator intervention** as the only recovery path for the victim — the victim cannot self-serve their refund.

If the DAO/Operator is not actively monitoring, or cannot determine which `refund_address` is legitimate (the `deposit_msg` contains only the NEAR `recipient_id`, not the depositor's BTC address), the victim's BTC is permanently lost to the attacker.

This matches: **Medium — attacker-triggered temporary locking of bridged funds**, escalating to **Critical — theft of user funds** if the DAO/Operator fails to act.

---

### Likelihood Explanation

- The `deposit_msg` is publicly observable from NEAR events (`LogDepositAddress`), giving the attacker all inputs needed to construct the call.
- Any NEAR account can call `request_refund` with no special role.
- Front-running is straightforward on NEAR (monitor mempool/events, submit before victim).
- Deposits with `refund_address: None` in `DepositMsg` are the common case (the field is `Option` and `skip_serializing_if = "Option::is_none"`).
- The 14-day window is long but finite; an inattentive or under-resourced DAO/Operator may miss the window.

---

### Recommendation

Validate that the caller of `request_refund` is the original depositor (i.e., `env::predecessor_account_id()` matches `deposit_msg.recipient_id`), or require that `deposit_msg.refund_address` is always pre-set (non-`None`) so the refund destination is committed to at deposit time and cannot be overridden by a third party. Alternatively, restrict permissionless `request_refund` calls to only the `recipient_id` account, while still allowing DAO/Operator to submit on behalf of users.

---

### Proof of Concept

1. Victim calls `get_user_deposit_address(DepositMsg { recipient_id: "victim.near", refund_address: None, ... })`. The `deposit_msg` is emitted in a `LogDepositAddress` event.
2. Victim sends BTC to the derived deposit address. The deposit is never finalized (e.g., the relayer is slow or the deposit is below minimum).
3. Attacker observes the `LogDepositAddress` event, extracts `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = <victim's deposit_msg>,
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's deposit tx>,
     vout = <victim's vout>,
     proof = <valid inclusion proof>,
     gas_fee = None
   )
   ```
   with sufficient attached NEAR for storage.
4. The Light Client verifies the transaction. `request_refund_callback` stores the request with `refund_address = "attacker_btc_address"`.
5. Victim attempts `request_refund` with their own address — it panics: `"Refund request already exists for this UTXO"`.
6. After 14 days, attacker (or anyone) calls `execute_refund(utxo_storage_key)`. The BTC is sent to the attacker's address via the MPC signing pipeline.

    pub fn request_refund(

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,

        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
