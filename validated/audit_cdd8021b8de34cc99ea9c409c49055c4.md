### Title
Peras Certificate Validation Unconditionally Accepts Any Inbound Certificate — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. This is the validation function wired directly into the live inbound-certificate processing pipeline. Any unprivileged peer can send a fabricated Peras certificate claiming to boost an arbitrary block, and the node will accept it, store it, and trigger chain selection for the boosted block — potentially causing the node to prefer a non-canonical or adversarially-controlled chain.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must be passed before a received certificate is stored and acted upon. The universal instance (covering all block types, including the production Cardano block) implements this gate as a no-op stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no quorum is checked, no round-number bounds are enforced, and no boosted-block plausibility is tested. The stub is not isolated to a test path — it is the function called by the live inbound pipeline.

`makePerasCertPoolWriterFromChainDB` wires this stub directly into the object-diffusion layer that processes certificates arriving from peers:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

`processCerts` then uses the result of that call to decide whether to accept or reject the batch. Because the stub always returns `Right`, every certificate passes.

Once accepted, the certificate is forwarded to `chainSelSync` via `ChainDB.addPerasCertAsync`. Inside `chainSelSync`, the certificate's `boostedBlock` field is used to trigger `chainSelectionForBlock` for the named block, granting it the full Peras weight boost (`vpcCertBoost = perasWeight params`). This directly influences which chain the node selects as its current tip.

The same stub also governs `validatePerasVote`: it only checks that the claimed voter ID appears in the stake distribution map, but never verifies the vote signature. An adversary who knows any registered pool ID can fabricate votes attributed to that pool.

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` message with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The node will:

1. Accept the certificate without any cryptographic check.
2. Store it in `PerasCertDB`, granting it the full Peras weight boost.
3. Trigger `chainSelectionForBlock` for the adversarially-chosen block.
4. Potentially switch its current chain to one that includes the boosted block, even if that chain is non-canonical or adversarially constructed.

This is a **bypass of Peras certificate validation** that enables unauthorized certificate acceptance and can cause an honest node to prefer a non-canonical chain — matching the "Critical: Bypass of certificate/signature validation" impact class.

---

### Likelihood Explanation

The entry path requires only a network connection to the target node. The object-diffusion miniprotocol for Peras certificates is reachable by any peer the node is connected to. No key material, stake, or privileged access is needed. The attacker only needs to craft a well-formed CBOR-encoded `PerasCert` message with a desired `pcCertRound` and `pcCertBoostedBlock`. The stub is unconditional, so the attack succeeds on every attempt.

---

### Recommendation

- **Short term:** Gate `validatePerasCert` (and `validatePerasVote`) behind a real implementation before the Peras diffusion layer is enabled in any network-reachable configuration. At minimum, add a hard `error` or `Left` fallback in the stub so that the absence of real validation causes an explicit failure rather than silent acceptance.
- **Long term:** Implement full cryptographic certificate validation — aggregate BLS signature verification, quorum-stake threshold check, round-number range enforcement, and boosted-block plausibility — as specified by the `BlockSupportsPeras` type class contract and the Peras design. Add negative tests covering fabricated certificates (wrong signature, insufficient quorum, out-of-range round) to prevent regression.
