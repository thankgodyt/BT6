### Title
`safe_mint` Returns Hardcoded `U128(0)` on Unregistered Recipient, Permanently Locking Minted nBTC in Bridge — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function unconditionally mints `amount` nBTC tokens into the bridge's own account, then returns the hardcoded static value `U128(0)` when the intended recipient account is not registered for nBTC storage. This is the direct analog of the reported vulnerability: a static value is returned instead of the correct computed amount, causing the bridge's callback to receive `0` while `amount` tokens are silently stranded in the bridge's balance with no automatic recovery path.

---

### Finding Description

`safe_mint` (lines 101–124 of `contracts/nbtc/src/lib.rs`) executes in two distinct steps:

**Step 1 — Unconditional mint to bridge:**
```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
```
This always succeeds because `bridge_id` is registered at construction time.

**Step 2 — Early return with hardcoded zero:**
```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
```

When the recipient (`account_id`) has no nBTC storage registration, the function returns `U128(0)` — a hardcoded static value — without transferring the already-minted tokens. The `amount` tokens remain in the bridge's nBTC balance. The bridge's callback receives `U128(0)`, which it may interpret as "nothing was transferred," and no entry is added to the `lost_found` map (that map is only populated in `transfer_nbtc_callback`, a separate code path in `contracts/satoshi-bridge/src/token_transfer.rs` lines 54–75). There is no automatic mechanism to credit the user or flag the stuck amount.

The `mint` function (lines 126–148) does not have this flaw — it calls `mint_inner` which auto-registers the account. `safe_mint` is the only public bridge-callable mint path that silently discards the minted amount.

---

### Impact Explanation

A user whose NEAR account is not registered for nBTC storage triggers this path. Their BTC deposit UTXO is consumed and verified on-chain, but the corresponding nBTC is permanently stranded in the bridge's own token balance. The user receives no nBTC and has no on-chain mechanism to reclaim it. The bridge's total nBTC supply increases (tokens are minted) while the user's balance stays at zero — a supply/accounting divergence. Recovery requires privileged operator intervention to manually identify and redistribute the stuck tokens.

This matches the allowed impact: **Medium — broken callback rollback / stuck bridge state requiring operator intervention**, and potentially **Critical — significant loss of user funds** if the operator does not intervene.

---

### Likelihood Explanation

Any user who initiates a BTC deposit without first registering their NEAR account for nBTC storage (via `storage_deposit`) triggers this silently. New users unfamiliar with NEP-141 storage registration are the natural victim class. The entry path is fully unprivileged: any BTC holder can deposit and trigger the flaw without any special access.

---

### Recommendation

Replace the early-return-with-zero with one of:

1. **Auto-register the account** before minting (matching the behavior of `mint_inner`):
   ```rust
   if self.token.accounts.get(&account_id).is_none() {
       self.token.internal_register_account(&account_id);
   }
   ```

2. **Add to `lost_found`** so the bridge can recover the amount for the user later, and return `amount` (not `U128(0)`) so the bridge's callback correctly accounts for the minted tokens.

3. **Revert the entire operation** if the account is not registered, so no tokens are minted and the bridge can handle the failure cleanly.

---

### Proof of Concept

1. User sends BTC to their bridge deposit address.
2. Relayer submits inclusion proof; bridge verifies and calls `safe_mint(user_account_id, amount, None)` on the nBTC contract.
3. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `amount` nBTC tokens are now in the bridge's balance.
4. `self.token.accounts.get(&user_account_id)` returns `None` (user never called `storage_deposit`).
5. `safe_mint` returns `PromiseOrValue::Value(U128(0))`.
6. The bridge's callback receives `U128(0)` — it believes zero tokens were transferred.
7. No `lost_found` entry is created for the user.
8. `amount` nBTC tokens are permanently stranded in the bridge's balance; the user's BTC is spent with no nBTC received. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
