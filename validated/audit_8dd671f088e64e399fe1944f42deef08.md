## Title
Token-2022 Transfer Fee Causes Vault Under-Crediting vs. Cross-Chain Message Amount — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

`InitTransfer::process` calls `transfer_checked` with `payload.amount` and serialises that same value into the Wormhole message. For Token-2022 mints with a `TransferFeeConfig` extension, the SPL runtime withholds a fee from the vault recipient, so the vault receives strictly less than `payload.amount`. NEAR is told the full amount was locked and mints or releases that many wrapped tokens, causing the vault balance and NEAR-side supply to permanently diverge. The last users to bridge back cannot be made whole.

## Finding Description

**No extension guard in `log_metadata`.**
`LogMetadata::process` unpacks the mint's extensions only to resolve `MetadataPointer` for name/symbol; it never inspects `TransferFeeConfig`. The vault PDA is created unconditionally via `init_if_needed` for any Token-2022 mint whose `mint_authority` is not the bridge authority. [1](#0-0) [2](#0-1) 

**`transfer_checked` amount vs. received amount.**
`InitTransfer::process` calls `transfer_checked` with the caller-supplied `payload.amount`. Under Token-2022 transfer fees, the vault (recipient) receives `payload.amount − fee`; the withheld fee sits in the vault's token account as non-spendable withheld tokens, recoverable only by the fee-harvest authority — not by the bridge. [3](#0-2) 

**Wormhole message carries the unreduced amount.**
Immediately after the transfer, `payload.serialize_for_near` is called with the original `payload` struct, encoding `self.amount` verbatim — there is no post-transfer balance snapshot or delta calculation. [4](#0-3) [5](#0-4) 

**No existing guard is sufficient.** The only validation in `process` is `payload.amount > payload.fee` (line 73), which is unrelated to mint-level transfer fees. Neither `init_transfer` nor `log_metadata` calls `get_extension::<TransferFeeConfig>()` at any point. [6](#0-5) 

## Impact Explanation

This is a concrete instance of **escrow mis-accounting / fee mis-accounting** — an explicitly listed Critical impact class. For every `init_transfer` on a fee-bearing mint:

- Vault spendable balance increases by `amount × (1 − fee_rate)`
- NEAR-side wrapped supply increases by `amount`

The discrepancy accumulates linearly. When users bridge back, `finalize_transfer` attempts to release the full NEAR-reported amount from the vault. Once cumulative withheld fees exceed the vault's spendable balance, redemptions fail and locked funds are permanently unrecoverable by the affected users. An attacker who controls the fee-bearing mint can set `fee_rate` to maximise the drain, effectively stealing other depositors' locked collateral.

## Likelihood Explanation

- Token-2022 `TransferFeeConfig` is a standard, widely-deployed extension; legitimate tokens carry it.
- `log_metadata` imposes no extension whitelist, so any such mint can be registered permissionlessly.
- The exploit requires only two public on-chain calls (`log_metadata`, then `init_transfer`) — no admin access, key compromise, oracle manipulation, or Wormhole guardian interaction is needed beyond normal VAA relaying.
- The discrepancy is deterministic and non-zero for any `fee_rate > 0`.

## Recommendation

1. **Reject fee-bearing mints at registration.** In `log_metadata.rs`, after unpacking extensions, return an error if `TransferFeeConfig` is present:
   ```rust
   use spl_token_2022::extension::transfer_fee::TransferFeeConfig;
   require!(
       mint_with_extension.get_extension::<TransferFeeConfig>().is_err(),
       ErrorCode::UnsupportedMintExtension
   );
   ```

2. **Alternatively, measure the vault delta.** Record the vault's spendable balance before and after `transfer_checked` and use the delta — not `payload.amount` — as the value serialised into the Wormhole message.

3. **Apply the same guard in `init_transfer`** as defence-in-depth, since a mint's fee config can be added after registration if the fee authority is not frozen.

## Title
Token-2022 TransferFeeConfig Causes Vault Under-Crediting vs. Cross-Chain Message Amount — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary

`InitTransfer::process` calls `transfer_checked` with `payload.amount` and then posts a Wormhole message containing that same `payload.amount`. For Token-2022 mints with a `TransferFeeConfig` extension, the SPL runtime withholds a fee from the vault (recipient), so the vault receives strictly less than `payload.amount`. NEAR is told the full `payload.amount` was locked and mints or releases that many wrapped tokens. The vault balance and NEAR-side accounting permanently diverge, causing the last users to bridge back to be unable to redeem their funds.

## Finding Description

**Vault creation — no transfer-fee guard**

`LogMetadata::process` unpacks the mint's extensions to check for `MetadataPointer`, but performs no inspection for `TransferFeeConfig`. The vault PDA is created unconditionally via `init_if_needed` for any Token-2022 mint whose `mint_authority` is not the bridge authority. [1](#0-0) [2](#0-1) 

**Transfer — amount posted equals amount requested, not amount received**

`InitTransfer::process` calls `transfer_checked` with the caller-supplied `payload.amount`, then immediately serialises that same value into the Wormhole message. There is no pre/post balance snapshot of the vault. [3](#0-2) [4](#0-3) 

With Token-2022 `TransferFeeConfig`, `transfer_checked(amount=N)` debits the sender `N` tokens but credits the vault only `N − fee`. The withheld fee is stored inside the vault's token account as a non-spendable "withheld" balance, recoverable only by the fee-harvest authority — not by the bridge.

**Payload serialisation — no post-transfer balance check**

`InitTransferPayload::serialize_for_near` encodes `self.amount` verbatim with no mechanism to substitute the actually-received amount. [7](#0-6) 

## Impact Explanation

For every `init_transfer` on a fee-bearing Token-2022 mint:
- Vault spendable balance increases by `amount × (1 − fee_rate)`
- NEAR-side wrapped supply increases by `amount`

The ratio diverges with each transfer. When users later bridge back, `finalize_transfer` attempts to release the full NEAR-reported amount from the vault. The vault runs short by the cumulative withheld fees, causing the last redeemers to receive nothing. An attacker who controls the fee-bearing mint can set the fee rate to maximise the discrepancy and drain other users' locked funds.

This is a concrete instance of **escrow mis-accounting / fee mis-accounting that changes user and protocol balances**, and **loss of bridged funds**, both of which are listed critical impacts.

## Likelihood Explanation

- Token-2022 `TransferFeeConfig` is a standard, widely-used extension; legitimate tokens carry it.
- `log_metadata` imposes no extension whitelist, so any such token can be registered permissionlessly.
- The attacker path requires only two permissionless on-chain calls (`log_metadata`, then `init_transfer`); no admin access, key compromise, or oracle manipulation is needed.
- The discrepancy is deterministic and grows linearly with transfer volume.
- A malicious actor can deploy a Token-2022 mint with a high fee rate (up to 100%) and maximise the drain.

## Recommendation

1. **Reject fee-bearing mints at registration.** In `log_metadata.rs`, after unpacking the mint's extensions, return an error if `TransferFeeConfig` is present:

   ```rust
   use spl_token_2022::extension::transfer_fee::TransferFeeConfig;

   // in LogMetadata::process, inside the token_2022::ID branch
   require!(
       mint_with_extension.get_extension::<TransferFeeConfig>().is_err(),
       ErrorCode::UnsupportedMintExtension
   );
   ```

2. **Alternatively, measure the vault delta.** Record the vault's spendable balance before and after `transfer_checked` and use the delta — not `payload.amount` — as the value posted in the Wormhole message.

3. **Apply the same guard to `init_transfer`** as defence-in-depth, since a mint's fee config can be added after registration if the fee authority is not frozen.

## Proof of Concept

```
1. Create a Token-2022 mint with TransferFeeConfig: fee_rate=1000 bps (10%), max_fee=u64::MAX.
2. Call log_metadata with this mint → vault PDA is created, no error.
3. Mint 1000 tokens to attacker's ATA.
4. Call init_transfer(amount=1000, recipient="attacker.near", fee=0, native_fee=0).
   - transfer_checked moves 1000 from ATA to vault.
   - Token-2022 runtime withholds 100 in vault; vault spendable balance = 900.
   - Wormhole message payload.amount = 1000.
5. NEAR finalises the VAA and mints 1000 wrapped tokens to attacker.near.
6. Attacker bridges back 1000 wrapped tokens from NEAR.
   - NEAR burns 1000 wrapped tokens, posts finalize message with amount=1000.
   - Solana finalize_transfer tries to release 1000 from vault.
   - Vault only has 900 spendable → transaction fails or a different user's deposit is consumed.

Invariant: vault.spendable_amount after step 4 < payload.amount in the Wormhole message.
Fuzz: vary fee_rate from 1 to 10000 bps; invariant breaks for any non-zero value.
```
