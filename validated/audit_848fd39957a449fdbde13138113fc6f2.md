### Title
Missing `refund_address` Chain Validation Causes Permanently Unexecutable `RefundRequest` — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/network.rs`)

---

### Summary

`request_refund` / `request_refund_callback` stores a `RefundRequest` with an attacker-supplied `refund_address` string that is **never validated** against the bridge's configured chain. When `execute_refund` later calls `build_refund_output`, `Address::parse` returns `Err` for a cross-chain address and `.expect()` panics, leaving the request permanently unexecutable until a DAO/Operator manually rejects it.

---

### Finding Description

**Entry point — public, unprivileged:**

`request_refund` in `api/bridge.rs` is `#[payable]` with no role restriction (only `gas_fee` requires DAO/Operator). [1](#0-0) 

It calls `internal_request_refund`, which performs light-client proof verification and then fires `request_refund_callback`. Neither function validates that `refund_address` is parseable for the bridge's configured chain: [2](#0-1) 

**Storage — no address validation:**

`request_refund_callback` stores the raw `refund_address` string verbatim into `RefundRequest` after only checking it matches `deposit_msg.refund_address` (if set). No chain-format check is performed: [3](#0-2) 

**Execution — guaranteed panic:**

`internal_execute_refund` calls `build_refund_output`, which calls `Address::parse(...).expect("Invalid refund address")`. For a Litecoin address (prefix `0x30`) on a Bitcoin bridge (expects `0x00`/`0x05`/`bc` bech32), `Address::parse` returns `Err` and `.expect()` panics: [4](#0-3) [5](#0-4) 

**Duplicate guard blocks re-submission:**

Once the bad request is stored, the duplicate check in `request_refund_callback` prevents any new request for the same UTXO: [6](#0-5) 

---

### Impact Explanation

- **`execute_refund` always panics** for the stored request — the invariant that every stored `RefundRequest` is executable is broken.
- The refund is stuck in `refund_requests` indefinitely. Note: the question's claim that the UTXO is locked in `verified_deposit_utxo` is **incorrect** — `verified_deposit_utxo` is only written in `finalize_refund_with_psbt`, which is never reached. The UTXO is not in that set.
- Recovery requires a DAO/Operator to call `reject_refund`. After rejection, a new request with a valid address can be submitted (only if `deposit_msg.refund_address` is `None`).
- If `deposit_msg.refund_address` is `Some` with a cross-chain address, the refund is **permanently unrecoverable**: any new request must supply the same bad address (enforced at line 154–158), so `execute_refund` will always panic. [7](#0-6) 

---

### Likelihood Explanation

- The `None`-address griefing path (third party front-runs with a bad address) requires the attacker to pay the storage deposit and is mitigated by DAO rejection — low operational risk.
- The `Some`-address permanent-stuck path is self-inflicted (depositor embeds a cross-chain address), but is a realistic user mistake given the bridge supports multiple chains (Bitcoin, Litecoin, Dogecoin, Zcash) with visually similar address formats.
- No privileged access is required to trigger either path.

---

### Recommendation

Validate `refund_address` against `config.chain` at storage time in `request_refund_callback`, before inserting into `refund_requests`:

```rust
// In request_refund_callback, before building RefundRequest:
crate::network::Address::parse(&refund_address, config.chain.clone())
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address for chain: {e}")));
```

This eagerly rejects cross-chain addresses at request time, preserving the invariant that every stored `RefundRequest` is always executable.

---

### Proof of Concept

1. Deploy the bridge configured for `Chain::BitcoinMainnet`.
2. Send a real BTC deposit with `deposit_msg.refund_address = Some("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd")` (valid Litecoin mainnet P2PKH address, prefix `0x30`).
3. Call `request_refund` — `request_refund_callback` stores the `RefundRequest` with the Litecoin address. No panic yet.
4. Wait for the timelock. Call `execute_refund`.
5. `build_refund_output` calls `Address::parse("LWrHnw5xztWiPafMhKYTQued8iuhaET7Yd", Chain::BitcoinMainnet)`:
   - Segwit: no `bc` HRP match.
   - Base58 prefix `0x30` ≠ `0x00` (P2PKH) and ≠ `0x05` (P2SH).
   - Returns `Err("Unknown address format or unsupported chain")`.
6. `.expect("Invalid refund address")` panics. The request remains in `refund_requests` forever.
7. Assert: `execute_refund` panics on every subsequent call; no new `request_refund` can be submitted for the same UTXO.
