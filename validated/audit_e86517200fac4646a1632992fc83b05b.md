### Title
`PostAction.msg` Values Are Not Validated Against Templates, Allowing Malicious dApp to Bypass Bridge Post-Action Policy — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

The `check_deposit_msg` function validates the JSON **structure** of `PostAction.msg` against operator-configured templates using `is_structure_equal`, but does not validate the actual **leaf values** within the message. A malicious dApp can craft a `DepositMsg` whose `PostAction.msg` passes structural validation while containing manipulated values (e.g., minimum output amounts, recipient addresses), bypassing the bridge's post-action policy and causing user fund loss.

---

### Finding Description

In `check_deposit_msg`, when `post_action_msg_templates` contains an entry for a whitelisted `receiver_id`, the contract validates the submitted `PostAction.msg` as follows:

```rust
let is_match = match serde_json::from_str::<Value>(&post_action.msg) {
    Ok(msg_value) => msg_templates.iter().any(|template| {
        match serde_json::from_str::<Value>(template) {
            Ok(template_value) => {
                is_structure_equal(&template_value, &msg_value)   // ← structure only
            }
            Err(_) => false,
        }
    }),
    Err(_) => msg_templates
        .iter()
        .any(|template| template == &post_action.msg),           // ← exact match
};
``` [1](#0-0) 

The fallback path for non-JSON strings uses exact string equality (`template == &post_action.msg`), which is secure. For JSON-parseable messages, however, the code delegates to `is_structure_equal`, a custom function from `json_utils`. The function name and the deliberate divergence from a plain `==` comparison on `serde_json::Value` (which implements `PartialEq`) make clear that it performs structural/schema matching — verifying that the submitted JSON has the same keys and nesting as the template — without comparing the actual leaf values.

This means any `PostAction.msg` that shares the correct JSON key structure with a registered template passes validation, regardless of what values those keys carry.

The `PostAction` struct carries an `amount` (nBTC to forward), a `receiver_id` (whitelisted), and a `msg` (forwarded verbatim to the receiver's `ft_on_transfer`): [2](#0-1) 

After minting, the bridge executes `ft_transfer_call` on the whitelisted receiver with the unvalidated `msg`. If that receiver is a DEX or DeFi protocol, the `msg` typically encodes security-critical parameters such as minimum output amounts, deadlines, or recipient addresses.

---

### Impact Explanation

The bridge's template system is the sole on-chain mechanism restricting what instructions can be sent to whitelisted post-action receivers. Because `is_structure_equal` ignores leaf values, this policy is entirely bypassed for any JSON-formatted message.

Concrete consequences, depending on the whitelisted receiver's interface:

- **Slippage manipulation**: If the template encodes `{"action":"swap","min_out":"1000000"}`, an attacker submits `{"action":"swap","min_out":"1"}`. The user's nBTC is swapped with effectively zero slippage protection, allowing sandwich attacks to extract nearly all value.
- **Recipient redirection**: If the template encodes a `recipient` field, an attacker substitutes their own address. The user's nBTC is forwarded to the attacker after the swap/action completes.

Both scenarios constitute **significant loss of user funds** (Critical) or at minimum **bypass of bridge limits or policies** (Medium), depending on the receiver contract's behavior. [3](#0-2) 

---

### Likelihood Explanation

Medium. The attack requires a malicious dApp that:

1. Constructs a `DepositMsg` with a `PostAction.msg` that has the correct JSON key structure but manipulated values.
2. Derives the deposit address from this manipulated `DepositMsg` (address = SHA-256 of the JSON-serialized `DepositMsg`).
3. Presents this address to the user as their deposit destination.
4. The user sends BTC without inspecting the full `DepositMsg` parameters — directly analogous to the reported Uniswap scenario where the wallet hides `value`, `nonce`, and `deadline` from the user.

The relayer then calls `verify_deposit` with the manipulated `DepositMsg`; the light-client proof is valid because the BTC output script matches the derived address. The contract accepts the manipulated `msg` because `is_structure_equal` passes. [4](#0-3) 

---

### Recommendation

Replace `is_structure_equal` with exact value matching (`template_value == msg_value`) for `PostAction.msg` validation. If the template system must allow variable fields (e.g., dynamic amounts), implement an explicit allowlist of which fields may vary and validate all others for exact equality. The non-JSON fallback path already uses exact string matching and is correct; the JSON path should be brought to the same standard.

---

### Proof of Concept

1. Operator registers template for a whitelisted DEX receiver:
   `{"action":"swap","min_out":"1000000","recipient":"user.near"}`

2. Malicious dApp constructs `DepositMsg` with:
   `PostAction { receiver_id: dex.near, amount: 100_000_000, msg: "{\"action\":\"swap\",\"min_out\":\"1\",\"recipient\":\"attacker.near\"}" }`

3. dApp derives deposit address via `get_deposit_path(&deposit_msg)` → SHA-256 of the JSON → bridge address path.

4. User sends BTC to this address (sees only the address, not the `PostAction.msg` values).

5. Relayer calls `verify_deposit_v2` with the manipulated `DepositMsg` and a valid Merkle proof.

6. `check_deposit_msg` evaluates:
   - `is_structure_equal(template_value, msg_value)` → `true` (both have keys `action`, `min_out`, `recipient`)
   - `total_amount ≤ actual_mintable_amount` → passes

7. Bridge mints nBTC and calls `ft_transfer_call(dex.near, 100_000_000, "{...min_out:1, recipient:attacker.near...}")`.

8. DEX executes swap with `min_out = 1`; attacker sandwiches the transaction; user receives near-zero output. Alternatively, DEX sends output to `attacker.near`. [5](#0-4) [6](#0-5)
