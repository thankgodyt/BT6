Audit Report

## Title
Permanent Fund Freeze via u128→u64 Overflow in `FinalizeTransfer::process` with No NEAR-Side Guard — (`solana/programs/bridge_token_factory/src/instructions/user/finalize_transfer.rs`)

## Summary

`FinalizeTransferPayload.amount` is typed as `u128`, but Solana SPL token operations require `u64`. When NEAR's `sign_transfer` produces a normalized amount exceeding `u64::MAX`, every Solana finalization attempt returns `AmountOverflow` (error 6010). Solana's transaction atomicity rolls back `use_nonce` on failure, so the nonce is never consumed — but the transfer can never succeed either, permanently locking the user's funds on NEAR with no refund path.

## Finding Description

`FinalizeTransferPayload` carries `amount: u128`: [1](#0-0) 

`FinalizeTransfer::process` calls `use_nonce` first (lines 91–99), then attempts the narrowing cast at lines 114 and 134: [2](#0-1) [3](#0-2) [4](#0-3) 

The same pattern exists in `FinalizeTransferSol::process`: [5](#0-4) 

On the NEAR side, `sign_transfer` normalizes the amount to `u128` and places it directly into the MPC-signed payload with no check that the result fits in `u64`. The only guard is `amount_to_transfer > 0`: [6](#0-5) 

`normalize_amount` is pure floor-division returning `u128`: [7](#0-6) 

There is no `require!(amount_to_transfer <= u64::MAX as u128, ...)` guard anywhere in the signing path. The `sign_transfer_callback` does not trigger any refund on the NEAR side: [8](#0-7) 

## Impact Explanation

If a user initiates a transfer whose normalized Solana-side amount exceeds `u64::MAX`: (1) NEAR locks the funds and MPC signs the payload; (2) every call to `finalize_transfer` or `finalize_transfer_sol` on Solana returns `AmountOverflow`; (3) Solana's transaction atomicity rolls back `use_nonce`, so the nonce is never consumed; (4) the transfer is permanently unfinalizeable; (5) there is no NEAR-side timeout or refund path in the contract. This matches the Critical scope: **permanent freezing of bridged funds**.

## Likelihood Explanation

For a token with 18 origin decimals and 9 Solana decimals, normalization divides by 10⁹. Overflow requires a normalized amount > ~1.84 × 10¹⁹, meaning an original balance > ~1.84 × 10²⁸ base units (~18 billion tokens at 18 decimals). For tokens with equal decimals on both sides (e.g., 9/9), the threshold is ~18.4 billion tokens. This is a very large amount for most tokens, making the likelihood low in practice. However, for high-supply tokens (meme coins, governance tokens with quadrillions of supply), the threshold is reachable. No attacker action is required — a legitimate large transfer by the token holder, processed by a trusted relayer acting normally, suffices.

## Recommendation

Add a guard in `sign_transfer` (NEAR side) before MPC signing:

```rust
require!(
    amount_to_transfer <= u64::MAX as u128,
    BridgeError::AmountExceedsSolanaMax
);
```

Alternatively, add the check in `FinalizeTransfer::process` *before* `use_nonce` so that a bad payload is rejected without consuming any state, and ensure NEAR emits a refund event in that case.

## Proof of Concept

The existing tests already confirm the failure path for both token and SOL transfers: [9](#0-8) [10](#0-9) 

To confirm permanent lock: call `finalize_transfer` with `amount = u64::MAX + 1`, observe `ProgramResult::Failure(ProgramError::Custom(6010))`, then verify the nonce account bit remains unset (rolled back). Repeat the call — it fails identically every time. No NEAR-side refund is triggered.
