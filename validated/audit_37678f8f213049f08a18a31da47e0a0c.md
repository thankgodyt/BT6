### Title
Attacker Can Front-Run `request_refund` to Temporarily Lock Victim's Refund Funds and Redirect Refund Address — (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `request_refund` flow in `satoshi-bridge` is a two-step async process: a verification promise is dispatched first, and the refund request is only stored in the callback. The duplicate-existence guard (`"Refund request already exists for this UTXO"`) lives exclusively in the callback. Because all inputs required to construct a valid competing `request_refund` call (deposit transaction bytes, Merkle proof, `deposit_msg`) are public on-chain data, an attacker can race the victim's in-flight verification with their own call using an attacker-controlled `refund_address`. If the attacker's callback settles first, the victim's callback panics and the victim is locked out of the refund flow until a privileged operator manually rejects the attacker's entry.

### Finding Description

**Root cause — existence guard placed only in the callback, not before the async dispatch.**

`internal_request_refund` dispatches a `verify_transaction_inclusion_promise` and chains `request_refund_callback` to it. Before dispatching, the function performs only three checks: [1](#0-0) 

None of these checks whether a refund request for the derived `utxo_storage_key` already exists or is already in-flight. The `utxo_storage_key` *is* computable at this point — the function already decodes `tx_bytes` to extract `tx_id`: [2](#0-1) 

The only guard against duplicates is deferred to the callback: [3](#0-2) 

**Attacker-controlled entry path:**

When `deposit_msg.refund_address` is `None`, the caller freely supplies any `refund_address`: [4](#0-3) 

The attacker reads the victim's `deposit_msg` (embedded in the BTC transaction's OP_RETURN or equivalent), the raw `tx_bytes`, and the Merkle inclusion proof — all public Bitcoin blockchain data — and submits an identical `request_refund` call substituting their own `refund_address`. Both calls enter the async verification pipeline. Whichever callback settles first wins the slot; the second panics with `"Refund request already exists for this UTXO"`.

**Stored refund address is the attacker's:**

In `request_refund_callback`, the `refund_address` argument (attacker-supplied) is stored verbatim: [5](#0-4) 

**Timelock for attacker-supplied addresses:**

Because `deposit_msg.refund_address` is `None`, `resolve_execute_refund_timelock` applies `config.unsafe_refund_timelock_sec` — the longer timelock intended to give the DAO time to reject suspicious requests: [6](#0-5) 

If the DAO does not call `internal_reject_refund` within that window, the attacker can call `execute_refund` and redirect the victim's BTC to their own address.

### Impact Explanation

**Primary (Medium):** The victim's `request_refund_callback` panics; the victim loses their attached storage deposit and cannot submit a new refund request until a privileged operator manually rejects the attacker's entry via `internal_reject_refund`. This constitutes attacker-triggered temporary locking of bridged funds.

**Secondary (Critical, conditional):** If the DAO/RefundOperator fails to reject the attacker's request within `unsafe_refund_timelock_sec`, the attacker executes the refund and receives the victim's BTC at their own address — direct theft of user funds.

### Likelihood Explanation

- All inputs needed to construct the competing call (`deposit_msg`, `tx_bytes`, Merkle proof) are public on the Bitcoin blockchain.
- The attacker only needs to pay the storage deposit (`required_balance_for_request_refund`) — a small, recoverable cost.
- The NEAR async model guarantees at least one block between the victim's dispatch and their callback, giving the attacker a reliable window.
- The attack is most effective against users who do not pre-authorize a `refund_address` in their `deposit_msg` (i.e., `deposit_msg.refund_address = None`), which is the common case.

### Recommendation

Add an early existence check in `internal_request_refund` before dispatching the verification promise. Since `tx_bytes` is already decoded at that point, the `utxo_storage_key` can be computed and checked immediately:

```rust
// In internal_request_refund, after decoding tx_bytes:
let utxo_storage_key = generate_utxo_storage_key(
    tx_id.clone(),
    u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
);
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit"
);
```

This mirrors the recommended fix in the original report: move the guard to before the async operation so the state is checked and locked atomically, eliminating the race window entirely. Additionally, consider making `deposit_msg.refund_address` mandatory to prevent caller-supplied redirect attacks by design.

### Proof of Concept

1. Victim deposits BTC with a `deposit_msg` where `refund_address: None`.
2. Victim calls `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof, None)`. The bridge dispatches a `verify_transaction_inclusion` promise; the callback is pending.
3. Attacker observes the victim's NEAR transaction (mempool or block). Attacker extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof` from the Bitcoin blockchain.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with `attacker_btc_addr` as the `refund_address`. The bridge dispatches a second verification promise.
5. Both callbacks resolve. Whichever settles first stores its `refund_address`. If the attacker's settles first:
   - Attacker's `RefundRequest` is stored with `refund_address = attacker_btc_addr`.
   - Victim's callback panics: `"Refund request already exists for this UTXO"`. Victim loses their attached deposit.
6. Victim cannot submit a new request. Their BTC is locked until the DAO calls `internal_reject_refund`.
7. If the DAO does not act within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund`, builds a PSBT paying `attacker_btc_addr`, and broadcasts it — stealing the victim's BTC.
