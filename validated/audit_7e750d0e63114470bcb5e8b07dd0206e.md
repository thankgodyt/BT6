### Title
Degenerate `BlockSupportsPeras` Instance Bypasses Peras Certificate and Vote Validation for All Block Types - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` typeclass, which governs Peras certificate and vote validation for chain selection, ships a single global degenerate instance that applies to **all** block types. This instance unconditionally accepts every Peras certificate (`validatePerasCert` always returns `Right`), never extracts certificates from blocks (`getPerasCertInBlock` always returns `Nothing`), and performs no cryptographic checks. Any unprivileged peer can inject a crafted Peras certificate over the `ObjectDiffusion` mini-protocol; the node will accept it without verification and apply its chain-weight boost, enabling chain-selection manipulation.

---

---

### Impact Explanation

**Chain-selection manipulation via fake Peras certificates (High).**

Peras certificates carry a `PerasWeight` boost that is added to the chain weight of the block they certify. Because `validatePerasCert` unconditionally returns `Right` with the full `perasWeight params` boost, an attacker who sends a crafted `PerasCert` pointing to any block — including a non-canonical or adversarial fork — will have that certificate accepted and its boost applied to chain selection. This lets an unprivileged peer cause an honest node to prefer a non-canonical chain, violating chain-selection safety.

**Cooldown-period bypass via missing on-chain certificate extraction (High).**

`getPerasCertInBlock _ = Nothing` means that even legitimate Peras certificates embedded in blocks are never extracted. Consequently, `getLatestPerasCertRound` always returns `Nothing`, so the cooldown period that should follow a certified round never starts. This breaks the Peras safety invariant that prevents voting during cooldown, allowing an attacker to trigger votes in rounds that should be suppressed.

---

### Likelihood Explanation

The attack path is fully reachable by any unprivileged peer:

1. A peer connects to the target node via the standard node-to-node mini-protocol stack.
2. The peer sends a crafted `PerasCert` message through the `ObjectDiffusion` mini-protocol.
3. The node calls `validatePerasCert`, which returns `Right` unconditionally.
4. The certificate's boost is applied to chain selection.

No keys, stake, or operator access are required. The `BlockSupportsPeras` instance is the only instance in the codebase for production block types (no `OVERLAPPING`/`OVERLAPPABLE` more-specific instance exists for `HardForkBlock` or `CardanoBlock`).

---

### Recommendation

1. **Remove the global degenerate instance** and require each block type to provide a real implementation of `BlockSupportsPeras`, or gate the instance behind a feature flag that is disabled until the full Peras HFC plumbing is in place.
2. **Implement `validatePerasCert`** to verify the cryptographic signature over the certificate (VRF/KES proof, committee membership, round number bounds).
3. **Implement `getPerasCertInBlock`** to extract certificates from blocks so that `getLatestPerasCertRound` reflects the actual on-chain state and cooldown periods are enforced correctly.
4. Track progress against the referenced issues (`tweag/cardano-peras#73`, `tweag/cardano-peras#120`) and block deployment of the Peras mini-protocol until real validation is in place.

### Proof of Concept

**Attacker-controlled entry path:**

```
Peer (attacker)
  │
  │  ObjectDiffusion mini-protocol (node-to-node)
  │  sends: PerasCert { pcCertRound = R, pcCertBoostedBlock = <adversarial fork tip> }
  ▼
ObjectPool/PerasCert.hs  →  validatePerasCert params cert
                                 = Right ValidatedPerasCert
                                     { vpcCert      = cert          -- no checks
                                     , vpcCertBoost = perasWeight params }
  ▼
Chain selection: adversarial fork tip receives full Peras boost
  ▼
Honest node switches to adversarial fork
```

The degenerate instance is the necessary vulnerable step: without it, `validatePerasCert` would reject a certificate that lacks a valid cryptographic proof. With it, every certificate is accepted, and the full chain-weight boost is applied unconditionally. [7](#0-6)
