### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inflate Peras Chain Weight and Trigger Unauthorized Chain Switches - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound `PerasCert` without performing any cryptographic or quorum verification. An unprivileged peer can craft and send a certificate for any block, causing the receiving node to inflate that block's chain weight by `perasWeight` and potentially switch to a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve a certificate before it enters the `PerasCertDB` and influences chain selection. The production default instance (used for all `StandardHash blk`) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function returns `Right` for every input — no signature check, no committee membership check, no quorum check. The `vpcCertBoost` is unconditionally set to `perasWeight params` from `mkPerasParams`.

The inbound certificate handler `makePerasCertPoolWriterFromChainDB` wires this stub directly into the network-facing object diffusion writer:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound cert and, if all pass (which they always do), timestamps and inserts them: [3](#0-2) 

Once inserted, `chainSelSync` processes the cert and immediately triggers chain selection for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

Chain selection then uses `preferAnchoredCandidate`, which — when the `PerasWeightSnapshot` is non-empty — computes `wsvTotalWeight = blockNo + weightBoost` for each candidate suffix: [5](#0-4) [6](#0-5) 

The weight boost is accumulated into the `PerasWeightSnapshot` from the `ValidatedPerasCert.vpcCertBoost` field, which was set to `perasWeight mkPerasParams` without any validation. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` naming any block hash and any round number not yet in the DB. The cert passes "validation" unconditionally, is stored, and its `perasWeight` boost is added to the named block's chain weight. If the adversary's fork contains that block, its `wsvTotalWeight` (block number + boost) can exceed the honest chain's total weight, causing the honest node to switch to the adversary's fork. This is a **chain selection error** that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain — matching the High impact category.

---

### Likelihood Explanation

The object diffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a `PerasCert` message. The only deduplication guard is the round number (`Set PerasRoundNo`), so an attacker can inject one cert per round number not yet seen. No stake, key material, or operator access is required. The attack is trivially reproducible on a private testnet by connecting a crafted peer that sends a `PerasCert` pointing to a block on a minority fork.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the certificate's aggregate signature against the claimed committee members.
2. Confirms the signers were elected to the voting committee for the stated round (using the epoch's stake distribution and WFA committee selection).
3. Confirms the total stake of the signers meets the quorum threshold (`stakeAboveThreshold`).
4. Rejects any cert whose `pcCertBoostedBlock` does not correspond to a known, header-validated block.

Until the real implementation is ready, the node should refuse to process inbound certificates from peers (i.e., the object diffusion writer for certs should be disabled), rather than accepting all of them unconditionally.

---

### Proof of Concept

**Private-testnet sequence:**

1. Start an honest node `H` syncing a chain where block `B_fork` is on a minority fork at block number `N`.
2. Connect adversarial peer `A` to `H` via the object diffusion mini-protocol.
3. `A` sends a single `PerasCert { pcCertRound = R, pcCertBoostedBlock = point(B_fork) }` for a round `R` not yet in `H`'s DB.
4. `H` calls `validatePerasCert mkPerasParams cert` → returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams }` unconditionally. [8](#0-7) 
5. `processCerts` inserts the cert; `addPerasCertAsync` enqueues it for chain selection. [9](#0-8) 
6. `chainSelSync` triggers `chainSelectionForBlock` for `B_fork`. [10](#0-9) 
7. `preferAnchoredCandidate` computes `wsvTotalWeight(fork) = N + perasWeight` vs `wsvTotalWeight(honest) = N_honest + 0`. If `perasWeight > N_honest - N`, the node switches to the adversary's fork. [11](#0-10)
