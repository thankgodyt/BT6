Audit Report

## Title
Detached `send_tokens` with pre-mutation state in `utxo_fin_transfer_fast` causes permanent loss of relayer's fronted tokens — (File: near/omni-bridge/src/lib.rs)

## Summary
In `utxo_fin_transfer_fast`, the fast-transfer record is unconditionally removed or marked finalised before the relayer repayment is attempted. The repayment call `send_tokens(...).detach()` is fire-and-forget with no callback or rollback path. If the inner `ft_transfer` fails (e.g., relayer not storage-registered for the BTC token), the fast-transfer record is already gone and the relayer's fronted tokens are permanently unrecoverable.

## Finding Description
At lines 2529–2540, for NEAR-destination transfers `remove_fast_transfer` is called unconditionally, and for other-chain destinations `mark_fast_transfer_as_finalised` is called unconditionally — both before any repayment attempt. At lines 2542–2548, `send_tokens` is called and immediately `.detach()`ed. There is no success callback, no failure callback, and no mechanism to restore the fast-transfer record if the promise fails. The developer-authored `// TODO: check how to deal with failed send_tokens` comment at line 2484 confirms this failure path is known and unresolved. The entry point is the normal BTC cross-chain finalization flow (`ft_transfer_call` from the registered connector), not an admin-only path.

## Impact Explanation
If `send_tokens` fails after state mutation, the relayer permanently loses the tokens they fronted for the fast transfer. There is no re-entry point: the fast-transfer record is deleted (NEAR destination) or marked finalised (other-chain destination), so no subsequent call can trigger repayment. This constitutes permanent loss of bridged funds held/fronted by the relayer, matching the Critical impact scope.

## Likelihood Explanation
NEP-141 tokens require explicit storage registration per account. A relayer account that has not registered storage for the specific BTC-wrapped token will cause `ft_transfer` to panic inside `send_tokens`. This is a realistic operational condition that can arise without any malicious actor — simply a relayer that registered for fast transfers but did not pre-register storage for every possible token. The flow is triggered through the normal BTC bridge finalization path, which is a production code path exercised on every UTXO settlement.

## Recommendation
- Move `remove_fast_transfer` / `mark_fast_transfer_as_finalised` into a callback that executes only after `send_tokens` resolves successfully; on failure, leave the record intact so repayment can be retried.
- Alternatively, add a failure callback that restores the fast-transfer record (un-removes or un-finalises) so the relayer can be repaid in a subsequent call.
- Before mutating state, verify (or force) the relayer's storage registration for the token, reverting the entire operation if registration is absent.

## Proof of Concept
1. Deploy the bridge with a BTC connector and a NEP-141 BTC-wrapped token.
2. Register a fast transfer where `relayer.near` has fronted tokens but has **not** called `storage_deposit` on the BTC token contract.
3. Have the BTC connector invoke `ft_transfer_call` with the matching UTXO data, triggering `utxo_fin_transfer` → `utxo_fin_transfer_fast`.
4. Observe line 2530: `remove_fast_transfer` executes and deletes the record from state.
5. Observe lines 2542–2548: `send_tokens(...).detach()` fires; the inner `ft_transfer` panics due to missing storage registration; the promise failure is silently discarded.
6. Assert: fast-transfer record no longer exists in contract state; `relayer.near` token balance is unchanged. No call path exists to recover the relayer's fronted tokens.
