### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Normalization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares the accumulated `PerasVoteStake` (drawn directly from the ledger stake distribution, in absolute units) against `perasQuorumStakeThreshold` (a relative fraction, currently `3/4`), without any normalization step. The code itself carries a `TODO` comment acknowledging this unit mismatch. When the actual committee selection data is wired into the production vote-diffusion path, any single voter whose absolute stake exceeds `0.77` (trivially true for any lovelace amount) can single-handedly forge a Peras certificate, bypassing the quorum requirement entirely.

---

### Finding Description

**Vulnerability class:** Bypass of Peras voting/certificate quorum check — a running total (`ptvtTotalStake`) is accumulated in absolute units and then compared against a threshold expressed in relative units, an exact analog of the external report's "wrong unit in running-total update."

**Root cause — `stakeAboveThreshold`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The quorum threshold is a relative fraction:

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2 / 100)
``` [2](#0-1) 

The `PerasVoteStake` type is a bare `Rational` with no unit enforcement:

```haskell
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [3](#0-2) 

**How the tally is accumulated:**

`updateTargetVoteTally` adds each vote's `vpvVoteStake` to `ptvtTotalStake`:

```haskell
| (Nothing, votes') <- swapVote vote ptvtVotes =
    (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
``` [4](#0-3) 

`votesReachQuorum` then calls `stakeAboveThreshold` on this accumulated total:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [5](#0-4) 

**How `vpvVoteStake` is assigned:**

`validatePerasVote` assigns the stake by looking up the voter in `PerasVoteStakeDistr`, which is populated directly from the ledger stake distribution (absolute lovelace values):

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [6](#0-5) 

The `WFALS.hs` committee code confirms that persistent members receive their raw `LedgerStake` as vote weight (absolute, not normalized):

```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight stake
``` [7](#0-6) 

**Current production wiring (placeholder):**

The production node-to-node handler currently passes an empty distribution as a placeholder:

```haskell

-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.

When the actual committee selection data is wired in (the intended production state), `PerasVoteStakeDistr` will contain absolute lovelace values. A voter with even 1 lovelace of stake would have `PerasVoteStake = 1` (or a large integer), which trivially satisfies `stake >= 3/4 + 2/100 = 0.77`.

---

### Impact Explanation

When the Peras vote-diffusion plumbing is completed and the real `PerasVoteStakeDistr` (containing absolute ledger stake values) is wired in, `stakeAboveThreshold` will compare an absolute lovelace sum against the relative threshold `0.77`. Any single vote from any registered stake pool (whose absolute stake is ≥ 1 lovelace, i.e., every pool) will cause `stakeAboveThreshold` to return `True`, forging a Peras certificate immediately. This completely bypasses the quorum requirement (intended to require ≥ 3/4 of total committee stake), allowing a single unprivileged voter to boost an arbitrary block with a Peras certificate. This undermines the chain-selection security guarantee of the Peras protocol, as adversarially boosted blocks would be preferred by all honest nodes.

**Allowed scope match:** Critical — bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The current production code uses `PerasVoteStakeDistr mempty`, so the bug is not yet exploitable on mainnet. However:
1. The TODO comment and the surrounding code make clear this is an active development gap, not a permanent design choice.
2. The `makePerasVotePoolWriterFromVoteDB` path (used in integration tests and private testnets) already accepts a caller-supplied `STM m PerasVoteStakeDistr`, making the bug reachable in private-testnet sequences today.
3. The unit mismatch is self-documented in the codebase and will become exploitable the moment the committee selection data is wired in.

---

### Recommendation

`stakeAboveThreshold` must normalize `PerasVoteStake` before comparing it to the relative threshold. The fix should either:

1. Accept the total stake of the committee as an additional parameter and divide: `normalizedStake = totalVoteStake / totalCommitteeStake`, then compare against `3/4`; or
2. Require that `PerasVoteStakeDistr` always stores pre-normalized (relative) values, enforced by the committee selection layer before populating the distribution.

The `WFALS` committee code already computes normalized weights for non-persistent members (`stake / nonPersistentStake`); the same normalization must be applied to persistent members and enforced at the `PerasVoteStakeDistr` population site.

---

### Proof of Concept

On a private testnet with the Peras vote-diffusion plumbing wired to a real `PerasVoteStakeDistr` (populated with absolute lovelace values from the ledger):

1. Attacker controls one stake pool with stake `S` lovelace (any positive value).
2. Attacker sends a single `PerasVote` for an arbitrary block `B` in round `R` via the Peras vote-diffusion mini-protocol.
3. `validatePerasVote` assigns `vpvVoteStake = S` (absolute lovelace).
4. `updateTargetVoteTally` sets `ptvtTotalStake = S`.
5. `votesReachQuorum` calls `stakeAboveThreshold`: `S >= 3/4 + 2/100` → `True` (since `S ≥ 1`).
6. A `ValidatedPerasCert` is forged for block `B`, boosting it by `perasWeight = 15` in chain selection.
7. All honest nodes prefer the adversarially boosted chain, regardless of honest chain density.
