### Title
Unauthorized Refund Request Allows Any Caller to Redirect Victim's BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`request_refund` imposes no caller-identity check. Any unprivileged NEAR account can submit a refund request for any observed BTC UTXO and supply an arbitrary attacker-controlled Bitcoin address as the refund destination. If the DAO does not reject the request within `unsafe_refund_timelock_sec`, `execute_refund` (also publicly callable) will route the victim's BTC to the attacker.

### Finding Description
`request_refund` is a public, payable function that accepts a `deposit_msg`, a caller-supplied `refund_address`, and a Bitcoin transaction proof: [1](#0-0) 

The only access restriction is on the optional `gas_fee` parameter (DAO/Operator only). There is no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` or any other authorized party for the UTXO.

Inside `internal_request_refund`, the `refund_address` is validated against `deposit_msg.refund_address` only when that field is `Some`: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the caller-supplied `refund_address` is accepted without restriction and stored verbatim in the `RefundRequest`: [3](#0-2) 

`execute_refund` is also publicly callable by anyone after the timelock elapses: [4](#0-3) 

The timelock applied when `deposit_msg.refund_address` is `None` is `unsafe_refund_timelock_sec` (the longer one), which is the only on-chain defense: [5](#0-4) 

### Impact Explanation
An attacker who observes a victim's BTC deposit transaction on-chain (both `tx_bytes` and `deposit_msg` are public Bitcoin data) can:

1. Call `request_refund` with the victim's `deposit_msg` and `tx_bytes`, but supply the attacker's own BTC address as `refund_address`.
2. The refund request is stored with the attacker's address as the destination.
3. After `unsafe_refund_timelock_sec` elapses without DAO rejection, call `execute_refund`.
4. The bridge constructs and signs a BTC transaction sending the victim's deposited BTC to the attacker's address.

This constitutes direct theft of user BTC funds — a Critical impact matching "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

The `verified_deposit_utxo` guard only blocks `execute_refund` if `verify_deposit` was already finalized for that UTXO: [6](#0-5) 

If the relayer has not yet called `verify_deposit` (e.g., the deposit is recent, the relayer is slow, or the attacker front-runs), the refund path is fully open.

### Likelihood Explanation
- All inputs needed for the attack (`deposit_msg`, `tx_bytes`, `vout`, Merkle proof) are publicly observable on the Bitcoin blockchain.
- The attacker only needs to pay a small NEAR storage deposit (`required_balance_for_request_refund`), which is not a meaningful deterrent.
- The sole on-chain defense is the `unsafe_refund_timelock_sec` window during which the DAO can call `reject_refund`. If the DAO is offline, slow, or the timelock is short, the attack succeeds.
- The attack is most effective against deposits where `verify_deposit` has not yet been submitted by the relayer (e.g., newly confirmed BTC transactions).

### Recommendation
Add a caller-identity check in `request_refund` to ensure only the intended recipient (or a privileged role) can submit a refund request for a given `deposit_msg`:

```rust
let caller = env::predecessor_account_id();
require!(
    caller == deposit_msg.recipient_id
        || self.acl_has_role(Role::DAO.into(), caller.clone())
        || self.acl_has_role(Role::Operator.into(), caller),
    "Only the deposit recipient or a privileged role can request a refund"
);
```

This mirrors the fix applied in the referenced StakingVault report, which added `if (receiver != _msgSender() && ...)` to prevent third-party state manipulation.

### Proof of Concept
1. Alice sends 1 BTC to her bridge deposit address, derived from `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The BTC transaction is confirmed on Bitcoin.
2. Before the relayer calls `verify_deposit`, Bob observes the transaction on-chain and extracts `tx_bytes`, `vout`, and the Merkle proof.
3. Bob calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None },
     refund_address = "bob_btc_address",
     tx_bytes = <alice's tx>,
     vout = 0,
     proof = <valid merkle proof>,
     gas_fee = None
   )
   ```
   attaching the required NEAR storage deposit.
4. `request_refund_callback` stores a `RefundRequest` with `refund_address = "bob_btc_address"`.
5. The DAO does not reject within `unsafe_refund_timelock_sec`.
6. Bob calls `execute_refund(utxo_storage_key)`. The bridge builds and MPC-signs a BTC transaction paying Alice's 1 BTC to Bob's address.
7. Alice's BTC is stolen.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
