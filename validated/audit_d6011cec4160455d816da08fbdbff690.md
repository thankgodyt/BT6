### Title
Zcash Sighash Computed Over Zero Input Amounts and Empty Scripts, Producing Permanently Invalid Withdrawal Signatures - (File: contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs)

### Summary
The Zcash `PsbtWrapper` initializes `inputs_utxo` with zero-value, empty-script placeholders and never populates them with actual UTXO data before computing the ZIP-244 sighash. Every Zcash withdrawal transaction is signed over an incorrect hash, producing a signature that the Zcash network will always reject. Because the user's nZEC is burned at withdrawal initiation (the `ft_on_transfer` callback returns `U128(0)`), the funds are permanently lost.

### Finding Description

`PsbtWrapper::new()` initializes `inputs_utxo` with dummy zero-value, empty-script entries:

```rust
// psbt_wrapper.rs line 74-75
let inputs =
    vec![ZcashTxOut::new(Zatoshis::from_u64(0).unwrap(), Script::default()); vin.len()];
``` [1](#0-0) 

These placeholders are stored directly into `self.inputs_utxo` and serialized into `psbt_hex` without ever calling `set_input_utxo`:

```rust
// contract_methods.rs lines 124-134
let psbt = PsbtWrapper::new(input, output, orchard_bundle, expiry_height, ...);
self.create_btc_pending_info(sender_id, amount.0, target_btc_address, psbt, max_gas_fee);
``` [2](#0-1) 

Inside `create_btc_pending_info`, `check_withdraw_psbt_valid` receives `&psbt` (immutable reference), so `set_input_utxo` cannot mutate it there. The PSBT is then serialized and stored with zero `inputs_utxo`. [3](#0-2) 

When `sign_btc_transaction` is later called, `internal_sign_btc_transaction` deserializes the stored PSBT and calls `get_hash_to_sign`, which feeds the zero-value, empty-script `inputs_utxo` directly into the ZIP-244 sighash computation:

```rust
// psbt_wrapper.rs lines 466-477
let script = self.inputs_utxo[vin].script_pubkey();   // Script::default() — empty
...
self.inputs_utxo[vin].value(),                         // Zatoshis(0)
``` [4](#0-3) 

The MPC signs this incorrect hash. When the resulting transaction is broadcast, the Zcash network recomputes the sighash using the actual on-chain UTXO amounts and scripts (ZIP-244 commits to both), finds a mismatch, and rejects the transaction.

### Impact Explanation

The Zcash `ft_on_transfer` callback returns `U128(0)`, meaning zero nZEC is refunded to the sender — all tokens are consumed by the bridge at withdrawal initiation. [5](#0-4) 

Because the signed transaction is always invalid on the Zcash network, the bridge-controlled ZEC UTXOs are never spent. The user's nZEC is permanently burned with no corresponding ZEC release. This is a **Critical** impact: permanent loss of user funds matching the allowed scope item "Zcash-specific validation failure that enables … permanent loss."

### Likelihood Explanation

This affects every Zcash withdrawal unconditionally. Any user who calls `ft_transfer_call` to withdraw nZEC triggers the path. No special attacker capability is required — a normal bridge user initiating a standard withdrawal is sufficient to trigger the loss.

### Recommendation

Populate `inputs_utxo` with the actual UTXO values and scripts before serializing the PSBT. The correct place is immediately after constructing the `PsbtWrapper` in `ft_on_transfer_callback`, using the UTXO data already available from the bridge's UTXO registry (the same data used to build `vutxos`). Call `psbt.set_input_utxo(...)` with the real `TxOut` values before passing the PSBT to `create_btc_pending_info`.

### Proof of Concept

1. User holds nZEC and calls `ft_transfer_call` on the nZEC contract targeting the bridge, with a valid Zcash address and a PSBT specifying real bridge UTXOs.
2. `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `get_last_block_height_promise` → `ft_on_transfer_callback`.
3. `ft_on_transfer_callback` calls `PsbtWrapper::new(input, output, ...)`. `inputs_utxo` is set to `[ZcashTxOut(0, Script::default()); n]`.
4. `create_btc_pending_info` serializes the PSBT (with zero `inputs_utxo`) into `psbt_hex` and stores it. The callback returns `U128(0)` — nZEC is burned.
5. User (or relayer) calls `sign_btc_transaction(btc_pending_sign_id, 0, key_version)`.
6. `internal_sign_btc_transaction` deserializes the stored PSBT, calls `get_hash_to_sign(0, &public_keys)`. The sighash is computed with `value = 0` and `script = []` for every input.
7. MPC signs this hash and returns a valid ECDSA signature over the wrong digest.
8. `sign_btc_transaction_callback` embeds the signature into the transaction and emits `SignedBtcTransaction`.
9. The relayer broadcasts the transaction. The Zcash network computes the ZIP-244 sighash using the actual UTXO amounts and scripts, finds the signature invalid, and rejects the transaction.
10. The user's nZEC is permanently burned; the ZEC UTXOs remain locked in the bridge with no recovery path.

    pub fn get_hash_to_sign(&self, vin: usize, public_keys: &[bitcoin::PublicKey]) -> [u8; 32] {
        let tx_data = WrappedTransaction::to_zcash_tx(
            &self.vin,
            &self.vout,
            &self.inputs_utxo,
            self.expiry_height,
            public_keys,
            self.branch_id,
        );
        let txid_parts =
            self.tx_digest(&tx_data, zcash_primitives::transaction::txid::TxIdDigester);

        let script = self.inputs_utxo[vin].script_pubkey();
        let transparent_bundle = tx_data.transparent_bundle().unwrap_or_else(|| {
            env::panic_str("ERR_NO_TRANSPARENT_BUNDLE: missing transparent bundle")
        });
        let sig_input = zcash_primitives::transaction::sighash::SignableInput::Transparent(
            zcash_transparent::sighash::SignableInput::from_parts(
                transparent_bundle,
                SighashType::ALL,
                vin,
                script,
                script,
                self.inputs_utxo[vin].value(),
            )
            .unwrap_or_else(|_| env::panic_str("ERR_SIGNABLE_INPUT: invalid input index")),
        );

        *zcash_primitives::transaction::sighash::signature_hash(&tx_data, &sig_input, &txid_parts)
            .as_ref()
    }
