### Title
Peras Certificate Validation Always Returns `Right`, Allowing Any Peer to Inject Fake Certificates That Manipulate Chain-Selection Weight — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every peer-supplied certificate, performing no cryptographic or structural checks. The object-diffusion inbound path calls this function for every certificate received from an unprivileged peer and, on success, persists the certificate to the ChainDB. Because the `PerasWeightSnapshot` used in chain selection is populated from those persisted certificates, an attacker can inject a certificate that boosts the weight of an arbitrary block on a minority fork, causing an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub always succeeds**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, lines 350–358:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This is the **only** instance of `BlockSupportsPeras` in the repository (the comment "degenerate instance for all blks to get things to compile" confirms it is the universal default). Every `PerasCert` value, regardless of content, is wrapped in `ValidatedPerasCert` and assigned the full `perasWeight` boost.

**Reachable entry path — object-diffusion inbound pipeline**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, lines 121–133:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)   -- ← always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
```

`processCerts` (lines 156–185 of the same file) calls `validatePerasCert` for every certificate not already in the database. Because the function always returns `Right`, every novel certificate from any peer is unconditionally persisted via `ChainDB.addPerasCertAsync`.

**Chain-selection consequence — weight snapshot is populated from persisted certificates**

`preferAnchoredCandidate` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Util/AnchoredFragment.hs`, lines 186–213, branches on whether the `PerasWeightSnapshot` is empty. When it is non-empty (i.e., after a certificate has been accepted), it computes `weightedSelectView` over both fragments and uses the boosted total weight to decide which chain to prefer. A fake certificate that boosts a block on a minority fork can therefore flip the chain-selection outcome.

Note: `checkPreferTheirsOverOurs` in the ChainSync client (line 1842) hard-codes `emptyPerasWeightSnapshot`, so that particular guard is unaffected. The vulnerability manifests in the main ChainDB chain-selection loop (`initialChainSelection`, `ChainSel.hs` line 177) which receives the real snapshot.

---

### Impact Explanation

**Impact: High**

An unprivileged peer can craft a `PerasCert` whose `pcCertBoostedBlock` points to any block on a minority fork. After injection, the `PerasWeightSnapshot` held by the ChainDB assigns that block a non-zero `PerasWeight`. `preferAnchoredCandidate` then computes `wsvTotalWeight = BlockNo + PerasWeight` for each candidate; a sufficiently large boost can make a shorter fork appear heavier than the honest chain, causing the node to switch to the attacker's chain. This is a chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.

---

### Likelihood Explanation

**Likelihood: Medium**

The object-diffusion mini-protocol is reachable by any peer that can establish a connection. No stake, keys, or prior state are required. The only precondition is that the attacker knows (or guesses) the hash of a block already in the node's VolatileDB to use as `pcCertBoostedBlock`. Because block hashes are public, this is trivially satisfied. The attack requires sending a single crafted message.

---

### Recommendation

1. **Implement real certificate validation** before the Peras object-diffusion protocol is enabled in production. At minimum, `validatePerasCert` must verify the certificate's cryptographic proof of quorum (committee signatures / BLS aggregate) and check that the certified block and round number are consistent with the current ledger state.
2. **Gate the object-diffusion handler** on whether Peras is active in the current era; reject all inbound certificates when Peras is not yet active.
3. **Remove the universal stub instance** and require each concrete block type to provide an explicit, non-trivial implementation of `validatePerasCert`.

### Proof of Concept

1. Attacker connects to a target node via the Peras object-diffusion mini-protocol.
2. Attacker constructs a `PerasCert` value:
   ```haskell
   PerasCert
     { pcCertRound      = PerasRoundNo 1
     , pcCertBoostedBlock = BlockPoint slotNo (hashOfAttackerBlock)
     }
   ```
   where `hashOfAttackerBlock` is the hash of a block on the attacker's minority fork already present in the node's VolatileDB.
3. Attacker sends this certificate to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..., vpcCertBoost = perasWeight params}` unconditionally.
5. The certificate is persisted to the ChainDB certificate store.
6. On the next chain-selection trigger, `preferAnchoredCandidate` is called with a non-empty `PerasWeightSnapshot` that assigns `perasWeight` to the attacker's block.
7. If `perasWeight` is large enough relative to the honest chain's length advantage, `wsvTotalWeight` of the attacker's fragment exceeds that of the honest fragment, and the node switches to the attacker's chain. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
