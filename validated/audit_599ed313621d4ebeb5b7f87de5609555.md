Audit Report

## Title
ERC721/ERC20 `transferFrom` Selector Collision Permanently Freezes NFTs in Bridge — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer()` unconditionally casts any caller-supplied `tokenAddress` to `IERC20` and calls `safeTransferFrom`. Because `ERC721.transferFrom(address,address,uint256)` and `ERC20.transferFrom(address,address,uint256)` share the identical 4-byte selector `0x23b872dd`, an ERC721 token is silently accepted. The NFT is then permanently locked in the bridge because `finTransfer()` calls `IERC20.safeTransfer()` (selector `0xa9059cbb`), which does not exist on ERC721, causing every redemption attempt to revert.

## Finding Description

**Root cause — no token-type guard in `initTransfer`:**

The else-branch at L406–412 unconditionally treats any non-bridge, non-custom-minter address as an ERC20:

```solidity
} else {
    IERC20(tokenAddress).safeTransferFrom(
        msg.sender,
        address(this),
        amount          // interpreted as tokenId by ERC721
    );
}
```

`SafeERC20.safeTransferFrom` issues a low-level call to selector `0x23b872dd`. ERC721's `transferFrom(address,address,uint256)` carries the same selector and returns no data. `SafeERC20` treats an empty return as success (it only reverts on an explicit `false`), so the call completes without reverting and the NFT is deposited into the bridge.

**`logMetadata` is permissionless and performs no token-type check (L224–232):**

```solidity
function logMetadata(address tokenAddress) external payable {
    string memory name = IERC20Metadata(tokenAddress).name();
    string memory symbol = IERC20Metadata(tokenAddress).symbol();
    uint8 decimals = IERC20Metadata(tokenAddress).decimals();
    logMetadataExtension(tokenAddress, name, symbol, decimals);
    emit BridgeTypes.LogMetadata(tokenAddress, name, symbol, decimals);
}
```

`evm/SECURITY.md` explicitly confirms this is intentionally permissionless. Many ERC721 contracts implement `name()`, `symbol()`, and `decimals()` (e.g., OpenZeppelin's `ERC721` + `ERC721Metadata`), so `logMetadata` succeeds for them and emits a `LogMetadata` event that the relayer picks up.

**Permanent lock in `finTransfer` (L350–355):**

```solidity
} else {
    IERC20(payload.tokenAddress).safeTransfer(
        payload.recipient,
        payload.amount
    );
}
```

`safeTransfer` dispatches selector `0xa9059cbb` (`transfer(address,uint256)`). ERC721 has no such function. Every `finTransfer` call for this token address reverts unconditionally, making the NFT irrecoverable.

**Existing guards are insufficient:** `IERC165` is imported but only used in the bridge's own `supportsInterface` override (L510–520). No ERC-165 check is performed on incoming `tokenAddress` values in either `logMetadata` or `initTransfer`. The `isBridgeToken` / `customMinters` checks only gate the burn/mint path; they do not block arbitrary ERC721 addresses from reaching the else-branch.

**`amount` is `uint128`:** The function signature takes `uint128 amount`. ERC721 tokenIds are `uint256`, but the vast majority of deployed NFT collections use sequential small integer IDs that fit within `uint128`, so this is not a meaningful barrier.

## Impact Explanation

**Permanent freezing of bridged funds (Critical):** Any ERC721 token whose `tokenId` fits in `uint128` and whose contract exposes `name()`/`symbol()`/`decimals()` can be deposited into the bridge via the selector collision. Because `finTransfer` always reverts for ERC721 addresses, the NFT is irrecoverable. This directly matches the "permanent freezing of bridged funds" critical impact category.

**Unauthorized minting of unbacked NEP-141 tokens on NEAR (Critical):** After `logMetadata` registers the ERC721 address on NEAR, the NEAR side mints NEP-141 tokens to the attacker equal to `tokenId` when it receives proof of the `InitTransfer` event. These tokens are unbacked and can be transferred or sold on NEAR but can never be redeemed for the underlying asset. This matches the "unauthorized minting" critical impact category.

## Likelihood Explanation

The attack is fully permissionless. `logMetadata` requires no role, no signature, and no admin action. `initTransfer` requires only that the caller holds and has approved the NFT. No admin compromise, key leak, threshold-signature bypass, or victim mistake is required. Any ERC721 implementing `name()`/`symbol()`/`decimals()` is a viable target — a common pattern in OpenZeppelin-based NFT contracts. The bridge relayer processes `LogMetadata` and `InitTransfer` events automatically.

## Recommendation

1. **Add an ERC-165 interface check** in both `initTransfer` and `logMetadata`: call `IERC165(tokenAddress).supportsInterface(0x80ac58cd)` (IERC721) and revert if it returns `true`. Also check `0xd9b67a26` (IERC1155).
2. **Require explicit token registration** before `initTransfer` accepts a token in the else-branch — extend the existing `isBridgeToken` / `customMinters` allowlist pattern to cover native ERC20s as well.
3. **Alternatively**, verify `IERC165(tokenAddress).supportsInterface(type(IERC20).interfaceId)` returns `true`, with the caveat that not all ERC20s implement ERC-165.

## Proof of Concept

1. Attacker holds ERC721 at address `nft` with `tokenId = T` (fits in `uint128`). The ERC721 implements `name()`, `symbol()`, `decimals()`.
2. Attacker calls `OmniBridge.logMetadata(nft)`. Succeeds; emits `LogMetadata(nft, ...)`.
3. Bridge relayer submits proof to NEAR; NEAR deploys a NEP-141 token mapped to `nft`.
4. Attacker calls `nft.approve(bridge, T)` (ERC721 approval).
5. Attacker calls `OmniBridge.initTransfer(nft, T, 0, 0, "attacker.near", "")`.
   - `customMinters[nft]` is zero → skipped.
   - `isBridgeToken[nft]` is false → skipped.
   - `IERC20(nft).safeTransferFrom(attacker, bridge, T)` → dispatches selector `0x23b872dd` → ERC721's `transferFrom(attacker, bridge, T)` executes → NFT is now in bridge. Returns no data → `SafeERC20` treats as success.
   - `InitTransfer` event emitted.
6. Bridge relayer submits proof to NEAR; NEAR mints `T` NEP-141 tokens to `attacker.near`.
7. Attacker transfers or sells the NEP-141 tokens on NEAR.
8. Any call to `finTransfer` for this token on EVM reverts: `IERC20(nft).safeTransfer(recipient, T)` dispatches selector `0xa9059cbb`, which does not exist on ERC721 → permanent revert → NFT frozen forever.

**Minimal test plan:** Deploy a mock ERC721 implementing `name()`/`symbol()`/`decimals()`. Deploy `OmniBridge` on a local fork. Execute steps 4–5 above and assert the NFT balance of the bridge increases. Then attempt `finTransfer` and assert it reverts. This is reproducible in a standard Foundry/Hardhat local test without any external dependencies.
