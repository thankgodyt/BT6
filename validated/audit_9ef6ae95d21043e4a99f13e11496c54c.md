### Title
DAO `cancel_withdraw` blocked by user-controlled `pending_sign_count` via `withdraw_rbf` griefing — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` checks `require_pending_sign_capacity` against the **withdrawal owner's** account, not the DAO caller's. A user can call `withdraw_rbf` after their withdrawal moves to PendingVerify to fill their `btc_pending_sign_ids` slot, causing the DAO's `cancel_withdraw` to panic and temporarily preventing cancellation of the stuck withdrawal.

### Finding Description
In `cancel_withdraw` (api/bridge.rs:291), the guard `require_pending_sign_capacity(&user_account_id)` is applied to the original withdrawal owner rather than being skipped for privileged callers. The purpose of this check is to ensure there is room in `btc_pending_sign_ids` for the new cancel-RBF entry that `define_rbf_method!` will insert. However, the check is not conditioned on the caller's role.

A user whose withdrawal is in PendingVerify (count = 0) can call `withdraw_rbf` to insert a new entry into `btc_pending_sign_ids` (count = 1). If the user then withholds signing the RBF, `btc_pending_sign_ids` stays full. Any subsequent DAO call to `cancel_withdraw` panics before reaching the state-validation logic inside `internal_cancel_withdraw`.

### Impact Explanation
The DAO cannot cancel a stuck withdrawal while the user's `btc_pending_sign_ids` is at capacity. The original withdrawal remains in PendingVerify, the bridge UTXOs consumed by it are not reclaimed, and the user's burned nBTC is not refunded. The DAO can work around this by calling `set_pending_tx_limit` to raise the user's limit, so the lock is not permanent, but it requires an unplanned DAO transaction and the user can repeat the griefing up to `rbf_num_limit` times.

**Impact class:** Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention.

### Likelihood Explanation
Any user with a pending withdrawal can trigger this with a single `withdraw_rbf` call. No special privileges or leaked keys are required. The default `pending_tx_limits` of 1 makes every ordinary user a potential trigger.

### Recommendation
In `cancel_withdraw` (and `cancel_active_utxo_management`), bypass `require_pending_sign_capacity` when the caller holds `Role::DAO` or `Role::Operator`, or restructure the check so it only applies to user-initiated RBF paths. The DAO must always be able to cancel a stuck withdrawal regardless of the owner's pending sign count.

### Proof of Concept
```
State: user alice has pending_sign_count == 0 (original withdrawal in PendingVerify)
1. alice calls withdraw_rbf(original_id, ...) → btc_pending_sign_ids = {rbf_id}, count = 1
2. alice does NOT call sign_btc_transaction on the RBF
3. max_btc_tx_pending_sec elapses
4. DAO calls cancel_withdraw(original_id, ...)
   → require_pending_sign_capacity(&alice) → 1 < 1 is false → panic "Too many pending sign transactions"
Assert: cancel_withdraw panics; original withdrawal remains stuck in PendingVerify
```

    pub fn set_pending_tx_limit(&mut self, account_id: AccountId, max_pending: Option<u32>) {

                prev.is_some(),
                format!("Invalid account_id: {}", account_id)
