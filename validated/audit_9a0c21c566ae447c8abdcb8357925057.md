Audit Report

## Title
Partial `ft_on_transfer` Refund Leaves Bridged Tokens Permanently Stuck in `omni-bridge` Contract — (File: near/omni-bridge/src/lib.rs)

## Summary

`is_refund_required()` only triggers a bridge-state revert when `ft_transfer_call` reports zero tokens used. When a recipient's `ft_on_transfer` returns a partial unused amount, the NEP-141 token contract refunds those tokens to the bridge, but all three callback paths treat the transfer as fully successful. The partially refunded tokens are permanently stuck in the bridge contract with no automatic recovery path.

## Finding Description

When a cross-chain transfer includes a non-empty `msg` field, `send_tokens()` calls `ft_transfer_call` on the token contract instead of `ft_transfer`. [1](#0-0) 

Under NEP-141, the recipient's `ft_on_transfer` returns the number of tokens it did **not** use. The token contract refunds that amount back to the bridge and returns the number of tokens **used** to the bridge's callback. `is_refund_required()` reads this result and only triggers a revert when the used amount equals zero: [2](#0-1) 

If the recipient uses 998 out of 999 tokens and returns 1 unused, `ft_transfer_call` reports `998` used. `is_refund_required` sees `998 != 0` and returns `false`. The bridge proceeds as fully successful, pays the relayer fee, and emits `FinTransferEvent`. The 1 token refunded by the NEP-141 contract to the bridge address is never forwarded to the original sender.

All three callback paths share this same flawed binary check:

1. **`fin_transfer_send_tokens_callback`** — regular inbound finalization with `msg`: [3](#0-2) 

2. **`resolve_fast_transfer`** — fast-transfer path with `msg`: [4](#0-3) 

3. **`resolve_utxo_fin_transfer`** — UTXO-chain finalization with `msg`: [5](#0-4) 

The integration test suite explicitly documents this behavior as an accepted outcome — `expected_locker_balance: 1` confirms 1 token is left stranded in the bridge contract: [6](#0-5) 

## Impact Explanation

Bridged tokens that are partially rejected by the recipient's `ft_on_transfer` are permanently locked inside the `omni-bridge` contract. The bridge's `locked_tokens` accounting is already decremented (for native tokens) or bridge tokens are already minted (for deployed tokens) before `ft_transfer_call`, so the accounting does not reflect the stuck balance. The only recovery path is a DAO-privileged `transfer_token_as_dao` call, which is not automatic and requires admin intervention. This constitutes **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation

Any user who initiates a cross-chain transfer with a non-empty `msg` field targeting a NEAR contract that partially consumes tokens triggers this path. This is a realistic scenario for DeFi integrations (e.g., a DEX or lending protocol that accepts only part of the offered tokens). The user controls the `msg` and recipient fields on the source chain. No special privileges are required. The bridge provides no protection against partial refunds.

## Recommendation

Replace the binary `is_refund_required` check with a function that returns the actual used amount. In each of the three callback functions:

- If `used_amount == 0`: full revert (existing behavior).
- If `0 < used_amount < sent_amount`: partial refund — send `sent_amount - used_amount` back to the original sender (or burn if it is a deployed bridge token).
- If `used_amount == sent_amount`: full success (existing behavior).

This requires passing the original `sent_amount` into each callback and comparing it against the promise result from `ft_transfer_call`.

## Proof of Concept

The existing integration test at `near/omni-tests/src/fin_transfer.rs:533-544` already demonstrates the bug: [6](#0-5) 

```
amount = 1000, fee = 1
msg.return_value = U128(1)   // recipient returns 1 token unused

expected_recipient_balance = 998   // recipient got 998 (not 999)
expected_relayer_balance   = 1     // relayer got fee
expected_locker_balance    = 1     // 1 token stuck in bridge ← BUG
```

The bridge emits `FinTransferEvent` (success) despite 1 token being silently absorbed. The original cross-chain sender has no recourse. This test passes, confirming the bug is present and accepted in the current codebase.
