### Title
Frontrunning `request_refund` with Attacker-Controlled `refund_address` Redirects Victim's BTC - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user calls `request_refund` with a `DepositMsg` whose `refund_address` field is `None`, any unprivileged NEAR account can frontrun that call using the same `deposit_msg` and BTC transaction bytes but substituting their own Bitcoin address as `refund_address`. Because the contract stores only one refund request per UTXO, the victim's subsequent `request_refund` reverts with "Refund request already exists for this UTXO", and the attacker's request — pointing to the attacker's BTC address — remains in storage. After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and the victim's deposited BTC is sent to the attacker.

---

### Finding Description

`request_refund` is publicly callable (no `#[trusted_relayer]` guard on the function itself, confirmed by tests where the unprivileged account "alice" calls it successfully). [1](#0-0) 

The function accepts a `refund_address` parameter that is only validated against `deposit_msg.refund_address` when that optional field is `Some`: [2](#0-1) 

When `deposit_msg.refund_address` is `None`, the check is skipped entirely and any caller-supplied Bitcoin address is accepted. In `request_refund_callback`, the contract verifies that the BTC transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg` — but it does **not** verify that the caller is the original depositor or that the `refund_address` belongs to the depositor: [3](#0-2) 

The duplicate-request guard fires only after the attacker's request is already stored: [4](#0-3) 

The stored `refund_address` is later used verbatim by `execute_refund` → `finalize_refund_with_psbt` → `build_refund_output` to construct the Bitcoin output paying the refund: [5](#0-4) 

The longer `unsafe_refund_timelock_sec` is applied when `deposit_msg.refund_address` is `None`, giving DAO/Operator a window to reject — but rejection requires privileged action and is not guaranteed: [6](#0-5) 

Only DAO or Operator can reject a refund request that has not yet been finalized via `verify_deposit`; the victim (a regular user) has no self-service remedy: [7](#0-6) 

---

### Impact Explanation

The attacker's refund request is stored with the attacker's Bitcoin address. After the timelock, `execute_refund` is callable by anyone, and the MPC-signed Bitcoin transaction sends the victim's deposited BTC to the attacker's address. This constitutes a direct theft of user funds — a Critical-class bridge impact. The only protection is DAO/Operator intervention during the `unsafe_refund_timelock_sec` window, which is not guaranteed.

---

### Likelihood Explanation

All inputs needed for the attack are public: `deposit_msg` is emitted as an on-chain event by `get_user_deposit_address`; the BTC transaction and its Merkle proof are visible on the Bitcoin blockchain. The attacker only needs to observe the victim's pending `request_refund` NEAR transaction and submit their own version first. The required attached NEAR deposit is a small, fixed cost. The attack is realistic for any deposit where the user omitted `deposit_msg.refund_address`.

---

### Recommendation

1. **Bind `refund_address` to the caller**: In `request_refund_callback`, require that the caller (`env::predecessor_account_id()` at the time of the outer call, passed through the callback) matches the `deposit_msg.recipient_id`, or store the caller and enforce it at `execute_refund` time.
2. **Alternatively, require `deposit_msg.refund_address` to always be set**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None`, eliminating the unchecked `refund_address` parameter path entirely.
3. **Permissionless reject for the depositor**: Allow `deposit_msg.recipient_id` to reject a refund request that was not submitted by them, so the victim is not solely dependent on DAO/Operator intervention.

---

### Proof of Concept

1. Alice deposits BTC to the address derived from `DepositMsg { recipient_id: "alice", refund_address: None, … }`. The event is emitted publicly.
2. The deposit is never finalized (e.g., amount below minimum, or relayer is offline). Alice calls `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, vout, proof, None)`.
3. Attacker observes Alice's pending NEAR transaction. Attacker calls `request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)` with higher priority (or simply races it).
4. Attacker's call lands first. `request_refund_callback` stores `RefundRequest { refund_address: "attacker_btc_addr", … }`.
5. Alice's call reverts: "Refund request already exists for this UTXO".
6. DAO/Operator does not notice or does not act within `unsafe_refund_timelock_sec`.
7. Attacker calls `execute_refund(utxo_storage_key, None)`. The MPC-signed Bitcoin transaction sends Alice's BTC to `"attacker_btc_addr"`.
8. Alice's BTC is stolen.

**Self-protection**: Alice can prevent this by setting `deposit_msg.refund_address = Some("alice_btc_addr")` at deposit time, which forces the `refund_address` parameter to match. However, this protection is optional and not enforced by the protocol.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
