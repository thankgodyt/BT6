### Title
`HistoricityCheck` Disconnects Honest Peers During Low-Density Disaster Scenarios, Enabling Adversarial Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client/HistoricityCheck.hs`)

---

### Summary

The `HistoricityCheck` mechanism in the Genesis ChainSync client is a protective guard against adversarial peers abusing `MsgRollBackward` and `MsgAwaitReply` messages to waste CPU. However, exactly like the OpenLeverage anti-flashloan check that blocks liquidations when the spot price keeps trending below TWAP, this check can also disconnect **honest** peers during a disaster scenario where the honest chain has grown sparsely for longer than `HistoricityCutoff` (default: `3k/f + 1 hour ≈ 37 hours` on mainnet). When all honest peers are disconnected, adversarial peers serving a denser alternative chain are not subject to the same check, allowing the GDD to prefer and the syncing node to select the adversarial chain.

---

### Finding Description

`mkCheck` in `HistoricityCheck.hs` applies the historicity check in both `PreSyncing` and `Syncing` GSM states:

```haskell
mkCheck systemTime getCurrentGsmState cshc =
  HistoricityCheck
    { judgeMessageHistoricity = \msg hswt ->
        getCurrentGsmState >>= \case
          PreSyncing -> judgeRollback msg hswt
          Syncing    -> judgeRollback msg hswt
          CaughtUp   -> pure $ Right ()
    }
```

The `judgeRollback` function disconnects any peer whose `MsgRollBackward` rewinds a header, or whose `MsgAwaitReply` is sent at a candidate tip, that is older than `HistoricityCutoff` at arrival time:

```haskell
judgeRollback msg (HeaderStateWithTime headerState slotTime) = do
  arrivalTime <- systemTimeCurrent systemTime
  let actualRollbackAge = arrivalTime `diffRelTime` slotTime
  pure $
    when (historicityCutoff < actualRollbackAge) $
      throwError HistoricityException { ... }
```

The check is intentionally disabled in `CaughtUp` state (comment: *"extra resilience against disconnects between honest nodes in disaster scenarios with very low chain density"*), but it remains **fully active** in `Syncing` state — precisely the state a node occupies while syncing through a historical low-density region.

**Attack path:**

1. The honest Cardano chain has a sparse region exceeding `HistoricityCutoff` (e.g., a network-wide outage lasting > 37 hours).
2. A syncing node in `Syncing` state connects to both honest peers and adversarial peers.
3. Honest peers serving the sparse honest chain eventually send `MsgAwaitReply` at a tip whose slot time is older than `HistoricityCutoff`. The historicity check fires (`throwIO $ HistoricityError ex`) and disconnects every honest peer.
4. Adversarial peers serve a denser alternative chain forked just before the sparse region. Their chain tip is recent; they never send `MsgAwaitReply` at an old tip, so the historicity check never fires against them.
5. With honest peers gone, the GDD compares only adversarial chains. The adversarial chain is denser in the GDD window than the (now-absent) honest chain. The syncing node selects the adversarial chain.

The code comment in `mkCheck` explicitly acknowledges the tension but only resolves it for `CaughtUp`:

> *"This is used to disable the historicity check when we are caught up. The rationale is extra resilience against disconnects between honest nodes in disaster scenarios with very low chain density."*

The genesis design document also acknowledges the limitation:

> *"This cannot be a perfect mitigation, since it's possible that an honest peer would need to rollback a header that is at most Scg slots old, even though that's very unlikely."*

Neither mitigation covers the `Syncing` state during a disaster.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest syncing node prefer a non-canonical chain beyond the intended security assumptions.**

A syncing node in `Syncing` state, during a disaster scenario where the honest chain has a sparse region exceeding `HistoricityCutoff`, will disconnect from all honest peers via `HistoricityError`. Adversarial peers serving a denser alternative chain are unaffected by the check. The GDD then favors the adversarial chain, and the syncing node permanently selects it. This is a durable chain selection failure: once the adversarial chain is selected and blocks become immutable, the node cannot roll back.

---

### Likelihood Explanation

**Low.** The trigger requires a genuine disaster scenario: the honest Cardano chain must have a sparse region exceeding `HistoricityCutoff` (`3k/f + 1 hour ≈ 37 hours` on mainnet). Such an event has not occurred on mainnet. However, the design document explicitly identifies this as a real risk class ("disaster scenario"), and the code comment acknowledges the check can disconnect honest nodes in exactly this condition. The adversary requires no special privileges — any unprivileged peer can serve a denser alternative chain once honest peers are disconnected.

---

### Recommendation

Apply the same `CaughtUp`-bypass logic to the `Syncing` state when the node is "almost caught up" (i.e., the immutable tip is within `HistoricityCutoff` of the wall clock), or replace the hard disconnect with a softer demotion (e.g., move the peer to a lower-priority role rather than disconnecting). Alternatively, the `HistoricityCutoff` check for `MsgAwaitReply` could be conditioned on whether the peer's tip is on a chain that is actually denser than the honest chain, rather than purely on wall-clock age. The design document itself notes that Lightweight Checkpointing is the intended mitigation for disaster scenarios, but that mitigation is out-of-band and requires operator action; the in-code check should not preemptively destroy all honest peer connections before checkpoints can be applied.

```haskell
data HistoricityException
  = -- | We received a @MsgRollBackward@ or a @MsgAwaitReply@ while their

    -- INVARIANT: @'historicityCutoff' < 'arrivalTime' `diffRelTime` 'slotTime'@
```

```markdown
In order to prevent adversarial peers from using MsgAwaitReply or MsgRollBack in order to waste the syncing nodes bandwidth and CPU by running full ChainSync for the historical chain, CSJ also enforces a {Limit on the Age of MsgAwaitReply/MsgRollBack}.
This cannot be a perfect mitigation, since it's possible that an honest peer would need to rollback a header that is at most Scg slots old, even though that's very unlikely.
But it's sufficient to simply limit that extra CPU cost to the final Scg window of the sync, instead of potentially paying that cost for the entire age of the chain.
The maximum allowed age of a rolled back header is HistoricityCutoff, which cannot be less than Scg; see the [Parameter Tuning](#parameter-tuning) section below for more details.
Any MsgRollBack that rolls back a header older than HistoricityCutoff (according to the wall clock) and any MsgAwaitReply that is sent when the candidate fragment tip is older than HistoricityCutoff immediately incurs a disconnection from that peer.
```
