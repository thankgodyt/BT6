### Title
Peras Vote and Certificate Validation Bypass via Missing Cryptographic Signature Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The catch-all `BlockSupportsPeras` instance, which is the only instance in production for all block types, unconditionally accepts every inbound Peras certificate without any validation, and accepts votes without verifying any cryptographic signature. The `PerasVote blk` data type in this instance carries no signature field at all. Any unprivileged peer connected via the object-diffusion miniprotocol can inject arbitrary Peras certificates boosting any block, and can forge votes impersonating any stake pool that appears in the stake distribution.

### Finding Description

The `BlockSupportsPeras` class in `SupportsPeras.hs` is the interface through which Peras votes and certificates are validated before being stored in the ChainDB. The only concrete instance in the codebase is the catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

This instance defines `PerasVote blk` with **no signature field**:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

`validatePerasVote` only performs a stake-distribution lookup — it never verifies any cryptographic proof that the claimed voter actually cast the vote:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

`validatePerasCert` is even weaker — it unconditionally returns `Right` for every certificate, performing zero checks:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [4](#0-3) 

These stub validators are wired directly into the production inbound-object pipeline. `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote` on every peer-supplied vote: [5](#0-4) 

`makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` on every peer-supplied certificate and, if it passes, calls `ChainDB.addPerasCertAsync chainDB`: [6](#0-5) 

The concrete `V1.PerasVote` type (used in the BLS-based Peras implementation) **does** carry a `pvSignature` field and `verifyVoteSignature` exists in `PerasBLSCrypto`: [7](#0-6) [8](#0-7) 

However, neither the `V1.PerasVote` type nor `verifyVoteSignature` is used in the `BlockSupportsPeras` instance that is actually dispatched at runtime. The concrete BLS crypto and the stub instance are entirely disconnected.

The analog to the external report is exact: just as the Gnosis Safe trusted-validator signature omitted `safeTxGas`/`gasPrice`/`refundReceiver`, the Peras vote validation omits the cryptographic signature entirely — the data type does not even carry one — and the certificate validation omits every check.

### Impact Explanation

**High — Bypass of Peras voting and certificate checks enabling unauthorized certificate acceptance.**

An unprivileged peer can:

1. **Forge votes**: Craft a `PerasVote blk` naming any `PerasVoterId` that appears in the stake distribution. `validatePerasVote` will accept it and assign it the full stake weight of that pool. By sending enough forged votes (one per high-stake pool), the attacker can manufacture a quorum without holding any keys.

2. **Inject arbitrary certificates**: Send a `PerasCert blk` naming any block as the boosted block for any round. `validatePerasCert` returns `Right` unconditionally. The certificate is stored in the ChainDB via `addPerasCertAsync` and its boost weight is applied to chain selection.

3. **Manipulate chain selection**: By injecting a certificate that boosts a block on a weaker chain, the attacker can cause an honest node to prefer a non-canonical chain, violating the Peras safety guarantee that only a legitimately quorum-certified block receives a boost.

### Likelihood Explanation

**High.** The attack entry point is the object-diffusion miniprotocol, which is reachable by any peer that can establish a connection to the node. No keys, stake, or special privileges are required. The attacker only needs to know the `PerasVoterId` (stake pool key hash) of pools in the current stake distribution, which is public on-chain data. The forged objects pass all validation checks as currently implemented.

### Recommendation

1. **Immediate**: Gate the Peras object-diffusion writers behind a feature flag that is disabled until proper validation is implemented, so that the stub instance is never reachable from the network.

2. **Structural**: Add a `pvSignature` field to the `PerasVote blk` data type in the `BlockSupportsPeras` instance (mirroring `V1.PerasVote.pvSignature`), and implement `validatePerasVote` to call `verifyVoteSignature` from `CryptoSupportsVoteSigning` before accepting a vote.

3. **Certificate**: Implement `validatePerasCert` to verify the aggregate BLS signature (`pcSignature` in `V1.PerasCert`) against the claimed voters and boosted block, mirroring the checks already defined in `PerasBLSCrypto`.

4. **Tracking**: The existing issue https://github.com/tweag/cardano-peras/issues/120 tracks enriching validation error types; the missing signature verification must be resolved before Peras object diffusion is enabled on any network.

### Proof of Concept

An attacker connected to a Peras-enabled node:

1. Reads the current stake distribution from the public ledger state to obtain a set of `PerasVoterId` values (stake pool key hashes) with high stake.

2. For each target pool, constructs a `PerasVote blk` value:
   ```
   PerasVote { pvVoteRound = <current round>
             , pvVoteBlock = <attacker-chosen block point>
             , pvVoteVoterId = <stolen pool key hash> }
   ```
   No signing key is needed; the data type carries no signature field.

3. Sends the batch of forged votes via the object-diffusion protocol. `processVotes` calls `validatePerasVote mkPerasParams sd vote` for each; since each claimed voter ID is present in the stake distribution, all votes pass and are stored.

4. `votesReachQuorum` is called with the accumulated `ValidatedPerasVote` values. Because the total stake of the forged votes exceeds the quorum threshold, it returns `Just ValidatedPerasVotesWithQuorum`.

5. `forgePerasCert` produces a `ValidatedPerasCert` boosting the attacker-chosen block. Alternatively, the attacker directly sends a `PerasCert blk` via the cert diffusion path; `validatePerasCert` returns `Right` unconditionally.

6. The certificate is added to the ChainDB. Chain selection now applies the Peras boost weight to the attacker-chosen block, potentially causing the node to switch to a non-canonical chain.
