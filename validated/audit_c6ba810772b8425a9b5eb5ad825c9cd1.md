### Title
Peras Certificate Aggregate-Signature Verification (`verifyCert`) Never Invoked in Production Inbound Path — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The `CryptoSupportsVotingCommittee` class defines `verifyCert` for cryptographic aggregate-signature verification of Peras certificates. This method is implemented in both `EveryoneVotes` and `WFALS` committee schemes. However, the production inbound certificate diffusion path calls `validatePerasCert mkPerasParams` — a function that receives only Peras protocol parameters and has no access to the `VotingCommittee` context required to invoke `verifyCert`. As a result, the aggregate signature of every inbound Peras certificate is never checked. An unprivileged peer can send a structurally valid but cryptographically forged certificate that passes validation and is stored in the node's cert database, where it influences Peras-weighted chain selection.

---

### Finding Description

The `CryptoSupportsVotingCommittee` type class declares `verifyCert` as the authoritative check for whether a Peras certificate's aggregate signature is valid:

```haskell
verifyCert ::
  VotingCommittee crypto committee ->
  Cert crypto committee ->
  Either (VotingCommitteeError crypto committee) (NE [EligibilityWitness crypto committee])
``` [1](#0-0) 

This method is fully implemented in both `EveryoneVotes` (`implVerifyCert`) and `WFALS`, where it verifies the BLS aggregate signature over the election ID and candidate using the aggregated public keys of the claimed voters. [2](#0-1) 

The production inbound path for Peras certificates is wired in `NodeToNode.hs`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      ...
``` [4](#0-3) 

`validatePerasCert mkPerasParams` accepts only Peras protocol parameters — it has no `VotingCommittee` argument and therefore **cannot** call `verifyCert`. The aggregate signature over the claimed voter set is structurally impossible to check from within this call. The `processCerts` function then accepts every cert that passes the structural check:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [5](#0-4) 

The accepted `ValidatedPerasCert` is then stored in the `PerasCertDB` and its weight snapshot is used directly in chain selection:

```haskell
, getWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
-- ^ Return the Peras weights in order compare the current selection against
-- potential candidate chains
``` [6](#0-5) 

The same structural gap exists for the vote diffusion path. The vote writer is wired with a hardcoded empty stake distribution, with an explicit TODO acknowledging that the committee selection context is not yet plumbed:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [7](#0-6) 

The certificate path has no equivalent masking: `validatePerasCert mkPerasParams` is called with real parameters, so structurally valid but cryptographically forged certificates pass and are stored.

---

### Impact Explanation

Peras certificates carry aggregate BLS signatures attesting that a quorum of committee members voted for a specific block. These certificates are used to compute `PerasWeightSnapshot`, which boosts the apparent weight of certified chains during chain selection. Because `verifyCert` is never called, an unprivileged peer can craft a certificate that:

1. References any real block (including one on a minority or adversarial fork).
2. Claims any set of voter seat indices.
3. Carries an arbitrary (invalid) aggregate signature.

This certificate passes `validatePerasCert`, is stored as a `ValidatedPerasCert`, and its weight boost is applied during chain selection. The node is thereby made to prefer a non-canonical or adversarially chosen chain over the honest canonical chain, violating Peras chain-selection safety.

**Impact class**: High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is open to every connected peer. No authentication or privilege is required to send a `PerasCert` message. The attacker only needs to:

- Construct a `PerasCert` with a valid round number and a reference to a real (non-canonical) block.
- Populate the voter set with any seat indices present in the stake distribution.
- Supply an arbitrary byte string as the aggregate signature.

The structural checks in `validatePerasCert mkPerasParams` (round number range, block reference format) are trivially satisfiable. The cryptographic check (`verifyCert`) is the only gate that would reject the forgery, and it is never reached.

---

### Recommendation

Wire the `VotingCommittee` context into the certificate inbound path, mirroring the pattern already used in the `CryptoSupportsVotingCommittee` test suite. Concretely:

1. Extract the current `VotingCommittee` from the `ChainDB` (or a dedicated committee-selection component) and pass it to `makePerasCertPoolWriterFromChainDB`.
2. Replace `validatePerasCert mkPerasParams` with a validation function that calls `verifyCert committee cert` and only wraps the result as `ValidatedPerasCert` on `Right`.
3. Apply the same fix to the vote path: replace `pure (PerasVoteStakeDistr mempty)` with the real committee selection context and ensure `verifyVote` is invoked.
4. Add an integration test that sends a cert with a corrupted aggregate signature over the `PerasCertDiffusion` mini-protocol and asserts the peer is disconnected.

---

### Proof of Concept

```
1. Node A connects to malicious peer M over the PerasCertDiffusion mini-protocol.

2. M constructs a PerasCert:
     - electionId  = round R (any valid round number)
     - candidate   = hash of block B' (a minority-fork block)
     - voters      = { seatIndex_1, seatIndex_2, ... }  (any valid seat indices)
     - aggSig      = 0x00...00  (invalid aggregate signature)

3. M sends the cert to Node A via the ObjectDiffusion inbound protocol.

4. Node A calls:
     validatePerasCert mkPerasParams cert
   This checks structural fields only (round range, block reference format).
   It returns Right (ValidatedPerasCert ...) because verifyCert is never called.

5. processCerts stores the ValidatedPerasCert in the PerasCertDB.

6. getWeightSnapshot now includes a Peras weight boost for block B'.

7. During chain selection, Node A computes the Peras-weighted length of the
   chain ending at B' as heavier than the honest canonical chain, and switches
   to the adversarial fork.
```

implVerifyCert ::
  forall crypto.
  CryptoSupportsAggregateVoteSigning crypto =>
  VotingCommittee crypto EveryoneVotes ->
  Cert crypto EveryoneVotes ->
  Either
    (VotingCommitteeError crypto EveryoneVotes)
    (NE [EligibilityWitness crypto EveryoneVotes])
implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
        aggregateVoteVerificationKeys
          (Proxy @crypto)
          voteVerificationKeys
    bimap InvalidCertSignature id $
      verifyAggregateVoteSignature
        (Proxy @crypto)
        aggVerificationKey
        electionId
        candidate
        aggSig

    -- Return the list of voters attesting the election winner
    pure members

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
