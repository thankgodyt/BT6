Audit Report

## Title
Zero-Amount Normalization Check After Irreversible Token Burn/Lock Causes Permanent Fund Loss - (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates a NEAR → foreign-chain transfer with an amount that floor-divides to zero after decimal normalization, their tokens are permanently burned or locked inside `init_transfer_internal` before the zero-amount guard in `sign_transfer` is ever reached. Because `sign_transfer` is gated by `#[trusted_relayer]` and will unconditionally revert on the zero-normalized amount, the `TransferMessage` remains in `pending_transfers` indefinitely with no cancel or refund path available to the user.

## Finding Description

`init_transfer` (L523–600) validates only that `fee < amount`: [1](#0-0) 

It then calls `init_transfer_internal`, which unconditionally burns or locks the full `transfer_message.amount` before returning: [2](#0-1) 

Only later, when a trusted relayer calls `sign_transfer`, does the contract normalize `amount_without_fee` via floor division: [3](#0-2) 

And only then is the zero-amount guard enforced: [4](#0-3) 

Because `sign_transfer` carries `#[trusted_relayer]` (L445–446), the user cannot call it themselves. The relayer's call reverts with `InvalidAmountToTransfer`, the `TransferMessage` is never removed, and the burned/locked tokens are irrecoverable. The `normalize_amount` doc comment even acknowledges this outcome but frames it as acceptable "dust": [5](#0-4) 

The function `remove_transfer_message_without_refund` (called in error paths within `init_transfer_internal`) confirms by name that no refund is issued when a transfer message is removed. [6](#0-5) 

## Impact Explanation

This constitutes **permanent loss of bridged funds** via **decimal/normalization abuse and escrow mis-accounting**, matching the Critical allowed impact class. For any token registered with `origin_decimals = 24` and `dest_decimals = 6` (a supported and documented configuration), any transfer of fewer than `10^18` base units with `fee = 0` results in the full amount being burned or locked on NEAR with zero tokens delivered on the destination chain and no recovery path.

## Likelihood Explanation

The entry point (`ft_transfer_call` → `ft_on_transfer` → `init_transfer`) is fully public and requires no special role. Tokens with large decimal spreads are a supported configuration. A user who miscalculates the minimum viable transfer amount, or who sends a "dust" amount, will silently lose funds. No UI or contract-level guard at the point of token transfer prevents this. The scenario is repeatable by any token holder.

## Recommendation

Add a decimal-normalization check inside `init_transfer`, before `init_transfer_internal` is called, to reject transfers whose `amount_without_fee` normalizes to zero. This mirrors the guard already present in `sign_transfer` but places it at the point where the user's tokens have not yet been touched:

```rust
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This should be inserted in `init_transfer` after the `fee < amount` check at L554–557 and before the call to `init_transfer_internal` at L583.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (diff = 18).
2. User calls `ft_transfer_call` with `amount = 10^17` base units, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (`0 < 10^17`). [1](#0-0) 
4. `init_transfer_internal` burns/locks `10^17` tokens. [2](#0-1) 
5. Trusted relayer calls `sign_transfer`. `normalize_amount(10^17, {origin:24, dest:6}) = 10^17 / 10^18 = 0`. [3](#0-2) 
6. `require!(amount_to_transfer > 0, ...)` reverts. [4](#0-3) 
7. The `TransferMessage` is never removed; the user's `10^17` tokens are permanently burned/locked with no recourse.
