### Title
Any NEAR Account Can Submit a Refund Request with an Arbitrary BTC Refund Address for Unfinalized Deposits - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund` carries no caller-identity check and accepts any `refund_address` when `deposit_msg.refund_address` is `None`. An unprivileged NEAR account can submit a refund request for any deposit UTXO that has not yet been finalized, pointing the BTC payout to an attacker-controlled address. The only on-chain protection is a 14-day timelock (`unsafe_refund_timelock_sec`) during which the DAO can reject the request — mirroring the external report's pattern of relying on an off-chain trusted actor as the sole guard against a reachable on-chain exploit path.

### Finding Description
`request_refund` is a public, payable function with no `#[trusted_relayer]` attribute on the method itself: [1](#0-0) 

The function accepts a caller-supplied `refund_address`. In `request_refund_callback`, the address is validated only when `deposit_msg.refund_address` is `Some(...)`: [2](#0-1) 

When `deposit_msg.refund_address` is `None`, any BTC address passes. The callback then stores the caller-supplied address verbatim in the `RefundRequest`: [3](#0-2) 

`execute_refund` is likewise unrestricted — any NEAR account can call it after the timelock: [4](#0-3) 

The timelock for the unsafe (caller-supplied address) path is `unsafe_refund_timelock_sec` (default 14 days): [5](#0-4) [6](#0-5) 

After the timelock, `execute_refund` builds a refund PSBT paying `refund_amount` to the stored `refund_address` and creates a `BTCPendingInfo` owned by the caller: [7](#0-6) [8](#0-7) 

The caller then signs the transaction via `sign_btc_transaction` and broadcasts it, sending BTC to the attacker-controlled address.

### Impact Explanation
An attacker who successfully executes this path receives the victim's deposited BTC at an address they control. The victim's UTXO is simultaneously marked in `verified_deposit_utxo`, permanently blocking any future `verify_deposit` for that UTXO: [9](#0-8) 

The victim loses their BTC with no on-chain recourse. This matches **Critical — Significant loss or theft of user funds** and **Medium — Bypass of bridge limits or policies** depending on whether the DAO acts in time.

### Likelihood Explanation
The attack requires only:
1. A deposit UTXO that has not yet been finalized (relayer delay, nBTC mint failure that removes the UTXO from `verified_deposit_utxo`, or any window before `verify_deposit` is called).
2. Knowledge of the victim's `deposit_msg` — emitted publicly via `LogDepositAddress` events and derivable from the deposit address.
3. Attaching the required storage deposit for `request_refund`.
4. Waiting 14 days without the DAO rejecting the request.

The 14-day window is the sole on-chain guard. If the DAO is slow, offline, or overwhelmed, the attack succeeds. This is structurally identical to the external report's finding: the codebase relies entirely on an off-chain trusted actor (DAO monitoring) to prevent a reachable on-chain exploit.

### Recommendation
Add an on-chain ownership check in `request_refund`: require that `env::predecessor_account_id() == deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. This ensures only the intended recipient can nominate an arbitrary BTC refund address, eliminating the need to rely solely on DAO monitoring for this path. Alternatively, require `deposit_msg.refund_address` to always be pre-set (non-`None`) so the refund destination is fixed at deposit time and cannot be overridden by a third party.

### Proof of Concept
1. Alice sends BTC to her deposit address derived from `{recipient_id: "alice.near", refund_address: None}`.
2. The relayer has not yet called `verify_deposit` (or the mint failed, removing the UTXO from `verified_deposit_utxo`).
3. Bob calls `request_refund(deposit_msg={recipient_id:"alice.near", refund_address:None}, refund_address="bc1q<bob>", tx_bytes=<alice_tx>, vout=0, proof=<valid_proof>)` with the required storage deposit attached.
4. `request_refund_callback` verifies the proof via the Light Client, finds `deposit_msg.refund_address == None`, accepts Bob's address, and stores the `RefundRequest` with `refund_address = "bc1q<bob>"`.
5. 14 days pass; the DAO does not reject.
6. Bob calls `execute_refund(utxo_storage_key)` — timelock passed, no caller restriction.
7. A refund PSBT is built paying Alice's BTC to `"bc1q<bob>"`. Bob's account owns the `BTCPendingInfo`.
8. Bob calls `sign_btc_transaction`, receives the MPC signature, assembles and broadcasts the transaction.
9. Alice's BTC is transferred to Bob's address. Alice's UTXO is permanently blocked from deposit.

    pub(crate) fn internal_execute_refund(
        &mut self,
        utxo_storage_key: String,
        timelock_sec: u64,
        _chain_specific_data: Option<ChainSpecificData>,
    ) -> PromiseOrValue<()> {
        let refund_request = self.load_refund_request_for_execute(&utxo_storage_key, timelock_sec);
        let RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        } = self.refund_execution_inputs(&refund_request);
        let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);

        let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
        psbt.set_input_utxo(vec![deposit_output]);

        let caller = env::predecessor_account_id();
        self.finalize_refund_with_psbt(
            caller,
            refund_request,
            psbt,
            refund_amount,
            utxo_storage_key,
        );
        PromiseOrValue::Value(())
    }
