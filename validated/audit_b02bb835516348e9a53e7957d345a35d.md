### Title
Peras Quorum Check Bypassed by Missing Stake Normalization in `stakeAboveThreshold` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `stakeAboveThreshold` function, which gates Peras certificate forging, compares a `PerasVoteStake` value directly against a relative quorum threshold (3/4 + safety margin) without enforcing that the vote stake has been normalized to the same unit. The code itself documents this assumption as unverified and unresolved. If `PerasVoteStake` values are populated from absolute ledger stake (as the code comment strongly implies is the current state), any single vote from a registered stake pool would trivially satisfy the quorum check, allowing an unprivileged peer to cause a Peras certificate to be forged for an arbitrary block and boost its chain weight.

---

### Finding Description

**Root cause — `stakeAboveThreshold` in `SupportsPeras.hs`:**

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. That is,
-- both are either absolute or relative (normalized) values. Under the current
-- current implementation of 'PerasParams', this function only makes sense when
-- both values are relative (normalized) values, so we should either normalize
-- the 'PerasVoteStake' before calling this function, or change this function to
-- accept a stake distribution and perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The quorum threshold is a relative value (3/4 = 0.75, plus a safety margin of 0.02, totalling 0.77) set in `mkPerasParams`: [2](#0-1) 

The `PerasVoteStake` type is a bare `Rational` with no unit enforcement: [3](#0-2) 

The comment on `PerasVoteStake` explicitly states there is "no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake," meaning the normalization step is absent.

**Code path to exploitation:**

1. An inbound `PerasVote` arrives from a peer and is processed by `processVotes` in `ObjectPool/PerasVote.hs`. [4](#0-3) 

2. `validatePerasVote` is called. The degenerate production instance accepts the vote if the voter ID is present in the stake distribution, assigning the raw (potentially absolute) stake value directly to `vpvVoteStake` with no normalization: [5](#0-4) 

3. The validated vote is added to the `PerasVoteDB` via `implAddVote`, which calls `updatePerasRoundVoteStates`. [6](#0-5) 

4. Inside `updateCandidateVoteState`, `votesReachQuorum` is called, which sums `vpvVoteStake` values and passes the total to `stakeAboveThreshold`: [7](#0-6) 

5. If the stake values are absolute (e.g., a pool with 1,000,000 Lovelace), the comparison `1000000 >= 0.77` is trivially `True`. Quorum is declared reached, and `forgePerasCert` is called immediately, producing a `ValidatedPerasCert` that boosts the voted block's chain weight.

---

### Impact Explanation

**High — Chain selection manipulation via unauthorized Peras certificate forging.**

A single vote from any registered stake pool (or a peer that knows a registered pool's ID) would immediately satisfy the quorum check if absolute stake values are used. The resulting `ValidatedPerasCert` is stored in the `PerasVoteDB` and applied to chain selection, causing honest nodes to assign elevated chain weight (`perasWeight = 15` by default) to the adversarially chosen block. This lets an unprivileged peer make honest nodes prefer a non-canonical chain beyond the intended Peras security assumptions, directly violating the chain selection invariant.

---

### Likelihood Explanation

**Medium.** The attack requires only that the attacker be a registered stake pool (or know a registered pool's key hash), which is a realistic unprivileged capability on any network where Peras is active. The vulnerability is triggered by a single well-formed vote message. No key compromise, stake majority, or privileged access is required. The likelihood is bounded to Medium because Peras is still under active development and may not yet be enabled on mainnet; however, the code is wired into the production network layer and the vulnerability is present in the current codebase.

---

### Recommendation

1. **Enforce normalization before comparison**: `stakeAboveThreshold` must normalize `PerasVoteStake` to a relative value (dividing by total committee stake) before comparing against the relative quorum threshold. The function signature should be changed to accept the total stake distribution so normalization can be performed internally, or a separate normalization step must be enforced at the call site.

2. **Add a type-level or newtype distinction** between absolute and relative stake to prevent unit confusion at compile time.

3. **Resolve the open TODO** at `SupportsPeras.hs` lines 155–161 before enabling Peras on any network.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Register a stake pool with any positive stake (e.g., 1,000,000 Lovelace).
2. Populate `PerasVoteStakeDistr` with the pool's absolute stake value (as the current code does, since normalization is absent).
3. Send a single `PerasVote` for an arbitrary target block from that pool.
4. Observe that `stakeAboveThreshold` returns `True` immediately (1,000,000 ≥ 0.77).
5. Observe that a `ValidatedPerasCert` is forged for the target block after a single vote, without requiring the intended 3/4 quorum of total committee stake.
6. Observe that honest nodes boost the target block's chain weight by `perasWeight = 15`, causing them to prefer it over competing chains of equal or slightly greater length.
