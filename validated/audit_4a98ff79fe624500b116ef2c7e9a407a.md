### Title
Any NEAR Account Can Call `withdraw_rbf` on Another User's Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` is documented as a user-initiated action to accelerate their own pending withdrawal by increasing the gas fee. However, the function contains no ownership check: any unprivileged NEAR account can invoke it against any other user's pending withdrawal ID, passing attacker-controlled `output` data and using the attacker's own `account_id` as the RBF initiator.

### Finding Description

`withdraw_rbf` is defined without any role guard and without verifying that the caller owns the pending transaction: [1](#0-0) 

```rust
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not pending-info owner
    self.require_pending_sign_capacity(&account_id);  // ← checks caller's quota, not victim's
    self.withdraw_rbf_chain_specific(
        account_id,                          // ← attacker's account passed as owner
        original_btc_pending_verify_id,     // ← victim's pending tx ID
        output,                             // ← attacker-controlled outputs
        chain_specific_data,
    );
}
```

Contrast this with `cancel_withdraw`, which is correctly restricted to `Role::DAO`/`Role::Operator` **and** explicitly fetches the pending info's true owner before proceeding: [2](#0-1) 

```rust
#[access_control_any(roles(Role::DAO, Role::Operator))]
pub fn cancel_withdraw(...) {
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id   // ← correct: reads owner from state
        .clone();
    ...
    self.cancel_withdraw_chain_specific(user_account_id, ...);
}
```

`withdraw_rbf` performs neither check. The `BTCPendingInfo` struct records the true owner in its `account_id` field, but `withdraw_rbf` never reads it. [1](#0-0) 

### Impact Explanation

An attacker who knows (or can enumerate) a victim's `btc_pending_sign_id` can:

1. **Inject an unauthorized RBF** on the victim's in-flight withdrawal, replacing the pending transaction with one whose `output` is attacker-supplied. If `withdraw_rbf_chain_specific` does not re-validate that the new outputs preserve the original recipient address, BTC can be redirected — **Critical: unauthorized redirection of bridge-controlled funds**.
2. Even if output validation prevents full redirection, the attacker can force the victim's withdrawal into an RBF loop, inflating the gas fee deducted from the victim's bridged funds and potentially leaving the withdrawal in a stuck or degraded state — **Medium: attacker-triggered disruption/temporary locking of bridged funds**.
3. The capacity check (`require_pending_sign_capacity`) is performed against the **attacker's** account, not the victim's, so the attacker bypasses the per-account pending-tx limit that is meant to throttle abuse. [3](#0-2) 

### Likelihood Explanation

`withdraw_rbf` is a public, payable-free function with no role restriction. Pending IDs are derived from PSBT content and are observable on-chain via `GenerateBtcPendingInfo` events. Any NEAR account can call this function at any time against any active withdrawal. No privileged access, leaked key, or social engineering is required. [4](#0-3) 

### Recommendation

Add an ownership assertion at the top of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let caller = env::predecessor_account_id();
    // Verify caller owns the pending transaction
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the withdrawal owner can submit an RBF");
    self.require_pending_sign_capacity(&owner);
    self.withdraw_rbf_chain_specific(owner, original_btc_pending_verify_id, output, chain_specific_data);
}
``` [2](#0-1) 

### Proof of Concept

1. Alice calls `ft_transfer_call` → `ft_on_transfer` → withdrawal is created; `GenerateBtcPendingInfo` event emits `btc_pending_id = X` with `account_id = alice`.
2. Attacker observes `X` on-chain.
3. Attacker calls `withdraw_rbf(X, [TxOut { value: ..., script_pubkey: attacker_address }], None)`.
4. Inside `withdraw_rbf`: `account_id = attacker`, capacity check passes against attacker's (empty) quota, `withdraw_rbf_chain_specific(attacker, X, attacker_output, ...)` is invoked.
5. A new RBF pending transaction is created under the attacker's account with attacker-controlled outputs, superseding Alice's original withdrawal. Alice's BTC is now routed through an attacker-authored transaction. [1](#0-0)
