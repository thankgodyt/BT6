### Title
Unconditional `validatePerasCert` Stub Allows Unauthenticated Certificate Injection to Manipulate Peras Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally accepts every inbound certificate without any cryptographic or semantic check. An unprivileged peer can exploit the object diffusion mini-protocol to inject crafted `PerasCert` objects that boost arbitrary blocks, artificially inflating their chain weight and causing the victim node to prefer a non-canonical fork under Peras chain selection. The analog to the external report is direct: just as `selfdestruct` injects ETH to bypass a balance check and manipulate contract state, a peer injects a crafted certificate to bypass certificate validation and manipulate chain-selection weight.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:**

The `BlockSupportsPeras` instance at line 320 of `SupportsPeras.hs` is explicitly labelled "degenerate instance for all blks to get things to compile." Its `validatePerasCert` implementation (lines 353–358) unconditionally returns `Right` for any input, assigning the configured `perasWeight` boost without verifying:

- any cryptographic signature over the certificate,
- the round number's validity or ordering,
- the existence or validity of the claimed boosted block, or
- the quorum of votes that should back the certificate.

```haskell

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params

```

**Production entry path — object diffusion mini-protocol:**

`makePerasCertPoolWriterFromChainDB` (in `PerasCert.hs`, line 126) is the production handler for inbound peer certificates. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

`processCerts` (lines 164–173 of `PerasCert.hs`) calls this validator for every certificate received from a peer. Because the validator always returns `Right`, every certificate passes, is timestamped, and is forwarded to `addPerasCertAsync`.

**Chain-selection manipulation path:**

Once accepted, the certificate flows through `chainSelSync` (`ChainSel.hs` lines 483–532):

1. The certificate is stored in `PerasCertDB` via `PerasCertDB.addCert`.
2. `chainSelectionForBlock` is triggered for the boosted block.
3. `implGetWeightSnapshot` builds a `PerasWeightSnapshot` that includes the fake boost.
4. `weightedSelectView` (`SelectView.hs` lines 104–112) computes `wsvWeightBoost` from this snapshot.
5. `WeightedSelectView.preferCandidate` (lines 81–87) compares `wsvTotalWeight` values; if the adversarial fork's inflated total weight exceeds the honest chain's, `ShouldSwitch` is returned and the node adopts the fork.

Additionally, `forksAtMostKWeight` (`AnchoredFragment.hs` lines 85–89) uses `totalWeightOfFragment` which includes Peras boosts. An attacker can inject certificates boosting blocks on the node's current chain to inflate its suffix weight beyond `k`, causing `forksAtMostKWeight` to return `False` for a legitimate candidate and preventing the node from rolling back to adopt a valid longer chain.

### Impact Explanation

When Peras is enabled, any unprivileged peer can inject certificates that boost blocks on an adversarial fork. Because `validatePerasCert` never rejects any input, the fake certificate is accepted, its weight boost is applied to chain selection, and — if the boost is large enough — the victim node switches to the adversarial fork. This is a **High** chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol. The secondary effect (inflating the current chain's suffix weight to block legitimate rollbacks) further degrades chain-selection correctness.

### Likelihood Explanation

The attack requires only that Peras is enabled and that the attacker can connect as a standard peer — no stake, no keys, no privileged access. The object diffusion mini-protocol is designed to accept certificates from peers, and the validation stub makes no attempt to reject crafted inputs. The `perasWeight` boost value is taken directly from the node's own `PerasParams` configuration, so the attacker does not even need to guess a valid boost magnitude.

### Recommendation

Implement actual cryptographic validation in `validatePerasCert` before enabling Peras in production. At minimum, verify the certificate's aggregate BLS signature against the claimed quorum of committee members using the primitives already present in `Ouroboros.Consensus.Peras.Crypto.BLS`. Until proper validation is implemented, Peras must remain disabled (which is the current default). The tracked issue is https://github.com/tweag/cardano-peras/issues/120.

### Proof of Concept

1. Enable Peras on a private-testnet node (set `eraPerasRoundLength` in `EraParams`).
2. Connect as an unprivileged peer via the standard node-to-node protocol.
3. Send a `PerasCert` via the object diffusion mini-protocol with `pcCertBoostedBlock` pointing to a block on an adversarial fork and `pcCertRound` set to any round number not yet in the `PerasCertDB`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`; the stub returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` unconditionally.
5. The certificate is added to `PerasCertDB`; `addPerasCertAsync` queues it for chain selection.
6. `chainSelSync` triggers `chainSelectionForBlock` for the boosted block; `implGetWeightSnapshot` now includes the fake boost in the `PerasWeightSnapshot`.
7. `weightedSelectView` computes the adversarial fork's `wsvTotalWeight = blockNo + fakeBoost`; `preferCandidate` returns `ShouldSwitch (Heavier ...)` if this exceeds the honest chain's weight.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
