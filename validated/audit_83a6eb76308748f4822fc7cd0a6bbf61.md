### Title
`FixedPoint` Precision Underflow and Hardcoded `boundX` in `localSortitionNumSeats` Causes Incorrect Non-Persistent Seat Counts in Peras Voting Committee — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` contains two precision limitations that are a direct structural analog to the `interestPerSecond` minimum-precision bug in the external report. First, the Poisson parameter `lambda` is computed via `fromRational` into a `FixedPoint` type (34 decimal bits of precision); for voters with sufficiently small stake the conversion underflows to zero and the voter is unconditionally denied all non-persistent seats. Second, the Taylor-expansion error-bound helper `taylorExpCmpFirstNonLower` is called with a hardcoded `boundX = 3`, which is only a valid upper bound for `e^lambda` when `lambda ≤ ln 3 ≈ 1.099`; for any voter whose expected seat count exceeds that threshold the error term is systematically underestimated, potentially causing the algorithm to terminate early with an incorrect seat count. Both defects affect the seat-count value that `implVerifyVote` and `implVerifyCert` in `WFALS.hs` use to accept or reject incoming Peras votes and certificates.

---

### Finding Description

**Root cause 1 — `FixedPoint` underflow (precision floor)**

`lambda` is the expected number of non-persistent seats for a voter:

```haskell
lambda :: FixedPoint
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
```

`FixedPoint` from `Cardano.Ledger.BaseTypes` carries 34 decimal digits of precision (the formal spec states "34 decimal bits … enough to represent the fraction of a single lovelace"). The minimum representable non-zero value is therefore ≈ 10⁻³⁴. When `numNonPersistentVoters * voterStake / totalNonPersistentStake < 10⁻³⁴`, the conversion silently rounds to zero. The guard at line 60 then returns `LocalSortitionNumSeats 0`, permanently excluding the voter from every election in the epoch regardless of their actual positive stake. The code itself documents this:

> "If the voter has stake close to zero, the conversion from 'Rational' to 'FixedPoint' for 'lambda' might underflow to zero"

This is the direct analog of `interestPerSecond = 1` being the minimum non-zero unit: here `FixedPoint`'s LSB is the minimum non-zero `lambda`, creating a hard minimum-stake floor below which a voter is always assigned zero seats.

**Root cause 2 — hardcoded `boundX = 3` incorrect for `lambda > ln 3`**

The seat count is determined by:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- boundX, must equal e^{|x|} = e^lambda for correct bounds
      orders
      (-lambda)
```

The contract of `taylorExpCmpFirstNonLower` requires `boundX = e^{|x|}` (documented at line 121). Since `x = -lambda`, the correct value is `e^lambda`. The hardcoded `3` is only valid when `lambda ≤ ln 3 ≈ 1.099`. For any voter whose `lambda` exceeds this threshold the error term `errorTerm = abs(err' * boundX)` is smaller than the true remainder of the Taylor series. The algorithm may therefore:

- Prematurely declare a threshold "ABOVE" (granting a seat) when the true `e^{-lambda}` is below it, or
- Prematurely declare a threshold "BELOW" (denying a seat) when the true `e^{-lambda}` is above it.

The TODO comment at lines 86–92 explicitly flags this as unresolved:

> "TODO(peras): evaluate whether the limit used below (3) makes sense in this context … Tracked by this issue: https://github.com/tweag/cardano-peras/issues/234"

`lambda > ln 3` is reached whenever a voter holds more than `ln(3) / numNonPersistentVoters` of the total non-persistent stake — e.g., with 100 non-persistent seats, any voter with more than ~1.1 % of the non-persistent stake triggers the incorrect bound.

### Impact Explanation

`localSortitionNumSeats` is called in three places in `WFALS.hs`:

1. `implCheckShouldVote` (lines 285–290) — self-check before forging a vote.
2. `implVerifyVote` (lines 375–390) — verifying an incoming vote from a peer.
3. `implVerifyCert` (lines 528–543) — verifying an incoming certificate from a peer.

In paths 2 and 3 the result directly gates acceptance of a Peras vote or certificate. An incorrect non-zero result where zero is correct causes `implVerifyVote`/`implVerifyCert` to accept a vote or certificate that should be rejected (`ZeroNonPersistentSeats` is the rejection path). An incorrect zero where non-zero is correct causes a legitimate vote or certificate to be rejected. Both directions corrupt the quorum accounting for Peras certificates, which are used to boost chain weight in chain selection. Systematic exclusion of small-stake voters (root cause 1) reduces the effective committee size and can prevent quorum from being reached. Incorrect seat counts for large-lambda voters (root cause 2) distort the voting-weight calculation in `implEligiblePartyVoteWeight` (lines 421–432), since `numSeats` is multiplied directly into the vote weight.

Impact classification: **Medium** — materially weakens Peras vote and certificate authorization without requiring DoS.

---

### Likelihood Explanation

- Root cause 1 (underflow) is triggered by any voter whose `voterStake / totalNonPersistentStake < 10⁻³⁴ / numNonPersistentVoters`. With Lovelace-denominated stake this threshold is reachable for pools with very small but non-zero stake.
- Root cause 2 (incorrect `boundX`) is triggered for any voter with more than ~1.1 % of the non-persistent stake when there are 100 non-persistent seats — a routine scenario. The code's own TODO acknowledges the issue is unresolved.

Both defects are deterministic and reproducible given the same stake distribution and VRF output. They are reachable via any peer that sends a `WFALSNonPersistentVote` or `WFALSCert` message containing a valid VRF output for a voter in the affected stake range.

---

### Recommendation

1. **Avoid `FixedPoint` for `lambda`**: compute `lambda` as an exact `Rational` (or store numerator and denominator separately, as the external report recommends) and only convert to `FixedPoint` at the final comparison step, or use a higher-precision fixed-point type.
2. **Compute `boundX` dynamically**: replace the hardcoded `3` with `exp lambda` (or a safe upper bound derived from `lambda`) so the error bound is always valid.
3. **Add a property test** asserting that `localSortitionNumSeats` agrees with the `Rational`-arithmetic reference model in `Test.Consensus.Committee.WFALS.Model` across the full range of `lambda` values, including `lambda > ln 3`.

### Proof of Concept

**Root cause 1 — underflow:**

Suppose `numNonPersistentVoters = 100`, `totalNonPersistentStake = 10^36` Lovelace, `voterStake = 1` Lovelace.

```
lambda_rational = 100 * 1 / 10^36 = 10^{-34}
```

`FixedPoint` precision is 10⁻³⁴; the conversion rounds to exactly 0. The guard `| lambda <= 0` fires and the voter receives `LocalSortitionNumSeats 0` for every election in the epoch, despite holding positive stake.

**Root cause 2 — incorrect `boundX`:**

Suppose `numNonPersistentVoters = 10`, `voterStake = 50 %` of `totalNonPersistentStake`.

```
lambda = 10 * 0.5 = 5.0
e^lambda = e^5 ≈ 148.4
```

`taylorExpCmpFirstNonLower` is called with `boundX = 3` instead of `148.4`. The error term `errorTerm = abs(err' * 3)` is ~49× smaller than the true remainder `abs(err' * 148.4)`. The algorithm may prematurely classify a threshold as "ABOVE" or "BELOW" before the partial sum has converged, returning a seat count that differs from the mathematically correct value. Since `implEligiblePartyVoteWeight` multiplies `numSeats` directly into the vote weight, even a one-seat error for a 50 %-stake voter produces a proportionally incorrect voting weight in the certificate.
