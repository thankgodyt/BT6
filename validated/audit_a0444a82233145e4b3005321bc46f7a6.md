### Title
Orchard Bundle ZK Proof Not Verified On-Chain Allows Attacker-Triggered Stuck Bridge State - (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary
The Zcash bridge variant accepts user-supplied Orchard bundles and commits to them (MPC-signs the transaction) without ever verifying the Orchard ZK proof on NEAR. Combined with a publicly-known all-zeroes `BRIDGE_OVK`, an unprivileged attacker holding nZEC can craft a structurally valid bundle whose ZK proof is garbage, pass all on-chain validation, force the MPC network to sign the transaction, and then have Zcash reject it — leaving the bridge's UTXOs locked in pending state and requiring operator intervention to recover.

---

### Finding Description

**Root cause 1 — ZK proof is never verified on NEAR.**

`extract_orchard_bundle` in `orchard_policy.rs` calls `read_v5_bundle` (pure deserialization) and then `recover_output_with_ovk` (note decryption). Neither step verifies the Halo2 ZK proof embedded in the bundle. [1](#0-0) 

The `ProofSizeEnforcement::Strict` flag used for Nu6.2 only enforces the byte-length of the proof field; it does not verify proof validity. [2](#0-1) 

**Root cause 2 — `BRIDGE_OVK` is the all-zeroes constant (publicly known).** [3](#0-2) 

Because the OVK is public, any party can construct an Orchard note that decrypts correctly under it, choosing any recipient address and any amount — without needing a valid ZK proof.

**Root cause 3 — Bridge commits to the transaction before Zcash can reject it.**

`validate_orchard_bundle` checks only the recovered recipient and the `value_balance` field of the bundle struct (both of which the attacker controls when the ZK proof is not verified): [4](#0-3) 

After passing these checks, `check_psbt_chain_specific` calls `validate_orchard_bundle` and returns, and the bridge proceeds to MPC-sign the transaction: [5](#0-4) 

Once signed, the UTXOs are moved to the unavailable pool and a `BTCPendingInfo` entry is created. When the transaction is broadcast to Zcash, the network rejects it (invalid proof), but the bridge state is already committed.

---

### Impact Explanation

The bridge's UTXOs are locked in `btc_pending_infos` / `unavailable_utxos` for a transaction that can never confirm on Zcash. Recovery requires the operator to manually cancel each pending withdrawal (via the RBF/cancel flow), returning nZEC to the attacker, who can immediately repeat the attack. An attacker with multiple accounts and a small nZEC balance can continuously saturate the bridge's pending-transaction capacity, degrading or halting normal withdrawals for all users. This matches **Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

- The attacker only needs a small nZEC balance (any bridge user qualifies).
- Constructing a structurally valid Orchard bundle with a garbage proof is straightforward: build a legitimate bundle with the Orchard SDK, then overwrite the proof bytes with arbitrary data of the correct length. The all-zeroes OVK is public, so note encryption is trivial.
- No privileged access, leaked keys, or external dependency compromise is required.
- The attack is repeatable at low cost because nZEC is returned on cancellation.

---

### Recommendation

1. **Add a ZK-proof validity check on NEAR** using the Orchard verifying key before accepting any bundle. If on-chain verification is too expensive, consider a trusted relayer attestation model with economic slashing for invalid proofs.
2. **Replace the all-zeroes `BRIDGE_OVK`** with a key derived from the bridge's MPC root key, so only the bridge can construct recoverable notes. This raises the bar for crafting a plausible-looking malicious bundle.
3. **Add a bundle-validity timeout**: if a signed transaction is not confirmed on Zcash within N blocks, automatically cancel it and return funds, reducing the manual operator burden.
4. **Per-account pending-transaction limits** (if not already enforced) should be verified to cap the blast radius of repeated attacks.

---

### Proof of Concept

```
1. Attacker holds any amount of nZEC.

2. Using the Orchard SDK (e.g., the `orchard` Rust crate):
   a. Build a legitimate Orchard bundle:
      - recipient  = attacker's own Unified Address (Orchard receiver)
      - amount     = withdrawal amount
      - OVK       = [0u8; 32]  (the public BRIDGE_OVK)
   b. Serialize the bundle to bytes.
   c. Locate the Halo2 proof field in the serialized bytes and overwrite it
      with random bytes of the same length (proof size is fixed / enforced).

3. Call ft_transfer_call on the nZEC contract:
   - receiver_id = satoshi-bridge
   - amount      = withdrawal amount
   - msg         = WithdrawMsg { target_btc_address: <attacker UA>,
                                 input: [<bridge UTXO>],
                                 output: [],          // shielded-only
                                 chain_specific_data: { orchard_bundle_bytes: <crafted bundle> } }

4. Bridge flow:
   - ft_on_transfer_callback → PsbtWrapper::new → extract_orchard_bundle
     → read_v5_bundle (deserializes OK, proof not verified)
     → recover_output_with_ovk (decrypts correctly, returns attacker addr + amount)
   - validate_orchard_bundle: recipient ✓, value_balance ✓  → passes
   - create_btc_pending_info: UTXOs moved to unavailable, BTCPendingInfo created
   - sign_btc_transaction: MPC signs the transaction

5. Attacker (or anyone) broadcasts the signed transaction to Zcash.
   Zcash consensus rejects it: invalid Halo2 proof.

6. Bridge UTXOs remain locked. Operator must manually cancel the pending
   withdrawal. Attacker receives nZEC back and repeats from step 3.

pub fn extract_orchard_bundle(
    orchard_bundle_bytes: Option<Vec<u8>>,
    proof_size_enforcement: ProofSizeEnforcement,
) -> Result<Option<ParsedOrchardBundle>, String> {
    if let Some(orchard_bundle_bytes) = orchard_bundle_bytes {
        let mut reader = Cursor::new(orchard_bundle_bytes);
        let bundle = read_v5_bundle(&mut reader, proof_size_enforcement)
            .map_err(|_| "Failed to read orchard bundle".to_string())?
            .ok_or_else(|| "Orchard bundle is empty".to_string())?;

        // Check action count first per Orchard protocol requirements
        if bundle.actions().len() != EXPECTED_ACTIONS_NUMBER {
            return Err(format!(
                "Orchard bundle must have {} actions, got {}",
                EXPECTED_ACTIONS_NUMBER,
                bundle.actions().len()
            ));
        }

        // Since we require exactly 1 action, directly recover the single output
        let ovk = orchard::keys::OutgoingViewingKey::from(BRIDGE_OVK);
        let (note, addr, _memo) = bundle
            .recover_output_with_ovk(0, &ovk)
            .ok_or_else(|| "Failed to recover Orchard output with bridge OVK".to_string())?;

        let value = note.value().inner();
        if value == 0 {
            return Err("Orchard output value must be non-zero".to_string());
        }

        Ok(Some(ParsedOrchardBundle {
            bundle,
            output: OrchardOutput {
                amount: value,
                recipient_addr: addr.to_raw_address_bytes(),
            },
        }))
    } else {
        Ok(None)
    }
}

pub fn validate_orchard_bundle(
    orchard: &ParsedOrchardBundle,
    expected_recipient: &str,
    chain: &Chain,
) -> Result<(), String> {
    let recipient_address = Address::parse(expected_recipient, chain.clone())?;

    // Validate recipient
    let expected_addr_bytes = recipient_address.extract_orchard_receiver()?;
    if orchard.recipient_addr() != &expected_addr_bytes {
        return Err(format!(
            "Orchard recipient mismatch: expected {} does not match recovered output",
            expected_recipient
        ));
    }

    // Validate value balance: for withdrawal, value flows FROM transparent TO Orchard
    // So value_balance should be negative and equal to the output amount
    let value_balance = orchard.bundle.value_balance();
    let expected_value_balance =
        -i64::try_from(orchard.amount()).map_err(|_| "Orchard amount too large for i64")?;

    let actual_value_balance: i64 = (*value_balance).into();
    if actual_value_balance != expected_value_balance {
        return Err(format!(
            "Orchard value balance mismatch: expected {}, got {}. \
             Value balance must equal negative output amount for withdrawals",
            expected_value_balance, actual_value_balance
        ));
    }

    Ok(())
