### Title
Unauthenticated `request_refund` Allows Any Caller to Hijack a Deposit's Refund Destination - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` imposes no check that the caller is the intended beneficiary of the deposit (`deposit_msg.recipient_id`). Any NEAR account can submit a refund request for any unfinalized deposit and supply an arbitrary `refund_address`. Because only one refund request can exist per UTXO, a front-runner who lands first permanently redirects the BTC refund to their own address, blocking the legitimate depositor.

### Finding Description
`request_refund` is a publicly callable, payable function. Its only caller-related guard is a role check that applies exclusively when a custom `gas_fee` is requested. [1](#0-0) 

Inside `internal_request_refund`, the only constraint on `refund_address` is that it must equal `deposit_msg.refund_address` **when that field is `Some`**. When `deposit_msg.refund_address` is `None` — the common case for standard deposits — the caller may supply any BTC address. [2](#0-1) 

There is no statement of the form `require!(env::predecessor_account_id() == deposit_msg.recipient_id, ...)` anywhere in `internal_request_refund` or `request_refund_callback`. [3](#0-2) 

`request_refund_callback` enforces that only one refund request may exist per UTXO: [4](#0-3) 

This "first writer wins" rule is the crux of the vulnerability: whoever submits first owns the `refund_address` field for that UTXO.

`execute_refund` is also publicly callable with no caller restriction; it sends BTC to whatever `refund_address` was stored at request time. [5](#0-4) 

### Impact Explanation
An attacker who front-runs `request_refund` with their own BTC address as `refund_address` causes the bridge's MPC pipeline to sign and broadcast a Bitcoin transaction paying the attacker. The legitimate depositor's BTC is permanently transferred to the attacker. This is a direct, complete theft of user funds — a critical impact.

### Likelihood Explanation
NEAR transactions are publicly visible before finality. Any deposit whose `deposit_msg.refund_address` is `None` (the default for standard deposits) is vulnerable. The attacker only needs to pay the small NEAR storage deposit (`required_balance_for_request_refund`). The `unsafe_refund_timelock_sec` gives DAO/Operator a window to reject, but this is an operational safeguard, not a protocol-level guarantee; a slow or inattentive operator, or a griefing loop where the attacker re-front-runs every new request, leaves the user's funds permanently at risk.

### Recommendation
Add a caller-identity check in `internal_request_refund` (or `request_refund_callback`) that requires `env::predecessor_account_id() == deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. This mirrors the fix applied to `NativeTokenPaymentEnforcer`: bind the refund authorization to the identity of the party whose funds are at stake.


### Proof of Concept

1. Alice deposits 1 BTC with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The deposit is never finalized.
2. Alice calls `request_refund(deposit_msg, "alice_btc_addr", tx_bytes, vout, proof, None)`.
3. Attacker Bob observes Alice's pending NEAR transaction and submits `request_refund(deposit_msg, "bob_btc_addr", tx_bytes, vout, proof, None)` with higher priority (NEAR allows ordering by gas price / nonce).
4. Bob's transaction lands first. `request_refund_callback` stores `RefundRequest { refund_address: "bob_btc_addr", ... }`. [6](#0-5) 

5. Alice's transaction reverts: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (and assuming DAO/Operator does not reject), Bob calls `execute_refund(utxo_storage_key, None)`.
7. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `refund_amount` to `"bob_btc_addr"` and submits it to the MPC signing pipeline. [7](#0-6) 

8. The signed transaction is broadcast; Alice's 1 BTC (minus gas fee) is delivered to Bob.

```rust
    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
```
