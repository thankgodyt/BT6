Audit Report

## Title
`HyperliquedBridgeToken` 3-arg `mint` permanently re-routes bridged funds to `_systemAddress` instead of `payload.recipient` when `finTransfer` carries a non-empty message — (`File: evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary
`HyperliquedBridgeToken` overrides the 3-arg `mint(address, uint256, bytes)` to call `_mint(account, value)` and then immediately `_update(account, _systemAddress, value)`, netting `account` zero tokens and crediting `_systemAddress` with the full amount. `OmniBridge.finTransfer` selects this 3-arg override whenever `payload.message.length != 0`. Any user who includes a non-empty `msg` when initiating a cross-chain transfer to HyperEVM will have their entire bridged amount permanently deposited to `_systemAddress` instead of to themselves.

## Finding Description
`HyperliquedBridgeToken` documents two mint paths: the 2-arg `mint(address, uint256)` (inherited from `BridgeToken`) mints directly to `account` for HyperEVM delivery; the 3-arg `mint(address, uint256, bytes)` override mints to `account` then calls `_update(account, _systemAddress, value)` to park tokens at `_systemAddress` for HyperCore spot-balance tracking. The net ERC-20 effect of the 3-arg override is that `account` ends with a balance of zero and `_systemAddress` holds `value` tokens.

`OmniBridge.finTransfer` checks `customMinters[payload.tokenAddress]` first; because `HyperliquedBridgeToken` is registered via `addCustomToken` with `customMinter = address(0)`, execution falls through to the `isBridgeToken` branch. There, if `payload.message.length == 0` the 2-arg mint is called (correct); if `payload.message.length != 0` the 3-arg mint is called (incorrect for HyperEVM delivery).

On the NEAR side, `sign_transfer` builds `TransferMessagePayload.message` from the user-supplied `msg` field of `InitTransferMsg` via `DestinationChainMsg::from_json(&transfer_message.msg).and_then(|s| s.destination_msg()).unwrap_or_default()`. A user who provides a valid, non-empty `msg` targeting HyperEVM produces a non-empty `message` bytes field in the MPC-signed payload. The relayer then calls `OmniBridge.finTransfer`, which dispatches to `HyperliquedBridgeToken.mint(payload.recipient, payload.amount, payload.message)`, routing all tokens to `_systemAddress`.

Recovery is impossible for the user: `coreReceiveWithData` with `ACTION_TRANSFER` can release tokens from `_systemAddress`, but it is gated to `msg.sender == _systemAddress` — a HyperCore system operation the user cannot invoke.

## Impact Explanation
**Critical — permanent loss of bridged funds.** The recipient receives zero tokens. The full bridged amount accumulates at `_systemAddress` with no user-accessible recovery path. This matches the allowed impact class: *permanent freezing / loss of bridged funds across EVM flows*.

## Likelihood Explanation
The `msg` field in `InitTransferMsg` is a standard, documented, user-facing parameter used for cross-chain message passing (e.g., DeFi composability calls on the destination chain). Any unprivileged user who sets a non-empty `msg` while targeting HyperEVM triggers the loss. No special privileges, front-running, or external compromise is required; the relayer simply finalizes the MPC-signed transfer as normal.

## Recommendation
The 3-arg `mint` override in `HyperliquedBridgeToken` must not re-route tokens away from `account` for the `finTransfer` (HyperEVM delivery) path. The `_update(account, _systemAddress, value)` call is only correct for the HyperCore accounting path, which is handled exclusively via `coreReceiveWithData`. The fix is to remove the `_update` re-route from the `IBridgeToken`-conforming 3-arg `mint` override:

```solidity
function mint(
    address account,
    uint256 value,
    bytes memory
) external override onlyOwner {
    _mint(account, value);
    // Remove: _update(account, _systemAddress, value);
}
```

Alternatively, introduce a dedicated `mintForHyperCore` function used only by `coreReceiveWithData`, and keep both `IBridgeToken`-conforming `mint` overrides free of the `_systemAddress` re-route.

## Proof of Concept
1. User calls `ft_transfer_call` on NEAR targeting HyperEVM with `msg = '{"InitTransfer": {"recipient": "hyp:0xUSER", "fee": "0", "native_token_fee": "0", "msg": "some_dex_call"}}'`.
2. NEAR bridge stores the transfer; `sign_transfer` builds `TransferMessagePayload` with `message = b"some_dex_call"` (non-empty).
3. MPC signs the payload; relayer calls `OmniBridge.finTransfer(signature, payload)` on HyperEVM.
4. `finTransfer` enters the `isBridgeToken` branch; because `payload.message.length != 0`, it calls `HyperliquedBridgeToken.mint(0xUSER, amount, b"some_dex_call")`.
5. Inside `mint`: `_mint(0xUSER, amount)` — user balance = `amount`. Then `_update(0xUSER, _systemAddress, amount)` — user balance = 0, `_systemAddress` balance = `amount`.
6. `0xUSER` receives zero tokens. Funds are permanently stranded at `_systemAddress`.

A minimal Hardhat/Foundry test reproduces this by: deploying `HyperliquedBridgeToken`, registering it via `addCustomToken` with `customMinter = address(0)`, then calling `finTransfer` with a payload whose `message` field is non-empty and asserting `balanceOf(recipient) == 0` and `balanceOf(_systemAddress) == amount`.
