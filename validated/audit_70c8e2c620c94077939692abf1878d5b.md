### Title
Supply Inflation in `safe_mint` When Recipient Account Is Unregistered - (File: contracts/nbtc/src/lib.rs)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints `amount` tokens to the bridge's own balance before checking whether the recipient account is registered. If the account is unregistered, the function returns `U128(0)` without burning the already-minted tokens, permanently inflating `total_supply` by `amount` and leaving those tokens irrecoverably stuck in the bridge's nBTC balance.

### Finding Description
In `safe_mint`, the order of operations is:

1. `self.token.internal_deposit(&self.bridge_id, amount.into())` — unconditionally increases `total_supply` and the bridge's token balance by `amount`.
2. `if self.token.accounts.get(&account_id).is_none() { return PromiseOrValue::Value(U128(0)); }` — if the recipient is unregistered, returns early **without** burning or withdrawing the already-minted tokens. [1](#0-0) 

Because `internal_deposit` has already mutated the nBTC contract's state (both the bridge's account balance and `total_supply`), and NEAR cross-contract call state changes are **not** rolled back when a downstream callback panics, the minted tokens remain in the bridge's balance permanently. The bridge's safe-deposit callback can panic to revert its own state, but it cannot undo the nBTC contract's `internal_deposit`.

This is the direct analog of the reported VotingEscrow bug: just as `_deposit_for` increments `supply` without a prior decrement in `merge`, `safe_mint` increments `total_supply` via `internal_deposit` without a corresponding decrement when the transfer cannot proceed.

### Impact Explanation
Every safe-deposit attempt where the recipient account is unregistered in the nBTC contract results in:
- **Permanent `total_supply` inflation** by `amount` — the circulating supply figure overstates the actual tokens in user hands.
- **`amount` nBTC permanently stuck** in the bridge's own nBTC balance with no automatic recovery path.
- **User's BTC locked** in the bridge's Bitcoin address: the deposit UTXO is marked verified before `safe_mint` is called, blocking any subsequent `request_refund` for that UTXO.

This matches the **Medium** impact class: harmful smart-contract behavior causing permanent supply inflation and stuck bridge state requiring operator intervention. [2](#0-1) 

### Likelihood Explanation
The safe-deposit path (`verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`) is the standard flow for Omni Bridge integrations. Any depositor whose NEAR account has not yet called `storage_deposit` on the nBTC contract — a common situation for first-time users — will trigger this path. The attacker-controlled input is simply the choice not to register storage before depositing BTC. No privileged access is required; any public bridge user can reach `safe_mint` via the relayer-submitted `verify_deposit_v2`. [3](#0-2) 

### Recommendation
Move the account-registration check **before** `internal_deposit` so that no tokens are minted if the transfer cannot proceed:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );

    // Guard BEFORE minting — avoids irrecoverable supply inflation.
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

### Proof of Concept
1. User deposits BTC to the bridge's Bitcoin deposit address (UTXO created on-chain).
2. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)` on the satoshi-bridge.
3. Bridge verifies the BTC transaction via the Light Client and marks the UTXO in `verified_deposit_utxo` (blocking future refunds).
4. Bridge issues a cross-contract call to `nbtc.safe_mint(user_account, amount, msg)`.
5. nBTC contract executes `internal_deposit(&self.bridge_id, amount)` → `total_supply += amount`, bridge nBTC balance `+= amount`. State is committed.
6. nBTC contract checks `self.token.accounts.get(&user_account)` → `None` (user never called `storage_deposit`).
7. nBTC contract returns `PromiseOrValue::Value(U128(0))` to the bridge callback.
8. Bridge callback panics (safe-deposit semantics: "revert on failure") — bridge's own state rolls back, but the nBTC contract's `internal_deposit` is **not** rolled back.
9. **Result**: `amount` nBTC is permanently stuck in the bridge's nBTC balance; `total_supply` is permanently inflated by `amount`; user's BTC UTXO is marked verified and cannot be refunded. [4](#0-3) [5](#0-4)
