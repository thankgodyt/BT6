### Title
Arithmetic Underflow Panic Before Gas-Fee Range Validation in `check_withdraw_psbt` - (File: `contracts/satoshi-bridge/src/psbt.rs`)

### Summary
In `check_withdraw_psbt`, the subtraction `amount - withdraw_fee - gas_fee` (and the subsequent `max_received_amount - config.min_change_amount`) is performed **before** the gas-fee range guard (`gas_fee >= min_btc_gas_fee && gas_fee <= max_btc_gas_fee`). Because the release profile sets `overflow-checks = true`, a user-controlled PSBT with an excessively large implicit gas fee causes a Rust panic/abort at the arithmetic site rather than a clean `require!` rejection. This is the direct analog of the reported pattern: a value check and a subtraction are in the wrong order.

### Finding Description
In `check_withdraw_psbt` (`contracts/satoshi-bridge/src/psbt.rs`):

```
line 238: let gas_fee = total_input_amount - total_output_amount;
line 242: let max_received_amount = amount - withdraw_fee - gas_fee;   // ← subtraction first
line 243: let min_received_amount = max_received_amount - config.min_change_amount; // ← subtraction first
...
line 252: require!(
              gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee, // ← check too late
              ...
          );
```

The gas-fee range check at lines 252–258 is intended to reject PSBTs whose implicit fee is outside `[min_btc_gas_fee, max_btc_gas_fee]`. However, the arithmetic at lines 242–243 executes first. With `overflow-checks = true` (confirmed in `Cargo.toml` line 27), if `withdraw_fee + gas_fee > amount` the subtraction at line 242 panics before the range guard is ever evaluated. Similarly, if `max_received_amount < config.min_change_amount`, line 243 panics.

A user initiating a withdrawal via `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info` → `check_withdraw_psbt_valid` → `check_withdraw_psbt` controls the PSBT `output` vector. By setting the total transparent output value very low (e.g., just at `min_change_amount`), the implicit `gas_fee = total_input_amount - total_output_amount` becomes arbitrarily large, triggering the underflow panic at line 242 before the gas-fee guard fires. ### Impact Explanation
With `panic = "abort"` (also set in the release profile), the NEAR runtime aborts the `ft_on_transfer` cross-contract call. NEAR rolls back all state mutations (including the UTXO removal performed by `generate_vutxos` at line 79 of `token_receiver.rs`), and the NEP-141 `ft_resolve_transfer` callback returns the nBTC tokens to the user. No funds are permanently lost. The impact is a publicly reachable panic-driven fault in the production withdrawal path: the transaction fails with an unhandled abort instead of a clean `require!` error, which is an invariant violation in the bridge's error-handling contract. [4](#0-3) 

### Likelihood Explanation
Any NEAR account holding nBTC can trigger this by calling `ft_transfer_call` with a crafted `Withdraw` message whose `output` vector sums to a value small enough that `total_input_amount - total_output_amount > amount - withdraw_fee`. No privileged role is required. The entry path is fully public. [5](#0-4) 

### Recommendation
Move the gas-fee range check **before** the dependent arithmetic:

```rust
// 1. Compute gas_fee
let gas_fee = total_input_amount - total_output_amount;

// 2. Validate gas_fee range FIRST
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!("Invalid gas fee ({})...", gas_fee)
);

// 3. Now the subtractions are safe
let max_received_amount = amount
    .checked_sub(withdraw_fee)
    .and_then(|v| v.checked_sub(gas_fee))
    .expect("amount too small to cover fees");
let min_received_amount = max_received_amount
    .checked_sub(config.min_change_amount)
    .expect("max_received_amount below min_change_amount");
```

Using `checked_sub` with explicit error messages mirrors the pattern already used in `refund_execution_inputs` (`refund.rs` line 281–283). [6](#0-5) 

### Proof of Concept
1. Bridge has a UTXO of 500 000 sat. Config: `min_btc_gas_fee = 1000`, `max_btc_gas_fee = 100 000`, `min_change_amount = 546`, `withdraw_bridge_fee.fee_min = 1000`, `min_withdraw_amount = 10 000`.
2. Alice holds 10 000 nBTC and calls `ft_transfer_call` with `amount = 10 000` and a `Withdraw` message specifying:
   - `input`: the 500 000-sat UTXO
   - `output`: a single change output of 546 sat (= `min_change_amount`)
3. Inside `check_withdraw_psbt`:
   - `gas_fee = 500 000 − 546 = 499 454` (far above `max_btc_gas_fee`)
   - `max_received_amount = 10 000 − 1 000 − 499 454` → **u128 underflow → panic/abort**
4. The gas-fee guard at line 252 is never reached. The contract aborts, state is rolled back, Alice's tokens are returned — but the abort is an unhandled panic rather than a protocol-level rejection. [7](#0-6)

            amount >= self.internal_config().min_withdraw_amount,

                    amount: U128(amount),

                target_btc_address,
                input,
                output,

                target_btc_address,
                input,
                output,
