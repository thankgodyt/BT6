### Title
Unconditional Peras Certificate Acceptance Bypasses Chain-Selection Authorization — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types unconditionally accepts every inbound Peras certificate as valid. Because this stub is wired into the live certificate-diffusion ingest path, an unprivileged peer can inject a crafted certificate that boosts an arbitrary block, triggering chain selection for a non-canonical fork without any cryptographic authorization.

---

### Finding Description

`BlockSupportsPeras` defines `validatePerasCert` as the hook that must authenticate a certificate before it is stored and acted upon. The only instance in the codebase is the degenerate one that covers every `StandardHash blk`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No check is performed on the certificate's aggregate BLS signature, its round number, or the binding between the claimed boosted-block point and any actual chain state. The function always returns `Right`.

This stub is directly wired into the production certificate-ingest pipeline via `processCerts`, which is called by both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` partitions the result of `validateCert` over the incoming batch; because the stub always returns `Right`, every certificate in every batch is classified as valid and forwarded to `addCert`: [4](#0-3) 

Once stored, the certificate is handed to `ChainDB.addPerasCertAsync`, which calls `chainSelSync`. That function reads `pcCertBoostedBlock` from the certificate and, if the boosted block is present in the `VolatileDB` but not on the current chain, immediately triggers `chainSelectionForBlock` for it: [5](#0-4) 

The `PerasCert` data type carried over the wire contains only `pcCertRound :: PerasRoundNo` and `pcCertBoostedBlock :: Point blk` — both fully attacker-controlled fields with no cryptographic binding enforced at ingest: [6](#0-5) 

The analog to the external report is exact: the external code checks `governor.smart_wallet == smart_wallet` but omits `locker.governor == governor`; here, the code omits **all** checks — neither the aggregate signature nor the round-to-chain binding is verified — so any peer can substitute a fake certificate for a legitimate one.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker who has a block `B` in the target node's `VolatileDB` (obtained via normal block diffusion) can craft a `PerasCert` claiming to boost `B` with an arbitrarily large `perasWeight`. Because `validatePerasCert` never rejects anything, the certificate is stored and chain selection is triggered for `B`. The Peras boost weight is added to `B`'s chain fragment, potentially making it preferred over the node's current canonical chain. This violates the Peras security assumption that only a quorum of authorized committee members can boost a block.

---

### Likelihood Explanation

**Medium.** The Peras certificate diffusion mini-protocol (`ObjectDiffusion`) must be active and reachable from an unprivileged peer. The code is present and wired into the production `ChainDB` path. Whether the protocol is currently enabled on mainnet depends on deployment configuration not visible in this repository, but the vulnerable code path is unconditional once the protocol is active. No special privileges, keys, or stake are required — only the ability to send a well-formed CBOR-encoded `PerasCert` message.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the committee's aggregate verification key for that round.
2. Checks that `pcCertRound` falls within the expected range relative to the current chain tip.
3. Checks that `pcCertBoostedBlock` refers to a block that is a valid candidate for boosting (i.e., it is on a chain that extends the most recently certified block).

Until the real implementation is ready, the ingest path should reject all inbound certificates rather than accept them unconditionally, or the diffusion protocol should be gated behind a feature flag that is disabled by default.

---

### Proof of Concept

1. Node **N** has block **B** (on a minority fork) in its `VolatileDB`.
2. Attacker peer **A** connects to **N** via the Peras certificate diffusion mini-protocol.
3. **A** sends a `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B) }` with no valid BLS signature.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB` and `ChainDB.addPerasCertAsync` is called.
6. `chainSelSync` finds **B** in the `VolatileDB`, calls `chainSelectionForBlock` for **B**.
7. Chain selection adds `vpcCertBoost` to **B**'s fragment weight; if this exceeds the current chain's weight, **N** switches to the minority fork containing **B**.
8. **N** now considers an unauthorized, non-canonical chain as its preferred chain.
