### Title
Excess NEAR Attached to `request_refund` and `execute_refund` Is Permanently Locked in the Bridge Contract — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

### Summary
The `request_refund` and `execute_refund` payable entry points on the `satoshi-bridge` contract enforce a minimum `attached_deposit` but impose no upper bound. Any NEAR sent above the minimum is silently absorbed into the contract's raw balance with no refund path and no general NEAR-withdrawal mechanism, permanently locking the excess.

### Finding Description
`request_refund` is a `#[payable]` function publicly callable by any NEAR account. Its only deposit guard is:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_request_refund(),
    "Insufficient deposit for storage"
);
``` [1](#0-0) 

`required_balance_for_request_refund()` returns a fixed 2 NEAR. [2](#0-1) 

`execute_refund` has the same pattern via `resolve_execute_refund_timelock`, which requires 1 NEAR:

```rust
require!(
    env::attached_deposit() >= self.required_balance_for_execute_refund(),
    "Insufficient deposit for storage"
);
``` [3](#0-2) 

Neither function refunds any amount above the minimum, and neither function has an upper-bound check. The only NEAR-withdrawal function in the contract is `withdraw_protocol_fee`, which exclusively drains the bookkeeping field `cur_available_protocol_fee` — it has no visibility into the contract's raw NEAR balance and cannot recover excess deposits:

```rust
pub fn withdraw_protocol_fee(&mut self, amount: Option<U128>) -> Promise {
    assert_one_yocto();
    let total_protocol_fee = self.data().cur_available_protocol_fee;
    ...
}
``` [4](#0-3) 

There is no `withdraw_near`, `rescue`, or equivalent function anywhere in the bridge contract.


### Impact Explanation
Any NEAR sent above the required minimum to `request_refund` (≥ 2 NEAR) or `execute_refund` (≥ 1 NEAR) is permanently locked in the bridge contract with no recovery path. The `withdraw_protocol_fee` function cannot access this balance. This constitutes permanent loss of user funds with no operator intervention possible.

This maps to the allowed impact: **Medium — harmful smart-contract behavior without direct funds theft, including permanent locking of user funds with no recovery mechanism.**

### Likelihood Explanation
Both `request_refund` and `execute_refund` are publicly reachable by any NEAR account. A user who mistakenly attaches 5 NEAR instead of 2 NEAR (e.g., following a stale UI, script error, or wallet default) loses the excess permanently. The permissionless nature of these endpoints and the absence of any upper-bound guard or refund logic make this straightforwardly reachable.

### Recommendation
1. Add an exact-match or upper-bound check and refund any excess `attached_deposit` back to `env::predecessor_account_id()` at the start of both functions, analogous to the NEP-145 storage-deposit pattern.
2. Alternatively, add a privileged `withdraw_near(amount)` function (DAO-gated) that can drain the contract's raw NEAR balance to recover accidentally locked funds.

### Proof of Concept
1. Alice calls `request_refund` with `attached_deposit = 10 NEAR` (minimum is 2 NEAR).
2. The check `env::attached_deposit() >= 2 NEAR` passes.
3. The function proceeds normally; no refund of the 8 NEAR surplus is issued.
4. The bridge contract's raw NEAR balance increases by 10 NEAR, but `cur_available_protocol_fee` is unchanged.
5. `withdraw_protocol_fee` cannot access the 8 NEAR surplus.
6. The 8 NEAR is permanently locked with no recovery path for Alice or the DAO. [1](#0-0) [2](#0-1) [4](#0-3)

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
```

    pub fn withdraw_protocol_fee(&mut self, amount: Option<U128>) -> Promise {
        assert_one_yocto();
        let total_protocol_fee = self.data().cur_available_protocol_fee;
        let amount = amount.map_or(total_protocol_fee, |v| v.0);
        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
        self.internal_withdraw_protocol_fee(amount)
    }
