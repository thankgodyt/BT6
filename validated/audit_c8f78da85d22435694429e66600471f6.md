Audit Report

## Title
Silent `ft_transfer` Failure Permanently Freezes Bridged Funds — (File: near/omni-bridge/src/lib.rs)

## Summary

`fin_transfer_send_tokens_callback` delegates failure detection entirely to `is_refund_required`, which unconditionally returns `false` when `is_ft_transfer_call = false`. Because `is_ft_transfer_call` is `false` for every plain `ft_transfer` delivery (non-deployed token, empty `msg`), a failed `ft_transfer` promise is never detected. The callback pays the relayer fee, emits `FinTransferEvent`, and leaves the transfer ID permanently in `finalised_transfers`, consuming the proof and freezing the bridged tokens inside the contract with no recovery path.

## Finding Description

`process_fin_transfer_to_near` calls `add_fin_transfer` at line 1875, inserting the transfer ID into `finalised_transfers` before the promise chain is constructed. It then calls `send_tokens`, which — for a non-deployed token with an empty `msg` — issues a plain `ft_transfer` at lines 2102–2106. The flag passed to the callback is `!msg.is_empty()` (line 1973), so `is_ft_transfer_call = false`.

Inside `fin_transfer_send_tokens_callback`, the sole gate for the failure path is:

```rust
if Self::is_refund_required(is_ft_transfer_call) { … }
```

`is_refund_required` at lines 1784–1803 reads:

```rust

    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) { … }
    } else {
        // Not ft_transfer_call: don't refund
        false   // ← promise result is NEVER inspected
```

When `is_ft_transfer_call = false`, the function returns `false` regardless of the underlying promise outcome. The callback therefore always falls into the `else` branch (lines 1719–1746), which mints/transfers the fee to the relayer and emits `FinTransferEvent`. `remove_fin_transfer` (line 1714) is only reachable through the refund branch, so the transfer ID remains in `finalised_transfers` permanently. Any subsequent attempt to replay the same proof is rejected by `add_fin_transfer`'s `require!` at line 2228–2230 with `BridgeError::TransferAlreadyFinalised`. ## Impact Explanation

**Critical — permanent freezing of bridged funds.** When `ft_transfer` fails, the bridged tokens remain locked inside the bridge contract with no mechanism to recover them. The cross-chain proof is consumed (transfer ID permanently in `finalised_transfers`), so the same proof cannot be re-submitted. The recipient receives nothing, the relayer is paid as if the transfer succeeded, and there is no admin escape hatch or retry function in the contract. This directly matches the allowed Critical impact: *permanent freezing of bridged funds across NEAR*.

## Likelihood Explanation

**Medium.** The trigger requires a non-deployed (locked) token whose contract implements an on-chain denylist — USDC, USDT, and WBTC all qualify — and a NEAR recipient account that is on that denylist. No privileged access is required. Any user who initiates a cross-chain transfer to a blacklisted NEAR address, or whose address is blacklisted after the source-chain transaction is confirmed, will trigger this path. The condition is externally observable and can be induced without any special capability.

## Recommendation

`is_refund_required` must inspect the promise result for the plain `ft_transfer` path. The fix is to call `env::promise_result_checked` unconditionally and treat a failed promise as requiring a refund:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Err(_) => true,  // ft_transfer or ft_transfer_call panicked → refund/burn
        Ok(value) if is_ft_transfer_call => {
            near_sdk::serde_json::from_slice::<U128>(&value)
                .map_or(false, |a| a.0 == 0)
        }
        Ok(_) => false,  // ft_transfer succeeded
    }
}
```

This ensures a failed `ft_transfer` triggers `burn_tokens_if_needed`, `revert_lock_actions`, and `remove_fin_transfer`, allowing the proof to be re-submitted after the underlying issue is resolved and preventing silent fund loss.

## Proof of Concept

**Precondition:** USDC is a non-deployed (locked) token on the NEAR bridge. `alice.near` is on USDC's on-chain denylist.

1. Alice initiates a transfer of 1000 USDC from Ethereum to `alice.near` via `OmniBridge.sol::initTransfer`.
2. A relayer generates a proof and calls `fin_transfer` on the NEAR bridge with valid `prover_args` and empty `msg`.
3. `process_fin_transfer_to_near` calls `add_fin_transfer`, inserting the transfer ID into `finalised_transfers` (line 1875).
4. `send_tokens` issues `ft_transfer(alice.near, 1000 USDC)` on the USDC token contract (lines 2102–2106).
5. The USDC contract panics because `alice.near` is blacklisted; the promise result is `Failed`.
6. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` at line 1802 without reading the promise result.
8. The callback enters the `else` branch: mints fee tokens to the relayer, emits `FinTransferEvent` (lines 1719–1745).
9. The transfer ID remains in `finalised_transfers`; any retry is rejected with `TransferAlreadyFinalised`.
10. 1000 USDC remain locked in the bridge contract. Alice receives nothing. Funds are permanently frozen.

A local integration test can reproduce this by deploying a mock USDC token contract that panics on `ft_transfer` for a specific account, submitting a `fin_transfer` proof targeting that account, and asserting that (a) the callback emits `FinTransferEvent`, (b) the transfer ID is still present in `finalised_transfers`, and (c) a second `fin_transfer` call with the same proof is rejected.
