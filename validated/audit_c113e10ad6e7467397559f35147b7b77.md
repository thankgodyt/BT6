### Title
Unchecked u128 Multiplication Overflow in `denormalize_amount` Permanently Freezes Inbound Bridged Funds — (`near/omni-bridge/src/lib.rs`)

### Summary

`denormalize_amount` performs a plain `u128` multiplication (`amount * 10_u128.pow(diff_decimals)`) with no overflow guard. When a user initiates a large but valid inbound transfer from an EVM chain, the NEAR-side `fin_transfer_callback` calls this function and panics (overflow-checks enabled) or silently wraps (overflow-checks disabled), permanently freezing the user's funds or crediting a wrong amount.

### Finding Description

`denormalize_amount` is defined as:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← unchecked multiplication
}
``` [1](#0-0) 

The `amount` argument is the **normalized** value carried in `InitTransferMessage.amount` (a `U128`). The EVM bridge contract accepts amounts up to `uint128::MAX` (≈ 3.4 × 10³⁸). After on-chain normalization (dividing by `10^diff_decimals`), the normalized value can still be as large as `uint128::MAX`. When NEAR multiplies it back by `10^diff_decimals`, the product exceeds `u128::MAX` and overflows.

Concrete example with `origin_decimals = 24`, `decimals = 18` (`diff = 6`):

| Value | Number |
|---|---|
| Safe upper bound for `amount` | `u128::MAX / 10^6 ≈ 3.4 × 10³²` |
| Maximum EVM-side normalized amount | `u128::MAX ≈ 3.4 × 10³⁸` |
| Overflow zone | any normalized amount > `3.4 × 10³²` |

`denormalize_amount` is called in three critical paths:

1. **`fin_transfer_callback`** (line 725) — inbound transfer finalization (Foreign → NEAR): [2](#0-1) 

2. **`fast_fin_transfer`** (line 771) — fast-transfer path: [3](#0-2) 

3. **`claim_fee_callback`** (line 1122) — fee-claim path: [4](#0-3) 

`denormalize_fee` also delegates to `denormalize_amount`, so the fee field is equally affected: [5](#0-4) 

### Impact Explanation

**If Rust overflow-checks are enabled (panic on overflow):** `fin_transfer_callback` panics. Because this is a NEAR callback, the state changes of the callback are reverted, but the proof has already been consumed and the source-chain tokens are already locked or burned. The transfer is permanently stuck — the user loses their funds with no recovery path. This is **permanent freezing of bridged funds**.

**If overflow-checks are disabled (wrapping arithmetic):** The denormalized amount wraps to a small incorrect value. The user receives far fewer tokens than they deposited on the source chain. This is **balance manipulation / escrow mis-accounting**.

Both outcomes fall within the critical impact scope.

### Likelihood Explanation

Any unprivileged user who initiates a transfer on an EVM chain with a normalized amount exceeding `u128::MAX / 10^diff_decimals` triggers this. For tokens with `diff_decimals ≥ 6` (e.g., a 24-decimal origin token bridged to an 18-decimal EVM token), the overflow threshold is `≈ 3.4 × 10³²` in normalized units — reachable with a sufficiently large but valid `uint128` transfer. No special role or privilege is required; the attacker is simply a token holder initiating a standard bridge transfer.

### Recommendation

Replace the unchecked multiplication with a checked or saturating variant and propagate the error:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> Option<u128> {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount.checked_mul(10_u128.pow(diff_decimals))
}
```

All call sites (`fin_transfer_callback`, `fast_fin_transfer`, `claim_fee_callback`, `denormalize_fee`) must handle the `None` case by returning a user-facing error rather than panicking, and must ensure any locked/burned source-chain tokens are refunded or the transfer is rolled back safely.

### Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff_decimals = 6`).
2. On the EVM chain, call `initTransfer` with `amount = u128::MAX` (valid `uint128`).
3. A relayer submits the proof to NEAR `fin_transfer`.
4. `fin_transfer_callback` calls `denormalize_amount(u128::MAX, decimals)`.
5. The multiplication `u128::MAX * 10^6` overflows `u128`.
6. With overflow-checks on: the callback panics → transfer permanently frozen, funds lost.
7. With overflow-checks off: the callback stores a wrapped (near-zero) amount → user receives almost nothing while source-chain tokens are burned.

The existing unit test `test_denormalize_amount` confirms the function is exercised with `u64::MAX` inputs and large multipliers, but does **not** test the overflow boundary: [6](#0-5)
