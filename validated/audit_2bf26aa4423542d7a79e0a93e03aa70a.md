### Title
Unconditional Peras Certificate Acceptance Bypasses Chain-Selection Weight Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, regardless of content. When Peras is enabled, any unprivileged peer can inject arbitrarily crafted `PerasCert` objects through the object-diffusion mini-protocol. Each accepted certificate adds a configurable weight boost (`PerasWeight 15` by default) to an attacker-chosen block, allowing the peer to make the local node prefer a non-canonical or adversarially-controlled chain over the honest chain.

---

### Finding Description

**Root cause — stub validator always succeeds**

The degenerate `BlockSupportsPeras` instance, which is the only instance compiled for all block types, contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The `PerasCert` data type itself carries no cryptographic proof — only a round number and a boosted block point:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

**Production inbound path uses the stub**

`makePerasCertPoolWriterFromChainDB` — the production writer wired to the ChainDB — passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
processCerts
  systemTime
  (ChainDB.getPerasCertIds chainDB)
  -- TODO replace when actual plumbing is in place
  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)
  certs
``` [3](#0-2) 

`processCerts` partitions the results of `validateCert` and adds all `Right` results to the database. Because the stub always returns `Right`, every inbound certificate is accepted: [4](#0-3) 

**Chain selection consumes the injected weight**

Once a `ValidatedPerasCert` is stored, `chainSelSync` triggers `chainSelectionForBlock` for the boosted block: [5](#0-4) 

Chain selection reads the `PerasWeightSnapshot` and computes `wsvTotalWeight = BlockNo + ΣweightBoosts`. The `WeightedSelectView` `ChainOrder` instance switches to a candidate whenever its total weight exceeds the current chain's: [6](#0-5) 

**Attack sequence**

1. Attacker connects as an unprivileged peer to a node with Peras enabled.
2. Attacker crafts one or more `PerasCert` messages, each naming a block on an adversarial fork as `pcCertBoostedBlock`.
3. The object-diffusion inbound handler calls `processCerts` → `validatePerasCert` → always `Right`.
4. Each accepted certificate adds `PerasWeight 15` to the adversarial block's weight in the `PerasWeightSnapshot`.
5. Sending N certificates for N distinct blocks on the adversarial fork accumulates N × 15 weight units.
6. Chain selection now computes `TotalWeight(adversarial) = BlockNo + N×15 > TotalWeight(honest)` and switches.

---

### Impact Explanation

An unprivileged network peer can cause an honest node to abandon the canonical chain and adopt an adversarially-controlled fork by injecting structurally valid but cryptographically unverified Peras certificates. Because weight accumulates additively across all boosted points on a fragment, the attacker can overcome an arbitrarily large block-number deficit on the adversarial chain by sending enough certificates. This constitutes a **chain-selection safety failure** matching the "High" impact category (unprivileged peer makes an honest node prefer a non-canonical chain beyond intended security assumptions) and potentially "Critical" (bypass of Peras certificate checks enabling unauthorized certificate acceptance).

---

### Likelihood Explanation

Peras is disabled by default; the CHANGELOG explicitly notes "if Peras is disabled (which is the default), there is no observable difference." However, the feature is designed to be operator-enabled via `rnFeatureFlags`, and the full object-diffusion mini-protocol infrastructure for receiving peer certificates is already wired into the production `NodeKernel`. Once a node operator enables Peras, every connected peer can immediately exploit this with zero additional privilege. The TODO comments and linked issue (`cardano-peras/issues/120`) confirm the stub is a known incomplete placeholder, not a deliberate design choice.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` before Peras is enabled in any production or pre-production environment. The validation must verify the aggregate BLS/committee signature over the `(electionId, candidate)` pair using the stake distribution from the ledger view, analogous to how `implVerifyCert` works in `Ouroboros.Consensus.Committee.WFALS` and `EveryoneVotes`.
2. **Gate the object-diffusion inbound handler** so that `processCerts` is unreachable when Peras is disabled, preventing the stub from being exercised even in the default configuration.
3. **Remove or replace the degenerate `instance StandardHash blk => BlockSupportsPeras blk`** with a compile-time error or a `Void`-returning stub that cannot be called, forcing each concrete block type to supply a real implementation before the feature can be activated.

---

### Proof of Concept

With Peras enabled, an attacker peer constructs and sends the following over the object-diffusion mini-protocol:

```
PerasCert
  { pcCertRound      = PerasRoundNo <any_round>
  , pcCertBoostedBlock = BlockPoint <slot> <hash_of_adversarial_block>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }
```

unconditionally. The certificate is stored and `addPerasCertAsync` triggers `chainSelectionForBlock` for the adversarial block. Repeating this for every block on the adversarial fork accumulates enough weight to satisfy `preferCandidate` and cause the node to switch chains. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
