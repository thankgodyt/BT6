### Title
Hardcoded `GAS_FOR_MINT_CALL` (90 Tgas) Is Insufficient to Dispatch User-Specified `post_actions` Gas (up to 130 Tgas), Causing Deposit Failure and Stuck Bridge State - (File: `contracts/satoshi-bridge/src/nbtc/mint.rs`)

---

### Summary

The bridge allocates a fixed 90 Tgas to the `nbtc.mint()` cross-contract call. Inside `mint()`, user-specified `post_actions` are dispatched as detached sub-receipts whose gas is drawn from that same 90 Tgas budget. The bridge's own validation layer permits `post_actions` with a combined gas total of up to 130 Tgas. When a user legitimately specifies post_actions whose total gas exceeds the remaining budget inside `mint()` (~80–85 Tgas after execution overhead), the `mint()` receipt runs out of gas, the mint fails, and the UTXO is removed from `verified_deposit_utxo` without the nBTC ever being issued. The user's BTC is stuck in the deposit address until a manual refund is processed.

---

### Finding Description

**Root cause — gas budget mismatch:**

`internal_mint_promise` in `contracts/satoshi-bridge/src/nbtc/mint.rs` allocates exactly 90 Tgas to the `nbtc.mint()` call:

```rust
pub const GAS_FOR_MINT_CALL: Gas = Gas::from_tgas(90);
// ...
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_MINT_CALL)   // ← hardcoded 90 Tgas
    .mint(recipient_id.clone(), mint_amount, protocol_fee,
          env::signer_account_id(), relayer_fee, post_actions)
``` [1](#0-0) 

Inside `nbtc.mint()`, if `post_actions` is `Some`, a detached call to `handle_post_actions` is scheduled:

```rust
if let Some(post_actions) = post_actions {
    Self::ext(env::current_account_id())
        .handle_post_actions(mint_account_id, post_actions)
        .detach();   // gas drawn from mint()'s 90 Tgas budget
}
``` [2](#0-1) 

Inside `handle_post_actions`, each post_action is dispatched with the user-specified gas:

```rust
Self::ext(env::current_account_id())
    .with_static_gas(gas)   // user-controlled, up to 100 Tgas per action
    .handle_post_action(sender_id.clone(), receiver_id, amount, memo, msg)
    .detach();
``` [3](#0-2) 

In NEAR Protocol, gas for detached sub-receipts is deducted from the current receipt's prepaid gas. The chain is:

```
mint() [90 Tgas]
  └─ handle_post_actions [~80–85 Tgas remaining after mint() overhead]
       ├─ handle_post_action #1 [user gas, e.g. 50 Tgas]
       └─ handle_post_action #2 [user gas, e.g. 50 Tgas]  ← total 100 Tgas > budget
```

**The bridge's own validation explicitly permits this over-budget configuration.** In `contracts/satoshi-bridge/src/deposit_msg.rs`:

```rust
const MAX_TOTAL_POST_ACTIONS_GAS: Gas = Gas::from_tgas(130);
const MAX_PER_POST_ACTIONS_GAS:   Gas = Gas::from_tgas(100);
const MIN_PER_POST_ACTIONS_GAS:   Gas = Gas::from_tgas(30);
``` [4](#0-3) 

`check_deposit_msg` accepts any combination where each action is 30–100 Tgas and the total ≤ 130 Tgas. Two actions at 50 Tgas each (total 100 Tgas) pass validation but exceed the ~80–85 Tgas available inside `mint()`. [5](#0-4) 

**Failure consequence — UTXO removed, deposit lost:**

`verify_deposit_callback` inserts the UTXO into `verified_deposit_utxo` and then calls `internal_mint_promise`. If `mint()` fails, `mint_callback` removes the UTXO:

```rust
} else {
    self.data_mut()
        .verified_deposit_utxo
        .remove(&pending_utxo_info.utxo_storage_key);
}
``` [6](#0-5) 

`internal_set_utxo` is never called on failure, so the bridge holds no record of the UTXO. The user's BTC sits in the deposit address with no corresponding nBTC minted and no UTXO tracked by the bridge. [7](#0-6) 

---

### Impact Explanation

**Medium — stuck bridge state requiring operator intervention.**

- nBTC is never minted for the user's confirmed BTC deposit.
- The UTXO is removed from `verified_deposit_utxo` and never stored in the bridge's UTXO set.
- The user's BTC is locked in the deposit address. Recovery requires the user to submit a `request_refund` and wait for the timelock, then have the operator execute the refund — a multi-step, time-delayed process that is not the normal bridge flow.
- No direct theft occurs, but the deposit is effectively frozen and the bridge enters a broken state for that UTXO.

---

### Likelihood Explanation

**Medium.**

- The feature (`post_actions` with user-specified gas) is documented and intended for dApp integrations.
- Any user who specifies two post_actions with gas ≥ 43 Tgas each (total ≥ 86 Tgas, within the allowed 130 Tgas) will trigger the failure.
- The minimum per-action gas is 30 Tgas, so even a single action at 85+ Tgas can exhaust the budget.
- No malicious intent is required — ordinary dApp users following the bridge's documented API will hit this.

---

### Recommendation

Increase `GAS_FOR_MINT_CALL` to account for the maximum possible post_actions gas budget. The minimum safe value is:

```
GAS_FOR_MINT_CALL ≥ mint_execution_overhead + MAX_TOTAL_POST_ACTIONS_GAS
                  ≥ ~10 Tgas + 130 Tgas = ~140 Tgas
```

Alternatively, compute the gas dynamically based on the actual post_actions gas sum before dispatching the `mint()` call, so the allocated gas always covers the full dispatch chain.

---

### Proof of Concept

1. User constructs a `DepositMsg` with two `PostAction` entries, each specifying `gas: Some(Gas::from_tgas(50))` (total 100 Tgas — within the bridge's 130 Tgas limit and each within the 100 Tgas per-action limit).
2. User sends BTC to the deposit address derived from this `DepositMsg`.
3. Relayer calls `verify_deposit_v2` with the `DepositMsg`.
4. `verify_deposit_callback` runs: UTXO inserted into `verified_deposit_utxo`, `internal_mint_promise` called with `GAS_FOR_MINT_CALL = 90 Tgas`.
5. `nbtc.mint()` executes (~5–10 Tgas overhead), schedules `handle_post_actions` as a detached call with ~80–85 Tgas remaining.
6. `handle_post_actions` attempts to schedule two `handle_post_action` receipts at 50 Tgas each (100 Tgas total) — exceeds available budget; execution fails with out-of-gas.
7. `mint_callback` observes `is_promise_success() == false`, removes UTXO from `verified_deposit_utxo`.
8. No nBTC is minted. No UTXO is stored. User's BTC is stuck in the deposit address.
