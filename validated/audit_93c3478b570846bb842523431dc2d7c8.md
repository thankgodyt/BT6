Audit Report

## Title
Permanent User Fund Loss in `swap_migrated_token` Due to Detached Promise with No Mint-Failure Rollback — (`near/omni-bridge/src/lib.rs`)

## Summary

In `ft_on_transfer`, the `SwapMigratedToken` branch calls `swap_migrated_token(...).detach()` and immediately returns `U128(0)`, unconditionally finalizing the user's old-token transfer before any cross-contract call executes. Because the promise is detached, no callback exists to detect a failed mint. If `new_token.mint` fails for any reason, the user's old tokens are burned with no recovery path, resulting in permanent, irreversible fund loss.

## Finding Description

The `SwapMigratedToken` branch in `ft_on_transfer` (lines 275–279) is:

```rust
BridgeOnTransferMsg::SwapMigratedToken => {
    self.swap_migrated_token(sender_id, token_id, amount)
        .detach();
    PromiseOrPromiseIndexOrValue::Value(U128(0))
}
```

Under the NEP-141 `ft_transfer_call` protocol, the return value of `ft_on_transfer` is the number of tokens to refund to the sender. Returning `U128(0)` means **all transferred tokens are kept by the bridge** — the transfer is finalized before any promise executes. The `.detach()` call severs the promise chain from the return value entirely, so there is no callback registered on the result of `swap_migrated_token`. The burn (`BURN_TOKEN_GAS = 3 TGas`, line 72) and mint (`MINT_TOKEN_GAS = 5 TGas`, line 73) operations execute independently with no success verification. The `migrated_tokens` map (line 241) maps `old_token → new_token` and is populated by a legitimate admin operation. If `new_token.mint(user, amount)` fails, the execution path is: old tokens consumed → old tokens burned → mint fails silently → user receives nothing.

## Impact Explanation

This is a direct, irreversible loss of bridged user funds. Old tokens are permanently destroyed and new tokens are never credited. This matches the Critical impact class: **permanent loss/freezing of bridged funds** across NEAR token migration flows. The loss is not recoverable without a contract upgrade and manual remediation.

## Likelihood Explanation

Any unprivileged token holder can trigger this by calling `old_token.ft_transfer_call(bridge, amount, '{"SwapMigratedToken": null}')` once an admin has populated the `migrated_tokens` map — a routine, expected admin operation. Mint failure is realistic via: (1) the bridge not being set as controller of `new_token`; (2) `new_token` contract being paused; (3) the recipient account lacking storage registration on `new_token`; (4) gas exhaustion — 5 TGas is a tight budget for any non-trivial mint implementation. The exploit is repeatable for every user who calls the migration path while any of these conditions hold.

## Recommendation

Replace the detach-and-return-zero pattern with a sequential promise chain with a callback:

1. Do **not** burn `old_token` until mint is confirmed. The old tokens are already held by the bridge after `ft_transfer_call` — hold them in escrow.
2. Call `new_token.mint(user, amount)`.
3. In the mint callback: on success, burn `old_token`; on failure, call `old_token.ft_transfer(user, amount)` to refund the user.

This ensures atomicity: either the user receives `new_token` and `old_token` is burned, or the user is refunded their `old_token`.

## Proof of Concept

1. Admin calls `migrate_deployed_token(old_token, new_token)` — populates `migrated_tokens`.
2. Deploy a mock `new_token` whose `mint` always panics (or use a real token where the bridge is not the controller).
3. User calls `old_token.ft_transfer_call(bridge, 100, '{"SwapMigratedToken": null}')`.
4. `ft_on_transfer` fires: `swap_migrated_token` promise is detached, `U128(0)` returned.
5. `old_token` finalizes transfer — user's 100 tokens are now in the bridge account.
6. Burn promise executes: bridge's 100 old tokens are burned.
7. Mint promise executes: `new_token.mint` panics — promise fails silently with no callback.
8. **Result**: user's `old_token` balance decreased by 100; `new_token` balance unchanged; funds permanently lost with no on-chain recovery path.
