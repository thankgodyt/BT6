### Title
`validatePerasCert` Stub Unconditionally Accepts All Peras Certificates, Enabling Chain-Selection Manipulation by Any Peer - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate received, regardless of content. Because this function is the sole validation gate in the production inbound-certificate pipeline (`processCerts` → `addPerasCertAsync`), any unprivileged peer can send a crafted `PerasCert` that claims to boost an arbitrary block, bypasses all cryptographic and quorum checks, is stored in the `PerasCertDB`, and triggers chain selection for the boosted block. This allows an adversary to inject unearned Peras weight boosts and steer an honest node toward a non-canonical chain.

### Finding Description

**Root cause — stub validation that always succeeds**

The universal instance for all block types in `SupportsPeras.hs` (lines 350–358) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (declared as `instance StandardHash blk => BlockSupportsPeras blk`), so it applies to all block types including Cardano production blocks.

**Production inbound pipeline uses this stub**

Both production pool writers pass `validatePerasCert mkPerasParams` as the sole validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**`processCerts` has no other validation**

`processCerts` calls `validateCert` on each certificate and, if all return `Right`, adds them to the pool. Since the stub always returns `Right`, every certificate passes:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Chain selection acts on the accepted certificate**

`chainSelSync` in `ChainSel.hs` (lines 483–532) adds the certificate to the `PerasCertDB` and then calls `chainSelectionForBlock` for the boosted block. The only guards are: (1) the boosted block's slot is not older than the immutable tip, (2) the boosted block is not already on the current chain, and (3) the boosted block exists in the `VolatileDB`. None of these verify the certificate's cryptographic authenticity or quorum. [4](#0-3) 

**Peras weight boost magnitude**

The default `perasWeight` is 15 (`PerasWeight 15`). Chain weight is `blockNo + weightBoost`, so a fork that is up to 15 blocks shorter than the canonical chain can be preferred if it carries a forged boost. [5](#0-4) 

### Impact Explanation

An unprivileged peer can forge a `PerasCert` claiming to boost any block that exists in the target node's `VolatileDB`. Because `validatePerasCert` never rejects any certificate, the forged certificate is stored and triggers chain selection. If the boosted block is on a fork, the node may switch to that fork, violating the Peras security assumption that only blocks with a genuine quorum of committee votes receive a weight boost. This is a **bypass of Peras certificate validation** enabling unauthorized chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" and "High: chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain" impact categories.

### Likelihood Explanation

Any peer connected via the object-diffusion mini-protocol can send `PerasCert` messages. No privileged keys, stake, or special role is required. The attacker only needs to know the hash of a valid block already in the target node's `VolatileDB` (easily obtained via `ChainSync`). The attack is deterministic and requires no brute force. Likelihood is **high** whenever Peras is enabled.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real cryptographic and quorum check before the Peras object-diffusion pipeline is activated in production. At minimum, the function must verify:

1. The aggregate BLS signature over the certificate covers the claimed `(electionId, candidate)` pair.
2. The set of signers constitutes a valid quorum (total stake ≥ `perasQuorumStakeThreshold`) drawn from the correct epoch's stake distribution.
3. The certificate's round number is within the valid window (`≤ perasCertMaxRounds` rounds old).

Until a real implementation is in place, the object-diffusion pipeline for Peras certificates must not be activated in any deployment where Peras weight influences chain selection.

### Proof of Concept

1. Node A is running with Peras enabled. Its `VolatileDB` contains block `B` on a fork that is 10 blocks shorter than the canonical chain.
2. Attacker peer constructs `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(B) }` with arbitrary content — no valid aggregate signature, no quorum proof.
3. Attacker sends this certificate via the object-diffusion mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
5. The certificate is added to the `PerasCertDB`; `addPerasCertAsync` is called.
6. `chainSelSync` finds block `B` in the `VolatileDB`, triggers `chainSelectionForBlock` for `B`.
7. The fork containing `B` now has weight `blockNo(B) + 15`. If this exceeds the canonical chain's weight, Node A switches to the fork. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
