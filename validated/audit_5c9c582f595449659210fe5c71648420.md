Audit Report

## Title
`deploy_token` Missing Pause Guard Allows Deployer-Equivalent Action During Emergency Pause — (`solana/programs/bridge_token_factory/src/lib.rs`)

## Summary
The Solana `bridge_token_factory` program's `deploy_token` instruction performs no check against the `config.paused` field. When the admin or pausable admin calls `pause()`, it sets `paused = ALL_PAUSED`, which is defined as only `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED`. Because no `DEPLOY_TOKEN_PAUSED` bit exists and `deploy_token` never reads `config.paused`, any party holding a valid MPC-signed `DeployTokenPayload` can register a new wrapped token on Solana regardless of pause state, bypassing the admin's intended emergency halt.

## Finding Description
**Root cause — missing pause constant and missing guard:**

`constants.rs` defines only two pause bits and `ALL_PAUSED` covers only those two: [1](#0-0) 

`pause.rs` sets `config.paused = ALL_PAUSED`, so calling `pause()` only blocks the two transfer instructions: [2](#0-1) 

`deploy_token` in `lib.rs` reads no pause field — it only verifies the MPC signature and initializes token metadata: [3](#0-2) 

By contrast, `finalize_transfer` and `init_transfer` both enforce their respective bits before proceeding: [4](#0-3) [5](#0-4) 

**Cross-chain inconsistency confirms the design intent:**
The EVM counterpart enforces `whenNotPaused(PAUSED_DEPLOY_TOKEN)` on `deployToken`, and the Starknet counterpart asserts `!_is_paused(@self, PAUSE_DEPLOY_TOKEN)` on its `deploy_token`. The Solana implementation is missing the equivalent guard entirely.

**Exploit flow:**
1. A new token is registered on NEAR via `log_metadata`; the NEAR bridge MPC signs a `DeployTokenPayload` and emits it as a public NEAR event.
2. A relayer (including a custom or adversarial one) observes and caches the `SignedPayload<DeployTokenPayload>`.
3. A security incident is detected; the admin calls `pause()`, setting `paused = ALL_PAUSED`.
4. `init_transfer` and `finalize_transfer` are now blocked.
5. The relayer submits the cached `SignedPayload` to `deploy_token`. The function never reads `config.paused` and succeeds, deploying the new wrapped token on Solana.
6. The admin's emergency pause has not stopped the deployer action; the bridge state has changed in a way the admin explicitly tried to prevent.

`set_paused` / `unpause` in `change_config.rs` allows writing an arbitrary `u8` to `config.paused`, but since `deploy_token` never reads that field, no value the admin writes will stop it: [6](#0-5) 

## Impact Explanation
This is a **pause bypass** that lets an unprivileged external actor (any relayer holding a cached MPC-signed payload) execute a deployer-equivalent action on the bridge while the admin believes all sensitive operations are halted. This matches the allowed critical impact class: *"pause bypass… that lets an attacker execute bridge, token, deployer, relayer, or admin-equivalent actions."* If the pause was triggered precisely because a malicious or erroneous token registration was detected on NEAR, the Solana-side deployment cannot be stopped. The deployed token's on-chain metadata is immutable after deployment, and it becomes immediately mintable via `finalize_transfer` once the pause is lifted.

## Likelihood Explanation
The signed payload is produced by the NEAR bridge's MPC signing flow and broadcast as a public NEAR event. No key material beyond what is already public on NEAR is required. Any relayer — including a custom or adversarial one — who observes the event before the pause is enacted can cache the payload and submit it to Solana after the pause. The window between a NEAR-side `log_metadata` event and an admin pause is realistic in incident-response scenarios. The call requires no special on-chain privileges beyond possessing the already-public signed payload.

## Recommendation
1. Add `pub const DEPLOY_TOKEN_PAUSED: u8 = 1 << 2;` to `constants.rs`.
2. Update `ALL_PAUSED` to `INIT_TRANSFER_PAUSED | FINALIZE_TRANSFER_PAUSED | DEPLOY_TOKEN_PAUSED`.
3. Add the pause guard to `deploy_token` in `lib.rs`, consistent with `finalize_transfer` and `init_transfer`:

```rust
pub fn deploy_token(
    ctx: Context<DeployToken>,
    data: SignedPayload<DeployTokenPayload>,
) -> Result<()> {
    require!(
        ctx.accounts.common.config.paused & DEPLOY_TOKEN_PAUSED == 0,
        error::ErrorCode::Paused
    );
    msg!("Deploying token");
    data.verify_signature((), &ctx.accounts.common.config.derived_near_bridge_address)?;
    ctx.accounts.initialize_token_metadata(data.payload)?;
    Ok(())
}
```

## Proof of Concept
**Local integration test plan:**
1. Deploy the `bridge_token_factory` program on a local validator (e.g., `anchor test` or `solana-test-validator`).
2. Initialize the program; obtain a valid MPC-signed `DeployTokenPayload` (can be constructed with a test keypair substituted for `derived_near_bridge_address`).
3. Call `pause()` as the pausable admin; assert `config.paused == ALL_PAUSED`.
4. Verify that `init_transfer` and `finalize_transfer` return `ErrorCode::Paused`.
5. Submit the cached `SignedPayload<DeployTokenPayload>` to `deploy_token`; observe that it **succeeds** and the wrapped mint account is created — confirming the pause bypass.
6. Apply the fix (add the `require!` guard); repeat step 5 and confirm it now returns `ErrorCode::Paused`.
