Looking at the RBF and cancellation mechanisms in the bridge contract, I need to examine the access control on `cancel_withdraw` and whether any unprivileged user can front-run a user's withdrawal.

### Title
Unrestricted `cancel_withdraw` Allows Any Caller to Force-Cancel Another User's Pending Withdrawal After Timeout - (File: contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs)

### Summary
The `internal_cancel_withdraw` function ignores its `_account_id` parameter entirely and imposes no caller-identity check. After `max_btc_tx_pending_sec` elapses, any unprivileged NEAR account can supply a valid cancel PSBT and force-cancel another user's pending withdrawal. The cancel RBF redirects the user's BTC to the bridge's internal change address and deducts the cancel gas fee from the user's `transfer_amount`, causing involuntary fund redirection and fee loss without any attacker-side financial incentive check.

### Finding Description
In `internal_cancel_withdraw` the first parameter is declared `_account_id: &AccountId` — the leading underscore signals it is intentionally unused and no identity assertion is ever made against it:

```rust
pub fn internal_cancel_withdraw(
    &mut self,
    _account_id: &AccountId,          // ← never read
    original_btc_pending_verify_id: String,
    cancel_withdraw_rbf_psbt: PsbtWrapper,
    predecessor_account_id: AccountId, // only used for the DAO excess-fee guard
) -> String {
``` [1](#0-0) 

The only temporal guard is:

```rust
require!(
    nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
        > self.internal_config().max_btc_tx_pending_sec,
    "Please wait user rbf"
);
``` [2](#0-1) 

`create_time_sec` is the timestamp of the **original** withdrawal, not of any subsequent user RBF. So even if the user has already bumped fees via `withdraw_rbf`, the timeout window is still measured from the original creation time, and an attacker can race to call `cancel_withdraw` the moment the window opens.

By contrast, `internal_withdraw_rbf` correctly enforces ownership:

```rust
require!(
    &original_tx_btc_pending_info.account_id == account_id,
    "Not allow"
);
``` [3](#0-2) 

No equivalent check exists in `internal_cancel_withdraw`.

When the cancel succeeds, the accounting sets:

```rust
btc_pending_info.burn_amount = gas_fee;
btc_pending_info.actual_received_amount = actual_received_amount;
``` [4](#0-3) 

The gas fee is deducted from the user's `transfer_amount`, and the remaining BTC is swept to the bridge's change address. The original withdrawal is permanently marked cancelled via `do_cancel`:

```rust
self.internal_unwrap_mut_btc_pending_info(&original_btc_pending_verify_id)
    .do_cancel(gas_fee, excess_gas_fee);
``` [5](#0-4) 

All inputs to construct a valid cancel PSBT (UTXOs, change address, amount bounds) are readable from public contract view functions, so the attacker has everything needed to craft the required `cancel_withdraw_rbf_psbt`.

### Impact Explanation
Any unprivileged NEAR account can, after `max_btc_tx_pending_sec`, force-cancel any user's pending withdrawal. The user's BTC is redirected to the bridge's internal change address and the cancel gas fee is deducted from their `transfer_amount`. The user's nBTC remains locked in the bridge until the cancel RBF is verified on-chain, after which they must re-initiate the withdrawal and pay a new withdrawal fee. During a BTC fee spike the cancel gas fee can be substantial. This constitutes attacker-triggered temporary locking of bridged funds and involuntary fee extraction from the victim.

**Allowed impact matched:** Medium — "Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds."

### Likelihood Explanation
The attack is reachable by any NEAR account with no special role. The only prerequisite is waiting for `max_btc_tx_pending_sec` to elapse and constructing a valid cancel PSBT from publicly visible contract state. No privileged access, leaked keys, or external dependency compromise is required. The attack is most profitable (highest gas fee extracted from victim) during BTC fee spikes, which are the exact scenario where users are most likely to have stuck withdrawals.

### Recommendation
Add an explicit caller check in `internal_cancel_withdraw` mirroring the one in `internal_withdraw_rbf`. Restrict cancellation to the original withdrawal owner, or to accounts holding the `Operator` or `DAO` role:

```rust
require!(
    &original_tx_btc_pending_info.account_id == account_id
        || self.acl_has_role(Role::Operator.into(), predecessor_account_id.clone())
        || self.acl_has_role(Role::DAO.into(), predecessor_account_id.clone()),
    "Not allowed to cancel"
);
```

### Proof of Concept
1. Alice calls `ft_transfer_call` to bridge 1 BTC → nBTC is held by the bridge, a `BTCPendingInfo` (id `tx_0`) is created with `create_time_sec = T`.
2. A BTC fee spike causes `tx_0` to remain unconfirmed. Alice calls `withdraw_rbf` to bump the fee; a new `BTCPendingInfo` (`tx_rbf_1`) is created, but `tx_0` remains in `WithdrawOriginal / PendingVerify` with `create_time_sec = T`.
3. At time `T + max_btc_tx_pending_sec + 1`, Bob (any NEAR account) reads the UTXOs from `tx_0` via a view call, constructs a valid cancel PSBT that spends those UTXOs and sends all outputs to the bridge's `change_script_pubkey`.
4. Bob calls `cancel_withdraw(tx_0, cancel_psbt)`. The contract passes all checks (timeout elapsed, not yet cancelled, original tx), deducts the cancel gas fee from Alice's `transfer_amount`, marks `tx_0` as cancelled, and creates `tx_cancel` in `PendingSign` stage.
5. MPC signs `tx_cancel`; it is broadcast and confirmed on Bitcoin.
6. Alice's original withdrawal and her RBF (`tx_rbf_1`) are both invalidated. Alice loses the cancel gas fee and must re-initiate the withdrawal from scratch. [6](#0-5) [7](#0-6)

    pub fn internal_cancel_withdraw(
        &mut self,
        _account_id: &AccountId,
        original_btc_pending_verify_id: String,
        cancel_withdraw_rbf_psbt: PsbtWrapper,
        predecessor_account_id: AccountId,
    ) -> String {
        let original_tx_btc_pending_info =
            self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
        require!(
            nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
                > self.internal_config().max_btc_tx_pending_sec,
            "Please wait user rbf"
        );
        original_tx_btc_pending_info.assert_not_canceled();
        original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();

        let mut btc_pending_info = init_rbf_btc_pending_info(
            original_tx_btc_pending_info,
            PendingInfoState::WithdrawCancelRbf(RbfState {
                stage: PendingInfoStage::PendingSign,
                original_tx_id: original_btc_pending_verify_id.clone(),
            }),
        );
        let (actual_received_amount, gas_fee) = self.check_cancel_withdraw_rbf_psbt_valid(
            original_tx_btc_pending_info,
            &cancel_withdraw_rbf_psbt,
        );

        btc_pending_info.gas_fee = gas_fee;
        btc_pending_info.burn_amount = gas_fee;
        btc_pending_info.actual_received_amount = actual_received_amount;
        Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);
        let excess_gas_fee = gas_fee
            .saturating_sub(btc_pending_info.transfer_amount - btc_pending_info.withdraw_fee);
        if excess_gas_fee > 0 {
            require!(
                self.acl_has_role(Role::DAO.into(), predecessor_account_id),
                "gas fee exceeds the user's balance, only the owner is allowed to cancel"
            );
            require!(
                self.data().cur_available_protocol_fee >= excess_gas_fee,
                "Insufficient protocol fee"
            );
            self.data_mut().cur_available_protocol_fee -= excess_gas_fee;
            self.data_mut().cur_reserved_protocol_fee += excess_gas_fee;
        }
        self.internal_unwrap_mut_btc_pending_info(&original_btc_pending_verify_id)
            .do_cancel(gas_fee, excess_gas_fee);
        self.set_rbf_pending_info(
            &original_btc_pending_verify_id,
            btc_pending_info,
            cancel_withdraw_rbf_psbt,
            true,
        )
    }
