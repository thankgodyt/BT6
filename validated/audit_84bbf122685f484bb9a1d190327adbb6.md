### Title
Attacker Can Front-Run `request_refund` to Block a User's Refund and Temporarily Lock BTC/ZEC Funds — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

The public `request_refund` entry point is vulnerable to a front-running race condition. Because the uniqueness check for a refund request only executes inside the async callback (after a cross-contract call to the BTC light client), an attacker who observes a user's pending `request_refund` transaction on NEAR can copy all public proof parameters and submit a competing `request_refund` for the same UTXO with an attacker-controlled `refund_address`. If the attacker's callback settles first, the user's callback panics with "Refund request already exists for this UTXO", the user's non-refundable NEAR storage deposit is permanently lost, and the user's BTC/ZEC remains locked in the deposit address until the DAO/Operator manually rejects the attacker's request.

---

### Finding Description

**Entry point — `request_refund` is callable by any NEAR account:** [1](#0-0) 

The function carries `#[payable]` and `#[pause]` but no per-function `#[trusted_relayer]` restriction (compare `verify_refund_finalize` at line 602 which does carry it). Any NEAR account that attaches the required storage deposit can call it.

**All parameters are publicly observable.** The `deposit_msg`, `tx_bytes`, `vout`, and `proof` are submitted by the user in a NEAR transaction that is visible in the mempool/block before the cross-contract call to the BTC light client completes. The attacker copies them verbatim and substitutes only `refund_address` with their own BTC address.

**The uniqueness guard is deferred to the callback, not the entry point:** [2](#0-1) 

The comment on line 543 itself acknowledges the race: *"another request_refund could have landed between our check and callback"*. The guard prevents double-storage but does not prevent a competing request from winning the race.

**The cross-contract call to the BTC light client introduces the timing window:** [3](#0-2) 

On NEAR, cross-contract calls take at least one block to resolve. Both the user's and the attacker's callbacks are scheduled for a future block. Whichever original transaction was ordered first in the block will have its callback settle first. An attacker who submits in the same block as the user (or even a block earlier if they detect the user's intent from a signed-but-not-yet-submitted transaction) wins the race.

**The winning attacker's request is stored with `deposit_msg.refund_address = None` and `refund_address = attacker_btc_address`**, which triggers the longer `unsafe_refund_timelock_sec` path: [4](#0-3) 

After that timelock elapses, anyone (including the attacker) can call `execute_refund`, which builds a PSBT paying the stored `refund_address` — the attacker's BTC address — and routes it through the MPC signing pipeline.

**The user's NEAR deposit is non-refundable by design:** [5](#0-4) 

---

### Impact Explanation

| Stage | Effect |
|---|---|
| Attacker's callback wins | User's callback panics; user's NEAR storage deposit is permanently lost |
| Attacker's refund request stored | User's BTC/ZEC locked in deposit address; user cannot re-submit until attacker's request is rejected |
| DAO/Operator rejects in time | User must re-submit and pay another NEAR deposit; BTC temporarily locked |
| DAO/Operator fails to reject within `unsafe_refund_timelock_sec` | Attacker calls `execute_refund`; MPC signs a transaction paying attacker's BTC address; user's BTC is stolen |

The guaranteed minimum impact is **attacker-triggered temporary locking of bridged funds** plus loss of the user's NEAR deposit. The worst-case impact is **theft of the user's BTC/ZEC** if the DAO/Operator does not monitor and reject the malicious request within the timelock window.

---

### Likelihood Explanation

- `request_refund` is permissionless; any NEAR account can call it.
- All required parameters (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the user's pending NEAR transaction before the light-client callback resolves.
- The attacker's only cost is the NEAR storage deposit (same as the user's) and a small gas fee.
- NEAR transaction ordering within a block is deterministic and can be influenced by submitting with higher priority or in the same block.
- No special knowledge or privileged access is required.

---

### Recommendation

1. **Bind the refund request to the caller at the entry point.** Record `(utxo_storage_key → predecessor_account_id)` in a pending-requests map before the cross-contract call. Reject any competing `request_refund` for the same UTXO while a pending entry exists.
2. **Alternatively, require `deposit_msg.refund_address` to be set** (non-`None`) for permissionless callers, so the refund destination is committed in the deposit address derivation path and cannot be substituted by an attacker.
3. **Or restrict `request_refund` to trusted relayers** (add `#[trusted_relayer]` to the function), consistent with the other proof-submission endpoints.

---

### Proof of Concept

```
// Scenario: user has sent BTC to their deposit address and wants a refund.
// All parameters below are visible on-chain in the user's pending NEAR tx.

// Step 1 — User submits (block N):
contract.request_refund(
    deposit_msg,          // publicly visible
    "user_btc_address",   // user's BTC address
    tx_bytes,             // publicly visible
    vout,                 // publicly visible
    proof,                // publicly visible
    None,
);

// Step 2 — Attacker submits in the same block N (or earlier):
contract.request_refund(
    deposit_msg,              // copied from user's tx
    "attacker_btc_address",   // attacker substitutes their own address
    tx_bytes,                 // copied
    vout,                     // copied
    proof,                    // copied
    None,
);

// Step 3 — Block N+1: attacker's callback settles first.
//   → refund_requests[utxo_storage_key] = { refund_address: "attacker_btc_address", ... }

// Step 4 — Block N+1: user's callback panics:
//   "Refund request already exists for this UTXO"
//   User's NEAR deposit is lost.

// Step 5 — After unsafe_refund_timelock_sec elapses:
contract.execute_refund(utxo_storage_key, None);
// MPC signs a Bitcoin tx paying "attacker_btc_address".
// User's BTC is transferred to the attacker.
```
