Audit Report

## Title
Missing Pre-Transfer Normalization Guard Causes Permanent Fund Freezing — (`File: near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` / `init_transfer_internal` accept and permanently lock tokens for any transfer where `fee < amount`, but never verify that `normalize_amount(amount - fee, decimals) > 0`. The downstream `sign_transfer` function performs this check and panics when the normalized amount is zero. Because the lock occurs in a prior transaction and no user-callable cancel path exists, any transfer whose net amount is smaller than the decimal-normalization divisor results in permanently frozen funds.

## Finding Description

**Root cause — missing upstream guard:**

`init_transfer` validates only that `fee < amount`:

```rust
// near/omni-bridge/src/lib.rs:554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It never checks whether `normalize_amount(amount - fee, decimals) > 0`. `init_transfer_internal` then locks or burns the full token amount and returns `U128(0)` to the `ft_transfer_call` caller, meaning no refund is issued:

```rust
// near/omni-bridge/src/lib.rs:1850-1864
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(..., transfer_message.amount.0);
} ...
env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
U128(0)  // ← no refund; tokens are gone from the user
```

**Downstream rejection — `sign_transfer` always panics for this transfer:**

```rust
// near/omni-bridge/src/lib.rs:475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` performs integer floor division:

```rust
// near/omni-bridge/src/lib.rs:2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a NEAR-native token registered with `origin_decimals = 24` and a destination chain with `decimals = 18`, the divisor is `10^6`. Any `amount - fee < 10^6` normalizes to 0. For a destination with `decimals = 6` (e.g., Solana USDC), the divisor is `10^18`, so any amount below 1 full token normalizes to 0.

**No recovery path exists.** `remove_transfer_message` is internal-only and is only reached via `sign_transfer_callback` (requires a successful MPC signature) or `claim_fee_callback` (requires destination-chain finalization). There is no user-callable cancel or refund function. `update_transfer_fee` can only increase the fee (`fee.fee >= current_fee.fee`), which makes `amount - fee` smaller, not larger, and cannot help when `amount < divisor`.

**Exploit flow:**
1. User calls `ft_transfer_call` on a NEAR token (24 decimals) with `amount = 5`, `fee = 0`, recipient = EVM address (18 decimals).
2. `init_transfer` passes the `fee < amount` check (0 < 5).
3. `init_transfer_internal` locks 5 token units and returns `U128(0)` — no refund.
4. Trusted relayer calls `sign_transfer`.
5. `normalize_amount(5, {origin_decimals:24, decimals:18})` = `5 / 10^6` = 0.
6. `require!(0 > 0, ...)` panics — the NEAR transaction reverts, but the transfer message stored in the prior transaction remains in `pending_transfers` and the tokens remain locked.
7. Every future `sign_transfer` call for this transfer ID will also panic.
8. Tokens are permanently frozen.

## Impact Explanation

Permanent freezing of bridged funds. Any user who initiates a transfer with a net amount below the decimal-normalization divisor loses their tokens with no on-chain recovery mechanism. This matches the Critical impact class: "permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."

## Likelihood Explanation

Triggerable by any unprivileged user through the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow. No special role is required to initiate the transfer. The condition is met whenever `amount - fee < 10^(origin_decimals - dest_decimals)`. For tokens with large decimal gaps (e.g., 24 → 6), the minimum safe amount is 1 full token (`10^18` units), making accidental triggering plausible for users unfamiliar with decimal normalization. The bug is repeatable and affects every such transfer independently.

## Recommendation

Add a normalization check inside `init_transfer` (or at the start of `init_transfer_internal`) before locking or burning tokens. The token address and decimals must be resolved at init time:

```rust
// After resolving token_address and decimals:
let normalized = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing guard in `sign_transfer` and ensures the check fires before funds are committed, allowing the `ft_transfer_call` to refund the user instead of locking their tokens.

## Proof of Concept

**Unit test (add to `near/omni-bridge/src/tests/lib_test.rs`):**

```rust
#[test]
#[should_panic(expected = "ERR_INVALID_AMOUNT_TO_TRANSFER")]
fn test_init_transfer_zero_normalized_amount_locks_funds() {
    let mut contract = get_default_contract();

    // Register token with origin_decimals=24, dest_decimals=18 → divisor=10^6
    let token_id: AccountId = DEFAULT_FT_CONTRACT_ACCOUNT.parse().unwrap();
    let eth_address = OmniAddress::Eth(EvmAddress::from_str(DEFAULT_ETH_USER_ADDRESS).unwrap());
    contract.token_id_to_address.insert(&(ChainKind::Eth, token_id.clone()), &eth_address);
    contract.token_decimals.insert(&eth_address, &Decimals { decimals: 18, origin_decimals: 24 });

    // amount=5 < 10^6 → normalize_amount(5) = 0
    run_ft_on_transfer(
        &mut contract,
        DEFAULT_NEAR_USER_ACCOUNT.to_string(),
        DEFAULT_FT_CONTRACT_ACCOUNT.to_string(),
        U128(5),
        None,
        &BridgeOnTransferMsg::InitTransfer(InitTransferMsg {
            recipient: OmniAddress::Eth(EvmAddress::from_str(DEFAULT_ETH_USER_ADDRESS).unwrap()),
            fee: U128(0),
            native_token_fee: U128(0),
            msg: None,
            external_id: None,
        }),
    );
    // Without the fix: ft_on_transfer returns U128(0) (tokens locked, no refund).
    // sign_transfer then panics with ERR_INVALID_AMOUNT_TO_TRANSFER.
    // With the fix: ft_on_transfer should panic here, refunding the user.
}
```

**Integration test plan:** Deploy the locker on a local NEAR sandbox, register a token with `origin_decimals=24` / `dest_decimals=18`, call `ft_transfer_call` with `amount=1` (< 10^6), confirm `ft_on_transfer` returns `U128(0)` (tokens locked), then call `sign_transfer` from a trusted relayer and observe the `ERR_INVALID_AMOUNT_TO_TRANSFER` panic while the transfer message persists in `pending_transfers`.
