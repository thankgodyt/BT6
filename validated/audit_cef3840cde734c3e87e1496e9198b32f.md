### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Peer-Supplied Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` (success) for every certificate it receives, performing no cryptographic or semantic checks. This stub is wired directly into the production node-to-node Peras certificate diffusion mini-protocol. An unprivileged peer can inject a crafted `PerasCert` with an arbitrary round number and boosted block point; the node will accept it as valid, add it to the ChainDB, and trigger chain selection with a fraudulent weight boost for an attacker-chosen block.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve every inbound Peras certificate before it is stored and acted upon. The degenerate instance that covers all block types is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is verified, no round number is range-checked, and no boosted-block point is validated against the known chain. [1](#0-0) 

This stub is the concrete validator passed to `processCerts` in both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` is the writer wired into the live node-to-node handler `hPerasCertDiffusionClient`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

`processCerts` accepts any certificate that passes `validateCert` and immediately adds it to the database: [5](#0-4) 

The `PerasCert` data type carries a `pcCertRound` and a `pcCertBoostedBlock` (a `Point blk`), both of which are fully attacker-controlled because no field is checked. [6](#0-5) 

---

### Impact Explanation

A Peras certificate, once accepted as `ValidatedPerasCert`, carries a `vpcCertBoost` weight that is added to the boosted block during chain selection. By injecting a certificate that names an arbitrary `pcCertBoostedBlock`, an attacker can cause the receiving node to assign a weight boost to any block of the attacker's choosing — including a block on a minority or adversarial fork. This directly manipulates chain selection, potentially causing the node to prefer a non-canonical chain over the honest chain, which is a **High** chain-selection safety violation. It also constitutes a **Critical** bypass of Peras certificate verification, since the entire cryptographic gate (`validatePerasCert`) is a no-op.

---

### Likelihood Explanation

The attack requires only that the Peras certificate diffusion mini-protocol is active and reachable, which it is: the handler is unconditionally registered in `NodeToNode.hs`. Any peer that can establish a node-to-node connection can send a `PerasCert` message. No keys, stake, or special privileges are required. The attacker only needs to craft a CBOR-encoded `PerasCert` with a desired `pcCertRound` and `pcCertBoostedBlock`.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. Checks that the voter set meets the quorum threshold for the given round.
3. Validates that `pcCertBoostedBlock` refers to a known, valid block on the candidate chain.
4. Validates that `pcCertRound` is within the expected range for the current epoch.

Until the real implementation is ready, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), to fail safely.

---

### Proof of Concept

An attacker node connects to a victim node via the Peras certificate diffusion mini-protocol and sends:

```
PerasCert
  { pcCertRound      = <any round number>
  , pcCertBoostedBlock = <Point of an attacker-chosen block>
  , pcVoters         = <empty or minimal voter bitmap>
  , pcSignature      = <any bytes>
  }
```

Because `validatePerasCert` is:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

the certificate passes validation unconditionally. `processCerts` timestamps it and calls `ChainDB.addPerasCertAsync`, which triggers chain selection with the fraudulent boost applied to the attacker-chosen block. [7](#0-6) [5](#0-4)
