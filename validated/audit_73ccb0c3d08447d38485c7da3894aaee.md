Audit Report

## Title
Partial `ft_on_transfer` Refund Permanently Freezes Bridged Tokens via Binary `amount.0 == 0` Check — (`near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` performs a binary all-or-nothing check (`amount.0 == 0`) on the used-amount returned by `ft_transfer_call`. When a NEAR recipient contract partially rejects tokens — returning a non-zero refund `R` where `0 < R < amount_without_fee` — the bridge treats the transfer as fully successful, finalizes the nonce, and pays the relayer fee. The `R` tokens returned to the bridge by the token contract's `ft_resolve_transfer` are permanently stuck in the bridge contract with no recovery path. The existing integration test at `near/omni-tests/src/fin_transfer.rs:533–544` explicitly encodes and confirms this outcome.

## Finding Description

In `fin_transfer_send_tokens_callback` (`lib.rs:1692`), when a `msg` is present, the bridge sends `amount_without_fee` tokens to the recipient via `ft_transfer_call`. The callback at `lib.rs:1702` calls `is_refund_required` to decide whether to revert:

```rust
// lib.rs:1784–1804
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    amount.0 == 0   // ← only handles full rejection
                } else {
                    false
                }
            }
            Err(_) => false,
        }
    } else {
        false
    }
}
```

Under NEP-141, `ft_resolve_transfer` returns the amount **used** (`sent − refund`). If `ft_on_transfer` returns a partial refund `R` where `0 < R < amount_without_fee`, then `ft_resolve_transfer` returns `amount_without_fee − R > 0`. The check `amount.0 == 0` evaluates to `false`, so `is_refund_required` returns `false`. Consequently:

1. `revert_lock_actions` is never called — `locked_tokens` counter is not restored.
2. `burn_tokens_if_needed` is never called — for bridged tokens, the `R` minted tokens are not burned.
3. The relayer fee is paid and `FinTransferEvent` is emitted — the transfer nonce is permanently consumed via `finalised_transfers`.

The `R` tokens refunded by the token contract into the bridge's balance are now orphaned with no admin or user recovery function. The same `is_refund_required` logic is reused identically in `resolve_fast_transfer` (`lib.rs:906`) and `resolve_utxo_fin_transfer` (`lib.rs:1025`), making all three finalization paths equally affected.

## Impact Explanation

This is a **Critical** impact matching "permanent freezing of bridged funds" and "escrow mis-accounting." The transfer nonce is consumed (`finalised_transfers` marked), so the transfer cannot be re-submitted. For bridged (deployed) tokens, `R` extra minted tokens exist in the bridge's balance and are never burned, inflating supply relative to locked collateral on the source chain — a direct balance manipulation. For native tokens, the bridge holds `R` extra tokens not tracked by `locked_tokens`, breaking escrow accounting. Both outcomes are irreversible without a contract upgrade.

## Likelihood Explanation

Any unprivileged user who initiates a cross-chain transfer to a NEAR contract recipient and includes a non-empty `msg` field triggers `ft_transfer_call` instead of `ft_transfer`. The `msg` field and recipient address are both user-controlled inputs accepted by the bridge without restriction. Standard NEAR DeFi contracts (DEXes, vaults, lending protocols) routinely implement `ft_on_transfer` with capacity limits or conditional acceptance that return a non-zero partial refund — this is a standard NEP-141 pattern, not an adversarial one. No special privileges, key compromise, or validator collusion are required.

## Recommendation

In `is_refund_required` (or its callers), pass the expected `amount_without_fee` and compare the used amount against it. Trigger the revert path whenever `used_amount < amount_without_fee`:

```rust
// Instead of:
amount.0 == 0
// Use:
amount.0 < expected_amount_without_fee
```

Apply the same partial-refund revert logic (burn + revert lock actions + remove transfer) currently applied to the full-rejection case. Alternatively, handle the partial case explicitly by re-locking or burning only the `R` difference, and emitting a partial-success event.

## Proof of Concept

The existing integration test at `near/omni-tests/src/fin_transfer.rs:533–544` directly and unambiguously demonstrates the stuck-token outcome:

```rust
#[case(FinTransferWithMsgCase {
    amount: 1000,
    fee: 1,
    msg: TokenReceiverMessage {
        return_value: U128(1),   // receiver returns 1 token unused (partial refund)
        panic: false,
        extra_msg: String::new(),
    },
    expected_recipient_balance: 998,   // recipient receives 998, not 999
    expected_relayer_balance: 1,       // relayer gets fee — transfer "succeeded"
    expected_locker_balance: 1,        // 1 token permanently frozen in bridge
})]
```

`expected_locker_balance: 1` confirms that 1 token is permanently frozen in the bridge contract after a partial rejection. The transfer nonce is consumed, the fee is paid, and there is no mechanism to recover the stuck token. Run `cargo test` in `near/omni-tests` to reproduce.
