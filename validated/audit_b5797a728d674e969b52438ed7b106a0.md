### Title
Peras Vote and Certificate Validation Unconditionally Accepts Unauthenticated Inputs — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance, which applies to **all** block types, contains two stub validation functions that skip cryptographic checks entirely. `validatePerasCert` unconditionally returns `Right` for any certificate, and `validatePerasVote` accepts any vote whose voter ID appears in the stake distribution without verifying the vote's cryptographic signature. An unprivileged peer can exploit both paths to inject unauthorized votes and certificates into the node's Peras vote pool, bypassing the authorization checks that are supposed to gate Peras weight boosts and chain selection.

### Finding Description

The `BlockSupportsPeras` typeclass defines two validation entry points:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote ::
  PerasCfg blk ->
  PerasVoteStakeDistr ->
  PerasVote blk ->
  Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The only concrete instance in the codebase is the degenerate catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

  -- TODO: perform actual validation against all possible 'PerasValidationErr' variants
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

`validatePerasCert` returns `Right` for **every** certificate regardless of its cryptographic content. `validatePerasVote` only checks that the voter ID (`pvVoteVoterId`) exists in the stake distribution map; it never verifies the vote's BLS/KES signature. The analogy to the external report is exact: just as `_numberOfPledges = 1` was hardcoded for `NoResolution` instead of consulting the actual pledge record, here the validation result is hardcoded to success instead of consulting the cryptographic proof.

These functions are called on the inbound path in `processVotes` (via `makePerasVotePoolWriterFromChainDB` / `makePerasVotePoolWriterFromVoteDB`), which is the production handler for Peras votes arriving from peers over the miniprotocol.

### Impact Explanation

An unprivileged peer can:

1. **Forge votes**: Craft a `PerasVote` carrying any voter ID that appears in the current stake distribution, targeting any block hash, with a completely fabricated or zeroed signature. `validatePerasVote` will accept it because it only calls `lookupPerasVoteStake` and never calls a signature-verification primitive.

2. **Forge certificates**: Craft a `PerasCert` for any round and any block point. `validatePerasCert` returns `Right` unconditionally, so the certificate is stamped as `ValidatedPerasCert` with the full `perasWeight` boost.

Once enough forged votes accumulate in the vote pool, the node's own certificate-forging logic (`forgePerasCert` / `updatePerasRoundVoteStates`) may produce a certificate for an attacker-chosen block. That certificate is then eligible to apply a Peras weight boost to that block during chain selection, causing the node to prefer a chain the attacker controls over the honest chain.

This matches the **Critical** impact category: bypass of Peras voting and certificate checks enabling unauthorized vote and certificate acceptance.

### Likelihood Explanation

- The instance `instance StandardHash blk => BlockSupportsPeras blk` is the **only** instance in the repository and covers every block type used in production.
- The inbound vote-processing path (`processVotes`) is wired into the production node via `makePerasVotePoolWriterFromChainDB`, which is called from the Peras vote miniprotocol handler.
- No special privileges, keys, or stake are required; the attacker only needs to know a pool ID that appears in the current stake distribution, which is public on-chain data.
- The TODO comments confirm the missing checks are known but not yet implemented, meaning the gap is present in every build until the issue is resolved.

### Recommendation

- **Short term**: In `validatePerasVote`, add a call to the appropriate signature-verification primitive (e.g., BLS `verifyVoteSignature`) before returning `Right`. In `validatePerasCert`, add cryptographic certificate verification (aggregate signature check) before accepting the certificate.
- **Long term**: Replace the degenerate catch-all instance with era-specific instances that implement full validation, mirroring the pattern already used in `implVerifyVote` / `implVerifyCert` in `WFALS.hs` and `EveryoneVotes.hs`. Add property-based tests that confirm forged votes and certificates are rejected.

### Proof of Concept

1. Observe the current stake distribution to obtain any live pool ID `P`.
2. Construct a `PerasVote` with `pvVoteVoterId = P`, `pvVoteRound = <current round>`, `pvVoteBlock = <attacker-chosen block point>`, and a zeroed/random signature field.
3. Send this vote to the target node via the Peras vote miniprotocol.
4. `processVotes` calls `validatePerasVote mkPerasParams stakeDistr vote`; `lookupPerasVoteStake` finds `P` in the distribution and returns `Just stake`; the function returns `Right ValidatedPerasVote` without ever inspecting the signature.
5. The vote is added to the pool. Repeat with different pool IDs until `votesReachQuorum` is satisfied.
6. The node forges a `ValidatedPerasCert` for the attacker-chosen block, applying the Peras weight boost and biasing chain selection toward that block. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
