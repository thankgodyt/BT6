### Title
Peras Certificate and Vote Validation Stubs Always Accept Any Input — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default catch-all `BlockSupportsPeras` instance provides stub implementations of `validatePerasCert` and `validatePerasVote` that unconditionally return `Right` (success) or only perform a stake-lookup check, respectively, without performing any cryptographic or structural validation. Because this instance applies to all block types via `instance StandardHash blk => BlockSupportsPeras blk`, any Peras certificate or vote received from an unprivileged peer passes validation regardless of its content, enabling unauthorized chain-weight boosts and incorrect chain selection.

### Finding Description

In `Ouroboros.Consensus.Block.SupportsPeras`, the catch-all instance for `BlockSupportsPeras` provides the following stub implementations:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This function is supposed to validate a Peras certificate and return `Left (PerasValidationErr blk)` for any invalid certificate. Instead, it unconditionally returns `Right` for every input, accepting any certificate without checking its cryptographic proof, committee membership, round number consistency, or any other invariant.

Similarly, `validatePerasVote` only checks whether the voter appears in the stake distribution, but performs no signature verification:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [2](#0-1) 

This instance is declared as a catch-all:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [3](#0-2) 

The inbound certificate processing pipeline in `processCerts` calls `validateCert` on every received certificate and only rejects a batch if `validateCert` returns `Left`. Since `validatePerasCert` always returns `Right`, no certificate is ever rejected: [4](#0-3) 

Accepted certificates are stored in the `PerasCertDB` and used to compute chain weight boosts via `vpcCertBoost`, which directly influences chain selection: [5](#0-4) 

### Impact Explanation

**Impact: Critical.** An unprivileged peer can craft and broadcast arbitrary Peras certificates for any block point and any round number. Because `validatePerasCert` always returns `Right`, these certificates pass validation, are stored in the `PerasCertDB`, and their `vpcCertBoost` weight is applied to the certified block during chain selection. This allows an adversary to make an honest node prefer a non-canonical or adversary-controlled chain by artificially inflating its weight, constituting a bypass of Peras certificate validation and a chain-selection safety failure.

The same applies to `validatePerasVote`: any entity with stake can submit votes with forged or absent signatures, and those votes will be counted toward quorum, potentially causing the node to forge and accept certificates based on fraudulent votes.

### Likelihood Explanation

**Likelihood: High.** The entry path is the standard Peras object-diffusion miniprotocol, reachable by any peer that connects to the node. No special privileges, keys, or stake majority are required beyond having any stake entry in the distribution (for votes) or nothing at all (for certificates). The stub is in the production source tree and is the only `BlockSupportsPeras` instance in the codebase.

### Recommendation

Replace the stub `validatePerasCert` and `validatePerasVote` implementations with real cryptographic validation before enabling Peras in any production or testnet environment. At minimum, gate the object-diffusion handlers so that certificates and votes are rejected at the protocol level when no real validation is available, rather than silently accepting all inputs. The existing `Either (PerasValidationErr blk) (ValidatedPerasCert blk)` return type already provides the correct structure for signaling rejection.

### Proof of Concept

1. Connect to a node as an unprivileged peer via the Peras object-diffusion miniprotocol.
2. Construct a `PerasCert blk` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block on a minority fork.
3. Send the certificate batch to the node.
4. `processCerts` calls `validatePerasCert` on the certificate.
5. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. The certificate is stored in `PerasCertDB` and its boost weight is applied to the targeted block.
7. Chain selection now treats the minority-fork block as heavier, potentially causing the node to switch to the adversary's chain. [1](#0-0) [4](#0-3)
