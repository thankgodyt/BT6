### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Submitted Certificate, Bypassing All Authorization Checks - (File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs)

### Summary

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` provides a stub `validatePerasCert` that unconditionally returns `Right` (success) for every certificate, performing zero cryptographic or committee-membership verification. This stub is wired directly into the production Peras certificate inbound processing pipeline (`processCerts` in `ObjectPool/PerasCert.hs`), meaning any unprivileged peer can submit an arbitrary `PerasCert` for any block and have it accepted as a `ValidatedPerasCert` with a full chain-selection weight boost. This is the direct analog of the reported "lack of appropriate access control" pattern: just as `initAuctionLauncher()` allowed any caller to self-authorize as admin, `validatePerasCert` allows any peer to self-authorize any certificate as valid.

### Finding Description

**Root cause — stub validator with no access control:**

The `BlockSupportsPeras` class defines `validatePerasCert` as the authorization gate for inbound Peras certificates. The universal instance (applied to all block types) implements it as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is verified, no committee membership is checked, no quorum threshold is enforced. The `PerasCert` supplied by the peer is wrapped directly into a `ValidatedPerasCert` carrying the full protocol-defined weight boost (`perasWeight params`).

**Production wiring — stub is the live validator for inbound peer certificates:**

`makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` both pass `(validatePerasCert mkPerasParams)` as the validation function to `processCerts`:

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass, adds them to the database. Since `validatePerasCert` always returns `Right`, every certificate from every peer passes:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Attacker-controlled entry path:**

A peer connects via the NTN object-diffusion protocol and sends a crafted `PerasCert` naming any block hash as `pcCertBoostedBlock`. The certificate flows through `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert` (returns `Right`) → `ChainDB.addPerasCertAsync`. The certificate is stored as a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` and is subsequently used in chain selection weight computation. [4](#0-3) 

### Impact Explanation

Peras certificates carry a weight boost that directly influences chain selection: a block with an accepted certificate is preferred over an equal-length chain without one. Because `validatePerasCert` performs no authorization check, an unprivileged peer can inject a certificate boosting any block — including an attacker-controlled fork — causing an honest node to prefer that fork over the canonical chain. This is a **Critical** bypass of Peras certificate/vote authorization checks that enables unauthorized certificate acceptance and chain-selection manipulation, matching the allowed impact category: *"Bypass of leader eligibility, VRF/KES/certificate/signature validation, PBFT/Praos/TPraos/Peras voting or certificate checks … that enables unauthorized block, vote, or certificate acceptance."*

### Likelihood Explanation

Any peer reachable via the NTN object-diffusion protocol can trigger this. No keys, stake, or privileged access are required — only the ability to connect and send a well-formed `PerasCert` CBOR message. The stub is the only validator in the live code path; there is no secondary check downstream.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that:
1. Verifies the aggregate BLS/committee signature over `(electionId, boostedBlock)`.
2. Confirms the signers constitute a valid quorum of the epoch's voting committee.
3. Checks that `pcCertBoostedBlock` refers to a block that exists on a plausible chain.

Until the real implementation is ready, the inbound Peras certificate diffusion path should either be disabled or gated behind a feature flag that is off by default in production builds, so that the stub cannot be reached by untrusted peers.

### Proof of Concept

1. Connect to a target node via the NTN object-diffusion protocol.
2. Craft a `PerasCert` with `pcCertRound = <current round>` and `pcCertBoostedBlock = <attacker fork tip>`.
3. Send the certificate. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
4. The certificate is stored via `ChainDB.addPerasCertAsync`.
5. Chain selection now treats the attacker's fork as carrying a full Peras weight boost, causing the honest node to prefer it over the canonical chain of equal or lesser length. [1](#0-0) [5](#0-4) [3](#0-2)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
