### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates While `validatePerasVote` Enforces Stake Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` (success) for every certificate it receives, performing zero validation. In contrast, the parallel `validatePerasVote` function enforces at least a stake-distribution membership check before accepting a vote. Both functions are called from structurally identical processing pipelines (`processCerts` / `processVotes`) that are designed to reject invalid objects. Because `validatePerasCert` never rejects anything, any unprivileged peer can inject arbitrarily crafted Peras certificates through the object-diffusion miniprotocol. Accepted certificates are stored in the `PerasCertDB` and immediately trigger chain selection for the block they claim to boost, allowing an attacker to manipulate the node's chain preference.

---

### Finding Description

**Root cause — misaligned validation coverage between `validatePerasCert` and `validatePerasVote`**

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the universal `BlockSupportsPeras` instance provides two validation functions:

```haskell
-- Always succeeds — no checks whatsoever
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }

-- At least checks stake-distribution membership
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`validatePerasCert` accepts every certificate unconditionally. `validatePerasVote` rejects a vote whose voter ID is absent from the stake distribution. The two functions are consumed by structurally identical processing pipelines:

- `processCerts` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs` calls `validateCert` on each inbound certificate and throws `PerasCertInboundException` only when validation returns `Left`. Because `validatePerasCert` never returns `Left`, the exception is never thrown and every certificate is accepted.

- `processVotes` in `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs` calls `validateVote` on each inbound vote and throws `PerasVoteInboundException` when validation returns `Left`. Because `validatePerasVote` does return `Left` for unknown voters, invalid votes are rejected.

The misalignment is exact: the processing layer (`processCerts`) is designed to gate on validation, but the validation function it calls (`validatePerasCert`) is a stub that always passes.

**Attacker-controlled entry path**

Both `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB` wire `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
```

These writers are exposed to the network via the object-diffusion miniprotocol. Any peer that speaks this protocol can send a `[PerasCert blk]` batch. The batch passes through `processCerts`, which calls `validatePerasCert` on each certificate. Since `validatePerasCert` always returns `Right`, every certificate in the batch is timestamped and forwarded to `addCert` / `addPerasCertAsync`.

**Chain-selection consequence**

`addPerasCertAsync` enqueues the certificate into `cdbChainSelQueue`. The background thread processes it via `chainSelSync` (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/ChainDB/Impl/ChainSel.hs`):

1. The certificate is stored in `PerasCertDB`.
2. If the boosted block is not on the current chain, `chainSelectionForBlock` is called for that block.
3. `getPerasWeightSnapshot` returns the accumulated Peras weight boosts; the boosted block's chain now carries extra weight.
4. If the extra weight tips the chain-order comparison, the node switches to the boosted (potentially weaker) chain.

A crafted certificate with an arbitrary `pcCertBoostedBlock` pointing to a block on an adversarial fork can therefore cause the node to prefer that fork over the honest chain.

---

### Impact Explanation

**High — chain selection error enabling preference of a non-canonical chain.**

An unprivileged peer can inject crafted Peras certificates that boost blocks on adversarial forks. Because `validatePerasCert` never rejects any certificate, the node's chain-selection weight snapshot is polluted with attacker-controlled boosts. If the boosted fork accumulates enough artificial weight to exceed the honest chain's weight, the node switches to the adversarial fork. This violates the chain-selection security assumption that only legitimately certified blocks receive Peras weight boosts.

---

### Likelihood Explanation

**High.** The object-diffusion miniprotocol is reachable by any connected peer without any privilege. The attack requires only sending a well-formed CBOR-encoded `PerasCert` value with an attacker-chosen `pcCertRound` and `pcCertBoostedBlock`. No key material, stake, or operator access is needed. The stub is present in the production source tree and is wired into both the `PerasCertDB`-backed and `ChainDB`-backed pool writers.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with actual certificate validation that mirrors the checks applied to votes. At minimum, the certificate must be checked for:

1. A valid committee quorum proof (VRF/KES signatures from eligible committee members).
2. A `pcCertBoostedBlock` that refers to a known, non-ancient block.
3. A `pcCertRound` that is within the current or recent Peras round window.

Until real validation is in place, the `processCerts` pipeline should reject all inbound certificates to prevent chain-selection manipulation. The misalignment between `validatePerasCert` (no checks) and `validatePerasVote` (stake check) should be resolved so that both functions enforce equivalent levels of authorization before accepting objects into the database.

---

### Proof of Concept

1. Connect to a target node that has the Peras object-diffusion miniprotocol enabled.
2. Craft a `PerasCert blk` value:
   - `pcCertRound`: any `PerasRoundNo`
   - `pcCertBoostedBlock`: the `Point` of a block on an adversarial fork that is in the node's `VolatileDB`
3. Send the certificate as a single-element batch via the miniprotocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
5. The certificate is forwarded to `addPerasCertAsync`, enqueued in `cdbChainSelQueue`, and processed by `chainSelSync`.
6. `chainSelectionForBlock` is invoked for the boosted block; the `PerasWeightSnapshot` now includes the attacker-supplied boost.
7. If the boosted fork's total weight (honest weight + injected Peras boost) exceeds the current chain's weight, the node switches to the adversarial fork.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

```haskell
-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
