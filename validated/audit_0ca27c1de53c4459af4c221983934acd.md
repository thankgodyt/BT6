### Title
Peras Certificate Validation Bypass via Unconditional-Accept Stub `validatePerasCert` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal default instance `instance StandardHash blk => BlockSupportsPeras blk` provides a stub `validatePerasCert` that unconditionally returns `Right ValidatedPerasCert` for every certificate it receives, performing zero cryptographic or structural checks. A `grep` over the entire repository confirms this is the **only** `BlockSupportsPeras` instance — no concrete override exists for `CardanoBlock` (`HardForkBlock (CardanoEras c)`) or any other production block type. Because the `PerasCertDiffusion` mini-protocol is wired into the production `NodeToNode` handler record, any unprivileged peer can inject arbitrary Peras certificates that pass validation and are stored with full chain-weight boost, enabling unauthorized chain-selection manipulation.

### Impact Explanation

Every `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` field that is consumed by the Peras chain-weight calculation. Because `validatePerasCert` always returns `Right` and assigns `perasWeight params` as the boost, an attacker who sends a crafted certificate for any block — including a block on a non-canonical fork — causes that block to receive the full Peras weight boost. Honest nodes that incorporate this boost into chain selection will prefer the attacker-boosted fork over the canonical chain. This is a bypass of Peras certificate/signature validation that enables unauthorized certificate acceptance and chain-selection divergence, matching the **Critical** impact class: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is compiled into and registered in the production `NodeToNode` application bundle without any feature flag gating it at the handler level. The stub is the only live implementation. Any peer that can open a node-to-node connection — which requires no special privileges on a public network — can send a well-formed CBOR-encoded `PerasCert` message. The only uncertainty is whether Peras chain-weight boosting is currently active in the chain-selection logic on mainnet; if it is, exploitation is immediate and requires no key material or stake.

---

### Recommendation

1. **Block deployment of `PerasCertDiffusion` until a concrete `BlockSupportsPeras` instance with full validation is provided for `CardanoBlock`.** The degenerate universal instance must not be reachable from the live diffusion path.
2. Implement `validatePerasCert` to verify: (a) the aggregate BLS signature over `(roundNo, boostedBlock)`, (b) that each claimed voter seat index was eligible for the given round via the committee selection mechanism, and (c) that the number of eligible voters meets the quorum threshold.
3. Implement `validatePerasVote` to verify the per-voter BLS or VRF signature in addition to the existing stake-distribution membership check.
4. Add a guard in the `PerasCert` inbound object pool that rejects any certificate whose `validatePerasCert` call returns `Left`, and disconnects the sending peer.

### Proof of Concept

1. Establish a node-to-node connection to a Cardano node running with `PerasCertDiffusion` active.
2. Construct a `PerasCert blk` value (using the `Serialise` instance at lines 400–409 of `SupportsPeras.hs`) referencing any block point on a minority fork.
3. Send it via the `PerasCertDiffusion` inbound channel.
4. The node calls `validatePerasCert params cert`, which returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
5. The certificate is stored in `PerasCertDB` and its boost is applied to the minority-fork block's chain weight.
6. If the boost is sufficient to exceed the canonical chain's weight, the node switches to the minority fork — a chain-selection safety failure triggered by an unprivileged peer with no cryptographic material. [5](#0-4)
