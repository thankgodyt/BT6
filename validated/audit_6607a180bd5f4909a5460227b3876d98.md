### Title
Stub `validatePerasCert` Always Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Selection Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance ships a placeholder `validatePerasCert` that unconditionally returns `Right` for every certificate it receives. Because the inbound certificate diffusion path (`processCerts`) calls this function as its sole gate before storing a certificate and triggering chain selection, any unprivileged peer can inject a crafted `PerasCert` that boosts an arbitrary block, causing the local node to apply a spurious Peras weight to a non-canonical fork and potentially switch away from the honest chain.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory check that must be passed before a certificate is treated as `ValidatedPerasCert`. The degenerate instance that covers all block types in production is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No aggregate BLS signature is verified, no committee membership is checked, no round-number or boosted-block validity is enforced. The `PerasValidationErr` type itself is a single-constructor stub with no semantic content: [2](#0-1) 

The inbound certificate processing function `processCerts` in the object-diffusion layer calls this stub as its only validation step before storing and acting on the certificate:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Both the `PerasCertDB` writer and the `ChainDB` writer pass `validatePerasCert mkPerasParams` as the `validateCert` argument: [4](#0-3) [5](#0-4) 

Once stored, the certificate is consumed by `chainSelSync` in `ChainSel.hs`, which calls `chainSelectionForBlock` for the boosted block, applying the certificate's weight to chain selection: [6](#0-5) 

The `implAddCert` in `PerasCertDB/Impl.hs` also carries the same TODO, confirming no secondary validation gate exists there either: [7](#0-6) 

The analog to the original report is direct: just as `grants[]` and `claims[]` lacked auxiliary functions to enforce invariants on their elements, the `PerasCert` validation data object (`PerasValidationErr`) is a non-functional stub — the "validation" of inbound certificates is entirely absent, so any peer-supplied certificate is accepted without restriction.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any `pcCertBoostedBlock` (any block point the attacker chooses) and any `pcCertRound`. Because `validatePerasCert` always returns `Right`, the certificate passes the only validation gate, is stored in `PerasCertDB`, and triggers `chainSelectionForBlock` for the attacker-chosen block. The Peras weight boost (`perasWeight params`) is then applied to that block during chain selection. If the attacker's chosen block is on a minority fork, the honest node may switch to that fork, diverging from the canonical chain. This constitutes a **bypass of Peras certificate verification** enabling unauthorized chain-selection weight injection.

---

### Likelihood Explanation

The attack requires only that the attacker be a connected peer and be able to send a well-formed CBOR-encoded `PerasCert` message over the object-diffusion mini-protocol. No key material, stake, or privileged access is needed. The code path is exercised for every inbound certificate. Likelihood is **high** once the Peras protocol is active on a live network.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real check that:
1. Verifies the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. Verifies each claimed voter's committee membership and eligibility proof against the current stake distribution.
3. Verifies that the voter set's combined stake exceeds the quorum threshold.

Until issue #120 is resolved, the node should not accept externally supplied Peras certificates at all (e.g., by disabling the inbound object-diffusion path for certificates), rather than silently accepting every certificate.

---

### Proof of Concept

1. Connect to a target node as a peer via the object-diffusion mini-protocol.
2. Send a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of a minority-fork block>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert cert (perasWeight params))`.
4. The certificate is stored in `PerasCertDB` and `addPerasCertAsync` is called on the `ChainDB`.
5. `chainSelSync` calls `chainSelectionForBlock` for the minority-fork block with the injected weight boost.
6. If the boosted fork's total weight now exceeds the current selection, the node switches to the attacker-controlled fork.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
