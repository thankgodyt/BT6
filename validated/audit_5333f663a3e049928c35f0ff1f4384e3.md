### Title
Incomplete Peras Vote Eligibility Validation Allows Non-Persistent Members to Bypass VRF Sortition Check - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

### Summary

The Peras vote ingestion path validates incoming peer votes using only the stake distribution, without the full committee selection context required to verify whether a voter claiming persistent membership actually holds that status. An unprivileged peer can craft a `PerasVote` with `PersistentPerasVoteEligibilityProof` (tag `0`, no VRF output required) for a seat index that belongs to a non-persistent committee member, bypassing the VRF-based local sortition eligibility check entirely.

### Finding Description

`PerasVoteEligibilityProof` is a two-constructor sum type:

```haskell
data PerasVoteEligibilityProof
  = PersistentPerasVoteEligibilityProof          -- tag 0, no proof required
  | NonPersistentPerasVoteEligibilityProof !(VRFOutput PerasBLSCrypto)  -- tag 1, VRF proof required
``` [1](#0-0) 

The `PersistentPerasVoteEligibilityProof` constructor carries no cryptographic material. Persistent membership is supposed to be verified at validation time by checking the voter's seat index against the committee's `persistentCommitteeSize` boundary:

```haskell
isPersistentMember seatIndex committee =
  unSeatIndex seatIndex < unPersistentCommitteeSize (persistentCommitteeSize committee)
``` [2](#0-1) 

`implVerifyVote` in `WFALS.hs` correctly enforces this check — a `WFALSPersistentVote` is rejected with `NotAPersistentMember` if `isPersistentMember` fails: [3](#0-2) 

However, the live vote ingestion path in `makePerasVotePoolWriterFromChainDB` explicitly acknowledges that it validates votes using **only the stake distribution**, not the full committee selection context:

```haskell
-- TODO: in the future we won't need just the stake distribution for
-- validating votes, but also the whole committee selection context
-- (containing vote weights of committee members = voters)
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

Without the `VotingCommittee` record (which carries `persistentCommitteeSize`), the `isPersistentMember` predicate cannot be evaluated. The `pvEligibilityProof` field is therefore accepted at face value: a vote claiming `PersistentPerasVoteEligibilityProof` is treated as persistent without verifying the claim against the committee.

The conversion layer in `fromPerasVote` (WFALS instance) faithfully maps the self-declared proof type to the abstract `WFALSPersistentVote` constructor: [5](#0-4) 

If `validatePerasVote` does not subsequently invoke `implVerifyVote` with a fully-constructed `VotingCommittee`, the membership check is never performed.

### Impact Explanation

Peras uses accepted votes to boost the weight of blocks during chain selection. An unauthorized vote accepted for a non-persistent seat index inflates the weight of the boosted block. If an attacker can inject enough such votes (one per non-persistent seat they control the signing key for, but without needing a valid VRF output), they can cause honest nodes to prefer a non-canonical chain, constituting a chain selection manipulation. This maps to: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions.**

### Likelihood Explanation

The attacker-controlled entry path is the Peras vote mini-protocol: any peer can submit a `PerasVote` message. Crafting a vote with `PersistentPerasVoteEligibilityProof` (CBOR tag `0`, no VRF output) for a seat index that is actually non-persistent requires only a valid BLS vote signature, which the attacker can produce if they hold the private key for a registered pool at that seat. The TODO comment confirms the incomplete validation is a known, present limitation of the production code path, not a hypothetical.

### Recommendation

Pass the full `VotingCommittee` context (including `persistentCommitteeSize`) into `validatePerasVote` so that `isPersistentMember` can be evaluated. The `implVerifyVote` function in `WFALS.hs` already implements the correct check; the fix is to ensure the live ingestion path calls it with a fully-constructed committee rather than only the stake distribution.

### Proof of Concept

1. Obtain the BLS signing key for a registered pool whose seat index falls in the non-persistent range (i.e., `seatIndex >= persistentCommitteeSize`).
2. Craft a `PerasVote` with:
   - `pvSeatIndex` = that non-persistent seat index
   - `pvEligibilityProof` = `PersistentPerasVoteEligibilityProof` (CBOR: `[0]`)
   - `pvSignature` = valid BLS signature over `(pvRoundNo, pvBoostedBlock)` using the pool's signing key
3. Submit the vote via the Peras vote mini-protocol to a target node.
4. Because `validatePerasVote` uses only the stake distribution (no `persistentCommitteeSize` boundary check), the vote passes validation without a VRF proof.
5. The vote is stored and contributes weight to the boosted block, influencing chain selection in favor of the attacker's preferred chain. [6](#0-5) [7](#0-6)
