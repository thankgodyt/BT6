### Title
`OmniBridgeWormhole.finTransferExtension` Forwards Full `msg.value` to Wormhole After Already Spending Part of It on Native ETH Delivery, Permanently Blocking Native ETH Finalization - (File: `evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

---

### Summary

`OmniBridgeWormhole.finTransferExtension` passes the original `msg.value` to `_wormhole.publishMessage`, but for native-ETH transfers (`tokenAddress == address(0)`) the base `finTransfer` has already spent `payload.amount` of that ETH sending it to the recipient. The contract's remaining balance is only `msg.value − payload.amount`, so the Wormhole call always reverts, making every native-ETH cross-chain finalization permanently impossible via the Wormhole path.

---

### Finding Description

`OmniBridge.finTransfer` is `payable` and handles native ETH delivery when `payload.tokenAddress == address(0)`:

```
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
// ...
finTransferExtension(payload);   // called AFTER ETH is already sent
``` [1](#0-0) [2](#0-1) 

`OmniBridgeWormhole.finTransferExtension` then unconditionally forwards the **original** `msg.value` to Wormhole:

```
_wormhole.publishMessage{value: msg.value}(
    wormholeNonce,
    messagePayload,
    _consistencyLevel
);
``` [3](#0-2) 

After the `payload.recipient.call{value: payload.amount}` succeeds, the contract's ETH balance is `msg.value − payload.amount`. Attempting to forward the full original `msg.value` to Wormhole will always revert because the contract no longer holds that amount. The entire transaction reverts (including the ETH send to the recipient and the nonce mark), so the nonce is never consumed and the transfer can never be finalized.

For non-ETH token transfers `msg.value` equals only the Wormhole fee and is never partially spent beforehand, so those paths are unaffected. The bug is isolated to the `tokenAddress == address(0)` branch.

---

### Impact Explanation

Any native ETH transfer initiated on NEAR and routed through `OmniBridgeWormhole` for finalization on EVM is permanently unfinalizeable. The ETH is locked on NEAR (the NEAR side records the outbound transfer), but no relayer can ever successfully call `finTransfer` for it. This constitutes **permanent freezing of bridged ETH funds** across the Wormhole-routed flow.

---

### Likelihood Explanation

The `tokenAddress == address(0)` path is an explicitly supported and documented feature of `OmniBridge`. Any user who bridges native ETH from NEAR to EVM via the Wormhole deployment triggers this path. The revert is deterministic and 100% reproducible — no special conditions are required.

---

### Recommendation

In `OmniBridgeWormhole.finTransferExtension`, do not use `msg.value` as the Wormhole fee when a native ETH amount has already been disbursed. The base contract should pass the remaining value (i.e., `msg.value − payload.amount` for native ETH transfers) into `finTransferExtension`, or `finTransferExtension` should receive an explicit `wormholeFee` parameter that excludes the disbursed ETH amount. The `initTransferExtension` already follows this correct pattern — it receives an explicit `value` parameter computed as `msg.value − nativeFee − amount`: [4](#0-3) [5](#0-4) 

Apply the same pattern to `finTransferExtension`: pass `msg.value − payload.amount` (for native ETH) or `msg.value` (for ERC-20) as the Wormhole fee.

---

### Proof of Concept

1. User initiates a native ETH transfer from NEAR to EVM via the Wormhole bridge path.
2. Relayer calls `OmniBridgeWormhole.finTransfer(sig, payload)` with `payload.tokenAddress = address(0)`, `payload.amount = 1 ether`, and `msg.value = 1 ether + wormholeFee`.
3. `finTransfer` sends `1 ether` to `payload.recipient` — contract balance is now `wormholeFee`.
4. `finTransferExtension` calls `_wormhole.publishMessage{value: msg.value}(...)` = `{value: 1 ether + wormholeFee}`.
5. Contract only holds `wormholeFee` → EVM reverts with insufficient balance.
6. All state changes (nonce mark, ETH send) are rolled back.
7. No relayer can ever finalize this transfer; the ETH is permanently locked on NEAR. [6](#0-5) [7](#0-6)
