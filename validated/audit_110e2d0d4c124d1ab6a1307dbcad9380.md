### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Enabling Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the universal `BlockSupportsPeras` instance is a placeholder stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic or structural validation whatsoever. This function is wired directly into the production node-to-node `PerasCertDiffusion` miniprotocol handler. Any unprivileged peer can therefore inject an arbitrary crafted `PerasCert` — targeting any block hash and any round number — which will be accepted, stored in the `ChainDB`, and used to boost that block's chain weight, potentially triggering a chain-selection fork switch to a non-canonical chain.

---

### Finding Description

**Root cause — stub validation function:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must approve a certificate before it enters the node's state. The universal instance (the only one in the codebase) implements it as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

It never returns `Left`. No aggregate-signature check, no committee-membership check, no round-number bounds check, no boosted-block existence check — nothing. [1](#0-0) 

**Production wiring — cert diffusion inbound handler:**

`makePerasCertPoolWriterFromChainDB` is the production writer used by the node-to-node cert diffusion handler. It passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← stub, always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is registered as the inbound handler for the `PerasCertDiffusion` miniprotocol in the node-to-node application:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [3](#0-2) 

**End-to-end exploit path:**

1. Peer connects via node-to-node protocol and speaks the `PerasCertDiffusion` miniprotocol.
2. Peer sends a crafted `PerasCert{pcCertRound = r, pcCertBoostedBlock = p}` for any round `r` and any block point `p`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right (ValidatedPerasCert cert boost)`.
4. The validated cert is passed to `ChainDB.addPerasCertAsync`.
5. Per the `ChainDB` API contract: *"If this leads to a fork to be weightier than our current selection, this will trigger a fork switch."* [4](#0-3) 
6. The node may switch to the attacker-chosen chain.

**Contrast with the vote path:** The vote diffusion handler deliberately passes `(pure (PerasVoteStakeDistr mempty))` — an empty stake distribution — so all votes from peers fail `validatePerasVote` and are rejected. The certificate path has no equivalent guard. [5](#0-4) 

---

### Impact Explanation

**Impact: High — Chain selection bug enabling unauthorized chain-weight manipulation.**

A Peras certificate carries a `vpcCertBoost :: PerasWeight` that is added to the weight of the boosted block's chain. [6](#0-5)  An attacker who can inject arbitrary certificates can:

- Boost any block (including one on a minority fork) to make it appear heavier than the honest chain.
- Trigger a chain-selection fork switch on the victim node, causing it to prefer a non-canonical chain.
- Repeat for multiple rounds to sustain the deviation.

This directly violates the Peras security assumption that only legitimately elected committee members can issue valid certificates. The impact matches the "High" category: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

**Likelihood: High.**

- No privileged access is required. Any node that accepts inbound node-to-node connections is reachable.
- The `PerasCertDiffusion` miniprotocol is registered and active in the production handler table.
- The crafted message is a simple CBOR-encoded `PerasCert` with two fields (`pcCertRound :: Word64`, `pcCertBoostedBlock :: Point blk`). No cryptographic material is needed.
- The only existing guard (`processCerts` deduplication by round number) only prevents re-injection of a cert for a round already in the DB; it does not prevent the first injection for any new round. [7](#0-6) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that verifies:

1. **Aggregate BLS signature** over `(pcCertRound, pcCertBoostedBlock)` against the aggregated public keys of the claimed committee members.
2. **Committee membership and eligibility** of each signer for the given round, using the epoch nonce and stake distribution from the ledger view at the relevant slot.
3. **Quorum threshold** — the aggregate stake of the signers must exceed the configured Peras quorum.
4. **Round validity** — `pcCertRound` must fall within the current or recent window; stale or future rounds should be rejected.

Until the real implementation is ready, the cert diffusion inbound handler should be disabled or gated behind a feature flag (analogous to how the vote path is currently neutralized by passing an empty stake distribution). [1](#0-0)

### Proof of Concept

**Setup:** A private testnet with one honest node `N` running the Peras-enabled consensus layer.

**Steps:**

1. Connect a malicious peer `A` to `N` via the node-to-node protocol, negotiating a version that includes `PerasCertDiffusion`.
2. Identify a block `B_fork` on a minority fork (e.g., a block that `N` has seen but not selected).
3. Construct a `PerasCert`:
   ```
   pcCertRound      = <any round not yet in N's cert DB>
   pcCertBoostedBlock = <point of B_fork>
   ```
   No signature or committee data is required.
4. Send the cert to `N` via the `PerasCertDiffusion` miniprotocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right`.
6. `ChainDB.addPerasCertAsync` stores the cert and recomputes chain weights.
7. **Expected outcome:** `N` switches its selected chain to the fork containing `B_fork`, as the injected boost makes that fork heavier than the honest chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
