### Title
Peras Certificate Quorum and Signature Checks Absent at Receipt Phase Enables Unauthorized Certificate Acceptance and Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras certificate lifecycle has a two-phase structure that directly mirrors the Pool contract's proposal/execution split. The quorum invariant — "a certificate must represent a quorum of votes from the correct committee" — is enforced only during **local vote aggregation** (the proposal phase), but is **entirely absent** when a certificate is received from a remote peer via the object-diffusion mini-protocol (the execution phase). The production `validatePerasCert` implementation unconditionally returns `Right` without performing any quorum, committee-membership, or cryptographic check. An unprivileged peer can therefore inject a crafted `PerasCert` for any round targeting any block, which will be accepted, stored in `PerasCertDB`, and used to boost that block's weight in chain selection.

---

### Finding Description

**Phase 1 — Local vote aggregation (the "proposal" phase):**

`updateCandidateVoteState` calls `votesReachQuorum`, which calls `stakeAboveThreshold` to verify that the total stake of the collected votes exceeds the quorum threshold. Only if this check passes is a certificate forged via `forgePerasCert`. [1](#0-0) [2](#0-1) 

**Phase 2 — Remote certificate receipt (the "execution" phase):**

`processCerts`, called from both `makePerasCertPoolWriterFromCertDB` and the production path `makePerasCertPoolWriterFromChainDB`, invokes `validatePerasCert mkPerasParams` for every inbound certificate. [3](#0-2) 

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right ValidatedPerasCert{...}` — no quorum check, no committee-membership check, no cryptographic signature verification: [4](#0-3) 

The `mkPerasParams` argument is a hardcoded stub, not ledger-state-derived parameters: [5](#0-4) 

**Structural analog to the Pool contract bug:**

| Pool contract | Ouroboros Consensus |
|---|---|
| `removeFromCommittee` checks `committeeArray.length > committeeThreshold` at proposal time | `updateCandidateVoteState` checks `votesReachQuorum` / `stakeAboveThreshold` at local aggregation time |
| `_executeRemoveFromCommittee` omits the check at execution time | `validatePerasCert` omits all checks at certificate receipt time |
| Two proposals queued → invariant violated on both executing | Crafted cert from peer bypasses quorum invariant entirely |

The accepted certificate is then fed into `chainSelSync`, which stores it in `PerasCertDB` and triggers chain selection, boosting the weight of the attacker-chosen block: [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` for any round, targeting any block. Because `validatePerasCert` always returns `Right`, the certificate is accepted, stored in `PerasCertDB`, and used by `chainSelSync` to add `perasWeight` to the targeted block's chain-selection weight. This allows the peer to make the node prefer a non-canonical chain — a direct bypass of Peras certificate/vote checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

Any peer connected via the object-diffusion mini-protocol can send crafted certificates. No special privileges, stake, or cryptographic keys are required. The attack path is fully reachable from an unprivileged network peer.

---

### Recommendation

1. Implement `validatePerasCert` to verify: (a) quorum threshold — total stake of the votes in the certificate exceeds `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`; (b) committee membership — each voter is an eligible committee member for the round; (c) cryptographic signatures — each vote is signed by the claimed voter's key.
2. Replace the hardcoded `mkPerasParams` stub with the actual `PerasCfg` derived from the current ledger state, so that the quorum threshold and committee are consistent with the chain state at the time of receipt.
3. Apply the same checks in `chainSelSync` before a certificate is allowed to influence chain selection, mirroring the pattern of re-validating at execution time as recommended in the external report.

---

### Proof of Concept

1. Connect to a target node as a peer via the object-diffusion mini-protocol.
2. Construct a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block on a minority fork.
3. Send the certificate to the node. `processCerts` calls `validatePerasCert mkPerasParams`, which returns `Right` unconditionally.
4. The certificate is stored in `PerasCertDB` and `chainSelSync` is triggered.
5. The targeted block receives an additional weight of `perasWeight` (currently 15) in chain selection.
6. If the minority fork's accumulated Peras boost exceeds the honest chain's lead, the node switches to the attacker-chosen fork — accepting a non-canonical chain without any legitimate quorum having been reached.

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
