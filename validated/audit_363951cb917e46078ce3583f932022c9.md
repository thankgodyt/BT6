### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance, which is the only active instance for all block types including production Cardano blocks, implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives. Any unprivileged peer can send a crafted Peras certificate via the ObjectDiffusion mini-protocol; the certificate bypasses all validation and is stored in the `PerasCertDB` / `ChainDB`, where it can influence Peras chain-selection boosts.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate that must verify a received `PerasCert` before it is stored and used to boost a block's chain-selection weight. The only deployed instance is the catch-all `instance StandardHash blk => BlockSupportsPeras blk`, which provides:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No cryptographic signature check, no committee-membership check, no round-number range check, and no timing constraint is applied. The function assigns the full `perasWeight` boost to every certificate regardless of its content.

This stub is invoked directly in the production inbound-certificate pipeline. `processCerts` (called from both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` then stores every certificate that passes this non-validation:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, the `errs` branch is unreachable and every inbound certificate is accepted and forwarded to `ChainDB.addPerasCertAsync`.

The analogous `validatePerasVote` path also carries a TODO for full validation, but at minimum it checks stake-distribution membership; `validatePerasCert` performs no check at all. [4](#0-3) 

---

### Impact Explanation

Peras certificates boost a block's chain-selection weight by `perasWeight`. An adversary who can send a certificate claiming to boost an adversarial block will have that certificate accepted, stored, and applied to chain selection without any cryptographic or committee check. This enables:

- **Unauthorized chain-selection manipulation**: a crafted certificate can boost an adversarial fork, causing honest nodes to prefer it over the canonical chain.
- **Certificate/vote verification bypass**: the entire Peras certificate-verification gate is absent, matching the "Bypass of … certificate … checks" impact class.

This is the direct analog of the external report: just as a validator group owner could call `updateCommission` immediately before reward distribution to redirect all rewards, an adversary here can inject a certificate immediately before chain selection to redirect the Peras boost to an arbitrary block — with no delay, no cryptographic barrier, and no committee check.

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol for Peras certificates is active in the production node. Any connected peer can submit a `[PerasCert blk]` batch. The `processCerts` function is the sole inbound gate, and it delegates validation entirely to the stub. No operator action or key compromise is required; a single network message suffices to inject an accepted certificate.

---

### Recommendation

Replace the stub with a real implementation that enforces, at minimum:

1. **Cryptographic signature verification** of the certificate against the claimed committee.
2. **Committee-membership check**: the signers must be elected members for the claimed round.
3. **Round-number range check**: the certificate's round must be within the current or immediately preceding Peras round window.
4. **Boosted-block existence check**: the boosted block must be a known block on a plausible chain.

Until a real implementation is available, the ObjectDiffusion inbound path for Peras certificates should either be disabled or gated behind a feature flag so that the stub is never reachable from untrusted peers in production.

---

### Proof of Concept

1. Connect to a production Cardano node that has the ObjectDiffusion Peras-certificate mini-protocol enabled.
2. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to an adversarial block.
3. Send the certificate batch via the mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
5. The certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`.
6. The ChainDB stores the certificate; the Peras chain-selection logic applies the boost to the adversarial block, potentially causing the node to prefer the adversarial chain. [5](#0-4) [6](#0-5)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
