### Title
`max_change_amount` Enforcement Skipped When `input_num <= change_num` in Withdrawal PSBT — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary
The `max_change_amount` cap on change outputs in `check_withdraw_psbt` is guarded by `if input_num > change_num`. Any withdrawal PSBT where the number of inputs does not exceed the number of change outputs bypasses this cap entirely, allowing an unprivileged caller to create change UTXOs of arbitrary size (up to `min_input_amount`).

### Finding Description
In `check_withdraw_psbt` (lines 227–236), the check `change_amounts.all(|v| v < config.max_change_amount)` is wrapped in `if input_num > change_num`. When `input_num <= change_num`, the block is skipped and no upper bound is enforced on individual change output values.

`check_withdraw_psbt_valid` (lines 56–60) only enforces a relationship between `input_num` and `change_num` when `utxo_num` is outside the passive management band. Within the band — the normal operating range — no such constraint exists, so `input_num <= change_num` is freely submittable.

The only remaining per-change guard is `output_value < min_input_amount`. When the bridge holds UTXOs larger than `max_change_amount` (routine), an attacker can set a change output to any value in `[max_change_amount, min_input_amount)`, violating the invariant.

### Impact Explanation
The resulting oversized change UTXO is registered in the bridge's UTXO set. `check_psbt_output_all_change_address` enforces `<= max_change_amount` on all outputs for both active management and cancel operations, so the oversized UTXO cannot participate as an output in those flows. This strands it from the normal UTXO management pipeline, requiring operator intervention to spend it. No direct theft of funds occurs; the impact is a policy bypass causing operational disruption and potential temporary locking of the affected UTXO.

**Severity: Medium** — Bypass of bridge limits/policies; attacker-triggered operational disruption without direct fund theft.

### Likelihood Explanation
The attack is reachable by any user who can transfer nBTC to the bridge (i.e., any nBTC holder). The precondition — `utxo_num` within the passive management band — is the normal steady-state of the bridge. No privileged role is required.

### Recommendation
Remove the `if input_num > change_num` condition and enforce `max_change_amount` unconditionally for all change outputs in `check_withdraw_psbt`:

```rust
// Replace lines 227-237 with:
require!(
    change_amounts.into_iter().all(|v| v < config.max_change_amount),
    format!("Any change amount should be less than {}", config.max_change_amount)
);
```

### Proof of Concept
1. Bridge is in normal state: `passive_management_lower_limit <= utxo_num <= passive_management_upper_limit`.
2. Bridge holds UTXOs each worth `min_input_amount = 10_000_000 sat`; `max_change_amount = 5_000_000 sat`.
3. Attacker calls `ft_on_transfer` with a `Withdraw` message specifying 2 inputs and 3 change outputs, each change output valued at `7_000_000 sat` (< `min_input_amount`, >= `max_change_amount`).
4. `check_withdraw_psbt_valid`: `utxo_num` is in-band → no `input_num`/`change_num` constraint.
5. `check_withdraw_psbt`: `input_num (2) <= change_num (3)` → `max_change_amount` block skipped; `7_000_000 < 10_000_000` passes the `< min_input_amount` check.
6. Three `7_000_000 sat` change UTXOs are registered, each exceeding `max_change_amount`, and are subsequently rejected as outputs by `check_psbt_output_all_change_address` in any active management PSBT.
