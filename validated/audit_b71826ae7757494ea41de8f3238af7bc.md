### Title
Attached NEAR Deposit Permanently Stuck in Bridge on MPC Signing Failure - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
`sign_btc_transaction` is a publicly accessible `#[payable]` function that forwards the caller's entire `env::attached_deposit()` to the MPC chain-signatures contract. When the MPC cross-contract call fails, NEAR protocol returns the deposit to the bridge contract, but `sign_btc_transaction_callback` contains no refund logic — it simply returns `false`. The caller's attached NEAR is permanently locked inside the bridge with no recovery path.

### Finding Description
`sign_btc_transaction` is marked `#[payable]` and has no role restriction beyond the global pause guard, making it callable by any NEAR account that holds a valid `btc_pending_sign_id`. [1](#0-0) 

Internally it delegates to `internal_sign_btc_transaction`, which calls `sign_promise`. `sign_promise` forwards the **full** `env::attached_deposit()` to the MPC contract: [2](#0-1) 

The callback that handles the MPC response is: [3](#0-2) 

On the failure branch (`else { false }`), there is no `Promise::new(original_caller).transfer(env::attached_deposit())` or equivalent. [4](#0-3) 

When the MPC call fails, NEAR protocol credits the deposit back to the bridge contract's own balance. Because the callback does not issue a refund promise, those tokens are permanently stranded in the bridge with no sweep or recovery function visible in the production surface.

There is also a secondary variant: if the caller attaches more NEAR than the MPC contract requires, MPC may refund the excess to the bridge. The bridge again has no mechanism to forward that excess to the original caller.

### Impact Explanation
Every failed MPC signing attempt causes the caller's attached NEAR deposit to be permanently locked inside the bridge contract. There is no operator-callable sweep or user-callable reclaim function for these stranded deposits. Over time, repeated MPC failures (e.g., during MPC service degradation) accumulate irrecoverable NEAR inside the bridge. This constitutes a permanent, publicly-reachable loss of user funds without direct theft.

**Impact: Low** — Publicly reachable stuck-state fault in a production bridge path; no direct theft of BTC/nBTC, but real NEAR is permanently lost per failed signing call.

### Likelihood Explanation
`sign_btc_transaction` is permissionless (any account with a pending sign ID can call it). MPC signing can fail due to transient MPC service unavailability, gas exhaustion in the MPC contract, or network issues. Any user who calls `sign_btc_transaction` during such a window loses their attached deposit. Likelihood is low-to-medium given MPC is an external dependency with its own availability profile.

### Recommendation
In `sign_btc_transaction_callback`, on the failure branch, issue a refund promise back to the original caller:

```rust
} else {
    // Refund the attached deposit to the original caller on MPC failure
    Promise::new(account_id).transfer(env::attached_deposit());
    false
}
```

Alternatively, enforce `env::attached_deposit() == expected_mpc_fee` at the entry point so that no excess can accumulate, and document the exact required amount in the view API.

### Proof of Concept

1. User initiates a withdrawal via `ft_transfer_call`; bridge creates a `BTCPendingInfo` entry.
2. User calls `sign_btc_transaction(btc_pending_sign_id, 0, 0)` attaching 1 NEAR (the MPC signing fee).
3. `sign_promise` forwards the full 1 NEAR to the MPC contract via `.with_attached_deposit(env::attached_deposit())`.
4. The MPC contract call fails (service temporarily unavailable or gas issue).
5. NEAR protocol returns 1 NEAR to the bridge contract's balance.
6. `sign_btc_transaction_callback` is invoked; the `else` branch executes and returns `false` — no refund promise is issued.
7. The 1 NEAR is now permanently locked in the bridge. The user must re-attach NEAR and retry, losing the first deposit with no recourse. [2](#0-1) [4](#0-3)
