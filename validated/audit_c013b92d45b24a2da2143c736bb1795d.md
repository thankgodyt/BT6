### Title
Unprotected Initializer Allows Frontrunning to Seize Control of nBTC Token Contract - (File: contracts/nbtc/src/lib.rs)

### Summary
The `nbtc` token contract's `new()` initializer carries no caller restriction. Any unprivileged NEAR account that calls it before the legitimate deployer becomes the `controller` and can supply an arbitrary `bridge_id`, granting that account the exclusive right to mint and burn nBTC.

### Finding Description
`contracts/nbtc/src/lib.rs` exposes a public `#[init]` function `new()` that accepts `controller` and `bridge_id` as caller-supplied parameters: [1](#0-0) 

The only guard present is: [2](#0-1) 

`require!(!env::state_exists(), "Already initialized")` prevents a *second* call, but it does not restrict *who* makes the first call. NEAR's `#[init]` macro adds no implicit access control; it only enforces single-initialization semantics.

The `bridge_id` field is the sole gatekeeper for `mint()` and `burn()`: [3](#0-2) 

If an attacker supplies their own contract address as `bridge_id`, they satisfy `assert_bridge()` and can call `mint()` freely: [4](#0-3) 

The `controller` field is equally attacker-controlled, giving the attacker the ability to call `set_controller()`, `set_metadata()`, and `set_withdraw_relayer_address()`: [5](#0-4) 

An analogous unprotected initializer exists in `contracts/satoshi-bridge/src/lib.rs` where the caller of `new()` is unconditionally granted DAO/super-admin roles: [6](#0-5) 

### Impact Explanation
An attacker who wins the initialization race on the nBTC contract can:
1. Mint an unlimited supply of nBTC to any account by calling `mint()` through their own `bridge_id` contract.
2. Burn legitimate users' balances via `burn()`.
3. Redirect the `withdraw_relayer_address`, silently stealing withdrawal funds.

This directly satisfies the **Critical** impact class: *Unauthorized minting of nBTC* and *significant theft or destruction of user funds*.

### Likelihood Explanation
NEAR deployment tooling (`near deploy --initFunction`) can atomically bundle code deployment and initialization in a single transaction batch, which would prevent frontrunning. However, if the deployer issues the WASM deployment and the `new()` call in two separate transactions — a common pattern in scripted or staged deployments — a window exists for any observer of the mempool/transaction stream to race in with their own `new()` call. Given that this is a production bridge, the risk is real and the cost of exploitation is a single cheap NEAR transaction.

### Recommendation
Add an explicit caller check at the top of `new()` in both `contracts/nbtc/src/lib.rs` and `contracts/satoshi-bridge/src/lib.rs`. The simplest approach is to require that the predecessor is the contract's own account ID (i.e., the deployer):

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

Alternatively, accept an `owner` parameter and verify `env::predecessor_account_id() == owner`, mirroring the pattern used in the satoshi-bridge's privileged management functions such as `add_super_admin`: [7](#0-6) 

### Proof of Concept
1. Deployer broadcasts transaction A: deploy nBTC WASM to `nbtc.near`.
2. Attacker observes transaction A and immediately broadcasts transaction B (higher priority / same block):
   ```
   nbtc.near::new(
     controller = "attacker.near",
     bridge_id  = "attacker-bridge.near",
     ...
   )
   ```
3. Transaction B executes first; state is written with attacker-controlled fields.
4. Deployer's legitimate `new()` call reverts with `"Already initialized"`.
5. Attacker calls `attacker-bridge.near::trigger_mint()` which cross-contract calls `nbtc.near::mint(attacker.near, U128::MAX, ...)`.
6. `assert_bridge()` passes because `env::predecessor_account_id() == "attacker-bridge.near" == self.bridge_id`.
7. Attacker holds an unbacked nBTC balance and can sell or redeem it against the bridge's BTC reserves.
