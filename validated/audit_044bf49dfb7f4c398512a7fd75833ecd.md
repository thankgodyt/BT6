### Title
Chain Sync Client Uses `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Instead of Actual Peras Weights, Enabling Incorrect Peer Disconnection and Non-Canonical Chain Adoption When Peras Is Active - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the Chain Sync client unconditionally uses `emptyPerasWeightSnapshot` (zero Peras weight) when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. The actual chain selection logic in `ChainSel.hs` uses the real `PerasWeightSnapshot` from `getPerasWeightSnapshot`. This inconsistency is structurally identical to the Plaza Finance bug: a metric valid only for one context (non-Peras, block-count-only comparison) is applied unconditionally to all contexts, including the Peras-active case where total weight (block count + certificate boosts) governs chain preference. When Peras is active, a peer offering the canonical Peras-boosted chain (fewer blocks, higher total weight) is incorrectly classified as non-preferred and disconnected, while an adversary-controlled chain with more blocks but zero Peras weight is retained.

---

### Finding Description

In `checkPreferTheirsOverOurs`:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always uses zero Peras weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`. When the snapshot is empty it falls into the block-count-only path; when non-empty it computes `weightedSelectView`, which sums `BlockNo` and `wsvWeightBoost` (Peras certificate boosts):

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count only
      ...
  | otherwise =
      -- uses weightedSelectView: BlockNo + PerasWeight boost
      ...
``` [2](#0-1) 

The chain selection path in `constructPreferableCandidates` and `chainSelection` always passes the real `weights` snapshot obtained from `getPerasWeightSnapshot`:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [3](#0-2) 

`checkPreferTheirsOverOurs` is invoked when the node cannot forecast a ledger view for the peer's current slot (the slot is beyond the forecast horizon). In that case the node must decide whether to stay connected or disconnect. The decision is made with `emptyPerasWeightSnapshot`, so it is always a pure block-count comparison — regardless of whether Peras is active.

The `WeightedSelectView` total weight is `BlockNo + PerasWeight`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

When Peras certificates have boosted blocks on the honest chain, the honest chain can have fewer raw blocks than an adversary chain yet be strictly preferred by total weight. `checkPreferTheirsOverOurs` cannot see this and disconnects from the honest peer.

---

### Impact Explanation

When Peras is active:

1. An adversary presents a chain with `N_adv` blocks and zero Peras boosts to the target node. The target node adopts it (more blocks than the current chain).
2. Honest peers hold the canonical chain with `N_hon < N_adv` blocks but with Peras certificate boosts `B` such that `N_hon + B > N_adv` (canonical chain is heavier).
3. When the target node connects to honest peers and their headers are beyond the forecast horizon, `checkPreferTheirsOverOurs` is called.
4. Using `emptyPerasWeightSnapshot`, the honest chain appears non-preferred (`N_hon < N_adv`).
5. The node throws `CandidateTooSparse` and disconnects from the honest peer.
6. The node remains on the adversary's lighter (non-canonical) chain.

If the adversary can cause disconnection from all honest peers in this way, the node is permanently isolated on the non-canonical chain. This is a chain selection safety failure: an unprivileged peer can cause an honest node to prefer a non-canonical chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

- Peras is an active development track in this repository; the `PerasWeightSnapshot` infrastructure is already wired into production chain selection.
- The condition (headers beyond the forecast horizon) arises naturally during initial sync and after network partitions.
- The adversary needs only to produce a chain with more raw blocks than the honest Peras-boosted chain — no stake majority is required; a modest stake advantage during a window where honest blocks are being boosted suffices.
- The bug is self-confirming: the TODO comment at line 1841 explicitly acknowledges the check is broken with respect to Peras (`"TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64"`), confirming the developers recognise the inconsistency.

---

### Recommendation

Either:

1. **Pass the real weight snapshot**: replace `emptyPerasWeightSnapshot` with the actual `PerasWeightSnapshot` obtained from `ChainDB.getPerasWeightSnapshot` (as done everywhere else in chain selection), so the comparison in `checkPreferTheirsOverOurs` is consistent with the chain selection decision that will ultimately be made; or
2. **Remove the check entirely** as the TODO comment proposes, since the check is only a heuristic guard and its incorrectness under Peras makes it actively harmful.

The fix is directly analogous to the Plaza Finance mitigation: gate the special-case comparison on the relevant context (non-Peras) rather than applying it unconditionally to all cases.

---

### Proof of Concept

```
Peras active; certificate boost B = 1000 weight units.

Honest chain  : 100 blocks, boosted → total weight = 1100
Adversary chain: 150 blocks, no boost → total weight = 150

Step 1: Adversary sends its 150-block chain to target node.
        Chain selection (real weights): 150 < 1100 → adversary chain NOT preferred.
        But target node has not yet seen the honest chain; it starts from genesis
        and adopts the adversary chain (150 > 0).

Step 2: Target node connects to honest peer.
        Honest peer's tip is beyond the forecast horizon.
        checkPreferTheirsOverOurs called with emptyPerasWeightSnapshot:
          preferAnchoredCandidate emptyPerasWeightSnapshot ourFrag theirFrag
          → block-count only: 100 < 150 → honest chain NOT preferred
          → throwSTM CandidateTooSparse → disconnect.

Step 3: Target node stays on adversary's 150-block non-canonical chain.
        Actual chain selection (real weights) would have preferred honest chain
        (1100 > 150), but the node never reaches that point.
