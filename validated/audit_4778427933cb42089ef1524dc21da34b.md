Audit Report

## Title
Missing Zero-Address Validation on Transfer Recipient Permanently Freezes Bridged ERC-20 Funds - (File: near/omni-bridge/src/lib.rs)

## Summary
The `init_transfer` function in `near/omni-bridge/src/lib.rs` validates only that the recipient chain is not NEAR, but never calls `recipient.is_zero()` despite that helper being fully implemented in `near/omni-types/src/lib.rs`. A user supplying `recipient = OmniAddress::Eth(H160::ZERO)` causes tokens to be locked in the NEAR bridge permanently: after MPC signing succeeds and the transfer message is removed from NEAR storage, every `finTransfer` attempt on the EVM side reverts because OpenZeppelin ERC-20/ERC-1155/BridgeToken contracts reject transfers to `address(0)`, and no on-chain recovery path exists.

## Finding Description
`init_transfer` (L531–534) performs exactly one recipient-side check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

It does not call `recipient.is_zero()`, even though `OmniAddress::is_zero()` is fully implemented in `near/omni-types/src/lib.rs` (L299–313) for all EVM chains. The zero-address recipient is stored verbatim in `TransferMessage` (L540–553) and later copied into `TransferMessagePayload` (L491–500) without any additional validation.

In `sign_transfer_callback` (L655–658), when the MPC signing succeeds and `fee.is_zero()`, the transfer message is removed from NEAR storage:

```rust
if let Ok(signature) = call_result {
    if fee.is_zero() {
        self.remove_transfer_message(message_payload.transfer_id);
    }
```

This removal is unconditional with respect to whether EVM finalization will succeed. On the EVM side, `finTransfer` in `OmniBridge.sol` marks the destination nonce used at L287 before attempting the transfer. For ERC-20 tokens (L351–354), bridge tokens (L339–342), and ERC-1155 tokens (L324–330), OpenZeppelin reverts on `to == address(0)`, causing the entire EVM transaction to revert (including the nonce mark). The relayer can retry indefinitely, but every attempt reverts identically. The NEAR-side tokens remain locked in the bridge contract with the transfer message already deleted and no public cancellation or refund entrypoint available.

The `InvalidRecipient` error variant already exists in `near/omni-types/src/errors.rs` but is never applied in `init_transfer`.

## Impact Explanation
This constitutes **permanent freezing of bridged funds**: any ERC-20, ERC-1155, or bridge token transferred from NEAR to an EVM chain with `recipient = address(0)` is irreversibly locked in the NEAR bridge contract. The MPC signature is valid, the NEAR transfer message is deleted, and EVM finalization is permanently blocked. This matches the allowed critical impact: *permanent freezing of bridged funds across NEAR and EVM chains*.

## Likelihood Explanation
The entry point is `ft_transfer_call` on NEAR, callable by any token holder with no special role or privilege. The attacker (or a misconfigured dApp) need only supply `"eth:0x0000000000000000000000000000000000000000"` as the recipient string. The condition is trivially reachable, repeatable for any registered ERC-20 or ERC-1155 token, and realistic as an accidental dApp bug or deliberate exploit.

## Recommendation
Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipient.as_ref()
);
```

The `InvalidRecipient` error variant already exists in `near/omni-types/src/errors.rs` and requires no new additions.

## Proof of Concept
1. Alice holds 1000 USDC as a NEP-141 token on NEAR.
2. Alice calls `ft_transfer_call` on the USDC NEP-141 contract, transferring 1000 tokens to the NEAR bridge with message `{"InitTransfer": {"recipient": "eth:0x0000000000000000000000000000000000000000", "fee": "0", "native_token_fee": "0"}}`.
3. `init_transfer` passes the only check (`get_chain() != Near`) and stores `TransferMessage` with `recipient = OmniAddress::Eth(H160::ZERO)`.
4. A relayer calls `sign_transfer`. The MPC signs a `TransferMessagePayload` containing `recipient = 0x0000...0000`. Because `fee.is_zero()`, `sign_transfer_callback` calls `remove_transfer_message`, deleting the record from NEAR storage.
5. The relayer submits `finTransfer` on Ethereum. The signature is valid. `completedTransfers[nonce] = true` is set. The contract reaches `IERC20(payload.tokenAddress).safeTransfer(address(0), 1000)`, which reverts with `ERC20InvalidReceiver`. The entire EVM transaction reverts, including the nonce mark.
6. Every retry of step 5 reverts identically. Alice's 1000 USDC are permanently locked in the NEAR bridge with no recovery path.
