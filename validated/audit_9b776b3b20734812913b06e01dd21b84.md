### Title
Fee Truncation in `BridgeFee::get_fee` Rounds Down, Systematically Undercharging Users — (File: `contracts/satoshi-bridge/src/config.rs`)

### Summary

`BridgeFee::get_fee` computes the bridge fee using integer division that always truncates toward zero. Because the rounding always favors the user, every withdrawal (and deposit) where `amount * fee_rate` is not an exact multiple of `MAX_RATIO` results in the protocol collecting one fewer satoshi than the mathematically correct fee. Any unprivileged bridge user can exploit this systematically by choosing withdrawal amounts that maximize the truncation remainder, accumulating a fee discount across many transactions.

### Finding Description

`BridgeFee::get_fee` in `contracts/satoshi-bridge/src/config.rs` computes the bridge fee as:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
``` [1](#0-0) 

`MAX_RATIO` is `10000`. Rust's `/` operator on integers truncates toward zero, so the computed fee is always `floor(amount * fee_rate / 10000)`. The mathematically correct fee is `amount * fee_rate / 10000`, which is not an integer whenever `(amount * fee_rate) % 10000 != 0`. In those cases the protocol receives one fewer satoshi than it should.

This fee is consumed in the withdrawal path. When a user calls `ft_transfer_call` on the nBTC token with a `Withdraw` message, the bridge's `ft_on_transfer` handler calls `create_btc_pending_info`, which computes:

```rust
let withdraw_fee = self.internal_config().withdraw_bridge_fee.get_fee(amount);
``` [2](#0-1) 

The `withdraw_fee` is then used to derive `actual_received_amount` and `burn_amount`:

```rust
burn_amount: actual_received_amount + gas_fee,
``` [3](#0-2) 

Because `burn_amount = amount - withdraw_fee`, a truncated (lower) `withdraw_fee` means the bridge burns less nBTC than it should, keeping less as protocol revenue. The user effectively receives a small discount on every withdrawal where the truncation fires.

The same function is used for the deposit fee path, as `deposit_bridge_fee` is also a `BridgeFee` instance: [4](#0-3) 

A secondary rounding issue exists in `get_protocol_and_relayer_fee`, where `protocol_fee` is also truncated down and the relayer absorbs the remainder:

```rust
pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
    let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
    let relayer_fee = fee_amount - protocol_fee;
    (protocol_fee, relayer_fee)
}
``` [5](#0-4) 

This means the protocol's share of the fee is also systematically rounded down, with the relayer receiving the extra satoshi.

### Impact Explanation

Every withdrawal or deposit where `(amount * fee_rate) % 10000 != 0` causes the protocol to collect one fewer satoshi than intended. An attacker who repeatedly withdraws amounts chosen to maximize the truncation remainder (e.g., `amount` such that `(amount * fee_rate) % 10000 == 9999`) pays the minimum possible fee on each transaction. Over many transactions this accumulates as a systematic, permanent loss of fee revenue to the protocol — an invariant violation in the bridge's fee accounting. No funds are directly stolen from users, but the protocol's nBTC backing is eroded by the uncollected fees.

This maps to the **Low** allowed impact: *Publicly reachable invariant-violation in production bridge/token paths without direct theft.*

### Likelihood Explanation

The truncation fires on every transaction where the amount is not an exact multiple of `MAX_RATIO / gcd(fee_rate, MAX_RATIO)`. With a typical `fee_rate` of 30 (0.3%) and `MAX_RATIO = 10000`, the truncation fires for any amount not divisible by `10000 / gcd(30, 10000) = 10000 / 10 = 1000` satoshis. Since most real withdrawal amounts are arbitrary satoshi values, the truncation fires on the vast majority of transactions. No special access or privilege is required — any user initiating a withdrawal triggers this path.

### Recommendation

Replace the truncating division with ceiling division so the fee always rounds in the protocol's favor:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    let rate = u128::from(self.fee_rate);
    let ratio = u128::from(MAX_RATIO);
    let fee = (amount * rate + ratio - 1) / ratio; // ceiling division
    std::cmp::max(fee, self.fee_min)
}
```

Apply the same ceiling division in `get_protocol_and_relayer_fee` for the `protocol_fee` split, and subtract from `fee_amount` to derive `relayer_fee`, so the protocol always receives at least its intended share.

### Proof of Concept

With `fee_rate = 30` and `MAX_RATIO = 10000`:

- User withdraws `amount = 9999` satoshis of nBTC.
- Correct fee: `9999 * 30 / 10000 = 29.997` → should charge **30** satoshis.
- Actual fee charged: `floor(299970 / 10000) = 29` satoshis.
- Protocol shortfall: **1 satoshi** per transaction.

An attacker repeating this withdrawal 1,000,000 times loses 1 satoshi of fee per iteration, costing the protocol **10,000 satoshis (0.0001 BTC)** in uncollected fees. The attacker pays only NEAR gas costs, which are negligible. The attack is permissionless and requires no special role — any account holding nBTC can call `ft_transfer_call` with a `Withdraw` message targeting any valid BTC address they control.
