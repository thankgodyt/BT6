### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peras Certificate via Object-Diffusion Inbound Path — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which is the **only** instance in the codebase and applies to all block types, implements `validatePerasCert` as an unconditional `Right`. Any structurally well-formed `PerasCert` received from a NodeToNode peer via the object-diffusion inbound protocol is accepted, stored in the `PerasCertDB` via `ChainDB`, and subsequently re-served to other peers by `objectDiffusionOutbound`. No committee-signature check, boosted-block existence check, round-number range check, or any other semantic validation is performed.

---

**Root cause — `SupportsPeras.hs:320,353-358`**

### Impact Explanation

An unprivileged NodeToNode peer can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` (pointing to a non-existent or adversarial block) and an arbitrary `pcCertRound`. The cert passes `validatePerasCert` unconditionally, is stored in the `PerasCertDB`, and is re-diffused to all connected peers. Chain selection then applies the `perasWeight = 15` boost to the adversarially chosen block, enabling an illegitimate chain-selection weight advantage without any stake, VRF key, KES key, or committee membership. This is a direct bypass of Peras certificate/signature validation and voting checks, matching the Critical scope: *"Bypass of leader eligibility, VRF/KES/certificate/signature validation, PBFT/Praos/TPraos/Peras voting or certificate checks, or hot-key rules that enables unauthorized block, vote, or certificate acceptance."*

---

### Likelihood Explanation

The exploit requires only a NodeToNode connection and the ability to send a well-formed `MsgReplyObjects` message containing a crafted `PerasCert`. No key material, stake, or privileged access is needed. The object-diffusion protocol is listed as a supported production path in the scope rules. The degenerate instance is in production source code (not test code) and is the only available instance. The TODO comments confirm the gap is known but unresolved.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that checks:
- Committee membership and aggregate/threshold signature over `(pcCertRound, pcCertBoostedBlock)`
- That `pcCertBoostedBlock` refers to a block present in the local chain or volatile DB
- That `pcCertRound` is within the valid window (not in the future beyond the forecast horizon, not older than `perasCertMaxRounds`)
- That no certificate for the same round already exists with a different boosted block

Until real validation is implemented, the object-diffusion inbound handler for `PerasCert` should be disabled or should unconditionally reject all inbound certificates.

  --
  -- We set tentatively T_heal to 2B/asc = 600 slots, as the CIP suggests a
  -- bigO(B/asc) for that value so that sufficiently many blocks are produced to
  -- overcome an adversarially boosted block.

  -- We also set tentatively perasCertArrivalThreshold (= X in the formal spec)
  -- to 30 slots (it must be strictly smaller than perasRoundLength)
  -- See https://github.com/tweag/cardano-peras/issues/88 and
  -- https://github.com/tweag/cardano-peras/issues/99 for more information on
  -- this parameter.

  -- We also have T_cp = 129_600 and T_cq = 43_200 as per the design document
  PerasParams
    { -- ceil(T_heal + T_cq) / perasRoundLength) as per the design document
      perasIgnoranceRounds =
        PerasIgnoranceRounds 487

        PerasCooldownRounds 1928

      perasBlockMinSlots =
        PerasBlockMinSlots 90

        PerasRoundLength 90
    , perasWeight =

    , perasQuorumStakeThreshold =
