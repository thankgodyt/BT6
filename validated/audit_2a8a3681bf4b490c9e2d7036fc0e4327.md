### Title
Orchard Bundle Action Count Mismatch Permanently Breaks All Standard-Wallet Shielded Withdrawals — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary

`EXPECTED_ACTIONS_NUMBER` is set to `1`, but the standard `orchard` crate `Builder` always pads bundles to a minimum of 2 actions (`MIN_ACTIONS = 2`). The strict equality check in `extract_orchard_bundle` therefore rejects every bundle produced by standard Zcash wallet tooling, making the shielded-withdrawal path permanently non-functional for all users.

---

### Finding Description

`EXPECTED_ACTIONS_NUMBER` is defined as `1`: [1](#0-0) 

The code's own comment acknowledges that the Orchard builder pads bundles to a minimum for privacy and links to `builder.rs#L36` in the upstream `orchard` crate — where `pub const MIN_ACTIONS: usize = 2` is defined. Despite this, the constant is set to `1`, creating a direct contradiction.

The enforcement check is a strict equality: [2](#0-1) 

Any bundle with `actions().len() != 1` is rejected. Because the standard `orchard::Builder` always produces at least 2 actions (padding a 1-note spend to 2 for privacy), every bundle built with standard tooling will have `actions().len() == 2` and will be rejected here.

`extract_orchard_bundle` is called from `PsbtWrapper::new` and `PsbtWrapper::from_original_psbt`, both of which convert the `Err` into a hard `env::panic_str`: [3](#0-2) 

The public entry point is `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `ft_on_transfer_callback` → `PsbtWrapper::new`: [4](#0-3) 

---

### Impact Explanation

Every shielded (Orchard) withdrawal submitted via standard Zcash wallet software is unconditionally rejected. The callback panics, the nZEC tokens are refunded by the NEP-141 protocol, so funds are not permanently lost — but the entire shielded-withdrawal feature is permanently non-functional for any user relying on standard tooling. This is a publicly reachable invariant-violation and panic-driven fault in a production bridge path, qualifying as **Low** under the allowed impact scope.

---

### Likelihood Explanation

Likelihood is **certain** for any user attempting a shielded withdrawal with standard Zcash wallet software. No special attacker capability is required; the bug is triggered by normal, correct usage of the `orchard` crate.

---

### Recommendation

Change `EXPECTED_ACTIONS_NUMBER` from `1` to `2` (matching `orchard::MIN_ACTIONS`), or replace the strict equality check with a minimum-count check (`>= EXPECTED_ACTIONS_NUMBER`) and update the output-recovery logic to handle the dummy padding action correctly. The `recover_output_with_ovk(0, &ovk)` call at index 0 may also need to iterate over all actions to find the real output rather than assuming index 0.

---

### Proof of Concept

1. Use the `orchard` crate `Builder` to construct a 1-note spend bundle targeting the bridge's Unified Address.
2. Observe the builder pads to 2 actions (`MIN_ACTIONS = 2`).
3. Serialize the bundle and submit it via `ft_on_transfer` with a `Withdraw` message containing `chain_specific_data.orchard_bundle_bytes`.
4. Observe the contract panics with `ERR_INVALID_ORCHARD_BUNDLE: failed to extract Orchard bundle` (root cause: `"Orchard bundle must have 1 actions, got 2"`).
5. Confirm the nZEC tokens are refunded but the withdrawal is rejected — reproducible for every standard-library-constructed bundle.
