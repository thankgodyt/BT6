### Title
Unprivileged Caller Can Redirect Victim's Unfinalized BTC Deposit to Attacker-Controlled Address via `request_refund` - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` imposes no ownership check on the caller. When a deposit's `DepositMsg` was constructed with `refund_address: None`, any unprivileged NEAR account can submit a refund request for that deposit and supply an arbitrary attacker-controlled BTC address as the `refund_address`. After the `unsafe_refund_timelock_sec` elapses, the same attacker calls `execute_refund` and the bridge MPC-signs a transaction that sends the victim's BTC to the attacker's address.

### Finding Description

`request_refund` is a public, permissionless entry point: [1](#0-0) 

The only caller-identity check inside it is for the optional `gas_fee` parameter: [2](#0-1) 

There is no check that `env::predecessor_account_id()` is the owner of the deposit (i.e., `deposit_msg.recipient_id`).

Inside `internal_request_refund`, the `refund_address` validation only fires when `deposit_msg.refund_address` is already `Some`: [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case — the field is `skip_serializing_if = "Option::is_none"` and optional by design), the caller-supplied `refund_address` is accepted verbatim and stored in the `RefundRequest`: [4](#0-3) 

`execute_refund` is also permissionless: [5](#0-4) 

`finalize_refund_with_psbt` builds the refund output directly from `refund_request.refund_address` — the address the attacker injected: [6](#0-5) 

The `DepositMsg` needed to reconstruct the deposit path is fully public: `get_user_deposit_address` emits it as an on-chain event, and the BTC deposit transaction is visible on the public blockchain. [7](#0-6) 

### Impact Explanation

An attacker can steal the full BTC value of any unfinalized deposit whose `DepositMsg` was created without a `refund_address`. The bridge MPC service signs a transaction paying the attacker's BTC address. This is a direct, complete loss of user funds — Critical severity.

The only code-level mitigation is the `unsafe_refund_timelock_sec` (default 14 days), during which DAO/Operator can call `reject_refund`. This is an operational control, not a code-level ownership guard, and it fails if the DAO/Operator is slow, offline, or overwhelmed by simultaneous requests. [8](#0-7) 

### Likelihood Explanation

- All inputs needed (deposit `tx_bytes`, `vout`, Merkle proof, `DepositMsg`) are publicly observable on the Bitcoin blockchain and NEAR event logs.
- The attacker pays only the anti-spam storage deposit (`required_balance_for_request_refund()`), a small NEAR amount, to attempt theft of arbitrarily large BTC.
- The attack targets deposits that are unfinalized — a normal operational state during any relayer delay, congestion, or outage.
- The 14-day window is the only barrier; a determined attacker simply waits.

Likelihood: **Medium** (requires a 14-day wait and DAO inaction, but all other preconditions are trivially met by any NEAR account).

### Recommendation

Add an ownership check in `request_refund` (or `internal_request_refund`) that enforces the caller is the deposit recipient when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may submit a refund without a pre-authorized refund_address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` always be `Some` (i.e., users must pre-authorize a refund address at deposit time), eliminating the caller-supplied address path entirely.

### Proof of Concept

1. Victim calls `get_user_deposit_address` with `DepositMsg { recipient_id: "victim.near", refund_address: None, ... }`. The event is emitted on-chain; the BTC deposit address is derived and published.
2. Victim sends BTC to the derived address. The transaction is confirmed on Bitcoin but the relayer has not yet called `verify_deposit_v2` (e.g., relayer is delayed).
3. Attacker observes the unfinalized BTC UTXO on-chain, reconstructs `deposit_msg` from the NEAR event log, fetches `tx_bytes` and builds a valid `TxInclusionProof`.
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's BTC tx>,
     vout = <victim's output index>,
     proof = <valid merkle proof>,
     gas_fee = None,
   )
   ```
   with the required NEAR storage deposit attached. The light-client proof passes; the `RefundRequest` is stored with `refund_address = "attacker_btc_address"`.
5. After `unsafe_refund_timelock_sec` (14 days) elapses without DAO/Operator intervention, attacker calls:
   ```
   execute_refund(utxo_storage_key = "<tx_id>@<vout>", chain_specific_data = None)
   ```
6. The bridge builds a PSBT paying `"attacker_btc_address"`, requests an MPC signature, and broadcasts the transaction. Victim's BTC is transferred to the attacker. [9](#0-8)

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,

        if gas_fee.is_some() {

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,

        )
    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
