### Title
Permissionless `sign_btc_transaction` with Attacker-Controlled `key_version` Permanently Locks User Withdrawal Funds - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

### Summary
The `sign_btc_transaction` function has no access control and accepts a caller-supplied `key_version` parameter. Any unprivileged NEAR account can front-run a legitimate user's signing call with a wrong `key_version`, causing the MPC service to produce and store a signature for the wrong key. Once stored, the "Already signed" guard in the callback prevents re-signing. The resulting Bitcoin transaction carries invalid signatures, can never confirm on-chain, and the user's nBTC remains permanently locked in the bridge with no self-recovery path.

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` carries only `#[payable]` and `#[pause]` decorators — no role restriction whatsoever:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,          // ← fully attacker-controlled
) -> PromiseOrValue<bool> {
```

The `key_version` is forwarded verbatim to the MPC chain-signatures service:

```rust
self.sign_promise(SignRequest {
    payload,
    path,
    key_version,   // ← attacker's value
})
```

The callback stores whatever signature the MPC returns and then enforces a one-time write:

```rust
require!(
    btc_pending_info.signatures[sign_index].is_none(),
    "Already signed"
);
btc_pending_info.signatures[sign_index] = Some(signature.clone());
```

Attack sequence:

1. User calls `ft_on_transfer` → bridge holds nBTC, creates `BTCPendingInfo`, moves UTXOs to `unavailable_utxos`.
2. Attacker monitors the chain for new `BTCPendingInfo` entries.
3. Attacker calls `sign_btc_transaction(id, 0, wrong_key_version)` before the user/relayer does.
4. MPC returns a valid ECDSA signature but for the wrong derived key (different `key_version` → different key path).
5. Callback stores the wrong signature at `signatures[0]`.
6. Legitimate user's subsequent call for `sign_index = 0` hits `"Already signed"` and panics.
7. When all inputs are "signed" (each potentially with wrong key), `tx_bytes_with_sign` is assembled and state advances to `PendingVerify`.
8. The assembled Bitcoin transaction has invalid signatures; Bitcoin miners reject it; it never confirms.
9. `verify_withdraw` is never successfully called; nBTC stays locked in the bridge; BTC UTXOs stay in `unavailable_utxos`.

There is no user-accessible recovery path. Only `cancel_withdraw`, restricted to `Role::DAO` or `Role::Operator`, can unblock the state.

### Impact Explanation

When a user initiates a withdrawal via `ft_on_transfer`, their nBTC is transferred to and held by the bridge contract. If the signing is corrupted, the user loses access to both their nBTC (locked in the bridge) and their BTC (UTXOs locked in `unavailable_utxos`). Without operator intervention the loss is permanent. This matches **Critical — significant loss or permanent locking of user funds**.

### Likelihood Explanation

The attack requires only:
- Watching the NEAR chain for new `BTCPendingInfo` entries (trivially done via event indexing).
- Calling a public, payable function with a crafted `key_version` before the legitimate signer does.

No special role, leaked key, or privileged access is needed. The attacker pays only the NEAR gas cost of one cross-contract call. Any withdrawal with at least one unsigned input is vulnerable from the moment it is created until the legitimate signing call lands.

### Recommendation

Restrict `sign_btc_transaction` so that only the withdrawal owner or a whitelisted relayer/keeper can call it:

```rust
// Option A: owner-only
let caller = env::predecessor_account_id();
require!(
    caller == btc_pending_info.account_id
        || self.acl_has_role(Role::UnrestrictedRelayer.into(), caller.clone())
        || self.acl_has_role(Role::DAO.into(), caller),
    "Unauthorized signer"
);
```

Alternatively, derive `key_version` from the contract's own configuration rather than accepting it from the caller, so the parameter cannot be weaponised:

```rust
let key_version = self.internal_config().key_version; // fixed, not caller-supplied
```

### Proof of Concept

```
1. Alice calls nbtc.ft_transfer_call(bridge, 100_000, WithdrawMsg{...})
   → bridge creates BTCPendingInfo{id: "abc", signatures: [None], ...}

2. Attacker observes the GenerateBtcPendingInfo event.

3. Attacker calls:
   bridge.sign_btc_transaction("abc", 0, 999)   // wrong key_version
   → MPC signs with key derived from version 999
   → sign_btc_transaction_callback stores signatures[0] = Some(<wrong sig>)

4. Alice calls:
   bridge.sign_btc_transaction("abc", 0, 0)     // correct key_version
   → MPC returns correct signature
   → sign_btc_transaction_callback: require!(signatures[0].is_none()) → PANIC "Already signed"

5. BTCPendingInfo now has an invalid signature. is_all_signed() returns true.
   tx_bytes_with_sign is assembled with the wrong signature.
   State advances to PendingVerify.

6. The assembled Bitcoin transaction is broadcast but rejected by miners (invalid sig).
   verify_withdraw is never called.
   Alice's nBTC remains locked in the bridge indefinitely.
```
