### Title
Adversary Can Pre-empt Peras Certificate Uniqueness Constraint to Inject Wrong Chain Boost — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

`processCerts` enforces a uniqueness constraint of one certificate per `PerasRoundNo`. Because `validatePerasCert` is currently a stub that unconditionally accepts any certificate without signature or committee verification, an unprivileged peer can send a crafted certificate for any round with an arbitrary boosted block before the legitimate certificate arrives. The legitimate certificate is then silently filtered out as "already in DB", causing the node to permanently boost the wrong block for that round and potentially prefer a non-canonical chain.

---

### Finding Description

The `processCerts` function in `PerasCert.hs` implements the inbound certificate processing pipeline:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
``` [1](#0-0) 

The uniqueness constraint is enforced at line 166: any certificate whose `PerasRoundNo` is already present in the database is silently dropped before validation. This is the direct analog of `SpaceFactory#create`'s `_require(pools[adapter][maturity] == address(0), Errors.POOL_ALREADY_EXISTS)` — the first writer wins, and all subsequent arrivals for the same key are discarded.

The `validateCert` argument is wired to `validatePerasCert mkPerasParams` in both production call sites:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

This stub unconditionally returns `Right` for every certificate, regardless of its content. No committee membership, no aggregate BLS signature, no round-number range, and no boosted-block validity are checked.

The production writer is constructed in `makePerasCertPoolWriterFromChainDB`:

```haskell
opwAddObjects = \certs ->
  processCerts
    systemTime
    (ChainDB.getPerasCertIds chainDB)
    (validatePerasCert mkPerasParams)   -- stub: always Right
    (void . ChainDB.addPerasCertAsync chainDB)
    certs
``` [3](#0-2)

**Attack sequence (direct analog to H-3):**

1. Honest node A is waiting for the legitimate Peras certificate for round R, which will boost block B (the canonical tip).
2. Adversary peer sends a crafted `PerasCert { pcCertRound = R, pcCertBoostedBlock = B' }` where `B'` is a competing or adversarial block.
3. `processCerts` reads `alreadyInDb` (round R is absent), passes the cert to `validatePerasCert` (stub returns `Right`), and calls `addCert`. Round R is now occupied by the adversary's cert boosting `B'`.
4. The legitimate cert for round R arrives from an honest peer. `processCerts` reads `alreadyInDb` again — round R is now present — and the legitimate cert is silently dropped at line 166.
5. Node A's `PerasCertDB` permanently holds the adversary's cert for round R. Chain selection applies the Peras weight boost (`perasWeight = 15` in `mkPerasParams`) to `B'` instead of `B`. [5](#0-4) 

The `addPerasCertAsync` path feeds into `chainSelSync`, which uses the cert's boosted block to influence `PerasWeightSnapshot` and therefore `preferAnchoredCandidate`:

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert _varProcessed) = ...
``` [6](#0-5) 

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.**

The Peras weight boost is a first-class input to `preferAnchoredCandidate`. By injecting a cert that boosts an adversarial block, the attacker causes the victim node to assign extra weight to a competing fork. If the adversary controls or can predict a fork that is otherwise close in length to the canonical chain, the injected boost can tip chain selection in favour of the non-canonical fork. The effect is durable: the cert is stored in the `PerasCertDB` and survives node restarts (it is replayed from disk), so the wrong boost persists until the round's cert is garbage-collected.

---

### Likelihood Explanation

**High.** The object-diffusion mini-protocol for Peras certificates is reachable by any peer that connects to the node. No stake, no keys, and no prior relationship are required. The adversary only needs to send a single well-formed CBOR-encoded `PerasCert` message for the target round before the legitimate cert propagates. Because `validatePerasCert` is a stub, the crafted cert requires no cryptographic material whatsoever. The race window is the network propagation delay between the adversary and the victim versus the propagation delay of the legitimate cert.

---

### Recommendation

1. **Implement `validatePerasCert` before enabling the Peras cert diffusion mini-protocol in production.** The stub at `SupportsPeras.hs:350–358` must verify committee membership, aggregate BLS signature, round-number bounds, and that the boosted block is on a known chain. The linked issue `cardano-peras#120` tracks this.

2. **Decouple the uniqueness check from the "first writer wins" semantics.** `processCerts` should validate the cert *before* checking `alreadyInDb`, or should compare the incoming cert against the stored one and replace it only if the incoming cert is provably superior (e.g., has a higher aggregate signature weight). This mirrors the fix direction suggested for H-3: do not let the uniqueness constraint silently discard a later, potentially more authoritative resource.

3. **Consider making `addCert` idempotent with equality checking** rather than a silent no-op on duplicate round numbers, so that a cert for a round that already has a different boosted block raises an equivocation alarm rather than being silently ignored.

### Proof of Concept

```
Adversary connects to victim node via the Peras cert object-diffusion mini-protocol.

Round R is currently in progress; the legitimate cert (boosting canonical block B)
has not yet propagated to the victim.

Adversary sends:
  PerasCert { pcCertRound = R, pcCertBoostedBlock = B' }
  where B' is the tip of an adversary-controlled fork.

processCerts (PerasCert.hs:164):
  alreadyInDb = {}  -- round R not yet present
  certsNotAlreadyInDb = [adversary cert]
  validatePerasCert mkPerasParams (adversary cert)
    => Right (ValidatedPerasCert { vpcCert = adversary cert,
                                   vpcCertBoost = 15 })
  addCert (adversary cert)  -- stored; round R now occupied

Legitimate cert (boosting B) arrives from honest peer:
  alreadyInDb = {R}  -- round R now present
  certsNotAlreadyInDb = []  -- legitimate cert silently dropped
  -- no exception, no log, no equivocation alarm

Chain selection:
  PerasWeightSnapshot now boosts B' by weight 15.
  If adversary fork length + 15 > canonical chain length,
  victim switches to adversary fork.
