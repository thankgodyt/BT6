### Title
Peras BLS Vote Signatures Lack Chain-Specific Domain Separation, Enabling Cross-Network Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

### Summary
The `hashVoteSignature` function used to sign and verify Peras BLS votes does not include any chain-specific context (network magic, genesis hash, or epoch nonce) in the signed message. A valid vote signature produced on one Cardano network or one side of a chain fork can be replayed verbatim on another network or fork side where the same block hash exists, causing a receiving node to accept a vote that was never legitimately cast for its chain.

### Finding Description
The production vote-signing hash in `Peras/Crypto/BLS.hs` is:

```haskell
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
```

The signed payload is exactly `roundNo (8 bytes) || boostedBlockSlot (8 bytes) || boostedBlockHash (32 bytes)`. There is no network magic, genesis hash, or epoch nonce included. [1](#0-0) 

This same function is used for both individual vote signing/verification and aggregate certificate signing/verification: [2](#0-1) [3](#0-2) 

Contrast this with:

1. **Byron block signatures**, which explicitly bind to `ProtocolMagicId` in the signing context: [4](#0-3) 

2. **Praos VRF inputs**, which include the epoch nonce (a chain-history-derived value) providing implicit chain binding: [5](#0-4) 

3. **Peras VRF eligibility proofs** (`hashVRFInput`), which also include the epoch nonce: [6](#0-5) 

Only the vote signature hash (`hashVoteSignature`) is missing this chain-specific binding. The `CryptoSupportsVoteSigning` interface itself provides no mechanism to pass chain context into `signVote` or `verifyVoteSignature`: [7](#0-6) 

### Impact Explanation
Peras certificates boost the weight of a block in chain selection. A replayed vote that passes verification contributes to quorum, potentially causing a certificate to be forged for a block that was never legitimately voted for on the target network. This allows an unprivileged peer to inject cross-chain votes that affect chain selection, constituting a bypass of Peras vote/certificate verification checks enabling unauthorized certificate acceptance.

The `processVotes` inbound handler accepts votes from any peer over the network miniprotocol and validates them using `validatePerasVote`, which calls the BLS verification path: [8](#0-7) 

A replayed vote passes this check because the signature is valid — it was legitimately produced, just on a different chain.

### Likelihood Explanation
The attack is realistic in two scenarios:

1. **Chain fork**: When a chain splits (e.g., during a contentious hard fork), the same block exists on both sides. A committee member who votes on one side has their signature replayed on the other side by any peer who observed the original vote.

2. **Testnet/mainnet key reuse**: If a committee member uses the same BLS key pair on a testnet and mainnet (or any two networks), votes cast on one network are valid on the other for any round/block combination that coincidentally matches.

Both scenarios require no privileged access — any peer that observed a vote on one network can replay it on another.

### Recommendation
Include a chain-specific domain separator in `hashVoteSignature`. The most appropriate value is the genesis hash or network magic, following the pattern already established by Byron (`ProtocolMagicId`) and Praos (epoch nonce). Concretely, prepend a fixed-length encoding of the genesis hash or network magic to the byte builder in `hashVoteSignature`, and thread this value through `signVote` and `verifyVoteSignature` in the `CryptoSupportsVoteSigning` interface (analogous to how `ContextDSIGN` is used in `ByronDSIGN`).

### Proof of Concept
1. Node A is on network X (e.g., a testnet fork). Committee member M signs a vote: `sig = BLS.sign(sk, hash(roundNo || slot || blockHash))`.
2. The same `(roundNo, slot, blockHash)` tuple exists on network Y (the other side of the fork, or mainnet with a shared block).
3. An attacker relays the `PerasVote` message containing `sig` to a node on network Y.
4. Network Y's node calls `verifyVoteSignature pk roundNo boostedBlock sig`, which recomputes `hashVoteSignature roundNo boostedBlock` — identical to what was signed on network X — and the BLS verification succeeds.
5. The vote is accepted, counted toward quorum, and if enough such replayed votes are collected, a `PerasCert` is forged and submitted to chain selection via `addPerasCertAsync`, boosting the weight of a block that was never legitimately voted for on network Y. [9](#0-8)

  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
