### Title
Any Caller Can Invoke `withdraw_rbf` on Another User's Pending Withdrawal Without Ownership Check - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
`withdraw_rbf` is a public, unprivileged function that accepts an arbitrary `original_btc_pending_verify_id` and an attacker-controlled `output` vector. It sets `account_id = env::predecessor_account_id()` (the caller) without verifying that the caller owns the referenced pending transaction. Any NEAR account can invoke it against any other user's in-flight withdrawal, supplying attacker-chosen outputs that are forwarded into PSBT construction and submitted to the MPC for signing.

### Finding Description

`withdraw_rbf` in `contracts/satoshi-bridge/src/api/bridge.rs` (lines 258–274) is decorated only with `#[pause(except(roles(Role::DAO)))]` — no `#[trusted_relayer]`, no `#[access_control_any]`, and no ownership assertion:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← attacker's account
    self.require_pending_sign_capacity(&account_id);  // ← checks attacker's quota

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← attacker passed as owner
        original_btc_pending_verify_id,      // ← victim's pending tx
        output,                              // ← attacker-controlled outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

The function uses `env::predecessor_account_id()` as the acting `account_id` and never checks whether that account is the owner of `original_btc_pending_verify_id`. The attacker's account is then forwarded through `withdraw_rbf_chain_specific` → `withdraw_rbf_callback` → `internal_withdraw_rbf`, where it is used to insert the new RBF pending ID into the attacker's account and to build a new PSBT from the victim's original PSBT inputs combined with the attacker-supplied `output`. [2](#0-1) 

Contrast this with `cancel_withdraw`, which is correctly restricted to DAO/Operator **and** explicitly looks up the real owner from the pending info before proceeding:

```rust
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
``` [3](#0-2) 

`withdraw_rbf` performs neither the privilege check nor the ownership lookup.

### Impact Explanation

An unprivileged attacker can:

1. **Redirect bridge-controlled BTC**: Supply a crafted `output` vector that changes the recipient address of the victim's withdrawal. The new PSBT is built from the victim's reserved UTXOs (bridge-controlled inputs) and the attacker's outputs, then submitted to the MPC for signing. If the MPC signs the attacker-constructed transaction, the victim's BTC is sent to the attacker's address instead of the victim's `target_btc_address`. This matches the allowed critical impact: *"Chain-signature, PSBT, or transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds."*

2. **Permanently lock or grief a withdrawal**: Even if output validation inside `generate_psbt_from_original_psbt_and_new_output` prevents full redirection, the attacker can repeatedly submit RBF replacements for the victim's pending transaction, consuming MPC signing slots, inflating gas fees beyond the victim's intent, or creating a state where the victim's original pending info is superseded by an attacker-owned RBF entry — leaving the victim's funds stuck in the bridge.

### Likelihood Explanation

The entry point is fully public and requires no tokens, no role, and no special setup. Any NEAR account can call `withdraw_rbf` with any `original_btc_pending_verify_id` string. Pending transaction IDs are emitted as on-chain events (`GenerateBtcPendingInfo`), so they are trivially discoverable by any observer. Likelihood is high.

### Recommendation

Add an ownership check at the top of `withdraw_rbf`, mirroring the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(...) {
    let account_id = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(account_id == owner, "Only the owner can RBF their own withdrawal");
    self.require_pending_sign_capacity(&account_id);
    self.withdraw_rbf_chain_specific(account_id, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Alice calls `nbtc.ft_transfer_call(bridge, 500_000, Withdraw{...})`, creating a pending withdrawal with ID `btc_pending_id_alice` (emitted in `GenerateBtcPendingInfo` event, publicly visible).
2. Attacker Eve observes `btc_pending_id_alice` on-chain.
3. Eve calls `bridge.withdraw_rbf(btc_pending_id_alice, [TxOut { value: 490_000, script_pubkey: eve_address }], None)`.
4. `withdraw_rbf` sets `account_id = eve`, passes `eve` as the acting owner and `btc_pending_id_alice` as the original tx to `withdraw_rbf_chain_specific`.
5. The callback builds a new PSBT from Alice's reserved UTXOs (bridge inputs) and Eve's output, then calls `internal_withdraw_rbf` with `account_id = eve`.
6. The MPC is asked to sign a transaction spending Alice's deposit UTXO to Eve's address.
7. If signed and broadcast, Alice's BTC is delivered to Eve. [1](#0-0) [3](#0-2) [4](#0-3)

macro_rules! define_rbf_callback {
    ($method:ident, $callback_name:ident, $internal_fn:ident) => {
        impl Contract {
            pub(crate) fn $method(
                &mut self,
                user_account_id: AccountId,
                original_btc_pending_verify_id: String,
                output: Vec<TxOut>,
                chain_specific_data: Option<ChainSpecificData>,
            ) {
                let predecessor_account_id = env::predecessor_account_id();
                let _ = self.get_last_block_height_promise().then(
                    Self::ext(env::current_account_id())
                        .with_static_gas(GAS_RBF_CALL_BACK)
                        .$callback_name(
                            user_account_id,
                            original_btc_pending_verify_id,
                            output,
                            chain_specific_data,
                            predecessor_account_id,
                        ),
                );
            }
        }

        #[near]
        impl Contract {
            #[private]
            pub fn $callback_name(
                &mut self,
                account_id: AccountId,
                original_btc_pending_verify_id: String,
                output: Vec<TxOut>,
                chain_specific_data: Option<ChainSpecificData>,
                presecessor_account_id: AccountId,
                #[callback_unwrap] last_block_height: u32,
            ) {
                let expiry_height = self.get_expiry_height(&chain_specific_data, last_block_height);
                let orchard_bundle_bytes = chain_specific_data.map(|c| c.orchard_bundle_bytes);

                let original_tx_btc_pending_info =
                    self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);

                let new_psbt = self.generate_psbt_from_original_psbt_and_new_output(
                    original_tx_btc_pending_info,
                    output,
                    orchard_bundle_bytes.map(|b| b.0),
                    expiry_height,
                    last_block_height,
                );

                let btc_pending_id = self.$internal_fn(
                    &account_id,
                    original_btc_pending_verify_id,
                    new_psbt,
                    presecessor_account_id,
                );

                self.internal_unwrap_mut_account(&account_id)
                    .btc_pending_sign_ids
                    .insert(btc_pending_id.clone());

                Event::GenerateBtcPendingInfo {
                    account_id: &account_id,
                    btc_pending_id: &btc_pending_id,
                }
                .emit();
            }
        }
    };
