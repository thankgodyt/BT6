### Title
`validatePerasCert` Stub Always Accepts Any Certificate, Enabling Unauthorized Chain-Selection Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` — accepting every certificate without any cryptographic or structural verification. Because the Peras certificate diffusion mini-protocol is wired into the production node-to-node handler and feeds directly into `processCerts`, any unprivileged peer can inject arbitrary `PerasCert` objects that will be stored in the `PerasCertDB` and applied as weight boosts during chain selection. This is the direct analog of the "Anybody can mint DebtToken" pattern: a function that is supposed to gate privileged state mutation behind an authorization check instead performs no check at all.

### Finding Description

**Root cause — stub validation that always succeeds:** [1](#0-0) 

The only `BlockSupportsPeras` instance in the codebase is the universal one:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

`validatePerasCert` wraps every incoming `PerasCert` in `Right ValidatedPerasCert` regardless of its content. No signature, no committee membership, no round-number bounds, no boosted-block existence check — nothing.

**Inbound path — reachable from any peer:**

`processCerts` in the object-pool layer calls the supplied `validateCert` function on every certificate received from a peer: [2](#0-1) 

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
```

Because `validateCert` is `validatePerasCert mkPerasParams` and that always returns `Right`, the `(errs, _)` branch is unreachable; every certificate passes.

The production node-to-node handler wires this directly to the live `ChainDB`: [3](#0-2) 

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
```

**Effect on chain selection:**

The `ChainDB` API documents the consequence of accepting a certificate: [4](#0-3) 

```haskell
, addPerasCertAsync :: WithArrivalTime (ValidatedPerasCert blk) -> m (AddPerasCertPromise m)
-- ^ Asynchronously insert a certificate to the DB. If this leads to a fork to
-- be weightier than our current selection, this will trigger a fork switch.
```

A `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` that is added to the weight of the boosted block's chain fragment during chain selection. An attacker who can inject a certificate pointing at any `Point blk` they choose can therefore make an arbitrary chain fragment appear heavier than the honest chain.

**Contrast with the vote path (not exploitable in the same way):**

The vote diffusion handler passes an empty stake distribution: [5](#0-4) 

```haskell
( makePerasVotePoolWriterFromChainDB
    systemTime
    -- Note that the empty stake distribution will cause all votes to
    -- be considered invalid.
    (pure (PerasVoteStakeDistr mempty))
    getChainDB
)
```

`validatePerasVote` at least checks stake-distribution membership, so with an empty distribution all votes are rejected. No such guard exists for certificates — `validatePerasCert` ignores its arguments entirely.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point and any round number, send it over the `PerasCertDiffusion` mini-protocol, and have it stored as a `ValidatedPerasCert` with a full Peras weight boost. Because the `ChainDB` triggers chain selection on every accepted certificate, the attacker can repeatedly inject certificates that boost blocks on a minority fork, causing an honest node to switch away from the canonical chain. This is a **High** chain-selection integrity failure: an unprivileged peer can make an honest node prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

### Likelihood Explanation

The `PerasCertDiffusion` client is unconditionally instantiated for every peer connection in the production node-to-node handler. No special role, stake, or key material is required. Any peer that can open a connection can send crafted certificates. The only friction is that Peras must be active on the network; the code is already deployed and the protocol handlers are live.

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before the Peras certificate diffusion protocol is enabled on any network. At minimum, validation must:

1. Verify the aggregate BLS signature over the certificate against the committee's aggregate verification key.
2. Confirm the claimed voters are eligible committee members for the stated round.
3. Confirm the total stake of the signers meets the quorum threshold.
4. Confirm the boosted block point exists in the node's known chain history (or at least is structurally plausible).

Until real validation is in place, the `hPerasCertDiffusionClient` handler should be disabled or should unconditionally reject all inbound certificates rather than delegating to a no-op validator. [6](#0-5) 

### Proof of Concept

1. Connect to a node as a peer via the node-to-node protocol.
2. Negotiate the `PerasCertDiffusion` sub-protocol.
3. Send a batch containing one `PerasCert` with:
   - `pcCertRound` = any round number not yet in the `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of a block on a minority fork
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert cert (perasWeight mkPerasParams))` unconditionally.
5. The certificate is passed to `addPerasCertAsync` in the `ChainDB`.
6. Chain selection fires; the minority fork now carries a Peras weight boost equal to `perasWeight mkPerasParams`.
7. If the boosted fork's total weight exceeds the current selection's weight, the node switches forks.
8. Repeat with fresh round numbers to continuously re-boost the attacker's preferred fork. [6](#0-5) [7](#0-6) [3](#0-2) [4](#0-3)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool

      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
