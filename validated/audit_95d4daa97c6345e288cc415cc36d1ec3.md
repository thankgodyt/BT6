### Title
`revalidateHeader` silently drops all envelope validation in production builds — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` is designed to skip only expensive cryptographic checks (KES/VRF via `reupdateChainDepState`) while retaining envelope checks (block number, slot, hash chain) as assertions. However, the envelope check is wrapped in `assertWithMsg`, which is a compile-time no-op in production builds (without `ENABLE_ASSERTIONS`). In production, `revalidateHeader` therefore performs **zero validation** — neither cryptographic nor structural. A crafted ImmutableDB or snapshot containing blocks with invalid envelope properties (wrong `prevHash`, wrong `BlockNo`, wrong `SlotNo`) will be silently accepted during LedgerDB initialization replay, causing the node to durably build on an inconsistent ledger state.

---

### Finding Description

**Root cause — the guard is a compile-time no-op in production:**

`assertWithMsg` in `Assert.hs` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [1](#0-0) 

Without `ENABLE_ASSERTIONS` (the production default), this compiles to `assertWithMsg _ a = a` — the check argument is evaluated but its result is unconditionally discarded.

**The vulnerable function:**

`revalidateHeader` wraps the entire `validateEnvelope` call inside `assertWithMsg`:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' = reupdateChainDepState ...
  envelopeCheck  = runExcept $ withExcept show $
                     validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [2](#0-1) 

In production, this reduces to:

```haskell
revalidateHeader cfg _ hdr st =
  HeaderState (NotOrigin (getAnnTip hdr))
              (reupdateChainDepState ...)
```

No envelope check. No crypto check. Pure state update.

**Contrast with `validateHeader`**, which enforces both checks as hard errors:

```haskell
validateHeader cfg ledgerView hdr st = do
  withExcept HeaderEnvelopeError $
    validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
  chainDepState' <- withExcept HeaderProtocolError $
    updateChainDepState ...
  return $ HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
``` [3](#0-2) 

**What `validateEnvelope` enforces** (all silently skipped in production via `revalidateHeader`):

- `BlockNo` consecutiveness
- `SlotNo` strict monotonicity
- `prevHash` chain linkage
- Checkpoint hash enforcement (`validateIfCheckpoint`)
- Protocol-specific additional envelope checks (`additionalEnvelopeChecks`) [4](#0-3) 

**Call path — LedgerDB initialization replay:**

`revalidateHeader` is called from `Extended.hs` (2 call sites) via `reapplyExtLedgerState`. This function is invoked during LedgerDB initialization when replaying blocks from the ImmutableDB or a snapshot. The design comment in `Abstract.hs` confirms the intent:

> "since we already know that the block is valid in the provided ledger state, the ledger layer should not perform any validation checks. Thus this function will call the ledger rules with `ValidateNone` policy." [5](#0-4) 

The assumption is that ImmutableDB/snapshot blocks are always previously validated. But `revalidateHeader` was supposed to at least assert envelope consistency — and in production it does not.

**The analog to the external report:**

| External Report | This Finding |
|---|---|
| `accessRegistry != address(0)` guards both allowlist AND denylist | `assertWithMsg` guards the envelope check |
| Setting registry to `address(0)` disables BOTH checks | `ENABLE_ASSERTIONS` absent disables the envelope check entirely |
| Intended: bypass allowlist only | Intended: skip expensive crypto only |
| Unintended: denylist also disabled | Unintended: envelope checks also disabled |

---

### Impact Explanation

**High.** A crafted ImmutableDB or snapshot file containing a block with an invalid `prevHash` (pointing to a different chain), an incorrect `BlockNo`, or an out-of-order `SlotNo` will be silently accepted during LedgerDB initialization. The node will durably build its in-memory and on-disk ledger state on top of an inconsistent chain, diverging from the honest network. This matches: *"ChainDB, ImmutableDB, VolatileDB, LedgerDB, snapshot, or LSM corruption/replay/rollback bug that causes durable use of the wrong ledger state."*

The checkpoint enforcement path (`validateIfCheckpoint`) is also silently bypassed, meaning a crafted replay can skip past a hardcoded checkpoint hash without detection.

---

### Likelihood Explanation

**Medium.** The attack requires writing a crafted ImmutableDB chunk file or ledger snapshot to the node's data directory — a "DB/snapshot input in a local reproduction" entry path explicitly listed as in-scope. No cryptographic key material is needed. The node operator need not be malicious; a compromised deployment pipeline, a malicious container image, or a supply-chain attack on the node's storage volume suffices. The vulnerability is silent in production (no log, no error, no crash), making it difficult to detect after the fact.

---

### Recommendation

Replace `assertWithMsg` in `revalidateHeader` with an unconditional check that throws a hard error in all build configurations:

```haskell
revalidateHeader cfg ledgerView hdr st =
  case runExcept (validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr) of
    Left err -> error $ "revalidateHeader: envelope invariant violated: " <> show err
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  chainDepState' = reupdateChainDepState ...
```

The envelope check is cheap (no cryptography, no I/O) and its cost is negligible compared to the LedgerDB replay workload. Only `reupdateChainDepState` (the expensive KES/VRF path) should be skipped during replay.

---

### Proof of Concept

1. Build a production node binary (without `-DENABLE_ASSERTIONS`).
2. Craft an ImmutableDB chunk file where one block's `prevHash` field points to a hash that does not match the preceding block's hash.
3. Place the crafted chunk in the node's ImmutableDB directory.
4. Start the node. Observe that it initializes without error and builds its ledger state on the inconsistent chain.
5. Repeat with `ENABLE_ASSERTIONS` enabled: the node will crash with `"revalidateHeader: ..."` at the same block, confirming the check exists but is disabled in production.

The divergence is durable: the node will write ledger snapshots based on the corrupted state and will not self-heal on restart.
