### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` for every inbound `PerasCert`, performing zero cryptographic or structural checks. This stub is wired directly into the production `PerasCertDiffusion` inbound miniprotocol handler. When Peras is enabled, any unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing the receiving node to prefer a non-canonical chain in chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class defines `validatePerasCert` as the gate that must authenticate a Peras certificate before it may influence chain selection. The universal instance — explicitly labelled a degenerate placeholder — implements this gate as an unconditional pass-through:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature is verified, no committee membership is checked, no round number is validated against the current chain state, and no boosted-block existence check is performed. The cert is simply wrapped and returned as `ValidatedPerasCert` with the full configured weight boost.

This stub is used verbatim in the **production** inbound pool writer for the `PerasCertDiffusion` miniprotocol:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

This writer is registered as the production handler in `mkHandlers`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)

`processCerts` calls `validateCert` on each inbound cert and, if all pass (which they always do with the stub), adds them to the ChainDB: [4](#0-3) 

Once added, `chainSelSync` processes the certificate: it looks up the boosted block in the VolatileDB and triggers chain selection for it, giving the block the full Peras weight boost: [5](#0-4) 

Chain selection then compares candidates using `wsvTotalWeight`, which sums block number and weight boost: [6](#0-5)

### Impact Explanation

When Peras is enabled, an unprivileged peer can send a `PerasCert` with `pcCertBoostedBlock` pointing to any block in the node's VolatileDB — including a block on a non-canonical fork. Because `validatePerasCert` never rejects any certificate, the cert is accepted as `ValidatedPerasCert` with the full configured `perasWeight`. Chain selection then re-evaluates the boosted block's chain, and if the weight boost is large enough, the node switches to the adversarial fork. This is a **bypass of Peras certificate verification** enabling unauthorized certificate acceptance and chain selection manipulation — matching the "Critical: bypass of certificate/vote verification checks" impact class.

The analogous pattern to the TOFT report is exact: in TOFT, `removeParams.marketHelper` is an attacker-controlled address passed through without validation, and the contract's own identity executes the call. Here, the attacker-controlled `PerasCert` (with arbitrary `pcCertBoostedBlock`) is passed through `validatePerasCert` without any check, and the node's own ChainDB executes chain selection using the fraudulent weight.

---

### Likelihood Explanation

The `PerasCertDiffusion` miniprotocol handler is registered unconditionally in `mkHandlers` for all NTN connections. The vulnerability is exploitable whenever Peras is enabled with a non-zero `perasWeight`. The CHANGELOG notes Peras is disabled by default, but the production code path is fully wired and the stub is explicitly marked as a temporary placeholder pending real validation. Any private testnet or experimental deployment with Peras enabled is immediately vulnerable to any connected peer.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before enabling Peras in any network. At minimum, validation must:

1. Verify the certificate's cryptographic signature against the known committee public keys for the relevant round.
2. Check that the `pcCertRound` is within the valid range relative to the current chain tip.
3. Verify that the `pcCertBoostedBlock` corresponds to a block that was actually a valid candidate in that round.
4. Reject certificates whose round number already has a different certificate in the DB (equivocation check).

Until real validation is implemented, the `PerasCertDiffusion` inbound miniprotocol should not be negotiated on any network where `perasWeight > 0`.

### Proof of Concept

An attacker operating a peer node:

1. Connects to a victim node via the `PerasCertDiffusion` NTN miniprotocol.
2. Sends a single `PerasCert`:
   ```
   PerasCert
     { pcCertRound    = <any round number>
     , pcCertBoostedBlock = <Point of adversarial fork block in victim's VolatileDB>
     }
   ```
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The cert is added to the `PerasCertDB` via `ChainDB.addPerasCertAsync`.
5. `chainSelSync` retrieves the boosted block from the VolatileDB and calls `chainSelectionForBlock`.
6. Chain selection now computes `wsvTotalWeight` for the adversarial fork as `blockNo + perasWeight`, which may exceed the honest chain's total weight.
7. The node switches to the adversarial fork. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

-- Process a Peras certificate by adding it to the PerasCertDB and potentially
-- performing chain selection if a candidate is now better than our selection.
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
