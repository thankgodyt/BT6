### Title
Missing Minimum-Amount Validation at `init_transfer` Causes Permanent Freezing of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

### Summary
The NEAR bridge contract accepts and locks user tokens during `init_transfer` without verifying that the net transfer amount (after fee) will survive decimal normalization to a non-zero value. When `sign_transfer` is later called, `normalize_amount` applies floor division and the result is zero, causing an unconditional panic. Because no cancel/refund path exists for pending transfers, the user's tokens are permanently frozen in the bridge.

### Finding Description
`init_transfer` validates only that `fee.fee < amount`: [1](#0-0) 

It then locks the full token amount and stores the transfer message: [2](#0-1) 

Later, when a trusted relayer calls `sign_transfer`, the net amount is normalized for the destination chain: [3](#0-2) 

`normalize_amount` uses integer floor division: [4](#0-3) 

For a token where `origin_decimals > decimals` (e.g., NEAR-native token: 24 on NEAR, 18 on EVM, giving a divisor of `10^6`), any `amount_without_fee()` value less than `10^6` normalizes to zero. The `require!(amount_to_transfer > 0, ...)` guard then panics unconditionally on every `sign_transfer` call for that transfer ID. The transfer message is never removed and the locked tokens are never released.

The `Decimals` struct that drives this: [5](#0-4) 

### Impact Explanation
Tokens are locked at `init_transfer_internal` time and remain locked permanently. There is no cancel or refund entry point for a pending transfer. Every subsequent `sign_transfer` call for the affected transfer ID panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, making the lock irrecoverable. This constitutes **permanent freezing of bridged funds**.

**Impact: Critical** — permanent loss of user funds.

### Likelihood Explanation
Any token registered with `origin_decimals > decimals` (the common case for NEAR-native tokens bridged to EVM chains, e.g., 24 → 18) is affected. A user who sends an amount smaller than `10^(origin_decimals - decimals)` — for example, 1 yoctoNEAR-equivalent unit of a wrapped token — triggers the freeze. This is reachable by any unprivileged user calling `ft_transfer_call` with a small amount. No special permissions are required.

**Likelihood: Medium** — requires a small transfer amount on a token with a decimal gap, which is a realistic user mistake or a deliberate griefing action.

### Recommendation
Add a normalization check inside `init_transfer` before locking tokens:

```rust
let amount_after_normalization = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_after_normalization > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` but applies it at deposit time, before tokens are locked, so the user receives a clear rejection rather than a permanent freeze.

### Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (6-decimal gap, divisor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 1` and `fee = 0`, targeting an EVM recipient.
3. `init_transfer` passes the `fee < amount` check (`0 < 1`), locks 1 token unit, and stores the `TransferMessage`.
4. Trusted relayer calls `sign_transfer` for the stored transfer ID.
5. `normalize_amount(1 - 0, Decimals { decimals: 18, origin_decimals: 24 }) = 1 / 1_000_000 = 0`.
6. `require!(0 > 0, ...)` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
7. The transfer message remains in `pending_transfers`; the 1-unit token balance remains locked with no recovery path. [3](#0-2) [4](#0-3) [1](#0-0) [2](#0-1)
