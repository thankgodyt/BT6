### Title
`BlockSupportsPeras` Degenerate Instance Unconditionally Accepts All Peras Certificates and Votes Without Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` provides stub implementations of `validatePerasCert` and `validatePerasVote` that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate it receives. `validatePerasVote` only checks stake-distribution membership but never verifies the vote's cryptographic signature. Both stubs are wired directly into the production inbound-object processing paths (`processCerts`, `processVotes`), meaning any unprivileged peer can inject arbitrary Peras certificates and votes that will be accepted and stored without any proof of authenticity.

### Impact Explanation

**Critical — Bypass of Peras certificate and vote verification enabling unauthorized certificate acceptance and chain-selection manipulation.**

A `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` that is applied during chain selection to boost the weight of the certified block. Because `validatePerasCert` always returns `Right`, an unprivileged peer can craft a `PerasCert` naming any block point and any round number, have it accepted into the node's CertDB, and thereby cause the node to apply an artificial weight boost to an arbitrary block during chain selection. This lets an attacker make an honest node prefer a non-canonical chain without holding any stake, keys, or committee membership — a direct bypass of the Peras certificate-verification gate that the `BlockSupportsPeras` class is designed to enforce.

For votes, any peer who knows a stake-pool key hash (public information) can forge votes attributed to that pool without possessing its private key, because `validatePerasVote` never checks the vote signature. Forged votes accumulate toward quorum, potentially triggering spurious certificate forging inside `implAddVote`.

### Likelihood Explanation

The entry path is the Peras object-diffusion mini-protocol, reachable by any peer that connects to the node. No privilege, stake, or key material is required. The only precondition is that Peras is active on the network. The stubs are in the production source tree (not in `unstable-*` test libraries) and are wired into the live `NodeToNode` diffusion setup.

### Recommendation

Replace the degenerate `instance StandardHash blk => BlockSupportsPeras blk` with a proper era-specific instance (or a `NoPerasSupport` newtype that rejects all certificates and votes) before Peras is activated on any network. At minimum, `validatePerasCert` must verify the aggregate committee signature over `(electionId, candidate)` and check that the round number and boosted-block point are within protocol-defined bounds. `validatePerasVote` must verify the per-voter cryptographic signature (and, for non-persistent voters, the VRF eligibility proof) before accepting a vote.

### Proof of Concept

A peer connects via the Peras certificate object-diffusion mini-protocol and sends a batch containing a single `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block on the victim's chain. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally. The certificate is timestamped and added to the ChainDB via `addPerasCertAsync`. On the next chain-selection pass, the node applies the Peras weight boost to the attacker-chosen block, potentially switching to a fork the attacker controls. [8](#0-7)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
