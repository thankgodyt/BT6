### Title
MPC Signing Failure Can Permanently Lock User nBTC in `PendingSign` State — (File: `contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

When a user initiates a withdrawal, their nBTC is transferred to the bridge contract and a `BTCPendingInfo` record is created in `PendingSign` state. If the NEAR Chain Signatures MPC service fails permanently, there is no escape mechanism to cancel the withdrawal and return the nBTC to the user. The bridge has no analog to an `exitAwardPhase()` for the `PendingSign` stage.

---

### Finding Description

**Withdrawal initiation** — `ft_on_transfer` in `token_receiver.rs` receives the user's nBTC (returning `U128(0)` so the tokens stay with the bridge) and calls `create_btc_pending_info`, which stores a `BTCPendingInfo` with `state: PendingInfoState::WithdrawOriginal(OriginalState { stage: PendingInfoStage::PendingSign, … })` and moves the selected UTXOs to `unavailable_utxos`. [1](#0-0) 

**MPC signing request** — `sign_btc_transaction` calls `internal_sign_btc_transaction`, which dispatches a cross-contract call to `ext_chain_signatures::sign()` and chains `sign_btc_transaction_callback`. [2](#0-1) 

**Silent failure on MPC error** — In `sign_btc_transaction_callback`, if `env::promise_result_checked` returns `Err`, the callback simply returns `false`. No state is changed: the `BTCPendingInfo` remains in `PendingSign`, the nBTC remains locked in the bridge, and the account's `btc_pending_sign_ids` slot is still occupied. [3](#0-2) 

**No escape for `PendingSign` state** — `cancel_withdraw` (the only cancellation path) operates on a `btc_pending_verify_id` and internally asserts `PendingVerify` stage via `assert_withdraw_related_pending_verify_tx`. A `PendingSign` record will always fail this assertion. [4](#0-3) [5](#0-4) 

**Pending-sign slot exhaustion** — Each account has a `max_pending_sign_txs` limit (default: 1). A stuck `PendingSign` record fills the slot, blocking any new withdrawal attempt. [6](#0-5) [7](#0-6) 

There is no privileged admin function (DAO/Operator) that can force-remove a `PendingSign` `BTCPendingInfo` and return the nBTC to the user. The nBTC burn only occurs after `verify_withdraw` succeeds (i.e., after `PendingVerify` → on-chain confirmation), so the tokens remain held by the bridge indefinitely. [8](#0-7) 

---

### Impact Explanation

If the NEAR Chain Signatures MPC service fails permanently (or is decommissioned/upgraded in a breaking way), every user whose withdrawal is in `PendingSign` state has their nBTC permanently locked inside the bridge contract with no recovery path. This matches: **Critical — Significant permanent locking of user funds.**

---

### Likelihood Explanation

The NEAR Chain Signatures service is a core protocol dependency, not a third-party contract. A permanent failure is unlikely under normal conditions, but a breaking upgrade, key-rotation failure, or contract migration could leave in-flight `PendingSign` records unresolvable. The risk is low-to-medium in probability but critical in impact, and the absence of any escape hatch means even a temporary extended outage forces users to wait indefinitely with no recourse.

---

### Recommendation

Add a `cancel_pending_sign_withdrawal(btc_pending_sign_id: String)` function (callable by the owning user, or by DAO/Operator after a timeout) that:
1. Asserts the `BTCPendingInfo` is in `PendingSign` state.
2. Removes the `BTCPendingInfo` and clears the account's `btc_pending_sign_ids` slot.
3. Returns the UTXOs from `unavailable_utxos` back to `utxos`.
4. Transfers the locked nBTC back to the user (or routes to `lost_found` on transfer failure).

This is the direct analog of the recommended `exitAwardPhase()` in the reference report.

---

### Proof of Concept

1. User calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message → bridge receives nBTC, `BTCPendingInfo` created in `PendingSign`.
2. Anyone calls `sign_btc_transaction(btc_pending_sign_id, 0, 0)` → MPC cross-contract call dispatched.
3. MPC service is permanently unavailable → `sign_btc_transaction_callback` receives `Err`, returns `false`, no state change.
4. User retries `sign_btc_transaction` indefinitely — always fails.
5. User attempts `cancel_withdraw(btc_pending_sign_id, …)` → panics with `"Not pending verify stage"` because the record is still in `PendingSign`.
6. User attempts a new withdrawal → panics with `"Too many pending sign transactions"` (slot full).
7. nBTC is permanently locked in the bridge with no recovery path for the user or any privileged role. [9](#0-8) [5](#0-4) [10](#0-9)

    pub fn internal_sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> Promise {
        let pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);

        let public_keys: Vec<_> = pending_info
            .vutxos
            .iter()
            .map(|vutxo| self.generate_btc_public_key(&vutxo.get_path()))
            .collect();

        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        require!(
            btc_pending_info.signatures[sign_index].is_none(),
            "Already signed"
        );
        let payload = btc_pending_info
            .get_psbt()
            .get_hash_to_sign(sign_index, &public_keys);
        let path = btc_pending_info.vutxos[sign_index].get_path();
        self.sign_promise(SignRequest {
            payload,
            path,
            key_version,
        })
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_SIGN_BTC_TRANSACTION_CALL_BACK)
                .sign_btc_transaction_callback(
                    btc_pending_info.account_id.clone(),
                    btc_pending_sign_id,
                    sign_index,
                ),
        )
    }

    #[private]
    pub fn sign_btc_transaction_callback(
        &mut self,
        account_id: AccountId,
        btc_pending_sign_id: String,
        sign_index: usize,
    ) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_SIGNATURE_RESULT) {
            let signature = serde_json::from_slice::<SignatureResponse>(&result_bytes)
                .expect("Invalid signature");

            let public_key = self
                .generate_btc_public_key(
                    &self
                        .internal_unwrap_btc_pending_info(&btc_pending_sign_id)
                        .vutxos[sign_index]
                        .get_path(),
                )
                .inner;
            let btc_pending_info = self.internal_unwrap_mut_btc_pending_info(&btc_pending_sign_id);
            require!(
                btc_pending_info.signatures[sign_index].is_none(),
                "Already signed"
            );
            btc_pending_info.signatures[sign_index] = Some(signature.clone());
            btc_pending_info.last_sign_time_sec = nano_to_sec(env::block_timestamp());
            Event::BtcInputSignature {
                account_id: &account_id,
                btc_pending_id: &btc_pending_sign_id,
                sign_index,
                signature: &signature,
            }
            .emit();
            let mut psbt = btc_pending_info.get_psbt();
            psbt.save_signature(sign_index, signature, public_key);

            btc_pending_info.psbt_hex = psbt.serialize();
            if btc_pending_info.is_all_signed() {
                let tx_bytes_with_sign = psbt.extract_tx_bytes_with_sign();

                // For ZCash chains, use base64 encoding to save space (1.33x vs 2x overhead for hex)
                // ZCash transactions with Orchard bundles are larger and benefit from compact encoding
                // For Bitcoin chains, keep hex encoding for backward compatibility

                #[cfg(feature = "zcash")]
                let tx_bytes_base64 = {
                    use near_sdk::base64::{engine::general_purpose::STANDARD, Engine};
                    STANDARD.encode(&tx_bytes_with_sign)
                };

                Event::SignedBtcTransaction {
                    account_id: &account_id,
                    tx_id: btc_pending_sign_id.clone(),
                    #[cfg(not(feature = "zcash"))]
                    tx_bytes: &tx_bytes_with_sign,
                    #[cfg(feature = "zcash")]
                    tx_bytes_base64,
                }
                .emit();

                btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
                btc_pending_info.to_pending_verify_stage();

                let is_original_tx = btc_pending_info.get_original_tx_id().is_none();
                let account = self.internal_unwrap_mut_account(&account_id);
                require!(
                    account.btc_pending_sign_ids.remove(&btc_pending_sign_id),
                    "Internal error"
                );
                if is_original_tx {
                    account
                        .btc_pending_verify_list
                        .insert(btc_pending_sign_id.clone());
                }
            }
            true
        } else {
            false
        }
    }

    pub fn assert_withdraw_related_pending_verify_tx(&self) {
        match self.state.borrow() {
            PendingInfoState::WithdrawOriginal(state) => state.assert_pending_verify(),
            PendingInfoState::WithdrawUserRbf(state) => state.assert_pending_verify(),
            PendingInfoState::WithdrawCancelRbf(state) => state.assert_pending_verify(),
            _ => env::panic_str("Not withdraw related tx"),
        }
    }
