### Title
Degenerate `validatePerasCert` Allows Unprivileged Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The global degenerate `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for any input certificate. The `PerasCertDiffusion` mini-protocol is wired up in production node-to-node handlers with no version or feature-flag gate, and the inbound handler calls this degenerate validator. Any peer can therefore inject an arbitrary `PerasCert` with an attacker-chosen `pcCertBoostedBlock` point. The cert is stored in the `PerasCertDB`, which causes `getPerasWeightSnapshot` to return a non-empty snapshot. `preferAnchoredCandidate` then switches from the normal (length-based) chain-selection path to the Peras-weighted path, applying a `PerasWeight 15` boost to the adversary's chosen block. This lets an unprivileged peer cause an honest node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — degenerate validator, lines 353–358 of `SupportsPeras.hs`:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- always PerasWeight 15
      }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the codebase (it is a catch-all `instance StandardHash blk => BlockSupportsPeras blk`). No era-specific override exists yet. [2](#0-1) 

**Inbound handler wires the degenerate validator directly into the production path:**

`hPerasCertDiffusionClient` in `mkHandlers` calls `makePerasCertPoolWriterFromChainDB`, which passes `validatePerasCert mkPerasParams` as the cert validator to `processCerts`. [3](#0-2) [4](#0-3) 

**`processCerts` adds every cert that passes validation:**

Since `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every received cert is timestamped and forwarded to `addPerasCertAsync`. [5](#0-4) 

**`chainSelSync` processes the cert and triggers chain selection:**

The only guard in `chainSelSync` for a cert is whether the boosted block is older than the immutable tip. If the adversary targets a recent volatile block, the cert is added to `PerasCertDB` and chain selection is re-run. [6](#0-5) 

**`implGetWeightSnapshot` builds the weight snapshot from stored certs:**

Every cert in `pcdsCertsByTicket` contributes its `pcCertBoostedBlock` point and `vpcCertBoost` weight to the snapshot. [7](#0-6) 

**`preferAnchoredCandidate` switches to the weighted path when the snapshot is non-empty:**

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights = ...  -- normal length-based selection
  | otherwise = ...                           -- Peras-weighted selection
``` [8](#0-7) 

The weighted path computes `wsvTotalWeight = blockNo + weightBoost`. A chain whose tip has `blockNo = N` and a boost of 15 beats a chain with `blockNo = N+14` and no boost. [9](#0-8) 

**The `PerasCertDiffusion` protocol is unconditionally enabled:**

The comment in `NodeToNode.hs` explicitly states: *"network currently doesn't enable protocols conditional on the protocol version, but it eventually may; this is why `_version` is currently unused."* The protocol is registered in both `initiator` and `initiatorAndResponder` with no feature-flag guard at the consensus layer. [10](#0-9) 

**There is no era-level guard.** Even though all current Shelley-family eras set `eraPerasRoundLength = NoPerasEnabled`, this flag is never consulted in the cert inbound path or in `preferAnchoredCandidate`. The weight snapshot check is purely `isEmptyPerasWeightSnapshot`, which becomes `False` the moment any cert is stored. [11](#0-10) 

---

### Impact Explanation

An unprivileged peer can cause an honest node to prefer a non-canonical chain. With `PerasWeight 15`, a chain boosted by a single injected cert beats any competing chain that is up to 14 blocks longer. The adversary can:

1. Inject a cert boosting a block on a shorter adversarial fork.
2. The honest node's `preferAnchoredCandidate` now returns `ShouldSwitch` for the adversarial fork.
3. The honest node downloads and validates the adversarial fork's blocks, potentially switching away from the canonical chain.

This matches the **High** impact scope: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

- The `PerasCertDiffusion` protocol is wired up and unconditionally enabled at the consensus layer.
- The degenerate instance is the only instance; no production block type overrides it.
- The attack requires only a valid TCP connection and knowledge of the CBOR wire format for `PerasCert` (two fields: `PerasRoundNo` and `Point blk`), both of which are publicly documented.
- No stake, keys, or privileged access are required.
- The only constraint is that the boosted block must be in the volatile DB (not yet immutable), which is trivially satisfiable for any recent block.

---

### Recommendation

1. **Immediate:** Gate the `PerasCertDiffusion` inbound handler behind a runtime check that Peras is actually enabled for the current era (consult `eraPerasRoundLength` from the hard-fork summary). If Peras is disabled, reject all inbound certs before they reach `processCerts`.

2. **Short-term:** Replace the degenerate `validatePerasCert` with a real implementation that verifies committee membership, VRF/KES signatures, round number bounds, and the boosted block's existence and age. Track this under the existing issue [tweag/cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120).

3. **Defense-in-depth:** Add a guard in `chainSelSync` (the `ChainSelAddPerasCert` branch) that checks `eraPerasRoundLength` before adding the cert to `PerasCertDB` and triggering chain selection.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"

            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
