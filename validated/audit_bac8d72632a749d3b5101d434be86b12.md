### Title
Unauthorized Refund Request Allows Any Caller to Redirect Victim's BTC to Attacker-Controlled Address — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` contains no ownership check binding the caller to the `deposit_msg.recipient_id`. When a deposit's `DepositMsg` was created without a pre-authorized `refund_address`, any unprivileged NEAR account can submit a refund request for that deposit and supply an arbitrary attacker-controlled BTC address. After the `unsafe_refund_timelock_sec` elapses, the attacker (or anyone) can call the permissionless `execute_refund` to redirect the victim's BTC to the attacker's address.

---

### Finding Description

`request_refund` is a public, unpermissioned function. Its only caller-identity check is a narrow one: if `gas_fee` is `Some`, the caller must be DAO or Operator. No check is ever made that `env::predecessor_account_id()` equals `deposit_msg.recipient_id`. [1](#0-0) 

Inside `internal_request_refund`, the only constraint on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case — it is an optional field), this branch is skipped entirely and the caller's arbitrary `refund_address` is accepted verbatim and stored in the `RefundRequest`. [3](#0-2) 

The `execute_refund` entry point is also public and unpermissioned (no role guard), so after the timelock elapses, anyone — including the attacker — can trigger the BTC payout to the stored attacker address. [4](#0-3) 

The design acknowledges this risk by applying a longer `unsafe_refund_timelock_sec` when `deposit_msg.refund_address` is `None`, giving DAO/Operator time to call `reject_refund`. However, this is a reactive safety net, not an authorization control. The root cause — the absence of any ownership binding between the caller and the deposit — is never addressed. [5](#0-4) 

---

### Impact Explanation

An attacker who successfully times the attack (or whose request is missed by the DAO) causes the victim's BTC deposit to be refunded to the attacker's BTC address instead of the victim's. The victim loses their BTC permanently. This is direct theft of user funds from the bridge's UTXO pool.

**Impact class:** Critical — significant theft of user funds.

---

### Likelihood Explanation

- The `deposit_msg` is public information (it is submitted on-chain by the relayer during `verify_deposit_v2` and emitted in `LogDepositAddress` events).
- Any deposit that was never finalized (e.g., the relayer missed it, or the user sent BTC to a stale address) is a target.
- The attacker only needs to pay the anti-spam storage deposit (`required_balance_for_request_refund`), which is a small NEAR amount.
- The DAO must actively monitor all refund requests and reject suspicious ones within `unsafe_refund_timelock_sec`. Any gap in monitoring (weekends, incidents, high volume) opens the window.
- The attack is silent: the event emitted is `RefundRequested`, which looks identical to a legitimate request.

**Likelihood class:** Medium — requires DAO inattention, but the attack is cheap, silent, and repeatable.

---

### Recommendation

Add an ownership check in `internal_request_refund` (or `request_refund`) that requires the caller to be the `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient can request a refund"
);
```

Alternatively, allow a DAO/Operator bypass for cases where the recipient is unreachable, but enforce the ownership check for all unprivileged callers. This mirrors the fix described in the external report: binding the operation to the authenticated owner rather than relying solely on a reactive rejection window.

---

### Proof of Concept

1. Victim sends BTC to a deposit address derived from `DepositMsg { recipient_id: "victim.near", refund_address: None, ... }`.
2. The deposit is never finalized (relayer missed it, or the victim used a stale address).
3. Attacker observes the BTC transaction on-chain and the emitted `LogDepositAddress` event to recover the exact `deposit_msg`.
4. Attacker calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's BTC tx>,
     vout = <correct vout>,
     proof = <valid light-client proof>,
     gas_fee = None
   )
   ```
   with `attached_deposit >= required_balance_for_request_refund()`.
5. `internal_request_refund` verifies the proof, skips the `refund_address` constraint (because `deposit_msg.refund_address` is `None`), and stores a `RefundRequest` with `refund_address = "attacker_btc_address"`.
6. DAO does not reject within `unsafe_refund_timelock_sec`.
7. Attacker (or anyone) calls `execute_refund(utxo_storage_key, None)`.
8. The bridge constructs and signs a BTC transaction paying the victim's deposit amount (minus gas fee) to `"attacker_btc_address"`.
