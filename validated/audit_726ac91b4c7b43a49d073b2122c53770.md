Audit Report

## Title
`fin_transfer_send_tokens_callback` Removes Replay-Protection Record on `ft_transfer_call` Refund, Enabling Proof Replay and Double-Minting — (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a `fin_transfer` to a NEAR recipient uses `ft_transfer_call` (triggered by a non-empty `msg` field) and the recipient's `ft_on_transfer` returns `0` (full refund), `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which deletes the `TransferId` from `finalised_transfers`. This is the sole replay-protection record for that cross-chain transfer. Once removed, the identical foreign-chain proof can be re-submitted to `fin_transfer`, causing the bridge to mint or release tokens a second time for the same origin event, repeatable indefinitely.

## Finding Description

**Root cause:** `finalised_transfers` is the only guard preventing proof replay. `add_fin_transfer` inserts the `TransferId` and panics if already present. `remove_fin_transfer` unconditionally deletes it. On a refund path, the callback removes the record, leaving the bridge in a state indistinguishable from "never finalized."

**Code path:**

1. `process_fin_transfer_to_near` calls `add_fin_transfer` (L1875), inserting the `TransferId` into `finalised_transfers`. [1](#0-0) 

2. `add_fin_transfer` enforces uniqueness via `require!(self.finalised_transfers.insert(transfer_id), ...)` — this is the only replay guard. [2](#0-1) 

3. Because `msg` is non-empty, `send_tokens` uses `ft_transfer_call`, chaining to `fin_transfer_send_tokens_callback` with `is_ft_transfer_call = true`. [3](#0-2) 

4. When the recipient's `ft_on_transfer` returns `0`, `is_refund_required` returns `true`, and the callback calls `remove_fin_transfer` at L1714, deleting the `TransferId` from `finalised_transfers`. [4](#0-3) 

5. `remove_fin_transfer` unconditionally removes the entry with no tombstone or alternative record. [5](#0-4) 

6. The same foreign-chain proof is now re-submittable. `add_fin_transfer` will succeed again (set no longer contains the ID), and the bridge will mint or release tokens a second time. The cycle repeats indefinitely.

**Why existing checks fail:** The `require!` in `add_fin_transfer` is the only replay check. There is no secondary record, tombstone, or nonce that persists after `remove_fin_transfer`. After deletion, the contract state is identical to the pre-finalization state.

## Impact Explanation

This directly enables **cross-chain proof replay** and **unauthorized minting / double-spending**:

- **Mintable (bridge-deployed) tokens:** Bridge mints → recipient refunds → bridge burns refunded tokens → record deleted → same proof re-submitted → bridge mints again → unlimited token inflation.
- **Native locked tokens:** Bridge unlocks and transfers → recipient refunds → `revert_lock_actions` re-locks → record deleted → same proof re-submitted → bridge unlocks again → double-spending from the locked pool.

Both match the allowed critical impact: *Cross-chain replay, event/proof parsing flaw, or nonce/replay misuse enabling invalid finalization or double-spending.*

## Likelihood Explanation

The exploit requires no privileged access:

- Any user can deploy a NEAR contract with `ft_on_transfer` returning `0`.
- Any user can initiate a permissionless cross-chain transfer on a supported foreign chain with a non-empty `msg` and their malicious contract as recipient.
- The relayer role is either automated (automated relayers naturally retry transfers whose IDs are absent from `finalised_transfers`) or the attacker can operate their own relayer.
- The attack is repeatable in a loop with no per-iteration cost beyond gas.

## Recommendation

Do **not** remove the `TransferId` from `finalised_transfers` when a refund is required. The finalization record must be permanent regardless of downstream `ft_transfer_call` outcome. Remove only this line from `fin_transfer_send_tokens_callback`:

```rust
// Remove this line — it deletes the only replay guard:
self.remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner);
``` [6](#0-5) 

If storage cost refund is desired, handle it separately without touching `finalised_transfers`. If retry with different parameters is needed, implement a dedicated retry entry-point that does not re-verify the proof and cannot re-insert an already-finalized ID.

## Proof of Concept

1. Deploy `evil.near` on NEAR with `ft_on_transfer` always returning `"0"` (full refund).
2. On Ethereum, call `OmniBridge.initTransfer(token, amount, fee, "evil.near", "trigger")` — the non-empty `"trigger"` string ensures `ft_transfer_call` is used on NEAR.
3. Relayer submits `fin_transfer` with the Ethereum proof. Bridge calls `add_fin_transfer` (ID inserted into `finalised_transfers`), mints tokens, calls `ft_transfer_call("evil.near", amount, "trigger")`.
4. `evil.near::ft_on_transfer` returns `"0"`. Tokens refunded to bridge. `fin_transfer_send_tokens_callback` fires: `is_refund_required` = `true` → `burn_tokens_if_needed` burns refunded tokens → `revert_lock_actions` → `remove_fin_transfer` deletes the ID from `finalised_transfers`.
5. Relayer (or attacker acting as relayer) re-submits the identical Ethereum proof to `fin_transfer`. `add_fin_transfer` succeeds (ID absent). Bridge mints tokens again. Return to step 4. Repeat indefinitely.
