### Title
Peras Certificate Silently Dropped from Chain Selection After Quorum-Completing Vote — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/ChainDB/Impl/ChainSel.hs`)

### Summary

`addPerasVoteWithAsyncCertHandling` commits a vote to the `PerasVoteDB` — including generating a certificate when quorum is reached — inside an atomic STM transaction, but then submits that certificate to the `ChainSelQueue` in a separate, non-atomic IO step. Any per-peer thread killed between these two steps permanently loses the certificate from chain selection. Because the certificate is also never written to the `PerasCertDB`, it is not diffused to other peers either, so no recovery path exists on the affected node without receiving the cert externally.

### Finding Description

The root cause is in `addPerasVoteWithAsyncCertHandling`:

```haskell
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote   -- (1) Effect: VoteDB mutated, cert forged
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      let certTime = getArrivalTime vote
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)  -- (2) Interaction: cert enqueued
      pure (addVoteRes, Just promise)
    _ -> pure (addVoteRes, Nothing)
``` [1](#0-0) 

Step (1) is the **Effect**: `implAddVote` runs inside `atomically`, reads the `pvdeState` TVar, inserts the vote, and — if quorum is reached — forges a `ValidatedPerasCert` and writes the updated `PerasVoteDbState` (including the cert in `pvdsRoundVoteStates`) back to the TVar atomically. [2](#0-1) 

Step (2) is the **Interaction**: `addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message onto `cdbChainSelQueue`. Only when the background `chainSelSync` thread dequeues this message does `PerasCertDB.addCert` run, making the cert visible to chain selection and to the cert-diffusion protocol. [3](#0-2) 

These two steps are **not atomic**. `addPerasVoteWithAsyncCertHandling` is called from per-peer diffusion threads, which are cancelled whenever a peer disconnects. If a peer sends the quorum-completing vote and the connection is dropped before `addPerasCertAsync` returns, the thread receives an async exception and terminates. The VoteDB already holds the forged cert (step 1 committed), but the cert is never enqueued (step 2 never executes).

The cert is **not** written to `PerasCertDB` at this point — that only happens inside `chainSelSync` after dequeuing. Therefore:

- `getPerasCertsAfter` (used by cert diffusion) returns nothing for this cert.
- `chainSelectionForBlock` / `chainSelection` never sees the Peras weight boost.
- No in-process recovery path exists; the cert can only be recovered if another peer independently diffuses it. [4](#0-3) 

### Impact Explanation

The Peras weight boost for the affected round is silently absent from chain selection on the targeted node. The node may therefore prefer a chain that lacks the Peras boost over one that carries it, diverging from the canonical selection that every other honest node performs. This is a **chain-selection bug triggered by an unprivileged peer** that causes an honest node to prefer a non-canonical (less-boosted) chain, matching the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*.

Recovery depends entirely on whether another peer later diffuses the same cert. If the attacker is the sole sender of the quorum-completing vote (e.g., by withholding it from all other nodes), no other node generates the cert, and the divergence is permanent for the affected node.

### Likelihood Explanation

The trigger is straightforward and requires no privileged access:

1. Attacker connects as a normal Peras vote-diffusion peer.
2. Attacker sends exactly the votes needed to bring the round to one vote below quorum.
3. Attacker sends the quorum-completing vote.
4. Attacker immediately closes the TCP connection (or sends a RST).

The per-peer thread receives an async exception during or just after `join . atomically . addVote` but before `addPerasCertAsync`. Because `addVote` is atomic and completes before any IO, the window is the entire duration of `addPerasCertAsync` (a TBQueue write plus a TMVar allocation), which is non-zero and reliably reachable by a network-level disconnect.

### Recommendation

The cert submission must be made atomic with the vote commit, or a durable recovery path must exist. Concrete options:

1. **Atomic enqueue**: Extend `addVote`'s STM transaction to also write the cert directly into `cdbChainSelQueue` (a `TBQueue`), so both the VoteDB update and the queue write happen in a single `atomically` block with no interruptible gap.
2. **Recovery on startup / reconnect**: On node startup and whenever a new peer connects, scan `getForgedCertForRound` for all rounds in the VoteDB and re-submit any cert not yet present in the `PerasCertDB` to `addPerasCertAsync`.
3. **`bracket`/`onException` guard**: Wrap `addPerasCertAsync` in `onException` that re-enqueues the cert, though this is weaker than option 1 because it still relies on the thread being alive long enough to run the handler.

### Proof of Concept

```
Attacker peer  →  node: [vote_1, vote_2, ..., vote_{q-1}]   -- below quorum
Attacker peer  →  node: [vote_q]                             -- quorum-completing
                                                             -- VoteDB atomically updated, cert forged
Attacker peer  →  node: TCP RST / FIN                        -- thread killed
                                                             -- addPerasCertAsync never called
                                                             -- cert absent from PerasCertDB
                                                             -- cert absent from ChainSelQueue
                                                             -- Peras boost never applied
node selects chain without Peras boost ← diverges from canonical selection
```

The cert stored in `pvdsRoundVoteStates` is retrievable via `implGetForgedCertForRound` but is never consumed by any code path that feeds into chain selection or cert diffusion, confirming the permanent loss on the affected node. [5](#0-4)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB
