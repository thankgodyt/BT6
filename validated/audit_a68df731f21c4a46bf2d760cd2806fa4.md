### Title
Unconditional Peras Certificate and Vote Acceptance Bypasses Cryptographic Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance — the only instance in the codebase, applied universally to all block types — implements `validatePerasCert` as an unconditional `Right` (no-op) and `validatePerasVote` without any cryptographic or eligibility check. Both functions are wired directly into the live node-to-node Peras diffusion mini-protocol. An unprivileged peer can send crafted `PerasCert` or `PerasVote` messages that are accepted without any signature, VRF, or committee-membership verification, enabling unauthorized certificate acceptance and artificial quorum construction that distorts Peras chain-weight boosting.

---

### Finding Description

**Vulnerability class:** Bypass of certificate/vote verification — the direct analog of the "missing epoch guard on `poke`" in the original report. Just as `poke` lacked the `onlyNewEpoch` modifier that `vote`/`reset` had, `validatePerasCert` and `validatePerasVote` lack the cryptographic checks that the `BlockSupportsPeras` typeclass contract requires.

**Root cause — `validatePerasCert` is a no-op:**

The universal degenerate instance (the only `BlockSupportsPeras` instance in the codebase) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every `PerasCert` received from the network — regardless of its round number, boosted block, or whether any quorum of legitimate votes ever existed — is unconditionally wrapped in `ValidatedPerasCert` and assigned the full `perasWeight` boost. No signature, no quorum proof, no committee check.

**Root cause — `validatePerasVote` skips cryptographic eligibility:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

The `PerasVote blk` data type in this instance carries no signature field at all:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound :: PerasRoundNo
  , pvVoteBlock :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [3](#0-2) 

Validation only checks whether the claimed `pvVoteVoterId` appears in the stake distribution. There is no BLS signature check, no VRF eligibility proof, and no committee-seat verification. Any peer who knows the public key hashes of committee members (which are public) can craft votes for all of them.

**This is the universal production instance:**

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
``` [4](#0-3) 

There is no other `BlockSupportsPeras` instance. This instance governs all block types including Cardano blocks.

**Network entry path — cert diffusion:**

The cert diffusion inbound handler in the live node-to-node stack calls `makePerasCertPoolWriterFromChainDB`, which feeds received certs through `validatePerasCert`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [5](#0-4) 

**Network entry path — vote diffusion:**

The vote diffusion inbound handler calls `processVotes` → `validatePerasVote`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [6](#0-5) 

The `processVotes` function is the gating function for all inbound votes: [7](#0-6) 

Note: the current production wiring passes `(pure (PerasVoteStakeDistr mempty))` as the stake distribution, which causes all votes to be rejected today. However, the code comment explicitly states this is a temporary placeholder:

```haskell
-- TODO: when actual plumbing for Peras is ready, we will have to
-- extract the committee selection data from the chainDB to pass
-- it here, instead of relying on an empty the stake distribution.
--
-- Note that the empty stake distribution will cause all votes to
-- be considered invalid.
(pure (PerasVoteStakeDistr mempty))
``` [8](#0-7) 

Once the real stake distribution is wired in (as the TODO requires), the vote path becomes exploitable. The cert path has no such temporary mitigation.

---

### Impact Explanation

**For `validatePerasCert` (active now):** An unprivileged peer can send a crafted `PerasCert` for any `(roundNo, blockPoint)` pair. The node accepts it as a `ValidatedPerasCert` with full `perasWeight` boost. This allows the attacker to artificially boost any block's chain weight, causing the victim node to prefer a non-canonical chain. This is a **Critical** bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-selection manipulation.

**For `validatePerasVote` (active once TODO is resolved):** An unprivileged peer who knows the public key hashes of committee members (public information) can craft votes for all of them without possessing their BLS signing keys. Since `PerasVoteId = (roundNo, voterId)` deduplication prevents the same voter from being counted twice, the attacker needs one crafted vote per committee member — but needs no cryptographic material. This enables artificial quorum construction and unauthorized certificate forging.

---

### Likelihood Explanation

The cert path is **immediately exploitable** by any peer connected via the node-to-node protocol. The `PerasCert` wire format is public (CBOR-serialized `(PerasRoundNo, Point blk)`), and the cert diffusion inbound handler is active in the live stack. No keys, no stake, no special position required — just a network connection and knowledge of the serialization format.

The vote path becomes exploitable as soon as the `PerasVoteStakeDistr mempty` placeholder is replaced with real data, which is a planned and necessary step for Peras activation.

---

### Recommendation

1. **`validatePerasCert`**: Implement full certificate validation before the cert diffusion protocol is enabled in production. At minimum, verify that the certificate is backed by a quorum of valid, cryptographically signed votes from eligible committee members for the claimed round. The `PerasBLSCrypto` infrastructure in `Ouroboros.Consensus.Peras.Crypto.BLS` already provides `verifyVoteSignature` — use it.

2. **`validatePerasVote`**: Add the `pvSignature` field (as already done in `Ouroboros.Consensus.Peras.Vote.V1.PerasVote`) to the production `PerasVote blk` type and implement `verifyVoteSignature` + VRF eligibility proof verification in `validatePerasVote` before wiring in the real stake distribution.

3. **Do not resolve the `PerasVoteStakeDistr mempty` TODO** until `validatePerasVote` performs full cryptographic validation.

4. Track both issues under the existing `https://github.com/tweag/cardano-peras/issues/120`.

### Proof of Concept

A private-testnet node running with Peras cert diffusion enabled receives the following crafted CBOR message from an attacker peer (using the `PerasCertDiffusion` mini-protocol):

```
-- Attacker constructs a PerasCert for an arbitrary block at round 999
-- Wire format: CBOR list of length 2: [roundNo, blockPoint]
craftedCert :: PerasCert TestBlock
craftedCert = PerasCert
  { pcCertRound      = PerasRoundNo 999
  , pcCertBoostedBlock = someAdversarialBlockPoint
  }

-- validatePerasCert is called on receipt:
validatePerasCert mkPerasParams craftedCert
-- Returns: Right (ValidatedPerasCert { vpcCert = craftedCert
--                                    , vpcCertBoost = perasWeight mkPerasParams })
-- No error. No signature checked. No quorum verified.
-- The adversarial block now has boosted chain weight.
```

The node accepts the cert, boosts `someAdversarialBlockPoint`'s chain weight by `perasWeight`, and may switch its selection to the adversarial chain — all triggered by a single unauthenticated network message from an unprivileged peer. [9](#0-8)

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
