Audit Report

## Title
Fee Validation Without Decimal Normalization Check Causes Permanent Locking of User Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

`init_transfer` locks or burns user tokens after only checking `fee < amount`, without verifying that `normalize_amount(amount - fee, decimals) > 0`. When the net transfer amount is below the decimal normalization threshold, `sign_transfer` panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` in a separate transaction, leaving the already-locked tokens permanently frozen with no recovery path.

## Finding Description

In `init_transfer` (called via `ft_on_transfer`), the only fee guard before tokens are committed is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

This passes for any `fee = 0` and any `amount > 0`. Control then flows to `init_transfer_internal`, which locks or burns the full `transfer_message.amount`:

```rust
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
``` [2](#0-1) 

Later, when a relayer calls `sign_transfer` in a separate transaction, the bridge normalizes the net amount via floor division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) 

For a token pair with `origin_decimals = 24`, `dest_decimals = 6`, the divisor is `10^18`. Any `amount_without_fee < 10^18` normalizes to 0, triggering:

```rust
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [4](#0-3) 

This panic occurs in a separate transaction after the lock/burn is already committed. There is no `cancel_transfer` function in the contract, and `update_transfer_fee` enforces `fee.fee >= current_fee.fee`, meaning the fee can only be increased — not decreased to create a valid normalized amount: [5](#0-4) 

The codebase itself acknowledges this behavior in a comment on `normalize_amount`: *"When fee = 0, dust stays locked/burned. See SECURITY.md for details."* — but the referenced SECURITY.md contains no details about this scenario or any recovery mechanism. [6](#0-5) 

## Impact Explanation

User funds are permanently frozen in the bridge contract with no recovery path. This directly matches the Critical impact category: **permanent freezing of bridged funds**. For a 24→6 decimal pair (e.g., NEAR-native token to a 6-decimal EVM token), any transfer where `amount_without_fee < 10^18` yoctoNEAR (up to ~1 NEAR per transfer) is unrecoverable. The tokens are locked in `init_transfer_internal` and the only subsequent operation (`sign_transfer`) panics, leaving the contract state permanently inconsistent.

## Likelihood Explanation

Any unprivileged user can trigger this by calling `ft_on_transfer` with an `amount` and `fee` such that `amount - fee < 10^(origin_decimals - dest_decimals)`. This is reachable on any token pair where `origin_decimals > dest_decimals`, which is the standard operating mode for bridging NEAR-native tokens to EVM chains. The condition can be hit accidentally (user underestimates the normalization threshold) or deliberately (self-griefing). No special privileges, oracle manipulation, or external collusion is required.

## Recommendation

Add a normalization check inside `init_transfer` (or `init_transfer_internal`) before tokens are locked or burned. Retrieve the destination token's `Decimals` and assert `normalize_amount(amount_without_fee, decimals) > 0` at the same point where `fee < amount` is currently checked. This mirrors the guard already present in `sign_transfer` but must be enforced atomically at the point of commitment, not deferred to a later transaction.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (divisor = `10^18`).
2. User calls `ft_on_transfer` transferring `amount = 5 * 10^17` yoctoNEAR (0.5 NEAR) with `fee = 0`.
3. Check at L554–557: `0 < 5×10^17` passes. `init_transfer_internal` locks 0.5 NEAR.
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(5 * 10^17, {24, 6}) = 5 * 10^17 / 10^18 = 0`.
6. `require!(0 > 0, ...)` panics → transaction reverts, transfer message remains stored, tokens remain locked.
7. `update_transfer_fee` cannot reduce the fee below its current value; no `cancel_transfer` exists. The 0.5 NEAR is permanently locked.
