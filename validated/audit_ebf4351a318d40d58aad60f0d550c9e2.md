### Title
Missing Upper-Bound Validation on Caller-Supplied Refund Gas Fee Enables Attacker to Drain User Refund to Miners - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund_callback` accepts a caller-supplied `gas_fee` with only a lower-bound check (`gas_fee < amount`). There is no upper-bound (maximum) validation. Any unprivileged account can submit a refund request for any deposit UTXO with `gas_fee = amount - 1`, causing the refund PSBT to be constructed with a 1-satoshi user output and the entire remaining deposit value paid to miners. Because the duplicate-request guard blocks subsequent legitimate requests for the same UTXO, the victim cannot self-correct without DAO intervention.

### Finding Description
In `request_refund_callback` the resolved gas fee is validated only as:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

No maximum gas fee is enforced. The stored `gas_fee` is later consumed without re-validation in `refund_execution_inputs`:

```rust
let refund_amount = refund_request.amount.checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [2](#0-1) 

The resulting PSBT is built with a single output of `refund_amount` to the refund address; the entire `gas_fee` difference is implicitly paid to miners. No change output returns excess value to the bridge. [3](#0-2) 

Once a refund request is stored, the duplicate guard prevents any other request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

This is in direct contrast to the withdrawal flow, which enforces `gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee`: [5](#0-4) 

### Impact Explanation
An attacker can cause a victim's entire deposit to be consumed as a miner fee, leaving the victim with 1 satoshi. The victim cannot submit a competing refund request (duplicate guard). Recovery requires the DAO to reject the malicious request within the timelock window. If the DAO is slow or unresponsive, the refund PSBT is signed and broadcast with the attacker-chosen fee, resulting in significant, irreversible loss of user funds. This matches **Medium: attacker-triggered loss of bridged funds / bypass of bridge fee policies**.

### Likelihood Explanation
`request_refund` is a public, permissionless entry point. Any NEAR account can call it for any deposit UTXO whose `tx_bytes` and `deposit_msg` are publicly observable on-chain. The attacker only needs to pay a small NEAR storage deposit. The `unsafe_refund_timelock_sec` gives the DAO time to reject, but the attack is trivially executable and the DAO must actively monitor every refund request to prevent it.

### Recommendation
Add a configurable `max_refund_gas_fee` to the bridge `Config` and enforce it in `request_refund_callback`:

```rust
require!(
    resolved_gas_fee <= config.max_refund_gas_fee,
    "Gas fee exceeds maximum allowed refund gas fee"
);
```

This mirrors the existing `max_btc_gas_fee` bound used in `check_withdraw_psbt`.

### Proof of Concept
1. Alice deposits 500,000 sat to the bridge; the deposit is verified on-chain.
2. Mallory observes the deposit transaction on Bitcoin and the corresponding `deposit_msg` (emitted as an event or derivable from the deposit address).
3. Mallory calls `request_refund(deposit_msg, alice_address, tx_bytes, vout, proof, gas_fee = Some(499_999))` with a small NEAR storage deposit attached.
4. The call passes: `499_999 < 500_000`. A `RefundRequest` is stored with `gas_fee = 499_999`.
5. Alice attempts `request_refund` for the same UTXO — it panics: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` elapses (if DAO does not reject), anyone calls `execute_refund`.
7. `refund_execution_inputs` computes `refund_amount = 500_000 - 499_999 = 1`.
8. The PSBT is built: 1 input (500,000 sat), 1 output (1 sat to Alice). 499,999 sat goes to miners.
9. The MPC signs the PSBT; the transaction is broadcast. Alice receives 1 satoshi. [1](#0-0) [6](#0-5)
