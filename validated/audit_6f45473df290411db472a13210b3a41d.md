### Title
`safe_mint` Mints nBTC to Bridge Before Checking Recipient Registration, Causing Permanent Token Inflation and Stuck Funds — (File: `contracts/nbtc/src/lib.rs`)

### Summary

The `safe_mint` function in the nBTC contract unconditionally mints `amount` tokens to the bridge's own balance before checking whether the intended recipient account is registered. If the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens, leaving them permanently stuck in the bridge's balance while the total nBTC supply is inflated without any corresponding user benefit.

### Finding Description

In `contracts/nbtc/src/lib.rs` lines 101–124, `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally, increasing the total nBTC supply by `amount` and crediting the bridge's own token balance. Only after this irreversible state change does it check whether the recipient is registered:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mint committed here

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← tokens stuck, supply inflated
    }
    // ...transfer to account_id...
}
``` [1](#0-0) 

If the recipient is unregistered, the function returns `PromiseOrValue::Value(U128(0))` — signaling zero tokens transferred — but the minted tokens remain in the bridge's balance with no mechanism to burn them back.

The safe deposit flow (triggered via `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`) is documented as reverting the whole transaction if minting fails: [2](#0-1) 

However, in NEAR's asynchronous execution model, the `safe_mint` cross-contract call has already committed its state change (the mint to `bridge_id`) before the bridge's callback can observe the `U128(0)` return value. The bridge cannot atomically undo the mint — the `internal_deposit` to `bridge_id` is final.

By contrast, the standard `mint` path uses `mint_inner`, which auto-registers the account before depositing, so it never leaves tokens stranded: [3](#0-2) 

The `safe_mint` path deliberately skips auto-registration (to avoid paying storage for unregistered accounts), but the current ordering — mint first, check second — is the root cause of the accounting failure.

### Impact Explanation

- Total nBTC supply increases by `amount` without the user receiving any tokens.
- The bridge's nBTC balance holds unbacked tokens not tied to any user's withdrawal claim, breaking the 1:1 BTC-to-nBTC invariant.
- The user's BTC remains locked in the bridge with no corresponding nBTC issued.
- Recovery requires privileged operator intervention to manually burn the stuck tokens and reconcile state.

This matches: **Medium — harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply, broken callback rollback, or stuck bridge state requiring operator intervention.**

### Likelihood Explanation

The safe deposit flow requires the caller to attach NEAR for the user's token storage registration (`required_balance_for_safe_deposit`). If the attached NEAR is insufficient, or if the user's nBTC account is unregistered at the time `safe_mint` executes (e.g., the user called `storage_unregister` between their BTC deposit and the relayer's `verify_deposit_v2` call), the bug triggers. Any user depositing BTC via the safe deposit path without a properly registered nBTC account can cause this condition — no privileged access is required to initiate the BTC deposit.

### Recommendation

Check recipient registration **before** minting, and revert if unregistered, so no tokens are ever committed to the bridge's balance when the transfer cannot proceed:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    // Check BEFORE minting
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ...transfer to account_id...
}
```

### Proof of Concept

1. User deposits BTC to the bridge's deposit address (unprivileged action).
2. User's NEAR account (`alice.near`) is not registered in the nBTC contract — either never registered, or the user called `storage_unregister` before the relayer processes the deposit.
3. Relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`.
4. Bridge verifies the deposit and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
5. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — total nBTC supply increases by 1,000,000 satoshis, bridge balance credited.
6. `safe_mint` checks `accounts.get(&alice.near)` — account not found.
7. `safe_mint` returns `U128(0)` — `alice.near` receives 0 nBTC.
8. Bridge's callback observes `U128(0)` but cannot undo the already-committed `internal_deposit`.
9. **Result**: 1,000,000 satoshis of nBTC are permanently stuck in the bridge's balance, `alice.near`'s BTC is locked with no recourse, and the total nBTC supply is inflated above the amount of BTC actually backing it.
