### Title
Fixed `min_btc_gas_fee` Lower Bound Does Not Scale With Transaction Size on Bitcoin Path - (`File: contracts/satoshi-bridge/src/bitcoin_utils/contract_methods.rs`)

### Summary

The Bitcoin withdrawal path enforces only a static `min_btc_gas_fee` lower bound on the miner fee, without accounting for the actual byte-size of the transaction. A user can submit a withdrawal PSBT with the maximum allowed number of inputs and outputs while paying only the fixed minimum fee, producing a transaction with a fee rate far below what is needed for timely confirmation. The Zcash path correctly validates a structure-aware ZIP-317 minimum fee, but the Bitcoin `check_psbt_chain_specific` is a deliberate no-op, leaving the Bitcoin path unprotected.

### Finding Description

In `check_withdraw_psbt`, after computing `gas_fee = total_input_amount - total_output_amount`, the only fee floor enforced for Bitcoin is:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
self.check_psbt_chain_specific(psbt, gas_fee, target_btc_address);
``` [1](#0-0) 

The call to `check_psbt_chain_specific` is supposed to enforce a structure-aware minimum. On the Zcash path it does exactly that — it calls `psbt.get_min_fee()` (ZIP-317, which accounts for input count, output sizes, and Orchard actions) and rejects any fee below that floor: [2](#0-1) 

On the Bitcoin path, however, `check_psbt_chain_specific` is an empty stub:

```rust
pub(crate) fn check_psbt_chain_specific(
    &self,
    _psbt: &PsbtWrapper,
    _gas_fee: u128,
    _target_btc_address: String,
) {
}
``` [3](#0-2) 

The config allows up to `max_withdrawal_input_number = 10` inputs and `max_change_number = 10` change outputs. [4](#0-3) 

A P2WPKH input is ~68 vbytes and a P2WPKH output is ~31 vbytes. A 10-input / 10-output transaction is roughly 1,000 vbytes. With `min_btc_gas_fee = 10,000 sat` (the deployed value), the effective fee rate is ~10 sat/vbyte — already marginal. An attacker who deliberately maximises inputs and outputs while paying exactly `min_btc_gas_fee` can produce a transaction whose fee rate is 10× lower than a single-input transaction paying the same floor, making it likely to be stuck in the mempool during any fee-rate spike. [5](#0-4) 

### Impact Explanation

A stuck Bitcoin transaction locks the user's withdrawal UTXO(s) in a `PendingSign` / `PendingVerify` state. The bridge must issue an RBF bump (consuming additional bridge-side gas and operator attention) to unstick it. An attacker who repeatedly opens maximum-size withdrawals at the minimum fee can saturate the bridge's pending-transaction capacity and force continuous RBF operations, temporarily locking bridged funds and requiring operator intervention. This matches the **Medium** impact class: attacker-triggered temporary locking of bridged funds / bypass of bridge fee policies.

### Likelihood Explanation

Any unprivileged NEAR account holding nBTC can call `ft_transfer_call` with a `TokenReceiverMessage::Withdraw` payload specifying up to 10 inputs and 10 change outputs while setting the fee to exactly `min_btc_gas_fee`. No special role or leaked key is required. The attack is cheap to execute repeatedly.

### Recommendation

Replace the empty Bitcoin `check_psbt_chain_specific` with a size-aware minimum-fee check analogous to the Zcash ZIP-317 check. For Bitcoin SegWit (P2WPKH) transactions the minimum fee can be computed as:

```
min_fee = ceil(tx_vbytes * min_fee_rate_sat_per_vbyte)
tx_vbytes ≈ 10 + 41 * n_inputs + 31 * n_outputs   // P2WPKH
```

where `min_fee_rate_sat_per_vbyte` is a new config parameter (e.g. 5–10 sat/vbyte). Alternatively, expose a `min_fee_rate` config field and enforce `gas_fee >= min_fee_rate * estimated_vbytes` inside `check_psbt_chain_specific` for the Bitcoin feature flag, mirroring the Zcash path's structure-aware validation.

### Proof of Concept

1. Alice holds 1,000,000 sat of nBTC and the bridge has 10 UTXOs of ~100,000 sat each.
2. Alice calls `ft_transfer_call` with `TokenReceiverMessage::Withdraw`, specifying all 10 UTXOs as inputs, 9 change outputs, and a fee of exactly `min_btc_gas_fee` (10,000 sat).
3. `check_withdraw_psbt` passes: `gas_fee = 10,000 >= min_btc_gas_fee`; `check_psbt_chain_specific` is a no-op.
4. The bridge signs and broadcasts a ~1,000-vbyte transaction paying 10 sat/vbyte.
5. During a fee-rate spike (common on Bitcoin mainnet), the transaction is not confirmed. All 10 UTXOs are locked in a pending state.
6. The bridge operator must issue RBF bumps, paying additional fees from bridge reserves, to unstick the transaction.
7. Alice repeats the attack with fresh UTXOs, continuously exhausting bridge pending capacity. [6](#0-5)

    pub(crate) fn check_psbt_chain_specific(
        &self,
        psbt: &PsbtWrapper,
        gas_fee: u128,
        target_btc_address: String,
    ) {
        let min_fee = psbt.get_min_fee();
        require!(
            gas_fee >= min_fee.into_u64() as u128,
            format!(
                "Invalid gas fee ({}). min fee = {}.",
                gas_fee,
                min_fee.into_u64()
            )
        );

        // For withdrawals with Orchard bundle, calculate the expected net amount after fees
        if psbt.has_orchard_bundle() {
            psbt.validate_orchard_bundle(target_btc_address, self.internal_config().chain.clone());
        }
    }
