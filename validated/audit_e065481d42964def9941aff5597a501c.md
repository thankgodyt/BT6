### Title
Silent `tx_bytes` Corruption for Oversized Safe-Deposit Transactions Permanently Locks Bridge UTXOs - (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

In `internal_safe_verify_deposit_entry`, when the caller-supplied `tx_bytes` exceed 10,000 bytes, the code silently replaces them with 300 zero bytes before storing the UTXO. nBTC is still minted to the user, but the bridge's stored UTXO record is permanently corrupted. Any later attempt to spend that UTXO (withdrawal, active UTXO management, or refund) will fail because the bridge cannot reconstruct a valid PSBT from zeroed-out transaction bytes.

---

### Finding Description

In `internal_safe_verify_deposit_entry` (lines 204–209 of `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`):

```rust
let tx_bytes = if tx_bytes.len() > 10000 {
    env::log_str("tx_bytes length exceeds 10000, truncating to 300 bytes");
    vec![0u8; 300]
} else {
    tx_bytes
};

let utxo = UTXO {
    path,
    tx_bytes,          // ← 300 zero bytes when original > 10 000 bytes
    vout,
    balance: transaction.output()[vout].value.to_sat(),  // ← correct, from original
};
```

The `balance` field is computed from the original decoded `transaction` (before the replacement), so the accounting is numerically correct. However, the `tx_bytes` field stored in the `UTXO` struct is now `[0u8; 300]` — an invalid Bitcoin transaction.

This corrupted UTXO is later inserted into the bridge's live UTXO set via `safe_mint_callback` → `internal_set_utxo` when the `safe_mint` call succeeds. From that point on, the bridge holds a UTXO record whose `tx_bytes` cannot be decoded into a real Bitcoin transaction.

When the bridge later tries to spend this UTXO — whether for a user withdrawal, active UTXO management, or a refund — it must reconstruct a PSBT from the stored `tx_bytes`. The PSBT builder calls `WrappedTransaction::decode` on those bytes. Decoding 300 zero bytes as a Bitcoin transaction will panic (`.expect("Deserialization tx_bytes failed")`), permanently blocking any spend of that UTXO.

The analog to the Chainlink `latestAnswer` issue is direct: just as `latestAnswer` silently returns `0` instead of reverting when no answer is available — causing downstream logic to proceed with an invalid price — this bridge silently stores `[0u8; 300]` instead of rejecting the oversized input, causing all downstream spend operations to fail.

---

### Impact Explanation

**Medium — stuck bridge state requiring operator intervention / attacker-triggered temporary locking of bridged funds.**

- The depositor receives correctly-minted nBTC.
- The corresponding BTC UTXO is permanently unspendable by the bridge because the stored `tx_bytes` are invalid.
- Every withdrawal attempt that selects this UTXO will panic during PSBT construction.
- The BTC is not lost from the Bitcoin blockchain, but the bridge cannot move it without manual operator recovery (e.g., a contract upgrade that patches the stored UTXO record).
- If multiple such deposits accumulate, the bridge's spendable UTXO pool shrinks, degrading withdrawal capacity.

---

### Likelihood Explanation

A Bitcoin transaction exceeds 10,000 bytes when it consolidates roughly 60–100+ inputs (e.g., a user sweeping many small UTXOs into a single deposit). This is uncommon in normal usage but is a realistic scenario for users consolidating dust or for an adversary deliberately constructing such a transaction to grief the protocol. The `safe_verify_deposit` / `verify_deposit_v2` path is publicly callable by any NEAR account (subject to the `#[trusted_relayer]` whitelist), so the entry point is reachable by a whitelisted relayer submitting a legitimately large BTC transaction.

---

### Recommendation

Replace the silent truncation with an explicit rejection:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes too large for safe deposit"
);
```

If large transactions must be supported, store the full `tx_bytes` (accepting the higher storage cost) or derive and store only the minimal data needed for PSBT construction (the specific previous output at `vout`), rather than replacing the bytes with an invalid placeholder.

---

### Proof of Concept

1. Construct a Bitcoin transaction with ≥ 100 P2PKH inputs paying to the bridge deposit address, making `tx_bytes.len() > 10_000`.
2. Call `safe_verify_deposit` (or `verify_deposit_v2` with `safe_deposit = Some(..)`) with this transaction.
3. The light-client proof passes; `verify_safe_deposit_callback` fires; `safe_mint` succeeds; `safe_mint_callback` calls `internal_set_utxo` storing `UTXO { tx_bytes: vec![0u8; 300], balance: <correct>, … }`.
4. nBTC is minted to the recipient.
5. Later, any call that selects this UTXO for spending (user withdrawal, `active_utxo_management`, `execute_refund`) reaches `WrappedTransaction::decode(&utxo.tx_bytes, …).expect("Deserialization tx_bytes failed")` and panics, permanently blocking the spend path for that UTXO.
