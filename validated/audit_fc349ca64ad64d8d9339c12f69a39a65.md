### Title
Concurrent `sign_btc_transaction` calls for the same index cause second callback to panic and lose attached NEAR deposit — (`contracts/satoshi-bridge/src/chain_signature.rs`)

---

### Summary

The pre-call guard in `internal_sign_btc_transaction` (line 92) and the write in `sign_btc_transaction_callback` (line 158) are not atomic. Two concurrent calls for the same `btc_pending_sign_id` and `sign_index` can both pass the `is_none()` check, dispatch two MPC sign promises, and when both callbacks land the second one panics at the `require!` on line 154–157. The NEAR deposit attached to the second call was already forwarded to the MPC contract and is unrecoverable.

---

### Finding Description

`sign_btc_transaction` is a public, payable function with no caller-authorization check: [1](#0-0) 

It delegates to `internal_sign_btc_transaction`, which performs a pre-call guard: [2](#0-1) 

If the check passes, the attached deposit is forwarded to the MPC contract and a callback is chained: [3](#0-2) 

The callback re-checks the same invariant before writing: [4](#0-3) 

Because NEAR cross-contract calls are asynchronous, two transactions submitted before either callback lands will both read `signatures[sign_index]` as `None`, both pass line 92, both forward their deposits to MPC, and both schedule callbacks. When the callbacks execute sequentially, the first succeeds and writes the signature; the second finds `signatures[sign_index].is_some()` and panics at line 154. The panic reverts the second callback's state changes but **cannot recover the deposit already consumed by the MPC sign call**.

There is no "in-flight" marker set between the pre-call check and the callback write, so the window is open for the entire MPC signing round-trip (typically multiple blocks).

---

### Impact Explanation

- The NEAR deposit attached to the second `sign_btc_transaction` call is permanently lost; it was forwarded to the MPC contract via `with_attached_deposit(env::attached_deposit())` before the callback panics.
- The callback panic is publicly reachable and reproducible.
- Bridge state is not permanently corrupted (the first callback's write stands), but the panic constitutes a reachable invariant violation in the production signing path.

Impact: **Low** — publicly reachable panic-driven fault with attached-deposit loss, no direct theft of bridged funds.

---

### Likelihood Explanation

- `sign_btc_transaction` has no caller-authorization check, so any account can call it for any `btc_pending_sign_id`.
- An attacker observing a pending sign entry in contract state can race or front-run the legitimate caller for the same index.
- Accidental double-submission by a relayer also triggers the same path.
- The race window spans the full MPC signing latency (multiple NEAR blocks), making it easy to hit.

---

### Recommendation

Set an "in-flight" flag on `signatures[sign_index]` (e.g., a sentinel value or a separate `signing_in_flight: Vec<bool>`) atomically within `internal_sign_btc_transaction`, before dispatching the MPC promise. The callback should check and clear this flag. This closes the TOCTOU window and prevents duplicate MPC dispatches for the same index.

---

### Proof of Concept

```
1. Contract state: BTCPendingInfo with 2 inputs, signatures = [None, None], stage = PendingSign.

2. Block N:
   - Tx A: caller_A calls sign_btc_transaction(id, sign_index=0) with deposit D_A
     → line 92: signatures[0].is_none() == true → passes
     → forwards D_A to MPC, schedules callback_A
   - Tx B: caller_B calls sign_btc_transaction(id, sign_index=0) with deposit D_B
     → line 92: signatures[0].is_none() == true (callback_A not yet landed) → passes
     → forwards D_B to MPC, schedules callback_B

3. Block N+k (MPC responds):
   - callback_A executes: line 154 passes, writes signatures[0] = Some(...), D_A consumed.
   - callback_B executes: line 154 → signatures[0].is_some() → require! panics.
     D_B is already gone (forwarded to MPC in step 2). Panic reverts callback_B state only.

Result: D_B is permanently lost; second callback panics in production signing path.
```

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
