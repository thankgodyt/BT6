Audit Report

## Title
Silent ERC1155 `safeTransferFrom` on Codeless Address Enables Unauthorized NEP-141 Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` calls `IERC1155(tokenAddress).safeTransferFrom(...)` — a void function — on a caller-supplied address with no code-existence check. In Solidity ≥0.8, a high-level call to a void function on a codeless address silently returns success because the EVM `CALL` opcode to a codeless address returns `(success=true, returndata=empty)` and Solidity has no returndata to decode. Combined with the permissionless `logMetadata1155`, an attacker can register a phantom ERC1155 address, trigger a silent "lock" of zero real tokens, and cause NEAR to mint an arbitrary quantity of NEP-141 bridged tokens for free.

## Finding Description

**Root cause 1 — `logMetadata1155` accepts any address without code check:**

`logMetadata1155` (lines 234–270) never calls any function on `tokenAddress`. It only writes `multiTokens[deterministicToken]` and emits `LogMetadata`. There is no `require(tokenAddress.code.length > 0)` guard. Any EOA can register a phantom address.

**Root cause 2 — `initTransfer1155` calls a void function on an unverified address:**

At line 458, `initTransfer1155` executes:
```solidity
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender, address(this), tokenId, amount, ""
);
```
`IERC1155.safeTransferFrom` has no return value. The Solidity compiler emits no `extcodesize` check for void high-level calls. When `tokenAddress` has no deployed code, the EVM `CALL` returns `(success=true, returndata=empty)`; Solidity has nothing to decode and does not revert. The bridge believes tokens were locked when none were.

**Contrast with ERC-20 path:**

`initTransfer` uses `SafeERC20.safeTransferFrom` (line 407), which internally calls OZ's `Address.functionCall`, which explicitly checks `address(token).code.length > 0` before proceeding. The ERC-20 path is therefore protected; the ERC-1155 path is not.

**`onERC1155Received` does not help:**

The bridge's `onERC1155Received` callback (lines 522–535) is only invoked by the ERC1155 token contract itself during a real transfer. If `tokenAddress` has no code, no callback is ever made, so this guard is irrelevant.

**NEAR-side processing:**

`fin_transfer_callback` (near/omni-bridge/src/lib.rs, lines 704–718) checks that the emitter is a known factory and that `token_decimals` is set for `init_transfer.token`. After `logMetadata1155` is processed by the relayer, `token_decimals` is populated (with decimals=0 as passed by `logMetadata1155`). The NEAR side then proceeds to mint NEP-141 tokens for the claimed amount.

**Full exploit path:**

1. Attacker calls `logMetadata1155(phantomAddress, tokenId)` — no code check, mapping written, `LogMetadata` emitted.
2. NEAR relayer processes `LogMetadata`; `deploy_token_callback` deploys a NEP-141 token and sets `token_decimals[deterministicToken] = 0`.
3. Attacker calls `initTransfer1155(phantomAddress, tokenId, 1_000_000e18, 0, 0, "attacker.near", "")` — `safeTransferFrom` silently succeeds, `InitTransfer` emitted claiming 1,000,000e18 tokens locked.
4. NEAR relayer processes `InitTransfer` proof; `fin_transfer_callback` mints 1,000,000e18 NEP-141 tokens to attacker.

Zero real ERC1155 tokens are ever held by the bridge.

## Impact Explanation

An attacker can mint an unbounded quantity of NEP-141 bridged tokens on NEAR without locking any real ERC1155 collateral on EVM. This directly inflates the NEP-141 supply beyond the real collateral held by the bridge, rendering it insolvent. Legitimate users who later bridge real ERC1155 tokens from NEAR back to EVM will find the bridge holds no collateral; their `finTransfer` calls silently consume nonces without delivering tokens — permanent loss of bridged funds. This matches the Critical impact class: **unauthorized minting and permanent freezing of bridged funds**.

## Likelihood Explanation

Both entry-point functions (`logMetadata1155` and `initTransfer1155`) are fully permissionless and callable by any EOA with no special role. The attack requires only two on-chain transactions plus waiting for the relayer to process the resulting events. No victim interaction, no privileged access, and no external dependency is required. The attack is repeatable indefinitely until the bridge is paused.

## Recommendation

1. Add a code-existence check in `initTransfer1155` before calling `safeTransferFrom`:
   ```solidity
   require(tokenAddress.code.length > 0, "ERC1155: token address has no code");
   ```
2. Add the same guard in `logMetadata1155` to prevent registering phantom tokens before the ERC1155 is deployed:
   ```solidity
   require(tokenAddress.code.length > 0, "ERC1155: token address has no code");
   ```
3. Alternatively, implement a `SafeERC1155` wrapper analogous to OZ's `SafeERC20` that performs a code-existence check (`Address.functionCall`) before any ERC1155 call, mirroring the protection already present on the ERC-20 path.

## Proof of Concept

```solidity
// SPDX-License-Identifier: GPL-3.0-or-later
pragma solidity ^0.8.24;

// Step 1: Register phantom address (no code at phantomAddr)
bridge.logMetadata1155(phantomAddr, tokenId);
// → multiTokens[deterministicToken] written, LogMetadata emitted
// → NEAR relayer deploys NEP-141, sets token_decimals

// Step 2: Trigger silent lock
bridge.initTransfer1155{value: nativeFee}(
    phantomAddr,   // no code here
    tokenId,
    1_000_000e18, // claimed amount
    0,             // fee
    nativeFee,
    "attacker.near",
    ""
);
// → IERC1155(phantomAddr).safeTransferFrom(...) → void call on codeless address → silent success
// → InitTransfer emitted claiming 1_000_000e18 tokens locked
// → NEAR relayer mints 1_000_000e18 NEP-141 to attacker.near
```

A Foundry invariant test can confirm this: deploy `OmniBridge`, call `logMetadata1155` with an address that has no code, then call `initTransfer1155` — both calls succeed and `InitTransfer` is emitted with the full claimed amount, while the bridge's actual ERC1155 balance remains zero.
