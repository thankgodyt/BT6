### Title
Unconditional Pre-Minting in `safe_mint` Inflates nBTC Supply When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge's own account **before** verifying that the intended recipient has a registered token account. When the recipient is unregistered, the minted tokens are permanently stranded in the bridge's balance, inflating the nBTC total supply beyond its BTC backing. Depending on how the bridge's callback handles the `U128(0)` return, this either enables double-minting (if the bridge reverts UTXO verification) or causes permanent loss of the user's BTC deposit (if it does not).

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function executes as follows:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0)); // ← returns 0, tokens stuck in bridge_id
    }
    // ... transfer to account_id
}
```

The call to `self.token.internal_deposit(&self.bridge_id, amount.into())` is a **direct, committed state mutation** — it increases both the bridge's nBTC balance and the total supply by `amount`. This happens unconditionally, before the account registration check. If `account_id` is not registered, the function returns `U128(0)` without transferring, leaving `amount` nBTC permanently minted to `bridge_id` with no corresponding BTC backing for those tokens.

In NEAR's asynchronous execution model, `safe_mint` executes in its own receipt. If the bridge's callback receipt subsequently panics (because `safe_mint` returned 0, signaling failure), only the bridge's callback-receipt state changes are reverted — the nBTC minting in the prior receipt is **irrevocable**.

**Scenario A — Bridge callback reverts UTXO verification on `U128(0)` return:**
1. User makes a BTC deposit with a `safe_deposit` message (e.g., Omni Bridge flow), but their NEAR account is not registered in the nBTC contract.
2. Relayer submits proof via `verify_deposit_v2`; bridge calls `safe_mint(user, amount, msg)`.
3. nBTC mints `amount` to `bridge_id`, sees `user` unregistered, returns `U128(0)`.
4. Bridge callback panics/reverts → UTXO is **not** marked as verified.
5. `amount` nBTC is now permanently in `bridge_id` (supply inflated, unbacked).
6. User registers their nBTC account and calls `safe_verify_deposit` again.
7. Bridge calls `safe_mint` again → mints another `amount` to `bridge_id`, transfers to user.
8. UTXO is now marked verified.

**Result:** 2× `amount` nBTC minted for 1× BTC deposit. The extra `amount` in `bridge_id` is unbacked supply.

**Scenario B — Bridge callback does not revert on `U128(0)` return:**
1. Same steps 1–4 above, but the bridge marks the UTXO as verified.
2. User's BTC is permanently locked in the bridge's Bitcoin address.
3. User receives 0 nBTC.
4. `amount` nBTC is stranded in `bridge_id`.

**Result:** Permanent loss of user's BTC deposit; nBTC supply inflated by `amount`.

In both scenarios, the nBTC total supply exceeds the BTC actually backing it, breaking the 1:1 peg invariant.

---

### Impact Explanation

- **Scenario A:** Unauthorized double-minting of nBTC — `amount` extra nBTC in `bridge_id` is not backed by BTC. These tokens sit in the bridge's own balance and can be used in future `burn` calls (during withdrawal finalization), effectively allowing BTC to be released without a corresponding user-held nBTC burn. This is unauthorized release of bridge-controlled BTC funds.
- **Scenario B:** Permanent loss of user's BTC deposit — the BTC is locked in the bridge's Bitcoin address with no nBTC issued to the user and no recovery path (UTXO marked verified, refund blocked).

Both scenarios match: **Critical — Unauthorized minting of nBTC / Significant loss or permanent locking of user funds.**

---

### Likelihood Explanation

The `safe_deposit` flow is the standard path for Omni Bridge integration. Any user whose NEAR account is not yet registered in the nBTC contract — a routine condition for new users — will trigger this bug when a relayer submits their deposit proof. No malicious intent is required; the condition arises naturally. The relayer is trusted but acts on any valid BTC deposit proof, making this reachable through normal bridge usage.

---

### Recommendation

Move the account registration check **before** the `internal_deposit` call, or register the account automatically before minting:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer to account_id
}
```

Alternatively, auto-register the account before minting (consistent with how `mint_inner` works), so that `safe_mint` never silently discards minted tokens.
