### Title
Any NEAR account can front-run and permanently block a user's `request_refund`, locking their BTC refund for up to 14 days — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund` entrypoint is fully permissionless and performs no caller-identity check. Any NEAR account that knows a victim's `deposit_msg` (publicly emitted on-chain) and holds 2 NEAR can front-run the victim's own refund submission. Once stored, the duplicate-request guard prevents the victim from filing their own request. Only DAO/Operator can remove the attacker's entry during the timelock window. When `deposit_msg.refund_address` is `None`, the attacker also supplies their own BTC address, creating a path to redirect the victim's BTC after the 14-day `unsafe_refund_timelock_sec` expires.

---

### Finding Description

**Root cause — no caller identity check in `request_refund`**

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` is decorated `#[payable]` and `#[pause(…)]` but carries no ownership guard. The only privileged check is for the optional `gas_fee` parameter: [1](#0-0) 

Any NEAR account that attaches ≥ 2 NEAR and supplies a valid Merkle proof can call this function for any UTXO, regardless of who the intended recipient is.

**Duplicate-request guard permanently blocks the victim**

Inside `request_refund_callback`, after the light-client proof succeeds, the contract inserts the request and guards against duplicates: [2](#0-1) 

Once the attacker's entry is stored, the victim's subsequent `request_refund` call reverts with `"Refund request already exists for this UTXO"`. There is no mechanism for the victim to override or supersede the attacker's entry.

**Rejection is gated to DAO/Operator**

`reject_refund` allows permissionless rejection only when the UTXO has already been finalized via `verify_deposit`. While the refund request is pending (i.e., the deposit has not yet been processed), only DAO or Operator can remove it: [3](#0-2) 

The victim has no self-service path to cancel the attacker's entry.

**Timelock durations**

The default timelocks are: [4](#0-3) 

- `refund_timelock_sec` = 2 days (pre-authorized `refund_address` in `deposit_msg`)
- `unsafe_refund_timelock_sec` = 14 days (caller-supplied `refund_address`, i.e., `deposit_msg.refund_address = None`)

**Attacker-controlled `refund_address` when `deposit_msg.refund_address = None`**

When the victim's `deposit_msg` carries no pre-authorized `refund_address`, the check in `internal_request_refund` is skipped entirely: [5](#0-4) 

The attacker freely supplies their own BTC address. After 14 days, `execute_refund` (also permissionless) can be called by anyone — including the attacker — to initiate an MPC-signed transaction paying the victim's UTXO to the attacker's address.

**`request_refund` cost** [6](#0-5) 

The required deposit is 2 NEAR (≈ $4–10). This is the entire cost of locking a victim's refund for up to 14 days.

**`deposit_msg` is public**

`get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`: [7](#0-6) 

An attacker can reconstruct the exact `deposit_msg` from on-chain events and the visible BTC transaction, then immediately submit `request_refund` before the victim does.

---

### Impact Explanation

**Primary — attacker-triggered temporary locking of the refund path (Medium)**

The victim's `request_refund` is permanently blocked until DAO/Operator intervenes. The victim cannot self-service their way out. This matches: *"attacker-triggered temporary locking of bridged funds"* and *"stuck bridge state requiring operator intervention."*

**Secondary — potential BTC theft when `deposit_msg.refund_address = None`**

If the relayer fails to process the deposit within 14 days and DAO/Operator does not reject the attacker's request, the attacker calls `execute_refund` after the timelock, triggering an MPC-signed BTC transaction to their own address. The victim's BTC is permanently redirected. This matches: *"theft … of underlying BTC."*

---

### Likelihood Explanation

- **Cost**: 2 NEAR — low barrier for any motivated attacker targeting a large BTC deposit.
- **Information availability**: `deposit_msg` is emitted publicly; the BTC transaction is visible on-chain. No privileged knowledge is required.
- **Timing**: The attacker only needs to submit before the victim. A mempool-watching bot can do this reliably.
- **Operator dependency**: The 14-day window is long; DAO/Operator monitoring is not guaranteed to be real-time.
- **Theft precondition**: Requires the relayer to be offline for 14 days — unlikely in normal operation, but possible during incidents, upgrades, or targeted disruption.

---

### Recommendation

1. **Require caller to be the intended recipient**: In `request_refund`, assert `env::predecessor_account_id() == deposit_msg.recipient_id` (or a DAO/Operator role). This prevents any third party from filing a refund on behalf of a user.

2. **Allow the recipient to override a pending request**: If a caller proves they are `deposit_msg.recipient_id`, permit them to replace an existing refund request (resetting the timelock).

3. **Allow the recipient to self-reject**: Extend `reject_refund` to permit rejection by `deposit_msg.recipient_id`, not only by DAO/Operator.

---

### Proof of Concept

```
1. Alice calls get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })
   → Bridge emits LogDepositAddress event with full deposit_msg

2. Alice sends 1 BTC to the deposit address on Bitcoin.

3. Attacker observes the LogDepditAddress event and the BTC transaction on-chain.

4. Attacker calls request_refund(
       deposit_msg = alice's deposit_msg,
       refund_address = "attacker_btc_address",
       tx_bytes = alice's BTC tx,
       vout = 0,
       proof = valid Merkle proof,
       gas_fee = None
   ) with 2 NEAR attached.
   → request_refund_callback stores RefundRequest { refund_address: "attacker_btc_address", ... }

5. Alice calls request_refund(..., refund_address = "alice_btc_address", ...)
   → PANICS: "Refund request already exists for this UTXO"

6. Alice cannot refund. Only DAO/Operator can call reject_refund.

7. If the relayer does not call verify_deposit within 14 days AND DAO/Operator does not reject:
   Attacker calls execute_refund(utxo_storage_key) with 1 NEAR attached.
   → Bridge builds MPC-signed BTC tx paying 1 BTC to "attacker_btc_address".
   → Alice's BTC is stolen.
```

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,

            deposit_msg,
            refund_address,

            vout,

        )
    }

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
