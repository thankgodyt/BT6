### Title
Push-Payment ETH Delivery in `finTransfer` Permanently Freezes Bridged Funds When Recipient Reverts — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

`OmniBridge.finTransfer` delivers native ETH to the recipient via a direct push-call. The recipient address is cryptographically bound inside the MPC-signed payload and cannot be changed after signing. If the recipient is a contract that reverts on receiving ETH, every attempt to finalize the transfer will revert, while the corresponding tokens on NEAR have already been burned or locked. There is no pull-payment fallback and no admin rescue path, so the bridged funds are permanently frozen.

---

### Finding Description

In `finTransfer`, when `payload.tokenAddress == address(0)` (native ETH), the contract pushes ETH directly to the recipient:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
``` [1](#0-0) 

The nonce is marked used on line 287 before the transfer, but because `revert FailedToSendEther()` rolls back the entire transaction, the nonce is never durably consumed. [2](#0-1) 

The recipient address is embedded in the Borsh-encoded payload that the NEAR MPC network signs:

```solidity
Borsh.encodeAddress(payload.recipient),
``` [3](#0-2) 

The signature is verified against `nearBridgeDerivedAddress`, so no field in the payload — including `recipient` — can be altered without invalidating the signature. [4](#0-3) 

On the NEAR side, `init_transfer_internal` burns deployed tokens (or locks native tokens) and emits `InitTransferEvent` before any EVM interaction occurs: [5](#0-4) 

Once that NEAR transaction is final, the tokens are gone from the user's balance. There is no mechanism in the NEAR contract to un-burn or un-lock them if the EVM leg fails permanently.

The same root cause applies to the ERC-1155 path (`safeTransferFrom` calls `onERC1155Received` on the recipient, which can revert) and to ERC-20 tokens with transfer blacklists such as USDC (`safeTransfer` reverts for blacklisted addresses): [6](#0-5) 

No admin rescue function exists in `OmniBridge.sol`. The only theoretical recovery path is a full UUPS contract upgrade, which is an out-of-band emergency measure, not a protocol-level safeguard. [7](#0-6) 

---

### Impact Explanation

A user whose NEAR → EVM transfer targets a contract recipient that cannot accept ETH (no `receive()`, or a reverting `receive()`) will have their NEAR-side tokens permanently burned with zero recourse. The ETH is never delivered, the nonce is never consumed, and no alternative delivery path exists. The same outcome occurs when the EVM recipient is blacklisted on a token such as USDC after the NEAR-side burn has already been committed. This constitutes **permanent freezing of bridged funds**, which is within the Critical impact scope.

---

### Likelihood Explanation

The scenario is realistic under two independent conditions:

1. **Contract recipient without ETH acceptance** — Users routinely bridge to multisig wallets, DeFi vaults, or other contracts. Many such contracts lack a `receive()` function. A user who specifies such an address as the EVM recipient will permanently lose their NEAR tokens.

2. **ERC-20 blacklist race** — For USDC or similar tokens, Circle can blacklist an address between the moment the NEAR-side burn is committed and the moment the relayer calls `finTransfer` on EVM. This is an externally triggerable condition that permanently freezes the transfer.

Both conditions are reachable by any bridge user without any privileged access.

---

### Recommendation

Replace the push-payment pattern with a pull-payment (claimable balance) pattern for ETH delivery:

```solidity
// Instead of pushing ETH:
pendingWithdrawals[payload.recipient] += payload.amount;
// Emit event so recipient knows to call claim()

function claimETH() external {
    uint256 amount = pendingWithdrawals[msg.sender];
    pendingWithdrawals[msg.sender] = 0;
    (bool ok,) = msg.sender.call{value: amount}("");
    require(ok, "FailedToSendEther");
}
```

For ERC-20 tokens with blacklists, consider a similar claimable-balance mapping so that a blacklisted recipient does not permanently block finalization. Additionally, consider an admin-accessible rescue path that can redirect a stuck transfer to an alternative address after a timeout, analogous to the NEAR contract's existing `migrate_deployed_token` pattern. [8](#0-7) 

---

### Proof of Concept

**Setup:** Deploy a malicious contract `NoReceive` on an EVM testnet:

```solidity
contract NoReceive {
    // No receive() or fallback() — ETH transfers revert
}
```

**Attack flow:**

1. On NEAR, call `ft_on_transfer` (or equivalent) to initiate a transfer of wrapped ETH to `NoReceive`'s address. The NEAR bridge burns the wrapped ETH and emits `InitTransferEvent`. [5](#0-4) 

2. The relayer calls `sign_transfer` on NEAR. The MPC network signs a `TransferMessagePayload` with `recipient = address(NoReceive)` and `tokenAddress = address(0)`. [9](#0-8) 

3. The relayer calls `OmniBridge.finTransfer(signature, payload)` on EVM with `msg.value = payload.amount`.

4. Execution reaches line 319. `NoReceive` has no `receive()`, so the low-level call returns `success = false`. The function reverts with `FailedToSendEther`. [10](#0-9) 

5. The nonce is not durably consumed (transaction reverted). Every subsequent retry produces the same revert.

6. The user's NEAR-side wrapped ETH is permanently burned. The ETH remains with the relayer (returned on revert). The user has no recovery path.
