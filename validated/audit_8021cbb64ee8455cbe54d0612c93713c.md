### Title
Unnormalized `PerasVoteStake` Compared Against Relative Quorum Threshold in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` accumulates raw (absolute) ledger-stake values in `ptvtTotalStake` and compares them directly against a relative (normalized) quorum threshold from `PerasParams`, without any unit conversion. This is the exact same vulnerability class as the reference report: a cumulative tracking variable is updated with the wrong denomination, making every downstream threshold check incorrect. Because absolute ledger stakes (e.g., lovelace) are orders of magnitude larger than a relative threshold (e.g., `0.75`), quorum is trivially satisfied by a single inbound vote from any unprivileged peer, bypassing the Peras certificate-forging quorum requirement entirely.

---

### Finding Description

`stakeAboveThreshold` in `SupportsPeras.hs` performs a direct numeric comparison:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [1](#0-0) 

The function's own TODO comment explicitly documents the unit mismatch:

> "this function only makes sense when both values are relative (normalized) values, **so we should either normalize the `PerasVoteStake` before calling this function**, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` fed into this comparison is accumulated in `updateTargetVoteTally` by summing individual `vpvVoteStake` values:

```haskell
ptvtTotalStake = ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote)
``` [3](#0-2) 

Each `vpvVoteStake` is assigned during `validatePerasVote` by a direct lookup from `PerasVoteStakeDistr`, which is populated from the ledger's absolute stake distribution — **no normalization step exists anywhere in this path**:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [4](#0-3) 

The quorum threshold in `PerasParams` is a relative value (`Rational` in `[0,1]`), while the accumulated `ptvtTotalStake` is a sum of absolute ledger stakes (lovelace-scale integers). The comparison is therefore between incommensurable units.

`stakeAboveThreshold` is called in two critical production paths:

1. **`votesReachQuorum`** → **`updateCandidateVoteState`**: decides whether a block target has reached quorum and a certificate should be forged. [5](#0-4) 

2. **`updateLoserVoteState`**: decides whether a losing target has gone above quorum (an error condition that triggers `RoundVoteStateLoserAboveQuorum`). [6](#0-5) 

---

### Impact Explanation

Because absolute ledger stakes (e.g., millions of lovelace) are compared against a relative threshold (e.g., `0.75`), the condition `stake >= quorumThreshold + safetyMargin` is trivially `True` for any single voter. Consequently:

- **A single inbound vote from any unprivileged peer causes `votesReachQuorum` to return `Just`**, triggering `forgePerasCert` and producing a `ValidatedPerasCert` without the required quorum of stake-weighted votes.
- The Peras certificate-forging quorum check — the core security invariant of the Peras protocol — is completely bypassed.
- Every `updateLoserVoteState` call also immediately returns `Left` (loser-above-quorum error), corrupting the round vote state machine for all subsequent votes in that round.

This matches the **Critical** allowed impact: bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.

---

### Likelihood Explanation

The entry path is fully reachable by any unprivileged peer. `processVotes` in `PerasVote.hs` accepts votes from the network, validates them via `validatePerasVote`, and immediately feeds them into the aggregation pipeline:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [7](#0-6) 

No special privilege, key material, or stake majority is required. Any peer that can send a single valid `PerasVote` (i.e., one whose `PerasVoterId` appears in the current epoch's `PerasVoteStakeDistr`) triggers the incorrect quorum check.

---

### Recommendation

Normalize `PerasVoteStake` to a relative value (fraction of total committee stake) **before** it is stored in `ValidatedPerasVote.vpvVoteStake`. The normalization must happen at the point where the absolute ledger stake is looked up from `PerasVoteStakeDistr` — i.e., inside `validatePerasVote` — by dividing the voter's absolute stake by the total stake of the committee. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, as the TODO comment suggests.

---

### Proof of Concept

Given:
- `PerasParams` with `perasQuorumStakeThreshold = 0.75` (relative)
- A `PerasVoteStakeDistr` containing voter `V` with absolute ledger stake `1_000_000` lovelace (1 ADA)
- Peer sends one vote from voter `V`

Execution path:
1. `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake 1_000_000`
2. `updateTargetVoteTally` sets `ptvtTotalStake = PerasVoteStake 1_000_000`
3. `votesReachQuorum` calls `stakeAboveThreshold params (PerasVoteStake 1_000_000)`
4. Check: `1_000_000 >= 0.75 + safetyMargin` → **True**
5. `forgePerasCert` is called → certificate forged with one vote

The quorum requirement (intended to require a supermajority of committee stake) is bypassed by a single vote. [1](#0-0) [8](#0-7)
