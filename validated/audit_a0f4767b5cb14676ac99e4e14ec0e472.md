### Title
Hardcoded `GAS_FOR_SIGN_CALL` for Chain Signatures call can permanently block all withdrawals and refunds if the MPC contract increases its minimum gas requirement - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
The bridge hardcodes `GAS_FOR_SIGN_CALL = Gas::from_tgas(50)` as the gas forwarded to the external NEAR Chain Signatures (MPC) contract on every signing request. The chain signatures contract validates that the prepaid gas meets its own minimum requirement. If the MPC contract is upgraded to require more than 50 Tgas, every call to `sign_btc_transaction` — which is the only path to complete a withdrawal or refund — will fail, permanently blocking all in-flight and future withdrawals and refunds until the bridge contract itself is upgraded.

### Finding Description
In `contracts/satoshi-bridge/src/chain_signature.rs`, the gas forwarded to the chain signatures contract is a compile-time constant:

```rust
pub const GAS_FOR_SIGN_CALL: Gas = Gas::from_tgas(50);
```

This constant is used unconditionally in `sign_promise()`:

```rust
ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
    .with_static_gas(GAS_FOR_SIGN_CALL)   // always 50 Tgas, never configurable
    .with_attached_deposit(env::attached_deposit())
    .sign(request)
```

`sign_promise()` is called from `internal_sign_btc_transaction()`, which is the sole implementation path for `sign_btc_transaction` (the public entry point for both the withdrawal flow and the refund flow).

The mock chain signatures contract in this repository already demonstrates the validation pattern the real contract enforces:

```rust
assert!(
    env::prepaid_gas() >= GAS_FOR_SIGN_CALL,
    "Insufficient gas provided. Provided: {} Required: {}",
    env::prepaid_gas(),
    GAS_FOR_SIGN_CALL
);
```

The real NEAR chain signatures contract is an independently deployed, upgradeable contract managed by the NEAR MPC team. Its minimum gas requirement is a configurable parameter of that external system. Unlike every other bridge parameter (fees, limits, timeouts, account IDs — all in `Config` / `ConfigUpdate`), the gas forwarded to the MPC contract is not configurable and cannot be updated without redeploying the bridge contract.

### Impact Explanation
If the chain signatures contract is upgraded to require more than 50 Tgas:

1. **All withdrawals are blocked.** In the withdrawal flow, nBTC tokens are transferred to the bridge in step 1 (`ft_transfer_call`). The bridge holds them until `verify_withdraw` burns them after BTC confirmation. If `sign_btc_transaction` fails for every pending withdrawal, those nBTC tokens are stuck in the bridge balance indefinitely — a stuck bridge state requiring operator intervention (contract upgrade).

2. **All refunds are blocked.** The refund flow also calls `sign_btc_transaction` to sign the refund PSBT. If signing fails, users who deposited BTC and requested a refund cannot recover their BTC.

3. **No user-side workaround exists.** The gas constant is baked into the compiled WASM. No config update, no admin call, and no user action can change it without a full contract redeployment.

### Likelihood Explanation
The NEAR chain signatures contract is actively developed and has already gone through multiple versions. The MPC team can upgrade it at any time. The current 50 Tgas allocation was chosen to match the current contract's requirements, but there is no on-chain enforcement or monitoring that would alert the bridge team if the requirement changes. The scenario is directly analogous to the GMX `MAX_CALLBACK_GAS_LIMIT` issue: a configurable external limit that the bridge assumes will never change.

### Recommendation
Move the gas allocation for the chain signatures call into the bridge's `Config` struct, alongside the other external-dependency parameters:

```rust
// In Config:
pub chain_signatures_sign_gas: Gas,

// In sign_promise():
ext_chain_signatures::ext(config.chain_signatures_account_id.clone())
    .with_static_gas(config.chain_signatures_sign_gas)
    .with_attached_deposit(env::attached_deposit())
    .sign(request)
```

Add it to `ConfigUpdate` so the DAO can adjust it via `update_config` without a contract redeployment, matching the pattern already used for every other external-facing parameter.

### Proof of Concept
1. Chain signatures contract is upgraded; its `sign()` now requires ≥ 100 Tgas.
2. User initiates a withdrawal: calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg)`. Bridge receives tokens and creates a `BTCPendingInfo`. Tokens are now in the bridge balance.
3. Anyone calls `bridge.sign_btc_transaction(btc_pending_sign_id, 0, 0)`.
4. Bridge calls `chain_signatures.sign(request)` with `.with_static_gas(Gas::from_tgas(50))`.
5. Chain signatures contract asserts `prepaid_gas >= 100 Tgas` → assertion fails → promise fails.
6. `sign_btc_transaction_callback` receives a failed promise result → returns `false`, no signature stored.
7. The `BTCPendingInfo` remains in `PendingSign` state forever. The nBTC tokens remain locked in the bridge. No withdrawal can complete. No refund can be signed. The bridge is stuck until a contract upgrade changes the hardcoded constant.
