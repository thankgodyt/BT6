Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Yield-Resume Path in `init_transfer_resume` — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function enforces the `NativeFeeRestricted` role check to block flagged accounts from registering transfers with a non-zero `native_token_fee`. This check is entirely absent in `init_transfer_resume`, the yield-resume callback. A restricted account can route around the restriction by triggering the yield path (insufficient storage at call time) and then depositing NEAR to the deterministic message-storage account, causing `init_transfer_resume` to proceed without any role check and call `init_transfer_internal` with the non-zero native fee intact.

## Finding Description
In `init_transfer` the direct-execution branch is guarded by a two-part condition:

```rust
if self.try_to_transfer_balance_from_message_account(...).is_ok()
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

When a `NativeFeeRestricted` account submits `native_token_fee > 0` and the message-storage account has no pre-existing balance:
- Branch 1 (`try_to_transfer_balance_from_message_account`) returns `StorageError::MessageAccountNotRegistered` → fails.
- Branch 2 evaluates to `false` because `native_token_fee > 0` AND the account holds `NativeFeeRestricted`.

Both branches fail, so execution falls into the `else` block at line 586, which calls `env::promise_yield_create("init_transfer_resume", ...)` and registers a pending yield keyed to the deterministic `message_storage_account_id`.

`init_transfer_resume` (lines 621–646) contains no role check whatsoever:

```rust
pub fn init_transfer_resume(...) -> U128 {
    self.remove_promise(&message_storage_account_id);
    if let Err(err) = self.try_to_transfer_balance_from_message_account(
        &message_storage_account_id,
        NearToken::from_yoctonear(transfer_message.fee.native_fee.0),
        &storage_owner,
        self.required_balance_for_init_transfer_message(transfer_message.clone()),
    ) { ... return transfer_message.amount; }
    self.init_transfer_internal(transfer_message, storage_owner)
}
```

Once the attacker calls `storage_deposit` for the message account with sufficient NEAR (covering storage + native fee), `try_to_transfer_balance_from_message_account` succeeds and `init_transfer_internal` is called with the original `TransferMessage` — which carries the non-zero `native_fee` — bypassing the restriction entirely.

The `message_storage_account_id` is deterministically derived from the transfer parameters via `TransferMessage::calculate_storage_account_id`, so the attacker can compute it off-chain before making the `storage_deposit` call.

## Impact Explanation
This is a concrete **role bypass**: the sole mechanism preventing `NativeFeeRestricted` accounts from setting native fees is rendered ineffective via the yield path. The attacker registers an outbound transfer with an arbitrary non-zero `native_fee`. Upon `sign_transfer` / `claim_fee`, `send_fee_internal` (line 2656) pays that native fee to the relayer from the attacker's deposited NEAR. The `NativeFeeRestricted` administrative control — the only guard against flagged accounts using native fees — is fully circumvented through standard, permissionless bridge calls. This matches the allowed critical impact: **authorization bypass / role bypass that lets an attacker execute bridge actions they are explicitly prohibited from performing**.

## Likelihood Explanation
The attacker must already hold the `NativeFeeRestricted` role (i.e., have been explicitly flagged by the DAO). Once flagged, the bypass requires only two standard, permissionless on-chain calls: `ft_transfer_call` (to enter the yield path) and `storage_deposit` (to fund the message account and fire the resume). No special privileges, leaked keys, or off-chain coordination beyond what the attacker already controls are needed. The `message_storage_account_id` is fully deterministic and computable before submitting either call. The attack is repeatable for every transfer the restricted account wishes to initiate.

## Recommendation
Re-apply the `NativeFeeRestricted` role check at the top of `init_transfer_resume`, mirroring the guard in `init_transfer`. If `storage_owner` holds `NativeFeeRestricted` and `transfer_message.fee.native_fee.0 > 0`, the resume should reject the transfer and return `transfer_message.amount` as a refund, consistent with how other invalid-state resumes are handled (e.g., the timeout/error branch at line 641–643). The check should be placed before `try_to_transfer_balance_from_message_account` is called so that no state mutation occurs for restricted accounts.

## Proof of Concept
1. DAO calls `acl_grant_role("NativeFeeRestricted", attacker)` on the bridge contract.
2. Attacker calls `ft_transfer_call` on a registered token with `msg` containing `native_token_fee > 0`. Inside `ft_on_transfer → init_transfer`, both direct-path branches fail; the yield path fires and a pending promise is registered against the deterministic `message_storage_account_id`.
3. Attacker computes `message_storage_account_id` off-chain (same derivation as `TransferMessage::calculate_storage_account_id`) and calls `storage_deposit` on the bridge contract for that account ID, depositing `required_balance_for_init_transfer + native_token_fee` yoctoNEAR.
4. The yield fires: `init_transfer_resume` is invoked. `try_to_transfer_balance_from_message_account` succeeds (message account now has sufficient balance). No role check is performed. `init_transfer_internal` is called with the original `TransferMessage` carrying the non-zero `native_fee`. An `InitTransferEvent` is emitted.
5. A relayer calls `sign_transfer` for the resulting `TransferId`, then `claim_fee` with a proof from the destination chain. `send_fee_internal` pays `native_fee` yoctoNEAR to the relayer — the `NativeFeeRestricted` restriction is fully bypassed.

A sandbox integration test can be structured analogously to the existing `test_native_fee_restriction` test in `near/omni-tests/src/native_fee_role.rs`, adding a step that omits the `storage_deposit` to the sender's own account (forcing the yield path) and instead deposits to the virtual message account, then awaiting the `ft_transfer_call` result and asserting that an `InitTransferEvent` with non-zero `native_fee` is emitted despite the role being active.
