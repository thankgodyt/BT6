### Title
Unconditional Peras Certificate Acceptance Allows Unprivileged Peer to Manipulate Chain Selection Weight - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or semantic validation. This stub is wired directly into the live inbound-certificate processing path (`makePerasCertPoolWriterFromChainDB`) that accepts certificates from untrusted peers. Any peer can therefore inject an arbitrary `PerasCert` with a crafted `pcCertBoostedBlock` pointing to an adversarial block, causing the receiving node to add a chain-selection weight boost of `perasWeight = 15` to that block, potentially making the node prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub wired into production:**

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the mandatory gate before any certificate is stored or acted upon. The only concrete instance in the codebase is the catch-all `instance StandardHash blk => BlockSupportsPeras blk`, which implements the method as:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No field of `cert` is inspected. No signature is verified. No round-number bounds are checked. No boosted-block existence is confirmed. Every certificate, regardless of content, is wrapped in `ValidatedPerasCert` and returned as `Right`.

**Attacker-controlled entry path — inbound peer certificate diffusion:**

`makePerasCertPoolWriterFromChainDB` constructs the production `ObjectPoolWriter` that receives certificates from remote peers. It passes `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` applies the validator to every certificate not already in the database. Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is immediately forwarded to `ChainDB.addPerasCertAsync`: [3](#0-2) 

The `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params`. With `mkPerasParams`, this is `PerasWeight 15`: [4](#0-3) 

This boost is applied to chain selection for the block identified by `pcCertBoostedBlock` in the certificate. A peer can set `pcCertBoostedBlock` to any block hash, including one on an adversarial fork.

**Analogy to the external report:**

The external report describes `MagnetarV2._permit()` checking only the first ABI parameter (msg.sender) while ignoring the function selector, allowing an attacker to craft calldata that passes the partial check but executes an unintended function. Here, `processCerts` calls `validatePerasCert` which is supposed to check the certificate's cryptographic validity and semantic correctness, but instead checks nothing at all — the structural parallel is exact: a validation gate that performs only a subset (zero) of the required checks.

---

### Impact Explanation

**High — Chain selection manipulation by an unprivileged peer.**

A malicious peer sends a `PerasCert` with `pcCertBoostedBlock` set to the tip of an adversarial fork. The receiving node accepts it unconditionally, stores it in `PerasCertDB`, and triggers `ChainDB.addPerasCertAsync`. Chain selection then adds `PerasWeight 15` to the adversarial block's chain weight. If the adversarial chain is otherwise close in weight to the honest chain, this injected boost can cause the node to switch to the adversarial fork, violating the chain-selection invariant that only legitimately quorum-certified blocks receive a Peras boost.

This falls squarely within the allowed impact scope: *"Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

**High.** The attack requires only a network connection to the target node and the ability to send a well-formed `PerasCert` CBOR message over the Peras certificate object-diffusion mini-protocol. No keys, stake, or privileged access are needed. The `PerasCert` type is simple — it contains only a `PerasRoundNo` and a `Point blk` (block hash + slot): [5](#0-4) 

Any peer that can connect to the node's object-diffusion endpoint can craft and send such a message. The only existing guard is the deduplication check on `pcCertRound` (one cert per round number), but an attacker can use any unused round number.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before the Peras certificate diffusion path is enabled in production. At minimum, the validation must:

1. Verify the aggregate BLS signature in the certificate against the claimed voter set and the `(electionId, candidate)` pair, using the committee's public keys.
2. Confirm that the `pcCertBoostedBlock` exists in the node's known chain or is a plausible recent block (within the stability window).
3. Confirm that `pcCertRound` falls within the valid range relative to the current slot.
4. Confirm that the voter set meets the quorum threshold.

Until real validation is implemented, the inbound certificate diffusion path (`makePerasCertPoolWriterFromChainDB` / `makePerasCertPoolWriterFromCertDB`) must not be exposed to untrusted peers.

---

### Proof of Concept

**Attacker-controlled input sequence (no privileges required):**

1. Attacker connects to the target node's Peras certificate object-diffusion endpoint.
2. Attacker identifies an adversarial block `B_adv` on a fork that is 14 weight units behind the honest tip.
3. Attacker sends a single `PerasCert` message:
   ```
   PerasCert { pcCertRound = <any unused round number>
             , pcCertBoostedBlock = <Point of B_adv> }
   ```
   encoded as CBOR per the `Serialise (PerasCert blk)` instance.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })` unconditionally.
5. The cert is stored in `PerasCertDB` and forwarded to `ChainDB.addPerasCertAsync`.
6. Chain selection adds weight 15 to `B_adv`'s chain, making it heavier than the honest chain by 1 unit.
7. The node switches to the adversarial fork.

**Expected outcome without the bug:** Step 4 should fail with a `PerasValidationErr` because the certificate carries no valid aggregate signature from a quorum of committee members.

**Actual outcome:** Step 4 always succeeds; the adversarial certificate is accepted and stored. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
