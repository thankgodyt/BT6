Audit Report

## Title
ERC-1155 `safeTransferFrom` Recipient Hook Revert Causes Permanent Freezing of Bridged Funds — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

In `finTransfer`, the `completedTransfers` nonce is written at line 287 before the ERC-1155 token transfer at lines 323–330. Because `IERC1155.safeTransferFrom` unconditionally invokes `onERC1155Received` on any contract recipient, a revert inside that hook rolls back the entire transaction — including the nonce write. The nonce is never consumed, and since the MPC signature is bound to the exact `(destinationNonce, recipient, amount, token)` tuple, every subsequent relay attempt reverts identically. Tokens already burned or locked on NEAR are permanently unrecoverable.

## Finding Description

`finTransfer` follows the checks-effects-interactions pattern: it marks the nonce used at line 287, verifies the MPC signature, then dispatches the token. [1](#0-0) 

For the ERC-1155 branch, the dispatch is: [2](#0-1) 

The ERC-1155 standard mandates that `safeTransferFrom` calls `onERC1155Received` on any contract `to` address. If that call reverts, the EVM unwinds all state changes in the transaction, including the `completedTransfers[payload.destinationNonce] = true` write. The nonce is reset to `false`.

The MPC signature encodes the full `TransferMessagePayload` — including `destinationNonce`, `recipient`, `tokenAddress`, and `amount` — via Borsh serialization: [3](#0-2) 

No alternative payload can be signed for the same origin transfer. Every relay attempt with the same signed payload will reach `safeTransferFrom`, trigger the hook, revert, and leave the nonce unconsumed. There is no admin escape hatch, timeout, or re-routing function in `OmniBridge.sol` to force-complete or redirect the transfer.

On the NEAR side, `init_transfer_internal` burns or locks tokens before emitting `InitTransferEvent`, with no cancellation or refund path: [4](#0-3) 

The `evm/SECURITY.md` known-issues list does not acknowledge this scenario, and `evm/CLAUDE.md` explicitly requires state-before-external-calls as the reentrancy defense without noting that a reverting external call also undoes that state write: [5](#0-4) 

## Impact Explanation

Any user who initiates a NEAR→EVM ERC-1155 transfer to a contract recipient that does not implement `IERC1155Receiver` (or that deliberately reverts in `onERC1155Received`) permanently loses their bridged funds. The tokens are burned or locked on NEAR at `init_transfer` time and can never be recovered because `finTransfer` on EVM will always revert. This is a concrete, irreversible loss of user funds matching the allowed critical impact: **permanent freezing of bridged funds across NEAR and EVM**.

## Likelihood Explanation

ERC-1155 transfers are explicitly supported via `logMetadata1155` / `initTransfer1155` / `finTransfer`. Numerous legitimate contract recipients — multisig wallets (Gnosis Safe without ERC-1155 module), DAO treasuries, DeFi vaults — do not implement `IERC1155Receiver`. A user bridging to any such address, even accidentally, permanently loses funds. No special privilege is required; any bridge user initiating an ERC-1155 transfer to a contract address is exposed. A malicious actor can also deploy a contract that deliberately reverts in `onERC1155Received` and grief any sender who targets that address.

## Recommendation

Replace the push-to-recipient pattern with a pull (claim) pattern for ERC-1155 deliveries:

1. In `finTransfer`, when the token is ERC-1155, store the pending claim in a mapping (e.g., `pendingClaims[recipient][tokenAddress][tokenId] += amount`) instead of calling `safeTransferFrom` immediately. The nonce is consumed and the bridge state is finalized regardless of whether the recipient can accept the token.
2. Expose a separate `claimERC1155(address token, uint256 tokenId)` function that the recipient calls to pull their tokens. The recipient's own call context handles any hook reversion without affecting the bridge's finalization state.

Alternatively, use a low-level call pattern that catches the revert and stores unclaimed tokens for later retrieval, ensuring the nonce is always consumed on the first valid relay.

## Proof of Concept

1. Deploy `BadRecipient` on EVM — a contract with no `onERC1155Received` implementation (or one that explicitly reverts).
2. On NEAR, call `ft_transfer_call` to the bridge with an `InitTransferMsg` specifying an ERC-1155 token and `recipient = BadRecipient_address`. The bridge burns/locks the tokens and emits `InitTransferEvent`.
3. The MPC signs a `TransferMessagePayload` with `recipient = BadRecipient_address`.
4. A relayer calls `finTransfer(signature, payload)` on `OmniBridge.sol`.
5. Execution reaches line 324: `IERC1155(...).safeTransferFrom(address(this), BadRecipient_address, ...)`.
6. `safeTransferFrom` calls `BadRecipient.onERC1155Received(...)`, which reverts (either via missing implementation or explicit revert).
7. The entire transaction reverts. `completedTransfers[nonce]` is reset to `false`.
8. Every subsequent `finTransfer` attempt with the same signed payload repeats steps 5–7.
9. The user's tokens on NEAR are permanently burned/locked with no recovery path.

A local Hardhat/Foundry test can reproduce this by deploying a mock ERC-1155 token, a `BadRecipient` contract, and calling `finTransfer` with a crafted payload signed by a test key set as `nearBridgeDerivedAddress`, confirming the transaction reverts and `completedTransfers[nonce]` remains `false` after each attempt.
