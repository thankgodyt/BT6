### Title
`safe_mint` Calls `ft_transfer`/`ft_transfer_call` That Require 1 yoctoNEAR But `safe_mint` Is Not `#[payable]`, Permanently Breaking the Safe-Deposit Flow for Registered Accounts - (File: contracts/nbtc/src/lib.rs)

---

### Summary

`safe_mint` in the nBTC token contract is not marked `#[payable]`, meaning the NEAR runtime enforces that it is called with **zero** attached deposit. However, both execution branches for a registered account internally call `ft_transfer` or `ft_transfer_call`, which delegate to `near_contract_standards::FungibleToken::ft_transfer[_call]`. Those standard-library functions unconditionally call `assert_one_yocto()`, requiring exactly 1 yoctoNEAR to be attached. Because the deposit is always 0 when `safe_mint` executes, every call that reaches either branch panics. The safe-deposit path (used by Omni Bridge) is therefore permanently broken for any user whose account is already registered.

---

### Finding Description

`safe_mint` is declared without `#[payable]`:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    ...
    self.token.internal_deposit(&self.bridge_id, amount.into());

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));   // unregistered → safe failure
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)   // ← panics
    } else {
        self.ft_transfer(account_id, amount, None);            // ← panics
        PromiseOrValue::Value(amount)
    }
}
``` [1](#0-0) 

The NEAR SDK automatically inserts a "no deposit allowed" guard for every non-`#[payable]` function, so `env::attached_deposit()` is always `NearToken::from_yoctonear(0)` inside `safe_mint`.

Both `self.ft_transfer(...)` and `self.ft_transfer_call(...)` are internal Rust calls that resolve to the nBTC contract's own `FungibleTokenCore` implementation:

```rust
#[payable]
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    ...
    self.token.ft_transfer(receiver_id, amount, memo);   // calls assert_one_yocto()
}

#[payable]
fn ft_transfer_call(...) -> PromiseOrValue<U128> {
    self.token.ft_transfer_call(receiver_id, amount, memo, msg)  // calls assert_one_yocto()
}
``` [2](#0-1) 

`near_contract_standards::FungibleToken::ft_transfer` and `ft_transfer_call` both call `assert_one_yocto()` as mandated by NEP-141. Because `env::attached_deposit()` is 0 inside `safe_mint`, both calls panic unconditionally for any registered account.

The only path that does **not** panic is the early return for an unregistered account (`return PromiseOrValue::Value(U128(0))`), which signals failure to the bridge. For registered accounts — the success case — `safe_mint` always panics instead of succeeding.

This is structurally identical to the reported pattern: a public entry point (`safe_mint`) delegates to an inner function (`ft_transfer` / `ft_transfer_call`) that carries an authorization/requirement guard (`assert_one_yocto`) that can never be satisfied given the constraints imposed on the outer function (non-`#[payable]`).

---

### Impact Explanation

The `safe_mint` function is the designated integration point for the Omni Bridge safe-deposit flow, as documented in CLAUDE.md:

> **safe_mint (integration):** Checks if account is registered first. If NOT registered → returns `U128(0)` instead of panicking. Used by `safe_verify_deposit` to detect failures. [3](#0-2) 

For any user whose NEAR account is already registered (the normal case for Omni Bridge users), every call to `safe_verify_deposit` / `verify_deposit_v2` with `safe_deposit: Some(..)` will trigger a `safe_mint` call that panics. The bridge callback detects the panic as a mint failure and reverts the deposit. The user's BTC remains on the Bitcoin network but the UTXO may be marked as consumed in bridge state, depending on whether the rollback path correctly un-marks it. At minimum, the entire safe-deposit integration is non-functional for registered accounts. At worst, if the UTXO is not properly reverted, the user's BTC is permanently locked with no nBTC minted.

**Impact class:** Medium (broken callback rollback / stuck bridge state requiring operator intervention) escalating to Critical (permanent loss of user BTC) if the bridge's failure callback does not correctly restore the UTXO to the available set.

---

### Likelihood Explanation

The safe-deposit flow is the primary integration path for Omni Bridge. Omni Bridge users are virtually always registered accounts. Every safe deposit attempted by any registered user triggers this panic. Likelihood is **High** — the broken path is hit on every normal Omni Bridge deposit.

---

### Recommendation

Add `#[payable]` to `safe_mint` so that the bridge can attach exactly 1 yoctoNEAR when calling it, satisfying the `assert_one_yocto()` requirement inside `ft_transfer` and `ft_transfer_call`. Alternatively, replace the internal calls to `self.ft_transfer` / `self.ft_transfer_call` with direct calls to `self.token.internal_transfer` (which does not require an attached deposit), consistent with how `mint_inner` already operates. [4](#0-3) 

Also add unit tests that exercise `safe_mint` with a registered account to confirm tokens are transferred successfully.

---

### Proof of Concept

1. Deploy the nBTC contract and the satoshi-bridge contract.
2. Register a NEAR account `alice.near` in the nBTC token (via `storage_deposit`).
3. Trigger a safe deposit: call `verify_deposit_v2` (or `safe_verify_deposit`) with a valid BTC proof and `deposit_msg.safe_deposit = Some(SafeDepositMsg { receiver_id: "alice.near", ... })`.
4. The bridge cross-contract-calls `nbtc.safe_mint("alice.near", amount, None)` with 0 attached deposit (because `safe_mint` is not `#[payable]`).
5. Inside `safe_mint`, `alice.near` is registered, so execution reaches `self.ft_transfer(alice.near, amount, None)`.
6. `self.ft_transfer` calls `self.token.ft_transfer(...)` from `near_contract_standards`, which calls `assert_one_yocto()`.
7. `env::attached_deposit()` is 0 → panic: `"Requires attached deposit of exactly 1 yoctoNEAR"`.
8. The bridge callback receives a failed promise. The safe deposit is reverted. Alice receives no nBTC despite her BTC being locked on the Bitcoin network. [1](#0-0) [5](#0-4)
