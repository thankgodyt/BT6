Audit Report

## Title
Missing Zero-Address Recipient Validation in `init_transfer` Allows Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` function in the NEAR omni-bridge contract validates only that the recipient chain is not NEAR, but does not check whether the recipient address is a zero address. A user who supplies `eth:0x0000000000000000000000000000000000000000` as the recipient will have their tokens burned or locked on NEAR with no recovery path, because no cancellation mechanism exists and the EVM finalization either permanently burns ETH or permanently locks tokens on NEAR.

## Finding Description
In `near/omni-bridge/src/lib.rs`, `init_transfer` performs only a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

No `is_zero()` guard follows. The method `OmniAddress::is_zero()` already exists in the shared type library and covers all chain variants: [2](#0-1) 

After the chain-kind check passes, the transfer message is stored and the user's tokens are burned/locked on NEAR. The relayer then calls `sign_transfer`, the MPC network signs the payload containing `recipient = address(0)`, and the relayer submits to `finTransfer` on the EVM bridge. [3](#0-2) 

In `finTransfer`, for the native ETH path (`tokenAddress == address(0)`), a low-level call to `address(0)` is made:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
``` [4](#0-3) 

A low-level `.call` to `address(0)` in the EVM **succeeds** and returns `true` — ETH is permanently burned. For ERC20/bridge-token paths, OpenZeppelin's `safeTransfer` and `mint` to `address(0)` revert, causing the entire EVM transaction to revert (including the `completedTransfers` assignment). The nonce is therefore not consumed on the EVM side, but the transfer message remains stored on NEAR with no cancellation function available, permanently locking the tokens. [5](#0-4) 

The same missing validation exists in `finish_withdraw_v2`, which parses the recipient string as `H160` but does not check for the zero value: [6](#0-5) 

## Impact Explanation
- **Native ETH path**: Tokens are burned on NEAR; `finTransfer` sends ETH to `address(0)` successfully — ETH is permanently destroyed. This is permanent loss of bridged funds, matching the Critical impact scope.
- **ERC20/bridge-token path**: `finTransfer` reverts (EVM state fully rolled back), but the NEAR-side transfer message remains stored with no cancellation or refund mechanism, permanently freezing the user's bridged tokens. This is permanent freezing of bridged funds, also matching the Critical impact scope.

## Likelihood Explanation
The entry point (`ft_transfer_call` → `ft_on_transfer` → `init_transfer`) is callable by any unprivileged token holder. No special role or access is required. The `OmniAddress` type parses and accepts a zero EVM address without error. A user can trigger this accidentally (mistyped address) or intentionally. The exploit is repeatable and requires no coordination with any privileged party.

## Recommendation
Add a zero-address guard in `init_transfer` immediately after the chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipientAddress.as_ref()
);
```

Apply the same guard in `finish_withdraw_v2` after parsing the `H160` recipient, and audit any other entry point that accepts a user-supplied recipient address.

## Proof of Concept
1. User holds 1 wETH (NEP-141) on NEAR.
2. User calls `ft_transfer_call` on the wETH token contract with `receiver_id` = omni-bridge and `msg` = `InitTransfer { recipient: "eth:0x0000000000000000000000000000000000000000", fee: 0 }`.
3. `init_transfer` passes the chain-kind check (`Eth != Near`), stores the transfer message, and burns 1 wETH on NEAR.
4. Relayer calls `sign_transfer`; MPC signs the payload with `recipient = address(0)`.
5. Relayer calls `finTransfer` on the EVM bridge with the valid MPC signature.
6. **ETH path**: `address(0).call{value: 1 ether}("")` returns `success = true`; 1 ETH is permanently burned. User's wETH on NEAR is already gone.
7. **ERC20 path**: `safeTransfer(address(0), amount)` reverts; EVM state rolls back; NEAR transfer message remains stored permanently with no cancellation path — tokens are frozen.
