### Title
Missing Access Control on `sign_btc_transaction` Allows Any Caller to Trigger MPC Signing with Arbitrary Parameters - (File: contracts/satoshi-bridge/src/api/chain_signatures.rs)

### Summary
`sign_btc_transaction` is a critical bridge operation that triggers NEAR Chain Signatures (MPC) to sign a pending Bitcoin withdrawal PSBT. Unlike every other state-mutating bridge function, it carries no caller restriction — any unprivileged NEAR account can invoke it with an arbitrary `key_version` or `sign_index`, causing MPC signing to fail and leaving user withdrawal funds permanently stuck until an operator manually intervenes.

### Finding Description
Every other state-mutating bridge function in `satoshi-bridge` is gated by either `#[trusted_relayer]` (deposit/withdraw verification) or `#[access_control_any(roles(Role::DAO, Role::Operator))]` (UTXO management, cancel-withdraw, RBF). `sign_btc_transaction` carries only `#[pause(except(roles(Role::DAO)))]`, which only blocks calls when the contract is paused — it imposes no restriction on *who* may call it. [1](#0-0) 

Compare with the consistent pattern on all other privileged operations: [2](#0-1) [3](#0-2) 

`sign_btc_transaction` accepts a caller-supplied `key_version: u32` that is forwarded directly to the Chain Signatures MPC contract to select the signing key. If the wrong key version is supplied, the MPC produces a signature over the wrong key path; the resulting Bitcoin transaction is cryptographically invalid and cannot be broadcast. The pending sign entry remains in `btc_pending_infos` in `PendingSign` state, blocking the user's withdrawal indefinitely. [4](#0-3) 

The `btc_pending_sign_id` values are emitted as on-chain events (`GenerateBtcPendingInfo`) and are enumerable from contract state, so an attacker has no difficulty discovering live targets. [5](#0-4) 

A secondary, analogous gap exists on `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`, which the code comment explicitly labels as intended for "the off-chain program" (i.e., operators) yet carry no role guard: [6](#0-5) 

### Impact Explanation
A user who has burned nBTC and is awaiting a Bitcoin withdrawal has their funds locked inside the bridge. An attacker who continuously calls `sign_btc_transaction` with a wrong `key_version` on every new pending sign entry prevents the MPC pipeline from ever completing successfully, keeping those funds locked until an operator detects and manually retries — constituting attacker-triggered temporary locking of bridged funds. Repeated abuse across many pending entries can escalate to a sustained denial-of-withdrawal condition.

### Likelihood Explanation
Medium. All `btc_pending_sign_id` values are publicly observable via on-chain events. No NEAR deposit is required to call the function (despite `#[payable]`, no minimum is enforced). Any NEAR account can execute the attack at negligible cost, and the attacker can race each new pending entry as it appears.

### Recommendation
Add `#[access_control_any(roles(Role::DAO, Role::Operator))]` (or `#[trusted_relayer]`) to `sign_btc_transaction`, consistent with the access-control pattern applied to `active_utxo_management`, `cancel_withdraw`, and all other privileged bridge operations. Apply the same fix to `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`.

### Proof of Concept
1. User calls `ft_transfer_call` on the nBTC token, initiating a withdrawal. The bridge creates a `BTCPendingInfo` entry with state `PendingSign` and emits `GenerateBtcPendingInfo { btc_pending_id }`.
2. Attacker observes the emitted `btc_pending_id`.
3. Attacker calls `sign_btc_transaction(btc_pending_id, 0, 9999)` with a fabricated `key_version=9999`.
4. The bridge forwards the call to the Chain Signatures MPC contract using key version 9999, which either fails outright or produces a signature under a non-existent key path.
5. The MPC callback returns failure; the `BTCPendingInfo` remains in `PendingSign` state.
6. The user's nBTC is already burned; their BTC is not released. Funds are locked until an operator retries with the correct `key_version`.
7. Attacker repeats for every new pending entry, sustaining the denial-of-withdrawal.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
