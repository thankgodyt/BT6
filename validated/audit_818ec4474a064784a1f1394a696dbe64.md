### Title
Peras Vote and Certificate Validation Bypass Enables Unauthorized Chain-Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The `validatePerasCert` and `validatePerasVote` functions in the production `BlockSupportsPeras` instance are stub implementations that perform no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every input; `validatePerasVote` only checks stake-distribution membership without verifying any signature or committee-eligibility proof. An unprivileged peer can exploit this to inject fabricated votes or certificates that are accepted as valid, artificially boosting a block's Peras chain weight and causing honest nodes to switch to an attacker-controlled chain.

### Finding Description

The `BlockSupportsPeras` instance for all `blk` in `SupportsPeras.hs` provides two stub validation functions:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }

validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

`validatePerasCert` accepts every certificate unconditionally — no signature, no quorum proof, no round-number bounds check. [1](#0-0) 

`validatePerasVote` only checks that the claimed voter ID appears in the public stake distribution, without verifying any cryptographic signature or VRF/committee-selection proof. [2](#0-1) 

These functions sit on the hot path for inbound network objects. `processVotes` in `ObjectPool/PerasVote.hs` calls `validatePerasVote` for every batch of votes received from a peer before adding them to the database: [3](#0-2) 

The `implAddVote` and `implAddCert` functions in the respective DB implementations carry the same TODO comment acknowledging that non-trivial validation logic is missing: [4](#0-3) [5](#0-4) 

The analogy to the original report is direct: just as `updateProposal` accepted any new parameter values without checking their validity or prior state, `validatePerasCert` and `validatePerasVote` accept any inbound object without checking its cryptographic validity or prior consensus state. In both cases, the missing check is the guard that should make the state transition permanent and authoritative.

Once a fabricated vote passes `validatePerasVote`, it is inserted into `PerasVoteDB` via `implAddVote`. When enough fabricated votes accumulate to cross the quorum threshold, `updateCandidateVoteState` calls `forgePerasCert` and produces a `ValidatedPerasCert` for the attacker's target block. [6](#0-5) 

That certificate is then added to `PerasCertDB` via `implAddCert`, which only deduplicates by round number — it does not re-validate the certificate content. [7](#0-6) 

Chain selection then reads the weight snapshot from `PerasCertDB` and may switch to the boosted block. [8](#0-7) 

### Impact Explanation

An unprivileged peer can fabricate votes attributed to any known voter ID (all voter IDs are public via the stake distribution), send enough fake votes to cross the quorum threshold for any target block, trigger certificate forging for that block, and cause honest nodes to prefer the attacker's chain over the canonical chain. This is a direct bypass of Peras voting and certificate checks, enabling unauthorized certificate acceptance and chain-weight manipulation — matching the "Critical: Bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance" impact class.

### Likelihood Explanation

The stake distribution is public. Any peer connected to the node can send a batch of votes with fabricated voter IDs drawn from the public stake distribution. `processVotes` is reachable from the network miniprotocol layer without any authentication. The only prerequisite is knowing the voter IDs, which are public on-chain data.

### Recommendation

Implement actual cryptographic validation in `validatePerasCert` and `validatePerasVote`:
- `validatePerasCert` must verify the certificate's cryptographic signature and that it was produced by a legitimate quorum of committee members for the claimed round.
- `validatePerasVote` must verify the voter's cryptographic signature and committee-eligibility proof (VRF output), not merely stake-distribution membership.
- Remove the unconditional `Right` stub and implement the full validation logic referenced in issue #120.
- Enforce these checks at both the `validate*` layer and inside `implAddVote`/`implAddCert` as a defense-in-depth measure.

### Proof of Concept

1. Connect to a node as an unprivileged peer via the vote miniprotocol.
2. Observe the public stake distribution to obtain valid voter IDs and their associated stakes.
3. Fabricate N `PerasVote` messages (where N × average-stake ≥ quorum threshold) for a target block B, using voter IDs from the stake distribution.
4. Send the fabricated votes via `processVotes`.
5. Each vote passes `validatePerasVote` because the voter ID is in the stake distribution — no signature is checked.
6. The votes are inserted into `PerasVoteDB`; when quorum is reached, `updateCandidateVoteState` forges a `ValidatedPerasCert` for block B.
7. The certificate is added to `PerasCertDB` and chain selection is triggered.
8. The node's `getWeightSnapshot` now returns a boosted weight for block B, and `chainSelectionForBlock` may switch the node to the attacker's chain.

implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
