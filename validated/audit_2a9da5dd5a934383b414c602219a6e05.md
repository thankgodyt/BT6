### Title
Hardcoded `BranchId::Nu6_2` in `Transaction::decode` permanently blocks refunds for pre-NU6.2 Zcash deposits — (`contracts/satoshi-bridge/src/zcash_utils/transaction.rs`)

---

### Summary

`Transaction::decode` unconditionally uses `BranchId::Nu6_2` when deserializing any Zcash transaction, ignoring the `_chain` parameter entirely. Because Zcash V5 transactions embed the consensus branch ID in their serialized bytes and `ZCashTransaction::read` validates it against the caller-supplied value, any transaction confirmed before NU6.2 activation (mainnet block 3,364,600) carries `BranchId::Nu6` or `BranchId::Nu6_1` and will always fail to decode. Every code path that calls `WrappedTransaction::decode` — including the public `request_refund` entrypoint — panics on pre-NU6.2 bytes, making those deposits permanently unrefundable.

---

### Finding Description

**Root cause — `zcash_utils/transaction.rs` line 53:**

```rust
pub fn decode(data: &[u8], _chain: &network::Chain) -> Result<Self, std::io::Error> {
    let mut cursor = std::io::Cursor::new(data);
    let branch_id = BranchId::Nu6_2;          // ← hardcoded; _chain is ignored
    let tx = ZCashTransaction::read(&mut cursor, branch_id)?;
    Ok(Self { inner_tx: tx })
}

---

### Impact Explanation

Any Zcash deposit transaction confirmed before mainnet block 3,364,600 (NU6.2 activation) carries `nConsensusBranchId = Nu6` or `Nu6_1` in its serialized V5 bytes. `ZCashTransaction::read` validates this field against the caller-supplied `BranchId`; a mismatch returns an `io::Error`, which the `.expect(…)` turns into a NEAR panic. The refund request is never stored. Because the UTXO was never finalized via `verify_deposit`, it is also not in `verified_deposit_utxo`. There is no alternative recovery path: the deposit is permanently locked in the bridge's MPC-controlled address with no way to retrieve it.

---

### Likelihood Explanation

The bridge's own `network.rs` defines activation heights for NU6, NU6.1, and NU6.2, and `get_branch_id` is already wired up for the signing path (`execute_refund_callback` fetches `last_block_height` precisely to select the right branch ID for building the refund transaction). The decode path simply forgot to use the same logic. Any deposit made before block 3,364,600 that was not finalized — due to a failed relayer, a deposit to a wrong address, or any other reason — is permanently unrefundable.

---

### Recommendation

Replace the hardcoded constant with a branch-ID lookup that reads the embedded `nConsensusBranchId` from the transaction bytes before validating, or try each known branch ID in descending activation order. The simplest correct fix is to parse the 4-byte branch-ID field at offset 8 of a V5 transaction before calling `ZCashTransaction::read`, then pass the parsed value. Alternatively, expose a `decode_with_branch_id` that accepts the block height and delegates to `chain.get_branch_id(height)`.

---

### Proof of Concept

1. Serialize a real Zcash V5 transaction confirmed at mainnet height < 3,364,600 (e.g., any transaction from the NU6 or NU6.1 era). Its bytes contain `nConsensusBranchId = 0xC2D6D0B4` (Nu6) or `0x37519621` (Nu6_1).
2. Call `Transaction::decode(&pre_nu6_2_bytes, &Chain::ZcashMainnet)`.
3. Observe `ZCashTransaction::read` returns `Err(…)` because the embedded branch ID does not match `BranchId::Nu6_2 = 0xDAAB6B7B`.
4. The `.expect("Deserialization tx_bytes failed")` panics.
5. Confirm the same bytes decode correctly when `BranchId::Nu6` or `BranchId::Nu6_1` is supplied instead.
6. On-chain: call `request_refund(deposit_msg, refund_address, pre_nu6_2_tx_bytes, vout, proof, None)` with a valid light-client proof for the pre-NU6.2 deposit. The NEAR transaction reverts at step 1 of `internal_request_refund`; the refund request is never created; the deposit UTXO is permanently unrecoverable.
