### Title
Peras Certificate and Vote Signature Verification Bypass via Stub `BlockSupportsPeras` Instance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal degenerate `BlockSupportsPeras` instance used in production accepts all inbound Peras certificates unconditionally and accepts votes based solely on a self-declared voter ID without verifying any BLS signature. An unprivileged peer can craft a `PerasCert` for any block in any round and have it accepted by a node, directly inflating that block's chain-selection weight and causing the node to prefer a non-canonical chain.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, a universal stub instance is declared for all block types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

This instance provides two critically incomplete validators:

**1. `validatePerasCert` — unconditional acceptance:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

Every certificate received from any peer is immediately wrapped in `Right` — no signature, no round validity, no boosted-block existence check.

**2. `validatePerasVote` — stake-only check, no signature:**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

The stub `PerasVote blk` type carries no signature field at all — only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId`. Validation only checks whether `pvVoteVoterId` appears in the stake distribution; the claimed identity is never cryptographically proven. [4](#0-3) 

Both validators are wired directly into the production inbound-object paths. `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` and `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote mkPerasParams sd vote`: [5](#0-4) [6](#0-5) 

The structural parallel to the original report is exact: just as `feeRecipient == address(0)` causes the fee to flow to `msg.sender` (the submitter) without any proof of legitimacy, `validatePerasCert` causes every certificate to be accepted based solely on the submitter presenting it — no cryptographic proof of the claimed committee identity is required.

---

### Impact Explanation

Accepted Peras certificates are stored in `PerasCertDB` and used directly in chain selection via `WeightedSelectView`. The total weight of a chain fragment is:

```
wsvTotalWeight = BlockNo + wsvWeightBoost
``` [7](#0-6) 

`preferCandidate` switches to a candidate chain when its `wsvTotalWeight` exceeds the current chain's: [8](#0-7) 

A forged certificate adds `perasWeight params` to the boosted block's chain. An attacker who sends a crafted `PerasCert` pointing to a block on a minority fork can cause an honest node to switch away from the canonical chain to that fork — a chain-selection safety failure triggered by a single unauthenticated network message.

For votes: an attacker who knows the stake distribution can impersonate any committee member (by setting `pvVoteVoterId` to their `KeyHash`), accumulate enough forged votes to satisfy `votesReachQuorum`, and trigger local certificate forging for an arbitrary target block. [9](#0-8) 

---

### Likelihood Explanation

The CHANGELOG confirms the code path is active when Peras is enabled:

> "Make the ChainDB aware of the PerasCertDB, and modify the chain selection function accordingly. In practice, it means that the candidate fragment is now selected based on its Peras weight, instead of its length. Note that if Peras is disabled (which is the default), there is no observable difference." [10](#0-9) 

When Peras is enabled on a private testnet or future mainnet deployment, any connected peer can exploit this with a single crafted message. No keys, no stake, no special privileges are required — only knowledge of a valid `PerasRoundNo` and a target block `Point`. The `PerasCert` type in the stub instance carries only those two fields. [11](#0-10) 

---

### Recommendation

1. **`validatePerasCert`**: Implement full BLS aggregate signature verification using `verifyAggregateVoteSignature` and `batchVerifyVRFOutputs` from `CryptoSupportsAggregateVoteSigning` / `CryptoSupportsBatchVRFVerification`. The concrete crypto machinery already exists in `Ouroboros.Consensus.Peras.Crypto.BLS` and `Ouroboros.Consensus.Committee.WFALS`. [12](#0-11) 

2. **`validatePerasVote`**: Add a `pvSignature` field to the stub `PerasVote blk` type and call `verifyVoteSignature` against the voter's registered public key before accepting the vote.

3. **Guard the production path**: Until real validation is implemented, the Peras object-diffusion writers (`makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`) should refuse all inbound objects when running with the stub instance, rather than silently accepting them.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe the current canonical chain tip at block `B_canonical` (block number `N`).
2. Identify a minority-fork block `B_fork` at block number `N-1` (one block shorter).
3. Craft a `PerasCert` with `pcCertRound = <any valid round>` and `pcCertBoostedBlock = Point B_fork`.
4. Send this certificate to the target node via the Peras certificate diffusion mini-protocol.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right` unconditionally. [13](#0-12) 

6. The certificate is stored in `PerasCertDB`; `B_fork`'s chain gains `perasWeight params` boost.
7. `preferAnchoredCandidate` now computes `wsvTotalWeight(B_fork chain) = (N-1) + perasWeight > N = wsvTotalWeight(B_canonical chain)` when `perasWeight ≥ 2`.
8. The node switches to the minority fork, abandoning the canonical chain. [14](#0-13)

  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the

              , vpvqPerasCfg = cfg
              }
