### Title
Unvalidated Peras Certificate Acceptance Allows Unbounded Chain-Weight Inflation via Crafted Peer Messages - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` implementation in the degenerate `BlockSupportsPeras` instance unconditionally returns `Right` for every inbound certificate, performing no cryptographic or structural checks. An unprivileged peer can exploit this by sending N crafted `PerasCert` messages (one per distinct round number) all pointing to the same block on a minority fork. Each certificate is stored and its boost is accumulated without bound in the `PerasWeightSnapshot`. Once the accumulated boost for that block exceeds the security parameter `k`, chain selection treats the block as immutable and the node permanently prefers the attacker's fork.

**`takeVolatileSuffix` treats over-boosted blocks as immutable**

### Impact Explanation

An unprivileged peer sends N `PerasCert` messages with distinct `pcCertRound` values (0, 1, …, N−1) and the same `pcCertBoostedBlock` pointing to a block on a minority fork. Because `validatePerasCert` never rejects any certificate, all N are stored. The `PerasWeightSnapshot` for that block accumulates `N × perasWeight`. Once `N × perasWeight > k`, `takeVolatileSuffix` returns an empty fragment for any chain containing that block, making it appear immutable. `preferCandidate` then permanently prefers the attacker's fork over the honest chain, constituting a chain-selection safety failure reachable from a single unauthenticated peer connection.

This is the direct analog of the ZeroLocker `merge` bug: just as `merge` allows `end − start` to exceed `MAXTIME` and inflate `_calculatePower` beyond its intended maximum, the missing `validatePerasCert` check allows `weightBoostOfFragment` to exceed `k` and inflate `wsvTotalWeight` beyond the security parameter, corrupting chain selection.

---

### Likelihood Explanation

The attack requires only a TCP connection to a Peras-enabled node and the ability to send well-formed `PerasCert` wire messages. No stake, keys, or prior chain knowledge is needed. The number of messages required is `ceil(k / perasWeight)`, which with default parameters is a small integer. The attack is deterministic and repeatable.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before Peras is enabled in production. At minimum, verify the cryptographic proof of quorum (aggregate BLS signature over the voting committee), the round number is within the valid window, and the boosted block point is a known recent block.
2. **Cap the total boost per block** in `addToPerasWeightSnapshot` or in `implAddCert` so that no single block can accumulate boost exceeding `k`, regardless of how many certificates reference it.
3. **Enforce a maximum number of stored certificates** per boosted block point to bound the attack surface until full validation is in place.

### Proof of Concept

```
-- Attacker connects as a peer to a Peras-enabled node.
-- Let k = maxRollbacks secParam, W = perasWeight params.
-- N = ceil(k / W) + 1

for round in [0 .. N-1]:
  send PerasCert { pcCertRound = round, pcCertBoostedBlock = forkBlockPoint }

-- Each cert passes validatePerasCert (always Right).
-- implAddCert stores each (distinct round → cert).
-- implGetWeightSnapshot builds PerasWeightSnapshot:
--   forkBlockPoint → N * W  (> k)
-- takeVolatileSuffix on any chain containing forkBlockPoint returns [].
-- preferCandidate switches to the fork: ShouldSwitch (Heavier ...).
-- Node is now permanently anchored to the attacker's fork.
```
