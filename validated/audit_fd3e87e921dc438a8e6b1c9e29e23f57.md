### Title
`validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate Without Validation, Enabling Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or quorum validation. Because this function is the sole gate between a peer-supplied `PerasCert` and the `PerasCertDB` / chain-selection pipeline, any unprivileged peer can inject a crafted certificate that boosts an arbitrary block, causing an honest node to trigger chain selection for a non-canonical fork.

---

### Finding Description

`validatePerasCert` is the typeclass method responsible for verifying that a `PerasCert` received from the network represents a legitimately formed Peras quorum certificate before it is stored and acted upon. The production instance (the only concrete instance in the codebase) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

The function ignores every field of `cert` and always returns `Right`. No quorum check, no aggregate signature verification, no round-number bounds check, and no cross-reference against the ledger stake distribution is performed.

This function is called directly on the inbound network path in `processCerts`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [2](#0-1) 

Both production pool writers pass `validatePerasCert mkPerasParams` as the validator:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [3](#0-2) [4](#0-3) 

Once accepted, the certificate is stored in `PerasCertDB` and `addPerasCertAsync` is called, which enqueues a `ChainSelAddPerasCert` message. The chain-selection handler then calls `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [5](#0-4) 

The `PerasWeightSnapshot` derived from the `PerasCertDB` is then used during chain selection to add `perasWeight` (default 15) to the boosted block's chain, potentially making a minority fork appear heavier than the honest chain. [6](#0-5) 

**Analog to the DEXE pattern:** In DEXE, `delegateTreasury` calls `IERC20.transfer` and then unconditionally updates the delegatee's voting power without verifying the transfer actually moved tokens. Here, `validatePerasCert` is called and unconditionally produces a `ValidatedPerasCert` without verifying the certificate actually represents a valid quorum. In both cases, an accounting/weight value is updated based on an assumed successful operation that was never verified, breaking the invariant that the `Validated*` wrapper guarantees genuine validation.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on any fork and `pcCertRound` set to any round number. The certificate will pass `validatePerasCert` unconditionally, be stored in `PerasCertDB`, and trigger chain selection. The boosted block's chain receives an extra weight of `perasWeight` (15 slots by default). If the attacker's fork is within 15 blocks of the honest tip, the honest node will switch to the adversarial chain. This constitutes a chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions of the Peras protocol. [7](#0-6) 

---

### Likelihood Explanation

The attack requires only that the adversary be a connected peer and be able to send a `PerasCert` message via the Peras certificate diffusion mini-protocol. No keys, stake, or privileged access are needed. The only pre-check in `processCerts` is a deduplication guard on `pcCertRound`; a fresh round number bypasses it entirely. The attack is therefore trivially reachable by any peer. [2](#0-1) 

---

### Recommendation

Replace the stub `validatePerasCert` implementation with genuine validation before the Peras certificate diffusion path is enabled in production. At minimum, validation must:

1. Verify the aggregate BLS/KES signature over `(electionId, candidate)` against the aggregated public keys of the claimed quorum members.
2. Verify that the claimed voters' combined stake exceeds the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`) using the epoch stake distribution.
3. Verify that `pcCertRound` falls within the valid acceptance window relative to the current slot.
4. Verify that `pcCertBoostedBlock` refers to a block that is a plausible candidate (e.g., within the volatile window).

Until these checks are implemented, the `validatePerasCert` function must not be wired into any live peer-facing code path.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects as a peer and sends a `PerasCert` message via the Peras certificate object-diffusion mini-protocol with:
   - `pcCertRound = <any round not yet in PerasCertDB>`
   - `pcCertBoostedBlock = <point of a block on a minority fork>`

2. `makePerasCertPoolWriterFromChainDB` receives the cert and calls `processCerts`. [8](#0-7) 

3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })` unconditionally. [9](#0-8) 

4. The cert is stored in `PerasCertDB` and `addPerasCertAsync` is called. [10](#0-9) 

5. `chainSelSync` processes the cert, looks up the boosted block in `VolatileDB`, and calls `chainSelectionForBlock` for it. [11](#0-10) 

6. Chain selection now treats the minority fork as having 15 additional weight units, potentially causing the honest node to switch to the adversarial chain — breaking consensus safety.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
