### Title
Stub `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate, Bypassing Quorum Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance, which applies to all block types lacking a more specific override, implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives. Because this function is the sole gate used by the inbound certificate pipeline (`processCerts`) before a certificate is committed to the `PerasCertDB` or `ChainDB`, any unprivileged peer can inject an arbitrary, fabricated certificate. The accepted certificate immediately boosts the weight of the targeted block by `perasWeight params` (default 15) in chain selection, potentially causing an honest node to prefer a non-canonical chain.

### Finding Description

The degenerate catch-all instance of `BlockSupportsPeras` is declared with an explicit TODO acknowledging it is a placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature check, no quorum check, no round-number bounds check, and no check that the certificate's boosted block actually exists on any known chain is performed. The function simply wraps the raw `PerasCert` in a `ValidatedPerasCert` and returns it as valid.

This stub is wired directly into the inbound certificate processing pipeline. `makePerasCertPoolWriterFromChainDB` (and its `PerasCertDB` counterpart) passes `validatePerasCert mkPerasParams` as the validator to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

Inside `processCerts`, the only guard before `addCert` is called is whether the certificate's round number is already present in the database:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validateCert` is `validatePerasCert mkPerasParams` and that always returns `Right`, `partitionEithers` always produces `([], validatedCerts)`, so every certificate in the batch is unconditionally committed.

This is structurally identical to the external report's root cause: the `_repay` function did not validate that `amount > 0`, so the check `currentShares == shares` (both 0) was trivially satisfied and triggered `_cleanupLoan`. Here, `validatePerasCert` does not validate anything, so the check `partitionEithers ... == ([], ...)` is trivially satisfied and triggers `addCert`.

### Impact Explanation

Once a fabricated `ValidatedPerasCert` is stored in the `ChainDB`, the Peras weight snapshot used during chain selection is updated. The boosted block gains `perasWeight = 15` additional weight units: [4](#0-3) 

Chain selection uses `preferAnchoredCandidate` / `rollbackExceedsSuffix`, both of which call `totalWeightOfFragment` over the Peras weight snapshot: [5](#0-4) 

An attacker who injects one certificate per round for a target block on a minority fork can accumulate enough artificial weight to make that fork appear heavier than the honest chain, causing the victim node to switch to the adversarial fork. This is a **Critical** chain-selection safety failure: an unprivileged peer can make an honest node accept and prefer a non-canonical chain without holding any stake or keys.

### Likelihood Explanation

The object diffusion mini-protocol for Peras certificates is a public, unauthenticated channel. Any connected peer can send a `[PerasCert blk]` batch. The only deduplication is by round number; a fresh round number bypasses even that check. No stake, no key material, and no prior relationship with the node is required.

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the Peras object diffusion layer is enabled in production. At minimum, the implementation must verify that the certificate is backed by a quorum of valid, cryptographically signed votes from eligible committee members, and that the boosted block is a known block on a plausible chain.
2. **Add a non-zero guard** analogous to the fix recommended in the external report: reject any certificate whose backing vote set is empty or whose total stake does not exceed `perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`.
3. **Track the open issue** at `https://github.com/tweag/cardano-peras/issues/120` and ensure the stub is replaced before the Peras diffusion layer is activated on any network that uses real stake.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
