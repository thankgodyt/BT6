### Title
Uncapped User-Supplied `gas_fee` in `request_refund` Bypasses Stored Configuration, Enabling Near-Zero Refund and Potential Permanent UTXO Lockup — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Any unprivileged NEAR account can call `request_refund` and supply an arbitrarily large `gas_fee` value. The contract only checks that `gas_fee < deposit_amount`, with no validation against a configured maximum. This allows an attacker to submit a refund request that reduces the depositor's refund to 1 satoshi. If the resulting refund amount falls below Bitcoin's dust limit (~546 satoshis), the signed refund transaction will be rejected by the Bitcoin network, while the UTXO is simultaneously marked as verified — permanently blocking both `verify_deposit` and any future `execute_refund` re-attempt.

---

### Finding Description

In `request_refund_callback`, the caller-supplied `gas_fee` is resolved and validated with only a single bound check:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

There is no upper bound check against any stored configuration value (e.g., a `max_refund_gas_fee` field). The `gas_fee` is then stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,
    ...
};
``` [2](#0-1) 

Later, in `refund_execution_inputs`, the refund amount is computed as:

```rust
let refund_amount = refund_request.amount.checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

The only guard is `refund_amount > 0`. There is no dust-limit check. If `gas_fee = deposit_amount - 1`, the refund output is 1 satoshi — below Bitcoin's dust threshold — and the resulting transaction will be rejected by the Bitcoin network.

Critically, `finalize_refund_with_psbt` marks the UTXO as verified **before** the transaction is broadcast:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

And the `BTCPendingInfo` insertion guard prevents re-execution:

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
``` [5](#0-4) 

Once `execute_refund` runs with a dust-level output:
- `verify_deposit` is blocked (UTXO in `verified_deposit_utxo`)
- `execute_refund` re-attempt panics with "pending info already exist"
- `verify_refund_finalize` is never called (transaction never confirms)
- `internal_remove_refund_pending_tx_id` cannot remove the pending tx while the refund request is still active [6](#0-5) 

The UTXO is permanently locked.

---

### Impact Explanation

An attacker can cause permanent locking of a depositor's BTC UTXO. The depositor cannot claim nBTC (blocked by `verified_deposit_utxo`) and cannot get a proper refund (pending info blocks re-execution). This matches the allowed impact: **significant permanent locking of user funds**.

---

### Likelihood Explanation

- `request_refund` is callable by any NEAR account — no role restriction.
- Deposits where `deposit_msg.refund_address` is `None` are the common case (users who did not pre-authorize a refund address).
- The attacker only needs to front-run the depositor's own refund request for the same UTXO.
- The `unsafe_refund_timelock_sec` (14 days) gives the DAO time to reject, but the DAO must actively monitor every refund request's gas fee value — a non-trivial operational requirement. If the DAO rejects after `execute_refund` has already been called, the UTXO is already locked.
- The attack is cheap: submitting a refund request costs only the storage deposit.

---

### Recommendation

Add a configured maximum refund gas fee to `Config` and enforce it in `request_refund_callback`:

```rust
// In Config:
pub max_refund_gas_fee: u128,

// In request_refund_callback:
require!(
    resolved_gas_fee <= config.max_refund_gas_fee,
    "Gas fee exceeds configured maximum"
);
```

Additionally, add a dust-limit check before accepting the refund request:

```rust
require!(
    amount - resolved_gas_fee >= config.min_refund_output_amount,
    "Refund amount would be below dust limit"
);
```

---

### Proof of Concept

1. Depositor sends 10,000 satoshis to a bridge address with `deposit_msg.refund_address = None`.
2. Attacker observes the deposit transaction on-chain.
3. Attacker calls `request_refund` with:
   - `deposit_msg` = the depositor's deposit message
   - `refund_address` = depositor's BTC address (to appear legitimate)
   - `gas_fee` = `9_999` (leaving 1 satoshi, below dust limit)
   - Valid `tx_bytes` and `proof`
4. `request_refund_callback` stores the request: `gas_fee = 9_999`, `amount = 10_000`.
5. After 14 days (`unsafe_refund_timelock_sec`), attacker calls `execute_refund`.
6. `refund_execution_inputs` computes `refund_amount = 10_000 - 9_999 = 1`.
7. `finalize_refund_with_psbt` marks the UTXO in `verified_deposit_utxo` and inserts `BTCPendingInfo`.
8. MPC signs the refund transaction with a 1-satoshi output.
9. The signed transaction is broadcast but rejected by the Bitcoin network (dust).
10. `verify_refund_finalize` is never called; the UTXO is permanently locked.
