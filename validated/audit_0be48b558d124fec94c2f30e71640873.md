### Title
Hardcoded `TriggerHardForkNotDuringThisExecution` in `partialLedgerConfigConway` Silently Ignores `triggerHardForkDijkstra`, Preventing Conway→Dijkstra Era Transition - (File: `ouroboros-consensus-cardano/src/ouroboros-consensus-cardano/Ouroboros/Consensus/Cardano/Node.hs`)

---

### Summary

`protocolInfoCardano` in `Node.hs` hardcodes `TriggerHardForkNotDuringThisExecution` as the hard-fork trigger for the Conway ledger config, instead of using the caller-supplied `triggerHardForkDijkstra` value. The `triggerHardForkDijkstra` field is accepted in the `CardanoHardForkTriggers'` record and correctly set by the node configuration layer, but it is never destructured from the pattern match and never wired into `partialLedgerConfigConway`. As a result, `singleEraTransition` for Conway always returns `Nothing`, the Conway era never ends according to this node's consensus layer, and the Conway→Dijkstra hard fork can never be triggered — regardless of on-chain governance or operator configuration.

---

### Finding Description

**Root cause — missing destructuring of `triggerHardForkDijkstra`:**

The pattern match that unpacks `CardanoHardForkTriggers'` in `protocolInfoCardano` stops at `triggerHardForkConway` and silently drops `triggerHardForkDijkstra`:

```haskell
cardanoHardForkTriggers =
  CardanoHardForkTriggers'
    { triggerHardForkShelley
    , triggerHardForkAllegra
    , triggerHardForkMary
    , triggerHardForkAlonzo
    , triggerHardForkBabbage
    , triggerHardForkConway
    -- triggerHardForkDijkstra is absent
    }
``` [1](#0-0) 

**Root cause — hardcoded `TriggerHardForkNotDuringThisExecution` for Conway:**

Every preceding era wires its trigger into the next era's `partialLedgerConfig`. For example, Babbage correctly uses `toTriggerHardFork triggerHardForkConway`. But Conway uses the hardcoded sentinel that means "never transition during this execution":

```haskell
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    TriggerHardForkNotDuringThisExecution   -- should be: toTriggerHardFork triggerHardForkDijkstra
``` [2](#0-1) 

Compare with the correct pattern used for Babbage→Conway: [3](#0-2) 

**Effect on `singleEraTransition`:**

`SingleEraBlock (ShelleyBlock proto era)` dispatches on `shelleyTriggerHardFork pcfg`. When that field is `TriggerHardForkNotDuringThisExecution`, `singleEraTransition` unconditionally returns `Nothing`:

```haskell
case shelleyTriggerHardFork pcfg of
  TriggerHardForkNotDuringThisExecution -> Nothing
  TriggerHardForkAtEpoch epoch          -> Just epoch
  TriggerHardForkAtVersion v            -> shelleyTransition pcfg v ledgerState
``` [4](#0-3) 

This puts Conway on the **NEVER trajectory** — `singleEraTransition` will never return `Just`, so the HFC will never compute an end-bound for the Conway era and will never transition to Dijkstra.

**The caller-supplied trigger is correctly set but silently discarded:**

The node configuration layer (`Cardano/Node/Protocol/Cardano.hs`) correctly populates `triggerHardForkDijkstra` with either `CardanoTriggerHardForkAtDefaultVersion` or `CardanoTriggerHardForkAtEpoch epochNo`: [5](#0-4) 

The `CardanoHardForkTriggers'` pattern synonym confirms `triggerHardForkDijkstra` is a first-class field: [6](#0-5) 

---

### Impact Explanation

When the Cardano chain transitions from Conway to Dijkstra via on-chain governance (a protocol-version increment accepted by the ledger), any node running this code will:

1. **Fail to follow the era transition.** `reconstructSummaryLedger` calls `singleEraTransition` for each era to build the `HardForkSummary`. Because Conway's `singleEraTransition` always returns `Nothing`, the summary will never include a Dijkstra era bound, and the HFC will never switch the active era to Dijkstra.

2. **Reject valid Dijkstra blocks.** Blocks tagged with the Dijkstra era tag (CBOR tag `8`) will be decoded correctly at the wire level, but the HFC ledger will refuse to apply them because the ledger state is still in Conway and no transition has been recorded.

3. **Diverge from the honest chain.** The node will remain on a Conway-only fork while the rest of the network advances into Dijkstra, constituting a permanent chain-selection divergence.

This matches the **High** impact category: *Hard-fork, era transition, ledger-view, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.*

---

### Likelihood Explanation

The Dijkstra era is already present in the codebase as a production era (it has a full `SerialiseHFC` tag, `BlockConfig`, `PartialLedgerConfig`, and `PartialConsensusConfig`). The Conway→Dijkstra transition is the next scheduled hard fork. When on-chain governance votes to increment the major protocol version to 12 (Dijkstra), every node running this binary will silently fail to follow the transition. No special attacker capability is required — the trigger is a normal on-chain governance action reachable by any stakeholder with sufficient stake.

---

### Recommendation

In `protocolInfoCardano`, destructure `triggerHardForkDijkstra` from `CardanoHardForkTriggers'` and wire it into `partialLedgerConfigConway`, mirroring the pattern used for every preceding era transition:

```haskell
-- In the CardanoHardForkTriggers' pattern match, add:
, triggerHardForkDijkstra

-- Replace:
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    TriggerHardForkNotDuringThisExecution

-- With:
partialLedgerConfigConway =
  mkPartialLedgerConfigShelley
    transitionConfigConway
    (toTriggerHardFork triggerHardForkDijkstra)
```
