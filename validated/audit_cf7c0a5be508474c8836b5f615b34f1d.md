### Title
Incomplete State Cleanup in `internal_clear_invalid_pending_verify_rbf` Leaves Stale Account Tracking Entries - (File: contracts/satoshi-bridge/src/btc_pending_info.rs)

### Summary

`internal_clear_invalid_pending_verify_rbf` removes a `BTCPendingInfo` entry from the global `btc_pending_infos` map but fails to remove the corresponding ID from the owning account's `btc_pending_sign_ids` and `btc_pending_verify_list` tracking sets. This is the same class of incomplete deletion described in the audit report: a cleanup function only clears a subset of the state that tracks the deleted item, leaving the rest inconsistent.

### Finding Description

`internal_clear_invalid_pending_verify_rbf` is the production cleanup path for stale RBF pending-verify entries: [1](#0-0) 

It calls `internal_remove_btc_pending_info`, which only removes from `btc_pending_infos`: [2](#0-1) 

It never touches the account-level tracking sets. Compare this to the correct cleanup pattern used in `verify_refund_finalize_callback`: [3](#0-2) 

And in `internal_remove_refund_pending_tx_id`: [4](#0-3) 

Both of those correctly remove from `btc_pending_infos` **and** from `account.btc_pending_sign_ids` / `account.btc_pending_verify_list`. The RBF cleanup path omits this second step entirely.

The public entry point is permissionless (no role guard, only `#[pause]`): [5](#0-4) 

### Impact Explanation

After `clear_invalid_pending_verify_rbf` is called, the account's `btc_pending_sign_ids` and/or `btc_pending_verify_list` retain a dangling ID whose backing `BTCPendingInfo` no longer exists. The pending-capacity guard (`require_pending_sign_capacity`) reads these sets to enforce the per-account limit: [6](#0-5) 

Each stale entry permanently inflates the user's apparent pending count. Once the count reaches the configured limit, the user can never submit another withdrawal (`ft_on_transfer` → `Withdraw`) or refund execution, permanently locking their ability to move bridged funds. This matches the **Low** allowed impact: publicly reachable invariant-violation / stuck-state in production bridge paths without direct theft.

### Likelihood Explanation

`clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf` are called by off-chain relayer programs as part of normal post-RBF housekeeping. Every legitimate invocation of this path silently corrupts the affected account's tracking state. No special privilege or adversarial intent is required; the bug triggers on every normal cleanup call.

### Recommendation

Mirror the cleanup pattern used in `verify_refund_finalize_callback` and `internal_remove_refund_pending_tx_id`. After removing from `btc_pending_infos`, also remove the ID from the account's tracking sets:

```rust
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
    // --- ADD: clean up account-level tracking ---
    let account_id = btc_pending_info.account_id.clone();
    let account = self.internal_unwrap_mut_account(&account_id);
    account.btc_pending_sign_ids.remove(&btc_pending_id);
    account.btc_pending_verify_list.remove(&btc_pending_id);
}
```

### Proof of Concept

1. User Alice submits a withdrawal → `btc_pending_sign_ids` gains entry `X`.
2. MPC signs; entry moves to `btc_pending_verify_list` as `X_rbf` (RBF variant).
3. Original tx `X` is verified on-chain; `rbf_txs[X]` is removed.
4. Relayer calls `clear_invalid_pending_verify_rbf("X_rbf")`.
5. `btc_pending_infos["X_rbf"]` is deleted, but `alice.btc_pending_verify_list` still contains `"X_rbf"`.
6. Alice's `pending_sign_count()` is permanently inflated by 1.
7. Repeat steps 1–6 up to the per-account limit; Alice can no longer initiate any withdrawal or refund execution. [1](#0-0) [7](#0-6)
