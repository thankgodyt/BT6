### Title
`checkPreferTheirsOverOurs` Uses Hardcoded Empty Peras Weight Snapshot, Causing Incorrect Peer Disconnection Under Peras — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect a peer whose headers are beyond the forecast horizon. When the Peras protocol is active, this ignores certificate-based weight boosts entirely, causing the node to use a strictly weaker chain-selection metric than the one used everywhere else in the system. A peer offering a Peras-boosted candidate chain that is genuinely preferred over the local chain can be incorrectly disconnected, leaving the node permanently on a less-secure, lower-weight chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever the forecast horizon is exceeded — i.e., when the peer's next header is too far ahead of the intersection for the node to obtain a ledger view and validate it. The function's purpose is to disconnect peers whose candidate chain is already known to be worse than the local selection, so the node does not wait indefinitely for a chain it will never adopt.

The comparison is performed by calling `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`. When the snapshot is empty it falls back to the plain `SelectView` path, which compares chains solely by block number and tiebreaker. When the snapshot is non-empty (i.e., Peras is active) it uses `weightedSelectView`, which adds the sum of Peras certificate boosts to the block number before comparing.

Because `checkPreferTheirsOverOurs` always supplies the empty snapshot, it always takes the block-count-only path, regardless of whether Peras is active. The rest of the chain-selection pipeline — `constructPreferableCandidates`, `chainSelection`, and `compareChainDiffs` in `ChainSel.hs` — all receive the real `PerasWeightSnapshot` from `cdbPerasWeights` and therefore use the correct weighted comparison.

This creates a split: the gate-keeping check in the ChainSync client uses a strictly weaker metric than the actual chain-selection logic. The two metrics disagree whenever a candidate chain has fewer blocks than the local chain but enough Peras certificate boosts to make its total weight higher.

**Concrete mismatch scenario:**

| | Local chain | Candidate chain |
|---|---|---|
| Block count | 10 | 9 |
| Peras boost | 0 | 3 |
| Total weight | 10 | 12 |

`checkPreferTheirsOverOurs` (empty snapshot): candidate has block count 9 < 10 → `ShouldNotSwitch` → peer disconnected with `CandidateTooSparse`.

Actual chain selection (real snapshot): candidate total weight 12 > 10 → `ShouldSwitch` → candidate should be adopted.

The peer is disconnected before the node ever gets to run the correct comparison.

---

### Impact Explanation

**Classification: High — Chain selection bug that lets an unprivileged peer cause an honest node to stay on a less-secure chain beyond the intended Peras security assumptions.**

When Peras is active, the protocol's security guarantee is that the chain with the highest total weight (block count + certificate boosts) is the canonical chain. A node that ignores certificate boosts in `checkPreferTheirsOverOurs` can be made to disconnect from every peer that offers the canonical Peras-boosted chain, provided those peers' headers happen to arrive beyond the forecast horizon. The node then remains on a chain with lower total weight, which is precisely the chain the Peras protocol defines as less secure. This is a durable outcome: once the peer is disconnected, the node does not re-evaluate the decision.

---

### Likelihood Explanation

**Medium.** The conditions required are:

1. Peras is active (a planned protocol upgrade; the code already contains the full `PerasWeightSnapshot` infrastructure and the `TODO` comment acknowledges the issue is Peras-specific).
2. A candidate chain exists whose total Peras weight exceeds the local chain's total weight, but whose block count is lower (a natural outcome when the local chain has a slot gap and the candidate has accumulated certificates).
3. The candidate's next header arrives beyond the forecast horizon — a normal occurrence during initial sync or after a long slot gap.

All three conditions are reachable by any unprivileged peer simply by serving valid headers in the normal ChainSync protocol. No key compromise, stake majority, or operator action is required.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual `PerasWeightSnapshot` sourced from `cdbPerasWeights` (the same snapshot already threaded through `ChainSelEnv` and `constructPreferableCandidates`). This ensures the gate-keeping check uses the same metric as the rest of chain selection.

Alternatively, as the in-code `TODO` already notes (referencing `https://github.com/tweag/cardano-peras/issues/64`), remove the `checkPreferTheirsOverOurs` check entirely if the Genesis/LoE machinery already provides a sufficient safety net against being stuck on a sparse candidate chain.

**Entry path:** unprivileged peer → ChainSync miniprotocol → `Client.hs` → `readLedgerStateHelper` → `checkPreferTheirsOverOurs`.

**Step-by-step:**

1. Peras is active; the node's local chain has 10 blocks and zero certificate boosts (total weight 10).
2. A peer advertises a candidate chain with 9 blocks and a Peras certificate boost of 3 (total weight 12).
3. The peer sends the header at slot S, which is beyond the current forecast horizon (e.g., there is a slot gap larger than the stability window between the intersection and slot S).
4. `readLedgerStateHelper` calls `projectLedgerView slot lst`, which returns `Nothing` (outside forecast range).
5. `checkPreferTheirsOverOurs` is called with `ourFrag` (10 blocks) and `theirFrag` (9 blocks).
6. `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag` compares block numbers: 9 < 10 → `ShouldNotSwitch`.
7. `throwSTM $ CandidateTooSparse ...` disconnects the peer.

  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))

              ShouldNotSwitch o -> ShouldNotSwitch o
