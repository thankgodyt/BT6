### Title
Refund execution transiently blocked when caller holds a pending-sign slot — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
`finalize_refund_with_psbt` enforces the per-account pending-sign capacity limit against the refund caller. With the default limit of 1, a user who already has one pending-sign transaction (e.g. a withdrawal) cannot execute a valid, timelock-expired refund until that slot is freed.

### Finding Description
`execute_refund` is a public, unprivileged entry point. [1](#0-0) 

It delegates to `internal_execute_refund`, which calls `finalize_refund_with_psbt`. [2](#0-1) 

Inside `finalize_refund_with_psbt`, after optionally registering the account, the capacity guard fires unconditionally: [3](#0-2) 

`require_pending_sign_capacity` compares `pending_sign_count()` against `get_max_pending_sign_txs`, which defaults to **1** for any account without an explicit override: [4](#0-3) 

If the caller already holds one pending-sign entry (e.g. an in-flight withdrawal), the `require!` panics and the refund cannot be created, even though the timelock has fully elapsed.

### Impact Explanation
The user's deposit UTXO is held in a `RefundRequest` that cannot be advanced to the MPC-sign pipeline. The funds are not lost — the refund request persists — but the user cannot retrieve their BTC until the blocking slot is freed. This violates the invariant that a timelock-expired refund must always be executable by the depositor.

### Likelihood Explanation
Any user who initiates a withdrawal and separately has a deposit UTXO with an expired refund timelock hits this condition. With the default limit of 1 this is a routine operational scenario, not a contrived edge case.

### Recommendation
Exempt refund execution from the pending-sign capacity check, or use a separate per-type counter so that a pending withdrawal does not consume the slot needed for a refund. Alternatively, raise the default `pending_tx_limit` to at least 2 so that one withdrawal and one refund can coexist.

### Proof of Concept
1. Alice initiates a withdrawal → `btc_pending_sign_ids` now has 1 entry (default limit = 1).
2. Alice's separate deposit UTXO has a `RefundRequest` whose timelock has passed.
3. Alice calls `execute_refund(utxo_storage_key)`.
4. `finalize_refund_with_psbt` reaches line 342 and panics: `"Too many pending sign transactions"`.
5. Alice can unblock herself by calling `sign_btc_transaction` on her pending withdrawal (public, no caller check), which on callback removes the entry from `btc_pending_sign_ids`: [5](#0-4) 
6. After the slot is freed, `execute_refund` succeeds.

**Severity: Low** — the block is temporary and self-resolvable without operator intervention; no funds are permanently locked and no theft is possible.

    pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
        require!(
            self.get_account(account_id)
                .unwrap_or_else(|| {
                    env::panic_str(&format!("ERR_ACCOUNT_NOT_REGISTERED: {}", account_id))
                })
                .pending_sign_count()
