### Title
Strict `max_btc_gas_fee` Upper Bound in PSBT Validation Freezes All Withdrawals During BTC Fee Market Spikes — (File: `contracts/satoshi-bridge/src/psbt.rs`)

### Summary
The `check_withdraw_psbt` function enforces a hard upper bound (`max_btc_gas_fee`) on the Bitcoin gas fee embedded in every withdrawal PSBT. During BTC fee-market volatility, the actual fee required for timely confirmation can exceed this bound, causing every withdrawal PSBT to be rejected and all pending user withdrawals to be stuck until a DAO/Operator manually updates the config.

### Finding Description
`check_withdraw_psbt` (and its shared helper `check_psbt_output_all_change_address`) both enforce:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!(
        "Invalid gas fee ({}). valid range: [{}, {}].",
        gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
``` [1](#0-0) 

This is a strict two-sided range check with no fallback path. The `max_btc_gas_fee` value is set in `Config` and can only be changed by a privileged `update_config` call. [2](#0-1) 

The withdrawal flow is:
1. An unprivileged user calls `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`, locking their nBTC in a `PendingSign` state.
2. A relayer constructs a PSBT and calls the signing pipeline, which invokes `check_withdraw_psbt_valid` → `check_withdraw_psbt`.
3. If the current BTC mempool fee rate requires a fee above `max_btc_gas_fee`, the `require!` panics and the PSBT is rejected. [3](#0-2) 

Because the check is a hard revert with no fallback (no "use a lower-priority fee" path, no emergency bypass for the relayer), every withdrawal PSBT is rejected until the DAO/Operator issues an `update_config` transaction raising `max_btc_gas_fee`. During the gap, all user withdrawals remain stuck in `PendingSign`.

The same bound is also enforced in `check_psbt_output_all_change_address`, which is used for active UTXO management: [4](#0-3) 

### Impact Explanation
**Low.** All pending and new user withdrawals enter a stuck state — nBTC has already been transferred to the bridge but BTC cannot be sent back — until a privileged operator updates the config. There is no direct theft; funds are not lost, only temporarily inaccessible. This matches the allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

### Likelihood Explanation
BTC fee-market spikes are a recurring, well-documented phenomenon (inscription/ordinal frenzies, halving periods, mempool congestion events). During such events, fee rates can increase 10–50× within minutes, easily exceeding a statically configured `max_btc_gas_fee`. The stuck state persists until a DAO/Operator transaction is confirmed, which — unlike Salty's 10-day governance vote — can happen in one block, but still requires human intervention and introduces a locking window of unpredictable duration.

### Recommendation
1. **Introduce a relayer-accessible fee ceiling override**: allow a whitelisted relayer to submit a PSBT with a fee up to a secondary `emergency_max_btc_gas_fee` (set higher than `max_btc_gas_fee`) without a full config update, so withdrawals can proceed during spikes.
2. **Alternatively, replace the hard upper bound with a soft warning/event** and only enforce a hard floor (`min_btc_gas_fee`) to prevent dust-fee griefing, while letting the relayer choose any fee above the floor.
3. At minimum, document the operational runbook so operators can react within minutes of a fee spike.

### Proof of Concept
1. User calls `ft_transfer_call` transferring 0.01 nBTC to the bridge with a withdrawal message. The bridge records a `BTCPendingInfo` in `PendingSign` state and the user's nBTC is locked.
2. BTC mempool fee rate spikes to 500 sat/vB (e.g., during an inscription event). The relayer computes that a standard 2-input/2-output withdrawal transaction requires ~450,000 sat in fees.
3. `config.max_btc_gas_fee` is set to 200,000 sat (a reasonable value at deployment time).
4. The relayer constructs a PSBT with `gas_fee = 450,000`. `check_withdraw_psbt` computes `gas_fee = total_input - total_output = 450,000` and hits:
   ```
   require!(450_000 >= 10_000 && 450_000 <= 200_000, ...)
   // → panics: "Invalid gas fee (450000). valid range: [10000, 200000]."
   ``` [1](#0-0) 
5. Every withdrawal PSBT is rejected. All users with pending withdrawals are stuck. The bridge remains in this state until a DAO/Operator transaction updates `max_btc_gas_fee` to a value ≥ 450,000.

    pub fn check_withdraw_psbt_valid(
        &self,
        target_btc_address: String,
        withdraw_change_address_script_pubkey: &ScriptBuf,
        withdraw_psbt: &PsbtWrapper,
        vutxos: &[VUTXO],
        amount: u128,
        withdraw_fee: u128,
        max_gas_fee: Option<U128>,
    ) -> (u128, u128) {
        let config = self.internal_config();
        let vutxos_len = u32::try_from(vutxos.len()).unwrap_or_else(|_| {
            env::panic_str("vutxos len overflow");
        });
        let utxo_num = self.data().utxos.len() + vutxos_len;
        let (input_num, change_num, actual_received_amount, gas_fee) = self.check_withdraw_psbt(
            withdraw_psbt,
            target_btc_address,
            withdraw_change_address_script_pubkey,
            vutxos,
            amount,
            withdraw_fee,
        );

        if let Some(max_gas_fee) = max_gas_fee {
            require!(
                gas_fee <= max_gas_fee.0,
                format!(
                    "Gas fee does not match the provided max fee (gas fee = {}; max gas fee = {})",
                    gas_fee, max_gas_fee.0
                )
            );
        }
