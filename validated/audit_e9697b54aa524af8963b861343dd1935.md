### Title
OCert Cold-Key Signature Lacks Network Domain Separation, Enabling Cross-Network Replay - (`ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos.hs`)

### Summary

The Praos Operational Certificate (OCert) cold-key DSIGN verification in `doValidateKESSignature` passes `()` (unit) as the cryptographic context and signs a payload of `(vkHot, n, c0)` that contains no network magic. This is the direct analog of the EIP-4337 missing `chainId` vulnerability: an OCert signed for one Cardano network (e.g., testnet) is cryptographically valid on any other network (e.g., mainnet) where the same cold key is registered, because no network-specific domain separator is included in either the signing context or the signed payload.

### Finding Description

In `doValidateKESSignature`, the OCert cold-key signature is verified as:

```haskell
DSIGN.verifySignedDSIGN () vkcold (OCert.ocertToSignable oc) tau
  ?!: InvalidSignatureOCERT n c0
```

The first argument `()` is the `ContextDSIGN` — the domain-separation context passed to the DSIGN algorithm. It is unit, carrying no network identity. The signed payload `OCert.ocertToSignable oc` serialises only `(vkHot, n, c0)` — the hot KES verification key, the certificate issue counter, and the KES start period — with no network magic, no genesis hash, and no chain identifier of any kind.

This is in direct contrast to the Byron era, where `ContextDSIGN ByronDSIGN = (ProtocolMagicId, VerKeyDSIGN ByronDSIGN)` explicitly binds every signature to a `ProtocolMagicId`. The Shelley/Praos OCert cold-key signature has no equivalent binding.

The formal specification confirms the signed payload is exactly `serialised(vkHot, n, c0)` with no network field, and the Haskell implementation faithfully reproduces this omission.

### Impact Explanation

An OCert generated for testnet is a valid OCert on mainnet if the same cold key is registered on both networks. An attacker who obtains the KES hot signing key corresponding to a testnet OCert (e.g., by compromising a testnet node, which operators routinely run with weaker physical and operational security than mainnet) can present that testnet OCert to a mainnet node. The mainnet node's `doValidateKESSignature` will accept it: the cold-key DSIGN check passes (no network binding), the KES period and counter checks pass (counters are per-network state, but the replayed OCert counter value `n` satisfies `m ≤ n ≤ m+1` if the mainnet counter for that cold key is at `m`), and the KES signature over the block header body passes (the attacker holds the KES signing key). The result is unauthorized block production on mainnet by a party whose mainnet cold key has not been directly compromised.

This constitutes a bypass of the OCert authorization check — the mechanism that delegates block-production rights from a cold key to a hot KES key — enabling unauthorized block acceptance on the target network.

### Likelihood Explanation

The preconditions are realistic:
1. **Same cold key on multiple networks**: Many stake pool operators register the same cold key on both mainnet and a testnet for operational testing. This is a documented and common practice.
2. **Testnet KES key exposure**: Testnet nodes are routinely operated with weaker security posture (shared infrastructure, less hardened environments). An attacker who compromises a testnet node obtains the KES hot signing key.
3. **Counter alignment**: The mainnet OCert counter for the cold key starts at 0 for a newly registered pool, so a testnet OCert with `n = 0` satisfies the counter check on mainnet immediately.

The attack does not require any mainnet key material to be compromised. It exploits the absence of network domain separation in the OCert cold-key signature.

### Recommendation

Include the network magic (or a network-specific genesis hash) in the `OCertSignable` payload, mirroring the Byron approach. The `ContextDSIGN` for the Shelley/Praos DSIGN algorithm should be changed from `()` to include the `NetworkMagic` or `ProtocolMagicId`, so that:

```
sigma = sign(coldKey, networkMagic || vkHot || n || c0)
```

This ensures an OCert signed for testnet is cryptographically invalid on mainnet, eliminating the cross-network replay path. The change must be coordinated with a hard fork since it alters the on-chain signature format.

**Attack sequence:**

1. Operator registers cold key `CK` on both mainnet and testnet.
2. Operator generates testnet OCert: `sigma_testnet = sign(CK, (vkHot_test, 0, c0_test))`.
3. Attacker compromises testnet node, obtains `skHot_test` (the KES signing key).
4. Attacker submits a block to mainnet with the testnet OCert embedded in the header.
5. Mainnet node calls `doValidateKESSignature`: `verifySignedDSIGN () CK (vkHot_test, 0, c0_test) sigma_testnet` — **passes**, because `()` carries no network identity.
6. Mainnet node calls `verifySignedKES () vkHot_test t headerBody headerSig` — **passes**, because the attacker holds `skHot_test`.
7. Counter check: mainnet counter for `CK` is 0 (newly registered), `n = 0` satisfies `0 ≤ 0 ≤ 1` — **passes**.
8. Block is accepted on mainnet; attacker has forged a block without ever touching mainnet key material. [5](#0-4)
