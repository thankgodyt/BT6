Audit Report

## Title
`finTransferExtension` Forwards Full `msg.value` to Wormhole After Native ETH Recipient Payment, Causing `finTransfer` Revert When Contract Has Insufficient Pre-existing ETH — (`evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol`)

## Summary

`OmniBridgeWormhole.finTransferExtension` calls `_wormhole.publishMessage{value: msg.value}(...)` using the original `msg.value` of the transaction. When `payload.tokenAddress == address(0)`, the base `OmniBridge.finTransfer` has already spent `payload.amount` wei sending ETH to the recipient before `finTransferExtension` is invoked. If the contract's pre-existing ETH balance `B < payload.amount`, the relayer must supply the shortfall via `msg.value`, but then the Wormhole call attempts to forward the full `msg.value` when only `msg.value - payload.amount` remains, causing the entire transaction to revert. This is directly inconsistent with `initTransferExtension`, which correctly computes the residual value before forwarding it.

## Finding Description

In `OmniBridge.finTransfer`, when `payload.tokenAddress == address(0)`, `payload.amount` wei is sent to the recipient before `finTransferExtension` is called: [1](#0-0) 

Control then passes to `finTransferExtension`: [2](#0-1) 

The contract's available ETH at the point of the Wormhole call is `B + msg.value - payload.amount`, where `B` is the pre-existing contract balance. The call attempts to forward `msg.value`. This succeeds only if `B >= payload.amount`. When `B < payload.amount` — which occurs on new deployments or when outbound ETH flows exceed inbound flows — the relayer must supply the shortfall as part of `msg.value`. In that case, `B + msg.value - payload.amount < msg.value`, and the Wormhole call reverts due to insufficient ETH. The entire transaction reverts, including the `completedTransfers[payload.destinationNonce] = true` write at line 287, so the nonce is not consumed and the relayer cannot make progress.

By contrast, `initTransfer` correctly subtracts the locked amount before computing the value forwarded to Wormhole: [3](#0-2) [4](#0-3) 

`finTransferExtension` lacks the equivalent subtraction, making the two paths asymmetric.

## Impact Explanation

When the destination-chain `OmniBridgeWormhole` contract holds insufficient ETH to cover `payload.amount` from its pre-existing balance, every relayer attempt to finalize a native ETH transfer reverts. Because there is no `cancelTransfer` or withdrawal path in the contract, the source-chain ETH locked by `initTransfer` has no built-in recovery mechanism. The only workaround — manually pre-funding the destination contract via `receive()` — is not part of the protocol design and requires an out-of-pocket ETH contribution. This constitutes permanent freezing of bridged native ETH funds, matching the critical impact class of "permanent freezing of bridged funds across EVM chains." [5](#0-4) 

## Likelihood Explanation

Any unprivileged relayer calling `finTransfer` for a native ETH payload triggers this path. The condition `B < payload.amount` is realistic and common: it applies to every new `OmniBridgeWormhole` deployment before any reverse-direction ETH flows have accumulated, and to any deployment where outbound ETH transfers exceed inbound ones. No special role, key, or collusion is required. The Wormhole variant is deployed on Arbitrum and Base, where the native token is ETH, making this path reachable in production. [6](#0-5) 

## Recommendation

In `finTransferExtension`, compute the Wormhole fee as the ETH remaining after the recipient payment, mirroring the pattern used in `initTransferExtension`:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload
) internal override {
    uint256 wormholeFee = payload.tokenAddress == address(0)
        ? msg.value - payload.amount
        : msg.value;

    bytes memory messagePayload = bytes.concat(
        bytes1(uint8(MessageType.FinTransfer)),
        bytes1(payload.originChain),
        Borsh.encodeUint64(payload.originNonce),
        bytes1(omniBridgeChainId),
        Borsh.encodeAddress(payload.tokenAddress),
        Borsh.encodeUint128(payload.amount),
        Borsh.encodeString(payload.feeRecipient)
    );
    _wormhole.publishMessage{value: wormholeFee}(
        wormholeNonce,
        messagePayload,
        _consistencyLevel
    );
    wormholeNonce++;
}
``` [6](#0-5) 

## Proof of Concept

1. Deploy `OmniBridgeWormhole` on Arbitrum Sepolia with zero pre-existing ETH balance.
2. On the source chain, call `initTransfer(address(0), 1 ether, 0, nativeFee, recipient, "")` with `msg.value = 1 ether + nativeFee + wormholeFee`. ETH is locked in the source contract.
3. NEAR produces a signed `TransferMessagePayload` with `tokenAddress = address(0)`, `amount = 1 ether`.
4. A relayer calls `finTransfer(sig, payload)` on the destination `OmniBridgeWormhole`, attaching `msg.value = wormholeFee` (the minimum needed to pay Wormhole). The contract has `B = 0`, so `B + msg.value = wormholeFee < 1 ether = payload.amount`. The recipient payment at line 319 fails immediately — the relayer must attach at least `1 ether + wormholeFee`.
5. Relayer retries with `msg.value = 1 ether + wormholeFee`. Recipient payment succeeds. Contract balance is now `wormholeFee`. `finTransferExtension` attempts `publishMessage{value: 1 ether + wormholeFee}` — only `wormholeFee` remains. Wormhole call reverts.
6. Entire transaction reverts; `completedTransfers[nonce]` is not set. Source-chain ETH remains locked with no protocol-level recovery path. [7](#0-6) [1](#0-0)
