### Title
Stale `branch_id` in `PsbtWrapper` Causes Signed Zcash Transactions to Be Rejected After Network Upgrade, Temporarily Locking Bridge UTXOs — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

---

### Summary

`PsbtWrapper` computes and serializes `branch_id` at PSBT construction time. If a network upgrade (e.g., Nu6 → Nu6_1) activates between PSBT construction and signing, the stored `branch_id` is stale. The sighash computed in `get_hash_to_sign` uses the stale `branch_id`, producing a signature that is invalid under the post-upgrade consensus rules. The signed transaction is rejected by the Zcash network, and the bridge UTXOs are temporarily locked.

---

### Finding Description

**Step 1 — PSBT construction with stale `branch_id`:**

In `ft_on_transfer_callback`, `PsbtWrapper::new` is called with `last_block_height` obtained from a cross-contract promise. The `branch_id` is computed once via `get_branch_id(current_height, config)` and stored in the struct field. [1](#0-0) [2](#0-1) 

**Step 2 — `branch_id` serialized into `psbt_hex`:**

`to_bytes()` encodes the `branch_id` as a single byte (7=Nu6, 8=Nu6_1, 9=Nu6_2) and stores it in `BTCPendingInfo.psbt_hex`. [3](#0-2) 

**Step 3 — `deserialize` faithfully restores the stale `branch_id`:**

When `sign_btc_transaction` is called later, `get_psbt()` calls `PsbtWrapper::deserialize`, which reads back the stored byte and reconstructs the original (now stale) `branch_id`. [4](#0-3) [5](#0-4) 

**Step 4 — `get_hash_to_sign` uses the stale `branch_id`:**

`internal_sign_btc_transaction` calls `get_psbt().get_hash_to_sign(sign_index, &public_keys)`, which passes `self.branch_id` (the stale Nu6 value) directly into the sighash computation. [6](#0-5) [7](#0-6) 

**Step 5 — Final transaction also encodes the stale `branch_id`:**

`get_zcash_tx` / `extract_tx_bytes_with_sign` also uses `self.branch_id`, so the serialized transaction carries the Nu6 `consensus_branch_id` field. [8](#0-7) 

**The activation heights are hardcoded:** [9](#0-8) [10](#0-9) 

Under ZIP-244, the `consensus_branch_id` is committed to in the v5 transaction sighash. A Nu6_1 node rejects any transaction whose `consensus_branch_id` field is Nu6, because the signature was computed over a hash that includes the wrong branch identifier.

---

### Impact Explanation

- UTXOs are removed from the bridge's UTXO set at PSBT creation time (via `generate_vutxos`).
- After all inputs are signed, the state transitions to `PendingVerify`, waiting for `verify_withdraw` to be called with a confirmed on-chain transaction.
- The signed transaction is rejected by the Zcash network; it will never confirm.
- The bridge UTXOs are locked in `PendingVerify` state until an RBF is initiated.

**Recovery path:** `withdraw_rbf` → `generate_psbt_from_original_psbt_and_new_output` with the current (post-upgrade) `last_block_height` recomputes the correct `branch_id` and creates a new signable PSBT. This is a user/operator action and is not automatic. [11](#0-10) [12](#0-11) 

Impact: **Medium** — temporary locking of bridged funds requiring user/operator RBF intervention to recover.

---

### Likelihood Explanation

- The window is narrow: only withdrawals initiated in the blocks immediately before a scheduled network upgrade activation height are affected.
- Network upgrades are publicly announced well in advance; operators can pause the bridge (`#[pause]`) around the activation height.
- No adversarial action is required beyond initiating a normal withdrawal at an unfortunate time.
- Likelihood: **Low** in practice, but the path is concrete and locally testable.

---

### Recommendation

Re-derive `branch_id` from the current block height at signing time rather than trusting the serialized value. In `internal_sign_btc_transaction`, after deserializing the PSBT, overwrite `branch_id` with `config.chain.get_branch_id(current_block_height)` before calling `get_hash_to_sign`. Alternatively, add a guard in `sign_btc_transaction` that rejects signing if the deserialized `branch_id` does not match the current consensus branch, forcing an RBF before signing can proceed.
