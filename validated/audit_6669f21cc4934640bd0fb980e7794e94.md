### Title
Fire-and-Forget `burn().detach()` After Failed Safe-Mint Leaves UTXO Unprotected, Enabling Potential Double-Mint - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary
In `safe_mint_callback`, when the `safe_mint` cross-contract call returns 0 (indicating the receiver did not consume the tokens and a refund is required), the bridge removes the deposit UTXO from `verified_deposit_utxo` and then fires a `burn()` call with `.detach()` — a fire-and-forget pattern with no error-handling callback. If the burn fails silently for any reason, the UTXO is permanently unprotected while unbacked nBTC tokens remain in the bridge's balance. A relayer can then re-submit the same BTC UTXO through the standard `verify_deposit` path, minting a second batch of nBTC against the same on-chain BTC output.

### Finding Description
The vulnerable code is in `safe_mint_callback` inside `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`. When `is_refund_required()` returns `true` (i.e., `safe_mint` returned `U128(0)`), the following sequence executes:

```rust
// Step 1 – UTXO protection is removed immediately
self.data_mut()
    .verified_deposit_utxo
    .remove(&pending_utxo_info.utxo_storage_key);

// Step 2 – burn is fire-and-forget; failure is silently ignored
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(env::current_account_id(), mint_amount, relayer_account_id, U128(0))
    .detach();                                          // ← no callback

// Step 3 – NEAR refund is also fire-and-forget
Promise::new(env::signer_account_id())
    .transfer(self.required_balance_for_safe_deposit())
    .detach();                                          // ← no callback
``` [1](#0-0) 

The UTXO is removed from `verified_deposit_utxo` **before** the burn is confirmed. The `verify_deposit_callback` (standard deposit path) guards against re-use with:

```rust
require!(
    self.data_mut()
        .verified_deposit_utxo
        .insert(pending_utxo_info.utxo_storage_key.clone()),
    "Already deposit utxo"
);
``` [2](#0-1) 

Because the UTXO key was removed in step 1, this guard no longer blocks re-submission of the same UTXO. If the `burn()` in step 2 fails silently, the bridge holds `mint_amount` nBTC that should have been destroyed, and the same BTC UTXO can be re-deposited to mint a second `mint_amount` of nBTC — resulting in 2× nBTC supply backed by 1× BTC.

This is the direct NEAR analog of the Solidity `.transfer()` vulnerability: both are fund-transfer operations with no error-handling path. Solidity's `.transfer()` reverts the caller on failure (at least preventing silent inconsistency), whereas NEAR's `.detach()` silently discards the failure, leaving contract state permanently inconsistent.

### Impact Explanation
If the `burn()` call fails:
- `verified_deposit_utxo` no longer contains the UTXO key.
- The bridge holds `mint_amount` nBTC that are unbacked (should have been burned).
- A relayer can call `verify_deposit` (standard path) with the same BTC transaction bytes and `vout`, pass the light-client proof check (the BTC transaction is already confirmed on-chain), and mint a fresh `mint_amount` of nBTC to the user.
- Result: unauthorized minting — nBTC supply exceeds the BTC held by the bridge.

This matches the **Critical** allowed impact: *Unauthorized minting of nBTC*.

### Likelihood Explanation
The refund path is reachable by any user who creates a safe deposit (`deposit_msg.safe_deposit = Some(..)`) pointing to a receiver contract they control that returns `U128(0)` from `ft_on_transfer`. This is a standard, unprivileged user action. The `burn()` call can fail if:
- The nBTC contract is paused at the moment the callback executes (a realistic operational scenario during upgrades or incidents).
- The gas budget `GAS_FOR_BURN_CALL` is insufficient for the nBTC `burn` implementation (a configuration risk).
- The bridge's nBTC balance is unexpectedly zero due to a race condition with another concurrent operation.

Because the attacker controls the timing of the deposit and can observe contract state, they can attempt the re-deposit immediately after the `safe_mint_callback` executes, before any manual remediation.

### Recommendation
Replace the fire-and-forget `.detach()` pattern with a chained callback that checks the burn result and, on failure, re-inserts the UTXO key into `verified_deposit_utxo` to restore protection:

```rust
ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
    .with_static_gas(GAS_FOR_BURN_CALL)
    .burn(env::current_account_id(), mint_amount, relayer_account_id, U128(0))
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(GAS_FOR_BURN_CALLBACK)
            .safe_mint_burn_callback(
                pending_utxo_info.utxo_storage_key.clone(),
                mint_amount,
            ),
    );
```

In `safe_mint_burn_callback`, if `is_promise_success()` is false, re-insert the UTXO key into `verified_deposit_utxo` to prevent re-deposit, and emit an alert event for operator intervention. This mirrors the pattern already used correctly in `transfer_nbtc_callback` and `withdraw_protocol_fee_callback` in `token_transfer.rs`. [3](#0-2) 

### Proof of Concept
1. Attacker deploys a NEAR contract `attacker.near` whose `ft_on_transfer` always returns `U128(0)`.
2. Attacker registers `attacker.near` in the `post_action_receiver_id_white_list` — or uses any already-whitelisted receiver that can be made to return 0.
3. Attacker sends BTC to the bridge deposit address derived from a `DepositMsg` with `safe_deposit = Some(SafeDepositMsg { msg: "<msg targeting attacker.near>" })`.
4. Relayer calls `verify_deposit_v2` with the BTC proof. `verify_safe_deposit_callback` fires, then `safe_mint` is called on nBTC, which calls `ft_transfer_call` to `attacker.near`.
5. `attacker.near.ft_on_transfer` returns `U128(0)`. nBTC refunds the tokens back to the bridge.
6. `safe_mint_callback` runs: `is_refund_required()` → `true`; UTXO removed from `verified_deposit_utxo`; `burn().detach()` fires.
7. Attacker (or a colluding relayer) ensures the nBTC contract is paused at this instant (e.g., by front-running with a governance call during a known maintenance window), causing the detached `burn()` to fail silently.
8. Attacker immediately calls `verify_deposit` (standard path) with the same `tx_bytes` and `vout`. The light-client proof passes (BTC tx is confirmed). `verify_deposit_callback` inserts the UTXO key (succeeds because it was removed in step 6) and calls `internal_mint_promise`, minting a second `mint_amount` of nBTC to the attacker's account.
9. Attacker now holds `mint_amount` nBTC; the bridge also holds `mint_amount` unburned nBTC — total nBTC supply is 2× the BTC deposited. [4](#0-3)

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }
```

    #[private]
    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
