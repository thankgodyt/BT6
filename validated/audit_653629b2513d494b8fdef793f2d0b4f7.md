### Title
Unbounded `extra_msg` in `DepositMsg` Stored On-Chain Without Length Validation — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `extra_msg: Option<String>` field in `DepositMsg` has no length limit and no content validation. When a refund is requested, the entire `DepositMsg` — including an arbitrarily large `extra_msg` — is serialized to JSON and stored verbatim in `RefundRequest.deposit_msg_json` on-chain. The `request_refund_callback` is allocated only 20 Tgas. A sufficiently large `extra_msg` can exhaust this gas budget during serialization and storage write, causing the callback to panic and leaving the refund flow in a broken state. This is a direct analog to the Sablier bug: user-controlled string data passed through without length or content checks.

---

### Finding Description

`DepositMsg` is defined in `contracts/satoshi-bridge/src/deposit_msg.rs`:

```rust
pub struct DepositMsg {
    pub recipient_id: AccountId,
    pub post_actions: Option<Vec<PostAction>>,
    pub extra_msg: Option<String>,       // ← no length limit
    pub safe_deposit: Option<SafeDepositMsg>,
    pub refund_address: Option<String>,
}
``` [1](#0-0) 

The `extra_msg` field carries no length constraint. By contrast, the `tx_bytes` field in `request_refund` has an explicit cap with a detailed rationale comment:

```rust
pub(crate) const MAX_REQUEST_REFUND_TX_BYTES: usize = 200_000;
// ...
require!(
    tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
    "tx_bytes too large for refund request"
);
``` [2](#0-1) [3](#0-2) 

No equivalent cap exists for `extra_msg`. In `request_refund_callback`, the full `DepositMsg` (including `extra_msg`) is serialized to JSON and stored in `RefundRequest`:

```rust
let refund_request = RefundRequest {
    deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [4](#0-3) 

This callback is allocated only `GAS_FOR_REQUEST_REFUND_CALLBACK = 20 Tgas`: [5](#0-4) 

NEAR charges gas proportional to bytes written to storage. A multi-hundred-KB `extra_msg` embedded in `deposit_msg_json` can exhaust the 20 Tgas budget during the `serde_json::to_string` + borsh storage write, causing the callback to panic.

Additionally, `extra_msg` is emitted unsanitized in events:

```rust
Event::RefundRequested {
    deposit_msg: deposit_msg.clone(),
    ...
}
.emit();
``` [6](#0-5) 

The `DepositMsg` (including `extra_msg`) is serialized directly into the event log via `serde_json`, with no content filtering. The field is documented as "Used to support other dApps extending based on verify_deposit," meaning downstream dApps consume it without any bridge-side sanitization.

---

### Impact Explanation

**Low — Publicly reachable panic-driven fault in production bridge/token paths without direct theft.**

An attacker-crafted `extra_msg` of sufficient size causes `request_refund_callback` to run out of gas and panic. The refund request is never stored. The user's BTC deposit remains on-chain but the refund path is broken for that specific `DepositMsg`. Repeated exploitation can disrupt the refund system for any deposit whose `DepositMsg` contains a large `extra_msg`. Downstream dApps that consume `extra_msg` without their own sanitization are also exposed to injection-class issues analogous to the Sablier XSS.

---

### Likelihood Explanation

**Medium.** Any unprivileged user can construct a `DepositMsg` with an arbitrarily large `extra_msg`, embed it in a BTC deposit transaction, and then call `request_refund`. No privileged role is required. The only prerequisite is a valid on-chain BTC deposit, which is a normal bridge user action.

---

### Recommendation

1. Add a `MAX_EXTRA_MSG_LEN` constant (e.g., 256 bytes) and enforce it in `internal_request_refund` before the light-client call, mirroring the `MAX_REQUEST_REFUND_TX_BYTES` check on `tx_bytes`.
2. Apply the same limit in `verify_deposit` wherever `extra_msg` is processed.
3. Consider allowlist-based content validation (e.g., printable ASCII only) for `extra_msg` if it is intended to be forwarded to downstream dApps, analogous to the Sablier recommendation of restricting to `A-Za-z0-9`.
4. Apply a similar length cap to `PostAction.memo` and `SafeDepositMsg.msg`.

---

### Proof of Concept

1. Attacker constructs a `DepositMsg` with `extra_msg` set to a string of ~500 KB of arbitrary data.
2. Attacker sends a real BTC deposit to the address derived from `get_deposit_path(&deposit_msg)`.
3. After confirmation, attacker calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee)`.
4. `internal_request_refund` checks `tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES` — passes (tx_bytes is small).
5. No check on `extra_msg` length — passes unconditionally.
6. Light-client verification succeeds; `request_refund_callback` is scheduled with 20 Tgas.
7. Inside the callback, `serde_json::to_string(&deposit_msg)` produces a ~500 KB JSON string; the subsequent borsh storage write exhausts the 20 Tgas budget.
8. Callback panics; refund request is never stored; the deposit UTXO is not marked verified.
9. The refund path for this deposit is broken; operator intervention is required to resolve the stuck state.
