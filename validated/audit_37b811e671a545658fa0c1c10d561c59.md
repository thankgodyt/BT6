### Title
Unconditional Peras Certificate Acceptance Enables Arbitrary Chain Weight Injection via Crafted Peer Messages - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. Any unprivileged peer can send a crafted `PerasCert` naming any block as the boosted block; the certificate is accepted, stored, and its `PerasWeight` boost is applied to chain selection. This directly manipulates `wsvTotalWeight` and can cause an honest node to prefer a non-canonical chain. A compounding unit-mismatch in `stakeAboveThreshold` means the quorum gate that should precede certificate forging is also trivially bypassable.

### Finding Description

**Root cause 1 — `validatePerasCert` stub (primary)** [1](#0-0) 

The degenerate `instance StandardHash blk => BlockSupportsPeras blk` is the only instance in the production source tree. Its `validatePerasCert` ignores every field of the certificate and always returns `Right`, assigning the configured `perasWeight` boost to whatever block the attacker names. [2](#0-1) 

**Attacker-controlled entry path**

`processCerts` in the object-diffusion mini-protocol writer calls `validatePerasCert mkPerasParams` directly on peer-supplied certificates: [3](#0-2) [4](#0-3) 

A peer sends a `[PerasCert blk]` batch. Every certificate whose `PerasRoundNo` is not already in the DB is passed to `validatePerasCert`, which returns `Right` unconditionally. The validated certificate is then stored and its `pcCertBoostedBlock` point receives a `PerasWeight` boost in the `PerasWeightSnapshot`.

**How the boost reaches chain selection**

`implGetWeightSnapshot` builds the `PerasWeightSnapshot` from every stored certificate: [5](#0-4) 

`wsvTotalWeight` adds `BlockNo` and `wsvWeightBoost` together; `preferCandidate` switches to any chain whose total weight exceeds the current chain's: [6](#0-5) 

An attacker who injects a certificate boosting a block on their own fork can make that fork's `wsvTotalWeight` exceed the honest chain's, causing `chainSelection` to switch.

**Root cause 2 — `stakeAboveThreshold` unit mismatch (compounding)**

The quorum gate that should prevent certificate forging without sufficient stake compares a `PerasVoteStake` (whose unit is explicitly unresolved) against a relative threshold (`3/4`): [7](#0-6) 

If `PerasVoteStake` values are populated from absolute ledger lovelace (e.g., `1_000_000`), the comparison `1000000 >= 0.75 + 0.02` is trivially true, meaning a single voter with any positive stake can forge a certificate through the vote-aggregation path as well. [8](#0-7) 

### Impact Explanation

**High — Chain selection bug.** An unprivileged peer can send one crafted `PerasCert` per Peras round (deduplicated by `PerasRoundNo`). Each accepted certificate injects up to `perasWeight = 15` units of extra weight onto an attacker-chosen block. With `k = 2160` on mainnet, an attacker needs to inject roughly `k / perasWeight ≈ 144` certificates (one per round) to make a fork of zero honest blocks outweigh the honest chain. Because `takeVolatileSuffix` uses the same weight arithmetic, the immutability boundary is also shifted, potentially causing the node to treat adversarially-boosted blocks as immutable. [9](#0-8) [10](#0-9) 

### Likelihood Explanation

**High.** The object-diffusion mini-protocol for Peras certificates is wired into the production `ChainDB` writer path. Any connected peer can send a `[PerasCert blk]` message. No key material, stake, or privileged role is required. The only deduplication guard is the `PerasRoundNo` set, which an attacker can trivially exhaust by using a fresh round number per certificate.

### Recommendation

1. **Short term**: Gate `processCerts` behind a feature flag that is disabled until a real `validatePerasCert` implementation (verifying aggregate signatures, committee membership, and the boosted block's existence on a known chain) is in place. Do not ship the object-diffusion writer with the stub instance active.
2. **Long term**: Resolve the `PerasVoteStake` unit ambiguity documented in `stakeAboveThreshold` before enabling the vote-aggregation path. Enforce normalization at the point where `PerasVoteStakeDistr` is constructed from ledger data, and add property-based fuzz tests that verify `stakeAboveThreshold` is monotone and that no single voter with sub-quorum relative stake can satisfy the threshold.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

wsvTotalWeight :: WeightedSelectView proto -> PerasWeight

wsvTotalWeight wsv =

instance Ord (TiebreakerView proto) => Ord (WeightedSelectView proto) where
  compare =
    mconcat
      [ compare `on` wsvTotalWeight
      , compare `on` wsvTiebreaker
      ]

data WeightedSelectViewReasonForSwitch p
  = Heavier (Comparing PerasWeight)
  | WeightedSelectViewTiebreak (ReasonForSwitch (TiebreakerView p))

deriving instance
  Show (ReasonForSwitch (TiebreakerView p)) => Show (WeightedSelectViewReasonForSwitch p)

instance ChainOrder (TiebreakerView proto) => ChainOrder (WeightedSelectView proto) where
  type ChainOrderConfig (WeightedSelectView proto) = ChainOrderConfig (TiebreakerView proto)
  type ReasonForSwitch (WeightedSelectView proto) = WeightedSelectViewReasonForSwitch proto

  preferCandidate cfg ours cand =
    case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
      LT -> ShouldSwitch (Heavier $ Comparing (wsvTotalWeight ours) (wsvTotalWeight cand))
      EQ -> case preferCandidate cfg (wsvTiebreaker ours) (wsvTiebreaker cand) of

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14. In the latter case, the chain fragment has
-- total weight @2 + 2 * 14 = 30@.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
  deriving (Eq, Generic, NoThunks, ToCBOR, FromCBOR)
  deriving Show via Quiet SecurityParam

-- | The maximum amount of weight we can roll back.
maxRollbackWeight :: SecurityParam -> PerasWeight
maxRollbackWeight = PerasWeight . unNonZero . maxRollbacks
