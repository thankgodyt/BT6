The vulnerability is real. The `if let Some(msg_templates)` guard in `check_deposit_msg` silently skips msg validation when no templates are registered for a whitelisted receiver, allowing any arbitrary `msg` to pass through to `ft_on_transfer`.

---

### Title
Whitelisted Receiver With No Registered Templates Bypasses `msg` Validation in `check_deposit_msg` — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary
`check_deposit_msg` only validates `post_action.msg` when `post_action_msg_templates` contains an entry for the receiver. If the DAO has whitelisted a receiver but never called `extend_post_action_msg_templates` for it, the entire msg-validation block is skipped via `if let Some(...)`, and `check_deposit_msg` returns `Some(post_actions)` with an unconstrained `msg`. The resulting `ft_transfer_call` dispatched by `handle_post_action` carries attacker-controlled content to the whitelisted receiver's `ft_on_transfer`.

### Finding Description

In `contracts/satoshi-bridge/src/deposit_msg.rs`, the msg-validation block is guarded by an `if let Some(...)`:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)   // returns None → block skipped entirely
{
    let is_match = ...;
    if !is_match {
        return None;
    }
}
``` [1](#0-0) 

When `post_action_msg_templates` has no entry for the receiver, `get(...)` returns `None`, the block is never entered, and validation is silently skipped. The function then falls through to return `Some(post_actions)`. [2](#0-1) 

`extend_post_action_receiver_id_white_list` and `extend_post_action_msg_templates` are entirely independent DAO operations with no coupling — a receiver can be whitelisted without any templates ever being registered. [3](#0-2) [4](#0-3) 

The validated (or in this case, unvalidated) `post_actions` are passed through `verify_deposit_callback` → `internal_mint_promise` → nBTC `mint` → `handle_post_actions` → `handle_post_action`, which calls:

```rust
ext_ft_receiver::ext(receiver_id.clone())
    .ft_on_transfer(sender_id.clone(), amount.into(), msg)
``` [5](#0-4) 

The arbitrary attacker-supplied `msg` is delivered verbatim to the whitelisted receiver's `ft_on_transfer`.

### Impact Explanation

An unprivileged depositor can craft a BTC deposit whose `post_actions` field targets a whitelisted receiver that has no registered templates, and supply any `msg` string. The bridge will mint nBTC and dispatch an `ft_transfer_call` to that receiver with the attacker-controlled `msg`. This bypasses the bridge's msg-policy invariant — the entire purpose of `post_action_msg_templates` is to constrain what operations a depositor can trigger on downstream DeFi protocols. With no templates registered, that constraint is entirely absent. Depending on the whitelisted receiver (e.g., a lending protocol like Burrowland), an attacker could trigger unintended operations (borrows, collateral changes, etc.) on their own deposited nBTC, potentially causing loss of their own funds or exploiting receiver-side logic that assumes only pre-approved msg shapes arrive via `ft_on_transfer`.

**Impact: Medium** — Bypass of bridge msg-validation policy; unconstrained `ft_transfer_call` dispatched to a whitelisted receiver.

### Likelihood Explanation

The precondition — a whitelisted receiver with no templates — is a realistic deployment state. The DAO may whitelist a receiver first and add templates later, or may intentionally whitelist a receiver that accepts any msg (e.g., a simple escrow). There is no on-chain enforcement preventing this state. Any depositor who observes the whitelist (via `list_post_action_msg_templates`) can immediately exploit the gap.

### Recommendation

Replace the `if let Some(...)` pattern with an explicit two-branch check: if no templates are registered for a whitelisted receiver, **reject** the post_action rather than skipping validation:

```rust
match self.data().post_action_msg_templates.get(&post_action.receiver_id) {
    Some(msg_templates) => {
        // existing match logic
        if !is_match { return None; }
    }
    None => {
        // No templates registered → reject any non-empty msg,
        // or reject unconditionally to enforce explicit opt-in.
        Event::InvalidPostAction { ... }.emit();
        return None;
    }
}
```

Alternatively, enforce at the management layer that `extend_post_action_receiver_id_white_list` requires at least one template to be registered simultaneously.

### Proof of Concept

```rust
// 1. DAO whitelists burrowland but registers NO templates.
unit_env.contract.extend_post_action_receiver_id_white_list(vec![burrowland_id()]);
// post_action_msg_templates has NO entry for burrowland_id()

// 2. Depositor crafts arbitrary msg.
let result = unit_env.contract.check_deposit_msg(
    DepositMsg {
        recipient_id: recipient_id(),
        post_actions: Some(vec![PostAction {
            receiver_id: burrowland_id(),
            amount: U128(10),
            memo: None,
            msg: r#"{"Execute":{"actions":[{"Borrow":{"token_id":"usdc","amount":"999999999"}}]}}"#.to_string(),
            gas: Some(Gas::from_tgas(50)),
        }]),
        extra_msg: None,
        safe_deposit: None,
        refund_address: None,
    },
    100,
);
// ASSERT: returns Some — arbitrary msg accepted, policy bypassed
assert!(result.is_some());

// 3. After templates are registered, the same msg is rejected.
unit_env.contract.extend_post_action_msg_templates(
    burrowland_id(),
    HashSet::from([r#"{"Execute":{"actions":[{"IncreaseCollateral":{...}}]}}"#.to_string()]),
);
let result2 = unit_env.contract.check_deposit_msg(/* same msg as above */, 100);
assert!(result2.is_none()); // now correctly rejected
```

The existing test suite at `contracts/satoshi-bridge/src/unit/post_action.rs` already demonstrates the post-template case passing and the arbitrary-msg case failing after templates are set [6](#0-5) 
— but there is no test covering the no-templates state, which is where the bypass lives. [1](#0-0)
