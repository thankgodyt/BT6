### Title
Missing Caller-Ownership Check in `withdraw_rbf` Allows Any Account to RBF Another User's Pending Withdrawal — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`withdraw_rbf` is a public, unpermissioned function that accepts an arbitrary `original_btc_pending_verify_id` and caller-supplied `output` vector. It never verifies that the pending transaction identified by that ID belongs to the caller. Any NEAR account can invoke it against a victim's pending withdrawal, passing attacker-controlled outputs, which are forwarded directly into the RBF PSBT construction pipeline.

### Finding Description
`withdraw_rbf` (bridge.rs lines 258–274) is documented as the mechanism by which *the user* accelerates their own withdrawal by increasing the gas fee. However, the implementation uses `env::predecessor_account_id()` as the acting `account_id` and performs no check that `original_btc_pending_verify_id` is owned by that caller:

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not owner
    self.require_pending_sign_capacity(&account_id);  // ← capacity checked on caller
    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller's ID forwarded as owner
        original_btc_pending_verify_id,      // ← can belong to any user
        output,                              // ← fully attacker-controlled outputs
        chain_specific_data,
    );
}
``` [1](#0-0) 

Contrast this with `cancel_withdraw`, the privileged (DAO/Operator-only) counterpart, which explicitly resolves the *owner* of the pending transaction from on-chain state before proceeding:

```rust
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
self.cancel_withdraw_chain_specific(user_account_id, ...);
``` [2](#0-1) 

`withdraw_rbf` performs no equivalent ownership lookup. The `require_pending_sign_capacity` guard is evaluated against the *caller*, not the pending transaction's owner, so it provides no protection against acting on a victim's pending ID.

The `output` parameter — a `Vec<TxOut>` containing Bitcoin recipient addresses and amounts — is passed directly into `withdraw_rbf_chain_specific` and ultimately into PSBT construction. Because the caller controls both which pending transaction is targeted and what the replacement outputs are, an attacker can supply outputs that redirect the BTC to an address they control.

### Impact Explanation
An unprivileged attacker who knows (or can enumerate) a victim's `btc_pending_verify_id` can submit an RBF transaction that replaces the victim's pending withdrawal with a new PSBT whose outputs redirect the BTC to the attacker's Bitcoin address. The bridge's MPC signing pipeline then signs and broadcasts this attacker-constructed transaction. This constitutes unauthorized redirection of bridge-controlled funds — a critical impact matching "Chain-signature, PSBT, or transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds."

### Likelihood Explanation
`btc_pending_verify_id` values are derived from PSBT content and emitted in `GenerateBtcPendingInfo` events, making them publicly observable on-chain. The function has no access control, no yoctoNEAR deposit requirement, and no ownership assertion. Any NEAR account can call it at any time after a victim initiates a withdrawal. [1](#0-0) 

### Recommendation
Add an ownership check at the start of `withdraw_rbf` that mirrors the pattern used in `cancel_withdraw`:

```rust
pub fn withdraw_rbf(...) {
    let caller = env::predecessor_account_id();
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the owner can RBF their own withdrawal");
    self.require_pending_sign_capacity(&caller);
    self.withdraw_rbf_chain_specific(caller, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept
1. Alice calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message, initiating a withdrawal. The bridge emits `GenerateBtcPendingInfo { account_id: alice, btc_pending_id: "abc123" }`.
2. Bob observes the event and learns `btc_pending_id = "abc123"`.
3. Bob calls `withdraw_rbf("abc123", [TxOut { value: alice_amount, script_pubkey: bob_btc_address }], None)`.
4. Inside `withdraw_rbf`, `account_id = bob`. No check is made that `"abc123"` belongs to Alice.
5. `withdraw_rbf_chain_specific(bob, "abc123", bob_outputs, ...)` is invoked, constructing a replacement PSBT with Bob's output.
6. The MPC signing pipeline signs the replacement transaction; Bob's Bitcoin address receives Alice's BTC. [1](#0-0) [3](#0-2)
