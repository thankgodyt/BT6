### Title
Attacker-Controlled `sender_id` in `handle_post_action` Enables Impersonation of Any NEAR Account to Whitelisted Receivers - (File: contracts/nbtc/src/lib.rs)

### Summary
The `handle_post_action` function in the nbtc contract calls `ft_on_transfer` on whitelisted receiver contracts with a `sender_id` that is derived directly from the `recipient_id` field of the `DepositMsg`. Because `DepositMsg` is embedded in the BTC transaction output script and is entirely attacker-controlled, any unprivileged actor can set `recipient_id` to any arbitrary NEAR account. The whitelisted receiver then sees that arbitrary account as the token sender, with no way to distinguish a legitimate user-initiated transfer from an attacker-crafted one.

### Finding Description
The deposit flow is:

1. An attacker crafts a BTC transaction whose output script encodes a `DepositMsg` with `recipient_id = <victim_account>` and `post_actions = [{ receiver_id: <whitelisted_dapp>, amount, msg }]`.
2. A relayer calls `bridge.verify_deposit(...)`, which calls `nbtc.mint(mint_account_id = victim_account, ..., post_actions)`.
3. Inside `nbtc.mint`, tokens are minted to `victim_account`, then `handle_post_actions(sender_id = victim_account, post_actions)` is scheduled.
4. `handle_post_actions` dispatches `handle_post_action(sender_id = victim_account, receiver_id = whitelisted_dapp, amount, memo, msg)`.
5. `handle_post_action` executes `internal_transfer(&victim_account, &whitelisted_dapp, amount, ...)` and then calls `whitelisted_dapp.ft_on_transfer(sender_id = victim_account, amount, msg)`.

The whitelisted receiver contract receives `ft_on_transfer` with `sender_id = victim_account` — an account the attacker chose — and with `msg` being attacker-supplied content (unless `post_action_msg_templates` are configured for that receiver, in which case only the JSON structure is validated, not the values).

The `check_deposit_msg` validation enforces that `receiver_id` is on the whitelist and that `receiver_id != bridge`, but it does not restrict what `recipient_id` (which becomes `sender_id` in the callback) can be set to. [1](#0-0) [2](#0-1) [3](#0-2) 

### Impact Explanation
Any whitelisted receiver contract that uses the `sender_id` argument of `ft_on_transfer` to determine what action to perform — for example, crediting a user's internal balance, executing a pending order, or adjusting collateral — can be manipulated. The attacker can impersonate any NEAR account as the apparent token sender. If the receiver does not independently verify the origin of the call (e.g., by checking that `env::predecessor_account_id()` is the nbtc contract AND that the `sender_id` was legitimately initiated by that account), it may execute unintended state changes on behalf of the impersonated account. This maps to the allowed medium impact: harmful smart-contract behavior triggered by an unprivileged bridge user, without requiring any privileged role beyond the DAO having whitelisted at least one receiver. [4](#0-3) 

### Likelihood Explanation
The precondition is that the DAO has whitelisted at least one receiver contract (the intended production state, as the whitelist feature exists specifically to enable DeFi integrations). Once any receiver is whitelisted, any unprivileged actor who can send a BTC transaction — the standard bridge user — can craft a `DepositMsg` with an arbitrary `recipient_id` and target that receiver. The attacker bears the cost of the BTC deposit but gains the ability to invoke `ft_on_transfer` on the whitelisted receiver with any `sender_id` they choose. The likelihood is medium given that whitelisted integrations are an explicit design goal. [5](#0-4) 

### Recommendation
The `handle_post_action` function should not pass the user-supplied `recipient_id` as the `sender_id` to `ft_on_transfer`. Instead, it should pass the nbtc contract's own account ID (`env::current_account_id()`) as the `sender_id`, clearly signaling to receivers that the transfer originated from the bridge's post-action mechanism rather than from a user-initiated `ft_transfer_call`. Receiver contracts integrated with this bridge should be documented to treat `sender_id` in post-action callbacks as the bridge-controlled originator, not as an end-user identity. Additionally, `post_action_msg_templates` should be mandatory (not optional) for all whitelisted receivers to prevent arbitrary `msg` injection.

### Proof of Concept
1. DAO whitelists `dapp.near` as a post-action receiver (intended production operation).
2. Attacker sends BTC to the deposit address derived from:
   ```json
   {
     "recipient_id": "victim.near",
     "post_actions": [{
       "receiver_id": "dapp.near",
       "amount": "10000",
       "msg": "{\"action\":\"supply_collateral\"}",
       "gas": null
     }]
   }
   ```
3. Relayer submits `verify_deposit`. Bridge mints 10 000 nBTC to `victim.near`, then calls `handle_post_action(sender_id="victim.near", receiver_id="dapp.near", ...)`.
4. nbtc transfers 10 000 nBTC from `victim.near` to `dapp.near` and calls `dapp.near.ft_on_transfer(sender_id="victim.near", amount=10000, msg="{\"action\":\"supply_collateral\"}")`.
5. `dapp.near`, seeing `sender_id = "victim.near"`, credits `victim.near`'s collateral account — an action `victim.near` never authorized. [6](#0-5) [7](#0-6)

    pub fn handle_post_actions(&mut self, sender_id: AccountId, post_actions: Vec<PostAction>) {
        for post_action in post_actions {
            let PostAction {
                receiver_id,
                amount,
                memo,
                msg,
                gas,
            } = post_action;
            if let Some(gas) = gas {
                Self::ext(env::current_account_id())
                    .with_static_gas(gas)
                    .handle_post_action(sender_id.clone(), receiver_id, amount, memo, msg)
                    .detach();
            } else {
                Self::ext(env::current_account_id())
                    .handle_post_action(sender_id.clone(), receiver_id, amount, memo, msg)
                    .detach();
            }
        }
    }

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();

        deposit_msg: DepositMsg,

        if post_actions.is_empty() {
            Event::InvalidPostAction {
                index: None,
                err_msg: "empty post_actions.".to_string(),
            }
            .emit();
            return None;
        }
        // post_actions supports at most two.
        if post_actions.len() > MAX_POST_ACTIONS_NUM {
            Event::InvalidPostAction {
                index: None,
                err_msg: format!(
                    "The number({}) of post_actions exceeds the limit of {}.",
                    post_actions.len(),
                    MAX_POST_ACTIONS_NUM
                ),
            }
            .emit();
            return None;
        }
        let mut total_gas = 0;
        let mut total_amount = 0;
        for (index, post_action) in post_actions.iter().enumerate() {
            total_amount += post_action.amount.0;

            // deposit immediately drive the bridge's own ft_on_transfer flow
            // (e.g. TokenReceiverMessage::Withdraw) inside the relayer-paid
            // receipt, which is outside the intended deposit semantics.
            if post_action.receiver_id == env::current_account_id() {
                Event::InvalidPostAction {
                    index: Some(index),
                    err_msg: format!(
                        "The receiver_id({}) of the post_action cannot be the bridge itself.",
                        post_action.receiver_id
                    ),
                }
                .emit();
                return None;

                .data()
                .post_action_receiver_id_white_list
