### Title
Refund Request Front-Running Allows Attacker to Redirect BTC Refunds to Arbitrary Address - (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

Any unprivileged NEAR account can submit a `request_refund` for any unfinalized Bitcoin deposit UTXO with an attacker-controlled `refund_address`. Because there is no ownership check tying the caller to the deposit, an attacker can race the legitimate depositor, claim the refund slot for a given UTXO, and — if the DAO does not reject the request within the `unsafe_refund_timelock_sec` window — cause the BTC to be sent to the attacker's address. Even if the DAO acts in time, the legitimate user's refund path is blocked until the attacker's request is manually rejected.

---

### Finding Description

`request_refund` (and its callback `request_refund_callback`) accepts a caller-supplied `refund_address` with no verification that the caller has any relationship to the deposit. The only guard is:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 154-159
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This check is a no-op when `deposit_msg.refund_address` is `None` — the common case for standard deposits. [1](#0-0) 

The callback then stores the refund request keyed by `utxo_storage_key` and enforces a uniqueness invariant:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 543-547
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

Because the refund request slot is first-come-first-served and open to any caller, an attacker who submits `request_refund` before (or concurrently with) the legitimate user will win the slot. The stored `refund_address` is then used verbatim when `execute_refund` is called:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 323-324
let gas_fee = refund_request.gas_fee;
let refund_address = refund_request.refund_address.clone();
``` [3](#0-2) 

`execute_refund` itself carries no access-control restriction beyond the pause flag — any account can call it after the timelock elapses:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 581-589
#[payable]

    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,

``` [4](#0-3) 

The timelock applied to requests where `deposit_msg.refund_address` is `None` is `unsafe_refund_timelock_sec` (the longer, DAO-review window), not the shorter `refund_timelock_sec`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 216-227
if refund_request.deposit_msg().refund_address.is_some() {
    if is_privileged { 0 } else { config.refund_timelock_sec }
} else {
    config.unsafe_refund_timelock_sec
}
``` [5](#0-4) 

The longer timelock is a mitigation, not a prevention: if the DAO does not reject the attacker's request before `unsafe_refund_timelock_sec` expires, `execute_refund` can be called by anyone (including the attacker) and the BTC is sent to the attacker's address.

All inputs required to mount the attack — `deposit_msg`, `tx_bytes`, `vout`, and the Merkle proof — are publicly observable on the Bitcoin blockchain and in NEAR transaction history.

---

### Impact Explanation

**Medium / escalates to Critical on DAO inaction.**

- The attacker permanently blocks the legitimate depositor from submitting their own refund request for the affected UTXO (the duplicate check at line 544–547 rejects any subsequent attempt). [2](#0-1) 
- This creates a stuck bridge state that requires DAO/Operator intervention (`reject_refund`) before the user can recover their funds — matching the Medium impact class "stuck bridge state requiring operator intervention."
- If the DAO fails to reject within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the BTC is sent to the attacker's address — escalating to Critical: "Significant loss or theft of user funds."

---

### Likelihood Explanation

- All data needed to construct the attack (`deposit_msg`, `tx_bytes`, Merkle proof) is publicly available on Bitcoin and NEAR.
- No privileged role, leaked key, or social engineering is required.
- The attack is viable for any deposit where `deposit_msg.refund_address` is `None` that has not yet been finalized via `verify_deposit`.
- The attacker does not need to front-run in the traditional mempool sense — they can simply submit `request_refund` for any unfinalized UTXO they observe on Bitcoin before the legitimate user does.
- The `unsafe_refund_timelock_sec` window reduces the probability of successful theft but does not eliminate it, especially if the DAO is slow to respond or the timelock is short.

---

### Recommendation

1. **Bind the refund address to the deposit at deposit time**: Require `deposit_msg.refund_address` to be non-`None` for any permissionless refund request. Deposits without a pre-authorized refund address should only be refundable by a privileged role (DAO/Operator/RefundOperator).
2. **Restrict `request_refund` to the `recipient_id`**: If permissionless refunds without a pre-authorized address must be supported, require `env::predecessor_account_id() == deposit_msg.recipient_id` so only the intended NEAR recipient can claim the refund slot.
3. **Commit-reveal**: As suggested in the analogous DAO report, a commit-reveal scheme for `refund_address` would prevent front-running by hiding the target address until after the slot is claimed.

---

### Proof of Concept

1. Alice deposits BTC with `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The deposit is confirmed on Bitcoin but `verify_deposit` is never called (e.g., the deposit amount is below the minimum or the relayer is offline).
2. Bob (attacker) observes the unfinalized UTXO on Bitcoin and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
     refund_address = "bob_btc_address",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid Merkle proof>,
     gas_fee = None
   )
   ```
3. Bob's `request_refund_callback` succeeds and stores `RefundRequest { refund_address: "bob_btc_address", ... }` under Alice's UTXO key. [6](#0-5) 
4. Alice subsequently calls `request_refund` with her own address; her callback fails: `"Refund request already exists for this UTXO"`. [2](#0-1) 
5. If the DAO does not call `reject_refund` before `unsafe_refund_timelock_sec` elapses, Bob calls `execute_refund("alice_utxo_key", None)`.
6. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `refund_amount` to `"bob_btc_address"` — Alice's BTC is sent to Bob. [7](#0-6)
