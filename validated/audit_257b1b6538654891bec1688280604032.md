### Title
Single-Step Controller Transfer Without Zero-Address Check Enables Permanent Loss of nBTC Upgrade and Minting Controls - (File: contracts/nbtc/src/lib.rs)

---

### Summary

The `set_controller` function in the nBTC token contract performs an immediate, single-step, irreversible controller transfer with no zero-address validation and no two-step confirmation pattern. The `controller` role governs the most privileged operations in the nBTC contract, including arbitrary contract code deployment and full-access-key attachment. A mistaken or socially-engineered transfer to an uncontrolled address permanently locks these capabilities or hands them to an attacker.

---

### Finding Description

`contracts/nbtc/src/lib.rs` lines 94–98:

```rust
#[payable]
pub fn set_controller(&mut self, controller: AccountId) {
    assert_one_yocto();
    self.assert_controller();
    self.controller = controller;   // immediate, no confirmation, no zero-check
}
```

The `controller` field is the sole authorization gate for the following critical operations in `contracts/nbtc/src/migrate.rs`:

- **`attach_full_access_key`** (lines 26–29): adds an arbitrary full-access key to the nBTC contract account, granting the key holder unrestricted on-chain power over the contract.
- **`upgrade_and_migrate`** (lines 78–99): deploys arbitrary WASM bytecode to the nBTC contract, allowing complete replacement of contract logic.

And in `contracts/nbtc/src/lib.rs`:

- **`set_metadata`** (lines 282–319): modifies token metadata.
- **`set_withdraw_relayer_address`** (lines 324–328): redirects the legacy withdrawal relayer.

There is no pending-controller state, no acceptance step, and no zero-address (or equivalent NEAR account validity) guard. The `assert_controller` check (lines 336–339) only verifies the caller is the current controller; it does not validate the new address being written.

---

### Impact Explanation

**Scenario A — Typo / burned address (Medium → Critical):**
If the controller is set to an address that no one controls (e.g., a typo during the deployer-to-multisig handoff), the nBTC contract becomes permanently unupgradeable. The withdraw relayer address cannot be changed. No recovery path exists without a pre-existing full-access key on the contract account. This constitutes a stuck bridge state requiring operator intervention with no on-chain remedy.

**Scenario B — Attacker-controlled address (Critical):**
If the controller is set to an attacker-controlled address (social engineering, clipboard hijack, or a typo that resolves to an existing account the attacker controls):

1. Attacker calls `attach_full_access_key(attacker_pk)` — adds their own full-access key to the nBTC contract account.
2. With a full-access key, the attacker can sign any transaction as the nBTC contract itself, including direct calls to `mint` / `internal_deposit` bypassing all guards.
3. This enables **unauthorized minting of nBTC** — a Critical bridge impact.

Alternatively, the attacker calls `upgrade_and_migrate` with malicious WASM that removes all guards and mints arbitrary supply.

---

### Likelihood Explanation

Medium. The controller transfer is expected to occur at least once in the production lifecycle (deployer → DAO/multisig). NEAR account IDs are human-readable strings; a single character typo produces a syntactically valid `AccountId` that passes the SDK's type-level validation but resolves to an unintended or attacker-owned account. The absence of a two-step pattern means there is no window to detect and abort the mistake before it takes irreversible effect.

---

### Recommendation

Implement a two-step controller transfer pattern:

```rust
// Step 1: propose (current controller only)
pub fn propose_controller(&mut self, new_controller: AccountId) {
    assert_one_yocto();
    self.assert_controller();
    self.pending_controller = Some(new_controller);
}

// Step 2: accept (pending controller only)
pub fn accept_controller(&mut self) {
    let caller = env::predecessor_account_id();
    require!(
        Some(&caller) == self.pending_controller.as_ref(),
        "ERR_NOT_PENDING_CONTROLLER"
    );
    self.controller = caller;
    self.pending_controller = None;
}
```

This ensures the new address can actually sign transactions before control is relinquished.

### Proof of Concept

1. Current controller (deployer) calls `set_controller("att4cker.near")` — one character typo of `"attacker.near"` which happens to be a registered NEAR account.
2. `self.controller` is immediately overwritten; the deployer loses all control with no revert path.
3. Attacker (owner of `att4cker.near`) calls `attach_full_access_key(attacker_public_key)` from `contracts/nbtc/src/migrate.rs` line 26.
4. NEAR runtime adds a full-access key to the nBTC contract account.

    pub fn upgrade_and_migrate(&self) {
        self.assert_controller();

        // Receive the code directly from the input to avoid the
        // GAS overhead of deserializing parameters
        let code = env::input().unwrap_or_else(|| env::panic_str("ERR_NO_INPUT"));
        // Deploy the contract code.
        let promise_id = env::promise_batch_create(&env::current_account_id());
        env::promise_batch_action_deploy_contract(promise_id, &code);
        // Call promise to migrate the state.
        // Batched together to fail upgrade if migration fails.
        env::promise_batch_action_function_call(
            promise_id,
            "migrate",
            b"",
            NO_DEPOSIT,
            env::prepaid_gas()
                .saturating_sub(env::used_gas())
                .saturating_sub(OUTER_UPGRADE_GAS),
        );
        env::promise_return(promise_id);
    }
