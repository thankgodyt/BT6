### Title
Peras Certificate Validation Stub Unconditionally Accepts All Inbound Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or structural validation. This function is the sole validation gate called by `processCerts` when processing inbound Peras certificates received from unprivileged peers over the object-diffusion mini-protocol. Any peer can inject an arbitrary `PerasCert` for any round and any block point, and it will be accepted, stored in the `PerasCertDB`/`ChainDB`, and trigger chain-selection side-effects that boost a fraudulent block.

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the required validation entry point for inbound Peras certificates. The only deployed instance — the universal degenerate instance for `StandardHash blk` — implements this method as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature is verified, no round-number bounds are checked, no boosted-block existence is confirmed, and no quorum proof is required. The function accepts every certificate unconditionally.

This stub is directly wired into the inbound certificate processing pipeline. `processCerts` — called from both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` — passes `validatePerasCert mkPerasParams` as the sole validation callback:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

Inside `processCerts`, after filtering out round numbers already in the DB, every remaining certificate is passed through `validateCert`. Because the stub always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is immediately added to the database: [4](#0-3) 

The `makePerasCertPoolWriterFromChainDB` variant passes the accepted certificate to `ChainDB.addPerasCertAsync`, which triggers chain-selection side-effects: [5](#0-4) 

A secondary, compounding issue exists in `validatePerasVote`: it only checks whether the voter ID appears in the stake distribution but never verifies the vote's cryptographic signature. A peer can forge a vote for any block by any eligible voter ID: [6](#0-5) 

### Impact Explanation

A Peras certificate carries a `PerasWeight` boost that directly influences chain selection. A node that accepts a fraudulent certificate for a round will boost the wrong block, causing it to prefer a non-canonical chain over the honest chain. This is a **Critical** bypass of Peras certificate verification: an unprivileged peer can make an honest node permanently diverge from the canonical chain by injecting one certificate per round for an attacker-chosen block point, with no stake, no key material, and no quorum of votes required.

The `ValidatedPerasCert` wrapper is the type-level proof that a certificate has been checked. Because the stub produces this wrapper unconditionally, all downstream consumers that rely on the `Validated` prefix as a safety invariant are silently undermined.

### Likelihood Explanation

The attack requires only a TCP connection to the object-diffusion endpoint. No keys, no stake, and no prior chain knowledge are needed beyond knowing a valid `PerasRoundNo` and any `Point blk`. The degenerate instance is the only deployed instance (`-- TODO: degenerate instance for all blks to get things to compile`), so every node running this code is affected. [7](#0-6) 

### Recommendation

**Short term:** Replace the stub body of `validatePerasCert` with a real implementation that verifies the aggregate BLS signature over the certificate's `(electionId, candidate)` pair against the aggregated public keys of the claimed voters, checks that the round number is within the current epoch's valid range, and confirms that the boosted block point exists on a known chain. Until a real implementation is ready, the stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the fail-safe direction is rejection rather than acceptance.

**Long term:** Add a property-based test that feeds crafted certificates with invalid signatures, out-of-range round numbers, and unknown block points to `processCerts` and asserts that all are rejected. Enforce via CI that no `validatePerasCert` implementation may return `Right` without invoking a signature-verification primitive.

### Proof of Concept

1. Connect to a node's object-diffusion endpoint for Peras certificates.
2. Construct a `PerasCert` with an arbitrary `pcCertRound` (any round not yet in the DB) and `pcCertBoostedBlock` pointing to an attacker-chosen block.
3. Send the certificate in a batch via the mini-protocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate passes the `([], validatedCerts)` branch and is added to the ChainDB via `ChainDB.addPerasCertAsync`.
6. Chain selection applies the `PerasWeight` boost to the attacker-chosen block, causing the node to prefer the attacker's chain fragment over the honest canonical chain. [8](#0-7)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
