### Title
Peras Certificate Validation Stub Allows Unprivileged Peer to Inflate Chain Weight and Hijack Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `validatePerasCert` implementation in `BlockSupportsPeras` is a no-op stub that unconditionally accepts every inbound Peras certificate. Because the production object-diffusion pipeline calls this function before adding certificates to the `PerasCertDB`, any unprivileged peer can inject arbitrarily many crafted certificates. Each accepted certificate inflates the `PerasWeightSnapshot` used by chain selection, allowing an adversary to make their chain appear heavier than the honest chain and cause the node to switch to it.

This is the direct consensus analog of the ERC4626 inflate issue: just as `balance_of` is an externally manipulable quantity used in a critical ratio calculation instead of an internally tracked value, `validatePerasCert` is an externally supplied value (the certificate) that is accepted without any cryptographic or protocol-level check, and its boost is unconditionally added to the weight used in chain selection.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every certificate, regardless of its cryptographic content, round number plausibility, or boosted-block legitimacy, is wrapped in `ValidatedPerasCert` and returned as `Right`. There is no signature check, no committee-membership check, and no quorum check.

**Inbound path — `processCerts` calls the stub and adds the result to the DB:** [2](#0-1) 

```haskell
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- ← always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
```

`processCerts` partitions the batch into valid/invalid using the stub validator; because the stub never returns `Left`, every certificate in every peer-supplied batch is forwarded to `addPerasCertAsync`. [3](#0-2) 

**Weight snapshot built from all accepted certificates:**

`implGetWeightSnapshot` folds every certificate in `pcdsCertsByTicket` into a `PerasWeightSnapshot`: [4](#0-3) 

```haskell
implGetWeightSnapshot PerasCertDbEnv{pcdbState} = do
  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
          | cert <- Map.elems (pcdsCertsByTicket pcds) ]
  pure (WithFingerprint weights fp)
```

**Inflated snapshot drives chain selection:**

`weightBoostOfFragment` sums the boost for every point on a fragment using the snapshot: [5](#0-4) 

`wsvTotalWeight` adds `blockNo + weightBoost`, and `preferCandidate` switches to the candidate chain when its total weight exceeds the current chain's: [6](#0-5) 

An adversary who injects N crafted certificates each claiming to boost a block on their fork adds `N × perasWeight` to that fork's total weight, making it arbitrarily heavier than the honest chain.

---

### Impact Explanation

**Critical — chain selection failure via unauthorized certificate acceptance.**

An unprivileged peer can make an honest node permanently prefer a non-canonical adversarial chain by:

1. Connecting via the object-diffusion mini-protocol.
2. Sending a batch of crafted `PerasCert` objects whose `pcCertBoostedBlock` points to a block on the adversary's fork.
3. Because `validatePerasCert` is a no-op, all certificates pass and are stored in `PerasCertDB`.
4. `getWeightSnapshot` returns a snapshot with arbitrarily large boosts for the adversarial fork.
5. `preferCandidate` compares `wsvTotalWeight` and switches to the adversarial chain.

This is a bypass of the Peras certificate/vote verification check listed in the allowed impact scope: *"Bypass of … certificate/vote verification bypass … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

**High.** The object-diffusion protocol for Peras certificates is wired into the production node-to-node stack: [7](#0-6) 

Any peer that can establish a node-to-node connection can send crafted certificates. No stake, no key material, and no prior chain state is required. The attack is deterministic and requires only a single connection.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:

1. Verifies the BLS/committee signature(s) on the certificate against the known committee for the claimed round.
2. Checks that the boosted block's slot falls within the valid range for the claimed Peras round.
3. Verifies quorum: the certificate must aggregate votes from a sufficient fraction of the committee's stake.
4. Rejects certificates whose `pcCertBoostedBlock` does not correspond to a known, validated block header.

Until real validation is in place, the object-diffusion inbound handler should refuse all inbound Peras certificates (return an error or silently drop them) rather than accepting them unconditionally.

### Proof of Concept

```
Attacker (unprivileged peer)
  │
  │  [object-diffusion connection]
  │
  ▼
processCerts (ObjectPool/PerasCert.hs)
  │  validatePerasCert mkPerasParams cert  →  always Right ValidatedPerasCert
  │
  ▼
PerasCertDB.addCert  (stores cert with boost = perasWeight params)
  │
  ▼
implGetWeightSnapshot  →  PerasWeightSnapshot { adversarialBlock → N × perasWeight }
  │
  ▼
weightBoostOfFragment (adversarial fragment)  →  huge boost
  │
  ▼
wsvTotalWeight (adversarial) > wsvTotalWeight (honest)
  │
  ▼
preferCandidate → ShouldSwitch  →  node adopts adversarial chain
```

Concretely: with `perasWeight = 15` (the mainnet-plausible value used in the benchmark), sending 145 crafted certificates each boosting the same adversarial block adds `145 × 15 = 2175` to that chain's weight, exceeding the honest chain's block-number-based weight of `k = 2160` and causing the node to switch unconditionally.

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
```
