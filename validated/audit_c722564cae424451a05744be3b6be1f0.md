### Title
Unconditional Peras Certificate Acceptance Bypasses All Validation, Enabling Fraudulent Chain-Weight Injection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Any unprivileged peer can send a crafted `PerasCert` pointing to an arbitrary block; the certificate is accepted, stored in the `PerasCertDB`, and immediately used to boost that block's weight in chain selection, potentially causing an honest node to switch to a non-canonical fork.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must authenticate a Peras certificate before it is stored and acted upon. The sole production instance — a blanket `instance StandardHash blk => BlockSupportsPeras blk` — implements this gate as a stub that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into both production pool-writer constructors:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` applies this validator to every inbound certificate and, because `partitionEithers` will always see an empty error list, unconditionally adds all certificates to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Once stored, the certificate is forwarded to `addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` message. `chainSelSync` then calls `chainSelectionForBlock` for the boosted block, giving it the full `vpcCertBoost` weight in `preferAnchoredCandidate`: [5](#0-4) 

The analog to the external report's "loop variable overwritten" class is structural: just as the original bug caused only the last ticket update to be acted upon (incomplete processing), here the validation loop processes all certificates but the validation function itself is a no-op stub — the "check" step is silently skipped for every item in the batch, so the entire batch is accepted regardless of content.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to any block in the VolatileDB. The certificate is accepted without any signature, committee-membership, or quorum check. The boosted block receives a `PerasWeight` boost in chain selection equal to `perasWeight mkPerasParams`. If the attacker targets a block on a competing fork, the honest node may switch to that fork, violating chain-selection safety. This constitutes a bypass of Peras certificate verification enabling unauthorized certificate acceptance and non-canonical chain preference.

---

### Likelihood Explanation

The object-diffusion mini-protocol for Peras certificates is reachable by any connected peer. No stake, keys, or operator access are required. The attacker only needs to construct a valid CBOR-encoded `PerasCert` (two fields: `PerasRoundNo` and `Point blk`), which is trivially serialisable. The vulnerability is present in the only production instance of `BlockSupportsPeras`.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies: (1) the certificate's cryptographic signature against the expected committee key(s), (2) that the claimed quorum of votes actually exists and is correctly signed, (3) that the boosted block's slot falls within the valid range for the claimed round, and (4) that the voter set satisfies the committee-selection rules. Until real validation is in place, inbound certificates from untrusted peers should be rejected at the network boundary rather than accepted unconditionally.

---

### Proof of Concept

1. Connect to a target node as an unprivileged peer via the object-diffusion mini-protocol for Peras certificates.
2. Send a batch containing one `PerasCert` with `pcCertRound = N` (any round not yet in the DB) and `pcCertBoostedBlock` set to the tip of a competing fork present in the target's VolatileDB.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{..}` unconditionally.
4. The certificate is stored via `PerasCertDB.addCert`.
5. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`; `chainSelSync` calls `chainSelectionForBlock` for the boosted block.
6. `preferAnchoredCandidate` now sees the fork as having additional `PerasWeight` boost; if this tips the comparison, the node switches to the attacker-chosen fork.
