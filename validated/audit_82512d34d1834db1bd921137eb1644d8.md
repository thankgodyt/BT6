### Title
Attacker-Controlled `refund_address` in `request_refund` Enables BTC Theft via Front-Running - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account and accepts a caller-supplied `refund_address` without verifying the caller is the original depositor. When `deposit_msg.refund_address` is `None`, the contract stores any attacker-supplied BTC address as the refund destination. An attacker who observes an unfinalized deposit can front-run the legitimate user's refund request, locking in their own address. After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and the bridge MPC-signs a transaction paying the deposit UTXO to the attacker's BTC address.

---

### Finding Description

`request_refund` is in a `#[trusted_relayer]` impl block but carries no per-function `#[trusted_relayer]` attribute, making it callable by any NEAR account. [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

This check is a no-op when `deposit_msg.refund_address` is `None` — the common case for users who did not pre-authorize a refund address. The caller-supplied `refund_address` is then stored verbatim in the `RefundRequest`: [3](#0-2) 

The `deposit_msg` is public information: it is the pre-image of the deposit address derivation path (`get_deposit_path` hashes the full JSON of `deposit_msg`), so any observer can reconstruct it from the on-chain deposit address. [4](#0-3) 

Once a `RefundRequest` exists for a UTXO key, a second `request_refund` for the same UTXO is rejected: [5](#0-4) 

This means the legitimate user cannot overwrite the attacker's entry. After `unsafe_refund_timelock_sec` passes, `execute_refund` (also publicly callable — no per-function `#[trusted_relayer]`) builds the refund PSBT paying `refund_request.refund_address`: [6](#0-5) 

The MPC network signs this PSBT, and the deposit UTXO is sent to the attacker's BTC address.

---

### Impact Explanation

The attacker receives the victim's deposited BTC. The victim's deposit is permanently lost: the UTXO is marked `verified_deposit_utxo` after `execute_refund`, blocking any future `verify_deposit` mint, and the refund request is removed after `verify_refund_finalize`. [7](#0-6) 

This is a direct theft of user funds (BTC/nBTC) from the bridge's custody, matching the **Critical** impact class: *Significant loss or theft of user funds*.

---

### Likelihood Explanation

The preconditions are realistic:

1. A deposit that was never finalized (relayer downtime, user error, or deliberate intent to refund) is a normal operational scenario the refund system is designed for.
2. The `deposit_msg` is derivable from the deposit address, which is public on-chain.
3. `request_refund` is permissionless and cheap to call (only requires a storage deposit).
4. The attacker simply needs to submit their call before the legitimate user does — a standard front-run on NEAR.

The `unsafe_refund_timelock_sec` and DAO/Operator rejection window are a partial mitigation, but they require active monitoring and timely intervention for every suspicious refund request. A single missed rejection results in permanent fund loss.

---

### Recommendation

Bind the `refund_address` to the depositor's identity. The cleanest fix is to require that when `deposit_msg.refund_address` is `None`, only the NEAR account identified by `deposit_msg.recipient_id` may call `request_refund` and supply the `refund_address`. Alternatively, require that `deposit_msg.refund_address` always be set (non-`None`) and enforce that the caller-supplied address matches it, eliminating the open-address path entirely.

---

### Proof of Concept

1. Alice sends 1 BTC to the deposit address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: null }`.
2. The relayer fails to call `verify_deposit`; Alice's deposit is unfinalized.
3. Attacker Eve observes Alice's deposit on-chain, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: null },
     refund_address = "eve_btc_address",
     tx_bytes = <Alice's deposit tx>,
     vout = 0,
     proof = <valid inclusion proof>,
     gas_fee = null
   )
   ```
   with the required NEAR storage deposit attached.
4. `request_refund_callback` verifies the deposit is real, stores `RefundRequest { refund_address: "eve_btc_address", ... }`.
5. Alice calls `request_refund` with her own address — it panics: `"Refund request already exists for this UTXO"`.
6. After `unsafe_refund_timelock_sec` (assuming DAO does not intervene), Eve calls `execute_refund(utxo_storage_key)`.
7. The bridge builds a PSBT paying 1 BTC (minus gas fee) to `"eve_btc_address"`, MPC signs it, and broadcasts it.
8. `verify_refund_finalize` finalizes the refund; Alice's 1 BTC is permanently transferred to Eve.
