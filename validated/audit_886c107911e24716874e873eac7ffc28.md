Audit Report

## Title
`is_refund_required` Ignores Promise Failure for Non-`ft_transfer_call` Paths, Permanently Freezing Locked Tokens — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`fin_transfer_send_tokens_callback` delegates the failure decision to `is_refund_required`, which unconditionally returns `false` when `is_ft_transfer_call` is `false`. This means any promise error from `ft_transfer`, `mint`, or the `near_withdraw → near_withdraw_callback` chain is silently treated as success: the relayer fee is paid, `FinTransferEvent` is emitted, and the `locked_tokens` decrement from `unlock_tokens_if_needed` is never reverted. Because the proof is consumed by `add_fin_transfer` before `send_tokens` is called, there is no on-chain retry path, leaving bridged funds permanently frozen in the bridge contract.

## Finding Description

**Step 1 — `locked_tokens` decremented before async call.**
`process_fin_transfer_to_near` calls `unlock_tokens_if_needed` synchronously, decrementing `locked_tokens` for non-deployed tokens, and stores the resulting `LockAction` in `lock_actions`: [1](#0-0) 

The transfer ID is also inserted into `finalised_transfers` at this point via `add_fin_transfer` (line 1875), consuming the proof.

**Step 2 — `send_tokens` dispatches `ft_transfer` (or `mint`/`near_withdraw`) as a promise.**
For a non-deployed token with an empty `msg`, `send_tokens` dispatches `ft_transfer`: [2](#0-1) 

`is_ft_transfer_call` is set to `!msg.is_empty()`, so it is `false` for this path: [3](#0-2) 

**Step 3 — `is_refund_required` returns `false` unconditionally for the non-`ft_transfer_call` branch.** [4](#0-3) 

The function never inspects `env::promise_result_checked` when `is_ft_transfer_call` is `false`. A promise error from `ft_transfer`, `mint`, or `near_withdraw_callback` (which itself panics on failure at line 1050, propagating as `Err` to the outer callback) is indistinguishable from success.

**Step 4 — Callback takes the success branch.**
Because `is_refund_required` returns `false`, `fin_transfer_send_tokens_callback` enters the `else` branch: [5](#0-4) 

`revert_lock_actions` is never called, so the `locked_tokens` decrement is permanent. `remove_fin_transfer` is not called, so the transfer ID stays in `finalised_transfers`. The relayer receives its fee and `FinTransferEvent` is emitted.

**Step 5 — Same bug for `ft_transfer_call` promise error.**
Even when `is_ft_transfer_call` is `true`, the `Err(_)` arm also returns `false`: [6](#0-5) 

**Existing guards are insufficient.** The storage-deposit check before `send_tokens` verifies that the recipient has storage, but it cannot prevent the token contract from panicking after the check (e.g., due to a pause). `revert_lock_actions` exists and is correctly wired in the refund branch, but `is_refund_required` never returns `true` for non-`ft_transfer_call` failures: [7](#0-6) 

## Impact Explanation
For non-deployed (locked) tokens (e.g., USDC, wETH bridged from Ethereum): the bridge holds the physical tokens in its balance inside the token contract. When `ft_transfer` fails, the tokens remain in the bridge's balance, but `locked_tokens` has been decremented. The recipient receives nothing. The proof is consumed and cannot be resubmitted. There is no admin function that can re-execute the delivery (only `set_locked_tokens` exists for DAO, which corrects accounting but cannot deliver tokens). This constitutes **permanent freezing of bridged funds**, matching the critical impact class.

A secondary accounting inconsistency results: `locked_tokens` under-counts the actual reserve, which could allow additional outbound transfers beyond the true backing.

For deployed (minted) tokens: `mint()` failing means no tokens are created for the recipient, yet `FinTransferEvent` is emitted and the proof is consumed, constituting an unrecoverable loss of the user's cross-chain transfer.

## Likelihood Explanation
The trigger is a promise error from the token contract during `ft_transfer` or `mint`. Realistic causes that do not require privileged access by the attacker:

- **Token pause**: USDC, USDT, and many bridged ERC-20s on NEAR have pause functionality. If the token admin pauses the contract between the storage-deposit check and the `ft_transfer` execution (two separate NEAR blocks), the `ft_transfer` panics and the promise result is `Err`. This is an external condition, not a user mistake.
- **Recipient account deletion**: A NEAR account can be deleted by its owner between the storage-deposit check and the `ft_transfer`. Any in-flight transfer to that account is permanently lost.
- **Token contract bug or upgrade**: Any panic in the token contract during `ft_transfer` triggers the same path.

None of these require the attacker to have privileged access; the victim is simply a user whose transfer lands during one of these conditions.

## Recommendation
In `is_refund_required`, check the promise result for all paths, not just `ft_transfer_call`:

1. **For `is_ft_transfer_call = false`**: call `env::promise_result_checked(0, usize::MAX)` and return `true` if the result is `Err(_)`, indicating the token delivery failed and the lock actions must be reverted.
2. **For `is_ft_transfer_call = true`, `Err(_)` arm**: change the return value from `false` to `true` so that a panicking token contract during `ft_transfer_call` also triggers the refund path.
3. Ensure `near_withdraw_callback` failure is also handled: since it panics (propagating `Err` to the outer callback), the `is_ft_transfer_call = false` fix above covers this path as well.

## Proof of Concept

**Scenario**: USDC (non-deployed, locked token) is paused on NEAR between the storage-check step and the `ft_transfer` step.

1. User initiates transfer of 1000 USDC from Ethereum → `alice.near`.
2. Relayer calls `fin_transfer()` with a valid EVM proof.
3. `fin_transfer_callback` verifies the proof and calls `process_fin_transfer_to_near`.
4. `add_fin_transfer` inserts the transfer ID into `finalised_transfers` (proof consumed).
5. `unlock_tokens_if_needed` decrements `locked_tokens[Eth][usdc.near]` by 1000.
6. `send_tokens` dispatches `ft_transfer(alice.near, 1000)` on `usdc.near` with `msg = ""`, so `is_ft_transfer_call = false`.
7. USDC contract is paused → `ft_transfer` panics → promise result is `Err(_)`.
8. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
9. `is_refund_required(false)` returns `false` unconditionally (line 1801–1803).
10. Callback enters `else` branch: sends fee to relayer, emits `FinTransferEvent`.
11. `revert_lock_actions` is never called; `locked_tokens` remains decremented by 1000.
12. `alice.near` receives 0 USDC. The proof is consumed. No retry is possible.
13. 1000 USDC remain in the bridge's balance with no on-chain recovery path.

**Reproducible test plan**: In `near/omni-bridge/src/tests/lib_test.rs`, extend the pattern of `test_fin_transfer_callback_refund_restores_locked_tokens` with `is_ft_transfer_call = false` and a `PromiseResult::Failed` result. Assert that `get_locked_tokens` returns the original amount (i.e., `revert_lock_actions` was called). The test will currently fail, demonstrating the bug.

        for lock_action in lock_actions {
            match lock_action {
                LockAction::Locked {
                    chain_kind,
                    token_id,

                    token_id,
