### Title
No Minimum Amount Enforcement in Refund Path Allows Dust Refund Requests to Permanently Clog Bridge State — (`contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `request_refund_callback` function stores refund requests without enforcing `min_deposit_amount` and without validating a minimum `gas_fee`. An attacker can send many dust BTC deposits and submit refund requests with `gas_fee: Some(0)`, creating refund entries whose resulting BTC transactions will never confirm (output equals input, leaving no miner fee). These requests accumulate in the contract's `refund_requests` map and can only be cleared by a privileged `RefundOperator`/DAO call to `internal_reject_refund`, permanently requiring operator intervention.

---

### Finding Description

The bridge config defines two minimum-amount guards: [1](#0-0) 

`min_deposit_amount` is described as the threshold below which `verify_deposit` will not mint nBTC. However, the refund path — the alternative flow for deposits that were never claimed — does **not** apply this guard.

In `request_refund_callback`, the only economic check is: [2](#0-1) 

The caller supplies `gas_fee` as an `Option<u128>`. Passing `gas_fee: Some(0)` satisfies `resolved_gas_fee < amount` for any `amount > 0`, and there is no floor on `gas_fee`. The refund request is then persisted unconditionally: [3](#0-2) 

When `execute_refund` later calls `refund_execution_inputs`, it computes: [4](#0-3) 

With `gas_fee = 0` and `amount = 546` (dust), `refund_amount = 546`. The resulting BTC transaction has input = output = 546 sat and zero miner fee. Miners will never include it. `verify_refund_finalize` therefore never succeeds, and the refund request is never removed from `refund_requests`. The only removal path is a privileged `internal_reject_refund`: [5](#0-4) 

---

### Impact Explanation

Each stuck refund request:
- Permanently occupies a slot in the `refund_requests` `IterableMap`, growing contract state.
- Consumes a `BTCPendingInfo` entry and an account `btc_pending_sign_ids` slot after `execute_refund` is called, blocking the account's pending-sign capacity (`require_pending_sign_capacity`).
- Requires a DAO/`RefundOperator` transaction to reject — one per stuck request.

A large volume of such requests forces sustained operator intervention and can exhaust per-account pending-sign limits, temporarily locking legitimate users' withdrawal capacity. This matches **Medium: attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

The attacker must pay:
1. A BTC transaction fee per dust deposit (a few hundred satoshis each at typical fee rates).
2. A NEAR storage deposit per `request_refund` call (`required_balance_for_request_refund`).

Both costs are low relative to the disruption caused. The attack is fully permissionless — no privileged role is needed. Any NEAR account can call `request_refund` for any BTC UTXO that passes light-client verification.

---

### Recommendation

1. **Enforce `min_deposit_amount` in `request_refund_callback`**: add `require!(amount >= config.min_deposit_amount, "Deposit below minimum")` before storing the request.
2. **Enforce a minimum `gas_fee`**: add `require!(resolved_gas_fee >= config.min_btc_gas_fee, "gas_fee below minimum")` so that the resulting BTC refund transaction is always economically viable.
3. **Alternatively**, derive `gas_fee` entirely from the protocol config and disallow caller-supplied overrides below the protocol minimum.

---

### Proof of Concept

1. Attacker sends N BTC deposits of 546 satoshis each to distinct deposit addresses (each derived from a unique `DepositMsg`).
2. For each deposit, attacker calls `request_refund(..., gas_fee: Some(0))` on NEAR, attaching the required storage deposit.
3. Light-client verification passes; `request_refund_callback` stores N `RefundRequest` entries with `gas_fee = 0`.
4. Operator (or attacker) calls `execute_refund` for each. `refund_execution_inputs` computes `refund_amount = 546 - 0 = 546`. A BTC PSBT is built with 546-sat input and 546-sat output, zero fee.
5. MPC signs the PSBT. The signed transaction is broadcast but never mined (zero fee).
6. `verify_refund_finalize` is never callable. The N `RefundRequest` entries and N `BTCPendingInfo` entries remain in contract state indefinitely.
7. DAO/`RefundOperator` must call `internal_reject_refund` N times to clean up, and `internal_remove_refund_pending_tx_id` N times for the pending infos — one privileged transaction per dust deposit.
