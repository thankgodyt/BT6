### Title
Unrestricted `new()` Initializer Allows Front-Running to Seize Minting Authority and Bridge DAO Control - (File: contracts/nbtc/src/lib.rs, contracts/satoshi-bridge/src/lib.rs)

### Summary
Both the `nbtc` token contract and the `satoshi-bridge` contract expose their `new()` initializer as an unrestricted public function. Any NEAR account can call `new()` after the WASM code is deployed but before the legitimate deployer initializes the contract. An attacker who wins this race sets themselves as `bridge_id` (the sole authorized minter) in `nbtc`, and as DAO super-admin in `satoshi-bridge`, achieving unauthorized minting capability and full bridge control respectively.

### Finding Description

**`nbtc::new()` — `contracts/nbtc/src/lib.rs:58-91`**

```rust
#[init]
pub fn new(
    controller: AccountId,
    bridge_id: AccountId,
    ...
) -> Self {
    require!(!env::state_exists(), "Already initialized");
    // No check on env::predecessor_account_id()
    let mut contract = Self { controller, bridge_id, ... };
    ...
}
```

The only guard is `require!(!env::state_exists(), ...)`, which prevents double-initialization but does not restrict the caller. Whoever calls `new()` first supplies arbitrary `controller` and `bridge_id` values.

`mint()` and `burn()` are gated solely by `assert_bridge()`:

```rust
fn assert_bridge(&self) {
    require!(self.bridge_id == env::predecessor_account_id(), "Not Allow");
}
```

If the attacker supplies their own account as `bridge_id`, they satisfy `assert_bridge()` and can call `mint()` freely to issue arbitrary nBTC.

**`satoshi-bridge::new()` — `contracts/satoshi-bridge/src/lib.rs:182-230`**

```rust
#[init]
pub fn new(config: Config) -> Self {
    config.assert_valid();
    // No check on env::predecessor_account_id()
    ...
    contract.acl_init_super_admin(env::predecessor_account_id());
    contract.acl_grant_role(Role::DAO.into(), env::predecessor_account_id());
    ...
}
```

Again, no caller restriction. The attacker becomes the sole DAO super-admin, gaining control over all privileged operations: `update_config`, `withdraw_protocol_fee`, relayer whitelists, upgrade, and pause.

### Impact Explanation

- **`nbtc` front-run**: Attacker sets `bridge_id = attacker_account`. They then call `mint(victim, U128(MAX), ...)` — `assert_bridge()` passes because `predecessor == bridge_id`. Arbitrary nBTC is minted with no BTC backing. This is **unauthorized minting of nBTC** — Critical.
- **`satoshi-bridge` front-run**: Attacker becomes DAO. They can redirect `nbtc_account_id` to a malicious token, drain `cur_available_protocol_fee` via `withdraw_protocol_fee`, and block all legitimate operations. This is **bypass of bridge authorization controls** — Critical.

### Likelihood Explanation

In NEAR Protocol, contract deployment (`DeployContractAction`) and initialization (`FunctionCallAction` calling `new()`) are separate operations. They can be batched atomically, but nothing in the contract code enforces this. If the deployer uses two separate transactions — or if a deployment script fails between the two steps — there is an observable window on-chain during which any account can call `new()`. An attacker monitoring the NEAR blockchain for new deployments of known contract hashes can detect this window and submit a `new()` call with attacker-controlled parameters. The attack requires no special privilege, only a funded NEAR account and network access.

### Recommendation

1. **Restrict the caller** in both `new()` functions. In NEAR the deployer is the account owner, so check `env::predecessor_account_id() == env::current_account_id()` (self-call via batch) or require a specific expected deployer address.
2. **Deploy and initialize atomically** using a single batch transaction containing both `DeployContractAction` and `FunctionCallAction { method_name: "new", ... }`.
3. **Validate account-ID parameters** in `nbtc::new()`: assert that `controller` and `bridge_id` are non-empty and differ from each other where appropriate.

### Proof of Concept

1. Legitimate deployer broadcasts `DeployContractAction` for `nbtc` WASM to account `nbtc.near` (state not yet initialized).
2. Attacker observes the deployment on-chain and immediately submits:
   ```
   FunctionCallAction {
     receiver_id: "nbtc.near",
     method_name: "new",
     args: {
       "controller": "attacker.near",
       "bridge_id": "attacker.near",
       "name": "Near BTC", "symbol": "NBTC", "decimals": 8
     }
   }
   ```
3. Attacker's transaction lands before the deployer's `new()` call. `env::state_exists()` is `false`, so the `require!` passes. `controller = attacker.near`, `bridge_id = attacker.near` are stored.
4. Attacker calls `mint(victim_account, U128(1_000_000_000_000), U128(0), attacker.near, U128(0), None)` from `attacker.near`. `assert_bridge()` checks `bridge_id == predecessor` → `attacker.near == attacker.near` → passes. Arbitrary nBTC is minted with no BTC collateral. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
