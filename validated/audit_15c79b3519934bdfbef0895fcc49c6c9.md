### Title
Predictable WFA Persistent-Seat Tiebreaker Under `NeutralNonce` Enables Pool-Key Grinding for Unauthorized Peras Committee Membership — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/WFA.hs`)

---

### Summary

`wFATiebreakerWithEpochNonce` in `WFA.hs` silently degrades to a zero-entropy, fully deterministic function when the epoch nonce is `NeutralNonce`. Because the pool cold key is entirely attacker-controlled, an adversary can brute-force pool keys offline to find a `PoolId` that wins the tiebreaker against any target pool with equal stake, guaranteeing themselves a persistent seat in the Peras voting committee without any legitimate stake advantage.

---

### Finding Description

The `wFATiebreakerWithEpochNonce` function is the sole mechanism that prevents an adversary from gaming the Weighted Fait-Accompli (WFA) persistent-seat assignment. Its design rationale is stated explicitly in the code:

> "For this, we throw the current epoch nonce into the mix to avoid giving an adversary an edge to manipulate the tiebreaking in their favor, as they cannot predict the epoch nonce in advance."

The implementation is:

```haskell
wFATiebreakerWithEpochNonce epochNonce =
  WFATiebreaker (compare `on` hashWithNonce)
 where
  hashWithNonce poolId =
    Hash.castHash . Hash.hashWith id . runByteBuilder (32 + 32)
      $ epochNonceBytes <> poolIdBytes
   where
    epochNonceBytes =
      case epochNonce of
        NeutralNonce -> mempty          -- ← zero bytes contributed
        Nonce h      -> BS.byteStringCopy (Hash.hashToBytes h)
    poolIdBytes = BS.byteStringCopy . Hash.hashToBytes . unKeyHash . unPoolId $ poolId
```

When `epochNonce = NeutralNonce`, `epochNonceBytes = mempty`, so the tiebreaker hash collapses to:

```
H(poolId)  =  H(H(cold_vk))
```

This is a pure function of the pool's cold verification key — a value the pool operator chooses freely before registering. The entire anti-grinding protection disappears.

The tiebreaker is consumed by `mkExtWFAStakeDistr` via `descendingStakeWithTiebreaker`:

```haskell
| stake1 == stake2 = unWFATiebreaker tiebreaker poolId1 poolId2
```

The resulting `ExtWFAStakeDistr` determines seat indices, and `weightedFaitAccompliSplitSeats` uses those indices to decide which pools receive persistent seats via `isAbovePersistentSeatThreshold`. A pool that wins the tiebreaker gets a lower seat index, which increases its probability of crossing the persistent-seat threshold.

**`NeutralNonce` reachability in production paths:**

- `translateChainDepStateByronToShelley` explicitly sets `ticknStatePrevHashNonce = SL.NeutralNonce` at the Byron→Shelley era transition.
- Any chain whose genesis sets `tpraosInitialNonce = NeutralNonce` (the test genesis JSON in the repo uses `"extraEntropy": {"tag": "NeutralNonce"}`) starts with a neutral nonce.
- On a fresh Peras-enabled testnet or private chain, the first epoch's nonce is `NeutralNonce` or a known constant, making the tiebreaker fully predictable from day one.

**Attack steps (analogous to the CREATE2 meet-in-the-middle):**

1. Observe the live stake distribution and identify pools with equal stake near the persistent-seat threshold.
2. Offline, brute-force cold verification keys. For each candidate key, compute `poolId = H(vk)` and then `tiebreakerHash = H(poolId)`. Using a meet-in-the-middle approach (~2^80 hashes, feasible with GPU clusters comparable to a fraction of the Bitcoin network), find a key whose `tiebreakerHash` is smaller than every target pool's hash (winning the `compare` ordering).
3. Register the pool on-chain with the chosen cold key.
4. Delegate exactly the same amount of stake as the target pool(s).
5. At epoch boundary, `mkExtWFAStakeDistr` sorts equal-stake pools by the predictable tiebreaker, placing the attacker's pool at a lower seat index and granting it a persistent committee seat.

The attacker now holds a guaranteed persistent Peras voting seat — no VRF proof required per election — and can cast votes on every round without the per-round eligibility check that non-persistent members must pass.

---

### Impact Explanation

A persistent Peras committee seat grants the attacker unconditional voting rights in every Peras election for the entire epoch. Peras certificates add a weight boost to blocks, directly influencing chain selection (`preferCandidate`). An adversary with a disproportionate number of persistent seats can:

- Bias which blocks receive Peras weight boosts, steering chain selection toward attacker-preferred forks.
- Suppress certificates for honest blocks by withholding votes, degrading Peras finality guarantees.
- On a small testnet or private chain where the committee is small, a single gamed persistent seat may represent a significant fraction of total voting weight.

This maps to the allowed impact scope: **bypass of Peras voting committee checks that enables unauthorized vote/certificate acceptance**.

---

### Likelihood Explanation

- **`NeutralNonce` is reachable**: it is explicitly handled in production code (`CanHardFork.hs` line 369, `VRF.hs` line 76) and appears in the genesis JSON shipped with the repository.
- **Pool key is fully attacker-controlled**: registering a pool requires only a deposit and a self-chosen cold key — no privileged access.
- **Brute-force is feasible**: the tiebreaker hash space is 256 bits, but a meet-in-the-middle search over 2^80 values is sufficient to find a winning key. The Bitcoin network already exceeds 6.5×10^20 hashes/second; a small fraction of that compute finds a collision in under an hour.
- **Equal-stake condition is engineerable**: the attacker can observe the stake distribution and delegate precisely the required amount to match a target pool.
- **Waiting is free**: the attacker can register the pool and wait for the right epoch conditions before the attack becomes active, exactly as in the CREATE2 report.

---

### Recommendation

1. **Reject `NeutralNonce` as a tiebreaker input.** When `epochNonce = NeutralNonce`, either refuse to construct the `ExtWFAStakeDistr` (returning a `WFAError`) or substitute a chain-specific constant (e.g., the genesis hash) so the tiebreaker is not purely a function of the pool key.

2. **Add additional entropy sources.** Mix in the epoch number or the hash of the previous epoch's last block header alongside the nonce, so even a known nonce does not give the attacker a static target to grind against.

3. **Document the security assumption explicitly.** The `wFATiebreakerWithEpochNonce` docstring should state that calling it with `NeutralNonce` removes all grinding resistance, and callers must ensure a non-neutral nonce is available before invoking it.

### Proof of Concept

The root cause is directly visible in the production source. No hash collision needs to be exhibited; the structural argument is:

```
-- When NeutralNonce:
epochNonceBytes = mempty
hashWithNonce poolId = H(poolIdBytes)   -- pure function of cold_vk

-- Attacker's search:
for each candidate cold_vk:
    poolId        = H(cold_vk)          -- KeyHash derivation
    tiebreakerVal = H(poolId)           -- wFATiebreakerWithEpochNonce output
    if tiebreakerVal < targetPool.tiebreakerVal:
        register this pool, delegate equal stake
        → attacker wins tiebreaker → lower seat index → persistent seat
```

The `descendingStakeWithTiebreaker` comparator in `mkExtWFAStakeDistr` (line 401–407) uses `unWFATiebreaker tiebreaker poolId1 poolId2` for equal-stake pools, and `weightedFaitAccompliSplitSeats` (line 113–133) grants persistent seats to pools with lower seat indices that pass `isAbovePersistentSeatThreshold`. Winning the tiebreaker deterministically shifts the attacker's pool to a lower seat index, crossing the threshold. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
