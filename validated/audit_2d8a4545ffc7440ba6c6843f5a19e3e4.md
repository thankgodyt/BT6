Audit Report

## Title
Missing `locked_tokens` Initialization in `deploy_token_internal` and `add_deployed_tokens` Causes Silent Escrow Mis-Accounting - (File: `near/omni-bridge/src/lib.rs`, `near/omni-bridge/src/token_lock.rs`)

## Summary
Tokens registered via `deploy_token_internal` (called by the public `deploy_token` function) and `add_deployed_tokens` never receive a zero-initialized entry in the `locked_tokens` map. Because `lock_tokens` and `unlock_tokens` both silently return `LockAction::Unchanged` when the map key is absent, escrow accounting is permanently broken for cross-chain re-routing flows involving these tokens.

## Finding Description
**Root cause confirmed in code:**

`lock_tokens` ( [1](#0-0) ) and `unlock_tokens` ( [2](#0-1) ) both perform an early return of `LockAction::Unchanged` when the `locked_tokens` map has no entry for the `(ChainKind, AccountId)` key.

`bind_token_callback` correctly seeds the entry to `0` immediately after registration: [3](#0-2) 

`deploy_token_internal` calls `add_token`, inserts into `deployed_tokens` and `deployed_tokens_v2`, but never touches `locked_tokens`: [4](#0-3) 

`add_deployed_tokens` has the same omission: [5](#0-4) 

**Important nuance on exploit path:** `lock_tokens_if_needed` and `unlock_tokens_if_needed` both contain a guard: [6](#0-5)  that returns `Unchanged` when `get_token_origin_chain(token_id) == chain_kind`. This means for the *standard* round-trip (e.g., ETH-origin token → NEAR → ETH), the origin-chain guard fires first and the missing map entry is never reached — that path is not affected.

The bug is triggered in **cross-chain re-routing**: when an ETH-origin token deployed via `deploy_token_internal` is finalized to a non-ETH destination (e.g., ETH token → NEAR → Solana). In `process_fin_transfer_to_other_chain`: [7](#0-6)  both `unlock_tokens_if_needed(origin=ETH)` and `lock_tokens_if_needed(dest=Solana)` are called. Since `ETH ≠ Solana`, the origin-chain guard does not fire, `lock_tokens`/`unlock_tokens` are reached, find no map entry, and silently return `Unchanged`. The escrow counter is never updated.

## Impact Explanation
This is a confirmed **escrow mis-accounting** impact. For every token registered through `deploy_token_internal` (the public, permissionless path) and used in cross-chain re-routing:

- `unlock_tokens_if_needed` silently skips decrementing the escrow counter and bypasses the `InsufficientLockedTokens` guard entirely.
- `lock_tokens_if_needed` silently skips incrementing the escrow counter.
- `revert_lock_actions` cannot restore state on failure because the stored action is always `Unchanged`.

The bridge's `locked_tokens` ledger is permanently incorrect for all such tokens, making the escrow invariant unenforceable. This matches the allowed critical impact: *"Balance manipulation, escrow mis-accounting… that changes user or protocol balances."*

## Likelihood Explanation
`deploy_token` is the standard permissionless deployment path callable by any user who pays the storage deposit. Every token deployed through it is affected from the moment of deployment. Cross-chain re-routing (finalization to a non-origin chain) is a supported and documented bridge flow (`process_fin_transfer_to_other_chain`). No special privileges, timing windows, or victim mistakes are required.

## Recommendation
In `deploy_token_internal`, after `add_token` succeeds, insert a zero entry into `locked_tokens` for the token's origin chain, mirroring `bind_token_callback`:

```rust
self.locked_tokens.insert(
    &(token_address.get_chain(), token_id.clone()),
    &0,
);
```

Apply the same fix in `add_deployed_tokens` for each token in the batch. This ensures `lock_tokens` and `unlock_tokens` always find an existing entry and correctly update the escrow counter for cross-chain re-routing flows.

## Proof of Concept
1. Any user calls `deploy_token` for an ETH-origin token. `deploy_token_internal` runs; `locked_tokens[(Eth, token_id)]` is never set.
2. A cross-chain re-routing finalization occurs: a relayer calls `fin_transfer` with `origin_chain=Eth` and `destination=Solana` (i.e., `process_fin_transfer_to_other_chain`).
3. `unlock_tokens_if_needed(Eth, token_id, amount)` is called. Since `get_token_origin_chain(token_id) = Eth ≠ Solana` (destination), the origin-chain guard does not fire. `unlock_tokens` is reached, finds no map entry, and returns `Unchanged`. The `InsufficientLockedTokens` guard is never evaluated.
4. `lock_tokens_if_needed(Solana, token_id, amount)` is called. Same result — no entry, returns `Unchanged`.
5. `get_locked_tokens(Eth, token_id)` returns `None` throughout, confirming the escrow ledger was never updated despite real token movements. A unit test asserting that `locked_tokens` is non-`None` after `deploy_token_internal` and non-zero after a cross-chain re-routing finalization would reproduce this failure.
