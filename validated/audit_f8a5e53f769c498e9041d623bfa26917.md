### Title
MPC Signature Output Not Verified Against Payload and Derived Public Key Before Transaction Finalization - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
The `sign_btc_transaction_callback` function accepts the raw `SignatureResponse` from the Chain Signatures MPC and embeds it directly into the Bitcoin/Zcash PSBT without ever verifying that the returned `(r, s)` values constitute a valid ECDSA signature over the expected `payload` hash under the bridge's derived public key. This is the direct analog of the AZTEC finding: the MPC output is trusted and used without cryptographic validation of its correctness.

### Finding Description
In `sign_btc_transaction_callback` (chain_signature.rs lines 134–213), after receiving the MPC result:

1. The response is deserialized: `serde_json::from_slice::<SignatureResponse>(&result_bytes)` — this only checks JSON structure.
2. The derived public key is computed locally via `generate_btc_public_key(path)`.
3. The signature is stored immediately: `btc_pending_info.signatures[sign_index] = Some(signature.clone())` — no verification.
4. `psbt.save_signature(sign_index, signature, public_key)` is called, which in `bitcoin_utils/psbt_wrapper.rs` line 162–163 calls `Witness::p2wpkh(&signature.to_btc_signature(), &public_key)` — this constructs the witness stack but performs no ECDSA verification.
5. `psbt.extract_tx_bytes_with_sign()` finalizes and serializes the transaction.

The `to_btc_signature()` method (chain_signature.rs lines 41–49) calls `bitcoin::secp256k1::ecdsa::Signature::from_compact(...)`, which only validates that `r` and `s` are structurally valid 32-byte non-zero scalars in the secp256k1 field. It does **not** call `secp256k1::Secp256k1::verify_ecdsa(payload, &sig, &pubkey)` to confirm the signature actually authenticates the correct payload under the correct key.

The same pattern applies to the Zcash path in `zcash_utils/psbt_wrapper.rs` lines 486–501, where `save_signature` also embeds the signature without verification.

The `key_version` parameter is caller-supplied (any unprivileged user passes it in `sign_btc_transaction`), forwarded verbatim to the MPC. If the MPC signs under a different key version than the one used to derive the bridge's public key, the resulting signature is invalid for the expected public key — and the bridge accepts it without detection.

### Impact Explanation
If the MPC returns a structurally valid but semantically incorrect signature (wrong key version, edge-case MPC output, or a signature over a different payload), the bridge:
- Accepts and stores the invalid signature
- Emits a `SignedBtcTransaction` event with invalid transaction bytes
- Advances the pending state to `pending_verify`

The resulting Bitcoin transaction will be rejected by the Bitcoin network (invalid witness). The UTXOs consumed as inputs are locked in the pending state. The user's nBTC tokens remain in the bridge's balance (not yet burned, since `verify_withdraw` requires a Merkle proof that can never be obtained for an unconfirmed transaction). The bridge enters a stuck state requiring operator intervention to clear the pending entry and recover the UTXOs.

This matches the allowed Medium impact: **stuck bridge state requiring operator intervention**.

### Likelihood Explanation
The `key_version` is an unprivileged caller-supplied parameter. A caller can pass any `key_version` value. If the MPC derives a different key for a non-zero `key_version` than the key used to compute the bridge's `change_address` and UTXO paths (which are derived with `key_version` implicitly 0 via `generate_btc_public_key`), the returned signature will be invalid for the expected public key. The bridge will accept it. This is a reachable, low-effort trigger requiring no special privileges.

### Recommendation
In `sign_btc_transaction_callback`, after deserializing the `SignatureResponse`, add an explicit ECDSA verification step before storing or embedding the signature:

```rust
// Reconstruct the payload that was signed
let payload = btc_pending_info
    .get_psbt()
    .get_hash_to_sign(sign_index, &public_keys);

// Verify the MPC signature is valid for the expected payload and public key
let secp = bitcoin::secp256k1::Secp256k1::verification_only();
let msg = bitcoin::secp256k1::Message::from_digest(payload);
let btc_sig = signature.to_btc_signature();
require!(
    secp.verify_ecdsa(&msg, &btc_sig.signature, &public_key).is_ok(),
    "MPC signature does not verify against expected payload and public key"
);
```

Additionally, validate that the `key_version` used for signing matches the version used to derive the bridge's registered public keys, or reject signing requests with unexpected key versions.

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call`, creating a `BTCPendingInfo` entry with `sign_index=0` and a derived public key for path `"bitcoin-1"` (key version 0).
2. Any caller invokes `sign_btc_transaction(btc_pending_sign_id, 0, key_version=99)`.
3. The bridge sends `SignRequest { payload, path: "bitcoin-1", key_version: 99 }` to the MPC.
4. The MPC signs `payload` under the key derived for `key_version=99`, which is a different key than the bridge's registered public key (derived at version 0).
5. `sign_btc_transaction_callback` receives the response, calls `generate_btc_public_key("bitcoin-1")` (version 0), and calls `from_compact(r || s)` — this passes because the bytes are structurally valid.
6. The signature is stored and embedded into the PSBT witness without any `verify_ecdsa` call.
7. The transaction is serialized and the state advances to `pending_verify`.
8. The Bitcoin transaction is broadcast but rejected by every node (invalid witness). No Merkle proof can ever be obtained. The UTXOs are locked in the pending state indefinitely. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
