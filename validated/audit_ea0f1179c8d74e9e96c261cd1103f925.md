### Title
`validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory certificate validation gate. The production catch-all instance implements it to **unconditionally return `Right`**, making the validation guard in `processCerts` completely ineffective. Any unprivileged peer can inject crafted Peras certificates through the object-diffusion miniprotocol; every certificate passes validation and is added to the ChainDB, where it contributes a configurable boost weight to chain selection.

---

### Finding Description

`BlockSupportsPeras` declares `validatePerasCert` as the required validation function for inbound Peras certificates: [1](#0-0) 

The production catch-all instance — the only instance currently present in the codebase — implements this function to always return `Right` without performing any cryptographic or semantic check: [2](#0-1) 

The comment explicitly acknowledges this: `"TODO: perform actual validation against all possible 'PerasValidationErr' variants"`. The instance itself is labelled `"TODO: degenerate instance for all blks to get things to compile"`: [3](#0-2) 

`processCerts`, the inbound-certificate handler in the object-diffusion miniprotocol, correctly calls `validateCert` and would reject invalid certificates if it returned `Left`. Because the implementation always returns `Right`, the rejection branch is unreachable: [4](#0-3) 

`processCerts` is wired directly to the peer-facing object-diffusion writer with the stub validator: [5](#0-4) 

Every accepted certificate is forwarded to `ChainDB.addPerasCertAsync`, where it is stored and its boost weight (`vpcCertBoost = perasWeight params`) is applied to chain selection via the Peras weight snapshot read in `chainSelectionForBlock`: [6](#0-5) 

The structural parallel to the external report is exact: `PausableUpgradeable` was inherited and `_pause()`/`_unpause()` were exposed (guard declared), but `whenNotPaused` was never applied to `withdraw`/`claim` (guard not enforced). Here, `validatePerasCert` is declared in the type class (guard declared), `processCerts` calls it (guard invoked), but the implementation always returns `Right` (guard never enforced).

---

### Impact Explanation

An unprivileged peer can craft and send arbitrary Peras certificates — for any round number and any block point — through the object-diffusion miniprotocol. Because `validatePerasCert` never rejects, every such certificate is stored in the ChainDB and contributes its full `perasWeight` boost to chain selection. This allows a peer to:

1. Boost a non-canonical or adversarially-chosen block, causing honest nodes to prefer it over the canonical chain.
2. Inject certificates for rounds that have not yet occurred or for blocks that do not exist, corrupting the Peras weight state.

This maps to: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**, and **Critical — bypass of Peras certificate checks that enables unauthorized certificate acceptance**.

---

### Likelihood Explanation

The object-diffusion miniprotocol is peer-facing and requires no authentication. Any connected peer can send a batch of `PerasCert` objects. The `processCerts` path is exercised for every inbound certificate batch. No special privileges, keys, or stake are required. Likelihood is **High** once the Peras miniprotocol is active on a node.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic and semantic validation before the Peras object-diffusion miniprotocol is enabled on production nodes. At minimum, the implementation must verify:

- The aggregate BLS signature over the election identifier and boosted block hash.
- That the voters are eligible committee members for the claimed round (VRF-based sortition proof).
- That the certificate's round number is within the acceptable window.
- That the boosted block point refers to a known, valid block.

Until real validation is in place, the object-diffusion miniprotocol for Peras certificates should be disabled or gated behind a feature flag so that no peer-supplied certificate can reach `processCerts`.

---

### Proof of Concept

1. Connect to a node with the Peras object-diffusion miniprotocol active.
2. Send a `PerasCert` message with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to a non-canonical block.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}` unconditionally.
4. The certificate is added to the ChainDB via `ChainDB.addPerasCertAsync`.
5. On the next call to `chainSelectionForBlock`, `getPerasWeightSnapshot` returns a snapshot that includes the injected certificate's boost weight.
6. `preferAnchoredCandidate` uses this weight, potentially causing the node to switch to the attacker-chosen chain.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
```
