### Title
Inverted Timelock Logic in `resolve_execute_refund_timelock` Gives DAO/Operator Less Time to Reject Suspicious Non-Pre-Authorized Refund Requests — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`resolve_execute_refund_timelock` applies the **shorter** `unsafe_refund_timelock_sec` (4 h default) to the **more dangerous** non-pre-authorized refund case (caller-supplied `refund_address`), while applying the **longer** `refund_timelock_sec` (24 h default) to the **safer** pre-authorized case. The code comment inside the function explicitly states the opposite intent: *"longer timelock to give DAO/Operator time to reject suspicious requests."* Because `request_refund` and `execute_refund` are both callable by any unprivileged NEAR account, an attacker can front-run a legitimate refund request with a fraudulent `refund_address` and execute it after only 4 h, leaving the DAO/Operator a fraction of the intended review window to intervene.

---

### Finding Description

`resolve_execute_refund_timelock` selects the timelock that must elapse before `execute_refund` may proceed:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 216-227
if refund_request.deposit_msg().refund_address.is_some() {
    // Pre-authorized refund address: privileged users can fast-track.
    if is_privileged {
        0
    } else {
        config.refund_timelock_sec          // ← 24 h (safer case)
    }
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec       // ← 4 h  (more dangerous case)
}
``` [1](#0-0) 

The two config fields have opposite semantics to what the branch uses them for:

| Config field | Default | Applied to |
|---|---|---|
| `refund_timelock_sec` | 24 h | Pre-authorized `refund_address` (safe) |
| `unsafe_refund_timelock_sec` | 4 h | Caller-supplied `refund_address` (dangerous) |

The non-pre-authorized branch is the one where an arbitrary NEAR account supplies the destination BTC address. This is the branch that requires the longest review window, yet it receives the shortest one.

---

### Impact Explanation

An attacker who front-runs a legitimate refund request with a fraudulent `refund_address` will have their malicious request accepted (first-writer wins). The DAO/Operator then has only **4 h** — not the intended 24 h — to detect and call `reject_refund`. If the window passes, the attacker calls `execute_refund`, the bridge constructs and MPC-signs a Bitcoin transaction paying the attacker's address, and the deposited BTC is permanently redirected. The victim (the original depositor) loses their BTC without ever receiving nBTC. This constitutes a significant, permanent loss of user funds — matching the **Critical** impact class (significant loss or theft of user funds) or at minimum **Medium** (bypass of bridge limits/policies with real security impact).

---

### Likelihood Explanation

The attack is realistic and requires only public information:

1. Watch NEAR for `LogDepositAddress` events to learn `deposit_msg` values and their corresponding BTC deposit addresses.
2. Watch the Bitcoin chain for UTXOs sent to those addresses that are not yet finalized by a `verify_deposit` call.
3. Call `request_refund` with the correct `deposit_msg`, the observed `tx_bytes`/`proof`, and an attacker-controlled `refund_address` — before the legitimate user does.
4. Wait 4 h and call `execute_refund`.

No privileged access, leaked keys, or external dependency compromise is required. The only race condition is against the legitimate user submitting their own refund request first, which is easily won by an automated bot.

---

### Recommendation

Swap the timelock assignments to match the stated intent:

```rust
if refund_request.deposit_msg().refund_address.is_some() {
    if is_privileged { 0 } else { config.unsafe_refund_timelock_sec }  // shorter for pre-authorized
} else {
    config.refund_timelock_sec   // longer for caller-supplied (suspicious) address
}
```

Alternatively, rename the fields (`safe_refund_timelock_sec` / `unsafe_refund_timelock_sec`) so the semantics are unambiguous, and ensure the "unsafe" field always holds the larger value. Consider also restricting `request_refund` so that only the original depositor (or a whitelisted relayer) may supply a `refund_address` when `deposit_msg.refund_address` is `None`.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address(deposit_msg)` on NEAR — the `LogDepositAddress` event is emitted publicly.
2. Alice sends 1 BTC to the derived deposit address on Bitcoin. The relayer is offline; `verify_deposit` is never called.
3. Attacker observes the NEAR event and the Bitcoin UTXO. Attacker calls:
   ```
   request_refund(
       deposit_msg = <Alice's deposit_msg>,
       refund_address = <attacker's BTC address>,
       tx_bytes = <Alice's deposit tx>,
       vout = 0,
       proof = <valid inclusion proof>
   )
   ```
   `request_refund_callback` stores the request (first-writer wins; Alice has not yet submitted hers).
4. `resolve_execute_refund_timelock` returns `config.unsafe_refund_timelock_sec` = 4 h (because `deposit_msg.refund_address` is `None`).
5. After 4 h the attacker calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying the attacker's address, MPC signs it, and broadcasts it to Bitcoin.
6. Alice's 1 BTC is permanently transferred to the attacker. The DAO/Operator had only 4 h (not 24 h) to call `reject_refund` and prevent this.
