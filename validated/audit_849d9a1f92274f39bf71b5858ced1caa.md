### Title
Unprivileged Front-Running of `execute_refund` Wastes Legitimate Caller's Storage Deposit and Hijacks Pending-Info Ownership - (File: contracts/satoshi-bridge/src/api/bridge.rs, contracts/satoshi-bridge/src/refund.rs)

### Summary
`execute_refund` carries no caller-identity restriction beyond the pause guard. Any NEAR account can observe a pending `execute_refund` call in the mempool and submit an identical call with higher gas priority. The front-runner becomes the recorded owner (`account_id`) of the resulting `BTCPendingInfo`, the legitimate caller's attached storage deposit is permanently consumed, and their transaction reverts with "pending info already exist".

### Finding Description
`execute_refund` is declared `#[payable] #[pause(except(roles(Role::DAO)))]` with no `#[access_control_any]` guard: [1](#0-0) 

Inside `resolve_execute_refund_timelock`, `env::predecessor_account_id()` is captured only to decide whether the caller is privileged enough to skip the timelock — it is never bound to the refund request itself: [2](#0-1) 

`finalize_refund_with_psbt` then records the caller as the `account_id` of the new `BTCPendingInfo` and inserts the pending-sign ID into that account's set: [3](#0-2) 

The insertion is guarded by a uniqueness check: [4](#0-3) 

Because the PSBT (and therefore `btc_pending_id`) is deterministic from the stored `RefundRequest`, whichever caller lands first wins. The second caller's transaction reverts at this `require!`, and their attached deposit — required by `resolve_execute_refund_timelock` — is not returned. [5](#0-4) 

### Impact Explanation
The BTC refund destination is fixed in the stored `RefundRequest.refund_address` and cannot be altered by the front-runner, so no BTC is stolen. However:

1. The legitimate caller's `required_balance_for_execute_refund()` NEAR deposit is permanently lost (it is consumed as storage cost even on revert).
2. The front-runner's account becomes the recorded owner of the `BTCPendingInfo`, consuming their `pending_tx_limits` slot and potentially interfering with their own future bridge operations.
3. If the front-runner's account later hits capacity limits or is otherwise unable to proceed, the refund pending info may require operator intervention to clean up.

This matches the **Low** allowed impact: publicly reachable stuck-state or invariant fault in a production bridge path without direct theft.

### Likelihood Explanation
`execute_refund` is callable by any NEAR account after the timelock elapses. NEAR transaction ordering is observable before finality. Any actor monitoring the bridge (e.g., a competing relayer or a griefing bot) can replicate the call with higher gas. No special knowledge or privilege is required beyond reading the `utxo_storage_key` from on-chain state or event logs. [6](#0-5) 

The `RefundRequested` event emits the `utxo_storage_key` publicly, making the target trivially discoverable.

### Recommendation
Bind the executor's identity to the refund request at submission time, or enforce it at execution time. Two options:

1. **Store the authorized executor in `RefundRequest`**: During `request_refund`, record `executor: env::predecessor_account_id()` in the `RefundRequest`. In `execute_refund`, require `env::predecessor_account_id() == refund_request.executor` (with a DAO/Operator override).

2. **Pass caller through to `finalize_refund_with_psbt` from the public entry point**: Capture `env::predecessor_account_id()` in `execute_refund` and thread it explicitly through `internal_execute_refund` → `finalize_refund_with_psbt`, then verify it matches the stored requester or a whitelisted executor.

### Proof of Concept
1. Alice calls `request_refund(...)` for UTXO `abc@0`, paying the storage deposit. The `RefundRequested` event is emitted with `utxo_storage_key = "abc@0"`.
2. The timelock elapses. Alice constructs and broadcasts `execute_refund("abc@0", None)` with the required attached deposit.
3. Bob observes Alice's pending transaction. Bob submits an identical `execute_refund("abc@0", None)` with higher gas priority.
4. Bob's transaction executes first. `finalize_refund_with_psbt` records `account_id = Bob`, inserts the pending-sign ID into Bob's account, and succeeds.
5. Alice's transaction executes next. It reaches the `require!(... .insert(...).is_none(), "pending info already exist")` check and reverts. Alice's attached deposit is consumed.
6. Alice has lost her storage deposit. Bob owns the `BTCPendingInfo`. The BTC refund still proceeds to the original `refund_address` (no theft), but Alice's funds are wasted and the pending info is under an unintended owner.

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
