### Title
Stub `validatePerasCert` Permits Unconstrained Peras Certificate Acceptance, Enabling Chain Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`)

---

### Summary

The `processCerts` function, which handles all inbound Peras certificates received from network peers, delegates certificate validation to `validatePerasCert mkPerasParams` — a function explicitly marked with a `TODO` comment as a placeholder pending real implementation. Because no genuine cryptographic or committee-membership checks are enforced at this boundary, any unprivileged peer can submit a crafted `PerasCert` that is accepted, stored in the `PerasCertDB`, and used to inflate the chain-selection weight of an arbitrary block. This is the direct consensus analog of the `strategyMinting` issue: an unconstrained privileged action (here, certificate acceptance) that can produce an invalid state (here, a non-canonical chain being preferred) without any backing proof of legitimacy.

---

### Finding Description

**Root cause — stub validator at the peer-facing ingest boundary**

In `PerasCert.hs`, both production pool writers call `processCerts` with the same placeholder validator:

```haskell
-- makePerasCertPoolWriterFromCertDB (line 103)
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place

-- makePerasCertPoolWriterFromChainDB (line 126)
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
```

`processCerts` has the signature:

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
```

The third argument is the validation function. When it returns `Right`, the certificate is wrapped in the `ValidatedPerasCert` newtype and forwarded to the database. Because `validatePerasCert mkPerasParams` is a stub, the `ValidatedPerasCert` wrapper provides false assurance: it carries no proof that committee membership, BLS aggregate signature, quorum threshold, or round/slot constraints were actually checked.

**Corroborating TODO in the storage layer**

`implAddCert` in `PerasCertDB/Impl.hs` carries a matching admission:

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert ::
  IOLike m =>
  PerasCertDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
```

Both the ingest boundary and the storage layer therefore lack real validation.

**End-to-end exploit path**

1. Attacker connects as a peer via the ObjectDiffusion mini-protocol.
2. Attacker crafts a `PerasCert` with an arbitrary `boostedBlock` (pointing to a block on an adversarial fork) and an arbitrarily large `boost` value; any signature bytes are accepted because the stub does not verify them.
3. `processCerts` calls `validatePerasCert mkPerasParams`; the stub returns `Right`, producing a `ValidatedPerasCert`.
4. The cert is timestamped and forwarded to `ChainDB.addPerasCertAsync`.
5. `chainSelSync` in `ChainSel.hs` (lines 483–532) adds the cert to `PerasCertDB` via `PerasCertDB.addCert cdbPerasCertDB cert` and triggers `chainSelectionForBlock` for the boosted block.
6. `implGetWeightSnapshot` in `PerasCertDB/Impl.hs` (lines 203–214) now returns a `PerasWeightSnapshot` that includes the attacker-chosen boost for the attacker-chosen block.
7. `weightedSelectView` in `SelectView.hs` (lines 94–112) computes `wsvWeightBoost` from this snapshot; `wsvTotalWeight` (line 58–61) adds it to the block number.
8. `preferCandidate` (lines 81–87) switches to the adversarial chain if its total weight exceeds the honest chain's total weight.

### Impact Explanation

**High — chain selection manipulation by an unprivileged peer.**

An attacker with no stake, no keys, and no privileged access can cause an honest node to abandon the canonical chain and adopt an adversarial fork by submitting a single crafted certificate. The Peras weight boost is unbounded (`PerasWeight` is a `Word64`), so a single certificate can make any block appear arbitrarily heavier than the honest tip. This violates the core Ouroboros Peras chain-selection invariant that weight boosts must be backed by a quorum of legitimately elected committee members.

---

### Likelihood Explanation

**High.** The ObjectDiffusion protocol is a standard peer-to-peer channel; any connected peer can submit certificates. No key compromise, stake majority, or operator access is required. The attack is deterministic and requires crafting a single well-formed `PerasCert` struct with arbitrary field values.

---

### Recommendation

Replace the stub `validatePerasCert mkPerasParams` with a real implementation that, before wrapping a certificate in `ValidatedPerasCert`, verifies:

1. **Committee membership** — each claimed signer is in the voting committee for the relevant epoch, using the ledger's stake distribution (via `VotingCommittee` / `extWFAStakeDistr`).
2. **BLS aggregate signature** — the aggregate signature over `(electionId, candidate)` verifies against the aggregate of the signers' public keys, using `verifyAggregateVoteSignature`.
3. **Quorum threshold** — the combined voting weight of the signers meets the required quorum.
4. **Round/slot constraints** — the certificate's round number and boosted block slot are within the permitted window relative to the current ledger state.

The `mkPerasParams` placeholder must be replaced with actual protocol parameters threaded from the ledger configuration. The `implAddCert` TODO (issue #120) should be resolved as a defense-in-depth measure, but the primary fix must be at the `processCerts` validation boundary.
