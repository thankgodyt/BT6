### Title
Off-by-One Gas Floor Causes `handle_post_action` to Always Panic When Minimum Allowed Gas Is Specified - (File: contracts/nbtc/src/lib.rs, contracts/satoshi-bridge/src/deposit_msg.rs)

---

### Summary

The bridge-side validation in `check_deposit_msg` permits a per-`PostAction` gas value as low as `MIN_PER_POST_ACTIONS_GAS = 30 Tgas`. However, `handle_post_action` in the nBTC contract enforces a **strict** greater-than check against `GAS_FOR_FT_TRANSFER_CALL = 30 Tgas`. When a user specifies exactly 30 Tgas — the minimum the bridge accepts — the receipt always panics, silently dropping the post-action while nBTC is already minted.

---

### Finding Description

In `contracts/satoshi-bridge/src/deposit_msg.rs`, the minimum per-post-action gas floor is defined and enforced with a `<` (strict less-than) comparison:

```rust
const MIN_PER_POST_ACTIONS_GAS: Gas = Gas::from_tgas(30);
// ...
if gas.as_gas() < MIN_PER_POST_ACTIONS_GAS.as_gas() { // rejects only < 30 Tgas
``` [1](#0-0) [2](#0-1) 

This means a `PostAction` with `gas = Some(Gas::from_tgas(30))` passes bridge-side validation.

In `contracts/nbtc/src/lib.rs`, the reserved overhead constant is:

```rust
const GAS_FOR_FT_TRANSFER_CALL: Gas = Gas::from_tgas(30);
``` [3](#0-2) 

`handle_post_action` then enforces a **strict** greater-than guard:

```rust
require!(
    env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
    "More gas is required"
);
``` [4](#0-3) 

When `prepaid_gas == 30 Tgas`, the condition `30 > 30` is `false`, so the receipt panics unconditionally. Because `handle_post_actions` dispatches each `handle_post_action` with `.detach()`, this panic is silently swallowed — the nBTC mint has already completed and is unaffected. [5](#0-4) 

The full call chain is:

1. Relayer calls `verify_deposit` → bridge calls `internal_mint_promise` with `GAS_FOR_MINT_CALL = 90 Tgas`. [6](#0-5) 
2. nBTC `mint()` calls `handle_post_actions(...).detach()`. [7](#0-6) 
3. `handle_post_actions` dispatches `handle_post_action` with the user-supplied 30 Tgas via `.detach()`. [5](#0-4) 
4. `handle_post_action` panics at the `require!` guard; the receipt fails silently. [4](#0-3) 

---

### Impact Explanation

The post-action (e.g., auto-deposit of freshly minted nBTC into a whitelisted DeFi protocol) silently fails. The nBTC is minted to the user's account but never forwarded to the intended `receiver_id`. The user's funds are not lost, but the intended cross-contract action is permanently skipped with no on-chain error surfaced to the user. This constitutes **broken callback rollback / stuck bridge state** — a Medium-severity impact per the allowed scope.

---

### Likelihood Explanation

Any unprivileged user constructing a `DepositMsg` can set `gas: Some(Gas::from_tgas(30))` for a `PostAction`. The bridge-side check explicitly accepts this value (it only rejects values strictly below 30 Tgas). The failure is therefore deterministic and 100% reproducible for any deposit that uses the minimum allowed gas value. No special role or privileged access is required.

---

### Recommendation

Align the two constants so the floor enforced during validation is strictly greater than the gas reserved for overhead. Either:

1. Raise `MIN_PER_POST_ACTIONS_GAS` to at least `GAS_FOR_FT_TRANSFER_CALL + 1` (or a meaningful margin above it), **or**
2. Change the guard in `handle_post_action` from `>` to `>=` and ensure the remaining `receiver_gas` is still sufficient for `ft_on_transfer`.

The safest fix is option 1 — set `MIN_PER_POST_ACTIONS_GAS` to a value that leaves meaningful gas for the downstream `ft_on_transfer` call after the 30 Tgas overhead is subtracted.

---

### Proof of Concept

1. User constructs:
   ```json
   DepositMsg {
     recipient_id: "alice.near",
     post_actions: [{
       receiver_id: "<whitelisted-dapp>",
       amount: "10000",
       msg: "",
       gas: "30000000000000"   // exactly 30 Tgas = MIN_PER_POST_ACTIONS_GAS
     }]
   }
   ```
2. User sends BTC to the derived deposit address.
3. Relayer calls `verify_deposit`. Bridge validates gas: `30 Tgas >= 30 Tgas` → **passes**. [2](#0-1) 
4. nBTC is minted; `handle_post_actions` is called with `.detach()`. [7](#0-6) 
5. `handle_post_action` receives `prepaid_gas = 30 Tgas`; `require!(30 > 30)` → **panics**. [4](#0-3) 
6. Receipt fails silently. Alice's nBTC is minted but never forwarded to the dApp. The post-action is permanently lost with no rollback or error event.
