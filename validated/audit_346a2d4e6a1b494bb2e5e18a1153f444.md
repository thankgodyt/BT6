### Title
Unprivileged Attacker Can Front-Run `request_refund` to Redirect Victim's BTC to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund` contains no check that the caller is the `recipient_id` named in the `deposit_msg`. Any NEAR account can submit a refund request for any unfinalized deposit and supply an arbitrary `refund_address`. Because the stored `refund_address` is used verbatim when `execute_refund` is later called, an attacker who front-runs the victim's own refund request can redirect the victim's BTC to an attacker-controlled Bitcoin address.

### Finding Description
`internal_request_refund` (refund.rs lines 137–184) verifies the BTC transaction via the light client and then calls `request_refund_callback` (lines 497–581). Inside the callback the only address-ownership check is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

This guard is only active when the depositor pre-committed a `refund_address` inside the `deposit_msg` itself. For the common case where `deposit_msg.refund_address` is `None` (the depositor did not pre-authorize an address), the caller-supplied `refund_address` is accepted unconditionally and stored:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,          // ← attacker-controlled value
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
```

The `deposit_msg` is public: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`, path, and deposit address. The BTC transaction is public on-chain. An attacker can therefore:

1. Monitor `LogDepositAddress` events to learn a victim's `deposit_msg`.
2. Watch the Bitcoin network for a deposit to that address that is never finalized (e.g., amount below `min_deposit_amount`, or the relayer is delayed).
3. Call `request_refund` with the victim's `deposit_msg` but the attacker's own BTC address as `refund_address`.
4. The duplicate-request guard (`"Refund request already exists for this UTXO"`) prevents the victim from submitting their own request afterward.
5. After `unsafe_refund_timelock_sec` (default 14 days) elapses without DAO intervention, call `execute_refund`.
6. `build_refund_output` parses the stored `refund_address` (the attacker's address) and the MPC pipeline signs a transaction paying the victim's BTC to the attacker.

The only on-chain mitigation is that DAO/Operator can call `reject_refund` during the 14-day window. The victim themselves cannot reject the request (only DAO/Operator can, unless the UTXO was already verified via a deposit).

### Impact Explanation
If the DAO fails to monitor and reject the malicious request within the 14-day window, the victim's BTC is permanently transferred to the attacker's Bitcoin address. The victim loses their entire deposited BTC with no on-chain recourse. This constitutes significant theft of user funds.

### Likelihood Explanation
The `deposit_msg` is emitted publicly via `LogDepositAddress` events. The BTC transaction is visible on-chain. Deposits that fall below `min_deposit_amount` or are delayed by relayer issues are a realistic scenario. The attacker only needs to pay the `required_balance_for_request_refund` storage deposit and wait 14 days. The DAO must actively monitor all refund requests globally; a single missed or delayed review is sufficient for the attack to succeed.

### Recommendation
Add a caller-identity check in `internal_request_refund` or `request_refund_callback` that requires the caller to be the `recipient_id` specified in the `deposit_msg`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id,
    "Only the deposit recipient may request a refund"
);
```

Alternatively, if third-party refund submission must be supported (e.g., for relayer-assisted flows), require that `deposit_msg.refund_address` is always pre-committed (`Some`) so the caller cannot substitute an arbitrary address. The current `unsafe_refund_timelock_sec` path that accepts a caller-supplied address with no ownership proof should be removed or gated behind a privileged role.

### Proof of Concept

1. Alice calls `get_user_deposit_address({"recipient_id": "alice.near"})`. The bridge emits `LogDepositAddress` with the full `deposit_msg` and deposit address.
2. Alice sends 0.0005 BTC to the deposit address (below `min_deposit_amount`), so `verify_deposit` is never called.
3. Attacker Eve observes the event and the BTC transaction on-chain.
4. Eve calls `request_refund(deposit_msg={"recipient_id":"alice.near"}, refund_address="<Eve's BTC address>", tx_bytes=<Alice's tx>, vout=0, proof=<valid proof>)` with the required NEAR storage deposit.
5. `request_refund_callback` verifies the proof, confirms the output script matches Alice's deposit address, finds `deposit_msg.refund_address == None`, and stores Eve's BTC address as the `refund_address`.
6. Alice attempts `request_refund` for the same UTXO — it reverts with `"Refund request already exists for this UTXO"`.
7. After 14 days, Eve calls `execute_refund("alice_txid@0", None)`. `build_refund_output` parses Eve's BTC address, the MPC signs the transaction, and Alice's BTC is sent to Eve.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
