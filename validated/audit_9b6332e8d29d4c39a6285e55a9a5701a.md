### Title
Uninitialized `_systemAddress` After `upgradeToken` to `HyperliquedBridgeToken` Permanently Burns Bridged Funds — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`, `evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

### Summary
`OmniBridge.upgradeToken` always calls `upgradeToAndCall(implementation, bytes(""))` with empty calldata. `HyperliquedBridgeToken` introduces a critical new state variable `_systemAddress` that is only set inside `initialize()`, which is guarded by the `initializer` modifier and therefore cannot be called on an already-initialized proxy. No `reinitializer()` function exists. After the upgrade, `_systemAddress` is `address(0)`, causing the 3-arg `mint` to immediately burn every token it mints, resulting in permanent loss of bridged funds for users.

### Finding Description
`OmniBridge.upgradeToken` is the designated path for upgrading deployed bridge-token proxies to a new implementation: [1](#0-0) 

It unconditionally passes `bytes("")` as the call data, so no post-upgrade initialization is ever performed.

`HyperliquedBridgeToken` extends `BridgeToken` and introduces two new storage slots that must be set at initialization time: [2](#0-1) 

Both are written only inside `initialize()`, which is protected by the `initializer` modifier: [3](#0-2) 

Because the proxy was already initialized as a `BridgeToken`, the `initializer` modifier will revert any subsequent call to `initialize()`. No `reinitializer()` variant exists anywhere in the contract. The result is that after `upgradeToken` points the proxy at `HyperliquedBridgeToken`, `_systemAddress` is permanently `address(0)`.

### Impact Explanation
The 3-arg `mint` path, used by `OmniBridge.finTransfer` whenever `payload.message.length > 0`, executes: [4](#0-3) 

Step 1 (`_mint`) credits `value` tokens to `account`. Step 2 (`_update(account, address(0), value)`) immediately transfers all of them to `address(0)`, which is the OpenZeppelin ERC20 burn path. The recipient receives zero tokens while the bridge's accounting records the transfer as complete. The loss is irreversible.

Additionally, `coreReceiveWithData` becomes permanently bricked: [5](#0-4) 

Because `_systemAddress == address(0)` and `msg.sender` can never be `address(0)`, every call reverts with `NotSystemAddress`, freezing the HyperCore→HyperEVM bridge path for that token.

The `finTransfer` dispatch that triggers the 3-arg mint: [6](#0-5) 

### Likelihood Explanation
`upgradeToken` is a standard admin operation explicitly provided for upgrading bridge tokens. Upgrading an existing `BridgeToken` proxy to `HyperliquedBridgeToken` is the natural migration path when onboarding a Hyperliquid-specific token. The broken state is silent — the upgrade transaction succeeds, no revert occurs, and the bug only manifests when a user bridges with a non-empty message. Any relayer or user who submits a `finTransfer` with `message.length > 0` after the upgrade will lose their funds.

### Recommendation
Add a `reinitializer(2)` function to `HyperliquedBridgeToken` that sets `_systemAddress` and `HYPER_CORE_DEPLOYER_SLOT`:

```solidity
function initializeV2(
    address systemAddress_,
    address hyperCoreDeployer_
) external reinitializer(2) {
    _systemAddress = systemAddress_;
    bytes32 slot = HYPER_CORE_DEPLOYER_SLOT;
    assembly { sstore(slot, hyperCoreDeployer_) }
    emit HyperCoreDeployerSet(hyperCoreDeployer_);
}
```

Update `OmniBridge.upgradeToken` to accept and forward initialization calldata instead of hardcoding `bytes("")`:

```solidity
function upgradeToken(
    address tokenAddress,
    address implementation,
    bytes calldata initData          // ← caller supplies reinitializer calldata
) external onlyRole(DEFAULT_ADMIN_ROLE) {
    require(isBridgeToken[tokenAddress], "ERR_NOT_BRIDGE_TOKEN");
    BridgeToken(tokenAddress).upgradeToAndCall(implementation, initData);
}
```

### Proof of Concept
1. Admin deploys `BridgeToken` implementation and `HyperliquedBridgeToken` implementation.
2. `OmniBridge.deployToken` creates a `BridgeToken` proxy `P` (initialized, version 1).
3. Admin calls `OmniBridge.upgradeToken(P, hlImpl)`. Internally: `P.upgradeToAndCall(hlImpl, bytes(""))`. Upgrade succeeds; `_systemAddress` is `address(0)`.
4. Relayer calls `OmniBridge.finTransfer(sig, payload)` where `payload.message.length > 0` and `payload.tokenAddress == P`.
5. `finTransfer` calls `IBridgeToken(P).mint(recipient, amount, message)` — the 3-arg overload.
6. Inside `HyperliquedBridgeToken.mint`: `_mint(recipient, amount)` credits tokens; `_update(recipient, address(0), amount)` burns them all.
7. Recipient balance: 0. Tokens are permanently destroyed. Bridge accounting marks the transfer complete.
