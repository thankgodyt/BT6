Audit Report

## Title
Unchecked `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Loss of Bridged Funds - (File: near/omni-bridge/src/lib.rs)

## Summary

When finalizing a bridge transfer to a NEAR recipient for a non-deployed (externally-locked) token with an empty `msg`, `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`. The `is_refund_required` helper unconditionally returns `false` in this branch without inspecting the `ft_transfer` promise result. If `ft_transfer` panics, the NEAR runtime rolls back the token delivery but still executes the callback, which silently treats the failure as success: the locked-token escrow counter remains decremented, the finalization nonce is consumed, and the user's bridged funds are permanently lost.

## Finding Description

In `process_fin_transfer_to_near`, `unlock_tokens_if_needed` is called synchronously before dispatching `send_tokens`, decrementing `locked_tokens[(origin_chain, token)]`:

```rust
// near/omni-bridge/src/lib.rs L1881-1885
let lock_actions = vec![self.unlock_tokens_if_needed(
    transfer_message.get_origin_chain(),
    &token,
    transfer_message.amount.0,
)];
```

`send_tokens` dispatches a plain `ft_transfer` when `msg.is_empty()`:

```rust
// near/omni-bridge/src/lib.rs L2102-2106
} else if msg.is_empty() {
    ext_token::ext(token)
        .with_attached_deposit(ONE_YOCTO)
        .with_static_gas(FT_TRANSFER_GAS)
        .ft_transfer(recipient, amount, None)
```

The callback is chained with `is_ft_transfer_call = !msg.is_empty()`, so for the empty-msg path it is `false`:

```rust
// near/omni-bridge/src/lib.rs L1967-1977
.then(
    Self::ext(env::current_account_id())
        .with_static_gas(SEND_TOKENS_CALLBACK_GAS)
        .fin_transfer_send_tokens_callback(
            transfer_message,
            &fee_recipient,
            !msg.is_empty(),   // false when msg is empty
            predecessor_account_id,
            lock_actions,
        ),
)
```

Inside `is_refund_required`, the `false` branch never reads the promise result:

```rust
// near/omni-bridge/src/lib.rs L1800-1803
} else {
    // Not ft_transfer_call: don't refund
    false
}
```

Because `is_refund_required` returns `false`, the callback skips the entire recovery block (`revert_lock_actions`, `remove_fin_transfer`, `FailedFinTransferEvent`) and instead emits `FinTransferEvent` and pays the fee to the relayer, as if the transfer succeeded. The `revert_lock_actions` path — which would call `lock_tokens` to restore the escrow counter — is never reached.

## Impact Explanation

This is a concrete critical impact matching **escrow mis-accounting and permanent loss of bridged funds**:

1. `locked_tokens[(origin_chain, token)]` is permanently decremented without the corresponding NEP-141 delivery occurring. Future origin-chain withdrawals can be processed against a counter that no longer reflects actual on-NEAR holdings.
2. The finalization nonce is consumed (`add_fin_transfer` records it; `remove_fin_transfer` is never called on failure), so the proof cannot be replayed to retry the transfer.
3. The user receives zero tokens on NEAR while the origin-chain escrow treats the funds as released.

## Likelihood Explanation

The `ft_transfer` path is the default for all simple (no-message) bridge withdrawals. Failure conditions are realistic and externally triggerable:

- **Gas exhaustion**: `FT_TRANSFER_GAS` is a static constant; a token contract with non-trivial transfer logic can exhaust it.
- **Token-specific rejection**: NEP-141 tokens may implement blacklists, pause mechanisms, or transfer limits that cause `ft_transfer` to panic.
- **Storage registration race**: Despite pre-transfer storage checks, a race or incorrect deposit amount can leave the recipient unregistered, causing `ft_transfer` to panic.

Any of these conditions can be triggered by the token contract's own state, not requiring attacker privilege. The affected path is the most common withdrawal flow.

## Recommendation

Extend `is_refund_required` to check the promise result unconditionally, regardless of whether the call was `ft_transfer` or `ft_transfer_call`:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
        Err(_) => true, // promise panicked — always revert
        Ok(value) if is_ft_transfer_call => {
            near_sdk::serde_json::from_slice::<U128>(&value)
                .map_or(false, |amount| amount.0 == 0)
        }
        Ok(_) => false, // ft_transfer succeeded
    }
}
```

This ensures that a panicking `ft_transfer` triggers `revert_lock_actions` (restoring the escrow counter), `remove_fin_transfer` (freeing the nonce for replay), and `FailedFinTransferEvent` logging.

## Proof of Concept

1. Alice locks 1000 USDC on Ethereum; a relayer submits the proof via `fin_transfer`.
2. `process_fin_transfer_to_near` calls `unlock_tokens_if_needed`, decrementing `locked_tokens[(Eth, usdc)]` by 1000, and records the finalization nonce via `add_fin_transfer`.
3. `send_tokens` dispatches `ft_transfer(alice.near, 1000)` with `FT_TRANSFER_GAS` (empty `msg`).
4. The USDC token contract panics (e.g., gas exhaustion or blacklist). NEAR runtime rolls back the token transfer but schedules `fin_transfer_send_tokens_callback`.
5. Callback executes: `is_ft_transfer_call = false` → `is_refund_required(false)` returns `false` without reading the promise result.
6. The `else` branch fires: fee is sent to the relayer, `FinTransferEvent` is logged.
7. `revert_lock_actions` is never called → `locked_tokens[(Eth, usdc)]` stays at the decremented value.
8. `remove_fin_transfer` is never called → nonce is consumed, replay is impossible.
9. Alice receives 0 USDC on NEAR; the Ethereum escrow counter is permanently mis-accounted.

A local integration test can reproduce this by deploying a mock NEP-141 token whose `ft_transfer` panics unconditionally, then calling `fin_transfer` with a valid proof and an empty `msg`, and asserting that `locked_tokens` was decremented while the recipient balance remains zero.
