### Title
Front-Running `request_refund` Allows Attacker to Redirect BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
When a user submits `request_refund` for a deposit whose `deposit_msg.refund_address` is `None`, an attacker can observe the pending NEAR transaction in the mempool, copy all proof parameters, and front-run it with their own BTC address. Because only one refund request can exist per UTXO, the attacker's request wins the race and the subsequent `execute_refund` sends the BTC to the attacker's address.

### Finding Description
`request_refund` is a publicly callable, payable function. When `deposit_msg.refund_address` is `None`, the caller may supply any arbitrary `refund_address`: [1](#0-0) 

The callback enforces uniqueness — only the first request for a given UTXO is accepted: [2](#0-1) 

The stored `refund_address` is later used verbatim when `execute_refund` builds the refund PSBT and sends BTC on-chain: [3](#0-2) 

`execute_refund` itself has no caller restriction beyond the timelock: [4](#0-3) 

Because all parameters needed to construct a valid `request_refund` call (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are visible in the NEAR mempool before the transaction is included in a block, an attacker can copy them verbatim and race the user with their own `refund_address`.

### Impact Explanation
If the attacker's transaction is ordered before the victim's, the refund request is stored with the attacker's BTC address. The victim's transaction reverts with "Refund request already exists for this UTXO". After `unsafe_refund_timelock_sec` elapses, `execute_refund` constructs and signs a Bitcoin transaction paying the full deposit amount (minus gas fee) to the attacker's address. This constitutes direct, permanent theft of the user's bridged BTC — a critical impact.

### Likelihood Explanation
NEAR's mempool is observable. Any account can submit `request_refund` (the function is payable and has no role gate beyond the pause check). The attacker only needs to attach the same storage deposit and copy the proof. The `unsafe_refund_timelock_sec` gives the DAO a window to reject, but the DAO is not guaranteed to monitor every request, and the timelock is a configuration value that may be short. The attack is straightforward and requires no special privilege.

### Recommendation
Require `deposit_msg.refund_address` to be `Some` for all `request_refund` calls, so the refund destination is committed at deposit time and cannot be overwritten by a racing transaction. Alternatively, bind the refund request to `env::predecessor_account_id()` and require that only the original submitter (or a privileged role) can execute it, preventing a third party from benefiting from a front-run.

### Proof of Concept
1. User deposits BTC with a `deposit_msg` that has `refund_address: None`.
2. User submits:
   ```
   request_refund(deposit_msg, "user_btc_addr", tx_bytes, vout, proof, None)
   ```
3. Attacker observes the pending NEAR transaction, extracts all parameters, and submits:
   ```
   request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)
   ```
   with sufficient gas to be ordered first.
4. Attacker's callback succeeds; `refund_requests[utxo_key].refund_address = "attacker_btc_addr"` is stored. [5](#0-4) 
5. User's callback reverts: "Refund request already exists for this UTXO".
6. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_key, None)`.
7. `finalize_refund_with_psbt` builds a PSBT paying `refund_amount` to `"attacker_btc_addr"`. [6](#0-5) 
8. MPC signs and broadcasts; BTC is permanently transferred to the attacker.

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
