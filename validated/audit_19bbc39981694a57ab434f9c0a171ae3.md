### Title
Corrupted UTXO `tx_bytes` in Safe Deposit Path Causes Permanently Unspendable Bridge UTXO - (File: contracts/satoshi-bridge/src/btc_light_client/deposit.rs)

### Summary

In `internal_safe_verify_deposit_entry`, when the submitted `tx_bytes` exceeds 10,000 bytes, the code silently replaces the stored UTXO's `tx_bytes` with `vec![0u8; 300]` (300 zero bytes) while still computing `deposit_amount` and `utxo.balance` from the original transaction. The nBTC mint proceeds with the correct amount, but the UTXO stored in `data.utxos` carries garbage bytes in its `tx_bytes` field. Any downstream operation that requires the full transaction bytes to spend this UTXO — such as constructing a non-witness PSBT input or passing the raw transaction to the MPC signing service — will fail, permanently locking the deposited BTC inside the bridge.

### Finding Description

`internal_safe_verify_deposit_entry` (lines 171–237) processes the safe-deposit path used by Omni Bridge. The sequence is:

1. **Lines 191–193** — decode `tx_bytes` and extract `deposit_amount` from the real transaction output.
2. **Lines 195–202** — verify the output's `script_pubkey` matches the bridge's deposit address.
3. **Lines 204–209** — if `tx_bytes.len() > 10_000`, replace `tx_bytes` with `vec![0u8; 300]`.
4. **Lines 211–216** — build the `UTXO` struct using the (now-zeroed) `tx_bytes` but the correct `balance`.
5. **Lines 223–236** — pass `deposit_amount` (from the original tx) to `internal_safe_verify_deposit`, which mints nBTC for the full amount.

The UTXO stored in `data.utxos` therefore has:
- `balance`: correct satoshi value from the real transaction
- `tx_bytes`: `[0u8; 300]` — invalid garbage

The `UTXO` struct explicitly carries `tx_bytes` as a first-class field alongside `balance`, `path`, and `vout`. The `generate_vutxos` helper in `psbt.rs` (lines 266–283) constructs PSBT inputs from `v.get_amount()` and `v.get_path()`, but the raw `tx_bytes` field is retained in the stored struct and is available to any code path that reads the UTXO directly. For non-segwit (legacy) inputs the PSBT `non_witness_utxo` field requires the full parent transaction; zeroed bytes would produce an invalid PSBT that the MPC service cannot sign. Even for segwit inputs, if the MPC signing pipeline or any future code path reads `utxo.tx_bytes` to reconstruct the spending transaction, it will receive garbage and fail.

### Impact Explanation

A UTXO deposited via a large Bitcoin transaction (>10,000 bytes) through the safe-deposit path is stored with corrupted `tx_bytes`. The bridge has minted nBTC for the full deposit amount, so the user holds valid tokens. However, the bridge can never correctly spend this UTXO: any attempt to construct a valid spending transaction or PSBT for it will use zeroed bytes, producing an invalid or unverifiable transaction. The BTC is permanently locked in the bridge's MPC-controlled address with no recovery path short of operator intervention and a manual key-signing ceremony outside the contract. This constitutes permanent locking of protocol-controlled funds and a backed-supply discrepancy (nBTC in circulation without spendable BTC backing).

**Allowed impact matched**: *Medium — stuck bridge state requiring operator intervention* / *Critical — significant permanent locking of user or protocol funds*.

### Likelihood Explanation

A Bitcoin transaction exceeding 10,000 bytes requires many inputs (e.g., consolidating hundreds of small UTXOs into one deposit). While uncommon in normal usage, it is entirely within the Bitcoin protocol limits (standard relay limit is 100 kB). A user who controls many small UTXOs can deliberately construct such a transaction and route it through the Omni Bridge safe-deposit path (`verify_deposit_v2` with `safe_deposit: Some(…)` or the deprecated `safe_verify_deposit`). No privileged access is required beyond being a bridge user with a large UTXO set. The relayer submitting the proof is trusted but does not need to be malicious — any honest relayer will trigger the bug by submitting a legitimately large transaction.

### Recommendation

Remove the truncation block entirely. If storage cost for large `tx_bytes` is a concern, store only the specific output (`vout` index and its `TxOut`) rather than the full transaction, and update the PSBT construction path accordingly. At minimum, if `tx_bytes` must be bounded, the function should **reject** (panic/require) oversized transactions rather than silently replacing them with zeros:

```rust
require!(
    tx_bytes.len() <= 10_000,
    "tx_bytes exceeds maximum allowed size"
);
```

This ensures the deposit fails loudly rather than storing a UTXO that can never be spent.
