### Title
Peras Certificate Validation Unconditionally Accepts Any Inbound Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. Because this function is the sole validator called on inbound Peras certificates received from network peers, any unprivileged peer can inject arbitrary crafted certificates that are accepted into the `PerasCertDB` / `ChainDB` and immediately influence chain selection by boosting arbitrary blocks.

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for accepting Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only concrete instance in the codebase — the "degenerate instance for all blks" — implements this as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is directly wired into the production network ingest path. Both `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` pass `(validatePerasCert mkPerasParams)` as the validator to `processCerts`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` is the function that processes every batch of inbound `PerasCert` objects received from a remote peer over the ObjectDiffusion mini-protocol. It calls `validateCert` on each certificate and, if all pass, adds them to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [3](#0-2) 

Because `validatePerasCert` never returns `Left`, every certificate from every peer passes validation. The accepted certificate is stored with `vpcCertBoost = perasWeight params`, which is the boost weight applied during chain selection. No check is made on:
- The cryptographic aggregate BLS signature over the voters
- Whether the claimed voters are actually eligible committee members
- Whether the round number is plausible relative to the current chain tip
- Whether the boosted block hash corresponds to any known block

The analog to the external report is exact: just as `_getPcsAttestationData` only checks that the returned bytes are non-empty and performs no expiry or issuer-matching validation, `validatePerasCert` only checks that a certificate struct exists and performs no cryptographic or semantic validation. [4](#0-3) 

### Impact Explanation

An unprivileged peer can craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` (pointing to any block hash, including one on an adversarial fork). The certificate passes `validatePerasCert` unconditionally, is stored in the `PerasCertDB`, and its `vpcCertBoost` weight is applied during chain selection. This allows an adversary to make an honest node prefer a non-canonical or adversarially-controlled chain by injecting fake Peras boost certificates, bypassing the entire Peras voting and quorum mechanism. This matches the allowed impact: **bypass of Peras certificate checks that enables unauthorized certificate acceptance**.

### Likelihood Explanation

The attack requires only a network connection to the target node. No stake, no keys, no operator access, and no prior compromise are needed. The ObjectDiffusion mini-protocol is a standard node-to-node protocol. The vulnerability is present in every code path that processes inbound certificates, including both the `PerasCertDB`-direct path and the `ChainDB` path used in production. Likelihood is high given the complete absence of any validation gate.

### Recommendation

- **Short term**: Replace the stub `validatePerasCert` implementation with one that performs at minimum: (1) aggregate BLS signature verification over the claimed voter set, (2) committee membership and eligibility checks for each claimed voter, and (3) a plausibility check on the round number relative to the current chain tip.
- **Long term**: Complete the plumbing referenced in the TODO comments (cardano-peras issue #73 and #120) so that `validatePerasCert` receives the correct `VotingCommittee` context rather than the static `mkPerasParams` placeholder, enabling full cryptographic and semantic validation of inbound certificates before they influence chain selection.

### Proof of Concept

1. Connect to a target node running the Peras-enabled consensus layer via the ObjectDiffusion mini-protocol.
2. Send a batch containing a single crafted `PerasCert`:
   - `pcCertRound`: any round number not yet in the node's `PerasCertDB`
   - `pcCertBoostedBlock`: the `Point` of any block on an adversarial fork
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}` unconditionally.
4. The certificate is added to the `ChainDB` via `ChainDB.addPerasCertAsync`.
5. Chain selection now applies the Peras boost weight to the adversarially-chosen block, potentially causing the node to prefer the adversarial fork over the honest chain. [5](#0-4) [6](#0-5)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
