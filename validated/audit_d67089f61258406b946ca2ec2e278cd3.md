### Title
Stub `validatePerasCert` Allows Peer-Injected Future-Round Certificate to Corrupt `pcdsLatestCertSeen`, Permanently Suppressing Peras Voting - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance ships a `validatePerasCert` stub that unconditionally accepts every inbound certificate. An unprivileged peer can exploit this via the ObjectDiffusion mini-protocol to inject a certificate whose round number is arbitrarily far in the future. Because `implAddCert` monotonically advances `pcdsLatestCertSeen` to the highest-round certificate ever seen, the injected future-round certificate permanently corrupts that field. Both Peras voting-rule paths (VR-1A and VR-2A) then fail for every subsequent round, silencing the victim node's votes indefinitely. The adversary can repeat the injection with an even higher round number to extend the suppression window without limit.

---

### Finding Description

**Step 1 – The stub validation.**

`validatePerasCert` in the degenerate `BlockSupportsPeras` instance always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [1](#0-0) 

No round-number range check, no BLS signature check, no committee-membership check. Every certificate from every peer passes.

**Step 2 – The production inbound path uses this stub.**

`makePerasCertPoolWriterFromChainDB` wires the stub directly into the ObjectDiffusion pool writer that processes peer-supplied certificates:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this validator and, on success, timestamps and stores the certificate: [3](#0-2) 

**Step 3 – `implAddCert` monotonically advances `pcdsLatestCertSeen`.**

```haskell
pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
  Nothing -> Just cert
  Just prev
    | getPerasCertRound cert > getPerasCertRound prev -> Just cert
    | otherwise -> Just prev
``` [4](#0-3) 

A certificate with round `currRoundNo + N` (N > 0) replaces the current `pcdsLatestCertSeen`. The field can only move forward; it can never be corrected downward.

The API documentation explicitly flags this field as a voting precondition:

> "This field impacts voting directly because having seen a certificate is a precondition for voting in any round except for the very first one (at origin)." [5](#0-4) 

**Step 4 – Both voting-rule paths fail.**

`latestCertSeen` (sourced from `pcdsLatestCertSeen`) is consumed by VR-1A and VR-2A:

*VR-1A* requires the latest cert seen to be from the **previous** round:
```haskell
currRoundNo :==: getPerasCertRound (lcsCert cert) + 1
``` [6](#0-5) 

If `pcdsLatestCertSeen` holds a cert from round `currRoundNo + N`, this equality fails for all rounds until `currRoundNo + N + 1`.

*VR-2A* requires the latest cert seen to be at least **R rounds old**:
```haskell
getPerasCertRound (lcsCert cert) + _R :<=: currRoundNo
``` [7](#0-6) 

A future-round cert makes this false for the next `N + R` rounds.

Since voting is allowed only when `VR-1 ∨ VR-2` holds: [8](#0-7) 

…both paths fail simultaneously, and the node emits no votes.

**Step 5 – Secondary impact: unauthorized chain-selection weight boost.**

`chainSelSync` for `ChainSelAddPerasCert` adds the certificate to `PerasCertDB` and then triggers chain selection for the boosted block:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [9](#0-8) 

Because the certificate is accepted without signature or committee-membership validation, an adversary can boost any valid block on any fork without holding the required stake, biasing chain selection toward an adversarial fork.

### Impact Explanation

**Primary (voting suppression / Peras protocol bypass):** An unprivileged peer can permanently silence a node's Peras votes by injecting a single certificate with a sufficiently large future round number. The adversary can repeat the injection with an ever-higher round number to extend the suppression indefinitely. If enough nodes are targeted, quorum is never reached, the Peras boosting mechanism is neutralised, and the chain-quality and finality guarantees of the Peras protocol are lost.

**Secondary (chain-selection manipulation):** The same stub allows the adversary to inject a certificate boosting any valid block on any fork without possessing the required BLS key or committee seat. The boosted block receives a weight advantage in chain selection, potentially causing the honest node to prefer a non-canonical fork over the honest chain.

Both impacts match the allowed scope: bypass of Peras certificate/signature validation enabling unauthorized certificate acceptance, and a chain-selection bug letting an unprivileged peer make an honest node prefer a less-secure chain.

---

### Likelihood Explanation

The attack requires only a network connection and the ability to send a single ObjectDiffusion message containing a well-formed `PerasCert` with an arbitrary round number. No cryptographic keys, no stake, no special privileges. The stub is wired into the production `makePerasCertPoolWriterFromChainDB` path with an explicit TODO acknowledging the missing validation. The attack is trivially repeatable.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before the ObjectDiffusion path is active in production. At minimum, validate:
   - The certificate's round number is not in the future (i.e., `pcCertRound ≤ currentRound`).
   - The BLS aggregate signature over `(roundNo, boostedBlock)` is valid against the declared committee.
   - The declared voters are eligible committee members for that round.

2. **Harvest `pcdsLatestCertSeen` before updating it**, analogous to the mitigation suggested in the external report: if the new certificate's round is ahead of the current round, reject it rather than storing it.

3. **Add a round-number range guard in `implAddCert`** as a defence-in-depth measure, independent of the validation layer.

### Proof of Concept

```
Attacker (unprivileged peer)                    Victim node
─────────────────────────────────────────────────────────────
1. Connect via ObjectDiffusion mini-protocol

2. Send PerasCert { pcCertRound = currRound + 10000,
                    pcCertBoostedBlock = <any valid block> }

3. processCerts calls validatePerasCert
   → stub returns Right unconditionally              ← no rejection

4. implAddCert: getPerasCertRound cert (10000+)
              > getPerasCertRound prev
   → pcdsLatestCertSeen := future-round cert         ← state corrupted

5. Node evaluates VR-1A:
   currRound == (currRound+10000) + 1  → False
   Node evaluates VR-2A:
   (currRound+10000) + R <= currRound  → False
   → isPerasVotingAllowed = NoVote                   ← voting suppressed

6. Repeat step 2 with pcCertRound = currRound + 20000
   → suppression window extended indefinitely
```

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
