### Title
Peras Quorum Bypass via Missing Vote-Stake Normalization in `stakeAboveThreshold` - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares the accumulated `PerasVoteStake` (a raw `Rational` sourced directly from the ledger's `PerasVoteStakeDistr`) against `perasQuorumStakeThreshold` (a relative `Rational` = 3/4) with no normalization step enforced anywhere in the call chain. The code itself documents this assumption as unresolved. If the distribution is populated with absolute lovelace values — the natural representation from the ledger — any single vote from any committee member trivially satisfies `absolute_lovelace >= 0.75`, collapsing the quorum requirement to a single-voter threshold and enabling unauthorized certificate forging.

### Finding Description

`stakeAboveThreshold` is the sole gate that decides whether accumulated vote stake is sufficient to forge a Peras certificate:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake          = unPerasVoteStake voteStake          -- raw Rational
  quorumThreshold = unPerasQuorumStakeThreshold
                      (perasQuorumStakeThreshold params) -- 3/4
  safetyMargin   = ...                                  -- 2/100
``` [1](#0-0) 

The comment immediately above the type definition of `PerasVoteStake` explicitly acknowledges the unresolved unit problem:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee … this function only makes sense when both values are relative (normalized) values, so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The stake assigned to each validated vote comes from `validatePerasVote`, which performs a plain map lookup with no normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

Note that `_params` (which carries the quorum threshold) is **ignored** during vote validation; the threshold is only consulted later in `stakeAboveThreshold`. No normalization occurs between the two sites.

The accumulated stake is then checked in `updateCandidateVoteState` via `votesReachQuorum`:

```haskell
totalVoteStake    = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

And in `updateLoserVoteState` the same unnormalized running total is used:

```haskell
aboveQuorum = stakeAboveThreshold cfg (ptvtTotalStake newVoteTally)
``` [5](#0-4) 

The `PerasVoteStakeDistr` is injected at the network ingress point:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [6](#0-5) 

If `getStakeDistrSTM` returns a distribution whose values are absolute lovelace (e.g., a voter holding 1 ADA = 1,000,000 lovelace), then `totalVoteStake` after a single vote is `1,000,000`, and `1,000,000 >= 0.75 + 0.02` is trivially true. Quorum is reached with one vote.

### Impact Explanation

An unprivileged peer that is a legitimate committee member (or that can impersonate one) can send a single `PerasVote` message. If the node's `PerasVoteStakeDistr` is populated with absolute lovelace values — the natural representation from the Cardano ledger — the quorum check collapses: `stakeAboveThreshold` returns `True` for any positive stake, and `forgePerasCert` is called immediately. The attacker can therefore forge a Peras certificate for any block of their choosing with a single message, bypassing the intended ≥ 3/4 quorum requirement entirely. This constitutes a **bypass of Peras voting and certificate checks** enabling unauthorized certificate acceptance, which in turn corrupts chain-selection via the boosting weight (`perasWeight = 15` blocks).

### Likelihood Explanation

The Peras vote ingestion pipeline is reachable from any peer via the ObjectDiffusion mini-protocol. The `PerasVoteStakeDistr` is sourced from the ledger's stake distribution, which natively stores absolute lovelace. No normalization step is present anywhere between the ledger query and `stakeAboveThreshold`. The code comment confirms the normalization is not yet implemented. Any committee member (a set of stake pools, not a privileged role) can trigger this with a single well-formed vote message.

### Recommendation

1. **Enforce normalization at the boundary**: when populating `PerasVoteStakeDistr` from the ledger, divide each pool's absolute stake by the total committee stake so every entry is a value in `[0, 1]`.
2. **Alternatively**, change `stakeAboveThreshold` to accept the total committee stake and perform the division internally, removing the implicit unit assumption.
3. **Type-level enforcement**: introduce distinct newtypes for absolute and relative stake (e.g., `AbsoluteStake` vs `RelativeStake`) so the compiler rejects mixing them at the call site of `stakeAboveThreshold`.

### Proof of Concept

Scenario: `PerasVoteStakeDistr` contains `{ poolA -> PerasVoteStake (1_000_000 % 1) }` (1 ADA in lovelace). `mkPerasParams` sets `perasQuorumStakeThreshold = 3/4` and `perasQuorumStakeThresholdSafetyMargin = 2/100`.

1. Peer sends one `PerasVote { pvVoteRound = r, pvVoteBlock = b, pvVoteVoterId = poolA }`.
2. `validatePerasVote` looks up `poolA` → `vpvVoteStake = 1_000_000`.
3. `updateTargetVoteTally` sets `ptvtTotalStake = 1_000_000`.
4. `votesReachQuorum`: `totalVoteStake = 1_000_000`; `stakeAboveThreshold`: `1_000_000 >= 3/4 + 2/100` → `True`.
5. `forgePerasCert` is called; a `ValidatedPerasCert` boosting block `b` is produced and stored.
6. Chain selection applies the `perasWeight = 15` boost to block `b`, making it preferred over honest competing chains. [7](#0-6) [8](#0-7)
