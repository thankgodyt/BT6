### Title
`internal_reject_refund` does not remove `verified_deposit_utxo` entry set by `execute_refund`, permanently blocking `verify_deposit` for that UTXO — (`contracts/satoshi-bridge/src/refund.rs`)

### Summary
When `execute_refund` is called (public, after timelock), `finalize_refund_with_psbt` inserts the UTXO storage key into `verified_deposit_utxo` and keeps the refund request with `executed = true`. If the DAO subsequently calls `reject_refund`, `internal_reject_refund` removes the entry from `refund_requests` but **never** removes it from `verified_deposit_utxo`. Because `verify_deposit_callback` requires `verified_deposit_utxo.insert(key)` to return `true` (i.e., the key must be absent), the deposit path for that UTXO is permanently blocked.

### Finding Description
`internal_reject_refund` performs exactly one state mutation:

```rust
// refund.rs:187-196
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [4](#0-3) 

It does not touch `verified_deposit_utxo`. After `execute_refund` has already inserted the key there, the entry persists indefinitely. Any subsequent call to `verify_deposit_callback` for the same UTXO hits:

```rust
// deposit.rs:369-374
require!(
    self.data_mut()
        .verified_deposit_utxo
        .insert(pending_utxo_info.utxo_storage_key.clone()),
    "Already deposit utxo"
);
``` [5](#0-4) 

and panics, making the deposit permanently unreachable.

The `load_refund_request_for_execute` guard that allows re-execution when `executed == true` relies on the refund request still being present; after `reject_refund` removes it, `execute_refund` also becomes impossible ("Refund request not found"), so there is no self-healing path. [8](#0-7) 

### Impact Explanation
The BTC UTXO is stuck: it cannot be minted as nBTC (deposit blocked) and the refund was rejected by the DAO. The only recovery is a privileged contract upgrade or a new admin function to manually remove the key from `verified_deposit_utxo`. This matches **Medium — stuck bridge state requiring operator intervention / temporary locking of bridged funds**.

### Likelihood Explanation
The trigger requires two steps: (1) any unprivileged user calls `execute_refund` after the timelock (fully public, no role check), and (2) the DAO calls `reject_refund` on the now-executed request (a legitimate, documented DAO power). The DAO has a clear reason to reject a suspicious refund request even after execution (e.g., the refund address was not pre-authorized). Both steps are individually normal operations; their combination is the bug.

### Recommendation
In `internal_reject_refund`, when the request being removed has `executed == true`, also remove the key from `verified_deposit_utxo`:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    let vreq = self.data_mut()
        .refund_requests
        .remove(&utxo_storage_key)
        .expect("Refund request not found");
    let req = RefundRequest::from(vreq);
    // If execute_refund already ran, it inserted the key into verified_deposit_utxo
    // to block a racing deposit. Rejection undoes that so deposits can proceed.
    if req.executed {
        self.data_mut().verified_deposit_utxo.remove(&utxo_storage_key);
    }
    Event::RefundRejected { utxo_storage_key }.emit();
}
```

### Proof of Concept
State assertions (pseudo-test):
1. Call `request_refund` → `refund_requests` contains key, `verified_deposit_utxo` does not.
2. Advance time past timelock; call `execute_refund` → `verified_deposit_utxo` now contains key, `refund_requests[key].executed == true`.
3. DAO calls `reject_refund` → `refund_requests` no longer contains key.
4. Assert `verified_deposit_utxo.contains(key)` → **true** (orphaned entry).
5. Call `verify_deposit` for the same UTXO → panics with "Already deposit utxo".

The existing test `test_reject_refund_blocked_after_execute` stops at step 3 and does not assert step 4/5, confirming the gap. [9](#0-8)
