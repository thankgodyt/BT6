Audit Report

## Title
Permanent Freezing of Bridged Funds When Recipient Is Blacklisted on Destination Chain — (`evm/src/omni-bridge/contracts/OmniBridge.sol`, `starknet/src/omni_bridge.cairo`)

## Summary
`finTransfer` on both EVM and Starknet delivers tokens exclusively to `payload.recipient`, which is Borsh-encoded and MPC-signed and therefore immutable. If that address is blacklisted by a token such as USDC or USDT, every delivery attempt reverts. Because the MPC will not re-sign the same transfer with a different recipient, and because NEAR exposes no public cancel/refund path for a pending transfer whose source-chain tokens have already been burned or locked, the bridged funds are permanently frozen.

## Finding Description

**EVM — `OmniBridge.finTransfer` (lines 283–355)**

The nonce guard and nonce-consumption write occur before the transfer:

```solidity
completedTransfers[payload.destinationNonce] = true;   // L287
```

Because the entire transaction reverts on transfer failure, the nonce is not permanently consumed and the relayer can retry. However, `payload.recipient` is Borsh-encoded into the signed blob at line 298:

```solidity
Borsh.encodeAddress(payload.recipient),   // L298
```

The MPC signature covers this exact encoding. The NEAR `sign_transfer` function reads the recipient verbatim from the stored `TransferMessage` and embeds it into `TransferMessagePayload` (lines 491–497 of `near/omni-bridge/src/lib.rs`). The MPC will not re-sign with a different recipient.

For native ERC-20 tokens (the `else` branch, lines 350–355):

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
```

OpenZeppelin's `safeTransfer` reverts on any non-`true` return value, including the revert that USDC/USDT emit for blacklisted addresses. Every retry reverts identically.

**Starknet — `omni_bridge.fin_transfer` (lines 242–263)**

The same pattern: `_set_transfer_finalised` is called at line 250 before the transfer, but Cairo rolls back all state on revert, so the nonce is not permanently consumed. The transfer:

```cairo
let success = IERC20Dispatcher { contract_address: payload.token_address }
    .transfer(payload.recipient, payload.amount.into());
assert(success, 'ERR_TRANSFER_FAILED');
```

reverts for blacklisted recipients, and the recipient is equally fixed in the signed payload.

**No cancel/refund path on NEAR**

`init_transfer_internal` (lines 1829–1865) burns or locks source-chain tokens and stores a `pending_transfers` entry. `remove_transfer_message` (lines 2194–2211) is only called internally after a successful fee claim. `remove_transfer_message_without_refund` (lines 2213–2224) is only called in internal error paths. No public function allows the original sender to cancel the pending transfer and recover their tokens.

## Impact Explanation

This concretely satisfies the allowed impact: **permanent freezing of bridged funds across NEAR and EVM/Starknet flows**. Source-chain tokens are burned/locked, every finalization attempt reverts because the blacklisted recipient cannot receive the token, the signed payload is immutable so no alternative recipient can be substituted, and no on-chain recovery path exists. The funds are irrecoverably frozen.

## Likelihood Explanation

USDC and USDT both implement address blacklists and have historically blacklisted addresses in response to regulatory or security events. A user can be blacklisted between the time they initiate a bridge transfer and the time the relayer finalizes it. No privileged access is required; the scenario is reachable by any bridge user holding a blacklistable token. The blacklisting event itself is performed by Circle or Tether, not the attacker, but the resulting fund loss is a direct consequence of the bridge's missing fallback and recovery mechanisms.

## Recommendation

1. **Try-catch / escrow-and-claim on EVM**: Wrap the `safeTransfer` in a try/catch (or use a low-level call with a return-value check). On failure, hold the tokens in the bridge contract and emit an event. Allow the original recipient (or a governance-approved alternative) to claim from a different address.
2. **Source-chain cancel path on NEAR**: Add a DAO- or user-callable public function that, given proof that finalization has permanently failed (e.g., a signed attestation or an on-chain timeout), removes the `pending_transfers` entry and re-mints/unlocks the tokens to the original sender or a sender-specified recovery address.
3. **Starknet**: Apply the same escrow-and-claim pattern around the `transfer` + `assert` block.

## Proof of Concept

1. Alice holds 10,000 USDC on NEAR (bridged token). She calls `ft_transfer_call` → `init_transfer`, specifying her EVM address `0xAlice` as recipient. Tokens are burned on NEAR; a `pending_transfers` entry is created (`init_transfer_internal`, lines 1829–1865).
2. A relayer calls `sign_transfer`; the MPC signs a `TransferMessagePayload` with `recipient = 0xAlice` embedded verbatim (lines 491–497 of `near/omni-bridge/src/lib.rs`).
3. Before the relayer submits `finTransfer` on EVM, Circle blacklists `0xAlice`.
4. The relayer calls `OmniBridge.finTransfer(signatureData, payload)`. The signature check passes. `completedTransfers[nonce] = true` is set (line 287). Then `IERC20(usdc).safeTransfer(0xAlice, amount)` (lines 351–354) reverts. The entire transaction reverts; the nonce is not consumed.
5. Every subsequent retry reverts identically. The MPC payload is immutable. No cancel function exists on NEAR.
6. Alice's 10,000 USDC are permanently frozen.
