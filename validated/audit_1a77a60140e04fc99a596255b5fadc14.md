### Title
Permissionless `request_refund` Front-Running Enables BTC Theft for Deposits Without Pre-Authorized Refund Address — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user deposits BTC using a `DepositMsg` with `refund_address: None`, any unprivileged NEAR account can call `request_refund` for that UTXO and supply an arbitrary attacker-controlled BTC address. Because only one refund request can exist per UTXO, the first caller wins. An attacker who front-runs the legitimate user's `request_refund` call locks the user out and, if the DAO fails to reject the request within `unsafe_refund_timelock_sec`, can execute the refund and redirect the BTC to their own address. This is a direct analog to TRST-H-2: a permissionless two-step process (request → execute) where a critical parameter (the refund destination) can be set by an attacker in step 1, forcing the victim into an unfavorable outcome in step 2.

---

### Finding Description

**Root cause — `request_refund` accepts any `refund_address` when `deposit_msg.refund_address` is `None`:** [1](#0-0) 

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None`, the `require!` block is skipped entirely. Any caller may pass any BTC address as `refund_address`. The function is `#[payable]` and open to all NEAR accounts. [2](#0-1) 

**First-caller-wins race — duplicate requests are rejected:** [3](#0-2) 

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

Once the attacker's request is stored, the legitimate user's subsequent `request_refund` call panics here. The user is completely locked out.

**Stored `refund_address` is used verbatim to build the Bitcoin output:** [4](#0-3) 

The `refund_address` stored in the `RefundRequest` at request time is the sole destination of the refund transaction. It cannot be changed after storage.

**`execute_refund` is permissionless after `unsafe_refund_timelock_sec`:** [5](#0-4) 

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
```

After this timelock elapses, any account — including the attacker — can call `execute_refund`. The BTC is sent to the attacker's stored `refund_address`. [6](#0-5) 

**Only DAO/Operator can reject — the user has no self-help remedy:** [7](#0-6) 

The user cannot reject the attacker's refund request themselves. They are entirely dependent on the DAO/Operator acting within `unsafe_refund_timelock_sec`.

**All inputs needed for the attack are public on-chain:**

The `deposit_msg`, `tx_bytes`, `vout`, and Merkle proof are all derivable from the public Bitcoin blockchain. The attacker pays only the 2 NEAR anti-spam deposit. [8](#0-7) 

---

### Impact Explanation

If the DAO/Operator does not reject the attacker's refund request before `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, the bridge constructs and MPC-signs a Bitcoin transaction paying the attacker's address, and the user's deposited BTC is permanently transferred to the attacker. The user's own `request_refund` call is permanently blocked by the duplicate-request guard. This constitutes **significant theft of user funds** — a Critical impact under the allowed scope.

---

### Likelihood Explanation

- The attack requires no privileged access: any NEAR account with 2 NEAR can execute it.
- All required inputs (`deposit_msg`, `tx_bytes`, proof) are publicly available on the Bitcoin blockchain.
- The only mitigation is DAO/Operator rejection within `unsafe_refund_timelock_sec`. If the DAO is slow, offline, or not monitoring refund requests, the window is fully exploitable.
- Deposits with `refund_address: None` in the `DepositMsg` are a normal, documented use case (users who do not pre-specify a refund address).
- The attacker can repeat the front-run each time the DAO rejects, paying 2 NEAR per attempt, until the DAO fails to respond in time.

Likelihood: **Medium** — realistic for any period of DAO inattention or governance delay.

---

### Recommendation

1. **Require `deposit_msg.refund_address` to be non-`None` in `request_refund`**, or alternatively bind the refund request to `env::predecessor_account_id()` so only the original requester can benefit.
2. If open-address refunds must be supported, **require the caller to prove ownership** of the `refund_address` (e.g., via a signed challenge), or restrict `execute_refund` so only the account that submitted `request_refund` can execute it when `deposit_msg.refund_address` is `None`.
3. Emit a prominent on-chain event immediately on `request_refund` storage so monitoring infrastructure can detect and reject suspicious requests quickly.

---

### Proof of Concept

1. Alice deposits 1 BTC to a bridge address derived from `DepositMsg { recipient_id: alice, refund_address: None, ... }`.
2. The relayer never calls `verify_deposit` (e.g., relayer is down).
3. Alice submits `request_refund(deposit_msg, alice_btc_addr, tx_bytes, vout, proof, None)`.
4. Attacker observes Alice's pending NEAR transaction in the mempool and submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof, None)` with higher gas, landing first.
5. Alice's transaction executes and panics: `"Refund request already exists for this UTXO"`.
6. The DAO does not reject the attacker's request within `unsafe_refund_timelock_sec`.
7. Attacker calls `execute_refund(utxo_storage_key, None)`. The bridge builds a Bitcoin transaction paying `attacker_btc_addr` and requests an MPC signature.
8. The signed transaction is broadcast; Alice's 1 BTC (minus gas fee) is delivered to the attacker.

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```

```rust
    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
```
