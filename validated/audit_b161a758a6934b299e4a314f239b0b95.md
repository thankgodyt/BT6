### Title
Fee-Exceeds-Deposit Arithmetic Underflow Permanently Locks User BTC — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
`internal_verify_deposit` subtracts `deposit_fee` from `deposit_amount` without first verifying that `deposit_fee < deposit_amount`. Because `get_fee` returns `fee_min` when `fee_min > amount * fee_rate / MAX_RATIO`, and because `assert_valid()` never enforces `min_deposit_amount >= deposit_bridge_fee.fee_min`, any deposit whose satoshi value falls in the range `[min_deposit_amount, fee_min)` causes an arithmetic underflow panic. The transaction reverts before the UTXO is registered, permanently locking the user's BTC in the deposit address with no on-chain recovery path.

### Finding Description

`BridgeFee::get_fee` returns the larger of the proportional fee and `fee_min`:

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
``` [1](#0-0) 

When `fee_min > amount`, `get_fee` returns `fee_min`, which is strictly greater than `amount`. In `internal_verify_deposit`, the code then executes:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;   // underflow → panic
``` [2](#0-1) 

This subtraction is reached only after the `min_deposit_amount` guard passes:

```rust
if deposit_amount < config.min_deposit_amount {
    // route to unavailable UTXO callback
} else {
    let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
    let mint_amount = deposit_amount - deposit_fee;   // ← panic zone
``` [3](#0-2)

### Impact Explanation

When the panic fires, the entire NEAR transaction reverts. The UTXO is never written to `verified_deposit_utxo` or `utxos`, so the bridge has no record of the deposit. The user's BTC is permanently locked in the MPC-controlled deposit address: the bridge cannot mint nBTC for it, and the refund system only operates on registered UTXOs. Recovery requires out-of-band DAO intervention (constructing a sweep transaction via chain signatures and re-registering via `verify_migrate_deposit`), which is complex and not guaranteed.

Impact: **Medium** — stuck bridge state with permanent loss of user BTC without direct theft, requiring operator intervention.

### Likelihood Explanation

The trigger condition is `deposit_bridge_fee.fee_min > min_deposit_amount`. The DAO can set these two fields independently via `update_config` without any on-chain guard preventing the unsafe combination. Once set, every user who deposits a satoshi amount in `[min_deposit_amount, fee_min)` is affected. The misconfiguration is easy to introduce inadvertently (e.g., raising `fee_min` to cover on-chain costs without simultaneously raising `min_deposit_amount`).

### Recommendation

Add an explicit invariant to `Config::assert_valid()`:

```rust
require!(
    self.min_deposit_amount >= self.deposit_bridge_fee.fee_min,
    "min_deposit_amount must be >= deposit_bridge_fee.fee_min"
);
```

Additionally, add a defensive check inside `internal_verify_deposit` before the subtraction:

```rust
require!(deposit_amount > deposit_fee, "Deposit amount does not cover the bridge fee");
let mint_amount = deposit_amount - deposit_fee;
```

### Proof of Concept

1. DAO calls `update_config` with `deposit_bridge_fee.fee_min = 50_000` and `min_deposit_amount = 20_000`. `assert_valid()` passes because neither field individually violates any existing check.
2. User sends 30_000 satoshis to their deposit address on Bitcoin.
3. Relayer calls `verify_deposit` (or `verify_deposit_v2`) with the transaction proof.
4. `internal_verify_deposit` is reached; `deposit_amount (30_000) >= min_deposit_amount (20_000)` passes the guard.
5. `get_fee(30_000)` returns `max(0, 50_000) = 50_000`.
6. `30_000u128 - 50_000u128` underflows → NEAR runtime panics, transaction reverts.
7. No UTXO is registered. The user's 30_000 satoshis are permanently locked in the deposit address with no on-chain recovery path.
