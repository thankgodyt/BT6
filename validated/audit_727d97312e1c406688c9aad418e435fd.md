### Title
`assert`-only underflow guards in `HardFork.History.Util` are silently disabled in production builds while `addSlots`/`addEpochs` carry no guards at all, creating inconsistent overflow protection in the `mkUpperBound` `Summary`-construction call path — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HardFork/History/Util.hs`)

---

### Summary

`Util.hs` guards its subtraction helpers (`subSlots`, `countSlots`, `countEpochs`, `countPerasRounds`) with `Control.Exception.assert`. GHC silently drops every `assert` when compiling with `-O` (via the implied `-fignore-asserts` flag), which is the standard production build mode. The addition helpers (`addSlots`, `addEpochs`) carry **no guard at all**, not even an `assert`. In `Summary.hs`, `mkUpperBound` calls `countEpochs` (assert-guarded, no-op in production) and immediately feeds the result into `addSlots` (unguarded). If the precondition `hiEpoch >= boundEpoch lo` is ever violated in a production binary, `countEpochs` silently wraps to a huge `Word64`, which is then multiplied and passed to `addSlots`, overflowing the `boundSlot` field of the returned `Bound`. The corrupted `Bound` is stored in the `Summary` that every time/slot/epoch translation in the consensus layer depends on.

---

### Finding Description

**Root cause — `Util.hs`**

```haskell
subSlots :: Word64 -> SlotNo -> SlotNo
subSlots n (SlotNo x) = assert (x >= n) $ SlotNo (x - n)   -- assert is a no-op with -O

countSlots :: HasCallStack => SlotNo -> SlotNo -> Word64
countSlots (SlotNo to) (SlotNo fr) = assert (to >= fr) $ to - fr  -- same

addSlots :: Word64 -> SlotNo -> SlotNo
addSlots n (SlotNo x) = SlotNo (x + n)   -- no guard whatsoever
``` [1](#0-0) 

In a production binary (`-O`), GHC replaces every `assert p e` with `e`, so `subSlots` and `countSlots` become bare `Word64` subtractions with no runtime check. `addSlots` and `addEpochs` never had any check. The project's own `Internal.hs` uses a separate `#if ENABLE_ASSERTIONS` CPP guard for its bounds checks, making the inconsistency explicit: one subsystem uses a compile-time-controlled mechanism, the other uses `assert` that vanishes in optimized builds. [2](#0-1) 

**Vulnerable call path — `Summary.hs` `mkUpperBound`**

```haskell
mkUpperBound EraParams{..} lo hiEpoch =
  Bound
    { boundSlot = addSlots inEraSlots $ boundSlot lo   -- (3) unguarded add
    , ...
    }
 where
  inEraEpochs = countEpochs hiEpoch (boundEpoch lo)   -- (1) assert disabled in prod
  inEraSlots  = inEraEpochs * unEpochSize eraEpochSize -- (2) multiplies huge Word64
``` [3](#0-2) 

Step-by-step in a production binary when `hiEpoch < boundEpoch lo`:

1. `countEpochs hiEpoch (boundEpoch lo)` — `assert` is a no-op; `Word64` subtraction wraps to `(2^64 - delta)`.
2. `inEraEpochs * unEpochSize eraEpochSize` — multiplies the huge value, overflows `Word64`.
3. `addSlots inEraSlots (boundSlot lo)` — adds the overflowed value to the era's start slot, producing a nonsensical `boundSlot` in the returned `Bound`.

The same pattern appears in `slotToEpochBound`, which calls `countSlots hiSlot (boundSlot lo)` (assert-guarded, disabled in production) and then passes the result to `addEpochs` (unguarded): [4](#0-3) 

By contrast, `Qry.hs` correctly uses a proper `guard` (not `assert`) before calling `countSlots`, so that path is safe: [5](#0-4) 

The inconsistency is exact: `Qry.hs` uses a real runtime `guard`; `Summary.hs` relies on `assert` that is silently stripped in production.

---

### Impact Explanation

The `Summary` produced by `mkUpperBound` / `summarize` is the single source of truth for every slot↔epoch↔wallclock translation in the consensus layer. A corrupted `boundSlot` in any era's `Bound` causes:

- Wrong era-boundary detection → a node may believe it is in a different era than its peers.
- Wrong slot-to-epoch translations → epoch-boundary logic (stake-distribution snapshots, leadership schedule) uses incorrect epoch numbers.
- Cross-era consensus divergence: honest nodes that received the same chain but built their `Summary` under different arithmetic outcomes will disagree on which era a given slot belongs to, breaking the hard-fork combinator's invariants.

This maps to the **High** allowed impact: *"Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes."*

---

### Likelihood Explanation

Triggering the bug requires `hiEpoch < boundEpoch lo` to reach `mkUpperBound`. In normal operation the ledger rules enforce monotone era-transition epochs, so this precondition is maintained. The likelihood is therefore **low** — matching the external report's own assessment that "the likelihood of this should be quite small." However, the inconsistency is a latent defect: any future ledger rule bug, snapshot-replay edge case, or era-parameter misconfiguration that produces a non-monotone transition epoch would silently corrupt the `Summary` in production while the same input would throw an `AssertionFailed` in a debug build, making the bug invisible in CI.

---

### Recommendation

1. **Replace `assert` in `Util.hs` with explicit runtime checks** that are active in production — either throw a descriptive exception or return `Maybe`/`Either`, consistent with how `Internal.hs` uses `#if ENABLE_ASSERTIONS` for its own bounds checks.
2. **Add overflow guards to `addSlots` and `addEpochs`** (e.g., check `x + n >= x` before returning) so that the addition side of the same call path is equally protected.
3. **Add a precondition check in `mkUpperBound`** that `hiEpoch >= boundEpoch lo` using a real runtime assertion (not `assert`), mirroring the `guard` already present in `Qry.hs`.

### Proof of Concept

```
-- Production binary (compiled with -O, so assert is a no-op):

let lo      = initBound                          -- boundEpoch = EpochNo 5
    hiEpoch = EpochNo 3                          -- hiEpoch < boundEpoch lo
    params  = EraParams { eraEpochSize = EpochSize 432000, ... }

-- countEpochs (EpochNo 3) (EpochNo 5)
--   = assert (3 >= 5) $ 3 - 5   -- assert is no-op in production
--   = 3 - 5                      -- Word64 underflow
--   = 18446744073709551614        -- 2^64 - 2

-- inEraSlots = 18446744073709551614 * 432000
--            = overflows Word64 → some small garbage value

-- addSlots garbage (boundSlot lo)
--   = SlotNo (garbage + lo.boundSlot)   -- wrong era upper-bound slot

-- The Summary now contains a Bound with a nonsensical boundSlot.
-- Every subsequent slotToEpoch / wallclockToSlot query returns wrong results.
-- Nodes that computed the Summary correctly diverge from this node on era membership.
```
