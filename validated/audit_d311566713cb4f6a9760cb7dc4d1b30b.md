### Title
Peras Vote Signature Digest Missing Chain-Specific Identifier Enables Cross-Fork Vote Replay - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Crypto/BLS.hs`)

### Summary
The `hashVoteSignature` function in `PerasBLSCrypto` constructs the message digest for Peras vote BLS signatures using only the round number, boosted block slot, and boosted block hash. No chain-specific identifier (genesis hash, network magic, or chain ID) is included in the digest. The `KeyScope` mechanism provides network-level domain separation but not fork-level separation. An unprivileged peer can collect valid Peras votes broadcast on one fork of the network and replay them on a competing fork, causing honest nodes to accept a Peras certificate that was never intended for their chain.

### Finding Description

`hashVoteSignature` in `PerasBLSCrypto` computes the signed digest as:

```
roundNoBytes (8) || boostedBlockSlotBytes (8) || boostedBlockHashBytes (32)
``` [1](#0-0) 

No genesis hash, network magic, or any other chain-specific identifier is included. The only domain-separation mechanism is the `KeyScope` embedded in the BLS key struct: [2](#0-1) 

The `KeyScope` is used as the BLS augmentation string `"VOTE:" <> keyScope <> ":V0"`: [3](#0-2) 

This scope is stored as metadata in the key struct and is **not serialized as part of the key bytes**. `rawSerialisePublicKey` only serializes `unPublicKey`, discarding the scope: [4](#0-3) 

When a key is deserialized, the scope must be supplied externally via `rawDeserialisePublicKey scope bs`: [5](#0-4) 

Critically, in a natural chain fork, both forks share the same genesis configuration and thus the same `KeyScope` (e.g., `"PERAS/MAINNET"`). The `KeyScope` mechanism therefore provides **network-level** domain separation (mainnet vs. testnet) but **not fork-level** (chain A vs. chain B after a split). Since the `hashVoteSignature` digest also contains no chain-specific identifier, a vote signature produced on fork A is cryptographically indistinguishable from a vote signature on fork B when the same pre-fork block is referenced.

Vote verification in `implVerifyVote` calls `verifyVoteSignature` using the voter's public key from the committee stake distribution, with no chain-context check: [6](#0-5) 

The same pattern holds in `WFALS.implVerifyVote`: [7](#0-6) 

Votes received over the network are validated and stored via `processVotes`, which calls the `validateVote` callback but has no chain-identity check: [8](#0-7) 

### Impact Explanation

In a fork scenario (which occurs naturally in Cardano during chain selection), both forks share the same genesis and thus the same `KeyScope`. Pre-fork blocks have identical hashes on both forks. An adversary who observes Peras votes broadcast on fork A for a pre-fork block can replay those votes verbatim on fork B. Because the digest `(roundNo, boostedBlockSlot, boostedBlockHash)` is identical for the same pre-fork block on both forks, and the `KeyScope` is the same, the BLS signatures verify successfully on fork B. This allows the adversary to inject a quorum of votes on fork B for a block that was voted for on fork A, potentially forging a Peras certificate that boosts a pre-fork block on fork B. Since Peras certificates add weight to chain selection, this can cause honest nodes on fork B to prefer a chain that the legitimate Peras committee never intended to certify on that fork, constituting a chain-selection manipulation beyond the intended security assumptions.

### Likelihood Explanation

Chain forks are a normal occurrence in Cardano (they are resolved by chain selection). Peras votes are broadcast publicly over the network miniprotocol. Any peer connected to both sides of a fork can trivially collect votes from one side and replay them on the other. No key compromise, stake majority, or privileged access is required. The attack is passive collection followed by replay, executable by any unprivileged network participant.

### Recommendation

Include a chain-specific identifier in the `hashVoteSignature` digest. The genesis hash or a hash of the genesis configuration is the standard approach (analogous to how EIP-712 includes `chainId` in the domain separator). Concretely, extend `hashVoteSignature` to accept and commit to a genesis hash or network-specific nonce:

```haskell
hashVoteSignature ::
  GenesisHash ->          -- chain-specific identifier
  ElectionId PerasBLSCrypto ->
  VoteCandidate PerasBLSCrypto ->
  Hash HASH (SigDSIGN BLS12381MinSigDSIGN)
hashVoteSignature genesisHash roundNo boostedBlock = ...
  $ genesisHashBytes <> roundNoBytes <> boostedBlockSlotBytes <> boostedBlockHashBytes
```

This ensures that a vote signed on one fork cannot verify on a different fork, even if the `KeyScope` is identical.

### Proof of Concept

1. Start two nodes, A and B, on the same network that have diverged at slot S (fork point). Both use `KeyScope = "PERAS/MAINNET"`.
2. At Peras round R, a quorum of committee members on node A's fork broadcast votes for pre-fork block `B_pre` (slot < S, hash `H`). These votes are `(roundNo=R, boostedBlockSlot=slot(B_pre), boostedBlockHash=H, sig)`.
3. An adversary connected to both forks collects these votes from fork A.
4. The adversary submits the same votes to node B via the Peras vote diffusion miniprotocol.
5. Node B calls `processVotes` → `validatePerasVote` → `implVerifyVote` → `verifyVoteSignature` with `hashVoteSignature R B_pre`. Since `R`, `slot(B_pre)`, and `H` are identical on both forks, and the `KeyScope` is the same, `BLS.verifyWithRole` succeeds.
6. Node B accumulates a quorum and forges a Peras certificate for `B_pre` on fork B, boosting it in chain selection — a certificate the legitimate committee never produced for fork B. [9](#0-8) [10](#0-9)

hashVoteSignature ::
  ElectionId PerasBLSCrypto ->
  VoteCandidate PerasBLSCrypto ->
  Hash HASH (SigDSIGN BLS12381MinSigDSIGN)
hashVoteSignature roundNo boostedBlock =
  Hash.castHash
    . Hash.hashWith id
    . runByteBuilder (8 + 8 + 32)
    $ roundNoBytes
      <> boostedBlockSlotBytes
      <> boostedBlockHashBytes
 where
  roundNoBytes =
    BS.word64BE
      . unPerasRoundNo
      $ roundNo
  boostedBlockSlotBytes =
    BS.word64BE
      . unSlotNo
      . bytes32RealPointSlot
      . unPerasBoostedBlock
      $ boostedBlock
  boostedBlockHashBytes =
    BS.byteStringCopy
      . BS.fromShort
      . bytes32RealPointHash
      . unPerasBoostedBlock
      $ boostedBlock
```

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
