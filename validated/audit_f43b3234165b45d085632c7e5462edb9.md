Audit Report

## Title
Missing `token::authority` Constraint on `from` Allows Delegate to Bridge Victim's Tokens — (`solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary
The `from` token account in `InitTransfer` is constrained only by `token::mint` and `token::token_program`, with no `token::authority = user` check. Because SPL Token's `transfer_checked` and `burn` accept either the account owner or an approved delegate as the signing authority, any attacker holding a valid SPL delegation over a victim's token account can call `init_transfer` with `from = victim_ata` and `user = attacker`, successfully locking or burning the victim's tokens and receiving the equivalent amount on NEAR at an attacker-controlled address.

## Finding Description
The `from` account is declared at lines 34–39 without an authority constraint:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    // no token::authority = user
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

`user` is only required to be a `Signer` and a system-owned account (lines 60–64); there is no on-chain check that `from.owner == user.key()`.

In `process()`, the native-token path (lines 90–102) issues:
```rust
TransferChecked {
    from: self.from.to_account_info(),
    to: vault.to_account_info(),
    authority: self.user.to_account_info(),  // attacker signs
    mint: self.mint.to_account_info(),
}
```
And the bridged-token path (lines 110–120) issues:
```rust
Burn {
    mint: self.mint.to_account_info(),
    from: self.from.to_account_info(),
    authority: self.user.to_account_info(),  // attacker signs
}
```
SPL Token's `transfer_checked` and `burn` both accept a valid delegate as `authority`. If the victim has ever called `spl_token::approve` granting the attacker delegate rights over their ATA, both CPIs succeed with `from = victim_ata` and `authority = attacker`. The Wormhole message is then posted with `self.user.key()` (attacker) as sender and an attacker-supplied `recipient` NEAR address (lines 123–127), completing the cross-chain theft.

No guard anywhere in `InitTransfer::process` checks `from.owner == user.key()`.

## Impact Explanation
This is a direct, irreversible theft of bridged funds — matching the Critical scope item: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

- **Native path:** victim's SPL tokens are locked in the bridge vault; attacker receives equivalent tokens on NEAR.
- **Bridged path:** victim's bridged SPL tokens are burned; attacker receives equivalent tokens on NEAR.

In both cases the victim suffers a permanent, unrecoverable loss with no on-chain recourse.

## Likelihood Explanation
SPL token delegations are a routine, widely-used mechanism: DEX routers, lending protocols, and yield aggregators all request `approve` from users. A victim who has ever approved any program or wallet as a delegate — even for a completely unrelated purpose — is vulnerable if the attacker controls that delegate key. The attacker requires no privileged access to the bridge, no compromised keys beyond the delegation already granted, and no off-chain coordination. The attack is fully on-chain, permissionless, and repeatable.

## Recommendation
Add `token::authority = user` to the `from` account constraint:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    token::authority = user,   // enforce from.owner == user.key()
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

Anchor evaluates this constraint at account-validation time, before `process()` is entered, rejecting any transaction where `from.owner != user.key()` and closing the delegation-drain path entirely.
