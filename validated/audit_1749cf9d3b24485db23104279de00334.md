### Title
Peras Vote Validation Omits `perasBlockMinSlots` Age Check, Allowing Premature Block Boosting — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function in the `BlockSupportsPeras` instance does not verify that the voted block has reached the minimum required age (`perasBlockMinSlots`). An unprivileged peer can submit votes for blocks that are too young to be eligible for a Peras boost. If enough such votes accumulate, a certificate can be forged for an ineligible block, causing chain selection to assign unearned weight to that block.

---

### Finding Description

The Peras protocol defines `perasBlockMinSlots` (`L`) as the minimum number of slots a block must be old before it is eligible to be voted on for a boost. This age gate is correctly enforced on the *local* voting path: `perasChainAtCandidateBlock` splits the chain at `currRoundStart - L` to determine the candidate block before the node casts its own vote. [1](#0-0) 

However, the *inbound* validation path — `validatePerasVote`, which is called by `processVotes` for every vote received from a remote peer — performs no such check. The only check it performs is a stake-distribution lookup: [2](#0-1) 

The function ignores `_params` entirely (note the leading underscore), so `perasBlockMinSlots` is never consulted. The TODO comment at line 350 acknowledges that actual validation is absent: [3](#0-2) 

`processVotes` is production code that accepts a batch of inbound votes, calls `validateVote` (which resolves to `validatePerasVote`) for each, and adds all passing votes to the `PerasVoteDB`: [4](#0-3) 

Once votes are in the `PerasVoteDB`, `implAddVote` calls `updatePerasRoundVoteStates`, which can forge a certificate as soon as the quorum stake threshold is reached: [5](#0-4) 

The forged certificate is then used to assign a `perasWeight` boost to the targeted block in chain selection. The `perasBlockMinSlots` parameter is defined as: [6](#0-5) 

---

### Impact Explanation

**High — Chain selection bug.** A coordinated set of unprivileged peers holding sufficient combined stake can submit votes for a block that has not yet reached the `perasBlockMinSlots` age threshold. Because `validatePerasVote` never checks this condition, the votes pass validation, accumulate in the `PerasVoteDB`, and — once the quorum stake threshold is crossed — cause a certificate to be forged for an ineligible block. That certificate assigns a `perasWeight` boost to the block, causing the local node's chain selection to prefer a chain that should not be preferred under the Peras protocol rules. This is a direct chain-selection manipulation: the security assumption that only sufficiently old, stable blocks can receive a boost is violated without any operator fault. [7](#0-6) 

---

### Likelihood Explanation

**Medium.** The attacker needs a set of registered stake pool keys whose combined stake exceeds the quorum threshold (`perasQuorumStakeThreshold`, default ¾ of active stake). No special privileges, leaked keys, or operator compromise are required beyond holding that stake. The network-facing entry point (`processVotes`) is reachable by any peer that can open a connection and send a Peras vote batch. The attack is deterministic once the stake threshold is met.

---

### Recommendation

In `validatePerasVote`, verify that the slot of the voted block (`pvVoteBlock`) is at least `perasBlockMinSlots` slots before the start of the current round, mirroring the check already performed in `perasChainAtCandidateBlock`. Concretely, the validation should reject any vote whose targeted block slot satisfies:

```
blockSlot > currRoundStart - perasBlockMinSlots
```

This is the same horizon computed in `perasChainAtCandidateBlock` and should be enforced symmetrically on the inbound validation path. [8](#0-7) 

---

### Proof of Concept

1. Attacker controls stake pool keys whose combined stake exceeds `perasQuorumStakeThreshold` (¾ by default).
2. A block `B` is produced at slot `s`. The current round starts at slot `s + 1` (i.e., `B` is only 1 slot old, far below `perasBlockMinSlots = 90`).
3. Attacker sends a batch of `PerasVote` messages to the victim node, each with `pvVoteBlock = point(B)` and `pvVoteRound = currRound`.
4. `processVotes` calls `validatePerasVote` for each vote. The function only checks `lookupPerasVoteStake`; it never inspects `pvVoteBlock`'s slot age. All votes pass.
5. `implAddVote` → `updatePerasRoundVoteStates` detects that the quorum stake threshold is crossed and calls `forgePerasCert`, producing a `ValidatedPerasCert` boosting `B`.
6. The certificate is stored in `PerasCertDB` and its `perasWeight` boost is applied to `B` in chain selection via `getWeightSnapshot`.
7. The victim node's chain selection now prefers any chain containing `B` over a longer honest chain that lacks the boost — a chain selection outcome that violates the Peras protocol's age-gate invariant. [2](#0-1) [9](#0-8)

perasChainAtCandidateBlock ::
  GetHeader blk =>
  PerasBlockMinSlots ->
  PerasRoundNo ->
  AnchoredFragment (Header blk) ->
  PerasQry xs (AnchoredFragment (Header blk))
perasChainAtCandidateBlock blockMinSlots currRoundNo currChain = do
  -- Slot number at the start of the current round
  currRoundStart <- perasRoundStart currRoundNo
  -- Minimum number of slots to consider before the candidate block
  let _L = SlotNo (unPerasBlockMinSlots blockMinSlots)
  -- Determine the candidate slot horizon
  -- NOTE: here we need make sure that the result doesn't underflow
  let candidateSlotHorizon
        | currRoundStart >= _L = currRoundStart - _L
        | otherwise = SlotNo 0
  -- Split the chain at the candidate slot horizon
  pure $ fst $ AF.splitAtSlot candidateSlotHorizon currChain

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
