### Title
Peras Certificate Validation Bypass Enables Unprivileged Peer to Manipulate Chain Selection Weight - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — the only instance currently wired into the production certificate-ingestion path — implements `validatePerasCert` as an unconditional `Right`, performing zero cryptographic or semantic checks. Any peer can therefore inject an arbitrary crafted `PerasCert` that passes "validation", is stored in the `PerasCertDB`, and triggers chain selection. Because Peras weight is additive to block count in `wsvTotalWeight`, a single crafted certificate can cause a sudden, large jump in a candidate chain's weight, making an honest node switch away from the canonical chain.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate that must reject invalid certificates before they influence chain selection. The universal degenerate instance (the only one compiled for all block types) implements this gate as:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the function called by the production network-facing certificate writer:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
``` [2](#0-1) 

`processCerts` treats any `Right` result as a valid certificate and immediately forwards it to `ChainDB.addPerasCertAsync`: [3](#0-2) 

`addPerasCertAsync` enqueues a `ChainSelAddPerasCert` message. The background `chainSelSync` handler then:
1. Stores the certificate in `PerasCertDB`
2. Looks up the boosted block in the `VolatileDB`
3. Calls `chainSelectionForBlock` for that block [4](#0-3) 

Chain selection then computes `wsvTotalWeight` as `BlockNo + wsvWeightBoost` for each candidate fragment: [5](#0-4) 

A crafted certificate injects `perasWeight params` (a configurable `Word64`) of boost onto any block the attacker names, causing a sudden jump in that candidate chain's total weight. `preferAnchoredCandidate` then compares this inflated weight against the current chain and switches if the candidate is heavier: [6](#0-5) 

---

### Impact Explanation

This is a **High** chain-selection bug. An unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended security assumptions:

- The attacker sends a `PerasCert` naming any block already in the node's `VolatileDB` (e.g., a stale fork tip).
- The certificate bypasses all validation and is accepted.
- The candidate chain containing that block receives a large weight boost.
- If `BlockNo(candidate) + boost > BlockNo(current)`, the node rolls back to the adversarial fork.
- Because the rollback depth is bounded only by `k` (the security parameter), the attacker can force a rollback of up to `k` blocks, violating the Common Prefix property for that node.

The analog to the external report is exact: just as toggling `yieldConvEnabled` causes `_totalAssets` to jump sharply and be exploited, receiving a crafted certificate causes `wsvTotalWeight` to jump sharply for a candidate chain, triggering an unwarranted chain switch.

---

### Likelihood Explanation

- **Reachable**: The Peras certificate mini-protocol is a public network-facing endpoint; any connected peer can send `PerasCert` messages.
- **No privilege required**: No keys, stake, or committee membership are needed — the validation function unconditionally returns `Right`.
- **Precondition**: The attacker only needs the node to have a stale fork block in its `VolatileDB`, which is a normal condition during syncing or after any natural fork.
- **Peras is gated by `eraPerasRoundLength`**: If Peras is disabled (the current default), the weight snapshot is empty and `isEmptyPerasWeightSnapshot` causes the old length-only comparison to be used, neutralizing the attack. However, the code is explicitly being prepared for production enablement, and the TODO comments reference open issues for completing the plumbing. [7](#0-6) 

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's aggregate verification key (as already implemented in `implVerifyCert` in `Ouroboros.Consensus.Committee.EveryoneVotes`).
2. Checks that the voters form a valid quorum (sufficient stake).
3. Checks that the certificate's round number is within the valid window (not too old, not in the future).

Until real validation is wired in, the `makePerasCertPoolWriterFromChainDB` path must not be reachable from untrusted peers when Peras is enabled. [8](#0-7) 

---

### Proof of Concept

**Setup**: Node N has its current chain at tip `C` (block number `B`). A stale fork block `F` (block number `B - d`, where `d < k`) is in N's `VolatileDB`. Peras is enabled with `perasWeight = W`.

**Attack**:
1. Attacker connects to N via the Peras certificate mini-protocol.
2. Attacker sends `PerasCert { pcCertRound = r, pcCertBoostedBlock = point(F) }`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right ValidatedPerasCert { vpcCertBoost = W }`.
4. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
5. `chainSelSync` stores the cert, finds `F` in the VolatileDB, calls `chainSelectionForBlock`.
6. Chain selection computes: `wsvTotalWeight(fork) = (B - d) + W`. If `W > d`, this exceeds `wsvTotalWeight(current) = B + 0`.
7. Node rolls back `d` blocks and adopts the adversarial fork.

**Condition for success**: `W > d`, i.e., the configured Peras weight boost exceeds the depth of the stale fork. Since `W` is a protocol parameter (e.g., `PerasWeight 1000`) and `d` can be as small as 1, this condition is trivially satisfied. [9](#0-8) [10](#0-9)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
