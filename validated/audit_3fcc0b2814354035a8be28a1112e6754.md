### Title
`revalidateHeader` Envelope Check Silently Bypassed in Production Builds via `assertWithMsg` No-Op — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` guards its entire envelope check (block number, slot number, and prev-hash chain continuity) behind `assertWithMsg`, which is a **compile-time no-op in production builds** (i.e., when `ENABLE_ASSERTIONS` is not defined). This is the direct analog of the reported Solidity pattern: a critical validity check is present in the source but silently omitted at runtime, so the operation "succeeds" regardless of whether the check would have passed.

---

### Finding Description

`assertWithMsg` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [1](#0-0) 

Without `ENABLE_ASSERTIONS`, the first branch is compiled away entirely. The function unconditionally returns its second argument, ignoring the `Either String ()` check result.

`revalidateHeader` uses this macro-guarded assertion as the **sole enforcement point** for the header envelope check:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState
      (NotOrigin (getAnnTip hdr))
      chainDepState'
``` [2](#0-1) 

`envelopeCheck` runs `validateEnvelope`, which verifies:
- Block numbers are consecutive
- Slot numbers are strictly increasing
- The `prevHash` field chains to the current tip [3](#0-2) 

In a production binary (no `ENABLE_ASSERTIONS`), `assertWithMsg envelopeCheck result` always returns `result`. A header whose `prevHash` does not match the current tip, or whose block/slot numbers are wrong, is silently accepted and a new `HeaderState` is returned as if the check passed.

Additionally, `revalidateHeader` calls `reupdateChainDepState` instead of `updateChainDepState`, which explicitly skips VRF/KES signature verification: [4](#0-3) 

The contrast with `validateHeader` (the full-validation path) is stark: `validateHeader` calls `validateEnvelope` inside `Except` and propagates errors; `revalidateHeader` wraps the same call in a no-op assertion. [5](#0-4) 

`revalidateHeader` is called from production code in `Ouroboros.Consensus.Ledger.Extended` (2 call sites), which is exercised during chain selection fork-switching and ImmutableDB replay on node startup.

---

### Impact Explanation

If `revalidateHeader` is invoked with a header whose envelope invariants do not hold against the supplied `HeaderState` — wrong `prevHash`, non-consecutive block number, or non-increasing slot — the function silently returns a `HeaderState` that records the invalid header as the new tip. Downstream consumers of that `HeaderState` (chain selection, ledger-view forecasting, header-state history used by the ChainSync client) will operate on a corrupted consensus state. This can cause the node to accept a chain that violates hash-chain continuity or block-ordering invariants, constituting an invalid-header acceptance.

---

### Likelihood Explanation

`revalidateHeader` is documented as being called only for headers "previously validated w.r.t. the same exact `HeaderState`". Under normal operation this precondition holds, so the envelope check would pass anyway. The risk materialises when:

1. A bug in chain-selection fork-switching supplies a mismatched `HeaderState` (the header was validated against fork A's tip but is reapplied against fork B's tip).
2. A crafted sequence of blocks from an unprivileged peer triggers such a mismatch — the peer controls the content of headers stored in the VolatileDB and the order in which forks are presented, giving partial influence over which `HeaderState` is paired with which header during revalidation.

Because the assertion is the only guard and it is unconditionally disabled in production, any such mismatch is invisible to the node. Likelihood is **Low** for a direct exploit but elevated by the fact that the protection is entirely absent in production rather than merely weak.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with a proper `Either`/`Except` return type (matching `validateHeader`) so that envelope failures are propagated as errors in all build configurations. If the performance cost of the full envelope check is unacceptable on the hot path, at minimum the `prevHash` continuity check should be retained unconditionally, as it is the cheapest and most critical of the three checks.

---

### Proof of Concept

1. `ENABLE_ASSERTIONS` is absent in a standard production Cabal build (confirmed: the flag appears only in `ouroboros-consensus.cabal` and `ImmutableDB/Chunks/Internal.hs`; it is not set by default). [1](#0-0) 

2. In a production binary, `assertWithMsg (Left "prevHash mismatch") result` evaluates to `result` — the error is discarded.

3. `revalidateHeader` constructs and returns `HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'` unconditionally, recording `hdr` as the new tip regardless of whether its `prevHash` matches the prior tip stored in `st`. [6](#0-5) 

4. The contrast with `validateHeader` confirms the missing enforcement: `validateHeader` uses `withExcept HeaderEnvelopeError $ validateEnvelope ...` inside `Except`, making failure impossible to ignore. [7](#0-6)
