### Title
Missing Cryptographic Authority Check in Peras Vote Validation Allows Vote Forgery - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function in the `BlockSupportsPeras` instance accepts a Peras vote as valid solely by checking whether the claimed `pvVoteVoterId` (a pool key hash) exists in the stake distribution. No cryptographic signature is present in the `PerasVote blk` data type, and no authority check is performed. Any unprivileged peer can craft a vote claiming to be from any pool in the stake distribution, have it accepted as valid, and contribute its full stake weight toward quorum. This is the direct analog of the liquidation bug: a caller-supplied identity field is trusted without verifying the submitter actually controls the corresponding key.

---

### Finding Description

The `BlockSupportsPeras` instance defines the `PerasVote blk` data type without a signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- claimed pool key hash, unverified
  }
```

The `validatePerasVote` implementation performs only a stake-distribution lookup on the claimed voter identity:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`lookupPerasVoteStake` simply does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. There is no signature field to verify, and no check that the submitter controls the private key corresponding to `pvVoteVoterId`. The vote is stamped `ValidatedPerasVote` and assigned the pool's full stake weight purely on the basis of the claimed identity.

This validated vote then flows into `updatePerasRoundVoteStates`, which accumulates stake toward quorum and, once quorum is reached, calls `forgePerasCert` to produce a `ValidatedPerasCert` that influences chain selection.

The inbound path from the network is:

`processVotes` (called by `makePerasVotePoolWriterFromChainDB` / `makePerasVotePoolWriterFromVoteDB`) → `validatePerasVote` → `PerasVoteDB.addVote` → `updatePerasRoundVoteStates` → `forgePerasCert` → chain selection boost.

Additionally, `validatePerasCert` unconditionally returns `Right` for every certificate, compounding the issue.

---

### Impact Explanation

An attacker who knows the stake distribution (public information) can craft `PerasVote` messages claiming to be from any pool with high stake. Because `validatePerasVote` only checks that the claimed `PerasVoterId` exists in the distribution, these forged votes pass validation and accumulate stake. Once the attacker's fabricated votes exceed the quorum threshold, a false `ValidatedPerasCert` is forged for an attacker-chosen block. Peras certificates boost specific blocks in chain selection (`vpcCertBoost`), so a false certificate causes honest nodes to prefer a non-canonical chain, breaking chain selection safety beyond the intended security assumptions.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain.

---

### Likelihood Explanation

The attack requires only knowledge of the public stake distribution and the ability to send Peras vote messages over the object-diffusion mini-protocol. No keys, stake, or privileged access are needed. The `processVotes` handler is the live production inbound path for peer-submitted votes. Likelihood is high given the complete absence of any cryptographic check.

---

### Recommendation

1. Add a `VoteSignature` field to `PerasVote blk` (analogous to the `pvSignature` field already present in `Ouroboros.Consensus.Peras.Vote.V1.PerasVote`).
2. In `validatePerasVote`, after confirming the voter ID is in the stake distribution, retrieve the pool's public key and verify the vote signature over `(pvVoteRound, pvVoteBlock)` before returning `Right`.
3. Implement `validatePerasCert` to verify the aggregate certificate signature rather than unconditionally returning `Right`.
4. The referenced GitHub issue (`tweag/cardano-peras#120`) should be treated as a security-critical blocker before any deployment of the Peras vote diffusion path.

---

### Proof of Concept

1. Observe the public `PerasVoteStakeDistr` to find pool `P` with stake above the quorum threshold.
2. Craft `PerasVote { pvVoteRound = r, pvVoteBlock = attacker_block, pvVoteVoterId = P }`.
3. Send this vote (and enough similar votes for other high-stake pools) to a target node via the object-diffusion mini-protocol.
4. `processVotes` calls `validatePerasVote mkPerasParams sd vote`; `lookupPerasVoteStake` finds `P` in the distribution and returns its stake.
5. The vote is accepted as `ValidatedPerasVote` with full stake weight.
6. `updatePerasRoundVoteStates` accumulates stake; once quorum is reached, `forgePerasCert` produces a `ValidatedPerasCert` boosting `attacker_block`.
7. Chain selection now prefers `attacker_block` over the honest canonical tip.

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
