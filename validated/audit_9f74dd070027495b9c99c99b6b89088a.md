### Title
`checkPreferTheirsOverOurs` Hardcodes `emptyPerasWeightSnapshot`, Causing Incorrect Peer Disconnection When Peras Weight Boosts Would Make Candidate Preferred - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` instead of the real Peras weight snapshot. This mirrors the external report's root cause exactly: two authorization sources exist (non-Peras block-count comparison and Peras-weighted comparison), but the code only consults the first one and disconnects if it is insufficient, even when the second source would have made the candidate preferred. When Peras is active, a candidate chain that is strictly preferred under the weighted rule (due to certificate-backed weight boosts) but equal or inferior under the plain block-count rule will be incorrectly rejected with `CandidateTooSparse`, causing the node to sever the connection and permanently miss the canonical Peras-boosted chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever the ledger view cannot be projected for an incoming header (i.e., the header is beyond the forecast horizon). Its purpose is to guard against a node tracking a candidate chain that can never be adopted:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot          -- ← always ignores Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

`preferAnchoredCandidate` has two distinct code paths gated on `isEmptyPerasWeightSnapshot`:

- **Non-Peras path** (`isEmptyPerasWeightSnapshot weights = True`): compares tips via `SelectView` (block number + VRF tiebreaker).
- **Peras path** (`otherwise`): computes `WeightedSelectView` over the suffix after the intersection, adding certificate-backed `PerasWeight` boosts to the block number. [2](#0-1) 

By hardcoding `emptyPerasWeightSnapshot`, `checkPreferTheirsOverOurs` always takes the non-Peras path. The actual chain-selection logic in `chainSelection` and `initialChainSelection` correctly receives the real `PerasWeightSnapshot`: [3](#0-2) 

This creates an inconsistency: the ChainDB uses Peras weights to decide which chain to adopt, but the ChainSync client uses a weight-blind comparison to decide whether to keep tracking a peer. The two "allowance sources" are never composed — the code checks the first (block count) and disconnects on failure without ever consulting the second (Peras weight).

### Impact Explanation

When Peras is active, the canonical chain is determined by `wsvTotalWeight = blockNo + PerasWeight`. A candidate chain with the same block count as the local chain but carrying Peras certificate boosts is strictly preferred under the weighted rule (`wsvTotalWeight cand > wsvTotalWeight ours`) yet equal or inferior under the plain block-count rule (`svBlockNo cand == svBlockNo ours`, tiebreaker may not favor it). [5](#0-4) 

When such a candidate has a header beyond the forecast horizon, `checkPreferTheirsOverOurs` fires, the non-Peras comparison returns `ShouldNotSwitch`, and the node throws `CandidateTooSparse`. The peer is disconnected. The node then retains its current (less-preferred) chain. If all peers serving the canonical Peras-boosted chain are disconnected this way, the node permanently diverges from the canonical chain — a chain-selection failure that lets an unprivileged peer (or network condition) cause an honest node to prefer a non-canonical, less-secure chain.

---

### Likelihood Explanation

The preconditions are:
1. Peras is activated (certificates are being issued and weight boosts are non-zero).
2. A candidate chain exists whose Peras-weighted total exceeds the local chain's total, but whose raw block count does not.
3. The candidate has at least one header beyond the current forecast horizon (common during initial sync or after a long slot gap).

Condition 3 is routinely satisfied during node startup and sync. Conditions 1–2 become satisfied as soon as Peras certificates are issued on a fork that has not yet grown longer in raw blocks. No privileged access, key material, or stake majority is required; any peer serving a valid Peras-boosted chain triggers the bug.

---

### Recommendation

Pass the real `PerasWeightSnapshot` (already available in the `ChainSyncClientEnv`) to `preferAnchoredCandidate` inside `checkPreferTheirsOverOurs`, mirroring how `chainSelection` and `initialChainSelection` use it. The existing TODO comment at line 1841 already acknowledges this:

```
-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
emptyPerasWeightSnapshot
```

Until the check is removed entirely (per the linked issue), it must use the real snapshot so that the two comparison sources are consulted in order — first Peras-weighted, falling back to block-count — exactly as the external report recommends for the analogous allowance check.

---

### Proof of Concept

1. Peras is active; certificates have been issued boosting blocks on fork **F** (same block count as the local chain **L**, but `wsvTotalWeight(F) > wsvTotalWeight(L)`).
2. Peer **P** serves fork **F**. Its next header is beyond the local forecast horizon (e.g., a slot gap exceeds the stability window).
3. `readLedgerStateHelper` calls `projectLedgerView`; it returns `Nothing` (outside forecast range).
4. `checkPreferTheirsOverOurs` is called with `emptyPerasWeightSnapshot`.
5. `preferAnchoredCandidate` takes the non-Peras path: `svBlockNo(F_tip) == svBlockNo(L_tip)`, tiebreaker does not favor **F** → `ShouldNotSwitch`.
6. `throwSTM CandidateTooSparse` fires; peer **P** is disconnected.
7. The node retains chain **L**, which is strictly less preferred than **F** under the Peras rule.
8. If all peers serving **F** are disconnected this way, the node never adopts the canonical chain. [6](#0-5)

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
