### Title
`unavailable_utxo_callback` pre-marks `verified_deposit_utxo`, permanently blocking re-deposit after `min_deposit_amount` is lowered — (`contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

`unavailable_utxo_callback` inserts the UTXO key into `verified_deposit_utxo` as a replay guard, but this is the same set checked by `verify_deposit_callback`. If `min_deposit_amount` is later lowered via `update_config`, a relayer's legitimate re-submission of the same UTXO routes to `verify_deposit_callback`, which tries to insert the already-present key and panics with `"Already deposit utxo"`. The UTXO is permanently stuck in `unavailable_utxos` with no nBTC ever minted and no admin recovery path.

---

### Finding Description

**Step 1 — sub-minimum UTXO routed to `unavailable_utxo_callback`.**

`internal_verify_deposit` checks `deposit_amount < config.min_deposit_amount` at call time and schedules `unavailable_utxo_callback`: [1](#0-0) 

**Step 2 — `unavailable_utxo_callback` inserts into `verified_deposit_utxo`.**

The callback unconditionally inserts the UTXO key into `verified_deposit_utxo` before writing to `unavailable_utxos`: [2](#0-1) 

After this call the UTXO key is in `verified_deposit_utxo` and the UTXO data is in `unavailable_utxos`. No nBTC is minted.

**Step 3 — DAO lowers `min_deposit_amount`.**

`update_config` applies the change immediately with no guard for UTXOs already in `unavailable_utxos`: [3](#0-2) 

**Step 4 — relayer re-submits the same UTXO.**

Now `deposit_amount >= config.min_deposit_amount`, so `internal_verify_deposit` routes to `verify_deposit_callback`: [4](#0-3) 

**Step 5 — `verify_deposit_callback` panics.**

The callback tries to insert the same key that `unavailable_utxo_callback` already inserted: [5](#0-4) 

`LookupSet::insert` returns `false` for a duplicate; `require!` turns that into a panic. The transaction is reverted, the UTXO remains in `unavailable_utxos`, and no minting path exists.

**No recovery mechanism.** There is no admin function that removes a key from `verified_deposit_utxo` or promotes a UTXO from `unavailable_utxos` to `utxos`. The UTXO is permanently locked. [6](#0-5) 

---

### Impact Explanation

Every UTXO that was processed as sub-minimum before a `min_deposit_amount` reduction becomes permanently unprocessable. The user's BTC sits in the bridge deposit address with no nBTC ever minted and no on-chain path to recover it. This is permanent locking of user funds.

---

### Likelihood Explanation

The scenario requires only two routine operational events: a relayer processing a small deposit (normal behavior), and the DAO later lowering the minimum deposit threshold (a plausible governance action, e.g., to improve UX or respond to BTC price changes). Neither actor needs to be malicious. Any UTXO that was sub-minimum at the time of the first `verify_deposit` call and is above the new minimum after the config change will be permanently locked.

---

### Recommendation

`unavailable_utxo_callback` should **not** insert into `verified_deposit_utxo`. The purpose of `verified_deposit_utxo` is to prevent double-minting; a UTXO that was rejected for being too small has never been minted, so it must remain re-processable. The insert in `unavailable_utxo_callback` (lines 306–311) should be removed. If replay protection for unavailable UTXOs is desired, a separate set (e.g., `verified_unavailable_utxo`) should be used, and `internal_verify_deposit` should check that set before routing to `unavailable_utxo_callback` to prevent duplicate unavailable-UTXO submissions.

---

### Proof of Concept

```rust
// 1. min_deposit_amount = 10_000 sats
// 2. Relayer calls verify_deposit for UTXO with balance = 5_000 sats
//    → internal_verify_deposit routes to unavailable_utxo_callback
//    → unavailable_utxo_callback inserts key into verified_deposit_utxo
//    → UTXO stored in unavailable_utxos; no nBTC minted
// 3. DAO calls update_config({ min_deposit_amount: 3_000 })
// 4. Relayer calls verify_deposit again for the same UTXO (5_000 >= 3_000)
//    → internal_verify_deposit routes to verify_deposit_callback
//    → verify_deposit_callback: verified_deposit_utxo.insert(...) returns false
//    → require! panics: "Already deposit utxo"
// 5. UTXO permanently stuck in unavailable_utxos; no recovery path exists.
```
