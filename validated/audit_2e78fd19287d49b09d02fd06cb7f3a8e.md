### Title
Missing Cryptographic Signature Verification in `validatePerasVote` Allows Voter Identity Spoofing — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `PerasVote blk` data type carries no cryptographic signature field, and `validatePerasVote` only checks whether the claimed `pvVoteVoterId` is present in the stake distribution. Any unprivileged peer can craft a `PerasVote` message claiming to be from any legitimate stake pool voter without possessing that voter's private key, bypassing Peras vote authorization entirely.

---

### Finding Description

The `BlockSupportsPeras` instance for all blocks defines:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- attacker-controlled, no proof of ownership
  }
``` [1](#0-0) 

There is no signature field. The `pvVoteVoterId` is a bare `KeyHash StakePool` that any peer can set to any value.

The validation function is:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

The only check is a map lookup on `pvVoteVoterId`. There is no cryptographic proof that the claimed voter signed the vote. This is the direct analog of the Hypervisor `deposit(from, to, ...)` bug: `pvVoteVoterId` plays the role of `from`, and there is no equivalent of `require(msg.sender == from)`.

This `validatePerasVote` is called in the production vote ingestion path:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

which is wired into `makePerasVotePoolWriterFromChainDB`, the production writer used by the vote diffusion miniprotocol handler: [4](#0-3) 

The vote diffusion inbound handler is registered for every peer connection: [5](#0-4) 

A temporary mitigation exists: the production wiring currently passes `pure (PerasVoteStakeDistr mempty)` — an empty stake distribution — which causes every vote to fail the `lookupPerasVoteStake` check and be rejected: [6](#0-5) 

However, this is explicitly marked as a TODO pending proper plumbing of the committee selection data. The structural flaw — the missing signature field and missing signature check — is present in the production code path today.

Note that a properly designed vote type already exists in `Ouroboros.Consensus.Peras.Vote.V1`, which includes `pvSignature :: VoteSignature PerasBLSCrypto` and a VRF eligibility proof: [7](#0-6) 

The production diffusion layer uses the signature-free `PerasVote blk` type instead.

---

### Impact Explanation

Once the TODO is resolved and a real stake distribution is supplied, any unprivileged peer can:

1. Enumerate legitimate stake pool IDs from the public ledger.
2. Craft `PerasVote` messages with `pvVoteVoterId` set to those IDs, claiming any round and any target block.
3. Send them via the vote diffusion miniprotocol.
4. `validatePerasVote` accepts each vote as `ValidatedPerasVote` carrying the victim voter's full stake weight.
5. Accumulate enough forged votes to satisfy `votesReachQuorum`, triggering `forgePerasCert` and producing a `ValidatedPerasCert` with a `vpcCertBoost` weight for an attacker-chosen block.
6. The ChainDB applies this boost during chain selection, causing the node to prefer a minority or attacker-controlled fork over the canonical chain.

This is a **bypass of Peras vote authorization** leading to a **chain selection manipulation** — an honest node is made to prefer a non-canonical chain through forged committee votes, violating the Peras safety assumption that only legitimate committee members can cast valid votes.

---

### Likelihood Explanation

**Currently low** because the empty stake distribution blocks all votes. **Immediately high** once the TODO is resolved, since:
- The attack requires only a TCP connection to the node's vote diffusion port.
- No private keys, stake, or privileged access are needed.
- Legitimate voter IDs are publicly derivable from the ledger stake distribution.
- The forged votes are structurally indistinguishable from legitimate ones.

---

### Recommendation

1. Add a mandatory cryptographic signature field to `PerasVote blk` (as already done in `Peras.Vote.V1`).
2. In `validatePerasVote`, verify the signature against the public key associated with `pvVoteVoterId` in the committee before accepting the vote.
3. Do not resolve the stake distribution TODO without simultaneously implementing signature verification — the two must be introduced together.
4. Apply the same fix to `validatePerasCert`, which currently accepts any certificate unconditionally: [8](#0-7)
