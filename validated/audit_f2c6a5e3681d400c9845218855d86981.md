Audit Report

## Title
Non-Atomic `burn.and(mint)` in `swap_migrated_token` Causes Permanent Token Loss on Mint Failure — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`swap_migrated_token` dispatches `burn` and `mint` as two independent parallel NEAR action receipts via `burn.and(mint)`, with no callback and no rollback mechanism. The promise is immediately `.detach()`ed, and `ft_on_transfer` returns `U128(0)`, irrevocably signaling to the old token contract that all transferred tokens are consumed. If `mint` panics — which it will for any user not pre-registered on the new token — the `burn` receipt has already executed and the user's tokens are permanently destroyed with no recovery path.

## Finding Description

In `ft_on_transfer`, the `SwapMigratedToken` branch calls `swap_migrated_token`, detaches the returned promise, and immediately returns `U128(0)`: [1](#0-0) 

`swap_migrated_token` constructs the two sub-promises and joins them: [2](#0-1) 

In NEAR's execution model, `Promise::and()` schedules both sub-promises as **independent, parallel action receipts**. There is no causal dependency between them: `mint` does not wait for `burn` to succeed, and a panic in `mint` does not roll back `burn`. Because the joint promise is `.detach()`ed, there is no callback to observe or handle failure.

The `mint` function on `OmniToken` calls `self.token.internal_deposit(&account_id, amount.into())`: [3](#0-2) 

NEAR's `FungibleToken::internal_deposit` panics with "The account X is not registered" if the recipient has no storage registration. `migrate_deployed_token` only registers the bridge contract itself on the new token — not individual users: [4](#0-3) 

The `burn` receipt calls `internal_withdraw` on the bridge's balance of the old token, which succeeds because the bridge received the tokens via `ft_transfer_call`. The `mint` receipt then panics. The old tokens are gone; no new tokens are minted; the `migrated_tokens` mapping still maps old→new, so a retry is impossible (the bridge no longer holds the old tokens).

## Impact Explanation

Permanent, irreversible loss of user funds. Old tokens are burned from the bridge's custody on the old token contract. New tokens are never minted. This directly matches the Critical impact class: **permanent freezing/loss of bridged funds** on NEAR. There is no admin recovery path: the burn is final, the mint failure is silent, and the `migrated_tokens` state is unchanged.

## Likelihood Explanation

Any ordinary user who calls `ft_transfer_call` on the old token with `SwapMigratedToken` before having storage registered on the new token contract will lose their funds. The new token is a freshly deployed contract; the vast majority of migrating users will not have pre-existing storage registrations on it. No attacker action is required — the user's own migration attempt is sufficient to trigger the loss. The condition is realistic and expected to occur frequently during any token migration event.

## Recommendation

Replace the fire-and-forget `burn.and(mint)` pattern with a callback-guarded sequential flow. The safest approach is **mint-first, then burn**:

1. Call `mint` on the new token for the recipient.
2. In the mint callback, verify success.
3. Only if mint succeeded, call `burn` on the old token.
4. If mint failed, return the old tokens to the user via the `ft_on_transfer` refund mechanism (return `amount` instead of `0`).

This is safe because a failed mint leaves the old tokens intact in the bridge's custody, and the NEP-141 `ft_on_transfer` refund mechanism can return them. Additionally, ensure storage registration for the recipient on the new token is performed and confirmed before or during the swap, similar to how `fin_transfer` handles `storage_deposit_actions`.

## Proof of Concept

1. Deploy `old.token` and `new.token` as `OmniToken` contracts; deploy the bridge.
2. Call `migrate_deployed_token(chain, old.token, new.token)` — this registers only the bridge on `new.token`.
3. Create a user account with storage on `old.token` but **not** on `new.token`.
4. Mint 1000 old tokens to the user.
5. User calls `old.token.ft_transfer_call(bridge, 1000, "\"SwapMigratedToken\"")`.
6. Observe: the `burn` receipt executes successfully (bridge's old token balance decreases by 1000); the `mint` receipt panics (`internal_deposit` fails — user not registered on `new.token`).
7. Assert: user holds 0 old tokens and 0 new tokens; 1000 tokens are permanently destroyed.
