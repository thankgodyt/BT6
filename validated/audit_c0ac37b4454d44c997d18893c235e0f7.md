### Title
Missing Cryptographic Signature Verification in `validatePerasVote` Allows Unprivileged Peers to Forge Peras Votes and Manipulate Chain Selection — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` typeclass instance provides a stub `validatePerasVote` that accepts any inbound vote whose `PerasVoterId` appears in the stake distribution, without verifying the cryptographic signature that would prove the sender controls the corresponding key. Any unprivileged peer can craft a `PerasVote` message claiming to be any registered committee member, accumulate artificial stake toward quorum for an adversarially-chosen block, and cause honest nodes to apply a Peras chain-selection weight boost to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasVote` as the gate that must be passed before a vote is admitted to the `PerasVoteDB` and counted toward quorum. The only production instance of this typeclass is the degenerate one at: [1](#0-0) 

Its `validatePerasVote` implementation is: [2](#0-1) 

The check is purely a stake-distribution lookup: if the `pvVoteVoterId` field of the incoming `PerasVote` is a key present in `PerasVoteStakeDistr`, the vote is stamped `ValidatedPerasVote` and returned as `Right`. No signature over `(pvVoteRound, pvVoteBlock, pvVoteVoterId)` is verified. The `_params` argument is explicitly discarded.

The same stub pattern applies to `validatePerasCert`, which accepts every certificate unconditionally: [3](#0-2) 

The network entry point `processVotes` calls this validation for every inbound vote batch: [4](#0-3) 

A vote that passes `validatePerasVote` is immediately forwarded to `implAddVote` in `PerasVoteDB`: [5](#0-4) 

Once enough forged votes accumulate for a target block, `updatePerasRoundVoteStates` fires `VoteGeneratedNewCert`, a `ValidatedPerasCert` is forged, and `addPerasCertAsync` queues a chain-selection re-evaluation with the boosted weight applied to the attacker's chosen block: [6](#0-5) 

The `PerasWeightSnapshot` then inflates the chain-selection score of the adversarially-chosen block: [7](#0-6) 

A proper cryptographic implementation does exist in `WFALS.hs` (`implVerifyVote`), which verifies DSIGN vote signatures and VRF eligibility proofs: [8](#0-7) 

However, this path is never reached from `processVotes`; the `BlockSupportsPeras` typeclass dispatch goes to the stub instance exclusively.

---

### Impact Explanation

**High.** An unprivileged peer can send crafted `PerasVote` messages that impersonate any registered committee member (any `PerasVoterId` in the current stake distribution). By sending enough such votes targeting a block of the attacker's choice, the peer can:

1. Cause the victim node to forge a `ValidatedPerasCert` for an adversarially-chosen block.
2. Insert that certificate into the `PerasCertDB`, adding a Peras weight boost to that block's chain.
3. Trigger chain selection to prefer the boosted (potentially non-canonical) chain over the honest chain.

This is a chain-selection manipulation bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

---

### Likelihood Explanation

**High.** The attack requires only network access and knowledge of the current stake distribution (which is public). There is no cost beyond bandwidth. The attacker does not need any private key material, stake, or special privilege. The `processVotes` entry point is reachable from any connected peer via the Peras vote mini-protocol.

---

### Recommendation

Replace the stub `validatePerasVote` with a real implementation that:
1. Verifies the cryptographic signature in the `PerasVote` against the public key associated with `pvVoteVoterId` in the committee selection context.
2. Verifies VRF eligibility for non-persistent committee members.
3. Rejects votes whose `pvVoteVoterId` does not match the signing key used.

The `implVerifyVote` function in `Ouroboros.Consensus.Committee.WFALS` already implements this logic correctly and should be wired into the `BlockSupportsPeras` typeclass dispatch for production block types. The tracked issue `https://github.com/tweag/cardano-peras/issues/120` covers this gap and should be treated as a security-critical fix.

---

### Proof of Concept

1. Observe the current epoch's `PerasVoteStakeDistr` (public, derivable from the ledger state).
2. Pick any `PerasVoterId` (a `KeyHash`) present in that distribution with non-zero stake.
3. Craft a `PerasVote { pvVoteRound = r, pvVoteBlock = adversarialBlock, pvVoteVoterId = stolenId }`.
4. Send this vote to the target node via the Peras vote mini-protocol.
5. `processVotes` calls `validatePerasVote mkPerasParams sd vote`; since `stolenId` is in `sd`, the vote is accepted as `ValidatedPerasVote` with the stolen stake weight.
6. Repeat with different stolen `PerasVoterId` values until the accumulated stake exceeds the quorum threshold.
7. `updatePerasRoundVoteStates` fires `VoteGeneratedNewCert`; a certificate boosting `adversarialBlock` is inserted into `PerasCertDB`.
8. Chain selection re-runs with the boosted weight; the node may switch to the adversarial chain.

implAddVote perasCfg PerasVoteDbEnv{pvdeTracer, pvdeState} vote = do
  let voteId = getPerasVoteId vote
  addPerasVoteRes <- do
    WithFingerprint pvds fp <- readTVar pvdeState
    (res, pvds') <- addOrIgnoreVote pvds voteId
    writeTVar pvdeState (WithFingerprint pvds' (succ fp))
    pure res
  pure $ do
    traceWith pvdeTracer (AddVote voteId vote addPerasVoteRes)
    return addPerasVoteRes
 where
  addOrIgnoreVote pvds voteId
    -- Vote is already in the DB => ignore it
    | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
    -- New vote => try to add it to the DB
    | otherwise = tryAddVote pvds voteId

  voteAlreadyInDB pvds = pure (PerasVoteAlreadyInDB, pvds)

  tryAddVote pvds voteId = do
    let pvsVoteIds' = Set.insert voteId (pvdsVoteIds pvds)
        pvsLastTicketNo' = succ (pvdsLastTicketNo pvds)
        pvsVotesByTicket' = Map.insert pvsLastTicketNo' vote (pvdsVotesByTicket pvds)

    (addPerasVoteRes, pvsRoundVoteStates') <-
      case updatePerasRoundVoteStates vote perasCfg (pvdsRoundVoteStates pvds) of
        -- Added vote and reached a quorum, forging a new certificate
        Right (VoteGeneratedNewCert cert, pvsRoundVoteStates') ->
          pure (AddedPerasVoteAndGeneratedNewCert cert, pvsRoundVoteStates')
