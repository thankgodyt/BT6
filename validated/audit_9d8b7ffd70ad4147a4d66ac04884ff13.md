Audit Report

## Title
BTC/Zcash Address Case-Sensitivity Causes Permanent Locking of Bridged Funds - (`near/omni-bridge/src/btc.rs`, `near/omni-types/src/lib.rs`)

## Summary

`OmniAddress::Btc` and `OmniAddress::Zcash` store recipient addresses as raw, unnormalized `String` values with no case folding. When a user submits a BTC or Zcash address in non-lowercase form (e.g., uppercase Bech32 `"BC1Q..."`), the bridge stores it verbatim. The trusted relayer's BTC connector normalizes addresses to lowercase per Bech32 convention, causing the case-sensitive `require!` equality check in `submit_transfer_to_utxo_chain_connector` to fail unconditionally, permanently locking the user's bridged funds with no recovery path.

## Finding Description

`UTXOChainAddress` is a plain `String` alias with no format constraints: [1](#0-0) 

`OmniAddress` derives `PartialEq` and `Hash` from its inner types, making equality and hashing byte-for-byte string comparisons with no case folding: [2](#0-1) 

`OmniAddress::from_str` accepts the raw string for BTC and Zcash without any normalization: [3](#0-2) 

`get_utxo_address()` clones the raw stored string with no transformation: [4](#0-3) 

In `submit_transfer_to_utxo_chain_connector`, the stored address is compared byte-for-byte against the relayer-supplied `target_btc_address`: [5](#0-4) 

If the user stored `"BC1Q..."` and the relayer supplies `"bc1q..."`, the `require!` panics with `IncorrectTargetUtxoAddress` every time. The transfer is never removed from `pending_transfers` and no alternative finalization path exists. A grep across the entire codebase confirms there is no `to_lowercase` or equivalent normalization applied to BTC/Zcash addresses in any production code path.

A secondary impact exists in the `FastTransfer` matching path: `FastTransfer::id()` is computed as `sha256(borsh(self))` where `self` includes `recipient: OmniAddress`: [6](#0-5) 

If the fast relayer registered the fast transfer with `OmniAddress::Btc("bc1q...")` but the stored pending transfer has `OmniAddress::Btc("BC1Q...")`, `FastTransfer::from_transfer` produces a different ID, the `get_fast_transfer_status` lookup returns `None`, and the fast relayer's advanced funds are not reimbursed.

## Impact Explanation

An unprivileged user who submits a BTC or Zcash recipient address in non-lowercase form causes their bridged tokens to be permanently locked in the NEAR bridge contract. The `require!` in `submit_transfer_to_utxo_chain_connector` always fails, and no code path exists to recover or redirect the stuck transfer. This matches the Critical impact class: **permanent freezing of bridged funds**.

## Likelihood Explanation

Bech32 (BTC `bc1q...`, `bc1p...`) and Bech32m (Zcash `u1...`, `zs1...`) addresses are defined as case-insensitive by their respective BIPs/ZIPs — encoders MUST output lowercase, but decoders MUST accept both cases. Many wallets display addresses in uppercase or mixed case. The bridge imposes no format validation on BTC/Zcash addresses at ingestion: [3](#0-2) 

Any user who submits an address in uppercase or mixed case — by mistake, through a non-conforming wallet, or deliberately — triggers the permanent lock. The mismatch is systematic: the bridge accepts any case at ingestion but the relayer always normalizes to lowercase.

## Recommendation

Normalize BTC and Zcash addresses to lowercase at the point of ingestion in `OmniAddress::from_str` for the `"btc"` and `"zcash"` arms:

```rust
"btc"   => Ok(Self::Btc(recipient.to_lowercase())),
"zcash" => Ok(Self::Zcash(recipient.to_lowercase())),
```

Apply the same normalization in `new_from_slice` for `ChainKind::Btc` and `ChainKind::Zcash`. Optionally, also normalize `target_btc_address` before the equality check in `submit_transfer_to_utxo_chain_connector` as a defense-in-depth measure.

## Proof of Concept

**Entry path (unprivileged user):**

1. User calls `ft_transfer_call` on the nBTC token with `msg`:
   ```json
   {"InitTransfer": {"recipient": "btc:BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4", "fee": "0", "native_token_fee": "0"}}
   ```
2. `ft_on_transfer` → `init_transfer` stores `OmniAddress::Btc("BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4")` in `pending_transfers`.
3. Trusted relayer calls `submit_transfer_to_utxo_chain_connector` with:
   ```json
   {"Withdraw": {"target_btc_address": "bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4", ...}}
   ```
4. Inside `submit_transfer_to_utxo_chain_connector`:
   - `btc_address` = `"BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4"` (from storage)
   - `target_btc_address` = `"bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4"` (from relayer)
   - `require!(btc_address == target_btc_address, ...)` → **panics with `IncorrectTargetUtxoAddress`**
5. Transfer remains in `pending_transfers` indefinitely. No alternative finalization path exists. User's bridged BTC is permanently locked.

**Minimal unit test to reproduce:**
```rust
#[test]
fn test_uppercase_btc_address_locks_funds() {
    let upper = OmniAddress::from_str("btc:BC1QW508D6QEJXTDG4Y5R3ZARVARY0C5XW7KV8F3T4").unwrap();
    let lower = "bc1qw508d6qejxtdg4y5r3zarvary0c5xw7kv8f3t4".to_string();
    // Simulates the require! check in submit_transfer_to_utxo_chain_connector
    assert_ne!(upper.get_utxo_address().unwrap(), lower); // This passes — proving the mismatch
}
```
