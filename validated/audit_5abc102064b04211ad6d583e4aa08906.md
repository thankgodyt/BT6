### Title
Peras Certificate Verification Bypass Allows Unprivileged Peer to Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` — accepting every certificate without any cryptographic check. This stub is wired directly into the production `makePerasCertPoolWriterFromChainDB` path. An unprivileged peer can send a crafted `PerasCert` over the object-diffusion miniprotocol, have it accepted as "validated," and cause the receiving node to apply a Peras weight boost to an arbitrary block in its VolatileDB, potentially triggering a chain switch to an attacker-chosen fork.

### Finding Description

**Root cause — unconditional `Right` in `validatePerasCert`:**

The `BlockSupportsPeras` class requires implementors to supply a `validatePerasCert` function that cryptographically verifies a certificate before it may influence chain selection. The default instance, explicitly labelled a "degenerate instance for all blks to get things to compile," satisfies this requirement with a no-op:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of content, is wrapped in `ValidatedPerasCert` and returned as valid. No signature, committee membership, round-number range, or boosted-block existence check is performed.

**Production wiring — `makePerasCertPoolWriterFromChainDB`:**

The comment on `makePerasCertPoolWriterFromCertDB` explicitly states it is "mostly meant for tests"; the production writer is `makePerasCertPoolWriterFromChainDB`. Both pass `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

**`processCerts` — the validation gate that never rejects:**

`processCerts` calls `validateCert` on each inbound certificate and only rejects a batch when at least one call returns `Left`. Because the stub always returns `Right`, the entire batch is unconditionally accepted and forwarded to `addCert`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**Chain-selection side-effect — `chainSelSync` / `addPerasCertAsync`:**

Once a certificate clears `processCerts`, it is enqueued via `addPerasCertAsync` → `addPerasCertToQueue` → `chainSelSync`. Inside `chainSelSync`, if the boosted block exists in the VolatileDB and is not already on the current chain, `chainSelectionForBlock` is invoked for that block, potentially switching the node to a different fork:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Analogy to the external report:**

The external report's `distributeRewardToRelayers` has an `onlyGateway` modifier that is satisfied because the call is routed through `_applyMessages`; the attacker controls the *parameters* while the *origin check* passes. Here, `processCerts` is the "origin check" — it is supposed to reject invalid certificates — but because `validatePerasCert` always returns `Right`, the check is trivially satisfied for any peer-supplied certificate. The attacker controls the certificate content (`pcCertBoostedBlock`, `pcCertRound`) while the validation gate passes unconditionally.

### Impact Explanation

**Severity: High — chain selection manipulation.**

An unprivileged peer can craft a `PerasCert` naming any block hash present in the target node's VolatileDB as `pcCertBoostedBlock`. The certificate passes validation, is stored in `PerasCertDB`, and triggers `chainSelectionForBlock` for the named block. Because Peras weight boosts are additive to chain length in the `preferAnchoredCandidate` comparison, a sufficiently large boost (`vpcCertBoost = perasWeight params`) can cause the node to prefer a shorter fork over its current selection, constituting a chain-selection manipulation that lets an unprivileged peer make an honest node prefer a non-canonical chain beyond the intended security assumptions. [5](#0-4) 

### Likelihood Explanation

The object-diffusion miniprotocol for Peras certificates is reachable from any node-to-node peer without authentication. The stub validation is in the production source tree (`ouroboros-consensus/src/ouroboros-consensus/`, not `unstable-*` or test directories), and `makePerasCertPoolWriterFromChainDB` is explicitly documented as the production writer. Any peer that can establish a node-to-node connection and speak the object-diffusion protocol can exploit this. No stake, keys, or prior relationship is required. [6](#0-5) 

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:
1. The aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. That each claimed voter is a legitimate committee member for the given round (eligibility proof / VRF output).
3. That the voter bitmap represents a quorum of stake.
4. That `pcCertRound` falls within an acceptable window relative to the current slot.

Until the real implementation is in place, the production `makePerasCertPoolWriterFromChainDB` should refuse to accept any externally received certificate (return a hard error or drop all inbound certs) rather than silently accepting them. The `TODO replace when actual plumbing is in place` comment at line 125–126 of `PerasCert.hs` confirms the developers are aware this is incomplete; the risk is that the incomplete code is already wired into the live chain-selection path. [7](#0-6) 

### Proof of Concept

1. **Setup**: Run a node with the Peras object-diffusion miniprotocol enabled (production configuration using `makePerasCertPoolWriterFromChainDB`).

2. **Identify target block**: Observe the node's VolatileDB to find a block hash `H` on a minority fork that the node has not selected.

3. **Craft certificate**: Construct a `PerasCert` with:
   - `pcCertRound = <any round not yet in PerasCertDB>`
   - `pcCertBoostedBlock = BlockPoint <slot> H`

4. **Send via miniprotocol**: Connect as a peer and send the crafted certificate through the object-diffusion protocol for Peras certificates.

5. **Observe**: `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert=cert, vpcCertBoost=perasWeight params}`. The certificate is enqueued via `addPerasCertAsync`. `chainSelSync` calls `chainSelectionForBlock` for block `H`. If the Peras weight boost makes the fork containing `H` heavier than the current selection, the node switches to that fork.

**Expected outcome**: The node switches to the attacker-chosen fork without any cryptographic proof that a legitimate Peras committee ever voted for that block.

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
