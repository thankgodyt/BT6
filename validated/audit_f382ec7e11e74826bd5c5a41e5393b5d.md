### Title
Unrestricted Caller and Attacker-Controlled `refund_address` in `request_refund` Enables BTC Redirection After Timelock — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is publicly callable by any NEAR account and accepts a fully attacker-controlled `refund_address` with no check that the caller is the original depositor. If the DAO/Operator fails to reject the malicious request within the 14-day `unsafe_refund_timelock_sec`, the attacker can call `execute_refund`, causing the MPC to sign a PSBT that sends the deposited BTC to the attacker's address, permanently blocking the legitimate `verify_deposit` path.

---

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries only a `#[pause]` guard and a narrow `gas_fee` role-check:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,   // ← fully attacker-controlled
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
    if gas_fee.is_some() {
        // only DAO/Operator can set custom gas_fee
        ...
    }
    self.internal_request_refund(...)
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), the `refund_address` argument is accepted verbatim from any caller with no identity check against `deposit_msg.recipient_id`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

The callback verifies the BTC transaction is real and the output script matches the deposit address, but stores the attacker-supplied `refund_address` directly into the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,   // ← attacker's BTC address stored here
    gas_fee: resolved_gas_fee,
    ...
};
self.data_mut().refund_requests.insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

After `unsafe_refund_timelock_sec` (14 days by default) elapses, `execute_refund` is also publicly callable. It calls `finalize_refund_with_psbt`, which inserts the UTXO into `verified_deposit_utxo` and creates a PSBT paying `refund_amount` to the stored `refund_address`:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [4](#0-3) 

Once `verified_deposit_utxo` contains the key, any subsequent `verify_deposit` call for the same UTXO is permanently blocked. The MPC then signs the PSBT and the BTC is sent to the attacker's address.

The `unsafe_refund_timelock_sec` is the only protection, relying entirely on the DAO/Operator actively monitoring and rejecting suspicious requests within 14 days:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [5](#0-4) 

This is directly analogous to the external report's finding: the "allow-list" of who may supply a `refund_address` is too permissive (any caller), just as the snap's origin regex was too permissive (allowing `http://` and `localhost` in production).

---

### Impact Explanation

If the DAO/Operator fails to reject the malicious refund request within 14 days **and** the relayer has not yet called `verify_deposit` for the same UTXO, the attacker can:

1. Trigger `execute_refund`, causing the MPC to sign a PSBT paying the deposited BTC to the attacker's address.
2. Permanently block the legitimate `verify_deposit` path via the `verified_deposit_utxo` insertion.

Result: the depositor loses their BTC and receives no nBTC. This is a significant loss of user funds. Classified **Medium** because the 14-day timelock and active DAO rejection are meaningful mitigations, but the root cause is a missing caller restriction, not a governance assumption.

---

### Likelihood Explanation

- `request_refund` is publicly reachable by any NEAR account with no role requirement.
- The attacker only needs to know the `deposit_msg` (derivable from the deposit address, which is public) and the raw BTC transaction bytes (public on-chain).
- The attack window is 14 days — a realistic period during which a relayer may be slow or a DAO may miss a monitoring alert.
- No privileged key or operator collusion is required.

---

### Recommendation

Add a caller-identity check in `request_refund` (or its callback) that requires the caller to be `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`. Alternatively, restrict the permissionless `refund_address` path to whitelisted relayers, mirroring the `#[trusted_relayer]` pattern already used on deposit/withdraw endpoints. The pre-authorized path (`deposit_msg.refund_address.is_some()`) is safe as-is.

---

### Proof of Concept

1. User deposits BTC to the bridge address derived from `deposit_msg { recipient_id: "user.near", refund_address: None, ... }`.
2. Attacker observes the BTC transaction on-chain, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(deposit_msg, "attacker_btc_addr", tx_bytes, vout, proof, None)
   ```
3. `request_refund_callback` verifies the BTC proof, confirms the output script matches the deposit address, and stores `refund_address = "attacker_btc_addr"` in `refund_requests`.
4. DAO does not reject within 14 days; relayer has not called `verify_deposit`.
5. Attacker calls `execute_refund(utxo_storage_key, None)`.
6. `finalize_refund_with_psbt` inserts the UTXO into `verified_deposit_utxo` (blocking future `verify_deposit`) and submits a PSBT to the MPC paying `deposit_amount - gas_fee` to `"attacker_btc_addr"`.
7. MPC signs; attacker broadcasts; BTC is received by the attacker. The user's nBTC is never minted.
