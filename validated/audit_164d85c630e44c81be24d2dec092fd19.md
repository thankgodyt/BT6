### Title
Silent Permanent Token Loss in Legacy `ft_transfer` Redirect When `withdraw_relayer` Is Unset — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `ft_transfer` override in the nbtc contract implements a legacy Near Intents bridging flow. When a user calls `ft_transfer` targeting the nbtc contract itself with a `WITHDRAW_TO:` memo, the function attempts to redirect the transfer to a configured `withdraw_relayer`. If `withdraw_relayer` has not been set, the function silently falls through and transfers the user's tokens into the nbtc contract's **own** balance — a dead-end with no recovery path — instead of reverting.

---

### Finding Description

In `contracts/nbtc/src/lib.rs` at lines 183–196, the `FungibleTokenCore::ft_transfer` override contains the following logic: [1](#0-0) 

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);
}
```

When the outer condition is true (`receiver_id == nbtc_contract` and memo starts with `WITHDRAW_TO:`), but `read_withdraw_relayer_address()` returns `None`, the inner `if let Some(...)` block is skipped entirely. Execution falls through to the final line:

```rust
self.token.ft_transfer(receiver_id, amount, memo);
```

Here `receiver_id` is still `env::current_account_id()` — the nbtc contract itself. The nbtc contract's own account is explicitly registered during initialization: [2](#0-1) 

So the transfer **succeeds silently** — the user's nBTC is moved into the nbtc contract's own token balance.

The `withdraw_relayer` is set via `set_withdraw_relayer_address`, which is a controller-only function with no on-chain enforcement that it must be set before the legacy flow is usable: [3](#0-2) 

The bridge's `burn` function only withdraws from the **bridge contract's** balance (`self.bridge_id`), not from the nbtc contract's own balance: [4](#0-3) 

There is no function in the nbtc contract that allows the controller, bridge, or any party to transfer tokens out of the nbtc contract's own balance. The tokens are permanently locked.

---

### Impact Explanation

Any user who calls `ft_transfer(nbtc_contract_id, amount, "WITHDRAW_TO:...")` while `withdraw_relayer` is unset permanently loses their nBTC. The total supply is unchanged (no burn event), but the user's balance is zeroed and the tokens accumulate in the nbtc contract's own account with no withdrawal mechanism. This constitutes a **permanent locking of user funds** requiring at minimum a contract upgrade to recover.

This maps to the allowed impact: **Medium — harmful smart-contract behavior without direct funds theft, including stuck bridge state requiring operator intervention.**

---

### Likelihood Explanation

The `withdraw_relayer` is an optional, controller-set storage value. It is absent:
- During any deployment window before `set_withdraw_relayer_address` is called
- If the controller intentionally or accidentally clears it
- If the controller key is rotated and the new controller forgets to re-set it

Any NEAR account holder who uses the Near Intents legacy flow (`ft_transfer` with `WITHDRAW_TO:` memo) during such a window will silently lose funds. The call succeeds with no error, giving the user no indication that anything went wrong.

---

### Recommendation

Replace the silent fall-through with an explicit panic when `withdraw_relayer` is not configured:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("withdraw_relayer not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This ensures the transaction reverts rather than silently misdirecting funds.

---

### Proof of Concept

1. Deploy the nbtc contract. Do **not** call `set_withdraw_relayer_address`.
2. Alice holds 1,000 nBTC and attempts to use the Near Intents legacy withdrawal flow:
   ```
   nbtc.ft_transfer(
       receiver_id = "nbtc.contract.near",   // nbtc contract itself
       amount = 1000,
       memo = "WITHDRAW_TO:bc1qalice..."
   )
   ```
3. Inside `ft_transfer`: `receiver_id == env::current_account_id()` ✓, memo starts with `WITHDRAW_TO:` ✓.
4. `read_withdraw_relayer_address()` returns `None` → inner block skipped.
5. Falls through to `self.token.ft_transfer("nbtc.contract.near", 1000, memo)`.
6. The nbtc contract's own account is registered → transfer **succeeds**.
7. Alice's balance: 0. nbtc contract's own balance: +1,000. No error emitted.
8. `burn` can only withdraw from `bridge_id`'s balance. No recovery path exists.
9. Alice's 1,000 nBTC are permanently locked.
