### Title
Unbound Refund Address in `request_refund` Allows Attacker to Redirect BTC Refunds to Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user creates a deposit with `deposit_msg.refund_address = None`, any unprivileged caller can invoke `request_refund` and supply an arbitrary attacker-controlled BTC address as `refund_address`. After the `unsafe_refund_timelock_sec` elapses without DAO/Operator rejection, the attacker calls `execute_refund` and the bridge's MPC pipeline sends the victim's BTC to the attacker's address. The `deposit_msg` contains no binding to the original depositor's refund address, mirroring the external report's root cause: a message that omits the account field, allowing it to be replayed for a different beneficiary.

### Finding Description

`DepositMsg` has an optional `refund_address` field: [1](#0-0) 

When a user omits `refund_address` (sets it to `None`), the `internal_request_refund` function accepts any caller-supplied BTC address without verifying that the caller is the original depositor: [2](#0-1) 

The only guard is a longer `unsafe_refund_timelock_sec` to give DAO/Operator time to reject: [3](#0-2) 

`execute_refund` is publicly callable with no caller restriction: [4](#0-3) 

The `deposit_msg` is fully public: `get_user_deposit_address` emits a `LogDepositAddress` event containing the complete `deposit_msg`, making it trivially observable by any on-chain watcher: [5](#0-4) 

The stored `RefundRequest` records the attacker-supplied `refund_address` verbatim, and `finalize_refund_with_psbt` builds the Bitcoin output to that address: [6](#0-5) 

### Impact Explanation

If the DAO/Operator does not reject the malicious request before `unsafe_refund_timelock_sec` expires, the bridge's MPC pipeline signs and broadcasts a Bitcoin transaction paying the victim's deposited BTC to the attacker's address. The victim loses their BTC permanently. This constitutes significant theft of user funds.

### Likelihood Explanation

The attack requires two preconditions: (1) the relayer fails to call `verify_deposit` (relayer downtime, network partition, or deliberate omission), and (2) the DAO/Operator fails to reject the malicious `request_refund` within `unsafe_refund_timelock_sec`. Both are realistic: relayer downtime is the exact scenario the refund system is designed for, and the DAO/Operator monitoring is a human process that can be slow or miss events. The attacker's cost is only the NEAR storage deposit for `request_refund` and `execute_refund`, which is negligible compared to any meaningful BTC deposit.

### Recommendation

Bind the refund address to the depositor at deposit time. Require that `deposit_msg.refund_address` is always set (non-`None`) before a refund can be requested, or require the caller of `request_refund` to be the `recipient_id` specified in `deposit_msg`. This mirrors the external report's recommendation: include the account field in the signed message so the message cannot be replayed for a different beneficiary.

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: "alice.near", refund_address: None, ... })`. The bridge emits `LogDepositAddress` with the full `deposit_msg` and derived BTC address.
2. Alice sends BTC to that address. The relayer goes offline; `verify_deposit` is never called.
3. Attacker observes the `LogDepositAddress` event, reconstructs Alice's `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = Alice's DepositMsg,
     refund_address = "attacker_btc_address",
     tx_bytes = <Alice's deposit tx>,
     vout = <Alice's vout>,
     proof = <valid Merkle proof>,
     gas_fee = None
   )
   ``` [7](#0-6) 
4. The Light Client validates the proof. `request_refund_callback` stores a `RefundRequest` with `refund_address = "attacker_btc_address"`. [8](#0-7) 
5. DAO/Operator does not reject within `unsafe_refund_timelock_sec`.
6. Attacker calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying Alice's BTC to the attacker's address and submits it to the MPC signer.
7. After MPC signing, the attacker calls `sign_btc_transaction` and `verify_refund_finalize`. Alice's BTC is permanently transferred to the attacker.

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
```
