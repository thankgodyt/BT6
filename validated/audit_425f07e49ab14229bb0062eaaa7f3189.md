### Title
Zcash `check_withdraw_chain_specific` Is an Empty Stub, Allowing RBF Without Fee Increase — (`contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`)

---

### Summary

The bridge uses a chain-specific dispatch pattern where Bitcoin and Zcash each provide their own implementation of `check_withdraw_chain_specific`. The Bitcoin implementation enforces that any RBF transaction pays a strictly higher gas fee than the original. The Zcash implementation is an empty stub that performs no validation at all. As a result, a Zcash user can submit a `withdraw_rbf` or `cancel_withdraw` RBF transaction with the same (or lower) gas fee as the original, which the bridge accepts on-chain but which the Zcash network will reject, leaving the bridge in a stuck state requiring operator intervention.

---

### Finding Description

The bridge compiles chain-specific logic via Rust feature flags. For RBF operations, both chains call `check_withdraw_chain_specific` inside `internal_withdraw_rbf` and `internal_cancel_withdraw`.

**Bitcoin implementation** — enforces fee increase:

```rust
// contracts/satoshi-bridge/src/bitcoin_utils/contract_methods.rs:56-64
pub(crate) fn check_withdraw_chain_specific(
    original_tx_btc_pending_info: &BTCPendingInfo,
    gas_fee: u128,
) {
    let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
    let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
    require!(additional_gas_amount > 0, "No gas increase.");
}
```

**Zcash implementation** — empty stub, no validation:

```rust
// contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs:214-218
pub(crate) fn check_withdraw_chain_specific(
    _original_tx_btc_pending_info: &BTCPendingInfo,
    _gas_fee: u128,
) {
}
```

This function is called unconditionally in both `internal_withdraw_rbf` and `internal_cancel_withdraw`:

- `contracts/satoshi-bridge/src/rbf/withdraw.rs` line 62: `Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);`
- `contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs` line 54: `Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);`

The only fee validation that does exist for Zcash RBF is inside `check_psbt_chain_specific` (ZIP-317 minimum fee check), but that only enforces a floor — it does not compare the new fee against the original transaction's fee. A user whose original withdrawal already paid the ZIP-317 minimum can re-submit an RBF at the exact same fee level and the bridge will accept it.

---

### Impact Explanation

When the bridge accepts a Zcash RBF with a non-increasing fee:

1. The bridge creates a new `BTCPendingInfo` entry and marks the original as having an RBF in flight.
2. The user (or relayer) broadcasts the RBF transaction to the Zcash network.
3. The Zcash network rejects it because it does not pay a higher fee than the mempool transaction it is supposed to replace.
4. Neither the original nor the RBF transaction confirms.
5. The UTXOs consumed by the pending transaction remain locked in the bridge's pending state indefinitely.
6. The bridge cannot recover without operator intervention (manual cleanup of the stuck `BTCPendingInfo`).

This matches the allowed Medium impact: **attacker-triggered temporary locking of bridged funds** and **stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

The `withdraw_rbf` endpoint is publicly callable by any nZEC holder who has an active pending withdrawal. No privileged role is required. A user who wishes to grief the bridge (or whose client software has a bug) can trivially submit an RBF with an unchanged fee. The Zcash `ft_on_transfer_withdraw_chain_specific` path is already in production use, making this reachable on every Zcash withdrawal that enters the RBF flow.

---

### Recommendation

Implement `check_withdraw_chain_specific` in the Zcash module to mirror the Bitcoin enforcement:

```rust
pub(crate) fn check_withdraw_chain_specific(
    original_tx_btc_pending_info: &BTCPendingInfo,
    gas_fee: u128,
) {
    let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
    let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
    require!(additional_gas_amount > 0, "No gas increase.");
}
```

### Proof of Concept

1. User calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg{...})` on the Zcash bridge.
2. Bridge creates `BTCPendingInfo` with `gas_fee = X` (at the ZIP-317 minimum).
3. User calls `withdraw_rbf(original_id, same_output_with_fee_X)`.
4. Bridge dispatches to `withdraw_rbf_chain_specific` → async `withdraw_rbf_callback` → `internal_withdraw_rbf`.
5. `internal_withdraw_rbf` calls `Self::check_withdraw_chain_specific(...)` — **no-op in Zcash**.
6. Bridge accepts the RBF, creates a second `BTCPendingInfo` with the same `gas_fee = X`, and marks the original as having an RBF.
7. User broadcasts the RBF transaction; Zcash network rejects it (fee not increased).
8. Neither transaction confirms; UTXOs are permanently locked in the bridge's pending state until an operator manually intervenes. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
