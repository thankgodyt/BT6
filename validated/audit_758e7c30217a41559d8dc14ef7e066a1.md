### Title
Missing Zero-Address Recipient Check in `init_transfer` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

The NEAR bridge's `init_transfer` function accepts any `OmniAddress` as a recipient without checking whether it is a zero address. The `OmniAddress::is_zero()` method exists in the type system but is never called at the entry point. A user can initiate a cross-chain transfer to `eth:0x0000000000000000000000000000000000000000` (or the zero address of any other supported chain). Tokens are immediately locked or burned on NEAR, the MPC service signs the transfer, and the resulting `finTransfer` call on the EVM either permanently destroys the ETH (for native-ETH transfers) or always reverts (for ERC-20/bridge-token transfers). Because no cancel or refund path exists for pending transfers, the funds are permanently frozen and the bridge's `locked_tokens` escrow counter is permanently inflated.

---

### Finding Description

**Root cause — `init_transfer` in `near/omni-bridge/src/lib.rs`:**

The only recipient validation performed is a chain-kind check:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [1](#0-0) 

There is no call to `recipient.is_zero()`. The method is fully implemented in the shared type library:

```rust
pub fn is_zero(&self) -> bool {
    match self {
        Self::Eth(address) | Self::Arb(address) | ... => address.is_zero(),
        Self::Near(address) => *address == ZERO_ACCOUNT_ID,
        Self::Sol(address) | Self::Fogo(address) => address.is_zero(),
        Self::Btc(address) | Self::Zcash(address) => address.is_empty(),
        Self::Strk(address) => address.is_zero(),
    }
}
``` [2](#0-1) 

After the missing check, `init_transfer_internal` is called, which locks or burns the user's tokens and emits an `InitTransferEvent`: [3](#0-2) 

The pending transfer is stored in `pending_transfers` and `locked_tokens` is incremented. The MPC service then signs whatever recipient is stored in the `TransferMessage` — including `address(0)`.

**Destination-side behavior — `OmniBridge.sol` `finTransfer`:**

The EVM `finTransfer` function also performs no zero-address check on `payload.recipient`:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
} else if (isBridgeToken[payload.tokenAddress]) {
    IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
} else {
    IERC20(payload.tokenAddress).safeTransfer(payload.recipient, payload.amount);
}
``` [4](#0-3) 

- **Native ETH** (`tokenAddress == address(0)`): `address(0).call{value: amount}("")` succeeds in Solidity — ETH is permanently destroyed. The destination nonce is consumed and the funds are unrecoverable.
- **ERC-20 / bridge tokens**: OpenZeppelin's `_mint` and `safeTransfer` both revert on `address(0)`. `finTransfer` always reverts, so no valid proof is ever generated.

**No refund path exists.** The `pending_transfers` entry on NEAR is only removed inside `claim_fee_callback`, which requires a valid proof from the destination chain: [5](#0-4) 

If `finTransfer` always reverts, no proof is ever produced, `claim_fee_callback` is never called, and the tokens remain locked forever. The `locked_tokens` counter is never decremented, permanently mis-accounting the bridge's escrow state.

**`BridgeToken.mint` delegates to OpenZeppelin `_mint` with no added zero-address guard:** [6](#0-5) 

---

### Impact Explanation

| Token type | `finTransfer` outcome | Fund fate |
|---|---|---|
| Native ETH (`tokenAddress == 0`) | Succeeds — ETH sent to `address(0)` | ETH permanently destroyed |
| ERC-20 / bridge token | Reverts (OZ zero-address guard) | Tokens permanently frozen on NEAR |

In both cases the user's bridged assets are unrecoverable. Additionally, `locked_tokens[(destination_chain, token_id)]` is permanently inflated, causing the bridge's escrow accounting to diverge from reality for the lifetime of the contract.

---

### Likelihood Explanation

The entry point is `ft_transfer_call` → `ft_on_transfer` → `init_transfer`, callable by any token holder. A user who supplies `recipient = "eth:0x0000000000000000000000000000000000000000"` (a syntactically valid `OmniAddress`) triggers the bug. This can occur through a malicious or buggy frontend, a programmatic integration that constructs the recipient from user-supplied data without sanitization, or a deliberate self-burn. No privileged role is required.

---

### Recommendation

Add a zero-address guard immediately after the chain-kind check in `init_transfer`:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
require!(
    !init_transfer_msg.recipient.is_zero(),
    BridgeError::InvalidRecipientAddress.as_ref()  // error variant already exists
);
``` [7](#0-6) 

Apply the same guard in the EVM `initTransfer` (reject empty `recipient` string) and in the Starknet `init_transfer` (reject zero `ContractAddress` recipient).

---

### Proof of Concept

1. Alice holds 1 000 USDC bridged on NEAR.
2. Alice (or a malicious frontend on her behalf) calls:
   ```
   ft_transfer_call(
     receiver_id = "omni-bridge.near",
     amount      = "1000000000",
     msg         = '{"InitTransfer":{"recipient":"eth:0x0000000000000000000000000000000000000000","fee":"0","native_token_fee":"0"}}'
   )
   ```
3. `init_transfer` passes the chain-kind check (`Eth != Near`), locks 1 000 USDC, stores the pending transfer, and emits `InitTransferEvent`.
4. The MPC service signs the `TransferMessage` containing `recipient = 0x0000…0000`.
5. A relayer submits `finTransfer` on Ethereum with `payload.recipient = address(0)`.
   - USDC is an ERC-20: `safeTransfer(address(0), amount)` reverts.
   - The relayer retries indefinitely — every attempt reverts.
6. No proof is ever produced. `claim_fee_callback` is never called. Alice's 1 000 USDC remain locked in the NEAR bridge contract forever. `locked_tokens[(Eth, usdc.near)]` is permanently inflated by 1 000 USDC.
