### Title
Missing Low-S Normalization on MPC Signature Allows Invalid Bitcoin/Zcash Transactions and Zcash Txid Malleability - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
`SignatureResponse::to_btc_signature()` converts the raw MPC-returned `(r, s)` pair into a Bitcoin ECDSA signature using `Signature::from_compact()` without calling `normalize_s()`. Because the NEAR chain-signatures MPC service does not guarantee a low-s value, a high-s signature can be returned and embedded into the transaction. Bitcoin (for P2WPKH inputs) and Zcash (for transparent inputs) both enforce low-s at consensus level, so the resulting transaction is network-invalid. For Zcash transparent transactions the txid additionally covers the `script_sig`, making it malleable: a third party can flip s to low-s, broadcast a valid transaction with a different txid, and leave the bridge permanently unable to finalize the withdrawal.

### Finding Description
`to_btc_signature()` assembles the compact signature directly from the MPC response fields:

```rust
// contracts/satoshi-bridge/src/chain_signature.rs  lines 41-49
pub fn to_btc_signature(&self) -> Signature {
    let r_hex = self.big_r.affine_point[2..].to_string();
    let s_hex = self.s.scalar.clone();
    let r = hex::decode(r_hex).expect("Invalid r hex");
    let s = hex::decode(s_hex).expect("Invalid s hex");
    let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
        .expect("Invalid signature");
    Signature::sighash_all(signature)   // no normalize_s() call
}
```

`from_compact` accepts any valid 64-byte `(r ‖ s)` pair, including high-s values. No `normalize_s()` call follows.

This signature is consumed in two places:

**Bitcoin P2WPKH** (`bitcoin_utils/psbt_wrapper.rs` line 163):
```rust
Some(Witness::p2wpkh(&signature.to_btc_signature(), &public_key))
```

**Zcash transparent** (`zcash_utils/psbt_wrapper.rs` lines 492-495):
```rust
let script_sig = bitcoin::script::Builder::new()
    .push_slice(signature.to_btc_signature().serialize())
    .push_key(&bitcoin::PublicKey::new(public_key))
    .into_script();
```

For Bitcoin P2WPKH, consensus enforces `SCRIPT_VERIFY_LOW_S`; a high-s witness causes the transaction to be rejected by every full node. For Zcash transparent inputs, the same low-s rule applies, and additionally the `script_sig` is committed to in the txid, so flipping s to low-s produces a different txid.

After `sign_btc_transaction_callback` stores the (potentially high-s) signature and emits `SignedBtcTransaction`, the pending entry transitions to `PendingVerify` stage keyed by `btc_pending_sign_id`. The relayer broadcasts the invalid transaction, which is rejected. The bridge is now stuck: `verify_withdraw` / `verify_withdraw_v2` / `verify_refund_finalize` all require the light-client to confirm the txid, which never confirms.

For Zcash, a third party can take the emitted `tx_bytes_base64`, flip s to low-s (a trivial arithmetic operation: `s' = curve_order - s`), broadcast the valid transaction, and the ZEC is released to the correct recipient address. The bridge, however, is looking for the original (high-s) txid, which was never mined. The `BTCPendingInfo` entry cannot be finalized, and the nBTC held in the bridge's balance cannot be burned.

### Impact Explanation
**Bitcoin path:** The bridge is stuck in `PendingVerify` state. The user can attempt `withdraw_rbf`, but if the MPC again returns a high-s value the cycle repeats. Operator intervention is required to unstick the withdrawal. This matches the allowed Medium impact: *stuck bridge state requiring operator intervention*.

**Zcash path:** The user's ZEC is released (to the correct address) by the attacker's normalized transaction, but the bridge cannot verify the withdrawal and cannot burn the corresponding nBTC. The nBTC remains locked in the bridge's balance indefinitely, creating a permanent accounting discrepancy between the nBTC supply and the backed ZEC. This matches the allowed Medium impact: *harmful smart-contract behavior without direct funds theft, including permanent burning below backed supply or stuck bridge state*.

### Likelihood Explanation
The NEAR chain-signatures MPC service returns raw secp256k1 ECDSA signatures and does not guarantee low-s. Approximately half of all signatures produced by a uniform random nonce will have s > n/2 (high-s). Every withdrawal or refund that triggers `sign_btc_transaction` has a ~50% chance of receiving a high-s value from the MPC, making this a near-certain occurrence in production at scale.

### Recommendation
Call `normalize_s()` on the secp256k1 signature before wrapping it in `Signature::sighash_all`:

```rust
pub fn to_btc_signature(&self) -> Signature {
    let r = hex::decode(&self.big_r.affine_point[2..]).expect("Invalid r hex");
    let s = hex::decode(&self.s.scalar).expect("Invalid s hex");
    let mut signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
        .expect("Invalid signature");
    signature.normalize_s();   // enforce low-s (BIP 62 / consensus)
    Signature::sighash_all(signature)
}
```

This fix applies to both the Bitcoin P2WPKH path (`bitcoin_utils/psbt_wrapper.rs`) and the Zcash transparent path (`zcash_utils/psbt_wrapper.rs`), since both call `to_btc_signature()`.

### Proof of Concept

1. Alice initiates a withdrawal: `ft_transfer_call` → `ft_on_transfer` → PSBT constructed.
2. Anyone calls `sign_btc_transaction("alice_pending_id", 0, 0)`.
3. The NEAR MPC returns a `SignatureResponse` where `s > n/2` (high-s, ~50% probability).
4. `sign_btc_transaction_callback` calls `psbt.save_signature(0, signature, pubkey)`.
   - **Bitcoin:** `Witness::p2wpkh(&signature.to_btc_signature(), &pubkey)` stores the high-s witness.
   - **Zcash:** `script_sig` is built with the high-s DER bytes.
5. `SignedBtcTransaction` event is emitted with the invalid `tx_bytes`.
6. Relayer broadcasts the transaction; every Bitcoin/Zcash node rejects it (`non-mandatory-script-verify-flag (Non-canonical DER signature)`).
7. **Zcash only:** Attacker reads `tx_bytes_base64` from the event, computes `s' = secp256k1_order - s`, replaces s in the script_sig, and broadcasts the valid transaction. It confirms with a different txid.
8. `verify_withdraw_v2("alice_pending_id", proof_for_original_txid)` is called; the light client returns `false` because the original txid was never mined. The bridge panics / reverts.

    pub fn save_signature(
        &mut self,
        sign_index: usize,
        signature: SignatureResponse,
        public_key: bitcoin::secp256k1::PublicKey,
    ) {
        let script_sig = bitcoin::script::Builder::new()
            .push_slice(signature.to_btc_signature().serialize())
            .push_key(&bitcoin::PublicKey::new(public_key))
            .into_script();

        let prevout = self.vin[sign_index].prevout().clone();
        let sequence = self.vin[sign_index].sequence();
        self.vin[sign_index] =
            ZcashTxIn::from_parts(prevout, Script(Code(script_sig.to_bytes())), sequence);
    }
