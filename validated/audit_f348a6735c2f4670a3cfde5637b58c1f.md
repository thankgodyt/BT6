### Title
Peras Vote Voter Identity Not Cryptographically Authenticated — Any Peer Can Impersonate Any Registered Stake Pool in Vote Submission - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasVote` function accepts a `PerasVote` as valid solely because the self-declared `pvVoteVoterId` field (a `KeyHash StakePool`) appears in the stake distribution. No cryptographic signature is present in the vote type, and none is verified. Any unprivileged peer can craft a `PerasVote` claiming to be any registered stake pool and have it accepted by the receiving node's Peras vote pool, directly analogous to M-21's pattern of an unvalidated identity parameter enabling impersonation.

---

### Finding Description

**Root cause — missing signature field and missing signature check in the default `BlockSupportsPeras` instance:**

The `PerasVote` data type in the default instance carries only three fields: round number, block point, and a self-declared voter identity (`pvVoteVoterId :: PerasVoterId`). There is no `VoteSignature` field. [1](#0-0) 

`validatePerasVote` only performs a stake-distribution membership lookup on the self-declared `pvVoteVoterId`. It never verifies that the sender actually controls the private key corresponding to that pool ID. [2](#0-1) 

The lookup function `lookupPerasVoteStake` simply does a `Map.lookup` on the voter ID extracted from the vote — the voter ID is entirely attacker-controlled. [3](#0-2) 

**Contrast with the properly-implemented committee schemes:**

Both `EveryoneVotes` and `WFALS` committee implementations include a `VoteSignature` in their vote types and call `verifyVoteSignature` against the pool's registered public key during `implVerifyVote`. The default instance has neither. [4](#0-3) [5](#0-4) 

**Network entry path:**

The `hPerasVoteDiffusionClient` handler in `NodeToNode.hs` wires `makePerasVotePoolWriterFromChainDB` directly into the peer-facing Peras vote diffusion miniprotocol. Any connecting peer can submit `PerasVote` messages. [6](#0-5) 

`processVotes` calls `validatePerasVote` for each inbound vote. If validation passes, the vote is added to the `PerasVoteDB` and may trigger certificate forging. [7](#0-6) [8](#0-7) 

**Current partial mitigation and why it is insufficient:**

The current wiring passes `pure (PerasVoteStakeDistr mempty)` as the stake distribution, which causes all votes to fail the lookup and be rejected. However, this is explicitly marked as a temporary TODO pending full Peras deployment. [9](#0-8) 

Once the stake distribution is wired from the ledger (as the TODO requires), the missing signature check becomes a live, exploitable bypass. The production code path — the default `BlockSupportsPeras` instance — will remain broken unless the vote type and `validatePerasVote` are corrected before that wiring is completed.

**`validatePerasCert` is also unconditionally accepting:**

The same default instance's `validatePerasCert` accepts every certificate without any check, compounding the risk. [10](#0-9) 

---

### Impact Explanation

Once the stake distribution is populated (the stated production goal), an unprivileged peer can:

1. Enumerate registered stake pools from the public ledger state.
2. Craft `PerasVote` messages claiming to be high-stake pools, targeting any block the attacker wishes to boost.
3. Submit these votes via the Peras vote diffusion miniprotocol.
4. The receiving node accepts them as valid, accumulates their stake weight, and — if quorum is reached — forges a `ValidatedPerasCert` boosting the attacker-chosen block.

A Peras certificate directly influences chain selection by adding a `perasWeight` boost to the certified block. An attacker who can forge a quorum certificate for an arbitrary block can cause honest nodes to prefer a non-canonical chain, constituting a **critical bypass of Peras vote/certificate authorization** and a **high chain-selection manipulation** impact.

---

### Likelihood Explanation

- The entry path is the public Peras vote diffusion miniprotocol, reachable by any peer with a network connection.
- No privileged access, keys, or stake is required — only knowledge of registered pool IDs (publicly available on-chain).
- The vulnerability activates the moment the stake distribution TODO is resolved, which is a planned production step.
- The `validatePerasCert` unconditional acceptance is already live regardless of the stake distribution state.

---

### Recommendation

1. **Add a `VoteSignature` field to the default `PerasVote` data type** (or require a signature as a separate parameter to `validatePerasVote`), mirroring the `EveryoneVotesVote` and `WFALSPersistentVote` designs.
2. **Implement signature verification in `validatePerasVote`**: look up the pool's registered public key from the stake distribution and call `verifyVoteSignature` (or equivalent) before accepting the vote.
3. **Implement certificate verification in `validatePerasCert`**: verify the aggregate signature against the declared voter set before returning `Right`.
4. **Do not populate the stake distribution** (remove the `mempty` TODO) until steps 1–3 are complete, to prevent the partial mitigation from being silently removed before the fix lands.

---

### Proof of Concept

**Preconditions:** A node is running with a non-empty `PerasVoteStakeDistr` (i.e., the TODO in `NodeToNode.hs` has been resolved as planned).

**Steps:**

1. Attacker reads the current stake distribution from the public ledger to obtain a set of `PerasVoterId` values (pool key hashes) with high stake.
2. Attacker connects to the target node as a peer via the node-to-node protocol.
3. Attacker sends a batch of `PerasVote` messages via the Peras vote diffusion miniprotocol, each with:
   - `pvVoteRound` = current Peras round
   - `pvVoteBlock` = point of the attacker's chosen block
   - `pvVoteVoterId` = a high-stake pool's `KeyHash` (no signing key needed)
4. `processVotes` → `validatePerasVote` → `lookupPerasVoteStake` succeeds for each vote (the voter ID is in the distribution).
5. Each vote is added to the `PerasVoteDB` with the legitimate pool's stake weight.
6. Once accumulated stake exceeds the quorum threshold, `implAddVote` triggers `forgePerasCert`, producing a `ValidatedPerasCert` boosting the attacker's chosen block.
7. The certificate propagates via the Peras cert diffusion miniprotocol and influences chain selection on all receiving nodes.

**Expected outcome:** The attacker's chosen block receives a Peras boost without the attacker controlling any stake pool private key, bypassing the entire Peras vote authorization model.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
