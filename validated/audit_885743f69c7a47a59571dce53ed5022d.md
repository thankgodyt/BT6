### Title
Decimal Normalization Rounding to Zero After Fee Deduction Permanently Freezes Bridged Funds - (`near/omni-bridge/src/lib.rs`)

### Summary

`init_transfer` validates only that `fee < amount` (in origin-decimal units) before locking or burning the user's tokens. Later, `sign_transfer` computes `normalize_amount(amount - fee, decimals)` — which performs integer floor-division by `10^(origin_decimals - decimals)` — and requires the result to be `> 0`. When `amount - fee` is smaller than the normalization divisor, the result is `0`, `sign_transfer` always panics with `InvalidAmountToTransfer`, and there is no cancel or refund path. The user's tokens are permanently frozen.

### Finding Description

**Step 1 — Transfer accepted with only a coarse fee check.**

In `init_transfer`, the sole amount validation is:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

Immediately after, `init_transfer_internal` locks (for non-deployed tokens) or burns (for bridge-deployed tokens) the full `amount`. No check is made that the post-fee, post-normalization value will be non-zero. [1](#0-0) [2](#0-1) 

**Step 2 — `sign_transfer` applies decimal normalization and enforces `> 0`.**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

`normalize_amount` is pure floor-division:

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [3](#0-2) [4](#0-3) 

**Step 3 — No recovery path exists.**

`InvalidAmountToTransfer` is the only error string for this case. [5](#0-4) 

`update_transfer_fee` only allows the fee to be *increased* (`fee.fee >= current_fee.fee`), which makes `amount - fee` even smaller. There is no public `cancel_transfer` or refund function. [6](#0-5) 

### Impact Explanation

For any token where `origin_decimals > decimals` (e.g., a NEAR-native token with 24 decimals bridged to an EVM chain registered with 6 decimals, giving a divisor of `10^18`), any transfer where `amount - fee < 10^(origin_decimals - decimals)` will:

1. Pass the `fee < amount` guard and have its tokens locked or burned.
2. Cause every subsequent `sign_transfer` call to panic unconditionally.
3. Leave the transfer permanently stuck in `pending_transfers` with no on-chain escape hatch.

**Concrete example** (origin_decimals = 24, decimals = 6):

| Parameter | Value |
|---|---|
| `amount` | `5` (origin units) |
| `fee` | `0` |
| `fee < amount` check | passes (0 < 5) |
| `normalize_amount(5, diff=18)` | `5 / 10^18 = 0` |
| `sign_transfer` result | always panics |
| Token fate | permanently locked / burned |

This is a **permanent, irrecoverable loss of bridged funds** for the affected user.

### Likelihood Explanation

The condition is reachable by any unprivileged bridge user who calls `ft_transfer_call` → `ft_on_transfer` → `init_transfer` with a small amount on a token that has a large decimal gap. The user has no on-chain signal at initiation time that the transfer is uncompletable. The decimal gap is a protocol-level configuration (set by DAO via `bind_token` / `deploy_token`) and is not visible to ordinary users. Accidental triggering is realistic; deliberate self-harm is also possible. [7](#0-6) 

### Recommendation

Add a normalization-aware guard inside `init_transfer`, before tokens are locked or burned, that mirrors the check already present in `sign_transfer`:

```rust
// Fetch decimals for the destination token
let token_address = self.get_token_address(
    init_transfer_msg.get_destination_chain(),
    self.get_token_id(&OmniAddress::Near(token_id.clone())),
);
if let Some(addr) = token_address {
    if let Some(decimals) = self.token_decimals.get(&addr) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee().unwrap_or(0),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This ensures the transfer is rejected at initiation — before any tokens are moved — rather than silently accepted and then permanently stuck.

### Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 6` (divisor = `10^18`).
2. Call `ft_transfer_call` with `amount = 5`, `fee = 0`, valid EVM recipient.
3. Observe: `init_transfer` succeeds; tokens are locked/burned; `InitTransferEvent` is emitted.
4. Call `sign_transfer` for the resulting `transfer_id`.
5. Observe: call panics with `ERR_INVALID_AMOUNT_TO_TRANSFER` because `normalize_amount(5, {decimals:6, origin_decimals:24}) = 0`.
6. Attempt `update_transfer_fee` to raise fee — impossible to make `amount - fee` larger.
7. Tokens remain permanently locked with no recovery path. [3](#0-2) [1](#0-0) [4](#0-3)

    fn init_transfer_internal(
        &mut self,
        transfer_message: TransferMessage,
        storage_owner: AccountId,
    ) -> U128 {
        let required_storage_balance = self
            .add_transfer_message(transfer_message.clone(), storage_owner.clone())
            .saturating_add(NearToken::from_yoctonear(transfer_message.fee.native_fee.0));

        if self
            .try_update_storage_balance(
                storage_owner,
                required_storage_balance,
                NearToken::from_yoctonear(0),
            )
            .is_err()
        {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
            self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);

            self.lock_tokens_if_needed(
                transfer_message.get_destination_chain(),
                &token_id,
                transfer_message.amount.0,
            );
        } else {
            self.remove_transfer_message_without_refund(transfer_message.get_transfer_id());
            return transfer_message.amount;
        }

        env::log_str(&OmniBridgeEvent::InitTransferEvent { transfer_message }.to_log_string());
        U128(0)
    }
