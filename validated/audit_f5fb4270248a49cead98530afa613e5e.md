Audit Report

## Title
Re-entrancy via Malicious ERC1155 Token in `initTransfer1155` Enables Unauthorized NEAR-Side Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` in `OmniBridge.sol` performs an external call to an attacker-controlled `tokenAddress` via `IERC1155(tokenAddress).safeTransferFrom` before emitting the `InitTransfer` event, with no reentrancy guard. A malicious ERC1155 contract can re-enter `initTransfer1155` during this call, causing multiple `InitTransfer` events to be emitted with distinct, valid nonces while locking zero real tokens. The NEAR side treats each emitted event as authoritative proof of a locked deposit and mints the corresponding bridged tokens, resulting in unbacked minting and theft from the protocol's collateral pool.

## Finding Description
In `initTransfer1155` (L439–L490), the execution order is:

1. **L448**: `currentOriginNonce += 1` — nonce is incremented before the external call.
2. **L458–L464**: `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` — external call to a fully attacker-controlled address with no whitelist check.
3. **L468–L478**: `initTransferExtension(...)` — called after the external call.
4. **L480–L489**: `emit BridgeTypes.InitTransfer(...)` — event emitted after the external call.

Because the nonce is incremented at step 1 before the external call at step 2, each re-entrant invocation of `initTransfer1155` receives a fresh, unique `currentOriginNonce`. As the re-entrant call stack unwinds, each frame emits its own `InitTransfer` event with a distinct nonce. The malicious `safeTransferFrom` implementation never actually transfers any tokens to the bridge.

The `onERC1155Received` guard (L522–L535) checks `operator != address(this)` and reverts for direct pushes, but this is entirely irrelevant to the attack: the malicious token's `safeTransferFrom` re-enters `initTransfer1155` directly and does not trigger `onERC1155Received` on the bridge at all.

There is no `ReentrancyGuard` or `nonReentrant` modifier on `initTransfer1155`. The contract does not import or use OpenZeppelin's `ReentrancyGuardUpgradeable`.

The documented security invariant in `evm/CLAUDE.md` (L36) explicitly states: *"`InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held."* This invariant is violated by the reentrancy path.

On the NEAR side, `fin_transfer` (in `near/omni-bridge/src/lib.rs` L673) calls `verify_proof` against the EVM light client, then in `fin_transfer_callback` (L700–L746) processes the `InitTransferMessage` parsed from the proven log entry. The `add_fin_transfer` function (L2226–L2234) uses a `finalised_transfers` set keyed by `TransferId { origin_chain, origin_nonce }`. Since each re-entrant frame emits a distinct `origin_nonce`, each event produces a distinct `TransferId`, and `add_fin_transfer` will not detect any duplicate — every one of the N forged events can be independently finalized on NEAR, minting N × `amount` tokens to the attacker.

## Impact Explanation
This is a direct, concrete instance of **unauthorized minting of bridged funds**. An attacker locks zero (or one) real ERC1155 tokens on EVM but receives N × `amount` minted bridged tokens on NEAR. Each re-entrant frame produces a cryptographically valid, light-client-provable `InitTransfer` event with a unique nonce. The NEAR bridge has no mechanism to detect that these events originated from a reentrancy attack rather than legitimate deposits. This directly inflates the bridged token supply without backing collateral, constituting theft of value from all legitimate holders of the bridged token and from the protocol's collateral pool. This matches the allowed Critical impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."*

## Likelihood Explanation
The attack requires no privileged access, no leaked keys, no external dependency failure, and no victim mistakes. `initTransfer1155` is `external payable` with only a pause check. Any address can supply an arbitrary `tokenAddress`. Deploying a malicious ERC1155 contract costs only gas. The attack is fully self-contained in a single transaction. The entry point is completely open to any unprivileged external caller.

## Recommendation
1. **Add `ReentrancyGuard`**: Apply OpenZeppelin's `ReentrancyGuardUpgradeable` and the `nonReentrant` modifier to `initTransfer1155` (and `initTransfer` for consistency, as it also makes external calls to arbitrary ERC20 tokens).
2. **Checks-Effects-Interactions**: Emit `InitTransfer` and call `initTransferExtension` *before* the external `safeTransferFrom` call, or record the nonce in a used-nonces mapping before the external call so re-entrant invocations with the same nonce are rejected.
3. **Token allowlist**: Require that `tokenAddress` has been pre-registered via `logMetadata1155` before `initTransfer1155` will accept it, limiting the attack surface to tokens the protocol has explicitly acknowledged.

## Proof of Concept
```solidity
contract MaliciousERC1155 is IERC1155 {
    OmniBridge bridge;
    uint256 depth;

    constructor(address _bridge) { bridge = OmniBridge(_bridge); }

    function safeTransferFrom(
        address from, address to, uint256 id, uint256 amount, bytes calldata
    ) external override {
        // Re-enter up to 5 times; never actually transfer tokens
        if (depth < 5) {
            depth++;
            bridge.initTransfer1155(
                address(this), id, uint128(amount), 0, 0, "attacker.near", ""
            );
            depth--;
        }
        // onERC1155Received is never called; no tokens move
    }
    // ... other IERC1155 stubs returning true / empty
}

// Attack sequence (single transaction):
// 1. Deploy MaliciousERC1155 pointing at bridge
// 2. Call bridge.initTransfer1155(address(malicious), tokenId, amount, 0, 0, "attacker.near", "")
//    → safeTransferFrom re-enters initTransfer1155 five more times
//    → 6 InitTransfer events emitted, nonces N, N+1, N+2, N+3, N+4, N+5
//    → 0 real tokens locked
// 3. Submit each of the 6 proven log entries to NEAR fin_transfer
//    → 6 × amount bridged tokens minted to attacker.near
//    → Each has a distinct origin_nonce; add_fin_transfer sees no duplicate
```

A local Hardhat/Foundry test can reproduce this by deploying `MaliciousERC1155`, calling `initTransfer1155`, and asserting that 6 `InitTransfer` events are emitted while the bridge's ERC1155 balance remains 0.
