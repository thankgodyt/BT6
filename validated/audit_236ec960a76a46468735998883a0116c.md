### Title
Missing Cryptographic Ownership Verification in `validatePerasVote` Enables Peras Vote Impersonation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance defines a `PerasVote blk` type with **no signature field** and a `validatePerasVote` implementation that only checks whether the claimed `pvVoteVoterId` exists in the stake distribution. It performs no cryptographic proof that the sender actually controls the pool identity embedded in the vote. Any unprivileged peer can craft a `PerasVote` impersonating any registered stake pool, have it accepted by `processVotes`, and drive unauthorized Peras certificate generation and chain boosting.

---

### Finding Description

The `BlockSupportsPeras` typeclass instance in `SupportsPeras.hs` is the **only** instance in the codebase (confirmed: `grep "instance.*BlockSupportsPeras"` returns exactly two hits, both in this file). It defines:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- no signature field
  }
``` [1](#0-0) 

The corresponding validation function is:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

The check `lookupPerasVoteStake vote stakeDistr` resolves to a `Map.lookup` on `pvVoteVoterId`:

```haskell
lookupPerasVoteStake vote distr =
  Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)
``` [3](#0-2) 

There is no signature field in `PerasVote`, and no cryptographic check that the network peer submitting the vote actually controls the private key corresponding to `pvVoteVoterId`. The validation succeeds for any vote whose claimed voter ID appears in the stake distribution, regardless of who sent it.

This `validatePerasVote` is called directly in the production inbound-vote processing path:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [4](#0-3) 

This lambda is wired into both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`, which are the writers used by the object-diffusion mini-protocol to ingest votes received from peers. [5](#0-4) 

The `processVotes` function that drives this path rejects a batch only if `validatePerasVote` returns `Left`; otherwise every vote in the batch is timestamped and inserted into the DB: [6](#0-5) 

Once enough fake votes accumulate for the same target, `updatePerasRoundVoteStates` triggers `forgePerasCert`, which in the same degenerate instance also performs **no cryptographic verification** and unconditionally returns `Right`:

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can:

1. Craft `PerasVote` messages claiming to be any registered stake pool (any `pvVoteVoterId` present in the current stake distribution).
2. Send them via the object-diffusion mini-protocol. `processVotes` calls `validatePerasVote`, which accepts the vote because the claimed voter ID is in the stake distribution.
3. By sending enough such votes for the same `(pvVoteRound, pvVoteBlock)` target, the attacker drives the internal `updatePerasRoundVoteStates` logic past the quorum threshold.
4. A Peras certificate is forged and injected into the ChainDB, boosting an attacker-chosen block.
5. Chain selection is influenced by the boosted block, potentially causing honest nodes to prefer a non-canonical or adversarially chosen chain.

This is a **bypass of Peras voting and certificate checks** that enables unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical/High" impact scope.

---

### Likelihood Explanation

The attack requires only the ability to send well-formed `PerasVote` CBOR messages over the object-diffusion mini-protocol, which is accessible to any peer that can establish a node-to-node connection. No key material, stake, or privileged access is needed. The `PerasVote` type carries no signature field, so there is nothing to forge. The attacker only needs to know which pool IDs are in the current stake distribution (publicly available on-chain) and the current round number and target block hash (observable from the chain tip).

---

### Recommendation

1. Add a cryptographic signature field to `PerasVote blk` (analogous to the `VoteSignature` field in `EveryoneVotesVote` and `WFALSPersistentVote`).
2. In `validatePerasVote`, verify the signature against the public key associated with `pvVoteVoterId` in the stake distribution before accepting the vote, mirroring the pattern in `implVerifyVote` for `EveryoneVotes` and `WFALS`.
3. Similarly, implement real cryptographic verification in `validatePerasCert` rather than unconditionally returning `Right`.
4. Track and resolve issue `https://github.com/tweag/cardano-peras/issues/120` before any deployment of the Peras protocol extension.

---

### Proof of Concept

```
Attacker (any peer) connects via node-to-node object-diffusion protocol.

1. Observe current epoch stake distribution → collect all registered PoolIds.
2. Observe current chain tip → determine current PerasRoundNo and target block Point.
3. Craft N PerasVote messages:
     PerasVote { pvVoteRound = currentRound
               , pvVoteBlock = targetBlock
               , pvVoteVoterId = victimPoolId_i }   -- for i = 1..N
   No signature is required; the PerasVote type has no such field.
4. Send the batch to the target node via the object-diffusion mini-protocol.
5. processVotes calls validatePerasVote for each vote.
   validatePerasVote succeeds for each vote because victimPoolId_i ∈ stakeDistr.
6. Votes are inserted into PerasVoteDB.
7. updatePerasRoundVoteStates accumulates stake; once quorum is reached,
   forgePerasCert is called and a ValidatedPerasCert is produced.
8. The certificate boosts targetBlock in ChainDB, influencing chain selection
   on the honest node without any legitimate pool participation.
``` [8](#0-7) [9](#0-8)

```haskell
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
