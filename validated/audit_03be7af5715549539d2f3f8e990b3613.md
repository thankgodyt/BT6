Audit Report

## Title
Re-entrancy via Malicious ERC1155 Token Causes `currentOriginNonce` Collision, Enabling Unauthorized Minting on NEAR - (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary

`initTransfer1155` increments `currentOriginNonce` before the external `safeTransferFrom` call but reads the live storage value of `currentOriginNonce` in both `initTransferExtension` and the `emit` after the external call returns. A malicious ERC1155 token can re-enter `initTransfer1155` during `safeTransferFrom`, incrementing `currentOriginNonce` a second time, causing both the re-entrant and outer invocations to emit `InitTransfer` events with the same `origin_nonce`. NEAR processes the first (re-entrant, no tokens locked) event and mints tokens to the attacker, while the second event is rejected as a duplicate `TransferId`.

## Finding Description

In `initTransfer1155`, the nonce is incremented at line 448, but `initTransferExtension` (line 471) and `emit BridgeTypes.InitTransfer` (line 483) both read `currentOriginNonce` from live storage after the external call at line 458 returns:

```solidity
currentOriginNonce += 1;                          // L448: nonce = N+1
...
IERC1155(tokenAddress).safeTransferFrom(          // L458: external call — re-entrancy window
    msg.sender, address(this), tokenId, amount, ""
);
...
initTransferExtension(..., currentOriginNonce, ...); // L471: reads live storage
emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...); // L483: reads live storage
```

The same pattern exists in `initTransfer` for ERC20 tokens (lines 381, 418, 430).

**Attack trace:**

1. Attacker deploys a malicious ERC1155 whose `safeTransferFrom` re-enters `initTransfer1155` before returning.
2. Attacker calls `logMetadata1155` (permissionless) to register the token on NEAR.
3. Attacker calls `initTransfer1155(maliciousToken, ...)`:
   - `currentOriginNonce` → N+1
   - Bridge calls `maliciousToken.safeTransferFrom(attacker, bridge, ...)`
   - Malicious token re-enters `initTransfer1155`:
     - `currentOriginNonce` → N+2
     - Inner `safeTransferFrom` returns immediately (no tokens transferred)
     - Re-entrant call emits `InitTransfer` with `origin_nonce = N+2` — **no tokens locked**
   - Outer call resumes; `currentOriginNonce` is now N+2
   - Outer call emits `InitTransfer` with `origin_nonce = N+2` — **same nonce, no tokens locked**
4. Transaction log contains two `InitTransfer` events with `origin_nonce = N+2`; nonce N+1 is permanently skipped.
5. NEAR processes the first (re-entrant) event and mints tokens to the attacker.
6. NEAR rejects the second event via `add_fin_transfer` → `finalised_transfers.insert` returning false → `BridgeError::TransferAlreadyFinalised`.

**Why `onERC1155Received` does not prevent this:**

The `onERC1155Received` hook is declared `view` and checks `operator != address(this)`. However, the re-entrancy occurs inside the malicious token's `safeTransferFrom` body, *before* `onERC1155Received` is ever called. The malicious token controls its own `safeTransferFrom` implementation entirely and is not required to call `onERC1155Received` at all on the inner (re-entrant) call. The bridge does not verify that `onERC1155Received` was invoked. The `view` modifier is therefore irrelevant to the re-entrancy window.

**No reentrancy guard exists:** `OmniBridge.sol` imports no `ReentrancyGuard` and applies no `nonReentrant` modifier to `initTransfer` or `initTransfer1155`. The only reentrancy-related comment in the file is a Slither suppression on `deployToken` (line 161), unrelated to transfer functions.

This directly violates the stated invariant in `evm/CLAUDE.md`: *"Always mutate state (e.g. mark nonce used) before any external call"* — the nonce is incremented before the call, but the emitted value is read from live storage after the call, defeating the invariant's purpose.

## Impact Explanation

The NEAR `fin_transfer_callback` constructs a `TransferMessage` keyed by `origin_nonce` and calls `add_fin_transfer`, which inserts into `finalised_transfers` using `TransferId { origin_chain, origin_nonce }` as the unique key. When two `InitTransfer` events share the same `origin_nonce`, only the first is honored. Because the re-entrant event is emitted first in the transaction log and carries no actual EVM collateral, NEAR mints or releases bridged tokens to the attacker without any corresponding ERC1155 tokens being locked on EVM. This is unauthorized minting of bridged funds — a direct violation of the bridge's core accounting invariant and a match for the critical impact class: *"Balance manipulation, escrow mis-accounting… nonce/replay misuse… that changes user or protocol balances."*

## Likelihood Explanation

- `logMetadata1155` is explicitly permissionless; any address can register any ERC1155 token.
- No `nonReentrant` guard exists on `initTransfer1155` or `initTransfer`.
- ERC1155 tokens with arbitrary `safeTransferFrom` logic are a standard, well-understood attack surface.
- The attacker needs only to deploy one malicious contract and call two public functions. No privileged access, victim interaction, or external dependency is required.
- The attack is repeatable across any number of transactions.

## Recommendation

1. **Capture the nonce into a local variable before any external call** and use that local variable in `initTransferExtension` and `emit`:

```solidity
function initTransfer1155(...) external payable whenNotPaused(PAUSED_INIT_TRANSFER) {
    currentOriginNonce += 1;
    uint64 nonce = currentOriginNonce;  // capture before external call
    ...
    IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "");
    ...
    initTransferExtension(msg.sender, deterministicToken, nonce, ...);
    emit BridgeTypes.InitTransfer(msg.sender, deterministicToken, nonce, ...);
}
```

Apply the identical fix to `initTransfer` (replace `currentOriginNonce` with a captured local at lines 418 and 430).

2. **Add `ReentrancyGuard` (`nonReentrant` modifier)** to both `initTransfer` and `initTransfer1155` as defense-in-depth, consistent with the security invariant documented in `evm/CLAUDE.md`.

## Proof of Concept

Deploy the following malicious ERC1155 on a local fork, register it via `logMetadata1155`, then call `initTransfer1155`:

```solidity
contract MaliciousERC1155 {
    IOmniBridge bridge;
    bool reentered;

    constructor(address _bridge) { bridge = IOmniBridge(_bridge); }

    function safeTransferFrom(address, address, uint256 tokenId, uint256 amount, bytes calldata) external {
        if (!reentered) {
            reentered = true;
            // Re-enter: inner call increments nonce to N+2 and emits InitTransfer(N+2)
            bridge.initTransfer1155(address(this), tokenId, uint128(amount), 0, 0, "attacker.near", "");
            reentered = false;
        }
        // Neither call transfers tokens; bridge receives nothing
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
}
```

**Expected result:** Transaction emits two `InitTransfer` events both with `origin_nonce = N+2`. Nonce N+1 is skipped. NEAR relayer submits proof of the first event; `fin_transfer_callback` mints tokens to `attacker.near`. Submission of the second event fails with `TransferAlreadyFinalised`. Attacker retains ERC1155 tokens on EVM while receiving bridged value on NEAR.
