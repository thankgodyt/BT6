### Title
Whitelisted Receiver Without `msg_templates` Bypasses Post-Action Msg Validation, Allowing Attacker-Controlled `ft_transfer_call` Msg — (`contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

`check_deposit_msg` only validates a `PostAction.msg` against approved templates when `post_action_msg_templates` contains an entry for the receiver. When a receiver is on `post_action_receiver_id_white_list` but has **no** entry in `post_action_msg_templates`, the `if let Some(msg_templates)` branch is never entered and any arbitrary `msg` passes validation. Because the deposit address is derived from the `DepositMsg` hash, an attacker can encode a malicious `DepositMsg` in the BTC transaction's OP_RETURN, send BTC to the derived address, and have a trusted relayer faithfully relay it — causing `ft_transfer_call` to execute on the whitelisted receiver with an attacker-controlled `msg`.

---

### Finding Description

In `check_deposit_msg`, after confirming the receiver is on the whitelist, the msg template check is wrapped in an `if let Some(...)`:

```rust
if let Some(msg_templates) = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
{
    // validation only runs here
    let is_match = ...;
    if !is_match {
        return None;
    }
}
// falls through with arbitrary msg when templates == None
``` [1](#0-0) 

If `post_action_msg_templates.get(&receiver_id)` returns `None`, the entire validation block is skipped and execution falls through to `Some(post_actions)` at line 191. [2](#0-1) 

The two management operations that govern this state are independent: `extend_post_action_receiver_id_white_list` adds to the whitelist, and `extend_post_action_msg_templates` adds templates — there is no atomicity or enforcement that a whitelisted receiver must have templates. [3](#0-2) [4](#0-3) 

The deposit address is derived from the `DepositMsg` hash via `get_deposit_path`, and the contract enforces that the BTC transaction output's `script_pubkey` matches this derived address: [5](#0-4) 

This means the attacker controls the deposit address by controlling the `DepositMsg` (encoded in the BTC transaction's OP_RETURN). The trusted relayer reads the OP_RETURN and submits the exact `DepositMsg` to `verify_deposit_v2`. The relayer does not validate `post_action.msg` content — it faithfully relays whatever is in the BTC transaction. [6](#0-5) 

The validated (or in this case, unvalidated) `post_actions` are then passed through `internal_mint_promise` → `ext_nbtc::mint` → `ft_transfer_call` on the whitelisted receiver with the attacker-controlled `msg`. [7](#0-6) 

---

### Impact Explanation

The `ft_transfer_call` is executed on a DAO-whitelisted receiver contract with an attacker-controlled `msg`. The receiver's `ft_on_transfer` interprets this `msg` as instructions (e.g., swap parameters, withdrawal targets, routing data). Depending on the receiver contract's logic, this can trigger unintended operations such as misdirected token routing, locking of transferred nBTC, or other harmful state transitions in the receiver. This violates the invariant that post-action messages must conform to approved templates.

---

### Likelihood Explanation

The precondition — a receiver on the whitelist without templates — is a realistic operational state. A DAO operator adding a new integration may add the receiver to the whitelist in one transaction and intend to add templates later, or may deliberately omit templates believing the whitelist alone is sufficient protection. Once this state exists, the attack requires only sending real BTC (permissionless) to the address derived from a malicious `DepositMsg`. The trusted relayer will relay it without inspecting `post_action.msg` content.

---

### Recommendation

Enforce that a whitelisted receiver **must** have at least one template entry. Change the `if let Some(msg_templates)` branch to a hard requirement:

```rust
let msg_templates = self
    .data()
    .post_action_msg_templates
    .get(&post_action.receiver_id)
    .unwrap_or_else(|| {
        // emit event and return None
        Event::InvalidPostAction { ... }.emit();
        return None; // propagate via early return
    });
// then validate msg against msg_templates
```

Alternatively, treat `None` templates as "no msg allowed" (reject any non-empty msg) rather than "any msg allowed."

Also consider making `extend_post_action_receiver_id_white_list` require simultaneous template registration, or add a view-layer invariant check.

---

### Proof of Concept

1. DAO calls `extend_post_action_receiver_id_white_list(["defi.near"])` — no templates set for `defi.near`.
2. Attacker constructs:
   ```json
   {
     "recipient_id": "attacker.near",
     "post_actions": [{
       "receiver_id": "defi.near",
       "amount": "1000",
       "msg": "{\"action\":\"drain\",\"target\":\"attacker.near\"}"
     }]
   }
   ```
3. Attacker computes `sha256(json(deposit_msg))` → derives the BTC deposit address.
4. Attacker sends BTC to that address with the `DepositMsg` JSON in OP_RETURN.
5. Trusted relayer calls `verify_deposit_v2(deposit_msg, tx_bytes, vout, proof)`.
6. `check_deposit_msg` runs: receiver `defi.near` is on whitelist ✓; `post_action_msg_templates.get("defi.near")` → `None`; `if let Some(...)` branch not taken; returns `Some(post_actions)`.
7. `ft_transfer_call("defi.near", 1000, msg="{\"action\":\"drain\",...}")` executes.
8. `defi.near`'s `ft_on_transfer` receives the attacker-crafted `msg` and acts on it. [8](#0-7)

    pub fn extend_post_action_msg_templates(
        &mut self,
        contract_id: AccountId,
        templates: HashSet<String>,
    ) {
        assert_one_yocto();
        require!(!templates.is_empty(), "empty templates.");
        if let Some(msg_templates) = self
            .data_mut()
            .post_action_msg_templates
            .get_mut(&contract_id)
        {
            for template in templates {
                let is_success = msg_templates.insert(template.clone());
                require!(is_success, format!("{:?} is exist.", template));
            }
        } else {
            self.data_mut()
                .post_action_msg_templates
                .insert(contract_id, templates);
        }
    }
