### Title
`max_btc_gas_fee` Hard Cap Blocks User RBF During Bitcoin Fee Spikes, Permanently Locking In-Flight Withdrawal Funds Until Operator Intervention — (File: `contracts/satoshi-bridge/src/psbt.rs`)

### Summary

The bridge enforces a hard upper bound (`max_btc_gas_fee`) on the Bitcoin gas fee accepted in any withdrawal PSBT. This protective cap, intended to prevent fee-draining attacks, creates an exact analog to the OpenLeverage anti-flashloan issue: when Bitcoin network fees spike above the configured cap, any in-flight withdrawal whose transaction is stuck in the mempool cannot be accelerated via user-initiated RBF (`withdraw_rbf`). The user's nBTC remains locked inside the bridge contract until a privileged operator calls `cancel_withdraw`, which is the only path that bypasses the gas fee check.

### Finding Description

`check_withdraw_psbt` in `psbt.rs` enforces:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    format!(
        "Invalid gas fee ({}). valid range: [{}, {}].",
        gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
    )
);
``` [1](#0-0) 

This check is applied unconditionally to every withdrawal PSBT, including those submitted via `withdraw_rbf`. The public `withdraw_rbf` entry point in `api/bridge.rs` calls `withdraw_rbf_chain_specific`, which ultimately validates the new PSBT through the same pipeline. [2](#0-1) 

The only escape hatch that skips the gas fee check is `check_psbt_output_all_change_address` called with `is_cancel: true`:

```rust
if !is_cancel {
    require!(
        gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
        ...
    );
}
``` [3](#0-2) 

This bypass is only reachable through `cancel_withdraw`, which is restricted to `Role::DAO` or `Role::Operator`: [4](#0-3) 

The withdrawal lifecycle is:
1. User calls `ft_transfer_call` → nBTC is transferred to and held by the bridge.
2. Bridge constructs a Bitcoin transaction and requests MPC signature.
3. If the Bitcoin transaction is stuck (low fee), the user calls `withdraw_rbf` to bump the fee.
4. If the required fee now exceeds `max_btc_gas_fee`, `withdraw_rbf` reverts.
5. The user's nBTC remains locked in the bridge with no self-service recovery path. [5](#0-4) 

### Impact Explanation

When Bitcoin network fees spike above `max_btc_gas_fee` (a realistic market event during congestion), every in-flight withdrawal becomes permanently stuck from the user's perspective. The user cannot:
- Accelerate the transaction via `withdraw_rbf` (blocked by the cap).
- Self-cancel the withdrawal (only DAO/Operator can call `cancel_withdraw`).

The nBTC is held by the bridge contract and cannot be recovered without privileged operator action. This constitutes a **stuck bridge state requiring operator intervention**, matching the medium impact category.

### Likelihood Explanation

Bitcoin fee spikes above any static configured cap are a recurring, well-documented market event (e.g., Ordinals inscription waves, halving periods). The `max_btc_gas_fee` is a static config value set at deployment or by DAO update. Any withdrawal initiated just before a fee spike and not yet confirmed is immediately affected. No attacker action is required; the condition arises from normal market dynamics, exactly as in the OpenLeverage analog.

### Recommendation

Mirror the OpenLeverage judge's conclusion: instead of reverting when the fee exceeds the cap, use the cap as a soft policy for new withdrawals only. For in-flight RBF, allow the user to pay any fee up to the full value of their locked nBTC, or introduce a user-accessible emergency cancel path (analogous to `cancel_withdraw` but without the role restriction) that returns nBTC to the user when the withdrawal has been pending beyond `max_btc_tx_pending_sec`. [6](#0-5) 

### Proof of Concept

1. User initiates a withdrawal of 0.1 BTC, paying a gas fee of 5,000 sat (within `[min_btc_gas_fee, max_btc_gas_fee]`). nBTC is locked in the bridge.
2. Bitcoin network fees spike to 50,000 sat/tx due to congestion. The original transaction is stuck in the mempool.
3. User calls `withdraw_rbf` with a new PSBT specifying a 50,000 sat gas fee.
4. `check_withdraw_psbt` evaluates `gas_fee (50,000) <= config.max_btc_gas_fee (e.g., 20,000)` → `require!` panics with `"Invalid gas fee"`.
5. The RBF fails. The original low-fee transaction remains unconfirmed. The user's nBTC stays locked.
6. Only a DAO/Operator calling `cancel_withdraw` (which uses `is_cancel: true` to skip the fee check) can unblock the user. [7](#0-6)

    pub fn check_psbt_output_all_change_address(
        &self,
        psbt: &PsbtWrapper,
        vutxos: &[VUTXO],
        force_healthy_output: bool,
        is_cancel: bool,
    ) -> (u128, u128) {
        let config = self.internal_config();
        let withdraw_change_address_script_pubkey = config.get_change_script_pubkey();
        let input_amount = vutxos
            .iter()
            .map(|vutxo| u128::from(vutxo.get_amount()))
            .sum::<u128>();
        let output_amount = psbt
            .get_output()
            .iter()
            .map(|v| {
                if force_healthy_output {
                    require!(
                        v.value.to_sat() > config.unhealthy_utxo_amount
                            && u128::from(v.value.to_sat()) <= config.max_change_amount,
                        "The output amount is not in the valid range"
                    );
                } else {
                    require!(
                        u128::from(v.value.to_sat()) >= config.min_change_amount
                            && u128::from(v.value.to_sat()) <= config.max_change_amount,
                        "The output amount is not in the valid range"
                    );
                }
                require!(
                    v.script_pubkey == withdraw_change_address_script_pubkey,
                    "Invalid output script_pubkey"
                );
                u128::from(v.value.to_sat())
            })
            .sum::<u128>();
        let gas_fee = input_amount - output_amount;
        if !is_cancel {
            require!(
                gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
                format!(
                    "Invalid gas fee ({}). valid range: [{}, {}].",
                    gas_fee, config.min_btc_gas_fee, config.max_btc_gas_fee
                )
            );
        }
        (output_amount, gas_fee)
    }
