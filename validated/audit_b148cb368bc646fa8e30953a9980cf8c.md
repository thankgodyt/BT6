Now I have all the information needed. Let me analyze the critical pieces:

1. `DestinationChainMsg` enum has two variants: `MaxGasFee(U64)` and `DestHexMsg(Vec<u8>)`. Only `DestHexMsg` produces a non-empty `message` via `destination_msg()`.
2. The NEAR `sign_transfer` uses `DestinationChainMsg::from_json(&transfer_message.msg).and_then(|s| s.destination_msg()).unwrap_or_default()` — a generic string like `"some_dex_call"` fails JSON parsing and defaults to empty bytes.
3. The 3-arg `mint` in `HyperliquedBridgeToken` is confirmed to route all tokens to `_systemAddress`.
4. `OmniBridge.finTransfer` calls the 3-arg mint when `payload.message.length != 0`.

The PoC's specific example (`"msg": "some_dex_call"`) would NOT trigger the vulnerability because it fails `DestinationChainMsg` JSON parsing and defaults to empty `message`. However, the vulnerability IS real for users who use the `DestHexMsg` variant (`{"DestHexMsg": "<hex_bytes>"}`) — which is the correct, documented format for cross-chain message passing to destination chains.

Audit Report

## Title
`HyperliquedBridgeToken` 3-arg `mint` permanently routes bridged funds to `_systemAddress` when `DestHexMsg` is used for HyperEVM delivery — (`File: evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary
`HyperliquedBridgeToken.mint(address, uint256, bytes)` calls `_mint(account, value)` followed immediately by `_update(account, _systemAddress, value)`, leaving `account` with zero tokens and `_systemAddress` with the full amount. `OmniBridge.finTransfer` dispatches to this 3-arg override whenever `payload.message.length != 0`. The `message` field in the EVM payload is populated from the `DestHexMsg` variant of `DestinationChainMsg` in the user's NEAR-side `msg`. Any user who uses `{"DestHexMsg": "<hex_bytes>"}` when initiating a cross-chain transfer targeting HyperEVM will have their bridged tokens permanently deposited to `_systemAddress` instead of to themselves.

## Finding Description
**Root cause — `HlBridgeToken.sol` L76–83:**
```solidity
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value);  // net effect: account receives 0
}
```
The `_update` call immediately transfers the full `value` from `account` to `_systemAddress`, confirmed by the test suite (`HlBridgeToken.ts` L75–79: `balanceOf(user1) == 0`, `balanceOf(SYSTEM_ADDRESS) == 1000`).

**Dispatch path — `OmniBridge.sol` L337–349:**
```solidity
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount, payload.message);
    }
}
```
The 3-arg mint is selected whenever `payload.message` is non-empty.

**Message population — `near/omni-bridge/src/lib.rs` L487–489:**
```rust
let message = DestinationChainMsg::from_json(&transfer_message.msg)
    .and_then(|s| s.destination_msg())
    .unwrap_or_default();
```
`destination_msg()` returns `Some(bytes)` only for the `DestHexMsg(Vec<u8>)` variant (`near/omni-types/src/lib.rs` L931–937). A user who sets `msg = {"DestHexMsg": "deadbeef"}` produces a non-empty `message` in the signed EVM payload. `finTransfer` then calls `mint(payload.recipient, payload.amount, 0xdeadbeef)`, routing all tokens to `_systemAddress`.

**Registration path:** `HyperliquedBridgeToken` is registered via `addCustomToken` with `customMinter = address(0)` (`OmniBridge.sol` L94, `HlBridgeToken.ts` L64–65), placing it in the `isBridgeToken` branch with no `customMinters` override.

**Recovery is impossible:** `coreReceiveWithData` with `ACTION_TRANSFER` can release tokens from `_systemAddress`, but it is gated to `msg.sender == _systemAddress` (`HlBridgeToken.sol` L114) — a HyperCore system operation the user cannot invoke.

## Impact Explanation
**Critical — permanent loss of bridged funds.** The recipient receives 0 tokens. Tokens accumulate at `_systemAddress` with no user-accessible recovery path. This matches the allowed impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, … flows."*

## Likelihood Explanation
`DestHexMsg` is the protocol-defined mechanism for cross-chain message passing to destination chains (e.g., DeFi composability calls). A user who correctly uses `{"DestHexMsg": "<hex_bytes>"}` in their `InitTransferMsg.msg` when targeting HyperEVM triggers the loss. No special privileges, front-running, or external compromise is required — the relayer simply finalizes the MPC-signed transfer. Note: a generic non-JSON string (e.g., `"some_dex_call"`) fails `DestinationChainMsg` parsing and defaults to empty `message`, so only users using the `DestHexMsg` format are affected.

## Recommendation
The 3-arg `mint` override must not re-route tokens away from `account` for the `finTransfer` (HyperEVM delivery) path. Either:

1. Remove the `_update` call from the `IBridgeToken`-conforming `mint` overrides and introduce a dedicated `mintForHyperCore` function called only by `coreReceiveWithData`; or
2. Make the 3-arg `mint` behave identically to the 2-arg `mint` (mint directly to `account`), and handle HyperCore spot-balance accounting exclusively through `coreReceiveWithData`.

## Proof of Concept
1. User calls `ft_transfer_call` on NEAR targeting HyperEVM with `msg = {"DestHexMsg": "deadbeef"}` inside `InitTransferMsg`.
2. NEAR `sign_transfer` parses `DestHexMsg`, calls `destination_msg()` → `Some([0xde, 0xad, 0xbe, 0xef])`, populates `TransferMessagePayload.message = 0xdeadbeef` (non-empty).
3. MPC signs the payload; relayer calls `OmniBridge.finTransfer(signature, payload)` on HyperEVM.
4. `finTransfer` enters the `isBridgeToken` branch; `payload.message.length == 4 != 0`, so it calls `HyperliquedBridgeToken.mint(0xUSER, amount, 0xdeadbeef)`.
5. Inside `mint`: `_mint(0xUSER, amount)` → user balance = `amount`; `_update(0xUSER, _systemAddress, amount)` → user balance = 0, `_systemAddress` balance = `amount`.
6. `0xUSER` receives 0 tokens. Funds are permanently stranded at `_systemAddress`.

Reproducible as a Hardhat integration test by extending `HlBridgeToken.ts`: register the token on OmniBridge, call `finTransfer` with a non-empty `message` bytes field, and assert `balanceOf(recipient) == 0` and `balanceOf(SYSTEM_ADDRESS) == amount`. #[near(serializers=[json])]
```rust
#[derive(Debug, PartialEq)]
pub enum DestinationChainMsg {
    MaxGasFee(U64),
    DestHexMsg(#[serde_as(as = "Hex")] Vec<u8>),
}

impl DestinationChainMsg {
    pub fn max_gas_fee(&self) -> Option<U128> {
        if let Self::MaxGasFee(fee) = self {
            Some(U128(fee.0.into()))
        } else {
            None
        }
    }

    pub fn destination_msg(&self) -> Option<Vec<u8>> {
        if let Self::DestHexMsg(msg) = self {
            Some(msg.clone())
        } else {
            None
        }
    }

    pub fn from_json(s: &str) -> Option<Self> {
        serde_json::from_str(s).ok()
    }
```
