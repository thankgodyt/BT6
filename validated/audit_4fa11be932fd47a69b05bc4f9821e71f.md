Audit Report

## Title
Missing Destination Chain and Token Registration Check in `init_transfer` Causes Permanent Loss of Bridged Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts outbound bridge requests without verifying that the destination chain has a registered factory or that the token has a registered address mapping for that chain. For deployed (bridged) tokens, `burn_tokens_if_needed` is called with `.detach()` — a fire-and-forget burn — before any such validation can occur. The only completion path, `sign_transfer`, will always panic with `FailedToGetTokenAddress` for an unregistered destination, leaving burned tokens permanently destroyed and locked native tokens permanently frozen with no public recovery mechanism.

## Finding Description

`init_transfer` (L523–619) performs only one destination-chain guard:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

There is no check against `self.factories` (the authoritative registry of supported chains) and no check against `self.token_id_to_address` (the authoritative registry of token mappings per chain). Control passes to `init_transfer_internal` (L1829–1865), which:

1. Stores the transfer in `pending_transfers` via `add_transfer_message`.
2. Calls `burn_tokens_if_needed` (L1851) — for deployed tokens this dispatches a `.detach()` burn promise that executes independently of the rest of the call.
3. Calls `lock_tokens_if_needed` (L1853–1857) — for native tokens this locks funds inside the bridge.
4. Emits `InitTransferEvent`.

Later, when a relayer calls `sign_transfer` (L447), the first substantive operation is:

```rust
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

If the destination chain has no registered token mapping, this panics unconditionally. The transfer remains in `pending_transfers` forever; no public cancel or refund function exists to recover the burned or locked tokens.

The inbound path (`fin_transfer_callback`, L700–713) correctly enforces a factory check before processing, but no equivalent guard exists on the outbound `init_transfer` path.

## Impact Explanation

This directly matches the allowed critical impact: **permanent loss of bridged funds**.

- **Deployed (bridged) tokens** (e.g., bridged USDC): `burn_tokens_if_needed` destroys tokens via a detached promise. Because `sign_transfer` will always panic for an unregistered destination, the burned tokens are irrecoverably lost.
- **Native NEAR tokens**: tokens are locked inside the bridge via `lock_tokens_if_needed`. With no public cancel/refund function, they are permanently frozen.

## Likelihood Explanation

The entry point is fully unprivileged — any token holder can call `ft_transfer_call` on any NEP-141 token with the bridge as receiver. Realistic triggering scenarios that do not require victim mistakes:

1. **Partially deployed chain**: A new `ChainKind` variant (e.g., `Fogo`) is added to the enum before its factory and token mappings are registered. Any user bridging to that chain during the configuration window loses their tokens.
2. **Token not registered on target chain**: A token is registered for `Eth` but not for `Arb`. A user bridging to `Arb` loses their tokens — this is a normal operational state, not an unrealistic assumption.
3. **User chain mismatch**: A user specifies `Pol` instead of `Eth` for a token only registered on Ethereum. The contract accepts the transfer and burns the tokens.

All three scenarios are reachable through standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flows with no special privileges.

## Recommendation

Add factory and token address registration checks at the start of `init_transfer`, before any tokens are burned or locked:

```rust
fn init_transfer(...) {
    require!(
        init_transfer_msg.recipient.get_chain() != ChainKind::Near,
        BridgeError::InvalidRecipientChain.as_ref()
    );

    // Verify destination chain has a registered factory
    require!(
        self.factories.contains_key(&init_transfer_msg.get_destination_chain()),
        BridgeError::UnknownFactory.as_ref()
    );

    // Verify the token is registered for the destination chain
    require!(
        self.get_token_address(
            init_transfer_msg.get_destination_chain(),
            token_id.clone(),
        ).is_some(),
        BridgeError::FailedToGetTokenAddress.as_ref()
    );
    // ... rest of function
}
```

These checks mirror the guards already present on the inbound path in `fin_transfer_callback` and ensure a transfer can only be initiated when the destination chain and token are fully configured.

## Proof of Concept

1. Deploy the bridge with a factory registered only for `ChainKind::Eth`.
2. Register `usdc.near` with a mapping to `Eth:0xA0b86991...` only (no `Pol` mapping).
3. User holds 1000 bridged USDC (`usdc.near` is a deployed token, so `is_deployed_token` returns true).
4. User calls `ft_transfer_call` on `usdc.near`:
   ```json
   {
     "receiver_id": "omni.bridge.near",
     "amount": "1000",
     "msg": "{\"InitTransfer\":{\"recipient\":\"pol:0xUserAddress\",\"fee\":\"0\",\"native_token_fee\":\"0\"}}"
   }
   ```
5. `ft_on_transfer` → `init_transfer`: passes the only check (`Pol != Near`).
6. `init_transfer_internal` → `burn_tokens_if_needed`: 1000 USDC burned via `.detach()` promise (L1806–1812).
7. Transfer stored in `pending_transfers`; `InitTransferEvent` emitted.
8. Relayer calls `sign_transfer` → `get_token_address(ChainKind::Pol, usdc.near)` returns `None` → panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS` (L462–469).
9. Transfer remains in `pending_transfers` indefinitely; 1000 USDC are permanently destroyed.
