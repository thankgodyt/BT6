Audit Report

## Title
`NativeFeeRestricted` Role Bypass via Pre-Funded Message Storage Account — (File: near/omni-bridge/src/lib.rs)

## Summary
The `init_transfer` function enforces the `NativeFeeRestricted` role check only in Branch B of a two-branch `||` condition. Because Branch A (`try_to_transfer_balance_from_message_account(...).is_ok()`) contains no role check and the `message_storage_account_id` is deterministically computable before the call, an attacker holding `NativeFeeRestricted` can pre-fund that account via the public `storage_deposit` function, causing Branch A to return `Ok` and short-circuit the entire condition — bypassing the role restriction entirely and allowing a non-zero `native_token_fee` to be set on any outbound transfer.

## Finding Description
In `near/omni-bridge/src/lib.rs` at lines 566–581, `init_transfer` decides whether to proceed immediately via:

```rust
if self
    .try_to_transfer_balance_from_message_account(   // Branch A — no role check
        &message_storage_account_id,
        NearToken::from_yoctonear(init_transfer_msg.native_token_fee.0),
        &signer_id,
        required_storage_balance,
    )
    .is_ok()
    || (self.has_storage_balance(...)                 // Branch B — role check present
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

Branch B correctly gates on `NativeFeeRestricted`, but Branch A has no such guard. Due to short-circuit evaluation of `||`, a `true` result from Branch A causes Branch B — and its role check — to be skipped entirely.

`try_to_transfer_balance_from_message_account` (storage.rs lines 260–290) returns `Ok` when: (1) the message account exists in `accounts_balances`, (2) its total balance ≥ `native_fee`, and (3) after crediting the message account's balance to the signer's available balance, the combined amount ≥ `required_storage_balance + native_fee`. All three conditions are satisfiable by the attacker through a prior `storage_deposit` call.

The `message_storage_account_id` is computed at lines 562–563 as a SHA-256 hash of the borsh-serialized `TransferMessageStorageAccount` struct (which includes `token`, `amount`, `recipient`, `fee` — including `native_fee` — `sender`, and `msg`) plus an optional `external_id`. Nonces are excluded from the hash. Because all inputs are attacker-controlled and nonce-independent, the account ID is fully computable off-chain before `ft_transfer_call` is invoked.

`storage_deposit` is a public, permissionless function that accepts any `account_id`. An attacker can therefore register and fund the exact `message_storage_account_id` for their intended transfer before calling `ft_transfer_call`, guaranteeing Branch A succeeds.

## Impact Explanation
This is a concrete role bypass: an account explicitly granted `NativeFeeRestricted` — meaning the protocol has decided it must not set a non-zero `native_token_fee` — can circumvent that restriction entirely and attach an arbitrary native fee to any outbound bridge transfer. This matches the allowed critical impact class: "Unauthorized transaction, authorization bypass, role bypass… that lets an attacker execute bridge… actions." The `NativeFeeRestricted` access control is rendered completely ineffective against any account willing to pre-fund a storage account.

## Likelihood Explanation
The attacker population is exactly the set of accounts the DAO has explicitly restricted. The exploit requires only: (1) holding the `NativeFeeRestricted` role (already true by assumption), (2) computing the deterministic storage account ID off-chain (requires no privileged access, only knowledge of the transfer parameters), and (3) calling the public `storage_deposit` function with sufficient NEAR. No victim interaction, no front-running, no external oracle, and no privileged co-conspirator is required. The attack is repeatable for every transfer the attacker initiates.

## Recommendation
Add the `NativeFeeRestricted` role check to Branch A as well, so that a pre-funded message account cannot bypass the restriction:

```rust
if self
    .try_to_transfer_balance_from_message_account(...)
    .is_ok()
    && (init_transfer_msg.native_token_fee.0 == 0
        || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone()))
    || (self.has_storage_balance(...)
        && (init_transfer_msg.native_token_fee.0 == 0
            || !self.acl_has_role(Role::NativeFeeRestricted.into(), signer_id.clone())))
```

Alternatively, hoist the `NativeFeeRestricted` check to the very top of `init_transfer`, before any branching, so it cannot be bypassed by any storage path.

## Proof of Concept
1. DAO grants `NativeFeeRestricted` to `attacker.near`.
2. `attacker.near` selects transfer parameters: token, amount, recipient, `native_token_fee = 1_000_000_000_000_000_000_000_000` (1 NEAR), fee, msg.
3. `attacker.near` constructs `TransferMessageStorageAccount { token, amount, recipient, fee: Fee { fee, native_fee: 1 NEAR }, sender: attacker.near, msg }` and computes `sha256(borsh(struct))` to obtain `message_storage_account_id` — identical to what `calculate_storage_account_id` will produce at runtime (lines 562–563, 589–591 of lib.rs and omni-types/src/lib.rs).
4. `attacker.near` calls `storage_deposit` on the bridge contract with `account_id = message_storage_account_id`, depositing `required_storage_balance + 1 NEAR` to satisfy the checks in `try_to_transfer_balance_from_message_account` (storage.rs lines 272–284).
5. `attacker.near` calls `ft_transfer_call` on the token contract with the same transfer parameters.
6. Inside `init_transfer`, `try_to_transfer_balance_from_message_account` finds the pre-funded account, passes all balance checks, and returns `Ok`. Branch A is `true`; the `||` short-circuits; Branch B and its `acl_has_role` check are never evaluated.
7. `init_transfer_internal` is called with `native_token_fee = 1 NEAR` stored in the `TransferMessage`, despite `attacker.near` holding `NativeFeeRestricted`. The transfer is accepted and logged as a valid `InitTransferEvent`.
