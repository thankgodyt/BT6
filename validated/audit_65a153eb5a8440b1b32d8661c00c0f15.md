### Title
`safe_mint` Permanently Traps nBTC in Bridge's Own Token Balance When Recipient Is Unregistered - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nbtc contract unconditionally mints tokens into the bridge's own nbtc balance **before** verifying that the recipient has registered for token storage. When the recipient is unregistered, the function returns early with `U128(0)` but leaves the freshly minted tokens permanently stranded in the bridge's own nbtc account, with no on-chain recovery path available to any caller.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mint first** — `self.token.internal_deposit(&self.bridge_id, amount.into())` unconditionally credits `amount` nBTC to the bridge contract's own token balance.
2. **Check registration after** — `if self.token.accounts.get(&account_id).is_none()` tests whether the intended recipient is registered.
3. **Silent early return** — if the recipient is not registered, the function returns `PromiseOrValue::Value(U128(0))` without transferring or burning the already-minted tokens. [1](#0-0) 

The tokens now reside in the bridge contract's own nbtc balance. Examining every public function on the bridge contract that touches nbtc balances:

- `withdraw_protocol_fee` — withdraws only from `cur_available_protocol_fee`, a separately tracked counter, not from the bridge's raw token balance. [2](#0-1) 

- `claim_lost_found` — recovers only from the `lost_found` map, populated only on failed `internal_transfer_nbtc` callbacks. [3](#0-2) 

- `burn` in nbtc — withdraws from `bridge_id`'s balance, but is only invoked by the bridge during a verified withdrawal flow with a caller-specified `burn_amount`; there is no admin-callable standalone burn for excess balance. [4](#0-3) 

No function exists to burn, transfer, or otherwise recover nBTC tokens that accumulate in the bridge's own token balance through this path.

---

### Impact Explanation

When `safe_mint` returns `U128(0)` due to an unregistered recipient:

- `amount` nBTC tokens are minted and permanently locked in the bridge's own nbtc balance.
- The nBTC total supply is inflated above the amount of BTC actually backing it.
- If the bridge's deposit callback treats the `U128(0)` return as a failure and does **not** mark the UTXO as verified, the BTC deposit remains accessible for a refund — but the nBTC supply is already inflated with no way to deflate it.
- If the bridge's deposit callback treats it as success and **does** mark the UTXO as verified, the user loses their BTC with no nBTC received, and the tokens are permanently locked.

Either outcome constitutes a permanent loss of user or protocol funds and a broken supply invariant, matching:
> **Critical. Significant loss, theft, destruction, or permanent locking of user or protocol funds.**

---

### Likelihood Explanation

The `safe_deposit` flow (which calls `safe_mint`) is explicitly designed for integrations such as Omni Bridge where the recipient NEAR account may not have pre-registered for nBTC storage. [5](#0-4) 

Any deposit where the recipient's NEAR account lacks nBTC storage registration will trigger this path. This is a realistic, non-adversarial scenario for any new user interacting through a third-party integration.

---

### Recommendation

Reverse the order of operations in `safe_mint`: check whether the recipient is registered **before** minting tokens to `bridge_id`. If the recipient is not registered, either:

1. Panic immediately (preventing the mint entirely and allowing the bridge callback to revert the deposit cleanly), or
2. Mint and immediately burn the tokens if the subsequent transfer fails.

Additionally, add an admin-callable function on the bridge contract to burn any excess nBTC held in the bridge's own token balance, as a safety backstop.

---

### Proof of Concept

1. User deposits BTC to a bridge-derived address with a `safe_deposit` message targeting a NEAR account that has **not** registered for nBTC storage.
2. A relayer calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(..)`. [6](#0-5) 
3. The bridge verifies the deposit and calls `safe_mint(account_id, amount, msg)` on the nbtc contract.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `amount` nBTC is minted into the bridge's own token balance. [7](#0-6) 
5. `self.token.accounts.get(&account_id).is_none()` returns `true` (recipient not registered).
6. The function returns `PromiseOrValue::Value(U128(0))` — tokens remain in the bridge's nbtc balance. [8](#0-7) 
7. The bridge callback receives `0`. Regardless of whether it marks the UTXO as verified or not, `amount` nBTC tokens are permanently stranded in the bridge's own nbtc balance with no callable recovery path on either the nbtc or bridge contract.
