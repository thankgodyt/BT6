### Title
Missing Stake Normalization in Peras Quorum Check Enables Unauthorized Certificate Acceptance - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a relative quorum threshold (`3/4`) without normalizing the stake from absolute ledger units to a relative fraction. If the `PerasVoteStakeDistr` is populated with absolute lovelace values (as the ledger provides), any single vote from a pool with positive stake would immediately satisfy the quorum check, allowing unauthorized Peras certificate forging with a single vote.

### Finding Description

The `stakeAboveThreshold` function in `SupportsPeras.hs` performs a direct numeric comparison between the accumulated `PerasVoteStake` and the `perasQuorumStakeThreshold` parameter:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin = ...
```

The `perasQuorumStakeThreshold` is set to `3/4` (a relative fraction of total stake):

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
```

The code's own comment explicitly acknowledges the unit mismatch:

> "TODO: this function assumes that the 'PerasVoteStake' and the quorum threshold used in 'PerasParams' are expressed in the same units. That is, both are either absolute or relative (normalized) values. Under the current implementation of 'PerasParams', this function only makes sense when both values are relative (normalized) values, so we should either normalize the 'PerasVoteStake' before calling this function, or change this function to accept a stake distribution and perform the normalization internally."

The `validatePerasVote` default instance assigns the stake directly from the distribution without normalization:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
```

And `votesReachQuorum` sums these raw stakes and passes them directly to `stakeAboveThreshold`:

```haskell
totalVoteStake = mconcat (vpvVoteStake <$> votes)
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
```

The ledger provides stake in absolute lovelace units (e.g., `1_000_000_000_000 % 1`). When such a value is stored in `PerasVoteStakeDistr` and later compared to `3/4`, the condition `1_000_000_000_000 >= 3/4 + 2/100` is trivially `True`. A single vote from any pool with positive stake immediately satisfies quorum.

This is structurally identical to the Balancer H-5 bug: in Balancer, `primaryAmount` was scaled to 1e18 before being passed to `_getSpotPrice`, which then applied the scale factor again, inflating the value and corrupting the price check. Here, the ledger provides absolute stake, which is stored without normalization, and `stakeAboveThreshold` then compares it against a relative threshold — the wrong unit is used at the comparison step, corrupting the quorum check.

### Impact Explanation

If `PerasVoteStakeDistr` is populated with absolute lovelace values from the ledger (the natural source), then `stakeAboveThreshold` returns `True` for any single vote from a pool with positive stake. This means:

1. A single vote from any stake pool operator triggers quorum.
2. `votesReachQuorum` returns `Just` with a single vote, causing `forgePerasCert` to be called.
3. An unauthorized Peras certificate is forged and injected into the chain.
4. The certificate carries a `perasWeight` boost (default: 15 blocks), causing chain selection to prefer the boosted chain over honest chains.

This is a bypass of the Peras certificate quorum check, enabling unauthorized certificate acceptance and chain selection manipulation.

### Likelihood Explanation

The attack is reachable by any unprivileged peer that is a registered stake pool operator (a normal network participant). The attacker sends a single `PerasVote` message. The vote is processed by `processVotes` → `validatePerasVote` → `votesReachQuorum` → `stakeAboveThreshold`. No privileged keys, admin access, or stake majority is required. The only precondition is that the `PerasVoteStakeDistr` is populated with absolute ledger values, which is the natural production behavior since the ledger tracks stake in lovelace.

### Recommendation

Normalize `PerasVoteStake` to a relative fraction before calling `stakeAboveThreshold`. Either:

1. Divide each voter's absolute stake by the total active stake when populating `PerasVoteStakeDistr`, or
2. Change `stakeAboveThreshold` to accept the total active stake and perform normalization internally: `stake / totalActiveStake >= quorumThreshold + safetyMargin`.

The comment at line 155–161 already identifies this fix.

### Proof of Concept

Assume a pool with 1,000,000 lovelace absolute stake. The `PerasVoteStakeDistr` stores `PerasVoteStake (1000000 % 1)`. The pool sends one vote. `validatePerasVote` assigns `vpvVoteStake = PerasVoteStake (1000000 % 1)`. `votesReachQuorum` computes `totalVoteStake = PerasVoteStake (1000000 % 1)`. `stakeAboveThreshold` evaluates `1000000 >= 3/4 + 2/100 = 0.77` → `True`. A certificate is forged with a single vote, bypassing the intended 3/4 quorum requirement. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
