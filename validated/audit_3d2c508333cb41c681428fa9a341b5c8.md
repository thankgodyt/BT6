### Title
Anyone Can Redirect BTC Refunds to an Arbitrary Address When `deposit_msg.refund_address` Is Unset — (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary
`request_refund` in `satoshi-bridge` performs no caller-identity check and only validates `refund_address` against `deposit_msg.refund_address` when the latter is `Some`. When it is `None`, any unprivileged NEAR account can supply an attacker-controlled BTC address, causing the victim's deposited BTC to be sent to the attacker after the timelock.

### Finding Description
`internal_request_refund` guards `refund_address` only conditionally:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
// When deposit_msg.refund_address is None → any refund_address is accepted
``` [1](#0-0) 

There is no check that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` or any other ownership assertion. The supplied `refund_address` is stored verbatim in `RefundRequest`: [2](#0-1) 

`execute_refund` is also unrestricted — any caller may invoke it after the timelock — and it builds the refund PSBT using the stored `refund_address`: [3](#0-2) 

The victim's `deposit_msg` is publicly observable: `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`: [4](#0-3) 

The BTC transaction bytes and Merkle proof are public on the Bitcoin network.

### Impact Explanation
**Critical.** An attacker who observes a victim's `LogDepositAddress` event (where `deposit_msg.refund_address = None`) and the corresponding on-chain BTC deposit can call `request_refund` with their own BTC address as `refund_address`. After the timelock, `execute_refund` → MPC sign pipeline sends the victim's BTC to the attacker. The victim receives nothing. This is a direct, complete theft of deposited BTC.

### Likelihood Explanation
**Medium.** All required inputs are public: `deposit_msg` from NEAR events, `tx_bytes`/`vout`/Merkle proof from Bitcoin. The attacker must pay a NEAR storage deposit (anti-spam fee) and wait for the timelock. No privileged access is required. The attack is viable whenever a user deposits BTC without embedding a `refund_address` in their `deposit_msg` and `verify_deposit` is not called (relayer downtime, user changed mind, etc.).

### Recommendation
Require the caller to be the original depositor, or require `deposit_msg.refund_address` to always be set:

```rust
// Option A: bind refund_address to the caller
require!(
    env::predecessor_account_id().as_str() == deposit_msg.recipient_id.as_str()
        || deposit_msg.refund_address.as_deref() == Some(refund_address.as_str()),
    "Unauthorized: caller is not the depositor"
);

// Option B: always require refund_address in deposit_msg
require!(
    deposit_msg.refund_address.is_some(),
    "deposit_msg.refund_address must be set to use request_refund"
);
```

### Proof of Concept
1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, ... })`. The `LogDepositAddress` event is emitted with the full `deposit_msg`.
2. Alice sends BTC to the returned deposit address. `verify_deposit` is never called (relayer is down).
3. Attacker observes the NEAR event and the Bitcoin transaction. Attacker calls:
   ```
   request_refund(
       deposit_msg = alice_deposit_msg,   // from public event
       refund_address = "attacker_btc_addr",
       tx_bytes = <alice's BTC tx>,       // from Bitcoin
       vout = 0,
       proof = <merkle proof>,            // from Bitcoin
       gas_fee = None
   )
   ```
   The check at `refund.rs:154` is skipped because `deposit_msg.refund_address` is `None`. The `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`.
4. After `refund_timelock_sec` passes, attacker (or anyone) calls `execute_refund(utxo_storage_key)`.
5. The bridge builds a PSBT sending Alice's BTC to `"attacker_btc_addr"`, MPC signs it, and the transaction is broadcast. Alice's BTC is stolen. [5](#0-4)

    #[allow(clippy::too_many_arguments)]
    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
