### Title
Permissionless `request_refund` Allows Any Caller to Redirect Unprocessed Deposits to Attacker-Controlled BTC Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

The `request_refund` entry point is callable by any unprivileged NEAR account. When a deposit was made without a pre-authorized `refund_address` (i.e., `deposit_msg.refund_address = None`), any caller can submit a refund request for that UTXO and supply an **attacker-controlled** BTC address as the `refund_address`. The only protection is the `unsafe_refund_timelock_sec` window during which the DAO/Operator can reject the request. An attacker who floods the bridge with many such requests simultaneously can overwhelm the operator's review capacity, causing some requests to go unrejected and allowing the attacker to drain those deposits — a direct analog to the FaultDisputeGame resource-exhaustion attack.

---

### Finding Description

`request_refund` is a `#[payable]` function with no ownership check on the deposit UTXO: [1](#0-0) 

Inside `internal_request_refund`, the only caller-side validation is an attached-deposit check and a `tx_bytes` size cap: [2](#0-1) 

The callback `request_refund_callback` verifies that the supplied `deposit_msg` correctly derives the deposit address (i.e., the BTC output script matches), but it **never checks that the caller is the `recipient_id`** or any other owner of the deposit: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, the caller freely supplies any `refund_address`. The `unsafe_refund_timelock_sec` is then applied — described in the code comment as the "longer" timelock to give the DAO/Operator time to reject suspicious requests: [4](#0-3) 

After that timelock elapses, `execute_refund` is also permissionless — any account can call it: [5](#0-4) 

The resulting `BTCPendingInfo` is attributed to the executor (caller), not the original depositor, and the refund is sent to the `refund_address` stored in the `RefundRequest` — the attacker's address: [6](#0-5) 

All inputs required for the attack are publicly available:
- `deposit_msg` is emitted on-chain via `LogDepositAddress` when the user calls `get_user_deposit_address`
- The BTC transaction bytes and Merkle proof are public on the Bitcoin blockchain

---

### Impact Explanation

If the DAO/Operator fails to call `reject_refund` for even one attacker-submitted request before `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund`, the bridge's MPC service signs a PSBT paying the attacker's BTC address, and the victim's deposited BTC is permanently redirected. This constitutes **unauthorized claiming/release of BTC held by the bridge** — a critical bridge impact. [7](#0-6) 

---

### Likelihood Explanation

The analog to the FaultDisputeGame attack is direct: just as the attacker opens many subgames to exhaust the honest defender's funds, here the attacker submits many `request_refund` calls simultaneously — one per unprocessed deposit UTXO visible on-chain — each costing only 2 NEAR (non-refundable, ~$6): [8](#0-7) 

The DAO/Operator must manually review and call `reject_refund` for every suspicious request within the timelock window. With enough simultaneous requests, at least one will slip through. The attack is realistic because:
1. All `deposit_msg` values are public (emitted as NEAR events)
2. All BTC transaction data is public (Bitcoin blockchain)
3. No privileged access is required — any NEAR account can call `request_refund`
4. The 2 NEAR cost per request is negligible relative to BTC deposit values [9](#0-8) 

---

1. **Ownership check**: In `request_refund_callback`, verify that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`. This ensures only the intended recipient (or their delegate) can submit a refund request for a given deposit.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);

    pub fn required_balance_for_request_refund(&self) -> NearToken {
        // request_refund stores a RefundRequest holding the deposit tx_bytes verbatim, so
        // storage grows ~1:1 with tx size (measured: storage ≈ tx_bytes + ~442 bytes). A
        // normal deposit (1-2 inputs, ~500 bytes) costs ~0.005 NEAR, but tx_bytes is capped
        // at MAX_REQUEST_REFUND_TX_BYTES (200 KB) — at that worst case storage is ~2 NEAR.
        // We size the deposit to cover that worst case; for normal deposits the bulk of it
        // is an anti-spam fee on this permissionless entrypoint (the deposit is NOT refunded).
        // Refunds are a rare, abnormal event anyway.
        NearToken::from_near(2)
    }
