Audit Report

## Title
Fee Validation Uses Raw Amount While `sign_transfer` Enforces Normalized-Amount Floor, Enabling Permanent Fund Freezing — (File: `near/omni-bridge/src/lib.rs`)

## Summary
The `init_transfer` and `update_transfer_fee` functions validate the user-supplied fee against the raw token amount, but `sign_transfer` later enforces a stricter floor by normalizing `amount - fee` via floor division. For any token whose `origin_decimals > decimals`, a user can submit a transfer that passes the raw fee guard yet produces a normalized net amount of zero, causing every subsequent `sign_transfer` call to revert permanently with no on-chain recovery path.

## Finding Description
**Root cause — mismatched validation domains:**

`init_transfer` stores the transfer after a raw-unit check: [1](#0-0) 

`update_transfer_fee` applies the same raw-unit check: [2](#0-1) 

`sign_transfer` then normalizes the net amount using floor division before the `> 0` guard: [3](#0-2) 

`normalize_amount` performs integer floor division: [4](#0-3) 

`amount_without_fee` is a plain subtraction: [5](#0-4) 

**Exploit flow (concrete example):**
- Token registered with `origin_decimals = 24`, `decimals = 18` → normalization factor = 10^6.
- User calls `ft_transfer_call` with `amount = 5`, `fee = 4`.
- `init_transfer`: `4 < 5` passes; tokens are locked/burned; transfer stored.
- Relayer calls `sign_transfer`: `normalize_amount(5 - 4) = 1 / 10^6 = 0` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
- The same panic repeats on every subsequent `sign_transfer` call.

The same state is reachable via `update_transfer_fee`: a user raises their fee to `amount - 1` (passes the raw check), reducing the net amount below the normalization floor.

**No recovery path:** There is no public `cancel_transfer` function. `remove_transfer_message` is called only internally during successful finalization or fee-claim flows, neither of which can complete when `sign_transfer` always reverts. [6](#0-5) 

The code comment at `normalize_amount` acknowledges dust truncation but only addresses the case where dust is absorbed into the fee — it does not address the case where the entire net amount normalizes to zero: [7](#0-6) 

## Impact Explanation
Tokens consumed by `ft_on_transfer` (locked for native tokens, burned for deployed tokens) are permanently inaccessible. The transfer record exists on-chain but can never be finalized because `sign_transfer` will always revert. This constitutes **permanent freezing of bridged funds**, matching the Critical impact class: *"permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."*

## Likelihood Explanation
The condition requires a token with `origin_decimals > decimals` — common for tokens bridged from chains with 18+ decimals to a NEAR representation with fewer decimals — and a net amount after fee that falls below the normalization factor. A user who sets a fee close to the transfer amount, or who later raises the fee via `update_transfer_fee` to near the amount, can trigger this inadvertently. The `update_transfer_fee` path makes it reachable even for transfers that were initially valid. No privileged access is required; any token holder can trigger this through standard public contract calls.

## Recommendation
Add a normalized-amount check at both `init_transfer` and `update_transfer_fee` time. Before storing or updating the transfer message, verify:

```rust
require!(
    Self::normalize_amount(amount - fee, decimals) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This requires fetching `decimals` at `init_transfer` time (already available via `token_decimals`) and at `update_transfer_fee` time, mirroring the validation already performed in `sign_transfer`.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (factor = 10^6).
2. Call `ft_transfer_call` on that token with `amount = 5`, passing `InitTransferMsg { fee: 4, ... }`.
3. `init_transfer` stores the transfer: `4 < 5` passes; tokens are locked/burned.
4. Call `sign_transfer` for the resulting `transfer_id`.
5. `normalize_amount(5 - 4) = 1 / 1_000_000 = 0` → panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
6. Repeat step 4 indefinitely — it always fails. Tokens are permanently frozen.

Alternatively, via `update_transfer_fee`: start with a valid transfer (`amount = 2_000_000`, `fee = 0`), then call `update_transfer_fee` setting `fee = 1_999_999` (passes `fee < amount`), after which `normalize_amount(1) = 0` and `sign_transfer` always reverts.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.

    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
