### Title
Panic in `generate_public_key` via `request_refund_callback` When `chain_signatures_root_public_key` Is `None` - (`contracts/satoshi-bridge/src/kdf.rs`)

### Summary

`generate_public_key` unconditionally panics if `chain_signatures_root_public_key` is `None`. This field starts as `None` at deployment and is only populated after the DAO calls `sync_chain_signatures_root_public_key` and its callback succeeds. During that window, any caller can submit a valid `request_refund`, have `verify_transaction_inclusion` succeed, and then trigger a panic in `request_refund_callback` — consuming the attached storage deposit without storing a `RefundRequest`.

---

### Finding Description

**Initialization state.** The contract is deployed with `chain_signatures_root_public_key = None`: [1](#0-0) 

The field is only set inside `sync_root_public_key_callback`, which is triggered by the DAO-only `sync_chain_signatures_root_public_key`: [2](#0-1) 

**Panic site.** `generate_public_key` calls `.expect("Missing chain_signatures_root_public_key")` with no prior guard: [3](#0-2) 

**Reachable path.** `request_refund` is `#[payable]` and callable by any user (non-whitelisted callers are permitted with extra confirmations, not blocked): [4](#0-3) 

`internal_request_refund` fires `verify_transaction_inclusion_promise` and chains `request_refund_callback`: [5](#0-4) 

Inside `request_refund_callback`, after the light-client call succeeds, `generate_utxo_chain_address` is called — which calls `generate_btc_public_key` → `generate_public_key` → panic: [6](#0-5) 

---

### Impact Explanation

- The callback panics **after** `verify_transaction_inclusion` returns `true`, so the NEAR state changes in the callback are reverted — no `RefundRequest` is stored.
- The attached storage deposit (sized to cover ~2 NEAR per `required_balance_for_request_refund`) is **not refunded** on panic; it is consumed by the contract.
- The UTXO is **not permanently stuck**: once the DAO successfully runs `sync_chain_signatures_root_public_key`, the user can re-submit `request_refund` for the same UTXO (no `RefundRequest` entry exists to block it). The impact is therefore **storage deposit loss** and **temporary inaccessibility**, not permanent UTXO locking as the question claims.

The broken invariant — "a successful `verify_transaction_inclusion` must always result in a stored `RefundRequest` or a clean revert with deposit returned" — is violated, but the severity is **Low**, not Medium.

---

### Likelihood Explanation

The vulnerable window is the period between contract deployment and the first successful `sync_root_public_key_callback`. In practice this window is short (the DAO syncs the key immediately after deployment), but it is non-zero and exploitable by any user who submits a valid BTC proof during that window.

---

### Recommendation

Guard `request_refund_callback` (or `internal_request_refund`) with an early check:

```rust
require!(
    self.internal_config().chain_signatures_root_public_key.is_some(),
    "chain_signatures_root_public_key not yet initialized"
);
```

This converts the panic into a clean `require!` revert before the light-client cross-contract call is even dispatched, preserving the deposit and allowing the user to retry.

Alternatively, add the same guard inside `generate_public_key` itself so every call site is protected uniformly. [3](#0-2) 

---

            true
