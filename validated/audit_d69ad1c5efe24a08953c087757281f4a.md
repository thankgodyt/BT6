### Title
`safe_mint` Silently Mints nBTC to Bridge Account When Recipient Has No Storage — Tokens Permanently Unrecoverable - (File: contracts/nbtc/src/lib.rs)

---

### Summary

When `safe_mint` is called and the recipient account has no storage registered on the nBTC contract, nBTC tokens are minted into the bridge's own account (`bridge_id`) but never forwarded to the user. Because NEAR cross-contract state changes are committed asynchronously and the satoshi-bridge has no sweep/recovery function for its own nBTC balance, these tokens accumulate permanently with no on-chain path to retrieve them.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` unconditionally deposits `amount` nBTC into `bridge_id` before checking whether the recipient has storage:

```rust
self.token.internal_deposit(&self.bridge_id, amount.into());   // committed immediately

if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));                      // early return, no transfer
}
``` [1](#0-0) 

The `internal_deposit` call mutates the nBTC contract's state. In NEAR Protocol, cross-contract call state changes are committed per-receipt; a panic in the satoshi-bridge's subsequent callback **cannot roll back** the nBTC contract's ledger. The tokens are therefore permanently credited to `bridge_id` on the nBTC contract regardless of what the satoshi-bridge callback does.

The satoshi-bridge has three mechanisms for moving nBTC out of its own account:

1. `withdraw_protocol_fee` — only drains `cur_available_protocol_fee`, a separately tracked counter. [2](#0-1) 

2. `claim_lost_found` — only drains entries in the `lost_found` map, populated only by failed `internal_transfer_nbtc` callbacks. [3](#0-2) 

3. `internal_transfer_nbtc` — called only from specific deposit/withdraw/cancel flows; never from a general recovery path. [4](#0-3) 

None of these paths can reach nBTC that was silently minted to `bridge_id` by a failed `safe_mint`. There is no sweep, rescue, or admin-recovery function for the bridge's own nBTC balance. [5](#0-4) 

---

### Impact Explanation

Every `safe_deposit` flow where the recipient has no nBTC storage registered causes `amount` nBTC to be permanently stranded in the bridge's own token balance. The nBTC total supply is inflated by the stuck amount (the BTC backing remains in the UTXO pool, so the bridge is not insolvent, but the minted tokens are irrecoverable). This constitutes a **stuck bridge state requiring operator intervention** with no existing on-chain remedy — matching the Medium impact class: *broken callback rollback / stuck bridge state requiring operator intervention*.

---

### Likelihood Explanation

The `safe_deposit` path is the standard flow used by Omni Bridge integrations. Any user who deposits BTC with a `safe_deposit` message before registering storage on the nBTC contract triggers this path. Storage registration is a separate, optional step that users frequently omit. The entry point is fully public and requires no privilege.

---

### Recommendation

Move the storage check **before** `internal_deposit`, or replace the early-return with a `panic!`/`env::panic_str` so the entire receipt fails atomically and no tokens are minted:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient has no storage registered"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

Alternatively, add a privileged `recover_bridge_nbtc(amount, recipient)` function (analogous to the `sweep` function recommended in the AeraVault report) so the DAO can redistribute any nBTC that accumulates in the bridge's own balance.

---

### Proof of Concept

1. User registers a BTC deposit with `deposit_msg.safe_deposit = Some(..)` but does **not** call `storage_deposit` on the nBTC contract for their NEAR account.
2. Relayer submits `verify_deposit_v2`; the satoshi-bridge verifies the BTC inclusion proof and calls `safe_mint(user_account, amount, None)` on the nBTC contract.
3. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — nBTC is minted to the bridge. State is committed.
4. `self.token.accounts.get(&account_id).is_none()` is `true`; function returns `U128(0)`.
5. The satoshi-bridge callback receives `U128(0)`. Even if it panics, the nBTC contract's ledger is not rolled back.
6. `amount` nBTC now sits in the bridge's nBTC balance. No existing function in the satoshi-bridge can retrieve it. The tokens are permanently stuck. [6](#0-5) [7](#0-6)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn withdraw_protocol_fee(&mut self, amount: Option<U128>) -> Promise {
        assert_one_yocto();
        let total_protocol_fee = self.data().cur_available_protocol_fee;
        let amount = amount.map_or(total_protocol_fee, |v| v.0);
        require!(amount > 0 && amount <= total_protocol_fee, "Invalid amount");
        self.data_mut().cur_available_protocol_fee -= amount;
        self.data_mut().acc_claimed_protocol_fee += amount;
        self.internal_withdraw_protocol_fee(amount)
    }
