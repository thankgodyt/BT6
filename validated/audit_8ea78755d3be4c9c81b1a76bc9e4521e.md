### Title
Peras Certificate Validation Stub Always Accepts Any Peer-Supplied Certificate, Enabling Chain-Selection Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right` — accepting every inbound Peras certificate without performing any cryptographic or semantic check. This is the direct analog of the external report's pattern: a required validation check is absent from the function that is actually called on peer-supplied data. Because `processCerts` in the ObjectDiffusion layer calls this stub to gate certificate admission into the `PerasCertDB` / `ChainDB`, any unprivileged peer can inject arbitrary certificates that receive a chain-selection boost weight, potentially causing honest nodes to prefer a non-canonical chain.

---

### Finding Description

**Root cause — stub always returns `Right`:**

The universal instance is explicitly labelled a "degenerate instance for all blks to get things to compile":

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

Every field of the certificate — round number, boosted-block point, cryptographic proof — is ignored. The function unconditionally wraps the raw peer-supplied `PerasCert` in a `ValidatedPerasCert` and assigns it the full `perasWeight` boost.

**Call site — inbound certificate pipeline:**

`processCerts` in the ObjectDiffusion layer is the function that handles batches of certificates received from remote peers. It calls the validation function before storing each certificate:

```haskell
makePerasCertPoolWriterFromCertDB systemTime perasCertDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (PerasCertDB.getCertIds perasCertDB)
          (validatePerasCert mkPerasParams)   -- ← stub called here
          (void . join . atomically . PerasCertDB.addCert perasCertDB)
          certs
    ...
    }
``` [2](#0-1) 

The same stub is used in the `ChainDB`-backed writer: [3](#0-2) 

`processCerts` partitions results into `(errs, validatedCerts)` and only rejects a batch when `errs` is non-empty. Because `validatePerasCert` never produces an error, `errs` is always `[]` and every certificate is stored: [4](#0-3) 

**Secondary issue — `validatePerasVote` omits signature verification:**

`validatePerasVote` only checks that the voter ID appears in the stake distribution; it does not verify the vote's cryptographic signature. An attacker who knows any eligible voter ID (public information from the ledger) can forge votes for that voter:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [5](#0-4) 

This is used in both the `PerasVoteDB`-backed and `ChainDB`-backed vote writers: [6](#0-5) [7](#0-6)

### Impact Explanation

Peras certificates carry a `vpcCertBoost` weight that is added to the chain-selection score of the boosted block. Because `validatePerasCert` always returns `Right` and assigns the full `perasWeight` boost to every certificate, an unprivileged peer can:

1. Craft a `PerasCert` pointing to any block on any fork.
2. Send it via the ObjectDiffusion mini-protocol.
3. Have it stored in the `PerasCertDB` / `ChainDB` with full boost weight.
4. Cause honest nodes to prefer the adversary's fork over the canonical chain.

This is a **Critical** bypass of Peras certificate verification that enables unauthorized certificate acceptance and chain-selection manipulation by an unprivileged peer. The secondary `validatePerasVote` issue enables forged votes from any known eligible voter ID, allowing an attacker to manufacture quorum and trigger spurious certificate generation internally. [8](#0-7) 

---

### Likelihood Explanation

The ObjectDiffusion mini-protocol is a standard peer-to-peer channel reachable by any node on the network without authentication. The `processCerts` and `processVotes` entry points are called directly on data received from remote peers. No privilege, key material, or stake is required — any peer can send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` and `pcCertRound`. The stub is the active production code path for all block types via the universal instance.

---

### Recommendation

- **Short term:** Replace the stub `validatePerasCert` implementation with a real check that verifies at minimum: (a) the certificate's round number is within the expected range, (b) the boosted block point is a known block on the chain, and (c) the aggregate cryptographic proof over the committee's votes is valid. Until real validation is implemented, the ObjectDiffusion certificate ingestion path should be disabled or gated behind a feature flag.
- **Short term (votes):** `validatePerasVote` must verify the cryptographic signature of the vote against the voter's registered verification key, not merely check stake-distribution membership.
- **Long term:** Resolve [issue #120](https://github.com/tweag/cardano-peras/issues/120) before enabling the Peras ObjectDiffusion mini-protocol on any network where chain-selection integrity is required.

---

### Proof of Concept

1. Connect to a node running this code as an unprivileged peer via the ObjectDiffusion mini-protocol.
2. Send a `PerasCert` message with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversary's fork tip>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}` unconditionally.
4. The certificate is stored in the `PerasCertDB` / `ChainDB` with full boost weight.
5. Chain selection now scores the adversary's fork higher by `perasWeight` than the canonical chain, causing the honest node to switch to the adversary's fork. [9](#0-8)

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
