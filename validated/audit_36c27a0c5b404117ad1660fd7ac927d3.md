### Title
Tokens Permanently Locked in Bridge When `safe_mint` Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract mints tokens to the bridge's own account **before** verifying that the intended recipient account is registered. If the recipient is not registered, the function silently returns `U128(0)` with no transfer, no recovery entry, and no revert — leaving the minted nBTC permanently stranded in the bridge's token balance while the corresponding BTC remains locked in the bridge. This is a direct analog to the MobileCoin report's "type mismatch" class: an intermediate aggregation step (minting to bridge) is committed before the final delivery step is validated, and when delivery fails the intermediate state is never unwound.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124):

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← (1) tokens minted to bridge

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← (2) silent early return, no transfer
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

**Step (1)** unconditionally calls `internal_deposit(&self.bridge_id, amount)`, which increases the bridge's token balance and the total supply.

**Step (2)** checks whether `account_id` is registered. If it is not, the function returns `U128(0)` immediately. No `ft_transfer` is attempted, no `lost_found` entry is written (compare `transfer_nbtc_callback` in `token_transfer.rs` lines 62–68, which does write a `lost_found` entry — but that path is never reached here), and no revert of the `internal_deposit` occurs.

The contrast with `mint` (lines 126–148) is instructive: `mint` calls `mint_inner`, which auto-registers the account before depositing:

```rust
fn mint_inner(&mut self, account_id: &AccountId, amount: U128) {
    if self.token.accounts.get(account_id).is_none() {
        self.token.internal_register_account(account_id);   // ← auto-registers
    }
    self.token.internal_deposit(account_id, amount.into()); // ← deposits directly to recipient
    ...
}
```

`safe_mint` was introduced to avoid auto-registration (a storage-cost concern), but the implementation mints to the bridge first and then checks registration — the wrong order. The correct order is to check registration first and only mint if delivery is possible. [1](#0-0) [2](#0-1) [3](#0-2) 

---

### Impact Explanation

When `safe_mint` is invoked by the bridge for a recipient whose NEAR account is not registered in the nBTC contract:

- `internal_deposit(&self.bridge_id, amount)` permanently increases the bridge's nBTC balance and the total supply.
- The function returns `U128(0)` — the recipient receives nothing.
- No `lost_found` record is created for the recipient.
- No mechanism exists in the bridge or nBTC contract to detect or recover these stranded tokens.
- The BTC that was deposited on-chain to trigger this mint remains locked in the bridge's UTXO set.

Result: the user's BTC is permanently locked and the corresponding nBTC is permanently stranded in the bridge's own token balance, inflating the bridge's balance above what is legitimately owed to it. This is **permanent locking of user funds** — a Critical impact under the allowed scope. [4](#0-3) 

---

### Likelihood Explanation

Any user who:
1. Sends BTC to their bridge deposit address, and
2. Has not previously called `storage_deposit` on the nBTC contract to register their NEAR account,

will trigger this path when the relayer submits the deposit proof and the bridge calls `safe_mint`. New users who are unfamiliar with the NEP-141 storage registration requirement are the natural victim class. No privileged access, no leaked keys, and no malicious operator behavior is required — only a standard deposit by an unregistered account. [5](#0-4) 

---

### Recommendation

Reorder the registration check to occur **before** `internal_deposit`. If the account is not registered, return early without minting:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "safe_mint: account_id must not be the bridge");

    // Check BEFORE minting — if unregistered, no tokens are created and no funds are lost.
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

Additionally, the bridge's deposit callback should handle a `U128(0)` return from `safe_mint` by writing a `lost_found` entry or emitting a recoverable event so operators can detect and remediate affected deposits. [1](#0-0)

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address (derived from her NEAR account `alice.near` and a `DepositMsg`).
2. Alice has **never** called `storage_deposit` on the nBTC contract, so `alice.near` is not in `token.accounts`.
3. A relayer submits the `TxInclusionProof` to the bridge's deposit endpoint.
4. The bridge verifies the proof and calls `safe_mint(alice.near, 1_000_000, None)` on the nBTC contract.
5. Inside `safe_mint`:
   - Line 112: `internal_deposit(&self.bridge_id, 1_000_000)` — bridge's nBTC balance increases by 1,000,000 satoshis; total supply increases.
   - Line 114: `self.token.accounts.get(&alice.near)` returns `None`.
   - Line 115: function returns `U128(0)`.
6. Alice receives 0 nBTC. Her BTC is locked in the bridge's UTXO set. The bridge's nBTC balance is inflated by 1,000,000 satoshis with no corresponding user entitlement. No `lost_found` entry exists for Alice. No recovery path exists. [4](#0-3) [6](#0-5)

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
