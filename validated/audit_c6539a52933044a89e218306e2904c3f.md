### Title
Refund Timelock Resolved from Live Config at Execution Time, Not at Request Time — (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`resolve_execute_refund_timelock` reads `unsafe_refund_timelock_sec` and `refund_timelock_sec` from the **current** contract config at the moment `execute_refund` is called, not from the config that was in effect when `request_refund` was submitted. Because users have no mechanism to cancel their own pending refund requests, a DAO `update_config` call that increases either timelock retroactively extends the lock on already-pending BTC/ZEC refunds, leaving depositors unable to recover their funds for an indefinitely extended period. Conversely, a DAO decrease of `unsafe_refund_timelock_sec` allows a pending "unsafe" refund (one whose address was supplied by the caller, not pre-authorized) to be executed before the DAO/Operator has had time to review and reject it.

### Finding Description

When `request_refund` succeeds, a `RefundRequest` is stored with `created_at_sec` capturing the submission timestamp:

```rust
// contracts/satoshi-bridge/src/refund.rs  line 572
created_at_sec: nano_to_sec(env::block_timestamp()),
```

The timelock that must elapse before `execute_refund` can proceed is **not** stored in the `RefundRequest`. Instead, `execute_refund` calls `resolve_execute_refund_timelock`, which fetches the timelock from the live config:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 215-227
let config = self.internal_config();
if refund_request.deposit_msg().refund_address.is_some() {
    if is_privileged { 0 } else { config.refund_timelock_sec }
} else {
    config.unsafe_refund_timelock_sec   // ← live value, not request-time value
}
```

The DAO can update both fields at any time via `update_config` / `ConfigUpdate::apply`, which only enforces `refund_timelock_sec <= unsafe_refund_timelock_sec` — it places no upper bound on either value and has no awareness of pending refund requests:

```rust
// contracts/satoshi-bridge/src/config.rs  lines 154-157
require!(
    self.refund_timelock_sec <= self.unsafe_refund_timelock_sec,
    "refund_timelock_sec must be <= unsafe_refund_timelock_sec"
);
```

The defaults are `DEFAULT_REFUND_TIMELOCK_SEC = 2 days` and `DEFAULT_UNSAFE_REFUND_TIMELOCK_SEC = 14 days`.

A user who submitted a refund request under the 14-day `unsafe_refund_timelock_sec` has **no way to cancel** that request. `reject_refund` is gated to DAO/Operator or to the case where the UTXO was already finalized via deposit:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  lines 564-567
require!(
    is_privileged || is_already_deposited,
    "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
);
```

There is no user-facing cancel path.

### Impact Explanation

**Scenario A — DAO increases `unsafe_refund_timelock_sec`:**  
A user who submitted `request_refund` expecting a 14-day wait now faces an arbitrarily longer wait (e.g., 60 days). Their BTC/ZEC remains locked in the bridge-controlled UTXO set for the extended period with no recourse. This constitutes attacker-triggered (or governance-triggered) temporary locking of bridged funds.

**Scenario B — DAO decreases `unsafe_refund_timelock_sec`:**  
A third party who submitted a `request_refund` with a caller-supplied `refund_address` (the "unsafe" path, where `deposit_msg.refund_address` was `None`) can execute the refund before the DAO/Operator has had time to review and reject it. Because any party who knows the original `deposit_msg` can submit a refund request pointing to their own address, this can redirect a depositor's BTC/ZEC to an attacker-controlled address if the DAO reduces the timelock while such a request is pending.

Both scenarios match the allowed Medium impact: **"Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds."**

### Likelihood Explanation

The DAO legitimately adjusts `unsafe_refund_timelock_sec` as operational needs evolve (e.g., increasing it to give more review time, or decreasing it to speed up legitimate refunds). Neither action requires malicious intent. Because the timelock is not snapshotted at request time, any such adjustment silently retroacts on all pending refund requests. The absence of a user cancel path means the user has no defensive option once the config changes.

### Recommendation

1. **Snapshot the timelock at request time.** Add a `timelock_sec: u64` field to `RefundRequest` (and `RefundRequestV0` migration path), populated in `request_refund_callback` from the config at that moment. `load_refund_request_for_execute` should use the stored value instead of `config.unsafe_refund_timelock_sec`.

2. **Allow users to cancel their own refund requests.** Add a permissionless `cancel_refund` that lets the original submitter withdraw their storage deposit and remove the request, analogous to the bidder-cancel recommendation in the NibblVault report.

3. **Alternatively**, enforce that `update_config` cannot reduce `unsafe_refund_timelock_sec` below the maximum `created_at_sec` of any currently pending refund request, preventing retroactive shortening.

### Proof of Concept

**Scenario A (retroactive extension):**

1. User calls `request_refund` with `deposit_msg.refund_address = None`. Config has `unsafe_refund_timelock_sec = 14 days`. `RefundRequest.created_at_sec` is recorded.
2. DAO calls `update_config` with `unsafe_refund_timelock_sec = 60 days` for operational reasons.
3. User calls `execute_refund` after 14 days. `resolve_execute_refund_timelock` reads the live config: `60 days`. The check `now >= created_at_sec + 60 days` fails. Execution reverts.
4. User has no cancel path (`reject_refund` requires DAO/Operator). BTC remains locked for 46 additional days beyond the user's expectation.

**Scenario B (retroactive shortening enabling premature execution):**

1. Attacker knows the `deposit_msg` (public on-chain) for a deposit whose `refund_address` was `None` and which was never finalized. Attacker calls `request_refund` supplying their own `refund_address`. Config has `unsafe_refund_timelock_sec = 14 days`.
2. DAO calls `update_config` with `unsafe_refund_timelock_sec = 1 day` to speed up legitimate refunds.
3. After 1 day, attacker calls `execute_refund`. `resolve_execute_refund_timelock` reads the live config: `1 day`. The timelock check passes. The refund PSBT is built sending the original depositor's BTC to the attacker's address.
4. The DAO had no opportunity to call `reject_refund` within 1 day. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

```rust
    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
```

```rust
    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
