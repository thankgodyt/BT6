### Title
Silent Panic in Detached `handle_post_action` Receipt When Depositor Drains Balance Before Execution — (`contracts/nbtc/src/lib.rs`)

---

### Summary

`mint()` mints tokens to `mint_account_id` and then schedules `handle_post_actions` via a detached promise. Because NEAR receipts execute asynchronously across blocks, the depositor can call `ft_transfer` between the `mint` receipt and the `handle_post_action` receipt. When `handle_post_action` then calls `internal_transfer` on an account with insufficient balance, it panics. Because every promise in this chain is detached, the panic is a silent receipt failure: no `FtTransfer` event is emitted, no recovery path exists, and the bridge has no on-chain evidence the post_action was ever attempted.

---

### Finding Description

**Execution path:**

`mint()` (line 136) calls `mint_inner(&mint_account_id, mint_amount)`, crediting tokens to the depositor in the same receipt. It then schedules the post-action chain with `.detach()`: [1](#0-0) 

`handle_post_actions` iterates over each `PostAction` and again calls `.detach()` for every individual action: [2](#0-1) 

`handle_post_action` then calls `internal_transfer` unconditionally, with no balance pre-check: [3](#0-2) 

**The race window:**

In NEAR, a detached promise creates a new receipt that is enqueued for a future block. Between the `mint` receipt (which credits the depositor) and the `handle_post_action` receipt (which tries to debit the depositor), any number of other transactions can execute. The depositor can legitimately call `ft_transfer` during this window, reducing their balance below `post_action.amount`. When `handle_post_action` executes, `internal_transfer` panics with an insufficient-balance error. Because the promise is detached, the panic is a silent receipt failure — no callback observes it, no state is updated, and no event is emitted.

**No recovery mechanism exists.** The bridge has no callback on the `handle_post_actions` or `handle_post_action` receipts, so it cannot detect the failure, re-queue the action, or refund the depositor.

---

### Impact Explanation

- The post_action amount is neither delivered to `receiver_id` nor returned to `sender_id`.
- No `FtTransfer` event is emitted for the post_action amount.
- The bridge has no on-chain evidence the post_action was attempted or failed.
- The depositor's intended DeFi action is permanently and silently lost.
- The invariant that a scheduled post_action either completes or fails with observable recovery is broken.

This matches the **Low** allowed impact: publicly reachable invariant-violation / panic-driven fault in a production bridge/token path without direct theft.

---

### Likelihood Explanation

The race window is real and reachable by any unprivileged depositor. It requires only a standard `ft_transfer` call between two NEAR receipts — a normal user action. It can also occur accidentally (e.g., a wallet or DeFi protocol auto-moving tokens). No privileged access is required.

---

### Recommendation

1. **Pre-check balance before scheduling.** In `handle_post_action`, verify `sender_id` has at least `amount` before calling `internal_transfer`, and emit a failure event if not.
2. **Add a callback on the detached chain.** Replace `.detach()` with a `.then(Self::ext(...).handle_post_action_callback(...))` that handles failure by emitting an event and/or crediting a lost-found ledger (similar to the pattern already used in `transfer_nbtc_callback` in `contracts/satoshi-bridge/src/token_transfer.rs`).
3. **Alternatively, lock the post_action amount at mint time** by transferring it to an escrow sub-account or holding it in the bridge account before scheduling the detached receipt, so the depositor cannot drain it.

---

### Proof of Concept

```
1. Bridge calls: nbtc.mint(
       mint_account_id = "alice",
       mint_amount     = 1_000_000,
       post_actions    = [{ receiver_id: "defi", amount: 1_000_000, msg: "...", ... }]
   )
   → Receipt A executes: alice's balance = 1_000_000
   → Receipt B (handle_post_actions) is enqueued, detached

2. Before Receipt B executes, alice calls:
   nbtc.ft_transfer(receiver_id = "bob", amount = 1_000_000)
   → alice's balance = 0

3. Receipt B executes handle_post_action(alice, defi, 1_000_000, ...):
   → internal_transfer("alice", "defi", 1_000_000) panics: insufficient balance
   → Receipt B fails silently (detached, no callback)
   → No FtTransfer event emitted
   → No recovery, no on-chain evidence
```

Assert: after step 3, `ft_balance_of("defi") == 0`, no `FtTransfer` log exists for the post_action amount, and the bridge state is unchanged.
