### Title
ChainSync Client `checkPreferTheirsOverOurs` Ignores Peras Weight Snapshot, Causing Incorrect Chain Selection Decisions - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the production ChainSync client hardcodes `emptyPerasWeightSnapshot` instead of using the actual Peras weight snapshot when comparing a candidate chain against the current selection. This is the direct analog of the external report: a parameter that should constrain behavior (the Peras weight snapshot) is silently ignored, causing the comparison to use only block count rather than total Peras weight. When Peras is active, this produces incorrect peer-management decisions that can cause a node to disconnect from peers offering the canonical (Peras-boosted) chain, or to continue following a non-canonical chain that is heavier only by block count.

---

### Finding Description

When a header received from a peer is beyond the forecast horizon, the ChainSync client cannot yet validate it. It calls `checkPreferTheirsOverOurs` to decide whether to keep waiting (if the candidate is still preferred over our selection) or to disconnect from the peer with `CandidateTooSparse` (if the candidate is no longer preferred).

The function calls `preferAnchoredCandidate` with `emptyPerasWeightSnapshot` hardcoded as the weight argument:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty, ignores real Peras weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $ CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` is designed to accept a `PerasWeightSnapshot blk` and, when it is non-empty, computes total weight (block count + Peras boost) over the suffix after the intersection point:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- falls back to pure block-count comparison
      ...
  | otherwise =
      -- uses weightedSelectView, accounting for Peras boosts
      case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                               (weightedSelectView cfg weights candSuffix) of ...
``` [2](#0-1) 

Because `emptyPerasWeightSnapshot` is always passed, `isEmptyPerasWeightSnapshot weights` is always `True`, and the function always falls back to pure block-count comparison — exactly as if Peras did not exist. The actual Peras weight snapshot is available at the call site (the `NodeKernel` reads it via `ChainDB.getPerasWeightSnapshot` and passes it to `preferAnchoredCandidate` everywhere else), but it is never threaded into `checkPreferTheirsOverOurs`. [3](#0-2) 

The `WeightedSelectView` and `wsvTotalWeight` show that total weight is `BlockNo + PerasWeightBoost`, so a chain with fewer blocks but large Peras boosts can be heavier: [4](#0-3)

### Impact Explanation

When Peras is active, two incorrect outcomes arise from ignoring the weight snapshot:

**Case A — False disconnect (chain selection error):** The canonical chain has received Peras certificate boosts, making it heavier than its block count alone. A peer offers this chain, but its tip has fewer blocks than our current selection. `checkPreferTheirsOverOurs` sees only block count, concludes the candidate is not preferred, and disconnects with `CandidateTooSparse`. The node permanently loses the connection to the peer offering the canonical chain and may never adopt it. This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical chain.

**Case B — False continuation:** Our current chain has Peras boosts; a peer offers a chain that is longer by block count but lighter in total weight. `checkPreferTheirsOverOurs` sees the candidate as preferred (more blocks) and does not disconnect. The node continues following a chain it will ultimately not adopt, wasting resources and potentially delaying convergence.

Case A is the security-critical path. It allows an unprivileged peer (or network partition) to cause an honest node to diverge from the canonical Peras-boosted chain.

---

### Likelihood Explanation

- **Requires Peras to be enabled.** Peras is currently disabled by default (`emptyPerasWeightSnapshot` is the default everywhere). Once Peras is enabled in production, this code path becomes live.
- **Triggered by any peer.** Any upstream peer can send a header beyond the forecast horizon; no special privileges are needed. The check fires whenever `projectLedgerView` returns `Nothing`.
- **The developers are aware** — the TODO comment at line 1841 references issue #64 and says "remove this entire check," confirming the code is known to be incorrect in the Peras context but has not yet been fixed. [5](#0-4) 

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with the actual Peras weight snapshot. The snapshot is already available in the `NodeKernel` and is passed correctly to every other call site of `preferAnchoredCandidate`. The fix requires threading the snapshot into the ChainSync client's configuration or dynamic environment so `checkPreferTheirsOverOurs` can use it.

Alternatively, if the intent (per the TODO) is to remove the check entirely, it should be removed promptly rather than left in a broken state that will silently misbehave once Peras is enabled.

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Let the canonical chain accumulate several Peras certificate boosts so its total weight exceeds its block count significantly.
3. Connect a node to a peer that offers the canonical (Peras-boosted) chain. Arrange for the peer's tip to be beyond the node's forecast horizon (e.g., by advancing the peer's chain faster than the node can forecast).
4. Observe that `checkPreferTheirsOverOurs` compares purely by block count. If the canonical chain's tip has a lower `BlockNo` than the node's current selection (possible when Peras boosts make a shorter chain heavier), the node throws `CandidateTooSparse` and disconnects.
5. The node is now isolated from the canonical chain and will not adopt it, demonstrating the chain-selection divergence.
