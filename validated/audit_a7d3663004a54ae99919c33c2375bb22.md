### Title
Fee-on-Transfer Token Escrow Mis-Accounting in `initTransfer` — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

---

### Summary

The `OmniBridge` contract correctly uses `SafeERC20` wrappers, so the direct analog of the report's type-3 token revert issue does not exist. However, the same vulnerability class — erroneous ERC20 token handling — manifests in a distinct and critical form: the bridge encodes the caller-supplied `amount` into the cross-chain message without verifying the actual tokens received. For fee-on-transfer ERC20 tokens, the bridge is credited with fewer tokens than it reports to the NEAR side, causing permanent escrow undercollateralization and eventual loss of bridged funds.

---

### Finding Description

In `initTransfer`, for native (non-bridge, non-custom-minter) ERC20 tokens, the contract executes:

```solidity
IERC20(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    amount          // caller-supplied, not verified post-transfer
);
``` [1](#0-0) 

Immediately after, the unmodified `amount` is forwarded to `initTransferExtension`, which (in `OmniBridgeWormhole`) encodes it verbatim into the Wormhole payload:

```solidity
Borsh.encodeUint128(amount),
``` [2](#0-1) 

For a fee-on-transfer ERC20 token (e.g., PAXG, or any token that deducts a percentage on `transferFrom`), the bridge receives `amount − fee` but the cross-chain message asserts `amount`. The NEAR side credits the user with the full `amount`, creating a deficit in the EVM escrow.

The same mis-accounting occurs in the reverse direction: `finTransfer` calls:

```solidity
IERC20(payload.tokenAddress).safeTransfer(
    payload.recipient,
    payload.amount
);
``` [3](#0-2) 

Here the bridge's escrow is debited by `payload.amount` but the recipient only receives `payload.amount − fee`, compounding the undercollateralization on every round trip.

The `customMinters` path has an additional variant: the bridge transfers `amount` to the custom minter and then calls `burn(tokenAddress, amount)`, but the minter only received `amount − fee`, so the burn call operates on a balance that does not exist. [4](#0-3) 

---

### Impact Explanation

Each deposit of a fee-on-transfer token leaves the EVM escrow short by the transfer fee. Each withdrawal compounds the deficit. Over multiple round trips, the bridge holds materially fewer tokens than it owes to NEAR-side token holders. Any user who attempts to withdraw after the escrow is exhausted loses their funds permanently. Because the bridge is permissionless and accepts arbitrary ERC20 tokens, this affects any fee-on-transfer token that users choose to bridge.

Impact classification: **escrow mis-accounting leading to permanent loss of bridged funds** — within the allowed critical impact scope.

---

### Likelihood Explanation

Fee-on-transfer tokens are a well-known, deployed token class (PAXG charges 0.02% per transfer; various DeFi tokens implement dynamic fees). No special privilege is required: any unprivileged user can call `initTransfer` with such a token. The bridge is fully permissionless for ERC20 deposits, so no admin action is needed to enable the vulnerable path.

---

### Recommendation

Record the actual balance change rather than trusting the caller-supplied `amount`. A standard pattern:

```solidity
uint256 balanceBefore = IERC20(tokenAddress).balanceOf(address(this));
IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
uint256 actualReceived = IERC20(tokenAddress).balanceOf(address(this)) - balanceBefore;
// Use actualReceived in the cross-chain message, not amount
```

Apply the same balance-delta check in the `customMinters` path before calling `burn`. For `finTransfer`, either record the balance delta and emit it, or document and enforce that fee-on-transfer tokens are not supported (and add an on-chain registry check to enforce this).

---

### Proof of Concept

1. Token `T` charges a 1% fee on every `transferFrom` and `transfer`.
2. Alice calls `initTransfer(T, 1000, ...)`. Bridge receives 990 T. Wormhole message encodes `amount = 1000`.
3. NEAR side credits Alice with 1000 T (NEAR-side representation).
4. Alice bridges back: NEAR burns 1000 T, `finTransfer` is called with `payload.amount = 1000`.
5. Bridge calls `safeTransfer(Alice, 1000)`. Bridge escrow decreases by 1000; Alice receives 990.
6. Net: bridge lost 10 T per round trip (990 in, 1000 out). After 99 such round trips the bridge is fully drained of T, and the 100th legitimate depositor cannot withdraw.
7. Because the bridge is permissionless, any user can repeat this with any fee-on-transfer token, draining the escrow for that token at the cost of the transfer fees paid.
