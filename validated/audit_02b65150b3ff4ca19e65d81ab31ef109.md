### Title
`safe_mint` Mints nBTC to Bridge Account Before Checking Recipient Registration, Creating Unbacked Token Supply — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC token contract unconditionally mints tokens to the bridge's own account (`bridge_id`) before verifying whether the intended recipient's account is registered. When the recipient is unregistered, the function returns `U128(0)` as a failure signal but leaves the freshly minted tokens stranded in `bridge_id` without burning them back, permanently inflating nBTC supply above the BTC-backed amount.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124) executes in this order:

```rust
// Step 1 — tokens are minted to bridge_id unconditionally
self.token.internal_deposit(&self.bridge_id, amount.into());

// Step 2 — only NOW is registration checked
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));   // tokens already minted; nothing burned
}
``` [1](#0-0) 

When `account_id` is not registered the function returns the NEP-141 "all tokens rejected" sentinel `U128(0)`, but the `internal_deposit` call on line 112 has already increased `bridge_id`'s balance and the global total supply by `amount`. No compensating `internal_withdraw` (burn) is issued inside `safe_mint`.

The `burn` entry-point that could undo this always withdraws from `bridge_id`:

```rust
self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
``` [2](#0-1) 

`burn` is a separate cross-contract call that the bridge's safe-deposit callback must explicitly schedule. If that callback treats the `U128(0)` return as a simple "revert deposit state" signal without also scheduling a `burn`, the minted tokens remain in `bridge_id` indefinitely as unbacked supply.

The safe-deposit flow is documented to "revert the whole transaction if minting fails": [3](#0-2) 

In NEAR, cross-contract state cannot be atomically rolled back; the callback must explicitly compensate. The design of `safe_mint` makes this compensation easy to miss because the function itself does not burn on the failure path.

---

### Impact Explanation

Every failed `safe_mint` call (unregistered recipient) permanently mints `amount` nBTC to `bridge_id` with no corresponding BTC locked for those tokens. Over time this inflates total nBTC supply above the BTC-backed amount. Because `burn` always withdraws from `bridge_id`, these phantom tokens are indistinguishable from legitimately held withdrawal-in-transit tokens and can be consumed by any subsequent `burn` call, effectively allowing a future withdrawal to be settled without a real BTC deposit backing it — unauthorized release of bridged funds.

This matches the allowed impact: **Critical — unauthorized minting / reminting of nBTC** and **significant loss or permanent locking of user or protocol funds** (the depositing user's BTC is locked in the bridge UTXO pool while they receive no nBTC, and the phantom supply corrupts the 1:1 peg).

---

### Likelihood Explanation

The safe-deposit path (`deposit_msg.safe_deposit = Some(..)`) is the recommended flow for integrations such as Omni Bridge. The caller is required to attach NEAR for storage, but the nBTC account registration for the recipient is a separate step. Any integration that attaches storage NEAR to the bridge call but does not pre-register the recipient in the nBTC contract will trigger this path. This is a realistic integration mistake, especially for new dApp integrators.

---

### Recommendation

Reverse the order of operations in `safe_mint`: check recipient registration **before** minting to `bridge_id`. If the account is absent, return `U128(0)` without touching the token supply.

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Guard FIRST — no state change if recipient is unregistered
    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));
    }

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... transfer / ft_transfer_call as before
}
```

Alternatively, add an explicit `internal_withdraw(&self.bridge_id, amount)` on the early-return path to restore the invariant even if the check-first refactor is not applied.

---

### Proof of Concept

1. Integrator calls `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(SafeDepositMsg { msg: "..." })` for a recipient NEAR account that has never called `storage_deposit` on the nBTC contract.
2. Bridge verifies the BTC Merkle proof and calls `nbtc.safe_mint(recipient, amount, Some(msg))`.
3. `safe_mint` executes `internal_deposit(&bridge_id, amount)` — total nBTC supply increases by `amount`, all held in `bridge_id`.
4. `safe_mint` checks `accounts.get(&recipient)` → `None` → returns `U128(0)`.
5. Bridge's safe-deposit callback receives `U128(0)`, treats it as failure, does **not** mark the UTXO as `verified_deposit_utxo`, and does **not** schedule a `burn` call.
6. Result: `amount` nBTC exists in `bridge_id` with no BTC backing. The depositing user's BTC is locked in the bridge UTXO pool. The phantom tokens are available to be consumed by any future `burn` call (e.g., a legitimate withdrawal), effectively granting that withdrawal free BTC. [4](#0-3) [5](#0-4) [6](#0-5)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
