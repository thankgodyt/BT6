### Title
Unconditional Peras Certificate Acceptance via `validatePerasCert` Stub Enables Unauthorized Chain-Selection Boost from Any Internet Peer — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `BlockSupportsPeras` contains a stub `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or committee-membership checks. Because the `PerasCertDiffusion` miniprotocol is wired into the node-to-node (NTN) responder stack and is reachable by any internet peer, an unprivileged attacker can inject a crafted `PerasCert` for an arbitrary block, have it accepted as "validated," and cause the node to apply a Peras chain-selection boost to a non-canonical block.

---

### Finding Description

**Root cause — `validatePerasCert` stub always returns `Right`:** [1](#0-0) 

The comment on line 318 explicitly marks this as a "degenerate instance for all blks to get things to compile." The implementation at lines 353–358 is:

```haskell
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

No signature is checked, no committee membership is verified, no quorum is confirmed. Every `PerasCert` — regardless of origin or content — is accepted and wrapped in a `ValidatedPerasCert` carrying the full `perasWeight` boost.

**This is the only `BlockSupportsPeras` instance in the repository.** There is no Cardano-specific override that replaces it with real validation.

**Inbound path — `makePerasCertPoolWriterFromChainDB` calls this stub directly:** [2](#0-1) 

The `validateCert` argument passed to `processCerts` is `validatePerasCert mkPerasParams`, which always returns `Right`. Any certificate that is not already in the DB is immediately accepted and forwarded to `ChainDB.addPerasCertAsync`.

**NTN exposure — `PerasCertDiffusion` is active in the responder stack for all internet peers:** [3](#0-2) [4](#0-3) 

The `perasCertDiffusionProtocol` is registered as `InitiatorAndResponderProtocol` in `initiatorAndResponder`, meaning every connected NTN peer can push certificates to the node.

---

### Impact Explanation

A `ValidatedPerasCert` accepted by `processCerts` is added to the ChainDB via `addPerasCertAsync`. The `vpcCertBoost` field carries `perasWeight params`, which is the Peras chain-selection weight applied to the boosted block. An attacker who injects a certificate pointing to a non-canonical block causes the node to apply a Peras weight boost to that block during chain selection, potentially making the node prefer a non-canonical or adversary-controlled chain over the honest chain.

This is a bypass of Peras certificate verification that enables unauthorized certificate acceptance and chain-selection manipulation — matching the **Critical** impact category: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

**High.** The `PerasCertDiffusion` responder is active in the standard NTN stack. Any peer that can establish a TCP connection to the node's P2P port (which is intentionally open to the internet) can immediately send crafted `PerasCert` messages. No stake, no key material, and no prior relationship is required. The stub has been present since the Peras diffusion infrastructure was introduced and is the only instance of `BlockSupportsPeras` in the codebase.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the BLS aggregate signature over the certificate, checks that the signers form a valid quorum of the elected committee for the given round, and confirms the boosted block is on a known chain.
2. Until real validation is implemented, gate the `PerasCertDiffusion` responder behind a feature flag that is disabled by default, so the protocol is not active on production nodes.
3. Track this against the existing issue referenced in the TODO: `https://github.com/tweag/cardano-peras/issues/120`.

---

### Proof of Concept

**Step 1.** Connect to a target node's P2P port and complete NTN handshake (standard Ouroboros mux negotiation).

**Step 2.** On the `PerasCertDiffusion` miniprotocol channel, send a `MsgObjects` message containing a single crafted `PerasCert`:

```
PerasCert
  { pcCertRound      = <any round number, e.g. current round>
  , pcCertBoostedBlock = <Point of a non-canonical block known to the attacker>
  }
```

**Step 3.** The node's `hPerasCertDiffusionClient` handler calls `makePerasCertPoolWriterFromChainDB`, which calls `processCerts` with `validatePerasCert mkPerasParams` as the validator.

**Step 4.** `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally. [5](#0-4) 

**Step 5.** `ChainDB.addPerasCertAsync` is called with the accepted certificate. The Peras weight boost is applied to the attacker-chosen block in chain selection, causing the node to prefer the non-canonical chain. [6](#0-5)
