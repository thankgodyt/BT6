### Title
`emptyPerasWeightSnapshot` Hardcoded in ChainSync `checkPreferTheirsOverOurs` Causes Incorrect Chain-Preference Decision — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

In `checkPreferTheirsOverOurs`, the Peras weight snapshot is hardcoded to `emptyPerasWeightSnapshot` — the default zero-weight value — instead of the live snapshot maintained by the ChainDB. This mirrors the external report's root cause exactly: a state field that should be populated is left at its default, and that default is then used in a critical decision path. The result is that the ChainSync client evaluates chain preference purely by block count, ignoring Peras weight boosts. An adversary can exploit this asymmetry to cause an honest node to disconnect from peers offering the canonical (Peras-weighted) chain while remaining connected to a longer-by-block-count but lighter-by-weight adversarial chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is called during ChainSync header processing to decide whether to disconnect from a peer whose chain is not preferred over the node's own chain. It calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot          -- ← hardcoded default, not the live snapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`emptyPerasWeightSnapshot` is defined as `PerasWeightSnapshot Map.empty` — a map with no entries, giving every block a weight boost of zero: [2](#0-1) 

When `isEmptyPerasWeightSnapshot weights` is `True`, `preferAnchoredCandidate` falls into the block-count-only branch, completely ignoring Peras weight boosts: [3](#0-2) 

By contrast, the actual chain-selection path in `chainSelectionForBlock` correctly reads the live snapshot from the ChainDB via `getPerasWeightSnapshot`: [4](#0-3) 

The `ChainSelEnv` used in real chain selection also carries the live `weights` field: [5](#0-4) 

The live snapshot is populated by `implGetWeightSnapshot` from the `PerasCertDB`, which aggregates boosted blocks from all stored Peras certificates: [6](#0-5) 

The `getPerasWeightSnapshot` accessor is part of the public `ChainDB` API and is available to the ChainSync client via `chainDbView`: [7](#0-6) 

---

### Impact Explanation

When Peras is active, the canonical chain may have fewer blocks than a competing chain but carry more total weight due to Peras certificate boosts. Because `checkPreferTheirsOverOurs` uses empty weights:

- A peer offering the canonical chain (fewer blocks, higher Peras weight) will appear **not preferred** → the node throws `CandidateTooSparse` and disconnects.
- A peer offering an adversarial chain (more blocks, zero Peras weight) will appear **preferred** → the node stays connected.

The node is therefore systematically disconnected from honest peers serving the canonical chain and kept connected only to the adversarial chain. Since the node never downloads the canonical chain's blocks, the actual chain-selection logic (which does use real weights) never gets to evaluate them. The node is effectively locked onto the non-canonical chain.

This is a **High** chain-selection bug: an unprivileged peer can cause an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

**Medium.** The preconditions are:

1. Peras is active and certificates have been issued, populating the live weight snapshot with non-zero boosts.
2. An adversary produces a chain that is longer by block count but lighter by Peras weight than the canonical chain — achievable by any block-producing adversary who withholds Peras certificates.
3. The honest node connects to both the adversary's peers and honest peers, which is the normal operating condition.

The TODO comment in the source (`-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is problematic in the Peras context, but the fix has not yet been applied.

---

### Recommendation

Either:

1. **Remove `checkPreferTheirsOverOurs` entirely**, as the TODO comment proposes. The check is redundant because the actual chain-selection loop already enforces preference using real weights.
2. **Or**, if the check is retained, replace `emptyPerasWeightSnapshot` with the live snapshot obtained from `chainDbView`:

```haskell
weights <- atomically $ forgetFingerprint <$> getPerasWeightSnapshot chainDbView
checkPreferTheirsOverOurs weights kis
```

This mirrors the fix pattern from the external report: before using the state field in a critical operation, ensure it is populated with the actual value rather than the default.

---

### Proof of Concept

1. Peras is active; the canonical chain `C` has `N` blocks and total Peras weight `W > 0`.
2. Adversary constructs chain `A` with `N+1` blocks and zero Peras weight.
3. Node connects to adversary's peers. `checkPreferTheirsOverOurs` evaluates `preferAnchoredCandidate cfg emptyPerasWeightSnapshot ourFrag theirFrag`. With empty weights, `A` (N+1 blocks) > `C` (N blocks) → `ShouldSwitch` → `pure ()` → node stays connected to adversary.
4. Node connects to honest peers serving `C`. `checkPreferTheirsOverOurs` evaluates the same comparison. With empty weights, `C` (N blocks) < `A` (N+1 blocks) → `ShouldNotSwitch` → `throwSTM CandidateTooSparse` → node disconnects from honest peers.
5. Node never downloads `C`'s blocks. The actual chain-selection logic in `chainSelectionForBlock` (which uses real weights) never evaluates `C`. Node remains on `A`.

The root cause is structurally identical to the external report: `s.auctionData[collateralId].liquidator` defaults to `address(0)` when not set in `listForSaleOnSeaport`; here, `emptyPerasWeightSnapshot` (the zero-weight default) is used in `checkPreferTheirsOverOurs` instead of the live snapshot that is correctly used everywhere else in the chain-selection pipeline.

      assertWithMsg (precondition ours cand) $
        case (ours, cand) of

          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))

              ShouldNotSwitch o -> ShouldNotSwitch o

implGetWeightSnapshot ::

  WithFingerprint pcds fp <- readTVar pcdbState
  let weights =
        mkPerasWeightSnapshot
          [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
