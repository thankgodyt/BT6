Audit Report

## Title
Decimal Normalization Check After Token Lock/Burn Permanently Freezes User Funds - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer_internal` irreversibly burns or locks a user's tokens before any normalized-amount validation occurs. When a relayer later calls `sign_transfer`, `normalize_amount` applies floor division to scale the amount to the destination chain's precision. If the user's `amount_without_fee` is smaller than `10^(origin_decimals - decimals)`, the result is 0, causing `sign_transfer` to panic with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because the panic occurs after the tokens are already burned/locked and no cancel or refund path exists, the user's funds are permanently lost.

## Finding Description

**Root cause:** The normalization guard in `sign_transfer` fires too late — after the irreversible state change in `init_transfer_internal`.

**Step 1 — Tokens burned/locked in `init_transfer_internal` (lines 1850–1857):**

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
}
```

This is called from `init_transfer` (line 645) or `init_transfer_resume` (line 645), both of which are triggered by the user's `ft_transfer_call`. The only pre-flight check in `init_transfer` is `fee < amount` (lines 554–557); there is no check that the normalized amount is non-zero.

**Step 2 — `normalize_amount` performs floor division (lines 2784–2787):**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For any `amount < 10^(origin_decimals - decimals)`, this returns 0.

**Step 3 — Guard in `sign_transfer` panics (lines 475–485):**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

The panic aborts `sign_transfer` before the MPC call is made.

**Step 4 — No recovery path:** `sign_transfer_callback` only removes the transfer message when signing *succeeds* and fee is zero (lines 655–658). Since `sign_transfer` panics before reaching the MPC call, `sign_transfer_callback` is never invoked. `claim_fee_callback` is similarly unreachable. A grep search for `cancel`, `refund_transfer`, and `cancel_transfer` in `lib.rs` returns no matches. The transfer entry persists in `pending_transfers` indefinitely while the underlying tokens are gone.

**Why the CLAUDE.md false-positive note does not cover this:** Note #2 ("Decimal Arithmetic Underflow") addresses the case where `origin_decimals < decimals`, causing an underflow panic in the subtraction itself. The present scenario uses a *valid* configuration (`origin_decimals > decimals`) where the subtraction succeeds but the user's amount is simply too small to survive floor division.

## Impact Explanation

Permanent, unrecoverable loss of bridged funds for any user who initiates a NEAR→external-chain transfer with an amount below the normalization threshold. This matches the Critical impact category: *"permanent freezing of bridged funds"* and *"decimal/normalization abuse that changes user or protocol balances."* Concrete examples:

- NEAR-native token (24 decimals) → Solana (9 decimals): any transfer below `10^15` yoctoNEAR (0.001 NEAR) is permanently lost.
- BTC-like token (8 decimals) → 6-decimal EVM token: any transfer below 100 satoshis is permanently lost.

## Likelihood Explanation

No attacker action is required. Any ordinary user who calls `ft_transfer_call` with an amount below the threshold triggers the loss. The normalization threshold is determined by the registered `Decimals` configuration, which is set at token deployment time and is not surfaced to end users. A user bridging a small "test" amount or a dust balance from a prior operation can unknowingly hit this condition. The condition is repeatable for every such transfer.

## Recommendation

Add a pre-flight normalization check inside `init_transfer`, after constructing `transfer_message` but before calling `init_transfer_internal`, so that rejection happens before any token state change and the NEP-141 `ft_transfer_call` mechanism automatically refunds the user:

```rust
// After constructing transfer_message in init_transfer:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

Returning a non-zero value from `ft_on_transfer` (which `init_transfer` feeds into) causes the NEP-141 standard to refund the tokens to the sender, so no separate refund mechanism is needed.

## Proof of Concept

1. Register a token with `origin_decimals = 8`, `decimals = 6` (e.g., a BTC-like token bridged to a 6-decimal EVM representation).
2. User calls `ft_transfer_call` with `amount = 50` (50 satoshis) and `fee = 0`.
3. Bridge's `ft_on_transfer` → `init_transfer` → `init_transfer_internal`: 50 satoshis are burned/locked (lines 1851–1857); transfer message stored; function returns `U128(0)` (tokens not refunded).
4. Relayer calls `sign_transfer` for this transfer ID.
5. `normalize_amount(50, Decimals { decimals: 6, origin_decimals: 8 })` = `50 / 100` = **0** (line 2786).
6. `require!(amount_to_transfer > 0)` panics (lines 482–485); MPC call never made.
7. `sign_transfer_callback` never fires; transfer message remains in `pending_transfers`; 50 satoshis are permanently lost.

A local integration test using `near-workspaces` can reproduce this by: deploying the bridge and a mock NEP-141 token with `origin_decimals=8`/`decimals=6`, registering the token, calling `ft_transfer_call` with `amount=50`, then calling `sign_transfer` and asserting the panic while verifying the token balance is not restored.
