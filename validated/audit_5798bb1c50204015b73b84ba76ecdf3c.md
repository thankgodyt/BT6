### Title
Silent Token Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nbtc token contract mints tokens to the bridge account first, then silently returns without transferring or burning them if the recipient's account is not registered. The minted tokens are permanently locked in the bridge account with no recovery path.

### Finding Description
In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 100–124) executes in this order:

1. **Mints tokens to `bridge_id`** unconditionally via `internal_deposit` (line 112).
2. **Checks registration** of the intended recipient `account_id` (line 114).
3. **If unregistered**, returns `PromiseOrValue::Value(U128(0))` immediately — without transferring, burning, or recording the minted tokens anywhere (lines 114–116). [1](#0-0) 

The return value `U128(0)` signals to the caller that zero tokens were transferred, but `amount` tokens have already been credited to `bridge_id` and are now orphaned. There is no burn, no lost-found entry, and no revert of the `internal_deposit`. The `lost_found` map used elsewhere in the bridge (e.g., in `transfer_nbtc_callback`) is never populated here. [2](#0-1) 

### Impact Explanation
**Critical — Permanent locking of user funds.**

Any user whose NEAR account is not registered in the nbtc token contract at the time `safe_mint` is called will have their entire deposit amount permanently locked inside the bridge account. The tokens are minted (total supply increases) but are unreachable by the user. There is no administrative recovery function that targets this specific stuck balance, and the bridge's `lost_found` mechanism is not invoked.

### Likelihood Explanation
**Medium.** NEP-141 storage registration is a prerequisite that is separate from the deposit action. A user who sends BTC to their deposit address before registering their NEAR account in the nbtc contract — a realistic ordering for new users — will trigger this path. The `assert_bridge()` guard means only the bridge can call `safe_mint`, but the bridge calls it as part of the normal deposit flow, making this reachable by any depositor who is unregistered. [3](#0-2) 

### Recommendation
Replace the silent early-return with one of the following:

1. **Panic/revert**: Do not call `internal_deposit` before confirming registration. Check registration first; if unregistered, panic so the entire cross-contract call reverts and the bridge can handle the failure.
2. **Auto-register**: Call `internal_register_account(&account_id)` before `internal_deposit`, mirroring the pattern used in `mint_inner` (lines 342–344).
3. **Lost-found fallback**: If silent continuation is required, record the stuck amount in `lost_found` (as done in `transfer_nbtc_callback`) so the user can later claim it. [4](#0-3) 

### Proof of Concept

1. User sends BTC to their bridge deposit address.
2. Relayer submits an inclusion proof to `satoshi-bridge`.
3. `satoshi-bridge` calls `nbtc::safe_mint(user_account_id, amount, msg)`.
4. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — `amount` tokens are now credited to `bridge_id`. [5](#0-4) 
5. `self.token.accounts.get(&account_id).is_none()` evaluates to `true` because the user never registered. [6](#0-5) 
6. The function returns `U128(0)`. No transfer occurs. No burn occurs. No lost-found entry is created.
7. `amount` tokens are permanently locked in `bridge_id`. The user's BTC is spent on-chain; their nBTC is irrecoverable.
