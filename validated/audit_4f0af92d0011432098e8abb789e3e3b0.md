### Title
Peras Certificate and Vote Validation Stubs Unconditionally Accept Peer-Supplied Objects Without Cryptographic Verification — (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `BlockSupportsPeras` type class provides default implementations of `validatePerasCert` and `validatePerasVote` that are stubs performing no cryptographic verification. `validatePerasCert` unconditionally returns `Right` for every certificate, and `validatePerasVote` only checks stake-distribution membership without verifying the vote's cryptographic signature. No concrete override of either method exists in the production codebase. Both stubs are wired directly into the peer-facing object-diffusion mini-protocol handlers. An unprivileged peer can therefore inject arbitrary Peras certificates and votes that the node will accept, store, and act upon without any signature check, enabling unauthorized chain-weight boosts and chain-selection manipulation.

---

### Finding Description

`BlockSupportsPeras` declares two validation methods with default implementations:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/120

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

`validatePerasCert` is a total no-op: it ignores every field of the certificate and returns `Right` unconditionally. `validatePerasVote` performs only a map lookup against the stake distribution; it never calls any signature-verification primitive.

These stubs are the **only** implementations in the repository (grep for `validatePerasCert` and `validatePerasVote` returns exactly two files each: the class definition and the call site). They are invoked directly from the inbound object-diffusion handlers:

```haskell
-- PerasCert.hs
opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      (validatePerasCert mkPerasParams)   -- ← always Right
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
```

```haskell
-- PerasVote.hs
opwAddObjects = \votes ->
    processVotes
      systemTime
      (ChainDB.getPerasVoteIds chainDB)
      (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
      -- ↑ no signature check
      (void . ChainDB.addPerasVoteWithAsyncCertHandling chainDB)
      votes
```

`processCerts` and `processVotes` accept the entire batch if every object passes validation, then persist each object to the ChainDB. Because `validatePerasCert` always returns `Right`, every certificate a peer sends is stored and its boost applied to chain selection.

The structural analogy to the LooksRare bug is direct: in LooksRare the `managerSelectorOfAssetType` mapping was a configurable slot that could be pointed at an arbitrary function selector, bypassing the intended NFT-transfer interface. Here, `validatePerasCert`/`validatePerasVote` are the pluggable validation slots in the `BlockSupportsPeras` type class; the "arbitrary selector" is the no-op stub that replaces the intended cryptographic check, and the "attacker-controlled parameters" are the peer-supplied certificate/vote objects that flow through unchanged.

---

### Impact Explanation

A Peras certificate attests that a quorum of committee members voted for a specific block, granting that block a weight boost in chain selection. Accepting a certificate without verifying the aggregate BLS signature means:

- Any peer can fabricate a certificate for any block hash and any round number.
- The fabricated certificate is stored in `PerasCertDB` and its boost (`perasWeight params`) is applied during chain selection.
- By injecting certificates for a minority or adversarial chain, an attacker can make an honest node prefer a non-canonical chain, constituting a consensus safety failure.

For votes: a quorum of accepted-but-unverified votes triggers `forgePerasCert` inside `implAddVote`, producing a locally-forged certificate that is then propagated to other nodes, amplifying the attack.

This matches the **Critical** allowed impact: bypass of Peras certificate/vote verification checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The object-diffusion mini-protocol is a standard peer-to-peer channel; any node that connects to a Peras-enabled node can send certificate and vote objects. No special privileges, keys, or stake are required. The attacker only needs to craft a `PerasCert` with a desired `pcCertRound` and `pcCertBoostedBlock` and send it over the wire. The round-deduplication check (`Set.member roundNo certIds`) is the only gate, and it is trivially bypassed by using a fresh round number.

---

### Recommendation

1. Replace the stub `validatePerasCert` default with a real implementation that calls the committee's `implVerifyCert` (already implemented in `EveryoneVotes.hs` and `WFALS.hs`) before accepting any certificate.
2. Replace the stub `validatePerasVote` default with a real implementation that calls `verifyVoteSignature` (already implemented in `Crypto.hs`) before accepting any vote.
3. Remove the `default` keyword from both methods in `BlockSupportsPeras` so that any future concrete instance is forced to provide an explicit implementation, preventing accidental reuse of a no-op stub.
4. Add a property test asserting that a certificate with a forged aggregate signature is rejected by `validatePerasCert`.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Peer connects to a Peras-enabled node via the object-diffusion mini-protocol.
2. Peer constructs a `PerasCert` with an arbitrary `pcCertRound` (not yet in the DB) and `pcCertBoostedBlock` pointing to an adversarial block hash.
3. Peer sends the certificate batch to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`.
5. The default stub returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` without inspecting any signature field.
6. `ChainDB.addPerasCertAsync chainDB` stores the certificate.
7. Chain selection now applies `perasWeight params` boost to the adversarial block, potentially causing the node to switch to a non-canonical chain.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
