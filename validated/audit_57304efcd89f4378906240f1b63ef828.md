### Title
`validatePerasCert` Default Instance Unconditionally Accepts Any Peer-Crafted Peras Certificate Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The default `BlockSupportsPeras` instance, which is the only instance in the codebase for all block types including production Cardano blocks, implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate it receives. This means the `processCerts` inbound path — which is the live network entry point for Peras certificates received from peers — accepts and stores any certificate without performing any cryptographic signature verification, voter eligibility checking, or committee membership validation. An unprivileged peer can inject arbitrary forged Peras certificates that will be accepted and stored, directly influencing the Peras chain-selection boost mechanism.

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the mandatory certificate validation hook: [1](#0-0) 

The only instance in the entire codebase is the catch-all default instance, explicitly marked as a degenerate placeholder: [2](#0-1) 

The implementation body is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This stub is wired directly into both production inbound certificate paths. `makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB` both pass `(validatePerasCert mkPerasParams)` as the validation callback to `processCerts`: [3](#0-2) 

`processCerts` applies this callback to every inbound certificate from a peer and, because the callback always returns `Right`, every certificate passes and is stored: [4](#0-3) 

The same pattern applies to `validatePerasVote`, which only checks stake-distribution membership but never verifies the vote's cryptographic signature or VRF eligibility proof: [5](#0-4) 

This is wired into both production vote inbound paths via `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`: [6](#0-5) 

Additionally, `getPerasCertInBlock` — the hook for extracting Peras certificates embedded in blocks — is also stubbed to always return `Nothing`, meaning certificates carried inside blocks are never extracted or processed: [7](#0-6) 

### Impact Explanation

Peras certificates provide a chain-selection "boost" (`vpcCertBoost = perasWeight params`) that causes a node to prefer the chain containing the boosted block. Because `validatePerasCert` always returns `Right`, an unprivileged peer can send a crafted `PerasCert` with:

- A forged or absent aggregate BLS signature
- Fabricated voter seat indices not belonging to any committee member
- A certificate for an arbitrary round number and arbitrary block point

The certificate will be stored in the `PerasCertDB` and will influence chain selection with full boost weight. This enables an adversary to make an honest node prefer a non-canonical or attacker-controlled chain by injecting a certificate boosting a weaker fork, without holding any stake or committee membership.

### Likelihood Explanation

The `ObjectDiffusion` mini-protocol is a live network-facing component. Any connected peer can send a batch of `PerasCert` objects via the protocol. The inbound path (`makePerasCertPoolWriterFromChainDB`) is the production path. No authentication, stake ownership, or key material is required from the attacker — only a network connection to the target node.

### Recommendation

1. Implement real cryptographic validation inside `validatePerasCert`: verify the aggregate BLS signature over `(electionId, candidate)` against the aggregated public keys of the claimed voters, verify each voter's committee membership and eligibility proof (VRF output for non-persistent members), and check that the voter set meets the quorum threshold.
2. Implement real signature and VRF verification inside `validatePerasVote` rather than only checking stake-distribution membership.
3. Implement `getPerasCertInBlock` to extract and validate certificates embedded in received blocks.
4. Until (1)–(3) are complete, the `ObjectDiffusion` inbound paths for Peras objects should not be enabled in production nodes.

### Proof of Concept

A peer connects to a node running the `ObjectDiffusion` protocol. It sends a single-element batch containing:

```haskell
PerasCert
  { pcCertRound = PerasRoundNo 9999
  , pcCertBoostedBlock = <point of attacker-chosen fork tip>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which immediately returns:

```haskell
Right ValidatedPerasCert
  { vpcCert = cert
  , vpcCertBoost = perasWeight mkPerasParams  -- full boost applied
  }
```

The certificate is stored in the `PerasCertDB`. The node's chain-selection logic now sees a certificate boosting the attacker's fork with full Peras weight, causing it to prefer that fork over the honest canonical chain — without the attacker holding any stake or committee seat. processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
