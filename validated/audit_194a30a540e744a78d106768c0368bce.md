Audit Report

## Title
Cross-Chain Replay of MPC-Signed `DeployTokenPayload` Enables Unauthorized Wrapped Mint on Solana — (`solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

## Summary

`DeployTokenPayload::serialize_for_near` produces a byte sequence with no destination chain identifier. The EVM `OmniBridge.deployToken` constructs an identical byte sequence and signs it with the same MPC key. Because the signed message bytes are chain-agnostic, a valid MPC signature from a public EVM `deployToken` transaction can be submitted verbatim to Solana's permissionless `deploy_token` instruction, where `verify_signature` will accept it and create an unauthorized wrapped SPL mint.

## Finding Description

`DeployTokenPayload::serialize_for_near` serializes only a one-byte message-type prefix followed by the Borsh-encoded token fields: [1](#0-0) 

No chain ID is written. The EVM `OmniBridge.deployToken` constructs the identical layout: [2](#0-1) 

Both sides then keccak256-hash the same bytes. Solana's `verify_signature` recovers the 64-byte uncompressed secp256k1 public key from the signature and compares it to `derived_near_bridge_address`: [3](#0-2) 

Because secp256k1 recovery is deterministic over the message hash, a signature produced by the MPC for the EVM call recovers to the same 64-byte key on Solana, and the check passes. The `deploy_token` instruction has no `UsedNonces` account; the only idempotency guard is the `init` constraint on the mint PDA, which only blocks a *second* deployment of the same token — not the first unauthorized one: [4](#0-3) 

Contrast with `FinalizeTransferPayload`, which correctly binds the signed message to Solana by writing `SOLANA_OMNI_BRIDGE_CHAIN_ID` into both the token and recipient fields: [5](#0-4) 

`DeployTokenPayload` has no equivalent protection.

## Impact Explanation

An attacker who replays the EVM signature on Solana causes `deploy_token` to succeed, creating a wrapped SPL mint for token T under `WRAPPED_MINT_SEED`. The instruction then posts a `DeployTokenResponse` Wormhole message. If the NEAR bridge processes that VAA (the Solana factory is a registered factory), it creates a NEAR-side binding for the unauthorized Solana mint. Subsequent `finalize_transfer` calls can then mint against this illegitimate mint, enabling unauthorized token issuance on Solana for a token whose NEAR-side binding was intended exclusively for EVM. This is a concrete chain/domain separation flaw enabling unauthorized minting of bridged funds — a Critical allowed impact.

## Likelihood Explanation

The EVM `deployToken` calldata, including the MPC signature, is fully public on-chain. Submitting the replayed payload to Solana requires no special privilege; `deploy_token` is a permissionless instruction callable by any account. The attack succeeds on the first submission for any token not yet deployed on Solana. No MPC compromise is required — the attacker only reuses an already-produced, publicly visible signature.

## Recommendation

Include `SOLANA_OMNI_BRIDGE_CHAIN_ID` in the signed message body of `DeployTokenPayload::serialize_for_near`, mirroring the pattern already used in `FinalizeTransferPayload`:

```rust
fn serialize_for_near(&self, _params: Self::AdditionalParams) -> Result<Vec<u8>> {
    let mut writer = BufWriter::new(Vec::with_capacity(DEFAULT_SERIALIZER_CAPACITY));
    IncomingMessageType::Metadata.serialize(&mut writer)?;
    writer.write_all(&[SOLANA_OMNI_BRIDGE_CHAIN_ID])?; // ADD THIS
    self.serialize(&mut writer)?;
    writer.into_inner().map_err(|_| error!(ErrorCode::InvalidArgs))
}
```

The EVM and Starknet counterparts must be updated symmetrically to include their respective chain IDs in the signed payload, and the NEAR MPC must re-sign all existing `DeployTokenPayload` messages with the new format before deployment.

## Proof of Concept

1. Observe any EVM `deployToken` transaction on-chain; extract `signatureData` and `metadata` from calldata.
2. Construct a Solana `deploy_token` instruction with `SignedPayload { payload: DeployTokenPayload { token, name, symbol, decimals }, signature }` using the extracted values verbatim.
3. Submit the instruction to the Solana bridge program. `verify_signature` recovers the same 64-byte public key as the MPC key stored in `derived_near_bridge_address` and accepts the signature.
4. The `init` constraint on the mint PDA succeeds (token not yet deployed on Solana), creating an unauthorized wrapped SPL mint.
5. The emitted `DeployTokenResponse` Wormhole VAA, when relayed to NEAR, causes the NEAR bridge to bind the unauthorized Solana mint to token T, enabling subsequent unauthorized minting via `finalize_transfer`.

A minimal unit test can be written entirely within the Solana program's test suite: sign `serialize_for_near(())` output with a test secp256k1 key, verify it passes `verify_signature` on Solana, then verify the same signature also satisfies `ECDSA.recover` on the EVM side against the same message bytes — confirming the two verification paths are not domain-separated.

```rust
    pub fn verify_signature(
        &self,
        params: P::AdditionalParams,
        derived_near_bridge_address: &[u8; 64],
    ) -> Result<()> {
        let serialized = self.payload.serialize_for_near(params)?;
        let hash = keccak::hash(&serialized);

        let signature_bytes = &self.signature[0..64];

        let signature = libsecp256k1::Signature::parse_standard_slice(signature_bytes)
            .map_err(|_| ProgramError::InvalidArgument)?;
        require!(!signature.s.is_high(), ErrorCode::MalleableSignature);

        let signer = secp256k1_recover(&hash.to_bytes(), self.signature[64], signature_bytes)
            .map_err(|_| error!(ErrorCode::SignatureVerificationFailed))?;

        require!(
            signer.0 == *derived_near_bridge_address,
            ErrorCode::SignatureVerificationFailed
        );

        Ok(())
    }
```
