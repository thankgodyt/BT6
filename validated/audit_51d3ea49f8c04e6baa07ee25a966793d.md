### Title
Peras Vote Signature Validation Completely Absent — Any Peer Can Forge Votes for Arbitrary Legitimate Voters - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance's `validatePerasVote` implementation performs no cryptographic signature check whatsoever. It only looks up the claimed voter ID in the stake distribution. Any unprivileged peer connected via the ObjectDiffusion mini-protocol can craft `PerasVote` messages claiming to be any legitimate voter, have those votes accepted as valid, accumulate enough stake to trigger a false quorum, and cause the node to forge a `ValidatedPerasCert` boosting an adversarial block — directly influencing Peras-weighted chain selection.

---

### Finding Description

**Root cause — `validatePerasVote` stub:**

The `BlockSupportsPeras` typeclass defines `validatePerasVote` as the gate that must authenticate an inbound vote before it enters the system. The only instance in the entire codebase is the catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [1](#0-0) 

The `_params` argument is explicitly discarded (underscore prefix). The `PerasVote` data type carries only `{pvVoteRound, pvVoteBlock, pvVoteVoterId}` — no signature field exists in this type at all. The only check performed is `lookupPerasVoteStake`, which succeeds for any `pvVoteVoterId` present in the stake distribution map. There is no Cardano-specific override: `grep` confirms this is the only `instance.*BlockSupportsPeras` in the repository. [2](#0-1) 

**Attacker-controlled entry path — `processVotes`:**

Inbound votes from peers arrive via the ObjectDiffusion mini-protocol and are processed by `processVotes` in `makePerasVotePoolWriterFromChainDB`:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [3](#0-2) 

`processVotes` atomically filters out votes whose `PerasVoteId` is already in the DB, then calls `validatePerasVote` on the remainder. Since `PerasVoteId = (roundNo, voterId)` does **not** include the voted block, and since `validatePerasVote` only checks stake distribution membership, a malicious peer can submit votes for any voter ID in the stake distribution and they will pass validation. [4](#0-3) 

**Stake accumulation and false certificate forging:**

Accepted votes flow into `implAddVote`, which calls `updatePerasRoundVoteStates`. This accumulates `vpvVoteStake` per block target. When the total stake for a target exceeds the quorum threshold, `forgePerasCert` is called and a `ValidatedPerasCert` is produced and stored. [5](#0-4) 

The `updateTargetVoteTally` function deduplicates by `PerasVoteId` within the tally, so a single voter's stake is counted at most once per round per target. However, since the attacker can forge votes for **every** voter in the stake distribution, they can accumulate the full quorum stake for any block they choose. [6](#0-5) 

The `PerasVoteId` deduplication assumption is explicitly documented as relying on honest behavior:

> "NOTE: this is under the assumption that a voter doesn't cast two different votes for the same round (that is, with the same ID but different body)." [7](#0-6) 

---

### Impact Explanation

**Impact: Critical.** This is a bypass of Peras vote signature validation that enables unauthorized vote acceptance. A single malicious peer can:

1. Enumerate all voter IDs in the current `PerasVoteStakeDistr`.
2. Craft one `PerasVote` per voter ID, all targeting the same adversarial block in the same round.
3. Submit them in a single batch via the ObjectDiffusion protocol.
4. All votes pass `validatePerasVote` (stake distribution membership check only).
5. `updatePerasRoundVoteStates` accumulates their combined stake.
6. A `ValidatedPerasCert` is forged for the adversarial block.
7. The certificate's `vpcCertBoost` (Peras weight) is applied to that block in chain selection via `PerasWeightSnapshot`.
8. Honest nodes may prefer the adversarial chain over the canonical chain.

This directly breaks Peras's finality guarantee: the certificate is supposed to represent honest committee consensus, but here it is manufactured by a single peer with no stake.

---

### Likelihood Explanation

**Likelihood: High** (given the current state of the code). The attack requires only:
- A network connection to a node running the ObjectDiffusion mini-protocol for Peras votes.
- Knowledge of the current `PerasVoteStakeDistr` (a public on-chain data structure).
- The ability to craft well-formed CBOR-serialized `PerasVote` messages.

No key material, no stake, no privileged access is required. The `PerasVote` type has no signature field, so there is nothing to forge cryptographically — the attacker simply sets `pvVoteVoterId` to any known voter ID.

---

### Recommendation

1. **Immediate**: The `PerasVote` data type must include a cryptographic signature field (as the separate `Peras.Vote.V1.PerasVote` type already does with `pvSignature :: VoteSignature PerasBLSCrypto`). The `validatePerasVote` implementation must verify this signature using the voter's public key from the committee.

2. **Short-term**: Replace the degenerate `instance StandardHash blk => BlockSupportsPeras blk` with a proper era-specific instance (e.g., for the Peras-enabled Cardano era) that performs full BLS signature verification via `verifyVoteSignature` / `verifyAggregateVoteSignature` as already implemented in `Peras.Crypto.BLS`.

3. **Structural**: The `PerasVoteId` should either include the voted block (to detect equivocation at the ID level) or equivocating votes (same ID, different body) should trigger peer disconnection rather than silent discard. [8](#0-7) [9](#0-8)

### Proof of Concept

**Private testnet sequence:**

1. Start a node with Peras enabled and ObjectDiffusion active.
2. Obtain the current `PerasVoteStakeDistr` (public, derivable from the ledger state).
3. From a connecting peer, send a single ObjectDiffusion batch containing one `PerasVote` per voter ID in the distribution, all with:
   - `pvVoteRound = <current round>`
   - `pvVoteBlock = <adversarial block point>`
   - `pvVoteVoterId = <each legitimate voter ID in turn>`
4. Observe that `processVotes` accepts all votes (each passes `lookupPerasVoteStake`).
5. Observe that `updatePerasRoundVoteStates` accumulates stake until `stakeAboveThreshold` returns `True`.
6. Observe that `AddedPerasVoteAndGeneratedNewCert` is returned, and a `ValidatedPerasCert` for the adversarial block is stored in `PerasVoteDB`.
7. Observe that subsequent chain selection applies the Peras weight boost to the adversarial block.

The critical code path is:

```
peer sends PerasVote{pvVoteVoterId = legitimateVoter, pvVoteBlock = adversarialBlock}
  → processVotes
  → validatePerasVote _params stakeDistr vote   -- only checks Map.lookup pvVoteVoterId
  → implAddVote → updatePerasRoundVoteStates
  → VoteGeneratedNewCert adversarialCert
  → chain selection boosts adversarialBlock
``` [10](#0-9) [11](#0-10) [12](#0-11)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

updateTargetVoteTally ::
  StandardHash blk =>
  WithArrivalTime (ValidatedPerasVote blk) ->
  PerasTargetVoteTally blk ->
  PerasTargetVoteTally blk
updateTargetVoteTally
  vote
  ptvt@PerasTargetVoteTally
    { ptvtVotes
    , ptvtTarget
    , ptvtTotalStake
    } =
    assert (getPerasVoteTarget vote == ptvtTarget) $ do
      ptvt
        { ptvtVotes = pvaVotes'
        , ptvtTotalStake = pvaTotalStake'
        }
   where
    swapVote =
      Map.insertLookupWithKey
        (\_k old _new -> old)
        (getPerasVoteId vote)

    (pvaVotes', pvaTotalStake')
      -- key WAS NOT present → vote inserted and stake updated
      | (Nothing, votes') <- swapVote vote ptvtVotes =
          (votes', ptvtTotalStake + vpvVoteStake (forgetArrivalTime vote))
      -- key WAS already present → votes and stake unchanged
      | otherwise =
          (ptvtVotes, ptvtTotalStake)
