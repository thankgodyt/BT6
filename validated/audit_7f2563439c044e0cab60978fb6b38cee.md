### Title
Peras Certificate Validation Unconditionally Returns Success Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — the catch-all instance used for all block types — implements `validatePerasCert` as an unconditional `Right` return. No aggregate BLS signature, no voter eligibility proof, and no round/block consistency check is performed. The production certificate-ingest path (`makePerasCertPoolWriterFromChainDB`) calls this stub directly, so any peer can inject an arbitrary `PerasCert` carrying the full `perasWeight` chain-selection boost without possessing a valid quorum of committee signatures.

---

### Finding Description

`validatePerasCert` in the degenerate instance is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** instance in scope for all production block types (the comment explicitly marks it as the catch-all: `-- TODO: degenerate instance for all blks to get things to compile`). [2](#0-1) 

The production ingest path `makePerasCertPoolWriterFromChainDB` passes this stub directly as the validator:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then calls `validateCert` on each inbound certificate and, because `validatePerasCert` always returns `Right`, every certificate passes and is forwarded to `ChainDB.addPerasCertAsync`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
``` [4](#0-3) 

The accepted `ValidatedPerasCert` carries `vpcCertBoost = perasWeight params` — the full Peras chain-selection weight — regardless of whether any real quorum of committee members signed it.

This is structurally identical to the reported "unbacked deposits" pattern: a conditional validation branch is absent (here, entirely missing rather than gated on a flag), yet the downstream state (`ValidatedPerasCert` with full boost, stored in ChainDB) is updated as if validation succeeded.

---

### Impact Explanation

Peras certificates directly influence chain selection: a block boosted by a valid certificate gains `perasWeight` additional weight over an unboosted competing chain of equal length. An attacker who can inject arbitrary certificates for any `PerasRoundNo` and any `Point blk` can:

1. Boost a minority or adversarial fork to make honest nodes prefer it over the canonical chain.
2. Suppress the boost of the honest chain by pre-occupying a round's certificate slot with a certificate pointing to a different block (since `processCerts` silently skips certs whose round is already present).

This constitutes a **chain-selection manipulation** that lets an unprivileged peer cause an honest node to prefer a non-canonical chain, matching the **High** impact tier: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The Peras certificate object-diffusion mini-protocol is wired into the production `ChainDB` path (`makePerasCertPoolWriterFromChainDB` → `ChainDB.addPerasCertAsync`). Any peer participating in the Peras cert-diffusion sub-protocol can send a crafted `PerasCert` CBOR message. No special privileges, keys, or stake are required. The only gate is the per-round deduplication check (`Set.member roundNo alreadyInDb`), which an attacker trivially satisfies by targeting a round not yet seen by the victim node. Likelihood is **High** once the Peras diffusion sub-protocol is active on any network (testnet or mainnet).

---

### Recommendation

Replace the stub with a real implementation that:

1. Verifies the aggregate BLS signature (`pcSignature`) over the canonical encoding of `(pcRoundNo, pcBoostedBlock)` against the aggregate public key derived from the claimed voter set.
2. Verifies each voter's eligibility proof (persistent seat membership or non-persistent VRF sortition proof) against the committee computed from the current stake distribution.
3. Checks that the number of voters meets the quorum threshold.
4. Checks that `pcBoostedBlock` is a known block on a valid chain.

Until the real implementation is in place, the `validatePerasCert` stub should return `Left PerasValidationErr` (reject all) rather than `Right` (accept all), so that the absence of validation is safe-by-default.

---

### Proof of Concept

An attacker node connects to a victim via the Peras cert-diffusion mini-protocol and sends:

```
PerasCert
  { pcCertRound      = <target round not yet in victim DB>
  , pcBoostedBlock   = <hash of attacker's fork tip>
  , pcVoters         = <any bitmap, e.g. single voter>
  , pcSignature      = <zeroed / garbage BLS aggregate>
  }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams }
``` [5](#0-4) 

The cert is timestamped and forwarded to `ChainDB.addPerasCertAsync`. The ChainDB stores it and triggers chain selection, now weighting the attacker's fork by `perasWeight` — causing the victim to switch to the adversarial chain without any legitimate quorum having voted for it.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
