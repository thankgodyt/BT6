### Title
Input-limit bypass via `is_merge_unhealthy_utxos` path in `check_active_management_psbt_valid` — (`contracts/satoshi-bridge/src/psbt.rs`)

### Summary

`check_active_management_psbt_valid` entirely skips the `max_active_utxo_management_input_number` guard when `is_merge_unhealthy_utxos` returns `true`. Any caller who can reach `create_active_utxo_management_pending_info` with a PSBT whose inputs are all unhealthy UTXOs and whose `output_num == 1` can submit a PSBT with an arbitrarily large number of inputs, bypassing the configured limit.

### Finding Description

In `check_active_management_psbt_valid`: [1](#0-0) 

The entire `if` block — which contains both the `input_num <= max_active_utxo_management_input_number` check and the `output_num <= max_active_utxo_management_output_number` check — is guarded by `if !is_merge_unhealthy_utxos(...)`. When that function returns `true`, **all** limit checks are skipped.

`is_merge_unhealthy_utxos` returns `true` whenever `output_num == 1` and every vutxo's amount is `<= unhealthy_utxo_amount`: [2](#0-1) 

After the bypass, `create_active_utxo_management_pending_info` records `need_signature_num = psbt.get_input_num()` and allocates `signatures: vec![None; need_signature_num]` sized to the actual (unchecked) input count: [3](#0-2) 

The only remaining validation is `check_psbt_output_all_change_address`, which enforces that all outputs go to the bridge's change address and that the BTC gas fee is within `[min_btc_gas_fee, max_btc_gas_fee]`. It does **not** bound the number of inputs. [4](#0-3) 

### Impact Explanation

The impact does **not** reach Critical:

- **No fund theft**: `check_psbt_output_all_change_address` enforces that every output goes to the bridge's own change address. An attacker cannot redirect funds.
- **No unauthorized minting**: this path does not mint nBTC.
- **Temporary UTXO locking**: if the signing process stalls or the resulting Bitcoin transaction is rejected (e.g., due to non-standard relay policies for very large transactions), the consumed UTXOs are locked until `max_btc_tx_pending_sec` expires — temporary, not permanent.
- **Bypass of bridge limits**: the `max_active_utxo_management_input_number` policy is completely unenforced on the unhealthy-merge path. An attacker can force the signing subsystem to process far more inputs than the operator intended, increasing chain-signature call overhead and NEAR gas costs for the signing relayer.
- **Oversized Bitcoin transaction**: for realistic unhealthy-UTXO counts (hundreds), the resulting transaction stays well within Bitcoin's 100 KB relay limit, so broadcast failure is unlikely in practice.

The realistic impact is **Medium**: bypass of a bridge policy limit and attacker-triggered temporary locking of bridge UTXOs.

### Likelihood Explanation

The preconditions are:
1. The bridge must hold unhealthy UTXOs (amounts ≤ `unhealthy_utxo_amount`) — a normal operational state.
2. The caller must be able to reach `create_active_utxo_management_pending_info`. Whether this requires a relayer role could not be fully confirmed from the available code (the public API surface in `api/bridge.rs` was not read), but the function itself contains no role check beyond `require_pending_sign_capacity`. [5](#0-4) 

If the entry point is reachable by any relayer (privileged or not), the bypass is straightforward to trigger.

### Recommendation

Add an explicit input-count cap inside the `is_merge_unhealthy_utxos` branch, for example:

```rust
if !is_merge_unhealthy_utxos(output_num, vutxos, config.unhealthy_utxo_amount) {
    // existing checks …
} else {
    require!(
        input_num <= usize::from(config.max_active_utxo_management_input_number),
        format!("require input_num <= {}", config.max_active_utxo_management_input_number)
    );
}
```

This preserves the intentional unhealthy-merge shortcut (no output-count constraint, no split/merge direction constraint) while still bounding the number of inputs the signing subsystem must process.

### Proof of Concept

1. Ensure the bridge holds N unhealthy UTXOs (each ≤ `unhealthy_utxo_amount`), where N > `max_active_utxo_management_input_number`.
2. Construct a PSBT referencing all N UTXOs as inputs and exactly 1 output to the bridge's change address, with a BTC gas fee within `[min_btc_gas_fee, max_btc_gas_fee]`.
3. Call `create_active_utxo_management_pending_info` with this PSBT.
4. Observe that the call succeeds and `signatures` is allocated with N slots — the input limit was never checked.

---

**Verdict**: This is a real, reachable vulnerability. The `is_merge_unhealthy_utxos` branch unconditionally skips `max_active_utxo_management_input_number` enforcement, constituting a bypass of bridge limits. Impact is **Medium** (policy bypass + attacker-triggered temporary UTXO locking); the Critical impact framing in the question (gas exhaustion, unbroadcastable transaction) is not realistic for the described input sizes.
