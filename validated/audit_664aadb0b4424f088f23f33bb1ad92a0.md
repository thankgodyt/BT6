### Title
Shared UTXO Pool Exhaustion Enables Attacker-Triggered Temporary Locking of All User Withdrawals - (File: contracts/satoshi-bridge/src/api/token_receiver.rs)

### Summary

The bridge maintains a single shared UTXO pool from which all withdrawal PSBTs draw their inputs. When a withdrawal is initiated via `ft_on_transfer`, selected UTXOs are removed from the pool immediately and are not returned until the Bitcoin transaction is confirmed on-chain via `verify_withdraw`. A well-funded attacker can deposit BTC across multiple NEAR accounts, initiate simultaneous withdrawals that consume all available UTXOs, and then stall the signing step — keeping the pool empty and blocking every other user from initiating a withdrawal for the duration of the attack.

### Finding Description

**Root cause — shared pool, immediate removal, no protocol-wide throughput cap.**

In `create_btc_pending_info` (`contracts/satoshi-bridge/src/api/token_receiver.rs`, lines 71-140), the bridge calls `generate_vutxos` to select UTXOs from the shared pool and removes them immediately:

```rust
let (utxo_storage_keys, vutxos) = self.generate_vutxos(&mut psbt);
// ...
Event::UtxoRemoved { utxo_storage_keys }.emit();
``` [1](#0-0) 

The only per-account guard is `require_pending_sign_capacity`, which defaults to **1 pending withdrawal per account**:

```rust
pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
    self.data()
        .pending_tx_limits
        .get(account_id)
        .copied()
        .unwrap_or(1)
}
``` [2](#0-1) 

There is **no protocol-wide limit** on how many UTXOs can be simultaneously in-flight across all accounts. Creating additional NEAR accounts is trivial and cheap.

**Attack path:**

1. Attacker creates N NEAR accounts (trivial on NEAR).
2. Each account deposits BTC → receives nBTC.
3. Each account calls `nbtc.ft_transfer_call(bridge, amount, WithdrawMsg{...})`, constructing a PSBT that consumes UTXOs from the shared pool. Each call removes those UTXOs immediately.
4. Attacker deliberately does **not** call `sign_btc_transaction`, leaving all N pending infos in `PendingSign` state. The UTXOs remain absent from the pool.
5. The shared pool is now empty (or below `passive_management_lower_limit`). Any legitimate user who calls `ft_transfer_call` to withdraw will fail at PSBT construction because there are no available UTXOs.
6. After `max_btc_tx_pending_sec` elapses, the pending transactions can be cancelled and UTXOs eventually return — but the attacker simply repeats the cycle with fresh withdrawals, sustaining the DoS.

**Passive management constraint amplifies the impact.** `check_withdraw_psbt_valid` enforces:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
}
``` [3](#0-2) 

Even before the pool reaches zero, once `utxo_num` drops below `passive_management_lower_limit`, every withdrawal must produce more change outputs than inputs. For users with a single UTXO and a small balance, this constraint may make it impossible to construct a valid PSBT at all, further tightening the DoS window.

### Impact Explanation

All legitimate users holding nBTC on NEAR are unable to initiate withdrawals to Bitcoin for as long as the attacker sustains the attack. Their nBTC is locked on NEAR — not stolen, but inaccessible for redemption. This matches the **Medium** impact category: *attacker-triggered temporary locking of bridged funds*.

### Likelihood Explanation

The attack requires the attacker to hold BTC (to deposit and receive nBTC), but the cost per cycle is only the withdrawal fee (minimum `fee_min = 50000` satoshis) plus Bitcoin gas fees. The attacker recovers their principal BTC each cycle. Creating multiple NEAR accounts costs negligible NEAR. A moderately funded attacker can sustain this indefinitely.

### Recommendation

1. **Introduce a protocol-wide in-flight UTXO cap**: limit the total number of UTXOs that can be simultaneously locked in pending withdrawals across all accounts.
2. **Require a non-refundable NEAR deposit** (beyond storage) when initiating a withdrawal, slashed if the signing step is not completed within a deadline. This raises the cost of stalling.
3. **Reduce `max_btc_tx_pending_sec`** to shorten the window during which UTXOs remain locked in unsigned pending infos.
4. **Monitor and alert** when the available UTXO count drops below a safety threshold.

### Proof of Concept

```
// Attacker setup (off-chain):
for i in 0..N:
    account_i = create_near_account()
    deposit_btc(account_i, amount_i)          // UTXOs enter pool
    wait for verify_deposit → nBTC minted

// Attack:
for i in 0..N:
    account_i.ft_transfer_call(bridge, amount_i, WithdrawMsg {
        input: [utxo_i],   // consumes utxo_i from pool immediately
        output: [...],
    })
    // DO NOT call sign_btc_transaction — leave in PendingSign

// Pool is now empty.
// Any legitimate user calling ft_transfer_call → generate_vutxos panics
// or returns empty, PSBT construction fails, ft_on_transfer refunds nBTC.
// Users cannot withdraw until attacker's pending txs time out AND
// attacker does not re-initiate — which they can do continuously.
