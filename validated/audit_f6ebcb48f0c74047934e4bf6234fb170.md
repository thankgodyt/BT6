Audit Report

## Title
Unverified `burn` Promise in `burn_tokens_if_needed` Allows Token Supply Inflation on Cross-Chain Transfer - (File: near/omni-bridge/src/lib.rs)

## Summary
`burn_tokens_if_needed` fires a cross-contract `burn()` call with `.detach()`, meaning the result is never observed. If the burn fails for any reason, `init_transfer_internal` proceeds unconditionally to emit `InitTransferEvent`, allowing a relayer to finalize the transfer on the destination chain and mint tokens there while the NEAR-side supply is never reduced. This constitutes escrow mis-accounting and unauthorized token supply inflation.

## Finding Description
`burn_tokens_if_needed` is defined at lines 1806–1813:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // result never observed
    }
}

It is called inside `init_transfer_internal` at lines 1850–1864:

```rust

The `InitTransferEvent` log is emitted unconditionally after the detached burn, with no callback or promise chaining to verify success. There is no guard between the `.detach()` call and the event emission. The same unsafe pattern appears in `fin_transfer_send_tokens_callback` at lines 1703–1710, where a failed burn during a refund path also goes undetected. [3](#0-2) 

The project's own security checklist explicitly flags this pattern as risky: [4](#0-3) 

## Impact Explanation
When the burn fails silently during `init_transfer_internal`:
1. The user's tokens were transferred to the bridge via `ft_transfer_call` and remain there (bridge returns `U128(0)`, so the token contract keeps them at the bridge).
2. The detached burn fires but fails — the bridge's balance of the deployed token is not reduced.
3. `InitTransferEvent` is emitted anyway.
4. A relayer calls `sign_transfer`, MPC signs, and the destination chain's `finTransfer` mints tokens to the recipient.
5. The destination chain has new tokens, but the NEAR-side supply was never reduced. The bridge holds "ghost" tokens that should not exist.
6. These ghost tokens can later be transferred out to a NEAR recipient via a legitimate `fin_transfer`, effectively double-spending the same token units.

This is a concrete **escrow mis-accounting / token supply inflation** impact, matching the allowed critical scope: *"Balance manipulation, escrow mis-accounting... that changes user or protocol balances."*

## Likelihood Explanation
The burn can fail due to:
- **Insufficient `BURN_TOKEN_GAS`**: The gas constant is fixed at compile time. If the deployed token's `burn` implementation consumes more gas than allocated (e.g., due to storage operations, non-standard logic, or gas cost schedule changes), the promise panics silently.
- **Token contract panic**: Any unexpected panic in the token's `burn` implementation (storage exhaustion, arithmetic overflow in a non-standard token) causes silent failure.

Any user initiating a transfer of a bridge-deployed token from NEAR traverses this code path. No special role or privilege is required. The vulnerability is repeatable and exploitable by any unprivileged user who can trigger a burn failure condition.

## Recommendation
Replace the fire-and-forget `.detach()` with a chained callback that verifies the burn succeeded before emitting `InitTransferEvent`. The event and transfer message storage must only be committed after confirming the burn promise succeeded. If the burn fails, the transfer message should be removed and the full amount returned from `ft_on_transfer` to trigger a refund:

```rust
ext_token::ext(token_id)
    .with_static_gas(BURN_TOKEN_GAS)
    .burn(transfer_message.amount)
    .then(
        Self::ext(env::current_account_id())
            .with_static_gas(INIT_TRANSFER_CONFIRM_GAS)
            .init_transfer_burn_callback(transfer_message, storage_owner),
    )
```

The callback should check `env::promise_result(0)` and only emit `InitTransferEvent` and return `U128(0)` on success; on failure it should remove the transfer message and return the full amount. The same fix applies to the `fin_transfer_send_tokens_callback` burn path.

## Proof of Concept
1. Deploy a bridge-deployed NEP-141 token via the bridge's token deployer.
2. Arrange for the token's `burn` function to consume more gas than `BURN_TOKEN_GAS` (e.g., by deploying a custom token with additional storage operations in `burn`, or by triggering gas exhaustion naturally).
3. Call `ft_transfer_call(bridge, amount, init_transfer_msg)` on the token.
4. The bridge's `ft_on_transfer` fires the detached burn (which fails due to gas exhaustion), emits `InitTransferEvent`, and returns `U128(0)`.
5. The token contract keeps the tokens at the bridge (not refunded to sender).
6. A relayer calls `sign_transfer`; MPC signs; destination chain calls `finTransfer` and mints `amount` tokens to the recipient.
7. Observe: recipient has tokens on the destination chain, and the bridge holds `amount` of the deployed token on NEAR that was never burned — total supply is inflated by `amount`. These ghost tokens can be extracted via a subsequent `fin_transfer` to a NEAR recipient, constituting double-spend.
