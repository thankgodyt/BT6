Audit Report

## Title
Silent Fall-Through in Legacy `ft_transfer` Branch Permanently Freezes Caller's Tokens — (File: `near/omni-token/src/lib.rs`)

## Summary

When `ft_transfer` is called with `receiver_id == current_account_id()` and a memo prefixed `WITHDRAW_TO:`, but `withdraw_relayer_address` is not configured, the function silently falls through and executes an unconditional `self.token.ft_transfer(receiver_id, amount, memo)` where `receiver_id` is still the token contract itself. Because the NEAR FT standard only requires `predecessor_account_id != receiver_id` (not `current_account_id != receiver_id`), the transfer succeeds and tokens are credited to the token contract's own FT balance with no on-chain recovery path.

## Finding Description

In `near/omni-token/src/lib.rs` lines 194–207, the `ft_transfer` implementation contains a legacy Near Intents bridging branch:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
        // ← no else/panic: falls through
    }
    self.token.ft_transfer(receiver_id, amount, memo); // receiver_id == current_account_id()
}
```

When `read_withdraw_relayer_address()` returns `None`, the `if let` arm is skipped with no `else` branch or panic. Execution falls through to the unconditional `self.token.ft_transfer(receiver_id, amount, memo)` on line 206, where `receiver_id` is still `current_account_id()`.

The NEAR FT standard's `internal_transfer` checks `sender_id != receiver_id`, where `sender_id = env::predecessor_account_id()` (the external caller) and `receiver_id = env::current_account_id()` (the token contract). These are distinct accounts, so the check passes and the transfer succeeds — crediting the token contract's own FT balance.

**Preconditions:**
1. `withdraw_relayer_address` is unset (e.g., during deployment, migration, or upgrade windows).
2. The token contract's own account is registered in FT storage. This is permissionless: any caller can invoke `storage_deposit(Some(token_contract_id), None)`.

**No recovery path exists.** The `burn()` function at lines 146–151 calls `self.token.internal_withdraw(&env::predecessor_account_id(), amount.into())` — it withdraws from the *controller's* balance, not from the token contract's own FT balance. There is no admin sweep, no `ft_on_transfer` implementation, and no other mechanism to move tokens out of the token contract's own FT balance.

## Impact Explanation

This is a **permanent freezing of bridged tokens**. Any user who calls `ft_transfer(token_contract_id, amount, Some("WITHDRAW_TO:..."))` while the relayer is unconfigured loses `amount` tokens irreversibly. The tokens are credited to the token contract's own FT balance with no callable function able to reduce it. This matches the critical allowed impact: *permanent freezing of bridged funds on NEAR*.

## Likelihood Explanation

- The `WITHDRAW_TO:` memo prefix is part of the documented Near Intents legacy flow; users migrating from that system are likely to use it.
- `withdraw_relayer_address` may be unset during deployment windows, contract upgrades, or migrations — a realistic operational state.
- Registering the token contract's own FT storage account via `storage_deposit` is permissionless and costs only a small NEAR deposit.
- The attack requires only 1 yoctoNEAR attached — a standard, low-friction operation.
- The vulnerability is repeatable: any user can trigger it independently.

## Recommendation

Replace the silent fall-through with an explicit panic when the legacy branch is entered but no relayer is configured:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let withdraw_relayer = Self::read_withdraw_relayer_address()
            .unwrap_or_else(|| env::panic_str("Withdraw relayer address not configured"));
        return self.token.ft_transfer(withdraw_relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

This ensures the legacy path either routes correctly or reverts atomically, never silently depositing tokens into the contract itself.

## Proof of Concept

1. Deploy `OmniToken` without calling `set_withdraw_relayer_address` (or simulate a migration window where it is unset).
2. Call `storage_deposit(Some(token_contract_id), None)` with sufficient NEAR to register the token contract's own FT account — permissionless.
3. Mint tokens to an attacker account via the controller.
4. Call `ft_transfer(token_contract_id, 50, Some("WITHDRAW_TO:attacker_eth_addr"))` with 1 yoctoNEAR attached from the attacker account.
5. Assert `ft_balance_of(token_contract_id) == 50` and `ft_balance_of(attacker) == 0`.
6. Attempt every callable function (`burn`, `storage_unregister`, etc.) and confirm none can reduce `ft_balance_of(token_contract_id)` — tokens are permanently frozen.
