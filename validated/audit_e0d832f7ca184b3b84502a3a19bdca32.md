### Title
Duplicate `BTCPendingInfo` via Re-execution of Shielded Refund with Different Orchard Bundle — (`contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/zcash_utils/refund.rs`)

### Summary

After a shielded refund is executed (`executed = true`), the guard in `load_refund_request_for_execute` explicitly re-admits the same UTXO for another `execute_refund` call. Because the Zcash `pending_id` is derived from the full transaction digest (which includes the Orchard bundle), supplying a different Orchard bundle — even one paying the same address and amount — produces a different `pending_id` and bypasses the uniqueness check in `finalize_refund_with_psbt`. The result is two live `BTCPendingInfo` entries for the same deposit UTXO, both of which will be signed and broadcast, creating stuck bridge state.

### Finding Description

**Step 1 — First execution (legitimate).**

`execute_refund_callback` calls `load_refund_request_for_execute`, which enforces: [1](#0-0) 

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

After the first successful execution, `finalize_refund_with_psbt` inserts `utxo_storage_key` into `verified_deposit_utxo` and sets `executed = true`: [2](#0-1) 

**Step 2 — Re-execution with a different Orchard bundle.**

On the second call, `verified_deposit_utxo` contains the key **and** `executed == true`. The `||` short-circuits: the `require!` passes unconditionally whenever `executed` is true, regardless of how many times `execute_refund` has already run. [3](#0-2) 

**Step 3 — Validation passes for a different bundle.**

`execute_refund_callback` validates the new Orchard bundle against `refund_address` and `refund_amount`: [4](#0-3) 

A different Orchard bundle can satisfy both checks (same recipient, same amount) while using different randomness/proof bytes, producing a different Zcash transaction digest.

**Step 4 — `pending_id` is the Zcash txid, which changes with the bundle.** [5](#0-4) 

```rust
pub fn get_pending_id(self) -> String {
    self.get_zcash_tx().compute_txid().to_string()
}
```

The Zcash v5 txid digest covers the Orchard bundle. Two bundles with different randomness produce different txids.

**Step 5 — Uniqueness check in `finalize_refund_with_psbt` is bypassed.** [6](#0-5) 

```rust
require!(
    self.data_mut()
        .btc_pending_infos
        .insert(btc_pending_id.clone(), btc_pending_info.into())
        .is_none(),
    "pending info already exist"
);
```

Because `pending_id_B ≠ pending_id_A`, the insert succeeds. Two `BTCPendingInfo` entries now exist for the same deposit UTXO.

### Impact Explanation

Both entries enter the signing pipeline. The bridge's chain-signature infrastructure will sign both transactions. One will confirm on-chain; the other is an invalid double-spend attempt. The confirmed entry is cleaned up by `verify_refund_finalize_callback`, but the stale entry remains in `btc_pending_infos` and `btc_pending_sign_ids` until an operator manually calls `internal_remove_refund_pending_tx_id`. [7](#0-6) 

Importantly, the attacker **cannot redirect funds** to a different address — `check_psbt_chain_specific` enforces the recipient matches `refund_request.refund_address`. The question's framing of "paying to a different Orchard address" is therefore incorrect; the actual impact is stuck/inconsistent bridge state, not fund theft.

### Likelihood Explanation

The path is fully public: any account can call `execute_refund` after the timelock has elapsed. No privileged role is required. Constructing a second valid Orchard bundle paying the same address and amount with different randomness is a standard Zcash wallet operation. The attack is locally reproducible.

### Recommendation

In `finalize_refund_with_psbt`, before inserting a new `BTCPendingInfo`, check whether any existing pending entry already references the same UTXO storage key (e.g., by maintaining a `utxo_key → pending_id` index, or by removing the old pending entry before creating the new one). Alternatively, remove the old `BTCPendingInfo` atomically when `execute_refund` is re-run for an already-executed request, so only one live signing entry exists at any time.

### Proof of Concept

```
1. Call execute_refund(utxo_key, orchard_bundle_A) → pending_id_A inserted, executed=true.
2. Call execute_refund(utxo_key, orchard_bundle_B) (same recipient/amount, different randomness).
   - load_refund_request_for_execute: executed==true → guard passes.
   - check_psbt_chain_specific: recipient and amount match → passes.
   - get_pending_id() → pending_id_B ≠ pending_id_A.
   - btc_pending_infos.insert(pending_id_B, ...) → is_none() == true → succeeds.
3. Assert btc_pending_infos contains both pending_id_A and pending_id_B.
4. Both entries are signed; one confirms; stale entry requires operator cleanup.
```

        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,

        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();

        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),

            balance: u64::try_from(refund_request.amount)

        let btc_pending_id = psbt.get_pending_id();

        }

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(

                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),

        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,

        .emit();

        Event::GenerateBtcPendingInfo {

    pub(crate) fn internal_remove_refund_pending_tx_id(&mut self, tx_id: String) {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&tx_id).clone();
        btc_pending_info.assert_refund_related();

        // A refund spends exactly one deposit UTXO, whose key is the refund request key.
        let utxo_storage_keys = btc_pending_info.get_psbt().get_utxo_storage_keys();
        require!(
            utxo_storage_keys.len() == 1,
            "refund transaction must spend exactly one input"
        );
        require!(
            !self
                .data()
                .refund_requests
                .contains_key(&utxo_storage_keys[0]),
            "refund request still active"
        );

        let account_id = btc_pending_info.account_id.clone();
        self.internal_remove_btc_pending_info(&tx_id);
        let account = self.internal_unwrap_mut_account(&account_id);
        account.btc_pending_sign_ids.remove(&tx_id);
        account.btc_pending_verify_list.remove(&tx_id);
