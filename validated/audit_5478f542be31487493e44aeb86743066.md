Audit Report

## Title
Delegated SPL Token Authority Allows Attacker to Bridge Victim's Tokens to Attacker-Controlled NEAR Recipient — (File: `solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary
The `InitTransfer` account struct constrains `from` only by mint and token-program membership, with no `token::authority = user` check. Because SPL Token's `transfer_checked` and `burn` accept an approved delegate as a valid authority, any attacker holding a delegation over a victim's token account can call `init_transfer` with `from = victim_ata` and `user = attacker`, causing the victim's tokens to be locked in the vault or burned on Solana while the attacker redeems the equivalent on NEAR at an address they control.

## Finding Description
The `from` account is declared as:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
``` [1](#0-0) 

No `token::authority = user` constraint is present. The `user` account is only required to be a signer and system-program-owned:

```rust
#[account(
    mut,
    owner = common.system_program.key(),
)]
pub user: Signer<'info>,
``` [2](#0-1) 

In `process`, both CPI paths pass `self.user` as the authority:

- Native path: `authority: self.user.to_account_info()` in `TransferChecked` [3](#0-2) 

- Bridged path: `authority: self.user.to_account_info()` in `Burn` [4](#0-3) 

SPL Token's `transfer_checked` and `burn` accept either the token account's `owner` field **or** an approved `delegate` as a valid authority. The bridge never checks which case applies. After the CPI succeeds, the Wormhole message encodes `sender = self.user.key()` (attacker) and the attacker-supplied `recipient`: [5](#0-4) 

The NEAR-side finalization then releases funds to the attacker-controlled address.

## Impact Explanation
This is a direct, permanent theft of user funds routed through the bridge. Victim's SPL tokens are irreversibly locked in the vault (native path) or burned (bridged path) on Solana, and the attacker redeems the equivalent bridged tokens on NEAR at an address they control. This matches the Critical impact class: **stealing or permanent loss of bridged funds across Solana and NEAR**.

## Likelihood Explanation
The prerequisite is that the attacker holds an SPL Token delegation over the victim's token account. This is a realistic condition: users routinely grant delegations to DEX routers, lending protocols, and yield aggregators. A compromised or malicious protocol holding such a delegation can immediately exploit this path. No admin compromise, key leak, or bridge-internal privilege is required — only a valid SPL Token `approve` from the victim to any address the attacker controls. The attack is repeatable up to the delegated amount.

## Recommendation
Add `token::authority = user` to the `from` account constraint:

```rust
#[account(
    mut,
    token::mint = mint,
    token::token_program = token_program,
    token::authority = user,   // enforce owner == user
)]
pub from: Box<InterfaceAccount<'info, TokenAccount>>,
```

Anchor resolves `token::authority` against the token account's `owner` field, not the `delegate` field, so this rejects delegated-authority callers at the constraint layer before any CPI is attempted.

## Proof of Concept
1. Victim holds `victim_ata` (`owner = victim`, `mint = M`).
2. Victim calls `spl_token::approve(victim_ata, delegate = attacker, amount = X)` (e.g., via a DeFi protocol the attacker controls).
3. Attacker calls `init_transfer` with:
   - `from = victim_ata`
   - `user = attacker` (signs the transaction; system-program-owned wallet)
   - `mint = M`
   - `vault` present (native path) or absent with valid `mint_authority` (bridged path)
   - `payload.recipient = attacker_near_address`
4. Anchor constraints pass: mint matches, token_program matches, no authority check.
5. `transfer_checked` / `burn` CPI succeeds: SPL Token validates attacker as approved delegate of `victim_ata`.
6. Wormhole message posted: `sender = attacker`, `recipient = attacker_near_address`.
7. Victim's balance decreases by `payload.amount`; attacker redeems on NEAR.

**Reproducible test plan:** Deploy the program on a local validator. Mint tokens to a victim keypair. Call `spl_token::approve` granting the attacker keypair delegation. Invoke `init_transfer` signed by the attacker with `from = victim_ata`. Assert the vault receives (or mint supply decreases by) `payload.amount` and the emitted Wormhole message contains `sender = attacker` and `recipient = attacker_near_address`.
