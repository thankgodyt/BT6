### Title
Front-Running `request_refund` Allows Attacker to Redirect BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

The `request_refund` function is publicly callable by any NEAR account and uses a "first come, first served" key (`{txid}@{vout}`) to register refund requests. When a victim submits a refund request with `deposit_msg.refund_address = None` (the common case), an attacker can observe the pending transaction and front-run it with the same UTXO but a different `refund_address`, blocking the victim's request and registering the attacker's own BTC address as the refund destination.

### Finding Description

`request_refund` is a two-step async flow: the first call triggers a light-client cross-contract verification, and `request_refund_callback` stores the refund request. The storage key is `generate_utxo_storage_key(tx_id, vout)` — a deterministic string `{txid}@{vout}` — and the first callback to complete wins: [1](#0-0) [2](#0-1) 

The code itself acknowledges the race: *"another request_refund could have landed between our check and callback"*. The `request_refund` public entry point carries no `#[trusted_relayer]` guard on the function itself (unlike `verify_deposit_v2`), so any NEAR account can call it: [3](#0-2) 

When `deposit_msg.refund_address` is `None`, the callback accepts any caller-supplied `refund_address` without binding it to the original depositor: [4](#0-3) 

The stored `refund_address` is later used verbatim to build the Bitcoin output in `execute_refund` → `build_refund_output`: [5](#0-4) 

`execute_refund` is also publicly callable (no role restriction), so after the timelock the attacker can trigger the payout themselves: [6](#0-5) 

### Impact Explanation

If the attacker's callback executes before the victim's, the victim's `request_refund` call reverts with "Refund request already exists for this UTXO". The attacker's entry — with `refund_address = attacker_btc_addr` — is the only one stored. After `unsafe_refund_timelock_sec` elapses, the attacker calls `execute_refund` and the MPC pipeline sends the deposit BTC to the attacker's address. The victim's BTC is stolen. The only protocol-level mitigation is the DAO/Operator's ability to call `reject_refund` during the timelock window: [7](#0-6) 

If the DAO/Operator does not reject in time, the theft is complete. Even if they do reject, the victim's funds are temporarily locked and the victim must re-submit, creating a griefing/DoS vector.

### Likelihood Explanation

- `request_refund` is publicly callable with no role restriction.
- NEAR has an observable mempool; an attacker can watch for `request_refund` calls and submit a competing transaction in the same or next block.
- The attack is cheap: only the anti-spam storage deposit is required.
- The victim's `deposit_msg.refund_address` is `None` in the common case (the field is `skip_serializing_if = "Option::is_none"`), so the attacker can freely substitute their own `refund_address`.
- The attacker only needs to copy `deposit_msg`, `tx_bytes`, `vout`, and `proof` from the victim's observed call — all are public inputs. [8](#0-7) 

### Recommendation

1. **Bind refund address to the depositor at deposit time**: Require `deposit_msg.refund_address` to be `Some` for any refund to be eligible, eliminating the free-choice `refund_address` parameter. The current `unsafe_refund_timelock_sec` path exists precisely because the address is untrusted.
2. **Bind the refund request to the caller's NEAR account**: Store `caller = env::predecessor_account_id()` in the `RefundRequest` and require that only the original caller (or DAO/Operator) can call `execute_refund` for that request.
3. **Commit-reveal**: Require callers to first commit to a hash of `(utxo_storage_key, refund_address, nonce)` and reveal in a second step, preventing front-running.

### Proof of Concept

1. Victim calls `request_refund(deposit_msg={recipient_id: "victim.near", refund_address: None, ...}, refund_address="victim_btc_addr", tx_bytes=..., vout=0, proof=...)`.
2. Attacker observes the call in the NEAR mempool and immediately calls `request_refund(deposit_msg={recipient_id: "victim.near", refund_address: None, ...}, refund_address="attacker_btc_addr", tx_bytes=<same>, vout=0, proof=<same>)`.
3. Both trigger light-client verification. Attacker's callback executes first (same or next block, higher priority).
4. `request_refund_callback` stores `RefundRequest { refund_address: "attacker_btc_addr", ... }` under key `{txid}@0`.
5. Victim's callback hits `require!(!self.data().refund_requests.contains_key(&utxo_storage_key), "Refund request already exists for this UTXO")` and reverts.
6. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund("{txid}@0", None)`.
7. `build_refund_output` constructs a Bitcoin output paying `refund_amount` to `"attacker_btc_addr"`.
8. MPC signs and broadcasts the transaction; victim's BTC is sent to the attacker. [9](#0-8)

            ),

        }

    #[allow(clippy::too_many_arguments)]
    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
