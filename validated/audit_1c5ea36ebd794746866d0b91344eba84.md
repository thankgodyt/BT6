Audit Report

## Title
Fire-and-Forget Native-Fee Promise and Unguarded `ClaimFeeEvent` Emission Before Token Transfer in `send_fee_internal` — (`near/omni-bridge/src/lib.rs`)

## Summary

In `send_fee_internal`, the native-fee sub-transfer is dispatched with `.detach()` (result silently discarded), `ClaimFeeEvent` is logged synchronously before the token-fee cross-contract call is dispatched, and `unlock_tokens_if_needed` permanently decrements the locked-token counter before any transfer succeeds. Because `remove_transfer_message` has already executed in `claim_fee_callback`, there is no stored state to retry from. If either the native-fee or token-fee transfer fails, the relayer permanently loses their fee, the locked-token escrow counter is permanently understated, and a `ClaimFeeEvent` is committed to the chain for a payout that never occurred. The same detach-then-mutate pattern appears in `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast`, where relayer reimbursement tokens are also silently lost.

## Finding Description

**Call chain for `claim_fee`:**

```
claim_fee (#[trusted_relayer])
  → verify_proof (cross-contract)
    → claim_fee_callback (#[private])
        → remove_transfer_message   ← state permanently removed (L1094)
        → send_fee_internal
            → Promise::transfer / ext_token::mint  .detach()  ← L2665-2673, result ignored
            → env::log_str(ClaimFeeEvent)                     ← L2677-2682, committed
            → unlock_tokens_if_needed(...)                    ← L2684, counter decremented
            → ft_transfer / mint returned as PromiseOrValue   ← L2686-2698, no failure callback
```

**Issue A – Native fee is detached:** [1](#0-0) 

`Promise::new(fee_recipient).transfer(...)` and `ext_token::ext(...).mint(...).detach()` both discard their result. If the NEAR transfer fails (e.g., fee-recipient account does not exist) or the wrapped-token mint fails (e.g., out-of-gas), the native fee is silently lost.

**Issue B – `ClaimFeeEvent` emitted before token-fee transfer:** [2](#0-1) 

The event is logged synchronously, then the token-fee cross-contract call is returned: [3](#0-2) 

`claim_fee_callback` returns this `PromiseOrValue<()>` directly with no chained failure callback: [4](#0-3) 

**Issue C – `unlock_tokens_if_needed` called before transfer succeeds:** [5](#0-4) 

`unlock_tokens` permanently decrements `locked_tokens`: [6](#0-5) 

If the subsequent `ft_transfer` or `mint` fails, the locked-token counter is permanently understated — tokens remain in the contract but the escrow accounting says they are unlocked.

**Issue D – Same pattern in `process_fin_transfer_to_other_chain`:** [7](#0-6) 

`send_tokens(...).detach()` is called, `mark_fast_transfer_as_finalised` permanently mutates state, and `FinTransferEvent` is logged — all before the transfer result is known.

**Issue E – Same pattern in `utxo_fin_transfer_fast`:** [8](#0-7) 

`send_tokens(...).detach()` is called after state is permanently mutated (`remove_fast_transfer` or `mark_fast_transfer_as_finalised` at L2530/2533), and `UtxoTransferEvent` is logged with no failure handling.

**Existing guards are insufficient:** `remove_transfer_message` at L1094 executes unconditionally before `send_fee_internal` is entered. There is no re-insertion path, no escrow credit, and no retry mechanism anywhere in the callback chain. [9](#0-8) 

## Impact Explanation

Two concrete allowed impacts are triggered:

1. **Permanent loss of bridged/relayer funds:** The relayer's token fee (NEP-141 bridged tokens held by the bridge contract) is permanently lost when `ft_transfer` fails. `remove_transfer_message` has already executed; there is no stored state to retry from. In the `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast` paths, the relayer's fast-transfer reimbursement (bridged tokens they pre-funded) is also permanently lost.

2. **Escrow mis-accounting:** `unlock_tokens_if_needed` decrements `locked_tokens` before the transfer succeeds. If the transfer fails, the locked-token counter is permanently understated relative to the tokens actually held in the contract. This breaks the invariant that `locked_tokens[chain][token] == tokens committed to pending cross-chain transfers`, which the bridge relies on to enforce `ERR_INSUFFICIENT_LOCKED_TOKENS` checks on subsequent operations. [10](#0-9) 

## Likelihood Explanation

The failure condition is realistic and reachable by any account that becomes a trusted relayer (an open, permissionless process via `apply_for_trusted_relayer` with a stake): [11](#0-10) 

1. A fee recipient that has never called `storage_deposit` on the bridged token contract will cause `ft_transfer` to panic (NEP-141 requires prior storage registration). This is a normal operational condition — a relayer that is new to a token simply may not have registered.
2. Insufficient gas allocated via the static `MINT_TOKEN_GAS` / `FT_TRANSFER_GAS` constants under congestion causes silent failure.
3. A paused or blacklisting token contract panics on `ft_transfer`, silently dropping the receipt.

Any of these conditions causes the silent loss without any attacker action — the relayer triggers it themselves by calling `claim_fee` under normal operational conditions.

## Recommendation

1. **Remove `.detach()` on native-fee transfers** and chain them with the token-fee promise so a single `#[private]` callback can verify both succeeded.
2. **Move `env::log_str(ClaimFeeEvent)` into that callback**, firing only after both promises resolve successfully.
3. **Add a failure branch** in the callback that re-inserts the transfer message (or credits the fee to a claimable escrow) and re-locks the tokens via `revert_lock_actions` so the relayer can retry.
4. Apply the same pattern to `utxo_fin_transfer_fast` and `process_fin_transfer_to_other_chain`: replace `.detach()` with a chained callback that emits the event only on success and restores state on failure. Note that `revert_lock_actions` already exists for this purpose: [12](#0-11) 

## Proof of Concept

1. Any account calls `apply_for_trusted_relayer` with the required stake and waits for the activation period.
2. A cross-chain transfer with `fee.native_fee = 0` and `fee.fee > 0` (token fee only) is initiated and finalized on-chain, creating a pending transfer message.
3. The trusted relayer calls `claim_fee` for that transfer. The `fee_recipient` is the relayer's own account, which exists on NEAR but has **never called `storage_deposit`** on the bridged token contract.
4. `claim_fee_callback` executes: `remove_transfer_message` removes the transfer (L1094); `send_fee_internal` is entered.
5. `ClaimFeeEvent` is logged on-chain (L2677-2682).
6. `unlock_tokens_if_needed` decrements `locked_tokens` (L2684).
7. `ft_transfer(fee_recipient, token_fee, None)` is dispatched (L2693-2697). Because the recipient has no storage registration, the NEP-141 token contract panics and the receipt fails.
8. No callback exists to catch this failure. The failed receipt is silently dropped.
9. **Result:** transfer message is gone, `ClaimFeeEvent` is on-chain, `locked_tokens` counter is permanently understated, and the relayer received no fee.

To verify the escrow mis-accounting: after step 9, call `get_locked_tokens(destination_chain, token_id)` and observe it is lower than the sum of all remaining pending transfer amounts for that token — confirming the invariant is broken.

```rust
    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }
```

```rust
    pub fn revert_lock_actions(&mut self, lock_actions: &[LockAction]) {
        for lock_action in lock_actions {
            match lock_action {
                LockAction::Locked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.unlock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unlocked {
                    chain_kind,
                    token_id,
                    amount,
                } => {
                    self.lock_tokens(*chain_kind, token_id, *amount);
                }
                LockAction::Unchanged => {}
            }
        }
    }
```
