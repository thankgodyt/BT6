### Title
Unconditional Peras Certificate Validation Bypass Allows Any Peer to Inject Arbitrary Certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `validatePerasCert` implementation for the `BlockSupportsPeras` instance is a stub that unconditionally returns `Right` (success) for every certificate it receives, performing zero cryptographic or quorum verification. This is wired directly into the live miniprotocol inbound-certificate pipeline. An unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and boosted block, and the node will accept it without any BLS aggregate-signature check, voter eligibility check, or quorum threshold check.

---

### Finding Description

In `Ouroboros/Consensus/Block/SupportsPeras.hs`, the `BlockSupportsPeras` instance's `validatePerasCert` method is a placeholder that always succeeds:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is not confined to tests. It is wired into the production certificate inbound pipeline via `makePerasCertPoolWriterFromChainDB` and `makePerasCertPoolWriterFromCertDB`, both of which pass `validatePerasCert mkPerasParams` as the validation callback to `processCerts`:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

`processCerts` is the function that handles every batch of inbound `PerasCert` objects received from a remote peer. It calls `validateCert` on each certificate and, if all pass, timestamps and stores them:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [4](#0-3) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted unconditionally.

The concrete Peras certificate type (`V1.PerasCert`) carries a `pcVoters` bitmap, an aggregate BLS signature (`pcSignature`), a round number, and a boosted block hash. None of these fields are checked. The full verification logic that *should* be applied is implemented in `implVerifyCert` for the `WFALS` and `EveryoneVotes` committee schemes, which checks persistent/non-persistent voter eligibility, BLS aggregate signature validity, and VRF outputs — but this path is never reached from the inbound pipeline. [5](#0-4) 

---

### Impact Explanation

A Peras certificate boosts the chain-selection weight of the block it certifies by `perasWeight` (a `Word64` addend). An adversary who can inject a fake certificate for an arbitrary block can cause an honest node to assign inflated chain-selection weight to a non-canonical or adversarially chosen block, making the node prefer a weaker or attacker-controlled chain over the honest chain. This directly undermines the Peras fast-finality guarantee and constitutes a **bypass of Peras certificate validation enabling unauthorized certificate acceptance** and a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain**.

---

### Likelihood Explanation

The attack requires only a network connection to the node's Peras certificate miniprotocol endpoint. No keys, stake, or privileged access are needed. The attacker constructs a `PerasCert` CBOR payload with a chosen `pcRoundNo` and `pcBoostedBlock`, sends it over the miniprotocol, and the node accepts it. The `processCerts` path is exercised for every inbound certificate batch, so the vulnerable code is on the hot path for any node running with Peras enabled.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS signature in `pcSignature` against the aggregated voter verification keys derived from `pcVoters`.
2. Checks that each voter in `pcVoters` is a legitimate committee member with a valid eligibility proof (persistent or non-persistent VRF output).
3. Verifies that the total stake of the voters meets the quorum threshold (`perasQuorumStakeThreshold`).
4. Validates the round number and boosted block against the current ledger state.

Until this is implemented, the Peras certificate miniprotocol endpoint should not be exposed to untrusted peers in any deployment.

---

### Proof of Concept

1. Connect to a node's Peras certificate miniprotocol endpoint.
2. Craft a CBOR-encoded `PerasCert` with:
   - `pcRoundNo`: any target round number
   - `pcBoostedBlock`: the hash of an adversarially chosen block
   - `pcVoters`: a minimal non-empty `PerasCertVoters` bitmap (e.g., one bit set, zero non-persistent sigs)
   - `pcSignature`: any bytes (not checked)
3. Send the certificate as a batch via the miniprotocol.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
5. The certificate is stored in the `PerasCertDB` / `ChainDB` and the adversarially chosen block receives a `perasWeight` boost in chain selection. [6](#0-5) [7](#0-6)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool

      mapM_
        (addCert . WithArrivalTime now)
