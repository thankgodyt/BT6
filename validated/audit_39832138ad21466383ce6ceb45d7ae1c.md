### Title
Gas Limit Enforcement Bypass via `gas: None` in `post_actions` Deposit Messages — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

### Summary

The `check_deposit_msg` function enforces three hardcoded gas constants (`MIN_PER_POST_ACTIONS_GAS = 30 Tgas`, `MAX_PER_POST_ACTIONS_GAS = 100 Tgas`, `MAX_TOTAL_POST_ACTIONS_GAS = 130 Tgas`) only when a `PostAction`'s `gas` field is `Some`. When `gas` is `None`, all three checks are silently skipped, creating a direct discrepancy between the hardcoded limits and the actual runtime gas consumed — the same class of bug as the Etherlink report.

### Finding Description

In `check_deposit_msg`, the gas validation block is guarded by `if let Some(gas) = post_action.gas`: [1](#0-0) 

When `gas` is `None`, `total_gas` is never incremented and neither the per-action nor the total cap is checked. A user-controlled `DepositMsg` with one or two `PostAction` entries each carrying `gas: None` passes all validation and is forwarded to the nBTC contract.

In `nbtc/src/lib.rs`, `handle_post_actions` dispatches the call **without** `with_static_gas` when `gas` is `None`: [2](#0-1) 

The `handle_post_action` entry point then checks: [3](#0-2) 

Because no static gas was attached, `env::prepaid_gas()` reflects only the default (effectively 0 or whatever the NEAR SDK assigns when no gas is specified), which is below `GAS_FOR_FT_TRANSFER_CALL = 30 Tgas`, causing a panic. The panic fires inside a `.detach()`-ed receipt, so the mint already succeeded and the state is inconsistent: tokens are minted but the post_action never executes.

The hardcoded constants that are supposed to govern this path: [4](#0-3) 

are never consulted for `gas: None` entries, making the enforcement purely nominal for that code path.

### Impact Explanation

**Low.** This is a publicly reachable invariant violation in the production deposit path. The gas-limit invariant (`30 Tgas ≤ per-action gas ≤ 100 Tgas`, `total ≤ 130 Tgas`) is silently bypassed. The concrete consequence is a panic-driven fault inside `handle_post_action`: the token transfer inside the post_action never executes, leaving the user's minted nBTC in their account rather than forwarded to the intended dApp receiver. No funds are lost (tokens remain with the recipient), but the bridge's stated post_action semantics are broken for any deposit that uses `gas: None`.

### Likelihood Explanation

High. The `DepositMsg` is constructed entirely by the depositing user and embedded in the BTC transaction before the relayer submits it. Any unprivileged user can set `gas: None` on any `PostAction`. The `gas` field is explicitly `Option<Gas>` and `skip_serializing_if = "Option::is_none"`, so omitting it is the natural default for users who do not read the gas-limit documentation. [5](#0-4) 

### Recommendation

Remove the `Option` wrapping from the gas enforcement path, or treat `gas: None` as equivalent to `gas: Some(MIN_PER_POST_ACTIONS_GAS)` (i.e., assign a default and apply all three checks unconditionally). The simplest fix is to require `gas` to be `Some` for every `PostAction` and reject any entry where it is absent, mirroring the intent of the existing constants.

### Proof of Concept

1. User constructs a `DepositMsg` with one `PostAction` where `gas` is omitted:
   ```json
   {
     "recipient_id": "alice.near",
     "post_actions": [{
       "receiver_id": "whitelisted-dapp.near",
       "amount": "10000",
       "msg": ""
     }]
   }
   ```
2. Relayer calls `verify_deposit` with this message. `check_deposit_msg` iterates the post_actions; the `if let Some(gas)` branch is never entered; `total_gas` stays 0; all three cap checks pass trivially.
3. The bridge calls `nbtc.mint(..., post_actions)`. `mint` calls `handle_post_actions` with `.detach()`.
4. `handle_post_actions` dispatches `handle_post_action` without `with_static_gas`; the receipt receives 0 (or near-0) gas.
5. `handle_post_action` panics at `require!(env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL, "More gas is required")`.
6. The panic is inside a detached receipt; the mint callback already recorded the UTXO and minted tokens. The post_action silently fails. [6](#0-5) [7](#0-6)

    pub fn handle_post_actions(&mut self, sender_id: AccountId, post_actions: Vec<PostAction>) {
        for post_action in post_actions {
            let PostAction {
                receiver_id,
                amount,
                memo,
                msg,
                gas,
            } = post_action;
            if let Some(gas) = gas {
                Self::ext(env::current_account_id())
                    .with_static_gas(gas)
                    .handle_post_action(sender_id.clone(), receiver_id, amount, memo, msg)
                    .detach();
            } else {
                Self::ext(env::current_account_id())
                    .handle_post_action(sender_id.clone(), receiver_id, amount, memo, msg)
                    .detach();
            }
        }
    }

    #[private]
    pub fn handle_post_action(
        &mut self,
        sender_id: AccountId,
        receiver_id: AccountId,
        amount: U128,
        memo: Option<String>,
        msg: String,
    ) {
        require!(
            env::prepaid_gas() > GAS_FOR_FT_TRANSFER_CALL,
            "More gas is required"
        );
        require!(
            receiver_id != self.bridge_id,
            "handle_post_action: receiver_id must not be the bridge"
        );
        let amount = amount.into();
        self.token
            .internal_transfer(&sender_id, &receiver_id, amount, memo);
        let receiver_gas = env::prepaid_gas()
            .checked_sub(GAS_FOR_FT_TRANSFER_CALL)
            .unwrap_or_else(|| env::panic_str("Prepaid gas overflow"));
        // Initiating receiver's call and the callback
        ext_ft_receiver::ext(receiver_id.clone())
            .with_static_gas(receiver_gas)
            .ft_on_transfer(sender_id.clone(), amount.into(), msg)
            .then(
                ext_ft_resolver::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_RESOLVE_TRANSFER)
                    .ft_resolve_transfer(sender_id, receiver_id, amount.into()),
            )
            .detach();
