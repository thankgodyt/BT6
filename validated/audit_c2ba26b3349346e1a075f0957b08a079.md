### Title
Peras Vote and Certificate Validation Bypass via Incomplete Checks in `validatePerasVote` / `validatePerasCert` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance, which is the **only** `BlockSupportsPeras` instance in the codebase and is wired into the production object-diffusion mini-protocol handlers, contains two incomplete validation checks that are directly analogous to the external report's root cause:

1. `validatePerasCert` unconditionally returns `Right` — it performs **zero** validation on any inbound certificate.
2. `validatePerasVote` checks only that the voter ID appears in the stake distribution, but **never verifies the cryptographic signature** of the vote.

Both functions are called on data received from unprivileged peers via `processVotes` / `processCerts`, which are invoked by `makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB`.

---

### Finding Description

**Root cause — `validatePerasCert` (complete bypass):**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

Every certificate received from any peer is unconditionally accepted and stamped with a boost weight. No round-number bounds, no aggregate-signature check, no boosted-block existence check. [1](#0-0) 

**Root cause — `validatePerasVote` (incomplete check):**

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

The only check performed is `lookupPerasVoteStake` — i.e., "is this voter ID present in the stake distribution?" The cryptographic signature of the vote is **never verified**. The degenerate `PerasVote` data type does not even carry a signature field, whereas the concrete `V1.PerasVote` type (in `Peras/Vote/V1.hs`) does carry `pvSignature :: VoteSignature PerasBLSCrypto`. [2](#0-1) 

The concrete vote type that carries the BLS signature is defined separately but is not connected to the validation path: [3](#0-2) 

The `CryptoSupportsVoteSigning` interface that provides `verifyVoteSignature` exists and is implemented for `PerasBLSCrypto`, but is never called from `validatePerasVote`: [4](#0-3) 

**Production entry path:**

`makePerasVotePoolWriterFromChainDB` and `makePerasCertPoolWriterFromChainDB` are the production writers that receive objects from peers via the object-diffusion mini-protocol. Both call the stub validators: [5](#0-4) [6](#0-5) 

`processVotes` and `processCerts` call these validators on every inbound object before storing it: [7](#0-6) [8](#0-7) 

The only `BlockSupportsPeras` instance in the entire codebase is the degenerate one: [9](#0-8)

### Impact Explanation

**Certificate bypass (Critical):** `validatePerasCert` always returns `Right`. Any peer can send a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The certificate is stored in the `PerasCertDB` / `ChainDB` and assigned a `vpcCertBoost = perasWeight params`. Because Peras certificates boost blocks during chain selection, an attacker can inject certificates that cause an honest node to prefer an attacker-chosen block over the canonical chain — a direct chain-selection safety failure.

**Vote bypass (Critical):** `validatePerasVote` accepts any vote whose `pvVoteVoterId` appears in the stake distribution, without verifying the BLS signature. An attacker who knows the public voter IDs (which are derived from the stake distribution, a public ledger object) can craft votes for any committee member. By sending enough such forged votes to reach the quorum threshold (`votesReachQuorum`), the node's own `PerasVoteDB` will forge a certificate internally via `updatePerasRoundVoteStates`, boosting an attacker-chosen block. [10](#0-9) 

Both paths bypass the Peras voting/certificate authorization checks that are the security foundation of the Peras protocol, enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The object-diffusion mini-protocol is a peer-facing network protocol. Any node connected to the Cardano network can send crafted `PerasVote` and `PerasCert` objects. The voter IDs required to pass the stake-distribution check are public (derivable from the ledger state). No keys, operator access, or stake majority are required. The attack is fully executable by an unprivileged peer once the Peras object-diffusion handlers are active.

---

### Recommendation

1. **`validatePerasCert`**: Implement actual certificate validation — verify the aggregate BLS signature over the boosted block and round number, check that the round number is within the valid window, and verify that the boosted block exists on a known chain.

2. **`validatePerasVote`**: Add cryptographic signature verification using `verifyVoteSignature` from `CryptoSupportsVoteSigning`. The concrete `V1.PerasVote` type already carries `pvSignature`; the degenerate `PerasVote` data type must be replaced with the concrete type and the signature check must be added before a vote is accepted.

3. Connect the concrete `V1.PerasVote` type (which carries `pvSignature`) to the validation path instead of the signatureless degenerate type.

4. Track resolution of [cardano-peras#120](https://github.com/tweag/cardano-peras/issues/120) and [cardano-peras#73](https://github.com/tweag/cardano-peras/issues/73) as blocking issues before enabling Peras in any production environment.

---

### Proof of Concept

An attacker node connected via the object-diffusion mini-protocol:

1. Reads the current `PerasVoteStakeDistr` from the ledger (public data) to enumerate valid `PerasVoterId` values.
2. Constructs `N` `PerasVote` objects — one per committee seat — each with `pvVoteRound = targetRound`, `pvVoteBlock = attackerChosenBlock`, and `pvVoteVoterId = knownVoterId_i`. No valid signature is needed because `validatePerasVote` never calls `verifyVoteSignature`.
3. Sends the batch to the victim node via the vote object-diffusion protocol. `processVotes` calls `validatePerasVote` on each; all pass because each voter ID is in the stake distribution.
4. Once `votesReachQuorum` is satisfied, `updatePerasRoundVoteStates` forges a `ValidatedPerasCert` boosting `attackerChosenBlock`.
5. Alternatively, the attacker directly sends a `PerasCert{pcCertRound, pcCertBoostedBlock = attackerChosenBlock}` via the cert object-diffusion protocol. `validatePerasCert` returns `Right` unconditionally; the cert is stored with `vpcCertBoost = perasWeight params`.
6. The boosted certificate influences chain selection, causing the honest node to prefer `attackerChosenBlock`. [11](#0-10)

votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
  allVotesMatchTarget target =
    all ((== (getPerasVoteTarget target)) . getPerasVoteTarget)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
