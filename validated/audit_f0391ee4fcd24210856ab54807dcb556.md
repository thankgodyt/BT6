### Title
`revalidateHeader` Silently Discards Envelope Validation Result in Production Builds — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/HeaderValidation.hs`)

---

### Summary

`revalidateHeader` computes a full `validateEnvelope` result and passes it to `assertWithMsg`. However, `assertWithMsg` is a **compile-time no-op in production builds** (i.e., when `ENABLE_ASSERTIONS` is not set). The envelope check return value is therefore silently discarded in every production deployment, meaning `revalidateHeader` performs **zero envelope validation** at runtime. This is the direct structural analog of the Augur `onTransferOwnership` bug: a function returns a status value that is supposed to gate a security-critical operation, but the caller ignores it.

---

### Finding Description

`revalidateHeader` is the "fast-path" re-validation function used during block re-application (e.g., replaying blocks from the ImmutableDB on startup via `reapplyBlockLedgerResult`). It is defined as:

```haskell
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
 where
  envelopeCheck =
    runExcept $ withExcept show $
      validateEnvelope cfg ledgerView (untickedHeaderStateTip st) hdr
``` [1](#0-0) 

`assertWithMsg` is defined as:

```haskell
assertWithMsg :: HasCallStack => Either String () -> a -> a
#if ENABLE_ASSERTIONS
assertWithMsg (Left msg) _ = error msg
#endif
assertWithMsg _ a = a
``` [2](#0-1) 

The `#if ENABLE_ASSERTIONS` guard means the `Left msg -> error msg` branch is **compiled out in production**. The fallthrough `assertWithMsg _ a = a` unconditionally returns `a`, making the entire `envelopeCheck` computation a dead expression. The `validateEnvelope` call — which checks block number sequence, slot ordering, and prev-hash chain linkage — is evaluated but its result is thrown away. [3](#0-2) 

`revalidateHeader` is called from `reapplyBlockLedgerResult` in `ExtLedgerState`:

```haskell
reapplyBlockLedgerResult evs cfg blk TickedExtLedgerState{..} =
    (\l -> ExtLedgerState l hdr) <$> castLedgerResult ledgerResult
  where
    hdr = revalidateHeader (getExtLedgerCfg cfg) ledgerView (getHeader blk) tickedHeaderState
``` [4](#0-3) 

`reapplyBlockLedgerResult` is the path used to replay blocks from the ImmutableDB during node startup. The ImmutableDB's own integrity check (`checkIntegrity` / `nodeCheckIntegrity`) verifies CRC and cryptographic signatures, but **does not verify envelope fields** (block number, slot number, prev-hash linkage). Those checks are the exclusive responsibility of `validateEnvelope`, which is now silently bypassed. [5](#0-4) 

---

### Impact Explanation

In production builds, `revalidateHeader` constructs a new `HeaderState` (and thus a new `ExtLedgerState`) without enforcing any of the following envelope invariants:

- Block numbers are consecutive (`UnexpectedBlockNo`)
- Slot numbers are strictly increasing (`UnexpectedSlotNo`)
- The `prevHash` field of the new block matches the hash of the current tip (`UnexpectedPrevHash`)
- Checkpoint hash matches (`CheckpointMismatch`) [6](#0-5) 

If a block with a crafted or corrupted envelope (valid signature/CRC but wrong block number, slot, or prev-hash) is stored in the ImmutableDB or included in a loaded snapshot, the node will silently accept it during replay and persist the resulting invalid `ExtLedgerState` as its canonical ledger state. This constitutes durable use of a wrong ledger state — a ChainDB/LedgerDB corruption impact.

---

### Likelihood Explanation

The attack requires placing a crafted block into the ImmutableDB or a snapshot file that the node will load. Realistic entry paths include:

1. **Snapshot loading**: The `snapshot-converter` tool and LedgerDB snapshot loading accept on-disk snapshot files. A snapshot sourced from an untrusted peer (e.g., in a Genesis bootstrap scenario) or a compromised distribution channel could contain blocks with invalid envelopes that pass `checkIntegrity` but fail `validateEnvelope`.
2. **ImmutableDB corruption**: A block that passes CRC and signature checks but has a manipulated block number or prev-hash field would not be caught by `checkIntegrity` and would slip through `revalidateHeader` silently.

The likelihood is **medium**: it requires write access to on-disk storage or control over a snapshot source, but does not require stake majority, key compromise, or protocol-level privileges.

---

### Recommendation

Replace the `assertWithMsg` guard in `revalidateHeader` with an unconditional error, or restructure the function to return `Either` and propagate the failure, consistent with how `validateHeader` handles the same check:

```haskell
-- Current (broken in production):
revalidateHeader cfg ledgerView hdr st =
  assertWithMsg envelopeCheck $
    HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'

-- Recommended:
revalidateHeader cfg ledgerView hdr st =
  case envelopeCheck of
    Left err -> error ("revalidateHeader: envelope check failed: " <> err)
    Right () -> HeaderState (NotOrigin (getAnnTip hdr)) chainDepState'
```

This mirrors the fix applied in the Augur codebase: the return value of the validation sub-function must be unconditionally enforced, not gated behind a compile-time flag.

---

### Proof of Concept

1. Compile `ouroboros-consensus` **without** `-DENABLE_ASSERTIONS` (the default production build).
2. Construct a `ByronBlock` or `ShelleyBlock` whose header has a valid KES/VRF signature and correct CRC (so `nodeCheckIntegrity` returns `True`) but whose `blockNo` field is set to an arbitrary value (e.g., `BlockNo 9999`) inconsistent with the chain tip.
3. Write this block into the ImmutableDB chunk file at the position of a legitimate block.
4. Start the node. During startup, `reapplyBlockLedgerResult` is called for each ImmutableDB block. `revalidateHeader` is invoked; `envelopeCheck` evaluates to `Left "UnexpectedBlockNo ..."`, but `assertWithMsg` discards this result and returns the constructed `HeaderState` unconditionally.
5. The node proceeds with an `ExtLedgerState` whose `headerState` records `BlockNo 9999` as the tip, diverging from the true chain state. [7](#0-6) [2](#0-1) [4](#0-3)
