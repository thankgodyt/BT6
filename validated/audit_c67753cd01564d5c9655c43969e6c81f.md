Audit Report

## Title
Fees Permanently Frozen When Fee-Recipient Relayer Loses Trusted Status - (File: near/omni-bridge/src/lib.rs)

## Summary
`claim_fee()` enforces two independent guards: a `#[trusted_relayer]` macro (Guard 1) and an inner `fee_recipient == predecessor_account_id` equality check (Guard 2). When the designated `fee_recipient` loses trusted-relayer status — via `resign_trusted_relayer` or DAO calling `reject_relayer_application` — no account can satisfy both guards simultaneously. The `pending_transfers` entry is never removed, and the fee tokens (burned or locked on NEAR at `init_transfer`) are permanently frozen with no rescue path.

## Finding Description
The NEAR → EVM transfer flow burns or locks the full user amount (including fee) at `init_transfer`. A trusted relayer calls `sign_transfer`, embedding `fee_recipient` into the MPC-signed `TransferMessagePayload`. After EVM finalization, the relayer calls `claim_fee()` to collect the fee.

`claim_fee()` is decorated with `#[trusted_relayer]`:

```rust
// near/omni-bridge/src/lib.rs:1054-1064
#[payable]
#[trusted_relayer]
#[pause(except(roles(Role::DAO)))]
pub fn claim_fee(&mut self, #[serializer(borsh)] args: ClaimFeeArgs) -> Promise { ... }
```

The macro is configured with bypass roles `Role::DAO` and `Role::UnrestrictedRelayer`:

```rust
// near/omni-bridge/src/lib.rs:245-249
#[trusted_relayer(
    bypass_roles(Role::DAO, Role::UnrestrictedRelayer),
    manager_roles(Role::DAO, Role::RelayerManager),
    config_roles(Role::DAO)
)]
```

Inside `claim_fee_callback`, Guard 2 requires the caller to be the exact `fee_recipient` embedded in the proof:

```rust
// near/omni-bridge/src/lib.rs:1083-1086
require!(
    fee_recipient == *predecessor_account_id,
    BridgeError::OnlyFeeRecipientCanClaim.as_ref()
);
```

If the `fee_recipient` loses trusted status (confirmed reachable via `resign_trusted_relayer` and `reject_relayer_application` as shown in `near/omni-tests/src/relayer_staking.rs`):

- The `fee_recipient` fails Guard 1 (no longer trusted, no bypass role).
- DAO bypasses Guard 1 but fails Guard 2 (`fee_recipient != DAO account`).
- `UnrestrictedRelayer` bypasses Guard 1 but fails Guard 2 (`fee_recipient != UnrestrictedRelayer account`).

No account can satisfy both guards simultaneously. `remove_transfer_message` (lines 2194–2211) is only called inside `claim_fee_callback` after both guards pass, so the `pending_transfers` entry is never removed and the fee tokens are permanently frozen.

## Impact Explanation
For deployed tokens, the fee portion was burned on NEAR at `init_transfer` and is never minted to anyone — permanently destroyed. For locked tokens, the fee portion remains locked in `locked_tokens` accounting forever. This constitutes permanent freezing of bridged funds, matching the Critical allowed impact scope. The `pending_transfers` entry also persists indefinitely, permanently consuming storage.

## Likelihood Explanation
Low-to-medium. The scenario requires the `fee_recipient` to lose trusted status between `sign_transfer` and `claim_fee`. Both triggering paths are normal protocol operations requiring no adversarial precondition: a relayer can call `resign_trusted_relayer` before claiming pending fees (self-triggered), or the DAO can call `reject_relayer_application` on an active relayer with unclaimed fees (confirmed by `test_dao_revoke_active_relayer` in `near/omni-tests/src/relayer_staking.rs`). The window is typically short but is not bounded by any protocol mechanism.

## Recommendation
Remove `#[trusted_relayer]` from `claim_fee()`. The proof already cryptographically binds `fee_recipient` to the EVM finalization event; the `fee_recipient == predecessor_account_id` check in the callback is sufficient to ensure only the correct party claims the fee. The trusted-relayer guard is redundant at claim time and creates an irrecoverable deadlock. Alternatively, add a DAO-callable rescue function that, given a `TransferId`, distributes the fee to the recorded `fee_recipient` without requiring the caller to be the `fee_recipient`.

## Proof of Concept
```
1. Trusted relayer R calls sign_transfer(transfer_id, fee_recipient=R, fee=X).
   → MPC signs payload with fee_recipient=R embedded.
   → pending_transfers[transfer_id] holds full amount including X.

2. EVM finalizes: recipient receives (amount - X) tokens.

3. R calls resign_trusted_relayer() (or DAO calls reject_relayer_application(R)).
   → R is no longer a trusted relayer.

4. R calls claim_fee(proof_of_evm_finalization).
   → #[trusted_relayer] macro rejects R: not a trusted relayer.
   → Fee X is permanently stuck.

5. DAO calls claim_fee(proof_of_evm_finalization).
   → #[trusted_relayer] passes (DAO has bypass_role).
   → claim_fee_callback: require!(fee_recipient == predecessor_account_id)
      → fee_recipient = R, predecessor = DAO → PANIC.
   → Fee X is permanently stuck.

6. No code path exists to remove pending_transfers[transfer_id]
   or distribute the fee. Tokens are frozen forever.
```
