Audit Report

## Title
`is_refund_required` Ignores Promise Result for Plain `ft_transfer`, Permanently Finalizing Failed Inbound Transfers — (`near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call == false`, without inspecting the promise result. When `send_tokens` dispatches a plain `ft_transfer` (non-deployed token, empty `msg`), any failure of that promise is silently treated as success. `fin_transfer_send_tokens_callback` then enters the success branch: it pays the relayer fee, emits `FinTransferEvent`, and never calls `revert_lock_actions` or `remove_fin_transfer`. The transfer is permanently finalized while the recipient receives nothing and the source-chain escrow is irrecoverably decremented.

## Finding Description

`send_tokens` dispatches `ft_transfer` (not `ft_transfer_call`) when the token is non-deployed and `msg` is empty:

```rust
} else if msg.is_empty() {
    ext_token::ext(token)
        .with_attached_deposit(ONE_YOCTO)
        .with_static_gas(FT_TRANSFER_GAS)
        .ft_transfer(recipient, amount, None)
``` [1](#0-0) 

The callback is registered with `is_ft_transfer_call = !msg.is_empty()`, which evaluates to `false`: [2](#0-1) 

`is_refund_required` never reads the promise result in this branch:

```rust
} else {
    // Not ft_transfer_call: don't refund
    false
}
``` [3](#0-2) 

So when `ft_transfer` fails, `fin_transfer_send_tokens_callback` enters the `else` (success) branch unconditionally: [4](#0-3) 

In that branch the callback pays the relayer fee and emits `FinTransferEvent` but never calls `revert_lock_actions` or `remove_fin_transfer`. The transfer ID was already inserted into `finalised_transfers` at the top of `process_fin_transfer_to_near`: [5](#0-4) 

And `locked_tokens` was already decremented by `unlock_tokens_if_needed` in the same function: [6](#0-5) 

The same blind spot exists in `resolve_utxo_fin_transfer` — when `msg` is empty, `is_ft_transfer_call` is `false`, `is_refund_required` returns `false`, and `remove_fin_utxo_transfer` is never called on failure: [7](#0-6) 

And in `resolve_fast_transfer`, `burn_tokens_if_needed` is called unconditionally before the (also blind) refund check: [8](#0-7) 

## Impact Explanation

For the `fin_transfer_send_tokens_callback` path (inbound EVM/Wormhole/MPC transfer to NEAR, non-deployed token, empty `msg`):

- `finalised_transfers` permanently contains the transfer ID — replay is impossible.
- `locked_tokens` for the origin chain is decremented but the tokens are never released to the recipient — this is a concrete escrow mis-accounting.
- The relayer collects the fee for a transfer that delivered nothing.
- The user's bridged funds are permanently frozen: burned/locked on the source chain, undelivered on NEAR, with no recovery path.

This matches the Critical impact class: **permanent freezing of bridged funds** and **escrow mis-accounting that changes user balances**.

## Likelihood Explanation

`ft_transfer` can fail without any privileged compromise:

1. **Token contract paused by its own governance** — the bridge has no control over third-party NEP-141 contracts; a governance pause on the token side causes every in-flight `ft_transfer` to fail.
2. **Recipient account deleted** — NEAR accounts can be deleted; if the recipient account no longer exists at settlement time, `ft_transfer` panics inside the token contract.
3. **Token contract upgrade introduces a panic** — a routine upgrade between proof submission and callback execution can cause `ft_transfer` to revert.

None of these require compromising any privileged key. The condition is reachable by any unprivileged external user or by ordinary external events (token governance, account lifecycle).

## Recommendation

`is_refund_required` must inspect the promise result for the non-`ft_transfer_call` path:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                near_sdk::serde_json::from_slice::<U128>(&value)
                    .map_or(false, |amount| amount.0 == 0)
            }
            Err(_) => false,
        }
    } else {
        // Plain ft_transfer or mint: treat any promise failure as requiring revert
        env::promise_result_checked(0, 0).is_err()
    }
}
```

Additionally, `resolve_fast_transfer` should move `burn_tokens_if_needed` inside the success branch only, so a failed `mint`/`ft_transfer` does not burn the relayer's collateral while leaving the fast-transfer record in place. [9](#0-8) 

## Proof of Concept

1. Alice initiates a transfer of 1,000 USDC from Ethereum to `alice.near` with an empty `msg`. The EVM bridge contract locks 1,000 USDC.
2. A relayer submits the proof via `fin_transfer`. `process_fin_transfer_to_near` runs: the transfer ID is inserted into `finalised_transfers`, `locked_tokens[Eth][usdc]` is decremented by 1,000, and `ft_transfer(alice.near, 1000)` is dispatched to the USDC token contract.
3. Between step 2 and the callback, the USDC token contract is paused by its own governance (or `alice.near` is deleted). The `ft_transfer` promise fails.
4. `fin_transfer_send_tokens_callback` is called with `is_ft_transfer_call = false`. `is_refund_required(false)` returns `false` without reading the promise result. The else branch fires: the relayer's fee is paid, `FinTransferEvent` is emitted.
5. Result: `finalised_transfers` contains the transfer ID (no replay possible), `locked_tokens` is permanently decremented, Alice receives 0 USDC. The 1,000 USDC remain locked on Ethereum with no recovery mechanism.

A local integration test can reproduce this by deploying a mock NEP-141 that panics on `ft_transfer`, submitting a valid inbound proof, and asserting that `finalised_transfers` contains the transfer ID while the recipient balance remains zero and no `FailedFinTransferEvent` is emitted.
