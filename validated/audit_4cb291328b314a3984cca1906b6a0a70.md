### Title
`validatePerasCert` Accepts All Peer-Supplied Peras Certificates Without Cryptographic Verification, Enabling Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary
The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally accepts every inbound Peras certificate without performing any cryptographic verification. Any unprivileged peer can craft and send a `PerasCert` message that will be accepted, stored in the ChainDB, and used to apply a Peras weight boost to an arbitrary block during chain selection, potentially causing an honest node to prefer a non-canonical chain. The analog to the external report is direct: `deposit()` uses `isValidDNft()` (checks if DNft exists) instead of `isDNftOwner()` (checks if caller owns it); here, `validatePerasCert` uses no check at all instead of aggregate BLS signature verification, allowing any peer to inject fake certificates on behalf of any quorum of committee members.

### Finding Description
The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must authenticate a certificate before it is stored and acted upon. The universal production instance at `SupportsPeras.hs` lines 318–389 provides a degenerate implementation explicitly marked as a TODO stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This function ignores the certificate's contents entirely and returns `Right` for every input. [1](#0-0) 

This is the only `BlockSupportsPeras` instance in the codebase — it is a universal instance covering all `StandardHash blk` types, meaning it is the production implementation for all block types including Cardano blocks. [2](#0-1) 

The function is called directly from the network inbound path:

**Step 1.** `hPerasCertDiffusionClient` in `NodeToNode.hs` registers `makePerasCertPoolWriterFromChainDB` as the handler for all inbound Peras certificates received from peers. [3](#0-2) 

**Step 2.** `makePerasCertPoolWriterFromChainDB` in `PerasCert.hs` passes `(validatePerasCert mkPerasParams)` as the validation function to `processCerts`. [4](#0-3) 

**Step 3.** `processCerts` calls this validation function for each received certificate. Since `validatePerasCert` always returns `Right`, every certificate passes. [5](#0-4) 

**Step 4.** The accepted certificate is added to the ChainDB via `addPerasCertAsync`, which triggers chain selection with a Peras weight boost for the boosted block. [6](#0-5) 

The correct check that is missing is aggregate BLS signature verification. The `implVerifyCert` function in `WFALS.hs` demonstrates what proper certificate verification looks like — it verifies the aggregate BLS signature against the claimed committee members' public keys and validates VRF outputs for non-persistent voters. [7](#0-6) 

A secondary related issue exists in `validatePerasVote`, which checks only whether the voter's seat index maps to an entry in the stake distribution (an existence check) but does not verify the BLS vote signature — the exact "existence check vs. ownership check" pattern from the external report. However, the production `NodeToNode.hs` handler currently passes `(pure (PerasVoteStakeDistr mempty))` as the stake distribution, which causes all votes to fail validation and acts as an accidental mitigation. No such mitigation exists for `validatePerasCert`. [8](#0-7) 

### Impact Explanation
An unprivileged peer can inject a `PerasCert` claiming to boost any block of their choice. The ChainDB stores this certificate and applies a Peras weight boost to the claimed block during chain selection. This can cause an honest node to prefer a non-canonical chain (one with a fake Peras weight boost) over the honest chain. This is a **High** impact chain selection manipulation: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol.

### Likelihood Explanation
The attack requires only a network connection to the target node. No special privileges, keys, or stake are required. The attacker simply sends a crafted `PerasCert` message via the Peras cert diffusion protocol. The attack is trivially reproducible in a private testnet running this code with Peras enabled, and would be effective on any production node once Peras is activated.

### Recommendation
Implement proper certificate validation in `validatePerasCert` that:
1. Verifies the aggregate BLS signature against the claimed committee members' public keys (using `verifyAggregateVoteSignature` from `CryptoSupportsAggregateVoteSigning`).
2. Verifies that the claimed voters are eligible committee members with sufficient stake to reach quorum.
3. Verifies VRF outputs for non-persistent voters.

The `implVerifyCert` function in `WFALS.hs` provides a reference implementation that should be adapted for use here. [9](#0-8) 

Similarly, `validatePerasVote` must be updated to verify the BLS vote signature using `verifyVoteSignature` before accepting a vote as valid. [10](#0-9) 

### Proof of Concept
1. Connect to a target node as a peer via the Peras cert diffusion protocol (`hPerasCertDiffusionClient`).
2. Send a crafted `PerasCert` with `pcCertRound = <target round>` and `pcCertBoostedBlock = <adversarial block hash>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally — no signature is checked.
4. The certificate is timestamped and added to the ChainDB via `addPerasCertAsync`.
5. Chain selection runs with a Peras weight boost applied to the adversarial block.
6. If the adversarial chain with the fake boost is heavier than the current selection, the node switches to it, accepting a non-canonical chain.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do

  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)

implVerifyCert ::
  forall crypto.
  ( CryptoSupportsAggregateVoteSigning crypto
  , CryptoSupportsBatchVRFVerification crypto
  ) =>
  VotingCommittee crypto WFALS ->
  Cert crypto WFALS ->
  Either
    (VotingCommitteeError crypto WFALS)
    (NE [EligibilityWitness crypto WFALS])
implVerifyCert committee = \case
  WFALSCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    -- 3. optionally, their VRF verification keys and outputs (to verify the
    --    aggregate VRF output for non-persistent voters, if any)
    (members, voteVerificationKeys, optionalVRFKeysAndOutputs) <-
      fmap nonEmptyUnzip3 . flip traverse (NEMap.toAscList voters) $ \case
        -- Persistent voter
        (seatIndex, Nothing)
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee)
          , isPersistentMember seatIndex committee -> do
              let voterVoteVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              pure
                ( WFALSPersistentMember
                    seatIndex
                    voterStake
                , voterVoteVerificationKey
                , Nothing
                )
          | otherwise ->
              Left (NotAPersistentMember seatIndex)
