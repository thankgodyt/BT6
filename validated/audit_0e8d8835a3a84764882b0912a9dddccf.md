### Title
Missing `recipient_id` Validation Allows nBTC to Be Permanently Minted to Bridge Contract — (File: `contracts/satoshi-bridge/src/deposit_msg.rs`)

---

### Summary

The `DepositMsg.recipient_id` field — the NEAR account that receives minted nBTC — is never validated to ensure it is not the bridge contract itself. A deposit message specifying `recipient_id = bridge_contract_id` causes nBTC to be minted directly into the bridge's own token balance, where it is permanently irrecoverable. The deposited BTC is simultaneously locked in the bridge's MPC-controlled address and marked as verified, blocking any refund path.

---

### Finding Description

`check_deposit_msg` in `deposit_msg.rs` explicitly guards against `post_actions[i].receiver_id == env::current_account_id()`: [1](#0-0) 

The inline comment explains the rationale: routing nBTC to the bridge itself via `ft_transfer_call` would re-enter the bridge's own `ft_on_transfer` / `TokenReceiverMessage::Withdraw` flow. However, the top-level `recipient_id` field — the account to which nBTC is **minted** — carries no equivalent guard: [2](#0-1) 

Minting (unlike `ft_transfer_call`) does **not** invoke `ft_on_transfer` on the receiver. Consequently, if `recipient_id` equals the bridge contract's own account ID, nBTC is silently credited to the bridge's NEP-141 balance with no callback, no state transition, and no recovery path.

The bridge exposes no external function that lets the DAO (or anyone else) spend an arbitrary nBTC balance held by the bridge contract itself:

- `withdraw_protocol_fee` only drains `cur_available_protocol_fee`. [3](#0-2) 
- `claim_lost_found` only drains entries in the `lost_found` map for `env::predecessor_account_id()`. [4](#0-3) 
- `internal_transfer_nbtc` is an internal helper, not an externally callable admin escape hatch. [5](#0-4) 

Once the deposit is verified, the UTXO is inserted into `verified_deposit_utxo`, permanently blocking the refund path: [6](#0-5) 

---

### Impact Explanation

- The user's BTC is permanently locked in the bridge's MPC-controlled deposit address; the UTXO is marked verified, so `request_refund` is rejected.
- The minted nBTC is permanently stranded in the bridge contract's own balance with no on-chain recovery mechanism.
- This constitutes **permanent, irrecoverable loss of user funds** — matching the Critical impact class: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

---

### Likelihood Explanation

A whitelisted relayer submits `verify_deposit_v2` with the caller-supplied `deposit_msg`. Relayers are not required by the contract to validate `recipient_id`; the bridge contract itself is the only enforcement point. A user who crafts a `deposit_msg` with `recipient_id = bridge_contract_id`, derives the corresponding deposit address, and sends BTC to it can induce any relayer that does not independently sanitize the message to trigger this path. The `#[trusted_relayer]` gate limits the attack surface to whitelisted relayers, but the contract provides no defense-in-depth check at the protocol layer. [7](#0-6) 

---

### Recommendation

Add a guard in `check_deposit_msg` (or at the top of each `internal_verify_deposit_entry` / `internal_safe_verify_deposit_entry` call site) analogous to the existing `post_actions` check:

```rust
require!(
    deposit_msg.recipient_id != env::current_account_id(),
    "recipient_id cannot be the bridge contract itself"
);
```

This mirrors the already-present guard for `post_actions.receiver_id` and closes the same class of self-referential routing bug.

---

### Proof of Concept

1. Attacker constructs `DepositMsg { recipient_id: bridge_contract_id, post_actions: None, … }`.
2. Attacker calls `get_user_deposit_address` to derive the BTC deposit address for this message.
3. Attacker sends BTC to that address on-chain.
4. A whitelisted relayer (or the attacker if they hold `UnrestrictedRelayer`) calls `verify_deposit_v2` with the crafted `deposit_msg`.
5. The bridge verifies the Merkle proof, marks the UTXO in `verified_deposit_utxo`, and calls `mint(bridge_contract_id, amount)` on the nBTC contract.
6. nBTC is credited to the bridge's own balance — no `ft_on_transfer` fires, no state machine advances.
7. The attacker's BTC is permanently locked; `request_refund` is rejected because the UTXO is already in `verified_deposit_utxo`; the minted nBTC has no recovery path.
