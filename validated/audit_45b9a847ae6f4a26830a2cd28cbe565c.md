### Title
Chain-Selection Bypass via Hardcoded Empty Peras Weight Snapshot in `checkPreferTheirsOverOurs` — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` when deciding whether to disconnect from a peer whose header lies beyond the forecast horizon. When Peras is active and the peer's chain carries Peras weight boosts that make it heavier than the local chain despite having the same block number, the comparison silently treats the two chains as equal, returns `ShouldNotSwitch EQ`, and the node disconnects from the peer. The node then remains on the lighter, less-secure chain. This is the direct analog of the external report's pattern: a "bypass" flag (empty snapshot) suppresses the correct state signal (actual weight), and the final decision is made on stale data.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `projectLedgerView` returns `Nothing` — i.e., the incoming header is beyond the current forecast horizon and the node must block until its ledger state advances. The function's purpose is to guard against a peer that is serving a chain that will never be preferred: if the peer's fragment is not preferred over ours even ignoring Peras boosts, there is no point waiting, so the node disconnects with `CandidateTooSparse`.

The critical code path is:

```haskell
-- ChainSync/Client.hs lines 1834-1857
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check,
        -- see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
```

`preferAnchoredCandidate` branches on `isEmptyPerasWeightSnapshot weights`:

```haskell
-- AnchoredFragment.hs lines 186-213
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- pure block-number comparison
      case preferCandidate (projectChainOrderConfig cfg)
             (selectView cfg (getHeader1 ourTip))
             (selectView cfg (getHeader1 theirTip)) of
        ShouldSwitch r    -> ShouldSwitch (Right r)
        ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      -- weighted comparison using actual boosts
      case preferCandidate (projectChainOrderConfig cfg)
             (weightedSelectView cfg weights oursSuffix)
             (weightedSelectView cfg weights candSuffix) of ...
```

Because `emptyPerasWeightSnapshot` is always passed, the `otherwise` branch — which accounts for Peras boosts — is **never reached** inside `checkPreferTheirsOverOurs`. The comparison degenerates to a pure block-number comparison regardless of whether Peras is enabled.

**Concrete failure scenario:**

| Chain | Block number | Peras boost | Total weight |
|-------|-------------|-------------|--------------|
| Local (ours) | N | 0 | N |
| Peer (theirs) | N | B > 0 | N + B |

With real weights, `preferAnchoredCandidate` would return `ShouldSwitch (Heavier …)` and the node would keep waiting. With `emptyPerasWeightSnapshot`, it returns `ShouldNotSwitch EQ` and the node throws `CandidateTooSparse`, disconnecting from the peer. The node stays on the lighter chain.

The root cause is structurally identical to the external report: a "bypass" value (`emptyPerasWeightSnapshot`) suppresses the correct state signal (actual Peras weight), and the downstream decision (disconnect vs. wait) is made on stale/zeroed data. The external report's `wethToZap` returning 0 and skipping the `ChefIncentivesController` notification maps directly to `emptyPerasWeightSnapshot` causing `preferAnchoredCandidate` to skip the weighted branch and return the wrong answer.

---

### Impact Explanation

When Peras is active, an honest node can be made to permanently disconnect from a peer serving the canonically heavier chain whenever that peer's tip is beyond the local forecast horizon. The node then remains on a lighter chain. Because Peras chain selection is weight-based (block number + cumulative boosts), a lighter chain is by definition less secure: it is easier to outweigh with an adversarial fork. This satisfies the **High** impact criterion: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

Three conditions must hold simultaneously:

1. **Peras is enabled** — the protocol is being actively deployed on Cardano.
2. **At least one block on the peer's chain carries a Peras boost** — this is the normal operating condition once Peras certificates are being produced.
3. **The peer's tip is beyond the local forecast horizon** — this occurs naturally during periods of low block density (the forecast horizon is bounded by the stability window, roughly `3k/f` slots).

All three conditions are expected to occur in normal Peras operation. No special adversarial capability is required; a crafted private-testnet sequence with Peras enabled, a boosted block, and a slot gap exceeding the forecast window reproduces the bug deterministically.

---

### Recommendation

Pass the live `PerasWeightSnapshot` (already available via `ChainDB.getPerasWeightSnapshot` in the surrounding `ChainDbView`) into `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`. Alternatively, follow the existing TODO and remove the check entirely (issue #64), letting the node always wait when the header is beyond the forecast horizon, which is the safer default.

---

### Proof of Concept

On a private testnet with Peras enabled (`k = 5`, active slot coefficient `f = 0.5`):

1. Start node **N** synced to chain `C` of block number 100, no Peras boosts.
2. Connect peer **P** whose chain `C'` also has block number 100 but includes one boosted block (total weight 101).
3. Arrange for **P**'s next header (block 101) to be at a slot beyond the forecast horizon of **N** (e.g., slot gap > stability window).
4. **N** calls `checkTime` → `readLedgerStateHelper` → `projectLedgerView` returns `Nothing`.
5. `checkPreferTheirsOverOurs` is invoked; `preferAnchoredCandidate … emptyPerasWeightSnapshot` compares block numbers 100 vs 100 → `ShouldNotSwitch EQ`.
6. **N** throws `CandidateTooSparse` and disconnects from **P**.
