Audit Report

## Title
`tx.origin`-Equivalent (`env::signer_account_id()`) Used for Trusted-Relayer Authorization Enables Fee Theft via Intermediary Contract — (`File: near/omni-bridge/src/lib.rs`)

## Summary

`ft_on_transfer` reads `env::signer_account_id()` — NEAR's `tx.origin` analog — and passes it as `signer_id` to `fast_fin_transfer`, where it is the sole authorization gate for the trusted-relayer check. Because `signer_account_id` propagates unchanged through cross-contract calls, any attacker who can induce a trusted relayer to sign a transaction that eventually calls `ft_transfer_call` on a bridged token (via a malicious intermediary contract) will have the relayer's identity accepted by the bridge. The attacker controls the entire `FastFinTransferMsg` payload, including the `relayer` field that determines who receives the fee when the cross-chain proof is later finalized.

## Finding Description

In `ft_on_transfer`, `env::signer_account_id()` is captured and forwarded to `fast_fin_transfer`:

```rust
// near/omni-bridge/src/lib.rs:259-266
// We can't trust sender_id to pay for storage as it can be spoofed.
let signer_id = env::signer_account_id();
...
BridgeOnTransferMsg::FastFinTransfer(fast_fin_transfer_msg) => {
    self.fast_fin_transfer(token_id, amount, signer_id, fast_fin_transfer_msg)
}
```

Inside `fast_fin_transfer`, `signer_id` is the only authorization check:

```rust
// near/omni-bridge/src/lib.rs:756
require!(self.is_trusted_relayer(&signer_id), "Relayer is not active");
```

The `FastFinTransferMsg` struct contains a `relayer` field that is fully attacker-controlled:

```rust
// near/omni-types/src/lib.rs:504-513
pub struct FastFinTransferMsg {
    pub transfer_id: UnifiedTransferId,
    pub recipient: OmniAddress,
    ...
    pub relayer: AccountId,   // attacker sets this to their own account
}
```

This `relayer` field is passed directly into `add_fast_transfer` and stored in `FastTransferStatus`:

```rust
// near/omni-bridge/src/lib.rs:821-825
.fast_fin_transfer_to_near_callback(
    &fast_transfer,
    signer_id,
    fast_fin_transfer_msg.relayer,  // attacker-controlled
),
```

```rust
// near/omni-bridge/src/lib.rs:2257-2259
FastTransferStatusStorage::V0(FastTransferStatus {
    relayer,   // stored as Eve's account
    ...
```

When the cross-chain proof is later finalized via `process_fin_transfer_to_near`, the stored `relayer` becomes both the token recipient and the fee recipient:

```rust
// near/omni-bridge/src/lib.rs:1888-1895
let (recipient, msg, fee_recipient) = match fast_transfer_status {
    Some(status) => {
        ...
        (status.relayer.clone(), String::new(), status.relayer)
    }
```

**Call chain for the attack:**
`Alice (trusted relayer) → MaliciousContract.trigger() → wETH.ft_transfer_call(...) → omni-bridge.ft_on_transfer(...)`

At the point `ft_on_transfer` executes:
- `env::signer_account_id()` = Alice → `is_trusted_relayer(Alice)` = `true` ✓
- `env::predecessor_account_id()` = `wETH` token contract
- `sender_id` parameter = `MaliciousContract`
- `fast_fin_transfer_msg.relayer` = Eve's account (attacker-controlled)

No existing check prevents this. The only guard is `is_trusted_relayer(&signer_id)` at line 756, which passes because `signer_id` is the original transaction signer (Alice), not the actual initiator of the `ft_transfer_call` (MaliciousContract).

## Impact Explanation

This is a **Critical** authorization bypass and fee mis-accounting issue:

1. **Relayer role bypass**: An unprivileged attacker can execute `fast_fin_transfer` — a function gated by staking and waiting-period requirements — without being a registered trusted relayer, by exploiting a legitimate relayer's transaction signature.
2. **Fee theft**: The attacker sets `relayer = Eve` in the message. When the legitimate cross-chain proof arrives and `process_fin_transfer_to_near` runs, the entire fee (and in the NEAR-recipient case, the principal token amount) is sent to Eve's account instead of the legitimate relayer.
3. **Front-running legitimate relayers**: The attacker can front-run a legitimate relayer's pending fast transfer for a specific `transfer_id`. The legitimate relayer's subsequent `ft_transfer_call` will fail with `ERR_FAST_TRANSFER_ALREADY_PERFORMED`, and the fee is permanently redirected to Eve.

This matches the allowed impact scope: unauthorized relayer-equivalent action execution and fee mis-accounting that changes protocol balances.

## Likelihood Explanation

Trusted relayers are automated bots that interact with multiple NEAR contracts. An attacker deploys a contract mimicking a legitimate DeFi protocol or bridge component. When a trusted relayer calls it for any routine purpose (reward claiming, token swapping, liquidity operations), the malicious contract executes `ft_transfer_call` on a bridged token with a crafted `FastFinTransfer` payload as a side effect. The attacker needs only to hold a small amount of the bridged token in the malicious contract to fund the call. No private key compromise is required — only the relayer's willingness to call the malicious contract, which is achievable without social engineering by deploying a contract that offers a legitimate-looking incentive.

## Recommendation

Replace `env::signer_account_id()` with `sender_id` (the parameter provided by the NEP-141 token contract) for the purpose of relayer authorization in `fast_fin_transfer`. For whitelisted NEP-141 tokens, `sender_id` is set by the token contract itself from its own `predecessor_account_id` at the time of `ft_transfer_call`, making it reliable for authorization. The bridge already validates that `token_id = env::predecessor_account_id()` is a known token, so `sender_id` from a trusted token contract is trustworthy. Alternatively, require the `FastFinTransferMsg.relayer` field to equal the authorized caller, eliminating the split between the authorization identity and the fee-recipient identity.

## Proof of Concept

1. Eve deploys `MaliciousContract` holding a small balance of `wETH.omni-bridge.near`.
2. `MaliciousContract.trigger()` calls:
   ```
   wETH.ft_transfer_call(
     receiver_id = omni-bridge.near,
     amount = X,
     msg = FastFinTransfer {
       transfer_id = <real pending transfer ID>,
       recipient = <any NEAR address>,
       amount = X,
       fee = { fee: Y, native_fee: 0 },
       relayer = Eve's account,
       ...
     }
   )
   ```
3. Alice (trusted relayer) calls `MaliciousContract.trigger()` for any routine purpose.
4. Call chain: `Alice → MaliciousContract → wETH.ft_transfer_call → omni-bridge.ft_on_transfer`.
5. In `ft_on_transfer`: `env::signer_account_id()` = Alice → `is_trusted_relayer(Alice)` = `true`.
6. `fast_fin_transfer` executes: tokens sent to recipient; `FastTransfer { relayer: Eve }` stored.
7. When the legitimate cross-chain proof is submitted (by anyone calling `fin_transfer`), `process_fin_transfer_to_near` reads `status.relayer = Eve` and sends the fee to Eve.
8. The legitimate relayer receives nothing; Eve receives the fee without ever being a registered trusted relayer.

**Minimal integration test plan**: In `near/omni-tests/src/fast_transfer.rs`, add a test that:
- Registers `relayer_account` as a trusted relayer
- Creates a second account `intermediary` (not a trusted relayer) that holds bridged tokens
- Has `intermediary` call `ft_transfer_call` with `signer` set to `relayer_account` (simulated via workspaces by having `relayer_account` call a sub-contract that calls `ft_transfer_call`)
- Asserts that `fast_fin_transfer` succeeds and the stored `FastTransfer.relayer` is Eve's account
- Runs finalization and asserts Eve receives the fee
