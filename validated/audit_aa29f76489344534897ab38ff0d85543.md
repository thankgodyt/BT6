### Title
Permanent Fund Loss and Locked-Token Mis-Accounting When Bridge Contract's Own Account ID Is Used as `fin_transfer` Recipient — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

When a cross-chain transfer is finalized to NEAR with the bridge contract's own NEAR account ID as the recipient, the bridge either mints tokens to itself (for deployed bridge tokens) or issues an `ft_transfer` that NEP-141 rejects (for non-deployed tokens). In both cases the `locked_tokens` decrement is never reverted, the `FinTransferEvent` is emitted as if the transfer succeeded, and the user's EVM-side tokens are permanently lost.

---

### Finding Description

`process_fin_transfer_to_near` (called from `fin_transfer_callback`) accepts the `recipient` field verbatim from the verified cross-chain event and passes it directly to `send_tokens` with no guard against `recipient == env::current_account_id()`. [1](#0-0) 

**Step 1 — locked-token accounting is mutated before the transfer:**

```rust
let lock_actions = vec![self.unlock_tokens_if_needed(
    transfer_message.get_origin_chain(),
    &token,
    transfer_message.amount.0,
)];
``` [2](#0-1) 

For non-deployed (native NEAR) tokens this decrements `locked_tokens[(origin_chain, token)]` immediately. [3](#0-2) 

**Step 2 — `send_tokens` is called with the bridge contract as recipient:**

```rust
self.send_tokens(token.clone(), recipient, U128(...), &msg)
    .then(Self::ext(env::current_account_id())
        .fin_transfer_send_tokens_callback(
            transfer_message, &fee_recipient,
            !msg.is_empty(),   // ← is_ft_transfer_call
            predecessor_account_id, lock_actions))
``` [4](#0-3) 

For a normal transfer with an empty `msg`, `is_ft_transfer_call = false`.

**Step 3 — the callback never reverts lock actions on failure:**

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call { /* check promise result */ }
    else { false }   // ← always false when ft_transfer (not ft_transfer_call)
}
``` [5](#0-4) 

```rust
if Self::is_refund_required(is_ft_transfer_call) {
    self.revert_lock_actions(&lock_actions);   // ← never reached
    ...
} else {
    // emit FinTransferEvent as if success
}
``` [6](#0-5) 

**Two concrete failure modes:**

| Token type | What `send_tokens` does | Outcome |
|---|---|---|
| Non-deployed (native NEAR) | `ft_transfer(bridge_id, amount)` | NEP-141 rejects self-transfer; promise fails; `locked_tokens` decrement is permanent; tokens stay in bridge with no owner |
| Deployed bridge token | `mint(bridge_id, amount)` | Succeeds; tokens minted to bridge contract; no withdrawal path exists |

In both cases `FinTransferEvent` is emitted, the EVM-side tokens are already burned/locked, and the user receives nothing.

The `init_transfer` path on NEAR already guards against a NEAR recipient for NEAR-originated transfers:

```rust
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
``` [7](#0-6) 

No equivalent guard exists in `process_fin_transfer_to_near` for EVM-originated transfers.

---

### Impact Explanation

Any user who initiates a transfer on EVM with the bridge contract's NEAR account ID as the recipient permanently loses their bridged funds. The EVM tokens are burned/locked, the NEAR recipient receives nothing, and `locked_tokens` is permanently understated for non-deployed tokens. This is a direct, irreversible loss of bridged funds — within the "escrow mis-accounting / permanent freezing of bridged funds" critical impact class.

---

### Likelihood Explanation

Medium. The bridge contract's NEAR account ID is publicly known. A user can supply any NEAR account ID string as the `recipient` parameter in `initTransfer` on EVM. No special role, key, or privilege is required. Accidental use (e.g., copy-paste error, testing) or deliberate self-sabotage are both realistic paths.

---

### Recommendation

Add a guard at the top of `process_fin_transfer_to_near` (or inside `fin_transfer_callback` before dispatching):

```rust
require!(
    recipient != env::current_account_id(),
    BridgeError::InvalidRecipient.as_ref()
);
```

This mirrors the recommendation in the original report (`require(to != address(this))`).

---

### Proof of Concept

1. Attacker calls `initTransfer` on the EVM `OmniBridge` with `recipient = "near:omni-locker.near"` (the bridge contract's NEAR account ID) and any supported non-deployed token.
2. Relayer picks up the `InitTransfer` event and calls `fin_transfer` on NEAR.
3. `fin_transfer_callback` decodes `recipient = OmniAddress::Near("omni-locker.near")` and routes to `process_fin_transfer_to_near`.
4. `unlock_tokens_if_needed(Eth, token, amount)` decrements `locked_tokens[(Eth, token)]`.
5. `send_tokens("omni-locker.near", amount, "")` issues `ft_transfer("omni-locker.near", amount)` on the token contract.
6. The token contract rejects the call (NEP-141: `receiver_id == predecessor_account_id`).
7. `fin_transfer_send_tokens_callback` fires with `is_ft_transfer_call = false`.
8. `is_refund_required(false)` → `false`; `revert_lock_actions` is never called.
9. `FinTransferEvent` is emitted as if the transfer succeeded.
10. User's EVM tokens are burned; NEAR tokens are never delivered; `locked_tokens` is permanently understated.

    fn unlock_tokens(
        &mut self,
        chain_kind: ChainKind,
        token_id: &AccountId,
        amount: u128,
    ) -> LockAction {
        let key = (chain_kind, token_id.clone());
        let Some(available) = self.locked_tokens.get(&key) else {
            return LockAction::Unchanged;
        };
        require!(
            available >= amount,
            TokenLockError::InsufficientLockedTokens.as_ref()
        );

        let remaining = available - amount;
        self.locked_tokens.insert(&key, &remaining);

        LockAction::Unlocked {
            chain_kind,
            token_id: token_id.clone(),
            amount,
        }
    }
