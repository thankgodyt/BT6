Audit Report

## Title
Missing `multiTokens` Registration Guard in `initTransfer1155` Allows Permanent ERC1155 Token Lock — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`initTransfer1155` accepts and escrows any ERC1155 token without verifying that `logMetadata1155` was previously called for the `(tokenAddress, tokenId)` pair. Because only `logMetadata1155` populates `multiTokens` and emits the `LogMetadata` event NEAR requires to register the token binding, tokens transferred without a prior `logMetadata1155` call are permanently locked: NEAR cannot finalize the inbound transfer, and the EVM-side `finTransfer` path also fails to release them.

## Finding Description
`initTransfer1155` computes `deterministicToken` via `deriveDeterministicAddress` and immediately pulls ERC1155 tokens into the bridge with no guard on `multiTokens[deterministicToken]`: [1](#0-0) 

The only function that writes to `multiTokens` is `logMetadata1155`, which also emits the `LogMetadata` event that NEAR uses to register the token binding: [2](#0-1) 

Without that event, NEAR has no record of `deterministicToken` and cannot finalize the inbound transfer.

On the EVM return path, `finTransfer` reads `multiTokens[payload.tokenAddress]`. If `logMetadata1155` was never called, `multiToken.tokenAddress == address(0)`, so the ERC1155 branch is skipped and execution falls through to the `IERC20.safeTransfer` fallback, which reverts because `deterministicToken` is not a deployed contract: [3](#0-2) 

The `onERC1155Received` hook does not block this path: when the bridge itself calls `safeTransferFrom`, `operator == address(this)` and the hook accepts the transfer: [4](#0-3) 

The test suite confirms the missing guard — `initTransfer1155` is called without any prior `logMetadata1155` and succeeds: [5](#0-4) 

## Impact Explanation
Any user who calls `initTransfer1155` before `logMetadata1155` permanently loses their ERC1155 tokens. The tokens are held by the bridge contract with no release mechanism: NEAR cannot finalize the inbound transfer (no `LogMetadata` event), and EVM `finTransfer` reverts when attempting to return them via the `IERC20.safeTransfer` fallback. This is a **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation
The protocol provides no on-chain enforcement of the required call ordering. `initTransfer1155` is a public, permissionless function. Any user unfamiliar with the two-step flow, or any UI that omits the `logMetadata1155` step, will silently and irreversibly lock funds. The attack surface is every public call to `initTransfer1155` for any unregistered `(tokenAddress, tokenId)` pair.

## Recommendation
Add a registration guard at the top of `initTransfer1155`:

```solidity
require(
    multiTokens[deterministicToken].tokenAddress != address(0),
    "ERC1155 not registered: call logMetadata1155 first"
);
```

Alternatively, inline the `logMetadata1155` logic inside `initTransfer1155` (populate `multiTokens` and emit `LogMetadata`) before the token transfer, ensuring atomicity and eliminating the ordering requirement entirely.

## Proof of Concept
1. Deploy a mock ERC1155 and the bridge (no `logMetadata1155` call).
2. Call `initTransfer1155(mockERC1155, tokenId, amount, 0, 0, "victim.near", "")`.
3. Assert `erc1155.balanceOf(bridge, tokenId) == amount` — tokens are held by the bridge.
4. Confirm `multiTokens[deterministicToken].tokenAddress == address(0)` — no mapping exists.
5. Attempt `finTransfer` with `payload.tokenAddress = deterministicToken` — execution skips the ERC1155 branch and reverts at `IERC20(deterministicToken).safeTransfer(...)` because `deterministicToken` is not a contract.
6. Tokens are permanently locked with no release path. The existing test at `evm/tests/OmniBridge1155.test.ts` lines 191–194 already demonstrates step 2–3 passing without any prior `logMetadata1155`.
