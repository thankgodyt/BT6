### Title
Unauthenticated `request_refund` Allows Any Caller to Redirect a Victim's BTC Refund to an Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`request_refund` is publicly callable by any NEAR account. When `deposit_msg.refund_address` is `None`, the caller freely supplies any `refund_address`. Because only one refund request per UTXO is allowed, an attacker who submits this call before the legitimate depositor — using the same on-chain-observable inputs but their own BTC address — permanently occupies the slot and causes the victim's subsequent call to revert. After the timelock, `execute_refund` (also publicly callable) sends the BTC to the attacker's address.

---

### Finding Description

`request_refund` is declared inside a `#[trusted_relayer] #[near] impl Contract` block but carries **no individual** `#[trusted_relayer]` or `#[access_control_any]` attribute of its own. [1](#0-0) 

The pattern in this codebase is that the impl-block `#[trusted_relayer]` is a configuration macro (it carries `bypass_roles`, `manager_roles`, `config_roles` parameters on the first block), while the **per-function** `#[trusted_relayer]` attribute is what actually gates access. Functions that are intentionally restricted — `verify_refund_finalize` and `remove_refund_pending_tx_id` — carry the individual attribute; `request_refund`, `reject_refund`, and `execute_refund` do not. [2](#0-1) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case — users typically do not pre-commit a BTC refund address at deposit time), the check is skipped entirely and any caller-supplied `refund_address` is accepted.

In `request_refund_callback`, the UTXO key is derived deterministically from the Bitcoin transaction:

```rust
let utxo_storage_key = generate_utxo_storage_key(tx_id, vout);
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [4](#0-3) 

Only one request per UTXO is permitted. Whichever call lands first wins the slot. The stored `refund_address` is then used verbatim by `execute_refund` → `finalize_refund_with_psbt` → `build_refund_output` to construct the Bitcoin output paying the refund. [5](#0-4) 

`execute_refund` is also publicly callable (no individual access-control attribute): [6](#0-5) 

---

### Impact Explanation

**Critical — theft of user BTC funds.**

An attacker who successfully occupies the refund-request slot with their own `refund_address` causes the bridge's MPC signing pipeline to construct and broadcast a Bitcoin transaction paying the attacker's address. The victim's BTC is permanently transferred to the attacker. The victim cannot submit a competing refund request (the slot is taken), and `reject_refund` requires DAO/Operator privilege or proof that the UTXO was already verified via deposit — neither of which the victim controls. [7](#0-6) 

---

### Likelihood Explanation

**Medium-High.** All inputs needed to mount the attack are publicly observable:

- `deposit_msg` — emitted in NEAR events or visible in the original `verify_deposit` call arguments on-chain.
- `tx_bytes` and `vout` — the raw Bitcoin transaction is public on the Bitcoin blockchain.
- `proof` (Merkle proof) — derivable from any Bitcoin block explorer or full node.
- Storage deposit — a small, fixed NEAR amount (`required_balance_for_request_refund()`).

The attacker does not need any privileged role, leaked key, or special capability. The only timing requirement is submitting before the legitimate depositor, which is straightforward given that the Bitcoin transaction confirming the deposit is visible to everyone before either party calls `request_refund`.

---

### Recommendation

Bind the `refund_address` to the depositor at the time of deposit, or enforce caller authorization in `request_refund`. Concretely:

1. **Preferred**: Require `deposit_msg.refund_address` to be `Some` (non-`None`) and enforce the existing match check unconditionally. This mirrors the Connext fix: embed the authorized address in the invariant data (here, `deposit_msg`) so no caller can substitute a different one.
2. **Alternative**: Record `env::predecessor_account_id()` as the `requester` in `RefundRequest` and require that only the same account (or DAO/Operator) can call `execute_refund` for that request.

---

### Proof of Concept

1. Alice deposits BTC using `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`. The deposit fails to finalize (e.g., wrong amount, expired).
2. The Bitcoin transaction `TX` paying the bridge's deposit address is confirmed on-chain. Its `txid` and `vout` are public.
3. Bob (attacker) constructs the Merkle inclusion proof for `TX`, attaches the required NEAR storage deposit, and calls:
   ```
   request_refund(
       deposit_msg = { recipient_id: "alice.near", refund_address: None, ... },
       refund_address = "bob_btc_address",
       tx_bytes = <TX bytes>,
       vout = 0,
       proof = <valid Merkle proof>,
       gas_fee = None,
   )
   ```
4. Bob's call lands first. `request_refund_callback` stores `RefundRequest { refund_address: "bob_btc_address", ... }` under `utxo_storage_key = txid@0`.
5. Alice calls `request_refund` with her own BTC address. It reverts: `"Refund request already exists for this UTXO"`.
6. After `config.unsafe_refund_timelock_sec` elapses, Bob (or anyone) calls `execute_refund("txid@0", None)`. The bridge builds a Bitcoin transaction paying `"bob_btc_address"` and requests an MPC signature.
7. The signed transaction is broadcast; Alice's BTC is sent to Bob. [8](#0-7)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
