Audit Report

## Title
`initTransfer1155()` Locks ERC1155 Tokens Without Validating `multiTokens` Mapping, Causing Permanent Fund Loss - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155()` accepts and locks ERC1155 tokens into the bridge without verifying that `logMetadata1155()` has been called first to populate `multiTokens[deterministicToken]`. When a user calls `initTransfer1155()` without the prior registration step, their tokens are permanently frozen: the NEAR side panics with `TokenDecimalsNotFound` (no wrapped tokens minted, no return leg created), and there is no on-chain mechanism to recover the locked ERC1155 tokens.

## Finding Description

`initTransfer1155()` computes `deterministicToken`, immediately calls `IERC1155.safeTransferFrom` to lock tokens, and emits `InitTransfer` — without ever reading or requiring `multiTokens[deterministicToken]` to be set: [1](#0-0) 

The `multiTokens` mapping is exclusively populated by `logMetadata1155()`: [2](#0-1) 

The `onERC1155Received` hook does not block this path. When the bridge contract itself calls `safeTransferFrom`, the ERC1155 standard sets `operator = address(this)` (the bridge), so the guard passes: [3](#0-2) 

On the NEAR side, `fin_transfer_callback` unconditionally looks up `token_decimals` for the incoming token. Since `logMetadata1155()` was never called, the `LogMetadata` event was never emitted, `token_decimals` was never populated, and the call panics with `TokenDecimalsNotFound`: [4](#0-3) 

No wrapped tokens are minted on NEAR, no return transfer is ever initiated, and `finTransfer()` on the EVM side is never called. Even if it were called, `multiTokens[deterministicToken].tokenAddress == address(0)` causes `finTransfer()` to fall through to the ERC20 branch and revert: [5](#0-4) 

The existing test suite confirms this exploit path: the "validates ERC1155 receiver hooks" test calls `initTransfer1155()` directly without `logMetadata1155()` and observes that tokens are locked, without verifying recoverability: [6](#0-5) 

There is no admin rescue function, no refund mechanism, and no upgrade path that could recover the locked tokens without a full contract upgrade.

## Impact Explanation

This is a permanent freezing of bridged funds on the EVM chain, matching the Critical allowed impact: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet, Bitcoin, Zcash, or Wormhole-routed flows."* Any ERC1155 tokens sent via `initTransfer1155()` without a prior `logMetadata1155()` call are irrecoverably locked in the bridge contract with no on-chain recovery path.

## Likelihood Explanation

`initTransfer1155()` is a public, permissionless function. The two-step prerequisite (`logMetadata1155` → `initTransfer1155`) is not enforced at the contract level, not documented in the function signature, and not enforced by any on-chain guard. A user who reads the function name and ABI will naturally call `initTransfer1155()` directly. The test suite itself demonstrates this call sequence succeeds (tokens are locked) without the prerequisite step. [7](#0-6) 

## Recommendation

Add a guard at the top of `initTransfer1155()` that requires `multiTokens[deterministicToken].tokenAddress != address(0)` before accepting the token lock. Alternatively, `initTransfer1155()` can atomically invoke the registration logic (setting `multiTokens` and emitting `LogMetadata`) if the mapping is not yet set, mirroring the idempotent behavior of `logMetadata1155()`. Either approach closes the gap between the two functions.

## Proof of Concept

The existing test at `evm/tests/OmniBridge1155.test.ts` lines 191–195 already demonstrates the exploit path:

1. Deploy `OmniBridge` and `TestERC1155`. Do **not** call `logMetadata1155()`.
2. Mint tokens to `user` and approve the bridge.
3. Call `bridge.connect(user).initTransfer1155(erc1155, tokenId, 1, 0, 0, "receiver.near", "")`.
4. Assert: `erc1155.balanceOf(bridge, tokenId) == 1` — tokens are locked.
5. Assert: `bridge.multiTokens(deterministicToken).tokenAddress == address(0)` — mapping is unset.
6. Attempt NEAR-side `fin_transfer` — panics with `TokenDecimalsNotFound`; no wrapped tokens minted.
7. No `finTransfer()` call is ever initiated; tokens are permanently frozen.
