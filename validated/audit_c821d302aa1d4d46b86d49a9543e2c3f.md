### Title
Anyone Can Call `request_refund` for Any Deposit with an Arbitrary `refund_address`, Redirecting Victim BTC to Attacker - (File: contracts/satoshi-bridge/src/api/bridge.rs)

---

### Summary

`request_refund` has no authorization check tying the caller to the deposit's intended recipient. When a `DepositMsg` was created without a pre-authorized `refund_address` (i.e., `deposit_msg.refund_address == None`), any unprivileged NEAR account can call `request_refund` for that deposit and supply an attacker-controlled BTC address. After the `unsafe_refund_timelock_sec` elapses, the same attacker calls `execute_refund` and the victim's BTC is sent to the attacker's address.

---

### Finding Description

`request_refund` is a public, permissionless function: [1](#0-0) 

Inside `internal_request_refund`, the only checks performed are:

1. Sufficient attached deposit (anti-spam fee).
2. `tx_bytes` size limit.
3. If `deposit_msg.refund_address` is `Some`, it must equal the supplied `refund_address`. [2](#0-1) 

There is **no check** that `env::predecessor_account_id() == deposit_msg.recipient_id`. When the original `DepositMsg` was created with `refund_address: None`, the caller is free to supply any BTC address as `refund_address`, and that address is stored verbatim in the `RefundRequest`: [3](#0-2) 

`execute_refund` is equally permissionless after the timelock: [4](#0-3) 

The timelock applied to the "no pre-authorized address" path is `unsafe_refund_timelock_sec`, which is longer than the normal timelock but still finite and operator-dependent: [5](#0-4) 

Once the timelock expires, `finalize_refund_with_psbt` builds the BTC transaction paying the stored `refund_address` — the attacker's address — and submits it for MPC signing: [6](#0-5) 

---

### Impact Explanation

**Critical.** An attacker can permanently redirect a victim's deposited BTC to an attacker-controlled Bitcoin address. The victim's BTC is irreversibly lost. This constitutes significant theft of user funds via an unauthorized release of bridge-controlled BTC.

---

### Likelihood Explanation

**Medium-High.** The `DepositMsg` used to derive a deposit address is emitted publicly via the `LogDepositAddress` event when `get_user_deposit_address` is called: [7](#0-6) 

Any on-chain observer can reconstruct the `deposit_msg` for any deposit address. Deposits that fail to be processed by a relayer (e.g., during relayer downtime) are the natural target. The attacker races to call `request_refund` before the legitimate user, since only one refund request per UTXO is allowed (duplicate check in `request_refund_callback`). The only mitigation is DAO/Operator rejection during the `unsafe_refund_timelock_sec` window, which is an operational control, not a protocol-level guarantee.

---

### Recommendation

Add an authorization check in `request_refund` (or `internal_request_refund`) requiring that the caller is the `deposit_msg.recipient_id`:

```rust
require!(
    env::predecessor_account_id() == deposit_msg.recipient_id
        || self.acl_has_role(Role::DAO.into(), env::predecessor_account_id())
        || self.acl_has_role(Role::Operator.into(), env::predecessor_account_id()),
    "Only the deposit recipient or a privileged role can request a refund"
);
```

This mirrors the pattern already used elsewhere in the contract where only the account owner or a privileged role can act on behalf of a position.

---

### Proof of Concept

1. Alice calls `get_user_deposit_address` with `DepositMsg { recipient_id: alice.near, refund_address: None, ... }`. The `LogDepositAddress` event is emitted publicly.
2. Alice sends BTC to the derived deposit address. The relayer is temporarily offline; `verify_deposit` is never called.
3. Attacker observes the `LogDepositAddress` event, reconstructs Alice's `deposit_msg`, and calls:
   ```
   request_refund(
       deposit_msg = { recipient_id: alice.near, refund_address: None, ... },
       refund_address = "attacker_btc_address",
       tx_bytes = <Alice's BTC tx>,
       vout = 0,
       proof = <valid Light Client proof>,
       gas_fee = None
   )
   ```
   with sufficient attached NEAR deposit.
4. The Light Client verifies the proof. `request_refund_callback` stores a `RefundRequest` with `refund_address = attacker_btc_address`.
5. Alice cannot create her own refund request — the duplicate check rejects it.
6. After `unsafe_refund_timelock_sec` elapses (assuming DAO/Operator does not intervene), attacker calls `execute_refund(utxo_storage_key, None)`.
7. The bridge builds a BTC transaction paying `attacker_btc_address` and submits it for MPC signing. Alice's BTC is permanently redirected to the attacker. [8](#0-7) [9](#0-8)

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );

        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
