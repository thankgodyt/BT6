### Title
Hardcoded Single-Action Assumption in Orchard Bundle Validation Breaks All Standard Zcash Shielded Withdrawals — (File: `contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary
`extract_orchard_bundle` enforces `bundle.actions().len() == EXPECTED_ACTIONS_NUMBER` where `EXPECTED_ACTIONS_NUMBER` is hardcoded to `1`. The Orchard protocol's standard builder (`BundleType::Transactional`) automatically pads every bundle to a minimum of 2 actions for privacy. Any user submitting a standard wallet-generated Orchard bundle for a shielded ZEC withdrawal will always trigger a panic in `PsbtWrapper::new()`, making the entire Orchard withdrawal path permanently broken for standard wallets.

### Finding Description
`EXPECTED_ACTIONS_NUMBER` is defined as `1`: [1](#0-0) 

`extract_orchard_bundle` enforces an exact match: [2](#0-1) 

When `extract_orchard_bundle` returns an `Err`, `PsbtWrapper::new()` calls `env::panic_str`, aborting the transaction: [3](#0-2) 

The Orchard protocol's standard `BundleType::Transactional` builder pads every bundle to at least 2 actions for privacy — a fact the code's own comment acknowledges ("The Orchard builder automatically pads bundles to meet this minimum for privacy"). The only bundle type that produces exactly 1 action is `BundleType::Coinbase`, which is a special type intended for mining coinbase transactions, not user withdrawals. The test suite works around this by explicitly using `BundleType::Coinbase`: [4](#0-3) 

Any real Zcash wallet generating an Orchard output for a bridge withdrawal would use `BundleType::Transactional`, producing 2+ actions, and the bridge would always reject it.

### Impact Explanation
Every attempt by a standard Zcash wallet user to withdraw nZEC to a shielded Orchard address triggers `env::panic_str` inside `ft_on_transfer`. The panic causes the `ft_transfer_call` promise to fail; NEP-141's `ft_resolve_transfer` returns the tokens to the sender, so there is no permanent fund loss. However, the entire Orchard shielded withdrawal path is permanently non-functional for any standard wallet-generated bundle. This is a publicly reachable panic-driven fault in a production bridge/token path.

**Impact: Low** — panic-driven fault in production bridge path without direct theft; the Orchard withdrawal feature is completely broken for standard wallets.

### Likelihood Explanation
The Orchard protocol guarantees that `BundleType::Transactional` bundles always have ≥ 2 actions. Every standard Zcash wallet (Zashi, YWallet, etc.) uses transactional bundles. Any user attempting a shielded ZEC withdrawal via a standard wallet will always hit this failure. Likelihood is **High** for any Zcash user of the bridge.

### Recommendation
Replace the exact-match check with logic that accepts bundles with one or more actions and iterates over all actions to find the one recoverable with the bridge OVK, rather than hardcoding index `0` and count `1`. Alternatively, document clearly that only `BundleType::Coinbase` bundles are accepted and provide tooling that generates such bundles, since standard wallets cannot produce them.

### Proof of Concept
1. User holds nZEC and calls `ft_transfer_call` on the nZEC contract targeting the bridge, with a `WithdrawMsg` containing a Unified Address and an Orchard bundle generated by any standard Zcash wallet (`BundleType::Transactional`, 2 actions due to padding).
2. Bridge's `ft_on_transfer` is invoked; it constructs a `PsbtWrapper` via `PsbtWrapper::new()`.
3. `PsbtWrapper::new()` calls `orchard_policy::extract_orchard_bundle`.
4. `extract_orchard_bundle` checks `bundle.actions().len() != 1` → `true` (bundle has 2 actions) → returns `Err("Orchard bundle must have 1 actions, got 2")`.
5. `PsbtWrapper::new()` calls `env::panic_str("ERR_INVALID_ORCHARD_BUNDLE: failed to extract Orchard bundle")`.
6. The transaction panics; tokens are returned to the user via NEP-141 rollback.
7. The user can never successfully withdraw to a shielded Orchard address using any standard wallet.
