### Title
Missing Minimum Viable Amount Check After Gas Fee Deduction in Refund Flow - (File: `contracts/satoshi-bridge/src/refund.rs`)

### Summary

The `request_refund_callback` function only validates that the gas fee is strictly less than the deposit amount (`resolved_gas_fee < amount`), but never checks that the resulting `refund_amount = amount - gas_fee` meets a minimum viable Bitcoin output value (the Bitcoin dust limit, ~546 satoshis for P2WPKH). This mirrors the original report's pattern: a pre-operation check is performed, but no post-deduction check ensures the remaining amount is economically viable.

### Finding Description

In `request_refund_callback` (`contracts/satoshi-bridge/src/refund.rs`, lines 549–553), the only guard on the refund economics is:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

This allows `refund_amount = amount - gas_fee` to be any positive integer, including values below the Bitcoin dust limit. Later, in `refund_execution_inputs`, the only additional check is:

```rust
let refund_amount = refund_request.amount.checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [2](#0-1) 

`> 0` is not the same as `>= dust_limit`. A refund output of, say, 100 satoshis is non-zero but is a Bitcoin dust output that standard miners will reject.

The gas fee is fixed at request time and stored immutably in `RefundRequest.gas_fee`. Once `execute_refund` runs and `finalize_refund_with_psbt` marks the UTXO as verified:

```rust
self.data_mut()
    .verified_deposit_utxo
    .insert(utxo_storage_key.clone());
``` [3](#0-2) 

…the deposit UTXO is permanently blocked from being claimed via `verify_deposit`. If the resulting Bitcoin transaction carries a dust output, miners reject it. The refund request is kept with `executed = true`, and `execute_refund` can be called again, but the gas fee stored in the request is immutable — every re-execution produces the same dust output. The user's BTC is permanently locked.

The `config.assert_valid()` does not enforce any relationship between `max_btc_gas_fee` and `min_deposit_amount` that would prevent this:

```rust
require!(
    self.min_btc_gas_fee < self.max_btc_gas_fee,
    "min_btc_gas_fee must be less than max_btc_gas_fee"
);
``` [4](#0-3) 

There is no `require!(max_btc_gas_fee + dust_limit <= min_deposit_amount)` constraint.

### Impact Explanation

If `amount - gas_fee` falls below the Bitcoin dust limit (~546 satoshis for P2WPKH), the signed refund transaction is non-standard and will be rejected by miners. The UTXO is already marked as verified (blocking `verify_deposit`), and the stored gas fee cannot be changed, so no valid refund transaction can ever be produced. The user's BTC is permanently locked in the bridge's UTXO set with no recovery path. This maps to **Medium** (stuck bridge state requiring operator intervention / permanent locking of bridged funds) or potentially **Critical** (permanent loss of user funds) depending on whether the operator can recover via `reject_refund` — but `reject_refund` only removes the request, it does not return the BTC to the user.

### Likelihood Explanation

The scenario is reachable by any unprivileged user who:
1. Deposits a small BTC amount (e.g., just above `min_deposit_amount`, or even below it — `request_refund` has no `min_deposit_amount` check).
2. Calls `request_refund` with `gas_fee = None`, so the default `max_btc_gas_fee` is used.
3. If `deposit_amount - max_btc_gas_fee < 546 satoshis`, the refund output is dust.

This is realistic when `max_btc_gas_fee` is configured close to `min_deposit_amount` (e.g., during high-fee periods where `max_btc_gas_fee` is set high), or when a user deposits an amount only slightly above the gas fee. No privileged access is required.

### Recommendation

Add a minimum viable refund amount check in `request_refund_callback` immediately after computing `resolved_gas_fee`:

```rust
let refund_amount = amount.checked_sub(resolved_gas_fee)
    .expect("gas fee exceeds deposit amount");
require!(
    refund_amount >= MIN_BITCOIN_DUST_LIMIT, // e.g., 546 satoshis
    "Refund amount after gas fee is below dust limit"
);
```

Additionally, add a config invariant in `Config::assert_valid()` ensuring `max_btc_gas_fee + MIN_BITCOIN_DUST_LIMIT <= min_deposit_amount` so the configuration itself cannot produce dust refunds.

### Proof of Concept

1. Config: `min_deposit_amount = 10_000 sats`, `max_btc_gas_fee = 9_600 sats`.
2. User sends 10,000 satoshis to their deposit address. `verify_deposit` is never called (or fails for any reason).
3. User calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee: None)`.
4. In `request_refund_callback`: `resolved_gas_fee = 9_600`, `amount = 10_000`. Check `9_600 < 10_000` passes. `RefundRequest` is stored with `gas_fee = 9_600`.
5. After timelock, anyone calls `execute_refund`. `refund_execution_inputs` computes `refund_amount = 10_000 - 9_600 = 400 satoshis`. Check `400 > 0` passes.
6. A Bitcoin transaction is built with a 400-satoshi output to the user's address. This is below the P2WPKH dust limit (546 sats). The transaction is signed by MPC and broadcast.
7. Bitcoin miners reject the transaction as non-standard (dust output).
8. `finalize_refund_with_psbt` has already inserted the UTXO into `verified_deposit_utxo`, blocking `verify_deposit`. The refund request is marked `executed = true`. Every subsequent `execute_refund` call produces the same invalid transaction. The user's 10,000 satoshis are permanently locked.
