### Title
Missing Upfront Terminal-State Check in `request_refund` Causes Permanent Loss of Attached NEAR Deposit — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`internal_request_refund` does not check whether the target UTXO is already in a terminal state (`verified_deposit_utxo`) before consuming the caller's attached NEAR deposit and dispatching a cross-contract call to the light client. The state guard only fires inside the asynchronous callback `request_refund_callback`. When the UTXO is already finalized, the callback panics and the attached NEAR deposit is permanently lost with no service rendered.

---

### Finding Description

`internal_request_refund` (called by the public `request_refund` entrypoint) enforces a storage deposit up-front: [1](#0-0) 

It then immediately dispatches a cross-contract call to the BTC light client and chains `request_refund_callback` as the continuation: [2](#0-1) 

The only check that the UTXO has not already been finalized lives inside the callback: [3](#0-2) 

By the time this check runs, the NEAR deposit is already held by the contract. In NEAR Protocol, a deposit attached to the *original* call is transferred to the contract when that call executes successfully. If a *subsequent callback* panics, the state changes in the callback are rolled back, but the deposit that was already credited to the contract in the first receipt is **not** automatically returned to the caller. Because `request_refund` succeeds (it only schedules work), the deposit is irrecoverably consumed even when the callback later panics.

Two concrete trigger paths exist:

1. **Already-deposited UTXO**: A user calls `request_refund` on a UTXO that was already finalized by `verify_deposit` / `verify_deposit_v2`. The UTXO is in `verified_deposit_utxo`. The light client call succeeds (the BTC transaction is real), but `request_refund_callback` panics at the `verified_deposit_utxo` check. The NEAR deposit is lost.

2. **Concurrent duplicate requests**: Two callers race to submit `request_refund` for the same UTXO. The first callback inserts the entry; the second callback panics at the duplicate-request check. The second caller's NEAR deposit is lost.

The `finalize_refund_with_psbt` helper inserts the UTXO into `verified_deposit_utxo` to block a later `verify_deposit`: [4](#0-3) 

This means a UTXO that was already refunded on-chain (and whose request was removed by `verify_refund_finalize_callback`) also remains in `verified_deposit_utxo`, making it a permanent terminal state that triggers the same loss path.

---

### Impact Explanation

The attached NEAR deposit is sized to cover up to ~200 KB of `tx_bytes` storage, which the code comments estimate at ~2 NEAR: [5](#0-4) 

A user who calls `request_refund` on a UTXO already in a terminal state loses up to ~2 NEAR with no refund request created and no service rendered. The loss is permanent; there is no recovery path. This matches the **Low** impact tier: a publicly reachable panic-driven fault in a production bridge path that causes direct, irreversible loss of user funds (NEAR tokens), without theft of BTC/nBTC.

---

### Likelihood Explanation

The scenario is reachable by any unprivileged NEAR account without any privileged access. It arises naturally from:

- A user who is unaware that their deposit was already processed by a relayer calling `verify_deposit`.
- A race condition between a relayer submitting `verify_deposit` and a user submitting `request_refund` for the same UTXO.
- A user retrying `request_refund` after a previous refund was already finalized on-chain.

No special knowledge or coordination is required; the BTC transaction bytes and proof are publicly observable on-chain.

---

### Recommendation

Add an upfront check in `internal_request_refund`, before the cross-contract call is dispatched, that rejects the call immediately (causing the deposit to be refunded by the NEAR runtime) if the UTXO is already in a terminal state:

```rust
// In internal_request_refund, before verify_transaction_inclusion_promise:
require!(
    !self.data().verified_deposit_utxo.contains(&utxo_storage_key),
    "UTXO already verified via deposit, cannot request refund"
);
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
```

Because these checks fire in the original call (before any cross-contract call), a panic here causes the NEAR runtime to refund the attached deposit automatically. The `utxo_storage_key` can be derived from `tx_bytes` and `vout` before the light-client call, exactly as `request_refund_callback` already does at lines 529–532. [6](#0-5) 

---

### Proof of Concept

1. Relayer calls `verify_deposit_v2` for UTXO `abc123@0`; it succeeds and `abc123@0` is inserted into `verified_deposit_utxo`.
2. User calls `request_refund` for the same UTXO, attaching 2 NEAR as the storage deposit.
3. `internal_request_refund` passes the deposit check and dispatches the light-client cross-contract call. The 2 NEAR is now held by the bridge contract.
4. The light client confirms the BTC transaction is valid (it is — the deposit was real).
5. `request_refund_callback` fires, reaches the check at line 535, finds `abc123@0` in `verified_deposit_utxo`, and panics: `"UTXO already verified via deposit"`.
6. The callback's state changes are rolled back, but the 2 NEAR deposit credited to the contract in step 3 is not returned. The user has permanently lost 2 NEAR.
