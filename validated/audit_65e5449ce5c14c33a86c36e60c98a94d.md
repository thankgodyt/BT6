### Title
Unregistered `current_account_id` receiver causes panic in `ft_transfer` legacy withdrawal fallthrough — (`contracts/nbtc/src/lib.rs`)

### Summary

When `WITHDRAW_RELAYER_ADDRESS` is absent, the legacy Near Intents withdrawal branch in `ft_transfer` falls through and calls `self.token.ft_transfer(env::current_account_id(), amount, memo)`. Because the nBTC contract itself is never registered as a token holder, the underlying NEP-141 `internal_deposit` panics, reverting any caller who attempts this path.

### Finding Description

`ft_transfer` contains a special branch for the legacy Near Intents withdrawal flow: [1](#0-0) 

When both conditions hold — `receiver_id == env::current_account_id()` and the memo starts with `"WITHDRAW_TO:"` — the code checks for a configured relayer: [2](#0-1) 

If `read_withdraw_relayer_address()` returns `None` (storage key absent), the `if let Some(...)` arm is skipped and execution falls through to: [3](#0-2) 

At this point `receiver_id` is still `env::current_account_id()`. The underlying `FungibleToken::ft_transfer` calls `internal_transfer` → `internal_deposit` on that account. The nBTC contract itself is never registered as a token holder — only `bridge_id` is registered at construction: [4](#0-3) 

The `near_contract_standards` `internal_deposit` panics with "The account is not registered" when the receiver has no storage entry, causing the entire transaction to revert.

### Impact Explanation

Any registered nBTC holder can trigger this panic by calling:

```
ft_transfer(receiver_id = nbtc_contract_id, amount = X, memo = "WITHDRAW_TO:btc_addr")
```

with 1 yoctoNEAR attached, whenever the relayer has not been configured (or has been cleared). The caller's transaction reverts, their balance is unchanged, but the legacy Near Intents withdrawal path is completely non-functional for all users during that window. This is a publicly reachable panic-driven fault in a production bridge/token path with no direct theft.

### Likelihood Explanation

The relayer address is set via `set_withdraw_relayer_address`, which requires controller access. Any gap between deployment and relayer configuration — or any future clearing of the key — exposes every user of the legacy withdrawal path to this panic. The triggering call is a standard NEP-141 `ft_transfer` requiring no special privileges. [5](#0-4) 

### Recommendation

Replace the silent fallthrough with an explicit guard. When the relayer is absent and the special withdrawal conditions are met, either panic with a descriptive message or redirect to a safe default, rather than forwarding `env::current_account_id()` as the receiver to the underlying token:

```rust
if receiver_id == env::current_account_id()
    && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
{
    let withdraw_relayer = Self::read_withdraw_relayer_address()
        .unwrap_or_else(|| env::panic_str("Withdraw relayer not configured"));
    return self.token.ft_transfer(withdraw_relayer, amount, memo);
}
self.token.ft_transfer(receiver_id, amount, memo);
```

### Proof of Concept

1. Deploy nBTC contract without calling `set_withdraw_relayer_address`.
2. Register a holder account and mint tokens to it.
3. Call `ft_transfer(nbtc_contract_id, 1, Some("WITHDRAW_TO:bc1qxxx"))` with 1 yoctoNEAR from the holder.
4. Observe the transaction panics with "The account `<nbtc_contract_id>` is not registered".
5. Confirm the holder's balance is unchanged (revert) and the withdrawal path is permanently broken until the relayer is set.

    fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
        // Legacy bridging flow used by Near Intents
        if receiver_id == env::current_account_id()
            && memo
                .as_ref()
                .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
        {
            if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
                return self.token.ft_transfer(withdraw_relayer, amount, memo);
            }
        }

        self.token.ft_transfer(receiver_id, amount, memo);
    }
