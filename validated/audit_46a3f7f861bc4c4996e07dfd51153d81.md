### Title
Unconditional Peras Certificate Acceptance Bypasses All Cryptographic Validation, Enabling Unprivileged Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every inbound certificate, performing zero cryptographic or committee-membership verification. This stub is wired directly into the live Peras certificate diffusion pipeline (`makePerasCertPoolWriterFromChainDB`). Any unprivileged peer can therefore inject an arbitrary crafted `PerasCert` — with any round number and any boosted-block pointer — that will be accepted, stored in the `PerasCertDB`, and used to trigger chain selection, potentially causing the node to prefer a non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

In the default `BlockSupportsPeras` instance, `validatePerasCert` is implemented as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its content, is unconditionally wrapped in `Right` and assigned the full `perasWeight` boost (15 by default). No BLS aggregate signature is checked, no committee membership is verified, no round-number bounds are enforced, and no boosted-block validity is confirmed.

**Wiring into the production diffusion pipeline:**

`makePerasCertPoolWriterFromChainDB` — the production writer used when Peras is enabled — passes this stub directly as the `validateCert` argument:

```haskell
(validatePerasCert mkPerasParams)  -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

**`processCerts` calls the stub on every inbound certificate from a peer:**

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because the stub never produces a `Left`, the `(errs, _)` branch is unreachable. Every certificate from every peer is accepted and forwarded to `addPerasCertAsync`.

**Chain selection is then triggered for the boosted block:**

`chainSelSync` looks up the boosted block in the `VolatileDB` and, if present, calls `chainSelectionForBlock`:

```haskell
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

**Chain comparison incorporates the injected boost:**

`preferAnchoredCandidate` / `compareAnchoredFragments` use `weightedSelectView`, which adds `wsvWeightBoost` (the sum of all Peras boosts on the fragment) to the block number when comparing candidates:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [5](#0-4) 

A fraudulent certificate granting `PerasWeight 15` to a block on a shorter fork can make that fork's total weight exceed the canonical chain's total weight, causing the node to switch.

---

### Impact Explanation

**Classification:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain, and Critical — bypass of Peras certificate/vote checks enabling unauthorized certificate acceptance.

An attacker who can connect to a Peras-enabled node as a peer can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block currently in the node's `VolatileDB` (i.e., any block within the last `k` blocks of any known fork).
2. Send it via the Peras certificate diffusion mini-protocol.
3. The certificate passes "validation" (the stub always returns `Right`).
4. The certificate is stored in `PerasCertDB` and chain selection is triggered for the boosted block.
5. The node's `WeightedSelectView` now adds `PerasWeight 15` to any fragment containing that block.
6. If the boosted block is on a fork that is at most 15 blocks shorter than the canonical chain, the node switches to the fork.

This constitutes unauthorized chain selection manipulation: a single unprivileged peer, without any stake or cryptographic key material, can cause an honest node to abandon the canonical chain and adopt a non-canonical one.

---

### Likelihood Explanation

Peras is currently disabled by default (the CHANGELOG notes: "if Peras is disabled (which is the default), there is no observable difference"). However:

- The code is already wired into the production path and will activate when Peras is enabled.
- The TODO comment at line 103 of `PerasCert.hs` explicitly acknowledges the stub is temporary, confirming this is a known incomplete state that has not yet been secured.
- No feature flag or compile-time guard prevents the stub from being called once Peras is enabled.
- Exploitation requires only a peer connection and knowledge of a block hash in the target node's VolatileDB — both trivially obtainable via the ChainSync mini-protocol.

---

### Recommendation

1. **Implement real certificate validation** in `validatePerasCert` before enabling Peras in production. At minimum this must verify: (a) the BLS aggregate signature over the `(electionId, candidate)` pair using the public keys of the claimed committee members; (b) that the claimed voters are eligible members of the committee for the given round (using the stake distribution and the WFALS/EveryoneVotes committee scheme); (c) that the boosted block's slot satisfies `perasBlockMinSlots`; and (d) that the certificate's round number is within the valid window (`perasCertMaxRounds`).

2. **Remove the universal `BlockSupportsPeras` instance** (lines 320–389 of `SupportsPeras.hs`) that provides the stub for all block types. Replace it with a proper instance for Cardano blocks only, so the type system prevents accidentally deploying an unvalidated path.

3. **Add a guard** in `processCerts` or `makePerasCertPoolWriterFromChainDB` that refuses to process any certificate when Peras is enabled but `validatePerasCert` is still the stub, failing loudly rather than silently accepting everything.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to the target node as a peer via the Peras certificate diffusion mini-protocol.
2. Obtain the hash and slot of a block `B` on a fork that is up to 15 blocks shorter than the canonical chain (observable via ChainSync).
3. Craft and send:
   ```
   PerasCert { pcCertRound = <any round not yet in DB>, pcCertBoostedBlock = BlockPoint <slot_of_B> <hash_of_B> }
   ```
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 })`.
5. The certificate is added to `PerasCertDB` and `addPerasCertAsync` is called.
6. `chainSelSync` finds `B` in `VolatileDB` and calls `chainSelectionForBlock`.
7. `preferAnchoredCandidate` computes `wsvTotalWeight` for the fork containing `B` as `blockNo(B) + 15`, which now exceeds the canonical chain's `blockNo(tip)` if the fork is ≤15 blocks shorter.
8. The node switches to the non-canonical fork. [6](#0-5) [7](#0-6) [8](#0-7) [9](#0-8)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
