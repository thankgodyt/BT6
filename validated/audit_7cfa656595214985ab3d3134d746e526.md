### Title
Unvalidated Peras Certificate Acceptance Enables Unprivileged Chain-Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` function in the default `BlockSupportsPeras` instance unconditionally returns `Right` for every certificate, performing no cryptographic or eligibility checks. Any unprivileged peer can therefore submit crafted `PerasCert` objects that are accepted into the `PerasCertDB`, update the `PerasWeightSnapshot`, and shift chain selection toward an adversarial fork — directly analogous to the permissionless `distributeRewards` call that manipulates vault state before `settleFunds` runs.

---

### Finding Description

**Root cause — stub validation always succeeds:**

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the catch-all instance for all `StandardHash blk` types. No BLS signature, no VRF eligibility proof, and no round-number sanity check is performed. The `ValidatedPerasCert` wrapper is supposed to be proof of validation, but it is trivially obtained.

**Accepted certificate immediately updates the weight snapshot:**

`implAddCert` in `PerasCertDB.Impl` inserts the certificate into `pcdbState` without any further check beyond a duplicate-round guard: [2](#0-1) 

`implGetWeightSnapshot` then builds a `PerasWeightSnapshot` from every certificate in the DB, assigning `vpcCertBoost` weight to the boosted block's `Point`: [3](#0-2) 

**Weight snapshot drives chain selection:**

`chainSelectionForBlock` and `constructPreferableCandidates` both read the weight snapshot atomically and pass it to `preferAnchoredCandidate`, which compares `wsvTotalWeight` (block-count + Peras boost) between the current chain and candidates: [4](#0-3) [5](#0-4) 

**`chainSelSync` for `ChainSelAddPerasCert` only checks slot age, not certificate authenticity:** [6](#0-5) 

The sole guard is `pointSlot boostedBlock < AF.anchorToSlotNo immTip`. There is no check on round-number validity, voter eligibility, or cryptographic signature.

---

### Impact Explanation

An unprivileged peer can submit N crafted certificates (one per distinct `PerasRoundNo`) all targeting the same block on an adversarial fork. Each accepted certificate adds `perasWeight params` to that block's weight in the `PerasWeightSnapshot`. Once the accumulated boost exceeds the honest chain's length advantage, `preferAnchoredCandidate` returns `ShouldSwitch` and the node adopts the adversarial fork. This is a **High** chain-selection bug: an honest node is made to prefer a non-canonical chain beyond the intended security assumptions, without any stake majority or key compromise.

---

### Likelihood Explanation

The attack entry point is the Peras certificate miniprotocol, reachable from any connected peer. The attacker needs only to:
1. Have blocks for an adversarial fork present in the target node's VolatileDB (achievable by serving headers/blocks via ChainSync/BlockFetch).
2. Submit enough certificates (one per round, each costing a single network message) to accumulate sufficient weight.

No privileged access, no key material, and no stake majority is required. The only constraint is that the boosted block's slot must not be older than the immutable tip, which is easily satisfied for recent forks.

---

### Recommendation

1. **Implement `validatePerasCert` properly** before enabling Peras on any network. The function must verify the aggregate BLS signature over `(roundNo, boostedBlock)` against the committee's public keys, and confirm that the signers' combined stake meets the quorum threshold. The existing TODO at issue `cardano-peras#120` tracks this.
2. **Reject certificates whose `pcCertRound` is in the future** (beyond the current slot's Peras round) to prevent pre-emptive weight accumulation.
3. **Enforce one-certificate-per-round at the network boundary**, not only inside `PerasCertDB`, so that equivocating or spurious certificates are dropped before touching the weight snapshot.

---

### Proof of Concept

1. Honest node A has current chain `C` of length 10 (weight 10). Peras `perasWeight` = 5.
2. Attacker serves adversarial fork `F` of length 8 (weight 8) to node A via BlockFetch; `F` is now in node A's VolatileDB.
3. Attacker submits 3 crafted `PerasCert` objects (rounds 1, 2, 3) each with `pcCertBoostedBlock = tip(F)`.
4. Each certificate passes `validatePerasCert` (returns `Right` unconditionally) and is inserted into `PerasCertDB`.
5. `PerasWeightSnapshot` now assigns weight 15 (3 × 5) to `tip(F)`.
6. `totalWeightOfFragment` for `F` = 8 (length) + 15 (boost) = 23 > 10 (weight of `C`).
7. Next call to `constructPreferableCandidates` returns `F` as preferred; `chainSelection` validates and commits `F`; node A switches to the adversarial fork. [7](#0-6) [8](#0-7)

implAddCert ::
  IOLike m =>
  PerasCertDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)
    pure addPerasCertRes

    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
