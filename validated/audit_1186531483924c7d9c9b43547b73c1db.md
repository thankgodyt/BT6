### Title
Peras Certificate Verification Bypass Allows Unprivileged Peer to Inject Arbitrary Weight Boosts into Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, `File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasCertDB/Impl.hs`)

---

### Summary

The `validatePerasCert` function in `SupportsPeras.hs` is a stub that unconditionally returns `Right` without performing any cryptographic or structural validation of a Peras certificate. Downstream, `implAddCert` in `PerasCertDB/Impl.hs` accepts any `ValidatedPerasCert` without checking that the certificate's boost weight is below the security parameter `k`. An unprivileged peer can therefore inject Peras certificates for arbitrary blocks — including non-canonical ones — bypassing the certificate-verification gate entirely and inserting weight boosts into the `PerasWeightSnapshot` that drives chain selection.

---

### Finding Description

**Vulnerability class:** Bypass of Peras certificate/signature validation checks; chain-selection weight manipulation.

**Root cause 1 — `validatePerasCert` is a no-op stub:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every call to `validatePerasCert` returns `Right` regardless of the certificate's content. No cryptographic proof, no round-number range check, no check that the boosted block exists on the current chain, and no check that the boost value is below `k`.

**Root cause 2 — `implAddCert` has no upper-bound check on the boost:** [2](#0-1) 

```haskell
-- TODO: we will need to update this method with non-trivial validation logic
-- see https://github.com/tweag/cardano-peras/issues/120
implAddCert PerasCertDbEnv{..} cert = do
  let roundNo = getPerasCertRound cert
  ...
  if Set.member roundNo (pcdsCertIds pcds)
    then pure PerasCertAlreadyInDB
    else do
      -- inserts cert unconditionally, no boost-vs-k check
```

The only guard is deduplication by round number. There is no check that `vpcCertBoost cert < maxRollbackWeight secParam`.

**Why the boost cap matters:**

`SecurityParam` is explicitly documented to bound the maximum rollback *weight* in Peras: [3](#0-2) 

```
-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14.
```

The test generator itself acknowledges that a boost ≥ k is invalid: [4](#0-3) 

```haskell
-- Generate an almost-always-valid boost, i.e., below the maximum rollback
let k = unPerasWeight (maxRollbackWeight secParam)
boost <-
  PerasWeight
    <$> frequency
      [ (10, choose (1, k - 1))
      , (1, choose (k, k + 1))   -- intentionally out-of-bounds for testing
      ]
```

No equivalent guard exists in the production path.

**Weight snapshot propagation into chain selection:**

Accepted certificates are immediately reflected in the `PerasWeightSnapshot` returned by `implGetWeightSnapshot`: [5](#0-4) 

That snapshot is consumed by `totalWeightOfFragment` and `takeVolatileSuffix`, which determine the immutable/volatile boundary and the preferred candidate chain: [6](#0-5) [7](#0-6)

### Impact Explanation

**Allowed impact category:** *Bypass of certificate/vote/certificate checks that enables unauthorized certificate acceptance* (Critical); and *chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain* (High).

Two concrete consequences:

1. **Certificate injection for non-canonical blocks.** Because `validatePerasCert` never rejects, a peer can submit a `PerasCert` whose `pcCertBoostedBlock` points to any block — including one on a minority fork. The boost (`perasWeight params = 15` by default) is added to that block's weight in the snapshot. One certificate per round is accepted; with a Peras round length of 90 slots and `k = 2160` blocks, an attacker can inject on the order of hundreds of certificates before they are garbage-collected, accumulating hundreds of weight units on a non-canonical chain. If the canonical and adversarial chains are close in length, this can tip chain selection toward the adversarial fork.

2. **Boost ≥ k accepted without error.** If `perasWeight params` is ever set to a value ≥ `k` (no production enforcement prevents this), a single accepted certificate causes `takeVolatileSuffix` to treat the boosted block as immutable even though it has not been copied to the ImmutableDB. This corrupts the ImmutableDB/VolatileDB split, causing the node to permanently accept the wrong ledger state.

---

### Likelihood Explanation

The entry path is fully reachable by any peer connected via the Peras mini-protocol. No special keys, stake, or operator access are required. The attacker only needs to craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` and submit it; `validatePerasCert` will accept it unconditionally. The deduplication-by-round-number guard in `implAddCert` is the only obstacle, and it is trivially circumvented by using a fresh round number for each injected certificate.

---

### Recommendation

1. **Implement `validatePerasCert` properly.** At minimum, verify that the boosted block exists in the node's chain, that the certificate's round number is within the valid window (`perasCertMaxRounds`), and that the boost value satisfies `vpcCertBoost < maxRollbackWeight secParam`. Track issue #120.

2. **Add a boost-cap guard in `implAddCert`.** Before inserting a certificate, assert `getPerasCertBoost cert < maxRollbackWeight secParam` and reject (or log and discard) certificates that violate this invariant — analogous to the deposit-cap check recommended in the external report.

3. **Enforce `perasWeight params < k` at configuration time.** Add a startup sanity check (similar to `sanityCheckSnapshotPolicyArgs`) that rejects configurations where `perasWeight >= maxRollbackWeight secParam`.

### Proof of Concept

```
1. Attacker connects to a node via the Peras certificate mini-protocol.
2. Attacker constructs PerasCert { pcCertRound = R, pcCertBoostedBlock = <minority-fork-block> }
   for a block on a minority fork that is within the volatile window.
3. Attacker calls the mini-protocol handler, which invokes:
     validatePerasCert params cert
   → always returns Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })
4. addPerasCertAsync is called with the ValidatedPerasCert.
5. implAddCert inserts the cert (round R not yet seen → passes dedup check).
6. implGetWeightSnapshot now includes (minority-fork-block, PerasWeight 15).
7. Chain selection via totalWeightOfFragment / compareAnchoredFragments
   now assigns extra weight to the minority fork.
8. Attacker repeats with fresh round numbers R+1, R+2, … accumulating
   weight on the minority fork until it is preferred over the canonical chain.

implAddCert ::

  PerasCertDbEnv m blk ->
  WithArrivalTime (ValidatedPerasCert blk) ->
  STM m (m AddPerasCertResult)
implAddCert PerasCertDbEnv{pcdbTracer, pcdbState} cert = do
  let roundNo = getPerasCertRound cert
  addPerasCertRes <- do
    WithFingerprint pcds fp <- readTVar pcdbState
    if Set.member roundNo (pcdsCertIds pcds)
      then pure PerasCertAlreadyInDB
      else do
        let pcdsLastTicketNo' = succ (pcdsLastTicketNo pcds)
            pcdsCertIds' = Set.insert roundNo (pcdsCertIds pcds)
            pcdsCertsByTicket' = Map.insert pcdsLastTicketNo' cert (pcdsCertsByTicket pcds)
            pcdsLatestCertSeen' = case pcdsLatestCertSeen pcds of
              Nothing -> Just cert
              Just prev
                | getPerasCertRound cert > getPerasCertRound prev -> Just cert
                | otherwise -> Just prev
        writeTVar pcdbState $
          WithFingerprint
            PerasCertDbState
              { pcdsCertIds = pcdsCertIds'
              , pcdsCertsByTicket = pcdsCertsByTicket'
              , pcdsLastTicketNo = pcdsLastTicketNo'
              , pcdsLatestCertSeen = pcdsLatestCertSeen'
              }
            (succ fp)
        pure AddedPerasCertToDB
  pure $ do
    traceWith pcdbTracer (AddCert roundNo cert addPerasCertRes)
    pure addPerasCertRes

-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back. Here, the total weight of a
-- chain (fragment) is defined to be its length plus the sum of all weight
-- boosts given to some of its blocks on the chain (fragment).
--
-- i.e. k == 30: we can roll back at most 30 unweighted blocks, or two blocks
-- each having additional weight 14. In the latter case, the chain fragment has
-- total weight @2 + 2 * 14 = 30@.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
  deriving (Eq, Generic, NoThunks, ToCBOR, FromCBOR)
  deriving Show via Quiet SecurityParam

-- | The maximum amount of weight we can roll back.
maxRollbackWeight :: SecurityParam -> PerasWeight
maxRollbackWeight = PerasWeight . unNonZero . maxRollbacks

takeVolatileSuffix ::
  forall blk h.
  (StandardHash blk, HasHeader h, HeaderHash blk ~ HeaderHash h) =>
  PerasWeightSnapshot blk ->
  -- | The security parameter @k@ is interpreted as a weight.
  SecurityParam ->
  AnchoredFragment h ->

takeVolatileSuffix snap secParam
  | Map.null $ getPerasWeightSnapshot snap =
      -- Optimize the case where Peras is disabled.
      AF.anchorNewest (unPerasWeight k)
  | otherwise =
      takeLongestSuffix (totalWeightOfFragment snap) (<= k)
 where
  k :: PerasWeight
  k = maxRollbackWeight secParam
