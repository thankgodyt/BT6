### Title
Silent nBTC Loss in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC contract unconditionally mints tokens into the bridge's own balance first, then silently returns `U128(0)` without transferring or recording anything if the recipient NEAR account is not registered for nBTC storage. The minted tokens are permanently stranded in the bridge's balance with no recovery path for the depositing user.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` executes in this order:

1. **Mint to bridge unconditionally** — `self.token.internal_deposit(&self.bridge_id, amount.into())` increases the bridge's nBTC balance by `amount`, regardless of whether the recipient is registered.
2. **Silent early return** — if `self.token.accounts.get(&account_id).is_none()` (recipient has no storage deposit), the function immediately returns `PromiseOrValue::Value(U128(0))`. No transfer is attempted, no error is raised, and no lost-found entry is created.
3. **No recovery** — the minted tokens remain in the bridge's balance. There is no mechanism in `safe_mint` or its callers to reclaim or credit these tokens to the user later. [1](#0-0) 

This is structurally identical to the external report's vulnerability class: a token transfer silently fails (here, is silently skipped) after the accounting side-effect (minting) has already been committed, leaving funds irrecoverably locked.

Compare with `mint_inner`, which auto-registers the account before depositing, ensuring the transfer always succeeds: [2](#0-1) 

`safe_mint` deliberately does not auto-register, but also does not roll back the `internal_deposit` on the early-return path — this is the root cause.

---

### Impact Explanation

- The satoshi-bridge calls `safe_mint` during the deposit flow after the Bitcoin light-client proof has already been verified and the deposit UTXO has been consumed/marked.
- If the recipient NEAR account is unregistered, `safe_mint` returns `U128(0)`. The satoshi-bridge callback receives this value; the deposit is treated as processed (proof already accepted by the light client).
- The user's BTC is locked on-chain. The equivalent nBTC is minted into the bridge's balance but is never credited to the user and has no recovery path.
- This constitutes **significant permanent loss of user funds** — the user loses their BTC deposit with no recourse.

The `lost_found` mechanism used in `transfer_nbtc_callback` for failed `ft_transfer` calls is entirely absent from `safe_mint`: [3](#0-2) 

---

### Likelihood Explanation

Any user who deposits BTC without first calling `storage_deposit` on the nBTC contract triggers this path. NEAR's storage-deposit requirement is non-obvious to users coming from EVM chains. New bridge users, users relying on dApps that do not pre-register accounts, or users whose storage registration expired are all realistic victims. No privileged access is required — the attacker surface is every public deposit.

---

### Recommendation

Do not call `internal_deposit` before confirming the recipient is registered. Either:

1. **Reorder the check**: verify `account_id` is registered before minting to the bridge, and revert if not.
2. **Add to `lost_found`**: if the recipient is unregistered, record the minted amount in the bridge's `lost_found` map (mirroring the pattern in `transfer_nbtc_callback`) so the user can recover after registering.
3. **Auto-register**: follow `mint_inner`'s pattern and call `internal_register_account` before depositing, eliminating the unregistered-account case entirely.

---

### Proof of Concept

1. User deposits BTC to their bridge deposit address on Bitcoin.
2. Relayer submits a valid `TxInclusionProof` to the satoshi-bridge; the light-client verifies inclusion.
3. satoshi-bridge calls `nbtc.safe_mint(user_account_id, amount, None)`.
4. Inside `safe_mint`: `self.token.internal_deposit(&self.bridge_id, amount.into())` executes — `amount` nBTC is now in the bridge's balance.
5. `self.token.accounts.get(&user_account_id).is_none()` → `true` (user never called `storage_deposit` on nBTC).
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — no transfer, no error, no lost-found entry.
7. The satoshi-bridge callback receives `U128(0)` and marks the deposit as processed (UTXO added to `verified_deposit_utxo`).
8. User has no nBTC. The `amount` nBTC sits in the bridge's balance, indistinguishable from protocol fees or other bridge-held tokens. User's BTC is permanently locked. [4](#0-3)

    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }

    pub fn transfer_nbtc_callback(&mut self, account_id: AccountId, amount: U128) -> bool {
        let promise_success = is_promise_success();
        let event = Event::TransferNbtc {
            account_id: &account_id,
            amount,
            success: promise_success,
        };
        if !promise_success {
            self.data_mut()
                .lost_found
                .entry(account_id.clone())
                .and_modify(|v| *v += amount.0)
                .or_insert(amount.0);
            Event::LostFoundNbtc {
                account_id: &account_id,
                amount,
            }
            .emit();
        }
        event.emit();
        promise_success
    }
