### Title
Bridge messages can be permanently lost when `fin_transfer` is paused — (File: `near/omni-bridge/src/lib.rs`)

### Summary
The NEAR `omni-bridge` contract's `fin_transfer` function is guarded by a `#[pause(except(roles(Role::DAO)))]` macro that blocks all non-DAO callers when the contract is paused. In the inbound transfer flow (EVM → NEAR or Solana → NEAR), tokens are irreversibly burned or locked on the source chain before the relayer attempts to finalize on NEAR. If the NEAR bridge is paused during the relay window, `fin_transfer` reverts for the relayer, and with no guaranteed indefinite retry and no source-chain refund path, the user's funds are permanently lost.

---

### Finding Description

The `fin_transfer` entry point in the NEAR bridge contract is decorated with the `near-plugins` pause macro:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn fin_transfer(&mut self, #[serializer(borsh)] args: FinTransferArgs) -> Promise {
``` [1](#0-0) 

When the contract is paused, this macro causes the function to panic for every caller that does not hold the `Role::DAO` role. The relayer — an unprivileged external account — is therefore completely blocked from finalizing inbound transfers.

The inbound transfer flow proceeds as follows:

**Step 1 — Source chain (EVM): tokens are irreversibly consumed.**

On the EVM side, `initTransfer` in `OmniBridge.sol` burns bridge tokens or locks native ERC-20s before emitting the event that the relayer will later prove on NEAR:

```solidity
} else if (isBridgeToken[tokenAddress]) {
    BridgeToken(tokenAddress).burn(msg.sender, amount);
} else {
    IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);
}
``` [2](#0-1) 

On the Solana side, `init_transfer` burns bridged tokens or locks native tokens into a vault before posting the Wormhole message:

```rust
burn(...)?;
// or
transfer_checked(...)?;
``` [3](#0-2) 

In both cases the source-chain action is atomic and irreversible: there is no cancel or refund instruction on the source chain.

**Step 2 — Destination chain (NEAR): finalization is blocked by pause.**

The relayer calls `fin_transfer` on NEAR with a proof of the source-chain event. If the NEAR bridge is paused at this moment, the call panics immediately via the `#[pause]` macro before any state is written: [4](#0-3) 

The `PauseManager` role (separate from `DAO`) can trigger a pause: [5](#0-4) 

**Step 3 — No recovery path.**

There is no on-chain mechanism that:
- stores the proof for deferred processing once the contract is unpaused, or
- allows the user to reclaim burned/locked tokens on the source chain.

The relayer must retry off-chain. If the relayer stops retrying (operator decision, infrastructure failure, economic disincentive), the user's funds are permanently lost.

---

### Impact Explanation

**Critical / High.** Tokens burned or locked on EVM or Solana cannot be recovered. The user suffers a complete, permanent loss of bridged funds with no on-chain recourse. The impact is identical to the reference vulnerability: assets destroyed on the source chain, never minted on the destination chain.

---

### Likelihood Explanation

**Low.** The NEAR bridge must be paused during the specific relay window between source-chain confirmation and NEAR finalization. Pauses are an intentional admin action (e.g., emergency response to an exploit), so the scenario is realistic but not routine. The `PauseManager` role is distinct from `DAO`, meaning a broader set of accounts can trigger a pause. [6](#0-5) 

---

### Recommendation

1. **Queue proofs during pause.** Store submitted proofs (or their hashes) in contract state when the contract is paused, and process them automatically upon unpause.
2. **Allow relayer retry without time limit.** Document and enforce an SLA that relayers must retry until the contract is unpaused.
3. **Source-chain escape hatch.** Provide a cancel/refund instruction on EVM and Solana that is only callable after a timeout and only if the NEAR transfer has not been finalized (requires cross-chain proof of non-finalization, which is complex but eliminates the loss scenario).
4. **Separate pause granularity.** Consider a finer-grained pause that blocks new outbound transfers (`initTransfer`) but never blocks inbound finalization (`fin_transfer`), mirroring the selective pause already implemented on EVM (`PAUSED_INIT_TRANSFER` vs `PAUSED_FIN_TRANSFER`). [7](#0-6) 

---

### Proof of Concept

1. User calls `initTransfer` on EVM with a bridge token (e.g., `wNEAR`). `BridgeToken.burn` is called; the user's tokens are gone.
2. The NEAR `PauseManager` pauses the bridge (e.g., in response to an unrelated security incident).
3. The relayer picks up the EVM event and calls `fin_transfer` on NEAR with the RLP proof.
4. The `#[pause(except(roles(Role::DAO)))]` macro fires; the transaction panics with `Contract is paused`.
5. The relayer retries several times, then stops (no SLA guarantee).
6. The NEAR bridge is eventually unpaused, but the relayer has already abandoned the message.
7. The user's tokens are burned on EVM and never minted on NEAR — permanent loss. [8](#0-7) [9](#0-8)

    pub fn fin_transfer(&mut self, #[serializer(borsh)] args: FinTransferArgs) -> Promise {
        require!(
            args.storage_deposit_actions.len() <= 3,
            BridgeError::InvalidStorageAccountsLen.as_ref()
        );
        let mut main_promise = self.verify_proof(args.chain_kind, args.prover_args);

        let mut attached_deposit = env::attached_deposit();

        for action in &args.storage_deposit_actions {
            main_promise =
                main_promise.and(Self::check_or_pay_ft_storage(action, &mut attached_deposit));
        }

        main_promise.then(

                .with_attached_deposit(attached_deposit)
                .with_static_gas(FIN_TRANSFER_CALLBACK_GAS)
                .fin_transfer_callback(
                    &args.storage_deposit_actions,
                    env::predecessor_account_id(),
                ),
        )
    }
