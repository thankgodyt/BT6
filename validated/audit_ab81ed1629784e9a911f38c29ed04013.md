Audit Report

## Title
Sub-Unit Amount Passes `init_transfer` But Panics in `sign_transfer`, Permanently Freezing Burned/Locked Tokens — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates only that `fee.fee < amount`, allowing transfers where the net amount normalizes to zero on the destination chain. After `init_transfer_internal` burns or locks the user's tokens and stores the transfer in `pending_transfers`, any subsequent call to `sign_transfer` will always panic at the `amount_to_transfer > 0` guard. No cancel or refund path exists for outbound pending transfers, so the user's funds are permanently frozen.

## Finding Description

**Root cause — missing normalization check at creation time:**

`init_transfer` (via `ft_transfer_call`) enforces only: [1](#0-0) 

This allows `amount = 500_000` with `fee = 0` to pass when `origin_decimals - decimals = 6`, because `0 < 500_000`.

`init_transfer_internal` then immediately burns or locks the full `amount` and stores the transfer: [2](#0-1) 

Later, `sign_transfer` calls `normalize_amount` using floor division: [3](#0-2) 

For `amount = 500_000` and `diff = 6`: `500_000 / 1_000_000 = 0`. The subsequent guard panics: [4](#0-3) 

**Why existing checks fail:**

- `sign_transfer_callback` only removes the transfer on a successful MPC signature — it is never reached because `sign_transfer` panics before the MPC call: [5](#0-4) 
- `claim_fee` (L1094) requires a `FinTransfer` proof from the destination chain, which can never exist because the transfer was never signed.
- `update_transfer_fee` can only increase the fee (`fee.fee >= current_fee.fee`), making `amount_without_fee` smaller and worsening the condition: [6](#0-5) 
- No `cancel_transfer` or equivalent function exists in the contract.

The panic is deterministic — the same inputs always produce the same result, so the transfer can never be processed or removed.

## Impact Explanation

This is a **permanent freezing of bridged funds** triggered by an unprivileged user through the standard `ft_transfer_call` → `init_transfer` flow. Once tokens are burned or locked in `init_transfer_internal` and the transfer is stored in `pending_transfers`, there is no on-chain path to recover them. This matches the Critical allowed impact: *permanent freezing of bridged funds across NEAR, EVM, Solana, Starknet*.

## Likelihood Explanation

Any token registered with `origin_decimals > decimals` (e.g., a 24-decimal NEAR-native token bridged to an 18-decimal EVM representation, giving `diff = 6`) is affected. A user sending fewer than `10^diff` base units — a realistic user error for high-precision tokens or small-value transfers — triggers the freeze. No attacker capability is required; the victim triggers it themselves through a normal bridge call. The condition is repeatable and permanent.

## Recommendation

Add a normalization check inside `init_transfer` (or at the top of `init_transfer_internal`) **before** storing the transfer and burning/locking tokens:

```rust
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the guard already present in `sign_transfer` at L482–485 but must be enforced at creation time, before any state mutation or token burn/lock occurs.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (`diff = 6`).
2. Call `ft_transfer_call` with `amount = 500_000`, `fee = 0`, destination = any EVM address.
3. `init_transfer` passes: `0 < 500_000`. ✓
4. `init_transfer_internal` burns 500,000 tokens and stores the transfer in `pending_transfers`.
5. Relayer calls `sign_transfer`. `normalize_amount(500_000, diff=6)` = `500_000 / 1_000_000` = `0`.
6. `require!(amount_to_transfer > 0)` panics → `InvalidAmountToTransfer`.
7. Transfer remains in `pending_transfers` indefinitely. Tokens are burned. No recovery path exists.

**Minimal test:** Write a NEAR integration test that registers a token with the above decimals, calls `ft_transfer_call` with a sub-unit amount, then calls `sign_transfer` and asserts it panics, then confirms the transfer still exists in `pending_transfers` and the token balance is reduced.
