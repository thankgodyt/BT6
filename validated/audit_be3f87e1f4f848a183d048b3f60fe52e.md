Audit Report

## Title
Silent `fee_recipient.parse().ok()` Causes Permanent `pending_transfer` Freeze and Relayer Fee Loss via `claim_fee_callback` Panic — (`near/omni-prover/wormhole-omni-prover-proxy/src/parsed_vaa.rs`, `near/omni-bridge/src/lib.rs`)

## Summary

In `TryInto<FinTransferMessage> for ParsedVAA`, the `fee_recipient` field is silently converted to `None` via `.parse().ok()` when the string is not a valid NEAR `AccountId`. The downstream `claim_fee_callback` unconditionally panics on `None` **before** `remove_transfer_message` is called. Because NEAR's receipt model only reverts state changes made within the panicking receipt, the `pending_transfer` entry — committed in a prior receipt — remains permanently in state with no admin escape hatch, freezing the storage deposit and permanently losing the relayer fee.

## Finding Description

**Root cause — silent `None` in the Wormhole prover proxy:**

`TryInto<FinTransferMessage> for ParsedVAA` at line 197 uses `.parse().ok()`:

```rust
fee_recipient: transfer.fee_recipient.parse().ok(),
``` [1](#0-0) 

Any `fee_recipient` string that fails `AccountId::from_str` — empty string, string with invalid characters, string exceeding 64 bytes — silently becomes `None`. No error is returned; `verify_vaa_callback` returns `Ok(ProverResult::FinTransfer(...))` with `fee_recipient: None`. This is inconsistent with the `InitTransferMessage` parser in the same file, which uses `.map_err(stringify)?` (a hard error) for its `recipient` field. [2](#0-1) 

The same silent pattern appears in the EVM event parser:

```rust
fee_recipient: event.data.feeRecipient.parse().ok(),
``` [3](#0-2) 

**Panic before state cleanup in `claim_fee_callback`:**

`claim_fee_callback` panics at line 1079–1081 when `fee_recipient` is `None`:

```rust
let fee_recipient = fin_transfer.fee_recipient.unwrap_or_else(|| {
    env::panic_str(BridgeError::FeeRecipientNotSetOrEmpty.to_string().as_str());
});
``` [4](#0-3) 

`remove_transfer_message` — which removes the entry from `pending_transfers` and refunds the storage deposit — is only called at line 1094, after the panic point. [5](#0-4) 

In NEAR's execution model, a panic in a callback reverts only that callback's own state mutations. The `pending_transfer` was inserted in a prior receipt and is not touched by this panic, so it remains in `pending_transfers` indefinitely.

**No recovery path:**

A search for any DAO/admin function to force-remove a `pending_transfer` returns no results. `remove_transfer_message` is only reachable through `claim_fee_callback` (and one other internal path), and the same VAA re-submitted will always produce `fee_recipient: None` and always panic. [6](#0-5) 

## Impact Explanation

When `pending_transfer` cannot be removed:

1. **Storage deposit frozen**: `remove_transfer_message` credits the storage refund back to `accounts_balances` for the transfer owner. This never executes, permanently locking the NEAR storage deposit.
2. **`locked_tokens` counter not decremented**: `send_fee_internal` (which decrements `locked_tokens`) is never reached, permanently inflating the accounting counter for that `(chain, token)` pair, which can affect future bridge operations.
3. **Relayer fee permanently lost**: The relayer cannot claim their fee for the finalized transfer; the fee amount remains locked in the bridge contract with no withdrawal path.

This matches the Critical impact class: **permanent freezing of bridged funds** (storage deposits and relayer fees locked with no recovery path) and **fee mis-accounting** (`locked_tokens` permanently inflated).

## Likelihood Explanation

The precondition is a Wormhole-signed VAA reaching `claim_fee` with an invalid `fee_recipient` string. The `#[trusted_relayer]` gate on `claim_fee` requires the caller to be a staked relayer. [7](#0-6) 

The EVM `FinTransfer` event defines `feeRecipient` as a plain Solidity `string` with no on-chain validation of NEAR account ID format. [8](#0-7) 

If the source-chain bridge contract permits any caller to supply an arbitrary `feeRecipient` string when finalizing a transfer (a common pattern in permissionless bridge designs), an attacker can emit a legitimate `FinTransfer` event with `feeRecipient = ""`, obtain a valid Wormhole-signed VAA, stake to become a trusted relayer, and submit the VAA. The same VAA can be re-submitted indefinitely, always producing the same panic. A relayer software bug encoding an invalid NEAR account ID is an additional realistic trigger.

## Recommendation

Replace the silent `.parse().ok()` with a hard error in both parsers:

```rust
// parsed_vaa.rs and evm/events.rs
fee_recipient: if transfer.fee_recipient.is_empty() {
    None
} else {
    Some(transfer.fee_recipient.parse().map_err(stringify)?)
},
```

Additionally, `claim_fee_callback` should return `Err` (not panic) when `fee_recipient` is `None`, so the callback fails gracefully without leaving `pending_transfer` stranded. A DAO-gated `force_remove_pending_transfer` escape hatch should be added to recover any future stuck entries.

## Proof of Concept

**Unit test** (`parsed_vaa.rs`): Construct a `FinTransferWh` with `fee_recipient = ""`, Borsh-encode it as a fake VAA payload, call `TryInto<FinTransferMessage>`, assert `fee_recipient == None` — demonstrating the silent conversion.

**Integration test** (`claim_fee_callback`): Insert a `pending_transfer` into state. Call `claim_fee_callback` with `ProverResult::FinTransfer(FinTransferMessage { fee_recipient: None, .. })`. Assert the call panics with `FeeRecipientNotSetOrEmpty`. Then assert `get_transfer_message(transfer_id)` still returns the entry — proving it was not removed and is permanently stranded.         #[serializer(borsh)]
        call_result: Result<ProverResult, PromiseError>,

    fn remove_transfer_message(&mut self, transfer_id: TransferId) -> TransferMessage {
        let storage_usage = env::storage_usage();
        let transfer = self
            .pending_transfers
            .remove(&transfer_id)
            .map(storage::TransferMessageStorage::into_main)
            .near_expect(BridgeError::TransferNotExist);

        let refund =
            env::storage_byte_cost().saturating_mul((storage_usage - env::storage_usage()).into());

        if let Some(mut storage) = self.accounts_balances.get(&transfer.owner) {
            storage.available = storage.available.saturating_add(refund);
            self.accounts_balances.insert(&transfer.owner, &storage);
        }

        transfer.message
    }
