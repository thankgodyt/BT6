Audit Report

## Title
Native SOL `native_fee` Permanently Locked in `sol_vault` with No Withdrawal Path — (File: `solana/programs/bridge_token_factory/src/instructions/user/init_transfer.rs`)

## Summary
When a user calls `init_transfer` to bridge SPL tokens with a non-zero `native_fee`, that SOL is transferred into the `sol_vault` PDA. No instruction in the program — admin or user — withdraws these accumulated fee lamports. The NEAR side compensates the relayer by minting wrapped SOL, leaving the actual deposited SOL permanently locked in `sol_vault` on Solana.

## Finding Description
In `init_transfer.rs` (L75–86), when `payload.native_fee > 0`, the program executes a system `transfer` from the user to `sol_vault`: [1](#0-0) 

The only instruction that ever withdraws from `sol_vault` is `finalize_transfer_sol`, which transfers exactly `data.amount` — the bridged SOL principal — to the recipient: [2](#0-1) 

The complete set of admin instructions (`change_config`, `initialize`, `pause`, `update_metadata`) contains no `sol_vault` withdrawal logic:


The complete set of user instructions (`deploy_token`, `finalize_transfer`, `finalize_transfer_sol`, `get_version`, `init_transfer`, `init_transfer_sol`, `log_metadata`) likewise contains no fee-withdrawal instruction:


On the NEAR side, `send_fee_internal` compensates the relayer by **minting** wrapped SOL (the native token for the Solana origin chain) rather than claiming the actual deposited lamports: [3](#0-2) 

This means the Solana-side `native_fee` lamports deposited into `sol_vault` are never claimed by any party.

## Impact Explanation
Every `init_transfer` call with `native_fee > 0` permanently locks that SOL in the `sol_vault` PDA. The `sol_vault` balance grows monotonically beyond what is needed to service `finalize_transfer_sol` withdrawals. The excess is irrecoverable without a program upgrade. This constitutes **permanent freezing of protocol fee funds** and **fee mis-accounting** — both matching the Critical allowed impact scope ("permanent freezing of bridged funds" and "fee mis-accounting… that changes user or protocol balances").

## Likelihood Explanation
This is triggered by any unprivileged user calling `init_transfer` with a non-zero `native_fee`, which is the standard, documented operating mode for SPL-token bridge transfers where the user pays a SOL-denominated relayer fee. No special attacker capability is required — normal bridge usage triggers the condition on every such transfer.

## Recommendation
Add an admin-gated `withdraw_fees` instruction that signs with the `sol_vault` PDA seeds and transfers `sol_vault.lamports() - rent_exempt_minimum` to a designated fee recipient. This ensures accumulated `native_fee` lamports are recoverable by the authorized party without disrupting the SOL bridging principal held for `finalize_transfer_sol`.

## Proof of Concept
1. User calls `init_transfer` with any SPL token, `amount = 1_000_000`, `fee = 100`, `native_fee = 5_000_000`.
2. `init_transfer.process()` transfers 5,000,000 lamports from the user to `sol_vault` (L75–86 of `init_transfer.rs`).
3. The Wormhole VAA is relayed; the NEAR bridge calls `send_fee_internal`, which mints wrapped SOL to the relayer via `ext_token::mint` (NEAR `lib.rs` L2669–2672). The relayer is compensated on NEAR.
4. The 5,000,000 lamports remain in `sol_vault` on Solana. No instruction exists to withdraw them.
5. Repeat for every SPL-token bridge transfer with `native_fee > 0`. The `sol_vault` balance grows unboundedly. The excess beyond the rent-exempt minimum and any pending `finalize_transfer_sol` amounts is permanently irrecoverable.
