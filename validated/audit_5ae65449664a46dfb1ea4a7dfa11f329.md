### Title
Non-Transitive `RestrictedVRFTiebreaker` Chain Order Enables Path-Dependent Consensus Divergence - (File: `ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos/Common.hs`)

---

### Summary

The `ChainOrder` instance for `PraosTiebreakerView` under `RestrictedVRFTiebreaker` — active for all Conway-and-later eras — is explicitly non-transitive. Because `preferCandidate` only arms the VRF comparison when the two chain tips are within `maxDist = 5` slots of each other, an adversary controlling stake pools can craft a sequence of three competing equal-length chains (A, B, C) such that a node transitioning A→B→C ends on C, while a node that only ever sees A vs C stays on A. Two honest nodes end up on permanently different chains without either violating any local rule.

---

### Finding Description

`comparePraos` in `Praos/Common.hs` drives both the `Ord` instance (always uses `UnrestrictedVRFTiebreaker`) and the `ChainOrder` instance (uses the configured `VRFTiebreakerFlavor`). [1](#0-0) 

When `tiebreakerFlavor = RestrictedVRFTiebreaker maxDist`, `vrfArmed` returns `False` whenever `slotDist v1 v2 > maxDist`, causing the comparison to fall through to the catch-all `(False, _, False, _) -> ShouldNotSwitch EQ`. [2](#0-1) 

The code itself documents the resulting non-transitivity: [3](#0-2) 

For Conway era, `mkShelleyBlockConfig` hard-codes `maxDist = 5`: [4](#0-3) 

`SelectView.preferCandidate` delegates to the tiebreaker exactly when block numbers are equal: [5](#0-4) 

The `ChainOrder` class requires only one-way consistency with `Ord` ("if `ours ⊏ cand` then `ours < cand`"), not the converse: [6](#0-5) 

This means `Ord` (unrestricted) may rank chain C above chain A, yet `preferCandidate (RestrictedVRFTiebreaker 5) A C = ShouldNotSwitch EQ`. The `Ord` instance is used for candidate prioritization in initial chain selection and BlockFetch: [7](#0-6) 

---

### Impact Explanation

The non-transitivity makes chain selection **path-dependent**: the chain a node ends up on depends on the order in which it encounters competing candidates, not solely on their intrinsic properties. Two honest nodes that apply `preferCandidate` correctly and locally can permanently diverge:

- **Node 1** (receives B, then C): A → B (VRF armed, switches) → C (VRF armed, switches). Final: **C**.
- **Node 2** (receives C without first seeing B): A vs C — slot distance 6 > 5, VRF disarmed, `ShouldNotSwitch EQ`. Final: **A**.

Neither node has violated any local rule. The result is a persistent, irreconcilable chain split — a consensus safety failure. This is the direct Ouroboros analog of the Clique single-node issue: in Clique, equal difficulty makes canonical selection impossible and nodes prefer whichever fork arrived first; here, the disabled tiebreaker makes canonical selection impossible for chains whose tips are more than 5 slots apart, and nodes prefer whichever ordering they happened to observe.

**Impact class**: High — chain-selection bug that lets a network-capable adversary make honest nodes permanently prefer different chains.

---

### Likelihood Explanation

The adversary needs:

1. **Two stake pools elected in nearby slots** (e.g., slots 3 and 6 at the same block height) to produce competing chains B and C. This requires some stake but not a majority.
2. **Selective delivery**: broadcast B to a subset of nodes before broadcasting C, so that those nodes transition A→B→C while others only ever compare A vs C directly.

A stake pool operator already controls when and to whom they relay their own blocks. By withholding block B from a partition of the network and then releasing C globally, the adversary achieves the divergence without any cryptographic break or admin-level access. The slot distance threshold of 5 is small enough that naturally occurring slot gaps between competing blocks (common during network partitions or slow diffusion) can satisfy the condition without deliberate crafting.

---

### Recommendation

1. **Short term**: Document explicitly that `RestrictedVRFTiebreaker` breaks the transitivity assumption that Ouroboros safety proofs rely on, and add a property-based test asserting that no three reachable `PraosTiebreakerView` triples (A, B, C) satisfy `preferCandidate A B ∧ preferCandidate B C ∧ ¬preferCandidate A C` under the production `maxDist = 5` configuration.

2. **Medium term**: Replace the slot-distance gate with a monotone function that preserves transitivity — for example, by using a weighted combination of slot distance and VRF value that is still a total order, or by only suppressing the VRF comparison when the candidate's slot is *strictly later* than ours by more than `maxDist` (one-sided gate), which eliminates the non-transitive triangle.

3. **Long term**: Formally verify that the chosen `ChainOrder` instance satisfies the transitivity property required by the Ouroboros security proof, either in the existing Agda specification or via a mechanized proof obligation attached to the `ChainOrder` type class.

### Proof of Concept

Using `RestrictedVRFTiebreaker 5` (production Conway configuration):

```
Chain A: block N, slot 0, VRF output 3  (honest tip)
Chain B: block N, slot 3, VRF output 2  (adversary fork 1)
Chain C: block N, slot 6, VRF output 1  (adversary fork 2)
```

**Step 1 — `preferCandidate cfg A B`** (`comparePraos (RestrictedVRFTiebreaker 5) A B`):
- `issueNoArmed = False` (different issuers)
- `vrfArmed = True` (slotDist 3 ≤ 5)
- `compare (Down 3) (Down 2) = LT` → **`ShouldSwitch`** ✓

**Step 2 — `preferCandidate cfg B C`**:
- `issueNoArmed = False`
- `vrfArmed = True` (slotDist 3 ≤ 5)
- `compare (Down 2) (Down 1) = LT` → **`ShouldSwitch`** ✓

**Step 3 — `preferCandidate cfg A C`**:
- `issueNoArmed = False`
- `vrfArmed = False` (slotDist 6 > 5) ← gate fires
- Falls to `(False, _, False, _) -> ShouldNotSwitch EQ` → **`ShouldNotSwitch`** ✓

**Delivery sequence**:
- Adversary broadcasts B to Node 1 only → Node 1 switches A→B.
- Adversary broadcasts C to all nodes → Node 1 switches B→C; Node 2 compares A vs C and stays on A.

**Result**: Node 1 on C, Node 2 on A. Persistent divergence with no local rule violation on either node. [8](#0-7) [9](#0-8) [4](#0-3)

```haskell
-- Used to implement the 'Ord' and 'ChainOrder' instances for Praos.
comparePraos ::
  VRFTiebreakerFlavor ->
  PraosTiebreakerView c ->
  PraosTiebreakerView c ->
  ShouldSwitch (PraosReasonForSwitch c)
comparePraos tiebreakerFlavor ours cand =
  case ( issueNoArmed ours cand
       , (compare `on` ptvIssueNo) ours cand
       , vrfArmed ours cand
       , (compare `on` Down . ptvTieBreakVRF) ours cand
       ) of
    -- IssueNo armed: compare OCert issue numbers
    (True, LT, _, _) -> ShouldSwitch (HigherOCert (Comparing (ptvIssueNo ours) (ptvIssueNo cand)))
    (True, GT, _, _) -> ShouldNotSwitch GT
    -- IssueNo armed and equal issue numbers, VRF armed: use VRF tiebreaker
    (True, EQ, True, GT) -> ShouldNotSwitch GT -- ours has better VRF
    (True, EQ, True, EQ) -> ShouldNotSwitch EQ
    (True, EQ, True, LT) -> ShouldSwitch (VRFTiebreak (Comparing (ptvTieBreakVRF ours) (ptvTieBreakVRF cand)))
    -- IssueNo armed and equal, VRF not armed: no tiebreaker
    (True, EQ, False, _) -> ShouldNotSwitch EQ
    -- IssueNo not armed, VRF armed: use VRF tiebreaker
    (False, _, True, GT) -> ShouldNotSwitch GT -- ours has better VRF
    (False, _, True, EQ) -> ShouldNotSwitch EQ
    (False, _, True, LT) -> ShouldSwitch (VRFTiebreak (Comparing (ptvTieBreakVRF ours) (ptvTieBreakVRF cand)))
    -- IssueNo not armed, VRF not armed: no tiebreaker
    (False, _, False, _) -> ShouldNotSwitch EQ
 where
  -- Only compare the issue numbers when the issuers and slots are identical.
  -- Note that this case implies the VRFs also coincide.
  issueNoArmed v1 v2 =
    ptvSlotNo v1 == ptvSlotNo v2
      && ptvIssuer v1 == ptvIssuer v2

  -- Whether to do a VRF comparison.
  vrfArmed v1 v2 = case tiebreakerFlavor of
    UnrestrictedVRFTiebreaker -> True
    RestrictedVRFTiebreaker maxDist ->
      slotDist (ptvSlotNo v1) (ptvSlotNo v2) <= maxDist

  slotDist :: SlotNo -> SlotNo -> SlotNo
  slotDist s t
    -- slot numbers are unsigned, so have to take care with subtraction
    | s >= t = s - t
    | otherwise = t - s
```

```haskell
--
```
