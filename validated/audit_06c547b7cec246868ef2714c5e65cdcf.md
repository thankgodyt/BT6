### Title
Degenerate `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Peras Certificate Without Cryptographic Verification — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance in `SupportsPeras.hs` implements `validatePerasCert` to unconditionally return `Right` for every certificate it receives, performing zero cryptographic or quorum checks. This instance is wired directly into the production Peras certificate ingestion path (`makePerasCertPoolWriterFromChainDB` → `processCerts`). Any unprivileged peer can therefore inject a `PerasCert` with an arbitrary round number and an arbitrary boosted-block point; the certificate will be stored in the `ChainDB` with the full configured `perasWeight` boost, manipulating chain selection in favour of the attacker's chosen block.

---

### Finding Description

**Root cause — `validatePerasCert` always succeeds**

`SupportsPeras.hs` defines a universal catch-all instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

No signature is checked, no quorum is verified, no voter eligibility is confirmed. The function ignores every field of `cert` and returns a fully `ValidatedPerasCert` carrying the maximum configured weight boost.

**Production wiring — `makePerasCertPoolWriterFromChainDB`**

The production certificate pool writer for the `ChainDB` calls this function directly:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { ...
    , opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions the batch into valid/invalid using the supplied `validateCert` function. Because `validatePerasCert` never returns `Left`, every certificate in every batch is classified as valid and forwarded to `ChainDB.addPerasCertAsync`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _) ->
      throw (PerasCertValidationError errs)
``` [3](#0-2) 

The `(errs, _)` branch is **never reached** because `validatePerasCert` always produces `Right`.

**The degenerate `PerasCert` type carries no signature**

The certificate type in the degenerate instance has no cryptographic field at all:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound       :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [4](#0-3) 

An attacker supplies only a round number and a block point — no BLS aggregate signature, no VRF eligibility proof, no quorum evidence. There is nothing to verify even if the code tried.

**Contrast with the real V1 certificate type**

The concrete `V1.PerasCert` used by the actual Peras implementation carries `pcVoters` and `pcSignature` (an aggregate BLS signature), and the `EveryoneVotes` committee verifies the aggregate signature and seat membership before accepting a certificate: [5](#0-4) [6](#0-5) 

The degenerate instance bypasses all of this.

---

### Impact Explanation

**Impact: High — chain selection manipulation by an unprivileged peer.**

Peras certificates grant a configurable weight boost (`perasWeight`) to the block they certify. Chain selection compares candidate chains by weight; a boosted block is preferred over an unboosted one of equal or even greater length. An attacker who can inject a `ValidatedPerasCert` for an arbitrary block point can therefore:

1. **Force the victim node to prefer a non-canonical chain.** By injecting a certificate for a block on a minority fork, the attacker makes that fork appear heavier than the honest majority chain, causing the node to switch away from the canonical chain.
2. **Override a legitimate certificate for the current round.** Because `processCerts` skips certificates whose `pcCertRound` is already in the database, the attacker can race to inject a fake certificate for the current round before the honest one arrives, permanently preventing the legitimate certificate from being stored for that round.

This directly matches the "High" impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**Likelihood: High.**

- The attacker needs only a standard peer connection to the target node; no keys, no stake, no privileged access.
- The `PerasCert` wire format is trivially constructable: two fields (`pcCertRound`, `pcCertBoostedBlock`), no signature.
- The validation gate (`validatePerasCert`) is a compile-time no-op; there is no runtime defence.
- The only natural filter is the "already in DB" deduplication check, which the attacker trivially avoids by targeting a round not yet seen.

---

### Recommendation

1. **Remove or gate the degenerate instance.** The `instance StandardHash blk => BlockSupportsPeras blk` catch-all must not be reachable in any code path that processes network input. Either restrict it to a newtype wrapper used only in tests, or guard it behind a compile-time flag that is disabled in production builds.

2. **Implement real validation before the instance is used in production.** `validatePerasCert` must verify: (a) the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` against the aggregated public keys of the claimed voters; (b) that each claimed voter seat index is within bounds and has non-zero stake; (c) that the total stake of the voters meets the quorum threshold. The `EveryoneVotes` committee already implements this logic correctly in `implVerifyCert`.

3. **Resolve the linked issues** (`cardano-peras/issues/73` and `cardano-peras/issues/120`) before enabling Peras certificate diffusion on any network where the degenerate instance is the active `BlockSupportsPeras` instance.

---

### Proof of Concept

**Preconditions:** A node running with Peras certificate diffusion enabled, using the degenerate `BlockSupportsPeras` instance (i.e., no concrete `BlockSupportsPeras CardanoBlock` instance overriding the catch-all).

**Steps:**

1. Establish a peer connection to the target node via the Peras object-diffusion mini-protocol.
2. Craft a `PerasCert` with:
   - `pcCertRound = <current Peras round>`
   - `pcCertBoostedBlock = <point of an attacker-controlled block on a minority fork>`
3. Send the certificate to the node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params })` unconditionally.
5. The certificate is timestamped and forwarded to `ChainDB.addPerasCertAsync`.
6. Chain selection now treats the attacker's block as carrying the full `perasWeight` boost.
7. If the boosted fork is otherwise competitive (e.g., equal block count), the node switches to the attacker's fork.

**Expected outcome:** The node adopts a non-canonical chain. A legitimate certificate for the same round arriving later is silently dropped by the "already in DB" filter at line 166 of `PerasCert.hs`, making the attack durable for that round. [7](#0-6)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

implVerifyCert committee = \case
  EveryoneVotesCert electionId candidate voters aggSig -> do
    -- Traverse the list of voters in ascending seat index order, collecting:
    -- 1. their membership status
    -- 2. their vote verification keys (to verify the aggregate vote signature)
    (members, voteVerificationKeys) <-
      fmap munzip . flip traverse (NESet.toAscList voters) $ \case
        seatIndex
          | Just (_, voterPublicKey, voterStake, _) <-
              getCandidateIfSeatWithinBounds seatIndex (extWFAStakeDistr committee) -> do
              let voterVerificationKey =
                    getVoteVerificationKey (Proxy @crypto) voterPublicKey
              case nonZero voterStake of
                Nothing ->
                  Left (PoolHasNoStake seatIndex)
                Just nonZeroVoterStake ->
                  pure
                    ( EveryoneVotesMember
                        seatIndex
                        nonZeroVoterStake
                    , voterVerificationKey
                    )
          | otherwise ->
              Left (MissingSeatIndex seatIndex)
    -- Verify aggregate signature
    aggVerificationKey <-
      bimap CryptoError id $ do
