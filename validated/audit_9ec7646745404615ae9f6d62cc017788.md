Audit Report

## Title
Bridged Funds Permanently Locked When Transfer Amount Normalizes to Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` accepts any transfer where `fee < amount` and immediately burns or locks the tokens on NEAR. `sign_transfer` later enforces a stricter implicit minimum by requiring `normalize_amount(amount - fee) > 0`. For tokens with a large decimal difference between NEAR and the destination chain (e.g., `origin_decimals = 24`, `decimals = 18`), any net amount below the normalization factor (`10^6`) causes `sign_transfer` to permanently revert with `ERR_INVALID_AMOUNT_TO_TRANSFER`. Because no `cancel_transfer` or user-callable refund path exists, the tokens are irrecoverably burned or locked on NEAR.

## Finding Description

**`init_transfer` — no normalized-amount minimum:**

`init_transfer` constructs the `TransferMessage` and validates only that `fee < amount`:

```rust
// near/omni-bridge/src/lib.rs L554-557
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

It then immediately calls `init_transfer_internal`, which burns or locks the tokens:

```rust
// near/omni-bridge/src/lib.rs L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

At this point the transfer is stored in `pending_transfers` and the tokens are gone from the user's account.

**`sign_transfer` — implicit minimum via floor division:**

`sign_transfer` normalizes the net amount for the destination chain using floor division:

```rust
// near/omni-bridge/src/lib.rs L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message
        .amount_without_fee()
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`normalize_amount` divides by `10^(origin_decimals - decimals)`:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For `origin_decimals = 24`, `decimals = 18`, the divisor is `10^6`. Any `amount - fee < 1_000_000` yields `0`, causing `sign_transfer` to always panic.

**No recovery path:**

A search across the entire repository confirms there is no `cancel_transfer` or `refund_transfer` function. The only internal removal helper is `remove_transfer_message_without_refund`, which is called only on storage-balance failure during `init_transfer_internal` — not as a user-callable escape hatch. Once `init_transfer_internal` succeeds past the storage check and burns/locks tokens, there is no code path that can return them.

## Impact Explanation

This is a concrete, permanent loss of bridged funds triggered entirely through normal bridge usage. The tokens are burned (for deployed tokens) or locked (for native tokens) on NEAR, the transfer record sits in `pending_transfers` indefinitely, and every `sign_transfer` call for that transfer ID will revert. This matches the Critical impact category: **permanent freezing of bridged funds**.

## Likelihood Explanation

- NEAR-native tokens standardly use 24 decimals; EVM representations standardly use 18 decimals. The 6-decimal gap and `10^6` normalization factor are the default production configuration.
- Any unprivileged user who calls `ft_transfer_call` with a net amount below `10^6` base units triggers the bug. No special role, leaked key, or external condition is required.
- `init_transfer` gives no error or warning — the transaction succeeds and the user has no indication their funds are permanently stuck until a relayer attempts `sign_transfer`.
- The condition is repeatable and deterministic: every transfer with `amount - fee < 10^6` for this decimal configuration will be permanently locked.

## Recommendation

Add a normalized-amount minimum check inside `init_transfer` (before burning/locking tokens), mirroring the check already present in `sign_transfer`:

```rust
let amount_to_transfer = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0)
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This requires looking up `token_decimals` for the destination chain at `init_transfer` time, which is already done in `sign_transfer`. Alternatively, implement a user-callable `cancel_transfer` that allows the original sender to reclaim tokens from a pending transfer that has never been signed.

## Proof of Concept

1. Register a token with `origin_decimals = 24` (NEAR) and `decimals = 18` (EVM). Normalization factor = `10^6`.
2. Alice calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`. `init_transfer` passes the `fee < amount` check (0 < 500_000). `init_transfer_internal` burns/locks Alice's 500_000 base units and stores the transfer in `pending_transfers`.
3. A relayer calls `sign_transfer` for Alice's transfer ID. `normalize_amount(500_000, {origin_decimals:24, decimals:18}) = 500_000 / 1_000_000 = 0`. The `require!(amount_to_transfer > 0, ...)` check panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`.
4. No `cancel_transfer` exists. Alice's 500_000 base units are permanently burned/locked on NEAR with no recovery path.
