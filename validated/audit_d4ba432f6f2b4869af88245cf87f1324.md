### Title
Unvalidated `key_version` and Missing Caller Identity Check in `sign_btc_transaction` Allows Any User to Corrupt Withdrawal Signing, Causing Stuck Bridge State - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

`sign_btc_transaction` is a public, permissionless function that accepts a caller-supplied `key_version: u32` parameter with no validation against any stored expected value, and performs no check that the caller is the owner of the pending withdrawal. Any NEAR account can invoke it for any pending withdrawal with an arbitrary `key_version`. If the MPC service signs with the wrong key version, the resulting signature is cryptographically valid from the MPC's perspective but invalid for the Bitcoin UTXO's script. Once all inputs are "signed" (even with wrong-key signatures), the state irreversibly transitions to `PendingVerify`, the malformed transaction is broadcast, Bitcoin rejects it, and the withdrawal is permanently stuck — requiring privileged operator intervention to cancel.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is decorated only with `#[payable]` and `#[pause(except(roles(Role::DAO)))]`. There is no `#[access_control_any]` guard and no runtime check that `env::predecessor_account_id() == btc_pending_info.account_id`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    btc_pending_info.assert_pending_sign();
    // ... RBF cleanup only ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
```

The `key_version` parameter selects which MPC key version is used to produce the signature. The contract stores no expected `key_version` in `BTCPendingInfo` and performs no comparison. The `btc_pending_sign_id` is deterministic (derived from the PSBT hash) and observable on-chain, so any attacker can discover it.

When the last input is signed — regardless of whether the `key_version` was correct — the state machine transitions from `PendingSign` to `PendingVerify` (via `to_pending_verify_stage`). At that point `assert_pending_sign()` will panic on any subsequent call, making re-signing impossible without operator cancellation.

The `BTCPendingInfo` struct stores signatures as `Vec<Option<SignatureResponse>>`. Once a slot is filled and the stage advances, the signing window is closed.

---

### Impact Explanation

A user initiates a withdrawal by transferring nBTC to the bridge via `ft_transfer_call`. The bridge immediately removes the corresponding UTXOs from the available pool and creates a `BTCPendingInfo` in `PendingSign` state. The user's nBTC is held by the bridge.

If an attacker corrupts the signing by supplying a wrong `key_version`:

1. The MPC produces a signature under a key that does not correspond to the UTXO's locking script.
2. Once all inputs are "signed", the state advances to `PendingVerify` — irreversibly from the user's perspective.
3. The assembled transaction is broadcast to Bitcoin but rejected (invalid witness/signature).
4. The withdrawal is stuck: `verify_withdraw` will never succeed (the transaction is not confirmed), and `sign_btc_transaction` can no longer be called (wrong stage).
5. The user's nBTC remains locked in the bridge and the BTC UTXOs remain unavailable.

Recovery requires a privileged `cancel_withdraw` call (DAO/Operator only), which itself creates a new `PendingSign` transaction that the attacker can corrupt again in a loop, forcing repeated operator intervention and gas expenditure.

**Impact class**: Medium — attacker-triggered stuck bridge state requiring operator intervention; temporary locking of user funds.

---

### Likelihood Explanation

- `sign_btc_transaction` is callable by any NEAR account with no deposit or stake requirement beyond the `#[payable]` annotation.
- The `btc_pending_sign_id` is derived deterministically from the PSBT and is emitted in the `GenerateBtcPendingInfo` event, making it trivially discoverable.
- The attacker only needs to submit the call before the legitimate relayer/user does, which is feasible via transaction ordering on NEAR.
- No special knowledge, tokens, or privileges are required.

---

### Recommendation

1. **Validate `key_version`**: Store the expected `key_version` in `Config` or `BTCPendingInfo` at creation time and assert equality at the start of `sign_btc_transaction`.
2. **Restrict callers**: Add a check that `env::predecessor_account_id() == btc_pending_info.account_id`, or restrict the function to trusted relayer / operator roles via `#[access_control_any]` or `#[trusted_relayer]`.
3. **Allow re-signing**: If a signature slot is filled with an invalid signature (detectable via on-chain verification), allow overwriting it before the stage advances.

---

### Proof of Concept

1. Alice calls `ft_transfer_call(bridge, 100_000, Withdraw{...})`. The bridge creates `BTCPendingInfo` with `btc_pending_sign_id = "abc123"`, `signatures = [None]`, state = `PendingSign`.
2. The `GenerateBtcPendingInfo` event is emitted with `btc_pending_id = "abc123"`.
3. Attacker observes the event and calls:
   ```
   sign_btc_transaction("abc123", 0, 999)  // wrong key_version
   ```
4. The MPC signs input 0 with key version 999 (a key that does not control the UTXO). The signature is stored: `signatures = [Some(bad_sig)]`.
5. Since all inputs are now "signed", `to_pending_verify_stage()` is called. State = `PendingVerify`.
6. The assembled transaction is broadcast to Bitcoin and rejected (invalid signature for the P2WPKH/P2TR script).
7. Alice cannot call `sign_btc_transaction` again — `assert_pending_sign()` panics.
8. Alice cannot call `verify_withdraw` — the transaction never confirms.
9. Alice's nBTC is locked in the bridge. Only DAO/Operator can call `cancel_withdraw`, which itself creates a new signing round the attacker can corrupt again. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
