### Title
Peras Certificate Validation Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Chain Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` is a stub that unconditionally returns `Right` (success) for every certificate, regardless of cryptographic content. When Peras is enabled, an unprivileged peer can inject a crafted certificate via the ObjectDiffusion mini-protocol, causing the receiving node to immediately apply a weight boost to an arbitrary block and switch to a non-canonical chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass defines `validatePerasCert` as the gate that must authenticate Peras certificates received from peers before they influence chain selection. The universal default instance (applied to every `StandardHash blk`) is a stub that skips all validation:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired directly into the production certificate ingestion path. `makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validation callback:

```haskell
(validatePerasCert mkPerasParams)   -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

`processCerts` calls this callback on every inbound certificate. Because the callback always returns `Right`, every certificate from every peer is accepted and stored: [3](#0-2) 

Stored certificates are immediately converted into a `PerasWeightSnapshot` by `implGetWeightSnapshot`, mapping each certificate's `pcCertBoostedBlock` to its weight boost: [4](#0-3) 

That snapshot is read atomically and fed into `chainSelectionForBlock` via `preferAnchoredCandidate`, which uses `weightedSelectView` to compare chain fragments: [5](#0-4) 

`chainSelSync` then triggers a full chain selection for the boosted block: [6](#0-5) 

The `preferAnchoredCandidate` function uses the weight snapshot to compare fragments when Peras is active: [7](#0-6) 

**Analog to the external report:** Just as `proposeArbitrator` immediately writes `arbitratorFee` into shared state without the other party's agreement, and `release` then uses that fee to distribute funds, `validatePerasCert` immediately accepts any certificate into shared state (`PerasCertDB`) without real validation, and chain selection immediately uses the resulting weight boost to decide which chain to follow.

---

### Impact Explanation

When Peras is enabled, an unprivileged peer can:

1. Craft a `PerasCert` naming any block as `pcCertBoostedBlock`.
2. Deliver it via the ObjectDiffusion mini-protocol.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → unconditionally `Right`.
4. The certificate is stored; `implGetWeightSnapshot` adds the boost to the target block.
5. `chainSelSync` triggers chain selection for the boosted block.
6. `preferAnchoredCandidate` now sees the adversarial fork as heavier than the honest chain.
7. The honest node switches to the adversarial fork.

This is a **chain selection manipulation** vulnerability: an unprivileged peer can make an honest node prefer a non-canonical chain by injecting unauthenticated certificates, bypassing the Peras certificate validation entirely.

**Impact class:** High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

**Medium** (conditional on Peras being enabled). The CHANGELOG notes Peras is disabled by default. However, the production code path (`makePerasCertPoolWriterFromChainDB`) is already wired with the stub validator. Once Peras is enabled on any network (private testnet or future mainnet), the attack requires only network connectivity — no keys, stake, or special privileges. The attacker needs only to send a single well-formed `PerasCert` message.

---

### Recommendation

Implement real cryptographic validation inside `validatePerasCert` before enabling Peras in any production or semi-production environment. Validation must verify:

1. The certificate's aggregate BLS signature against the expected committee members' public keys.
2. That the certificate's `pcCertRound` is within the valid range for the current chain state.
3. That the `pcCertBoostedBlock` refers to a block that actually exists and is within the valid Peras boosting window.
4. That the certificate was produced by a legitimately elected voting committee (VRF-based committee selection).

Until these checks are in place, the `makePerasCertPoolWriterFromChainDB` path must not be reachable from untrusted peers.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
