### Title
Token Metadata Binding Confusion via Unvalidated Third-Party Metaplex Account in `log_metadata` — (`File: solana/programs/bridge_token_factory/src/instructions/user/log_metadata.rs`)

### Summary

In the Solana `bridge_token_factory` program, the `LogMetadata` instruction's `parse_metadata_account` function validates that the caller-supplied `metadata` account key matches the address stored in a Token-2022 mint's `MetadataPointer` extension, but **never verifies that the deserialized Metaplex metadata account's `mint` field matches the actual mint being logged**. An attacker can create a Token-2022 mint whose metadata pointer references the Metaplex metadata PDA of any legitimate token (e.g., USDC), causing the bridge to emit a Wormhole message to NEAR that binds the attacker's worthless mint to a reputable token's name, symbol, and decimals.

### Finding Description

The `LogMetadata` account struct declares the metadata account as a fully unchecked optional account with no PDA seed constraints at the Anchor level: [1](#0-0) 

At runtime, `parse_metadata_account` is called with the address taken directly from the mint's `MetadataPointer` extension: [2](#0-1) 

Inside `parse_metadata_account`, the only check performed is a key equality between the provided account and the pointer address: [3](#0-2) 

If the account is owned by MetaplexID, the metadata is deserialized and its `name`/`symbol` fields are returned directly: [4](#0-3) 

**There is no check that `metadata.mint == self.mint.key()`**. The Metaplex `MetadataAccount` struct contains a `mint` field that identifies which mint the metadata belongs to. This field is never validated against the actual mint being processed.

The resulting payload is then posted as a Wormhole message to NEAR: [5](#0-4) 

### Impact Explanation

An attacker:
1. Creates a Token-2022 mint (with their own mint authority, satisfying the `!mint.mint_authority.contains(authority.key)` constraint) and sets its `MetadataPointer` extension to point to the Metaplex metadata PDA of a legitimate token such as USDC (`EPjFWdd5AufqSSqeM2qN1xzybapC8G4wEGGkZwyTDt1v`'s metadata PDA).
2. Calls `log_metadata`, passing the legitimate token's Metaplex metadata account as the `metadata` argument.
3. The `require_keys_eq!` check passes (the provided account key matches the pointer address).
4. The Metaplex metadata is deserialized, returning `name="USD Coin"`, `symbol="USDC"`, and the attacker's mint's `decimals`.
5. A Wormhole message is emitted to NEAR binding the attacker's worthless mint pubkey to the name "USDC" / symbol "USDC".
6. NEAR deploys a wrapped token for the attacker's mint named "USDC".
7. The attacker mints their worthless tokens, bridges them to NEAR as wrapped "USDC", and sells them on NEAR DEXes to users who trust the token name/symbol.
8. Victims who receive and hold this fake wrapped "USDC" and attempt to bridge back receive the attacker's worthless tokens.

This is a **token metadata binding confusion** leading to user fund loss.

### Likelihood Explanation

The attack requires no privileged access. Any unprivileged user can create a Token-2022 mint, set an arbitrary `MetadataPointer`, and call `log_metadata`. The Solana Token-2022 program allows setting a metadata pointer to any arbitrary address at mint creation time. The constraint `!mint.mint_authority.contains(authority.key)` is trivially satisfied by using any non-bridge mint authority. The attack is fully permissionless and deterministic.

### Recommendation

Inside `parse_metadata_account`, after deserializing the Metaplex metadata, add a check that the metadata's `mint` field matches the actual mint being processed:

```rust
if metadata.owner == &MetaplexID {
    let data = metadata.try_borrow_data()?;
    let metadata = MplMetadata::try_deserialize(&mut data.as_ref())?;
    // ADD THIS CHECK:
    require_keys_eq!(
        metadata.mint,
        self.mint.key(),
        ErrorCode::InvalidTokenMetadataAddress,
    );
    Ok((metadata.name.clone(), metadata.symbol.clone()))
} else {
    Ok((String::default(), String::default()))
}
```

This ensures that even if an attacker points a Token-2022 metadata pointer at a legitimate token's Metaplex metadata PDA, the bridge will reject the instruction because the deserialized metadata's `mint` field will not match the attacker's mint.

### Proof of Concept

1. Deploy a Token-2022 mint `ATTACKER_MINT` with mint authority = attacker keypair and `MetadataPointer` extension set to `find_program_address([b"metadata", MetaplexID, USDC_MINT], MetaplexID).0` (USDC's Metaplex metadata PDA).
2. Call `log_metadata` with:
   - `mint` = `ATTACKER_MINT`
   - `metadata` = USDC's Metaplex metadata PDA account (publicly readable on-chain)
3. Observe: `require_keys_eq!(metadata.key(), metadata_pointer.metadata_address.0)` passes because both equal USDC's metadata PDA.
4. Observe: `metadata.owner == &MetaplexID` is true; deserialization returns `name="USD Coin"`, `symbol="USDC"`.
5. A Wormhole message is posted to NEAR: `LogMetadataPayload { token: ATTACKER_MINT, name: "USD Coin", symbol: "USDC", decimals: <attacker_decimals> }`.
6. NEAR deploys a wrapped token for `ATTACKER_MINT` named "USD Coin" / "USDC". [6](#0-5)

impl LogMetadata<'_> {
    fn parse_metadata_account(&self, address: Pubkey) -> Result<(String, String)> {
        let metadata = self
            .metadata
            .as_ref()
            .ok_or_else(|| error!(ErrorCode::TokenMetadataNotProvided))?
            .to_account_info();

            metadata.key(),
            address,
            ErrorCode::InvalidTokenMetadataAddress,

        }
    }
