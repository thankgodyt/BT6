### Title
Peras Certificate Verification Bypass: `validatePerasCert` Unconditionally Accepts Any Certificate — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or quorum verification. Any unprivileged peer can inject a crafted `PerasCert` for an arbitrary block, which will be accepted, stored, and used to boost that block's weight in chain selection — directly analogous to the Governor quorum bypass in the external report, where the quorum check produces a result lower than intended. Here the quorum check is absent entirely.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasCert` as the gate that must verify a received Peras certificate before it is stored and applied to chain selection. The only deployed instance — a blanket `instance StandardHash blk => BlockSupportsPeras blk` — implements this method as an unconditional pass-through:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is wired directly into the production node-to-node diffusion path. `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` on every inbound certificate batch:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) 

The `processCerts` function then timestamps and stores every certificate that passes this non-check: [3](#0-2) 

The stored `ValidatedPerasCert` carries a `vpcCertBoost :: PerasWeight` (set to `perasWeight mkPerasParams = PerasWeight 15`) that is applied to the boosted block's weight during chain selection. A certificate for a block that never legitimately reached quorum thus receives the same chain-selection boost as a genuine one.

The `BlockSupportsPeras` class contract requires that `validatePerasCert` check:
1. That the certificate's aggregate signature is valid over the claimed round and block.
2. That the aggregate represents a quorum of stake from the correct epoch snapshot.
3. That the round number is within the valid window.

None of these checks are performed. [4](#0-3) 

A secondary, related issue exists in `stakeAboveThreshold`: the function's own comment acknowledges that `PerasVoteStake` and the quorum threshold `perasQuorumStakeThreshold` must be in the same units (both relative/normalized), but no normalization is enforced, leaving the quorum comparison semantically undefined when absolute stake values are supplied: [5](#0-4) 

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` for any block point and any round number and send it over the Peras certificate diffusion mini-protocol. The receiving node will:

1. Accept it unconditionally via `validatePerasCert`.
2. Store it in the `PerasCertDB` / `ChainDB`.
3. Apply a `PerasWeight 15` boost to the targeted block during chain selection.

Because Peras certificate boosts are additive to chain weight, an adversary can make an honest node prefer a non-canonical or adversarially-chosen chain over the honest chain, bypassing the Praos longest-chain rule. This is a **chain selection safety failure** triggered by a crafted network message from an unprivileged peer.

---

### Likelihood Explanation

The Peras vote diffusion mini-protocol is active in the production node-to-node handler. Any peer that can establish a connection can send certificate objects. The `processCerts` path has no rate-limiting or round-number bounds check beyond deduplication by round number. A single crafted certificate per round is sufficient to inject a boost. The attack requires only network access to a running node.

---

### Recommendation

1. **Implement `validatePerasCert` with real cryptographic verification**: check the aggregate BLS signature over `(roundNo, boostedBlock)` against the aggregate public key derived from the epoch's stake-weighted committee, and verify that the aggregate stake meets the quorum threshold.
2. **Enforce unit consistency in `stakeAboveThreshold`**: either normalize `PerasVoteStake` to a relative value before comparison, or change the function signature to accept the total stake and perform normalization internally, removing the ambiguity documented in the TODO comment.
3. **Add round-number validity checks** in `validatePerasCert`: reject certificates whose round number is outside the acceptable window relative to the current tip.

---

### Proof of Concept

A malicious peer connects to an honest node and sends a single `PerasCert` message via the Peras certificate diffusion protocol:

```
PerasCert { pcCertRound = PerasRoundNo 1
           , pcCertBoostedBlock = <point of adversary's chosen block> }
```

`processCerts` calls `validatePerasCert mkPerasParams cert`, which returns:

```haskell
Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = PerasWeight 15 }
``` [6](#0-5) 

The certificate is stored via `ChainDB.addPerasCertAsync`. The targeted block now carries an extra weight of 15 in chain selection, potentially causing the honest node to prefer the adversary's chain over the canonical chain — a consensus safety failure reachable from an unprivileged peer with no stake, no keys, and no operator access. processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
