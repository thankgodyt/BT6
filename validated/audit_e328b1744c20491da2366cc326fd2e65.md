### Title
Hardcoded `GAS_FOR_BURN_CALL = 5 Tgas` Too Low for nBTC Cross-Contract Burn, Causing Stuck Withdrawal State and Potential Double-Minting - (File: `contracts/satoshi-bridge/src/nbtc/burn.rs`)

---

### Summary

The bridge allocates only 5 Tgas for every cross-contract call to the nBTC contract's `burn` function. This is the NEAR analog of Solidity's `transfer` (fixed 2300 gas stipend): if the nBTC `burn` implementation requires more gas than the hardcoded ceiling — whether today or after a future upgrade — the call silently fails. Depending on the call site, the consequence ranges from a permanently stuck withdrawal state to a double-minting scenario where the same BTC deposit can be credited twice.

---

### Finding Description

`GAS_FOR_BURN_CALL` is defined as 5 Tgas and is used in three production call sites:

**Site 1 — Withdrawal finalization** (`verify_withdraw_burn_promise`): [1](#0-0) [2](#0-1) 

The burn call receives exactly 5 Tgas. If it runs out of gas, `verify_withdraw_burn_callback` observes `is_promise_success() == false` and calls `to_pending_verify_stage()`, leaving the withdrawal permanently stuck even though the BTC transaction is already confirmed on-chain. [3](#0-2) 

**Site 2 — Safe-deposit rollback** (`safe_mint_callback`): [4](#0-3) 

When `safe_mint` fails (receiver returns 0 tokens), the bridge:
1. Removes the UTXO from `verified_deposit_utxo` (line 440).
2. Fires a `.detach()`-ed burn with only 5 Tgas — result is never checked.
3. Refunds the storage deposit to the relayer.

If the burn fails due to insufficient gas, the minted tokens remain in the bridge's nBTC balance, but the UTXO guard is gone. A relayer can immediately re-call `safe_verify_deposit` for the same UTXO: [5](#0-4) 

`verified_deposit_utxo.insert(...)` succeeds (UTXO was removed), `safe_mint` is called again, and a second batch of nBTC is minted for the same BTC deposit — unauthorized double-minting.

**Site 3 — Active UTXO management burn** (`verify_active_utxo_management_burn_promise`): [6](#0-5) 

Same 5 Tgas ceiling; failure leaves UTXO management stuck.

For comparison, the mint call is allocated 90 Tgas: [7](#0-6) 

The nBTC `burn` function accepts four parameters including a `relayer_fee`, suggesting it performs storage reads/writes, balance updates, total-supply adjustments, event emission, and potentially a relayer-fee cross-contract call — all of which require far more than 5 Tgas.

---

### Impact Explanation

**Critical (Site 2):** If the burn fails in `safe_mint_callback`, the UTXO is removed from `verified_deposit_utxo` while the minted tokens remain in the bridge. A relayer re-submitting the same deposit triggers a second `safe_mint`, producing nBTC unbacked by BTC — unauthorized minting of bridge tokens.

**Medium (Sites 1 & 3):** If the burn fails in the withdrawal or UTXO-management flow, the bridge enters a stuck state: the BTC transaction is confirmed on-chain but nBTC is never burned, inflating the circulating supply above the backed amount and requiring operator intervention to recover.

---

### Likelihood Explanation

The nBTC `burn` function handles four arguments including a relayer fee, implying non-trivial on-chain logic. Even a simple NEP-141 burn (balance read, subtract, total-supply update, event) typically consumes 3–8 Tgas; any relayer-fee transfer or additional bookkeeping pushes it above 5 Tgas. The gap between the 5 Tgas ceiling and the 90 Tgas allocated to the analogous `mint` call strongly suggests the ceiling is underprovisioned. The risk materialises immediately if the nBTC contract is upgraded, and may already be present depending on the current burn implementation.

---

### Recommendation

Increase `GAS_FOR_BURN_CALL` to match the complexity of the nBTC burn function — a value in the 20–30 Tgas range is consistent with similar NEAR bridge patterns. For the `.detach()` call in `safe_mint_callback`, consider attaching the callback to observe the result and re-insert the UTXO into `verified_deposit_utxo` only after confirming the burn succeeded, preventing the double-minting window.

```rust
// Before
pub const GAS_FOR_BURN_CALL: Gas = Gas::from_tgas(5);

// After
pub const GAS_FOR_BURN_CALL: Gas = Gas::from_tgas(25);
```

### Proof of Concept

1. User calls `safe_verify_deposit` with a valid BTC deposit proof. The bridge verifies the proof and calls `safe_mint` (90 Tgas) on the nBTC contract.
2. The nBTC contract mints tokens to the bridge and calls `ft_transfer_call` to the recipient. The recipient's `ft_on_transfer` returns `0` (used 0 tokens), so `safe_mint` returns `U128(0)`.
3. `safe_mint_callback` is invoked. `is_refund_required()` returns `true` (amount == 0).
4. The bridge removes the UTXO from `verified_deposit_utxo` and fires a `.detach()`-ed `burn` with 5 Tgas.
5. The nBTC `burn` function exhausts its 5 Tgas budget and fails. The minted tokens remain in the bridge's nBTC balance. No callback is observed (`.detach()`).
6. A relayer re-calls `safe_verify_deposit` with the same BTC proof. `verify_safe_deposit_callback` calls `verified_deposit_utxo.insert(...)` — succeeds because the UTXO was removed in step 4.
7. `safe_mint` is called again, minting a second batch of nBTC for the same BTC deposit. The recipient receives tokens; the bridge retains the first (unburned) batch. Total nBTC supply is now `2 × mint_amount` for a single BTC input.
