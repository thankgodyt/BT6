### Title
Peras Vote and Certificate Validation Accepts Caller-Supplied Voter Identity Without Cryptographic Verification - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance — which is the catch-all production instance for all block types — implements `validatePerasCert` as an unconditional `Right` (accepts every certificate) and implements `validatePerasVote` as a pure stake-distribution map lookup against the self-declared `pvVoteVoterId` field in the network message, with no cryptographic signature verification. An unprivileged peer can craft a `PerasCert` or a `PerasVote` claiming any voter identity and have it accepted by the receiving node.

---

### Finding Description

**Root cause — `validatePerasCert` unconditionally accepts any certificate:** [1](#0-0) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

Every `PerasCert` received over the network is immediately wrapped in `ValidatedPerasCert` and returned as `Right`. No signature, no committee membership check, no round-number sanity check — nothing.

**Root cause — `validatePerasVote` checks only a map lookup against a self-declared voter ID:** [2](#0-1) 

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
```

`lookupPerasVoteStake` simply does `Map.lookup (pvVoteVoterId vote) (unPerasVoteStakeDistr distr)`. [3](#0-2) 

The `pvVoteVoterId` field is a plain data field in the wire-format `PerasVote` message — it is entirely attacker-controlled: [4](#0-3) 

There is no BLS signature, VRF proof, or any other cryptographic binding between the claimed `pvVoteVoterId` and the actual network peer sending the message. This is the direct analog of the H-01 `from` parameter: the identity is caller-supplied and unverified.

**Production wiring — cert diffusion has no compensating control:** [5](#0-4) 

`makePerasCertPoolWriterFromChainDB` is wired directly into the Peras cert diffusion inbound handler with no empty-distribution guard. Every `PerasCert` received from any peer passes `validatePerasCert` and is stored.

**Production wiring — vote diffusion has a temporary `mempty` guard (but the validation logic is still broken):** [6](#0-5) 

The vote path currently passes `(pure (PerasVoteStakeDistr mempty))`, which causes all votes to fail the map lookup and be rejected. The inline comment explicitly acknowledges this is a temporary placeholder: *"Note that the empty stake distribution will cause all votes to be considered invalid."* Once the TODO is resolved and a real stake distribution is plumbed in, the missing signature check in `validatePerasVote` becomes directly exploitable.

**The `processVotes` inbound handler** calls the broken `validatePerasVote` for every batch received from a peer: [7](#0-6) 

---

### Impact Explanation

**For certificates (immediately exploitable):** Any unprivileged peer can send a crafted `PerasCert` over the Peras cert diffusion mini-protocol claiming to boost an arbitrary block. Because `validatePerasCert` always returns `Right`, the certificate is stored and used in chain selection. A Peras certificate boost shifts chain preference; injecting a forged certificate for an attacker-controlled block can cause an honest node to prefer a non-canonical chain, constituting a chain-selection safety failure.

**For votes (exploitable once real stake distribution is wired in):** Once the `mempty` placeholder is replaced with a real stake distribution, any peer can craft a `PerasVote` claiming to be any `PerasVoterId` present in that distribution. Because `validatePerasVote` performs only a map lookup with no signature check, the forged vote passes validation. Accumulating enough such forged votes triggers `votesReachQuorum` and causes the node to forge a false `PerasCert`, which then feeds back into the cert path above.

This maps to: **Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.**

---

### Likelihood Explanation

- The cert diffusion path is active in production with no compensating control; any connected peer can send a `PerasCert`.
- The vote path is currently blocked by the `mempty` guard, but the guard is explicitly temporary (developer TODO). The underlying validation logic is broken and will become exploitable as soon as the plumbing is completed.
- No special privileges, keys, or stake are required — any unprivileged peer that can establish a node-to-node connection can exploit the cert path today.

---

### Recommendation

1. **`validatePerasCert`**: Implement real certificate verification — check the aggregate BLS signature against the declared committee members' public keys, verify each member's eligibility (VRF proof for non-persistent members), and confirm the round number and boosted block are within acceptable bounds. Until this is implemented, the function must not return `Right` unconditionally.

2. **`validatePerasVote`**: Implement cryptographic signature verification using the voter's public key (looked up from the stake distribution or committee selection context) before accepting the vote. The `pvVoteVoterId` field must be treated as untrusted until the signature over `(pvVoteRound, pvVoteBlock)` is verified against the corresponding public key.

3. Consider adding a compile-time or runtime guard that prevents the degenerate `BlockSupportsPeras` instance from being used in production until real validation is implemented.

---

### Proof of Concept

**Cert forgery (active today):**

1. Attacker establishes a node-to-node connection to an honest node.
2. Attacker sends a `PerasCert { pcCertRound = r, pcCertBoostedBlock = attackerBlock }` over the Peras cert diffusion mini-protocol.
3. The inbound handler calls `makePerasCertPoolWriterFromChainDB` → `processVotes`-equivalent → `validatePerasCert`.
4. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }` unconditionally.
5. The forged certificate is stored in the `ChainDB` and used to boost `attackerBlock` in chain selection. [8](#0-7) 

**Vote identity spoofing (exploitable once real stake distribution is wired):**

1. Attacker observes the stake distribution to identify a legitimate `PerasVoterId` (e.g., `victimId`) with high stake.
2. Attacker sends `PerasVote { pvVoteRound = r, pvVoteBlock = attackerBlock, pvVoteVoterId = victimId }`.
3. `validatePerasVote` calls `lookupPerasVoteStake vote stakeDistr` → finds `victimId` in the map → returns `Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = victimStake }`.
4. No signature over `(r, attackerBlock)` by `victimId`'s key is ever checked.
5. Attacker repeats with multiple spoofed voter IDs until `votesReachQuorum` triggers, forging a certificate for `attackerBlock`. [9](#0-8)
