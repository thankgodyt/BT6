### Title
Peras Certificate Validation Universally Stubbed — Any Peer-Supplied Certificate Accepted Without Cryptographic Verification - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The Peras protocol extension ships a universal `BlockSupportsPeras` instance whose `validatePerasCert` implementation is an explicit stub that unconditionally returns `Right` for every certificate it receives. Because this instance is the one wired into the live object-diffusion inbound pipeline, any unprivileged peer can inject arbitrary `PerasCert` objects that are accepted without any cryptographic or structural verification and are then stored in the `PerasCertDB` / `ChainDB`, where they influence chain selection via the Peras weight-boost mechanism.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that every block type must satisfy to participate in the Peras voting protocol. It exposes three critical operations: `validatePerasCert`, `validatePerasVote`, and `forgePerasCert`. The repository ships a single catch-all instance (`instance StandardHash blk => BlockSupportsPeras blk`) that is used for all block types until era-specific instances are wired in.

That instance's `validatePerasCert` is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

It never inspects the certificate's content; it always succeeds. [1](#0-0) 

This stub is directly wired into the two live inbound certificate pool writers:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) [3](#0-2) 

`processCerts` calls `validateCert` on every inbound certificate and, if all pass, stores them via `addCert`. Because `validatePerasCert` always passes, every certificate a peer sends is stored. [4](#0-3) 

A parallel stub exists for `validatePerasVote` (only checks stake-distribution membership, no cryptographic proof) and `forgePerasCert` (no validation of the aggregated votes): [5](#0-4) 

Additionally, `getPerasCertInBlock` always returns `Nothing`, meaning certificates embedded in on-chain blocks are never extracted and the chain-selection weight boost is never applied from canonical chain data — only from peer-supplied off-chain objects: [6](#0-5) 

The `PerasCertDB` and `PerasVoteDB` `implAddCert`/`implAddVote` functions also carry explicit TODOs noting that non-trivial validation logic is missing: [7](#0-6) [8](#0-7)

### Impact Explanation

Peras certificates carry a `vpcCertBoost` weight that is added to the chain-selection `SelectView` for the boosted block. A node that stores a crafted certificate for an adversary-controlled block will assign that block extra weight during chain selection, potentially causing it to prefer a non-canonical or adversary-controlled chain over the honest chain. This is a **chain-selection bug** triggered by an unprivileged peer via the object-diffusion mini-protocol, matching the "High" impact tier: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*.

---

### Likelihood Explanation

The object-diffusion protocol is open to any connected peer. No stake, key material, or special privilege is required to send a `PerasCert` message. The stub validation is the **only** gate between a peer-supplied certificate and the `PerasCertDB`/`ChainDB`. Once Peras is activated on a network running this code, exploitation requires only a network connection and knowledge of the wire format.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the BLS aggregate signature, checks committee eligibility, and validates the boosted block's existence and round number before returning `Right`.
2. Implement `getPerasCertInBlock` to extract certificates from blocks so that the canonical chain is the authoritative source of certificate truth, not peer gossip alone.
3. Implement `validatePerasVote` to verify the VRF/eligibility proof and cryptographic signature, not merely stake-distribution membership.
4. Do not activate the Peras object-diffusion mini-protocol on any network until all three stubs are replaced.

---

### Proof of Concept

1. Connect to a node running this code with Peras enabled.
2. Send a `PerasCert` message via the object-diffusion protocol for an adversary-controlled block `B_adv` in round `R`, with `pcCertBoostedBlock = point(B_adv)`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. The certificate is stored in `PerasCertDB` with `vpcCertBoost = perasWeight params`.
5. During the next chain-selection pass, `B_adv`'s `SelectView` includes the weight boost, causing the node to prefer the adversary's chain over the honest chain of equal or slightly greater length.

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
