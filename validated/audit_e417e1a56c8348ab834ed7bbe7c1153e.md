### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Returns `Right` Without Performing Any Cryptographic or Quorum Checks — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally accepts every inbound Peras certificate without performing any cryptographic signature verification, committee eligibility checks, or quorum validation. An unprivileged peer can submit arbitrary, fabricated certificates that are accepted as valid, causing the node to apply unearned chain-weight boosts and potentially switch to a non-canonical, adversary-controlled chain.

---

### Finding Description

The `BlockSupportsPeras` typeclass in `ouroboros-consensus` defines the interface for validating Peras votes and certificates. The class has a single blanket instance for all `StandardHash blk` types, which is the instance used in production until per-era HFC plumbing is complete.

In this instance, `validatePerasCert` is implemented as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This function **always returns `Right`** — it never inspects the certificate's aggregate BLS signature (`pcSignature`), never verifies the voters' eligibility proofs, never checks that the claimed voters actually reached quorum, and never validates the boosted block point against the chain. The `cert` value is wrapped directly into a `ValidatedPerasCert` with the full configured `perasWeight` boost, regardless of its content.

This stub is the function called by both inbound certificate processing paths:

- `makePerasCertPoolWriterFromCertDB` → `processCerts` → `validatePerasCert mkPerasParams`
- `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams`

Once a certificate passes `validatePerasCert`, it is stored via `addPerasCertAsync` and triggers chain selection via `ChainDB.addPerasCertAsync`, which applies the `vpcCertBoost` weight to the boosted block's chain fragment. Chain selection then uses `preferAnchoredCandidate` / `compareChainDiffs` with Peras weights, potentially switching the node to a shorter chain that has been artificially boosted.

The analog to the external report is direct: just as an attacker could mint unlimited points for free by exploiting a missing fee check, here an attacker can mint unlimited Peras chain-weight boosts for free by submitting certificates that skip all cryptographic cost (signature verification, VRF proof verification, quorum threshold check).

---

### Impact Explanation

**Critical — Bypass of Peras certificate/vote verification that enables unauthorized certificate acceptance and chain-selection manipulation.**

A malicious peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound`, `pcCertBoostedBlock`, and a garbage `pcSignature`.
2. Send it via the Peras certificate mini-protocol diffusion path.
3. The receiving node calls `validatePerasCert mkPerasParams cert`, which returns `Right` unconditionally.
4. The certificate is stored and `addPerasCertAsync` triggers chain selection.
5. The adversary's chosen block receives a full `perasWeight` boost, potentially causing the honest node to prefer a shorter adversary-controlled chain over the honest longer chain.

This breaks the core Peras security guarantee: that only blocks backed by a genuine quorum of stake-weighted committee votes receive a boost. An adversary with zero stake can generate an unlimited number of valid-looking certificates at negligible cost (no BLS signing required, no VRF proof required), analogous to the "free points minting" in the external report.

---

### Likelihood Explanation

**High.** The vulnerability is reachable by any peer that can connect to the node's Peras certificate diffusion mini-protocol. No special privileges, keys, or stake are required. The attacker only needs to construct a well-formed CBOR-serialized `PerasCert` with any content — the signature field is never checked. The code path is active in the current production codebase (the blanket instance is the only instance), and the TODO comment explicitly acknowledges the missing validation.

---

### Recommendation

1. **Do not ship the blanket stub instance as a production code path.** Gate the Peras certificate diffusion mini-protocol behind a feature flag or era check so that `validatePerasCert` is only reachable once a proper implementation exists.
2. **Implement full certificate validation** in `validatePerasCert`: verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the aggregate public key of the declared voters, verify each non-persistent voter's VRF eligibility proof, and confirm that the total stake of declared voters exceeds the quorum threshold.
3. **Until (2) is complete**, replace the `Right` stub with `Left PerasValidationErr` so that all inbound certificates are rejected rather than unconditionally accepted.

---

### Proof of Concept

**Entry path:**

1. Peer connects and sends a `PerasCert` message via the Peras certificate object-diffusion mini-protocol.
2. `makePerasCertPoolWriterFromChainDB` is the active writer: [1](#0-0) 

3. It calls `processCerts` with `validatePerasCert mkPerasParams` as the validator: [2](#0-1) 

4. `validatePerasCert` is the stub that always returns `Right`: [3](#0-2) 

5. The accepted certificate is passed to `ChainDB.addPerasCertAsync`, which triggers chain selection with the full Peras weight boost applied to the adversary's chosen block: [4](#0-3) 

**Fabricated certificate construction:** The attacker serializes a `PerasCert` with `pcCertRound = <any round>`, `pcCertBoostedBlock = <target block point>`, and a zero-byte or random `pcSignature`. Since `validatePerasCert` never calls `verifyAggregateVoteSignature` or any other check, the certificate passes validation and the boost is applied.

The `WFALS` committee implementation does contain proper validation logic (`implVerifyVote`, `implVerifyCert`): [5](#0-4) 

However, this logic is **never invoked** by the production `validatePerasCert` path — the blanket instance bypasses it entirely. [6](#0-5)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
