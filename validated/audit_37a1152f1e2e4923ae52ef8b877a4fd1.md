Audit Report

## Title
Native ETH Delivery Revert in `finTransfer` Permanently Freezes Bridged Funds — (File: evm/src/omni-bridge/contracts/OmniBridge.sol)

## Summary
When a user bridges native ETH from NEAR to EVM and specifies a contract recipient that cannot accept ETH, every call to `finTransfer` reverts via `FailedToSendEther()`, rolling back the `completedTransfers` nonce write. Because the nonce is never consumed, the relayer can retry indefinitely — but every attempt produces the same revert. The user's NEAR-side tokens, already locked or burned at transfer initiation, have no user-callable recovery path, resulting in permanent fund freezing.

## Finding Description
In `OmniBridge.sol`, `finTransfer` marks the destination nonce as consumed at line 287 before attempting ETH delivery:

```solidity
completedTransfers[payload.destinationNonce] = true;   // L287
```

For native ETH transfers (`payload.tokenAddress == address(0)`), delivery is attempted at lines 317–322:

```solidity
(bool success, ) = payload.recipient.call{value: payload.amount}("");
if (!success) revert FailedToSendEther();
```

`revert FailedToSendEther()` rolls back the entire transaction, including the L287 storage write. The nonce is never durably consumed. If the recipient is a contract without a `receive`/`fallback` function (or one that explicitly reverts), every retry by the relayer produces the same outcome.

On the NEAR side, `init_transfer_internal` burns or locks the user's tokens at lines 1850–1857 of `near/omni-bridge/src/lib.rs` before the EVM finalization occurs. The `remove_transfer_message` and `remove_transfer_message_without_refund` functions are only invoked through internal callbacks (e.g., storage-deposit failure paths), not through any public, user-callable entry point. There is no cancel or refund function that the original sender can invoke to recover tokens from a `TransferMessage` whose EVM finalization is permanently blocked.

## Impact Explanation
This is a **Critical** impact matching the allowed scope: *permanent freezing of bridged funds*. The user's NEAR-side tokens (locked or burned at initiation) are irrecoverable: the EVM `finTransfer` will always revert for an ETH-rejecting recipient, the NEAR bridge exposes no user-callable cancel path, and the relayer's ETH is returned on each revert while the user's funds remain frozen indefinitely.

## Likelihood Explanation
Low-to-medium. No privileged access is required. Any bridge user can trigger this by specifying as the EVM recipient a contract that does not implement `receive`/`fallback` — for example, a plain ERC-20 token contract address, a multisig wallet deployment lacking a payable fallback, or a contract recently upgraded to remove ETH acceptance. The user need not be malicious; an honest mistake in address selection is sufficient.

## Recommendation
Replace the hard revert on ETH delivery failure with a pull-payment (escrow) pattern so the nonce is durably consumed and the ETH is held for later claim:

```solidity
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) {
        pendingWithdrawals[payload.recipient] += payload.amount;
        emit EthDeliveryFailed(payload.recipient, payload.amount, payload.destinationNonce);
    }
}
```

Alternatively, add a NEAR-side user-callable cancel entry point that allows the original sender to reclaim tokens when EVM finalization is provably impossible (e.g., after a timeout or an admin-attested failure).

## Proof of Concept
1. User on NEAR calls `ft_transfer_call` → `init_transfer_internal` → NEAR tokens burned/locked; `TransferMessage` stored.
2. User specifies as EVM recipient a contract `C` with no `receive` function (e.g., a plain ERC-20 token contract).
3. Relayer calls `finTransfer` on EVM with `msg.value = payload.amount`.
4. L287: `completedTransfers[nonce] = true` (written to state).
5. L319–321: `C.call{value: amount}("")` returns `success = false`.
6. L322: `revert FailedToSendEther()` — entire transaction reverts, including L287 write.
7. Relayer retries; every attempt reverts identically.
8. User's NEAR tokens remain locked/burned with no recovery path.

**Minimal test plan:** Deploy a contract `C` with no `receive` function on a local EVM testnet. Deploy `OmniBridge` with a mock `nearBridgeDerivedAddress`. Call `finTransfer` with `payload.tokenAddress = address(0)`, `payload.recipient = address(C)`, and valid `msg.value`. Assert the transaction reverts and `completedTransfers[nonce]` remains `false`. Confirm repeated calls always revert.
