### Title
Front-Runnable `request_refund` Allows Attacker to Redirect User's BTC Refund to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` accepts a caller-supplied `refund_address` that is not bound to the caller's identity when `deposit_msg.refund_address` is `None`. Any observer can extract a pending `request_refund` transaction from the NEAR mempool and re-submit it with an attacker-controlled BTC address, consuming the one-time UTXO slot and redirecting the refund payout.

### Finding Description

`request_refund` is a public, permissionless function (no `#[trusted_relayer]` on the method itself, only on the impl block which generates whitelist-management infrastructure but does not gate individual methods lacking the per-method attribute — confirmed by `withdraw_rbf` in the same impl block being user-callable). [1](#0-0) 

The function accepts two independent parameters: `deposit_msg` (which encodes the deposit path and optionally a pre-authorized `refund_address`) and a separate `refund_address` string. The only guard against a mismatched address is: [2](#0-1) 

This guard fires only when `deposit_msg.refund_address` is `Some`. When it is `None` — the common case for users who did not embed a BTC return address at deposit time — any caller may supply any `refund_address`.

The callback enforces uniqueness per UTXO: [3](#0-2) 

So the first `request_refund` call that lands for a given UTXO wins. A second call for the same UTXO panics with "Refund request already exists for this UTXO", permanently blocking the legitimate user from creating their own request.

After the `unsafe_refund_timelock_sec` elapses, `execute_refund` (also permissionless) can be called by anyone, and the bridge's MPC pipeline sends the BTC to whichever `refund_address` was stored in the winning request: [4](#0-3) 

The only mitigation is the `unsafe_refund_timelock_sec` window during which DAO/Operator can call `reject_refund`. The victim user cannot self-help: `reject_refund` requires `is_privileged || is_already_deposited`, and the UTXO is not in `verified_deposit_utxo` (that is precisely why a refund is needed). [5](#0-4) 

### Impact Explanation

An attacker who front-runs `request_refund` with an attacker-controlled `refund_address` causes the bridge's MPC layer to sign and broadcast a Bitcoin transaction paying the attacker's address. The victim's BTC deposit is permanently transferred to the attacker. This is direct theft of user funds and matches the **Critical** impact: "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

### Likelihood Explanation

- NEAR transactions are observable in the mempool before finalization; front-running is a known attack vector on NEAR.
- `request_refund` is permissionless and requires only an attached NEAR storage deposit (a small, fixed cost).
- The attack parameters are fully visible on-chain: `deposit_msg`, `tx_bytes`, `vout`, and the Merkle `proof` are all passed as plain arguments.
- The only prerequisite is that the victim's `deposit_msg.refund_address` is `None`, which is the default for most deposit flows that do not pre-authorize a return address.
- The DAO mitigation window (`unsafe_refund_timelock_sec`) requires active, continuous monitoring and timely intervention; it is not a reliable on-chain safeguard.

### Recommendation

Bind the `refund_address` to the caller's identity or to the deposit message at submission time. Concretely:

1. **Require `deposit_msg.refund_address` to be `Some`** for permissionless callers. If it is `None`, require the caller to be a trusted relayer or DAO/Operator.
2. **Alternatively**, store `env::predecessor_account_id()` as the authorized executor of the refund and only allow that account (or DAO) to call `execute_refund` for that request.
3. **Or**, derive the `refund_address` exclusively from `deposit_msg.refund_address` and reject any call where that field is absent, forcing users to embed their BTC return address at deposit time.

### Proof of Concept

```
// Victim submits (visible in NEAR mempool):
request_refund(
    deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },
    refund_address = "bc1q...victim...",
    tx_bytes = <victim's BTC tx>,
    vout = 0,
    proof = <valid Merkle proof>,
    gas_fee = None,
)

// Attacker observes the pending tx, copies all parameters,
// substitutes their own BTC address, and submits first:
request_refund(
    deposit_msg = { recipient_id: "victim.near", refund_address: None, ... },  // identical
    refund_address = "bc1q...ATTACKER...",   // <-- changed
    tx_bytes = <same BTC tx>,
    vout = 0,
    proof = <same Merkle proof>,
    gas_fee = None,
)

// Attacker's tx lands first:
// - request_refund_callback stores RefundRequest { refund_address: "bc1q...ATTACKER..." }
// - Victim's tx panics: "Refund request already exists for this UTXO"

// After unsafe_refund_timelock_sec (if DAO does not intervene):
execute_refund(utxo_storage_key = "<txid>@0", ...)
// Bridge MPC signs a BTC tx paying bc1q...ATTACKER...
// Victim's BTC is stolen.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
