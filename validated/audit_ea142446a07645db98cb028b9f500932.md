### Title
Any Caller Can Redirect Victim's Unfinalized BTC Deposit to Attacker-Controlled Address via `request_refund` - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary
The `request_refund` function imposes no check that the caller is the original depositor. When a `DepositMsg` was constructed without a pre-authorized `refund_address` (i.e., `deposit_msg.refund_address` is `None`), any unprivileged NEAR account can submit a refund request for that UTXO and supply an arbitrary attacker-controlled BTC address as the refund destination. Because only one refund request can exist per UTXO, a front-running attacker can permanently block the legitimate depositor from reclaiming their own funds and redirect the BTC to themselves once the timelock elapses.

### Finding Description
`request_refund` is publicly callable by any NEAR account. Its only caller-identity check is the optional `gas_fee` guard: [1](#0-0) 

No check verifies that `env::predecessor_account_id()` matches `deposit_msg.recipient_id` or any other depositor-linked identity. Inside `internal_request_refund`, the only `refund_address` validation is: [2](#0-1) 

This guard only fires when `deposit_msg.refund_address` is `Some(...)`. When it is `None`, the caller-supplied `refund_address` is accepted verbatim and stored in the `RefundRequest`: [3](#0-2) 

The stored `refund_address` is later used directly to build the Bitcoin output that pays the refund: [4](#0-3) 

A duplicate-request guard prevents a second request for the same UTXO: [5](#0-4) 

This means whichever caller submits first wins. An attacker who front-runs the legitimate depositor's `request_refund` call locks in their own BTC address as the sole refund destination.

The timelock applied in this case is `unsafe_refund_timelock_sec` (the longer one), which is intended to give the DAO time to reject: [6](#0-5) 

However, DAO rejection is not guaranteed: the DAO may be unavailable, slow, or simply not monitoring. After the timelock elapses, `execute_refund` is also callable by anyone: [7](#0-6) 

### Impact Explanation
If the DAO fails to reject the malicious request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the MPC pipeline builds and signs a Bitcoin transaction paying the attacker's address. The victim's BTC is permanently redirected. This matches the allowed impact: **Medium — bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds**, and escalates to **Critical — significant loss or theft of user funds** if the DAO does not intervene.

### Likelihood Explanation
The attack requires:
1. A deposit whose `deposit_msg.refund_address` is `None` (the common case — users rarely pre-authorize a refund address).
2. The deposit to remain unfinalized (invalid deposit, relayer outage, or race window before `verify_deposit` lands).
3. The attacker to submit `request_refund` before the legitimate depositor.

All three conditions are realistic. The `deposit_msg` is fully reconstructible from public on-chain data (the deposit address is derived from its hash and is visible on Bitcoin). NEAR transaction ordering does not prevent front-running. The window between a failed/delayed deposit and the victim's refund attempt can be hours or days.

### Recommendation
Bind the refund request to the depositor's identity. The simplest fix is to require that when `deposit_msg.refund_address` is `None`, the caller must be `deposit_msg.recipient_id` (the NEAR account that was to receive the minted nBTC). Alternatively, require that `deposit_msg.refund_address` always be set at deposit time (i.e., make it mandatory), so the refund destination is locked into the deposit address derivation and cannot be overridden by a third party.

### Proof of Concept
1. Victim sends BTC to the deposit address derived from `deposit_msg = { recipient_id: "victim.near", refund_address: null }`.
2. The deposit is not finalized (relayer outage or invalid deposit).
3. Attacker observes the Bitcoin transaction on-chain, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: null },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's raw BTC tx>,
     vout = 0,
     proof = <valid SPV proof>,
     gas_fee = null
   )
   ```
   with the required NEAR storage deposit attached.
4. The `RefundRequest` is stored with `refund_address = "attacker_btc_address"`. The victim's subsequent `request_refund` call reverts with `"Refund request already exists for this UTXO"`.
5. After `unsafe_refund_timelock_sec` elapses (and assuming DAO does not reject), attacker calls `execute_refund(utxo_storage_key, None)`.
6. `finalize_refund_with_psbt` builds a Bitcoin PSBT paying `"attacker_btc_address"` and submits it to the MPC signing pipeline. The victim's BTC is sent to the attacker.

        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
