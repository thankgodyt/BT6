### Title
Permissionless `request_refund` with Attacker-Controlled `refund_address` Enables Theft of User BTC - (File: contracts/satoshi-bridge/src/api/bridge.rs)

### Summary

`request_refund` is callable by any unprivileged NEAR account with no ownership check on the UTXO. When a user's `deposit_msg.refund_address` is `None`, an attacker can front-run or race the user's refund submission, supplying the attacker's own BTC address. This locks the user out of submitting their own refund request and, if the DAO/Operator does not reject the fraudulent request within the `unsafe_refund_timelock_sec` window, allows the attacker to redirect the user's deposited BTC to themselves via the MPC signing pipeline.

### Finding Description

`request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs` carries no caller-identity restriction: [1](#0-0) 

Inside `internal_request_refund`, the only guard on `refund_address` is: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-authorize a return address), the check is skipped entirely and the caller-supplied `refund_address` is stored verbatim in the `RefundRequest`: [3](#0-2) 

Because only one refund request may exist per UTXO: [4](#0-3) 

the first caller wins. An attacker who submits before the legitimate user permanently blocks the user from registering their own refund address.

After `unsafe_refund_timelock_sec` elapses, `execute_refund` is also unrestricted: [5](#0-4) 

`internal_execute_refund` builds the PSBT paying `refund_request.refund_address` (the attacker's address) and creates a `BTCPendingInfo` owned by the caller: [6](#0-5) 

`sign_btc_transaction` has no caller-identity check either: [7](#0-6) 

So the attacker calls `sign_btc_transaction`, obtains the MPC-signed transaction bytes (emitted in the `SignedBtcTransaction` event), broadcasts it on Bitcoin, and receives the user's BTC at their own address.

### Impact Explanation

**Critical.** The attacker receives the user's full deposited BTC minus the gas fee. The user's UTXO is simultaneously added to `verified_deposit_utxo`: [8](#0-7) 

This permanently blocks `verify_deposit` for that UTXO, so the user cannot recover via the normal deposit path either. The user loses their entire deposit.

### Likelihood Explanation

**Medium–High.** All information the attacker needs is publicly observable:

- The `deposit_msg` is emitted in a `LogDepositAddress` event by `get_user_deposit_address`: [9](#0-8) 
- The BTC transaction bytes and Merkle proof are visible on the Bitcoin chain.

The attacker pays only the small NEAR storage deposit for `request_refund` (non-refundable but negligible vs. the BTC at stake). The only mitigation is DAO/Operator rejection within the 4-hour `unsafe_refund_timelock_sec` window, which requires continuous monitoring and is not guaranteed.

### Recommendation

1. **Bind `request_refund` to the deposit recipient.** Require `env::predecessor_account_id()` to equal `deposit_msg.recipient_id`, or require a signature from `recipient_id` authorizing the `refund_address`.
2. **Require a pre-authorized refund address for permissionless requests.** Reject `request_refund` calls where `deposit_msg.refund_address` is `None` unless the caller is DAO/Operator.
3. **Alternatively**, store the `refund_address` only from the `deposit_msg` field and disallow caller-supplied addresses entirely for non-privileged callers.

### Proof of Concept

1. Alice calls `get_user_deposit_address(DepositMsg { recipient_id: alice, refund_address: None, … })`. The `LogDepositAddress` event reveals the full `deposit_msg`.
2. Alice sends 1 BTC to the derived address. The transaction is confirmed on Bitcoin.
3. Attacker observes the event and the on-chain BTC transaction; constructs `tx_bytes` and `proof`.
4. Attacker calls `request_refund(deposit_msg, attacker_btc_address, tx_bytes, vout, proof, None)` — succeeds because there is no ownership check.
5. Alice calls `request_refund` — **panics**: `"Refund request already exists for this UTXO"`. [4](#0-3) 
6. DAO/Operator does not reject within 4 hours (`unsafe_refund_timelock_sec`).
7. Attacker calls `execute_refund(utxo_storage_key, None)` — PSBT is built paying `attacker_btc_address`. [10](#0-9) 
8. Attacker calls `sign_btc_transaction(pending_id, 0, 0)` — MPC signs the transaction (no caller check).
9. Attacker reads the signed transaction bytes from the `SignedBtcTransaction` event and broadcasts it on Bitcoin.
10. Alice's 1 BTC arrives at the attacker's address. Alice's UTXO is permanently marked in `verified_deposit_utxo`, blocking any recovery via `verify_deposit`.

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
