### Title
Attacker Can Front-Run `request_refund` to Redirect Refund Funds or Permanently Block User Refunds - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
The `request_refund` function is callable by any NEAR account and accepts an arbitrary `refund_address` when `deposit_msg.refund_address` is `None`. An attacker who observes a BTC deposit can race the legitimate user to submit a refund request for the same UTXO with the attacker's own BTC address. The legitimate user's subsequent call is then rejected with "Refund request already exists for this UTXO," and if the DAO/Operator fails to reject the malicious request within `unsafe_refund_timelock_sec`, the attacker can redirect the bridged funds to their own address.

### Finding Description

`request_refund` is declared inside a `#[trusted_relayer] #[near] impl Contract` block but carries **no individual** `#[trusted_relayer]` attribute of its own. [1](#0-0) 

Functions that are genuinely restricted to whitelisted relayers carry an explicit per-function `#[trusted_relayer]` attribute (e.g., `verify_deposit_v2`, `verify_refund_finalize`). Functions intended to be publicly callable — `execute_refund`, `claim_lost_found`, `withdraw_rbf`, and `request_refund` — do not. The anti-spam attached-deposit requirement in the docs further confirms public access is intended. [2](#0-1) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(msg_refund_address == &refund_address, ...);
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), **any caller may supply any BTC address**. The callback only verifies that the deposit output's `script_pubkey` matches the address derived from `deposit_msg`; it does not verify that the caller is the intended recipient. [4](#0-3) 

The `deposit_msg` itself is publicly observable: every call to `get_user_deposit_address` emits a `LogDepositAddress` event containing the full `deposit_msg`. [5](#0-4) 

Attack path:

1. Attacker monitors NEAR events for `LogDepositAddress` to obtain the victim's `deposit_msg`.
2. Attacker observes the corresponding BTC deposit on-chain and obtains `tx_bytes`, `vout`, and a valid `TxInclusionProof`.
3. Attacker calls `request_refund(deposit_msg, "attacker_btc_address", tx_bytes, vout, proof, None)` with the required attached deposit.
4. The callback passes all checks and stores a `RefundRequest` with `refund_address = "attacker_btc_address"` and `deposit_msg.refund_address = None`, so `unsafe_refund_timelock_sec` applies.
5. Victim calls `request_refund(...)` → panics: **"Refund request already exists for this UTXO"**.
6. After `unsafe_refund_timelock_sec`, attacker calls `execute_refund(utxo_storage_key, None)` → bridge constructs and signs a BTC transaction paying the attacker's address. [6](#0-5) 

The DAO/Operator can reject the malicious request via `reject_refund`, but the attacker can immediately re-submit a new `request_refund` for the same UTXO (after the previous one is removed), creating an indefinite griefing loop that permanently prevents the victim from recovering their funds. [7](#0-6) 

### Impact Explanation

**Critical.** Two distinct harms are reachable:

- **Permanent locking**: The attacker continuously front-runs every `request_refund` attempt. Each time the DAO/Operator rejects the malicious request, the attacker immediately re-submits. The victim can never create a valid refund request, permanently locking their deposited BTC/ZEC in the bridge.
- **Fund theft**: If the DAO/Operator does not reject the malicious request within `unsafe_refund_timelock_sec`, the attacker calls `execute_refund` and the MPC network signs a transaction paying the attacker's BTC address, constituting direct theft of user funds.

Both outcomes match the allowed Critical impact: "Significant loss, theft, destruction, or permanent locking of user or protocol funds."

### Likelihood Explanation

Moderate-to-high. The attacker requires no privileged access — only a NEAR account, the attached storage deposit (a small NEAR amount), and publicly observable data (`LogDepositAddress` events + the Bitcoin transaction). The attack window is large: the victim must wait for BTC confirmations before calling `request_refund`, giving the attacker hours or days to act. No NEAR mempool front-running is needed; the attacker simply needs to submit their transaction before the victim does.

### Recommendation

1. **Require `deposit_msg.refund_address` to be set**: Reject `request_refund` calls where `deposit_msg.refund_address` is `None`, forcing users to pre-commit their BTC refund address in the deposit message. This makes the address immutable and removes the attacker's ability to substitute their own.
2. **Bind the refund request to the caller**: If `deposit_msg.refund_address` is `None`, record the caller's NEAR account ID in the `RefundRequest` and only allow that account (or DAO/Operator) to call `execute_refund` for that request.
3. **Rate-limit re-submission**: After a refund request is rejected, impose a cooldown before the same UTXO can be re-requested, reducing the attacker's ability to loop indefinitely.

### Proof of Concept

```
// Setup
// - victim.near calls get_user_deposit_address({account_id: "victim.near", refund_address: None, ...})
//   → emits LogDepositAddress with deposit_msg
// - victim sends 1 BTC to the bridge address
// - BTC tx is confirmed; victim obtains tx_bytes, vout, proof

// Step 1: Attacker reads LogDepositAddress event → gets deposit_msg
// Step 2: Attacker reads Bitcoin chain → gets tx_bytes, vout, proof

// Step 3: Attacker calls request_refund BEFORE victim
attacker.near → bridge.request_refund(
    deposit_msg,           // copied from LogDepositAddress event
    "attacker_btc_addr",   // attacker's own BTC address
    tx_bytes, vout, proof,
    None
)
// → RefundRequest stored with refund_address = "attacker_btc_addr"
// → unsafe_refund_timelock_sec applies (no pre-authorized address)

// Step 4: Victim tries to request refund
victim.near → bridge.request_refund(
    deposit_msg, "victim_btc_addr", tx_bytes, vout, proof, None
)
// → PANICS: "Refund request already exists for this UTXO"

// Step 5: After unsafe_refund_timelock_sec (if DAO/Operator does not reject)
attacker.near → bridge.execute_refund(utxo_storage_key, None)
// → MPC signs BTC tx paying "attacker_btc_addr"
// → victim's 1 BTC is sent to attacker
```

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
    }
