### Title
Incomplete State Cleanup in `internal_clear_invalid_pending_verify_rbf` Leaves Stale Account Entries — (File: `contracts/satoshi-bridge/src/btc_pending_info.rs`)

---

### Summary

`internal_clear_invalid_pending_verify_rbf` removes a `BTCPendingInfo` record from `btc_pending_infos` but never removes the corresponding tx-id from the owning account's `btc_pending_sign_ids` or `btc_pending_verify_list` sets. This creates a persistent mismatch between two parallel data structures — the same class of bug as H-03, where one array is updated while a second, coupled array is left stale.

---

### Finding Description

`internal_clear_invalid_pending_verify_rbf` (called by the publicly accessible `clear_invalid_pending_verify_rbf` and `batch_clear_invalid_pending_verify_rbf`) performs only a single removal:

```rust
// btc_pending_info.rs lines 403-413
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id); // removes from btc_pending_infos
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
    // ← account.btc_pending_sign_ids and account.btc_pending_verify_list are NEVER touched
}
```

The sibling function `internal_remove_refund_pending_tx_id` shows the correct pattern — it removes from **both** the global map and the account's sets:

```rust
// btc_pending_info.rs lines 426-430
self.internal_remove_btc_pending_info(&tx_id);
let account = self.internal_unwrap_mut_account(&account_id);
account.btc_pending_sign_ids.remove(&tx_id);
account.btc_pending_verify_list.remove(&tx_id);
```

After `internal_clear_invalid_pending_verify_rbf` succeeds, the global `btc_pending_infos` map no longer contains the entry, but the account's `btc_pending_sign_ids` and/or `btc_pending_verify_list` still hold the now-dangling tx-id. The two data structures are permanently out of sync.

The public entry points that expose this path carry no access-control restriction beyond the pause guard:

```rust
// api/bridge.rs lines 436-446
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) {
    self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
}

#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) {
    for btc_pending_verify_id in btc_pending_verify_ids {
        self.internal_clear_invalid_pending_verify_rbf(btc_pending_verify_id);
    }
}
```

Any unprivileged NEAR account may call either function.

---

### Impact Explanation

**Stale entry in `btc_pending_sign_ids`:** `require_pending_sign_capacity` counts `btc_pending_sign_ids.len()` against the per-account limit (default 1). A dangling entry permanently inflates this count, blocking the victim from initiating any further withdrawal, RBF, or refund that calls `require_pending_sign_capacity`. The victim's funds remain locked on NEAR with no self-service recovery path.

**Stale entry in `btc_pending_verify_list`:** Any code path that iterates or looks up entries in `btc_pending_verify_list` and then fetches the corresponding `BTCPendingInfo` will panic with "BTC pending info not exist", producing a stuck state requiring operator intervention.

Both effects match the allowed impact: *"Medium. Attacker-triggered temporary locking of bridged funds"* / *"Low. Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

---

### Likelihood Explanation

The precondition — an RBF pending-verify tx whose original tx-id is absent from `rbf_txs` — is the normal post-finalization state. Once the original withdrawal is verified on-chain and its `rbf_txs` entry is cleaned up, any leftover RBF pending-verify entries satisfy the guard. An attacker monitoring on-chain state can identify such entries and call `clear_invalid_pending_verify_rbf` targeting any victim's tx-id. No privileged access is required.

---

### Recommendation

Mirror the cleanup performed by `internal_remove_refund_pending_tx_id`. After removing from `btc_pending_infos`, also remove the tx-id from the account's sets:

```rust
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
    // Add the missing account cleanup:
    let account_id = btc_pending_info.account_id.clone();
    let account = self.internal_unwrap_mut_account(&account_id);
    account.btc_pending_sign_ids.remove(&btc_pending_id);
    account.btc_pending_verify_list.remove(&btc_pending_id);
}
```

### Proof of Concept

1. User U initiates a withdrawal; a `BTCPendingInfo` is created and `btc_pending_sign_ids` is updated for U's account.
2. U (or the protocol) submits an RBF transaction; a second `BTCPendingInfo` (RBF) is created and linked to the original via `rbf_txs`.
3. The original withdrawal is verified on-chain; `rbf_txs` entry for the original tx-id is removed during finalization.
4. The RBF pending-verify entry now satisfies `!rbf_txs.contains_key(original_tx_id)`.
5. Attacker calls `clear_invalid_pending_verify_rbf(rbf_tx_id)`.
6. `btc_pending_infos` loses the RBF entry; U's `btc_pending_sign_ids` / `btc_pending_verify_list` retains the dangling `rbf_tx_id`.
7. U's `pending_sign_count()` is now permanently ≥ 1 (the default limit), blocking all future withdrawals for U until an operator manually repairs state. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
