### Title
Unchecked `.unwrap()` on `transparent_bundle()` in Zcash `output()` Causes Publicly-Reachable Panic via `request_refund` - (File: contracts/satoshi-bridge/src/zcash_utils/transaction.rs)

---

### Summary

The `output()` method in the Zcash transaction wrapper unconditionally calls `.unwrap()` on `transparent_bundle()`. A Zcash transaction with no transparent bundle (a fully-shielded transaction) will cause a panic. This method is invoked inside `internal_request_refund` **before** any light-client proof is verified, so any unprivileged user can trigger the panic by submitting crafted `tx_bytes` to the public `request_refund` entry point.

---

### Finding Description

In `contracts/satoshi-bridge/src/zcash_utils/transaction.rs`, the `output()` method is:

```rust
pub fn output(&self) -> Vec<TxOut> {
    let outputs = self.inner_tx.transparent_bundle().unwrap().vout.clone();
```

`transparent_bundle()` returns `Option<&Bundle<…>>`. For a fully-shielded Zcash transaction (no transparent inputs or outputs), it returns `None`, and `.unwrap()` panics. [1](#0-0) 

This method is called inside `internal_request_refund` in `contracts/satoshi-bridge/src/refund.rs`:

```rust
let transaction =
    crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
        .expect("Deserialization tx_bytes failed");
let tx_id = transaction.compute_txid().to_string();

let config = self.internal_config();
let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
``` [2](#0-1) 

This code runs in the **first call** (not the callback), before the `verify_transaction_inclusion_promise` chain is even constructed. The light-client proof is never checked before `output()` is called.

The public entry point is `request_refund` in `contracts/satoshi-bridge/src/api/bridge.rs`:

```rust
pub fn request_refund(
    &mut self,
    deposit_msg: DepositMsg,
    refund_address: String,
    tx_bytes: Base64VecU8,
    vout: usize,
    proof: TxInclusionProof,
    gas_fee: Option<U128>,
) -> Promise {
``` [3](#0-2) 

The `#[trusted_relayer]` macro on the outer `impl` block does not apply to `request_refund` — it is callable by any NEAR account. The only prerequisite is attaching the required storage deposit, which is refunded on panic.

The same `output()` call also appears in `request_refund_callback` and `refund_execution_inputs`: [4](#0-3) [5](#0-4) 

The Bitcoin path does not share this defect; its `output()` method accesses `self.inner_tx.output` directly without an `Option` unwrap: [6](#0-5) 

---

### Impact Explanation

When the panic fires, NEAR reverts all state changes and refunds the attached deposit to the caller. No funds are permanently lost. However, this is a publicly reachable, panic-driven fault in a production bridge path (`request_refund`) that any unprivileged account can trigger at will. The contract's parsing layer fails to guard against a well-formed but fully-shielded Zcash transaction, matching the vulnerability class of unexpected-input-driven parser failure.

**Impact: Low** — publicly reachable panic-driven fault in production bridge/token path without direct theft.

---

### Likelihood Explanation

Any NEAR account can call `request_refund`. The only cost to the attacker is the attached storage deposit (refunded on panic) and gas. Constructing a valid fully-shielded Zcash transaction is straightforward with standard Zcash tooling. No privileged role, leaked key, or third-party compromise is required.

---

### Recommendation

Replace the bare `.unwrap()` with explicit error handling that propagates a meaningful error to the caller rather than panicking:

```rust
pub fn output(&self) -> Result<Vec<TxOut>, String> {
    let bundle = self.inner_tx.transparent_bundle()
        .ok_or_else(|| "Transaction has no transparent bundle".to_string())?;
    Ok(bundle.vout.iter().map(|o| { /* convert */ }).collect())
}
```

All call sites in `refund.rs` should then propagate the error with `expect` or `map_err` so the failure is surfaced as a clean `require!` rejection rather than an uncontrolled panic.

---

### Proof of Concept

1. Using standard Zcash tooling, construct a valid fully-shielded Zcash V5 transaction (Orchard-only, no transparent bundle). Serialize it to bytes.
2. Call `request_refund` on the Zcash bridge contract with:
   - `tx_bytes` = the fully-shielded transaction bytes
   - `vout` = 0
   - Any valid `deposit_msg`, `refund_address`, and `proof` fields
   - Attached deposit ≥ `required_balance_for_request_refund()`
3. Inside `internal_request_refund`, `WrappedTransaction::decode` succeeds (the transaction is structurally valid).
4. `transaction.output()` calls `self.inner_tx.transparent_bundle().unwrap()` — `transparent_bundle()` returns `None` — `.unwrap()` panics.
5. NEAR reverts the call; the attached deposit is returned; the caller loses only gas.
