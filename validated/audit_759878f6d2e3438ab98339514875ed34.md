### Title
`validatePerasCert` Stub Unconditionally Accepts Any Peer-Sent Peras Certificate, Enabling Unauthorized Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub that always returns `Right`, performing zero cryptographic or protocol-level checks. The network-facing Peras certificate diffusion path calls this stub as its only validation gate before storing a peer-supplied certificate as a `ValidatedPerasCert` and triggering chain selection. An unprivileged peer can therefore send a crafted `PerasCert` boosting any block — including a block on a minority fork — and cause an honest node to prefer that non-canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:** [1](#0-0) 

The only defined `BlockSupportsPeras` instance (the "degenerate instance for all blks") implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

No signature is checked, no committee membership is verified, no round-number bounds are enforced. Every input certificate unconditionally becomes a `ValidatedPerasCert`.

**The gatekeeper that is bypassed — `processCerts`:** [2](#0-1) 

`processCerts` is the sole validation gate in the inbound certificate diffusion path. It calls the injected `validateCert` function and only rejects a batch when that function returns `Left`. Because `validatePerasCert` always returns `Right`, no peer-supplied certificate is ever rejected.

**The production writer wires the stub directly into the ChainDB path:** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` — explicitly described as the production path — passes `validatePerasCert mkPerasParams` as the validation function, with a TODO comment acknowledging the placeholder.

**Chain selection is triggered for the boosted block:** [4](#0-3) 

`chainSelSync` receives the `ValidatedPerasCert`, stores it in `PerasCertDB`, and calls `chainSelectionForBlock` for the boosted block. The `getWeightSnapshot` snapshot then returns the boost weight for that block, causing the node to prefer the boosted chain.

**End-to-end attacker-controlled path:**

1. Peer connects via the `PerasCertDiffusion` mini-protocol (wired in `NodeToNode.hs`).
2. Peer sends a crafted `PerasCert { pcCertRound = r, pcCertBoostedBlock = <minority-fork-block> }`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. Certificate is timestamped and passed to `ChainDB.addPerasCertAsync`.
5. `chainSelSync` stores it in `PerasCertDB` and triggers chain selection for the boosted block.
6. The node's chain selection now assigns `perasWeight = 15` extra weight to the minority-fork block, potentially switching the node's preferred chain.

---

### Impact Explanation

**Severity: High — chain selection manipulation by an unprivileged peer.**

Any peer that can establish a `PerasCertDiffusion` connection can inject an arbitrary number of certificates boosting any block in the VolatileDB. Because the boost weight (`perasWeight = 15`) is added to chain selection, a peer can cause an honest node to prefer a non-canonical fork over the honest chain, violating the chain-selection invariant that only legitimately certified blocks receive Peras boosts. This directly matches the allowed impact category: *"Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol is fully wired into the node-to-node application in `NodeToNode.hs`. Any peer that connects to the node can send Peras certificates. No stake, key material, or operator privilege is required. The attack requires only the ability to open a standard node-to-node connection and send a well-formed (but semantically fraudulent) `PerasCert` message. Likelihood is **high** given the zero-privilege entry point.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real validation before the Peras certificate diffusion path is active in any networked environment. At minimum, the validation must:

1. Verify the aggregate BLS signature against the claimed voter set and the committee derived from the current ledger stake distribution.
2. Check that the claimed voters are eligible committee members for the given round.
3. Verify that the quorum threshold is met by the aggregate stake of the signers.
4. Enforce round-number bounds (not expired, not from the future).

Until real validation is in place, the `makePerasCertPoolWriterFromChainDB` writer should either be disabled or guarded so that it is unreachable from the live network stack. The structural fix mirrors the external report's resolution: consolidate to a single, validated code path so that no `ValidatedPerasCert` can enter the system without passing all checks.

---

### Proof of Concept

On a private testnet with Peras diffusion enabled:

```
# Attacker node sends a crafted PerasCert over the PerasCertDiffusion mini-protocol:
#   pcCertRound      = <current round>
#   pcCertBoostedBlock = <tip of a minority fork in the victim's VolatileDB>
#
# processCerts calls validatePerasCert mkPerasParams cert
#   => always Right (no signature check)
#
# chainSelSync stores the cert and calls chainSelectionForBlock for the minority tip.
# getWeightSnapshot now returns perasWeight=15 for the minority block.
# If the minority chain's length + 15 > honest chain's length, the node switches.
```

The degenerate `validatePerasCert` at lines 353–358 of `SupportsPeras.hs` is the necessary vulnerable step: removing the stub and replacing it with a real check that returns `Left` for unsigned certificates immediately closes the attack path. [5](#0-4) [6](#0-5) [7](#0-6) [8](#0-7)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
