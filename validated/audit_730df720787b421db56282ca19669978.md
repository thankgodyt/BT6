### Title
Hardcoded `mkPerasParams` Passed to `validatePerasVote` Instead of Node-Configured `PerasCfg` in Inbound Vote Processing — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

Both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` — the two production entry points for processing inbound Peras votes received from network peers — call `validatePerasVote` with the hardcoded constant `mkPerasParams` instead of the node's actual configured `PerasCfg`. This is a direct analog of the reported bug: a function that accepts a configuration parameter is called with a wrong/hardcoded value instead of the correct one from the relevant interface.

---

### Finding Description

The `BlockSupportsPeras` class defines `validatePerasVote` with the signature:

```haskell
validatePerasVote :: PerasCfg blk -> PerasVoteStakeDistr -> PerasVote blk
                  -> Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The first argument is the protocol configuration (`PerasCfg blk`), which for the current degenerate instance equals `PerasParams`. This configuration controls the quorum stake threshold (`perasQuorumStakeThreshold`) and safety margin (`perasQuorumStakeThresholdSafetyMargin`) used downstream in `votesReachQuorum` and `stakeAboveThreshold` when aggregating votes and forging certificates.

In both pool-writer constructors, the validation lambda ignores the `PerasCfg` that should come from the node's actual configuration and instead passes the hardcoded `mkPerasParams` constant:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
```

This appears at line 111 (`makePerasVotePoolWriterFromVoteDB`) and line 141 (`makePerasVotePoolWriterFromChainDB`).

The correct `PerasCfg` is available at the `PerasVoteDB` level: `createDB` in `PerasVoteDB.Impl` accepts a `pvdbaPerasCfg :: HKD f (PerasCfg blk)` and correctly threads it into `implAddVote`. However, the pool-writer layer — which is the network-facing inbound path — bypasses this and uses the hardcoded constant.

The `mkPerasParams` constant is explicitly documented as tentative:

> "Many of these parameters are provided with sensible default values for now, waiting for a final decision (in a future stage of the project) on the exact values to use." [1](#0-0)

### Impact Explanation

**Impact: High — Bypass of Peras certificate/vote validation checks.**

The `PerasCfg` (i.e., `PerasParams`) governs the quorum stake threshold used to decide when a certificate is forged. Specifically, `votesReachQuorum` calls `stakeAboveThreshold cfg totalVoteStake`, where `cfg` is the `PerasCfg` passed to `validatePerasVote` and then forwarded through `ValidatedPerasVotesWithQuorum.vpvqPerasCfg`. [6](#0-5) 

If the actual network-deployed `PerasParams` differ from `mkPerasParams` (e.g., a lower `perasQuorumStakeThreshold`), the inbound vote validation path uses the wrong threshold. An adversarial peer can craft a batch of votes that:

1. Passes the hardcoded `mkPerasParams` threshold (e.g., 3/4 stake), causing `validatePerasVote` to accept them.
2. Would fail under the real configured threshold, meaning the node accepts and stores votes — and potentially forges certificates — that should have been rejected.

Conversely, if the real threshold is lower than `mkPerasParams`, legitimate votes may be rejected, causing the node to disconnect from honest peers (via `PerasVoteInboundException`). [7](#0-6) 

A forged certificate with wrong quorum parameters can trigger a chain-selection fork switch via `addPerasCertAsync`, causing the node to prefer a non-canonical chain boosted by an illegitimate certificate. [8](#0-7) 

---

### Likelihood Explanation

**Likelihood: Medium.** The degenerate `BlockSupportsPeras` instance currently used for all blocks means `PerasCfg blk = PerasParams`, and `mkPerasParams` is the only available value. The mismatch is latent today but becomes exploitable as soon as the Peras protocol is activated with real, potentially different parameters. The network-facing path (`makePerasVotePoolWriterFromChainDB`) is the production path used by the object-diffusion miniprotocol to process votes from any connected peer, making the attacker-controlled entry path direct and unauthenticated.

---

### Recommendation

Both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB` must accept the node's actual `PerasCfg blk` as a parameter and pass it to `validatePerasVote` instead of `mkPerasParams`. The `PerasCfg` should be threaded from the node's `TopLevelConfig` or `BlockConfig` down to these constructors, consistent with how `createDB` in `PerasVoteDB.Impl` already accepts `pvdbaPerasCfg`. [9](#0-8) 

---

### Proof of Concept

1. A peer connects and sends a batch of `PerasVote` messages via the object-diffusion miniprotocol.
2. `makePerasVotePoolWriterFromChainDB` is the active pool writer; its `opwAddObjects` calls `processVotes`.
3. `processVotes` calls the validation lambda `(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)`.
4. `validatePerasVote mkPerasParams` uses `perasQuorumStakeThreshold = 3/4` regardless of the node's actual configured threshold.
5. If the real threshold is higher (e.g., 9/10), votes from a minority coalition (e.g., 80% stake) pass the hardcoded check but should fail the real check.
6. The validated votes are stored and `updatePerasRoundVoteStates` is called with the `PerasCfg` from `pvdbaPerasCfg` (the DB-level config), which may now forge a certificate using votes that were improperly admitted.
7. The forged `ValidatedPerasCert` is submitted via `addPerasCertAsync`, potentially triggering a chain-selection fork switch to a block boosted by an illegitimate certificate. [10](#0-9)

data PerasVoteInboundException
  = forall blk. PerasVoteValidationError [PerasValidationErr blk]

deriving instance Show PerasVoteInboundException

instance Exception PerasVoteInboundException

-- | Process a batch of inbound Peras votes received from a peer.
--
-- Votes whose ID is already present in the database (as determined by
-- @alreadyInDbSTM@) are silently skipped. The remaining votes are validated;
-- if /any/ vote in the batch fails validation, the entire batch is rejected
-- by throwing a 'PerasVoteInboundException' (which should make us disconnect
-- from the distant peer, see 'withPeer' bracket function from
-- `ouroboros-network`). Otherwise, each valid vote is timestamped with the
-- current wall-clock time and added to the database via @addVote@.
processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)

```haskell
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```

addPerasVoteWithAsyncCertHandling ::
  forall m blk.
  IOLike m =>
  ChainDbEnv m blk ->
  WithArrivalTime (ValidatedPerasVote blk) ->
  m (AddPerasVoteResult blk, Maybe (AddPerasCertPromise m))
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      let certTime = getArrivalTime vote
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)
      pure (addVoteRes, Just promise)
    _ -> pure (addVoteRes, Nothing)
