### Title
Hardcoded Zero `BRIDGE_OVK` Causes `recover_output_with_ovk` to Return `None` for All Standard-Wallet Orchard Bundles, Permanently Breaking the Shielded Withdrawal Path — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary

`BRIDGE_OVK` is hardcoded to `[0u8; 32]`. Every standard Zcash wallet encrypts Orchard output notes to a real, non-zero outgoing viewing key. When such a bundle is submitted through the public `Withdraw` path, `recover_output_with_ovk` cannot decrypt the note, returns `None`, and the bridge panics with `ERR_INVALID_ORCHARD_BUNDLE`. The shielded withdrawal path is therefore unreachable for any user relying on a standard Zcash wallet.

---

### Finding Description

`BRIDGE_OVK` is defined as an all-zero constant: [1](#0-0) 

Inside `extract_orchard_bundle`, this constant is used as the sole OVK to attempt decryption of the action's outgoing ciphertext: [2](#0-1) 

`recover_output_with_ovk` (from the `orchard` crate) derives a symmetric key from the OVK and the action's ephemeral key, then attempts to decrypt the outgoing ciphertext. If the bundle was encrypted with any other OVK — which is the case for every standard Zcash wallet — decryption fails and the function returns `None`. The `ok_or_else` on line 61 converts that `None` into `Err("Failed to recover Orchard output with bridge OVK")`.

`PsbtWrapper::new` converts that `Err` into an unconditional `env::panic_str`: [3](#0-2) 

`PsbtWrapper::new` is called from `ft_on_transfer_callback`, the private callback in the NEP-141 withdraw promise chain: [4](#0-3) 

The full public call sequence is:

```
ft_transfer_call (token contract, unprivileged)
  → ft_on_transfer (bridge, public)
    → ft_on_transfer_withdraw_chain_specific
      → [promise] ft_on_transfer_callback
          → PsbtWrapper::new
              → extract_orchard_bundle
                  → recover_output_with_ovk(0, &zero_ovk) → None
                      → panic_str("ERR_INVALID_ORCHARD_BUNDLE")
```

The entry point is fully public: [5](#0-4) 

---

### Impact Explanation

Every Orchard bundle produced by a standard Zcash wallet (non-zero OVK) is unconditionally rejected. The shielded withdrawal path — the only mechanism for withdrawing to an Orchard address — is permanently broken for all real-world users. Because the panic occurs inside the NEP-141 callback, NEAR's `ft_resolve_transfer` refunds the tokens, so there is no direct fund loss; however, the intended bridge functionality is completely non-operational for its target use case.

---

### Likelihood Explanation

The likelihood is **high** for any user attempting a shielded withdrawal with a standard Zcash wallet. The zero-OVK requirement is not documented anywhere in the public API, and no standard Zcash wallet produces bundles encrypted to `[0u8; 32]`. Every real-world attempt to use the shielded withdrawal path will trigger the panic.

---

### Recommendation

The bridge must either:

1. **Expose and distribute `BRIDGE_OVK` to users** so that wallets or client-side tooling can encrypt the Orchard output note to the bridge's OVK before submission. The OVK should be a real key derived from a bridge-controlled spending key, not the all-zero placeholder.
2. **Or document and enforce at the API boundary** that `orchard_bundle_bytes` must be encrypted to `BRIDGE_OVK = [0u8; 32]`, and provide a reference client library that constructs such bundles. The current code comment ("can be made configurable later") confirms this is an unfinished design.

The all-zero OVK is also cryptographically weak as a long-term choice; a proper OVK derived from a bridge-controlled key should be used.
