### Title
Peras Certificate Signature Verification Bypass Enables Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `BlockSupportsPeras` provides a `validatePerasCert` implementation that unconditionally accepts every inbound certificate without performing any cryptographic verification. Because the `PerasCert blk` data type carries no signature field and `validatePerasCert` always returns `Right`, any unprivileged peer can send a crafted certificate for an arbitrary round and block, have it accepted as "validated," and trigger chain-selection weight boosts for a block of the attacker's choosing.

---

### Finding Description

`BlockSupportsPeras` is the typeclass that governs Peras certificate and vote validation. Its only concrete instance is declared as a "degenerate instance for all blks to get things to compile":

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  data PerasCert blk = PerasCert
    { pcCertRound       :: PerasRoundNo
    , pcCertBoostedBlock :: Point blk
    }
```

The `PerasCert blk` type carries **no signature field and no voter list**. The corresponding `validatePerasCert` implementation is:

```haskell
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

This function ignores `cert` entirely and always returns `Right`. [1](#0-0) 

The production inbound path for certificates received from peers is `makePerasCertPoolWriterFromChainDB`, which calls `processCerts` with `validatePerasCert mkPerasParams` as the validator:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` filters out already-known round numbers, then calls `validateCert` on each remaining certificate. Because `validatePerasCert` always returns `Right`, every novel `(roundNo, boostedBlock)` pair passes validation and is forwarded to `addPerasCertAsync`. [3](#0-2) 

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which processes it by adding it to the `PerasCertDB` and then calling `chainSelectionForBlock` for the boosted block, potentially switching the node to a different fork: [4](#0-3) 

A parallel issue exists in `validatePerasVote`, which only checks whether the voter ID appears in the stake distribution but never verifies the vote's cryptographic signature. The `PerasVote blk` type likewise carries no signature field. An attacker can therefore forge votes for any registered voter ID, accumulate enough fake stake to reach quorum, and cause the node to locally forge a certificate — all without possessing any private key. [5](#0-4) 

A proper `V1.PerasCert` type with a `pvSignature` field and a `pcVoters` map does exist in `Peras/Vote/V1.hs`, and the `WFALS`/`EveryoneVotes` committee implementations do perform full BLS aggregate-signature verification in `implVerifyCert`. However, none of this code is wired into the `BlockSupportsPeras` instance that the production diffusion layer actually calls. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can send a `PerasCert blk` message containing any `(pcCertRound, pcCertBoostedBlock)` pair. The receiving node will accept it as a `ValidatedPerasCert`, store it in the `PerasCertDB`, and trigger chain selection for the boosted block. If the attacker's chosen block is on a competing fork, the node will switch to that fork, diverging from the canonical chain. Because Peras certificates provide weight boosts that override the normal longest-chain rule, a single forged certificate is sufficient to cause a chain-selection switch. This constitutes a **High** impact: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

The attack requires only the ability to send a well-formed CBOR-encoded `PerasCert blk` message over the Peras certificate mini-protocol. No private key, no stake, and no prior interaction with the target node is needed. Any peer that can establish a connection and speak the object-diffusion protocol can exploit this. Likelihood is **High**.

---

### Recommendation

1. **Immediate**: Gate the Peras certificate and vote mini-protocols behind a feature flag or era check so they are not reachable until the full `BlockSupportsPeras` instance — including BLS aggregate-signature verification via `implVerifyCert` from `WFALS`/`EveryoneVotes` — is wired in.
2. **Structural**: Replace the degenerate `instance StandardHash blk => BlockSupportsPeras blk` with a proper Cardano-era-specific instance that delegates `validatePerasCert` to `verifyCert` (from `Committee.Class`) and `validatePerasVote` to `verifyVote`, using the concrete `V1.PerasCert`/`V1.PerasVote` types that carry the required BLS signatures and voter maps.
3. **Type-level enforcement**: Add the BLS signature field to the `PerasCert blk` and `PerasVote blk` associated data types in the `BlockSupportsPeras` class so that the type system prevents a no-op validator from compiling without explicitly discarding the signature.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a target node and speaks the Peras certificate object-diffusion mini-protocol.
2. Attacker sends a batch containing one `PerasCert blk`:
   - `pcCertRound = <any round not yet in the DB>`
   - `pcCertBoostedBlock = <point of a block on a competing fork>`
3. `processCerts` reads `alreadyInDb` (the set of known round numbers), finds the round absent, and calls `validatePerasCert mkPerasParams cert`.
4. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally. [7](#0-6) 
5. `addPerasCertAsync` enqueues the cert; `chainSelSync` processes it, adds it to `PerasCertDB`, and calls `chainSelectionForBlock` for the attacker's chosen block. [8](#0-7) 
6. The node switches to the attacker's fork.

**Vote-based variant (quorum forgery):**

1. Attacker reads the current `PerasVoteStakeDistr` (available via the local state-query protocol or inferred from the public stake distribution).
2. Attacker sends a batch of `PerasVote blk` messages, each with a distinct `pvVoteVoterId` drawn from the stake distribution, all targeting the same `(pvVoteRound, pvVoteBlock)`.
3. `validatePerasVote` accepts each vote (stake lookup succeeds; no signature check). [9](#0-8) 
4. Once accumulated stake exceeds the quorum threshold, `updatePerasRoundVoteStates` forges a certificate locally, which is then added via `addPerasCertAsync`, triggering chain selection. [10](#0-9)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
