### Title
Unvalidated `refund_address` Stored at Request Time Enables Attacker-Triggered Stuck Refund State — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` accepts a caller-supplied `refund_address` string and stores it in a `RefundRequest` without validating it against the configured chain's address format. Validation only occurs later, inside `execute_refund → build_refund_output`, via a hard `expect` panic. Because `request_refund` is publicly callable and only one refund request is allowed per UTXO, an unprivileged attacker can front-run a legitimate depositor's refund call with an invalid address, permanently blocking that UTXO's refund path until an operator manually rejects the stuck request.

---

### Finding Description

**Analog to the external report:** The external report shows that `erc20TokensValid` is set from a single `address == 0` check, so any non-zero address—including a malicious contract—is accepted as a valid ERC-20 token without whitelist validation. The fix is to validate the token against a whitelist at storage time, not at payment time. The same pattern exists here: the `refund_address` is accepted and stored at request time without format validation; the only validation happens at execution time via a panicking `expect`.

**Root cause — storage without validation:**

In `internal_request_refund` the address is forwarded to the callback without any format check: [1](#0-0) 

In `request_refund_callback` the address is written directly into the stored `RefundRequest`: [2](#0-1) 

**Validation deferred to execution time — panics on invalid input:**

`build_refund_output` calls `Address::parse(...).expect("Invalid refund address")`. If the stored string is not a valid address for the configured chain, this panics and `execute_refund` aborts: [3](#0-2) 

**One-request-per-UTXO gate blocks the legitimate depositor:**

`request_refund_callback` enforces that only one refund request may exist per UTXO storage key. Once the attacker's request is stored, the legitimate depositor's subsequent call is rejected: [4](#0-3) 

**No role restriction on `request_refund`:**

The function carries only `#[pause(except(roles(Role::DAO)))]`—no caller whitelist. Any NEAR account can call it when the contract is unpaused: [5](#0-4) 

---

### Impact Explanation

An attacker who front-runs a depositor's `request_refund` with a syntactically invalid `refund_address` (e.g., `"not_an_address"`) causes:

1. The stuck `RefundRequest` to be stored on-chain.
2. Every subsequent `execute_refund` call for that UTXO to panic.
3. The depositor to be unable to submit a new refund request until an operator calls `reject_refund`.

This is a **publicly reachable, panic-driven stuck-state fault in a production bridge path** — matching the Low allowed impact: *"Publicly reachable invariant-violation, stuck-state, or panic-driven fault in production bridge/token paths without direct theft."*

The deposit itself is not permanently lost: `verify_deposit` can still finalize it (since `verified_deposit_utxo` is only set inside `finalize_refund_with_psbt`, which is never reached), and DAO/Operator can call `reject_refund`. However, the depositor's refund is blocked until operator intervention occurs.

---

### Likelihood Explanation

- `request_refund` is callable by any NEAR account with no role restriction.
- The attacker only needs to observe a pending, unfinalized deposit (publicly visible on-chain) and submit a `request_refund` with an invalid address before the legitimate depositor does.
- The cost to the attacker is the non-refunded storage deposit (`required_balance_for_request_refund`), which is a small NEAR amount.
- Front-running on NEAR is feasible via transaction ordering within a block.

---

### Recommendation

Validate `refund_address` against the chain's address format inside `request_refund_callback` (or in `internal_request_refund`) before storing it, mirroring the validation already present in `build_refund_output`:

```rust
// In request_refund_callback, before constructing RefundRequest:
crate::network::Address::parse(&refund_address, &config.chain)
    .unwrap_or_else(|e| env::panic_str(&format!("Invalid refund_address: {e}")));
```

This ensures that any invalid address is rejected at request time, preventing stuck requests and aligning with the whitelist/validation-at-storage-time pattern recommended in the external report.

---

### Proof of Concept

1. Alice deposits BTC with `deposit_msg.refund_address = None`; the deposit is not yet finalized via `verify_deposit`.
2. Alice submits `request_refund` with a valid BTC address and the correct `tx_bytes` + proof.
3. Bob (attacker) observes Alice's pending transaction and submits his own `request_refund` for the same UTXO with `refund_address = "INVALID"` and a higher gas price, landing first.
4. Bob's callback stores `RefundRequest { refund_address: "INVALID", ... }`.
5. Alice's callback reverts: `"Refund request already exists for this UTXO"`.
6. Any call to `execute_refund` for this UTXO panics inside `build_refund_output` at `Address::parse("INVALID", ...).expect(...)`.
7. Alice's refund is blocked until DAO calls `reject_refund`, after which Alice must re-submit and re-pay the storage deposit.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }

    #[payable]
    #[pause(except(roles(Role::DAO)))]
    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
