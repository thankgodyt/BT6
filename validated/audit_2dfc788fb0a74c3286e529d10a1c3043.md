### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain Weight Boost - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance for all block types defines a `validatePerasCert` that unconditionally returns `Right` (success) without performing any cryptographic or structural validation. The `PerasCert` data type itself carries no cryptographic signature. Because this is the only `BlockSupportsPeras` instance in the codebase (no Cardano-specific override exists), any peer-supplied certificate is accepted as valid, stored in the `PerasCertDB`, and used to boost an attacker-chosen block's weight in chain selection.

---

### Finding Description

**Vulnerability class (analog mapping):** The OmnichainStaking report describes an *authorization bypass via equivalent-weight substitution*: a function that should only act on a resource owned by the caller instead accepts any resource with equivalent "power", because the ownership binding is never checked. The analog here is a *certificate validation bypass*: a function that should cryptographically bind a certificate to a legitimate quorum of stake-weighted voters instead accepts any certificate unconditionally, because the binding is never checked.

**Root cause — `validatePerasCert` stub:**

`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` defines the only `BlockSupportsPeras` instance in the repository as a catch-all over all `StandardHash blk` types:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
``` [1](#0-0) 

The `PerasCert` data type defined in this instance carries **no cryptographic signature field**:

```haskell
data PerasCert blk = PerasCert
  { pcCertRound        :: PerasRoundNo
  , pcCertBoostedBlock :: Point blk
  }
``` [2](#0-1) 

The `validatePerasCert` implementation unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [3](#0-2) 

There is no more specific `BlockSupportsPeras` instance anywhere in `ouroboros-consensus-cardano` (confirmed: grep returns no matches). This catch-all is therefore the live production code path.

**Attacker-controlled entry path — `processCerts`:**

`makePerasCertPoolWriterFromChainDB` (the production writer used for peer-received certificates) calls `processCerts` with `validatePerasCert mkPerasParams` as the validation function:

```haskell
opwAddObjects = \certs ->
  processCerts
    systemTime
    (ChainDB.getPerasCertIds chainDB)
    -- TODO replace when actual plumbing is in place
    (validatePerasCert mkPerasParams)
    (void . ChainDB.addPerasCertAsync chainDB)
    certs
``` [4](#0-3) 

`processCerts` applies `validateCert` to every inbound certificate and, if all pass, adds them to the database:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [5](#0-4) 

Because `validatePerasCert` always returns `Right`, the `(errs, _)` branch is never taken. Every certificate from every peer is accepted.

**Chain selection consequence:**

Once a certificate is stored, `chainSelSync` in `ChainSel.hs` triggers chain selection for the boosted block. The certificate contributes a `PerasWeight` boost (derived from `perasWeight params`) to whichever block the attacker named in `pcCertBoostedBlock`. The `WeightedSelectView` chain-order comparison in `SelectView.hs` then prefers the heavier chain:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch (Heavier $ ...)
``` [6](#0-5) 

An attacker who names a block on a minority fork as `pcCertBoostedBlock` causes the honest node to switch to that fork.

**Secondary: `validatePerasVote` also performs no signature check:**

The `validatePerasVote` stub only checks stake-distribution membership, not any cryptographic proof:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [7](#0-6) 

An attacker can forge votes from any pool ID present in the stake distribution, trivially reach quorum via `votesReachQuorum`, and cause `forgePerasCert` to produce a certificate for any block — compounding the certificate-level bypass.

---

### Impact Explanation

An unprivileged peer with a network connection can:

1. Construct a `PerasCert { pcCertRound = r, pcCertBoostedBlock = p }` for any block point `p` in the node's VolatileDB and any round `r`.
2. Deliver it via the Peras cert diffusion mini-protocol.
3. The node accepts it unconditionally, stores it, and triggers chain selection.
4. The certificate adds a `PerasWeight` boost to block `p`, potentially making a minority-fork chain heavier than the canonical chain.
5. The node switches to the attacker's preferred chain — a consensus safety failure.

This is a **Critical** bypass of Peras certificate validation checks that enables unauthorized certificate acceptance and chain selection manipulation by an unprivileged peer.

---

### Likelihood Explanation

**High.** The attack requires only a TCP connection to a node running the Peras cert diffusion protocol. No keys, stake, or operator access are needed. The `PerasCert` type has no signature field, so the attacker does not need to break any cryptography — they simply construct a well-typed Haskell value and serialize it. The catch-all instance applies to all block types with no Cardano-specific override in the repository.

---

### Recommendation

1. **Add a cryptographic proof field to `PerasCert`** (e.g., an aggregate BLS signature over the election ID and candidate, as already designed in `Committee/Crypto.hs` and `Committee/WFALS.hs`).
2. **Implement `validatePerasCert`** to verify the aggregate signature against the declared voter set and the epoch's stake distribution, following the pattern already established in `WFALS.implVerifyCert`.
3. **Implement `validatePerasVote`** to verify the individual vote signature (and VRF proof for non-persistent voters) before accepting a vote from a peer.
4. Track and close issues [#73](https://github.com/tweag/cardano-peras/issues/73) and [#120](https://github.com/tweag/cardano-peras/issues/120) before the Peras cert diffusion protocol is enabled on any network that enforces chain selection by certificate weight.

### Proof of Concept

```
-- Attacker node connects to victim via the Peras cert diffusion mini-protocol.
-- Attacker picks a block hash on a minority fork that is in the victim's VolatileDB.

let forgeCert = PerasCert
      { pcCertRound        = PerasRoundNo 42          -- any round
      , pcCertBoostedBlock = BlockPoint slotNo forkHash  -- minority-fork block
      }

-- Send [forgeCert] via the ObjectDiffusion cert channel.
-- processCerts calls (validatePerasCert mkPerasParams forgeCert)
--   => always Right ValidatedPerasCert { vpcCertBoost = perasWeight params }
-- Certificate is stored in PerasCertDB.
-- chainSelSync triggers chain selection for forkHash.
-- WeightedSelectView: wsvTotalWeight(fork) > wsvTotalWeight(canonical)
--   because fork now carries the Peras weight boost.
-- Victim node switches to the minority fork.
```
