### Title
Hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` Causes Incorrect Chain-Selection Decision Beyond Forecast Horizon - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` helper inside the ChainSync client passes a hardcoded `emptyPerasWeightSnapshot` (all-zero Peras certificate weights) to `preferAnchoredCandidate` instead of the live `PerasWeightSnapshot` maintained by the `PerasCertDB`. This is the direct analog of the external report's bug: a critical calculation uses an incorrect parameter that does not account for state that has already been committed elsewhere in the system. When Peras is active and certificates have been issued, the comparison silently ignores all certificate boosts, producing a wrong chain-preference verdict that can cause a node to disconnect from a peer serving the canonical chain.

---

### Finding Description

When the ChainSync client receives a header whose slot is beyond the current forecast horizon, it blocks in `readLedgerStateHelper` waiting for the local selection to advance. While blocked it calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or to throw `CandidateTooSparse` and disconnect:

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded zero weights
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` is the central chain-order function. When the `PerasWeightSnapshot` is non-empty (Peras active), it computes `weightedSelectView` for both fragments and compares total weight (block count + certificate boost). When the snapshot is empty it falls back to a pure block-count comparison:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- block-count-only path
      ...
  | otherwise =
      -- full weighted path using certificate boosts
      ...
``` [2](#0-1) 

By always supplying `emptyPerasWeightSnapshot`, `checkPreferTheirsOverOurs` always takes the block-count-only path, regardless of what the live `PerasCertDB` contains. The `PerasCertDB` exposes the correct snapshot via `getWeightSnapshot`:

```haskell
getWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
``` [3](#0-2) 

and the `ChainDB` re-exports it:

```haskell
getPerasWeightSnapshot :: STM m (WithFingerprint (PerasWeightSnapshot blk))
``` [4](#0-3) 

The `checkPreferTheirsOverOurs` call site already has access to `cfg` and the `ChainDbView` (which includes `getPerasWeightSnapshot`), so the correct snapshot is available but is not used.

The `readLedgerStateHelper` call site that invokes `checkPreferTheirsOverOurs`:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
``` [5](#0-4) 

---

### Impact Explanation

**Classification: High — Chain-selection bug that causes an honest node to prefer a non-canonical chain beyond the intended security assumptions.**

When Peras is active, the canonical chain is determined by total weight (block count + certificate boosts), not block count alone. Consider:

- **C₁** (our current chain): 10 blocks, 0 certificate boosts → total weight 10.
- **C₂** (peer's chain): 9 blocks, 3 certificate boosts → total weight 12 (canonical).

A peer serving C₂ sends a header beyond the forecast horizon. `checkPreferTheirsOverOurs` compares the fragments using `emptyPerasWeightSnapshot`, so it sees C₂ as having weight 9 vs C₁'s weight 10. `shouldSwitch` returns `False`, the node throws `CandidateTooSparse`, and disconnects from the peer serving the canonical chain. The node remains on C₁, the non-canonical chain, indefinitely until another peer re-offers C₂ and the forecast horizon has advanced.

This is a durable chain-selection error: the node actively rejects the canonical chain and stays on a lighter fork, violating the Peras security guarantee that certificate boosts determine chain preference.

---

### Likelihood Explanation

- **Peras must be active.** The CHANGELOG notes "if Peras is disabled (which is the default), there is no observable difference." The bug is latent today but becomes exploitable once Peras is enabled on a production network.
- **Headers must be beyond the forecast horizon.** This is a normal condition during initial sync or when a peer is significantly ahead.
- **The canonical chain must be heavier due to certificate boosts but shorter in block count.** This is the intended use-case of Peras: a chain with a quorum certificate is preferred even if it is slightly shorter.
- **No special privileges required.** Any peer serving valid headers triggers the code path. The peer does not need to be malicious; an honest peer serving the canonical chain is sufficient.

The TODO comment (`// TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is incorrect, but the code remains in production files and will execute when Peras is enabled.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` with the live snapshot read from the `PerasCertDB` (available via `ChainDbView.getPerasWeightSnapshot`) inside `checkPreferTheirsOverOurs`. Since this function already runs inside an `STM` block, reading the snapshot atomically is straightforward. Alternatively, if the intent is to remove the check entirely (as the TODO suggests), do so before enabling Peras on production networks, as the current code produces incorrect chain-preference decisions whenever Peras certificates are present.

---

### Proof of Concept

1. Enable Peras on a private testnet with security parameter `k = 5`.
2. Issue a Peras certificate boosting block `B` on chain `C₂` (9 blocks, total weight 12).
3. The local node is on chain `C₁` (10 blocks, total weight 10).
4. A peer begins serving headers for `C₂`; the tip of `C₂` is beyond the current forecast horizon.
5. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
6. `preferAnchoredCandidate` is invoked with `emptyPerasWeightSnapshot`; it compares block counts: 10 vs 9.
7. `shouldSwitch` returns `False` (C₁ appears heavier by block count).
8. `throwSTM CandidateTooSparse` fires; the node disconnects from the peer.
9. The node remains on `C₁` (weight 10) and never adopts `C₂` (weight 12, the canonical chain).

          (Empty ourAnchor, _ :> theirTip) ->
