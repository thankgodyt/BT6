Audit Report

## Title
Tokens Burned or Permanently Frozen Before Destination-Chain Validation in `init_transfer_internal` - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer` accepts any non-NEAR destination chain without verifying that the chain has a registered factory or that the token is mapped to an address on that chain. `init_transfer_internal` then immediately burns deployed tokens via a detached (fire-and-forget) promise and silently skips lock accounting for unregistered pairs. The only validation that would catch the misconfiguration — `get_token_address` in `sign_transfer` — runs after the irreversible state change, leaving the transfer permanently stuck and the user's funds unrecoverable.

## Finding Description
`init_transfer` performs exactly one destination-chain guard:

```rust
// L531-534
require!(
    init_transfer_msg.recipient.get_chain() != ChainKind::Near,
    BridgeError::InvalidRecipientChain.as_ref()
);
```

There is no check that `self.factories` or `self.token_id_to_address` contains an entry for the destination chain. Execution proceeds to `init_transfer_internal` (L1829), which unconditionally calls:

```rust
// L1850-1857
self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
self.lock_tokens_if_needed(
    transfer_message.get_destination_chain(),
    &token_id,
    transfer_message.amount.0,
);
```

`burn_tokens_if_needed` (L1806-1813) issues a detached cross-contract call — the burn is submitted and the current execution frame continues regardless of the outcome:

```rust
fn burn_tokens_if_needed(&self, token: AccountId, amount: U128) {
    if self.is_deployed_token(&token) {
        ext_token::ext(token)
            .with_static_gas(BURN_TOKEN_GAS)
            .burn(amount)
            .detach();   // fire-and-forget; no rollback possible
    }
}
```

`lock_tokens_if_needed` (token_lock.rs L96-107) calls `lock_tokens`, which checks `self.locked_tokens.get(&key)`. When the `(chain_kind, token_id)` key is absent — as it will be for any unregistered chain — it returns `LockAction::Unchanged` and records nothing. The tokens are held by the bridge contract but completely untracked.

The validation that would detect the problem only runs in `sign_transfer` (L462-469), called later by a trusted relayer:

```rust
let token_address = self
    .get_token_address(
        transfer_message.get_destination_chain(),
        self.get_token_id(&transfer_message.token),
    )
    .unwrap_or_else(|| {
        env::panic_str(BridgeError::FailedToGetTokenAddress.to_string().as_str())
    });
```

`get_token_address` (L1360-1366) is a plain map lookup returning `None` for any unregistered pair, causing `sign_transfer` to panic on every invocation. The transfer record remains in `pending_transfers` indefinitely. No user-accessible cancel or refund function exists in the contract; `transfer_token_as_dao` (L1511-1529) is DAO-gated and cannot recover already-burned tokens.

## Impact Explanation
This directly matches the Critical allowed impact: **permanent freezing or loss of bridged funds**.

- **Deployed (bridged) tokens** (e.g., an ETH-originated token held on NEAR): `burn_tokens_if_needed` destroys them via a detached promise before any destination-chain check. The tokens are permanently destroyed with no on-chain recovery path.
- **Native NEAR tokens** (e.g., USDC.near): transferred into the bridge via `ft_transfer_call`, then `lock_tokens_if_needed` silently does nothing because the `(chain, token)` key is absent from `locked_tokens`. The tokens are held by the bridge contract but untracked and inaccessible to the user. Every subsequent relayer call to `sign_transfer` panics, leaving the transfer permanently stuck.

In both cases the `InitTransferEvent` is emitted and the transfer is stored in `pending_transfers`, giving the false appearance of a valid in-flight transfer.

## Likelihood Explanation
Any unprivileged token holder can trigger this with a single `ft_transfer_call` to any NEP-141 token, passing an `InitTransfer` message whose `recipient` encodes a chain for which the token has not been registered via `bind_token` / `deploy_token`. The bridge supports many chains (`Eth`, `Sol`, `Arb`, `Base`, `Bnb`, `Pol`, `Abs`, `HyperEvm`, `Strk`, `Fogo`, `Btc`, `Zcash`), and a token is typically registered on only a subset of them. A user who selects a valid-looking chain enum value for an unregistered token-chain pair will silently lose funds. No special privileges, leaked keys, or external collusion are required. The condition is repeatable and deterministic.

## Recommendation
Add upfront validation in `init_transfer`, before `init_transfer_internal` is entered, that:

1. Confirms `self.factories.get(&destination_chain).is_some()`, and
2. Confirms `self.token_id_to_address.get(&(destination_chain, token_id)).is_some()`.

Both checks must occur before any token state change, mirroring the pattern already used in `sign_transfer` but moved to the point where the transfer is first accepted. This ensures that a transfer to an unconfigured destination chain is rejected atomically, allowing `ft_transfer_call` to refund the caller via the standard NEP-141 return-value mechanism.

## Proof of Concept
1. Token `usdc.near` is registered for `ChainKind::Eth` but **not** for `ChainKind::Sol` (no `token_id_to_address` entry for `(Sol, usdc.near)`).
2. Attacker/user calls `usdc.near::ft_transfer_call(bridge, amount, '{"recipient":"Sol:<valid_sol_addr>","fee":"0",...}')`.
3. `init_transfer` passes the only guard at L531-534 (`Sol != Near`).
4. `init_transfer_internal` is entered. If `usdc.near` is a deployed token, `burn_tokens_if_needed` fires a detached burn at L1808-1811 — tokens destroyed. If it is a native token, `lock_tokens_if_needed` returns `Unchanged` at token_lock.rs L56 — tokens held but untracked.
5. `InitTransferEvent` is emitted; transfer stored in `pending_transfers`.
6. Relayer calls `sign_transfer`. `get_token_address(ChainKind::Sol, usdc.near)` returns `None` at L1365 → panic `ERR_FAILED_TO_GET_TOKEN_ADDRESS` at L467-469.
7. Transfer is permanently stuck. User's tokens are gone or frozen with no user-accessible recovery path.

A local integration test can reproduce this by: (a) deploying the bridge with `usdc.near` registered only for `Eth`, (b) calling `ft_transfer_call` with a `Sol` recipient, (c) asserting that the burn cross-contract call was submitted (for deployed tokens) or that `locked_tokens` was not updated (for native tokens), and (d) asserting that `sign_transfer` panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`.
