### Title
Silent Fallthrough in `ft_transfer` Legacy Path Permanently Locks nBTC in Token Contract When `withdraw_relayer` Is Unset - (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `ft_transfer` override in the nbtc token contract contains a legacy Near Intents withdrawal path that silently falls through to a self-transfer when `withdraw_relayer` is not configured. A user calling `ft_transfer(nbtc_contract_id, amount, Some("WITHDRAW_TO:..."))` while `withdraw_relayer` is unset will have their nBTC transferred into the nbtc contract's own token balance. No rescue or recovery function exists in the nbtc contract, making those tokens permanently irrecoverable.

---

### Finding Description

The `ft_transfer` function in `contracts/nbtc/src/lib.rs` overrides the standard NEP-141 implementation to support a legacy Near Intents withdrawal flow:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    // Legacy bridging flow used by Near Intents
    if receiver_id == env::current_account_id()
        && memo
            .as_ref()
            .is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        if let Some(withdraw_relayer) = Self::read_withdraw_relayer_address() {
            return self.token.ft_transfer(withdraw_relayer, amount, memo);
        }
    }

    self.token.ft_transfer(receiver_id, amount, memo);
}
``` [1](#0-0) 

When the two outer conditions are satisfied (`receiver_id == env::current_account_id()` and `memo.starts_with("WITHDRAW_TO:")`) but `withdraw_relayer` is `None`, the inner `if let` block is skipped and execution falls through to the final `self.token.ft_transfer(receiver_id, amount, memo)` call — where `receiver_id` is still `env::current_account_id()`, i.e., the nbtc contract itself. [2](#0-1) 

The `withdraw_relayer` is stored in raw contract storage and is **not** initialized in the `new()` constructor:

```rust
fn read_withdraw_relayer_address() -> Option<AccountId> {
    env::storage_read(WITHDRAW_RELAYER_ADDRESS).and_then(|data| borsh::from_slice(&data).ok())
}
``` [3](#0-2) 

It must be set separately via `set_withdraw_relayer_address`, which is only callable by the controller: [4](#0-3) 

This creates a deployment window — and any misconfiguration window — during which the fallthrough is live. The nbtc contract's own account can be registered in its own token ledger by any caller via the public `storage_deposit` function, making the self-transfer succeed.

Once tokens land in the nbtc contract's own balance, there is no path to recover them:

- The `burn` function is only callable by the bridge and always withdraws from `self.bridge_id` (the bridge's balance), not from the nbtc contract's own balance.
- No rescue or sweep function exists in the nbtc contract.
- The controller has no privileged withdrawal capability. [5](#0-4) 

---

### Impact Explanation

Any nBTC transferred into the nbtc contract's own balance via this path is permanently locked. The total supply remains inflated (tokens are not burned), but those tokens are inaccessible to any user or admin. This constitutes a permanent, irrecoverable loss of user funds with no operator intervention path. It matches the allowed impact: **Medium — harmful smart-contract behavior including permanent burning below backed supply or stuck bridge state requiring operator intervention** (here, no intervention is even possible).

---

### Likelihood Explanation

The `withdraw_relayer` is absent from the `new()` constructor and must be set in a separate transaction. Any deployment that omits or delays this step leaves the fallthrough live. Additionally, the nbtc contract's own account is not registered by default, but any external caller can register it via `storage_deposit` at zero cost. The Near Intents legacy flow is documented as a real user-facing path ("Legacy bridging flow used by Near Intents"), so real users may invoke it. Likelihood is **Low** in a correctly operated deployment but non-negligible during deployment windows or after contract upgrades that reset storage.

---

### Recommendation

Replace the silent fallthrough with an explicit `require!` that reverts the transaction when `withdraw_relayer` is not set:

```rust
fn ft_transfer(&mut self, receiver_id: AccountId, amount: U128, memo: Option<String>) {
    if receiver_id == env::current_account_id()
        && memo.as_ref().is_some_and(|m| m.starts_with(WITHDRAW_MEMO_PREFIX))
    {
        let relayer = Self::read_withdraw_relayer_address()
            .expect("withdraw_relayer not configured");
        return self.token.ft_transfer(relayer, amount, memo);
    }
    self.token.ft_transfer(receiver_id, amount, memo);
}
```

Additionally, add a controller-only rescue function to sweep any tokens accidentally accumulated in the nbtc contract's own balance, analogous to the fix applied in the ImmutableBundle report.

---

### Proof of Concept

1. Deploy the nbtc contract via `new(controller, bridge_id, ...)` **without** calling `set_withdraw_relayer_address`. `read_withdraw_relayer_address()` returns `None`.
2. Any caller registers the nbtc contract as an account in its own ledger: `nbtc.storage_deposit(Some(nbtc_contract_id), Some(true))`.
3. A Near Intents user (or any user following the legacy flow) calls:
   ```
   nbtc.ft_transfer(
       receiver_id = nbtc_contract_id,
       amount     = 1_000_000,
       memo       = Some("WITHDRAW_TO:bc1q...")
   )
   ```
4. Both outer conditions are true; `withdraw_relayer` is `None`; the inner `return` is skipped.
5. `self.token.ft_transfer(nbtc_contract_id, 1_000_000, memo)` executes — tokens move from the user's balance into the nbtc contract's own balance.
6. No `burn`, rescue, or sweep function can reach those tokens. They are permanently locked. Total supply remains unchanged while the user's balance is zeroed. [6](#0-5) [1](#0-0) [7](#0-6)
