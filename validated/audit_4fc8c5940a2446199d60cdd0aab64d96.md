### Title
Peras Quorum Check Compares Absolute Vote Stake Against Relative Threshold Without Unit Normalization - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value (a raw `Rational` that may be an absolute lovelace amount) directly against `perasQuorumStakeThreshold` (hardcoded as the relative fraction `3/4`). The code itself documents this assumption is unverified. If the stake distribution is populated with absolute ledger values — the natural representation from the Cardano ledger — any single vote from any non-zero-stake peer immediately satisfies the quorum check, allowing unauthorized Peras certificate forging and chain boosting.

---

### Finding Description

`stakeAboveThreshold` performs the comparison:

```haskell
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
```

where `quorumThreshold = 3/4` and `safetyMargin = 2/100`, giving a threshold of `0.77`. [1](#0-0) 

The function's own TODO comment explicitly acknowledges the unit assumption is unverified:

> "this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally." [2](#0-1) 

The `PerasVoteStake` type is a bare `Rational` with no invariant enforcing normalization: [3](#0-2) 

A companion comment on the type itself confirms the normalization step is absent:

> "At the moment there is no consensus from researchers/engineers on how we go from the absolute stake of a voter in the ledger to the relative stake of their vote in the voting committee." [4](#0-3) 

`PerasVoteStake` values are sourced from `PerasVoteStakeDistr`, which is provided externally via `getStakeDistrSTM` with no normalization enforced at the call site: [5](#0-4) 

The validated vote stake is accumulated in `updateTargetVoteTally` and then passed directly to `stakeAboveThreshold` via `votesReachQuorum`: [6](#0-5) [7](#0-6) 

---

### Impact Explanation

**Critical — Bypass of Peras quorum/certificate check enabling unauthorized certificate acceptance and chain boosting.**

If `PerasVoteStakeDistr` is populated with absolute lovelace values (the natural representation from the Cardano ledger, e.g., `1_000_000_000` lovelace), then for any voter:

```
1_000_000_000  >=  0.77   →  True
```

A single vote from any non-zero-stake peer immediately satisfies the quorum check. `votesReachQuorum` returns `Just`, `forgePerasCert` is called, and a `ValidatedPerasCert` is produced for the attacker's chosen block. This certificate carries `perasWeight = 15` in chain selection, allowing the attacker to boost an arbitrary block and cause honest nodes to prefer a non-canonical chain. [8](#0-7) 

Conversely, if values are fractional but not normalized to the committee's total stake, quorum may never be reachable, permanently preventing certificate formation and disabling the Peras finality boost.

---

### Likelihood Explanation

**High.** The Cardano ledger natively represents stake in absolute lovelace. The code that supplies `getStakeDistrSTM` has no normalization step, and the TODO comment confirms this is an open, unresolved design gap. Any deployment that wires the ledger's raw stake distribution into `PerasVoteStakeDistr` — the most natural implementation — triggers the bug. The attack requires only a valid vote from any peer with non-zero stake, which is reachable via the ObjectDiffusion mini-protocol without any privileged access. [9](#0-8) 

---

### Recommendation

1. **Enforce normalization at the boundary.** Before inserting values into `PerasVoteStakeDistr`, divide each voter's absolute stake by the total stake of the committee to produce a value in `[0, 1]`. This normalization must happen before `validatePerasVote` assigns the stake to a `ValidatedPerasVote`.

2. **Remove the unit ambiguity from the type.** Introduce a `newtype NormalizedStake = NormalizedStake Rational` with a smart constructor that asserts the value is in `[0, 1]`, and change `PerasVoteStake` to wrap it. This makes the invariant machine-checked.

3. **Update `stakeAboveThreshold`.** Either accept the total stake distribution and perform normalization internally, or add a precondition assertion that `unPerasVoteStake voteStake <= 1`.

4. **Resolve the open design question.** The TODO at line 136 of `SupportsPeras.hs` must be resolved before Peras is activated on any network. The quorum threshold and the vote stake representation must be defined in the same units by specification. [10](#0-9) 

---

### Proof of Concept

**Setup:** Populate `PerasVoteStakeDistr` with a single voter whose `PerasVoteStake` is `1_000_000_000` (one billion lovelace, a plausible absolute stake value).

**Step 1.** A peer sends one `PerasVote` for block `B` in round `R` via the ObjectDiffusion mini-protocol. `processVotes` calls `validatePerasVote mkPerasParams sd vote`. [11](#0-10) 

**Step 2.** `validatePerasVote` looks up the voter's stake (`1_000_000_000`) and returns `Right ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1_000_000_000 }`. [12](#0-11) 

**Step 3.** The vote is added to the aggregation state. `updateCandidateVoteState` calls `votesReachQuorum cfg [vote]`, which calls `stakeAboveThreshold params (PerasVoteStake 1_000_000_000)`. [6](#0-5) 

**Step 4.** `stakeAboveThreshold` evaluates `1_000_000_000 >= 3/4 + 2/100` → `True`. `votesReachQuorum` returns `Just votesWithQuorum`. [1](#0-0) 

**Step 5.** `forgePerasCert` is called and returns a `ValidatedPerasCert` boosting block `B` with weight 15. The attacker has forged a Peras certificate with a single vote, bypassing the intended 3/4-stake quorum requirement. [13](#0-12)
