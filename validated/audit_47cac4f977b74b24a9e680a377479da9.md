Audit Report

## Title
Unconditional State Finalisation Before Confirming Token Transfer Success in Fast Transfer Reimbursement - (File: `near/omni-bridge/src/lib.rs`)

## Summary
In `process_fin_transfer_to_other_chain`, when a fast transfer relayer is owed reimbursement, `send_tokens(...).detach()` fires the token transfer promise with no callback, then `mark_fast_transfer_as_finalised` is called unconditionally. If the token transfer to the relayer fails, the fast transfer is permanently marked as finalised with no revert path, and the relayer's pre-funded tokens are irrecoverably lost. The identical pattern exists in `utxo_fin_transfer_fast`.

## Finding Description
In `process_fin_transfer_to_other_chain` (lines 2027–2040), when a fast transfer was previously performed for a non-NEAR destination transfer, the bridge reimburses the relayer:

```rust
if let Some(relayer) = recipient {
    self.send_tokens(token, relayer, U128(...), "").detach();
    self.mark_fast_transfer_as_finalised(&fast_transfer.id());
}
```

The `.detach()` call registers no callback — the promise result (success or failure) is completely ignored. Immediately after, `mark_fast_transfer_as_finalised` permanently records the fast transfer as done. Prior to this block, `unlock_tokens_if_needed` (line 1997) and `lock_tokens_if_needed` (line 2002) have already mutated `locked_tokens`.

If `send_tokens` fails — for example, `ft_transfer` panics because the relayer account has no storage registered for the token contract, or the token contract itself reverts — all state mutations (`unlock_tokens`, `lock_tokens`, `mark_fast_transfer_as_finalised`) remain committed with no revert path. The fast transfer ID is permanently finalised, so no re-trigger of reimbursement is possible.

The same pattern exists in `utxo_fin_transfer_fast` (lines 2529–2548): `mark_fast_transfer_as_finalised` is called at line 2533 before `send_tokens(...).detach()` at line 2548.

By contrast, the NEAR-destination path correctly uses a callback. In `fast_fin_transfer_to_near_callback` (lines 877–892), `send_tokens` is chained with `.then(Self::ext(...).resolve_fast_transfer(...))`, and `resolve_fast_transfer` (lines 896–912) handles failure by calling `remove_fast_transfer`, allowing retry. No equivalent protection exists for the non-NEAR destination path.

## Impact Explanation
The relayer who performed the fast transfer burned their own tokens on NEAR (via `burn_tokens_if_needed` in `fast_fin_transfer_to_other_chain`) and pre-funded the recipient on the destination chain. The reimbursement in `process_fin_transfer_to_other_chain` is the only mechanism to return those tokens. If `send_tokens` fails silently and `mark_fast_transfer_as_finalised` commits, the relayer's pre-funded tokens are permanently unrecoverable — the fast transfer record is finalised so no retry path exists, and the tokens remain in the bridge with no claimable state. This constitutes permanent loss of bridged funds, matching the Critical impact category: "Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."

## Likelihood Explanation
For non-deployed (native) tokens, `send_tokens` calls `ft_transfer` on the token contract, which requires the recipient (relayer) to have a storage deposit registered. A relayer who performed a fast transfer for a token they have not registered storage for on NEAR will trigger this silently. Additionally, any transient failure in the token contract (panic, out-of-gas in the token's `ft_transfer` handler) produces the same outcome. The entry path is reachable by any trusted relayer performing a fast transfer on a cross-chain (non-NEAR destination) route, and the canonical `fin_transfer` that triggers `process_fin_transfer_to_other_chain` can be submitted by any trusted relayer. The condition is realistic and repeatable.

## Recommendation
Replace `.detach()` in both `process_fin_transfer_to_other_chain` and `utxo_fin_transfer_fast` with a proper callback that checks the transfer result before committing `mark_fast_transfer_as_finalised`. If the token transfer fails, the callback should revert the `locked_tokens` changes using the existing `revert_lock_actions` mechanism and remove or leave the finalised-transfer record uncommitted, allowing the relayer to retry. This mirrors the pattern already used in the NEAR-destination fast transfer path via `resolve_fast_transfer` (lines 896–912).

## Proof of Concept
1. Trusted relayer R performs a fast transfer for a cross-chain transfer T (origin: Eth → destination: Sol) by calling `fast_fin_transfer` on NEAR. The bridge burns R's tokens on NEAR, locks them for Sol, and records `fast_transfers[T.id] = { relayer: R, finalised: false }`.
2. The canonical `fin_transfer` is called (by any trusted relayer) with a valid proof of T, triggering `process_fin_transfer_to_other_chain`.
3. `unlock_tokens_if_needed` decrements `locked_tokens[Eth][token]`; `lock_tokens_if_needed` increments `locked_tokens[Sol][token]` for the fee portion.
4. `send_tokens(token, R, amount_without_fee, "").detach()` fires an `ft_transfer` to R. R's account has no storage deposit for `token` on NEAR, so the `ft_transfer` panics inside the token contract. The promise fails silently — no callback observes this.
5. `mark_fast_transfer_as_finalised` is called unconditionally, setting `fast_transfers[T.id].finalised = true`.
6. R never receives their reimbursement. The tokens remain in the bridge with no claimable path. The `locked_tokens` accounting is permanently skewed with no revert.

To reproduce: deploy the bridge on a local NEAR testnet, register a trusted relayer R without storage deposit for the token, execute steps 1–5 above, and verify that `fast_transfers[T.id].finalised == true` while R's token balance is unchanged.
