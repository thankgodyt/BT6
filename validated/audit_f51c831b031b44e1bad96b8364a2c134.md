### Title
Missing Chain-ID Binding in `deploy_token` Signed Message Enables Cross-Chain Replay — (Files: `starknet/src/bridge_types.cairo`, `solana/programs/bridge_token_factory/src/state/message/deploy_token.rs`)

---

### Summary

The `MetadataPayload` Borsh encoding used to authorize `deploy_token` on both Starknet and Solana omits any chain identifier. A valid NEAR MPC signature authorizing token deployment on one chain can be replayed verbatim on another chain, deploying the token without NEAR's per-chain authorization. This is a concrete chain/domain-separation flaw: the same signed bytes are accepted by every bridge instance that shares the same `nearBridgeDerivedAddress`.

---

### Finding Description

`fin_transfer` / `finalize_transfer` signed messages include the destination chain ID, preventing cross-chain replay. `deploy_token` / `MetadataPayload` signed messages do not.

**Starknet — `MetadataPayload::to_borsh()` (no chain_id argument, no chain_id in output):** [1](#0-0) 

The serialized bytes are exactly: `[0x01 (PayloadType::Metadata), token, name, symbol, decimals]`. No chain identifier is appended.

**Contrast with `TransferMessagePayload::to_borsh(chain_id)`**, which receives and embeds `chain_id` twice: [2](#0-1) 

**Starknet call-site asymmetry** — `deploy_token` passes no chain_id; `fin_transfer` does: [3](#0-2) [4](#0-3) 

**Solana — `DeployTokenPayload::serialize_for_near()` (no `SOLANA_OMNI_BRIDGE_CHAIN_ID`):** [5](#0-4) 

**Contrast with `FinalizeTransferPayload::serialize_for_near()`**, which writes `SOLANA_OMNI_BRIDGE_CHAIN_ID` at positions 3 and 5: [6](#0-5) 

The Starknet CLAUDE.md explicitly documents chain-ID binding only for `fin_transfer`, confirming the omission for `deploy_token` is unintentional: [7](#0-6) 

Because all bridge instances share the same `nearBridgeDerivedAddress` / `derived_near_bridge_address`, the signature verification in `_verify_borsh_signature` (Starknet) and `SignedPayload::verify_signature` (Solana) will accept a `deploy_token` signature produced for chain A when submitted to chain B: [8](#0-7) [9](#0-8) 

---

### Impact Explanation

An attacker who observes a valid `deploy_token` transaction on chain A (public blockchain data) can submit the identical `(signature, MetadataPayload)` to chain B's bridge contract. The bridge on chain B:

1. Verifies the signature — **passes**, because the signed bytes are chain-agnostic.
2. Checks `ERR_TOKEN_ALREADY_DEPLOYED` — **passes** if the token has not yet been deployed on chain B.
3. Deploys the bridge token contract and registers it in `near_to_starknet_token` / `starknet_to_near_token` mappings.

Consequences:
- The token is now registered in chain B's bridge mappings as a valid bridge token, making it eligible for `fin_transfer` minting on chain B.
- Legitimate future deployment of the same token on chain B is permanently blocked (`ERR_TOKEN_ALREADY_DEPLOYED`).
- If NEAR's backend monitors `DeployToken` events to determine which tokens are authorized on which chains, it may subsequently sign `fin_transfer` for this token on chain B, enabling unauthorized minting of bridged assets on chain B without a corresponding lock/burn on the origin chain.

The third consequence — unauthorized minting — maps directly to the allowed critical impact scope: *unauthorized minting of bridged funds* and *chain/domain separation flaw enabling invalid finalization*.

---

### Likelihood Explanation

The attack requires zero privileged access:
- The attacker only needs to observe a `deploy_token` transaction on any supported chain (all data is public on-chain).
- The attacker submits the same `(signature, payload)` to another chain's bridge contract.
- No key material, admin role, or off-chain coordination is needed.

The precondition (a `deploy_token` signature existing for at least one chain) is met every time a new token is bridged for the first time. This is a routine bridge operation.

---

### Recommendation

Include the destination chain ID in the `MetadataPayload` Borsh encoding, mirroring the pattern already used for `TransferMessagePayload`.

- **Starknet**: Change `MetadataPayload::to_borsh()` to accept a `chain_id: u8` parameter and append it after the `PayloadType::Metadata` byte (or at a fixed position). Update the `deploy_token` call-site to pass `self.omni_bridge_chain_id.read()`.
- **Solana**: In `DeployTokenPayload::serialize_for_near()`, write `SOLANA_OMNI_BRIDGE_CHAIN_ID` into the serialized buffer at a fixed position (e.g., after the `IncomingMessageType::Metadata` prefix), matching the pattern used in `FinalizeTransferPayload::serialize_for_near()`.
- **EVM**: Verify that the EVM `deployToken` Borsh encoding similarly includes `omniBridgeChainId`; apply the same fix if absent.

---

### Proof of Concept

1. NEAR backend signs `MetadataPayload { token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6 }` to authorize deployment on Solana. Signed bytes: `[0x01, "usdc.near", "USD Coin", "USDC", 6]`.
2. Attacker observes the Solana `deploy_token` transaction and extracts `(signature, payload)`.
3. Attacker calls `deploy_token(signature, MetadataPayload { token: "usdc.near", name: "USD Coin", symbol: "USDC", decimals: 6 })` on the Starknet bridge.
4. Starknet's `_verify_borsh_signature` hashes the identical Borsh bytes and recovers the same `nearBridgeDerivedAddress` — **signature accepted**.
5. `ERR_TOKEN_ALREADY_DEPLOYED` check passes (token not yet on Starknet).
6. "usdc.near" bridge token is deployed on Starknet and registered in the bridge mappings.
7. Legitimate NEAR-authorized deployment of "usdc.near" on Starknet is now permanently blocked.
8. If NEAR's backend treats the emitted `DeployToken` event as proof of authorized deployment, it will sign `fin_transfer` for "usdc.near" on Starknet, minting tokens to any recipient the attacker specifies in a subsequent `fin_transfer` call — without a corresponding lock on the origin chain.

```rust
impl<P: Payload> SignedPayload<P> {
    pub fn verify_signature(
        &self,
        params: P::AdditionalParams,
        derived_near_bridge_address: &[u8; 64],
    ) -> Result<()> {
        let serialized = self.payload.serialize_for_near(params)?;
        let hash = keccak::hash(&serialized);

        let signature_bytes = &self.signature[0..64];

        let signature = libsecp256k1::Signature::parse_standard_slice(signature_bytes)
            .map_err(|_| ProgramError::InvalidArgument)?;
        require!(!signature.s.is_high(), ErrorCode::MalleableSignature);

        let signer = secp256k1_recover(&hash.to_bytes(), self.signature[64], signature_bytes)
            .map_err(|_| error!(ErrorCode::SignatureVerificationFailed))?;

        require!(
            signer.0 == *derived_near_bridge_address,
            ErrorCode::SignatureVerificationFailed
        );

        Ok(())
    }
```
