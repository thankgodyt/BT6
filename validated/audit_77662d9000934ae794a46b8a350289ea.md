### Title
Sapling-only Unified Address with Orchard Bundle Triggers Unhandled Panic in `validate_orchard_bundle` — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

---

### Summary

An unprivileged user can supply a valid Orchard bundle paired with a Sapling-only Unified Address (no Orchard receiver) as `target_btc_address`. The bridge parses the UA successfully, then calls `extract_orchard_receiver`, which returns `Err("Unified address missing Orchard receiver")`. That error propagates through `validate_orchard_bundle` and is caught by an `.unwrap_or_else(|_| env::panic_str(...))` in `PsbtWrapper::validate_orchard_bundle`, causing a NEAR panic. The panic reverts all state changes and the user's nZEC tokens are returned via the NEP-141 refund mechanism, but the withdrawal fails with a raw panic string rather than a clean contract error.

---

### Finding Description

**Step 1 — Public entry point.**
`ft_transfer_call` (NEP-141) is callable by any user. It invokes `ft_on_transfer`, which dispatches to `ft_on_transfer_withdraw_chain_specific`, scheduling `ft_on_transfer_callback` as a cross-contract callback. [1](#0-0) 

**Step 2 — PSBT construction.**
Inside `ft_on_transfer_callback`, `PsbtWrapper::new` is called with the user-supplied `orchard_bundle` bytes and `target_btc_address`. `extract_orchard_bundle` succeeds because the bundle itself is structurally valid. [2](#0-1) 

**Step 3 — Chain-specific validation.**
`check_psbt_chain_specific` is called (from `check_withdraw_psbt` → `check_withdraw_psbt_valid`). When `psbt.has_orchard_bundle()` is true, it unconditionally calls `psbt.validate_orchard_bundle(target_btc_address, chain)`. [3](#0-2) 

**Step 4 — Address parsed successfully, receiver extraction fails.**
`orchard_policy::validate_orchard_bundle` calls `Address::parse(expected_recipient, chain)`, which succeeds for any well-formed Zcash UA (including Sapling-only). It then calls `recipient_address.extract_orchard_receiver()?`. [4](#0-3) 

`extract_orchard_receiver` iterates the UA's receiver list. For a Sapling-only UA it finds no `Receiver::Orchard` entry and returns `Err("Unified address missing Orchard receiver")`. [5](#0-4) 

**Step 5 — Error converted to panic.**
The `?` propagates the `Err` out of `validate_orchard_bundle`. Back in `PsbtWrapper::validate_orchard_bundle`, the result is consumed by `.unwrap_or_else(|_| env::panic_str("ERR_ORCHARD_VALIDATION: Orchard bundle validation failed"))`. [6](#0-5) 

The same panic path is also reachable through the refund execution flow (`execute_refund_callback` → `check_psbt_chain_specific`). [7](#0-6) 

---

### Impact Explanation

The NEAR runtime reverts all state changes on panic, so no UTXO state is permanently corrupted and the user's nZEC tokens are returned by the NEP-141 `ft_transfer_call` refund mechanism. The impact is therefore limited to:

- A panic-driven rejection instead of a clean contract error, violating the bridge's own error-handling contract.
- Any gas consumed by the failed callback is lost.
- The combination of a Sapling-only UA + Orchard bundle is permanently unserviceable without a contract upgrade.

No funds are stolen or permanently locked. This matches the **Low** impact tier: publicly reachable panic-driven fault in production bridge/token paths without direct theft.

---

### Likelihood Explanation

The precondition is trivially constructable: any Zcash wallet can produce a Sapling-only UA (omitting the Orchard diversifier), and a valid Orchard bundle can be crafted independently. No privileged role is required. The path is reachable on every call to `ft_transfer_call` that supplies this combination.

---

### Recommendation

Add an explicit guard in `check_psbt_chain_specific` (or at the top of `orchard_policy::validate_orchard_bundle`) that checks whether the parsed address actually contains an Orchard receiver before proceeding, and returns a descriptive `require!` / `Err` rather than allowing the panic to propagate. Alternatively, change `PsbtWrapper::validate_orchard_bundle` to return `Result<(), String>` and surface the error as a `require!` failure so the rejection is clean and auditable.

    pub fn extract_orchard_receiver(&self) -> Result<OrchardRawAddress, String> {
        match self {
            Address::Unified { address, .. } => {
                let receiver_list = address.items_as_parsed();
                for receiver in receiver_list {
                    match receiver {
                        Receiver::Orchard(bytes) => return Ok(*bytes),
                        _ => continue,
                    }
                }

                Err("Unified address missing Orchard receiver".to_string())
            }
            _ => Err("No Orchard address found".to_string()),
        }
    }
