### Title
Unprivileged NEAR Account Can Submit `request_refund` With Attacker-Controlled `refund_address`, Enabling BTC Theft - (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary

Any unprivileged NEAR account can call `request_refund` for any victim's deposit UTXO and supply an arbitrary attacker-controlled `refund_address` when the original `deposit_msg.refund_address` is `None`. After the `unsafe_refund_timelock_sec` elapses without DAO/Operator rejection, the attacker can call `execute_refund` to redirect the victim's BTC to their own Bitcoin address.

### Finding Description

`request_refund` is a publicly callable function — it carries no `#[trusted_relayer]` guard on the function itself and no caller-identity check against `deposit_msg.recipient_id`. [1](#0-0) 

The function is placed inside a `#[trusted_relayer] #[near] impl Contract` block, but that block-level attribute only generates relayer-management helpers; individual methods require their own `#[trusted_relayer]` decorator to be gated. Functions like `verify_deposit`, `verify_withdraw`, and `verify_refund_finalize` carry the per-function decorator; `request_refund`, `reject_refund`, and `execute_refund` do not. [2](#0-1) 

Inside `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [3](#0-2) 

When `deposit_msg.refund_address` is `None` (the common case for standard deposits), **any caller may supply any Bitcoin address as `refund_address`**. The callback only verifies that the BTC transaction output matches the deposit address derived from `deposit_msg`; it never checks that the caller is the `deposit_msg.recipient_id` or any authorized party. [4](#0-3) 

The stored `RefundRequest.refund_address` is later used verbatim in `execute_refund` → `build_refund_output` to construct the Bitcoin output paying the refund: [5](#0-4) 

The only protection is `unsafe_refund_timelock_sec` — a longer timelock applied when `deposit_msg.refund_address` is `None` — which gives DAO/Operator time to call `reject_refund`. If the DAO does not act within that window, `execute_refund` is open to anyone: [6](#0-5) 

### Impact Explanation

If the DAO/Operator fails to reject the malicious refund request within `unsafe_refund_timelock_sec`:

1. The attacker calls `execute_refund`, which marks the UTXO in `verified_deposit_utxo` (blocking any subsequent `verify_deposit`) and builds a Bitcoin PSBT paying the attacker's address.
2. The MPC signs the transaction via `sign_btc_transaction`.
3. The attacker broadcasts the signed transaction, receiving the victim's BTC.
4. The victim's BTC is permanently lost; no nBTC is minted.

This is a **Critical** impact: significant theft of user BTC funds with no on-chain recovery path once the refund transaction is confirmed. [7](#0-6) 

### Likelihood Explanation

The attack is straightforward:

- `deposit_msg` is public — emitted as a NEAR event by `get_user_deposit_address`.
- The BTC transaction bytes and Merkle proof are public on the Bitcoin blockchain.
- The attacker only needs to pay the NEAR storage deposit for `request_refund` (a small, fixed amount).
- The attack window is the entire `unsafe_refund_timelock_sec` period. If the DAO is offline, slow, or overwhelmed with requests, the attack succeeds.

The analog to the PythPriceFeedUpdate report is direct: just as any external actor could submit price-feed messages that should only come from the oracle thread, any external actor here can submit refund requests that should only come from the deposit owner, manipulating bridge state to redirect funds.

### Recommendation

Add a caller-identity check in `request_refund` (or `internal_request_refund`) when `deposit_msg.refund_address` is `None`:

```rust
// When no refund_address is pre-authorized in deposit_msg,
// only the deposit recipient may supply one.
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may specify a refund_address"
    );
}
```

Alternatively, disallow `request_refund` entirely when `deposit_msg.refund_address` is `None` and require users to always pre-authorize a refund address at deposit time.

### Proof of Concept

1. Victim calls `get_user_deposit_address(DepositMsg { recipient_id: victim.near, refund_address: None, ... })` — the `deposit_msg` is emitted as a NEAR event.
2. Victim sends 1 BTC to the returned deposit address; the transaction is confirmed on Bitcoin.
3. Attacker observes the NEAR event (gets `deposit_msg`) and the Bitcoin transaction (gets `tx_bytes`, `vout`, Merkle proof).
4. Attacker calls:
   ```
   request_refund(
       deposit_msg,          // victim's deposit_msg with refund_address: None
       "attacker_btc_addr",  // attacker's Bitcoin address
       tx_bytes,
       vout,
       proof,
       None
   )
   ```
   with sufficient NEAR attached. Light Client verifies the transaction; `RefundRequest` is stored with `refund_address = "attacker_btc_addr"`.
5. Attacker waits for `unsafe_refund_timelock_sec` without DAO intervention.
6. Attacker calls `execute_refund(utxo_storage_key, None)`. The PSBT is built paying `"attacker_btc_addr"`.
7. Attacker calls `sign_btc_transaction` to obtain the MPC signature, broadcasts the transaction, and receives the victim's 1 BTC.
8. `verified_deposit_utxo` now contains the UTXO key, permanently blocking `verify_deposit` — no nBTC is ever minted for the victim.

    }

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
