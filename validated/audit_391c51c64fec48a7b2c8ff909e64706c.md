### Title
Peras Weight Boosts Omitted from `checkPreferTheirsOverOurs` Chain Preference Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` function in the ChainSync client evaluates whether a candidate chain is preferable to the node's current chain when a header is beyond the forecast horizon. It calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the live Peras weight snapshot. This omits all Peras certificate weight boosts from the comparison, exactly mirroring the external report's pattern of an incomplete asset tally driving a critical security decision.

---

### Finding Description

In `checkPreferTheirsOverOurs`, the preference check is:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always zero weight boosts
        ourFrag
        theirFrag =
    pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` has two code paths: when `isEmptyPerasWeightSnapshot weights` is true it compares only raw `selectView` (block number + tiebreaker at the tip), and when weights are non-empty it computes `weightedSelectView` over the suffix from the intersection, which adds Peras certificate boosts to the comparison. [2](#0-1) 

By passing `emptyPerasWeightSnapshot`, the function always takes the raw-block-count-only path, ignoring all Peras weight boosts. The live snapshot is available in the same STM context via `getPerasWeightSnapshot` and is correctly used everywhere else in chain selection: [3](#0-2) 

`totalWeightOfFragment` is defined as `weightLength <> weightBoost` — the boost component is entirely absent from `checkPreferTheirsOverOurs`. [4](#0-3) 

---

### Impact Explanation

`checkPreferTheirsOverOurs` is invoked when a received header is beyond the forecast horizon. If the check concludes the candidate is not preferable, the node throws `CandidateTooSparse` and disconnects from that peer. Because Peras weight boosts are excluded, a candidate chain that is genuinely heavier (more total weight = raw blocks + Peras certificate boosts) but shorter in raw block count than the node's current chain will be incorrectly judged as not preferable. The node disconnects from the honest peer offering the canonical Peras-boosted chain and retains its current, lighter chain. If all honest peers offering the canonical chain are disconnected this way, the node is left on a non-canonical, less-secure chain — a chain selection safety failure.

This matches the **High** impact category: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

---

### Likelihood Explanation

The condition is reachable whenever:
1. Peras is active (certificates are being issued and boosting blocks).
2. The canonical chain has at least one Peras-boosted block that makes its total weight exceed the node's current chain, but its raw block count does not.
3. A header on that canonical chain arrives beyond the current forecast horizon (a normal occurrence during syncing or after a slot gap).

All three conditions are expected to occur in normal Peras operation. The code path is exercised by any peer sending headers beyond the forecast horizon, requiring no special privileges. The developers have already flagged this with a `TODO` comment referencing issue `cardano-peras#64`, confirming awareness of the incomplete accounting. [5](#0-4) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live Peras weight snapshot. The snapshot is already available as an STM-readable value via `getPerasWeightSnapshot` on the `ChainDbView`, the same way it is read in `chainSelectionForBlock`. The function should read the snapshot atomically (it already runs in STM) and pass it to `preferAnchoredCandidate`, making the preference check consistent with the rest of chain selection.

---

### Proof of Concept

**Setup**: Peras is active. The node's current chain `C_ours` has 10 raw blocks, no Peras boosts → total weight 10. An honest peer offers chain `C_theirs` with 9 raw blocks but one block boosted by a Peras certificate of weight 5 → total weight 14. A header in `C_theirs` is beyond the forecast horizon.

**Trigger**: The ChainSync client calls `checkPreferTheirsOverOurs`. It calls `preferAnchoredCandidate` with `emptyPerasWeightSnapshot`. The comparison reduces to raw block count: `C_ours` has 10 blocks, `C_theirs` has 9 → `ShouldNotSwitch`. The node throws `CandidateTooSparse` and disconnects.

**Result**: The node stays on `C_ours` (total weight 10) and disconnects from the honest peer offering `C_theirs` (total weight 14). The node is now on the non-canonical, lighter chain. The canonical chain is not adopted because the Peras weight boost — the exact component that makes `C_theirs` the correct chain — was excluded from the tally, directly mirroring the external report's omission of fees from the asset tally.

      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of

              ShouldNotSwitch o -> ShouldNotSwitch o
