Audit Report

## Title
Decimal Normalization Dust Permanently Locked When Fee Is Zero - (File: `near/omni-bridge/src/lib.rs`)

## Summary
When a user initiates an outbound transfer with `fee = 0`, the sub-unit remainder ("dust") produced by `normalize_amount`'s floor division is permanently locked in the bridge contract. Because `sign_transfer_callback` removes the transfer message immediately when the fee is zero, `claim_fee` can never be called for that transfer, leaving the dust with no recovery path.

## Finding Description
**Root cause — `normalize_amount` truncates via floor division:** [1](#0-0) 

The bridge locks the user's full amount in `init_transfer_internal`: [2](#0-1) 

`sign_transfer` normalizes the amount sent to the destination chain: [3](#0-2) 

**Critical branch — transfer message deleted when fee is zero:** [4](#0-3) 

Once the transfer message is deleted, `claim_fee` (the only mechanism that disburses dust) cannot be called — it calls `remove_transfer_message` internally and would panic on a missing key. Even if it could be called, `claim_fee` is `#[trusted_relayer]`-gated with no economic incentive for a relayer to submit a proof for a zero-fee transfer: [5](#0-4) 

**How `claim_fee_callback` captures dust (only reachable when fee > 0):** [6](#0-5) 

`send_fee_internal` is a no-op when `token_fee == 0`, so even if `claim_fee` were somehow called with zero computed fee, nothing would be disbursed: [7](#0-6) 

The code's own doc-comment on `normalize_amount` acknowledges the outcome: *"When fee = 0, dust stays locked/burned."* The referenced `SECURITY.md` contains only a generic exclusion list and does not address this scenario. [8](#0-7) 

## Impact Explanation
Every outbound transfer where `fee = 0` and `origin_decimals > decimals` results in permanent freezing of up to `10^diff_decimals − 1` of the user's tokens in the bridge escrow. The locked tokens are not burned (on-chain supply is preserved on NEAR) but are inaccessible to the user or any other party. This directly matches the allowed Critical impact: **permanent freezing of bridged funds** and **decimal/normalization abuse that changes user or protocol balances**.

## Likelihood Explanation
Any unprivileged user can trigger this by calling `ft_on_transfer` with an `InitTransfer` message specifying `fee = 0` and an amount that is not an exact multiple of `10^diff_decimals`. Zero-fee transfers are explicitly supported by the protocol. The condition `origin_decimals > decimals` is the normal case for tokens normalized to lower precision on NEAR. No special role, timing, or external condition is required.

## Recommendation
- **Refund dust to sender**: After `normalize_amount`, compute `dust = amount % 10^diff_decimals` and return it to the sender before locking the normalized amount.
- **Alternatively, enforce representable amounts**: Require `amount % 10^diff_decimals == 0` in `init_transfer`, rejecting non-representable amounts with a clear error.
- **At minimum**: Remove the misleading `SECURITY.md` reference from the `normalize_amount` doc-comment and add an explicit on-chain check or refund.

## Proof of Concept
1. Register a token with `origin_decimals = 18`, `decimals = 6` (`diff_decimals = 12`).
2. User calls `ft_on_transfer` (NEAR → Ethereum) with `amount = 1_000_000_999_999_999_999` and `fee = 0`.
3. `init_transfer_internal` locks `1_000_000_999_999_999_999` units from the user.
4. Relayer calls `sign_transfer`; `normalize_amount` computes `1_000_000_999_999_999_999 / 10^12 = 1_000_000`; Ethereum receives `1_000_000` normalized units.
5. `sign_transfer_callback` sees `fee.is_zero() == true` and calls `remove_transfer_message`, deleting the pending transfer record.
6. `999_999_999_999` origin-token units (`~0.000001` tokens at 18-decimal precision, scaling to up to `10^18 − 1` for diff=18) remain locked in the bridge contract permanently with no callable recovery path.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
