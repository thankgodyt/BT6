### Title
Unconditional `validatePerasCert` Stub Enables Unauthenticated Peras Certificate Injection and Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `validatePerasCert` unconditionally returns `Right` for every inbound certificate, performing no cryptographic or semantic checks. Combined with first-writer-wins semantics in `implAddCert` (keyed on `PerasRoundNo`), an unprivileged peer can inject a crafted certificate for any Peras round, pre-empting the legitimate certificate for that round. The injected certificate is then used by chain selection to boost an attacker-controlled block, causing honest nodes to prefer a non-canonical chain.

---

### Finding Description

**Root cause 1 — validation stub always accepts:**

`validatePerasCert` in the only production `BlockSupportsPeras` instance unconditionally wraps every inbound certificate in `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the only `BlockSupportsPeras` instance in the codebase. No signature, quorum proof, committee membership, or round-number plausibility check is performed. Any peer-supplied `PerasCert` is unconditionally promoted to `ValidatedPerasCert`.

**Root cause 2 — non-atomic check-then-act in `processCerts`:**

`processCerts` reads the set of already-known round numbers in one `atomically` block, then validates and adds certificates in separate, non-atomic steps:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM          -- (1) snapshot
  let certsNotAlreadyInDb =
        filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  ...
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) ->
      mapM_ (addCert . WithArrivalTime now) validatedCerts  -- (2) add
``` [2](#0-1) 

Between steps (1) and (2), another peer's certificate for the same round can be inserted, but the filter at step (1) already passed. Both certificates then reach `addCert`.

**Root cause 3 — first-writer-wins in `implAddCert`:**

`implAddCert` stores the first certificate seen for a given `PerasRoundNo` and silently drops all subsequent ones:

```haskell
if Set.member roundNo (pcdsCertIds pcds)
  then pure PerasCertAlreadyInDB
  else do
    ...
    writeTVar pcdbState ...
    pure AddedPerasCertToDB
``` [3](#0-2) 

The `AddPerasCertPromise` comment in the ChainDB API explicitly assumes "the two certificates must be identical because certificate equivocation is impossible," but this invariant is never enforced: [4](#0-3) 

**End-to-end exploit path:**

1. Attacker connects as an unprivileged peer via the ObjectDiffusion mini-protocol.
2. Attacker sends a `PerasCert` for round R with `pcCertBoostedBlock = B_attacker` (any block hash the attacker controls or wishes to boost).
3. `processCerts` calls `validatePerasCert`, which returns `Right` unconditionally.
4. `implAddCert` stores the attacker's cert; `pcdsCertIds` now contains round R.
5. The legitimate cert for round R (boosting `B_legitimate`) arrives from an honest peer. `implAddCert` finds round R already present and returns `PerasCertAlreadyInDB`; the legitimate cert is silently discarded.
6. `chainSelSync` uses the stored cert to trigger `chainSelectionForBlock` for `B_attacker`: [5](#0-4) 

7. The Peras weight snapshot used for chain selection now reflects the boost for `B_attacker` instead of `B_legitimate`, causing honest nodes to prefer the attacker-boosted chain.

---

### Impact Explanation

**Severity: Critical / High.**

- **Peras certificate verification bypass (Critical):** The `validatePerasCert` stub unconditionally accepts every inbound certificate, completely bypassing the Peras voting/certificate check. This satisfies the "Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance" criterion.
- **Chain-selection manipulation (High):** By injecting a certificate for a given round before the legitimate one arrives, an attacker causes honest nodes to apply a Peras boost to an attacker-chosen block. This can make an honest node prefer a non-canonical or adversarially-selected chain, violating the Peras security assumption that only legitimately quorum-certified blocks receive a boost.

The `getLatestCertSeen` field is also affected: it gates whether a node is eligible to vote in subsequent rounds, so injecting a cert for a high round number can additionally suppress legitimate voting. [6](#0-5) 

---

### Likelihood Explanation

**High.** The ObjectDiffusion inbound handler is reachable by any peer that connects to the node. No stake, key material, or special privilege is required. The attacker only needs to send a well-formed `PerasCert` CBOR message (round number + block point) before the legitimate certificate for that round is received. Because `validatePerasCert` never rejects, there is no barrier to exploitation. The TOCTOU window in `processCerts` further widens the race surface.

---

### Recommendation

1. **Implement real validation in `validatePerasCert`:** Verify the certificate's aggregate BLS/committee signature, confirm the round number is plausible relative to the current chain tip, and check that the boosted block point is a known, valid block. Remove the unconditional `Right` stub before any production deployment of Peras.

2. **Enforce equivocation rejection at the DB layer:** `implAddCert` should compare the `pcCertBoostedBlock` of an incoming cert against the stored cert for the same round and reject (or disconnect the peer) if they differ, rather than silently dropping the second cert.

3. **Make `processCerts` atomic:** Merge the `alreadyInDb` snapshot and the `addCert` call into a single STM transaction to eliminate the TOCTOU window.

---

### Proof of Concept

**Setup:** Node N is running with the ObjectDiffusion mini-protocol active. Legitimate cert `C_legit = PerasCert { pcCertRound = 42, pcCertBoostedBlock = B_legit }` is in transit from an honest peer.

**Attacker steps:**

```
-- Attacker constructs a crafted cert for round 42 boosting their own block
let craftedCert = PerasCert { pcCertRound = 42, pcCertBoostedBlock = B_attacker }

-- Attacker sends it via ObjectDiffusion before C_legit arrives
sendObjectDiffusionBatch peer [craftedCert]
```

**Node processing:**

```haskell
-- processCerts: alreadyInDb does not contain round 42 yet
certsNotAlreadyInDb = [craftedCert]   -- passes filter

-- validatePerasCert: unconditionally accepts
validatePerasCert params craftedCert = Right (ValidatedPerasCert { vpcCert = craftedCert, ... })

-- implAddCert: round 42 not in pcdsCertIds → stored
pcdsCertIds' = Set.insert 42 pcdsCertIds   -- attacker's cert wins
```

**Legitimate cert arrives:**

```haskell
-- implAddCert: round 42 already in pcdsCertIds → silently dropped
Set.member 42 pcdsCertIds  -- True → PerasCertAlreadyInDB
```

**Chain selection outcome:**

```haskell
-- chainSelSync uses attacker's cert to boost B_attacker
chainSelectionForBlock cdb BlockCache.empty hdr_B_attacker noPunishment
-- Node now prefers the chain containing B_attacker over B_legit
```

The node's chain selection is permanently skewed toward `B_attacker` for round 42, with no way to correct it short of a restart (since `implAddCert` will continue to return `PerasCertAlreadyInDB` for any subsequent legitimate cert for round 42).
