### Title
Unauthenticated Peras Vote Submission Allows Any Peer to Forge Votes on Behalf of Legitimate Validators - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasVote` function in the production `BlockSupportsPeras` instance accepts inbound Peras votes from any peer without verifying any cryptographic proof of identity. The `PerasVote` data type carries no signature field, and the validation logic only checks whether the claimed `PerasVoterId` exists in the stake distribution. Any unprivileged peer can craft a `PerasVote` claiming to be from any legitimate validator and have it accepted, accumulate stake weight, and potentially trigger certificate generation for an attacker-chosen block.

---

### Finding Description

The `PerasVote` data type is defined without a signature field:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [1](#0-0) 

The production `BlockSupportsPeras` instance's `validatePerasVote` implementation only checks whether the claimed voter ID is present in the stake distribution map:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [2](#0-1) 

`lookupPerasVoteStake` performs only a `Map.lookup` on `pvVoteVoterId`: [3](#0-2) 

There is no check that the sender of the vote is actually the key-holder for the claimed `PerasVoterId`. The production inbound path in `processVotes` calls this validation and, on success, adds the vote to the `PerasVoteDB` with the legitimate validator's full stake weight: [4](#0-3) 

Once enough stake-weighted votes accumulate for a given block target, `updateCandidateVoteState` forges a `ValidatedPerasCert` for that block, which is then used in chain selection to boost that block's preference. [5](#0-4) 

---

### Impact Explanation

**High — Chain selection manipulation via unauthorized Peras certificate generation.**

An attacker who can connect as a peer can submit crafted `PerasVote` messages claiming to be from any set of legitimate validators (whose `PerasVoterId` values are public, derived from public keys). By impersonating enough validators to exceed the quorum threshold, the attacker causes the victim node to forge a `ValidatedPerasCert` for an attacker-chosen block. This certificate boosts that block's weight in chain selection, causing the honest node to prefer a non-canonical or attacker-controlled chain over the legitimate chain — a chain-selection bug that lets an unprivileged peer make an honest node prefer a less-secure chain beyond the intended security assumptions.

---

### Likelihood Explanation

**High.** The object diffusion mini-protocol is reachable by any peer that can establish a connection. The `PerasVoterId` values are derived from public stake pool keys, which are publicly known on-chain. No key material, admin access, or stake majority is required. The attacker only needs to know the voter IDs of validators with sufficient combined stake to exceed the quorum threshold, then send crafted `PerasVote` messages with those IDs pointing to their preferred block.

---

### Recommendation

1. Add a cryptographic signature field to `PerasVote` (analogous to how `EveryoneVotes` and `WFALS` committee votes carry a `VoteSignature`).
2. Implement signature verification inside `validatePerasVote` — verify that the vote was signed by the private key corresponding to the claimed `PerasVoterId`'s public key before accepting it.
3. Until the full committee selection context is available (as noted in the TODO at issue #120), at minimum reject votes that carry no verifiable proof of identity rather than accepting them based solely on stake-distribution membership.

---

### Proof of Concept

1. Attacker connects to a victim node as a peer via the object diffusion mini-protocol.
2. Attacker reads the public `PerasVoteStakeDistr` (voter IDs and their stakes are derived from public on-chain data).
3. Attacker selects a set of `PerasVoterId` values whose combined `PerasVoteStake` exceeds the quorum threshold (`perasQuorumStakeThreshold + perasQuorumStakeThresholdSafetyMargin`).
4. Attacker crafts `PerasVote { pvVoteRound = r, pvVoteBlock = attackerBlock, pvVoteVoterId = legitimateVoterId }` for each selected voter ID, all pointing to `attackerBlock`.
5. Attacker sends these votes to the victim node via `opwAddObjects`.
6. `processVotes` calls `validatePerasVote` for each vote; each passes because `lookupPerasVoteStake` finds the voter ID in the distribution.
7. Each vote is added to `PerasVoteDB` via `implAddVote`; `updatePerasRoundVoteStates` accumulates stake.
8. Once quorum is reached, `updateCandidateVoteState` calls `forgePerasCert`, producing a `ValidatedPerasCert` for `attackerBlock`.
9. The victim node's chain selection now treats `attackerBlock` as Peras-boosted, preferring it over the honest canonical chain. [6](#0-5) [7](#0-6)

processVotes ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set (PerasVoteId blk)) ->
  (PerasVote blk -> STM m (Either (PerasValidationErr blk) (ValidatedPerasVote blk))) ->
  (WithArrivalTime (ValidatedPerasVote blk) -> m ()) ->
  [PerasVote blk] ->
  m ()
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
