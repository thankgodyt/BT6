### Title
Peras Weight Ignored in ChainSync Forecast-Horizon Disconnection Check Causes Canonical Chain Abandonment - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

`checkPreferTheirsOverOurs` in the ChainSync client evaluates whether a peer's candidate chain is preferable using `emptyPerasWeightSnapshot`, completely ignoring Peras weight boosts. The actual chain selection in `ChainSel.hs` uses the real `PerasWeightSnapshot`. This accounting mismatch — one type of chain weight (block count) is tracked, another (Peras boost) is silently zeroed — causes a node to disconnect from peers offering the canonical Peras-heavier chain when a header falls beyond the forecast horizon, leaving the node on a lighter, non-canonical chain.

---

### Finding Description

When a header arrives beyond the forecast horizon, `readLedgerStateHelper` calls `checkPreferTheirsOverOurs` before retrying:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
``` [1](#0-0) 

`checkPreferTheirsOverOurs` calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot`:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [2](#0-1) 

`preferAnchoredCandidate` has two branches: when `isEmptyPerasWeightSnapshot weights` is true it falls back to pure `BlockNo` comparison; when false it computes `weightedSelectView` over the suffix after the intersection, summing block count and Peras boosts:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      ...
      case preferCandidate ... (selectView cfg ...) (selectView cfg ...) of ...
  | otherwise =
      case AF.intersect ours cand of
        ...
        Just (_,_,oursSuffix,candSuffix) ->
          case preferCandidate ... (weightedSelectView cfg weights oursSuffix)
                                   (weightedSelectView cfg weights candSuffix) of ...
``` [3](#0-2) 

`wsvTotalWeight` is defined as `BlockNo + PerasWeightBoost`:

```haskell
wsvTotalWeight wsv =
  PerasWeight (unBlockNo (wsvBlockNo wsv)) <> wsvWeightBoost wsv
``` [4](#0-3) 

By contrast, the actual chain selection in `constructPreferableCandidates` passes the real `weights` snapshot:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [5](#0-4) 

The two code paths therefore use **different accounting**: `ChainSel` counts `BlockNo + PerasBoost`; `checkPreferTheirsOverOurs` counts only `BlockNo`. This is the direct analog of the LP/Synth mismatch: one type of "share" (Peras boost) is not tracked in the disconnection gate, so the gate fires incorrectly.

---

### Impact Explanation

When Peras is active and a peer's candidate chain has fewer blocks than the local chain but enough Peras boosts to make it heavier (i.e., the canonical chain under Peras), the following sequence occurs:

1. A header on the peer's chain falls beyond the forecast horizon.
2. `checkPreferTheirsOverOurs` fires, comparing only block counts.
3. The peer's chain appears shorter → `CandidateTooSparse` is thrown → the peer is disconnected.
4. The node remains on its current, lighter chain.
5. The canonical Peras-weighted chain is never adopted.

An adversary can exploit this by maintaining a chain with the same or higher block count but zero Peras boosts. The honest peer offering the canonical (heavier but shorter) chain is evicted; the adversary's chain is retained. This constitutes a **chain selection failure**: the node durably prefers a non-canonical chain without operator fault.

This maps to: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

Peras is described as an extension under active development and is disabled by default. The TODO comment at line 1841 explicitly acknowledges the issue and links to a tracking issue (`cardano-peras/issues/64`). Once Peras is enabled in production, any scenario where a Peras-boosted chain is shorter in block count than the local chain — a normal occurrence when a certificate boosts a block on a fork — triggers this path. The forecast-horizon condition is also a normal operational condition (large slot gaps, slow ledger state advancement). The combination is realistic and requires no special attacker capability beyond serving a valid chain.

---

### Recommendation

Pass the real `PerasWeightSnapshot` to `checkPreferTheirsOverOurs` instead of `emptyPerasWeightSnapshot`. The snapshot is already available in the `ChainDB` via `getPerasWeightSnapshot` and is read atomically in `chainSelectionForBlock`. The ChainSync client's `dynEnv` or `cfgEnv` should be extended to carry a `STM m (PerasWeightSnapshot blk)` reader, which is then read inside the `atomically` block in `readLedgerStateHelper` and forwarded to `checkPreferTheirsOverOurs`. Alternatively, as the TODO suggests, the entire check may be removable once the Peras chain selection design is finalised — but until then the empty snapshot must not be used when Peras is enabled.

### Proof of Concept

**Setup (private testnet, Peras enabled, `k = 2160`, boost weight `B = 15`):**

1. Node starts with chain `C_ours`: tip at `BlockNo 100`, no Peras boosts. Total weight = 100.
2. Honest peer serves chain `C_theirs`: tip at `BlockNo 99`, one Peras-boosted block with boost 15. Total weight = 99 + 15 = 114 > 100. This is the canonical chain.
3. The next header on `C_theirs` falls beyond the forecast horizon (e.g., large slot gap).
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`.
5. `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag theirFrag` compares `BlockNo 100` vs `BlockNo 99` → `ShouldNotSwitch`.
6. `throwSTM (CandidateTooSparse ...)` fires; the honest peer is disconnected.
7. Node stays on `C_ours` (weight 100) and never adopts `C_theirs` (weight 114).
8. An adversary serving any chain with `BlockNo ≥ 100` and zero boosts is retained indefinitely.

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of

              ShouldNotSwitch o -> ShouldNotSwitch o

      case AF.intersect ours cand of
