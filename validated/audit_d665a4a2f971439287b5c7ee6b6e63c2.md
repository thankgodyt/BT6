### Title
Anyone Can Call `sign_btc_transaction` to Force-Sign Any User's Pending BTC Withdrawal — (`File: contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The `sign_btc_transaction` function is a public NEAR entry point that initiates MPC signing of a pending BTC withdrawal transaction. It carries no authorization check — any unprivileged NEAR account can call it for any `btc_pending_sign_id`, including those belonging to other users. This is a direct analog to the MapleLoan `closeLoan()` missing-authorization bug: a state-advancing function that should be restricted to the transaction owner (or a privileged role) is callable by anyone.

---

### Finding Description

`sign_btc_transaction` in `contracts/satoshi-bridge/src/api/chain_signatures.rs` is decorated only with `#[pause(except(roles(Role::DAO)))]`. There is no `#[access_control_any]` macro and no runtime check of `env::predecessor_account_id()` against the pending transaction's owner (`btc_pending_info.account_id`). [1](#0-0) 

The function:
1. Fetches the `BTCPendingInfo` for the caller-supplied `btc_pending_sign_id`.
2. Asserts the transaction is in `PendingSign` state.
3. Unconditionally calls `internal_sign_btc_transaction`, which dispatches a cross-contract call to the NEAR Chain Signatures (MPC) network to sign the specified input.

At no point is `env::predecessor_account_id()` compared to `btc_pending_info.account_id`. Any NEAR account can supply any `btc_pending_sign_id` and advance another user's pending withdrawal through the signing pipeline.

Compare this to the correctly guarded operator-only functions in the same file's sibling module, which all carry `#[access_control_any(roles(Role::DAO, Role::Operator))]`: [2](#0-1) 

`sign_btc_transaction` has no equivalent guard.

---

### Impact Explanation

Once `sign_btc_transaction` is called and the MPC network returns a signature, the pending transaction advances out of `PendingSign` state into `PendingVerify`. The user's only self-service recourse before that transition is `withdraw_rbf`: [3](#0-2) 

`withdraw_rbf` calls `btc_pending_info.assert_pending_sign()` internally (the same guard used in `sign_btc_transaction`). Once the attacker has advanced the state past `PendingSign`, the user can no longer call `withdraw_rbf` to increase the fee or redirect the change output. The only remaining recourse is `cancel_withdraw`, which is restricted to `Role::DAO` or `Role::Operator`: [4](#0-3) 

**Concrete attacker-controlled outcome:**
- A user initiates a withdrawal with a low fee (e.g., during a fee spike they haven't yet responded to).
- Before the user can call `withdraw_rbf` to bump the fee, an attacker calls `sign_btc_transaction` on the user's `btc_pending_sign_id`.
- The transaction is signed and broadcast to Bitcoin with the original low fee.
- The transaction stalls in the Bitcoin mempool. The user's nBTC is already burned (or held in escrow), and the BTC output is stuck until the transaction confirms or an operator intervenes with `cancel_withdraw`.

This constitutes **attacker-triggered temporary locking of bridged funds** and forces operator intervention to resolve, matching the **Medium** allowed impact: *"Bypass of bridge limits or policies, or attacker-triggered temporary locking of bridged funds."*

---

### Likelihood Explanation

`btc_pending_sign_id` values are emitted as on-chain events (`Event::GenerateBtcPendingInfo`) and are deterministically derived from the PSBT, making them publicly observable. Any NEAR account can monitor the chain for new pending sign IDs and immediately call `sign_btc_transaction` before the legitimate owner does. No special privilege, leaked key, or off-chain coordination is required. [5](#0-4) 

The same event pattern is used for withdrawal-initiated pending infos, so all pending sign IDs are publicly known.

---

### Recommendation

Add a caller identity check at the top of `sign_btc_transaction`, mirroring the pattern used in `withdraw_rbf`:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,
) -> PromiseOrValue<bool> {
    let caller = env::predecessor_account_id();
    let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
    // Only the transaction owner or a privileged role may advance signing.
    require!(
        caller == btc_pending_info.account_id
            || self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller),
        "sign_btc_transaction: caller is not the transaction owner"
    );
    btc_pending_info.assert_pending_sign();
    ...
}
```

### Proof of Concept

1. Alice calls `ft_transfer_call` on the nBTC contract to initiate a withdrawal. The bridge emits `Event::GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Alice's transaction is in `PendingSign` state. She intends to call `withdraw_rbf` to increase the fee.
3. Attacker Bob observes the event and immediately calls:
   ```
   sign_btc_transaction("abc123", 0, 0)
   ```
   with no attached deposit beyond the NEAR gas fee.
4. The MPC network signs the transaction. State advances to `PendingVerify`.
5. Alice's call to `withdraw_rbf("abc123", ...)` now panics at `assert_pending_sign()` — the state is no longer `PendingSign`.
6. The low-fee transaction is broadcast to Bitcoin and stalls. Alice's funds are locked until an operator calls `cancel_withdraw` or the transaction eventually confirms.

    pub fn sign_btc_transaction(
