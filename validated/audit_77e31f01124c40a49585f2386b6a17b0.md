### Title
Supply Inflation via Undelivered Mint When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

`safe_mint` in the nBTC token contract mints `amount` nBTC to the bridge's own account **before** checking whether the intended recipient is registered. If the recipient is not registered, the function silently returns `U128(0)` without transferring the minted tokens. The nBTC total supply is permanently inflated, the user receives zero tokens, and the BTC deposit is consumed by the satoshi-bridge — resulting in a permanent loss of user funds.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint` (lines 101–124):

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // (1) mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // (2) silent return, no transfer
    }

    if let Some(msg) = msg {
        self.ft_transfer_call(account_id, amount, None, msg)
    } else {
        self.ft_transfer(account_id, amount, None);
        PromiseOrValue::Value(amount)
    }
}
```

**Step (1):** `internal_deposit(&self.bridge_id, amount)` unconditionally increases the nBTC total supply by `amount` and credits the bridge's own token balance.

**Step (2):** If `account_id` has no registered storage slot on the nBTC contract, the function returns `U128(0)` immediately. No `ft_transfer` or `ft_transfer_call` is issued. The `amount` nBTC minted in step (1) remains in the bridge's nBTC balance on the token contract and is never delivered to the user.

This is the direct analog of the external report's pattern: the contract records (mints) more tokens than are actually delivered to the intended recipient, creating an accounting discrepancy between the total supply and the tokens in user hands. [1](#0-0) 

The satoshi-bridge calls `safe_mint` as part of the BTC deposit verification flow. The satoshi-bridge marks the deposit UTXO as verified in `verified_deposit_utxo` (a `LookupSet`) to prevent double-spending. Once the UTXO is marked verified, the deposit cannot be replayed. If `safe_mint` returns `U128(0)`, the satoshi-bridge has no mechanism to roll back the UTXO verification, leaving the user's BTC permanently locked with no nBTC issued. [2](#0-1) 

The bridge's own nBTC balance on the token contract is now inflated by `amount`. The `burn` function withdraws from `bridge_id`'s balance:

```rust
pub fn burn(...) {
    self.assert_bridge();
    self.token.internal_withdraw(&self.bridge_id, burn_amount.into());
    ...
}
```

This means the inflated balance can be consumed by a future legitimate withdrawal, effectively allowing the bridge to release BTC that was deposited by the victim user to a different withdrawing user — a supply/backing mismatch. [3](#0-2) 

---

### Impact Explanation

- **nBTC total supply is inflated** by `amount` without a corresponding user balance increase.
- **User's BTC deposit is consumed** (UTXO marked verified in satoshi-bridge), with no nBTC issued to the user.
- **User funds are permanently lost**: the BTC is locked in the bridge's UTXO set, the deposit cannot be retried (UTXO already verified), and the user holds zero nBTC.
- **Bridge nBTC balance is inflated**: the extra nBTC in the bridge's token account can be burned in a future unrelated withdrawal, meaning a different user's BTC withdrawal is backed by the victim's BTC deposit — a critical supply/backing invariant violation.

This matches: **Critical — Significant loss, theft, destruction, or permanent locking of user or protocol funds.**

---

### Likelihood Explanation

Any user who has not called `storage_deposit` on the nBTC contract before their BTC deposit is verified will trigger this path. This is a realistic scenario for first-time bridge users who are unaware of the NEP-141 storage registration requirement. The satoshi-bridge does not enforce or verify that the recipient is registered on the nBTC contract before initiating the mint. No privileged access is required; the trigger is simply the absence of a storage registration call.

---

### Recommendation

**Short-term:** In `safe_mint`, check whether `account_id` is registered **before** calling `internal_deposit`. If the account is not registered, either revert with a clear error or return without minting:

```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0)); // move this check BEFORE internal_deposit
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

**Long-term:** The satoshi-bridge should verify recipient registration on the nBTC contract before submitting a deposit verification, or handle a `U128(0)` return from `safe_mint` by reverting the UTXO verification so the deposit can be retried after the user registers storage.

---

### Proof of Concept

1. Alice sends 0.01 BTC to her bridge deposit address.
2. Alice has never called `storage_deposit` on the nBTC contract — her account is unregistered.
3. A relayer calls `verify_deposit_v2` on the satoshi-bridge with a valid Merkle proof.
4. The satoshi-bridge validates the proof, marks Alice's UTXO in `verified_deposit_utxo`, and calls `safe_mint(alice, 1_000_000, None)` on the nBTC contract.
5. Inside `safe_mint`: `internal_deposit(&bridge_id, 1_000_000)` executes — nBTC total supply increases by 1,000,000 satoshis, credited to the bridge's own nBTC balance.
6. `self.token.accounts.get(&alice)` returns `None` → function returns `U128(0)`.
7. The satoshi-bridge receives `U128(0)`. Alice's UTXO is already in `verified_deposit_utxo` — the deposit cannot be retried.
8. Alice holds 0 nBTC. Her 0.01 BTC is permanently locked. The bridge's nBTC balance is 1,000,000 satoshis higher than it should be, and this surplus will be consumed by the next unrelated user's withdrawal burn. [4](#0-3)
