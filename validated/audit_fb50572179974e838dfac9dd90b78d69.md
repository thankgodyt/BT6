### Title
Missing Peras Certificate Validation Implementation Allows Unauthorized Certificate Acceptance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance contains a stub `validatePerasCert` that unconditionally returns `Right` (success) for every certificate, performing no cryptographic or semantic checks. A companion function, `getVotingCommitteeForElection`, is entirely unimplemented and throws a hard runtime `error`. Together these constitute a missing-implementation pattern directly analogous to the external report: mechanisms that should process and validate accumulated protocol objects simply do not exist, so any inbound Peras certificate is accepted without verification and any cross-epoch committee lookup crashes the node.

---

### Finding Description

**Root cause 1 — `validatePerasCert` stub (always-`Right`):** [1](#0-0) 

The blanket instance `instance StandardHash blk => BlockSupportsPeras blk` is explicitly marked *"TODO: degenerate instance for all blks to get things to compile"*. Its `validatePerasCert` implementation is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
```

No signature verification, no committee membership check, no round-number sanity check — every certificate, including a completely fabricated one, is returned as `ValidatedPerasCert`.

**Root cause 2 — `getVotingCommitteeForElection` unimplemented:** [2](#0-1) 

```haskell
getVotingCommitteeForElection _electionId _interEpochVotingCommittee = do
  error "TODO: implement getVotingCommitteeForElection"
```

This is the production function responsible for resolving which voting committee applies to a given election ID across epoch boundaries. Any call to it crashes the calling thread with an impure Haskell `error`.

**How inbound certificates reach these stubs:**

`processCerts` in the Peras certificate object pool calls `validateCert` (which resolves to `validatePerasCert`) on every certificate received from a peer: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is unconditionally added to the pool. The `ObjectDiffusion` inbound handler feeds peer-supplied objects directly into this path: [4](#0-3) 

---

### Impact Explanation

Peras certificates carry a `vpcCertBoost` weight that is used in chain selection to prefer the boosted chain. Because `validatePerasCert` never rejects a certificate, an unprivileged peer can inject certificates for arbitrary rounds and arbitrary block hashes. These forged certificates are stored in the `PerasCertDB` and subsequently used by the chain-selection logic to boost whichever chain the attacker designates. This constitutes a **bypass of Peras certificate checks enabling unauthorized certificate acceptance**, which can cause an honest node to prefer a non-canonical or attacker-chosen chain over the legitimate heaviest chain — a chain-selection safety failure.

Additionally, once the TODO stubs are replaced with real implementations that call `getVotingCommitteeForElection`, any peer-triggered cross-epoch certificate validation will crash the processing thread via the hard `error`, permanently disabling certificate processing for that session.

---

### Likelihood Explanation

The `ObjectDiffusion` mini-protocol is already wired into the diffusion layer and accepts inbound objects from any connected peer without authentication. No stake, no keys, and no privileged access are required. An attacker needs only to connect as a normal peer and send a well-formed (but cryptographically invalid) `PerasCert` CBOR payload. The blanket instance applies to all block types including `CardanoBlock`, so the vulnerable path is active for every node that has the Peras diffusion code enabled.

---

### Recommendation

1. Replace the stub `validatePerasCert` with a real implementation that verifies the aggregate BLS signature against the committee's aggregate public key, checks committee membership for each voter, and validates the round number and boosted-block hash against the current chain state.
2. Implement `getVotingCommitteeForElection` to correctly resolve the `InterEpochVotingCommittee` by matching the `ElectionId` against the current and previous epoch committees, returning `Nothing` (not crashing) when no match is found.
3. Add integration tests that send crafted/invalid certificates over the `ObjectDiffusion` mini-protocol and assert they are rejected.

---

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
