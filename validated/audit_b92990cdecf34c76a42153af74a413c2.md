### Title
Tokens Minted to Bridge Without Rollback When Recipient Is Unregistered in `safe_mint()` — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

In `safe_mint()`, the nBTC token contract mints `amount` tokens to `bridge_id` **before** checking whether the intended recipient account is registered. If the recipient is not registered, the function returns `U128(0)` without burning the already-minted tokens. This permanently inflates the nBTC total supply beyond the amount of BTC actually locked in the bridge's Bitcoin addresses, and leaves the depositing user's BTC locked with no nBTC delivered.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, `safe_mint()` executes the following sequence:

```rust
// Line 112 — tokens are minted to bridge_id FIRST
self.token.internal_deposit(&self.bridge_id, amount.into());

// Lines 114-116 — recipient registration check AFTER the mint
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));  // no burn, tokens stay in bridge_id
}
``` [1](#0-0) 

The state-mutating operation (`internal_deposit` to `bridge_id`) occurs unconditionally before the guard that determines whether the transfer can proceed. When the guard fires (unregistered recipient), the function returns early with `U128(0)` but performs **no compensating burn**. The minted tokens remain in `bridge_id`'s balance and the total supply is permanently inflated for the duration until (if ever) the bridge explicitly burns them.

This is structurally identical to the Compound-class vulnerability described in the report: a state change is committed before a condition is checked, and the failure path does not roll back the state change.

---

### Impact Explanation

- **Supply inflation**: `ft_total_supply()` now exceeds the amount of BTC locked in the bridge's Bitcoin addresses. The nBTC supply is no longer fully backed 1:1.
- **User fund loss**: The depositing user's BTC is locked in the bridge's Bitcoin address, but they receive zero nBTC. Their deposit is effectively stranded.
- **Bridge balance distortion**: `bridge_id`'s nBTC balance silently grows. Any downstream logic that relies on the bridge's own nBTC balance (e.g., burn accounting, protocol fee tracking) operates on an inflated figure.

This matches the allowed Medium impact: **broken callback rollback** — the mint state change is not rolled back when the transfer cannot be completed — and potentially Critical if the bridge's callback does not explicitly burn the orphaned tokens, causing permanent supply/backing divergence.

---

### Likelihood Explanation

NEAR NEP-141 requires explicit `storage_deposit` registration before a token account can hold a balance. A user who deposits BTC to the bridge without having previously registered their NEAR account with the nBTC contract will trigger this path. This is a realistic and reachable scenario: the bridge deposit flow is initiated on the Bitcoin side (sending BTC to a derived address), and there is no on-chain enforcement that the NEAR recipient has pre-registered with the nBTC contract before the BTC transaction is submitted.

---

### Recommendation

Reorder the logic so the state change only occurs after the guard passes, or add an explicit burn on the failure path:

**Option A — Check before minting:**
```rust
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
self.token.internal_deposit(&self.bridge_id, amount.into());
```

**Option B — Burn on failure:**
```rust
self.token.internal_deposit(&self.bridge_id, amount.into());
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_withdraw(&self.bridge_id, amount.into());
    return PromiseOrValue::Value(U128(0));
}
```

Option A is preferred as it avoids the unnecessary mint/burn round-trip and keeps the supply invariant clean.

---

### Proof of Concept

1. User sends BTC to their bridge deposit address on the Bitcoin network.
2. A relayer submits the Merkle proof; the satoshi-bridge verifies it and calls `safe_mint(user_near_account, amount, None)` on the nBTC contract.
3. `safe_mint` executes `self.token.internal_deposit(&self.bridge_id, amount.into())` — total nBTC supply increases by `amount`, all held by `bridge_id`.
4. `safe_mint` checks `self.token.accounts.get(&user_near_account)` — the account is not registered (user never called `storage_deposit`).
5. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — **no burn is performed**.
6. Result: total nBTC supply is inflated by `amount` with no corresponding user credit. The user's BTC remains locked in the bridge's Bitcoin address. The bridge's nBTC balance is `amount` higher than it should be, silently breaking the 1:1 backing invariant. [2](#0-1)

```rust
    pub fn safe_mint(
        &mut self,
        account_id: AccountId,
        amount: U128,
        msg: Option<String>,
    ) -> PromiseOrValue<U128> {
        self.assert_bridge();
        require!(
            account_id != self.bridge_id,
            "safe_mint: account_id must not be the bridge"
        );
        self.token.internal_deposit(&self.bridge_id, amount.into());

        if self.token.accounts.get(&account_id).is_none() {
            return PromiseOrValue::Value(U128(0));
        }

        if let Some(msg) = msg {
            self.ft_transfer_call(account_id, amount, None, msg)
        } else {
            self.ft_transfer(account_id, amount, None);
            PromiseOrValue::Value(amount)
        }
    }
```
