### Title
Unauthenticated Refund Address Substitution Allows Theft of User BTC Refunds - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`internal_request_refund` accepts a caller-supplied `refund_address` without verifying that the caller is the `deposit_msg.recipient_id`. When a deposit's `DepositMsg` contains no pre-authorized `refund_address`, any unprivileged NEAR account can submit a refund request for a victim's UTXO and redirect the BTC refund to an attacker-controlled Bitcoin address.

### Finding Description

`internal_request_refund` enforces a `refund_address` match only when `deposit_msg.refund_address` is already set: [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case — users rarely pre-specify a BTC refund address), the check is skipped entirely and the caller-supplied `refund_address` is stored verbatim: [2](#0-1) 

There is no check anywhere in `internal_request_refund` or `request_refund_callback` that `env::predecessor_account_id() == deposit_msg.recipient_id`. The `deposit_msg` is a public artifact — its JSON is hashed to derive the deposit address, and the hash is embedded in the BTC transaction, making it fully observable on-chain. Any NEAR account can reconstruct it and call `request_refund` with an attacker-controlled `refund_address`.

The stored `refund_address` is later used verbatim to build the refund PSBT output: [3](#0-2) 

The MPC then signs and broadcasts this transaction, sending the victim's BTC to the attacker's address.

### Impact Explanation

**Critical.** The attacker receives the victim's BTC directly. The victim's deposit UTXO is spent by the bridge's MPC-signed refund transaction paying the attacker's address. The victim loses their entire deposited BTC with no recourse, because `verified_deposit_utxo` is marked after `execute_refund`, blocking any subsequent `verify_deposit` for the same UTXO. [4](#0-3) 

### Likelihood Explanation

**High.** The attack requires only:
1. Observing a victim's BTC deposit transaction on-chain (public).
2. Reconstructing the `deposit_msg` from the transaction (public OP_RETURN / derivation path).
3. Submitting a valid Merkle inclusion proof (public, from any BTC node).
4. Waiting for `unsafe_refund_timelock_sec` to elapse without DAO intervention.

The `unsafe_refund_timelock_sec` is a delay, not a prevention. The DAO has no reliable way to distinguish a legitimate refund request from an attacker's request when the original `deposit_msg` contained no `refund_address`, because the legitimate BTC address of the depositor is not recorded anywhere in contract state. [5](#0-4) 

### Recommendation

Add a caller-identity check in `internal_request_refund` when `deposit_msg.refund_address` is `None`:

```rust
// When no refund_address is pre-authorized in the deposit_msg,
// only the deposit recipient may submit the refund request.
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may submit a refund request without a pre-authorized refund address"
    );
}
```

Alternatively, require that `deposit_msg.refund_address` is always set (non-`None`) before a refund request can be submitted, forcing users to pre-authorize their BTC refund address at deposit time.

### Proof of Concept

1. **Victim** sends BTC to the deposit address derived from `deposit_msg = { recipient_id: "victim.near", refund_address: null }`. The deposit is never finalized (e.g., the UTXO is below the minimum or the light client proof window expires).

2. **Attacker** observes the BTC transaction on-chain, reconstructs `deposit_msg`, and calls:
   ```
   request_refund(
     deposit_msg = { recipient_id: "victim.near", refund_address: null },
     refund_address = "attacker_btc_address",
     tx_bytes = <victim's raw BTC tx>,
     vout = 0,
     proof = <valid Merkle proof>
   )
   ```

3. `internal_request_refund` at line 154 skips the `refund_address` check because `deposit_msg.refund_address` is `None`. [6](#0-5) 

4. `request_refund_callback` stores `RefundRequest { refund_address: "attacker_btc_address", ... }`.

5. After `unsafe_refund_timelock_sec` elapses, attacker calls `execute_refund`. The bridge builds a PSBT paying `attacker_btc_address`, MPC signs it, and broadcasts it. Victim's BTC is transferred to the attacker.

    /// Build a transparent refund output paying `refund_amount` to `refund_address`.
    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
