Audit Report

## Title
Trusted Relayer Can Forward Unchecked `max_gas_fee` to BTC Connector When User `msg` Lacks `MaxGasFee` Variant — (`near/omni-bridge/src/btc.rs`)

## Summary
In `submit_transfer_to_utxo_chain_connector`, the `max_gas_fee` constraint extracted from the user's on-chain `msg` is only enforced when the stored `msg` successfully deserializes as `DestinationChainMsg::MaxGasFee`. When the user's `msg` is empty, unparseable, or is the `DestHexMsg` variant, the validation block is skipped entirely, and the relayer's caller-supplied `max_gas_fee` is forwarded verbatim to the BTC connector. A malicious trusted relayer can exploit this to inflate the gas fee deducted from the user's satoshi output.

## Finding Description
In `near/omni-bridge/src/btc.rs` lines 54–62, the bridge reads the user's stored `msg` and attempts to extract a `max_gas_fee` constraint:

```rust
let max_gas_fee_msg = DestinationChainMsg::from_json(&transfer.message.msg)
    .and_then(|s| s.max_gas_fee());

if let Some(max_gas_fee_msg) = max_gas_fee_msg {
    require!(
        max_gas_fee.expect("max_gas_fee is missing") == max_gas_fee_msg,
        "Invalid max gas fee"
    );
}
```

`DestinationChainMsg::from_json` is implemented as `serde_json::from_str(s).ok()` (`near/omni-types/src/lib.rs` line 939–941), returning `None` on any parse failure — including an empty string. `DestinationChainMsg::max_gas_fee()` also returns `None` for the `DestHexMsg` variant (lines 923–929). In both cases, `max_gas_fee_msg` is `None`, the `if let Some(...)` block is skipped, and the relayer's `max_gas_fee` value is never validated against anything the user committed to on-chain.

The raw relayer-supplied `msg` string — including the unchecked `max_gas_fee` — is then forwarded verbatim to the BTC connector at line 91:

```rust
.ft_transfer_call(self.get_utxo_chain_connector(chain_kind), amount, None, msg)
```

The `TokenReceiverMessage::Withdraw` struct (`near/omni-types/src/btc.rs` lines 10–15) carries `max_gas_fee: Option<U128>`, which the BTC connector uses to determine the maximum gas fee it may deduct from the user's satoshi output. Since the bridge never validates this field when the user's `msg` is empty or `DestHexMsg`, the relayer controls it freely.

The root cause is that the guard is conditional rather than unconditional: the bridge only enforces the user's commitment when one exists, but does not restrict the relayer's `max_gas_fee` when no commitment exists.

## Impact Explanation
This is a concrete instance of **fee mis-accounting that changes user balances**, which is an explicitly listed Critical impact. A malicious trusted relayer targeting a pending BTC transfer whose `msg` is empty or `DestHexMsg` can set `max_gas_fee` to the connector's configured ceiling (e.g., 80,000 satoshis). The connector deducts up to that inflated ceiling from the user's output, reducing the satoshis delivered to the user's BTC address. The user receives fewer satoshis than they are owed, with the difference captured as excess fee. This is a direct, relayer-controlled balance manipulation affecting real user funds.

## Likelihood Explanation
The attacker must hold the trusted relayer role, which requires staking and an application period — a privileged but non-admin role reachable through the normal production relayer onboarding path. Any BTC withdrawal initiated without an explicit `MaxGasFee` in the `msg` — including all transfers from EVM chains where the source chain message format uses `DestHexMsg` or no `msg` at all — is vulnerable. This covers a large fraction of real production transfers, as EVM-originated BTC withdrawals commonly carry no `MaxGasFee` commitment. The attack is repeatable across any such pending transfer.

## Recommendation
Remove the conditional and always enforce the constraint. When the user's stored `msg` contains no `MaxGasFee`, the relayer's `max_gas_fee` must also be `None`. The simplest safe fix:

```rust
let max_gas_fee_msg = DestinationChainMsg::from_json(&transfer.message.msg)
    .and_then(|s| s.max_gas_fee());

require!(
    max_gas_fee == max_gas_fee_msg,
    "Invalid max gas fee"
);
```

This ensures that if the user did not commit to a `max_gas_fee`, the relayer cannot supply one, and if the user did commit to one, the relayer must match it exactly.

## Proof of Concept
1. User calls `ft_transfer_call` on the nBTC token contract with `msg = ""` (empty string), initiating a BTC withdrawal. The transfer is stored in `pending_transfers` with `transfer.message.msg = ""`.
2. Trusted relayer calls `submit_transfer_to_utxo_chain_connector` with a `msg` JSON containing `"max_gas_fee": "80000"` inside the `Withdraw` variant.
3. At line 54, `DestinationChainMsg::from_json("")` calls `serde_json::from_str("").ok()`, which returns `None`. Therefore `max_gas_fee_msg = None`.
4. The `if let Some(max_gas_fee_msg)` block at line 57 is skipped — no validation occurs.
5. The bridge calls `ft_transfer_call` on the nBTC token at line 91, forwarding the relayer's `msg` (with `max_gas_fee = 80000`) to the BTC connector.
6. The BTC connector deducts up to 80,000 satoshis as gas fee from the user's output, even if the actual network fee is 1,000 satoshis.
7. The user receives 79,000 fewer satoshis than owed. The bridge contract never rejected the call.

To reproduce: write a NEAR integration test that (a) stores a transfer with `msg = ""`, (b) calls `submit_transfer_to_utxo_chain_connector` as a trusted relayer with `max_gas_fee = 80000`, and (c) asserts the call succeeds without panic — confirming the invariant is broken.
