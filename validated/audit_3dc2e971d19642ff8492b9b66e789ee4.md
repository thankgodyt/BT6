### Title
Refund Address Front-Running in `request_refund` Allows Attacker to Redirect BTC Refunds to Arbitrary Address - (File: contracts/satoshi-bridge/src/refund.rs)

---

### Summary

When a user submits a refund request for a failed BTC deposit where `deposit_msg.refund_address` is `None`, any unprivileged NEAR account can front-run that transaction and substitute an arbitrary attacker-controlled Bitcoin address as the `refund_address`. Because the bridge stores only one refund request per UTXO (first-writer wins), the legitimate depositor's request is permanently blocked and the BTC refund is redirected to the attacker.

---

### Finding Description

`internal_request_refund` accepts a caller-supplied `refund_address` parameter and only validates it against `deposit_msg.refund_address` when that field is `Some`:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case where the user did not pre-authorize a refund address at deposit time), the check is skipped entirely and any caller-supplied Bitcoin address is accepted without restriction. [1](#0-0) 

The `deposit_msg` itself is public information: it is the data used to derive the on-chain Bitcoin deposit address, so an attacker who observes a victim's pending `request_refund` NEAR transaction in the mempool already has every input needed to replay it with a different `refund_address`.

After the callback stores the request, a duplicate is permanently rejected:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

The stored `refund_address` is later used verbatim when building the Bitcoin refund transaction: [3](#0-2) 

There is no check anywhere in `internal_request_refund` or its callback that the NEAR caller matches the `deposit_msg.near_account_id` (the intended recipient of the deposit). [4](#0-3) 

---

### Impact Explanation

**Critical.** A successful front-run permanently redirects the BTC refund to the attacker's Bitcoin address. The victim's subsequent `request_refund` call fails with "Refund request already exists for this UTXO", and the UTXO is then spent by `execute_refund` to the attacker's address. The victim loses their entire deposited BTC with no recovery path.

---

### Likelihood Explanation

NEAR validators can reorder transactions within a block, making mempool front-running feasible. The attacker needs only to observe the victim's pending `request_refund` call (all parameters are visible in the NEAR transaction payload) and submit an identical call with a substituted `refund_address` at a higher priority. No privileged access, leaked keys, or external dependencies are required. Any NEAR account can execute this attack against any refund request where `deposit_msg.refund_address` is `None`.

---

### Recommendation

Restrict `request_refund` so that only the NEAR account named in `deposit_msg` (i.e., the intended deposit recipient) may submit the refund request when no pre-authorized `refund_address` is embedded in the `deposit_msg`. Concretely, add a check such as:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.near_account_id,
        "Only the deposit recipient may request a refund without a pre-authorized refund address"
    );
}
```

This mirrors the remediation applied in the referenced Story Protocol report: binding the privileged action to the specific authorized caller rather than allowing any account to supply arbitrary parameters alongside a valid proof.

---

### Proof of Concept

1. Alice makes a BTC deposit to an address derived from her `DepositMsg` with `refund_address: None`.
2. The deposit is not processed (e.g., wrong amount, expired window).
3. Alice constructs and broadcasts a NEAR `request_refund` call with her own BTC address as `refund_address`, along with the valid `tx_bytes`, `vout`, and Merkle proof.
4. Bob (attacker) observes Alice's pending transaction in the NEAR mempool. He extracts `deposit_msg`, `tx_bytes`, `vout`, and `proof` — all public.
5. Bob submits an identical `request_refund` call but sets `refund_address` to his own Bitcoin address, with sufficient gas priority to land first.
6. Bob's `request_refund_callback` executes first and stores a `RefundRequest` with Bob's Bitcoin address.
7. Alice's callback fails: `"Refund request already exists for this UTXO"`.
8. After the timelock elapses, anyone calls `execute_refund`. The bridge builds a Bitcoin transaction paying Bob's address and requests an MPC signature.
9. Alice's BTC is permanently transferred to Bob.

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
```

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
