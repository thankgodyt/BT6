### Title
Caller Identity Not Validated Against Pending-Info Owner in `withdraw_rbf` — (File: `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`withdraw_rbf` uses `env::predecessor_account_id()` as the authoritative account identity and checks pending-sign capacity against the **caller**, not the actual owner recorded in the `BTCPendingInfo`. Any unprivileged NEAR account can invoke `withdraw_rbf` on a victim's pending withdrawal, supplying attacker-controlled `output` data, without ever being verified as the owner of that pending info.

---

### Finding Description

`withdraw_rbf` is a public, unprivileged function:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  L259-L274
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let account_id = env::predecessor_account_id();   // ← caller, not owner
    self.require_pending_sign_capacity(&account_id);  // ← checked against caller

    self.withdraw_rbf_chain_specific(
        account_id,                          // ← caller passed as owner
        original_btc_pending_verify_id,
        output,                              // ← fully attacker-controlled
        chain_specific_data,
    );
}
``` [1](#0-0) 

The privileged counterpart `cancel_withdraw` demonstrates the correct pattern: it explicitly reads the owner from the stored `BTCPendingInfo` before proceeding:

```rust
// contracts/satoshi-bridge/src/api/bridge.rs  L285-L299
pub fn cancel_withdraw(&mut self, original_btc_pending_verify_id: String, output: Vec<TxOut>) {
    assert_one_yocto();
    let user_account_id = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id          // ← reads actual owner
        .clone();
    self.require_pending_sign_capacity(&user_account_id);
    ...
}
``` [2](#0-1) 

`withdraw_rbf` performs no equivalent ownership lookup. Because `cancel_withdraw` (the privileged analog) must look up the owner explicitly, the design pattern confirms that `withdraw_rbf_chain_specific` does not perform this check internally — ownership validation is the caller's responsibility, and `withdraw_rbf` omits it entirely.

Each `BTCPendingInfo` stores the authoritative owner:

```rust
// contracts/satoshi-bridge/src/btc_pending_info.rs (inferred from create_btc_pending_info)
pub struct BTCPendingInfo {
    pub account_id: AccountId,   // ← actual owner
    ...
}
``` [3](#0-2) 

The attacker passes their own `account_id` into `withdraw_rbf_chain_specific`, which creates a new `BTCPendingInfo` attributed to the attacker, while the attacker-supplied `output` (the new Bitcoin transaction outputs) is used to construct the replacement PSBT that the MPC network will sign.

---

### Impact Explanation

The MPC chain-signature service signs whatever PSBT the bridge presents. If an attacker can invoke `withdraw_rbf` on a victim's pending withdrawal and supply attacker-controlled `output` (including a different BTC destination address), the signed replacement transaction can redirect the victim's BTC to the attacker's address. Even if output-address redirection is blocked by PSBT validation, the attacker can still:

- Trigger unsolicited RBF on any user's withdrawal, consuming bridge signing resources and modifying the victim's pending state without consent.
- Attribute the new `BTCPendingInfo` to themselves, corrupting the ownership accounting of the pending-sign pipeline.
- Cause the victim's original pending info to be superseded, leaving the victim's withdrawal in an unrecoverable or operator-intervention-required state.

This maps to **Critical** (chain-signature / PSBT construction failure enabling unauthorized redirection of bridge-controlled funds) or at minimum **Medium** (attacker-triggered stuck bridge state requiring operator intervention).

---

### Likelihood Explanation

`withdraw_rbf` is a public function with no access-control guard beyond the pause check. Any NEAR account can call it with an arbitrary `original_btc_pending_verify_id`. Pending withdrawal IDs are observable on-chain via emitted events (`GenerateBtcPendingInfo`). The attack requires no special privilege, no leaked key, and no third-party compromise. [4](#0-3) 

---

### Recommendation

Mirror the pattern used in `cancel_withdraw`: look up the actual owner from the stored `BTCPendingInfo` and assert it equals `env::predecessor_account_id()` before proceeding.

```rust
pub fn withdraw_rbf(
    &mut self,
    original_btc_pending_verify_id: String,
    output: Vec<TxOut>,
    chain_specific_data: Option<ChainSpecificData>,
) {
    let caller = env::predecessor_account_id();
    // Verify caller is the actual owner of this pending withdrawal
    let owner = self
        .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
        .account_id
        .clone();
    require!(caller == owner, "Only the withdrawal owner can trigger RBF");
    self.require_pending_sign_capacity(&owner);
    self.withdraw_rbf_chain_specific(owner, original_btc_pending_verify_id, output, chain_specific_data);
}
```

### Proof of Concept

1. Victim calls `ft_transfer_call(bridge, 1_BTC, WithdrawMsg { target_btc_address: victim_btc_addr, ... })`. Bridge emits `GenerateBtcPendingInfo { btc_pending_id: "abc123" }`.
2. Attacker observes `"abc123"` on-chain.
3. Attacker calls `withdraw_rbf("abc123", [TxOut { value: ..., script_pubkey: attacker_btc_script }], None)`.
4. `withdraw_rbf` sets `account_id = attacker`, checks attacker's (not victim's) pending capacity, and calls `withdraw_rbf_chain_specific(attacker, "abc123", attacker_output, ...)`.
5. A new `BTCPendingInfo` is created attributed to the attacker, with attacker-controlled outputs. The MPC network signs the replacement PSBT.
6. The replacement transaction (paying attacker's BTC address) propagates and confirms, while the victim's original transaction is replaced. Victim's nBTC is burned; BTC goes to attacker. [1](#0-0) [2](#0-1)
