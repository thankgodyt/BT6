After thorough investigation of the codebase, I found a genuine analog to the GeVault first-depositor share price manipulation vulnerability.

---

### Title
Peras Certificate Validation Bypass Allows Adversarial Chain Weight Inflation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The `validatePerasCert` method in the `BlockSupportsPeras` class is a stub that unconditionally accepts every certificate without performing any cryptographic or quorum validation. An unprivileged peer can submit crafted Peras certificates that boost arbitrary blocks, inflating the weight of an adversarial chain fragment and causing honest nodes to prefer it over the honest chain — a direct analog to the GeVault first-depositor share-price manipulation where an attacker inflates the denominator of a ratio used for proportional allocation.

---

### Finding Description

**Root cause — the stub validator**

The only instance of `BlockSupportsPeras` is a catch-all degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This always returns `Right`, accepting any `PerasCert` regardless of BLS signatures, committee membership, or quorum. The resulting `ValidatedPerasCert` carries a `vpcCertBoost` equal to the configured `perasWeight params`.

**How the inflated weight propagates into chain selection**

1. The `ValidatedPerasCert` is added to `PerasCertDB` via `addPerasCertAsync` → `chainSelSync`. [2](#0-1) 

2. `getWeightSnapshot` builds a `PerasWeightSnapshot` from all stored certificates, mapping each `pcCertBoostedBlock` to its `vpcCertBoost`. [3](#0-2) 

3. `weightBoostOfFragment` sums the boosts for every block in a candidate fragment. [4](#0-3) 

4. `wsvTotalWeight` adds the block count to the boost, and `preferCandidate` in `WeightedSelectView` switches to the candidate if its total weight exceeds the current chain's. [5](#0-4) 

5. `takeVolatileSuffix` uses the same inflated weight to determine the immutable prefix, potentially treating volatile blocks as immutable and preventing legitimate rollbacks. [6](#0-5) 

**The GeVault analog**

| GeVault | Ouroboros Consensus |
|---|---|
| `balanceOf(address(this))` — external state used in share-price ratio | `PerasWeightSnapshot` — external state used in chain-weight comparison |
| Attacker donates tokens directly to inflate the denominator | Attacker submits crafted certificates to inflate `wsvWeightBoost` |
| `totalSupply == 0` initial state makes the ratio manipulable | Empty `PerasCertDB` at startup means the first certificates set the weight baseline |
| Subsequent depositors receive fewer shares | Subsequent chain selection prefers the adversarially-boosted chain |

The only partial guard in `chainSelSync` is the `IgnorePerasCertTooOld` check, which uses strict `<`:

```haskell
when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
  idExitEarly PerasCertIgnoredTooOld
``` [7](#0-6) 

This rejects certificates boosting blocks *strictly older* than the immutable tip, but certificates boosting blocks at or after the immutable tip slot pass through. There is also a `GenesisHash` early-exit that prevents genesis-boosting certificates from triggering chain selection, but the certificate is still stored in `PerasCertDB` and included in the snapshot. [8](#0-7) 

---

### Impact Explanation

An adversary can submit crafted `PerasCert` messages boosting blocks on their adversarial chain. Because `validatePerasCert` always returns `Right`, each certificate is accepted and adds `perasWeight params` to the adversarial chain's `wsvWeightBoost`. Once the accumulated boost causes `wsvTotalWeight(adversarial) > wsvTotalWeight(honest)`, `preferCandidate` returns `ShouldSwitch` and the node adopts the adversarial chain — a **chain selection safety failure** caused by unauthorized certificate acceptance. This matches the "Critical. Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance" impact class.

---

### Likelihood Explanation

Any peer connected to the node via the standard mini-protocol can submit `PerasCert` messages. No stake, keys, or special privileges are required. The bypass is unconditional — there is no code path that performs real validation for any block type using the catch-all instance.

---

### Recommendation

1. Implement BLS aggregate signature verification and committee-membership / quorum checks inside `validatePerasCert` before the Peras certificate path is enabled on any network.
2. Gate `addPerasCertAsync` behind a feature flag that is disabled until proper validation is in place.
3. Add a minimum-boost sanity check so that a single certificate cannot exceed a protocol-defined maximum weight contribution.
4. Consider burning a small amount of "minimum weight" at genesis (analogous to the GeVault mitigation of burning `MINIMUM_LIQUIDITY`) so that the initial weight baseline cannot be set arbitrarily by the first certificate received.

### Proof of Concept

```
Private-testnet sequence:

1. Start a node with Peras enabled (any block type using the catch-all
   BlockSupportsPeras instance).

2. As an unprivileged peer, construct a PerasCert:
     pcCertRound      = <any round number>
     pcCertBoostedBlock = <point of a block on the adversarial fork>

3. Call validatePerasCert params cert  →  always returns Right ValidatedPerasCert
     { vpcCert = cert, vpcCertBoost = perasWeight params }

4. Submit via addPerasCertAsync (the ChainDB API entry point reachable
   from the network layer).

5. chainSelSync stores the cert in PerasCertDB; getWeightSnapshot now
   includes (adversarialBlockPoint, perasWeight params).

6. Repeat steps 2–5 for each block on the adversarial fork to accumulate
   total boost B = n * perasWeight params.

7. Once B > (honest chain length - adversarial chain length), preferCandidate
   returns ShouldSwitch and the node adopts the adversarial chain.
```
