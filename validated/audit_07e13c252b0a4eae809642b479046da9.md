Audit Report

## Title
Replay of `fin_transfer` Proof After Recipient-Rejection Refund Enables Double-Spend — (File: near/omni-bridge/src/lib.rs)

## Summary

When a `fin_transfer` targets a NEAR recipient with a non-empty `msg`, tokens are delivered via `ft_transfer_call`. If the recipient contract rejects all tokens (its `ft_on_transfer` returns the full amount), `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which deletes the `TransferId` from `finalised_transfers` — the sole replay-protection barrier for inbound proofs. The identical foreign-chain proof can then be re-submitted, causing a second minting or unlocking of tokens for a single on-chain lock event.

## Finding Description

`process_fin_transfer_to_near` inserts the `TransferId` into `finalised_transfers` via `add_fin_transfer` at line 1875, then issues `send_tokens` with `ft_transfer_call` when `msg` is non-empty (line 1973: `!msg.is_empty()`). [1](#0-0) 

The callback `fin_transfer_send_tokens_callback` evaluates `is_refund_required`. This function reads the result of `ft_transfer_call` (the amount of tokens actually used). In NEP-141, if `ft_on_transfer` returns the full amount (reject all), `ft_transfer_call` returns 0. `is_refund_required` returns `true` when `amount.0 == 0`: [2](#0-1) 

When `is_refund_required` is `true`, the callback calls `remove_fin_transfer`, unconditionally deleting the entry from `finalised_transfers`: [3](#0-2) [4](#0-3) 

After removal, `add_fin_transfer` will succeed again for the same `TransferId` because `finalised_transfers.insert` returns `true` for a fresh insert: [5](#0-4) 

The prover verifies the cryptographic proof against the light-client state but does not independently track consumed proofs. `finalised_transfers` is the only replay barrier, and it has been cleared.

## Impact Explanation

This is a **critical cross-chain replay / double-spend**. An attacker receives two token deliveries for a single foreign-chain lock event: unauthorized minting (for deployed tokens) or double-unlock (for native bridged tokens), permanently inflating supply or draining the bridge escrow. This matches the allowed impact: *"Cross-chain replay, message forgery, event/proof parsing flaw … enabling invalid finalization or double-spending"* and *"Stealing, loss, double-spending, unauthorized minting … of bridged funds."*

## Likelihood Explanation

- The attacker controls both the recipient address and the `msg` field when initiating the transfer on the EVM side — both are user-supplied inputs with no privilege requirement.
- The `FailedFinTransferEvent` emitted after the first rejection is a natural signal for relayers to retry, making the second submission occur without any social engineering.
- No admin compromise, key leak, or MPC collusion is required. Any unprivileged user can execute this by deploying a malicious NEAR contract.

## Recommendation

Do **not** remove the `finalised_transfers` entry on a failed token delivery. The entry records that the foreign-chain event was consumed; that fact is permanent regardless of what happens on the NEAR side.

- Keep the `finalised_transfers` entry intact on refund in `fin_transfer_send_tokens_callback`.
- If token delivery fails, record the failure separately (e.g., a `failed_transfers` map keyed by `TransferId`) and allow the user to claim a refund through a separate, authenticated path that does not re-accept the original proof.
- The storage cost refund motivation for `remove_fin_transfer` can be addressed by charging storage upfront and refunding from a separate accounting mechanism that does not touch the replay-protection set.

## Proof of Concept

**Setup:**
- Deploy malicious NEAR contract `evil.near` whose `ft_on_transfer` returns the full `amount` on the first call and `0` on the second call.
- Initiate a transfer on EVM: `recipient = "evil.near"`, `msg = "x"` (non-empty).

**Step 1 — First `fin_transfer`:**
```
relayer → fin_transfer(proof)
  → process_fin_transfer_to_near
    → add_fin_transfer(transfer_id)        // finalised_transfers: {transfer_id}
    → ft_transfer_call → evil.near::ft_on_transfer returns amount  // reject
  → fin_transfer_send_tokens_callback
    → is_refund_required = true (ft_transfer_call returned 0)
    → remove_fin_transfer(transfer_id)     // finalised_transfers: {}  ← guard cleared
    → emits FailedFinTransferEvent
```

**Step 2 — Replay with same proof:**
```
relayer → fin_transfer(same proof)
  → process_fin_transfer_to_near
    → add_fin_transfer(transfer_id)        // succeeds! finalised_transfers: {transfer_id}
    → ft_transfer_call → evil.near::ft_on_transfer returns 0  // accept
  → fin_transfer_send_tokens_callback
    → is_refund_required = false
    → tokens delivered to evil.near        // DOUBLE SPEND
```

A local integration test can confirm this by: (1) registering a mock prover that always returns valid, (2) deploying a mock token and mock recipient that rejects on first call, (3) calling `fin_transfer` twice with the same proof bytes, and (4) asserting the recipient's token balance equals twice the transfer amount.
