### Title
No check for MPC service availability causes Zcash withdrawal transactions to expire during MPC downtime - (File: `contracts/satoshi-bridge/src/zcash_utils/contract_methods.rs`)

### Summary

When a Zcash withdrawal is initiated, the transaction's `expiry_height` is fixed at construction time based on the current Zcash block height. If the NEAR Chain Signatures (MPC) service is unavailable for longer than `expiry_height_gap` blocks, the pre-built transaction will be expired by the time it can be signed and broadcast. The bridge has no mechanism to detect MPC downtime or to rebuild the transaction with a fresh expiry height, leaving the user's nBTC locked in the bridge in a stuck `PendingVerify` state that requires operator intervention to resolve.

### Finding Description

In `zcash_utils/contract_methods.rs`, `get_expiry_height` computes the expiry height as `last_block_height + expiry_height_gap` (default 1000 blocks, roughly 20 hours on Zcash mainnet):

```rust
let expiry_height = if let Some(chain_specific_data) = chain_specific_data {
    chain_specific_data.expiry_height
} else {
    last_block_height + self.get_config().expiry_height_gap
};
```

This value is fetched asynchronously at withdrawal initiation time (via `ft_on_transfer_withdraw_chain_specific` → `get_last_block_height_promise` → `ft_on_transfer_callback`) and is baked into the PSBT stored in `BTCPendingInfo.psbt_hex`. The PSBT is never reconstructed after this point.

When the user later calls `sign_btc_transaction`, the bridge calls the MPC service to sign the pre-built PSBT. If the MPC service was unavailable for more than `expiry_height_gap` Zcash blocks between withdrawal initiation and signing, the signed transaction will carry an expiry height that is already in the past. The Zcash network will reject such a transaction as expired.

Simultaneously, the `max_btc_tx_pending_sec` wall-clock timer (stored in `BTCPendingInfo.create_time_sec`) continues to advance during MPC downtime. Once it elapses, the DAO/Operator is permitted to call `cancel_withdraw`, which races against the user's ability to sign and broadcast when MPC recovers.

The bridge contains no check for MPC liveness, no mechanism to rebuild the PSBT with a refreshed expiry height, and no pause of the `max_btc_tx_pending_sec` countdown during MPC outages.

### Impact Explanation

A user who initiates a Zcash withdrawal during or just before an MPC outage lasting more than `expiry_height_gap` blocks will have their nBTC locked in the bridge in a `PendingVerify` state. The signed transaction is rejected by the Zcash network as expired. The user cannot complete the withdrawal without operator intervention (`cancel_withdraw`), which returns nBTC via `lost_found`. This constitutes a stuck bridge state requiring operator intervention — a Medium-severity impact under the allowed scope.

### Likelihood Explanation

The NEAR Chain Signatures MPC network is an external service that can experience outages. The default `expiry_height_gap` of 1000 Zcash blocks (~20 hours) is not an unreasonably long outage window. Any MPC downtime exceeding this threshold during an active withdrawal triggers the issue. The condition is realistic and has no on-chain mitigation.

### Recommendation

1. Fetch the current Zcash block height at signing time (inside `sign_btc_transaction` or its callback) rather than at PSBT construction time, and rebuild the PSBT with a fresh `expiry_height` if the stored one has expired or is about to expire.
2. Alternatively, expose a permissionless `refresh_expiry_height` entry point that allows a user to reconstruct the PSBT with an updated expiry height when the original is stale.
3. Consider pausing or resetting the `max_btc_tx_pending_sec` countdown when MPC signing failures are detected, so that operator cancellation cannot race against a user who was blocked by MPC downtime.

### Proof of Concept

1. Alice initiates a Zcash withdrawal via `ft_transfer_call`. The bridge fetches `last_block_height = H` and stores `expiry_height = H + 1000` in the PSBT.
2. The MPC service goes offline for 1001+ Zcash blocks.
3. Alice cannot call `sign_btc_transaction` — the MPC call fails or is unavailable.
4. The `max_btc_tx_pending_sec` timer (default 86400 s) elapses; the DAO/Operator may now call `cancel_withdraw`.
5. MPC recovers. Alice calls `sign_btc_transaction`; the MPC signs the stale PSBT.
6. Alice (or a relayer) broadcasts the signed transaction to the Zcash network.
7. The Zcash network rejects the transaction: `expiry_height = H + 1000 < current_height`.

```rust
    pub(crate) fn get_expiry_height(
        &self,
        chain_specific_data: &Option<ChainSpecificData>,
        last_block_height: u32,
    ) -> u32 {
        let expiry_height = if let Some(chain_specific_data) = chain_specific_data {
            chain_specific_data.expiry_height
        } else {
            last_block_height + self.get_config().expiry_height_gap
        };

        require!(
            expiry_height >= last_block_height + self.get_config().expiry_height_gap
                && expiry_height <= last_block_height + 2 * self.get_config().expiry_height_gap,
            format!(
                "Invalid expiry height: {}. Expected value between {} and {}.",
                expiry_height,
                last_block_height + self.get_config().expiry_height_gap,
                last_block_height + 2 * self.get_config().expiry_height_gap
            )
        );

        expiry_height
    }
```
