### Title
Stub `validatePerasCert` Unconditionally Accepts All Peer-Supplied Peras Certificates, Enabling Unauthorized Chain-Selection Manipulation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` implementation is a deliberate stub that returns `Right` (success) for every certificate it receives, performing zero cryptographic or semantic checks. Both production pool-writer paths (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) call this stub directly on inbound peer data. Any unprivileged peer can therefore inject an arbitrary `PerasCert` — with any round number and any boosted-block pointer — that will be unconditionally accepted, stored in the `PerasCertDB`, and used to trigger chain selection with a `perasWeight` boost, potentially causing the node to switch to a non-canonical chain.

---

### Finding Description

**Root cause — stub validator always returns `Right`:**

The universal `BlockSupportsPeras` instance in `SupportsPeras.hs` contains:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature verification, no quorum check, no committee membership check, no round-number sanity check — the function unconditionally wraps the raw peer-supplied `PerasCert` in a `ValidatedPerasCert` and returns it as valid.

**Production inbound path — both pool writers use this stub:**

`makePerasCertPoolWriterFromChainDB` (the production path wired into the `NodeKernel`) passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` calls `validateCert` on every new inbound certificate and, if all pass, calls `addCert` on each: [3](#0-2) 

`addCert` is bound to `ChainDB.addPerasCertAsync chainDB`, which enqueues a `ChainSelAddPerasCert` message: [4](#0-3) 

**Chain-selection consequence:**

`chainSelSync` processes `ChainSelAddPerasCert` by adding the certificate to the `PerasCertDB` and, if the boosted block is present in the `VolatileDB`, immediately triggering `chainSelectionForBlock` for that block with the full `perasWeight` boost (default: 15): [5](#0-4) 

The `PerasWeightSnapshot` used during chain selection is derived from the `PerasCertDB`, so a fake certificate permanently inflates the weight of the attacker-chosen block for the lifetime of that block in the VolatileDB.

---

### Impact Explanation

An unprivileged peer can craft a `PerasCert` pointing to any block hash currently in the target node's VolatileDB. Because `validatePerasCert` never rejects anything, the certificate is stored and the boosted block gains `perasWeight = 15` extra weight in chain selection. If the attacker's chosen block is on a fork that is currently losing chain selection by fewer than 15 units of weight, the node will switch to that fork. This constitutes:

- **Bypass of Peras certificate validation** — the entire cryptographic and committee-membership check is absent, enabling unauthorized certificate acceptance.
- **Chain-selection manipulation** — an honest node can be made to prefer a non-canonical chain solely on the basis of a forged certificate, violating the Peras security assumption that only legitimately quorum-certified blocks receive a boost.

---

### Likelihood Explanation

The attack requires only a network connection to the target node (the object-diffusion mini-protocol is open to any peer) and knowledge of a block hash in the node's VolatileDB (obtainable via the ChainSync protocol). No keys, stake, or privileged access are needed. The stub is present in the production code path (`makePerasCertPoolWriterFromChainDB`) and is explicitly marked as a temporary placeholder pending real plumbing, meaning it is active in any deployment that includes the Peras object-diffusion layer.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that:
1. Verifies the aggregate BLS signature over `(roundNo, boostedBlock)` against the claimed committee members' public keys.
2. Checks that the set of signers constitutes a valid quorum (total stake ≥ threshold + safety margin).
3. Verifies each signer's committee membership and proof of possession.
4. Rejects certificates whose `pcCertRound` is outside the valid window relative to the current slot.

Until real validation is in place, the pool writer should refuse all inbound certificates (return a hard error or silently drop them) rather than unconditionally accepting them. The `TODO` comment references `https://github.com/tweag/cardano-peras/issues/120` as the tracking issue. [6](#0-5) 

---

### Proof of Concept

1. Connect to a target node via the object-diffusion mini-protocol for Peras certificates.
2. Observe (via ChainSync) a block hash `H` on a fork that is currently losing chain selection.
3. Craft a `PerasCert { pcCertRound = r, pcCertBoostedBlock = H }` for any round `r` not already in the node's `PerasCertDB`.
4. Send the certificate to the node.
5. `processCerts` calls `validatePerasCert mkPerasParams cert` → returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })`.
6. `addPerasCertAsync` enqueues `ChainSelAddPerasCert`.
7. `chainSelSync` adds the cert to `PerasCertDB`, finds block `H` in the VolatileDB, and calls `chainSelectionForBlock` for `H` with weight boost 15.
8. If the fork containing `H` was previously losing by < 15 weight units, the node switches to it.

**Expected outcome:** The node adopts a non-canonical chain that it would have rejected without the forged certificate, demonstrating unauthorized chain-selection manipulation by an unprivileged peer.

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
