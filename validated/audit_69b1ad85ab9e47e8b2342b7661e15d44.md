### Title
Peras Certificate Validation Bypass: `validatePerasCert` Unconditionally Accepts All Inbound Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The degenerate `BlockSupportsPeras` instance, which is the active catch-all instance for all block types including `CardanoBlock` until a concrete override is provided, implements `validatePerasCert` as a function that unconditionally returns `Right` without performing any cryptographic or semantic validation. An unprivileged peer can send arbitrarily crafted Peras certificates over the network mini-protocol; every such certificate is accepted, stored in the `PerasCertDB`, and used to compute `PerasWeightSnapshot` values that directly influence chain selection. This is a direct analog to the original report's pattern: a function whose name and type contract promise validation but whose implementation silently omits all required checks, granting unlimited acceptance where restricted acceptance was intended.

### Finding Description

**Root cause — `validatePerasCert` always succeeds:** [1](#0-0) 

The catch-all instance comment explicitly acknowledges this is a placeholder:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No signature verification, no round-number bounds check, no quorum check, no voter eligibility check — the function returns `Right` for every input unconditionally.

**Entry path — inbound certificates from peers:**

The network-facing `processCerts` function is wired to call `validatePerasCert` directly on every certificate batch received from a peer: [2](#0-1) 

```haskell
, opwAddObjects = \certs ->
    processCerts
      systemTime
      (ChainDB.getPerasCertIds chainDB)
      -- TODO replace when actual plumbing is in place
      (validatePerasCert mkPerasParams)
      (void . ChainDB.addPerasCertAsync chainDB)
      certs
```

`processCerts` partitions the batch into valid/invalid using `validateCert`: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is forwarded to `addCert` → `implAddCert` → stored in `PerasCertDB`.

**Chain-selection impact — fake certificates alter `PerasWeightSnapshot`:**

`implGetWeightSnapshot` builds a `PerasWeightSnapshot` from all stored certificates: [4](#0-3) 

`preferAnchoredCandidate` uses this snapshot. When `isEmptyPerasWeightSnapshot weights` is `False` (i.e., after fake certificates have been stored), it switches to the Peras-weighted comparison path instead of the standard longest-chain rule: [5](#0-4) 

An attacker who injects certificates claiming to boost a block on their preferred fork causes the node to compute a higher `WeightedSelectView` for that fork, potentially causing the node to switch to a chain it would otherwise reject under the standard Praos longest-chain rule.

### Impact Explanation

**Severity: Critical** — matches the allowed scope item: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

A single unprivileged peer can:
1. Forge Peras certificates for any block hash and any round number.
2. Transmit them via the existing Peras certificate object-diffusion mini-protocol.
3. Have them unconditionally accepted and stored.
4. Cause the victim node's chain selection to assign artificial Peras boost weight to the attacker's preferred fork, overriding the honest longest-chain preference.

This constitutes a consensus safety failure: an honest node can be made to prefer a non-canonical or adversarially-chosen chain beyond the intended security assumptions of Praos/Peras.

### Likelihood Explanation

**High.** The entry path requires no credentials, no stake, and no key material — only the ability to connect to the node's Peras certificate diffusion endpoint and send a well-formed (but cryptographically unsigned) `PerasCert` object. The degenerate instance is the only active instance for `CardanoBlock` until a concrete override is merged (tracked in the referenced GitHub issue). The network handler is already wired and active.

### Recommendation

1. Remove or gate the degenerate `validatePerasCert` implementation so that it returns `Left PerasValidationErr` (reject-all) rather than `Right` (accept-all) until the real cryptographic validation is implemented.
2. Implement the full certificate validation — aggregate BLS signature verification, round-number range check, quorum threshold check, and voter eligibility check — before merging the concrete `BlockSupportsPeras` instance for `CardanoBlock`.
3. Add a property-based test that confirms `validatePerasCert` rejects certificates with invalid aggregate signatures.

### Proof of Concept

**Deterministic reasoning (no live network required):**

1. Construct any `PerasCert blk` value with an arbitrary `pcRoundNo`, `pcBoostedBlock`, and a zeroed/garbage `pcSignature`.
2. Submit it to a node's Peras certificate diffusion endpoint.
3. `processCerts` calls `validatePerasCert mkPerasParams cert`.
4. `validatePerasCert` pattern-matches on nothing — it immediately returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight params}`.
5. `processCerts` sees `([], [validatedCert])` and calls `addCert (WithArrivalTime now validatedCert)`.
6. `implAddCert` inserts the round number into `pcdsCertIds` and the cert into `pcdsCertsByTicket`.
7. On the next chain-selection trigger, `getWeightSnapshot` returns a non-empty `PerasWeightSnapshot` containing the attacker's boost for `pcBoostedBlock`.
8. `preferAnchoredCandidate` takes the Peras-weighted branch and may prefer the attacker's fork over the honest chain. [6](#0-5) [7](#0-6) [5](#0-4)

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
