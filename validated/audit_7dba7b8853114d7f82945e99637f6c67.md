### Title
Passive UTXO Management Directional Check Without Magnitude Validation Allows UTXO Count to Overshoot Healthy Range - (File: `contracts/satoshi-bridge/src/psbt.rs`)

---

### Summary

The `check_withdraw_psbt_valid` function enforces a directional check on UTXO count changes during user-initiated withdrawals but never validates the magnitude of the change. Any unprivileged user can craft a withdrawal PSBT that satisfies the directional guard while overshooting the healthy UTXO range in the opposite direction, bypassing the bridge's passive UTXO management policy.

---

### Finding Description

In `check_withdraw_psbt_valid`, after computing `utxo_num` (the current pool size before the withdrawal), the contract applies a passive management guard:

```rust
// psbt.rs lines 56-60
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
}
``` [1](#0-0) 

The guard checks only the **sign** of the net UTXO delta (`change_num - input_num`), not its **magnitude**. This is the direct analog of the Lyra `canHedge()` bug: just as `canHedge()` returned `true` whenever a trade moved pool delta in the same direction as `expectedHedge` without checking whether the trade size would overshoot zero and flip the sign of risk, this guard returns `true` whenever the UTXO delta has the correct sign without checking whether the resulting pool size will overshoot the opposite boundary.

The `utxo_num` value is computed as:

```rust
// psbt.rs lines 21-24
let vutxos_len = u32::try_from(vutxos.len())...;
let utxo_num = self.data().utxos.len() + vutxos_len;
``` [2](#0-1) 

Because `generate_vutxos` already removed the input UTXOs from `self.data().utxos` before this call, `utxo_num` equals the **original** pool size. After the withdrawal the pool size becomes `utxo_num − input_num + change_num`. The guard never checks this post-withdrawal value against either boundary.

The user-supplied PSBT inputs and outputs are bounded only by:

```rust
// psbt.rs lines 44-54
require!(change_num <= usize::from(config.max_change_number), ...);
require!(input_num <= usize::from(config.max_withdrawal_input_number), ...);
``` [3](#0-2) 

These per-transaction caps are independent of the healthy range width `upper_limit − lower_limit`, so the net delta can easily exceed the gap between the two limits.

**Concrete overshoot scenario (pool too small):**

| Parameter | Value |
|---|---|
| `passive_management_lower_limit` | 10 |
| `passive_management_upper_limit` | 15 |
| `max_change_number` | 10 |
| Current `utxo_num` | 9 (one below lower limit) |

User submits a withdrawal with `input_num = 1`, `change_num = 10`.
- Guard check: `1 < 10` → **passes**.
- Post-withdrawal pool size: `9 − 1 + 10 = 18` → **above upper limit (15)**.

**Concrete overshoot scenario (pool too large):**

| Parameter | Value |
|---|---|
| `passive_management_lower_limit` | 10 |
| `passive_management_upper_limit` | 15 |
| `max_withdrawal_input_number` | 10 |
| Current `utxo_num` | 16 (one above upper limit) |

User submits a withdrawal with `input_num = 10`, `change_num = 1`.
- Guard check: `10 > 1` → **passes**.
- Post-withdrawal pool size: `16 − 10 + 1 = 7` → **below lower limit (10)**.

The entry path is fully unprivileged: any token holder calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message, which triggers `ft_on_transfer` → `ft_on_transfer_withdraw_chain_specific` → `create_btc_pending_info` → `check_withdraw_psbt_valid`. [4](#0-3) 

---

### Impact Explanation

The bridge's passive UTXO management policy exists to keep the pool within a healthy operating range. Overshooting the opposite boundary:

- **Pool driven below lower limit**: future withdrawals that need multiple inputs may find insufficient UTXOs, causing them to fail or stall until new deposits arrive or an operator performs active management — an attacker-triggered temporary locking of bridged funds.
- **Pool driven above upper limit**: the pool accumulates dust-level UTXOs, increasing signing costs and degrading bridge liveness.

Both outcomes require operator intervention to restore the healthy range, matching the **Medium** impact class: bypass of bridge limits/policies and attacker-triggered temporary locking of bridged funds.

---

### Likelihood Explanation

Any nBTC holder can trigger this during a normal withdrawal. No special role, leaked key, or external dependency is required. The attacker pays only the standard BTC gas fee. The attack is repeatable as long as the pool is near either boundary, which is the normal operating condition the passive management policy is designed to maintain.

---

### Recommendation

After computing the post-withdrawal pool size, assert it remains within the healthy range:

```rust
if utxo_num < config.passive_management_lower_limit {
    require!(input_num < change_num, "require input_num < change_num");
    let new_utxo_num = utxo_num as usize - input_num + change_num;
    require!(
        new_utxo_num <= config.passive_management_upper_limit as usize,
        "withdrawal would overshoot passive_management_upper_limit"
    );
} else if utxo_num > config.passive_management_upper_limit {
    require!(input_num > change_num, "require input_num > change_num");
    let new_utxo_num = utxo_num as usize - input_num + change_num;
    require!(
        new_utxo_num >= config.passive_management_lower_limit as usize,
        "withdrawal would undershoot passive_management_lower_limit"
    );
}
```

### Proof of Concept

1. Bridge is deployed with `passive_management_lower_limit = 10`, `passive_management_upper_limit = 15`, `max_change_number = 10`, `max_withdrawal_input_number = 10`.
2. Pool currently holds 9 UTXOs (one below lower limit).
3. Attacker holds sufficient nBTC and calls `ft_transfer_call` on the nBTC contract with a `Withdraw` message specifying a PSBT that consumes 1 UTXO and produces 10 change outputs.
4. `check_withdraw_psbt_valid` evaluates `utxo_num = 9 < 10` → enters the first branch → checks `1 < 10` → **passes**.
5. Post-withdrawal pool size: `9 − 1 + 10 = 18`, which is 3 above the upper limit.
6. The bridge is now in the "too many UTXOs" regime. A second attacker (or the same one) immediately submits a withdrawal with `input_num = 10`, `change_num = 1` (guard: `10 > 1` → passes), leaving `18 − 10 + 1 = 9` UTXOs — back below the lower limit.
7. By alternating these two withdrawals the attacker keeps the pool perpetually outside the healthy range, forcing the bridge into a degraded state that requires operator intervention to resolve.
