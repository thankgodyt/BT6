### Title
Relayer-Supplied BTC Transaction `output` Field Is Not Validated Against the Intended Recipient — (`File: near/omni-bridge/src/btc.rs`)

### Summary
`submit_transfer_to_utxo_chain_connector` validates only `target_btc_address` from the relayer-supplied `TokenReceiverMessage::Withdraw`, while silently discarding the `input` and `output` fields with wildcard patterns. The raw, unvalidated `msg` (including the `output` entries that determine where Bitcoin actually flows) is forwarded verbatim to the BTC connector. A malicious trusted relayer can pass the on-chain address check while supplying `output` entries whose `script_pubkey` values redirect funds to an attacker-controlled Bitcoin address.

### Finding Description

`TokenReceiverMessage::Withdraw` carries three security-critical fields:

- `target_btc_address` — the intended recipient's Bitcoin address (string)
- `input: Vec<OutPoint>` — UTXOs to spend
- `output: Vec<TxOut>` — actual transaction outputs, each with `value` and `script_pubkey` [1](#0-0) 

In `submit_transfer_to_utxo_chain_connector`, the contract destructures the message and explicitly wildcards both `input` and `output`:

```rust
if let TokenReceiverMessage::Withdraw {
    target_btc_address,
    input: _,
    output: _,
    max_gas_fee,
} = message
{
    require!(
        btc_address == target_btc_address,
        BridgeError::IncorrectTargetUtxoAddress.as_ref()
    );
``` [2](#0-1) 

After this check, the original relayer-supplied `msg` string — which still contains the unvalidated `output` entries — is forwarded verbatim to the BTC connector:

```rust
ext_token::ext(btc_account_id)
    .with_static_gas(FT_TRANSFER_CALL_GAS)
    .ft_transfer_call(self.get_utxo_chain_connector(chain_kind), amount, None, msg)
``` [3](#0-2) 

The BTC connector receives this `msg` and uses the `output` entries to construct the actual Bitcoin transaction. Because the bridge never verifies that any `TxOut.script_pubkey` in `output` corresponds to `target_btc_address`, the relayer can craft a message where:

- `target_btc_address` = the legitimate user's address (passes the `require!` check)
- `output` = `[TxOut { value: full_amount, script_pubkey: <attacker_script> }]`

The Bitcoin transaction is then broadcast with funds going to the attacker.

### Impact Explanation

A malicious trusted relayer can permanently redirect any BTC withdrawal to an attacker-controlled Bitcoin address. The user's nBTC tokens are burned/transferred from the bridge, the transfer record is removed (`self.remove_transfer_message`), and the BTC is sent to the wrong on-chain output. There is no recovery path. This constitutes a direct, permanent loss of bridged funds. [4](#0-3) 

### Likelihood Explanation

The `submit_transfer_to_utxo_chain_connector` function is gated by `#[trusted_relayer]`, which is a role granted by `RelayerManager` — not an admin or DAO role. The objective explicitly lists "custom relayer" and "relayer applicant" as valid attacker types. A relayer that obtains the trusted-relayer role (a realistic operational scenario) can exploit this on any pending BTC withdrawal without any additional privilege escalation. [5](#0-4) 

### Recommendation

After destructuring `TokenReceiverMessage::Withdraw`, validate that at least one `TxOut` in `output` has a `script_pubkey` that encodes `target_btc_address`, and that the sum of matching output values equals the expected transfer amount. Reject the call if no output matches the stored recipient address. The `input` UTXOs should similarly be validated against known/expected UTXOs if the connector tracks them.

### Proof of Concept

1. User initiates a BTC withdrawal: calls `ft_transfer_call` on the nBTC token with `recipient = "btc:bc1q<user_address>"`. A `TransferMessage` is stored with `transfer_id = {origin_chain: Near, origin_nonce: 1}`.

2. Malicious trusted relayer calls `submit_transfer_to_utxo_chain_connector` with:
   ```json
   {
     "transfer_id": { "origin_chain": "Near", "origin_nonce": 1 },
     "msg": "{\"Withdraw\":{\"target_btc_address\":\"bc1q<user_address>\",\"input\":[],\"output\":[{\"value\":7486,\"script_pubkey\":\"<attacker_p2wpkh_script>\"}],\"max_gas_fee\":null}}",
     "fee_recipient": null,
     "fee": null
   }
   ```

3. The bridge checks `btc_address == target_btc_address` → passes (user address matches).

4. `input: _` and `output: _` are ignored. The original `msg` (with attacker's `script_pubkey`) is forwarded to the BTC connector via `ft_transfer_call`.

5. The BTC connector constructs and broadcasts a Bitcoin transaction paying `<attacker_p2wpkh_script>`. The user's funds are permanently lost. [6](#0-5) [7](#0-6)
