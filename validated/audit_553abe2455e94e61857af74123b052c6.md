### Title
`reject_refund` Cannot Cancel an In-Flight Refund After `execute_refund` Has Been Called — (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

The `reject_refund` function is the DAO/Operator's only mechanism to cancel a suspicious or invalid refund request. However, once `execute_refund` has been called by any unprivileged user (after the timelock expires), `reject_refund` only removes the `RefundRequest` record but leaves the `BTCPendingInfo` intact. The MPC signing pipeline then proceeds unimpeded, and `verify_refund_finalize_callback` explicitly tolerates a missing refund request, completing the BTC transfer regardless. The DAO's cancellation power is fully neutralized.

---

### Finding Description

The refund flow has two relevant timelocks:

- `refund_timelock_sec` — for pre-authorized refund addresses embedded in `deposit_msg.refund_address`
- `unsafe_refund_timelock_sec` — a longer window specifically designed to give the DAO/Operator time to reject suspicious requests where the refund address was supplied freely by the caller

Once either timelock expires, `execute_refund` is callable by **anyone** with no access control:

```rust
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn execute_refund(
    &mut self,
    utxo_storage_key: String,
    chain_specific_data: Option<ChainSpecificData>,
) -> PromiseOrValue<()> {
    let timelock_sec = self.resolve_execute_refund_timelock(&utxo_storage_key);
    self.internal_execute_refund(utxo_storage_key, timelock_sec, chain_specific_data)
}
``` [1](#0-0) 

When `execute_refund` succeeds, `finalize_refund_with_psbt` creates a `BTCPendingInfo` entry and inserts the UTXO into `verified_deposit_utxo`, then marks the request `executed = true` and re-saves it. [2](#0-1) 

If the DAO then calls `reject_refund`, the access-control gate allows it (the `is_privileged` path is always open to DAO/Operator regardless of `executed`): [3](#0-2) 

But `internal_reject_refund` only removes the `RefundRequest` from storage and emits an event — it does **not** touch `btc_pending_infos`, `verified_deposit_utxo`, or the account's `btc_pending_sign_ids`:

```rust
pub(crate) fn internal_reject_refund(&mut self, utxo_storage_key: String) {
    require!(
        self.data_mut()
            .refund_requests
            .remove(&utxo_storage_key)
            .is_some(),
        "Refund request not found"
    );
    Event::RefundRejected { utxo_storage_key }.emit();
}
``` [4](#0-3) 

The MPC signing step then proceeds on the surviving `BTCPendingInfo`. When the signed transaction is confirmed on-chain and `verify_refund_finalize_callback` is invoked, it explicitly handles the already-removed request as a harmless no-op and completes successfully:

```rust
// Refund confirmed on-chain → drop the request so no further execute_refund
// is possible. If it was already removed, this is harmlessly a no-op.
self.data_mut()
    .refund_requests
    .remove(&utxo_storage_keys[0]);
``` [5](#0-4) 

The BTC transfer to the user's chosen address completes despite the DAO's rejection.

---

### Impact Explanation

The `unsafe_refund_timelock_sec` window exists precisely to give the DAO time to reject suspicious refund requests — for example, requests where the caller freely supplied a refund address not embedded in the original `deposit_msg`. Once the timelock expires and `execute_refund` is called, the DAO's only intervention tool (`reject_refund`) becomes a no-op against the live MPC pipeline. Any refund request the DAO deems invalid but fails to reject before `execute_refund` is called will complete unconditionally. This is a bypass of the bridge's operator-intervention policy.

**Allowed impact matched**: *Medium — Bypass of bridge limits or policies.*

---

### Likelihood Explanation

The timelock is a publicly observable on-chain timestamp (`created_at_sec` in `RefundRequest`). Any user who submitted a `request_refund` knows exactly when the timelock expires and can call `execute_refund` at that moment. On NEAR, there is no mempool to monitor, but the user does not need to frontrun in the Ethereum sense — they simply need to call `execute_refund` before the DAO calls `reject_refund`. Because the DAO must monitor all pending refund requests and act proactively, a determined user can reliably race the DAO by calling `execute_refund` the instant the timelock expires.

---

### Recommendation

`internal_reject_refund` must be extended to also cancel any in-flight `BTCPendingInfo` associated with the refund when `executed == true`. Specifically:

1. When `executed` is `true`, look up the `BTCPendingInfo` whose PSBT input matches the `utxo_storage_key`.
2. Remove that `BTCPendingInfo` from `btc_pending_infos` and from the account's `btc_pending_sign_ids` / `btc_pending_verify_list`.
3. Remove the UTXO from `verified_deposit_utxo` so a legitimate `verify_deposit` can still proceed if appropriate.

Alternatively, restrict `reject_refund` to only work when `executed == false`, and introduce a separate privileged `cancel_executed_refund` that performs the full teardown atomically.

---

### Proof of Concept

1. User deposits BTC to the bridge-derived address.
2. User calls `request_refund` supplying a freely chosen `refund_address` (no pre-authorization in `deposit_msg`). The request is stored with `executed = false`.
3. `unsafe_refund_timelock_sec` elapses (e.g., 7 days).
4. User calls `execute_refund(utxo_storage_key, ...)`. `finalize_refund_with_psbt` runs: `BTCPendingInfo` is created, UTXO is inserted into `verified_deposit_utxo`, request is re-saved with `executed = true`. [6](#0-5) 
5. DAO observes the suspicious request and calls `reject_refund(utxo_storage_key)`. `internal_reject_refund` removes the `RefundRequest` record and emits `RefundRejected`. The `BTCPendingInfo` is untouched. [4](#0-3) 
6. MPC nodes sign the refund PSBT (the `BTCPendingInfo` is still in `PendingSign` state). The signed transaction is broadcast to Bitcoin.
7. Relayer calls `verify_refund_finalize(tx_id, proof)`. `verify_refund_finalize_callback` runs, finds the refund request already removed, treats it as a no-op, removes the `BTCPendingInfo`, and returns `true`. [7](#0-6) 
8. BTC is delivered to the user's chosen address. The DAO's rejection had no effect.

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```

    pub(crate) fn finalize_refund_with_psbt(
        &mut self,
        caller: AccountId,
        mut refund_request: RefundRequest,
        psbt: PsbtWrapper,
        refund_amount: u128,
        utxo_storage_key: String,
    ) {
        let gas_fee = refund_request.gas_fee;
        let refund_address = refund_request.refund_address.clone();

        let deposit_msg = refund_request.deposit_msg();
        let path = get_deposit_path(&deposit_msg);
        let vutxo = VUTXO::Current(UTXO {
            path,
            tx_bytes: refund_request.tx_bytes.0.clone(),
            vout: refund_request.vout,
            balance: u64::try_from(refund_request.amount)
                .unwrap_or_else(|_| env::panic_str("Amount overflow")),
        });

        let psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();

        if !self.check_account_exists(&caller) {
            self.internal_set_account(&caller, crate::Account::new(&caller));
        }
        self.require_pending_sign_capacity(&caller);

        let btc_pending_info = BTCPendingInfo {
            account_id: caller.clone(),
            btc_pending_id: btc_pending_id.clone(),
            transfer_amount: 0,
            actual_received_amount: refund_amount,
            withdraw_fee: 0,
            gas_fee,
            burn_amount: 0,
            psbt_hex,
            vutxos: vec![vutxo],
            signatures: vec![None; 1],
            tx_bytes_with_sign: None,
            create_time_sec: nano_to_sec(env::block_timestamp()),
            last_sign_time_sec: 0,
            state: PendingInfoState::Refund(OriginalState {
                stage: PendingInfoStage::PendingSign,
                max_gas_fee: gas_fee,
                last_rbf_time_sec: None,
                cancel_rbf_reserved: None,
            }),
        };

        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        self.internal_unwrap_mut_account(&caller)
            .btc_pending_sign_ids
            .insert(btc_pending_id.clone());

        // Mark UTXO as verified to prevent verify_deposit later
        self.data_mut()
            .verified_deposit_utxo
            .insert(utxo_storage_key.clone());

        Event::RefundExecuted {
            utxo_storage_key: utxo_storage_key.clone(),
            amount: refund_request.amount.into(),
            refund_address,
        }
        .emit();

        Event::GenerateBtcPendingInfo {
            account_id: &caller,
            btc_pending_id: &btc_pending_id,
        }
        .emit();

        // Keep the request (so `execute_refund` can be called again to re-create
        // the transaction) but mark it executed; it is removed only when the
        // refund is finalized in `verify_refund_finalize`.
        refund_request.executed = true;
        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());
