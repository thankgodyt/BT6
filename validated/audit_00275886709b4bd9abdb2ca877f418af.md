### Title
Unconditional Peras Certificate and Vote Acceptance Bypasses Cryptographic Validation, Enabling Unauthorized Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance used for all block types implements `validatePerasCert` as an unconditional `Right` (always-accept), performing zero cryptographic verification of the certificate. Simultaneously, `validatePerasVote` only checks stake-distribution membership but never verifies the vote signature. Both functions are wired directly into the live Peras certificate diffusion pipeline (`makePerasCertPoolWriterFromChainDB`) and into the `ChainDB` chain-selection path. An unprivileged peer can therefore inject arbitrary crafted Peras certificates that boost any block of its choosing, causing the receiving node to trigger chain selection for that block and potentially switch to a non-canonical fork.

### Finding Description

**Root cause — `validatePerasCert` always returns `Right`:** [1](#0-0) 

The degenerate instance (marked `TODO: degenerate instance for all blks to get things to compile`) is the only `BlockSupportsPeras` instance in the codebase. It unconditionally wraps any inbound `PerasCert` in `Right ValidatedPerasCert` without checking any cryptographic field.

**Root cause — `validatePerasVote` skips signature verification:** [2](#0-1) 

`validatePerasVote` only calls `lookupPerasVoteStake` to confirm the voter ID exists in the stake distribution. It never calls `verifyVoteSignature` (which is defined and used correctly in the `EveryoneVotes` and `WFALS` committee implementations). Any peer can therefore forge a vote attributed to any registered pool.

**Production wiring — both validators are used in the live ChainDB path:** [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` directly to `processCerts`. Every inbound certificate received from a peer over the Peras certificate diffusion mini-protocol flows through this writer.

**`processCerts` accepts and stores any cert that passes `validateCert`:** [4](#0-3) 

Because `validatePerasCert` never returns `Left`, the `([], validatedCerts)` branch is always taken and every received certificate is forwarded to `addPerasCertAsync`.

**Chain selection is then triggered for the boosted block:** [5](#0-4) 

`chainSelSync` calls `chainSelectionForBlock` for the block named in the attacker-controlled `pcCertBoostedBlock` field. The `WeightedSelectView` then compares chains by total Peras weight: [6](#0-5) 

A crafted certificate with a large `perasWeight` boost for a fork tip can make the node's `preferCandidate` return `ShouldSwitch`, causing the node to abandon its canonical chain.

**End-to-end exploit path:**

1. Attacker connects as an unprivileged peer via the Peras certificate diffusion mini-protocol (`aPerasCertDiffusionClient`/`aPerasCertDiffusionServer`).
2. Attacker sends a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <tip of attacker's fork>`.
3. `processCerts` calls `validatePerasCert mkPerasParams cert` → always `Right`.
4. `addPerasCertAsync chainDB cert` enqueues the cert.
5. `chainSelSync` processes it, calls `chainSelectionForBlock` for the fork tip.
6. `WeightedSelectView.preferCandidate` sees the boosted fork as heavier and switches the node's selection.

### Impact Explanation

**High — chain selection bug enabling non-canonical chain preference.** An unprivileged peer can make an honest node prefer a fork of its choosing by injecting a certificate that artificially boosts the fork's Peras weight. This violates the chain-selection security invariant: the node's selection is no longer determined solely by honest block production and legitimate Peras quorums. If Peras is enabled (the feature flag path), this is a direct consensus safety failure. The `validatePerasVote` bypass additionally allows forged votes to accumulate toward a quorum threshold, compounding the attack.

### Likelihood Explanation

Any peer that can establish a Peras diffusion connection (no privilege required) can trigger this. The Peras diffusion mini-protocol is exposed to all node-to-node peers via `aPerasCertDiffusionServer`/`aPerasCertDiffusionClient`. The attack requires only crafting a valid CBOR-encoded `PerasCert` struct (two fields: a round number and a block point), which is trivially constructable from the public serialisation instance: [7](#0-6) 

The only precondition is that Peras is enabled on the target node. The CHANGELOG confirms the feature is present and wired into chain selection, with the note that it is "disabled by default" — meaning the risk is live for any deployment that enables it.

### Recommendation

1. **Replace the degenerate `validatePerasCert` stub** with a real implementation that verifies the aggregate BLS/committee signature over `(electionId, candidate)` before accepting any certificate, mirroring the `implVerifyCert` logic in `EveryoneVotes` or `WFALS`.
2. **Replace the degenerate `validatePerasVote` stub** with a real implementation that calls `verifyVoteSignature` (already defined in `CryptoSupportsVoteSigning`) before accepting any vote.
3. **Gate the diffusion handlers** so that Peras cert/vote diffusion is only active when Peras is fully enabled and the real validation implementations are in place.
4. **Add integration tests** that send crafted certificates/votes from a simulated malicious peer and assert they are rejected.

### Proof of Concept

```
-- Attacker constructs a minimal crafted certificate:
let craftedCert = PerasCert
      { pcCertRound     = PerasRoundNo 1          -- any round not yet in DB
      , pcCertBoostedBlock = forkTipPoint          -- tip of attacker's fork
      }

-- Attacker sends [craftedCert] over the Peras cert diffusion protocol.
-- On the receiving node:
--   processCerts ... (validatePerasCert mkPerasParams) addCert [craftedCert]
--   => validatePerasCert mkPerasParams craftedCert
--   => Right (ValidatedPerasCert { vpcCert = craftedCert, vpcCertBoost = perasWeight params })
--   => addCert (WithArrivalTime now validatedCert)
--   => addPerasCertAsync chainDB validatedCert
--   => chainSelSync triggers chainSelectionForBlock for forkTipPoint
--   => WeightedSelectView sees fork as heavier => ShouldSwitch
```

The receiving node switches its selection to the attacker's fork without any legitimate quorum having been reached.

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
