Audit Report

## Title
Unchecked Multiplication Overflow in `denormalize_amount` Permanently Freezes Bridged Funds During Inbound Finalization — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`denormalize_amount` performs a bare `u128` multiplication without overflow protection. With `overflow-checks = true` set in the release profile, any overflow causes the NEAR transaction to panic and abort. When triggered inside `fin_transfer_callback`, the foreign-chain tokens are already locked or burned, and the aborted NEAR transaction leaves them permanently frozen with no recovery path.

## Finding Description
The function at `near/omni-bridge/src/lib.rs` lines 2776–2779 is:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount * (10_u128.pow(diff_decimals))   // ← unchecked multiplication
}
``` [1](#0-0) 

`near/Cargo.toml` sets `overflow-checks = true` in the release profile, meaning any arithmetic overflow causes an immediate panic/abort rather than wrapping: [2](#0-1) 

The `Decimals` struct stores both fields as `u8`, so `diff_decimals` can range from 0 to 255: [3](#0-2) 

`denormalize_amount` is called unconditionally in three places:

1. `fin_transfer_callback` (line 725) — the primary inbound finalization handler: [4](#0-3) 

2. `fast_fin_transfer` (lines 770–771): [5](#0-4) 

3. `claim_fee_callback` (lines 1122–1127): [6](#0-5) 

The overflow threshold is `u128::MAX / 10^diff_decimals`. For `diff_decimals = 38`, this is approximately 3 tokens; for `diff_decimals = 30`, approximately 340 million tokens. No guard exists between proof verification and the multiplication call. There is no rollback or refund mechanism on the foreign chain side once the inbound proof is submitted.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds**. The inbound bridge flow locks or burns tokens on the foreign chain before the NEAR-side `fin_transfer_callback` executes. If the callback panics due to overflow, the NEAR transaction is aborted, but the foreign-chain lock/burn is irreversible. Every subsequent finalization attempt for the same transfer reproduces the identical overflow, making the freeze permanent. This matches the Critical allowed impact: *permanent freezing of bridged funds across NEAR, EVM, Solana, or other supported chains*.

## Likelihood Explanation
The amount is entirely user-controlled — the user chooses how many tokens to send on the foreign chain. The `Decimals` struct permits any `u8` value for both fields, so tokens with large `diff_decimals` are representable and registerable. For tokens where `diff_decimals ≥ 30`, the overflow is reachable with amounts in the hundreds-of-millions range, which is realistic for high-supply tokens. The relayer is the proximate caller of `fin_transfer`, but the root cause is the user's transfer amount combined with the registered decimal configuration. The vulnerability is repeatable: every finalization attempt for the overflowing transfer will panic identically.

## Recommendation
Replace the bare multiplication with `checked_mul` and propagate the error gracefully:

```rust
fn denormalize_amount(amount: u128, decimals: Decimals) -> Option<u128> {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount.checked_mul(10_u128.pow(diff_decimals))
}
```

All three call sites (`fin_transfer_callback`, `fast_fin_transfer`, `claim_fee_callback`) must handle `None` by returning an error or emitting a refund event rather than panicking, so that the NEAR transaction fails cleanly without permanently locking foreign-chain funds. Additionally, consider enforcing an upper bound on `diff_decimals` during token registration to prevent extreme configurations.

## Proof of Concept
1. Register a token with `origin_decimals = 38`, `decimals = 0` (`diff_decimals = 38`).
2. User sends 4 units of that token on the EVM chain → tokens locked in EVM bridge contract.
3. Relayer submits proof to NEAR `fin_transfer`.
4. `fin_transfer_callback` computes `denormalize_amount(4, Decimals { decimals: 0, origin_decimals: 38 })` = `4 * 10^38` = `4 × 10^38 > u128::MAX (~3.4 × 10^38)`.
5. With `overflow-checks = true`, the NEAR runtime aborts the transaction with a panic.
6. The EVM tokens remain locked forever; every subsequent finalization attempt reproduces the same overflow.

A minimal unit test to reproduce:
```rust
#[test]
#[should_panic]
fn test_denormalize_overflow() {
    let decimals = Decimals { decimals: 0, origin_decimals: 38 };
    let _ = Contract::denormalize_amount(4, decimals); // panics: 4 * 10^38 > u128::MAX
}
```
