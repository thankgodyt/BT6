### Title
`migrate_deployed_token` Does Not Enforce Completion of Pending Outbound Transfers Before Remapping Token State, Permanently Freezing User Funds - (File: near/omni-bridge/src/lib.rs)

### Summary
`Contract::migrate_deployed_token` atomically removes all routing state for `old_token` and replaces it with `new_token`, but performs no check—and provides no documentation warning—that all pending outbound transfers referencing `old_token` must be completed first. Any in-flight outbound transfer whose `TransferMessage.token` encodes `old_token` becomes permanently unresolvable: `sign_transfer` will panic because the `token_id_to_address` entry for `(destination_chain, old_token)` has been deleted, and no public cancellation path exists to refund the locked NEP-141 tokens to users.

### Finding Description

`migrate_deployed_token` performs the following state mutations atomically:

1. Removes `old_token` from `deployed_tokens` and `deployed_tokens_v2`.
2. **Removes** `token_id_to_address[(origin_chain, old_token)]`.
3. Inserts `token_id_to_address[(origin_chain, new_token)] = origin_address`.
4. Overwrites `token_address_to_id[origin_address] = new_token`.
5. Records `migrated_tokens[old_token] = new_token`. [1](#0-0) 

After step 2, any `TransferMessage` stored in `pending_transfers` whose `token` field is `OmniAddress::Near(old_token)` becomes permanently unresolvable. When a relayer calls `sign_transfer` for such a transfer:

```
sign_transfer
  → get_token_id(&transfer_message.token)   // returns old_token
  → get_token_address(destination_chain, old_token)
      // looks up token_id_to_address[(destination_chain, old_token)]
      // → None  (entry was deleted by migrate_deployed_token)
  → env::panic_str(BridgeError::FailedToGetTokenAddress)
``` [2](#0-1) 

The NEP-141 tokens were already transferred into the bridge contract at `init_transfer` time and are held there. There is no public `cancel_transfer` or user-callable refund path. The only escape would be a separate DAO call to `transfer_token_as_dao`, which is an out-of-band emergency action not guaranteed to be taken.

Additionally, `migrate_deployed_token` does not migrate the `locked_tokens` entry: `locked_tokens[(origin_chain, old_token)]` retains its old value while `locked_tokens[(origin_chain, new_token)]` is never created, permanently corrupting the locked-token accounting for `new_token`. [3](#0-2) 

Unlike the external report's analog, the NEAR bridge does not even include a NatSpec/doc comment warning that pending transfers must be drained before calling this function. The prerequisite is entirely undocumented and unenforced.

### Impact Explanation

Any user who initiated an outbound transfer (`ft_on_transfer` → `init_transfer`) for `old_token` before `migrate_deployed_token` is called, and whose transfer has not yet been signed and finalized on the destination chain, permanently loses their bridged tokens. The tokens are locked inside the bridge contract with no on-chain mechanism to recover them without additional DAO intervention. This constitutes permanent freezing of bridged funds. [4](#0-3) 

### Likelihood Explanation

Likelihood is **Low**. The DAO must call `migrate_deployed_token` while at least one pending outbound transfer for `old_token` exists. This requires either an honest operational mistake (forgetting to drain pending transfers before migrating) or a malicious/compromised DAO. Token migrations are infrequent but real operational events (evidenced by the existence of the function and the `migrated_tokens` map in production state). The absence of any warning or guard makes an honest mistake plausible.

### Recommendation

Before executing the token remapping, verify that no pending outbound transfers reference `old_token`. This can be enforced by:

1. Adding a storage variable or flag (e.g., a counter of pending transfers per token) that is incremented on `init_transfer` and decremented on `sign_transfer_callback` / cancellation, and requiring it to be zero before `migrate_deployed_token` proceeds.
2. Alternatively, add a `locked_tokens` check: require `locked_tokens[(origin_chain, old_token)] == 0` as a proxy for no in-flight transfers, and migrate the entry to `new_token` atomically.
3. At minimum, migrate the `locked_tokens` entry from `old_token` to `new_token` inside `migrate_deployed_token` to prevent accounting corruption.

### Proof of Concept

1. User calls `ft_transfer_call` on `old_token` contract → bridge's `ft_on_transfer` → `init_transfer`. A `TransferMessage { token: OmniAddress::Near(old_token), ... }` is stored in `pending_transfers`. The NEP-141 tokens are now held by the bridge. [5](#0-4) 

2. DAO calls `migrate_deployed_token(origin_chain, old_token, new_token)`. The mapping `token_id_to_address[(destination_chain, old_token)]` is deleted. [6](#0-5) 

3. Relayer calls `sign_transfer` for the pending transfer. `get_token_address(destination_chain, old_token)` returns `None`. The call panics with `ERR_FAILED_TO_GET_TOKEN_ADDRESS`. [2](#0-1) 

4. The user's tokens remain locked in the bridge contract indefinitely. No public function allows the user to reclaim them. The pending transfer entry in `pending_transfers` is never removed. [7](#0-6)

    #[access_control_any(roles(Role::DAO))]
    #[payable]
    pub fn migrate_deployed_token(
        &mut self,
        origin_chain: ChainKind,
        old_token: AccountId,
        new_token: AccountId,
    ) {
        require!(
            env::attached_deposit() >= NEP141_DEPOSIT,
            BridgeError::NotEnoughAttachedDeposit.as_ref()
        );

        require!(
            self.deployed_tokens.remove(&old_token),
            BridgeError::OldTokenNotDeployed.as_ref(),
        );
        require!(
            self.deployed_tokens.insert(&new_token),
            BridgeError::TokenExists.as_ref()
        );
        self.deployed_tokens_v2.remove(&old_token);
        self.deployed_tokens_v2.insert(&new_token, &origin_chain);

        let origin_address = self
            .token_id_to_address
            .remove(&(origin_chain, old_token.clone()))
            .near_expect(BridgeError::FailedToGetTokenAddress);

        require!(
            self.token_id_to_address
                .insert(&(origin_chain, new_token.clone()), &origin_address)
                .is_none(),
            BridgeError::TokenExists.as_ref()
        );

        self.token_address_to_id
            .insert(&origin_address, &new_token)
            .near_expect(BridgeError::ExpectedToOverwriteTokenAddress);

        require!(
            self.migrated_tokens
                .insert(&old_token, &new_token)
                .is_none(),
            BridgeError::TokenAlreadyMigrated.as_ref()
        );

        ext_token::ext(new_token.clone())
            .with_static_gas(STORAGE_DEPOSIT_GAS)
            .with_attached_deposit(NEP141_DEPOSIT)
            .storage_deposit(&env::current_account_id(), Some(true))
            .detach();

        env::log_str(
            &OmniBridgeEvent::MigrateTokenEvent {
                old_token_id: old_token,
                new_token_id: new_token,
            }
            .to_log_string(),
        );
    }
