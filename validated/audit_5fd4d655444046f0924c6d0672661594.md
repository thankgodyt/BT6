### Title
`checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot` During Forecast-Horizon Blocking, Enabling Incorrect Chain Selection Under Peras — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer sends a header whose slot is beyond the local forecast horizon, the ChainSync client blocks in `readLedgerStateHelper` waiting for the local chain to advance. During that wait it calls `checkPreferTheirsOverOurs` to decide whether to keep waiting or disconnect. That function invokes `preferAnchoredCandidate` with a **hardcoded `emptyPerasWeightSnapshot`** instead of the live Peras weight snapshot from the ChainDB. When Peras is active, this makes the comparison blind to certificate-based block boosts, so the node can be made to disconnect from peers offering the canonical Peras-boosted chain, or to keep waiting for a non-canonical chain that is merely longer by block count.

---

### Finding Description

The vulnerable path is:

```
rollForward → checkTime → readLedgerStateHelper
                              └─ checkPreferTheirsOverOurs   ← uses emptyPerasWeightSnapshot
```

Inside `readLedgerStateHelper` (an STM `retry` loop), when `projectLedgerView` returns `Nothing` (slot is outside the forecast range), the code calls `checkPreferTheirsOverOurs` before issuing `retry`:

```haskell
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
  Just ledgerView ->
    return $ return $ Intersects kis' ledgerView
```

`checkPreferTheirsOverOurs` is:

```haskell
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← hardcoded, ignores live Peras boosts
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

`preferAnchoredCandidate` with `emptyPerasWeightSnapshot` falls into the `isEmptyPerasWeightSnapshot` fast path and compares chains **purely by block number** (length), completely ignoring any Peras certificate weight accumulated on either fragment. The live snapshot is available in the ChainDB via `getPerasWeightSnapshot` (an STM action) and is already used everywhere else in chain selection.

The entire `checkTime` call is wrapped in `pauseBucket`, which suspends the LoP token-bucket for the duration of the wait. This means the peer is not penalised for the time the node spends blocked at the forecast horizon, making the window for exploitation unbounded in time.

---

### Impact Explanation

**Scenario A — adversary keeps a non-canonical chain alive:**
An adversary sends a header for a slot just beyond the forecast horizon, advertising a chain that is longer by block number but carries zero Peras boosts. `checkPreferTheirsOverOurs` (using empty weights) concludes the adversary's chain is preferable and issues `retry`, keeping the node blocked waiting for that chain indefinitely (LoP is paused). The canonical chain, which is shorter by block number but heavier due to Peras certificates, would cause `checkPreferTheirsOverOurs` to fire `CandidateTooSparse` and disconnect the honest peer. The node is thus steered toward the adversary's non-canonical chain.

**Scenario B — honest peer incorrectly disconnected:**
An honest peer's chain is Peras-boosted (heavier) but has fewer blocks than the local selection. When that peer's header lands beyond the forecast horizon, `checkPreferTheirsOverOurs` sees only block numbers, concludes the peer's chain is not preferable, and throws `CandidateTooSparse`, disconnecting the honest peer. The node loses its path to the canonical chain.

Both scenarios constitute a **chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain**, matching the High impact tier.

---

### Likelihood Explanation

- Any peer can send a header for a slot beyond the current forecast horizon; no special privilege is required.
- The LoP bucket is explicitly paused during `checkTime`, so the adversary pays no patience cost while the node is blocked.
- The bug is latent until Peras is activated on mainnet; once active, every syncing node that encounters a header beyond the forecast horizon is exposed.
- The TODO comment (`https://github.com/tweag/cardano-peras/issues/64`) confirms the developers are aware the check is incorrect but have not yet removed or fixed it.

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from the ChainDB. Because `readLedgerStateHelper` already executes inside an STM transaction, and `getPerasWeightSnapshot` is an `STM m` action, the fix is straightforward:

```haskell
checkPreferTheirsOverOurs kis = do
  weights <- forgetFingerprint <$> getPerasWeightSnapshot  -- read live snapshot
  let result = preferAnchoredCandidate (configBlock cfg) weights ourFrag theirFrag
  unless (shouldSwitch result) $
    throwSTM $ CandidateTooSparse ...
```

This aligns the forecast-horizon guard with the chain-selection logic in `ChainSel.hs`, which already uses the live `PerasWeightSnapshot`.

### Proof of Concept

1. Peras is active; several blocks on the canonical chain carry certificate boosts, making it heavier than a competing fork of equal or greater length.
2. Adversary peer A advertises a tip whose slot is just beyond the local forecast horizon. Its chain is one block longer than the canonical chain but carries no Peras boosts.
3. Honest peer B advertises the canonical chain, which is shorter by one block but heavier due to Peras boosts. Its tip slot is also beyond the forecast horizon.
4. For peer A: `checkPreferTheirsOverOurs` computes `preferAnchoredCandidate … emptyPerasWeightSnapshot`; the adversary's chain wins on block number → `pure ()` → node keeps waiting.
5. For peer B: same computation; the canonical chain loses on block number → `throwSTM CandidateTooSparse` → honest peer disconnected.
