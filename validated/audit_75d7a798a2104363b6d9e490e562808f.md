### Title
Incorrect unit comparison in `stakeAboveThreshold` allows Peras quorum bypass — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value (which may carry un-normalized, absolute ledger stake) directly against `perasQuorumStakeThreshold` (a relative `Rational` value, e.g. `3/4`). The normalization step that would convert absolute stake into a relative fraction is explicitly acknowledged as missing in the source code. This is the direct analog of the QuantAMM report: two quantities that represent the same logical value but in different "units" (packed vs. unpacked length there; absolute vs. relative stake here) are compared without conversion, making the check produce incorrect results.

### Finding Description

In `SupportsPeras.hs`, the `PerasVoteStake` type carries a `Rational` that the code itself describes as an unresolved approximation:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
--
-- So, for now you can consider this 'Rational' as the best approximation we
-- have at the moment of the concrete type for a relative vote stake that can be
-- compared to the quorum threshold value (also currently a 'Rational').
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [1](#0-0) 

The quorum gate that decides whether to forge a certificate is:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. ...
-- Under the current implementation of 'PerasParams', this function only
-- makes sense when both values are relative (normalized) values, so we
-- should either normalize the 'PerasVoteStake' before calling this function,
-- or change this function to accept a stake distribution and perform the
-- normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

The default parameters set the threshold to a relative value:

```haskell
perasQuorumStakeThreshold = PerasQuorumStakeThreshold (3 / 4)
perasQuorumStakeThresholdSafetyMargin = PerasQuorumStakeThresholdSafetyMargin (2 / 100)
``` [3](#0-2) 

`stakeAboveThreshold` is called from `votesReachQuorum`, which is the gate that triggers certificate forging:

```haskell
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [4](#0-3) 

The `PerasVoteStakeDistr` that supplies the per-voter `PerasVoteStake` values is populated externally via `getStakeDistrSTM` in the production vote-pool writers:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

If the `PerasVoteStake` values stored in that distribution are absolute ledger stake (e.g. lovelace, which is on the order of billions), then `stake >= 0.77` is trivially true for every voter, and the quorum check passes after a single vote. If they are relative but not normalized to sum to 1 across the committee, the threshold is still wrong. The code explicitly states the normalization is missing and deferred.

A compounding issue is that `validatePerasCert` is currently a stub that unconditionally returns `Right`, meaning any certificate forged under the broken quorum check is accepted by all receiving nodes without further scrutiny:

```haskell
-- TODO: perform actual validation against all possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [6](#0-5) 

### Impact Explanation

Peras certificates boost the chain-selection weight of the block they reference by `perasWeight` (currently 15). If the quorum check always passes, a single voter can cause a local node to forge a certificate for any block after receiving just one vote. Because `validatePerasCert` is a stub that accepts all certificates, every other node that receives a block containing this certificate will also accept it and apply the weight boost. An adversary with any positive stake can therefore steer chain selection toward an arbitrary block, causing honest nodes to prefer a non-canonical or adversarially chosen chain beyond the intended security assumptions of the Peras protocol.

### Likelihood Explanation

The code is in production source files (not tests or mocks), is wired into the live vote-diffusion pipeline via `makePerasVotePoolWriterFromChainDB`, and uses `mkPerasParams` with the relative `3/4` threshold. The unit mismatch is self-documented as unresolved. Any peer that is a registered stake pool operator (an unprivileged network participant) can send a single vote message to trigger the broken quorum path. No key compromise, admin access, or stake majority is required.

### Recommendation

1. **Normalize `PerasVoteStake` before comparison.** Before calling `stakeAboveThreshold`, divide each voter's absolute ledger stake by the total stake of the committee to produce a value in `[0,1]`. Alternatively, change `stakeAboveThreshold` to accept the total committee stake and perform the normalization internally, removing the implicit unit assumption.

2. **Implement `validatePerasCert`.** The stub that unconditionally returns `Right` must be replaced with a real check that verifies the certificate's aggregate BLS signature and that the claimed voters collectively hold stake above the quorum threshold.

3. **Add a type-level distinction** between absolute and relative stake (e.g., `AbsoluteStake` vs `RelativeStake` newtypes) so the compiler enforces that only normalized values reach `stakeAboveThreshold`.

### Proof of Concept

1. Configure a private testnet with the Peras extension enabled and `mkPerasParams` defaults (`perasQuorumStakeThreshold = 3/4`).
2. Register a stake pool with any positive stake (e.g., 1 ADA = 1,000,000 lovelace).
3. Send a single `PerasVote` message targeting an arbitrary block to a node running `makePerasVotePoolWriterFromChainDB`.
4. The node calls `validatePerasVote`, which looks up the voter's `PerasVoteStake` from `PerasVoteStakeDistr`. If the distribution holds absolute lovelace values, `vpvVoteStake = 1_000_000`.
5. `stakeAboveThreshold` evaluates `1_000_000 >= 3/4 + 2/100 = 0.77` → `True`.
6. `votesReachQuorum` returns `Just`, a certificate is forged for the targeted block, and the block receives a weight boost of 15.
7. Any peer receiving a block containing this certificate passes `validatePerasCert` (stub returns `Right`) and applies the boost, preferring the adversarially chosen chain.
