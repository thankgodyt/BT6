Audit Report

## Title
Non-Atomic `burn.and(mint)` with No Failure Callback in `swap_migrated_token` Causes Permanent Fund Loss or Unauthorized Minting — (File: `near/omni-bridge/src/lib.rs`)

## Summary
`swap_migrated_token` dispatches `burn` and `mint` as parallel, independent NEAR action receipts via `Promise::and()`. Because `ft_on_transfer` immediately returns `U128(0)` and the combined promise is `.detach()`ed, any asymmetric failure between the two receipts is undetectable and unrecoverable: a failed `mint` after a successful `burn` permanently destroys the user's old tokens with no new tokens issued, and a failed `burn` after a successful `mint` produces unauthorized token inflation.

## Finding Description
In `ft_on_transfer`, the `SwapMigratedToken` branch calls `self.swap_migrated_token(sender_id, token_id, amount).detach()` and returns `PromiseOrPromiseIndexOrValue::Value(U128(0))`. The NEP-141 `ft_transfer_call` protocol interprets a return of `0` as "all tokens consumed by the callee," so no refund of old tokens is possible from this point forward regardless of what happens next.

Inside `swap_migrated_token`, `burn.and(mint)` schedules two cross-contract calls as independent action receipts. In NEAR Protocol, `Promise::and()` does not provide atomicity: both receipts are dispatched and execute independently. A panic in `mint` (e.g., storage not registered on the new token contract, gas exhaustion, or a bug in the new token's `mint` implementation) does not cancel or roll back the already-dispatched `burn` receipt. Because the promise is `.detach()`ed, there is no `#[private]` callback that could observe the failure and issue a refund or re-mint. The `ext_token` trait confirms both `burn` and `mint` are genuine cross-contract calls.

## Impact Explanation
- **Primary (fund loss):** If `mint` fails after `burn` succeeds, the user's old tokens are permanently destroyed with zero new tokens issued — direct, irreversible loss of bridged funds. This matches the critical impact class: *permanent loss of bridged funds*.
- **Secondary (unauthorized minting):** If `burn` fails while `mint` succeeds, the user receives new tokens without surrendering old ones, inflating the new token supply and breaking the 1:1 migration invariant. This matches the critical impact class: *unauthorized minting of bridged funds*.

## Likelihood Explanation
The entry point (`old_token.ft_transfer_call → ft_on_transfer` with `SwapMigratedToken`) requires no privilege — any token holder can trigger it. The `mint` call fails under realistic, non-adversarial conditions: (1) the bridge contract has not called `storage_deposit` on the new token contract before the migration goes live — a common operational gap; (2) insufficient prepaid gas causes the `mint` receipt to fail while the `burn` receipt (dispatched in parallel) succeeds independently. Neither condition requires attacker sophistication; the first can occur on any migration deployment.

## Recommendation
Replace the parallel `burn.and(mint)` pattern with a sequential, callback-guarded chain:
1. Call `burn` with explicit gas (`.with_static_gas(BURN_TOKEN_GAS)`).
2. In a `#[private]` callback, check `PromiseResult` for the burn; only if it succeeded, call `mint` with explicit gas.
3. In a second `#[private]` callback, check `PromiseResult` for the mint; if it failed, re-mint the old tokens back to the user or store a claimable refund record.

Do not `.detach()` the promise chain. Ensure the bridge has a storage deposit on the new token contract before enabling the migration path.

## Proof of Concept
1. Admin registers migration: `migrated_tokens[old_token] = new_token`.
2. Bridge contract has **not** called `storage_deposit` on `new_token` for itself.
3. User calls `old_token.ft_transfer_call(bridge, amount, msg: "SwapMigratedToken")`.
4. `ft_on_transfer` returns `U128(0)` — old tokens are irrevocably consumed by the bridge.
5. `swap_migrated_token` dispatches `burn.and(mint).detach()`.
6. `burn` receipt executes on `old_token`: bridge's balance is destroyed. ✓
7. `mint` receipt executes on `new_token`: panics with "account not registered" (no storage deposit). ✗
8. No callback exists; failure is silently dropped.
9. User has lost `amount` of `old_token` and received 0 `new_token`. Funds are permanently destroyed.
