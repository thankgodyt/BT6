Audit Report

## Title
Reentrancy in `initTransfer1155` via Malicious ERC1155 Callback Allows Fraudulent `InitTransfer` Events Without Locking Tokens — (`evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer1155` makes an external call to an attacker-controlled ERC1155 token contract (`safeTransferFrom`) before emitting `InitTransfer`. Because there is no reentrancy guard, a malicious ERC1155 token can re-enter `initTransfer1155` during the callback, causing multiple `InitTransfer` events with distinct nonces to be emitted while zero tokens are actually locked. The NEAR side treats every such event as proof of locked funds and mints bridge tokens accordingly, violating the core event–transfer atomicity invariant.

## Finding Description

`initTransfer1155` executes in this order:

1. `currentOriginNonce += 1` (line 448) — state mutated
2. `IERC1155(tokenAddress).safeTransferFrom(msg.sender, address(this), tokenId, amount, "")` (lines 458–464) — **external call to attacker-controlled contract**
3. `initTransferExtension(...)` (lines 468–478)
4. `emit BridgeTypes.InitTransfer(...)` (lines 480–489)

The contract has no `ReentrancyGuard` and no `nonReentrant` modifier on `initTransfer1155`. The only reentrancy defense is the `onERC1155Received` guard at lines 522–535, which rejects transfers where `operator != address(this)`. However, this guard is ineffective against a malicious token because:

- The bridge itself calls `safeTransferFrom`, making `operator = address(bridge)`.
- A malicious token's `safeTransferFrom` can re-enter `initTransfer1155` before calling `onERC1155Received`.
- In the re-entrant call, the bridge again calls `safeTransferFrom` on the malicious token; the malicious token calls `onERC1155Received(bridge, ...)` with `operator = bridge` — the guard passes — and returns normally.
- The re-entrant call emits `InitTransfer` with nonce N+2 without any tokens being transferred.
- Control returns to the outer `safeTransferFrom`; the malicious token calls `onERC1155Received` for the outer call (operator = bridge, guard passes).
- The outer call emits `InitTransfer` with nonce N+1.

The malicious token never needs to transfer any tokens. `onERC1155Received` only checks the operator identity and returns the selector — it does not verify that tokens were actually received.

`logMetadata1155` is fully permissionless (lines 234–270): no role check, no whitelist. Any attacker can register a malicious ERC1155 token. The NEAR `fin_transfer_callback` (lines 705–718) validates only that the emitter is a registered factory and that `token_decimals` are registered — both conditions are satisfied after `logMetadata1155` is processed by the relayer. The NEAR side does not deduplicate by `origin_nonce` from the EVM side; each distinct nonce is processed as a separate transfer.

This directly violates the documented invariant in `evm/CLAUDE.md` line 36: *"InitTransfer must only be emitted in a code path where tokens have already been burned/locked in the same transaction."*

## Impact Explanation

Every fraudulent `InitTransfer` event emitted by the bridge contract is indistinguishable from a legitimate one on the NEAR side. NEAR mints bridge tokens for each event. The attacker receives N×amount bridge tokens while locking zero ERC1155 tokens on EVM. This constitutes **unauthorized minting of bridged funds** — a Critical impact under the allowed scope. If the minted bridge token has market value or is used as collateral, the attacker profits directly. If legitimate ERC1155 deposits accumulate later, the inflated NEAR-side supply enables redemption of more tokens than were ever deposited — direct theft of bridged funds.

## Likelihood Explanation

The attack requires no privileged role and is fully self-contained:
1. Deploy a malicious ERC1155 contract (trivial, gas only).
2. Call `logMetadata1155` (permissionless, no access control).
3. Wait for the NEAR relayer to process the `LogMetadata` event and register token decimals.
4. Call `initTransfer1155` with the malicious token address.

This is repeatable indefinitely by any EVM user.

## Recommendation

Add `ReentrancyGuardUpgradeable` to `OmniBridge` and apply `nonReentrant` to `initTransfer1155`, `initTransfer`, and `finTransfer`:

```solidity
import {ReentrancyGuardUpgradeable} from
    "@openzeppelin/contracts-upgradeable/utils/ReentrancyGuardUpgradeable.sol";

contract OmniBridge is
    UUPSUpgradeable,
    AccessControlUpgradeable,
    SelectivePausableUpgradable,
    ReentrancyGuardUpgradeable,
    IERC1155Receiver
{
    function initTransfer1155(...) external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
    function initTransfer(...)    external payable nonReentrant whenNotPaused(PAUSED_INIT_TRANSFER) { ... }
    function finTransfer(...)     external payable nonReentrant whenNotPaused(PAUSED_FIN_TRANSFER)  { ... }
}
```

Add `__ReentrancyGuard_init()` to the `initialize` function and decrease `__gap` by 1 slot to preserve storage layout.

## Proof of Concept

```solidity
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.24;

import {IERC1155Receiver} from "@openzeppelin/contracts/token/ERC1155/IERC1155Receiver.sol";

interface IOmniBridge {
    function initTransfer1155(
        address tokenAddress, uint256 tokenId, uint128 amount,
        uint128 fee, uint128 nativeFee,
        string calldata recipient, string calldata message
    ) external payable;
}

contract MaliciousERC1155 {
    IOmniBridge public bridge;
    uint256 public depth;

    constructor(address _bridge) { bridge = IOmniBridge(_bridge); }

    function safeTransferFrom(
        address, address, uint256 tokenId, uint256, bytes calldata
    ) external {
        if (depth < 3) {
            depth++;
            // Re-enter: gets a new nonce, emits InitTransfer, locks zero tokens
            bridge.initTransfer1155(address(this), tokenId, 1, 0, 0, "attacker.near", "");
            depth--;
        }
        // operator = msg.sender = bridge address → passes onERC1155Received guard
        IERC1155Receiver(msg.sender).onERC1155Received(msg.sender, address(this), tokenId, 1, "");
    }

    function balanceOf(address, uint256) external pure returns (uint256) { return 1e18; }
    function isApprovedForAll(address, address) external pure returns (bool) { return true; }
    function setApprovalForAll(address, bool) external {}
    function supportsInterface(bytes4) external pure returns (bool) { return true; }
}
```

**Steps:**
1. Deploy `MaliciousERC1155(bridgeAddress)`.
2. Call `bridge.logMetadata1155(maliciousToken, tokenId)` — permissionless.
3. Wait for NEAR relayer to register the token and its decimals.
4. Call `bridge.initTransfer1155(maliciousToken, tokenId, 1, 0, 0, "attacker.near", "")`.
5. Reentrancy fires: 3 `InitTransfer` events emitted (nonces N+1, N+2, N+3) while zero tokens are locked.
6. NEAR processes all three events and mints 3× bridge tokens to `attacker.near`. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
