### Title
Orchard Bundle Action-Count Check Permanently Rejects All Standard Shielded Withdrawals and Refunds — (`contracts/satoshi-bridge/src/zcash_utils/orchard_policy.rs`)

### Summary

`EXPECTED_ACTIONS_NUMBER = 1` is enforced as an **exact equality** against `bundle.actions().len()`, but the Orchard protocol's own builder always pads bundles to a minimum of 2 actions (`MIN_ACTIONS = 2`, referenced in the code's own comment). Every Orchard bundle produced by standard Zcash tooling has at least 2 actions and is unconditionally rejected.

### Finding Description

`EXPECTED_ACTIONS_NUMBER` is declared as `1`: [1](#0-0) 

The comment on lines 13–15 explicitly acknowledges that the Orchard builder pads to a minimum for privacy and links to `orchard/src/builder.rs#L36` — the `MIN_ACTIONS = 2` constant. Despite this, the constant is set to `1` and the check is strict equality (`!=`), not a minimum: [2](#0-1) 

`extract_orchard_bundle` is called unconditionally from `PsbtWrapper::new`, which panics on error: [3](#0-2) 

`PsbtWrapper::new` is invoked in both the withdrawal callback and the refund callback: [4](#0-3) [5](#0-4) 

### Impact Explanation

Any user submitting an Orchard bundle built with standard Zcash tooling (which always produces ≥ 2 actions) will trigger the panic `ERR_INVALID_ORCHARD_BUNDLE` in both the withdrawal and shielded-refund paths. The shielded path is **permanently and completely broken** for all standard wallets.

However, the impact is bounded:

- **Withdrawals**: The panic occurs inside `ft_on_transfer_callback`, a promise callback. Under NEAR's NEP-141 `ft_transfer_call` semantics, a failed callback causes the FT contract to refund the nZEC tokens to the sender. No permanent loss of funds.
- **Refunds**: The panic occurs inside `execute_refund_callback`. The user can retry with a transparent (non-shielded) refund by omitting `chain_specific_data`. No permanent loss of funds.
- The transparent withdrawal and refund paths remain fully functional.

There is no theft, unauthorized minting, or permanent locking of funds. The impact is a **permanent, publicly reachable DoS on the shielded path** for all users of standard Zcash wallets.

### Likelihood Explanation

Likelihood is **certain** for any user attempting a shielded withdrawal or refund with a standard Zcash wallet. The Orchard builder's `MIN_ACTIONS = 2` is a protocol-level invariant, not a configuration choice. Every standard bundle will have 2 actions and fail the `!= 1` check.

### Recommendation

Change `EXPECTED_ACTIONS_NUMBER` to `2` to match the Orchard builder's actual minimum, and change the check from exact equality (`!=`) to a minimum check (`<`) if bundles with more than 2 actions should also be accepted. Additionally, update `shielded_refund_min_fee` in `refund.rs` (which uses `EXPECTED_ACTIONS_NUMBER` for fee calculation) to reflect the corrected value. [6](#0-5) 

### Proof of Concept

1. Build an Orchard bundle with the standard `orchard` crate builder targeting a bridge Unified Address.
2. The builder pads to 2 actions (enforced by `MIN_ACTIONS = 2` in `orchard/src/builder.rs`).
3. Serialize the bundle bytes and submit a `ft_transfer_call` to the nZEC token contract with `chain_specific_data.orchard_bundle_bytes` set to those bytes.
4. `ft_on_transfer_callback` → `PsbtWrapper::new` → `extract_orchard_bundle` → `bundle.actions().len() == 2 != 1` → returns `Err("Orchard bundle must have 1 actions, got 2")` → `env::panic_str("ERR_INVALID_ORCHARD_BUNDLE")`.
5. The callback panics; the FT contract refunds the nZEC tokens. Shielded withdrawal fails for every standard bundle.
