### Title
`clear_invalid_pending_verify_rbf` Omits Account Tracking Cleanup, Creating Permanent Stuck State - (File: `contracts/satoshi-bridge/src/btc_pending_info.rs`)

### Summary
The publicly callable `clear_invalid_pending_verify_rbf` (and its batch variant) removes a `BTCPendingInfo` entry from `btc_pending_infos` without removing the corresponding entry from the account's `btc_pending_verify_list`. Any unprivileged caller can trigger this on a qualifying RBF pending info belonging to another user, permanently inflating that account's pending-verify tracking set with a stale, uncleanable entry.

### Finding Description
`internal_clear_invalid_pending_verify_rbf` removes the pending info record but never touches the owning account's `btc_pending_verify_list`:

```rust
// contracts/satoshi-bridge/src/btc_pending_info.rs
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
    // ← account.btc_pending_verify_list.remove(&btc_pending_id) is NEVER called
}
```

Every other code path that removes a `BTCPendingInfo` also removes the corresponding account-level tracking entry. For example, `verify_refund_finalize_callback` does:

```rust
self.internal_remove_btc_pending_info(&tx_id);
self.internal_unwrap_mut_account(&account_id)
    .btc_pending_verify_list
    .remove(&tx_id);   // ← present here
```

And `sign_btc_transaction`'s early-exit path does:

```rust
self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
    .btc_pending_sign_ids
    .remove(&btc_pending_sign_id);   // ← present here
self.internal_remove_btc_pending_info(&btc_pending_sign_id);
```

The public entry points have no role restriction — only a pause guard — so any unprivileged NEAR account can call them:

```rust
#[pause(except(roles(Role::DAO)))]
pub fn clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_id: String) { … }

#[pause(except(roles(Role::DAO)))]
pub fn batch_clear_invalid_pending_verify_rbf(&mut self, btc_pending_verify_ids: Vec<String>) { … }
```

The analog to the external report is exact: just as `endAuction` modified `liveAuctions` without validating the NFT's existence in the auction registry, `clear_invalid_pending_verify_rbf` modifies `btc_pending_infos` without performing the symmetric update to the account's `btc_pending_verify_list` — leaving the accounting in an inconsistent state that no other function can repair.

### Impact Explanation
**Low.** After the call, the invariant `∀ id ∈ account.btc_pending_verify_list → btc_pending_infos.contains(id)` is permanently broken for the victim account. The stale entry in `btc_pending_verify_list` can never be removed: no public function removes from that set without first successfully looking up the corresponding `BTCPendingInfo` (which no longer exists). The contract stores per-account `pending_tx_limits`; if any downstream logic counts entries in `btc_pending_verify_list` toward that cap, the victim's account is permanently blocked from initiating further withdrawals — a stuck-state requiring operator intervention. No direct fund theft occurs.

### Likelihood Explanation
**Medium.** The qualifying condition — an RBF pending info in `PendingVerify` stage whose original tx_id is absent from `rbf_txs` — arises naturally during normal bridge operation whenever a withdrawal is confirmed on-chain and its RBF alternatives are awaiting cleanup. Any unprivileged NEAR account can observe the public state (via view functions) to identify qualifying entries and call `clear_invalid_pending_verify_rbf` on another user's RBF pending info before the legitimate off-chain relayer does so.

### Recommendation
Mirror the cleanup pattern used in every other removal path. In `internal_clear_invalid_pending_verify_rbf`, after removing from `btc_pending_infos`, also remove the entry from the account's `btc_pending_verify_list`:

```rust
pub fn internal_clear_invalid_pending_verify_rbf(&mut self, btc_pending_id: String) {
    let btc_pending_info = self.internal_remove_btc_pending_info(&btc_pending_id);
    btc_pending_info.assert_pending_verify();
    let original_tx_id = btc_pending_info
        .get_original_tx_id()
        .expect("Not rbf transaction");
    require!(
        !self.data().rbf_txs.contains_key(original_tx_id),
        "Not invalid pending verify rbf"
    );
    // Add:
    let account_id = btc_pending_info.account_id.clone();
    self.internal_unwrap_mut_account(&account_id)
        .btc_pending_verify_list
        .remove(&btc_pending_id);
}
```

### Proof of Concept
1. User A initiates a withdrawal; an RBF is created and reaches `PendingVerify` stage. The original tx is confirmed on-chain, so its `rbf_txs` entry is removed.
2. Attacker observes (via view API) that `btc_pending_infos` contains User A's RBF entry in `PendingVerify` stage and that the original tx_id is absent from `rbf_txs`.
3. Attacker calls `clear_invalid_pending_verify_rbf(user_a_rbf_tx_id)` — no role or deposit required.
4. `btc_pending_infos` no longer contains the entry; User A's `btc_pending_verify_list` still does.
5. User A's account permanently carries a stale entry. Any per-account limit enforced against `btc_pending_verify_list` is now permanently consumed, blocking future withdrawals without operator intervention. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4)
