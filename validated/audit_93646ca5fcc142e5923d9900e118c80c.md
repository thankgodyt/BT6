### Title
Unprotected `new()` Initializer Allows Any Caller to Seize Controller and Bridge Roles — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `new()` constructor of the `nbtc` token contract does not verify that the caller is the contract account itself (`env::current_account_id()`). In NEAR, contract deployment and initialization are separate transactions. Any unprivileged account that observes the deployment can front-run the initialization call, supplying attacker-controlled `controller` and `bridge_id` values. This grants the attacker exclusive authority to mint and burn nBTC tokens.

---

### Finding Description

`contracts/nbtc/src/lib.rs` defines the `new()` initializer: [1](#0-0) 

The function accepts `controller` and `bridge_id` as caller-supplied parameters and writes them directly into contract state. The only guard present is: [2](#0-1) 

This prevents a second initialization, but does **not** restrict *who* may perform the first one. There is no check of the form `require!(env::predecessor_account_id() == env::current_account_id(), ...)`.

The two stored values are the sole gatekeepers for all privileged operations:

- `assert_bridge()` — gates `mint()`, `burn()`, and `safe_mint()`: [3](#0-2) 

- `assert_controller()` — gates `set_controller()`, `set_metadata()`, `set_withdraw_relayer_address()`, `attach_full_access_key()`, and `upgrade_and_migrate()`: [4](#0-3) 

The `mint()` function, once `bridge_id` is attacker-controlled, allows minting arbitrary amounts of nBTC to any account: [5](#0-4) 

The same structural flaw exists in the `satoshi-bridge` contract's `new()`, where the caller is unconditionally granted DAO super-admin: [6](#0-5) 

---

### Impact Explanation

An attacker who front-runs `nbtc::new()` with `controller = attacker` and `bridge_id = attacker` gains:

1. **Unauthorized minting of nBTC** — `mint()` passes `assert_bridge()` for the attacker's account, allowing them to mint unbounded nBTC to any recipient.
2. **Unauthorized burning** — `burn()` similarly passes, enabling destruction of legitimate user balances held in the bridge account.
3. **Full administrative takeover** — `assert_controller()` passes, granting the attacker the ability to rotate the controller key, upgrade the contract, and redirect the withdraw relayer address.

This directly matches the **Critical** allowed impact: *Unauthorized minting of nBTC*.

---

### Likelihood Explanation

In NEAR Protocol, contract deployment (`DeployContract` action) and the initialization call are separate transactions unless the deployer explicitly batches them into a single `Promise` chain. If the deployer uses a script, CLI command, or deployment tool that sends them as independent transactions, a window exists between deployment and initialization. A monitoring bot watching the NEAR mempool or block stream for `DeployContract` actions targeting the nBTC account ID can immediately submit a `new()` call with attacker-controlled arguments before the legitimate deployer does. This is a low-complexity, one-shot attack requiring no special privileges.

---

### Recommendation

Add a caller check at the top of `new()` in both `contracts/nbtc/src/lib.rs` and `contracts/satoshi-bridge/src/lib.rs`:

```rust
require!(
    env::predecessor_account_id() == env::current_account_id(),
    "Only the contract account may initialize"
);
```

This mirrors the remediation applied in the referenced Solana report (commit `1df65f7f6f672651bb488e8c811f1674d2b37fb6`), which restricted initialization to the deployer/upgrade authority. Additionally, deployment scripts should batch the `DeployContract` action and the `new()` call into a single atomic `Promise` to eliminate the race window entirely.

---

### Proof of Concept

1. Observe the NEAR blockchain for a `DeployContract` action targeting the nBTC contract account (e.g., `nbtc.bridge.near`).
2. Immediately submit a transaction calling `new()` on that account with:
   - `controller`: attacker's account ID
   - `bridge_id`: attacker's account ID
   - Arbitrary `name`, `symbol`, `decimals`
3. The call succeeds because `env::state_exists()` is still `false` and no caller check exists.
4. Now call `mint(attacker_account, U128(1_000_000_000_000), ...)` from the attacker's account. `assert_bridge()` passes because `self.bridge_id == env::predecessor_account_id()` is satisfied.
5. Attacker holds minted nBTC backed by no real BTC deposit. [1](#0-0) [7](#0-6)

        controller: AccountId,
        bridge_id: AccountId,

        let mut contract = Self {

                    symbol,
                    icon,
                    reference: None,
                    reference_hash: None,
                    decimals,
                }),
            ),
        };

        contract
            .token
            .internal_register_account(&contract.bridge_id);

        contract
    }
