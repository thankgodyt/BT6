### Title
Peras Certificate Validation Bypass Allows Unprivileged Peer to Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance — which applies to all block types including production Cardano blocks — implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) and `validatePerasVote` without any cryptographic signature check. An unprivileged peer can send crafted Peras certificates or forge votes attributed to any registered stake pool, bypassing all cryptographic verification, causing them to be accepted and used to boost arbitrary blocks in chain selection.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` and `validatePerasVote` as the gatekeepers for accepting Peras certificates and votes from the network. The only deployed instance is the catch-all `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs`, which implements both methods as stubs:

```haskell

  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
``` [2](#0-1) 

`validatePerasCert` **always returns `Right`** regardless of the certificate's content — no aggregate BLS signature, no committee membership proof, no round-number plausibility check is performed. `validatePerasVote` only checks whether the claimed voter ID appears in the stake distribution; it never verifies the vote's cryptographic signature.

The network-facing inbound path in `processCerts` calls this function directly before inserting into the `PerasCertDB`:

```haskell
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (...) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
    (errs, _)            -> throw (PerasCertValidationError errs)
``` [3](#0-2) 

Because `validateCert` is bound to `validatePerasCert mkPerasParams`, every certificate from every peer passes. The accepted certificate is then forwarded to `ChainDB.addPerasCertAsync`, which enqueues a `ChainSelAddPerasCert` event. The chain-selection handler adds the certificate to the `PerasCertDB`, records its weight boost in the `PerasWeightSnapshot`, and immediately calls `chainSelectionForBlock` for the boosted block:

```haskell
-- Trigger chain selection for the boosted block.
lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
``` [4](#0-3) 

The `PerasWeightSnapshot` is consulted by `preferAnchoredCandidate` during every chain-selection comparison, so the injected weight boost directly influences which chain the node adopts.

The same path exists for votes via `processVotes` / `makePerasVotePoolWriterFromChainDB`: [5](#0-4) 

Because `validatePerasVote` never checks the vote signature, an attacker can forge votes attributed to any pool in the stake distribution. Once enough forged votes accumulate to exceed the quorum threshold, `updatePerasRoundVoteStates` triggers `forgePerasCert` — which is also a stub that returns `Right` unconditionally — producing a `ValidatedPerasCert` that is then inserted into the chain-selection pipeline.

**Structural analogy to the external report:** In the Smart Vault bug, `removeAsset` checked whether a token was registered in the `TokenManager`; tokens absent from that registry (Hypervisor tokens) silently bypassed the collateralisation check. Here, `processCerts` delegates all trust to `validatePerasCert`; because that function is a registry-less stub that always succeeds, every inbound certificate bypasses the cryptographic check — the same "absent from the registry → check skipped" pattern, expressed as a stub that never rejects.

---

### Impact Explanation

An unprivileged peer can inject a `PerasCert` pointing to any block currently in the `VolatileDB`. The certificate is accepted without any cryptographic check, stored in the `PerasCertDB`, and its weight boost is added to the `PerasWeightSnapshot`. Chain selection then re-evaluates the boosted block's chain against the current selection. If the adversarial chain's total Peras weight exceeds the honest chain's, the node switches forks — accepting a non-canonical chain beyond the intended security assumptions of Ouroboros Praos/Peras.

Via the vote path, an attacker who sends enough forged votes (one per registered pool ID, all without valid signatures) can manufacture a quorum, causing the node itself to forge and store a certificate for an arbitrary block, with the same chain-selection consequence.

This matches the **High** impact category: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions*, and the **Critical** category: *bypass of Peras voting or certificate checks that enables unauthorized certificate acceptance*.

---

### Likelihood Explanation

The attack requires only that the Peras object-diffusion mini-protocol is reachable from an unprivileged peer — no stake, no keys, no prior authentication. The `makePerasCertPoolWriterFromChainDB` and `makePerasVotePoolWriterFromChainDB` wrappers are production-path code (not test-only). The stub is the **only** deployed instance of `BlockSupportsPeras`; no era-specific override exists in the repository. The attack is a single network message.

---

### Recommendation

1. **Implement real cryptographic validation** in `validatePerasCert` (aggregate BLS signature over the committee's keys) and `validatePerasVote` (individual vote signature) before the Peras object-diffusion mini-protocol is enabled in any production or pre-production deployment.
2. **Add a compile-time or runtime guard** that prevents `makePerasCertPoolWriterFromChainDB` / `makePerasVotePoolWriterFromChainDB` from being wired into the node while the stub instance is in place, analogous to how the Smart Vault fix validated the asset before allowing removal.
3. Track resolution at the linked issue (`cardano-peras#120`).

### Proof of Concept

2. Peer constructs a PerasCert:

3. Peer sends the certificate via the mini-protocol.

4. makePerasCertPoolWriterFromChainDB.opwAddObjects calls:

5. validatePerasCert always returns Right ValidatedPerasCert { ... }

6. addPerasCertAsync enqueues ChainSelAddPerasCert.

7. chainSelSync adds the cert to PerasCertDB, records weight boost in

8. preferAnchoredCandidate now sees the adversarial chain as heavier;

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
