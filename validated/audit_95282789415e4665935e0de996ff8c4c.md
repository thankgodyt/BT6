### Title
Unconstrained `refund_address` in Open Refund Requests Enables Attacker to Redirect BTC Refunds to Attacker-Controlled Address - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a depositor's `DepositMsg` omits `refund_address` (i.e., `refund_address: None`), any NEAR account can call `request_refund` using the publicly available Bitcoin deposit proof while substituting their own BTC address as `refund_address`. Because only one refund request can exist per UTXO, the first caller wins. The legitimate depositor's BTC refund is permanently redirected to the attacker's address.

### Finding Description
The `internal_request_refund` function accepts a caller-supplied `refund_address`. The only guard binding `refund_address` to the deposit is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None`, this block is skipped entirely. There is no check that the caller is the original depositor, nor that the supplied `refund_address` belongs to the caller. The `deposit_msg` and the Bitcoin inclusion proof are both fully public (the `DepositMsg` is encoded in the Bitcoin transaction's OP_RETURN output, and the Merkle proof is derivable from any Bitcoin full node). An attacker can therefore construct a valid `request_refund` call for any deposit that lacks a pre-authorized `refund_address`.

In `request_refund_callback`, the only uniqueness guard is:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

Once the attacker's request is stored, the legitimate depositor cannot submit their own. The attacker's `refund_address` is persisted in the `RefundRequest` struct and is used verbatim when building the refund Bitcoin transaction in `finalize_refund_with_psbt`. [3](#0-2) 

The protocol acknowledges this risk by applying a longer `unsafe_refund_timelock_sec` when `deposit_msg.refund_address` is absent, giving the DAO time to reject suspicious requests:

```rust
} else {
    // Refund address supplied by caller of `request_refund`: longer
    // timelock to give DAO/Operator time to reject suspicious requests.
    config.unsafe_refund_timelock_sec
}
``` [4](#0-3) 

However, `execute_refund` is callable by anyone (the role check in `resolve_execute_refund_timelock` only selects which timelock applies, it does not gate access). After the `unsafe_refund_timelock_sec` elapses without a DAO rejection, the attacker calls `execute_refund`, and the BTC is sent to their address. [5](#0-4) 

### Impact Explanation
**Critical.** A depositor who did not embed a `refund_address` in their `DepositMsg` can have their entire BTC deposit stolen. The attacker receives the full deposit amount minus the gas fee. This is a direct, permanent loss of user funds with no recovery path once `execute_refund` is finalized.

### Likelihood Explanation
**Medium.** The attack requires no special privileges. All inputs (deposit transaction bytes, Merkle proof, `DepositMsg`) are publicly readable from the Bitcoin blockchain. The attacker only needs to monitor Bitcoin for deposits to the bridge's derived addresses and race to submit `request_refund` before the legitimate depositor. The `unsafe_refund_timelock_sec` window provides a partial mitigation, but it relies entirely on the DAO actively monitoring and rejecting every suspicious request — a trust assumption that fails if the DAO is offline, slow, or overwhelmed. Deposits without a pre-authorized `refund_address` are the common case for users who did not anticipate needing a refund.

### Recommendation
Bind the `refund_address` to the caller's identity when `deposit_msg.refund_address` is `None`. One approach: require the caller to sign a message proving ownership of the supplied BTC address, or alternatively, store `env::predecessor_account_id()` at request time and enforce that only that same NEAR account can later call `execute_refund`. A simpler mitigation is to require that `deposit_msg.refund_address` always be set (i.e., disallow `None`) so that the refund destination is committed to at deposit time and cannot be overridden by any caller.

### Proof of Concept
1. Alice sends BTC to the bridge with `DepositMsg { recipient_id: "alice.near", refund_address: None, ... }`. The deposit address is derived from the hash of this message.
2. The deposit is not finalized (e.g., bridge is paused).
3. Attacker Bob observes the Bitcoin transaction on-chain, extracts the `DepositMsg` from the OP_RETURN, and obtains the Merkle inclusion proof from a Bitcoin node.
4. Bob calls `request_refund(deposit_msg, "bob_btc_address", tx_bytes, vout, proof, None)` on the bridge contract.
5. `request_refund_callback` verifies the proof, confirms the output script matches the deposit address, finds no existing refund request, and stores `RefundRequest { refund_address: "bob_btc_address", ... }`.
6. Alice attempts to call `request_refund` with her own BTC address — it reverts with `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` elapses (assuming the DAO does not reject), Bob calls `execute_refund`.
8. `finalize_refund_with_psbt` builds a Bitcoin transaction paying `refund_amount` to `"bob_btc_address"` and submits it for MPC signing.
9. Alice's BTC is permanently transferred to Bob.

    pub(crate) fn resolve_execute_refund_timelock(&self, utxo_storage_key: &str) -> u64 {
        require!(
            env::attached_deposit() >= self.required_balance_for_execute_refund(),
            "Insufficient deposit for storage"
        );
        let caller = env::predecessor_account_id();
        let is_privileged =
            self.acl_has_any_role(vec![Role::DAO.into(), Role::RefundOperator.into()], caller);
        let refund_request: RefundRequest = self
            .data()
            .refund_requests
            .get(utxo_storage_key)
            .expect("Refund request not found")
            .into();
        let config = self.internal_config();
        if refund_request.deposit_msg().refund_address.is_some() {
            // Pre-authorized refund address: privileged users can fast-track.
            if is_privileged {
                0
            } else {
                config.refund_timelock_sec
            }
        } else {
            // Refund address supplied by caller of `request_refund`: longer
            // timelock to give DAO/Operator time to reject suspicious requests.
            config.unsafe_refund_timelock_sec
        }
    }
