### Title
Incorrect `boundX` Constant in `taylorExpCmpFirstNonLower` Causes Wrong Peras Non-Persistent Seat Counts - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Committee/LS.hs`)

---

### Summary

`localSortitionNumSeats` in `LS.hs` calls `taylorExpCmpFirstNonLower` with a hardcoded `boundX = 3`, but the function's own documented precondition requires `boundX = e^|x|`. Because `x = -lambda` is passed, the correct value is `e^lambda`. When `lambda > ln(3) ≈ 1.099` — which occurs for any non-persistent voter holding more than roughly 1% of the non-persistent stake in a 100-seat committee — the error bound is underestimated, causing the Taylor-series comparison to terminate with an incorrect result and assign a wrong number of Peras voting seats.

---

### Finding Description

`localSortitionNumSeats` computes how many non-persistent Peras committee seats a voter receives via local sortition. The seat count is determined by comparing the voter's normalized VRF output against Poisson CDF thresholds using `taylorExpCmpFirstNonLower`:

```haskell
expectedSeats :: Int
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      3          -- boundX (hardcoded)
      orders
      (-lambda)  -- x
``` [1](#0-0) 

The function's own inline documentation states:

```
-- IMPORTANT: boundX must be e^{|x|} for correct error bounds (see taylorExpCmp).
``` [2](#0-1) 

Since `x = -lambda`, the required value is `boundX = e^lambda`. The hardcoded `3` is only a valid overestimate when `lambda ≤ ln(3) ≈ 1.099`. For larger `lambda`, `3 < e^lambda`, so the error bound `errorTerm = abs(err' * boundX)` is too small:

```haskell
errorTerm = abs (err' * boundX)
``` [3](#0-2) 

With an underestimated `errorTerm`, the decision logic in `decideOne` prematurely classifies thresholds as "ABOVE" (`Stop`) or "BELOW" before the Taylor series has converged:

```haskell
| cmp >= acc' + errorTerm = Stop   -- declares ABOVE too early
| cmp < acc' - errorTerm = Below   -- declares BELOW too early
``` [4](#0-3) 

`lambda` is computed as:

```haskell
lambda =
  fromRational $
    fromIntegral numNonPersistentVoters
      * voterStake
      / totalNonPersistentStake
``` [5](#0-4) 

For a committee with 100 non-persistent voters, any voter holding more than ~1.1% of the non-persistent stake produces `lambda > ln(3)`, violating the precondition. For `lambda = 5` (5% stake, 100 voters), `e^5 ≈ 148.4` vs the hardcoded `3` — a 49× underestimate of the required error bound.

### Impact Explanation

When `lambda > ln(3)`, the Taylor comparison terminates with an incorrect seat count. Premature `Stop` (false "ABOVE") returns a higher seat index than warranted, granting the voter more non-persistent seats than the Poisson distribution dictates. Because both the voter and the verifier run the same flawed code, the verifier accepts the inflated seat count as valid. A voter with disproportionately many seats contributes a proportionally larger `VoteWeight`:

```haskell
VoteWeight $
  fromIntegral (unLocalSortitionNumSeats (unNonZero numSeats))
    * stake
    / nonPersistentStake
``` [9](#0-8) 

This inflated vote weight can push a Peras election past the quorum threshold with fewer actual participants than the protocol requires, weakening the security guarantees of Peras certificate formation. Conversely, premature `Below` (false "BELOW") can deny seats to eligible voters, preventing quorum from being reached and stalling certificate production.

**Impact class:** High — Peras voting or certificate check bug that lets an unprivileged peer (any pool with >~1% non-persistent stake) receive incorrect committee representation, materially weakening or bypassing the intended quorum security of Peras certificate acceptance.

---

### Likelihood Explanation

The threshold `lambda > ln(3) ≈ 1.099` is crossed by any non-persistent voter whose stake fraction exceeds `1.099 / numNonPersistentVoters`. With a 100-seat non-persistent committee, this is any pool with more than ~1.1% of the non-persistent stake — a very common condition on a real network. The bug is deterministic (not probabilistic) and triggers on every election for any such voter. No special privileges, leaked keys, or social engineering are required; the voter simply participates in normal Peras voting.

---

### Recommendation

Replace the hardcoded `3` with the mathematically correct value `exp(lambda)`:

```haskell
expectedSeats =
  fromMaybe 0 $
    taylorExpCmpFirstNonLower
      (exp lambda)   -- correct: e^|x| where x = -lambda
      orders
      (-lambda)
```

This matches the documented precondition `boundX = e^{|x|}` and is consistent with how `checkLeaderNatValue` in `cardano-ledger` handles the analogous leader-eligibility check (where `boundX` is also derived from the exponent argument, not hardcoded).

---

### Proof of Concept

Consider a Peras committee with:
- `numNonPersistentVoters = 100`
- A voter with 5% of the non-persistent stake → `lambda = 5.0`
- Required `boundX = e^5 ≈ 148.4`; actual `boundX = 3`

At `lambda = 5`, the Taylor series for `e^(-5) ≈ 0.00674` converges slowly. With `errorTerm` underestimated by a factor of ~49, `decideOne` will declare thresholds as "ABOVE" or "BELOW" after far fewer iterations than needed for the series to converge. Concretely, for a VRF output near a Poisson CDF boundary (e.g., near the threshold between 4 and 5 seats), the premature termination will resolve the ambiguity in the wrong direction, granting the voter 5 seats when the correct answer is 4 (or vice versa). Since both `implCheckShouldVote` and `implVerifyVote` call the same `localSortitionNumSeats`, the incorrect seat count passes verification, and the inflated `VoteWeight` is accepted into the Peras certificate aggregation.
