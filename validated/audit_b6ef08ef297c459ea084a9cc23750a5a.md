Audit Report

## Title
Undetected `ft_transfer` Failure in `fin_transfer_send_tokens_callback` Causes Permanent Freezing of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`fin_transfer_send_tokens_callback` delegates failure detection entirely to `is_refund_required(is_ft_transfer_call)`. When a plain `ft_transfer` is used (i.e., `msg` is empty and the token is not a deployed bridge token), `is_ft_transfer_call` is `false` and `is_refund_required` unconditionally returns `false` without reading the promise result. If the token contract rejects the transfer, the bridge has already committed the transfer ID to `finalised_transfers` and decremented `locked_tokens`, with no recovery path, permanently freezing the user's funds inside the bridge contract.

## Finding Description

`process_fin_transfer_to_near` (L1868) performs three irreversible state mutations before `send_tokens` is called:

1. `add_fin_transfer` (L1875) inserts the transfer ID into `finalised_transfers` — replay is now impossible.
2. `unlock_tokens_if_needed` (L1881–1885) decrements `locked_tokens` — accounting is now off.
3. `send_tokens` (L1957–1966) issues a plain `ft_transfer` when `msg.is_empty()` and the token is not a deployed bridge token (L2102–2106).

The callback is chained with `is_ft_transfer_call = !msg.is_empty()` (L1973), so for the plain `ft_transfer` path, `is_ft_transfer_call = false`.

Inside `fin_transfer_send_tokens_callback` (L1702), `is_refund_required(false)` is called. The function (L1784–1803) only reads the promise result when `is_ft_transfer_call` is `true`; the `else` branch at L1800–1802 unconditionally returns `false` with no promise inspection. Consequently, the `else` branch of the callback (L1719–1746) always fires: it sends the fee and emits `FinTransferEvent`, regardless of whether `ft_transfer` succeeded or panicked.

The refund path (L1702–1718) — which calls `revert_lock_actions`, `remove_fin_transfer`, and emits `FailedFinTransferEvent` — is never reached for the plain `ft_transfer` case.

## Impact Explanation

When `ft_transfer` fails (token contract panics):

- The transfer ID remains in `finalised_transfers` — the transfer cannot be replayed or retried.
- `locked_tokens` was already decremented — the bridge's accounting is permanently incorrect.
- The tokens remain in the bridge contract's balance with no function to recover them.
- `FinTransferEvent` is emitted, misleading off-chain systems into treating the transfer as successful.

This is a concrete instance of **permanent freezing of bridged funds**, matching the Critical allowed impact scope.

## Likelihood Explanation

The affected code path is reached for any non-deployed (native NEAR) NEP-141 token bridged from EVM back to NEAR with an empty `msg`. Tokens such as USDC implement blacklists; the token issuer (or any party with blacklist authority) can blacklist the recipient between the storage-deposit receipt and the `ft_transfer` receipt. No attacker-controlled bridge state is required — only the ability to blacklist an address on the token contract, which is a standard operator capability for regulated tokens. The bridge itself has no control over whether the token contract accepts the transfer.

## Recommendation

In `fin_transfer_send_tokens_callback`, explicitly check the promise result for the plain `ft_transfer` case. When `is_ft_transfer_call` is `false`, call `env::promise_result_checked(0, ...)` and treat an `Err` result as a failure. On failure, execute the same revert path as the existing refund branch: call `revert_lock_actions(&lock_actions)`, `remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner)`, and emit `FailedFinTransferEvent`. This mirrors the existing handling for `ft_transfer_call` failures and closes the blind spot for plain `ft_transfer`.

## Proof of Concept

1. Deploy a NEP-141 token on NEAR with a blacklist (e.g., a USDC-style token). Register it with the Omni Bridge.
2. Bridge some amount from NEAR to EVM: tokens are locked in the bridge, `locked_tokens` is incremented.
3. On EVM, initiate a return transfer back to NEAR with a NEAR recipient address and empty `msg`.
4. Before the relayer calls `fin_transfer`, blacklist the recipient on the NEAR token contract.
5. Relayer calls `fin_transfer` with a valid proof. `fin_transfer_callback` → `process_fin_transfer_to_near`:
   - `add_fin_transfer` (L1875): transfer ID inserted into `finalised_transfers`.
   - `unlock_tokens_if_needed` (L1881): `locked_tokens` decremented.
   - `send_tokens` (L1957, L2102–2106): `ft_transfer(recipient, amount, None)` issued — token contract panics (blacklisted), promise result is `Err`.
6. `fin_transfer_send_tokens_callback` fires with `is_ft_transfer_call = false`.
7. `is_refund_required(false)` returns `false` (L1800–1802); the `else` branch fires (L1719), emitting `FinTransferEvent`.
8. Result: transfer ID consumed, `locked_tokens` permanently decremented, tokens stuck in bridge balance, no recovery function exists.
