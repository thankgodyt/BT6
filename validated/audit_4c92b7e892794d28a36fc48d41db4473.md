### Title
Caller-Controlled Refund Destination Allows Third-Party Theft of Unfinalized Deposits - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
When a user creates a deposit address with `deposit_msg.refund_address = None`, any unprivileged NEAR account can call `request_refund` and set an arbitrary BTC address as the refund destination. After `unsafe_refund_timelock_sec` (14 days by default), anyone can call `execute_refund`, sending the victim's BTC to the attacker's address. The only protection is DAO/Operator vigilance during the 14-day window — there is no cryptographic enforcement of the refund destination at the binding step.

### Finding Description
The deposit address is derived by hashing the entire `deposit_msg` JSON, including the `refund_address` field. When a user deposits with `deposit_msg.refund_address = None`, the hash commits to the absence of a refund address. At the binding step — `request_refund` — the contract accepts a caller-supplied `refund_address` parameter and only validates it against `deposit_msg.refund_address` when the latter is `Some`:

```rust
// contracts/satoshi-bridge/src/refund.rs  (internal_request_refund)
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
```

When `deposit_msg.refund_address` is `None`, this block is skipped entirely. The callback then validates only that the transaction output's `script_pubkey` matches the deposit address derived from `deposit_msg`:

```rust
// contracts/satoshi-bridge/src/refund.rs  (request_refund_callback)
require!(
    deposit_script_pubkey == output.script_pubkey,
    "Output script_pubkey does not match deposit address"
);
```

This check passes for any caller who supplies the correct `deposit_msg` (which is publicly observable from the `LogDepositAddress` event emitted by `get_user_deposit_address`). The caller-supplied `refund_address` is then stored verbatim in the `RefundRequest` and used as the BTC output destination when `execute_refund` is called.

There is no check on the identity of the `request_refund` caller relative to the original depositor (`deposit_msg.recipient_id`). The `gas_fee` guard is the only caller-identity check in `request_refund`, and it is irrelevant to the refund destination.

This is the direct analog to the Saffron H-02 bug: a commitment is made at one step (`get_user_deposit_address` / `deposit_msg`), but the economically binding parameter (refund destination) is not validated against that commitment at the binding step (`request_refund`). The contract mutates the stored refund destination from attacker input instead of validating it against the original depositor's intent.

### Impact Explanation
An attacker can redirect any unfinalized deposit (where `deposit_msg.refund_address = None`) to their own BTC address. If the DAO/Operator does not reject the malicious request within 14 days, `execute_refund` sends the victim's BTC to the attacker. This constitutes direct theft of user funds — the victim loses their entire deposited BTC with no on-chain recourse after the refund is executed and confirmed.

This falls under: **Critical — Significant loss, theft, destruction, or permanent locking of user or protocol funds.**

### Likelihood Explanation
**Medium.** The attack requires two conditions:
1. A deposit with `deposit_msg.refund_address = None` that is never finalized via `verify_deposit` (relayer downtime, deposit below `min_deposit_amount`, or deliberate griefing of the relayer).
2. DAO/Operator failing to call `reject_refund` within `unsafe_refund_timelock_sec` (14 days default).

Both conditions are realistic. Deposits with `refund_address: None` are a supported and documented flow. The 14-day window is long but finite, and DAO/Operator monitoring is an operational assumption, not a cryptographic guarantee. The attacker's only cost is the non-refundable storage deposit for `request_refund`, which is negligible compared to any meaningful BTC deposit.

### Recommendation
1. **Enforce caller identity when `deposit_msg.refund_address = None`**: require that `env::predecessor_account_id() == deposit_msg.recipient_id` (or a pre-authorized delegate) when no refund address was committed at deposit time.
2. **Alternatively, make `refund_address` mandatory in `deposit_msg`**: remove the `None` path entirely, forcing users to pre-commit a refund address before depositing. This eliminates the caller-controlled destination entirely.
3. **At minimum, emit a warning event** when a refund request is submitted by an account that is not the `recipient_id`, to aid DAO/Operator monitoring.

### Proof of Concept
1. Alice calls `get_user_deposit_address({recipient_id: alice.near, refund_address: None})`. The contract emits a `LogDepositAddress` event containing the full `deposit_msg` — publicly observable on NEAR.
2. Alice sends BTC to the derived deposit address. The relayer is down or the deposit is below `min_deposit_amount`, so `verify_deposit` is never called.
3. Attacker observes the `LogDepositAddress` event and the BTC transaction on-chain.
4. Attacker calls `request_refund(deposit_msg={recipient_id: alice.near, refund_address: None}, refund_address="attacker_btc_addr", tx_bytes=..., vout=..., proof=...)`.
   - `internal_request_refund`: `deposit_msg.refund_address` is `None` → the consistency check is skipped.
   - `request_refund_callback`: `script_pubkey` derived from the correct `deposit_msg` matches the tx output → check passes. Attacker's address is stored as `RefundRequest.refund_address`.
5. DAO/Operator does not call `reject_refund` within 14 days.
6. Attacker (or anyone) calls `execute_refund(utxo_storage_key)`. The bridge builds a PSBT paying `deposit - gas_fee` to `attacker_btc_addr` and routes it through MPC signing.
7. Alice's BTC is permanently transferred to the attacker's address.

    pub fn request_refund(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<U128>,
    ) -> Promise {
        if gas_fee.is_some() {
            let caller = env::predecessor_account_id();
            require!(
                self.acl_has_role(Role::DAO.into(), caller.clone())
                    || self.acl_has_role(Role::Operator.into(), caller),
                "Only DAO or Operator can specify custom gas_fee"
            );
        }
        self.internal_request_refund(
            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }
