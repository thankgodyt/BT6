Audit Report

## Title
Missing Pre-Burn Normalization Guard Causes Permanent Loss of Bridged Tokens When Amount Normalizes to Zero - (File: near/omni-bridge/src/lib.rs)

## Summary
When a user initiates a NEAR→foreign transfer with an amount smaller than the decimal normalization factor (`10^(origin_decimals - decimals)`), `normalize_amount` silently returns 0 via floor division. Tokens are irreversibly burned or locked in `init_transfer_internal` before this is detected. The subsequent `sign_transfer` call always reverts with `InvalidAmountToTransfer`, and no cancel or refund path exists for the stuck pending transfer, resulting in permanent loss of the user's bridged tokens.

## Finding Description
`normalize_amount` performs floor division and is explicitly documented as such:

```rust
// near/omni-bridge/src/lib.rs L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The comment at L2781-2783 acknowledges: *"When fee = 0, dust stays locked/burned."* However, this framing treats only remainders as dust — it does not account for the case where the **entire** amount normalizes to zero.

`init_transfer` (called via `ft_on_transfer`) validates only that `fee < amount` (L554-557) before calling `init_transfer_internal`. There is no pre-burn check that `normalize_amount(amount_without_fee, decimals) > 0`.

`init_transfer_internal` (L1829-1865) then:
1. Stores the transfer message in `pending_transfers`
2. Calls `burn_tokens_if_needed` (for deployed tokens) or `lock_tokens_if_needed` (for native tokens) — both irreversible
3. Returns `U128(0)` to the NEP-141 token contract, signaling all tokens were consumed with no refund

Later, when a relayer calls `sign_transfer`, the guard at L475-485 fires:
```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(amount_to_transfer > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```
This always reverts. `remove_transfer_message_without_refund` is only invoked on storage failure (L1846) or non-NEAR token (L1859) — neither applies here. The transfer message remains in `pending_transfers` indefinitely with no public cancel or recovery function.

## Impact Explanation
For deployed (bridged) tokens: they are burned and cannot be recovered. For native tokens: they are locked in the bridge contract with no recovery path. This constitutes **permanent freezing/loss of bridged funds**, matching the Critical impact scope: *"permanent freezing of bridged funds"* and *"decimal/normalization abuse... that changes user or protocol balances."*

## Likelihood Explanation
Low-to-medium. The condition requires a user to send an amount below the normalization threshold. For a token with `origin_decimals=24` normalized to `decimals=18`, the threshold is `10^6` base units. Users unfamiliar with decimal normalization can trigger this inadvertently. The CLAUDE.md false-positive list (item 2) covers only the `origin_decimals < decimals` underflow/panic case, not the floor-division-to-zero case. The vulnerability is triggerable by any unprivileged user via the standard `ft_transfer_call` → `ft_on_transfer` → `init_transfer` flow.

## Recommendation
Add a normalization sanity check in `init_transfer` (before `init_transfer_internal` is called, i.e., after L557) that validates the net amount survives normalization:

```rust
let token_address = self.get_token_address(destination_chain, token_id.clone())
    .near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals.get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

When this check fails, `ft_on_transfer` should return the full `amount` (refunding the caller) rather than `U128(0)`.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (normalization factor = `10^6`).
2. User calls `ft_transfer_call` with `amount = 5` (5 base units), `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 5). No normalization check exists.
4. `init_transfer_internal` burns 5 base units of the deployed token (or locks them). Returns `U128(0)` — no refund issued.
5. Relayer calls `sign_transfer`.
6. `normalize_amount(5, Decimals{decimals:18, origin_decimals:24})` = `5 / 1_000_000` = `0`.
7. `require!(0 > 0, ...)` panics with `InvalidAmountToTransfer`. Transaction reverts.
8. Transfer message remains in `pending_transfers` forever. The 5 base units are permanently lost with no recovery path.
