### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The catch-all `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural validation. Because this function is wired directly into the production node-to-node Peras certificate diffusion miniprotocol handler, any unprivileged peer can send a crafted `PerasCert` message that will be accepted, stored in the `ChainDB`, and used to apply an arbitrary Peras weight boost to any block the attacker chooses, causing the victim node to prefer a non-canonical chain.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the degenerate `BlockSupportsPeras` instance (the catch-all instance used for all block types, including production Cardano blocks until era-specific plumbing is complete) implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

This function accepts **every** certificate unconditionally — no aggregate signature verification, no quorum check, no round-number bounds check, no boosted-block existence check. The `TODO` comment acknowledges this is a stub, but the stub is wired into the live production network path.

The call chain from network ingress to chain selection is:

1. **Miniprotocol handler** (`NodeToNode.hs`, `hPerasCertDiffusionClient`): calls `makePerasCertPoolWriterFromChainDB`, which passes `(validatePerasCert mkPerasParams)` as the validation function.
2. **`processCerts`** (`PerasCert.hs`): calls `validateCert` on each inbound cert; if all pass (they always do), calls `addCert . WithArrivalTime now` for each.
3. **`addPerasCertAsync`** (`ChainSel.hs`): enqueues the cert for chain selection, which applies the `vpcCertBoost` weight to the boosted block.

The analog to the external report is exact: just as `addGasFee` accepted an attacker-supplied `_sender` without verifying `msg.sender == _sender`, `validatePerasCert` accepts an attacker-supplied `PerasCert` without verifying any cryptographic identity or quorum. In both cases, the "validation" gate that should enforce authorization is absent, and the downstream state-mutation path executes unconditionally.

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` naming any block (including a non-canonical or attacker-controlled fork tip) as the boosted block. The node will:

- Accept the cert as `ValidatedPerasCert` with `vpcCertBoost = perasWeight params`.
- Store it in the `PerasCertDB` via `ChainDB`.
- Trigger chain selection, which adds the Peras weight boost to the attacker-chosen block.
- Potentially switch to a non-canonical chain if the boosted fork's total weight (PoS chain length + Peras boost) exceeds the honest chain's weight.

This is a **High** impact chain-selection bug: an unprivileged peer can make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions of the Peras protocol, by bypassing the certificate verification that is the sole authorization gate for applying Peras weight boosts.

---

### Likelihood Explanation

**High.** The Peras certificate diffusion miniprotocol (`perasCertDiffusionProtocol`) is exposed to all node-to-node peers in the production `initiatorAndResponder` bundle. No authentication, rate-limiting, or stake-gating is applied before `validatePerasCert` is called. Any peer that can establish a node-to-node connection — which is the normal operating condition for any Cardano node — can send a crafted `PerasCert` message. The attack requires no keys, no stake, and no prior knowledge beyond the target node's address.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:

1. Verifies the aggregate BLS signature over the claimed voter set against the election ID and boosted block.
2. Checks that the claimed voter set constitutes a valid quorum (total stake ≥ threshold) according to the committee selection data for the relevant epoch.
3. Verifies that the boosted block exists and is within the valid round window.
4. Rejects any certificate that fails any of these checks with a typed `PerasValidationErr`.

Until the real implementation is in place, the stub should at minimum reject all inbound certificates (return `Left PerasValidationErr` unconditionally) rather than accept them all, so that the network path is safe-by-default.

### Proof of Concept

**Attacker preconditions:** Any node-to-node peer; no keys or stake required.

**Steps:**

1. Attacker establishes a node-to-node connection to the victim node.
2. Attacker sends a `PerasCert` message via the `perasCertDiffusion` miniprotocol with:
   - `pcCertRound` = any round number not yet in the victim's `PerasCertDB`
   - `pcCertBoostedBlock` = the `Point` of any block the attacker wants to boost (e.g., a fork tip)
3. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
4. The cert is stored via `addPerasCertAsync`, triggering chain selection.
5. Chain selection applies `vpcCertBoost` to the attacker-chosen block; if the boosted fork's total weight exceeds the current selection, the node switches chains.
