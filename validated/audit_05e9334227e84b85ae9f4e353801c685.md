Audit Report

## Title
Wormhole VAA `emitter_chain` Ignored — Attacker-Controlled Payload Chain Kind Enables Factory Check Bypass - (File: `near/omni-prover/wormhole-omni-prover-proxy/src/parsed_vaa.rs`)

## Summary
Every `TryInto<*Message>` implementation in `parsed_vaa.rs` constructs `emitter_address` using the chain kind extracted from the payload's `token_address` field rather than from `self.emitter_chain`, the Wormhole-attested chain identifier in the VAA header. Because any contract on any chain can emit a Wormhole message with an arbitrary payload, an attacker controls which chain slot is consulted in the factory authorization check. If the attacker's contract address bytes match a registered factory's address bytes on a different chain (a realistic condition under CREATE2 same-address deployment), the factory check passes and the bridge finalizes a fabricated transfer, minting or unlocking tokens with no corresponding source-chain deposit.

## Finding Description
In `parsed_vaa.rs`, all four `TryInto` conversions construct `emitter_address` as:

```rust
emitter_address: OmniAddress::new_from_slice(
    transfer.token_address.get_chain(),  // chain kind from PAYLOAD — attacker-controlled
    &self.emitter_address,               // address bytes from VAA header — Wormhole-attested
)?,
```

`ParsedVAA` carries `emitter_chain: u16` — the Wormhole-assigned chain ID set by the guardian network — but this field is never consulted when determining the chain kind of the emitter.

The downstream factory check in `fin_transfer_callback` and `claim_fee_callback` uses `emitter_address.get_chain()` to select which registered factory to compare against:

```rust
require!(
    self.factories
        .get(&init_transfer.emitter_address.get_chain())
        == Some(init_transfer.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
```

The `OmniBridgeWormhole.sol` contract encodes `omniBridgeChainId` (a storage variable set at initialization) into the payload at lines 131 and 133. For the legitimate bridge this value is correct. However, Wormhole guardians sign any message emitted on-chain regardless of payload content — they only attest that the message originated from `emitter_address` on `emitter_chain`. An attacker who deploys their own contract on any Wormhole-supported chain can emit a message with an arbitrary payload, including a `token_address` whose chain kind differs from the actual source chain. The `emitter_chain` field in the VAA header will correctly reflect the attacker's chain, but this field is silently discarded. The chain kind used for the factory lookup comes entirely from the attacker-supplied payload.

The CLAUDE.md note labeling this "Correct Design" is incorrect: the reasoning that "chain ID is explicitly encoded in the payload by source bridge" only holds for the legitimate bridge contract. It does not hold for arbitrary contracts that can emit Wormhole messages with any payload.

## Impact Explanation
**Critical.** The factory check is the sole on-chain authorization gate preventing arbitrary Wormhole messages from finalizing bridge transfers. If an attacker makes `emitter_address.get_chain()` resolve to chain B while the actual VAA emitter is a contract they control on chain A, and if the address bytes of their contract on chain A equal the registered factory bytes for chain B, the check passes. The attacker can then finalize a fabricated `InitTransferMessage` with arbitrary `recipient`, `token`, and `amount`, causing the bridge to mint or unlock bridged tokens on NEAR with no corresponding source-chain deposit. This matches the Critical impact class: unauthorized minting and authorization bypass enabling invalid finalization.

## Likelihood Explanation
**Medium.** The attack requires the attacker's contract address bytes to match a registered factory's address bytes on a different chain. This is realistic under two conditions common in production bridge deployments: (1) same-address factory deployment across EVM chains via CREATE2 with a fixed salt and deployer (widely used for operational symmetry), and (2) a race window on newly added chains (HyperEvm, Abs) where the legitimate factory has not yet been deployed. An attacker who observes the factory address on existing chains can front-run the legitimate deployment on a new chain. The entry path is fully permissionless: deploying a contract and emitting a Wormhole message requires no special role.

## Recommendation
Replace `token_address.get_chain()` with a chain kind derived from `self.emitter_chain` (the Wormhole chain ID in the VAA header), using a validated mapping from Wormhole chain IDs to `ChainKind`. This ensures the chain dimension of `emitter_address` is Wormhole-attested rather than payload-supplied. Additionally, assert that the chain kind derived from `emitter_chain` matches the chain kind embedded in `token_address` to catch inconsistent payloads early and reject them.

## Proof of Concept
**Precondition**: Omni Bridge factories are deployed at address `0xF00...` on Ethereum and Arbitrum via CREATE2 (same address). The factory on HyperEvm has not yet been deployed.

1. Attacker deploys a malicious contract at `0xF00...` on HyperEvm (before the legitimate factory).
2. Attacker's contract calls the Wormhole core bridge on HyperEvm, emitting a Borsh-encoded `InitTransferWh` payload where:
   - `sender = OmniAddress::Eth(0xF00...)` (chain kind byte = 0 for Eth)
   - `token_address = OmniAddress::Eth(some_registered_eth_token)` (chain kind byte = 0 for Eth)
   - `recipient = OmniAddress::Near(attacker_near_account)`
   - `amount = 1_000_000_000`
3. Wormhole guardians observe the message on HyperEvm and produce a signed VAA with `emitter_chain = HyperEvm_wormhole_id`, `emitter_address = 0xF00...`.
4. Attacker submits the VAA to the NEAR Wormhole prover proxy via `fin_transfer`.
5. `parsed_vaa.rs` constructs `emitter_address = OmniAddress::Eth(0xF00...)` (chain kind from payload = Eth, bytes from VAA header = `0xF00...`).
6. `fin_transfer_callback` checks `factories.get(&ChainKind::Eth) == Some(OmniAddress::Eth(0xF00...))` — **passes**, because the Eth factory is registered at `0xF00...`.
7. The bridge mints/unlocks tokens to the attacker's NEAR account with no corresponding deposit on any source chain.

A local integration test can be written using `near-workspaces` by: registering a factory at address `X` for `ChainKind::Eth`, then constructing a synthetic VAA with `emitter_chain = HyperEvm_wormhole_id`, `emitter_address = X`, and a payload containing `token_address = OmniAddress::Eth(registered_token)`, submitting it through the prover proxy mock, and asserting that `fin_transfer_callback` does not revert — demonstrating the bypass.
