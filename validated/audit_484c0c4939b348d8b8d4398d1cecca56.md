Audit Report

## Title
Silent Failure of `ft_transfer`/`mint` in `fin_transfer_send_tokens_callback` Causes Permanent Loss of Bridged Funds — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`is_refund_required` unconditionally returns `false` when `is_ft_transfer_call` is `false`, without inspecting the promise result of the preceding `ft_transfer` or `mint` call. When `msg` is empty, `send_tokens` issues a plain `ft_transfer` or `mint` and passes `is_ft_transfer_call = false` to the callback. If that call fails for any reason, `fin_transfer_send_tokens_callback` silently takes the success branch: the fee is paid out, `FinTransferEvent` is emitted, and `remove_fin_transfer` is never called. The transfer ID is permanently finalised while the recipient receives nothing, and the source-chain funds are irrecoverably locked or burned.

## Finding Description

**`is_refund_required` short-circuits to `false` without reading the promise result:** [1](#0-0) 

When `is_ft_transfer_call` is `false`, the function returns `false` at line 1802 without ever calling `env::promise_result_checked`. There is no branch that inspects whether the downstream `ft_transfer` or `mint` succeeded.

**`send_tokens` issues a plain `ft_transfer` or `mint` when `msg` is empty, and passes `is_ft_transfer_call = !msg.is_empty()` (i.e., `false`) to the callback:** [2](#0-1) [3](#0-2) 

**`add_fin_transfer` consumes the transfer nonce before `send_tokens` is called:** [4](#0-3) 

**`fin_transfer_send_tokens_callback` takes the success branch when `is_refund_required` returns `false`, emitting `FinTransferEvent` and never calling `remove_fin_transfer`:** [5](#0-4) 

The same flaw exists in `resolve_fast_transfer` and `resolve_utxo_fin_transfer`: [6](#0-5) [7](#0-6) 

## Impact Explanation

This is a **permanent loss of bridged funds**. The transfer nonce is consumed by `add_fin_transfer`, the transfer ID is permanently recorded as finalised in `fin_transfers`, and the prover proof cannot be replayed. The recipient's balance is zero. The source-chain tokens are locked or burned with no recourse. This matches the allowed critical impact: *permanent freezing / loss of bridged funds across NEAR, EVM, Solana, or other supported chains*.

## Likelihood Explanation

The trigger is any failure of `ft_transfer` or `mint` on the destination token contract. Realistic, non-speculative causes include:

- A stablecoin (USDC, USDT) paused by its issuer — a documented, recurring real-world event.
- A bridge token whose `mint` panics due to an edge case (e.g., overflow, access control).
- Insufficient gas forwarded to the token call causing a gas exhaustion panic.

No attacker action is required; the failure can be caused by the token contract's own state. Any user bridging tokens to NEAR is exposed whenever the destination token contract is in a non-operational state at the time of finalization.

## Recommendation

`is_refund_required` must inspect the promise result even when `is_ft_transfer_call` is `false`:

```rust
fn is_refund_required(is_ft_transfer_call: bool) -> bool {
    if is_ft_transfer_call {
        match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
            Ok(value) => {
                if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                    amount.0 == 0
                } else {
                    false
                }
            }
            Err(_) => false, // existing behaviour: don't refund on unexpected failure
        }
    } else {
        // ft_transfer or mint: refund if the promise failed
        env::promise_result_checked(0, 0).is_err()
    }
}
```

Additionally, `fin_transfer_send_tokens_callback`, `resolve_fast_transfer`, and `resolve_utxo_fin_transfer` should all treat a failed non-`ft_transfer_call` promise as requiring a revert/refund, and the revert path in `fin_transfer_send_tokens_callback` should call `remove_fin_transfer` to release the finalised transfer ID.

## Proof of Concept

1. User initiates a USDC transfer from Ethereum to NEAR via `initTransfer` on `OmniBridge.sol` — USDC is locked on Ethereum.
2. Relayer calls `fin_transfer` on the NEAR bridge with a valid Ethereum proof.
3. `fin_transfer_callback` decodes the proof and calls `process_fin_transfer_to_near`.
4. `add_fin_transfer` records the transfer ID as finalised (nonce consumed).
5. `send_tokens` issues `ft_transfer(recipient, amount)` to the USDC contract on NEAR.
6. USDC on NEAR is paused by Circle; `ft_transfer` fails (promise result is `Err`).
7. `fin_transfer_send_tokens_callback` is invoked with `is_ft_transfer_call = false`.
8. `is_refund_required(false)` returns `false` at line 1802 without reading the promise result.
9. The success branch executes: fee is minted/transferred to the relayer, `FinTransferEvent` is emitted.
10. `remove_fin_transfer` is never called; the transfer ID stays permanently finalised.
11. Recipient balance: 0. Transfer nonce: consumed. Ethereum USDC: permanently locked. User funds: permanently lost.

A local integration test can reproduce this by deploying a mock token contract whose `ft_transfer` always panics, submitting a valid `fin_transfer` proof, and asserting that (a) the recipient balance remains zero and (b) the transfer ID is still present in `fin_transfers` after the callback.
