### Title
Hardcoded `perasWeight` in `mkPerasParams` causes incorrect chain-selection boost when Peras is enabled — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Peras/Params.hs`)

### Summary

`mkPerasParams` is a zero-argument function that returns a fully hardcoded `PerasParams` bundle. Its `perasWeight = 15` field is consumed by the production certificate-validation path (`makePerasCertPoolWriterFromChainDB`) to stamp every accepted Peras certificate with a fixed chain-selection boost. Because the actual Peras parameters must depend on `BlockConfig` (acknowledged by the in-code TODO), any deployment where the real protocol weight differs from 15 will apply the wrong boost to every peer-supplied certificate, corrupting the weighted chain-selection comparison.

### Finding Description

`mkPerasParams` in `Ouroboros/Consensus/Peras/Params.hs` (lines 137–177) is a constant — it takes no arguments and returns the same `PerasParams` for every call site. The comment on line 136 explicitly states: *"NOTE: in the future this will depend on a concrete 'BlockConfig'."*

The hardcoded fields include:

| Field | Hardcoded value | Role |
|---|---|---|
| `perasWeight` | `15` | boost added to chain weight per accepted certificate |
| `perasQuorumStakeThreshold` | `3/4` | fraction of stake required to forge a certificate |
| `perasRoundLength` | `90` | slots per Peras round |
| `perasIgnoranceRounds` | `487` | cooldown ignoring rounds |
| `perasCooldownRounds` | `1928` | full cooldown length |

`mkPerasParams` is called directly in two production miniprotocol writers:

- `makePerasCertPoolWriterFromChainDB` (`PerasCert.hs`, line 126):
  ```haskell
  (validatePerasCert mkPerasParams)
  ```
- `makePerasVotePoolWriterFromChainDB` (`PerasVote.hs`, line 141):
  ```haskell
  (\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
  ```

`validatePerasCert` (defined in `Block/SupportsPeras.hs`, lines 353–358) stamps every accepted certificate with `vpcCertBoost = perasWeight params`, i.e., always `15`. This boost is then accumulated into `PerasWeightSnapshot` and consumed by `weightedSelectView` / `preferAnchoredCandidate` during chain selection, where `wsvTotalWeight = blockNo + weightBoost`.

The `perasQuorumStakeThreshold = 3/4` is consumed by `stakeAboveThreshold` (called from `votesReachQuorum`, `updateCandidateVoteState`, and `updateLoserVoteState`) to decide when a certificate may be forged from accumulated votes.

### Impact Explanation

When Peras is enabled (via `rnFeatureFlags`), every inbound certificate from an unprivileged peer is accepted and assigned a chain-selection boost of exactly `15`, regardless of what the actual protocol parameters specify. If the deployed network's `perasWeight` differs from `15` — for example, a private testnet or a future mainnet deployment that finalises a different value — the node will apply the wrong boost to every peer-supplied certificate. A peer can therefore send certificates that shift the node's chain-selection preference away from the canonical chain by an amount that does not correspond to the protocol's intended security margin. Similarly, the hardcoded `perasQuorumStakeThreshold = 3/4` means the quorum check used when aggregating votes into certificates does not reflect the actual protocol threshold, allowing certificates to be forged (or rejected) at the wrong stake level.

**Impact class**: High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.

### Likelihood Explanation

Peras is not enabled by default (`eraPerasRoundLength = NoPerasEnabled` in `defaultEraParams`), so mainnet nodes are currently unaffected. However, the feature is explicitly designed to be enabled via `rnFeatureFlags` / `rnFeatureFlags` in `RunNodeArgs`, and the production writers (`makePerasCertPoolWriterFromChainDB`, `makePerasVotePoolWriterFromChainDB`) are already wired into the live `ChainDB` and miniprotocol stack. Any private testnet or early-adopter deployment that enables Peras is immediately exposed. No special privileges are required: any connected peer can send a `PerasCert` message.

**Likelihood**: Medium — gated behind an experimental feature flag today, but the vulnerable code path is fully wired into production and the flag is the only barrier.

### Recommendation

Replace the zero-argument `mkPerasParams :: PerasParams` constant with a function `mkPerasParams :: BlockConfig blk -> PerasParams` (as the existing TODO comment already prescribes). The derived values should be computed from the genesis-sourced fields of `BlockConfig` — in particular, `perasWeight` and `perasQuorumStakeThreshold` must come from the on-chain / genesis Peras configuration rather than being compile-time literals. All call sites in `makePerasCertPoolWriterFromChainDB` and `makePerasVotePoolWriterFromChainDB` must be updated to pass the live `BlockConfig` so that the correct parameters are used for every certificate and vote validation.

### Proof of Concept

1. Start a private testnet with Peras enabled (`rnFeatureFlags = Set.singleton PerasFlag`).
2. From an unprivileged peer, send a `PerasCert` message via the Peras cert miniprotocol targeting any block on the honest chain.
3. `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams`, which unconditionally returns `Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }` (hardcoded).
4. The certificate is stored in `PerasCertDB` and its boost is added to `PerasWeightSnapshot`.
5. On the next chain-selection run, `weightedSelectView` computes `wsvTotalWeight = blockNo + 15` for the boosted block.
6. If the actual protocol specifies `perasWeight = 20`, the node applies only 15 units of boost, causing it to under-weight the boosted chain and potentially prefer a competing, non-canonical fork that accumulates more raw block numbers. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3) [5](#0-4) [6](#0-5)

-- | Instantiate default Peras protocol parameters.
--
-- NOTE: in the future this will depend on a concrete 'BlockConfig'.
mkPerasParams :: PerasParams
mkPerasParams =
  -- Many of these parameters are provided with sensible default values for now,
  -- waiting for a final decision (in a future stage of the project) on the
  -- exact values to use. See https://github.com/tweag/cardano-peras/issues/97.
  --
  -- We set tentatively T_heal to 2B/asc = 600 slots, as the CIP suggests a
  -- bigO(B/asc) for that value so that sufficiently many blocks are produced to
  -- overcome an adversarially boosted block.
  --
  -- We also set tentatively perasCertArrivalThreshold (= X in the formal spec)
  -- to 30 slots (it must be strictly smaller than perasRoundLength)
  -- See https://github.com/tweag/cardano-peras/issues/88 and
  -- https://github.com/tweag/cardano-peras/issues/99 for more information on
  -- this parameter.
  --
  -- We also have T_cp = 129_600 and T_cq = 43_200 as per the design document
  PerasParams
    { -- ceil(T_heal + T_cq) / perasRoundLength) as per the design document
      perasIgnoranceRounds =
        PerasIgnoranceRounds 487
    , -- ceil(T_heal + T_cq + T_cp) / perasRoundLength) + 1 as per the design document
      perasCooldownRounds =
        PerasCooldownRounds 1928
    , -- must be between 30 and 900 as per the design document
      perasBlockMinSlots =
        PerasBlockMinSlots 90
    , -- equal to perasIgnoranceRounds as per the design document
      perasCertMaxRounds =
        PerasCertMaxRounds 487
    , perasCertArrivalThreshold =
        PerasCertArrivalThreshold 30
    , perasRoundLength =
        PerasRoundLength 90
    , perasWeight =
        PerasWeight 15
    , perasQuorumStakeThreshold =
        PerasQuorumStakeThreshold (3 / 4)
    , perasQuorumStakeThresholdSafetyMargin =
        PerasQuorumStakeThresholdSafetyMargin (2 / 100)
    }
