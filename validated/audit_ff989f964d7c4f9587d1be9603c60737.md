### Title
Protocol Fee Bypass via Integer Division Truncation in `BridgeFee::get_fee` — (`contracts/satoshi-bridge/src/config.rs`)

---

### Summary

`BridgeFee::get_fee` computes the fee as `max(amount * fee_rate / 10000, fee_min)`. When `fee_min = 0` and `fee_rate > 0`, integer division truncates the fee to zero for any deposit amount below `10000 / fee_rate` satoshis. Neither `BridgeFee::assert_valid` nor `Config::assert_valid` enforces that `fee_min > 0` when `fee_rate > 0`, nor that `min_deposit_amount * fee_rate / 10000 >= 1`. A valid, accepted configuration can therefore produce a zero fee for every deposit at the minimum threshold, allowing any unprivileged user to bridge BTC to nBTC without paying the protocol fee.

---

### Finding Description

`BridgeFee::get_fee` in `contracts/satoshi-bridge/src/config.rs` (lines 30–35):

```rust
pub fn get_fee(&self, amount: u128) -> u128 {
    std::cmp::max(
        amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
        self.fee_min,
    )
}
```

`MAX_RATIO` is `10000` (basis points). When `fee_min = 0` and `fee_rate > 0`, the expression `amount * fee_rate / 10000` truncates to zero for any `amount < 10000 / fee_rate`. The `max(…, fee_min)` guard is ineffective because `fee_min` itself is zero.

`BridgeFee::assert_valid` (lines 22–28) only checks:

```rust
require!(self.fee_rate < MAX_RATIO, "Invalid fee_rate");
require!(self.protocol_fee_rate <= MAX_RATIO, "Invalid protocol_fee_rate");
```

`Config::assert_valid` (lines 124–158) calls `self.deposit_bridge_fee.assert_valid()` but adds no cross-field check relating `fee_min`, `fee_rate`, and `min_deposit_amount`.

In `internal_verify_deposit` (lines 45–71 of `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`), the only guard before fee computation is:

```rust
if deposit_amount < config.min_deposit_amount { … }
```

If `min_deposit_amount * fee_rate / 10000 < 1`, the fee computed for the minimum-allowed deposit is zero. The user is minted the full `deposit_amount` as nBTC with no fee deducted.

The default test/integration configuration already ships with `deposit_bridge_fee.fee_min = 0` and `deposit_bridge_fee.fee_rate = 0`. If the DAO later enables a percentage-only deposit fee (e.g., `fee_rate = 1`, 0.01 %) while leaving `fee_min = 0` and `min_deposit_amount` below 10 000 satoshis, every deposit at the minimum threshold pays zero fee. Because the PSBT-based withdrawal path enforces `withdraw_bridge_fee.fee_min = 50 000` satoshis, the withdrawal side is not affected under the default configuration; the deposit side is the exposed surface.

---

### Impact Explanation

Any unprivileged depositor can receive nBTC without paying the protocol's deposit fee. The protocol treasury and relayer both receive zero satoshis for those deposits. Repeated deposits at the truncation threshold drain the bridge's fee revenue entirely for the deposit direction. This is a bypass of bridge fee policies.

**Allowed impact class matched**: Medium — Bypass of bridge limits or policies.

---

### Likelihood Explanation

The default `deposit_bridge_fee` already has `fee_min = 0`. The DAO enabling a non-zero `fee_rate` without simultaneously setting a non-zero `fee_min` is a plausible operational step (e.g., introducing a small percentage fee for the first time). No attacker capability beyond being a normal bridge user is required once the configuration is in that state. The `assert_valid` path provides no safety net.

---

### Recommendation

Add a coherence check in `BridgeFee::assert_valid` or `Config::assert_valid`:

```rust
// Option A – require fee_min > 0 whenever fee_rate > 0
if self.fee_rate > 0 {
    require!(self.fee_min > 0, "fee_min must be > 0 when fee_rate > 0");
}

// Option B – cross-field check in Config::assert_valid
if self.deposit_bridge_fee.fee_rate > 0 && self.deposit_bridge_fee.fee_min == 0 {
    require!(
        self.min_deposit_amount * u128::from(self.deposit_bridge_fee.fee_rate)
            / u128::from(MAX_RATIO) >= 1,
        "min_deposit_amount too low: fee truncates to zero"
    );
}
```

Option A is simpler and eliminates the class of misconfiguration entirely.

---

### Proof of Concept

**Configuration** (valid per `assert_valid`):
```
deposit_bridge_fee = { fee_min: 0, fee_rate: 1, protocol_fee_rate: 9000 }
min_deposit_amount = 9999  // satoshis
```

**Fee calculation for a deposit of 9 999 satoshis**:
```
fee = max(9999 * 1 / 10000, 0)
    = max(0, 0)          // integer truncation
    = 0
```

**Result**: `mint_amount = 9999 - 0 = 9999` satoshis of nBTC minted; `protocol_fee = 0`; `relayer_fee = 0`. The user pays no fee. By repeating deposits at 9 999 satoshis, any user can bridge arbitrary amounts of BTC to nBTC with zero protocol cost.

The root cause is in `BridgeFee::get_fee` at [1](#0-0)  and the absence of a coherence guard in `BridgeFee::assert_valid` at [2](#0-1)  and `Config::assert_valid` at [3](#0-2) . The fee is applied in `internal_verify_deposit` at [4](#0-3) .
