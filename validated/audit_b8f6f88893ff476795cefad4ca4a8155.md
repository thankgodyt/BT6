### Title
Unconditional `validatePerasCert` Acceptance Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every certificate it receives, performing no cryptographic, quorum, or eligibility checks. This stub is wired directly into the production node-to-node Peras certificate diffusion inbound handler. Any unprivileged peer can therefore inject a `PerasCert` for an arbitrary block, which will be accepted, stored, and used to apply a `PerasWeight` boost to that block in chain selection, potentially causing the honest node to switch to a non-canonical chain.

---

### Finding Description

The catch-all `BlockSupportsPeras` instance in `SupportsPeras.hs` (lines 318–389) is explicitly labelled a "degenerate instance for all blks to get things to compile" and its `validatePerasCert` method always returns `Right` without inspecting the certificate's round number, boosted block reference, aggregate BLS signature, voter set, or quorum threshold:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This stub is consumed by `makePerasCertPoolWriterFromChainDB` in `PerasCert.hs`, which is the writer used in the production inbound cert-diffusion handler:

```haskell
(validatePerasCert mkPerasParams) -- TODO replace when actual plumbing is in place
``` [2](#0-1) [3](#0-2) 

The production node-to-node handler wires this writer directly to the network-facing `hPerasCertDiffusionClient`:

```haskell
(makePerasCertPoolWriterFromChainDB systemTime getChainDB)
``` [4](#0-3) 

Once a certificate passes `validatePerasCert` (which it always does), it is forwarded to `ChainDB.addPerasCertAsync`. The ChainDB API documents the consequence explicitly:

> "If this leads to a fork to be weightier than our current selection, this will trigger a fork switch." [5](#0-4) 

The `ValidatedPerasCert` produced by the stub carries `vpcCertBoost = perasWeight params`, the full production `PerasWeight` value, so the injected certificate has the same chain-selection weight as a legitimately forged one. [6](#0-5) 

The `PerasWeightSnapshot` is then consulted during chain selection to decide which fork to prefer: [7](#0-6)

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block point as `pcCertBoostedBlock` and any round number as `pcCertRound`. Because `validatePerasCert` never checks the aggregate BLS signature, the voter set, or whether quorum was actually reached, the certificate is accepted and stored. The boosted block then receives a `PerasWeight` advantage in chain selection. If the adversary targets a block on a minority or adversarial fork, the honest node may switch away from the canonical chain, constituting a chain-selection safety failure reachable by any connected peer.

This matches the allowed impact: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

---

### Likelihood Explanation

The attack requires only a standard node-to-node connection. No keys, stake, or operator access are needed. The `hPerasCertDiffusionClient` handler is active for every connected peer. The adversary needs only to send a well-formed CBOR-encoded `PerasCert` message with an arbitrary `pcCertRound` and `pcCertBoostedBlock`. The stub is the only validation gate and it always passes.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the aggregate BLS signature against the claimed voter set.
2. Checks that the voter set corresponds to the committee elected for `pcCertRound` using the epoch-appropriate `VotingCommittee` (e.g., via `InterEpochVotingCommittee`).
3. Confirms that the accumulated vote weight meets the quorum threshold (`stakeAboveThreshold`).
4. Validates that `pcCertBoostedBlock` refers to a block that is a plausible candidate (within the immutability window, correct era, etc.).

Until the real implementation is in place, the inbound cert-diffusion handler should reject all incoming certificates rather than accept them unconditionally, to avoid the chain-selection manipulation vector. [8](#0-7) 

---

### Proof of Concept

1. Attacker connects to an honest node via the node-to-node protocol.
2. Attacker sends a `PerasCertDiffusion` message containing a `PerasCert` with:
   - `pcCertRound = <any round number>`
   - `pcCertBoostedBlock = <point of a block on an adversarial fork>`
3. The inbound handler calls `processCerts` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert { vpcCertBoost = perasWeight mkPerasParams })`.
4. The validated cert is passed to `ChainDB.addPerasCertAsync`.
5. The ChainDB applies the `PerasWeight` boost to the targeted block and re-runs chain selection.
6. If the boosted block is on a fork that is now heavier than the current selection, the node switches to that fork. [9](#0-8) [10](#0-9)
