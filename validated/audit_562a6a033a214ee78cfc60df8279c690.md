Audit Report

## Title
`msg.value` Forwarded in Full After ETH Already Sent to Recipient in `finTransferExtension`, Permanently Blocking Native ETH Finalization - (File: evm/src/omni-bridge/contracts/OmniBridgeWormhole.sol)

## Summary

`OmniBridgeWormhole.finTransferExtension` calls `_wormhole.publishMessage{value: msg.value}(...)`, but when `payload.tokenAddress == address(0)`, `finTransfer` has already disbursed `payload.amount` of that ETH to the recipient before reaching the extension. The contract's remaining balance is `msg.value - payload.amount`, which is insufficient to cover the `{value: msg.value}` sub-call, causing every native ETH finalization to revert and permanently freezing bridged ETH.

## Finding Description

`OmniBridge.finTransfer` is `payable`. For native ETH transfers (`payload.tokenAddress == address(0)`), it first sends `payload.amount` ETH to the recipient:

```solidity
// OmniBridge.sol lines 317-322
if (payload.tokenAddress == address(0)) {
    (bool success, ) = payload.recipient.call{value: payload.amount}("");
    if (!success) revert FailedToSendEther();
}
```

After this transfer, the contract's ETH balance is reduced by `payload.amount`. Then `finTransferExtension(payload)` is called at line 357. The `OmniBridgeWormhole` override does:

```solidity
// OmniBridgeWormhole.sol lines 109-113
_wormhole.publishMessage{value: msg.value}(
    wormholeNonce,
    messagePayload,
    _consistencyLevel
);
```

`msg.value` here is the **original** full call value. The contract only holds `msg.value - payload.amount` at this point, so the `{value: msg.value}` sub-call reverts with an insufficient-balance error every time (assuming no pre-existing contract ETH balance >= `payload.amount`).

The correct pattern is already applied in `initTransfer`/`initTransferExtension`: `initTransfer` computes `extensionValue = msg.value - amount - nativeFee` for native ETH (line 391) and passes it explicitly to `initTransferExtension`, which then uses `{value: value}` (line 143). `finTransferExtension` receives no such pre-computed value and incorrectly uses `msg.value` directly. ## Impact Explanation

Any cross-chain transfer of native ETH whose finalization goes through `OmniBridgeWormhole` (deployed on BNB, Arbitrum, Base, Polygon) will always revert. The user's tokens are already locked/burned on the source chain (NEAR or another EVM chain), but `finTransfer` can never succeed, so the funds are permanently frozen with no recovery path. This matches the "permanent freezing of bridged funds" critical impact class. [6](#0-5) 

## Likelihood Explanation

Any unprivileged relayer or user who attempts to finalize a native ETH transfer on `OmniBridgeWormhole` triggers this path. The entry point is the public `finTransfer` function. No special role or precondition is required beyond a valid MPC signature for a legitimate native ETH transfer. The condition `tokenAddress == address(0)` is a standard, documented bridge feature for native token transfers. [7](#0-6) 

## Recommendation

Mirror the `initTransferExtension` pattern: compute the remaining ETH value before calling the extension and pass it as an explicit parameter.

In `OmniBridge.sol`, compute the remaining value before calling the extension:

```solidity
uint256 extensionValue = (payload.tokenAddress == address(0))
    ? msg.value - payload.amount
    : msg.value;
finTransferExtension(payload, extensionValue);
```

Update the base `finTransferExtension` signature:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload,
    uint256 value
) internal virtual {}
```

In `OmniBridgeWormhole.sol`, update the override to use the passed value:

```solidity
function finTransferExtension(
    BridgeTypes.TransferMessagePayload memory payload,
    uint256 value
) internal override {
    ...
    _wormhole.publishMessage{value: value}(...);
}
``` [8](#0-7) [9](#0-8) 

## Proof of Concept

1. Deploy `OmniBridgeWormhole` with a mock Wormhole that requires `messageFee() = 10_000 wei`.
2. A user bridges 1 ETH from NEAR to Arbitrum (native ETH, `tokenAddress = address(0)`).
3. A relayer calls `finTransfer` with `msg.value = 1 ETH + 10_000 wei` and a valid MPC signature.
4. `finTransfer` sends 1 ETH to `payload.recipient` — succeeds; contract balance is now `10_000 wei`.
5. `finTransferExtension` attempts `_wormhole.publishMessage{value: 1 ETH + 10_000 wei}(...)` but the contract only holds `10_000 wei` — **reverts**.
6. The entire transaction reverts (all state changes including `completedTransfers[nonce]` are unwound), so the nonce remains available for retry — but every retry will revert for the same reason, permanently preventing finalization of the bridged ETH. [10](#0-9) [3](#0-2)
