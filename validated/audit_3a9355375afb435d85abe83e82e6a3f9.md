### Title
Caller-Supplied `key_version` in `sign_btc_transaction` Allows Any Account to Corrupt MPC Signatures and Lock Bridged Funds — (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The `sign_btc_transaction` entry point accepts a caller-supplied `key_version` parameter with no validation against the canonical key version used to derive the UTXO's locking script. Any unprivileged NEAR account can call this function on any pending withdrawal, supply an arbitrary `key_version`, and cause the MPC to produce a signature that is cryptographically invalid for the UTXO being spent. The contract stores the invalid signature, marks the signing slot as consumed, and advances the pending transaction to the `pending_verify` stage — from which it can never confirm on Bitcoin, locking the bridged funds.

---

### Finding Description

**Analog to the external report:** BeaconKit uses the *active* (mutable) fork version instead of the *genesis* (fixed canonical) fork version when verifying deposit signatures. The analog here is that the bridge uses a *caller-supplied* (mutable, unvalidated) `key_version` instead of a *stored canonical* key version that corresponds to the key used to derive each UTXO's locking script.

**Root cause — `sign_btc_transaction` accepts arbitrary `key_version`:** [1](#0-0) 

The function is decorated with `#[payable]` and `#[pause]` but carries **no** `#[trusted_relayer]` guard and **no** check that `env::predecessor_account_id()` matches `btc_pending_info.account_id`. Any NEAR account can call it on any pending-sign transaction.

The `key_version` is forwarded verbatim to the MPC: [2](#0-1) 

The MPC `sign` contract uses `key_version` to select which generation of its root key to sign with. The deposit address was derived from the root public key stored in `chain_signatures_root_public_key` at deposit time (corresponding to a specific key version). There is no field in `UTXO`, `VUTXO`, or `BTCPendingInfo` that records which `key_version` was in effect when the address was derived, so the contract cannot validate the caller's input.

**Signature stored unconditionally — no cryptographic validation:** [3](#0-2) 

The callback deserialises whatever the MPC returns and stores it. If the MPC signed with the wrong key (because `key_version` was wrong), the signature is still stored and the slot is marked consumed (`signatures[sign_index] = Some(...)`). Once all slots are filled, the PSBT is finalised and the state transitions to `pending_verify`: [4](#0-3) 

The resulting Bitcoin transaction carries a signature that does not satisfy the UTXO's locking script and will be rejected by every Bitcoin node. The bridge is now stuck in `pending_verify` with funds that cannot be recovered without operator intervention.

**Deposit address derivation uses the current root public key — no key-version binding:** [5](#0-4) 

The `generate_public_key` function always reads `chain_signatures_root_public_key` from the live config. Neither the `UTXO` struct nor the `BTCPendingInfo` records which key version was active at deposit time, so there is no on-chain source of truth to validate the caller's `key_version` against.

---

### Impact Explanation

**Medium — Attacker-triggered temporary locking of bridged funds.**

An attacker who front-runs a legitimate `sign_btc_transaction` call with a wrong `key_version` causes the MPC to produce an invalid signature. The contract stores it, marks the slot consumed, and advances the state to `pending_verify`. The signed-but-invalid Bitcoin transaction cannot confirm. The withdrawal funds are locked until an operator creates a cancel or RBF transaction — which itself must be signed, giving the attacker another opportunity to repeat the attack. This matches the allowed impact: *"attacker-triggered temporary locking of bridged funds."*

---

### Likelihood Explanation

**Medium.** The `sign_btc_transaction` function is publicly callable by any NEAR account with no role restriction. Pending-sign transaction IDs are emitted as on-chain events (`GenerateBtcPendingInfo`), so an attacker can trivially monitor for new withdrawal transactions and front-run the legitimate relayer's signing call. The attack requires no special privileges, no capital, and no off-chain infrastructure beyond a NEAR account.

---

### Recommendation

1. **Store the canonical `key_version` at UTXO creation time.** Add a `key_version: u32` field to `UTXO`/`VUTXO` and populate it when the deposit address is derived. Validate the caller-supplied `key_version` against the stored value inside `sign_btc_transaction`.

2. **Restrict `sign_btc_transaction` to trusted callers.** Add a `#[trusted_relayer]` guard (or an equivalent role check) so that only authorised relayers can trigger MPC signing, eliminating the front-running surface.

3. **Validate the signature before storing it.** In `sign_btc_transaction_callback`, verify the returned signature against the expected public key (derived from the stored `key_version`) before writing it to `btc_pending_info.signatures`.

---

### Proof of Concept

1. Alice initiates a withdrawal; the bridge creates a `BTCPendingInfo` in `pending_sign` state and emits a `GenerateBtcPendingInfo` event with `btc_pending_id = "abc123"`.
2. Attacker observes the event and immediately calls:
   ```
   sign_btc_transaction("abc123", 0, 9999)
   ```
   passing `key_version=9999` (any value other than the correct one).
3. The bridge calls `chain_signatures.sign({payload, path, key_version: 9999})`. The MPC signs with key version 9999, producing a signature that does not correspond to the key that controls the UTXO.
4. `sign_btc_transaction_callback` stores the invalid signature; `signatures[0]` is now `Some(...)`.
5. `is_all_signed()` returns `true`; the PSBT is finalised with the invalid signature and the state moves to `pending_verify`.
6. The relayer broadcasts the transaction; every Bitcoin node rejects it (invalid witness/script).
7. The withdrawal is permanently stuck in `pending_verify`. Alice's nBTC has already been transferred to the bridge (step 1 of the withdrawal flow) and cannot be recovered without operator intervention to cancel and re-sign — which the attacker can disrupt again.

                return PromiseOrValue::Value(true);
            }
        }

    }
