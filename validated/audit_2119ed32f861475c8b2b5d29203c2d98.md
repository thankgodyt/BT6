### Title
Peras Certificate Validation Unconditionally Accepts All Certificates — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production `BlockSupportsPeras` instance defines `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate, performing zero cryptographic or semantic checks. This stub is wired directly into the live inbound-certificate pipeline. Any unprivileged peer can send a crafted `PerasCert` with an arbitrary round number and an adversarially chosen boosted block; the certificate will be accepted, stored in the `PerasCertDB`, and its boost weight will feed into chain selection.

---

### Finding Description

**Root cause — missing validation body at definition time.**

`BlockSupportsPeras` declares `validatePerasCert` as the mandatory acceptance gate for Peras certificates. The only concrete instance in the codebase is the blanket:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its implementation of `validatePerasCert` (lines 353–358) is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
```

The function ignores both the `PerasParams` argument and every field of the certificate. It returns `Right` unconditionally. [1](#0-0) 

**Production wiring.**

`processCerts` in the `ObjectDiffusion` inbound pipeline is called with `validatePerasCert mkPerasParams` as its validation callback:

```haskell
(validatePerasCert mkPerasParams)
``` [2](#0-1) 

`processCerts` partitions the batch into `(errors, validCerts)` and adds every element of `validCerts` to the `PerasCertDB`. Because `validatePerasCert` never produces a `Left`, the error list is always empty and every received certificate is stored. [3](#0-2) 

**Chain-selection consumption.**

During `ChainDB.openDBInternal`, the weight snapshot from the `PerasCertDB` is passed directly to `ChainSel.initialChainSelection`:

```haskell
initialWeights <- atomically $ PerasCertDB.getWeightSnapshot perasCertDB
chain <-
  ChainSel.initialChainSelection
    ...
    (forgetFingerprint initialWeights)
``` [4](#0-3) 

**Structural analogy to the external report.**

The external report describes a `LockingMultiRewards` constructor that was deployed without calling `BlastYields.configureDefaultClaimables`, leaving gas-yield mode permanently unconfigured. The pattern here is identical: the `BlockSupportsPeras` instance was defined (the Haskell equivalent of a constructor) without implementing the required validation body, leaving the certificate acceptance gate permanently open. In both cases a component is instantiated, a critical initialization/configuration step is absent, and the resulting incorrect state is permanent for the lifetime of the running node.

---

### Impact Explanation

An attacker who can establish a peer connection can send a `PerasCert` with:
- an arbitrary `pcCertRound` (any round number, including future rounds), and
- a `pcCertBoostedBlock` pointing to any block the attacker wishes to boost.

Because `validatePerasCert` returns `Right` unconditionally, the certificate is stored in the `PerasCertDB`. `PerasCertDB.getWeightSnapshot` then returns a snapshot that includes the injected boost weight (`perasWeight mkPerasParams = 15`). Chain selection uses this snapshot to assign Peras boost weights to candidate chains. By injecting certificates that boost an adversarially chosen block, the attacker can cause an honest node to prefer a non-canonical or adversarially controlled chain over the honest canonical chain.

This is a bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation — matching the "Critical: bypass of Peras voting or certificate checks" impact category.

---

### Likelihood Explanation

The `PerasCertDB` is unconditionally created during every `ChainDB.openDBInternal` call. The `ObjectDiffusion` mini-protocol for Peras certificates is present and wired in the production codebase. No special privileges, stake, keys, or operator access are required; any peer that can open a connection to the node can send crafted certificates. The only precondition is that the Peras certificate diffusion mini-protocol is active on the target node.

---

### Recommendation

Implement the actual cryptographic and semantic validation in `validatePerasCert` before the Peras certificate diffusion path is enabled in production. At minimum the function must:

1. Verify the aggregate BLS signature over `(pcCertRound, pcCertBoostedBlock)` against the claimed voter set.
2. Check that the certificate's round number is within the valid window relative to the current chain tip.
3. Verify that the boosted block exists and is within the permissible age range (`perasBlockMinSlots`).
4. Enforce the one-certificate-per-round invariant (no equivocation).

Until these checks are in place, the inbound certificate pipeline should be disabled or the `validatePerasCert` stub should return `Left PerasValidationErr` by default rather than `Right`.

---

### Proof of Concept

1. Attacker connects to a node and sends a `PerasCert { pcCertRound = R, pcCertBoostedBlock = adversarialBlock }` via the Peras certificate `ObjectDiffusion` mini-protocol.
2. `processCerts` (in `ObjectPool/PerasCert.hs`) calls `validatePerasCert mkPerasParams cert`.
3. `validatePerasCert` returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })` unconditionally — no signature, no round-range, no block-age check is performed.
4. The certificate is stored in the `PerasCertDB`.
5. `PerasCertDB.getWeightSnapshot` returns a snapshot that includes a boost of weight 15 for `adversarialBlock`.
6. `ChainSel.initialChainSelection` (and subsequent chain-selection events triggered by `addPerasCertAsync`) uses this snapshot, assigning extra weight to the adversarially chosen block and potentially causing the node to select a non-canonical chain. [5](#0-4) [6](#0-5) [7](#0-6)
