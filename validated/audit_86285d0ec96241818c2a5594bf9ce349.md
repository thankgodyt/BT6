### Title
Missing Cryptographic Validation in Peras Certificate and Vote Acceptance — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance provides a stub `validatePerasCert` that unconditionally returns `Right` (success) without performing any cryptographic checks. Both production inbound-certificate paths (`makePerasCertPoolWriterFromCertDB` and `makePerasCertPoolWriterFromChainDB`) call this stub directly. An unprivileged peer can therefore inject arbitrary Peras certificates that are accepted without BLS-signature, VRF-eligibility, or committee-membership verification, and those certificates are then stored in the ChainDB and applied to chain selection.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate before any certificate is stored. The only deployed instance is the universal one:

```haskell

-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  -- TODO: perform actual validation against all
  -- possible 'PerasValidationErr' variants
  -- see https://github.com/tweag/cardano-peras/issues/120
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
``` [1](#0-0) 

This stub is wired directly into both production pool-writer constructors:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` treats every certificate that passes `validateCert` as legitimate and forwards it to `addCert`: [3](#0-2) 

Because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every peer-supplied certificate is stored.

The concrete `V1.PerasCert` type carries a full BLS aggregate signature (`pcSignature :: AggregateVoteSignature PerasBLSCrypto`) and per-voter VRF eligibility proofs (`pcVoters :: PerasCertVoters`): [4](#0-3) 

The cryptographic primitives to verify these (`verifyAggregateVoteSignature`, `batchVerifyVRFOutputs`) exist in `PerasBLSCrypto`: [5](#0-4) 

None of them are invoked on the inbound path.

A secondary, structurally identical gap exists in `validatePerasVote`: it checks only that the voter ID appears in the stake distribution but never verifies the BLS vote signature or VRF eligibility proof: [6](#0-5) 

Both pool writers for votes use this same stub: [7](#0-6) 

---

### Impact Explanation

Peras certificates carry a `vpcCertBoost` weight (`perasWeight params`) that is applied during chain selection. A certificate accepted into the ChainDB for a given round boosts the apparent weight of the block it references. Because `validatePerasCert` is a no-op, any peer can:

1. Craft a `PerasCert` with an arbitrary `pcCertRound` and `pcCertBoostedBlock` pointing to a non-canonical or adversarial block.
2. Send it via the object-diffusion mini-protocol.
3. Have it unconditionally stored and applied to chain selection, causing the honest node to prefer a non-canonical chain.

This is a **bypass of Peras certificate/vote verification** enabling unauthorized certificate acceptance and chain-selection manipulation by an unprivileged peer — matching the "Critical: bypass of certificate/vote checks" and "High: chain selection bug" categories in the allowed impact scope.

---

### Likelihood Explanation

The attack path is direct and requires no special privileges: any peer that can speak the object-diffusion mini-protocol can send a crafted `PerasCert`. The stub is the only deployed instance (no block-specific override exists in the codebase), and both the `CertDB` and `ChainDB` pool-writer paths are affected. The TODO comments confirm this is a known placeholder, not an intentional design choice, making it a real gap rather than a deliberate trade-off.

---

### Recommendation

1. **`validatePerasCert`**: Before storing any inbound certificate, verify (a) the aggregate BLS signature over `(pcRoundNo, pcBoostedBlock)` using `verifyAggregateVoteSignature`, (b) each voter's committee membership and seat index against the current committee snapshot, and (c) VRF eligibility proofs for non-persistent voters using `batchVerifyVRFOutputs`.

2. **`validatePerasVote`**: In addition to the stake-distribution lookup, verify the BLS vote signature (`verifyVoteSignature`) and, for non-persistent voters, the VRF eligibility proof.

3. Until the concrete validation logic is wired in, consider gating the object-diffusion handlers behind a feature flag so that the stub is never reachable from a live peer connection.

---

**Attacker-controlled entry path:**

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
