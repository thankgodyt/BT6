### Title
Unbacked nBTC Supply Inflation via `safe_mint` Minting Before User-Registration Check — (File: `contracts/nbtc/src/lib.rs`)

### Summary
The `safe_mint` function in the nBTC token contract unconditionally mints `amount` tokens into the bridge's own token balance **before** verifying that the recipient account is registered. When the recipient is unregistered, the function returns `U128(0)` (signalling failure to the bridge callback) but never burns the already-minted tokens. Each such failure permanently inflates the nBTC total supply beyond its BTC-backed amount.

### Finding Description
`safe_mint` is the entry point used by the satoshi-bridge for the "safe deposit" flow (deposits that must revert cleanly on failure). Its implementation is:

```rust
// contracts/nbtc/src/lib.rs  lines 101-124
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← returns 0, no burn
    }
    // ... transfer to user
}
``` [1](#0-0) 

`internal_deposit` increases both `bridge_id`'s balance and `ft_total_supply` atomically. [2](#0-1) 

When `account_id` has no registered storage slot, the early-return path exits without calling any burn or `internal_withdraw`, leaving the freshly minted tokens stranded in `bridge_id`'s balance. [3](#0-2) 

The bridge's own documentation for `verify_deposit_v2` states the safe-deposit path "reverts the whole transaction if minting fails (no lost & found)". [4](#0-3) 

The revert guarantee is broken: the nBTC contract does not burn on failure, so the bridge callback would need to issue a separate `burn` call to restore supply integrity. If it does not (or if the callback itself fails), the inflation is permanent.

### Impact Explanation
Every failed `safe_mint` call (unregistered recipient) permanently increases `ft_total_supply()` by `amount` without any corresponding BTC being credited. The bridge's own nBTC balance grows with unbacked tokens. Over repeated failures the circulating supply of nBTC exceeds the BTC held by the bridge, breaking the 1:1 peg invariant. Downstream systems (indexers, DeFi integrations, auditors) that rely on `ft_total_supply` to verify backing will observe a falsely inflated supply. Additionally, if the bridge ever uses its own nBTC balance for emergency recovery or fee distribution, those unbacked tokens could be transferred to real users, constituting an unauthorized release of value.

**Impact tier:** Medium — broken callback rollback leading to permanent supply inflation above backed BTC, requiring operator intervention to identify and burn orphaned tokens.

### Likelihood Explanation
The trigger is straightforward and requires no privilege:

1. A user makes a real BTC deposit targeting a NEAR account that has **not** called `storage_deposit` on the nBTC contract.
2. A relayer calls `verify_deposit_v2` (or the deprecated `safe_verify_deposit`) with `deposit_msg.safe_deposit = Some(..)`.
3. The bridge verifies the Merkle proof and calls `safe_mint(account_id, amount, ...)` on the nBTC contract.
4. Because `account_id` has no storage slot, `safe_mint` mints `amount` to `bridge_id` and returns `U128(0)`.
5. Tokens are permanently stranded in `bridge_id`'s balance; total supply is inflated.

This is reachable by any unprivileged NEAR account. New users who have never interacted with the nBTC contract will not have a storage slot, making accidental triggering likely and deliberate triggering trivial.

### Recommendation
Move the registration check **before** the `internal_deposit` call, or add an explicit `internal_withdraw` / burn on the early-return path:

```rust
// Option A: check first, mint only if registered
if self.token.accounts.get(&account_id).is_none() {
    return PromiseOrValue::Value(U128(0));
}
self.token.internal_deposit(&self.bridge_id, amount.into());
// ... transfer to user

// Option B: burn on failure (if minting must happen first)
self.token.internal_deposit(&self.bridge_id, amount.into());
if self.token.accounts.get(&account_id).is_none() {
    self.token.internal_withdraw(&self.bridge_id, amount.into()); // restore supply
    return PromiseOrValue::Value(U128(0));
}
```

Option A is preferred because it avoids the unnecessary state mutation entirely.

### Proof of Concept
1. Deploy nBTC and satoshi-bridge contracts on NEAR testnet.
2. Record `ft_total_supply()` → `S0`.
3. Alice sends 0.001 BTC to her bridge deposit address. Her NEAR account `alice.near` has **never** called `storage_deposit` on the nBTC contract.
4. A relayer submits `verify_deposit_v2` with `deposit_msg.safe_deposit = Some(...)` and a valid Merkle proof.
5. The bridge calls `safe_mint("alice.near", 100_000, None)`.
6. Inside `safe_mint`: `internal_deposit(&bridge_id, 100_000)` executes; `accounts.get("alice.near")` returns `None`; function returns `U128(0)`.
7. Record `ft_total_supply()` → `S1`. Observe `S1 = S0 + 100_000` even though Alice received 0 nBTC.
8. Alice's BTC is locked in the bridge address; no nBTC was issued to her; yet total supply grew by 100,000 satoshis worth of nBTC — unbacked inflation confirmed.
