### Title
User-Supplied Zero Gas Fee in Refund Request Bypasses `min_btc_gas_fee` Policy, Producing an Unconfirmable Refund Transaction - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary

In `request_refund_callback`, the caller-supplied `gas_fee` is accepted as long as it is strictly less than the deposit amount. There is no lower-bound check against the protocol's configured `min_btc_gas_fee`. An unprivileged depositor can pass `gas_fee = Some(0)`, causing the stored `RefundRequest` to carry a zero gas fee. When `execute_refund` later builds the Bitcoin PSBT from that stored value, the output equals the full deposit input, leaving a zero miner fee. A zero-fee Bitcoin transaction is non-standard and will not be relayed or confirmed, permanently stalling the refund in a `PendingSign` state until an operator intervenes with RBF.

### Finding Description

`request_refund_callback` resolves the gas fee as follows:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The only guard is `resolved_gas_fee < amount`. There is no check that `resolved_gas_fee >= config.min_btc_gas_fee`. The resolved value is then stored verbatim in the `RefundRequest`:

```rust
let refund_request = RefundRequest {
    ...
    gas_fee: resolved_gas_fee,
    ...
};
``` [2](#0-1) 

Later, `refund_execution_inputs` computes `refund_amount = amount - gas_fee` with no minimum-fee enforcement:

```rust
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [3](#0-2) 

`internal_execute_refund` then builds the PSBT directly from `refund_amount` without invoking any gas-fee range check:

```rust
let refund_output = self.build_refund_output(&refund_request.refund_address, refund_amount);
let mut psbt = PsbtWrapper::new(vec![outpoint], vec![refund_output]);
``` [4](#0-3) 

By contrast, the withdrawal and active-UTXO-management paths both enforce `min_btc_gas_fee` through `check_psbt_output_all_change_address` and `check_withdraw_psbt`:

```rust
require!(
    gas_fee >= config.min_btc_gas_fee && gas_fee <= config.max_btc_gas_fee,
    ...
);
``` [5](#0-4) 

The refund path is the only financial path that skips this check entirely.

The `min_btc_gas_fee` field exists precisely to guarantee that every bridge-constructed Bitcoin transaction carries a fee sufficient for timely confirmation: [6](#0-5) 

### Impact Explanation

When `gas_fee = 0` is stored and `execute_refund` is called:

- `refund_amount = deposit_amount − 0 = deposit_amount`
- The PSBT output value equals the input value → miner fee = 0 satoshis
- A zero-fee transaction is non-standard; Bitcoin nodes will not relay it and miners will not include it
- The `BTCPendingInfo` is created with `max_gas_fee = 0`, locking the refund UTXO in `PendingSign` state
- The depositor's BTC is temporarily locked; the bridge cannot process a normal deposit for the same UTXO while the pending info exists

This matches the allowed Medium impact: **attacker-triggered temporary locking of bridged funds** and **bypass of bridge limits or policies** (`min_btc_gas_fee`).

### Likelihood Explanation

Any NEAR account that has sent BTC to a bridge deposit address can call `request_refund`. The `gas_fee` parameter is optional and user-supplied. Passing `gas_fee = Some(0)` requires no special privilege, no leaked key, and no third-party compromise. The timelock (default 2 days for pre-authorized addresses, 14 days otherwise) delays but does not prevent exploitation. An operator can reject the request during the timelock window, but if `execute_refund` is called immediately after the timelock expires, the stuck PSBT is created before the operator can react.

### Recommendation

Add a minimum-fee guard in `request_refund_callback` immediately after resolving the gas fee:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee >= config.min_btc_gas_fee,
    "Gas fee is below the minimum required"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

This mirrors the enforcement already present in `check_psbt_output_all_change_address` and `check_withdraw_psbt`, closing the gap in the refund path.

### Proof of Concept

1. Attacker deposits BTC to a bridge address, obtaining a confirmed UTXO.
2. Attacker calls `request_refund(deposit_msg, refund_address, tx_bytes, vout, proof, gas_fee = Some(0))`.
3. `request_refund_callback` resolves `resolved_gas_fee = 0`; the check `0 < deposit_amount` passes; the `RefundRequest` is stored with `gas_fee = 0`.
4. After the timelock elapses, attacker (or anyone) calls `execute_refund(utxo_storage_key, ...)`.
5. `refund_execution_inputs` computes `refund_amount = deposit_amount − 0 = deposit_amount`; the check `refund_amount > 0` passes.
6. `internal_execute_refund` builds a PSBT: one input of `deposit_amount` sat, one output of `deposit_amount` sat → miner fee = 0.
7. The PSBT is signed by MPC and broadcast. Bitcoin nodes reject the zero-fee transaction; it never confirms.
8. The deposit UTXO is locked in `BTCPendingInfo` with `max_gas_fee = 0`, and the depositor's BTC is stuck until an operator performs RBF or manual intervention.
