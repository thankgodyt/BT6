Audit Report

## Title
Missing `assert_one_yocto()` in `update_transfer_fee` Enables Function Call Key to Inflate Transfer Fee — (File: `near/omni-bridge/src/lib.rs`)

## Summary

`update_transfer_fee` is `#[payable]` but contains no `assert_one_yocto()` guard. When the `native_fee` component of the new fee equals the current `native_fee`, the required attached deposit is exactly 0 yoctoNEAR, which NEAR Function Call keys are permitted to supply. Any website that holds a Function Call key for the omni-bridge contract on behalf of a user can therefore call this function silently, inflating the token fee on a pending transfer to just below the full transfer amount and causing the relayer to deliver dust to the user while collecting nearly all bridged tokens as fee.

## Finding Description

`update_transfer_fee` at lines 386–436 of `near/omni-bridge/src/lib.rs` enforces the deposit constraint dynamically:

```rust
let diff_native_fee = fee.native_fee.0
    .checked_sub(current_fee.native_fee.0)
    .near_expect(BridgeError::LowerFee);

require!(
    NearToken::from_yoctonear(diff_native_fee) == env::attached_deposit(),
    BridgeError::InvalidAttachedDeposit.as_ref()
);
```

When the attacker keeps `fee.native_fee == current_fee.native_fee`, `diff_native_fee = 0`, so `env::attached_deposit()` must be 0. NEAR Function Call keys — which dApps routinely store after a user signs in — are permitted to call contract methods only when the attached deposit is 0. There is no `assert_one_yocto()` to block this path.

The only other guard is the sender check (lines 404–408):

```rust
require!(
    fee.fee == current_fee.fee
        || OmniAddress::Near(env::predecessor_account_id())
            == transfer.message.sender,
    BridgeError::SenderCanUpdateTokenFeeOnly.as_ref()
);
```

A Function Call key is scoped to the user's own account, so `env::predecessor_account_id()` returns the user's account ID, satisfying `== transfer.message.sender`. The fee ceiling check (lines 399–402) allows `fee.fee` up to `transfer.message.amount - 1`.

After the fee is inflated, `amount_without_fee()` (defined in `near/omni-types/src/lib.rs` line 593) returns `amount - fee.fee`, which can be reduced to 1. The relayer calls `sign_transfer` (lines 444–521), reads the stored (now-inflated) fee, and signs a payload for 1 token unit to the destination chain. The relayer then claims `amount - 1` tokens as fee via `claim_fee`.

## Impact Explanation

This is a concrete instance of **fee mis-accounting / unauthorized balance manipulation that changes user balances**, matching the Critical allowed impact scope. Tokens already locked or burned in `init_transfer_internal` are effectively stolen: the user receives 1 token unit on the destination chain while the relayer collects `transfer.amount - 1` tokens as fee. No admin access, leaked keys, or MPC compromise is required.

## Likelihood Explanation

The attack requires three realistic conditions: (1) the user has previously signed in to any website that requested a Function Call key for the omni-bridge contract — standard dApp onboarding on NEAR; (2) that website is malicious or later compromised — a well-documented threat in web3; (3) the user has a pending transfer. The attacker does not need to be a trusted relayer; the legitimate relayer processes the transfer normally, unaware the fee was inflated, because it simply reads the current stored fee. The attack is repeatable for every pending transfer associated with any user who has granted a Function Call key.

## Recommendation

Add `assert_one_yocto()` at the top of `update_transfer_fee`, consistent with the pattern already used in `storage_withdraw` and `storage_unregister` in `near/omni-bridge/src/storage.rs` (lines 188 and 216). The `diff_native_fee` attachment check must then subtract 1 yoctoNEAR from `env::attached_deposit()` before comparing, or the mandatory 1 yocto must be treated as a separate deposit from the native-fee delta.

```rust
#[payable]
#[pause]
pub fn update_transfer_fee(&mut self, transfer_id: TransferId, fee: UpdateFee) {
    assert_one_yocto();
    // adjust diff_native_fee check: env::attached_deposit() - 1 yocto == diff_native_fee
    ...
}
```

## Proof of Concept

1. User signs in to `bridge-dapp.example`; browser stores a Function Call key for `omni-bridge.near` on the user's NEAR account.
2. User calls `ft_transfer_call` on their NEP-141 token contract, sending 1,000,000 tokens to `omni-bridge.near` with `msg = InitTransferMsg { recipient: "eth:0xVictim", fee: { fee: 0, native_fee: 0 }, ... }`. Transfer is stored with `transfer_id = T`.
3. Malicious/compromised website uses the stored Function Call key (0-deposit call) to invoke:
   ```json
   {
     "method": "update_transfer_fee",
     "args": { "transfer_id": T, "fee": { "Fee": { "fee": "999999", "native_fee": "0" } } },
     "deposit": "0"
   }
   ```
   - `diff_native_fee = 0`, `attached_deposit = 0` ✓  
   - `predecessor == sender` ✓  
   - `999999 >= 0 && 999999 < 1000000` ✓  
   - No `assert_one_yocto()` → call succeeds.
4. Relayer reads the `UpdateFeeEvent`, calls `sign_transfer(T, relayer.near, Some({fee:999999, native_fee:0}))`. `amount_without_fee = 1`. MPC signs a payload for 1 token to `0xVictim`.
5. On the destination chain, `finTransfer` delivers 1 token to the user. Relayer calls `claim_fee` and receives 999,999 tokens.

A local unit test can reproduce step 3 by calling `contract.update_transfer_fee(transfer_id, UpdateFee::Fee(Fee { fee: U128(amount - 1), native_fee: U128(0) }))` with `setup_test_env` configured for the sender account and `attached_deposit = NearToken::from_yoctonear(0)`, mirroring the existing test harness in `near/omni-bridge/src/tests/lib_test.rs` lines 345–388.
