### Title
Batch-rejection in `processVotes`/`processCerts` allows an unprivileged peer to suppress valid Peras votes and certificates - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

The `processVotes` and `processCerts` functions in the Peras ObjectDiffusion miniprotocol apply an all-or-nothing validation policy to inbound batches: if **any** item in a batch fails `validatePerasVote`/`validatePerasCert`, the **entire** batch is thrown away and the sending peer is disconnected. An unprivileged peer can exploit this by crafting a batch that mixes one invalid vote (or certificate) with multiple valid ones, causing all valid items to be silently dropped. This is structurally identical to the LinearVesting bug: a validation check that is too strict permanently blocks a legitimate operation.

---

### Finding Description

**Root cause — `processVotes`** (`PerasVote.hs`, lines 178–201):

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (...) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _) ->                          -- ← valid votes in the Right list are discarded
      throw (PerasVoteValidationError errs)
``` [1](#0-0) 

The `(errs, _)` branch discards the entire `_` (the valid, right-hand side) and throws an exception. The same pattern is present in `processCerts`: [2](#0-1) 

**Validation that can return `Left`** — `validatePerasVote` in `Block/SupportsPeras.hs`:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
  | otherwise = Left PerasValidationErr
``` [3](#0-2) 

Any vote whose `pvVoteVoterId` is absent from the current stake distribution returns `Left`. An attacker who is not a registered voter can trivially produce such a vote.

**Production wiring** — `NodeToNode.hs` wires `makePerasVotePoolWriterFromChainDB` directly into the node-to-node `hPerasVoteDiffusionClient` handler, making `processVotes` reachable from any unprivileged peer: [4](#0-3) 

**Peras votes drive chain selection** — from the changelog, Peras certificates cause the ChainDB to re-run chain selection, preferring the chain with the highest Peras weight: [5](#0-4) 

`addPerasCertAsync` triggers `chainSelectionForBlock` for the boosted block: [6](#0-5)

### Impact Explanation

**Medium — miniprotocol flaw that materially weakens Peras vote and certificate authorization without relying on DoS.**

By sending a single crafted batch (one invalid vote + N valid votes), an attacker causes the receiving node to:

1. Discard all N valid votes — they are never written to the `PerasVoteDB`.
2. Disconnect from the attacker (who can immediately reconnect and repeat).
3. Fail to accumulate the quorum needed to forge a Peras certificate.
4. Fall back to pure Praos chain selection, losing the Peras weight boost on the honest chain.

Because Peras certificates directly influence `preferAnchoredCandidate` via `PerasWeightSnapshot`, suppressing them can cause an honest node to prefer a chain that is less boosted than the canonical one, weakening the security guarantees Peras is designed to provide beyond Praos.

---

### Likelihood Explanation

- **No special privileges required.** Any peer that can open a `PerasVoteDiffusion` connection can send a crafted batch.
- **Trivial to construct.** The attacker only needs to include one vote whose `pvVoteVoterId` is not in the current stake distribution (e.g., a freshly generated key hash).
- **Repeatable.** After disconnection the attacker reconnects and repeats, continuously suppressing honest votes relayed through that peer.
- **Timing sensitivity.** Peras rounds are time-bounded; suppressing votes for even one round prevents certificate formation for that round, permanently losing the boost for that round's block.

---

### Recommendation

Replace the all-or-nothing batch policy with a per-item policy: accept valid items and silently drop (or log) invalid ones. Disconnect the peer only if the fraction of invalid items exceeds a configurable threshold, or if the invalid items carry a cryptographic signature that proves deliberate forgery.

```haskell
-- Proposed fix sketch
case partitionEithers validationResults of
  ([], validatedVotes) ->
    mapM_ (addVote . WithArrivalTime now) validatedVotes
  (errs, validatedVotes) -> do
    -- Log the errors but still add the valid votes
    mapM_ (addVote . WithArrivalTime now) validatedVotes
    -- Optionally disconnect if too many invalid items
    when (length errs > threshold) $
      throw (PerasVoteValidationError errs)
```

This mirrors the LinearVesting fix: rather than reverting the entire operation when one sub-component fails its expiry check, the fix allows the valid sub-operations to proceed.

### Proof of Concept

**Private-testnet sequence:**

1. Start a two-node private testnet with Peras enabled.
2. On the attacker node, construct a `PerasVote` batch:
   - Generate a fresh key pair not registered in the stake distribution → `invalidVote`.
   - Collect N legitimate votes from honest committee members → `validVotes`.
   - Send `[invalidVote] ++ validVotes` as a single ObjectDiffusion batch to the victim node.
3. Observe on the victim node:
   - `processVotes` calls `validatePerasVote` for each item.
   - `invalidVote` returns `Left PerasValidationErr` (voter not in stake distribution).
   - `partitionEithers` yields `(errs=[...], _=[validatedVotes])`.
   - The `(errs, _)` branch fires: `throw (PerasVoteValidationError errs)`.
   - All `validVotes` are discarded; the victim disconnects from the attacker.
4. Verify that the victim's `PerasVoteDB` contains none of the valid votes.
5. Confirm that no Peras certificate is forged for that round, and that chain selection proceeds without the Peras weight boost. [7](#0-6) [8](#0-7)

  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool

      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
