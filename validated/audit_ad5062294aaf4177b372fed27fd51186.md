Audit Report

## Title
Floor Division in `normalize_amount` Permanently Locks/Burns User Tokens When Transfer Amount Rounds to Zero - (File: near/omni-bridge/src/lib.rs)

## Summary

`normalize_amount` uses integer floor division to scale token amounts across decimal boundaries. When a user initiates a transfer whose `amount_without_fee` is smaller than `10^diff_decimals`, the normalized result is zero. The relayer's subsequent `sign_transfer` call unconditionally panics with `ERR_INVALID_AMOUNT_TO_TRANSFER`, but the user's tokens were already burned or locked during `init_transfer_internal`. No cancel or refund entrypoint exists, leaving the funds permanently frozen.

## Finding Description

**Root cause — `normalize_amount` (L2784–2787):**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

The doc-comment at L2781–2783 acknowledges floor-division dust but only addresses the case where `normalize_amount > 0`; it does not address the case where the entire amount rounds to zero.

**Step 1 — `init_transfer` validation is insufficient (L554–557):**

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

Only `fee < amount` is checked. There is no pre-flight check that `normalize_amount(amount - fee) > 0`.

**Step 2 — `init_transfer_internal` locks/burns tokens and returns success (L1850–1857):**

```rust
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

`burn_tokens_if_needed` fires via `.detach()` — a fire-and-forget cross-contract call that executes regardless of future call outcomes. `lock_tokens_if_needed` increments the `locked_tokens` counter. The function then returns `U128(0)`, signalling to the NEP-141 standard that all tokens are kept by the bridge.

**Step 3 — `sign_transfer` panics on zero normalized amount (L475–485):**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

`sign_transfer` is a separate NEAR transaction (decorated `#[trusted_relayer]`). When it panics, the NEAR runtime reverts only that call. The transfer message remains in `pending_transfers` and the tokens remain burned/locked.

**No recovery path exists:** A search of the contract reveals no public `cancel_transfer`, `refund_transfer`, or equivalent entrypoint. `remove_transfer_message` and `remove_transfer_message_without_refund` are private helpers called only in specific internal flows (storage failure, `claim_fee`, `fin_transfer`). None of these flows are reachable for a transfer whose `sign_transfer` permanently panics.

## Impact Explanation

This constitutes **permanent freezing of bridged funds**:

- For bridge-deployed tokens: `burn_tokens_if_needed` permanently destroys the user's tokens (total supply reduced, no mint-back path).
- For native/non-deployed tokens: `lock_tokens_if_needed` increments `locked_tokens`, and the tokens held in bridge escrow can never be unlocked because no cancel path exists.

The transfer message persists in `pending_transfers` indefinitely but can never be finalized (every `sign_transfer` attempt panics) and can never be cancelled (no such entrypoint). This matches the allowed critical impact: *permanent freezing of bridged funds* and *decimal/normalization abuse that changes user or protocol balances*.

## Likelihood Explanation

Any token holder can trigger this by calling `ft_transfer_call` with a sufficiently small amount — a fully unprivileged action. The `init_transfer` guard only checks `fee < amount`; it does not validate the normalized result. For tokens with `origin_decimals = 24` and `decimals = 8` (diff = 16), any transfer below `10^16` base units triggers the path. For the common NEAR→EVM case (diff = 6), any transfer below `10^6` base units triggers it. These thresholds are reachable through UI rounding errors or deliberate dust sends. The condition is repeatable and requires no special privilege.

## Recommendation

Add a pre-flight normalization check inside `init_transfer` (before `init_transfer_internal` is called), so tokens are never locked or burned for an amount that will round to zero:

```rust
let token_address = self.get_token_address(
    init_transfer_msg.get_destination_chain(),
    token_id.clone(),
).near_expect(BridgeError::TokenNotFound);
let decimals = self.token_decimals
    .get(&token_address)
    .near_expect(BridgeError::TokenDecimalsNotFound);
let normalized = Self::normalize_amount(
    amount.0.checked_sub(init_transfer_msg.fee.0)
        .near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
```

This mirrors the existing guard in `sign_transfer` but places it at the point of commitment, before any tokens are escrowed.

## Proof of Concept

1. Register a NEAR token on the bridge with `origin_decimals = 24`, EVM `decimals = 8` (diff = 16).
2. Call `ft_transfer_call` on the token contract with `amount = 5 * 10^15`, `fee = 0`, valid EVM recipient, targeting the bridge contract.
3. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `burn_tokens_if_needed` fires (`.detach()`), burning `5 * 10^15` tokens.
   - `lock_tokens_if_needed` increments `locked_tokens` by `5 * 10^15`.
   - Returns `U128(0)` — bridge keeps all tokens.
4. Relayer calls `sign_transfer` for the resulting `TransferId`.
5. `normalize_amount(5 * 10^15, diff=16) = 5 * 10^15 / 10^16 = 0`.
6. `require!(0 > 0, ...)` panics — only `sign_transfer` reverts.
7. Transfer message remains in `pending_transfers`; tokens are permanently burned/locked. No refund is issued.

A local unit test can reproduce steps 3–7 by directly calling `init_transfer_internal` with a crafted `TransferMessage` (small amount, large decimal diff) and then calling `sign_transfer`, asserting the panic and verifying `locked_tokens` is non-zero with no recovery path.
