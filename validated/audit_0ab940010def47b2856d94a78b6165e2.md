### Title
`safe_verify_deposit` Bypasses `deposit_bridge_fee` Protocol Fee — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

### Summary
The `safe_verify_deposit` code path mints the full BTC deposit amount as nBTC without deducting the `deposit_bridge_fee`, while the standard `verify_deposit` path correctly deducts the fee and credits the `protocol_fee` portion to `cur_available_protocol_fee`. Any user can choose the `safe_verify_deposit` path from the start, permanently bypassing the protocol fee on deposits.

### Finding Description
In `internal_verify_deposit` (the standard deposit path), the bridge correctly calculates and applies fees:

```rust
let deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount);
let mint_amount = deposit_amount - deposit_fee;
let (protocol_fee, relayer_fee) = config
    .deposit_bridge_fee
    .get_protocol_and_relayer_fee(deposit_fee);
```

These values flow through `verify_deposit_callback` → `internal_mint_promise` → `mint_callback`, which credits `protocol_fee` to `cur_available_protocol_fee`. [1](#0-0) [2](#0-1) 

In contrast, `internal_safe_verify_deposit` passes the **full** `deposit_amount` as `mint_amount` to `verify_safe_deposit_callback` with no fee deduction whatsoever:

```rust
// internal_safe_verify_deposit — no fee calculation, full amount forwarded
promise.then(
    Self::ext(env::current_account_id())
        .with_static_gas(GAS_FOR_VERIFY_DEPOSIT_CALL_BACK)
        .verify_safe_deposit_callback(
            recipient_id,
            deposit_amount.into(),  // ← full amount, no deposit_bridge_fee deducted
            deposit_msg.msg,
            pending_utxo_info,
        ),
)
``` [3](#0-2) 

`safe_mint_callback` then hardcodes `protocol_fee: U128(0)` and `relayer_fee: U128(0)` in the event and never credits any amount to `cur_available_protocol_fee`:

```rust
Event::VerifyDepositDetails {
    recipient_id: &recipient_id,
    mint_amount,
    protocol_fee: U128(0),   // ← hardcoded zero
    relayer_account_id: env::signer_account_id(),
    relayer_fee: U128(0),    // ← hardcoded zero
    success: is_success,
}
``` [4](#0-3) 

The `BridgeFee` struct and its `get_protocol_and_relayer_fee` method are the canonical fee-splitting mechanism used by the standard path but entirely absent from the safe path: [5](#0-4) 

The only gate on `internal_safe_verify_deposit_entry` is a NEAR storage deposit requirement — no role restriction: [6](#0-5) 

### Impact Explanation
The protocol loses the entire `deposit_bridge_fee` (both `protocol_fee` and `relayer_fee`) on every deposit routed through `safe_verify_deposit`. With a `protocol_fee_rate` of 9000 (90%) and a `fee_min` of 10,000 satoshis (as seen in test configuration), the protocol loses 9,000 satoshis of nBTC per deposit. The user receives the full `deposit_amount` as nBTC instead of `deposit_amount − deposit_bridge_fee`. This is a direct bypass of bridge fee policies and causes permanent under-collection of protocol revenue proportional to deposit volume. [7](#0-6) 

### Likelihood Explanation
Any unprivileged user can exploit this from the very first step of the deposit flow. The only additional cost is the NEAR storage deposit (`required_balance_for_safe_deposit()`), which is refunded on failure. A rational user who wants to minimize fees will always prefer `safe_verify_deposit` over `verify_deposit` once this is known. The attack requires no special privileges, no leaked keys, and no coordination.

### Recommendation
Apply the `deposit_bridge_fee` calculation inside `internal_safe_verify_deposit`, mirroring the logic in `internal_verify_deposit`:
1. Compute `deposit_fee = config.deposit_bridge_fee.get_fee(deposit_amount)`.
2. Set `mint_amount = deposit_amount - deposit_fee`.
3. Split into `(protocol_fee, relayer_fee)` via `get_protocol_and_relayer_fee`.
4. Pass `protocol_fee` and `relayer_fee` to `verify_safe_deposit_callback` and credit `protocol_fee` to `cur_available_protocol_fee` in `safe_mint_callback`.

### Proof of Concept
1. User calls `get_user_deposit_address` with `DepositMsg { recipient_id: user, safe_deposit: Some(SafeDepositMsg { msg: "..." }), ... }`.
2. User sends 500,000 satoshis to the returned address.
3. User calls `safe_verify_deposit` with the same `deposit_msg`, attaching only the required NEAR storage deposit.
4. `internal_safe_verify_deposit` is called with `deposit_amount = 500_000`; no fee is deducted.
5. `verify_safe_deposit_callback` calls `safe_mint(recipient_id, 500_000, msg)`.
6. `safe_mint_callback` emits `protocol_fee: U128(0)` and never credits `cur_available_protocol_fee`.
7. User receives **500,000 nBTC** instead of the correct **490,000 nBTC** (with 10,000 satoshi `fee_min` deducted).
8. Protocol loses 9,000 satoshis in protocol fees (90% of 10,000) per deposit — indefinitely, at scale.

    pub fn get_fee(&self, amount: u128) -> u128 {
        std::cmp::max(
            amount * u128::from(self.fee_rate) / u128::from(MAX_RATIO),
            self.fee_min,
        )
    }

    pub fn get_protocol_and_relayer_fee(&self, fee_amount: u128) -> (u128, u128) {
        let protocol_fee = fee_amount * u128::from(self.protocol_fee_rate) / u128::from(MAX_RATIO);
        let relayer_fee = fee_amount - protocol_fee;
        (protocol_fee, relayer_fee)
    }
