### Title
Peras Certificate Validation Unconditionally Accepts All Inbound Certificates — Bypass of Certificate Verification Enables Unauthorized Chain-Weight Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation is a stub that unconditionally returns `Right` for every inbound certificate, performing zero cryptographic or structural checks. Because this is the only instance in the codebase and is wired directly into the production Peras certificate diffusion inbound path, any unprivileged peer can send a crafted `PerasCert` that will be accepted, stored in `PerasCertDB`, and used to boost the weight of an arbitrary block in chain selection — without any signature, committee-membership, or round-validity check ever being performed.

---

### Finding Description

The `BlockSupportsPeras` typeclass declares `validatePerasCert` as the gate that must be passed before a received certificate is stored and acted upon. The sole instance — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` — implements this gate as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params
        }
```

No signature is verified, no committee membership is checked, no round number is validated, and no boosted-block existence is confirmed. The function always succeeds. [1](#0-0) 

This stub is the validator passed directly into the production inbound certificate processing pipeline. `makePerasCertPoolWriterFromChainDB` — the writer used by the live node-to-node diffusion handler — calls `processCerts` with `validatePerasCert mkPerasParams` as its validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          (validatePerasCert mkPerasParams)   -- ← always Right
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` partitions the results of `validateCert` and, when all results are `Right` (which is always), adds every certificate to the database: [3](#0-2) 

This writer is wired into the live node-to-node Peras certificate diffusion client in `NodeToNode.hs`:

```haskell
, hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

Once a fraudulent certificate is stored, `chainSelSync` triggers chain selection for the boosted block, applying the certificate's weight boost (`vpcCertBoost = perasWeight params`) to `WeightedSelectView` comparisons: [5](#0-4) 

The weight boost is then used in `preferCandidate` to decide whether to switch chains: [6](#0-5) 

The analog to the external report is exact: just as `interestData()` returned non-zero fees that were never charged, `validatePerasCert` is supposed to enforce certificate validity but the enforcement is entirely absent — the "validation" function computes a `ValidatedPerasCert` wrapper and returns it unconditionally, never applying any actual checks.

---

### Impact Explanation

An unprivileged peer can send a `PerasCert` naming any block hash and any round number. The certificate will pass "validation," be stored in `PerasCertDB`, and cause `chainSelectionForBlock` to be invoked for the targeted block. If the targeted block is on a fork, the fraudulent weight boost (`perasWeight params`) is added to that fork's `WeightedSelectView`, potentially making it heavier than the honest chain and causing the victim node to switch to a non-canonical chain. This is a chain-selection safety failure triggered by a single unauthenticated network message.

**Impact class:** Critical — bypass of Peras certificate verification enabling unauthorized certificate acceptance and chain-weight manipulation that can cause an honest node to prefer a non-canonical chain.

---

### Likelihood Explanation

The Peras certificate diffusion mini-protocol is active in the production node-to-node handler. Any connected peer can send a `PerasCert` message. No stake, no key material, and no prior knowledge is required. The attack requires only knowledge of a target block hash (observable from the public chain) and the ability to connect to a node. When Peras is enabled (e.g., on a private testnet or future mainnet deployment), this is trivially exploitable by any peer.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real implementation that:
1. Verifies the aggregate BLS/committee signature over `(electionId, candidate)` using the committee's public keys for the relevant round.
2. Confirms the boosted block's slot falls within the valid range for the claimed round number.
3. Confirms the certificate issuer(s) are registered committee members with sufficient stake.
4. Rejects certificates whose round number is in the future or whose boosted block is unknown.

Until a real implementation exists, the inbound diffusion handler should not accept certificates from untrusted peers, or the `processCerts` path should be gated behind a Peras-enabled feature flag that is off by default and not reachable from the network.

---

### Proof of Concept

**Attacker-controlled entry path:**

1. Attacker connects to a victim node via the node-to-node protocol.
2. Attacker sends a `MsgObjects [craftedCert]` on the Peras certificate diffusion channel, where `craftedCert = PerasCert { pcCertRound = r, pcCertBoostedBlock = forkTipPoint }` for any fork tip `forkTipPoint` the attacker wants to boost.
3. `objectDiffusionInbound` → `makePerasCertPoolWriterFromChainDB` → `processCerts` → `validatePerasCert mkPerasParams craftedCert` returns `Right ValidatedPerasCert{vpcCertBoost = perasWeight mkPerasParams}`.
4. `ChainDB.addPerasCertAsync` stores the certificate; `chainSelSync` triggers `chainSelectionForBlock` for `forkTipPoint`.
5. `weightedSelectView` computes the fork's `WeightedSelectView` with the fraudulent boost added; `preferCandidate` returns `ShouldSwitch` if the boosted fork is now heavier than the current chain.
6. The victim node switches to the attacker-chosen fork.

**Root cause line:** `validatePerasCert params cert = Right ValidatedPerasCert{...}` — no checks performed. [7](#0-6)
