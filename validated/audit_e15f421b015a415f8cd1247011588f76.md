### Title
Incomplete Peras Vote and Certificate Validation — Signature Checks Absent When Stake Condition Is Met - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance, which applies to all block types via `instance StandardHash blk => BlockSupportsPeras blk`, implements `validatePerasVote` and `validatePerasCert` with incomplete validation. `validatePerasVote` only checks whether the voter has stake in the distribution but never verifies the vote's cryptographic signature. `validatePerasCert` performs no validation at all and unconditionally returns `Right`. These functions are called on network-received objects via `processCerts`, meaning any unprivileged peer can inject crafted Peras votes and certificates that pass validation without valid cryptographic proofs.

---

### Finding Description

`validatePerasVote` is guarded by a single condition — whether the voter appears in the stake distribution — but the check for signature validity is entirely absent:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
``` [1](#0-0) 

The condition `Just stake <- lookupPerasVoteStake vote stakeDistr` is the only gate. When it is satisfied, the function returns `Right` (valid) without ever verifying the vote's cryptographic signature. When it is not satisfied, the function returns `Left`. The signature check is never performed in either branch — directly mirroring the original report's pattern where a check is only done when a condition holds, leaving the complementary case uncovered.

`validatePerasCert` is even more permissive — it performs no checks at all and always returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
validatePerasCert params cert =
  Right ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight params }
``` [2](#0-1) 

These stubs are the concrete implementations used at runtime because the `instance StandardHash blk => BlockSupportsPeras blk` declaration makes them the default for all block types, including production Cardano blocks. [3](#0-2) 

The attacker-controlled entry path runs through `processCerts`, which is wired into both the `PerasCertDB` writer and the `ChainDB` writer in the object diffusion layer:

```haskell
makePerasCertPoolWriterFromCertDB systemTime perasCertDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (PerasCertDB.getCertIds perasCertDB)
          (validatePerasCert mkPerasParams)   -- stub: always Right
          ...
          certs
    }
``` [4](#0-3) 

`processCerts` filters out certificates whose round number is already in the database, then calls `validateCert` on the remainder. Because `validateCert` is the stub that always returns `Right`, every new-round certificate from any peer passes:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) -> mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _)            -> throw (PerasCertValidationError errs)
``` [5](#0-4) 

The real cryptographic verification that should be performed is demonstrated by the non-stub implementations in `WFALS.hs` and `EveryoneVotes.hs`, which verify aggregate BLS signatures and VRF outputs: [6](#0-5) [7](#0-6) 

None of those checks are invoked through the default `BlockSupportsPeras` instance.

---

### Impact Explanation

Peras certificates carry a chain-selection boost (`vpcCertBoost = perasWeight params`). A node that accepts a forged certificate for a round it has not yet seen will apply that boost to the attacker's chosen block, potentially causing the node to prefer a non-canonical or adversarially-controlled chain over the honest chain. This is a **bypass of Peras certificate/vote signature verification** that enables unauthorized chain selection influence — matching the "Bypass of leader eligibility, VRF/KES/certificate/signature validation, PBFT/Praos/TPraos/Peras voting or certificate checks" impact category.

---

### Likelihood Explanation

The entry path requires only a network peer connection and the ability to craft a Peras certificate or vote with an arbitrary round number not yet present in the target node's database. No keys, stake, or privileged access are required. The object diffusion protocol is designed to accept objects from any connected peer, and the only gate (`certsNotAlreadyInDb`) is trivially satisfied for any fresh round number.

---

### Recommendation

Replace the stub `validatePerasCert` and `validatePerasVote` implementations with real cryptographic verification before the Peras object diffusion protocol is enabled in production. The correct verification logic already exists in `WFALS.implVerifyCert`, `WFALS.implVerifyVote`, and `EveryoneVotes.implVerifyCert`. The default instance should either delegate to those implementations or, if no concrete committee scheme is available for a given block type, return `Left` (reject) rather than `Right` (accept). The incomplete-check pattern in `validatePerasVote` — where the stake condition gates acceptance but the signature condition is absent — should be treated as a two-part guard: both stake presence **and** signature validity must be checked before returning `Right`.

---

### Proof of Concept

1. Connect to a target node running the Peras object diffusion protocol.
2. Craft a `PerasCert blk` with an arbitrary `pcCertRound` not yet in the node's `PerasCertDB` and a `pcCertBoostedBlock` pointing to an attacker-controlled block.
3. Send the certificate batch via the object diffusion miniprotocol.
4. `processCerts` filters out already-known rounds (none match), calls `validatePerasCert mkPerasParams` on the crafted cert, which unconditionally returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }`.
5. The cert is timestamped and added to the database via `addCert`.
6. The Peras chain-selection weight is now applied to the attacker's block, biasing the node's chain selection toward the adversarial chain without any valid cryptographic proof of a quorum. [8](#0-7) [9](#0-8)

```haskell
processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
