### Title
`validatePerasCert` Performs No Cryptographic Verification, Allowing Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The production `BlockSupportsPeras` instance's `validatePerasCert` function unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or structural validation. Any unprivileged peer connected via the node-to-node `PerasCertDiffusion` miniprotocol can inject a crafted `PerasCert` claiming to certify any block, and the receiving node will accept it, store it, and apply its weight boost during chain selection — without ever verifying committee membership, aggregate BLS signatures, or round eligibility.

### Finding Description

**Root cause — `validatePerasCert` is a no-op stub:**

The default `BlockSupportsPeras` instance, which is the only instance in the codebase and therefore the one used for all production block types, implements `validatePerasCert` as:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function ignores every field of the certificate and always returns `Right`. There is no check of:
- The aggregate BLS signature over the election ID and vote candidate
- Committee membership of the claimed voters
- VRF eligibility proofs for non-persistent members
- Whether the round number is valid for the current epoch
- Whether the boosted block actually exists on any known chain

**How the stub is wired into the production inbound path:**

`makePerasCertPoolWriterFromChainDB` — the writer used by the live NTN handler — passes `validatePerasCert mkPerasParams` directly as the validation callback to `processCerts`:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each received certificate; if all pass (which they always do), it calls `addCert` — here `ChainDB.addPerasCertAsync` — for each one:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

**How the writer is connected to the live NTN handler:**

In `mkHandlers` for node-to-node protocols, `hPerasCertDiffusionClient` is wired directly to `makePerasCertPoolWriterFromChainDB`:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      version
      controlMessageSTM
``` [4](#0-3) 

**Chain selection consequence:**

`ChainDB.addPerasCertAsync` enqueues the accepted certificate for chain selection. The certificate's `vpcCertBoost` (set to `perasWeight params` by the stub) is applied as a weight boost to `pcCertBoostedBlock` during chain selection, potentially making a non-canonical fork appear heavier than the honest chain. [5](#0-4) 

**Contrast with vote validation:**

Vote validation (`validatePerasVote`) at least checks that the claimed voter ID exists in the stake distribution, and the production handler deliberately passes an empty distribution (`pure (PerasVoteStakeDistr mempty)`) so all votes are rejected. Certificate validation has no equivalent guard — it accepts everything unconditionally. [6](#0-5) 

### Impact Explanation

**Impact: High** — Chain selection manipulation by an unprivileged peer.

An attacker who can establish a standard NTN connection (no special privileges required) can:

1. Craft a `PerasCert` with `pcCertBoostedBlock` pointing to any block on a minority or adversarial fork.
2. Send it via the `PerasCertDiffusion` miniprotocol.
3. The receiving node stores it and applies the Peras weight boost to that block during chain selection.
4. If the boosted block is on a fork, the node may switch to that fork, diverging from the honest majority chain.

This matches the allowed impact scope: *"High. Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."*

### Likelihood Explanation

**Likelihood: High.** The `PerasCertDiffusion` miniprotocol is open to all NTN peers. No authentication, stake ownership, or key material is required to connect and send a certificate message. The code path from peer connection to `addPerasCertAsync` is fully exercised in production with zero validation gates.

### Recommendation

Replace the stub `validatePerasCert` implementation with a real one that:
1. Verifies the aggregate BLS signature over `(electionId, candidate)` using the combined verification keys of the claimed committee members.
2. Checks that each claimed voter seat index is within bounds and corresponds to a committee member with non-zero stake.
3. For non-persistent members, verifies the VRF eligibility proof.
4. Validates that the round number falls within the current or recent epoch window.

Until the real implementation is ready, the production inbound handler should reject all inbound certificates (analogous to how votes are rejected via the empty stake distribution), rather than accepting them unconditionally.

### Proof of Concept

An attacker node connects to a victim node via the standard NTN handshake and negotiates `PerasCertDiffusion`. It then sends a single `PerasCert` message:

```
PerasCert
  { pcCertRound      = <any round number not yet in victim's DB>
  , pcCertBoostedBlock = <point of a block on an adversarial fork>
  }
```

Execution trace on the victim:
1. `objectDiffusionInbound` receives the cert ID, requests the object, receives the cert body.
2. `opwAddObjects [cert]` → `processCerts` → `validatePerasCert mkPerasParams cert` → `Right (ValidatedPerasCert cert (perasWeight mkPerasParams))`.
3. `ChainDB.addPerasCertAsync (WithArrivalTime now validatedCert)` enqueues the cert.
4. `chainSelSync` applies the Peras weight boost to `pcCertBoostedBlock`.
5. If the boosted fork's cumulative weight now exceeds the current selection, the victim switches to the adversarial fork.

No cryptographic material, stake, or operator access is required by the attacker.

    { opwObjectId = getPerasCertRound

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
