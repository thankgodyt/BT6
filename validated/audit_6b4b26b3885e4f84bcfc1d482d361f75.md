### Title
Unprivileged user can trigger `"only one user output is allowed"` panic in `withdraw_rbf_callback` by submitting empty `output` with an Orchard bundle against a transparent withdrawal — (`contracts/satoshi-bridge/src/zcash_utils/psbt_wrapper.rs`)

### Summary

When a user calls `withdraw_rbf` with `output = []` and a non-`None` `chain_specific_data` (Orchard bundle) against an original transparent withdrawal, `from_original_psbt` silently copies the original transparent vout (including the user's transparent output). The resulting `PsbtWrapper` then carries both the original transparent user output AND the new Orchard bundle. `check_withdraw_psbt` pushes both into `actual_received_amounts`, violating the `len() == 1` invariant and panicking. The callback reverts cleanly; no funds are lost.

### Finding Description

**Step 1 — Public entrypoint.**
`withdraw_rbf` in `contracts/satoshi-bridge/src/api/bridge.rs` is callable by any registered user who owns the original pending withdrawal. The only pre-callback check is a read-only capacity guard. [1](#0-0) 

**Step 2 — Callback construction.**
`withdraw_rbf_chain_specific` (Zcash variant) schedules `withdraw_rbf_callback`, passing `output` and `chain_specific_data` verbatim. [2](#0-1) 

**Step 3 — `from_original_psbt` copies original vout when `output` is empty.**
When `output.is_empty()` is `true`, the function unconditionally clones `original_psbt.vout` — which contains the original transparent user output. The new Orchard bundle is then stored alongside it. [3](#0-2) 

**Step 4 — Output-count guard does not catch the mismatch.**
`check_withdraw_rbf_psbt_valid` checks `original_tx.output().len() == withdraw_rbf_psbt.get_output_num()`. `get_output_num()` returns `self.vout.len()` (transparent outputs only), which equals the original count because the vout was copied verbatim. The Orchard bundle is invisible to this check. [4](#0-3) 

**Step 5 — Double push into `actual_received_amounts`.**
`check_withdraw_psbt` iterates transparent outputs: the user's transparent output matches `target_address_script_pubkey` and is pushed → `len = 1`. Then `add_extra_outputs` is called; because `self.orchard.is_some()`, it pushes the Orchard amount → `len = 2`. [5](#0-4) [6](#0-5) 

**Step 6 — Invariant violation → panic.**
The `require!` on line 220–223 fires with `"only one user output is allowed."` because `actual_received_amounts.len() == 2`. [7](#0-6) 

### Impact Explanation

The panic occurs entirely inside the `#[private]` `withdraw_rbf_callback`. In NEAR, a panicking callback reverts all state changes made within that callback transaction. No state was mutated before the callback was scheduled (the outer `withdraw_rbf` call is read-only). The original `WithdrawOriginal` pending info is untouched; the user's nZEC tokens remain in the bridge; the original withdrawal can still be signed and verified normally. There is no fund loss, no stuck state, and no corruption.

Impact: **Low** — publicly reachable invariant-violation / panic in a production bridge path without direct theft or permanent fund lock.

### Likelihood Explanation

Any user who owns a transparent Zcash withdrawal in `PendingVerify` state can trigger this by calling `withdraw_rbf(id, [], Some(ChainSpecificData { orchard_bundle_bytes: <valid_bundle>, expiry_height: <valid> }))`. No privilege is required beyond owning the original withdrawal. The Orchard bundle must be valid (passes `extract_orchard_bundle`), but that is straightforward to construct.

### Recommendation

In `from_original_psbt`, when `output` is empty but `orchard_bundle_bytes` is `Some`, the function should not silently inherit the original transparent vout. Either:
- Reject the combination: `require!(output.is_empty() == orchard_bundle_bytes.is_none() || !output.is_empty(), "cannot combine empty output with Orchard bundle on a transparent original withdrawal")`, or
- Clear `vout` to empty when an Orchard bundle is provided and `output` is empty, so the resulting PSBT is shielded-only.

Additionally, `check_withdraw_rbf_psbt_valid` should verify that the new PSBT's Orchard-bundle presence is consistent with the original PSBT's payment type (transparent vs. shielded).

### Proof of Concept

```

Attack:
  alice.withdraw_rbf(
      original_btc_pending_verify_id = "TX_ID",
      output = [],                          // empty → triggers vout copy
      chain_specific_data = Some({
          orchard_bundle_bytes: <valid 1-action Orchard bundle>,
          expiry_height: <current_height + gap>
      })
  )

Execution trace:
  withdraw_rbf_callback:

      → vout = original_psbt.vout.clone()   // [user_output, change_output]

      original_tx.output().len() == 2
      withdraw_rbf_psbt.get_output_num() == 2  // passes!
    check_withdraw_psbt:
      transparent loop: actual_received_amounts = [X]   // user_output matched
      add_extra_outputs:  actual_received_amounts = [X, orchard_amount]  // len=2
```

```rust
macro_rules! define_rbf_callback {
    ($method:ident, $callback_name:ident, $internal_fn:ident) => {
```
