Audit Report

## Title
`init_transfer` Accepts Sub-Divisor Amounts That Permanently Freeze Funds via Zero Normalization — (`near/omni-bridge/src/lib.rs`)

## Summary

`init_transfer` validates only that `fee < amount`, without checking whether the amount survives decimal normalization. When a token has more decimals on NEAR than on the destination chain, any `amount_without_fee` below the normalization divisor passes `init_transfer`, locks or burns the user's tokens, and stores the `TransferMessage` — but `sign_transfer` will always panic on the stored transfer because `normalize_amount` floors the amount to zero. No cancel or refund path exists for the stuck transfer, permanently freezing the user's funds.

## Finding Description

**Root cause — missing pre-normalization guard in `init_transfer`:**

`init_transfer` constructs a `TransferMessage` and enforces only:

```rust
require!(
    transfer_message.fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
``` [1](#0-0) 

No check is made on whether the normalized destination-chain amount is non-zero. The function then proceeds to lock or burn the user's tokens and persist the `TransferMessage`.

**`normalize_amount` uses floor division:**

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
``` [2](#0-1) 

When `origin_decimals > decimals`, the divisor is `10^(origin_decimals − decimals)`. Any `amount_without_fee` strictly less than this divisor produces zero.

**`sign_transfer` enforces non-zero and always panics for such transfers:**

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
``` [3](#0-2) 

Because the `TransferMessage` is stored with the original (un-normalized) amount, every future call to `sign_transfer` for this transfer ID will re-compute the same zero and panic. The transfer can never be completed.

**No cancel or refund path exists:** A search across `lib.rs` for `cancel`, `revert_transfer`, `unlock_transfer`, and `recover` returns no matches. The only `refund` helper (line 2770) handles NEAR-token storage refunds, not token-transfer reversals. The code comment on `normalize_amount` acknowledges that "dust stays locked/burned" when `fee = 0`, but this is documented as an accepted dust-rounding behavior — not as a mechanism for recovering a transfer whose entire amount normalizes to zero. [4](#0-3) 

## Impact Explanation

This is a **permanent freezing of bridged funds**, matching the Critical allowed impact: *"permanent freezing of bridged funds across NEAR … flows."* For any token registered with `origin_decimals > decimals` (e.g., 24 NEAR decimals → 18 destination decimals, divisor = 10^6), any transfer with `amount_without_fee < 1,000,000` will have its tokens locked or burned on NEAR with no recovery path. The funds are irrecoverably lost.

## Likelihood Explanation

The exploit path is fully unprivileged: `ft_transfer_call` → `ft_on_transfer` → `init_transfer`. Any token holder can trigger this on themselves (accidentally, by choosing a small amount) or an attacker can grief another user by front-running or social engineering a small transfer. No special role, key, or privileged access is required. Any token pair where `origin_decimals > decimals` is affected, which is a common real-world configuration (e.g., NEAR-native tokens bridging to EVM chains).

## Recommendation

Add a normalization guard inside `init_transfer` (or `init_transfer_internal`) immediately after the fee check, before tokens are locked or burned:

```rust
let decimals = self
    .token_decimals
    .get(&token_address_for_destination)
    .near_expect(BridgeError::TokenDecimalsNotFound);
require!(
    Self::normalize_amount(
        transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
        decimals,
    ) > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

This mirrors the guard already present in `sign_transfer` and prevents the transfer from being accepted in the first place, returning the tokens to the caller via the `ft_on_transfer` return value before any state mutation occurs.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `decimals = 18` (divisor = 10^6).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`.
3. `init_transfer` passes the `fee < amount` check (0 < 500,000), locks 500,000 tokens, stores the `TransferMessage` with `amount = 500_000`.
4. Relayer calls `sign_transfer` for the stored transfer ID.
5. `normalize_amount(500_000, decimals) = 500_000 / 1_000_000 = 0` (floor division).
6. `require!(amount_to_transfer > 0, ...)` panics — every subsequent call to `sign_transfer` for this transfer also panics identically.
7. The 500,000 tokens are permanently locked on NEAR with no cancel, revert, or refund mechanism available.
