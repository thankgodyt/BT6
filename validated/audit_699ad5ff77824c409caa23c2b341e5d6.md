### Title
Unvalidated Caller-Supplied `key_version` in `sign_btc_transaction` Enables Attacker-Triggered Permanent Locking of Withdrawal Funds - (File: `contracts/satoshi-bridge/src/api/chain_signatures.rs`)

---

### Summary

The public `sign_btc_transaction` function accepts a caller-controlled `key_version: u32` parameter that is forwarded directly to the NEAR Chain Signatures (MPC) service without any validation. Any unprivileged NEAR account can invoke this function with an arbitrary `key_version`, causing the MPC to sign the withdrawal PSBT with a key version that does not correspond to the public key embedded in the UTXO's locking script. The resulting Bitcoin transaction carries an invalid witness and will be permanently rejected by the Bitcoin network, locking the user's escrowed nBTC in the bridge. The attacker can repeat this on every RBF replacement, making the lock indefinite.

---

### Finding Description

`sign_btc_transaction` is a public, unprivileged entry point — its only gate is `#[pause]`, which does not restrict callers by role:

```rust
// contracts/satoshi-bridge/src/api/chain_signatures.rs
#[payable]
#[pause(except(roles(Role::DAO)))]
pub fn sign_btc_transaction(
    &mut self,
    btc_pending_sign_id: String,
    sign_index: usize,
    key_version: u32,          // ← fully attacker-controlled, no validation
) -> PromiseOrValue<bool> {
    ...
    self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
        .into()
}
``` [1](#0-0) 

The value is forwarded verbatim into the MPC `SignRequest`:

```rust
// contracts/satoshi-bridge/src/chain_signature.rs
self.sign_promise(SignRequest {
    payload,
    path,
    key_version,   // ← attacker value reaches MPC
})
``` [2](#0-1) 

In the callback, the contract derives the expected public key using the **current root key** (implicitly `key_version=0`) and saves the MPC-returned signature alongside it:

```rust
let public_key = self.generate_btc_public_key(&path).inner;
psbt.save_signature(sign_index, signature, public_key);
``` [3](#0-2) 

`generate_btc_public_key` always derives from the stored `chain_signatures_root_public_key` (key version 0):

```rust
pub fn generate_public_key(&self, path: &str) -> Vec<u8> {
    let mpc_pk = crypto_shared::near_public_key_to_affine_point(
        self.internal_config()
            .chain_signatures_root_public_key
            .clone()
            .expect("Missing chain_signatures_root_public_key"),
    );
    ...
}
``` [4](#0-3) 

The UTXO's P2WPKH locking script was created from the key-version-0 public key. When the MPC signs with a different `key_version`, the resulting ECDSA signature is valid for a **different** key, not the one committed in the on-chain UTXO. The assembled Bitcoin transaction therefore carries an invalid witness and is permanently unspendable.

---

### Impact Explanation

Once `sign_btc_transaction_callback` runs, the PSBT is marked fully signed and the pending info transitions to `pending_verify` state:

```rust
btc_pending_info.tx_bytes_with_sign = Some(tx_bytes_with_sign);
btc_pending_info.to_pending_verify_stage();
``` [5](#0-4) 

The user's escrowed nBTC remains locked in the bridge. The invalid transaction can never be confirmed on Bitcoin, so `verify_withdraw` can never succeed. The attacker can repeat the same call on every RBF replacement transaction (`withdraw_rbf`, `cancel_withdraw`, `active_utxo_management_rbf`), each time supplying a wrong `key_version`, making the lock indefinite and requiring operator intervention to recover funds.

**Impact**: Medium — attacker-triggered permanent locking of bridged withdrawal funds requiring operator intervention.

---

### Likelihood Explanation

- `sign_btc_transaction` is callable by **any** NEAR account with no role restriction.
- The `key_version` parameter is documented in the function signature and visible on-chain; an attacker simply passes any non-zero value (e.g., `key_version=1`).
- No special knowledge, privileged access, or off-chain capability is required.
- The attack is repeatable on every RBF attempt.

**Likelihood**: Medium — straightforward to execute by any NEAR account holder once a withdrawal is in `pending_sign` state.

---

### Recommendation

Validate `key_version` against a protocol-configured constant (e.g., `0`) before forwarding to the MPC. Reject any call that supplies a value other than the expected version:

```rust
require!(key_version == EXPECTED_KEY_VERSION, "Invalid key_version");
```

Alternatively, remove `key_version` from the public API entirely and hardcode the expected value inside `internal_sign_btc_transaction`.

---

### Proof of Concept

1. Alice initiates a withdrawal; the bridge creates a `BTCPendingInfo` in `pending_sign` state with `btc_pending_sign_id = X`.
2. Attacker (any NEAR account) calls:
   ```
   sign_btc_transaction(btc_pending_sign_id: "X", sign_index: 0, key_version: 999)
   ```
3. The MPC signs the PSBT payload with key version 999 — a key that does not correspond to the P2WPKH address locking Alice's deposited UTXO.
4. `sign_btc_transaction_callback` stores the mismatched signature, assembles the transaction, and transitions state to `pending_verify`.
5. The signed transaction is broadcast; Bitcoin nodes reject it because the witness signature does not satisfy the P2WPKH script.
6. `verify_withdraw` can never succeed; Alice's nBTC remains permanently escrowed in the bridge.
7. If an operator issues `cancel_withdraw` to create an RBF, the attacker repeats step 2 on the new pending sign ID, re-locking the replacement transaction.
