### Title
Refund Address Frontrunning in `request_refund_callback` Allows Theft of Refunded BTC — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

When a user submits a refund request for a deposit whose `deposit_msg.refund_address` is `None`, the BTC refund destination is entirely caller-supplied at call time and is not bound to any on-chain identity. Because NEAR transactions are observable via RPC before finalization, an attacker can copy all parameters from a pending `request_refund` call, substitute their own BTC address as `refund_address`, and race to have their callback land first. The first callback to succeed claims the refund slot, redirecting the victim's BTC to the attacker.

---

### Finding Description

**Root cause — caller-supplied `refund_address` with no identity binding when `deposit_msg.refund_address` is `None`:**

In `internal_request_refund`, the only guard on `refund_address` is:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [1](#0-0) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a BTC return address in the on-chain deposit message), the `refund_address` argument passes through unchecked. There is no verification that the caller is the `recipient_id` named in `deposit_msg`, nor any binding between the NEAR caller identity and the BTC address supplied.

**Race-condition entry point — first callback wins:**

`internal_request_refund` fires a cross-contract call to the light client and chains `request_refund_callback`. Inside the callback, the only protection against a competing submission is:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [2](#0-1) 

Whichever callback resolves first wins the slot. The `RefundRequest` is then persisted with the winning caller's `refund_address`:

```rust
let refund_request = RefundRequest {
    ...
    refund_address,
    ...
};
self.data_mut()
    .refund_requests
    .insert(utxo_storage_key, refund_request.into());
``` [3](#0-2) 

**Exploit path:**

1. Victim sends BTC to a deposit address derived from a `deposit_msg` with `refund_address: None`.
2. The deposit cannot be finalized (e.g., wrong amount, expired, or the victim simply wants a refund).
3. Victim submits `request_refund(deposit_msg, victim_btc_addr, tx_bytes, vout, proof)`. All parameters are visible on the NEAR RPC before the transaction is included in a block.
4. Attacker observes the pending call, extracts all parameters, and immediately submits `request_refund(deposit_msg, attacker_btc_addr, tx_bytes, vout, proof)` with their own BTC address.
5. Both calls trigger independent light-client verification cross-contract calls. The one whose callback resolves first inserts the `RefundRequest`.
6. The second callback fails with "Refund request already exists for this UTXO".
7. When `execute_refund` is later called, the BTC is sent to whichever address won the race.

The `deposit_msg` is fully public (it is the hash path used to derive the deposit address on-chain via `get_deposit_path`), and `tx_bytes`/`proof` are submitted by a relayer and are observable. No secret knowledge is required. [4](#0-3) 

---

### Impact Explanation

If the attacker wins the race, the `RefundRequest` is stored with the attacker's BTC address. When `execute_refund` is subsequently called, the bridge constructs and signs a Bitcoin transaction paying `refund_amount` to the attacker's address. The victim's deposited BTC is permanently transferred to the attacker. This is a direct, complete theft of user funds with no recovery path once the refund Bitcoin transaction is broadcast and confirmed.

**Impact category:** Critical — significant loss of user funds.

---

### Likelihood Explanation

- NEAR transactions are visible via public RPC nodes before block inclusion (~1-second block time). An attacker running a monitoring bot can react within milliseconds.
- All parameters needed to construct the competing call (`deposit_msg`, `tx_bytes`, `vout`, `proof`) are present in the pending transaction's arguments — no privileged access or secret is required.
- The attacker only needs to attach the small NEAR storage deposit (`required_balance_for_request_refund`) to participate.
- The race is between two independent async cross-contract call chains to the same light client. Ordering is non-deterministic and an attacker submitting immediately after observing the victim's transaction has a realistic chance of winning.
- The attack is most reliable when the victim's transaction is observed early (e.g., submitted to a validator the attacker also monitors), but even a best-effort submission has meaningful probability of success.

**Likelihood:** Medium-High for any deposit whose `deposit_msg` omits `refund_address`.

---

### Recommendation

1. **Bind `refund_address` to the `deposit_msg.recipient_id`:** In `request_refund_callback`, when `deposit_msg.refund_address` is `None`, require that `env::predecessor_account_id()` matches `deposit_msg.recipient_id`. Only the intended NEAR recipient should be allowed to supply a BTC refund address at call time.

2. **Alternatively, require pre-commitment:** Enforce that `deposit_msg.refund_address` is always `Some` (i.e., the BTC refund address must be committed inside the deposit message before the BTC transaction is sent). This eliminates the caller-supplied path entirely.

3. **Minimum:** If the open-caller design is intentional, document that any deposit with `refund_address: None` is vulnerable to refund-destination theft and strongly advise users to always pre-commit a `refund_address` in their `deposit_msg`.

---

### Proof of Concept

**Setup:**
- Victim NEAR account: `alice.near`
- Victim's `deposit_msg`: `{ "recipient_id": "alice.near", "refund_address": null }`
- Victim sends BTC to the deposit address derived from this `deposit_msg`.
- Victim's BTC address for refund: `bc1qalice...`
- Attacker's BTC address: `bc1qattacker...`

**Steps:**

1. Victim submits:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: null },
     refund_address = "bc1qalice...",
     tx_bytes = <victim's deposit tx>,
     vout = 0,
     proof = <merkle proof>
   )
   ```

2. Attacker's bot detects this pending NEAR transaction via RPC and immediately submits:
   ```
   request_refund(
     deposit_msg = { recipient_id: "alice.near", refund_address: null },
     refund_address = "bc1qattacker...",
     tx_bytes = <same tx_bytes>,
     vout = 0,
     proof = <same proof>
   )
   ```

3. Both calls trigger `verify_transaction_inclusion` on the light client. The light client returns `true` for both (same valid proof).

4. Attacker's `request_refund_callback` resolves first. The check at line 544 passes (no existing request). `RefundRequest { refund_address: "bc1qattacker..." }` is stored.

5. Victim's `request_refund_callback` resolves second. The check at line 544 fails: "Refund request already exists for this UTXO". Victim's call reverts; their attached NEAR deposit is returned but the refund slot is taken.

6. `execute_refund` is called (by anyone after the timelock). The bridge builds a Bitcoin transaction paying `bc1qattacker...` and requests an MPC signature. The BTC is sent to the attacker.

**Expected outcome:** Alice's deposited BTC is refunded to the attacker's address. Alice loses her funds with no recourse. [5](#0-4) [6](#0-5)

            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"

            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");

        let config = self.internal_config();

    #[private]
    pub fn request_refund_callback(
        &mut self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        gas_fee: Option<u128>,
    ) -> bool {
        let result_bytes = env::promise_result_checked(0, MAX_BOOL_RESULT)
            .expect("Call verify_transaction_inclusion failed");
        let is_valid = serde_json::from_slice::<bool>(&result_bytes)
            .expect("verify_transaction_inclusion return not bool");
        require!(is_valid, "verify_transaction_inclusion return false");

        let config = self.internal_config();
        let transaction = crate::WrappedTransaction::decode(&tx_bytes.0, &config.chain)
            .expect("Deserialization tx_bytes failed");
        let output = &transaction.output()[vout];

        // Verify that the output script matches the deposit address derived from deposit_msg
        let path = get_deposit_path(&deposit_msg);
        let deposit_address = self.generate_utxo_chain_address(&path);
        let deposit_script_pubkey = deposit_address
            .script_pubkey()
            .expect("Invalid deposit address");
        require!(
            deposit_script_pubkey == output.script_pubkey,
            "Output script_pubkey does not match deposit address"
        );

        let amount = u128::from(output.value.to_sat());
        let tx_id = transaction.compute_txid().to_string();
        let utxo_storage_key = generate_utxo_storage_key(
            tx_id,
            u32::try_from(vout).unwrap_or_else(|_| env::panic_str("vout overflow")),
        );

        // Double-check not finalized (could have been verified between request and callback)
        require!(
            !self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key),
            "UTXO already verified via deposit"
        );

        // Double-check no duplicate (another request_refund could have landed between our check and callback)
        require!(
            !self.data().refund_requests.contains_key(&utxo_storage_key),
            "Refund request already exists for this UTXO"
        );

        let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
        require!(
            resolved_gas_fee < amount,
            "Gas fee must be less than deposit amount"
        );

        Event::RefundRequested {
            deposit_msg: deposit_msg.clone(),
            utxo_storage_key: utxo_storage_key.clone(),
            amount: amount.into(),
            refund_address: refund_address.clone(),
            gas_fee: resolved_gas_fee.into(),
        }
        .emit();

        let refund_request = RefundRequest {
            deposit_msg_json: serde_json::to_string(&deposit_msg).unwrap(),
            utxo_storage_key: utxo_storage_key.clone(),
            tx_bytes,
            vout,
            amount,
            refund_address,
            gas_fee: resolved_gas_fee,
            created_at_sec: nano_to_sec(env::block_timestamp()),
            executed: false,
        };

        self.data_mut()
            .refund_requests
            .insert(utxo_storage_key, refund_request.into());

        true
    }
