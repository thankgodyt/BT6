### Title
Silent Discard of Peras Certificates Embedded in Blocks via Stub `getPerasCertInBlock` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The global `BlockSupportsPeras` instance unconditionally returns `Nothing` from `getPerasCertInBlock`, silently discarding every Peras certificate embedded in any block when the ledger applies it. This is structurally identical to the reported DeFi bug: a specific item type (RDNT token / Peras certificate) is present in a list that is iterated, but is silently skipped because the handling code is a stub. When Peras is activated and blocks begin carrying certificates, the `shelleyLedgerLatestPerasCertRound` ledger-state field will never be updated from on-chain data, permanently breaking the ledger invariant that tracks the latest Peras certificate round on the preferred chain.

---

### Finding Description

`BlockSupportsPeras` declares `getPerasCertInBlock :: blk -> Maybe (PerasCert blk)` to extract a Peras certificate from a block. The global catch-all instance at line 389 of `SupportsPeras.hs` implements this as:

```haskell
-- TODO: extract actual Peras certificates from blocks when the HFC plumbing
-- is in place.
getPerasCertInBlock _ = Nothing
``` [1](#0-0) 

This is the **only** instance of `getPerasCertInBlock` in the production codebase (confirmed by grep: the function appears only in `SupportsPeras.hs`, `TestBlock.hs`, and `Ledger.hs`). No era-specific override exists for `ShelleyBlock` or `CardanoBlock`.

This function is called during block application in `Shelley/Ledger/Ledger.hs` via `getPerasCertRoundInBlock`:

```haskell
getPerasCertRoundInBlock :: ShelleyBlock proto era -> StrictMaybe PerasRoundNo
getPerasCertRoundInBlock =
  fmap getPerasCertRound . maybeToStrictMaybe . getPerasCertInBlock
``` [2](#0-1) 

The result feeds directly into the update of `shelleyLedgerLatestPerasCertRound'` during `applyBlockLedgerResultWithValidation`:

```haskell
shelleyLedgerLatestPerasCertRound' =
  case getPerasCertRoundInBlock blk of
    SNothing ->
      tickedShelleyLedgerLatestPerasCertRound stBefore
    SJust certRoundInBlock -> ...
``` [3](#0-2) 

Because `getPerasCertInBlock` always returns `Nothing`, the `SJust` branch is **never reached**. The ledger state field `shelleyLedgerLatestPerasCertRound` is permanently frozen at `SNothing` regardless of what certificates blocks carry.

The test infrastructure explicitly acknowledges and works around this stub:

```haskell
-- NOTE: this bypasses the degenerate global implementation of
-- 'BlockSupportsPeras.getPerasCertInBlock' for 'TestBlock',
-- which currently always returns 'Nothing'.
--
-- TODO: refactor this to use 'getPerasCertInBlock' after the
-- HFC plumbing for 'BlockSupportsPeras' is in place.
``` [4](#0-3) 

This confirms the production path is broken: the test code bypasses the stub precisely because the production path silently drops the certificate.

The `shelleyLedgerLatestPerasCertRound` field is surfaced through `getLatestPerasCertOnChainRound` in the `ChainDB` API:

```haskell
, getLatestPerasCertOnChainRound :: STM m (Maybe PerasRoundNo)
-- ^ Get the round number of the latest Peras certificate on the currently
-- preferred chain.
``` [5](#0-4) 

This will always return `Nothing`, even when the chain contains Peras certificates.

---

### Impact Explanation

When Peras is activated and blocks begin carrying certificates, every honest node running this code will silently discard all on-chain Peras certificates during ledger application. The consequences are:

1. **Ledger invariant broken**: `shelleyLedgerLatestPerasCertRound` will always be `SNothing`, diverging from the true on-chain Peras state. This is a durable ledger-state corruption triggered by any peer sending a valid block with a certificate.

2. **Chain selection divergence**: `getLatestPerasCertOnChainRound` always returns `Nothing`. Any chain-selection or voting logic that consults the on-chain certificate round will operate on a permanently stale value, potentially causing nodes to disagree on the canonical chain.

3. **Voting eligibility broken**: The `PerasCertDB` comment states that "having seen a certificate is a precondition for voting in any round except for the very first one." If the on-chain certificate round is never updated, nodes may fail to satisfy this precondition even when the chain clearly contains the required certificate.

This maps to: **High — Hard-fork/era transition/ledger-view mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes.**

---

### Likelihood Explanation

The broken code path is already wired into the production ledger application logic. The moment Peras is activated and any block carries a certificate, every node running this code will silently ignore it. There is no conditional guard, no feature flag, and no fallback. The likelihood is **certain** upon Peras activation, and the entry path requires only a valid block from any peer — no privileged access needed.

---

### Recommendation

Implement `getPerasCertInBlock` for each concrete era block type (e.g., `ShelleyBlock`, `CardanoBlock`) to properly extract Peras certificates. Until the HFC plumbing is complete, add a runtime assertion or compile-time guard ensuring that no era claiming Peras support can silently return `Nothing` from `getPerasCertInBlock`. This mirrors the fix described in the external report: either handle the item type properly, or add a safety check preventing unhandled types from reaching the processing loop.

### Proof of Concept

1. A peer sends a valid block `blk` containing a Peras certificate for round `R`.
2. The node calls `applyBlockLedgerResultWithValidation` on `blk`.
3. Inside, `getPerasCertRoundInBlock blk` calls `getPerasCertInBlock blk`.
4. The global instance returns `Nothing` unconditionally.
5. `shelleyLedgerLatestPerasCertRound'` is set to the unchanged previous value (`SNothing`).
6. The certificate is silently discarded from the ledger state.
7. `getLatestPerasCertOnChainRound` returns `Nothing` despite the chain containing round `R`.
8. Any downstream logic (voting eligibility, chain comparison) operates on a permanently incorrect ledger view. [6](#0-5) [7](#0-6)

  -- Update the latest Peras certificate round if the new block contains a

  shelleyLedgerLatestPerasCertRound' :: StrictMaybe PerasRoundNo
  shelleyLedgerLatestPerasCertRound' =
    case getPerasCertRoundInBlock blk of
      SNothing ->
        tickedShelleyLedgerLatestPerasCertRound stBefore
      SJust certRoundInBlock ->
        case tickedShelleyLedgerLatestPerasCertRound stBefore of
          SNothing ->
            SJust certRoundInBlock
          SJust latestCertRoundInLedgerState ->
            SJust (certRoundInBlock `max` latestCertRoundInLedgerState)
