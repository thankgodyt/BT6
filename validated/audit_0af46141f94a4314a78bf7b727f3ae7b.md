### Title
Unconditional Peras Certificate Acceptance Enables Arbitrary Chain-Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` catch-all instance implements `validatePerasCert` as a stub that unconditionally accepts every inbound certificate without any cryptographic or semantic check. An unprivileged peer can inject a crafted `PerasCert` that boosts any block's weight, causing an honest node to prefer a non-canonical chain. This is the direct analog of the external report's "missed validation of a potentially corrupted oracle": individual data passes the acceptance gate, but the aggregate chain-selection state is corrupted because the gate performs no real cross-validation.

---

### Finding Description

The file `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs` contains the only `BlockSupportsPeras` instance in the codebase — a catch-all `instance StandardHash blk => BlockSupportsPeras blk` that applies to every block type. [1](#0-0) 

Its `validatePerasCert` implementation unconditionally returns `Right` for every input: [2](#0-1) 

No check is performed on:
- the aggregate BLS signature over the constituent votes,
- VRF eligibility proofs for the claimed voters,
- the certificate's round number vs. the current epoch,
- whether the boosted block exists on any known chain, or
- whether the quorum threshold was actually reached.

The `validatePerasVote` stub in the same instance at least looks up the voter in the stake distribution before accepting a vote: [3](#0-2) 

`validatePerasCert` does not even perform that minimal check — it accepts any certificate unconditionally.

The inbound path for certificates mirrors the vote path. `PerasCert.hs` calls `validatePerasCert` for each certificate received from a peer (confirmed by grep: the only call sites are `SupportsPeras.hs` and `PerasCert.hs`). A `ValidatedPerasCert` produced by this stub is then enqueued via `addPerasCertAsync`: [4](#0-3) 

`chainSelSync` processes the certificate, adds it to the `PerasCertDB`, and triggers chain selection for the boosted block: [5](#0-4) 

Chain selection then uses `wsvTotalWeight = BlockNo + WeightBoost` to prefer chains: [6](#0-5) 

The weight boost is accumulated in a `PerasWeightSnapshot` keyed by block point: [7](#0-6) 

A secondary, related weakness exists in `stakeAboveThreshold`, which carries an explicit TODO acknowledging that it assumes `PerasVoteStake` and the quorum threshold are expressed in the same units (both relative/normalized), but performs no enforcement of this invariant: [8](#0-7) 

If the stake distribution supplies absolute lovelace values while the threshold is a relative fraction (e.g., `0.75`), then `totalVoteStake >= quorumThreshold` would be trivially true for any single vote, allowing one voter to forge a certificate unilaterally. This is the closest structural analog to the external report's division-truncation-to-zero issue: the per-vote sanity check (voter in distribution) passes, but the aggregate quorum comparison is meaningless due to the unit mismatch.

---

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

When Peras is enabled, an attacker can inject a crafted `PerasCert` whose `pcCertBoostedBlock` points to any block — including one on a minority fork. Because `validatePerasCert` accepts it unconditionally, the node adds the certificate to its `PerasCertDB`, boosts the targeted block's weight, and may switch its selection to the attacker's preferred chain. The `PerasWeight` boost is additive with `BlockNo`, so a single certificate with a large configured `perasWeight` can outweigh many honest blocks.

---

### Likelihood Explanation

**High when Peras is enabled.** The attack requires only that the attacker be a connected peer and that Peras be active. No key material, stake, or privileged access is needed. The crafted certificate requires only a valid `PerasRoundNo` and a `Point blk` — both are public information. The CHANGELOG confirms Peras is disabled by default, but the code is present and the vulnerability is fully exploitable the moment Peras is switched on.

---

### Recommendation

1. Implement real validation in `validatePerasCert`: verify the aggregate BLS signature, VRF eligibility proofs, round number bounds, and that the boosted block is known and on a valid chain.
2. Enforce the unit invariant in `stakeAboveThreshold`: either normalize `PerasVoteStake` to a relative value before the comparison, or pass the total stake distribution into the function and perform normalization internally, as the TODO suggests.
3. Remove the degenerate catch-all `BlockSupportsPeras` instance and replace it with a type-class constraint that forces concrete block types to supply real implementations before Peras can be enabled.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Observe the honest chain tip at block `B_honest` (block number `N`).
2. Obtain the hash of any block `B_fork` on a minority fork with block number `N - k + 1` (just within the rollback window).
3. Construct `PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = BlockPoint <slot> <hash of B_fork> }`.
4. Send this certificate to the target node via the Peras certificate diffusion mini-protocol.
5. `validatePerasCert` returns `Right ValidatedPerasCert { vpcCertBoost = perasWeight params }` unconditionally.
6. `chainSelSync` adds the certificate to `PerasCertDB` and calls `chainSelectionForBlock` for `B_fork`.
7. The node's `WeightedSelectView` for the fork chain now has `wsvTotalWeight = (N - k + 1) + perasWeight`, which exceeds the honest chain's `wsvTotalWeight = N + 0` when `perasWeight > k - 1`.
8. The node switches its selection to the minority fork — a chain-selection safety failure triggered by a single unauthenticated network message. [2](#0-1) [9](#0-8) [10](#0-9)

```haskell
chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
```
