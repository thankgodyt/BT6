### Title
Caller-Supplied `gas_fee` in `request_refund` Is Unbounded, Enabling Any Caller to Drain a Victim's Refund Amount to Miners - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
`request_refund_callback` accepts a caller-supplied `gas_fee` parameter with no upper-bound validation against `max_btc_gas_fee`. Any unprivileged NEAR account can submit a refund request for any deposit UTXO and set `gas_fee` to `amount - 1`, causing the resulting refund Bitcoin transaction to pay nearly the entire deposit as a miner fee, leaving the victim with 1 satoshi.

### Finding Description
In `request_refund_callback` (the callback that stores a `RefundRequest` after light-client verification), the `gas_fee` supplied by the caller is resolved and stored with only one guard:

```rust
// contracts/satoshi-bridge/src/refund.rs, lines 549-553
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
``` [1](#0-0) 

The only constraint is `resolved_gas_fee < amount`. The config field `max_btc_gas_fee` exists and is validated on config updates, but it is **never applied** in the refund request path. The stored `gas_fee` is later consumed verbatim in `refund_execution_inputs`:

```rust
// contracts/satoshi-bridge/src/refund.rs, lines 280-284
let refund_amount = refund_request
    .amount
    .checked_sub(refund_request.gas_fee)
    .expect("Deposit amount too small to cover gas fee");
require!(refund_amount > 0, "Refund amount is zero after gas fee");
``` [2](#0-1) 

There is no access control on who may call `request_refund` — the function does not verify that `env::predecessor_account_id()` is the original depositor. Any caller who possesses the deposit transaction bytes and a valid Merkle proof can submit a refund request for any UTXO: [3](#0-2) 

When `deposit_msg.refund_address` is pre-set (the common safe-deposit pattern), the `refund_address` parameter must match it, so the attacker cannot redirect funds to themselves — but they can still set `gas_fee = amount - 1`, leaving the victim with 1 satoshi and sending the rest to Bitcoin miners. [4](#0-3) 

The `max_btc_gas_fee` config field is defined and validated: [5](#0-4) 

But it is never referenced in the refund request or execution path.

### Impact Explanation
An attacker can cause a victim's entire BTC deposit (minus 1 satoshi) to be paid as a Bitcoin miner fee during refund execution. The victim receives 1 satoshi instead of their full deposit. This constitutes **significant destruction of user funds** — matching the allowed critical impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation
- `request_refund` is a fully public, permissionless entry point.
- All deposit transaction data is publicly visible on the Bitcoin chain, so the attacker has everything needed to construct the call.
- For deposits with a pre-authorized `refund_address`, the applicable timelock is only `refund_timelock_sec` (default 2 days), giving the DAO a narrow window to detect and reject the malicious request.
- The DAO rejection mechanism is reactive and not guaranteed to catch every request, especially under high volume or targeted timing.

### Recommendation
Cap the caller-supplied `gas_fee` against `max_btc_gas_fee` in `request_refund_callback`:

```rust
let resolved_gas_fee = gas_fee.unwrap_or_else(|| self.get_refund_gas_fee());
require!(
    resolved_gas_fee <= config.max_btc_gas_fee,
    "Gas fee exceeds max_btc_gas_fee"
);
require!(
    resolved_gas_fee < amount,
    "Gas fee must be less than deposit amount"
);
```

This mirrors the analog fix recommended in the external report: do not let one party unilaterally commit a fee that is immediately applied to another party's payout without a mutual agreement or a protocol-enforced cap.

### Proof of Concept
1. Victim deposits 100,000 satoshi to the bridge with `deposit_msg.refund_address = "victim_btc_addr"`. The deposit fails the minimum amount check and is eligible for refund.
2. Attacker observes the deposit transaction on the Bitcoin chain and obtains `tx_bytes`, `vout`, `deposit_msg`, and constructs a valid `TxInclusionProof`.
3. Attacker calls `request_refund(deposit_msg, "victim_btc_addr", tx_bytes, vout, proof, gas_fee=99999)` (i.e., `amount - 1`).
4. `request_refund_callback` stores `RefundRequest { amount: 100000, gas_fee: 99999, refund_address: "victim_btc_addr", ... }`. The only check (`99999 < 100000`) passes.
5. After `refund_timelock_sec` (2 days), anyone calls `execute_refund`. `refund_execution_inputs` computes `refund_amount = 100000 - 99999 = 1`.
6. The refund Bitcoin transaction is built with a 1-satoshi output to `victim_btc_addr` and a 99,999-satoshi implicit miner fee.
7. The victim receives 1 satoshi; 99,999 satoshi are permanently destroyed as miner fees. [6](#0-5)

    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }

    /// Parse the original deposit transaction and compute the refund economics.
    pub(crate) fn refund_execution_inputs(
        &self,
        refund_request: &RefundRequest,
    ) -> RefundExecutionInputs {
        let config = self.internal_config();
        let transaction =
            crate::WrappedTransaction::decode(&refund_request.tx_bytes.0, &config.chain)
                .expect("Deserialization tx_bytes failed");
        let txid = transaction.compute_txid();
        let outpoint = OutPoint {
            txid,
            vout: u32::try_from(refund_request.vout)
                .unwrap_or_else(|_| env::panic_str("vout overflow")),
        };
        let deposit_output = transaction.output()[refund_request.vout].clone();

        let refund_amount = refund_request
            .amount
            .checked_sub(refund_request.gas_fee)
            .expect("Deposit amount too small to cover gas fee");
        require!(refund_amount > 0, "Refund amount is zero after gas fee");

        RefundExecutionInputs {
            outpoint,
            deposit_output,
            refund_amount,
        }
    }
