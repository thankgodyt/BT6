### Title
`praosStatePreviousEpochNonce` Written But Never Read in Any Validation — Peras Certificate Epoch-Nonce Check Is Unimplemented - (File: `ouroboros-consensus-protocol/src/ouroboros-consensus-protocol/Ouroboros/Consensus/Protocol/Praos.hs`)

---

### Summary

`PraosState` carries a field `praosStatePreviousEpochNonce` that is written on every epoch transition and serialised into the on-disk chain-dep state, but is **never read** in any validation, leader-check, or certificate-verification path. The code comment that introduces the write explicitly states the field is required to validate Peras certificates when they appear in blocks. Because the consuming validation logic is absent, Peras certificates can be accepted without the epoch-nonce binding check, enabling an unprivileged peer to submit certificates that should be rejected.

---

### Finding Description

`PraosState` is the `ChainDepState` for the Praos consensus protocol. It contains eight fields, one of which is `praosStatePreviousEpochNonce`:

```haskell
data PraosState = PraosState
  { ...
  , praosStateEpochNonce         :: !Nonce   -- current epoch nonce
  , praosStatePreviousEpochNonce :: !Nonce   -- previous epoch nonce
  , ...
  }
``` [1](#0-0) 

The field is written exactly once, inside `tickChainDepState`, on every epoch boundary:

```haskell
praosStatePreviousEpochNonce = praosStateEpochNonce st
```

The comment that accompanies this write is explicit about its purpose:

```
-- - Store the existing current epoch nonce as the "previous epoch" nonce.
--   This is needed to validate Peras certificates when they appear in blocks.
``` [2](#0-1) 

The field is also faithfully serialised and deserialised (position 6 of 8 in the CBOR encoding): [3](#0-2) 

And it is initialised during the TPraos→Praos era translation: [4](#0-3) 

However, a complete audit of every read site in the file shows that `praosStatePreviousEpochNonce` is **never accessed** in:

- `checkIsLeader` — uses only `praosStateEpochNonce`
- `updateChainDepState` — uses only `praosStateEpochNonce` for VRF validation
- `reupdateChainDepState` — does not reference the field at all
- `getPraosNonces` — exports five nonces (`candidateNonce`, `epochNonce`, `evolvingNonce`, `labNonce`, `previousLabNonce`) but **omits** `praosStatePreviousEpochNonce` [5](#0-4) 

The Peras certificate ingestion path (`addCert` in `PerasCertDB`, `chainSelectionForCert` in `ChainSel`) never retrieves `praosStatePreviousEpochNonce` from the chain-dep state to bind a certificate to the epoch in which it was produced. [6](#0-5) [7](#0-6) 

---

### Impact Explanation

Peras certificates boost the weight of a specific block, directly influencing chain selection via `WeightedSelectView`. The intended design requires that a certificate be bound to the epoch in which it was produced, using the previous epoch nonce as a cryptographic anchor. Without this check, a certificate produced in epoch *N* can be replayed or crafted to boost a block in epoch *N+1* (or any other epoch), because the epoch-nonce binding is never enforced.

An attacker who can submit a crafted or replayed Peras certificate to an honest node can cause that node to assign an inflated weight boost to an attacker-chosen block, making the node prefer a non-canonical or adversarially-controlled chain over the honest chain. This is a chain-selection manipulation that bypasses the intended Peras certificate authorization check.

**Impact class:** High — Bypass of Peras certificate checks enabling unauthorized certificate acceptance and chain-selection manipulation.

---

### Likelihood Explanation

The Peras certificate submission path is reachable by any unprivileged peer via the Peras mini-protocol. No special keys, stake majority, or operator access is required to submit a certificate. The missing check is structural (the field is never read), so it is triggered on every certificate submission, not only under adversarial conditions. Likelihood is **Medium-High** given that Peras is an active protocol extension and the certificate submission surface is externally reachable.

---

### Recommendation

Implement the epoch-nonce binding check that the comment promises. When a Peras certificate is validated (either on receipt or when it appears in a block), retrieve `praosStatePreviousEpochNonce` from the current `PraosState` and verify that the certificate's embedded epoch nonce matches. If the field is no longer needed for this purpose (e.g., the check was moved elsewhere or the design changed), remove `praosStatePreviousEpochNonce` from `PraosState`, its serialisation, and its update in `tickChainDepState` to eliminate the dead state and the misleading comment.

  -- Updating the chain dependent state for Praos.
  --
  -- If we are not in a new epoch, then nothing happens. If we are in a new
  -- epoch, we do three things:
  -- - Store the existing current epoch nonce as the "previous epoch" nonce.
  --   This is needed to validate Peras certificates when they appear in blocks.
  -- - Update the epoch nonce to the combination of the candidate nonce and the
  --   nonce derived from the last block of the previous epoch.
  -- - Update the "last block of previous epoch" nonce to the nonce derived
  --   from the last applied block.
  tickChainDepState
    PraosConfig{praosEpochInfo}
    lv
    slot
    st =
      TickedPraosState
        { tickedPraosStateChainDepState = st'
        , tickedPraosStateLedgerView = lv
        }
     where
      newEpoch =
        isNewEpoch
          (History.toPureEpochInfo praosEpochInfo)
          (praosStateLastSlot st)
          slot
      st' =
        if newEpoch
          then
            st
              { praosStateEpochNonce =
                  praosStateCandidateNonce st
                    ⭒ praosStateLastEpochBlockNonce st
              , praosStatePreviousEpochNonce =
                  praosStateEpochNonce st
              , praosStateLastEpochBlockNonce =
                  praosStateLabNonce st
              }
          else st
