### Title
Peras Certificate Validation Bypass via Unconditional `validatePerasCert` Stub — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` method is a stub that unconditionally returns `Right` (success) for every inbound Peras certificate, performing zero cryptographic or structural checks. Because this is the only instance in the codebase and it is wired directly into the production `PerasCertDiffusion` inbound path, any unprivileged peer can inject an arbitrary crafted certificate that will be stored in the `PerasCertDB` and used to influence Peras chain-selection boosting.

---

### Finding Description

The `BlockSupportsPeras` type class declares `validatePerasCert` as the mandatory gate for accepting inbound Peras certificates:

```haskell
validatePerasCert ::
  PerasCfg blk ->
  PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)
```

The only instance in the codebase is a universal stub:

### Impact Explanation

**Impact: Critical — Bypass of Peras certificate validation enabling unauthorized certificate acceptance.**

A `ValidatedPerasCert` stored in the `PerasCertDB` carries a `vpcCertBoost` weight that is used by the Peras chain-selection logic to boost the certified block. Because `validatePerasCert` never rejects any certificate, an attacker can:

1. Craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block point (including a non-canonical or attacker-controlled block).
2. Send it over the `PerasCertDiffusion` miniprotocol.
3. The certificate passes validation unconditionally and is stored with full `perasWeight` boost.
4. The Peras chain-selection logic treats the boosted block as having received a valid quorum certificate, causing honest nodes to prefer the attacker's chosen chain over the canonical one.

This directly satisfies the allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."*

---

### Likelihood Explanation

**Likelihood: High.**

- The `PerasCertDiffusion` server is reachable by any node-to-node peer without authentication.
- No stake, key material, or privileged access is required — the attacker only needs to open a standard peer connection and send a well-formed CBOR-encoded `PerasCert` message.
- The stub is the *only* instance; there is no override for Cardano block types.
- The `TODO` comment and linked issue confirm the validation is intentionally absent, not accidentally removed.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that verifies:

1. **Aggregate BLS signature** over the certified block and round number against the aggregate public key of the claimed voter set (using `verifyAggregateVoteSignature` from `CryptoSupportsAggregateVoteSigning`).
2. **VRF eligibility proofs** for non-persistent voters (using `batchVerifyVRFOutputs` from `CryptoSupportsBatchVRFVerification`).
3. **Quorum threshold**: the claimed voter set's total stake exceeds the Peras quorum threshold.
4. **Round number bounds**: the certificate's round number is within the expected window.

Until the real implementation is in place, the `PerasCertDiffusion` server should be disabled or gated behind a feature flag so that the stub is never reachable from untrusted peers.

---

### Proof of Concept

On a private testnet with Peras enabled:

1. Connect to a target node as a standard peer (no special keys needed).
2. Send a `PerasCertDiffusion` batch containing a single crafted certificate:
   ```
   PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = <attacker-chosen block point> }
   ```
   encoded as CBOR per the `Serialise (PerasCert blk)` instance.
3. Observe that `processCerts` calls `validatePerasCert mkPerasParams cert` → `Right ValidatedPerasCert{…}` unconditionally.
4. The certificate is stored in `PerasCertDB` with full `perasWeight` boost.
5. The Peras chain-selection logic now treats the attacker-chosen block as having a valid quorum certificate, causing the node to prefer it over the honest canonical chain.
