### Title
Peras Vote and Certificate Validation Bypass via Stub Implementation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The default `BlockSupportsPeras` instance ships in production source with a `validatePerasCert` that unconditionally returns `Right` for every inbound certificate, and a `validatePerasVote` that performs no cryptographic verification whatsoever — the `PerasVote` wire type carries no signature field at all. An unprivileged peer can therefore forge votes attributed to any registered voter, manufacture a false quorum, obtain a `ValidatedPerasCert` with a non-zero chain-selection boost, and inject it into the node's ChainDB. The result is that chain selection can be made to prefer a non-canonical fork without the attacker controlling any stake or keys.

---

### Finding Description

**Root cause 1 — `validatePerasCert` is an unconditional stub:** [1](#0-0) 

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params   -- non-zero boost assigned unconditionally
      }
```

Every certificate received from a peer is accepted and assigned a chain-selection boost equal to `perasWeight params`, regardless of its round number, boosted-block pointer, or any cryptographic proof.

**Root cause 2 — `validatePerasVote` performs no signature check; `PerasVote` carries no signature field:** [2](#0-1) 

The `PerasVote` data type is:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound   :: PerasRoundNo
  , pvVoteBlock   :: Point blk
  , pvVoteVoterId :: PerasVoterId   -- no signature field
  }
```

`validatePerasVote` only checks that `pvVoteVoterId` appears in the stake distribution; it never verifies that the sender actually controls the corresponding key:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
  | otherwise = Left PerasValidationErr
```

**Root cause 3 — the production inbound pipeline calls these stubs directly:**

`processCerts` and `processVotes` are the live inbound handlers wired into the node's `ObjectDiffusion` layer. They call `validatePerasCert` / `validatePerasVote` and add every passing object to the ChainDB: [3](#0-2) [4](#0-3) 

The comment at the call site confirms the stub is intentionally wired in for now:

```haskell
-- TODO replace when actual plumbing is in place
(validatePerasCert mkPerasParams)
```

**Quorum logic uses the injected stake directly:**

`votesReachQuorum` sums `vpvVoteStake` values from `ValidatedPerasVote` objects and compares against the quorum threshold. Because `validatePerasVote` assigns the real registered stake of the impersonated voter, an attacker who sends `N` forged votes for high-stake pools can trivially exceed the quorum threshold: [5](#0-4) 

---

### Impact Explanation

This is a **bypass of Peras voting and certificate checks** that enables unauthorized certificate acceptance and chain-selection manipulation. Concretely:

1. A peer forges `ValidatedPerasVote` objects for high-stake pool IDs (no key material required).
2. `votesReachQuorum` returns a `ValidatedPerasVotesWithQuorum` once the summed stake exceeds the threshold.
3. `forgePerasCert` (also a stub returning `Right`) produces a `ValidatedPerasCert` with `vpcCertBoost = perasWeight params`.
4. Alternatively, the attacker skips votes entirely and directly injects a `PerasCert` pointing at any `Point blk`; `validatePerasCert` accepts it unconditionally.
5. The boosted block gains a chain-selection advantage proportional to `perasWeight`, potentially causing an honest node to switch to a non-canonical fork.

This matches the **Critical** allowed impact: *"Bypass of … Peras voting or certificate checks … that enables unauthorized … certificate acceptance."* It also matches **High**: *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The Peras `ObjectDiffusion` mini-protocol is compiled into the production binary and the `BlockSupportsPeras` instance is the only instance in the repository (the comment explicitly calls it "degenerate instance for all blks to get things to compile"). Any deployment — including a private testnet or a Peras-enabled preview network — that activates the Peras object-diffusion handlers exposes this path to every connected peer. No stake, keys, or operator access is required; a single TCP connection suffices.

---

### Recommendation

1. **Add a signature field to `PerasVote`** (e.g., a DSIGN signature over `(pvVoteRound, pvVoteBlock)` under the voter's cold or hot key) and verify it in `validatePerasVote` before accepting the vote.
2. **Implement real certificate validation in `validatePerasCert`**: verify the committee-selection proof, check that the certificate's quorum of signed votes is present and cryptographically valid, and confirm the boosted block is on a known chain.
3. **Do not wire stub validators into the live inbound pipeline.** Gate the `ObjectDiffusion` handlers behind a feature flag or return `Left PerasValidationErr` from the stubs until real validation is in place, so that no inbound object can be accepted before the checks exist.
4. **Track the open issue** referenced in the TODO comments (`cardano-peras/issues/120`) as a security-critical item, not merely a correctness TODO.

---

### Proof of Concept

With the Peras `ObjectDiffusion` handlers active (private testnet or preview network):

```
# Attacker connects as a peer and sends crafted PerasVote messages:
#   pvVoteRound  = <current round>
#   pvVoteBlock  = <point of a fork tip the attacker wants to boost>
#   pvVoteVoterId = <ID of any high-stake pool visible in the stake distribution>
#
# validatePerasVote checks only Map.lookup pvVoteVoterId stakeDistr — succeeds.
# Repeat for enough pool IDs to exceed the quorum threshold.
# votesReachQuorum returns Just ValidatedPerasVotesWithQuorum.
# forgePerasCert produces a ValidatedPerasCert with vpcCertBoost = perasWeight params.
# ChainDB.addPerasCertAsync stores the cert.
# Chain selection now applies the boost to the fork tip, potentially switching the node.
#
# Alternatively, skip votes entirely:
# Send a PerasCert { pcCertRound = r, pcCertBoostedBlock = <fork tip> }.
# validatePerasCert returns Right unconditionally.
# Same chain-selection effect with a single message.
```

The attacker-controlled entry path is the Peras object-diffusion mini-protocol, reachable by any unprivileged peer over the standard node-to-node connection.

```haskell
-- It returns 'Nothing' if either of these conditions is not met.
votesReachQuorum ::
  StandardHash blk =>
  PerasCfg blk ->
  [ValidatedPerasVote blk] ->
  Maybe (ValidatedPerasVotesWithQuorum blk)
votesReachQuorum cfg votes =
  case votes of
    -- We need at least one vote to determine who these votes are for, so we
    -- can't vacuously reach a quorum, even if the quorum threshold is 0.
    [] -> Nothing
    -- If we have at least one vote, we must check that all votes are for the
    -- same target, and that their total stake of is above the quorum threshold.
    (v0 : vs)
      | not (allVotesMatchTarget v0 vs) ->
          Nothing
      | not votesHaveEnoughStake ->
          Nothing
      | otherwise ->
          Just
            ValidatedPerasVotesWithQuorum
              { vpvqTarget = getPerasVoteTarget v0
              , vpvqVotes = v0 :| vs
              , vpvqPerasCfg = cfg
              }
 where
  totalVoteStake =
    mconcat (vpvVoteStake <$> votes)
  votesHaveEnoughStake =
    stakeAboveThreshold cfg totalVoteStake
```
