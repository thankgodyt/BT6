### Title
Impossibility to Update Chain Signatures Root Public Key After Initial Sync — (File: `contracts/satoshi-bridge/src/api/management.rs`)

### Summary
The `sync_chain_signatures_root_public_key` function enforces a one-time-only restriction via a hard `require!` guard. Once the root public key is set, neither this function nor `update_config` (which omits `chain_signatures_root_public_key` and `change_address` from `ConfigUpdate`) provides any DAO-accessible path to refresh these values. If the MPC chain-signatures contract ever rotates its root key, the bridge is permanently locked to the stale key: all new deposit addresses are derived from the wrong key, and MPC signing for withdrawals and refunds will fail, causing irreversible loss of bridged funds.

### Finding Description

In `management.rs`, `sync_chain_signatures_root_public_key` contains:

```rust
require!(
    self.internal_config()
        .chain_signatures_root_public_key
        .is_none(),
    "Already sync"
);
``` [1](#0-0) 

Once the callback `sync_root_public_key_callback` successfully writes `Some(root_public_key)` and derives `change_address`, the guard permanently blocks any future call to this function. [2](#0-1) 

The `ConfigUpdate` struct — the only other DAO-accessible config mutation path — does not include `chain_signatures_root_public_key` or `change_address`: [3](#0-2) 

`chain_signatures_root_public_key` is the root of the KDF used to derive every deposit address and the bridge's own `change_address`. Both are set once and never updatable: [4](#0-3) 

### Impact Explanation

If the NEAR MPC chain-signatures contract rotates its root public key (a normal operational event for MPC systems):

1. The bridge's stored `chain_signatures_root_public_key` is now stale.
2. All new deposit addresses are derived from the old key via KDF — users send BTC to addresses the MPC can no longer sign for.
3. Withdrawal and refund signing requests sent to the MPC will produce signatures that do not correspond to the UTXOs being spent, causing on-chain transaction invalidity.
4. The `change_address` is also stale, so any BTC change output goes to an address the bridge cannot spend.
5. There is no DAO function to correct this; a full contract upgrade is the only escape, during which all in-flight deposits and withdrawals are at risk.

This constitutes **permanent locking / loss of user and protocol funds** — a Critical impact.

### Likelihood Explanation

MPC key rotation is a standard security practice for threshold-signature systems. The NEAR chain-signatures service is an actively developed MPC network; key rotation upon node set changes, security incidents, or protocol upgrades is expected. The bridge provides no update path, so any rotation event triggers the impact above without any attacker action required — a public user simply depositing BTC after a rotation is sufficient to lose funds.

### Recommendation

Remove the one-time-only guard and replace it with a DAO-only re-sync function, or add `chain_signatures_root_public_key` and `change_address` to `ConfigUpdate` with appropriate DAO access control:

```rust
#[payable]
#[access_control_any(roles(Role::DAO))]
pub fn resync_chain_signatures_root_public_key(&mut self) -> Promise {
    assert_one_yocto();
    // Allow DAO to re-sync at any time (e.g., after MPC key rotation)
    self.sync_chain_signatures_root_public_key_promise()
}
```

The original `sync_chain_signatures_root_public_key` can retain its `is_none()` guard for the initial bootstrap path; the new function provides the update path.

### Proof of Concept

1. DAO calls `sync_chain_signatures_root_public_key` → `chain_signatures_root_public_key` is set to `Some(key_v1)`, `change_address` derived from `key_v1`.
2. MPC chain-signatures contract rotates to `key_v2` (routine operational event).
3. DAO calls `sync_chain_signatures_root_public_key` again → **panics**: `"Already sync"`.
4. DAO calls `update_config` with a `ConfigUpdate` → `chain_signatures_root_public_key` and `change_address` are absent from `ConfigUpdate`; no update possible.
5. Bridge continues deriving deposit addresses from `key_v1`. Users deposit BTC to these addresses.
6. MPC signs with `key_v2`; signatures do not match `key_v1`-derived scripts → withdrawals and refunds are invalid on-chain.
7. BTC sent to `key_v1`-derived addresses is permanently unspendable by the bridge.

    pub fn sync_root_public_key_callback(&mut self) -> bool {
        if let Ok(result_bytes) = env::promise_result_checked(0, MAX_PUBLIC_KEY_RESULT) {
            let root_public_key =
                serde_json::from_slice::<PublicKey>(&result_bytes).expect("Invalid PublicKey");
            self.internal_mut_config().chain_signatures_root_public_key = Some(root_public_key);
            let change_address = self
                .generate_utxo_chain_address(env::current_account_id().as_str())
                .to_string();
            self.internal_mut_config().change_address = Some(change_address);
            true
        } else {
            false
