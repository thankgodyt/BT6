### Title
Hardcoded Static Gas for Cross-Contract Token Transfers Creates Stuck-State Risk - (File: contracts/satoshi-bridge/src/token_transfer.rs)

### Summary
`token_transfer.rs` allocates fixed static gas amounts (`GAS_FOR_TOKEN_TRANSFER = 20 Tgas`, `GAS_FOR_AFTER_TOKEN_TRANSFER = 10 Tgas`) for every cross-contract `ft_transfer` call and its callback. This is the NEAR analog of Solidity's `.transfer` anti-pattern: a hardcoded gas ceiling that silently breaks if the underlying gas cost model changes. If the `ft_transfer` XCC exhausts its 20 Tgas budget, the transfer fails; if the callback then exhausts its 10 Tgas budget and panics, the state mutation that already removed the user's entry from `lost_found` is not rolled back, permanently destroying those funds.

### Finding Description

`internal_transfer_nbtc` and `internal_withdraw_protocol_fee` both use `with_static_gas` with compile-time constants:

```rust
// contracts/satoshi-bridge/src/token_transfer.rs
pub const GAS_FOR_TOKEN_TRANSFER: Gas = Gas::from_tgas(20);
pub const GAS_FOR_AFTER_TOKEN_TRANSFER: Gas = Gas::from_tgas(10);
``` [1](#0-0) 

`internal_transfer_nbtc` is called from `claim_lost_found`, which removes the user's balance from `lost_found` **before** the async transfer resolves:

```rust
// api/bridge.rs – claim_lost_found
let amount = self.data_mut().lost_found.remove(&account_id)   // committed immediately
    .expect("The account does not have lostfound");
self.internal_transfer_nbtc(&account_id, amount)               // async, may fail
``` [2](#0-1) 

The callback is supposed to restore the balance on failure:

```rust
// token_transfer.rs – transfer_nbtc_callback
if !promise_success {
    self.data_mut().lost_found.entry(account_id.clone())
        .and_modify(|v| *v += amount.0).or_insert(amount.0);
}
``` [3](#0-2) 

There are two failure modes:

**Mode 1 (Medium – stuck state):** If `ft_transfer` exhausts its 20 Tgas budget, the XCC fails. The callback fires with `is_promise_success() = false` and re-inserts the amount into `lost_found`. The user's funds are not lost but are stuck: every subsequent `claim_lost_found` call will repeat the same failure loop until the contract is upgraded with a higher gas constant. This requires operator/DAO intervention.

**Mode 2 (Critical – permanent loss):** If the callback itself exhausts its 10 Tgas budget and panics, NEAR rolls back only the callback's state changes. The `lost_found.remove()` executed in `claim_lost_found` is already committed to state. The user's nBTC balance is gone from `lost_found` and was never transferred — permanently destroyed. [4](#0-3) 

### Impact Explanation

- **Mode 1:** All users whose nBTC is held in `lost_found` are unable to reclaim it. The bridge enters a stuck state for those balances, requiring a DAO-authorized contract upgrade to fix. This matches the allowed Medium impact: *"stuck bridge state requiring operator intervention."*
- **Mode 2:** If the callback gas budget is also exhausted, the user's `lost_found` balance is silently destroyed — a permanent, irrecoverable loss of bridged funds. This matches the allowed Critical impact: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds."*

### Likelihood Explanation

The trigger is a mismatch between the hardcoded gas constants and the actual gas consumed by `ft_transfer` or the callback. This can occur if:
- The NEAR protocol adjusts opcode/storage gas costs (as Ethereum's Istanbul hard fork did for EVM opcodes, motivating the original report).
- The nBTC token contract is upgraded to perform additional storage operations inside `ft_transfer`.
- The `lost_found` map grows large enough that storage-trie operations cost more gas than anticipated.

Mode 1 likelihood is Low-to-Medium (protocol gas changes are infrequent but have precedent). Mode 2 likelihood is Low (10 Tgas is currently ample for the callback's storage write), but the consequence is irreversible, making the risk non-negligible.

### Recommendation

Replace `with_static_gas` with `with_unused_gas` (passing remaining gas minus a reserved buffer) so that the XCC and callback always receive the gas actually available at call time, rather than a compile-time constant. This is the NEAR equivalent of replacing `.transfer` with `.call{value: ...}("")`:

```rust
// Instead of:
.with_static_gas(GAS_FOR_TOKEN_TRANSFER)
// Use:
.with_unused_gas_weight(1)  // or compute dynamically: env::prepaid_gas() - env::used_gas() - RESERVE
```

Additionally, ensure the callback always has a guaranteed minimum gas reservation so it cannot be starved even if the XCC consumes more than expected.

### Proof of Concept

1. User has nBTC in `lost_found` (e.g., from a failed cancel-withdraw refund).
2. NEAR protocol upgrades storage gas costs so that `ft_transfer` on the nBTC contract now requires 25 Tgas.
3. User calls `claim_lost_found()`.
4. `lost_found.remove(&account_id)` executes and commits — balance is gone from state.
5. `internal_transfer_nbtc` fires `ft_transfer` with only 20 Tgas → XCC runs out of gas → fails.
6. `transfer_nbtc_callback` fires with `is_promise_success() = false` and 10 Tgas.
   - **Mode 1:** Callback succeeds → re-inserts into `lost_found` → user retries → same failure → stuck indefinitely.
   - **Mode 2:** If callback also runs out of gas (e.g., storage costs also rose) → callback panics → re-insertion rolled back → `lost_found` entry is gone → funds permanently destroyed. [5](#0-4) [6](#0-5)

pub const GAS_FOR_TOKEN_TRANSFER: Gas = Gas::from_tgas(20);

impl Contract {
    pub fn internal_withdraw_protocol_fee(&self, amount: u128) -> Promise {
        ext_ft_core::ext(self.internal_config().nbtc_account_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(GAS_FOR_TOKEN_TRANSFER)
            .ft_transfer(env::predecessor_account_id(), amount.into(), None)
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_AFTER_TOKEN_TRANSFER)
                    .withdraw_protocol_fee_callback(amount.into()),
            )
    }

    pub fn internal_transfer_nbtc(&self, account_id: &AccountId, amount: u128) -> Promise {
        ext_ft_core::ext(self.internal_config().nbtc_account_id.clone())
            .with_attached_deposit(NearToken::from_yoctonear(1))
            .with_static_gas(GAS_FOR_TOKEN_TRANSFER)
            .ft_transfer(account_id.clone(), amount.into(), None)
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_AFTER_TOKEN_TRANSFER)
                    .transfer_nbtc_callback(account_id.clone(), amount.into()),
