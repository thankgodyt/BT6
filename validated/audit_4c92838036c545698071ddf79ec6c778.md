### Title
ChainSync Client `checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot`, Causing Incorrect Chain Preference Decisions Under Peras — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard in the ChainSync client unconditionally passes `emptyPerasWeightSnapshot` (zero weight for all blocks) to `preferAnchoredCandidate` when deciding whether to disconnect from a peer whose headers are beyond the forecast horizon. When Peras is active and the canonical chain carries weight boosts, this guard compares chains by raw block count only, ignoring Peras weight entirely. A candidate chain that is shorter in block count but heavier in total Peras weight is incorrectly judged "not preferred," causing the node to disconnect from every peer offering the canonical chain and remain permanently on a lighter, non-canonical fork.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside `readLedgerStateHelper` whenever `forecastFor` returns `OutsideForecastRange` — i.e., the incoming header's slot is beyond the current forecast horizon. Its purpose is: if the candidate chain is not preferred over ours, there is no point waiting for the horizon to advance, so disconnect (`CandidateTooSparse`). If it is preferred, block and retry.

```haskell
-- ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot          -- ← always zero weight
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
``` [1](#0-0) 

`preferAnchoredCandidate` dispatches on whether the weight snapshot is empty. When it is empty (as hardcoded here), it falls into the block-count-only path:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      ...
      (_ :> ourTip, _ :> theirTip) ->
        case preferCandidate
          (projectChainOrderConfig cfg)
          (selectView cfg (getHeader1 ourTip))   -- block number only
          (selectView cfg (getHeader1 theirTip)) of ...
  | otherwise =
      -- uses weightedSelectView (block number + Peras boost)
``` [2](#0-1) 

When Peras is active, the canonical chain is the *heaviest* chain (block count + sum of Peras boosts), not necessarily the longest. `SecurityParam` is explicitly redefined to mean maximum rollback *weight*, not block count:

```haskell
-- In weightiest-chain protocols (such as Ouroboros Peras), we interpret this as
-- the maximum amount of weight we can roll back.
newtype SecurityParam = SecurityParam {maxRollbacks :: NonZero Word64}
``` [3](#0-2) 

Chain selection in ChainDB correctly uses the actual `weights` snapshot:

```haskell
ShouldSwitch reason <- [preferAnchoredCandidate bcfg weights curChain $ Diff.getSuffix chain]
``` [4](#0-3) 

But `checkPreferTheirsOverOurs` — the earlier gate that decides whether to even *attempt* chain selection — does not. The two paths are inconsistent: ChainDB would select the heavier chain, but the ChainSync client disconnects before ChainDB ever sees it.

---

### Impact Explanation

**Scenario (Peras active):**

1. An adversarial peer feeds the syncing node a long chain `A` (many blocks, zero Peras boosts). The node adopts `A` as its current selection.
2. The canonical chain `B` is shorter in block count but carries Peras weight boosts, making its total weight exceed `A`'s.
3. An honest peer begins serving `B`. Because the node is far ahead on `A`, `B`'s headers fall beyond the forecast horizon.
4. `readLedgerStateHelper` calls `checkPreferTheirsOverOurs`. With `emptyPerasWeightSnapshot`, `preferAnchoredCandidate` compares only block numbers: `B` is shorter → `ShouldNotSwitch` → `throwSTM CandidateTooSparse`.
5. The node disconnects from every honest peer offering `B`. It never reaches ChainDB's correct weight-aware selection.
6. The node remains permanently on the lighter, non-canonical chain `A`.

This matches: **High — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.**

The analog to the Balancer report is direct: the Balancer strategy used the wrong exit kind (`BPT_IN_FOR_EXACT_TOKENS_OUT`) and accepted any slippage; here the ChainSync client uses the wrong weight snapshot (`emptyPerasWeightSnapshot`) and accepts any block-count comparison, ignoring the actual security metric (total weight) that the protocol is designed around.

---

### Likelihood Explanation

- **Peras deployment**: Peras is under active development and integration into the codebase. The weight infrastructure (`PerasWeightSnapshot`, `WeightedSelectView`, `maxRollbackWeight`) is already wired into ChainDB's chain selection. The bug is latent and will become exploitable upon Peras activation.
- **Attacker capability**: No special privileges required. Any peer can serve a long, unboosted chain to push the node ahead in block count, then the canonical (boosted) chain naturally falls behind the forecast horizon during the catch-up phase.
- **Persistence**: The disconnect is not a one-time event. As long as the canonical chain is shorter by block count and its headers remain beyond the forecast horizon, every reconnection attempt triggers the same incorrect disconnect.
- **Known issue**: The developers have flagged this with `-- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64`, confirming awareness but no fix yet in the production path. [5](#0-4) 

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the actual Peras weight snapshot sourced from the same place ChainDB obtains it (e.g., via a `STM` read of the shared `PerasWeightSnapshot` TVar). Alternatively, remove the check entirely as the TODO suggests — the Genesis Density Disconnection Rule (GDD) already handles the case of candidates that cannot win, making this guard redundant and incorrect under Peras.

---

### Proof of Concept

```
Setup (private testnet, Peras active):

1. Node N starts syncing.
2. Adversary A serves chain C_long:
     blocks: 5000, Peras boosts: 0, total weight: 5000
   Node N adopts C_long.

3. Honest peer H serves canonical chain C_canon:
     blocks: 4800, Peras boosts: 600 (e.g., 30 boosted blocks × 20 each)
     total weight: 5400  >  5000  → C_canon is canonical

4. C_canon's tip slot is beyond N's forecast horizon
   (N is far ahead on C_long; forecast horizon = 3k/f slots from intersection).

5. N calls readLedgerStateHelper → forecastFor returns OutsideForecastRange
   → checkPreferTheirsOverOurs is invoked.

6. preferAnchoredCandidate(emptyPerasWeightSnapshot, C_long_frag, C_canon_frag):
     C_long tip blockNo = 5000
     C_canon tip blockNo = 4800
     5000 > 4800 → ShouldNotSwitch GT

7. throwSTM CandidateTooSparse → N disconnects from H.

8. N reconnects to H → same result → N permanently stuck on C_long (weight 5000)
   instead of C_canon (weight 5400).

Expected (correct) behavior:
   preferAnchoredCandidate(actualWeights, ...) would compute:
     C_long total weight  = 5000
     C_canon total weight = 5400
     5000 < 5400 → ShouldSwitch → N continues waiting, eventually adopts C_canon.
```

preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          (Empty _, Empty _) -> ShouldNotSwitch EQ
          (_, Empty _) -> ShouldNotSwitch GT
          (Empty ourAnchor, _ :> theirTip) ->
            if blockPoint theirTip /= castPoint (AF.anchorToPoint ourAnchor)
              then
                ShouldSwitch (Right $ Longer $ Comparing (AF.anchorToBlockNo ourAnchor) (At (blockNo theirTip)))
              else ShouldNotSwitch EQ
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of
              ShouldSwitch r -> ShouldSwitch (Right r)
              ShouldNotSwitch o -> ShouldNotSwitch o
  | otherwise =
      case AF.intersect ours cand of
        Nothing -> error "precondition violated: fragments must intersect"
        Just (_oursPrefix, _candPrefix, oursSuffix, candSuffix) ->
          case preferCandidate
            (projectChainOrderConfig cfg)
            (weightedSelectView cfg weights oursSuffix)
            (weightedSelectView cfg weights candSuffix) of
            ShouldSwitch r -> ShouldSwitch (Left r)
            ShouldNotSwitch o -> ShouldNotSwitch o
