### Title
`checkPreferTheirsOverOurs` Uses Hardcoded `emptyPerasWeightSnapshot`, Ignoring Live Certificate Boosts in Chain-Preference Decision - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

When a peer's header is beyond the forecast horizon, the ChainSync client calls `checkPreferTheirsOverOurs` to decide whether to disconnect from that peer. This function calls `preferAnchoredCandidate` with a hardcoded `emptyPerasWeightSnapshot` instead of the live snapshot from `PerasCertDB`. When Peras is enabled, this causes the node to evaluate chain preference purely by block count, ignoring certificate boosts. A peer serving the correct (heavier-by-Peras-weight) chain can be incorrectly disconnected, while an adversary serving a longer-by-block-count but lighter chain is retained, enabling the node to be steered onto a less-secure chain.

---

### Finding Description

`checkPreferTheirsOverOurs` is invoked inside the ChainSync client when a received header slot is beyond the forecast horizon. Its purpose is to disconnect from peers whose candidate chain is not preferable to the node's current selection, since such a chain will never be adopted:

```haskell
checkPreferTheirsOverOurs :: KnownIntersectionState blk -> STM m ()
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty; never reads PerasCertDB
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse ...
```

The `emptyPerasWeightSnapshot` constant is a `Map` with no entries:

```haskell
emptyPerasWeightSnapshot :: PerasWeightSnapshot blk
emptyPerasWeightSnapshot = PerasWeightSnapshot Map.empty
```

`preferAnchoredCandidate` short-circuits to a pure block-count comparison when the snapshot is empty:

```haskell
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      -- compare by SelectView (block number + tiebreaker) only
      ...
  | otherwise =
      -- compare by weighted (Peras-boosted) suffix length
      ...
```

Everywhere else in the production path — `chainSelSync`, `constructPreferableCandidates`, `switchTo`, and the GSM's `getCandidateOverSelection` — the actual live snapshot is fetched from `PerasCertDB`:

```haskell
-- ChainSel.hs
weights <- atomically $ (forgetFingerprint <$> Query.getPerasWeightSnapshot cdb)

-- NodeKernel.hs
weights <- ChainDB.getPerasWeightSnapshot chainDB
pure $ \(headers, _lst) state -> ...
  preferAnchoredCandidate (configBlock cfg) (forgetFingerprint weights) headers (csCandidate state)
```

`checkPreferTheirsOverOurs` is the only production call site that substitutes `emptyPerasWeightSnapshot` for the live snapshot. The TODO comment acknowledges this is a known defect tracked at `https://github.com/tweag/cardano-peras/issues/64`.

---

### Impact Explanation

When Peras is enabled, a chain's total weight is the sum of its block count and the Peras certificate boosts accumulated on its blocks. A chain with fewer blocks but large certificate boosts can be strictly preferred over a longer-by-block-count chain.

Because `checkPreferTheirsOverOurs` ignores boosts, the following scenario arises:

- **Honest peer** serves a chain: 99 blocks, large Peras boost → actually preferred.
- **Adversary** serves a chain: 100 blocks, zero Peras boost → actually not preferred.

`checkPreferTheirsOverOurs` evaluates the honest peer's chain as "not preferred" (99 < 100 blocks) and fires `throwSTM CandidateTooSparse`, disconnecting from the honest peer. The adversary's chain is evaluated as "preferred" (100 > 99 blocks) and the connection is retained. The node then downloads and validates the adversary's blocks through the normal `ChainSel` path, which does use the live snapshot — but by that point the honest peer has been evicted and the adversary's chain is the only candidate.

This is a chain-selection bug that lets an unprivileged peer cause an honest node to prefer a non-canonical, less-secure chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

Peras is currently disabled by default (`emptyPerasWeightSnapshot` is the effective snapshot everywhere when Peras is off, so the bug is dormant). Once Peras is enabled on a network, the bug becomes reachable by any peer that:

1. Sends a header whose slot exceeds the node's forecast horizon (a normal condition during initial sync or after a long outage — the forecast horizon is `3k/f ≈ 36 hours` on mainnet).
2. Serves a chain that is longer by block count than the honest chain but lighter by Peras weight.

No special privileges, key material, or stake majority are required. The entry path is the standard ChainSync miniprotocol message stream.

---

### Recommendation

Replace `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live snapshot read from `PerasCertDB`, consistent with every other call site. The snapshot is already available via `Query.getPerasWeightSnapshot cdb` (an STM action), so it can be read atomically inside the same `STM m ()` block. Alternatively, if the intent of the TODO is to remove the check entirely (as the linked issue suggests), the removal should be completed before Peras is enabled on any production network.

---

### Proof of Concept

1. Enable Peras on a private testnet.
2. Issue enough Peras certificates to give the honest chain's tip a large weight boost, making it heavier than a competing adversarial chain that has one more block but no boosts.
3. Connect the target node to both the honest peer and the adversarial peer.
4. Arrange for the honest peer's next header to be beyond the target node's forecast horizon (e.g., by pausing the target node for longer than `3k/f` slots).
5. Observe: `checkPreferTheirsOverOurs` fires `CandidateTooSparse` for the honest peer (its chain is shorter by block count) and retains the adversarial peer.
6. The target node downloads and selects the adversarial chain via the normal `ChainSel` path, which now has no honest candidate to compare against.
