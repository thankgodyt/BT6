### Title
`safe_mint` Mints nBTC to Bridge Account Before Registration Check, Leaving Tokens Permanently Stuck and Inflating Supply — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nBTC contract unconditionally mints tokens to the bridge's own account **before** verifying that the intended recipient is registered. When the recipient is unregistered, the function returns `U128(0)` and exits — but the minted tokens remain in the bridge's account with no on-chain mechanism to burn them. Because NEAR cross-contract calls cannot be retroactively reverted, the bridge's callback cannot undo the minting, permanently inflating the nBTC total supply without corresponding BTC collateral.

---

### Finding Description

In `contracts/nbtc/src/lib.rs`, the `safe_mint` function follows this sequence:

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← mints unconditionally

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← exits, tokens stuck
    }
    ...
}
``` [1](#0-0) 

Step 1 (`internal_deposit(&self.bridge_id, amount)`) executes and succeeds on the nBTC contract before the registration check on line 114. When the recipient account is absent, the function returns `U128(0)` to the bridge's callback. The bridge's callback interprets this as a failed mint and, per the documented design, does **not** mark the deposit UTXO as verified — allowing the user to request a BTC refund. However, the nBTC tokens already minted to the bridge's account cannot be un-minted from the callback: NEAR's async model means the `safe_mint` call already committed its state change.

The `burn` function, which is the only mechanism to reduce the bridge's nBTC balance, is only invoked during the normal withdrawal verification path (`verify_withdraw`):

```rust
pub fn burn(
    &mut self,
    burn_account_id: AccountId,
    burn_amount: U128,
    ...
) {
    self.assert_bridge();
    self.token
        .internal_withdraw(&self.bridge_id, burn_amount.into());
``` [2](#0-1) 

There is no call to `burn` in the safe-deposit failure path. The extra tokens accumulate in the bridge's account.

The safe deposit flow is documented as:

> `Some(..)` — safe deposit (e.g. Omni Bridge): charges no fee, **reverts the whole transaction if minting fails** (no lost & found) [3](#0-2) 

This guarantee is broken: the nBTC minting cannot be reverted once `internal_deposit` has executed.
