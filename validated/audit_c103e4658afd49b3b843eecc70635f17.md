### Title
No Bitcoin Reorganization Handling Enables Permanent Unauthorized nBTC Minting After Reorg — (File: `contracts/satoshi-bridge/src/btc_light_client/deposit.rs`)

---

### Summary

The `satoshi-bridge` deposit verification flow permanently marks UTXOs as verified and mints nBTC with no mechanism to detect or respond to Bitcoin chain reorganizations. Once `verify_deposit_callback` executes, the UTXO key is inserted into `verified_deposit_utxo` (an append-only `LookupSet` with no removal path for reorganized deposits) and nBTC is minted. If the underlying Bitcoin transaction is subsequently reorganized away from the canonical chain, the minted nBTC cannot be reclaimed and the bridge has no recovery path.

---

### Finding Description

The deposit flow in `verify_deposit_callback` (and its safe-deposit counterpart `verify_safe_deposit_callback`) performs three irreversible state mutations on a single `verify_transaction_inclusion` result:

1. **Permanent UTXO marking** — `verified_deposit_utxo.insert(utxo_storage_key)` is called unconditionally on success. [1](#0-0) 

2. **nBTC minting** — `internal_mint_promise` is called immediately after, crediting the recipient. [2](#0-1) 

3. **No rollback path** — `verified_deposit_utxo` is a `LookupSet<String>` stored in `ContractData`. There is no code path anywhere in the bridge that removes an entry from this set for a reorganized deposit. [3](#0-2) 

The bridge's only protection against reorganizations is the `confirmations_strategy` configuration, which is enforced by the external `btc-light-client` contract at the moment `verify_transaction_inclusion` is called. [4](#0-3) 

The bridge itself performs no block-hash comparison, tracks no chain tip, and has no post-mint reorganization detection. The `confirmations_strategy` enforces a minimum of 2 and maximum of 100 confirmations. [5](#0-4) 

If a reorganization occurs **after** the light client returns `true` (e.g., the reorg is processed by the light client after the NEAR callback has already executed), the bridge state is permanently inconsistent: nBTC exists on NEAR with no backing BTC on the canonical Bitcoin chain, and the `verified_deposit_utxo` entry blocks any future `request_refund` for that UTXO. [6](#0-5) 

The `safe_mint_callback` does implement a rollback for failed `ft_on_transfer` calls, but this is entirely unrelated to Bitcoin reorganizations — it handles NEAR-side cross-contract call failures only. [7](#0-6) 

---

### Impact Explanation

**Critical — Unauthorized minting of nBTC.**

An attacker who deposits BTC and has nBTC minted before a reorganization removes their deposit transaction from the canonical chain retains the minted nBTC with no corresponding BTC locked in the bridge. The bridge's `verified_deposit_utxo` set permanently blocks any refund path for that UTXO, and there is no operator-accessible burn or rollback function for reorganized deposits. The protocol's nBTC supply becomes unbacked by the corresponding amount of BTC.

---

### Likelihood Explanation

**Low.** Bitcoin reorganizations beyond 6 blocks are essentially impossible on mainnet under normal conditions. The confirmation strategy (minimum 2, typically configured higher) provides meaningful protection. However:

- The minimum allowed confirmation count is 2, which is insufficient protection against shallow reorgs.
- A timing window exists between the light client processing a reorg and the NEAR callback executing — if the callback lands before the light client updates its chain view, a recently reorganized block could pass verification.
- The structural gap (no rollback mechanism) means any reorg that does slip through causes permanent, irrecoverable damage to the nBTC supply.

---

### Recommendation

**Short term:** Add a post-mint reorganization guard. Store the `tx_block_blockhash` alongside each `verified_deposit_utxo` entry. Expose a privileged `invalidate_deposit(utxo_storage_key)` function (DAO/Operator only) that, after verifying via the light client that the block hash no longer exists on the canonical chain, removes the UTXO from `verified_deposit_utxo` and burns the corresponding nBTC.

**Long term:** Implement a two-phase deposit finalization: a "pending" phase where nBTC is escrowed (not freely transferable) for a reorganization safety window, and a "finalized" phase after the window passes. This mirrors the confirmation-interval approach recommended in the original report.

---

### Proof of Concept

1. Attacker sends BTC to their deposit address on Bitcoin.
2. Relayer calls `verify_deposit_v2` with a valid Merkle proof once the transaction has 2+ confirmations (the minimum).
3. The light client's `verify_transaction_inclusion_v2` returns `true`.
4. `verify_deposit_callback` executes: `verified_deposit_utxo.insert(utxo_storage_key)` and `internal_mint_promise` credit nBTC to the attacker. [8](#0-7) 
5. A Bitcoin reorganization removes the attacker's deposit transaction from the canonical chain (naturally or via a shallow reorg with low confirmation count).
6. The attacker retains the minted nBTC. The `verified_deposit_utxo` entry blocks `request_refund` from being accepted for this UTXO. [6](#0-5) 
7. The bridge's nBTC supply is now unbacked by the corresponding BTC amount, with no operator-accessible recovery path in the production code.

    #[private]
    pub fn safe_mint_callback(
        &mut self,
        recipient_id: AccountId,
        mint_amount: U128,
        pending_utxo_info: PendingUTXOInfo,
    ) -> bool {
        let is_success = !is_refund_required();
        let relayer_account_id = env::signer_account_id();

        if is_success {
            Event::UtxoAdded {
                utxo_storage_keys: vec![pending_utxo_info.utxo_storage_key.clone()],
                balances: Some(vec![U128(pending_utxo_info.utxo.balance.into())]),
            }
            .emit();
            self.internal_set_utxo(&pending_utxo_info.utxo_storage_key, pending_utxo_info.utxo);
        } else {
            self.data_mut()
                .verified_deposit_utxo
                .remove(&pending_utxo_info.utxo_storage_key);

            ext_nbtc::ext(self.internal_config().nbtc_account_id.clone())
                .with_static_gas(GAS_FOR_BURN_CALL)
                .burn(
                    env::current_account_id(),
                    mint_amount,
                    relayer_account_id,
                    U128(0),
                )
                .detach();

            Promise::new(env::signer_account_id())
                .transfer(self.required_balance_for_safe_deposit())
                .detach();
        }

        Event::VerifyDepositDetails {
            recipient_id: &recipient_id,
            mint_amount,
            protocol_fee: U128(0),
            relayer_account_id: env::signer_account_id(),
            relayer_fee: U128(0),
            success: is_success,
        }
        .emit();
        is_success
    }
