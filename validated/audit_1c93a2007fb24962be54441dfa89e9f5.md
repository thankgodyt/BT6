Audit Report

## Title
Reentrancy in `initTransfer` via Malicious ERC20 Enables Double `InitTransfer` Event Emission and Unauthorized NEAR-Side Token Release — (`File: evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`OmniBridge.initTransfer` makes an external `safeTransferFrom` call to an arbitrary, attacker-supplied ERC20 token address before emitting the `InitTransfer` event, with no reentrancy guard present anywhere in the contract. A malicious ERC20's `transferFrom` can reenter `initTransfer`, causing two `InitTransfer` events (with distinct nonces) to be emitted while zero tokens are actually locked. Because the NEAR side treats every emitted `InitTransfer` event as authoritative proof of locked funds, it will release tokens for both events, enabling the attacker to receive 2× (or more) the tokens they locked.

## Finding Description

`currentOriginNonce` is a `uint64` storage variable declared at line 45. In `initTransfer` (lines 373–437), the execution order is:

1. **Line 381**: `currentOriginNonce += 1;` — nonce incremented to N in storage
2. **Lines 407–411**: `IERC20(tokenAddress).safeTransferFrom(msg.sender, address(this), amount);` — untrusted external call into attacker-controlled contract
3. **Lines 415–425**: `initTransferExtension(...)` — called after external call
4. **Lines 427–436**: `emit BridgeTypes.InitTransfer(...)` — event emitted after external call

The external call at step 2 is reached only when `tokenAddress` is not in `customMinters` and not in `isBridgeToken` — i.e., for any arbitrary ERC20 the attacker deploys. A malicious `transferFrom` implementation can reenter `initTransfer` before step 4 executes. During reentry, `currentOriginNonce` is incremented to N+1, the reentrant call runs to completion (the malicious `transferFrom` returns `true` on the second call without moving tokens), and `InitTransfer` for nonce N+1 is emitted. Control then returns to the outer call, which emits `InitTransfer` for nonce N — even though no tokens were ever transferred.

A grep across all EVM Solidity files confirms there is no `ReentrancyGuard` import or `nonReentrant` modifier anywhere in the codebase. The CLAUDE.md security invariant "State before external calls" is partially satisfied (nonce is incremented before the call) but is insufficient: the event emission — which is the NEAR side's sole proof of token locking — occurs after the external call, violating the "Event–transfer atomicity" invariant stated in CLAUDE.md line 36.

## Impact Explanation

**Critical — Unauthorized minting / escrow mis-accounting.**

CLAUDE.md explicitly states: *"The NEAR side reads this event (via light client or Wormhole) to complete the transfer. Every field needed to reconstruct the transfer must be in the event — it is the only data the NEAR side sees."* Two distinct `InitTransfer` events with valid, unique nonces (N and N+1) will each be independently verified and processed by the NEAR bridge, releasing `amount` tokens per event. With zero tokens actually locked on EVM, the attacker receives 2× `amount` on NEAR backed by nothing. This is direct theft from the NEAR-side liquidity pool or unbacked minting of bridge tokens, matching the critical impact class of unauthorized minting and escrow mis-accounting.

## Likelihood Explanation

**High.** The attack requires only: (1) deploying a malicious ERC20 contract (permissionless, trivial); (2) calling the public `initTransfer` function with no role or privilege required. The vulnerable code path (the `else` branch at lines 406–411) is explicitly the path for arbitrary non-bridge ERC20 tokens, which the bridge is designed to accept. No admin compromise, oracle failure, or external dependency is needed. The attack is repeatable indefinitely.

## Recommendation

Add OpenZeppelin's `ReentrancyGuardUpgradeable` to `OmniBridge` and apply the `nonReentrant` modifier to `initTransfer`, `initTransfer1155`, and `finTransfer`. This is the minimal, robust fix. Alternatively, restructure `initTransfer` to emit `InitTransfer` and call `initTransferExtension` before any external token call (full CEI compliance), though a mutex guard is simpler and less error-prone across all three functions. Note that the storage gap at line 598 (`uint256[49] private __gap`) must be decremented by 1 if a `ReentrancyGuardUpgradeable` storage slot is added.

## Proof of Concept

**Attack contract:**
```solidity
contract MaliciousERC20 {
    IOmniBridge public bridge;
    bool public reentered;

    constructor(address _bridge) { bridge = IOmniBridge(_bridge); }

    function balanceOf(address) external pure returns (uint256) { return 1e30; }
    function allowance(address, address) external pure returns (uint256) { return 1e30; }

    function transferFrom(address, address, uint256 amount) external returns (bool) {
        if (!reentered) {
            reentered = true;
            // Reenter: nonce becomes N+1, emits InitTransfer(N+1), 0 tokens moved
            bridge.initTransfer(address(this), uint128(amount), 0, 0, "attacker.near", "");
        }
        return true; // Outer call: emits InitTransfer(N), 0 tokens moved
    }
}
```

**Attack sequence:**
1. Deploy `MaliciousERC20(bridgeAddress)`
2. Call `bridge.initTransfer(maliciousERC20, 1000, 0, 0, "attacker.near", "")` with `msg.value = 0`
3. `currentOriginNonce` increments to N; `safeTransferFrom` calls `MaliciousERC20.transferFrom`
4. Reentrant call: nonce increments to N+1; inner `transferFrom` returns `true` (no tokens moved); `InitTransfer(sender, maliciousERC20, N+1, 1000, ...)` emitted
5. Outer call resumes: `InitTransfer(sender, maliciousERC20, N, 1000, ...)` emitted
6. Result: two valid `InitTransfer` events on-chain, zero tokens locked; NEAR releases 1000 tokens twice = 2000 tokens stolen

**Verification:** A Foundry test can assert that after the attack, `currentOriginNonce == N+1`, two `InitTransfer` events were emitted with nonces N and N+1, and the bridge's ERC20 balance of `MaliciousERC20` is 0.
