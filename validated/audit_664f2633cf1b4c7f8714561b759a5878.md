### Title
Arithmetic Underflow in `check_withdraw_psbt` Blocks Withdrawals When `max_received_amount < min_change_amount` - (File: contracts/satoshi-bridge/src/psbt.rs)

### Summary
In `contracts/satoshi-bridge/src/psbt.rs`, the function `check_withdraw_psbt` computes `min_received_amount` by subtracting `config.min_change_amount` from `max_received_amount` without a bounds check. When `max_received_amount < config.min_change_amount`, the `u128` subtraction silently wraps around to a value near `u128::MAX`, making the subsequent range check always fail. This permanently blocks any withdrawal whose net payout after fees falls below `min_change_amount`, locking the user's nBTC in the bridge until an operator cancels the pending transaction.

### Finding Description
In `check_withdraw_psbt` (called from `check_withdraw_psbt_valid` during every withdrawal), the contract computes the acceptable output range for the user's received amount:

```rust
// contracts/satoshi-bridge/src/psbt.rs, lines 242-243
let max_received_amount = amount - withdraw_fee - gas_fee;
let min_received_amount = max_received_amount - config.min_change_amount;
```

The comment explains the intent: the relayer is allowed to deduct up to `min_change_amount` from the user's output to avoid dust change outputs. So the user should receive between `max_received_amount - min_change_amount` and `max_received_amount`.

However, when `max_received_amount < config.min_change_amount` (i.e., the net payout after fees is smaller than the dust threshold), the subtraction on line 243 underflows. NEAR contracts are compiled in release mode without overflow checks, so `u128` arithmetic wraps silently. The result is that `min_received_amount` becomes a value near `u128::MAX`.

The subsequent range check then always fails:

```rust
// contracts/satoshi-bridge/src/psbt.rs, lines 244-251
require!(
    actual_received_amount >= min_received_amount   // always false: normal amount < u128::MAX
        && actual_received_amount <= max_received_amount,
    format!(
        "The user's output amount ({}) is out of the valid range ({}, {})",
        actual_received_amount, min_received_amount, max_received_amount
    )
);
```

No valid PSBT can satisfy this condition, so the withdrawal can never be completed.

The condition `max_received_amount < min_change_amount` is reachable because there is no config invariant enforcing:

```
min_withdraw_amount > fee_min + max_btc_gas_fee + min_change_amount
``` [1](#0-0) 

The config validation only checks:

```rust
require!(self.min_change_amount < self.max_change_amount, ...);
require!(self.min_btc_gas_fee < self.max_btc_gas_fee, ...);
``` [2](#0-1) 

There is no constraint relating `min_withdraw_amount`, `min_change_amount`, `fee_min`, and `max_btc_gas_fee` to each other.

### Impact Explanation
When triggered, the user's nBTC has already been transferred to the bridge contract via `ft_transfer_call` and is recorded in a `BTCPendingInfo`. Because every PSBT submitted by the relayer will fail the range check, the withdrawal can never be finalized. The user's nBTC remains locked in the bridge until an operator calls `cancel_withdraw` to initiate an RBF cancellation and return the funds. This constitutes a **stuck bridge state requiring operator intervention**.

**Impact: Medium** — matches "stuck bridge state requiring operator intervention" in the allowed impact scope.

### Likelihood Explanation
The condition is reachable whenever a user withdraws an amount where `amount - withdraw_fee - gas_fee < min_change_amount`. This can occur:
- With a small withdrawal amount close to `min_withdraw_amount` combined with a high gas fee (up to `max_btc_gas_fee`).
- If the operator sets `min_change_amount` to a value that is not carefully coordinated with `min_withdraw_amount` and fee parameters.

No privileged access is required. Any unprivileged user initiating a withdrawal can trigger this condition.

**Likelihood: Medium** — reachable by any bridge user under plausible but non-default config combinations; no special knowledge required beyond knowing the config parameters.

### Recommendation
Replace the plain subtraction with a saturating subtraction to floor `min_received_amount` at zero:

```rust
let min_received_amount = max_received_amount.saturating_sub(config.min_change_amount);
```

Additionally, add a config invariant in `Config::assert_valid` to ensure the minimum withdrawal amount always exceeds the maximum possible fee plus `min_change_amount`:

```rust
require!(
    self.min_withdraw_amount
        > self.deposit_bridge_fee.fee_min
            .max(self.min_withdraw_amount * u128::from(self.withdraw_bridge_fee.fee_rate) / u128::from(MAX_RATIO))
            + self.max_btc_gas_fee
            + self.min_change_amount,
    "min_withdraw_amount too small relative to fees and min_change_amount"
);
```

### Proof of Concept
Assume the following config (all values in satoshis):
- `min_withdraw_amount` = 10,000
- `withdraw_bridge_fee.fee_min` = 1,000, `fee_rate` = 0
- `max_btc_gas_fee` = 8,000
- `min_change_amount` = 2,000

A user withdraws `amount = 10,000`. The relayer constructs a PSBT with `gas_fee = 8,000`:

```
max_received_amount = 10,000 - 1,000 - 8,000 = 1,000
min_received_amount = 1,000 - 2,000
                    = u128::MAX - 999   (wraps around)
```

The check `actual_received_amount >= u128::MAX - 999` is always false for any real output amount. The `require!` panics on every PSBT submission. The user's 10,000 sat worth of nBTC is locked in the bridge. [3](#0-2) [4](#0-3)
