### Title
Incorrect Assumption That `PerasVoteStake` Is Normalized When Checking Peras Quorum — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` in `SupportsPeras.hs` compares a `PerasVoteStake` value directly against the `perasQuorumStakeThreshold` without verifying that both quantities are expressed in the same units. The code itself documents this as an unresolved assumption: `PerasVoteStake` may carry an absolute ledger stake (in Lovelace), while the quorum threshold is a relative fraction. This is the direct analog of the Pendle H-8 bug, where `1 SY token == 1 Yield Token` was assumed without verification.

---

### Finding Description

In `SupportsPeras.hs`, the `PerasVoteStake` newtype is defined with an explicit acknowledgment that its unit is unresolved:

```haskell
-- NOTE: At the moment there is no consensus from researchers/engineers on how
-- we go from the absolute stake of a voter in the ledger to the relative stake
-- of their vote in the voting commitee (given that the quorum is expressed as
-- a relative value of the voting commitee total stake).
newtype PerasVoteStake = PerasVoteStake { unPerasVoteStake :: Rational }
``` [1](#0-0) 

The function `stakeAboveThreshold` then directly compares this value against the quorum threshold:

```haskell
-- TODO: this function assumes that the 'PerasVoteStake' and the quorum
-- threshold used in 'PerasParams' are expressed in the same units. ...
-- this function only makes sense when both values are relative (normalized)
-- values, so we should either normalize the 'PerasVoteStake' before calling
-- this function, or change this function to accept a stake distribution and
-- perform the normalization internally.
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
``` [2](#0-1) 

`stakeAboveThreshold` is called inside `votesReachQuorum`, which is the production quorum gate for Peras certificate creation:

```haskell
votesHaveEnoughStake =
  stakeAboveThreshold cfg totalVoteStake
``` [3](#0-2) 

The `PerasVoteStake` for each vote is sourced from `PerasVoteStakeDistr` via `lookupPerasVoteStake`, and the `ValidatedPerasVote` carries it forward without any normalization step:

```haskell
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
``` [4](#0-3) 

Separately, `implEligiblePartyVoteWeight` in `WFALS.hs` shows that for **persistent** committee members the vote weight is set to the raw `LedgerStake` (absolute Lovelace), not a normalized fraction:

```haskell
WFALSPersistentMember _seatIndex (LedgerStake stake) ->
  VoteWeight stake
``` [5](#0-4) 

The `perasQuorumStakeThreshold` is a relative value (a `Rational` fraction of total stake, e.g. `0.75`). If `PerasVoteStake` is populated with absolute Lovelace values (e.g. `1_000_000`), then `1_000_000 >= 0.75` is trivially true for every single vote, and quorum is always declared reached regardless of actual stake coverage.

---

### Impact Explanation

**Impact class: Critical — Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.**

If `PerasVoteStakeDistr` is populated with absolute ledger stake values (Lovelace), any single vote from any registered stake pool — regardless of how small its stake is — would satisfy `stakeAboveThreshold`. `votesReachQuorum` would return `Just` for a single-vote set, and `forgePerasCert` would produce a valid `ValidatedPerasCert` for an attacker-chosen block. That certificate would then be accepted by the node and used to boost the attacker's block in chain selection, potentially causing honest nodes to prefer a non-canonical chain.

---

### Likelihood Explanation

The bug is reachable by any node that participates in Peras voting. An attacker needs only to operate a registered stake pool (no key compromise, no majority stake required) and send a Peras vote for a target block of their choice. The quorum check is the only gate between a received vote and a forged certificate; if that gate is broken by the unit mismatch, the attack succeeds deterministically. The TODO comment in the production source confirms the assumption is unverified and the normalization step is missing.

---

### Recommendation

1. **Normalize `PerasVoteStake` before comparison.** Before calling `stakeAboveThreshold`, divide each voter's absolute ledger stake by the total active stake in the `PerasVoteStakeDistr` to obtain a relative fraction.
2. **Alternatively**, change `stakeAboveThreshold` to accept the total stake as an additional parameter and perform the division internally, making the unit contract explicit in the type signature.
3. **Enforce the invariant at the type level** by introducing a `NormalizedPerasVoteStake` newtype that can only be constructed via a function that performs the division, preventing future callers from accidentally passing absolute values.

---

### Proof of Concept

**Setup:** A stake pool operator controls pool `P` with 1 ADA (1,000,000 Lovelace) of stake. The `perasQuorumStakeThreshold` is `0.75` (75% of total stake). The `PerasVoteStakeDistr` is populated with absolute Lovelace values.

**Steps:**
1. Pool `P` sends a `PerasVote` targeting an attacker-chosen block `B`.
2. The node calls `validatePerasVote`, which looks up `P`'s stake in `PerasVoteStakeDistr` and returns `ValidatedPerasVote { vpvVoteStake = PerasVoteStake 1_000_000 }`.
3. `votesReachQuorum` accumulates `totalVoteStake = PerasVoteStake 1_000_000`.
4. `stakeAboveThreshold` evaluates `1_000_000 >= 0.75 + safetyMargin` → `True`.
5. `votesReachQuorum` returns `Just ValidatedPerasVotesWithQuorum` for block `B`.
6. `forgePerasCert` produces a `ValidatedPerasCert` boosting `B`.
7. The node accepts the certificate and boosts `B` in chain selection, despite `P` holding only 0.000002% of total stake. [6](#0-5)
