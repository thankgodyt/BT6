### Title
Unsafe Raw-Byte Concatenation in `to_btc_signature` Produces Wrong-Length Compact Signature, Permanently Locking User nBTC - (File: contracts/satoshi-bridge/src/chain_signature.rs)

### Summary
`SignatureResponse::to_btc_signature` concatenates the raw bytes of `r` and `s` using `[r, s].concat()` without first validating that each component is exactly 32 bytes. `bitcoin::secp256k1::ecdsa::Signature::from_compact` strictly requires exactly 64 bytes. When the MPC returns an `s.scalar` hex string shorter than 64 hex characters (i.e., the scalar has leading zero bytes that are omitted), the concatenated slice is fewer than 64 bytes, causing an unconditional panic via `.expect("Invalid signature")` inside `sign_btc_transaction_callback`. Because the callback panics before the `BTCPendingInfo` can advance to `PendingVerify` stage, the withdrawal is permanently stuck in `PendingSign` state and the user's nBTC tokens — already transferred to the bridge — cannot be recovered without operator intervention.

### Finding Description

In `to_btc_signature`:

```rust
// contracts/satoshi-bridge/src/chain_signature.rs L41-49
pub fn to_btc_signature(&self) -> Signature {
    let r_hex = self.big_r.affine_point[2..].to_string(); // strips 1-byte prefix
    let s_hex = self.s.scalar.clone();
    let r = hex::decode(r_hex).expect("Invalid r hex");
    let s = hex::decode(s_hex).expect("Invalid s hex");
    let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&[r, s].concat())
        .expect("Invalid signature");   // panics if len != 64
    Signature::sighash_all(signature)
}
```

`big_r.affine_point` is a hex-encoded compressed secp256k1 point (33 bytes). Stripping the 2-character prefix leaves exactly 32 bytes for `r` — that part is safe. However, `s.scalar` is a hex-encoded big integer. The NEAR chain-signatures MPC contract serialises this as a variable-length hex string: if the scalar's most-significant byte is `0x00`, that byte (and any further leading zeros) is omitted. A scalar with one leading zero byte produces a 31-byte `s`; `[r, s].concat()` then yields 63 bytes, and `from_compact` panics.

The panic propagates out of `sign_btc_transaction_callback`:

```rust

```

Because `to_pending_verify_stage()` is never reached, the `BTCPendingInfo` remains in `PendingSign` state. The `cancel_withdraw` path requires `PendingVerify` state:

```rust
// contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs L37
original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();
```

So the stuck transaction cannot be cancelled through any public path.

### Impact Explanation

When a user initiates a withdrawal via `ft_transfer_call → ft_on_transfer`, their nBTC tokens are immediately transferred to the bridge contract. If the MPC subsequently returns a short `s` scalar and the callback panics, those tokens are locked inside the bridge with no public recovery path. The `BTCPendingInfo` sits in `PendingSign` state indefinitely. Only privileged operator intervention (a manual state-repair upgrade or DAO action) can unblock the funds. This matches **Medium — broken callback rollback / stuck bridge state requiring operator intervention**.

### Likelihood Explanation

The probability that a single secp256k1 scalar `s` has at least one leading zero byte is approximately 1/256 ≈ 0.4 % per signing attempt. For a bridge processing hundreds or thousands of withdrawals this event is statistically certain to occur in production. No attacker action is required; it is a natural property of the MPC output distribution.

### Recommendation

Left-pad both `r` and `s` to exactly 32 bytes before concatenating:

```rust
pub fn to_btc_signature(&self) -> Signature {
    let r_hex = self.big_r.affine_point[2..].to_string();
    let s_hex = self.s.scalar.clone();
    let r_raw = hex::decode(r_hex).expect("Invalid r hex");
    let s_raw = hex::decode(s_hex).expect("Invalid s hex");

    let mut compact = [0u8; 64];
    compact[32 - r_raw.len()..32].copy_from_slice(&r_raw);
    compact[64 - s_raw.len()..64].copy_from_slice(&s_raw);

    let signature = bitcoin::secp256k1::ecdsa::Signature::from_compact(&compact)
        .expect("Invalid signature");
    Signature::sighash_all(signature)
}
```

Also add a `require!(r_raw.len() <= 32 && s_raw.len() <= 32, "Oversized r/s")` guard to reject malformed MPC responses early.

### Proof of Concept

1. User calls `ft_transfer_call(bridge, 1_000_000, withdraw_msg)` — nBTC tokens are transferred to the bridge; `BTCPendingInfo` is created in `PendingSign` state.
2. Relayer calls `sign_btc_transaction(btc_pending_sign_id, 0, key_version)`.
3. Bridge calls MPC `sign(payload, path, key_version)`.
4. MPC returns a `SignatureResponse` where `s.scalar = "00" * 0 + hex(s_value)` with a leading zero byte omitted — e.g., `s.scalar = "aabbcc..."` (31 bytes decoded).
5. `sign_btc_transaction_callback` is invoked; `to_btc_signature` calls `[r(32B), s(31B)].concat()` → 63-byte slice → `from_compact` returns `Err` → `.expect` panics.
6. NEAR reverts all state changes made inside the callback. `BTCPendingInfo` remains in `PendingSign` stage.
7. Relayer retries `sign_btc_transaction`; MPC returns the same (or another short) `s`; callback panics again.
8. `cancel_withdraw` is called but fails: `assert_withdraw_original_pending_verify_tx` panics because state is still `PendingSign`.
9. User's nBTC tokens remain locked in the bridge contract with no public recovery path.
