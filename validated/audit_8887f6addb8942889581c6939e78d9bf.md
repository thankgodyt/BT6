### Title
Chain Selection Bypass via Stale Peras Weight Snapshot in Forecast-Horizon Disconnect Check — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ChainSync/Client.hs`)

---

### Summary

The `checkPreferTheirsOverOurs` guard inside the ChainSync client's forecast-horizon blocking loop unconditionally passes `emptyPerasWeightSnapshot` to `preferAnchoredCandidate` instead of the live Peras weight snapshot held by the ChainDB. When Peras certificates are active, this causes the node to evaluate chain preference using only raw block-count, ignoring certificate-boosted weight. An adversarial peer serving a longer-by-block-count but lighter-by-Peras-weight chain will survive the check, while an honest peer serving a shorter-by-block-count but heavier-by-Peras-weight chain will be incorrectly disconnected with `CandidateTooSparse`. The node then selects the adversary's non-canonical chain.

---

### Finding Description

When the ChainSync client receives a header whose slot is beyond the current forecast horizon, it enters a blocking STM `retry` loop in `readLedgerStateHelper`, waiting for the local selection to advance far enough to produce a `LedgerView` for that slot. On every iteration of the retry, before calling `retry`, it calls `checkPreferTheirsOverOurs` to decide whether the peer's candidate is still worth waiting for:

```haskell
-- Client.hs lines 1814–1817
case prj lst of
  Nothing -> do
    checkPreferTheirsOverOurs kis'
    retry
```

`checkPreferTheirsOverOurs` calls `preferAnchoredCandidate` with a **hardcoded** `emptyPerasWeightSnapshot`:

```haskell
-- Client.hs lines 1834–1851
checkPreferTheirsOverOurs kis
  | shouldSwitch $
      preferAnchoredCandidate
        (configBlock cfg)
        -- TODO: remove this entire check, see https://github.com/tweag/cardano-peras/issues/64
        emptyPerasWeightSnapshot   -- ← always empty, never the live snapshot
        ourFrag
        theirFrag =
      pure ()
  | otherwise =
      throwSTM $
        CandidateTooSparse
          mostRecentIntersection
          (ourTipFromChain ourFrag)
          (theirTipFromChain theirFrag)
``` [1](#0-0) 

`preferAnchoredCandidate` short-circuits to pure block-number comparison when the weight snapshot is empty:

```haskell
-- AnchoredFragment.hs lines 186–203
preferAnchoredCandidate cfg weights ours cand
  | isEmptyPerasWeightSnapshot weights =
      assertWithMsg (precondition ours cand) $
        case (ours, cand) of
          ...
          (_ :> ourTip, _ :> theirTip) ->
            case preferCandidate
              (projectChainOrderConfig cfg)
              (selectView cfg (getHeader1 ourTip))
              (selectView cfg (getHeader1 theirTip)) of ...
``` [2](#0-1) 

The live Peras weight snapshot is available from `ChainDB.getPerasWeightSnapshot` and is used correctly everywhere else in chain selection (e.g., `constructPreferableCandidates`, `chainSelection`): [3](#0-2) 

The discrepancy means the disconnect guard and the actual chain selection engine use different comparison semantics when Peras certificates are present.

---

### Impact Explanation

In a Peras-enabled network, a block can be boosted by a Peras certificate, making a shorter-by-block-count chain heavier-by-weight and therefore the canonical chain. The attack proceeds as follows:

1. **Honest peer** serves the canonical chain: it has Peras certificate boosts, making it heavier by weight, but it is shorter by raw block count than the adversary's chain. Its tip header is beyond the victim node's current forecast horizon.
2. **Adversarial peer** serves a non-canonical chain: longer by block count, no Peras certificate boosts, lighter by weight.
3. When the victim node processes the honest peer's beyond-horizon header, `checkPreferTheirsOverOurs` evaluates `preferAnchoredCandidate ... emptyPerasWeightSnapshot ourFrag honestFrag`. Because the honest chain is shorter by block count, this returns `ShouldNotSwitch`, and the node throws `CandidateTooSparse`, **disconnecting from the honest peer**.
4. The adversarial peer's chain is longer by block count, so it passes the same check and the connection is maintained.
5. The node eventually selects the adversary's non-canonical, lighter-by-Peras-weight chain.

This is a **chain selection safety failure**: an unprivileged peer can cause an honest node to prefer a non-canonical chain by exploiting the stale weight snapshot in the forecast-horizon guard.

---

### Likelihood Explanation

- **Entry path**: Fully reachable by any unprivileged peer via the standard ChainSync mini-protocol (`MsgRollForward`). No special privileges, keys, or stake are required.
- **Trigger condition**: The peer's header must be beyond the local forecast horizon. This is a normal occurrence during syncing and at epoch boundaries.
- **Peras dependency**: The bug is latent until Peras certificates are actively issued on the network. Once Peras is live, the condition is realistic: an adversary with any stake can produce a longer-by-block-count fork without certificates, while the honest chain accumulates certificate boosts.
- **Known to developers**: The `TODO` comment at line 1841 explicitly references `https://github.com/tweag/cardano-peras/issues/64` and notes the check should be removed, confirming the developers are aware the current code is incorrect for the Peras case. [4](#0-3) 

---

### Recommendation

Replace the hardcoded `emptyPerasWeightSnapshot` in `checkPreferTheirsOverOurs` with the live Peras weight snapshot read from the ChainDB (the same snapshot used by `constructPreferableCandidates` and `chainSelection`). Concretely, thread `getPerasWeightSnapshot` from `ChainDbView` into `checkPreferTheirsOverOurs` and pass the result to `preferAnchoredCandidate`. Alternatively, as the TODO suggests, remove the `checkPreferTheirsOverOurs` check entirely and rely solely on the GDD and LoP to disconnect from non-canonical peers, which avoids the weight-comparison problem altogether.

---

### Proof of Concept

The following scenario can be reproduced in the existing peer-simulator test framework (`Test.Consensus.PeerSimulator`):

1. Configure a two-peer setup with Peras active and certificates being issued on the honest chain.
2. Peer A (honest): serves the canonical chain — shorter by block count, heavier by Peras certificate weight. Its tip slot is beyond the victim node's forecast horizon.
3. Peer B (adversary): serves a fork — longer by block count, no Peras certificates, lighter by weight.
4. Observe that when the victim node processes Peer A's beyond-horizon header, `checkPreferTheirsOverOurs` fires with `emptyPerasWeightSnapshot`. Since Peer A's chain is shorter by block count, `preferAnchoredCandidate` returns `ShouldNotSwitch`, and the node throws `CandidateTooSparse`, disconnecting from Peer A.
5. The node remains connected to Peer B and ultimately selects Peer B's non-canonical chain.
