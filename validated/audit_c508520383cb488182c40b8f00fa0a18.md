### Title
Peras Quorum Check Bypassed by Unit Mismatch in `stakeAboveThreshold` — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

`stakeAboveThreshold` compares a `PerasVoteStake` value directly against a relative quorum threshold without enforcing that both operands are in the same unit (relative vs. absolute). The function's own TODO comment acknowledges this assumption is unverified. If `PerasVoteStake` carries an absolute ledger stake value (e.g., raw lovelace) while the quorum threshold is a relative fraction (e.g., `0.75`), the comparison `stake >= quorumThreshold + safetyMargin` trivially evaluates to `True` for any pool with non-trivial absolute stake. This allows a single vote from any pool to forge a Peras certificate without the required quorum, bypassing the core Peras voting security invariant.

---

### Finding Description

`stakeAboveThreshold` is the sole gate that decides whether accumulated votes have reached quorum:

```haskell
stakeAboveThreshold :: PerasParams -> PerasVoteStake -> Bool
stakeAboveThreshold params voteStake =
  stake >= quorumThreshold + safetyMargin
 where
  stake      = unPerasVoteStake voteStake
  quorumThreshold = unPerasQuorumStakeThreshold (perasQuorumStakeThreshold params)
  safetyMargin    = unPerasQuorumStakeThresholdSafetyMargin (perasQuorumStakeThresholdSafetyMargin params)
```

The function's own documentation explicitly flags the unit mismatch:

> **TODO**: this function assumes that the `PerasVoteStake` and the quorum threshold used in `PerasParams` are expressed in the same units … Under the current implementation of `PerasParams`, this function only makes sense when both values are relative (normalized) values, **so we should either normalize the `PerasVoteStake` before calling this function, or change this function to accept a stake distribution and perform the normalization internally.** [1](#0-0) 

The phrasing "we should … normalize … before calling this function" confirms that normalization is **not** currently performed at the call site. `PerasVoteStake` is a bare `Rational` newtype with no unit enforcement: [2](#0-1) 

`stakeAboveThreshold` is called inside `votesReachQuorum`, which is the only guard before `forgePerasCert` is invoked:

```haskell
votesHaveEnoughStake = stakeAboveThreshold cfg totalVoteStake
``` [3](#0-2) 

`votesReachQuorum` is called from `updateCandidateVoteState`, which triggers certificate forging:

```haskell
case votesReachQuorum cfg voteList of
  Just votesWithQuorum -> do
    cert <- forgePerasCert cfg votesWithQuorum
    pure $ BecameWinner (PerasTargetVoteWinner newVoteTally cert)
``` [4](#0-3) 

The `ExtWFAStakeDistr` used by the `EveryoneVotes` committee stores raw `LedgerStake` (absolute lovelace-scale integers) alongside cumulative stake: [5](#0-4) 

If the absolute `LedgerStake` value (e.g., `1_000_000`) flows into `vpvVoteStake` without normalization, the comparison `1_000_000 >= 0.75 + 0` is trivially `True`, and a single vote from any pool with non-trivial stake forges a certificate.

---

### Impact Explanation

**Critical — Bypass of Peras certificate/vote quorum check enabling unauthorized certificate acceptance.**

A single vote from any pool with non-trivial absolute stake would satisfy `stakeAboveThreshold`, causing `votesReachQuorum` to return `Just` and `forgePerasCert` to be called immediately. The resulting `ValidatedPerasCert` is stored in the `PerasVoteDB` and applied to chain selection as a Peras boost. An adversary can therefore:

1. Cast a single vote for an adversarially chosen block.
2. Have the node immediately forge a certificate for that block.
3. The certificate applies a `PerasWeight` boost to that block in chain selection, causing honest nodes to prefer the adversary's block over the canonical chain.

This directly undermines the Peras protocol's safety guarantee that a certificate requires >75% of stake to be forged.

---

### Likelihood Explanation

Any pool operator (no stake majority required) who can submit a valid signed vote to a node triggers this path. The vote is validated cryptographically first (`validatePerasVote`), so the attacker must be a legitimate registered pool, but no threshold of stake is needed. The entry path is the standard Peras vote diffusion miniprotocol, reachable by any peer.

---

### Recommendation

Normalize `PerasVoteStake` to a relative value (dividing by total committee stake) before passing it to `stakeAboveThreshold`, or change `stakeAboveThreshold` to accept the total stake distribution and perform normalization internally. Add a type-level or runtime invariant that `PerasVoteStake` is always in `[0, 1]` before any quorum comparison. The TODO comment at line 155–161 already identifies the exact fix needed. [6](#0-5) 

---

### Proof of Concept

```
Assume:
  perasQuorumStakeThreshold params = 0.75   -- relative, as documented
  perasQuorumStakeThresholdSafetyMargin params = 0.0

Attacker (pool with 1,000,000 lovelace absolute stake) submits one vote.
  vpvVoteStake = PerasVoteStake 1000000   -- absolute, not normalized

stakeAboveThreshold params (PerasVoteStake 1000000)
  = 1000000 >= 0.75 + 0.0
  = True   ← quorum declared with a single vote

votesReachQuorum returns Just votesWithQuorum
  → forgePerasCert is called
  → ValidatedPerasCert is stored and applied as a chain-selection boost
  → Peras quorum invariant violated; attacker's block is preferred
```
