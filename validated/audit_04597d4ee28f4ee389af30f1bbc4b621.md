Audit Report

## Title
Missing `chain_id` in `MetadataPayload::to_borsh()` Enables Cross-Chain Replay of `deploy_token` MPC Signatures — (`starknet/src/bridge_types.cairo`, `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary
`MetadataPayloadTrait::to_borsh()` serializes the `deploy_token` signed payload without any chain identifier, while `TransferMessagePayloadTrait::to_borsh(chain_id)` correctly binds its payload to the destination chain. Because `_verify_borsh_signature` checks only that the ECDSA signature was produced by `omni_bridge_derived_address` — a value shared across deployments using the same MPC key — a valid MPC-signed `deploy_token` payload from one chain (e.g., testnet) is cryptographically identical and accepted verbatim on any other chain sharing the same derived address (e.g., mainnet). The same omission is present in the EVM `deployToken` implementation, confirming a systemic domain-separation flaw.

## Finding Description
`MetadataPayloadTrait::to_borsh()` encodes exactly five fields with no chain context: [1](#0-0) 

By contrast, `TransferMessagePayloadTrait::to_borsh(chain_id)` receives the chain identifier as an explicit parameter and embeds it in the serialized payload: [2](#0-1) 

In `deploy_token`, the borsh bytes are passed to `_verify_borsh_signature` with no chain context: [3](#0-2) 

In `fin_transfer`, the chain id is correctly injected: [4](#0-3) 

`_verify_borsh_signature` verifies the ECDSA signature against `omni_bridge_derived_address`, which is the same Ethereum-style address on every deployment sharing the same MPC key path: [5](#0-4) 

The storage layout confirms both `omni_bridge_chain_id` and `omni_bridge_derived_address` are independent per-deployment values, but only `omni_bridge_derived_address` participates in `deploy_token` signature verification: [6](#0-5) 

The same omission exists in the EVM `deployToken` implementation: [7](#0-6) 

**Exploit flow:**
1. Attacker observes a valid `deploy_token` transaction on testnet (chain_id `0x10`) — the signed borsh bytes contain no chain identifier.
2. Attacker submits the identical `(signature, payload)` tuple to the mainnet contract (chain_id `0x11`) sharing the same `omni_bridge_derived_address`.
3. `_verify_borsh_signature` passes — the signed bytes are chain-agnostic.
4. `ERR_TOKEN_ALREADY_DEPLOYED` check passes if the token has not yet been deployed on mainnet.
5. A bridge token contract is deployed and registered in `near_to_starknet_token` / `starknet_to_near_token`. [8](#0-7) 

There is no mechanism to remove a deployed token, so the legitimate mainnet deployment of the same NEAR token ID is permanently blocked by `ERR_TOKEN_ALREADY_DEPLOYED`.

## Impact Explanation
This is a **Critical** chain/domain separation flaw. An attacker can deploy a bridge token on mainnet without the MPC cluster having authorized it for mainnet. The legitimate mainnet deployment of the same NEAR token ID is permanently blocked with no admin recovery path visible in the contract. Any subsequent valid mainnet `fin_transfer` (obtained by initiating a real NEAR-side lock) will mint against this attacker-front-run token contract. This matches the allowed critical impact: *cross-chain replay / chain/domain separation flaw enabling unauthorized bridge actions and invalid finalization*.

## Likelihood Explanation
The precondition — same `omni_bridge_derived_address` across testnet and mainnet — is the standard operational model for MPC-based bridges: the derived address is deterministic from the MPC key and derivation path, and the same protocol-level key is routinely used across environments. Testnet `deploy_token` transactions are observable on-chain. No privileged access, key compromise, or threshold collusion is required. The attacker only needs to observe a valid testnet `deploy_token` transaction and replay it on mainnet before the legitimate deployment occurs.

## Recommendation
Add `chain_id` to `MetadataPayload::to_borsh()`, mirroring the pattern already used in `TransferMessagePayloadTrait::to_borsh`:

```cairo
fn to_borsh(self: @MetadataPayload, chain_id: u8) -> ByteArray {
    let mut borsh_bytes: ByteArray = Default::default();
    borsh_bytes.append_byte(PayloadType::Metadata.into());
    borsh_bytes.append_byte(chain_id);  // <-- add this
    borsh_bytes.append(@borsh::encode_byte_array(self.token));
    borsh_bytes.append(@borsh::encode_byte_array(self.name));
    borsh_bytes.append(@borsh::encode_byte_array(self.symbol));
    borsh_bytes.append_byte(*self.decimals);
    borsh_bytes
}
```

Update `deploy_token` to pass `self.omni_bridge_chain_id.read()`. Apply the equivalent fix to the EVM `deployToken` borsh encoding in `OmniBridge.sol`. All existing MPC-signed `deploy_token` messages must be re-signed after the fix.

## Proof of Concept
```cairo
// 1. Deploy two OmniBridge instances with different chain_ids but the same derived address.
let (bridge_a, _) = deploy_bridge_with(derived_addr, chain_id_a); // testnet (0x10)
let (bridge_b, _) = deploy_bridge_with(derived_addr, chain_id_b); // mainnet (0x11)

// 2. Obtain a valid deploy_token signature for bridge_a (testnet).
let payload = MetadataPayload { token: "token.near", name: "T", symbol: "T", decimals: 18 };
let sig = sign_for_bridge_a(@payload); // MPC signs chain-agnostic borsh bytes

// 3. Replay the identical (sig, payload) on bridge_b (mainnet).
bridge_b.deploy_token(sig, payload); // succeeds — no chain_id in signed bytes

// 4. Assert the token is now registered on mainnet without mainnet MPC authorization.
assert(!bridge_b.get_token_address("token.near").is_zero());

// 5. Legitimate mainnet deployment is now permanently blocked.
let mainnet_sig = sign_for_bridge_b(@payload);
bridge_b.deploy_token(mainnet_sig, payload); // panics: ERR_TOKEN_ALREADY_DEPLOYED
```
