Audit Report

## Title
Missing `burn_tokens_if_needed` in `resolve_utxo_fin_transfer` Causes Permanent Token Supply Inflation — (File: near/omni-bridge/src/lib.rs)

## Summary

`resolve_utxo_fin_transfer` omits the `burn_tokens_if_needed` call that its structural counterpart `resolve_fast_transfer` performs. When the UTXO-chain token is a deployed bridge token, `send_tokens` mints new tokens to the recipient while the tokens deposited by the UTXO connector via `ft_transfer_call` remain permanently in the bridge's balance, unburned. This inflates the on-chain token supply by `amount` on every successful UTXO → NEAR finalization.

## Finding Description

`resolve_fast_transfer` (L895–912) explicitly calls `self.burn_tokens_if_needed(token_id.clone(), amount)` with the comment *"Burn the tokens to ensure the locked tokens are not double-minted"* before handling the refund/success branch. [1](#0-0) 

`resolve_utxo_fin_transfer` (L1016–1044) is the structurally identical callback for the UTXO finalization path. It handles the same two branches (refund or success log) but contains **no call to `burn_tokens_if_needed`**. [2](#0-1) 

The call chain is:

```
utxo_fin_transfer_to_near_callback
  └─ send_tokens → mint(recipient, amount)   [for deployed tokens]
       └─ resolve_utxo_fin_transfer           [no burn here]
```

`utxo_fin_transfer_to_near_callback` calls `send_tokens`, which for a deployed bridge token mints `amount` new tokens to the recipient. [3](#0-2) 

After the mint resolves, `resolve_utxo_fin_transfer` is invoked. In the success branch it only emits a log and returns `U128(0)` — no burn is issued. [4](#0-3) 

`burn_tokens_if_needed` burns from the bridge's own balance via the token's `burn` entry-point, which withdraws from `predecessor_account_id` (the bridge contract). [5](#0-4) 

Because the burn is never called, the `amount` of tokens the UTXO connector deposited into the bridge via `ft_transfer_call` remain in the bridge's balance permanently, while an equal `amount` of freshly minted tokens now exist in the recipient's account. Total supply grows by `amount` per transfer.

## Impact Explanation

Every successful UTXO → NEAR finalization where the token is a deployed bridge token (e.g., BTC, ZEC) permanently inflates the circulating supply by `amount`. The bridge accumulates a growing balance of tokens that represent unbacked supply, breaking the 1:1 peg between locked UTXO-chain assets and NEAR-side tokens. This constitutes **escrow mis-accounting and unauthorized token minting** — a concrete match for the Critical impact class: *"Balance manipulation, escrow mis-accounting… that changes user or protocol balances"* and *"Stealing, loss, double-spending, unauthorized minting… of bridged funds."*

## Likelihood Explanation

No special privilege is required. Any user who sends BTC or ZEC on the origin chain causes the trusted UTXO connector to call `ft_transfer_call` on the bridge, which triggers the full flow. The bug fires on every successful UTXO → NEAR transfer where the token is deployed, making it continuously and automatically exploitable at scale through normal bridge usage.

## Recommendation

Add `self.burn_tokens_if_needed(token_id.clone(), amount)` at the top of `resolve_utxo_fin_transfer`, mirroring `resolve_fast_transfer`:

```rust
pub fn resolve_utxo_fin_transfer(...) -> U128 {
    let is_ft_transfer_call = !utxo_fin_transfer_msg.msg.is_empty();
    // Burn the tokens received from the connector to prevent supply inflation
    self.burn_tokens_if_needed(token_id.clone(), amount);
    if Self::is_refund_required(is_ft_transfer_call) {
        self.remove_fin_utxo_transfer(
            &utxo_fin_transfer_msg.get_transfer_id(origin_chain),
            storage_owner,
        );
        amount
    } else {
        env::log_str(...);
        U128(0)
    }
}
```

## Proof of Concept

1. Admin calls `deploy_native_token(ChainKind::Btc, "Bitcoin", "BTC", 8)` — BTC token is inserted into `deployed_tokens`.
2. Admin calls `add_utxo_chain_connector(ChainKind::Btc, connector_id, btc_token_id, 8)`.
3. User sends 1 BTC on Bitcoin. The UTXO connector calls `ft_transfer_call(bridge, 100_000_000, ..., UtxoFinTransfer{recipient: Near("alice")})`.
4. Bridge receives 100_000_000 satoshi-units of BTC token via `ft_transfer_call`.
5. `utxo_fin_transfer_to_near_callback` → `send_tokens` → `mint(alice, 100_000_000)` — 100_000_000 new tokens minted to Alice.
6. `resolve_utxo_fin_transfer` returns `U128(0)` — bridge retains 100_000_000 BTC tokens that are never burned.
7. BTC token total supply is inflated by 100_000_000 per transfer. Repeating N times inflates supply by N × amount, unbacked by any locked BTC on-chain.

A local integration test can assert `ft_total_supply` before and after a simulated UTXO fin transfer and observe the supply grows by `amount` rather than remaining constant.
