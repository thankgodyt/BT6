### Title
Peras `validatePerasCert` Stub Unconditionally Accepts Any Certificate, Enabling Unauthorized Chain-Weight Manipulation — (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance ships a stub `validatePerasCert` that always returns `Right` — accepting every `PerasCert` without any cryptographic or structural check. Because validated certificates are fed directly into the `PerasWeightSnapshot` that drives Peras-aware chain selection, an unprivileged peer that can deliver a crafted certificate object causes the receiving node to apply an illegitimate weight boost to an arbitrary block, potentially making a non-canonical chain appear heavier than the honest chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  validatePerasCert params cert =
    Right
      ValidatedPerasCert
        { vpcCert = cert
        , vpcCertBoost = perasWeight params   -- always 15 by default
        }
``` [1](#0-0) 

This is the **only** `BlockSupportsPeras` instance in the repository (it is an overlapping catch-all for every `StandardHash blk`). No concrete per-era override exists. Every `PerasCert` presented to the node — regardless of its round number, boosted-block point, or cryptographic authenticity — is unconditionally promoted to a `ValidatedPerasCert` carrying the full `perasWeight` boost.

**Downstream chain-selection path:**

1. `validatePerasCert` → `ValidatedPerasCert { vpcCertBoost = perasWeight params }` [2](#0-1) 
2. Validated cert is stored in `PerasCertDB` and exposed as a `PerasWeightSnapshot`. [3](#0-2) 
3. `weightedSelectView` builds a `WeightedSelectView` whose `wsvWeightBoost` is drawn from that snapshot. [4](#0-3) 
4. `wsvTotalWeight` adds `BlockNo` and `wsvWeightBoost`; `preferCandidate` switches to the heavier chain. [5](#0-4) 

**Companion stub that widens the attack surface:**

`getPerasCertInBlock _ = Nothing` means the node never extracts a cert from a block body, so the only source of certs is the Peras object-diffusion miniprotocol — exactly the channel an adversarial peer controls. [6](#0-5) 

**`PerasCooldownRounds` — direct structural analog to `setCoolDownInSecs()`:**

`PerasCooldownRounds` is a raw `Word64` with no lower or upper bound enforced anywhere in `mkPerasParams` or `PerasParams`. It is consumed as the modulus `_K` in `perasVR2B`:

```haskell
_K = PerasRoundNo $ unPerasCooldownRounds $ perasCooldownRounds $ perasParams
...
(currRoundNo `rmod` _K) :==: (getPerasCertRound (lcocCert cert) `rmod` _K)
``` [7](#0-6) [8](#0-7) 

`_K = 0` triggers a Haskell `divMod`-by-zero exception (DoS, disqualified on its own). However, the absence of any positive-nonzero guard means the parameter is structurally unbounded — the same class of defect as the reported `setCoolDownInSecs()` — and the certificate-validation bypass above is the exploitable consequence when the parameter bundle is accepted without integrity checks.

---

### Impact Explanation

When Peras is enabled, an adversarial peer delivers one or more crafted `PerasCert` objects (each referencing a block on a minority fork) via the Peras diffusion channel. Because `validatePerasCert` never rejects them, each cert adds `perasWeight` (default 15) to the target block's `PerasWeightSnapshot` entry. After enough forged certs, `wsvTotalWeight` of the adversarial fragment exceeds that of the honest chain, and `preferCandidate` returns `ShouldSwitch`, causing the node to adopt the non-canonical chain. This is a **chain-selection safety failure** driven entirely by forged, unvalidated certificates — matching the "Bypass of Peras certificate checks that enables unauthorized certificate acceptance" criterion.

---

### Likelihood Explanation

Peras is gated behind a feature flag and disabled by default on mainnet. However, the code is production-quality (not test-only), Peras is under active integration, and the attack requires only that a peer be able to send a `PerasCert` message — no stake, no keys, no admin access. On any private testnet or staging environment where Peras is enabled, the attack is trivially reproducible.

---

### Recommendation

1. **Remove the degenerate catch-all instance** or replace the stub body with an explicit `error`/`Left` that rejects all certificates until a real implementation exists, preventing silent acceptance.
2. **Add a `PerasCooldownRounds > 0` guard** (and analogous guards for `PerasRoundLength`, `PerasIgnoranceRounds`) inside `mkPerasParams` or at the point of deserialization, mirroring the recommendation in the external report to add `require` checks for the cooldown parameter.
3. **Gate `PerasCertDB` insertion** on a runtime check that Peras is fully configured with a validated `BlockSupportsPeras` instance before accepting any certificate from the network.

### Proof of Concept

```
Private testnet, Peras enabled:

1. Adversary connects as a normal peer.
2. Adversary constructs PerasCert { pcCertRound = r, pcCertBoostedBlock = adversarialPoint }
   for a block on a minority fork.
3. Adversary sends the cert via the Peras object-diffusion miniprotocol.
4. Victim node calls validatePerasCert params cert
   → always returns Right ValidatedPerasCert { vpcCertBoost = PerasWeight 15 }
5. Cert is stored in PerasCertDB; PerasWeightSnapshot updated.
6. weightedSelectView computes wsvTotalWeight(adversarial) > wsvTotalWeight(honest).
7. preferCandidate returns ShouldSwitch; victim adopts the adversarial chain.
```

The only precondition is that the victim has Peras enabled — no cryptographic material, no stake, and no operator interaction is required from the attacker.
