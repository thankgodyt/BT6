### Title
Peras Certificate Verification Stub Unconditionally Accepts Any Peer-Supplied Certificate, Enabling Unauthorized Chain-Selection Boost — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The sole production instance of `BlockSupportsPeras` implements `validatePerasCert` as a stub that unconditionally returns `Right` for every certificate it receives, assigning it the full configured Peras weight boost without performing any cryptographic or quorum verification. Because the Peras certificate diffusion miniprotocol is open to any peer, an unprivileged attacker can craft a `PerasCert` pointing to any block on a minority fork, have it accepted without verification, and cause the receiving node's chain-selection logic to prefer that fork over the canonical chain.

---

### Finding Description

`validatePerasCert` in the universal `instance StandardHash blk => BlockSupportsPeras blk` is a placeholder:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This is the **only** instance of `BlockSupportsPeras` (it covers all `StandardHash blk`), so every production code path that calls `validatePerasCert` goes through this stub. [2](#0-1) 

The production inbound certificate handler `makePerasCertPoolWriterFromChainDB` calls `validatePerasCert mkPerasParams` directly on every certificate received from a peer:

```haskell
(validatePerasCert mkPerasParams)
-- TODO replace when actual plumbing is in place
``` [3](#0-2) 

`processCerts` then passes every cert that clears this non-check to `ChainDB.addPerasCertAsync`: [4](#0-3) 

`chainSelSync` in `ChainSel.hs` then triggers a full chain-selection pass for the block named in the certificate: [5](#0-4) 

Chain selection uses `WeightedSelectView`, which adds `wsvWeightBoost` (derived from `vpcCertBoost`) to the block count when comparing forks: [6](#0-5) 

A second structural issue compounds this: `PerasCertDB` stores at most one certificate per round (keyed by `PerasRoundNo`). Certificates whose round is already present are silently dropped: [7](#0-6) 

This means an attacker who submits a fraudulent certificate for round R first permanently blocks the legitimate certificate for that round from ever being stored or applied.

The miniprotocol handler is wired unconditionally in `mkHandlers` for every node-to-node connection: [8](#0-7)

### Impact Explanation

**High — Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain.**

An attacker with a network connection to the victim node can:

1. Craft a `PerasCert { pcCertRound = R, pcCertBoostedBlock = <fork tip> }` for any block on a minority fork.
2. Send it via the `PerasCertDiffusion` miniprotocol before the legitimate certificate for round R arrives.
3. The stub accepts it unconditionally, assigns it the full `perasWeight` boost, and stores it as the authoritative certificate for round R.
4. Chain selection now computes the fork's total weight as `blockNo + perasWeight`, which can exceed the canonical chain's weight.
5. The node switches to the attacker's fork. The legitimate certificate for round R is subsequently ignored (already in DB).

No stake, no VRF key, no KES key, and no quorum of votes is required. The entire Peras certificate quorum requirement — the mechanism that is supposed to make certified blocks resistant to rollback — is bypassed.

---

### Likelihood Explanation

**Medium.** The `PerasCertDiffusion` miniprotocol is active on every node-to-node connection. Any peer (including an adversarial one) can send certificates. The only prerequisite is knowing a valid block hash on a fork the attacker wants to promote, which is publicly observable from the chain-sync protocol. The attack requires no privileged access and no cryptographic material.

---

### Recommendation

Replace the stub with a real implementation of `validatePerasCert` that verifies:

1. The aggregate signature over the certificate covers the claimed `pcCertBoostedBlock` and `pcCertRound`.
2. The signers collectively hold stake exceeding the configured quorum threshold.
3. Each signer was a legitimate committee member for that round (per the committee selection scheme).

Until the real implementation is in place, consider rejecting all inbound certificates at the miniprotocol boundary (returning a validation error for every cert) rather than accepting them unconditionally, to prevent the chain-selection manipulation described above.

---

### Proof of Concept

```
Attacker node A connects to honest node V via PerasCertDiffusion.

1. A observes that V's canonical chain tip is at block C (round R already passed).
2. A also knows of a minority-fork block F at the same height as C.
3. A sends:
     PerasCert { pcCertRound = R, pcCertBoostedBlock = BlockPoint slotF hashF }
4. V calls:
     validatePerasCert mkPerasParams cert
   → always returns Right (ValidatedPerasCert { vpcCertBoost = perasWeight })
5. V stores the cert in PerasCertDB for round R.
6. chainSelSync triggers chainSelectionForBlock for F.
7. WeightedSelectView computes:
     weight(F-chain) = blockNo(F) + perasWeight   -- e.g. 100 + 1000 = 1100
     weight(C-chain) = blockNo(C) + 0             -- e.g. 100 + 0    = 100
8. V switches to the attacker's fork F.
9. Any subsequent legitimate cert for round R is silently dropped
   (PerasCertAlreadyInDB).
```

processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
