### Title
Attacker Can Redirect Any User's BTC Refund to an Arbitrary Address via `request_refund` - (File: `contracts/satoshi-bridge/src/api/bridge.rs`, `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`request_refund` is a permissionless function that accepts a caller-supplied `refund_address`. When the original `DepositMsg` was created without a `refund_address` (i.e., `deposit_msg.refund_address == None`), the contract performs no ownership check and stores whatever BTC address the caller provides. An attacker who observes a victim's unfinalized deposit on Bitcoin can front-run the victim's own refund request, locking in the attacker's BTC address as the refund destination and causing the victim's BTC to be sent to the attacker.

---

### Finding Description

`request_refund` in `bridge.rs` is callable by any NEAR account (it carries `#[payable]` and `#[pause]` but **no** `#[trusted_relayer]` guard on the function itself): [1](#0-0) 

It delegates to `internal_request_refund`, which contains the only address-validation logic:

```rust
if let Some(msg_refund_address) = &deposit_msg.refund_address {
    require!(
        msg_refund_address == &refund_address,
        "refund_address does not match deposit_msg.refund_address"
    );
}
``` [2](#0-1) 

When `deposit_msg.refund_address` is `None` the branch is skipped entirely, so the caller-supplied `refund_address` is stored verbatim with no verification that the caller is the intended beneficiary.

After the request is stored, a duplicate-request guard prevents the victim from submitting their own request for the same UTXO:

```rust
require!(
    !self.data().refund_requests.contains_key(&utxo_storage_key),
    "Refund request already exists for this UTXO"
);
``` [3](#0-2) 

The victim is then permanently locked out. Only DAO/Operator can reject the attacker's request via `reject_refund`: [4](#0-3) 

After `unsafe_refund_timelock_sec` elapses, `execute_refund` (also permissionless) can be called by anyone to finalize the refund to the attacker's address: [5](#0-4) 

---

### Impact Explanation

The victim's BTC is sent to the attacker's BTC address instead of the victim's. The victim has no on-chain recourse once the attacker's request is stored — they cannot overwrite it, and `reject_refund` is restricted to DAO/Operator. This constitutes a **direct theft of user funds** (the full deposit minus the gas fee). Matches: *Critical — Significant loss, theft, or destruction of user funds.*

---

### Likelihood Explanation

- `DepositMsg` is public information: it is passed to `get_user_deposit_address` and shared with relayers; the Bitcoin transaction itself is on-chain.
- `request_refund` requires only an attached NEAR storage deposit (a few NEAR), which is trivially affordable.
- The attack window opens whenever a deposit is unfinalized (relayer downtime, invalid deposit, network congestion) — a realistic and recurring condition.
- The only mitigation is DAO/Operator monitoring and manual rejection within `unsafe_refund_timelock_sec`. If operators are offline or slow, the theft completes automatically.

Likelihood: **Medium-High**.

---

### Recommendation

Bind the refund destination to the original depositor. The simplest fix is to require the caller of `request_refund` to be the `deposit_msg.recipient_id` when `deposit_msg.refund_address` is `None`:

```rust
if deposit_msg.refund_address.is_none() {
    require!(
        env::predecessor_account_id() == deposit_msg.recipient_id,
        "Only the deposit recipient may set refund_address when none is pre-authorized"
    );
}
```

Alternatively, disallow permissionless refund requests entirely when `deposit_msg.refund_address` is `None`, restricting them to DAO/Operator only (matching the existing `unsafe_refund_timelock_sec` intent).

---

### Proof of Concept

1. **Alice** creates `DepositMsg { recipient_id: "alice.near", refund_address: None, … }`, derives the deposit address via `get_user_deposit_address`, and sends 1 BTC to it.
2. The relayer is temporarily offline; the deposit is never finalized via `verify_deposit`.
3. **Bob** (attacker) observes Alice's BTC transaction on-chain and reconstructs her `DepositMsg` (public, shared with the relayer).
4. Bob calls:
   ```
   request_refund(
       deposit_msg  = alice_deposit_msg,   // refund_address field = None
       refund_address = "bob_btc_address",
       tx_bytes     = alice_tx_bytes,
       vout         = 0,
       proof        = <valid SPV proof>,
       gas_fee      = None,
   )
   ```
   with the required NEAR storage deposit attached.
5. The contract stores `RefundRequest { refund_address: "bob_btc_address", … }`.
6. Alice calls `request_refund` with her own BTC address → **reverts**: `"Refund request already exists for this UTXO"`.
7. After `unsafe_refund_timelock_sec` elapses (DAO/Operator did not reject), Bob calls `execute_refund(utxo_storage_key, None)`.
8. The bridge constructs and MPC-signs a Bitcoin transaction paying **Alice's 1 BTC to Bob's address**. [2](#0-1) [6](#0-5) [7](#0-6)

    pub fn reject_refund(&mut self, utxo_storage_key: String) {
        let caller = env::predecessor_account_id();
        let is_privileged = self.acl_has_role(Role::DAO.into(), caller.clone())
            || self.acl_has_role(Role::Operator.into(), caller);
        // `execute_refund` also inserts the UTXO into `verified_deposit_utxo` (to block a
        // later deposit) while keeping the request with `executed == true`. That membership
        // must NOT open the permissionless reject path, otherwise anyone could cancel an
        // in-flight refund — so only treat the UTXO as "already deposited" when the request
        // was not executed by us, i.e. a real `verify_deposit` finalized it.
        let executed = self
            .data()
            .refund_requests
            .get(&utxo_storage_key)
            .map(|r| RefundRequest::from(r).executed)
            .unwrap_or(false);
        let is_already_deposited = !executed
            && self
                .data()
                .verified_deposit_utxo
                .contains(&utxo_storage_key);
        require!(
            is_privileged || is_already_deposited,
            "Only DAO/Operator can reject, or UTXO must be already verified via deposit"
        );
        self.internal_reject_refund(utxo_storage_key);
```
