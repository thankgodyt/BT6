### Title
`validatePerasCert` Unconditionally Accepts Any Inbound Peras Certificate Without Cryptographic or Semantic Validation — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance's `validatePerasCert` implementation unconditionally returns `Right` for every certificate it receives, performing zero cryptographic or semantic checks. This is the only `BlockSupportsPeras` instance in the production codebase and is wired directly into the production `makePerasCertPoolWriterFromChainDB` path. An unprivileged peer can send a completely fabricated `PerasCert` — with an arbitrary round number, arbitrary boosted block, and no valid quorum proof — and the node will accept it, store it, and apply its weight boost during chain selection.

---

### Finding Description

**Root cause:**

The universal instance at `SupportsPeras.hs` lines 320–358 is the sole production implementation of `BlockSupportsPeras`. Its `validatePerasCert` method is:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

This function never inspects the certificate's content. It does not verify:
- That the certificate was produced by a legitimate quorum of committee members
- That the boosted block (`pcCertBoostedBlock`) exists or is valid
- That the round number (`pcCertRound`) is within any acceptable range
- Any cryptographic signature or BLS proof

**Production call path:**

`makePerasCertPoolWriterFromChainDB` — explicitly documented as the production writer (as opposed to the test-only `makePerasCertPoolWriterFromCertDB`) — passes `validatePerasCert mkPerasParams` directly as the validator:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each inbound certificate and, because `validatePerasCert` always returns `Right`, the `([], validatedCerts)` branch is always taken and every certificate is unconditionally stored:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [3](#0-2) 

The accepted certificate is then forwarded to `ChainDB.addPerasCertAsync`, which applies the certificate's weight boost (`vpcCertBoost`) during chain selection.

**Analog to the Seaport bug:**
The Seaport bug had an `errorBuffer` that could reach an unhandled combined state (value `3`), causing the validation to silently pass. Here, the analogous flaw is that the error path (`Left`) is structurally unreachable — `validatePerasCert` can never produce a `Left`, so the rejection branch in `processCerts` is dead code. Both bugs result in a validation function that cannot reject invalid inputs.

---

### Impact Explanation

**Severity: High** — Bypass of Peras certificate validation that enables unauthorized certificate acceptance.

A crafted `PerasCert` accepted by the node is stored in the `PerasCertDB` and applied via `ChainDB.addPerasCertAsync`. The certificate's `vpcCertBoost` (derived from `perasWeight params`) is then used to boost the weight of the attacker-specified block during chain selection. By fabricating a certificate that boosts an adversarial block, an unprivileged peer can cause an honest node to prefer a non-canonical or adversarially-controlled chain over the honest chain, violating chain selection safety.

This fits the allowed impact: *"Bypass of … certificate … checks … that enables unauthorized … certificate acceptance"* and *"Chain selection … bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain."*

---

### Likelihood Explanation

The Peras certificate mini-protocol is a public-facing network interface. Any peer that can connect to the node can send `PerasCert` messages. No stake, key material, or privileged access is required. The attacker only needs to craft a `PerasCert` with a desired `pcCertRound` and `pcCertBoostedBlock` — both are plain data fields with no cryptographic binding. The deduplication filter (`certsNotAlreadyInDb`) only blocks re-submission of the same round number, so one certificate per round can be injected freely.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with a real validator that checks:
1. The certificate contains a valid cryptographic proof of quorum (e.g., BLS aggregate signature over the correct message).
2. The signing committee members are eligible for the claimed round under the current stake distribution.
3. The boosted block (`pcCertBoostedBlock`) is a known, valid block on the chain.
4. The round number is within the acceptable window relative to the current tip.

Until the real implementation is in place, the `processCerts` path should refuse all inbound certificates rather than accepting them unconditionally, to avoid the current bypass.

---

### Proof of Concept

1. Connect to a target node via the Peras certificate object-diffusion mini-protocol.
2. Construct a `PerasCert` with:
   - `pcCertRound` set to the current Peras round
   - `pcCertBoostedBlock` set to the hash of an adversarially-controlled block
3. Send the certificate in a batch to `opwAddObjects`.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams}` unconditionally.
5. `partitionEithers` produces `([], [validatedCert])`, so the certificate is passed to `ChainDB.addPerasCertAsync`.
6. The ChainDB applies the weight boost to the adversarially-specified block, causing chain selection to prefer it over the honest chain tip. [4](#0-3) [5](#0-4)
