### Title
Unconditional `validatePerasCert` Stub Allows Any Peer to Inject Arbitrary Peras Certificates and Manipulate Chain Selection - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production `BlockSupportsPeras` instance implements `validatePerasCert` as a stub that unconditionally returns `Right` (success) for every certificate, performing no cryptographic, committee, or quorum verification. This stub is wired directly into the live Peras certificate diffusion inbound handler (`makePerasCertPoolWriterFromChainDB`), which is reachable by any unprivileged peer over the node-to-node network. An attacker can send a crafted `PerasCert` pointing to any block in the VolatileDB, have it accepted without any check, and cause the receiving node to apply a `perasWeight = 15`-block boost to that block during chain selection, potentially switching the node to a non-canonical fork.

---

### Finding Description

**Root cause — stub validation always succeeds:**

The `instance StandardHash blk => BlockSupportsPeras blk` in `SupportsPeras.hs` is explicitly marked as a "degenerate instance for all blks to get things to compile" and its `validatePerasCert` implementation unconditionally returns `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No signature, no committee membership, no quorum, no round-number bounds, and no boosted-block existence check is performed. Every `PerasCert` value, regardless of origin or content, is stamped as `ValidatedPerasCert` with `vpcCertBoost = perasWeight params` (= 15 blocks of weight).

**Wiring into the production inbound handler:**

`makePerasCertPoolWriterFromChainDB` is the production writer used for all inbound Peras certificates received from peers. It passes `validatePerasCert mkPerasParams` as the validation function:

```haskell
makePerasCertPoolWriterFromChainDB systemTime chainDB =
  ObjectPoolWriter
    { opwAddObjects = \certs ->
        processCerts
          systemTime
          (ChainDB.getPerasCertIds chainDB)
          -- TODO replace when actual plumbing is in place
          (validatePerasCert mkPerasParams)
          (void . ChainDB.addPerasCertAsync chainDB)
          certs
    ...
    }
``` [2](#0-1) 

`processCerts` calls `validateCert` on each certificate and, if all pass (which they always do), adds them via `addPerasCertAsync`: [3](#0-2) 

**Reachable from any peer via the node-to-node mini-protocol:**

`mkHandlers` in `NodeToNode.hs` wires `makePerasCertPoolWriterFromChainDB` directly into `hPerasCertDiffusionClient`, which is the live inbound handler for the Peras certificate diffusion mini-protocol, reachable by any connecting peer:

```haskell
hPerasCertDiffusionClient = \version controlMessageSTM peer ->
    objectDiffusionInbound
      ...
      (makePerasCertPoolWriterFromChainDB systemTime getChainDB)
      ...
``` [4](#0-3) 

**Chain selection impact:**

Once accepted, the certificate is enqueued via `addPerasCertAsync` and processed by `chainSelSync`. The chain selection logic reads the `PerasWeightSnapshot` and applies the `vpcCertBoost` (15 blocks) to the boosted block's chain weight, potentially triggering a fork switch: [5](#0-4) 

The `getPerasWeightSnapshot` is used during chain selection to prefer chains with Peras certificate boosts: [6](#0-5) 

**Contrast with vote handling (not vulnerable):**

The analogous vote inbound handler deliberately passes `(pure (PerasVoteStakeDistr mempty))` as the stake distribution, and the code comment explicitly notes "the empty stake distribution will cause all votes to be considered invalid." Votes are therefore rejected. Certificates have no equivalent guard. [7](#0-6) 

---

### Impact Explanation

An unprivileged peer can send a crafted `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block currently in the VolatileDB. The certificate passes validation unconditionally, is stored in the `PerasCertDB`, and triggers chain selection. The boosted block gains 15 blocks of extra weight (`perasWeight = 15`). If the boosted block is on a fork, the receiving node may switch away from the canonical chain to a non-canonical fork that it would not otherwise prefer. This constitutes a **chain selection manipulation** by an unprivileged peer, violating the Peras security assumption that only certificates backed by a quorum of legitimate committee members should influence chain selection.

**Severity: High** — matches "Chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

---

### Likelihood Explanation

Any peer that can establish a node-to-node connection and negotiate the Peras certificate diffusion mini-protocol can exploit this. No keys, stake, or special privileges are required. The attacker only needs to know the hash and slot of a block in the target node's VolatileDB (obtainable via ChainSync). The attack is deterministic and requires sending a single well-formed CBOR-encoded `PerasCert` message.

---

### Recommendation

Replace the stub `validatePerasCert` implementation with real cryptographic and committee verification before the Peras certificate diffusion mini-protocol is enabled in production. As an immediate mitigation (analogous to the vote-side guard), the certificate inbound handler should be disabled or should reject all certificates until real validation is in place — for example, by passing a validation function that always returns `Left` when the committee selection plumbing is not yet wired up, rather than one that always returns `Right`.

---

### Proof of Concept

1. Attacker connects to a target node and runs ChainSync to learn the hash `H` and slot `S` of a block on a fork in the node's VolatileDB.
2. Attacker constructs a `PerasCert` value: `PerasCert { pcCertRound = <any round>, pcCertBoostedBlock = BlockPoint S H }`.
3. Attacker serialises this as CBOR and sends it via the Peras certificate diffusion mini-protocol (`hPerasCertDiffusionClient` / `objectDiffusionInbound`).
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = 15 })` unconditionally.
5. `addPerasCertAsync` enqueues the certificate; `chainSelSync` processes it, applies 15 blocks of weight to the fork block, and may switch the node's selection to the fork.
6. The node now tracks a non-canonical chain, diverging from honest peers that have not received this certificate. [8](#0-7) [9](#0-8) [4](#0-3) [10](#0-9)

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
