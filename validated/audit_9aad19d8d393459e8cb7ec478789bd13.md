### Title
`validatePerasCert` Unconditionally Accepts Any Peras Certificate, Disabling the Entire Certificate Validation Mechanism - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance's `validatePerasCert` always returns `Right` without performing any cryptographic or structural validation. This is the direct analog of the reported bug: just as `_enforceLiquidationQueue()` checks shares at `address(this)` (which holds none) instead of `address(node)`, `validatePerasCert` checks the certificate against nothing instead of against the actual committee/cryptographic proof — always producing a trivially passing result. The function is wired into the live production path for processing inbound Peras certificates from peers, meaning any unprivileged peer can inject arbitrary certificates that apply weight boosts to any block they choose, corrupting chain selection.

---

### Finding Description

In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`, the universal `BlockSupportsPeras` instance implements `validatePerasCert` as an unconditional stub:

```haskell

-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

Every certificate, regardless of its content, round number, boosted block, or cryptographic proof, is unconditionally wrapped in `Right` and returned as a `ValidatedPerasCert`. No committee membership check, no signature verification, no round-number sanity check is performed.

This stub is directly wired into the production certificate ingestion path. In `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasCert.hs`, `makePerasCertPoolWriterFromChainDB` — the writer used for all inbound peer certificates — calls:

```haskell

  (validatePerasCert mkPerasParams)
  (void . ChainDB.addPerasCertAsync chainDB)

``` [2](#0-1) 

`processCerts` rejects a batch only if `validateCert` returns `Left` for any certificate. Since `validatePerasCert` never returns `Left`, every batch from every peer is accepted in full. [3](#0-2) 

Accepted certificates are stored in the `PerasCertDB`. The `implGetWeightSnapshot` function then builds a `PerasWeightSnapshot` from every stored certificate's `getPerasCertBoostedBlock` and `getPerasCertBoost`:

```haskell

        [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
        | cert <- Map.elems (pcdsCertsByTicket pcds)
        ]
``` [4](#0-3) 

This snapshot is consumed by `chainSelectionForBlock` and `preferAnchoredCandidate` during every chain selection decision: [5](#0-4) [6](#0-5)

### Impact Explanation

**High — Chain selection corruption via unauthorized Peras weight injection.**

An unprivileged peer connected via the Peras certificate object-diffusion mini-protocol can craft a `PerasCert` with an arbitrary `pcCertBoostedBlock` pointing to any block on an adversarial fork. Because `validatePerasCert` never rejects anything, the certificate is stored and its weight boost is applied to that block in every subsequent chain selection comparison. A sufficiently large `perasWeight` (drawn from `mkPerasParams`) applied to an adversarial block can cause an honest node to prefer a non-canonical, adversary-controlled chain over the honest chain, violating chain selection safety. This matches the **High** impact class: *chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

**High.** The object-diffusion mini-protocol for Peras certificates is a standard peer-to-peer channel. Any connected peer can send a batch of crafted `PerasCert` objects. No special privileges, keys, or stake are required. The only prerequisite is a live peer connection, which is the normal operating condition of any Cardano node.

---

### Recommendation

Replace the stub `validatePerasCert` with a real implementation that:
1. Verifies the certificate's aggregate BLS/cryptographic signature against the claimed committee members.
2. Checks that the claimed voters are eligible members of the voting committee for the stated round (using the stake distribution from the ledger view at the relevant epoch).
3. Confirms the boosted block exists and is on a plausible chain.
4. Validates the round number is within the expected range relative to the current chain tip.

Until real validation is in place, the `processCerts` call in `makePerasCertPoolWriterFromChainDB` should reject all inbound certificates rather than accept them unconditionally, to prevent weight-injection attacks. [7](#0-6) 

---

### Proof of Concept

1. Connect to a target node as a peer via the Peras certificate object-diffusion mini-protocol.
2. Craft a `PerasCert` with `pcCertRound = <any round>` and `pcCertBoostedBlock = <point of an adversarial block on a fork>`.
3. Send the certificate in a batch to the target node.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right ValidatedPerasCert{...}` unconditionally.
5. The certificate is stored in `PerasCertDB` via `ChainDB.addPerasCertAsync`.
6. `implGetWeightSnapshot` includes the adversarial block's point in the `PerasWeightSnapshot` with boost `perasWeight mkPerasParams`.
7. On the next chain selection event, `preferAnchoredCandidate` computes `weightedSelectView` for the adversarial fork, which now includes the injected boost, potentially making it heavier than the honest chain.
8. The node switches to the adversarial fork. [8](#0-7)

  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasCertValidationError errs)
