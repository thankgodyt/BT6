### Title
Stub `validatePerasCert` Always Accepts Any Certificate, Enabling Unbounded Peras Weight Boost Accumulation via Crafted Peer Messages - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The production catch-all instance of `validatePerasCert` unconditionally returns `Right` (success) for every certificate it receives, performing zero quorum or signature verification. An unprivileged peer can exploit this by sending many crafted certificates with distinct round numbers, all boosting the same block on their chain. Because `PerasWeightSnapshot` accumulates weight additively per round, the adversary's chain acquires an arbitrarily large weight boost, causing honest nodes to prefer it over the canonical chain.

---

### Finding Description

**Root cause — `validatePerasCert` stub:**

The catch-all `BlockSupportsPeras` instance, explicitly labelled a "degenerate instance for all blks to get things to compile," implements `validatePerasCert` as an unconditional `Right`:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasCert params cert =
  Right
    ValidatedPerasCert
      { vpcCert = cert
      , vpcCertBoost = perasWeight params
      }
``` [1](#0-0) 

No quorum threshold, no aggregate BLS signature check, no committee membership check — any byte sequence that deserialises as a `PerasCert` is immediately wrapped in `ValidatedPerasCert`.

**Entry path — `processCerts` in the Peras certificate mini-protocol:**

Inbound certificates from a remote peer are processed by `processCerts`, which calls the `validateCert` callback (bound to `validatePerasCert`) and, because it always returns `Right`, adds every certificate to the `PerasCertDB`:

```haskell
case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
  ([], validatedCerts) ->
    mapM_ (addCert . WithArrivalTime now) validatedCerts
  (errs, _) ->
    throw (PerasCertValidationError errs)
``` [2](#0-1) 

The only deduplication is by `PerasRoundNo`; certificates with distinct round numbers are all stored.

**Unbounded weight accumulation — `addToPerasWeightSnapshot`:**

`implGetWeightSnapshot` builds the weight snapshot by iterating over every stored certificate and calling `addToPerasWeightSnapshot`, which uses `Map.insertWith (<>)` — i.e., it **adds** the new boost on top of any existing boost for the same block point:

```haskell
addToPerasWeightSnapshot pt weight =
  PerasWeightSnapshot . Map.insertWith (<>) pt weight . getPerasWeightSnapshot
``` [3](#0-2) 

The snapshot is computed as:

```haskell
mkPerasWeightSnapshot
  [ (getPerasCertBoostedBlock cert, getPerasCertBoost cert)
  | cert <- Map.elems (pcdsCertsByTicket pcds)
  ]
``` [4](#0-3) 

If N certificates all name the same block as their boosted target, that block accumulates weight `N × perasWeight`.

**Chain selection uses this inflated weight:**

`preferCandidate` compares `wsvTotalWeight = blockNo + weightBoost`. A chain whose tip block has accumulated `N × perasWeight` will dominate any honest chain:

```haskell
preferCandidate cfg ours cand =
  case compare (wsvTotalWeight ours) (wsvTotalWeight cand) of
    LT -> ShouldSwitch ...
``` [5](#0-4) 

**Secondary impact — premature immutability via `takeVolatileSuffix`:**

`takeVolatileSuffix` uses `totalWeightOfFragment` (block count + weight boost) to decide which blocks are buried under weight `k` and therefore immutable. Inflated weight can push blocks into the immutable prefix prematurely, preventing rollback to the honest chain even after the attack is detected. [6](#0-5) 

---

### Impact Explanation

An unprivileged peer can make an honest node permanently prefer a non-canonical adversarial chain by inflating its Peras weight boost to an arbitrarily large value. This is a **chain-selection safety failure**: the honest node adopts an invalid or minority chain, violating the Common Prefix property. The secondary `takeVolatileSuffix` effect can make the switch irreversible within the node's lifetime (blocks treated as immutable cannot be rolled back).

This matches the **High** impact category: *Chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions.*

---

### Likelihood Explanation

- The entry path is the Peras certificate object-diffusion mini-protocol, reachable by any connected peer.
- The adversary only needs to craft certificates with distinct `PerasRoundNo` values (plain integers) pointing to the same block — no cryptographic material is required because `validatePerasCert` performs no checks.
- The TODO comment and the linked issue (`tweag/cardano-peras#120`) confirm this is a known stub, not a temporary placeholder with validation elsewhere.
- The `PerasCert` type is fully serialisable/deserialisable, so crafting valid-looking wire messages is trivial.

---

### Recommendation

1. **Implement `validatePerasCert` properly** for the production `HardForkBlock` instance: verify the aggregate BLS signature against the claimed voter set, check that the voter set meets the quorum threshold, and verify each voter's committee eligibility (persistent or non-persistent seat via VRF).
2. **Cap the total weight boost per block point** in `PerasWeightSnapshot` to at most one certificate's worth of boost (since the Peras protocol guarantees at most one certificate per round, and each round boosts at most one block).
3. **Rate-limit or bound** the number of certificates accepted per peer connection before full validation is in place.

---

### Proof of Concept

```
1. Adversary connects to an honest node via the Peras cert mini-protocol.

2. Adversary crafts N certificates:
     cert_i = PerasCert { pcCertRound = i, pcCertBoostedBlock = adversaryBlock }
   for i = 0, 1, ..., N-1, all pointing to the same adversaryBlock on their chain.

3. processCerts calls validatePerasCert on each cert_i.
   validatePerasCert always returns Right, so all N certs pass.

4. implAddCert stores each cert_i (distinct round numbers, no deduplication).

5. implGetWeightSnapshot computes:
     weight(adversaryBlock) = N × perasWeight

6. Chain selection:
     wsvTotalWeight(adversaryChain) = blockNo + N × perasWeight
     wsvTotalWeight(honestChain)    = blockNo + 0  (or small legitimate boost)

   For large N, preferCandidate returns ShouldSwitch for the adversary's chain.

7. The honest node adopts the adversary's chain.
   takeVolatileSuffix may additionally push adversaryBlock into the immutable
   prefix, preventing future rollback.
```

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts
    -- Some certs are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that cert validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
