### Title
Double-Spend via `remove_fin_transfer` Erasing Replay Protection on Failed `ft_transfer_call` — (`near/omni-bridge/src/lib.rs`)

---

### Summary

When a finalized inbound transfer uses a non-empty `msg` (triggering `ft_transfer_call` / `mint`-with-msg semantics) and the recipient's `ft_on_transfer` causes the promise result to be `U128(0)`, `fin_transfer_send_tokens_callback` calls `remove_fin_transfer`, which **permanently deletes the `transfer_id` from `finalised_transfers`**. This is the contract's sole replay guard. After deletion, the identical proof can be re-submitted through `fin_transfer`, re-inserting the `transfer_id` and minting or releasing tokens a second time.

---

### Finding Description

**Full call chain:**

```
fin_transfer
  → verify_proof + fin_transfer_callback
    → process_fin_transfer_to_near
        add_fin_transfer(transfer_id)          // inserts into finalised_transfers
        send_tokens(token, recipient, amount, msg)   // msg non-empty → ft_transfer_call / mint-with-msg
        .then(fin_transfer_send_tokens_callback(
                transfer_message,
                fee_recipient,
                is_ft_transfer_call = !msg.is_empty(),   // TRUE
                storage_owner,
                lock_actions))
```

Inside `fin_transfer_send_tokens_callback`:

```rust
if Self::is_refund_required(is_ft_transfer_call) {   // true when promise result == U128(0)
    self.burn_tokens_if_needed(...);
    self.revert_lock_actions(&lock_actions);
    self.remove_fin_transfer(&transfer_message.get_transfer_id(), storage_owner);  // ← DELETES replay guard
    env::log_str(&OmniBridgeEvent::FailedFinTransferEvent { transfer_message }.to_log_string());
}
``` [1](#0-0) 

`is_refund_required` returns `true` when the promise result deserializes to `U128(0)`: [2](#0-1) 

`remove_fin_transfer` unconditionally removes the entry: [3](#0-2) 

`add_fin_transfer` (the only replay guard) panics with `TransferAlreadyFinalised` only if the entry is **present**: [4](#0-3) 

After `remove_fin_transfer` runs, the entry is gone, so a second `fin_transfer` call with the same proof passes `add_fin_transfer` without error.

**How `U128(0)` is produced by a malicious recipient:**

In NEP-141, `ft_transfer_call` → `ft_on_transfer` → `ft_resolve_transfer`. `ft_resolve_transfer` returns the number of tokens **actually transferred** (used). If `ft_on_transfer` returns the full amount (all tokens rejected), `ft_resolve_transfer` returns `0`. The bridge's `send_tokens` uses `ft_transfer_call` for non-deployed tokens with a non-empty msg, and `mint(recipient, amount, Some(msg))` for deployed tokens — both paths ultimately produce a `U128(0)` promise result when the recipient rejects all tokens. [5](#0-4) 

The `msg` field is attacker-controlled: it is taken verbatim from `init_transfer.msg` in the proof, which the attacker sets when initiating the cross-chain transfer on the source chain. [6](#0-5) 

---

### Impact Explanation

**For deployed (minted) tokens:**
- Attempt 1: tokens minted → malicious `ft_on_transfer` rejects → `burn_tokens_if_needed` burns them → `remove_fin_transfer` clears the guard.
- Attempt 2 (same proof): tokens minted again → malicious contract now accepts → attacker holds tokens.
- Net: one lock on the source chain, two mint events on NEAR. Classic double-spend.

**For non-deployed (locked) tokens:**
- Attempt 1: `ft_transfer_call` sends tokens → recipient rejects → tokens returned to bridge → `remove_fin_transfer` clears the guard.
- Attempt 2: `ft_transfer_call` sends tokens again → recipient accepts → attacker holds tokens.
- Net: bridge releases the same locked tokens twice against a single source-chain lock.

---

### Likelihood Explanation

The attacker only needs to:
1. Deploy a stateful NEAR contract that rejects tokens on the first `ft_on_transfer` call and accepts on the second.
2. Initiate a cross-chain transfer from the source chain specifying that contract as recipient and any non-empty string as `msg`.
3. Wait for a relayer to submit the proof (standard relayer behavior).
4. After `FailedFinTransferEvent` is emitted, wait for any relayer to re-submit the proof — this is the **intended retry behavior** for failed transfers, so it happens automatically.
5. The malicious contract accepts tokens on the second call.

The `#[trusted_relayer]` gate on `fin_transfer` does not block the attack: the attacker does not need to call `fin_transfer` themselves; they only need to control the recipient contract. A legitimate relayer performs both submissions. [7](#0-6) 

---

### Recommendation

**Do not remove `transfer_id` from `finalised_transfers` on failure.** The entry must be permanent — it is the only replay barrier. Instead:

- On `ft_on_transfer` rejection, store the failed transfer in a separate `failed_transfers` map keyed by `transfer_id`, allowing the original recipient (or a governance action) to redirect delivery without re-verifying the proof.
- Alternatively, keep the `finalised_transfers` entry and introduce a separate `pending_delivery` map for retry logic, so replay protection is never weakened.

### Proof of Concept

```rust
// Malicious recipient contract (pseudo-code)
static mut CALL_COUNT: u32 = 0;

#[near_bindgen]
impl MaliciousReceiver {
    pub fn ft_on_transfer(&mut self, _sender: AccountId, amount: U128, _msg: String) -> U128 {
        unsafe {
            CALL_COUNT += 1;
            if CALL_COUNT == 1 {
                amount  // reject all tokens → ft_resolve_transfer returns 0
            } else {
                U128(0) // accept all tokens on second call
            }
        }
    }
}
```

**Localnet sequence:**
1. Deploy bridge + bridge token factory + malicious receiver on localnet.
2. Register malicious receiver as a NEAR account; set `msg = "attack"` in the source-chain transfer.
3. Submit proof via `fin_transfer` → observe `FailedFinTransferEvent` in logs.
4. Assert `is_transfer_finalised(transfer_id) == false` (guard removed).
5. Re-submit identical proof via `fin_transfer` → observe `FinTransferEvent`.
6. Assert malicious receiver's token balance equals the bridged amount (tokens received on second attempt while source chain lock was only created once).

    fn is_refund_required(is_ft_transfer_call: bool) -> bool {
        if is_ft_transfer_call {
            match env::promise_result_checked(0, MAX_FT_TRANSFER_CALL_RESULT) {
                Ok(value) => {
                    if let Ok(amount) = near_sdk::serde_json::from_slice::<U128>(&value) {
                        // Normal case: refund if the used token amount is zero
                        // The amount can be zero if the `ft_on_transfer` in the receiver contract returns an amount instead of `0`, or if it panics.
                        amount.0 == 0
                    } else {
                        // Unexpected case: don't refund
                        false
                    }
                }
                // Unexpected case: don't refund
                Err(_) => false,
            }
        } else {
            // Not ft_transfer_call: don't refund
            false
        }
    }
