### Title
Permanent Fund Freeze via `normalize_amount` Floor-Division Rounding to Zero in `sign_transfer` — (File: `near/omni-bridge/src/lib.rs`)

---

### Summary

`init_transfer` accepts any amount satisfying `fee < amount` and immediately burns or locks the full token amount. The `normalize_amount` floor-division applied later in `sign_transfer` can produce zero for sub-minimum amounts, causing `sign_transfer` to panic with `InvalidAmountToTransfer`. Because no cancel or refund path exists for a successfully initiated transfer, the user's tokens are permanently frozen in the bridge.

---

### Finding Description

**Root cause — `normalize_amount` uses floor division:** [1](#0-0) 

```rust
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))   // floor division
}
```

For a token with `origin_decimals = 24` (NEAR) and `decimals = 6` (EVM, e.g. USDC), `diff_decimals = 18`. Any `amount_without_fee < 10^18` normalizes to **0**.

**`init_transfer` has no minimum-amount guard:** [2](#0-1) 

Only `fee < amount` is enforced. There is no check that `amount - fee >= 10^diff_decimals`.

**Tokens are burned/locked before the zero-check fires:** [3](#0-2) 

`init_transfer_internal` calls `burn_tokens_if_needed` / `lock_tokens_if_needed` and returns `U128(0)` (no refund to the caller via `ft_transfer_call`). The tokens are gone from the user's perspective at this point.

**`sign_transfer` checks for zero only after the fact:** [4](#0-3) 

```rust
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee()...,
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

The panic here does **not** revert the earlier `init_transfer` state change; NEAR promise execution is already complete.

**No cancel/refund path exists.** `update_transfer_fee` only allows *increasing* the fee: [5](#0-4) 

```rust
require!(
    fee.fee >= current_fee.fee && fee.fee < transfer_message.amount,
    BridgeError::InvalidFee.as_ref()
);
```

Increasing the fee makes `amount_without_fee` even smaller, so the zero-normalization condition cannot be escaped. There is no `cancel_transfer` function anywhere in the contract.

**Distinction from documented "dust" behavior.** The `normalize_amount` docstring acknowledges that sub-unit remainders ("dust") stay locked when `fee = 0`: [6](#0-5) 

However, "dust" refers to the *remainder* after a successful normalization (e.g., 999 999 out of 1 999 999 tokens). The scenario here is the *entire* `amount_without_fee` rounding to zero — the user receives nothing on the destination chain and loses the full principal. This is not covered by the documented dust-handling design.

The CLAUDE.md false-positive item #2 ("Decimal Arithmetic Underflow") addresses only the case where `origin_decimals < decimals` causes integer underflow in `diff_decimals`: [7](#0-6) 

It does not address `normalize_amount` silently returning 0 for a valid (non-underflowing) decimal configuration.

---

### Impact Explanation

Permanent freezing of bridged funds. For any token pair where `origin_decimals > decimals` (the normal case), a user who initiates a transfer with `amount_without_fee < 10^(origin_decimals − decimals)` will have their tokens burned or locked with no recovery path. For USDC (24 NEAR decimals, 6 EVM decimals, diff = 18), the threshold is `10^18` NEAR-side smallest units. Deployed (bridge-minted) tokens are **burned** outright; native locked tokens are frozen until DAO intervention.

---

### Likelihood Explanation

Low-to-medium. The condition is reachable by any unprivileged user calling `ft_transfer_call` with a sufficiently small amount. For tokens with large decimal gaps (e.g., USDC, USDT), the threshold is non-trivial in absolute token terms. Accidental triggering is plausible for users who mis-specify amounts in raw smallest-unit arithmetic; deliberate triggering (griefing) requires only a dust-sized token balance.

---

### Recommendation

1. **Add a minimum-amount guard in `init_transfer`** (or `init_transfer_internal`) that rejects transfers where `amount_without_fee < 10^(origin_decimals − decimals)` for the target chain, returning the full amount to the caller.
2. **Alternatively, add a `cancel_transfer` function** that allows the original sender to reclaim locked tokens for a pending transfer that has not yet been signed, subject to a time-lock or relayer-absence condition.

---

### Proof of Concept

**Setup:** USDC registered with `origin_decimals = 24`, `decimals = 6` → `diff_decimals = 18`.

1. User calls `ft_transfer_call(bridge, amount=5×10^17, msg=<InitTransferMsg to EVM>)`.
2. `ft_on_transfer` → `init_transfer` → `init_transfer_internal`:
   - `burn_tokens_if_needed` burns `5×10^17` USDC tokens.
   - Returns `U128(0)` → token contract refunds 0 to user.
3. Relayer calls `sign_transfer(transfer_id, ...)`:
   - `amount_without_fee = 5×10^17` (fee = 0).
   - `normalize_amount(5×10^17, {24, 6}) = 5×10^17 / 10^18 = 0`.
   - `require!(0 > 0, ...)` → **panic: `InvalidAmountToTransfer`**.
4. No further call can complete this transfer. `update_transfer_fee` can only raise the fee, making `amount_without_fee` smaller. No cancel function exists.
5. The `5×10^17` USDC tokens are **permanently destroyed**.
