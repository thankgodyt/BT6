### Title
Publicly Callable `request_refund` Allows Frontrunner to Redirect BTC Refund to Attacker-Controlled Address - (File: `contracts/satoshi-bridge/src/refund.rs`, `contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`request_refund` is publicly callable with no caller restriction. When `deposit_msg.refund_address` is `None`, the `refund_address` argument is entirely caller-supplied and is not cryptographically bound to the deposit message. An attacker who observes a pending `request_refund` transaction can race it with an identical call that substitutes their own BTC address, causing the bridge's MPC-signed refund transaction to send the user's BTC to the attacker.

---

### Finding Description

The `request_refund` entry point carries only `#[payable]` and `#[pause]` guards — no `#[trusted_relayer]` restriction: [1](#0-0) 

Inside `internal_request_refund`, the only check on `refund_address` is a conditional equality test that fires **only when `deposit_msg.refund_address` is `Some`**: [2](#0-1) 

When `deposit_msg.refund_address` is `None` (the common case for users who did not pre-commit a BTC address in their `DepositMsg`), the `refund_address` argument passes through unchecked and is stored verbatim in the `RefundRequest`: [3](#0-2) 

The callback enforces that only one refund request may exist per UTXO: [4](#0-3) 

Because the deposit address is derived solely from the hash of `deposit_msg`, and `deposit_msg` is fully public once the user broadcasts their transaction, an attacker can copy every parameter (`deposit_msg`, `tx_bytes`, `vout`, `proof`) and substitute their own BTC address as `refund_address`. Whichever call lands first owns the refund request. When `execute_refund` is later called, the bridge's MPC pipeline builds and signs a Bitcoin transaction paying the attacker's address: [5](#0-4) 

---

### Impact Explanation

If the attacker's `request_refund` is processed before the legitimate user's call, the stored `refund_address` is the attacker's BTC address. The user's subsequent call fails with "Refund request already exists for this UTXO". Once `unsafe_refund_timelock_sec` elapses without DAO/Operator intervention, `execute_refund` constructs and MPC-signs a Bitcoin transaction that pays the attacker. The user's BTC — which was deposited to a bridge-controlled address and never finalized as a deposit — is permanently transferred to the attacker. This constitutes unauthorized redirection of bridge-controlled BTC funds.

---

### Likelihood Explanation

NEAR validators observe pending transactions before block inclusion and can reorder them within a shard. Any actor running a validator node, or one co-located with a validator, can reliably win the race. Even without validator access, the attack is viable: `request_refund` requires a storage deposit and a Light Client proof, both of which are copyable from the victim's broadcast transaction. The `unsafe_refund_timelock_sec` window is a partial mitigation but depends entirely on continuous DAO/Operator monitoring; it does not prevent the attack, only delays execution.

---

### Recommendation

Bind the `refund_address` to the deposit message at deposit time. The simplest fix is to require that `deposit_msg.refund_address` is always `Some` when `request_refund` is called, so the BTC destination is committed in the hash that derives the deposit address and cannot be substituted by a third party. Alternatively, restrict `request_refund` to a `#[trusted_relayer]` role, consistent with the deposit verification endpoints.

---

### Proof of Concept

1. User Alice deposits BTC to the bridge address derived from `deposit_msg = { recipient_id: "alice.near", refund_address: None, ... }`.
2. The deposit is never finalized (e.g., the relayer misses it).
3. Alice broadcasts `request_refund(deposit_msg, refund_address="alice_btc_addr", tx_bytes, vout, proof, None)`.
4. Attacker Bob observes Alice's pending transaction, copies all parameters, and broadcasts `request_refund(deposit_msg, refund_address="bob_btc_addr", tx_bytes, vout, proof, None)` with higher priority or via validator collusion.
5. Bob's call lands first. `request_refund_callback` stores `RefundRequest { refund_address: "bob_btc_addr", ... }`.
6. Alice's call fails: "Refund request already exists for this UTXO".
7. After `unsafe_refund_timelock_sec` elapses (assuming no DAO/Operator rejection), anyone calls `execute_refund`.
8. `build_refund_output` constructs a `TxOut` paying `"bob_btc_addr"`. The MPC pipeline signs and broadcasts this transaction.
9. Alice's BTC is sent to Bob. Alice has no recourse. [6](#0-5) [7](#0-6)

    pub fn request_refund(

        proof: TxInclusionProof,

            );

            deposit_msg,
            refund_address,
            tx_bytes,
            vout,
            proof,
            gas_fee.map(|v| v.0),
        )
    }

    pub(crate) fn build_refund_output(&self, refund_address: &str, refund_amount: u128) -> TxOut {
        let config = self.internal_config();
        let refund_addr = crate::network::Address::parse(refund_address, config.chain.clone())
            .expect("Invalid refund address");
        let refund_script_pubkey = refund_addr
            .script_pubkey()
            .expect("Invalid refund script_pubkey");
        TxOut {
            value: Amount::from_sat(
                u64::try_from(refund_amount)
                    .unwrap_or_else(|_| env::panic_str("Refund amount overflow")),
            ),
            script_pubkey: refund_script_pubkey,
        }
    }
