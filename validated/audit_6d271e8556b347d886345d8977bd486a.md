### Title
Silent Overcounting in `shelleyAfterVoting` Enables Premature Era Transition During Chain Growth Violation — (File: `ouroboros-consensus-cardano/src/shelley/Ouroboros/Consensus/Shelley/Ledger/Ledger.hs`)

---

### Summary

The `shelleyAfterVoting` counter in `ShelleyTransitionInfo` is incremented for **every** block whose slot is at or after the voting deadline, but the HFC's Iteration 4 design requires counting only blocks within the **first stability window** after the voting deadline. This overcounting causes `singleEraTransition` to signal a hard-fork era transition even when the stability window after the voting deadline contained fewer than `k` blocks — a Chain Growth violation — when the correct behavior is to silently suppress the transition. The bug is self-documented in the codebase as a known TODO.

---

### Finding Description

**Root cause — `applyHelper` in `Ledger.hs`:** [1](#0-0) 

```haskell
shelleyAfterVoting =
    (if blockSlot blk >= votingDeadline then succ else id) $
      shelleyAfterVoting tickedShelleyLedgerTransition
```

The `votingDeadline` is computed as: [2](#0-1) 

```haskell
votingDeadline = subSlots (2 * swindow) startOfNextEpoch
```

where `swindow = 3k/f`. This places the voting deadline at `startOfNextEpoch − 6k/f`. The counter is reset to zero at each epoch boundary: [3](#0-2) 

So within a given epoch, `shelleyAfterVoting` accumulates **all** blocks from slot `startOfNextEpoch − 6k/f` through `startOfNextEpoch − 1` — a window of `6k/f` slots.

**Gate in `shelleyTransition` in `ShelleyHFC.hs`:** [4](#0-3) 

```haskell
isTransition (ShelleyUpdatedPParams maybePParams newPParamsEpochNo) = do
  ...
  guard $ shelleyAfterVoting >= fromIntegral k
  return newPParamsEpochNo
```

The HFC's Iteration 4 design (documented in `civic_time.md`) requires that the era transition be **silently suppressed** if the stability window immediately after the voting deadline — slots `[votingDeadline, votingDeadline + swindow)` = `[startOfNextEpoch − 6k/f, startOfNextEpoch − 3k/f)` — contains fewer than `k+1` blocks. The code instead counts all blocks from `votingDeadline` to the end of the epoch (`6k/f` slots), which includes a second stability window `[startOfNextEpoch − 3k/f, startOfNextEpoch)`.

**Self-documented bug:** [5](#0-4) 

> "Silently ignore the on-chain governance … if the stability window after the voting deadline contains less than k+1 blocks (ie violates Chain Growth). **(TODO this is today's intended behavior, but a bug is counting all blocks after the voting deadline instead of only those in the subsequent stability window.)**"

---

### Impact Explanation

When a Chain Growth violation occurs in the first stability window after the voting deadline (fewer than `k` blocks in `[votingDeadline, votingDeadline + swindow)`), but enough blocks exist in the second stability window to bring the total `shelleyAfterVoting` count to `≥ k`, the HFC's `singleEraTransition` returns `Just epochNo` and signals the era transition. The correct behavior per Iteration 4 is to return `Nothing` and suppress the transition.

This causes nodes with different chain histories (different block distributions across the two stability windows) to disagree on whether to transition to the next era. One node may apply the new era's ledger rules while another remains in the current era, producing a **hard-fork era transition mismatch that breaks cross-era consensus invariants** — a High-severity impact matching the allowed scope: *"Hard-fork, era transition, ledger-view, query, or network-version mismatch that breaks cross-era consensus or ledger invariants for production Cardano nodes."*

---

### Likelihood Explanation

**Low.** The scenario requires a Chain Growth violation specifically in the first stability window after the voting deadline (fewer than `k` blocks in `3k/f` slots), while the second stability window compensates with enough blocks to satisfy the overcounted threshold. This can arise from:

- A natural network partition that suppresses block production during the first stability window but resolves before the epoch ends.
- An adversary with significant (but not majority) stake who withholds blocks during the first stability window and produces them in the second.

This does not require stake majority, but does require a specific temporal pattern of block production that is uncommon under normal network conditions.

---

### Recommendation

Restrict the `shelleyAfterVoting` counter to count only blocks within the first stability window after the voting deadline. Concretely, in `applyHelper`, change the increment condition from:

```haskell
if blockSlot blk >= votingDeadline
```

to:

```haskell
if blockSlot blk >= votingDeadline && blockSlot blk < votingDeadline + swindow
```

where `swindow = SL.stabilityWindow globals`. This aligns the counter with the Iteration 4 design intent described in `civic_time.md`.

---

### Proof of Concept

1. Configure a Shelley-era private testnet with `k = 10`, `f = 0.05` (so `swindow = 3k/f = 600` slots, epoch length `= 10k/f = 2000` slots, voting deadline at slot `2000 − 1200 = 800`).
2. Submit a governance proposal to increment the major protocol version (triggering the next era) before slot 800.
3. Simulate a Chain Growth violation: produce only 9 blocks in slots `[800, 1400)` (the first stability window after the voting deadline — fewer than `k = 10`).
4. Produce 10 blocks in slots `[1400, 2000)` (the second stability window).
5. Observe: `shelleyAfterVoting = 19 ≥ k = 10`, so `singleEraTransition` returns `Just epochNo` and the HFC signals the era transition.
6. On a second node that received the same blocks in a different order (e.g., the second window's blocks arrived first), the counter may differ, causing divergence on whether to transition.
7. The correct behavior (Iteration 4) would suppress the transition because the first stability window had only 9 < k+1 blocks. [6](#0-5) [7](#0-6)

shelleyTransition
  ShelleyPartialLedgerConfig{..}
  transitionMajorVersionRaw
  state =
    isTransition
      . Shelley.Inspect.pparamsUpdate
      $ state
   where
    ShelleyTransitionInfo{..} = shelleyLedgerTransition state

    -- 'shelleyLedgerConfig' contains a dummy 'EpochInfo' but this does not

    k :: Word64
