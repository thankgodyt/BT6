### Title
Silent Token Trap in `safe_mint` When Recipient Account Is Unregistered — (File: `contracts/nbtc/src/lib.rs`)

---

### Summary

The `safe_mint` function in the nbtc token contract mints tokens to the bridge's own account **before** verifying that the recipient account is registered. When the recipient is unregistered, the function silently returns `U128(0)` without transferring the tokens, leaving them permanently trapped in the bridge's token balance while the depositing user receives nothing. This is the direct analog of the Balancer zero-balance accounting failure: a zero/empty state (unregistered account = zero balance) causes a supply/accounting failure that traps funds.

---

### Finding Description

In `safe_mint` (`contracts/nbtc/src/lib.rs`, lines 101–124):

```rust
pub fn safe_mint(
    &mut self,
    account_id: AccountId,
    amount: U128,
    msg: Option<String>,
) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(
        account_id != self.bridge_id,
        "safe_mint: account_id must not be the bridge"
    );
    self.token.internal_deposit(&self.bridge_id, amount.into()); // ← tokens minted HERE

    if self.token.accounts.get(&account_id).is_none() {
        return PromiseOrValue::Value(U128(0));                   // ← silent return, no transfer
    }
    // ... transfer to account_id only if registered
}
```

The sequence of operations is:

1. **Line 112**: `internal_deposit(&self.bridge_id, amount)` — nBTC total supply increases by `amount`; tokens land in the bridge's own account.
2. **Lines 114–116**: If `account_id` has no registered storage slot in the token contract, the function returns `U128(0)` — **no transfer occurs, no panic, no revert**.

The tokens are now in `bridge_id`'s nBTC balance. The total nBTC supply has increased by `amount`, but the user has received zero tokens.

The documented intent of the safe-deposit flow (from `contracts/satoshi-bridge/src/api/bridge.rs`, lines 54–57) is:

> *"safe deposit: reverts the whole transaction if minting fails (no lost & found)"*

However, `safe_mint` does **not** panic on failure — it returns `U128(0)`. A cross-contract callback in the satoshi-bridge that uses `is_promise_success()` to detect failure will see the call as **successful** (no panic occurred), and will proceed to mark the deposit UTXO as verified (`verified_deposit_utxo`). Once the UTXO is in `verified_deposit_utxo`, the refund path is blocked (`contracts/satoshi-bridge/src/refund.rs`, lines 254–258):

```rust
require!(
    !self.data().verified_deposit_utxo.contains(utxo_storage_key)
        || refund_request.executed,
    "UTXO already verified via deposit, cannot refund"
);
```

The result is:
- User's BTC is permanently locked in the bridge's Bitcoin address.
- nBTC total supply is inflated by `amount` with no corresponding user balance.
- The bridge's own nBTC balance holds the orphaned tokens, which can be silently consumed by future `burn` calls for legitimate withdrawals, breaking the 1:1 BTC-backing invariant.

---

### Impact Explanation

**Critical / Medium** (depending on callback behavior):

- **Critical path**: If the satoshi-bridge callback marks the deposit UTXO as verified after `safe_mint` returns `U128(0)`, the user's BTC is permanently locked with no recourse (refund is blocked, no nBTC received). This is an unauthorized permanent loss of user funds.
- **Medium path**: Even if the callback does not mark the UTXO verified, nBTC total supply is inflated above the backed BTC amount. The orphaned tokens in `bridge_id`'s balance can be consumed by subsequent `burn` calls, permanently breaking the backed-supply invariant.

Both paths match the allowed impact scope: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds"* and *"permanent burning below backed supply"*.

---

### Likelihood Explanation

The safe-deposit flow is specifically designed for integrations like Omni Bridge where the recipient NEAR account may not have pre-registered storage in the nbtc token contract. Any user who initiates a BTC deposit via the safe-deposit path without first calling `storage_deposit` on the nbtc contract will trigger this condition. No privileged access is required — any unprivileged bridge user can reach this path by submitting a valid BTC deposit transaction with `deposit_msg.safe_deposit = Some(..)`.

---

### Recommendation

Move the account-registration check **before** the `internal_deposit` call, or panic (rather than returning `U128(0)`) when the account is unregistered, so that the cross-contract callback correctly detects failure via `is_promise_success()`:

```rust
pub fn safe_mint(...) -> PromiseOrValue<U128> {
    self.assert_bridge();
    require!(account_id != self.bridge_id, "...");

    // Check registration BEFORE minting
    require!(
        self.token.accounts.get(&account_id).is_some(),
        "safe_mint: recipient account not registered"
    );

    self.token.internal_deposit(&self.bridge_id, amount.into());
    // ... proceed with transfer
}
```

This ensures that a missing registration causes a panic, which propagates as a failed promise to the satoshi-bridge callback, triggering the intended revert behavior.

### Proof of Concept

1. Alice deposits 0.01 BTC to the bridge using the safe-deposit flow (`deposit_msg.safe_deposit = Some(..)`), targeting her NEAR account `alice.near`.
2. Alice has **not** called `storage_deposit` on the nbtc token contract, so `alice.near` has no registered storage slot.
3. The satoshi-bridge verifies the BTC transaction via the light client and calls `safe_mint("alice.near", 1_000_000, None)` on the nbtc contract.
4. `safe_mint` executes `internal_deposit(&bridge_id, 1_000_000)` — nBTC total supply increases by 1,000,000 satoshis; tokens land in `bridge_id`'s balance.
5. `safe_mint` checks `self.token.accounts.get(&"alice.near")` — returns `None`.
6. `safe_mint` returns `PromiseOrValue::Value(U128(0))` — **no panic, no transfer**.
7. The satoshi-bridge callback sees `is_promise_success() == true` and marks the UTXO in `verified_deposit_utxo`.
8. Alice's BTC is permanently locked. Alice has 0 nBTC. The bridge holds 1,000,000 orphaned nBTC. The refund path is blocked by the `verified_deposit_utxo` check. [1](#0-0) [2](#0-1) [3](#0-2) [4](#0-3)
