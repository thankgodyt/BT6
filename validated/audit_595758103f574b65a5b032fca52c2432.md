### Title
Peras Vote Replay After Garbage Collection Enables Unauthorized Certificate Forging - (`ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Storage/PerasVoteDB/Impl.hs`)

---

### Summary

The `PerasVoteDB` uses `pvdsVoteIds` as its sole deduplication guard for inbound Peras votes. `implGarbageCollect` permanently removes vote IDs from this set when a round is GC'd. After GC, any previously-seen vote for that round passes the deduplication filter again and is re-accepted, re-validated, and re-counted toward quorum. An unprivileged peer who captured old votes from the gossip network can replay them after GC to forge a fresh certificate for an already-decided round, which can then be embedded in a block and influence Peras-weighted chain selection.

---

### Finding Description

**Root cause — `implGarbageCollect` destroys the only replay barrier:** [1](#0-0) 

The GC function computes `votesToRemove` (all votes belonging to expired rounds) and then deletes their IDs from `pvdsVoteIds`:

```haskell
pvsVoteIds' =
  Foldable.foldl'
    (\set vote -> Set.delete (getPerasVoteId vote) set)
    pvdsVoteIds
    votesToRemove
```

`pvdsVoteIds` is the **only** persistent record that a vote has been seen. There is no secondary store (e.g., a bloom filter, a monotone counter, or a ledger-anchored nonce) that survives GC.

**Deduplication check in `implAddVote`:** [2](#0-1) 

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise = tryAddVote pvds voteId
```

After GC the `Set.member` check returns `False` for any previously-seen vote whose round was collected, so `tryAddVote` is called and the vote is counted again.

**Inbound path in `processVotes`:** [3](#0-2) 

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM          -- reads pvdsVoteIds (empty after GC)
    let votesNotAlreadyInDb =
          filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb  -- all replayed votes pass
  ...
  mapM_ (addVote . WithArrivalTime now) validatedVotes
```

The `alreadyInDbSTM` action reads `pvdsVoteIds` directly; after GC it no longer contains the old IDs, so every replayed vote passes the filter and is forwarded to `addVote`.

**The model explicitly acknowledges the assumption that is violated:** [4](#0-3) 

```haskell
-- NOTE: this is under the assumption that a voter doesn't cast two different
-- votes for the same round (that is, with the same ID but different body).
```

This assumption is broken by replay: the same `(roundNo, voterId)` pair is re-submitted with the same body, and the DB has no memory of it.

**`PerasVoteId` is only `(roundNo, voterId)` — no epoch, no nonce, no signature commitment:** [5](#0-4) 

```haskell
data PerasVoteId blk = PerasVoteId
  { pviRoundNo :: !PerasRoundNo
  , pviVoterId :: !PerasVoterId
  }
```

There is no epoch tag, no chain-specific nonce, and no cryptographic commitment that would make a vote from one protocol instance distinguishable from a replay in a later one.

**Network entry point:** [6](#0-5) 

The `hPerasVoteDiffusionClient` handler wires `makePerasVotePoolWriterFromChainDB` directly to the inbound object-diffusion mini-protocol, making the path reachable by any unprivileged peer.

---

### Impact Explanation

After GC removes a round's vote IDs, an attacker who captured those votes from the gossip network can replay them. If enough votes are replayed to exceed the quorum threshold, `updatePerasRoundVoteStates` forges a fresh `ValidatedPerasCert` for the old round: [7](#0-6) 

This certificate can be embedded in a new block. Peras chain selection uses certificate boosts to prefer chains; a fraudulently forged certificate for a round within the cert-expiry window (`_A` rounds, governed by `perasCertMaxRounds`) causes honest nodes to assign extra weight to the attacker's chain, enabling a chain-selection manipulation that bypasses the intended Peras security assumptions.

The `latestCertSeenIsNotExpired` predicate: [8](#0-7) 

only filters certificates older than `_A` rounds; replayed votes for a round within that window produce a certificate that passes this check.

**Impact class:** High — chain-selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain by replaying legitimately-signed votes after GC clears the deduplication barrier.

---

### Likelihood Explanation

- Peras votes are broadcast to all peers via the object-diffusion mini-protocol; any observer can store them.
- GC is triggered automatically by the background thread whenever blocks are copied to the ImmutableDB.
- The attacker needs no special privileges, no key material, and no stake — only a cache of previously-observed votes.
- The attack window is bounded by `_A` (cert max rounds), but that window is deliberately wide to tolerate network delays.

**Note:** The current production wiring passes `PerasVoteStakeDistr mempty` as the stake distribution, causing `validatePerasVote` to reject all votes today: [9](#0-8) 

This is an acknowledged TODO placeholder. The vulnerability becomes fully exploitable as soon as the real stake distribution is plumbed in, which is the stated next step for Peras integration.

---

### Recommendation

1. **Persist vote IDs across GC.** Maintain a separate, compactly-encoded set (e.g., a per-epoch bloom filter or a monotone high-water mark per voter) that is not cleared by GC. A vote whose `(epoch, roundNo, voterId)` tuple has been seen before must be rejected even after the full round state is collected.

2. **Bind votes to a chain-specific nonce.** Include the epoch nonce (already computed in Praos/TPraos) in the signed vote payload so that a vote from epoch E cannot be replayed in epoch E+1 even if the round number is the same.

3. **Verify cryptographic signatures before deduplication.** The `validatePerasVote` stub currently performs no signature check: [10](#0-9) 

Without signature verification, the deduplication guard is the only barrier against forged or replayed votes. Completing the signature check (tracked in issue #120) would independently prevent replay of votes whose signing key has since been rotated.

---

### Proof of Concept

```
1. Connect to a Cardano node running Peras (private testnet).
2. Observe and store all PerasVote messages for round R broadcast
   via the PerasVoteDiffusion mini-protocol.
3. Wait until the background GC thread fires for a slot past the
   youngest target of round R's votes (triggered by copyToImmutableDB).
4. Reconnect and re-submit the stored votes for round R via the
   PerasVoteDiffusion inbound handler.
5. processVotes reads alreadyInDbSTM → pvdsVoteIds no longer contains
   round-R IDs → all replayed votes pass the filter.
6. validatePerasVote accepts each vote (voter is in stake distribution).
7. implAddVote re-inserts the votes; updatePerasRoundVoteStates re-counts
   stake; quorum is reached; a fresh ValidatedPerasCert for round R is forged.
8. The attacker includes this certificate in a block on their fork.
9. Honest nodes receiving this block see a valid Peras certificate for
   round R (within the _A-round expiry window) and assign it extra chain
   weight, causing them to prefer the attacker's fork over the canonical chain.
```
