### Title
Multiple Simultaneous RBF PendingSign Entries Allowed Per Original Withdraw — (`contracts/satoshi-bridge/src/rbf/withdraw.rs`)

### Summary

`internal_withdraw_rbf` contains no guard preventing a second (or third, up to `rbf_num_limit`) RBF from being created while a prior RBF for the same original tx is still in `PendingSign`. The only limit is the `rbf_txs.len() <= rbf_num_limit` check in `set_rbf_pending_info`. With `rbf_num_limit >= 2`, the original withdraw owner can create `rbf_num_limit` simultaneous `PendingSign` RBF entries, all of which will be signed by MPC and all of which spend the same UTXOs.

The question's specific sub-claim — "all with the **same** gas_fee" — is **blocked** by `check_withdraw_chain_specific`, which enforces a strict gas increase. However, the broader invariant violation (multiple simultaneous PendingSign RBFs) is reachable with incrementally higher gas fees.

---

### Finding Description

**Entrypoint**: `internal_withdraw_rbf` (called via `withdraw_rbf_chain_specific` → public API).

**Guard that is present — gas increase check**: [1](#0-0) 

`check_withdraw_chain_specific` requires `gas_fee > max_gas_fee`. After each successful call, `update_max_gas_fee` raises the stored ceiling: [2](#0-1) 

So same-gas-fee submissions are rejected. But with gas_fee₁ < gas_fee₂ < … < gas_feeₙ, all `n ≤ rbf_num_limit` calls succeed.

**Guard that is missing — no PendingSign check**:

`internal_withdraw_rbf` only asserts the **original** tx is in `PendingVerify`: [3](#0-2) 

There is no check that inspects `rbf_txs` for existing `PendingSign` entries before creating a new one.

**The only limit is `rbf_num_limit`**: [4](#0-3) 

`rbf_txs.len() <= rbf_num_limit` is checked **after** insertion, so up to `rbf_num_limit` simultaneous RBF entries (each with a distinct `btc_pending_id` derived from distinct PSBT outputs) are allowed into `btc_pending_infos` in `PendingSign` state.

`rbf_num_limit` is a configurable `u8` field: [5](#0-4) 

---

### Impact Explanation

All `rbf_num_limit` RBF entries proceed through MPC signing (`sign_btc_transaction_callback`) and transition to `PendingVerify`. They all spend the **same UTXOs**. Only one can be confirmed on-chain. The remaining entries become stale `PendingVerify` records in `btc_pending_infos` that require explicit operator cleanup via `internal_clear_invalid_pending_verify_rbf`: [6](#0-5) 

This is a **Medium** impact: bypass of bridge policy (the intended one-RBF-pending-sign-at-a-time invariant), stuck/inconsistent bridge state requiring operator intervention, and unnecessary MPC signing load. There is no direct fund theft — the user is the original withdraw owner and cannot redirect funds to a third party through this path.

---

### Likelihood Explanation

Reachable by the original withdraw owner with no special privileges. Requires `rbf_num_limit >= 2` (the default is a configurable value; any value ≥ 2 enables the issue) and the ability to construct PSBTs with distinct outputs (different amounts or change splits) to produce distinct `btc_pending_id`s. The gas-fee increase requirement adds friction but does not prevent the attack.

---

### Recommendation

Before inserting a new RBF entry, check whether any existing entry in `rbf_txs` for the same original tx is still in `PendingSign` stage. Reject the new submission until the prior one has been signed (transitioned to `PendingVerify`). Alternatively, enforce a strict "at most one PendingSign RBF per original tx" invariant inside `set_rbf_pending_info` by iterating the existing `rbf_txs` set and asserting none are in `PendingSign`.

---

### Proof of Concept

1. User initiates a withdraw; original tx enters `PendingVerify`.
2. User calls `withdraw_rbf` with PSBT₁ (gas_fee = F₁ > max_gas_fee). `max_gas_fee` updated to F₁. RBF₁ inserted into `btc_pending_infos` (PendingSign) and `rbf_txs`.
3. User calls `withdraw_rbf` with PSBT₂ (gas_fee = F₂ > F₁, different output amounts → different `btc_pending_id`). `max_gas_fee` updated to F₂. RBF₂ inserted. `rbf_txs.len() == 2 <= rbf_num_limit`. No rejection.
4. Repeat up to `rbf_num_limit` times.
5. MPC signs all entries. All transition to `PendingVerify`.
6. User broadcasts one; the rest are stale signed transactions spending the same UTXOs, permanently stuck in `btc_pending_infos` until operator calls `clear_invalid_pending_verify_rbf` for each.

**Note**: The question's "same gas_fee" variant is **not reachable** — `check_withdraw_chain_specific` blocks it. The reachable variant uses strictly increasing gas fees. [7](#0-6) [8](#0-7)

    pub(crate) fn check_withdraw_chain_specific(
        original_tx_btc_pending_info: &BTCPendingInfo,
        gas_fee: u128,
    ) {
        // Ensure that the RBF transaction pays more gas than the previous transaction.
        let max_gas_fee = original_tx_btc_pending_info.get_max_gas_fee();
        let additional_gas_amount = gas_fee.saturating_sub(max_gas_fee);
        require!(additional_gas_amount > 0, "No gas increase.");
    }

    pub fn update_max_gas_fee(&mut self, gas_fee: u128) {
        match self.state.borrow_mut() {
            PendingInfoState::WithdrawOriginal(state) => {
                state.max_gas_fee = gas_fee;
                state.last_rbf_time_sec = Some(nano_to_sec(env::block_timestamp()));
            }
            PendingInfoState::ActiveUtxoManagementOriginal(state) => {
                state.max_gas_fee = gas_fee;
                state.last_rbf_time_sec = Some(nano_to_sec(env::block_timestamp()));
            }
            _ => env::panic_str("Not original tx"),
        }
    }

    pub fn internal_withdraw_rbf(
        &mut self,
        account_id: &AccountId,
        original_btc_pending_verify_id: String,
        withdraw_rbf_psbt: PsbtWrapper,
        _predecessor_account_id: AccountId,
    ) -> String {
        let original_tx_btc_pending_info =
            self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
        require!(
            &original_tx_btc_pending_info.account_id == account_id,
            "Not allow"
        );
        original_tx_btc_pending_info.assert_not_canceled();
        original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();

        let mut btc_pending_info = init_rbf_btc_pending_info(
            original_tx_btc_pending_info,
            PendingInfoState::WithdrawUserRbf(RbfState {
                stage: PendingInfoStage::PendingSign,
                original_tx_id: original_btc_pending_verify_id.clone(),
            }),
        );
        let (actual_received_amount, gas_fee) =
            self.check_withdraw_rbf_psbt_valid(original_tx_btc_pending_info, &withdraw_rbf_psbt);
        btc_pending_info.gas_fee = gas_fee;
        btc_pending_info.actual_received_amount = actual_received_amount;
        btc_pending_info.burn_amount = actual_received_amount + gas_fee;
        Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);

        self.internal_unwrap_mut_btc_pending_info(&original_btc_pending_verify_id)
            .update_max_gas_fee(gas_fee);
        self.set_rbf_pending_info(
            &original_btc_pending_verify_id,
            btc_pending_info,
            withdraw_rbf_psbt,
            false,
        )
    }

    pub fn set_rbf_pending_info(
        &mut self,
        original_btc_pending_verify_id: &str,
        mut btc_pending_info: BTCPendingInfo,
        psbt: PsbtWrapper,
        is_cancel: bool,
    ) -> String {
        let rbf_psbt_hex = psbt.serialize();
        let btc_pending_id = psbt.get_pending_id();
        btc_pending_info.btc_pending_id.clone_from(&btc_pending_id);
        btc_pending_info.psbt_hex = rbf_psbt_hex;
        require!(
            self.data_mut()
                .btc_pending_infos
                .insert(btc_pending_id.clone(), btc_pending_info.into())
                .is_none(),
            "pending info already exist"
        );
        let rbf_txs = self
            .data_mut()
            .rbf_txs
            .entry(original_btc_pending_verify_id.to_owned())
            .or_default();
        require!(rbf_txs.insert(btc_pending_id.clone()), "Rbf already exist");
        if !is_cancel {
            require!(
                rbf_txs.len() <= self.internal_config().rbf_num_limit.into(),
                "Exceed rbf_num_limit"
            );
        }
        btc_pending_id
    }
