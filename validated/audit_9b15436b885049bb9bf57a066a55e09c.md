### Title
Unauthenticated `sign_btc_transaction` with attacker-controlled `key_version` permanently freezes withdrawal funds — (`contracts/satoshi-bridge/src/api/chain_signatures.rs`, `contracts/satoshi-bridge/src/chain_signature.rs`)

### Summary

`sign_btc_transaction` is a public, payable function with no caller-identity check. Any account can call it for any pending sign ID with an arbitrary `key_version`. The chain-signatures contract will sign the payload with the key corresponding to that version. The callback stores the resulting signature without verifying it against the expected public key. If the attacker calls first (or wins the parallel-callback race), an invalid signature is committed to the PSBT, the state transitions irreversibly to `PendingVerify`, and the withdrawal funds are permanently frozen.

### Finding Description

**Step 1 — No access control on the entrypoint.**
`sign_btc_transaction` checks only that the pending info exists and is in `PendingSign` stage. It never checks `env::predecessor_account_id() == btc_pending_info.account_id`. [8](#0-7) 

**Step 2 — Attacker calls first with wrong `key_version`.**
The attacker observes the pending sign ID (publicly readable via view functions), then calls `sign_btc_transaction(victim_id, sign_index, key_version=1)`. The initial guard `signatures[sign_index].is_none()` passes because no callback has run yet. A sign promise is dispatched to the chain-signatures contract requesting a signature under key₁. [2](#0-1) 

**Step 3 — Callback stores the wrong-key signature without validation.**
`sign_btc_transaction_callback` receives the signature from key₁. It derives the public key using `generate_btc_public_key(path)` — which uses only the path, not `key_version`, so it always returns the public key for key₀. It then calls `psbt.save_signature(sign_index, sig_from_key1, pubkey_for_key0)`. No cryptographic check is performed. [9](#0-8) 

**Step 4 — PSBT is finalized with an invalid witness.**
`save_signature` writes `Witness::p2wpkh(sig_from_key1, pubkey_for_key0)` into the PSBT input. `extract_tx_bytes_with_sign` serializes this without any validation. The resulting `tx_bytes_with_sign` contains a Bitcoin transaction whose witness will fail script validation on the Bitcoin network. [5](#0-4) 

**Step 5 — State transitions irreversibly to `PendingVerify`.**
`to_pending_verify_stage()` is called, `btc_pending_sign_ids` is cleared, and the entry moves to `btc_pending_verify_list`. There is no code path that allows re-signing once the stage is `PendingVerify`. The user's nBTC has already been burned; the BTC is now locked in bridge UTXOs with no valid spending transaction. [10](#0-9) 

**Parallel-callback variant (same `sign_index`).**
If the legitimate caller has already dispatched their sign promise, the attacker can still submit a parallel call in the same block. Both pass the pre-callback `is_none()` check. Whichever callback lands first wins; the second is rejected with "Already signed". If the attacker's callback lands first (attacker submitted earlier in the block), the invalid signature is committed. [11](#0-10) 

### Impact Explanation

The user's nBTC is burned at withdrawal initiation. The bridge UTXOs are locked to the pending transaction. Once the PSBT is finalized with an invalid witness and the state moves to `PendingVerify`, there is no re-sign path. The BTC is permanently frozen in the bridge's UTXOs. This matches: *"Significant loss, theft, destruction, or permanent locking of user or protocol funds"* and *"Chain-signature, PSBT, or transaction-construction failure that enables unauthorized spending or redirection of bridge-controlled funds."*

### Likelihood Explanation

- The pending sign ID is publicly readable from contract state.
- The attacker needs no special role, no leaked key, and no privileged access.
- The simplest form of the attack (call before the legitimate caller) requires only submitting a transaction before the victim's signing call is processed — a one-block window that is trivially achievable.
- The parallel-callback race is also realistic since NEAR cross-contract calls resolve asynchronously across blocks.

### Recommendation

1. **Add caller authentication**: In `sign_btc_transaction`, require `env::predecessor_account_id() == btc_pending_info.account_id` (or a whitelisted relayer set).
2. **Validate the signature in the callback**: After `psbt.save_signature`, verify the ECDSA signature against the expected public key before committing it to state.
3. **Bind `key_version` to the pending info**: Store the expected `key_version` in `BTCPendingInfo` at creation time and assert it matches in both `internal_sign_btc_transaction` and `sign_btc_transaction_callback`.

### Proof of Concept

```
# 1. Alice initiates a withdrawal; a BTCPendingInfo with id=TX_ID is created in PendingSign.
# 2. Attacker observes TX_ID via get_btc_pending_infos_paged().
# 3. Attacker calls (before Alice's relayer does):
near call <bridge> sign_btc_transaction \
  '{"btc_pending_sign_id":"TX_ID","sign_index":0,"key_version":1}' \
  --accountId attacker.near --deposit 1

# 4. Chain-signatures contract signs the payload with key_version=1 (a different key).
# 5. sign_btc_transaction_callback stores sig_from_key1 paired with pubkey_for_key0.
# 6. If TX_ID has only one input, is_all_signed() == true:
#    - tx_bytes_with_sign is set (invalid Bitcoin tx)
#    - state → PendingVerify
#    - btc_pending_sign_ids cleared
# 7. Alice's nBTC is burned; BTC is permanently frozen.
# 8. Any subsequent sign_btc_transaction call for TX_ID fails: "Not pending sign stage".
```

    pub fn sign_btc_transaction(
        &mut self,
        btc_pending_sign_id: String,
        sign_index: usize,
        key_version: u32,
    ) -> PromiseOrValue<bool> {
        let btc_pending_info = self.internal_unwrap_btc_pending_info(&btc_pending_sign_id);
        btc_pending_info.assert_pending_sign();
        if let Some(original_tx_id) = btc_pending_info.get_original_tx_id() {
            if !self.check_btc_pending_info_exists(original_tx_id) {
                require!(
                    self.internal_unwrap_mut_account(&btc_pending_info.account_id.clone())
                        .btc_pending_sign_ids
                        .remove(&btc_pending_sign_id),
                    "Internal error"
                );
                self.internal_remove_btc_pending_info(&btc_pending_sign_id);
                return PromiseOrValue::Value(true);
            }
        }
        self.internal_sign_btc_transaction(btc_pending_sign_id, sign_index, key_version)
            .into()
    }
