### Title
`cancel_withdraw` Blocked by User-Filled Pending Sign Slot via `withdraw_rbf` — (`contracts/satoshi-bridge/src/api/bridge.rs`)

### Summary
`cancel_withdraw` calls `require_pending_sign_capacity(&user_account_id)` against the **withdrawal owner's** account before executing any cancel logic. A user can call `withdraw_rbf` (public, no role gate) after their original withdrawal is signed, filling their pending sign slot to the limit. This causes every subsequent operator `cancel_withdraw` call to panic, temporarily blocking the DAO/Operator from canceling a stuck withdrawal.

### Finding Description
In `contracts/satoshi-bridge/src/api/bridge.rs`, `cancel_withdraw` retrieves the original withdrawal owner's account ID and immediately calls `require_pending_sign_capacity(&user_account_id)`:

```rust
// api/bridge.rs:287-291
let user_account_id = self
    .internal_unwrap_btc_pending_info(&original_btc_pending_verify_id)
    .account_id
    .clone();
self.require_pending_sign_capacity(&user_account_id);
```

`require_pending_sign_capacity` panics if `pending_sign_count() >= get_max_pending_sign_txs()`. The default per-account limit is **1** (`unwrap_or(1)` in `get_max_pending_sign_txs`).

The public `withdraw_rbf` function also calls `require_pending_sign_capacity` before inserting a new RBF pending sign ID. Once the original tx is signed (moved to `PendingVerify`, removed from `btc_pending_sign_ids`), the user's count drops to 0, allowing one `withdraw_rbf` call that brings the count back to 1. `set_rbf_pending_info` never removes the old pending sign ID; only `sign_btc_transaction_callback` does so when all inputs are signed.

With count = 1 and max = 1, the operator's `cancel_withdraw` panics at the capacity check. The cancel logic (`internal_cancel_withdraw`, `do_cancel`, `cancel_rbf_reserved`) is never reached, so the original tx remains uncanceled and the user can maintain the block indefinitely by not signing the RBF.

### Impact Explanation
The DAO/Operator invariant "can always cancel a stuck withdrawal" is broken. A user can keep a withdrawal permanently in limbo: the original tx is signed but unconfirmed on Bitcoin, the operator cannot issue a cancel-RBF, and the user's funds remain locked in the bridge's UTXO set until the user cooperates. This matches the scoped Medium impact: attacker-triggered temporary locking of bridged funds requiring operator intervention.

### Likelihood Explanation
Any user with a pending withdrawal can trigger this with a single `withdraw_rbf` call after signing their original tx. No special privileges, no leaked keys, no external dependencies. The default limit of 1 makes this trivially reachable. The user has a direct incentive to do this if they want to prevent the operator from reclaiming the UTXO (e.g., to avoid a cancel fee or to stall the protocol).

### Recommendation
Remove `require_pending_sign_capacity` from `cancel_withdraw` (and `cancel_active_utxo_management`). The capacity check exists to prevent users from flooding the signing queue; it should not gate operator/DAO cancel paths. The cancel operation creates exactly one new pending sign entry, so the operator should be allowed to exceed the user's normal limit when performing a protocol-initiated cancel. Alternatively, skip the check when the caller holds `Role::DAO` or `Role::Operator`.
