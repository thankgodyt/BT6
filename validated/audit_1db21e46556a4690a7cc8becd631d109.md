### Title
Excess Attached NEAR Deposit Permanently Locked in Refund Functions - (File: contracts/satoshi-bridge/src/refund.rs)

### Summary
The `internal_request_refund` and `resolve_execute_refund_timelock` functions accept attached NEAR deposits using a `>=` comparison against a required minimum, but never refund the excess. Any NEAR sent above the required storage deposit is permanently locked in the contract with no withdrawal path.

### Finding Description
In `refund.rs`, two functions gate execution on a minimum attached deposit:

- `internal_request_refund` (line 147): `require!(env::attached_deposit() >= self.required_balance_for_request_refund(), ...)`
- `resolve_execute_refund_timelock` (line 203): `require!(env::attached_deposit() >= self.required_balance_for_execute_refund(), ...)` [1](#0-0) [2](#0-1) 

Neither function contains any logic to compute the excess (`attached - required`) and return it to the caller via `Promise::new(predecessor).transfer(excess)`. The full attached deposit is consumed by the contract. Because these are `pub(crate)` helpers called from `#[payable]` public API entrypoints in `api/bridge.rs`, any user who attaches more than the exact required amount loses the difference permanently. [3](#0-2) 

The `ContractData` struct tracks `lost_found` for nBTC accounting but has no analogous ledger for excess NEAR storage deposits, and no public function exists to sweep or reclaim them. [4](#0-3) 

### Impact Explanation
Any NEAR attached above the required storage deposit is permanently locked inside the contract. Users cannot recover it. Over time, across many `request_refund` and `execute_refund` calls, this accumulates as irrecoverable user funds. This matches the **Medium** impact class: harmful smart-contract behavior causing permanent loss of user funds without direct theft of bridged BTC/nBTC.

### Likelihood Explanation
Likelihood is medium-to-high. Users and integrators routinely over-attach NEAR to cover storage costs when the exact required amount is not known in advance or changes between calls. The `required_balance_for_request_refund` value depends on runtime storage pricing, making exact attachment difficult. Any over-payment is silently absorbed.

### Recommendation
After the minimum deposit check, compute the excess and refund it to the caller before proceeding:

```rust
let required = self.required_balance_for_request_refund();
let attached = env::attached_deposit();
require!(attached >= required, "Insufficient deposit for storage");
let excess = attached.saturating_sub(required);
if excess > NearToken::from_yoctonear(0) {
    Promise::new(env::predecessor_account_id()).transfer(excess);
}
```

Apply the same pattern in `resolve_execute_refund_timelock`.

### Proof of Concept
1. Attacker/user calls the public `request_refund` entrypoint (in `api/bridge.rs`) with a valid proof and attaches `required_balance_for_request_refund() + 1_000_000_000_000_000_000_000_000` yoctoNEAR (1 extra NEAR).
2. `internal_request_refund` checks `attached >= required` — passes.
3. No refund of the 1 NEAR excess is issued anywhere in the call chain.
4. The 1 NEAR is permanently locked in the contract balance with no recovery path.
5. Repeat across many users/calls; locked NEAR accumulates indefinitely. [5](#0-4)

impl Contract {
    /// Submit a refund request. Verifies the BTC transaction via Light Client first.
    /// If `deposit_msg.refund_address` is set, it must match the provided `refund_address`.
    /// If `deposit_msg.refund_address` is None, the provided `refund_address` is used.
    #[allow(clippy::too_many_arguments)]
    pub(crate) fn internal_request_refund(
        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,
    ) -> Promise {
        require!(
            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"
        );
        require!(
            tx_bytes.0.len() <= MAX_REQUEST_REFUND_TX_BYTES,
            "tx_bytes too large for refund request"
        );
        if let Some(msg_refund_address) = &deposit_msg.refund_address {
            require!(
                msg_refund_address == &refund_address,
                "refund_address does not match deposit_msg.refund_address"
            );
        }

        let transaction =
            crate::WrappedTransaction::decode(&tx_bytes.0, &self.internal_config().chain)
                .expect("Deserialization tx_bytes failed");
        let tx_id = transaction.compute_txid().to_string();

        let config = self.internal_config();
        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());
        let confirmations = self.get_confirmations(config, deposit_amount);

        self.verify_transaction_inclusion_promise(
            config.btc_light_client_account_id.clone(),
            tx_id,
            proof.tx_block_blockhash,
            proof.tx_index,
            proof.merkle_proof,
            Some((proof.coinbase_tx_id, proof.coinbase_merkle_proof)),
            confirmations,
        )
        .then(
            Self::ext(env::current_account_id())
                .with_static_gas(GAS_FOR_REQUEST_REFUND_CALLBACK)
                .request_refund_callback(deposit_msg, refund_address, tx_bytes, vout, gas_fee),
        )
    }
