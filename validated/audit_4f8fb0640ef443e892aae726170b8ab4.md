### Title
Missing Ownership Check in `internal_cancel_withdraw` Allows Any User to Cancel Another User's Withdrawal — (File: `contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs`)

---

### Summary

`internal_cancel_withdraw` accepts an `_account_id` parameter but never uses it to verify that the caller owns the pending withdrawal being cancelled. Any unprivileged NEAR account can force-cancel another user's legitimate withdrawal after the timelock expires.

---

### Finding Description

The vulnerability class from H-01 is: a state-modifying function performs partial validation (checks that *some* condition is met) but omits the critical ownership check that ties the caller to the specific resource being modified.

In `internal_cancel_withdraw`, the `_account_id` parameter is explicitly unused (Rust underscore prefix convention):

```rust
// contracts/satoshi-bridge/src/rbf/cancel_withdraw.rs
pub fn internal_cancel_withdraw(
    &mut self,
    _account_id: &AccountId,          // ← unused, never checked
    original_btc_pending_verify_id: String,
    cancel_withdraw_rbf_psbt: PsbtWrapper,
    predecessor_account_id: AccountId,
) -> String {
    let original_tx_btc_pending_info =
        self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
    require!(
        nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
            > self.internal_config().max_btc_tx_pending_sec,
        "Please wait user rbf"
    );
    original_tx_btc_pending_info.assert_not_canceled();
    original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();
    // ... no check: original_tx_btc_pending_info.account_id == _account_id
``` [1](#0-0) 

The function only checks:
1. The timelock has elapsed (`max_btc_tx_pending_sec`).
2. The pending info is not already cancelled.
3. The pending info is a valid withdraw-original tx.

It never verifies that `original_tx_btc_pending_info.account_id` equals the caller's account. Compare this directly with `internal_withdraw_rbf`, which performs the correct ownership check:

```rust
// contracts/satoshi-bridge/src/rbf/withdraw.rs
require!(
    &original_tx_btc_pending_info.account_id == account_id,
    "Not allow"
);
``` [2](#0-1) 

The ownership check exists in `internal_withdraw_rbf` but is absent in `internal_cancel_withdraw`, making the asymmetry a clear oversight.

---

### Impact Explanation

When `internal_cancel_withdraw` executes, it:
- Calls `do_cancel` on the original pending info, marking it cancelled.
- Creates a new cancel-RBF PSBT that sweeps the UTXOs back to the bridge's change address.
- Sets `burn_amount = gas_fee` (only gas is burned; the rest returns to the bridge). [3](#0-2) 

An attacker who force-cancels a victim's withdrawal:
- Causes the victim's BTC withdrawal to be aborted after the timelock.
- Forces the victim's funds into a cancelled state requiring operator intervention or re-initiation.
- Can repeatedly grief any user whose withdrawal has passed `max_btc_tx_pending_sec`.

**Impact class**: Medium — attacker-triggered temporary locking of bridged funds / forced stuck bridge state requiring operator intervention.

---

### Likelihood Explanation

- The entry point is public and callable by any NEAR account after the timelock expires.
- No privileged role is required.
- The attacker only needs to know the `original_btc_pending_verify_id` (a transaction ID, observable on-chain via events) and supply a valid cancel-RBF PSBT.
- The timelock (`max_btc_tx_pending_sec`) is a delay, not a barrier — it merely sets the earliest moment the attack can execute.

---

### Recommendation

Add the same ownership check that `internal_withdraw_rbf` already performs:

```rust
require!(
    &original_tx_btc_pending_info.account_id == _account_id,
    "Not the owner of this pending withdrawal"
);
``` [4](#0-3) 

Rename `_account_id` to `account_id` once the check is added so the compiler does not suppress the unused-variable warning.

---

### Proof of Concept

1. Alice calls `ft_transfer_call` to initiate a withdrawal. A `BTCPendingInfo` entry is created with `account_id = Alice`, keyed by `original_btc_pending_verify_id = TX_ID_A`.
2. The bridge emits a `GenerateBtcPendingInfo` event revealing `TX_ID_A`.
3. Bob waits until `block_timestamp - create_time_sec > max_btc_tx_pending_sec`.
4. Bob constructs a valid cancel-RBF PSBT (all outputs to the bridge's change address, satisfying `check_psbt_output_all_change_address`).
5. Bob calls the public cancel-withdraw entry point with `original_btc_pending_verify_id = TX_ID_A`.
6. `internal_cancel_withdraw` is invoked with `_account_id = Bob` — the parameter is ignored, no ownership check fires.
7. Alice's withdrawal is cancelled; her BTC is swept back to the bridge's change address; Alice's withdrawal is stuck until she re-initiates. [5](#0-4) [6](#0-5)

    pub fn internal_cancel_withdraw(
        &mut self,
        _account_id: &AccountId,
        original_btc_pending_verify_id: String,
        cancel_withdraw_rbf_psbt: PsbtWrapper,
        predecessor_account_id: AccountId,
    ) -> String {
        let original_tx_btc_pending_info =
            self.internal_unwrap_btc_pending_info(&original_btc_pending_verify_id);
        require!(
            nano_to_sec(env::block_timestamp()) - original_tx_btc_pending_info.create_time_sec
                > self.internal_config().max_btc_tx_pending_sec,
            "Please wait user rbf"
        );
        original_tx_btc_pending_info.assert_not_canceled();
        original_tx_btc_pending_info.assert_withdraw_original_pending_verify_tx();

        let mut btc_pending_info = init_rbf_btc_pending_info(
            original_tx_btc_pending_info,
            PendingInfoState::WithdrawCancelRbf(RbfState {
                stage: PendingInfoStage::PendingSign,
                original_tx_id: original_btc_pending_verify_id.clone(),
            }),
        );
        let (actual_received_amount, gas_fee) = self.check_cancel_withdraw_rbf_psbt_valid(
            original_tx_btc_pending_info,
            &cancel_withdraw_rbf_psbt,
        );

        btc_pending_info.gas_fee = gas_fee;
        btc_pending_info.burn_amount = gas_fee;
        btc_pending_info.actual_received_amount = actual_received_amount;
        Self::check_withdraw_chain_specific(original_tx_btc_pending_info, gas_fee);
        let excess_gas_fee = gas_fee
            .saturating_sub(btc_pending_info.transfer_amount - btc_pending_info.withdraw_fee);
        if excess_gas_fee > 0 {
            require!(
                self.acl_has_role(Role::DAO.into(), predecessor_account_id),
                "gas fee exceeds the user's balance, only the owner is allowed to cancel"
            );
            require!(
                self.data().cur_available_protocol_fee >= excess_gas_fee,
                "Insufficient protocol fee"
            );
            self.data_mut().cur_available_protocol_fee -= excess_gas_fee;
            self.data_mut().cur_reserved_protocol_fee += excess_gas_fee;
        }
        self.internal_unwrap_mut_btc_pending_info(&original_btc_pending_verify_id)
            .do_cancel(gas_fee, excess_gas_fee);
        self.set_rbf_pending_info(
            &original_btc_pending_verify_id,
            btc_pending_info,
            cancel_withdraw_rbf_psbt,
            true,
        )
    }
