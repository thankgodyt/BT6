### Title
Operator `cancel_withdraw` Blocked by User-Controlled `pending_sign_count` — (`contracts/satoshi-bridge/src/api/bridge.rs`)

---

### Summary

`cancel_withdraw` calls `require_pending_sign_capacity(&user_account_id)` — checking the **withdrawal owner's** pending-sign slot count, not the caller's. A user can fill that slot via a second public `ft_on_transfer` Withdraw call, causing the operator's cancellation to panic and leaving the original withdrawal's UTXOs stuck.

---

### Finding Description

`cancel_withdraw` in `bridge.rs` resolves the withdrawal owner's account ID and immediately gates on their pending-sign capacity: [1](#0-0) 

`require_pending_sign_capacity` panics with `"Too many pending sign transactions"` when `pending_sign_count() >= max_pending_sign_txs`: [2](#0-1) 

The default per-account limit is **1**: [3](#0-2) 

`pending_sign_count()` counts entries in `btc_pending_sign_ids`: [4](#0-3) 

When the relayer fully signs W1, `sign_btc_transaction_callback` removes W1 from `btc_pending_sign_ids` and moves it to `btc_pending_verify_list`: [5](#0-4) 

At that point the user's `btc_pending_sign_ids` is **empty** (count = 0), so a second `ft_on_transfer` Withdraw call passes the capacity check in `create_btc_pending_info` (`0 < 1`): [6](#0-5) 

and inserts W2 into `btc_pending_sign_ids`: [7](#0-6) 

Now the user's count is 1. When the operator calls `cancel_withdraw(W1)`, line 291 evaluates `1 < 1` → false → panic. The operator call reverts entirely.

The same effect is achievable via `withdraw_rbf(W1)`, which also inserts a new RBF entry into `btc_pending_sign_ids` (via `define_rbf_method!`): [8](#0-7) 

---

### Impact Explanation

While the block is not cryptographically permanent (the relayer will eventually sign W2, clearing the slot), the user can sustain it by repeatedly creating new withdrawals as each one is signed. During the window, the operator cannot issue the cancel-RBF PSBT, leaving the original withdrawal's bridge UTXOs in a stuck `PendingVerify` state that cannot be reclaimed. This matches **Medium — attacker-triggered temporary locking of bridged funds / stuck bridge state requiring operator intervention**.

---

### Likelihood Explanation

The attack requires only two sequential public calls (`ft_on_transfer` Withdraw × 2, or `ft_on_transfer` + `withdraw_rbf`) and a small amount of nBTC. No privileged access, leaked keys, or external dependencies are needed. Any user who wants to prevent their own withdrawal from being cancelled can execute this trivially.

---

### Recommendation

Remove `require_pending_sign_capacity(&user_account_id)` from `cancel_withdraw` (and analogously from `cancel_active_utxo_management`). The capacity guard exists to rate-limit **new** user-initiated pending sign entries; it has no legitimate role in operator-initiated cancellation. The cancel-RBF PSBT must always be creatable by DAO/Operator regardless of the user's current pending-sign count.

// Step 1: alice initiates W1 via ft_on_transfer(Withdraw{...})

//   capacity check: 0 < 1 → passes
//   → alice.btc_pending_sign_ids = {W2}

// Step 4: operator calls cancel_withdraw(W1)
//   require_pending_sign_capacity(&alice):
//     pending_sign_count() = 1, max = 1
//     1 < 1 → false → PANIC "Too many pending sign transactions"
//
// cancel_withdraw reverts; W1 UTXOs remain stuck.
