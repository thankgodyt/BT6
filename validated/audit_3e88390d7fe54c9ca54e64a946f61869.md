### Title
Peras Vote DB First-Caller-Wins Registration with Missing Signature Validation Permanently Blocks Legitimate Votes and Certificate Generation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

### Summary

The `processVotes` inbound handler enforces a strict first-caller-wins rule: only the first vote per `(voterId, roundNo)` pair is ever accepted into the `PerasVoteDB`. The production `validatePerasVote` implementation is an acknowledged stub that performs **no signature verification** — it accepts any vote whose `voterId` appears in the stake distribution. An unprivileged peer can therefore flood the node with structurally valid but forged votes for every committee member before honest voters send their own, permanently occupying every slot in the DB for that round and preventing quorum from being reached. This blocks Peras certificate generation and degrades chain selection to Praos-only, removing the Peras boost from the honest chain.

### Finding Description

**Root cause — missing signature field and stub validation**

The `PerasVote blk` type carries no cryptographic signature:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
```

The production `validatePerasVote` implementation (the only instance, via the blanket `StandardHash blk => BlockSupportsPeras blk`) is an explicit stub:

```haskell
-- TODO: perform actual validation against all
-- possible 'PerasValidationErr' variants
-- see https://github.com/tweag/cardano-peras/issues/120
validatePerasVote _params stakeDistr vote
  | Just stake <- lookupPerasVoteStake vote stakeDistr =
      Right ValidatedPerasVote{ vpvVote = vote, vpvVoteStake = stake }
  | otherwise =
      Left PerasValidationErr
```

Validation succeeds for any vote whose `pvVoteVoterId` is present in the stake distribution — no signature, no eligibility proof, no round-range check.

**Root cause — first-caller-wins deduplication**

`implAddVote` in `PerasVoteDB/Impl.hs` silently drops any vote whose `PerasVoteId` is already in `pvdsVoteIds`:

```haskell
addOrIgnoreVote pvds voteId
  | Set.member voteId (pvdsVoteIds pvds) = voteAlreadyInDB pvds
  | otherwise                            = tryAddVote pvds voteId
```

`PerasVoteId` is `(pviRoundNo, pviVoterId)`. Once a vote for voter V in round R is stored, every subsequent vote from V for round R — including the honest one — is silently discarded.

**Inbound path**

`processVotes` in `PerasVote.hs` is the network-facing entry point called by both `makePerasVotePoolWriterFromVoteDB` and `makePerasVotePoolWriterFromChainDB`:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb =
          filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  ...
```

The duplicate check and validation are atomic, but the `addVote` calls happen outside the transaction. More critically, the filter uses the DB snapshot taken at the start of the transaction: an attacker who races ahead of honest voters will find the DB empty and have all forged votes accepted.

**Combined exploit**

1. Attacker connects as an ordinary peer (no privileges required).
2. Attacker reads the public stake distribution to enumerate all `PerasVoterId` values for the current epoch.
3. Before the voting window opens, attacker sends one forged `PerasVote` per committee member, all targeting a non-canonical block.
4. Each vote passes `validatePerasVote` (voter is in the stake distribution).
5. Each vote is inserted into `pvdsVoteIds` via `implAddVote`.
6. Honest committee members later send their real votes; `processVotes` filters them out as `alreadyInDb`.
7. No quorum is ever reached for the honest block; no `ValidatedPerasCert` is forged.

### Impact Explanation

Peras certificates boost blocks during chain selection via `getWeightSnapshot` in `PerasCertDB`. Suppressing certificate generation for a round removes the Peras weight from the honest chain tip, making it indistinguishable from (or lighter than) an adversarial fork that also has no certificate. This is a chain-selection bug: an unprivileged peer can make an honest node prefer a less-secure chain beyond the intended Peras security assumptions. Impact: **High** — chain selection / Peras voting/certificate verification bypass that enables unauthorized suppression of certificate acceptance.

### Likelihood Explanation

The attack requires only a network connection and knowledge of the public stake distribution (both freely available). The attacker must send forged votes before honest committee members, which is straightforward given that voting windows are slot-aligned and predictable. No key material, stake, or privileged access is needed. The stub validation has been open since the Peras feature branch was merged and is tracked as a known issue (`cardano-peras#120`), meaning the window is indefinitely open until the TODO is resolved.

### Recommendation

1. **Immediate**: Add a cryptographic signature field to `PerasVote blk` and implement real signature verification in `validatePerasVote` before the Peras diffusion layer is enabled on any network. The `WFALS.hs` `implVerifyVote` already shows the correct pattern (BLS signature + VRF eligibility proof).
2. **Structural**: Decouple the duplicate-suppression check from the validation step so that a vote already in the DB is silently skipped *only after* its signature is verified, preventing a forged first-arrival from permanently occupying a slot.
3. **Defense-in-depth**: Rate-limit or authenticate the Peras vote diffusion mini-protocol so that a single peer cannot submit votes on behalf of the entire committee in one batch.

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.
    (errs, _) ->
      throw (PerasVoteValidationError errs)
```
