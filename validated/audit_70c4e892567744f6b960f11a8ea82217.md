### Title
Peras Vote Batch All-or-Nothing Rejection Allows Unprivileged Peer to Suppress Valid Votes and Prevent Quorum, Causing Chain Selection Divergence - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/MiniProtocol/ObjectDiffusion/ObjectPool/PerasVote.hs`)

---

### Summary

`processVotes` rejects an entire inbound batch of Peras votes if any single vote fails validation, silently discarding all valid votes in the same batch. An unprivileged peer can exploit this by including one crafted invalid vote alongside many legitimate votes. The valid votes are permanently lost for that delivery, preventing the receiving node from accumulating enough votes to reach quorum. Without quorum, no Peras certificate is formed, the Peras weight boost is never applied to the correct chain, and the node's chain selection diverges from honest nodes that did receive the certificate.

---

### Finding Description

`processVotes` in `PerasVote.hs` uses `partitionEithers` to separate valid from invalid validation results, but then throws a `PerasVoteInboundException` — discarding the entire batch including the valid partition — whenever the error list is non-empty:

```haskell
case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, _) ->                                   -- valid votes silently dropped
      throw (PerasVoteValidationError errs)
``` [1](#0-0) 

The `_` in the error branch is the non-empty list of validated votes that were successfully verified — they are thrown away.

Vote validation fails when a vote's voter ID is absent from the stake distribution:

```haskell
validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr = Right ...
    | otherwise = Left PerasValidationErr
``` [2](#0-1) 

A malicious peer can trivially craft a vote whose voter ID is not in the current stake distribution and append it to a batch of otherwise valid votes. The entire batch is then rejected and the peer is disconnected, but the valid votes are permanently lost for that delivery window.

The same structural flaw exists in `processCerts`: [3](#0-2) 

The cert path is currently shielded by a stub `validatePerasCert` that always returns `Right`, but the vote path is live: `validatePerasVote` has a real failure branch today.

The inbound handler is wired into the production node-to-node stack via `hPerasVoteDiffusionClient`: [4](#0-3) 

(The current placeholder passes `PerasVoteStakeDistr mempty`, causing all votes to fail; this is an acknowledged TODO that will be replaced with the real stake distribution when Peras plumbing is complete, at which point the vulnerability becomes fully exploitable.)

---

### Impact Explanation

Peras certificates boost block weight in chain selection. `WeightedSelectView` computes `wsvTotalWeight` as block number plus `wsvWeightBoost`: [5](#0-4) 

`preferCandidate` switches to a candidate chain when its `wsvTotalWeight` exceeds the current chain's: [6](#0-5) 

If a node is prevented from accumulating enough votes to reach quorum, no certificate is formed, `wsvWeightBoost` remains zero for the boosted block, and the node's chain selection outcome diverges from honest nodes that did receive the certificate. A node that does not apply the boost may fail to switch to the heavier (boosted) canonical chain, or may switch to a lighter chain that honest nodes reject. This is a **High** chain-selection divergence: an unprivileged peer can make an honest node prefer a non-canonical chain beyond the intended Peras security assumptions.

---

### Likelihood Explanation

**Medium.** Any peer connected via the Peras vote diffusion mini-protocol can send a crafted batch. No stake, no keys, and no special privileges are required — only knowledge of the wire format (which is public). The attack requires a single crafted vote appended to a batch of legitimate votes. The peer is disconnected after the attack, but the damage (lost votes) is already done. The vulnerability becomes fully exploitable once the real stake distribution is wired in to replace the current `mempty` placeholder.

---

### Recommendation

Replace the all-or-nothing rejection with selective processing: add valid votes to the pool and log or trace invalid ones individually. The `partitionEithers` result already provides the split; the fix is to use the valid partition unconditionally:

```haskell
case partitionEithers validationResults of
    ([], validatedVotes) ->
      mapM_ (addVote . WithArrivalTime now) validatedVotes
    (errs, validatedVotes) -> do
      -- log/trace errs, but still add the valid votes
      mapM_ (addVote . WithArrivalTime now) validatedVotes
      -- optionally still disconnect the peer for sending invalid votes
      throw (PerasVoteValidationError errs)
```

Apply the same fix to `processCerts` before real certificate validation is wired in. [1](#0-0) 

---

### Proof of Concept

1. Attacker peer connects to a victim node via the `hPerasVoteDiffusionClient` mini-protocol.
2. Attacker constructs a batch: `[valid_vote_1, valid_vote_2, …, valid_vote_N, crafted_vote]` where `crafted_vote` has a `pvVoteVoterId` not present in the current `PerasVoteStakeDistr`.
3. `processVotes` runs `mapM validateVote votesNotAlreadyInDb` inside STM.
4. `validatePerasVote` returns `Left PerasValidationErr` for `crafted_vote` and `Right ...` for all others.
5. `partitionEithers` yields `(errs = [PerasValidationErr], validatedVotes = [v1..vN])`.
6. The `(errs, _)` branch fires; `throw (PerasVoteValidationError errs)` discards `v1..vN`.
7. The peer is disconnected; `v1..vN` are never added to the vote pool.
8. If the victim node cannot obtain those votes from other peers before the round closes, quorum is not reached.
9. No `ValidatedPerasCert` is produced; `addToPerasWeightSnapshot` is never called for the boosted block.
10. `weightBoostOfFragment` returns `mempty` for that block; `wsvTotalWeight` is lower than on honest nodes.
11. `preferCandidate` does not switch to the heavier boosted chain; the victim node's selection diverges from the canonical chain. [7](#0-6) [8](#0-7)

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
    -- Some votes are invalid => reject the whole batch
    --
    -- N.B. it has been requested in PR review
    -- https://github.com/IntersectMBO/ouroboros-consensus/pull/1768#discussion_r2747873186
    -- to gather all validation errors and report them together in the exception
    -- rather than just report the first error encountered.
    -- This assumes that vote validation is cheap, which may not be true in
    -- practice depending on the actual crypto/committee selection scheme.
    -- Hence we may revisit this to lazily abort validation upon the first error
    -- encountered.

      throw (PerasVoteValidationError errs)
