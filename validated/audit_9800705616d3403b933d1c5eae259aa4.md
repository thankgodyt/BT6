### Title
Peras Certificate Validation Stub Unconditionally Accepts All Peer-Supplied Certificates, Enabling Chain Selection Manipulation - (File: `ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

### Summary

The universal `BlockSupportsPeras` instance — the only production instance — implements `validatePerasCert` as a stub that unconditionally returns `Right` without performing any cryptographic or semantic checks. Because the `ValidatedPerasCert` wrapper type is the sole gate between a raw peer-supplied `PerasCert` and the chain-selection pipeline, any unprivileged peer can inject an arbitrary certificate over the live `PerasCertDiffusion` mini-protocol. The certificate is stored in the `PerasCertDB` and triggers `chainSelectionForBlock`, potentially causing the node to switch to a non-canonical fork boosted by the fraudulent certificate.

### Finding Description

**Root cause — validation absent from the smart constructor**

The `BlockSupportsPeras` type class declares `validatePerasCert` as the function that produces a `ValidatedPerasCert`, the type-level proof that a certificate has been checked: [1](#0-0) 

The only concrete instance in the codebase is the universal `instance StandardHash blk => BlockSupportsPeras blk`. Its implementation of `validatePerasCert` is a stub that ignores all certificate content and always returns `Right`: [2](#0-1) 

The TODO comment explicitly acknowledges that no actual validation is performed.

**Attacker-controlled entry path**

The production node-to-node handler wires the `PerasCertDiffusion` mini-protocol directly to `makePerasCertPoolWriterFromChainDB`: [3](#0-2) 

`makePerasCertPoolWriterFromChainDB` passes `validatePerasCert mkPerasParams` as the validator to `processCerts`: [4](#0-3) 

`processCerts` calls `validateCert` on each inbound certificate and, if all pass (they always do), forwards them to `addCert` → `addPerasCertAsync`: [5](#0-4) 

**Chain selection impact**

`addPerasCertAsync` enqueues the certificate for `chainSelSync`, which calls `chainSelectionForBlock` for the block named in the certificate: [6](#0-5) 

The certificate's `vpcCertBoost` weight is incorporated into the `PerasWeightSnapshot` used during chain comparison, so a fraudulent certificate can make a minority fork appear heavier than the honest chain.

**Analog to the external report**

The external report describes validation logic placed in a factory (`LoanFactoryBase.deployLoan`) rather than in the data constructor (`LoanState`), so a caller who bypasses the factory gets an unvalidated object. Here the analog is exact: `ValidatedPerasCert` is the "constructor" that is supposed to carry a proof of validation, but `validatePerasCert` — the only way to produce one from a raw `PerasCert` — performs no checks. Any code that receives a `ValidatedPerasCert` assumes it has been verified; that assumption is false for every certificate received from the network.

### Impact Explanation

An unprivileged peer can craft a `PerasCert` naming any block in the VolatileDB as the boosted block. The certificate passes "validation" (the stub), is stored in the `PerasCertDB`, and triggers chain selection. Because the Peras boost weight is added to the chain's `SelectView`, the attacker can cause the honest node to prefer a fork that would otherwise be rejected, constituting a **chain-selection manipulation** that lets an adversary steer the node away from the canonical chain without any stake or key material.

**Severity: High** — chain selection bug that lets an unprivileged peer make an honest node prefer a non-canonical chain, matching the allowed impact scope for "chain selection, rollback, forecast, genesis, or header-state bug that lets an unprivileged peer make an honest node prefer a non-canonical or less-secure chain beyond the intended security assumptions."

### Likelihood Explanation

The `PerasCertDiffusion` mini-protocol handler is wired up in the production `NodeToNode` handlers and is reachable by any connected peer. No keys, stake, or special privileges are required. The attacker only needs to send a well-formed CBOR-encoded `PerasCert` message targeting a block that the victim node has in its VolatileDB.

### Recommendation

Move the actual certificate validation logic (signature verification, committee membership, quorum proof) into `validatePerasCert` before the `ValidatedPerasCert` wrapper is constructed, mirroring the pattern already used for `validatePerasVote` (which at least checks stake-distribution membership). Until real cryptographic checks are implemented, the stub should reject all certificates (`Left PerasValidationErr`) rather than accept all of them, so that the `ValidatedPerasCert` type invariant is not vacuously satisfied.

### Proof of Concept

1. Connect to a victim node as a peer supporting the `PerasCertDiffusion` mini-protocol.
2. Identify a block hash `H` in the victim's VolatileDB that is on a competing fork (e.g., obtained via `ChainSync`).
3. Send a `PerasCert { pcCertRound = R, pcCertBoostedBlock = H }` over the `PerasCertDiffusion` channel.
4. `processCerts` calls `validatePerasCert mkPerasParams cert`, which returns `Right (ValidatedPerasCert { vpcCert = cert, vpcCertBoost = perasWeight mkPerasParams })` unconditionally.
5. The cert is enqueued via `addPerasCertAsync` → `chainSelSync` → `chainSelectionForBlock`.
6. The victim node's chain selection now treats the fork containing `H` as having additional Peras boost weight and may switch to it. [7](#0-6) [8](#0-7) [9](#0-8)

processCerts ::
  MonadSTM m =>
  SystemTime m ->
  STM m (Set PerasRoundNo) ->
  (PerasCert blk -> Either (PerasValidationErr blk) (ValidatedPerasCert blk)) ->
  (WithArrivalTime (ValidatedPerasCert blk) -> m ()) ->
  [PerasCert blk] ->
  m ()
processCerts systemTime alreadyInDbSTM validateCert addCert certs = do
  alreadyInDb <- atomically alreadyInDbSTM
  let certsNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasCertRound) certs
  now <- systemTimeCurrent systemTime
  case partitionEithers (validateCert <$> certsNotAlreadyInDb) of
    -- All certs are valid => add them to the pool
    ([], validatedCerts) ->
      mapM_
        (addCert . WithArrivalTime now)
        validatedCerts

chainSelSync cdb@CDB{..} (ChainSelAddPerasCert cert varProcessed) = do
  curChain <- lift $ atomically $ Query.getCurrentChain cdb
  let immTip = AF.castAnchor $ AF.anchor curChain

  certResult <- withEarlyExitId $ do
    -- Ignore the certificate if it boosts a block that is so old that it can't
    -- influence our selection.
    when (pointSlot boostedBlock < AF.anchorToSlotNo immTip) $ do
      lift $ lift $ traceWith tracer $ IgnorePerasCertTooOld certRound boostedBlock immTip
      idExitEarly PerasCertIgnoredTooOld

    -- Add the certificate to the PerasCertDB.
    certRes <- lift $ lift $ join $ atomically $ PerasCertDB.addCert cdbPerasCertDB cert
    -- Here:
    -- \* if the certificate is already in the PerasCertDB, we exit early with that result
    -- \* if the certificate is newly added to the PerasCertDB, we bind  the result value that we will return in any of the branches below
    addedCertRes <-
      case certRes of
        PerasCertDB.PerasCertAlreadyInDB -> idExitEarly $ PerasCertProcessed PerasCertDB.PerasCertAlreadyInDB
        PerasCertDB.AddedPerasCertToDB -> pure $ PerasCertProcessed PerasCertDB.AddedPerasCertToDB

    -- If the certificate boosts a block on our current chain (including the
    -- anchor), then it just makes our selection even stronger.
    when (AF.withinFragmentBounds (castPoint boostedBlock) curChain) $ do
      lift $ lift $ traceWith tracer $ PerasCertBoostsCurrentChain certRound boostedBlock
      idExitEarly $ addedCertRes

    boostedHash <- case pointHash boostedBlock of
      -- If the certificate boosts the Genesis point, then it can not influence
      -- chain selection as all chains contain it.
      GenesisHash -> do
        lift $ lift $ traceWith tracer $ PerasCertBoostsGenesis certRound
        idExitEarly $ addedCertRes
      -- Otherwise, the certificate boosts a block potentially on a (future)
      -- candidate.
      BlockHash boostedHash -> pure boostedHash
    boostedHdr <-
      lift (lift $ VolatileDB.getBlockComponent cdbVolatileDB GetHeader boostedHash) >>= \case
        -- If we have not (yet) received the boosted block, we don't need to do
        -- anything further for now regarding chain selection. Once we receive
        -- it, the additional weight of the certificate is taken into account.
        Nothing -> do
          lift $ lift $ traceWith tracer $ PerasCertBoostsBlockNotYetReceived certRound boostedBlock
          idExitEarly $ addedCertRes
        Just boostedHdr -> pure boostedHdr

    -- Trigger chain selection for the boosted block.
    lift $ lift $ traceWith tracer $ ChainSelectionForBoostedBlock certRound boostedBlock
    lift $ chainSelectionForBlock cdb BlockCache.empty boostedHdr noPunishment
    pure $ addedCertRes
