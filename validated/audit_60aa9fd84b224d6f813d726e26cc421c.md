Audit Report

## Title
`HyperliquedBridgeToken.mint(address,uint256,bytes)` Permanently Redirects Bridged Funds to `_systemAddress` When `finTransfer` Is Called With Non-Empty `message` — (`evm/src/omni-bridge/contracts/HlBridgeToken.sol`)

## Summary

`OmniBridge.finTransfer` dispatches to the 3-arg `IBridgeToken.mint` overload whenever `payload.message.length != 0` for any registered bridge token. `HyperliquedBridgeToken` overrides this overload to implement HyperCore spot-balance accounting: it mints tokens to `account` and immediately transfers the full amount to `_systemAddress`. When a user bridges tokens from NEAR to HyperEVM with a non-empty `message` targeting an `HyperliquedBridgeToken`, the recipient receives zero tokens, the entire amount is parked at `_systemAddress`, and the nonce is irrevocably consumed.

## Finding Description

**Dispatch in `OmniBridge.finTransfer`** (lines 337–349):

```solidity
} else if (isBridgeToken[payload.tokenAddress]) {
    if (payload.message.length == 0) {
        IBridgeToken(payload.tokenAddress).mint(payload.recipient, payload.amount);
    } else {
        IBridgeToken(payload.tokenAddress).mint(
            payload.recipient, payload.amount, payload.message
        );
    }
}
```

For the base `BridgeToken`, the 3-arg overload (lines 54–60 of `BridgeToken.sol`) simply ignores the bytes parameter and calls `_mint(account, value)` — tokens reach the recipient normally.

`HyperliquedBridgeToken` overrides this overload differently (lines 76–83 of `HlBridgeToken.sol`):

```solidity
function mint(address account, uint256 value, bytes memory) external override onlyOwner {
    _mint(account, value);
    _update(account, _systemAddress, value);
}
```

`_mint(account, value)` increases `account`'s balance by `value`. `_update(account, _systemAddress, value)` immediately transfers the full `value` from `account` to `_systemAddress`. The net change to `account` is zero. This overload is intentionally designed for the HyperCore accounting path (as documented in the contract's NatSpec at lines 29–31 and 85–105), where tokens are "parked" at `_systemAddress` to mirror HyperCore-side spot balances. It is not designed to deliver tokens to a bridge recipient.

The nonce is consumed unconditionally before the mint (line 287: `completedTransfers[payload.destinationNonce] = true`), and `FinTransfer` is emitted after (lines 359–366). There is no retry or refund path.

**Why existing checks fail**: The signature verification (line 311) only authenticates that the MPC signed the payload; it does not validate whether the `message` field is appropriate for the token type. The `isBridgeToken` check (line 337) does not distinguish between `BridgeToken` and `HyperliquedBridgeToken` implementations. No guard prevents `finTransfer` from invoking the HyperCore-specific accounting path on a standard NEAR→EVM bridge finalization.

## Impact Explanation

This is a direct, permanent loss of bridged funds. Any user who bridges tokens from NEAR to HyperEVM with a non-empty `message` targeting an `HyperliquedBridgeToken` loses the entire bridged amount to `_systemAddress`. The transfer is marked complete; the nonce cannot be reused. This matches the critical impact class: **permanent loss of bridged funds across NEAR→EVM flows**.

## Likelihood Explanation

The `message` field is freely set by the originating user on NEAR during `ft_on_transfer` or `initTransfer`. Passing a non-empty message is a standard pattern for cross-chain contract calls (e.g., triggering downstream DeFi actions on the destination chain). No special privilege is required — any unprivileged user can trigger this by including any non-empty string as `msg` in their NEAR-side transfer. The only structural precondition is that `HyperliquedBridgeToken` is registered in `OmniBridge` with `isBridgeToken[addr] = true` and `customMinters[addr] == address(0)`, which is the natural registration path for a token where the bridge itself is the mint authority.

## Recommendation

1. **Override the 3-arg `mint` in `HyperliquedBridgeToken` to behave identically to the 2-arg path** when called by the owner (i.e., `OmniBridge`): simply call `_mint(account, value)` and ignore the bytes parameter. Reserve the `_update(account, _systemAddress, value)` accounting exclusively for the `coreReceiveWithData` path, which is the only context where HyperCore spot-balance parking is semantically correct.
2. **Alternatively**, remove the `message`-based dispatch from `OmniBridge.finTransfer` entirely for the `isBridgeToken` branch. Token delivery to the recipient should be unconditional; any message-triggered side-effects should be handled post-mint via a separate callback mechanism.

## Proof of Concept

1. `HyperliquedBridgeToken` is deployed and registered: `isBridgeToken[hlToken] = true`, `customMinters[hlToken] = address(0)`, `OmniBridge` is the token owner.
2. User on NEAR calls `ft_on_transfer` with `msg = '{"InitTransfer":{"recipient":"evm:0xRecipient","fee":"0","native_token_fee":"0","msg":"hello"}}'`. The non-empty `msg` is forwarded as `payload.message = "hello"`.
3. NEAR MPC signs the `TransferMessagePayload` including `message = "hello"`.
4. Relayer calls `OmniBridge.finTransfer(signature, payload)` on HyperEVM.
5. `completedTransfers[payload.destinationNonce] = true` (line 287) — nonce consumed.
6. `payload.message.length != 0` → branch at line 344 executes: `IBridgeToken(hlToken).mint(recipient, amount, "hello")`.
7. `HyperliquedBridgeToken.mint`: `_mint(recipient, amount)` → `recipient.balance = amount`; then `_update(recipient, _systemAddress, amount)` → `recipient.balance = 0`, `_systemAddress.balance += amount`.
8. `FinTransfer` event emitted — transfer finalized.
9. `recipient.balanceOf(hlToken) == 0`; `_systemAddress.balanceOf(hlToken) += amount`. Funds are permanently lost to the recipient.

A minimal Foundry test can reproduce this by: deploying `OmniBridge` + `HyperliquedBridgeToken`, registering the token, constructing a valid signed `TransferMessagePayload` with `message = "x"`, calling `finTransfer`, and asserting `balanceOf(recipient) == 0` and `balanceOf(_systemAddress) == amount`.
