### Title
Migration Callback Uses Stale `ft_total_supply()` Snapshot, Allowing Concurrent Deposits to Strand User Funds — (File: `contracts/satoshi-bridge/src/nbtc/migration.rs`)

### Summary

`internal_migrate_to_new_token` issues parallel cross-contract queries for `ft_total_supply()` and every account's `ft_balance_of()` on the old token. Because NEAR cross-contract calls are asynchronous, the callback `migrate_to_new_token_mint` executes in a later block. Any `verify_deposit` mint that lands between the query block and the callback block increases the old token's live supply without being reflected in the captured snapshot. The completeness guard `sum == total_supply` still passes (both sides use the stale snapshot), but the new token is minted with fewer tokens than the old token's current supply, permanently stranding the newly minted nBTC on the old contract.

### Finding Description

`internal_migrate_to_new_token` builds a batch of parallel promises:

```rust
let mut queries = ext_nbtc::ext(old_token.clone())
    .with_static_gas(GAS_FOR_FT_QUERY)
    .ft_total_supply();
for account in &accounts {
    queries = queries.and(
        ext_nbtc::ext(old_token.clone())
            .with_static_gas(GAS_FOR_FT_QUERY)
            .ft_balance_of(account.clone()),
    );
}
``` [1](#0-0) 

All queries execute atomically in the same receipt batch (block N), so `total_supply` and every `balance_of` are mutually consistent **at block N**. The callback `migrate_to_new_token_mint` runs in block N+1 or later:

```rust
let total_supply = Self::parse_ft_result(0);
// ...
require!(
    sum == total_supply,
    "Sum of account balances does not match total supply"
);
``` [2](#0-1) 

If a relayer calls `verify_deposit` between block N and the callback block, the nbtc contract mints `M` new tokens to a depositor. The old token's live supply is now `T + M`, but the captured snapshot still shows `T`. The guard `sum == total_supply` evaluates `T == T` and passes. The callback then mints only `T` tokens to the new contract. After `migrate_to_new_token_resolve` switches `nbtc_account_id` to the new token:

```rust
self.internal_mut_config().nbtc_account_id = new_token.clone();
``` [3](#0-2) 

the depositor holds `M` nBTC on the old (now-abandoned) contract and zero on the new one. Their BTC is locked in the bridge's UTXO pool, but the bridge no longer recognises the old token for any operation, so those tokens cannot be used for withdrawals or any other bridge function.

### Impact Explanation

A user's freshly minted nBTC is permanently stranded on the old token contract. Their underlying BTC remains locked in the bridge UTXO pool with no reachable withdrawal path on the new token. This matches the allowed medium impact: **stuck bridge state requiring operator intervention** (manual re-minting on the new token, which itself requires a privileged call and introduces further accounting risk).

### Likelihood Explanation

Relayers continuously submit deposit proofs. Migration is not required to pause the old token first — the code contains no such guard. Any deposit proof submitted in the 1–2 block window between the query receipt and the callback receipt triggers the issue. On a live bridge with active deposits this window is routinely occupied. The depositor need not take any special action; ordinary BTC deposit activity is sufficient.

### Recommendation

Enforce that the old token is paused before migration begins, or perform the supply/balance snapshot inside the same synchronous execution context (impossible with cross-contract calls on NEAR). The practical fix is to add a `require!(old_token_is_paused())` check at the start of `internal_migrate_to_new_token`, ensuring no new mints can occur between the snapshot and the callback. Alternatively, record the `total_supply` snapshot in contract storage at query time and re-verify it in the callback against a fresh live query, reverting if the two differ.

### Proof of Concept

1. Bridge holds UTXO pool with active deposits pending proof submission.
2. Operator calls `migrate_to_new_token(new_token, accounts)`. Bridge dispatches parallel `ft_total_supply()` + `ft_balance_of()` queries at block N; captured `total_supply = T`.
3. At block N (same block or N+1), a relayer calls `verify_deposit` for Alice's pending deposit. nbtc mints `M` tokens to Alice. Old token live supply is now `T + M`; Alice's balance = `M`.
4. Migration callback `migrate_to_new_token_mint` executes. Alice's captured balance = 0 (query was before her mint). `sum = T`, `total_supply = T`. Guard passes. New token receives `T` tokens; Alice gets 0 on new token.
5. `migrate_to_new_token_resolve` sets `nbtc_account_id = new_token`.
6. Alice has `M` nBTC on old token (unusable) and 0 on new token. Her BTC is locked in the UTXO pool. No withdrawal is possible without operator intervention to manually re-mint on the new token. [4](#0-3)

```rust
    pub fn migrate_to_new_token_mint(
        &mut self,
        new_token: AccountId,
        accounts: Vec<AccountId>,
    ) -> PromiseOrValue<()> {
        require!(
            env::promise_results_count() == accounts.len() as u64 + 1,
            "Unexpected number of promise results"
        );

        let total_supply = Self::parse_ft_result(0);
        let mut sum: u128 = 0;
        let mut entries: Vec<(AccountId, u128)> = Vec::new();
        for (index, account) in accounts.into_iter().enumerate() {
            let balance = Self::parse_ft_result(index as u64 + 1);
            sum += balance;
            if balance > 0 {
                entries.push((account, balance));
            }
        }
        require!(
            sum == total_supply,
            "Sum of account balances does not match total supply"
        );

        let accounts_count = entries.len();
        let mut mint_batch = Promise::new(new_token.clone());
        for (account, amount) in entries {
            let args = serde_json::to_vec(&json!({
                "mint_account_id": account,
                "mint_amount": U128(amount),
                "protocol_fee": U128(0),
                "relayer_account_id": env::current_account_id(),
                "relayer_fee": U128(0),
                "post_actions": null,
            }))
            .unwrap_or_else(|_| env::panic_str("Failed to serialize mint args"));
            mint_batch = mint_batch.function_call(
                "mint".to_string(),
                args,
                NearToken::from_yoctonear(0),
                GAS_FOR_MINT_ACTION,
            );
        }
        mint_batch
            .then(
                Self::ext(env::current_account_id())
                    .with_static_gas(GAS_FOR_MIGRATION_RESOLVE_CALL_BACK)
                    .migrate_to_new_token_resolve(new_token, accounts_count, U128(total_supply)),
            )
            .into()
    }
