### Title
Missing Cryptographic Signature Verification in Peras Vote and Certificate Validation Allows Any Peer to Forge Votes and Manipulate Chain Selection — (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The degenerate `BlockSupportsPeras` instance used for all block types provides a `validatePerasVote` that only checks stake-distribution membership and a `validatePerasCert` that unconditionally accepts every certificate. Because the `PerasVote` data type carries no cryptographic signature field, there is no mechanism to verify that a vote was actually cast by the claimed voter. Any unprivileged peer can craft votes impersonating any registered pool, accumulate a quorum, and cause the node to generate and accept a certificate that boosts an arbitrary block, directly manipulating Peras chain selection.

---

### Finding Description

**Root cause — `validatePerasVote` performs no signature check**

The catch-all instance at line 320 of `SupportsPeras.hs` is the only `BlockSupportsPeras` instance in the production source tree:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/120
instance StandardHash blk => BlockSupportsPeras blk where
  ...
  validatePerasVote _params stakeDistr vote
    | Just stake <- lookupPerasVoteStake vote stakeDistr =
        Right ValidatedPerasVote { vpvVote = vote, vpvVoteStake = stake }
    | otherwise =
        Left PerasValidationErr
``` [1](#0-0) 

The only check performed is whether `pvVoteVoterId` appears in the stake distribution. No cryptographic proof is required or verified. This is structurally impossible to fix within the current type because the `PerasVote` data type itself carries no signature:

```haskell
data PerasVote blk = PerasVote
  { pvVoteRound  :: PerasRoundNo
  , pvVoteBlock  :: Point blk
  , pvVoteVoterId :: PerasVoterId
  }
``` [2](#0-1) 

**Root cause — `validatePerasCert` unconditionally accepts every certificate**

```haskell
validatePerasCert params cert =
  Right ValidatedPerasCert
    { vpcCert = cert
    , vpcCertBoost = perasWeight params
    }
``` [3](#0-2) 

Every certificate received from a peer is immediately wrapped in `ValidatedPerasCert` and treated as legitimate, regardless of its content.

**Attacker-controlled entry path**

Inbound votes from peers flow through `processVotes` in the Peras vote object-diffusion mini-protocol:

```haskell
processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (...) votes
    mapM validateVote votesNotAlreadyInDb
``` [4](#0-3) 

The `validateVote` callback supplied by `makePerasVotePoolWriterFromChainDB` calls `validatePerasVote` from the degenerate instance:

```haskell
(\vote -> getStakeDistrSTM >>= \sd -> pure $ validatePerasVote mkPerasParams sd vote)
``` [5](#0-4) 

A validated vote is then stored and, once quorum is reached, a certificate is automatically forged and submitted to the `ChainDB` via `addPerasVoteWithAsyncCertHandling`:

```haskell
addPerasVoteWithAsyncCertHandling cdb@CDB{cdbPerasVoteDB} vote = do
  addVoteRes <- join . atomically . addVote cdbPerasVoteDB $ vote
  case addVoteRes of
    AddedPerasVoteAndGeneratedNewCert cert -> do
      promise <- addPerasCertAsync cdb (WithArrivalTime (certTime) cert)
``` [6](#0-5) 

The resulting certificate is stored in the `PerasCertDB` and its boost weight is applied to chain selection via `getWeightSnapshot`, causing the node to prefer the boosted block.

### Impact Explanation

**Classification: Critical — Bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance.**

An adversary who knows the current stake distribution (public information) can:

1. Craft `PerasVote` messages with `pvVoteVoterId` values belonging to any registered pool.
2. Send enough such votes to exceed the quorum threshold (`stakeAboveThreshold`).
3. The node automatically forges a `ValidatedPerasCert` boosting the adversary's chosen block.
4. The certificate is inserted into `PerasCertDB` and its weight boost is applied during chain selection, causing honest nodes to prefer the adversary-controlled chain over the canonical one.

This directly subverts the Peras security guarantee: the weight boost is supposed to be evidence of honest committee participation, but here it can be manufactured by any peer without holding any private key.

---

### Likelihood Explanation

**High.** The Peras vote diffusion mini-protocol is a standard peer-to-peer channel. Any connected peer can send crafted `PerasVote` messages. The stake distribution is public. No key material, operator access, or stake majority is required. The only prerequisite is knowing which voter IDs are in the current stake distribution, which is trivially available from the ledger state.

---

### Recommendation

1. **Add a cryptographic signature field to `PerasVote`** (analogous to the `VoteSignature` field in the `EveryoneVotes` and `WFALS` committee implementations in `Committee/EveryoneVotes.hs` and `Committee/WFALS.hs`).
2. **Implement real signature verification in `validatePerasVote`** — verify that the signature in the vote was produced by the private key corresponding to the claimed `pvVoteVoterId`, using the voter's public key from the stake distribution.
3. **Implement real certificate verification in `validatePerasCert`** — verify the aggregate BLS signature against the declared voter set, as already specified in `Peras/Cert/V1.hs` and `Committee/WFALS.hs`'s `implVerifyCert`.
4. Remove the degenerate catch-all `BlockSupportsPeras` instance or replace it with one that fails closed (rejects all votes and certificates) until proper validation is implemented.

### Proof of Concept

```
Attacker connects to an honest node via the Peras vote diffusion mini-protocol.

1. Attacker queries the current stake distribution (public ledger state).
   Suppose pools P1, P2, P3 each hold 10% stake; quorum threshold is 25%.

2. Attacker crafts three PerasVote messages:
     PerasVote { pvVoteRound = R, pvVoteBlock = adversaryBlock, pvVoteVoterId = P1 }
     PerasVote { pvVoteRound = R, pvVoteBlock = adversaryBlock, pvVoteVoterId = P2 }
     PerasVote { pvVoteRound = R, pvVoteBlock = adversaryBlock, pvVoteVoterId = P3 }

3. Attacker sends these votes to the honest node.

4. processVotes calls validatePerasVote for each vote.
   validatePerasVote only checks: is P1/P2/P3 in the stake distribution? Yes.
   All three votes pass validation and are stored in PerasVoteDB.

5. After the third vote, stakeAboveThreshold returns True (30% > 25%).
   implAddVote triggers updatePerasRoundVoteStates → VoteGeneratedNewCert.
   A ValidatedPerasCert boosting adversaryBlock is forged and submitted to ChainDB.

6. The certificate's weight boost is applied in chain selection.
   The honest node now prefers adversaryBlock over the canonical chain tip.
```

The analog to the WPunkGateway bug is exact: just as `offerPunkForSaleToAddress` with price 0 "approved" the gateway without binding the caller of `supplyPunk`, being listed in the stake distribution "approves" a voter ID without binding the sender of the `PerasVote` message — because neither the vote type nor the validation function requires any proof of key ownership.

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes

  now <- systemTimeCurrent systemTime

      mapM_
