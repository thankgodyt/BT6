### Title
Missing Cryptographic Signature Verification in Peras Vote and Certificate Validation Allows Unprivileged Peer to Forge Votes for Any Staked Pool - (`File: ouroboros-consensus/src/ouroboros-consensus/Ouroboros/Consensus/Block/SupportsPeras.hs`)

---

### Summary

The universal `BlockSupportsPeras` instance — the only instance in the codebase — implements `validatePerasVote` and `validatePerasCert` as stubs that perform no cryptographic verification. `validatePerasVote` only checks whether the claimed voter ID has stake; it never verifies the vote's signature. `validatePerasCert` unconditionally accepts every certificate. An unprivileged peer can therefore send crafted `PerasVote` objects claiming to be from any staked pool, have them accepted as valid, accumulate a quorum of fake votes, and cause the node to forge and accept a certificate that boosts an attacker-chosen block — directly manipulating chain selection.

---

### Finding Description

The `BlockSupportsPeras` class defines two validation methods:

```haskell
validatePerasCert ::
  PerasCfg blk -> PerasCert blk ->
  Either (PerasValidationErr blk) (ValidatedPerasCert blk)

validatePerasVote ::
  PerasCfg blk -> PerasVoteStakeDistr -> PerasVote blk ->
  Either (PerasValidationErr blk) (ValidatedPerasVote blk)
```

The only instance in the repository is the universal degenerate instance:

```haskell
-- TODO: degenerate instance for all blks to get things to compile
-- see https://github.com/tweag/cardano-peras/issues/73
instance StandardHash blk => BlockSupportsPeras blk where
```

Its `validatePerasCert` unconditionally returns `Right` for every certificate: [1](#0-0) 

Its `validatePerasVote` only calls `lookupPerasVoteStake` — a stake-distribution lookup — and never inspects any cryptographic signature: [2](#0-1) 

The `PerasVote blk` data type in this instance carries only `pvVoteRound`, `pvVoteBlock`, and `pvVoteVoterId` — there is no signature field at all: [3](#0-2) 

Inbound votes from peers flow through `processVotes`, which calls the `validateVote` callback (wired to `validatePerasVote`) and, on success, stores the vote in the VoteDB: [4](#0-3) 

The production writer (`makePerasVotePoolWriterFromChainDB`) passes `validatePerasVote` as the validator for all peer-supplied votes: [5](#0-4) 

A grep search confirms `validatePerasVote` is defined and used only in these two files — there is no Cardano-specific override that adds real signature verification.

---

### Impact Explanation

This is a **bypass of Peras vote and certificate signature verification**. An attacker can:

1. Craft `PerasVote` objects with `pvVoteVoterId` set to any staked pool's ID and `pvVoteBlock` pointing to the attacker's chosen block.
2. Send them via the Peras vote diffusion mini-protocol to an honest node.
3. `validatePerasVote` accepts each vote because `lookupPerasVoteStake` finds the claimed voter ID in the stake distribution — no signature is checked.
4. Once enough fake votes accumulate to reach quorum, `implAddVote` in `PerasVoteDB/Impl.hs` triggers `updatePerasRoundVoteStates`, which calls `forgePerasCert` and stores a `ValidatedPerasCert`.
5. The certificate carries a Peras weight boost for the attacker's chosen block, directly influencing chain selection.

Separately, `validatePerasCert` accepts any certificate unconditionally, so an attacker can also inject a pre-formed certificate directly without going through the vote accumulation path.

This maps to the allowed impact: **Critical — bypass of Peras voting/certificate checks enabling unauthorized certificate acceptance**, and **High — chain selection bug letting an unprivileged peer make an honest node prefer a non-canonical chain**. [6](#0-5) 

---

### Likelihood Explanation

- The attack requires only a standard peer connection — no privileged keys, no stake, no operator access.
- The Peras vote diffusion protocol is wired into the node-to-node application bundle and is reachable from any connected peer.
- The degenerate instance is the **only** `BlockSupportsPeras` instance; there is no production override.
- The TODO comments and issue references confirm this is known incomplete work that is currently the live code path. [7](#0-6) 

---

### Recommendation

1. **Implement real signature verification in `validatePerasVote`**: verify the vote's cryptographic signature against the public key associated with the claimed `pvVoteVoterId` in the committee/stake distribution before accepting the vote.
2. **Implement real certificate verification in `validatePerasCert`**: verify the aggregate BLS signature and VRF outputs against the declared voter set before accepting a certificate.
3. **Add a signature field to `PerasVote blk`**: the current stub type carries no cryptographic material, making verification structurally impossible.
4. **Do not ship the degenerate instance to production** until the above are complete; gate Peras vote diffusion behind a feature flag that is disabled until the real instance is in place.

---

### Proof of Concept

```
1. Attacker connects to an honest node as a peer via the Peras vote diffusion
   mini-protocol (aPerasVoteDiffusionServer / aPerasVoteDiffusionClient).

2. Attacker reads the current stake distribution (publicly available on-chain)
   to enumerate all PerasVoterIds with positive stake.

3. For each staked voter ID V_i, attacker constructs:
     PerasVote
       { pvVoteRound    = <current round>
       , pvVoteBlock    = <attacker's chosen block point>
       , pvVoteVoterId  = V_i   -- claimed identity, no proof required
       }

4. Attacker sends the batch to the honest node.

5. processVotes calls validatePerasVote for each vote.
   validatePerasVote calls lookupPerasVoteStake:
     - V_i is in the stake distribution => returns Just stake
     - Returns Right (ValidatedPerasVote { vpvVote, vpvVoteStake })
   No signature field exists; no signature is checked.

6. All votes are stored in the PerasVoteDB as ValidatedPerasVote.

7. implAddVote calls updatePerasRoundVoteStates. Once accumulated stake
   exceeds the quorum threshold, forgePerasCert is called and a
   ValidatedPerasCert is stored, boosting the attacker's chosen block.

8. Chain selection now applies the Peras weight boost to the attacker's
   block, potentially causing the honest node to prefer a non-canonical chain.
```

processVotes systemTime alreadyInDbSTM validateVote addVote votes = do
  validationResults <- atomically $ do
    alreadyInDb <- alreadyInDbSTM
    let votesNotAlreadyInDb = filter (not . (`Set.member` alreadyInDb) . getPerasVoteId) votes
    mapM validateVote votesNotAlreadyInDb
  now <- systemTimeCurrent systemTime
  case partitionEithers validationResults of
    -- All votes are valid => add them to the pool
    ([], validatedVotes) ->
      mapM_
        (addVote . WithArrivalTime now)
        validatedVotes
