Audit Report

## Title
User Funds Permanently Burned/Locked When `normalize_amount` Returns Zero Due to Missing Pre-Transfer Validation - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`init_transfer_internal` burns or locks user tokens and commits the transfer message to storage before any check that the decimal-normalized transfer amount is non-zero. When a trusted relayer subsequently calls `sign_transfer`, it rejects the transfer with `InvalidAmountToTransfer` if the normalized amount is 0, but the prior `init_transfer` transaction is already committed. No cancel or refund path exists, leaving tokens permanently consumed and the transfer message permanently stuck.

## Finding Description
`normalize_amount` uses floor division and returns 0 for any `amount < 10^(origin_decimals - decimals)`:

```rust
// L2784-2787
fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
    let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
    amount / (10_u128.pow(diff_decimals))
}
```

For a standard NEAR→EVM pair (`origin_decimals=24`, `decimals=18`), `diff_decimals=6`, so any `amount_without_fee < 1_000_000` normalizes to 0.

**Step 1 — `init_transfer_internal` (L1834–1864):** The transfer message is stored, then tokens are burned/locked. The only pre-burn validation is `fee < amount` (L554–557). There is no check that `normalize_amount(amount_without_fee) > 0`:

```rust
// L1850-1857
if let OmniAddress::Near(token_id) = transfer_message.token.clone() {
    self.burn_tokens_if_needed(token_id.clone(), transfer_message.amount);
    self.lock_tokens_if_needed(
        transfer_message.get_destination_chain(),
        &token_id,
        transfer_message.amount.0,
    );
```

The `remove_transfer_message_without_refund` call at L1846 only fires when storage balance is insufficient — it executes before the burn/lock and does not apply here.

**Step 2 — `sign_transfer` (L475–485):** The normalization check exists here, but it is too late — it runs in a separate, later transaction:

```rust
// L475-485
let amount_to_transfer = Self::normalize_amount(
    transfer_message.amount_without_fee().near_expect(BridgeError::InvalidFee),
    decimals,
);
require!(
    amount_to_transfer > 0,
    BridgeError::InvalidAmountToTransfer.as_ref()
);
```

When this `require!` panics, only the `sign_transfer` transaction reverts. The `init_transfer` transaction — which burned/locked the tokens and stored the message — is already finalized and cannot be undone.

**No recovery path:** `sign_transfer_callback` (L648–668) only removes the transfer message on a successful MPC signature. `claim_fee_callback` requires on-chain finalization proof from the destination chain, which is unreachable when `amount_to_transfer = 0`. No `cancel_transfer` or user-accessible refund function exists. The transfer message and the consumed tokens are permanently irrecoverable.

## Impact Explanation
This is a concrete instance of **permanent freezing of bridged funds** and **decimal/normalization abuse that changes user or protocol balances** — both listed Critical impact classes. Any user who initiates a transfer where `amount_without_fee < 10^(origin_decimals - decimals)` suffers an irrecoverable loss of their full transferred amount, with a permanently stuck transfer message in contract storage.

## Likelihood Explanation
The condition is reachable by any holder of a whitelisted token via the public `ft_transfer_call` entry point. The standard NEAR→EVM configuration (`origin_decimals=24`, `decimals=18`) creates a 6-decimal gap, meaning any transfer below 1,000,000 base units (0.000001 of the 18-decimal representation) triggers the bug. This threshold is easily hit by users testing with small amounts, UI rounding errors, or dust sweeps. No special privileges are required to initiate the transfer; the trusted-relayer restriction on `sign_transfer` is irrelevant because the funds are already permanently consumed after `init_transfer` regardless of whether a relayer ever attempts to sign.

## Recommendation
Add the normalization check inside `init_transfer_internal` (or at the `init_transfer` call site), before `burn_tokens_if_needed` and `lock_tokens_if_needed` are called. The `token_decimals` map and `get_token_address` are already available at that point:

```rust
// Before burn/lock in init_transfer_internal:
if let Some(token_address) = self.get_token_address(
    transfer_message.get_destination_chain(),
    self.get_token_id(&transfer_message.token),
) {
    if let Some(decimals) = self.token_decimals.get(&token_address) {
        let normalized = Self::normalize_amount(
            transfer_message.amount_without_fee()
                .near_expect(BridgeError::InvalidFee),
            decimals,
        );
        require!(normalized > 0, BridgeError::InvalidAmountToTransfer.as_ref());
    }
}
```

This causes `init_transfer` to revert atomically before any tokens are consumed, returning the full amount to the caller via the `ft_transfer_call` refund mechanism.

## Proof of Concept
1. Register a token with `origin_decimals = 24`, `decimals = 18` (standard NEAR→EVM pair).
2. User calls `ft_transfer_call` with `amount = 500_000`, `fee = 0`, EVM recipient.
3. `init_transfer` passes: `fee (0) < amount (500_000)` ✓ — no normalization check.
4. `init_transfer_internal` stores the transfer message, then burns 500,000 tokens. Returns `U128(0)`. Transaction commits.
5. Trusted relayer calls `sign_transfer` for this transfer ID.
6. `normalize_amount(500_000, {origin_decimals:24, decimals:18})` = `500_000 / 1_000_000` = **0**.
7. `require!(0 > 0, ...)` panics → `sign_transfer` transaction reverts atomically.
8. The 500,000 tokens are permanently burned. The transfer message is permanently stored. No recovery path exists.

A local integration test can reproduce this by: (a) deploying the bridge with a mock token at 24 decimals registered to an 18-decimal EVM address, (b) calling `ft_transfer_call` with `amount = 500_000`, (c) asserting `U128(0)` is returned and the transfer message is stored, (d) calling `sign_transfer` and asserting it panics with `InvalidAmountToTransfer`, (e) asserting the transfer message still exists and the token supply is reduced by 500,000.
