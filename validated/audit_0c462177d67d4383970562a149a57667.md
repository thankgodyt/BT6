Audit Report

## Title
Tokens Permanently Burned/Locked When Transfer Amount Normalizes to Zero in `init_transfer_internal` - (File: `near/omni-bridge/src/lib.rs`)

## Summary
`normalize_amount` applies floor division to scale a NEAR-side token amount to the destination chain's decimal precision. When a user's `amount_without_fee` is smaller than the normalization factor (`10^(origin_decimals - dest_decimals)`), the result is zero. Tokens are burned or locked inside `init_transfer_internal` before this check is ever applied; `sign_transfer` then permanently rejects the transfer with `InvalidAmountToTransfer`, and no public cancel or refund function exists, causing irreversible loss of the user's funds.

## Finding Description

`normalize_amount` performs integer floor division with no zero-result guard: [1](#0-0) 

The code comment explicitly acknowledges that when `fee = 0`, dust "stays locked/burned," but this only addresses sub-unit remainders, not the case where the entire `amount_without_fee` falls below the normalization threshold and the whole amount is lost.

`init_transfer` (called from `ft_on_transfer`) validates only that `fee < amount`: [2](#0-1) 

It then calls `init_transfer_internal`, which **immediately burns or locks the full token amount** with no normalization pre-check: [3](#0-2) 

Only later, when a relayer calls `sign_transfer` (restricted to `#[trusted_relayer]`), is normalization applied and the zero-amount guard enforced: [4](#0-3) 

`sign_transfer` panics, the transfer remains in `pending_transfers` indefinitely, and no public `cancel_transfer` or `refund_transfer` function exists anywhere in the contract.

## Impact Explanation

This constitutes permanent, irreversible loss of bridged funds — a Critical impact matching "permanent freezing of bridged funds" and "decimal/normalization abuse that changes user or protocol balances." The burned tokens (for deployed bridge tokens) or locked tokens (for native tokens) are unrecoverable with no on-chain remedy.

## Likelihood Explanation

For any token pair where `origin_decimals > dest_decimals` (e.g., a 24-decimal NEAR token bridged to a 6-decimal EVM token, normalization factor = `10^18`), any user sending less than 1 NEAR-equivalent triggers the bug. No special privileges or coordination are required — a normal `ft_transfer_call` from any token holder is sufficient. The scenario is realistic and likely accidental for users unfamiliar with decimal normalization.

## Recommendation

Add a normalization check inside `init_transfer` or `init_transfer_internal` **before** burning or locking tokens. Look up the destination token's `Decimals` and assert `normalize_amount(amount_without_fee, decimals) > 0`. If decimals are not yet registered, reject the transfer early. As defense-in-depth, implement a public `cancel_transfer` function allowing the original sender to reclaim funds from stuck transfers.

## Proof of Concept

1. Register a token with `origin_decimals = 24`, `dest_decimals = 6` (normalization factor = `10^18`).
2. User calls `ft_transfer_call` on the NEAR token contract with `amount = 5 * 10^17` (0.5 NEAR-equivalent) and `fee = 0`, targeting an EVM recipient.
3. `ft_on_transfer` → `init_transfer`: only guard is `fee < amount` → `0 < 5*10^17` ✓, passes.
4. `init_transfer_internal` burns `5 * 10^17` tokens (deployed token) or locks them — tokens are gone.
5. Relayer calls `sign_transfer`.
6. `normalize_amount(5 * 10^17, {24, 6}) = 5 * 10^17 / 10^18 = 0`.
7. `require!(amount_to_transfer > 0, ...)` panics — `sign_transfer` reverts.
8. Transfer stays in `pending_transfers` forever; `5 * 10^17` tokens are permanently lost with no recovery path.

    /// Uses floor division — any sub-unit remainder ("dust") is truncated and not transferred
    /// to the destination chain. When fee > 0, dust is absorbed into the fee via `claim_fee`.
    /// When fee = 0, dust stays locked/burned. See SECURITY.md for details.
    fn normalize_amount(amount: u128, decimals: Decimals) -> u128 {
        let diff_decimals: u32 = (decimals.origin_decimals - decimals.decimals).into();
        amount / (10_u128.pow(diff_decimals))
    }
