Looking at the actual code to verify each step of the claimed exploit path.

Audit Report

## Title
Missing Contract Existence Check in `initTransfer1155` Allows Silent No-Op Token Transfer and Unauthorized NEAR Minting — (File: `evm/src/omni-bridge/contracts/OmniBridge.sol`)

## Summary

`OmniBridge.initTransfer1155` calls `IERC1155(tokenAddress).safeTransferFrom(...)` without verifying that `tokenAddress` has deployed contract code. In Solidity 0.8.24, a high-level call to a void function on an EOA returns `(success=true, returndata="")` and does not revert, because Solidity only checks returndata length when the callee declares a return value. Zero ERC1155 tokens are transferred to the bridge, yet `InitTransfer` is emitted. The NEAR bridge treats any `InitTransfer` from a registered factory as proof of a locked escrow and mints bridged tokens on NEAR, permanently breaking the 1:1 backing invariant.

## Finding Description

**Root cause — Solidity void-function call to EOA succeeds silently:**

`initTransfer1155` at line 458 makes a direct high-level interface dispatch:

```solidity
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    tokenId,
    amount,
    ""
);
```

`IERC1155.safeTransferFrom` declares no return value. When `tokenAddress` is an EOA, the EVM `CALL` opcode returns `(success=true, returndata="")`. Solidity's high-level call machinery only asserts `returndata.length > 0` when the callee declares a return value; for void functions it performs no such check. The call completes without reverting. This is the exact gap that `SafeERC20.safeTransferFrom` closes via `Address.functionCall`, which explicitly asserts `address.code.length > 0` before dispatching. No equivalent guard exists here.

**Prerequisite — `logMetadata1155` also accepts EOAs:**

`logMetadata1155` (line 234) stores `tokenAddress` in `multiTokens[deterministicToken]` and emits `LogMetadata` without any `extcodesize` check. A relayer submitting this event to NEAR triggers `deploy_token_callback`, which passes the factory guard (`self.factories.get(&chain) == Some(metadata.emitter_address)`) because the event originates from the legitimate OmniBridge contract, and then calls `deploy_token_internal`, setting `token_decimals` for `deterministicToken`. This is the prerequisite that satisfies NEAR's `fin_transfer_callback` check at line 715–718.

**NEAR `fin_transfer_callback` checks that are bypassed:**

```rust
require!(
    self.factories.get(&init_transfer.emitter_address.get_chain())
        == Some(init_transfer.emitter_address),
    BridgeError::UnknownFactory.as_ref()
);
let decimals = self
    .token_decimals
    .get(&init_transfer.token)
    .near_expect(BridgeError::TokenDecimalsNotFound);
```

Both checks pass: the factory check passes because `InitTransfer` is emitted by the legitimate OmniBridge; the decimals check passes because `logMetadata1155` (with `decimals=0`) already caused NEAR to deploy the token and populate `token_decimals`. No check verifies that the EVM-side escrow actually holds the claimed tokens.

**`evm/CLAUDE.md` invariant explicitly violated:**

> *"Event–transfer atomicity: `InitTransfer` must only be emitted in a code path where tokens have already been burned/locked in the same transaction. If the token transfer reverts or is skipped, the event must not emit — the NEAR side will treat any emitted event as proof that tokens are held."*

This invariant is broken: the token transfer is silently skipped, yet `InitTransfer` is emitted.

**`finTransfer` on EVM also silently no-ops for EOA token address:**

When the attacker later redeems on EVM, `finTransfer` calls `IERC1155(multiToken.tokenAddress).safeTransferFrom(address(this), payload.recipient, ...)` on the same EOA — again succeeding silently and delivering nothing. This means the attacker cannot drain legitimate users' ERC1155 deposits via redemption, but the minted NEAR-side tokens remain unbacked.

## Impact Explanation

An unprivileged attacker mints an arbitrary quantity of NEAR-side bridged tokens backed by zero locked ERC1155 tokens. This is unauthorized minting of bridged funds, directly matching the Critical impact class: *"Stealing, loss, double-spending, unauthorized minting, or permanent freezing of bridged funds."* The bridge's core 1:1 backing invariant is permanently broken for the affected token. The minted tokens are valid NEP-141 tokens on NEAR and can be transferred, used in DeFi, or submitted as the "fast-transfer" leg of a two-leg transfer to extract value from the bridge's other liquidity pools.

## Likelihood Explanation

The attack requires no special privileges. `logMetadata1155` and `initTransfer1155` are both permissionless external functions callable by any EOA. The only external dependency is a trusted relayer processing the resulting events — but trusted relayers are automated systems that process all structurally valid events emitted by the registered OmniBridge factory address and cannot distinguish a fraudulent `InitTransfer` from a legitimate one. The attack is repeatable with any EOA address and any `tokenId`, and each invocation mints a fresh unbacked supply. No leaked keys, admin access, or oracle manipulation is required.

## Recommendation

Add an explicit contract existence check before the `safeTransferFrom` call in `initTransfer1155`, mirroring the guard used by OpenZeppelin's `Address.functionCall`:

```solidity
if (tokenAddress.code.length == 0) revert NotAContract();
IERC1155(tokenAddress).safeTransferFrom(
    msg.sender,
    address(this),
    tokenId,
    amount,
    ""
);
```

Apply the same guard in `logMetadata1155` to prevent registration of EOAs as token addresses in the first place. Optionally, require that `multiTokens[deterministicToken]` is already populated (i.e., `logMetadata1155` was called first) before `initTransfer1155` proceeds, adding defense-in-depth.

## Proof of Concept

**Minimal Hardhat/Foundry test sequence (local fork):**

1. Deploy `OmniBridge` and configure a factory address on NEAR (testnet or local NEAR sandbox).
2. Generate a random EOA address `fakeToken` (no deployed code).
3. Call `bridge.logMetadata1155(fakeToken, tokenId)` — succeeds, emits `LogMetadata(deterministicToken, ...)`.
4. Submit the `LogMetadata` proof to NEAR `deploy_token` — NEAR deploys a NEP-141 token for `deterministicToken` and sets `token_decimals`.
5. Call `bridge.initTransfer1155(fakeToken, tokenId, 1_000_000, 0, 0, "attacker.near", "")` — `safeTransferFrom` on `fakeToken` (EOA) returns success silently; `InitTransfer` is emitted.
6. Assert `erc1155.balanceOf(bridge, tokenId) == 0` — bridge holds nothing.
7. Submit the `InitTransfer` proof to NEAR `fin_transfer` — NEAR mints 1,000,000 bridged tokens to `attacker.near`.
8. Assert attacker's NEAR token balance is 1,000,000 with zero ERC1155 backing.
