### Title
Pending-Sign Capacity Check Blocks Refund Execution for Users with an Active Withdrawal — (File: `contracts/satoshi-bridge/src/refund.rs`)

---

### Summary

`finalize_refund_with_psbt` applies the same `require_pending_sign_capacity` guard that governs withdrawals to refund execution. Because the default per-user limit is **1**, any user who already has one pending withdrawal cannot call `execute_refund` for their own stuck deposit. Their BTC remains locked in the refund request until the unrelated withdrawal is resolved or a third party executes the refund on their behalf.

---

### Finding Description

`execute_refund` (public, no role restriction beyond `#[pause]`) ultimately calls `finalize_refund_with_psbt`, which unconditionally checks the **caller's** pending-sign capacity before creating the refund `BTCPendingInfo`:

```rust
// contracts/satoshi-bridge/src/refund.rs  lines 339-342
if !self.check_account_exists(&caller) {
    self.internal_set_account(&caller, crate::Account::new(&caller));
}
self.require_pending_sign_capacity(&caller);   // ← blocks if caller has ≥ 1 pending sign tx
```

`require_pending_sign_capacity` is defined in `account.rs` (lines 113-123):

```rust
pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
    require!(
        self.get_account(account_id)
            .unwrap_or_else(|| env::panic_str(...))
            .pending_sign_count()
            < self.get_max_pending_sign_txs(account_id),
        "Too many pending sign transactions"
    );
}
```

`get_max_pending_sign_txs` returns **1** by default (lines 105-111 of `account.rs`). A pending withdrawal created via `create_btc_pending_info` (token_receiver.rs lines 71-140) inserts an entry into `btc_pending_sign_ids`, consuming that single slot.

A refund and a withdrawal are logically independent operations on different UTXOs, but they share the same per-user pending-sign counter. The limit was designed to throttle withdrawal spam; its application to refund execution is an unintended side-effect that mirrors the Size protocol bug exactly: a cap on one operation type silently blocks an unrelated, protective operation.

---

### Impact Explanation

A user who has initiated a withdrawal (consuming their one pending-sign slot) and simultaneously has a stuck deposit eligible for refund **cannot execute their own refund**. The call reverts with `"Too many pending sign transactions"`. Their BTC deposit remains locked in the `refund_requests` map until:

1. The pending withdrawal is resolved (verified on-chain or cancelled via RBF), freeing the slot, **or**
2. A third-party account with a free slot calls `execute_refund` on their behalf.

Option 2 is possible because `execute_refund` has no caller restriction, but it requires an external actor to attach the required NEAR storage deposit and act voluntarily. In the absence of such an actor, the refund is stuck — a bridge state requiring operator intervention.

This matches the allowed Medium impact: *"stuck bridge state requiring operator intervention"* and *"attacker-triggered temporary locking of bridged funds"* (an adversary who knows the victim has a pending withdrawal can time a deposit to the victim's address to ensure the refund path is blocked).

---

### Likelihood Explanation

The scenario is realistic and requires no privileged access:

- The default pending-sign limit is 1 for every account.
- Any user who has initiated a withdrawal and also has a stuck deposit (e.g., a deposit whose `verify_deposit` was never submitted by a relayer) hits this condition.
- The refund timelock is 2–14 days, a long window during which the withdrawal may still be pending.

---

### Recommendation

Decouple the pending-sign capacity check from refund execution. Refunds spend a UTXO that is already locked in the bridge (the original deposit); they do not introduce new economic exposure the way a withdrawal does. Options:

1. **Separate counter**: Track refund pending-sign entries in a distinct field, independent of the withdrawal counter.
2. **Exempt refunds**: Skip `require_pending_sign_capacity` in `finalize_refund_with_psbt` entirely, since a refund can only be created for a UTXO that has already been verified by the light client.
3. **Use the depositor, not the caller**: Associate the refund `BTCPendingInfo` with the original depositor (from `refund_request.deposit_msg`) rather than the executor, and check capacity against that account — but still exempt refunds from the withdrawal limit.

---

### Proof of Concept

1. Alice initiates a withdrawal via `ft_transfer_call` → `ft_on_transfer` → `create_btc_pending_info`. Her `btc_pending_sign_ids` now has 1 entry; `pending_sign_count() == 1`. [1](#0-0) 

2. Separately, Alice sent BTC to a deposit address but the relayer never called `verify_deposit`. Alice calls `request_refund` (after attaching the required NEAR deposit). The light-client proof succeeds and a `RefundRequest` is stored. [2](#0-1) 

3. After `refund_timelock_sec` seconds, Alice calls `execute_refund(utxo_storage_key, None)`.

4. Internally, `finalize_refund_with_psbt` is reached. It calls `self.require_pending_sign_capacity(&caller)` where `caller == Alice`. [3](#0-2) 

5. `pending_sign_count()` returns 1; `get_max_pending_sign_txs` returns 1 (default). The condition `1 < 1` is **false**. [4](#0-3) 

6. The call panics: `"Too many pending sign transactions"`. Alice's BTC deposit remains locked in `refund_requests` with no path to recovery until her withdrawal is finalized or a third party intervenes.

        &self,
        deposit_msg: DepositMsg,
        refund_address: String,
        tx_bytes: Base64VecU8,
        vout: usize,
        proof: TxInclusionProof,
        gas_fee: Option<u128>,

            env::attached_deposit() >= self.required_balance_for_request_refund(),
            "Insufficient deposit for storage"

            "tx_bytes too large for refund request"

        if let Some(msg_refund_address) = &deposit_msg.refund_address {

                msg_refund_address == &refund_address,

                .expect("Deserialization tx_bytes failed");

        let deposit_amount = u128::from(transaction.output()[vout].value.to_sat());

    pub fn get_max_pending_sign_txs(&self, account_id: &AccountId) -> u32 {
        self.data()
            .pending_tx_limits
            .get(account_id)
            .copied()
            .unwrap_or(1)
    }

    pub fn require_pending_sign_capacity(&self, account_id: &AccountId) {
        require!(
            self.get_account(account_id)
                .unwrap_or_else(|| {
                    env::panic_str(&format!("ERR_ACCOUNT_NOT_REGISTERED: {}", account_id))
                })
                .pending_sign_count()
                < self.get_max_pending_sign_txs(account_id),
